Steps（DAG）
  • 學習目標：理解系統設計面試在考什麼（問題解決、溝通、取捨判斷），以及它不是什麼（不是背答案、不是追求完美方案）。

    它考的不是你以為的

    系統設計面試跟演算法面試最大的不同：演算法有對錯，系統設計沒有。面試官給你一個開放式問題——「設計一個短網址服務」「設計一個聊天系統」——你不可能給出一個「完美」的答案，因為根本不存在。面試官評的不是結果，而是你的思考過程。

    三個核心評估維度：

    • 問題解決能力——拿到模糊問題後，能不能自己拆解成具體的、可設計的子問題
    • 溝通能力——系統設計面試是一場對話，不是獨白。你需要一邊思考一邊講
    • 取捨判斷——每個設計決策都有代價，選 SQL 犧牲水平擴展的便利，選 NoSQL 犧牲強一致性
    核心洞察 你做過 REST API、用過 Postgres 和 Redis，這些經驗不是用來「炫耀」的，而是用來建立連結的：當被問到快取設計時，你可以说「我之前在專案中用 Redis 做 session cache，但那個場景是 X，這裡是 Y，所以我選 Z」。

  • 學習目標：掌握系統設計面試的 7 步驟回答流程，並理解每一步的目標與時間分配。

    可複用的流程

    系統設計面試是開放式的，但不代表你可以隨便講。你需要一套可複用的流程：

    1. 需求澄清（~2 min）——核心功能是什麼、規模多大、需要支援哪些裝置
    2. 粗估（~3 min）——日活、峰值 QPS、資料量、讀寫比
    3. API 定義（~3 min）——系統對外暴露的 API
    4. 資料模型（~2 min）——SQL vs NoSQL、核心實體、索引
    5. 高階設計（~10 min）——5-6 個方塊的架構圖
    6. 詳細設計（~15 min）——面試官指定的深入組件
    7. 瓶頸分析（~5 min）——單點故障、擴展性瓶頸
    面試要點 步驟 7 瓶頸分析最容易被忽略，但面試官很看重。它展示你能自我批判——回頭審視自己的設計有沒有漏洞。

  • 學習目標：認識 DNS、LB、CDN、Cache 等常見元件，在設計中靈活選用。

    你的工具箱

    每個系統設計題，你都是從這個工具箱裡挑選組件來組裝：

    組件用途何時選用
    DNS網域名稱解析需要自訂網域
    Load Balancer分發流量到多台伺服器水平擴展
    CDN全球邊緣快取靜態資源、低延遲
    Cache記憶體/磁碟快取高頻讀取、重複計算
    Message Queue非同步任務處理解耦、削峰
    Database持久化儲存結構化資料

  • 學習目標：識別並避開忽略需求、太早深入細節、忽略取捨等常見錯誤。

    大多數人都會踩的坑

    • 忽略需求就開 design——沒搞清楚「要支撐多少用戶」就開始畫架構圖
    • 太早深入細節——面試官要你畫高階架構，你卻在討論資料庫欄位型別
    • 忽略取捨——只講「用 Redis」，不講「為什麼不用 Memcached」
    • 不跟面試官互動——45 分鐘獨白，面試官完全沒參與
    • 假裝什麼都懂——遇到不確定的技術假裝知道，不如大方說「這個我不確定，但我的推理是……」
    • 跳過瓶頸分析——設計完就停了，沒回頭檢視自己的方案
    • 沒有備案——只有一套方案，沒有 Plan B
    關鍵提醒 面試不是一個人的表演。每 5-10 分鐘就該跟面試官確認一次方向，讓對話自然流動。
