先檢查、別急著動手：用「只讀取」提示詞摸清環境

Step 1/4 · 版本控制與 MCP：讓每次 AI 編輯都能回復

這一步要完成什麼

用一句「只檢查、不做其他操作」的提示詞，請 agent 回報電腦上是否有 Git、目前專案能不能進行版本控制，以及為什麼要把「診斷」和「變更」拆開。

為什麼第一句話要叫 agent 什麼都別做

用自然語言驅動 coding agent，交出去的不只是問題，還可能是一組可執行的權限。你說「幫我整理專案」，它可能直接修改檔案、刪除目錄，甚至執行安裝指令。

問題是，你可能還沒看清楚現況，agent 的手已經伸進專案裡了。它動作很快，但快也可能把風險一起放大。

因此，整套流程的第一步要反過來做：先請它只看，不動。這一步不會產生成品，卻能先建立一張環境地圖，避免後面一邊猜、一邊收拾殘局。

這其實是在拆開兩種不同的工作：

  • 診斷：確認現在有什麼，原則上是唯讀操作。
  • 變更：修改或建立內容，會寫入環境，因此有風險。

先診斷，再決定是否變更，就像先打開引擎蓋檢查，再拿工具拆零件。

提示詞怎麼寫

示範中的兩個版本大致相同，關鍵都在最後那句限制：

幫我看一下目前專案所在的環境，是否可以把這個專案提交到本地的 git 倉庫。只幫我檢查，不做其他操作。
請你幫我看一下目前的電腦環境，有沒有 git 環境，是否可以把這個專案建立版本到本地的 git 倉庫。只幫我檢查，不要做其他任何操作。

「只幫我檢查」不是禮貌用語，而是行為規則。它把 agent 限制在安全範圍內：可以讀取、可以回報，但不能寫入。

少了這句，同一個問題可能得到這種回答：「好的，我幫你初始化了。」等你發現時，.git 或其他檔案可能已經被建立或修改。

一次好的檢查，應該回報什麼

請 agent 檢查時，至少要能回答這幾個問題：

  • 電腦上是否安裝 Git，以及目前的版本。
  • 這個專案資料夾是否已經在版本控制之下，也就是有沒有 .git 目錄。
  • 專案實際位於磁碟上的哪個路徑，避免 agent 檢查到另一個同名目錄。
  • 目前是否有任何因素，讓你還不能建立版本。

拿到這些答案，你就有了一張環境地圖。接下來要不要動手、應該從哪裡動手，都能根據現況決定，而不是靠猜。

唯讀與寫入，風險差在哪裡

可以把 agent 的動作分成兩類。

唯讀操作包括查看檔案、列出目錄，以及執行 git status。最壞的情況通常是 agent 解讀錯誤，但你的檔案內容不會因此改變。

寫入操作則包括修改檔案、刪除內容，以及執行 git push。這些動作會真的改變環境；一旦做錯，就需要還原、重建，甚至處理遠端影響。

「只檢查」提示詞的作用，就是先把 agent 綁在唯讀那一側。這在陌生目錄、剛接手的新專案，或剛完成環境設定的電腦上尤其重要。

如果你十分鐘前才確認過同一個資料夾，當然可以省略這一步；但面對陌生環境，先做一次唯讀診斷，是成本很低、卻能避免大麻煩的保險。
