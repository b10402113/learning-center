查歷史、做回退：AI 改壞了也能安全還原

Step 3/4 · 版本控制與 MCP：讓每次 AI 編輯都能回復

學習目標

你會請 agent 列出所有 Git 存檔紀錄，從中挑出一個 hash，再用白話指示它把專案回到那個版本。最後，你也能判斷：現在適合回退，還是應該繼續往前修。

存檔點要能派上用場

上一節已經建立 repo 和第一個存檔點。不過，存檔真正的價值，不在於「曾經存過」，而在於出問題時能把它叫回來。

想像一下：agent 原本把頁面做得可以執行，後來卻改到整個壞掉。你繼續叫它修，結果每修一次，錯誤就像打結的耳機線一樣越纏越緊。

這時最安全的做法不是硬撐著繼續修，而是先停手，回到一個已經確認能用的版本，再重新開始。

第一步：先把歷史攤開

請 agent 列出所有 Git 存檔紀錄：

查看所有 git 存檔記錄。

agent 會回傳一串清單，每一行代表一個存檔點。行首通常會有一組短代碼，例如 edd05fc。這就是該版本的 hash，可以把它想成存檔點的身分證號。

為什麼不用「第 3 版」這種流水號？因為 hash 是根據存檔內容計算出來的。同一份內容在不同機器上會得到同一組代碼；只要內容有任何改動，代碼就會完全不同。因此，hash 同時是版本編號，也能用來確認內容是否一致。

第二步：把 hash 貼進回退指令

從清單中挑好要回去的版本後，把那組 hash 原封不動貼給 agent：

回退 git 版本到 edd05fc。

這裡的重點不是背下 edd05fc，而是把上一個步驟看到的 hash 複製到下一個提示詞。agent 取得這組身分證號，就知道要回到哪一個存檔點。

整個流程使用白話指令就夠了，但順序不能亂：先查清單，再回退。查清單是唯讀動作，回退則會改變目前的工作狀態；你得先看清楚有哪些版本，才能選定要回去哪裡。

回退前，先確認有沒有要保留的改動

回退會把專案拉回舊狀態，也代表該存檔點之後的改動會離開目前的工作狀態。

所以執行前先問自己：這段期間有沒有其實想留下的內容？

  • 如果沒有要保留的東西，可以放心回退。
  • 如果有重要改動，先備份，或請 agent 用保留現場的方式處理，再進行回退。

這個確認只需要幾秒，卻能避免回退後才想起「剛才那段其實有用」。安全網的前提，是你清楚自己要回到哪一個版本。

該回退，還是繼續往前修？

不是每個錯誤都需要回退。可以用下面的準則判斷：

情況該怎麼做
小問題，方向正確，只是還沒完成繼續往前修，讓 agent 沿著同一個方向調整
越修越亂，已經偏離原本目標回退到上一個存檔點，再重新下指令
改動牽連太廣，修一處、壞三處先回退，再把需求拆小後重做
不確定目前離目標有多遠先回退到確定能用的版本，再重新檢查

回退是在控制損失：放棄一小段走錯的路，換回乾淨而確定的起點。對 vibe coding 來說，回退不是失敗，而是安全網。願意在適當時機退回去，反而能減少在混亂程式碼上反覆修補的時間。

小重現：完成一次「查歷史 → 選 hash → 回退」

現在實際做一次：先請 agent 查看所有 Git 存檔紀錄，從清單挑出要回去的 hash，確認沒有需要保留的改動後，再把該 hash 貼進回退指令。

完成後，你應該能做到一件具體的事：當 agent 把原本能跑的專案改壞時，不再盲目要求它繼續修，而是能先找到一個確定的版本，安全地回到那裡。
