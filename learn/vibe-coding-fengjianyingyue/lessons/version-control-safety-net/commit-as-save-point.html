把 commit 當存檔點：初始化 repo 與第一次存檔

Step 2/4 · 版本控制與 MCP：讓每次 AI 編輯都能回復

這一階段要完成什麼

你會讓 agent 在專案資料夾建立本地 git repo，確認不該進 repo 的檔案已排除，再完成第一次 commit。最後，你要能看懂這個 commit 在存什麼，以及為什麼它日後能當成回復點。

先把 commit 想成遊戲存檔

如果你玩過單機遊戲，就知道存檔點的用途：過了一個難關先存一次。之後打王失敗，讀檔重來，不必從頭開始。

版本控制裡的存檔點叫 commit（提交）。每個 commit 都記錄專案當下的狀態，並附上一句說明，告訴你這次改了什麼。

例如 agent 把一個頁面改壞了，你可以退回上一個 commit，回到它動手前的狀態。Vibe coding 之所以敢讓 agent 一次修改一大片，底氣就在這裡：最壞的情況通常是讀檔，而不是整個專案重做。

repo 是放存檔點的盒子

commit 要放在 git 倉庫（repository，簡稱 repo）裡。你在專案資料夾執行初始化後，裡面會多出一個隱藏的 .git 目錄；commit、差異與歷史都會記在這個目錄中。

所以「第一次存檔」其實有兩步：

  1. 先建立 git repo，做出放存檔的盒子。
  2. 再把目前的專案狀態存成第一個 commit。

順序不能顛倒：盒子還沒建好，存檔點就沒有地方可放。

完整實跑：從一句話到第一次 commit

1. 給 agent 的提示詞

先在目標專案資料夾開啟 agent，直接說：

把 xxx 這個專案，也就是本專案建立一個 git 倉庫，完成第一次存檔初始化。請先確認 `.gitignore` 是否排除不該進 repo 的檔案，再執行第一次 commit，commit message 請根據這次內容自動總結。

這句話把三件事放在同一個任務裡：初始化 repo、檢查排除規則、完成第一次存檔。若你想分開確認，也可以先只要求建立 repo，再要求第一次存檔。

2. agent 應該做什麼

正常流程會是：agent 先確認目前所在的是目標專案，建立或檢查 .git，查看 .gitignore，整理目前要納入版本控制的檔案，最後建立第一個 commit。

你不必只看 agent 回覆的「完成」。真正重要的是確認結果，而不是相信一句口頭報告。可以要求它回報：

  • repo 是否已初始化。
  • 哪些檔案會被納入第一次 commit。
  • 哪些檔案被 .gitignore 排除。
  • 第一個 commit 的 message 是什麼。

3. 你應該看到的結果

完成後，專案資料夾應該有一個 .git 目錄，並且已經存在第一個 commit。agent 自動產生的 commit message 應該能概括這次初始化內容，而不是只有「改一下」這種無法辨識的句子。

你也可以再說：

使用 git 存檔，備註請你自動總結。

這會把目前尚未存下來的變更建立成新的 commit。之後每次完成一個可運作、也能清楚說明的進度，就可以用同樣的說法存檔。

為什麼提示詞用「存檔」，不直接用「commit」

這是刻意的用詞。vibecoding 的溝通原則，是用你已經理解的語言下指令，再讓 agent 把它對應到技術操作。

你只要知道「現在要把這個進度存起來」，不必先背熟 git 術語，才能使用 git。對你來說是存檔；對 agent 來說，對應的動作就是建立 commit。

為什麼 commit message 可以交給 agent

commit message 的用途，是讓未來的你或隊友快速知道這個版本做了什麼。自己手寫很容易變成「修 bug」「改一下」，過幾天回頭看，幾乎沒有辨識力。

agent 能查看這次的差異（diff），知道哪些檔案被修改、實際改了什麼，再根據差異產生摘要。你負責決定「這個進度要存檔了」，摘要則交給它處理。

不過，摘要不是審核。若 agent 把不該納入的檔案一起提交，commit message 寫得再漂亮也沒有用。存檔前仍要看一次變更範圍，特別是設定檔、金鑰與環境變數。

存檔顆粒度：別一次存太多，也別每一行都存

太粗，例如整個階段只存一次，某個地方壞掉時就得退回很遠；太細，例如每改一行就存一次，歷史會被瑣碎紀錄淹沒。

比較實用的判斷方式是：當你完成一個「能跑，也能清楚說明做了什麼」的進度，就存一次。像是完成一個頁面、修好一個明確的流程，或完成一次可驗證的初始化。這樣每個 commit 都像一個可辨識的存檔點，而不是滿地散落的小紙條。

第一次存檔前，先擋住兩種風險

不要把大型產物存進 repo

常見例子是套件目錄 node_modules。它通常體積很大，也能透過套件描述重新安裝，沒有必要塞進版本歷史。這類檔案應該列在專案根目錄的 .gitignore 中。

不要把敏感資訊存進 repo

例如放著金鑰或環境設定的 .env。一旦被 commit，敏感資訊可能跟著版本歷史留下來；事後刪掉目前檔案，也不代表歷史中的內容自動消失。

因此第一次動手前，先對 agent 說：

第一次存檔前，請檢查 `.gitignore`，確認 `node_modules`、`.env` 與其他不應提交的檔案不會進入 repo；若發現可能包含敏感資訊的檔案，先停下來告訴我，不要直接 commit。

這不是多餘的防護，而是初始化流程的一部分。先建立正確的排除規則，通常比事後清理版本歷史省事得多。

小重現：自己驗證這個存檔點

讓 agent 完成第一次 commit 後，請它回報目前的 commit 歷史與尚未存檔的變更。你要確認三件事：

  1. repo 確實已建立。
  2. 第一個 commit 確實存在，而且 message 能說明初始化內容。
  3. .env、node_modules 等不該提交的檔案沒有被納入。

如果這三件事都成立，你就完成了本階段真正重要的結果：專案現在有一個可辨識、可回復的第一個存檔點。之後讓 agent 大幅修改前，先存檔；修改後確認能跑，再存下一個檔案。
