先讓 agent 檢查，再讓它動手設定環境

Step 3/3 · 工具鏈就緒：Claude Code / Node / git / JDK+Maven

檢查和設定，像看診與開藥

前兩步的環境安裝，可以自己一步步完成，也可以交給 agent 協助。不過，先把兩種工作分開：檢查環境是只讀操作，設定環境是寫入操作。

比較安全的流程是：先請 agent 回報現況，確認缺少什麼，再決定要不要讓它修改。這就像先量血壓、看檢查報告，再開藥，而不是一進門就把整個藥櫃搬回家。

這樣做有兩個好處：你知道它改了什麼，也不會在還沒搞清楚狀況時，讓它擅自修改 PATH 或安裝其他工具。

第一階段：只讀檢查，先把邊界講死

agent 通常很主動。它發現環境少了東西，可能不只回報問題，還會順手下載 JDK、修改環境變數。你只想先知道現況時，提示詞要明確寫出「只檢查，不做其他操作」：

請你檢查本機的 Java 開發環境是否就緒。
只檢查，不做其他操作。

這句限制看似簡單，卻是關鍵。agent 應該停在診斷階段，只回報 Java 是否安裝、安裝位置與版本，把下一步的決定權留在你手上。

同樣的做法也能用來檢查 git：

幫我看一下當前電腦環境有沒有 git，
以及這個專案能不能建立成版本庫。
只幫我檢查，不要做其他任何操作。

風險提醒：如果沒有寫清楚「只檢查」，agent 可能把「發現問題」直接理解成「立刻修好」。這不一定符合你的預期，也可能改到 PATH、專案設定或其他既有環境。

第二階段：寫入設定，路徑由你提供

確認需要補環境變數後，才進入寫入操作。這時的分工很清楚：你負責告訴 agent 工具實際放在哪裡，它負責處理作業系統的設定方式。

路徑不能讓 agent 猜。你可能把 JDK 解壓在自訂資料夾，agent 不知道那個位置，猜錯就會把環境變數指向不存在的目錄。相對地，macOS 要寫入 ~/.zshrc、Windows 要修改系統環境變數、Linux 要看目前使用的 shell，這些系統差異正適合交給 agent 處理。

我已經下載了 JDK，目錄在 /你的/實際/路徑，
請你根據我的作業系統設定這個 JDK 的環境變數。

我已經下載了 Maven，目錄在 /你的/實際/路徑，
請你根據我的作業系統設定這個 Maven 的環境變數。

這裡最重要的是兩件事：路徑要填成真實位置，而且要明確要求它依照你的作業系統設定。如此一來，你不用自己背 macOS、Windows、Linux 各自要修改哪個檔案，但也不會把路徑這個關鍵資訊交給 agent 猜。

第三階段：agent 說完成，不代表真的生效

agent 回報「設定好了」，只是代表它執行過寫入指令，不代表目前的終端機已經讀到新設定。

環境變數通常會在 shell 啟動時載入。agent 剛把設定寫進檔案時，你原本開著的終端機仍可能使用舊值。因此要做兩件事：

  1. 開一個全新的終端機，或執行 source ~/.zshrc，重新載入設定。
  2. 執行版本命令，確認實際使用的工具與路徑。

以前面的 JDK 與 Maven 為例：

java -version
mvn -version

尤其要看 mvn -version 輸出的 Java version 那一行，確認 Maven 使用的 Java，正是你交給 agent 的那一套。

如果版本不對，可能是設定尚未生效，也可能是另一套 Java 排在 PATH 前面。這時要回頭檢查 PATH 順序與 JAVA_HOME。這一步不是多餘的收尾，而是唯一能證明「設定真的正確」的實跑驗證。

把流程固定成三步

換新電腦、重灌系統，或第一次接手公司的開發環境時，都可以重複這個流程：

  1. 檢查：請 agent 只讀地回報環境現況。
  2. 設定：由你提供實際路徑，讓 agent 依作業系統完成設定。
  3. 複驗：開新終端機，再執行版本命令確認結果。

只有三步都完成，你才是真的掌握這台機器的工具鏈，而不是只看著 agent 的一句「完成」就相信它。

診斷與變更要分開，是整條 vibe coding 流程都適用的安全習慣：先讓 agent 只讀地報告現況，再由你決定是否寫入，最後親自驗證結果。
