角色化資料夾骨架：先把整條產線排好，agent 才知道該往哪裡走

Step 1/4 · 專案骨架與 agent 說明書：角色化資料夾、AGENTS.md 與 CLAUDE.md

學習目標

完成這一步後，你要能替新產品規劃一套以角色命名的資料夾骨架，說清楚每個資料夾該放什麼，也能解釋為什麼這種排法能讓你和 coding agent 都更快找到正確位置。

先處理最常見的問題：檔案找不到

一個人做完整個產品時，最容易失控的通常不是能力，而是秩序。你可能同時是產品經理，要寫需求；也是設計師，要畫畫面；還要當前端、後端、DBA，最後負責測試、交付與營運。

每一種工作都會產生檔案。若所有內容都塞在同一層，三個月後連自己都可能分不清楚哪個檔案屬於哪個階段。

用白話提示 agent 寫程式，只會讓這個問題更明顯。agent 不會記得你昨天把需求放在哪裡，它當下能依賴的線索，主要就是目前看到的目錄與檔名。資料夾沒有把「這是什麼」寫在名字上，它就得自行猜測；猜錯時，新頁面可能就被丟到資料庫腳本旁邊。

因此，開工的第一件事不是立刻寫程式，而是先把整條產線排成一個專案。這就是角色化資料夾：每個交付階段各自有一個資料夾，名稱直接說明這個階段由哪個角色負責。

角色化資料夾長什麼樣？

以「財務管家」示範專案為例，整個專案分成十二個編號資料夾。前三位數字代表流程順序，括號則標示負責的角色：

資料夾角色裝什麼
001.产品PRD（产品经理）產品經理需求文件、功能清單、成功指標
002.产品UI原型（美术设计）美術設計畫面原型、設計 token、配色與字體
003.前端代码（前端工程师）前端工程師頁面、共用 JS、樣式；後端 Node 也放在這裡的 backend/
004.数据库脚本（数据库管理员DBA）DBA建表、view、預存程序、種子資料
005.后端代码（Java工程师）Java 工程師企業級後端：Spring Boot + MyBatis
006.后台管理系统（运营专员）營運專員另一組 API 與後台靜態頁
007.跨端APP应用（移动端开发工程师）移動端工程師uni-app 專案
008.项目测试（测试工程师）測試工程師測試計畫、測試報告、測試工程設定
009.交付与上线（交付经理和运维人员）交付與運維產品說明書、上線文件
010.内容运营內容營運PPT、路演、營運手冊、說明書
011.数据可视化資料視覺化儀表板、圖表資料、營運報告
012.文案推广推廣推廣文案、宣傳影片

把這些資料夾畫成樹狀結構，就像一條從「定義產品」一路走到「把產品推出去」的流水線：

claude-my-product/
├── AGENTS.md            # 給 agent 的專案說明書（下一步會寫）
├── CLAUDE.md            # 同一份內容，給另一個 agent
├── skills-lock.json     # 釘住第三方技能的版本
├── 001.产品PRD（产品经理）/
├── 002.产品UI原型（美术设计）/
├── 003.前端代码（前端工程师）/
│   ├── frontend/
│   └── backend/
├── 004.数据库脚本（数据库管理员DBA）/
├── 005.后端代码（Java工程师）/
├── 006.后台管理系统（运营专员）/
├── 007.跨端APP应用（移动端开发工程师）/
├── 008.项目测试（测试工程师）/
│   ├── 测试计划/
│   ├── 测试报告/
│   └── 测试工程配置/
├── 009.交付与上线（交付经理和运维人员）/
├── 010.内容运营（自媒体与运营）/
├── 011.数据可视化/
└── 012.文案推广/

為什麼按角色分，而不是按技術分？

另一種常見排法，是建立一個 frontend/、一個 backend/，再加上一個 database/。這種「按技術分」的方式很直覺，適合你已經確定要用哪些技術，也只需要在技術邊界內管理程式碼的情境。

但當你一個人負責整條產線時，真正容易迷路的往往不是技術，而是階段：需求文件在哪裡？測試計畫放哪裡？交付文件又在哪裡？

按角色分，資料夾名稱直接回答兩個問題：「這個階段誰在做事？」以及「這個階段會產出什麼？」你換一頂帽子，就切換到對應的資料夾。對 agent 來說也一樣：看到 008.项目测试（测试工程师），它就有明確線索，知道測試計畫應該放在這裡，而不是塞進前端的 pages/。

編號還有一個額外作用：它本身就是流程圖。從 001 到 012，表示這門課要走過的十二個階段。只要看一眼資料夾清單，就像拿到一份 playbook 的目錄。

編號與命名有三個注意事項

第一，順序要對得起內容。編號是用來表示閱讀與執行順序的。如果 005 經常要回頭修改 002，可能表示兩個階段的界線沒有切好，或其實應該把它們合併。編號不是裝飾，它應該能預測你下一步會打開哪個資料夾。

第二，一個階段一個家，不要開分身。示範專案裡曾出現兩個以 010.内容运营 開頭的資料夾，一個標示「自媒體與運營」，另一個標示「自媒體與運維」。重複編號或相似名稱，很容易讓 agent 走錯門；它可能挑到第一個符合的資料夾，然後把檔案放錯位置。每個階段的名稱都應該唯一、好辨認。

第三，不要為了對齊而建立空殼。一開始不必把十二個資料夾全部建立好，先建立目前階段真正會用到的資料夾即可，其他等流程走到再開。空資料夾不會自動幫 agent 找到答案，反而可能讓它以為那裡已經有可用內容。

根目錄放的是規則，不是階段產出

你可能會注意到，樹狀結構的根目錄除了十二個角色資料夾，還有 AGENTS.md、CLAUDE.md、skills-lock.json，以及隱藏的 .claude/ 和 .agents/。

這些檔案不是某一個階段的產出，而是整個專案的設定：它們用來告訴 agent 這個專案是什麼，以及有哪些能力可以使用。

把「規則」放在根目錄，把「產出」放在角色資料夾，這條界線一旦固定，之後建立新專案就不必每次重新設計。根目錄複製必要的設定，角色資料夾則依照實際階段逐步建立。

這一步要交出什麼？

完成這一步，你應該能交出一張自己的資料夾清單。不一定要有十二個階段，但每個名稱與順序都要能回答兩個問題：

  • 這個階段由誰負責？
  • 這個階段會產出什麼？
