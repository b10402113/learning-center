AGENTS.md 與 CLAUDE.md：給 coding agent 的專案說明書

Step 2/4 · 專案骨架與 agent 說明書：角色化資料夾 + AGENTS.md/CLAUDE.md

學習目標

完成這一步後，你應該能寫出一份實用的 agent 說明書，交代專案概述、檔案結構、開發指令、技術棧、設計系統與資料模型；也能用內容相同的 AGENTS.md 與 CLAUDE.md，讓不同的 coding agent 讀到同一套規則。

每次開工，agent 都像第一天上班

coding agent 有個很容易被忽略的特性：它不記得昨天。你昨天花十分鐘解釋「這個專案用 localStorage，不要加後端」，今天換一個對話，它可能全部忘光，又從零開始猜。

沒有專案說明書時，agent 主要依賴兩種線索：你這次下的指令，以及它掃到的檔案。這兩種線索都不一定可靠。

例如，你只說「幫我加一個記帳頁面」，agent 可能看到 PRD 裡完整的多表後端規格，就直接朝資料庫與後端服務前進。它不會自動知道：V1 其實只要一個單頁 HTML。

專案說明書就是放在根目錄的工作簡報，明確寫下「這個專案是什麼、現在做到哪裡、有哪些規矩」。agent 每次開工先讀它，你就不用每天重新說明一次。

為什麼要有兩個檔案：AGENTS.md 與 CLAUDE.md

示範專案的根目錄同時放著 AGENTS.md 與 CLAUDE.md。兩份內容幾乎一模一樣，只差開頭的自我介紹：

  • AGENTS.md 說明這份文件是給 Codex 在此程式碼庫工作的指引。
  • CLAUDE.md 說明這份文件是給 Claude Code 在此程式碼庫工作的指引。

原因很直接：不同的 coding agent 有各自慣用、約定要讀的檔名。Codex 讀 AGENTS.md，Claude Code 讀 CLAUDE.md。準備兩份，就像把同一份簡報放上兩張不同顏色的名牌，讓兩個 agent 都能收到。

這不是把規則拆成兩套，而是「內容相同、入口不同」。實務上最簡單的維護方式是先寫好一份，再複製成另一份，只改開頭那一行的 agent 名稱，避免兩份內容慢慢分叉。

說明書要回答哪六個問題？

這份檔案不是行銷文案，也不是把整個程式碼庫搬進來的百科全書。它是 agent 動手前會讀的工作簡報，至少要回答下面六個問題，而且越具體越好：

區塊回答的問題示範專案寫了什麼
專案概述這東西是什麼？一個名為「財務管家」的個人財務管理網頁應用，單頁 HTML，無需建置系統
專案結構檔案放哪？主應用檔 + PRD 資料夾的樹狀圖
開發指令怎麼跑、怎麼測？直接用瀏覽器開、存檔重新整理、npx serve . 或 python -m http.server 8000
技術棧用什麼做？原生 HTML/CSS/JS、Chart.js（CDN）、Google Fonts、localStorage
設計系統視覺規矩是什麼？粉嫩主題，主色櫻花粉 #FFB7C5、收入薄荷綠 #7DD3C0、支出珊瑚紅 #FFA09B
資料模型資料長什麼樣？交易與帳戶兩個物件的欄位定義

先把啟動與驗收方式寫清楚

「開發指令」常被當成小事，卻直接決定 agent 能不能自己驗收。它如果不知道專案怎麼啟動，就只能盲改；改完也不知道畫面或功能是否真的正常。

示範專案是純 HTML，沒有建置流程，因此指令很短：

# 查看應用：直接用瀏覽器開啟 財務管家.html
# 測試更改：存檔後重新整理瀏覽器
# 本地伺服器（可選）：
npx serve .
python -m http.server 8000

你可以把這一段想成新同事第一天一定會問的三件事：怎麼啟動、怎麼修改、怎麼確認修改有效。寫進說明書，agent 就不用猜，也不用反覆問你。

設計系統與資料模型：把已拍板的決定釘住

agent 很會發明。你沒有指定顏色，它就自己挑一組；你沒有指定欄位，它可能自行加上 note。這不一定是能力不足，而是它缺少「哪些事情不能自行決定」的界線。

設計系統與資料模型的價值，就是把已經拍板的決定寫下來，讓 agent 沿用現有規格，而不是每次都重新創作。

示範專案的資料模型是一組明確的欄位：

// 交易記錄
{
  id: string,
  type: 'expense' | 'income',  // 支出或收入
  category: string,            // 分類ID
  amount: number,              // 金額
  account: number,             // 帳戶ID
  remark: string,              // 備註
  date: ISO string             // 日期
}

// 帳戶
{
  id: number,
  name: string,     // 帳戶名稱
  type: string,     // 帳戶類型
  icon: emoji,      // 圖示
  balance: number   // 餘額
}

設計系統也要寫得夠具體。除了主色，還應交代收入色、支出色與強調色，以及開發時不能忽略的限制：

  • 所有程式碼都放在同一個 HTML 檔，檔案約 48KB。
  • 資料存放在 localStorage 的 financeData 鍵下。
  • 使用 CSS 自訂屬性處理主題。
  • 使用 prefers-color-scheme 支援暗色模式。
  • 採行動優先設計，最大寬度為 480px。

這些規則像鐵軌：agent 可以在軌道上加功能，但不會每次都把路線改掉。

說明書也在決定「現在做哪一版」

這個示範專案有一個很值得記住的對照。它的 PRD 描述的是完整系統：包含多表後端與資料庫；但 AGENTS.md 把 V1 鎖定為「使用 localStorage 的單頁 HTML」。

兩份文件並不矛盾，因為它們回答的是不同問題：

  • PRD 說明「產品最終可能長什麼樣」。
  • AGENTS.md 說明「目前這一版實際要做什麼」。

agent 每天開工讀的是後者，因此它會照規則做單頁 HTML，不會自作主張先幫你開一個 MySQL。

這就是專案說明書最重要的作用：把當下的實作目標釘在文件裡，而不是只放在你的腦中。如果沒有這一層，agent 往往會把內容最完整的文件當成眼前目標，結果一次跳過好幾個版本。

說明書是工作簡報，不是百科全書

先記住第一個界線：AGENTS.md 不需要貼滿程式碼，也不需要鉅細靡遺地解釋所有背景。它只要放進 agent 動手前一定得知道的事。內容太長，重點反而像被塞進雜物箱，agent 可能抓不到真正重要的規矩。

第二個界線更危險：過期的說明書，可能比沒有說明書更糟。

假設專案已經從單頁 HTML 改成前後端分離，但你忘了更新技術棧。agent 仍會按照舊規則修改，甚至把舊文件當成依據來反駁你的新指示。

因此，只要架構或開發流程改變，就先更新 AGENTS.md 與 CLAUDE.md，再叫 agent 動手。完成這件事後，下一次對話就不必重新猜專案的玩法。
