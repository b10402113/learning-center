換成你的產品：從專案骨架到第一份 AGENTS.md

Step 4/4 · 角色化資料夾與 agent 說明書：AGENTS.md／CLAUDE.md

學習目標

把角色化資料夾與 agent 說明書套到自己的產品，完成第一版可用的 AGENTS.md 與專案骨架清單；同時分清楚哪些資訊一定要寫，哪些還不知道、應該先留白。

前情提要：三塊零件，現在要組起來

前三步各自處理了一件事：角色化資料夾回答「東西放哪裡」；AGENTS.md／CLAUDE.md回答「agent 需要知道什麼」；skills-lock.json回答「agent 的能力從哪裡來」。現在把三者接起來，換成你自己的產品。

這次的實作載體是知識影片生成 agent：素材進來，中間產出 HTML slides 或文章，最後生成一支全動畫的知識影片。它不像記帳 App 那樣明確切成十二段，但一樣有「輸入、加工、輸出、驗收、發佈」幾個關卡。你要做的，就是替這條產線排出一套能工作的角色骨架。

第一步：先畫出角色資料夾

不要急著照抄財務管家的十二個資料夾。先沿著產品的產線往前走一遍：素材會經過哪些階段？每個階段由誰負責？會留下什麼產出？以知識影片為例，可以先從這樣的切法開始：

knowledge-video-agent/
├── 001.素材与选题（内容企划）/
├── 002.脚本与分镜（编导）/
├── 003.模板与设计（视觉设计）/
├── 004.生成管线（工程）/
├── 005.渲染与动画（动画工程）/
├── 006.校对与测试（QA）/
├── 007.交付与发布（运营）/
├── AGENTS.md
├── CLAUDE.md
└── skills-lock.json

重點不在資料夾有幾個，而在於每一個名稱都能立刻對應到工作內容。看到 003.模板与设计（视觉设计），你應該能說出：「這裡放設計 token、版型與插圖規範。」看到 006.校对与测试（QA），則應該能說出：「這裡放真實斷言、失敗截圖與測試報告。」

如果你說不出某個資料夾要收什麼，它就像還沒貼標籤的抽屜：先別急著建立，代表這個階段還沒想清楚。

根目錄則要和財務管家的做法對齊：放規則，不放各階段產出。AGENTS.md、CLAUDE.md 與 skills-lock.json 從第一天就放在最上層；角色資料夾才用來收各階段的成品與工作物。

第二步：寫出第一份 AGENTS.md

可以先用六個區塊搭骨架，再逐格填入專案事實。括號中的內容換成你的資訊；還不知道的地方先寫 TBD，不要替 agent 猜一個假的答案。

# AGENTS.md

本文件為（你的 agent 名稱）在此代碼庫中工作提供指導。

## 專案概述
（一句話：這是什麼產品、給誰用、現在這版做到哪。）

## 專案結構
（把第一步的角色資料夾樹貼進來，每個資料夾一句話說明。）

## 開發指令
（怎麼啟動、怎麼改、怎麼驗證。三件事各一行。）

## 架構
### 技術棧
（前端、後端、資料庫、關鍵套件；沒有後端就寫沒有。）
### 設計系統
（主色與語意色的 hex、字體、間距規則。）
### 資料模型
（核心物件的欄位定義；先寫 V1 真正會用到的那幾個。）

## 開發注意事項
（容易踩雷或已拍板的決定：資料存哪、有哪些模式要沿用、
 哪些東西這版先不做。）

有幾格是「寧可留白，也不要亂寫」。例如技術棧還沒定案，就老實寫：「V1 先用單頁 HTML 原型，未定後端。」這比假裝已經有完整架構安全得多，因為 agent 會把說明書當成施工規則。

前面看過的反面例子正好說明這點：PRD 寫著多表後端，說明書卻把 V1 鎖成單頁 HTML。規則一致時，agent 才能做出正確版本；規則互相打架時，它只會在錯的方向上努力。

第三步：把設定當成會長大的東西

第一版 AGENTS.md 不可能一次寫完。專案今天加了後端，就補上技術棧；明天發現 agent 老是把圖表頁做成另一種風格，就把「圖表一律沿用 003.模板与设计 裡的 token」寫進開發注意事項。

每一次 agent 做錯，都可能是一條應該補進說明書的規則。與其在每次對話裡重複糾正，不如把修正寫進檔案，讓下一次開工直接吃到這條經驗。

技能也用同樣的節奏管理。還沒安裝任何第三方 skill 時，skills-lock.json 可以是空的，甚至先不建立。等第一次從 GitHub 引入技能，再替它記下 source、skillPath 與 computedHash。這是一筆低成本的紀錄：之後 agent 行為出現異常時，你至少知道它用了哪個技能版本。

怎麼知道第一版真的有用？

設定檔不是寫完就算。把 AGENTS.md 放進 repo 根目錄，開一個新的 agent 對話，請它先讀過說明，再交一件小任務，例如：「照目前的 token 生成一個統計頁的 HTML。」接著觀察兩件事：

  • 它有沒有去正確的位置找資料、放檔案？如果檔案被丟進錯的資料夾，代表專案結構寫得還不夠清楚。
  • 它有沒有沿用已經拍板的決定？如果它自行發明一組顏色或欄位，代表設計系統或資料模型仍有缺口。

這就是你的回饋迴路。agent 每次走偏，就回頭修說明書，而不是只在當下的對話裡把它拉回來。修正一次，之後每次開工都能受益。

走完這節，你手上會有什麼？

你會得到一張自己的角色資料夾清單、一份填好六個區塊的 AGENTS.md（以及它的鏡像 CLAUDE.md），還有把技能當成依賴管理的習慣。

這三樣東西合起來，就是「專案骨架與 agent 說明書」的完整產出：下一次換產品時，不必從空白畫布開始，只要沿著同一套方法重新排出產線，並把已經確定的規則交給 agent。
