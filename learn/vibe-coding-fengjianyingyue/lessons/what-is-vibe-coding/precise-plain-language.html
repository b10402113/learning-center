讓白話變精確：用說明書、逐頁規格與計畫引導 agent

Vibe Coding · 什麼是 vibe coding · Step 3/4

學習目標

這一階段要學會三種把白話收斂成可執行指令的方法：

  • 用 agent 說明書固定技術棧與資料模型
  • 用逐頁功能規格把畫面拆成可驗收的項目
  • 要求 agent 先做計畫，再開始寫程式

為什麼一句「做個好看的首頁」不夠？

你對 agent 說：「做一個好看的首頁。」它確實做出了一個首頁，但打開後可能和你想像的完全不同。

問題不一定是 agent 不聽話，而是這句話留下太多空白：

  • 「好看」是誰的標準？
  • 首頁要顯示哪些資料？
  • 金額要從哪裡取得？
  • 哪些內容完成後才算交付？

這些地方沒有指定時，agent 只能自行猜測。你以為自己交代了方向，它聽到的卻像是一張沒有路名的地圖。

讓白話變精確，不代表要寫一份厚重的規格書。更實用的做法，是準備幾個小道具，把自由發揮的範圍縮到可以實作、也可以驗收。

第一個道具：agent 說明書

在專案根目錄放一份 AGENTS.md 或 CLAUDE.md，用來寫下這個專案「不變的事」。agent 每次開始工作前讀取它，就不用每次重新猜測專案的基本規則。

財務管家的 AGENTS.md 與 CLAUDE.md 內容相同，一份提供給 Codex，另一份提供給 Claude Code。裡面固定了這些資訊：

  • 這是一個單頁 HTML App，沒有建置流程，直接用瀏覽器開啟即可執行
  • 技術棧是原生 HTML、CSS、JS，圖表使用從 CDN 載入的 Chart.js
  • 資料儲存在瀏覽器的 localStorage，鍵名是 financeData
  • 版面採手機優先，最大寬度為 480px
  • 交易資料模型是 {id, type, category, amount, account, remark, date}
  • 帳戶資料模型是 {id, name, type, icon, balance}

其中，資料模型特別關鍵。它先定義「一筆交易長什麼樣」，之後首頁、明細頁與統計頁都使用同一組欄位，不會每個頁面各自發明一套資料格式。

技術棧那一條也在限制 agent 的想像力。財務管家的 PRD 描述了一套多表的後端架構，但說明書把 V1 的實作方向固定為「一個使用 localStorage 儲存資料的單頁檔案」。這表示 agent 不應自行把專案擴張成另一套後端系統。

完整實跑：先用說明書固定方向

提示詞：

請先讀取專案根目錄的 AGENTS.md，依照其中的技術棧、資料儲存方式與資料模型工作。不要自行改成後端架構，也不要新增說明書沒有指定的資料格式。

agent 行為：

agent 會先把說明書當成專案的邊界條件，知道這個 V1 應該是能直接用瀏覽器開啟的單頁 HTML App，資料要從 localStorage 的 financeData 取得，交易與帳戶也要沿用既定欄位。

產出結果：

後續產出的功能會朝既有方向延伸，而不是自行改用另一套技術或資料模型。這就是說明書的作用：它不是在教 agent 每一行怎麼寫，而是在專案入口放一扇門，告訴它哪些路不能走。

第二個道具：逐頁功能規格

agent 說明書負責固定整個專案的基本規則；逐頁功能規格則負責說清楚某一個畫面要完成什麼。

不要只說「做一個統計頁」，而要把畫面拆成可以逐條檢查的功能。以財務管家的首頁為例，可以拆成三個區塊：

  1. 顯示本月標題，例如「2028 年 12 月」，以及本月收入、支出、結餘三個數字
  2. 顯示本月支出金額最高的前三名分類
  3. 依時間排序，顯示最近三筆交易

這三條都能直接打開畫面確認。規格還必須講清楚：數字要從真實資料計算，不能放一組看起來像真的假資料。

統計頁也可以拆成五個獨立項目：

  1. 年份選擇
  2. 年度收入、支出與結餘
  3. 分類圓餅圖
  4. 12 個月折線圖
  5. Excel 匯出

完整實跑：把「做統計頁」拆成驗收清單

提示詞：

請製作財務管家的統計頁，並逐項完成以下功能：年份選擇、年度收支結餘、分類圓餅圖、12 個月折線圖，以及 Excel 匯出。所有數字與圖表都必須根據真實資料計算，不要使用假資料。完成後，請逐項回報每個功能的實作狀態。

agent 行為：

agent 不再只接收一個模糊的「統計頁」目標，而是取得五個可以分開處理與檢查的工作項目。它也知道圖表與數字不能只是畫面上的裝飾，必須連到真實資料。

產出結果：

你可以依序檢查年份選擇、年度數字、圓餅圖、折線圖與匯出功能，而不是看到一個外觀完整的頁面，就猜測裡面是否真的做完。

第三個道具：先要計畫，再寫程式

第三個道具不是檔案，而是提示詞的順序。直接要求 agent 開始寫程式，等於先讓它蓋房子，再問它打算把樓梯放在哪裡。

你可以明確要求：

不要立刻寫程式，先輸出計畫。

課程中的測試提示詞就是從這個方向開始。它要求 agent 先分析三種客戶端：

  • 前端
  • 後端
  • 跨端 App

接著，各自找出技術棧、專案結構與啟動方式，再整理核心業務模組與高風險功能，最後設計分層測試計畫。重點是每個專案各有一份計畫，不是把所有專案混成一張清單。

完整實跑：先審查測試計畫

提示詞：

不要立刻寫測試程式。請先分析前端、後端與跨端 App 的技術棧、專案結構和啟動方式，找出核心業務模組與高風險功能，再為每個專案分別提出一份分層測試計畫。

agent 行為：

agent 會先整理分析與測試方向，而不是直接產生一批測試檔案。你可以先檢查它是否理解三種客戶端的差異、是否抓到核心業務模組，以及高風險功能是否被列入測試範圍。

產出結果：

你得到的是一份可以先審查的計畫。若方向錯了，只需修改提示詞或計畫內容；不必等 agent 寫完大量程式，才發現它測錯東西。

為什麼要先計畫？

計畫是成本最低的驗收點。計畫錯了，通常改幾行文字就能修正；程式錯了，可能得回頭拆解大量程式碼。

因此，先要計畫不是多一道形式上的流程，而是把檢查時間往前移。錯誤越早被看見，修正成本越低。

要注意的 AI 失敗模式：規格清楚，不代表功能已交付

規格寫得清楚，仍然不代表 agent 已經把功能做完。課程裡就有一個很醒目的例子：功能規格完成後，「明細、統計、首頁」的功能又被重新列在「目前缺失以下功能」之下。

這代表規格與交付是兩件不同的事：

  • 規格：告訴 agent 應該做什麼
  • 交付：確認功能是否真的存在、能否使用

這也是 AI 生成碼常見的風險：agent 可能完成了部分工作，卻回報整體完成。尤其當畫面看起來完整時，更容易產生錯覺。

因此，驗收不能只看 agent 的回覆，也要逐項打開功能確認。發現缺漏時，再下一個範圍明確的指令，直到實際結果符合規格。

三個道具要一起使用

道具 放在哪裡 解決什麼問題
agent 說明書 專案根目錄的 AGENTS.md / CLAUDE.md 固定技術棧、結構、慣例與資料模型，避免每次重新說明
逐頁功能規格 寫給 agent 的功能清單 把「做一個頁面」拆成可以當場驗收的項目
先計畫再寫碼 每次動工前的第一句提示詞 把審查往前移，在計畫階段攔下錯誤方向

這三個方法都不複雜，真正困難的是每次都記得使用。說明書固定不變的邊界，逐頁規格說清楚這次要交付什麼，計畫則讓你在程式產生前先檢查方向。

當你能從 agent 得到「依照固定技術棧產出的程式」、「逐條可驗收的功能」，以及「可以先審查的實作計畫」，白話就不再只是願望，而會變成真的能執行、也真的能決定是否完成的指令。

來源

本課的 agent 說明書內容與資料模型取自財務管家的 AGENTS.md；逐頁功能規格與「目前缺失以下功能」取自功能點梳理；先計畫再寫碼與分層測試計畫取自測試提示詞。
