什麼時候該從白話快跑升級成 SDD？

Vibe Coding · 什麼是 vibe coding · Step 4/4

先學會換檔，而不是選邊站

vibe coding 和工程化的 SDD，不是互相取代的兩派，而是同一台車的兩個檔位：路平、方向還在探索時，可以先輕快前進；遇到陡坡、彎道或載著貴重貨物，就要換成更穩的檔位。

這一課的目標，是讓你能根據風險、規模、協作方式與正確性要求，判斷何時該從白話快跑升級成 SDD，並知道升級時要交接哪些東西。

SDD 多了哪些關卡？

SDD（spec-driven development，規格驅動開發）就是先把需求寫清楚，再拆成一張張可以獨立完成的小單子（ticket），逐張實作，完成後再回頭審查。

相較於白話開發，SDD 多了幾道關卡：需求釐清、規格、tickets、實作與 review。代價是速度慢一些；換來的則是每一步都有紀錄，日後能追查「當時為什麼這樣做」。

你已經在其他課程學過這套流程：反覆盤問需求、寫成規格、拆成 tickets、實作，再 review。這一課不再教你怎麼做 SDD，而是練習判斷什麼時候值得切換到 SDD。

什麼時候白話快跑就夠？

如果你還在探索方向，白話快跑通常比較划算：

  • 點子還在驗證，連自己都還不確定真正要什麼
  • 只是一次性的小工具、個人使用工具或內部演示
  • 做錯了可以直接刪掉重來，而且重來成本很低
  • 需求會持續變動，現在把規格寫死反而會綁住後續嘗試

這些情況有一個共同點：出錯後，回頭重做很便宜。既然重來的代價低，就不必一開始先支付大量規劃成本。先做出能跑的版本，讓真實使用情況幫你修正想法，反而更有效率。

哪些訊號代表該升檔？

只要出現下面任一個訊號，就該認真考慮 SDD：

訊號為什麼需要升檔
牽涉金錢、個資或權限 出錯的後果可能不可逆，不能只靠「再跑一次」補救
要交給別人接手，或預計長期維護 沒有規格與紀錄，接手的人只能靠猜，容易把原本的假設猜錯
正確性要求高，錯誤代價很大 付款、法遵與醫療等場景，需要可驗證的驗收條件
多人同時修改同一個專案 需要共同規格作為協作介面，否則每個人都可能按照自己的理解修改
需要能回答「為什麼這樣做」 規格與 ticket 本身就是決策紀錄，能留下可追溯的脈絡

升檔，不代表砍掉重來

從白話快跑切到 SDD，不是把前面做過的東西全部丟掉。白話階段累積的內容，往往正是 SDD 的原料：

  • AGENTS.md 裡的技術棧與資料模型，可以直接成為規格的地基
  • 逐頁功能規格，可以整理成最初那份 spec 的雛形
  • 測試計畫與驗收方式，可以轉成 tickets 與完成條件

前面的白話功夫沒有浪費。它像先用粉筆在地上畫出房子的輪廓：此時修改很便宜；等方向確認後，再把輪廓整理成正式圖紙，就能少走很多冤枉路。

最實用的答案：在 SDD 的框裡白話快跑

實務上通常不必二選一，混搭往往更好。財務管家的測試提示詞就是一個例子：它先要求 agent 分析三端、找出核心模組，並輸出測試計畫。這一步很接近 SDD，因為先建立範圍與驗收方向。

計畫通過後，實作仍然可以一圈一圈用白話迭代。規格與測試提供護欄，白話開發則保留速度與彈性。你要決定的不是「全部 SDD」或「全部 vibe coding」，而是：哪幾段路需要護欄？

三個情境，練習自己判斷

情境適合的檔位理由
週末替自己做一個記帳小工具 白話快跑 個人使用、錯了重來便宜，而且需求還在變
公司要上線的收款系統，需要對帳與稽核 SDD 會碰到真錢，錯誤可能不可逆，也需要可追溯的紀錄
三個同事一起開發一個需求常變的內部後台 至少混搭 多人協作需要共同規格，但需求變動仍需要白話開發的彈性

用一句話決定是否升檔

不確定時，先用白話快跑驗證想法；一旦要碰真錢、真資料或真人協作，就考慮升檔。

判斷的尺很簡單：問自己「如果它壞了，我能不能回復？」

能回復，就先快跑；不能回復，就把需求規格化，留下可驗收、可追蹤、可交接的紀錄。
