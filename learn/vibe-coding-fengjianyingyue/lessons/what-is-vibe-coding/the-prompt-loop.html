Vibe coding 的短迴路：描述、產出、跑起來、修正

Vibe Coding · 什麼是 vibe coding · Step 2/4

學習目標

看懂 vibe coding 怎麼運作，認得 AI 生成程式碼常見的失敗模式，也知道為什麼每一圈都要小、要能立刻驗收。

一圈迴路怎麼跑

Vibe coding 不是對 AI 說一句話，就坐著等完整產品交件。它比較像開著導航走路：走一小段、確認方向，再決定下一步。

  1. 描述一個具體目標
  2. 讓 agent 動手改檔並產出結果
  3. 把結果跑起來、實際操作
  4. 找出落差，修正或補充描述

接著回到第一步，繼續繞。整條 12 階段的產線，就是這個迴路重複很多次的結果。每次被處理的對象可能不同：一開始是產品需求，後來可能是資料庫、後台或測試。

為什麼迴路要短

關鍵在於錯誤定位的成本。

如果你一次要求 agent「把整個記帳 app 做完」，它交出三百行程式，結果首頁只顯示一片空白，你很難知道是哪一段出錯，只能在一大坨程式裡慢慢猜。

但如果這一圈只要求它完成「首頁顯示本月收入、支出、結餘三個數字，而且要從交易資料算出來」，首頁一打開就是驗收現場。數字有沒有出現、算得對不對，都能立刻看見；出錯時，也比較容易鎖定問題。

迴路短，不代表做事比較慢。它代表每一圈都有清楚的驗收點，讓你隨時知道目前走到哪裡。

驗證要靠「跑起來看」，不只是「讀程式」

傳統開發常會先讀一次 diff，再送出修改。使用 vibe coding 時，還要養成另一個動作：把結果真的跑起來。

「財務管家」示範 App 是單頁 HTML 檔，沒有建置流程。驗證時可以直接用瀏覽器開檔，也可以在資料夾中執行 npx serve . 或 python -m http.server 8000，再連到啟動的頁面。

打開後，不要只看畫面像不像完成品。實際點選「記一筆」、修改分類，再確認首頁數字是否跟著變動。

程式碼寫得漂不漂亮不是第一優先，真正重要的是行為是否正確。你比較像導演，而不是逐字背台詞的演員：不必看懂每一行，但要看得出這一幕有沒有演對。

AI 生成碼最常怎麼壞

知道常見的壞法，才有辦法守住品質。以下幾種失敗模式，尤其容易讓人誤以為功能已經完成。

失敗模式長什麼樣子為什麼危險
假綠測試 測試裡寫 expect(true).toBe(true)，或只檢查頁面有沒有載入 測試全部通過，卻沒有驗證真正的功能，讓你誤以為產品沒問題
規格不等於交付 你把功能寫進規格，agent 回報「已完成」，實際打開卻找不到這一塊 把「說要做」誤當成「已經做了」，直到驗收才發現功能根本缺席
假資料硬編碼 首頁金額是寫死的數字，或用 mock 假資料冒充真實資料 畫面看起來很完整，產品卻沒有真正接上資料庫
改到一半被截斷 檔案太長，agent 只改了一半就停下來，後半段仍然是舊內容 功能可能時好時壞，而且只看檔尾不一定看得出來
樣式漂移 每個頁面各自寫一套樣式，幾輪之後間距、字級和顏色逐漸不一致 產品看起來像拼貼，修改一個地方時也可能連帶影響其他頁面
敏感資訊外洩 API key、密碼被寫進前端程式，或存進瀏覽器的 localStorage 任何人打開開發者工具都能看見，等於把金鑰公開出去

一圈應該做多大

記住一個原則：每一圈都以一個能當場驗收的小功能為單位。

「首頁顯示本月收支結餘」是好的工作單位，因為你能立刻確認數字有沒有出現、是否算對。

「做一個好看的首頁」就不夠具體，因為「好看」沒有明確的驗收點；「把整個記帳 app 做完」則太大，容易做到最後也不知道哪裡算完成。

大需求不是不能做，而是先請 agent 把它拆成一份計畫，再分成一圈一圈的小功能逐步完成。下一課會介紹，如何用一句「先不要寫程式，先給我計畫」，把拆解需求變成固定習慣。

發現落差後，先分辨是「缺少」還是「錯誤」

看到結果不對時，修正通常有兩個方向。

第一種是缺了什麼：例如規格要求匯出 Excel，但畫面和功能都沒有出現。這時要請 agent 補上。

第二種是哪裡錯了：例如圓餅圖的比例加總超過一百。這時要請 agent 修正既有邏輯。

把問題分清楚，agent 才知道要補功能，還是要修改錯誤。最沒有幫助的回饋是「感覺怪怪的」。把這句話翻譯成具體描述，例如「圓餅圖的比例總和超過 100%」，就是在訓練自己的判斷力。

來源

本課內容整理自課程的提示詞 playbook：測試提示詞要求「不要立刻寫程式，先輸出計畫」，並明確禁止 expect(true).toBe(true) 這類沒有實際斷言的測試；功能點梳理則要求首頁的每個數字都必須從真實資料庫資料計算，不能用假資料代替。
