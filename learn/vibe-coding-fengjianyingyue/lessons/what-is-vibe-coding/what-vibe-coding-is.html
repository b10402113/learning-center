什麼是 vibe coding？

學習目標

讀完這一篇，你應該能用一句話說明 vibe coding 是什麼，分辨它和自己從頭寫程式有何不同，也能理解為什麼這種做法直到現在才真正可行。

你要的是客廳，不是磚頭

以前做軟體，像是自己搬磚蓋房子：語法、迴圈、資料庫連線、API 格式，每一塊都得親手處理。哪裡砌歪了，還得自己找原因、自己修正。就算你知道自己想做一道菜，也得先學會蓋廚房。

現在可以換一種方式。你走進設計工作室，告訴設計師：「我要一個採光好的客廳，放得下一台鋼琴，地板還要耐磨。」設計師負責規劃與施工，你則檢查成品是不是符合需求。你不必知道鋼筋怎麼綁，但要看得出牆歪了、門打不開，或鋼琴根本搬不進去。

vibe coding 就是這種角色轉換：你不再主要描述「每一步怎麼做」，而是先說清楚「想要什麼」，再由 AI 協助決定實作方式。

把白話變成新的開發介面

vibe coding，也可以理解成白話驅動開發：把日常語言當成開發介面，用中文說明需求，由 AI agent 產出能執行的成品，再根據實際結果持續修正。

這裡的 agent 不是只會聊天的視窗，而是能讀寫專案檔案、執行終端機指令，甚至上網查資料的程式助理，例如 Claude Code、opencode、Codex。你提出需求後，它可能會開檔、改檔、執行指令，最後交給你一個可以打開或執行的結果。

一句話記住：你說明意圖，它撰寫程式，你驗收結果。

「介面」這個詞很重要。過去你和電腦溝通，必須使用它理解的語法與符號；現在，你可以先用平常說話的方式描述目標。介面變簡單了，入門門檻也跟著降低。

你的角色：從工班變成導演

自己寫程式時，主要產出是一行一行的程式碼；用白話開發時，主要產出則變成一段段清楚的需求描述。你的價值不只在於打字快、記得多少語法，而在於能不能說明白、看得準、驗得嚴格。

這就像當導演。演員負責演出，但導演要決定這一幕想呈現什麼、哪裡不對、要不要重拍。你不一定要親自完成每個技術細節，卻必須看得出結果是否符合需求。後面所有技巧，都是在訓練這種判斷力。

為什麼現在才真正可行？

用白話叫電腦做事，其實不是新想法。早期的語音助理也能理解人話，但通常只能處理查天氣、設鬧鐘這類範圍固定的小任務。

現在的差別在於，模型能一次讀懂較完整的專案脈絡，並且不只回覆文字，還能主動執行動作。當模型只能回傳一段文字時，你最多只能叫它「幫我想一個函式」；當它能讀資料夾、修改檔案、執行指令，白話就能串成一條完整的開發流程。

你可以從一句需求開始，逐步完成前端、後端、資料庫、測試與上線工作。

不只是「幫我補一段程式」

第一次接觸時，很多人會把 vibe coding 想成「請 AI 幫我寫一個小工具」。但這門課要看的範圍更大。

課程會反覆使用一個實際做過的全端專案作為示範：財務管家，一個記帳 App。它從一句需求開始，最後成為可以交付的產品，包含網頁前端、後端 API、MySQL 資料庫、Java 企業級重寫、營運後台、跨端 App、測試報告、上線文件，以及推廣文案與影片。

整條流程被拆成 12 個階段，每個階段對應一種角色，例如產品經理、設計師、前端、後端、DBA、測試、交付與運營。每個角色都有自己的資料夾與提示詞，一個人也能依序走完。

因此，這門課教的不是幾個零散的 AI 技巧，而是一條可以重複使用的交付流程：讓需求一路走到能驗收、能決定是否交付的成果。

速度很快，代價也很真實

白話開發最大的優點是快；最大的風險，也正是快。它可能繞過傳統工程裡的規格、測試與審查。錯誤不會因此消失，而是換成更難察覺的形式。

  • 假功能：畫面看起來能操作，實際上關鍵按鈕沒有完成真正的邏輯。
  • 假綠測試：測試全部通過，但只是在檢查固定值、沒有斷言，或根本沒有走到重要路徑。
  • 文件與程式不一致：文件寫著某功能已完成，程式裡卻沒有實作，或只留下硬編碼與暫時性替代方案。
  • 截斷與硬編碼：AI 為了快速交出結果，可能只處理範例資料、截短內容，或把本來應該來自設定與資料庫的值直接寫死。
  • 跨端漂移：網頁、App 與後端各自修改後，介面、欄位或行為逐漸不一致。
  • 敏感資訊外洩：提示詞、日誌或提交內容可能意外包含金鑰、個資或資料庫連線資訊。

所以，vibe coding 不是把責任交給 AI，而是把人的工作重心移到需求描述、結果驗證與風險判斷。知道 AI 會怎麼失敗，你才有辦法分辨「真的完成」和「看起來完成」。

接下來要學會的迴路

後續內容會把這條流程拆開來看：描述需求、取得產出、實際跑起來、檢查結果，再修正。每一輪都要留下可以驗證的成果，而不是只相信 AI 的說法。

學完這一階段，你至少應該能做出一個清楚的判斷：vibe coding 不是「不用懂程式」，而是用白話提出意圖，再用工程方法驗收 AI 產出的程式。
