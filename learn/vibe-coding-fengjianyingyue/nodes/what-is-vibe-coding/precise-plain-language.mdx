<LearningGoal>
能說出三種讓白話變精確的作法：釘住技術棧與資料模型的 agent 說明書、逐頁功能規格、以及先要計畫再寫程式的提示詞。
</LearningGoal>

## Lesson

你對 agent 說「做一個好看的首頁」。它照做了，但打開一看跟你心裡想差很遠。問題不在它不聽話，而在這句話本身太鬆：「好看」是誰的標準？要放哪些資料？金額從哪裡來？讓白話變精確，不是叫你回頭寫厚重的規格書，而是用三個小道具把一句話收窄到能驗收的範圍。

第一個道具是 agent 說明書。在專案根目錄放一份 `AGENTS.md` 或 `CLAUDE.md`，對 agent 說明這個專案不變的那些事。財務管家的說明書宣告：這是單頁 HTML App、沒有建置流程；技術棧是原生 HTML/CSS/JS，圖表用 CDN 載入的 Chart.js；資料存在 localStorage，鍵名 `financeData`；版面手機優先，最大寬度 480px；還有資料模型，交易是 `{id, type, category, amount, account, remark, date}`，帳戶是 `{id, name, type, icon, balance}`。把資料模型寫死，等於先講好「一筆交易長什麼樣」，後面每一頁都用同一套欄位。技術棧那一條更微妙：PRD 描述的是多表後端，說明書卻把 V1 釘成「一個存在 localStorage 的單頁檔案」，這個動作阻止 agent 自己決定要往哪個方向發展，也讓白話少了很多猜測空間。

第二個道具是逐頁功能規格。不要說「做統計頁」，而是把一個畫面拆成一塊一塊可以逐條驗收的功能。首頁被拆成三塊：本月標題加上收入、支出、結餘三個數字；本月支出最高的前三名分類；依時間排序的最近三筆交易。規格裡還明講，這些數字都要從真實資料算出來，不能用假資料代替。統計頁也一樣，拆成年份選擇、年度收支結餘、分類圓餅圖、12 個月折線圖、Excel 匯出五件獨立的事。驗收點一多，你和 agent 之間就少了爭論的空間。

第三個道具藏在提示詞的寫法裡：直接命令它「不要立刻寫程式，先輸出計畫」。課程的測試提示詞就是這樣開場，先要求分析前端、後端、跨端 App 三端，找出核心業務模組與高風險功能，再輸出一份分層測試計畫，而且一個專案一份。先要計畫，因為計畫是最便宜的驗收點：計畫錯了改幾行文字就好，程式錯了得回頭拆三百行。

還有一件事要記得：規格不等於交付。功能規格寫完之後，同一批「明細、統計、首頁」的功能又被重列了一次，標題是「目前缺失以下功能」。寫得再清楚，agent 也可能只做一部分就回報完成。所以精確是雙向的，一邊把話說精確，一邊把驗收做精確，看到缺的就再下一次明確的指令。
