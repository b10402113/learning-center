<LearningGoal>
能根據風險、規模、協作與正確性需求，判斷何時該從 vibe coding 升級成工程化的 SDD 流程，並說出升級時要交接哪些東西。
</LearningGoal>

## Lesson

vibe coding 和工程化的 SDD 不是互相取代的兩派，而是同一台車的兩個檔位。SDD（spec-driven development，規格驅動開發）指的是先把規格寫清楚，再把規格拆成一張張可以獨立完成的小單子（ticket），逐張實作，做完回頭審查。它比白話開發多出好幾道關卡，代價是慢，好處是每一步都留下可追溯的紀錄。

大部分探索性的工作，白話快跑是更好的選擇：點子還在驗證、做錯砍掉重來的成本很低、需求會一直變、只是個人使用或內部演示。這些情況的共同點是錯了可以重來，既然重來便宜，就不必先付一大筆規劃成本。

但只要出現下面任何一個訊號，就該考慮升檔：牽涉金錢、個資或權限，出錯的後果不可逆；要交給別人接手或長期維護；正確性要求高，付款、法遵、醫療這類場景需要可驗證的驗收條件；多人同時改同一個專案，需要共同的規格當協作介面；或者需要可追溯、能回答「為什麼這樣做」。

升級不等於砍掉重來。白話階段累積的三樣東西正好是 SDD 的原料：`AGENTS.md` 裡的技術棧與資料模型，直接變成規格的地基；逐頁功能規格，就是一開始那份 spec 的雛形；測試計畫與驗收方式，可以轉成 tickets 與完成條件。前面花的白話功夫不是白費，它幫你在還很便宜的時候先摸出產品的輪廓。

最實用的做法其實是混搭。財務管家的測試提示詞就是例子：先要求 agent 分析三端、找出核心模組、輸出一份測試計畫，這是很 SDD 的動作；計畫通過之後，實作仍然是一圈一圈用白話迭代出來的。護欄來自規格與測試，引擎仍然是白話，你不必二選一，你可以選擇在哪幾段路裝護欄。

判斷的尺很簡單：問自己「如果它壞了，我能不能回復？」能，就快跑；不能，就規格化。不確定時，先白話快跑驗證想法，一旦這個東西要碰真錢、真資料、真人協作，就升檔。
