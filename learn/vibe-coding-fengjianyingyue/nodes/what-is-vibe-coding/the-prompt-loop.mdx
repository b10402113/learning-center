能說出 vibe coding 的運作迴路，並認得 AI 生成程式碼的幾種典型失敗模式，知道為什麼迴路要短。

## Lesson

白話開發不是「講一句話，坐等成品」。它是一個一直轉的圈：你描述一個具體目標，agent 動手改檔並產出東西，你把它跑起來動手操作，看到落差之後修正或補充描述，再轉下一圈。

這個圈的每一圈都要小。原因不在速度，而在錯誤定位的成本。一句話要 agent「把整個記帳 app 做完」，它交了三百行，結果首頁打開是白的，你只能從一大坨程式裡猜哪裡壞了。反過來，如果這一圈只要它「讓首頁顯示本月收入、支出、結餘三個數字，而且從交易資料算出來」，首頁一打開就是驗收現場，錯了也馬上看得出是哪一條。

另一個要練的動作是：驗證靠「跑起來看」，不是靠「讀程式」。財務管家是單頁 HTML 檔，沒有建置流程，驗證方式就是打開它，在資料夾裡跑 `npx serve .` 或 `python -m http.server 8000` 再連上去，點記一筆、改一個分類、看首頁數字有沒有跟著動。程式碼漂不漂亮不是重點，行為對不對才是。

知道 AI 生成碼會怎麼壞，你才守得住。最常見的失敗模式有幾種。假綠測試，測試裡寫 `expect(true).toBe(true)`，或只檢查頁面有沒有載入，全部通過卻什麼都沒驗證。規格不等於交付，你把功能寫進規格，agent 回報完成，實際打開卻沒有這一塊。假資料硬編碼，首頁的金額是寫死的數字，或用假資料冒充真實資料，畫面漂亮但根本沒接上資料庫。改到一半被截斷，長檔案只改了一半就停下。樣式漂移，每頁各自寫一套樣式，過幾輪之後間距與字級開始不一致。還有敏感資訊外洩，API key 或密碼被寫進前端程式或瀏覽器的 localStorage，任何人打開開發者工具就看得到。

修正的方向通常有兩種：一種是「缺了什麼」，另一種是「哪裡錯了」。講清楚是哪一種，agent 才知道要補還是要改。最怕的是只說「怪怪的」。把「怪怪的」翻譯成一句具體的話，就是在練你自己的判斷力。
