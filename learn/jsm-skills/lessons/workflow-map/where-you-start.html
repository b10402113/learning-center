從哪裡起跑：greenfield、brownfield、monorepo 與 debug

jsm-skills · 工作流總覽 · Step 3/4

學習目標

能說出 greenfield、brownfield、monorepo 三種入口各自的起跑順序與背後理由，並說明 /debug 迴圈為什麼不需要 scope 或 spec 就能走。

前言：同一套流程，兩種截然不同的起點

上一節決定了「這次要跑哪些階段」。但在那之前還有一個更前面的問題：你是從哪一站進來的？如果手上是一個剛開好的空專案，跟面對一份已經長了三年的 codebase，用同一種順序硬跑，結果會很不一樣。

原因很簡單：這套流程裡有一個階段叫 /audit，它的工作是讀懂你的專案，並把 stack、指令、慣例寫進 AGENTS.md，讓後面每一個 skill 都懂你的專案。如果專案根本還不存在，audit 就只能對著空資料夾瞎猜；但如果專案早就長滿了東西，audit 又應該先跑，免得後面的 skill 在還不認識你的專案時就開始動工。所以「從哪裡進」不是小事，它會決定整條流程讀到的東西對不對。

全新產品（greenfield）

如果你要從零開始做一個新產品，順序是這樣：

  1. 先跑 /scope。因為還沒有任何程式碼，它會把這當成一個全新專案，規劃出第一批工作，從地基與第一個正式功能開始。
  2. 再跑 /architect 決定整個 stack。這種情況下它會做一輪比較廣的選項比較，給出明確的推薦與備案，而不是丟一張清單讓你自己挑。
  3. 然後你自己用這個 stack 的官方 setup 工具，把空專案 scaffold 出來。這一步刻意交給你，因為建立專案骨架本來就是人該決定的事。
  4. 最後才跑 /audit。這時候它讀到的是一個真實、已經 scaffold 好的專案，於是能寫下準確的 AGENTS.md，記錄 stack、指令，以及它看得出來的慣例。

這個順序的關鍵在第 2 步和第 3 步為什麼要排在 /audit 前面：stack 先選好、專案先存在，audit 才是對著一份真專案寫筆記，而不是對一個空資料夾憑空猜測。之後才進入反覆跑的功能迴圈。

既有專案（brownfield）

如果你面對的是一份已經存在的 codebase，順序要反過來：

  1. 先跑 /audit，讓每一個 skill 在動手之前就懂你的專案。
  2. 再跑 /scope，請它把既有的東西「收編」進來，在現況之上規劃下一個 slice。
  3. 接著才進入同樣的功能迴圈。

差別在於：新專案是「先有計畫與 stack，才有專案可讀」；既有專案是「先讀懂既有的東西，才談得上規劃下一步」。把 /audit 擺在第一位，是為了讓後面每一步都站在對的認識上。

monorepo

monorepo 是一個 repo 裡裝了好幾個專案。在這種結構下，每一件事都會被 scope 到「你正在處理的那一個 workspace」，而不是整個 repo。

每個 workspace 有自己的 scope、自己的 spec、自己的嵌套 AGENTS.md、自己的 stack 與指令。所有 skill 都待在目標 workspace 裡，用它自己的指令做事。這樣設計的好處是，改一個 app 不會意外伸進另一個 app。你不需要記得「這一站在哪個 workspace 要做什麼」，因為檔案本身就分好了。

起點第一步接著為什麼這樣排
全新產品/scope/architect 決定 stack、自己 scaffold、/audit讓 audit 讀真專案，而不是空資料夾
既有專案/audit/scope 收編既有、規劃下一片先讓每個 skill 懂你的專案
monorepo指定目標 workspace各 workspace 有自己的 scope 與 AGENTS.md改動不跨到別的 app

隨時可走的 debug 迴圈

上面講的都是「有東西要做」。但還有一種情境：東西壞掉了。這時候你不需要先規劃，也不需要先寫 spec，直接走 /debug 就好。它只做一件事，找出並修掉根本的原因，而且它有一套很嚴的順序。

  1. 重現（reproduce）：先把問題重新製造出來，確定自己修的是真的存在的東西，而不是憑印象猜的。
  2. 定位（localize）：把故障可能的位置縮小到一個範圍。
  3. 假設（hypothesize）：針對原因提出一個清楚、可以被否證的猜測。
  4. 測試（test）：設計方式去驗證這個猜測。猜錯了，就換一個新假設，而不是開始亂改一通。
  5. 修補（fix）：找到原因之後，做最小、足以解決問題的修改。
  6. 驗證（verify）：確認原本的問題真的消失了，然後把一個回歸測試交給 /test，讓同一個 bug 不會再悄悄回來。

這套迴圈有兩條紀律值得記住。第一是一次只測一個假設；如果你的猜測錯了，那就提出新的，而不是同時做一堆改動，因為那樣就算問題好了，你也不知道是哪一個改動奏效。第二是它不順手做別的事：不加新功能，也不整理不相關的程式碼。壞掉的東西修好就好。

小結

起跑順序看你手上的起點。全新產品是 /scope、/architect 決定 stack、自己 scaffold、/audit，關鍵是讓 audit 讀到真專案。既有專案是 /audit 先讀懂專案、/scope 再收編既有並規劃下一片。monorepo 則把每件事 scope 到目標 workspace，各自有自己的檔案與指令。/debug 是一條不需要 scope 或 spec 的獨立迴圈：重現、定位、假設、測試、修補、驗證，一次只驗一個假設，最後把回歸測試交給 /test。

到這裡，你已經能把這張圖畫出來、裁剪它，也知道從哪裡進。最後一步要把這一切對回你本來就在跑的那套流程，也就是 SDD 七階段，看看 jsm-skills 不一樣的地方在哪裡。
