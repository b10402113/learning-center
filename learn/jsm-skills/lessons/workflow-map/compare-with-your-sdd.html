對照你的 SDD：三個真正不同的地方

jsm-skills · 工作流總覽 · Step 4/4

學習目標

能把 jsm-skills 九階段對回自己熟悉的 SDD 流程，並指出 decision gate、驗證分工、檔案即狀態這三個關鍵差異與各自的取捨。

前言：學一套新流程，最怕把每個名詞都當成新發明

前面三步已經讓你能畫出這張圖、裁剪它，也知道從哪裡進。最後要處理的是最實際的問題：你本來就有一套跑得動的 SDD，大致是 grill、spec、issues、implement、review 這條路。那 jsm-skills 到底多給了你什麼？

學一套新流程最大的風險，是把它的每個名詞都當成新發明，然後愈看愈覺得「這不就換句話說嗎」，最後整套丟掉。有用的問法是：同一個環節，它怎麼解？差在哪裡？這個差值，才是你決定要不要偷的依據。這一節先放一張對照表，再挑出三個不同的地方，最後點出一個你就算不採用整套、也能單獨偷走的招式。

先對一次表

jsm-skills你 SDD 裡的對應關鍵差異
/scopegrill（把想法問清楚、定義範圍）scope 產出的是一份會持續更新的檔案，而不是只留在對話裡

表上大致看得出，前三站與你的 SDD 是同一件事的不同做法，後面幾站則是你流程裡常常沒有的環節。但值得停下來看的，是下面三個差異。

差異一：決策閘門是可以機械檢查的

在你的 SDD 裡，「把事情問清楚」主要靠 grill 的對話功夫。這件事很吃當天的狀態：問得夠不夠細、有沒有漏掉某個關鍵決定，取決於問的人當下想到什麼。jsm-skills 把同一個環節拆成兩道可以檢查的動作。

第一道在 /architect：寫 spec 的時候，它會為「這個功能必須產生的每一個值」指名來源。例如一個畫面要顯示使用者的名字，那個名字從哪裡來、由誰決定，必須在 spec 裡寫清楚。這樣一來，缺漏在設計階段就會自己浮出來，而不是等到寫程式才發現。

第二道在 /develop：動手之前，它會再檢查一次覆蓋率。它會列出這次建置必須產生的每個值，如果 spec 沒有交代某個值的來源，就代表這裡還欠一個決策，於是停下來。develop 自己的說法是：這是很強的閘門，但不是絕對保證，沒有任何提示詞能做到絕對。它的價值不在完美，而在可重複：不會因為今天誰在問、問得累不累，而漏掉同一個決策。你可以偷的正是這個思路，把「需要決定的事」變成一個可檢查的動作，而不是一次對話的印象。

差異二：驗證被拆成三層，各問各的問題

你熟悉的 review 通常承擔了所有「檢查」的責任：看程式碼、想邏輯、猜有沒有 bug。jsm-skills 把驗證拆成三層，每一層問的問題不同，也由不同的角色負責。

層它問的問題怎麼回答
/check verify它真的會動嗎？符合當初的承諾嗎？把 app 真的跑起來，照驗收條件操作一遍
/test這個行為以後會不會悄悄壞掉？把會長期成立的行為鎖成回歸測試
/check review寫法對嗎？有沒有自己看不到的盲點？換一個模型讀 diff，給出發現與評價

分開的好處是，每一層都能把力氣花在它擅長的事上。驗證在乎「行為對不對」，測試在乎「未來穩不穩」，審查在乎「設計與品質好不好」。把它們混在一次 review 裡，通常就會變成什麼都看一點、什麼都不深。

其中 review 用「不同模型」這一點，對你來說是新的。理由是：一個模型審自己寫的程式碼，會傾向同意自己。換一個模型，等於換一組訓練出來的偏好與盲點，比較容易看到另一個角度的問題。這一層只讀、只報告，不動你的程式碼，要不要改由你決定。

差異三：檔案即狀態，而且每個檔案只有一個擁有者

你的 SDD 應該也把 spec、issues 放進檔案，但你大概體會過那種痛：同一件事在三個地方各有一份，其中兩份已經過期，而你不知道該信哪一份。jsm-skills 對每種檔案指定唯一的擁有者，試圖從規則上避免這件事。

只有 architect 能寫 spec 的內容；只有 develop 能移動 spec 的狀態那一行；只有 sync 能去修正已經過期的專案文件。因為每份檔案的作者只有一個，它們就不容易互相打架。再往上一層，還有一條「驗收條件」的線把所有階段串起來：spec 裡的每一條需求都有編號，build plan 的每個任務都說明它服務哪一條，驗證步驟和測試也回溯到同一批編號。所以「哪一條需求被證明過」是查得到的，不是憑感覺。這種把狀態放在檔案、又把擁有權寫死的做法，是整條流程能跨 session、跨人的根本原因。

就算不整套採用，也值得偷的一招

你可能會想：九個階段全導入，對手上的小專案會不會太重？確實可能。這套流程自己也留了伸縮空間，四個深度就是允許你用 Prototype 或 Alpha，不必每件事都跑完整條鏈。

但如果只挑一個招式帶走，我會選 Assumed spec 這個模式。你的 SDD 遇到「先做再說」的時候，通常是默默假設，事後沒人記得當初假設了什麼。jsm-skills 的做法是把它寫成一筆小小的檔案，記下假設是什麼、誰授權、動到哪些程式碼，並讓這個功能一直帶著「還欠一個正式決定」的標記。它不擋你合併，也不擋你宣告完成，只是讓那個決定不會消失在對話裡。這個招式可以單獨搬進任何流程，不需要你先接受九個階段。

小結

jsm-skills 的前幾站和你的 SDD 是同一件事的不同做法，後面幾站則補上你流程裡常缺的驗證、測試、撰寫與知識對齊。三個差異是：決策閘門被做成可重複檢查的動作、驗證被拆成「會不會動／會不會壞／寫法對不對」三層、以及每份檔案都有唯一擁有者並由驗收條件串起。最值得先偷的一招是 Assumed spec：讓「先做再說」的決定留下書面痕跡，而不是默默消失。

這張地圖到這裡就完整了。你知道九階段的 DAG、知道怎麼裁剪與起跑、也知道它和 SDD 的差別。接下來要更細看的是這張圖上那些檔案本身：AGENTS.md、scope、spec 各自裝什麼、誰能改、彼此怎麼搭配，那會是下一個節點的主題。
