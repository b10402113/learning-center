九階段地圖：每一階段回答什麼、吃什麼、留下什麼

jsm-skills · 工作流總覽 · Step 1/4

學習目標

能畫出九階段的 DAG，說出每一階段的輸入、輸出與它寫進 repo 的檔案，並指出 /debug 與裸 /scope 這兩條隨時可走的旁路。

前言：一個月後，你忘了當初為什麼這樣做

「幫我做一個小 app，可以註冊登入，每個人有自己的待辦清單。」你把這句話丟給 coding agent，它很快回你一份看起來能跑的專案，當下一切順利。麻煩的是三個禮拜後：你想加一個「分享清單」的功能，打開專案卻想不起來資料庫當初為什麼選這一個、登入用哪一套、上一版到底做到哪一步。於是你又翻對話紀錄，結果那個 session 早就被清掉了。

問題通常不在 agent 不夠聰明，而在這段開發過程幾乎沒有留下可以讀的東西。jsm-skills 想解的正是這件事：把「從一句話到交付」拆成一條有階段的輸送帶，而且每個階段做完，都會把結果寫成一份放在專案裡的檔案。這一節先把整條輸送帶攤開，看清楚有哪幾站、每站在做什麼、彼此怎麼銜接。

先分清楚：九個 skill，不是九道關卡

第一個要拆掉的誤會，是把這九個階段當成九道非過不可的關卡。這套工作流的主張正好相反：每個階段是一個獨立的 skill，你只跑這個改動需要的那些，順序也可以自己配。它沒有逼你每次都從頭走到尾。

那九個階段的骨架到底是什麼？是「上一個階段的產出，變成下一個階段的輸入」，而且這些產出全部是實體檔案。所以這張圖的主角其實是檔案在階段之間流動，而不是九個步驟依序被簽核通過。

主幹長什麼樣

把慣例上的順序攤開，主幹是這樣一條線：

idea → /scope → /audit → /architect → /develop → /check verify → /test → /check review → /document → /sync

你可以把它想成一條輸送帶：最前面是你腦中的一句話，最後面是已經上線、寫好說明、而且專案文件也對齊的一項改動。不過要先提醒，這條線的順序是慣例上的排列，不等於每次都得照這個次序起跑。該從哪一站進，要看你手上的專案是全新的、既有的，還是一個 monorepo，這段留到 Step 3 再講。

九階段各自回答一個問題

每一個階段其實都在回答一個特定的問題，並且只負責那一個問題。把問題、輸入、輸出排成一張表，整條流程就清楚了。

階段它回答的問題吃什麼（輸入）留下什麼（輸出檔案）
/scope要建什麼、先做哪一塊？一句點子、既有的 repodocs/scope/ 裡的計畫
/audit這個專案實際上怎麼運作？真實的專案檔AGENTS.md，加上指向它的小 CLAUDE.md
/architect這個重大決策怎麼做？模糊的請求、既有 contextdocs/specs/ 裡一紙 spec（狀態 Proposed）
/develop照著決策把它蓋出來spec、AGENTS.md、design.md應用程式碼；spec 轉 In Progress、scope 前進
/check verify它真的跑得起來、符合規格嗎？真的跑起來的 app、spec 的驗收條件驗證結果（可存成 spec 旁的 verify.md）
/test這次的改動要怎麼防回歸？尚未提交的變更測試檔，外加記下框架選擇的 test-preferences.json
/check review換一雙眼睛看，這份 diff 有沒有問題？這份 diffdocs/reviews/ 裡的發現（只讀，不改碼）
/document這件事要怎麼講給人聽？真實的 commit 與 diffPR 描述、CHANGELOG.md、release note
/sync檔案和程式碼現在還一致嗎？repo 現在的樣子對齊過的 AGENTS.md、scope、spec 狀態

表裡有兩件事值得先記住。第一，check 是一個 skill、兩種模式。verify 負責真的把 app 跑起來，照規格證明功能會動；review 負責讓另一個模型讀 diff，給出資深審查的意見。它們解決的是不同問題，所以會出現在流程的兩個不同位置。

第二，document 和 sync 最常被當成「有空再做」的兩站，但它們其實是這套流程對團隊最值錢的地方。document 把冷冰冰的 diff 翻成人看得懂的文字；sync 則回頭確認專案文件沒有因為這次改動而開始說謊。

拆成兩段：專案層與功能迴圈

這條主幹可以再拆成性質不同的兩段。

最前面兩站 /scope 和 /audit 屬於專案層。它們處理的是整個專案：要建什麼、實際上怎麼運作、有哪些慣例。一個新專案跑一次，之後每次要規劃新的一批工作時，再回頭更新一次。

中間那段才是會反覆跑的功能迴圈：

/architect → /develop → /check verify → /test → /check review → /document → /sync

每一輪處理一個功能，先決定、再實作、再驗證、再補測試、再換人審、再寫說明，最後把知識對齊。你之後的日常，多半都在這一小段裡循環。

兩個容易看漏的設計

第一個設計是：每個階段的輸出，都是下一個階段讀得到的檔案。scope 寫的計畫會被 architect 和 develop 讀；architect 寫的 spec 會被 develop 讀；develop 留下的檢查步驟會被 check verify 拿去跑。階段之間是靠檔案在交接，不是靠對話的記憶。

第二個設計是：每一站只動它自己擁有的檔案。scope 建立 scope，architect 寫 spec 的內容，develop 只移動 spec 狀態那一行，sync 修正過期的地方。這條「單一擁有者」的規矩，是這些檔案不會愈改愈亂的原因。之後 Step 4 對照 SDD 時，會再回來看這個設計為什麼重要。

兩條隨時可走的旁路

主幹之外有兩條路不屬於固定順序，而是你隨時可以切進去。

第一條是 /debug。只要東西壞掉、拋錯、行為不對，就直接走它，不需要先有 scope，也不需要先有 spec。它做的是一套紀律很嚴的找因流程：先重現問題，把範圍縮小到某個位置，提出一個可以被否證的假設，測試這個假設，找到原因後做最小修補，確認問題消失，最後把一個回歸測試交給 /test，確保同一個 bug 不會安靜地跑回來。它只做這一件正事，不會順手加功能，也不會整理不相關的程式碼。

第二條是裸的 /scope，也就是不帶任何參數直接下 /scope。當你想知道「我現在做到哪、下一步是什麼」，它會讀檔案回答你，等於是在整條輸送帶上隨時按一下「我在哪」。

為什麼這條輸送帶能跨 session

你應該已經注意到一件事：上面每一站的產出都是檔案。這件事讓整個流程可以「停下來再繼續」。你可以做到一半就把 session 清掉，下次它從磁碟重讀狀態，告訴你哪些工作已經完成、從第一件還沒完成的事接著做。

對團隊也一樣。隊友只要 pull 下這個分支，就能看到同一份 scope、同一紙 spec、同一組測試。狀態不在某個人的對話裡，所以在誰手上都長得一樣。

小結

九個階段各回答一個問題：scope 定要做什麼，audit 記專案怎麼運作，architect 做決策，develop 照著蓋，check 用 verify 與 review 兩種方式確認，test 防回歸，document 寫給人看，sync 把文件對回程式碼。scope 與 audit 屬專案層，中間七站是會反覆跑的功能迴圈。每一站的產出都是檔案，所以階段之間靠檔案交接，流程也能跨 session、跨人。/debug 與裸 /scope 則是兩條隨時可走的旁路。

知道了全貌，下一個問題自然會冒出來：這九站每一次都要跑嗎？如果我只是改個按鈕顏色呢？下一步要講的，就是這張圖怎麼裁剪，也就是四個 workflow depth 與「建議不是閘門」這條規則。
