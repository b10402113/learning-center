只跑該跑的：四個深度與「建議不是閘門」

jsm-skills · 工作流總覽 · Step 2/4

學習目標

能依情境決定要跑哪些階段、跳過哪些，說出 Prototype、Alpha、Beta、GA 四個深度各跑什麼，並分辨「建議的檢查尾巴」與「唯一硬性要求：重大決策要寫下來」。

前言：改一顆按鈕，也要跑完整套嗎？

上一節把九階段的地圖攤開，也點出它最重要的一句規則是「只跑這個改動需要的階段」。問題是，如果沒有判斷準則，這句話等於沒說。你很可能還是會陷入兩種極端：一種是每一件小事都照九站跑一遍，把自己累死；另一種是乾脆全部跳過，最後連當初做了什麼決定都說不清楚。

這一節要補上的，就是那套判斷準則。它包含兩個部分：一個是隨專案或功能調整的四段「深度」，另一個是「建議不是閘門」這條規則。兩者合起來，你才有辦法回答「這次到底要跑到哪」。你可以先把四個深度想成醫療處置：小擦傷自己貼 OK 繃就好，重大手術才需要第二意見與完整病歷。風險不同，投入的檢查就不同。

四個 workflow depth

在 /scope 快結束時，它會依你描述的情境推薦一個「預設深度」，也就是這個專案平常打算跑多少驗證。這個選擇可以隨時被單一功能覆蓋。四個深度如下。

深度develop 之後跑什麼適合什麼
Prototype只跑 /develop，除此之外沒有了丟棄式原型、實驗、個人專案
Alpha加跑 /check verify低風險功能、想被證明的內部工具
Beta加跑 /check verify 與 /test大多數真實產品
GA再加 /check review 與 /document付款、登入、合規等高風險工作、團隊 codebase

Prototype 是最輕的一級。它只跑 /develop，之後沒有任何獨立檢查，你靠的是 develop 自己的建置期自檢，還有你自己的眼睛。因為你在一開始就選擇跳過獨立驗證，所以 develop 在功能建好、自檢通過時，會直接把它標成完成。適合拿來做隨時可以丟掉的原型或實驗。

Alpha 在 /develop 之後加上 /check verify，讓功能在真的跑起來的 app 上被證明一次，通過就標完成。它沒有獨立的測試套件，也沒有第二雙眼睛，除非某個功能自己要求。這一級適合低風險、但還是想看到證明的功能，例如內部工具。

Beta 再加上 /test。驗證跑完之後，測試會把這個功能的重要行為鎖住，然後功能才算收尾。這一級預設不做換模型的審查。對大多數認真的產品來說，Beta 是很合理的預設值。

GA 是最完整的一級：/develop 之後依序跑 /check verify、/test、/check review（換一個模型審）、最後 /document。到了這一級，多數功能會被視為需要一紙 spec。凡是碰錢、碰登入、牽涉合規，或是在一個多人共用的 codebase 裡動刀，就適合用 GA。

關鍵一：這是建議，不是鎖定的軌道

四個深度最容易被誤解的地方，是把它當成一條一旦選了就無法脫身的軌道。它其實只是「建議的檢查尾巴」，以及「建議的完成時機」。

你隨時可以跑得比建議多，也可以跑得比建議少。done 永遠是由你宣告的，不是某個 skill 扣著不給你，直到你把每個欄位都打勾才發下來。如果你跳過了一個建議要跑的階段，那件事會被誠實地記成「已跳過」，而不是被當成沒發生。反過來說，如果你覺得這個功能風險特別高，想直接給它 GA 等級的對待，也完全可以。

所以這個深度的作用，是幫後面的階段拿捏力道：它讓其他 skill 知道「這個專案平常不需要被逼著跑完整條鏈」，不會一直來煩你。它是一份課表，不是打卡機。

關鍵二：深度不關掉決策的閘門

這裡有一個很重要的但書：調低深度不等於可以跳過 /architect。任何深度下，只要一個功能真的需要一個尚未決定的重大選擇，流程還是會把你導向 /architect 先做決定。

那為什麼低深度看起來很少有 /architect 的身影？因為低風險的功能本來就很少真的需要重大決策，所以你就很少走到那一站。一旦某個功能牽涉到需要拍板的東西，閘門仍然會把你擋下來。換句話說，低深度並沒有把閘門關掉，只是「很少需要用到閘門」而已。

唯一的要求：把決策寫下來

整套流程裡，唯一稱得上硬性要求的事情只有一件：一個會帶來後續影響的重大決策，要被寫成一份 spec。這件事的目的很單純，就是不要讓決定憑空消失在對話裡。

而且連這個要求都不是強制執行的。假設 /develop 發現有一個決策還沒做，而你想先往下衝，它不會默默替你猜，而是會把這個假設寫成一份標記為 Assumed 的小 spec，裡面記清楚它建立在什麼假設上、是誰授權這樣做的、會動到哪些程式碼。這個功能之後會一直被標記為「欠一個正式決定（ratification）」，但這個標記不會擋住你宣告完成。它只是個持續存在的提醒，等哪天你有空，再回頭把這個決策好好想清楚。

/develop 遇到缺決策時，通常會給你三個選項：先回去 /architect 把它決定好再回來（這是推薦路徑）、你判斷這裡根本沒有真的要決策所以直接建、或是先建下去但把它記成一紙 Assumed spec。這三個選項的共同點是：決定不會被靜靜吞掉。

什麼時候只跑兩步就好

把深度和閘門放回真實情境，你會發現很多改動其實很短。一個 bug 直接丟給 /debug，不需要先規劃、也不需要先寫 spec。一個很小的改動，可以只有 /develop 加 /check verify 兩步。該問的是這次的風險需不需要那些站，而不是有沒有跑完九站。

小結

四個深度是隨風險調整的檢查尾巴：Prototype 只有 /develop，Alpha 加 /check verify，Beta 再加 /test，GA 再加 /check review 與 /document。它們是建議，不是鎖定的軌道，done 永遠由你宣告，跳過的階段會被誠實記錄。調整深度不會關掉決策閘門：任何深度下，需要決策的功能都還是會導向 /architect。整套流程唯一的要求，是讓重大決策留下書面紀錄；連這件事都是用標記提醒，而不是強制擋下。

知道「要跑哪些」之後，下一個實務問題是「從哪裡進」。全新的專案、已經長了好幾年的 codebase、還是一個 monorepo，起跑順序其實不一樣。下一步就來處理這三種入口，也順便看清楚 /debug 迴圈。
