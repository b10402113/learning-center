這次要跑多深：從 Prototype 到 GA，以及何時可以跳過

Step 3/4 · 端到端實跑與覆盤

學習目標

學完這一節，你應該能用 Prototype、Alpha、Beta、GA 四種深度，判斷一次改動需要跑哪些階段；也能說清楚「suggestions, never gates」的界線、這套流程明確不會做什麼，以及它要防哪些常見失敗。

前言：上線前只改一個錯字，也要跑完整套嗎？

你已經知道完整流程怎麼跑。但現實中的改動，大小差距很大：有時候你從零開始做一個產品，有時候只是把按鈕上的錯字改掉。

如果每次改動都跑滿九個階段，時間會花在不必要的檢查上。反過來說，如果所有事情都只跑 /develop，付款流程或登入功能出問題時，往往等到太晚才發現。

這套流程的做法，不是替所有改動套上同一條固定流水線，而是在 /scope 時先替專案選一個預設深度，再依照單一改動的風險增減檢查。這一節要看的，就是這把尺：四種深度各自會跑哪些階段、什麼時候可以跳過，以及流程明確承諾「不會做」哪些事。

四級深度：從只跑 develop，到整套流程

深度分成四級。選定深度後，主要決定的是 /develop 之後要接多長的「建議檢查尾巴」，以及建議在什麼時間點把功能標成 done。

請先記住一件事：這些是建議，不是把你鎖在鐵軌上的硬性流程。

深度develop 之後跑什麼建議的 done 時機適合什麼
Prototype什麼都不跑，只依靠 develop 自己的建置期自檢建置完成並通過自檢後，由 /develop 自己標記 done用完即丟的原型、實驗、個人專案
Alpha加上 /check verify，在實際啟動的應用程式上驗證verify 通過時低風險功能，但仍希望有人證明它真的能運作的內部工具
Beta加上 /check verify，再跑 /test測試進來後，由 test 收尾大多數真正要使用的產品
GA加上 /check verify、/test、換模型執行的 /check review，最後再跑 /document整套流程跑完，而且多數功能會被視為需要 spec高風險工作、付款、登入、合規，以及團隊共用的程式庫

拿上一節的登入加待辦清單小 app 來說，/scope 會建議使用 Beta。它已經是真正的產品，也包含登入這種不能出錯的部分；但它還不至於每次都需要另一個模型來審查。

這就是深度的運作方式：/scope 會依照你描述的內容推薦一個深度。用完即丟的實驗通常會落在 Prototype；小型專案則可能落在 Alpha 或 Beta。接著，你的選擇會被記錄成專案預設值。

不過，這個預設只是基準線，不是最高上限，也不是最低限制。

第一，某個功能如果本身風險很高，仍然可以走一條比較重的流程，不會因為專案預設很輕就被放過。第二，後續階段會讀取這個預設值，因此不會對 Prototype 或 Alpha 專案窮追猛打，硬逼它跑完整條鏈。

這就是「深度」省事的地方：它讓整套流程知道什麼時候該繼續檢查，也知道什麼時候可以先停下來。

一個關鍵誤解：輕量深度不等於跳過 architect

看到 Prototype 只跑 /develop，很容易得出一個錯誤結論：「輕量深度就是不用做決定，也不用跑 architect。」

正確的理解是：低嚴謹度的功能，通常本來就沒有太多需要拍板的事情，所以很少會走到 /architect。但只要真的出現需要決定的事項，那道閘仍然會把你送過去。

換句話說，四種深度調整的是 /develop 之後的檢查尾巴，不是前面那道「不要偷偷發明決定」的閘。

不論選哪一級，流程都只要求同一件事：每個 load-bearing 的決定，都要被寫下來。其他步驟則是建議。

Suggestions, never gates：done 永遠由你決定

這條原則在整套流程中最容易被誤解，所以值得單獨說清楚。

/develop 之後的每一步，包括 /check verify、/test、/check review 和 /document，都只是依照深度提出的建議。你可以選擇跳過。

「功能完成了」也永遠由你宣告。沒有哪個 skill 會扣住 done 不讓你標記，直到你把整張檢查清單全部打勾。你跳過的步驟會被誠實記成「跳過」，不會變成一筆一直追著你的欠帳。

深度只會建議你在什麼時間點喊 done：

  • Prototype：建置期自檢通過後。
  • Alpha：verify 通過後。
  • Beta 以上：測試完成後。

這三個時間點都是建議。你可以更早標記，也可以先多跑幾個步驟再標記。

唯一仍然被要求的事情，是把 load-bearing 的決定寫下來。如果你先用 Assumed 的方式假設一個決定、直接建置，功能就會一直帶著「欠 ratification」的標記。不過，這個標記同樣不會阻擋你標記 done。

它明確承諾不會做的事

工具能做什麼很重要，但它不會做什麼，同樣重要。這套流程把自己的界線畫得很清楚：

  • 不會偷偷判斷功能完成，也不會扣住 done。done 永遠是你的宣告；深度只設定建議的時機。
  • 不會發明你沒做過的決定，再把它藏起來。如果建置時必須猜一個 provider、一個資料形狀或一個設計，/develop 會停下來，把你送回 /architect。你可以 override、直接建置，但流程會把這個假設寫成一份 Assumed 規格。這道閘自己也承認，它是強力防線，不是絕對保證：/architect 會先替每個值標出來源，/develop 在建置前再檢查一次覆蓋率；較高深度還會建議使用獨立模型審查規格。若仍有遺漏，最後會由 verify 和 test 透過「行為不正確」把問題抓回來。
  • 不會未經你同意連上網路。要搜尋外部 connector 或查詢資料前，它一定會先詢問，並記錄實際使用了什麼。
  • review 不會修改你的程式碼。它只讀取、只產生報告；要不要修改，由你決定。
  • 沒有 skill 會重寫你的文章，也不會伸手修改其他 skill 擁有的檔案。檔案擁有權固定，這正是內容能長期維持可信的原因。

對照失敗模式：這些機制究竟在防什麼？

把上一節學到的機制，和幾種常見失敗模式放在一起看，就會更清楚每條規矩存在的理由。

失敗模式流程裡防它的機制
假綠測試：套件全綠，但功能其實不存在/check verify 會真的啟動應用程式並操作它，還要求留下證據；測試變綠不等於功能已被證明
agent 留下死碼：新舊兩套實作並存/develop 會明確要求刪除被取代的程式碼，並證明沒有殘留引用
自己審自己的盲點/check review 堅持改用與作者不同的模型執行審查
context 變笨：對話越長、成本越高，也越容易迷糊狀態全部放在檔案中；交接時使用 /clear，讓新的 session 從磁碟重新讀取
curated prose 被覆寫：原本整理好的文件被 AI 改壞/sync 只修改自己擁有的行；遇到你的文字只 flag，不覆寫
偷偷做了你沒有核准的決定Step 0 的 input coverage 閘會在缺少決定時停下來；若使用 override，則留下 Assumed 紀錄

前面那些看起來有點囉唆的規矩，其實各自都對準一種具體失敗：防止測試假綠、防止死碼殘留、防止自己審自己的盲點，也防止長對話和自動同步把內容越改越不可靠。

這也是為什麼這套流程值得整條學完，而不是東撿一個 skill、西撿一個 skill。單一機制只能擋住單一類型的問題；把它們串起來，才有機會在不同階段接住不同風險。

小結

深度分成四級：Prototype 只跑 develop；Alpha 加上 verify；Beta 再加 test；GA 則再加上 fresh-model review 與 document。深度只決定 /develop 之後「建議的檢查尾巴」以及建議的 done 時機，不是把你鎖死的軌道，也不會關掉前面那道「把決定寫下來」的閘。develop 之後的每一步都可以跳過，done 永遠由你宣告，跳過的步驟會被誠實記錄。流程也明確承諾：不偷偷標記 done、不藏起尚未完成的決定、不擅自連網、review 不修改程式碼，也沒有 skill 會重寫你的文章。

到這裡，你已經走過這套流程的形狀、狀態如何流轉，以及深度如何拿捏。真正的問題也因此浮現：它和你原本使用的那套 SDD 流程，到底差在哪裡？哪些是它多出來的能力，哪些地方反而是你自己的流程更好？
