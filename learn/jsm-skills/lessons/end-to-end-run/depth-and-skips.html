這次要跑多深：Prototype 到 GA，以及何時跳過

Step 3/4 · 端到端實跑與覆盤

學習目標

能用 Prototype、Alpha、Beta、GA 四級深度判斷這次改動要跑哪些階段，並說出「suggestions, never gates」的界線、這個流程不會做什麼，以及最常見的幾種失敗模式。

前言：上線前改一個錯字，也要跑完整套嗎

你已經知道完整的一條線怎麼跑了。但現實裡的改動大小差很多：有時候是從零開始做一個產品，有時候只是把按鈕上的錯字改掉。如果每個改動都跑滿九個階段，你會把時間浪費在根本不需要的檢查上；反過來說，如果每個改動都只跑 /develop，高風險的付款流程出事時你就來不及了。

這套流程的解法不是「一套標準套到底」，而是讓你在 /scope 的時候就替專案選一個預設深度，再依單一改動的需要加減。這一節要看的就是這把尺：四個深度各自跑哪些階段、什麼時候該跳過、以及流程明確承諾「它不會做」哪些事。

四級深度：從只跑 develop，到整套跑完

深度分成四級。選了哪一級，決定的其實是 /develop 之後「建議的檢查尾巴」要拉多長，以及建議在什麼時間點把功能標成 done。注意開頭這句：它是建議，不是把你鎖住的軌道。

深度develop 之後跑什麼建議的 done 時機適合什麼
Prototype什麼都不跑，只靠 develop 自己的建置期自檢建好並自檢通過，/develop 就自己標 done用完就丟的原型、實驗、個人專案
Alpha加 /check verify，在真的跑起來的應用上驗證verify 通過時低風險功能、但你仍想被證明的內部工具
Beta加 /check verify 再 /test測試進來時，由 test 收尾大多數真正的產品
GA加 /check verify、/test、換模型的 /check review，再 /document整套跑完，且多數功能被視為需要 spec高風險工作、付款、登入、合規、團隊程式庫

用上一節那個登入加待辦清單的小 app 當例子，/scope 會建議 Beta：它是真的產品、有登入這種不能出錯的地方，但又不至於需要每次都請另一個模型來審查。這就是它的運作方式：/scope 依你描述的東西推薦一個深度，用完就丟的實驗會落在 Prototype，小專案落在 Alpha 或 Beta，然後把你的選擇記成專案預設。

這個預設只是基準線。有兩個地方會讓它偏離。第一，某一個高風險功能仍然會走它自己比較重的那條路，不受專案預設拖累。第二，後面的階段會讀這個預設值，所以它們不會去騷擾一個 Prototype 或 Alpha 的專案，逼它跑完整條鏈。這就是為什麼「深度」是一個很省事的設計：它讓整個流程知道，在什麼地方該閉嘴。

一個關鍵誤解：輕的深度不等於跳過 architect

看到 Prototype 只跑 /develop，很容易推論成「輕深度就是不用做決定、不用 architect」。這是錯的。正確的說法是：低嚴謹度的功能通常本來就沒什麼決定要做，所以你很少走到 /architect；但真的需要決定時，那道閘還是會把你送過去。

換句話說，四個深度動的是「/develop 之後的檢查尾巴」，不是前面那道「不要偷偷發明決定」的閘。不論哪一級，流程都只跟你要求同一件事：一個 load-bearing 的決定要被寫下來。其餘都是建議。

Suggestions, never gates：done 永遠是你的

這條哲學在整條流程裡最常被誤解，值得單獨拉出來講。/develop 之後的每一步，包含 /check verify、/test、/check review、/document，都只是深度「建議」你跑的，你可以自由跳過。而「功能完成了」這件事，永遠是你說了算，沒有哪個 skill 會扣住 done 不給你，直到你把格子全部打勾。你跳過的一步，會被誠實地記成「跳過」，不會被當成欠帳來追殺你。

深度只決定「建議在哪個時間點喊 done」。在 Prototype，是建置自檢通過的那一刻；在 Alpha，是 verify 通過；在 Beta 以上，是測試進來之後。這三個都是建議，你可以更早喊、也可以先多跑幾個再喊。唯一仍被要求的那件事，是寫下 load-bearing 的決定。而如果那個決定是靠 Assumed 先建再說的，功能會一直帶著「欠 ratification」的標記，但這個標記同樣不擋 done。

它明確承諾不會做的事

一個工具的能力重要，它的界限也一樣重要。這套流程把界線講得很清楚：

  • 不會偷偷判斷功能完成，也不會扣住 done。done 永遠是你的宣告。深度只設定建議的時機。
  • 不會發明你沒做過的決定並把它藏起來。如果建置被迫要猜一個 provider、一個資料形狀、一個設計，/develop 會停下來把你送回 /architect。你可以 override 直接建，但它會把假設寫成一份 Assumed 規格。它自己承認這是強閘、不是絕對保證，但這道閘是分層的：/architect 先為每個值指名來源，/develop 建置前再檢查一次覆蓋率，高一階的深度還會建議跑一個獨立模型來審規格。漏掉的，最後由 verify 與 test 用「行為不對」抓回來。
  • 不會未經你同意連上網路。要搜尋外部 connector 或查資料之前，它一定先問，而且會記錄它用了什麼。
  • review 不會改你的程式碼。它只讀、只報告，改不改由你決定。
  • 沒有 skill 會重寫你的文章，或伸手進別的 skill 的檔案。擁有權固定，這正是檔案能長期可信的原因。

對照失敗模式：這些機制在防什麼

把上一節學的機制跟幾個常見的失敗模式對起來，你會更清楚每一條規矩存在的理由。

失敗模式流程裡防它的機制
假綠測試：套件全綠，功能其實不存在/check verify 真的把應用開起來操作，並要求證據，測試綠不算證明
agent 留死碼不刪：新舊兩套並存/develop 明確要求刪掉被取代的程式碼，並證明沒有殘留引用
自己審自己的盲點/check review 堅持換一個跟作者不同的模型
context 變笨：對話越長越貴越迷糊狀態全在檔案，交接時 /clear，新 session 從磁碟重讀
curated prose 被覆寫：你寫過的文件被 AI 改爛/sync 只動它擁有的行，遇到你的文字只 flag 不覆寫
偷偷做了你沒核准的決定Step 0 的 input coverage 閘，缺決定就停，override 則留 Assumed 紀錄

看懂了嗎？前面每一節講的那些有點囉唆的規矩，其實都是衝著某一種具體的失敗來的。這也是為什麼這套流程值得整條學完，而不是東撿一個 skill、西撿一個 skill。

小結

深度分四級：Prototype（只跑 develop）、Alpha（加 verify）、Beta（加 test）、GA（加 fresh-model review 與 document）。它只決定 /develop 之後「建議的檢查尾巴」與建議的 done 時機，不是把你鎖死的軌道，也不會關掉前面那道「決定要寫下來」的閘。develop 之後每一步都可跳過，done 永遠由你宣告，跳過會被誠實記成跳過。流程也明確承諾：不偷偷標 done、不藏起沒做的決定、不擅自連網、review 不改碼、沒有 skill 會重寫你的文章。

到這裡，這套流程的形狀、它的狀態怎麼流轉、它的深度怎麼拿捏，你都走過一遍了。但學到這裡，真正的問題才浮上來：它跟你原本在用的那套 SDD 流程，到底差在哪？哪些是它多出來的、哪些是你的流程反而更好？下一節，我們把你自己的流程攤開來，一環一環對照。
