九階段排成一條線：一次完整跑的順序與起手式

Step 1/4 · 端到端實跑與覆盤

學習目標

能在自己的練習專案上排出一次完整跑的順序，並依 greenfield、brownfield、monorepo 三種 repo 形狀選對第一鏟挖在哪。

前言：每個 skill 都會用，卻不知道第一句打什麼

你把九個階段一個一個學完了。/scope 在幹嘛、/architect 的四個模式、/develop 的 spec gate，這些你都說得出來。可是現在真的要開一個新專案，你打開終端機，游標在那裡閃，卻卡住了：第一個該打的是什麼？什麼時候該從 /develop 換到 /check？

會用一個 skill，跟會跑一整條流程，是兩件事。前者是零件，後者是裝配線。零件你都認識了，但裝配線有它自己的順序、自己的交接點，還有「這次根本不用跑滿」的判斷。這一節先把整條線攤開來看，包含它從哪裡開始、什麼情況下從不同的地方開始，以及為什麼它可以隨時停下來、之後再接回去。

一條線的順序

這套工作流預設的路線長這樣：

idea → /scope → /audit → /architect → /develop →
/check verify → /test → /check review → /document → /sync

而在這條線的外面，/debug 隨時待命。有兩件事值得先指出來。第一，/check 出現了兩次，但它不是同一件事跑兩遍：verify 是「把應用真的開起來，證明它會動」，review 是「換一個沒寫過這段碼的模型，讀程式碼挑問題」。它們解決的是不同的風險，所以站在線上的不同位置。第二，這條線不是規定，是一條預設路線。後面你會看到，它其實可以只跑其中一段。

還有一個容易被忽略的重點：這條線真正在傳的東西是狀態，不是程式碼。順序之所以重要，是因為每一棒都吃上一棒的產出、又交出下一棒要用的東西。/scope 產出一份計畫，/architect 讀它、寫出一份規格，/develop 讀規格、寫出程式碼，/check 讀規格、對照程式碼。順序一旦亂掉，交接到手上的東西就不完整，skill 就只能猜。

三種起手式：先看你的 repo 長什麼樣

完整的十個階段是給「全新專案」看的，因為那是涵蓋最多步驟的情境。實際上你的專案可能有別的樣子，起手式也不同。

全新專案（greenfield）

從一句點子開始，照著上面的順序走。有兩個地方次序不能顛倒。第一是「先選技術棧、再建專案、才跑 /audit」：/architect 決定要用什麼 stack 之後，你親手用那個 stack 的工具把空專案骨架生出來，然後才跑 /audit。順序反了的話，/audit 面對的是一個空資料夾，只能靠猜寫 AGENTS.md。第二是「foundations first」：/scope 會把標準、stack、資料模型、設計系統、走路骨架這些地基，當成獨立的功能排在最前面，而不是藏進某個功能裡順手做完。

既有的程式庫（brownfield）

如果你已經有一包程式碼，第一步是 /audit，先讓它讀你真的程式碼、寫出 AGENTS.md，後面每個 skill 才知道你的 stack 與慣例。然後才跑 /scope，它會把你已經做好的功能登記成 existing 或 in-progress（附上程式碼位置），再把「下一個切片」排成 planned。它不會假裝那些舊功能是這套流程建的，所以計畫是誠實的。

Monorepo

一個 repo 裡裝好幾個專案時，一切以「你正在動的那個 workspace」為單位。每個 workspace 有自己的 scope、自己的 spec、自己那一層 AGENTS.md，每個 skill 都待在那個 workspace 裡、用它自己的指令。命令長得像 /scope 。跨 app 的共用地基放到 _root 的 scope，而不是塞進某一個 app 底下。

更小的情境：bug 與小改動

不是每次都要跑滿。一個 bug 直接交給 /debug，它不需要 scope、也不需要 spec。一個小小的改動，可能只跑 /develop 再 /check verify 就結束了。這就是「run only what you need」的意思：這條線是自助餐，不是套餐。

狀態住在檔案裡，所以隨時可以停

這條線之所以能斷在任何一個交接點再接回來，是因為它知道的每一件事都寫進了檔案，而不是留在對話裡。主要有四種：AGENTS.md（專案怎麼運作、stack、指令、慣例）、docs/scope/（粗略的建置計畫）、docs/specs/（每一個真實決定的書面紀錄，也是建置的合約）、design.md（介面的美術方向）。測試檔案則是另一批會留下來的證據。

因為狀態在磁碟上，每個 skill 都會在交接時建議你 /clear，開一個乾淨的 session。新的 session 從磁碟重新讀取現況，直接接著做，不會因為前面聊太久而變貴、變笨，也不會漏掉任何東西。同一份檔案跟著 branch 走，隊友 pull 下來就接得上。

把十個階段走一遍：一個登入加待辦清單的小 app

光看流程圖很抽象，跟著一個具體想法走一次就清楚了。假設你要做一個「登入後看自己的待辦清單」的小 app，全新專案，所以幾乎每個階段都會碰到。

階段你跑什麼這一棒交出了什麼
1/scope粗計畫，選好交付風格與四級深度（這個 app 用 Beta）
2/architect整組技術棧的決定，寫成 Proposed 的 spec
3手動建骨架 + /audit真的有專案可讀，寫出根 AGENTS.md
4/architect登入功能的設計，另一份 spec，並連回 scope 的對應列
5/develop程式碼；spec 狀態推進到 In Progress
6/check verify真的開起來操作，證明登入與清單會動
7/test回歸測試；功能可以標 done，spec 走到 Accepted
8/check review另一個模型對 diff 的資深審查，寫進 docs/reviews/
9/documentPR 描述、changelog 等人看的文字
10/sync把 AGENTS.md、scope、spec 狀態對回程式碼現在的樣子

走完這十步，/clear，下一個功能從乾淨的 session 開始，而它一讀磁碟就知道現在走到哪。這就是這條線完整的形狀：它把幾個指令串成一個會自己收尾的閉環。等這個環走完，專案裡的知識又跟程式碼對齊了。

旁邊那條迴圈：/debug

當東西壞掉、拋錯、行為不對，你會叫 /debug，而它只做一件事：找到並修掉真正的根因。它先重現問題（確定自己修的是真的東西，不是猜的），再把範圍縮到出錯的位置，一次形成一個可否證的假設、測它，錯了就換一個，而不是隨手亂改。找到根因後，它套上「能修好問題的最小修補」，確認問題消失，再交一份回歸測試給 /test，讓同一個 bug 不能悄悄回來。它不偷做功能、不順手整理無關的碼，也不貼症狀補丁。

小結

一次完整跑是 idea → /scope → /audit → /architect → /develop → /check verify → /test → /check review → /document → /sync，/debug 在旁邊待命。它傳的是狀態不是程式碼，而狀態全寫在檔案裡，所以可以斷在任何交接點、清掉 session 再接回來。起手式看 repo 形狀：全新從 /scope 起、先選 stack 再建專案再 /audit；既有程式庫從 /audit 起；monorepo 以 workspace 為單位；bug 直接 /debug，小改動可能只跑 /develop 加 /check verify。

線畫出來了，但你可能注意到一件事：這條線上好幾棒都在碰同一份檔案，也就是規格。/architect 寫它、/develop 改它的狀態、/sync 標記它過時。它到底是怎麼在這些手之間流轉的？下一節就跟著一份規格，走完它的一生。
