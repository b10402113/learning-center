九階段排成一條線：一次完整跑的順序與起手式

Step 1/4 · 端到端實跑與覆盤

學習目標

完成這一節後，你應該能在自己的練習專案上排出一輪完整流程，也能根據 greenfield、brownfield 與 monorepo 的 repo 形狀，判斷第一步該從哪裡開始。

前言：每個 skill 都會用，卻不知道第一句該打什麼

你已經分別學過九個階段：知道 /scope 在做什麼、/architect 有四種模式，也知道 /develop 會經過 spec gate。可是，真正打開終端機、準備開始一個專案時，游標一閃一閃，你可能還是會卡住：第一個該打什麼？什麼時候該從 /develop 換到 /check？

會用單一 skill，和會跑完整條流程，是兩回事。前者像認得一個個零件，後者則是知道怎麼把零件接成裝配線。裝配線有固定的交接點，也有「這次根本不用全部跑完」的判斷。

這一節先把整條線攤開來看：流程從哪裡開始、不同 repo 形狀該從哪裡起步、每一棒交出什麼，以及為什麼流程可以隨時停下來，之後再接著跑。

一條線的預設順序

完整的預設路線如下：

idea → /scope → /audit → /architect → /develop →
/check verify → /test → /check review → /document → /sync

/check 在這條線上出現兩次，但不是同一件事重複跑。

verify 是把應用程式真的開起來操作，證明它能運作；review 則是交給一個沒有參與撰寫這段程式碼的模型，從程式碼與 diff 中找問題。前者驗證「東西有沒有動」，後者檢查「東西是不是做對」，兩者處理的是不同風險，因此會放在不同位置。

這條線也不是硬性規定。它比較像一條預設路線：完整專案可以走完全部階段，bug 或小改動則只需要取用其中一段。

流程真正傳遞的是狀態，不是程式碼

順序之所以重要，不是因為指令排得漂亮，而是因為每一棒都會讀取前一棒留下的產出，再交給下一棒繼續使用。

  • /scope 產出建置計畫。
  • /architect 讀取計畫，寫出規格。
  • /develop 讀取規格，實作程式碼。
  • /check 讀取規格與程式碼，進行驗證或審查。

如果順序打亂，交接到手上的資訊就會不完整，skill 只好靠猜。問題不一定立刻爆出來，卻可能在後面變成錯誤的技術決策、漏掉的測試，或一份和實際程式碼對不起來的規格。

三種起手式：先看你的 repo 長什麼樣

完整流程是針對「全新專案」設計的，因為它涵蓋最多步驟。但實際專案可能已經有程式碼，也可能是多個 workspace 放在同一個 repo 裡。不同形狀，第一步自然不同。

全新專案（greenfield）

從一句點子開始，照著預設順序走。不過有兩個順序不能顛倒。

第一，必須先由 /architect 選定技術棧，再由你使用該 stack 的工具建立空專案骨架，最後才執行 /audit。如果先跑 /audit，它面對的只是一個空資料夾，只能靠猜測產生 AGENTS.md。

第二，要遵守「foundations first」。/scope 會把標準、stack、資料模型、設計系統與走路骨架等地基，獨立排在前面，而不是等做到某個功能時再順手補上。地基若藏在功能裡，後續每個切片都可能用不同方式重做同一件事。

既有程式庫（brownfield）

如果手上已經有一包程式碼，第一步是 /audit。先讓它讀取實際程式碼，整理出 AGENTS.md，後續每個 skill 才知道目前使用的 stack、指令與慣例。

接著才執行 /scope。它會把已經存在的功能登記為 existing，把尚未完成的工作標記為 in-progress，並附上對應的程式碼位置；下一個要做的切片則排成 planned。這樣的計畫不會假裝舊功能也是由這套流程建出來的，專案現況會保持誠實。

Monorepo

一個 repo 裡有多個專案時，流程應以「目前正在修改的 workspace」為單位。每個 workspace 都有自己的 scope、spec，以及自己那一層的 AGENTS.md；每個 skill 也應該在該 workspace 裡，用它自己的指令執行。

命令可以長得像 /scope <workspace> <idea>。如果是跨 app 共用的地基，就放進 _root 的 scope，而不是硬塞到某一個 app 底下。

更小的情境：bug 與小改動

不是每次都需要跑完整套餐。

遇到 bug，可以直接交給 /debug，不需要先做 scope，也不需要先寫 spec。若只是小幅修改，可能執行 /develop，再接 /check verify 就完成。

這就是「run only what you need」：這條線比較像自助餐，而不是每次都得全部端走的套餐。

狀態寫在檔案裡，所以流程可以隨時暫停

這條線能在任何交接點停下來，關鍵在於流程知道的事情都寫進檔案，而不是只留在對話紀錄裡。主要狀態分散在幾個地方：

  • AGENTS.md：專案的運作方式、stack、指令與慣例。
  • docs/scope/：粗略的建置計畫。
  • docs/specs/：每個真實決定的書面紀錄，也是建置時依循的合約。
  • design.md：介面的美術方向。

測試檔案則是另一批會留下來的證據，記錄功能是否真的能運作，以及之後能不能防止同一個問題再次出現。

因為狀態都在磁碟上，每個 skill 在交接時都會建議執行 /clear，開一個乾淨的 session。新的 session 會重新讀取磁碟上的現況，直接接著做，不必把前面冗長的對話重新塞進 context。這能避免 session 越聊越貴、越聊越笨，也降低重要資訊被淹沒的機會。

同一份檔案會跟著 branch 走，隊友 pull 下來後，也能從相同狀態繼續工作。

把十個階段走一遍：登入加待辦清單的小 app

流程圖容易停留在抽象層次。現在用一個具體想法走一遍：假設你要做一個「登入後查看自己的待辦清單」的小 app，而且是全新專案，因此幾乎每個階段都會用到。

階段你跑什麼這一棒交出了什麼
1/scope粗略計畫，選好交付風格與四級深度；這個 app 使用 Beta
2/architect決定整組技術棧，並寫成 Proposed 狀態的 spec
3手動建立骨架 + /audit產生真正可讀的專案，並寫出根層 AGENTS.md
4/architect設計登入功能，建立另一份 spec，並連回 scope 的對應列
5/develop產出程式碼，並將 spec 狀態推進到 In Progress
6/check verify實際啟動並操作 app，證明登入與待辦清單能運作
7/test執行回歸測試；功能可以標記為 done，spec 進入 Accepted
8/check review由另一個模型對 diff 做資深審查，結果寫入 docs/reviews/
9/document整理 PR 描述、changelog 等給人閱讀的文字
10/sync讓 AGENTS.md、scope 與 spec 狀態回應目前的程式碼

十步完成後，執行 /clear，下一個功能就能從乾淨的 session 開始。新的 session 只要讀取磁碟，就知道目前專案走到哪裡。

這就是完整流程的閉環：指令把工作往前推，檔案保存狀態，最後再把文件知識與實際程式碼對齊。

旁邊那條迴圈：/debug

當程式壞掉、拋出錯誤，或行為和預期不同，就叫 /debug。它的任務很單純：找出真正的根因，並用最小修補把問題修掉。

它會先重現問題，確認自己處理的是實際存在的問題，而不是憑感覺猜測。接著縮小範圍，建立一個可以被否證的假設，實際測試；如果假設錯了，就換下一個，而不是隨手改幾行程式碼碰碰運氣。

找到根因後，/debug 會套用能修好問題的最小修補，再確認問題確實消失。最後交出回歸測試給 /test，避免同一個 bug 悄悄回來。

它不會順手開發新功能、不會整理無關的程式碼，也不會只貼一塊補丁掩蓋症狀。

小結

一次完整跑是 idea → /scope → /audit → /architect → /develop → /check verify → /test → /check review → /document → /sync，/debug 在旁邊待命。這條線傳遞的是狀態，不是程式碼；而狀態都寫在檔案裡，所以可以在任何交接點停下來、清掉 session，再從原處接回去。起手式要看 repo 形狀：全新專案從 /scope 開始，先選 stack、再建立專案、最後跑 /audit；既有程式庫從 /audit 開始；monorepo 以 workspace 為單位；bug 直接交給 /debug；小改動則可能只需要 /develop 加上 /check verify。

流程線畫出來後，還有一個問題值得追下去：好幾棒都會碰到同一份檔案，也就是規格。/architect 寫下它，/develop 推進它的狀態，/sync 則在程式碼變化後標記它是否過時。
