規格的一生：Proposed、In Progress、Accepted，還有 Assumed 與 Superseded

Step 2/4 · 端到端實跑與覆盤

學習目標

能沿著一次實跑說出每階段的輸入輸出與誰寫誰讀，尤其規格從 Proposed 走到 Accepted 的每一棒，以及 Assumed 與 Superseded 這兩個支線狀態何時出現、由誰清掉。

前言：同一份文件，四隻手在碰

上一節把線畫出來了。現在仔細看那條線，你會發現有個東西一直被傳下去：/architect 寫它，/develop 讀它、改它的一行狀態，/sync 檢查它、標記它。同一份檔案，四隻不同的手碰過。如果沒有規矩，這份檔案很快就會爛掉，變成前後矛盾、誰也說不準哪一句還算數。

這套流程防止檔案腐爛的方法，是把「誰能改什麼」寫死。哪一個 skill 有權寫規格的內容、哪一個只能動狀態那一行、哪一個只能 flag 不能改，全部固定。這一節就跟著一份規格，看它從出生到退休的每一棒。搞懂這條生命線，你才看得懂交接時「東西為什麼是這樣」。

先認識四種載體，重點放在規格

整個工作流的知識分成四種檔案，各有各的壽命。專案怎麼運作（stack、指令、慣例）寫在 AGENTS.md；粗略的建置計畫寫在 docs/scope/；介面的美術方向寫在 design.md。而今天的主角是 docs/specs/ 裡的規格：一份規格記錄的是「一個真實的決定」，同時也是建置要遵守的合約。

一份規格的內容分成兩個受眾。一半是給 /develop 讀的建置規格：需求與它們的驗收條件、決定本身、設計段落、有序的建置計畫。另一半是給人讀的決策紀錄：背景、考慮過的選項、理由、參考資料。這兩半住在同一個檔案裡，但服務不同的人，這個切法本身就防止了「寫給機器看的東西」被拿去當文件。

規格的一生：五個動作

一份規格會經歷五個動作，順序大致固定。

出生：Proposed，或 Accepted

當 /architect 做出一個真實的決定（例如登入要用哪種方式、資料長什麼樣），它就把這份決定寫成規格，狀態是 Proposed，意思是「決定了，但還沒開始建」。這裡有一個例外：如果這份規格是在「記錄已經上線的東西」，那它出生就是 Accepted。因為那時候的真相已經是程式碼，規格只是補紀錄。判斷的關鍵不是「誰寫的」，而是「這件事還沒建，還是已經建了」。

載入：develop 只讀它需要的部分

建置開始時 /develop 會讀這份規格，但它刻意只讀「要動手需要的部分才叫 build input」：需求與驗收條件、決定、設計、建置計畫。它不會把當初考慮過哪些選項、為什麼否決某個方案那段長長的推論再讀一遍，因為那是歷史，不是建置的輸入。這條規矩同時省 context，也讓建置的人不會被舊的辯論牽著走。

改狀態：只有 develop 能推進那一行

建置的過程裡，/develop 會把狀態那一行從 Proposed 改成 In Progress；等這個功能建好、也驗證過，再從 In Progress 改成 Accepted。這裡的重點是「非常窄的改動」：/develop 只碰狀態那一行，它絕對不會去改決定本身的內容。決定是 /architect 的領土，建置的人只能回報進度，不能偷偷重新設計。

替換：architect 把舊的標成 Superseded

如果一個決定後來被真正推翻了，/architect 會寫一份新的規格，然後把舊的標成 Superseded，並留下一個指向新規格的指標。它不刪掉舊的，因為歷史要可讀：半年後有人問「當初為什麼這樣做」，那份被取代的規格還在，只是上面寫著它已經被誰取代。刪掉它就等於抹掉決策的軌跡。

標記：sync 發現過時就舉手

最後，如果後來的某個改動悄悄讓一份規格跟現況對不上，/sync 會把它 flag 出來，讓真人去處理。注意它只 flag，不改。/sync 的原則是「外科手術式、只動它擁有的那些行」，它不會去重寫你的規格內容，也不會擅自判定某個決定作廢。舉手是最保守、也最安全的做法。

支線狀態 Assumed：當你先建再說

上面是一條主線，但有一條支線你一定要認識，因為它正是這套流程「允許你作弊、但不讓你偷偷作弊」的地方。

想像這個情境：/develop 要開始建了，卻碰到一個 load-bearing 的選擇（也就是這個選擇會影響到很多東西、不決定就沒法建），可是根本沒有對應的規格。它會停下來，給你三條路：先去 /architect 把決定做出來（建議路線）、你判斷這裡沒什麼好決定的直接建、或者你想先往前走，那就「先建，但記下來」。

如果你選第三條，/develop 不會默默猜一個。它會寫一份小規格，狀態標成 Assumed，裡面記下它建在哪個假設上、是誰授權它先建的、以及它碰了哪些程式碼。這是 /develop 唯一被允許建立的規格，而且只能建成這一個狀態。從此，這個功能就帶著一個「欠 ratification」的標記。重點來了：這個標記不會擋住你把功能標成 done。它只是誠實地讓這個未經思考的決定留在 repo 裡，而不是逃進聊天記錄。

要清掉這個標記，你得再跑一次 /architect，請它對著已經建好的程式碼，好好把這個決定審一遍，這就叫 ratification（追認）。審完有兩種結果：假設站得住，就把真正的理由補上、拿掉 Assumed 的標記；假設是錯的，就寫一份修正版規格、把舊的標成 Superseded，讓 /develop 照著重建。整條路走完，你既保持了前進的速度，又沒有讓任何一個決定消失在對話裡。

誰能碰哪個檔案：一張表定生死

前面反覆講「只有誰能改什麼」，這裡把它收成一張表。檔案之所以能長期可信，就是因為這張表不會浮動。

design.md 與它指向的 CSS 值developdevelop、checkdevelop

這張表背後是兩條鐵律：只有 /architect 能寫規格的內容，也只有它能清掉 Assumed；只有 /develop 能沿著建置生命週期推狀態，而它唯一能建的新規格就是那個 Assumed 骨架。單一擁有權，正是這些檔案不會隨著時間糊成一團的原因。

串起全場的那條線：驗收條件

還有一條線在整條流程底下跑，把每一棒串起來，那就是驗收條件（acceptance criteria）。/architect 寫規格時，會把每一個需求變成一句簡短、有編號的「怎樣才算完成」，例如「登入的人只會看到自己的待辦」。然後建置計畫裡的每一個任務，都要指名它服務哪一號條件。/develop 建完之後寫下的檢查步驟，追溯回的是同一組編號；/check verify 真的去跑那些步驟；/test 把其中會長期成立的鎖進測試套件。

於是同一個需求可以被一條直線追下來：從決定，到滿足它的程式碼，到它會動的證明，再到防止它壞掉的測試。沒有重要的東西漏量，也沒有哪個東西明明沒被證明卻被標成 done。這就是「端到端」最實質的意義：不是跑過九個指令，而是這條線沒有斷點。

小結

一份規格由 /architect 建立，出生是 Proposed（若在記錄已上線的東西則直接 Accepted）。/develop 只讀它需要的建置段落，只推狀態那一行（Proposed → In Progress → Accepted），絕不改決定本身。/architect 寫新規格並把舊的標 Superseded；/sync 只 flag 過時的，不動刀。當開發先建再說時，/develop 寫一份 Assumed 小規格，欠一個由 /architect 做的 ratification，而這個標記永遠不擋 done。底下還有一條驗收條件線，把需求、程式碼、證明、測試串成一條直線。

規格的一生看完了，你現在應該能解釋「為什麼每一棒只碰它該碰的」。不過還有個更實際的問題沒回答：這些階段每次都要全跑嗎？一個改個文案的小改動，也要跑 review 跟 document 嗎？下一節要看的，就是用四級深度決定「這次到底要跑多深」。
