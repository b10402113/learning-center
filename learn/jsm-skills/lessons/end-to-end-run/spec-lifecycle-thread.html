規格的一生：從 Proposed 到 Accepted，還有 Assumed 與 Superseded

Step 2/4 · 端到端實跑與覆盤

學習目標

這一節要追蹤一份規格的完整生命線：誰建立它、誰讀它、誰能改它，以及它如何從 Proposed 走到 Accepted。你也會看到兩條支線何時出現：Assumed 代表「先建再追認」，Superseded 則代表「這個決定已被新決定取代」。

前言：同一份檔案，不能讓四隻手隨便亂改

上一節畫出了工作流的主線。仔細看，你會發現有一個東西一路被交接：/architect 寫規格，/develop 讀規格並推進狀態，/sync 檢查它是否仍符合現況，其他流程也會依照它做事。

同一份檔案被不同角色碰過，如果沒有清楚的權限邊界，它很快就會像多人共編卻沒有版本規則的文件：內容互相矛盾，狀態與實作對不起來，最後沒人說得準哪一句才算數。

這套流程的解法很直接：把「誰能改什麼」固定下來。哪個 skill 可以寫規格內容、哪個只能改狀態那一行、哪個只能提出過時警告而不能動內容，都先定義好。接下來就跟著一份規格，看它從出生、建置，到被取代或追認的每一棒。

先認識四種載體，今天主角是規格

整個工作流的知識分散在四種檔案中，每一種都有自己的用途與壽命。

  • 專案如何運作，例如 stack、指令與慣例，寫在 AGENTS.md。
  • 粗略的建置計畫，放在 docs/scope/。
  • 介面的美術方向，寫在 design.md。
  • 一個真實決定，以及建置時必須遵守的合約，寫在 docs/specs/ 的規格中。

一份規格同時服務兩種讀者。

給 /develop 的部分，是可以直接拿來建置的內容：需求、驗收條件、已做出的決定、設計段落，以及有順序的建置計畫。

給人讀的部分，則是決策紀錄：當時的背景、考慮過哪些選項、為什麼否決某些方案，以及相關參考資料。

這兩部分放在同一份檔案裡，卻不是同一種用途。建置時只讀需要的內容，可以避免把過去的辯論誤當成現在的工作指令。

規格的一生：五個主要動作

一份規格大致會依序經過五個動作：出生、載入、改狀態、替換，以及標記過時。

1. 出生：Proposed，或直接是 Accepted

當 /architect 做出一個真實決定，例如登入要採用哪種方式、資料要長什麼樣子，就會把決定寫成規格，初始狀態通常是 Proposed。

Proposed 的意思是：「決定已經做出來，但建置還沒開始。」

有一個例外：如果這份規格是用來記錄已經上線的功能，它一出生就可以是 Accepted。因為此時真正的現況已經存在於程式碼中，規格只是把決策補記下來。

判斷起始狀態的關鍵，不是「誰寫了這份文件」，而是「這件事還沒建，還是已經建好了」。

2. 載入：develop 只讀建置需要的部分

建置開始時，/develop 會讀取規格，但不會把整份文件一口氣吞進 context。

它只把真正需要動手的部分當成 build input：

  • 需求與驗收條件
  • 已做出的決定
  • 設計內容
  • 建置計畫

至於「當初考慮過哪些選項」或「為什麼否決某個方案」，通常屬於歷史紀錄，不是目前的建置輸入。

這就是 progressive disclosure 的實際作用：先只揭露眼前任務需要的資訊，而不是把所有背景都塞進 context。context 變小，agent 比較不容易被舊辯論帶偏，也不會因為資訊過量而抓錯重點。

3. 改狀態：只有 develop 能推進建置狀態

建置開始時，/develop 會把狀態從 Proposed 改成 In Progress。功能完成並且驗證過後，再把它改成 Accepted。

但這裡的權限非常窄：/develop 只能改狀態那一行，不能修改決定本身。

這條界線很重要。決定是 /architect 的領土；建置中的 agent 可以回報進度，卻不能因為實作途中遇到麻煩，就偷偷把原本的設計改掉。

失敗模式：如果讓 /develop 同時負責建置與重新設計，它可能為了讓目前的程式碼「看起來能過」而改寫規格。最後文件與程式碼都像是完成品，卻沒有人真正審過那個新決定。

4. 替換：architect 將舊規格標成 Superseded

如果原本的決定後來真的被推翻，/architect 會建立一份新的規格，再把舊規格標成 Superseded，並留下指向新規格的指標。

舊規格不會被刪掉。它雖然不再代表目前的決定，卻仍然保存著決策歷史。半年後有人問「當初為什麼會這樣設計」，還能回頭看到當時的背景與理由。

刪除舊規格，就像把道路上的舊路標整支拔掉：現在的人看不到以前怎麼走，也無法知道決定是在什麼時候、因為什麼原因改變的。

5. 標記：sync 發現過時就舉手

如果後續的程式碼改動，讓規格與現況對不上，/sync 會把問題 flag 出來，交給真人處理。

它只標記，不改內容。這是 /sync 的核心原則：採取外科手術式的最小改動，只碰自己擁有的那些行。

/sync 不會重寫規格，也不會擅自判定某個決定已經失效。它只負責舉手說「這裡可能不一致了」，而不是自行拿刀進去改。這種保守做法看似慢一點，卻能避免同步工具把原本精心整理的 curated prose 覆寫掉。

支線狀態 Assumed：允許先建，但不允許偷偷猜

主線之外，還有一條重要支線：Assumed。它處理的是「建置已經卡住，但規格還沒有做出決定」的情況。

假設 /develop 遇到一個 load-bearing 的選擇，也就是會影響許多後續工作、沒有決定就無法繼續建置的選擇，但 repo 裡找不到對應規格。此時它會停下來，提供三條路：

  1. 先回到 /architect，把決定正式做出來。這是建議路線。
  2. 判斷這裡沒有真正的設計決定，直接建置。
  3. 先往前建，但把使用的假設記錄下來。

如果選第三條，/develop 不會默默猜一個答案，也不會把決定藏在對話記錄裡。它會建立一份小規格，狀態標成 Assumed，並記下：

  • 這次建置依據的假設
  • 誰授權先建
  • 哪些程式碼受到這個假設影響

這是 /develop 唯一可以建立的規格類型，而且只能建立成 Assumed。功能仍然可以被標成 done；Assumed 不會阻擋完成狀態。它的作用不是當門禁，而是留下「這裡還欠一次正式追認」的明確記號。

失敗模式：如果不留下 Assumed，agent 可能先選一個看似合理的方案，功能也順利完成，卻讓這個未經討論的決定永久躲在程式碼裡。測試可能是綠的，但綠燈只代表目前的行為符合目前的測試，不代表當初的決定真的正確。

清掉 Assumed：由 architect 做 ratification

要清掉這個標記，必須再跑一次 /architect，針對已經建好的程式碼重新審視這個決定。這個過程叫做 ratification，也就是追認。

審查後有兩種結果。

  • 如果原本的假設站得住腳，/architect 會補上真正的理由，並移除 Assumed 標記。
  • 如果假設是錯的，/architect 會建立修正版規格，把舊規格標成 Superseded，再讓 /develop 按照新決定重建。

這裡不能讓建置 agent 自己審自己。負責先做假設的角色，通常最熟悉自己當時的脈絡，也最容易忽略盲點；把追認交給 /architect，才能讓決定重新經過設計層的檢查。

誰能碰哪個檔案：一張表定義權限

前面一直說「只有誰能改什麼」，現在把規則集中在一張表裡。檔案能長期保持可信，靠的不是大家自覺，而是權限邊界固定。

檔案誰建立誰讀誰能改
AGENTS.md 與它的 CLAUDE.md 指標audit每個 skillsync
docs/scope/ 的計畫scopearchitect、developdevelop 推進它，scope 與 sync 對帳
docs/specs/ 的規格architect（加上 develop 可建立的 Assumed 骨架）developdevelop 只推狀態、只建 Assumed；architect 擁有全部內容、清除 Assumed、標記被取代；sync 標記過時的規格
design.md 與它指向的 CSS 值developdevelop、checkdevelop

這張表背後有兩條鐵律：

  • 只有 /architect 能寫規格內容，也只有它能清除 Assumed。
  • 只有 /develop 能沿著建置生命週期推進狀態，而它唯一能新建的規格就是 Assumed 骨架。

這就是單一擁有權的價值。每個角色都知道自己的工具箱裡有哪些工具，也知道哪些抽屜不能碰。久了之後，文件才不會因為多人接手而逐漸糊成一團。

串起全場的那條線：驗收條件

整條流程底下還有一條把各階段串起來的線，那就是驗收條件（acceptance criteria）。

/architect 寫規格時，會把每個需求轉成一句簡短、具編號的完成條件。例如：「登入的人只會看到自己的待辦。」這個編號接著會一路出現在建置計畫、檢查步驟與測試中。

  • 建置計畫中的每個任務，要指明自己服務哪一號驗收條件。
  • /develop 完成後，要寫下可以檢查這些條件的步驟。
  • /check verify 會實際執行那些步驟。
  • /test 會把需要長期維持的條件鎖進測試套件。

於是，同一個需求可以沿著一條直線追蹤：

決定 → 程式碼 → 可運作的證明 → 防止回歸的測試

這才是端到端的實質意義。重點不是跑過幾個指令，而是每個重要需求都有對應的程式碼與證明；沒有被證明的東西，不應該只是因為表面上完成，就被標成 done。

失敗模式：如果只看測試是否通過，可能得到假綠測試：測試本身跑成功了，卻沒有真正覆蓋驗收條件。驗收條件編號把需求、檢查與測試綁在一起，才能降低「測試綠了，但功能其實沒被證明」的風險。

小結：每一棒只碰自己該碰的東西

一份規格通常由 /architect 建立，出生時是 Proposed；如果它是在記錄已經上線的內容，則可以直接是 Accepted。/develop 只讀建置需要的段落，只推進狀態那一行：Proposed → In Progress → Accepted，不改決定本身。/architect 負責建立新規格、清除 Assumed，並把被推翻的舊規格標成 Superseded；/sync 只標記過時，不自行改刀。當開發必須先建再說時，/develop 會建立一份 Assumed 小規格，之後由 /architect 做 ratification；這個標記不會阻擋 done。底下的驗收條件，則把需求、程式碼、證明與測試串成一條可追蹤的線。

到這裡，你應該能說明每一棒為什麼只能碰它該碰的部分：建置不能偷偷重新設計，sync 不能覆寫 curated prose，假設不能消失在聊天記錄裡，規格被取代也不能抹掉歷史。
