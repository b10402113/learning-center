覆盤：把 jsm-skills 對回你自己的 SDD

Step 4/4 · 端到端實跑與覆盤

學習目標

拿你自己的 SDD 流程，逐項對照 jsm-skills 的九個階段。你要能指出它多了什麼、少了什麼，也能說清楚哪些做法值得搬回自己的工作方式。

前言：學它不是為了換掉你的流程

你原本已經有一套能運作的流程：先用 grill 把問題問透，再寫成 spec，拆成 issues，接著實作，最後 review。現在你又花了一輪時間，把 jsm-skills 的九個階段拆開來看。真正值得問的問題是：這兩套流程到底差在哪裡？哪些是 jsm-skills 多做的、值得帶走？哪些地方反而是你的流程更順，應該繼續保留？

這一節不是要你把原本的流程整套丟掉。學新流程最有價值的地方，通常不是整包採用，而是看清楚別人怎麼處理同一個問題，再挑出一兩個真正補到缺口的做法。我們把這當成一次覆盤：先並排比較，再逐項檢查，最後列出你真正打算改動的地方。

第一步：把兩條線並排

先做最機械、也最容易看出差異的動作：把兩套流程的階段對起來。以你原本的 grill → spec → issues → implement → review 為例，大致可以這樣看：

你流程的環節對應到 jsm-skills差異在哪
grill（把問題問透）/architect 的 staged design conversationjsm 把設計討論放進「一個決定、一份 spec」的框架，邊釐清問題，邊產出驗收條件
spec/architect 寫入 docs/specs/jsm 的 spec 有生命週期，會從 Proposed 走到 Accepted，也有固定的內容擁有者
issues/scope 的計畫 + /develop 的 build planjsm 用一份 living scope，加上每個任務明確列出的驗收條件
implement/developjsm 在真正動手前多了一道閘，要求 agent 不要自行偷做尚未決定的事
review/check reviewjsm 要求使用不同模型，並把執行期的 verify 和讀碼 review 分開
（沒有）/audit、/check verify、/test、/document、/sync、/debug這六個是 jsm-skills 額外拆出的階段

表格填完後，答案其實已經浮現一半：你的五個環節幾乎都有對應，只是包裝方式不同；而 jsm-skills 多出來的部分，剛好集中在你原本沒有特別處理的地方。

它多出來的環節，哪些值得搬

接著逐一看它多做了什麼，以及這些做法對你的流程代表什麼。

1. 專案慣例的顯式檔案：AGENTS.md

在你原本的流程裡，專案怎麼跑、應該遵守哪些慣例，可能散落在對話、README，甚至某個人的記憶裡。jsm 把這些規則提升成一等公民：/audit 會讀取實際程式碼，寫出 AGENTS.md；而且這些檔案可以巢狀。root 的檔案管理全域規則，src/payments/ 底下的檔案則管理該區域。

每個 skill 執行時，會讀取離自己最近的那份檔案，因此同時取得全域規則與區域規則。它的價值不只是「讓 AI 看得懂」，更是讓專案的運作方式有一個單一來源，不再是每個人腦中各自保存一份版本。

2. scope 是活的：replan 與 add

你的 spec 可能比較像一次定稿；jsm 的 scope 則是一份 living plan。功能會從 planned 走到 designed、building、verified，最後到 done。

不帶參數執行 /scope 時，它會回頭對帳：上次做到哪裡，接下來該做什麼。需要重新安排工作時，可以使用 replan；過程中臨時冒出小功能，則可以用 add 收進來。

如果你的工作經常在進行中長出新需求，這種「計畫會跟著專案一起長大」的機制，可以省掉重新開一份文件、再手動對齊進度的麻煩。

3. spec 的生命週期與固定擁有權

前一節已經完整談過這件事。它的巧思有兩層。

第一層是狀態。從 Proposed 到 In Progress，再到 Accepted，讓「這個決定到底完成了沒、驗證了沒」變成檔案上看得見的事實。

第二層是擁有權。只有 architect 能修改 spec 內容，只有 develop 能推進狀態，sync 只能標記問題而不能直接改內容。這樣可以避免多人多手一起修改，最後把文件改成誰也不敢相信的版本。

如果你的 spec 常常寫完就沒人知道它現在還算不算數，這項做法很值得學。

4. 驗收條件串成的直線

需求、程式碼、證明與測試，使用同一組編號一路串起來。你的流程可能也有 traceability，但 jsm 把它推得更硬：每個 build 任務都要指明自己服務哪一條 AC，verify 驗證的也是這些 AC，test 鎖定的同樣是這些 AC。

這讓「功能算不算完成」不再只是感覺，而是能不能指回某個明確編號。當然，這裡仍然要小心假綠測試：測試通過，不代表它真的證明了需求；如果測試沒有對準正確的 AC，綠燈也可能只是看起來很安心。

5. verify 與 review 拆開，尤其是跨模型 review

這可能是你目前流程最大的缺口。你原本的 review，很可能仍然是同一個模型，或同一個人，從頭做到尾再審一次。

jsm 把兩個問題拆開：

  • verify 問的是：「這個東西真的會動嗎？」它驗證執行期行為。
  • review 問的是：「這段程式碼設計得好嗎？」它專注在讀碼與結構。

而 review 還要求換一個沒有寫過這段程式碼的模型。原因很直接：模型審自己，很容易把自己的假設當成正確答案。就像自己出題、自己改考卷，最容易漏掉的正是自己根本沒想到的盲點。

這是你目前流程裡可能沒有、但導入成本最低、回報很直接的一項改善。

6. 收尾的 document 與 sync

你的流程可能在 review 通過後就結束了。jsm 則在最後補上兩個收尾動作。

/document 會根據真正的 commits 與 diff，寫出 PR 描述、changelog 與 release note。/sync 則把 AGENTS.md、scope 與 spec 狀態，對回程式碼目前的真實樣子。

這兩個動作照顧的是下一個接手的人。沒有它們，專案知識會慢慢和程式碼脫節；而脫節的文件比完全沒有文件更危險，因為它會讓人帶著錯誤地圖上路。

它不替你承擔的部分

覆盤不能只看優點。這套流程也有幾個明顯留白，採用時要知道哪些責任仍然在你身上。

  • 它沒有強制力。整條流程是「建議」，不是閘門。沒有 CI 會擋住你，也沒有系統會強迫你一定要跑完。它能不能發揮效果，取決於團隊紀律；這和有硬性 gate 的流程，是完全不同的哲學。
  • 它不處理團隊、CI 與部署。review 只負責寫出發現，不直接改碼；push 與 PR 也永遠要由你確認。它假設你已經有自己的協作與交付方式。
  • 維護檔案的成本仍然由你支付。AGENTS.md、scope 與 spec 都需要人維護。/sync 只是讓同步變便宜，不是讓維護變成免費。如果專案規模不值得付出這些文件成本，硬套反而會增加負擔。

還有一點要看清楚：它不是「什麼都幫你想好」。它的 debug 是一條獨立的根因分析迴圈，明確拒絕順手加入功能，或重整無關的程式碼；它的 Loop 只是時間到了就重跑，不會替你判斷現在是否真的值得重跑。

它把判斷留給你。這是優點，因為 agent 不會擅自替你擴大範圍；也是限制，因為最後該不該繼續，你仍然要自己決定。

你的流程可能更好的地方，記得保留

反過來，也有一些你做得好的地方，不必因為學了新流程就丟掉。

grill 那種把問題追問到見底的深度，是很多流程缺少的能力。jsm 的 design conversation 也有提問紀律，但你可以保留自己更嚴格、更有壓力測試效果的問法。

issues 把 spec 拆成細粒度、能在 tracker 上追蹤的工作項，對團隊協作非常實用。jsm 的 build plan 比較偏向建置本身，沒有處理 issue tracker 的完整協作層。

另外，Loop/Harness 那種自動反覆迭代的能力，也是 jsm 刻意不碰的領域。如果你的工作需要持續執行、觀察結果、再自動調整，就不該因為採用 jsm 而放棄這項能力。

把這些放回對照表，你會發現兩套流程其實是互補的：jsm 補上驗證與收尾，你則補上追問深度與協作細節。

具體要搬哪幾件事

覆盤最後必須落地。如果只能挑三到四件事帶回自己的流程，我會這樣選：

  1. 先補跨模型 review。這填的是目前最大的洞，成本也最低。先從一個小 PR 開始，讓不同模型審一次，觀察它抓到哪些原本沒被看見的問題。
  2. 把決定寫成檔案，並指定單一擁有者。不必整套搬過來，可以先建立一條規則：每個重大決定各有一份檔案，只有指定的人能改內容，其他人只能推進狀態或提出問題。
  3. 每次改動先選擇深度。避免兩個極端：小改動也跑完整流程，或高風險改動卻完全略過檢查。先在心裡或文件上標出從 Prototype 到 GA 的深度，再決定要跑哪些階段。
  4. 收尾增加一輪 sync。即使只是手動執行一次，也把慣例檔與計畫對回程式碼現況。長期下來，能省掉大量「文件和程式碼已經不一致」的整理時間。

小結

覆盤的方法是先並排，再逐項對照。你的 grill、spec、issues、implement、review，在 jsm-skills 裡幾乎都有對應，只是包裝方式不同；它多出的則是 audit、verify、test、document、sync 與 debug。值得搬回來的做法，包括專案慣例的顯式檔案、活的 scope、spec 生命週期與固定擁有權、串起來的驗收條件、跨模型 review，以及收尾的 document 與 sync。它不提供強制閘門，也不處理團隊協作與交付；文件維護成本仍然要由你承擔。你的追問深度、細粒度 issue 追蹤與自動迭代能力，則值得保留。最後挑三到四件真正能落地的事，先從跨模型 review 開始。

四節走到這裡，你已經看過流程的形狀、規格如何流轉、工作深度如何拿捏，也完成了它和自己 SDD 的對照。接下來最有價值的動作，是打開練習專案，真的跑一次。

實跑時，你一定會遇到文章沒有寫到的縫隙。那正是這套流程把判斷權交回給你的地方，也是最值得記下來、再回頭修正流程的地方。
