覆盤：把 jsm-skills 對回你自己的 SDD

Step 4/4 · 端到端實跑與覆盤

學習目標

能拿自己 SDD 的每個環節逐項對照 jsm-skills 的九階段，指出它多了什麼、少了什麼，並講清楚你打算把哪些做法搬進自己的流程。

前言：學它不是為了換掉你的流程

你原本已經有一套在跑的東西了：grill 把問題問透，寫成 spec，拆成 issues，實作，最後 review。現在你又花了一整輪把 jsm-skills 的九個階段拆開來看。那麼真正的問題來了：這兩套到底差在哪？哪些是它多出來的、值得你搬走，哪些是你的流程反而更順、應該保留？

這一節不是要你把原本那套丟掉，換成這套。學一套新流程最大的價值，往往不是整包採用，而是看清楚「同一件事，別人怎麼解」，然後挑走一兩個真正補到洞的做法。所以我們把它當成一場覆盤：先並排，再逐項對照，最後列出你打算動的地方。

第一步：把兩條線並排

先做最機械的動作，把兩套階段對起來。以你原本的 grill → spec → issues → implement → review 為例，大致可以這樣對照：

你流程的環節對應到 jsm-skills差異在哪
grill（把問題問透）/architect 的 staged design conversationjsm 把它包在「一個決定一份 spec」的框架裡，邊問邊產出驗收條件
spec/architect 寫入 docs/specs/jsm 的 spec 有生命週期（Proposed 到 Accepted）與固定擁有者
issues/scope 的計畫 + /develop 的 build planjsm 用一份 living scope 加上每個任務指名的驗收條件
implement/developjsm 在前面加了一道「不准偷做決定」的閘
review/check reviewjsm 堅持用不同模型，還把它跟執行期的 verify 拆成兩件事
（沒有）/audit、/check verify、/test、/document、/sync、/debug這些是 jsm 多出來的六個環節

光是把表填完，答案就浮現一半了：你的五個環節，它幾乎都有對應，只是包裝不同；而它多出來的，剛好就是幾個你原本沒特別處理的地方。

它多出來的環節，哪些值得搬

逐一來看它多做了什麼，以及每一項對你意味著什麼。

1. 專案慣例的顯式檔案：AGENTS.md

你原本的流程裡，專案怎麼跑、用哪些慣例，很可能散在對話、README 或你的記憶裡。jsm 把這件事變成一等公民：/audit 讀真的程式碼，寫出 AGENTS.md，而且它可以巢狀，root 一份管全部，src/payments/ 底下再一份管那個區域。每個 skill 工作時讀「最近的那一份」，所以同時看到全域與區域規則。這件事的價值不只是給 AI 看，而是讓「專案的運作方式」有單一來源，不會每個人腦袋裡一套。

2. scope 是活的：replan 與 add

你原本的 spec 比較像一次性的定稿。jsm 的 scope 是一份 living plan：功能會從 planned 走到 designed、building、verified、done，而一個沒帶參數的 /scope 會回頭對帳「我上次做到哪、下一步是什麼」。還有 replan 用來在出貨後重新排、add 用來收一個臨時冒出來的功能。如果你的工作常常在過程中冒出新的小需求，這種「計畫會自己長大」的機制會省掉你很多重新開一份文件的麻煩。

3. spec 的生命週期與固定擁有權

上一節整節都在講這個。它的巧思有兩層：狀態（Proposed → In Progress → Accepted）讓「這東西到底建了沒、驗了沒」變成檔案上看得到的事實；擁有權（只有 architect 寫內容、只有 develop 推狀態、sync 只 flag）則防止多人多手把檔案改爛。如果你的 spec 常常寫完之後就沒人知道它還算不算數，這一項很值得學。

4. 驗收條件串成的直線

需求 → 程式碼 → 證明 → 測試，同一組編號一路追下去。你原本的流程可能也有 traceability，但 jsm 把它做成像是硬性的規則：每個 build 任務都要指名服務哪一條 AC，verify 跑的就是這些，test 鎖住的也是這些。這讓「這個功能算不算完成」不再是感覺問題，而是能不能指到編號。

5. verify 與 review 拆開，尤其跨模型 review

這是對你而言缺口最大的一項。你原本的 review 很可能還是同一個模型（或同一個人）在審。jsm 把「這個東西真的會動嗎」（verify，執行期）跟「這段碼寫得好不好」（review，讀碼）拆成兩件事，而且 review 硬性要求換一個沒寫過這段碼的模型，因為模型審自己會同意自己。這是你流程裡目前沒有、但投入成本最低、回報很直接的一項。

6. 收尾的 document 與 sync

你原本的流程大概在 review 通過就結束了。jsm 補了兩個尾巴：/document 從真 commits 與 diff 寫出 PR 描述、changelog、release note；/sync 把 AGENTS.md、scope、spec 狀態對回程式碼現在的樣子。這兩個動作的價值在「下一個接手的人」。沒有它們，專案知識會慢慢跟程式碼脫節，而脫節的知識比沒有知識更危險，因為它會誤導人。

它不給你的，你得自己承擔

覆盤不能只看優點。這套流程有幾個明顯的留白，你搬它的時候要清楚知道自己得補上什麼。

  • 它沒有強制力。整條流程是「建議，不是閘」，沒有 CI 會擋你、沒有系統會強迫你跑。它能不能發揮，完全取決於你的紀律。這跟有硬性 gate 的流程是完全不同的哲學。
  • 它不管團隊、CI 與部署。review 只寫發現不改碼，push 與 PR 永遠要你確認。它假設你已經有自己的一套協作與交付。
  • 維護檔案的成本是你的。AGENTS.md、scope、spec 都要人維護，/sync 只是把它變得便宜，不是免費。如果你的專案不值得這些文件的成本，硬套反而累。

另外有一點要說清楚：它並不是「什麼都幫你想到」。它的 debug 是一條獨立的根因迴圈，明確拒絕順手做功能或重整無關的碼；它的 Loop 只是時間到了重跑，不會幫你判斷該不該重跑。它把「判斷」留給你，這既是它的優點，也是它的限制。

你的流程可能更好的地方，記得保留

反過來，有幾件事你做得好，不必因為學了新東西就丟掉。grill 那種把問題問到見血的追問深度，是很多流程缺的；jsm 的 design conversation 也有 asking 的紀律，但你可以保留自己更狠的那一套。issues 把 spec 拆成細粒度、可在 tracker 上追蹤的工作項，是團隊協作面很實際的優勢，jsm 的 build plan 比較偏「建置用」，不處理 issue tracker 那一層。而 Loop/Harness 那種自動反覆迭代的能力，也是 jsm 刻意不碰的領域。

把這些放回對照表，你會發現兩套其實互補：它補你缺的驗證與收尾，你補它缺的追問與協作細節。

那具體要搬哪幾件

覆盤完總要落地。如果只能挑三到四件事帶回自己的流程，我會這樣挑：

  1. 先補跨模型 review。它填的是你目前最大的洞，成本也最低。先從一個小 PR 開始，讓不同模型審一次，感受一下它抓到什麼同模型沒抓到的東西。
  2. 把決定寫成檔案，並指定單一擁有者。不必整套搬，先從「每個重大決定一個檔案、只有指定的人能改內容、其他人只能推狀態」這條規矩開始。
  3. 每次改動先選深度。避免兩個極端：小改動也上全套，或高風險改動也全部略過。先在心裡（或文件上）標一個 Prototype 到 GA，再決定跑哪些。
  4. 收尾加一輪 sync。哪怕只是手動跑一次，把慣例檔與計畫對回程式碼現況，長期下來省下的「文件跟程式碼不一致」時間很可觀。

小結

覆盤的方法是先並排再逐項對照：你的 grill、spec、issues、implement、review，它幾乎都有對應，只是包裝不同；它多出來的是 audit、verify、test、document、sync 與 debug。值得搬的是專案慣例的顯式檔案、活的 scope、spec 生命週期與固定擁有權、驗收條件直線、跨模型 review，以及收尾的 document 與 sync。它不強制、不管團隊與交付，維護成本要你自己付。你的追問深度、細粒度 issue 追蹤與自動迭代，則值得保留。最後挑三到四件真正落地的事，先從補上跨模型 review 開始。

四節走到這裡，這條線的形狀、規格怎麼流轉、深度怎麼拿捏、以及它對你自己的意義，你都走過一遍了。接下來最該做的事，是打開你的練習專案，真的跑一次。在跑的過程裡，你會遇到文章沒寫到的縫，那正是這套流程要你自己判斷的地方，也是最值得回來問問題的地方。
