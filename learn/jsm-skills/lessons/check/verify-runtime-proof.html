verify：把應用跑起來，用證據下判斷

Step 2/4 · /check：合併前的驗證與審查

學習目標

能跑一輪 /check verify：把規格裡的驗收條件變成可觀察的行為、依 build approach 校準「怎樣才算會動」、實際啟動並操作應用、記下證據帳，最後用證據閘逐條給出 conformance 裁決。

前言：測試全綠，功能還是可能不存在

這是很多工程師都遇過的場景。你做了一個信箱驗證功能，程式碼寫完、測試檔也補了，指令跑下去一片綠。於是你打開 PR，覺得這件事結束了。直到有人真的去點「寄送驗證信」，信沒寄出來，原來那支新增 verified_at 欄位的 migration 寫了、也 commit 了，卻從來沒有在正式環境跑過。資料表根本沒有那個欄位。

測試綠只證明了一件事：作者想到要測的那些程式碼，跑起來是對的。它證明不了那個欄位真的存在，也證明不了規格裡承諾的另一個頁面有沒有被建出來。/check verify 要補的，就是「測試綠」到「功能真的會動」之間那道縫。它不讀你的程式碼猜答案，它把應用真的開起來，去按一遍。

你的角色是驗收工程師

跑 verify 的時候，請把心態切成驗收工程師：相信你親眼觀察到的行為，不相信綠色勾勾。這不是對測試不信任，而是清楚知道測試的極限，一個通過的測試套件，證明的是「作者以為要測的東西」，不是「功能真的存在」。

所以它的做法很直接：先把這次改動拆成幾個「人看著就能判斷」的觀察行為，然後照專案自己的方式把應用跑起來，實際操作那些行為，記錄你看到什麼，最後逐條給出通過或失敗。它是 /test 的執行期對應物：/test 寫下的斷言會往後每次自動跑，verify 則是這次親眼看到。

兩種起手式：feature 與 refactor

同樣是驗證，但改動的性質不同，判斷「怎樣才算過」的方式就不同。第一種是預設的 feature 模式：這次改動新增或改變了行為，你要確認它真的做了那件新的事。第二種是 refactor / regression 模式：改動是行為保持不變的（重構、去重、改名），這時候「有動」不是重點，「動作一模一樣」才是重點。

refactor 模式的做法值得一提，因為它把「不變」變成可以被證明的東西。它會在同一個應用的「改動前」與「改動後」各跑一次，把兩次的輸出抓下來對照。改動前的狀態，優先用一個用完就丟的 git worktree 還原到改動之前的 commit：在工作區裡起一份乾淨的舊版、啟動應用、把每個受影響的介面打一遍、存下原始輸出，再拆掉那個 worktree。只有在 worktree 不可用時，才退回 git stash --include-untracked，而且一定要加 --include-untracked，因為普通的 git stash 會把新增的檔案留在原地，反而污染了那份「改動前」。

兩份輸出逐面比對，行為保持不變的改動應該位元組完全相同。只要出現差異，就當成回歸，把精確的差異抓出來丟給 /debug。這種驗證特別適合沒有測試框架的專案，因為它等於臨時搭起了一張安全網。因為它要同時握著前後兩份輸出，所以通常在一個獨立的子代理裡跑，免得把主對話的上下文塞爆。

載入規格合約：AC-N 與要確認的介面

要驗收，就得先知道「什麼叫做對」。如果這次改動背後有一份治理它的規格（放在 docs/specs/NNNN-<feature>/），那它就是合約。規格裡的 ## Requirements 段會列出有編號的驗收條件 AC-1、AC-2 等等，也會寫明它承諾要做哪些介面，例如某個頁面、某條路由、某張資料表、某支 migration。

載入的方式有優先順序。最好的是規格旁邊那份每個功能專屬的 verify.md，那是 /develop 產出的，裡面的每一步都已經標好它對應到哪個 AC-N，等於一份現成的檢查清單。如果沒有，就退回規格的 ## Requirements，自己把每個 AC-N 變成一個可觀察的檢查。如果這次改動根本沒有規格（例如純粹的小修改、沒有留下決策紀錄），那就跳過這一步，只對照你觀察到的行為來判斷。

把這份合約帶進後面所有步驟之後，你會得到兩份清單：一份要確認是否滿足的 AC-N，一份要確認是否存在的介面清單。後面那步有個關鍵提醒：檢查範圍不要只縮到「有改動的檔案」。一個 AC 或一個介面完全沒有實作，正是這道閘最該抓到的漏，所以它會留在清單上，讓後面的裁決去點名。

校準「算不算會動」：看 build approach

知道要做什麼之後，還要知道「做到什麼程度才算過」。這件事由這個切片的 build approach 決定。同一個功能，用 Tracer Bullet 做的和用 Facade 做的，該有的完成度完全不同。用錯的尺去量，會製造出假失敗或假通過。

build approach 的優先順序是：先看這個功能在 scope 裡有沒有自己的覆寫，有就用它；沒有就用專案預設（寫在根目錄的 AGENTS.md，不然就是 scope 的檔頭）；兩個都沒有，才用推理出的預設值，而且要把這個假設講出來。幾個常見的標準可以幫你對齊：一條穿過每一層的薄薄端到端路徑，要求整條路真的把請求送到真的結果；一個最小可用的核心迴圈，只要求那個迴圈真的會動、周邊配件還不用；一個先接上佔位的 UI 外殼，要求外殼與佔位流程能渲染能導覽，資料源是假的在這個階段是計畫、不是缺陷。

一句話記住這條線：規格說「什麼必須為真」，build approach 說「後面這些層現在有多少是真的」。前者要驗得硬，後者不要拿還允許假裝的部分去判它失敗。

把改動變成可觀察的行為，並決定怎麼啟動

下一步是把抽象的「改動」翻譯成具體的觀察點。先找出 base 分支（main 不存在就用 master），把有改動的檔案列出來（包含還沒 commit 的）。如果有規格合約，那份 AC-N 與介面清單就是你的範圍；如果沒有，就從改動檔案裡寫出二到五個「人看著就能判斷」的具體行為，例如「/pricing 頁面渲染出三個方案，而且點 CTA 會開啟結帳流程」。

接著決定怎麼把應用跑起來。在 monorepo 裡，要跑受影響的那個應用，不是 repo 根目錄，因為根目錄通常沒有完整的啟動方式。啟動指令的尋找順序是：專案自己的 run/start skill、AGENTS.md、package.json 裡的 dev 或 start、Makefile、Procfile、docker-compose。優先採用專案本來就在用的方式。

如果專案沒有明講，就依型別套內建模式。網頁應用起 dev server 然後驅動路由，優先用連上的瀏覽器自動化工具，其次用 agent 自帶的瀏覽器工具，都不行就改用 HTTP 請求抓 HTML 並做一次啟動檢查。後端 API 起 server 後打端點；CLI 帶代表性的參數跑指令；函式庫用一個臨時腳本或 REPL 操作它的公開 API；背景工作就觸發它、看著它跑到結束。如果真的判斷不出怎麼啟動，就問工程師啟動指令，不要瞎猜。

跑、操作、邊跑邊記證據帳

啟動時優先用背景程序，這樣你才能一邊跑一邊互動。如果環境允許，盡量用連接上的工具讓檢查更真實：瀏覽器自動化工具可以真的導覽、點擊、輸入、送出、截圖；資料庫工具可以直接查線上的 schema，確認那支 migration 真的套用了，而不是用猜的。

逐個觀察行為操作時，重點是「抓到能證明的東西」。介面要走到那個路由、實際點擊輸入送出、把結果和錯誤狀態截圖下來，看的是渲染出來的畫面，不是只看回傳 200。API 要送出請求、抓下狀態碼和回應內容、確認形狀與關鍵欄位。CLI 或背景工作要實際跑起來，抓下它的輸出與產物。就算畫面上看起來一切正常，也要去翻 server 或主控台的日誌，看看有沒有錯誤或警告被吞掉。

然後是這個模式的核心習慣：邊做邊記一份證據帳。每操作完一個行為，就在當下把證明你操作過它的東西寫下來。介面的帳是載入的 URL、截圖路徑、你看到什麼；API 的帳是請求行、HTTP 狀態、回應的關鍵欄位；CLI 或工作的帳是指令、結束碼、輸出的節錄；資料層的帳是你對線上 schema 下的查詢與它的結果。這份帳不只是筆記，它等一下會被引用，因為沒有記到證據的行為，不管你多確定，都不算驗過。

逐條裁決：四種結果

操作完之後，把觀察到的東西滾成一份逐條的判斷。如果有載入規格合約，就對每一個 AC-N 與每一個承諾的介面，給出下列四種結果之一。

結果意思下一步
met ✅檢查通過，或介面存在且行為符合規格不用處理
specced but missing 🚫規格有寫，但完全沒有實作，根本沒東西可跑去 /develop 把它建出來
specced but not applied ⚠️程式碼在，但執行期檢查失敗（典型是 migration 沒跑）去套用它
blocked ⚠️缺資料、缺憑證或缺環境，根本跑不了說出需要什麼

這裡有兩個詞很容易被混為一談，但它們要分開報，因為修法完全不同。missing 是「從沒建」，屬於範圍漏掉，要去 /develop 補；not applied 是「建了但沒有生效」，屬於接線漏掉，例如程式碼寫了但 migration 還沒套用。兩個都會擋住「完成」，但要分開講，修的人才知道該補的是實作還是設定。

整條 conformance 要算 PASS，條件很硬：每一個 AC-N 都 met，而且每一個承諾的介面都存在。只要有一個 missing 或 not applied，整體就是 FAIL，即使你的測試一片綠燈也一樣。

證據閘：一個你不能捏造的判斷

這個 skill 存在的目的，就是用「真的跑過」來證明改動會動。所以它設了一道證據閘，四條規則要照字面遵守。

第一，沒有證據，就沒有 ✅。一個行為要能標成 met，前提是你能引用證據帳裡對應的那一筆，指令與輸出、URL 與渲染結果、截圖路徑、查詢與結果。引用不出來，它就只能是 blocked，不能是 met。

第二，沒有真的啟動，就永遠不能 PASS。如果這一輪你根本沒有把應用跑起來（沒起 dev server、沒送出請求、沒跑過任何指令），那你不能對任何一個行為發出 PASS 或 ✅，要老實地把每個行為都報成 blocked，說清楚什麼都沒跑以及原因，然後停手。

第三，用不了的工具是 block，不是 pass。沒有瀏覽器工具、沒有資料庫工具、缺憑證、build 起不來，這些都會讓需要它的行為變成 blocked。退一步說「我看程式碼覺得應該沒錯」，正是這個 skill 被設計出來要防的那種失敗。第四，說出你沒檢查什麼。如果有些行為跑了、有些沒跑，報告一定要把沒跑的那些列在 blocked 底下。一份只跑了一半卻報成全程通過的報告，比完全不跑還糟。

報告與收尾

報告的寫法是「先給結論，再列欠帳」。開頭一句就是裁決（PASS / FAIL / BLOCKED），接著只列失敗或欠處理的項目，通過的那些不用逐條列出來，因為真正的紀錄在證據帳裡。如果這次功能有對應的 scope 列，而且結果是 PASS，就把它的 Verify it 勾起來；同時把這次真的跑過、也通過的 verify.md 步驟逐格打勾，失敗或沒跑到的就留著不勾。

PASS 的時候，它會「建議」你把功能標成 done，而不是幫你卡住。如果 Verify it 是這個功能的最後一格（Alpha 等級），它會說一句「驗過且通過，可以標 done 了，或你想繼續也行」，由你決定。如果後面還有 Test it 之類的格子（Beta 或 GA），它會建議下一步跑 /test，但你同樣可以選擇標 done 跳過。FAIL 或 BLOCKED 的時候，它什麼都不勾，只把缺口講清楚。

收尾還有一個不能省的動作：明確說出你在每個檔案裡勾了什麼。例如「scope：勾了 Verify it；spec：狀態改成 Accepted」。如果找不到對應的 scope 列，就要明說「找不到符合的功能列」，不能默默結束。最後，把自己啟動的程序清乾淨。整個 verify 只確認現實，從不修也不斷言：失敗交給 /debug、沒建的介面交給 /develop、想讓通過的行為永久留下交給 /test。而捏造一個 PASS，是它絕對不能產出的東西，因為後面每一個階段都信任它。

小結

verify 的立場是驗收工程師：相信觀察，不相信綠色勾勾。它先載入規格合約（AC-N 與承諾的介面），依 build approach 校準「怎樣才算會動」，把改動翻成可觀察的行為，然後真的啟動應用、操作、邊做邊記一份證據帳。逐條裁決分四種：met ✅、specced but missing 🚫、specced but not applied ⚠️、blocked ⚠️。它有四條證據閘：沒證據就沒 ✅、沒啟動就永遠不能 PASS、用不了的工具有如 block、要說出沒檢查什麼。整條要 PASS，必須每個驗收條件都 met、每個承諾介面都存在。

verify 回答的是「這東西真的會動嗎」。但就算它會動，程式碼本身可能還有問題，錯誤處理沒做、有安全漏洞、寫法難維護。那種問題 verify 看不見，得換一雙眼睛。下一節要看的 review，就是請一個沒寫過這段碼的模型，來當那雙眼睛。
