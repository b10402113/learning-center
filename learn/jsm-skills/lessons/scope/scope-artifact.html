scope 檔案：一份會長大的計畫

Step 1/5 · /scope：從點子到計畫

學習目標

能說出 scope 檔案的兩段式形狀（At a glance 表加上依 phase 分組的 feature 段），並解釋 feature lifecycle、status、workflow tier 這三套標記各自在文件裡扮演什麼角色。

前言：聊完之後，東西留在哪裡？

想像你週末晚上有個 side project 的點子。你跟 AI 聊了半小時，把要做的功能、先後順序、哪些地方還拿不定主意都講過一輪。當下你很清楚要做什麼，但 session 一關、明天再回來，那份清楚就只剩下模糊的印象。你得從頭再解釋一遍，而且這次講的順序可能跟上次不一樣。

問題往往不在你想得不夠清楚，而是那些想法一直只存在對話裡。對話不是能累積的地方，關掉就散了。`/scope` 要解決的正是這件事：把「要做什麼」從對話裡撈出來，寫成一份有固定形狀的文件，讓它留在 repo 裡，可以一讀再讀、一改再改。

這一節先不談怎麼跑指令，先把那份文件本身看懂。因為你之後每一次的判斷，都是在這份文件的語法上做選擇。

scope 回答什麼、不回答什麼

scope 是一份粗略的、會長大的計畫，預設放在 `docs/scope/` 底下。它回答四件事：要做什麼、用什麼順序做、每件事需要多少流程、哪幾件必須先做決定。它刻意不回答「怎麼做」：不挑框架、不選資料庫、不決定要不要用 ORM。

把工具選擇擋在外面是有理由的。工具會過時、會換代，一份寫滿當代工具名字的計畫，半年後就開始發霉。scope 只描述產品的形狀，所以它可以活很久；真正牽涉到工具的那個決定，留給 `/architect` 在每個功能上單獨處理。

兩段式：先掃一眼，再讀細節

scope 的結構只有兩段。第一段是 At a glance 表，欄位是「編號、功能、階段、狀態」，讓你三秒鐘掃完這個專案有幾件事、各自到哪了。第二段是依 phase 分組的 feature 段，一個功能一個段落，把細節寫在裡面。

這裡有一個容易忽略的設計：建置順序就是段落順序。沒有另一份「build order」清單需要跟段落保持同步，因為順序本身就是閱讀順序。文件少一份要對齊的東西，就少一個出錯的地方。

#FeaturePhaseStatus
1Stack & architectureFoundationin-progress
2Coding standards & toolingFoundationplanned
3Data modelFoundationin-progress
4Core standup loopSlice 1planned

一個 feature 段長什麼樣

每個功能段的標題是 `### 編號. 功能名稱`，後面只掛真正帶著資訊的短標籤，例如 `needs a decision`、一個功能層級的切法覆寫、或一個流程等級的覆寫像 `· GA`。不要寫成「名稱 | 優先序 | 繼承 | …」這種用直線分隔的欄位列，那只是把表格硬塞進標題。

標題底下是三樣東西。第一，一到兩行的 intent，說這是什麼、為什麼重要。第二，只有一行的 `Done when:`，寫出可觀察的完成結果；它是驗收條件的種子，之後由 `/architect` 長成規格，不是現在就把規格寫完。第三，checkbox 步驟，每一格都是一個指令或一個可追蹤的里程碑。

還沒設計過的功能，只有一個格子，就是它的入口指令：需要決定時是 `/architect <功能>`，不需要時直接 `/develop <功能>`。當規格被捕捉之後，`/architect` 會把它填成「已設計」的形狀：`Design it` 打勾、連上規格、`Build it: /develop <功能>` 加上二到五個從規格彙總上來的里程碑，再依等級補上 `Verify it` 與 `Test it`。至於那些細碎的建置任務，全部留在規格自己的建置計畫裡，不搬進 scope。scope 只保留里程碑的彙總。

三套標記，各管一件事

文件上會看到三種標記，很多人第一次讀會把它們混在一起。它們其實各管一件事。

第一套是 feature lifecycle，描述一個功能在流程裡走到哪一步。它從 `planned` 開始，規格被捕捉後進入已設計，接著依序是建置中、已驗證、`done`。這條線的每一格都由不同的階段推進，而「下一個步驟」永遠是第一個沒打勾的格子。

第二套是 status，出現在表格和標題旁。除了 `planned`、`in-progress`、`done`，還有兩個容易搞混的：`existing` 表示這個功能在導入工作流之前就已經存在，`dropped` 表示它被移出範圍但保留歷史。這裡有個關鍵區別：`done` 不等於 `existing`。`done` 是這套流程親手建置並驗證的；`existing` 早於流程，`/develop` 和 `/sync` 都不會去動它。被移出範圍的功能設成 `dropped`，不刪除，因為歷史本身有價值。

第三套是 workflow tier，也就是流程等級，一個專案只有一個預設值，寫在檔案開頭的 `**Workflow:**` 行；個別功能要偏離預設時，才在標題旁掛一個標籤，例如 `· GA`。它決定的是「`/develop` 之後還要跑幾關」：`Prototype` 什麼都不跑，`Alpha` 多跑 `/check verify`，`Beta` 再多跑 `/test`，`GA` 再加一個換模型的 `/check review` 與 `/document`。它也連帶決定什麼時候算完成：`Prototype` 在建置後就算，`Alpha` 要驗證過，`Beta` 和 `GA` 要測試過。所以流程等級不是一個抽象的品質分數，它會直接改動 scope 上要勾的格子。

檔案怎麼放，以及它為什麼要粗

`docs/scope/` 這個位置屬於 `/scope`；規格則歸 `/architect` 管，放在 `docs/specs/`。兩個階段的檔案涇渭分明，`/scope` 不會去寫規格、程式碼或 `AGENTS.md`。

檔案形狀隨產品大小調整。小產品就是一個檔案 `docs/scope/scope.md`。當它大到一眼掃不完，大約十幾個功能、而且分屬幾個明顯不同的領域時，才升級成史詩拆分：把 `scope.md` 改名為 `index.md` 保留總表與每個領域的狀態彙總，再把各領域的段落搬到自己的 `<領域>.md`。原則是按需升級，不要提早拆，而且檔名一律用語意名稱，不用編號。

最後，scope 必須一直保持粗略而小。如果某個領域檔案長到讀不完，那代表你把它拆成了太多細碎功能，或者把建置任務倒進去了。該做的是把功能切得更清楚、把意圖寫得更緊，而不是讓文件膨脹。

小結

scope 是一份放在 docs/scope/ 的活計畫，兩段式：先用 At a glance 表掃一眼，再讀依 phase 分組的功能段。段落順序就是建置順序。功能段有 intent、一行 Done when、checkbox 步驟；未設計的功能只有一個入口指令。三套標記各管一件事：feature lifecycle 管流程走到哪，status 管功能的身分（planned / in-progress / done / existing / dropped），workflow tier 管 /develop 之後要跑幾關、什麼時候算 done。計畫要一直保持粗而小，並且刻意不碰工具選擇。

現在你認得這份文件了，但它不會自己長出來。下一節要看 `/scope` 怎麼從你的一句點子，推斷你其實想 plan、replan 還是 add，然後把整輪規劃走完。
