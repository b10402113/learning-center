專案活著之後：replan 與 add 的節奏

Step 5/5 · /scope：從點子到計畫

學習目標

能在功能出貨後跑一次 replan 把計畫對回現實，並用 add 把中途冒出的單一功能低儀式地收進 scope。

前言：一份放著不管的計畫，一週後就變成謊言

你在第一週把 scope 寫好了，功能清單整齊、順序清楚。然後你開始動手。兩週後回來看那份文件：有一個功能其實已經做完也上線了，狀態卻還停在 `planned`；建置過程中你發現「這樣不行，得先做限流」，但這件事沒人記得寫進計畫；還有一個功能你早就決定不做了，它還掛在清單上，每次掃過去都要重新想一次「這個到底要不要」。計畫沒有錯，它只是沒有跟上現實。

這不是因為你偷懶，而是因為「寫好一份計畫」和「維持一份計畫」是兩件不同的事。前面幾節處理的是前者，這一節處理後者。它也是 `/scope` 最常被使用的那一面，因為真正的開發大部分時間都花在「東西一直出貨、計畫一直要對帳」上。

replan：出貨之後的對帳

當 scope 已經存在、你又打一個不帶參數的 `/scope`，推斷出來的意圖就是 replan。它不是偶爾才需要跑的補救，而是這套流程的日常節奏：每當一個功能或一個階段落地，就再跑一次。

它的開場很實用。因為它會先讀一遍現況並給一段簡短報告：你現在在哪個分支、領先或落後遠端多少、各狀態的功能各有幾個、以及每一個進行中功能的接續點在哪裡。這讓一個空白的 `/scope` 順便變成「我上次做到哪、現在安全地可以接什麼」的定位工具。

讀完現況，它接著做四件事。

  1. 對帳已完成的功能。把真的做完的標成 `done`，而且是從程式碼或規格查證，不是一律蓋章。沒有確認的不勾；已經由 `/develop` 或 `/sync` 推進過的列，就留著不動。
  2. 把假設性決定攤到檯面上。如果某個功能的規格是「假設性」的（當時你先決定動手、還沒正式拍板），它會列成「已建置、待批准」，並指向 `/architect`。這種狀態被當成一種決策債，它不會阻擋功能被標成 done，但會一直顯眼地留在那裡，直到被正式批准。
  3. 登記建置過程冒出的需求。它會去讀那些剛出貨功能的規格裡「後果」與「後續」兩段。如果裡面提到一件還沒成為 scope 列的事，例如「加上限流」，它就變成一個新的 `planned` 列。計畫就是這樣從真實的建置回饋裡長出來的。
  4. 重新排序。把順序與階段重排一次，還沒做的基礎設施保持在最前面；掉出範圍的工作設成 `dropped`，不刪除。如果專案的風險輪廓明顯變了，例如中途加入了付款或驗證，它會重新推薦一次專案的預設流程等級。

做完對帳，它會排出下一片：最低順序的 `planned` 列裡，需要規格的先走 `/architect`，不需要的直接走 `/develop`。整個過程都是就地編輯：調整儲存格、追加列、不重寫整份檔案、也絕不產生一個新的日期檔。

add：把一個中途冒出的功能收進來

不是每一次變動都值得跑一輪完整的對帳。有時候你只是在做的過程中發現「對了，還需要匯出 CSV」，這是一個功能，不是一整個階段。這種時候，你打 `/scope 匯出 CSV`，scope 已經存在、參數又指名了一個功能，推斷出來的意圖就是 add。

add 的儀式刻意壓到最低，它只做幾件事。

  1. 先去重。重讀整份 scope，如果這個功能已經在任何狀態下出現過，就延伸那一列，而不是新增一筆。
  2. 只問必要的。如果意圖或等級不清楚，才問一張短面板；否則直接推斷。要問的是意圖、是否要偏離專案預設的流程等級、以及放在哪個順序與階段。
  3. 提供單一功能的切法面板。最上面的選項是「繼承專案預設」，下面是四種具名切法，只有在真的不同時才掛標籤。
  4. 用發明測試定下要不要規格。和 plan 用的是同一個判斷：會不會需要一個你還沒做的決定。要規格，它的下一步就是 `/architect`。
  5. 追加。在總表加一列（下一個空閒編號、狀態 `planned`），並在對應階段底下加一個功能段，裡面有意圖、一行 `Done when`、以及唯一那個入口格子。史詩拆分的話，就加到正確的領域檔，並更新 `index.md` 的彙總。
  6. 簡短報告。說出這一列、等級、切法、要不要規格，以及下一個指令。

兩種節奏的分工

replan 和 add 的差別，說到底就是全面對帳與單點收錄。replan 週期性地把整份計畫對回現實，把漂移補上、把下一片排出來；add 則是一收到單一功能就低儀式地寫進去，不重跑整輪規劃。兩者都遵守同一套共用的規則：就地編輯、追加而不重寫、去重而不重複。

它們共用的還有一件事：scope 是那個可以累積的地方。對話會蒸發，檔案不會。所以每到一個段落，讓計畫回到跟現實一致，下一個階段、甚至下一個隊友，才有辦法從檔案裡讀出「現在該做什麼」，而不是從一段已經結束的對話裡猜。

小結

replan 是出貨後的日常對帳：開場先報告現況（分支、遠端差距、各狀態數量、進行中功能的接續點），再對帳已完成功能、攤出假設性決定的債、登記建置回饋長出的新需求、重排順序並排下一片。add 是低儀式的單點收錄：先去重、只問必要、提供繼承為預設的切法面板、用發明測試定規格、追加一列與一個功能段。兩者都就地編輯、追加不重寫。假設性決定不會阻擋 done，但會一直被表面化直到批准。

五節走完，你已經看過 `/scope` 的全貌：它產出什麼、怎麼推斷意圖、怎麼依 repo 形狀起手、怎麼選切法，以及怎麼在出貨後維持。下一步就是把它真的跑在你的練習專案上。從一句點子開始，跑一次 `/scope`，然後看那份計畫怎麼帶著你往前走。
