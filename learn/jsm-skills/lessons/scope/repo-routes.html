三種起手式：greenfield、brownfield、monorepo

Step 3/5 · /scope：從點子到計畫

學習目標

能判斷手上的 repo 屬於 greenfield、brownfield 還是 monorepo，說出各自的第一步，並解釋為什麼所有路線都得先鋪基礎再做功能。

前言：同一個點子，三種第一步

假設你要做一個非同步站立會議工具。這個點子本身沒變，但你手上有三個不同的資料夾：一個是剛建立、什麼都還沒有的空目錄；一個是寫了三年、有十幾個畫面的老專案，你想把這個工具加進去；還有一個是把網站和後台放在同一份 repo 裡的 monorepo。

三種情況下，`/scope` 的第一步完全不同。空目錄要從「技術棧怎麼定」開始，從零把整個 MVP 拆出來；老專案不能重鋪基礎，只能把已經存在的功能登記進來，再規劃下一片；monorepo 則要先決定這件事屬於哪個工作區，還是全 repo 共用的。如果它不先分清楚你落在哪一種，用同一套劇本套上去，就會做出很荒謬的計畫，例如叫一個有三年的專案「重新決定技術棧」，或者把跨應用程式的功能塞進某一個 app 的計畫裡。

前一節提到 plan 的第一步是分類 repo。這一節就把那一步攤開。

先看它怎麼判斷

判斷靠掃描，掃描時會跳過 `node_modules/` 和 `.git/` 這種不該看的目錄。規則很簡單：看到任何原始碼檔（例如 `.ts`、`.tsx`、`.js`、`.py`、`.go`、`.rs`）就當作既有專案；一個都沒有，就是全新專案。如果看到多個工作區設定或好幾個 app／package 的清單，那就是 monorepo。

分類完，它只讀一個對應的路線檔案，不會把三個都讀進來。之後如果分類變了，才會換讀另一個。

Greenfield：從零，基礎先行

全新專案的劇本是從零把整個 MVP 拆出來，而且原則是基礎先行。意思是，任何功能切片都不應該在它站的地基還沒蓋好之前就開始動工。地基不是藏在某個任務底下的雜項，它們是檯面上的功能，按便宜的先做、依賴它的後做的順序排。

  1. 標準偏好。只有那些推不出來的輕量偏好，例如架構風格的傾向、排版口味。這一項可以併進技術棧那個功能，不一定要獨立一格。
  2. 技術棧與架構。這是一個功能，不是兩個。先有一個決定格（`Decide the stack (spec)`）交給 `/architect` 選定技術棧，再有一個執行格（`Scaffold from the decision`）交給 `/develop` 把可執行的骨架搭起來。這裡有個容易犯的錯：決定完整套技術棧是對的，但骨架上只裝第一片需要的那個最小集合，不是把未來會用到的套件全部先裝好。之後每個功能在真的被建置時，才裝自己的依賴。
  3. 編碼標準與工具鏈。先由 `/audit` 從真實搭好的專案裡擷取慣例與工具選擇，寫進根目錄的 `AGENTS.md`，再由 `/develop` 安裝這些工具。`/audit` 負責決定與記錄，不負責安裝，這也是為什麼它必須排在骨架之後。
  4. 資料模型。明確、不可省。核心實體、彼此的關係、持久化的形狀都要先定。一個錯的資料模型是最貴的錯誤，所以它本身就是一個需要規格的功能。
  5. 設計系統與 UI 基礎。如果產品有實質的介面，就先定視覺語言與基礎元件，因為之後每一頁都依賴它。
  6. 會動的骨架。一條薄的垂直切片，從資料庫一路接到介面，做一件小小的真事，證明整條線真的接得起來。在 Tracer Bullet 這種切法下，它會和第一片真實功能合併，不另外做一個丟掉式的骨架。

這六項完成後，才是功能切片。切片要怎麼切、怎麼排序，完全看前一節推薦的那一種 build approach，那是下一節的主題。

Brownfield：基礎已經在了，別重鋪

既有專案的劇本剛好相反：資料庫、技術棧、設計系統可能都已經存在了，所以不要重新規劃基礎。你要做的是先把已經建好的功能登記進來，當作背景資訊，再在上面規劃下一片。

登記靠讀根目錄的 `AGENTS.md`，加上一次輕量的程式碼掃描。如果 repo 很大，這次掃描會外包給一個唯讀的探索型 subagent，讓它回傳一張精簡的地圖，而不是把整棵目錄樹讀進對話裡。評估要誠實：已經完整上線的功能登記成 `existing`，只做了一半的登記成 `in-progress`，讓 `/develop` 之後能接手。不要把半成品蓋章成 `existing`，那等於假裝它完成了。

如果這個既有專案連根目錄的 `AGENTS.md` 都沒有，報告裡會提醒你應該先跑一次 `/audit` 取得真實的專案背景。另外，當 scope 已經存在、你又再跑一次時，它會把整份 scope 讀完當作去重的基準，絕不把已經在清單上的功能再加一次，只把漂移補上。

Monorepo：先問這是誰的事

多工作區的 repo 多一層問題：這件事屬於哪個工作區？劇本是每個工作區各自有一份 `docs/scope/<工作區>/`，而全 repo 共用的東西，例如 monorepo 工具鏈或一個共用的 UI 套件，放在 `docs/scope/_root/`。最上層再放一份 `index.md`，一個工作區一行，連到它的 scope 並附上狀態彙總。

平常的用法是 `/scope web <點子>`，明確指定要規劃那個工作區；如果你只打一個不帶參數的 `/scope`，它會用一張面板問你是哪個工作區，或者是不是全 repo 的範圍。每個工作區讀自己的巢狀 `AGENTS.md`，因為不同 app 的技術棧可能不一樣。

還有一個原則：跨工作區的功能，不要偷偷塞進某一個 app 的計畫裡。它應該放在 `_root`，或拆成幾個互相協調的、各屬於某個工作區的功能。哪一種工作區本身沒有程式碼，就走 greenfield 的基礎先行；哪一種已經有東西了，就走 brownfield 的登記。

為什麼三條路線都繞不開基礎

你可能注意到，三條路線裡只有 greenfield 真的要從頭鋪基礎。這是因為「基礎先行」是一個原則，不是一個步驟：greenfield 缺基礎，所以要把基礎當功能規劃出來；brownfield 的基礎已經在程式碼裡了，所以只要不重做即可；monorepo 則是每個工作區各自判斷。三種情況的共同點是：沒有任何功能切片可以在它腳下的地基還沒站穩時開始。

小結

plan 的第一步是掃描 repo 並分類，跳過 node_modules 與 .git：有原始碼就是 brownfield，沒有就是 greenfield，多個工作區設定就是 monorepo，然後只讀一個對應的路線檔案。Greenfield 從零基礎先行，依序規劃標準偏好、技術棧與架構（決定與搭骨架分開）、編碼標準與工具鏈、資料模型、設計系統、會動的骨架。Brownfield 的基礎已存在，不要重鋪，改為誠實登記 existing 與 in-progress 再規劃下一片。Monorepo 每個工作區各自一份 scope，全 repo 共用的放 _root，跨工作區的功能不塞進單一 app。

地基怎麼排你有譜了，但功能切片本身要怎麼切、怎麼排序，還沒有答案。下一節來看四種切法，它們會決定同樣一組功能被排成完全不同的形狀。
