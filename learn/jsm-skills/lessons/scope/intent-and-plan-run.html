一句 /scope，三種意圖：plan 怎麼跑完一輪

Step 2/5 · /scope：從點子到計畫

學習目標

能說明 `/scope` 如何從上下文推斷 plan、replan、add 三種意圖，並照著 plan 的步驟把一句點子拆成有序的 feature 清單。

前言：同一行指令，為什麼行為不同？

上一節你認得了 scope 檔案長什麼樣，但它不會自己冒出來。現在你坐下來，準備真的用一次。你打開 agent，打了一行 `/scope`，按下 enter。問題來了：它應該問你要做什麼、開始規劃一個新產品？還是應該先報告「你上次做到哪、下一步該接什麼」？

同樣是 `/scope`，兩個空白狀態下叫它，你要的東西完全不一樣。很多工具這時會要你打 `/scope plan`、`/scope replan`，用子指令把差別講清楚。但 jsm-skills 選擇不這樣做，它讓指令自己去讀上下文，推斷你現在要的是哪一種。這一節就來看這個推斷是怎麼運作的，以及推斷完成後，plan 這一輪實際上走了哪幾步。

還沒讀過上一節也沒關係，只要記得 scope 是那份放在 `docs/scope/`、用兩段式記錄功能與狀態的活計畫就好。

一行指令，三種意圖

`/scope` 的形式永遠是 `/scope [你要做的事]`，沒有子指令。它靠三條規則推斷你現在要的是哪一種行為。

你的處境推斷出的意圖它會做什麼
還沒有 scope，你給了一個產品規模的點子plan完整規劃一輪，從問問題到寫檔案
scope 已經存在，你什麼都沒給replan先報告現況，再對帳並排下一片
scope 已存在，你指名了單一功能add只收進這一個功能，不重跑整輪

其中最常被忽略的是 replan。它不是你偶爾才跑一次的補救，而是這套流程的日常節奏；一個功能或一個階段出貨之後，你就再跑一次不帶參數的 `/scope`，讓計畫回到跟現實一致。

如果狀態很模糊，例如你給了一句話，但看不出來那是「下一片功能」還是「單一功能」，它會依 scope 現況挑最可能的解讀，並在報告裡說明自己選了哪一種；真的說不清時，才用一行問題跟你確認。還有一種情況是：你連點子都沒給，也沒有既有的 scope 可以延伸。這時它不會硬猜，而是直接停下來問你：「你要做什麼？用一兩句話描述這個產品，或你想規劃的那一片。」

先分類：推論、發問、還是建議？

在動手問問題之前，`/scope` 會先把每一個資訊分成三類，這個紀律貫穿整輪規劃。

推論的，是點子本身就講明的事，例如產品的類別、顯而易見會有的能力，這些不用問。真的問的，是推不出來的商業、產品與上市考量，而且是一次一批地問，不是想到一句問一句。它建議的，是切法、建置順序、流程等級、還有哪些功能需要先做決定；這些它會給出判斷，但把最後決定權留給你。

有一件事它從不建議，就是工具。不挑供應商、不挑套件、不挑 ORM、不挑主機。工具選擇是每一個功能在規格階段才處理的事。如果一個功能本身暗示了某個工具決定，那正好就是它需要先做決定的訊號。

每個選擇都是一個決策面板

只要是需要你拍板的地方，`/scope` 都不會丟一個中性的問題給你，而是給一張決策面板：二到四個對這個產品真正具體的選項，其中恰好一個標著 (recommended)，附一句為什麼。它替你把判斷做出來，你不同意再改，而不是要你從零開始想。

它不會自己加一個「其他」選項，因為選單本身會自動附一個自由輸入的欄位；只有在沒有選單的純文字環境，它才會自己提供。問問題時一輪最多四個，一輪問完再進下一輪。

plan 的七個步驟

意圖確定是 plan 之後，整輪規劃照這個順序走。

  1. 定位與分類。先看這個 repo 是全新的、既有的，還是多個工作區組成的 monorepo，然後讀一個對應的路線檔案。這一步決定接下來用哪一套劇本。
  2. 問問題。不照固定的腳本、也不固定問幾輪。它會從這個產品生成出需要的維度，一批一批地問，直到重要維度都問到為止。至少涵蓋三組：產品與商業（MVP 邊界、受眾、收費、成功指標、硬性限制）、能力（登入、多租戶、付款、通知、上傳、搜尋、即時、後台、公開 API 等）、以及最常被忘掉的跨領域與上市考量（SEO、效能、分析、無障礙、國際化、法規）。
  3. 選切法。在你這個產品的目標與限制上，推薦四種 build approach 中的一種，選定之後就讀那個角色的檔案，後面所有的切片與排序都照它。
  4. 基礎先行。任何切法都不會在「立足點」還沒蓋好之前就開始做功能。基礎設施（技術棧、資料模型、設計系統、會動的骨架）會變成明確的功能，而不是藏在某個任務底下。
  5. 拆成粗略功能段。把答案變成功能清單：先基礎，再切片，最後是明確延後的好東西。每個功能保持小，一個功能就是一個頁面或一個內聚單位。
  6. 推薦流程等級。功能清單到手之後，依產品型態與功能輕重，提出專案的預設流程等級，同樣是一張恰有一個推薦的面板。
  7. 寫檔案並報告。寫入前再確認一次位置（隊友可能改過），照著格式寫，最後印出這輪完成了什麼、下一步是什麼。

這七步裡，第三步與第一步會各自展開成後面的兩節，這一節先把整條線路看清。另外，寫入前會有一個關於參考來源的小小同意問題：要不要在檔案裡加上「這個建議是從哪來的」。預設是不要，保持乾淨；如果加，也只是在小地方附上具名來源與做法，不會捏造連結。

Needs spec：一個決定，就該有一份規格

拆功能時，每個功能都要回答一個問題：它需要一份規格嗎？判斷的方法是所謂的「發明測試」：如果把它做出來，會需要一個你還沒做過的決定嗎？

會需要決定的情況包括：挑供應商或套件、決定資料模型、選一個跨領域的做法、定設計系統、一整頁畫面還沒有規格、或行為本身不平凡（搜尋、篩選、推薦）。只有當它是純實作、而且現有的 `design.md`、規格或慣例已經涵蓋時，才可以說不用。拿不準的時候，答案是要；等級在 `Beta` 或 `GA` 的功能，幾乎總是要。因為一個沒有被標記的決定，是最貴的那種失誤。

還有一條規則：一份規格，一個決定。如果一個功能裡藏著好幾個不同的決定，那就該拆成好幾個需要規格的功能，而不是把全部糊成一份「策略」規格。幾個功能共用一個大決定、之後再分岔的，可以讓一個總規格被它們引用，但絕不能因為有總規格，就把帶著自己決定的功能標成「不用」。

小結

`/scope` 沒有子指令，它靠三條規則推斷 plan、replan、add：沒有 scope 加產品點子就是 plan，有 scope 不給參數就是 replan，有 scope 又指名單一功能就是 add。整輪規劃的紀律是：能推論的就推論、推不出來的才一批批問、該判斷的給一張恰有一個推薦的面板。plan 走七步，從分類 repo、問問題、選切法、基礎先行、拆功能、推薦流程等級，到寫檔與報告。拆功能時用發明測試決定要不要規格，拿不準就說要，並且一份規格只裝一個決定。

七步裡的第一步，看起來只是一行「判斷 repo 形狀」，但它其實決定了你整輪要用哪一套劇本。下一節就把 greenfield、brownfield、monorepo 三種起手式拆開來看。
