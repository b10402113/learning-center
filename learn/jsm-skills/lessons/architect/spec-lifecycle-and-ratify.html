規格的生命週期：Proposed 到 Accepted，以及 Assumed 的補課

Step 5/5 · /architect：從請求到規格

學習目標

能用 spec lifecycle 管理規格：說出 Proposed → In Progress → Accepted 各由誰推進、Assumed 為什麼要由 /architect ratify，並走完寫完之後的自我檢查、跨模型 cross-check、accept 確認與 scope linking。

前言：檔案寫完，事情還沒完

上一節你跑完了訪談，規格也寫出來了。很多人（和很多 AI）到這裡就覺得任務完成、收工了。但如果只停在這裡，你會踩到兩種坑。

第一種是狀態錯亂：規格上那行 **Status**: 到底該寫什麼？剛寫好是 Proposed，可是功能都還沒蓋，為什麼有些人會看到 Accepted？如果分不清楚，你要嘛太早宣布決定已生效，要嘛把已經上線的東西永遠留在「提案中」。

第二種是漏掉收尾：一份規格寫完之後，還有一連串動作要跑。它要先自己檢查有沒有欄位空著、要不要讓另一個模型交叉檢查、等你確認、把狀態拍板，最後回到 scope 上把這個功能接起來，讓 /develop 知道從哪裡開工。漏掉這些，規格就會變成一座孤島。

這一節要把這條生命週期走完，包含那個最容易被誤解的 Assumed 狀態。

pre-flight：寫之前先看清全場

在訪談開始之前，它會先掃描環境，這些掃描結果直接影響後面的狀態判斷。它會查詢遠端有沒有新提交（落後就提醒你先拉），解析出 $SPEC_DIR 並在需要時建立目錄，確認今天是幾號，列出這個位置既有的規格來決定編號，數一數有多少原始檔（判斷要不要把讀碼外包給 scout），讀取專案的 AGENTS.md，以及讀出這個功能的建置策略。

其中兩件事和生命週期特別有關。第一是重疊規格偵測：如果找到明顯重疊的既有規格，它會先問你這是新決定、就地更新還是取代；如果那份重疊規格的狀態是 Assumed，那它就不走一般選項，而是進入「ratify」流程。第二是找出對應的 scope 功能：它掃描 docs/scope/，看有沒有哪一列在講同一件事。找到與否，決定了這份規格要採用哪一套狀態行為，這是下一步的關鍵。

兩套狀態行為：鏡射功能，還是獨立的決定

規格狀態的行為，取決於有沒有一個可建置的 scope 功能連到它。這條分界線是所有狀態規則的源頭。

有 scope 功能連著的規格（典型的 FEATURE、ENHANCEMENT，或真正有一個 scope 列的 ARCHITECTURE 基礎決定），狀態是鏡射功能生命週期的。/architect 建立它時寫 Proposed，擁有它的內容，但永遠不推進狀態；真正推進的人是 /develop：功能開始建置時推進到 In Progress，蓋好且驗證過（scope 標 done）時推進到 Accepted。你在確認面板上按下接受，代表的是「內容被確認了」，不是「已經上線」。

沒有 scope 功能連著的獨立決定規格（基礎技術棧或跨檔案標準），狀態是決定狀態：寫的時候是 Proposed，一旦你確認並批准，就變成 Accepted，因為這個決定當下就生效了，沒有後續的建置階段可以等。/develop 不會去推進它。

還有一種是一出生就 Accepted：描述「已經上線的工作」的規格，例如走文件化路徑、或連到的 scope 功能早就是 existing。它描述的是既成現實，不是提案。

狀態一覽：五種狀態與誰設定它

狀態意義由誰設定
Proposed規格寫好了、決定同意了，但功能還沒蓋/architect 建立時
In Progress這個規格管的功能正在建置/develop，功能轉為進行中時
Accepted功能蓋好且驗證過（scope done），塵埃落定/develop 完成時，或由 /sync 對帳
Superseded by [NNNN]被一份更新的規格取代/architect，走 supersede 時
Assumed建築在一個沒被正式討論過的假設上只有 /develop 能建立，只有 /architect 能清掉

另外要注意保護傘形狀：整個目錄裡，只有 index.md 有 **Status**: 這一行，子規格是規格內容，不帶生命週期狀態，由保護傘統一治理。

Assumed：先蓋再決的逃生口

Assumed 是一個很能反映「工程師決定」哲學的狀態。事情是這樣發生的：工程師選擇先動手、把某個承重決定留到之後再討論，於是 /develop 在建置時建立一份 Assumed 規格，記錄這次建置「用了什麼假設」，而不是「討論出來的決定」。

這份規格不會擋住功能完成。功能照樣可以被標成 done，Assumed 規格就掛在那裡，標明它欠一次正式批准。換句話說，這個流程唯一堅持的事情是「承重的決定要被寫下來」，連這件事都只是標記，不強制。而不一致的狀態清理，只有一個人有鑰匙：/architect 透過 ratify 來清掉它。

補課的流程是這樣：它先讀完整份 Assumed 規格，從 ## Owed decision、## Assumption built on 和 ## Code area 知道當初臨時決定了什麼、程式碼在哪。然後拿「實際上蓋出來的東西」當錨，跑一次正常的設計訪談，把決定好好討論一遍。結果有兩種：

  • 假設站得住。它把真正的決定內容補齊（Context、Options considered、Decision、Rationale、設計段、Consequences），清掉 Assumed，把狀態設成功能目前的生命週期位置（還沒驗證過就是 In Progress，已驗證就是 Accepted）。這個決定從此不再是臨時品。
  • 假設是錯的。它寫一份修正後的規格（create 或 supersede），把原本的 Assumed 標成 Superseded by [NNNN]，並且明確告訴你：這次的建置建築在一個錯誤的假設上，應該照修正後的規格重做。

不管哪一種結果，ratify 跑完就不該留下一份還是 Assumed 的規格。這是這個狀態存在的意義：/develop 記下假設，/architect 確認或修正它，並補上推理。

寫完之後：自我檢查與跨模型 cross-check

規格寫進檔案之後，它會先做一件最基本的事：確認檔案真的寫進去了。檔案不見或空的就是寫入失敗，會重寫，絕不捏造一份摘要。

接著是自我檢查：把剛寫好的規格再讀一次，逐項確認每個模式該有的段落都在。缺失或空著的欄位會在呈現時直接標一行 ⚠️ Incomplete，點名是哪個段落空著，請你補。這一步是它檢查自己，不假手他人。

然後是交叉檢查（cross-check）。這裡最重要的規則是：它永遠會問你要不要跑，絕不自己跑，也不自己跳過。因為這個決定是你的，它只負責讓你知道有這個選項。面板通常有四個選擇：另一個模型（由一個不同且能力足夠的模型做唯讀評論，它能看見作者自己看不見的盲點）、同一個模型（同一模型換一雙眼睛重讀）、我自己看、或跳過。

推薦哪一個，取決於這個功能的流程等級。若是 GA 或 Beta，它會強烈推薦「另一個模型」，因為這兩個等級是承重缺口真正會造成傷害的地方。若是 Alpha，基礎或高風險的規格才推薦，其餘只是提供選項。若是 Prototype 或根本沒有 scope 列，則推薦「跳過」（基礎規格可以選「同一個模型」）。

cross-check 的第一要務是決定的完整性：找出每個動作、端點或讀取路徑為了滿足驗收條件必須產生、計算或顯示，但規格沒有交代來源的值；以及建置的人將被迫自行決定、而規格沒有解決的選擇。換句話說，它在抓那種作者自我反省也抓不到的承重缺口。找到的每一個缺口都是一個承重決定，所以它絕不會默默修掉或自動補上：它會把每個缺口連同「我建議怎麼解」一起列出來，然後問你要怎麼處理（套用建議的修正、你逐項回答、或先留著之後再決定）。只有在你選了之後，它才動手改規格。

確認與拍板：accept 迴圈

cross-check 只會產生一段註記，不會結束流程，也不會替你決定。跑完（或跳過）之後，它把規格端到你面前，附上一個確認面板：接受，看起來很穩 / 要改，我告訴你改哪裡 / 整個方向重想。選「要改」它會問你改什麼，然後只針對你點名的段落做定點編輯，不會從頭重寫；選「重想」則回到相關階段重新討論。改完會再把同一個面板端出來，一直循環到你選「接受」為止。

按下接受，就是拍板。狀態怎麼設，回到前面那條分界線：有 scope 功能連著的規格，狀態行不動（確認只代表內容被確認，未建置的規格正確地停在 Proposed，等 /develop 推進）；獨立的決定規格，這一下把狀態設成 Accepted（批准本身就是交付物，若留在 Proposed 會永遠擱淺）；而走文件化路徑的，出生就是 Accepted，維持不動。

回到 scope：接線與推導任務

確認之後，它要回到 scope 把這個功能接起來。在動 scope 之前，有一個很容易寫錯的定位問題：每個功能身上恰好有一個「決定格」，也就是子任務標籤以 (spec) 結尾的那一格。它的字樣會依功能而不同（普通功能是 Design it (spec)，技術棧功能是 Decide the stack (spec)），所以要用 (spec) 這個後綴去定位，不能比對某一個固定字串。其他子任務都是執行格，這裡一律不會去勾它們。

接線的方式分兩種。若是決策型規格（ARCHITECTURE 技術棧或 CROSS-CUTTING 標準，依規則沒有 Build plan），沒有建置任務可以搬：它只是把功能列的 spec 格連上規格、把決定格打勾，然後放著執行格不管（例如技術棧功能上的 Scaffold from the decision），讓 /develop 在建置時才從這個決定推導步驟。這樣就避開了「同一件工作被規格兩次」的錯誤。

若是可建置的功能規格，它會把功能更新成「可以開工」的形狀，而且只做這幾件事：把決定格打勾、把標題上的 · needs a decision 拿掉；在指標行接上規格；加上一個 Build it 的勾選格，底下放二到五個從規格建置計畫「彙總」上來的里程碑（依 AC 群或依層分組，各自標註涵蓋哪些 AC）；再依這個功能的實際流程等級補上結尾的 Verify it（Alpha 以上）與 Test it（Beta 以上），GA 再加 Review it (fresh model) 與 Document it；把功能狀態移到 in-progress；最後把規格冒出來、其實是另一個功能的 follow-up 註冊成一條新功能。

這裡的關鍵字是彙總，不是原子任務的倒出。那些細碎的建置任務留在規格的 ## Build plan 裡，scope 只保留二到五個里程碑。如果一個功能塞不進大約五個里程碑，代表它太大了，該拆。

全部收好之後，它會在對話裡用白話給你一段摘要：決定了什麼、為什麼、接下來做什麼。通常的下一步是 /clear 開一個乾淨的 session（規格在磁碟上，讀得到，而剛剛那場冗長的設計對話從此不再花你的 context），然後跑 /develop 把它蓋出來。/architect 的任務，就在你確認規格的那一刻完成了；它不會自己去呼叫其他 skill。

小結

規格有生命週期。有 scope 功能連著的規格鏡射功能：/architect 寫 Proposed 且永不推進，/develop 推進到 In Progress、再到 Accepted；獨立決定規格在批准時直接變 Accepted；描述既成現實的一出生就是 Accepted。保護傘只有 index.md 帶狀態。Assumed 是 /develop 先蓋再決時建立的，不擋 done，只有 /architect ratify 能清掉：假設成立就補齊內容並清狀態，假設錯了就寫修正版並把舊的標成 Superseded。寫完之後跑自我檢查、依流程等級決定推薦的跨模型 cross-check（永遠先問、找到的缺口只列不改）、accept 迴圈拍板，最後回到 scope 用 (spec) 後綴定位決定格、接上規格、放上二到五個里程碑並依等級補驗證與測試格。
