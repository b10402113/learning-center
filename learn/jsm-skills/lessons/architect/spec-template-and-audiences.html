規格的骨架：兩個受眾、一條 AC 主線

Step 2/5 · /architect：從請求到規格

學習目標

能認出 spec 的段落順序，分辨 build spec 與 decision record 兩個受眾各讀哪些段落，並解釋 AC 主線、Options 必帶 con、decision-only spec 這幾條寫作規則。

前言：一份文件，兩種讀者

上一節你已經知道規格會落在 docs/specs/，也認得單檔和目錄兩種形狀。現在把檔案打開來看：裡面到底寫了什麼？

一份規格其實同時要給兩種完全不同的人讀。第一種是 /develop，它要照著這份文件把功能蓋出來，所以它需要的是「做什麼」：驗收條件、決定、要建的任務。第二種是半年後回頭查帳的人，可能是你自己，也可能是新加入的同事；他要問的是「為什麼當初這樣選」。如果把這兩種需求隨便混在一起，就會發生兩件壞事：建置時被迫載入一大段推理，浪費 context；或者推理被省略掉，未來的決定失去根據。

所以規格用一套固定的段落順序，把兩種讀者的內容分開標記。這一節就把這套骨架看懂，順便認識那條把所有東西串起來的主線。

段落順序：從摘要到參考

規格的段落是有固定順序的，這個順序本身就是設計。它從 ## Summary 開頭，接著 ## Context、## Requirements、## Options considered、## Decision、## Rationale，然後是依模式而定的設計段，最後是 ## Build plan、## Consequences、## Follow-up 與 ## References。

有幾個段落是依模式才出現的。FEATURE 模式放 ## Feature design，ARCHITECTURE 放 ## Proposed stack，CROSS-CUTTING 放 ## Standard definition，ENHANCEMENT 在遷移不單純時才加 ## Migration plan。這些設計段的內容下一節會逐個講，這裡先知道它們固定接在 ## Rationale 後面。

## Summary 要第一個寫，而且要用白話寫。它是給所有人的快速導讀，兩到四句話說清楚三件事：這個決定是什麼、為什麼這樣決定、對建置有什麼影響。技術背景或不技術的人，都該在二十秒內抓到重點。它不放在檔尾當結論，而是放在最前面，因為每個人打開規格都會先讀它。

兩個受眾：WHAT 與 WHY

把段落按讀者分一分，界線其實很乾淨。

受眾段落回答的問題
建置規格（/develop 讀）Requirements、Decision、設計段、Build plan、Consequences要做什麼（WHAT）
決定記錄（人讀，/develop 跳過）Context、Options considered、Rationale、References為什麼這樣選（WHY）

## Summary 站在建置規格這一邊，因為它是先幫人快速定錨的導讀。## Requirements 裡的驗收條件（acceptance criteria）就是合約：/develop 照著它蓋，/check verify 拿它來對帳。設計段是這個決定的內容本身，## Build plan 是從它推導出來的有序任務，## Consequences 則是建置時必須遵守的限制。

單檔規格裡，這兩個受眾共用同一個檔案，決定記錄的段落就寫在行內，但寫緊。目錄規格則把它們拆成兩個實體檔案：建置規格是 index.md，決定記錄搬到 rationale.md。注意，推理從頭到尾沒有被刪掉，只是被搬到建置時讀不到的位置。

AC 主線：把所有東西串成一條

驗收條件是整份規格的脊椎。它們寫在 ## Requirements 裡，每一條都有編號，像 AC-1、AC-2，而且每一條都要是「可觀察、可獨立檢查」的結果，不能寫成「支援登入功能」這種講了等於沒講的話。

主線之所以叫主線，是因為它要求雙向對齊，一個都不能落單：

  • 每一個 build task 都要標出它滿足哪幾條 AC。例如「建立資料表遷移，滿足 AC-1」。
  • 每一個測試情境都要對應到一條 AC。沒有例外。
  • 沒有 AC 可以沒有對應任務，也沒有任務可以沒有對應 AC。

這條規則擋掉的是一種常見的漂移：規格寫了五條驗收條件，但建置計畫只實作了三條，另外兩條悄悄消失。有了編號和雙向標註，漏掉的那兩條會明明白白地空在那裡。

驗收條件通常不是憑空長出來的。如果這個功能在 scope 上有一列，它的 intent 和種子驗收條件會被拿來當起點，再在訪談裡逐步長成正式的 AC。

寫作規則：讓每個字都值得留下

規格會被之後每一次建置載入，所以每個字都是反覆支付的成本。以下幾條規則就是為了把贅字擠掉。

每件事只說一次。同一個點不要在 Context、Rationale、Consequences 各講一遍。判斷標準很簡單：如果某段刪掉之後，讀者不會少懂任何東西，那段就該刪。

Context 只描述問題，不描述解法。它寫的是「現在面對什麼問題、有哪些力量在拉扯、不做決定會有什麼後果」，但不提前暗示選項，也不偷渡答案。

每個選項都要有真正的缺點。Options considered 裡每個選項都要用「它最好的辯護者會怎麼說」的角度公平描述，但至少附上一個真實的 con。一個找不出任何缺點的選項，通常代表它沒有被認真描述，也就是所謂的稻草人。

Rationale 要引用 Context 裡的力量，不能只是把 pros/cons 再抄一遍。它要解釋的是「為什麼是這個，而不是別的」，所以要扣回前面那些實際的拉扯。

Consequences 一定要有負面項。一份只有好處的規格不可信。任何決定都有代價，把它寫出來，未來的人才知道自己繼承了什麼。

一份規格只裝一個決定。如果它需要好幾個彼此獨立的決定，就拆成保護傘加子規格，而不是讓一個檔案無限膨脹。至於長度，跟著決定走，不要為了湊行數而灌水，也不要為了縮短而刪掉必要的設計欄位（資料模型、狀態機、API 表、安全模型、驗收條件都不該被砍）。

Decision 裡的 Implementation skills

## Decision 段落裡有一個欄位叫 Implementation skills。它列出這次設計用到的社群 skill，讓工程師在實作時知道該參考哪些慣例。

這個欄位是指標，不是貼上。它只記 skill 的名字、來源 repo 和它在專案裡的路徑，不會把 skill 的內容複製進規格。原因和前面一樣：規格是會被反覆載入的文件，把整份 skill 內容貼進來只會讓它變重，而且那些內容本來就有自己的出處。

決策型規格：只記錄決定，不寫建置計畫

有一種規格特別容易寫壞：ARCHITECTURE 的技術棧決定，和 CROSS-CUTTING 的標準定義。這兩種是所謂的「決策型規格」，它們不寫 ## Build plan，也不捏造像「規格有記錄到技術棧」這種空洞的驗收條件。

它們的規格本體就是那個決定本身：技術棧決定就是 ## Proposed stack，標準定義就是 ## Standard definition。真正執行這個決定的步驟（例如把專案 scaffold 起來），屬於執行它的那個功能，由 /develop 在建置時推導，不在這裡先寫。這樣做是為了避開「同一件工作被規格兩次」的錯誤。

References：可以選的裝飾，不能捏造

最後一個段落 ## References 是選配的。工程師在訪談時會選一個層級：none（乾淨，不寫參考引用）、sources（只列具名的專案來源與實務原則，不附網址）、或 sources+links（再加上查證過的網址）。

不管選哪一級，Rationale 永遠留著；被這個層級控制的只有 ## References 段落和行內的來源標註。選 none 時，整份規格的推理照寫，只是不掛引用，讀起來乾淨。無論如何都不能捏造網址：沒把握的來源就寫出它的名字，不附連結。

小結

規格有固定段落順序，Summary 第一個寫、用白話。段落分成兩個受眾：建置規格（Requirements、Decision、設計段、Build plan、Consequences）回答 WHAT，給 /develop 讀；決定記錄（Context、Options considered、Rationale、References）回答 WHY，給人讀、/develop 跳過。單檔把兩者寫在一起，目錄則拆成 index.md 與 rationale.md。AC 是脊椎，每條有編號、可獨立檢查，且 build task 與測試情境都要雙向對齊。寫作規則是每件事只說一次、Context 只寫問題、每個選項都要有真 con、Consequences 要有負面項、一份規格只裝一個決定。決策型規格不寫 Build plan，References 可選但不可捏造。

認得骨架之後，下一個問題是：這個骨架會因為設計的對象不同而長得不一樣。下一節要看四種模式，知道什麼情況該用哪一種，以及每種模式會多出哪個設計段。
