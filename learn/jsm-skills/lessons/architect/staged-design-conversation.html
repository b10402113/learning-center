設計訪談怎麼跑：從 scope 驗證到完整性關卡

Step 4/5 · /architect：從請求到規格

學習目標

能跑完 staged design conversation：先過 scope 驗證與 framing 推斷，再走 a 到 f 六個階段，並套用每題機制（一題一決定、恰好一個推薦、自訂選項最後、每批不超過四題），最後通過完整性關卡才動筆。

前言：一場好訪談，和一場壞訪談

上一節你已經知道模式會決定問什麼。但真正的重頭戲，是「怎麼問」。

壞訪談有兩種典型。第一種是審問：AI 丟來二十題通用清單，「你的使用者規模多大」「團隊幾個人」「要不要支援多語」，你答得很累，但很多問題跟眼前這個功能根本無關，答案也沒有被收攏成結論。第二種更隱蔽：AI 什麼都不問，默默替你選了 session 存法、選了錯誤回傳格式，等你看到程式碼才發現決定已經被做完了。

/architect 的訪談介於兩者之間，而且有一套明確的紀律。它的原則可以濃縮成一句：該推斷的推斷，該問的才問，該推薦的由它做球給你選；每一次只面對一個真正的決定，而且不把整個決定打包丟給你按同意。

這一節要把這套訪談的流程從頭走一遍。

前三道門：scope 驗證與 framing

在問任何設計問題之前，它先做兩件事，順序不能顛倒。

第一道是「已經蓋好了」偵測（Check B）。它會掃描你的描述裡有沒有透露「這是既成事實」的字眼，例如「我們現在用的是」「當初選擇了」「幫我把當初的決定記錄下來」。如果偵測到，它會先問你：這是既有的決定、你想把它「記錄成文件」，還是要從頭跑一次完整設計？選記錄的話，它會用自由作答的方式，問你當初考慮過哪些替代方案、為什麼選了現在這個、接受了哪些取捨，然後直接走「文件化路徑」：跳過整場訪談，把規格寫成既成事實，而且一出生就是 Accepted，因為它描述的是已經上線的現實，不是提案。

第二道是「產品願景還是具體決定」（Check A）。如果你說的是「一個管理團隊的 B2B SaaS」這種像在描述整個產品、沒有點名任何技術元件的話，它不會硬著頭皮開始訪談，而是會告訴你「這是一整個產品，但 /architect 一次只處理一個決定」，然後幫你挑出第一個基礎決定，再從那裡展開。

兩道門過了之後是 framing。這一步的關鍵字是「推斷，不要盤問」：模式、平台（web、mobile、API 或混合）、monorepo 的話屬於哪個 workspace、技術棧與慣例、限制與法規範圍，這些都從題目、AGENTS.md 和程式碼推出來，不問你。它只會把你的狀況用一兩句話回述：「我讀到這是一個新的 FEATURE，放在你現有的技術棧上，走 web，如果不對請糾正我。」這樣你很容易發現它讀錯，而所有問題都能花在真正屬於這個功能的細節上。

三種問題：推斷、詢問、推薦

訪談裡的每個維度都會被歸到三類之一，這決定了它會不會開口問你。

類別內容怎麼做
INFER題目、程式庫或 AGENTS.md 已經透露的直接推導，不問
ASK只有工程師本人知道的：需求、偏好、商業規則、法規範圍問，但要有推薦選項
RECOMMEND專業能拍板的：哪個供應商、函式庫、模式最合適它做決定，寫進規格，附一句理由與次佳選

這裡有一條硬規則：永遠不要把一整個資料模型、一整套技術棧或一整組驗收條件打包成一個「接受或修改」的面板。那等於把十個決定壓成一個按鈕，你沒有機會逐項表達。每個真正的選擇都要單獨問。同時，它也永遠不會默默替你決定一個工具、供應商或設定；連最小的選擇都要經過你。

每題的機制：一題一決定

每個問題都遵守同一套規則，沒有例外。

  • 給出真正可行的選項，不是湊數的兩個。只要是合理的選擇都要列；如果選項介面的數量上限裝不下，就分批問，而不是漏掉真的選項。
  • 恰好一個選項標上「推薦」，並附一句為什麼。它做球，你來選。
  • 最後一個選項永遠是自由輸入。在支援的工具裡這個「其他」選項會自動附上；沒有這種介面時，就明明白白地把它列成最後一項。
  • 一路鑽到最小的承重決定。從大的架構選擇到最小的工具設定，每個決定都各自成題，沒有哪個選擇小到可以不問。
  • 相關的問題一批最多四題。批次問是為了少幾輪往返，但每一題仍然是獨立的一題，不是把整包丟給你按同意。

這裡有個容易誤會的點：分批（把好幾個獨立的層各自成題）和打包（把一個完整的技術棧當一個選項）是兩回事。前者可以，後者不行。

六個階段，一次一個維度

訪談的骨幹是六個有順序的階段。它不會拿一份現成問卷來問，每個問題都是為這個題目當場生成的；一個 auth 功能、一個評論功能、一個選技術棧的決定，三者共享的問題數量是零。

階段 a：需求。它不會一開始就丟給你一張寫好的驗收條件清單，而是先一題一題問需求：核心任務是什麼、主要流程怎麼走、有哪些關鍵規則與限制、重要的失敗情況是什麼。然後從你的答案裡推導出驗收條件，邊問邊長成 AC-1、AC-2。這些條件就是合約，但你在最後看整份規格時才一次審閱，不是中途被逐條打斷。

階段 b：資料模型（必經，而且問、組、秀、確認、再迭代）。只要功能跟資料有關，這一步不能跳過，而且絕對不能猜。它分批問你：先問有哪些實體，再逐個實體問欄位（名稱、型別、必填或可為 null），再問關聯（誰跟誰、一對一、一對多、多對多），最後問規則與約束（唯一性、保留期限、不變條件）。它會提供範例選項讓你快答，但不會事先填好一張完整的實體關聯圖要你接受或否決。問完之後，它把模型組成一個表秀給你看（實體、主鍵、外鍵、基數），請你確認或修改，不滿意就改了再秀，直到你接受。為什麼要確認兩次？因為資料模型錯了會連鎖放錯，上面蓋的東西全部要重來。被你簽核的模型是「目標」，它的遷移會按功能大小放進建置計畫。

階段 c：技術棧與工具。它會自動依相依順序走過一層一層的選擇：應用型態、語言、框架、資料庫、auth、託管、背景工作、通知、檔案儲存、可觀測性、API 形狀等等。哪些層適用，是它依平台和題目判斷的，不是固定腳本；一個 web app、一個 mobile app、一個 API 服務、一條資料管線，需要的層完全不同。每一層它都給出當下真實、最新的選項（這個領域汰換最快，所以絕不用冷凍清單），標出推薦與一句理由，偏好重用專案已經在用的東西，然後讓你選。已經被 AGENTS.md 定下來的層就直接跳過。

這一階段夾著兩個重要的「先問再做」。第一個是 References 同意面板，只問一次：要不要在規格裡加一段參考來源？選項是「不要，保持乾淨」「只列具名來源，不查網」「列來源並附查證過的連結」。選到需要查網的層級時，會在一個唯讀的 researcher subagent 裡跑一次現況查證，上限是五次搜尋、八個頁面，官方文件優先，而且結果會快取三十天，不會反覆抓。第二個是 Agent Skill 與 MCP server 的探索，只有在這一輪選出了「新的」工具時才會觸發。它的鐵則是：問是必要的，搜尋不是。在你同意之前，什麼都不會搜、不會抓、不會安裝；同意之後，搜尋會在背景由一個低成本的唯讀 subagent 跑，不打斷訪談。找不到就直接說找不到，絕不硬湊一個候選來填版面。

階段 d：API 介面，並收斂「值來源」。先問這個功能需要哪些介面，再逐一問每個端點的方法、輸入、輸出、驗證要求與關鍵錯誤。然後是這階段真正的重點：關閉值來源的迴圈。對每一條驗收條件，把它需要某個動作去產生、計算或顯示的值列出來，逐一確認介面上有交代它的來源（是輸入參數、資料庫欄位、由某個具名值推導，還是另一個規格已決定）。某個必要的值找不到來源，那就是一個「還沒決定的輸入」，不是留給建置去填的細節：只有你才知道的就問你，專業能判斷的就推薦，並且當場把解法補進介面裡。舉個例子：一條驗收條件寫「使用者當地日期的昨天之前沒有讀取，連續天數就歸零」，這裡就必須交代「使用者當地日期」的時區從哪來。這個動作填的就是規格裡的「值來源」表，它擋掉的是建置時才發現少了輸入、於是被迫瞎掰的災難。

階段 e：安全與授權。逐一走過每條規則：誰能做什麼，包含擁有權、角色、跨租戶與跨組織的範圍；再確認這個功能有沒有觸發任何法規範圍（付款、個資、健康資料）。

階段 f：邊界情況與失敗模式。一次處理一種失敗：並發、重試、逾時、部分失敗，以及空、錯誤、載入中的各種狀態。

另外還有兩條特殊路徑。如果題目本身就是一個頁面或畫面（例如「首頁 UI」），會在階段 a 和 d 之間插進一個頁面設計階段，逐一問頁面要包含哪些區塊與順序、設計系統的來源、需要哪些元件、以及素材策略；其中「設計來源」是一定要問、絕不假設的，不能因為偵測到某個設計工具就連過去。如果題目本身就是選技術棧，那整場對話就是階段 c 的技術棧走查，驗收條件與資料模型改成在選完棧之後再推導，而不是開頭先卡一組。

完整性關卡：還沒問完不准動筆

在開始寫規格之前有一道不能跳過的門檻。它會核對每一個承重的維度都已經被處理：被問過了、被推斷了而且把推斷複述給你聽過、或明確標示為不適用。只要有任何一個還開著，就繼續問。

那哪些算承重維度？起點是一份檢查清單，但會依功能增減：功能範圍與界線、資料模型與持久化、生命週期與狀態機、API 或介面、認證與授權、驗證與商業規則、外部整合、函式庫與自建或外購、失敗與邊界情況、效能與規模、安全與法規、可觀測性、設定與密鑰、UI 介面（若有）、以及公開頁面才需要的可發現性與 SEO。

這道關卡背後的判斷很直白：每一段空著的維度，最後都會在建置中途變成一個問題，或一個猜錯的答案。所以它寧可多問一句。反過來說，一場很短的訪談是警訊，不是效率。一個真實的功能會橫跨很多維度、需要好幾批往返。

小結

訪談前先過 scope 驗證（Check B 偵測既成決定、Check A 分辨產品與單一決定）與 framing（推斷模式、平台、技術棧，不盤問）。維度分三類：INFER 直接推斷、ASK 問你、RECOMMEND 由它拍板附理由，且絕不把整個決定打包成一個話題。每題機制：給真選項、恰好一個推薦、自訂選項最後、鑽到最小承重決定、一批最多四題。六階段是需求推導 AC、資料模型必經確認、技術棧逐層走查並夾 References 與工具探索同意、API 與值來源收斂、安全授權、邊界與失敗。全部走完且通過完整性關卡，才開始寫規格。

訪談結束、規格也寫出來了，事情還沒完。下一節要看規格寫完之後：它的狀態怎麼流轉、Assumed 誰來補課，以及那個跨模型 cross-check 與 scope linking 怎麼收尾。
