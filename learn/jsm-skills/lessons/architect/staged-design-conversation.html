設計訪談怎麼跑：從 scope 驗證到完整性關卡

Step 4/5 · /architect：從請求到規格

學習目標

你將跑完一場 staged design conversation：先通過 scope 驗證與 framing 推斷，再依序走過 a 到 f 六個階段。過程中會套用幾條核心機制：一題一決定、恰好一個推薦、自訂選項放最後、每批不超過四題。全部確認完成，並通過完整性關卡後，才開始寫規格。

前言：一場好訪談，和一場壞訪談

上一節你已經知道模式會決定問什麼，但真正困難的地方是「怎麼問」。問題問錯了，AI 不是把你淹沒在問卷裡，就是在你沒有察覺時替你做完設計決定。

壞訪談通常有兩種。第一種像審問：AI 一口氣丟出二十題通用清單，例如「使用者規模多大」「團隊有幾個人」「要不要支援多語」，你答得很累，卻發現不少問題和眼前的功能無關，答案也沒有被收斂成具體結論。

第二種更隱蔽：AI 什麼都不問，默默替你選了 session 的儲存方式、錯誤回傳格式，等你看到程式碼時，才發現重要決定早已被做完。

/architect 的訪談介於兩者之間，並且遵守一套明確紀律：

該推斷的推斷，該問的才問，該推薦的由它提出；每次只處理一個真正的決定，不把整包決策塞成一個「接受或修改」的按鈕。

下面把這套訪談流程從頭走一遍。

前三道門：scope 驗證與 framing

開始問設計問題以前，/architect 會先做幾項檢查。順序不能顛倒，因為它必須先確認「現在到底要不要重新設計」，再判斷「這次要設計什麼」。

第一道門是「已經蓋好了」偵測（Check B）。

它會掃描你的描述，看看是否出現「這已經是既成事實」的字眼，例如「我們現在用的是」「當初選擇了」「幫我把當初的決定記錄下來」。如果偵測到，就會先確認：這是既有決定，你要把它「記錄成文件」，還是要從頭跑一次完整設計？

如果你選擇記錄，訪談會改走「文件化路徑」。它會用自由作答的方式詢問：當初考慮過哪些替代方案、為什麼選現在這個方案，以及接受了哪些取捨。接著跳過完整訪談，直接把規格寫成既成事實，而且一出生就是 Accepted。原因很簡單：這份文件描述的是已經上線的現實，不是一項等待批准的提案。

第二道門是「產品願景還是具體決定」（Check A）。

如果你說的是「一個管理團隊的 B2B SaaS」，這比較像整個產品的描述，還沒有點出任何具體技術元件。此時它不會硬著頭皮開始訪談，而會先告訴你：「這是一整個產品，但 /architect 一次只處理一個決定。」接著幫你挑出第一個基礎決定，再從那裡展開。

這兩道門通過後，才進入 framing。這一步的原則是「推斷，不要盤問」。模式、平台（web、mobile、API 或混合）、monorepo 所屬的 workspace、技術棧與慣例，以及限制與法規範圍，都應該從題目、AGENTS.md 和程式碼中推導出來，而不是把這些已知資訊再問你一次。

它只需要用一兩句話回述目前的理解，例如：「我讀到這是一個新的 FEATURE，會放在你現有的技術棧上，平台是 web；如果不對請糾正我。」這樣你能快速抓出它是否讀錯，後面的問題也能集中在真正屬於這個功能的細節。

三種問題：推斷、詢問、推薦

訪談中的每個維度，都會被歸到以下三類之一。分類會直接決定它該不該開口問你。

類別內容怎麼做
INFER題目、程式庫或 AGENTS.md 已經透露的資訊直接推導，不問
ASK只有工程師本人知道的需求、偏好、商業規則與法規範圍提出問題，但要附推薦選項
RECOMMEND專業判斷可以決定的供應商、函式庫或模式由它提出推薦，寫進規格，附一句理由與次佳選項

這裡有一條硬規則：不要把整個資料模型、整套技術棧或整組驗收條件包成一個「接受或修改」的面板。

那會把十個決定壓縮成一個按鈕，讓你失去逐項表達的機會。每個真正的選擇都必須單獨處理。同樣地，AI 也不能默默替你選工具、供應商或設定；就算只是很小的選擇，也要經過你。

每題的機制：一題一決定

每個問題都遵守同一套規則。

  • 提供真正可行的選項，不是為了湊數硬列兩個。所有合理選擇都應該出現。如果選項介面的數量上限放不下，就分批詢問，而不是刪掉真實存在的選項。
  • 恰好一個選項標上「推薦」，並附上一句理由。AI 負責做球，但最後由你選。
  • 最後一個選項永遠是自由輸入。支援這種介面的工具會自動附上「其他」；沒有這種介面時，也要清楚把自由輸入列為最後一項。
  • 一路鑽到最小的承重決定。從大型架構到細部工具設定，每個決定都各自成題，不能因為看起來很小就默默帶過。
  • 相關問題一批最多四題。批次詢問是為了減少往返，但每題仍然要是獨立決定，不能把整包內容變成一個同意按鈕。

要分清楚「分批」和「打包」。把幾個獨立層次各自列成問題，是分批，可以接受；把一整套技術棧包成一個選項，則是打包，不可以。

六個階段，一次一個維度

訪談的骨幹是六個依序進行的階段。它不會拿一份固定問卷照表操課，而是根據目前的題目即時生成問題。因此，auth 功能、評論功能，以及「選一套技術棧」的決定，三者共用的問題數量可能是零。

階段 a：需求。

它不會一開始就丟給你一張預先寫好的驗收條件清單，而是逐題詢問：核心任務是什麼、主要流程如何進行、有哪些關鍵規則與限制，以及重要的失敗情況。

接著，它會從你的答案推導驗收條件，讓 AC-1、AC-2 隨訪談逐步形成。這些條件最後會成為規格與建置之間的合約，但你是在看完整規格時一次審閱，而不是訪談中途被每條條件逐一打斷。

階段 b：資料模型。

只要功能和資料有關，這一步就不能跳過，而且絕對不能猜。訪談會分批處理：

  • 先確認有哪些實體。
  • 再逐一詢問每個實體的欄位，包括名稱、型別，以及必填或可為 null。
  • 接著確認關聯，例如誰和誰關聯，以及是一對一、一對多還是多對多。
  • 最後確認規則與約束，例如唯一性、保留期限與不變條件。

它可以提供範例選項，讓你更快回答，但不會先畫好一張完整的實體關聯圖，再叫你按下接受或否決。

問完後，它會把資料模型組成表格，清楚秀出實體、主鍵、外鍵與基數，請你確認或修改。如果你不滿意，就修改後再秀一次，直到你接受。

為什麼要確認這麼仔細？因為資料模型一旦錯了，錯誤會像骨牌一樣往上連鎖，後面蓋好的東西可能全部要重來。你簽核的模型是「目標」，而資料遷移會依功能大小安排進建置計畫。

階段 c：技術棧與工具。

這一階段會依照相依順序，一層一層走過選擇：應用型態、語言、框架、資料庫、auth、託管、背景工作、通知、檔案儲存、可觀測性、API 形狀等。

哪些層適用，由平台與題目決定，不是固定腳本。web app、mobile app、API 服務和資料管線需要的層完全不同。每一層都要提供當下真實、最新的選項；這個領域汰換很快，不能依賴一份冷凍清單。

它會標出推薦選項並附上一句理由，也會優先重用專案已經採用的工具。已經由 AGENTS.md 定下來的層，則直接跳過，不再重問。

這一階段還夾著兩個重要的「先問再做」。

第一個是 References 同意面板，整輪只問一次。選項包括：「不要，保持乾淨」「只列具名來源，不查網」，以及「列來源並附查證過的連結」。

如果你選擇需要查網的層級，會由唯讀的 researcher subagent 進行一次現況查證，上限是五次搜尋、八個頁面，並優先使用官方文件。結果會快取三十天，避免反覆抓取。

第二個是 Agent Skill 與 MCP server 的探索。只有在這一輪選出「新的」工具時才會觸發。它遵守一條鐵則：問是必要的，搜尋不是。

在你同意之前，什麼都不會搜尋、抓取或安裝。得到同意後，搜尋會交給背景中的低成本唯讀 subagent 執行，不打斷訪談。如果找不到，就直接說找不到，絕不硬湊候選項來填滿版面。

階段 d：API 介面，並收斂「值來源」。

先確認功能需要哪些介面，再逐一處理每個端點的方法、輸入、輸出、驗證要求與關鍵錯誤。

這一階段真正重要的是關閉值來源的迴圈。對每條驗收條件，列出它需要被產生、計算或顯示的值，並逐一確認介面是否交代了值的來源。來源可能是輸入參數、資料庫欄位、由某個具名值推導，或另一份規格已經決定的內容。

如果某個必要值找不到來源，那不是可以留給建置階段處理的小細節，而是一個「還沒決定的輸入」。只有你知道的事情，就問你；專業上可以判斷的事情，就提出推薦，並立即把解法補進介面。

例如，某條驗收條件寫著：「使用者當地日期的昨天之前沒有讀取，連續天數就歸零。」這裡就必須交代「使用者當地日期」的時區從哪裡取得。這個步驟填寫的就是規格裡的「值來源」表，目的是避免建置到一半才發現缺少輸入，最後只能臨時瞎掰。

階段 e：安全與授權。

逐一確認每條規則：誰能做什麼，包括擁有權、角色、跨租戶與跨組織的範圍；同時檢查功能是否觸及法規範圍，例如付款、個資或健康資料。

階段 f：邊界情況與失敗模式。

一次處理一種失敗：並發、重試、逾時、部分失敗，以及空白、錯誤、載入中的各種狀態。

另外還有兩條特殊路徑。

如果題目本身是一個頁面或畫面，例如「首頁 UI」，會在階段 a 和 d 之間插入頁面設計階段，逐一詢問頁面要包含哪些區塊與順序、設計系統的來源、需要哪些元件，以及素材策略。其中「設計來源」是一定要問、絕不假設的；不能因為偵測到某個設計工具，就自動連接過去。

如果題目本身是在選技術棧，整場對話就會聚焦在階段 c 的技術棧走查。驗收條件與資料模型會等技術棧選定後再推導，而不是一開始就先卡住一組。

完整性關卡：還沒問完，不准動筆

開始寫規格前，還有一道不能跳過的門檻。它會核對每個承重維度是否都已經被處理：可能是被問過、被推斷後複述給你確認，或明確標示為不適用。

只要還有任何維度沒有關閉，就必須繼續問。

承重維度的起點是一份檢查清單，但清單會依功能增減，通常包括：

  • 功能範圍與界線
  • 資料模型與持久化
  • 生命週期與狀態機
  • API 或其他介面
  • 認證與授權
  • 驗證與商業規則
  • 外部整合
  • 函式庫，以及自建或外購的選擇
  • 失敗與邊界情況
  • 效能與規模
  • 安全與法規
  • 可觀測性
  • 設定與密鑰
  • UI 介面（若有）
  • 公開頁面才需要的可發現性與 SEO

這道關卡背後的判斷很直接：每一段空白的維度，最後都會在建置中途變成一個問題，或一個猜錯的答案。

因此，訪談寧可多問一句。反過來說，一場短得不尋常的訪談通常是警訊，不是效率證明。真實功能往往會橫跨多個維度，也需要好幾批往返才能關閉所有決定。

小結

訪談先通過 scope 驗證：Check B 偵測既成決定，Check A 分辨產品願景與單一決定；接著進行 framing，推斷模式、平台與技術棧，而不是重新盤問已知資訊。維度分成三類：INFER 直接推斷、ASK 向你詢問、RECOMMEND 提出推薦並附理由；絕不把整個決定打包成一個話題。每題遵守幾項規則：提供真實選項、恰好一個推薦、自訂選項放最後、一路鑽到最小承重決定、每批最多四題。六個階段依序處理需求與 AC、資料模型確認、技術棧逐層走查並處理 References 與工具探索同意、API 與值來源、安全與授權，以及邊界與失敗。全部完成並通過完整性關卡後，才開始寫規格。

訪談結束、規格也寫出來了，但流程還沒有收尾。下一節會處理規格寫完之後的狀態流轉、Assumed 誰來補課，以及跨模型 cross-check 與 scope linking 如何完成。
