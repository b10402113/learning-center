把訪談結果寫成 spec，完成交叉檢查與 ratify

Step 5/5 · 把決策落成可交接的 spec

做完你會得到什麼

完成這一步後，你會得到一份位置正確、格式完整、狀態正確的 spec。它經過自我檢查與獨立交叉檢查，可以交給下一個 session、隊友或 /develop 繼續建置。

開始前，你需要先完成 /architect 的設計訪談，手上至少有確認過的驗收條件、資料模型、技術棧、API 介面、安全模型與邊界情境。這些答案目前還在對話裡，接下來要把它們變成真正的檔案。

/architect 的交付物只有 spec。它不寫程式碼，也不修改 AGENTS.md；後者是 /sync 的工作。

步驟 1：寫檔前才讀三個檔案

訪談完成、準備動筆時，才讀以下三個檔案：

  • agent-prompt.md：寫作人設與通用規則。
  • spec-template.md：spec 的段落結構。
  • agent-modes/<mode>.md：這次模式專用的規則。

不要在訪談一開始就載入它們。這些檔案可能很大，太早讀進 context，就像把厚重的工具箱一路背進整場會議；直到要寫 spec 時才拿出來，才能避免白白消耗每次呼叫的成本。

步驟 2：先決定 spec 放在哪裡

位置取決於 repo 的形狀，而且編號是「每個位置各自計算」。依序判斷：

  1. 如果是單一 repo，放在 docs/specs/。
  2. 如果是monorepo 的某個 workspace，放在 docs/specs/<workspace>/。
  3. 如果是影響整個 repo 的決策，放在 docs/specs/_root/。

接著確認 artifact base。docs/ 不一定適合放內部決策文件；如果它本身是對外發布的說明網站，請改用 .workflow/specs/。

通常可以從是否存在 Docusaurus、VitePress、MkDocs、Astro Starlight 或 Nextra 等設定檔，判斷 docs/ 是否為發布網站。若專案已經有既定的 artifact base，就跟隨現有結構，不要另起一套。

步驟 3：再決定 spec 的形狀

決策大小和 repo 形狀是兩件事。預設使用單一檔案，只有內容真的厚重或需要拆分時，才升級成目錄。

形狀適用情況內容
單檔 NNNN-title.md 一般、單純的決策 所有段落集中在同一個檔案，內容保持精簡
目錄 NNNN-title/ 傘狀決策、厚重或基礎決策，或需要 verify.md index.md 放建置規格，rationale.md 放決策紀錄；傘狀決策再放子 spec

目錄型 spec 有一個命名規則：目錄本身已經帶有編號，因此最上層檔案固定叫 index.md。不要建立 NNNN-title/NNNN-title.md 這種重複命名。

步驟 4：把訪談答案組成兩種材料

一份 spec 同時服務兩種讀者。先把內容分成「要怎麼蓋」和「為什麼這樣決定」兩組。

材料段落讀者
建置規格（WHAT） ## Summary、## Requirements、## Decision、模式專屬段落、## Build plan、## Consequences /develop
決策紀錄（WHY） ## Context、## Options considered、## Rationale、## References 人與未來的決策者

如果是單檔 spec，兩組內容放在同一個檔案裡。若是目錄型 spec，請實體分開：

  • index.md：建置規格。
  • rationale.md：決策紀錄。

這樣 /develop 建置時只需讀 index.md，不會把整段歷史推理一起載入，context 可以保持乾淨。

接著填入訪談中已確認的答案：

  1. 把驗收條件放進 ## Requirements，並保留它們的編號。
  2. 根據資料模型、API 介面與技術棧，整理出 ## Build plan。
  3. 為每個建置任務標註它滿足的 AC-N。

完成後要能雙向追蹤：每一條驗收條件至少對應一個任務；每一個任務也至少對應一條驗收條件。這能避免「規格寫了但沒人實作」或「做了規格沒要求的東西」。

步驟 5：寫完後先自己檢查

檔案寫好後，先把它讀回來，逐項檢查必要段落是否存在，欄位是否仍留著佔位符。

如果某個欄位確實沒有答案，請直接標示：

⚠️ Incomplete

同時指出是哪個段落不完整。不要自行捏造內容填空；空白規格可以繼續補，假造的規格卻會把後續建置帶向錯誤方向。

步驟 6：詢問是否進行交叉檢查

自我檢查後，做一次獨立且唯讀的審查。這一步永遠先詢問，不替工程師決定要不要跑，也不會擅自跳過。

它會提供四個選項，並按照功能的 workflow tier 給推薦：

  • GA 或 Beta：強烈建議使用「另一個模型」，因為這兩個層級的錯誤代價最高。
  • Alpha：若是基礎或高風險 spec，建議使用「另一個模型」；否則保持中立。
  • Prototype 或沒有 scope row：建議「跳過」；基礎 spec 也可以選「同一個模型」。

交叉檢查的重點是決策完整度。它會找出所有為了滿足驗收條件，必須產生、計算或顯示，卻沒有在 spec 中指明來源的值。

這是對「收斂值來源」的獨立複驗：換一個模型再看一次，找出原作者容易忽略的缺口。

若發現缺口，審查結果要同時列出建議修法，交給你決定。決策層級的缺口不能由 agent 默默改掉，因為那是工程師必須承擔的選擇。只有純粹的措辭或健全性小問題，才可以直接修正並留下註記。

步驟 7：確認 spec，再決定 ratify 狀態

交叉檢查只會產生註記，不會替你做決定。檢查完成或選擇跳過後，呈現完整 spec，讓你選擇：

  • 接受（推薦）
  • 改某個地方
  • 重新想整個方向

如果你選擇修改，系統只編輯你指出的段落，接著再次詢問同樣的確認。重複這個循環，直到你選擇「接受」。

按下接受後，依 spec 種類設定狀態：

  1. feature-linked spec：不修改狀態行。這份 spec 已確認但尚未建置，因此維持 Proposed，之後由 /develop 往前推進。
  2. standalone decision spec：將狀態設為 Accepted。這類 spec 沒有等待建置的階段，ratify 本身就是交付物。
  3. 既成事實的文件化路徑：出生時就是 Accepted，維持不變，之後由 /sync 對帳。

步驟 8：把 spec 連回 scope

確認完成後，找到對應功能，在它的決策框中找到標籤結尾為 (spec) 的子任務並打勾。

接著用相對路徑連結 spec，並把 spec 裡的 ## Build plan 原子任務整理成兩到五個里程碑寫進 scope。最後依功能 tier 補上驗證、測試等收尾框。

如果找不到對應功能，請選擇：

  • 把這個功能加入 scope；或
  • 只保留在 spec 裡。

步驟 9：遇到 Assumed spec 時，改走 ratify

如果題目對應到既有的 Assumed spec，這不是從零開始的流程。它代表 /develop 先建置、後補決策，留下了一張尚未兌現的欠條。

先完整讀完這三段：

  • ## Owed decision：欠的是哪個決定。
  • ## Assumption built on：當初建置依據的假設。
  • ## Code area：相關程式碼在哪裡。

接著拿已經建好的內容正式討論，最後只有兩條路：

  • 假設成立：補齊 Context、Options、Decision、Rationale、模式專屬段落與 Consequences，清掉 Assumed，再依功能目前的生命週期設定狀態。已建但尚未完成的是 In Progress；已完成驗證與測試的是 Accepted。
  • 假設不成立：建立修正後的 spec，將原 spec 標記為 Superseded by NNNN，並明確告知工程師目前的建置建立在錯誤假設上，應依修正後的 spec 重做。

ratify 完成後，專案裡不應再有任何 spec 停在 Assumed。

完成檢查

依序完成：讀三個寫作檔 → 依 repo 形狀決定 location → 依決策大小決定 shape → 組裝建置規格與決策紀錄 → 自我檢查並標出空白 → 永遠先詢問是否交叉檢查 → 確認直到接受 → 依 spec 種類設定狀態 → 連結 scope。

如果遇到 Assumed，改走 ratify：假設成立就補齊內容並清除狀態；假設不成立就建立新 spec、標記 superseded，並請工程師重做。

做到這裡，你已經能在自己的 repo 上獨立完成 /architect：從訪談答案整理出 spec，放到正確位置，選擇正確形狀，完成檢查與確認，並留下下一步可直接執行的建置規格。接下來由 /develop 依照它把功能蓋出來。
