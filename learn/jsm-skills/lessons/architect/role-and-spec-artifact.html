/architect 管什麼：一份規格的誕生

Step 1/5 · /architect：從請求到規格

學習目標

能說出 /architect 的角色與它擁有的產物，並指認一份 spec 的落點（$SPEC_DIR）、形狀（單檔或目錄）與 create / update / supersede 三個操作各自何時使用。

前言：當「決定」沒有被留下來

你對 AI 說「幫我設計登入功能」。它可能點點頭就開始寫程式：選了 cookie 存 session、挑了一套密碼雜湊演算法、順手決定了 token 的有效期限。你當下看過去覺得沒問題，可是三週後資安要求你說明「為什麼不用某一種做法」時，你才發現那個「為什麼」從沒被寫下來，只留在當時的對話裡。

另一種常見的失敗是反向的：AI 丟給你一張二十題的清單，一題一題問完，你回答得很累，最後卻沒有得到一個明確的結論。它把問題都問了，但沒有替你把答案收攏成一個可以照著蓋的東西。

/architect 要解決的就是這件事。它把「決定」本身當成要交付的產物：陪你做完一輪有結構的訪談，比較過選項，給出清楚的推薦，然後把結論寫成一份規格。這份規格是它存在的理由，也是下一個階段 /develop 照著動工的依據。

這一節先不談訪談怎麼進行，先把最底層的問題弄清楚：它到底產出什麼、放到哪裡、用什麼形狀放。

/architect 是什麼、不是什麼

/architect 是一個「設計決定」的 skill。它把一句模糊的請求（「設計 auth」、「挑一套技術棧」、「統一錯誤處理」）變成一紙經過確認的建置規格，預設放在 docs/specs/。它的工作流程是：跑結構化探索、比較選項、給出明確推薦，然後自己把規格寫下來。

它有四種模式，下一節會逐一拆開；這一節先記住它的本質是「一次面對一個承重的技術決定」。

它刻意不碰某些東西。它不寫程式，也不更新 AGENTS.md 或 CLAUDE.md，那些是 /sync 的責任。它的產物就是規格本身，加上規格需要的佐證。

還有一個分工值得先記住：規格由主執行緒親手寫，subagent 只負責讀。它會派出的幫手只有三種，全都是唯讀的：一個讀既有程式碼的 scout、一個上網查現況的 researcher，以及最後讀草稿做交叉檢查的那一位。而且它們一律用「最便宜又足以勝任」的模型，不會繼承你正在用的 session 模型。這樣分工有兩個好處：規格這種承重產物不會交到不可靠的手上，而掃碼、查網這類會灌進大量檔案的雜活，也不會把主對話的 context 撐爆。

四個操作：create、update、supersede

面對一個設計主題，/architect 先判斷這是哪一種操作，因為四種操作的流程不一樣。

操作什麼時候用做什麼
create一個全新的決定寫一份新規格，狀態從 Proposed 開始
update同一個決定要演化就地編輯既有規格，跳過設計訪談
supersede要取代一個過去的決定寫新規格，並把舊規格標成 Superseded by [NNNN]
ratify要補課一份 Assumed 規格把 /develop 先蓋後決的假設，補成正式決定

ratify 比較特別，它對應的是 /develop 的「先蓋再說」逃生口，完整的故事留到第 5 步。這裡先知道有這個操作就好。

在正式開始前，pre-flight 會掃描既有規格，找出明顯重疊的那些。如果找到，它不會擅自決定，而是先問你：這要當成一個新決定、就地更新既有規格，還是直接取代它？預設選項會依重疊程度給建議，幾乎一模一樣的偏向更新或取代，只是鄰近的則偏向開新規格。

規格歸誰、放哪裡

所有 spec 檔只有 /architect 能建立或更新。它順手產生的佐證（例如現況清單、審查紀錄）也有固定去處：目錄形狀的規格放進 rationale.md，單檔規格就寫在裡面，不會散落到 docs/scope/，因為那是 /scope 的地盤。

規格放在哪，由 repo 的形狀決定：

Repo 形狀規格落點
單一 repodocs/specs/
Monorepo，某個 workspace 的決定docs/specs/<workspace>/
Monorepo，repo 層級的決定docs/specs/_root/

編號是「每個位置各自算」的。它掃描該目錄裡最大的 NNNN，加一，補齊四位數。把解析出來的位置叫做 $SPEC_DIR，後面都用這個名字。

還有一個底線：規格預設住在 docs/ 底下，但如果 docs/ 本身是一個發佈出去的說明網站（偵測到 Docusaurus、VitePress、MkDocs、Starlight 或 Nextra），就會改住 .workflow/，免得工作檔案混進要公開的內容裡。

形狀：單檔還是目錄

和落點無關，規格還有第二個獨立選擇：形狀。判斷依據是「這個決定有多大」。

簡單的決定就是一顆單一檔案 $SPEC_DIR/NNNN-title.md，所有內容行內寫緊。當決定是保護傘（底下會拆出兩個以上相關子決定）、沉重或基礎的決定，或者你希望附一份 verify.md，就改用目錄形狀：$SPEC_DIR/NNNN-title/，裡面放一個 index.md 當主檔、一個 rationale.md 在旁邊，傘狀的話再加上幾個子規格 NNNN-child.md。

兩個常見的錯誤要避開。第一，不要寫成 NNNN-title/NNNN-title.md，數字由目錄本身帶著，主檔的名字固定是 index.md。第二，不要預設就用目錄，能用單檔就用單檔，只有真的需要才升級。

檔名規則是 kebab-case、全小寫、最多五個字、開頭不加冠詞。例如 0001-adopt-relational-db-for-primary-storage.md，講的是「採用關聯式資料庫當主要儲存」，而不是一串又長又含糊的描述。

為什麼目錄形狀要拆成兩個檔案

目錄形狀裡，index.md 是 /develop 要讀的建置規格，rationale.md 是給人看的決定記錄。這條分割是下一節的主角：一份規格同時服務兩個受眾，而它用檔案形狀把兩者分開，讓建置的時候只需要載入前者，不必背著整段推理。

這和整個 skill 的設計手法是同一套。頂層的 SKILL.md 只當協調者，把冗長的操作細節丟進 internal/ 底下的檔案，寫作指南這類只在寫入那一刻才需要的東西，也等到真的要寫規格時才讀。這樣在訪談過程中，context 裡不會一直躺著一份根本用不到的寫作手冊。這個手法叫做 progressive disclosure，你在 Tier 1 已經看過，這裡是它在一個真實 skill 裡的樣子。

小結

/architect 是設計決定的 skill，產物是一紙放進 docs/specs/ 的規格。規格由主執行緒親手寫，subagent 只讀、只用最便宜的模型。四個操作是 create 開新規格、update 就地演化、supersede 取代舊決定、ratify 補課 Assumed。落點由 repo 形狀決定（單一 repo、monorepo workspace、_root），編號每個位置各自算，這個解析出來的位置叫 $SPEC_DIR；形狀由決定大小決定，預設單檔，遇到保護傘或基礎決定才升成目錄，並拆成 index.md 與 rationale.md。

你現在知道規格會落在哪、長什麼形狀。但它裡面到底寫了什麼？下一節要把規格拆開，看它的段落順序、兩個受眾各讀哪些段落，以及那條把所有東西串起來的 AC 主線。
