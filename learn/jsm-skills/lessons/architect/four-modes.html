/architect 的四種模式與四種操作

Step 1/5 · 把決策寫成 spec

學習目標

看見一個設計情境時，能判斷該用 FEATURE、ARCHITECTURE、ENHANCEMENT 還是 CROSS-CUTTING，並分辨這次要 create、update、supersede 還是 ratify。

先問對問題：這到底是新建、改造，還是統一規則？

你打開 agent，輸入：「幫我設計一個會員系統。」接著它開始追問：資料表有哪些欄位？登入要用哪種方式？要不要寄驗證信？

這些問題本身沒有錯，但可能太早了。你還沒先決定：這是要從零蓋一個新功能，還是要替換一套已經存在、但不太可靠的系統？

從零設計時，核心問題是「這個功能要解決什麼使用者問題」；改造既有系統時，則要先弄清楚「目前怎麼運作、哪些地方不能動、如何安全搬遷」。一開始若走錯方向，後面問得再仔細，也只是把力氣花在錯的地方。

/architect 的工作，就是把尚未定案的技術決策問清楚、比較選項，最後寫成 spec。它不負責寫程式碼；在開始設計前，會先判斷眼前這題屬於哪一種模式，以及這份決策應該如何落進既有的 spec 檔案。

四種模式：這次要用哪種設計姿態？

/architect 用四種模式區分設計情境。模式不分難度等級，差別在設計行為：要不要讀既有程式碼、是否需要評估整個技術棧，以及 spec 要額外補上哪一段內容。

你只要描述題目，/architect 會自行推斷模式，不需要手動指定。

模式什麼時候用設計行為
FEATURE從零設計一個沒有既有實作的新功能從第一原理思考、套用最佳實務，只讀取這個功能必須整合的程式碼
ARCHITECTURE替新專案選技術棧或建立基礎架構全面評估技術棧、參考業界模式，沒有既有程式碼需要閱讀
ENHANCEMENT改善、替換或擴充已經存在的東西閱讀既有程式碼與 spec，聚焦比較不同方案
CROSS-CUTTING把一種做法統一到整個 codebase，例如錯誤處理、日誌、認證或命名抽樣檢查現況、精確定義標準，並建議如何強制執行

可以把這四種模式想成四種工程姿勢：

  • FEATURE 像設計一間新房間，先思考它要滿足哪些生活需求。
  • ARCHITECTURE 像決定整棟房子要用鋼骨還是磚造，這個選擇會影響後面很久。
  • ENHANCEMENT 像改造一間已經住人的舊房間，必須先確認哪些牆是承重牆。
  • CROSS-CUTTING 像替整個社區訂定統一的門牌規則，管的是所有房子都遵守同一套標準，不是單棟房子。

模式也會決定 spec 的專屬段落

模式不只影響提問方式，也會改變最後那份 spec 的形狀。每種模式都有自己的專屬段落；寫 spec 時只會加入對應內容，不會把其他模式的段落混進來。

模式spec 的專屬段落這段在講什麼
FEATURE## Feature design資料模型、API 介面、值的來源、安全性與測試情境
ARCHITECTURE## Proposed stack逐層說明語言、框架、資料庫、認證與部署的選擇及理由
ENHANCEMENT## Migration plan搬遷策略、執行階段、回復方式與風險；改動大一點才需要
CROSS-CUTTING## Standard definition唯一的正解寫法、要取代的舊寫法、強制方式與推行方式

這也是模式選錯會造成高成本的原因。假設你要統一整個 repo 的錯誤處理，卻把它當成單一功能來設計，spec 可能只會描述某一個地方怎麼實作，卻沒有說明哪些寫法算違規，也沒有定義如何阻止舊寫法繼續出現。最後，每個人仍然會用自己的方式處理錯誤。

四種操作：這份決策要怎麼放進既有 spec？

模式回答的是「這次要用什麼方式設計」；操作回答的則是「這個決策要如何處理既有的 spec 檔案」。這是兩條不同的判斷軸。

在動手前，/architect 會先掃描 docs/specs/，尋找是否已有內容相近的 spec，再從四種操作中選擇適合的方式。

操作什麼時候用動作
create這是一個全新的決策建立一份新 spec，狀態設為 Proposed
update同一個決策需要演進或微調直接修改既有 spec，不用重跑整套訪談
supersede要推翻過去的決策建立新 spec，並把舊 spec 的狀態改為 Superseded by NNNN
ratify發現一份 Assumed spec，需要補上正式討論跑一輪設計訪談、補齊內容，並移除 Assumed 狀態

如果發現舊 spec 和這次題目重疊，/architect 不會直接替你決定。它會把「建立新 spec」、「原地更新」或「取代舊 spec」三個選項連同推薦一起提出，最後由你做決定。

但如果舊 spec 的狀態是 Assumed，情境就不同了。這不是單純要不要覆蓋舊內容，而是當初先做了假設、現在要補上正式設計討論，因此應該走 ratify。

把兩條判斷軸接起來

/architect 在設計決策前，會先擺好兩種姿態。第一條軸是模式：FEATURE 設計新功能、ARCHITECTURE 選技術棧、ENHANCEMENT 改造既有系統、CROSS-CUTTING 統一整個 repo 的標準。模式決定它要不要讀程式碼，以及 spec 要寫哪一段專屬內容。第二條軸是操作：create、update、supersede、ratify，決定這份決策如何落進既有的 spec 檔案。模式選對，操作也選對，後面的問題才會問在正確的位置。

因此，模式和操作不是同一件事：前者描述「要怎麼設計」，後者描述「要怎麼處理這份決策的檔案」。下一個要接上的觀念，是 spec 寫完之後會經過哪些狀態，以及誰負責推進這些狀態。/architect 可以寫出狀態為 Proposed 的內容，但不會自己完成整條生命週期。
