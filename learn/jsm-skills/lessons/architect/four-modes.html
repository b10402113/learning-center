四種模式：feature、architecture、enhancement、cross-cutting

Step 3/5 · /architect：從請求到規格

學習目標

能依情境選對 FEATURE / ARCHITECTURE / ENHANCEMENT / CROSS-CUTTING，並說出每個模式多產出的設計段與它套用的專家預設。

前言：同一句請求，問法不該一樣

上一節你認得規格的骨架了。但骨架不是每個模式都長得一樣：不同的設計對象，除了共用的段落之外，還會多出一個屬於自己的設計段，訪談時要問的問題也完全不同。

想像兩個人同時下達指令。一個人說「設計團隊邀請功能」，另一個人說「幫我挑這個新專案的技術棧」。表面上看起來都是「設計」，但前者要問的是資料模型、邀請流程、權限；後者要問的是規模、團隊大小、每一層要選哪個產品。如果 /architect 把這兩件事用同一套問法處理，第一種會被問一堆無關的部署問題，第二種會被要求先確認驗收條件，兩邊都問錯重點。

所以它先判斷模式，再依模式決定訪談與設計段的內容。這一節要看的就是這四種模式，以及背後那位負責寫規格的「人」抱持什麼立場。

誰在寫這份規格

寫規格的那個角色被設定成一位有十五年經驗的 Staff Engineer 兼 Principal Architect：管過服務數百萬使用者的系統，半夜三點被自己的決定叫醒過，也看過同一批失敗模式在不同公司重複上演。它的立場不是提供一份中立菜單，而是把你帶向對的答案，坦白說出取捨，遇到明顯會撞上已知失敗模式的方向就直接講。

它的幾條思考原則值得記住，因為它們會反覆出現在每個模式的建議裡：

  • 簡單勝過聰明。最好的架構，是團隊在週二下午五點、資深工程師請假時還能搭得出來、看得懂、跑得動的那一個。
  • 無聊的技術是優點。有社群、有文件、失敗模式已經被摸透的成熟工具，勝過又新又炫的選擇。
  • 為失敗而設計，不是為順利的流程而設計。每個決定都要回答：這東西壞掉時會怎樣，我們怎麼回復？
  • 用三個時間尺度想事情。第一天能不能出貨、第一百八十天能不能維護、第七百三十天團隊擴大時要不要重寫。
  • 維運現實不是選配。一個需要多三套基礎設施元件才能運作的「優雅」方案，並不優雅。

它也列了幾件自己不做的事：不給沒有清楚推薦的選項、不因為某技術流行就推薦它、不為使用者從未提過的想像規模做設計、不忽略團隊實際能達成的能力、不說「這要看情況」卻不馬上說要看什麼。

動筆之前先挑戰前提

在進入模式之前，它會先質疑題目本身：這是對的問題嗎？有沒有更簡單的框架能達到同樣目的？這個方向是不是撞上了某個已知的失敗模式？

如果發現問題，它會在 ## Context 開頭放一段 ⚠️ Premise note：說明擔憂是什麼、會導致什麼失敗、正確的框架應該是什麼樣子，然後照原方向繼續做。你可以否決它的挑戰，但它必須先把話說出來。它同時會檢查三件事：題目是不是大到橫跨三份以上規格（若是，會先聚焦在最關鍵的那一個，其餘列出來建議另開規格）、這個功能有沒有碰觸受規範的資料（有的話要點名適用的法規，安全模型欄位變成必填，稽核紀錄不可協商）、以及它依賴的前置決定是否還沒有規格（例如「假設已經有 auth 與 session 模型，但這假設沒有規格」）。

模式什麼時候用設計行為

接下來逐個看每個模式多做了什麼。

FEATURE：設計一個新功能

FEATURE 模式面對的是從零開始的功能，所以它走第一原理：不讀整份程式庫，只讀這個功能必須整合的既有部分。它依序想清楚七個維度，一個都不跳過：使用者真正要解的問題（他們想達成什麼結果，而不是他們嘴巴上要的功能）、資料模型（實體、生命週期狀態、必須永遠成立的不變條件）、一致性需求（強一致或最終一致、誰寫誰讀、多常讀）、最小 API 介面（每個端點的方法、路徑、關鍵輸入輸出、驗證要求、最重要的錯誤）、失敗模式（資料庫慢、第三方呼叫失敗、兩個人同時動作）、安全表面（哪些資料敏感、誰能讀寫、授權模型）、以及設定需求（新的環境變數、密鑰、第三方憑證）。

它還會套用一批專家預設，這些都是踩過坑之後留下的意見：

  • 冪等性從第一天做起。每個會改動狀態的操作都要能安全重試；牽涉到金錢、通訊或外部副作用時，用冪等鍵。
  • 分頁不是選配。任何列表端點都要分頁，就算 MVP 也一樣；沒分頁的列表最後都會變成上線事故。
  • 軟刪除通常是錯的。它會污染查詢、破壞唯一約束、留下幽靈資料；改用明確的 archived_at 時間戳或封存表。
  • 不要預先計算並儲存衍生值，除非你已經量到效能問題。讀取時再算，存起來的值會過期。
  • 稽核紀錄是必要的，只要操作碰到金錢、存取控制、醫療資料或法規範圍就要有，事後補非常痛。
  • 公開端點一定要限流。沒有 MVP 例外，替未登入的端點加上限流只要一小時，卻能擋掉一整類濫用。
  • 永遠不要把密鑰存進資料庫或程式碼，改用環境變數或密鑰管理服務。

這些東西最後收進 ## Feature design 段落：資料模型草圖、狀態轉移、API 介面、值來源、關鍵不變條件、安全模型、設定、以及關鍵測試情境。其中「值來源」表是一個容易忽略卻很關鍵的設計：每個動作要產生、計算或顯示的值，都要寫出它從哪裡來。如果某個驗收條件需要的值沒有任何來源，那就是一個還沒決定的輸入，必須當場解決，不能留給建置的人去發明。

ARCHITECTURE：選一套技術棧

ARCHITECTURE 模式面對的是基礎的技術棧決定。它有個重要的順序：先選架構模式，再選技術。架構模式由規模和團隊大小決定：使用者不到一千、團隊五人以下，先做單體；一千到十萬、團隊五到十五人，用分層單體（controller → service → repository）；十萬以上、團隊十五人以上且界線清楚，才在領域邊界上拆出兩三條服務；資料密集的場合，先決定批次還是串流，批次（cron 加倉儲）通常就夠。

決定模式之後才逐層挑技術。這裡的手法很值得學：在耐久的分類上推理，再挑當前的產品。表格列的是類別與機制（耐久的建議），因為這個領域汰換很快，實際產品要當下重新挑、對齊專案已經在用的東西。這些耐久分類包括：主要資料庫用關聯式資料庫、快取用記憶體內快取（當它是暫時的，絕不當主要儲存）、auth 用成熟的函式庫或服務（絕不從零手刻）、背景工作先用資料庫驅動的佇列、檔案用物件儲存（絕不把檔案存進資料庫）、搜尋先用資料庫內建的全文本搜尋、可觀測性用結構化日誌加錯誤追蹤且第一天就要有。

它套用的專家意見延續同一套保守邏輯：單體優先，因為微服務貴三倍且難以合併回去；關聯式資料庫是預設，95% 的產品碰不到它處理不了的負載；serverless 跑 API 有真實取捨（冷啟動、無狀態、執行時限、連線限制），要明講；多區域部署延後到真的需要；ORM 處理 CRUD、複雜查詢寫 SQL；完整的容器編排是給有平台工程團隊的公司用的，小團隊用託管平台就好。

ARCHITECTURE 是決策型規格，所以它不寫 Build plan，產出的是 ## Proposed stack：一張逐層的技術棧表，每一層都要有一句理由。

ENHANCEMENT：改動一個已經存在的東西

ENHANCEMENT 模式面對的是上線中的系統。它的第一步是讀既有程式碼與相關規格，第二步是誠實診斷：目前的做法「實際上」怎麼運作（不是當初打算怎麼運作）、問題或落差的根因是什麼、既有系統加上了哪些限制（資料格式、API 合約、團隊知識、遷移風險）。

它的選項永遠有三個：就地修補（針對現有做法的定點改善，常常被低估，有時它就是正解）、用 strangler 取代（新舊並行、逐步遷移、證明可行才讓舊的退場）、直接取代（只在舊系統真的無法維護、或範圍小且風險低時才用）。

專家意見再次圍繞「不要衝動重寫」：

  • 先量測再最佳化。每次效能改善都從 profiling 資料開始。「感覺很慢」不是設計輸入，「p99 延遲 4 秒、profiling 顯示 80% 花在付款供應商呼叫」才是。
  • strangler 幾乎永遠是生產系統遷移的正確策略。大爆炸重寫會遲交，還會弄壞本來好好的東西。
  • 快取既是資產也是負債。推薦快取之前，先回答三題：快取什麼？什麼讓它失效？它過期時會怎樣？三題答不出來就還不能推薦。
  • 功能旗標是重大變更的部署機制。可以逐步放量、即時回滾、做 A/B 測試，不必重新部署。
  • 生產環境的資料庫遷移要有安全順序：先加可為 null 的欄位 → 部署同時寫新舊兩邊的程式 → 回填 → 加約束 → 移除舊欄位。絕不要在運行中的系統直接加一個沒有預設值的 NOT NULL 欄位。

當遷移不單純（需要超過一次部署、要轉換線上既有資料、需要協調窗口、或沒辦法靠回退一個 commit 完全還原），它會多寫一個 ## Migration plan，交代策略、階段、回滾方式與風險。

CROSS-CUTTING：定義一套跨檔案的標準

CROSS-CUTTING 模式處理的不是壞掉的系統，也不是選技術棧，而是結束不一致：把整個程式庫裡做同一件事的各種方式，收斂成一個明確、可強制執行的標準。它的產出是一份精確定義的「唯一正確做法」。

它的第一步是抽樣，不是全面審查。它列出大約五十個原始檔，但只細讀其中四到六個能代表當前不一致的代表性檔案，先辨認出兩到三種互相競爭的模式，再看它們並存時造成了什麼損害（送到客戶端的錯誤形狀不一致、日誌噪音、型別錯誤、同樣條件下行為不同）。

接著它把標準定義到「星期一早上誰都能照著套用」的程度，包含五件事：唯一的標準範式（一段具體的程式碼範例）、它取代掉哪些模式（明確列出現在算錯的寫法）、強制機制、例外（什麼情況不適用，「沒有例外」也是有效答案）、以及推行方式。

強制機制是有排序的，從最強到最弱：lint 規則或外掛（最好，自動化、CI 會擋）> 編譯期型別或抽象基底類別（好，編譯時就攔）> PR 範本清單（弱，靠人）> 審查慣例（最弱，沒有自動化）。這裡有個很實在的判斷：一個沒有可行強制機制的標準是弱的，因為它最後只會變成一句口號。

CROSS-CUTTING 的選項不是技術，而是強制層級與推行策略的組合：定義標準並向前強制（新程式碼一律遵守，舊的列為待償）、定義標準加上一次性的遷移 PR（一次把不合規的檔案全部改完）、或只寫成文件靠審查。它的設計段是 ## Standard definition，和 ARCHITECTURE 一樣屬於決策型規格，不寫 Build plan。

怎麼選模式

模式不是問來的，是從題目和「這東西在程式碼裡存不存在」推斷出來的，只有在真的模稜兩可時才向你確認。有幾條線索很容易分辨：題目講的是一個還不存在的新功能，就是 FEATURE；題目本身就是選技術棧或基礎架構，就是 ARCHITECTURE；題目要動一個已經在跑的系統，就是 ENHANCEMENT；題目講的是「整個專案都要統一某件事」，就是 CROSS-CUTTING。

還有一個防呆：如果推斷出 ENHANCEMENT，卻在程式庫裡找不到任何原始檔，它會停下來問你，是程式碼在別的目錄，還是其實根本還沒有實作？後者的話，這個題目其實是 FEATURE 或 ARCHITECTURE，模式就會被改掉。這個檢查擋掉「拿改動既有系統的問法，去設計一個全新東西」的錯位。

小結

/architect 背後是一位 Staff Engineer 兼 Principal Architect 的立場：簡單勝過聰明、無聊技術是優點、為失敗設計、用三個時間尺度想事情、維運現實不是選配。動筆前它先挑戰前提，並對照八個已知失敗模式。四種模式各有用途：FEATURE 用第一原理走七個維度並套用功能專家預設，產出 ## Feature design；ARCHITECTURE 先選架構模式再逐層挑技術，在耐久分類上推理、挑當前產品，產出 ## Proposed stack；ENHANCEMENT 讀既有系統、誠實診斷，永遠比較就地補丁、strangler 與直接取代，遷移不單純才加 ## Migration plan；CROSS-CUTTING 抽樣現況、精確定義標準，並依 lint > 型別 > PR 清單 > 審查慣例 排序強制機制，產出 ## Standard definition。

模式選定之後，真正的重頭戲是那場「一次一個決定」的訪談。下一節要看這場 staged design conversation 怎麼從 scope 驗證開始，走過六個階段，最後通過完整性關卡才動筆。
