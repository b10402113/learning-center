四種模式：FEATURE、ARCHITECTURE、ENHANCEMENT、CROSS-CUTTING

Step 3/5 · /architect：從請求到規格

學習目標

學完這一節，你應該能依照情境選出 FEATURE、ARCHITECTURE、ENHANCEMENT 或 CROSS-CUTTING，並說明每種模式會多產出哪個設計段，以及它套用了哪些專家預設。

前言：同一句「幫我設計」，不能用同一套問法

上一節我們看過規格的共同骨架。但骨架只是起點，因為不同的設計對象，真正需要回答的問題並不一樣。

例如，「設計團隊邀請功能」和「幫我挑新專案的技術棧」表面上都像是在做設計，實際上卻是兩種完全不同的工作。前者要釐清資料模型、邀請流程與權限；後者要比較系統規模、團隊能力，以及每一層該採用哪一類技術。

如果 /architect 用同一份問卷處理兩者，設計功能時可能被拖去回答一堆無關的部署問題；挑技術棧時，則可能被要求先寫驗收條件。問題不是問得不夠多，而是問錯了方向。

因此，/architect 會先判斷模式，再依模式決定訪談內容、設計重點與最後的規格段落。這一節就來看四種模式，以及負責寫規格的那個角色，背後採用什麼立場。

誰在寫這份規格？

這個角色被設定成一位有十五年經驗的 Staff Engineer 兼 Principal Architect：管理過服務數百萬使用者的系統，也曾在半夜三點被自己做過的架構決定叫醒，更看過同一批失敗模式在不同公司一再重演。

所以它不會端出一張看似中立的技術菜單，讓你自己從十個選項裡猜答案。它會給出明確方向、坦白說明取捨；如果某個方向明顯會撞上已知的失敗模式，也會直接指出來。

它的幾項思考原則會反覆出現在四種模式中：

  • 簡單勝過聰明。最好的架構，是團隊在週二下午五點、資深工程師請假時，仍然搭得出來、看得懂、跑得動的那一個。
  • 無聊的技術反而是優點。有社群、有文件，而且失敗模式已經被摸透的成熟工具，通常勝過又新又炫的選擇。
  • 為失敗設計，而不是只為順利流程設計。每個決定都要回答：它壞掉時會發生什麼事？我們要怎麼恢復？
  • 用三個時間尺度思考。第一天能不能出貨？第一百八十天能不能維護？第七百三十天團隊擴大後，是否需要重寫？
  • 維運現實不是選配。一個需要多三套基礎設施元件才能運作的「優雅」方案，實際上並不優雅。

它也明確列出幾件不會做的事：不給沒有清楚推薦的選項、不因為某項技術流行就推薦它、不為使用者從未提過的想像規模設計、不忽略團隊實際能達成的能力，也不會只說「這要看情況」卻不說明究竟要看什麼。

動筆之前，先挑戰題目的前提

正式進入模式前，它會先檢查題目本身：

  • 這是不是正確的問題？
  • 有沒有更簡單的框架，能達到同樣目的？
  • 這個方向是否撞上某個已知的失敗模式？

如果發現問題，它會在 ## Context 開頭加入 ⚠️ Premise note。這段內容會說明目前擔心什麼、可能導致哪種失敗，以及比較正確的框架應該長什麼樣子。接著它仍會依照原本的方向繼續工作。你可以否決這個挑戰，但它必須先把風險說清楚。

它同時會檢查三件事：

  • 題目是否大到橫跨三份以上規格。若是，先聚焦在最關鍵的一份，其餘列出來建議另開規格。
  • 功能是否碰觸受規範的資料。若有，就要點名適用法規；安全模型欄位會變成必填，稽核紀錄也不可協商。
  • 依賴的前置決定是否仍然沒有規格。例如題目假設已經存在 auth 與 session 模型，但這些模型其實尚未被定義。

四種模式：先用一張表分清楚

模式什麼時候使用設計行為
FEATURE從零設計一個新功能，不論是否已有部分程式碼以第一原理設計、套用最佳實務，只閱讀必要的程式碼
ARCHITECTURE為新專案選擇技術棧或基礎架構完整評估技術棧與業界模式，不閱讀程式碼
ENHANCEMENT改善、取代或擴充已經存在的東西閱讀既有程式碼與規格，進行聚焦的選項比較
CROSS-CUTTING把某個模式統一到整個程式庫，例如錯誤處理、日誌、auth 或命名抽樣檢查現況、精確定義標準，並提出強制機制

接下來逐一看每種模式多做了什麼。

FEATURE：設計一個新功能

FEATURE 面對的是從零開始的功能，因此採用第一原理。不會把整個程式庫讀完，而是只閱讀這個功能必須整合的既有部分。

它會依序釐清七個維度，一個都不跳過：

  1. 問題：使用者真正想解決什麼問題、想達成什麼結果，而不是只照抄他們口中的功能名稱。
  2. 資料模型：有哪些實體、生命週期狀態，以及哪些不變條件必須永遠成立。
  3. 一致性需求：需要強一致還是最終一致、誰負責寫入、誰負責讀取，以及讀取頻率。
  4. 最小 API 介面：每個端點的方法、路徑、關鍵輸入與輸出、驗證要求，以及最重要的錯誤。
  5. 失敗模式：資料庫變慢、第三方呼叫失敗，或兩個人同時進行相同操作時會發生什麼事。
  6. 安全表面：哪些資料敏感、誰能讀寫，以及採用什麼授權模型。
  7. 設定需求：是否需要新的環境變數、密鑰或第三方憑證。

它也會套用一批專家預設。這些不是為了讓規格看起來更完整，而是把常見的坑提前填掉：

  • 冪等性從第一天做起。所有會改變狀態的操作都要能安全重試；如果涉及金錢、通訊或外部副作用，就使用冪等鍵。
  • 分頁不是選配。任何列表端點都要分頁，MVP 也一樣。沒有分頁的列表，最後很容易變成上線事故。
  • 軟刪除通常是錯的。它會污染查詢、破壞唯一約束，還會留下幽靈資料。應改用明確的 archived_at 時間戳或封存表。
  • 不要預先計算並儲存衍生值。除非已經量到效能問題，否則應在讀取時再計算；儲存起來的值會過期。
  • 稽核紀錄是必要的。只要操作涉及金錢、存取控制、醫療資料或法規範圍，就要留下稽核紀錄。事後補做的成本非常高。
  • 公開端點一定要限流。沒有 MVP 例外。替未登入端點加上限流只需要一小時，卻能擋掉一整類濫用。
  • 永遠不要把密鑰存進資料庫或程式碼。應改用環境變數或密鑰管理服務。

最後，這些內容會收進 ## Feature design，包含資料模型草圖、狀態轉移、API 介面、值來源、關鍵不變條件、安全模型、設定，以及關鍵測試情境。

其中「值來源」表格很容易被忽略，卻是關鍵設計之一。每個動作要產生、計算或顯示的值，都必須寫清楚它從哪裡來。如果某個驗收條件需要一個值，但規格中沒有任何來源，那就代表這個輸入尚未決定。它必須在現在解決，不能留給建置的人自行發明。

ARCHITECTURE：選一套技術棧

ARCHITECTURE 面對的是新專案的技術棧或基礎架構決策。它有一個非常重要的順序：先選架構模式，再選技術。

架構模式主要由系統規模與團隊大小決定：

  • 使用者不到一千、團隊五人以下：先做單體。
  • 使用者一千到十萬、團隊五到十五人：使用分層單體，例如 controller → service → repository。
  • 使用者十萬以上、團隊十五人以上，而且界線清楚：才在領域邊界上拆出兩三條服務。
  • 資料密集的場合：先決定採用批次還是串流。批次，也就是 cron 加倉儲，通常已經足夠。

選好架構模式後，才逐層挑技術。這裡有一個值得記住的方法：先在耐久的分類上推理，再挑當前的產品。

技術產品汰換得很快，因此規格應先定義類別與背後的機制，而不是把某個當下流行的產品寫死。這些耐久分類包括：

  • 主要資料庫：使用關聯式資料庫。
  • 快取：使用記憶體內快取，而且只把它當成暫時資料，絕不當成主要儲存。
  • auth：使用成熟的函式庫或服務，絕不從零手刻。
  • 背景工作：先使用資料庫驅動的佇列。
  • 檔案：使用物件儲存，絕不把檔案塞進資料庫。
  • 搜尋：先使用資料庫內建的全文本搜尋。
  • 可觀測性：使用結構化日誌加錯誤追蹤，而且第一天就要有。

這個模式套用的專家意見，也延續相同的保守邏輯：

  • 單體優先，因為微服務成本高，之後也很難合併回去。
  • 關聯式資料庫是預設選擇，95% 的產品不會遇到它處理不了的負載。
  • serverless 用來跑 API 有真實取捨，包括冷啟動、無狀態、執行時限與連線限制，規格必須明講。
  • 多區域部署延後到真正需要時再做。
  • ORM 處理 CRUD，複雜查詢則直接寫 SQL。
  • 完整的容器編排適合有平台工程團隊的公司；小團隊使用託管平台即可。

ARCHITECTURE 是決策型規格，因此不寫 Build plan。它產出的是 ## Proposed stack：一張逐層列出的技術棧表，而且每一層都必須附上一句理由。

ENHANCEMENT：改動一個已經存在的東西

ENHANCEMENT 面對的是已經上線、正在運作的系統。第一步是閱讀既有程式碼與相關規格；第二步則是做出誠實診斷：

  • 目前的做法實際上如何運作，而不是當初預計如何運作？
  • 問題或落差的根因是什麼？
  • 既有系統帶來哪些限制，例如資料格式、API 合約、團隊知識與遷移風險？

它固定比較三個選項：

  • 就地修補：針對現有做法做定點改善。這個選項常常被低估，但有時它就是正解。
  • 用 strangler 取代：新舊系統並行、逐步遷移，等新方案證明可行後，才讓舊方案退場。
  • 直接取代：只有在舊系統真的無法維護，或範圍小、風險低時才使用。

這裡的專家意見再次圍繞「不要衝動重寫」：

  • 先量測，再最佳化。每次效能改善都要從 profiling 資料開始。「感覺很慢」不是設計輸入；「p99 延遲 4 秒，而且 profiling 顯示 80% 時間花在付款供應商呼叫」才是。
  • strangler 幾乎永遠是生產系統遷移的正確策略。大爆炸重寫容易遲交，也可能弄壞原本運作良好的部分。
  • 快取既是資產，也是負債。推薦快取之前，先回答三個問題：快取什麼？什麼情況會讓它失效？快取過期時會發生什麼事？三題答不出來，就還不能推薦快取。
  • 功能旗標是重大變更的部署機制。它可以逐步放量、即時回滾與進行 A/B 測試，不必重新部署。
  • 生產環境的資料庫遷移要遵守安全順序：先加入可為 null 的欄位 → 部署同時寫入新舊欄位的程式 → 回填資料 → 加上約束 → 移除舊欄位。絕不要在運行中的系統直接加入沒有預設值的 NOT NULL 欄位。

如果遷移不單純，例如需要超過一次部署、必須轉換線上既有資料、需要協調窗口，或無法靠回退一個 commit 完全還原，規格會多出 ## Migration plan，交代遷移策略、階段、回滾方式與風險。

CROSS-CUTTING：定義跨檔案的共同標準

CROSS-CUTTING 處理的不是壞掉的系統，也不是技術棧選擇，而是結束不一致：把整個程式庫裡處理同一件事的不同做法，收斂成一個明確、可以強制執行的標準。

它的第一步是抽樣，不是全面審查。它會先列出大約五十個原始檔，再細讀其中四到六個能代表目前不一致狀況的檔案。目標是先找出兩到三種互相競爭的模式，再確認這些模式並存時造成的損害，例如：

  • 送到客戶端的錯誤形狀不一致。
  • 日誌產生過多噪音。
  • 型別錯誤。
  • 相同條件下出現不同的行為。

接著，它會把標準定義到「星期一早上，任何人都能照著套用」的程度，至少包含五件事：

  • 唯一的標準範式：提供一段具體的程式碼範例。
  • 取代哪些模式：明確列出哪些現有寫法現在算錯。
  • 強制機制：說明如何讓標準真的被遵守。
  • 例外：定義什麼情況不適用；「沒有例外」也是有效答案。
  • 推行方式：說明標準要如何導入程式庫。

強制機制會依照效果排序，從強到弱如下：

lint 規則或外掛（最好，自動化，CI 會擋）> 編譯期型別或抽象基底類別（好，編譯時就攔）> PR 範本清單（弱，依賴人）> 審查慣例（最弱，沒有自動化）。

這裡有一個很實際的判斷：沒有可行強制機制的標準很弱。它最後通常只會變成一句大家都同意、卻沒有人穩定遵守的口號。

CROSS-CUTTING 的選項不是某項技術，而是強制層級與推行策略的組合：

  • 定義標準並向前強制：新程式碼一律遵守，舊程式碼列為待償。
  • 定義標準，再做一次性的遷移 PR：一次修改所有不合規檔案。
  • 只寫成文件，依賴審查執行。

它的設計段是 ## Standard definition。和 ARCHITECTURE 一樣，這是決策型規格，因此不寫 Build plan。

怎麼選模式？

模式不是靠一長串問題問出來的，而是根據題目，以及「這個東西在程式碼裡是否已經存在」推斷出來。只有真的模稜兩可時，才會向你確認。

  • 題目講的是還不存在的新功能：FEATURE。
  • 題目本身是在選技術棧或基礎架構：ARCHITECTURE。
  • 題目要修改已經在運作的系統：ENHANCEMENT。
  • 題目要讓整個專案統一某件事：CROSS-CUTTING。

還有一個重要的防呆檢查：如果推斷出 ENHANCEMENT，卻在程式庫裡找不到任何原始檔，/architect 會先停下來確認：程式碼是在其他目錄，還是其實根本尚未實作？

如果是後者，題目就不該使用 ENHANCEMENT，而應改成 FEATURE 或 ARCHITECTURE。這個檢查可以擋掉一種常見錯位：用「修改既有系統」的問法，去設計一個其實全新的東西。

小結

/architect 背後是一位 Staff Engineer 兼 Principal Architect：簡單勝過聰明、無聊技術是優點、為失敗設計、用三個時間尺度思考，並把維運現實當成必要條件。動筆前，它會先挑戰題目的前提，再對照八個已知失敗模式。

四種模式各自負責不同工作：FEATURE 以第一原理走過七個維度，套用功能設計的專家預設，產出 ## Feature design；ARCHITECTURE 先選架構模式，再逐層挑技術，在耐久的技術分類上推理並選擇當前產品，產出 ## Proposed stack；ENHANCEMENT 閱讀既有系統並做誠實診斷，固定比較就地修補、strangler 與直接取代，遷移不單純時再加入 ## Migration plan；CROSS-CUTTING 抽樣現況、精確定義標準，並依照 lint > 型別 > PR 清單 > 審查慣例排列強制機制，產出 ## Standard definition。

模式選定後，真正的重頭戲才開始：一場「一次只做一個決定」的訪談。下一節會看 staged design conversation 如何從 scope 驗證開始，走過六個階段，最後通過完整性關卡後才動筆。
