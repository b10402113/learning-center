收尾與回報：為什麼第二次執行不該再改東西

Step 6/6 · /sync：把知識對回 repo

學習目標

完成本節後，你應該能讀懂 /sync 的固定回報區塊與 Heads up 的四種指向，說明 idempotent 與 flag-don't-overwrite 如何讓第二次執行維持零新編輯，也能分辨 NOTHING_TO_SYNC 和真正的執行失敗。

前言：沒人看得完的報告，等於沒有報告

你可能收過這種自動工具產生的交差報告：三百行 log，把每個動作從頭到尾列出來。你滑了幾下就放棄，最後只能直接關掉。工具也許做了很多事，卻沒有告訴你哪些需要確認、哪些可以放心略過。

好的收尾報告應該反過來：讓你只看幾行，就知道目前完成了什麼，以及接下來哪些事情需要你決定。接下來看看 /sync 如何把成果交回手上。它會把「已經做好的事」留在檔案與固定報告裡，再用簡短的 Heads up 指出「不能替你決定的事」。這也會帶出整個技能最重要的性質：冪等。

它怎麼交回成果

/sync 在收尾時遵循一個清楚的順序：先說明它對帳了什麼，再列出需要你出手的事。

它不會把每一筆編輯逐項念給你聽，因為那些變更已經寫進檔案，你可以直接查看或還原。真正需要你注意的，是它不能自行決定的內容，例如某份 spec 已經過期、某個 context gap 需要另一個 skill 補足，或某段精心整理過的文字發生衝突。

它會用類似下面的模板回報：

## /sync complete · reconciled <N> changed files

**Updated <AGENTS.md files · scope features · spec statuses> to match the diff.**
Heads up (need you):
- Stale spec → /architect: `<file>` (<為什麼>)
- Assumed, not ratified → /architect: `<file>`
- Context gap → /audit: `<area>`
- Conflict, decide manually: `<path>`

這個模板有幾個重要的細節。某一類沒有內容時，對應的 bullet 會直接省略。如果整段 Heads up 都沒有項目，連整個區塊也不會出現，不會硬留下「Heads up: 無」這種沒有資訊量的句子。

同樣地，/sync 不會逐項列出自己做了哪些對帳動作，例如打了幾個勾、清掉哪些孤兒。這些結果都已經反映在檔案裡。最重要的是：它不會替你執行 /architect 或 /audit。它只指出方向，最後的決定權仍然在你手上。

Heads up 的四種指向

四種指向，對應四種 /sync 無法安全自行處理的情況：

指向情況
Stale spec → /architect某份 spec 被這次改動違反，或出現它無法安全對齊的狀態落差
Assumed, not ratified → /architect有一份 Assumed spec 尚未追認；它不會阻擋 done，但需要 /architect 正式承認
Context gap → /audit某個區域早已存在，卻沒有文件；只靠這次 diff 不足以寫出可靠的說明
Conflict, decide manually某段精心整理過的內容若要改動，就必須重寫；這類判斷交由人處理

看到這四類，你就能快速決定下一步：前兩類交給 /architect，第三類交給 /audit，第四類則由你手動判斷。原本可能很長的執行紀錄，就這樣被壓縮成幾行決策清單。

另一種回報：逐項的報告區塊

除了給人快速閱讀的摘要，/sync 的維護規則也定義了一個固定的報告區塊，逐項記錄它做過的事。這份區塊像一張可稽核的收據：欄位固定，有內容才列出，沒有內容就省略。

  • SCOPE：這次變更集包含幾個檔案。
  • AGENTS_UPDATED / AGENTS_CREATED：修改或新建了哪些 AGENTS.md。
  • ORPHANS_CLEANED：清掉哪些孤兒文件、修復哪些斷掉的指標。
  • SCOPE_RECONCILED：哪些 feature 的子任務被打勾，或哪些狀態被推進。
  • SPEC_STATUS_RECONCILED：哪些 spec 的 Status 行已完成對齊。
  • STALE_SPECS / CONTEXT_GAPS / CONFLICTS：需要交由後續工具或人處理的過期項目、資訊缺口與衝突。

如果這一趟沒有任何檔案需要修改，也沒有找到過期內容，/sync 不會硬湊一份空報告。它會直接輸出 SCOPE: <N> changed files，再加上 NOTHING_TO_SYNC: everything is already current。

NOTHING_TO_SYNC 不等於失敗

這裡有一個很容易混淆的差別。兩種「什麼都沒做」看起來相似，意義卻完全相反。

NOTHING_TO_SYNC 代表 /sync 確實完成檢查，確認所有內容都已經是最新狀態。這是正常的成功結果。

另一種則是真正的執行失敗，例如程式 crash，或只輸出無法解析的空內容。這時不能把失敗偽裝成 NOTHING_TO_SYNC。規則很直接：如果維護失敗，或沒有產生可解析的摘要，就照實回報，然後再做一次，絕對不能編造一個看似正常的結果。

這條規則正好反映了這個技能的工作態度：寧可明確說「我還沒完成」，也不要用假綠結果掩蓋問題。

為什麼第二次跑不該再改東西

現在回到整個技能最重要的性質：idempotent（冪等）。它的意思是，同一份變更第一次執行時會完成該做的編輯；第二次用同樣的輸入再執行，應該產生零筆新編輯。

這不是碰巧發生，而是每個動作都刻意這樣設計。修改 AGENTS.md 前，會先讀取現況；如果該事實已經存在，即使文字措辭不同，也不會再追加一次。對齊 spec 狀態前，會再次確認 Status 行；如果已經等於目標，就不做任何變更。scope 中已經打勾的框也會維持原樣，重跑不會重複修改。

冪等再加上「flag 而不覆寫」，就是 /sync 能安全重複執行的原因。你可以對同一個分支跑第二次、第三次，不必擔心文件被越改越亂。它每一次都像第一次一樣保守：只補真正缺少的內容，不覆寫已經存在的內容。

小結

/sync 的回報分成兩層：給人看的摘要只列出「需要你出手的事」，用四種 Heads up 指向對應的 skill 或人類；逐項的報告區塊則留下可稽核的紀錄，空的欄位直接省略。它不會幫你跑 /architect 或 /audit，只指出方向。NOTHING_TO_SYNC 是正常的成功，執行失敗則要據實回報並重做，不能捏造結果。整個技能靠 idempotent 加 flag 而不覆寫，保證同一份變更跑第二次時零新編輯。

到這裡，這個節點的六個步驟就完成了。你已經知道 /sync 如何圈出變更、探索新工具、對齊 AGENTS.md 與 scope／spec，以及如何用清楚的方式回報結果。

接下來，在自己的練習專案上實際跑一次。你要驗證的不是報告看起來漂不漂亮，而是兩件可觀察的事：第一次執行是否真的完成應有的對帳，第二次執行是否真的維持零新編輯。
