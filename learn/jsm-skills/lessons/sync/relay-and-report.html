收尾與回報：為什麼第二次跑不該再改東西

Step 6/6 · /sync：把知識對回 repo

學習目標

能讀懂 /sync 的固定回報區塊與 Heads up 四種指向，說明 idempotent 與 flag-don't-overwrite 如何在第二次執行時保證零新編輯，並分辨 NOTHING_TO_SYNC 與執行失敗。

前言：一份沒人看得完的報告，等於沒有報告

你有沒有收過那種自動工具吐出來的交差報告：三百行 log、每個動作都列一遍，你滑了兩下就放棄，直接關掉。工具做了很多事沒錯，但它沒有幫你分辨「哪些需要你看一眼、哪些可以完全放心」。一份好的收尾報告，應該是「你只需要看幾行」。

接下來看 /sync 怎麼把成果交回你手上。它把「做了什麼」和「需要你決定什麼」拆開：前者留在檔案裡，後者用一個簡短的 Heads up 段落點出來。看完這一節，你也能理解它整個技能最重要的一個性質：冪等。

它怎麼交回成果

/sync 在收尾時有一個很清楚的原則：先講它對帳了什麼，再列出「需要你出手的事」。它不小心把每一筆編輯都唸給你聽，因為那些編輯本身就在檔案裡，你看得到、也可以還原。真正需要你注意的是那些它不能自己決定的事，例如某份 spec 已經過期、某個 gap 需要另一個 skill 補、或某段精心寫過的內容出現了衝突。它會用一個模板來呈現，大致長這樣：

## /sync complete · reconciled <N> changed files

**Updated <AGENTS.md files · scope features · spec statuses> to match the diff.**
Heads up (need you):
- Stale spec → /architect: `<file>` (<為什麼>)
- Assumed, not ratified → /architect: `<file>`
- Context gap → /audit: `<area>`
- Conflict, decide manually: `<path>`

這個模板有幾個設計到細節的地方。它會把「這個區塊裡沒有東西」的 bullet 直接刪掉；如果整段 Heads up 一個項目都沒有，那就整段不出現，不留一句「Heads up: 無」。它也不會列出自己做了哪些對帳動作（打了幾個勾、清了哪些孤兒），那些都在檔案裡。最關鍵的一條是：它不幫你跑 /architect 或 /audit。它只負責指出方向，決定權留給你。

Heads up 的四種指向

這四種指向，剛好對應前面幾節學過的四種「它不能自己處理」的情況：

指向情況
Stale spec → /architect某份 spec 被這次改動違反了，或是一個它無法安全對齊的狀態落差
Assumed, not ratified → /architect有一份 Assumed spec 欠追認；它不擋 done，但需要 /architect 正式承認
Context gap → /audit一個早就存在但沒有文件的區域，光看這次 diff 不足以寫出好文件
Conflict, decide manually某段精心寫過的內容若要改準，就得重寫；這種事留給人

看到這四行，你就能很快決定下一步：前兩類去找 /architect，第三類去找 /audit，第四類自己判斷。這就是「只列需要你的」的價值，它把一份可能很長的執行紀錄，壓縮成幾行決策清單。

另一種回報：逐項的報告區塊

除了給人看的摘要，/sync 在維護規則裡還定義了一個固定的報告區塊，逐項列出它做了什麼。這個區塊的用意是當作一份可稽核的紀錄，欄位固定、缺的就省略，包括：

  • SCOPE：這次變更集有幾個檔案。
  • AGENTS_UPDATED / AGENTS_CREATED：改了或新建了哪些 AGENTS.md。
  • ORPHANS_CLEANED：清掉哪些孤兒文件、修好哪些斷掉的指標。
  • SCOPE_RECONCILED：哪些 feature 的子任務被打了勾、狀態被推進。
  • SPEC_STATUS_RECONCILED：哪些 spec 的 Status 行被對齊。
  • STALE_SPECS / CONTEXT_GAPS / CONFLICTS：需要交出去的過期、缺口與衝突。

如果它這一趟什麼都沒改、也沒找到任何過期的東西，它不會硬湊一份報告，而是直接輸出 SCOPE: <N> changed files 加上 NOTHING_TO_SYNC: everything is already current。

NOTHING_TO_SYNC 不等於失敗

這裡有一個容易混淆的區分。有兩種「什麼都沒做」長得很像，但意義完全相反：一種是 NOTHING_TO_SYNC，代表它確實檢查過、確認一切都已經是最新的，這是一個正常的成功結果；另一種是執行真的失敗了，例如 crash 或吐出無法解析的空輸出。後者不能當成前者。規則很直白：如果維護失敗、或沒有產生可解析的摘要，就據實回報，然後再做一次，絕不編一個結果出來交差。

這條規則其實是這個技能整個態度的縮影：它寧可老實說「我沒做完」，也不願假裝一切正常。

為什麼第二次跑不該再改東西

最後回到整個技能最重要的一個性質：idempotent（冪等）。意思是，同一份變更，第一次跑會做出該做的編輯；第二次再跑，應該是零新編輯。這不是巧合，而是每一個動作都被設計成這樣：改 AGENTS.md 前會先讀一次，如果那個事實已經在了，即使措辭不同也不再加；對齊 spec 狀態前會再讀一次，如果那一行已經等於目標，就什麼都不做；scope 上已經打勾的框維持打勾，重跑不會有任何變動。

冪等加上「flag 而不覆寫」，合起來解釋了 /sync 為什麼可以安全地反覆執行。你可以放心地對同一個分支跑第二次、第三次，不用擔心它會把文件愈改愈亂。它每一次執行，都像第一次那樣保守。

小結

/sync 的回報分成兩層：給人看的摘要只列出「需要你出手的事」，用四種 Heads up 指向對應的 skill 或人類；逐項的報告區塊則留下可稽核的紀錄，空的欄位直接省略。它不會幫你跑 /architect 或 /audit，只指出方向。NOTHING_TO_SYNC 是正常的成功，執行失敗則要據實回報並重做，不能捏造結果。整個技能靠 idempotent 加 flag 而不覆寫，保證同一份變更跑第二次時零新編輯。
