/sync 的定位與界線：外科手術，不是重寫

Step 1/6 · /sync：把知識對回 repo

學習目標

能說出 /sync 在流程裡的位置、AGENTS.md 與 CLAUDE.md 的 canonical 關係，並用 Boundaries 表分清它自己維護什麼、哪些要 flag 給 /audit、/architect、/scope 或人類。

前言：那份沒人更新、卻人人照著做的工作筆記

你接手一個專案，找到根目錄的 AGENTS.md，裡面寫著建置指令。你照著打，終端機回你一個錯誤。回頭問同事，他說：「喔，那條指令半年前就換了，筆記沒改。」

這種事每個 repo 都發生過。程式碼天天在動，但那些「給人跟 agent 看的說明」往往停在某個過去的時間點。平常沒人注意到，直到有人照著過期資訊做錯事，才發現文件跟現實已經對不上。jsm-skills 把「把知識對回現實」獨立成一個階段，就是 /sync。它跑在一個改動完成、快要合併的時候，專門負責讓 AGENTS.md、feature scope、spec 狀態重新跟 repo 現在的樣子一致。

這一節先把它的定位與界線講清楚。因為它最重要的設計，在於它拒絕做什麼，而不在它會做什麼。

它在流程裡的位置：收尾，不是開場

前面幾個階段都在「生出」東西。/architect 生規格，/develop 生程式碼，/test 生測試，/document 生文件。/sync 不生產，它做的是對帳：把已經發生的變動，反映到那些長期保存的知識檔上。所以它被放在接近合併的地方，處理的對象是「這次改動碰到的範圍」。

它的基本姿態是保守。它預設「什麼都不做」，只有在程式碼真的改掉了一條指令、一個慣例、一個約束、一個依賴或一個檔案結構時，才去動知識檔。一段只是「敘述這次改了什麼」的文字，它不會寫進去，因為那是 churn（製造無謂的變動），不是維護。

canonical 檔案：AGENTS.md 是本體，CLAUDE.md 只是指標

這套工作流把「跨工具的長期知識」放在 AGENTS.md，因為它是工具中立的，任何 agent 都讀得懂。CLAUDE.md 則被當成一個薄薄的指標檔，裡面不寫內容，只用 Claude Code 的 @ 指示把隔壁的 AGENTS.md 匯入進來。換句話說，知識只有一份，放在 AGENTS.md；CLAUDE.md 指過去就好。

當 /sync 為一個全新區域建立 nested AGENTS.md 時，它會順手生出一個同資料夾的 CLAUDE.md，內容固定是這三行：一個標題、一句「這個專案的 AI 上下文放在 AGENTS.md」、以及 @AGENTS.md 這行匯入。這樣 Claude Code 才接得到新區域。規則是死的：內容永遠不寫進 CLAUDE.md，而且永遠不覆寫一份已存在的 AGENTS.md。

它擁有什麼、不碰什麼：Boundaries 表

這套設計最值得學的地方，是它把「擁有權」寫成一張表。左邊是動作，中間是 /sync 做不做，右邊是真正的擁有者。看到這張表，你就知道它為什麼被形容成「外科手術」：它只加行、只改它擁有的單行，從不重寫整個段落。

看這張表要抓到一條分界線：新建的判斷標準是 context，不是 policy。只有當這次的 diff 讓你看見「整個區域」時，你才有資格替它寫文件；如果那個區域在你這個改動之前就存在，你只看到它的一角，就該 defer 給 /audit。不確定時，一律 flag，不要建立。

它什麼時候停下來

/sync 幾乎不打斷你。它唯一的暫停條件是「沒有任何東西可以對帳」，也就是這次的變更集是空的。除此之外它會一路做完，然後把每一筆動過的檔案列在報告裡，讓你可以自己檢查或還原。它不會幫你跑 /architect 或 /audit，它只負責指出問題，決定權留給你。

小結

/sync 是流程的收尾階段，跑在改動完成、接近合併時，把長期知識對回 repo 現況。長期知識的本體是工具中立的 AGENTS.md，CLAUDE.md 只是匯入它的指標。它靠一張 Boundaries 表界定擁有權：既有 AGENTS.md、相關 scope、spec 的 Status 行由它維護；root 的建立與重整、spec 內容、feature 清單則 flag 給對應的 skill 或人類。新建 nested 文件的判斷是「context，不是 policy」，不確定就 flag 而不動手。

現在你知道了它的界線，但它要對帳的前提是「知道這次到底改了什麼」。下一節就從最前線開始：怎麼用 git 把這次的變更集圈出來。
