/sync 的定位與界線：外科手術，不是重寫

Step 1/6 · /sync：把知識對回 repo

學習目標

完成這一節後，你應該能說清楚 /sync 在整個流程中的位置，理解 AGENTS.md 與 CLAUDE.md 的 canonical 關係，並用 Boundaries 表判斷：哪些事情由 /sync 維護，哪些要 flag 給 /audit、/architect、/scope 或人類。

前言：那份沒人更新，卻人人照著做的工作筆記

你接手一個專案，看到根目錄有一份 AGENTS.md，裡面寫著建置指令。你照著執行，終端機卻回報錯誤。回頭問同事，得到的答案是：「那條指令半年前就換了，只是文件一直沒改。」

這種情況在 repo 裡很常見。程式碼持續變動，但提供給人類與 agent 參考的說明，可能還停在某個過去的版本。平常大家不一定察覺，直到有人照著過期資訊操作，才發現文件與現實早已分叉。

jsm-skills 把「讓知識回到現實」獨立成一個階段，這就是 /sync。它通常在改動完成、接近合併時執行，專門讓 AGENTS.md、feature scope 與 spec 狀態重新對齊目前的 repo。

這一節先把它的定位與界線講清楚。因為 /sync 最重要的設計，不只是它會做什麼，更是它刻意拒絕做什麼。

它在流程裡的位置：收尾，不是開場

前面的階段都在產出新東西：/architect 產出規格，/develop 產出程式碼，/test 產出測試，/document 產出文件。

/sync 則不負責生產內容。它比較像對帳人員：把已經發生的程式碼變動，反映到需要長期保存的知識檔案中。因此它被放在接近合併的位置，而且只處理這次改動實際碰到的範圍。

它的基本姿態是保守。預設狀態是「什麼都不做」，只有在程式碼真的改變了某條指令、某個慣例、某項約束、某個依賴或某段檔案結構時，才會更新知識檔。單純描述這次改了什麼，不代表應該把那段文字寫進長期文件；那通常只是 churn，也就是製造沒有必要的變動。

canonical 檔案：AGENTS.md 是本體，CLAUDE.md 只是指標

這套工作流把跨工具的長期知識放在 AGENTS.md。它與特定工具無關，任何 agent 都能讀取。

CLAUDE.md 則是一個薄薄的指標檔。它不保存知識，只使用 Claude Code 的 @ 指示，把同一個資料夾中的 AGENTS.md 匯入進來。換句話說，知識只有一份：放在 AGENTS.md；CLAUDE.md 只負責指向它。

當 /sync 為全新區域建立 nested AGENTS.md 時，也會在同一個資料夾建立 CLAUDE.md。它的內容固定包含三部分：一個標題、一句「這個專案的 AI 上下文放在 AGENTS.md」，以及 @AGENTS.md 這行匯入指示。這樣 Claude Code 才能取得新區域的上下文。

規則很明確：知識永遠不寫進 CLAUDE.md，也永遠不覆寫已存在的 AGENTS.md。

它擁有什麼、不碰什麼：Boundaries 表

這套設計最值得掌握的地方，是把「誰擁有什麼」寫成一張表。你可以把 /sync 想成拿著手術刀的維護者：只在自己負責的地方加一行、改一行，避免整段重寫，更不會順手改掉別人精心整理的內容。

讀這張表時，最重要的是抓住一條界線：新建文件的判斷標準是 context，不是 policy。

只有當這次 diff 讓你看見「整個區域」時，才有足夠上下文替它建立文件。如果那個區域早在這次改動之前就存在，而你只看見其中一角，就應該 defer 給 /audit。不確定時，一律 flag，不要自行建立。

它什麼時候停下來

/sync 幾乎不會中途打斷流程。唯一的暫停條件是沒有任何東西可以對帳，也就是這次的變更集是空的。

除此之外，它會一路完成工作，並在報告中列出每一個被修改的檔案。你可以依報告自行檢查，也可以還原不想保留的變更。

它不會自動替你執行 /architect 或 /audit。遇到需要重新設計、追認或全面盤點的問題時，它只負責指出問題；下一步怎麼處理，仍由你決定。

小結

/sync 是流程的收尾階段，通常在改動完成、接近合併時執行，將長期知識對回 repo 現況。長期知識的本體是工具中立的 AGENTS.md，CLAUDE.md 只是匯入它的指標。

它透過 Boundaries 表界定擁有權：既有 AGENTS.md、相關 scope，以及 spec 的 Status 行由它維護；root 的建立與重整、spec 內容、feature 清單則 flag 給對應的 skill 或人類。建立 nested 文件時，判斷標準是「context，不是 policy」；不確定時就 flag，不要動手。

現在你已經知道 /sync 的界線。但要開始對帳，還有一個前提：先確認這次到底改了什麼。下一節會從最前線開始，說明如何用 git 圈出這次的變更集。
