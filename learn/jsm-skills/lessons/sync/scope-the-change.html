從 git 圈出這次要對的變更

Step 2/6 · /sync：把知識對回 repo

學習目標

能用 git 取出這次的變更集（先驗 freshness、判斷 base 與 mode、用 --name-status 取得 A/M/D），濾掉文件與測試只留 source 檔，並定位出該看的 AGENTS.md、specs 與這次相關的 scope 路徑。

前言：對帳前，先確認帳本是哪一本

上一節說 /sync 的工作是對帳。對帳的第一步永遠是「拿出這次的帳本」，也就是「這個改動到底碰了哪些檔案」。而這個問題的答案，取決於你現在站在哪裡：改動還沒 commit，跟改動已經在一個領先主線的分支上，是兩種完全不同的取法。

如果它一開始就亂抓，比方說不小心把整個 repo 當成變更範圍，那它會去更新一堆跟這次無關的東西，製造出大量噪音。所以它有一套固定的開場流程，先確認你身處的狀態，再精準地圈出範圍。這一節就來看這套流程，以及它圈完範圍後是怎麼定位相關檔案的。

第一件事：確認你沒有落後主線

在團隊裡，最怕的是「別人已經同步過同一份文件，你又跑一次」。所以 /sync 的開場是一個 freshness（新鮮度）檢查：先 git fetch 把遠端狀態抓下來，再看你落後主線幾個 commit。如果發現你落後了，它會停下來提醒你先 pull，因為可能已經有隊友處理過這些文件。這個檢查花不了多少成本，卻能避免重複勞動與互相打架。

判斷 base 與模式：你是在 commit 前還 commit 後

接下來要決定「拿什麼當比較基準」。基準分支是 main，如果沒有就用 master。然後看現在的 branch 是不是就是基準本身，這會決定走哪一種模式：

  • 如果當前分支就是基準分支，模式是 uncommitted，它用 git diff --name-status HEAD 看你還沒 commit 的改動。
  • 如果當前分支領先基準，模式是 branch，它先找出 git merge-base（兩條分支的共同祖先），再 git diff --name-status 比較那個共同點到現在。

這裡有一個容易忽略的小細節：它用的是 --name-status，不是 --name-only。差別在於，前者會給每個檔案一個狀態碼，而這個狀態碼決定了後面兩種邏輯怎麼跑。

三種狀態碼：A、M、D 各有用途

--name-status 會在每個檔案前面標一個字母：A 代表這次新增（Added），M 代表這次修改（Modified），D 代表這次刪除（Deleted）。這三個字母不是裝飾，它們直接餵給後面的判斷：一個區域是不是「全新」，要看它底下的檔案是不是全部都是 A；有沒有孤兒文件要清，要看那些 D 的檔案。

除了追蹤中的檔案，它還會用 git ls-files --others --exclude-standard 把還沒被追蹤的新檔案也撈進來，並幫它們補上一個 A，讓格式跟前面的輸出一致。到這裡，一份完整的變更清單就成形了。

過濾：只留程式碼，其餘分開擺

拿到清單後，它會先移除重複，再過濾成「拿來當作變更來源」的檔案。這裡的邏輯很值得學，因為它展現了 /sync 的分寸：有些檔案它不是不看，而是不把它們當成「變更的來源」，只把它們當成「要被更新的目標」。

首先被剔掉的，是文件與設定檔：任何層級的 AGENTS.md、docs/**、*.md、test-preferences.json、lock 檔、產生物。這些正是 /sync 要讀取的目標或上下文，如果把它們也當成變更來源，就會邏輯打結。接著被剔掉的是測試檔，因為測試不是某個區域的長期慣例。

但它沒有把刪除的檔案直接丟掉。那些 D 的項目會被單獨放進一份清單，留給後面的孤兒清理用。同樣地，依賴清單的變動（例如 package.json、pyproject.toml、go.mod 這類 manifest）也會單獨放一份，因為它們要餵給下一步的工具探索。要注意的是，它只拿 manifest 當訊號，不會把 lock 檔的內容拿去用。

最後有一個重要的煞車：如果把文件、測試、lock、產生物全濾掉之後，已經沒有 source 檔、也沒有 manifest 變動了，它就停下來，判定「沒有東西要同步」。這個 NOTHING_TO_SYNC 不是失敗，而是一個完全正常的結果。

第二步：定位相關檔案，但先不要讀

圈完變更集之後，它要找出「這次該看哪些知識檔」。這裡有一個紀律：這一步只記路徑，不讀內容。因為真正的閱讀要留到寫入階段，現在讀只會白白塞爆 context，而且讀到的還可能過期。它會用檔案搜尋工具做四件事：

  1. 確認 root 有沒有 AGENTS.md。
  2. 找出所有 AGENTS.md（root 加 nested），排除 node_modules/ 與 .git/。
  3. 找出 docs/specs/ 底下所有以數字開頭的 spec，並排序。
  4. 找出這次 diff 真正碰到的 workspace 對應的 scope 檔；在 monorepo 裡，一個像是 apps/<x>/… 的變更，會去選 docs/scope/<x>/，而且它永遠不會讀或傳入整個 docs/scope/。

唯一現在就讀的是 root AGENTS.md，因為它通常很短，而且能提供一個整體的錨點。它也會為每個變更檔記下「最靠近它的那個 AGENTS.md」是哪一個（root 或 nested），那通常是這份改動最可能需要更新的上下文檔。

把 scope 限定在「相關的 workspace」而不是整個 docs/scope/，是為了守住一條界線：一個 workspace 的改動，不該授權你去動另一個 workspace 的紀錄。

小結

/sync 的開場是圈出變更集。它先驗 freshness（落後主線就提醒先 pull），判斷 base（main，否則 master）與模式（uncommitted 或 branch），用 --name-status 取得每個檔案的 A／M／D 狀態，並補上未追蹤的新檔。接著把文件與測試濾掉，只留 source 檔當變更來源，但保留 D 清單（孤兒清理）與 manifest 清單（工具探索）。若濾完一無所有就停。第二步只記路徑不讀內容，會定位 root／nested AGENTS.md、docs/specs/ 的 spec，以及這次相關 workspace 的 scope 檔，並建立「變更檔 → 最近上下文檔」的對應。

範圍圈好了，接下來有一個岔路：如果這次改動新增了重量級的外部工具，/sync 會在中途停下來問你一件事。下一節就來處理這個「先問再做」的岔路。
