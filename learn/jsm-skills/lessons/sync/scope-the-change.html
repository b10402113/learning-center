先用 git 圈出這次真正要對的變更

Step 2/6 · /sync：把知識對回 repo

學習目標

完成這一節後，你會知道如何用 git 取出本次變更集：先檢查 freshness，再判斷 base 與 mode，接著用 --name-status 取得 A、M、D 狀態。之後，把文件與測試排除，只留下 source 檔，並定位這次真正相關的 AGENTS.md、spec 與 scope 路徑。

前言：對帳前，先確認拿的是哪一本帳

/sync 的工作是對帳，但對帳不能一開始就把整個 repo 攤在桌上。第一步應該先回答一個問題：這次改動到底碰了哪些檔案？

答案取決於改動目前處在哪種狀態。它可能還沒 commit，直接留在基準分支上；也可能已經 commit，存在一個領先主線的 branch。這兩種情況要用不同方式取得變更。

如果一開始就抓錯範圍，例如把整個 repo 都當成這次的變更，後續就會讀到大量無關內容，甚至更新不該碰的文件。這就像拿整本帳簿逐頁重對，最後噪音比線索還多。因此，/sync 有一套固定的開場流程：先確認目前狀態，再精準圈出變更，最後才找相關知識檔。

第一件事：確認沒有落後主線

團隊協作時，一個常見風險是：隊友已經同步過同一份文件，你卻在不知道的情況下又處理一次。結果可能是重複勞動，也可能讓兩次更新互相打架。

所以 /sync 一開始會做 freshness（新鮮度）檢查。它先執行 git fetch，取得遠端最新狀態，再檢查目前分支落後主線幾個 commit。

如果發現目前分支落後主線，流程就會停下來，提醒你先 pull。這個檢查成本很低，卻能先擋住「拿著過期狀態開始同步」的風險。

判斷 base 與模式：改動是在 commit 前，還是 commit 後？

確認沒有落後主線後，下一步是決定比較基準。基準分支優先使用 main；如果 repo 沒有 main，就使用 master。

接著檢查目前所在的 branch 是否就是這個基準分支。這會決定 /sync 要走哪一種模式：

  • 如果目前分支就是基準分支，模式是 uncommitted。此時用 git diff --name-status HEAD，查看尚未 commit 的改動。
  • 如果目前分支領先基準分支，模式是 branch。此時先找出 git merge-base，也就是兩條分支的共同祖先，再用 git diff --name-status 比較共同祖先到目前狀態之間的變更。

這裡不是單純列出檔名而已。/sync 特別使用 --name-status，而不是 --name-only。原因是後續判斷需要知道每個檔案的狀態碼；只拿檔名，就像只知道包裹的地址，卻不知道它是新寄出的、被修改過的，還是已經取消的。

三種狀態碼：A、M、D 各自提供線索

--name-status 會在每個檔案前標上一個字母：

  • A 代表新增（Added）。
  • M 代表修改（Modified）。
  • D 代表刪除（Deleted）。

這些狀態碼會直接影響後續邏輯。例如，要判斷某個區域是否全新，就要看其中的檔案是否全部都是 A；要找出需要清理的孤兒文件，則要另外查看狀態為 D 的檔案。

除了已被 git 追蹤的檔案，/sync 也會用 git ls-files --others --exclude-standard 找出尚未被追蹤的新檔案，並替它們補上 A。這樣一來，已追蹤與未追蹤的變更就能使用同一種格式處理。

到這裡，完整的變更清單才算建立完成。

過濾：只把 source 當成變更來源

有了完整清單後，/sync 會先移除重複項目，再把檔案分成不同用途。這裡有一個重要分寸：有些檔案不是不看，而是不把它們當成「變更來源」。它們可能是後續要讀取或更新的目標，角色不同，不能混在一起。

首先排除的是文件與設定檔，包括任何層級的 AGENTS.md、docs/**、*.md、test-preferences.json、lock 檔與產生物。這些檔案本身可能是同步的目標或上下文。如果把它們也當成變更來源，流程就會拿「要被更新的內容」反過來決定「要更新什麼」，範圍容易失控。

測試檔也會被排除。原因是測試描述的是驗證方式，不是某個區域長期維持的慣例；因此它們不應直接成為同步知識的來源。

不過，被排除不代表被丟掉。狀態為 D 的檔案會另外放進刪除清單，交給後續的孤兒清理使用。

依賴清單的變動也會單獨整理。例如 package.json、pyproject.toml 與 go.mod 這類 manifest，會提供給下一步的工具探索。要注意的是，這裡只把 manifest 當成訊號，不會把 lock 檔內容拿來使用。

安全煞車：什麼都沒有要同步時就停下來

完成過濾後，如果已經沒有 source 檔，也沒有 manifest 變動，/sync 就會停止，判定為 NOTHING_TO_SYNC。

這不是失敗，而是正常結果。它代表這次變更只有文件、測試、lock 或產生物等項目，沒有足以觸發同步的 source 或依賴清單變動。這個煞車能避免 agent 為了「做點什麼」而擴大範圍，留下不必要的更新。

第二步：定位相關檔案，但先不要讀內容

變更集圈好後，下一個問題是：這次應該查看哪些知識檔？這一步有一條嚴格紀律：只記錄路徑，不讀內容。

真正的閱讀會留到寫入階段。現在就把所有文件讀進 context，不只浪費空間，也可能讀到已經過期的內容。先定位、後閱讀，就像先把要查的書列成清單，而不是把整座圖書館搬進房間。

這一步會透過檔案搜尋工具完成四件事：

  1. 確認 repo root 是否有 AGENTS.md。
  2. 找出所有 AGENTS.md，包括 root 與 nested 版本，同時排除 node_modules/ 與 .git/。
  3. 找出 docs/specs/ 底下所有以數字開頭的 spec，並依序排序。
  4. 找出這次 diff 實際碰到的 workspace 所對應的 scope 檔。在 monorepo 中，如果變更路徑像是 apps/<x>/…，就選擇 docs/scope/<x>/；而且永遠不會讀取或傳入整個 docs/scope/。

唯一會在此時讀取的是 root AGENTS.md。它通常很短，可以提供整體規則與方向，作為後續處理的錨點。

此外，/sync 會為每個變更檔記下「離它最近的 AGENTS.md」。這份檔案可能是 root 版本，也可能是 nested 版本；它通常是這次變更最可能需要更新的上下文文件。

scope 只限定在相關 workspace，而不是整個 docs/scope/，是為了守住變更邊界：一個 workspace 的改動，不應該授權流程去修改另一個 workspace 的紀錄。

小結

/sync 的開場任務，是先把變更集圈準。它會先檢查 freshness；如果目前分支落後主線，就提醒先 pull。接著以 main 為優先、master 為備選，判斷要走 uncommitted 還是 branch 模式。

取得差異時使用 --name-status，保留每個檔案的 A、M、D 狀態，並把未追蹤的新檔案補成 A。之後移除文件、測試、lock 與產生物，只保留 source 檔作為變更來源；但會另外保留 D 清單供孤兒清理使用，也會保留 manifest 清單供工具探索。若過濾後沒有 source 或 manifest 變動，就以 NOTHING_TO_SYNC 正常停止。

完成變更定位後，第二步只記錄路徑、不讀內容。流程會找出 root 與 nested 的 AGENTS.md、docs/specs/ 中的 spec，以及這次變更所屬 workspace 的 scope 檔，並建立「變更檔 → 最近上下文檔」的對應。

範圍圈好後，流程會遇到下一個岔路：如果這次改動新增了重量級的外部工具，/sync 會先停下來問你是否要繼續。下一節將處理這個「先問再做」的岔路。
