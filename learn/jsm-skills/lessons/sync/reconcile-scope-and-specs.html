對齊 scope 與 spec：打勾、改狀態、標過期

Step 5/6 · /sync：把知識對回 repo

學習目標

這一節要處理的是「程式已經完成，但知識還停在原地」的落差。你會學會依照 scope 狀態，只修改 spec 的 Status 行；嚴格判斷什麼時候該把 spec 標成 stale；再以 universal sub task reconciler 的身分，根據證據替 feature 的子任務打勾並推進狀態。

同時要守住幾條界線：只能改狀態，不能新增或刪除 feature；不能猜測模糊的歸屬；不能把已完成的 feature 降級；也不能擅自修改 spec 內容。

前言：功能完成了，文件卻還停在原地

想像一個功能的程式碼已經存在，測試也通過，PR 甚至已經合併。但你打開 scope，對應的框仍然是空的，狀態還停在 in-progress；再看 spec，Status 甚至仍然是 Proposed。

只看文件，你會以為這個功能才剛開始。只有回到 repo，翻檔案、搜尋實作、執行驗證，才會發現它其實早就完成了。

這通常不是某個人忘了做事，而是每個 skill 只負責自己那一段：/develop 可能勾了開發子任務，卻沒有人補上 /test、/audit 或 /sync 的結果。最後 scope 有幾格一直空著，spec 狀態也永遠慢半拍。

/sync 的工作，就是把這些知識重新對回 repo 的實際狀態。但它不是來「順手整理文件」的萬能編輯器，而是一個有明確權限的 reconciler：能確認的才更新，無法確認的就留下紀錄，不靠猜測補洞。

先理解 spec 的狀態對應

spec 的狀態，是它所治理 feature 建置週期的鏡子。因此，兩邊的對應是固定的：

spec 的 Status意義對應的 scope 狀態
Proposed還沒開始建置planned
In Progress正在建置in-progress
Accepted已建置且驗證完成；功能尚未上線前，不算 Accepteddone
Superseded已被後來的 spec 取代不從 scope 狀態設定，而是另外 flag

這張表看似簡單，真正容易出錯的是適用範圍。

如果處理的是 umbrella decision，也就是總括多個決策的規格，應該對齊它連結的 index.md。子 spec 不帶狀態，也不參與這種對齊。

另外，這套規則只適用於連結到可建置 scope feature 的 spec。standalone 的決策 spec，例如基礎架構或跨領域標準，沒有連結到特定 feature，因此走的是決策生命週期：建立時是 Proposed，獲得追認後是 Accepted。它不會鏡射 feature 的 scope 狀態，也不應因為沒有連結 feature，就被列入 STALE_SPECS。

一次狀態對齊，實際要做什麼

對每一份確實連結到 feature 的 spec，/sync 依序做幾件事：

  1. 找出這份 spec 所治理的 feature。
  2. 讀取該 feature 目前的 scope 狀態。
  3. 依照固定對應表推導 spec 的目標狀態。
  4. 寫入前再讀一次 spec，確認隊友或另一個 session 沒有剛好改過。
  5. 如果現有狀態已經等於目標狀態，就不做任何事。
  6. 如果不同，只修改一次單行的 Status，並記錄到 SPEC_STATUS_RECONCILED。

最後再讀一次，看起來像多一個步驟，實際上是在避免把別人的新修改蓋掉。已經正確的狀態不重寫，則是 idempotent：同一個同步動作跑第二次，不會因為「重跑」而產生新的變更。

這裡有一條保命規則：不要猜。只要出現以下情況，就不要修改 spec：

  • 無法確定它只連到一個 feature。
  • spec 與 feature 的對應不清楚。
  • 目前狀態已經是 Superseded。
  • 你無法解釋為什麼要把狀態降級。

這些案例應該記錄到 STALE_SPECS，而不是硬寫一個看似合理的狀態。

標記 stale：要有具體違反，不能只靠懷疑

/sync 不會修改 spec 的內容。它只會判斷：這次變更是否明確違反了某份 spec 的決定。

標記 stale 的門檻要很高。你必須能清楚指出：「這次改動違反了哪一個具體決定。」例如：

  • spec 規定只能使用某一種資料庫，但這次改動為另一種資料庫新增 adapter。
  • spec 固定了某個介面或邊界，但這次改動直接把該介面或邊界打破。

另一種需要標記的情況，是某份 spec 已經被後來的 spec 取代。這時它的狀態應該是 Superseded；不過，設定這個狀態是 /architect 的工作，不是 /sync 進行一般 Status 對齊時可以自行做的事。

相反地，「這份 spec 可能受到影響」不夠具體，不能算命中。有疑慮時就不標。否則 stale 清單很快會變成一張「也許有問題」的願望清單，久了大家就不再相信它。

為了避免浪費 context，/sync 讀 spec 也要節制：先從標題與開頭幾行判斷主題是否可能受到影響，不會一開始就把所有 spec 全部讀完。只有確認命中時，才把具體違反的決定記到 STALE_SPECS，並建議由 /architect 更新或取代它。

這裡的權限邊界很清楚：/sync 可以指出問題，但不能代替架構角色改寫 spec。

對齊 scope：universal sub task reconciler

scope 是 /sync 最特別的工作區。它被稱為 universal sub task reconciler，也就是「萬用子任務收尾者」：其他 skill 沒有勾上的子任務，最後由它根據 repo 證據補齊。

它的判斷分成兩層：

  • 這次 diff 決定要重新檢查哪些 feature。
  • repo 的實際狀態決定哪些子任務真的完成。

因此，diff 只是檢查範圍，不是完成證據。不能因為某個檔案出現在 diff 裡，就直接把對應子任務打勾。/sync 必須直接查看檔案、搜尋內容，必要時執行指令，確認實作真的存在。

依證據表判斷子任務是否完成

不同子任務需要不同證據。不能拿「有一個相關檔案」去代替所有類型的驗證。

子任務類型可以打勾的證據
UI／資料模型／後端／整合／資料整合feature 的程式區中存在對應檔案，例如元件、schema、migration、service 或 endpoint；資料整合則必須是真實查詢取代 mock
Build it（含里程碑）feature 的程式存在於正確區域，且里程碑區塊也都存在；通常由 /develop 自己打勾
Verify itspec 旁有一份 verify.md，或存在通過的 runtime 驗證紀錄
Test it測試檔涵蓋這個 feature 所在的區域
Review it（fresh model）docs/reviews/ 底下有一份針對該 feature 的 findings 檔
Document itPR 內文、CHANGELOG.md 條目或 release note 中，有涵蓋這個 feature 的內容
SEO & metadatafeature 的頁面上可以看到 metadata 或結構化資料
Sync（record conventions）該區域存在 AGENTS.md，而且內容反映這個 feature
Coding standards／toolingrepo 中存在 linter、formatter 或 pre-commit 設定

這張表的重點，是讓「打勾」變成可重現的判斷，而不是 agent 的樂觀猜測。

例如，看到測試檔不代表測試真的涵蓋該 feature；看到一個 endpoint 也不代表資料整合已經不再使用 mock。證據必須符合該子任務的類型，否則就先不打勾。

更新 feature 狀態：兩個位置要一致

完成子任務判斷後，feature 的狀態要同步更新兩個地方：

  • At-a-glance 表格。
  • feature 標題旁邊的狀態。

狀態判斷規則如下：

  • 只要 feature 仍存在未勾選的框，就維持 in-progress。
  • 檢查範圍包括 Build it、它的里程碑，以及該流程等級包含的 Verify it／Test it。
  • 只有所有應有的框都已勾選，才能設成 done。

這裡有一個特別重要的防錯規則：永不降級已經被工程師標成 done 的 feature。

即使工程師選擇跳過某一步，也應該誠實記錄為「跳過」，而不是因為那個框沒有勾，就把整個 feature 重新開成 in-progress。否則同步工具會把原本已完成的工作倒退，讓狀態失去可信度。

三條不能越過的界線

1. 只能改狀態

/sync 永遠不能新增、刪除、改名或重排 feature 與 checkbox。這些是 /scope 的責任。

existing 與 dropped 的 feature 直接跳過。如果 repo 裡出現一段已上線、卻明顯不屬於任何 feature 的程式碼，/sync 只能記下：

unmapped：某區域，建議跑 /scope 把這個計畫外的工作納入

它不能自行發明一個 feature，否則同步工具就從「對齊現況」變成「偷偷修改計畫」。

2. 歸屬必須明確

只有在檔案與 feature 的對應毫無疑問時，才能打勾。

在 monorepo 中，變更檔案所在的 workspace 決定要更新哪一份 scope。不能因為名稱相似，就在錯的 workspace 打勾。

如果同一個區域同時可能屬於多個 feature，/sync 不猜。它應該記錄 ambiguous，等待更明確的歸屬。

3. 保守，而且必須冪等

已經打勾的框維持打勾。同一個同步動作重跑，應該不產生任何新變更。

證據不清楚時，框就留著不打。這個選擇看起來保守，卻比假裝完成安全得多：錯誤的打勾會把後續決策帶偏，未打勾則會提醒下一個人繼續確認。

符合條件時才提議 commit

如果 root AGENTS.md 的 ## Git 段落寫著 integration: on，而且 commit 不是 manual，/sync 會提議用一行訊息建立這次對齊的 commit，例如：

chore(sync): reconcile docs

這個提議還要附上 Co-Authored-By 標記。但無論設定如何，/sync 都永遠不會 push。

小結：同步不是整理，而是用證據對齊狀態

spec 的 Status 是 feature 建置週期的鏡子：planned 對應 Proposed、in-progress 對應 In Progress、done 對應 Accepted；Superseded 從不由一般同步自動設定。

只有連結到可建置 feature 的 spec 才參與對齊，standalone 決策 spec 維持原樣。寫入前要重新讀取，遇到模糊對應就不要猜，而是 flag。

標記 stale 必須有具體證據，能指名是哪個決定被違反；spec 內容則完全不由 /sync 編輯。

在 scope 方面，/sync 是萬用子任務收尾者，依照證據表逐項檢查並推進 feature 狀態，但永不降級已完成的 feature，也不能新增、刪除或重排任何 feature。
