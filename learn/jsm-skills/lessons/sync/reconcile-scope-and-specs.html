對齊 scope 與 spec：打勾、改狀態、標過期

Step 5/6 · /sync：把知識對回 repo

學習目標

能用 scope 狀態對應規則只改 spec 的 Status 行、嚴格判斷何時該把 spec 標為 stale，並以「universal sub task reconciler」身分依證據表把 feature 的子任務打勾與推進狀態，且守住只能改狀態、不增刪 feature 的界線。

前言：那個「差最後一哩」的錯覺

有一個功能其實早就做完了：程式碼在、測試也在、PR 也合併了。但你翻開 scope，發現上面那格還是空的，狀態還停在 in-progress。對照它的 spec，狀態也還寫著 Proposed。單看文件，你會以為這個功能才剛起步；只有真的去翻 repo，才知道它早就完成了。

問題在於，每個 skill 都只顧自己那一格。/develop 會打勾它自己的子任務，但 /test、/audit、/sync 這些子任務沒有人負責收尾。於是 scope 上有幾格永遠空著，spec 的狀態永遠慢半拍。這一節就來看 /sync 怎麼補上這道落差，以及它在補的時候如何不越界。

先講 spec 的狀態對應

一份 spec 的狀態，是它對應 feature 的建置生命週期的鏡子。所以對應關係是固定的：

spec 的 Status意義對應的 scope 狀態
Proposed還沒開始建planned
In Progress正在建in-progress
Accepted建好且驗證過；功能沒上線前不算 Accepteddone
Superseded被後來的 spec 取代不從 scope 狀態設定，改 flag

規則看起來簡單，但有幾個容易踩的坑。第一，如果處理的是 umbrella decision（一個總括性的決策），要對齊的是它連結的 index.md，因為子 spec 不帶狀態、也不做對齊。第二，這個動作只適用於連結到可建置 scope feature 的 spec。一份 standalone 的決策 spec（例如基礎架構或跨領域標準，沒有連結 feature）走的是決策狀態：寫下時是 Proposed，被追認後是 Accepted，它不鏡射 feature 狀態。這種 spec 沒有連結 feature 是正常的，不該因此被列進 STALE_SPECS。

對每一份真的有連結 feature 的 spec，它的流程是：找出這份 spec 治理的 feature，讀出該 feature 當前的 scope 狀態，推導出目標狀態，然後在寫入前再讀一次 spec（因為隊友或另一個 session 可能剛剛改過）。如果那一行已經等於目標，就什麼都不做，這就是 idempotent。否則只做一次單行編輯，並記錄在 SPEC_STATUS_RECONCILED。這裡有一條保命規則：不要猜。如果關聯模糊（無法確定只連到一個 feature、對應不清楚、狀態已經是 Superseded、或是一個你解釋不了的降級），就不要改，把它記到 STALE_SPECS。

標過期：證據要具體，態度要嚴格

spec 的內容本身，/sync 一個字都不改。但如果這次改動跟某份 spec 的決定互相矛盾，它必須把這件事標出來。這裡的紀律是「嚴格」，因為誤報會侵蝕信任。它只有在能指名道姓說出「這次改動違反了哪一個具體決定」時才會標，例如某份 spec 規定只能用一種資料庫，而這次卻為另一種加了 adapter；或是某份 spec 固定了一個介面或邊界，而這次改動把它打破了。還有一種情況也會標：某份 spec 被後來的 spec 取代了，它的狀態應該變成 Superseded，而設定這個狀態是 /architect 的工作，不是這裡的 Status 行對齊。

它絕不標那種「可能受影響」的模糊情況。有疑慮時就不標。而且它讀 spec 也很節制：只從標題與開頭幾行判斷這份 spec 的主題有沒有可能被動到，不會盲目地全部讀一遍。真正的命中會記在 STALE_SPECS，附上被違反的點，並建議 /architect 去更新或取代它。內容的任何編輯，都不在它的權限內。

對齊 scope：你才是那個「萬用子任務收尾者」

scope 這一段是 /sync 角色最特別的地方。它被稱為 universal sub task reconciler，意思是：所有其他 skill 沒有打勾的子任務，最後都由它來收。它的做法是，對這次 diff 碰到的每一個 feature，重新評估它的每一個子任務，然後把真正完成的打勾。注意這裡的措辭：diff 決定「要重新檢查哪些 feature」，但 repo 的實際狀態決定「哪些子任務真的做完了」。所以它會直接去看檔案、跑指令、搜尋，而不是只看這次 diff 加了什麼。

判斷完成靠的是一張證據表，不同類型的子任務有不同的證據：

子任務類型可打勾的證據
UI／資料模型／後端／整合／資料整合feature 的程式區裡對應的檔案存在（元件、schema 或 migration、service 或 endpoint、真實查詢取代了 mock）
Build it（含里程碑）feature 的程式存在於它的區域，里程碑的區塊也都在；通常 /develop 自己會打勾
Verify itspec 旁邊有一份 verify.md，或有通過的 runtime 驗證紀錄
Test it測試檔涵蓋了這個 feature 的區域
Review it（fresh model）docs/reviews/ 底下有一份針對這個 feature 的 findings 檔
Document it有一段涵蓋這個 feature 的 PR 內文、CHANGELOG.md 條目或 release note
SEO & metadatafeature 的頁面上看得到 metadata 或結構化資料
Sync（record conventions）該區域的 AGENTS.md 存在，而且反映了這個 feature
Coding standards／toolingrepo 裡有 linter、formatter 或 pre-commit 設定

打完勾之後，它會更新 feature 的狀態，而且是兩個地方一起改：At-a-glance 表格裡，以及 feature 標題旁邊。原則是：只要這個 feature 真的有、而且還沒打勾的框（Build it 加它的里程碑，加上該流程等級包含的 Verify it／Test it）還有剩，就維持 in-progress；等它所有的框都打勾了，才設成 done。有一件絕對不能做的事：永不降級一個工程師已經標成 done 的 feature。就算工程師選擇跳過某一步，那也只是被誠實記錄為「跳過」，不是重開它的理由。

它的三個界線

scope 的處理有三條不能越過的線。第一，只能改狀態：永遠不新增、刪除、改名或重排 feature 與 checkbox，那是 /scope 的工作；existing 與 dropped 的 feature 直接跳過。如果發現有已上線的程式碼明顯不屬於任何 feature，它只會記一句「unmapped：某區域，建議跑 /scope 把這個計畫外的工作納入」，而不是自己發明一個 feature。第二，歸屬要明確：只有在「檔案對到 feature」的對應毫無疑問時才打勾。在 monorepo 裡，變更檔的 workspace 決定要更新哪一份 scope，絕不會在錯的 workspace 打勾；如果一個區域同時對到多個 feature，它不猜，記一句 ambiguous 就好。第三，這是保守、冪等的：已經打勾的框維持打勾，同一件事重跑不會有任何變動；證據不明確時就留著不打。

如果 root AGENTS.md 的 ## Git 段落寫著 integration: on，而且 commit 不是 manual，它還會提議用一行訊息（例如 chore(sync): reconcile docs）加上 Co-Authored-By 標記，把這次的對齊 commit 起來。但它永遠不 push。

小結

spec 的 Status 是 feature 建置週期的鏡子：planned→Proposed、in-progress→In Progress、done→Accepted，而 Superseded 從不自動設定。只有連結到可建置 feature 的 spec 才對齊，standalone 決策 spec 維持原樣；寫入前要重讀、不能猜，模糊就 flag。標 stale 要嚴格，只有能指名被違反的具體決定才標，內容絕不編輯。scope 方面，/sync 是萬用子任務收尾者，依證據表對每條子任務打勾並推進 feature 狀態，但永不降級已完成的 feature，也不能新增、刪除或重排任何 feature。
