把 AGENTS.md 對回 repo：只補必要的一行

Step 4/6 · /sync：把知識同步回 repo

學習目標

這一節要學會依照 surgical、additive/corrective、durable 三個條件，判斷現有 AGENTS.md 到底該不該改；正確處理 Stack 與 Build approach 這兩個鏡射欄位；記錄 Skill、MCP 與 design system 指標；只在真正全新的區域建立 nested 文件；最後清理刪除檔案留下的孤兒與斷鏈。

前言：最難修的，往往是「九成正確」的文件

假設一份 AGENTS.md 大多數內容都還正確，只有一行 build 指令已經過期。整份重寫太粗暴，可能把仍然有用的知識一起洗掉；完全不處理，下一個照著做的人又會踩到同一個坑。

這時需要的不是大掃除，而是像外科手術一樣，只動那一行，其他文字一個字也不碰。

這套規則寫在 agent-prompt.md，是 /sync 動筆階段的權威依據。接下來會先看它如何修正既有的 AGENTS.md，再看什麼情況可以新建 nested 文件，以及刪除發生後要怎麼收尾。

大前提：預設什麼都不做

/sync 的底色是 default to doing nothing。只有在程式碼變更影響指令、慣例、約束、依賴或檔案結構時，才可能形成值得長期保存的知識。

如果內容只是描述「這次做了什麼」，那比較像變更流水帳，而不是維護文件。這類 churn 只會增加雜訊。因此，/sync 跑完後完全沒有修改，並不是失敗，而是很正常、甚至很理想的結果。

改既有文件：三個條件缺一不可

它會讀取 diff，逐一檢查受影響的 root 或 nested AGENTS.md。檢查的重點包括：

  • 建置、測試或執行指令是否改變。
  • 慣例或約束是否改變。
  • 依賴是否更換。
  • 某個檔案指標是否指向不存在的位置。
  • 是否新增一條屬於這份文件的長期規則。

一筆編輯必須同時符合以下三個條件，才可以動手：

條件意思
Surgical（外科手術式）只修改或新增特定幾行，不能整段重寫。
Additive or corrective（增補或修正）補上缺少的事實，或修正錯誤的事實；不能刪除自己尚未完全理解的珍藏指引。
Durable（長期有效）這項事實必須能超越這一次變更持續有用；一次性備註、歷史或功能摘要都跳過。

最容易被忽略的是 durable。把「這次做了什麼」順手塞進 AGENTS.md，短期看似完整，長期卻會讓文件變成流水帳。下一個讀者需要的是穩定的做法與規則，不是某次變更的紀錄。

兩個鏡射欄位：Stack 與 Build approach

root AGENTS.md 裡有兩個欄位，各自都有外部的唯一真相來源。任何 skill 都不能自行猜測或捏造值：

  • ## Stack：鏡射架構 spec，也就是 docs/specs/ 底下含有 ## Proposed stack 章節的規格。
  • ## Build approach：鏡射 scope 標頭中的 build approach 那一行，也就是 /scope 記錄的值。

/sync 對這兩個欄位採用「一次只對一行」的做法，而且只在兩種情況下修改：

  • 欄位缺少來源設定的值時，精準補上那一行。例如綠色專案的 root 先建立了，但架構 spec 尚未出現；或 root 缺少 build approach 行，而 scope 標頭已經有值。
  • 欄位與來源互相矛盾、root 內的版本是被精心擴寫過的散文，或無法判斷哪一邊才是權威時，不覆寫，而是記為 CONFLICTS，並指出正在比對的 spec 或 scope。

它不會重整或建立 root AGENTS.md。那是 /audit 的工作。

把 Skill 與 MCP 記錄放到正確位置

如果上一節帶回來的三個欄位不是 none，這一節就要把它們寫進最相關的 AGENTS.md。位置取決於影響範圍：

  • 專案層級的工具，例如框架、ORM、樣式、核心資料庫、hosting、測試 runner，放在 root。
  • 區域層級的工具，例如金流、認證、email、上傳、搜尋、佇列，放在該區域的 nested 文件。

如果這個區域還沒有 nested 文件，先在 root 加一條短註記，並把該區域記到 CONTEXT_GAPS。

已安裝的 skill 會在 ## Agent skills 區塊中各佔一行，格式固定：

- [<skill>](<skills-dir>/<skill>/): `<owner>/<repo>`, <what it covers>

這裡有兩個重要細節。第一，使用專案實際採用的 skills 目錄，而不是寫死 Claude 專屬路徑，因為不同工具都會讀這份文件。第二，保留 registry 的 <owner>/<repo>，讓它成為跨工具一致的身分識別。

如果文件還沒有 ## Agent skills，就建立一個，位置放在接近結尾、## Context files 之前。

被拒絕的工具，以及已連線或推薦的 MCP，沒有需要載入的內容，因此維持一行即可：

Declined: <tool>
MCP servers: <server> (connected|recommended)

design system 只加指標，不複製內容

如果這次變更新增或確立了 design.md，而最近的 AGENTS.md 還沒有指向它的指標，就補上一行：所有 UI build 都必須遵循 design.md，token 值放在 CSS。

這裡的原則是「指標，不是複製品」。/sync 不會把 design.md 的內容整段貼進 AGENTS.md，避免同一份知識出現兩個版本，日後互相漂移。

三條不能破的規則

修改既有文件時，有三條硬規則：

  1. Idempotent（冪等）：動筆前重新讀取目標文件。如果相同事實、指令或指標已經存在，即使措辭不同，也不再補一次。同一份變更執行第二次，必須產生零筆新編輯。
  2. 不覆寫或重寫珍藏散文：如果要達到準確就必須改寫作者精心整理的一段內容，改記到 CONFLICTS，交給人處理。
  3. root 保持簡短、全專案相關：區域專屬的細節留在 nested 文件，不要把 root 變成所有事情的垃圾場。

新建 nested 文件：只給真正全新的區域

建立 nested 文件時，判斷依據是 diff 提供的 context，而不是 policy。只有當某個區域底下的每一個 source 檔，在這次變更中都是 A（新增）狀態，才代表整個區域是 net-new，具備足夠上下文可以寫出好文件。

只要其中有一個檔案是 M（修改），就表示這個區域早已存在，不能因此建立新的 nested 文件。

新文件只寫必要內容：

  • 本地檔案指標。
  • 本地指令。
  • 新程式碼中可觀察到的慣例與約束。
  • 指向治理這個區域的 spec 連結。

文件結尾固定加入：

_Drafted by /sync from the introducing change, worth a quick human pass._

接著在 root 的 ## Context files 底下加入恰好一行指標：

- [<area>/AGENTS.md](<area>/AGENTS.md): <one-line description>

如果 root 還沒有 ## Context files，就建立這個標題，再放入指標。最後，在同一個資料夾建立 CLAUDE.md 指標，讓 Claude Code 也能找到這個新區域。

反過來，若只是既有區域被 diff 切到一角，無法取得完整上下文，就把它記到 CONTEXT_GAPS，建議執行 /audit。/sync 永遠不會建立或重整 root；如果 repo 根本沒有 root AGENTS.md，同樣交給 /audit。

真正獨立的新區域只需要一份 nested 文件，不是每個資料夾都各放一份。

孤兒清理：刪除後要把斷掉的線收好

對每一個 D 清單中的路徑，/sync 會檢查 nested AGENTS.md 描述的內容是否仍然存在。

  • 如果整個區域的目錄都被刪除，才移除對應的 nested 文件。
  • 如果只是部分檔案消失，保留文件，只修正其中已斷掉的檔案指標。
  • 移除 nested 文件時，同時刪掉 root 中對應的那一行指標。
  • 任何 AGENTS.md 指向已刪除或已搬移路徑的指標，都要一併修正。

這些處理結果記在 ORPHANS_CLEANED。如果無法確定某個刪除是不是永久性的，就記到 CONFLICTS，不能自行判斷後直接刪除。

小結：只保存真正會留下來的知識

AGENTS.md 的維護原則是「預設什麼都不做」，只記錄真正長期有效的知識。修改既有文件時，必須同時符合 surgical、additive/corrective、durable。Stack 與 Build approach 各有唯一來源：缺少時補上，衝突時標記而不覆寫。Skill、MCP 與 design system 指標要放在正確層級；design system 只保留指標，不複製內容。

三條硬規則是：保持 idempotent、不覆寫珍藏散文、讓 root 維持簡短。新建 nested 文件只限整個區域都是新增的 net-new 情況；舊區域交給 /audit。刪除後則要清理孤兒文件與斷掉的指標。

處理完 AGENTS.md，還有另一類知識載體要同步：scope 與 spec。下一節會看它如何打勾、如何更新那一行狀態，以及如何判斷一份規格是否該被標成過期。
