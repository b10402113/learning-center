把 AGENTS.md 對回 repo：只加必要的一行

Step 4/6 · /sync：把知識對回 repo

學習目標

能依 surgical、additive/corrective、durable 三條件判斷該不該改現有 AGENTS.md，處理 Stack 與 Build approach 兩個鏡射欄位、Skill／MCP 記錄與 design system 指標，只對 net-new 區域新建 nested 文件，並清理刪除造成的孤兒。

前言：一份「幾乎都對」的文件，最難修

想像一份 AGENTS.md，裡面九成的內容都還準確，只有一行建置指令過期了。這種文件最麻煩：重寫它太粗暴，會把一堆還有效的珍藏知識一起洗掉；放著不管，下一個照著做的人又會踩雷。真正需要的，是精準地只改那一行，其他一個字都不動。

接下來就看這門「外科手術」怎麼動刀。它藏在 agent-prompt.md 裡，是 /sync 動筆階段的權威規則。我們先看它怎麼改既有的 AGENTS.md，再看它什麼時候有資格新建一份，以及刪除發生時怎麼收拾。

大前提：預設什麼都不做

動筆之前，先記住這個技能的底色：default to doing nothing。一段程式碼只要沒有改動到指令、慣例、約束、依賴或檔案結構，就不屬於長期知識，不需要寫進文件。一條只是「敘述這次做了什麼」的說明，是 churn，是雜訊，不是維護。所以在 /sync 的世界裡，「這次跑完什麼都沒改」是一個正常、而且很好的結果。

改既有文件：三個條件都要滿足

它會讀 diff，對每個被碰到的 root 或 nested AGENTS.md 檢查：這次改動有沒有動到建置、測試、執行的指令？有沒有改掉一個慣例或約束？有沒有換掉一個依賴？有沒有讓某個檔案指標指向不存在的位置？有沒有新增一條屬於這份文件的長期規則？

只有當一筆編輯同時滿足這三個條件，它才會動手：

條件意思
Surgical（外科手術式）改或加特定幾行，絕不重寫整個段落
Additive or corrective（增補或修正）補一個缺的事實，或修一個錯的事實；絕不刪掉自己沒完全理解的珍藏指引
Durable（長期有效）這個事實要能超越這一次改動；一次性的備註、歷史、功能摘要都跳過

第三個條件特別容易被忽略。很多人會想順手把「這次做了什麼」寫進文件，但那對下一個讀者沒有長期價值，只會讓文件愈來愈像流水帳。

兩個鏡射欄位：Stack 與 Build approach

root AGENTS.md 裡有兩個欄位比較特別，它們各自在外面有一個「唯一真相來源」，任何 skill 都不能自己掰一個值出來：

  • ## Stack 鏡射架構 spec，也就是 docs/specs/ 底下那份帶有 ## Proposed stack 章節的規格。
  • ## Build approach 鏡射 scope 標頭裡的 build approach 那一行，也就是 /scope 記錄下來的值。

/sync 對這兩個欄位的處理是「一次對一行」，而且只有兩種情況會出手：當欄位缺少它來源設定的值（例如一個綠色專案的 root 在架構 spec 出現前就先被生出來，或 root 沒有 build approach 行而 scope 標頭有），它就精準地補上那一行；當欄位和來源互相矛盾，或 root 的版本是被精心擴寫過的散文，或你根本判斷不出哪邊權威，它就不覆寫，而是把它記為 CONFLICTS，並指出你比對的是哪一份 spec 或 scope。它永遠不會重整或建立 root，那是 /audit 的工作。

把 Skill 與 MCP 記錄寫進對的地方

還記得上一節帶回來的三個欄位嗎？如果它們不是 none，這裡就要寫進最相關的 AGENTS.md。寫哪裡有講究：專案層級的工具（框架、ORM、樣式、核心資料庫、hosting、測試 runner）放 root；區域層級的工具（金流、認證、email、上傳、搜尋、佇列）放該區域的 nested 文件，如果那個區域還沒有 nested 文件，就先在 root 放一條短註記，並把這個區域記到 CONTEXT_GAPS 裡。

已安裝的 skill 會在 ## Agent skills 區塊裡各佔一行，格式固定：- [<skill>](<skills-dir>/<skill>/): `<owner>/<repo>`, <what it covers>。這裡有兩個細節：它用專案真正使用的 skills 目錄，而不是寫死 Claude 專屬的路徑，因為每個工具都會讀這份檔案；它保留 registry 的 <owner>/<repo> 當作跨工具的身分識別。如果文件裡還沒有 ## Agent skills 區塊，它會建立一個，並放在接近結尾、## Context files 之前。至於被拒絕的工具與已連線或推薦的 MCP，因為它們沒有東西要載入，就維持精簡的一行：Declined: <tool>、MCP servers: <server> (connected|recommended)。

另外，如果這次改動新增或確立了一份 design.md（UI 的設計系統），而最近的 AGENTS.md 還沒有指向它的指標，它會補上精準的一行：build 所有 UI 都要照 design.md，token 值放在 CSS。原則是：指標，不是複製品。它絕不把 design.md 的內容貼進 AGENTS.md。

三條不准破的規則

在改既有文件時，有三條規則是硬的。第一，idempotent（冪等）：動筆前再讀一次目標文件，如果這個事實、指令或指標已經在了，即使措辭不同，也不再加一次。同一份變更跑第二次，必須是零新編輯。第二，絕不覆寫或重寫珍藏的散文：如果要求準確就得重寫作者精心寫的一段，那就把它記到 CONFLICTS 留給人。第三，root 保持簡短、全專案相關：區域專屬的細節留給 nested 文件。

新建 nested 文件：只有全新區域才准

然後是「建立」的時機。判斷標準一樣是 context，不是 policy：只有當某個區域底下的每一個 source 檔，在這次變更裡都是 A（新增）狀態時，diff 才等於把整個區域攤在你面前，你才有足夠的上下文寫一份好文件。只要其中有一個檔是 M（修改），就代表這個區域早就存在，你不准建立。

新建的文件內容要聚焦：本地的檔案指標、本地指令、新程式碼裡看得見的慣例與約束、以及指向治理它的 spec 的連結。結尾固定加一行：_Drafted by /sync from the introducing change, worth a quick human pass._（由 /sync 從導入這次改動的 diff 草擬，值得人快速看過一遍）。然後在 root 的 ## Context files 底下加恰好一行指標，格式是 - [<area>/AGENTS.md](<area>/AGENTS.md): <one-line description>。如果 root 還沒有 ## Context files 這個標題，就建立它，再放進指標。最後，它還會建立同資料夾的 CLAUDE.md 指標，讓 Claude Code 也接得到這個新區域。

反過來，如果是早就存在、只是被 diff 切到一角的不成文區域，它會把這個區域記到 CONTEXT_GAPS，建議你跑 /audit。而且它永遠不會建立或重整 root，如果 repo 根本沒有 root AGENTS.md，那也是 /audit 的事。一個真正獨立的新區域寫一份 nested 文件就好，不是每個資料夾都來一份。

孤兒清理：刪除之後的收尾

最後一塊是刪除。對每一個 D 清單裡的路徑，它會檢查：有沒有 nested AGENTS.md 描述的東西已經不存在了？只有在整個區域的目錄都被刪掉時，它才會把那份文件整個移除；如果只是部分檔案消失，它就修正文件裡那些已經斷掉的檔案指標就好。移除一份 nested 文件時，root 裡對應的那行指標也要一起拿掉。任何 AGENTS.md 裡指向已刪除或已搬移路徑的指標，都要修好。這些動作記在 ORPHANS_CLEANED 裡。如果它不確定某個刪除是不是永久性的，就記到 CONFLICTS，而不是自己決定刪掉。

小結

AGENTS.md 的維護底色是「預設什麼都不做」，只改真正的長期知識。改既有文件要同時滿足 surgical、additive/corrective、durable；Stack 與 Build approach 兩個鏡射欄位各有唯一來源，缺就補、矛盾就 flag 不覆寫；Skill／MCP 記錄按專案層級或區域層級放對位置，design system 只加指標。三條硬規則是不准破的：idempotent、不覆寫珍藏散文、root 保持簡短。新建 nested 文件只限「整個區域都是新增」的 net-new 情況，舊區域 defer 給 /audit；刪除後要清理孤兒文件與斷掉的指標。

處理完 AGENTS.md，另一類知識載體還在等你：scope 與 spec。下一節要看它怎麼打勾、怎麼改那一行狀態、又怎麼判斷一份規格「該被標成過期」。
