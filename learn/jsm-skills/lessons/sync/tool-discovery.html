新工具要不要找 Skill 與 MCP：先問，再做

Step 3/6 · /sync：把知識對回 repo

學習目標

完成這一節後，你應該能說清楚三件事：Step 2.5 為什麼只在新增大型工具時觸發、TOOL-CONSENT 為什麼遵守「問是義務，搜尋不是」，以及探索工作為什麼要交給唯讀子代理，再只把精簡的候選清單帶回主線。

前言：你裝了 Stripe，agent 卻還照著三年前的舊寫法

假設這次改動替專案接上金流，你已經在依賴清單裡加入 Stripe。程式碼也許很快就能寫出來，但金流欄位一旦用錯，問題可能不是畫面顯示不漂亮，而是交易流程真的出錯。

這時，agent 對 Stripe 的理解是否跟得上目前的慣例，就很重要。如果有現成的 Agent Skill 能提供 Stripe 的實務寫法，agent 就不必只依賴可能過時的訓練資料。

這正是 /sync 的 Step 2.5 要處理的岔路：當這次變更新增了「重量級的外部工具」，它會主動問你要不要探索相關的 Agent Skill 與 MCP。但它不會先斬後奏，而是先徵求同意。這套「問是義務，搜尋不是」的設計，值得拆開來看。

什麼時候會觸發：只在新增大型工具時

Step 2.5 不是每次執行 /sync 都會跑。只有在依賴清單被修改，或 diff 明顯新增了重要的外部工具時，它才會啟動。

它刻意不處理一般工具函式庫，因為這類套件通常沒有值得另外探索的長期工作流或系統整合。它關心的是會改變專案工作方式的工具，例如：

  • 框架、router、樣式或 UI kit
  • 資料庫、ORM 或查詢層
  • 認證與 session
  • 金流、email 與通知
  • 儲存與上傳、搜尋
  • 佇列與背景工作
  • AI provider 與向量資料庫
  • 瀏覽器或 runtime 測試
  • observability、hosting 與部署

它會從 manifest 的差異裡找出這些新面孔，也會把套件名稱和常見別名一起納入判斷；搜尋不會只試第一個技術名稱就停下來。

找到候選後，還要先清掉已經處理過的項目。已安裝的 skill、已連上的 MCP，以及 AGENTS.md 裡已記錄為「拒絕」的工具，都不會被重複拿出來詢問。

核心規則：問是義務，搜尋不是

這一步不會直接替你上網搜尋。它會先停下來，把選擇權交給你，而且界線非常清楚：

提問是強制的，搜尋不是。 在你做出選擇之前，不會搜尋、抓取、安裝或啟動任何東西。它會提供四個選項：「幫我找」、「我自己指名」、「不用並記錄拒絕」、「之後再說」。只有第一個選項可以啟動搜尋指令；它不會靜默跳過詢問，也不會在你同意前先搜尋一次。

這就是 TOOL-CONSENT 的重點：同意不是搜尋完成後才補做的確認，而是搜尋開始前的必要閘門。這能避免 agent 因為「看起來有幫助」就擅自替你探索、安裝或連線。

TOOL-CONSENT 不只存在於 /sync，/architect 與 /audit 也各自保留完全相同的區塊，並註記：「要改就三份一起改，否則都別改。」

這種重複是刻意的。每個 skill 都必須能獨立散布與安裝，因此不能假設使用者一定會同時取得某個共用檔案。這是 repo 裡少數「明知重複，也要保留」的例外。

詢問本身也有固定形狀。它會先列出這次新增的工具，接著用一句話分清楚兩種載體：

  • Agent Skill：提供這個工具的真實慣例。
  • MCP server：提供對真實系統的即時存取。

然後它會問：「要不要幫你找這些工具的 Agent Skill 與 MCP server？」選項是「是，幫我找」（標為推薦）、「我自己指名要哪些」、「不用，跳過」、「之後再說」。只有選擇「是」時，流程才會繼續搜尋。

為什麼探索要交給唯讀子代理

即使你選了「幫我找」，主線也不會親自把搜尋結果全部吞進來。它會把工具清單交給一個唯讀的探索子代理。

這個子代理會使用明確、便宜且快速的模型層級，不會繼承你當下使用的模型；它的任務也被限制得很窄：只回傳一份精簡的候選清單。

原因在於搜尋結果很容易把 context 撐大。網頁搜尋帶回的是大量原始內容，如果全部塞進 /sync 的主線，真正重要的 repo 脈絡就會被雜訊稀釋，context 像一張被塞滿便條紙的桌子，最後反而找不到手邊真正要用的那張。

把探索隔離出去後，主線只需要接收「哪些 skill 值得考慮」這幾行結論。探索代理不能修改專案，也不能替你安裝或連線，因而能把搜尋工作和實際決策分開。

如果當下的 agent 不支援子代理，流程才會退回主線搜尋；如果連搜尋能力都沒有，就跳過探索並把這個結果記錄下來。

搜尋也有預算：有上限，還有快取

一旦開始搜尋，流程仍然受到明確的預算限制：最多五次網頁搜尋、最多八個頁面，並優先查看官方 registry 與官方文件。

搜尋指令是：

npx skills find <tool-or-package>

如果結果太弱，可以改用套件名稱或組織名稱的別名再試一次。MCP 的搜尋則是選配，不是完成這一步的必要條件。

搜尋結果會快取在 docs/.agent-cache/tool-discovery/<slug>.md。三十天內再次遇到同一個工具時，流程可以重用快取，不必每次都重新上網查。

不過，快取不是永久通行證。正式啟用前，流程仍會再過濾一次已安裝和已拒絕的項目，避免舊結果讓已處理的工具重新出現在選單裡。

最後決定權：多選面板，而且絕不自動安裝

搜尋結束後，找到的 Agent Skill 會依技術分組，集中放進多選面板，詢問你要安裝哪些，也提供跳過與拒絕的選項。

MCP 會使用另一個面板單獨詢問。這裡有一條不能模糊處理的鐵則：永遠不會自動安裝，也不會自動連線。

你選定的 skill 會使用以下指令安裝：

npx skills add <owner>/<repo> -y

至於 MCP，流程會引導你到自己的 connector 或 MCP 設定中完成連線。連線完成後，工具才會自動被使用。

最後，流程會整理三個欄位，帶到後續的寫入階段：

  • 這次安裝了哪些 skill
  • 哪些 MCP 被選中或推薦
  • 哪些工具被拒絕或跳過

這些欄位之後會記進對應的 AGENTS.md。如果什麼都沒找到，或環境根本沒有搜尋能力，就統一記為 none。

小結

Step 2.5 只在新增大型工具時觸發。它會從 manifest 差異中辨識框架、資料庫、金流等重量級依賴，再排除已由 skill、MCP 或拒絕清單處理過的項目。核心規則是 TOOL-CONSENT：提問是義務，搜尋不是。四個選項中，只有「幫我找」能啟動搜尋，而且流程絕不靜默跳過詢問，也不會先搜後問。搜尋會隔離到便宜、唯讀的子代理，最後只回傳精簡候選，並遵守最多 5 次搜尋、8 個頁面與三十天快取的限制。決定權始終在你手上；流程不會自動安裝 skill，也不會自動連線 MCP。結果則以三個欄位帶進寫入階段。

到這裡，變更範圍已經圈好，新工具也已經完成詢問與選擇。下一步就是把結果對回 repo，真正動筆寫入知識。這個寫入分成兩大類載體，首先處理 AGENTS.md；下一節會看它如何做到「只加必要的一行」。
