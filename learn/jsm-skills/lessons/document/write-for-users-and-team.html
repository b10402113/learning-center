寫給不看碼的人：release note 與 postmortem

Step 5/5 · /document：把變更寫成人話

學習目標

能把技術變更翻成使用者看得懂、不埋 breaking changes 的 release note，並寫出時間軸與根因分離的 blameless postmortem。

前言：這兩種讀者，連 diff 都看不到

上一節處理的兩種讀者，好歹看得到碼。這一節的兩種完全看不到：一種是付錢使用你產品的人，一種是跟你一起處理事故的團隊成員。

對這兩種人來說，你的改動會被讀成兩件事，而不是一組檔案。使用者只在乎「我現在能多做什麼、有沒有東西被我搞壞」；團隊只在乎「這次到底發生了什麼、下次要怎麼讓它不再發生」。把 PR 描述直接貼給使用者看，就像把引擎維修單貼在展示間裡：資訊不缺，但根本不是對方要的。這一節要練的就是這種「翻譯」與「事後敘事」的能力。

release note：把技術翻成使用者能做的事

release note 寫到 docs/releases/<version>.md，對象是終端使用者。核心原則是：把技術變更翻譯成使用者現在能做的事，並把他們最在乎的放最前面。 這是四種文件裡最精緻、也最不技術的一份；它的成功標準是「使用者讀得懂，並且知道這跟自己有什麼關係」。

它的結構長這樣：

# <產品> <版本>

_Released <日期>_

<一到兩句總結這個版本的主題，一句使用者會記住的重點。>

## Highlights

- **<功能名稱>**：<一句話說明它對使用者的價值。>

## Improvements

- <較小的增強，用使用者的語言寫。>

## Fixes

- <修正的問題，寫成使用者經歷的樣子，例如「修正了一個……的問題」。>

## Breaking changes

<只有真的有才寫。清楚說明壞了什麼、誰受影響、遷移步驟。沒有就省略。>

## Upgrade notes

<要怎麼升級；若升級是自動或無感的，就省略。>

幾條規則值得反覆咀嚼。第一，先講使用者價值，再講實作。「你現在可以把報表匯出成 CSV」遠比「在匯出模組裡加了 CSV 序列化」有用。第二，依重要性排序：Highlights 在前，接著 Improvements，最後 Fixes。第三，對 breaking changes 誠實，絕不把它埋掉。 任何會讓既有使用者壞掉的改動，都要有自己一個清楚標示的段落。第四，不要用內部術語、ticket 編號或檔名，這是四種文件裡最該把這些東西拿掉的一份。最後，一切都從區間內真的 commits 與 diff 推出來，不承諾根本不存在的功能。

postmortem：一場事故，一份不指責人的報告

postmortem 寫到 docs/postmortems/<date>-<slug>.md，素材是工程師提供的事故事實，加上 diff 或 /debug 紀錄裡的根因細節。它有一個很關鍵的性質叫 blameless（不歸咎個人）：整份報告聚焦在系統與促成因素上，永遠不針對人。「這個部署缺少健康檢查」是對的說法；「某人忘了加健康檢查」是錯的。

結構分成幾個段落：

  • 標題與基本資料表：包括 Severity（SEV1 到 SEV4，或 critical 到 low）、Duration（開始到解決，含時區）、User impact（誰受影響、怎麼影響，能量化就量化）、Status（Resolved 或 Monitoring）。
  • Summary：三到五句，讓忙碌的讀者一次吸收：發生什麼、影響、根因、修法。
  • Timeline：標註時區，只放有時間戳的事實：發生或觀察到什麼、怎麼被發現、關鍵診斷或緩解、最後解決。
  • Root cause：真正的技術原因，從觸發到失敗的整條鏈。這裡有一個很重要的區分：trigger（導火線） 與 underlying weakness（底層弱點） 要分開講。導火線是「那一次按下了什麼」，底層弱點是「為什麼那一下會釀成事故」。
  • Contributing factors：讓它變得更糟、更難偵測、或更難修的東西，例如少了一個警示、沒有 timeout、擁有權不清楚。
  • What went well：快速偵測、乾淨的 rollback、好用的工具。這裡要把功勞歸給系統，而不是歸給英雄。
  • Action items：一張表，欄位是 Action、Type、Owner、Priority。每個動作都要具體且可指派，並標上 Prevent（防止再發）、Detect（更快發現）、或 Mitigate（降低衝擊）。不要出現「更小心一點」這種空話。
  • Lessons：可以長久帶走的結論。如果這裡應該長出一份規格或一個具體後續，就直接點名它。

規則同樣重要：全程 blameless；時間軸只放事實，分析留在 Root cause 與 Contributing factors；action item 要具體可指派並分類；根因若對應到某種系統失敗模式，就建議一個具體的後續動作，若有過去的決策促成它，也把那份規格記下來。真正無法確定的，寫 Unknown, to investigate，不要猜。

小結

release note 給終端使用者，寫到 docs/releases/<version>.md：先講使用者價值、依重要性排序（Highlights → Improvements → Fixes）、breaking changes 絕不埋、不用內部術語與 ticket 編號，一切從區間內的 commits 與 diff 推。postmortem 給團隊，寫到 docs/postmortems/<date>-<slug>.md：全程 blameless，時間軸只放有時間戳的事實，Root cause 要分開導火線與底層弱點，action item 具體可指派並標 Prevent / Detect / Mitigate，未知的就寫 Unknown, to investigate。

五節走完，你已經看過 /document 的全貌：它產出哪四種文件、各自面對誰、素材怎麼從 git 撈出來、四條不能破的底線，以及最不技術的兩種文件要怎麼翻譯。下一步就是把它真的跑在你的練習專案上。挑一個剛做完的功能，跑一次 /document pr，看它怎麼把你三個檔的改動，講成一段審查者讀得懂、你也敢背書的描述。
