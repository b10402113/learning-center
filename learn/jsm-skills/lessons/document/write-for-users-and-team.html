寫給不看程式碼的人：release note 與 postmortem

Step 5/5 · /document：把變更寫成人話

學習目標

這一節要學兩種「翻譯」：把技術變更寫成使用者看得懂、也不會藏起 breaking changes 的 release note；以及把事故整理成有時間軸、能找出根因，而且不把責任推給個人的 blameless postmortem。

前言：有些讀者，連 diff 都不會看

前面幾節處理的讀者，至少還看得到程式碼。這一節面對的兩種讀者完全不同：一種是付費使用產品的人，另一種是和你一起處理事故的團隊成員。

對使用者來說，改動不是一組檔案，而是「我現在多了什麼能力？原本能用的東西會不會壞掉？」對團隊來說，事故也不是一串 log，而是「到底發生了什麼？為什麼會發生？下次怎麼避免重演？」

把 PR 描述原封不動貼給使用者，就像把引擎維修單貼在展示間裡：資訊也許齊全，卻不是對方真正需要的答案。這一節要練的，就是把同一批技術事實，翻譯成不同讀者能採取行動的文字。

release note：把技術翻成使用者做得到的事

release note 寫到 docs/releases/<version>.md，讀者是終端使用者。核心原則只有一句：先說使用者現在能做什麼，再說背後改了什麼。

這是四種文件裡最精緻、也最不技術的一份。它的成功標準不是列出最多實作細節，而是讓使用者讀完就知道：「這跟我有什麼關係？」

基本結構如下：

# <產品> <版本>

_Released <日期>_

<一到兩句總結這個版本的主題，一句使用者會記住的重點。>

## Highlights

- **<功能名稱>**：<一句話說明它對使用者的價值。>

## Improvements

- <較小的增強，用使用者的語言寫。>

## Fixes

- <修正的問題，寫成使用者經歷的樣子，例如「修正了一個……的問題」。>

## Breaking changes

<只有真的有才寫。清楚說明壞了什麼、誰受影響、遷移步驟。沒有就省略。>

## Upgrade notes

<要怎麼升級；若升級是自動或無感的，就省略。>

寫作時，可以把下面幾條規則當成檢查清單。

  • 先講使用者價值，再講實作。「你現在可以把報表匯出成 CSV」比「在匯出模組裡加入 CSV 序列化」有用得多。前者直接告訴使用者能做什麼，後者只是在描述工程師做了什麼。
  • 依重要性排序。先放 Highlights，再放 Improvements，最後才是 Fixes。使用者不需要在一長串修正項目裡尋找真正重要的新能力。
  • 對 breaking changes 誠實。任何會讓既有使用者出問題的改動，都要放進清楚標示的段落，說明壞了什麼、誰會受影響，以及該怎麼遷移。不能把它藏在一般修正項目裡。
  • 拿掉內部語言。不要寫內部術語、ticket 編號或檔名。release note 是寫給產品使用者的，不是把工程團隊的工作紀錄換個標題再貼上去。
  • 只寫有證據的內容。所有內容都必須從指定區間內的 commits 與 diff 推出來，不要替產品承諾根本不存在的功能。

postmortem：描述事故，但不把人送上被告席

postmortem 寫到 docs/postmortems/<date>-<slug>.md。素材來自工程師提供的事故事實，再搭配 diff 或 /debug 紀錄中的根因細節。

它最重要的特性是 blameless（不歸咎個人）。報告應該聚焦在系統設計、流程與促成事故的條件，而不是追究哪個人犯了錯。

例如，「這個部署缺少健康檢查」是在描述系統缺口；「某人忘了加健康檢查」則把焦點推向個人。前者能帶出改善方案，後者通常只會讓下一次事故更難被誠實地說出來。

postmortem 應該寫哪些段落？

  • 標題與基本資料表：包括 Severity（SEV1 到 SEV4，或 critical 到 low）、Duration（從開始到解決，並標明時區）、User impact（誰受到什麼影響，能量化就量化），以及 Status（Resolved 或 Monitoring）。
  • Summary：用三到五句話讓忙碌的讀者掌握全貌：發生了什麼、造成什麼影響、根因是什麼，以及最後怎麼修正。
  • Timeline：標明時區，只放有時間戳的事實。內容可以包括發生或觀察到什麼、如何被發現、關鍵診斷或緩解動作，以及最後何時解決。
  • Root cause：寫出真正的技術原因，從觸發事件一路連到失敗結果。這裡要分清楚 trigger（導火線） 與 underlying weakness（底層弱點）：導火線是「那一次發生了什麼」，底層弱點則是「為什麼那件事足以釀成事故」。
  • Contributing factors：列出讓事故變得更嚴重、更難偵測，或更難修復的因素，例如缺少警示、沒有 timeout，或系統擁有權不清楚。
  • What went well：記錄快速偵測、乾淨的 rollback、好用的工具等有效環節。這裡要把功勞歸給系統與流程，而不是塑造某位英雄。
  • Action items：使用一張表，欄位包括 Action、Type、Owner、Priority。每個動作都要具體且可指派，並標示為 Prevent（防止再發）、Detect（更快發現）或 Mitigate（降低衝擊）。「更小心一點」不是 action item，因為沒有人知道要做什麼，也無法驗證是否完成。
  • Lessons：整理可以長期帶走的結論。如果事故顯示需要新增一份規格或具體的後續工作，就直接在這裡點名。

時間軸寫事實，分析放到後面

postmortem 最容易混亂的地方，是把「當時看到的事」和「事後推導出的解釋」混在一起。時間軸只放事實：誰在什麼時間觀察到什麼、系統出現什麼現象、做了哪個緩解動作。

至於為什麼會發生，應該放進 Root cause 與 Contributing factors。這樣讀者可以先沿著時間軸重建事故，再看分析如何解釋這些現象，而不是把推測誤讀成當時已知的事實。

根因也要避免只停在「最後一次改動」。那通常只是 trigger。真正要問的是：為什麼這個改動能直接造成事故？是哪個檢查、警示、隔離或流程沒有發揮作用？如果答案還不確定，就寫 Unknown, to investigate，不要用猜測填滿空白。

這兩種文件各自守住什麼底線？

release note 的底線，是不讓使用者被技術細節淹沒，也不把 breaking changes 藏起來。它要從使用者價值開始，依重要性排列，並且只根據區間內的 commits 與 diff 寫作。

postmortem 的底線，則是不把事故簡化成某個人的疏忽。它要讓時間軸保持可驗證，讓 Root cause 清楚區分導火線與底層弱點，再把改善工作拆成可指派、可追蹤的 Prevent、Detect 或 Mitigate 動作。

release note 給終端使用者，寫到 docs/releases/<version>.md：先講使用者價值、依重要性排序（Highlights → Improvements → Fixes）、breaking changes 絕不埋、不用內部術語與 ticket 編號，一切從區間內的 commits 與 diff 推。postmortem 給團隊，寫到 docs/postmortems/<date>-<slug>.md：全程 blameless，時間軸只放有時間戳的事實，Root cause 要分開導火線與底層弱點，action item 具體可指派並標 Prevent / Detect / Mitigate，未知的就寫 Unknown, to investigate。

五節走完，你已經看過 /document 的全貌：它產出哪四種文件、各自面對誰、素材怎麼從 git 撈出來、四條不能破的底線，以及最不技術的兩種文件如何完成翻譯。

現在可以把它跑在練習專案上：挑一個剛做完的功能，執行一次 /document pr，觀察它如何把三個檔案的改動，整理成審查者讀得懂、你也敢背書的描述。
