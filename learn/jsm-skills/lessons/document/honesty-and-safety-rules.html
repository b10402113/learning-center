四條不准破的文件底線

Step 3/5 · /document：把變更寫成人話

學習目標

這一節要練習守住四條底線：忠於 diff、不編造、不洩漏機密、不重複。當手上的資料真的不足時，用 None 或 Unknown, to investigate 誠實收尾，不要拿猜測把空白硬填滿。

前言：文件通常不是少寫，而是多寫了一點

上一節已經把素材整理好了：diff、commit、規格，以及環境檢查結果。看起來只要套進樣板，文件就能完成。真正容易出錯的地方，卻常常是作者忍不住多補了一句。

想像你在 PR 描述裡寫：「這個改動讓查詢快了三倍。」你知道自己把一段 N+1 查詢改成一次 join，直覺上覺得一定會快很多。但 diff 裡沒有量測結果，你也沒跑過基準測試。審查者相信了這句話，還把它當成賣點寫進 release note；上線後，卻有人發現某些資料量下反而更慢。

問題不只是數字寫錯，而是文件的可信度一起被拖下水。這一節談的四條底線，分別對應真實世界的代價：信任崩壞、事故資訊失真、機密二次外洩，以及文件被重複內容塞到沒人想讀。

底線一：忠於 diff，不誇大

第一條規則最簡單，也最容易在不知不覺間被踩過：只描述這個改動實際做了什麼。

如果 diff 找不到根據，就不能宣稱效能提升、安全修補，或某個行為已經改變。當 commit 訊息和 diff 互相矛盾時，以 diff 為準。

難點在於：你通常知道的，比最後寫出來的多。寫程式時，你想過很多方案，也有原本的設計意圖；但文件要記錄的是「實際發生了什麼」，不是「原本打算做什麼」。沒有被 diff 證實的內容，就不要把它包裝成成果。

底線二：不編造，不知道就說不知道

第二條是：絕不虛構。 這在 postmortem 特別重要，因為事故時間軸與根因最容易被人用印象補齊。

例如，你依稀記得是早上十點左右發現異常，便寫成「10:00 發現異常」。但你其實沒有確認過時間，只是覺得表格留白很難看。這種填空不會讓檢討更完整，反而會把原本應該被信任的紀錄變成猜測。

正確做法是：凡是手上沒有證據的事實，就寫 Unknown, to investigate。這能清楚區分「已知」與「待查」，也讓下一位接手的人知道要從哪裡開始調查。

release note 也一樣。你可以把確實完成的變更翻譯成使用者看得懂的好處，但不能為了讓內容好看而誇大，更不能承諾尚未完成的功能。

底線三：絕不漏出機密

第三條和安全直接相關：如果 diff 裡出現憑證、token、API key、連線字串或私有 URL，任何文件都不能把它轉錄出來。

這裡的「任何文件」包括 PR 描述、changelog、release note 和 postmortem。只要把機密貼到其中一處，洩漏就發生了第二次，而且它通常會出現在更公開、更難回收的位置。

處理方式分成兩步：

  1. 用泛稱描述，例如「輪替了 API 憑證」，不要貼出實際值。
  2. 主動標示「這次 diff 裡出現過機密」，讓團隊知道需要檢查並採取後續處理。

文件作者的責任不是把機密藏在一句話裡，而是把機密隔離在文件之外，同時提醒團隊它曾經出現。

底線四：不重複，重跑也不會越堆越長

第四條主要適用於 changelog：idempotency（冪等性）。意思是同一個動作執行一次或多次，最後結果都應該一致。

寫 changelog 時，流程要先讀取既有的 CHANGELOG.md。如果這個改動已經有等價條目，就不要再盲目新增一條，而是調整既有內容或直接跳過。

這條規則很重要，因為人和 agent 都可能重跑同一個流程。若每次執行都直接追加，同一個修正很快就會出現三、四次。久而久之，changelog 像被重複貼上的便利貼，資訊還在，卻沒人想讀。

好的重複執行不應該讓結果持續變形，而應該讓檔案維持穩定。

寫作紀律：照樣板走，沒料就寫 None

除了這四條底線，所有文件還共用一項寫作紀律：嚴格依照樣板的結構與順序，每一段都要填寫；如果確實沒有內容，就寫 None，不要為了填滿而灌水。

這看起來有點死板，換來的卻是可預測性。當每一份 PR 描述都有固定的「風險與上線」段落，審查者就知道要去哪裡找關鍵資訊。若該段真的沒有內容，一句 None 反而比一段模糊的廢話更有用。

規格可以用來取得變更的動機，但不要拿它來推測規格沒有證實的細節。樣板是欄位的邊界，不是邀請你自由發揮的空白畫布。

小結

四條底線：忠於 diff，只寫改動實際做的事，且 diff 優先於 commit 訊息；不編造，不知道就寫 Unknown, to investigate；不漏密，憑證、token、金鑰與私有 URL 一律不轉錄，改用泛稱並標示曾出現機密；不重複，changelog 先讀既有條目，重跑也不堆疊。所有文件都要遵循樣板的段落與順序，每段都要填，真的沒有內容就寫 None。這四條底線分別避免信任崩壞、事故資訊失真、二次外洩，以及文件失去可讀性。

底線立好之後，才適合真正動筆。四種文件可以依讀者分成兩組：先處理給「看碼的人」的 PR 描述與 changelog，再處理給「不看碼的人」的 release note 與 postmortem。下一節先從第一組開始。
