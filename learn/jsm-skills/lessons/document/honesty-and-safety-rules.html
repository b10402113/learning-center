四條不准破的底線

Step 3/5 · /document：把變更寫成人話

學習目標

能守住「忠於 diff、不編造、不漏密、不重複」四條底線，並在真的無料可寫時用「None」或「Unknown, to investigate」收尾，而不是填充。

前言：文件寫壞，通常是多寫了一點

上一節把素材撈齊了：diff、commit、規格、環境檢查的結果。按理說，素材足夠，接下來照樣板填就好。但一份文件會壞掉，往往出在作者身上：素材明明夠了，他卻忍不住多寫了一點。

想像一個常見的畫面：你在 PR 描述裡寫下「這個改動讓查詢快了三倍」，因為你心裡清楚自己把一段 N+1 的查詢改成了一次 join，感覺上就應該快很多。問題是 diff 裡沒有任何量測，而且你根本沒跑過基準測試。審查者相信了你的說法，把它當成賣點寫進 release note；上線後卻有人發現某些資料量下反而更慢。信任就是這樣一次崩掉的。

這一節講的就是這四條最容易犯的錯。它們不是道德勸說。每一條背後都對應一個真實世界會付代價的下場。

底線一：忠於 diff，不誇大

第一條規則最簡單也最難守：只描述這個改動真的做的事。 你永遠不能在 diff 裡找不到根據的情況下，宣稱一個效能提升、一個安全修補、或一個行為改變。當 commit 訊息和 diff 互相矛盾時，以 diff 為準。

這條規則的難點在於「知道的比寫出來的多」。你寫程式的時候想了很多、考慮了很多，於是寫文件時會很自然地把那些「意圖」也寫進去，彷彿它們是成果。但文件要描述的是「實際發生了什麼」，不是「我原本打算做什麼」。凡是沒被 diff 證實的，就不寫。

底線二：不編造，不知道就說不知道

第二條：絕不虛構。 這條在 postmortem 上最關鍵，因為事故的時間軸和根因是最容易「補齊」的地方。你隱約記得是早上十點左右，於是寫下「10:00 發現異常」；其實你根本不確定，只是覺得空白看起來很糟。這種填空並不負責，只會把一份本該被信任的事後檢討變成一份猜測。

正確的做法是：凡是不在你手上有的事實，就老實寫 Unknown, to investigate。這是在把「已知」和「待查」分清楚，讓下一個接手的人知道從哪裡開始查。同樣的道理也適用在 release note 上：你可以把真的變更翻譯成使用者利益，但不能為了好看而誇大，更不能承諾一個根本還沒做的功能。

底線三：絕不漏出機密

第三條攸關安全。如果 diff 裡出現憑證、token、API key、連線字串或私有 URL，任何文件都不能把它轉錄出來。 注意，這裡的「任何文件」包含 PR 描述、changelog、release note、postmortem。只要你在某處貼上它，洩漏就發生了第二次，而且這次是留在一個更公開、更難回收的地方。

正確的處理有兩步：第一，用泛稱描述，例如「輪替了 API 憑證」，而不是貼出那串值；第二，主動標示「這次 diff 裡出現過機密」，讓團隊知道要去檢查並處理。寫文件的人碰到機密時，重點是把它隔離在文件之外。

底線四：不重複，重跑也不會愈堆愈長

第四條專門給 changelog：idempotency（冪等性）。意思是同一件事做一次和做很多次，結果一樣。寫 changelog 時，它會先讀既有的 CHANGELOG.md；如果這個改動已經有等價的條目在裡面，就不要再加一條，而是調整或跳過。

為什麼這條重要？因為人（和 agent）難免會重跑。如果每次重跑都盲目地追加，同一個修正就會在檔案裡出現三、四次，久了整份 changelog 就沒人想讀了。一個好的重複執行，不應該讓結果累積變形。

寫作紀律：照樣板走，沒料就寫 None

除了這四條底線，還有一條貫穿所有型別的寫作紀律：嚴格照樣板的結構寫：一樣的段落、一樣的順序。每一段都要填；如果某一段真的沒有內容，就寫 None，不要為了填滿而灌水。

這聽起來很死板，但它換來的是可預測性。當每一份 PR 描述都有固定的「風險與上線」段落，審查者就知道要去哪裡找關鍵資訊；如果那一節真的什麼都沒有，一句 None 反而比一段含糊的廢話更有價值。規格只拿來取「動機」，不要拿它去推測更多。

小結

四條底線：忠於 diff（只寫改動真做的事，diff 打敗 commit 訊息）；不編造（不知道就寫 Unknown, to investigate，不填空）；不漏密（憑證、token、金鑰、私有 URL 一概不轉錄，用泛稱並標示）；不重複（changelog 要先讀既有條目，重跑不堆疊）。寫作紀律是照樣板的段落與順序走，每段都要填，真的沒有就寫 None，不灌水。這四條對應四種真實下場：信任崩壞、事故再發、二次外洩、文件沒人讀。

底線立好了，接下來要真的動筆。四種文件其實可以依讀者分成兩組：先看給「看碼的人」的 PR 描述與 changelog，再看給「不看碼的人」的 release note 與 postmortem。下一節先處理第一組。
