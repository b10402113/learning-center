寫給看碼的人：PR 描述與 changelog

Step 4/5 · /document：把變更寫成人話

學習目標

能依樣板寫出可貼上的 PR 標題與內文，以及符合既有格式、不重複的 changelog 條目。

前言：讀者看得到碼，所以你不用從零解釋

前面三節把素材與紀律都備好了，這一節真的動筆。四種文件可以依「讀者看不看得到程式碼」分成兩組，先處理第一組：會讀碼、或至少讀得懂技術的人。PR 描述給審查者，changelog 給使用這套程式庫或服務的開發者。因為他們看得到碼，你要做的是幫他們把「該先看什麼、該擔心什麼」標出來，技術本身他們自己看得到。

這兩種文件最怕的，是把該有的資訊埋在細節裡：PR 把改動寫成逐檔流水帳，審查者讀了三段還不知道這個 PR 在幹嘛；changelog 用函式名稱當條目，讀者得先查原始碼才看懂。接下來看樣板怎麼避免這兩件事。

PR 描述：先抓住審查者的注意力

PR 描述是審查者打開這個改動後看到的第一個東西。它要做的第一件事，是幫審查者快速建立正確的心智模型，知道該從哪裡看起、哪裡可能有坑，完整反而是其次。

標題

標題只有一行，用祈使語氣，長度不超過 72 個字元。所謂祈使語氣，就是像在下指令：「add rate limiting to the orders API」而不是「added」或「adds」。如果 AGENTS.md 有指定 commit 慣例（例如 feat:、fix:），標題就跟著那個慣例走。兩個實際範例：

feat: add rate limiting to the orders API
fix: prevent double-charge on retried checkout

內文的六個段落

標題之下，內文照固定順序分六段。這個順序本身就在回答審查者腦中依序冒出的問題。

  1. What（做了什麼）：一到三句白話，說明這個 PR 做什麼。這是最多人先讀的一段，務必讓人一眼掃過就懂。
  2. Why（為什麼）：動機。如果有一份規格治理這個改動，就連結它，例如「Implements docs/specs/0007-rate-limiting.md」；如果知道對應的 issue 或 ticket，也一併附上。
  3. Changes（改了哪些）：列出重點變更，照意圖分組，不是逐 commit、也不是逐檔的流水帳。
  4. How to test / verify（怎麼測）：審查者可以跑來確認它能動的步驟或命令，以及他們應該觀察到什麼。不准自己編測試步驟；要從真的寫了的測試、或這個改動實際的行為推出來。
  5. Risk & rollout（風險與上線）：影響範圍、資料庫 migration、feature flag、rollback 的做法。如果這個改動真的低風險，就老實寫「Low risk, no migrations, no flags.」。如果這次有 review findings，把你們決定接受的殘餘風險寫在這裡。
  6. Notes for reviewers（給審查者的提醒）：任何能幫上審查的資訊，像是一個棘手的決定、一個刻意的取捨，或一個想多要一雙眼睛的地方。沒有的話就省略。

規則裡最常被違反的一條是分組：Group changes by intent, not by file or commit. 審查者要的是這個改動的故事，不是 git log 的影印。三個檔一起做了「加上速率限制」這件事，就把它們寫成一條，而不是三條。

寫完之後：什麼時候才會碰 gh

PR 的標題與內文永遠會以文字回傳，直接顯示在聊天室，所以就算沒裝 gh、或這個 repo 沒有 remote，你也拿得到可以貼上的完整內容。只有在你先前確認過的 GH_ACTION 指示下，它才會碰 gh：none 就只給文字；gh pr create 才建立 PR；gh pr edit 是更新既有 PR 的內文。它永遠不會自作主張換成別的 gh 命令，也不會在沒確認前推送。

changelog：給開發者的變更流水帳

changelog 的讀者是想知道「這個版本動了什麼」的開發者或整合者。它附加到 repo 根目錄的 CHANGELOG.md，插在現行的 unreleased、也就是最上面的區段，而且只用 Edit 插入，不改寫既有條目。

這裡有一條比格式更重要的規則：先沿用既有檔案的格式。 如果 CHANGELOG.md 早就存在，就照它自己的結構與措辭（標題層級、區段名稱、日期格式、條目語感）走，不要把 Keep a Changelog 的格式硬套上去。下面這套預設格式，只在你新建這個檔案時才拿來當開頭：

# Changelog

All notable changes to this project are documented in this file.
The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

條目放進 ## [Unreleased] 底下正確的子標題裡（子標題不存在就建立）。類別有固定順序：Added、Changed、Deprecated、Removed、Fixed、Security。實際寫起來像這樣：

## [Unreleased]

### Added
- 訂單端點現在支援分頁

### Fixed
- 修正重試結帳時可能重複扣款的問題

幾條要注意的規則：一個條目只寫一件事；純內部、對使用者或整合者沒有影響的 refactor 直接跳過。最關鍵的是從讀者的視角寫：「Added pagination to the orders endpoint」，而不是「Added limit param to getOrders」。前者告訴讀者能力變了，後者只是把程式碼換句話說。類別要對映正確：修 bug 放 Fixed、新旗標放 Added、行為改變放 Changed。只保留真的有條目的類別，不要留下空標題。若需要溯源，可以在括號裡附規格或 issue 編號，例如「(see spec 0007)」。

還記得上一節的 idempotency 嗎？它在 changelog 上就靠這一步落地：先讀既有條目。 如果這個改動已經有等價的條目在 unreleased 區段裡，就不要再加一條，調整它或直接跳過。

小結

PR 描述：一行祈使句標題、≤72 字元、跟隨專案 commit 慣例；內文六段依序是 What、Why、Changes、How to test / verify、Risk & rollout、Notes for reviewers。改動照意圖分組，不逐檔逐 commit；測試步驟不准編；標題與內文永遠以文字回傳，只有 GH_ACTION 決定要不要碰 gh。changelog：附加到 CHANGELOG.md 的 unreleased 區段，先沿用既有格式；類別順序 Added / Changed / Deprecated / Removed / Fixed / Security；從讀者視角寫，一則一事，純內部變更跳過，先讀再決定加或跳。

給看碼的人告一段落。下一節換兩種完全看不到碼的讀者：付錢用你產品的人，以及跟你一起處理事故的團隊。他們要的東西，是這四種文件裡最不技術、也最需要翻譯的兩種。
