寫給看碼的人：把 PR 與 changelog 寫成人話

Step 4/5 · /document：把變更寫成讀者看得懂的內容

學習目標

完成這一節後，你能依照既有樣板，寫出可以直接貼上的 PR 標題與內文，也能產生符合專案格式、內容不重複的 changelog 條目。

前言：讀者看得到程式碼，你要做的是帶路

前面三節已經準備好素材與紀律，現在輪到真正動筆。這一節處理兩種讀者：會讀碼，或至少看得懂技術內容的人。PR 描述寫給審查者；changelog 寫給使用這套程式庫或服務的開發者。

他們不需要你從第一行開始解釋程式碼。因為程式碼就在那裡，你真正要補上的，是閱讀路線：這次改動要解決什麼、應該先看哪裡、哪裡可能有風險。

最常見的問題，是把重要資訊埋進細節裡。PR 變成逐檔流水帳，審查者讀了好幾段，還是不知道這個 PR 到底要做什麼；changelog 則拿函式名稱當條目，讀者還得回頭查原始碼才明白功能變了什麼。好的樣板，就是用固定結構把這兩種雜訊擋在外面。

PR 描述：先讓審查者抓到重點

PR 描述是審查者打開改動後看到的第一份說明。它最重要的任務，是幫審查者快速建立正確的心智模型：知道這個改動在做什麼、應該從哪裡看、哪裡可能有坑。內容完整很重要，但不必用細節把重點淹沒。

標題：一行說清楚要做什麼

標題只有一行，使用祈使語氣，長度不超過 72 個字元。祈使語氣就像直接下指令，例如「add rate limiting to the orders API」，而不是「added」或「adds」。

如果 AGENTS.md 指定了 commit 慣例，例如 feat: 或 fix:，標題就要沿用那套慣例。以下是兩個例子：

feat: add rate limiting to the orders API
fix: prevent double-charge on retried checkout

內文：用六段回答審查者的問題

標題之後，內文依固定順序分成六段。這個順序對應審查者通常會依序提出的問題：做了什麼、為什麼做、改了哪些、怎麼確認、風險在哪裡，以及有沒有特別需要注意的地方。

  1. What（做了什麼）：用一到三句白話說明這個 PR 的目的與結果。這通常是最多人先讀的段落，應該讓人快速掃過就能理解。
  2. Why（為什麼）：交代改動動機。如果有規格治理這項改動，就連結它，例如「Implements docs/specs/0007-rate-limiting.md」；如果知道對應的 issue 或 ticket，也一併附上。
  3. Changes（改了哪些）：列出重要變更，並且按照意圖分組。不要照 commit 順序，也不要逐檔列出像 git log 一樣的流水帳。
  4. How to test / verify（怎麼測）：提供審查者可以執行的確認步驟或命令，並說明應該觀察到什麼。不要自己編造測試步驟；內容必須來自實際撰寫的測試，或這次改動確實產生的行為。
  5. Risk & rollout（風險與上線）：說明影響範圍、資料庫 migration、feature flag，以及 rollback 的做法。若改動確實低風險，可以直接寫「Low risk, no migrations, no flags.」。如果 review findings 中有決定接受的殘餘風險，也要放在這裡。
  6. Notes for reviewers（給審查者的提醒）：補充能幫助審查的資訊，例如棘手的設計決定、刻意做出的取捨，或特別希望再多一雙眼睛檢查的地方。沒有需要提醒的內容，就省略這一段。

最容易被忽略的規則，是「照意圖分組」：Group changes by intent, not by file or commit. 審查者要讀的是這次改動的故事，不是 commit 記錄的影印本。假設三個檔案共同完成「加上速率限制」這件事，就把它寫成一個變更，不要拆成三條檔案清單。

寫完之後：什麼時候才會碰 gh

PR 標題與內文永遠會以文字回傳，直接顯示在聊天室。因此，即使沒有安裝 gh，或目前 repo 沒有 remote，你仍然能拿到完整、可以貼上的內容。

只有在先前確認過的 GH_ACTION 指示下，才會操作 gh：none 只回傳文字；gh pr create 才建立 PR；gh pr edit 用來更新既有 PR 的內文。它不會自作主張改用其他 gh 命令，也不會在尚未確認前推送。

changelog：讓開發者知道版本變了什麼

changelog 的讀者，是想知道「這個版本動了什麼」的開發者或整合者。它會附加到 repo 根目錄的 CHANGELOG.md，插入現行的 unreleased，也就是檔案最上方的區段。操作時只用 Edit 插入，不改寫既有條目。

格式固然重要，但有一條規則更優先：先沿用既有檔案的格式。 如果 CHANGELOG.md 已經存在，就照它原本的結構與措辭，包括標題層級、區段名稱、日期格式與條目語氣。不要把 Keep a Changelog 的格式硬套上去。

以下預設格式，只在你新建這個檔案時，才用來作為開頭：

# Changelog

All notable changes to this project are documented in this file.
The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

條目要放在 ## [Unreleased] 底下正確的子標題中；如果子標題不存在，就建立它。類別有固定順序：

  • Added
  • Changed
  • Deprecated
  • Removed
  • Fixed
  • Security

實際寫起來如下：

## [Unreleased]

### Added
- 訂單端點現在支援分頁

### Fixed
- 修正重試結帳時可能重複扣款的問題

每個條目都要站在讀者這一邊

一個條目只寫一件事。純內部、對使用者或整合者沒有影響的 refactor，直接跳過。

最重要的是從讀者的視角寫。例如，「Added pagination to the orders endpoint」說的是使用者現在多了什麼能力；「Added limit param to getOrders」則只是把程式碼換一種說法。前者能讓讀者立刻判斷這項變更是否與自己有關。

類別也要對應正確：修 bug 放在 Fixed，新旗標放在 Added，行為改變放在 Changed。只保留真的有條目的類別，不要留下空標題。如果需要溯源，可以在括號裡附上規格或 issue 編號，例如「(see spec 0007)」。

先讀再寫，避免重複

還記得上一節談到的 idempotency 嗎？在 changelog 裡，它靠的是同一個動作：先讀既有條目。

如果 unreleased 區段已經有等價條目，就不要再新增一條。視情況調整既有條目，或直接跳過。這樣 changelog 才像一份可靠的變更紀錄，而不是同一件事被貼了兩遍。

小結

PR 描述：一行祈使句標題、≤72 字元、跟隨專案 commit 慣例；內文六段依序是 What、Why、Changes、How to test / verify、Risk & rollout、Notes for reviewers。改動照意圖分組，不逐檔逐 commit；測試步驟不准編；標題與內文永遠以文字回傳，只有 GH_ACTION 決定要不要碰 gh。changelog：附加到 CHANGELOG.md 的 unreleased 區段，先沿用既有格式；類別順序 Added / Changed / Deprecated / Removed / Fixed / Security；從讀者視角寫，一則一事，純內部變更跳過，先讀再決定加或跳。

給看碼的人告一段落。下一節換成兩種完全看不到碼的讀者：付費使用產品的人，以及和你一起處理事故的團隊。他們需要的，是四種文件裡最不技術、也最需要翻譯的兩種內容。
