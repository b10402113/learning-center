從真實 commit 與 diff 撈出文件素材

Step 2/5 · /document：把變更寫成人話

學習目標

完成這一節後，你應該能用 git 蒐集分支的變更集與規格依據，跑完 PR 所需的三項環境檢查，並正確處理 NO_TAGS、PR_EXISTS 與 postmortem 缺少事故資料等邊角情境。

前言：你記得的，通常比實際改的少

上一節提到四種文件與四種讀者。但無論最後要寫的是 PR 描述、changelog、release note，還是 postmortem，第一步都一樣：先把這次改動的真實樣貌撈出來。

這一步很容易被低估，因為人的記憶並不可靠。你可能以為自己「只改了三個檔案、加了一個端點」，結果一跑 git 才發現共有十一個檔案，其中還包含一個順手修掉的競態條件（race condition）。而那個順手修掉的問題，往往才是審查者最需要知道、也最可能出事的部分。

因此，這個工作流的基本態度是：不相信記憶，也不把 commit 訊息當成完整證據，只根據實際紀錄寫作。這一節會說明如何用 git 撈齊素材，以及遇到資料不足時，為什麼 agent 會停下來詢問，而不是自行猜測。

commit 是線索，diff 才是證據

蒐集素材時，commit 標題只能當作「提示」，不能當作「真相」。像「fix bug」或「update」這類訊息很常見，卻幾乎無法說明實際做了什麼。

真正能支撐文件每一句描述的，是 diff。/document 的紀律是：每一句話都要能在 diff 裡找到根據；如果 commit 訊息與 diff 不一致，以 diff 為準。

這條規則會在下一節再深入拆解。現在先記住一個實務結論：要讀 diff，不要只讀 commit 列表。

用 git 撈出變更集

這個流程使用的命令固定而且輕巧，刻意只依賴 git，以及需要時才使用的 gh。這樣做是因為兩者在不同作業系統上的行為相對一致。

第一步先決定 base 分支：如果存在 main，就使用 main；否則退回 master。

# base 分支：有 main 就用 main，否則用 master
git rev-parse --verify main
# 目前所在分支
git rev-parse --abbrev-ref HEAD

# pr / changelog：這個分支相對 base 的變更集（BASE = 上一步定出的 base）
git log --oneline "BASE..HEAD"
git diff --name-only "BASE...HEAD"

# release-note：需要 tag。列出它們；若一個都沒有，就優雅地退回 NO_TAGS
git tag --sort=-creatordate

接著，流程會列出 docs/specs/ 底下檔名以數字開頭的規格檔，並取最近修改的三份，只保留檔案路徑。這些規格主要用來提供改動的動機：當文件樣板問「為什麼要做這個改動」時，可以從規格中找依據。

但規格沒有寫的理由，不能自行補上。規格是素材來源，不是讓 agent 發揮想像力的空白支票。

diff 太大時：只外包閱讀，不外包寫作

如果 diff 大到超過二十五個檔案，完整閱讀可能會消耗大量 context。這時可以把「讀 diff」交給唯讀的 scout 子代理，並使用最便宜的模型，請它依檔案群組或功能整理摘要。

主線 agent 再根據摘要開始寫文件。不過，能外包的只有閱讀與整理；寫文件始終留在主線。這條界線很重要：唯讀子代理可以幫忙把一座雜亂的倉庫整理成地圖，卻不應該直接修改文件或替主線做最後判斷。

PR 專屬的三項環境檢查

如果要寫的是 PR 描述，動筆前會先確認三件事，並記下結果。後面要不要使用 gh，就根據這三項結果決定：

  1. GH_INSTALLED：系統上是否安裝了 gh？
  2. HAS_REMOTE：這個 repository 是否有 git remote？執行 git remote，只要輸出不為空，就代表有 remote。
  3. PR_EXISTS：這個 PR 是否已經存在？執行 gh pr view --json number -q .number；如果輸出 PR 編號，就視為已存在。

這三項檢查不是為了炫技，而是後續決策的唯一依據：能不能使用 gh，以及應該使用 create 還是 edit。

少了這一步，agent 很可能在沒有 remote 的 repository 裡硬跑 gh pr create，最後只丟回一個難以判讀的錯誤。

三個會停下來問你的邊角情境

蒐集素材時，遇到以下三種情況，流程不會硬猜或硬做，而是先請你補充或確認。它們正是這個階段最容易被忽略、也最容易造成錯誤的地方。

release note 找不到 tag：NO_TAGS

release note 需要一個版本區間。如果有 tag，區間就是「上一個 tag 到最新 tag」，或使用你指定的區間。

但如果一個 tag 都沒有，流程不會自行猜測。它會問你：「沒有找到版本 tag。請提供一個版本名稱與區間，例如 v1.0.0，涵蓋 <commit>..HEAD；或者，我可以涵蓋從第一個 commit 以來的所有內容。」

這樣做的原因很直接：版本範圍會影響 release note 的內容。沒有依據時，寧可停下來確認，也不要悄悄替你決定。

PR 與 gh：先確認，再對外

建立或更新 PR 都是「對外動作」，因此流程會守住三道界線：

  • 只有在 GH_INSTALLED 且 HAS_REMOTE 時，才會提議使用 gh 建立或更新 PR。如果 gh 無法使用，或 repository 沒有 remote，PR 內文就只留在聊天室，不嘗試執行 gh。
  • 如果 PR_EXISTS，應該執行 gh pr edit 更新內文，不能執行 gh pr create。只有不存在的 PR 才能建立，已存在的 PR 只能更新。
  • 執行 gh 前要先確認，push 前也要先確認。流程會先把內文交給你查看，再詢問是否送出。這項規則不受 AGENTS.md 裡 ## Git 設定的影響；該設定只決定這個工作流平常是否要碰 PR。若設定為 integration: off，就把文字交給你，不主動推送。

postmortem 缺料：git 裡沒有事故敘事

git 記得住程式碼如何變動，卻記不住「當時到底發生了什麼」。因此，寫 postmortem 時，流程會向你索取幾項無法從 git 讀出的關鍵事實：

  • 哪裡壞了；
  • 什麼時候發生，包含時區；
  • 使用者受到什麼影響；
  • 問題是如何被發現的；
  • 根因與修法是什麼。

如果有 /debug 的輸出，也請直接指向它。你提供的內容就是這起事故的「事故事實」，流程不能編造你沒有提供的時間軸或根因。

順帶一提：跨平台的可攜性

上述 git 命令在不同作業系統上的行為一致，因此可以直接照用。至於其他看起來像 shell 的片段，例如 find、grep、sed、test，它們只是 POSIX 的參考寫法，不是可以直接翻譯成腳本執行的內容。

因此，工作流要求 agent 使用跨平台的原生檔案工具來讀取、搜尋與寫入檔案，再自行套用分支邏輯，而不是依賴 shell 的 if、變數或重導向。

這看似只是工程細節，實際上卻決定了同一套 skill 能不能在 macOS、Linux 與 Windows 上正常運作。

小結

寫任何文件前，先把素材撈齊。以 main 為 base；如果不存在，就使用 master。接著執行 git log --oneline BASE..HEAD 與 git diff --name-only BASE...HEAD。release note 另外使用 git tag --sort=-creatordate 找 tag，改動動機則從最近修改的三份 docs/specs/ 規格中取得。

PR 需要額外檢查 GH_INSTALLED、HAS_REMOTE 與 PR_EXISTS。遇到三個邊角情境時要停下來確認：NO_TAGS 詢問版本與區間；PR_EXISTS 改用 gh pr edit；postmortem 缺料時，向你索取事故事實。

最重要的一句話是：commit 只是提示，diff 才是真相。

素材齊了，下一個風險才正要出現：素材越多，人越容易「補腦」，忍不住寫進 diff 裡沒有的內容。下一節會整理這個階段最重要的四條底線；它們也是一旦踩中，代價最高的失敗模式。
