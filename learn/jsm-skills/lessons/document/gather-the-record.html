從真 commits 與 diff 蒐集素材

Step 2/5 · /document：把變更寫成人話

學習目標

能用 git 蒐集分支變更集與規格依據、跑完 PR 的三項環境檢查，並處理 NO_TAGS、PR_EXISTS、postmortem 缺料這幾個邊角。

前言：你記得的，通常比實際改的少

上一節我們知道有四種文件、四種讀者。但不論最後寫的是哪一種，第一步永遠一樣：把這個改動的真實樣貌撈出來。這裡有個很容易被低估的陷阱：你的記憶不可靠。你以為自己「改了三個檔、加了一個端點」，git 一跑卻發現是十一個檔，其中一個是你順手修掉的競態條件（race condition）。那個順手修掉的東西，往往才是審查者最該知道、也最可能出事的部分。

所以這一步的姿態是：不相信記憶，也不完全相信 commit 訊息，只相信紀錄。這一節就來看它怎麼用 git 把素材撈齊，以及在幾個常見的邊角情境下，它會停下來問你而不是亂猜。

commit 是提示，diff 才是真相

蒐集素材時，commit 的標題只是「提示」，不是「真相」。你我都寫過那種又短又隨便的訊息，例如「fix bug」或「update」，它們幾乎沒有說明力。真正能支撐每一句描述的是 diff。/document 的紀律是：每一句都要能在 diff 裡找到根據；當 commit 訊息和 diff 打架時，diff 贏。 你會在下一節把這條紀律看得更仔細，這裡先記住一個實務結論：要讀 diff，不要只讀 commit 列表。

用 git 撈出變更集

它跑的命令固定而輕巧，而且刻意只依賴 git（以及選用的 gh），因為這兩個工具在每個作業系統上行為一致。第一步先確定 base 分支：如果 main 存在就用 main，否則退回 master。

# base 分支：有 main 就用 main，否則用 master
git rev-parse --verify main
# 目前所在分支
git rev-parse --abbrev-ref HEAD

# pr / changelog：這個分支相對 base 的變更集（BASE = 上一步定出的 base）
git log --oneline "BASE..HEAD"
git diff --name-only "BASE...HEAD"

# release-note：需要 tag。列出它們；若一個都沒有，就優雅地退回 NO_TAGS
git tag --sort=-creatordate

接著是「為什麼」的脈絡。它會列出 docs/specs/ 底下、檔名以數字開頭的那些規格檔，然後取最近修改的三份，只拿路徑。規格是用來說明這個改動的動機的，當樣板問到「為什麼」時就拿它來填，但也不能超譯；規格沒說的理由，不要替它編。

素材到手後，還有一件事要處理：這個 diff 可能很大。如果變更超過二十五個檔案這種規模，它可以把「讀 diff」外包給一個唯讀的 scout 子代理，用最便宜的模型跑，回來一份按檔案群或功能分組的摘要，主線再從摘要動筆。注意，能外包的只有讀；寫文件這件事始終留在主線。

PR 專屬的三項環境檢查

如果你要寫的是 PR 描述，它在動筆前會先確認三件事，並把結果記下來，等後面決定「要不要碰 gh」時使用：

  1. GH_INSTALLED：這個系統上裝了 gh 嗎？
  2. HAS_REMOTE：這個 repo 有 git remote 嗎？跑 git remote，結果不為空就是有。
  3. PR_EXISTS：這個 PR 是不是已經存在？跑 gh pr view --json number -q .number；如果印出一個 PR 編號，就當作已存在。

這三個結果不是拿來炫技的，它們是後面「能不能用 gh、該用 create 還是 edit」的唯一依據。少了這個步驟，agent 很容易在一間沒有 remote 的 repo 上硬跑 gh pr create，然後給你一個看不懂的錯誤。

三個會停下來問你的邊角

蒐集到一半，有三種情境它不會硬幹，而是先跟你確認。這幾個是這個階段最容易被忽略、也最常出錯的地方。

release-note 找不到 tag（NO_TAGS）

release note 需要一個版本區間。如果有 tag，區間就是「上一個 tag 到最新 tag」（或你指定的區間）。但如果一個 tag 都沒有，它不會猜，而是問你：「沒有找到版本 tag。給我一個版本名與區間（例如 v1.0.0，涵蓋 <commit>..HEAD），或者我就涵蓋從第一個 commit 以來的所有內容。」

PR 與 gh：先確認，再對外

開 PR、更新 PR 都是「對外動作」，所以它會守住三道界線：

  • 只有在 GH_INSTALLED 且 HAS_REMOTE 時，才提議用 gh 建立或更新。若 gh 不能用或沒有 remote，PR 內文就只留在聊天室，不嘗試 gh。
  • 如果 PR_EXISTS，動作是 gh pr edit（更新內文），不是 gh pr create。不存在的 PR 才能建立，已存在只能更新。
  • 永遠先確認再跑 gh、也先確認再 push。 它會先把內文給你看，再問你要不要送出。這一點不受 AGENTS.md 裡 ## Git 設定影響；那個設定只決定這個工作流平常要不要碰 PR（設成 integration: off 就把文字交給你，不主動推）。

postmortem 缺料：git 裡沒有事故敘事

git 只記得住程式碼的變化，記不住「當時到底怎麼了」。所以寫 postmortem 時，它會向你索取幾個讀不到的關鍵事實：壞了什麼、什麼時候發生的（含時區）、使用者怎麼受影響、是怎麼被發現的、以及根因與修法（如果有 /debug 的輸出，就請你指向它）。你給的說法就是它的「事故事實」，而它不能编造你沒說的時間軸或根因。

順帶一提：跨平台的可攜性

這些 git 命令在任何作業系統上行為都一樣，所以照抄即可。其他那些看起來像 shell 的片段（find、grep、sed、test 等）只是 POSIX 參考，不是可以直譯執行的腳本。這也是為什麼工作流要求 agent 用自己跨平台的原生檔案工具（讀、搜尋、寫）來做這些事，並自己套用分支邏輯，而不是靠 shell 的 if、變數或重導向。這件事看起來很工程細節，但它決定了同一套 skill 能不能在 macOS、Linux、Windows 上都跑得動。

小結

寫任何文件前都先撈素材。用 main（否則 master）當 base，跑 git log --oneline BASE..HEAD 與 git diff --name-only BASE...HEAD；release note 另外用 git tag --sort=-creatordate 找 tag。動機從最近修改的三份 docs/specs/ 規格取。PR 另外作三項檢查：GH_INSTALLED、HAS_REMOTE、PR_EXISTS。三個邊角要停下來問：NO_TAGS 問版本與區間、PR_EXISTS 改用 gh pr edit、postmortem 缺料就向你索取事故事實。commit 只是提示，diff 才是真相。

素材齊了，但素材越多，人越容易「補腦」，忍不住多寫一點 diff 裡沒有的東西。下一節就要講這個階段最重要的四條底線，它們是這個階段失敗起來最貴的地方。
