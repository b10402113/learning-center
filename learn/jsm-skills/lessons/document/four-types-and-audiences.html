四種文件，四種讀者

Step 1/5 · /document：把變更寫成人話

學習目標

能說出 PR、changelog、release note、postmortem 四種文件各自的來源、受眾與產出位置，並知道 /document 只寫文字、可自由跳過，以及它何時問型別、何時直接動手。

前言：一句「修正一些小問題」，換來三天後的追問

你剛把一個功能做完，測試也綠了，正要開 PR。描述欄你懶得想，隨手打了一句「修正一些小問題」，按下送出。三天後同事在留言裡問你：「這個到底改了什麼？有沒有動到資料庫？如果上線後出問題，rollback 要怎麼做？」你看著那個空白一片的描述，只能回頭翻 diff，一條一條跟他解釋。

問題不在這裡。「把程式寫完」和「把改動講清楚」本來就是兩件不同的事。程式碼回答的是機器「怎麼跑」；文件回答的是人「發生了什麼、我該不該在意」。jsm-skills 專門切出一個階段來做後者，就是 /document。它不寫程式、不寫測試、不寫規格，只把已經真實發生的改動，翻譯成對的讀者看得懂的文字。

這一節先把整張地圖鋪開：它到底會產出哪幾種文件、每一種是給誰看的、又各自寫到哪裡去。

四種文件，對應四種讀者

/document 依你手上這個改動的性質，產出四種文件之一。這四種的差別主要不在格式，而在「誰要讀它」：受眾決定了用字遣詞的深淺，也決定了它該被放在哪裡。

型別素材來源受眾產出位置
pr分支 commits ＋ 對比 base 的 diff審查者PR 標題＋內文（聊天室；可選用 gh 建立／更新）
changelog已合併的變更開發者附加到 CHANGELOG.md（Keep a Changelog）
release-note一個 tag／版本區間終端使用者docs/releases/<version>.md（或聊天室）
postmortem一場事故（工程師描述，外加任何 /debug 紀錄）團隊docs/postmortems/<date>-<slug>.md

看懂這張表，你就掌握了這個階段的骨架：同一個改動，面對審查者要講「怎麼測、風險在哪」，面對開發者要講「哪個能力變了」，面對使用者要講「你現在能多做什麼」，面對團隊要講「下次怎麼不再發生」。用錯受眾，就算文字再漂亮也是白寫。

它的角色：從紀錄寫，為讀者寫

這個階段的角色定位，可以濃縮成一句話：像一位技術寫手，從紀錄寫，不從想像寫；為讀者寫，不為作者寫。 每一句話都要能指回真的發生過的事實，可能是一個 commit、一段 diff，或一條你被提供的事故事實；而每一份文件都要以「讀者接下來要做什麼」為準來寫。你永遠不虛構一個時間軸、一個根因、或一個來源裡沒有的變更。

在這個前提下，/document 只管文字。它不會寫程式、測試或規格；它也不 commit、不 push、不合併。它唯一會動到的其他檔案，是幫你在 scope 裡把 Document it 那一格打勾。而且若你不想用 gh 開 PR，它也絕不會自作主張替你推出去。把它想成一個「只負責把事情講清楚、不負責動手」的角色。

也因為它只產文字，它被歸類為「可以自由跳過」的階段之一：流程等級會建議你要不要跑，但決定權在你。原型階段你可能只需要一份 PR 描述，到了正式版才需要 release note 和 postmortem。

型別怎麼決定：一個問題，或直接開工

事情有個先後順序。如果你在指令後面直接指名了型別，例如 /document pr，它就用你給的那個，不再多問。如果你沒給，它會先從上下文推斷：站在一個領先 base 分支的 feature branch 上，就推斷是 pr；剛打完一個版本 tag，就推斷是 release-note。

推斷完，它會用一個問題跟你確認，並把你最可能想要的那個選項標上「推薦」。問題長這樣：

"What should I write?"
  header: "Doc type"
  options:
    - label: "PR description"        → pr
    - label: "Changelog entry"      → changelog
    - label: "Release notes"        → release-note
    - label: "Postmortem"           → postmortem

若是從上下文推斷來的，它會把推斷的那一項標成 (recommended)；你的 agent 若支援互動選單就用選單，不支援就用同樣選項的文字問答，並且永遠把「自訂」放在最後一格。這是一個「幫你做好決定、但你隨時可改」的設計，不是要你面對一個冷冰冰的空白提問。

只有在 postmortem 這種情況，它會多問一件事：git 裡讀不到的事故敘事。除此之外，它最多就問這一個問題，不會把你的時間耗在問卷上。

小結

四種文件對四種讀者：pr 給審查者（分支 commits＋diff，PR 標題與內文）；changelog 給開發者（已合併變更，附加到 CHANGELOG.md）；release-note 給終端使用者（tag 區間，寫到 docs/releases/）；postmortem 給團隊（事故敘事，寫到 docs/postmortems/）。它的角色是「從紀錄寫、為讀者寫」，只產文字、不碰程式，也不 commit 或 push。型別有給就用給的，沒給就推斷後用一個問題確認；只有 postmortem 會另外向你索取事故事實。

你現在有了地圖，但還沒有一滴素材。下一節要處理的就是這個：這些文件要寫得忠於事實，那「事實」到底從哪裡撈出來？答案是 git，而且有一套固定的蒐集動作。
