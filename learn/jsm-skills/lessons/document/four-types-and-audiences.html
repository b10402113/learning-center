四種文件，四種讀者

Step 1/5 · /document：把變更寫成人話

學習目標

完成這一節後，你應該能說出 PR、changelog、release note、postmortem 四種文件各自的素材來源、讀者與產出位置，也知道 /document 只負責寫文字、可以自由跳過，以及它什麼時候會詢問文件型別、什麼時候能直接開始。

前言：一句「修正一些小問題」，換來三天後的追問

你剛完成一個功能，測試也全數通過，正準備開 PR。描述欄一時想不到要寫什麼，便隨手填上「修正一些小問題」，按下送出。

三天後，同事在留言裡追問：「這次到底改了什麼？有沒有動到資料庫？如果上線後出問題，rollback 要怎麼做？」你只好重新翻 diff，一條一條向他解釋。原本可以在 PR 裡一次說清楚的資訊，現在變成來回補充的對話。

問題不在於你不會寫程式，而在於「把程式寫完」和「把改動講清楚」本來就是兩件事。程式碼回答機器「怎麼跑」；文件回答人「發生了什麼，以及我該不該在意」。

jsm-skills 把後者獨立成一個階段，也就是 /document。它不寫程式、不寫測試、不寫規格，而是把已經真實發生的改動，翻譯成適合不同讀者閱讀的文字。

這一節先把整張地圖攤開：/document 會產出哪幾種文件、每一種文件是寫給誰看的，以及最後應該放在哪裡。

四種文件，對應四種讀者

/document 會依照改動的性質，產出四種文件之一。它們的差異不只是格式，而是「誰要讀」。讀者不同，應該使用的說法、保留的細節，以及文件存放的位置也會跟著不同。

型別素材來源受眾產出位置
pr分支 commits ＋ 對比 base 的 diff審查者PR 標題＋內文（聊天室；可選用 gh 建立／更新）
changelog已合併的變更開發者附加到 CHANGELOG.md（Keep a Changelog）
release-note一個 tag／版本區間終端使用者docs/releases/<version>.md（或聊天室）
postmortem一場事故（工程師描述，外加任何 /debug 紀錄）團隊docs/postmortems/<date>-<slug>.md

同一個改動，對不同讀者要回答的問題並不一樣：

  • pr 要讓審查者知道怎麼測、風險在哪裡。
  • changelog 要讓開發者知道哪項能力發生了變化。
  • release-note 要讓終端使用者知道現在多了什麼可以使用。
  • postmortem 要讓團隊知道事故如何發生，以及下次怎麼避免重演。

所以，寫錯受眾時，問題不一定是文字不好，而是文件從一開始就回答了錯的問題。

它的角色：從紀錄寫，為讀者寫

這個階段可以濃縮成一句話：像一位技術寫手，從紀錄寫，不從想像寫；為讀者寫，不為作者寫。

每一句話都應該能指回已發生的事實，例如一個 commit、一段 diff，或你被提供的一條事故事實。文件也要以讀者接下來需要做什麼為準，而不是以作者想表現多少內容為準。

因此，你不能自行補出來源裡沒有的時間軸、根因或變更。文件的價值就像地圖：它可以把路線畫得更清楚，卻不能憑空增加一條根本不存在的路。

在這個前提下，/document 只處理文字。它不會寫程式、測試或規格，也不會 commit、push 或合併。它唯一可能修改的其他檔案，是在 scope 裡把 Document it 那一格打勾。

如果你不想使用 gh 開 PR，它也不會自作主張替你送出。可以把它想成一位只負責把事情講清楚的技術寫手，而不是替你執行後續操作的自動化機器人。

也因為它只產文字，/document 被歸類為可以自由跳過的階段。流程等級會建議你是否該執行，但最後決定權在你手上。原型階段可能只需要一份 PR 描述；到了正式版本，才可能需要 release note 和 postmortem。

型別怎麼決定：一個問題，或直接開工

/document 的判斷順序很簡單。如果你在指令後面直接指定型別，例如 /document pr，它就會使用你指定的型別，不再額外詢問。

如果你沒有指定，它會先從上下文推斷。例如，目前位於領先 base 分支的 feature branch 上，通常會推斷為 pr；如果剛建立一個版本 tag，則會推斷為 release-note。

推斷完成後，它只會用一個問題向你確認，並把最可能符合情境的選項標成「推薦」。問題會長這樣：

"What should I write?"
  header: "Doc type"
  options:
    - label: "PR description"        → pr
    - label: "Changelog entry"      → changelog
    - label: "Release notes"        → release-note
    - label: "Postmortem"           → postmortem

如果型別是從上下文推斷出來的，推斷結果會標成 (recommended)。你的 agent 若支援互動選單，就使用選單；若不支援，就用相同選項進行文字問答。無論採用哪種方式，「自訂」都會永遠放在最後一格。

這樣的設計是替你先整理好最可能的答案，同時保留修改選擇的空間。它不是把你丟進一個冷冰冰的空白提問，也不是要求你填一長串問卷。

只有 postmortem 例外：因為事故敘事通常不會完整存在於 git 裡，它還會另外向你索取那些讀不到的事故事實。除此之外，最多只會問你這一個文件型別問題。

小結

四種文件對應四種讀者：pr 給審查者，素材是分支 commits 與 diff，產出為 PR 標題和內文；changelog 給開發者，素材是已合併的變更，附加到 CHANGELOG.md；release-note 給終端使用者，素材是 tag 或版本區間，寫到 docs/releases/；postmortem 給團隊，素材是事故敘事，寫到 docs/postmortems/。/document 的角色是「從紀錄寫、為讀者寫」，只產文字，不碰程式，也不 commit 或 push。型別若已指定就直接使用；若未指定，就先推斷，再用一個問題確認。只有 postmortem 會額外索取事故事實。

現在你有了文件型別與讀者的地圖，但還沒有開始蒐集素材。下一節會處理更實際的問題：如果文件必須忠於事實，那些事實到底要從哪裡取得？答案是 git，而且有一套固定的蒐集動作。
