誰能動哪個檔案

Step 3/5 · 知識載體與擁有權

學習目標

能說出每個知識載體由誰建立、誰讀、誰能改，並解釋單一擁有者與外科手術式修改為什麼讓這些檔案不會隨時間崩壞。

前言：文件不是沒人寫，是太多人能改

你一定看過這種場景。專案的 AGENTS.md 寫著「縮排用 tab」，但 .editorconfig 裡是 spaces；README 說部署跑 npm run deploy，但 package.json 裡根本沒這個 script。文件之所以會爛掉，通常不是因為沒人寫，問題出在誰都能改。當每個人、每個工具都能動同一份文件，最後就會出現兩份互相矛盾的真相，而沒有人知道該信哪一份。

這套流程的解法是把擁有權固定下來：每個檔案只有一個建立者、明確的讀者，以及非常有限的修改者。這一節把那張表攤開，並解釋它為什麼能讓文件多年後還可信。

擁有權總表

下表的每一列都是一個載體：誰生下它、誰讀它、誰有權改它。三欄的界線刻意分得很細，因為「讀」和「改」是兩件不同的事。

檔案建立者讀者修改者
AGENTS.md 與它的 CLAUDE.md 指標audit每一個 skillsync
docs/scope/ 裡的 scopescopearchitect、developdevelop 推進，scope 與 sync 對帳

除了這四種，還有幾個也一樣各有其主：審查結果寫到 docs/reviews/，由 check 負責；測試放進你的測試目錄，由 test 負責；應用程式碼在原始碼樹裡，由 develop 負責；給人看的文件，也就是 PR 內容、CHANGELOG.md、docs/releases/、docs/postmortems/，由 document 負責。

兩條讓表成立的紀律

一、單一擁有者

第一個紀律是每個檔案只有一個 skill 能改它的內容。spec 的內容只有 architect 能寫，develop 只能動狀態那一行（上一節講過的規則，正是這條紀律的具體例子）。scope 由 scope 建立、由 develop 推進、由 scope 與 sync 對帳，但沒有一個技能會越界去改別人的檔案。

這帶來一個很實際的結果：當你看到某份檔案被改動，你可以很確定知道是誰改的、依照什麼規則改的。可預測性就是可信度的來源。

二、外科手術式修改

第二個紀律是改動必須小而精準。負責對帳的 sync 只做兩件事：加上新的行、修正它擁有的行。它不會重寫你的敘述。這就是為什麼它能做到冪等：同一份變更再跑第二次，它一個字都不會動，因為第一次已經把該調的都調完了。

檔案可信還有一個前提，就是杜絕重複的真相來源：持久的專案情境活在與工具無關的 AGENTS.md 裡，CLAUDE.md 永遠只是一份指向它的薄指標。所以不存在「兩份都要更新，結果只更新了一份」的問題。

為什麼這件事對你重要

把擁有權固定下來，換到的是三件事。第一，跨 session 安全：每個階段交接時你可以清掉對話，因為下一個 skill 會從檔案讀到正確的狀態。第二，跨人一致：隊友 pull 下來看到的知識跟你一樣，不會各有一套。第三，不會腐化：檔案只會被它該改的那個角色改，所以長期不會出現「兩份文件互相打架」的爛帳。

小結

每個載體都有固定的建立者、讀者與修改者：AGENTS.md 由 audit 建立、所有 skill 讀、sync 維護；scope 由 scope 建立、develop 推進；specs 由 architect 掌管內容、develop 只推狀態；design.md 由 develop 負責。兩條紀律撐起這張表：單一擁有者，以及外科手術式修改。再加上 AGENTS.md 是唯一真實來源、CLAUDE.md 只是指標，檔案才不會隨時間崩壞。

有了各自的檔案、各自的狀態、各自的主人，下一個問題是：怎麼保證一個需求不會在流程中被漏掉或講不清？答案是一條從規格一路拉到測試的線：acceptance criteria。
