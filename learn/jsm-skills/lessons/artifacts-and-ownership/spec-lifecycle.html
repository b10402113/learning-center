一份 spec 的一生

Step 2/5 · 知識載體與擁有權

學習目標

能畫出一份 spec 的完整生命（Proposed → In Progress → Accepted，外加 Assumed 與 Superseded），並說清 Assumed 為什麼需要 ratification。

前言：三個月後回來，這份文件到底算什麼？

上一節把四種載體分開了，其中 spec 是最需要規矩的一種。想像你三個月後回到一個功能，資料夾裡躺著一份 spec，標題寫著「改用 OAuth 登入」。你心裡馬上浮出三個問題：這個決定是已經拍板了、還是只是提議？程式是照著它做了，還是根本沒動工？它到今天還算數嗎？

如果文件本身不回答這三個問題，你就得靠記憶或猜測，而記憶和猜測正是這套流程想擺脫的東西。所以每一份 spec 都帶著一個狀態，而且這個狀態只會被一條很窄的路徑改動。這一節就把那份狀態機講清楚。

spec 是什麼：決定加上合約

先確認定位。一份 spec 是「一個真實決定」的書面紀錄，例如要用哪種登入方式、資料長什麼形狀。它同時是兩件事：對決策者而言，它記下「當初為什麼這樣選」；對 build 而言，它是必須遵循的合約。

這個雙重身分讓它有兩群讀者。負責 build 的 develop 只讀它需要用來施工的那部分：需求與驗收條件、決策本身、設計、以及有序的施工計畫。它不會回頭重讀那長長的推論過程，因為那是歷史，不是施工輸入。而人要理解一個決定時，才會去讀它的來龍去脈。

第一階段：出生（Proposed）

當 architect 做出一個真實決定，它在那一刻被寫成一份 spec，出生時的狀態是 Proposed。這個字不是說「提案中、還在考慮」。它代表已經決定了、但還沒開始建：決策已經成立，只是施工還沒發生。

有一個例外：如果這份 spec 是要「記錄一件已經上線的事」，那它出生時直接就是 Accepted。因為它記的是已經發生的事實，不是未來的計畫。

第二階段：被讀、被改（In Progress → Accepted）

當 build 開始，develop 會載入 spec。它只讀施工需要的部分，讀完就照著做。

施工過程中，develop 會改這份 spec，但改法窄到只有一行。它把狀態列從 Proposed 推進到 In Progress，代表「決定已存在、施工正在進行」。等功能建好而且驗證通過，它再把狀態列從 In Progress 推進到 Accepted。

關鍵是：develop 只碰那一行狀態，永遠不編輯決策本身的內容。決策的內容只有 architect 能動。這條界線讓「誰做的決定」和「施工到哪了」兩件事不會混在一起。

第三階段：被取代（Superseded）

如果一個決定後來真的被推翻了，正確的做法是由 architect 重新走一次決定流程，而不是讓 develop 隨手改掉。它寫一份新的 spec，並把舊那份標成 Superseded，附上指向新版本的連結。這樣一來歷史仍然可讀：你看得到「當初選了 A、後來為什麼改成 B」，而不是舊文件被默默改寫、痕跡消失。

第四階段：被標記（flagged）

還有一種情況是沒人主動改它，但後來的某個變更讓它悄悄過期了。這種時候由 sync 負責把它標記出來，提醒人類去把它對齊，而不是讓它繼續掛在那裡當作仍然有效。

特殊狀態 Assumed：先做、後補

到這裡都是「先決定、再施工」的正常路徑。但實務上你一定會遇到另一種情況：你選擇在決定還沒做出來之前就先開工。

假設 develop 撞上一個關鍵選擇，例如某個 provider、某種資料形狀、某個介面設計，卻沒有對應的 spec，而你告訴它「照做就對了」。它不會默默地猜一個然後裝作沒事。它會先寫一份小小的 spec，狀態標成 Assumed，內容記下三件事：它正在用什麼假設、是誰授權它這樣做的、以及這個假設碰到哪些程式碼。

這是 develop 唯一被允許建立的 spec，而且只能是這個狀態。它的意思很直白：「記下來了，但還沒想透。」所以被它管的那個功能會一直掛著一個「欠 ratification」的標記。但這個標記不會擋住你，你照樣可以把它標成 done。它是一張站著的提醒，不是一道牆。

ratification：把欠的決定還掉

要清掉這個標記，你得再跑一次 architect。這次它面對的是「已經建好的程式碼」，好好地把這個決定想一遍。有兩種結局：如果你當初的假設是對的，它補上真實的理由、拿掉 Assumed 標記，這份 spec 就變成一份正式決策；如果當初假設錯了，它就寫一份更正版的 spec，並把舊那份標成 Superseded，讓 develop 照新的重做。

這個動作就叫 ratification（追認）。它讓「先做、後補」的 override 能夠繼續推進，同時保證那個決定最後一定會被好好想過一遍，不會永遠逃進對話裡消失。

兩條讓 spec 不糊掉的規則

整段生命能這麼乾淨，靠的是兩條規則。第一，只有 architect 能寫 spec 的內容，也只有 architect 能清除 Assumed 標記。第二，只有 develop 能沿著施工生命週期推進狀態列，而且它唯一能新建的 spec 就是那份 Assumed 草稿。單一擁有權，就是這些檔案多年後還讀得懂的原因。

小結

一份 spec 由 architect 出生為 Proposed（記錄已上線的事則直接 Accepted）。develop 讀施工需要的部分，只把狀態列推進成 In Progress、再推進成 Accepted，永不編輯決策內容。決定被推翻時由 architect 標舊的為 Superseded，過期時由 sync 標記。若你選擇在決定前先開工，develop 可建立唯一的 Assumed 草稿，功能就欠著一次 ratification，但那個標記永遠不擋 done。

既然每個檔案都有明確的主人，那整張「誰建立、誰讀、誰能改」的表長什麼樣子？下一節把它完整攤開，並說明單一擁有者紀律為什麼是這些檔案能長期可信的關鍵。
