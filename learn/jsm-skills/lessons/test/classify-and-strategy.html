先分類再下手：五種檔案各自對應的測試策略

Step 2/5 · /test：為變更寫回歸測試

學習目標

能從路徑與檔名把變更檔案分成 logic、component、page/flow、api/server、cli 五類，並說出每一類該用哪一種測試策略，以及大 diff 與 monorepo 該怎麼處理。

前言：同一句「寫測試」，卻是完全不同的兩件事

上一節你已經知道 /test 的範圍，是這條分支裡還沒提交的那些檔案。現在你手上有了清單，問題卻從「要測什麼」變成「每一個檔案該怎麼測」。

這兩個問題的難度差很多。一個純計算函式，測試就是餵它輸入、看它吐什麼；但一個 Vue 元件，你要驗證的是使用者看到什麼、點下去會怎樣；一個 API route 又不同，你要模擬一個真的請求進去看它回什麼；至於 CLI 指令，你得真的把它跑起來看它印了什麼、退出碼是多少。同樣叫「寫測試」，做法卻沒有一個通用版本。

所以 /test 在動手之前會先做一件事：把每個檔案歸類。這一節就來看它憑什麼分類、分成哪五類，以及每一類各自對應的策略。分類看起來像個小步驟，但它其實決定了測試會不會測錯地方。

只看路徑與檔名，就先把檔案歸類

它分類的方式刻意便宜：只看檔案的路徑與檔名，不打開內容。因為在這個階段，命名慣例通常已經講得夠清楚了。判斷規則如下。

路徑或檔名出現的訊號類別對應的測試策略
*.tsx、*.jsx、*.vue、*.svelte，且不在 route 或 page 路徑下component元件測試：render、互動、斷言 DOM 與 ARIA
app/**/page.*、pages/**（不含 pages/api）、*Screen.*、*View.*page/flowE2E 候選，外加各零件的元件測試
app/**/route.*、pages/api/**、*.controller.*、*.handler.*、*.resolver.*、actions.*api/server整合測試：呼叫 handler，只在邊界 mock
一般的 .ts、.js、.py、.go、.rs，以及 utils、hooks、services、domain logiclogic單元測試：輸入到輸出、邊界、錯誤
cli.*、bin/**、*.command.*、cmd/**cli整合測試：實際呼叫這個指令

真的遇到模糊、光看檔名判斷不出來的檔案時，它會先暫且標成 logic，等到真的打開檔案讀的時候再改標記。這個寬容的設計是為了讓分類保持便宜，不必為了歸類而先把所有檔案讀過一遍。

分完類，它會順手記下一個開關：只要清單裡有任何一個 page/flow 檔案，就把 E2E_RELEVANT 設成 yes。這個開關後面會決定它要不要問你 E2E 工具的事。

變更檔案太多時：先挑風險高的

如果這次的變更超過 15 個原始檔，它不會硬著頭皮一次全寫完。那種規模的變更一次寫完，品質一定下滑，而且很容易漏掉最該測的地方。它的做法是依照類別排優先序，先處理 logic 與 api/server，因為這兩類風險最高、也最便宜測得扎實，然後用一張決策面板問你打算怎麼聚焦：是先把 logic 與 API 測掉、其餘標成尚未覆蓋；還是分好幾批全部測完；或者由你直接指定最重要的檔案或目錄。

在 monorepo 裡還有一層解析。它會為每個檔案往上找出最近的那個 package.json，把同一個 root 的檔案歸成一組。不同的 root 可能用不同的框架、套件管理員與測試目錄，因此它會分組安裝、分組寫測試。如果往上找最終都指向同一個 root（這是常見情況），那就當成單一專案處理。

五類檔案，五種下手方式

分類完成後，每一類走自己的策略。這些策略的差別，說到底就是「該驗證到哪一層」與「哪些東西可以假裝」。

logic：純單元測試，餵真的輸入看真的輸出

純邏輯的檔案最好測，也最該測得徹底。做法是用真實輸入呼叫那個函式，斷言輸出，然後把邊界與錯誤情況盡量補齊。這裡有一條紀律：只 mock 真正的外部邊界，例如網路、檔案系統、時鐘、隨機數。你擁有的東西不要 mock，因為一旦把邏輯本身也 mock 掉，測試就只是在確認「我自己的假東西會回傳我自己設定好的值」。

component：測使用者看到什麼，不測元件內部

元件測試要 render 元件、用使用者事件去互動，然後斷言使用者實際感知到的東西，例如畫面上出現的文字、元素扮演的角色、按鈕是不是被 disabled、某個區塊是不是 expanded。無障礙也要一起驗。反過來說，不要斷言元件的內部 state，也不要斷言 class 名稱，那兩者都屬於實作細節，改了不該讓測試變紅。

page/flow：有 E2E 工具就走真實瀏覽器，沒有就退回元件層

頁面或流程如果設定了 E2E 工具，就為主要路徑寫一條真實瀏覽器流程：載入、操作、斷言結果，再加一條失敗路徑。頁面裡那些不簡單的零件，另外用元件測試覆蓋。要是沒有 E2E 工具，就在元件層把整個頁面覆蓋起來。這是一個務實的取捨：E2E 最接近真實使用，但成本也最高，所以只在有工具時才走這條路。

api/server：用代表性請求打 handler，只在邊界 mock

API 與 server 的檔案寫整合測試。用有代表性的請求去呼叫 handler、route 或 action，斷言回應的狀態、形狀，以及錯誤回應，例如壞輸入、未授權、找不到資源。資料庫與外部服務只在邊界那一層 mock 掉，其餘照真的走。

cli：真的把指令跑起來

命令列工具就用參數把它實際跑起來，斷言標準輸出、退出碼與副作用，並且至少涵蓋一條「參數不對」的路徑。因為 CLI 的價值就在於它被當成一個程式執行，所以測試也該這樣對待它。

為什麼分類這麼重要

如果分類錯了，測試就會測錯東西，而且錯得很隱蔽。把一個 React 元件當成 logic 來測，你就會去斷言它內部的 state，結果是改個 class 名稱測試就紅了，但元件真的壞掉時它卻不紅。這種假綠的測試，正是上一節說「比沒有更糟」的那一種。分類是為了對齊驗證的層次，讓你測的是這個檔案真正對外承諾的行為。

小結

/test 只用路徑與檔名就先把變更檔案分成五類：component、page/flow、api/server、logic、cli。每一類對應不同的策略，從純單元測試到真實瀏覽器流程都有。分類錯了，測試就會測到實作細節而不是行為。變更超過 15 個檔案時，先從風險高又便宜的 logic 與 api/server 下手；monorepo 則依最近的 package.json 分組處理。

知道每個檔案該用哪一招之後，下一步是：你要用哪一套工具來跑這些測試？這個選擇會被記在 test-preferences.json 裡。下一節就來看這個檔案，以及專案「刻意不裝測試 runner」時那套完全不同的形狀。
