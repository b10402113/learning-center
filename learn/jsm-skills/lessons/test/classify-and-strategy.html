先分類再下手：五種檔案，對應五種測試策略

Step 2/5 · /test：為變更寫回歸測試

學習目標

完成這一節後，你應該能根據路徑與檔名，把變更檔案分成 logic、component、page/flow、api/server、cli 五類；也能說明每一類該採用什麼測試策略，以及遇到大型 diff 或 monorepo 時該怎麼處理。

前言：同樣是「寫測試」，驗證的事情可能完全不同

上一節提到，/test 處理的是這條分支中尚未提交的檔案。現在清單已經有了，下一個問題就不再是「哪些東西需要測」，而是「每個檔案應該怎麼測」。

這兩個問題的難度並不一樣。對純計算函式來說，測試通常是餵入輸入，再檢查輸出；Vue 元件則要確認使用者看見什麼、點擊後發生什麼；API route 要模擬請求，檢查回應；CLI 指令則要真的執行，觀察輸出與退出碼。

它們都叫測試，卻像是不同尺寸的螺絲，不能拿同一把工具硬鎖。於是，/test 在開始寫測試前，會先把檔案歸類。分類看似只是前置作業，實際上卻會決定測試驗證的是對外行為，還是脆弱的實作細節。

先看路徑與檔名，再決定測試層級

分類方式刻意保持便宜：先只看檔案路徑與檔名，不急著打開每個檔案。因為在這個階段，命名慣例通常已經提供足夠線索。對應規則如下：

路徑或檔名出現的訊號類別對應的測試策略
*.tsx、*.jsx、*.vue、*.svelte，且不在 route 或 page 路徑下component元件測試：render、互動，以及斷言 DOM 與 ARIA
app/**/page.*、pages/**（不含 pages/api）、*Screen.*、*View.*page/flowE2E 候選，另外搭配各零件的元件測試
app/**/route.*、pages/api/**、*.controller.*、*.handler.*、*.resolver.*、actions.*api/server整合測試：呼叫 handler，只在邊界 mock
一般的 .ts、.js、.py、.go、.rs，以及 utils、hooks、services、domain logiclogic單元測試：輸入到輸出、邊界，以及錯誤情況
cli.*、bin/**、*.command.*、cmd/**cli整合測試：實際呼叫這個指令

如果檔案名稱太模糊，光看路徑無法判斷，就先暫時標成 logic。等到後續真正讀取檔案內容時，再更新分類。這樣做的目的，是讓初步分類維持低成本，不必為了分組而先把所有檔案讀完。

分類時還會記下一個開關：只要清單中出現任何 page/flow 檔案，就把 E2E_RELEVANT 設為 yes。後續是否需要詢問 E2E 工具，就由這個開關決定。

變更超過 15 個檔案：先處理高風險區域

如果這次變更超過 15 個原始檔，/test 不會硬把所有測試一次寫完。大型 diff 一口氣處理，容易讓品質往下掉，也容易漏掉真正重要的地方。

它會先按照類別排優先順序，從 logic 與 api/server 開始。這兩類通常風險較高，而且可以用相對低的成本建立扎實的測試覆蓋。接著，它會用決策面板詢問你要怎麼聚焦：

  • 先完成 logic 與 API 測試，其餘標記為尚未覆蓋。
  • 拆成好幾批，最後全部測完。
  • 由你直接指定最重要的檔案或目錄。

這裡的重點不是少測，而是先把有限的注意力放在風險最高、最值得先驗證的地方。

monorepo：先按最近的 package.json 分組

在 monorepo 裡，檔案可能分屬不同的專案。它會為每個檔案一路往上尋找最近的 package.json，再把同一個 root 下的檔案歸成一組。

這樣分組是有原因的：不同 root 可能使用不同的框架、套件管理員與測試目錄。因此，測試工具與測試檔案也要分組處理。如果所有檔案往上追查後都指向同一個 root，這種常見情況就直接當成單一專案處理。

五類檔案，五種下手方式

分類完成後，每一類會採用自己的策略。差別可以濃縮成兩個問題：應該驗證到哪一層？哪些外部依賴可以暫時假裝？

logic：用真實輸入，檢查真實輸出

純邏輯檔案通常最好測，也最適合測得完整。直接用真實輸入呼叫函式，斷言輸出，再補上邊界條件與錯誤情況。

這裡有一條重要紀律：只 mock 真正的外部邊界，例如網路、檔案系統、時鐘與隨機數。屬於自己程式的邏輯不要 mock。否則測試很可能只是在確認：「我設定的假物件，確實回傳了我設定好的值。」這種測試看起來有覆蓋率，實際上卻可能是假綠。

component：測使用者看見與操作的結果

元件測試應該 render 元件，再透過使用者會做的事件與它互動。接著，斷言使用者真正感知得到的結果，例如：

  • 畫面上是否出現指定文字。
  • 元素是否具有正確的角色。
  • 按鈕是否被設為 disabled。
  • 某個區塊是否已經展開。
  • 無障礙相關行為是否符合預期。

相反地，不要斷言元件內部的 state，也不要把 class 名稱當成測試契約。這些都屬於實作細節，正常的重構不應該讓測試變紅；如果測試綁得太緊，最後就會變成「改了 class 就壞，但真正的互動壞了卻不會紅」的假綠測試。

page/flow：有 E2E 就走真實瀏覽器，沒有就退回元件層

如果專案已設定 E2E 工具，就針對主要路徑寫一條真實瀏覽器流程：載入頁面、進行操作，再斷言結果；另外至少補上一條失敗路徑。

頁面裡較複雜的零件，仍然要另外用元件測試覆蓋。E2E 能最接近真實使用情境，但成本也最高，因此不該把所有細節都塞進 E2E。

如果專案沒有 E2E 工具，就在元件層覆蓋整個頁面。這是務實的退回方案：保留主要互動的驗證，同時避免為了測試而強行引入另一套工具。

api/server：用代表性請求打 handler，只在邊界 mock

API 與 server 檔案採用整合測試。用有代表性的請求呼叫 handler、route 或 action，然後檢查回應的狀態、資料形狀與錯誤結果。

錯誤情況至少要包括壞輸入、未授權與找不到資源。資料庫與外部服務只在邊界那一層 mock，其餘流程照真的執行。這樣才能驗證各部分接在一起時是否真的能工作，而不是只驗證一堆互相配合的假物件。

cli：真的執行指令，檢查它留下的結果

命令列工具要用參數實際執行，並斷言標準輸出、退出碼與副作用。至少也要涵蓋一條參數不正確的路徑。

CLI 的價值就在於它會被當成一個程式執行，所以測試也應該用同樣的方式對待它，而不是只把某個內部函式單獨拿出來測。

分類錯了，測試可能看起來正常卻沒有保護力

分類的重要性，在於它會決定測試應該對齊哪一層的行為。

例如，把 React 元件錯當成 logic 來測，測試可能會直接斷言內部 state。結果是元件只要改個 class 名稱，測試就變紅；但真正的使用者互動壞掉時，測試反而可能沒有反應。這就是假綠測試：報告看起來通過，實際上沒有測到使用者在意的行為。

正確分類不是為了讓檔案看起來整齊，而是為了讓驗證層級對準檔案真正對外承諾的行為。

小結

/test 會先根據路徑與檔名，把變更檔案分成五類：component、page/flow、api/server、logic、cli。每一類都有對應的測試策略，範圍從純單元測試到真實瀏覽器流程。分類錯了，測試就可能綁住實作細節，最後產生假綠。變更超過 15 個檔案時，先處理風險高且容易扎實驗證的 logic 與 api/server；monorepo 則依最近的 package.json 分組處理。

現在你已經知道每個檔案該用哪一種測試策略。下一個決定是：要用哪一套工具執行這些測試？這個選擇會記錄在 test-preferences.json。下一節將進一步說明這個檔案，以及專案刻意不安裝測試 runner 時，流程會變成什麼樣子。
