寫測試的紀律：驗證行為、不改原碼，還要追得回驗收條件

Step 4/5 · /test：為變更寫回歸測試

學習目標

這一節要把 /test 的寫作規則變成一份可以直接執行的清單：只修改測試、不碰應用程式原始碼；延伸既有測試、不另開平行版本；依照優先順序，從 happy path 一路補到無障礙案例；最後，讓每個測試都能追溯到規格中的驗收條件。

前言：工具都備好了，現在差的是下筆的規矩

前面三節已經處理好外圍工作：範圍由 git 決定，每個檔案完成分類，工具與偏好也記在 test-preferences.json。現在輪到真正寫測試。

測試寫得好不好，通常不只取決於你會多少語法，而在於幾條紀律有沒有守住。測試變紅時，你會不會忍不住修改原始碼，把它硬改到通過？遇到既有測試檔，你會在原檔補案例，還是另開一個平行檔案？看到登入流程時，你有沒有想到「未授權存取」？

這些選擇，比多會用幾個 matcher 更能決定測試最後是可靠的防護網，還是一盞看起來亮著、其實沒有接電的燈。以下把寫測試時的規則整理成可直接照做的清單。

誰負責寫：主執行緒下筆，讀檔可以外包

寫測試和讀檔是兩件事。真正下筆的工作由主執行緒完成，不另外派一個寫手來產生測試。這是刻意的安排：測試必須貼著這次變更的真實脈絡，由主執行緒寫，最能保持判斷前後一致。

比較昂貴的是閱讀那些被測檔案。如果檔案很多，或程式碼不熟，可以把閱讀工作交給唯讀的 scout 子代理，請它回傳一份精簡的檔案地圖。主執行緒再依照這份地圖判斷並寫測試。

外包的是閱讀，不是決策。這個界線很重要：子代理可以幫忙整理「有哪些檔案、哪些公開介面、既有測試放在哪裡」，但不應代替主執行緒決定要驗證什麼。

時序上也有一個細節：操作模板和規則手冊，應該等到真正要寫測試時才讀取。這能讓前面的 pre-flight 步驟保持輕巧，避免一開始就把所有寫作細節塞進上下文，導致後續判斷變笨。

四條不能破的底線

一、絕對不能改動應用程式原始碼

這是整套規則裡最硬的一條。/test 只寫測試，永遠不會為了讓測試變綠而修改被測程式碼。

如果測試變紅，卻立刻去改原碼讓它通過，那就不再是在驗證行為，而是在粉飾結果。真正發現程式有問題時，正確做法是讓測試保持紅色，並如實記錄問題，而不是把紅燈拆掉。

二、既有測試要延伸，不要複製或覆蓋

建立新測試檔之前，先確認是否已經有測試在覆蓋同一個來源檔案。通常可以找同名的測試後綴檔；它可能放在來源檔旁邊，也可能位於測試目錄下。

如果已經有，就直接編輯原檔，補上缺少的案例，同時保留工程師原本寫的測試。不要為同一個來源檔再開第二個平行測試檔，也不要覆蓋別人的手寫測試。

如果既有測試看起來有錯，或和目前的程式碼互相矛盾，也不要偷偷改成你認為正確的版本。把它記到 NOT_COVERED，註明「既有測試可能過時」，將判斷權交回工程師。

三、設定檔要最小，而且只做附加

一般情況下，你只需要新增或修改測試檔。唯一的例外是：選定的 runner 沒有一份必要的設定就無法執行，而那份設定檔目前不存在。

例如，Vitest 搭配 Testing Library 卻沒有設定檔時，可以建立一份最小設定，指定 jsdom 環境並載入 jest-dom。Playwright 沒有設定檔時，也只能建立執行所需的最小版本。

但既有設定檔永遠不要修改。已經存在的設定代表目前專案的選擇，測試應該配合它。如果真的發生衝突而無法處理，就把問題列入 NOT_COVERED，不要直接動設定檔。

四、安全敏感的程式碼，預設補安全案例

如果範圍裡包含認證、授權、session、付款或個資相關檔案，就應該預設加入安全案例。常見訊號包括檔名或路徑中的 auth、login、session、token、password、permission、role、payment、charge、webhook、checkout。

至少要檢查三類情境：

  • 未授權或被禁止的存取。
  • 憑證缺少、過期或遭到竄改。
  • 機密與敏感欄位不會外洩到回應或 log。

如果有風險無法用測試涵蓋，也要誠實記在 NOT_COVERED，不要假裝它不存在。

覆蓋率的優先順序

測試不是想到哪裡寫到哪裡。對一個剛改動的功能，建議依照以下順序補齊：

順位要覆蓋的內容例子
1Happy path：正常、預期的使用填入有效資料，送出成功
2邊界情況空值、null、零、邊界值、最大長度、unicode
3錯誤狀態壞輸入、依賴失敗、網路錯誤、未授權、找不到
4狀態轉移初始 → 動作 → 預期的新狀態
5無障礙（元件或頁面範圍）鍵盤可達、ARIA 正確、可存取名稱正確

只測「正常情況下會成功」，就像只測一扇門能不能打開，卻完全不測門鎖壞掉、鑰匙錯誤或有人沒有權限時會怎樣。真正容易出事的地方，往往就在 happy path 以外。

讓測試讀起來像文件

不論使用哪套工具，以下規則都通用。測試名稱應該是一個完整句子，例如 returns null when the cart is empty，不要寫成 test3。一個測試只驗證一個概念；多個斷言只有在它們共同描述同一個行為時才合理。

每個測試的身體都依照 arrange、act、assert 三段安排：先準備資料，再執行動作，最後檢查結果。這樣讀者不必在一團程式碼裡猜測「到底做了什麼，又期待什麼」。

測試公開介面，不要測內部實作。斷言應該放在使用者或呼叫端看得到的輸出，不要檢查某個私有方法是否被呼叫。同樣地，不要 mock 你擁有的東西；只在真正的系統邊界上 mock，例如 HTTP、資料庫、檔案系統、時鐘與隨機數。

測試也必須具備確定性：不依賴真實時間、真實網路或其他測試的執行順序。需要時間時就凍結時鐘。共用的 setup 放在 beforeEach 或 fixture 裡並保持精簡，但每個測試的主體仍然要能獨立讀懂。最後，每一個非同步呼叫都必須被 await，不要留下浮動的 promise。

幾套工具的實作慣例

規則相同，但不同工具有各自的寫法。以下整理幾套常見工具的重點。

Vitest 與 Jest：簡單的 mock 分別使用 vi.fn() 或 jest.fn()。模組層級的 mock 放在檔案最上方。計時器相關測試在 beforeEach 開啟 fake timers，並在 afterEach 還原。非同步錯誤使用 rejects.toThrow 斷言。

Testing Library：元素查詢優先使用 getByRole、getByLabelText、getByText，最後才使用 getByTestId。互動使用 userEvent.setup()，不要使用 fireEvent。非同步 render 使用 findByRole，不要用 waitFor 包住 getByRole。斷言應該針對使用者感知到的結果，而不是 class 或內部 state。

Playwright：每個測試都要獨立，setup 放在 beforeEach，teardown 放在 afterEach。元素定位優先使用 getByRole 或 getByLabel，不要依賴 CSS selector。等待斷言成立，不要等待固定時間，也不要寫任意 timeout。響應式頁面要同時測試手機的 375px 與桌面的 1280px。表單流程則依照填寫、送出，再斷言成功或錯誤狀態。

其他語言也有各自的慣例。例如 pytest 使用 fixture 與 parametrize，並用 pytest.raises 斷言錯誤；Go 使用表格式測試與 testify 的 assert.Equal；Rust 將單元測試放在 #[cfg(test)] 模組，整合測試放在 tests/。不論語言為何，核心都一樣：測試要可讀、可重複，而且斷言可觀察的行為。

無障礙案例：元件與頁面都要涵蓋

只要範圍包含元件或頁面，無障礙就應該一起測。至少要檢查以下情況：

  • 每個互動元素都能用 Tab 依合理順序到達。
  • 每個按鈕都有可存取名稱。
  • 每個輸入都有對應的 label。
  • 錯誤訊息透過 aria-describedby 連回對應輸入。
  • modal 開啟時，焦點被鎖在 modal 內；關閉時，焦點回到觸發它的元素。
  • disclosure 觸發器的 aria-expanded 會正確切換。
  • 只有圖示的按鈕，也會向螢幕報讀器暴露文字。

有一件事刻意不放進自動化測試：色彩對比。那是視覺判斷，應交給設計審查，不要硬塞進測試裡製造假綠。

測試放在哪裡

檔案位置要依照偏好檔中的 TEST_DIR 與 FILE_PATTERN，並配合 repo 現有慣例。常見安排有三種：

  • 測試放在來源檔旁邊，例如 login.test.ts 緊鄰 login.ts。
  • 測試鏡射到測試目錄，例如 src/auth/login.ts 對應 tests/auth/login.test.ts。
  • E2E 測試放在工具指定的目錄，並以流程命名，而不是以來源檔名命名。

可追溯：每個測試都要回到驗收條件

如果這次變更有對應的治理規格，測試目標就會清楚很多：每一條測試都要能追溯到規格中的驗收條件。

它會尋找 docs/specs/NNNN-<feature>/。如果旁邊有一份已經將項目解析成 AC-N 編號的 verify.md，就優先讀取這份清單；沒有時，才讀規格中的 Requirements 段落。

讀到驗收條件後，將其中可以自動化、而且具有長期價值的條件，一條一條鎖成自動化測試。每條測試都要標記對應的 AC，例如加入 covers: AC-3 註解，或將 AC-3 放進測試標題。這樣整組測試就像一份可以執行的合約，而不是一堆彼此沒有關係的斷言。

有些驗收條件本質上無法自動化，例如視覺呈現、需要人工判斷的內容，或依賴環境的結果——像是「信真的寄到信箱」。不要假裝這些已經測過。應該把它們記到 NOT_COVERED，寫清楚 AC-N、無法自動化的原因，以及交給 /check verify 的手動步驟。

一個誠實標記為未涵蓋的項目，遠比一條製造假綠的測試有價值。

還要再做一層校準：依照這次變更的切片，判斷哪些行為是真實且耐久的，可以鎖成穩定斷言；哪些只是刻意保留的 scaffolding，例如計畫尚未實作的真後端，或前端暫時使用的假資料。

對後者不要急著斷言尚未要實作的細節，否則測試會綁死在一個本來就預計替換的實作上。

小結

寫測試的底線有四條：絕不修改應用程式原始碼；既有測試只延伸、不覆蓋；設定檔保持最小，而且只做附加；安全敏感的程式碼預設加入安全案例。

覆蓋順序是 happy path、邊界、錯誤、狀態轉移與無障礙。通用規則則包括：測試名稱寫成句子、一個測試驗證一個概念、依照 arrange-act-assert 組織、測公開介面、只在系統邊界 mock，並保持測試具備確定性。

有治理規格時，每個可自動化的驗收條件都要鎖成測試並標記 AC-N；無法自動化的項目則誠實記到 NOT_COVERED，交給 /check verify。

測試寫完後，還有一個實際問題：它到底會不會通過？當它變紅時，你能不能分辨是測試本身寫錯，還是程式真的壞了？最後一段會處理跑測試的迴圈、辨認兩種失敗的方法，以及測試完成後的回報與收尾。
