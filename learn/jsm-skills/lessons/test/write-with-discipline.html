寫測試的紀律：抓行為、不改原碼、可追到驗收條件

Step 4/5 · /test：為變更寫回歸測試

學習目標

能套用 /test 的寫作紀律：只改測試不改原碼、延伸既有測試不重寫、依 coverage 優先序補齊 happy path 到 a11y，並讓每個測試可追到規格的驗收條件。

前言：工具都備好了，差的是下筆的規矩

前面三節把外圍都處理完了：範圍由 git 決定、每個檔案分好類、工具與偏好也記進 test-preferences.json。現在終於要下筆寫測試本身。

有趣的是，測試寫得好不好，差別往往不在你會多少技巧，而在幾條紀律有沒有守住。你有沒有忍不住去改一行原始碼讓測試變綠？遇到既有的測試檔，你是補在裡面，還是另開一個平行的檔案？範圍裡有登入流程，你有沒有想到補上「未授權存取」的案例？這些選擇比語法更決定測試的死活。這一節把寫測試時的規則整理成可以直接照著做的清單。

是誰在寫：主執行緒自己寫，讀檔可以外包

寫測試的動作和讀檔的動作可以分開。實際下筆寫測試的，是主執行緒本身，它不是另外派一個寫手去寫。這是刻意的：測試要貼著這次變更的真實脈絡，交給主執行緒寫最能保持一致。

真正昂貴的部分是「讀那些被測的檔案」。如果這次的檔案很多或很不熟，它可以只把這段閱讀外包給一個唯讀的 scout 子代理，請它回傳一份精簡的檔案地圖，主執行緒再照著地圖寫。外包的只有閱讀，不是判斷。

還有一個時序上的細節：它是在真正要寫的那一刻，才去讀操作模板與規則手冊這兩份文件。這樣做是為了讓前面那些 pre-flight 步驟保持輕巧，不要在一開始就把所有寫作細節塞進上下文。

交戰規則：四條不能破的底線

一、絕對不可以改動應用程式原始碼

這是整套規則裡最硬的一條。/test 只寫測試，它永遠不會為了讓測試通過而去改動被測的程式碼。這一條守住的正是前面說的信條：如果測試一紅你就去改原碼，那你根本沒在驗證任何東西，只是在粉飾。真的發現程式錯了，正確的動作是讓測試紅著、如實記錄，而不是把它改到會過。

二、既有測試：延伸，不要複製或覆蓋

在建立新的測試檔之前，先找有沒有既有的測試已經在覆蓋同一個來源檔案，通常看同名的測試後綴檔，位置可能在來源旁邊或測試目錄底下。如果找到了，就用編輯的方式在裡面補上缺少的案例，並且保留工程師原本寫的那些測試。

不要為同一個來源再開第二個平行的測試檔，也不要覆蓋別人手寫的測試。還有一種情況要特別小心：如果既有測試看起來是錯的、或和現在的程式碼互相矛盾，不要偷偷把它改寫成你認為對的樣子，而是記到 NOT_COVERED，註明「既有測試可能過時」，把判斷權交回工程師手上。

三、設定檔：最小、而且只做附加

你通常只會寫測試檔。唯一的例外是：選定的 runner 如果沒有一份還不存在的設定就無法執行，那才建立最小的一份。例如 Vitest 搭配 Testing Library 卻沒有設定檔時，建一份設好 jsdom 環境與載入 jest-dom 的設定；Playwright 沒有設定檔時，建一份最小的。

但永遠不要修改既有的設定檔。已經有設定就尊重它，讓測試去適應它；如果真的衝突到無法處理，把衝突列進 NOT_COVERED，而不是動手改。

四、安全敏感的程式碼，預設加上安全案例

如果範圍裡有處理認證、授權、session、付款或個資的檔案，它會預設補上安全案例。辨識的訊號像是檔名或路徑裡出現 auth、login、session、token、password、permission、role、payment、charge、webhook、checkout 這些字。

要補的案例有三類：未授權或禁止的存取、缺少或過期或被竄改的憑證、以及機密與敏感欄位不會外洩到回應或 log 裡。如果有風險是你沒辦法用測試涵蓋的，也要老實記到 NOT_COVERED，而不是當作沒看到。

覆蓋率的優先順序

同樣是寫測試，先寫什麼、後寫什麼是有講究的。它建議照這個順序來。

順位要覆蓋的東西例子
1Happy path：正常、預期的使用填入有效資料，送出成功
2邊界情況空值、null、零、邊界值、最大長度、unicode
3錯誤狀態壞輸入、依賴失敗、網路錯誤、未授權、找不到
4狀態轉移初始 → 動作 → 預期的新狀態
5無障礙（元件或頁面範圍）鍵盤可達、ARIA 正確、可存取名正確

一個剛改動過的功能，一組像樣的測試不會只有 happy path。只測「正常情況下會成功」等於沒測到大多數真正會出事的地方。

專家規則：讓測試讀起來像文件

不論用哪一套工具，這些規則是共通的。測試的名稱要是一個句子，例如 returns null when the cart is empty，而不是 test3。一個測試只驗一個概念，多個斷言只有在它們驗證同一個行為時才算合格。每個測試的身體照 arrange、act、assert 三段走。

要測公開介面，不要測內部。你斷言的是可觀察的輸出，不是某個私有方法有沒有被呼叫。同理，不要 mock 你擁有的東西，只在真正的系統邊界上 mock，例如 HTTP、資料庫、檔案系統、時鐘、隨機數。

測試要確定性：不依賴真實時間、不依賴真實網路、不依賴測試之間的執行順序。需要時間的時候就把時鐘凍結。共用的 setup 放在 beforeEach 或 fixture 裡保持精簡，但每個測試的身體還是要能自己讀懂。最後，每一個非同步呼叫都要被 await，不要留浮動的 promise。

幾套工具的細節

規則相同，但實際寫起來各有慣例。以下挑幾套常見的講重點。

Vitest 與 Jest：用 vi.fn() 或 jest.fn() 做簡單的 mock，模組層級的 mock 放在檔案最上面。計時器相關的在 beforeEach 開 fake timers，測完在 afterEach 還原。非同步的錯誤用 rejects.toThrow 來斷言。

Testing Library：查詢元素的優先序是 getByRole、getByLabelText、getByText，最後才是 getByTestId。互動要用 userEvent.setup()，不要用 fireEvent。非同步的 render 用 findByRole，不要用 waitFor 去包 getByRole。斷言的對象是使用者感知到的東西，不是 class 或內部 state。

Playwright：每個測試各自獨立，setup 放 beforeEach、teardown 放 afterEach。優先用 getByRole 或 getByLabel，而不是 CSS selector。要等待的是斷言成立，不是固定的時間；不要寫任意 timeout。響應式的頁面要同時測手機（375px）與桌面（1280px）。表單的流程就是填寫、送出、斷言成功或錯誤狀態。

其他語言也有各自的慣例，例如 pytest 用 fixture 與 parametrize、用 pytest.raises 斷言錯誤；Go 用表格式測試加 testify 的 assert.Equal；Rust 把單元測試放在 #[cfg(test)] 模組、整合測試放 tests/。重點都是同一件事：可讀、可重複、斷言可觀察的行為。

無障礙案例：元件與頁面範圍

只要範圍裡有元件或頁面，無障礙就該一起測。要涵蓋的包含：每個互動元素都能用 Tab 依合理順序到達；每個按鈕都有可存取名稱；每個輸入都有對應的 label；錯誤訊息用 aria-describedby 連回它的輸入；modal 開啟時把焦點鎖在裡面、關閉時把焦點還給觸發它的元素；disclosure 觸發器的 aria-expanded 正確切換；只有圖示的按鈕要對螢幕報讀器暴露文字。

有一件事刻意不測：色彩的對比。那是視覺判斷，交給設計審查，不硬塞進自動化測試裡當成假通過。

測試放哪裡

檔案的位置照偏好檔裡的 TEST_DIR 與 FILE_PATTERN，並且配合 repo 現有的慣例。三種常見安排：放在來源檔旁邊，例如 login.test.ts 緊鄰 login.ts；或鏡射到測試目錄底下，例如 src/auth/login.ts 對應 tests/auth/login.test.ts；E2E 測試放在工具的目錄底下，以流程命名而不是以來源檔名命名。

可追溯：每個測試都應該追得回驗收條件

如果這次變更有對應的治理規格，測試的目標就明確得多：每一條都要能追回規格上的驗收條件。它會去找 docs/specs/NNNN-<feature>/，優先讀旁邊那張已經把項目解析成 AC-N 編號的 verify.md 清單，沒有的話才讀規格的 Requirements 段。

讀到驗收條件後，它把可以自動化的耐久條件，一條一條鎖成自動化測試，並且在每條測試上標記它對應哪個 AC，例如加一行 covers: AC-3 的註解，或把 AC-3 放進測試標題。整組測試因此能追溯回一份合約，而不是各自獨立的斷言。

至於那些本質上無法自動化的驗收條件，例如視覺呈現、需要人工判斷的、或和環境有關的（像是「信真的寄到信箱」），不要假裝測得起來。它會把這些記到 NOT_COVERED，寫成「AC-N，為什麼無法自動化，交給 /check verify 的手動步驟」。誠實標記一個沒測到的項目，遠比給它一條假綠的測試有價值。

還有一層校準。它會用這次的切法來判斷哪些行為對這個切片是耐久、真實的，可以放心鎖成穩定斷言；哪些是刻意的 scaffolding，例如計畫還沒要做的真後端、前端先用假資料撐著。後者就不要去斷言一個計畫根本還沒要做的實作，否則測試會綁死在一個本來就會被換掉的東西上。

小結

寫測試的底線有四條：絕不改動應用程式原始碼、既有測試只延伸不覆蓋、設定檔最小且只做附加、安全敏感程式碼預設加安全案例。覆蓋順序是 happy path、邊界、錯誤、狀態轉移、無障礙。通用規則是名稱成句、一測試一概念、arrange-act-assert、測公開介面、只在系統邊界 mock、保持確定性。有治理規格時，每個可自動化的驗收條件都鎖成一條測試並標上 AC-N，無法自動化的誠實記到 NOT_COVERED，交給 /check verify。

測試寫完了，但它到底會不會過？又或者，它紅了的時候，你分得出是測試自己寫錯，還是程式真的壞了嗎？下一節就是最後一段路：跑測試的迴圈、誠實分辨兩種失敗，以及跑完之後怎麼回報與收尾。
