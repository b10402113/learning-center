/test 的角色：只為這條分支的未提交變更寫回歸測試

Step 1/5 · /test：為變更寫回歸測試

學習目標

完成這一節後，你應該能說清楚 /test 測什麼、不測什麼，也能理解為什麼「測試通過，卻抓不到真正的 bug」比沒有測試更危險。

你也會知道它和 /develop、/check verify、/check review 各自負責哪一段工作。

功能做完了，然後呢？

想像你剛用 /develop 完成一個新功能。你在瀏覽器裡手動點過流程：畫面正常出現、按鈕可以操作、資料也成功寫入。看起來一切沒問題，你準備把變更合併進主線，接著處理下一個功能。

但手動確認只存在於當下。下個月有人修改同一批檔案時，誰會提醒他：「這裡當初是為了修某個 bug 才這樣寫的？」兩週後你自己回來重構，也未必還記得哪一行不能碰。瀏覽器一關，剛才那次確認就只剩模糊的記憶。

/test 要補上的，正是這個缺口。它把「這次改動是否正確」從一次性的手動檢查，變成留在 repo 裡、之後每次都能重跑的回歸測試。

不過，在使用它之前，要先弄清楚它的角色。像是「測試不能修改原始碼」這種看似嚴格的規則，並不是額外限制，而是從它的職責自然推導出來的。

測試範圍由 git 決定，不由你描述

/test 的目標很單純：測試這條分支上已經改動、但還沒提交的程式碼。

它不會先問你「這次想做什麼」，因為測試範圍不是靠口頭描述決定，而是由 git 工作樹直接提供。這也是它和 /scope 最根本的差別：

  • /scope 要問出你想做什麼。
  • /test 只檢查你實際動了什麼。

它會收集所有已追蹤檔案的 staged 與 unstaged 變更，但排除刪除的檔案；同時也會納入沒有被忽略的未追蹤檔案。如果 repo 還沒有任何 commit，則改用已進入索引的變更作為範圍。

取得清單後，它會先排除明顯不適合測試的項目，包括：

  • 測試檔本身
  • 各種設定檔
  • lock 檔與建置產物
  • 樣式檔與只有型別的宣告檔
  • 文件、規格，以及 test-preferences.json

剩下的檔案，才是 /test 要處理的對象。

這個設計也畫出了它的邊界：它只測這次變更，不會順手把整個 repo 重測一遍。範圍刻意保持小，因為它要回答的是「這一改有沒有破壞行為」，不是「整個專案目前健不健康」。

它能寫什麼，又不能碰什麼？

/test 只擁有兩類檔案。

第一類是測試檔，例如 *.test.ts、*.spec.ts、test_*.py、*_test.go。這些是它為變更留下的回歸防線。

第二類是放在專案根目錄的 test-preferences.json。這個檔案記住專案使用哪一套測試工具，讓下次執行時不必重新詢問。

它也有兩塊明確不能進入的地盤：

  • 不寫應用程式碼。
  • 不更新 AGENTS.md 或 CLAUDE.md 這類 context 檔；那是 /sync 的職責。

把地盤劃清楚，產出才會可預期。你不會叫 /test 改功能，也不會在它完成後才發現專案說明被一起改掉。

核心哲學：假綠比沒有測試更危險

整個 skill 最重要的原則是：一個會通過、卻抓不到真 bug 的測試，比根本沒有測試更糟糕。

沒有測試時，你至少知道自己是在裸奔，做變更時會保持警覺。假綠測試卻像一扇看似上鎖的門：它讓你以為有人在把關，放心修改；等到真正出事，才發現那扇門從來沒有鎖上。

因此，/test 應該測的是呼叫者真正依賴的行為，也就是「如果這裡壞掉，誰會受到影響」。它不是為了讓覆蓋率數字變漂亮，才補一些沒有保護力的測試。

這也表示，它不會把切片中「刻意假裝的部分」鎖死成斷言。假設前端目前刻意使用假資料，目的是先讓流程跑通；這時就不該寫一條測試，斷言後端已經真的回傳資料，因為那根本不是這個切片承諾要完成的實作。

測試應該鎖住的是目前真正承諾的行為，而不是把暫時性的 scaffolding 誤認成產品契約。

它在工作流程中的位置

/test 接在 /develop 後面。把幾個相鄰階段放在一起看，分工會比較清楚：

  • /develop：把規格轉成能執行的程式碼。
  • /check verify：真的把應用程式跑起來，確認執行期行為符合規格。
  • /test：把這次變更寫成自動化回歸測試，讓它在未來持續發揮作用。
  • /check review：換另一個模型檢查 diff，進行資深審查。

最後一點很重要：寫碼的模型審查自己，容易忽略自己做過的假設，因此需要換模型來降低盲點。

整套工作流的基調是：除了 /develop 之外，後續步驟都是建議，不是強制關卡。工程師可以自由跳過，done 也是自己宣布的，不是由某個流程把選項鎖死。

實際使用哪個階段，取決於功能的流程等級：

  • Prototype：完成建置後就收尾。
  • Alpha：再執行一次 /check verify。
  • Beta：加入 /test。
  • GA：再加入換模型的審查與文件。

什麼時候直接執行，什麼時候才提問？

/test 不太需要詢問需求，因為範圍早已由 git 決定。當 test-preferences.json 已經存在、指定的測試工具也已安裝，而且確實有未提交檔案時，它會直接開始寫測試。

但有一件事每一輪都一定會問：測試完成後，要不要順便執行測試，還是只把指令交給你，由你自行執行。

這個選擇每次都要重新決定，/test 不會記住上一次的答案。

除此之外，只有以下四種情況它才會提問：

  1. 沒有 test-preferences.json，需要選擇測試框架。
  2. 選定的測試工具尚未安裝。
  3. 完全找不到未提交的變更。
  4. 變更檔案超過 15 個。

其他時候，它會保持安靜，把注意力放在寫出真正有保護力的回歸測試。

小結

/test 為這條分支的未提交變更寫回歸測試，範圍由 git 工作樹決定，不是由工程師描述。它只擁有測試檔與 test-preferences.json，不寫應用程式碼，也不碰 context 檔。

它的核心立場是：會通過卻抓不到 bug 的測試，比沒有測試更糟。因此，測試應該鎖住呼叫者依賴的行為，而不是追求覆蓋率數字，也不應把切片刻意假裝的 scaffolding 鎖成產品行為。

它接在 /develop 之後，並與 /check verify（執行期驗證）、/check review（換模型審查）分工。這是 Beta 以上才會使用的環節，而且每一輪都一定要問你「要不要執行測試」。
