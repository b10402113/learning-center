跑與不跑的差別：分辨測試錯還是程式錯，然後收尾

Step 5/5 · /test：為變更寫回歸測試

學習目標

能在跑測試後誠實分辨「測試寫錯」與「程式真的錯」，把後者留在 BUGS_FOUND 而不弱化斷言，並依 RUN_AFTER 產出正確的回報與 scope 收尾。

前言：測試寫完了，但它到底會不會過？

上一節你已經把測試寫出來，規則也都守住了。現在桌面上剩兩個問題。第一個很簡單：要不要現在把它跑一遍？第二個比較難：如果它紅了，你怎麼知道是測試自己寫錯，還是程式真的壞了？

這兩個問題之所以重要，是因為它們各自藏著一種失敗。/test 要你每次自己決定跑或不跑，因為這件事沒有標準答案，取決於你當下的時間與信心。而當測試紅了卻分不清是哪一種錯，人很容易做出兩種壞選擇：一種是動手改原碼，讓紅色消失；另一種是把斷言放寬，讓它看起來過了。兩者都在欺騙自己。這一節就是最後一段路：怎麼跑、怎麼分辨、怎麼回報與收尾。

每一輪都先問一次：跑，還是不跑？

這是 /test 每一輪都一定會問的問題，即使偏好檔已經存在也一樣。它會告訴你這次要為多少個變更檔案寫測試，然後給你兩條路：跑一遍並修到全綠；或只寫測試，把執行步驟交回你手上。這個選擇每輪重新決定，不會被存起來。因為要不要現在花時間跑，跟這次改動的風險、你的時間預算都有關，不適合寫死成一個長期偏好。

如果你選了「只寫不跑」，它就不會執行任何東西，而是寫完測試後給出一份手動執行說明，讓你自己跑、自己驗證。測試仍然寫得完整，只是把執行的責任交回你身上。

跑的時候：用小輸出，只重跑失敗的

選擇要跑的話，有兩個小技巧能讓過程順利。第一，它會用精簡的 reporter 來跑，例如 Vitest 與 Jest 用 --reporter=dot、Playwright 用 --reporter=line、pytest 與 go test 用 -q。你要看的是通過與失敗的計數，以及失敗案例的名字，不是全部通過的完整輸出。第二，第一次跑完之後，每次重試只跑剛剛失敗的那幾個檔案，而不是整個套件重跑一遍。這樣每一輪的輸出都小、都很快，你的注意力也不會被淹沒。

它從 package root 執行，所有路徑與指令都從那裡算起。

紅掉的時候：兩種失敗，兩種處理

迭代的規則只有三條，但每一條都很關鍵。

第一種：測試自己寫錯了

如果失敗的原因是測試本身有問題，例如 import 錯了、selector 抓錯、期望值寫錯、或少了必要的 setup，那就修測試，然後只重跑那個檔案，重複到這類失敗清空為止。這些是「我寫的測試有 bug」，跟被測的程式無關。

第二種：程式真的錯了

如果失敗的原因是應用程式碼真的違反了它自己的合約或規格，那這正是測試在盡它的職責。這時候不要改原始碼讓它通過，也不要弱化斷言。你要做的是讓這條測試保持紅色，把它記到 BUGS_FOUND 裡，然後繼續往下走。這條規則守的是整套流程的誠信：測試的價值就在於它會在你改壞時叫你，如果一紅你就把它哄睡，那它就不再是測試了。

第三種：停手

當剩下的失敗都已經被歸到 BUGS_FOUND 的真 bug，或者全部都綠了，迭代就結束。

分辨這兩種失敗要誠實。報告的時候也不要把原始的測試輸出整段貼上來，而是摘要成計數加上具體的失敗案例，讓人一眼看得懂。

回報：兩種格式，看你選了跑或不跑

報告的格式跟著你前面的選擇走。如果選了要跑，報告會包含四個區塊：測試寫在哪裡（每個檔案的路徑、類別、測試數、涵蓋摘要，以及是延伸既有還是新建）、執行結果（通過與失敗的計數，以及用的指令）、BUGS_FOUND（每個真 bug 的檔案與行號、哪個斷言失敗、揭露了程式哪裡壞掉；沒有就整段省略）、以及 NOT_COVERED（哪些情境沒涵蓋，以及原因）。

如果選了不跑，報告則由測試清單、手動執行說明（安裝步驟、跑全部、只跑單檔、預期會看到什麼、失敗時怎麼分辨測試缺口與真 bug）、以及 NOT_COVERED 組成。

這裡有一個特別的規矩：如果 BUGS_FOUND 不是空的，報告要把它放在最前面。因為一條正確地在壞掉的程式上失敗的測試，是一個真實的發現，不是該被消音的東西。/test 到這裡仍然不會去改應用程式碼。

收尾：勾 scope、鏡射 spec、絕不自己宣布 done

測試有了結果之後，還要把狀態對回專案的文件。如果這個功能列在 scope 上，而且這一輪測試通過了，它會勾掉 scope 裡那個對應的 Test it 格子，然後提議把這個功能標成 done，例如問你「測試進來而且通過了，要不要標成 done？」。它不會替你按下去，決定權在你。

你同意的話，它才會把狀態設成 done（同時更新 At a glance 表與標題），並把規格裡的 Status 一併鏡射成 Accepted。如果這個規格還是 Assumed 狀態，並不會擋住 done；它會標記「欠 ratification，有空時用 /architect 補」，把選擇權交給你。

反過來說，如果測試失敗、或覆蓋不完整，那個 Test it 格子就保持不打勾，並如實回報，不營造已經完成的假象。

收尾時一定要有一次確認，不能默默帶過：它會明講在每個檔案勾了什麼，例如「Scope：勾了 Test it，狀態變成 done。Spec：狀態變成 Accepted」。如果 scope 上根本找不到對應的那一列，也要說出來，而不是安靜地結束。

功能走到 done 之後，它會建議你在開始下一個功能前先清一次上下文。因為 scope 與 spec 已經把一切記下來了，一個乾淨的新 session 能讓下一個 build 更省、更準。

兩個和 git、和流程等級有關的細節

如果最近的 AGENTS.md 在 Git 段寫著會在整合時自動提交，而且提交不是手動模式，它會提議把這組測試順手提交，用一行像 test(<scope>): … 的訊息加上協作 trailer。它永遠不 push，提交與否、推不推都由你決定。

另外，要知道 /test 屬於哪一關。有效的流程等級以功能自己標的為準，沒標就用專案的預設。Prototype 在 /develop 就收尾、Alpha 在 /check verify 收尾，所以到 Beta 與 GA 才輪到 /test 當收尾者，之後才是換模型的審查。它會尊重你對等級的覆寫，永遠不會自己預設一條固定的流程鏈。

最後一個小地方：這個 skill 在回報完就結束了，它不會去呼叫別的 skill。把結果交給你，就交回你手上。

小結

/test 每一輪都問一次「跑或不跑」，這個選擇不被存起來。跑的時候用精簡 reporter，重試只跑失敗的檔案。失敗分兩種：測試自己寫錯就修測試；程式真的錯就讓它紅著、記到 BUGS_FOUND，絕不改原碼或弱化斷言。報告格式跟著 RUN_AFTER 走，BUGS_FOUND 不空時要放最前面。最後勾 scope 的 Test it、鏡射 spec 為 Accepted，但 done 由工程師宣布，不自己決定；測試通過才建議清理上下文，並可提議提交但永不 push。

你已經把 /test 整條路走完了：從範圍、分類、偏好、寫作紀律，到跑與收尾。把它放回整條工作流來看，它接著 /check verify 的執行期驗證，交出這一條分支的回歸測試，再交給 /check review 做換模型的審查。下一次你自己的專案改動完成時，就可以真的跑一次，體會它怎麼守住「會過，而且真的抓得到 bug」這條線。
