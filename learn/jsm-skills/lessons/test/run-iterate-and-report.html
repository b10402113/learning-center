跑，還是不跑？分辨測試錯誤與程式錯誤，完成最後收尾

Step 5/5 · /test：為變更寫回歸測試

學習目標

完成這一節後，你應該能在測試寫好之後，誠實判斷要不要執行；測試失敗時，也能分辨是測試本身寫錯，還是程式真的違反了合約。遇到真 bug 時，把它留在 BUGS_FOUND，而不是改弱斷言或偷偷修改原始碼讓畫面變綠。最後，再依照 RUN_AFTER 的選擇產出回報，正確完成 scope 與 spec 的收尾。

前言：測試寫好了，紅燈到底代表什麼？

上一節你已經把測試寫出來，也遵守了範圍與覆蓋規則。現在還有兩個關鍵問題：要不要立刻跑一次？如果測試變紅，又怎麼知道是測試寫壞了，還是程式真的有問題？

這兩題看似簡單，卻很容易把流程帶偏。有人看到紅燈就直接改原始碼，直到測試消失；也有人把斷言放寬，讓測試「看起來通過」。這兩種做法都像是把警報器拆掉，而不是修好問題。

/test 的最後一段路，就是保留這份誠實：依當下情況決定跑不跑，跑了就正確解讀結果，最後把測試、bug 與文件狀態交代清楚。

每一輪都重新決定：現在要跑，還是不跑？

/test 每一輪都會重新詢問這個問題，即使偏好檔裡已經有設定也一樣。它會先說明這次要為多少個變更檔案寫測試，接著提供兩個選項：

  • 立刻執行測試，並迭代修正直到所有可修正的項目通過。
  • 只寫測試，不執行，把手動執行與驗證交回你處理。

這個選擇不會被存成長期偏好。要不要現在花時間跑測試，取決於這次改動的風險、目前的時間預算，以及你對變更的信心。它比較像每次出門前重新看一次天氣，而不是把「永遠帶傘」寫死在設定裡。

如果你選擇「只寫不跑」，/test 不會執行任何測試。它仍會把測試完整寫好，並提供手動執行說明，讓你自行驗證結果。

選擇要跑：讓輸出小一點，重跑快一點

如果你選擇執行測試，有兩個做法能避免輸出淹沒真正重要的訊息。

第一，使用精簡的 reporter。例如 Vitest 與 Jest 使用 --reporter=dot，Playwright 使用 --reporter=line，pytest 與 go test 使用 -q。此時最值得看的，是通過與失敗的數量，以及失敗案例的名稱；所有通過案例的完整輸出，通常只會把注意力切碎。

第二，第一次執行後，如果需要重試，只重跑剛才失敗的檔案，不要每次都把整個套件重跑一遍。這能讓每輪回饋更快，也讓你更容易看出「剛才的修改是否真的解決了問題」。

所有指令都會從 package root 執行，因此路徑與指令都以 package root 為基準。

測試變紅時：先分清楚是哪一種失敗

迭代時有三條規則。順序很重要，因為如果一開始就把所有紅燈都當成程式 bug，測試自己的錯誤會被留下；反過來，如果把所有紅燈都修到綠，真正的 bug 又會被掩蓋。

第一種：測試本身寫錯

測試可能有自己的 bug，例如：

  • import 寫錯。
  • selector 抓錯元素。
  • 期望值寫錯。
  • 少了必要的 setup。

這類失敗與被測程式無關。修正測試後，只重跑那個測試檔案，持續處理到這類失敗清空為止。

第二種：程式真的違反合約

如果測試寫法正確，而失敗原因是應用程式碼違反自己的合約或規格，那就是測試發現了真 bug。此時不要修改原始碼讓測試通過，也不要弱化斷言。

正確做法是讓這條測試保持紅色，將問題記錄到 BUGS_FOUND，然後繼續完成其餘流程。測試的價值，就是在程式被改壞時亮起紅燈；如果每次紅燈一亮就把警報關掉，最後留下的只是「假綠測試」——畫面是綠的，問題卻還在。

第三種：到這裡停手

當所有可修正的測試失敗都已處理完，剩下的失敗已確認是真 bug 並記入 BUGS_FOUND，或者所有測試都通過，這一輪迭代就結束。

分辨失敗時要誠實，回報時也要保持可讀。不要把整段原始測試輸出直接貼上來，而應該整理成通過與失敗的計數，再列出具體失敗案例。

回報格式：依照你選擇跑或不跑

回報內容會跟著前面的選擇走。

如果你選擇執行測試，回報包含四個區塊：

  1. 測試寫在哪裡：列出每個檔案的路徑、類別、測試數量、涵蓋摘要，以及這次是延伸既有測試還是新建測試。
  2. 執行結果：列出通過與失敗的數量，以及實際使用的指令。
  3. BUGS_FOUND：針對每個真 bug，列出檔案與行號、失敗的斷言，以及它揭露了程式哪裡出錯。沒有真 bug 時，整段省略。
  4. NOT_COVERED：列出沒有涵蓋的情境，以及沒有涵蓋的原因。

如果你選擇不執行，回報則包含：

  • 測試清單。
  • 手動執行說明，包括安裝步驟、執行全部測試、執行單一檔案、預期看到的結果，以及失敗時如何分辨測試缺口與真 bug。
  • NOT_COVERED。

還有一條優先順序規則：只要 BUGS_FOUND 不為空，就要放在回報最前面。測試在壞掉的程式上正確失敗，是一項真實發現，不是需要藏到報告角落的瑕疵。到這一步，/test 仍然不會替你修改應用程式碼。

收尾：更新 scope 與 spec，但不要自己宣布完成

測試結果確認後，還要把狀態同步回專案文件。

如果這個功能列在 scope 上，而且這一輪測試通過，/test 會勾選 scope 中對應的 Test it 格子，接著提議把功能標記為 done。它可能會詢問：「測試已加入而且通過了，要不要標記為 done？」

這裡的關鍵是「提議」而不是「替你決定」。你同意後，它才會：

  • 把功能狀態設為 done。
  • 更新 At a glance 表與標題。
  • 把規格中的 Status 鏡射為 Accepted。

如果規格目前仍是 Assumed，也不會因此阻擋 done。系統會標記這份規格仍欠 ratification，並提醒你有空時使用 /architect 補上。是否現在處理，仍由你決定。

反過來，如果測試失敗，或覆蓋仍不完整，scope 上的 Test it 就維持未勾選，並如實回報。不能用文件狀態製造「好像完成了」的假象。

收尾時也一定要明確確認實際改了什麼，不能默默結束。例如說明：「Scope：勾選 Test it，狀態變成 done。Spec：狀態變成 Accepted。」如果 scope 找不到對應列，也要明講，而不是安靜地假設一切完成。

功能進入 done 後，/test 會建議你在開始下一個功能前清理上下文。scope 與 spec 已經留下決策與狀態，新的 session 可以少背一些舊內容，讓下一次 build 更省、更準。

與 Git 及流程等級相關的細節

如果最近的 AGENTS.md 在 Git 段落中寫明：整合時會自動提交，而且提交不是手動模式，/test 會提議順手提交這組測試。提交訊息會使用類似 test(<scope>): … 的格式，並加上協作 trailer。

但它永遠不會 push。是否提交、是否推送，都由你決定。

另外，/test 屬於哪一個流程階段，取決於功能本身標示的等級；如果功能沒有標示，就使用專案預設值：

  • Prototype：在 /develop 收尾。
  • Alpha：在 /check verify 收尾。
  • Beta 與 GA：才由 /test 負責收尾。

之後才會進入換模型的審查。若你覆寫了流程等級，/test 會尊重你的設定，不會自行套用一條固定的流程鏈。

最後，這個 skill 在回報完成後就會結束，不會再自動呼叫其他 skill。結果交付給你，下一步也交回你手上。

小結

/test 每一輪都會重新詢問「跑或不跑」，不會把這個選擇存成長期偏好。選擇執行時，使用精簡 reporter，重試只跑失敗的檔案。失敗有兩種：測試自己寫錯，就修測試；程式真的錯，就讓它保持紅色、記入 BUGS_FOUND，絕不修改原碼或弱化斷言。回報格式依 RUN_AFTER 決定；只要 BUGS_FOUND 不為空，就要放在最前面。最後更新 scope 的 Test it，並在獲得同意後把 spec 鏡射為 Accepted。done 由工程師宣布，不由 skill 自行決定；測試通過後才建議清理上下文，也可以提議提交，但永遠不 push。

到這裡，你已經走完 /test 的完整流程：從確認範圍、分類測試、遵守寫作紀律，到執行、辨識失敗與文件收尾。

放回整條工作流來看，它接續 /check verify 的執行期驗證，交出這條分支的回歸測試，再交給 /check review 進行換模型審查。下一次專案改動完成時，你可以實際跑一次這套流程，確認測試不是只會變綠，而是真的能在程式出錯時把問題指出來。
