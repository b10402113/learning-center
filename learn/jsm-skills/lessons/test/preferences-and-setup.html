test-preferences.json：記住測試框架，也記住你選擇不安裝

Step 3/5 · /test：為變更寫回歸測試

學習目標

完成這一節後，你應該能分辨 test-preferences.json 的 framework 與 gate 兩種形狀，知道它們各自適用的情境，也能正確處理第一次執行時的 setup 問答與安裝檢查。

前言：知道要測什麼，接下來要用什麼測？

上一節你已經學會替檔案分類，也知道不同檔案該採用哪一種測試策略。但還少了一個實務上很關鍵的決定：測試到底要交給哪套工具執行？這就像你已經知道要把釘子敲進木板，卻還沒決定手上要拿鐵鎚，還是拿螺絲起子。

Vitest、Jest、pytest、Playwright，各有適合的場景。更麻煩的是，如果每次執行 /test 都重新問一次「這次要用哪個框架」，流程會變得又慢又吵，而且答案通常和上次一樣。

因此，/test 會把這個選擇記在專案根目錄的 test-preferences.json。這一節會說明它如何讀取這個檔案、第一次沒有檔案時會問什麼，以及一個很容易被誤會的情況：有些專案是刻意不安裝測試 runner 的。

讀取偏好檔：關鍵是有沒有指定 tool

讀取偏好檔時，判斷重點不是「檔案存不存在」，而是「檔案裡有沒有指定 tool」。相同都是一個 JSON 檔，裡面的形狀不同，後續動作也會完全不同。

讀到的內容代表的情況接下來的動作
tool 有值一般的 framework 設定載入 tool、additionalTools、e2eTool、testDir、filePattern、packageManager，直接進入安裝檢查
tool 是 null，且 gate 有值專案刻意不用 runner，也就是 GATE_ONLY不寫入套件、不安裝，也不重新詢問；執行 typecheck 或 lint 關卡，並用 /check verify 確認行為
檔案不存在第一次執行，也就是 NO_PREFS進入 setup 模式：偵測技術堆疊、詢問框架、執行安裝檢查，最後儲存偏好
檔案存在，但兩個鍵都沒有，或 JSON 格式錯誤偏好檔格式損壞清楚說明問題，將它視為第一次執行，重新跑 setup 並覆蓋原檔

為什麼不直接用「檔案在不在」來判斷？因為 gate 形狀的檔案同樣存在，也同樣是有效設定；它只是表達了另一種選擇。若把它誤判成「還沒設定測試」，就可能自作主張安裝 runner，做出和專案原意相反的事。

第一次 setup：先辨識既有選擇，再問要不要設定

第一次執行 /test、而專案還沒有偏好檔時，系統會進入 setup 模式，先偵測專案的技術堆疊。

偵測方式很直接：套件管理員會看 lockfile；語言與框架會看 package.json、pyproject.toml、go.mod、Cargo.toml；已安裝的測試工具則會檢查依賴中是否有 vitest、jest、playwright、cypress 或 Testing Library。

如果專案已經使用其他 runner，例如 bun test、node:test、ava 或 deno test，系統會直接沿用既有選擇，不會硬塞另一套工具進來。這裡的原則很簡單：尊重專案已經在用的工具，比追逐「最新推薦」更重要。

Q0：完全沒有測試工具時，不要先假設對方想安裝

如果整個 repo，或 monorepo 裡的某個 package，完全沒有測試工具，/test 不會直接開始安裝。它會先檢查最近的 AGENTS.md 或規格，看看是否已經寫明專案「刻意不使用 runner」。例如，規格可能寫著：「這個專案不用 runner，typecheck 加上 /check verify 就是關卡。」

如果有這項慣例，就直接尊重它：儲存成 gate 形狀，執行 typecheck 作為關卡，並指向 /check verify 確認行為。

如果沒有寫明，才會詢問使用者。選項不是預設安裝，而是三條並列的路：

  • 設定一套測試框架。
  • 不用 runner，改用 typecheck 加上 /check verify。
  • 只做 typecheck。

在 monorepo 中，這個判斷會逐一套用到各個 package。某個 package 沒有測試工具，但兄弟 package 已經有完整測試套件，完全可能是合理的專案設計。

Q1 到 Q3：框架、E2E 與元件測試 addon

如果工程師選擇要設定測試框架，接下來才會進入 Q1。Q1 詢問單元測試與整合測試要使用哪個框架。選項會依偵測到的語言過濾；已經安裝的工具會排在第一個，並標示 (already installed)，作為推薦選項。

常見選項如下：

  • JavaScript 與 TypeScript：通常先列 Vitest，其次是 Jest。
  • Python：pytest 與 unittest。
  • Go：內建的 testing 加上 testify。
  • Rust：使用內建的 cargo test，不需要詢問，直接跳過。

Q2 只有在 E2E_RELEVANT 是 yes 時才會出現。也就是這次變更包含 page 或 flow 檔案，需要考慮端對端測試時，才會詢問是否使用 Playwright、Cypress，或不做 E2E，改在元件層覆蓋頁面行為。Playwright 是推薦選項。

Q3 只會出現在以下條件同時成立時：專案使用 JavaScript 或 TypeScript、偵測到 React、Vue 或 Svelte，而且這次範圍包含 component 或 page/flow 檔案。這一題會詢問是否加入元件測試 addon。

如果這次範圍只有 logic、api 或 cli，Q3 會整題跳過，不會為不相關的測試增加設定負擔。

兩種設定形狀：framework 與 gate 都要完整寫出來

問答完成後，系統會把 test-preferences.json 寫到專案根目錄。根據 Q0 的選擇，這個檔案有兩種合法形狀。

第一種是 framework 形狀，表示專案有一套 runner：

{
  "tool": "vitest",
  "gate": null,
  "additionalTools": ["@testing-library/react"],
  "e2eTool": "playwright",
  "testDir": "beside the source",
  "filePattern": "*.test.ts",
  "packageManager": "npm"
}

第二種是 gate 形狀，表示專案刻意不用 runner：

{
  "tool": null,
  "gate": "typecheck+verify",
  "packageManager": "npm"
}

有一條規則很重要：tool 與 gate 兩個鍵都要寫，不能只留下其中一個。

/test 會讀取 tool，藉此決定是否需要測試套件；/check review 則會讀取 gate，分辨這個專案是「刻意不用 runner」，還是「從來沒有設定過測試」。因此，兩個鍵都缺少的檔案會被視為損壞，而不是有效設定。

換句話說，gate 形狀不是「還沒設定」，而是「已經做出不使用 runner 的決定」。這種設定常見於重視型別安全，並透過 /check verify 手動確認行為的小型專案。辨識出這個選擇，才能避免每次執行 /test 都重新勸專案安裝一套 runner。

安裝檢查：缺工具時先詢問，不要擅自安裝

偏好確定後，系統會檢查選定的工具是否真的已經安裝。

  • JavaScript 與 TypeScript：檢查 node_modules 中是否有對應套件，或 package.json 的 devDependencies 是否列出該套件。
  • Python：檢查 pyproject.toml 或 requirements.txt。
  • Go：檢查 go.sum 是否包含 testify。

如果工具都已經安裝，就直接進入下一步。如果發現缺少工具，系統會先詢問，而不是自行執行安裝。使用者可以選擇：

  • 現在安裝，然後繼續執行。
  • 先不要安裝，把測試完整寫好，等自行安裝後再執行。

如果選擇延後安裝，系統會把安裝狀態記為 deferred，但仍然會寫出完整且正確的測試。差別只在於執行結果會回報「等工具安裝後再跑」。工具尚未安裝，不代表測試內容可以先打折。

小結

/test 會把測試工具記在專案根目錄的 test-preferences.json。判斷重點是有沒有指定 tool，不是檔案是否存在。tool 有值時，直接載入設定並進行安裝檢查；tool 是 null、gate 有值時，代表專案刻意不用 runner，只跑 typecheck 並指向 /check verify；檔案不存在時進入 setup；格式損壞時重新執行 setup 並覆蓋原檔。設定分成 framework 與 gate 兩種形狀，而且 tool 與 gate 兩個鍵都要寫，因為 /test 讀 tool，/check review 讀 gate。第一次 setup 會依序處理 Q0 到 Q3；缺少工具時，先詢問是否安裝，再決定如何繼續。

現在你已經知道要測哪些檔案、每類檔案採用什麼策略，也知道測試由哪套工具執行。下一步就是把這些選擇落實成測試：哪些情況一定要覆蓋、測試如何對應規格，以及如何讓每個測試都能追溯到驗收條件。
