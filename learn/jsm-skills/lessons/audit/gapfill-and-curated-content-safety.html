Gap-fill 與「絕不覆寫」的安全寫入準則

Step 5/5 · /audit：建立 AGENTS.md 與風格底線

學習目標

能跑 Phase 4 的 gap-fill，分辨「缺漏」與「矛盾」，並遵守 provenance 印章、proposed-diff、permission-gated 這三道保護既有內容的規則。

前言：當說明書已經有人寫過

前面三節處理的都是「沒有說明書」的情境：空的、剛 scaffold 的、有碼但沒文件的、只看一個區域的。但真實工作裡，你更常遇到的是第四種：root 說明書早就存在了，只是它跟現在的程式碼對不上。也許是半年前寫的，也許是某個同事隨手補的，也許是上一次 /audit 留下來的。裡面有些內容還是對的，有些已經過期，有些甚至跟程式碼互相矛盾。

這種情況最危險的地方在於：這份文件可能有人用心寫過。如果 /audit 像 Phase 2 那樣重寫一遍，就會把那些精心維護的內容一起抹掉。所以 Phase 4 的難點不是「怎麼寫」，而是「怎麼改才不會傷到不該傷的東西」。這一節要看它的四種判斷，以及撐起整條哲學的三道保護。

Phase 4：gap-fill 的觸發與心態

Phase 4 的觸發條件是：命令沒有指定區域、codebase 存在、而且 root AGENTS.md 已經有了。剛完成舊版 CLAUDE.md 遷移的專案，也會接進這條路線。

它的工作是拿整個 codebase 去對照現有的說明，把真正的漏洞補起來，但方式是保守的。掃描範圍和 Phase 2 一樣大，大型 repo 一樣可以把閱讀外包給唯讀的 scout 子代理，但目標完全不同：Phase 2 是從零建一份說明，Phase 4 是在既有說明上做最小的外科手術。動手寫檔的依然是主線程。

四種 finding：什麼能做、什麼只能問

掃描完成後，所有發現會被歸成四類，每一類的處理方式都不一樣。這張表可以說是整個 Phase 4 的核心。

類別發現了什麼處理方式
(a) root 缺口root 少了一個全局事實：日常指令、技術棧元素、專案級通則，或 scope 裡有但 root 沒寫的 build approach收成 ROOT_GAPS，取得許可才套用
(b) 未記錄的區域一個有獨特慣例或坑的主要區域，卻沒有 nested 文件直接建立 nested 文件（建立不是覆寫，安全）
(c) nested 文件不完整既有的 nested 文件漏了某件現在為真的事回報成 PROPOSED_ADDITIONS，自己不動手改
(d) 矛盾文件寫的跟程式碼、規格或 scope 不符收成 CONTRADICTIONS，交給你決定，絕不自動修

這四類的差別不是隨意的，而是沿著一條「誰擁有這行字」的線切開。(b) 之所以能直接做，是因為它建立一個本來不存在的檔案，不碰任何人的既有內容。(a) 和 (c) 都在動既有檔案，所以要嘛先問，要嘛只提案。(d) 最敏感，因為它牽涉的可能是某人刻意寫下的句子，/audit 頂多只能指出矛盾，不能選邊站。

什麼算是矛盾？例子包括：文件寫的測試框架實際上不是專案在用的；## Stack 跟架構規格打架；## Build approach 跟 scope 標頭不一致；文件寫的某個指令現在根本不存在。矛盾比單純的缺漏嚴重，因為缺漏只是少講，矛盾是講錯，會主動誤導下一個讀到它的人或 AI。面對矛盾，/audit 會用「某份文件說 X，但程式碼或規格顯示 Y」的形式回報，把決定權交回你手上。

還有一個重要的紀律是保守：只標記你有信心、而且耐久的發現。實作細節、TODO 註解、或任何經常變動的東西都不該被標；不確定時，寧可留著不動。

三道保護：印章、提案、許可

「絕不覆寫」不是一句口號，而是由三個機制一起撐起來的。

第一道是 provenance 印章。每一份由 /audit 建立的文件，結尾都會有一行 draft 註記，說明這份草稿是工具產生的、值得人快速看過一遍。這行字的功能是讓之後的執行能在開啟檔案前就知道：這份內容是機器草稿，還是已經被人接手編輯過？判斷規則是這樣的：如果檔案還帶著印章，就可以針對事實做外科手術式的增補，印章留著；如果印章已經不見了，代表有人把它接手了，那之後就只允許新增缺漏的事實、絕不重寫任何一行，任何會改動既有敘述的發現都改走矛盾回報。

這裡要小心一個誤解：印章記錄的是「來源」，不是「授權」。帶著印章不代表 /audit 就可以隨便覆寫；它只是讓後續能分辨內容是誰寫的。那條「不覆寫人工內容」的規則，不管有沒有印章都一樣成立。

第二道是 proposed-diff 格式。當一個檔案已經存在、而 /audit 想補東西時，它不會直接改，而是輸出一段提案，寫清楚：在哪個 ## 區塊下、要加入的確切 markdown、以及為什麼。而且它只提「缺少且真的有用」的東西，不會重寫既有段落。

第三道是 permission-gated 的套用。對既有 root 文件的增補、以及對既有 nested 文件的提案，都不會自動生效，而是走前面看過的那個三選一面板：現在就加（建議）、給我看差異、暫時跳過。你選「現在就加」時，它會照著收集時保存的原文一字不改地套用，不重新措辭。報告結尾則會用幾個固定的「需要你決定」欄位，把 root 缺口、提案、矛盾分開列出，方便你逐項處理。

mirrored fields 在 gap-fill 裡的兩種結局

前一節介紹過的兩個 mirrored fields，到了 Phase 4 有更明確的處理方式，因為它們正好對應到「缺漏」與「矛盾」的分界。

  • 欄位缺漏或還是佔位符：這是 ROOT_GAPS。例如 ## Stack 是空的，或還停在「待填」，就該補上。
  • 欄位與它的來源衝突：這是 CONTRADICTIONS。例如 ## Build approach 跟 scope 標頭講的不一樣，就回報出來，不自己認定誰對。

這個分法再一次說明，同一種資訊只要「沒寫」和「寫錯」就是兩件事，前者可以問你要不要補，後者只能交給你判斷。而無論在哪一種，/audit 都不會在沒有來源的情況下自己編一個值填進去。

完成前的自我檢查

所有 phase 跑完後，還有一個容易被忽略的收尾檢查：如果明明該寫 AGENTS.md 卻沒寫出來（檔案不存在或是空的），/audit 會直接回報失敗並重做，而不是回報一個它根本沒產生的成功。這個看似瑣碎的規則，是整個流程誠實原則的一部分：報告要對得上實際發生的事。

完成時，它會產出一段簡短的報告，先講寫了哪些文件、下一步是什麼，再只列出真正需要你處理的事。需要你的部分會分成幾個欄位：root 缺口、對既有檔案的提案、以及矛盾。沒有內容的欄位就整個省略，不會為了湊版面硬留一行空的。

小結

Phase 4 gap-fill 在 root 已存在時，拿整個 codebase 對照現有說明，做最小的外科手術。四種發現各走各的路：root 缺口收成 ROOT_GAPS 並先問許可；未記錄的區域可以直接建立 nested 文件；既有 nested 文件的不完整回報成 PROPOSED_ADDITIONS；矛盾回報成 CONTRADICTIONS，絕不自動修。三道保護是 provenance 印章（記錄來源而非授權）、proposed-diff 格式，以及 permission-gated 的套用。mirrored fields 缺漏算缺口、衝突算矛盾。整條哲學就是：既有內容可能有人用心寫過，所以只補、只問、不覆寫。

到這裡，整個 /audit 節點就完整了。你現在應該能把它的四條路線講清楚，也知道它為什麼對「不覆寫」這麼執著。往後當你在練習專案上跑 /audit 時，不妨留意一件事：它是整條工作流裡最安靜的一個階段，卻替後面每一站決定了要讀什麼。接下來可以接著讀 /architect，看它如何在這份情境說明之上，把一個模糊請求變成一紙 ratified spec。
