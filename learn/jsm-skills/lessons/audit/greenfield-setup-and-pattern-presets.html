Greenfield：決策面板與四種風格 preset

Step 3/5 · /audit：建立 AGENTS.md 與風格底線

學習目標

能跑完 Phase 1 的決策面板、選定一套 coding-style preset 並把它落成 root AGENTS.md 的 ## Rules，同時處理 ## Git 與 mirrored fields。

前言：唯一一次把慣例談清楚的機會

上一節把路線講完了。如果你手上的專案剛 scaffold，或者規格裡已經決定了技術棧，pre-flight 會把你送進 Phase 1，也就是 greenfield setup。

這條路線和其他三條有一個根本差別：只有它會主動問你一整套問題。whole-repo 和 gap-fill 都是先觀察再補，area 只顧一小塊，唯獨 greenfield 是把所有該定的慣例一次攤開來談。原因很簡單：一個還沒寫下任何真正功能碼的專案，正是決定風格最便宜的時刻。等到幾十個檔案都寫完才回頭統一風格，成本會高得多。

所以這個階段的態度是寧可問滿、不要假設。這一節要看的，就是它到底問什麼、四個風格選項怎麼選，以及這些選擇最後怎麼變成一份可被後續階段讀取的說明書。

Phase 1 的觸發與心法

Phase 1 的觸發條件有兩種：真的從零開始的空白專案，以及剛剛 scaffold 完、技術棧已定但還沒有說明書的專案。後者就是上一節講的 WORKFLOW_SETUP 情境。

有一個很容易搞錯的地方：即使專案裡已經有 manifest 和骨架原始碼，Phase 1 依然把它當成新專案，問答照跑。那些檔案只是 scaffold 的產物，不是累積的成品。判斷標準不是「有沒有檔案」，而是「有沒有一套已經定下來的開發慣例」。

進行方式上，Phase 1 會先把真實的 scaffold 讀過一遍：manifest、設定檔、已安裝的工具。讀完之後再客製化每一個問題。已經被技術棧決定的事情就不問，例如你用的是 JavaScript 這種沒有型別系統的語言，型別嚴格度那題就整題跳過；已經裝好的工具則會排在第一個並標成建議選項。問題的選項也會照真實的語言和框架調整措辭，而不是給一份通用的問卷。

Step 1：兩類決策面板

提問會用「決策面板」的方式進行，每一輪最多四個面板，需要幾輪就問幾輪。每個面板有兩個固定特徵：恰好一個標著「建議」的選項，以及結尾一個自由填寫欄位。面板大致分成兩類。

第一類是架構與程式慣例：

  • 架構風格：四個 preset 任選一個（下一段會介紹）。
  • 型別嚴格度：strict（不用 any、型別完整）／gradual（新程式碼從嚴）／loose。這一題只有有型別的語言才問。
  • 模組與資料夾結構：folder-by-feature（按功能聚集）／by-layer（controller、service、repo 分層）／沿用 scaffold 現有的結構。
  • 其他程式標準（可多選）：公開 API 要有文件、統一的錯誤處理方式、啟動時驗證環境變數、只用具名匯出、命名慣例一致、UI 達到無障礙基本標準、使用 conventional commit 訊息等。

第二類是工具鏈。這裡有一個關鍵設計要記住：/audit 只負責「記錄」選擇，不負責「安裝」。安裝套件、設定檔、pre-commit hook、CI，都是後續 /develop tooling 才做的事。面板只是趁決策還在手上的時候，先把選擇固定下來。

  • Lint 與格式化工具（依技術棧推薦，已安裝的排第一）。
  • 提交前的檢查：lint 加 format 加型別檢查／只做格式化／不設。
  • 測試門檻：單元加整合測試框架／只用型別檢查加手動驗證／測試先行（TDD）。
  • 持續整合：推送時跑基本的檢查／暫時不做／已經有了。
  • Git 整合：讓工作流按功能開分支、里程碑到了就提交（建議多數人用）／自己管 Git。

四種 coding-style preset

架構風格那一題的四個選項，是四套預先寫好的程式慣例。選定之後，只有被選中的那一份會被讀進 context，作為 root AGENTS.md 的 ## Rules 基礎。

Preset核心主張適合什麼
Clean Architecture嚴格分層，領域邏輯不碰框架與 I/O複雜且穩定的業務規則
Functional / Immutable純函式優先，資料不可變，副作用推到邊緣重視可預測與可測試的邏輯
Domain Driven Design顯式建模業務領域，bounded context 與 aggregate複雜且持續演進的業務邏輯
SOLID + OOP經典物件導向與 SOLID 五原則以類別與依賴注入為主的後端

用 Clean Architecture 當例子，看這些慣例具體長什麼樣。它把程式碼分成四層：domain（實體與值物件）、application（使用案例）、infrastructure（資料庫、API、框架）、presentation（UI、controller）。分完層之後，有一條最重要的規則：依賴方向只能由外往內，內層永遠不依賴外層。這樣一來，domain 層可以完全沒有外部匯入，商業規則就不會被框架或資料庫綁死。

這份 preset 還規定了幾個細節：使用案例只是薄薄的協調者，本身不實作業務規則；基礎層負責實作由內層定義的介面（依賴反轉）；domain 和 application 裡不准出現框架或 ORM 的程式碼；跨邊界的溝通一律用 DTO 或普通物件，實體不能外洩到呈現層。最後在測試上，內兩層用單元測試、不需要 mock 基礎設施，基礎設施則對真實系統做整合測試。

如果你選的是其中一個具名 preset，Phase 1 最後會把選擇解析成那個 preset 檔案的絕對路徑，只帶路徑、不把內容貼進對話。如果你選「其他」並自己打了文字，那段原文會被一字不改地放進 ## Rules，不會被改寫或重新詮釋。

Step 3：工具技能掃描與寫檔

慣例問完之後，Phase 1 會跑一輪 Agent Skill 與 MCP server 的掃描。這一步有一個很明確的同意閘門：問是必須的，搜尋不是。在你明確選擇「幫我找」之前，它不會搜尋、不會安裝、不會連線任何東西。它會先說明為什麼值得做（Agent Skill 能讓 AI 學會某個工具的真實慣例，MCP server 能讓它直接接上真實系統而不是靠猜），再給你四個選項：幫我找、我自己列名單、不用並記下拒絕、現在先不用。

搜尋工作會交給一個唯讀的 researcher 子代理在背景跑，而且用便宜快速的模型，不佔用你主要對話的模型。搜尋本身也設了上限（最多五次網路搜尋、八個頁面），結果還會快取三十天，避免每次執行都重複燒錢。找到的候選會分組用面板呈現，一律由你勾選後才安裝，絕不自動裝。被你拒絕過的工具會記在說明書裡，讓之後的執行不再重複推銷。

mirrored fields：## Stack 與 ## Build approach

寫 root AGENTS.md 時，有兩個欄位要特別對待，它們叫 mirrored fields：## Stack 和 ## Build approach。這兩個欄位的內容都不是 /audit 自己編的，而是鏡射自別的地方。

欄位唯一來源來源不存在時
## Stackdocs/specs/ 裡帶 ## Proposed stack 的架構規格沒規格就照程式碼與 manifest，再沒有就留待填
## Build approachscope 標頭的 build approach 那一行留 <TBD, set by /scope>

規則有三條：既不覆寫既有內容；只在欄位是空的或還是佔位符時才填；如果欄位和它的來源互相矛盾，就標記出來並說明是從哪個檔案讀到的，而不是自己選一邊。這樣設計是為了讓 /architect 到 /audit 的交接不受執行順序影響：無論哪個先跑，root 最後都會吸收到已經決定的技術棧。

## Git block 與 monorepo

Git 整合那題的答案會寫成一個小小的 ## Git 區塊，例如 integration: on、branch prefix: feat/、commit: per-milestone，或者單純 integration: off。它是被記錄下來的偏好，讓 /develop 知道怎麼開分支與提交，讓 /document 知道什麼時候該擋 PR。有一點很實際：如果整合選 on，而專案連 git repo 都還不是（git rev-parse 失敗），Phase 1 會當場幫你 git init，讓 repo 從啟用整合的那一刻就存在。

如果 pre-flight 偵測到這是 monorepo，寫法會調整。root 只留跨 workspace 的共通行為：整體的套件管理器與任務執行器工具、共享標準，以及一個指向各 workspace 文件的 ## Context files 區塊。每個 workspace（apps/*、packages/*）則在它自己的根目錄拿到一份輕量 stub，記錄它自己的技術棧與指令。即使某個 workspace 還沒有功能，scaffold 已經宣告了它的技術棧與指令，這些就值得先寫進它自己的文件，讓之後的 /architect 和 /develop 從該 workspace 讀，而不是從 root 猜。

小結

Phase 1 是唯一會主動問一整套慣例的路線，觸發於空白專案或剛 scaffold 完的工作流設定情境。它先用決策面板問架構風格、型別、資料夾結構、程式標準與工具鏈，每個面板恰好一個建議選項；/audit 只記錄不安裝。架構風格從四套 preset 中選一套，選中的慣例成為 ## Rules，選「其他」則原文照用。寫檔時 ## Stack 與 ## Build approach 只鏡射各自來源，## Git 記錄分支與提交偏好，monorepo 則在每個 workspace 各留一份 stub。

Phase 1 處理的是「還沒有慣例可掃」的專案。但更多時候，你面對的是一個已經跑了一段時間、卻沒有說明書的專案。下一節要換個姿態：不再問你，而是先讀完整個 codebase，再判斷哪些知識值得留下、哪些區域需要自己的 nested 文件。
