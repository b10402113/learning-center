pre-flight：先看五個訊號，再決定跑哪個 phase

Step 3/5 · 寫 AGENTS.md context 檔

你要做的決定：這次該跑哪個 phase？

你敲下 /audit，它不會每次都走同一條路。剛 scaffold 完、還沒開始寫功能的新專案，和已經跑了三年、卻沒有文件的舊專案，起點完全不同。

如果分類錯了，原本應該先確認編碼標準的新專案，可能被當成既有程式庫，直接進入掃描；也可能在一個早已有答案的舊專案裡，重新回答「要用哪種測試框架」。

因此，/audit 會先執行一段分類流程，稱為 pre-flight。它收集五個訊號，再依照固定順序選出 Phase 0、1、2、3 或 4。這一節不談怎麼背 phase 名稱，重點是訊號互相衝突時，哪個條件優先。

先比較：pre-flight 會看哪五個訊號？

不要只看檔案數或 commit 數。單一數字很容易誤導你：scaffold 可能一次產生許多檔案，陌生語言則可能讓原始碼檔案數看起來接近零。pre-flight 會把以下五組訊號放在一起判斷。

訊號看什麼可能的值
Context 檔根目錄是否有 AGENTS.md，或只有帶內容的 CLAUDE.mdROOT_EXISTS / ROOT_LEGACY / ROOT_MISSING
原始碼數量跨生態系的原始碼檔數；排除 node_modules、.git、dist 等目錄與 config 檔一個數字
既有專案訊號git log 的歷史深度，以及真實 manifest 是否存在有無歷史與 manifest
Monorepo 訊號workspace 標記，或根目錄附近是否有 apps/*/package.json、packages/*/package.jsonyes / no
Workflow setuproot 檔缺失，但流程已決定技術棧：docs/specs/ 有帶 ## Proposed stack 的架構 spec，或 docs/scope/ 有技術棧相關的 foundation featureWORKFLOW_SETUP 是否觸發

最後一個訊號特別重要。它辨認的是「greenfield 流程已經走到一半」：你已經透過 /scope → /architect 決定技術棧，也完成 scaffold，只是還沒寫下編碼標準。

這時專案可能已經有 manifest、原始碼，甚至有 commit，但它其實還是 greenfield，不是成熟的既有專案。

再比較：五個 phase 各自對應什麼情況？

收集完訊號後，從表格最上方開始比對。這不是隨便挑的，上面的條件會先攔截後面的。

條件應該跑的 phase
有給 area 路徑參數，例如 /audit src/authPhase 3（area 掃描）
ROOT_EXISTS，或 ROOT_LEGACY 搬遷完成後Phase 4（gap-fill）
ROOT_MISSING 且 workflow setup 觸發Phase 1（greenfield）；即使已有 manifest 與 scaffold 原始碼也一樣
ROOT_MISSING、沒有 workflow setup、沒有原始碼也沒有 manifestPhase 1（greenfield）
ROOT_MISSING、沒有 workflow setup、有原始碼（≥10 檔或一個 manifest）、至少 2 個 commit，且看得出是真功能程式碼Phase 2（whole-repo 掃描）
ROOT_MISSING、有原始碼但像沒動過的 scaffold，或只有 1 個 commit，或無法分辨新舊Phase 0（停下來問你）

這些 phase 的工作方式也不同：

  • Phase 1 會先用 decision panel 詢問編碼標準與工具，再寫檔。
  • Phase 2 會讀完整個 repository，直接動手寫，不先問你問題。
  • Phase 3 與 Phase 4 會先探索；但要改動既有 root 檔，或搬遷舊的 CLAUDE.md 前，一定先問你。
  • Phase 0 只做一件事：確認這是新專案還是既有程式庫，再交棒給 Phase 1 或 Phase 2。

自己判斷時，先問這幾句

把決策表轉成問題，你就不用靠直覺猜：

  1. 這次有沒有指定 area 路徑，例如 /audit src/auth？有的話，直接走 Phase 3。
  2. 根目錄是否已經有 AGENTS.md，或完成 CLAUDE.md 的搬遷？有的話，走 Phase 4。
  3. root 檔雖然不存在，但 docs/specs/ 或 docs/scope/ 是否顯示 workflow setup 已經決定技術棧？有的話，走 Phase 1。
  4. 如果沒有 workflow setup，原始碼是否真的代表功能，而不是 scaffold 產物？
  5. 是否同時有至少 2 個 commit、足夠的原始碼，以及一個真實 manifest？若都有，才可能走 Phase 2。
  6. 如果仍然分不清這是新專案還是舊程式庫，是否應該停下來問？是，走 Phase 0。

反例：為什麼 workflow setup 會壓過原始碼數量？

假設你剛用 /architect 決定技術棧，並 scaffold 出一個 Next.js 專案。現在目錄裡有三十幾個原始碼檔、一個 manifest，還有一個 commit。

如果只看「原始碼數量 ≥ 10、有 manifest、有 commit」，它看起來像既有專案，分類結果就可能變成 Phase 2：默默掃描整個 repository，直接寫檔，也不問你編碼標準。

但這個判斷是錯的。那些檔案只是 scaffold 產物，專案仍處於 greenfield 階段。原始碼數量在這裡很容易騙人，看起來像 brownfield，實際上卻沒有成熟的既有慣例可沿用。

因此，只要 root 檔缺失，而 workflow setup 已經顯示技術棧被決定，就直接判為 Phase 1。真正該跑 Phase 2 的既有專案，必須同時具備三件事：

  • 真功能程式碼；
  • 真實的專案歷史；
  • 沒有正在進行的 workflow setup。

如果專案卡在中間、怎麼看都不確定，pre-flight 不會賭一把。它會落到 Phase 0 問你。判斷原則很簡單：可能是 greenfield 的專案，絕不預設成 brownfield。因為誤判後會跳過編碼標準的提問，而這個遺漏最難補回來。

另一個反例：Monorepo 不會改變 phase，但會改變文件邊界

Monorepo 訊號是 yes 時，分類結果不變，變的是後續文件要放在哪裡。

root 文件只放整個 monorepo 共用的內容，例如 workspace 工具鏈、共享慣例，以及指向各 workspace 的 ## Context files。每個 workspace，例如 apps/web、packages/api，都算是第一級 area，主要文件放在自己的根目錄，例如 packages/api/AGENTS.md，而不是埋在更深的子資料夾。

whole-repo 那一輪不會深入掃描每個 workspace，只會依 manifest 為每個 workspace 建立一份輕量 stub。完整的慣例與踩雷點，等之後執行 /audit packages/api（Phase 3），或第一次在該 workspace 開發時再補。

如果發現某個 workspace 的文件被放在不該放的深處，系統會先問你：要把它移到 workspace 根目錄，還是保留巢狀文件，並在根目錄另外建立一份。這種搬動不會自行決定。

當場可用的決策規則

先收五個訊號，再從上到下比對：有 area 參數走 Phase 3；root 文件存在走 Phase 4；root 不存在但 workflow setup 觸發，或完全沒有程式碼與 manifest，走 Phase 1；有真功能程式碼、真實歷史且沒有 workflow setup，走 Phase 2；剩下分不清的情況走 Phase 0 問你。workflow setup 優先於原始碼數量，因為 scaffold 會讓新專案偽裝成舊專案。疑似 greenfield，絕不預設成 brownfield。

如果是 Monorepo，phase 判斷不變，但文件邊界要改成「root 共用規則，加上每個 workspace 一份 stub」。深入某個 workspace 的慣例，留到 Phase 3。

分類完成後，下一步就是進入 greenfield 專案的 Phase 1 setup：先確認標準，再寫出第一份 root AGENTS.md。
