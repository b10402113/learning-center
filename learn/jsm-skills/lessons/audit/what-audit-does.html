/audit 是什麼：把 durable context 寫進 AGENTS.md

Step 1/5 · 寫 AGENTS.md context 檔

為什麼每個 session 都要重新問一次？

你可能遇過這個畫面：開一個全新的對話，請 AI 幫你在專案裡加功能，結果它先問：「你們用哪個套件管理器？測試怎麼跑？這個資料夾有什麼慣例？」你才剛回答完，下一個 session 或另一個工具又重新問一遍。

問題不一定是 AI 記性不好，而是「這個專案怎麼運作」的知識沒有被寫下來。它只留在你的腦中，或留在很快就會被清掉的對話裡。

/audit 解決的就是這個缺口：把散落在對話中的專案背景知識整理成檔案，讓後續的 skill 與 AI 工具都能讀到同一份事實。它不碰功能、不寫規格，只負責建立 context 的固定落點。

學習目標

看完這一節，你應該能說出三件事：/audit 為什麼存在、為什麼 durable context 只寫進 AGENTS.md 而 CLAUDE.md 只是指標，以及它明確不碰哪三種檔案。

/audit 在整條流程裡的位置

每個 skill 開始工作前，都需要知道一組相同的事實：專案使用什麼語言與框架、日常要執行哪些指令，以及有哪些不能踩的慣例。

如果這些資訊只散在對話裡，這個 skill 問一次，那個 skill 再問一次，既浪費時間，也容易漏掉關鍵內容。/audit 會把它們集中寫成 context 檔，放進專案裡。後面的 skill 直接讀檔案，不必重新盤問你。

它需要處理三種專案狀態：

  • greenfield：還沒有真正的功能程式碼，通常剛完成 scaffold。
  • 已有程式碼，但完全沒有 context 檔。
  • 已有部分 context 檔，還需要補齊。

三種狀態會進入不同的 phase，但最後產出的檔案組合相同：AGENTS.md，以及旁邊作為指標的 CLAUDE.md。

為什麼正式內容放在 AGENTS.md？

專案知識需要有一個，而且只能有一個正式的家。對 /audit 來說，這個家就是 AGENTS.md。

檔名刻意保持工具中立。讀取它的可能不只是 Claude Code，也可能是 Codex、Cursor 或其他 AI 工具。把內容放在共用的檔案裡，專案就不會被綁死在某一個工具上。

那 CLAUDE.md 做什麼？它只是一個入口指標。Claude Code 習慣先找 CLAUDE.md，所以這個檔案不放專案知識，而是告訴 Claude Code：「真正的內容在隔壁。」

# CLAUDE.md

This project's context for all AI tools lives in [AGENTS.md](./AGENTS.md).
Claude Code loads it via the import below:

@AGENTS.md

最後一行 @AGENTS.md 是關鍵。Claude Code 讀到它時，會把隔壁的 AGENTS.md 匯入，因此寫在 AGENTS.md 的內容，Claude Code 一樣看得到。其他工具則可以直接讀取 AGENTS.md。

為什麼不能把內容複製到 CLAUDE.md？

因為同一份知識一旦存在兩個地方，就像同一張地圖被畫成兩份，早晚會出現不同版本。

例如，你更新了 AGENTS.md 裡的測試指令，卻忘了同步修改 CLAUDE.md。兩個檔案很快就會互相矛盾，而讀者也不知道該相信哪一份。

使用指標後，知識只有一份。改動 AGENTS.md，所有透過指標讀取它的工具都會看到最新內容。這就是 CLAUDE.md 只能當入口、不能複製正文的原因。

不覆寫既有內容，只補缺少的洞

AGENTS.md 可能是你手寫的，也可能是其他工具建立的。因此 /audit 有一條硬規則：永遠不覆寫既有的 AGENTS.md。

它只會在檔案不存在時建立新檔，或在確認後謹慎補上缺少的事實。/audit 是在整理專案記憶，不是取得權限後重寫整本記憶。

為了讓後續執行知道哪些內容是工具整理的、哪些內容是人修改的，每個由 /audit 建立的 AGENTS.md 結尾都會帶有 provenance（來源標記）。它會說明這份內容是由 /audit 從 repo 草擬出來，值得人工檢查。

如果有人改過其中某一行，這個標記也提醒後續執行要保守處理，而不是直接把人工修改覆蓋掉。

舊的 CLAUDE.md 也不能直接丟掉

如果 repo 裡有一份有內容、但還沒有 AGENTS.md 的舊 CLAUDE.md，/audit 不會默默刪除或取代它。

它會先詢問你。得到同意後，才把舊內容原封不動搬進新的 AGENTS.md，再把 CLAUDE.md 改成指標。

已經好好寫下的內容，不會因為執行一次工具就消失。

它刻意不碰的三種檔案

一條 pipeline 裡，每個 skill 都有自己的責任邊界。/audit 的邊界很清楚：

  • 不建立 spec，因為那是 /architect 的責任。
  • 不維護功能完成後的檔案更新，因為那是 /sync 的責任。
  • 不撰寫功能範圍，因為那屬於 /scope 的 docs/scope/。

所以，/audit 跑完後，應該多出的只有 AGENTS.md 與作為指標的 CLAUDE.md。它不會另外產生計畫或規格。

這不是少做事，而是把檔案的擁有權固定下來：誰建立、誰讀取、誰修改，都有明確答案。檔案才不會在幾個月後變成多人共同維護、卻沒有人真正負責的一團內容。這也接上前一課談到的「狀態在檔案」：狀態要能交接，就必須有固定的檔案與 owner。

把這個觀念掛回流程裡

/audit 是 context 的起點。它把「這個專案怎麼運作」寫成一組檔案，讓後續每個 skill 與工具讀同一份事實，而不是各自重新提問。正式內容只放在工具中立的 AGENTS.md；CLAUDE.md 只是一行匯入指標，絕不重複內容。既有的 AGENTS.md 永不覆寫，只補缺少的資訊；舊 CLAUDE.md 有內容時，則先詢問再搬移。它不寫 spec、不寫計畫，也不碰 scope。

因此，/audit 的位置可以這樣記：它先替整條流程建立共用背景，讓後面的 skill 有同一塊地面可以站。知道它的責任與邊界後，下一個問題就是：這份 AGENTS.md 實際長什麼樣子？root 與巢狀文件各有哪些段落？為什麼 root 不能寫太多？下一節會把兩個模板攤開來看。
