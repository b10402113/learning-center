跑完 greenfield setup：定下標準，寫出 root AGENTS.md

Step 4/5 · 寫 AGENTS.md context 檔

先確認目標與前置條件

這一節要完成 Phase 1：在剛 scaffold 完的 greenfield 專案中，讀取既有 spec 與 scope，用 decision panel 定下編碼標準和工具，最後產生 root AGENTS.md 與旁邊的 CLAUDE.md 指標。

開始前，請確認三件事：技術棧已經由 spec 決定、root AGENTS.md 尚不存在，而且你知道目前所在的專案根目錄。你已經用 /scope 規劃、用 /architect 決定技術棧，也完成 scaffold；現在還沒開始寫真正的功能，正是把團隊慣例寫下來的時機。

Step 1：先做最小探索

先讀專案，再問問題。工具會列出根目錄一到兩層的檔案，跳過 .git；接著讀 manifest，確認語言與套件管理器。

然後到 docs/specs/ 找含有 ## Proposed stack 的架構 spec。若找到，這個 stack 就是已決定的事實，直接放進之後的 ## Stack，不再重問，也不會違背它。

接著查看 docs/scope/，或不存在時查看 .workflow/scope/ 的開頭。若其中記錄了 build approach，就原封不動寫入 ## Build approach；若沒有，先留下佔位符：

**Build approach:** <TBD, set by /scope>

這一步是先分辨哪些決定已經存在。否則很容易問出「你們用 TypeScript，那型別要多嚴格？」這種答案其實早已被既有技術棧限制的問題。

Step 2：用 decision panel 定下標準

探索完成後，才開始提問。decision panel 會分輪提問，每輪最多四題，直到所有必要決定都完成。每題只有一個選項會標成 (recommended)，並保留一個自由輸入欄位。

題目會根據實際 scaffold、語言與框架調整。已由技術棧決定的項目會跳過；已安裝的工具會優先列為推薦。這裡是整個專案第一次、也是主要一次，把編碼慣例和工具選擇定下來。

第一類問題是架構與程式碼風格。預設選項如下：

風格一句話適合
Clean Architecture嚴格分層，領域邏輯不碰框架與 I/O複雜商業規則
Functional / Immutable純函式、不可變資料，將副作用推到邊緣好測試、可組合
Domain Driven Design以 bounded context、aggregate、領域事件建模複雜且會演進的業務邏輯
SOLID + OOP單一職責、介面與依賴注入經典物件導向設計

這時不會把四個風格檔全部讀進 context。它們一開始只是選項；等你選定後，寫檔時才讀取對應的風格檔。

接著會詢問型別嚴格度（若語言有型別系統）、模組與資料夾結構，以及可多選的額外標準，例如：

  • 公開 API 必須有文件
  • 使用一致的錯誤處理模式
  • 啟動時驗證環境變數
  • 只使用具名匯出
  • 採用一致的命名慣例
  • UI 達到 WCAG AA
  • 使用 conventional commit 訊息

Step 3：定下工具與 Git 策略

第二類問題是工具，包括 lint 與 format、commit 前檢查、測試閘門、push 時是否執行 CI，以及 git 整合。

要分清楚兩個責任：/audit 只記錄選擇，不負責安裝；真正安裝套件、寫設定、建立 pre-commit hook 和 CI 的，是後續的 /develop tooling 子任務。

Git 整合也有明確分支。若選 on，會記下類似以下的 ## Git 區塊：

## Git

- integration: on
- branch prefix: feat/
- commit: per-milestone

若此時還不是 git repo，且 git rev-parse 失敗，工具會直接執行 git init，並提議把 scaffold 與文件做成初始 commit。這樣 repo 從啟用整合的那一刻就存在了。

若選 off，則永遠不會自動初始化 git，後續完全由你管理。無論選哪個選項，push 與開 PR 都會再向你確認一次。

Step 4：先取得同意，再探勘工具

工具探勘有一個硬性同意閘門：提問是必要的，搜尋不是。在你做出選擇以前，不會搜尋、抓取、安裝或啟動任何工具。

decision panel 會提供四個選項：

  1. 幫我找
  2. 我自己指名
  3. 不用，並記下拒絕
  4. 現在先不要

只有第一個選項會真的搜尋。找到候選後，也只會列出結果，絕不自動安裝。最後，已安裝的 skill 會逐條記進 AGENTS.md；被拒絕的工具與 MCP server 則以精簡的一行記錄，避免下次又重複推銷。

不要因為 manifest 已經存在，就跳過這些提問。scaffold 只產生 manifest 與原始碼；專案仍是 greenfield，編碼標準還沒有被寫下來。這就是為什麼需要 workflow setup 訊號。

Step 5：解析風格並寫入 context 檔

問題完成後，工具會將你選擇的架構風格解析成檔案路徑。若你選「其他」並自行輸入文字，這段文字會原封不動使用，不會被擅自改寫或重新解釋。

接著它會執行一次工具探勘。完成同意閘門與候選整理後，才讀入寫作指引和被選中的風格檔，開始寫入：

  • root AGENTS.md
  • 旁邊的 CLAUDE.md 指標

寫檔時，內容來源固定如下：

  • ## Stack：從架構 spec 種入
  • ## Build approach：從 scope 開頭種入
  • 其餘規則：依選定的架構風格與額外標準加入

若專案是 monorepo，還會為每個 workspace 建立巢狀文件，將該 workspace 的 stack 與指令寫在自己的文件裡，而不是全部塞進 root。

做完後，確認這些結果

Phase 1 完成後，專案根目錄會多出兩份檔案：

  • root AGENTS.md：包含 Stack、Build approach、Commands、Specs、Rules 等段落，結尾帶有 provenance 標記
  • CLAUDE.md：指向 root context 的指標

最後的報告會告訴你下一步指令。通常會是 scope 清單中第一個尚未勾選的項目，例如 /develop tooling，由它實際安裝剛才選定的工具。

工具安裝刻意留給 /develop，不是讓 /audit 順手完成。/audit 的責任是把決定記錄成所有 skill 都能讀取的 context；安裝則屬於建置階段。兩者分開後，即使工具安裝失敗，決定仍會保留，context 檔也能繼續當一份乾淨的事實來源。

這一節的可驗證結果

Phase 1 的實際順序是：最小探索（讀 manifest、spec、scope）→ 用 decision panel 定下架構風格、型別、結構、額外標準與工具 → 解析風格並通過工具探勘的同意閘門 → 寫 root AGENTS.md 與 CLAUDE.md 指標。Git 選 on 且尚未是 repo 時會執行 git init；選 off 就永不初始化。工具只記錄、不安裝，安裝交給 /develop tooling。

完成後，你真的有一份能被後續 skill 讀取的專案 context，也完成了標準與工具的決定。greenfield setup 到此結束；既有程式碼卻缺少文件的專案，則會走 whole-repo、area 或 gap-fill phase。
