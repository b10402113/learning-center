/audit 在做什麼：AGENTS.md 是唯一正本

Step 1/5 · /audit：建立 AGENTS.md 與風格底線

學習目標

能說出 /audit 在整條工作流裡負責哪一件事、AGENTS.md 與 CLAUDE.md 各自扮演什麼角色，以及它刻意不碰哪些別人的地盤。

前言：每次都要重新自我介紹的專案

想像你開了一個新的小專案。第一次請 AI 幫你加一個功能，你得先花五分鐘解釋：這個專案用 TypeScript、資料夾怎麼分、錯誤處理有沒有統一寫法、命名用 camelCase 還是 snake_case。隔天再請它做另一件事，它又忘光了，你只好再解釋一次。

如果是接手的既有專案更麻煩。你把一個三年沒碰的 repo 丟給 AI，它讀了幾十個檔案後開始猜：這個服務是幹嘛的、測試怎麼跑、哪些目錄碰不得。猜錯了，你就得重來。

這兩個場景其實是同一個問題：專案的知識沒有被固定下來，每次都要靠對話臨時重建。/audit 就是來解這件事的。它把「這個專案是什麼、怎麼寫才對」寫成一份放在 repo 裡的說明書，之後每一個階段、每一種 AI 工具都直接讀它，不必再重新自我介紹。

這一節先建立心智模型：/audit 到底產出什麼、放在哪、誰能改。後面四節才會逐一進入它的四種工作模式。

/audit 是整條流程的情境啟動器

/audit 在整條工作流裡的位置很前面，功能卻非常單純：它只負責寫情境檔，不寫功能、不寫規格。你可以把它想成專案的「新人 onboarding 手冊產生器」。每來一個新工具或新階段，就像來了一個新同事，與其每個人各自摸索，不如先做一本手冊，大家看同一本。

它的產出會變成後續每個 skill 的共同起點。/architect 要設計東西前會讀它，/develop 要動工前會讀它，連你平常在用的 AI 工具也會自動載入它。這代表它的品質會一路往下傳：手冊寫得準，後面每一站都省事；寫得含糊，後面每一站都在猜。

AGENTS.md 是唯一正本，CLAUDE.md 只是指標

這套流程對「專案知識放哪裡」有一個很清楚的規定：耐久的情境知識一律放進 AGENTS.md，其他檔案都只是指向它。

為什麼要這樣分？因為不同的 AI 工具會看不同的檔名。Codex、Cursor 這類工具直接讀 AGENTS.md，而 Claude Code 習慣讀 CLAUDE.md。如果每個工具各放一份內容，早晚會出現三份版本互相打架的情況。所以這裡的做法是：內容只寫在 AGENTS.md，然後在旁邊放一個很薄的 CLAUDE.md，整份檔案的用途就只有一行，把內容轉接給 Claude Code 讀取：

# CLAUDE.md

This project's context for all AI tools lives in [AGENTS.md](./AGENTS.md).
Claude Code loads it via the import below:

@AGENTS.md

@AGENTS.md 這行是 Claude Code 的匯入語法，意思是「把隔壁的 AGENTS.md 內容讀進來」。這樣一來，工具再多，真正的內容也只有一份，永遠不會有兩個版本各說各話。

還有一個常被忽略的細節：這條「CLAUDE.md 只放指標、內容不重複」的規則，無論是 root 還是區域層級都一樣。如果你在某個子目錄也放了 nested 說明，它旁邊同樣只會有一個 pointing 用的 CLAUDE.md。

root 與 nested：一份全局，幾份局部

說明書不是只有一份。這套流程把它分成兩層，各管各的範圍。

層級位置裝什麼
root專案根目錄的 AGENTS.md全局事實：技術棧、常用指令、跨專案的通則，保持精簡
nested<area>/AGENTS.md只給真的有特殊慣例、特殊指令或坑的區域

root 有一條硬規則：維持在約 60 行以內。因為它每次都會被載入，太長就是在每一次對話裡持續燒 context。區域專屬的細節沒必要擠進 root，而是留在那個區域的程式碼旁邊，等到有人動那個區域時才被載入。

當一個區域有了自己的 nested 文件，root 的 ## Context files 區塊會多一行指標，告訴讀者「這裡還有幾份區域說明」。但要小心一個常見的誤解：不是每個資料夾都配一份。只有真的藏著非顯而易見的慣例時才值得，否則只是把 root 想省下的雜訊換個地方堆。

它刻意不碰的四塊地盤

一個 skill 好不好用，常常取決於它「不做什麼」。/audit 的地盤界定得很清楚，有四件事它絕對不碰：

  1. 不建立 spec。 設計決策與技術規格是 /architect 的產物，有自己的目錄與生命週期。
  2. 不維護變更後的文件。 專案改動後要把說明對回現況，那是 /sync 的工作。
  3. 不寫 feature scope。 功能清單與排序屬於 /scope，存在自己的目錄裡。
  4. 不覆寫既有內容。 已經存在的說明書可能是人寫的，/audit 只補、不改。

把界線畫清楚的好處是：你知道遇到哪一類問題該找哪一支 skill，而不是讓每一支都試著包山包海。之後的步驟會看到，這條「只補不改」的規則甚至是整個 /audit 最核心的設計。

小結

/audit 是工作流的情境啟動器，唯一的產出是 AGENTS.md。它是工具中立的唯一正本，CLAUDE.md 只是薄薄的指標，內容不重複。說明書分 root 與 nested 兩層，root 保持精簡，nested 只給真有慣例的區域。它不建 spec、不維護變更後文件、不寫 scope、不覆寫既有內容。

現在你知道 /audit 要產出什麼了。但同一個指令，用在空白專案、剛 scaffold 的專案、還有一個跑了好幾年的老專案上，做法完全不一樣。下一節要講它怎麼靠一串「線上訊號」判斷自己該走哪條路，以及為什麼有時它會寧可停下來問你一句，也不願意自己猜。
