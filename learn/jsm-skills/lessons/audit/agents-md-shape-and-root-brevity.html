AGENTS.md 的形狀：精簡 root、分層巢狀與兩個鏡像欄位

Step 2/5 · 寫 AGENTS.md context 檔

AGENTS.md 是每輪對話載入的專案 context 檔：root 記錄全域事實，巢狀文件記錄特定 area 的規則，## Stack 與 ## Build approach 則分別鏡像架構 spec 與 /scope 的決定。

文件用途

/audit 會產出 AGENTS.md。這份檔案每輪對話開始時整份載入，不是想到才翻的說明書。

每多放一行，後續每次任務都會多付一次載入成本。root 只保留最重要的全域事實，area 細節分層放進巢狀文件。這也決定了兩個鏡像欄位只能從既有來源取得，不能自己填。

Root AGENTS.md

root 文件放在專案根目錄，記的是全域事實。段落順序固定如下：

段落內容
# <Project name>專案名稱，一行。
## StackLanguage / Runtime、Framework、Key dependencies、Package manager。
## Build approach專案預設的建置策略；使用名稱加一行原則。
## Commandsinstall、dev server、build、test 四個指令。
## Specsspec 存放位置與命名格式，例如 docs/specs/NNNN-title.md。
## Rules全專案通用的慣例，最多 5 到 10 條。
## Agent skills已安裝的 skill，一條一個 bullet；沒有時省略整段。
## Context files巢狀文件清單；每新增一份巢狀檔就增加一行。

最小範例如下：

# My App

## Stack

- **Language / Runtime**: TypeScript, Node 20
- **Framework**: Next.js 14
- **Key dependencies**: Prisma, Clerk
- **Package manager**: pnpm

## Build approach

Tracer Bullet: vertical end to end slices, thin but complete through every layer.

## Commands

```bash
pnpm install
pnpm dev
pnpm build
pnpm test
```

## Specs

Stored in `docs/specs/`. Format: `docs/specs/NNNN-title.md`.

## Rules

- Validate env vars at startup.
- Named exports only, no default exports.

## Context files

- [src/auth/AGENTS.md](src/auth/AGENTS.md): auth session handling

root 要維持在約 60 行以內，而且只放全域、跨整個專案的事實。特定 area 的慣例與模組專屬指令，放進那個 area 的巢狀文件。

Nested AGENTS.md

巢狀文件放在有明確 area 的目錄，例如 src/auth/AGENTS.md。只有這個 area 有別處沒有的慣例時才建立，不為每個資料夾各放一份。

段落內容
# <Area name>area 名稱。
## Overview兩三句，說清楚這個 area 的用途，以及為什麼要有它。
## Key files檔案與職責的對照表，一行一個檔案。
## Commands只列與 root 不同的本地指令；相同時省略整段。
## Conventionsarea 專屬的慣例與限制。
## Gotchas容易讓新人踩雷、平常想不到的規則；沒有時省略。
## Agent skills只屬於該 area 的 skill；沒有時省略。
## Related specs已有 spec 時提供連結；沒有時省略。

root 與巢狀文件的模板結尾都帶有 provenance 標記，用來說明文件由工具草擬，仍需人工檢視。

巢狀文件建立後，root 的 ## Context files 要加一行指標，格式固定如下：

- [<area>/AGENTS.md](<area>/AGENTS.md): <one-line description>

Root 的行數限制

root AGENTS.md 約 60 行以內。這是載入成本的限制：root 每輪對話都會完整載入，是固定支出；巢狀文件則只在編輯對應 area 的程式碼時載入。

所以，全域事實放 root，area 細節放巢狀文件。每個資料夾各建一份不符合這個分層規則，因為多數文件平常不會用到。

兩個鏡像欄位

root 的 ## Stack 與 ## Build approach 有指定來源，不能由 /audit 自行產生。

欄位唯一真實來源找不到來源時
## Stackdocs/specs/ 中帶有 ## Proposed stack 的架構 spec。依序讀取程式碼與 manifest；仍沒有資料時寫 <to be filled>。
## Build approach/scope 開頭記錄的 build approach 那一行。寫 <TBD, set by /scope>。

兩個欄位都適用以下規則：

  • 不覆寫已由人員填寫的內容。
  • 只有欄位為空，或仍是佔位符時才填入內容。
  • 欄位與來源不一致時，標出分歧並註明讀取的檔案，不自行選邊。

例如 root 寫著 Jest、spec 寫著 Vitest 時，不能自己挑一個寫進去；應該回報矛盾，交由工程師決定。

## Git

## Git 記錄自行選定的偏好，例如 integration: on、branch prefix: feat/、commit: per-milestone，或單純寫 integration: off。

這不是鏡像欄位，也沒有外部真實來源。未記載時代表 off。後續的 /develop 會讀取這個欄位，決定分支與 commit 怎麼處理。

欄位與層級對照

root AGENTS.md 只放全域事實，維持約 60 行以內；area 細節放進巢狀文件，並只在編輯該 area 時載入。兩種模板的段落順序固定。## Stack 對應架構 spec，## Build approach 對應 /scope 開頭的那一行；兩者只能從來源填入，不能自行發明。與來源衝突時標出分歧，不自行選邊。
