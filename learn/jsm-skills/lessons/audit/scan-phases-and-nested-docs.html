掃描既有 repo：whole-repo 與 area 模式

Step 4/5 · /audit：建立 AGENTS.md 與風格底線

學習目標

能跑 Phase 2 的 whole-repo 掃描與 Phase 3 的 area 掃描，判斷一個區域值不值得寫 nested AGENTS.md，並用 scout 子代理分攤大量閱讀。

前言：有碼，但沒有人說得清它怎麼運作

前面談的都是「還沒有慣例」的專案。但現實裡更常見的，是一個已經跑了好幾年的 codebase，功能都在，卻沒有任何一份文件告訴 AI 它怎麼運作、測試怎麼跑、哪些目錄動了會出事。前一節的決策面板在這裡派不上用場，因為你問「要用哪種架構風格」時，答案早就寫在程式碼裡了，只是沒人把它寫下來。

這一節要看的兩條路線，換了完全不同的姿態：不再問你，而是先去讀。Phase 2 的 whole-repo 掃描面對整個沒有說明的 repo，目標是產出 root 說明書、外加幾個真正需要的區域文件；Phase 3 的 area 掃描則只針對你指定的那一小塊。先從範圍最大的 whole-repo 開始。

Phase 2：whole-repo 掃描

Phase 2 的觸發條件，就是上一節講過的「真 brownfield」：真的功能碼、真的開發歷史，而且沒有一個正在進行中的工作流設定。它和 Phase 1 最大的差別是：Phase 2 不問問題，直接動手。它寫出它判斷該寫的 root 與 nested 文件。

它的探索工作分成兩步。第一步是廣泛瀏覽：把專案樹狀結構看幾層深，跳過 .git、node_modules、dist 這類產生出來或外部的目錄。然後讀幾個關鍵檔案：manifest 或 go.mod 這類檔案看技術棧與依賴；.github/workflows/ 看 CI 與部署方式；主進入點看程式怎麼起跑；測試設定檔看用哪套測試框架；以及所有已經存在的 AGENTS.md。

第二步是從讀到的東西裡萃取真正耐久的知识：技術棧與執行環境、每天都會用到的指令（安裝、啟動、建置、測試）、程式碼裡看得出來的慣例（命名、檔案結構、常用模式），以及一個新人第一週一定會被絆倒的地方。反過來，實作細節、TODO 註解、任何經常變動的東西都要丟掉，因為它們寫進說明書只會誤導後人。

寫的時候有兩個尺寸上的紀律要記住。root 說明書維持在約 60 行以內，只放全局事實；區域專屬的細節全部留給 nested 文件。這裡呼應了第一步的兩層結構：root 要短，nested 才承載局部知識。

哪些區域值得一份 nested 文件

寫 nested 文件最難的不是寫，而是判斷值不值得寫。Phase 2 對每個主要區域逐一判斷，標準大致如下。

值得寫 nested 文件不值得寫
有自己獨特的慣例，跟其他區域不一樣只是個單純的模組，沒有意外之處
有非顯而易見的規則或限制root 已經完整涵蓋了它的內容
有自己專屬的本地指令只要照著 root 的通則就夠了
牽涉外部整合，或藏著會讓人踩雷的坑再拆一份只是把 root 省下的雜訊換地方放

判斷的關鍵字是「非顯而易見」。一份 nested 文件存在的理由，是讓人在動那個區域之前，先知道一些光讀程式碼看不出來的東西。絕對不是每個資料夾都配一份，那會讓說明書從知識變成噪音。每當建立一份 warranted 的 nested 文件，root 的 ## Context files 會多一行指向它的指標；全域事實留在 root，區域知識則貼著區域的程式碼放，等那一塊被編輯時才自動載入，不會平白佔用其他工作的 context。

scout 子代理：把閱讀外包出去

整個 Phase 2 裡最花成本的就是「掃描」這件事，因為它得讀過整個 codebase。針對大型 repo，流程會把純閱讀這一塊外包給一個唯讀的 scout 子代理。

scout 有幾個固定設定。第一，它是唯讀的，只負責掃描、不做任何寫入。第二，它跑在便宜快速的模型上，例如 Claude Code 的 haiku，不會佔用你主要對話的模型。第三，它的任務是回傳一份精簡的「地圖」：技術棧、指令、主要區域、慣例、坑，然後主線程就照著這份地圖來寫文件。反過來，小型的 repo 不需要 scout，主線程直接讀就好，因為外包的溝通成本可能比閱讀本身還高。

這裡有一條不能妥協的分工：真正寫 AGENTS.md 的永遠是主線程，不會交給子代理。子代理只提供原料，不下筆。這樣做的理由是，說明書的取捨需要對全局的理解與判斷，那正是主線程該負責的事，外包出去反而容易產生零碎、互相矛盾的文件。

Phase 2 的 monorepo 變體

如果專案是 monorepo，Phase 2 的寫法會簡化很多：不做逐區判斷，而是每個 workspace 都拿一份輕量 stub。你不需要替每個 apps/*、packages/* 決定它值不值得寫文件，因為每一個 workspace 本身就被視為一個獨立的區域。stub 的內容只有它的技術棧與指令，取自它的 manifest；真正的深入慣例與坑，留到之後有人對那個 workspace 單獨跑 /audit packages/api 時再補。

Phase 3：area 掃描

area 模式是範圍最小的路線，當你在指令後面給了路徑或區域名稱（例如 /audit src/auth）就會觸發。它的目標只有一個：處理那一個區域。

在開始之前，它會先做幾個額外檢查。第一，確認你給的路徑真的存在；不存在就立刻停下來，請你確認路徑後再試，不做任何其他動作。第二，檢查 root 說明書是否存在。如果 root 根本還沒寫，而你也沒有舊版 CLAUDE.md 可遷移，它會先完整跑一遍 whole-repo 掃描，把 root 補起來，再回頭做區域掃描。如果只有一份舊版 root CLAUDE.md，就先跑遷移。第三，確認這個區域是否已經有自己的 AGENTS.md。

檢查完之後，主線程負責寫這個區域的文件，做法跟在 Phase 2 判斷單一區域時一樣。閱讀區域同樣是成本所在，所以大型區域會外包給 scout，小區域則直接讀。如果該區域的 AGENTS.md 之前並不存在但有寫的價值，就建立它，並在 root 的 ## Context files 補上一行指標。這裡有一條要注意的：補指標是對 root 做編輯，不是重新建立 root。

Root gaps：區域看見的 root 缺口

區域掃描還會做一件額外的事：它會比對 root 說明書，看看有沒有什麼是工程師在這個區域工作時需要、卻沒被 root 記下來的事。

哪些算得上缺口？判斷標準收得很緊。只有三類才算：這個區域需要的指令但 root 沒提、這個區域用到的技術棧元素或主要依賴但 root 沒寫、或是某條區域讓它變得明顯的專案級通則（例如「所有資料庫呼叫都要走 repository 層」）。反過來，區域專屬的檔案清單、本地慣例，或任何本來就該放進 nested 文件的東西，都不算 root 缺口，因為它們不屬於 root 的層級。

缺口會用固定的格式收集起來，每一筆都記下「要插入的確切那一行」、「目標是哪個區塊」以及「為什麼」。這個格式刻意保留原文，是為了之後能一字不改地套用。如果掃完沒有任何缺口，就明確記成 ROOT_GAPS: none。

因為你可能已經在 root 花心思寫過東西，這些缺口不會自動被套用，而是用一個三選一的面板交給你決定，其中「現在就加」被標成建議選項：

選項會發生什麼
現在就加（建議）立刻把每一筆缺口照原文套進 root，不重新措辭
給我看差異印出每一筆會加入的內容與目標區塊，但不寫入
暫時跳過root 維持原樣，什麼都不動

不管你選哪一個，最後都會拿到完整報告。這套「先收集、再問、才套用」的流程，就是接下來最後一節要深入的核心：在不確定哪些內容是人工精心寫過的前提下，/audit 要怎麼改檔案才安全。

小結

Phase 2 面對有碼但沒說明的整個 repo，先廣泛瀏覽再萃取耐久知識，root 壓在約 60 行，區域細節分散到少數真正值得的 nested 文件。大型 repo 的閱讀外包給唯讀、便宜模型的 scout，但寫檔永遠由主線程負責。monorepo 則每個 workspace 各給一份 stub。Phase 3 只處理指定區域，先檢查路徑與 root 是否存在，再寫該區域的文件，並把區域看見的 root 缺口收集成 ROOT_GAPS，用三選一交給你決定要不要套用。

到目前為止，四種 phase 已經講了三種。剩下的 Phase 4 看起來最不起眼，卻最考驗紀律：當說明書已經存在、而且可能有人好好寫過，/audit 憑什麼判斷哪一行可以動、哪一行碰不得？下一節會拆開它的三道保護機制，也會把整條「絕不覆寫」的哲學收束起來。
