pre-flight 訊號與 phase 路由

Step 2/5 · /audit：建立 AGENTS.md 與風格底線

學習目標

能從一個 repo 的線上訊號判斷它該走哪個 phase，並解釋為什麼「工作流設定中」這個訊號會蓋過原始碼數量。

前言：同一個指令，四種做法

上一節我們確認了 /audit 的產出就是 AGENTS.md。但如果你真的只在一個空白專案上跑過它，會以為它的流程很單純：問幾個問題、寫一份檔案、結束。實際不然。

把它跑在一個剛 scaffold 出來的專案上，它會用面板問你一整套技術慣例；跑在一個有三年歷史、卻沒有任何說明文件的 repo 上，它反而不問，直接開始掃描；跑在你只說「幫我看一下 src/auth」時，它只處理那個區域；跑在已經有 root 說明書的專案上，它又變成保守的撿漏模式。

四種情境，四套做法。/audit 得先判斷自己站在哪一種，而它的判斷方式，是先用一輪叫做 pre-flight 的前置檢查，收集幾個具體的線上訊號，再照一張路由表決定走哪個 phase。這一節就把這套判斷邏輯拆開來看。

為什麼不能只看檔案數量

最直覺的分類方式大概是數檔案：檔案少就是新專案，檔案多就是老專案。這個做法看起來合理，卻會在最常見的情境上出錯。

想像一個剛剛 scaffold 好的專案。你用框架的初始化指令生出了專案骨架，裡面已經有 package.json、一堆設定檔，還有幾十個範例原始碼。如果只數檔案，它會被歸類成「有碼的既有專案」，於是 /audit 跳過所有技術慣例的提問，直接去掃描。可是這個專案根本沒有真正的功能，工程師心中的慣例也還沒定下來，跳過提問等於放掉最重要的一次設定機會。

反過來也有失準的時候。一個不熟的語言、冷門的副檔名，可能讓檔案計數直接歸零，把一個成熟專案誤判成空白專案。所以這套流程刻意不依賴單一數字，而是同時看幾種不同性質的訊號，互相校正。

pre-flight 收集的五種訊號

前置檢查在真正動手前收集以下幾類資訊。

訊號看什麼可能的值
情境檔狀態根目錄有沒有說明書ROOT_EXISTS / ROOT_LEGACY / ROOT_MISSING
原始碼數量跨常見語言的副檔名，排除 node_modules、dist、build 等一個數字
成熟度git log 的歷史深度、有沒有真正的 manifest（package.json、go.mod 等）有或無
Monorepoworkspace 標記（pnpm-workspace.yaml、turbo.json 等）MONOREPO=yes 或 no
工作流設定中根目錄沒有說明書，但工作流已經決定了技術棧WORKFLOW_SETUP

其中「情境檔狀態」有三種可能。ROOT_EXISTS 是根目錄已經有 AGENTS.md；ROOT_LEGACY 是只有一個有內容的舊版 CLAUDE.md；兩者都沒有則是 ROOT_MISSING。

最後那個 WORKFLOW_SETUP 訊號最需要解釋。它指的是：根目錄雖然還沒有說明書，但工作流後面的階段已經幫你把技術棧決定好了，證據通常是 docs/specs/ 裡有一份帶 ## Proposed stack 的架構規格，或是 docs/scope/ 裡有一個專門決定技術棧的功能項目。

路由表：條件對應到哪個 phase

訊號收齊後，照著下面這張表決定路線。注意它是一條由上往下逐一檢查的順序，不是同時比對。

條件Phase
命令後面有給區域路徑（例如 /audit src/auth）Phase 3（area 掃描）
根目錄已有 AGENTS.md（或遷移後就有了）Phase 4（gap-fill）
沒有說明書，但 WORKFLOW_SETUP 成立Phase 1（greenfield）
沒有說明書，沒有工作流設定，也沒有原始碼與 manifestPhase 1（greenfield）
沒有說明書，沒有工作流設定，但有真功能碼與至少兩次提交Phase 2（whole-repo 掃描）
有碼但看起來是沒動過的骨架，或只有一次提交，或分不清新舊Phase 0（停下來問你）

這張表讀下來的感覺是：越確定的情境走越特定的路，越模糊的情境越會退回中間。最後一列就是保險絲。當 /audit 無法從訊號判斷這個專案到底是新的還是舊的，它不會硬選一個，而是停下來問你一次。

為什麼工作流設定訊號要蓋過原始碼數量

這張表裡最值得玩味的一點是：WORKFLOW_SETUP 明明有原始碼、有 manifest，卻還是走 greenfield。這正是前面「不能只看檔案數」的具體解方。

還記得那條完整的工作流順序嗎？/scope 先想清楚要什麼，/architect 決定技術棧，然後照著技術棧把專案 scaffold 起來，最後才輪到 /audit 把慣例記錄下來。所以當 /audit 到達時，專案確實已經有一堆檔案了，但那些都是剛生出來的骨架，不是累積出來的成品。此時真正的狀態是「新專案還沒定慣例」，唯一的差別是它長得比較像老專案。

工作流設定訊號就是用來認出這件事。它一看到「說明書還沒有，但規格裡已經寫了 Proposed stack」，就知道這是剛 scaffold 完的合作專案，於是照樣走 greenfield，把技術標準問清楚。相對地，真正的 brownfield（Phase 2）有更嚴格的定義：是真的功能碼、真的開發歷史，而且沒有一個正在進行中的工作流設定。

那如果專案的狀態介於兩者之間，怎麼看都不像呢？這種情況會落到 Phase 0。Phase 0 的處理方式是不猜，直接問一次，而且問題會附上一個標著「建議」的選項，依當下哪個訊號比較強來決定建議值：如果是一個有 manifest 但幾乎沒有歷史的骨架，就建議「新專案」；如果是真功能碼加上很深的歷史，就建議「既有專案」。不管你選哪邊，之後的流程就會接上對應的 phase。

舊版 CLAUDE.md 的遷移

路由表外面還有一個特例要交代：ROOT_LEGACY。當根目錄只有一個有內容的舊版 CLAUDE.md，卻沒有 AGENTS.md 時，代表這個專案的知識全都鎖在只被單一工具讀取的檔案裡。這時候 /audit 不會直接動它，而是先問你的許可：「我找到一份有內容的 CLAUDE.md 但沒有 AGENTS.md，我打算把內容搬進新的 AGENTS.md，並把 CLAUDE.md 換成指標，可以嗎？」

你同意的話，它會把內容原封不動搬過去，再把舊檔換成那行指標，之後就當作 Phase 4 繼續跑。你不同意的話，兩個檔都原樣留著，/audit 就跳過遷移。這裡再次看到同一條哲學：既有內容可能是人寫的，任何會動到它的動作，都得先問過。

小結

/audit 靠 pre-flight 收集五類訊號，再照路由表選 phase。它不用單一檔案數判斷，因為 scaffold 會讓新專案看起來像老專案。關鍵是 WORKFLOW_SETUP 這條訊號：只要工作流已經決定技術棧，即使有一堆檔案也照走 greenfield。真的分不清時，它退回 Phase 0 問你一句，而不是硬猜。舊版 CLAUDE.md 的遷移也遵守「先問再動」的原則。

到這裡，你已經知道路線是怎麼選的。接下來三節會逐一走進每一條路線的操作內容。先登場的是最需要你深度參與的那一條：greenfield。它是唯一一次把所有技術慣例一次問清楚的機會，也是四種 coding-style preset 上場的地方。
