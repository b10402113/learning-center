開工流程：分軌、載入規格、探索後動手

Step 2/5 · /develop：依規格實作

學習目標

能跑完閘門後的 Step 1 到 Step 3：用訊號字判斷 UI、Logical 或 Both 軌，載入規格與 AGENTS.md 並做完整性檢查，用唯讀 subagent 隔離探索，從 build plan 續做且只在主線寫碼。

前言：閘門過了，然後呢

上一節你確認了這次要做的事沒有欠著任何決策，可以動手了。但「動手」不是打開編輯器就開始打字。一個有紀律的工程師在寫第一行程式碼之前，會先做三件很樸素的事：搞清楚這次是哪一種工作、把相關的合約與慣例攤開來讀、先把要動的地方摸清楚。

`/develop` 的 Step 1 到 Step 3 就是在做這三件事，順序固定。它先判斷這一刀切下去是畫面、是邏輯，還是兩者都要；接著載入治理這次建置的規格與規範；探索交給一個便宜的唯讀 subagent 去做，把讀取隔離在主線之外；最後才回到主線，從上次停下的地方接著寫。

這裡沒有什麼神奇的技巧，重點是把「憑感覺開工」換成「照順序開工」。後面會碰到幾個很具體的規矩，例如分支策略的優先順序、讀取為什麼要外包，以及發現規格錯了為什麼必須先回頭改規格。

Step 1：這次是畫面還是邏輯

分類的依據是提示詞裡的訊號字，不是你的猜測。這張表要背下來不難，因為它其實就是產品詞彙的直覺分類。

訊號軌道讀哪份指南
page、component、screen、layout、ui；附了截圖；對著 design.md 的視覺工作UIui-guide.md
api、endpoint、service、functionality、logic、data、job、webhook、integrationLogicallogical-guide.md
兩種訊號同時出現，例如「auth」既有頁面也有 session 邏輯Both兩份都讀，各做各的部分

如果真的很難判斷，它會問一次：「這是 UI、它背後的邏輯，還是兩者都要？」這個問題只會問一次，因為分類一旦定了，後面就照著走。軌道是加成關係的，同一個功能可以同時是 UI 與 Logical，也可能再帶一個 tooling 的子任務。

Step 2：把決策與慣例載進來

分類完，接下來讀五種東西。這一步只讀這次功能真的會用到的，不會去翻別的 feature 或無關的規格。

一、治理這次建置的規格

順著 feature 的 spec 指標打開規格，但只讀它裡面給建置用的段落：

  • Requirements：使用者故事加上有編號的驗收條件 AC-1…。這是合約，也是後面產生 verify 步驟的來源。
  • Decision：已經定案的選擇。
  • 設計段落：依類型是 Feature design、Proposed stack 或規格表。
  • Build plan：有序的任務清單，每個任務都標著它滿足哪個 AC-N。
  • Consequences：這次決定的限制條件。

反過來，Context、Options considered、Rationale 這幾段是決策的歷史，不是建置的輸入，除非某個限制需要回頭看理由，否則跳過。如果是 umbrella 規格，先讀 index.md（它裝著決策與子規格清單，還可能夾著跨子規格的合約），然後只讀這次子任務碰得到的子規格，通常只有一份，真的橫跨兩份才讀第二份，絕不全部讀。

開工前一定要看一眼狀態。單一檔案就是它的狀態，umbrella 的話看 index.md，子規格本身不帶狀態。Proposed 是正常的：對一份已經被 `/architect` 設計並連上的功能規格來說，它代表「談好了但還沒蓋」，所以可以直接蓋，並推進到 In Progress，不用警告。Superseded 就要改用取代它的那份。Assumed 則代表這是前一節的第三條出路留下的，照著記錄的假設蓋，並把補審提醒帶進收尾即可。

二、最近的 AGENTS.md

這是離目標程式區最近的那份 AGENTS.md，它裝著從先前功能同步過來的決策。已經拍板的事不要再問第二次，這正是 spec 一路傳到 AGENTS.md 這條鏈的意義。

三、design.md（只有 UI 軌）

UI 軌的視覺真相來源。要注意它的分工：design.md 放的是美術方向（性格、建置指令、構圖與元件規則），真正的 token 值活在專案自己的樣式或主題系統裡，兩者不重複。

四、build approach

這決定了這一刀「怎麼組裝」，而不是「裝進什麼」。優先順序是：feature 的 scope 那一列有覆寫就先用它，否則用 root AGENTS.md 的專案預設，再否則用 scope 檔開頭寫的。策略就是你在 `/scope` 學過的那幾種：垂直端到端切片、最薄可用整體、UI 殼先做原型後接、每個階段完成一條使用者旅程。如果通通沒有記錄，預設就是一個一致的端到端切片，把這個功能跨的每一層都包含進去。

五、工具 skills

規格的 ## Decision 裡有一個 Implementation skills 欄位，會列出這次會用到的工具；AGENTS.md 的 ## Agent skills 段落則列出專案裝了哪些 skill、放在哪。對每個真的會管到你即將寫的程式碼的 skill，去讀它的 SKILL.md 並照它的慣例走。按需讀取，只讀這次碰得到的，不是全部。讀不到就照規格加自己的知識去蓋，並在報告裡註明。

只要四件事裡有一件是真的，就要處理：monorepo、衝突、完整性

monorepo：Workspaces 設定或 apps/*、packages/* 就是訊號。認出功能屬於哪個 workspace，然後在那個 workspace 裡工作：用它自己的 AGENTS.md 與 design.md、它自己的套件管理指令，指令要 scoped 到那個 workspace。

衝突：規格贏過專案慣例（功能專屬的覆寫本來就該壓過通則），AGENTS.md 管一般情況。衝突時不是默默挑一個，而是立旗：「spec NNNN 在 X 點上跟 AGENTS.md 分歧，`/sync` 應該調解。」規格沒提到的點，才由 AGENTS.md 管。

完整性：寫任何一行程式之前（不是寫到一半才發現），要跑兩趟檢查。第一趟看段落有沒有到齊：Logical 要有資料模型、API 介面、安全模型、關鍵不變量；UI 要有每個畫面的各種狀態。缺了或是還留著佔位符，就問。第二趟就是上一節那條 input coverage 測試，再跑一次，專門抓那種悄悄溜進來的決策。抓到缺口時，依它是承重還是實作細節給不同選項；承重的缺口一定要先把答案持久化再動工，不能只留在對話裡。

Step 2.5：把「讀」外包出去

要動一個功能，你得先找到要改哪些檔、要對齊哪些既有模式、有哪些現成的符號可以重用。這些都要讀程式碼，而每一個被打開的檔會在主 context 裡留一整個 session。檔一多，主線的思考空間就被這些內容吃掉。

所以這一步把閱讀隔離到一個唯讀的探索 subagent。它只回傳一張精簡的「地圖」，大約一到兩千個 token，裡面只有：要建立或編輯的檔案路徑、要對齊的模式與慣例（標 file:line）、可以重用的符號與型別、還有一些坑。它不回傳檔案內容，也不做任何編輯，工具只有 Read、Grep、Glob。模型要用便宜快速的那一級，絕不用你這個 session 的主力模型。

什麼時候可以跳過？當這次改動很小、你已經知道是哪個檔，或是在一個 context 還很輕的新 session 裡。什麼時候一定要跑？當讀取會把主線撐爆的時候：大 repo、monorepo、要碰很多檔、或是不熟的区域。

地圖拿到之後，真正寫碼的那一步仍然留在主線，不會外包給 subagent 去寫。這個分工是刻意的：閱讀可以便宜地外包，判斷與寫入必須留在主線。

Step 2.6：需要時才查目前的 API

有時候你要用的工具又新又動得快，你不確定自己記得的用法是不是最新的。這時候才會派一個唯讀的網路 subagent 去查當前的用法，同樣用便宜模型，只回傳精簡的用法摘要。

但界線要抓緊：這個查詢只用來知道「已經決定的工具怎麼用」，永遠不用來「要不要用這個工具」。大多數建置根本不需要它；在穩定的技術棧上，直接寫，讓型別檢查、建置、lint 的迴圈去抓過時的 API。如果查了文件才發現這個工具根本行不通，那走的是「規格錯了」那條路，不是偷偷換一個工具。

Step 3：續做，然後在主線把碼寫完

任務清單住在規格裡。 規格的 ## Build plan 是原子級的清單，每個任務標著它服務哪個 AC；你照著它做，並在它上面勾進度，这本就是續做的軌跡。scope 只承載里程碑的彙總，放在功能的 Build it 框底下（二到五個子項）；Verify it 和 Test it 屬於 `/check verify` 與 `/test`，不歸這裡。

先續做，絕不重做已經完成的。 找到 build plan 裡第一個沒勾的 [ ]，已經打勾的不重來。如果功能在 scope 裡的狀態是 existing（已出貨）或 dropped（已移出範圍），它就不是進行中的工作，不要自動去蓋，先講清楚它的狀態並確認你要復活或修改它。開始時把功能狀態設成 in-progress，並把規格的 **Status** 從 Proposed 推進到 In Progress，而且是外科手術式地只改那一行：動手前再讀一次，狀態不是 Proposed 就立旗，不覆蓋。唯一的例外是 Assumed 規格，它的狀態要留著，因為決策還沒被審議。

碼在主線寫，不派 subagent。 就算這次建置很大、牽涉很多檔，也不派一個 subagent 去替你寫程式，而是把它切成有順序的區塊，一邊做一邊勾 build plan。功能跑得很長，可以在中途用 /compact，因為狀態都活在 scope 與 spec 這兩個檔案裡，壓縮不會弄丟任何東西。

大型 rollout 的安全順序

有一種情況很特別：要套用的是一個已經決定好的模式，範圍很大，例如「把 17 個檔案裡的行內輸入框通通換掉」。這種要照固定順序走，才不會把自己卡死。

  1. 先做原語（primitive）：把共用的那件事（helper、模組、schema）做好，確認它型別檢查通過，再去碰任何呼叫點。
  2. 逐站套用：一個檔一個檔把原語套上去，行為要完全保持一致，每完成一站就勾一站。
  3. 最後才一次 gate：等所有站都遷移完，才做整個套件的型別檢查、lint 與 `/check verify`，不是每站做一次。而被取代的舊碼，也要等到這趟全綠的掃描才移除。
  4. 只做一半就停的話，不要只遷移一半：如果沒能做完每一站，就保留舊碼、功能維持 in-progress，明確報告哪些站完成了、哪些還沒，並說明再跑一次 `/develop` 會跳過已遷移的、接著做完。舊碼要等到最後一站落地且全綠的那一輪才拿掉。

兩個一定要守住的原則

規格錯了就回頭改規格，不要默默偏離。 如果做到一半發現規格站不住腳，例如決定的資料模型撐不住、某條驗收條件跟 API 介面互相矛盾，而正確的做法必須偏離規格，那就在寫下偏離之前先停下來，把問題交回 /architect 去更新或取代規格，等規格反映現實之後再續。規格與程式碼必須保持同步。

資料層沒套用就不算完成。 產生 migration 不等於做完。要真的對目標資料庫跑過，然後確認 schema 真的上線了（表、欄位、關聯真的存在，去查資料庫或它的 introspection，不是只看 migration 檔）。「已產生但未套用」等於沒做。

如果規格指定了驗證方式（沒有測試框架的專案很常見，例如「每個子任務後 typecheck 必須通過」），就照那個協定跑，子任務跑過才算完成。不要假設專案一定有測試套件。

小結

閘門過後照三件事走。Step 1 用訊號字分類 UI、Logical 或 Both。Step 2 載入治理規格（只讀建置段落：Requirements 的 AC、Decision、設計段落、Build plan、Consequences）、最近的 AGENTS.md、design.md、build approach 與工具 skills，並跑段落完整性與 input coverage 兩趟檢查；monorepo 要在目標 workspace 裡工作，規格與慣例衝突時規格贏並立旗給 /sync。Step 2.5 用便宜唯讀的探索 subagent 回傳精簡地圖，把讀取隔離在主線之外；Step 2.6 只在需要時查當前 API，且永遠不拿來換工具。Step 3 從 build plan 第一個未勾的任務續做，碼在主線寫，大型 rollout 走「原語先、逐站套用、最後一次 gate、絕不只做一半」，規格錯就先回頭改規格，資料層要 migration 套用且 schema 確認上線才算完成。

分類完成就會分成兩條軌。下一節先走 UI 軌，看它的完成標準、四條設計來源，以及那套「設計先行、整合其次」的兩趟走法。
