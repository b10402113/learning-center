UI 軌：四條設計來源與產品級版面

Step 3/5 · /develop：依規格實作

學習目標

能說出 UI 的完成標準與失格清單，選對四條設計來源，並照「設計先行、整合其次」的兩趟走法與實作階段做出合規的介面。

前言：為什麼 AI 做的畫面總是像半成品

請 AI 做一個登入頁，它常常給你一個置中的表單、兩個輸入框、一顆按鈕，漂在一片空白上。功能上沒錯，按鈕也會送出，可是它不像一個產品，像一份還沒填完的作業。問題不在 AI 不會寫 CSS，而在它對「完成」的定義太寬鬆。

UI 軌最重要的貢獻，就是把「完成」定義得非常硬。它開宗明義說：你做的是資深產品設計師要出貨的真產品，不是開發者在接一個表單。你不是在美化，你是在滿足一個完成標準。接下來要拆的就是這個標準：什麼算完成、哪些一眼就是沒完成、當沒有設計稿時四條來源要怎麼選，以及為什麼要先設計、後整合。

完成標準：一個完整的產品版面

先講結論。UI 軌的完成標準是：每一個頁面離開時，都要是一個完整、專業的產品版面，那種你在頂尖產品或 Claude 自己的聊天介面會期待的品質，絕不是一個勉強及格的空殼。這不是「建議的樣式調整」，它就是 UI 建置的定義。

而且它給了六條失格清單。任何一條命中，就是還沒完成，報告之前必須先修掉：

  1. 一個孤零零的置中表單或單一輸入框，漂在空白頁面上。
  2. 大片死區，或內容被塞在一條窄欄裡、四周圍著空白畫布。
  3. 裸露、沒上樣式、或是滿版撐開的元素，像一條沒處理的黑條、一個未處理的表頭、一個平台預設控制項。
  4. 只用預設樣式：一顆扁平按鈕、預設的細邊框、系統字體、沒有考慮過的強調色、沒有層次。
  5. 狀態缺漏（沒有空、載入、錯誤狀態），或是孤立的控制項，像一顆開關或快速動作旁邊什麼都沒有。
  6. 一個功能性的裸小工具，而產品在此處本來會給出一整個版面（品牌、真文案、版型、輔助內容、頁尾）。

這份清單的價值是它把抽象的美感變成可檢查的條件。你不用爭論「這好不好看」，你只要逐條問「有沒有踩到」。

兩趟走法：設計先行，整合其次

為什麼要分兩趟？因為如果一邊想版面一邊被 codebase 的既有 token、函式庫、無障礙限制綁住，設計會在還沒成形之前就被壓扁。所以順序是：

趟次做什麼心態
第一趟：設計版面當成要獨立出貨一樣，大膽、完整、有主張地把整個頁面組出來，對齊談好的設計系統。先讓好設計存在
第二趟：整合進 codebase套上已安裝的樣式函式庫、真實 token、語意化 HTML、無障礙、響應式。再讓它真的住進專案

這順序還配了一個很重要的小動作：報告之前先自己審一遍。拿完成標準與失格清單，加上該頁 design.md 的建置指令，逐條檢查自己做的東西，踩到的每一條都要修。如果有瀏覽器或截圖工具，就真的把頁面渲染出來看一眼，修掉看到的視覺缺陷（這是唯一能抓到像「一條莫名的黑條」這種壞掉的可靠方法），並在報告裡說明你審了什麼。

四條設計來源：依你手上有的東西選一條

設計從哪來，是「做一次就好」的決策，而且通常規格早就記下了。原則是不再問第二次、也絕不因為某個 MCP 連著就預設用 Figma。四條來源各自對應一個檔案。

你手上的東西來源路線關鍵行為
規格說用 Figma 或某個設計 MCPui/mcp.md把真設計（token、間距、元件、具名 frame、素材）拉進 design.md，用真值。MCP 沒連上就明說並請你連上或改選來源，絕不默默改用生成的設計。
貼在對話裡的截圖（不是 repo 檔）ui/image.md忠實複製，像素級對齊。圖同時是外觀也是構圖，所以照它做，不加戲；把看到的東西 token 化，並補上截圖看不出來的響應式與無障礙行為。
已經有設計系統（design.md + 樣式裡的 token）ui/existing.md在這個系統裡設計新頁面，做得跟已出貨的一致。方向讀 design.md，token 的值讀樣式系統，兩者分開、不重複。
什麼都沒提供ui/generate.md先建立設計系統再蓋：找一個方向、推導並驗證 token（對比要算過）、寫進 CSS，把性格寫進 design.md。

四條路線最後都匯流到同一組流程：判斷是元件還是畫面、偵測平台與它現有的系統、同步 token，然後跑實作階段。要特別注意的是第三與第四條會拿到「完整聊天 App 等級」的對待，第二條拿到的是忠實還原，第一條拿到的是 Figma 忠實度。你照規格記錄的那條來源走就對了。

元件還是畫面

這個判斷會影響 prop 介面、路由整合與檔案放哪。

提示詞包含建置型別
screen、page、layout、route、dashboard、view畫面
component、button、card、input、modal、badge、dropdown、toggle、chip元件
看不出來問一次：「這是可重用元件，還是完整頁面？」

兩者各有規矩。元件：先定義 props 契約再寫標記；照這個 codebase 的方式從自己的檔案匯出；裡面不准 import 導航、也不准做畫面級的資料抓取；如果專案有元件工作台（stories、previews），就在旁邊加上它的檔。畫面：要整合進平台的導航系統（router 或 navigator）；在畫面層要有載入、錯誤、空狀態；如果專案有既有的 layout 或 shell 元件，就包進去。

先偵測平台，再照它的慣例做

動手之前，先讀專案「現在用什麼」，然後用它的慣例做，不要把你的偏好硬套上去。要偵測五件事：

  • 平台與 UI 框架：web、原生行動、跨平台行動還是桌面，用的是哪套 UI 工具包。它決定導航整合、版面原語與圖片字體處理。
  • 樣式與主題系統：這個專案怎麼表達樣式與 token。樣式照它的方式寫，token 值放在那裡，不放在 design.md。
  • 導航系統：把畫面接進專案的 router 或 navigator。
  • 亮暗主題機制：兩種主題都要當成第一級狀態支援，不是事後補。
  • 圖示系統：用專案裝的那一套，絕不用 emoji 或佔位圖；尺寸從間距 token 來；裝飾性圖示要對輔助科技隱藏，獨立可互動的圖示要有無障礙標籤。

如果某一項還沒裝，就選該平台當代慣用的最佳解，在報告裡註明這個選擇，不要在這裡把某個產品名寫死。

從版面到無障礙：六個實作階段

無論走哪條來源，最後都會收斂到這組階段。無障礙不是最後補上去的，它貫穿每一個階段。

階段做什麼
Phase 0組成完整的產品版面，依畫面類型（驗證、儀表板、列表、詳情、著陸頁、設定等）把整個頁面組出來。
Phase 1語意結構：用正確的語意標籤，不是一堆 div。
Phase 2套用 token：不用原始的字面值去重複一個已經存在的 token。
Phase 3響應式版面。
Phase 4狀態與動效。
Phase 5無障礙（用平台原生的方式）。
Phase 6報告前先自己審一遍。

其中字體的處理值得記一句：如果設計指定了專有字體，不能直接抓來用，要用替代字體對照表，並處理載入。素材也一樣：先在專案裡找，找不到就問，或用佔位服務或本機的漸層佔位，而且要集中管理、可替換。

無障礙的門檻：可量測的那幾條

無障礙清單是 pass/fail 的閘門，它列出要檢查的類別：不靠指標也能操作、focus 可見、語意結構、標籤與可存取名稱、name／role／state、色彩對比、modal 與 dialog、token 紀律、響應式（盡力而為）、載入／錯誤／空狀態。標記為 required 的項目，全部要通過，這個 skill 才算完成。其中幾個是具體可量的數字：

項目門檻
一般文字的色彩對比4.5:1
大字與控制項邊界的對比3:1
觸控目標尺寸44×44
focus 指示的對比3:1

還有一條 token 紀律要記牢：不要用原始字面值。如果需要的 token 不存在，就把它記成 // TODO: missing token: …，而不是自己發明一個值塞進去。這樣下一個人知道這裡缺一個 token，而不是以為這個硬編碼值是有意為之。

UI 軌怎麼服務專案的 build approach

最後一條常被忽略的關係：UI 軌服務專案的 build approach，不自己指定一個。在 Facade 模式裡，UI 殼先做、用佔位資料、之後再接真的後端；但那是四種策略之一，不是通則。端到端或 tracer bullet 切片會在同一趟就把資料層落地，所以 UI 直接綁真實來源；Journey 則是把一條使用者路徑整條做完整。這些階段在每一種 approach 下都適用，唯一變的是「真的資料什麼時候進來」。

小結

UI 軌的完成標準很硬：每個頁面都要是完整專業的產品版面，並有六條失格清單逐條要過。走法固定兩趟，先大膽設計整個版面，再整合進 codebase 的樣式函式庫、真實 token、語意 HTML、無障礙與響應式，並在報告前自己審一遍、能渲染就渲染。設計來源有四條，依規格記錄的選一條：Figma MCP、貼上的圖、既有設計系統、從零生成；來源是「什麼都沒有」時，先建立並驗證設計系統再蓋。動手前先判斷是元件還是畫面，並偵測平台既有的框架、樣式、導航、亮暗與圖示系統，照它的慣例做。實作收斂到 Phase 0 到 6，無障礙貫穿其中，並有可量測的門檻（一般文字 4.5:1、大字與邊界 3:1、觸控目標 44×44、focus 3:1），token 缺了就標 TODO 而不是硬編。
