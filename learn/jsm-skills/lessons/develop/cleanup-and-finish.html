收尾：刪掉被取代的碼、更新 scope、走 git

Step 5/5 · /develop：依規格實作

學習目標

能在建置落地後刪淨被取代的舊碼並證明無人引用，外科手術式更新 scope 與 spec 狀態，產生 verify 步驟，並照 git 政策分支出與提交。

前言：最像做完、其實還沒做完的那一刻

功能跑起來了、型別檢查也過了，功能清單打勾，心裡覺得收工了。可是這一刻剛好是 `/develop` 最需要誠實的地方。有兩個漏失特別容易在這裡發生，而且都不會亮紅燈。

第一個是舊碼沒有刪。新做法已經接手，但舊函式、舊分支、被孤立的檔案還靜靜躺在那裡。第二個是狀態回報太寬鬆：任務其實只做了一半，卻先在 scope 上打了勾，於是一個月後沒人知道當時到底完成了什麼。這兩個縫要補起來，另外還有一件很日常的事要講：當 `AGENTS.md` 說要開 git 時，分支與提交該在什麼時間點發生。

刪掉被取代的碼：新舊不能共存

這條規則是跨軌的，UI 軌與 Logical 軌都適用。只要這次建置取代了既有的模式或實作，例如重構，或把一種做法換成另一種，那這次建置就包含刪除。要刪的是：被取代的函式與類別、變成不可達的分支、因改動而孤立的檔案、以及任何懸空的 import 與 export。

刪完不能就算了，要證明沒有任何東西還在引用它。拿每一個被移除的符號去搜整個 codebase，包含它的名字與它的 import 路徑，確認沒有殘留的呼叫者、轉發用的 export，或指向它的 index barrel。如果還有東西需要它，那代表遷移還沒完成，你應該把那個呼叫者也遷移掉，而不是把舊碼留活。最後，在舊碼真的不在的情況下跑專案的型別檢查、建置與 lint，它必須通過；一個未使用 import 或無法解析引用的錯誤，就是漏了一個地方，不要靠把舊碼加回去來消掉訊號。

刪除的時機依範圍而定。單一站：新碼進去、型別檢查變綠的那一刻就刪。多站 rollout：要等所有站都遷移完、型別檢查全綠的那一趟，才移除被取代的碼，因為還沒遷移的站仍在引用它，太早刪會弄壞建置。唯一的例外是規格明確要求一段過渡期，例如用 feature flag 的遷移或回填視窗；那就照規格做，並留下「還剩什麼要移除、什麼時候移除」的註記。

更新 scope 與報告：只標真的落地的事

收尾的第一步是確認，不是宣布。動手勾之前先驗證：檔案真的寫了、程式碼真的在而且型別檢查通過；資料層的任務則要 migration 真的套用、schema 確認上線，而不是只有產生。如果是被打斷或只做一半的任務，就讓它保持未勾、功能維持 in-progress，並明確報告哪裡沒做完、為什麼。絕不在未驗證或未完成的建置上把任務標成 done。

勾選的層級要分清楚：原子任務勾在規格裡，里程碑勾在 scope 裡，而且只動 step 0 讀到的那一個 scope 檔。規格 ## Build plan 的每個完成任務勾在規格；某個里程碑的規格任務都完成時，勾 scope 的里程碑子框；所有里程碑都完成時，勾 Build it 框；最後把指標行填上（code in <path>）。沒有規格的功能，就直接勾它 scope 的 checkbox。這裡有一個收尾閘門：報告你分別在每個檔案勾了什麼（scope 的框加上 spec 的任務與狀態），或者說明沒有對應的 scope 列，絕不默默結束。

done 是工程師的決定，不是 skill 的閘門

把所有確定落地的事勾完、自我檢查過（型別或建置綠、能渲染就看過、migration 套用且上線）之後，不是自己宣布完成，而是提出選項：現在把它標成 done，還是先走建議的下一步。如果這個功能沒有 Verify it 或 Test it 的框（例如一個基礎或決策加骨架的功能，或一個 Prototype 建置），那 done 就是自然的下一步；如果它有後面的框，就把那些框當成建議的、可跳過的下一步說明清楚。什麼時候設 done，由工程師說了算，被跳過的步驟也要誠實記成跳過。

還有一條特別的規則：Assumed 規格不會擋住 done。如果是照著前一節那份假設在建置，就在報告裡立旗：「這個是建立在一個還沒被正式審議的決策上，方便的時候找 /architect 補審。」然後讓工程師自己決定。旗子要亮著，但不當成否決票。

當工程師把功能標成 done，要順手把治理規格的 **Status** 從 In Progress 推進到 Accepted，而且是外科手術式地只改那一行：動手前再讀一次，狀態不是 In Progress（例如已經是 Accepted、Superseded 或 Assumed），就立旗而不是覆蓋。這個鏡射動作由哪個 skill 設定 done 就由它做；如果工程師在 `/develop` 之後才跑 verify 或 test，那就輪到那個 skill 做。

發出 verify 步驟，然後問要放哪裡

這一步每次都會做，而且永遠不會自動存檔。它從驗收條件推導出具體的驗證步驟，每一步都要綁到它對應的 AC-N，例如「進到 /signup、註冊、預期被導到 /auth/verify-email，對應 AC-1」。除了 AC，還要為規格 Value sourcing 表的每一列各加一個步驟，因為真正的正確性保證是行為層，規格閘門只是設計期的檢查。這一步要真的去動每個值的來源：換一個輸入、時區、語系、幣別或租戶，再看輸出對不對。這樣就算閘門漏掉了一個被錯誤指源的値（例如用錯時區算出來的「今天」），行為層還是抓得到。

推導完，會給你一個面板問要怎麼處理：

選項它做什麼什麼時候推薦
Save to verify.md把步驟寫進功能旁的 verify.md，成為一份耐久清單，讓 `/check verify` 之後可以照跑、`/test` 可以鎖成測試。資料、認證或風險較高的功能，推薦這個。
Just show in summary只留在這次的報告裡，不寫檔。你只想先看一眼、不想多一份檔。

選了存檔，它會把 verify.md 寫在規格旁邊。如果規格是單一檔案，會先把它升級成目錄：docs/specs/NNNN-feature.md 變成 docs/specs/NNNN-feature/{index.md, rationale.md, verify.md}，把決策歷史的段落搬進 rationale.md、建置規格留在 index.md，並把 scope 的連結指向新的 index.md。已經有 verify.md 就用附加的，不覆蓋。

建議下一步，但講清楚是可選的

報告的結尾會從 scope 推導出建議的下一步，並很清楚地說它是可以選、可以跳過的。它會拿這個功能第一個還沒勾的框當建議；所有框都勾完了，就指向下一個功能；如果這個功能根本沒有 Verify it 或 Test it 的框，那就沒有可建議的，直接往下走。它絕不會把任何一個階段講成必要的。

兩個小地方很重要。如果規格是 Assumed，它會先建議補審：/architect <feature>: ratify the assumed <decision>，因為趁早抓到錯誤的假設，比之後繼續往上蓋要好；但這仍然由工程師決定。還有，它會提醒你在下一個功能之前先跑 /clear，因為狀態都活在檔案裡，冗長的 session 就算有快取也比較貴；建置很長的話，可以中途 /compact。最後劃清界線：/develop 只負責建置，不會替你跑 /check verify、/test、/sync 或 /architect，它只做指路，你決定。

git：分支在開工前，提交在里程碑

git 這一段只在最近的 AGENTS.md 的 ## Git 區塊寫著 integration: on 時才會讀。沒寫或寫 off，就不做任何主動的 git 操作，由工程師自己管分支與提交，但前面那些唯讀的狀態檢查照樣會跑。

設定有三個：integration、branch prefix（預設 feat/）、commit（預設 per-milestone，也可以是 end-of-build 或 manual）。本機的操作，例如開分支與提交，都是帶建議的選項；push 與 PR 永遠要先確認，因為那是對外的動作，而且 PR 是 /document 的工作，不是這裡。

如果 integration 開著、但專案還不是一個 git repo，它在開分支或提交之前會先跑 git init，並把已經存在的內容先 stage 起來當第一個 commit。`/audit` 通常在打開 integration 的那一刻就做掉了，這是給走到建置還沒 init 的專案一個保險。

分支：永遠不要在預設分支上建置

  • 在預設分支（main 或 master）上，它會提議開一條分支（推薦），名字是 <prefix><feature-slug>，用 scope 的功能名做 kebab case，例如 feat/accounts-sign-in。
  • 已經在功能分支上，就沿用，不再另開。
  • 續做一個半成品功能時，如果那個功能的分支存在、而你不在上面，就先切過去。
  • 如果不是新功能，用變更型別當前綴，例如 fix/、refine/；否則用設定的預設。

注意這個動作發生的時間點：在「動手建置之前」，它屬於開工前那一輪 freshness 與協作檢查的一部分，而不是收尾才做。

提交：里程碑落地就提，且要照格式

設定行為
per-milestone（預設）一個里程碑落地、型別檢查變綠時，提議只提交那個里程碑的檔案。
end-of-build建置整個落地時提一次。
manual永不提交，工程師自己來。

訊息是一行 Conventional Commit 主旨，不寫散文式的 body，並附上必要的 Co-Authored-By trailer。型別從工作性質來（feat、fix、refactor、test、chore），scope 可有可無，摘要用祈使句：

feat(auth): add session persistence

Co-Authored-By: Claude Opus 4.8 (1M context) <noreply@anthropic.com>

三個規矩：為什麼這件事留在規格與 PR 裡，永遠不寫進 commit body（單一來源）；只提交真的落地而且型別檢查通過的東西，絕不提交半個里程碑；這裡永遠不 git push，那個動作屬於 PR 時刻的 /document，而且要先確認。報告時，如果 integration 是開的，就加一行說明你在哪條分支、提交了什麼（例如 feat(auth): … · 3 commits），或是提交是 manual；如果 integration 關著或沒設定，就一個字都別提 git。

小結

收尾有兩個最容易漏的動作。第一，被取代的舊碼要刪乾淨並證明無人引用：刪掉被取代的函式、不可達分支、孤立檔案與懸空 import，搜尋每個被移除符號確認沒有殘留呼叫者，並在舊碼不在的情況下讓型別檢查、建置、lint 通過；單站的新碼綠了就刪，多站等全綠那一趟再刪，唯一例外是規格明講的過渡期。第二，只標真的落地的事：原子任務勾在規格、里程碑勾在 scope、只動那個 scope 檔，並遵守收尾閘門回報勾了什麼；done 是工程師的決定，Assumed 規格不擋 done，標 done 時把治理規格從 In Progress 鏡射成 Accepted，且動手前再讀一次。每次都要從 AC 與 Value sourcing 表推出綁著 AC 的 verify 步驟，並問要存進 verify.md 還是只放摘要，絕不自動存。建議下一步時講清楚它是可選的。git 只在 integration 開啟時作用：開工前先開功能分支，里程碑落地照設定提交一行 Conventional Commit 加 Co-Authored-By，push 與 PR 永遠先確認且屬於 /document。

走到這裡，你已經把 `/develop` 從閘門到收尾走完了一遍：先確認決策有人做過，分軌載入規格並隔離探索，在 UI 軌與 Logical 軌各自把東西蓋到位，最後把舊碼清乾淨、把狀態誠實回報、把驗證步驟交給下一個階段。下一步是把這條建置好的線交給 `/check verify` 與 `/test` 去證明它真的能動。
