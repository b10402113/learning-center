Logical 軌：從資料層到介面的七個階段

Step 4/5 · /develop：依規格實作

學習目標

能照 logical-guide 的七個階段實作後端：把不變量放進資料庫、對金流與訊息做冪等、在介面層做授權而不只驗證，並在整合層處理密鑰、webhook 與日誌。

前言：後端工程師最常偷的兩步

後端工作有一種很容易發生的墮落。第一種是「遷移檔寫好了就算做完」：migration 產生出來、型別也過了，任務就打勾，但那個 migration 從來沒對真正的資料庫跑過。第二種是「授權等於驗證」：確認了使用者有登入，就讓他呼叫 API，卻忘了檢查他能不能動這一筆資源。這兩個洞都不會在開發時報錯，只會在真實世界裡變成事故。

Logical 軌的七個階段，很大一部分就是在堵這些洞。它先給你一個清楚的自我定位：你是這個專案的資深後端工程師，你的工作是實作 `/architect` 已經做好的決策，不是再辯一次。規格是你的規格，程式區旁邊的 AGENTS.md 是你的慣例，既有的程式碼是你的風格指南。順著這三個來源走，你就不會重新發明一套模式。

三條地面規則

規則意思
照規格蓋資料模型、API 介面、關鍵不變量、安全模型、設定都來自規格的 Feature design。規格說狀態機是「試用 → 生效 → 逾期」，你就實作那一台，不是自己另開一台。
對齊 codebase動手前讀最近的 AGENTS.md 和二到三個鄰近檔案。用專案現有的 ORM、錯誤處理、驗證函式庫與檔案佈局。既有模式存在就絕不另立一套，因為那是決策，決策屬於規格。
推斷／詢問／建議能從規格、AGENTS.md 與程式碼推斷的就推斷，不要問已經記錄過的事。只有真正模糊、會擋住正確實作的商業規則才問。實作細節（helper 的形狀、檔案放哪）自己決定並往前，不要煩工程師。

Phase 1：先把決策吃進去

動手前先把要蓋的東西摸清楚，而且只在紙上確認，不先寫碼。這一步包含幾件事。

首先把治理規格整份讀過，尤其是 Feature design（資料模型、API 介面、不變量、安全模型、設定）與 Consequences。接著把 spec 的 ## Requirements 也讀進來，因為那些 AC-1… 是這次建置的合約，而 build plan 的每個任務都標明它服務哪個 AC。然後以 step 2.5 那張探索地圖為底，不要去重讀整個區域。如果這個任務會取代既有程式碼（一個重構或遷移，而不是全新的新增），就在這裡先把「它取代了哪些舊函式、舊檔案、舊模式」記下來，這樣你就知道 Phase 6 要刪什麼。

把整合點與建置順序列出來，這條軌的典型順序就是後面那幾個階段：資料 → 邏輯 → 介面 → 整合 → 清理。如果 grounding 的過程中發現規格站不住腳，例如決定的資料模型撐不住、驗收條件跟 API 介面矛盾，那就停下來交回 /architect，在動手寫出偏離之前先改規格。

Phase 2：資料層，套用並確認上線才算完

照規格的資料模型草圖實作 schema 與 migration：欄位型別、可否為 null、外鍵關聯、唯一約束。這裡有一條絕對規則：資料層的變更，要等 migration 套用且 schema 確認上線，才算完成。產生 migration 不等於做完，你要真的對目標資料庫跑它，然後確認表、欄位、關聯真的存在。最好用一個連上的資料庫 MCP 去查真實 schema，否則用專案自己的 introspection 或 describe 查詢。絕不要只是盯著 migration 檔看一眼就算過，也絕不在「產生但未套用」的 migration 上打勾。

另外兩件很實務的事。第一，能在資料庫層強制的不變量就放在那裡用約束表達，不要只靠應用層檢查。第二，在活系統上要遵守遷移紀律：新增欄位要「先可 null → 回填 → 再加約束」，絕不直接加一個沒有預設值的 NOT NULL 欄位。最後，用專案既有的 ORM 與命名慣例，不要自己拉一套。

Phase 3：核心邏輯與服務

把規格裡的商業邏輯與狀態轉移實作出來。狀態機要明確建模，遇到不合法的轉移要拒絕，而不是放任它流過去。

冪等是這個階段最容易被忽略、後果卻最嚴重的一點。任何牽涉金流、訊息或外部副作用的變更，都要產生並遵守 idempotency key，讓重試是安全的。想像一下：客戶網路抖一下，同一個付款請求送了兩次，如果沒有冪等，就會扣兩次款。這種 bug 上線後非常難補。

輸入在邊界就要驗證，而且要往安全的方向失敗（fail closed），不確定就拒絕，而不是放行。錯誤則用專案既有的模式處理，跟著已經存在於 codebase 的 result／exception／error 形狀走，不要自己發明一套新的。

Phase 4：介面層，API 與 action

每個 endpoint 或 action 都要完全照規格的 API 介面表實作：方法、路徑、輸入、輸出、認證需求、關鍵錯誤。這裡有四個規矩值得逐條看。

  1. 強制授權，不只是認證。 確認呼叫者可以對這個資源採取行動，依規格的安全模型檢查擁有權、角色或組織範圍。使用者有登入，只代表他身分有效，不代表他能動這筆資料。
  2. 每一個列表 endpoint 都要分頁，就算是 MVP 也一樣。不分頁的列表最後都會變成事故。
  3. 回傳客戶端可以依賴的一致錯誤形狀，並用正確的 HTTP 狀態碼。
  4. 公開的 endpoint 要限流。

Phase 5：整合與設定

外部供應商照規格決定的接上去（供應商本身是 `/architect` 已經做好的建議決策，直接用）。密鑰與金鑰一律從環境變數或密鑰管理服務讀，絕不硬編碼、也絕不提交進版控；每個新環境變數都要命名，並在報告裡提醒工程師去設定。

處理入站 webhook 時有三件事一定要做：驗證簽章、讓 handler 冪等（例如用一張事件表，讓重送的 webhook 不會重複套用）、以及依規格需要時，用定期補掃來跟 webhook 驅動的狀態對帳。最後，在邊界加上結構化日誌，並對任何碰到金流、存取控制或合規範圍的變更加上稽核日誌。

Phase 6：刪掉被取代的碼

只要這次建置取代了既有的模式或實作（一個重構，或一個把舊做法換成新做法的 rollout），這一步就適用。規則是：新舊實作不能共存。把死碼留在後面，是這一類工作最經典的漏失，而移除它是這次建置的一部分，不是之後再說的雜事。

要刪的有：已經被取代的函式與類別、變成不可達的分支、因為改動而被孤立的檔案、還有懸空的 import 與 export。刪完之後要證明沒有任何東西還在引用它：拿每一個被移除的符號去搜整個 codebase（用它的名字、它的 import 路徑），確認沒有殘留的呼叫者、轉發用的 export，或指向它的 index barrel。如果還有東西需要它，那代表遷移還沒完成，你要把那個呼叫者也遷移掉，而不是把舊碼留活。

最後要在舊碼真的不在的情況下驗證乾淨：跑專案的型別檢查、建置、lint，以及任何偵測死碼或未使用 import 的檢查。它必須在刪除之後通過，一個未使用 import 或無法解析的引用錯誤，就是你在告訴你漏了一個地方。不要靠把舊碼加回去來消掉這個訊號。

只有一種例外：規格要求一段過渡期，新舊必須同時跑（例如用 feature flag 的遷移，或一段回填視窗）。那就照規格做，並留下明確的註記：還剩什麼要移除、什麼時候移除，免得被忘掉。

Phase 7：正確性與安全檢查

這不是最後才做的一張清單，它貫穿每個階段，只是在這裡再強制檢查一次。

  • 安全：每個 endpoint 都對行為者做了授權；回應與日誌裡沒有敏感資料外洩；程式裡沒有密鑰。
  • 失敗模式：第三方逾時、資料庫變慢、並行寫入時會發生什麼？重試要有界且冪等。
  • 不變量在並行下成立：規格裡的關鍵不變量，不能因為兩個同時進來的請求而被破壞。
  • 設定完整：每個新環境變數都有被記錄；缺少必要密鑰時，功能要大聲失敗，而不是默默出錯。

報告的樣子

做完之後的報告有固定形狀：先給標題那一句，再給下一步，只有在真有的時候才給一個提醒。已經蓋好的檔案、資料模型、endpoint、設定都在程式碼與規格裡，不要重印一遍。例如：

Built <feature>：一句話，例如「votes API 加上一人一票的不變量，migration 已套用且 schema 上線」。
Next: /check verify <feature>
Heads up: <要設定的新環境變數 `X` · 規格沒定的一條商業規則 · 舊碼已移除>

報告只講需要工程師注意的事：一個要設定的新環境變數、一個規格沒定的開放問題，或一個沒套用成功的 migration。

小結

Logical 軌的定位是資深後端工程師：實作 `/architect` 的決策，不重辯，跟著規格、AGENTS.md 與既有程式碼的風格走。三條地面規則是照規格蓋、對齊 codebase、以及推斷／詢問／建議的紀律。七個階段依序是：Phase 1 先把決策吃進去並列出整合點與被取代的舊碼；Phase 2 資料層，migration 要套用且 schema 確認上線，能在資料庫強制的不變量就放那裡；Phase 3 核心邏輯，狀態機要明確，金流與訊息要冪等，輸入在邊界往安全方向失敗；Phase 4 介面層，照 API 表實作，強制授權、每個列表都分頁、一致錯誤形狀、公開端點限流；Phase 5 整合與設定，密鑰從環境讀、webhook 驗簽章並冪等、加結構化與稽核日誌；Phase 6 刪掉被取代的碼並證明無人引用，舊碼在則遷移未完成；Phase 7 正確性與安全檢查，涵蓋安全、失敗模式、並行下的不變量與設定完整。

兩條軌都介紹完了。接下來要處理的是它們共同的最後一段：把被取代的舊碼刪乾淨之後，怎麼只更新該動的那幾行 scope 與 spec 狀態、怎麼把驗證步驟留下來，以及 git 要在什麼時候開分支、什麼時候提交。
