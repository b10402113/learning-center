Token 預算與 progressive disclosure：為什麼每一行都是成本

Step 2/4 · 設計理念與 Skill 解剖

學習目標

能用「每次載入都是成本」解釋 progressive disclosure 與 token 預算，並用 cost-unit 權重判斷該先砍輸出、砍 fresh input，還是砍 resident 檔。

前言：為什麼一句提醒也要斤斤計較

上一課的第四條慣例說「skill 要瘦，因為每一行都是成本」。這句話很容易被當成口號：反正現在的模型 context window 很大，多寫幾句會怎樣？

問題在於「每次」這兩個字。你維護的規則是給 agent 讀的，而 agent 每次執行你的 skill，都會把那份指令從頭讀一遍。你今天多加的一句提醒，不是付一次錢，是往後每一次執行都要付一次。如果這句話又不改變 agent 的行為，那它就是在幫你穩定地燒錢，什麼都沒換到。要判斷哪一句該留、哪一段該拆檔，就得先搞清楚這筆帳是怎麼算的。

成本從哪裡來：三種載入路徑

一個 skill 的內容不是平均地花錢，它分三條路徑進場，成本結構完全不同，並不是平均地花錢。

第一條是 SKILL.md 的本文。只要這個 skill 被叫到，它的主體就會完整載入主對話的 context。這是每次執行都在付的固定成本，也是為什麼「瘦身」主要針對它。

第二條是 frontmatter 裡的 description。它更狠：每個安裝好的 skill，它的描述都會載入到「每一個 session」，不管你這次有沒有要用它。所以描述必須短，真正的理由是它出場次數最多，跟排版好不好看無關。jsm-skills 給它的上限是 400 個字元。

第三條是 skill 資料夾裡的支援檔案，例如各種 mode 或 guide。這些檔案通常在 subagent 被叫用時，才載入到 subagent 的 context。它們不會拖累主對話的每一次執行，但還是要控制大小。

把三條放在一起看，就能理解為什麼專案把「最常用的東西留在最小的地方」當成原則。

Progressive disclosure：把罕見又長的內容請出去

所謂 progressive disclosure（漸進式揭露），在 skill 設計裡的定義很具體：只把「罕見需要」而且「內容很長」的東西，移到另一個用到才讀的檔案；短或常用的內容，就留在入口。

你可以想像一位醫師的診間。牆上貼的是常見症狀的處置流程，一抬頭就看到，因為每天都在用。真正罕見病例的詳細手冊，則收在抽屜裡，遇到那種病人才拿出來翻。如果把整本手冊都貼在牆上，牆面會被塞爆，而且你九成時間根本用不到那些內容，只是每天抬頭都看到它。

這裡有兩個判準缺一不可。內容要「罕見」，拆出去才划算，因為它在主路徑上多半用不到；同時它要「長」，拆出去才值得，因為短的東西搬來搬去只是多一道讀取。只符合其中一個條件，就該留在原地。

拆檔的時候還有一個不能忘的細節：觸發條件要寫明。不能只留一個檔名，要寫成「如果遇到 X，先讀 Y 再繼續」。少了這句，agent 根本不知道什麼時候該去讀那個檔案，內容等於白拆。

把預算變成可執行的數字

既然成本可以量，jsm-skills 就把它寫成具體的上限，交給腳本去盯。主要幾條是這樣：每個 SKILL.md 的本文上限 32 KB；支援檔案上限 24 KB，少數歷史檔案有例外。除了單檔上限，還有一組「熱路徑預算」（hot path），用來模擬一次真實執行實際會載入的總量，例如 /architect 走完整設計流程、/scope 規劃、/develop 做 UI 時的完整讀取，各自有自己的總量上限。

更有意思的是預算政策。這些上限刻意設在「實際大小再往上留一點」的位置，大約是警告線的 0.9 再高一階，讓平常的小修改能安全過關，只有真正長胖時才會觸發。反過來，如果上限剛好貼著現在的大小設，那麼每一次編輯都會踩線，而面對一個永遠在叫的警報，工程師唯一能做的是把上限往上調。一旦開始這樣做，這個預算就再也沒有意義了。所以專案的原則是：接近上限要「先刪」，不是抬高天花板；例外名單只能往下修，不能往上加。

帳單其實長什麼樣：cost unit 的四種權重

要知道省錢該從哪裡下手，得先理解 token 不是等價的。專案裡的 analyze-token-usage.mjs 把一次 session 的用量拆成四類，並給了相對權重（以一個未快取的輸入 token 為 1）：

類別權重白話解釋
fresh input1.0這次真的新讀進來、沒有快取的輸入
cache-write1.25第一次寫進快取，比一般輸入還稍貴
cache-read0.1命中快取重讀，只算約十分之一
output5.0模型生成的字，權重最高

這張表推翻了一個直覺。你看到一次執行「讀了八萬個 token」，第一反應是「好多」，但如果其中大部分是 cache-read，實際帳單只有十分之一。工具在報表最後會提醒你：原始總量會高估成本，在 cost unit 的尺度上，真正的錢多半花在 output 生成上。

所以省錢的槓桿有明確排序：先砍 output 和 fresh input，cache-read 本來就便宜。而這兩個槓桿對應到很不一樣的動作。砍 output，靠的是減少冗長的來回：面談少問幾輪、問題問得更準，生成的字自然變少。砍 fresh input，靠的是不重複載入新的長內容。至於把常駐檔案改小，影響的其實只是便宜的 cache-read。

這正好接回上一課的慣例三。為什麼「每個問題都附一個推薦選項」不只是禮貌問題？因為它讓你少來回好幾趟，而每一趟都是一次 output 生成。把問題問好，就是最有效的省錢手段。

Subagent 是另一種省錢法

工具報表還會把用量拆成「主對話」與「subagent」兩邊。這個拆法的意義在於：你可以把大量、粗糙的讀取工作丟給 subagent，讓它回傳一份壓縮過的摘要，主對話只收摘要，不需把原始內容全部吃進來。

jsm-skills 的兩個唯讀 subagent 就是這個思路。scout 負責掃描程式庫，它被要求回傳一份約一到兩千 token 的精簡地圖，包含要建立或修改的檔案、可重用的符號、以及要注意的陷阱。researcher 負責查外部資料，只回傳查證過的連結與結論，不把整頁網頁搬回來。它們的產出有明確的 token 上限，這就是主對話不會被撐爆的原因。

小結

成本來自三條載入路徑：SKILL.md 本文每次執行都進主 context、description 進每個 session、支援檔案在 subagent 被叫用時載入。Progressive disclosure 的判準是「罕見又長」才拆檔，並寫明觸發條件。預算用 byte 上限與熱路徑總量來管，原則是接近上限先刪、例外只能下修。而 token 不等價：cache-read 只算約十分之一，output 權重最高，所以省錢要先砍 output 和 fresh input，把常駐檔案改小只能省到便宜的 cache-read。

既然每一行都有成本，下一個問題自然是：一個設計良好的 skill 到底該長什麼樣？下一課要拆開 skill 的資料夾結構，並整理出六條把成本意識落實在檔案裡的撰寫規則。
