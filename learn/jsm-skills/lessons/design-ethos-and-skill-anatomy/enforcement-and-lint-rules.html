把慣例變成守門員：11 條可執行檢查

Step 4/4 · 設計理念與 Skill 解剖

學習目標

能列出 check-portability 的 11 條規則與 byte budget，並解釋 prompt 的 lint 如何用 warn-before-fail 頻帶與 prose masking 讓風格和 token 預算不再靠人記得。

前言：寫在文件裡的規則，會慢慢失效

前三課建立了一套設計標準：四條慣例、成本模型、skill 結構與六條撰寫規則。但這些標準都寫在文件裡。只要是人寫的規則，就會漂移。有人新增一個 skill 時忘了加 allowed-tools，有人把「read only」寫成「read-only」，有人為了塞功能悄悄把檔案養到兩倍大，還有人在描述裡用了一個破折號，忘了整套 skill 正在教使用者不要用破折號。

這些問題單獨看都很小，累積起來卻會讓整套工作流失去一致性，甚至讓 token 預算失去意義。jsm-skills 的解法很直接：把規則變成程式碼。一支零依賴的檢查腳本掃過所有 skill 檔案，違規就讓 CI 紅燈，這比再寫一份「請大家遵守」的文件有用得多。這一課要拆開這支守門員，看它檢查哪 11 件事，以及兩個值得偷學的設計手法。

為什麼「檢查腳本就是測試套件」

在一般軟體專案，npm test 跑的是單元測試。在這個專案裡，package.json 把 test 直接指向 check，也就是 node scripts/check-portability.mjs。換句話說，這支慣例檢查腳本就是整個專案的測試套件。

這個安排透露了一個判斷：這裡的「產品」是一堆 prompt 檔案，最常壞掉的地方是風格與預算慢慢走鐘。既然如此，防線就該設在「檔案有沒有遵守約定」上面。腳本本身沒有安裝任何套件，只用 Node 標準函式庫，所以 CI 裡連 npm install 都不用跑，直接執行就行。

11 條規則，分三組看

規則乍看很雜，但大致落在三個主題：跨工具可攜性、預算，以及風格一致性。以下逐條說明。

跨工具可攜性

  • 規則 1：每個 SKILL.md 的 frontmatter 都要有 allowed-tools。宣告這個 skill 允許動用哪些工具，讓不同客戶端知道該開哪些權限。
  • 規則 2：不能把模型別名寫死成 spawn 指令。不能在檔案裡寫 model: "haiku" 這種指定。原因很實際：subagent 如果沒有被明確指定模型，通常會繼承主 session 用的模型，而那往往是比較貴的等級。正確做法是用角色詞描述，例如「用一個快而低成本的模型」，把各家工具的別名只當成不引號的範例。
  • 規則 3：不要在敘述裡指名 subagent 工具。不要寫「用 Agent 工具」「spawn 一個 Agent」，要改用能力描述，例如「派一個 subagent 去讀」。這樣換一個工具或工具改名，skill 都不用跟著改。
  • 規則 4：不能有會讓 PowerShell 爆掉的 shell 黏著語法。例如 >/dev/null、&& BASE= 這類只在類 Unix 環境成立的寫法。git 指令本身沒問題，有問題的是那些非 git 的 shell 花招。分支選擇的邏輯要用文字描述，而不是塞進 shell 表達式。
  • 規則 7：每個 skill 都要附上 agents/openai.yaml。而且必須含有 interface:、display_name:、short_description:、default_prompt: 四個欄位，這是給其他客戶端的介面轉接。
  • 規則 8：allowed-tools 要寫 Agent，不是舊的 Task。Claude Code 已經把 subagent 工具從 Task 改名為 Agent，舊名只保留相容性。既然要宣告，就宣告真正的名字。
  • 規則 9：被標記的共用區塊，在不同 skill 之間必須逐位元一致。因為 skill 是各自獨立安裝的資料夾，一條「兩個 skill 都必須遵守」的規則沒辦法放在單一共用檔裡，只能刻意複製。複製就會有漂移風險，所以腳本把這些區塊用 <!-- NAME:START --> 標記框起來，逐字比對，一旦有人只改了一邊就報錯。

預算

  • 規則 5：單檔 byte 上限。SKILL.md 本文 32 KB，支援檔案 24 KB，少數歷史檔案有列在例外名單裡。
  • 規則 5b：熱路徑總量預算。單檔沒超標，不代表一次執行不會超載。腳本另外模擬幾條真實路徑的總讀取量，例如 architect 完整設計流程 72 KB、scope 規劃 48 KB、develop 做 UI 的完整主對話讀取 90 KB，各有一條總量上限。哪條路徑快撐爆，報表會直接標出來。

風格一致性

  • 規則 6：description 不超過 400 個字元。這是全專案出場次數最多的文字，每個 session 都會載入，所以最該短，也順便套用規則 10 的破折號禁令。
  • 規則 10：任何指令檔與描述都不能出現 em dash 或 en dash。整套 skill 都在教模型輸出時不要用破折號，那麼自己的指令檔更該以身作則。破折號要改成逗號、冒號或括號。
  • 規則 11：敘述文字裡不能有連字號（hyphen）。複合詞要寫成簡單單字，例如「read only」而不是「read-only」。程式碼、路徑、旗標、全大寫關鍵字，以及少數「被解析的固定詞」可以保留連字號。

設計亮點一：warn-before-fail 的警告頻帶

這支腳本有一個值得偷學的設計：WARN_AT 設成 0.9。任何檔案若用到預算的九成以上，但還沒超標，會被列為警告；每次執行都印出各條路徑的使用率，超過九成就在報表上被點名。真正超標的才列入違規，讓程式回傳非零的結束碼。

為什麼要在「還沒壞」的時候就先提醒？把預算設得剛好貼著現況，會發生一件反效果的事：每一次正常編輯都會踩線，於是工程師唯一的出路就是把上限調高。只要開始抬高上限，這個預算就再也不能反映真實需要，變成一張好看的裝飾。留下一段警告頻帶，是要讓「正在變胖」在還便宜的時候就被看見；原則是接近上限先刪內容，真的需要更多才調高，而且要說明理由。例外名單只能往下修，不能往上加。

設計亮點二：用遮罩分辨程式碼與散文

規則 10 和 11 要求敘述不能有破折號與連字號，但程式碼裡到處都是連字號：allowed-tools、>/dev/null、檔名、URL。如果腳本不分青紅皂白地全抓，會產生大量誤報，最後沒人看警告。

它的解法是「先遮罩、再檢查」。腳本把圍起來的程式碼區塊、行內程式碼、HTML 註解、markdown 連結目標、裸 URL，以及 frontmatter 的鍵，全部用空白蓋掉（保留長度，行號才不會跑掉）。遮罩之後，任何還站著的連字號單字，就一定是散文，該被改寫。剩下的少數例外用一張固定清單處理，例如 in-progress、gap-fill、whole-repo、Follow-up、pre-flight。這些是 skill 會互相匹配的「具名值」，例如某個 phase 名稱或某個 section 標題，改掉它們等於要同步遷移所有 skill，不是單純的文案修改，所以特准保留。

這個手法的價值在於：它讓一條「風格規則」變成不會誤傷程式碼的自動檢查。規則不再只能靠 review 時用眼睛抓。

執法迴圈：本機與 CI

規則要真的生效，得進到流程裡。本機端，npm run check 負責跑完整檢查；npm run tokens 則是上一課那支唯讀的 token 分析工具，用來看一次 session 的錢花到哪。CI 端，.github/workflows/check.yml 在 push 到 main 以及每個 pull request 上執行：用 ubuntu、裝 Node 20、跑 npm run check，因為腳本零依賴，不需要安裝步驟。

把三條線接起來看：文字規則（慣例與撰寫標準）寫進腳本（11 條檢查）再進 CI（每個 PR 都跑）。任何人想改 skill，都得先通過這道守門員。風格和預算因此由流程把關，不必靠人記得。

小結

把 prompt 當產品、把慣例當測試，是這個專案的核心手法。檢查腳本零依賴、只掃 skills/ 下的所有 markdown，違規則回傳非零。11 條規則分成跨工具可攜性（allowed-tools、模型別名、工具命名、PowerShell 相容、openai 轉接、Agent 正名、共用區塊逐位元一致）、預算（單檔 32/24 KB 與熱路徑總量）、風格（description 400 字元、無破折號、散文無連字號）。兩個關鍵手法是：留一段九成的警告頻帶，讓變胖在還便宜時被看見；以及先遮罩程式碼再檢查散文，讓風格規則不會誤傷程式碼。

到這裡，你已經走完 Tier 1 的最後一塊拼圖：從四條慣例、成本模型、skill 結構，一路到可執行的檢查。接下來進入 Tier 2，會逐階段拆解九個 skill 的操作規則。你現在有了設計視角，讀那些規則時，會更容易看出每一句為什麼存在、哪一句可以拿掉。
