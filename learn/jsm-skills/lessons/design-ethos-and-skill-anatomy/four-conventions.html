四條核心慣例：誰握方向盤

Step 1/4 · 設計理念與 Skill 解剖

學習目標

能說出四條核心慣例（engineer decides、suggestions never gates、one recommended option、keep skills lean）各在防哪一種失敗，並解釋它們為什麼是同一套「人類握方向盤」的設計觀。

前言：AI 太自動，反而讓人不安心

你有沒有碰過這種情況？你請 AI 幫你審一份規格，它不只挑出幾個問題，還順手把問題都改掉了。等你回頭看那份檔案，已經分不清哪個決定是你拍的板、哪個是它自己決定的。或者反過來，它丟給你一份中性選單，問你要方案 A 還是方案 B，卻不告訴你它心裡建議哪個，讓你盯著螢幕想了五分鐘還選不出來。

這兩種狀況都不是模型能力不足，問題出在它預設把自己當成主導者，而不是助手。jsm-skills 把這套工作流的前提直接講白：方向盤在工程師手上，AI 只負責把選項、後果和風險攤在你面前。為了讓這個前提在每一個 skill、每一次對話裡都成立，整套專案定了四條慣例。

這四條慣例會一路出現在後面每一課。看懂它們之後，你再看任何一個 skill 的檔案，都會知道作者當初為什麼要這樣寫、哪些句子不能刪。

慣例一：工程師決定，AI 只推薦

第一條是整組慣例的地基：任何由 AI 主動發起的驗證或評論，都只能「提議」，不能代替工程師去跑，也不能代替工程師跳過。

最典型的例子是 /architect 在寫規格時，可以請另一個模型對這份規格做交叉檢查（cross-model check）。這個檢查本身是好東西，但它預設只是「被提出來」的選項。要不要做、做完怎麼處理，都由你決定。檢查如果真的找到問題，無論是一個缺口、一個關鍵決定，或一個該修的錯，都必須回報給你，由你判斷，不能自己默默修掉。

這裡有一個容易混淆的邊界：如果檢查是你自己喊的（例如你主動跑 /check verify 或 /check review），那它當然可以跑，因為那已經是你的選擇。但即使如此，它做完還是只「回報」，不會自動幫你改程式碼。把這條線記牢：AI 可以幫你動手，但最後要由你來下決定。

這條慣例在防的失敗是靜默決定。當一個工具悄悄幫你把決定做掉，你失去的不只是控制權，還有整個決策的來龍去脈。等到三個月後出問題，你翻遍紀錄也找不到「當初為什麼這樣選」。

慣例二：建議不是關卡

第二條處理的是流程：工程師才是負責人，`/develop` 之後的每一步（驗證、測試、審查、寫文件）都是被「建議」的，可以被自由跳過；而「做完了」這件事由工程師宣布，不是某個 skill 把關卡鎖住不讓你過。

很多自動化流程會偷偷把「建議」變成「強制」。你做完功能，系統說要通過五個檢查才能標記完成，於是你花了半小時跑一堆對這次改動根本不重要的驗證，只為了把紅燈弄成綠燈。jsm-skills 明確拒絕這種設計。工作流的分級（Prototype、Alpha、Beta、GA）會依專案需要的嚴謹度「建議」你跑哪些步驟，但它終究只是預設值，你可以針對單一功能覆寫，甚至整段跳過。

更關鍵的是，被跳過的步驟會誠實地記錄成「跳過」，而不是假裝完成。整套流程唯一真正開口要求的事，是希望你把「承重的決定」（load bearing decision）寫成一份規格文件。但就連這件事也是提出來提醒你，不是拿來當關卡：即使你只留了一份標成 Assumed（尚未正式核可）的規格，它也不會擋住你把工作標成完成。

把第一條和第二條放在一起看，差別就出來了。第一條管的是「AI 主動發起的驗證和評論」，第二條管的是「流程步驟本身」。前者約束 AI 的手，後者約束流程的閘門，兩者合起來確保工程師永遠是最終的決策者。

慣例三：每個問題都帶一個推薦選項

第三條很短，但影響每一句話：任何要問使用者的問題，都必須附上「恰好一個」推薦選項，並用一行說明為什麼推薦它。意思是 AI 要先做判斷、給你一個它認為最好的答案，你再決定要不要推翻它。不能丟一份中立菜單，不能丟一個冷冰冰的問題，更不能什麼都不問就自己決定。

你可以想想差別。一個冷問題是「你想用哪種拆解方式？」，把四個名詞倒給你，自己研究。一個好的問法長這樣：「我建議用 Tracer Bullet（先打一條貫穿所有層的細線），因為這次是全新專案、最大的風險是各層接不起來，先打通一條最早能驗證這點。」後面那個版本，你三秒內就能決定，因為它幫你做了八成的研究，只把最後的判斷權留給你。

這條慣例在防的是選擇癱瘓與無聲決定。它同時也降低了對話的來回次數，而這點在下一課談 token 成本時，會變成一個很具體的省錢手法。

慣例四：skill 要瘦，因為每一行都是成本

第四條把視角從「人」轉到「機器」：一個 skill 在它的執行路徑上，每次都會被完整載入，所以每一個字都是每次執行都要重付的成本。既然如此，寫 skill 的紀律就是：砍掉不會改變 agent 行為的行、把推理過程留在 commit 和 PR 而不是 skill 本文、用名稱直接叫出模型已知的概念而不是長篇解釋、只把「罕見又冗長」的內容拆成另一個檔案。

舉個最常見的違規：「請小心一點」「請仔細思考」「務必徹底檢查」。這些話聽起來很負責任，但模型本來就會這樣做，寫進去只是白白佔用每次載入的預算。真正該寫的是會改變行為的指令，例如「如果找不到測試檔，先問使用者偏好哪種測試框架」。

這條慣例還有具體的執法工具。專案要求每次改動 skill 後跑 npm run check，用一支腳本檢查跨工具相容性與檔案大小預算。這支腳本正是本節第四步的主角。而在那之前，下一課會先把「為什麼一行都算成本」的帳算清楚。

四條其實在講同一件事

把四條並排看，會發現它們其實是同一個信念的四個切面：人類握方向盤、過程誠實、不做靜默決定、對成本有意識。

這也解釋了為什麼讀別人的 skill 時，常常會覺得它「囉唆得很有禮貌」。它反覆把決定權交回給你，把跳過的選項明講出來，把推薦的理由寫在問題旁邊。那背後其實是一套把尊重使用者寫進程式碼的互動契約。等你後面開始改自己的 skill，這四條會是最好的檢查清單。

小結

四條核心慣例共用一個前提：方向盤在工程師手上。慣例一要求 AI 主動發起的檢查只能提議、不能代跑或代改；慣例二把 `/develop` 之後的步驟都設成可跳過的建議，`done` 由工程師宣布；慣例三要求每個問題都帶一個推薦選項與一行理由；慣例四把 skill 的每一行都當成 recurring cost，要求瘦身。四條合起來，就是一套「人類決策、過程誠實」的互動契約。

「每一行都是成本」聽起來像常識，但這筆成本到底花在哪裡、什麼時候最貴，多數人其實沒算過。下一課會把 token 的帳攤開：為什麼一個看起來嚇人的 resident 數字，大部分其實很便宜；以及當你要省錢時，該先砍輸出、砍 fresh input，還是砍檔案大小。
