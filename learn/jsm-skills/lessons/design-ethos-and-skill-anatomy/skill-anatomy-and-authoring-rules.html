Skill 解剖與撰寫規則：一個 skill 該長什麼樣

Step 3/4 · 設計理念與 Skill 解剖

學習目標

能講出一個 skill 的資料夾解剖（SKILL.md、modes、approaches、templates、agents/openai.yaml）與六條撰寫規則，並依「少用且長」的判準決定哪些內容要拆檔、哪些留在 SKILL.md。

前言：同一個 skill，為什麼有人寫得又短又準

上一課你已經拿到成本模型：每一行都是 recurring cost，而且成本分三條載入路徑。但知道「要省」和知道「怎麼寫」，還是兩回事。你可能打開過別人的 skill 檔案，發現它短短幾頁，卻能讓 agent 穩定做出複雜行為；而自己寫的 skill 又長又囉唆，agent 還是常跑偏。

差別通常在兩件事。第一是檔案結構：把不同情境要用的行為，放進不同的檔案，入口只留最常走的那條路。第二是句子層級的紀律：什麼該寫、什麼不該寫、一句話要長成什麼形狀。這一課先把一個 skill 的骨架攤開，再給你六條可以直接拿來檢查自己檔案的撰寫規則。

一個 skill 的資料夾解剖

jsm-skills 的每個 skill 都是一個資料夾。入口固定是 SKILL.md，其他的子資料夾則隨 skill 的需要出現。常見的幾塊是這樣：

檔案或資料夾裝什麼什麼時候被讀
SKILL.md路由器與共用規則：輸出風格、行為分派、前置檢查每次執行都完整載入
modes/各種行為模式，一次只讀一個依當次情境選一個載入
approaches/具名的拆解策略（例如 Tracer Bullet、Skateboard）只在被選中時讀
templates/產出格式的參考，例如 PR、postmortem 模板產出時才讀
agents/openai.yaml給其他工具（如 Codex）的介面轉接層由客戶端載入，本身沒有邏輯

這個結構其實就是上一課「progressive disclosure」的具體實踐。SKILL.md 是牆上的常見症狀表，只放每次都用得到的東西；modes/ 與 approaches/ 是抽屜裡的手冊，依情境挑一本。重點在於「選一個讀」而不是「全部讀」：/scope 規劃時只讀 plan 這一個 mode，加上它選中的那一個 approach，其他模式不會進場。

還有一個容易被忽略的角色是 agents/openai.yaml。它不是給模型看的指令，只是一層薄薄的轉接：提供顯示名稱、簡短描述、預設提示等介面資訊，讓同一份 skill 能被不同工具（Claude Code、Codex）以各自的介面呈現。真正的行為邏輯仍然只在 SKILL.md 裡。這種「一份可攜指令 + 各客戶端的薄轉接」是這個專案能跨工具的原因。

六條撰寫規則

結構決定成本的上限，句子決定成本的下限。以下是這個專案寫 skill 時遵守的六條規則，每一條都可以拿來審自己的檔案。

一、一行必須改變 agent 的行為

如果模型預設就會那樣做，這一行就是純成本、零效益，整句刪掉。最常見的違規是模糊的鼓勵：「請小心」「請徹底」「多想一下」。模型本來就會嘗試做這些事，寫進去只是每次載入都多幾個字。真正該寫的是會改變行為的具體條件，例如「找不到測試檔時，先詢問使用者偏好哪個框架」。

二、給指令，不要給理由

skill 只說「做什麼」。為什麼這樣做、當初考慮過哪些替代方案、這段歷史，都屬於 commit message 和 PR，不屬於 skill 本文。頂多留一個短句的理由，而且只在它能阻止 agent 做錯事的地方才留。把推理搬出 skill，是把它放到一個不用每次載入的地方，並不代表不重視它。

三、叫出概念，不要解釋概念

模型已經懂的標準術語，直接叫名字就好，不必展開定義，例如 idempotent（冪等）、invariant（不變量）、race condition（競態條件）、YAGNI、tracer bullet。真正需要展開的，是這個專案自己發明的詞，例如 Assumed 規格、workflow tier；而且只在一個地方解釋一次，其他檔案直接引用。

四、步驟是指令，不是敘述

步驟不要寫成連貫的段落。每個步驟一到三行，並且以一個「可檢查的條件」收尾，形式是「如果 X，就做 Y」，或是一個核取項目 [ ]，而不是描述接下來會發生什麼。可檢查的意思是：讀完之後，你能明確判斷這個步驟有沒有完成。

五、一條規則只說一次

同一個規則如果出現兩次，刪掉一個，改成指向另一個。唯一的例外是輸出風格區塊：因為每個 skill 必須能獨立安裝與散布，所以這個共用區塊刻意重複放在每個 SKILL.md 裡，而不是抽成共用檔。這不是疏漏，是被規則九特別保護的例外，後面談執法時會再看到。

六、一致的語氣，只定義一次

所有 skill 都用同一種語氣：對使用者說話用「你」，溫暖而直接，把每一步都框成「這是我的建議，你可以跳過」，而不是命令。這段語氣定義在每個 SKILL.md 的共用輸出風格區塊裡，只定義一次。它管的不只是對話，還包括 skill 產生的檔案（scope、spec、verify 報告）。因此模板不該寫進修飾好的段落，模板只帶事實與形狀的簡短提示，由 agent 在產生時套上這套語氣。把語氣再抄進模板，是每執行一次就被收費一次的重複成本。

收尾報告的固定形狀

skill 執行完會印一份總結給人看，而人是快速掃過的。所以這份報告有固定形狀，先講重點，其餘指向檔案：

  • Headline：一行，說明發生了什麼、以及唯一重要的結果。
  • Next：下一步要跑的那一個指令，或待決定的那件事。
  • Heads up：只有真的存在阻礙或需要你決定的事時才出現，絕不為了版面硬湊一個區塊。
  • 指標：指出哪個檔案藏著細節，而不是把細節重印一次。

要砍掉的是「欄位傾倒」和「一連串打勾清單」，例如「語意標籤：正確」「鍵盤操作：可導覽」。這些是確認噪音，或早就寫在檔案裡，不需要再印一次。真正該留的，是對這個 skill 有行動意義的欄位：一個 PASS/FAIL 的判定與其缺口、待修的發現、需要你過目的項目。

什麼時候才該多開一個檔案

這條規則直接連回上一課的判準：只有當一份內容同時「罕見需要」又「很長」時，才把它移到另一個檔案，讓它離開主路徑。罕見但短、或常用但短，都留在原地即可。真的拆檔時，觸發條件要寫明，像是「如果 X，先讀 Y 再繼續」，讓 agent 不會漏掉那個檔案。分檔是為了載入路徑，不是為了資料夾整齊。

提交前的檢查與大小的態度

改完 skill，提交前跑一次 npm run check，它會檢查跨工具相容性與熱路徑大小預算。如果某條路徑接近上限，原則是先刪內容，而不是抬高上限或再加一個檔案。接著重讀一次 diff，找出兩類問題：不改變任何行為的行，以及已經被說過兩次的規則。最後，刪減不應該改變行為；如果某個刪除有可能改變行為，就要明講，並跑一次驗證確認。

至於大小，預算的用途是讓 skill 長大時還能維持精瘦。收到警告代表該刪，不是代表上限訂太低。這些 skill 彼此串接、各自帶著模式，本來就會比單一用途的 skill 大一些，所以目標始終是「刪到剛好」，而不是追求某個固定行數。

小結

一個 skill 的骨架是：SKILL.md 當入口、modes/ 與 approaches/ 依情境各讀一個、templates/ 產出時才讀、agents/openai.yaml 只是薄轉接。六條撰寫規則分別是：一行必須改變行為、給指令不給理由、叫概念不解釋、步驟是可檢查的指令、一條規則只說一次、語氣只定義一次。收尾報告固定為 Headline、Next、必要時的 Heads up，以及一個指向檔案的指標。拆檔的唯一理由是「罕見又長」，且要寫明觸發條件。

規則寫在文件裡，終究會漂移。有人忘了、有人抄錯、有人悄悄把上限調高。下一課要把這些文字規則變成一組可執行的檢查：11 條 lint 規則、byte budget，以及一個很關鍵的設計，警告線要留一段「還在通過就先提醒」的餘裕。
