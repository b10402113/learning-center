除錯不是猜，而是證明：角色與六步迴圈

Step 1/5 · /debug：根因除錯迴圈

學習目標

學完這一節，你應該能說明 /debug 的調查員角色、六步迴圈（reproduce → localize → hypothesize → test → fix → verify）、適合叫用它的時機，以及它和 /loop 的差別。

你也會知道：/debug 只有在無法重現問題時才會發問，而且不會先詢問你是否准許它開始調查。

前言：它好了，然後又壞了

你可能遇過這種情況：測試偶爾紅一次，重跑卻又綠了。使用者回報「有時候存不進去」，但你在自己的機器上怎麼試都正常。

於是你打開出問題的檔案，看見一行可疑的程式碼，順手改掉它。測試通過了，你鬆了一口氣，以為問題已經解決。

幾天後，同一個 bug 從另一個入口冒出來，而且更難追。問題通常不在於你改錯了地方，而在於你的順序反了：你先動手，後理解。

一個沒有真正理解的修補，往往只是把症狀暫時壓下去，病因仍然留在原地。/debug 要做的，就是把順序倒過來：先用證據理解問題，再動手修補。

你的角色是調查員，不是修理工

/debug 對使用者的第一個定位是「調查員」：相信證據，不相信直覺。它把 bug 當成一個需要證明的案件，而不是一場只要趕快平息的事故。

調查時，你要能重現問題，把失敗範圍縮到最小，而且一次只改一個變因。這樣，每次實驗得到的結果才有意義。

有一句話很值得記住：如果你說不出修補為什麼有效，代表你可能還沒抓到 bug。

看到 null 就加一個判斷把它擋掉，看到 crash 就用 try/catch 包起來，這些做法或許能讓錯誤訊息暫時消失，卻沒有回答真正的問題：

  • 它為什麼會是 null？
  • 它為什麼會 crash？

因此，這套流程的目標不是讓症狀消失，而是讓原因被證明。修補只是根因獲得證實後，最後做的那一步。

六步迴圈：把猜測換成證據

/debug 不是「猜一個可能的地方，改改看」。它會依序執行一套固定的調查迴圈：

階段它要回答的問題
reproduce（重現）我能不能讓這個 bug 隨叫隨到？
localize（定位）失敗是從哪一小段開始的？
hypothesize（假設）我認為的根因，能不能被實驗證明是錯的？
test（測試）實驗結果支持假設，還是推翻它？
fix（修補）針對已證實的根因，最小的改動是什麼？
verify（驗證）真的修好了嗎？它會不會再回來？

這裡有一個容易漏掉的重點：如果 test 推翻了假設，流程不會硬著頭皮往下走，而是回到 localize 或 hypothesize，根據新線索再來一輪。

只有當某個假設獲得證據支持，流程才會進入 fix。所以，這不是一條只能往前走的直線，而是像調查員不斷縮小範圍的迴圈。

整個迴圈背後還有一條鐵則：一次只動一個變因。如果你同時改了三個地方，然後 bug 消失，你就不知道究竟是哪個改動有效。下一次問題再出現時，手上也沒有可靠線索可用。

什麼時候該叫用它？

如果你不確定現在是否該使用 /debug，可以先看三個訊號：

  1. 有一個測試失敗，但你暫時看不出原因。
  2. /check verify 執行後，回報某個行為和規格不一致。
  3. 你自己觀察到行為不對，例如按鈕按下去沒有反應。

/debug 常常接手前一個階段留下的失敗。當 /check verify 發現問題時，/check 本身不會修改程式碼，而是把問題指向 /debug 或 /develop。

換句話說，/debug 是「問題已經被發現，接下來要找出成因」的那條路。

它不是 /loop：名字相似，用途相反

這兩個名稱很容易混淆，但它們處理的是完全不同的事情。

/debug 裡的「loop」，指的是單次執行期間反覆進行的調查迴圈，也就是上面的六個階段。/loop 則是另一個獨立的 skill，負責按照時間間隔重複執行一個指令。

/debug/loop
問題型態有一個 bug，需要找出成因有一個指令，需要持續觀察
執行方式在單次執行中反覆進行六個階段按照時間間隔重複執行
典型場合測試失敗、行為不符合規格觀察不穩定的測試多久會失敗一次

判斷方法很簡單：你現在要的是弄清楚某個 bug 為什麼發生，還是要隨著時間觀察某個東西的表現？

如果你想知道一個不穩定的測試跑一百次會壞幾次，這是 /loop 的場合。如果你想知道它為什麼會壞，才是 /debug 的工作。

它平常自己調查，只有無法重現時才提問

/debug 有一個重要的設計：它不會先問你「我可以開始調查嗎？」

重現、追查與修補，都是它會主動執行的工作，不需要你逐項批准。它把工程師當成能夠下判斷的人，而不是每一步都必須蓋章的單位。

它只會在一種情況下反問你：無法從現有資訊重現這個 bug。

這時，它會要求四項資訊：

  • 確切的重現步驟
  • 輸入
  • 環境
  • 你觀察到的行為，以及預期行為

理由很直接：無法重現的問題，就無法證明已經修好。與其憑空猜一個原因，/debug 會先把缺少的條件問清楚，再開始調查。

小結

/debug 把除錯當成一場需要證明的調查，而不是猜一猜、改一改。它扮演的是相信證據勝過直覺的調查員，依序執行 reproduce → localize → hypothesize → test → fix → verify，並且一次只改一個變因。

只要你提供了足以重現問題的資訊，它就會自己一路調查、修補與驗證。只有在無法重現時，它才會回頭詢問四件事：步驟、輸入、環境，以及觀察到的行為與預期行為。

它和 /loop 名字相似，但用途不同：/loop 是按時間重複執行指令，用來持續觀察；/debug 則是用來找出 bug 的成因。

現在，角色與迴圈已經清楚了。下一節會從第一步開始，把模糊的「有時候會壞」變成一條可以隨叫隨到的重現指令，再用二分法把失敗縮到最小範圍。
