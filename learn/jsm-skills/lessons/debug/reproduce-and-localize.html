先重現，再定位：把 bug 縮到最小表面

Step 2/5 · /debug：根因除錯迴圈

學習目標

能依序完成 capture symptom（observed / expected / repro）、取得可重現的確定性重現，並用二分法把失敗縮到最小表面（二分程式路徑、二分歷史 git bisect、讀真實值）。

前言：一句「有時候會壞」沒辦法修

上一節建立了調查員的角色和六步迴圈，我們知道第一件事是重現。這一節就從那個最尷尬的起點開始：使用者跟你說「登入有時候會失敗」。

這句話幾乎沒辦法直接動手。什麼叫有時候？是特定帳號、特定瀏覽器，還是特定時間？如果連你自己都沒看過它壞，你怎麼知道等一下的修改有沒有真的把它修好？

所以 /debug 一開始不會急著打開程式碼，而是先把症狀問清楚、想辦法讓它隨叫隨到，再把失敗的範圍一層一層縮小。這一步做扎實，後面找原因會快很多；這一步偷懶，後面就會變成一場猜謎。

Step 0：先把症狀講精確

在碰任何程式碼之前，/debug 要求先把三件事釘死：

欄位要寫什麼
Observed（觀察到）實際的錯誤訊息、stack trace、錯誤輸出或截圖
Expected（預期）你本來以為會發生的行為
Repro（重現）能觸發它的步驟、輸入與環境

這三格看起來很基本，卻是最常被跳過的地方。很多時候「觀察到」和「預期」之所以對不起來，是因為其中一格根本沒被寫清楚。如果這三件事有任何一項不清楚，而且你自己也推不出來，那就問。理由很簡單：連重現都做不到的東西，根本無從除錯起。

Step 1：想辦法讓它隨叫隨到

症狀清楚了，下一步是拿到一個確定性的重現，一個測試、一道指令、一個請求，每次執行都會穩定地觸發這個 bug。

如果它是間歇性的，任務就變成找出「是什麼讓它變成確定」。常見的原因有幾種：時間相關（只在跨日或特定時區出錯）、執行順序（A 先跑完才出問題）、資料相關（只有某筆特定資料會踩到）、並行（多個請求同時跑才撞在一起）。把這些因素一個一個固定下來，間歇性常常就會變成穩定可重現。

這裡有一條判準很硬：不能隨叫隨到的 bug，你就不能證明自己修好了。如果試到最後真的重現不了，正確的做法是加一段 instrumentation（在關鍵位置埋記錄或監測）去等它自己現形，並且老實說出「目前還重現不了」。最糟的做法是假裝找到原因、盲修一發。

Step 2：定位，把失敗縮到最小

有了重現，接下來在開始猜原因之前，要先做一件事：把失敗縮到最小的可能範圍。範圍越小，你後面要考慮的假設就越少。定位有三個手段。

二分程式路徑

第一種是二分程式路徑。想像資料從「好的輸入」一路流到「壞的輸出」，中間一定有一個點是好的變壞的分界。二分法就是不斷往中間切：在程式碼中段印出當下的值，看它到這裡還是好的、還是已經壞了。如果中段還是好的，問題就在後半段；如果中段已經壞了，問題就在前半段。每切一次，範圍減半。工具可以是中段的 log、中斷點，或暫時註解掉後半段。

這就像玩猜數字遊戲，每次砍掉一半的候選範圍。比起從頭一行一行讀，二分能快很多地帶你逼近現場。

二分歷史

第二種是二分歷史。如果這是一個 regression（以前正常、最近才壞掉的問題），那答案可能不在程式碼本身，而在某一次改動裡。這時可以用 git bisect 沿著 commit 歷史二分，找出是哪一次改動引進了這個 bug；如果嫌 bisect 麻煩，也可以在可疑的檔案上跑 git log -p，逐筆看改動內容。

二分歷史的價值在於，找到「哪一次改動」通常就直接指出了成因，因為那次改動的意圖和這個 bug 往往只差一步。

讀真實的值，不要用猜的

第三種最容易被忽略：去讀真實的值。在資料的邊界，也就是輸入進來、輸出出去的地方，把實際的值印出來或記錄下來，而不是憑印象假設它是什麼。

很多 bug 拖很久，就是因為大家對某個值「想當然耳」。你以為 userId 一定是數字，結果它是字串；你以為那個欄位一定有值，結果它偶爾是 null。親眼看到值的那一秒，往往比讀十遍程式碼更有用。

小結

重現與定位是後面所有推理的地基。先做 Step 0，把 observed、expected、repro 三格寫清楚，不清楚就問。再做 Step 1，拿到一個隨叫隨到的確定性重現，間歇性就找出讓它變確定的因素，真的重現不了就加 instrumentation 並老實說，不盲修。最後做 Step 2，用二分程式路徑、二分歷史（git bisect）和讀真實值，把失敗縮到最小的範圍。

範圍縮小之後，你手上多半已經有一個隱約的猜想。下一節要處理的，就是怎麼把這個猜想變成一個可以被證明是錯的假設，並且一次只驗一個。
