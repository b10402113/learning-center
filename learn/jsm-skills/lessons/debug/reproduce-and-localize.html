先重現，再定位：把 bug 縮到最小範圍

Step 2/5 · /debug：根因除錯迴圈

學習目標

完成這一節後，你應該能依序做到三件事：記錄清楚 Observed、Expected、Repro；取得每次都能觸發問題的確定性重現；再用二分法縮小失敗範圍，包括二分程式路徑、二分 Git 歷史，以及直接讀取真實值。

前言：一句「有時候會壞」還不能拿來除錯

上一節建立了調查員的角色與六步迴圈，也確認了第一件事是重現問題。現在就從最常見、也最尷尬的起點開始：使用者告訴你「登入有時候會失敗」。

這句話幾乎無法直接拿來修。所謂「有時候」是特定帳號才會發生，還是只在某種瀏覽器、某個時間，或某種資料下發生？如果你自己從沒看過它壞，又怎麼知道下一次修改真的修好了？

因此，/debug 不會一開始就衝進程式碼裡找可疑的那一行。它會先把症狀問清楚，再設法讓問題變成每次都能出現，最後一層一層縮小失敗範圍。這就像先把迷霧變成地圖；地圖越清楚，後面的推理就越快。反過來，如果一開始就猜原因，除錯很容易變成猜謎。

Step 0：先把症狀說精確

碰任何程式碼以前，/debug 會先要求把三件事固定下來：

欄位要寫什麼
Observed（觀察到）實際看到的錯誤訊息、stack trace、錯誤輸出或截圖
Expected（預期）原本預期應該發生的行為
Repro（重現）能觸發問題的步驟、輸入與環境

這三格看似基本，卻是最常被略過的地方。很多「實際結果」和「預期結果」對不起來，不是程式真的那麼神祕，而是其中一格根本沒有寫清楚。

只要有任何一項不明確，而且你自己也推不出來，就應該先問清楚。理由很直接：連問題怎麼重現都不知道，就沒有穩固的基礎可以開始除錯。

Step 1：讓 bug 變成隨叫隨到

症狀清楚之後，下一步是取得一個確定性的重現。它可以是一個測試、一個指令，或一個請求；重點是每次執行，都能穩定觸發同一個 bug。

如果問題原本是間歇性的，任務就變成找出：究竟是什麼因素，讓它從「偶爾發生」變成「一定發生」。常見因素包括：

  • 時間相關：只有跨日或特定時區才出錯。
  • 執行順序：必須先完成 A，後面才會出問題。
  • 資料相關：只有某一筆特定資料會踩到問題。
  • 並行：多個請求同時執行時才會互相撞上。

把這些因素逐一固定下來，間歇性問題常常就會露出固定的形狀。

這裡有一條很硬的判準：不能隨叫隨到的 bug，就不能證明自己修好了。 如果試到最後仍然無法重現，正確做法是加入 instrumentation，也就是在關鍵位置埋下記錄或監測，等待問題自己現形。同時要清楚說明「目前還無法重現」。

最糟的做法，是假裝已經找到原因，然後盲目修改一處程式碼。那樣得到的可能只是一次沒有再出現的錯誤，而不是一個被證明修好的 bug。

Step 2：定位，把失敗縮到最小範圍

拿到可重現的案例後，先不要急著猜原因。下一步是把失敗縮到盡可能小的範圍。候選範圍越小，接下來要驗證的假設就越少。

可以使用三種定位方法。

二分程式路徑

第一種方法是二分程式路徑。把資料想成從「好的輸入」一路流向「壞的輸出」，中間一定有某個位置，讓它從好變壞。

做法是不斷從中間切開：在程式碼的中段記錄當下的值，確認資料走到這裡時仍然正常，還是已經變壞。如果中段仍然正常，問題就在後半段；如果中段已經錯了，問題就在前半段。每切一次，候選範圍就減少一半。

可以使用中段的 log、中斷點，或暫時註解掉後半段。這就像猜數字遊戲，不是從 1 開始逐個猜，而是每次砍掉一半可能性，快速逼近真正出問題的位置。

二分歷史

第二種方法是二分歷史。如果這是一個 regression，也就是過去正常、最近才壞掉的問題，答案可能不在某段孤立的程式碼裡，而在某一次改動。

這時可以使用 git bisect 沿著 commit 歷史二分，找出是哪一次改動引進 bug。如果不想使用 bisect，也可以針對可疑檔案執行 git log -p，逐筆檢查變更內容。

二分歷史的價值在於，找到「哪一次改動」往往就已經非常接近成因。因為那次改動原本想完成的事情，通常只需要再對照一次 bug 的行為，就能看出兩者在哪裡接上。

讀真實值，不要靠猜

第三種方法最容易被忽略：直接讀真實值。在資料進入與離開的邊界，把實際值印出來或記錄下來，不要只憑印象假設它應該長什麼樣子。

許多 bug 之所以拖了很久，是因為大家對某個值「想當然耳」。你以為 userId 一定是數字，實際上它可能是字串；你以為某個欄位一定有值，實際上它偶爾可能是 null。

親眼看到真實值的那一刻，往往比把同一段程式碼讀十遍更有用。除錯不是把猜測說得更有把握，而是把猜測換成可以檢查的事實。

小結

重現與定位，是後續所有推理的地基。先做 Step 0，把 Observed、Expected、Repro 三格寫清楚；不清楚就問。接著做 Step 1，取得一個隨叫隨到的確定性重現。遇到間歇性問題，就找出讓它變得確定的因素；真的無法重現時，就加入 instrumentation，並老實說明目前的狀態，不要盲修。最後做 Step 2，透過二分程式路徑、二分歷史（git bisect）和讀取真實值，把失敗縮到最小範圍。

當失敗範圍縮小之後，你手上通常已經有一個初步猜想。下一節要做的，就是把這個猜想改寫成一個可以被證明錯誤的假設，並且一次只驗證一個。
