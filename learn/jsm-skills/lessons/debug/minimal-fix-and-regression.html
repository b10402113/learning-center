最小修補、回歸測試與同源兄弟

Step 4/5 · /debug：根因除錯迴圈

學習目標

找到根因之後，只做針對它的最小修補，不順手重構，也不偷偷加入新功能。接著透過重跑重現、周邊測試、回歸測試，以及尋找同源兄弟，把修補確實鎖住。

前言：找到原因後，最容易修過頭

上一節你終於證實了根因。這通常是整場除錯裡最想「順便做點事」的時刻：既然檔案已經打開了，旁邊那個醜陋的函式要不要一起整理？那個命名早就想改了，要不要順手處理？還有一個小功能，看起來好像也能一起加進來。

這些念頭都很合理，卻會讓修補變得難以驗收。當 diff 混進太多無關變更，大家就很難判斷哪一行真正修好了 bug；日後若需要回滾，也會被那些「順手做的事」綁住。

因此，這一節只守一條主線：針對已證實的根因做最小改動，再用幾道檢查把成果固定下來，避免 bug 悄悄回來。

Step 5：修在根處，而且只修最少

/debug 在修補階段要求「最小、針對性」。這裡的最小，不是單純追求最少程式碼行數，而是讓改動範圍只涵蓋已證實的根因。你已經知道問題從哪裡來，就直接處理那個原因，不要繞去改一堆無關的地方。

例如，根因是「上游傳進來的值是 null」。修因，是追查上游為什麼會產生 null，並處理那個產生點；修症狀，則是在下游補一行「如果是 null，就當成 0」。後者也許能讓眼前這個錯誤暫時消失，卻沒有回答 null 從哪裡來。問題只是換個地方埋下，像把定時炸彈從桌面塞進抽屜。

同一條紀律也排除兩種常見誘惑。第一是 scope creep（範圍蔓延）：修 bug 時順手重構旁邊的程式碼。第二是偷偷加入功能：反正檔案都改了，多做一點似乎也沒關係。

這兩種做法都會讓 diff 變大，直到沒人分得清哪一行才是真正的修補。修 bug 不是偷偷換一套程式風格的時候，因此仍要遵循專案既有慣例：讀 AGENTS.md，也參考相鄰程式碼的寫法。

/debug 負責什麼，又刻意不做什麼

/debug 的工作邊界很清楚：針對已證實根因，做最小的程式修補。其他事情不要混進來。這條界線能幫你判斷，眼前的問題究竟適合交給誰處理。

它會做它不會做
針對已證實根因的最小修補偷做新功能
建議把回歸測試交給 /test，或直接寫一段先壞後好的測試順手重構無關的程式碼
如果 bug 揭露設計缺陷，就指出問題並導向 /architect重寫規格

最後一列尤其重要。有些 bug 看起來像是某一行寫錯，追查後才發現，真正的問題是當初的設計決策本身不成立。這時不該用程式碼把症狀蓋住，而要把設計問題清楚指出來，交給 /architect 處理。真正的修法可能是修改規格，而不是再補一行程式碼。

Step 6：驗證，然後把修補鎖住

程式改完不代表工作結束。/debug 還要完成四項驗證，分別確認「現在真的修好了嗎」以及「以後還會不會再犯」。

一、重跑 Step 1 的重現

先回到第一節建立的確定性重現，再跑一次，確認它現在會通過。這是最直接的證據：原本可以穩定觸發的失敗，現在已經穩定地不再發生。

二、跑周邊的測試套件

單一案例通過還不夠。修補可能改變其他行為，因此要跑周邊的測試套件，確認沒有造成 regression，也就是沒有把原本正常的功能弄壞。

三、加入真正有效的回歸測試

這是最關鍵的一道防線：加入一個在沒有修補時會失敗、加入修補後才會通過的回歸測試。它的任務是讓這個 bug 不能悄悄回來。

你可以直接在這次變更中加入測試，也可以把測試需求交給 /test。但要小心「假綠測試」：如果測試不曾在修補前失敗，或無法區分「修好了」與「沒修好」，那盞綠燈只是安慰，不能證明修補有效。

四、找出同源的兄弟

同一個根因往往不只出現在一個地方。相同的程式模式或錯誤假設，可能早已被複製到其他檔案。這時要用 grep 搜尋整個專案，找出同源的兄弟。

找到之後，能修的就一起修；目前不能修的，至少要記錄下來。否則你可能只是把同一個問題從一個入口堵住，其他入口仍然敞開。

四項檢查各自回答不同問題：重跑重現與周邊測試，確認這次現在真的修好了；回歸測試與同源兄弟檢查，則是保護未來，避免同一個問題再次出現，或藏在其他地方繼續發作。

小結

修補的紀律是「最小、針對根因」。修的是原因，不是症狀；不順手重構，不偷做功能，並遵循專案既有慣例。當 bug 揭露的是設計決策缺陷，而不是單純的程式錯誤，/debug 應該把問題導向 /architect，而不是用程式碼遮住它。修完後，再用四件事鎖住成果：重跑重現、執行周邊測試、加入一個沒有修補就會失敗的回歸測試，以及用 grep 找出同源的兄弟。

到這裡，一圈完整的根因迴圈就走完了。最後一節會處理兩個問題：一場不簡單的追查，是否該交給子代理；以及結束時的報告該怎麼寫，才能讓人一眼看見重點。
