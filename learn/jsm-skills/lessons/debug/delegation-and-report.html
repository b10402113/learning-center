交給子代理，並用根因收尾

Step 5/5 · /debug：根因除錯迴圈

學習目標

這一節要學會兩件事：判斷什麼時候該把調查交給子代理，以及如何用「先講根因與修補」的格式收尾報告。

子代理不是隨手丟出去的幫手。你需要明確指定較強的模型、可用工具與完整提示內容；如果最後發現問題其實來自設計決策，而不是某一行程式，就要改由 /architect 接手。

前言：追查越久，對話框越吵

前面四節已經把除錯迴圈走過一遍。但實際遇到的 bug，未必會乖乖在幾步內現形。有些問題需要反覆讀檔、執行指令、搜尋線索，再回頭讀更多檔案，來來回回幾十次。

如果所有過程都塞在同一個對話裡，主上下文很快會被中間步驟填滿。模型到了後面，可能忘記前面已經排除過哪些可能，像是桌面堆滿便條紙，真正重要的線索反而被壓在底下。

這一節處理兩個收尾功夫：第一，把複雜而吵雜的調查交給子代理；第二，結束時把報告寫成真正有用的結論，而不是一長串流水帳。

什麼時候該把調查外包

/debug 提供了一個清楚的判斷點：當追查「不簡單」時，就開一個子代理處理。

這裡的「不簡單」，通常是指需要大量重複工具操作。把這些反覆迭代留在子代理裡，主對話就能保留乾淨的上下文，專心負責決定方向與和你溝通。

分工可以想成這樣：主線是指揮台，負責判斷下一步；子代理則埋頭處理吵雜的查檔、搜尋與驗證工作，最後只把結論帶回來。這和前面幾個階段用子代理做唯讀探索，是同一套分工邏輯。

子代理怎麼設定

設定子代理時，有幾個欄位不能省略：

欄位要求
model明確指定一個較強的模型，不要繼承當前 session 的模型（以 Claude Code 為例是 sonnet）
description寫成 "Debug: <symptom>"，讓人一眼知道它正在查什麼
工具Read、Bash、Grep、Glob、Edit、Write
prompt直接內嵌整條迴圈、捕捉到的症狀、重現步驟，以及相關的 AGENTS.md

先看模型設定。為什麼不能直接沿用當前 session 的模型？因為除錯品質不該取決於你開場時剛好選了哪個模型。

如果一開始使用較弱的模型，子代理又直接繼承它，那麼這次重要的除錯工作也會交給同樣的模型。明確指定模型，就是在需要時替調查工作準備足夠的能力，而不是把結果交給 session 的歷史設定決定。

再來是 prompt。除了症狀與重現步驟，也要要求子代理「回報根因並附上證據」，不能只回一句「我修好了」。

子代理的輸出是你能直接檢查的結果。如果它只有結論、沒有證據，你無法判斷它是真的找到根因，還是只是把表面症狀壓下去。要求證據，正是把「先證明，再動手」延續到子代理身上。

報告：先講根因，過程是附錄

不管有沒有使用子代理，收尾都應該產出一份報告。/debug 對報告的要求，可以濃縮成一句話：

先寫根因與修補，再寫重現、證據與後續動作。

讀報告的人通常最想先知道三件事：哪裡壞了、怎麼修、接下來要做什麼。如果一開始從「我先做了 A，接著做了 B」講起，讀者得讀完整段過程，最後才拿到真正的結論。

把結論放在前面，就像先把地圖上的目的地圈出來，再補上沿途走過的路。過程仍然重要，但它是用來支持結論，不該把結論藏起來。

報告模板如下：

## /debug complete · <the bug, one line>

**Root cause: <the proven cause>. Fixed by <the minimal change, files touched>.**
Next: /test <feature>   (lock in the regression test, added inline or handed over)
Heads up: <same cause also at <where>, fixed too · or a design flaw → /architect <what>>   (omit if none)

拆開來看，第一行是這個 bug 的一句話描述。

第二行是整份報告的核心：已經證明的根因，以及修補方式。這裡要說明最小變更和碰過哪些檔案。

第三行是下一步，通常是把回歸測試鎖進 /test。測試可以直接加入，也可以交給下一個階段處理。

第四行是提醒欄位，只有在發現同一個根因還出現在其他位置，或發現設計缺陷時才需要寫。沒有這類事項，就整行省略。

當原因不是寫錯，而是想錯

除錯時，最後可能發現問題不是某一行程式寫錯，而是當初採用的決策本身有問題。

這時不能只用程式碼把症狀蓋住。正確修法可能不是改一行，而是回頭修改規格或設計。若把這種問題當成普通 bug 處理，就會錯過真正該修正的地方。

因此，這類設計缺陷必須放在報告的醒目位置，並把問題導向 /architect。這也再次說明流程中的分工：每個 skill 負責自己的階段，不越界替另一個階段做決定。

小結

當一場追查需要大量反覆操作時，把它交給子代理，避免中間過程吃掉主對話的上下文。子代理要明確指定較強的模型，附上工具集，prompt 要內嵌整條迴圈、症狀、重現步驟和相關的 AGENTS.md，並要求它回報根因時附證據。收尾報告先講根因與最小修補，再放下一步與提醒，重現與證據只是佐證。如果問題的根源是決策缺陷而不是程式錯誤，就把這件事放頭條，並指向 /architect。

五步走完，你手上就有一套完整的根因除錯法：先建立調查員的心態，再重現與定位，接著提出可否證的假設並進行實驗，完成最小修補與回歸保護，最後處理複雜調查與收尾報告。

下一次測試不明原因變紅時，你不必憑感覺亂改。先判斷是否值得交給子代理，再用根因、證據與下一步把結果寫清楚；如果真正的問題是設計決策，就把它送往 /architect。
