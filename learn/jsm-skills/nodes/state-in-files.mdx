# 狀態在檔案：四種檔與固定擁有權

## Learning goal

說出 AGENTS.md（巢狀）/ scope / specs / design.md 各由誰建立、誰讀、誰改，並解釋「狀態放檔案」為何可跨 session、跨團隊。

## Steps

這條路徑先回答「為什麼」，再回答「有哪些檔」，接著攤開擁有權表，最後收在「所以它才能跨 session、跨團隊」。照順序讀，每一步都接在前一步上。

1. [[learn/jsm-skills/nodes/state-in-files/why-state-in-files|為什麼狀態要放檔案，而不是留在對話裡]] — 從「功能愈加愈難改」的衰敗現象，說明狀態為什麼必須離開對話
2. [[learn/jsm-skills/nodes/state-in-files/four-kinds-of-state-files|四種狀態檔：AGENTS.md、scope、specs、design.md]] — 認識四種檔各放什麼、住哪裡，以及 AGENTS.md 的巢狀規則（接在第 1 步之後）
3. [[learn/jsm-skills/nodes/state-in-files/who-owns-which-file|誰建立、誰讀、誰改：固定擁有權]] — 用一張表對照每個檔的建立者、讀者、修改者與 spec 狀態線（接在第 2 步之後）
4. [[learn/jsm-skills/nodes/state-in-files/state-survives-handoffs|狀態如何跨 session、跨團隊存活]] — audit 從真實專案寫入、sync 對帳，讓檔案在換手後仍可信（接在第 3 步之後）

## Lesson

這節課要解的，是整套工作流最底層的那個決定：專案的知識要放在哪裡。放對話裡，它會隨著一次 `/clear`、一次換人、一次隔週回來而蒸發；放檔案裡，它才會留下來。

工作流把事情拆成四種檔：告訴每個 skill「這個專案怎麼運作」的 `AGENTS.md` 巢狀 context 檔、記錄「要蓋什麼、什麼順序」的 scope、把每個真實決定寫下來的 spec，以及保存 UI 風格方向的 `design.md`。四種檔各自有明確的家，也各自有固定的建立者、讀者與修改者。

擁有權固定，是這些檔不會在幾個月後糊成一團的原因：只有 `architect` 寫 spec 內容、只有 `develop` 動 spec 的狀態行、`audit` 建 context 檔、`sync` 對帳。走完四步之後，你應該能看著任何一個狀態檔，說出它從哪來、該由誰改，以及為什麼換個 session 或換個隊友，工作還能接得下去。
