# /check：合併前的驗證與審查

## Learning goal

能用 `/check verify` 實跑證明行為符合規格、用 `/check review` 讓不同模型對 diff 做資深審查，並知道兩者都不改碼、失敗時該丟回哪裡。

## Steps

1. [[learn/jsm-skills/nodes/check/routing-gate|/check 入口：兩個模式，而且它不猜]] — 認得兩個模式，以及那道不猜的路由閘
2. [[learn/jsm-skills/nodes/check/verify-runtime-proof|verify：把應用跑起來，用證據下判斷]] — 載入規格、實跑、記證據、逐條裁決 (after step 1)
3. [[learn/jsm-skills/nodes/check/review-cross-model|review：換一個模型，替你看見盲點]] — 跨模型不變量與唯讀審查子代理 (after step 1)
4. [[learn/jsm-skills/nodes/check/review-rubric|review 的尺：嚴重度、裁決與發現清單]] — 審查子代理用的評分標準 (after step 3)

## Lesson

`/check` 是合併前的那道關卡，它把兩件事拆成兩個模式。`verify` 站在驗收工程師的位置，真的把應用跑起來、操作一遍，用現場看到的證據去證明行為符合規格；`review` 則換一個沒寫過這段碼的模型，用資深工程師的眼睛對 diff 做審查。這裡有一個很容易被誤會的地方：兩個模式都不改程式碼，它們只負責判斷，修補是 `/debug` 與 `/develop` 的事。

這個節點分四步。先把入口看清楚，尤其是那道「沒給模式就停下來問、絕不自己猜」的路由閘。接著一路走完 `verify`：怎麼把規格裡的驗收條件變成可觀察的行為、怎麼依 build approach 校準「怎樣才算真的會動」、怎麼記下證據帳，最後用證據閘做出逐條裁決。再轉到 `review`：先講那個不能彎的跨模型不變量，以及審查子代理是怎麼被叫起來的；然後看子代理手上那把尺，也就是檢查優先序、四級嚴重度、四種裁決和 findings 格式。

走完這節，你應該能在自己的練習專案上真的跑一次 `/check`，不管是 `verify` 還是 `review`，都清楚它要看什麼、要留下什麼，以及失敗時該把問題丟回流程裡的哪一關。
