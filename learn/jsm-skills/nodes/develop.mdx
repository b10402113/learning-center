# /develop：依規格實作

## Learning goal

能在已核准 spec 與專案慣例上分軌實作（UI track vs logical track），選對 UI 的四條來源與 build/git 流程，並貫徹「刪除被取代的碼」。

## Steps

1. [[learn/jsm-skills/nodes/develop/spec-gate|規格閘門：先確認決策有人做過]] — 用 input coverage 測試判斷有沒有決策欠著，分清 load bearing 與 local detail，選對三條出路
2. [[learn/jsm-skills/nodes/develop/build-flow|開工流程：分軌、載入規格、探索後動手]] — 判斷 UI／Logical／Both 軌，載入規格與慣例，隔離探索，從 build plan 續做（after step 1）
3. [[learn/jsm-skills/nodes/develop/ui-track|UI 軌：四條設計來源與產品級版面]] — 完成標準與失格清單、四條設計來源、設計先行整合其次的兩趟走法（after step 2）
4. [[learn/jsm-skills/nodes/develop/logical-track|Logical 軌：從資料層到介面的七個階段]] — 資料層、核心邏輯、介面、整合與正確性安全檢查（after step 2）
5. [[learn/jsm-skills/nodes/develop/cleanup-and-finish|收尾：刪掉被取代的碼、更新 scope、走 git]] — 刪淨舊碼並證明無人引用、更新 scope 與 spec 狀態、發出 verify 步驟、分支與提交（after steps 2, 3, 4）

## Lesson

`/develop` 是這套工作流裡唯一真正動筆寫產品程式碼的階段。它站在兩個前提下工作：決策已經被想過，專案慣例已經被寫下來。所以它一開始做的事不是寫碼，而是先過一道規格閘門，確認要蓋的東西有人畫過圖。只要有一個會影響驗收的決策還沒被記錄，它就停下來把你送回 `/architect`，或用一紙 `Assumed` spec 先把假設釘進 repo，而不是在對話裡默默發明一個。

過了閘門之後，同一個節點分成兩條平行軌道：UI 軌處理畫面，Logical 軌處理資料與邏輯，一個功能可以只走一條，也可以兩條都走。兩條軌各自有它的完成標準。UI 軌的標準是「一個專業產品的完整版面」，不是一個孤零零的表單；它要求先設計、後整合，並且從四條設計來源（Figma、貼上的圖、既有設計系統、從零生成）中選對一條。Logical 軌的標準是把 `/architect` 的決策忠實落地：不變量放進資料庫、金流與訊息做冪等、介面層做授權而不只是驗證。

兩條軌最後在收尾階段合流。這裡有兩個最容易漏掉、卻最能區分「真的做完」與「看起來做完」的動作：一是把被取代的舊碼刪乾淨，並證明沒有任何人還在引用它；二是外科手術式地只更新該動的那幾行 scope 與 spec 狀態，把「哪些事真的落地了」誠實記下來。`/develop` 只負責建置與誠實回報，`/check`、`/test`、`/sync` 都是它建議但不代跑的下一步。
