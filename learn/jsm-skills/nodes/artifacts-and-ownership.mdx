# 知識載體與擁有權

## Learning goal

能說清 `AGENTS.md` / `docs/scope` / `docs/specs`（＋`design.md`）各自裝什麼、誰擁有、誰能改，以及 acceptance criteria 與 tier 深度（Prototype → GA）如何貫穿整條流程。

## Steps

1. [[learn/jsm-skills/nodes/artifacts-and-ownership/files-carry-the-work|檔案才是記憶：四種知識載體]] — 為什麼狀態活在檔案裡，以及四種載體各自裝什麼
2. [[learn/jsm-skills/nodes/artifacts-and-ownership/spec-lifecycle|一份 spec 的一生]] — Proposed → In Progress → Accepted，外加 Assumed 與 Superseded（after step 1）
3. [[learn/jsm-skills/nodes/artifacts-and-ownership/ownership-map|誰能動哪個檔案]] — 建立者、讀者、修改者，以及單一擁有者紀律（after steps 1–2）
4. [[learn/jsm-skills/nodes/artifacts-and-ownership/acceptance-criteria-thread|把決策一路串到測試]] — 一條 acceptance criterion 從規格走到程式、驗證與測試（after step 2）
5. [[learn/jsm-skills/nodes/artifacts-and-ownership/workflow-tiers|驗證深度：Prototype 到 GA]] — 四種深度各跑什麼，以及為什麼是建議不是關卡（after steps 3–4）

## Lesson

這節課回答一個問題：這套工作流把「專案知道的事」放在哪裡。答案不是某個模型的記憶，也不是某串對話，而是四種活在 repo 裡的檔案。`AGENTS.md` 記專案怎麼運作（stack、指令、慣例），`docs/scope/` 記要做什麼、什麼順序，`docs/specs/` 記每一個做過的決定，`design.md` 記介面的美術方向。四種檔案各有唯一的建立者、讀者與修改者，這條擁有權規則就是它們不會隨時間糊成一團的原因。

檔案之所以能撐起整條流程，還靠兩條貫穿的線。第一條是 acceptance criteria：規格把每個需求寫成編號的「做完了算什麼」，之後的程式、驗證、測試都回指同一批編號。第二條是 tier 深度：`Prototype` 到 `GA` 只決定 `/develop` 之後「預設」跑多少驗證，它永遠是建議不是關卡。走完這五步，你會看懂為什麼 jsm-skills 敢讓 stage 之間清掉 session——因為真正重要的東西從一開始就不在對話裡。
