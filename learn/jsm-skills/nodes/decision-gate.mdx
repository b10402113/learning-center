# 決策閘門與 acceptance-criteria 主線

## Learning goal

解釋「沒決定就別蓋」的閘門、`Assumed` spec 的意義與 ratification，以及一條需求如何從 spec → code → verify → test 一路追。

## Steps

前兩步把主線拉出來：先看一條需求如何被編號、被追蹤，再看 `/develop` 用什麼機械檢查在動手前攔下「還沒決定的東西」。中間兩步處理攔下來之後的兩條路：把決策記成 `Assumed` spec 先蓋，之後再補 ratification。最後一步攤開 spec 的五個狀態，把前面出現過的 `Assumed` 放回完整的生命週期裡看。

1. [[learn/jsm-skills/nodes/decision-gate/acceptance-criteria-thread|一條需求一路追：acceptance-criteria 主線]] — 認識從 spec 編號到 test 的那條追蹤線，以及它為何是整套流程的誠實機制
2. [[learn/jsm-skills/nodes/decision-gate/spec-gate|沒決定就別蓋：/develop 的 spec 閘門]] — 跑 input coverage 檢查，分辨載重決策與本地實作細節（接在第 1 步之後）
3. [[learn/jsm-skills/nodes/decision-gate/assumed-spec-escape-hatch|Assumed spec：先蓋再記的逃生口]] — 認識攔下之後的第三個選項、assumed spec 的三個欄位，以及它為何不擋 done（接在第 2 步之後）
4. [[learn/jsm-skills/nodes/decision-gate/ratify-assumed|Ratification：把暫定決策補成正式決策]] — 對著已蓋的程式碼重跑設計對話，依假設成立或錯誤收尾（接在第 3 步之後）
5. [[learn/jsm-skills/nodes/decision-gate/spec-status-lifecycle|Spec 狀態一覽：Proposed 到 Superseded]] — 攤開五個狀態與兩種狀態行為，知道每個狀態由誰設定（接在第 2 步之後）

## Lesson

這節課繞著同一條線打轉：一條需求從被決定的那一刻起，怎麼一路被追到測試裡。

核心是 acceptance criteria。`architect` 寫 spec 時，會把每一條需求變成一條短短的、有編號的「什麼叫做完成」。之後 build plan 的每個任務都要指名它服務哪一條編號，`develop` 寫的檢查步驟也回指同一批編號，`check verify` 把它們在真實 app 上跑一遍，`test` 再把長久有效的那些鎖進測試套件。於是同一條需求可以拉成一條直線：決策 → 滿足它的程式碼 → 證明它會動的證據 → 保住它不會壞的測試。

要讓這條線成立，前提是「沒決定就別蓋」。`/develop` 動手前一定會過一道閘門，用機械的 input coverage 測試問：這次 build 必須產生的每個值，spec 有沒有指名它從哪來？只要有一個來源沒被指名，就代表有一個決策還沒做。閘門不會幫你猜，它給三條路：先回 `/architect` 把決策寫成 spec、判斷這裡其實沒決策可以直接蓋、或是先寫一份 `Assumed` spec 把假設記下來再蓋。第三條路是這節課的重點——它讓你想往前衝的時候有路可走，同時把決策從對話裡撈出來、釘進 repo。

但先蓋的帳一定要還。`Assumed` spec 會一直掛著「欠 ratification」的記號，直到 `/architect` 對著實際蓋出來的程式碼重跑一次設計對話：假設成立就補上真正的理由並清掉 `Assumed`；假設錯了就寫一份修正版 spec，把舊的標成 `Superseded`，請你照新決定重做。這門記號從不阻擋你把 feature 標成 done，卻保證沒有哪個真實決策會永遠躲在對話裡。
