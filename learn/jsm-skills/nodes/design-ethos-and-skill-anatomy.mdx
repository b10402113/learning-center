# 設計理念與 Skill 解剖

## Learning goal

能用四條核心慣例（engineer decides、suggestions never gates、one recommended option、keep skills lean）與 progressive disclosure／token 預算，解釋一個 skill 為什麼這樣設計、要怎麼拆檔。

## Steps

1. [[learn/jsm-skills/nodes/design-ethos-and-skill-anatomy/four-conventions|四條核心慣例：誰握方向盤]] — 四條慣例各在防哪一種失敗，以及它們如何共用同一個前提：工程師握方向盤
2. [[learn/jsm-skills/nodes/design-ethos-and-skill-anatomy/token-budget-and-progressive-disclosure|Token 預算與 progressive disclosure]] — 為什麼每一行都是每次載入的成本，以及該砍輸出還是砍 resident 檔（after step 1）
3. [[learn/jsm-skills/nodes/design-ethos-and-skill-anatomy/skill-anatomy-and-authoring-rules|Skill 解剖與撰寫規則]] — 一個 skill 的檔案結構與六條作者規則，以及「少用且長」才拆檔的判準（after steps 1–2）
4. [[learn/jsm-skills/nodes/design-ethos-and-skill-anatomy/enforcement-and-lint-rules|把慣例變成守門員]] — 用 11 條可執行檢查、byte budget 與 warn-before-fail 頻帶擋住風格與預算漂移（after step 3）

## Lesson

這一節回答的是「jsm-skills 的 skill 為什麼長這樣」。前面已經看過整套工作流的階段與知識載體；但同一件事，為什麼它選擇用 `SKILL.md` 當入口、把長內容拆成 `modes/` 與 `approaches/`、還特地寫一支腳本替 prompt 做 lint？答案不在單一 skill 裡，而在四條貫穿全部檔案的設計慣例。

這四條慣例說穿了只有一個前提：**方向盤在工程師手上，AI 只負責把選項和後果講清楚。** 由此推導出「AI 發起的檢查只能提議、不能代跑」「流程建議不是關卡、`done` 由工程師宣布」「每個問題都帶一個推薦選項」「skill 要精簡，因為每一行都是 recurring cost」。第四條尤其反直覺：它把 prompt 當成有預算的程式碼，於是才有 progressive disclosure（常用且短的內容留在入口，少用且長的內容拆出去、用到才讀）與 token 預算這套成本模型。

四步走完之後，你不只知道規則，還能拿它當尺去量自己的 skill：哪一行沒改變 agent 行為該刪、哪個檔案該拆、哪條規則該寫成可檢查的條件而不是一段敘述。最後一步把這把尺變成 CI 裡的守門員，讓慣例不再靠人記得。
