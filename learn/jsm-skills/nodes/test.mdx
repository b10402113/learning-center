# /test：為變更寫回歸測試

## Learning goal

能用 `/test` 為本次變更寫出真正會抓到 bug 的回歸測試，依檔案分類選對策略，維護 `test-preferences.json`，且不以改原碼換過關。

## Steps

1. [[learn/jsm-skills/nodes/test/test-philosophy-and-scope|/test 的角色：只為這條分支的未提交變更寫回歸測試]] — 認清它測什麼、不測什麼，以及「過了卻抓不到 bug」為什麼比沒有更糟
2. [[learn/jsm-skills/nodes/test/classify-and-strategy|先分類再下手：五種檔案各自對應的測試策略]] — 從路徑把檔案歸類，再挑對應策略 (after step 1)
3. [[learn/jsm-skills/nodes/test/preferences-and-setup|test-preferences.json：記住測試框架，或記住你選擇不裝]] — 認得 framework 與 gate 兩種形狀，跑對首次 setup (after step 1)
4. [[learn/jsm-skills/nodes/test/write-with-discipline|寫測試的紀律：抓行為、不改原碼、可追到驗收條件]] — 套用寫作規則與 coverage 優先序 (after steps 2–3)
5. [[learn/jsm-skills/nodes/test/run-iterate-and-report|跑與不跑的差別：分辨測試錯還是程式錯，然後收尾]] — 跑迴圈、誠實分辨失敗、產出回報 (after step 4)

## Lesson

`/test` 站在 `/develop` 之後、`/check review` 之前，負責把「這次改動到底對不對」從一次性的手動確認，變成留在 repo 裡、以後每次都會重跑的回歸測試。它的範圍由 git 決定：你還沒提交的變更，就是它要測的東西，不需要再回答一次「這次要做什麼」。

這個節點最想扭轉的是一個常見心態：把測試當成覆蓋率數字在收集。`/test` 的立場剛好相反：一個會過、卻抓不到真 bug 的測試，比根本沒有測試更糟，因為它給你安全感，卻在改壞時靜靜放行。所以它要你測呼叫者真正依賴的行為，測「壞掉時會傷到誰」，而不是為了讓覆蓋率好看而補行數。它也因此有一條硬規則：測試永遠不能反過來改動被測的原始碼。

節點拆成五步。先講清楚 `/test` 的角色、範圍與哲學，以及它和相鄰階段的接力關係。接著進入它最核心的判斷：把變更檔案依路徑分成五類，每一類用不同的策略測；再處理第一次執行時的偏好設定，包含「這個專案有 runner」與「這個專案刻意不裝 runner」兩種完全不同的形狀。有了分類與偏好，才進到實際下筆的紀律：哪些該測、測試怎麼寫、怎麼對回規格的驗收條件。最後是跑測試的迴圈與收尾：跑完要能誠實分清楚哪個失敗是測試自己寫錯、哪個是程式真的壞了，然後產生對應的回報。

走完這節，你應該能在自己的分支上真的跑一次 `/test`，寫出一組會抓到 regression 的測試，並且在它變紅色的時候知道該修測試還是該回頭修程式。
