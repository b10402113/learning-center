# /sync：把知識對回 repo

## Learning goal

能用 `/sync` 外科手術式地把 `AGENTS.md`、feature scope、spec status 對回 repo 現在的樣子，並守住 boundaries（flag 而不覆寫）與 idempotent。

## Steps

1. [[learn/jsm-skills/nodes/sync/role-and-boundaries|/sync 的定位與界線：外科手術，不是重寫]] — 認清它自己維護什麼、要 flag 給誰，以及 AGENTS.md 與 CLAUDE.md 的關係
2. [[learn/jsm-skills/nodes/sync/scope-the-change|從 git 圈出這次要對的變更]] — 取變更集、濾出 source 檔、定位要看的 AGENTS.md／specs／scope（after step 1）
3. [[learn/jsm-skills/nodes/sync/tool-discovery|新工具要不要找 Skill 與 MCP：先問再做]] — Step 2.5 的觸發條件、consent 規則與唯讀子代理（after step 2）
4. [[learn/jsm-skills/nodes/sync/reconcile-agents-md|把 AGENTS.md 對回 repo：只加必要的一行]] — 三條件判斷、鏡射欄位、net-new 建檔與孤兒清理（after step 3）
5. [[learn/jsm-skills/nodes/sync/reconcile-scope-and-specs|對齊 scope 與 spec：打勾、改狀態、標過期]] — spec Status 對應、stale 判斷與 scope 子任務證據表（after step 2）
6. [[learn/jsm-skills/nodes/sync/relay-and-report|收尾與回報：為什麼第二次跑不該再改東西]] — 固定回報區塊、Heads up 指向、idempotent 與 NOTHING_TO_SYNC（after steps 4, 5）

## Lesson

`/sync` 是整條工作流的收尾階段，跑在一個改動已經完成、快要合併的時候。它處理的問題跟前面所有階段都不一樣：前面的階段負責「生」出東西，產出程式、規格、測試、文件；`/sync` 負責把这些東西對回 repo 現在的樣子。比如說，程式碼換了一個 build 指令，但 `AGENTS.md` 裡還寫著舊的；某個 feature 其實測試都寫了、PR 也開了，但 scope 上那一格還沒打勾；某份 spec 的狀態停在 `Proposed`，但它的功能早就上線了。這些不一致平常沒人會發現，等到下一個 agent 或下一個同事照著過期資訊做事，才會出問題。

它最特別的地方是「知道自己不該碰什麼」。一份工作流裡最危險的 AI 行為，是它好心幫你把整段文件重寫一遍；`/sync` 反過來，把「它擁有什麼」寫成一張 Boundaries 表，只做外科手術式的單行新增與修正。遇到不確定的情況，它選擇 flag 出來給人看，而不是自己動手。它的邊界分得很細：該由 `/audit` 建的 `AGENTS.md`、該由 `/architect` 改的 spec 內容、該由 `/scope` 動的 feature 清單，它一律只標記不代做。

六步走完，你會先拿到它的定位與界線，再學會用 git 圈出這次的變更、判斷要不要順手探索新工具的 Agent Skill 與 MCP，接著分別處理兩大類知識載體：`AGENTS.md`（含孤兒清理）與 scope／spec（含狀態對應與過期標記），最後看懂它那份固定的回報區塊，以及為什麼同一份變更跑第二次時它應該一行都不改。
