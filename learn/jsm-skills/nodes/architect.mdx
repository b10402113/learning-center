# /architect：從請求到規格

## Learning goal

能跑 `/architect` 的 staged design conversation，選對四模式，把模糊請求變成一紙 ratified spec，並用 spec lifecycle 管理它。

## Steps

1. [[learn/jsm-skills/nodes/architect/role-and-spec-artifact|/architect 管什麼：一份規格的誕生]] — 認得這個 skill 的角色、它擁有的產物與 create/update/supersede
2. [[learn/jsm-skills/nodes/architect/spec-template-and-audiences|規格的骨架：兩個受眾、一條 AC 主線]] — 看懂 spec 的段落與寫作規則 (after step 1)
3. [[learn/jsm-skills/nodes/architect/four-modes|四種模式：feature、architecture、enhancement、cross-cutting]] — 依情境選模式與對應的設計段 (after steps 1–2)
4. [[learn/jsm-skills/nodes/architect/staged-design-conversation|設計訪談怎麼跑：從 scope 驗證到完整性關卡]] — 跑完六階段訪談與每題機制 (after step 3)
5. [[learn/jsm-skills/nodes/architect/spec-lifecycle-and-ratify|規格的生命週期：Proposed 到 Accepted，以及 Assumed 的補課]] — 管好狀態、ratify assumed、寫完後收尾 (after steps 4, 1)

## Lesson

`/scope` 回答「要做什麼、先做什麼」，把工具選擇刻意留給下一個階段。`/architect` 接的正是那個被留下的空白：一次面對一個承重的技術決定，用一場 staged design conversation 把它問清楚，再寫成一紙規格，放進 `docs/specs/`。這份規格是 `/develop` 之後照著蓋的東西，也是 `/check verify` 拿來對帳的合約。

它的靈魂是「工程師決定、AI 推薦」。每個問題都帶著一個標了推薦的選項與一句理由，但選擇權始終在工程師手上；AI 主動發起的驗證（最後那個跨模型 cross-check）永遠是問過才跑，找到的缺口也只列出來給人決定，不會自己補上。所以它產出的不是一份漂亮的分析，而是一個有人簽核過的決定。

這個節點拆成五步。先看懂它的角色與產物：規格放在哪、長什麼形狀、create / update / supersede 差在哪。接著拆開規格的骨架，認出哪些段落是 `/develop` 要讀的建置規格，哪些是給人看的決定記錄。然後學四種模式，知道什麼情況用 FEATURE、ARCHITECTURE、ENHANCEMENT 還是 CROSS-CUTTING。再走一遍設計訪談的六個階段，理解它為什麼要一題一題問、為什麼資料模型要確認兩次。最後回到規格寫完之後：狀態怎麼流轉、`Assumed` 誰來補課、跨模型 cross-check 與 scope linking 怎麼收尾。

走完這節，你應該能對一個真實的模糊請求跑一次 `/architect`，拿到一紙有生命週期、能被下個階段直接開工的規格，而不是一坨丟不掉的討論紀錄。
