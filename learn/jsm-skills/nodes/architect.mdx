# 把決策寫成 spec

## Learning goal

跑 `/architect` 四種模式，把決策寫成 `Proposed` spec，並說明 spec 生命週期與 ownership。

## Steps

這條路徑先認識 `/architect` 的四種設計姿態，再弄懂它產出的 spec 有哪幾種狀態、歸誰管，接著學它問問題的分類法，然後跑完整場分階段訪談，最後把結果落成檔案並收尾。每一步都接在前一步上，照順序讀。

1. [[learn/jsm-skills/nodes/architect/four-modes|/architect 的四種模式與四種操作]] — 分辨 FEATURE、ARCHITECTURE、ENHANCEMENT、CROSS-CUTTING，以及 create/update/supersede/ratify 這四種操作
2. [[learn/jsm-skills/nodes/architect/spec-lifecycle-and-ownership|spec 生命週期與擁有權]] — 讀懂 `Proposed → In Progress → Accepted`、`Superseded`、`Assumed`，以及 `/architect` 與 `/develop` 各管哪一段（接在第 1 步之後）
3. [[learn/jsm-skills/nodes/architect/asks-vs-acts|問什麼、推什麼、自己查什麼]] — 用 INFER / ASK / RECOMMEND 三個抽屜分類每個設計問題，並學會「首選＋一句理由＋備選」的推薦格式（接在第 2 步之後）
4. [[learn/jsm-skills/nodes/architect/staged-design-conversation|分階段設計對話：閘門式訪談]] — 從 scope validation、framing 到 stages (a)–(f)，一維一題地把模糊需求問成完整契約（接在第 3 步之後）
5. [[learn/jsm-skills/nodes/architect/write-spec-and-ratify|寫 spec、交叉檢查、ratify]] — 把答案寫成正確位置與形狀的 spec，跑完交叉檢查與確認，依種類 ratify，並處理 `Assumed` spec（接在第 4 步之後）

## Lesson

`/architect` 是整套流程裡「承重」的那個 skill：它不寫任何程式碼，卻決定了後面 `/develop` 要照著蓋什麼。它的工作只有一句話——把一個還沒定案的技術決策，問清楚、比過選項、寫成一份放在 `docs/specs/` 的 spec。之後所有建置、驗證、測試都掛在這份文件上，所以這份文件寫得夠不夠完整，直接決定功能會不會中途冒出沒人決定過的岔路。

它有四種設計姿態，因為「設計一個新功能」、「替全新專案選技術棧」、「改造一個已經存在的東西」、「把一種寫法統一整個 repo」這四件事要問的問題完全不同。它也有四種操作：新決策是 create，既有決策演進是 update，推翻舊決策是 supersede，而替 `/develop` 應急留下的 `Assumed` spec 補上正式討論則是 ratify。

這份 spec 不是一次寫完的，而是靠一場「閘門式訪談」長出來的：先確認這個主題是不是其實已經做過、或其實大得需要拆，再一維度一維度地問，每一題只給一個推薦與它的理由，讓工程師做決定，最後再把自己寫的 spec 交叉檢查一遍、確認、ratify。走完五步之後，你應該能從一個模糊的題目開始，獨立跑完 `/architect`，並說出最後那份 spec 為什麼是 `Proposed` 而不是 `Accepted`。
