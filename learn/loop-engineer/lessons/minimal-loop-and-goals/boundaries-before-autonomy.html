先設界線，再放自主：max steps、timeout、dry-run、approval

Step 4/4 · 最小可執行 Loop 與 Goal 契約

學習目標

學會判斷一個最小 loop 應該先加上哪些界線：max steps、timeout、dry-run 與 approval gate。更重要的是，說清楚每一道界線要擋住哪一種失控。

先決定它最多能壞到哪裡

你的最小 loop 已經能選動作、執行工具、觀察結果，再評估下一步。它看起來已經像個 agent，這時很容易順手替它接上更多工具、放更多權限，甚至讓它自己決定要不要寫檔。

但「跑得動」不代表「可以放心放大」。沒有界線的迴圈可能一直重試、用過大的範圍呼叫工具，或留下難以追蹤的變更。它不一定會立刻報錯，反而可能安靜地把事情做歪。

所以這一節要做的決定是：先放界線，再擴充能力。界線不是 demo 做完後才補的細節，而是 loop 本身的一部分。它讓失敗模式變得可預測，也讓你知道這個迴圈最壞會走到哪裡。

四道界線，怎麼取捨

最小版本先從四道界線開始。它們各自擋住不同問題，但代價也不同，不能只是把所有限制無條件打開。

界線擋掉哪種失控代價與提醒
Max steps（步數上限）無限迴圈、鬼打牆，以及同一個錯誤不斷重試。設得太緊，會把正常的長任務提早切斷。要分清楚「還沒做完」和「已經撞牆」。
Timeout（逾時）單一工具卡死，或整個 run 被一個緩慢呼叫拖住。最好分層設定：步驟、工具呼叫與整體請求各有上限，並在觀察資料中留下逾時原因。
Dry-run（試跑模式）在意圖還沒確認前，就產生真實副作用。適合沙盤推演與事前檢視；但需要真實寫入才能驗證的步驟，不能永遠只靠 dry-run。
Approval gate（核准閘）高影響、敏感或不可逆的動作，在沒有人點頭前就執行。如果連低風險、高頻動作都要求核准，人就會變成瓶頸。

把它們放回 loop 的骨架來看：max steps 與 timeout 是迴圈的外框，限制它最多跑多久；dry-run 決定動作是否真的執行；approval gate 則是在動作執行前加上一道人工檢查。

這些界線不該由模型臨場決定，而要由 harness 或 policy 層強制執行。模型可以提出動作，但不能自己決定要不要遵守限制。

用判別問句決定哪裡要設界線

不要只憑直覺決定是否需要核准。面對每一個動作，可以先問幾個能實際驗證的問題：

  • 這個動作可逆嗎？如果不可逆，例如刪檔、對外送出內容或寫入正式環境的資料，就先接上 approval gate。
  • 失敗了看得到嗎？如果結果不容易觀察，就需要更強的觀察與驗證，不該急著放行。
  • 它會不會一直重複？可能鬼打牆或反覆重試的流程，一定要有步數上限。
  • 它會產生副作用嗎？有副作用的動作，先用 dry-run 看清楚意圖，再決定是否真的執行。
  • 錯一次的成本高嗎？成本越高，就越值得在動手前插入人類覆核。

反過來說，可逆、低風險，而且本來就具備冪等性的讀取動作，通常不需要每次核准。若所有動作都要人點頭，人的注意力會被低價值請求耗光，真正重要的核准反而可能被草草按過。

反例：界線太緊或太鬆，都會失效

第一個反例是界線太緊。假設 max steps 設成 2，但任務正常需要 4 步才能完成，agent 每次都只會回傳 LIMIT_REACHED。看起來像是 agent 能力不足，其實是你把路直接截斷了。

第二個反例是界線全部打開。如果每個動作都只能 dry-run、每個動作都要核准，那些必須真實寫入才能驗證的任務永遠無法完成。人類也會變成每一輪的瓶頸，agent 的效率幾乎歸零。

這兩個例子指向同一個原則：界線的目的，是讓失敗模式可預測，不是讓 agent 什麼都不能做。界線太緊會誤傷正常任務，太鬆則等於沒有設計；兩者都只是碰運氣。

最小版本可以把限制與需人工覆核的動作集中列出，而不是把常數散落在各處：

limits:
  max_steps: 8
  step_timeout_seconds: 30
  total_timeout_seconds: 180
  dry_run: true            # 預設只推演，確認後才真的落地
  require_approval_for:
    - "delete_file"
    - "write_outside_repo"
    - "network_command"
    - "install_package"

可直接採用的決策規則

  1. 先問「這個迴圈最壞會壞到哪裡」，再問「它還能多做什麼」。
  2. 最小版本預設啟用四道界線：max steps、timeout、dry-run、approval gate。
  3. approval gate 只放在不可逆、高影響或敏感的動作上，不要拿來阻擋低風險、高頻動作。
  4. 每一道界線都要在 trace 中留下「為什麼停」的原因，讓停止結果可以被審計。
  5. 等邊界到位後，再逐一放寬限制或擴充能力。每放寬一次，都重新確認失敗模式是否仍然可預測。

小結

先設界線，再放自主。max steps 擋住無限迴圈，timeout 擋住卡死，dry-run 先檢視意圖再產生副作用，approval gate 則在不可逆或高影響動作前插入人類覆核。判斷時問：可逆嗎、看得到嗎、會重複嗎、有副作用嗎、錯一次的成本高嗎？界線太緊會誤傷正常任務，太鬆則等於沒有設計。四道界線到位後，才一步步擴充能力。

走到這裡，你已經有一個完整的起點：四階段控制迴圈、一份可驗收的 goal 契約、一個責任清楚的最小骨架，以及一組讓失敗保持可控的界線。這就是最小可執行 loop 的基本形狀。

接下來要做的，是把工具真正接進去，讓這個骨架動起來。
