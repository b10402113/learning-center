設計最小可執行 Loop：先做出可除錯的骨架

Step 3/4 · 最小可執行 Loop 與 Goal 契約

這一節要完成什麼

你要把前一節的 Goal 契約，接到一個真的能跑的 loop。完成後，程式會依序載入 context、選擇動作、執行並觀察結果，再根據 completion criteria 判斷要停止或進入下一輪。

動手前，請先具備兩樣東西：

  • 理解 Goal、Act、Observe、Evaluate 四個階段各自負責什麼。
  • 準備好一份可執行的 goal 契約。

這一節的重點不是先蓋出完整的 agent 平台，而是先做出一個每一輪都看得懂、出了問題也找得到位置的骨架。之後要加入工具、記憶體、護欄與核准，都應該建立在這個控制流上。

先從最小骨架開始

很多人一開始就想設計工作流引擎、記憶體層、外掛市集和監控儀表板。結果平台越蓋越大，卻還沒有一個例子能端到端跑完。

最小可執行 loop 走相反的路：先讓 agent 做一次決定、拿回一次觀察，再決定是否繼續。控制流可以先縮成下面四行：

while not done:
    action = choose_next_action(context)   # 決定下一步
    observation = run(action)              # 真的去做，拿回結果
    state = update(state, observation)     # 把結果寫進狀態
    done = evaluate(state, goal)           # 對照 goal，決定要不要再一圈

這個版本不特別聰明，卻很容易檢查。每一個 action、每一個輸出，以及每一次停止決定，都有明確的位置。這就是它的價值：loop 不再是一坨只有作者看得懂的腳本，而是一條可以逐段除錯的控制流。

按照固定順序跑完一輪

實際執行時，loop 會從 input goal 開始，但不能直接跳到工具呼叫。請依照下面的順序組裝：

  1. 載入相關 context。讀取 instructions、可用工具、先前的觀察、限制條件，以及上一輪留下的 state。這些內容決定 agent 這一輪能看見什麼。
  2. 選擇並執行一個動作。從可用能力中選出一個 tool call、一條程式碼路徑或一次查詢，實際執行它。
  3. 擷取 observation。記錄執行結果，包括輸出、錯誤與狀態變化。
  4. 評估停止條件。把目前的 observation 和 state，拿去對照 goal 的 completion criteria。
  5. 回傳或繼續執行。若 goal 已完成，就回傳最終結果；若尚未完成，就把更新後的 state 當成下一輪的輸入。

第五步是 loop 和單次模型呼叫的分界。單次呼叫產出答案後就結束；loop 則會把更新後的 state 餵回下一輪，持續前進，直到抵達明確的停止點、撞到界線，或需要升級求助。

因此，每一輪都應該留下可觀察的紀錄。這些紀錄讓你之後能測試 agent 到底做了什麼，也能分辨問題發生在選擇、執行、狀態更新，還是停止判斷。

把責任分到清楚的介面

最小 loop 不需要龐大的架構，但仍然需要乾淨的責任分工。用檔案切開責任，是簡單而耐用的做法：

檔案放什麼
loop.py迴圈控制器：控制流本身，只負責串起其他介面。
tools.py工具包裝：實際碰真實世界的那一層。
state.py狀態管理：goal、輪數、觀察、evidence、trace。
evals.py評估邏輯：拿 criteria 判斷成功、重試或失敗。
CLAUDE.md操作規則：這個專案怎麼做事、有哪些慣例。
codebase-map.md架構地圖：重要邏輯放在哪裡、模組之間怎麼依賴。
claude-settings.json本機權限與工具行為。

前四個檔案分別對應四個獨立介面。這個切法比檔名本身更重要：

  • state 把 context 提供給 tools。
  • tools 執行動作，並透過 observation 更新 state。
  • policy 控制哪些動作可以執行。
  • evaluator 判斷結果是成功、重試還是失敗。

把介面分開後，你可以單獨替換一個工具、收緊一條政策，或改進評估邏輯，不必重寫整個 agent。更重要的是，出了問題時，你有座標可以查：是 action 選錯了、tool 壞了、policy 擋住了，還是 criteria 根本沒有被滿足？

把介面接回控制流

接下來把前面的骨架展開成一個完整的執行流程。下面這段程式碼中，loop 只負責控制順序；真正的執行、狀態管理、政策檢查與結果評估，各自交給對應介面：

def run_agent(goal, state, tools, policy, evaluator):
    while not evaluator.is_done(goal, state):
        context = state.load_context(goal)        # state → context
        action = select_action(context, tools)    # 依可用工具選動作
        if not policy.allows(action):             # policy：什麼可以跑
            state.record_blocked(action)
            break
        observation = tools.execute(action)       # tools：唯一碰真實世界的介面
        state.apply(observation)                  # 觀察回寫 state
        if evaluator.should_stop(goal, state):    # evaluator：拿 criteria 對照
            break
    return state.result()

可以依照這個順序檢查每個責任：

  1. state.load_context(goal) 從 state 準備這一輪要使用的 context。
  2. select_action(context, tools) 只根據 context 和可用工具選擇動作。
  3. policy.allows(action) 先檢查這個動作是否被允許。若不允許，就記錄 blocked action 並停止。
  4. tools.execute(action) 執行動作並回傳 observation。這是唯一碰觸真實世界的介面。
  5. state.apply(observation) 把結果寫回 state，供下一輪使用。
  6. evaluator.should_stop(goal, state) 重新對照 criteria，判斷是否應該停止。
  7. state.result() 在 loop 結束後整理並回傳結果。

select_action 不應該自己執行工具，tools.execute 也不應該替 evaluator 判斷是否完成。policy 和 evaluator 同樣只做判斷，不碰真實世界。這樣才能分開測試：你可以餵一個假的 state 給 evaluator，確認證據不足時它會判定「尚未完成」；也可以只測 policy，確認不該執行的動作確實會被擋下來。

完成後要能驗證什麼

把這個版本跑起來後，你應該能清楚回答每一輪的幾個問題：

  • 這一輪載入了哪些 context？
  • agent 選了哪一個 action？
  • 工具回傳了什麼 observation？
  • observation 如何更新 state？
  • evaluator 為什麼判定繼續、停止，或失敗？

如果這些問題無法回答，通常表示某些責任又混回同一支腳本裡了。最小可執行 loop 不需要大型架構，但一定需要清楚的 goal、明確的 completion criteria，以及可觀察的證據。前一節已經準備好這三樣東西；這一節只是把它們接上控制流。

小結

最小可執行 loop 是「做決定 → 觀察 → 決定下一步」的最小可跑版本。完整流程是：載入 context → 選動作 → 執行 → 擷取觀察 → 評估停止 → 回傳，或把更新後的 state 餵回下一輪。用 loop.py、tools.py、state.py、evals.py 切開責任，並讓 state、tools、policy、evaluator 保持獨立介面，迴圈才不會退化成不可測試的腳本。

做到這裡，你已經有一個真的跑得起來、也能逐輪檢查的骨架。下一步不是立刻增加更多能力，而是先替它放上界線：max steps、timeout、dry-run 與 approval gate。沒有界線的 loop，就像沒有煞車的車；先把可控範圍定下來，後續擴充才不會失去方向。
