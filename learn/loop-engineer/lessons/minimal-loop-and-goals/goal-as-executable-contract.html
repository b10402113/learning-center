把模糊需求寫成 Goal 契約與完成條件

Step 2/4 · 最小可執行 Loop 與 Goal 契約

先準備好：你要交付什麼

這一節的目標，是把一句模糊需求翻譯成一份可以執行、可以驗收的 goal 契約。完成後，你會有明確的結果、工作邊界、可用輸入、限制條件，以及能證明任務完成的 evidence；Evaluate 階段也能依照 completion criteria 判斷是否該停止。

開始前，請先讀過上一節的四個階段與各自的契約。這裡不會重新拆解單一 loop，而是直接處理最容易讓 loop 失控的部分：Goal 到底要寫成什麼樣子，agent 才知道該做什麼、不能做什麼，以及什麼時候真的做完。

先看問題：一句需求為什麼不夠

「幫我查一下這個測試為什麼壞掉」、「整理一下這次事故」、「改善 onboarding」，這些話對人來說有方向，對迴圈來說卻像一張沒有標線的地圖。

它不知道哪些來源可以讀、哪些動作不准做，也不知道做到什麼程度就能停。結果可能是一直規劃、一直呼叫工具、一直修改，看起來很忙，卻沒有人能客觀判斷它是否完成。

因此，第一步不是立刻啟動 runtime，而是先把需求寫成契約。這份契約會成為後續 Observe、Evaluate 與 Decision 的共同基準。

Goal 不是 prompt 開頭的一句話

把 goal 寫在 prompt 最上面很方便，但那通常只是一段描述，不是一份契約。真正的契約要固定四件事：成功長什麼樣、工作範圍在哪裡、進度要用什麼衡量，以及什麼時候可以停止。

缺少這些內容，就等於要求 agent 從一句模糊的話裡自行猜出整套標準。它可能完成了某些工作，卻無法回答：「這些工作是否足以算完成？」

一份可執行的 goal 至少要提供三個支點：

  • 靶心：要交付的結果是什麼。
  • 邊界：哪些事情可以做，哪些事情刻意不做。
  • 停止規則：看到什麼證據時，才可以說 done。

有了這三個支點，每次 observe → evaluate 都有東西可以對照。條件不滿足時，agent 可以誠實地說「還沒完成」，而不是把半成品當成完成品。

第一步：填好五個欄位

先把 goal 拆成五個欄位。這不是文件格式的講究：五個欄位都是後續決策邏輯的輸入。

欄位它要回答內容
Outcome（結果）要交付什麼可衡量的結果？agent 必須產出的、可被檢查的成果。
Scope（範圍）哪些算在內、哪些明確排除？把「包含」與「刻意不做」分開寫，避免默默擴張。
Inputs（輸入）能用哪些資訊、資料與參照？允許讀取的來源、資料、參考檔案。
Constraints（限制）規則、權限與安全要求是什麼？可以做與不可以做的動作、額度、需核准的動作。
Success evidence（成功證據）什麼能證明它完成了？完成的產物或訊號，例如測試結果、檔案變更、報告、已審核的 PR、核准紀錄。

這五欄會分別接到迴圈的不同位置：

  • Outcome 決定規劃要往哪裡走。
  • Scope 限制工具可以觸碰的範圍。
  • Inputs 決定 context 要載入哪些內容。
  • Constraints 讓 policy 知道哪些動作必須擋下來。
  • Success evidence 提供 Evaluate 判斷通過與否的標準。

所以 goal 不是流程旁邊的說明文件，它就是整個迴圈的判斷中樞。

第二步：依照 repository 寫出契約

接著依照下面的順序，把一句需求翻成可執行的規格。核心原則是：先以 repository 為事實來源定義契約，再啟動 runtime。

  1. 先讀 repository。查看專案說明、codebase map、設定檔、原始碼、測試與文件。這些內容才是定義 goal 的材料，不要讓 agent 只靠一句 prompt 腦補。
  2. 把 business intent 翻成 scope。例如「調查一個壞掉的測試」還不夠。要補上允許讀取的來源、允許採取的動作，以及明確排除的工作。
  3. 寫出 completion criteria。每項 criteria 都要指名完成證據，例如測試結果、檔案變更、結構化報告、已審核的 pull request，或核准紀錄。
  4. 把 criteria 放在 observe 與 decision 之間。agent 不會因為產出了某個檔案就自動停止；只有觀察結果符合預先定義的條件，才可以停止。
  5. 先寫 goal spec，再啟動 runtime。正確順序是：定義 goal 與 completion criteria → 載入 context → 規劃 → 呼叫工具 → 執行檢查 → 收集證據 → 做決定。
  6. 留下 evidence file 與 decision log。evidence file 提供可查驗的結果；decision log 記錄 criteria 是否通過、是否需要核准，以及迴圈為什麼停止或繼續。

第三步：寫出 goal spec

下面是一份依照五個欄位整理出的骨架。它不是某個語言的正式規格，重點是讓每個欄位都有明確落點，並且把「完成」寫成可以觀察的條件。

goal_spec:
  outcome: "test_percentage_discount 回復綠燈，且既有測試全數通過"
  scope:
    included: [ "calculator.py", "test_calculator.py" ]
    excluded: [ "重構無關模組", "調整測試期望值" ]
  inputs:
    allowed_sources: [ "repo", "test_output", "codebase_map" ]
  constraints:
    - "只修改一道已知錯誤的算式"
    - "寫入前先備份"
    - "不得刪除檔案"
  success_evidence:
    - "unittest -v 全部通過，exit code 0"
    - "檔案 diff 只變更目標那一行"
  completion_criteria:
    - "observed.test_exit_code == 0"
    - "observed.changed_lines == 1"

這份規格把原本模糊的任務拆成幾個可檢查的問題：要修哪個結果、能碰哪些檔案、不能做哪些事、成功要留下什麼證據，以及 evaluator 要檢查哪些觀察值。

第四步：用 bad / good 對照檢查

先看只有意圖、沒有契約的版本：

goal: "讓測試變好，順便整理一下程式碼"

這句話沒有指定測試、沒有指定修改範圍，也沒有說明「變好」要用什麼證明。迴圈沒有穩定的比較基準，很容易順手擴大工作範圍。

改成下面這樣，Evaluate 就有具體條件可以檢查：

goal: "讓 test_percentage_discount 通過；只改 calculate_discount 的算式；
       完成證據是 unittest 全綠（exit 0），且 diff 只動一行。"

這裡的重點是把結果、範圍與證據綁在一起，句子寫得長不長不重要。只要其中一項不符合，就不能直接宣布完成。

第五步：把 completion criteria 當成停止條件

Completion criteria 要回答的是：「在我們能說做完之前，什麼必須成立？」它可能包括輸出格式正確、測試通過、文件更新，也可能規定高風險變更必須先取得人類核准。

在客服或營運任務中，criteria 也可以是摘要正確、引用無誤、通過隱私檢查，或在信心不足時升級。任務不同，條件會不同；但寫法相同：把完成改寫成可觀察、可驗證的結果。

它在迴圈中的位置很關鍵：criteria 坐在 Observe 與 Decision 之間。

  1. Observe 取得測試結果、diff、報告或其他觀察值。
  2. Evaluate 將觀察值逐項對照 completion criteria。
  3. 若條件全部滿足，Decision 才能選擇 STOP。
  4. 若條件不滿足，則繼續修正、重試或升級求助。

因此，agent 不是因為「產出了東西」就停止，而是因為「觀察到的結果符合預先定義的 criteria」才停止。先定義 done，再開始跑，正是這個 loop 能可靠運作的原因。

第六步：留下 evidence 與 decision log

證據不能只存在 agent 的口頭回覆裡。請留下 evidence file 或 log，讓 evaluator 有一個客觀、可查驗的對象；再用 decision log 記錄 criteria 是否通過、是否需要核准，以及迴圈為什麼停止或繼續。

例如，當測試 exit code 是 0、變更行數是 1，且兩項 criteria 都通過時，決策可以記成：

{
  "turn": 2,
  "observed": { "test_exit_code": 0, "changed_lines": 1 },
  "criteria_passed": true,
  "approval_required": false,
  "decision": "STOP",
  "reason": "completion criteria met"
}

完成後，你應該看得到什麼

做完這一節，你應該能交出一份完整的 goal spec，至少包含 outcome、scope、inputs、constraints、success evidence 與 completion criteria。runtime 尚未開始前，任務的目標、邊界與停止條件就已經固定。

當 loop 執行後，Evaluate 可以拿 evidence 對照 criteria；若測試、diff 或核准狀態不符合要求，就不能停。若全部符合，decision log 會留下明確的 STOP 理由。這樣的結果才是「真的能決定」，而不是看起來像完成。

Goal 不是 prompt 裡的一句話，而是一份可執行的契約：outcome、scope、inputs、constraints、success evidence。Completion criteria 是迴圈的停止條件，位在 observe 與決定之間；agent 只在觀察結果滿足預先定義的條件時才停。順序永遠是「先定義 done，再開始跑」，並用 evidence file 與 decision log 留下判斷紀錄。

現在，Goal 階段已經有了清楚的契約。下一步要把它接進一個真正跑得起來的最小 loop，並在專案裡把 state、tools、policy、evaluator 拆成乾淨的介面。
