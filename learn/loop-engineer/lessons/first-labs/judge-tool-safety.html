一次 Tool Call：該執行、拒絕，還是安全重試？

Step 2/4 · 入門實作：Tool Dispatcher 與 Loop Map

Agent 發出請求後，難的不是「怎麼呼叫工具」，而是判斷這次呼叫能不能放行、失敗後能不能再試。擋得太嚴，agent 什麼事都做不了；放得太鬆，未授權的刪檔或重複建立訂單，就可能一路通關。

這一節會用三個判準做決定：工具是否會改變外部狀態、參數是否符合 schema，以及失敗後重試是否安全。特別要小心一種情況：請求送出去了，但結果既不知道成功，也不知道失敗。這時盲目重送，可能把一次操作變成兩次。

先看三個判準：你到底要決定什麼？

面對一次 tool call，harness 要做的不是單純按下「執行」鍵，而是替它做風險分流：

  • 可以執行：請求符合契約，也沒有超出授權範圍。
  • 應該拒絕：參數不合法、權限不足，或動作本身需要更高層級核准。
  • 可以重試：失敗屬於暫時性問題，而且重試不會放大副作用。

選項比較：唯讀工具與有副作用的工具

第一個問題是：這個工具會不會改變外部狀態？這個分類會直接影響驗證、核准與重試政策。

read-only（唯讀）side-effecting（有副作用）
典型例子搜尋、查狀態、讀檔案寫檔、建立訂單、刪除、退款
執行前要確認什麼參數是否落在允許範圍路徑、內容限制，以及是否有授權
失敗了能不能重試通常可以，重試代價較低必須非常小心，先確認前一次的結果
風險控制與核准政策通常較寬鬆需要更嚴格的界線，高風險動作還要人工核准

不過，唯讀不等於完全安全。搜尋工具雖然不會改變資料，卻可能一次回傳上千筆客戶資料。該問的不是「它會不會改壞東西」，而是「它回傳的內容有沒有超過這次任務需要的範圍」。

判別問句一：參數符合 schema 契約嗎？

假設工具的 schema 明確規定，limit 必須是 1 到 20 的整數，但模型送來了 50。dispatcher 不該默默照做，也不該把 50 偷偷改成其他值。

正確做法是回傳結構化的驗證錯誤。這樣 agent 會知道是 limit 超出範圍，能修正後再送一次。若 dispatcher 默默執行，違反契約的請求就會看起來像成功，之後資料量不對時，也很難追查問題從哪一步開始。

而且，格式正確也不代表一定能放行。請求可能未經授權、範圍過寬，或本身具有風險，例如建立使用者、寫入 repo、查詢客戶資料，或執行終端機指令。schema 解決的是「格式是否合法」；授權與風險政策決定的是「這件事該不該做」。

判別問句二：這次失敗是暫時的，還是規則性的？

重試有價值的前提，是這次失敗可能只是暫時狀況，再試一次有機會成功。如果問題本身違反規則，重送再多次也不會改變結果。

可以考慮有界自動重試不該自動重試
唯讀操作上的一次短暫網路逾時必填欄位無效，重送也不會變合法
帶有重試指引的 rate-limit 回應永久的權限拒絕，再試也不會被授權
暫時性的 503 服務不可用未經核准的破壞性請求

「有界」很重要：重試必須有次數上限與退避時間。無限重試會把一個小故障放大成更大的故障。至於有副作用的請求，即使錯誤看起來像暫時性，也要先確認前一次到底有沒有成功。

最危險的分支：結果未知

想像你送出建立訂單的請求，接著網路逾時。你沒有收到成功回應，也沒有收到失敗回應。這時不能直接假設「剛剛沒成功，所以再送一次」，因為請求可能已經成功，只是回應在途中遺失了。盲目重送，可能讓客人多出一張訂單。

較安全的設計有兩個部分：

  • 替請求帶上 idempotency key（冪等鍵），讓系統知道重送的是同一件事，而不是新的操作。
  • 重試前先查詢操作狀態，確認前一次究竟成功、失敗，還是仍在處理中。

這也是為什麼有副作用的工具，最好在結果中回傳穩定的 operation identifier。後續查詢與重試都能用它串起同一個操作，避免把不確定性變成重複執行。

四個判別問句，決定請求的命運

  1. 這個動作會不會改變外部狀態？會，就走較嚴格的 side-effecting 路徑，必要時先取得核准。
  2. 參數是否落在 schema 允許的範圍內？不是，就回傳結構化驗證錯誤，讓 agent 修正。
  3. 這次失敗是暫時的，還是規則性的？只有暫時性錯誤，且操作適合重試時，才進入有界重試。
  4. 上一次的結果已知嗎？未知就不能盲目重送，必須先用冪等鍵與狀態查詢釐清。

反例：規則會翻轉的地方

第一個反例是「唯讀就一定安全」。唯讀工具雖然不會改變外部狀態，卻可能回傳遠超過任務需要的資料，甚至把不該曝光的內容帶進 context。要求五筆結果，工具卻回傳數千筆，問題就在工具結果契約或實作把信任邊界放寬了。

第二個反例是「重試一定危險」。對唯讀操作來說，短暫逾時後重試通常沒有太大代價；完全不重試，反而會讓 agent 白等。危險的不是重試本身，而是對有副作用、且結果未知的操作無限重送。

小結：當場可用的決策規則

先問「會不會改變外部狀態」，再問「參數合不合法」，接著問「失敗是暫時的還是規則性的」，最後問「上一次結果知不知道」。四個問題依序問完，就能判斷該執行、拒絕，還是重試。只要結果未知，永遠先查狀態，不要先重送。
