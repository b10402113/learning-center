Tool Call 是 Loop 的 Action：模型提出請求，Harness 才是執行邊界

Step 1/4 · 入門實作：Tool Dispatcher 與 Loop Map

學習目標

這一節要建立一個核心觀念：模型送出的是結構化請求，實際執行工具的是 harness。學完後，你應該能說明 tool call 的可控邊界，並列出安全工具必備的四個部分，以及 governed execution pipeline 的四道關卡。

前言：模型突然能動你的系統了

想像你正在做一個會自己修 bug 的 agent。你對它說：「把這個檔案改好。」下一秒，它真的翻了檔案、執行測試，甚至改寫了內容。

這時你可能會問：模型不是只會產生文字嗎？它究竟怎麼碰到我的檔案？如果它判斷錯了，又是誰讓那個動作真的發生？

這一節要補上的就是這塊。前兩節我們已經搭好 loop 的骨架和 goal 契約，但那個 loop 還沒有「手」：它能做決定、能評估結果，卻還不能改變外部世界。

所以，這一節先不急著寫程式，而是先把接上這雙手時的規矩講清楚。tool call 不是模型偷偷伸出去的手，而是一張由模型交出的結構化請求單；這張單子能不能執行，由 loop 外面的 harness 決定。

只要搞懂這條邊界，你才知道 agent 什麼時候仍在你的控制之下，以及哪些動作必須先經過檢查。

Tool call 就是 loop 的 action step

agent 之所以有用，是因為它能做的不只是產生一段文字。在 agent loop 裡，工具呼叫就是那個 action step：每一次迭代中，agent 透過它實際查詢或改變世界。

但這裡有一個很容易被忽略的分工。模型本身不會直接編輯檔案、查詢資料庫，也不會自己執行測試。它負責的是三件事：

  • 從允許使用的工具中挑選一個。
  • 送出結構化的引數。
  • 等待工具的結果回來，並把結果當成 observation。

換句話說，模型負責「判斷要做什麼」，但「這件事究竟能不能執行」則由另一層負責。這一層就是 harness。

harness 是 prompt、policy、工具、狀態與控制邏輯的所在，也是整個 agent 系統裡實際可控的執行邊界。

模型可以推理、可以做決定；但 harness 決定哪些事情真的能被執行。這條界線，就是你能不能信任這個 agent 的關鍵。

可以把它想成公司的簽核流程。模型像一位幕僚：它讀完資料後寫出一張簽呈，清楚說明「要做什麼」以及「需要哪些條件」。

但簽呈本身不是命令。它仍然要經過核章，確認這件事是否獲得授權、金額是否超出限制、是否踩到不能碰的紅線，通過後才會真正執行。

你不會因為幕僚很聰明，就讓他自己拿公司的錢去匯款。tool call 也是一樣：模型可以提出請求，但不能繞過執行邊界。

一次工具呼叫的完整生命週期

把剛才的簽呈流程拆開，一次 tool call 通常會依序經過以下階段：

  1. 意圖：使用者或系統的 goal 產生「現在該做點什麼」的需求。
  2. 選工具：模型從可用工具中，挑選一個看起來與這個意圖相關的工具。
  3. 結構化引數：模型不只是送出模糊指令，而是提供結構化的引數，通常是 JSON，裡面寫明要使用哪個工具，以及要帶入哪些輸入。
  4. harness 驗證：在實際執行前，harness 會拿這些引數對照工具的 schema 與安全規則。
  5. 執行：只有通過驗證後，工具才會在被允許的環境裡執行。
  6. observation：工具結果會被捕捉成 observation，其中包含有用的資料、狀態，以及錯誤。
  7. 決定下一步：模型根據 observation，決定要再呼叫另一個工具、請使用者補充資訊、換一組引數重試，或直接收尾。

這條流程讓工具使用變得可審計、可重複。最重要的是，模型的行動不該被當成魔法；它是一個經過系統驗證的結構化請求，交給工具執行，再透過 observation 回到模型解讀。

少了這條鏈，當一次 run 失敗時，你很難判斷問題究竟出在模型選錯工具、引數不正確、工具執行失敗，還是環境本身阻擋了動作。

一個安全的工具需要四個部分

光有工具名稱還不夠。一個可以被安全呼叫的工具，需要四樣東西一起支撐。缺少其中任何一樣，除錯時都可能像在沒有地圖的黑暗房間裡找出口。

部分它回答什麼問題弱掉的時候會怎樣
schema這個工具做什麼，以及接受哪些引數？模型不知道該怎麼帶參數，可能亂選工具、亂填欄位。
runtime boundary它被允許在哪裡操作，例如檔案系統、shell、網路、資料庫或外部服務？工具可能跑到不該碰的地方，而且沒有人攔得住。
input validation執行前，這些輸入值是否合理，例如必填欄位、允許範圍與允許的操作？離譜的參數可能照樣被執行，直到很後面才發生錯誤。
observation contract工具執行後，哪些內容會回到 agent，例如成功結果、失敗狀態、錯誤訊息與足夠的 metadata？你分不清楚問題是模型選錯、工具故障，還是環境擋住了動作。

這四個部分如果都做得扎實，工具呼叫就不再是靠感覺運作的黑盒子，而會變成一個可以測試、監控與改進的工程介面。

反過來說，只要其中一部分很弱，agent 就會變得難以除錯。每次結果不如預期時，你只能猜測是哪個環節出了問題。

Governed execution pipeline：每張簽呈都要過四道關卡

企業環境的設計原則很直接：每一次工具呼叫，都應該被視為一個需要治理的動作。

所謂治理，具體來說就是讓每個請求依序通過四道關卡：

  1. policy check：這個意圖本身是否被允許？
  2. schema validation：這些輸入是否符合工具契約？
  3. execution sandbox：限制這個工具可以碰到的範圍。
  4. audit log：記錄誰要求了什麼、實際執行了什麼、回傳了什麼，以及 agent 如何回應。

這條管線不只是資安團隊才需要。對工程師來說，它也是做出「能被除錯的 agent」的方法。

當任務失敗時，你可以沿著這條管線逐段檢查：模型選了哪個工具、帶了什麼引數、驗證是否通過、執行輸出是什麼、最後形成的 observation 又長什麼樣子。有了這些線索，失敗才有機會被定位與修正。

這條執行邊界也讓高風險動作可以被分開處理。寫入 repo 之外的檔案、刪除檔案、執行網路指令、安裝套件，都不應該和一般查詢混在一起，而應該額外經過驗證或核准。

如此一來，agent 可以保有生產力，卻不會把每一項能力都變成不受限制的權力。你可以給它一雙有用的手，但這雙手必須受到明確的權限、可觀察的結果與審查閘門約束。

小結

tool call 是 loop 的 action step，但模型只負責送出結構化請求，決定能不能執行的是 harness。一個安全的工具需要 schema、runtime boundary、input validation 與 observation contract 四個部分；每一次呼叫都應該通過 policy、schema validation、sandbox 與 audit log 四道關卡。可靠的 agent 透過有界、可觀察的工具行動，而不是依賴隱形的副作用。

現在，模型與外部世界之間的關係就清楚了：模型提出請求，harness 掌握邊界，工具負責執行，observation 把結果帶回 loop。
