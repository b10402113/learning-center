實作 Python Tool Dispatcher：把請求驗證、路由與執行轉成 Observation

Step 3/4 · 入門實作：Tool Dispatcher 與 Loop Map

這一節要完成什麼

這一節會帶你寫出 dispatch_tool()。它會接收模型送來的結構化請求，確認請求格式、只把請求路由到註冊表中的工具、用關鍵字引數執行工具，最後把成功或失敗整理成固定形狀的 observation。

這個邊界很重要：如果沒有 dispatcher，模型送來的請求就可能直接碰到工具函式，錯誤格式也會一路往外漏。dispatcher 像一道閘門，先檢查請求，再決定能不能放行；即使失敗，也會用 loop 看得懂的格式回報。

開始前的準備

完成後，你會得到一個能通過五個單元測試的 dispatch_tool()。它是整個 loop 裡最先接觸外部世界的零件：請求進來後，由它負責驗證、選工具、執行，再把結果包成固定形狀送回去。

前置條件很簡單：準備 Python 3.10 以上，並熟悉字典與函式。你需要兩個檔案：

  • 測試檔 evaluate.py
  • 要實作的 tool_dispatcher.py

工具本身與註冊表已經提供，請不要修改它們；這一節只需要補完 dispatch_tool()。完成後，在終端機執行：

python3 -m unittest evaluate -v

五個測試全綠，就代表這一節完成。

先看工具箱：兩個工具與註冊表

這次要接的工具很單純。count_words 會計算文字中的字數，find_keyword 會判斷關鍵字是否出現在文字裡。

TOOL_REGISTRY 則是一份白名單，把工具名稱對應到實際函式。只有登記在這份表裡的工具，dispatcher 才能呼叫；未登記的名稱不會被放行。

def count_words(text):
    """Return the number of words in a string."""
    if not isinstance(text, str):
        raise TypeError("text must be a string")

    return len(text.split())

def find_keyword(text, keyword):
    """Return True when a keyword appears in the text."""
    if not isinstance(text, str) or not isinstance(keyword, str):
        raise TypeError("text and keyword must be strings")

    return keyword.lower() in text.lower()

TOOL_REGISTRY = {
    "count_words": count_words,
    "find_keyword": find_keyword,
}

這兩個工具在收到錯誤型別時，會主動丟出 TypeError。dispatcher 會攔截這個例外，把「引數不合法」轉成固定格式的錯誤 observation，而不是讓整個 loop 直接中斷。

先定義 observation 契約

工具請求執行後，回傳的 observation 只有兩種形狀。這是 dispatcher 和 loop 其他部分之間的契約：

情況回傳形狀
成功{"ok": True, "tool": <名稱>, "result": <結果>}
失敗{"ok": False, "tool": <名稱>, "error": <錯誤訊息>}

成功時一定有 result，失敗時一定有 error；ok 則明確表示這次執行是否成功。這樣 loop 的下一步不必猜測剛剛發生了什麼，只要依照固定欄位處理即可。

逐步實作 dispatch_tool()

下面的程式碼就是完整實作。每個檢查都對應一種請求情況；請先看整體流程，再對照後面的步驟理解每一段在守住什麼邊界。

def dispatch_tool(tool_call):
    """Validate and execute a structured tool call."""
    if not isinstance(tool_call, dict):
        return {
            "ok": False,
            "tool": None,
            "error": "Tool call must be a dictionary",
        }

    name = tool_call.get("name")
    arguments = tool_call.get("arguments", {})

    if not isinstance(arguments, dict):
        return {
            "ok": False,
            "tool": name,
            "error": "Arguments must be a dictionary",
        }

    tool = TOOL_REGISTRY.get(name)

    if tool is None:
        return {
            "ok": False,
            "tool": name,
            "error": "Unknown tool",
        }

    try:
        result = tool(**arguments)

        return {
            "ok": True,
            "tool": name,
            "result": result,
        }
    except TypeError:
        return {
            "ok": False,
            "tool": name,
            "error": "Invalid tool arguments",
        }

  1. 先確認請求是字典。 tool_call 是 dispatcher 預期的結構化請求。如果傳進來的不是字典，連工具名稱都還無法安全讀取，就立即回傳錯誤；因此 tool 欄位使用 None。這一步回傳的訊息是 "Tool call must be a dictionary"。

  2. 讀出工具名稱與引數。 name = tool_call.get("name") 取得工具名稱；arguments = tool_call.get("arguments", {}) 取得引數。若請求沒有提供 arguments，就先使用空字典，讓後續流程可以繼續檢查，而不是在讀取欄位時直接失敗。

  3. 確認引數是字典。 若 arguments 是串列或其他型別，就回傳 "Arguments must be a dictionary"。這個檢查必須放在執行工具之前，因為下一步會把字典展開成關鍵字引數。

  4. 從註冊表取得工具。 TOOL_REGISTRY.get(name) 是白名單查詢。若名稱不存在，get() 會回傳 None，dispatcher 就回傳 "Unknown tool"。這樣做比逐一判斷名稱更直接：未註冊的工具根本拿不到可執行的函式。

  5. 用關鍵字引數執行工具。 tool(**arguments) 會把字典展開成關鍵字引數。例如 {"text": "Agent loops use tools"} 會等同於呼叫 count_words(text="Agent loops use tools")。引數名稱負責對應，順序不必固定，這就是結構化請求的好處。

  6. 把成功結果包成固定形狀。 工具執行成功後，回傳 {"ok": True, "tool": name, "result": result}。呼叫方只要讀取 ok 與 result，就能處理這次 observation。

  7. 把引數錯誤轉成 observation。 如果缺少必填引數，或引數型別不符，工具會丟出 TypeError。這裡只攔截 TypeError，並回傳 "Invalid tool arguments"；不攔截所有例外，其他程式錯誤才會繼續浮現，方便除錯。

執行測試：確認每個邊界都被守住

完成後執行測試。五個測試各自鎖定契約的一個角落：

測試確認的行為
test_executes_count_words_tool合法的 count_words 請求會回傳 {"ok": True, "tool": "count_words", "result": 4}
test_routes_request_to_find_keyword_tool請求會正確路由到 find_keyword，並回傳 True
test_rejects_unknown_tool未註冊的工具名稱會回傳 "Unknown tool"
test_rejects_non_dictionary_arguments引數不是字典時，會回傳 "Arguments must be a dictionary"
test_handles_missing_tool_arguments缺少必填引數時，會回傳 "Invalid tool arguments"

以第一個測試為例，請求與預期結果直接並列，等於用程式碼寫下 dispatcher 必須遵守的契約：

        tool_call = {
            "name": "count_words",
            "arguments": {
                "text": "Agent loops use tools"
            },
        }

        self.assertEqual(
            dispatch_tool(tool_call),
            {
                "ok": True,
                "tool": "count_words",
                "result": 4,
            },
        )

完成後，你應該看到什麼

五個測試全綠，就是可驗證的完成結果。dispatch_tool() 會先檢查請求結構與引數型別，再從白名單註冊表取得工具，用關鍵字引數執行，最後無論成功或失敗，都回傳固定形狀的 observation。

這個零件把「模型送來的請求」與「實際執行的工具」之間的邊界，變成幾十行可以測試的程式。驗證與路由的原理，以及為什麼要回傳結構化錯誤，已在上一節說明；這一節的重點是把規則確實寫出來。
