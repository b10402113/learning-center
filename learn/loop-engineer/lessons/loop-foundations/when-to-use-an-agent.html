什麼時候該用 Agent，什麼時候不該

Step 4/4 · Loop Engineering 基礎與四層堆疊

先把要做的決定說清楚

新需求一進來，團隊很容易先問：「這個能不能做成 agent？」這個問題聽起來積極，卻可能把大家帶往錯的方向：它關心的是技術做不做得到，而不是這個問題是否真的需要自主決策。

真正該問的是：這個問題，需不需要系統看過結果之後，再決定下一步要做什麼？

如果不需要，多加一層 agent 就像為了走到巷口而開一台卡車：做得到，但成本、延遲與維護負擔都變大。這一節要幫你分辨兩條路：什麼情況值得使用 agent，什麼情況應該選擇單次呼叫、固定工作流、規則或批次服務。

選項比較：Agent 還是更簡單的機制？

先看問題的形狀，再決定工具。以下四個條件同時出現得越多，agent 越可能有價值：

問題特徵適合使用 agent 的理由若沒有這個特徵
路徑不明確事先不知道會經過哪些步驟，需要邊做邊找。若步驟固定，決定性工作流通常更容易測試、監控與維運。
需要使用外部工具任務必須真的操作外部系統，而不是只產生文字回答。若只需要一次性的答案，單次 LLM 呼叫通常就夠了。
需要檢視中間結果必須先看上一步實際產出什麼，才能判斷下一步。若不需要觀察過程，就不必為了觀察而增加 loop。
判斷會改變下一個動作下一步要做什麼，取決於剛才看到或判斷到的結果。若所有動作都能事先寫死，固定服務通常更便宜、更可靠。

這四個條件的共同核心是不確定性、觀察、工具使用與迭代。Agentic loop 的價值，就在於它能依照工作中的新資訊調整路徑：規劃、行動、觀察，再決定是否繼續。

反過來說，如果每一步早就確定，loop 就像在已經畫好的地圖上反覆問路，增加的是開銷，不是能力。

判別問句：下一步會因為結果而改變嗎？

你可以用下面這句話檢查一個需求：

這個問題，是否需要系統使用外部工具，查看中間結果，並根據結果改變下一步？

如果答案是「是」，再繼續確認四個條件：

  • 路徑是否不明確？事前是否無法完整列出所有步驟？
  • 是否需要外部工具？任務是否必須讀檔、查資料、操作雲端系統或執行命令？
  • 是否需要觀察中間結果？上一步的產出是否會影響後續判斷？
  • 判斷是否會改變下一個動作？系統是否可能因為新資訊而選擇不同路徑？

這不是在替 agent 找一個漂亮的名目，而是在確認它是否真的需要「做了再看、看了再決定」的能力。

哪些場景通常適合 Agent？

好的 agent 用例，通常會同時具備不確定性、工具使用與反覆驗證的特徵：

場景為什麼適合
程式碼導航系統需要先讀檔、查看專案指示與 codebase 地圖，再使用語言理解工具，才能提出有根據的修改。
研究與綜合系統要比較多個來源、處理彼此矛盾的資訊，再整理成結論。
營運排障日誌、終端機輸出與指標會隨著調查進展改變診斷方向。
多步驟工具工作任務需要查資料、呼叫雲端動作、執行 git 操作、轉換資料，並驗證最後結果。

這些場景並不是「永遠都該用 agent」的清單。它們只是常見的訊號：系統需要在工作過程中取得新資訊，並依照新資訊調整行動。是否採用 agent，仍要回到成本與可靠性的取捨。

反例：規則會翻轉的情況

當適應力帶來的價值，低於規劃開銷、額外延遲、不穩定行為與測試負擔時，agent 就不是好選擇。以下情況通常應先使用更簡單的機制：

情況通常更好的選擇
使用者只需要一個一次性的答案單次 LLM 呼叫通常就夠了。
步驟固定不變使用決定性工作流，較容易測試、監控與維運。
受嚴格法遵規則約束先放入規則、驗證與人工複核，再考慮是否增加自主性。
量大又重複批次工作或固定服務通常更便宜，也更可靠。

這裡最容易出現的誤判是：「只要任務複雜，就應該用 agent。」其實複雜不等於不確定。若複雜任務仍能事先拆成固定步驟，決定性工作流可能更適合；反過來，即使任務規模不大，只要下一步高度依賴中間觀察，agent 仍可能有價值。

即使適合，也要先窄後廣

判斷該用 agent，不代表要立刻把所有權限都交給它。企業導入時，較安全的做法是先選一個有界的用例，量測真實行為，等證據支持後再擴張。

  1. Intake：讓請求先經過清楚的入口，捕捉範圍與意圖。
  2. 政策檢查與風險分級：在 agent 取得工具與資料之前，先完成政策檢查與風險分級。
  3. 權限：由權限決定 agent 能讀取、修改與執行什麼。
  4. Harness 統籌：由 harness 協調 loop，連接 repo、MCP 工具、LSP、終端機、記憶與人類核准。
  5. 日誌與 trace：為每個有意義的動作留下日誌與 trace，之後才有辦法除錯。
  6. 評估與驗證：執行後確認品質、安全與政策合規。
  7. 稽核與回饋：用稽核與回饋關上迴圈，持續改進。

這套順序的重點，是讓 agent 保持有用，卻不變成不受控的自動化。自主性不是一次打開的開關，而是要隨著證據逐步增加的旋鈕。

最後的決策規則

做決定時，先檢查四件事：路徑是否不明、是否需要外部工具、是否要看中間結果、下一步是否會因判斷而改變。若多數答案是「是」，agent 才值得考慮；若答案多為「否」，優先選擇單次呼叫、決定性工作流、規則與人工複核，或批次服務。

即使選了 agent，也從狹窄且有界的用例開始，量測真實行為；只有在證據支持時，才逐步擴大範圍與權限。
