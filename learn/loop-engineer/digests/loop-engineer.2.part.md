# Digest — loop-engineer (part 2)

## Overview (L1)

- Build a Python Tool Dispatcher (exercise) — A hands-on coding exercise where learners implement `dispatch_tool()` to validate a structured tool call, dispatch only to tools registered in `TOOL_REGISTRY`, execute them with keyword arguments, and turn invalid requests into structured error observations. Ships with a `unittest` suite for `count_words`/`find_keyword` and a reference solution. Tests define exactly the contract: `{"ok", "tool", "result|error"}`.
- Agent Loops and Tool Calling (quiz) — A 10-question interactive quiz covering tool-call validation, schema constraint enforcement, tool-result contracts, read-only vs. side-effecting tools, idempotency on unknown outcomes, operational completion criteria, and which errors are safe to auto-retry. Reinforces chapter concepts with per-option feedback and overall explanations.
- Design a Minimal Executable Loop — The smallest runnable agent: a control loop with a goal, an action step, an observation step, and an evaluation step. Argues for starting with a debuggable control loop (never a giant platform) before adding tools, memory, guardrails, and approvals, and for keeping state/tools/policy/evaluator as separate interfaces.
- Define Goals and Completion Criteria — A goal is an executable contract, not a sentence in a prompt: it fixes what success looks like, what the agent may do, how progress is measured, and when the loop stops. Introduces the task contract (outcome, scope, inputs, constraints, success evidence) and stresses "define done before execution".
- Tool Calling as Agent Action — A tool call is the loop's action step: the model selects an allowed tool and emits structured arguments, but the harness validates and executes it, so the model never directly edits files or runs tests. Details the four pieces a safe tool needs (schema, runtime boundary, input validation, observation contract) and a governed execution pipeline (policy, schema validation, sandbox, audit log).
- Design Clear Tool Schemas — Tool schemas are a primary design surface because they turn intention into action. A strong schema names one clear purpose, types its parameters, marks required vs. optional fields, uses enums for constrained choices, describes fields in plain language, and returns a predictable shape; schemas should be reviewed against a checklist and treated as versioned engineering assets.
- Validate Tool Requests and Results — Validation happens on both sides of the tool boundary: before execution the request validator checks intent, schema, permissions/scope, and risk; after execution the result validator checks structure, freshness, evidence, and business rules before the output becomes a trusted observation. The enterprise pattern is validate → execute → prove, with failure paths designed in.
- Handle Errors, Timeouts, and Retries — Treats failure as normal loop execution, not an edge case, and places recovery logic between plan/act/observe/evaluate. Covers the recovery lifecycle (detect → classify → choose → recover with safeguards → verify), the six questions a retry policy must answer (attempts, backoff, timeout budget, idempotency, validation, stop/escalate), and layered timeouts tied to observability.
- Lab: Build a Test–Fix–Retest Agent — A 40–50 minute, dependency-free Python 3.10+ lab that builds a repair agent which runs tests, diagnoses a known failure (`discount_formula`), applies one exact guarded code change, and reruns tests to prove the fix. Demonstrates completion evidence (exit code 0), controlled terminal states (`VERIFIED`, `ESCALATED`, `FAILED`, `LIMIT_REACHED`), a backup artifact, and a full execution trace.

### build-a-python-tool-dispatcher

- Locator: `[[sources/loop-engineer/20261003/2 - Build a Tool-Using Agent/1. Build a Python Tool Dispatcher.html#build-a-python-tool-dispatcher]]`
- Summary: An exercise page with `unittest` tests (`evaluate.py`) and a reference solution (`tool_dispatcher.py`) for a `dispatch_tool()` function that validates and routes structured tool calls.
- Key claims: The dispatcher must confirm `tool_call` is a dict, read `name`/`arguments`, confirm `arguments` is a dict, execute only tools in `TOOL_REGISTRY`, pass arguments via `**arguments` (keyword arguments), return a structured success observation, and convert invalid requests into structured errors instead of crashing; the tests cover success routing (`count_words`, `find_keyword`), unknown tools (`"Unknown tool"`), non-dict arguments (`"Arguments must be a dictionary"`), and missing/wrong arguments (`"Invalid tool arguments"` via caught `TypeError`); the success shape is `{"ok": True, "tool", "result"}` and the error shape is `{"ok": False, "tool", "error"}`.
- Learner-relevant: Gives a concrete, test-driven artifact for the "tool call is a validated structured request" idea, ready to adapt into a runnable dispatch lesson.

### agent-loops-and-tool-calling

- Locator: `[[sources/loop-engineer/20261003/2 - Build a Tool-Using Agent/2. Agent Loops and Tool Calling.html#agent-loops-and-tool-calling]]`
- Summary: A self-contained interactive quiz (score board, reset, per-option feedback, expandable overall explanation) with 10 questions on agent loops and tool calling.
- Key claims: Before a side-effecting file-write tool runs, confirm path, content constraints, and authorization; when a schema says `limit` is an integer 1–20 and the model requests 50, reject with a structured validation error rather than silently executing; a useful tool result carries relevant output data, a stable operation identifier when side effects occur, clear success/failure status, and actionable error details (not hidden exceptions or unrelated logs); read-only and side-effecting tools need different risk controls and approval policies; after an order-creation network timeout with unknown outcome, safest is an idempotency key plus status query; an operational completion criterion is checkable with observable evidence; a search tool returning thousands of records when five were requested signals a defect in the tool-result contract/implementation; safe bounded retries are transient network timeouts on idempotent reads, rate-limit responses with retry guidance, and transient 503s (not invalid required fields, permission denials, or unapproved destructive requests); after a test tool reports failures, treat them as observations and choose a targeted corrective action; the clearest `replace_text` schema names file path, exact old text, replacement text, and expected match count.
- Learner-relevant: Provides an assessment bank and the chapter's intended mastery targets; each item maps directly to a lecture section and can seed `/tackle`-style checks.

### design-a-minimal-executable-loop

- Locator: `[[sources/loop-engineer/20261003/2 - Build a Tool-Using Agent/7. Design a Minimal Executable Loop.en.srt#design-a-minimal-executable-loop]]`
- Summary: Defines the minimal executable loop as the smallest agent that can run — decide, observe, decide what to do next — and argues for an explicit, debuggable control loop before adding capability.
- Key claims: Structure the loop as goal → load context (instructions, available tools, prior observations, constraints, state) → select and run an action → capture the observation → evaluate the stop condition → return a result or feed updated state into the next iteration; this is what separates a loop from a single model call, since a loop makes bounded progress until a clear stopping point, a limit, or escalation; a clean project shape separates responsibilities (`loop.py` controller, `tools.py` wrappers, `state.py` management, `evals.py` logic; `CLAUDE.md`, `codebase-map.md`, `claude-settings.json` for context/rules/permissions); state/tools/policy/evaluator must stay separate interfaces so the loop is not an untestable script; put boundaries around autonomy before expanding it — max steps, timeout, dry-run mode, and human approval gates for risky/high-impact actions — so failure modes are predictable.
- Learner-relevant: The blueprint for building a first runnable loop and the separation-of-concerns checklist used by the chapter's labs.

### define-goals-and-completion-criteria

- Locator: `[[sources/loop-engineer/20261003/2 - Build a Tool-Using Agent/8. Define Goals and Completion Criteria.en.srt#define-goals-and-completion-criteria]]`
- Summary: Explains how to turn a vague request into an executable goal contract with scope, inputs, constraints, success metrics, and a stopping rule.
- Key claims: Without a clear target the loop can plan, call tools, revise, and evaluate without knowing whether it is converging; translate business intent (summarize an incident, improve onboarding, prepare a release note, investigate a failing test) into a task contract that sets allowed sources/actions and out-of-scope boundaries; completion criteria name the evidence expected when done (test result, file change, structured report, reviewed PR, approval record); a well-defined goal has outcome, scope, inputs, constraints, and success evidence, ideally grounded in repo files (`CLAUDE.md`, `codebase-map.md`, `claude-settings.json`, MCP/LSP capabilities) rather than inferred from one prompt; criteria sit between observation and the past decision — the agent stops only when the observed result satisfies predefined criteria, otherwise it refines, retries, or escalates; define done before execution and evaluate every iteration against it.
- Learner-relevant: Supplies the goal/completion-criteria contract and evidence-log habit that make termination and reliability measurable.

### tool-calling-as-agent-action

- Locator: `[[sources/loop-engineer/20261003/2 - Build a Tool-Using Agent/9. Tool Calling as Agent Action.en.srt#tool-calling-as-agent-action]]`
- Summary: Frames a tool call as the loop's action step and details the governed lifecycle from intent to observation.
- Key claims: The model does not directly edit files, query databases, or run tests — it selects an allowed tool, supplies structured arguments (usually JSON), and waits for the result to return as an observation; the harness, not the model, decides what can actually execute, which is the controllable boundary; the lifecycle is intent → tool selection → structured arguments → harness validation against schema and safety rules → execution → observation (data, status, errors) → decide next (another tool, clarification, retry, or finish); a tool needs a schema, a runtime boundary (filesystem/shell/network/repo/database/service), input validation (required fields, allowed ranges, permitted operations), and an observation contract (results, failures, errors, metadata), otherwise you cannot tell whether the model chose badly, the tool failed, or the environment blocked it; risky actions (writing outside the repo, deleting files, network commands, installing packages) should require validation or approval; every tool call should pass through governance — policy check, schema validation, execution sandbox, audit log — and per-call approval pipelines are "not just for security teams" but how engineers build debuggable agents.
- Learner-relevant: The core "bounded observable tools, not hidden side effects" principle and the auditable pipeline later sections implement.

### design-clear-tool-schemas

- Locator: `[[sources/loop-engineer/20261003/2 - Build a Tool-Using Agent/10. Design Clear Tool Schemas.en.srt#design-clear-tool-schemas]]`
- Summary: Explains why schemas are a top design surface and the anatomy and review checklist of a strong tool schema.
- Key claims: Vague inputs, inconsistent parameter names, and unpredictable outputs cause ambiguous actions, extra retries, and loops that look intelligent but behave unreliably; a good schema names the tool, defines inputs, and states the output shape so the model can select confidently, the runtime can validate arguments, and the team can debug afterward; a strong schema has one clear purpose, typed parameters (string/number/array/object/boolean), explicit required vs. optional fields, enums for constrained choices, plain-language descriptions, and a predictable return shape; review checklist: use specific names (e.g. `search_codebase`, `create_ticket`, not `run_task`), type inputs, make constraints explicit, make errors recoverable, structure outputs so the next loop step can consume them, and ensure completion criteria are verifiable; schemas can live in a dedicated `schemas/` folder or beside the tool implementation and connect to MCP tools, LSP code intelligence, CI validation, and audit logging; treat schemas as versioned engineering assets, not prompt text hidden in an app.
- Learner-relevant: Provides the schema design checklist that turns each tool boundary into an operational safeguard.

### validate-tool-requests-and-results

- Locator: `[[sources/loop-engineer/20261003/2 - Build a Tool-Using Agent/11. Validate Tool Requests and Results.en.srt#validate-tool-requests-and-results]]`
- Summary: Shows validation on both sides of the tool boundary — request validation before execution and result validation before the output is trusted.
- Key claims: Tool calls are not automatically trusted because the model requested them, and tool results are not automatically trusted because a tool returned them; treat the request as a proposal, not a command — check intent (does the action support the goal/plan), schema (required fields, names, allowed formats), then permissions/scope (a well-formed request can still be unauthorized, too broad, or risky, e.g. creating a user, writing to a repo, querying customer data, running a terminal command); reject failed requests with a clear reason so the agent can repair or escalate; the result validator turns raw output into a trusted observation only after checking structure, freshness, source evidence, and business rules, guarding against silent failure, partial data, stale info, and syntactically-valid-but-useless output; on failure, retry with adjusted parameters, ask for clarification, escalate, or stop safely rather than guess; supporting components are the tool schema registry, policy engine, approval rules, retry strategy, MCP tool boundary, project context files, and an audit log; the enterprise pattern is validate → execute → prove, with failure paths (retry, human review, safe stop) designed in and correlation IDs recorded.
- Learner-relevant: The validate-both-sides discipline and failure-path design that make an agent loop debuggable, governable, and safe.

### handle-errors-timeouts-and-retries

- Locator: `[[sources/loop-engineer/20261003/2 - Build a Tool-Using Agent/12. Handle Errors, Timeouts, and Retries.en.srt#handle-errors-timeouts-and-retries]]`
- Summary: Treats error handling as a first-class control layer inside the loop and gives a recovery lifecycle plus retry/timeout policy.
- Key claims: Failure is normal loop execution, not an edge case — tools fail, APIs slow down, permissions change, and results can look successful but be incomplete; recovery logic sits between plan/act/observe/evaluate, and the agent should classify what happened, decide whether recovery is safe, and stay bounded; the user should get a valid result or a clear controlled outcome, never silent failure, infinite retries, duplicated actions, or vague responses; the recovery lifecycle is detect (exception, status code, missing output, schema mismatch, timeout) → classify (transient vs. permission vs. invalid result) → choose next action (retry, repair, approval, stop) → recover with safeguards → verify the result meets success criteria; a retry policy must answer attempts allowed, wait/backoff, timeout budget, duplicate-side-effect prevention (idempotency keys), whether the retry helped, and when to stop/escalate — with backoff and jitter to avoid worsening outages; timeouts are layered control boundaries (step, tool call, total request) owned by the harness (step-level) and tool adapter (tool-level, mapping low-level errors into observations); production recovery connects runtime, governance (approval, permission checks, audit logs), and observability (metrics, traces, error samples).
- Learner-relevant: The reliability control model for bounded retries, idempotency, and layered timeouts that later labs exercise.

### lab-build-a-test-fix-retest-agent

- Locator: `[[sources/loop-engineer/20261003/2 - Build a Tool-Using Agent/13. Lab Build a Test–Fix–Retest Agent.html#lab-build-a-test-fix-retest-agent]]`
- Summary: A 40–50 minute, dependency-free Python 3.10+ lab building `repair_agent.py`, a test–fix–retest agent that repairs a faulty discount calculation only when tests provide matching evidence.
- Key claims: Path A creates `lab02_test_fix_retest` with a deliberately buggy `calculate_discount` (`price - discount_percent` instead of `price - (price * percent / 100)`) plus `test_calculator.py` whose four tests (10% on $200 → $180, 0% preserves price, 100% → $0, >100 raises `ValueError`) serve as completion criteria; Path B builds `RepairState` (goal, `max_cycles=3`, cycle, status, diagnosis, change_applied, trace), a `run_tests()` tool (same interpreter, `unittest -v`, 10s timeout, captures output, exit code 0 = success), a narrow `diagnose_failure()` matching only `test_percentage_discount`/`test_full_discount` → `discount_formula`, a guarded `apply_fix()` that accepts only that diagnosis, replaces exactly one faulty line, refuses if the line is missing, and creates `calculator.py.bak` first, and a bounded `run_repair_agent()` loop (run tests → observation → stop if pass → diagnose → escalate if unknown → stop if already changed → apply fix → rerun); Path C verifies `VERIFIED` in 2 cycles with `change_applied: true`, confirms the repaired line and backup, runs an independent test pass, re-runs against an already-correct project (stops in 1 cycle, no edit), and tests the escalation path; completion requires initial failure, diagnosis, exact-line change, backup, passing second cycle, `VERIFIED`, independent OK, no edit when already correct, `ESCALATED` on unfamiliar failure, and a full trace.
- Learner-relevant: The capstone runnable artifact tying together tool validation, completion evidence, narrow diagnosis, guarded repair, retesting, terminal states, and execution traces.
