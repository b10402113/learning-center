# L1 overview

- Chapter 3 covers the Analyze step of the Analyze-Measure-Improve lifecycle — reading traces, categorizing failure modes, building a failure taxonomy, generating synthetic data — adapting Anthropic's (2024a) iterative cycle of test cases, prompt engineering, testing, and refining. Running example: a real estate CRM assistant (listing search, market analysis, email drafting, showing calendars) whose requests are multi-step and agentic — the LLM picks the next action from current state, each action triggers a tool, and tool output returns to the model.
- Terminology: a **query** is the raw input (from a human, pipeline, or scheduled job); a **trace** is the complete ordered record of every LLM message, tool call, tool return value, and final response. Evaluation targets whole traces, not individual steps, because a locally reasonable message can still yield a wrong final output. Traces are nondeterministic, so intermittent failures require rerunning the same query.
- Building a starting dataset: no fixed trace count — around 100 is a reasonable start, but the real signal is **saturation**, when new traces stop surfacing new failure categories. Sources are production logs (preferred; sample across features, include thumbs-down/rephrased/switched-channel sessions, consult domain experts) or synthetic queries.
- Naive synthetic generation ("Generate 50 queries for my app") collapses into near-duplicates testing one capability. The fix is indirection: define **dimensions** (feature, client persona, scenario type incl. well-specified/ambiguous/out-of-scope), generate structured **tuples**, then turn each into a natural-language query — write ~20 tuples by hand, then scale to 100+ (some teams prefer 10–20 deeply curated queries). Write down predictions of expected behavior first, then export full traces (Braintrust, LangSmith, Weave, or JSON/spreadsheet with one row per trace).
- **Open coding** (adapted from grounded theory): read traces as the user and write short, lowercase free-form notes about the first failure observed — usually the most upstream point, since one upstream error cascades. Do not group or diagnose causes yet. Optionally add a binary acceptable/unacceptable column. Known failure types (hallucination, malformed SQL joins, policy contradictions) can serve as "lenses." Continue until ~20 problematic traces are labeled and new modes stop appearing.
- Example open codes from the book: SQL dropped the pet-friendly filter; proposed a Saturday slot the calendar showed as blocked; investor email written in first-time-buyer tone; hallucinated bedroom/bath count contradicting the listing; emailed the wrong client from earlier context; silently resolved "Springfield" to the wrong state; gave an offer price with no comps lookup; ignored a tool error payload and fabricated results; six-paragraph "quick summary"; called send_email when only asked to draft.
- **Axial coding**: cluster open codes into higher-order failure categories. E.g. budget/bedroom omissions merge into "violation of user constraints," while hallucinated listing metadata and hallucinated user actions split apart because causes and fixes differ. An LLM may help cluster existing notes but must never generate the taxonomy from scratch (strong priors toward generic "hallucination"/"instruction following"/"tone"); it also should not do open coding, which requires human taste.
- **Structured labeling**: add one 0/1 column per failure mode (e.g. Missing constraint, Inappropriate tone, Wrong tool, Hallucinated fact) and compute **prevalence rate** = occurrences / total traces via spreadsheet, pandas, or pivot tables; two or three rounds of open coding and reannotation usually approach saturation, and analysis should be revisited periodically with fresh data. Caveat: first-failure labeling undercounts late-appearing modes (tone errors after constraint errors), so annotate all instances of any failure mode whose fix you want to measure.
- Chapter 3 pitfalls: unrepresentative data; skipping open coding for generic research categories or vendor metrics; Likert scales without detailed rubrics (noisy, low agreement) versus binary failure decisions; freezing the schema too early; excluding domain experts. Outputs: annotated trace dataset, failure taxonomy (the key artifact and shared vocabulary), and initial prevalence counts.
- Chapter 4 covers **collaborative evaluation** — aligning human judgment, since criteria are subjective and drift over time; Notion runs evals across ~70 engineers with a dedicated rubric team, and Shankar et al. (2024d) observed developers revising past labels as they saw more examples. The **benevolent dictator** model (one principal domain expert as ground truth) works when there is a trusted authority, criteria fall within their expertise, and volume is manageable (psychologist for mental health AI, lawyer for legal docs, support director, lead teacher, founder), but fails when the domain is too complex, criteria are contested, or rigor/unbiasedness must be demonstrated.
- **Nine-step collaborative workflow**: assemble annotators → draft rubrics (definition + Pass/Fail examples) → shared 20–50 trace set with borderline cases → independent labeling (no discussion) → measure IAA per criterion → alignment sessions on one criterion → revise rubrics → iterate to κ ≥ 0.6 → finalize rubrics and consensus gold-standard labels. Annotate multiple criteria per pass, but measure agreement and discuss them separately.
- **Agreement metrics**: percent agreement (Po) ignores chance — with 90% Pass labels, chance agreement is already 0.82. **Cohen's Kappa** κ = (Po − Pe)/(1 − Pe); the worked example gives Po = 0.85, Pe = 0.71, κ ≈ 0.48 despite 85% raw agreement. Landis & Koch bands: <0 poor, 0–0.2 slight, 0.21–0.4 fair, 0.41–0.6 moderate, 0.61–0.8 substantial, 0.81–1 almost perfect; targets vary (κ ≈ 0.5 rubric iteration, ≥ 0.6 judge validation, ≥ 0.7 training or regulatory). Alternatives: **Fleiss's Kappa** for 3+ raters, **weighted Kappa** for ordinal scales (quadratic weights), **Krippendorff's Alpha** for missing data/multiple raters/any scale (α ≥ 0.8 reliable, 0.67–0.8 tentative); the book prefers binary Pass/Fail. Cohen's Kappa is wrong for judge validation — peers vs. ground truth is classification, so use precision, recall, and false positive/negative rates.
- **Alignment sessions**: share IAA scores, list disputed traces, appoint a neutral moderator; ask what each annotator thought, where the rubric fails, and what would make future annotators agree; timebox to ~5 minutes per case. Rubric fixes: clarify wording, add concrete examples, add decision rules, split the criterion, acknowledge irreducible ambiguity with a tiebreaker. Avoid majority voting as a rubric fix, adversarial framing, and skipped documentation; escalate unresolved cases to a senior expert and record the ruling. Keep the gold-standard dataset and docs for judge validation, fine-tuning, auditing, and iteration.
- Chapter 4 pitfalls: skipping independent annotation (measures groupthink), starting with a vague rubric, using only percent agreement, ignoring **temporal drift** (relabel a 10–15 trace anchor set periodically), **synthetic-annotator collusion** (both annotators using the same LLM inflates κ), and relitigating past labels instead of improving future consistency. Outputs: refined rubric, consensus gold-standard dataset, edge-case documentation.
