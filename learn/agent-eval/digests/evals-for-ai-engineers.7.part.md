# L1 overview

- **Chapter 10. Interfaces for Human Review** argues that automated evaluators handle most monitoring, but humans must still review sampled traces to catch blind spots and keep evaluators calibrated against criteria drift. LLM traces (query, tool calls, retrievals, reasoning, output) do not fit spreadsheets; a custom review interface can cut a five-minute trace review to 30 seconds.
- Build options: Streamlit, Gradio, LLM-generated FastAPI/HTML dashboards, or purpose-built platforms current as of 2026 — Langfuse, Braintrust, Arize Phoenix, Helicone, W&B Weave, plus LangSmith and Arize for browsing. Start with the existing observability tool, log friction points for a week, then build.
- Table 10-1 applies Jakob Nielsen's usability heuristics (Nielsen 1994a) to review UI: visibility of system status, match with real-world rubric terms, user control and freedom, consistency, error prevention, recognition over recall, flexibility/efficiency, and aesthetic/minimalist design.
- Essential elements collapse low-value trace sections by default; feedback uses binary failure-mode tags from error analysis (Chapter 3) and collaborative evaluation (Chapter 4), quick thumbs/numeric ratings, and open-ended fields. Speed features include keyboard shortcuts, visual hierarchy, progressive disclosure; quality features include inline span annotation, feedback templates, and a prominent Defer button; navigation features include contextual metadata, channel filters, batch/bulk labeling, and progress indicators. Keyboard shortcuts are called the single highest-leverage feature, roughly doubling throughput.
- **Case Study: EvalGen** (Shankar et al. 2024d; EvalGen v2 in ChainForge, Arawjo et al. 2024) shows one output at a time, binary thumbs feedback, open comments, editable past labels, and a rubric builder that extracts candidate criteria from the prompt. It prioritizes traces where LLM judges disagree (uncertainty sampling) and its user studies found that human reviewers also experience criteria drift, so interfaces must allow revising earlier labels and adding failure categories midstream.
- **Selecting traces**: random sampling is unbiased but misses rare failures; uncertainty sampling targets evaluator disagreement (criteria split, inconsistent judge runs at temperature > 0, code-check vs LLM-judge conflicts); failure-driven sampling pulls guardrail flags and thumbs-down traces but has high precision and low recall. A starting blend is 50% failure-driven, 30% uncertainty, 20% random, adjusted by known failure rate (under 5% skew random/uncertainty; over 20% skew failure-driven). The random portion is the only unbiased estimate of overall quality.
- **Group-level navigation**: clustering by metadata (client persona, feature) or semantic embedding with k-means surfaces systematic problems such as overly casual investor emails or missing HOA fees and school-quality ratings; keyword, metadata, and semantic search find more traces like a spotted failure.
- **Workflow integration**: daily/weekly batch jobs selected by the sampling strategies notify reviewers via Slack/email; safety violations and regressions page on-call reviewers. Feedback flows into CI golden datasets and LLM-as-judge calibration; interfaces should offer one-click "add to golden set," prefilled bug filing, and dashboards of frequent failure types and human-judge disagreement.
- **Real estate walkthrough** traces the same email task from a Google Sheets row (truncated query, JSON blobs, semicolon-separated notes) to a Streamlit/Gradio single-trace UI with Good/Bad Email buttons, to an advanced UI with cluster views, bulk tagging, structured failure modes (Tone Mismatch, Missing Budget, Hallucinated Feature), hotkeys, metadata, and entity highlighting. Agentic systems should also surface tool-call counts/order, retrieval counts and ranks actually used, token/cost per trace, and latency by step — e.g., a correct answer at 10x cost from needless looping.
- **Case Study: DocWrangler** (Shankar et al. 2025) is an IDE for LLM document processing that shows document, output, and prompt side by side, encourages open coding notes ("missed the date field"), and feeds accumulated comments into a prompt-improvement feature with side-by-side old/new prompts.
- **Chapter 10 pitfalls**: not looking at enough traces (subtle and sub-1% failures still matter; always include a random sample of all-pass traces), overrelying on evaluator disagreement when judges are correlated (add at least one rule-based evaluator), and underestimating custom interfaces versus off-the-shelf platforms.
- **Chapter 11. Data Analysis for Traces** frames error analysis as one kind of data analysis and adds exploratory data analysis (EDA), a term coined by John Tukey in the 1970s as a counterweight to confirmatory analysis. Clusters, correlations, and bar charts are hypothesis prompts, not failure modes; read underlying traces and expect to drop most first hypotheses. A real estate example: clustering query embeddings found only obvious categories, but clustering final emails found a cluster of long-apology openings that earlier error analysis missed.
- **EDA techniques**: plot metric distributions (unimodal, bimodal, long-tailed), cross-tabulate metadata against outcomes (e.g., thumbs-down by session length), correlate metrics (tool calls vs latency or thumbs-down), filter to a slice and read 20 traces back to back, and hunt outliers with the IQR rule (below Q1 − 1.5×IQR or above Q3 + 1.5×IQR) or a top/bottom 1% percentile cut. Confirmation protocol: read 20 cluster traces, define a testable criterion, and require it to hold for 70–80%; LLM-extracted clustering features need at least 90% accuracy on a manually labeled validation set.
- **Semantic search and AI assistants**: expand a known failure via a seed trace's nearest neighbors or a natural-language description; embedding similarity is not task similarity (topic words dominate), so check precision/recall against labels or embed LLM-extracted application features instead. Claude Code and Codex are used as a scratchpad with traces, field docs, and app code in the working directory — plotting many charts at once, drafting classifiers/regexes, summarizing clusters, or searching traces directly while they fit the context window. Never accept an AI agent's causal explanation; treat it as a hypothesis and verify with a one-variable change against a golden set.
- **Chapter 11 pitfalls**: cluster labels as ground truth, confounders (more tool calls may just mean harder queries; stratify by query complexity, segment, time of day), AI explanations treated as conclusions, and analyses skewed toward unusual cases without a random sample.
- **Chapter 12. Improving LLM Agents** orders accuracy work by effort. Low effort is prompt refinement: fix Gulf of Specification errors first (the real estate "homes" means single-family houses case), add few-shot examples distinct from CI cases, retrieve dynamically similar examples, use personas, and use chain-of-thought only for non-reasoning models (o-series and DeepSeek R1 reason internally; tune the thinking budget instead).
- Medium effort changes architecture: decompose into focused steps, tune RAG query/chunking/reranking, improve tool descriptions (e.g., `date: string in YYYY-MM-DD format`), use self-consistency across temperature > 0 samples, add a second verifier LLM call, and add synchronous guardrails (regex for SSNs, SQL parser). DoorDash's support chatbot case cut hallucinations roughly 90% by summarizing noisy delivery history into structured context before prompting, validated with thousands of LLM-simulated dasher conversations.
- High effort is model-level: fine-tuning, usually PEFT such as LoRA or QLoRA (4-bit base model lets a 70B model train on one 48 GB GPU; 50–200 examples often suffice), preference tuning with DPO or KTO for style/verbosity, serving via vLLM/TGI or Together AI/Fireworks/Modal, and automated prompt optimization with DSPy (Khattab et al. 2024), TextGrad (Yuksekgonul et al. 2025), or OPRO (Yang et al. 2024).
- **Cost optimization** mirrors accuracy work: find the biggest drivers, change, and verify quality. Match model size to task complexity; cut tokens with concise instructions, fewer retrieved documents, upfront summarization, and compact YAML output; make prompts cache-friendly by putting constant instructions before variable data because KV-cache reuse requires an exact byte-for-byte prefix (Anthropic reported cache hits at 10% of input price and up to 85% lower latency); batch offline work (OpenAI Batch API within 24 hours at half cost); distill a teacher into a student (student cannot exceed teacher quality and is worse calibrated on rare inputs); and use model cascades.
- **Model cascades** set a target agreement rate (e.g., 95%) between the expensive oracle and the cheap proxy. The proxy needs a binary verdict and a confidence score: use logprobs for single-token classifications (convert with exp(), normalize, take the higher probability) or structured output with a verbalized 0–10 confidence for open-ended answers (less reliable, especially for instruction-tuned models). Calibrate offline by sorting held-out examples by proxy confidence and choosing the lowest threshold where proxy-oracle match rate meets the target; at runtime, escalate below threshold. If confidence does not separate correct from incorrect, everything routes to the oracle — safe but no savings. Chaining multiple models gives each its own threshold; FrugalGPT (Chen et al. 2023) introduced LLM cascades and task cascades (Shankar et al. 2026) vary the task per stage.
- **Routing** differs from cascading: a classifier sends each query directly to a model with no cheap-first attempt, avoiding cascade latency but offering no second chance for misroutes; teams often combine a router for obvious cases with a cascade for the ambiguous middle. Options include RouteLLM (Ong et al. 2024; 85% cost reduction on MT-Bench at 95% of GPT-4 quality), Microsoft Foundry's Model Router, and Martian.
- The closing recaps the Analyze-Measure-Improve lifecycle, warns that every fix shifts the failure distribution and that datasets and taxonomies go stale, and Table 12-1 maps strategies to effort, data needs, and best-fit failures (prompt refinement → architectural changes → automated prompt optimization → LoRA/QLoRA → full/preference tuning → distillation + cascade), recommending working top-down. Next Steps names open areas: reasoning-model intermediate-step evaluation, multi-agent evaluation, process reward models, and the blurring line between evaluation and monitoring.
