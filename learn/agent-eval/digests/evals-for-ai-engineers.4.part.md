# L1 overview

- Chapter 5. Implementing Automated Evaluators turns Chapter 3's trace-based error analysis and Chapter 4's rubric into automated measurement, so failure rates can be tracked at scale without reading every trace.
- Metrics split into reference-free (rule/intrinsic-property checks, no golden answer) and reference-based (comparison against a curated golden output); the book recommends trying to design both for each significant failure mode.
- Running example is Example 3-1, a real estate chat-based CRM assistant that issues SQL, drafts client emails, reads calendars, and searches the internet. Table 5-1 lists its failure modes: missing SQL constraints, incorrect SQL aggregation, invalid tool usage, incomplete email content, persona-tone mismatch, incorrect tool sequencing, unjustified tool calls, location ambiguity.
- Key prioritization rule: fix Gulf of Specification (prompt ambiguity) failures first, then build evals for Gulf of Generalization failures. Building an evaluator for a prompt-fixable failure is wasted effort and merely measures how well the LLM "reads our minds."
- Executability checks (running generated SQL against a test database, simulating tool calls) assess functional correctness, not just whether the output looks right.
- Table 5-2 pairs concrete reference-based and reference-free metrics per failure mode, e.g. SQL AST comparison vs. AST traversal for mandatory filter keywords, tool-registry schema check, geocoding consistency for location ambiguity.
- Code-based evaluators (JSON/SQL parsing, regex, structural counting, execution, logical checks) are fast, cheap, deterministic, and interpretable; LLM-as-judge (Zheng et al. 2023) is for nuance — tone, faithfulness, helpfulness — and works best on narrow binary Pass/Fail tasks.
- Zheng et al. (2023), from LMSYS (Chatbot Arena), documented three systematic judge biases: position bias (GPT-4 showed it on ~26% of judgments), verbosity bias, and self-enhancement bias.
- A well-structured judge prompt has four components: clear task and single evaluation criterion, precise Pass/Fail definitions, few-shot examples, and a structured JSON output with `reasoning` and `answer`. Example 5-1 gives a full tone-appropriateness template for three personas (Luxury Buyers, First-Time Homebuyers, Investors).
- Judge construction mirrors training a classifier via prompt engineering: disjoint training / dev / test splits (typical 10–20% train, 40–45% each dev and test), with 30–50 Pass and 30–50 Fail examples in each of dev and test; in-context learning saturates after a few examples (Min et al. 2022), so data goes to evaluation.
- The refinement loop measures TPR = p/P and TNR = f/F rather than precision/recall, because those two error modes map directly onto over/under-estimating the true pass rate. Stop at targets like >90%; DSPy (Khattab et al. 2024) can automate the loop but manual iteration is recommended first.
- Bias correction uses the Rogan-Gladen (1978) estimator θ̂ = (p_obs + TNR − 1) / (TPR + TNR − 1), clipped to [0,1], with a guard when TPR + TNR − 1 is near zero; uncertainty comes from a bootstrap over the test set with 2.5th/97.5th percentiles for a 95% CI. Table 5-4 shows how TPR/TNR combinations shift the estimate. The book open-sourced a numpy-only library called `judgy`.
- Shipping decisions depend on interval width, not just the point estimate: θ̂ = 0.87 with CI [0.81, 0.93] against a 0.85 threshold forces a cost-of-error judgment, whereas [0.85, 0.89] is decisive.
- Optional group-wise metrics cover multiple outputs per input: Success@k / Pass@k (Jain et al. 2025; Chen et al. 2021; Kulal et al. 2019), Precision@k, Recall@k, embedding cosine similarity for semantic closeness, and average pairwise semantic similarity for diversity (with a scikit-learn `cosine_similarity` + `np.triu_indices_from` snippet).
- Common pitfalls: omitting few-shot examples entirely, cramming multiple criteria into one prompt, skipping alignment, data leakage between prompt examples and the eval set, never re-aligning as production data drifts, and ignoring judge stochasticity (run 3–5 times at temperature > 0 to check label stability).
