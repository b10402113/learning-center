# Rogan-Gladen 修正：把 judge 的 TPR/TNR 誤差扣掉

上一篇提到，未修正的通過率可能會偏高。最危險的情況是：judge 放行了真正失敗的案例，讓你看著一個漂亮數字就準備上線。

但只知道「可能偏高」還不夠。這篇要進一步算出：到底偏了多少。

使用的工具叫做 **Rogan–Gladen 修正**。它在 1978 年提出，原本就是用來處理「用不完美的檢測工具，估計母體比例」的問題。這不是新方法，也不是專為 LLM 設計的公式，只是剛好能拿來估計真實的通過率。

而你手上正好有套用它所需的三個數字。

## 你需要先備好三個輸入

修正公式只需要三個輸入：

- `p_obs`：judge 在 `m` 筆未標註的 trace 上判定為 Pass 的比例，也就是上一篇算出的 `k / m`。
- **TPR**：judge 辨認真正成功案例的能力，從人工標註的 test set 測得。
- **TNR**：judge 擋下真正失敗案例的能力，同樣從人工標註的 test set 測得。

注意，這三個數字來自兩個不同地方。

TPR 和 TNR 來自人工標註的 test set；`p_obs` 則來自你真正想估計、但沒人標註過的那批 trace。

這個分工很重要，也會影響後面 bootstrap 要重抽樣哪一份資料。

## 公式長什麼樣子

修正後的估計值寫成 **θ̂**（theta hat），意思是「真實通過率的估計值」：

<!-- derived -->

```text
θ̂ = (p_obs + TNR − 1) / (TPR + TNR − 1)
```

分子是在調整 `p_obs`。TNR 離 1 越遠，分子扣掉的數字越多，因為這代表 judge 放行了更多原本應該被擋下的失敗案例。

分母則是在衡量 judge 比亂猜好多少：

<!-- derived -->

```text
TPR + TNR − 1
```

把這兩個調整合起來，就能把觀察到的通過率 `p_obs`，換算回比較接近人工判斷標準的通過率。

### 範例一：修正後通過率上升

假設：

- TPR = 0.90
- TNR = 0.95
- `p_obs` = 0.70

先算分子：

<!-- derived -->

```text
0.70 + 0.95 − 1 = 0.65
```

再算分母：

<!-- derived -->

```text
0.90 + 0.95 − 1 = 0.85
```

因此：

<!-- derived -->

```text
θ̂ = 0.65 / 0.85 ≈ 0.765
```

原始通過率 0.70 被往上修正到約 0.765。

原因是 TPR 只有 0.90，代表 judge 漏掉了一些真正成功的案例，所以原始通過率被壓低了。

### 範例二：修正後通過率下降

換一組數字：

- TPR = 0.95
- TNR = 0.60
- `p_obs` = 0.73

分子是：

<!-- derived -->

```text
0.73 + 0.60 − 1 = 0.33
```

分母是：

<!-- derived -->

```text
0.95 + 0.60 − 1 = 0.55
```

因此：

<!-- derived -->

```text
θ̂ = 0.33 / 0.55 = 0.60
```

這次方向相反，原始通過率 0.73 被拉回 0.60。中間相差的 0.13，就是 judge 放行失敗案例所造成的假象。

<!--image:2-->

同一條公式，可能把數字往上修，也可能往下修。

這也是為什麼上一篇要你分別檢查 TPR 和 TNR：修正後數字往哪個方向移動，取決於哪一種錯誤比較嚴重。

## 兩個邊界情況，處理方式不一樣

公式本身不難，真正需要小心的是：知道什麼時候不能使用它。

素材裡提到兩種邊界情況，處理方式完全不同。

### 第一種：分母接近零

當：

<!-- derived -->

```text
TPR + TNR − 1
```

接近 0，例如 TPR 和 TNR 都在 50% 附近時，這個修正會變得非常不穩定。

因為你正在除以一個極小的數，結果可能從 0.1 跳到 0.9；分子只要在小數點後第二位有一點變化，答案就可能完全不同。

這種 judge 的表現和亂猜差不多，修正結果不可靠，不應該拿來使用。

判準要在事前就設好：分母太小就拒絕下結論，而不是先算出一個奇怪的數字，再回頭檢查。

<!--image:3-->

### 第二種：結果超出 0 到 1

另一種情況是，數值雜訊把 θ̂ 推到 `[0, 1]` 之外。

即使 judge 的表現不錯，計算結果仍可能稍微低於 0，或稍微高於 1。但真實通過率不可能超出這個範圍，因此通常會把結果裁切到 `[0, 1]` 之間，這個動作就叫 **clip**。

裁切不是為了掩蓋錯誤。估計值本來就可能帶一點誤差，把它拉回合理的範圍而已。

## 程式碼裡怎麼寫

素材提供的 Python 實作，把這兩個處理方式放在同一段程式碼裡：

1. 分母小於 0.05，就直接拋出錯誤。
2. 算出 θ̂ 後，再把結果裁切到 `[0, 1]`。

<!-- source: sources/agent-eval/20261029/Evals for AI Engineers Systematically Measuring and Improving AI Applications .txt#L1588-L1592 -->

```python
    denom = TPR + TNR - 1
    if denom < 0.05:
        raise ValueError("Judge accuracy too low for correction")
    theta_hat = (p_obs + TNR - 1) / denom
    theta_hat = np.clip(theta_hat, 0, 1)
```

其中的 0.05 是實作選擇的門檻，不是理論上唯一正確的數字。

它的作用，是把「分母太小、結果可能爆掉」轉成明確的例外，讓 pipeline 停下來，而不是安靜地產出一個看起來正常、其實不可靠的數字。

這裡真正要緊的其實是錯誤處理。

如果一支 judge 的 TPR 和 TNR 都在 0.5 上下，就沒有辦法可靠地修正通過率。可接受的結局只有兩個：

- 修好這支 judge。
- 換一支更好的 judge。

「先算一個數字出來擋著」不算其中一個選項。

## 修完就結束了嗎？

到這裡，你已經有一個 θ̂。

假設算出的結果是 0.87，剛好越過團隊設定的 0.85 門檻，你可能就準備按下 ship。

但這個 0.87 是從一份 test set 測出來的。如果當初抽到的是另一份 test set，量到的 TPR 和 TNR 可能會稍微不同，最後算出的 θ̂ 也會跟著改變。

問題是：它到底會差多少？

如果換一份資料，結果就從 0.87 掉到 0.79，那麼 0.87 就不該直接拿來當作決策依據。

下一篇要處理的，就是替這個點估計加上一個區間，讓你看出這個數字到底有多穩。
