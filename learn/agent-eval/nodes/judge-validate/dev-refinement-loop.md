# Dev set 修正迴圈：看 disagreement、改 prompt、何時停

上一節，你已經把 trace 分成互不重疊的 train、dev、test 三組，也知道每一組各自負責什麼。

現在手上有三樣東西：

- 一份可以放進 prompt 的範例池
- 一份用來反覆試錯的 dev set
- 一份暫時不能碰的 test set

接下來的問題是：dev set 到底怎麼用？每次改完 prompt 要看什麼、改哪裡，什麼時候才該停？

這一段就把整個迴圈跑一遍，再跑一遍，直到你有足夠理由停手。

## 先寫一版 baseline，不要一次寫到完美

迴圈的第一步不是改進，是先有一個量得出來的起點。

先寫一版 baseline prompt，內容包括：

- 任務描述
- 清楚的 Pass／Fail 定義
- 固定的輸出格式
- 從 training set 挑出的 few-shot 範例

這版的目標不是好，而是「有」。

沒有 baseline，之後每次修改都回答不了一個問題：「這樣改，真的有變好嗎？」

這跟調整分類器很像：都是先看錯在哪，再往正確的方向修。差別只在你調的不是模型參數，而是 prompt 的文字和範例。

## 在 dev set 上跑，再跟人工標籤對照

有了 baseline，就讓 judge 跑過 dev set 裡的每一筆 trace。

跑完不要只看它通過幾筆，而是逐筆把 judge 判的 Pass／Fail 跟你自己做的人工標籤放在一起比。

這一步會得到一張對照表，每一列是一筆 trace，只有兩欄：

- 人工怎麼判
- judge 怎麼判

有用的資訊通常就在這兩欄對不上的那些列。

## disagreement 要分兩類看

不一致可以分成兩種，意思完全不同。

**false pass** 是 judge 說 Pass，但人工標籤是 Fail。

**false fail** 則是 judge 說 Fail，但人工標籤是 Pass。

這兩類不能混成一個「準確率」來看。

- false pass 代表 judge 太寬鬆，把真正的失敗放過去了。
- false fail 代表 judge 太嚴格，把原本好的成果擋下來。

通常你會發現其中一類明顯比另一類多。這個不平衡本身就是線索，它指出 prompt 的判斷標準偏哪一邊。

## 改 prompt 的三個動作

看完 disagreement，才輪到修 prompt。

看錯誤的性質，從下面三個方向挑一個做。

**把 Pass／Fail 的判斷標準寫清楚。**

如果錯誤集中在某個模糊地帶，問題通常不是 judge 不夠好，而是你的定義留下太多解釋空間。

**換上更有說明力的 few-shot 範例。**

範例一樣從 training set 裡挑，讓它更能說明你希望 judge 怎麼處理這類情況。

**補上新的 failure mode。**

如果 dev set 出現 training set 裡沒有的失敗類型，就把其中具代表性的 trace 加進 training set，下一輪再考慮要不要放進 prompt。

順序很重要：先補進 training set，再考慮放不放 prompt，不要直接把 dev set 的案例貼進 prompt。

上一節提到的 leakage，就是在這裡發生的。

## 改完後，跑同一份 dev set

修完 prompt，回到同一份 dev set 再跑一次，重新計算指標。

「同一份」是重點。

如果每次改完都換一批資料，量到的差異會混進樣本本身的差別，到最後你分不清是 prompt 變好了，還是這批題目剛好比較簡單。

接著重複這個流程：

**跑、看 disagreement、修改、再跑。**

## 什麼時候該停

停下來的條件不是「看起來差不多了」。

判準是：當 **TPR** 與 **TNR** 都達到可接受的水準，例如都超過 90%，就可以停。

這裡的門檻不是固定值，要看你的應用情境。

如果漏掉一個真正的失敗，代價比誤判一個成功還高，你就會想把門檻往上拉，尤其是負責抓失敗的那個比率。

## 先手動跑，別急著自動化

現在已經有工具可以自動化這個迴圈，直接在 dev set 上搜尋比較好的 prompt。

不過在用這些工具之前，建議先手動跑幾輪。

手動的價值不在效率，而在於你會被迫逐筆看 disagreement。看久了，你會慢慢知道：

- 這個 failure mode 通常長什麼樣子
- judge 在哪些情況下容易被騙

這兩件事，自動化工具不會直接告訴你。

## 你現在手上的東西

跑到這裡，你應該已經有：

- 一版定稿的 prompt
- 一組在 dev set 上穩定下來的表現
- 一個可以說明為什麼停手的理由

不過整段過程一直提到「TPR 與 TNR 都超過 90%」，這兩個數字卻還沒真的算出來。

下一個問題就是：這兩個比率怎麼從 2×2 的結果算出來？為什麼該看它們，而不是 precision 和 recall？
