# Test set 驗證：凍結 judge，量 TPR/TNR 而非只看通過率

上一節留下一個問題：

你的 prompt 是在 dev set 上調出來的，TPR 和 TNR 也是在那裡量到的。要怎麼確認這組數字在沒看過的新資料上還成立？

答案是那份從頭到尾都沒碰過的資料：**test set**。

## 第一步：凍結 prompt

驗證的起點不是「再改一點」，而是「不准再改」。

當 dev set 上的 TPR 和 TNR 穩定下來、數值也夠高，就把 judge prompt 凍結。接下來一個字都不要動，直接用這份 prompt 跑 test set。

凍結 prompt 本身就是驗證的一部分。

如果你在 test set 上看到結果不理想，又回頭改 prompt，test set 就變成第二個 dev set，你也失去唯一一份乾淨、沒被拿來調整的資料。

## 跑一次，會拿到兩個東西

凍結後跑 test set，你會同時得到兩樣東西。

第一個是**估計的通過率**：test set 中，被 judge 判定為 Pass 的比例。

第二個是 **judge 的 TPR 與 TNR 估計值**：把 judge 的判斷與人工標籤逐筆比對，再用上一節的 2×2 表格算出來。

<!--image:1-->

這兩樣東西性質完全不同，卻很容易被搞混。

通過率是你真正想知道的答案，TPR 和 TNR 則是這個答案有多可信。

只拿到通過率，就像找另一個人幫你數鈔票：你知道他數出的金額，卻不知道他有沒有漏數或多數。

兩個數字一起拿到，你才有辦法判斷這個通過率可能偏多少。

## 為什麼不能直接數 Pass？

問題出在下一步。

你最後想知道的，不是 test set 上的通過率，而是 production 裡那批**沒有標籤**的新 trace，到底有多常出現 failure mode。

那批資料沒有人工作標註，所以你只能依靠 judge。

於是，你把同一個 judge 跑過幾千筆新輸出，再數一數其中有幾筆被判成 Pass，直接把這個數字當成通過率。

這樣做會得到一個**有偏的估計**。

因為 judge 並不完美：它有時漏掉真正的 Fail，有時把不該通過的結果判成 Pass。

當你只數 judge 判定為 Pass 的筆數，這兩種錯誤就會一起混進結果裡，而且光看這個數字，看不出裡面混了多少錯。

<!--image:2-->

這就是 test set 的價值。

test set 有人工標籤，你可以在那裡量出 judge 的錯誤率；production 沒有，你只能帶著這組量好的錯誤率，去理解 production 上的計數結果。

## 兩個數字，兩種錯誤

對照上一節的結論，這裡的角色就清楚了。

在 test set 上，TPR 高、TNR 也高，代表 judge 漏掉真正的 Pass、放過真正的 Fail 的情況都比較少，你數出來的通過率就比較接近真實值。

如果 TNR 明顯偏低，之後在 production 上數出的通過率就會系統性偏高。

這個偏高不是雜訊，也不是樣本數不夠。它來自 judge 本身的結構性偏差，而且不會因為你多跑幾千筆資料就消失。

<!--image:3-->

所以驗證時要看兩個比率，不能只問「test set 的通過率是多少」。

只看通過率，你得到的只是一個數字，卻不知道它可能往哪個方向偏。

## 這個節點走到哪裡？

回頭看前面四節，你做的其實是一條完整的流程。

先把標註好的 trace 切成互不重疊的 train、dev、test，避免資料洩漏。

接著在 dev set 上反覆修正，根據 false pass 與 false fail 調 prompt，直到 TPR 與 TNR 穩定。

再用 2×2 表格算出這兩個比率，理解它們各自代表哪一種偏差方向。

最後凍結 prompt，在 test set 上跑一次，量出一組乾淨的錯誤率。

現在，你可以指著一份 test set 說出兩件事：

1. 這個 judge 的 TPR 與 TNR 是多少。
2. 如果直接數 judge 判定為 Pass 的筆數，結果會往哪個方向偏。

還沒解決的是偏差本身。

你已經知道偏差存在，也知道它會往哪個方向走，但還沒有把它從 production 的通過率中扣除。

下一步，就是利用這兩個比率，把一個有偏的計數，換成更接近真實值的估計。
