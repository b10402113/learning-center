# 三種偏誤的控制：pairwise 換位、長度中立、換 judge 模型

你已經用 gold set 對過 judge、算過 TPR/TNR，也開始讓它評估每一條 trace。跑一陣子之後，你可能會注意到幾個奇怪的現象：

同一組 A、B 回答，只是把順序對調再判一次，贏家竟然換人。或者 agent 多寫了三段廢話，分數反而上升。

先別急著怪 prompt。judge 這個工具本身就可能帶著系統性偏誤。

## LLM-as-a-judge 從哪裡來？

「LLM-as-a-judge」這個詞是 Zheng et al. (2023) 提出的。他們拿大量人類偏好資料訓練專門的 judge 模型，讓判斷盡量貼近人類期待，在 benchmark 上的表現也確實好。

但實務上很少有人真的從頭訓練這類模型。多數應用在開發初期根本沒有足夠的標註偏好資料，所以我們通常改用現成的 LLM 當 judge（off-the-shelf），再用 prompt engineering 把它的輸出對到自己定義的 failure。

麻煩也在這裡：現成模型沒有針對你的資料對齊。Zheng 的團隊（就是做 Chatbot Arena、讓模型兩兩對戰的 LMSYS）比對 judge 評分和人類評分的一致程度，找出三種系統性偏誤。

## Position bias：它偏好某個位置，不是某個答案

當你要求 judge 並排比較兩個回答，它可能偏向排在前面的那個；也有些模型偏好排在後面的。就算兩邊品質一樣，位置還是會影響它的選擇。

Zheng et al. (2023) 的研究指出，GPT-4 約有 **26%** 的判斷出現這種偏誤。大約四分之一，已經不能當成雜訊忽略。

最直接的辦法是 **pairwise 換位**：同一組 pair 跑兩次，一次讓 A 在前、B 在後；另一次對調順序。只有兩次都選同一方，才算那一方真的贏。兩次結果不一致，就記成 tie，或交給人工檢查。

它擋掉的誤判很具體：某個回答其實沒比較好，只是剛好被擺在 judge 偏好的位置。

換位順便還會給出另一個訊號。同一組 pair 只要對調順序就翻盤，表示這個判斷本來就不穩。

## Verbosity bias：話多就有分

第二種是長度偏誤：回答寫得越長，越容易被評為品質高，就算短的那個一樣正確。

judge 一旦有這種偏誤，等於在獎勵 agent 灌水。多寫幾段看起來很有內容的鋪陳，分數就上去了。

控制手段是採用**長度中立**的 rubric。評分規準只判斷「正確性」和「是否滿足需求」，並在 prompt 裡明講：長度、格式、詳盡程度都不計分。

如果 rubric 有針對內容的評分項目，也要補上一句：「多寫但沒有新增資訊的內容不加分。」

實作上還有一個輔助做法：不要讓 judge 拿著兩份全文比誰長，先列出兩份回答的差異點，再讓它判斷這些差異。這樣看的是它有沒有抓到關鍵差異，而不是誰的字數比較多。

## Self-enhancement bias：自己人判自己人

第三種偏誤最隱蔽。當 judge 和被評估的 agent 是同一個模型，例如用 GPT-4 評估 GPT-4 的輸出，judge 可能比中立評審更偏袒這份輸出。

控制手段是**換 judge 模型**。用不同家族的模型當 judge，至少不要讓 judge 和被評估的 agent 是同一個模型。

如果要做跨版本比較，例如比 v1 和 v2，就把 judge 固定住。不要同時換掉被評估的模型和 judge，否則分數一變，你會分不清是哪一邊造成的。

## 三個控制要寫進設定，別只記在腦裡

這些偏誤不代表 LLM judge 不能用，但原始分數不能單獨相信。你得在 prompt 和驗證流程裡把偏誤控制住。

做法是把每一項控制寫成 run 設定的一部分，例如：

- 這個 step 有沒有啟用換位
- rubric 有沒有包含長度中立條款
- judge 用哪個模型

這些欄位要跟著 judge 的版本一起留下來。下次要比「改了 prompt 有沒有變好」，得先確認兩次用的是同一套量測方式。
