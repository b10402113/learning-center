# Judge 會過期：資料漂移、模型升級與重新對齊

上一篇量到的穩定度，適用範圍寫得很清楚：今天的資料、這批資料，還有這個模型版本。

問題是，這三個條件沒有一個會固定不變。

production 的資料會漂移。上線三個月後，使用者提出的問題可能已經和建資料集時不同。新的 failure mode 會出現，但你的 judge 從來沒看過。

同時，模型可能被更新，行為也跟著改變。連你自己的評分標準也會變：上季判 fail 的情況，這季可能已經算可以接受。

<!--image:1-->

所以對齊一次不算收尾，事情才剛開始。

## 對齊是一個定期動作，不是一次性任務

建議定期重跑，例如每週一次。做法不複雜：

繼續標註一小批新的 trace，使用同一套 rubric 重算 TPR 和 TNR，再檢查信賴區間是否仍然夠窄。

區間還在可接受範圍內，judge 就繼續用；區間變寬，或 TPR、TNR 開始掉，就得重新對齊。

定位要放對：它是 LLM 應用的日常維運，跟 MLOps 裡的監控是同一類工作，不是交付一次就結束的專案。

## 重新對齊長什麼樣

重新對齊通常包含兩部分：prompt refinement，以及人類標註的驗證。

也就是把 rubric 的措辭修得更清楚，補上遺漏的邊界案例，再用新標註的資料重新計算一致度。

但如果對齊一直卡住，TPR 和 TNR 怎麼樣都拉不上來，那就不是再修一次措辭能解決的。

<!--image:2-->

這時候有三條路：

1. **換更強的模型**

   更大或更新的模型，通常比較能處理細緻、依賴上下文的錯誤。

2. **拆解 criterion**

   把一個複雜的 failure mode 拆成幾個更小、更原子的檢查，每個檢查配一個 judge。

   一次判斷太多事情，本來就會讓錯誤更難診斷。

3. **補充資料**

   補更多樣、品質更高的標註範例，尤其是邊界案例。

## 版本要綁在一起管

實務上最容易漏掉的一步：judge 版本要同時綁住 **rubric 版本**和**模型版本**。

<!--image:3-->

升級 judge 用的模型，等於換了一個 judge。舊的 TPR、TNR 不能直接搬到新模型上用，那些數字反映的是舊模型的行為，不是新模型的表現。

改 rubric 措辭也一樣，judge 已經變了。這兩個欄位只要動了一個，就重跑對齊，不要假設「只是小改」。

在 CI 或 dashboard 上，這幾個欄位都要和通過率一起顯示。

例如通過率從 0.87 掉到 0.72，第一件事是確認 judge 版本有沒有變，而不是立刻宣布 agent 退步。

## 新 failure mode 要進三個 split

production 出現新的 failure mode、整理成 examples 補進資料時，不能只放一個地方。

訓練、dev、test 三個 split 都要有這類案例。否則，驗證集看不到這個新問題，重新計算的 TPR、TNR 也就沒有涵蓋它。

<!--image:4-->

同時要守住上一篇那條線：放進 judge prompt 當 few-shot 的 trace，不能同時放在評估集裡。

如果兩邊重疊，TPR、TNR 可能會漂亮得像考前背過答案的學生，但那不代表 judge 真的學會判斷。

到這裡，judge 在時間軸上算是站得住了：偏誤有控制、label 有穩定度、版本追得回來。
