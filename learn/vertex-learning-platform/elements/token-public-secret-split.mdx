# Token Public/Secret Split：金鑰可見性分類

## Problem Statement

一個全端應用通常同時使用多個第三方服務——Clerk 管認證、Sanity 管內容、PostHog 管分析、OpenAI 管 AI 功能。每一個服務都發給你至少兩個金鑰：一個用來在瀏覽器端初始化 SDK 或發送事件（public / publishable key），另一個用來在 server 端存取完整 API 或管理資源（secret / private key）。問題是：這些金鑰在環境變數裡看起來很像（都是字串），但把它們放錯位置的後果天差地遠——把 secret key 暴露到瀏覽器端，相當於把你的資料庫門戶大開。你怎麼快速判斷哪個金鑰可以放 `NEXT_PUBLIC_`、哪個不行？

## Why it matters

AGENTS.md 的 traps 章節把所有環境變數分成兩類：client-safe 和 not client-safe。這不是建議，而是安全底線。在 AI 代理實作的場景下，這個分類尤其重要——AI 很容易選出一個「看起來合理但實際上錯誤」的替代方案，例如把 Sanity 的 read token 加上 `NEXT_PUBLIC_` 前綴以便在 client component 裡使用。Next.js 的 bundler 會把所有 `NEXT_PUBLIC_` 開頭的環境變數打包進 client bundle——這些值會出現在瀏覽器下載的 JavaScript 裡，任何人都能在 developer tools 裡看到。如果你的 Sanity read token 暴露了，你的私有資料集（包括未發佈的課程）就不隱私了。如果你的 OpenAI key 暴露了，任何人都能用它來呼叫 API，費用算你的。

## How it works

### 判斷原則

判斷一個金鑰是否 client-safe 的原則很簡單：**一個金鑰如果「只能做事、不能被拿來做別的事」，它就是 client-safe 的；一個金鑰如果「能做有副作用的操作」，它就絕對不能出現在瀏覽器端。**

具體來說：

| 金鑰類型 | Client-safe？ | 原因 |
|----------|--------------|------|
| Clerk publishable key | ✅ 是 | 只能初始化 Clerk SDK，不能讀寫資料 |
| PostHog public key | ✅ 是 | 只能發送追蹤事件，不能讀取分析資料 |
| Clerk secret key | ❌ 否 | 能管理使用者、存取 session、執行管理操作 |
| Sanity read token | ❌ 否 | 能讀取私有資料集的完整內容 |
| Sanity write token | ❌ 否 | 能建立、修改、刪除 Sanity 裡的文件 |
| OpenAI API key | ❌ 否 | 能呼叫 AI API，費用由金鑰持有者承擔 |
| PostHog private key | ❌ 否 | 能讀取分析資料、管理專案設定 |

### `NEXT_PUBLIC_` 前綴的機制

Next.js 的 bundler（webpack/Turbopack）在 build 時會：

1. **掃描所有 `process.env.NEXT_PUBLIC_*`**：把這些值硬編碼進 client bundle 的 JavaScript 裡。
2. **忽略所有非 `NEXT_PUBLIC_` 的環境變數**：這些值只在 server 端可用，不會出現在 client bundle 裡。

這意味著：**一個環境變數有沒有 `NEXT_PUBLIC_` 前綴，直接決定它會不會出現在瀏覽器端**。這不是一個配置選項，而是 Next.js 的架構邊界。

### Vertex 的環境變數分佈

| 環境變數 | 前綴 | 出現在 | 用途 |
|----------|------|--------|------|
| `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` | `NEXT_PUBLIC_` | Client bundle | 初始化 Clerk SDK |
| `CLERK_SECRET_KEY` | 無 | Server only | Clerk 管理操作 |
| `NEXT_PUBLIC_SANITY_PROJECT_ID` | `NEXT_PUBLIC_` | Client bundle | Sanity 專案識別（非敏感） |
| `SANITY_API_READ_TOKEN` | 無 | Server only | 讀取 Sanity 資料集 |
| `SANITY_API_WRITE_TOKEN` | 無 | Server only | 寫入 Sanity 資料集 |
| `NEXT_PUBLIC_POSTHOG_KEY` | `NEXT_PUBLIC_` | Client bundle | 初始化 PostHog SDK |
| `POSTHOG_PRIVATE_KEY` | 無 | Server only | PostHog 管理操作 |
| `OPENAI_API_KEY` | 無 | Server only | 呼叫 OpenAI API |

### `.env.example` 的角色

AGENTS.md 的 traps 章節建議：把所有環境變數列出在 `.env.example` 裡，並用註解標註哪些可以加 `NEXT_PUBLIC_`、哪些不行。這讓所有協作者（包括 AI 代理）在第一時間就知道規則，不需要猜測。

## In plain terms

想像你的錢包裡有兩種卡片：一張是「會員卡」（只能證明你是會員，不能領錢），另一張是「提款卡」（能領錢、能轉帳）。會員卡可以掛在鑰匙圈上讓別人看到（public key）；提款卡一定要鎖在保險箱裡（secret key）。`NEXT_PUBLIC_` 前綴就是「掛在鑰匙圈上」的動作——你不會把提款卡掛出去。

## Practical use

在 Vertex 專案中建立 token 安全分割：

1. **在 `.env.example` 裡列出所有環境變數**，並用註解標註：
   ```
   # Client-safe: 可加 NEXT_PUBLIC_
   NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=pk_test_xxx
   NEXT_PUBLIC_SANITY_PROJECT_ID=xxx
   NEXT_PUBLIC_POSTHOG_KEY=xxx
   
   # Server-only: 絕對不能加 NEXT_PUBLIC_
   CLERK_SECRET_KEY=sk_test_xxx
   SANITY_API_READ_TOKEN=sxxx
   SANITY_API_WRITE_TOKEN=sxxx
   POSTHOG_PRIVATE_KEY=xxx
   OPENAI_API_KEY=sk-xxx
   ```
2. **在 AI 代理的 prompt 中強調規則**：例如「Clerk secret key 只能在 server 端，不要加 NEXT_PUBLIC_ 前綴」。
3. **透過 `npm run build` 驗證**：Next.js 的 bundler 會在 build 時檢查 client bundle 裡有沒有不該出現的環境變數——如果有，build 會失敗。

## Questions

### Q1. 為什麼 Sanity 的 project ID 可以加 `NEXT_PUBLIC_` 前綴，但 read token 不行？
A1. Project ID 只是一個識別碼，用來告訴 Sanity SDK「你要連哪個專案」——它不包含任何存取權限，任何人都能看到你的 project ID（它在 Sanity 的 API URL 裡），所以暴露在瀏覽器端沒有安全風險。Read token 則包含了 API 存取權限——暴露了就等于把你的資料庫查詢權限交給任何人。

### Q2. 如果 AI 代理在實作時把 secret key 加上了 `NEXT_PUBLIC_` 前綴，Next.js 會怎麼反應？
A2. 在 development 模式下，Next.js 不會阻止你——app 可以正常運行，但 secret key 已經被打包進 client bundle，任何人都能在瀏覽器的 developer tools 裡看到。在 production build 時，Next.js 也不會自動阻止（它不知道哪些環境變數「應該」是 secret 的），所以這類錯誤通常要靠 code review 或安全掃描（如 CodeRabbit）來發現。這就是為什麼 AGENTS.md 把「不要把 secret key 加上 NEXT_PUBLIC_ 前綴」列為不可違反的規則——因為框架不會幫你擋。
