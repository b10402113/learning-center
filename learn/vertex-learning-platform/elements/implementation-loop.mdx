# 實作迴圈 (Implementation Loop)

## Problem Statement

當一個 AI 代理被要求「做一個功能」時，最常見的失敗不是能力不足，而是它默默自己決定要做什麼、寫下一大堆 code、最後才回報——等到人類發現方向錯了，成本已經付出。更深一層的問題是：人類是產品思考者（product thinker），AI 是實作代理（implementation agent），可是如果中間沒有一道閘門，AI 會在每一步實作裡代替人類重做產品與架構決策，而這些決策沒人審查過。規劃常常被當成拖延——一旦急著交付，第一個被犧牲的就是它——然而沒有經過批准的計劃就動手寫 code，反而是學習「產品本來該長什麼樣」最貴的方式。

## Why it matters

審批閘門（approval gate）正是讓 AI 寫出的 code 可信的關鍵。一個在 prompt 被批准之前就動工的 AI，可能選錯資料模型、洩漏密鑰、做出超出範圍的路由——這些錯誤在 prompt 階段只是幾行文字，改一下就修好；變成合併進去的 code 之後，修起來就貴得多。prompt 先於 code 的規則還迫使思考本身可以被檢視：每個假設、每個要動的檔案、每條驗收標準（acceptance criteria），都在一行 code 出現之前被寫下來。這把建置從「相信我」變成「先檢查這份計劃」。人類繼續當決策者，AI 繼續當執行者，整個循環變成一個可重複、可檢視的節奏：plan → review → approve → implement → test → fix → ship。

## How it works

這個迴圈有九步，而 code 只會在第六步之後出現：

1. 讀取操作手冊，載入角色、產品、邊界、已定決策與檢查清單。
2. 讀取手冊指定的技能與本地文件，而不是憑記憶猜測。
3. 檢視既有 code，讓計劃建立在現實上，而不是假設上。
4. 只有在請求真的含糊時，問一個聚焦的問題；不為問而問。
5. 在 `prompts/` 資料夾寫下實作 prompt（implementation prompt）：目標、讀過哪些技能、檢視了哪些 code、決策與假設、要動的檔案、需求、安全性考量、驗收標準、要跑的檢查、要做的手動測試。
6. 在寫任何 code 之前，詢問 Yes/No 的批准。
7. 嚴格照已批准的 prompt 實作——不加範圍、不出現驚喜功能。
8. 執行檢查並記錄真實輸出。
9. 用簡短報告收尾：What I did / Test / Needs your attention。細節留在 prompt 檔裡，不放進報告。

需要使用者裁量的決定，一律透過互動問答面板（interactive question panel）提出，絕不默默帶過。兩條硬規則撐住整個迴圈：除非被告知跳過，否則在 prompt 批准前不寫 code；以及絕不宣稱某個檢查通過——除非真的跑過它。

## In plain terms

把每個任務當成一張小合約。prompt 檔是合約條文，批准是簽名，code 是交貨，報告是收據。合約含糊，後面全部含糊——所以合約先寫。

## Analogy

像外科手術：手術前先有一份團隊共同審閱的書面計劃，才下第一刀。計劃不是延誤，是安全裝置。一個在決定菜單前就開始切菜的廚師，最後只會得到一冰箱互不匹配的食材——菜單是計劃，prompt 是備料清單，而批准是「知道客人真正想要什麼的人」按下開始的信號。

## Practical use

在一個真實功能開發裡，這個迴圈呈現為緊湊的節奏。人類說「在搜尋結果頁加一個排序控制」。代理讀取手冊、讀取搜尋行為那一節、打開搜尋路由與結果頁元件，發現一個真正的含糊點——預設排序該是最相關還是最新？——於是透過問答面板問這一個問題。它寫下 `prompts/add-sort-control.md`，內容含目標、被檢視的檔案、決策（預設＝最相關）、要動的檔案、驗收標準（排序控制正常顯示、計數保持正確）、以及檢查（type check、lint、build）。人類批准。代理只實作 prompt 寫到的部分，跑完檢查，最後用三條短句收尾：What I did、Test（確切的步驟）、Needs your attention（預設排序這個決定）。一個本會造成整段重寫的錯誤假設，在 prompt 裡只是一行的修改。

## Questions

### Q1. 為什麼「先寫實作 prompt 並取得批准」比「先寫 code」更省成本？
A1. 因為錯誤在 prompt 階段只是文字，改一行就修好；等寫成 code 才發現產品或架構假設錯了，就要整段重寫或反覆返工。審批閘門讓每個假設、每個檔案、每條驗收標準都在寫 code 之前被檢查過。

### Q2. 關係題：九步 loop 的第七步「嚴格照 prompt 實作」與「範圍邊界」有什麼關係？
A2. 第七步要求只實作已核准 prompt 裡列出的內容，不自己加功能、不超範圍發揮——這正是範圍邊界（build only what is listed）在工作流層面的執行方式，兩者互為表裡。

### Q3. 價值判斷題：如果 AI 回報「檢查通過」但其實沒有執行檢查，它違反了哪一條原則？為什麼這比一個功能錯誤更嚴重？
A3. 它違反了「沒有實際執行就不得宣稱檢查通過」的原則。功能錯誤可以被後續測試抓到；謊報檢查結果會摧毀「檢查＝當責契約」的信任基礎，讓人再也無法判斷哪些部分是真正可靠的。
