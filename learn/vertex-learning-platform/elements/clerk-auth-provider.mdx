# Clerk：託管認證服務

## Problem Statement

認證（authentication）是全端應用最複雜的子系統之一——你必須處理 session 管理、密碼流程、OAuth 第三方登入、Email 驗證、JWT 簽發與驗證、middleware 整合、路由保護、使用者檔案管理，以及未來的帳單系統。自己從零實作這些功能是很好的學習練習，但對一個要上線的產品來說，這代表數週的基礎設施工作，而且每一個環節都有安全邊界案例（security edge cases）需要處理。問題是：如果你花三週寫認證系統，你的學習平台就晚了三週上線——而認證系統本身並不是你的產品。

## Why it matters

Clerk 把上述整個 surface area 打包成一套託管服務：你透過 CLI 接入 Next.js，它幫你搞定 session、密碼流程、OAuth、Email 驗證、middleware、路由重導向和使用者檔案。免費方案支援最多 50,000 月活用戶，對原型和早期產品綽綽有餘。更關鍵的是，Clerk 的身份系統（identity）可以串接後續的功能——例如用 Clerk user id 作為學習進度（progress）的 key，或者接入帳單（billing）。選擇 Clerk 的核心邏輯是：**auth 是一個巨大的 surface area，把時間花在產品上而不是認證基礎設施上**。

## How it works

### 安裝流程

Clerk 的接入只需要幾個步驟：

1. **建立 Clerk 應用**：在 Clerk Dashboard 建立新應用（Vertex 的命名以 `JSM` 開頭），啟用 email 和 Google 兩種 provider。
2. **安裝 CLI**：透過 `npx` 安裝 Clerk 的 Next.js 整合。
3. **執行 `clerk oauth login`**：完成 OAuth 認證，把 Clerk 應用與你的開發環境串接。
4. **自動產生檔案**：Clerk CLI 自動生成以下內容：
   - 相依套件（`@clerk/nextjs`）
   - 環境變數（publishable key 和 secret key）
   - Proxy middleware（Next.js 16 的 middleware 重命名）
   - 包含 `ClerkProvider` 的 layout
   - Sign-in 和 sign-up 路由
   - Header 上的使用者按鈕（user button）
5. **執行 `clerk doctor`**：診斷安裝是否正確，確認環境變數和 middleware 設定無誤。

### 產生的檔案結構

| 檔案/設定 | 作用 |
|-----------|------|
| `@clerk/nextjs` | Clerk 的 Next.js SDK，提供 hooks 和元件 |
| 環境變數 | `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`（client-safe）和 `CLERK_SECRET_KEY`（server-only） |
| Proxy middleware | 讀取 session cookie、驗證 JWT、在 token 缺失/過期時執行 handshake |
| Layout + ClerkProvider | 在整個 app 外層包裹 Clerk 的 context |
| `/sign-in`、`/sign-up` 路由 | 預建的認證頁面 |
| Header user button | 顯示使用者頭像和登出選項 |

### 為什麼選 Clerk 而不是自己做

| 選項 | 優點 | 缺點 |
|------|------|------|
| 自己做認證 | 學習價值高，完全掌控 | 數週工作量、安全邊界案例多、維護成本高 |
| Clerk 託管服務 | 幾分鐘接入、免費 50K 月活、內建 OAuth/Email/Session | 依賴第三方、自訂彈性有限 |

核心判斷：**如果你在建產品而不是在學認證，用 Clerk 把時間還給產品本身**。如果目標是學習，自己做一次是值得的——但做完之後回到產品時，還是用託管服務。

## In plain terms

想像你在蓋一棟房子。認證系統就是門鎖、保全系統、鑰匙管理——你當然可以自己做，但你更想把時間花在室內設計和裝潢（你的產品功能）上。Clerk 就像一個專業的保全公司，幫你安裝好所有門禁系統，你只需要告訴它「哪些房間需要鑰匙、哪些可以自由進出」。

## Practical use

在 Vertex 專案中：

1. **建立 Clerk 應用**：命名以 `JSM` 開頭，啟用 email + Google provider。
2. **透過 CLI 接入**：Clerk 自動修改 Next.js 專案，加入 middleware、routes 和元件。
3. **執行 `clerk doctor`**：確認安裝正確。
4. **驗證 sign-in/up 頁面**：瀏覽器開啟 `/sign-in` 和 `/sign-up` 確認可用。
5. **理解生成的檔案**：要求 AI 代理解釋每一個生成或修改的檔案——middleware 做了什麼、route 怎麼運作、UI 元件怎麼接——保持對生成代碼的掌控。

## Questions

### Q1. 為什麼 Clerk 免費方案的 50,000 月活用戶對原型產品來說綽綽有餘？
A1. 原型或早期產品的用戶量通常在數百到數千之間，50,000 月活代表你可以讓產品上線、收集真實回饋，而不需要在用戶量成長到那個規模之前支付任何費用。這也是為什麼 Clerk 被認為是「免費開始」的工具之一。

### Q2. 為什麼要在接入 Clerk 之後要求 AI 代理解釋每一個生成的檔案？
A2. 因為 AI 生成的代碼「能跑」不代表你理解它。如果你不知道 middleware 在做什麼、route 怎麼保護頁面、環境變數怎麼分配，你就無法判斷 AI 是否做出了錯誤的決定（例如把 secret key 暴露到瀏覽器端）。解釋檔案是保持對 AI 生成代碼掌控的關鍵習慣。
