# Auth Middleware Resolver：解析不阻擋

## Problem Statement

大多數開發者第一次聽到「middleware 保護路由」時，會直覺認為 middleware 是一個閘門——使用者走到門口，middleware 檢查鑰匙，有鑰匙才放行，沒鑰匙就擋住。但在 Next.js 16 的架構下（Clerk 的 middleware 透過 proxy 實作），這個心智模型是錯的。如果 middleware 是閘門，那為什麼 Vertex 的首頁是公開的、任何人都能瀏覽？為什麼 Clerk middleware 接入之後，你的網站並沒有變成「必須登入才能看」？這個矛盾的解答是：**middleware 是 auth resolver，不是 auth gate**。它解析（resolve）認證狀態，但不阻擋（block）路由。

## Why it matters

理解 resolver vs gate 的區別，直接決定你怎麼設計路由保護策略。如果 middleware 是 gate，那所有路由預設都是受保護的，你必須逐一開放——這在一個以內容消費為主的學習平台（首頁、課程總覽、課程頁都是公開的）完全不合理。但如果 middleware 是 resolver，那所有路由預設都是公開的，你只在需要保護的路由上標記保護——這才是 Vertex 需要的模式：瀏覽是公開的，只有「我的學習」或「學習進度」這類功能需要登入。

AGENTS.md 裡的 app structure 章節明確指出：「browsing stays public per AGENTS.md, and routes are gated only when a feature marks them protected」。這不是一個偏好，而是架構決策——如果你把 middleware 當成 gate，你的 AI 代理可能會把所有頁面都設成 protected，導致學習者連課程都看不到。

## How it works

### Middleware 的真實行為

當一個 HTTP 請求到達 Next.js 時，middleware（在 Next.js 16 裡稱為 proxy）的執行流程是：

1. **讀取 session cookie**：從瀏覽器傳來的 cookie 中取出 Clerk 的 session token。
2. **驗證 JWT**：檢查 token 是否有效（未過期、簽章正確、屬於同一個 Clerk 應用）。
3. **執行 handshake**：如果 token 缺失、過期、或來自不同實例（instance），Clerk 會自動執行一次 handshake——重新驗證使用者身份。
4. **附加 auth state**：把解析後的認證狀態（`auth()` 回傳值）附加到請求物件上，讓後續的 server component 或 route handler 可以使用。

**關鍵：middleware 不會在任何路由上回傳 401 或 302。** 它只是把認證狀態「解析」出來，附加到請求上。真正決定「這個頁面要不要擋」的，是頁面本身或它的 layout。

### Next.js 16 的 proxy 重命名

Next.js 16 把 `middleware.ts` 重新命名為 `proxy.ts`。這不是功能改變，而是語義更準確——因為 middleware 在 Next.js 裡做的不是「攔截並修改請求」（傳統 middleware 的定義），而是「解析認證狀態並附加到請求」（proxy 的語義）。Clerk 的文件和 CLI 已經跟上了這個命名。

### 什麼時候才需要保護路由？

在 resolver 模式下，路由保護是**顯式的**——你必須在特定路由上標記「這裡需要登入」。在 Next.js + Clerk 的實作中，這通常透過以下方式達成：

1. **在 layout 或 page 中檢查 `auth()`**：如果回傳的 `userId` 是 null，重導向到 `/sign-in`。
2. **使用 Clerk 的 `Protect` 元件**：包住需要登入的區塊，未登入時顯示替代內容或重導向。
3. **在 server route 中檢查**：例如 `/api/progress` route 在寫入學習進度前先驗證 Clerk session。

### Vertex 的路由保護策略

| 路由 | 保護狀態 | 原因 |
|------|----------|------|
| `/`（首頁） | 公開 | 學習者的第一印象，不該被擋 |
| `/courses`（課程總覽） | 公開 | 內容消費是核心，不該強制登入 |
| `/courses/[slug]`（課程詳情） | 公開 | 課程頁是銷售/展示頁面 |
| `/courses/[slug]/[lesson]`（課程頁） | 公開（影片播放） | 內容是公開的，進度追蹤才需要登入 |
| `/my-learning`（我的學習） | 需要登入 | 個人化頁面，需要知道「你是誰」 |
| `/api/progress`（進度 API） | 需要登入 | 寫入操作必須驗證身份 |

這個策略的邏輯是：**消費公開，管理登入**。大多數頁面是公開的，只有涉及使用者個人狀態的操作才需要認證。

## In plain terms

把 middleware 想像成一個飯店的接待處。每個客人走進來，接待處會幫你登記「你是誰」（解析身份），但不會擋你——你可以在大廳走來走去（瀏覽公開頁面）。只有當你走到「住客專屬區域」（受保護頁面）時，門口的保全才會檢查你的房卡。接待處（resolver）做的事情是「登記並發卡」，不是「擋住所有門」。

## Practical use

在 Vertex 專案中落實 resolver 模式：

1. **安裝 Clerk middleware（proxy）**：CLI 自動產生，不需要手寫。
2. **不要在 middleware 裡加保護邏輯**：middleware 只負責解析認證狀態，不負責阻擋。
3. **在需要保護的頁面上檢查 `auth()`**：例如在 `/my-learning` 的 server component 裡呼叫 `auth()`，如果沒有 `userId` 就重導向。
4. **在需要保護的 API route 上檢查**：例如 `/api/progress` 的 route handler 先呼叫 `auth()`，未登入就回傳 401。
5. **驗證**：確保首頁和課程頁在未登入狀態下仍可正常瀏覽。

## Questions

### Q1. 為什麼 middleware 不直接回傳 401 或 302，而要讓頁面自己決定要不要擋？
A1. 因為不同的頁面有不同的保護需求。首頁、課程總覽、課程詳情都是公開的，只有「我的學習」和進度 API 需要登入。如果 middleware 直接擋，你要嘛全部放行（那受保護頁面就裸奔了），要嘛全部攔截（那公開頁面就看不到了）。讓頁面自己決定，才能做到「精準保護」。

### Q2. Next.js 16 把 middleware 重命名為 proxy，這對 Clerk 的整合有什麼影響？
A2. 功能上沒有影響——都是同一個 server-side function，在路由處理之前執行。差別在語義：proxy 更準確地描述了它的行為（解析認證狀態並附加到請求），而不是傳統 middleware 的語義（攔截並修改請求）。Clerk 的 CLI 已經跟上了這個命名變化。
