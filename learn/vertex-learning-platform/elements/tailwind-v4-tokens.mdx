## Problem Statement

設計稿上有一套完整的色彩、字級、間距系統，但程式碼裡沒有對應的值。每個元件實作時各自去「猜」顏色——button 用 `bg-blue-500`、card 用 `bg-blue-600`、badge 又冒出 `bg-indigo-400`。它們看起來都是「藍色系」，但沒有任何機制確保它們是同一個藍。更糟的是間距：一個元件用 `p-4`、另一個用 `p-5`、第三個用 `p-6`，這些 magic number 之間沒有統一的 scale，改一個地方就要全專案 grep。問題不在於 Tailwind 不夠好用，而在於 Tailwind 預設值沒有被替換成你的設計語言——你的品牌色、你的字級比例、你的圓角規則。沒有 token 層，設計系統就只停留在文件裡，無法被程式碼直接引用。

## Why it matters

Theme tokens 是設計系統從文件變成可執行規格的橋樑。設計師定義 `primary: #2563EB`，這行 CSS 變數被寫進 `globals.css`，之後每一個元件都引用同一個 token——改一個值，整個應用程式的主色瞬間統一更新。這不是便利，這是唯一可靠的跨頁一致性策略。Tailwind v4 的 `@theme` 指令讓你直接在 CSS 裡宣告 token，不需要 JavaScript config 檔案，也不需要 `tailwind.config.js` 裡的 `theme.extend`。token 是 CSS-native 的，瀏覽器直接解析，構建工具直接處理，AI 也只需要讀一個檔案就知道所有設計值。

## How it works

Tailwind v4 引入了 `@theme` 指令，讓你在 CSS 檔案裡直接定義主題變數。這些變數被 Tailwind 的 utility system 自動消費，例如你定義了 `--color-primary: #2563EB`，就能直接使用 `bg-primary`、`text-primary`、`border-primary` 等 class。

在 Vertex 專案中，token 被集中在 `globals.css` 裡定義，涵蓋以下幾個類別：

- **色彩系統**：品牌色（primary）、中性色（neutral）、語義色（success / warning / error），每個色階有明確的 CSS 變數名，例如 `--color-primary: #2563EB`、`--color-surface: #FFFFFF`。AI 在實作元件時，只能從這些已宣告的色彩中選擇，不能自行定義新色。
- **Typography scale**：heading 和 body 的字級大小、粗細、行高，被定義成 token 組合。例如 `--font-size-h1`、`--line-height-h1`，確保每一級 heading 在所有頁面保持一致的比例。
- **間距系統**：統一的 spacing scale，例如 `--spacing-1` 到 `--spacing-12`，對應固定的像素值。元件的 padding、margin、gap 全部從這個 scale 取值，消除 magic number。
- **Border-radius 與 Shadows**：按鈕的圓角、卡片的陰影、輸入框的 border，各自對應一個 token。例如 `--radius-md`、`--shadow-card`，元件引用時不需要記住具體數值。
- **字型引入**：字型在 `layout.tsx` 裡透過 Next.js 的 `next/font` 機制載入，然後在 CSS 變數中橋接——layout 設定 `className`，`globals.css` 把 font-family 對應到 token，讓 Tailwind 的 `font-sans`、`font-serif` 自動指向正確的字型。

為什麼 Tailwind v4 比舊版更適合做 token 層：舊版的 `tailwind.config.js` 是 JavaScript 檔案，token 定義和 CSS 之間有一層翻譯。v4 的 `@theme` 直接在 CSS 裡宣告，token 就是 CSS 變數，不需要轉譯，構建更快，也更容易從設計稿中批量提取。設計稿被解析後，色彩和間距值直接對應到 `@theme` 區塊裡的變數，AI 不需要「判斷」該用什麼顏色，只需要照著 token 表複製。

## In plain terms

Theme tokens 就像油漆色卡上的編號。裝潢師傅（AI）拿到色卡後，不需自己調色——牆壁用 `#001` 號色、門框用 `#003` 號色、天花板用 `#005` 號色，每個號碼對應精確的顏色配方。如果屋主想把全屋從藍色改成綠色，不需要重新粉刷每一面牆，只需要把 `#001` 的配方從藍色改成綠色，所有引用它的牆壁自動更新。沒有色卡時，師傅每次粉刷都靠肉眼「差不多」地調色，結果每面牆的藍都微妙地不一樣。

## Practical use

在 Vertex 專案中，theme tokens 的落地流程很具體：

1. AI 讀取設計稿圖片，從中提取色彩、字級、間距、圓角等具體數值。
2. 這些數值被寫進 `globals.css` 的 `@theme` 區塊，成為 CSS 變數——例如 `--color-primary`、`--spacing-md`、`--radius-lg`。
3. `layout.tsx` 透過 `next/font` 載入字型，設定為 `className`，橋接到 CSS 變數——讓 Tailwind 的 `font-sans` 等 utility 自動指向正確字型。
4. 後續每一個功能頁面（首頁、課程頁、搜尋頁）都直接引用同一份 `globals.css` 裡的 token，不需要在各自的元件裡重新定義顏色或間距。
5. 當設計調整時，只需修改 `globals.css` 中對應的 token 值，所有使用該 token 的元件同步更新——不需要逐頁 grep 和替換。

這就是為什麼 AGENTS.md 裡的規則能運作：AI 被要求「reproduce the design exactly」，而 theme tokens 提供了精確的值——它不需要「判斷」該用什麼藍色，只需要查 token 表然後照抄。

## Questions

### Q1. Tailwind v4 的 `@theme` 指令和舊版 `tailwind.config.js` 的 `theme.extend` 有什麼差別？為什麼 Vertex 選擇 v4？
A1. 舊版把 token 定義在 JavaScript 檔案裡，需要經過 Tailwind 的構建流程轉譯成 CSS 變數，多了一層抽象。v4 的 `@theme` 直接在 CSS 裡宣告，token 就是原生 CSS 變數，瀏覽器和構建工具直接解析，不需要轉譯。對 Vertex 來說，這意味著 AI 讀一個 `globals.css` 就能拿到所有設計值，不需要同時理解 JS config 和 CSS 之間的對應關係。

### Q2. 如果設計師把品牌色從 `#2563EB` 改成 `#3B82F6`，在有 theme tokens 的專案裡需要改什麼？
A2. 只需要修改 `globals.css` 中 `--color-primary` 的值——從 `#2563EB` 改成 `#3B82F6`。所有引用 `bg-primary`、`text-primary`、`border-primary` 的元件會在下次構建時自動更新。不需要逐頁搜尋替換，也不需要打開任何元件檔案。這就是 token 的單一真實來源（single source of truth）原則。

### Q3. 為什麼 theme tokens 放在 `globals.css` 而不是各元件自己的 CSS 檔案裡？
A3. 放在 `globals.css` 保證所有頁面和元件從同一份 token 檔案讀取設計值，實現 single source of truth。如果每個元件各自定義 token，就會回到「每面牆自己調色」的問題——改品牌色時需要找到每一個元件逐一修改，而且很容易遺漏。`globals.css` 是全域的，AI 在實作任何 UI 前只需要讀這一個檔案，就能拿到全部設計約束。
