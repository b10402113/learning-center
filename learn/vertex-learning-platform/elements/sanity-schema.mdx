# Sanity Schema-Driven 架構

## Problem Statement

建一個全端應用時，內容管理（admin dashboard）通常是最花時間的部分之一——你要自己設計資料表、寫 CRUD API、做後台介面、處理權限。Sanity 的做法完全不同：你定義 schema（內容結構），Sanity 自動幫你生出一個即時運作的 Studio（admin dashboard），作者可以直接在裡面建立、編輯、協作內容。問題在於：如果你把 Sanity 當成一個「通用 CMS」來用，而不去理解 schema-driven 的思維，你就無法設計出正確的資料模型——course 該有哪些欄位、module 該不該分開存、lesson 的影片 URL 該放哪——這些決定會連鎖影響搜尋、頁面、和整條產品線。

## Why it matters

Sanity 是 Vertex 的內容骨幹（content backbone），它做的工作比任何其他工具都多。schema 是整條資料管線的起點：schema 定義錯了，之後的目錄頁、課程頁、搜尋、影片深層連結全部跟著錯。更重要的是，Sanity 的 schema 不只是「資料庫結構」——它同時決定了 Studio 的介面長什麼樣、哪些欄位可以編輯、哪些關聯可以用拖拉來建立。一個設計良好的 schema 讓非技術的內容作者也能正確地建立內容，一個設計不良的 schema 則會讓作者困惑、讓 AI 在搜尋時拿到錯誤的關聯。

## How it works

Sanity 的架構有三個核心概念：

**1. Schema 定義內容結構**

每個 schema 是一個 TypeScript 檔案，定義一種文件型別（document type）的欄位、關聯、驗證規則。例如 `course.ts` 會定義 title（string）、slug（slug）、description（text）、modules（array of embedded objects）、instructors（array of references）等。

Schema 決定了三件事：
- Studio 裡會出現什麼表單（欄位順序、欄位型別、欄位驗證）
- API 回傳什麼結構（GROQ 查詢的結果形狀）
- 哪些關聯可以被建立（reference vs embedded 的差別在這裡生效）

**2. Structure 決定 Studio 介面**

`sanity.config.ts` 裡的 `structure` 欄位定義了 Studio 左側導覽列的樣子。你可以把常用的文件型別（courses, lessons, instructors）放在最上面，把設定類的文件（categories）放在下面。Structure 不影響資料模型，但它影響作者的工作流——好的 structure 讓作者找得到東西，壞的 structure 讓 Studio 變成迷宮。

**3. 安全規則控制存取**

Sanity 的 `sanity.config.ts` 裡可以定義 role-based 的存取規則：哪些角色可以建立文件、哪些只能編輯特定欄位、哪些欄位對外觀者唯讀。這在多作者協作的場景下特別重要——你不會希望有人不小心刪掉了整門課程。

## In plain terms

Sanity 的 schema 就像餐廳的菜單模板。你定義「主菜有什麼欄位（品名、價格、辣度、過敏原）」，後廚（Studio）就自動知道怎麼排菜單、怎麼讓服務生填寫、怎麼在結帳時正確計價。你不需要自己去刻菜單頁面、寫計價邏輯、做權限管理——這些都由模板（schema）驅動。

## Practical use

在 Vertex 專案中，Sanity schema 的建立流程很具體：

1. **CLI 初始化**：`npx sanity@latest init` 選擇 TypeScript、要不要 embedded studio、dataset 設定。完成後會自動產生 `sanity.config.ts`（主設定）、`sanity.cli.ts`（CLI 工具）、以及 `sanity/` 資料夾。
2. **定義 schema**：在 `sanity/schemas/` 裡為每種內容型別建立 TypeScript 檔案，例如 `course.ts`、`lesson.ts`、`instructor.ts`。
3. **在 structure 裡排列**：在 `sanity/structure.ts` 裡把 schema 排成 Studio 的導覽列。
4. **測試**：`cd studio && npm run dev`，在 localhost:3333 看到 Studio 介面，建立一筆測試資料確認欄位正確。
5. **接上 GROQ**：在 web 端用 Sanity client 查詢 schema 裡的資料，確認結構符合預期。

## Questions

### Q1. Sanity 的 schema 和傳統資料庫的 migration 有什麼不同？
A1. 傳統資料庫需要手寫 migration script（ALTER TABLE 等），每次改 schema 都有 downtime 風險。Sanity 的 schema 是宣告式的——你改了 TypeScript 檔案，Studio 和 API 自動反映新結構，不需要 migration。對 AI 來說，schema 是一個可讀的 TypeScript 檔案，AI 可以讀懂、修改、驗證，不需要理解 SQL migration 的狀態管理。

### Q2. 為什麼 schema-driven 的 admin dashboard 比手寫後台更好？
A2. 三個原因：（1）作者介面自動生成——不需要另外花時間做 CRUD 表單；（2）欄位驗證在 schema 裡定義——作者填錯資料時會即時提示；（3）關聯（reference）可以用拖拉建立——作者不需要知道 ID 或外鍵的概念，只要從下拉選單裡選講師就好。

### Q3. 如果 schema 設計錯了，在 Vertex 裡會影響哪些下游功能？
A3. 至少會影響四個地方：（1）目錄頁（/courses）需要的 aggregate 數據（總時數、課程數）會算錯；（2）課程詳情頁的模組展開、學習成果列表會缺少欄位或格式錯誤；（3）搜尋結果的 grounding 會拿到錯誤的關聯（例如 lesson 的課程名稱是空的）；（4）影片深層連結（deep-link）會找不到對應的 lesson，因為影片 URL 和 lesson 的關聯斷了。
