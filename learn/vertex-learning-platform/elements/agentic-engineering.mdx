# 代理式工程 (Agentic Engineering)

## Problem Statement

讓 AI 寫程式最省事的做法，是把需求丟給 AI，然後不斷修正提示詞（prompt）直到它能跑——這種「prompt 到能用」的方式做 demo 綽綽有餘，但一旦規模變大，就會在三個地方崩潰：擴展性（scalability）、安全性（security）與理解（understanding）。

崩潰的根源在於：一個薄弱的起始提示詞（weak starting prompt）給了 AI 太多的自由。AI 沒有產品的脈絡，於是自行發明資料模型（data model）與搜尋方式（search）——結果全都錯；沒有安全邊界，於是把密鑰（secrets）暴露到瀏覽器；沒有範圍定義，於是寫出超出任務範圍的路由（routes）。問題不是「AI 不夠強」，而是「人沒有先給它一個可以安全運作的系統」。代理式工程（Agentic Engineering）要解決的，正是這個「盲目 prompt」的盲點。

## Why it matters

因為當 AI 接手的是整個生產級應用時，「先試試看、壞了再修」的代價從幾分鐘變成幾週，而且可能修不回安全的狀態。AI 很擅長在沒有約束時挑出一個看起來合理、實際上錯誤的答案：資料模型錯，目錄（catalog）、課程頁、搜尋全部跟著亂；搜尋行為錯，使用者在結果頁找不到該去的精確時刻；密鑰外洩，等發現時已經在上線環境。在 AI 輔助的建置裡，**人依然是工程師**——人負責產品思考與架構決策，AI 只是讓執行變快。這個角色分工（role split）一旦模糊，等於把產品與架構的決定權交給一個沒有產品理解的執行者，專案越大，風險越失控。

## How it works

核心機制是把「AI 寫程式」從單次的盲目對話，改造成一套**先給系統、再放 AI 執行**的工作流。做法不是依賴更長的 prompt，而是給 AI 三樣東西：

1. **上下文檔案（context files）**——把「這個專案是什麼」寫成文件，例如 AGENTS.md：產品是什麼、技術棧、邊界、規則、工作流程。AI 每次動手前讀它，就不必猜。
2. **工具知識（skills）**——把「工具怎麼用」做成技能：AI 在實作某個功能前先讀對應的工具說明，不依賴過時的訓練資料。
3. **批准閘門（approval gates）**——AI 不得直接改 code：先讀檔案、研究程式碼、寫出實作計畫，等人工批准之後才動手。

把這三樣組合起來，就是一個「強健的起始提示詞」：它先給系統——產品、技術棧、邊界、規則、工作流程——而不是一個開放的問題。人保持在「產品思考者（product thinker）／架構師」的位置，AI 降級為「實作代理（implementation agent）」，且**絕不交出控制權**。

其中 AGENTS.md 是整個系統的載體：一份寫給 AI 代理（AI agent）看的操作手冊（operating manual），不是寫給使用者看的 README。它說明這個專案是什麼、要怎麼工作、哪些事絕對不能做、何時該請求批准、如何回報。它的完整章節構造屬於另一課，這裡只需記住：它把「系統優先」的抽象原則編碼成一份 AI 每次都會讀到的文件。

## In plain terms

以前是「一句話丟給 AI，看它亂做出來，再不斷罵它改到對」；現在是「先寫一本操作手冊，把要做的事、不能做的事、要遵守的規則都寫清楚，再放手讓 AI 照著做，每動一步都要你蓋章」。

## Analogy

像交給新人一份工作：你當然可以只說「把這個功能做出來」，然後看他自由發揮、做出來再修——但更穩的是先給一份作業手冊：專案是什麼、哪些地方不能碰、照什麼步驟做、動關鍵東西前先來問你。你不會因此無所事事，你依然是那個想清楚「這個功能為什麼存在、要長什麼樣」的人。

## Practical use

在 Vertex 學習平台的建置中，這套工作流從頭貫穿到尾。動手前的第一步不是選技術棧，而是先定義產品：誰創造內容、誰消費內容、哪些公開、哪些要登入、哪些必須留在伺服器端——答案出來後，技術棧自己浮現。接著寫下 AGENTS.md：說明這個 AI 扮演「principal 級全端工程師、負責建 Vertex」的角色；說明產品是「作者在 Sanity 建課程、學習者在 Next.js 網站用自然語言搜尋並跳轉到精確講解時刻」；規定怎麼工作——**絕不直接跳進 code**，要先讀檔案與技能、研究程式碼、提出聚焦的問題、寫實作 prompt、在寫 code 前請求批准；列出「never-do 規則」，例如不得把私有 token 放進瀏覽器。工具知識則交給技能（例如 Sanity 的 agent toolkit、Clerk 的 skills），AGENTS.md 只放專案規則，兩者分工，各自不會過時。最後，每項功能都透過 pull request 上線，由 CodeRabbit 這類 AI 審查在合併前掃描漏洞與洩漏的密鑰——人批准、AI 實作、工具把關，三層各司其職。

## Questions

### Q1. 為什麼「prompt 到能用」在 demo 階段可以，在生產級應用上卻會崩塌？請舉出至少兩個具體崩壞的面向。
A1. 因為 demo 規模小、沒有真實資料、沒有安全要求，壞了重來成本低；而生產級應用同時面對擴展性、安全性與理解三種壓力。具體例如：AI 沒有產品脈絡，自訂了錯誤的資料模型與搜尋方式，導致目錄、課程頁與搜尋全亂；沒有安全邊界，把密鑰暴露到瀏覽器；沒有範圍定義，寫出超出任務範圍的路由。

### Q2. 代理式工程把角色分工（role split）放在什麼位置？「人」與「AI」各自負責什麼？
A2. 分工是這套工作流的基石：人保持產品思考者與架構師的角色，負責定義產品、技術棧、邊界、規則與工作流程；AI 是實作代理，只在人給定的系統內執行。人絕不交出控制權——AI 可以信任，但每個關鍵動作都要經人批准與核驗。

### Q3. 關係題：AGENTS.md、技能（skills）與批准閘門（approval gates）在「系統優先」這個原則下各自扮演什麼角色？為什麼三者缺一不可？
A3. AGENTS.md 是系統的載體，把專案的產品、邊界與規則寫成 AI 每次都會讀的操作手冊；技能補充工具知識，避免 AI 依賴過時資料或亂猜 API；批准閘門保證 AI 在寫 code 前先提出實作計畫、經人確認才動手。三者缺一不可：只有手冊沒有技能，AI 不知道工具怎麼用；只有技能沒有手冊，AI 不知道專案是什麼；沒有批准閘門，即使有手冊，AI 仍可能跳過計畫直接動手。
