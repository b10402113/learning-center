# AGENTS.md 操作手冊

## Problem Statement

在 AI 輔助的專案裡，有一種看似省力的做法：隨便給 AI 一個提示詞，讓它自由發揮，做完再修。這種方式在 demo 階段或許夠用，但一碰到生產級應用——需要真實資料、安全邊界、多人協作——就開始崩潰。崩潰的原因不是 AI 不夠聰明，而是**它沒有拿到一份明確的系統說明**。

AI 沒有產品的脈絡，會自行發明資料模型（data model）——模組（module）該嵌入還是獨立、影片該怎麼切片、課程的關係該怎麼連結——全部猜錯；沒有安全邊界，把伺服器端才該持有的密鑰（secrets）暴露到瀏覽器；沒有工作流程，跳過規劃直接動手，做完才發現方向全錯。問題的根源在於：專案裡沒有一份「寫給 AI 看的操作手冊」，告訴它這個專案是什麼、要怎麼運作、哪些事絕對不能做。AGENTS.md 正是為了解決這個缺口而存在的核心文件。

## Why it matters

AGENTS.md 是 AI 輔助開發中**最重要的一份檔案**——它是專案的操作手冊（operating manual），是 AI 在每次實作前都會讀取的規則與系統說明。沒有它，AI 每次都從零開始猜測，猜對了是運氣，猜錯了要花數倍時間修正；有了它，AI 在一個明確的系統內執行，人保持產品思考者（product thinker）的角色，AI 降級為實作代理（implementation agent），且**絕不交出控制權**。

這份文件的重要性來自一個現實：AI 在沒有約束時，會挑出一個「看起來合理、實際上錯誤」的答案。它會把聊天介面當成搜尋的出口（實際上應該是完整的結果頁面），會把語義搜尋（semantic search）當成預設啟用（實際上可能需要降回關鍵字比對），會把整份逐字稿塞進一個欄位（實際上應該切成有時間戳記的短片段）。這些都不是「AI 不夠好」，而是「人沒有先把規則寫清楚」。AGENTS.md 把每一項這樣的決定都寫下來，讓 AI 不必猜、也不該猜。

## How it works

AGENTS.md 是一份**以專案為中心向外撰寫**的文件，包含十五個章節，每章解決一類 AI 不該自行決定的問題。它不是 README，不是寫給使用者看的說明書；它唯一的讀者是 AI 代理（AI agent），作用是讓 AI 在一個安全的系統內運作。

**第一組章節：角色與產品定義。** 文件首先定義 AI 的角色——「你是 principal 級的全端工程師，負責建置 Vertex」——然後用白話文描述產品本身：作者在 Sanity 管理中心建立課程，學習者在 Next.js 網站上用自然語言搜尋並跳轉到精確的講解時刻。產品描述的深度有一個判斷標準：**如果你寫不出這段產品說明，你還沒準備好開始建置。**

**第二組章節：工作流程。** 這裡規定了 AI 的九步迴圈（nine-step loop）：先讀 AGENTS.md 與相關技能（skills），再讀現有程式碼，提出一個聚焦的問題（僅在真正有歧義時），寫出實作計畫（implementation prompt），在動手寫 code 前取得人工批准，嚴格按照計畫實作，跑完檢查，最後以短報告回報。這不是建議，而是規則——**在 prompt 獲得批准前，絕不寫 code。**

**第三組章節：邊界與規則。** UI 規定 AI 不做設計、只複製提供的設計稿；技術棧明確列出該用什麼（Next.js、Clerk、PostHog、Sanity、Tailwind）以及**絕對不用什麼**（不用 `@sanity/context` plugin 當它落後 Sanity 大版本時、不用 `text::semanticSimilarity()` 除非嵌入已啟用、不嵌入 Studio、不把 dataset 設為公開、不用 client-side token、不用獨立後端框架）。App 結構章節定義了 server/client 的安全邊界：瀏覽器永遠不持有私有 token、永遠不直接呼叫 MCP 或 LLM、永遠不直接寫入內容或進度——所有的寫入都走 server route。

**第四組章節：資料模型與功能行為。** 資料模型章節精確定義每個實體的關係：Course 包含有序的 Module 列表（Module 是嵌入物件、不是獨立文件）；Lesson 不儲存自己的 Course（透過反向參照推導）；Video 文件用短時間戳片段（short timestamped chunks）取代整份逐字稿；Progress 以 Clerk user ID 為鍵，只在 server route 寫入。搜尋行為章節定義了搜尋的具體表現：完整結果頁（不是聊天介面）、兩種結果類型（影片結果和課程結果）、從章節再解析到逐字稿的兩階段時間戳解析、以及「一切都必須有根據」（grounded）——永遠不憑空發明課程、價格或時間戳。

**第五組章節：陷阱、檢查與退路。** 常見陷阱（traps）章節列出實務上容易踩的坑：Context MCP 需要已部署的 Studio、語義搜尋可能關閉（改用關鍵字萬用字元）、template-literal 中的反引號要跳過、Clerk secret 與 Sanity token 只能留在 server 端。檢查章節要求跑完 type check、lint、production build、dev server、Studio 部署與搜尋測試——**絕對不能聲稱「檢查通過」卻沒有真的跑過。** 最後的 when-in-doubt 章節是退路規則：回到最小可行規則、用對應技能、維護 server/client 邊界、比對設計稿、取得批准再動手。

## In plain terms

AGENTS.md 就是一本「寫給 AI 的作業手冊」。你把專案的所有重要決定——它是什麼產品、要用什麼工具、哪些地方不能碰、要照什麼步驟工作、做完了要跑什麼檢查——全都寫在一份文件裡。AI 每次要幫你做事之前，先把這本手冊讀一遍，然後照著做。你不需要每次重複解釋，AI 也不會自己亂猜。

## Analogy

想像你是一家新創的技術主管，要帶一個很能幹但完全不了解公司狀況的新工程師。你不會只說「幫我把搜尋功能做出來」——你會給他一份完整的 onboarding 文件：產品是什麼、技術棧選了什麼、資料模型長什麼樣、搜尋應該怎麼表現、絕對不能做什麼（比如把私有密鑰放進前端）。有了這份文件，新工程師可以在你的系統內高效工作，而不是按照自己的理解做出一個看起來對但完全偏離方向的東西。AGENTS.md 就是那份 onboarding 文件，只不過讀者是 AI。

## Practical use

在 Vertex 學習平台的建置中，AGENTS.md 從頭到尾貫穿。專案的技術棧（Next.js App Router、Clerk、PostHog、Sanity Studio with next-sanity、Tailwind、Sanity Context MCP、Vercel AI SDK with OpenAI provider、Zod、TypeScript）全部寫在裡面，包括「不用什麼」的負面清單。資料模型精確定義了 Course、Module、Lesson、Instructor、Category、Video、Agent Context、Progress 的關係，其中 Module 是 Course 的嵌入物件而非獨立文件，Lesson 透過反向參照推導所屬 Course，Video 的逐字稿被切成有時間戳記的短片段而非整份塞進一個欄位。

搜尋的行為也寫死在文件裡：搜尋結果是一整頁排列好的卡片（不是聊天介面），分為影片結果（跳轉到精確秒數）與課程結果（打開對應課程），時間戳記先解析章節再解析逐字稿，一切結果都必須來自真實資料（grounded）。安全邊界同樣明確：瀏覽器永遠不持有私有 token，不直接呼叫 MCP 或 LLM，所有的寫入都走 server route。

除了內容本身，文件還規定了 AI 的工作方式：每次接到任務，先讀 AGENTS.md 與相關技能，再讀現有程式碼，寫出實作計畫（implementation prompt），在動手寫 code 前取得人工批准，嚴格按照計畫實作，跑完 type check、lint、production build 與搜尋測試，最後以短報告回報。九步迴圈（nine-step loop）不是建議而是規則，確保每次實作都經過規劃與核驗，而不是 AI 自由發揮後再來補破網。

這份文件也是可維護的：當專案的路由結構、認證模型、搜尋策略、資料模型、新的 provider 或反覆出現的錯誤模式發生重大變更時，更新 AGENTS.md；微小的細節（例如某個特定功能的實作方式）則放在 per-feature prompt files 裡，不塞進 AGENTS.md 以免規則被淹沒。判斷的標準是：**如果 AI 可能做出一個危險或破壞產品的假設，就把規則寫下來；其餘的放別處。**

## Questions

### Q1. AGENTS.md 的主要讀者是誰？它與一般的 README 有什麼根本上的不同？
A1. AGENTS.md 的唯一讀者是 AI 代理（AI agent），不是人類使用者、也不是團隊新成員。它與 README 的根本差異在於目的：README 描述「如何啟動與使用這個專案」，AGENTS.md 則描述「AI 要如何在這個專案內安全且正確地工作」——包括角色定義、工作流程、never-do 規則、資料模型、安全邊界與檢查清單。它是一份操作手冊，不是使用說明。

### Q2. AGENTS.md 與技能（skills）之間的分工關係是什麼？為什麼不能把工具 API 細節寫進 AGENTS.md？
A2. AGENTS.md 放專案層級的規則：產品是什麼、技術棧選了什麼、資料模型長什麼樣、搜尋該怎麼表現、哪些事絕對不能做。技能（skills）則放工具專屬的知識：Sanity 的 API 怎麼用、Clerk 的整合方式、next-sanity 的慣用模式。兩者分工是為了避免過時：AGENTS.md 在每次功能開發時都會被載入，如果裡面塞滿了工具 API 細節，這些細節容易隨著版本更新而過時，而且每次純 UI 的功能也會被迫載入這些無關的內容。把工具知識放在技能裡，AI 只在需要時才讀取，內容更容易保持最新。

### Q3. 判斷 AGENTS.md 該寫多詳細的標準是什麼？什麼時候該更新、什麼時候不該？
A3. 判斷標準是：**如果 AI 可能做出一個危險的或破壞產品的假設，就把規則寫下來。** 太粗會讓 AI 自行發明錯誤的資料模型、搜尋行為或安全邊界；太細會讓規則被淹沒，AI 反而找不到重點。更新的時機是重大決策變更——例如路由結構改變、認證模型換了、搜尋策略調整、資料模型修改、引入新的 provider、或反覆出現的錯誤模式——而不是每一個微小的實作細節，那些細節應該留在 per-feature prompt files 裡。
