# Digest — vertex-prompts

## Overview (L1)

- **What these files are** — Twelve markdown implementation prompts in `sources/vertex-learning-platform/prompts/`. Each was written by an AI implementation agent *before* one build step of the "Vertex" learning platform, then approved by the human via a Yes/No question panel ("I prepared the implementation prompt at prompts/<name>.md. Is this good to execute?"). They are the written contract between plan and code: the agent's reasoning, decisions, and test plan for that step. They document the agentic engineering workflow (AGENTS.md §2 loop) as a series of concrete, reviewable steps rather than a transcript.
- **Shared template** — Every prompt follows the same skeleton: `Goal` (scope + what it builds, plus explicit non-goals) · `Skills and docs read` (which AGENTS.md sections, which skill references, which `node_modules/next/dist/docs/` guides) · `Code inspected` (a table of files and what each already does) · `Decisions and assumptions` (what was asked vs. decided without asking, flagged not buried) · `Files to touch` (new vs. changed) · `Requirements` · `Security considerations` · `Acceptance criteria` (numbered, testable) · `Checks to run` · `Manual test steps`. Several add a `Measurements taken from the reference` section (pixel-scanning the design PNG) and two add post-implementation sections (`Deviations found while implementing`, `Implementation notes written after the build`) — the agent records what it got wrong and what changed.
- **Build order** — The prompts cross-reference each other and reconstruct the project's build order: `design-system` (tokens + component library) → `home-page` (presentational, placeholder data) → `sanity-content-model` (schema + Studio + server-only data layer) → `seed-sample-content` (real content to render and rank against) → `course-page` → `home-courses-from-sanity` → `courses-catalog` → `lesson-page` (video playback) → `intelligent-search` (search backend, no UI) → `search-results-page` (search UI) → `analytics-instrumentation` (PostHog sweep over the shipped features) → `video-ingestion-pipeline` (offline tooling that fills the video-document gap search anticipated).
- **Recurring principles** — Read-only pages fed by a server-only Sanity client; browser never holds a token or calls the MCP/LLM; the design PNG is the source of truth for visuals but tokens win over pixel guesses; numbers (module 5, lesson 5.1, durations) are derived from data, never stored; content grounded in real data; every substantive claim/decision flagged; checks are run and reported, never assumed.

### sanity-content-model

- Locator: `[[sources/vertex-learning-platform/prompts/sanity-content-model.md#sanity-content-model]]`
- Summary: Stands up the data foundation: a standalone Sanity Studio workspace at `studio/` (schema for course/module/lesson/instructor/category plus objects) and a server-only read layer in the web app (token-holding client, typed `sanityFetch` with cache tags, GROQ queries). No pages, no UI, no ingestion, no search. Explicitly out of scope: `video`, `agentContext`, `progress` documents.
- Key claims: Two user-confirmed decisions: standalone Studio (embedded route and root Sanity config deleted; Studio auto-updates, Vite-speed builds, TypeGen watch, and `sanity deploy` which the Context MCP later requires), and server-only client + tagged fetch (no `defineLive`; `live.ts` deleted). Model rules: durations stored as seconds (formatted in the web app, `math::sum` for aggregates); numbering never stored (Module 5 / Lesson 5.1 derived from array order); `level` is a string `options.list` (beginner/intermediate/advanced); `popular`/`freePreview` stay booleans; `keyPoints` array of strings; `learningOutcomes` array of `{icon, title, description}` with `icon` constrained to lucide names the app ships; Portable Text `blockContent` for `lesson.notes` and `instructor.bio`; resource `size` deliberately **not** stored. A lesson does not store its parent course — derived by reverse reference `*[_type == "course" && references(^._id)][0]`. Generated `_id`s; `useCdn: false`; `apiVersion` env-driven (default `2026-08-15`). `videoUrl` host-restricted to YouTube/Vimeo/Bunny. Security: `SANITY_API_READ_TOKEN` in `server-only` modules (client import = build error); Viewer rights only; `.env.example` committed via `!.env.example`; `sanity.types.ts` (TypeGen) committed. Queries: `COURSES_LIST_QUERY`, `COURSE_SLUGS_QUERY`, `COURSE_BY_SLUG_QUERY`, `LESSON_SLUGS/BY_SLUG_QUERY`, `INSTRUCTORS_LIST/BY_SLUG_QUERY`, `CATEGORIES_LIST_QUERY` — all project `"slug": slug.current`, `_key` on array items, never whole Portable Text in list queries. Acceptance includes `grep -r "sk" .next/static` finding no token.
- Learner-relevant: Data foundation before UI; the `server-only` boundary as a build-time guard; TypeGen from schema+queries; decision discipline — each modeling choice justified and flagged ("data over presentation").

- Summary: Fills the `production` dataset with realistic, internally consistent content so pages have something to render and cross-course search has breadth to rank: 6 categories, 5 instructors, 10 courses × 4 modules × 3 lessons = 120 lessons. Content only — no schema, pages, ingestion, or search.
- Key claims: One unique, topically-matched real YouTube video per lesson, resolved by fetching `youtube.com/results?search_query=…` per lesson, parsing `ytInitialData`, filtering candidates (duration 3–90 min, unused title/id), verifying each against `https://www.youtube.com/oembed` (non-200 drops it), and caching to committed `studio/scripts/seed/videos.json` (throttled ~1/sec; re-runs do zero network). Lesson slugs globally unique, prefixed with course slug. Deterministic `_id`s (`course.<slug>`, `lesson.<lesson-slug>`, …) so `--replace` re-import is idempotent. Content is hand-authored, not templated — search quality depends on real topical text. `studentCount` consistent (course = first lesson's count, monotonic decay). Plain `.mjs` scripts, no new deps, no write token (authenticated CLI import). Course lineup across Web Development, AI Engineering, Backend & Infrastructure, Data, Languages, Security.
- Learner-relevant: Seeding as engineering (real data, deterministic ids, idempotent imports, offline caching); authored-not-generated content because downstream quality (search ranking) depends on it; no credentials by design.

### intelligent-search

- Locator: `[[sources/vertex-learning-platform/prompts/intelligent-search.md#intelligent-search]]`
- Summary: Wires the search backend end-to-end: connect the Sanity Context MCP, build the server-side `POST /api/search` route that turns a plain-language query into ranked, grounded results, and ship the Sanity Context document that configures it. **No UI** — the results page was explicitly deferred; verification is by `curl`. Studio deploy is in scope because the MCP will not serve the dataset without it.
- Key claims: Scope decided with the user: lesson results only (no `video` type exists yet), no results page, Studio deploy in scope, OpenAI provider. **Two-stage grounding — the model picks, Sanity supplies the facts**: the LLM runs a tool loop over the MCP and returns only `{lessonId, kind, reason, rank, startSeconds?}`; the route then re-reads every referenced lesson with a normal GROQ query and builds the card from that data, so grounding holds structurally rather than by instruction (the model never authors a title, label, count, or duration; unresolvable ids are dropped and logged). JSON response, not a token stream (no UI to consume one; upgrade later via `streamObject`). Zod structured output with the boundary "a Zod parse that rejects malformed model output with a 502". The `@sanity/context` plugin lags this Studio's major (peers `sanity: '^6'` vs `5.31.1`) so it is **not installed** — the Context document is created by import instead, and Conversation Insights stays unavailable. Context document slug `vertex-search`, filter `_type in ["course","lesson","instructor","category","video"] && !(_id in path("drafts.**"))`, instructions as pure deltas (reverse-reference course, positional numbering, `pt::text(notes)`, wildcard-and-OR matching, chapters-then-chunks, never project whole chunks, `video` may hold zero documents). System prompt carries grounding, return-every-result, rank-by-specificity, and refusal rules. Security: `server-only` modules, Zod-validated request (query 1–200 chars), model output treated as untrusted, read-only route, errors never echo env or MCP. Route: `runtime = "nodejs"`, `force-dynamic`, `maxDuration = 60`. **Implementation notes (post-build corrections)**: GROQ `match` against an array of patterns is **AND, not OR** — measured `match ["cach*","fetch*","revalidat*"]` → 1 result; the working OR idiom is `count($terms[^.title match @ || pt::text(^.notes) match @ || ^.keyPoints[] match @]) > 0` → 11 (a real query went 2 → 11 results); OpenAI structured outputs reject optional and constrained fields, so the model-facing schema uses `.nullable()` instead of `.optional()` with no range constraints; latency tuned `MAX_STEPS` 12→6 and `reasoningEffort: "low"`, ~72s → ~35s. Needs attention: the route is public and unrate-limited (every call costs an OpenAI request); video results stay empty until ingestion; prompt/context edits need a server restart.
- Learner-relevant: Grounding by architecture, not instruction; verifying against the live stack and recording what the plan got wrong; the OR-matching GROQ idiom; structured-output constraints; latency tuning with a hard `maxDuration`.

### search-results-page

- Locator: `[[sources/vertex-learning-platform/prompts/search-results-page.md#search-results-page]]`
- Summary: Ships the `/search` results page from `design/vertex-search.png`, wired to the existing `POST /api/search`. This is the UI: two result cards (video + lesson), the sort control, the header search field, and the empty/loading/error states. No new server intelligence.
- Key claims: **Client-side fetch, URL is the source of truth** — `/search?q=…&sort=…` is a server shell rendering a client `<SearchResults>` inside `<Suspense>`; rationale: the route runs an LLM tool loop with `maxDuration = 60`, so a server-rendered page would block the whole document. The client reads `q`/`sort` from the URL and `POST`s to `/api/search`. **Sort re-requests**: changing the select calls `router.replace`, re-running the fetch — sorting is a server concern (`groundHits`) and browser re-sort would diverge. Course icon comes from the course cover image (`courseIconRef` added to `LESSONS_BY_IDS_QUERY` and `SearchResultBaseSchema`; fallback initial-letter tile). Video thumbnail = `thumbnailRef` via `urlForImage`; when null, a neutral-900 tile with a play glyph. The check circle on lesson cards is presentational (progress not tracked yet). `reply` is **not rendered** — §7 says cards, not a chatbox; `react-markdown` is not installed. Header and home hero fields become a shared `SearchForm` client component (navigates to `/search?q=…`); `⌘ K` focuses it. Each fetch runs with an `AbortController` keyed to `q`+`sort` so a fast second search cancels the first. **No client PostHog capture** — `search_performed` is already captured server-side and double-counting would corrupt the metric. Errors show a generic line + Retry, never the raw route error; query is length-capped client-side so the route's 400 is a backstop. Acceptance: `Watch from mm:ss` actions carry `?t=<startSeconds>` and start the lesson video at that second; sort selection survives a reload; the empty state's "Browse all courses" links to `/courses`.
- Learner-relevant: A skeleton-loading client UI around a slow server route; URL-as-state and re-request-vs-re-sort reasoning; avoiding double-instrumentation; keeping raw errors off the screen.

### analytics-instrumentation

- Locator: `[[sources/vertex-learning-platform/prompts/analytics-instrumentation.md#analytics-instrumentation]]`
- Summary: Extends PostHog coverage to the features shipped since base setup — intelligent search, the search results page, and the lesson page — adding the engagement moments AGENTS.md §7 names (catalog/lesson views, a search, a video play and watch depth, a lesson completed) plus result-open and resume events. Analytics-only: no product features, no progress backend, no visual changes.
- Key claims: **Rule 34** — `capture()` enqueues synchronously; Next route handlers are torn down per invocation, so a shared/singleton client MUST `await posthog.flush()` before the handler returns or the event is silently dropped (the existing `/api/search` never flushes — a bug this change fixes). Watch depth is an **elapsed-time heuristic** (user's choice over provider SDKs/postMessage; no dependency): accumulate only while `document.visibilityState === "visible"`, stamp `measurement: "elapsed_time"`, ceiling 100, milestones 25/50/75/95 fire at most once per mount (slug is the key). `lesson_completed` is **derived from watch depth ≥ 95%** — an analytics proxy, since there is no progress record; the `signals-scout-course-funnel` scout reads `lesson_completed ÷ lesson_viewed`. The **raw search query is captured** on `search_performed`/`search_result_opened` — normally forbidden by the PII commandments, but user-confirmed because `signals-scout-search-quality` needs zero-result queries. `course_started` is renamed `course_resumed` with `location: "hero"|"progress_bar"` (one button, one event — splitting it would break the funnel). The browser sends its PostHog distinct id and `$session_id` to `/api/search` (Zod-validated, optional, length-bounded; the Clerk user id still wins as `distinctId` when signed in — a client-supplied id is never trusted over server identity). Event catalogue: new client events `catalog_viewed` (`course_count`), `course_viewed` (`course_slug`, `module_count`, `lesson_count`, `level`), `search_result_opened` (`query`, `sort`, `result_kind`, `rank`, `position`, `result_count`, `start_seconds`), `video_progress`, `lesson_completed`, `lesson_resumed` (`source: "deep_link"`), `lesson_navigated` (`direction`); changed `video_played` (gains `source: "deep_link"|"poster_click"`, drops `autostarted`) and server `search_performed` (gains `lesson_result_count`, `zero_results`, `duration_ms`, `signed_in`) plus new `search_failed` (coarse `reason`, never the error message — it could carry the MCP URL). Architecture: `lib/analytics/events.ts` constants, a generic `view-tracker` component, a `use-watch-depth` hook, client wrappers for footer nav and sticky-bar CTA. No PII beyond the Clerk user id; missing config must never break a page and must fail loudly in development only.
- Learner-relevant: Event-handler discipline over `useEffect`; the flush-before-return rule for server captures; measuring "how far watched" without a player API and being honest about the inaccuracy; naming conventions; property design that feeds existing scouts.

### video-ingestion-pipeline

- Locator: `[[sources/vertex-learning-platform/prompts/video-ingestion-pipeline.md#video-ingestion-pipeline]]`
- Summary: Builds the offline tooling that produces the `video` documents search depends on: one document per unique video URL holding chapter markers (table of contents) and the transcript split into short timestamped chunks. This fills the gap the intelligent-search task anticipated ("the video path lights up when ingestion lands"). Nothing about the request path changes.
- Key claims: **Findings probed live before writing the prompt** (verified, not assumed): the watch page's `captionTracks[].baseUrl` returns HTTP 200 with an empty body (YouTube blocks unauthenticated caption fetches); the InnerTube player endpoint with the **iOS client context** returns a working caption track and `&fmt=json3` returns real JSON cues (ANDROID returns XML, WEB returns `UNPLAYABLE`) → so: iOS client + `fmt=json3`, XML `<transcript>` as fallback; chapters come from `ytInitialData` (`chapterRenderer`/`macroMarkersListItemRenderer`, `timeRangeStartMillis`), duplicated across renderers so they must be deduped by start time. YouTube is the only provider with an ingestion adapter (§9: supported = both ingestion and playback; Vimeo needs a `/texttracks` API token and Bunny an API key — neither is available, so they are reported as skipped with a clear reason via a provider registry). The URL list comes from the dataset via the authenticated CLI (`sanity documents query`), deduped by provider id. Deterministic ids `video.youtube-<videoId>` (Bunny `video.bunny-<library>-<id>`), only `[A-Za-z0-9._-]` survives. Chunking: merge cues to ~45s or ~350 characters, breaking only on cue boundaries; `startSeconds` = floor of the first cue; ~120 chunks for a 90-min video — never one big field. Cache and generated NDJSON are **not committed** (megabytes; gitignored); re-runs read the cache with zero network. The `video` document is `readOnly` in the Studio with `ingestedAt`; deterministic `_key`s (`chapter-<startSeconds>`, `chunk-<index>`). The runner resumes from cache, supports `--force`/`--limit=N`, throttles, persists per video, exits non-zero on failure, and **never partially writes** a video (no cues = a recorded failure, not an empty `chunks` array). The builder refuses to write if any document would fail schema validation (well-formed ids, monotonic integer `startSeconds`, sorted chapters, no empty text). No write token — reads and imports go through CLI auth. Acceptance: one `video` per unique lesson video; re-running without `--force` produces byte-identical NDJSON; a GROQ filtered chapter query returns real matches; a site search for a mid-video topic returns a video hit whose Watch action opens the lesson page at that second.
- Learner-relevant: Probe-and-verify before designing against a hostile third-party API; the adapter pattern with honest "not supported" reporting; deterministic, resumable, offline-safe offline tooling; never partially writing a document.
