# AI 為什麼需要 Design System？多頁 UI 一致性的秘密

## Learning goal

能說明 AI 在多頁應用中會自行發揮導致不一致，以及 design system 如何作為人類與 AI 之間的視覺合約。

## Lesson

### 🎯 一組數字：AI 生成 UI 的崩塌率

假設你正在做一個 **5 頁面的 Next.js 學習平台**——首頁、課程目錄、課程詳情、單元頁面、搜尋結果頁。你讓 AI 逐頁生成 UI。

**結果**：每一頁單獨看都「還行」，但 5 頁放在一起，像 **5 個不同產品**拼起來的拼盤。

| 頁面 | 按鈕顏色 | 圓角大小 | 標題字級 | 設計者 |
|------|---------|---------|---------|--------|
| 首頁 | 藍色 | 8px | 28px | AI（第一次） |
| 課程目錄 | 綠色 | 16px | 32px | AI（第二次） |
| 課程詳情 | 紅色 | 12px | 28px | AI（第三次） |
| 單元頁面 | 紫色 | 16px | 30px | AI（第四次） |
| 搜尋結果 | 橘色 | 8px | 32px | AI（第五次） |

**為什麼會這樣？** 因為 AI **沒有視覺記憶**——它不知道自己前一頁用了什麼色號、什麼字級。每一页都是從零開始做設計決定。

### 💡 問題根源：AI 的「預設行為」是不一致

人類設計師做多頁應用時，會記住自己上一頁用的色號、間距和字級，然後在下一頁重複使用。

AI 沒有這種 **跨對話的視覺記憶**。每次你要求它做新頁面，它都是基於 prompt 和對「好看的 UI」的統計學偏好，**重新生成一套新的**。

| 比較項目 | 人類設計師 | AI |
|---------|-----------|-----|
| 視覺記憶 | ✅ 有 internalized design language | ❌ 無跨對話視覺記憶 |
| 設計一致性 | ✅ 自動重複使用已定義的 token | ❌ 每頁重新發明 |
| 問題類型 | 偶爾疏忽（bug） | **根本沒有在記**（default behavior） |

**這代表什麼？** 不一致不是偶發的 bug，而是 AI 的**預設行為**。它不是「偶爾記錯」，而是「根本沒有在記」。

單頁應用你感受不到這個問題，因為所有設計決定在一次對話裡就完成。多頁專案把這條裂縫拉大到每一個頁面之間，不一致就無所遁形。

### 🔧 解法：Design System × AI 的雙重鎖定

人類設計團隊解決不一致的方式是建立 **Design System**——一份寫下來的視覺規格。

但 AI 需要的不是「設計師之間的溝通文件」，而是一份 **「人類與 AI 之間的視覺合約」**（visual contract between human and AI）。

#### 📋 Design System 必須包含的 5 大規格

| 規格類型 | 內容 | 範例 |
|---------|------|------|
| **Typography** | 每級 heading 的字型、大小、粗細、行高 | h1: Inter, 28px, 700, 1.2 |
| **色彩系統** | primary color、neutral color、語義色，每個色階有 hex 值 | primary-500: #F97316 |
| **間距系統** | 統一的 spacing scale | 4px / 8px / 16px / 24px / 32px / 48px |
| **Border-radius 與 Shadows** | 按鈕圓角、卡片陰影、輸入框 border | radius-sm: 4px, shadow-md: ... |
| **可複用元件規格** | 按鈕 variants、大小、hover 與 disabled 狀態 | Button: primary/secondary/ghost |

**為什麼這樣設計？** 這份合約不只是讓 AI「知道」設計長什麼樣，而是要求 AI **嚴格照著做**——不能自己加漸層、不能自己選色、不能自己發明新的間距值。

設計稿的截圖是 source of truth，AI 的職責是**精確複製**它，而不是「改善」它。

這就是 [[learn/vertex-learning-platform/elements/design-system|設計系統 (Design System)]] 在 AI 實作流程中的角色：它不是 optional 的風格參考，而是一份**硬性的、可被機器執行的約束文件**。

### ⚡️ Vertex 的做法：設計稿 + AGENTS.md 雙重鎖定

在 Vertex 專案裡，設計系統的落地方式非常具體。

#### 第一道鎖：設計稿（What to build）

設計稿圖片放在 `design/` 資料夾，跟 `public/` 同級。AI 每次做 UI 都從這裡讀取參考——這就是 **source of truth** 的物理位置。

#### 第二道鎖：AGENTS.md 的 UI 規則（How to build it）

光有設計稿不夠。AI 可能會「稍微改善一下」或「加一點自己的品味」。所以 Vertex 在 AGENTS.md 裡寫了一條明確的 UI 規則：

> You do not design UI. The user gives you the design as desktop images plus a prompt. Reproduce them exactly: layout, spacing, typography, color, and states. Do not restyle or improve beyond the reference. Reuse the components and Tailwind patterns already in the project before you add new ones. When there is a reference image, it is the source of truth.

**這段規則做了三件事**：

1. **禁止 AI 做設計決策**——「You do not design UI」
2. **定義 AI 的唯一職責**——精確複製設計稿（layout、spacing、typography、color、states）
3. **要求複用已有元件**——優先使用 Tailwind pattern，不要重新發明

**為什麼兩道鎖缺一不可？**

| 鎖定方式 | 功能 | 缺少對方會怎樣 |
|---------|------|--------------|
| 設計稿 | 告訴 AI「要做什麼」 | AI 知道不能設計，但不知道該做什麼 |
| AGENTS.md | 告訴 AI「怎麼做、不能做什麼」 | AI 可能「稍微改善一下」，加漸層、換字型 |

兩者形成完整的約束系統：**設計稿告訴 AI 做什麼，AGENTS.md 告訴 AI 不能做什麼。**

### 🛠️ 技術落地：Design Token 怎麼轉成 Tailwind

有了設計稿和行為約束，接下來是怎麼把設計轉成 AI 能嚴格執行的技術格式。

Vertex 把設計系統轉譯成 **Tailwind v4 的 CSS 變數（theme tokens）**，寫進 `globals.css`。

#### 三層轉譯流程

**第一步：Design Token 定義**

| Token 類型 | 範例 | 說明 |
|-----------|------|------|
| 顏色 | `@theme { --color-primary-500: #F97316; }` | Primary 色系 50~500 六個色階 |
| 圓角 | `@theme { --radius-sm: 4px; --radius-xl: 24px; }` | xs(4px) 到 xl(24px) |
| 陰影 | `@theme { --shadow-sm: ...; --shadow-xl: ...; }` | sm 到 xl 層級 |
| 字級 | `.text-display-1 { font-size: 2.5rem; line-height: 1.2; }` | 一個 class 鎖定 size、line-height、weight |

**第二步：元件庫使用 Token**

元件不使用任何 raw hex 值：

| 元件 | ❌ 錯誤做法 | ✅ 正確做法 |
|-----|-----------|-----------|
| Button | `background: #F97316` | `bg-primary-500` |
| Card | `box-shadow: 0 4px 12px rgba(...)` | `shadow-md` |
| Badge | `background: #FFF3E0` | `bg-primary-100` + `text-primary-500` |

**第三步：Showcase 驗證**

Vertex 建了一個 `/design-system` 展示頁面，把所有 token 和元件的實際渲染結果攤在一個頁面上。

你可以一次看完所有顏色、字級、按鈕狀態、Badge 變體、卡片樣式，然後跟 `design/` 資料夾裡的設計稿做**視覺比對**。不一致的地方一目了然。

### 🎯 為什麼「有規則」和「有規格」缺一不可

這是整個設計系統最關鍵的觀念：

| 條件 | AI 知道什麼 | AI 不知道什麼 | 結果 |
|-----|-----------|-------------|------|
| **有規則 + 無規格** | 不能自己做設計 | 該做什麼 token、什麼元件 | 偏差 |
| **有規格 + 無規則** | 要用哪些 token | 不能自己「改善」 | 加漸層、換字型 |
| **有規則 + 有規格** | 不能自己做設計 | 要精確複製哪些 token | ✅ 一致 |

**用一句話說**：規則關上門，規格把門焊死。

### 🚀 回到你的 Next.js 專案：三步驟解法

如果你現在有一個 Next.js 應用，打算讓 AI 幫你做多個頁面，解法不複雜：

**步驟一：從一張設計稿開始**

哪怕是你自己畫的 wireframe 或 Figma 截圖，放在 `design/` 資料夾。

**步驟二：定義 Design Tokens**

把關鍵的色號、字級、間距、元件 states 轉成 Tailwind CSS 變數，寫進 `globals.css`。

**步驟三：寫死 AI 行為規則**

在你的 AGENTS.md 裡加上：「你不設計 UI，你複製設計稿。」

**為什麼這樣就夠了？** 這三步做完，AI 在每一個頁面就會重複使用相同的 token 和元件，多頁 UI 的一致性不再靠 AI 的品味，而是靠一份**寫下來的約束文件**。
