# Agentic Engineering 基礎：先給 AI 一套系統，再讓它動手

## Learning goal

能說出「prompt 到能用」為什麼會崩潰，以及「給 AI 一套系統」——human 是產品思考者、AI 是實作代理——為什麼是替代方案。

## Lesson

### 📝 這一課在講什麼

讓 AI 寫程式，最省事的做法是：把需求丟過去，AI 跑出結果，不滿意就再修一輪 prompt，直到它看起來能動。這種「prompt 到能用」（prompt until it works）的做法，做 demo 綽綽有餘。demo 只需要幾個畫面、一份假資料，改壞了按一下重來就好。但生產級應用不同——它有真實的使用者、要登入、要付費、要承受攻擊。一旦要建的是這種東西，「prompt 到能用」這條路就會在三個地方崩潰。

### 💥 三大崩潰點：擴展、安全、理解

**1. 擴展性（scalability）先崩潰。** 每一項新功能都要重新磨一輪 prompt，整個專案變成永遠修不完的對話。

**2. 安全性（security）接著崩潰。** AI 不知道哪些值不能進瀏覽器，可能把密鑰（secrets）直接寫進前端。

**3. 理解（understanding）的問題最隱蔽。** AI 沒有產品的脈絡，它不清楚自己正在建的是什麼東西。

**為什麼這三個崩潰很重要？** 因為它們不是三個獨立的小問題，而是來自同一個機制：一個薄弱的起始提示詞（weak starting prompt）給了 AI 太多的自由。

### 🧩 崩潰的根源：自由越多，猜錯越多

薄弱的起始提示詞，等於把決定權交給 AI。自由越多，AI 越傾向自己補上缺口，而它補上的往往是錯的：

- 不知道產品長什麼樣，就**發明一個資料模型（data model）**，錯誤的模型接著污染目錄、課程頁與搜尋，整棵樹都跟著亂。
- **搜尋方式（search）**自己定一套，使用者在結果頁找不到該去的精確時刻。
- **安全邊界**沒有著落，密鑰可能直接被寫進瀏覽器。
- **任務範圍**付之闕如，它會寫出超出範圍的路由（routes）。

這些都不代表 AI 不聰明。它們代表一件事：人沒有先給 AI 一個可以安全運作的系統，卻要求它自己畫出這個系統。這正是「prompt 到能用」這條路真正壞掉的地方。

### 🏗️ 替代方案：Agentic Engineering 的角色分工

替代這條路的做法叫做[[learn/vertex-learning-platform/elements/agentic-engineering|代理式工程（Agentic Engineering）]]。它先解決一件事，把**角色分工（role split）**講清楚：

| 角色 | 負責什麼 |
| --- | --- |
| **人＝產品思考者（product thinker）與架構師** | 定義產品、選擇技術棧、畫出邊界、訂下規則與工作流程 |
| **AI＝實作代理（implementation agent）** | 在這些定義之內把事情做出來 |

**為什麼這個分工很重要？** 因為它保住了控制權。人依然是工程師，AI 只是讓執行變快的那一方。人不會因為用了 AI 就變成觀眾，AI 也不會因為跑得快就變成設計者。關鍵動作都要經過人批准與核驗。

把控制權交出去會發生什麼？其實在 demo 階段就看得出來：AI 自由發揮時常常越做越大，一口氣把範圍擴出去，加了一堆沒人要求的東西，還自以為貼心。人若沒有在第一道閘門擋住，這些決定就會直接進到 code 裡，成為之後改不動的債。分工一旦模糊，等於把產品與架構的決定權交給一個沒有產品理解的執行者——專案越大，風險越失控。

### 🔧 給 AI 一套系統：三大核心元件

分工確立之後，機制就清楚了：**給 AI 一套系統，再讓它動手**。系統由三樣東西組成：

**1. 上下文檔案（context files）**——把「這個專案是什麼」寫成文件，例如 AGENTS.md。產品、技術棧、邊界、規則與工作流程，全都寫進去。AI 每次動手前先讀這份文件，就不必猜。

**2. 工具知識（skills）**——把「工具怎麼用」做成技能。AI 在實作某個功能前先讀對應的工具說明，不依賴過時的訓練資料，也不必亂猜 API 的寫法。

**3. 批准閘門（approval gates）**——AI 不得直接改 code。先讀檔案、研究程式碼、寫出實作計畫，等人工批准之後才動手。

**為什麼三樣都要？** 因為三樣東西各修一個缺口：

| 元件 | 補上的洞 |
| --- | --- |
| 上下文檔案 | 理解——AI 讀了才知道專案是什麼 |
| 工具知識 | 過時知識——AI 照著最新文件做，不靠舊記憶 |
| 批准閘門 | 最危險的一項——被擅自決定的產品與架構 |

三樣缺了任何一樣，系統就有一個洞。

### ⚡️ 強健的起始提示詞：先給系統，再開放問題

把三樣東西組合起來，就是一個**強健的起始提示詞（strong starting prompt）**。強健的意思，是它先給系統，再開放問題：一次交代清楚產品、技術棧、邊界、規則與工作流程，不把開放式請求丟給 AI。

同樣一句「幫我建一個學習平台」，兩個做法天差地遠：

- **弱 prompt**：讓 AI 自由發揮。
- **強 prompt**：讓 AI 在一個已經定義好的系統裡執行。

**為什麼不是 prompt 越長越好？** 因為系統的強弱不靠 prompt 的長短，靠的是這三樣結構化的東西。長 prompt 只是把話說多；結構化的系統把決定權從 AI 手上收回來，放到人可以審查的文件與閘門上。

### 🎯 實例：用 Vertex 看強弱 prompt 的差別

用 Vertex 當例子，可以看得更清楚。Vertex 是一個學習平台：作者在 Sanity 裡建立課程與模組，學習者在 Next.js 的網站上用自然語言搜尋，跳轉到影片講解的精確時刻。

假設人只丟一句「幫我建一個學習平台」：

- **弱 prompt 的結果**：AI 自己決定搜尋長成什麼樣子，它很可能做成一個**聊天框**——使用者問一句、它答一句。這就壞了，因為搜尋在產品裡的正確形狀是**結果頁**：一頁排名好的卡片，每張卡片連到影片的某個秒數。這個決定一旦被 AI 擅自做出來，之後的資料模型、影片資料結構、時間戳記解析全都得跟著它走，錯的方向越走越深。
- **強 prompt 的結果**：先講清楚產品與搜尋的規則，AI 只負責照規則實作，不會有機會把它做成聊天框。

同樣一句話，一條路走向壞掉的產品，另一條路走向照計畫執行的產品——差別全在系統先給或沒給。

### 📄 AGENTS.md：整個系統的載體

三樣東西之中，**上下文檔案是整個系統的載體**。具體到這門課的專案，載體是 AGENTS.md——一份寫給 AI 代理（AI agent）看的操作手冊（operating manual）。

**為什麼這份文件的讀者是 AI，不是人？** 兩份文件分工不同：

- **README** 是給人看的：說明怎麼安裝、怎麼使用。
- **AGENTS.md** 是給 AI 看的：說明這個專案是什麼、要怎麼工作、哪些事絕對不能做、何時該請求批准、如何回報。

**為什麼 AI 每次動手都要重讀？** 因為 AI 沒有長期記憶。每一次新的請求，AI 都像第一天上班，不知道這個專案是幹什麼的。AGENTS.md 就是讓它每次重新想起專案的檔案。人只要把規則寫好一次，之後每一輪工作都自動適用，不需要重複提醒。它的完整章節構造屬於後面的一課，這裡只需要記住它的角色：它是整套系統的承載者，也是「給 AI 一套系統」這句話落地的地方。

### ✅ 收束：記住 plan-before-code 的順序

最後把這一步落回一個具體的收穫。整個工作流的脊梁是 **plan-before-code**，先計畫後寫程式。code 只在一份經批准的 prompt 之後才出現。

計畫寫在 code 前面，代表所有關鍵決定都在寫 code 之前先攤開給人看：資料模型怎麼訂、搜尋怎麼做、密鑰放哪裡，這些在實作計畫裡都寫得明明白白。人有機會在蓋章之前喊停——這正是批准閘門存在的理由。AI 的決定沒有機會悄悄混進 code：它會先以計畫的形式接受檢查，之後才變成 code。

正確的執行順序是：

1. AI 先讀檔案與技能，再研究程式碼。
2. 遇到真正模糊的地方，提出一個聚焦的問題。
3. 寫出實作計畫。
4. 人看了蓋章。
5. AI 才動手寫 code，寫完再跑檢查、回報結果。

**為什麼這個順序很重要？** 因為順序一顛倒，前面講的所有崩潰都會回來。所以記住這個順序，比記住任何單一工具都重要：**系統先給，計畫先批，code 最後才出現**。這就是「為什麼先給 AI 一套系統，再讓它動手」的答案。
