# 範圍邊界 Scope Boundary：只建清單上列出的東西，擋下 overbuild

## Learning goal

能解釋「build only what is listed」的範圍邊界——standout feature 決定一切、不 overbuild、把範圍寫進操作手冊防止 AI 自己發明產品決策。

## Lesson

一句話，一個請求：「幫我建一個學習平台」，然後把剩下的交給 AI。幾分鐘後它開始動手，做出來的東西卻常常讓你認不得。它的能力沒問題，問題在於它沒有判斷依據。一句「建一個學習平台」只裝得下意圖，裝不下「要做到什麼程度」「哪些不准做」。意圖之外留下的空格，AI 會用看起來合理的預設值去填空，而這些預設值，幾乎都落在同幾個固定位置。

**四個最常被 AI 自行填空的位置：**

- 資料模型（data model）憑空猜，欄位和關係自己長出來
- 搜尋設計自己挑，外觀像什麼就做成什麼
- 機密（secrets）可能被寫進瀏覽器端程式碼，直接曝光
- 路由（routes）自行擴張，多出你沒規劃過的頁面

每一項單獨拿出來都算合理，合在一起，就是一個偏離你意圖的產品。

### ⚡️ 範圍邊界：管「做多少」的那一層

**為什麼同樣一句話，結果差這麼多？** 關鍵在提示詞（prompt）的強弱。弱的起手式只給一句話，自由度全在 AI 手上；強的起手式先把系統端出來——產品是什麼、用什麼技術、邊界畫在哪、規則有哪些、工作流怎麼走，一項一項交代清楚。系統在前，AI 的每個決定才有軌道可循。範圍邊界就是這套系統裡專門管「做多少」的那一層，也是[[learn/vertex-learning-platform/elements/agentic-engineering|代理式工程 (Agentic Engineering)]]控制 AI 的第一道閘門。

這個問題有一個名字，叫做[[learn/vertex-learning-platform/elements/scope-boundary|範圍邊界 (Scope Boundary)]]。它的口號是一句英文：**build only what is listed，只建清單上列出的東西**。清單上有的，一件一件做；清單上沒有的，一件也不做。補完整就是 build nothing beyond that——在清單之外什麼都不建。與它相對的壞習慣叫 overbuild，多建、超建，把沒列出來的功能也做了進去。範圍邊界要求你明確地拒絕 overbuild，把 AI 的執行權限鎖死在清單之內。聽起來像一句消極的提醒，實際上它是整個受控建置（controlled build）的基石：人先把範圍定好，AI 才有資格談加速。

### 📐 邊界從哪裡長出來：產品描述

範圍不會憑空訂出，它從產品描述（product description）長出來。動手之前，你先把要蓋什麼講清楚：這是給誰用、解決什麼問題、最拿得出手的功能是哪一個，然後沿著這個描述把邊界畫出來。

**核心順序：先有描述，後有邊界。**

描述寫不出來，代表你對產品的判斷還沒成形；那一刻讓 AI 動手，等於把產品決定權整個交出去。產品描述是範圍的最上層容器，邊界是它的外框。

### 🔗 源頭決定：特色功能

範圍裡有一個源頭決定，叫做特色功能（standout feature）。它是眾多決定裡特殊的一個——釘住其他所有決定的一顆釘子。以 Vertex 這個學習平台為例，特色功能是智慧搜尋（intelligent search）：讓學習者用自然語言搜尋影片，並跳轉到該主題講到的確實秒數。這個單一選擇一鎖定，下游整條鏈就跟着定案。

- 資料怎麼組織 → 資料模型：課程（course）、模組（module）、課程單元（lesson）、講師（instructor）、分類（category）、影片（video）、進度（progress）
- 影片怎麼進系統 → 影片攝取（ingestion）規則
- 搜尋結果長成什麼樣 → 搜尋 API 和結果卡片（result cards）
- 使用者要跳到哪裡 → 時間戳（timestamps）格式

一個特色功能，把資料模型、攝取、搜尋、結果、時間戳全部釘在同一個方向。這個連鎖反應叫做級聯（cascade）：範圍先鎖住源頭，下游自然一致，不會出現「資料模型為 A 設計、搜尋卻按 B 的假設實作」這種彼此打架的局面。

### 📘 範圍的載體：操作手冊

**為什麼範圍需要載體？** 因為你在開工那一天把範圍講清楚，只管得住那一天的那個 AI。下一個功能、下一輪對話，AI 又把範圍重新爭論一遍，又開始自己發明。範圍必須寫進操作手冊（operating manual）——在 Vertex 的流程裡就是 AGENTS.md。手冊把範圍記錄成文字，AI 每次動手前先讀它，範圍就在整條生產線上持續生效。

手冊裡有一節專門記錄已經做出的決定（decisions already made），把定案寫死，防止每個功能開發時重新被爭論。以 Vertex 為例，這一節列出七條：

1. 搜尋必須是結果頁面（results page），不作聊天介面（chatbox）
2. 搜尋結果必須有根據（grounded），絕不編造
3. 影片以文件型內容（video documents）儲存
4. 時間戳以章節優先（chapters-first）產生
5. 影片與模組就地嵌入頁面
6. 進度以 Clerk 使用者 id 為鍵記錄
7. 分析事件由 PostHog 統一發出

每一條都是一個不會再被翻案的決定。寫進手冊之前，這些都是 AI 可能自作主張的地方；寫進手冊之後，它們成了固定的軌道。操作手冊存在的理由，就是讓範圍成為長期記憶——一次性的口頭交代做不到這件事。

### ⚖️ 有邊界 vs 沒邊界：兩張圖擺在一起

把有邊界和沒邊界放在一起看，差別立刻清楚。沒有邊界的 AI 接到任務之後，自由度很大。它可能把搜尋做成一隻聊天機器人（chatbot），因為一個聊天框看起來就是最自然的搜尋介面——這卻偏離你真正要的結果頁面。它也可能在導覽列裡多放一條連結，開出一條你沒規劃過的路由，因為「後台管理」聽起來順理成章。每一項單獨看都合理，合在一起，就是你認不出來、也收不回的產品。

有邊界的 AI 不同。手冊寫着搜尋是結果頁面、路由只有清單上那幾條、機密只許待在伺服器端，它照着做，做完的每一個功能都跟上一個一致。你可以放心讓它加速，不必站在後面盯着它別亂跑。

**還有一層差別藏在時間裡。** 沒有邊界的專案，範圍會在每個功能開發時被重新爭論一次：做目錄頁時，AI 覺得搜尋該放進側邊欄，就塞了一個小搜尋框；做搜尋頁時，它又覺得聊天介面更自然，就改成聊天框。同一個產品裡，搜尋以好幾種不同的形狀出現，因為每一輪開發都在重新發明範圍。有邊界的專案，手冊裡「已經做出的決定」那一節讓搜尋的形狀只此一種，從第一個功能到最後一個功能都長得一樣。範圍不重複爭論，整條生產線才不會各自為政。

### 🛡️ 為什麼連「不要做的事」也要寫

**為什麼負面規則特別重要？** 因為 AI 對「合理但錯誤」的替代方案特別有親和力。你只說「做搜尋」，它會挑一個看起來最像搜尋的形狀——聊天框就是那個形狀。負面規則的作用，就是攔下這種看似合理、實則出界的實作。寫下「搜尋不作聊天介面」，就少一類要猜的決定；寫下「路由不許自行擴張」，就少一種越界的可能。

### 📏 範圍要寫多密：一條判準

範圍要寫得多密，有一個判準：凡是 AI 可能做出危險假設、或是會毀掉產品一致性的地方，就把它寫成規則；寫到這個程度就停，不必把每個細節都塞進去。常見的失敗在於規則太空泛——寫「用好的實作方式」「保持乾淨的程式碼」這種空泛的期許，AI 無從執行，等於沒寫。具體到能攔下一個錯誤假設的規則，才有邊界的作用。

### 🎯 總結：一句話帶走

到這裡，範圍邊界的運作就完整了：它是從產品描述長出來的清單，以特色功能為源頭，靠操作手冊長期生效，用負面規則攔住 AI 的合理錯誤。範圍邊界管的是自由度，能力一個字都沒動。整篇最值得帶走的一句話是——把不要做的也寫清楚，AI 才不會替你做決定。你劃掉的每一樣東西，都是它不會擅自加上去的意外。
