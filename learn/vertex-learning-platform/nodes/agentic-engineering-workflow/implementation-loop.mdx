# 實作迴圈 Implementation Loop：先批准再寫碼的九步流程

## Learning goal

能背出並解釋九步實作迴圈（read → 寫 implementation prompt → 人工批准 → 照 prompt 建 → 跑 checks → 回報），並說出為什麼「先批准再寫 code」是整套工作流的核心。

## Lesson

### ⚡️ 沒有迴圈時，AI 會怎麼失敗

假設你直接對一個 AI 代理說「做一個搜尋功能」。它沒先讀任何說明，跳過規劃，直接開始寫 code。搜尋要長什麼樣、資料從哪來、排序怎麼做，全部由它自己決定，做完才回報。結果通常只有兩種。一種是最小可用（bare-minimum）版本，能跑，但和你腦中的產品對不上。另一種是超出範圍（out-of-scope）版本，多做了一堆你沒要求的頁面。兩者的共同點是：你直到它完工才看到方向，修正的成本早就付出去了。

**這個失敗不是能力問題。** 同一個代理，只要先被告知要做什麼、範圍在哪、驗收標準是什麼，往往能寫得很好。真正的問題是它替你做完了產品決策。產品該長什麼樣、該涵蓋哪些部分，這些是人的決策，不該讓代理在寫 code 的過程中順手決定。每一次放任代理自行決定，就是悄悄把一個沒人審核過的決策埋進產品裡，等它長成 code 才被發現，代價已經翻了幾倍。

### 📝 規劃是第一步，不是額外的準備

規劃（planning）排在所有步驟的最前面，它本身就是工作流的第一步。這一步先把「做什麼」寫下來，讓人在成本還小的時候就能修正方向。方向錯了，code 寫得越快，錯得越遠，所以 code 只能在一個已經被批准的計畫之後出現。這個順序是整套流程的脊椎：它把決策和執行分開，讓每一件大事都先經過人這一關。

你可以把規劃想成寫購物清單。進超市前先列好要買什麼，才不會順手拿下一堆用不到的東西，最後結帳才發現買錯。**為什麼規劃很重要？** 因為它把「想清楚」放在「動手做」之前，而想清楚的成本，永遠比改 code 低得多。

### 💡 實作迴圈（Implementation Loop）這個名字

這套順序有一個名字：實作迴圈（Implementation Loop），也就是[[learn/vertex-learning-platform/elements/implementation-loop|實作迴圈 (Implementation Loop)]]。它是一個九步的迴圈，以實作 prompt（implementation prompt）當作計畫，以人工批准（approval）當作閘門。計畫負責把要做的事寫清楚，閘門負責在寫 code 之前攔住方向錯誤。整個迴圈繞一圈，是 plan → review → approve → implement → test → fix → ship 的節奏。

**為什麼閘門放在這裡這麼值錢？** 因為錯誤出現的階段決定了修復成本。錯誤在計畫階段只是一行文字，改成對的方向只要幾秒；錯誤在 code 階段是一整段重寫，改起來要花幾小時。閘門把成本的高峰從 code 之後移到 code 之前，這是整個工作流最划算的一筆交易。

而且這個迴圈不是跑一次就結束，每一個功能請求都重新繞一圈。所以它是可重複的節奏，也是可檢視的紀錄：每一圈都會留下 prompt 檔和報告，幾個月後回頭看，還能拼回當時每一項功能是怎麼被決定的。

### 🔧 九個步驟，一次看完整個迴圈

1. **讀取 AGENTS.md。** 這份操作手冊載明了角色、產品、邊界、已定決策和檢查清單。代理先讀它，工作才會有正確的上下文，後面的每一步都有依據。

2. **讀取被點名的技能（skill）與文件。** 手冊會列出該用的技能，代理照單讀取，不憑記憶猜測舊版本的寫法。技能和本地文件能把代理對工具的理解校正在最新狀態。

3. **檢視既有 code。** 代理打開相關檔案，確認系統現在的樣貌。計畫因此能建立在真實的 codebase 上，不會假設一個不存在的現況。要動哪個檔案、哪支路由、哪個元件，從這一步就能確認。

4. **只有在請求真的含糊時，問一個聚焦的問題。** 需要使用者裁量的決定，透過互動問答面板（interactive question panel）提出，絕不默默帶過。問得太多和問得太少同樣糟，所以一次只問真正卡住的點，其他靠讀文件和看 code 自行解答。能被文件解答的問題，就不值得占用你一次注意力。

5. **在 `prompts/` 資料夾寫下實作 prompt。** 內容要包含目標（goal）、讀過哪些技能（skills read）、檢視了哪些 code（code inspected）、決策與假設（decisions/assumptions）、要動的檔案（files to touch）、需求（requirements）、安全性考量（security）、驗收標準（acceptance criteria）、要跑的檢查（checks）、要做的測試（manual tests）。這份檔案就是計畫本身，也是事後可以回頭檢視的紀錄。你只要讀這一份檔案，就能知道它打算怎麼做、為什麼這樣做、做完要符合什麼才算完成。

6. **詢問 Yes/No 的批准。** 在寫任何 code 之前，把這份 prompt 交給人審，獲得明確同意才繼續。除非被告知跳過，否則這個閘門不能省。被拒絕時改的是 prompt，代價只是一行字。你回 Yes，代表你親手確認過方向，接下來的 code 就不再是代理擅自決定出來的東西。

7. **嚴格照已批准的 prompt 實作。** 只做 prompt 裡列出的內容，不加範圍，不加沒人要求的驚喜功能。已批准的計畫是界線，超出界線的衝動都該被壓下來。如果寫到一半發現計畫有問題，先停下來回去改 prompt、重新取得批准，而不是自己悄悄修正路線。計畫批准時的狀態就是你跟代理之間的約定，繞過約定就等於閘門白設。

8. **執行檢查（checks）。** 照 prompt 裡列的項目逐項跑，把真實輸出記錄下來。檢查清單在計畫階段就寫好，所以這一步沒有臨場發明的空間。型別檢查、lint、build、dev server，這些在計畫裡寫了什麼就跑什麼，輸出原封不動記下。

9. **用簡短報告收尾。** 報告很短，分三段：What I did、Test、Needs your attention。細節留在 prompt 檔裡，報告只留結論，讓人有辦法一眼判斷這次工作完成到什麼程度。你不需要重讀整份 prompt，就能決定要不要自己去驗證。

### 🧪 實作迴圈在一個具體任務上長什麼樣

以「在搜尋結果頁加一個排序控制」為例。代理先讀操作手冊，載入搜尋行為那一節的規則。接著讀手冊點名的技能，打開搜尋路由和結果頁元件，確認現在怎麼排序。它發現一個真正的含糊點：預設排序該依最相關還是最新。透過問答面板，它只問了這一個問題。你回答「最相關」。

它寫下 `prompts/add-sort-control.md`，列出目標、被檢視的檔案、決策（預設為最相關）、要動的檔案、驗收標準（排序控制正常顯示、計數保持正確）、要跑的檢查（type check、lint、build）。你讀完說 Yes。它只實作 prompt 寫到的部分，跑完檢查，最後用三條短句收尾。

**這個例子裡最貴的一次錯誤假設是什麼？** 如果沒走迴圈，預設排序猜錯會變成整段重寫；走了迴圈，它只是 prompt 裡一行字的修改。

### 🛡️ 為什麼檢查不能憑感覺回報

檢查是整套工作流的最後一道信任機制。如果代理回報「檢查通過」，但其實沒跑，它就把系統的可靠性建立在謊言上。所以規則很硬：宣稱通過的檢查必須真的跑過，回報的必須是真實輸出。完成（done）是可測量的，一個功能完成，代表它通過了所有該跑的檢查。你之所以敢信任代理寫的 code，靠的就是這道可驗證的關卡。

**同樣的道理也適用在你身上。** 當你看一份完成報告時，第一件事就是問：這些檢查是真的跑出來的嗎？把回報的內容和實際的執行結果對照，一對不上就退回重跑。這一道把關如果鬆了，前面八步的嚴謹就全部白費。

### 💬 一句話收束

把整套工作流收成一句：**計畫在鍵盤之前、批准在程式碼之前、檢查在回報之前。**
