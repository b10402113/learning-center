# Clerk 認證與安全邊界

## Learning goal

能接上 Clerk（sign-in/up、middleware）並說清「middleware 是 auth resolver 不是閘門」，以及 token 的 public/secret 分割與 server-only 邊界。

## Steps

1. [[learn/vertex-learning-platform/nodes/clerk-auth-and-boundaries/clerk-setup-and-wiring|安裝 Clerk、接上 Next.js、產生認證 UI]] — 安裝 Clerk、接入 Next.js middleware/proxy、產生 sign-in/up 路由與 header 按鈕
2. [[learn/vertex-learning-platform/nodes/clerk-auth-and-boundaries/middleware-as-resolver|Middleware 是 Auth Resolver，不是閘門]] — 理解 middleware 解析認證狀態但不阻擋路由（after step 1）
3. [[learn/vertex-learning-platform/nodes/clerk-auth-and-boundaries/token-security-boundaries|Token 安全邊界與 Server-Only Auth State]] — 建立 public/secret 分割與 server-only auth state 的完整架構（after step 2）

## Lesson

認證是全端應用最複雜的子系統——session、密碼流程、OAuth、Email 驗證、JWT、middleware、路由保護、使用者檔案——每一個環節都有安全邊界案例。Clerk 把這些打包成託管服務，讓你把時間花在產品上而不是基礎設施上。但接入 Clerk 只是起點：真正重要的是理解 middleware 的 resolver 行為（它解析認證狀態，但不阻擋路由）、token 的 public/secret 分割（哪個金鑰可以出現在瀏覽器端、哪個不行），以及 server-only auth state 的架構（認證狀態只在 server 端流動，不洩漏到 client）。

這三層理解——接入、行為、邊界——構成了 Vertex 安全架構的認證層。它們和 [[learn/vertex-learning-platform/elements/server-client-boundary|Server-Client 邊界]] 共同確保：瀏覽器永遠拿不到私有 token，永遠不直接呼叫 MCP 或 LLM，永遠不寫入內容或進度。AGENTS.md 把這些規則刻進操作手冊，就是為了讓 AI 代理在實作時不會做出「能跑但危險」的決定。
