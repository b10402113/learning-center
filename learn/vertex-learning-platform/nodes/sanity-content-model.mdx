# Sanity 資料模型與 server-only 讀取層

## Learning goal

能設計 course/module/lesson/instructor/category 模型（embedded vs reference）、架 standalone Studio，並建出只跑在 server 的讀取層與 GROQ。

## Steps

1. [[learn/vertex-learning-platform/nodes/sanity-content-model/sanity-as-content-backbone|Sanity：內容管理的單一真實來源]] — 為什麼 Sanity 做的工作比任何其他工具都多，schema 如何同時決定 Studio 介面和 API 結構
2. [[learn/vertex-learning-platform/nodes/sanity-content-model/embedded-vs-reference|Embedded vs Reference：資料模型的核心設計決策]] — 何時把子資料焊死在父文件裡、何時用 ID 指向獨立文件（after step 1）
3. [[learn/vertex-learning-platform/nodes/sanity-content-model/standalone-studio-workspace|Standalone Studio：把管理介面從 App Router 拆出去]] — 為什麼嵌入式 Studio 在 production 會崩，獨立 workspace 的架構與實作（after step 2）
4. [[learn/vertex-learning-platform/nodes/sanity-content-model/server-only-read-layer|Server-Only Read Layer：私有資料集的安全讀取與 GROQ]] — 私有資料集的 token 邊界、server component 的安全查詢、GROQ 的 reference 展開（after step 3）

## Lesson

Sanity 是 Vertex 的內容骨幹——它不只是一個 CMS，而是用 schema 驅動整個 admin dashboard 和 API 結構的平台。資料模型的設計從最核心的問題開始：module 該不該從 course 拆出來？答案取決於「子項目會離開父項目嗎」——module 永遠不會離開 course，所以用 embedded；lesson 有獨立路由和 slug，所以用 reference。架構上， Sanity 的官方推薦是把 Studio 拆成獨立 workspace，因為嵌入 Next.js 會造成版本衝突、依賴污染、和 typegen 失效。最後，資料集是私有的，read token 只能在 server 端使用——server-only read layer 確保瀏覽器永遠拿不到 token，server component 查好資料後再把結果傳給 client component。四步走完，從 schema 設計到安全讀取層，整條資料管線就位。
