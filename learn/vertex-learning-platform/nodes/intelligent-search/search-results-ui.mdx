# 搜尋結果頁面：四種狀態與 Cmd+K 互動

## Learning goal

能實作 `/search` 頁面——排序控制、結果卡片（lesson / video）、loading/empty/error 狀態、Cmd+K 快捷鍵，並解釋為什麼結果卡片的每一個欄位都必須來自 Sanity 而不是模型。

## Lesson

你可能以為搜尋結果頁就是「把 API 回傳的結果秀出來」。但 Vertex 的搜尋頁做了一件比「顯示」更重要的事：**它讓使用者自己判斷哪個結果最有用，而不是替使用者做決定**。

先想一個畫面：去超市買東西。你不會希望店員直接把「他覺得最好」的商品塞到你手上——你想看到一整排選項，自己比價、看成份、看評價，再決定買哪個。搜尋結果頁就是那「一整排選項」——把所有匹配結果攤開，讓你自己挑。

---

### 從首頁到搜尋頁的路徑

搜尋入口是首頁的搜尋欄。使用者輸入查詢後，系統導航到 `/search` 頁，把查詢當作 URL search params 帶過去。

```
使用者在首頁搜尋欄打 "React cache"
  ↓ 按下 Enter 或點擊搜尋
導航到 /search?q=React+cache
  ↓ /search 頁從 URL 讀取查詢
呼叫 /api/search 取得結果
  ↓
渲染結果卡片
```

為什麼導到獨立搜尋頁，不在首頁顯示結果？因為搜尋結果需要完整展示空間——排序控制、結果卡片、空狀態、錯誤處理。首頁搜尋欄是「入口」，搜尋頁才是「結果體驗」。

---

### Cmd+K 快捷鍵

搜尋欄支援 Cmd+K（Mac）/ Ctrl+K（Windows）——隨時按快捷鍵聚焦到搜尋欄，不用滑鼠點。

它是用 `useEffect` 監聽全域鍵盤事件實現的：

```
使用者按下 Cmd+K
  ↓ 全域鍵盤事件觸發
判斷：當前頁面有搜尋欄
  ↓ 聚焦到搜尋欄
使用者可以直接輸入查詢
```

為什麼 Cmd+K 重要？因為搜尋是平台「招牌功能」——使用者會一直搜。Cmd+K 讓搜尋變成「零摩擦」動作：不用找欄位、不用滑鼠、不用滾頁。搜尋不是附加功能，是核心功能。

---

### 結果卡片的兩種變體

搜尋結果有兩種卡片：影片結果（video result）和課程結果（lesson result）。共享外殼，內容不同：

| 卡片變體 | 顯示什麼 | 互動動作 | 使用者看到什麼 |
| --- | --- | --- | --- |
| **影片結果** | 課程名、模組名、單元名、縮圖、影片長度、描述、命中秒數 | 點擊後從該秒開始播 | 有時間戳的卡片，直接跳到影片那一刻 |
| **課程結果** | 主題匹配 | 點擊後開對應課程頁 | 主題匹配卡片，引導到課程詳情頁 |

兩種卡片的共同設計：

- **縮圖**：來自 Sanity 的課程封面圖或影片海報
- **標題**：來自 Sanity 的真實標題（不是模型生成的）
- **描述**：來自 Sanity 的真實描述（不是模型生成的）
- **連結**：連到真實課程頁或影片播放頁

為什麼兩種卡片？因為搜尋結果「具體性」不同——影片結果有具體時間點（「在 80 秒處提到 React cache」），課程結果只有主題匹配（「這門課跟 React 有關」）。放一起，使用者既能「跳具體時刻」，也能「瀏覽相關課程」。

---

### Loading、Empty、Error 狀態

搜尋頁不只處理「有結果」，還要處理三種異常狀態：

| 狀態 | 觸發條件 | 顯示什麼 | 使用者動作 |
| --- | --- | --- | --- |
| **Loading** | API 回應中 | 骨架屏（skeleton）——模擬卡片形狀的灰色佔位 | 等待 |
| **Empty** | API 回空結果 | 「沒有找到相關結果」+ 引導目錄頁 | 改查詢或逛目錄 |
| **Error** | API 錯誤或網路失敗 | 錯誤訊息 + 重試按鈕 | 點重試 |

Loading 用骨架屏而不是轉圈圈（spinner），因為骨架屏讓使用者「預期」結果長相——暗示「結果快出現，長得像這樣」。轉圈圈只說「系統在跑」，不告訴你「結果長怎樣」。

Empty 引導目錄頁，因為「搜不到」不代表「沒好內容」——可能只是查詢表達不同。給使用者下一步，別卡在空頁。

---

### 排序控制

結果排序預設「最相關」（most relevant），使用者可切換：

| 排序方式 | 怎麼排 | 適合什麼情境 |
| --- | --- | --- |
| **最相關**（default） | 按語義具體性排——影片結果（有時間戳）通常排前 | 大多搜尋情境 |
| **最新**（若實作） | 按內容發佈時間排 | 想找最近新增的內容 |

結果**不設上限**（no capping）——所有匹配結果都顯示。刻意設計：不想因人為限制丟掉真實結果。搜「React」有 15 支相關影片，就全顯示，使用者自己決定哪些有用。

---

### 為什麼卡片每個欄位都得來自 Sanity

這是接地機制在 UI 層的實踐。卡片的每個欄位——標題、描述、章節標籤、時間戳——都來自 Sanity 查詢結果，不是模型生成。

為什麼重要？因為使用者會靠這些欄位做決定：

- **標題**：「這門課看起來相關」→ 點擊
- **描述**：「這段影片在講 React cache 實作」→ 點播放
- **時間戳**：「80 秒開始講快取」→ 從 80 秒開始播

任一欄位是模型編的，使用者的決策基礎就崩了——點進去發現內容跟卡片描述不符。這不只是體驗問題，是信任問題。接地確保：**使用者在卡片上看到的每一行字，都能在 Sanity 資料庫找到對應的真實資料。**

---

### 影片播放的 deep-link

點影片結果卡片時，系統導到課程頁並帶 `?t=<seconds>` 參數，讓影片從命中秒數開始播。

```
使用者點影片結果卡片（命中秒數: 80s）
  ↓ 導航到 /lessons/react-cache-overview?t=80
課程頁載入
  ↓ 播放器讀取 ?t=80 參數
影片從第 80 秒開始播放
```

這是搜尋體驗的「最後一哩路」——把「搜尋結果」和「實際學習」串起來。使用者不用「找到結果 → 點進去 → 自己拖秒數」，而是直接落在教學那一刻。這是整個智慧搜尋的旗艦體驗，也是為什麼影片文件需要章節和逐字稿區塊。

---

### 搜尋品質依賴

結果頁品質還依賴一個更早的決定：種子資料品質。如果 Sanity 裡影片逐字稿亂、章節錯、主題不連貫，結果頁再漂亮也是空殼——因為它只能顯示 Sanity「真的有」的內容。搜尋品質依賴（Search Quality Dependency）就是這道理：**結果頁的上限，就是底層資料品質的上限。**

所以做搜尋 UI 前，先確認資料是好的——120 支真實 YouTube 影片、章節標記正確、逐字稿區塊可跳轉。UI 只是把資料品質「呈現」出來，它不能憑空創造品質。

---

### 總結：四種狀態，一次記住

**第一種是 Loading**——像餐廳出菜前的等待，骨架屏讓你知道菜快上、長什麼樣。

**第二種是 Empty**——像菜單上沒你要的菜，服務生不叫你空手回家，推薦你隔壁招牌菜（目錄頁）。

**第三種是 Error**——像廚房出問題，服務生說「稍等重做一盤」，按鈕就是「重試」。

**第四種是 Success**——像一整桌菜擺面前，你自己決定先吃哪道。卡片資訊全來自真實資料，你可以放心選擇。

**搜尋結果頁不只是「顯示結果」——它是「讓使用者信任結果」的舞台，而信任來自每一個欄位都紮根在真實資料裡。**
