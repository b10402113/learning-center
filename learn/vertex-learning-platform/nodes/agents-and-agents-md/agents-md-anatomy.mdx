## Learning goal

能照 15 節結構逐一解釋每節的意圖與邊界。

## Lesson

你手上有了一份專案，也裝好了 AI agent skills——但最關鍵的問題是：**AI 到底要照什麼規則做事？**

答案就是 [[learn/vertex-learning-platform/elements/agents-md|AGENTS.md 操作手冊]]。它不是 README，不是寫給人類看的專案說明，而是**專門寫給 AI agent 看的執行指令集**。AI 讀了它之後，才知道自己在這個專案裡是什麼角色、能做什麼、不能做什麼、做完怎麼報告。

在 Vertex 的案例裡，這份手冊被拆成 **15 個結構化章節**。每一節都在消滅 AI 可能犯的一類錯誤。接下來我們逐節解剖。

---

### 🎯 第 1 節：角色定義（Role Definition）

AI 的第一個決定就是「我是誰」。角色定義把 AI 定位為 **principal-level full-stack engineer**——資深等級的全端工程師，而不只是工具或助手。

**為什麼這很重要？** 角色定義決定行為姿態：

| 角色定位 | AI 行為模式 |
|---------|------------|
| 「幫手」 | 跳過規劃，直接寫 code |
| 「資深工程師」 | 先讀 AGENTS.md → 讀 skills → 問問題 → 寫 prompt → 等批准 → 才碰程式碼 |

定義為資深工程師，它就會先讀文件、再問問題、再寫 prompt、等批准——然後才碰程式碼。如果角色寫得太低（比如「幫手」），AI 會跳過規劃直接動手。

**消滅的錯誤類別：** AI 拿到任務就直接寫 code、跳過所有前置規劃。

---

### 📋 第 2 節：你在建什麼（What You Are Building）

用一段白話描述整個產品：Vertex 是一個學習平台，作者在 Sanity 裡建立課程，學習者在 Next.js 網站上觀看並搜尋。招牌功能是**智慧搜尋**——用自然語言搜影片，直接跳到被教學的那一秒。同時定義範圍邊界：只建描述到的東西，不要自己加功能。

**為什麼這很重要？** 如果這節寫得模糊（「建一個學習平台」），AI 會自己決定搜尋長什麼樣、資料模型怎麼長、哪些頁面要做。一旦它替你做了產品決策，做錯的機率極高——搜尋可能變成聊天介面、影片分析可能整段 transcript 進 request path、課程結構可能少掉 instructor 和 category。

**消滅的錯誤類別：** AI 在實作中自己做產品決策、過度發散建太多頁面、遺漏關鍵功能。

---

### 🔄 第 3 節：AI 怎麼工作（How the AI Works）

這是 [[learn/vertex-learning-platform/elements/implementation-loop|實作迴圈 (Implementation Loop)]] 的完整定義。九步迴圈：

1. 讀 AGENTS.md
2. 讀相關 skills
3. 檢查現有 code
4. 只在真的有歧義時問一個問題
5. 寫 implementation prompt（包含目標、已讀的 skills、已檢查的 code、決策、假設、要改的檔案、需求、安全考量、驗收標準、檢查清單）
6. 請求 Yes/No 核准
7. 嚴格按 prompt 實作
8. 跑檢查
9. 短報告收尾

**核心原則：** plan → review → approve → implement → test → fix → ship。Prompt 檔案就是計畫書，沒有批准就不動 code。報告用短條列，細節留在 prompt 檔案裡。

**消滅的錯誤類別：** AI 不寫計畫就動手、做完不跑測試、報告含糊或過長。

---

### 🎨 第 4 節：UI 規則（UI Rules）

AI 不是設計師。使用者提供桌面版參考截圖，AI 的唯一工作是**精確複製**——佈局、間距、字型、顏色、狀態都要一致。

**處理適配的規則：**

- 有手機版參考 → 精確複製
- 沒有手機版參考 → 合理適應（欄位堆疊、側邊欄收合）
- 優先重用現有元件和 Tailwind pattern，不要自己創造新的視覺語言

**為什麼這很重要？** AI 有「美化」的本能傾向。給它一張截圖，它可能在做得像的同時加入自己喜歡的漸層或間距。多頁面專案裡，一旦 AI 在每一頁「自由發揮」，整體 UI 會變得支離破碎。

**消滅的錯誤類別：** AI 跨頁面擅自改動設計語言、加入不在參考中的視覺元素。

---

### 📖 第 5 節：要讀哪些 skills 和文件（Skills & Docs to Use）

列出專案中已安裝的 skills（sanity-best-practices、sanity-migration、create-agent-with-sanity-context 等），明確標注每個 skill 的使用時機。

**關鍵規則：讀本地文件勝過讀記憶。** AI 的訓練資料可能已經過時，尤其是 Sanity、Clerk 等工具的 API 會有版本差異。專案裡的 `node_modules/next/dist/docs/` 有 Next.js 的最新慣例，各工具的 package docs 才是正確來源。

**不要把 tool-level 的 API 細節塞進 AGENTS.md。** 那些資訊會過時，而 AGENTS.md 在每次實作都會被讀取。

**消滅的錯誤類別：** AI 依賴過時的訓練資料猜 API 模式、把工具細節混進專案規則導致過時。
---

### 🔒 第 6 節：App 職責分工（App Responsibilities）

定義瀏覽器端和伺服器端的嚴格邊界。

**瀏覽器端永遠不做的事：**

- 不持有 private token
- 不呼叫 MCP 或 LLM
- 不寫入內容或進度

**所有寫操作都經過 server route。** Clerk 負責 auth，PostHog 負責 analytics（只用 public key），搜尋 API 是 server route 呼叫 MCP，資料存取是 server-only 的 Sanity client。

**為什麼這很重要？** 這個邊界是整個 app 的安全架構。一旦 AI 把 Sanity read token 暴露到瀏覽器端（即使只是 client component 裡的 `NEXT_PUBLIC_` 前綴誤用），資料庫就對全世界開放了。

**消滅的錯誤類別：** AI 把 server-only 的 token 或 API key 放到 client bundle、在瀏覽器端做伺服器才該做的事。

---

### 🛠️ 第 7 節：技術棧與禁止清單（Tech Stack + What NOT to Use）

**使用的工具：**

- Next.js App Router、Clerk（auth）、PostHog（analytics）
- Sanity Studio（next-sanity + @sanity/image-url + @portabletext/react）
- Tailwind with typography
- Sanity Context MCP over server-side HTTP
- Vercel AI SDK with OpenAI provider
- Zod + TypeScript

**禁止清單：**

| 禁止項目 | 原因 |
|---------|-----|
| 不裝 `@sanity/context` plugin | 可能跟不上 Sanity major 版本 |
| 不用 `text::semanticSimilarity()` | 除非確定有 embeddings |
| 不嵌入 Studio 到 web app | 架構不適合 |
| 不開 public dataset | 安全風險 |
| 不用 client-side token | 安全風險 |
| 不另起 backend framework | 重複且維護成本高 |

**為什麼這很重要？** 這些「看起來合理」的替代方案每一個都有具體的崩塌場景——沒有禁止清單，AI 會挑中其中一個。

**消滅的錯誤類別：** AI 選擇「看起來合理但實際上不適合」的替代方案。

---

### ✅ 第 8 節：已經做好的決定（Decisions Already Made）

記錄所有不該被重新討論的決定：

- **搜尋** = result cards 而非 chatbox
- **搜尋必須 grounded**（永遠不發明不存在的課程、價格、時間戳）
- **影片 intelligence** 存在獨立的 video documents 裡（TOC + timestamped chunks）
- **時間戳** 先解 chapter 再解 transcript
- **播放** 用 provider embeds + start-seconds
- **進度** keyed by Clerk user id，只經 server route 寫入
- **My Learning、通知、Notes tab** 都是展示用不建

**為什麼這很重要？** 搜尋品質和安全性完全依賴這些決定。如果 AI 重新決定「搜尋應該是聊天介面」，整個 search architecture 就要推倒重來；如果它決定「return 全段 transcript」，response 會 overflow。

**消滅的錯誤類別：** AI 在實作中新功能時重新討論已定案的架構決定。

---

### 🗂️ 第 9 節：資料模型（Data Model）

定義八大實體：

1. **Course**（頂層）：title/slug、行銷欄位、成果描述、instructor + category refs、有序 modules
2. **Module**（**嵌入物件**，不是獨立 document）：title/summary、有序 lesson refs
3. **Lesson**（document）：title/slug、video URL、poster、duration、free-preview flag、student count、Portable Text notes、key points、pro tip、resources；**不存 parent course**，靠 reverse ref 推導
4. **Instructor**
5. **Category**
6. **Video document**：id/url、chapters `{startSeconds, label}`、chunks `{startSeconds, text}`；**永遠不把整段 transcript 存成一個 field**
7. **Agent context document**：內容範圍 filter + 指令
8. **Progress record**：Clerk user id key、已完成 lessons + resume position

**為什麼這很重要？** 搜尋、頁面、路由、時間戳全部建在資料模型之上。Module 是嵌入而非 document、Lesson 不存 course、Video chunks 是短 timestamped pieces——這些看似微小的決定，每一個都會影響下游行為。

**消滅的錯誤類別：** AI 建出錯誤的關聯（例如 Lesson 存 parent course 導致雙向同步問題、Module 變成 document 導致巢狀查詢複雜度爆炸）。

---

### 📥 第 10 節：影片擷取流程（Video Ingestion）

Offline tooling 建立 video documents。三個核心動作：

1. 以影片 URL 派生 ID（去掉 datastore 不接受的字元）
2. 把 transcript 切成多個短 timestamped chunks
3. 把原始 chapter markers 變成 TOC

**核心規則：整段 transcript 永遠不進 request path。**

**Provider support 的要求：** ingestion + playback 都要 work。YouTube、Vimeo、Bunny 各自需要 caption-to-chunks ingestion、chapter source、embed seek case。重型處理在學習者需要之前就完成了，搜尋用的是已經準備好的結果。

**消滅的錯誤類別：** AI 把重型處理放進 request path、在搜尋 API 裡即時做 transcript 分析導致 timeout 或高延遲。

---

### ⚙️ 第 11 節：搜尋設定檔（Search Config Document）

一份 Sanity Context document 讓使用者不改 code 就能調整 AI 行為：

- **內容範圍 filter**：控制 AI 搜尋的範圍
- **短指令 delta**：微調 AI 的行為指令

編輯會在下次請求時生效，但 inline system-prompt 的變更需要 server restart。

**Critical rules 要雙層保障。** 同時寫在 Context document 和 inline system prompt 裡。模型跟隨 system prompt 的可靠性更高，因為 Sanity Context document 是動態注入的，而 inline system prompt 是硬編碼在程式碼裡的。兩層保障確保即使 Context 抽取失敗，核心規則仍然存在。

**消滅的錯誤類別：** AI 在搜尋時發明不存在的內容、忽略 grounding 規則，或 critical rules 只寫一層導致被覆蓋。

---

### 🔍 第 12 節：搜尋行為（Search Behavior）

定義搜尋的完整規格。幾個關鍵決定：

| 決定 | 規格 |
|-----|-----|
| 結果形式 | 完整結果頁面（不是聊天框） |
| 排序 | ranked best-first |
| 介面 | 顯示 count 和 sort control（預設 most relevant） |
| 上限 | 沒有上限 |
| 空狀態 | 指向 catalog |

**兩種結果類型：**

1. **Video result**：course/module/lesson label、thumbnail、clip length、description、matched second；action 在那個 second 開始播放
2. **Lesson result**：topic match；action 開啟 lesson

兩種都要 match 並 merge，按 specificity 排序。

**Text match 規則：** token-based——wildcard keywords、OR 多個詞、**永遠不用整段 phrase 去 match**；match Portable Text 透過 plain-text projection。Video documents 是 internal lookup——video result 總是繫到使用那支影片的 lesson。

**消滅的錯誤類別：** AI 把搜尋做成聊天介面、整段 phrase match 導致查不到、結果沒有 grounded 到實際資料。

---

### ⚠️ 第 13 節：常見陷阱（Common Traps）

幾個容易踩到的坑：

- Context MCP 需要 deployed Studio（不是本地跑就好）
- `@sanity/context` 可能跟不上 Sanity major
- semantic search 可能關著（退回 keyword wildcards）
- backtick 在 template-literal prompt 裡需要 escape
- 搜尋 route 應 cache 初始 context（指令變更需 restart）
- 永遠不 return 整段 transcript/chunks（overflow）
- dataset 是 private 的、read token server-only
- Clerk secret server-only、middleware 保護 routes
- PostHog public key browser-safe 但 private key server-only

**Client-safe vs not-client-safe 的清單特別關鍵：** Clerk publishable key 和 PostHog public key 可以放瀏覽器；Clerk secret、Sanity tokens、OpenAI keys、PostHog private key **絕對不行**。

**消滅的錯誤類別：** AI 寫出「看起來正確但實際上有安全漏洞或運作問題」的 code——這些陷阱從 code 外觀推斷不出來。

---

### 📝 第 14 節：檢查清單（Checks）

**Web 端：** type check、lint、production build（在 routes/config/server code 變更時）、dev server。

**Studio 端：** deploy Studio app（Context MCP 要求）、deploy schema、import content/config documents。

**搜尋和擷取：** 對 live MCP endpoint 做驗證。

**核心規則：永遠不要宣稱一個 check 通過了卻沒有實際跑它。** 報告真實的 output。Done 是可量化的——checks 是問責合約。

**消滅的錯誤類別：** AI 宣稱「測試通過」但沒有實際執行、跳過某些 check 細節。

---

### 🛡️ 第 15 節：不確定時（When in Doubt）

回歸最基本規則：

- 保持小範圍
- 用對的 skill
- 遵守 server/client 邊界和 private token 規則
- 精確複製提供的 UI
- 從 setup/config 取得具體值而非硬編碼
- 存 prompt 並獲得批准後才動 code
- 跑檢查、分享確切的測試步驟

**為什麼這很重要？** 當 AI 在實作中途遇到模糊地帶（比如「這個 token 應該放哪裡？」或「這個 API 要在 client 還是 server 呼叫？」），它會傾向挑一個「看起來合理」的選項。When in doubt 章節給它一個明確的重置起點，而不是讓它靠直覺猜。

**消滅的錯誤類別：** AI 在模糊地帶隨機選擇看似合理但違反安全或架構規則的方案。

## 從零寫一份 AGENTS.md 的通用方法

上述 15 節是 Vertex 的特例。如果要替自己的專案寫一份 AGENTS.md，通用方法是**從專案向外展開**：

1. **描述產品**——用一段白話。如果你寫不出來，你還沒準備好。
2. **列出使用者流程**——主要的 user journeys 是什麼。
3. **列出工具和各自存在的理由**——不是列清單，而是解釋每個工具的角色。
4. **定義邊界**——瀏覽器 vs 伺服器、offline vs request path。
5. **定義資料模型**——在寫任何 code 之前。
6. **定義主要功能的行為**——搜尋、影片、analytics 規則。
7. **定義 AI 工作流**——plan → approve → implement → test → ship。
8. **定義檢查**——可量化的 done 標準。

最大的錯誤是**模糊的靈感式描述**（「build clean code, use best practices」）——具體的、可操作的規則永遠勝過鼓勵性的空話。

## 細節校準（Detail Calibration）

AGENTS.md 要寫到多詳細？判斷標準是：**如果 AI 有可能做出危險或破壞產品的假設，就把規則寫下來**。但也不能太冗長，否則規則會被埋在文字裡。

維護的時機：**重大決定改變時更新**（路由結構、auth model、搜尋策略、資料模型、新 provider、重複出現的錯誤）；**不要為微小細節更新**——那些細節屬於 per-feature prompt files。

穩定的專案規則放在 AGENTS.md；功能特定的細節放在各功能的 prompt 檔案裡。
