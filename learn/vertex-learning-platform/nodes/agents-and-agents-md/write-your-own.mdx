# 從零寫 AGENTS.md 的八步驟完整指南

## Learning goal

能從零為自己的專案寫出一份完整的 AGENTS.md，涵蓋所有必要章節。

## Lesson

前面三步我們拆解了 Vertex 的 AGENTS.md 動詞結構——誰負責什麼（[[learn/vertex-learning-platform/elements/skills-context-separation|Skills 與 Context 的分層]]）、十五個章節各自做什麼（[[learn/vertex-learning-platform/elements/agents-md|AGENTS.md 操作手冊]]）、哪些決策要在文件裡釘死（[[learn/vertex-learning-platform/elements/decision-architecture|決策架構 (Decision Architecture)]]）。這一步是 Synthesis：把那些零件裝起來，從零寫出你自己的。

### 📝 你的準備門檻：product paragraph 測試

> 如果你寫不出一段「這產品是什麼」的白話描述，你還沒準備好。

不是詳細的 PRD，不是 README 的前半段。你只需要一段話，讓任何讀的人知道：這個產品解決什麼問題、主要流程是什麼、有什麼特別的點。

以 Vertex 為例，一段話可以是：

> Vertex 是一個線上學習平台——作者在 Sanity 後台建課程、學習者在 Next.js 網站上觀看影片和做筆記。最大的特色是智慧搜尋：用自然語言查詢，直接跳到影片的精準秒數。

如果你能寫出這段，往下走。如果卡住了，不是字數的問題——是你還沒把產品想清楚。先回去定義產品再回來。

### 🔧 八步驟法：按順序走，每步只專注一個問題

整份 AGENTS.md 不需要一次寫完。以下八個步驟，按固定順序一個一個走：

**步驟一：用白話描述產品。**

一段話，講清楚誰是使用者、做什麼事、有什麼不同。不要寫願景（vision），不要寫口號。問自己：一個完全不認識這個專案的 AI 讀了這段話，會不會知道它在做什麼？會，就過關了。

**步驟二：列出主要使用者流程。**

學員搜尋 → 觀看課程 → 完成課程 → 作者建課程。不需要列到每個邊角（edge case），只要列主要流程。目的是讓 AI 知道什麼是正常路徑、什麼是不該建的路外（out-of-scope）功能。

**步驟三：列出工具和各自存在的原因。**

不只列你用了什麼技術，還要解釋「為什麼是這個」。例如：Clerk（而不是自建認證）、Sanity（而不是直接寫入資料庫）、PostHog（而不是自架分析）。工具清單讓 AI 知道哪些 code 可以動、哪些 API 去哪裡找文件。

**步驟四：定義邊界——瀏覽器 vs 伺服器。**

哪些值可以安全地放在瀏覽器裡（publishable key、public key）？哪些絕對不行（secret key、token、OpenAI API key）？在 AGENTS.md 裡明確畫出來。以 Vertex 為例：瀏覽器不能持有 token、不能直接呼叫 MCP 或 LLM、不能寫入進度。這類規則一旦省略，AI 很容易寫出「看起來對但實際洩密」的 code。

**步驟五：定義資料模型。**

資料模型是所有其他決策的地基。課程、模組、課程單元、影片文件、進度——它們之間的關係是什麼？哪些是文件、哪些是內嵌物件（embedded object）？模組是課程內的內嵌物件，不是獨立文件；課程單元不反向存它的所屬課程。這些細節在 AGENTS.md 裡定了，AI 就不會自己猜。

**步驟六：定義主要功能的行為規則。**

搜尋應該怎麼運作（全頁結果、按相關性排序、有排序控制項）？進度怎麼追蹤（以 Clerk user id 為鍵、只透過 server route 寫入）？這些不是功能需求規格，而是「當 AI 要實作時，它必須遵守的規則」。重複的好規則在「已做的決策」章節釘死，避免每次新功能都重新解釋。

**步驟七：定義 AI 工作流。**

AI 的標準循環：先讀 AGENTS.md → 讀技能文件 → 檢查現有 code → 寫實作 prompt → 取得批准 → 才寫 code → 跑檢查 → 交報告。這是 [[learn/vertex-learning-platform/elements/skills-context-separation|Skills 與 Context 的分層]] 的實踐——把 Skills（怎麼做）和 Context（做什麼）分開。Prompt-before-code 的循環就是這條主線。

**步驟八：定義檢查和手動測試。**

Lint、型別檢查（type check）、production build、dev server、搜尋端點測試——列出來。規則只有一條：不要說「檢查通過了」但沒真的跑過。這是最後的問責合約（accountability contract）。

### 📊 詳細度校準：AGENTS.md vs per-feature prompt

一份好的 AGENTS.md 不是越長越好。這裡有個實用的判斷標準：

> 如果 AI 可能做出一個危險的或破壞產品的假設，就把那條規則寫下來。

以 Vertex 為例，三個判斷：

| 情境 | 是否放入 AGENTS.md | 原因 |
|---|---|---|
| 瀏覽器不能持有 token | ✅ 是 | 危險假設：把 Sanity token 放在 `NEXT_PUBLIC_` 環境變數 |
| 搜尋必須 grounded（不能捏造課程/價格/時間戳） | ✅ 是 | 危險假設：AI 自己猜一個不存在的課程名稱 |
| 某個 route 的 CSS 用 flexbox 而不是 grid | ❌ 否 | 不會破壞產品，只是風格偏好 |

簡單的規則：**專案級的穩定規則放 AGENTS.md；功能細節放 per-feature prompt files。** 文件過長只會讓重要規則被埋掉。

### ⚠️ 錯誤模式：什麼不該做

最大的錯誤是把 AGENTS.md 寫成一段「激勵人心的願景」而不是具體、可執行的操作規則。

| 類型 | 範例 | 效果 |
|---|---|---|
| ❌ 壞的 | 「我們要打造一個乾淨、高效、以使用者為中心的學習平台，運用 AI 提供個人化體驗。」 | 給 AI 零資訊 |
| ✅ 好的 | 「搜尋功能使用 Sanity Context MCP + LLM，結果以 result card 顯示，必須 grounded——永遠不要捏造課程名稱、價格、或時間戳。」 | 直接改變 AI 的行為 |

前者說了等於沒說；後者每一個詞都在塑造 AI 的產出。

### ⚡ 實作練習：挑一個小專案，現在就開始

拿你最近想建的一個 side project，現在就寫：

1. **Product paragraph**：一段白話描述，解決什麼問題、主要流程、特色。
2. **User flows**：列出 3-5 個主要使用者路徑。
3. **Tools**：列出你打算用的技術，以及每一個的「為什麼是這個」。

寫完之後，把 product paragraph 拿給一個不認識這個專案的人看（或假裝你是一個剛加入的 AI）。問：讀了這段話，你知道這個產品在做什麼嗎？如果會，恭喜你通過了準備門檻。如果不會，回去重寫——不是加更多字，是把你想清楚的東西寫明白。

### 💡 總結：AGENTS.md 是專案的作業系統

AGENTS.md 不是 README，也不是願景聲明。它是專案的作業系統（operating system）——給 AI 一個真正的系統來執行，而不是在每次實作時重新決定所有事情。

從產品描述開始，按照八步驟一個一個走，把危險的假設釘死在文件裡，細節度校準到「夠用但不埋人」，你的 AI 寫出來的 code 就會穩定、安全、可預期。
