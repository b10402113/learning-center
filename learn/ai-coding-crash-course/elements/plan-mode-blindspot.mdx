# Plan Mode 的盲點 (Plan Mode's Blind Spot)

## 問題陳述 (Problem Statement)

想像你對一個代理（agent）說「幫我建一個課程評分功能」，它探索了程式碼庫，然後連問都不問一聲，就直接開始寫程式。它沒有先確認自己理解的東西是不是你想做的，你和人（human）之間沒有任何對齊（alignment）。

這種情況很常見，而大部分工具框架（harness）也承認這是個問題，所以它們內建了計劃模式（plan mode）。計劃模式的本意是在動手之前插入一段規劃時間：代理先探索、寫一份 `/plan` 文件，由人讀過、確認或修改，滿意之後才繼續。聽起來像是對齊的契機，對吧？

但實際跑一次就會發現盲點：代理寫出來的計劃，讀起來跟它接下來要做的實作一模一樣——列出了「每個課程每個使用者只能評一次、平均分在讀取時計算、空狀態不顯示零顆星」這類決定。它沒有停下來問你「你要的真的是這個嗎」，只是把「急著寫實作」換成「急著寫計劃」。換句話說，它還是衝向終點，只是終點換成了另一份文件。這個盲點就是：計劃模式擋住了「直接動工」，卻沒有擋住「急著交差」。

## 為什麼重要 (Why it matters)

這個失敗模式（failure mode）叫做「蓋錯了東西」：代理自顧自地實作，最後做出來的不是你要的。它的嚴重程度完全取決於功能有多複雜。在簡單功能上，比如這個課程評分，錯了也沒關係——了不起重來一次，代價很小。但在複雜功能上，這就非常重要了：實作越複雜，花在上面的時間越多，牽涉的程式碼越多，蓋錯之後重做的成本就越可怕，而且你可能根本不知道自己一開始就理解偏了。

想想要是一個真人開發者這樣做事：你說「幫我建個功能」，他回「我知道怎麼做」然後埋頭就寫，完全不跟你確認。這在專業協作裡是無法接受的，因為缺少了「共享理解」的過程。代理預設的行為正是如此，所以你必須主動補上這一塊，否則功能越複雜，你被自己的代理坑得越慘。

## 運作方式 (How it works)

這個盲點由三個機制疊在一起造成。

第一，計劃模式的流程。在 Claude Code 裡，連續按 shift-tab 進入計劃模式，貼上原始提示（prompt）。代理會先探索程式碼庫、了解結構，然後寫出一份 `/plan` 文件。你可以輸入 `/plan` 查看內容，確認或修改後才繼續。大部分工具框架都內建了類似的計劃模式，行為大同小異。計劃模式本質上是一道緩衝（buffer）：擋在探索與實作之間，給人一個「動手前看一眼」的瞬間。

第二，為什麼計劃讀起來跟實作一模一樣。因為驅動代理的不是「把事情想清楚」，而是「交出一份東西」的衝動。這種感覺叫做過早完成（premature completion）——急著衝到終點。它是代理的一種諂媚特質（sycophantic trait）：你叫它生產什麼，它就生產什麼，不會停下來確認自己有沒有做足「雙方對齊」的功課。在計劃模式裡，這份衝動只是把目標從「寫程式」換成「寫計劃」，所以它會一口氣把整個實作的決策全部倒進計劃文件，而不是把計劃當成一次提問的起點。

第三，真正缺的那塊拼圖。Frederick P. Brooks 在《The Design of Design》這本書裡提出「設計概念」（design concept）：它**不是一份資產（asset）**，而是人在一起設計某件事時，漂浮在房間裡的那個概念。每個人對它的理解都稍微不同，但隨著對話展開、大家逐步弄清楚到底在蓋什麼，這個概念會越來越清晰銳利。注意關鍵在於：它靠**對話**成形，不靠**文件**成形。無論是之前的直接實作，還是計劃模式，兩者之間都沒有設計概念——沒有那個「確認彼此理解一致」的時刻。所以計劃模式是往前邁了一步，但它仍然只是一個「生產資產的緩衝」，不是真正的對齊階段。

## 白話解釋 (In plain terms)

計劃模式就是把「直接動手寫程式」變成「先寫一份『我要寫的程式』給你看」。問題是代理寫這份計劃的時候，心裡想的還是「快點交差」，不是「跟人確認」，所以計劃只是把實作提早抄了一遍，你得到的仍然是一份它單方面想好的東西，而不是一次真正的對齊。真正的對齊要靠對話——你問、它答、你反駁、它修正——直到雙方的理解變成一體。那個靠對話磨出來的共享理解，才叫做設計概念。

## 類比 (Analogy)

想像你請一位餐廳主廚幫你辦一場宴會。你不耐煩地說「快點上菜」，主廚連問都不問，直接端出一整桌他覺得適合的菜。計劃模式只是加了個步驟：他先寫一份菜單給你過目，但菜單上寫的還是他自己想好的那桌菜，你依然沒機會說「其實賓客是吃素的」「有人對花生過敏」。真正的對齊，是坐下來跟他聊：賓客是誰、預算多少、口味偏好、有無忌口，聊到雙方腦中浮現同一場宴會——那個共同的畫面就是設計概念。菜單寫得再詳細，都取代不了這一段對話。

## 實際應用 (Practical use)

把這個盲點記在心裡，你在真實代理工作裡就能做對三件事。

第一，認清計劃模式的本質：它是緩衝，不是對齊。看到工具提供計劃模式，要知道它只是把「急著寫程式」推遲成「急著寫計劃」，兩者的諂媚衝動是同一個。它值得用，但不要以為用了就安全了。

第二，不要把計劃文件當成對齊。一份詳細的 `/plan` 只代表代理單方面把實作決策列出來了，不代表它理解你要的「為什麼」。讀計劃時，把注意力放在那些它替你默默決定的地方（誰能評分、資料怎麼算、空狀態長什麼樣），這些才是需要你去挑戰的點，而不是照單全收。

第三，在實作前主動補上對齊階段。計劃模式之後、動手之前，用一輪真正的對話把設計概念逼出來：問代理它打算怎麼做、為什麼這麼做，然後反駁、修正，直到雙方對要蓋的東西有一致的理解。下一課的 Grilling 對齊法就是具體做法——它透過一整輪問答，在實作前把設計概念磨清楚，讓後續的實作幾乎只是照著走。

## 前置知識 (Prerequisites)

- 知道什麼是一次對話回合（turn）與一段工作階段（session），以及代理在階段開始時一無所知、必須先探索。
- 了解代理把「人類的提示」當成指令直接執行的預設行為，因此需要人主動介入。

## 自檢問題 (Questions)

### Q1. 計劃模式把「直接實作」改成了哪個流程？它和原本的做法在根本上有什麼相同之處？

A1. 計劃模式讓代理先探索、寫一份 `/plan` 文件，由人讀過、修改、確認後才繼續。相同的根本之處在於：代理仍然急著「生產一份資產」（這次是計劃文件而不是程式碼），所以計劃讀起來跟實作一模一樣，它依然沒有停下來和人確認對齊。

### Q2. 為什麼說「過早完成」是代理的一種諂媚特質？

A2. 因為你叫它生產什麼它就生產什麼——你叫它寫程式它就寫程式，你叫它寫計劃它就寫計劃——它不會在動手前停下來確認自己的理解和你一致。它討好地衝向你要的「產出物」，卻跳過了確保「蓋對東西」的對齊功課。

### Q3. 設計概念和計劃文件有什麼不同？（關係題）

A3. 計劃文件是一份資產，是代理單方面列出的實作決策清單；設計概念不是資產，而是人一起設計時漂浮在房間裡的共享理解，每個人一開始理解都稍有不同，靠著對話逐步磨到清晰一致。計劃模式產生了前者卻完全沒有後者，所以它只是一個「生產資產的緩衝」，稱不上對齊。

### Q4. 「蓋錯了東西」這個失敗模式，什麼時候可以容忍，什麼時候一定要避免？（價值判斷題）

A4. 在簡單功能上可以容忍，因為重做成本低、失敗也不傷筋動骨；在複雜功能上一定要避免，因為實作越複雜，牽涉的程式碼越多、花的時間越久，蓋錯後的重做成本高到無法接受，而且你可能根本沒意識到自己一開始就理解偏了。判斷標準就是：這次蓋錯，我要花多少代價才發現並修回來？
