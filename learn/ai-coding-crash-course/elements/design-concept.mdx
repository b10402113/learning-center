# 設計概念 (The Design Concept)

## 問題陳述（Problem Statement）

把一個功能丟給代理（agent），它會先探索（exploration）程式碼，然後立刻開始實作（implementation）——過程中完全不跟你確認它是不是在蓋對的東西。它之所以這樣，是因為代理有個傾向：你叫它產出某樣東西，它就會衝向那個東西，趕快把它做出來，這個傾向叫做過早完成（premature completion），一種帶有奉承意味（sycophantic）的特質。它不會停下來，先把「你希望它長成什麼樣」這份功課做足。

為了解決這個問題，大多數的 harness 都內建了計劃模式（plan mode）：代理先探索，寫出一份 `/plan` 計劃文件（plan document），由你審閱、修改，滿意了才繼續實作。乍看之下這是個緩衝——在探索與實作之間留一段可以對齊（alignment）的時間。但問題是：那份計劃讀起來跟實作幾乎一模一樣。代理只是把「趕著寫程式」換成「趕著寫計劃」，它仍然在衝向產出一個資產（asset），而不是停下來跟你對齊。

於是我們還是會遇到那個很常見的失敗模式：它蓋了錯的東西（build the wrong thing）。因為一份計劃文件，不等於對齊。

## 為什麼重要（Why it matters）

「先計劃再做」是句大家都點頭的話，但很容易被誤解成「先寫一份文件再做」。設計概念這個詞把它重新框起來：真正需要的不是文件，而是雙方腦中對同一件事有一致的想像。

代理蓋錯東西這個失敗模式出現得太頻繁了。在相對簡單的功能上，例如課程評分功能，蓋錯了可以容忍——重來成本低，結果也大致可接受。但在複雜的功能上，這真的非常要緊：方向錯得越晚發現，浪費的 token、時間與心力就越可觀。想像一個人類工程師只說一句「我知道怎麼蓋」，就直接動手——完全沒有對齊，也沒有發展出任何共享理解（shared understanding）。這在人類工程師身上不可接受，在代理身上同樣不可接受。

理解設計概念，你就看穿了 plan mode 的侷限：它只是一個會產出資產的緩衝，不等於對齊。真正該在實作之前發生的，是一個靠對話把共識談清楚的對齊階段（alignment phase）。

## 運作方式（How it works）

「設計概念（design concept）」這個想法出自 Frederick P. Brooks 的《The Design of Design》（Brooks 就是寫《人月神話 The Mythical Man-Month》的那位）。重點是：設計概念**不是一個資產**——不是文件、不是圖、不是任何可以交付的成品。它是當一群人在設計某樣東西時，「飄盪在房間裡」的那個概念。

每個人腦中對它的版本都稍有不同，你有一個版本，代理（或你的同事）有另一個版本。而讓它變得清晰的，是對話：隨著對話展開，隨著你們一起搞清楚到底在蓋什麼，所有人的理解開始逐步變銳利（sharpens），最後收斂成同一個共享理解。

對照一下 plan mode 做的事：它產出一個資產——那份 `/plan` 文件——而且那份文件讀起來跟實作一模一樣。換句話說，整個過程中從來沒有出現過設計概念。沒有哪個時刻是你們停下來互相確認「我們要蓋的，我們真的對齊了嗎」。代理仍然在滿足「產出資產」的衝動，只是換了形式。

所以修正的方式很直接：把那個奉承式的資產衝動（asset rush）拿掉，逼雙方進入對話。當對話真的發生，你得到的是一種跟代理更對齊的感受——像你們兩個站在同一頁上，對要蓋什麼有一致的理解。而那份理解，才是實作前該有的東西。

## 白話來說（In plain terms）

計劃模式像一個「仍然在趕路」的緩衝區：它只是把一種資產（程式碼）換成另一種資產（計劃），卻始終沒有停下來確認你跟它講的是不是同一件事。設計概念就是那份「我們講的是同一件事」——它不存在於紙面上，而是存在於對話裡。文件可以寫得很詳細、讀起來完全像實作，但如果你從頭到尾沒跟對方談過，那份文件只是代理自言自語的筆記，不是你們共同的設計。

## 類比（Analogy）

想像你要蓋一間房子。你寫了一份規格書交給營造商：「三間臥室、一個廚房、一個車庫」，然後就交給他了。營造商照著規格蓋——但蓋出來你才發現：你想要的廚房是開放式中島、臥室要有一面採光好的窗、車庫其實是要改成書房。規格書裡全都有「廚房」「車庫」這些字，卻沒有捕捉到你腦中真正的想像。

規格書就是那份 `/plan` 文件——它看起來很完整，卻不包含設計概念。唯有當你跟營造商坐下來談：「你說『採光好』是什麼意思？」「你希望進門先看到什麼？」——對話讓那份飄在空中的共識一點一點變銳利。到那一刻，你們才真的對齊了，蓋出來的東西才不會白費。

## 實際應用（Practical use）

把設計當成一場對話，而不是一份文件的生產流程：

- **別讓代理直接衝**。你一說「請蓋一個評分功能」，代理就會去蓋——它不會停下來確認你想要的樣貌。所以不要把「蓋」當成第一句話，把「談」當成第一件事。
- **認出 plan mode 的真面目**。它是往前走了一步，但仍只是產出資產的緩衝。當你看到 `/plan` 讀起來跟實作幾乎一樣、而且代理從頭到尾沒問你任何問題，這就是警訊：它沒有對齊，只是把將要做的事寫下來。
- **在實作前強制一段對話**。就「要做什麼（what）」與「為什麼這樣做（why）」跟代理來回問答，回答它的問題，推翻你不認同的建議。這一段對話，就是讓設計概念浮現並變銳利的過程。
- **按複雜度決定投入多少對齊**。簡單功能上，蓋錯東西可以容忍，你可以快速帶過；一旦功能複雜起來，多花在對話上的時間幾乎一定划算——因為它幫你省下的是「蓋錯整個功能」的巨大代價。

## 自我檢查（Questions）

### Q1. 設計概念（design concept）與計劃文件（plan document）在本質上有什麼不同？

A1. 計劃文件是一個資產（asset）——一份具體、靜止、可以交付的文件。設計概念不是資產，它是人設計東西時飄盪在房間裡的那個共識：每個人腦中的版本都稍有不同，只有透過對話才會越談越清晰。一份計劃文件可以寫得「讀起來就像實作」，卻完全不含設計概念，因為它從頭到尾沒有被對話打磨過。

### Q2. 為什麼 plan mode 產出的 `/plan` 文件「讀起來就跟實作一樣」反而是個警訊？

A2. 因為那代表代理仍然在衝向產出資產——它只是把原本要寫的程式，換成一份描述那段程式的文字，並沒有停下來確認彼此是不是真的對齊。計劃與實作越是一模一樣，越說明它沒有發展出共享理解（shared understanding），只是換了一種形式繼續「趕路」。

### Q3. 什麼時候「蓋錯東西」（build the wrong thing）是可以容忍的？什麼時候會很嚴重？

A3. 在相對簡單的功能上，蓋錯的代價小，可以容忍——重來成本低，結果也還算可用。但在複雜的功能上，這個失敗模式非常要緊：越晚發現方向錯了，浪費的 token、時間與心力就越大。所以越是複雜的功能，越需要在實作之前把對齊做好，而不是把希望寄託在「這次應該會蓋對」。

### Q4. 代理寫好了一份非常詳盡的計劃，卻從頭到尾沒有問你任何問題。你該不該直接讓它實作？

A4. 不該，至少該先拉回來談一輪。判斷的關鍵不是計劃夠不夠詳盡，而是它有沒有真的跟你對齊。一個問題都沒問，幾乎可以確定它沒有發展出設計概念——那份計劃只是它自言自語的筆記。把它拉回對話，就「要做什麼、為什麼這樣做」來回確認，讓共享理解先成形，再放它去實作。
