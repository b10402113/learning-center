# System Prompt 贅肉 (System Prompt Bloat)

## Problem Statement

代理（agent）的 system prompt 不是抽象背景，而是每次 request 都會一起送出的真實負擔。只要某個設定、工具定義、workflow、skill、artifact 或 connector 仍被放在系統提示裡，它就會在之後每一輪請求中反覆佔用 token，即使你根本不會用到它。

問題在於，這些內容很容易以「反正先留著」的方式一路堆積。結果是還沒開始做真正工作，context window 就已經被預先吃掉很大一塊。課程示範裡，單是 `.claude/settings.json` 內預設啟用的項目，就把初始 context 推到極高水位；而其中相當大一部分，其實只是你現在完全不需要的能力定義。

## Why it matters

System prompt 贅肉會同時傷害品質與效率。首先，它縮小了你真正可用的聰明區（smart zone）：還沒開始探索 repo 或討論需求，模型的注意力就先被不相干的能力說明分走。其次，它讓每次 request 都攜帶無用負載，這些 token 不會因為「只是設定」就變免費。

更重要的是，這些浪費不是一次性的。只要某段內容還在 system prompt 裡，它就會污染每一輪後續互動。因此 system prompt 的清理不是小氣地省 token，而是主動收回模型的注意力與上下文空間。這也是 context hygiene 的核心：把固定成本壓低，讓真正與當前任務有關的資訊更容易被模型看見。

## How it works

處理 system prompt 贅肉的方法很直接：逐項停用你不會用的能力，並在每一步之後重新啟動 harness、檢查 `/context`，看初始 token 是否下降。課程示範是在 `.claude/settings.json` 裡做這件事，依序移除幾類固定佔位物。

第一類是 claude.ai connectors。它們會把不需要的外部連接能力帶進 system prompt，停用後 token 立即大幅下降。第二類是 workflows 與 bundled skills：如果這些流程或技能不是你這次工作要用的，它們的定義留在 prompt 裡就只是純負擔。第三類是 artifacts。若你的工作根本不需要那套產物能力，把它關掉就能立刻回收上下文。

再來是工具權限（tool permissions）。示範中特別把一串不會用到的工具直接 deny，例如 notebook edit、design system sync、cron、plan-mode toggle、push notifications、remote trigger、report findings 與 wake-up scheduling。這個動作的重要性在於：當工具被 deny，不只是「不能用」，而是它的工具定義會整段從 system prompt 消失。最後，連冗長的 `ask user question` 工具定義也被拿掉，讓初始 context 掉到兩萬 token 以下。

整個過程不是靠猜，而是靠測量：改一項、重開、跑 `/context`、看數字。於是你能知道哪些東西真的在吃 prompt，哪些停用最有回報。

## In plain terms

把 system prompt 想成你每次開會都得背進會議室的背包。裡面若塞了根本用不到的工具、手冊與表單，你每次進門都先累一遍，桌上也先被占滿一部分。清掉贅肉不是把重要東西丟掉，而是把這次不會用的東西先放回倉庫，讓你帶著更輕、更聚焦的背包進場。

## Practical use

- **逐項停用並量測**：每改一個設定就重啟 harness，再用 `/context` 檢查初始 token 變化。
- **先砍固定大戶**：優先審查 connectors、workflows、bundled skills 與 artifacts，因為它們常是 system prompt 的大塊負載。
- **deny 不用的工具**：若某工具在當前工作流程中沒有角色，直接 deny，讓它的完整定義從 prompt 裡消失。
- **把 `/context` 當儀表板**：不要憑感覺猜哪裡腫，讓數字告訴你哪個設定最值得刪。
- **把心態帶去別的 harness**：示範雖然是 Claude Code，但原則是通用的：凡是會固定注入 system prompt 的東西，都該被審計。

## Questions

### Q1. 為什麼 system prompt 裡不用的能力不只是「看起來雜」，而是真實成本？

A1. 因為它們會在每次 request 中反覆送出，持續佔用 token 與注意力；只要還留在 system prompt，就不是一次性的雜訊，而是每一輪都在付費的固定負載。

### Q2. 為什麼要在每次修改設定後重新啟動並檢查 `/context`？

A2. 因為 system prompt 贅肉的處理依賴量測，而不是直覺。重啟後再看 `/context`，才能知道剛剛停用的那項設定是否真的從 prompt 中消失，以及它回收了多少 token。

### Q3. deny 一個不用的工具，和單純「不去用它」有什麼差別？

A3. 單純不用它，工具定義仍可能留在 system prompt 中持續佔位；直接 deny，則會把那段工具定義整個移出 prompt，回收固定上下文成本。

### Q4. 這個技巧為什麼不是 Claude Code 專屬偏方？

A4. 因為原理不依賴特定產品，而是任何 harness 都有的事實：凡是固定注入 system prompt 的內容，都會影響後續每個 request。工具名稱可能不同，但審計預載能力、刪掉不用項目的心態可以直接遷移。

### Q5. system prompt 贅肉和 context hygiene 的關係是什麼？

A5. Context hygiene 的目標是讓模型把有限上下文用在當前工作上；system prompt 贅肉清理就是最前端的一步，先把每輪都會自動進場、卻沒有價值的固定負載移掉，替真正重要的探索、對齊與實作騰出空間。
