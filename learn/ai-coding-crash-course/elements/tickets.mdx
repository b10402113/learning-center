# Tickets：Agent 大小的工作分解單元

## 問題描述 (Problem Statement)

當你用 Spec（規格書）定義了大型任務的目的地之後，下一個問題是：怎麼把這份 spec 拆成 Agent 在單次 context window（上下文視窗）內能可靠完成的小塊工作？如果直接把整份 spec 丟給 Agent 執行，它會在 context window 後半段開始失憶——遺漏先前決策、重複處理已完成的部分、甚至產生相互矛盾的實作。根因在於 context window 有一個可靠的「智慧區域」（Smart Zone），位於對話前段，越往後品質越差。你需要的是把 spec 拆成 Ticket（工作票）——每張 ticket 對應一次對話、一個智慧區域、一個可交付的成果。

## 為什麼重要 (Why it matters)

Ticket 是讓 Spec 從「目的地文件」變成「可執行的實作計畫」的關鍵載體。沒有 ticket，spec 只是一份漂亮的文件，Agent 每次對話都要從頭理解全部需求；有了 ticket，Agent 每次只需要讀入 spec 和當前這張 ticket，就能精準地在智慧區域內完成工作。這種拆分讓你能用多次對話去完成一個遠超單次 context window 承載量的大型功能——作者甚至成功用過拆成 30 張 ticket 的巨型 spec。

## 運作方式 (How it works)

### 一張 Ticket 對應一個 Smart Zone

Ticket 的核心設計原則是「一張 ticket = 一次 context window = 一個智慧區域」。你在腦中先估算一次對話的智慧區域大約能承載多少 token（例如約 450k tokens），然後把 spec 拆成大小恰好塞進去的小塊。每張 ticket 就是你在這次對話中要交付的全部工作——不多也不少。

### 垂直切片 vs 水平切片

Ticket 的切分方式直接決定執行效率。

- **垂直切片（Vertical Slicing）**：目標。每張 ticket 建立在前一張 ticket 的成果之上，形成一條遞進的實作鏈。例如 ticket 1 建資料模型、ticket 2 建 API 路由、ticket 3 建前端介面——每一張都離完整功能更近一步。
- **水平切片（Horizontal Slicing）**：陷阱。Agent 天然傾向做水平切片——把同一個功能的不同面向拆成獨立 ticket，結果每張 ticket 的完成度都很低，互相之間缺乏遞進關係。例如把「留言系統」拆成「資料模型 ticket」「API ticket」「UI ticket」，但每一張都只完成了一小塊，離可用的交付物很遠。水平切片產生的 ticket 數量通常偏多，token 消耗加總容易超出預算。

人類必須在 ticket 拋出後介入判斷：ticket 數量是否合理、是否該合併、是否形成了垂直遞進鏈。

### Token 預算控制

Ticket 的數量不是越多越好，而要受 token 預算約束。例如一份 spec 產生了 10 張 ticket，估算下來需要 1.5M tokens，但你的 context window 只能承載約 450k tokens——大約 3 張 ticket 的量。這時你需要合併或重排 ticket，讓整體落在可執行的範圍內。作者指出，大約 3 張 ticket 是一個典型的合理數量，超出這個範圍通常代表切得太細了。

### 阻塞關係（Blocking Relationships）

Ticket 可以宣告阻塞關係——例如「ticket 4 被 ticket 2 阻塞」，意思是 ticket 2 必須先完成，ticket 4 才能開始。這種機制讓多張沒有互相阻塞的 ticket 可以在不同的 context window 中平行執行（parallel fan-out），大幅加速整體交付速度。例如 ticket 1（資料模型）阻塞 ticket 2（API）和 ticket 3（前端），但 ticket 2 和 ticket 3 互不阻塞，就可以分配給兩個獨立的 context window 同時進行。

### 輕量 Ticket + 豐富 Spec

Ticket 刻意保持輕量——因為父 spec 已經承載了全部的細節。Ticket 的核心內容是：做什麼（what）和驗收標準（acceptance criteria）。驗收標準是特別重要的設計：它給 Agent 一個明確的「停下來的地方」，避免它做到超出範圍或做到一半就停。Agent 看到明確的驗收標準，就知道什麼時候算「完成」。

## 白話來說 (In plain terms)

把一份 spec 想像成整棟房子的建築藍圖。Ticket 就是每天的施工任務單：「今天把 B 棟三樓的水電管線佈好」。你不需要把整份藍圖從頭讀到尾——只要帶著藍圖和今天的任務單出門，就知道今天要做什麼、做完的樣子長什麼樣。

## 類比 (Analogy)

Ticket 就像旅行的行程表（Itinerary）中的「每一天」。

- 整份行程（spec）告訴你這次旅行要去哪裡、為什麼去、住哪裡
- 每一天（ticket）是一張獨立的卡片：今天從巴黎到里昂、參觀什麼、住在哪裡
- 有些天被前面的天卡住（blocked）——你必須先到里昂，才能從里昂出發去尼斯
- 每天結束時你看一眼「今天完成了什麼」（acceptance criteria），然後收起這張卡片、拿出下一张
- 行程走完後，整份行程表就歸檔了——它完成了引導的使命

## 實際應用 (Practical use)

在實務中，使用 AI Coding Agent 時的典型 ticket workflow 是：

1. 完成 grilling session 後，呼叫 `to-spec` skill 產生 spec
2. 人類根據 token 預算把 spec 拆成 3-5 張 ticket（垂直切片）
3. 每張 ticket 寫入 Issue Tracker（如 GitHub Issues），標註驗收標準與阻塞關係
4. 逐張 ticket 開啟新對話：Agent 讀入 spec + 當前 ticket，在智慧區域內執行
5. 每張 ticket 完成後跑 code review，確認不偏離 spec
6. 全部 ticket 完成後，spec issue 關閉並封存

如果執行到一半發現方向不對，不需要慌——ticket 是可拋棄的。保留 spec（目的地）、刪除未執行的 ticket、重新 grilling session 調整 spec，然後再產生新的 ticket。這種「spec + ticket」的雙文件設計，讓改道的成本極低。

## 自檢問題 (Questions)

### Q1. 為什麼 Ticket 的數量需要人類判斷，不能完全由 Agent 自動決定？
A1. Agent 天然傾向做水平切片，會產生過多 ticket，導致總 token 消耗超出 context window 的承載上限。例如一份 spec 產生了 10 張 ticket 估算需要 1.5M tokens，但 context window 只能承載約 450k tokens（約 3 張 ticket）。人類需要根據 token 預算合併或重排 ticket，確保整體可執行。

### Q2. 垂直切片和水平切片有什麼差別？為什麼垂直切片是目標？
A2. 垂直切片讓每張 ticket 建立在前一張的成果之上，形成遞進鏈——每完成一張 ticket 都離完整功能更近一步。水平切片把同一功能的不同面向拆成獨立 ticket，每張都只完成一小塊，離可用的交付物很遠。垂直切片讓每次對話的成果可以被下一張 ticket 直接利用，大幅減少重複探索和理解的成本。

### Q3. Ticket 刻意保持輕量的設計理由是什麼？
A3. 因為父 spec 已經承載了全部的細節——ticket 不需要重複這些資訊，只需要明確說出「做什麼」和「驗收標準是什麼」。輕量 ticket 讓 Agent 快速進入狀態、不需要消化大量文件，而驗收標準則給 Agent 一個明確的「停下來的地方」，避免它做到超出範圍或做到一半就停。
