# Compaction 壓縮機制 (Compaction)

## Problem Statement

一次長時間的 AI 輔助開發會話（session），例如先做對齊（alignment）、再寫程式、最後做品質檢驗（QA），很容易累積到約十五萬五千個 token（token），也就是聰明區（smart zone）的邊緣。繼續走下去，每一輪的結果會緩慢地變差，而且更花錢：每次向模型供應商發出請求（request），都會把之前所有的 token 一起重新發送一遍，這些 token 之所以便宜，只因為它們已經被快取（cache）過，而其中很大一部分是純粹的噪音——來自一次次的檔案讀取、檔案寫入，以及檔案在不同狀態之間的來回變化。

一個直覺的解法是直接清空上下文（clear the context）。但清空是有損的（lossy）：代理（agent）會丟失當初「為什麼這樣建」的緣由，於是必須重新探索程式碼，重新建立它在上一段對話裡早已知道的東西。就算你重新提示它「我們要對剛做完的部分做 QA」，它也可以再把程式碼讀一遍、重新探索，但那已是二次探索，而且那些你曾經在 grilling 階段反覆確認過的關鍵決策，往往就此消失。換句話說，長會話的問題不是「要不要繼續」，而是「如何把會話的知識帶進下一個會話，又不會拖著一大堆噪音」。

## Why it matters

壓縮（compaction）的價值在於：讓你在長會話逼近聰明區邊緣時，不必跳進笨區（dumb zone）硬撐，也不必靠清空上下文把好不容易建立的理解全部丟掉。它把當下會話的內容榨成一張摘要，作為新會話的種子，讓你能夠一直待在聰明區裡繼續工作，跨越多個會話而不斷線。

這件事情之所以重要，是因為笨區不只是「變慢」而已。在笨區裡結果是緩慢地、一點一點地退化，而不是立即出錯，所以你很容易在不知不覺中接受品質下滑的輸出；同時每次請求都把龐大歷史重新送一遍，成本也在不知不覺中堆高。清空上下文則走向另一個極端——省錢、有完整聰明區空間，但代價是代理必須重新探索，而且會丟失「為什麼」的脈絡。壓縮是這兩者之間的第三條路：把有用的部分保留下來，把噪音過濾掉，以可控的代價換回幾乎全新的聰明區空間。

## How it works

壓縮的基本動作，是把目前會話的內容「榨乾」後放進一個全新的會話裡。這就像把之前看過的子代理（sub-agent）機制倒過來：子代理是派出去做雜事、再回報結果；壓縮則是在兩個會話之間傳遞，而這兩個會話都由你控制。會話歷史被總結成一張摘要，然後用這張摘要去啟動一個全新的會話，你可以在新會話裡繼續工作。

具體操作上，在 Claude Code 裡，`/compact` 可以帶一個選用的總結指示（summarization instruction）。這段指示非常有用，因為負責總結的也是一個大型語言模型（large language model），它需要盡量多的脈絡來判斷哪些資訊重要；你不必寫得多詳細，例如「我們接下來要對這個區域做 QA」就足夠了。另外有一個小技巧：你可以在壓縮進行時排入訊息（queue a message），這樣一旦壓縮完成，代理就會自動接著處理你排入的訊息，不必傻等。壓縮也不是某個特定工具獨有的花招，它是跨工具通用的（harness-agnostic）技術，在 claude.ai 和 ChatGPT 裡也都存在。

壓縮的實際效果可以從數字看出來：一趟約十五萬個 token 的會話，被壓到約三萬個 token（示範中實際讀出 28.3k）。它會挑出對下一個會話重要的檔案，把其中一部分「逐字」留在上下文裡，其餘的則以檔案指標（file pointer）的形式儲存，需要時再讀取。於是你在聰明區裡重新擁有了大量空間。

不過壓縮不是沒有代價。負責壓縮的代理有點像一位歷史學家（historian），回頭檢視你過去的會話並做總結——用史學的詞彙來說，原始會話裡發生的事是主要史料（primary source），也就是當時在場者的紀錄；而壓縮出來的摘要則是次要史料（secondary source），是主要史料的一份有損壓縮。任何交接（handoff）機制都有這個共同問題：只要建立次要史料，你就必然流失一些資訊，但你換來的是效率。繼續使用主要史料，你保有一切資訊，但也背著大量噪音；改用次要史料，你獲得更大的迴旋空間，卻可能丟失主要史料裡的細節與微妙之處。這是一個資訊與效率之間的取捨（trade-off），遺失細膩度就是付出的價格。

正因為如此，壓縮最穩妥（cast-iron）的用途，是對一件已經完成的工作做 QA。到了 QA 階段，程式已經寫完、決策也已經落地，你需要的不是重演當時的推理過程，而是一張能讓代理知道「這個專案長什麼樣、做了哪些事」的可靠地圖，所以這個情境幾乎總是用壓縮的好時機。

## In plain terms

白話來說：長會話像一張寫滿了筆記、畫滿塗鴉的紙，有用的資訊和無意義的塗鴉混在一起。繼續在舊紙上寫，紙快滿了、字越寫越小、塗鴉越看越亂；把紙丟掉換新的，你就忘了先前想通的事情。壓縮就是請人把這張紙重新謄寫成一張乾淨的新紙：只留重點、刪掉塗鴉，讓你既保留知識，又有一張幾乎全新的紙可以繼續寫。

## Analogy

可以把壓縮想成一位歷史學家為一段事件寫史書。事件的當事人在現場留下的紀錄是主要史料——資訊完整，但雜亂、重複、夾雜大量枝節；史學家據此寫出的史書是次要史料——簡潔、有條理、好讀，但必然在篩選與濃縮的過程中遺失了現場的一些細節。當你繼續使用原始會話，就像直接翻閱當事人凌亂的筆記；當你壓縮後開啟新會話，就像捧著一本寫得清清楚楚的史書。史書不能替代原始證據，但對於「接下來該做什麼」的判斷，史書往往更實用。壓縮就是這種「把現場紀錄轉成史書」的動作，你付出的代價是細節，換來的是清晰與空間。

## Practical use

- **在階段的交界處壓縮**：在 grilling、實作、QA 這類階段的交界點做壓縮，而不是在實作途中隨機壓縮。中途壓縮可能讓代理迷失方向、忘掉剛討論過的事情，甚至在壓縮前後改變程式寫法。
- **給出總結指示**：啟動 `/compact` 時，附上一句話說明接下來要幹嘛（例如「接下來要做 QA」）。因為總結者是模型，它需要這份脈絡才能知道什麼該留、什麼該丟。指示不需要詳細。
- **排入訊息節省等待**：壓縮完成後你通常要接著下指令，與其乾等，不如先排入（queue）下一則訊息，讓代理一壓縮完就自動繼續。
- **用於 QA 已完成的成品**：這是最穩妥的用途。成品完成後，上下文裡塞滿的是實作過程的噪音，而 QA 只需要「專案長什麼樣、做了什麼、有哪些約定」這類地圖式知識——壓縮後的摘要正好提供這些，而且幾乎不會損失 QA 需要的資訊。
- **把壓縮當預設選項**：在階段的交界點，如果還想在同一個目錄、同一個代理裡繼續，壓縮通常是比「清空上下文」更保險的選擇：你保留了「為什麼」，也留下了空間。

## Prerequisites

- [[learn/ai-coding-crash-course/elements/grilling|Grilling 對齊法 (Grilling)]]：了解一次對齊會話會累積多少上下文，以及「為什麼」脈絡的價值。
- 上下文（context）與上下文窗口（context window）的概念：模型每輪請求都會把所有歷史 token 一起送出，空間有限、超出會報錯。
- 聰明區（smart zone）與笨區（dumb zone）：知道上下文占用越多、品質越低、成本越高。
- 會話（session）與輪次（turn）的詞彙：知道一次會話由多輪互動組成，以及子代理在「另一個會話」裡工作的概念。

## Connections

- [[learn/ai-coding-crash-course/elements/handoff|Handoff 跨代理交接 (Handoff)]] — 兩者都是在移動會話的狀態。壓縮留在同一個目錄、同一個代理內，交接則能跨代理、跨目錄、跨人。壓縮自動化程度高，交接較彈性但也較繁瑣——依照情境選擇。

## Questions

### Q1. 為什麼「繼續在同一個會話裡工作」到了聰明區邊緣會變糟？

A1. 因為每次向模型發出請求都會把所有歷史 token 重新送一遍（雖因快取而較便宜），其中很大部分是檔案讀寫產生的噪音；結果是結果緩慢退化、成本堆高，整體效率與品質一起下滑。

### Q2. 清空上下文與壓縮有何不同？為什麼清空是「有損的」？

A2. 清空上下文會把整個會話丟掉，代理失去「為什麼這樣建」的緣由，必須重新探索程式碼，而 grilling 階段確認過的決策也一併消失；壓縮則把會話總結成次要史料，保留關鍵決策與檔案，只遺失細微的噪音與細節。兩者都有損，但壓縮把「為什麼」留下來，清空則沒有。

### Q3. 壓縮「用資訊換效率」的代價具體是什麼？何時值得付這個代價？

A3. 代價是次要史料必然是有損的——原始會話裡的細節、微妙之處可能被濃縮掉。當你正要對一件已完成的工作做 QA 時，這筆交易幾乎總是有利的：QA 需要的只是地圖式的專案知識，而摘要正好提供，遺失的多是實作過程的噪音。反之，如果你還需要重演當時的推理細節，壓縮就未必划算。

### Q4. 在 Claude Code 裡執行 `/compact` 時，為什麼要給它一段總結指示？

A4. 因為負責總結的是一個語言模型，它需要脈絡才能判斷什麼資訊重要；例如「接下來要做 QA」這樣一句話就能讓它保留對 QA 有用的內容，避免把重點濃縮掉。
