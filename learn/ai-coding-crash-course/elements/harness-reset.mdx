# 代理外殼重置 (Harness Reset)

## Problem Statement

代理外殼（harness）會在真正收到工作指令前，先把內建技能、專案設定、MCP 工具與其他整合載入上下文。這些內容即使與目前任務無關，也會佔用上下文窗口，讓代理更快接近聰明區的邊界。上下文一旦塞入太多雜訊，每一次後續請求都會帶著這些負擔，結果品質就可能下降。

課程要求使用乾淨的外殼，原因不是要把費用壓到最低，而是要保留更多空間給真正重要的程式碼、需求與推理。示範中，重置前用 `/context` 看到約 23k token，包含內建技能、專案內容與 claude.ai MCP 工具；移除多餘設定與技能後只剩約 6.6k，取回約 17k token 的工作空間。

## Why it matters

上下文衛生（context hygiene）直接影響代理能否留在高品質的聰明區。固定載入的內容越多，代理就越需要在當前問題與無關規則之間分配注意力。這些內容也會被帶進後續請求，所以浪費不是只發生在啟動時。

乾淨基線還能讓課程中的結果比較可靠。課程不會使用學習者原本的預設設定；如果每個人的外殼都帶著不同的技能、連接器與自訂規則，就很難知道差異來自課程方法，還是來自外殼本身。先重置並測量基線，可以把環境噪音和學習內容分開。

## How it works

重置的核心是先備份，再暫時移開會造成膨脹的設定，而不是直接刪除它們。在 Claude Code 中，可以把 `.claude/settings.json` 改名為 `settings-backup.json`，也把 `.claude/skills` 改名為備份名稱，讓外殼回到預設狀態。這樣原有設定仍然保留，之後可以逐項放回或比較差異。

完成重置後，用 `/context` 檢查目前的 token 基線。這個數字會因外殼、帳號和已啟用的整合而不同，因此示範中的 6.6k 不是所有人的固定目標。重要的是觀察哪些內容在沒有輸入實際任務前就已經存在，以及重置前後回收了多少空間。

如果基線仍然異常膨脹，就逐項審核設定、技能與整合，而不是猜測。不同外殼的處理方式可能不同；課程提供其他外殼的指引，遇到難以移除的膨脹也可以尋求該工具社群的協助。

## In plain terms

代理外殼像一個工作背包。背包裡的工具越多，不代表每次工作都做得越好；如果塞滿今天用不到的工具，真正需要的東西反而難以找到。重置就是先把原有物品整理到備用袋，再只帶著乾淨、必要的工具開始工作。

## Practical use

- **先備份再重置**：把 `.claude/settings.json` 和 `.claude/skills` 改成備份名稱，保留恢復原環境的能力。
- **用 `/context` 建立基線**：在還沒有輸入真實任務前檢查 token 使用量，記錄外殼預先載入了什麼。
- **比較重置前後的差異**：不要只看總數，也要確認減少的是哪些技能、設定或 MCP 工具。
- **逐項處理頑固膨脹**：若重置後仍然很大，逐一停用或移開可疑來源，每次再用 `/context` 測量。
- **保留課程需要的預設**：不要為了追求最低數字而刪除外殼正常運作所需的內容；目標是品質與聰明區空間。
- **將方法轉移到其他外殼**：Claude Code 的檔名與操作不一定適用其他工具，但「備份、重置、測量、逐項審核」的流程可以沿用。

## Questions

### Q1. 為什麼要重置代理外殼？

A1. 因為外殼可能在工作開始前就載入大量無關設定、技能與工具，消耗上下文窗口並降低代理品質。重置可建立較乾淨的基線，留下更多空間給當前任務。

### Q2. 重置前為什麼要把設定和技能改名成備份？

A2. 改名可以暫時讓外殼看不到它們，同時保留原檔案。之後可以恢復、比較或逐項取回，不必用不可逆的刪除來換取乾淨環境。

### Q3. `/context` 在這個流程中有什麼用途？

A3. 它用來查看外殼在收到實際任務前已經佔用多少 token，並比較重置前後的基線。示範中的數字只是參考，因為不同外殼的預設內容會不同。

### Q4. 外殼重置和 steering 修剪有什麼差別？

A4. 外殼重置是先把整體設定與技能移開，建立乾淨起點；steering 修剪是在保留需要的引導時，逐條移除重複、過時或無作用內容。前者處理環境基線，後者處理長期規則的內容品質。

### Q5. 追求最低 token 數是不是重置的目的？

A5. 不是。目的在於最大化品質與聰明區空間，而不是單純把成本壓到最低。仍然需要的工具和引導應保留，只有無關或造成膨脹的內容才應移開。
