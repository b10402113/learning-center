# IDE 整合與 Diff 管理 (IDE Diff Management)

## Problem Statement

當 Claude Code 在終端機（terminal）裡對你的檔案做出修改時，預設的呈現方式是一段純文字的差異比較（diff），直接印在終端機輸出裡。這種 diff 沒有行號標記、沒有語法高亮、也沒有滾動檢視的便利，閱讀起來相當彆扭（awkward）。更麻煩的是，你必須在終端機裡用文字指令去接受或拒絕每一筆變更，操作節奏緩慢且容易遺漏細節。在一個實際的專案開發流程中，一個代理可能在一次對話中就改動十幾個檔案，如果每次都得在終端機裡逐一檢查 diff，效率會大打折扣。

## Why it matters

IDE 整合與 diff 管理解決的，正是「代理改了檔案，人類怎麼高效地審查」這個問題。在 AI 輔助程式碼撰寫的工作流中，人類最終要為每一行程式碼負責，所以「看清楚改了什麼」不是奢侈品，而是基本需求。如果 diff 的呈現方式讓你難以快速判斷變更是否正確，你就會花更多時間在審查上，甚至直接跳過審查——兩者都很糟糕。IDE 整合把 diff 搬進你最熟悉的開發環境（Integrated Development Environment, IDE），讓你在語法高亮、行號標記、滾動檢視的完整支援下審查每一筆變更，把審查從「在終端機裡猜」變成「在 IDE 裡像日常 review 一樣自然」。

## How it works

IDE 整合的核心機制其實很單純：Claude Code 透過一個名為 `/ide` 的指令與你的 IDE 建立連線。當你執行 `/ide` 時，它會回報目前的連線狀態，例如「已透過 Claude Code for VS Code 擴充套件連線到 Visual Studio Code」。這條連線建立之後，所有 Claude 產生的檔案修改，都會以 diff 的形式在 IDE 裡打開，而不是印在終端機上。

在 IDE 裡打開的 diff 跟你在 Git 工作流裡看到的 diff 幾乎一樣：左邊是原始版本，右邊是 Claude 提議的修改版本，行號清楚標示，語法會根據檔案類型自動高亮。你可以用滑鼠或觸控板上下滾動整個檔案，看看 Claude 做了哪些調整。最重要的是，你可以直接在 diff 視窗裡操作——點進去、手動編輯、然後儲存檔案，就等於同意了那筆變更。你也可以按「接受」（accept）一次接受全部變更，或逐筆檢查後再決定。

這個整合同時支援多種 IDE，不只是 VS Code。Cursor、Windsurf 等支援類似擴充套件機制的編輯器都能使用。但操作方式略有不同：在 VS Code 裡，diff 以編輯器分頁（editor tab）的形式打開；在其他 IDE 裡，可能以側邊欄或彈出視窗的方式呈現。核心概念都一樣——把終端機裡的文字 diff 搬到 IDE 裡的圖形化 diff。

實務上，講者強調他大約 99% 的時間都在使用這個 diff 功能，這也是他選擇在 VS Code 裡執行 Claude Code 的主要原因。如果你把 Claude Code 當成一個獨立的終端機工具來用，你會錯過這個最強大的審查介面。

## In plain terms

想像你請了一個同事幫你改一份文件，改完之後他把修改處用紅筆畫在紙上遞給你。如果你只能在遠處看那張紙（終端機 diff），你可能看不清紅筆畫在哪裡。但如果他直接把那份文件攤開在你面前的桌上，每一筆修改都用彩色標記、行號清楚標出，你就可以像日常看文件一樣，一行一行地檢查，覺得沒問題就點個頭說「好，保留」。IDE 整合做的就是這件事：把 diff 從終端機的遠處搬到你面前的桌上。

## Analogy

IDE 整合就像讓你的程式碼審查從「收到一封純文字的 email，裡面列出所有修改」變成「直接在 Google Docs 裡看到所有修改，每一筆都有紅線標記，你可以逐條接受或拒絕」。前者你需要在腦中重建上下文，後者則把上下文直接送到你眼前。在效率上，這兩者的差距就像用手寫信溝通和用即時協作工具溝通的差距。

## Practical use

以下是 IDE 整合在日常工作中的幾個典型場景：

- **日常檔案修改審查**：每次 Claude 修改檔案時，diff 直接在 IDE 裡打開，你像平常 review 同事的 pull request 一樣逐行檢查，覺得沒問題就接受。這幾乎不需要改變你現有的開發習慣。
- **快速接受加手動微調**：有時候 Claude 的修改大致正確，但有一兩行你想調整。在 IDE 的 diff 裡，你直接點進去修改那幾行，然後儲存，等於接受了整體的修改加上你的微調。不用先接受全部、再另外改——一次搞定。
- **多檔案同時審查**：當 Claude 一次改了好幾個檔案時，IDE 會在不同的分頁裡打開每個檔案的 diff。你可以按順序切換分頁、逐一審查，節奏跟你看 CI 自動跑出來的 lint diff 沒有什麼兩樣。
- **拒絕不合理的修改**：如果 Claude 的某筆修改你不想要，直接忽略它就好——不點「接受」、不儲存檔案，那個修改就不會生效。你也可以只接受某些檔案的修改，忽略其他檔案。

如果你不使用 IDE 整合，你依然可以透過終端機裡的文字 diff 來審查，只是效率會低很多，尤其在檔案數量多或修改範圍大的時候。從第一次使用 Claude Code 開始就安裝 IDE 整合，幾乎是一筆無需猶豫的投資。

## Questions

### Q1. 執行 `/ide` 之後發生什麼事？它在做什麼？
A1. `/ide` 指令會啟動或檢查 Claude Code 與你的 IDE 之間的整合連線。連線成功後，所有 Claude 產生的檔案修改都會以 diff 的形式在 IDE 裡打開，而不是印在終端機上。它本質上是在兩個工具之間架起一座橋梁，讓檔案變更的呈現和操作都在 IDE 的環境裡完成。

### Q2. 為什麼 diff 管理被認為是 IDE 整合最重要的功能？
A2. 因為在 AI 輔助開發的工作流中，人類最終要為每一行程式碼負責。diff 管理讓你用最高效的方式審查每一筆變更——語法高亮、行號標記、滾動檢視、點擊接受或拒絕——把審查從在終端機裡逐字讀文字 diff，變成在 IDE 裡像日常 code review 一樣自然。講者強調他 99% 的時間都在使用這個功能。

### Q3. 不裝 IDE 整合也能用 Claude Code 嗎？有什麼差別？
A3. 可以。不裝 IDE 整合時，Claude 產生的檔案修改會以純文字 diff 的形式印在終端機裡。你依然可以用文字指令去接受或拒絕變更，但閱讀體驗差很多——沒有語法高亮、沒有行號標記、不方便滾動。在修改範圍小的時候還可以接受，但在多檔案、大範圍修改時，效率會明顯下降。

### Q4. 如果我的 IDE 不是 VS Code，還能用 IDE 整合嗎？
A4. 可以。IDE 整合支援多種編輯器，包括 Cursor、Windsurf 等。不同 IDE 的擴充套件名稱和安裝方式可能不同，但核心功能——在 IDE 裡打開 diff 並接受或拒絕變更——是一致的。你只需要確認你的 IDE 有支援對應的擴充套件。

### Q5. 我可以接受部分修改、拒絕其他部分嗎？
A5. 可以。在 IDE 的 diff 視窗裡，你可以逐筆檢查每一筆變更，只接受你想要的部分。你也可以先接受全部、再手動修改其中幾行——因為 diff 視窗本身就是一個可編輯的編輯器分頁，你可以直接在裡面改，然後儲存，等於接受了整體變更加上你的微調。
