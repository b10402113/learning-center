# 上下文計數器 (Context Counter)

## Problem Statement

代理的上下文會隨著對話成長，但這個成長通常藏在介面背後。你可能只看到一句簡短的要求，實際送出的請求卻還包含系統提示、工具定義、先前訊息，以及代理在過程中讀寫檔案留下的歷史。若只能偶爾複製 log 再手動檢查，就很難在工作進行中知道上下文已經消耗多少。

問題因此不只是「上下文窗口還剩多少」，也是缺少持續的回饋。沒有即時數字時，使用者容易等到代理品質下降才發現 session 已經變得太肥；有了計數器，則可以在每次互動時觀察上下文如何累積。

## Why it matters

上下文計數器把上下文衛生從一次性的檢查，變成每個 session 都能執行的習慣。它讓你看見一個新 session 的基線，也能看見一則訊息、一次檔案讀取或一段工作流程大約增加多少 token。

課程示範中，status line 顯示約 11.7k token；送出一個簡單的「summarize this」請求後，數字上升到約 12k，約增加 300 token。這些數字不是所有外殼或設定的固定標準，但變化本身提供了重要訊號：上下文正在消耗，而且可以被觀察與管理。

## How it works

上下文計數器是放在代理介面底部 status line 的即時顯示。它會隨著對話成長更新，讓 token 使用量一直處於視線範圍內。課程中的做法是把一篇可複製成 Markdown 的設定文章交給代理，授予必要權限，再由代理在 `settings.json` 加入 `status_line` 指令。

設定完成後，不需要每次手動查看 request log。當你提出要求、讀入資料或讓代理繼續工作時，status line 會更新目前的上下文計數。這個計數器本身可以自訂，但課程刻意維持簡單，目的是提供穩定、低干擾的監測，而不是再加入一套複雜儀表板。

計數器不會自動替你清理上下文，也不會直接判斷某個數字一定代表失敗。它的作用是把趨勢暴露出來，讓你結合任務複雜度與代理表現，決定是否需要重置、清理或採取其他上下文管理動作。

## In plain terms

上下文計數器就像車上的里程表。它不會替你保養車子，也不會告訴你每一條路該不該走，但它讓你知道已經跑了多遠。看到數字持續上升，你就能在車子開始出問題前，先決定是否要停下來整理行李或換一段路線。

## Analogy

可以把 session 想成一張會議桌。每次新增訊息、工具結果或檔案內容，都像把更多紙張放到桌上。上下文計數器是一個一直亮著的桌面面積指示器，讓你不必等桌面完全被紙張覆蓋，才發現已經沒有空間分辨重點。

## Practical use

- **先觀察基線**：新 session 開始時記下 status line 的 token 數，知道外殼在真正工作前已經載入多少內容。
- **觀察增量**：完成一個簡單請求後比較數字變化，建立不同類型工作對上下文消耗的直覺。
- **把計數器保持簡單**：只顯示足以支援判斷的 token 數，避免監測工具本身變成新的上下文或操作負擔。
- **結合品質觀察**：不要只盯著數字，也要留意代理是否開始遺漏重點、重複探索或回應變差。
- **在階段邊界採取行動**：當上下文持續膨脹且即將影響工作時，依任務需要考慮重置或其他上下文管理方式，而不是等到代理明顯失準。
- **把數字當作訊號而非硬門檻**：不同 harness 的 status line、系統提示與工具設定不同，示範中的 11.7k 與 12k 只能用來理解變化，不能當成普遍標準。

## Questions

### Q1. 上下文計數器解決了什麼問題？

A1. 它把原本需要手動複製 log 才能查看的上下文消耗，變成 status line 上持續可見的即時訊號，讓使用者能在 session 變得過於龐大前察覺趨勢。

### Q2. 課程示範中，簡單的「summarize this」請求讓 token 數發生了什麼變化？

A2. status line 從約 11.7k token 上升到約 12k，約增加 300 token。重點是觀察增量，而不是把這些數字當成所有環境的固定標準。

### Q3. 上下文計數器會自動清理或壓縮 session 嗎？

A3. 不會。它只顯示上下文正在如何成長；使用者仍要根據任務、上下文趨勢與代理品質，決定是否重置、清理或採取其他管理方式。

### Q4. 為什麼計數器應該保持簡單？

A4. 目的是提供低干擾、持續可見的監測。如果儀表本身過於複雜，就可能增加操作負擔，偏離「讓上下文消耗容易被察覺」的目的。

### Q5. 看到 token 數變大時，是否代表一定要立刻重置？

A5. 不一定。數字是訊號，不是硬門檻。應同時觀察任務的複雜度與代理表現，判斷上下文是否已經帶來遺漏、重複探索或品質下降，再選擇合適的處理方式。
