# 注意力退化與 Smart Zone

## Problem Statement

AI coding agent 的 context 越長，不代表它就越聰明。每次 model provider request 都會把 system prompt、工具定義、對話、tool call 與 tool result 等內容送給模型；當這些內容不斷累積，模型需要在更多 token 之間維持更多關係，注意力便會逐漸退化。

這造成一個實務矛盾：context window 可以容納一百萬 tokens，卻不表示代理能在整個窗口裡維持同等品質。複雜的規劃、探索與實作需要模型仍處於能辨認重點、連結相關資訊的 **Smart Zone**；context 過大後，代理會進入 **Dumb Zone**，速度變慢、判斷變差，而且每次請求的 token 成本也更高。

## Why it matters

注意力退化會直接影響你交付功能的可靠性。代理可能仍然回覆、仍然執行工具，卻開始遺漏早先的限制、混淆檔案間的關係，或對已經存在的資訊做出不忠實的推論。這種下降通常是緩慢的，不會在某一個 token 數突然斷崖式失效，所以人很容易在品質已經下降後才發現問題。

對 coding workflow 而言，能容納多少內容只是容量問題；能否在內容很多時持續做出好決定，才是工作的瓶頸。把 session 留在 Smart Zone，通常同時改善品質、延遲與成本。

## How it works

Attention mechanism 需要處理 token 之間的關係。只有兩個 token 時，要追蹤的資訊包括兩個 token 與它們之間的關係。token 數增加後，關係數量近似平方成長：

- 1k tokens 約有 1M 個關係需要考慮。
- 100k tokens 約有 10B 個關係需要考慮。

這不是說模型會逐一用人類方式列出所有關係，而是說輸入規模會讓注意力分配變得更困難。context 越大，重要資訊越容易被無關內容稀釋，模型的表現便會退化；同時，較大的輸入也會提高每次 request 的 token 使用量。

因此可以把 context 粗略分成兩個工作區：

- **Smart Zone**：適合複雜規劃、深入探索、寫程式、驗證與需要跨檔案判斷的任務。
- **Dumb Zone**：仍可處理簡單操作，但不適合要求高可靠性的複雜推理與長鏈工作。

課程把目前約 **150k tokens** 視為需要提高警覺的數字，並指出這條邊界會隨模型進步而移動。它不是所有模型、所有 harness 都固定相同的硬限制，而是一個管理 session 的 paranoia number。

## In plain terms

Context 像是模型工作時的桌面。桌面放少量相關文件時，模型容易找到真正重要的內容；桌面堆滿整個專案的歷史、工具輸出與過時討論時，模型雖然「看得到」，卻更難分辨現在該依據什麼。

所以 `1M context window` 代表「最多能放多少」，不代表「放滿後仍然適合寫高品質程式」。對實務工作而言，應該主動控制 context，而不是把可用容量當成目標。

## Analogy

想像一位資深工程師坐在會議桌前。桌上只有需求、相關檔案與測試結果時，他能快速找出矛盾並做設計決策。若桌上堆了幾百份過時規格、所有歷史聊天與每次命令的完整輸出，他不會立刻停止工作，但閱讀速度會下降，也更容易引用錯誤版本。

Smart Zone 就是桌面仍然可工作的狀態；Dumb Zone 則像文件已經多到讓工程師必須花更多時間翻找，卻更容易漏掉關鍵限制。

## Practical use

- **監看 context 使用量**：把 context token 數當成 session 的健康指標，接近約 150k 時不要再把複雜工作硬塞進同一段對話。
- **在複雜階段前清理**：刪除不相關的探索輸出，或用新的 session、compaction、handoff 把必要狀態整理後再繼續。
- **把長工作切成階段**：探索、設計、實作與 review 不必全部堆在同一個 session；每個階段只攜帶下一階段需要的脈絡。
- **簡單任務才留在 Dumb Zone**：例如查一個檔案、執行單一命令或做小幅格式修改，可以接受較大的 context；跨檔案設計與除錯則應先恢復 Smart Zone。
- **不要追逐最大窗口**：評估 agent 時，觀察它在實際專案中的品質與成本，不要只看 provider 宣稱的 context window 大小。

## Questions

### Q1. 為什麼 context 越大，代理可能越不可靠？

A1. 因為模型需要在更多 token 之間分配注意力，token 間的關係近似平方成長；無關內容會稀釋重點，使模型更容易遺漏限制、混淆資訊或偏離已有脈絡。

### Q2. 1M-token context window 為什麼不等於 1M tokens 的 Smart Zone？

A2. context window 只是輸入容量上限，沒有保證模型在接近上限時仍能維持同等注意力與推理品質。實務上高品質 coding 工作需要在更小的 Smart Zone 內進行。

### Q3. 什麼是 Dumb Zone？

A3. Dumb Zone 是 context 過大後的工作區。代理通常仍能完成簡單任務，但複雜規劃、跨檔案推理與可靠驗證會逐漸變差；它是緩慢下降，不是明確斷崖。

### Q4. 約 150k tokens 應該如何使用？

A4. 把它當作目前的警戒數字，而不是所有模型的硬限制。session 接近這個規模時，應清理 context、做 compaction、建立 handoff 或開新 session，避免把複雜工作繼續堆在可能已退化的 context 中。

### Q5. 如果代理在 context 裡已經有正確資訊，卻仍然做錯，應該懷疑什麼？

A5. 應懷疑 faithfulness 問題，尤其是 context 已大到注意力退化時；先縮短或重建 context，再判斷是否仍有錯誤。若資訊根本不在 context，則應先補充來源，而不是只重試同一個 prompt。

### Q6. 為什麼管理 Smart Zone 同時能省錢？

A6. 因為每次 request 都要處理累積的 input tokens；context 越大，送出的 token 越多，成本也越高。控制不相關內容可以同時降低注意力負擔與 token 使用量。

### Q7. 在實作一個跨多檔案功能時，你會如何避免進入 Dumb Zone？

A7. 先把探索、設計與驗證分階段，保存必要結論，讓下一個 session 只載入相關規格、檔案與測試結果；並持續監看 context 數字，接近警戒線時主動交接或重置。
