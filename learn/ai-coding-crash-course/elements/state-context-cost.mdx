# Stateless Model、Stateful Harness 與環境記憶

## Problem Statement

代理在 session 中看起來像是記得先前的對話、工具結果與決策，但這種「記憶」究竟存在哪裡？如果把模型、代理外殼（harness）與工作環境混成同一個東西，就很容易對清空 session、重新開始或跨 session 協作產生錯誤期待。

真正的問題是：模型本身不會把一次呼叫的內容帶到下一次呼叫。若重要狀態只存在對話中，清除 session 後就會消失；若希望知識跨 session 留存，就必須把它保存到能持續存在的環境，例如程式碼庫與檔案系統。

## Why it matters

這個區分決定了你該把什麼交給對話、什麼寫入檔案，也決定了清理 context 是否安全。你可以清除一個過長或混亂的 session，而不必失去已經寫入檔案系統的程式碼、筆記、需求與決策。

它也能避免把代理誤當成具有長期內在記憶的同事。代理的 session 記憶有期限，環境記憶則能在新 session 中被重新探索與讀取。把 repo 當成主要記憶庫，通常比依賴額外的外掛記憶系統更直接、更可檢查。

## How it works

可以把狀態分成三層：

- **模型（model）**：完全無狀態。每次模型供應商請求都是獨立呼叫，模型不會自行保存前一次呼叫的內容。
- **代理外殼（harness）**：在 session 期間有狀態。它保存對話、工具呼叫與結果，並在下一次請求時把這些內容重新整合、整包送給模型，於是產生模型「記得」的效果。
- **環境（environment）**：具有持久狀態。檔案系統、程式碼、文件與其他寫入磁碟的產物，在清除 session 後仍然存在。

因此，當你在 session 中修改並保存一個檔案，再清除對話，檔案不會跟著消失。新的 session 仍然需要重新探索環境，因為模型不會自動知道檔案內容；但只要它讀取該檔案，就能恢復必要的工作脈絡。

所謂記憶系統，通常只是把更多狀態寫進環境的方式。它們可以增加可檢索的文件或資料，但沒有改變模型本身無狀態、harness 只在 session 內有狀態的基本結構。

## In plain terms

模型每次都像第一次見面，harness 只是把這次 session 的聊天紀錄拿給它看，檔案系統才是能長期保留東西的地方。想讓下一次的代理知道重要事情，就把事情寫下來，不要只期待它記住對話。

## Analogy

把模型想成一位每次接電話都失去上一通記憶的專家。harness 像是秘書，會在同一個工作期間保存通話紀錄，下一通電話時把紀錄重新交給專家。環境則像公司的檔案室，無論哪位專家、哪一天來工作，只要找到並讀取檔案，就能取得過去留下的資訊。

## Practical use

- **把可持續的知識寫入環境**：將需求、決策、探索結果、專案規則與待辦事項保存成清楚的檔案。
- **把 session 當成暫時工作區**：對話可以被清除、壓縮或重開，不要把唯一版本的重要脈絡留在對話裡。
- **清除前先檢查持久產物**：確認程式碼、筆記與其他需要延續的狀態已經寫入檔案系統。
- **讓 fresh session 重新探索**：新 session 不知道 repo 的完整內容，重新查看目錄與關鍵文件是恢復狀態的必要步驟。
- **優先使用可檢查的記憶**：檔案中的知識能被人閱讀、版本控制、修正與引用，比不可見的內部記憶更容易維護。

## Questions

### Q1. 模型為什麼是 stateless？

A1. 因為每次模型供應商請求都是獨立呼叫，模型不會自行保存前一次呼叫的對話或工具結果。

### Q2. harness 如何製造模型有記憶的感覺？

A2. harness 保存 session 內的訊息與工具結果，並在後續請求中把它們重新整合後送給模型。

### Q3. 清除 session 後，哪些狀態會留下來？

A3. 寫入環境的程式碼、文件與其他檔案會留下來；只存在 session 對話中的暫時狀態則會消失。

### Q4. 為什麼檔案系統可以作為跨 session 記憶？

A4. 因為檔案系統具有持久性。新的 session 雖然不會自動記得舊對話，但可以重新探索並讀取保存的檔案。

### Q5. 外掛記憶系統改變了模型的基本限制嗎？

A5. 沒有。它通常只是把可檢索的狀態加入環境，仍然需要在新的請求中載入相關資訊，模型本身依然是無狀態的。

### Q6. 重要資訊應該留在對話裡，還是寫入檔案？

A6. 只要資訊需要跨 session 延續，就應該寫入檔案或其他持久環境；對話適合承載當前工作的暫時狀態。
