# Re-grill 與 Spec 存檔：中途改道的正確做法

## Problem Statement

在 Spec-driven 開發流程中，你已經根據 Spec（規格書）拆出了一組 Tickets（工作票），正在逐一實作。但實做到一半，你發現原來的方案行不通——架構選錯了、需求理解有偏差、或某個技術假設被推翻。這時候你面對一個尷尬的局面：Ticket 已經開了，寫到一半的程式碼也已經有了，但方向明顯不對。最直覺的反應是要不要硬著頭皮做完，或者把整個專案砍掉重來。兩種做法都代價極高。

## Why it matters

中途改道是軟體開發的常態，不是例外。如果沒有明確的機制來處理這種情況，團隊往往會陷入兩個極端：要麼在錯誤的方向上浪費更多時間（因為捨不得丟掉已經拆好的 Ticket），要麼全面推倒重來造成巨大的心理與時間損耗。理解 Re-grill（重新審視 Spec）的正確做法，以及 Spec 完成後如何正確存檔，才能讓流程在遇到變化時保持靈活而不混亂。

## How it works

### Re-grill 的完整流程

當你在實作過程中發現方向錯誤，正確的做法分三步：

1. **刪除尚未實作的 Tickets**：把還沒開始做、或做到一半但明顯走錯方向的 Ticket 全部關掉或刪除。Tickets 是一次性的、可拋棄的工作單元，它們的價值在於指引實作，而不是作為歷史紀錄。不要心疼這些 Ticket。

2. **Re-grill（重新審視）Spec**：回到 Spec，重新檢視並修改。這通常意味著你要開一個新的 Grilling Session（審問會議），用同樣的壓力測試方式重新逼問 Spec 的假設與設計。你不是在「修補」舊 Spec，而是在更新目的地——把 destination 從錯誤的位置搬到正確的位置。

3. **從新 Spec 重新生成 Tickets**：根據修改後的 Spec，重新拆出一組全新的 Tickets。這些新 Ticket 會反映新的方向，你可以從目前的進度（已寫好的、仍然有用的程式碼）繼續往前推。

### 兩份文件設計的底層邏輯

整個流程之所以如此簡單，關鍵在於「Spec + Tickets」的兩份文件設計：

- **Spec 是目的地（Destination）**：它是你要去的地方，是可以修改的。當你發現目的地不對，你改 Spec 就好。
- **Tickets 是路徑指引（Turn-by-turn directions）**：它們是從目的地拆出來的導航指令。目的地都改了，舊的導航指令自然要丟掉重來。

這兩份文件的職責分離，讓你在改方向時不需要「丟掉所有工作」。你保留 Spec（修改後的版本），保留已經寫好的有效程式碼，只丟掉那些不再適用的 Tickets。你從你現在所在的位置繼續前進，而不是回到起點。

### Spec 存檔的陷阱

當一個專案（或一個階段）完成後，Spec 的處理方式也至關重要。Spec 必須**關閉並存檔**（Close & Archive），絕對不能留在本地 Repo 裡。

原因是 Spec 是一份**二級來源**（Secondary Source）——它是對程式碼運作方式的精簡投影。隨著開發推進，程式碼會自然偏離 Spec（Spec Drift）。如果把 Spec 留在 Repo 裡，AI Agent 在探索程式碼時，會優先信任那份更小、更容易掃描的 Spec，而不是真正的程式碼。這導致 Agent 基於過時的資訊做出錯誤的決斷。

正確做法是把 Spec 存到 Issue Tracker（議題追蹤器）裡，以 Closed / Archived Issue 的形式保留。好處包括：可審閱、可留言、團隊可搜尋、跨工作區持久存在，且 Agent 仍可在需要時探索它來理解實作意圖。

## In plain terms

想像你在用 GPS 導航開車。Spec 是你的目的地，Tickets 是每一轉彎的導航指令。開到一半發現目的地設錯了——你不會去重複開每一次轉彎的舊指令，你會直接改 GPS 上的目的地，然後跟著新的轉彎指令走。而到達目的地後，你會把行程紀錄（Spec）存到雲端而不是留在導航機裡，避免下次導航時被過時的路線誤導。

## Practical use

實務上，Re-grill 最常出現在以下情境：

- **技術驗證推翻假設**：實作到一半發現某個技術方案在效能或安全性上不可行，需要回到 Spec 重新評估架構。
- **需求變更**：客戶或 PM 在開發中途修改了核心需求，Spec 必須同步更新。
- **更好的解法出現**：在實作過程中對問題有了更深的理解，發現 Spec 裡的方案不是最優解。

每次 Re-grill 後，記得更新 Spec 的版本紀錄（在 Issue Tracker 裡留言或開新版本的 Issue），讓團隊可以追溯決策過程。完成後務必執行 `close & archive`，讓 Spec 退場而不是持續腐化。

## Questions

### Q1. 當你在實作 Tickets 時發現方向錯誤，應該先做什麼？
A1. 先刪除所有尚未實作（或已實作但方向錯誤）的 Tickets，然後回到 Spec 進行 Re-grill（重新審視與修改），最後再從新 Spec 重新生成 Tickets。不要硬著頭皮把錯的 Ticket 做完。

### Q2. 為什麼不能把完成的 Spec 留在 Repo 裡？
A2. Spec 是二級來源，會隨著開發推進與實際程式碼產生偏離（Spec Drift）。留在 Repo 裡會讓 AI Agent 優先信任過時的 Spec 而非真實的程式碼，導致錯誤決斷。正確做法是關閉並存檔到 Issue Tracker。

### Q3. 「兩份文件設計」（Spec + Tickets）的核心優勢是什麼？
A3. Spec 負責定義目的地，Tickets 負責導航指令。當目的地改變時，你可以只修改 Spec 並重新拆 Ticket，而不需要推倒整個專案——已經寫好的有效程式碼會被保留，你從當前位置繼續前進。
