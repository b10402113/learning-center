# Spec 文件：以 Issue Tracker 為家的目的地文件

## 問題描述

當你請 AI Agent 處理超出單次 context window（上下文視窗）承載量的任務時——例如跨多個架構層級的重構、功能大幅改寫——Agent 會在 context window 後半段開始失憶：遺漏先前討論過的決策、重複處理已完成的部分、或產生相互矛盾的實作。根本原因在於：context window 有一個可靠的「智慧區域」（Smart Zone），位於對話的前段，越往後推品質越差。把所有任務塞進一次對話裡，就像把一本完整的小說攤開在只能看清前三頁的放大鏡下閱讀。

## 為什麼重要

大型任務不可能在單次對話中可靠完成。問題不是 Agent 能力不足，而是資訊量超過了單一 context window 的可靠承載上限。要突破這個限制，你需要把「終點在哪裡」和「每一步怎麼走」拆成兩個獨立的文件，分別讓 Agent 持續參照：

- **Spec（規格書）**：定義目的地——這個任務要做什麼、解決什麼問題、預期的交付物是什麼。
- **Ticket（工作票）**：定義每一個子步驟——在一個 context window 內能完成的、明確的小塊工作。

沒有這兩份文件，Agent 在第二次對話時不記得第一次的決策，每次都在「重新理解需求」與「重複已完成的工作」之間振盪。有了它們，Agent 只需要在每次對話中讀入 spec 和當前 ticket，就能精準地在智慧區域內完成工作。

## 運作方式

### Spec 的結構與內容

Spec 是一份比需求文件更簡潔、更聚焦的文件，內容通常包含三個核心區塊：

1. **問題陳述（Problem Statement）**：精確描述使用者痛點，而不是技術實作細節。
2. **解決方案（Solution）**：你打算怎麼做，以及為什麼這個方向是對的。
3. **使用者故事（User Stories）**：從使用者角度描述完成後會有什麼體驗。

Spec 不是終極真理——它是一份 Secondary Source（二手來源）。它是對程式碼這個 Primary Source（一手來源）的「凝縮投射」。這意味著程式碼會隨著開發漂移（drift），而 spec 會逐漸過時（stale）。

### 建立 Spec 的流程

建立 spec 的方法是：先經過一場深度的 Grilling Session（質詢環節），把所有含糊之處和隱含假設都翻出來攤在陽光下；然後再根據質詢結果產生 spec。具體流程：

1. 與 Agent 進行 grilling session，把需求的每一個角落都質問清楚
2. 呼叫 `to-spec` skill，將對話內容和對程式碼的理解壓縮成一份 spec
3. 由人類判斷 spec 是否足夠「有料」——spec 必須給 Agent 足夠的資訊注入，讓它不靠額外問答也能動手

### Spec 存放在 Issue Tracker，不存本地

Spec 應該存放在 Issue Tracker（如 GitHub Issues、Jira、Linear）中，而不是本地的 markdown 檔案。原因是多方面的：

- **可跨團隊協調**：Issue tracker 是多人共享的工作介面
- **Agent 可以直接讀取**：Agent 透過 GitHub CLI（`gh`）就能在對話中拉取 spec 內容
- **可追蹤、可搜尋、可評論**：Issue 有留言功能，團隊成員可以追加討論
- **跨環境持久**：不綁定任何特定的 working directory 或 laptop
- **完成後可關閉並封存**：Issue 可以 closed + archived，保留歷史記錄但不會干擾當前工作

### 為什麼不要把 Spec 放在 Repo 裡

Spec 是二手來源，而程式碼是一手來源。隨著開發推進，程式碼會自然地偏離 spec（drift）。如果把 spec 放在 repo 裡的 markdown 檔案中，Agent 在探索程式碼時會先碰到那份更小、更容易消化的 spec，然後信任它——即使它已經過時。把 spec 存在 issue tracker 的封存 issues 中，Agent 只有在主動探索時才會去讀取，而且會以程式碼為主要參考。

### 預算控制：Tickets 的數量

一份 spec 通常會被拆成多個 ticket，每個 ticket 對應一次對話、一個 context window。但 ticket 的數量需要人工判斷——Agent 在切分工作時傾向做水平切片（horizontal slicing），把所有 ticket 的 token 消耗加總起來往往會超過預算。例如一份 spec 產生了 10 個 tickets，估算下來需要 1.5M tokens，但 context window 只能承載約 450k tokens（大約 3 個 tickets 的量）。人類需要在這一步把關，合併或重排 tickets，讓整體落在預算內。

## 白話來說

想像你要搬一間大型辦公室，不可能一次搬完。你先寫一份「搬遷計畫書」（spec）說明要搬到哪裡、為什麼要搬、搬哪些東西；然後把它拆成「今天的搬運任務」（ticket）——比如「第一趟：先把全部的桌椅搬到新辦公室 B 棟三樓」。每次出發前，你只需要讀「搬遷計畫」和「今天的任務」，不需要把整份計畫從頭讀到尾。

## 類比

Spec 就像一場馬拉松的路線圖（Route Map）。

- 路線圖告訴你終點在哪裡、沿途經過哪些地標（問題陳述與解決方案）
- 每一段賽程（ticket）就是你要在一個補給站到下一個補給站之間完成的距離
- 賽道會因為施工臨時改道（程式碼 drift），所以你到終點後，這份路線圖就完成了它的歷史使命
- 你不會帶著去年的路線圖去跑今年的比賽（spec 不應該留在 repo 裡作為未來參考）

## 實際應用

在使用 AI Coding Agent 開發功能時，典型的 workflow 是：

1. 先與 Agent 進行 grilling session，把需求的每一個細節都問清楚
2. 呼叫 `to-spec` skill 產生 spec，並寫入 GitHub Issue
3. 由人類將 spec 拆成 3-5 個 tickets（根據 token 預算），每個 ticket 寫入獨立的 Issue
4. 逐個 tickets 執行：每次新對話開始時，Agent 讀入 spec 和當前 ticket，在智慧區域內完成工作
5. 每完成一個 ticket，review + 合併
6. 全部完成後，將 spec issue 關閉並封存（closed + archived）

這套流程在作者自己的 repo 中已經累積了超過 1,200 個 closed issues，是大規模 AI 輔助開發的核心工作流。

## Questions

### Q1. 為什麼 Spec 不應該存放在 repo 中的 markdown 檔案裡？
A1. Spec 是對程式碼的二手凝縮投射。隨著開發推進，程式碼會偏離 spec（drift）。如果 spec 在 repo 裡，Agent 在探索程式碼時會先碰到這份更小、更容易消化的文件，然後信任它——即使它已經過時。把 spec 存在 issue tracker 的封存 issues 中，可以避免 Agent 被過時的二手來源誤導。

### Q2. 建立 Spec 之前必須先做什麼？為什麼？
A2. 必須先進行 grilling session（質詢環節）。Grilling session 的目的是把需求中所有含糊之處、隱含假設、邊界條件都翻出來攤在陽光下。如果跳過 grilling 直接寫 spec，spec 會包含大量未經檢驗的假設，Agent 在實作時才會發現這些假設相互矛盾，導致返工。

### Q3. 為什麼 Ticket 的數量需要人類判斷，不能完全由 Agent 自動決定？
A3. Agent 在拆分工作時傾向做水平切片（horizontal slicing），會產生過多 ticket，導致總 token 消耗超出 context window 的承載上限。例如 10 個 tickets 估算需要 1.5M tokens，但 context window 只能承載約 450k tokens（約 3 個 tickets）。人類需要根據 token 預算合併或重排 tickets，確保整體可執行。
