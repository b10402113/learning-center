# Bash 執行指令：讓 Claude Code 跑命令、讀輸出、自動除錯

## Learning goal
能用 `!` 執行 bash 命令、把輸出推進代理上下文、用 Ctrl+B 背景化長命令

## Lesson

## 📝 代理能寫代碼，但跑不了命令

你用 [[learn/ai-coding-crash-course/elements/bash-execution|Bash 執行 (Bash Execution in Claude Code)]] 之前，先搞清楚一件事：AI coding agent 本質上是個文字處理器。它能讀你的指令、改你的檔案、寫出漂亮的程式碼——但你自己去跑命令、複製貼上錯誤訊息、等它回應，這些動作它全都做不到。它是被動的，你是它的手腳。

寫程式的人都有體會：寫完一行就跑一次、根據結果修正，比一口氣寫五百行再來除錯快十倍。如果代理只會寫代碼卻不能驗證代碼，效率直接腰斬——你得不斷充當「人工轉接器」，把終端的輸出搬到它面前。

**Bash 執行**解決的就是這個問題。它是讓 AI coding agent 從被動的代碼生成器，升級為能主動形成 [[learn/ai-coding-crash-course/elements/bash-execution|回饋迴路（feedback loop）]] 的關鍵機制。寫完代碼後，代理能自動跑型別檢查、lint、測試，根據輸出結果自己修正，不需要你來回搬運錯誤訊息。

## 🔧 兩種觸發方式

Bash 執行有兩種觸發方式，核心差異是「誰決定要跑什麼命令」。

| 方式 | 怎麼操作 | 誰決定命令 | 適合場景 |
|------|---------|-----------|---------|
| 自然語言指令 | 說「跑一下型別檢查」 | 代理自己翻 `package.json` 找 script | 你只想描述目標，讓代理決定怎麼跑 |
| `!` 前綴 Bash Mode | 直接敲 `! npm run typecheck` | 你自己指定命令 | 你已經知道要跑什麼，或命令不在 scripts 裡 |

### 自然語言指令

你說「把 dev server 開起來」，代理會自己去你的 `package.json` 裡找對應的 script，判斷哪一條指令符合你的意思，然後透過 harness（外殼）呼叫 bash 工具執行。這不是盲目執行你給的字串——它先讀 `package.json`、找到 `scripts` 區塊、比對語意、再用正確的指令執行。是一個帶有理解力的過程。

### `!` 前綴 Bash Mode

在提示列（prompt line）直接輸入 `!` 加上命令，跳過自然語言的翻譯，直接在互動 shell 裡執行。命令和輸出都會顯示在畫面上，同時進入代理的 context（上下文）。

核心機制分三步：

1. 你敲的命令被送入 harness 執行
2. stdout 和 stderr（標準輸出和標準錯誤）的完整輸出被推進代理的 context
3. 代理拿到輸出後，根據內容採取行動

打個比方：自然語言指令像是你說「幫我煮一下看看」——代理自己決定怎麼煮、煮完自己嚐。`!` bash mode 則像是你直接把食譜丟過去——你告訴它跑什麼，它執行後自己評估結果。

## ⚡️ 從輸出到診斷：回饋迴路才是重點

Bash 執行真正有價值的地方，不在於「能跑命令」，而在於代理能根據輸出做出診斷。

### 一個實際例子

你在 `!` bash mode 裡跑 `npm run typecheck`。命令失敗了，輸出裡有一行：

```
Cannot find module 'zod'
```

這段錯誤訊息進入了代理的 context。代理立刻診斷出：`zod` 在 `package.json` 的 `dependencies` 裡列出來了，但沒有被安裝到 `node_modules`，所以型別檢查失敗。代理接著推薦你執行 `npm install`。

### 為什麼代理的診斷不是「猜」？

代理不是在猜問題在哪裡。它根據真實的命令輸出做出推論——看到了具體的錯誤訊息，做出了具體的診斷，提出了具體的修復建議。這就是回饋迴路的運作方式：

```
執行 → 觀察 → 診斷 → 修正 → 再執行
```

代理拿到輸出後，不只是看到一個錯誤就停下來。它會根據上下文判斷問題的根因，有時候甚至會跑額外的命令來進一步確認。例如看到 `Cannot find module 'zod'`，它可能還會去跑：

- `ls node_modules` — 確認目錄狀態
- `cat package.json | grep zod` — 確認 zod 確實在 dependencies 裡

這些後續動作都是代理根據輸出自主決定的。它不只是在跑你叫它跑的命令，而是在形成一個完整的診斷迴路。

## 🔧 長時間命令：Ctrl+B 背景執行

不是所有命令都能在幾秒內結束。`npm run dev` 這類 dev server 可能要跑好幾個小時，你不希望它佔據整個終端。

按下 **Ctrl+B** 可以把目前的命令丟到背景。機制如下：

| 步驟 | 發生了什麼 |
|------|-----------|
| 命令繼續在背景運行 | 不會被打斷 |
| 輸出不再顯示在終端上 | 被寫進一個本機檔案（local file） |
| 狀態列出現背景任務指示器 | 讓你知道有一個命令在跑 |
| 代理保留輸出檔案的路徑 | 它仍然可以根據輸出來做診斷 |

**為什麼 Ctrl+B 很重要？** 它讓你同時跑一個 dev server 和繼續在終端裡跟代理互動，兩件事互不干擾。背景化的命令輸出不會消失——它被安全地存進檔案裡，代理隨時可以去讀。即使你 Ctrl+B 了 `npm run dev`，代理仍然能在之後的對話中根據 server 的 log 診斷路由錯誤或啟動失敗的問題。

## 💡 三種方式，怎麼選？

實務上，什麼時候用哪一種？這裡有一個簡單的判斷框架：

| 指令方式 | 適合場景 | 範例 |
|---------|---------|------|
| 自然語言指令 | 你只想描述目標，讓代理決定怎麼跑 | 「幫我跑一下 lint」 |
| `!` bash mode | 你已經知道要跑什麼，或命令不在 scripts 裡 | `! git status`、`! ls -la` |
| Ctrl+B | 命令需要長時間運行，你不想終端被佔住 | `! npm run dev` → 觀察幾秒 → Ctrl+B 背景化 |

### 組合使用也很常見

你可以用 `! npm run dev` 啟動 dev server，觀察幾秒確認它跑起來了，然後 Ctrl+B 把它丟到背景，繼續在提示列裡跟代理互動說「幫我看一下 server log 有沒有錯誤」。代理會去讀背景任務的輸出檔案，根據 log 內容診斷問題。

## 💡 Bash 執行為什麼改變了代理的角色？

在沒有 Bash 執行的世界裡，AI coding agent 是「被動的代碼生成器」——你給它指令，它寫代碼，然後你得自己去驗證它寫的對不對。你是品質控制的唯一關卡，代理本身沒有能力自我驗證。

有了 Bash 執行之後，代理的角色變成了「能主動形成回饋迴路的開發夥伴」。它寫完代碼後能自己跑型別檢查、看到錯誤、診斷問題、修正代碼、再跑一次確認。這個循環不需要你介入——代理自己就能完成。你不再是品質控制的唯一關卡，而是品質控制的督導者。

這是一個根本性的角色轉變。代理從「你叫它做什麼它就做什麼」的工具，變成了「它知道做完之後要驗證、驗證不通過會自己修」的夥伴。Bash 執行就是促成這個轉變的核心機制。當你能用 `!` 把命令輸出推進代理的 context，或者用自然語言叫代理自己跑命令，代理就不再是一個只會打字的程式設計師——它變成了一個會動手做事的完整開發者。
