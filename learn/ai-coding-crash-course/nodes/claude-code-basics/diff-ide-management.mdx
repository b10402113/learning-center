# Claude Code IDE 整合：diff 審查安裝與實戰指南

## Learning goal
能安裝 IDE 整合、在 IDE 中審查並接受代理的檔案修改

## Lesson

### 📝 為什麼終端機 diff 很難用？

Claude Code 改了一個檔案，你還看得懂。改了五個檔案呢？終端機裡的文字 diff 沒有語法高亮、沒有行號，你只能在一堆 `+` 和 `-` 號之間猜「這行是新增還是刪除」。

一兩個小修改可以靠眼睛硬讀。但當 Claude 對三個檔案同時做了結構性調整，diff 在終端機裡變成一場災難——你來回捲動，最後乾脆放棄審查，直接全部接受。

**核心問題：** 終端機是文字輸出環境，天生不是拿來做 code diff 的。

| 問題 | 終端機 | IDE |
|------|--------|-----|
| 語法高亮 | ❌ 沒有 | ✅ 自動依照檔案類型著色 |
| 行號標記 | ❌ 無法對照 | ✅ 左右兩側清楚標示 |
| 檔案上下文 | ❌ 來回捲動 | ✅ 完整顯示前後文 |
| 編輯能力 | ❌ 純文字 | ✅ 可直接點進去改 |

**為什麼這個差異很重要？** 因為在典型對話中，Claude 一次可能改五到十個檔案。你花在「看懂 diff」上的時間，遠比花在「判斷修改是否正確」的時間多。前者是無謂的認知負擔，後者才是真正的工程判斷。

### 🔧 IDE 整合：把 diff 搬進你最熟悉的地方

[[learn/ai-coding-crash-course/elements/diff-ide-management|IDE 整合與 Diff 管理 (IDE Diff Management)]] 的核心思路很簡單：不在終端機裡看 diff，把 diff 搬進 IDE。

在 IDE 裡，你有語法高亮、行號、完整檔案上下文、滑鼠精確選取——你日常做 code review 的所有工具全部都在。實現這個目標的工具是 `/ide` 指令。

在 Claude Code 對話裡輸入 `/ide`，它會回報整合狀態：

```
IDE integration: connected to Visual Studio Code via Claude Code for VS Code
```

看到這條訊息，代表橋梁已經架好。從現在起，所有 Claude 產生的檔案修改都會自動在 IDE 裡打開 diff 視窗，而不是印在終端機上。

### ⚡️ 安裝步驟：3 步完成

以 VS Code 為例，安裝流程直覺快速：

1. **安裝擴充套件**：在 VS Code 的 Extensions 市場搜尋「Claude Code」，找到「Claude Code for VS Code」並安裝
2. **執行 `/ide`**：回到 Claude Code 終端機，輸入 `/ide` 確認連線
3. **確認狀態**：看到 `connected to Visual Studio Code` 就代表成功

**你用的不是 VS Code？** IDE 整合支援多種編輯器，包括 Cursor 和 Windsurf。Cursor 基於 VS Code 架構，運作方式幾乎相同；Windsurf 也是類似邏輯。你只需要確認 IDE 有安裝對應擴充套件，執行 `/ide` 確認連線即可。不同 IDE 的差異只在擴充套件名稱和安裝方式，核心功能——在 IDE 裡打開 diff 並接受或拒絕變更——完全一致。

### 💡 Diff 在 IDE 裡長什麼樣？

IDE 整合啟用後，Claude 修改檔案時的體驗完全不同。以 Claude 修改 `src/utils/helpers.ts` 為例，IDE 自動打開 diff 視窗：

- **左邊**：原始版本
- **右邊**：Claude 提議的修改版本
- **行號**：兩側清楚標示
- **語法著色**：TypeScript 型別註解是紫色、字串是綠色、函式名稱是黃色

你可以用滑鼠或觸控板上下滾動，完整看到每一筆變更的上下文。這跟你在 Git 工作流裡用 `git diff` 或在 GitHub 上看 Pull Request 的 diff 幾乎一樣——唯一的差異是，這次提出修改的不是你的同事，而是 AI 代理。

### ⚡️ 接受與拒絕：你的審查控制權

IDE 整合最關鍵的能力是讓你完全掌控每一筆變更。四種操作方式：

| 操作方式 | 做法 | 適合場景 |
|----------|------|----------|
| **逐筆審查** | 逐行檢查，點擊 Accept 同意，不點就是拒絕 | 重要檔案、不確定的修改 |
| **快速接受加手動微調** | 在 diff 視窗直接改那幾行，儲存即完成 | 大致正確但有一兩行想調 |
| **全部接受** | 一鍵接受所有變更 | 信任 Claude 或打算事後再看 |
| **拒絕** | 不點接受、不儲存，修改不生效 | 不想要的修改 |

**關鍵提醒：** 即使全部接受了，你仍然可以透過 Git 歷史記錄回頭檢查——前提是專案有做版本控制。

### 📝 為什麼講者 99% 的時間都在用這個功能？

在 AI 輔助程式碼撰寫的工作流中，diff 審查是人類參與最多、也最重要的環節。代理幫你寫程式碼，但最終你要為每一行負責。

IDE 整合把 diff 審查從「在終端機裡逐字讀文字 diff」變成「在 IDE 裡像日常 code review 一樣自然」。你有語法高亮、有行號、有完整檔案上下文、有最熟悉的鍵盤快捷鍵。講者選擇在 VS Code 裡執行 Claude Code，最大的原因就是這個 diff 功能。

**為什麼這一點值得強調？** 如果你把 Claude Code 當成一個獨立的終端機工具來用，你會錯過這個最強大的審查介面。

### 💡 實際工作流：從安裝到日常使用

讓我們把整個流程串起來：

1. **安裝 IDE 擴充套件**：在 VS Code 搜尋並安裝「Claude Code for VS Code」
2. **執行 `/ide`**：確認連線狀態
3. **正常使用 Claude Code**：對話、下指令、讓它修改檔案
4. **審查 diff**：每當 Claude 修改檔案，IDE 自動打開 diff 視窗
5. **接受或拒絕**：逐行檢查，覺得沒問題就接受，覺得需要微調就直接改
6. **繼續下一個任務**

如果你一次改了很多檔案，IDE 會在不同分頁裡打開每個檔案的 diff。你可以按順序切換分頁、逐一審查，節奏跟看 CI（Continuous Integration）自動跑出來的 lint diff 沒什麼兩樣。這種體驗讓 AI 輔助的程式碼修改不再像「黑箱輸出」，而更像「同事幫你寫了初稿，你來做最終審查」。

### ⚡️ 終端機不是不能用，只是效率差很多

不裝 IDE 整合，Claude Code 完全可以用。你依然可以透過終端機裡的文字 diff 來審查變更，修改範圍很小的時候甚至夠用。

但在實務上，Claude Code 的威力在於它能同時處理多個檔案的複雜修改，而這正是終端機 diff 最吃力的地方。從第一次使用 Claude Code 開始就安裝 IDE 整合，幾乎是一筆無需猶豫的投資。
