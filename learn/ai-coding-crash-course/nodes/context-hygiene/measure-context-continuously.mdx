# 持續測量上下文

## Learning goal

能在 AI coding agent 的每個 session 中設定並使用即時上下文計數器，建立初始基線、觀察每次互動帶來的 token 增量，並根據上下文趨勢與代理品質決定何時整理、重置或繼續工作。

## Lesson

### 先把上下文當成可觀察的工作負載

一個剛開啟的代理 session，畫面上看起來可能只有幾句話，但真正送到模型端的 request，往往已經包含很多東西：system prompt、工具定義、外殼設定、技能、先前訊息、讀過的檔案、工具結果。這些都會一起影響後續請求。所以，持續測量上下文，不是要你替每次互動做繁瑣記帳，而是要在工作進行時保留一個低干擾、但很有用的訊號。你要知道起點在哪裡，也要知道是哪一次讀檔、測試或追問，讓數字突然變大，最後再把這些數字和代理表現一起看。

最實用的做法通常是這樣：新 session 先記下基線；接著做一個可重現的小請求；之後在讀大型檔案、跑長測試，或跨到下一段工作時再看一次；如果 token 上升的同時，代理也開始遺漏、重複或混淆，再決定要整理、重置，還是繼續。這樣一來，上下文計數器就不只是顯示數字，而是真正幫你決定工作節奏的工具。

很多人會忽略一件事：你以為自己只是下了一個小指令，代理其實可能同時做了很多事。它可能讀了檔案、搜尋了程式碼、跑了指令，還把結果放進後續對話。等到回答開始漏東漏西、忘記前面講過的限制，或重複做過的探索時，你才發現這個 session 已經累積太多內容。這時問題往往不再是「要不要監測」，而是「哪些脈絡還值得留下」。

所以，第一個核心觀念很簡單：不要等出問題才看上下文，也不要只靠對話看起來長不長來猜消耗量。你需要一個一直看得到的數字，讓上下文從隱形成本變成即時訊號。這個數字就是 [[learn/ai-coding-crash-course/elements/context-counter|上下文計數器 (Context Counter)]]。

### 上下文計數器到底在量什麼

上下文計數器量的是目前這個 session 在發送請求時，會一起帶進模型的上下文規模，通常用 token 表示。token 是模型處理文字和其他輸入時使用的切分單位。它不等於字數，也不等於訊息數。一段程式碼、一份工具輸出、一個檔案內容，和一段自然語言，最後都可能變成不同數量的 token。

你可以把它想成桌上攤開的紙張數量。你說一句話，桌上多一張紙。代理讀進一個很長的檔案，可能一下多出幾十張。工具回傳大量測試輸出，又會再堆上一疊。計數器不幫你整理桌面，也不判斷哪一張比較重要，它只負責讓桌面到底變多亂、變多滿，這件事一直看得見。

這個差別很重要。計數器量的是負載，不是品質。上下文數字大，不代表回答一定錯；數字小，也不代表代理一定理解任務。真正有用的是一起觀察兩件事：token 是否持續上升，以及代理是否開始忽略限制、重複探索、搞混檔案，或提出明明已經回答過的問題。只有把數字和行為放在一起看，測量才會變成決策工具。

### 為什麼要放在 status line

如果每次都要自己去翻 request log，然後再找出上下文欄位，這件事很快就會被放棄。原因很簡單：太慢，而且會打斷工作。更麻煩的是，手動檢查通常發生在你已經懷疑哪裡不對之後，它很難幫你看見問題是怎麼慢慢形成的。

status line 是代理介面底部持續顯示資訊的一行。把上下文 token 數放在這裡，有三個直接好處。

1. 你不用離開現在的工作流，就能知道 session 變大了多少。
2. 你可以比較一次互動前後的數字，慢慢建立不同操作的消耗感。
3. 你能在品質明顯變差之前先看見趨勢，提早決定要整理還是換一個 session。

重點不是做一個很華麗的儀表板，而是把本來要額外操作才能看到的訊號，放到你每次工作都會經過的位置。監測越低干擾，越容易養成習慣。反過來說，如果每次檢查都要翻設定、開新視窗、讀一大段 log，多數人最後只會在出事後才去看它。

### 先建立你的基線

第一次用計數器時，不要急著把某個數字當成標準答案。先看一個全新的 session，在還沒要求代理做實際工作之前，status line 顯示多少 token。那就是你的基線。

這個基線本身就包含很多固定成本。不同的代理外殼、模型、系統提示、工具清單、技能設定和連接器，都可能讓起點不一樣。有些環境一開啟就載入很多工具定義；有些環境只保留最基本的 shell 和檔案操作。所以，就算兩個 session 都還沒有任何使用者訊息，它們的上下文數字也可能差很多。

建立基線時，可以順手記下下面幾件事。

| 觀察項目 | 你要知道的事情 |
| --- | --- |
| 新 session 的 token 數 | 外殼在開始工作前已經佔用了多少上下文 |
| 啟用的工具與技能 | 哪些固定內容可能在每次請求都重複出現 |
| 工作目錄與專案大小 | 代理後續探索時可能接觸到的資料範圍 |
| 代理初始回應 | 它是否在沒有讀檔前就假裝知道專案細節 |

這一步的目的，是把「我感覺上下文很多」變成一個真的可以比較的起點。之後你如果清理設定、停用不用的工具，或改變工作方式，就能回頭跟基線比較，看看效果是不是真的存在。

### 用一個小請求校準增量

有了基線之後，接著做一個很小、而且容易重現的請求。比如請代理摘要一段你已經給它的簡短內容，或請它說明目前的工作目錄。做完之後再看一次 status line，記下新的 token 數。

示範裡的數字，是從約 11.7k 上升到約 12k，增加大約 300 token。這個例子真正有價值的地方，不是 300 這個數字本身，而是你看見了一件事：就算看起來只是一次很小的互動，也會留下增量。等你把同樣的看法套到讀檔、跑測試、搜尋整個專案，還有多輪修改上，就能慢慢畫出自己的消耗地圖。

你可以像下面這樣記錄幾次操作。

| 操作 | 操作前 | 操作後 | 增量 | 可能原因 |
| --- | ---: | ---: | ---: | --- |
| 簡短摘要 | 11.7k | 12.0k | 約 0.3k | 新增訊息與代理回應 |
| 讀取小型設定檔 | 12.0k | 12.8k | 約 0.8k | 檔案內容進入對話 |
| 執行測試並回傳完整輸出 | 12.8k | 15.4k | 約 2.6k | 工具輸出佔用大量空間 |
| 重複追問同一個決定 | 15.4k | 16.1k | 約 0.7k | 新增對話與重複說明 |

表中的數字只是示意，不能直接套用到每一個模型或外殼。真正重要的是比較方法：每次操作前看一次，操作後再看一次，兩者的差距，就是這次操作在目前環境裡造成的近似增量。

### 把計數器變成工作節奏

持續測量，不代表你要在每一則訊息後都停下來做會計。那樣反而會讓監測妨礙工作。比較好的做法，是把觀察放在有意義的邊界上。

例如，session 一開始先看基線；做完一段探索再看一次；代理讀完大型檔案、跑完長測試、吐出一大段錯誤輸出，或進入多輪修正時，再看一次。你也可以在準備從分析切到實作、從實作切到測試，或者打算開始另一個獨立子任務時，把當下的數字記下來。

這樣做的好處是，你會慢慢知道哪些動作特別會吃上下文。像是只改一個函式，可能增加不多；但把整份 build log 都貼回來，可能比好幾輪簡短討論還要昂貴。如果你發現代理常常為了找一個檔案，反覆把整個目錄掃過一次又一次，也能從 token 的增量看出這種探索流程到底多花成本。

你可以把一個 session 粗分成四個觀察階段。

1. 起始階段：記錄基線，確認固定載入成本。
2. 探索階段：觀察讀檔、搜尋和工具輸出的增量。
3. 實作階段：比較每輪修改和驗證的成本。
4. 收尾階段：判斷目前脈絡是否還夠清楚，能不能直接完成 review，還是應該先整理再進下一個任務。

這套節奏不是要你精準預測未來還能再塞多少 token，而是訓練你對趨勢的敏感度。

### 讀懂上升速度

只看目前總量還不夠，還要看它是怎麼長上去的。兩個 session 都可能顯示 20k token，但其中一個是二十輪小互動慢慢累積出來的，另一個可能是在一次工具呼叫後突然暴增 8k。這兩種情況，處理方式不一定一樣。

如果增加得穩定而且幅度小，通常代表工作還在正常推進。你當然還是要留意總量，但不用每多一點就立刻中斷。相反地，如果數字突然跳很大，就值得查原因。可能是代理讀進了不必要的大檔案，工具輸出裡有一大堆重複內容，搜尋範圍沒有收斂，或某個技能把很多額外說明塞進了對話。

還有一種情況也很常見：數字增加不多，但品質明顯下降。這通常代表問題不只在總量，也在相關性。當上下文裡混進很多彼此無關的討論時，模型得先穿過更多雜訊，才能找到真正重要的限制。所以，低增量不等於低風險。

你可以用三個問題來判斷當下的訊號。

- 這次增加，來自我真正需要的檔案和結果嗎
- 代理還能準確引用先前的決定和限制嗎
- 後續互動的資訊密度，是否正在下降

如果三個答案都還正常，就可以繼續。要是 token 漲得很快，代理又開始重複或遺漏，那就是一個很明顯的整理訊號。

### 何時採取行動

上下文計數器不會自己幫你清理 session。看到數字上升，也不表示你一定要立刻重置。重置的代價，是失去目前對話裡的現場脈絡，得重新建立探索成本。繼續使用的代價，則是讓更多歷史內容繼續留在後續請求裡，可能慢慢拉低代理的注意力品質。

判斷時，可以從三個維度一起看。

| 維度 | 適合繼續的訊號 | 適合整理或重置的訊號 |
| --- | --- | --- |
| 數字趨勢 | 增加平穩，仍有可預期的工作量 | 短時間內大幅膨脹，原因不明或反覆發生 |
| 代理品質 | 能維持需求、檔案與決策的正確關聯 | 開始忘記限制、重複探索或混淆已驗證結果 |
| 任務階段 | 目前工作快完成，保留現場脈絡有價值 | 即將進入新階段，舊歷史大多不再相關 |

例如，數字雖然偏大，但任務只剩最後一次測試，那麼直接完成可能比重置更划算。反過來，如果數字還不算特別大，但代理已經一直重問同樣的問題，那麼整理脈絡還是合理。數字只是證據的一部分，任務狀態和代理表現也同樣重要。

### 一個實用的決策流程

當你看到 token 持續增加時，可以照著下面五步做。

1. 先記下目前數字，以及最近一次讓它明顯增加的操作。
2. 檢查這些增加的內容，是否真的和目前任務直接相關。
3. 觀察代理是否仍然能遵守需求、引用正確檔案，並避免重複探索。
4. 如果內容已經變雜，先不要再往裡面灌資料，先整理出目前真正需要的背景。
5. 如果 session 已經跨到下一個任務階段，就寫一份簡短交接摘要，再用新的 session 接手。

這個流程的好處，是把抽象的「上下文焦慮」變成具體行動。你不用等到某個神奇門檻才准自己重置，也不用等代理完全失準，才承認這個 session 已經失去效率。

### 讓 status line 保持簡單

status line 當然可以自訂，但自訂的目的應該是提高可見性，不是再做出另一套很難維護的系統。最小可用版本其實很簡單：只顯示目前的上下文 token 數就夠了。如果你的外殼本來就會顯示工作目錄、分支或執行狀態，也可以把計數器放在同一行，讓你工作時自然就會看到。

不要一開始就加上十幾種顏色、門檻、圖表和通知。太複雜的儀表板，很可能讓你把時間花在研究儀表，而不是完成工作。先確定三件事：數字會即時更新、位置固定、格式好讀。做到這一步之後，再考慮要不要加別的資訊。

簡單還有一個好處：你換模型、換專案，或調整外殼時，比較容易把這個基本計數器一起帶走。這樣你還是可以用同一套觀察方法，重新建立新的基線和增量直覺。

### 從測量回到上下文衛生

持續測量的真正價值，最後還是會回到上下文衛生。這裡說的衛生，不是要求每個 session 都永遠維持最小，而是要讓送進模型的內容大多有用、可追溯，而且和現在的任務有關。計數器幫你看見負載，但接下來真正減少浪費的，還是整理工作本身。

如果一個新 session 的基線就很高，你可以先檢查固定提示、沒在用的工具、連接器、工作流程和技能。要是基線本身合理，但做一個小任務後就膨脹很多，那就該檢查代理的探索方式、讀檔範圍，以及工具輸出的格式。要是數字增加看起來正常，但品質卻變差，那就要懷疑歷史內容裡是不是混進太多不同任務。

這三種情況，處理方式都不一樣。固定成本太高，就清理外殼設定。單次操作太貴，就縮小輸入範圍，或改善工具輸出。整個工作階段已經混雜，就寫摘要並切到新的 session。沒有計數器時，這些問題很容易全部混成一句模糊的「代理今天變笨了」。有了計數器，你至少能先把問題問得更準。

### 一個可重複的練習

你可以在自己的 TypeScript 或 Node 專案裡做一個簡單練習。先開一個乾淨的 session，記下 status line 的 token 基線。接著依序做三件事：請代理說明專案用途、請它讀一個小型設定檔、再請它執行一個可能會產生輸出的測試。每一步前後都記錄 token 數，同時也記下代理的回答是不是還一樣準確。

最後把結果整理成一張小表。

| 階段 | Token 數 | 變化 | 代理是否保持清楚 |
| --- | ---: | ---: | --- |
| 新 session | 你的基線 | 0 | 記錄初始狀態 |
| 專案說明 | 實測數字 | 與基線相比的增加 | 是否先探索再回答 |
| 讀取設定檔 | 實測數字 | 與上一階段相比的增加 | 是否抓到正確設定 |
| 執行測試 | 實測數字 | 與上一階段相比的增加 | 是否能區分錯誤與雜訊 |

這個練習不會給你一個放諸四海皆準的答案。它給你的，是你自己環境的輪廓。你會知道自己的外殼一開始就要花多少 token，小型檔案通常會增加多少，測試輸出從什麼時候開始變得昂貴，也會知道代理最容易在哪個階段偏離任務。這些觀察，之後都能直接幫助你設計 prompt、調整工具設定，還有切分 session。

最後記住三件事。第一，持續看得見，比事後回頭追查更有用。第二，增量通常比單一總量更能說明到底是哪個動作帶來成本。第三，數字一定要和代理品質、任務階段一起看。上下文計數器不是警報器，也不是自動修理工具。它比較像一個低干擾的觀測點，讓你在 session 還能控制時，就先看見它正往哪個方向走。
