## Learning goal

用 `/context` 與 status line 追蹤 token 消耗，維持 smart zone。

## Lesson

### 📝 手動查 log 的三個致命問題

假設你正在用 Claude Code 做跨三個檔案的 refactoring。你已經切換了六次、讀了十幾個檔案、提了三十多輪 prompt，session 早就不是新開的了。這時候你想知道一件事：我的上下文還剩多少空間？

最直覺的做法是打開 agent 的 request log，把整段 log 複製下來，貼進另一個工具去算 token 數量。這個方法能用，但它有三個致命問題。

**問題一：中斷工作。** 你得停下正在做的事，切到 log 介面，選取一大段文字，複製，貼到別處，等它計算，再切回來。每一步都是一個上下文切換，不只打斷 agent 的節奏，也打斷你自己的思考鏈。

**問題二：頻率太低。** 因為操作成本高，你不太可能每五分鐘就做一次。但上下文消耗的速度可能遠比你想像中快。一個簡單的「幫我整理這段註解」可能就花掉 300 token；一次檔案讀取可能吃掉數千 token。等你覺得「好像該檢查一下」的時候，數字可能已經遠超預期。

**問題三：只給快照。** 你看到的是過去某個時間點的數字，不是現在的。在你檢查完、決定「還好」、繼續工作的那幾分鐘裡，token 又在持續累積。

這就是為什麼「偶爾檢查一次」不夠。你需要一個不會中斷工作、不會讓你分心、卻能持續給你訊號的監測方式。

### 💡 從一次性檢查到持續監測

[[learn/ai-coding-crash-course/elements/context-counter|上下文計數器 (Context Counter)]] 的核心想法很簡單：把 token 使用量從需要主動查看的隱藏資訊，變成永遠在你視線範圍內的常駐顯示。

在 Claude Code 裡，這個機制叫做 **status line**。它會出現在介面底部，像一個小型儀表板，隨著每一次互動即時更新。你不需要按任何鍵、不需要切換畫面、不需要執行任何指令，數字就一直掛在那裡。

**為什麼這很重要？** 當你需要「主動去查」時，你會選擇性地忽略它。但當它一直亮在那裡，你自然會在每次互動時瞥一眼。就像車上的油錶，你不需要每五分鐘就刻意去讀，但因為它一直存在於 peripheral vision（周邊視覺），你會在它開始下降時自然地注意到。

更重要的是，status line 把「context paranoia」從一種焦慮變成一種可管理的常態。你不再需要擔心「我是不是該檢查了」，因為資訊已經在那裡。你只需要建立一個習慣：在做重要決策前，瞥一眼底部的數字。

### ⚡️ 設定只需要一分鐘

把 status line 接上 token 計數器的操作非常直接。在 Claude Code 的情境裡，你把一段可複製成 Markdown 的設定文章貼進 agent，授予它修改設定的權限，它就會在你的 `settings.json` 裡加入 `status_line` 指令。完成後，介面底部會出現一個持續更新的 token 計數。

這裡不逐字列出設定文章的內容，因為它可能會隨版本更新。重要的是理解它做了什麼：它讓 agent 在每次回合結束後，自動把當前的 token 使用量寫進 status line。這不需要你在每次互動後手動觸發，也不需要呼叫外部工具。它是 agent 工作流的一部分，安靜地在背景運作。

設定完成後，你得到的不是一個數字，而是一個**趨勢**。每一次 prompt、每一次工具呼叫、每一次檔案讀取，都會讓數字往上跳。而你不需要做任何額外動作就能看見這個趨勢。

### 📊 從數字建立直覺

設定好 status line 之後，下一步是建立對 token 消耗的直覺。這不需要你去背任何公式，只需要你在接下來幾次 session 中，養成偶爾瞥一眼的習慣。

從一個具體情境開始。假設你剛開一個新 session，status line 顯示約 **11.7k token**。這是你的基線，也就是外殼預載內容佔據的空間。你還沒輸入任何東西，11.7k 已經被吃掉了。

現在你輸入一個簡單的請求，例如「幫我總結一下這份文件」。agent 會讀取文件、產生摘要，然後把結果傳回來。等它完成後，再看一眼 status line。數字可能從 11.7k 跳到大約 **12k**。這代表你剛才那個簡單請求大約消耗了 **300 token**。

300 token 聽起來不多。但如果你在一個 session 裡做十個類似的請求，光是「總結」這個動作就吃掉 **3k token**。再加上你可能還會要求修改、追問、讀更多檔案，整個 session 的消耗很容易就從 11.7k 的基線往上推到 **30k、50k 甚至更多**。

你需要的不是記住每一個數字，而是建立**三層直覺**：

| 直覺層級 | 觀察內容 | 實際用途 |
|----------|----------|----------|
| 基線 | 新 session 開始時佔多少 token | 知道外殼本身的負擔有多重。基線異常高（例如超過 20k）代表外殼設定可能還有優化空間 |
| 增量 | 不同類型的動作消耗多少 token | 一個簡單的文字回應幾百 token；一次完整的檔案讀取數千 token；一次涉及多個檔案的 refactoring 指令可能吃掉上萬 token |
| 斜率 | 上下文消耗的速度是穩定、加速還是暴衝 | 穩定代表工作流程正常；加速代表你在反覆做高成本操作；暴衝代表某個工具呼叫或某段回覆特別長 |

### 🧭 status line 如何改變決策

當你有了持續可見的 token 數字，你的決策模式會自然改變。

#### 從「做到不能做」到「提前準備」

沒有 status line 時，你傾向於「做到不能再做為止」。你會一直繼續同一個 session，直到 agent 的品質明顯下降，或者你終於想起「好像該檢查一下」。這兩種觸發都太晚了。

有了 status line，你傾向於「在進入高風險區之前先準備」。你會在數字接近你認定的警戒線（例如 100k 或 120k token）之前，就開始考慮下一步：先做一個較小的任務、先把目前的狀態整理好、再決定是否開新的 session。

#### 從「抗拒重置」到「主動重置」

很多人抗拒開新 session，因為已經投入了不少時間，覺得重新交代很浪費。但當你看見 token 數字持續往上走，你會更清楚地意識到：繼續在同一個 session 裡工作，不只是浪費時間，還在為低品質判斷支付更多 token 費用。重置不是放棄，而是回到一個更有效率的工作環境。

#### 從「冗長 prompt」到「精簡 prompt」

當你知道一個 prompt 可能吃掉數百甚至數千 token，你會更傾向於把需求寫得更精確、更緊湊。你不會為了「禮貌」而多加幾句客套話，也不會為了「完整」而把所有背景全部重述一遍。你會學會只放 agent 需要知道的資訊，把不必要的描述從 prompt 裡移除。

### 🔧 保持簡單，避免監測變成負擔

status line 的一個重要設計原則是**保持簡單**。它只顯示 token 數量，不顯示百分比、不顯示預估剩餘時間、不顯示圖表。這個刻意的簡化有它的理由。

過度複雜的監測工具會變成另一個需要管理的東西。如果你的 status line 裡有五個數字、三個圖表和一個預估值，你就需要花時間去理解這些數字的意義、決定哪些數字重要、判斷它們是否異常。這反而增加了認知負擔，把原本要解決的問題（上下文管理）轉移到了另一個問題（監測工具管理）。

一個簡單的數字就夠了。你只需要知道「現在大概多少 token」，結合你對任務複雜度的判斷，就足以做出「繼續、整理、還是重開」的決策。過度儀表板化的傾向在工程文化中很常見，但在 context 管理這件事上，少即是多。

### 🎯 把計數器變成習慣

設定 status line 只是第一步。真正的價值來自你把它變成日常習慣。具體來說，有**三個時刻**特別值得瞥一眼底部的數字。

**第一個時刻：session 剛開始。** 你開了一個新 session，先看一眼基線。如果基線正常，你就放心開始工作。如果基線異常高，你先排查外殼設定。

**第二個時刻：準備交給 agent 高價值任務之前。** 例如你準備讓它做跨檔案的 design review、複雜的 bug 追蹤，或者需要記住多個前提的實作。在這些時候，確認 token 數字還在你認為安全的範圍內。如果已經偏高，先整理上下文，或直接開新 session。

**第三個時刻：session 進入後半段。** 你已經工作了一段時間，token 數字已經比基線高出不少。這時候你需要評估：目前的 context 密度是否仍然足夠支撐高品質推理？如果數字已經接近你認定的警戒線，而你還有重要工作要做，就該考慮重置或交接。

這三個時刻不需要你特別記住。只要 status line 一直在那裡，你會自然地在這些關鍵節點上去看它。幾次之後，這會變成一個不假思索的動作，就像開車時看油錶一樣自然。

### ✅ 最後記住的三件事

1. **token 計數器讓 context 管理從「偶爾手動檢查」變成「持續被動監測」。** 你不需要中斷工作就能知道上下文的消耗速度。

2. **計數器的價值不在於單一數字，而在於趨勢。** 你需要的是基線、增量和斜率這三層直覺，而不是背誦某個精確的 token 閾值。

3. **保持簡單。** 一個持續更新的數字就足以改變你的決策模式。過度複雜的監測工具只會把 context 管理的負擔轉移到另一個地方。

只要你的 status line 一直在那裡，你就比大多數人更清楚自己在做什麼。大多數人等到 agent 開始犯錯才發現 session 已經太長。你不會，因為數字一直在提醒你。
