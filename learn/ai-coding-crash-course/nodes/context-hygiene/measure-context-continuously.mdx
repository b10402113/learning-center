# 持續測量上下文

## Learning goal

能在 AI coding agent 的每個 session 中設定並使用即時上下文計數器，建立初始基線、觀察每次互動帶來的 token 增量，並根據上下文趨勢與代理品質決定何時整理、重置或繼續工作。

## Lesson

### 先把上下文當成可觀察的工作負載

一個剛開啟的代理 session，畫面上也許只有幾句話，送到模型端的 request 卻可能已經包含 system prompt、工具定義、外殼設定、技能、先前訊息、讀過的檔案和工具結果。這些內容都會影響後續請求。持續測量的目的，不是替每個互動做繁瑣記帳，而是在工作進行時保留一個低干擾的訊號。你要知道基線是多少，也要知道哪一次讀檔、測試或追問讓它突然增加，最後再把數字和代理品質放在一起判讀。

一個實用的觀察順序是：新 session 先記基線；做一個可重現的小請求；在讀取大型檔案、執行長測試或跨越工作階段時再次查看；若 token 上升同時伴隨遺漏、重複或混淆，再決定整理、重置或繼續。這樣上下文計數器就不只是顯示數字，而是支援工作節奏的決策工具。

一個剛開啟的代理 session，看起來可能只有幾句對話，實際上卻已經背著一大包內容。系統提示、工具定義、外殼設定、已啟用的技能、先前訊息、代理讀過的檔案、工具執行結果，都可能被放進後續請求。你在畫面上輸入一句「幫我修這個 bug」，送到模型端的內容通常遠比這句話長。

這種差距會帶來一個很實際的盲點。你以為自己只做了一個小動作，代理卻可能因為讀取檔案、搜尋程式碼、執行指令和回報結果，讓上下文持續增加。等到回答開始遺漏需求、忘記前面的決定、重複做過的探索，你才察覺 session 已經太肥。那時候問題通常已經從「要不要監測」變成「哪些脈絡還值得保留」。

因此，持續測量上下文的第一個觀念很簡單。你不能只在出現錯誤時才看上下文，也不能只靠對話長度猜測消耗量。你需要一個一直在視線內的數字，讓上下文從隱藏成本變成工作中的即時訊號。這個數字就是 [[learn/ai-coding-crash-course/elements/context-counter|上下文計數器 (Context Counter)]]。

### 上下文計數器到底在量什麼

上下文計數器顯示的是目前 session 會帶進請求的上下文規模，通常以 token 表示。token 是模型處理文字與其他輸入時使用的切分單位。它不完全等同於字數，也不等同於訊息數。一段程式碼、工具輸出、檔案內容和自然語言，會按照模型的切分方式轉成不同數量的 token。

你可以先把它理解成工作桌上已經攤開的紙張數量。你說了一句話，桌上多了一張紙。代理讀入一個很長的檔案，可能一下子多出幾十張。工具回傳大量測試輸出，又會繼續佔用桌面。計數器不負責整理紙張，也不負責判斷哪一張重要，它只讓桌面面積的變化保持可見。

這個區分很關鍵。計數器量的是負載，不是品質。上下文數字大，不代表回答一定錯。數字小，也不保證代理一定理解任務。真正要觀察的是兩條線是否一起惡化。第一條是 token 持續上升，第二條是代理是否開始忽略限制、重複探索、混淆檔案或提出已經回答過的問題。只有把數字和行為放在一起看，測量才會變成決策工具。

### 為什麼要放在 status line

如果你每次都要複製 request log，再找出上下文欄位，這個檢查很快就會被放棄。它太慢，也打斷工作。更麻煩的是，手動檢查通常發生在你已經懷疑出問題之後，無法幫你看見問題如何形成。

status line 是代理介面底部持續顯示資訊的一行。把上下文 token 數放在這裡，有三個直接好處。

1. 你不需要離開目前工作流，就能看見 session 正在變大多少。
2. 你可以在一次互動前後比較數字，建立不同操作的消耗直覺。
3. 你能在品質明顯下降以前注意到趨勢，提早選擇整理或換 session。

這種設計的重點不是做一個豪華儀表板，而是把一個原本需要額外操作才能取得的訊號，放到你每次工作都會看到的位置。監測工具越低干擾，越容易形成習慣。若每次檢查都要翻設定、開視窗、解析一大段 log，使用者最後只會在事故後才使用它。

### 先建立你的基線

第一次使用計數器時，不要急著把某個數字當成標準。先觀察一個全新的 session 在還沒有要求代理做實質工作時，status line 顯示多少 token。這就是你的基線。

基線包含了許多固定成本。不同代理外殼、模型、系統提示、工具清單、技能設定和連接器，會導致不同環境有不同起點。有些環境一開啟就載入大量工具定義，有些環境只保留基本 shell 與檔案操作。即使兩個 session 沒有任何使用者訊息，它們的上下文數字也可能差很多。

建立基線時可以記下以下資訊。

| 觀察項目 | 你要知道的事情 |
| --- | --- |
| 新 session 的 token 數 | 外殼在開始工作前已經佔用了多少上下文 |
| 啟用的工具與技能 | 哪些固定內容可能在每次請求都重複出現 |
| 工作目錄與專案大小 | 代理後續探索時可能接觸到的資料範圍 |
| 代理初始回應 | 它是否在沒有讀檔前就假裝知道專案細節 |

這個步驟的目的，是把「我覺得上下文很多」變成一個可以比較的起點。之後你清理設定、停用不用的工具，或改變工作方式，都能回到基線確認實際效果。

### 用一個小請求校準增量

建立基線後，做一個很小、很容易重現的請求。比如要求代理摘要一段已經提供給它的簡短內容，或要求它說明目前的工作目錄。完成後再次看 status line，記下新的 token 數。

示範中的數字從約 11.7k 上升到約 12k，增加大約 300 token。這個例子最有價值的地方不在於 300 這個數字本身，而在於你看見了「一次看似簡單的互動也會留下增量」。當你把同樣方法套用到讀取檔案、執行測試、搜尋整個專案和多輪修正，就能逐步建立自己的消耗地圖。

可以用下面的方式記錄幾次操作。

| 操作 | 操作前 | 操作後 | 增量 | 可能原因 |
| --- | ---: | ---: | ---: | --- |
| 簡短摘要 | 11.7k | 12.0k | 約 0.3k | 新增訊息與代理回應 |
| 讀取小型設定檔 | 12.0k | 12.8k | 約 0.8k | 檔案內容進入對話 |
| 執行測試並回傳完整輸出 | 12.8k | 15.4k | 約 2.6k | 工具輸出佔用大量空間 |
| 重複追問同一個決定 | 15.4k | 16.1k | 約 0.7k | 新增對話與重複說明 |

表中的數字只是示意，不能直接套用到每個模型或外殼。真正要保留的是比較方法。每次操作前看一次，操作完成後再看一次，兩個數字的差距就是這次操作在目前環境造成的近似增量。

### 把計數器變成工作節奏

持續測量不代表你要在每一則訊息後停下來做會計。那會讓監測反過來妨礙工作。較好的節奏是把觀察放在有意義的邊界。

在 session 開始時看基線。完成一段探索後看一次。代理讀完大型檔案、執行長測試、產生大段錯誤輸出，或進入多輪修正時，再看一次。準備從分析轉到實作、從實作轉到測試，或準備換一個獨立子任務時，也可以把當下數字記下來。

這樣做的好處，是你會逐漸知道哪些動作最容易消耗上下文。例如單純改一個函式可能只增加少量內容，但一次把整個 build log 貼回來，可能比幾輪簡短討論都更昂貴。若你發現代理常常為了尋找一個檔案而反覆讀取整個目錄，也能從 token 增量看出探索流程的成本。

你可以把 session 分成四個觀察階段。

1. 起始階段只記錄基線，確認固定載入成本。
2. 探索階段觀察讀檔、搜尋和工具輸出的增量。
3. 實作階段比較每輪修改與驗證的成本。
4. 收尾階段檢查是否還有足夠清楚的脈絡完成 review，或應該整理後再開始下一個任務。

這套節奏不要求精確預測未來還能容納多少 token。它訓練的是對趨勢的敏感度。

### 讀懂上升速度

單看目前總量不夠，還要看上升速度。兩個 session 都顯示 20k token，但其中一個是慢慢累積了二十輪小互動，另一個是在一次工具呼叫後突然增加 8k，兩者的處理方式可能不同。

穩定而小幅的增加，通常表示工作正在正常推進。你仍然要留意總量，但不必因為每次增加就立刻中斷。突然的大幅增加，則值得查原因。可能是代理讀入了不必要的大檔案，工具輸出包含大量重複內容，搜尋範圍沒有收斂，或某個技能把額外說明塞入對話。

還有一種情況是數字增加不多，品質卻明顯下降。這可能表示問題不在總量，而在脈絡的相關性。上下文中如果混入很多互不相干的討論，模型需要在更多雜訊裡找真正重要的限制。這時候低增量也不等於低風險。

可以用三個問題判斷當下訊號。

- 這次增加來自我真正需要的檔案與結果嗎
- 代理是否仍能準確引用先前的決定與限制
- 後續互動的資訊密度是否正在下降

如果三個答案都正常，就可以繼續。若 token 快速上升，同時代理開始重複或遺漏，就應該把它當成整理訊號。

### 何時採取行動

上下文計數器不會自動替你清理 session。看到數字上升，也不代表一定要立刻重置。重置的代價是失去目前對話中的現場脈絡，重新建立探索成本。繼續使用的代價則是讓更多歷史內容留在後續請求裡，可能逐漸降低注意力品質。

判斷時可以看三個維度。

| 維度 | 適合繼續的訊號 | 適合整理或重置的訊號 |
| --- | --- | --- |
| 數字趨勢 | 增加平穩，仍有可預期的工作量 | 短時間內大幅膨脹，原因不明或反覆發生 |
| 代理品質 | 能維持需求、檔案與決策的正確關聯 | 開始忘記限制、重複探索或混淆已驗證結果 |
| 任務階段 | 目前工作快完成，保留現場脈絡有價值 | 即將進入新階段，舊歷史大多不再相關 |

如果數字偏大但任務只剩最後一次測試，繼續完成可能比重置更划算。如果數字還不算大，但代理已經不斷重問相同問題，整理脈絡仍然合理。數字是證據的一部分，任務狀態與代理表現同樣重要。

### 一個實用的決策流程

當你看到 token 持續增加時，可以按照下面五步走。

1. 先記下目前數字，以及最近一次造成明顯增加的操作。
2. 檢查增加內容是否與目前任務直接相關。
3. 觀察代理是否仍能遵守需求、引用正確檔案並避免重複探索。
4. 若內容有雜訊，先停止繼續灌入資料，整理出目前真正需要的背景。
5. 若 session 已跨過任務階段，建立簡短交接摘要，再用新的 session 接手。

這個流程把「上下文焦慮」轉成具體行動。你不必看到某個神奇門檻才有資格重置，也不必等代理完全失準才承認 session 已經失去效率。

### 讓 status line 保持簡單

status line 可以自訂，但自訂的目的應該是提高可見性，而不是製造另一套需要維護的系統。最小可用版本只需要顯示目前上下文 token 數。若你的外殼本來就顯示工作目錄、分支或執行狀態，可以把計數器放在同一行，讓你在工作時自然看到它。

不要一開始就加入十幾個顏色、門檻、圖表和通知。複雜儀表板可能讓你花更多時間研究儀表，而不是完成工作。先確定數字會即時更新、位置固定、格式容易讀，再考慮是否真的需要額外資訊。

簡單還有另一個好處。當你換模型、換專案或調整外殼時，基本計數器容易移植。你仍然能使用同一套觀察方法，重新建立新的基線和增量直覺。

### 從測量回到上下文衛生

持續測量的價值，最後會回到上下文衛生。衛生不是追求每個 session 永遠保持最小，而是讓送進模型的內容大多有用、可追溯、和目前任務有關。計數器幫你看到負載，接下來的整理工作才是減少浪費。

如果新 session 的基線已經很高，你可以檢查固定提示、未使用的工具、連接器、工作流程和技能。若基線合理，但執行一個小任務後膨脹很多，你可以檢查代理的探索方式、檔案讀取範圍和工具輸出格式。若數字增加正常，品質卻變差，則要檢查歷史內容是否混入太多不同任務。

這三種情況需要不同的處理方式。固定成本過高時，清理外殼設定。單次操作過於昂貴時，縮小輸入範圍或改善工具輸出。工作階段已經混雜時，建立摘要並切換到新的 session。沒有計數器時，這些問題容易被混在一起，最後只剩下模糊的「代理今天變笨了」。有計數器後，你至少能先問出更精確的問題。

### 一個可重複的練習

在自己的 TypeScript 或 Node 專案中，開啟一個乾淨 session，先記錄 status line 的 token 基線。接著依序做三件事。要求代理說明專案用途，要求它讀取一個小型設定檔，再要求它執行一個可能產生輸出的測試。每一步前後都記錄 token 數，也記下代理的回應是否仍然準確。

完成後整理成一張小表。

| 階段 | Token 數 | 變化 | 代理是否保持清楚 |
| --- | ---: | ---: | --- |
| 新 session | 你的基線 | 0 | 記錄初始狀態 |
| 專案說明 | 實測數字 | 與基線相比的增加 | 是否先探索再回答 |
| 讀取設定檔 | 實測數字 | 與上一階段相比的增加 | 是否抓到正確設定 |
| 執行測試 | 實測數字 | 與上一階段相比的增加 | 是否能區分錯誤與雜訊 |

這個練習的結果不是一個通用答案，而是你的環境輪廓。你會知道自己的外殼在開始時花多少 token，小型檔案通常增加多少，測試輸出何時開始變得昂貴，也會知道代理在什麼階段最容易偏離任務。這些知識能直接支援之後的 prompt 設計、工具設定和 session 切分。

最後請記住三件事。第一，持續可見比事後追查更有用。第二，增量比單一總量更能解釋哪個動作造成成本。第三，數字必須和代理品質、任務階段一起判讀。上下文計數器不是警報器，也不是自動修理工具。它是一個低干擾的觀測點，讓你在 session 還能控制時看見它正在往哪裡走。
