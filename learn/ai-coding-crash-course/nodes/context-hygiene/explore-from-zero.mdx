## Learning goal

學完這一步，你能理解全新 Session 為什麼必須重新探索 repository，分辨代理在啟動時真正知道的環境中繼資料與完全未知的專案內容，並設計一個由證據開始的探索流程。你也能讓代理把探索結果寫入檔案系統，形成可以跨 Session 延續的學習工作區，而不是把專案理解寄託在模型暫時保留的對話脈絡上。這一步的核心概念是 [[learn/ai-coding-crash-course/elements/fresh-session-exploration|全新 Session 探索 (Fresh Session Exploration)]]。

## Lesson

### 用八步驟把陌生 repo 變成可工作的地圖

面對一個全新的 Session，你可以先用固定的八步驟探索 repository。先確認起點乾淨，知道目前用的是哪個 agent、工作目錄在哪裡、載入了哪些基本設定；接著先問技術棧、專案用途、主要結構和判斷證據，並明確要求先不要修改檔案；再觀察它實際讀了什麼、用了哪些工具、會不會在證據不足時承認不知道；之後檢查 README、依賴宣告、lockfile、scripts 和主要設定；再沿著路由、頁面、資料模型、服務邏輯和代表性測試，慢慢建立產品地圖；對重要結論都要求檔案證據；把比較穩定的理解寫進 mission、notes、resources、glossary 或 lesson；最後在實作前，先列出已知、未知、影響範圍和驗證指令。

這套順序的重點，是把工作方式從「先猜一個答案」改成「先拿到足夠證據」。它也能避免另一個常見問題：為了表示自己有探索，就把整個 repository 一次塞進上下文。真正好的探索，不是讀最多檔案，而是用剛剛好的證據，支撐下一步決策。

### 先接受一個不太舒服的事實：全新 Session 幾乎不認識你的專案

開一個新的 AI coding agent Session 時，你通常已經看得到專案目錄，代理也常能回答一些目前環境的問題。這很容易讓人誤以為它「已經進到 repository 裡」，所以應該已經知道專案大概長什麼樣。其實不是。它站在那個目錄裡，不等於它真的讀過裡面的內容。

一個 fresh Session 在正式探索前，通常只知道少量環境和 Git 中繼資料。比如平台是 Linux、WSL 或 macOS，主要工作目錄在哪裡，目前是不是 Git repository，使用哪個 shell，模型的知識截止時間，目前 branch 和主要 branch 是什麼，Git 使用者是誰，最近有哪些 commit。這些資訊只能回答「我現在在哪裡」和「最近發生過什麼」，卻回答不了「這個產品是做什麼的」或「這個專案怎麼運作」。

它通常還不知道下面這些事：

- 檔案系統裡到底有哪些檔案和目錄。
- 專案用的是 React、Vue、Svelte、Node、Python，還是其他技術棧。
- 啟動、測試、型別檢查和建置的正確指令是什麼。
- 哪些目錄分別負責前端、後端、資料庫、共用套件或測試。
- 最近的 commit 是否真的代表目前程式碼的主要設計。
- 產品的實際用途、使用者流程和重要限制。
- 團隊在命名、錯誤處理、測試和部署上的慣例。

所以，如果代理一開始就對專案講得很完整，但它其實還沒讀過任何檔案，那些內容本質上都還只是推測。它也許會猜中，但猜中不等於已經理解。

### 為什麼模型的無狀態性，會逼你每次重新探索

模型本身是無狀態的。每次收到模型請求時，它都是根據這次送進來的上下文，產生下一段輸出。它不會在參數裡幫你保存「昨天看過這個 repository」這種個人記憶。代理外殼確實能管理 Session、保存訊息、呼叫工具，讓整個系統看起來像有連續記憶，但那種連續性其實只存在於被重新送入請求的對話內容和工具結果裡。

一旦你清空上下文，或重新開一個新的 Session，先前那些沒有落盤的理解就不會自動留下來。代理不會因為你昨天花了兩小時解釋架構，今天就自然知道同一件事。對你來說是同一個專案；對新的 Session 來說，這還是第一次見面。

這聽起來像模型的限制，但它其實也是一個很實際的工作流程約束。既然模型不會自動帶著理解往前走，你每次重新開始時，就得做兩件事：先拿到足夠工作的證據，再把值得保留的理解存到環境裡。前者叫探索，後者叫外部記憶。兩個都不能少。

為什麼這麼重要？因為只要你跳過探索，後面的規劃、實作、測試和評論，就可能全都建立在錯的專案模型上。代理也許知道有一個叫「課程評論」的 commit，卻不知道評論資料到底存在什麼表；也許看到 `app` 目錄，就猜這是一個一般 React 應用，卻不知道真正的路由、loader 和 server boundary。第一個假設一旦偏掉，後面每一層都可能看起來合理，但整體其實早就歪了。

### 問對第一個問題：先問技術棧和用途

在全新 Session 裡，第一個任務不應該是「直接實作這個功能」。更好的開場，是先要求代理判斷專案的技術棧和預期用途，例如：

> 請探索這個專案，說明它使用的技術棧、主要用途、重要目錄，以及你用來做出判斷的證據。先不要修改任何檔案。

這個問題有三個作用。

第一，它會把代理從產出模式切到理解模式。如果你一開始就說「幫我加一個功能」，代理很容易把改出一個檔案當成首要目標，快速讀幾個看起來相關的位置後就開始寫。先要求探索，等於先把讀取和判斷排在修改前面。

第二，它逼代理交出證據，而不只是結論。技術棧不該靠目錄名字猜，而應該從 `package.json`、lockfile、設定檔、入口檔、路由檔和 README 交叉確認。產品用途也應該從 README、頁面結構、資料模型和實際執行方式推導，不是只看最後一個 commit 的標題。

第三，它能讓你看見代理的探索策略。它可能會自己列檔案、搜尋關鍵字，再讀幾個核心檔案；也可能把探索工作交給 sub-agent，等摘要回來再回答；也可能只讀 README 就太早下結論。你要看的不只是答案，還有它怎麼得到答案。探索路徑本身，會暴露這個 harness 的預設行為，也會讓你知道是不是需要把探索範圍講得更清楚。

### 好的探索，不是把整個 repository 一次讀完

重新探索，不代表把所有檔案一口氣塞進上下文。這樣做只會讓新的 Session 很快進入上下文膨脹，反而降低理解品質。探索的目的，是建立一張足夠精確的地圖，不是把每個檔案都背進模型。

比較好的方法，是由外往內分層看。

第一層是定位。先確認目前目錄、Git 狀態、根目錄有哪些重要入口檔，並找出 README、package manifest、lockfile、主要設定檔和常見的 source 目錄。這一層要回答的是：這個專案大致分成哪些區塊。

第二層是辨認技術棧。讀 `package.json` 或其他依賴宣告，確認 framework、runtime、測試工具、資料庫工具和 scripts。接著再讀 framework 的主要設定和入口檔，避免只靠依賴名稱去猜實際用法。這一層回答的是：這個專案是怎麼組起來的。

第三層是理解產品邊界。檢查 README、頁面或路由結構、核心資料模型，以及一兩條代表性的使用者流程。這一層回答的是：這套程式在幫誰解決什麼問題。

第四層才進入目前任務相關的局部細節。當你已經知道產品結構和技術棧，再去追某個功能涉及的 component、route、API、schema 和測試。這一層回答的是：眼前要改的地方，和其他部分怎麼接在一起。

這個順序能減少兩種錯誤。第一種是只看一個檔案，沒有架構脈絡，就把局部慣例誤認成全域規則。第二種是什麼都讀，結果真正重要的資訊反而被工具輸出淹沒。探索做得好不好，不是看你讀了多少檔案，而是看你能不能用足夠證據，支撐正確的下一步決策。

### 用「先讀檔再回答」，取代「先猜再補證據」

在陌生 repository 裡，代理最危險的表現，不一定是明顯亂講，而是用很自然、很流暢的語氣，說出其實沒有證據的內容。比如它看到 `routes` 目錄，就直接說「這是使用 React Router 的前端路由」；看到 `db` 目錄，就直接說「這裡使用 PostgreSQL」；看到一個叫 `server` 的檔案，就斷言所有資料存取都在 server side 完成。這些話有可能是對的，但也可能只是命名剛好看起來像。

你可以要求它把每個高層判斷，都綁到實際觀察到的檔案上。好的探索報告，至少會交代：它讀了哪個檔案、看到了什麼內容、因此做出什麼結論，還有哪些地方尚未確認。這種說法會自然露出不確定性，也比較方便你決定下一步要追問什麼。

例如，與其接受「這是一個 React Router 應用」，不如要求它說明：是不是在 `package.json` 裡看到了相依套件，路由檔裡是不是有 route module，server 和 browser 兩端是不是都有相關 component。與其接受「這個功能有用資料庫」，不如要求它找到 schema、query 或 migration 的實際位置。證據越貼近程式碼，結論就越容易驗證。

探索報告可以用下列表格整理：

| 問題 | 應尋找的證據 | 尚未確認時的做法 |
| --- | --- | --- |
| 使用什麼技術棧 | 依賴宣告、lockfile、入口與設定檔 | 標記推測，繼續讀核心設定 |
| 專案的用途 | README、路由、頁面、資料模型 | 先說已知使用流程，不擴大推論 |
| 如何啟動與驗證 | scripts、測試設定、建置設定 | 找到指令前不要自行發明指令 |
| 當前功能在哪裡 | route、component、service、schema、測試 | 先畫出呼叫鏈，再考慮修改 |
| 哪些規則必須遵守 | 專案指引、既有實作、測試與 lint 設定 | 以現有模式為準，明確標註未知處 |

重點不是叫代理寫一份漂亮報告，而是讓它的理解可以被檢查。能檢查的探索，比那種流暢卻無法追溯的自信，更有價值。

### 探索時，也要看 sub-agent 和主代理怎麼分工

有些 harness 會把深入探索交給 sub-agent。主代理比較像協調者：先提出探索問題，再啟動一個或多個較小的工作單位，分別去調查技術棧、路由、資料模型或測試策略，最後把摘要帶回主 Session。這樣做的好處，是把大量讀檔工作放進獨立上下文，避免主代理的工作桌被原始輸出塞滿。

但 sub-agent 不等於品質保證。你還是要確認它到底探索了哪些範圍、摘要有沒有保留關鍵檔案和不確定性，以及主代理是否真的用上了那些結果。如果 sub-agent 只讀一份 README，就回報「已了解整個專案」，那只是把過早猜測搬到另一個 Session。好的分工，應該讓主代理拿到更濃縮、也更有用的證據，而不是多一層看不見的黑箱。

課程示範裡的探索，沒有生成 sub-agent。代理是直接讀 README 和 `package.json`，再依照 teach skill 建立學習材料。這個例子很重要，因為它提醒你：不要把 sub-agent 當成固定儀式。專案規模、問題難度和 harness 能力不同時，直接探索可能更簡單；需要平行處理，或要大量深入閱讀時，才值得委派。判斷標準應該是上下文和任務是否匹配，不是「有 sub-agent 才專業」。

### 把探索結果寫進檔案系統

即時回答只能幫你應付當前 Session。只要探索結果沒有保存，下次一清空上下文，代理還是會從環境中繼資料重新開始。更穩定的做法，是把重要理解寫成外部文件，讓檔案系統承擔持久狀態。

在課程示範裡，代理啟動 teach skill 之後，不只是口頭介紹 playground，而是建立了一整組可以持續使用的學習資產，包含 mission、學習筆記、主要資源、共用樣式資產、詞彙表和第一篇教學文章。這些檔案的作用，不只是把陌生 repository 掃過一遍，而是把它變成一個可以反覆閱讀、提問和驗證的學習工作區。

這裡有一個很關鍵的轉變：代理不再只是回答「這個專案是什麼」，而是連「應該怎麼理解這個專案」也一起整理成可持續使用的資料。mission 用來說明學習或工作的方向；notes 保存已確認的理解和還待釐清的問題；resources 集中主要文件；glossary 固定專案中特殊的名詞；教學文章則把局部結構整理成讀者可以自行驗證的課程。

為什麼落盤這麼重要？因為檔案是環境的一部分，而環境可以跨 Session 存活。你清空對話，檔案還在；你換一個模型，只要它能讀檔，還是能接著做；你把工作交給另一位代理，也可以靠這些材料快速建立共同起點。這不是讓代理真的有永久記憶，而是把記憶放到一個可以檢查、修改、版本控制和移交的位置。

### 教學工作區不是自動生成的真相

把探索結果寫進檔案系統很有用，但你不能把這些生成文件當成永遠正確。它們還是代理根據當下證據整理出來的模型，可能漏掉重要路徑，也可能在程式碼改變後變舊。持久化解決的是「每次都要從零開始」的問題，不是「從此都不用再驗證」的問題。

比較好的做法，是在每份探索文件裡保留三種狀態：哪些內容已經由程式碼確認，哪些推論目前合理但還沒驗證，哪些問題留給下一輪調查。當專案發生重大變更時，優先更新技術棧、啟動方式、主要路由和核心資料模型。不要讓一篇看起來很完整的舊教學文章，掩蓋掉現在實際的程式行為。

如果代理之後要根據這些文件開始實作，也應該要求它先檢查文件是否仍和程式碼一致。這會形成一個小閉環：探索先產生文件，文件幫助後續工作，後續工作再暴露文件裡過時的地方，然後再回頭驗證。真正有價值的持久化記錄，不是做一次就永遠不碰，而是能在工作過程中持續修正。

### 進入實作前，先設一個檢查點

探索結束後，不要只問「你準備好了嗎」。更好的做法，是讓代理用短摘要回答幾個可以檢查的問題：

1. 這個專案的主要用途是什麼，證據在哪裡？
2. 使用的 runtime、framework、資料庫與測試工具各是什麼？
3. 目前任務涉及哪些檔案或模組，它們之間怎麼連接？
4. 啟動、測試、型別檢查和建置要用哪些既有指令？
5. 哪些需求、限制或設計決定仍然未知？
6. 哪些探索結果已經寫入檔案系統，下一個 Session 應該從哪裡讀起？

如果它只能回答前兩題，代表它還停在專案導覽階段；如果它能回答前四題，卻說不出未知之處，代表它可能還是過度自信；只有當它能同時指出證據、限制和持久化位置時，才比較接近可以安全進入局部實作的狀態。

這個檢查點還能防止另一個常見錯誤：把「代理能讀檔」誤認成「代理已經理解設計」。讀 README 和 `package.json` 只是開始。真正的理解還包括路由怎麼流動、資料怎麼保存、測試怎麼驗證，以及目前功能和產品目的之間的關係。探索不需要無限延長，但一定要足夠支撐下一步決策。

### 一個可以反覆使用的 fresh Session 探索流程

你可以把這套流程固定成八個步驟，之後套用到自己的 TypeScript、Node 或其他 repository。

1. **建立乾淨起點。** 確認目前使用的 agent、工作目錄和載入中的基本設定；不要假設新 Session 會繼承上一段對話。
2. **先問高層問題。** 請代理說明技術棧、專案用途、主要結構和證據，並要求它先不要修改檔案。
3. **檢查探索行為。** 看它讀了哪些檔案、用了哪些工具、是否啟動 sub-agent，以及會不會在證據不足時承認未知。
4. **確認入口資料。** 讓它讀 README、依賴宣告、lockfile、scripts 和主要設定，建立技術棧與操作方式的基線。
5. **建立產品地圖。** 依序探索路由、核心頁面、資料模型、服務邏輯和代表性測試，不要一次無差別讀完整個專案。
6. **用追問消除猜測。** 對每個重要結論都要求檔案證據，並繼續追問尚未確認的部分。
7. **把穩定理解落盤。** 使用 teach skill 或其他適合的工作流，保存 mission、筆記、資源、詞彙和可重用的教學材料。
8. **在實作前做摘要驗證。** 讓代理列出已知、未知、影響範圍和驗證指令，再決定要不要開始修改。

這八步的核心不在形式，而在順序。先建立地圖，再決定走哪條路；先取得證據，再要求產出；先保存理解，再把 Session 當成可以丟棄的暫時工作區。

### Fresh Session 和其他上下文技術，各自處理不同問題

全新探索很容易和其他上下文管理方法混在一起，但它其實在處理一個很特定的問題。外殼重置處理的是：代理開始前，載入了多少無關設定、技能和工具；上下文計數器讓你看見這些內容，以及後續工作怎麼一路增加；compaction 會把同一個代理、同一個目錄裡的舊 Session 濃縮成較短摘要；handoff 則把理解包成可攜文件，交給另一個代理、目錄或人。

fresh Session exploration 處理的則是：在沒有可靠既有脈絡時，代理要怎麼拿到 repository 的真實結構。你可以先重置外殼，讓起點更乾淨；再用計數器觀察探索成本；如果打算留在同一個工作流，可以用 compaction 保留重要決策；如果要跨工具移動，可以用 handoff 傳遞摘要。但這些技術，都不能取代第一次面對陌生專案時的證據式探索。

簡單說，重置是在清背景噪音，探索是在建立地圖，計數器是在顯示負載，compaction 是在濃縮歷史，handoff 是在搬運理解。每個工具處理的邊界都不同。只要你知道眼前問題屬於哪個邊界，就不會想用清空對話來解決缺少專案知識，也不會拿一份舊摘要去掩蓋程式碼已經變更的事實。

### 最後的實作練習

你可以在自己的 repository 裡開一個新的 Session，先不要急著交付功能。先輸入一個要求代理探索技術棧和用途的問題，保存它的回答和工具活動。接著要求它找出啟動、測試和型別檢查指令，再要求它挑一條使用者流程，從入口一路追到資料或畫面輸出。過程中，把它引用過的檔案記下來，也記下哪些判斷需要你補充或糾正。

接著讓代理建立一份小型探索筆記，至少包含下面這些欄位：

- 專案用途與主要使用者。
- runtime、framework、資料庫和測試工具。
- 根目錄的關鍵檔案與各自用途。
- 一條已追蹤的代表性流程。
- 已確認的慣例與尚未確認的問題。
- 下一次 Session 應該先讀取的檔案。

清空 Session 之後，再要求代理只讀這份筆記，重新回答同樣的高層問題。比較前後兩次回答，檢查這份筆記是不是真的降低了重新探索成本，以及它是不是還漏掉一些必須回到程式碼才能確認的細節。最後，再讓代理重新打開一個核心檔案，確認持久化筆記和目前程式碼仍然一致。

這個練習會讓你直接看到三件事。第一，新 Session 不會自動帶著上一個 Session 的理解。第二，好的探索其實只需要很少檔案，就能拿到足夠的架構資訊。第三，寫進檔案系統的學習記錄，確實能讓理解跨越對話邊界，但它仍然要持續接受程式碼驗證。

成熟的 AI coding 工作流，不是期待代理每次都像一位熟悉專案多年的同事，而是把「重新認識環境」設計成一個快速、可觀察、可重用的步驟。當 Session 本身是可丟棄的，理解就不應該只留在 Session 裡。把代理帶到專案門口只是開始；讓它讀地圖、走過關鍵街區、記下可驗證的路線，才算真的進入工作狀態。
