## Learning goal

理解一個全新的 AI coding session 啟動時，代理實際知道什麼、不知道什麼，並掌握用 request logger 檢視起始內容、用探索問題建立 repo 地圖的方法，最終把陌生專案轉成可延續的工作上下文。

## Lesson

上一步把代理外殼重置到乾淨基線，context window 從 23k 壓到 6.6k，所有多餘的技能、MCP 工具和歷史設定都被暫時移開。現在你有了乾淨的工作台。但乾淨的工作台不等於有方向的團隊。代理坐在那裡，安靜地等你開口。

它在你說話之前，到底已經知道多少？

### 📝 代理一開始拿到的東西

透過 request logger（請求日誌記錄器），你可以逐行檢查代理在第一輪收到的全部輸入。攤開來看，裡面只有一堆環境與 git 中繼資料：

| 類別 | 內容 |
|------|------|
| 平台資訊 | Linux、macOS 或 WSL 的作業系統類型 |
| 工作目錄 | 你打開代理時所在的資料夾路徑 |
| Git repo 狀態 | 這個目錄是否為一個 git repository |
| Shell 環境 | bash、zsh 或其他 shell |
| 知識截止時間 | 模型的 training cutoff 日期 |
| Git branch | 目前在哪個 branch、主要 branch 是哪個 |
| Git 使用者 | 設定的 git user.name 和 user.email |
| 最近 commit | 最近幾筆提交的標題和 hash |

這些資訊足以讓代理知道自己「在哪裡」和「最近發生過什麼」，但不足以回答一個最基本的問題：這個專案是什麼。

### 💡 代理一開始不知道的東西

清單很長，而且每一項都很關鍵：

- 不知道專案裡有哪些檔案和目錄（它不會自動收到 file system listing）
- 不知道 `package.json` 裡裝了哪些相依套件
- 不知道 README 寫了什麼
- 不知道 `src/` 裡面的模組結構
- 不知道用了 React 還是 Vue
- 不知道有沒有測試、有沒有 CI/CD 設定、有沒有 monorepo 配置

更直白地說，代理的起始認知範圍大概就是「我知道我在 `/Users/andy/my-project` 這個目錄，它是一個 git repo，最近一次 commit 叫 fix router bug，這樣而已」。這和一個新同事第一天走進辦公室，只知道門牌號碼和最近的會議紀錄標題，是同一種處境。

### 🔧 這就是全新 Session 探索的核心前提

模型本身是無狀態（stateless）的，每一個 fresh session 都是一次全新的開始。上一個 session 對專案的理解、你昨天花了兩小時教它的架構知識、你清楚交代過的 coding convention，全部都不會自動延續到這個 session。不是因為工具壞了，而是因為模型在設計上就不會保留跨 session 的狀態。這是這整個 [[learn/ai-coding-crash-course/elements/fresh-session-exploration|全新 Session 探索 (Fresh Session Exploration)]] 的起點。

### ⚡ 第一個問題：測試探索能力的起手式

知道了代理的認知盲區之後，最直接的做法是給它一個需要探索才能回答的問題。課程中示範了一個經典的起手問題：

「這個專案的 tech stack 和 intended purpose 是什麼？」

這個問題的巧妙之處在於，它不是一個可以用猜測或套話回答的問題。代理如果沒有先讀檔案，就不可能知道這個專案用了 Next.js 還是 Express，不知道它的目的是做一個學習平台還是做一個電商後台。所以這個問題會迫使代理做一件事：去探索。

觀察代理怎麼回答這個問題，本身就是一堂課。在課程示範中，代理收到問題後，並沒有呼叫 sub-agent（子代理）去做初步探勘，而是直接自己讀了 README 和 `package.json`。這代表它的探索策略是「直接讀取關鍵檔案」，而不是「委派另一個代理去做初步掃描」。兩種策略都合理，但觀察代理的選擇能讓你了解這個 harness 的預設工作方式。

你可以嘗試不同的探索問題，看看代理的反應：

| 你的問題 | 代理的預期反應 |
|----------|----------------|
| 這個專案的主要目錄結構是什麼 | 列出 `ls` 的結果 |
| 有沒有測試 | 去找 `__tests__`、`*.test.ts` 或 `jest.config` |
| README 裡講了什麼 | 直接讀取 README 並摘要 |

每一個問題都在測試代理的不同探索路徑，也在幫你建立「代理怎麼認識這個 repo」的心理模型。

### 📋 把探索沉澱成外部記錄

單次讀檔的探索有個限制：它只存在於當前 session 的 context window 裡。你今天讀了 README、`package.json` 和三個核心模組，建立了對專案的理解，但如果之後清空上下文、開新 session，這些理解就消失了。模型是無狀態的，context window 是暫時的，只有寫進檔案系統的東西才會留下來。

這就是為什麼更進階的做法，不只是叫代理讀幾個檔案然後口頭回答你，而是讓它把探索結果寫成外部記錄（external record）。

在課程示範中，代理啟動了叫做 teach skill（教學技能）的工具，產出了一整套持久化檔案：

- `mission.md` — 學習目標（例如「判斷一個全功能 mini-Udemy 應用程式的變更」）
- `notes.md` — 學習筆記，追蹤你的進度和理解
- `resources.md` — 主要參考來源（例如 React Router v7 的官方文件）
- `styles.css` 和問答元件 — 共用資產庫
- 詞彙表（glossary）— 把專案中用到的關鍵術語和定義集中管理
- 第一篇 HTML 格式的教學文章 — 用 React Router 的原生語言解釋應用程式的 routing 機制，裡面包含一個重要的觀念提示：同一個元件（component）會在伺服器端和瀏覽器端各執行一次，這是 SSR（Server-Side Rendering，伺服器端渲染）的運作方式

這份教學文章最後有一個練習指示：「Reading is not learning. Run the app and prove the boundary.」讀完不等於學會，跑起應用程式，證明你理解了那個邊界。這不是一個被動的摘要，而是一個要求你動手驗證的學習任務。

### 📝 為什麼寫入檔案系統才是關鍵

teach skill 的真正價值不在它讀了多少檔案，而在它把探索結果寫進了磁碟。`mission.md`、`notes.md`、`resources.md`、詞彙表、第一篇教學文章，這些全部都是持久化的檔案。即使你之後清空 context window、關掉 session、甚至換一台機器，只要這些檔案還在，下一個 session 的代理就可以從這些檔案開始，而不是從零重建理解。

這也解釋了為什麼「把探索寫成外部記錄」比「口頭問答」更有價值：

| 方式 | 生命週期 | 下一個 session 能否取得 |
|------|----------|------------------------|
| 口頭問答 | 只活在 context window，session 結束就消散 | 不能 |
| 寫成檔案 | 留在檔案系統，成為環境的一部分 | 能 |

你是在用環境的持久性來彌補模型的無狀態性。這個做法可以推廣到任何陌生 repo。你不需要一個叫做 teach skill 的特殊工具，你需要的是一個習慣：每當你探索完一個新專案，就把關鍵發現寫進一個檔案。可以是 `LEARNING.md`，可以是 `CONTEXT.md`，可以是任何你和你的團隊能辨識的格式。重點是它必須脫離 context window，變成檔案系統中的一個穩定存在。

### 💡 技能是有狀態的學習工作區

teach skill 的另一個特性值得單獨拿出來看。它不只是幫你讀檔案和寫筆記，它本身就是一個有狀態的學習工作區（stateful learning workspace）。它把 mission、進度、詞彙和教學內容全部寫成檔案之後，你可以隨時清空 context window，然後從這些檔案恢復進度。代理會讀取 `mission.md` 知道目標是什麼，讀取 `notes.md` 知道你學到了哪裡，讀取詞彙表知道你在用什麼語言。

這和無狀態的模型形成一個有趣的對比。模型本身不記得你，但檔案系統記得你。teach skill 的做法就是把「模型應該記得的東西」從模型的腦袋搬到磁碟上，讓環境承擔記憶的角色。這是上下文衛生（context hygiene）的一個重要延伸：不只是清理多餘的噪音，還要把有用的理解外部化，讓它不依賴 context window 的容量限制。

### ⚡ 探索的品質決定後續工作的上限

回到最核心的觀點。一個 fresh session 的探索品質，不是「準備工作」，而是「基礎建設」。如果你在探索階段就對專案結構產生了錯誤的理解，後續的規劃、實作、測試和 review 全部都會建立在那個錯誤之上。反之，如果你在探索階段就花時間把地圖建立起來，後續每一步都會更有效率。

這也是為什麼課程建議在實作任何功能之前，先讓自己成為這個 repo 的「絕對專家」（absolute expert）。不是讀了一篇 README 就覺得自己懂了，而是能回答這類結構性問題：

- 技術棧是什麼？
- 主要模組之間的依賴關係是什麼？
- 路由怎麼運作？
- 狀態管理用什麼方案？

只有在你能回答這些問題之後，開始寫程式碼才有意義。

所以，當你開了一個全新的 session，不要急著給任務。先問一個需要探索才能回答的問題。觀察代理怎麼回答，看它讀了什麼檔案、跳過了什麼檔案、猜測了什麼。然後根據觀察，決定你是否需要更深入的探索，或者用外部記錄把理解固定下來。探索不是浪費時間，探索是你在為後續所有工作建立品質的天花板。
