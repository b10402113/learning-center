## Learning goal

學完這一步，你能理解全新 Session 為什麼必須重新探索 repository，分辨代理在啟動時真正知道的環境中繼資料與完全未知的專案內容，並設計一個由證據開始的探索流程。你也能讓代理把探索結果寫入檔案系統，形成可以跨 Session 延續的學習工作區，而不是把專案理解寄託在模型暫時保留的對話脈絡上。這一步的核心概念是 [[learn/ai-coding-crash-course/elements/fresh-session-exploration|全新 Session 探索 (Fresh Session Exploration)]]。

## Lesson

### 用八步驟把陌生 repo 變成可工作的地圖

全新 Session 的探索可以先固定成八個步驟。建立乾淨起點，確認 agent、工作目錄和基本設定；先問技術棧、用途、主要結構與證據，並要求不要修改檔案；觀察它讀了什麼、用了哪些工具，以及是否承認未知；檢查 README、依賴宣告、lockfile、scripts 和主要設定；再沿著路由、頁面、資料模型、服務邏輯和代表性測試建立產品地圖；對重要結論要求檔案證據；把穩定理解寫入 mission、notes、resources、glossary 或 lesson；最後在實作前列出已知、未知、影響範圍與驗證指令。

這個順序的價值，在於把「先猜一個答案」改成「先取得足夠證據」。它也避免另一個極端：為了證明自己探索過，就把整個 repository 一次塞進上下文。好的探索不是讀最多檔案，而是用最少且合適的證據支撐下一個決策。

### 先接受一個不舒服的事實：全新 Session 幾乎不認識你的專案

開啟一個新的 AI coding agent Session 時，畫面通常已經顯示了專案目錄，代理也能回答一些關於目前環境的問題。這很容易讓人產生錯覺，以為它「已經進到 repository 裡」，所以應該已經知道專案的大致結構。實際上，進入目錄只代表它站在某個位置，不代表它讀過那個位置裡的任何內容。

一個 fresh Session 在真正開始探索前，通常只拿到幾類環境與 Git 中繼資料，例如平台是 Linux、WSL 或 macOS，主要工作目錄在哪裡，目前是不是 Git repository，使用哪個 shell，模型的知識截止時間，目前 branch 與主要 branch 是什麼，Git 使用者是誰，以及最近有哪些 commit。這些資料足以回答「我在哪裡」和「這裡最近發生過什麼」，卻不足以回答「這個產品服務誰」或「這個專案怎麼運作」。

它通常還不知道以下內容：

- 檔案系統中有哪些檔案與目錄。
- 專案使用 React、Vue、Svelte、Node、Python 或其他技術棧。
- 啟動、測試、型別檢查與建置的正確指令。
- 哪些目錄是前端、後端、資料庫、共用套件或測試。
- 最近的 commit 是否真的代表目前程式碼的主要設計。
- 產品的預期用途、使用者流程和重要限制。
- 團隊在命名、錯誤處理、測試和部署上的慣例。

因此，代理一開始若對專案做出非常完整的判斷，卻還沒有讀過任何檔案，那個判斷只能是推測。它可能碰巧猜對，但你不能把碰巧猜對當作已經理解。

### 為什麼模型的無狀態性會逼我們重新探索

模型本身是無狀態的。它每次收到一個模型請求時，都是根據這一次被送入的上下文產生下一段輸出，不會在參數裡替你保存「昨天曾經看過這個 repository」的個人記憶。代理外殼可以管理 Session、保存訊息、呼叫工具，讓整個系統看起來像有連續記憶，但這種連續性只存在於被重新送入請求的對話內容與工具結果中。

當你清空上下文或建立新的 Session，先前對話中那些沒有落盤的理解就不再自動存在。代理不會因為你昨天已經花兩小時解釋過架構，今天就自然知道同一件事。你知道的是同一個專案；對新 Session 來說，這是一個新的相遇。

這個限制聽起來像模型的缺點，但它其實也是一個工作流程約束。既然模型不會自動攜帶理解，我們就必須在每次重新開始時做兩件事：先取得足以工作的證據，再把值得延續的理解保存到環境。前者是探索，後者是外部記憶。兩者缺一不可。

為什麼這件事很重要？因為如果你跳過探索，後面所有規劃、實作、測試與評論都可能建立在錯誤的專案模型上。代理也許知道「課程評論」這個 commit 名稱，卻不知道評論資料儲存在什麼表；也許看到 `app` 目錄，就猜它是一般 React 應用，卻不知道真正的路由、loader 和 server boundary。錯誤的第一個假設會像地基偏掉一點的房子，後面每一層都可能看起來合理，最後卻整體不對。

### 把探索問題問對：先問技術棧與用途

全新 Session 的第一個任務，不應該是「直接實作這個功能」。更好的起手式是要求代理先判斷專案的技術棧與預期用途，例如：

> 請探索這個專案，說明它使用的技術棧、主要用途、重要目錄，以及你用來做出判斷的證據。先不要修改任何檔案。

這個問題有三個作用。

第一，它把代理從產出模式切換到理解模式。若你一開場就說「幫我加一個功能」，代理很容易把完成某個檔案當成首要目標，迅速讀幾個看似相關的位置後開始寫程式。先要求探索，則把讀取和判斷放在修改前面。

第二，它要求代理提供證據，不只給結論。技術棧不是從目錄名字猜出來的，而應該從 `package.json`、lockfile、設定檔、入口檔、路由檔和 README 等內容交叉確認。產品用途也應該從 README、頁面結構、資料模型和實際執行方式推導，而不是只根據最後一個 commit 的標題。

第三，它讓你觀察代理採用什麼探索策略。它可能自己列出檔案、搜尋關鍵字，再讀取幾個核心檔案；也可能把探索工作交給 sub-agent，等摘要回來後再回答；也可能只讀 README 就過早下結論。你不只要看答案，也要看它怎麼得到答案。探索路徑本身會告訴你這個 harness 的預設行為，以及你是否需要把探索範圍說得更清楚。

### 一次好的探索不是把整個 repository 全部讀完

「重新探索」不等於把所有檔案一次塞進上下文。這樣做會把新的 Session 很快推向上下文膨脹，反而破壞理解品質。探索的目標是建立一張足夠精確的地圖，不是把每一個檔案都背進模型。

可以採用由外而內的分層方式。

第一層是定位。先確認目前目錄、Git 狀態、根目錄有哪些重要入口檔，並找出 README、package manifest、lockfile、主要設定檔和常見的 source 目錄。這一層回答「專案由哪些大區塊組成」。

第二層是識別技術棧。讀取 `package.json` 或其他依賴宣告，確認 framework、runtime、測試工具、資料庫工具和 scripts。再讀取 framework 的主要設定與入口檔，避免只靠依賴名稱推斷實際用法。這一層回答「專案用什麼方法組裝起來」。

第三層是理解產品邊界。檢查 README、頁面或路由結構、核心資料模型，以及一兩條代表性的使用者流程。這一層回答「這套程式為誰解決什麼問題」。

第四層才是進入當前任務相關的局部細節。當你知道產品結構與技術棧後，再追蹤某個功能涉及的 component、route、API、schema 和測試。這一層回答「眼前要改的地方與其他部分怎麼連接」。

這個順序能減少兩種錯誤。一種是只看單一檔案，沒有架構脈絡，導致把局部慣例誤認成全域規則。另一種是無差別讀取所有內容，讓真正重要的資訊淹沒在工具輸出裡。探索的品質不由讀了多少檔案決定，而由是否以足夠證據建立正確的下一步決策決定。

### 用「讀檔再回答」取代「先猜再補證據」

代理在陌生 repository 中最危險的表現，不一定是明顯胡說，而是用非常自然的語氣說出沒有證據支持的內容。例如它看到 `routes` 目錄，就直接說「這是使用 React Router 的前端路由」；看到 `db` 目錄，就直接說「這裡使用 PostgreSQL」；看到一個名為 `server` 的檔案，就斷言所有資料存取都在 server side 完成。這些推斷可能正確，也可能只是命名巧合。

你可以要求它把每個高層判斷都綁定到觀察到的檔案。好的探索報告至少會說明：看了哪個檔案，看到什麼內容，因此得到什麼結論，還有哪些部分尚未確認。這種表達方式會自然暴露不確定性，也方便你挑選下一個追問。

例如，與其接受「這是一個 React Router 應用」，不如要求它說明是否在 `package.json` 中看到相依套件，是否在路由檔中看到 route module，是否在 server 與 browser 兩端都存在相同 component。與其接受「這個功能使用資料庫」，不如要求它找到 schema、query 或 migration 的實際位置。證據越接近程式碼，結論就越可驗證。

探索報告可以用下列表格整理：

| 問題 | 應尋找的證據 | 尚未確認時的做法 |
| --- | --- | --- |
| 使用什麼技術棧 | 依賴宣告、lockfile、入口與設定檔 | 標記推測，繼續讀核心設定 |
| 專案的用途 | README、路由、頁面、資料模型 | 先說已知使用流程，不擴大推論 |
| 如何啟動與驗證 | scripts、測試設定、建置設定 | 找到指令前不要自行發明指令 |
| 當前功能在哪裡 | route、component、service、schema、測試 | 先畫出呼叫鏈，再考慮修改 |
| 哪些規則必須遵守 | 專案指引、既有實作、測試與 lint 設定 | 以現有模式為準，明確標註未知處 |

重點不是要求代理寫一份漂亮的報告，而是讓它的理解可以被檢查。可檢查的探索比流暢但無法追溯的自信更有價值。

### 探索時要觀察 sub-agent 與主代理的分工

有些 harness 會把深入探索交給 sub-agent。主代理像是協調者，先提出探索問題，再啟動一個或多個較小的工作單位，讓它們分別調查技術棧、路由、資料模型或測試策略，最後把摘要帶回主 Session。這種安排可以把大量讀檔工作放在獨立上下文中，避免主代理的工作桌被所有原始輸出塞滿。

但 sub-agent 不是探索品質的保證。你仍然要確認它探索了什麼範圍、摘要是否保留關鍵檔案與不確定性，以及主代理是否真的使用了結果。若 sub-agent 只讀一份 README 就回報「已了解整個專案」，那只是把過早猜測搬到另一個 Session。好的分工應該讓主代理獲得較濃縮、較有用的證據，而不是多一層看不見的黑箱。

課程示範中的探索沒有生成 sub-agent。代理直接讀取 README 與 `package.json`，再依照 teach skill 建立學習材料。這個案例很有用，因為它提醒你不要把 sub-agent 當成固定儀式。專案規模、問題難度和 harness 能力不同時，直接探索可能更簡單；需要平行處理或大量深入閱讀時，才值得委派。判斷標準應該是上下文與任務的匹配，不是「有 sub-agent 才算專業」。

### 把探索結果寫進檔案系統

即時回答只能在目前 Session 裡幫助你。若探索結果沒有保存，下一次清空上下文後，代理仍然會從環境中繼資料重新開始。更穩定的做法是把重要理解寫成外部文件，讓檔案系統承擔持久狀態。

在課程示範裡，代理啟動 teach skill 後，不只是口頭介紹 playground，而是建立一組可以持續使用的學習資產，包括 mission、學習筆記、主要資源、共用樣式資產、詞彙表和第一篇教學文章。這些檔案讓陌生 repository 不只被「掃過」，而是被轉換成一個可以反覆閱讀、提問和驗證的學習工作區。

這種做法有一個關鍵轉變：代理不再只是回答「這個專案是什麼」，而是把「如何理解這個專案」也設計成可持續的資料。mission 說明學習或工作的方向；notes 保存已確認的理解和仍待釐清的問題；resources 集中列出應該查閱的主要文件；glossary 固定專案中特殊的名詞；教學文章則把局部結構組織成可以由讀者驗證的課程。

為什麼落盤很重要？因為檔案是環境的一部分，而環境可以跨 Session 存活。你清空對話，檔案還在；你換一個模型，只要它能讀檔，仍然可以接續；你把工作交給另一位代理，也能透過這些材料快速建立共同起點。這不是讓代理真正擁有永久記憶，而是把記憶放在一個可以檢查、修改、版本控制和移交的位置。

### 教學工作區不是自動產生的真相

把探索結果寫進檔案系統很有用，但不要把生成的文件當成永遠正確。它們仍然是代理根據當時證據整理出的模型，可能遺漏重要路徑，也可能在程式碼改變後過時。持久化解決的是「每次從零開始」的問題，不是「從此不必驗證」的問題。

可以在每份探索文件中保留三種狀態：已由程式碼確認的內容、合理但尚未驗證的推論，以及需要下一輪調查的問題。當專案發生重大變更時，優先更新技術棧、啟動方式、主要路由和核心資料模型。不要讓一篇很完整的舊教學文章掩蓋目前實際行為。

如果代理要根據這些文件開始實作，也應要求它在使用前檢查文件是否仍與程式碼一致。這會形成一個小型閉環：探索產生文件，文件幫助後續工作，後續工作再暴露文件中的過時部分，然後重新驗證。真正有價值的持久化記錄不是一次生成後永不觸碰，而是能在工作中被修正。

### 從探索進入實作前的檢查點

探索完成後，不要只問「你準備好了嗎」。請讓代理用短摘要回答幾個可驗證的問題：

1. 這個專案的主要用途是什麼，證據在哪裡？
2. 使用的 runtime、framework、資料庫與測試工具各是什麼？
3. 目前任務涉及哪些檔案或模組，它們之間如何連接？
4. 啟動、測試、型別檢查和建置要使用哪些既有指令？
5. 哪些需求、限制或設計決定仍然未知？
6. 哪些探索結果已經寫入檔案系統，下一個 Session 要從哪裡讀取？

如果它只能回答前兩題，代表還處於專案導覽階段；如果它能回答前四題但說不出未知之處，可能仍然過度自信；如果它能指出證據、限制與持久化位置，才比較接近可以安全進入局部實作的狀態。

這個檢查點也能防止另一個常見錯誤：把「代理能夠讀檔」誤認為「代理已經理解設計」。讀取 README 和 `package.json` 只是開始，真正的理解還包括路由如何流動、資料如何保存、測試如何驗證，以及當前功能與產品目的的關係。探索不需要無限延長，但必須足以支撐下一個決策。

### 一個可重複的 fresh Session 探索流程

你可以把流程固定成八個步驟，之後套用到自己的 TypeScript、Node 或其他 repository。

1. **建立乾淨起點。** 確認你知道目前使用的 agent、工作目錄和載入中的基本設定；不要假設新 Session 繼承上一段對話。
2. **先問高層問題。** 請代理說明技術棧、專案用途、主要結構與證據，並要求它先不要修改檔案。
3. **檢查探索行為。** 觀察它讀了哪些檔案、使用哪些工具、是否啟動 sub-agent，以及是否在證據不足時承認未知。
4. **確認入口資料。** 讓它讀 README、依賴宣告、lockfile、scripts 和主要設定，建立技術棧與操作方式的基線。
5. **建立產品地圖。** 依序探索路由、核心頁面、資料模型、服務邏輯與代表性測試，不要一次無差別讀完所有檔案。
6. **用追問消除猜測。** 對每個重要結論要求檔案證據，並追問尚未確認的部分。
7. **把穩定理解落盤。** 使用 teach skill 或其他適合的工作流，保存 mission、筆記、資源、詞彙和可重用的教學材料。
8. **在實作前做摘要驗證。** 讓代理列出已知、未知、影響範圍與驗證指令，再決定是否開始修改。

這八步的核心不是形式，而是順序。先建立地圖，再決定走哪條路；先取得證據，再要求產出；先保存理解，再把 Session 視為可以丟棄的暫時工作區。

### Fresh Session 與其他上下文技術的分工

全新探索很容易和其他上下文管理方法混在一起，但它處理的是一個特定問題。外殼重置處理的是代理開始前載入了多少無關設定、技能與工具；上下文計數器讓你看見這些內容和後續工作如何增加；compaction 會把同一個代理與同一個目錄中的舊 Session 濃縮成較短的摘要；handoff 則把理解包成可攜文件，交給另一個代理、目錄或人。

fresh Session exploration 處理的是：在沒有可靠既有脈絡時，代理如何取得 repository 的真實結構。你可以先重置外殼，讓起點更乾淨；再用計數器觀察探索成本；如果要留在同一個工作流，可以用 compaction 保留重要決策；如果要跨工具移動，可以用 handoff 傳遞摘要。但這些技術都不能替代第一次對陌生專案的證據式探索。

簡單地說，重置清掉背景噪音，探索建立地圖，計數器顯示負載，compaction 濃縮歷史，handoff 搬運理解。每個工具都在處理不同邊界。當你知道問題屬於哪個邊界，就不會用清空對話來解決缺少專案知識，也不會用一份舊摘要掩蓋程式碼已經變更的事實。

### 最後的實作練習

在自己的 repository 開一個新的 Session，先不要交付功能。輸入一個要求代理探索技術棧與用途的問題，保存它的回答和工具活動。接著要求它找出啟動、測試與型別檢查指令，再要求它選一條使用者流程，從入口一路追到資料或畫面輸出。過程中記下它引用的檔案，以及哪些判斷需要你補充或糾正。

然後讓代理建立一個小型探索筆記，至少包含以下欄位：

- 專案用途與主要使用者。
- runtime、framework、資料庫和測試工具。
- 根目錄的關鍵檔案與各自用途。
- 一條已追蹤的代表性流程。
- 已確認的慣例與尚未確認的問題。
- 下一次 Session 應該先讀取的檔案。

清空 Session 後，要求代理只讀這份筆記，再回答同樣的高層問題。比較兩次回答，檢查筆記是否真的降低重新探索成本，又是否遺漏了需要直接回到程式碼確認的細節。最後讓代理重新打開一個核心檔案，確認持久化筆記和目前程式碼仍然一致。

這個練習會讓你親眼看見三件事。第一，新 Session 不會自動擁有上一個 Session 的理解。第二，良好的探索可以在很少檔案中取得足夠的架構資訊。第三，寫進檔案系統的學習記錄能讓理解跨越對話邊界，但它必須持續接受程式碼驗證。

真正成熟的 AI coding 工作流，不是期待代理每次都像熟悉專案多年的同事，而是把「重新認識環境」設計成一個快速、可觀察、可重用的步驟。當 Session 是可丟棄的，理解就不應該只存在 Session 裡。把代理帶到專案門口只是開始；讓它讀地圖、走過關鍵街區、記下可驗證的路線，才算真正進入工作狀態。
