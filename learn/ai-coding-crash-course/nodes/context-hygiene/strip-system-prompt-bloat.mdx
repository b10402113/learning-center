## Learning goal

學完這一步，你能辨認代理的 system prompt 中哪些內容會在每次 request 固定出現，理解它們如何同時佔用 token、注意力與聰明區，並用一個可重複的測量流程逐項清除不需要的 connectors、workflows、bundled skills、artifacts 與工具定義。你會知道「現在沒有使用某工具」和「讓工具根本不出現在 system prompt」是兩件不同的事，也能把這套方法轉移到 Claude Code 以外的 harness。最後，你能在維持必要功能與安全限制的前提下，為自己的 TypeScript/Node 專案建立一個較輕、較容易診斷的代理工作起點。

## Lesson

### 先從一個數字看見問題

課程示範一開始的上下文大約是 68.3k token。這不表示代理已經做了 68.3k token 的事，而是還沒真正開始工作前，就先背了這麼多固定內容。停用 claude.ai connectors 之後，大約降到 47k；關閉 workflows 之後，大約 39k；停用 bundled skills 之後，大約 37k；停用 artifacts 之後，大約 33k。

這組數字先說明一件事：代理真正開始接任務前，工作空間就可能已經被一大堆預設能力吃掉了。所以後面的清理不能靠感覺，也不能只看設定檔有幾行。要用同樣條件，一項一項量。

### 先看見每一輪都要背上的東西

很多人會把 system prompt 想成一段開場白，但它其實比較像是每次 request 都會一起送出的固定資料。模型本身沒有持久記憶。外殼想讓它看起來能持續工作，就得在每一輪 request 裡重新塞進角色說明、可用工具、權限邊界、工作流程、技能描述，還有其他系統層級的資訊。對話歷史會越來越長，工具結果會越來越多，而 system prompt 則像一塊從第一輪就一直存在的底板。

這會帶來兩種成本。第一種是比較好算的 token 成本。凡是固定放進 request 的文字，每次都要一起處理。就算某個工具這一輪根本不會用到，它的名稱、描述、參數 schema 和使用限制，還是可能照樣送出。第二種比較不容易直接看到，但同樣重要，就是注意力成本。模型得同時處理目前的需求、剛讀到的程式碼、測試輸出，還有一大串工具定義。每多一段不相關的說明，就多一批要忽略的文字，而忽略本身也要花判斷力。

這就是 [[learn/ai-coding-crash-course/elements/system-prompt-bloat|System Prompt 贅肉 (System Prompt Bloat)]] 的核心問題。贅肉不只是看起來雜亂。它會在任務開始前就先壓縮上下文窗口的可用空間，讓代理更早碰到聰明區的邊界，也讓後面的探索、規劃和實作都得和更多固定噪音競爭。當 session 越拉越長，這幾千、幾萬 token 的固定開場負載還會一再重複出現。

所以，清理 system prompt 不是為了追求一個越小越好的漂亮數字，也不是要把代理削成沒有工具的空殼。真正目標是讓固定載入的內容和你現在要做的工作對齊。跨任務都需要的規則、必要的檔案操作能力、安全限制，應該保留。只有特定情境才需要的能力，可以延後載入。完全用不到、只是因為預設開啟或過去實驗殘留的內容，才應該停用或移開。

### 用一次實驗建立基線

清理之前，先量。不要在還沒輸入實際任務前，就憑印象猜哪個設定最肥。先開一個新的 session，不要要求代理讀檔、跑命令或改程式，直接看目前的上下文使用量。Claude Code 的示範是用 `/context` 觀察 system prompt、工具、技能、訊息等分類的 token 數量。其他 harness 可能用不同指令，或把資訊顯示在別的地方，但概念一樣：先拿到一個不受工作內容干擾的起始讀數。

這個基線至少要記兩件事。第一，總 token 數。第二，主要來源是什麼，例如連接器、技能、工作流程、工具定義，或其他系統說明。只記總數，你之後很難判斷哪個改動有效；只記來源名稱，你又不知道哪一類最值得先處理。把它當成工程裡的效能基準會比較好理解。每次只改一個有意義的設定，重新啟動 harness，再看同一個指標，前後差異才有辦法解釋。

課程裡那組數字很值得參考。開著多項預設功能時，初始上下文大約是 68.3k token。停用 claude.ai connectors 後，降到約 47k；再關掉 workflows，降到約 39k；停用 bundled skills 後約 37k；停用 artifacts 後約 33k。這些數字不會是所有環境的標準答案，但它清楚提醒你：固定能力的體積，常常比人直覺想的大很多。設定檔裡看起來只是幾行 JSON，真正注入的內容卻可能包含一長段說明和完整的介面定義。

有了基線，你也比較不會把問題一股腦怪到模型頭上。當代理一開始就背著六、七萬個固定 token，後面表現變差，原因可能來自模型、任務、程式碼，也可能只是環境先塞了太多東西。量過之後，你才知道自己是在改善 harness，不是在盲目換模型，也不是把所有失敗都推給提示詞。這就是上下文衛生的重要習慣：先看 request 裡實際有什麼，再決定要改哪裡。

### 優先處理固定的大來源

第一批值得審核的是 connectors。連接器會把外部服務或資料來源的能力帶進代理環境。它們也許很方便，可以搜尋、同步、讀取，或觸發某些操作，但方便不代表每次工作都需要。假設你今天只是要修一個 Node API 的型別錯誤，那外部設計工具、通知服務，或其他遠端整合的完整描述，就沒有理由固定佔用每一輪 request。停用一個大型 connector 後，如果 `/context` 數字明顯下降，你就拿到了一個很具體的證據：它原本確實是固定負載來源。

第二批是 workflows。工作流程通常比單一工具更肥，因為裡面往往同時包含觸發條件、步驟、輸入格式、輸出格式，以及相關工具。某個 workflow 可能是為了報告、部署、遠端操作，或某個特定產品功能準備的。只要現在的任務根本不會走那條路，整份 workflow 留在 system prompt 裡，就只是多出一組要判斷的可能性。停用後重新啟動，再讀一次上下文，看看數字有沒有下降，同時確認日常需要做的事還是能做。

第三批是 bundled skills。技能的價值本來就在於按需提供一套可重用流程，但模型可自動發現的技能，通常至少會把名稱和 description 放進 parent context。有些 harness 甚至會預載更多內容。技能一多，代理每一輪都得多考慮很多「也許該叫這個」的可能。偶爾才會用到的技能，可以改成由使用者明確呼叫，或把詳細內容留在文件裡，只保留短指標做導航。對眼前完全不需要的 bundled skills，就先停用，再用同一套基線方法量回收了多少空間。

第四批是 artifacts。產物能力對文件、互動畫面，或某些輸出任務可能很有用，但它不會因為名字聽起來通用，就自然適合所有 repo。假設你的工作主要是維護 TypeScript、跑測試、看 diff，那跟這次任務無關的產物工具，就不該在每一輪 request 裡固定存在。這裡要有分寸：暫時停用，不等於永久刪除。你完全可以保留原設定，等真正需要時再打開，或另外做一套工作配置。

這四類通常該先看，原因很簡單：它們不是零碎句子，而是整批注入的能力。刪掉一條短提示，也許只回收幾十個 token；停用一個 connector、一個 workflow，或一組技能，卻可能一次拿回幾千甚至幾萬個 token。優先順序應該交給測量結果決定，不是交給哪一行設定最好改來決定。

### 不使用工具，不代表工具沒有成本

清理工具定義時，很容易漏掉一個差別：你這次沒有呼叫某個工具，只代表它沒有產生操作結果，不代表它沒有佔用上下文。只要工具仍然被 harness 暴露給模型，它的名稱、描述、輸入參數、限制，還有可能的使用方式，就可能還留在 system prompt 裡。模型每次面對新任務時，仍然得把它算進可用能力的判斷。

課程示範用 deny 直接處理一批目前不會用到的工具，包括 notebook edit、design system sync、cron、plan-mode toggle、push notifications、remote trigger、report findings 和 wake-up scheduling。這樣做的重點，不只是把工具鎖起來，而是讓整段工具定義從 system prompt 移出去。這和把工具留著、只是操作時不選它，對上下文的結果完全不同。

你可以把工具分成三類。第一類是目前任務的核心工具，例如讀檔、寫檔、跑測試、檢查版本控制狀態。這些應該保留，因為你雖然能把數字壓小，卻也同時拿掉了代理完成工作的基本手段。第二類是偶爾使用的工具，例如特定資料庫、設計整合或通知整合。這些可以按工作類型啟用，或改成明確呼叫。第三類是你在現在的工作流程裡根本沒有角色、也說不清什麼時候會用到的工具。這種工具就適合直接 deny，因為它們有固定成本，卻沒有對應回報。

工具權限還有一層安全價值。保留的工具越多，代理可以走的路就越多，使用者也越難快速判斷它到底能做什麼。deny 讓不需要的工具同時離開可用操作集合和 system prompt，一方面減少上下文負載，一方面也縮小代理在這次任務裡走偏的空間。當然，權限規則不能只為了數字就隨便刪。像阻止危險命令的限制，可能只佔很小空間，但它對安全的價值很高。

示範最後還移除了冗長的 `ask user question` 工具定義，讓初始上下文降到兩萬 token 以下。這個例子提醒你，單一工具也可能很大。不要因為某個設定只出現一次，就以為它影響很小。要看的是它實際帶進來多少文字。也不要因為工具名稱看起來合理，就直接認定它值得固定載入。比較好的判斷方式，是把它放回目前工作流程裡問自己：模型真的需要在每一輪都看見它嗎？

### 每次只改一項，讓數字能說話

清理 system prompt 最怕一次改太多。你如果同時關掉 connectors、技能、workflow，外加十幾個工具，最後看到 token 降了，卻不知道到底是哪個改動最有用。之後如果某個功能壞掉，你也很難知道應該恢復哪一項。比較穩的做法是，一次只做一組邊界清楚的改動，重新啟動，查看 `/context`，記下前後差異，再做下一步。這樣雖然慢幾分鐘，但你會得到一張自己的上下文地圖。

重新啟動這一步不能省。system prompt 是在建立或初始化 request 時組出來的。已經開著的 session，可能還留著舊設定或舊工具列表。你在同一個 session 裡改設定，看到的結果不一定表示新設定真的生效了。正確的測量循環應該是：改設定、關掉舊 session、重新啟動 harness，然後在沒有實際任務的狀態下再次查看上下文。每次都維持同樣的觀測條件，前後比較才有意義。

記錄方式可以很簡單。你只要記下改了什麼、重啟後 token 變成多少、拿掉了哪些主要來源，以及有哪些功能受到影響。某個改動如果只讓數字掉一點點，卻讓工作變得不穩，那通常不值得留。反過來說，如果一個改動回收了很多 token，而且不影響目前任務，那它就很適合保留在精簡配置裡。這不是數字遊戲，而是在比較固定上下文成本和功能價值。

### 清理的邊界是「匹配工作」，不是「越少越好」

system prompt 不是越小越好。假設你為了回收空間，把跑測試需要的權限、團隊要求的安全限制，或代理理解專案結構必須用到的短指標都拿掉，起始數字也許會變漂亮，但後面可能只會換來更多失敗、返工和人工確認。那些錯誤花掉的上下文和時間，往往比你省下的幾百個 token 還多。

一項內容值不值得常駐，可以用三個問題來判斷。它是不是跨任務都適用。它能不能避免高代價的錯誤。它是不是真的需要模型在每一輪 request 都知道。如果這三個問題都答得很清楚，那內容通常值得保留。如果它只在特定情境才需要，就可以考慮把完整程序放進文件，只留下短小的 pointer。要是它已經在程式碼、README，或其他單一真實來源裡能取得，那也不必在 system prompt 再重複整段。若移除之後代理行為沒有可觀察差異，那它可能本來就是 no-op。

這裡也能看出 system prompt 贅肉和 steering 檔案修剪之間的關係。前者主要是在看 harness 自動注入的能力、工具和整合；後者則是在看人寫進引導檔案裡的規則，有沒有重複、過時，或根本沒作用。兩者其實都在回答同一個工程問題：這段內容值不值得一直佔著上下文。差別只是來源不同。通常先清外殼裡的固定大戶，再回頭處理長期引導裡的沉積物，會比較容易看見每一步的效果。

### 把方法帶到其他 harness

課程是用 `.claude/settings.json` 示範，所以裡面的欄位、工具名稱和操作方式，都屬於 Claude Code 的環境。你不應該把檔名、設定鍵或 slash command 直接當成所有代理工具通用的手冊。不同 harness 可能把 system prompt、工具清單、技能註冊和連接器配置放在不同位置，也可能提供完全不同的診斷介面。

真正可以轉移的是審計方法。先找到那個 harness 怎麼看初始上下文，再盤點哪些內容在第一個任務開始前就已經被注入。把來源分成設定、技能、工作流程、工具、連接器和其他整合。然後選一個目前不需要的來源，先暫時停用，重新啟動，再做一模一樣的量測。數字如果下降，就保留紀錄，再判斷停用會不會影響工作。數字如果沒有變，就檢查這個設定是不是根本沒有進入 system prompt，或真正來源其實在另一層。

這套方法也能用在你自己的專案配置上。你可以為日常功能開發、資料庫維護、部署工作，或學習實驗，準備不同而且可恢復的配置。每一套配置都應該有清楚目的，也應該知道哪些能力會常駐。切換專案時，不要只問代理「你現在會什麼」，還要看它在第一輪 request 真的收到了什麼。能夠查看、量測、調整這個輸入，才算真正掌握 harness，而不只是照單全收預設值。

### 一個可重複的清理流程

開始前，先開一個沒有真實任務的全新 session，取得上下文基線。接著看分類資訊，找出最大的固定來源。優先從 connectors、workflows、bundled skills 和 artifacts 開始，因為它們通常是整批載入的能力。每次停用一項，或一組邊界清楚的能力，重新啟動 harness，再查看同一個上下文指標。

接著審核工具。把工具分成必要、偶爾使用、目前沒有角色三組。必要工具不要為了壓低數字就移掉。偶爾使用的工具，可以考慮延後載入，或改成由使用者明確呼叫。沒有角色的工具就直接 deny，並確認工具定義是不是已經從 system prompt 消失。要是還有特別大的工具定義，就繼續逐項找、逐項量，直到初始上下文回到一個你能理解、也能順利工作的水位。

最後還要做一次功能驗證。讓代理完成一個小而安全的任務，例如讀取專案入口、執行既有 typecheck，或檢查某個指定模組的測試。確認精簡後的配置仍然能讀檔、能跑必要命令、能遵守權限限制，也能在需要時使用保留下來的技能。只有數字下降，卻沒有做功能驗證，這次清理就還不算完成。

做完之後，把結果整理成自己的配置決策。哪些能力固定開啟，哪些只在特定工作中啟用，哪些被明確 deny，哪些詳細流程改放進文件。這樣之後如果上下文又膨脹，你可以直接拿新的基線來比較，而不用重新猜。只要某項整合被加進來、某個 workflow 不再使用，或某個 bundled skill 只是短期實驗，都應該把它當成需要重新審計的變更。

### 你應該帶走的判斷

當你發現代理表現變差，先問它的上下文裡是不是塞了太多固定內容。看到設定檔變大，先問哪些項目真的會被注入 system prompt。看到某個工具沒有被呼叫，也不要急著把它當成沒有成本；只要它的定義還在，每一輪 request 就可能繼續帶著它。看到 token 數下降，也不要立刻認定所有被移掉的東西都不重要；還要確認必要功能、安全限制和工作流程有沒有一起被破壞。

清除 system prompt 贅肉，本質上是一種維護習慣。它讓代理的固定負載變得可觀察、可比較、可恢復。你不需要背下課程示範裡的每個數字，也不需要照抄某個產品的每個欄位。只要你能在開工前看見代理到底背著什麼，知道哪些內容只是預設留下來的能力，再用一次一項的方式把無關內容移開，你就能把更多上下文留給真正需要理解的程式碼、需求和推理。
