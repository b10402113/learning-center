## Learning goal

學完這一步，你能辨認代理的 system prompt 中哪些內容會在每次 request 固定出現，理解它們如何同時佔用 token、注意力與聰明區，並用一個可重複的測量流程逐項清除不需要的 connectors、workflows、bundled skills、artifacts 與工具定義。你會知道「現在沒有使用某工具」和「讓工具根本不出現在 system prompt」是兩件不同的事，也能把這套方法轉移到 Claude Code 以外的 harness。最後，你能在維持必要功能與安全限制的前提下，為自己的 TypeScript/Node 專案建立一個較輕、較容易診斷的代理工作起點。

## Lesson

### 先從一個數字看見問題

課程示範的初始上下文約為 68.3k token。這不是代理已經完成了 68.3k token 的工作，而是它在真正開始處理任務前，先背著這些固定內容。停用 claude.ai connectors 後約 47k，關閉 workflows 後約 39k，停用 bundled skills 後約 37k，停用 artifacts 後約 33k。這組數字先給我們一個簡單結論：代理的工作空間，可能在第一句任務送出前就被預設能力大量佔用。接下來的清理，必須用相同條件逐項測量，而不是靠設定檔看起來有幾行來猜大小。

### 先看見每一輪都要背上的東西

代理的 system prompt 很容易被誤會成一段開場白。它其實更接近每次送往模型供應商的請求所攜帶的一部分固定資料。模型本身沒有持久記憶，外殼要讓它看起來能連續工作，就得在每輪 request 中重新提供角色說明、可用工具、權限邊界、工作流程、技能描述與其他系統級資訊。對話歷史會越來越長，工具結果會不斷加入，system prompt 則像一塊從第一輪就存在的固定底板。

這件事帶來兩種成本。第一種是很容易計算的 token 成本。固定放進請求的文字，每次都需要被處理。即使某項工具在這一輪完全不會用到，它的名稱、描述、參數 schema 和使用限制仍可能隨請求送出。第二種成本比較難直接看見，卻同樣重要，那就是注意力成本。模型要在當前需求、剛讀到的程式碼、測試輸出和一大串工具定義之間建立關聯。每多一段無關說明，就多一批需要忽略的文字。忽略本身也需要模型做判斷。

這就是 [[learn/ai-coding-crash-course/elements/system-prompt-bloat|System Prompt 贅肉 (System Prompt Bloat)]] 所描述的問題。贅肉不是看起來不整齊而已。它會在任務真正開始前先縮小上下文窗口裡可用的空間，讓代理更早接近聰明區的邊界，也讓後面的探索、規劃和實作必須和更多固定噪音競爭。當 session 變長，原本只是幾千或幾萬個 token 的開場負載，還會在後續請求中反覆出現。

因此，清理 system prompt 的目標不是追求一個漂亮的最低數字，也不是把代理變成沒有工具的空殼。目標是把固定載入的內容和目前的工作對齊。跨任務都需要的規則、必要的檔案操作能力與安全限制應該保留。只有特定工作才會用到的能力，可以延後載入。完全不會用到、只因為預設開啟或過去某次實驗留下的內容，則應該停用或移開。

### 用一次實驗建立基線

任何清理工作都先量測。不要在還沒有輸入實際任務時，先憑印象猜測哪一項設定最肥。開啟一個新的 session，在沒有要求代理讀檔、執行命令或修改程式的狀態下，查看目前上下文使用量。Claude Code 的示範用 `/context` 觀察 system prompt、工具、技能、訊息等分類的 token 數量。其他 harness 可能有不同的指令或狀態列顯示方式，概念相同，都是先取得一個沒有工作內容干擾的起始讀數。

基線至少記下兩件事。第一是總 token 數。第二是主要來源，例如連接器、技能、工作流程、工具定義或其他系統說明。只有總數，後面很難判斷改動的效果；只有來源名稱，則無法知道哪一類值得優先處理。你可以把它當成工程上的效能基準。每一次只改一個有意義的設定，重新啟動 harness，再查同一個指標。如此一來，前後差異才有可解釋性。

課程示範的數字很有參考價值。啟用多項預設功能時，初始上下文大約是 68.3k token。停用 claude.ai connectors 後降到約 47k，接著關閉 workflows，降到約 39k；停用 bundled skills 後約 37k，停用 artifacts 後約 33k。這些數字不是所有環境都會重現的標準答案，卻清楚顯示固定能力的大小可能遠超過使用者直覺。你若只看設定檔的幾行 JSON，可能覺得它們很小；真正被注入的內容，往往包含每項能力的長描述和完整介面定義。

基線也讓你避免把問題錯怪給模型。代理在一開始就帶著六、七萬個固定 token 時，後續表現變差，原因可能來自模型、任務、程式碼，也可能只是環境先替它塞了太多內容。量測後，你可以清楚知道自己是在改善 harness，而不是盲目更換模型或把所有失敗歸因於提示詞。這是上下文衛生的重要習慣：先看請求裡實際有什麼，再決定要改哪裡。

### 優先處理固定的大來源

第一批應該審核 connectors。連接器把外部服務或資料來源的能力帶進代理環境。它們可能方便搜尋、同步、讀取或觸發某些操作，但便利性不代表每次工作都需要。若你今天要處理一個 Node API 的型別錯誤，外部設計工具、通知服務或其他遠端整合的完整描述，就沒有理由固定佔用每輪 request。停用一個大型 connector 後，如果 `/context` 的數字明顯下降，你便取得了一個具體證據，知道它原本確實是固定負載來源。

第二批是 workflows。工作流程通常比單一工具更肥，因為它可能同時描述觸發條件、步驟、輸入格式、輸出格式與相關工具。某個 workflow 也許是為報告、部署、遠端操作或特定產品功能準備的。當前任務沒有走那條路徑時，完整 workflow 留在 system prompt 裡，只會讓代理多一組要判斷的可能性。停用後重新啟動，再讀取上下文，觀察數字是否下降，並確認目前真正需要的日常工作仍可執行。

第三批是 bundled skills。技能的核心價值在於按需提供一套可重用程序，但模型可自動發現的技能通常至少會把名稱和 description 放進 parent context，有些 harness 還會預載更多說明。技能數量一多，代理每輪都要考慮更多「也許該呼叫」的能力。對偶爾使用的技能，可以改成使用者明確呼叫，或把詳細內容留在文件中，讓短指標負責導航。對目前完全不需要的 bundled skills，先停用，再用相同的基線方法測量回收了多少空間。

第四批是 artifacts。產物能力可能對文件、互動畫面或某些輸出工作很有用，但它不會因為名稱聽起來通用，就適合所有 repo。若你的工作主要是維護 TypeScript、跑測試和檢查 diff，與目前任務無關的產物工具不應在每輪 request 固定存在。這裡要保持判斷上的分寸。暫時停用不等於永久刪除。你可以保留原設定，等真正需要那項能力時再恢復或建立另一個工作配置。

這四類通常值得先看，是因為它們不是零散句子，而是成組注入的能力。刪掉一條短提示，可能只回收幾十個 token；停用一個 connector、workflow 或技能集合，則可能一次拿回數千甚至數萬個 token。優先順序應該由測量結果決定，而不是由設定檔中哪一行最容易改決定。

### 不使用工具，不代表工具沒有成本

清理工具定義時，有一個很容易漏掉的差別。你今天沒有呼叫某工具，只能說它沒有產生操作結果，不能說它沒有佔用上下文。只要工具仍被 harness 暴露給模型，工具的名稱、描述、輸入參數、限制和可能的使用方式就可能留在 system prompt 裡。模型每次面對新任務時，仍要把它納入可用能力的判斷。

課程示範用 deny 直接處理一批目前不會用到的工具，包括 notebook edit、design system sync、cron、plan-mode toggle、push notifications、remote trigger、report findings 和 wake-up scheduling。這個動作的意義不是只把工具鎖起來，還會讓工具定義整段從 system prompt 移出。這和把工具留著、只是在操作時不選它，對上下文的結果完全不同。

你可以把工具分成三種。第一種是目前任務的核心工具，例如讀檔、寫檔、執行測試與版本控制檢查。它們應該保留，因為移除後雖然數字變小，代理也失去完成工作的基本手段。第二種是偶爾使用的工具，例如特定資料庫、設計或通知整合。它們可以按工作類型啟用，或改成明確呼叫。第三種是你在當前工作流程中沒有角色、也無法說明何時會用到的工具。這類工具適合直接 deny，因為它們的固定成本沒有得到相應回報。

工具權限還有安全層面的價值。保留越多工具，代理可選的行動越多，使用者也越難快速檢查它到底可能做什麼。deny 讓不需要的工具同時離開可用操作集合和 system prompt，減少上下文負載，也縮小代理在當前任務中可能走錯的路。當然，權限規則不能為了數字而隨意刪除。像阻止危險命令的限制，可能只佔很小空間，卻對工作安全有很高價值。

示範最後移除了冗長的 `ask user question` 工具定義，讓初始上下文降到兩萬 token 以下。這個例子提醒你，單一工具也可能很大。不要因為一個設定只出現一次，就假定它影響很小；要看它實際帶入了多少文字。也不要因為工具名稱看起來合理，就認定它值得固定載入。合理的判斷方式是把工具放回目前工作流程，問自己它是否真的需要被模型在每輪都看見。

### 每次只改一項，讓數字能說話

清理 system prompt 最怕一次改太多。若你同時關閉 connectors、技能、workflow 和十幾個工具，最後看到 token 降了，卻不知道哪一項貢獻最大。之後某個功能壞掉，你也很難找出應該恢復什麼。一次只做一組有清楚邊界的改動，重新啟動，查看 `/context`，記下前後差異，再進行下一步。這樣做慢幾分鐘，卻能得到一張自己的上下文地圖。

重新啟動不能省略。system prompt 是在建立或初始化 request 時組合的，已經開啟的 session 可能仍保留舊設定或舊工具列表。你在同一個 session 裡修改設定，看到的結果不一定代表新設定已經生效。正確的測量循環是修改設定、關閉舊 session、重新啟動 harness、在沒有實際任務的狀態下查看上下文。每次都維持相同的觀測條件，前後比較才有意義。

記錄可以很簡單。你只需要保存改動項目、重啟後的 token 數、被移除的主要來源，以及目前有哪些功能受到影響。若一項改動只讓數字下降很少，卻讓工作變得不穩定，通常不值得保留。若一項改動回收大量 token，且沒有影響目前任務，就應該留在精簡配置。這不是追求數字遊戲，而是在比較固定上下文成本和功能價值。

### 清理的邊界是「匹配工作」，不是「越少越好」

最小的 system prompt 不必然帶來最好的代理。假設你為了回收空間，移除了測試命令的必要權限、團隊要求的安全限制，或代理理解專案結構所需的短指標，初始數字也許漂亮，後面卻會出現更多失敗、返工和人工確認。錯誤所消耗的上下文和時間，可能遠高於你刪掉的那幾百個 token。

一項內容是否值得常駐，可以用三個問題判斷。它是否跨任務都適用。它是否能避免高代價的錯誤。它是否真的需要模型在每輪 request 都知道。三個問題都回答得很清楚，內容通常值得保留。若只是特定情境才需要，應考慮把完整程序放進文件，再留下短小的 pointer。若它已經在程式碼、README 或其他單一真實來源中可取得，則不必在 system prompt 重複整段。若移除後代理行為沒有可觀察差異，內容可能就是 no-op。

這裡可以看出 system prompt 贅肉和 steering 檔案修剪的關係。前者主要審核 harness 自動注入的能力、工具與整合，後者審核人寫進引導檔案的規則是否重複、過時或沒有作用。兩者都在問同一個工程問題：這段內容是否值得持續佔用上下文。差異只在來源不同。先清掉外殼的固定大戶，再處理長期引導中的沉積物，通常比較容易看出每一步的效果。

### 把方法帶到其他 harness

課程用 `.claude/settings.json` 示範，所以實際欄位和工具名稱屬於 Claude Code 的環境。你不應把檔名、設定鍵或 slash command 當成所有代理工具都通用的操作手冊。不同 harness 可能把 system prompt、工具清單、技能註冊和連接器配置放在不同位置，也可能提供不同的診斷介面。

可以轉移的是審計方法。先找到它如何查看初始上下文，接著盤點哪些內容在第一個任務前就已經被注入。把來源分成設定、技能、工作流程、工具、連接器和其他整合。選一個目前不需要的來源暫時停用，重新啟動，重做同樣測量。若數字下降，保留紀錄並判斷停用是否影響工作；若數字沒有變，檢查這個設定是否根本沒有進入 system prompt，或真正來源位在另一層。

這套方法也適用於你自己的專案配置。你可以為日常功能開發、資料庫維護、部署工作或學習實驗準備不同的可恢復配置。每種配置都應有清楚目的，並且知道哪些能力會常駐。專案切換時，不要只問代理「你現在會什麼」，還要看它在第一輪 request 實際收到什麼。能夠查看、測量和調整這個輸入，才算真正掌握 harness，而不是只是在使用預設值。

### 一個可重複的清理流程

開始前，先開一個沒有真實任務的全新 session，取得上下文基線。接著讀取分類資訊，找出最大的固定來源。從 connectors、workflows、bundled skills 和 artifacts 開始，因為它們往往是整批載入的能力。每次停用一項或一組有明確邊界的能力，重新啟動 harness，再查看同一個上下文指標。

接下來審核工具。把工具分成必要、偶爾使用和目前無角色三組。必要工具不要為了降低數字而移除。偶爾使用的工具考慮延後載入或改成使用者明確呼叫。沒有角色的工具直接 deny，確認工具定義是否從 system prompt 消失。若仍有大型工具定義，逐項找出並測量，直到初始上下文回到你能理解、能工作的水位。

最後做一次功能驗證。讓代理完成一個小而安全的任務，例如讀取專案入口、執行既有 typecheck，或檢查一個指定模組的測試。確認精簡後的配置仍能讀檔、執行必要命令、遵守權限限制，也能在需要時使用保留下來的技能。只有數字下降而沒有功能驗證，清理就還沒有完成。

完成後，把結果寫成自己的配置決策。哪些能力固定開啟，哪些只在特定工作中啟用，哪些被明確 deny，哪些詳細程序改放在文件中。之後若上下文再次膨脹，你可以比較新的基線，而不必重新猜測。當某項整合被加入、某個 workflow 不再使用，或某個 bundled skill 只是暫時實驗，也要把它視為需要重新審計的變更。

### 你應該帶走的判斷

看到代理表現變差時，先問它的上下文裡是否有太多固定內容。看到設定檔變大時，先問哪些項目真的會被注入 system prompt。看到一個工具沒有被呼叫時，別急著把它當成沒有成本；只要它的定義還在，每輪 request 就可能繼續攜帶它。看到 token 數下降時，也別急著認為所有被移除的東西都不重要，還要確認必要功能、安全限制和工作流程沒有被破壞。

清除 system prompt 贅肉是一種維護習慣。它把代理的固定負載變成可觀察、可比較、可恢復的配置。你不需要記住課程示範的每個數字，也不需要模仿某個產品的每個欄位。只要能在開工前看見代理背著什麼，知道哪些內容只是預設留下的能力，並且用一次一項的實驗把無關內容移開，就能把更多上下文留給真正需要理解的程式碼、需求與推理。
