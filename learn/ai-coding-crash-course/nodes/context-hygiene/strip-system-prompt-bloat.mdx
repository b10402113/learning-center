## Learning goal

找出並移除會污染每次請求的無用工具、技能與連接器，讓你的 AI 編碼代理在每一輪互動中都能把 token 預算花在真正重要的事情上。

## Lesson

## 📝 System Prompt 贅肉是什麼？

你的 AI 編碼代理每次執行指令，都會把一整套預設啟用的東西打包送進模型的 system prompt。這些東西包括已啟用的 connector（外部連接器）、bundled skill（預裝技能）、workflow（自動化流程）、artifact（富媒體產物能力），以及每一個被允許的 tool（工具）的完整定義。

它們不是靜靜待在背景，而是每一次 request 都會佔用 context window 的真實成本。

一個典型的 Claude Code 環境，在完全不做任何清理的情況下，光是 system prompt 裡預設啟用的項目，就能把初始 token 推到六萬八千以上。這還沒有開始寫任何一行代碼、讀任何一個檔案、做任何一次討論，你的 context window 已經被吃掉一大半，而那些佔位的內容裡有相當大一部分是你這一次工作根本不會用到的能力定義。

這就是 [[learn/ai-coding-crash-course/elements/system-prompt-bloat|System Prompt 贅肉 (System Prompt Bloat)]]。它不是一個抽象概念，而是每一輪互動都在發生的真實消耗。

---

## 🔧 清理流程：改一項、重啟、量一次

整個清理流程的核心方法很簡單，只有一個姿態：改一項設定，重啟 harness（AI 編碼代理的運行環境），跑一次 context 檢查，看數字有沒有下降。不要靠猜，靠量。

五個步驟，一個比一個回收更多。下面逐項拆解。

### 第一步：找到你的設定檔

以 Claude Code 為例，主要的設定檔是 `.claude/settings.json`。這個檔案控制了哪些能力被啟用、哪些工具被允許。你打開它，會看到一長串已經被啟用的項目。這些項目就是待審計的對象。

### 第二步：關閉不需要的 Connector

**目標項目：** claude.ai connectors

這些外部連接器會把外部服務的整合能力帶進 system prompt，佔用大量 token。如果你的工作不需要這些連接，把它們關掉。

**測量結果：** 光是這一步，初始 token 從六萬八千多降到四萬七千左右。一個動作，省下超過兩萬 token。

這些 token 不是被釋放出來的，而是它們原本就不該在那裡。

### 第三步：關閉 Workflows 與 Bundled Skills

**目標項目：** workflows（自動化流程）+ bundled skills（預裝技能定義）

如果這些流程和技能不是你這次工作要用的，它們的定義留在 prompt 裡就純粹是負擔。

**測量結果：** 關掉之後，token 進一步降到三萬九千左右。每一步的下降都是量測出來的，不是估算。

### 第四步：關閉 Artifacts

**目標項目：** artifacts（富媒體產物能力，如互動式圖表、網頁預覽等）

如果你的編碼工作根本用不到這套能力，關掉它。

**測量結果：** token 從三萬九千降到三萬三千。這又回收了六千 token 的空間。

### 第五步：Deny 不需要的工具

**這是最關鍵的一步，也是回報最大的一步。**

在你的 AI 編碼代理中，有許多工具被預設允許。每一個被允許的工具，它的完整定義都會被寫進 system prompt。這不只是「允許它被呼叫」那麼簡單，而是「它的完整描述會在每一輪都跟著送出」。所以你要做的是把那些你不會用到的工具直接 deny（拒絕存取）。

deny 一個工具的效果是明確的：那段工具定義會從 system prompt 中完全消失。不是被標註為「不推薦使用」，不是被放在某個角落等你自己忽略，而是整個定義段落被移除，連帶它佔用的所有 token 一起回收。

**實際被 deny 的工具清單：**

- notebook edit
- design system sync
- cron
- plan-mode toggle
- push notifications
- remote trigger
- report findings
- wake-up scheduling

這些聽起來都是合理的能力，但如果在你的工作流程中它們沒有角色，它們留著就是純消耗。

**測量結果：** deny 這些工具之後，token 從三萬三千暴跌到二萬一千六百。這一步的回報超過一萬 token，是整個清理過程中最大的一塊。

最後，連 `ask user question` 這個工具也不放過。這個工具的定義本身就相當冗長，包含了提問格式、回應處理邏輯等描述。在許多工作場景中，這個工具並非必要。把它移除之後，初始 token 降到二萬以下。

## 📊 清理成果一覽

| 階段 | 操作 | Token 變化 |
|------|------|-----------|
| 起點 | 未清理 | ~68,000 |
| 關閉 Connectors | deny claude.ai connectors | ~47,000（省 21,000） |
| 關閉 Workflows + Skills | deny workflows 和 bundled skills | ~39,000（省 8,000） |
| 關閉 Artifacts | deny artifact 能力 | ~33,000（省 6,000） |
| Deny 工具 | deny 8+ 個不需要的工具 | ~21,600（省 11,400） |
| 移除 ask user question | deny 冗餘提問工具 | &lt;20,000（省 1,600+） |
| **總回收** | | **&gt;48,000 token** |

從六萬八千到不到二萬，整個清理過程回收了超過四萬八千 token 的固定負載。

## 💡 為什麼 System Prompt 清理很重要？

### 回收的是對話空間，不是 token 數字

Context window 是有限的。每一輪互動，模型能看見的東西就那麼多。當 system prompt 已經佔掉六萬多 token，你留給真正工作（探索 repo、討論需求、分析代碼、撰寫實作方案）的空間就只剩下一半甚至更少。但如果你把固定負載壓到二萬以下，你就把超過四萬 token 的空間還給了動態內容。這些空間可以用來放更多檔案內容、更長的對話歷史、更豐富的分析結果，每一輪都會受益。

### 固定負載 vs 動態內容

這些被清理掉的內容，跟動態載入的內容（例如你正在讀的檔案、正在討論的代碼片段、正在生成的實作方案）有本質上的不同。動態內容是隨任務而來的，有需要才佔用空間；而 system prompt 裡的冗餘定義是固定的，不管你在做什麼工作，它們都在那裡。這就是為什麼清理 system prompt 的回報特別高，因為你是在壓低一個每輪都會觸發的固定成本。

### 也提升模型品質

從模型的角度來看，system prompt 裡的每一段定義都是它需要「理解」的上下文。當 prompt 裡有一大堆它不需要的工具定義、技能描述和連接器規格，它的注意力（attention）會被這些內容分散。清理之後，prompt 變得更精簡，模型更容易把注意力集中在你真正需要的能力和當前任務上。這不只是省 token 的問題，更是提升品質的手段。

## ⚡️ 這是 Context Hygiene 的第一步

Context hygiene（上下文衛生）是指有意識地管理模型在每次互動中接觸到的資訊，確保只有與當前任務相關的內容才被送進去。而 system prompt 贅肉清理正是 context hygiene 中最前端、回報最直接的一環。它處理的是固定負載，也就是那些不管你做什麼都會自動進場的內容。把這些東西清乾淨，後續的動態內容管理才有意義。

你不需要是 Claude Code 的使用者才能從這個過程中受益。任何 AI 編碼代理都有 system prompt，都有預設啟用的能力，都面臨同樣的問題。工具名稱可能不同、設定檔路徑可能不同、deny 的語法可能不同，但核心邏輯是一樣的。

## ✅ 實作清單

1. **找到設定檔**：找出你的 AI 編碼代理的配置檔（如 `.claude/settings.json`）
2. **逐項審計**：檢查每一個啟用的項目，問自己「這個能力在接下來的工作中真的會用到嗎」
3. **逐項關閉**：對不需要的項目執行 deny 或 disable
4. **重啟量測**：每次修改後都重啟 harness 並檢查 context 變化
5. **不靠猜靠量**：有些項目可能佔用你以為很多的 token，結果關掉之後數字幾乎沒動；有些不起眼的設定可能藏著意想不到的消耗，只有數字能告訴你答案
6. **持續維護**：未來啟用新的 connector、skill、tool 時，同樣的審計邏輯要再跑一遍。保持 system prompt 的精簡不是一個狀態，而是一個持續的習慣

這就是為什麼 context hygiene 不是某一天做一次的事，而是你跟 AI 編碼代理合作的日常基本功。
