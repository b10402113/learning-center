## Learning goal

學完這一步，你能說清楚模型、harness 與環境各自保存什麼狀態，理解為什麼清空 Session 不等於失去所有工作成果，並把重要的專案理解、決策與進度寫成下一個 Session 可以重新讀取的檔案。你也能設計一個不依賴模型「自己記住」的跨 Session 工作流程，知道哪些內容值得落盤、應該放在哪裡、如何讓新代理找到它們，以及如何在使用持久化筆記前重新檢查它們是否仍然符合目前的程式碼。這一步的核心概念是 [[learn/ai-coding-crash-course/elements/filesystem-memory|檔案系統作為記憶 (Filesystem as Memory)]]。

## Lesson

### 先決定什麼值得跨過 Session 邊界

先用一個簡單問題判斷：如果明天換一個 Session，你還希望代理知道這件事嗎？如果答案是是，而且這件事可以用幾句可驗證的文字講清楚，就值得考慮落盤。通常適合寫進檔案的，是方向與目的、已確認的設計決策、探索地圖、目前進度、交接入口、專案詞彙和共享資產；不太適合的，則是一次性的猜測、整段工具輸出，或只是聊天時的閒話。落盤不是把全部對話搬進硬碟，而是整理出下一個工作者真正需要的事實、原因、限制和下一步。

但光寫下來還不夠，還要讓人找得到，也查得到真假。新的 Session 通常只知道工作目錄、平台、Git 狀態、branch 和最近 commit，不會自動知道哪篇筆記最重要。所以你需要清楚入口、穩定命名，還要用簡短指標告訴代理該先讀什麼。文件本身也要分清楚哪些是已確認、哪些待驗證、哪些是未解問題，免得一份舊摘要被當成目前程式碼的真相。持久化能解決的是「對話結束後狀態不會消失」，不是「以後都不用再檢查」。

### 把「記憶」拆成三個不同的地方

和 AI coding agent 一起工作時，最容易讓人誤會的字就是「記得」。你說「它知道這個專案」，可能只是它在這個對話裡讀過檔案；你說「它記得我昨天的決定」，可能其實是 harness 把昨天的訊息重新送進模型；你說「這個專案保留了我們的規則」，則可能是那些規則已經寫進 repository。這三種情況看起來都像記憶，但它們其實放在不同地方，壽命和可靠性也完全不同。

可以把整個 agent 系統想成三層。

第一層是模型。模型本身是無狀態的。每次呼叫都像一次新的計算：它根據當下拿到的 system prompt、對話內容、工具結果和使用者要求來產生回應。它不會因為上一輪看過某個檔案，就在下一輪自動保留那個檔案的內容；也不會因為昨天在同一個 repository 工作過，今天就自動知道你的專案慣例。模型的參數裡確實有訓練形成的廣泛知識，但那不是針對你這個 Session 的個人長期記憶。

第二層是 harness，也就是包住模型的代理外殼。它會管理 Session、保存訊息、呼叫工具、讀寫檔案、執行命令，並把前面發生過的事整理後送進後續請求。代理在同一個 Session 裡之所以像是「記得前情」，通常不是模型自己留住了記憶，而是 harness 把先前的對話和工具輸出保留下來，再整批或部分重送給模型。這種狀態確實存在，但範圍只限於目前 Session。只要你清空 Session、開新 Session，或換到另一個不共享歷史的 harness，沒有寫進環境的那部分脈絡就不會自動跟過來。

第三層是環境。這裡包括 repository、檔案系統、版本控制裡的檔案、文件、設定、工作產物，以及其他之後還能再讀取的資料。這一層不會因為你清空一段對話就消失。只要檔案還在，新的 Session、另一個模型，或另一個代理，就有機會重新把它讀回來。這就是「以檔案作為記憶」的基礎：不是把記憶塞進模型，而是把未來還有用的知識放到模型可以再次取得的環境裡。

這個區分很重要，因為它能幫你判斷問題出在哪裡。若模型在同一輪對話裡忘了剛剛讀過的內容，可能是上下文太長、注意力變差，或 harness 沒有正確傳遞工具結果。若你一清空 Session，它就不記得前面討論過什麼，這是 Session 的自然限制，不一定代表代理出錯。若新 Session 讀到的是過時的專案規則，那通常是檔案記憶沒有更新，或缺少驗證。沒先分清楚這三層，你就很容易用錯方法，例如把其實只是還沒寫檔的問題，誤以為要靠外部記憶系統來補；或把真正過期的文件，誤當成只是需求描述不夠清楚。

### Session 內的「記得」其實是重送上下文

你可以把這件事想成：你在白板室裡和一位很能幹的顧問合作。顧問每次只看眼前白板上的內容，離開房間後不會把白板帶走。為了讓合作看起來連續，有一位助理每次都把前幾次會議紀錄、已讀檔案和工具結果重新貼回白板。只要白板還沒塞滿，顧問就能接著往下做；但如果助理把白板清空，那些只存在會議紀錄裡的理解也就不在眼前了。

harness 的 Session 很像這個比喻。它把對話歷史、工具呼叫和結果保留在一個可延續的請求脈絡裡，所以模型看起來像是能接續前文。這件事有兩個直接後果。第一，Session 越長，能攜帶的內容越多，成本和注意力負擔也越大。第二，Session 的連續性不是檔案系統的持久性。你可以把幾百輪對話留在某個介面裡，但那仍然只是由特定 harness 管理的暫時歷史，不一定能被下一個代理或下一個工作目錄直接使用。

所以，不要把「它剛剛答對了」理解成「這個知識已經保存了」。如果你剛才花半小時向代理解釋資料模型、命名原則和某個看起來很奇怪但其實很重要的相容性限制，而這些內容沒有寫進文件，那麼一旦清空 Session，對新代理來說它們就還是不存在。就算你不清空，長 Session 也可能讓前面那些關鍵決策，被後面大量的檔案輸出淹沒。只有把穩定而重要的內容寫成可讀檔案，這些知識才算真的脫離了當前對話的壽命。

這也不表示每一句對話都要保存。對話裡本來就有很多一次性的思考、錯誤嘗試、重複確認，以及不值得長期保留的細節。如果把全部內容原封不動寫進檔案，反而會製造另一種上下文污染。真正該落盤的，是下一次工作還需要用到的事實、決策、限制、進度和入口，不是整段聊天錄音。好的檔案記憶是整理過的工作資產，不是把 Session 的殘留物整包倒進硬碟。

### 「我的 code base 就是記憶系統」意味著什麼

把 code base 當成記憶系統，意思不只是把幾份筆記放進 repository，而是整個工作習慣都要改。你不再問「怎麼讓模型永久記住這件事」，而是改問「怎麼把這件事寫進一個未來代理找得到、看得懂、查得到、也用得上的地方」。這時，記憶問題就不再是模型設計問題，而是檔案設計問題。

如果某個決定會影響後續實作，就應該留下可追蹤的紀錄。比如你決定某個功能只服務已登入使用者、某個資料表必須保留軟刪除、某個外部 API 只能從 server side 呼叫，這些都不應該只停在討論裡。它們可以寫進設計文件、任務規格、架構決策紀錄，或專案指引。下一個 Session 不需要相信代理曾經參加過會議，只需要先讀文件，再回頭用程式碼確認這些規則現在還成立。

如果某個探索結果能讓未來更快上手，也值得落盤。技術棧、啟動指令、測試指令、重要目錄、資料流、路由邊界和特殊術語，都是新代理第一次進入 repository 時要重新建立的地圖。你不需要把整個專案逐行抄進筆記；只要留下一張有證據支撐的導航圖，告訴代理先讀哪些檔案、哪些結論已確認、哪些問題還沒答案，就能明顯減少下一次探索的摩擦。

如果某個工作流程會一再重複，也應該把它變成文件或可重用的 skill。課程裡的 `teach` skill 就是一個很清楚的例子。它不是只在目前對話中介紹工作區，而是會建立 `mission.md`、`notes.md`、`resources.md`、glossary 和第一篇 lesson 這些實體學習資產。這些檔案合起來，形成一個可以重新閱讀的工作區。清空上下文之後，代理不是靠內在記憶去猜你學到哪裡，而是透過這些檔案恢復學習目標、已知內容、資源入口和下一步。

這種做法的關鍵力量在於：檔案是可檢查的。你可以直接讀它、改它、讓 Git 記錄它的變化、在 code review 裡討論它，也可以把它交給另一個代理。模型腦中的暫時印象做不到這些事。當你把記憶放進檔案系統，它就不再是看不見的模型狀態，而是團隊可以一起維護的工作資產。

### 什麼內容值得寫進檔案

有一個很好用的兩步判斷法。先問：「如果明天換一個 Session，我還希望代理知道這件事嗎？」如果答案是肯定的，再問：「這件事能不能用幾句可驗證的文字說清楚？」如果兩個答案都是肯定，就應該認真考慮落盤。

第一類是方向與目的。這包括專案服務的使用者、目前工作的目標、這個功能刻意不解決哪些問題，以及成功條件是什麼。沒有這些內容，代理也許能改出一段可執行的程式，但它未必知道什麼才叫做正確的產品行為。方向文件不一定要長，但它至少要幫助新 Session 分清楚「做出能跑的東西」和「做出這個專案真正需要的東西」之間的差別。

第二類是已確認的設計決策。像是資料模型選擇、介面行為、權限邊界、相容性承諾、錯誤處理策略，以及刻意保留的奇怪實作，都屬於這一類。尤其是那些不能從程式碼表面直接看出的決定，更值得記錄。程式碼能告訴代理現在做了什麼，但不一定能告訴它，為什麼不能用看起來更簡單的方式改寫。把原因留下來，能避免下一個 Session 把歷史決定當成偶然，再次引入已經排除過的風險。

第三類是探索地圖。這種文件會記錄根目錄的重要檔案、主要模組、啟動和驗證方式、代表性的呼叫鏈，以及下一個任務的入口。它的目的不是取代直接讀程式碼，而是降低找路成本。它比較像地圖索引，不是把整座城市整張拍下來。檔案名稱和位置要穩定，內容則要說明哪些結論來自哪些程式碼區域，哪些部分還沒確認。

第四類是當前進度和交接資訊。現在在處理什麼問題、已經完成了哪些部分、哪些測試通過了、哪些失敗還要查、下一步應該先讀什麼或先做什麼，這些都能幫助新 Session 很快接手。這種記錄特別適合在一段工作快結束時整理，因為那正好是自然的交接點。它不需要保留完整思考過程，只要留下足夠讓下一個工作者重新建立判斷的骨架就夠了。

第五類是專案詞彙和共享資產。專案裡的縮寫、領域名稱、特殊狀態值，以及容易混淆的概念，可以集中放進 glossary。共用的樣式、範例、測試資料、教學頁面和參考資源，也可以放在命名清楚的目錄裡。只要這些東西待在穩定的位置，新代理就能透過入口文件找到它們，不必依賴某位人類或某段舊對話再解釋一次。

反過來說，下列內容通常不適合直接當成長期記憶：一次性的猜測、還沒驗證的臨時方案、已經被否決但沒有標記的方向、整段工具輸出、敏感憑證，以及只跟某次對話有關的閒聊。如果某個未驗證的推論真的很重要，可以保留，但一定要明確標示成待確認，不要用像是在陳述既成事實的語氣去寫。若資訊涉及秘密，也要用安全的秘密管理方式，不要因為「檔案可以記憶」就把金鑰或個人資料直接寫進普通文件。

### 設計一個讓新 Session 找得到的記憶庫

檔案存在，不代表代理就會用。新的 Session 通常只知道工作目錄、平台、Git 狀態、branch 和最近 commit 這類環境中繼資料，不知道 repository 裡有哪些完整檔案，也不會自動知道哪一篇筆記最重要。要讓檔案系統真的變成記憶，你得同時設計保存方式、命名方式和取回方式。

第一步，是替不同用途的內容設計清楚而穩定的入口。你可以有一份專案導覽文件，講產品目的、技術棧和關鍵目錄；也可以有一份工作狀態文件，記錄目前進度和待辦；還可以有一份決策文件，保存那些程式碼表面看不出來的原因；或者用一個 docs 或 skills 目錄，收納按需讀取的詳細流程。重點不是一定要用哪組固定檔名，而是讓新代理能從少數入口一路找到更多內容。

第二步，是不要把所有記憶都硬塞進每一輪上下文。那些固定載入的長篇規則，會持續佔用 token 和注意力，即使當前任務根本用不到。通常更好的做法，是用短指標指出文件位置，等任務真的需要時再讀詳細內容。這樣檔案仍然可達，但不會變成每次請求都要背負的常駐負載。記憶需要持久，不代表它必須一直停在模型眼前。

第三步，是讓檔案一開頭就說清楚自己的用途、適用範圍和更新方式。新代理拿到一份文件時，最好能立刻知道它是架構導覽、目前交接、資料庫流程，還是學習筆記。如果所有文件都只叫 `notes.md`，或一份文件裡混了十個彼此無關的主題，就算代理找到了，也未必知道該用哪一段。對未來 Session 來說，清楚的結構本身就是一種引導。

最後，是在工作要求裡明白告訴代理先去找哪些入口。例如你可以要求它先讀專案導覽和目前狀態，再去檢查相關程式碼，最後回報哪些文件和現況一致。這不是因為代理不會讀檔，而是因為 fresh Session 根本不知道你的知識架構長什麼樣子。短短一句入口提示，常常就能把「盲目列出所有檔案」變成「先讀高價值索引，再按任務深入」。

### `teach` skill 示範的持久化工作流

`teach` skill 的重點，不在於它剛好用了哪幾個檔名，而在於它把一次性的理解工作，轉成可重複使用的工作區。它會把專案探索整理成 mission，讓工作目標不只停在對話裡；用 notes 保存目前已經學到的內容和疑問；用 resources 集中重要的閱讀入口；用 glossary 固定領域詞彙；再用 lesson 把局部知識整理成可閱讀、可驗證的材料。

這套做法不只適合教學，也能直接套用到其他長期工作。做一個長期功能時，mission 可以寫產品目的和成功條件；notes 可以記探索結果、決策與未解問題；resources 可以整理規格、API 文件和相關模組；glossary 可以整理領域詞彙；lesson 則可以幫新成員或新代理解釋某條重要流程。這樣一來，代理產生的檔案就不只是目前 Session 的副產品，而是下一次協作也用得上的中介層。

但要記得，這些檔案不是「代理腦袋的備份」。它們是外部記錄，所以必須讓人看得懂，也必須接受驗證。代理下次讀到 notes 之後，仍然應該回到相關程式碼去檢查關鍵事實，而不是把筆記當成不能懷疑的真相。如果程式碼改了，就要更新文件；如果某個問題已經解決，就要移除或標記舊的待辦；如果兩份文件彼此矛盾，就應該先停下來釐清，而不是隨便挑一份相信。

這也表示，持久化不是「寫完一次就結束」。它其實是一個循環：探索產生記錄，記錄幫助下一個 Session 定位，下一個 Session 再用程式碼驗證記錄，驗證結果回頭更新記錄。只有走完這個循環，檔案系統記憶才會愈來愈可靠。否則你只是把一份可能有錯的摘要保存得更久。

### 跨 Session 接續工作的具體流程

你可以把一個可重複的跨 Session 工作流程，拆成幾個明確階段。第一階段，是在目前 Session 裡先建立理解。先讓代理探索技術棧、產品用途、主要目錄，以及和目前任務有關的呼叫鏈，並要求它分清楚哪些是已確認、哪些是推論、哪些仍然未知。這一步的目標不是立刻改檔，而是先收集足夠證據。

第二階段，是整理要持久化的材料。讓代理把穩定內容寫進適當文件，包括工作目標、重要設計決策、探索地圖、已完成項目、失敗測試和下一步。整理時要刪掉重複敘述，保留那些真的會影響決策的細節，並把不確定的內容清楚標出來。如果這些材料要讓團隊共同使用，就應該放進 repository 裡適合版本控制的位置；如果只是一次性的跨工具交接，也可以用不污染專案的暫存 handoff 文件。

第三階段，是驗證你剛剛落盤的結果。要求代理列出它寫了哪些檔案、每份檔案的用途是什麼、下一個 Session 應該先讀哪一份，以及哪些內容還需要直接回去檢查。你自己也可以立刻讀一遍，確認它沒有把猜測寫成事實、沒有漏掉關鍵限制，也沒有留下秘密或不必要的整段輸出。這一步是在記憶交給未來之前，先把品質問題抓出來。

第四階段，是有意識地結束目前 Session。當上下文快到負擔上限、工作從實作轉向 QA，或你準備交給另一個代理時，不要只是按下清空。先把那些能跨過邊界的理解整理好、保存好。清空之後，新 Session 還是得重新探索檔案系統裡的入口，但它不必從頭猜所有歷史背景。這就是把 Session 當成可丟棄的暫時工作桌，把 repository 當成可以持續使用的工作場所。

第五階段，是新 Session 的恢復。開場時先讓代理讀取持久化入口，再要求它用目前程式碼去核對關鍵內容。你可以要求它回答：目前工作的目標是什麼、已經完成了什麼、有哪些決策、接下來的入口在哪裡、哪些事情還沒確認。如果它只是照著文件重述，卻沒有去查程式碼，那就代表恢復還沒完成；如果它發現文件和程式碼不一致，就應該先修正理解和記錄，再繼續工作。

第六階段，是把新發現回寫。新的 Session 可能會發現原本的導覽漏了一個模組、某條指令已經換掉了、某個設計決策需要補充。不要只是當下記住這些修正。如果它們對未來還有價值，就應該更新文件，讓後面的 Session 也能受益。這樣反覆幾輪之後，工作區就不只是檔案的集合，而會慢慢變成一張和實際程式碼同步的協作地圖。

### 不要把持久化文件誤認成真相

檔案記憶通常比 Session 對話可靠，但它不是永遠正確。文件可能是代理在有限探索下寫出來的，可能漏掉例外情況，也可能在程式碼演進後已經過時。持久化能解決的是「狀態不會跟著 Session 消失」，不是「內容從此不必再驗證」。這條界線一定要守住，否則新的錯誤就會借用一份看起來很正式的文件，被不斷重複放大。

你可以在文件裡用三種清楚標籤來管理可信度。第一種是已確認，表示目前程式碼、測試或正式規格都支持這個內容。第二種是待驗證，表示這是一個合理推論，但新 Session 在使用前必須先檢查。第三種是未解問題，表示這裡還有缺口，需要後續調查，而不是可以直接拿去實作的需求。這些標記能幫未來的代理分辨：哪些內容可以拿來當起點，哪些內容一定要先重新求證。

更新策略也要跟變更風險對得上。小型重構不一定需要重寫整份架構導覽；但如果更換了 framework、資料庫、路由系統、測試工具，或產品邊界本身已經改變，就應該重新檢查相關文件。如果文件能清楚列出適用範圍和最後驗證時間，代理和人類都更容易判斷要不要重新探索。不要讓一篇寫得很完整的舊文章，只因為形式漂亮，就比目前程式碼更有權威。

### 實作練習：親手證明檔案能跨越 Session

你可以在自己的 TypeScript 或 Node repository 裡做一個小實驗。先開一個新的 Session，不急著交付功能，只要求代理探索專案的技術棧、用途、重要目錄、啟動方式，以及一條代表性流程。要求它說明判斷依據，不接受只丟結論。過程中觀察它實際讀了哪些檔案，也看它會不會在不知道的地方老實承認未知。

接著，要求代理建立一組精簡的工作區記錄。至少要有一份 mission，說明你要完成的工作；一份 notes，保存已確認的架構和未解問題；一份 resources，列出下一次應該閱讀的入口；以及一份 glossary，解釋專案裡容易混淆的名稱。如果你不想用這組檔名，也可以用自己的結構，但用途和入口一定要清楚。重點是請代理把目前進度寫進檔案，不要只是回覆在終端畫面上。

保存之後，清空 Session，真的重新開始。不要先貼回舊對話，也不要告訴代理你剛才說過什麼。只給它一個短指標，要求它先找到並讀取工作區記錄，再回答目前任務的目標、專案結構和下一步。你會看到一個很關鍵的差異：它仍然不會自動記得上一段對話，但它可以透過檔案重新建立足夠的工作狀態。

接下來，再要求它打開一個核心程式碼檔案，去核對 notes 裡的一項判斷。如果判斷正確，就讓它指出目前檔案中的證據；如果判斷已經過時，就讓它更新 notes，並寫清楚修正原因。最後再問它：還有哪些資訊依然未知？這一步很重要，因為它能避免這個實驗最後只證明「代理會照著筆記朗讀」，而是真正測試檔案記憶能不能支援理解、驗證和修正。

做完之後，檢查四個結果。第一，清空 Session 是否真的讓沒落盤的對話狀態消失。第二，新 Session 是否能從檔案入口恢復任務方向。第三，持久化文件是否讓重新探索變短，而不是又多出一堆無關上下文。第四，代理是否能指出文件和目前程式碼之間的差異。如果四個答案都是肯定的，你就已經建立起一套比「希望模型自己記住」更可靠的跨 Session 工作方式。

### 最重要的工作習慣

每次你在 Session 裡說出「這件事之後還會用到」，就停一下，問自己它是不是該變成檔案。每次你做出一個後續工作者需要理解的決定，就把原因留下來。每次你完成一輪探索，就保存一張足以讓別人重新定位的地圖。每次你準備清空或交接，就先把目前狀態整理成可讀的工作產物。每次新 Session 讀回文件時，也都要求它回到程式碼驗證，而不是直接相信。

這些習慣會把代理協作從「一段很長的對話」，慢慢變成「Session 加上共享環境」的系統。Session 適合承載正在進行的推理、互動和暫時性的工具結果；檔案系統適合承載可重用的知識、規格、決策、進度和資產。前者可以被清空，後者需要被維護。你不需要讓每一段對話都永久存在，也不需要把所有背景固定塞進模型；你只需要把真正值得延續的部分，放到下一個工作者找得到、也查得到的位置。

當你接受模型無狀態、harness 只在 Session 內有狀態，而環境才是跨 Session 的持久層，很多看起來很神祕的代理行為就會變得比較好設計。新的 Session 不記得昨天，不是因為它不可靠，而是因為它本來就需要從環境重新取得狀態。你的工作不是消除這件事，而是建立好的文件入口、探索流程和驗證循環。把理解寫進 repository，讓檔案成為可讀取、可修改、可版本控制、也可交接的記憶系統，代理才有機會在每次重新開始後，很快恢復成可靠的工作夥伴。
