## Learning goal

學完這一步，你能說清楚模型、harness 與環境各自保存什麼狀態，理解為什麼清空 Session 不等於失去所有工作成果，並把重要的專案理解、決策與進度寫成下一個 Session 可以重新讀取的檔案。你也能設計一個不依賴模型「自己記住」的跨 Session 工作流程，知道哪些內容值得落盤、應該放在哪裡、如何讓新代理找到它們，以及如何在使用持久化筆記前重新檢查它們是否仍然符合目前的程式碼。這一步的核心概念是 [[learn/ai-coding-crash-course/elements/filesystem-memory|檔案系統作為記憶 (Filesystem as Memory)]]。

## Lesson

### 先決定什麼值得跨過 Session 邊界

如果明天換一個 Session，你仍然希望代理知道某件事，而且這件事可以用幾句可驗證的文字說清楚，它就值得考慮落盤。方向與目的、已確認的設計決策、探索地圖、目前進度、交接入口、專案詞彙和共享資產，通常比一次性的猜測、整段工具輸出或聊天閒話更適合成為檔案記憶。落盤不是把所有對話搬到硬碟，而是整理出下一個工作者需要的事實、原因、限制與下一步。

檔案要能被找到，也要能被驗證。新 Session 通常只知道工作目錄、平台、Git 狀態、branch 和最近 commit，不知道哪篇筆記最重要。因此需要清楚的入口、穩定的命名和按需讀取的指標。文件也要標示已確認、待驗證與未解問題，避免一份舊摘要被誤當成目前程式碼的真相。持久化解決的是狀態不會隨對話消失，不是從此可以停止檢查。

### 把「記憶」拆成三個不同的地方

與 AI coding agent 工作時，最容易造成誤判的詞就是「記得」。你說「它已經知道這個專案了」，可能是指它在目前對話中讀過檔案；你說「它記得我昨天的決定」，可能是指 harness 把昨天的訊息重新送回模型；你說「這個專案保留了我們的規則」，則可能是指規則被寫進了 repository。這三種情況表面上都像記憶，實際上保存位置、壽命和可靠性完全不同。

可以先把整個 agent 系統拆成三層。

第一層是模型。模型本身是無狀態的。每一次呼叫都可以視為一次新的計算，模型根據當下收到的 system prompt、對話內容、工具結果與使用者要求產生輸出。它不會因為上一次呼叫曾經看過某個檔案，就在下一次呼叫時自動保留那個檔案的內容；也不會因為昨天在同一個 repository 工作過，今天就從參數裡取出你的專案慣例。模型的參數包含訓練時形成的廣泛知識，但那不是針對你目前 Session 的個人長期記憶。

第二層是 harness，也就是包住模型的代理外殼。它負責管理 Session、保存訊息、呼叫工具、讀寫檔案、執行命令，以及把前面發生過的事情整理進後續請求。當代理在一個 Session 裡回答得像一位記得前情的同事，通常是因為 harness 把先前的對話和工具輸出持續保留，下一輪再整批或部分重送給模型。這種狀態是真實存在的，但它的範圍是目前 Session。清空 Session、建立新 Session，或換到另一個不共享歷史的 harness 後，沒有被保存到環境的那部分脈絡就不會自動跟過去。

第三層是環境。環境包括 repository、檔案系統、版本控制中的檔案、文件、設定、工作產物和其他可被再次讀取的資料。這一層的狀態不會因為你清空一段對話而消失。只要檔案還在，新的 Session、另一個模型或另一個代理就有機會透過探索把它讀回來。這就是「以檔案作為記憶」的基礎：不是把記憶硬塞進模型，而是把未來仍有價值的知識放在模型可以重新取得的環境裡。

這個區分很實用，因為它告訴你故障發生在哪裡。若模型在同一輪對話中忘記剛剛讀過的內容，可能是上下文太長、注意力下降或 harness 沒有正確傳遞工具結果。若清空後它不記得前一段討論，這是 Session 狀態的自然限制，不一定是代理出錯。若新 Session 讀到過時的專案規則，則是檔案記憶沒有更新或缺乏驗證。沒有先分清楚三層，你很容易用錯方法，例如用外部記憶幻想修補其實只是尚未寫檔的問題，或用重新解釋需求來掩蓋 repository 裡的文件已經過期。

### Session 內的「記得」其實是重送上下文

想像你在一間白板室裡和一位很會工作的顧問合作。顧問每次只會看眼前白板上的內容，離開房間後不會把白板內容帶在身上。為了讓合作看起來連續，助理每次在顧問回來時，把前幾次會議紀錄、已讀檔案和工具結果重新貼到白板上。只要白板還沒有太滿，顧問就能接著說；但若助理清空白板，先前只存在會議紀錄裡的理解也就不在眼前了。

harness 的 Session 很接近這個比喻。它把對話歷史、工具呼叫和結果保存在一個可延續的請求脈絡中，因此模型能根據先前內容作答。這個機制有兩個後果。第一，Session 越長，能夠攜帶的內容越多，成本和注意力負擔也越大。第二，Session 內的連續性不是檔案系統的持久性。你可以把幾百輪對話都留在某個介面裡，但那仍然是一份由特定 harness 管理的暫時歷史，不一定能被下一個代理或下一個工作目錄使用。

因此，不要把「它剛才答對了」當成「這個知識已經保存」。如果你剛剛花半小時向代理說明資料模型、命名原則和某個看似奇怪的相容性限制，而這些內容沒有寫進文件，那麼清空 Session 後，它們對新代理而言仍然不存在。即使你沒有清空，長 Session 也可能讓早期的關鍵決策被大量檔案輸出淹沒。只有把穩定而重要的內容轉換成可讀檔案，才能讓它脫離當前對話的壽命。

這不表示每一句對話都必須保存。對話裡有大量一次性的思考、錯誤嘗試、重複確認和不值得長期遵守的細節。把所有內容原封不動寫入檔案，會製造另一種上下文污染。真正需要落盤的是下一次工作仍然需要的事實、決策、限制、進度和入口，而不是完整的聊天錄音。好的檔案記憶是經過整理的工作資產，不是把 Session 的沉積物搬到硬碟。

### 「我的 code base 就是記憶系統」意味著什麼

把 code base 當成記憶系統，不只是把幾個筆記檔放進 repository，還包含一種工作習慣的改變。你不再問「怎麼讓模型永久記住這件事」，而會問「怎麼把這件事寫到一個未來的代理能找到、理解、檢查並使用的位置」。記憶的設計問題因此變成檔案設計問題。

如果某個決定會影響後續實作，就應該有一個可被追蹤的紀錄。例如你決定某個功能只服務已登入使用者、某個資料表必須保留軟刪除、某個外部 API 只能從 server side 呼叫，這些都不該只停在討論裡。它們可以進入設計文件、任務規格、架構決策紀錄或專案指引。下一個 Session 不需要相信代理曾經參加過會議，只需要讀取這份文件，再用程式碼確認它是否仍適用。

如果某個探索結果會縮短未來的入門時間，也值得落盤。技術棧、啟動指令、測試指令、重要目錄、資料流、路由邊界和特殊術語，都是新代理第一次進入 repository 時需要重新建立的地圖。你不必把整個專案每一行都複製到筆記裡；只要保存一張有證據支撐的導航圖，讓代理知道先讀哪些檔案、哪些結論已確認、哪些問題還沒有答案，就能大幅降低下一次探索的摩擦。

如果某個工作流程會被重複執行，也應該把它變成文件或可重用的 skill。課程中的 `teach` skill 是一個清楚的示範。它不只在目前對話裡介紹工作區，而是建立 `mission.md`、`notes.md`、`resources.md`、glossary 和第一篇 lesson 等實體學習資產。這些檔案形成一個能被重新閱讀的工作區。清空上下文後，代理不是靠內在記憶猜測你學到哪裡，而是透過這些檔案恢復學習目標、已知內容、資源入口和下一步。

這種做法的力量在於檔案是可檢查的。你可以直接閱讀它、修改它、讓 Git 記錄它的變化、在 code review 中討論它，也可以把它交給另一個代理。模型的暫時印象沒有這些特性。當你把記憶放進檔案系統，記憶就從一個不可見的模型狀態，變成團隊可以共同維護的工作資產。

### 什麼內容值得寫進檔案

一個簡單的判斷方法是問：「如果明天換一個 Session，我還希望代理知道這件事嗎？」如果答案是肯定的，再問第二個問題：「這個知識能否用幾句可驗證的文字表達？」若兩個答案都是肯定，就應該考慮落盤。

第一類是方向與目的。包括專案服務的使用者、當前工作的目標、功能不打算解決的問題，以及成功條件。沒有這些內容，代理可能能修改程式，卻不知道什麼叫正確的產品行為。方向文件不用很長，但應該能讓新 Session 分辨「做出一個可運作的東西」和「做出這個專案真正需要的東西」之間的差別。

第二類是已確認的設計決策。包括資料模型選擇、介面行為、權限邊界、相容性承諾、錯誤處理策略和刻意保留的怪異實作。尤其是那些不能從程式碼表面直接推導的決定，更值得記錄。程式碼能告訴代理現在做了什麼，但未必能告訴它為什麼不能用看似更簡單的方式改寫。把原因保存下來，可以避免下一個 Session 把歷史決定當成偶然，重新引入已經排除的風險。

第三類是探索地圖。記錄根目錄的重要檔案、主要模組、啟動和驗證方式、代表性呼叫鏈，以及下一個任務的入口。這類文件的目的不是取代直接讀程式碼，而是降低尋路成本。它像地圖上的索引，而不是整座城市的照片。檔案名稱和位置要穩定，內容要說明哪些結論來自哪些程式碼區域，並列出尚未確認的部分。

第四類是當前進度和交接資訊。正在處理哪個問題、已完成哪些部分、哪些測試已通過、哪些失敗仍待調查、下一步應先讀或先做什麼，都能幫助新的 Session 快速接手。這種記錄特別適合在工作階段交界處產生，因為那時候你已經有一個自然的整理時機。它不必保存整段思考，只要保存足以讓下一個工作者重新建立判斷的骨架。

第五類是專案詞彙和共享資產。專案中的縮寫、領域名稱、特殊狀態值和容易混淆的概念，可以集中到 glossary。共用的樣式、範例、測試資料、教學頁面和參考資源，也可以放在清楚命名的目錄中。當這些東西位於穩定的位置，新代理可以透過入口文件找到它們，不必依賴某一位人類或某一段舊對話來解釋。

相反地，以下內容通常不應直接成為長期記憶：一次性的猜測、沒有驗證的臨時方案、已經被否決但沒有標記的方向、整段工具輸出、敏感憑證，以及只與某次對話相關的閒聊。若未驗證的推論很重要，可以保留，但要明確標示為待確認，而不是寫成和程式碼事實相同的口氣。若資訊涉及秘密，應使用安全的秘密管理方式，不要因為「檔案可以記憶」就把金鑰或個人資料寫進普通文件。

### 設計一個讓新 Session 找得到的記憶庫

檔案存在不代表代理就會使用它。新的 Session 通常知道工作目錄、平台、Git 狀態、branch 和最近 commit 等環境中繼資料，但不知道 repository 裡完整的檔案清單，也不會自動知道哪一篇筆記最重要。要讓檔案系統真正成為記憶，需要同時設計保存、命名和取回。

首先，給不同用途的內容清楚而穩定的入口。可以有一份專案導覽文件，指出產品目的、技術棧和關鍵目錄；可以有一份工作狀態文件，記錄目前進度與待辦；可以有一份決策文件，保存不能從程式碼直接推導的原因；也可以有一個 docs 或 skills 目錄，收納按需讀取的詳細程序。重點不是採用某一組固定檔名，而是讓新代理能從少數入口沿著指標找到更多內容。

其次，避免把所有記憶推送到每一輪上下文。固定載入的長篇規則會持續佔用 token 與注意力，即使目前任務完全不涉及它們。更好的方式通常是用短指標指出文件位置，等任務需要時再讀取詳細內容。這樣檔案仍然可達，但不會變成每次請求都要支付的常駐負載。記憶要持久，卻不必常駐在模型眼前。

再次，讓檔案在開頭就說明自己的用途、適用範圍和更新方式。新代理讀到一份文件時，應該能快速知道它是架構導覽、目前交接、資料庫流程還是學習筆記。若所有文件都只叫 `notes.md`，或內容混合了十個互不相關的主題，代理即使能找到它，也不一定能正確判斷該使用哪一部分。清楚的結構本身就是對未來 Session 的引導。

最後，在工作要求裡明確告訴代理先找記憶入口。例如可以要求它先讀專案導覽和目前狀態，再檢查相關程式碼，最後回報哪些文件與現況一致。這不是因為代理沒有讀檔能力，而是因為 fresh Session 不知道你的知識架構。短短一句入口提示，能把「盲目列出所有檔案」變成「先讀高價值索引，再按任務深入」。

### `teach` skill 示範的持久化工作流

`teach` skill 的價值不在於某一組特定檔案名稱，而在於它把一次性的理解工作轉成可重複的工作區。它可以把專案探索整理為 mission，讓工作目標不只存在於對話；用 notes 保存已經學到的內容與疑問；用 resources 集中重要的閱讀入口；用 glossary 固定領域詞彙；再用 lesson 把局部知識編排成可閱讀、可驗證的材料。

這套結構可以套用到不只教學的工作。做一個長期功能時，mission 可以是功能的產品目的和成功條件；notes 可以是探索結果、決策與未解問題；resources 可以是規格、API 文件和相關模組；glossary 可以是領域詞彙；lesson 則可以替新成員或新代理解釋一條重要流程。這樣一來，代理產生的檔案不只是目前 Session 的副產品，而是下一次協作可以使用的中介層。

要注意，這些檔案不是「代理的腦袋備份」。它們是外部記錄，必須能被人讀懂，也必須接受驗證。代理下一次讀到 notes 後，仍然應該回到相關程式碼檢查關鍵事實，而不是把筆記當成不可質疑的真相。若程式碼已經改過，應該更新相應文件；若一個問題已經解決，應該移除或標記舊的待辦；若兩份文件互相矛盾，應該先停下來釐清，而不是任意選一份。

這也表示持久化不是一次性的「寫完就結束」。它是一個循環：探索產生記錄，記錄幫助下一個 Session 定位，下一個 Session 用程式碼驗證記錄，驗證結果再更新記錄。只有經過這個循環，檔案系統記憶才會逐漸變得可靠。否則你只是把一次可能錯誤的摘要保存得更久。

### 跨 Session 接續工作的具體流程

可以把一個可重複的工作流程分成幾個階段。第一階段是在目前 Session 中建立理解。先要求代理探索技術棧、產品用途、主要目錄和與當前任務有關的呼叫鏈，並要求它區分已確認、推論和未知。這一步的目標不是馬上修改檔案，而是收集足夠證據。

第二階段是整理持久化材料。讓代理把穩定的內容寫入適當文件，包括工作目標、重要設計決策、探索地圖、已完成項目、失敗測試和下一步。整理時刪除重複敘述，保留能影響決策的細節，並把不確定內容標記出來。若這些材料會由團隊共同使用，應放在 repository 內適合版本控制的位置；若只是一次性的跨工具交接，則可以使用不會污染專案的暫存 handoff 文件。

第三階段是驗證落盤結果。要求代理列出它寫了哪些檔案，每份檔案的用途是什麼，下一個 Session 應該先讀哪一份，以及哪些內容仍需要直接檢查。你也可以立刻閱讀文件，確認它沒有把猜測寫成事實、沒有漏掉關鍵限制、沒有留下秘密或不必要的整段輸出。這個檢查能在記憶被交給未來之前，先抓出品質問題。

第四階段是有意識地結束目前 Session。當上下文接近負擔上限、工作從實作轉向 QA，或你要交給另一個代理時，不要只按下清空。先把能跨越邊界的理解保存下來。清空後，新 Session 仍然要重新探索檔案系統中的入口，但它不必重新猜測所有歷史背景。這就是把 Session 當成可丟棄的暫時工作桌，而把 repository 當成可持續的工作場所。

第五階段是新 Session 的恢復。開場時先讀取持久化入口，再讓代理用目前程式碼核對關鍵內容。可以要求它回答：目前工作的目標是什麼、已經完成什麼、有哪些決策、接下來的入口在哪裡、哪些事項仍未確認。若它只能重述文件，卻沒有檢查程式碼，恢復尚未完成；若它發現文件與程式碼不一致，應優先修正理解和記錄，再繼續工作。

第六階段是把新發現回寫。新的 Session 可能發現原先的導覽漏掉了一個模組、某條指令已經更換、某個設計決策需要補充。不要只在當下記住這個修正。若它對未來仍有價值，就更新文件，讓後來的 Session 受益。如此反覆，工作區會從單純的檔案集合，逐漸變成一張與實際程式碼同步的協作地圖。

### 不要把持久化文件誤認成真相

檔案記憶比 Session 對話可靠，卻不代表它永遠正確。文件可能由代理根據有限探索產生，可能省略了例外情況，也可能在程式碼演進後過時。持久化解決的是「狀態隨 Session 消失」，不是「內容從此不必驗證」。這個界線一定要保留，否則新的錯誤會以一份看似正式的文件為依據被重複放大。

可以在文件中使用三種明確標籤來管理可信度。第一種是已確認，代表內容已由目前程式碼、測試或正式規格支持。第二種是待驗證，代表這是合理推論，但新 Session 使用前必須檢查。第三種是未解問題，代表它是需要後續調查的缺口，而不是可以直接拿來實作的需求。這些標記讓未來的代理知道哪些內容可以當作起點，哪些內容必須重新求證。

更新策略也要和變更風險匹配。小型重構可能不需要更新整份架構導覽，但若更換 framework、資料庫、路由系統、測試工具或產品邊界，就應該重新檢查相關文件。若文件明確列出適用範圍和最後驗證時間，代理和人類都更容易決定是否需要重新探索。不要讓一篇寫得很完整的舊文章，因為形式漂亮就獲得高於目前程式碼的權威。

### 實作練習：親手證明檔案能跨越 Session

在自己的 TypeScript 或 Node repository 中做一個小型實驗。先開一個新的 Session，不交付任何功能，只要求代理探索專案的技術棧、用途、重要目錄、啟動方式和一條代表性流程。要求它說明判斷的證據，不接受只列結論。觀察它實際讀了哪些檔案，以及它是否在未知處承認未知。

接著要求代理建立一組精簡的工作區記錄。至少包括一份 mission，說明你要完成的工作；一份 notes，保存已確認的架構與未解問題；一份 resources，列出下一次應閱讀的入口；以及一份 glossary，解釋專案中容易混淆的名稱。若你不想採用這組檔名，也可以使用自己的結構，但必須讓用途和入口清楚。請代理在檔案中寫入目前進度，不要只把內容回覆在終端畫面。

保存後，清空 Session，建立一個真正的新起點。不要先貼回舊對話，也不要告訴代理你剛剛說過什麼。只給它一個短指標，要求它先找到並讀取工作區記錄，再回答目前任務的目標、專案結構和下一步。這時你會看到一個重要差異：它仍然不會自動記得上一段對話，但它可以透過檔案重新建立足夠的工作狀態。

然後要求它打開一個核心程式碼檔案，核對 notes 中的一項判斷。若判斷正確，讓它指出目前檔案中的證據；若判斷已過時，讓它更新 notes 並標示修正原因。最後再問它哪些資訊仍然未知。這一步能防止實驗只證明「代理會照著筆記朗讀」，而是實際測試檔案記憶是否能支援理解、驗證和修正。

完成這個練習後，檢查四個結果。第一，清空 Session 是否確實讓未落盤的對話狀態消失。第二，新 Session 是否能從檔案入口恢復任務方向。第三，持久化文件是否讓重新探索變短，而不是增加另一堆無關上下文。第四，代理是否能指出文件與目前程式碼之間的差異。若答案是肯定的，你已經建立了比「希望模型記住」更可靠的跨 Session 工作方式。

### 最重要的工作習慣

每當你在 Session 中說出一句「這件事之後還會用到」，就停一下，判斷它是否應該成為檔案。每當你做出一個後續工作者需要理解的決定，就留下原因。每當你完成一輪探索，就保存一張足以讓別人重新定位的地圖。每當你準備清空或交接，就先把目前狀態整理成可讀的工作產物。每當新 Session 讀回文件，就要求它用程式碼確認，而不是無條件相信。

這套習慣會把代理協作從「一段長對話」改造成「Session 加上共享環境」的系統。Session 適合承載正在進行的推理、互動和暫時工具結果；檔案系統適合承載可重用的知識、規格、決策、進度和資產。前者可以被清空，後者應該被維護。你不必讓每一段對話永久存在，也不必把所有背景固定推送給模型；你只需要把真正值得延續的部分，放在下一個工作者能找到並檢查的位置。

當你接受模型無狀態、harness 只在 Session 內有狀態，環境才是跨 Session 的持久層，許多看似神祕的代理行為就會變得容易設計。新的 Session 不記得昨天，不是因為它不可靠，而是因為它本來就需要從環境重新取得狀態。你的工作不是消除這個事實，而是建立良好的文件入口、探索流程和驗證循環。把理解寫進 repository，讓檔案成為可以讀取、修改、版本控制和交接的記憶系統，代理才有機會在每次重新開始後快速恢復為可靠的工作夥伴。
