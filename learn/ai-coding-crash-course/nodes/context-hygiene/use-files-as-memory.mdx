## Learning goal

以檔案與探索紀錄跨 session 保存狀態，完成第一次有意識的 context 管理。

## Lesson

### 一個 18k token 的 session 消失後

你花了半小時帶代理讀懂一個 repo 的路由架構、模組邊界和 coding convention，context window 已經累積到 18k token。你關掉 session，隔天開了一個新的。代理坐在那裡，安靜地等你開口。

它記得昨天的對話嗎？

不記得。連一個字都不記得。

這不是工具壞了，是模型的根本特性。要跨 session 保留狀態，你必須先搞懂代理的狀態存在哪裡，然後學會把知識放對地方。

### 為什麼三層狀態模型很重要？

[[learn/ai-coding-crash-course/elements/filesystem-memory|檔案系統作為記憶 (Filesystem as Memory)]] 把代理的狀態分成三層，每一層的持久性完全不同。搞混這三層，你會在錯誤的地方找記憶。

**第一層：模型（model）完全無狀態。** 每次呼叫模型，它不會把前一次呼叫的任何內容帶進來。你給它一段文字，它回一段文字；你再給它一段文字，它再回一段文字。兩次呼叫之間，模型內部不存在任何記憶軌跡。你在對話中發現代理好像「記得」前幾輪的內容，那不是模型在記憶，而是 harness 把先前的對話重新整包送進模型的輸入。

**第二層：harness 有狀態，但只在當前 session 內有效。** Harness 是你和模型之間的橋樑，負責管理對話歷史、工具呼叫、技能載入和上下文組裝。在一次 session 裡，harness 會持續把目前為止的所有對話內容重新送給模型，讓模型看起來像「記得」之前發生過的事。但這個「記得」有兩個限制。第一，它消耗 context window 容量，每多一輪對話，下次請求的輸入就更大。第二，它只在 session 存活期間有效。你清空 session、關掉終端、重啟 harness，這些對話歷史就全部消失。Harness 的狀態是暫時的，它的「記憶」長度等於 session 的壽命。

**第三層：環境（environment）是真正持久的，尤其是檔案系統。** 你在 session 中寫下的每一個檔案、修改的每一行程式碼、建立的每一份文件，都會落盤到磁碟上。即使你關掉 session、重啟電腦、甚至換一台機器（只要 repo 被 push 過），這些檔案仍然存在。下一個 fresh session 的代理可以透過探索重新讀取它們。檔案系統不受 session 邊界限制，它是最穩定的持久狀態。

三層之間的關係很清楚。模型層負責運算，不負責存儲。Harness 層在 session 內維持對話連貫性，但 session 結束就清空。環境層把資訊持久化到磁碟，跨越所有 session 邊界。跨 session 要保留任何知識，你只有兩個選擇：依賴外掛式記憶系統（例如把摘要存到某個外部服務），或者直接把知識寫進檔案系統。課程的立場是，程式碼庫本身就是記憶系統。引用 Mario Zechner（Pi 的創造者）的說法：「my code base is my memory system。」

### Fresh Session 的認知邊界

上一步你已經用 request logger 看過 fresh session 拿到的內容。再回顧一次重點，因為它和檔案系統作為記憶直接相關。

一個全新 session 啟動時，代理收到的環境資訊包括：

| 資訊項目 | 代理知道嗎？ |
| --- | --- |
| 作業系統類型（Linux、macOS、WSL） | ✅ 知道 |
| 主要工作目錄路徑 | ✅ 知道 |
| 是否為 git repo | ✅ 知道 |
| 使用的 shell 類型 | ✅ 知道 |
| 目前 branch 和主要 branch | ✅ 知道 |
| 最近幾筆 commit 的標題和 hash | ✅ 知道 |
| repo 裡有哪些檔案和目錄 | ❌ 不知道 |
| `package.json` 裡有哪些相依套件 | ❌ 不知道 |
| README 寫了什麼 | ❌ 不知道 |
| `src/` 裡的模組結構 | ❌ 不知道 |
| 用了什麼框架 | ❌ 不知道 |
| 有沒有測試、有沒有 CI 設定 | ❌ 不知道 |

這些資訊足以讓代理知道「我在哪裡」和「最近做過什麼」，但完全不足以回答「這個專案是什麼」。

**為什麼這很重要？** 代理站在一個房間裡，能看到門牌號碼和一張最近的會議紀錄摘要，但房間裡的書架、文件櫃和白板對它來說全部是隱形的。它必須自己走過去翻閱，才能建立理解。上一步你學會的探索方法，就是在做這件事。但有一個問題沒有回答：這些探索結果怎麼跨 session 保留？

答案是，把探索結果寫成檔案。

### Teach Skill 示範了什麼？

課程中展示了一個叫做 teach skill（教學技能）的工具，它的設計清楚示範了檔案系統如何承擔跨 session 記憶的角色。

當你在一個陌生 repo 上啟動 teach skill，它不會只在對話裡口頭解釋專案。它會建立一組實體檔案：

| 檔案 | 內容 |
| --- | --- |
| `mission.md` | 學習目標，例如「判斷一個全功能 mini-Udemy 應用程式的變更」 |
| `notes.md` | 你的學習進度和目前的理解程度 |
| `resources.md` | 主要參考來源，例如 React Router v7 的官方文件 |
| 詞彙表（glossary） | 專案中用到的關鍵術語和定義 |
| `styles.css` 等共用資產 | 共用的樣式和元件 |
| 第一篇 HTML 教學文章 | 用 React Router 的原生語言解釋路由機制，裡面包含 SSR（Server-Side Rendering，伺服器端渲染）的重要觀念 |

那份教學文章最後有一個練習指示：「Reading is not learning. Run the app and prove the boundary.」讀完不等於學會，要跑起應用程式，證明你理解了那個邊界。這不是被動的摘要，而是要求動手驗證的學習任務。

但 teach skill 最關鍵的特性不在它讀了多少檔案，而在它把探索結果寫進了磁碟。`mission.md`、`notes.md`、`resources.md`、詞彙表、教學文章，這些全部是持久化檔案。你之後清空 context window、關掉 session、甚至換一台機器，只要這些檔案還在 repo 裡，下一個 fresh session 的代理就可以從這些檔案開始重建理解。

**為什麼這很重要？** 這就是「有狀態的學習工作區」（stateful learning workspace）的運作方式。代理本身不記得你，但檔案系統記得。teach skill 把「模型應該記得的東西」從模型的輸入搬到磁碟上，讓環境承擔記憶的角色。你可以隨時 clear context，再回來接著學。Skill 不是憑空記得你學到哪裡，而是重新讀取它先前寫下的檔案。

### 從被動保留到主動管理

teach skill 的做法可以推廣到任何工作場景，不一定要用這個特定的 skill。核心習慣只有一個：每當你在 session 中探索完一個專案、建立了一段有價值的理解，就把關鍵發現寫進檔案。可以是 `LEARNING.md`，可以是 `CONTEXT.md`，可以是任何你自己或團隊能辨識的格式。重點是它必須脫離 context window，變成檔案系統中的一個穩定存在。

舉個具體例子。你在上一步問了「這個專案的 tech stack 和 intended purpose 是什麼」，代理去讀了 README 和 `package.json`，回來告訴你用了什麼框架、專案目的是什麼。這段對話結束後，這些理解存在 context window 裡。如果你現在不寫任何檔案就離開，這些理解就跟著 session 消失。

但如果你在那個時候就叫代理把探索結果寫進一個檔案呢？例如寫一份 `PROJECT-NOTES.md`，裡面記著 tech stack、主要模組、路由結構、測試策略和任何你覺得下次 session 需要知道的東西。隔天開新 session，你第一句話可以說「讀取 `PROJECT-NOTES.md`，然後接著昨天的工作」。代理會去讀那個檔案，在幾秒鐘內恢復昨天花半小時建立的理解。

**為什麼這很重要？** 你省下的不只是時間，還有 context window 的空間，因為你不需要把整段探索過程重新跑一遍。這就是有意識的 context 管理。你不是被動地看著 context window 被對話填滿，然後在某個臨界點清掉重來。你是在主動決定哪些知識值得跨 session 保留，然後把它們從暫時的 context window 搬到持久的檔案系統。每一次這樣的搬移，都是一次 context 管理的決策。

### 檔案格式的四個設計原則

既然跨 session 的知識要靠檔案保存，這些檔案本身也需要設計。四個值得記住的原則。

**1. 穩定的命名和位置。** 如果你每次把探索結果存到不同名字的檔案，下一個 session 的代理就要猜哪個檔案才是最新的。統一命名（例如 `PROJECT-NOTES.md`）和固定位置（例如 repo 根目錄或 `.context/` 資料夾）可以消除這個猜測成本。

**2. 足夠的自含性。** 這些檔案是給一個「失憶的同事」讀的。他不知道你上次對話的脈絡，不知道你用了什麼縮寫，不知道你為什麼覺得某個設計決策很重要。檔案內容要寫到一個陌生的代理讀完就能恢復工作狀態的程度，不依賴口頭補充或隱含脈絡。

**3. 為重讀而寫。** 既然這些檔案的讀者是未來的代理（或者是未來的你自己），寫作時就應該想著「下次有人需要在 30 秒內理解這個專案，他需要看到什麼」。這和寫給人看的文件不同，它是寫給一個需要快速恢復狀態的代理人看的。

**4. 漸進式更新。** 不需要每次把整個檔案重寫一遍。隨著你對專案的理解加深，可以用 append 或 targeted edit 的方式更新特定段落。只要檔案的結構保持穩定，代理就能在重讀時快速定位需要的資訊。

### 五步 Context Hygiene 回顧

到目前為止，你已經完成了這條線路的全部步驟。回顧一下你走過的路。

1. **重置 harness**，把代理設定恢復到乾淨基線。
2. **清除 system prompt 裡的贅肉**，確保每次請求不會被無用的工具和技能佔據空間。
3. **學會用 token 計數器**持續追蹤 context 的消耗。
4. **理解 fresh session 的認知邊界**，學會探索的方法。
5. **把探索結果寫進檔案系統**，讓知識跨 session 持久化。

這五步串在一起，就是完整的 context hygiene（上下文衛生）。它不是一次性的設定，而是一套可以重複的工作習慣。每次開新 session，你都知道代理知道什麼、不知道什麼。每次探索完，你都知道哪些知識值得寫成檔案。每次 context 開始膨脹，你都知道該清理什麼、保留什麼。

### 心態轉變

最重要的轉變是心態上的。你不再把代理當成一個「應該自己記住一切」的工具，而是把它當成一個「需要你幫它管理記憶」的協作夥伴。它的記憶不在它的腦袋裡，在你的檔案系統裡。你管理檔案系統的方式，就是你管理這段協作關係的方式。

把探索沉澱成檔案，是你作為駕駛者（driver）能做的最簡單也最有效的 context 管理動作。從現在開始，每次你在 session 中建立了值得保留的理解，花 30 秒叫代理寫進檔案。下次 session 的你會感謝現在的你。
