## Learning goal

學完這一步，你能在開始一段重要的代理工作前，判斷外殼是否背著不必要的設定、技能與整合，安全地備份並暫時移開它們，建立乾淨的上下文基線，再用可觀察的數字確認你究竟取回了多少工作空間。你也能分辨「重置」與刪除、壓縮、修剪規則之間的差別，並把同一套思路轉移到不同的代理工具。

## Lesson

### 📝 先看一個前後對照

課程示範先量一次起始上下文：真正開始工作前，大約已經用了 23k token。把外殼裡不必要的設定和技能暫時移開後，再重新啟動、重新測量，剩下約 6.6k token，也就是拿回約 17k 的空間。

這組數字很有用，但它不是標準答案。不同帳號、版本、作業系統、harness、專案設定和啟用的整合，都會讓結果不同。你真正要學的不是背住 23k、6.6k、17k，而是學會做前後比較：先知道原本佔了多少，再知道重置後少了多少。

**為什麼這很重要？**
因為重置不是為了追求一個漂亮的最低數字，而是為了把更多空間還給需求、程式碼和推理。

### 💡 你在重置的不是聊天，而是工作外殼

很多人看到代理變慢，第一個反應是清掉聊天紀錄，或直接開一個新的 session。這有時有幫助，但它處理的主要是對話歷史，不一定碰到真正的負擔。

更常見的情況是，在你還沒輸入第一句正式任務前，外殼就已經先載入很多東西，例如系統指示、專案設定、權限規則、技能、MCP 工具、第三方連接器、工作流程和產出工具。畫面上看起來像是空白對話，但模型實際收到的工作材料，可能早就堆了不少。

這裡的「外殼」不是模型本身。模型每次都是根據當下收到的輸入產生輸出，它不會自己保留上一輪的私人記憶。真正負責管理 session、工具、檔案、權限和附加說明的，是外殼這一層。它會把對話內容和工具結果整理後，再送進下一次 request，所以代理才看起來像記得前情。

[[learn/ai-coding-crash-course/elements/harness-reset|代理外殼重置 (Harness Reset)]]的重點，就是把這個起點整理乾淨。不是把代理變成什麼都沒有，而是清楚知道：哪些能力正在常駐、哪些東西可以暫時移開、哪些內容其實不該每次都跟著任務一起進場。

### 🔧 為什麼無關內容會真的拖累工作

可以把上下文窗口想成代理的工作桌。桌子越大，能同時攤開的東西越多；但如果桌上先放滿資料庫 migration 手冊、設計系統同步說明、通知推送工具、遠端觸發器、瀏覽器自動化規則，還有這次根本不會用到的技能，那真正要處理的程式碼和需求，就會被擠壓。

問題不只是在於容量變少。代理還要額外花力氣判斷：哪些規則和現在的任務有關，哪些工具值得呼叫，哪些工作流其實只是背景噪音。假設你現在只是改一個 React 元件，外殼卻同時背著資料庫流程、部署流程、設計工具和通知服務。這些東西單看都可能有價值，但「可能有價值」不等於「每個任務都該常駐」。

固定負載越多，代理越容易發生兩種問題：

1. 把次要規則誤當成主要目標
2. 在一長串工具裡選錯該走的路

最後，你不只要付出更多 token，也要付出更多等待時間和更多人工監督。

### ⚖️ 上下文衛生不是清空，而是匹配任務

上下文衛生的意思，不是把環境清成全白，而是讓常駐的東西和眼前工作相配。

比較適合長期留下的，通常是跨任務都適用的內容，例如：

- 安全限制
- 測試規則
- 專案目錄慣例

比較不適合一直常駐的，通常是只在特定情境才用得到的內容，例如：

- 只有做資料庫工作時才需要的 checklist
- 只為了一次實驗裝上的技能
- 只有少數任務才會用到的整合或工作流

這類內容更適合放進文件，等真的需要時再讀，而不是每個 session 都先一起載入。

**為什麼這很重要？**
因為不相干的內容不只是「有點吵」，而是會變成每一次決策都要一起承擔的隱形成本。

### 📏 重置前先量，不要憑感覺改

在動手之前，先建立基線。最簡單的做法是開一個 fresh session，在還沒輸入真正工作內容前，先檢查上下文使用量。

Claude Code 在課程裡用的是 `/context`。這個指令可以幫你看到，外殼目前已經帶了哪些內容進來。你不只要看總 token 數，也要看來源大致在哪裡，例如：

- 內建技能
- 專案檔案
- MCP 工具
- 連接器
- 其他系統級說明

課程示範看到的起始量是約 23k token，內容包含內建技能、專案內容，以及 claude.ai 的 MCP 工具。重置後變成約 6.6k token，等於拿回約 17k 的可用空間。這告訴我們一件事：代理甚至還沒開始讀你的需求，環境本身就可能先吃掉很大一段上下文預算。

所以你不需要問：「為什麼我的結果不是剛好 6.6k？」
你真正該問的是：

- 我的基線是多少？
- 最大的來源是什麼？
- 哪些內容現在其實不需要？
- 移開之後，我拿回多少空間？

測量的價值，在於把環境噪音和模型能力分開。這樣之後如果出問題，你才不會把所有失誤都怪到模型或提示詞身上。

### 🛟 安全原則只有一句：備份，不要刪除

重置最重要的原則，是可逆。

以 Claude Code 的目錄結構為例，課程示範的做法是把 `.claude/settings.json` 改名成 `settings-backup.json`，再把 `.claude/skills` 改成一個清楚標示用途的備份目錄。這樣做之後，外殼會暫時找不到原本自動載入的設定和技能，但內容本身都還在。

這件事看起來只是改檔名，本質上卻和刪除完全不同。直接刪除，可能會把權限、工具選項、個人偏好或團隊約定一起弄丟。改名則是把「暫時停用」和「永久移除」分開。你可以先重啟代理，看基線有沒有下降，再決定要不要還原備份，或者只把真正需要的東西一個一個放回來。

備份時還要注意兩件事：

- 名稱要夠清楚，避免其他外殼把備份誤認成正式設定
- 如果是在團隊共用的 repo 裡操作，要分清楚哪些是個人設定，哪些是團隊共同配置

不要把個人備份誤提交進版本庫，也不要為了做一次課程實驗，順手改壞整個團隊都在依賴的規則。

### 🔄 改完之後，一定要重新啟動再量一次

把檔案改名之後，不要立刻在原本的 session 裡下結論。舊 session 可能早就讀過那些設定了。你如果還在同一個 session 觀察，很容易得到錯的結果。

正確流程是：

1. 建立基線
2. 把想停用的設定或技能改名成備份
3. 重新啟動或重新載入外殼
4. 再量一次上下文使用量
5. 比較前後差異

如果數字明顯下降，表示你確實移掉了一部分固定負載。如果數字幾乎沒變，就代表膨脹來源可能不只是在這批檔案，也可能還包括使用者層級設定、MCP、內建工作流，或其他系統級內容。

### 📦 怎麼判斷哪些東西該留，哪些該移開

重置後少了 token，不代表被移走的東西全部都是垃圾。有些技能這次用不到，下個任務卻可能很重要。有些連接器不適合課程實驗，卻可能是你平常工作的核心。

一個實用的分法，是把內容分成三類：

| 類別 | 代表內容 | 建議做法 |
| --- | --- | --- |
| 明確無關的固定負載 | 這次完全不會用到的整合、工作流、工具定義 | 維持停用 |
| 有價值但只在特定情境需要 | 例如資料庫 migration checklist | 改成按需讀取的文件 |
| 跨任務都適用的基本規則 | 測試方式、危險命令限制、專案目錄慣例 | 通常保留 |

這個分類背後有一個很重要的原則：不要把「最小化 token」當成唯一目標。你真正要最大化的，是工作品質和可用空間的平衡。若只是為了省下幾百個 token，就把安全規則也一起拿掉，最後可能會換來更多返工、錯誤和人工監督，總成本反而更高。

### 🧪 如果膨脹很頑固，就逐項做實驗

有時候你把設定和技能移開了，基線還是很大。這時不要一次亂改十個地方。比較穩的做法，是一次只動一個來源，然後重新啟動、重新測量、記下結果。

這樣做有兩個好處：

1. 你知道到底是哪一項真的在吃上下文
2. 如果功能突然壞掉，也比較容易快速恢復

可疑來源可能在很多層：

- 專案層級
- 使用者層級
- 外殼本身
- 自動載入的 MCP 連接器
- 內建工作流程
- 工具清單
- 產出功能
- 很長的系統提示

不同 harness 的設定位置和停用方法都不同，所以不要把 Claude Code 的檔名當成通用指令。真正可移植的，是這一套方法：先備份，建立乾淨起點，再重新量測，根據差異找來源，最後決定要保留、延後載入，還是停用。

### 🗺️ 重置完不代表代理已經懂你的 repo

外殼變乾淨，不等於代理已經理解專案。重置做的事，是把背景負載清掉，不會自動補上程式碼架構、產品目的或團隊慣例。

開一個 fresh session 之後，代理通常知道一些環境和版本控制中繼資料，例如平台、工作目錄、是否為 git repo、目前 branch、最近 commit 等等。但它不會因為站在 repo 根目錄，就自動理解整個專案。

所以重置之後，不要第一步就直接叫代理改功能。比較穩的做法，是先讓它探索 repo，請它判斷技術棧和專案的大致用途，再看它有沒有去讀 README、package.json 和關鍵目錄，最後再根據它找到的證據追問。這樣可以避免代理只憑資料夾名稱或最近 commit，就開始猜整個專案在做什麼。

乾淨上下文能提供工作空間，但不能代替專案地圖。

### 💾 長期知識要寫回檔案，不要只留在對話裡

重置還提醒我們另一件事：真正重要的理解，應該寫回檔案系統。

任務說明、設計決策、專案慣例、探索筆記和教學資產，只要已經落盤，下次 session 就能重新讀取。清空上下文會讓對話裡的暫時狀態消失，但不會刪掉已經保存的檔案。

這也是為什麼檔案比模型的臨時記憶，更適合當成長期延續的載體。重置不是在抹掉工作成果，而是在提醒你：該長久保存的東西，應該住在 repo 裡，不是住在某一段聊天裡。

### 🔀 什麼時候用重置，什麼時候用別的方法

重置最適合用在工作入口，特別是這幾種情況：

- 你要開始一段新的課程或實驗
- 你想做前後可比較的測試
- 你懷疑外殼在開工前就背著大量無關內容

因為它處理的是：session 建立之前，外殼先載入了什麼。

但不是每個問題都該靠重置解決。下面這張表比較清楚：

| 方法 | 主要處理的問題 |
| --- | --- |
| 重置 | 外殼在開工前預載了什麼 |
| 壓縮 | 同一個 session 已經累積了什麼 |
| 修剪 | 長期引導檔案裡寫了什麼 |
| fresh session 探索 | 代理重新開始後，怎麼重新建立專案理解 |

例如，如果問題是同一個 session 已經累積很多讀檔、寫檔和討論歷史，那更像是壓縮要處理的事。壓縮會保留一部分重要脈絡，再濃縮帶進新的 session；重置則不會保留你目前對話裡的決策。如果問題只是長期引導檔案太長，那更像是修剪的範圍。若某份詳細的資料庫程序只有特定任務才會用到，那它更適合放進文件，固定設定只留下入口。

這些方法可以互相搭配，但不能彼此冒充。你如果用清空對話去解決預載膨脹，或用壓縮去解決缺少專案地圖，問題通常還會再回來。

### ✅ 一套可以重複使用的檢查清單

如果你想把這件事做成穩定流程，可以照下面六步走：

1. 在還沒有真正任務前，先用 `/context` 看基線和主要來源
2. 確認 `.claude/settings.json`、`.claude/skills`，或其他 harness 對應的位置
3. 把想暫停的內容改名成備份，不要刪除
4. 重新啟動外殼後再量一次
5. 逐項決定哪些內容要取回、哪些維持備份、哪些改寫成按需文件
6. 讓 fresh session 先探索 repo，再開始實作

每次做完，你都可以再問自己四個問題：

- 真正輸入任務前，預載了多少內容？
- 最大的來源是設定、技能、工具，還是整合？
- 重置後拿回多少空間？
- 為了拿回這些空間，有沒有同時拿掉安全規則或必要的專案知識？

只要把這四題固定下來，上下文衛生就不再只是模糊的焦慮，而會變成可以操作、可以比較、可以持續改善的工程檢查。

### 🚀 最後記住一個原則

成熟的做法，不是永遠使用同一個最小外殼，而是讓外殼跟工作匹配。

學習課程需要乾淨基線，資料庫任務需要資料庫規範，安全敏感的部署需要明確限制，日常小修正可能只需要少數通用工具。你可以保留多組可恢復配置，但每次啟動時，都應該知道現在載入了什麼，以及它為什麼值得佔用上下文。

當你答得出這兩個問題，重置就不再只是緊急救火，而會變成日常維護的一部分。
