## Learning goal

備份並重置代理外殼（harness）設定，讓外殼回到預設狀態，用 `/context` 確認基線 token 使用量，建立後續所有工作的乾淨 context 基線。

## Lesson

### 📝 一張截圖揭開的問題

某個開發者打開 Claude Code，跑了一個簡單的 `/context` 指令，畫面顯示：當前 session 已經佔用 23,000 個 token。他還沒打任何字、還沒給任何指令。這 23k token 裡面裝了什麼？內建技能（skills）、專案設定、MCP 工具（Model Context Protocol）、各種從上次 session 帶過來的整合連接器。這些內容從第一秒就開始壓縮代理後續可用的工作空間。

這就是[[learn/ai-coding-crash-course/elements/harness-reset|代理外殼重置 (Harness Reset)]]要解決的問題。

### 🔧 外殼在你說話之前載入了什麼

要理解為什麼需要重置，先搞清楚「代理外殼」是什麼。

在 Claude Code 的語境裡，外殼就是整套代理運行環境的設定層，包含四個部分：

1. `.claude/settings.json` 裡的行為規則
2. `.claude/skills` 目錄裡的自訂技能
3. 透過 MCP 連接的外部工具（搜尋引擎、資料庫連線、第三方 API）
4. 工作目錄或使用者設定裡啟用的整合

這些東西的出發點很好。技能讓代理知道你專案的慣例，MCP 工具讓它能搜尋文件或查詢 API，設定讓它遵守你的編碼風格。但它們有一個共同問題：全部在你送出第一個 prompt 之前就被塞進 `context window`（上下文窗口）。不管你要寫一個簡單的 utility function，還是重構整個模組，這些預載內容都安靜地佔據著每一輪對話的空間。

### 💡 為什麼預載內容是問題？

Context window 有硬上限。模型在某個 token 數量之後，開始丟失前面的資訊，推理品質明顯下降。你可能已經經驗過這個症狀：代理回答到一半忘記你早先的指令，或者產生前後矛盾的建議。根源往往不在模型本身，而在於 context window 已經被外殼的固定載入內容擠壓到「聰明區」（smart zone）的邊界之外。

### ⚡ 用數字看清楚問題的規模

把 23k token 拆開來看。假設模型 context window 上限是 200k token，23k 聽起來只佔了 10% 多一點。但實際運作中，你還有每一次 prompt、代理的每一轮回應、程式碼片段、錯誤訊息、git diff、測試輸出，全部都要塞進同一個窗口。一個稍微複雜的 refactoring session，來回十幾輪，很容易累積到 80k、120k 甚至更多。在那個累積過程中，最前面的 23k 永遠不會消失，它們會一直佔據位置直到 session 結束。

更關鍵的是，這些預載內容不是被動佔位。它們會被代理在推理時「閱讀」。如果裡面有過時的技能規則、不再適用的 MCP 指令、或是和當前任務無關的專案設定，代理的注意力會被分散。上下文衛生（context hygiene）的目標不只是省 token 費用，而是最大化代理在當前任務上的推理品質。

### 🔒 重置操作：備份，然後移開

[[learn/ai-coding-crash-course/elements/harness-reset|代理外殼重置 (Harness Reset)]]的核心操作只有一個原則：備份，然後移開，不要刪除。

以 Claude Code 為例，具體步驟如下：

1. 進入專案根目錄，找到 `.claude` 資料夾
2. 把 `settings.json` 改名為 `settings-backup.json`
3. 把 `skills` 目錄改名為 `skills-backup`
4. 重啟代理，外殼回到預設狀態

為什麼是改名而不是刪除？因為你以後可能需要它們。某個技能在特定任務上也許很有用，你想逐項放回；或者你需要比較重置前後的差異，確認是哪個設定造成膨脹。改名保留了完整的恢復路徑，讓你有退路。

其他代理工具的操作方式會不同，但原則一樣：找到存放自訂設定、技能或 MCP 連線的位置，把它們備份到不會被外殼自動載入的路徑。有些工具把設定存在 `~/.config/` 下，有些存在專案根目錄。重點是理解你的外殼從哪裡讀取設定，然後暫時把那個來源搬走。

### 📊 用 /context 確認基線

重置完成後，打開代理，什麼都不要輸入，直接跑 `/context`。這個指令顯示當前 session 在還沒有任何實際工作時，已經佔用了多少 token。

在前面的例子裡，重置後的基線從 23k 降到了大約 6.6k。取回了大約 17,000 個 token 的工作空間。這 17k 就是後續所有 prompt、回應、程式碼和推理的額外容量。

你的數字不會和這個例子完全相同。不同的外殼版本、不同的帳號設定、不同的已啟用整合，都會影響基線。重要的是你現在知道了自己的起點。這是一個可測量的、可重複的基準，後續所有的上下文管理策略（例如 compaction 壓縮、steering 檔案修剪）都是在這個基準之上運作。

如果重置後的基線仍然異常高，就逐項審查。打開備份的設定檔，逐一比對哪些內容是你真的需要的，哪些是歷史殘留。每次只恢復一項，用 `/context` 重新測量，直到你找到造成膨脹的具體來源。

### 🎯 為什麼乾淨基線很重要

重置代理外殼的意義不只是省下 17k token。它建立了一個控制組。當外殼回到預設狀態，你知道每次 session 的起點是一致的。後續如果品質出現問題，你可以排除「外殼設定污染」這個變因，把注意力放在 prompt 品質、任務拆解、或模型本身的限制上。

這也是為什麼課程不會使用你原本的設定繼續。每個人的 `.claude/settings.json` 裡可能有不同的規則，skills 目錄裡可能有不同數量和品質的自訂技能，MCP 連接器的數量和種類也不同。如果直接在這樣的環境上開始課程，你很難判斷哪些效果來自課程方法，哪些效果來自你原有的設定。先重置再開始，把噪音和信號分開。

重置完成後，你的外殼就像一個整理過的工作台。你還沒有放上任何工具，但工作台是乾淨的，你知道上面有什麼、空間有多大。接下來的每一步，你都會更清楚自己在做什麼，因為你已經消除了最容易被忽略、卻影響最深遠的噪音來源。
