## Learning goal

學完這一步，你能在開始一段重要的代理工作前，判斷外殼是否背著不必要的設定、技能與整合，安全地備份並暫時移開它們，建立乾淨的上下文基線，再用可觀察的數字確認你究竟取回了多少工作空間。你也能分辨「重置」與刪除、壓縮、修剪規則之間的差別，並把同一套思路轉移到不同的代理工具。

## Lesson

### 先用兩個數字確認重置是否值得做

課程示範在真正工作前約有 23k token，重置後約 6.6k，取回約 17k。這組數字不是每個 harness 都必須達到的標準，而是一個前後比較的案例。你應先記下自己的基線，再用可逆的方式移開設定和技能，重新啟動後再測量。若結果沒有變，就繼續找其他固定來源；若結果下降，就檢查被移開的能力是否仍有安全或工作上的必要。重置的成功條件不是數字最低，而是你知道少了什麼、取回多少，以及目前任務仍然能可靠完成。

### 先把問題看對：你不是在清理聊天紀錄

很多人第一次遇到代理變慢，會立刻清掉對話，再開一個新的 session。這個動作有時確實能改善情況，但它只處理了聊天歷史。真正的負擔可能在更早的地方。代理還沒有收到第一個工作指令以前，外殼就可能已經載入系統指示、專案設定、權限規則、技能、MCP 工具、第三方連接器、工作流程和產出工具。你看到的是一個空白對話，模型收到的卻可能是一張已經塞滿的工作桌。

這裡所說的「外殼」不是模型本身。模型每次只根據當下收到的輸入產生輸出，不會自己保留上一輪的個人記憶。外殼才是負責管理 session、工具、檔案、權限和附加說明的那一層。它把對話與工具結果整理後送回下一次 request，所以代理才看起來像一直記得前情。也因此，外殼在開場預先注入的內容，可能在後續每一輪都持續存在。

[[learn/ai-coding-crash-course/elements/harness-reset|代理外殼重置 (Harness Reset)]]的重點，是把工作起點重新整理，而不是追求一個空無一物的代理。重置的結果應該是你知道哪些能力被載入、哪些能力暫時移開，以及這個決定為何適合目前任務。真正要取回的是給需求、程式碼與推理使用的聰明區，而不是一個漂亮的最低 token 數。

### 為什麼無關內容會造成實際傷害

可以把上下文窗口想成一張代理的工作桌。桌子越大，能同時攤開的材料越多；但如果桌面一開始放著資料庫 migration 手冊、設計系統同步說明、通知推送工具、遠端觸發器、瀏覽器自動化規則和幾十個不會用到的技能，真正要修改的檔案就沒有同樣多的空間。問題不只在容量。代理還要花注意力判斷哪些規則與眼前工作有關，哪些工具值得呼叫。

假設今天只是修改一個 React 元件。外殼卻同時帶入資料庫流程、部署工作流、設計工具和通知服務。每一項功能單獨看都可能有價值，但「有價值」不等於「每個任務都該常駐」。固定內容越多，代理越可能把偶然出現的規則誤當成主要目標，也越可能在龐大的工具清單中選錯路徑。使用者則要為這些不相關內容付出 token 和等待時間。

上下文衛生不是把環境清成空白，而是讓常駐負載與工作相配。跨任務都適用的安全限制、測試規則和目錄慣例可以保留。只在資料庫工作時才需要的 checklist，可以放到文件裡，等真正涉及資料庫時再讀取。只為一次實驗安裝的技能，則不應無條件成為每個 session 的背景。為什麼無關內容很重要？因為它會把環境成本變成每個後續決策都要承擔的隱形成本。

### 先測量，再動手

重置前先建立基線，不要憑感覺改設定。開一個新的 session，在尚未輸入實際工作內容時查看上下文使用量。Claude Code 的示範使用 `/context`，它能顯示目前外殼已帶入的內容。除了總 token 數，也要注意來源大致分成什麼，例如內建技能、專案檔案、MCP 工具、連接器或其他系統級說明。

課程示範在真正開始工作以前看到約 23k token。這些內容包括內建技能、專案內容與 claude.ai 的 MCP 工具。重置後只剩約 6.6k，等於取回約 17k 可用空間。這個差距說明代理還沒讀需求，環境就可能先花掉一大段上下文預算。它不是每個人的標準答案，而是一個前後比較的例子。

不要問自己為什麼沒有剛好 6.6k。帳號、版本、作業系統、外殼、專案設定和啟用的整合都會改變結果。應該問的是：我的基線有哪些目前不需要的內容，移開後回收了多少？測量的價值在於把環境噪音和模型能力分開。若重置前就有大量固定負載，你才不會把後面的失誤全部歸咎於模型或提示詞。

### 安全的重置原則：備份，不要刪除

重置的第一個動作是備份。以 Claude Code 的目錄結構為例，可以把 `.claude/settings.json` 改名為 `settings-backup.json`，再把 `.claude/skills` 改名成清楚標示用途的備份目錄。改名會讓外殼暫時找不到原本自動載入的設定與技能，但內容仍然完整保留。

這個差異看似只是檔名，實際上是可逆性。刪除會讓你失去權限、工具選項、個人偏好或團隊約定，之後只能靠記憶重建。改名則把暫時停用和永久移除分開。你可以重啟代理確認基線變化，之後再還原備份，或只把真正需要的項目逐一放回。某項工作突然失效時，也能拿原始內容做比較。

備份名稱要清楚，避免其他外殼把備份檔誤認成正式設定。在團隊共享的 repo 裡，還要確認哪些是個人設定、哪些是團隊共同配置。不要把個人備份意外提交到版本庫，也不要為了課程實驗改動所有人都依賴的規則。安全重置首先是環境管理，其次才是數字優化。

改名後要重新啟動或重新載入外殼，再執行一次基線檢查。舊 session 可能已經讀過原設定，繼續在裡面觀察會得到錯誤結論。若數字下降，記下下降來自哪一層；若沒有明顯下降，代表膨脹可能還在使用者層級、MCP、內建工作流或其他來源，不能只重複改名同一批檔案。

### 如何讀懂重置前後的差異

重置後少了 token，不表示所有被移走的東西都是垃圾。某個技能可能本次沒有用，下一個任務卻很重要；某個連接器可能不適合課程實驗，卻是日常工作的核心。要把「現在不需要」和「從來不需要」分開。

可以分成三類。第一類是明確無關的固定負載，例如本次完全不會使用的整合、工作流和工具定義。它們適合維持停用。第二類是有價值但只在特定情境需要的內容，例如資料庫 migration checklist。它們應該放在可按需讀取的文件裡，固定設定只留下短指標。第三類是跨任務都適用的基本規則，例如測試方式、危險命令限制和專案目錄慣例。它們值得保留，因為能避免的錯誤通常比所佔 token 更昂貴。

因此不要把「最小化 token」當成唯一目標。你真正要最大化的是工作品質乘上可用空間。若為了減少幾百個 token 而移除安全規則，代理可能產生更多返工、錯誤和人工監督，總成本反而上升。重置應該產生可工作的乾淨環境，而不是只產生最小數字。

### 遇到頑固膨脹時，採用逐項實驗

如果設定和技能移開後，基線仍然很大，不要一次改十個地方。一次只處理一個來源，重新啟動、再次測量並記錄結果。你才知道哪一項真正影響上下文，也能在功能缺失時快速恢復。

可疑來源可能在專案層級、使用者層級或外殼本身。它可能是自動載入的 MCP 連接器、內建工作流程、工具清單、產出功能或很長的系統提示。不同 harness 的存放位置與停用方法不同，因此不要把 Claude Code 的檔名當成通用命令。可移植的是方法：備份、建立乾淨起點、重新量測、根據差異定位來源，再決定保留、延後載入或停用。

逐項測試還能畫出自己的上下文地圖。你可能發現一個連接器佔用遠超過預期，一組技能雖然數量不多卻注入很長的說明，或一個看似方便的工具每輪都附加大量定義。這些資料比背誦 6.6k 或 23k 更有用，因為它們直接反映你的工作環境。

### 重置之後仍要承認：代理需要重新認識 repo

外殼乾淨不等於代理理解專案。重置只清掉背景負載，沒有自動提供程式碼架構、產品目的或團隊慣例。開啟 fresh session 後，代理通常知道平台、工作目錄、是否為 git repo、目前 branch 和最近 commit 等環境與版本控制中繼資料；它不會因為站在 repo 根目錄，就自動知道所有檔案。

所以重置後先讓代理探索，不要立刻叫它改功能。可以要求它判斷技術棧與預期用途，觀察它是否讀取 README、package.json 和關鍵目錄，再根據證據追問。這一步避免代理只憑資料夾名稱或最近 commit 猜測整個專案。乾淨上下文提供工作空間，卻不能替你建立專案地圖。

探索後仍然重要的理解應該寫入檔案系統。任務說明、設計決策、專案慣例、探索筆記和教學資產只要落盤，下次 session 就能重新讀取。清空上下文會丟掉對話中的暫時狀態，卻不會刪掉已保存的檔案。這讓檔案成為比模型臨時記憶更可靠的延續載體。

### 什麼時候選重置，什麼時候選其他方法

重置適合發生在工作入口，特別是要開始課程、進行可比較的實驗，或懷疑外殼在開工前已經背著大量無關內容時。它處理的是 session 建立之前載入了什麼。

如果問題是同一個 session 已累積大量讀檔、寫檔和討論歷史，就考慮壓縮。壓縮會保留一部分重要脈絡並濃縮後帶進新 session；重置不會保留目前對話的決策。如果只是長期引導檔案太長，應修剪重複、過時或沒有實際效果的規則。如果詳細資料庫程序只有特定任務需要，就把它放在文件中，固定設定只留下入口。

四者的邊界可以這樣記。重置處理外殼在開工前帶了什麼；壓縮處理會話已累積什麼；修剪處理長期引導寫了什麼；fresh session 探索處理代理重新開始後如何取得專案理解。方法可以配合，卻不能互相冒充。用清空對話解決預載膨脹，或用壓縮解決缺少專案地圖，都會讓問題反覆出現。

### 一個可重複的操作清單

把流程固定成幾個檢查點。第一，在沒有真實任務時查看 `/context`，記下基線與主要來源。第二，確認 `.claude/settings.json`、`.claude/skills` 或其他 harness 對應位置。第三，把需要暫停的內容改名為備份，不要刪除。第四，重啟外殼後再次測量。第五，逐項決定哪些內容取回、哪些留在備份、哪些改放成按需文件。第六，讓 fresh session 探索 repo，再開始實作。

每次都記錄四個問題：第一句任務前預載多少內容；最大的來源是設定、技能、工具還是整合；重置後回收多少空間；為了回收空間是否拿掉了安全規則或必要的專案知識。這四題能把上下文衛生從模糊焦慮變成工程檢查。

成熟的做法不是永遠使用同一個最小外殼，而是讓外殼與工作匹配。學習課程需要乾淨基線，資料庫任務需要資料庫規範，安全敏感的部署需要明確限制，日常小修正可能只需要少數通用工具。你可以保留多個可恢復配置，但每次啟動都應知道目前載入什麼，以及它為何值得佔用上下文。能回答這兩題，重置就會從緊急救火變成正常維護。
