# 注意力退化與 Smart Zone

## Learning goal

能從 token 關係數量推導 attention 退化，並判斷 agent 何時仍在 smart zone。

## Lesson

### 📝 先認出問題：agent 變鈍了

新的 agent session 往往很俐落。它能先讀對檔案、先驗證重要假設，也能記住哪些地方暫時不能動。你交給它一個需求，它不只會回答，還會順著目標探索、規劃、實作和驗證。

但同一個 session 使用久了，表現通常會慢慢改變。它未必突然忘光，也未必立刻產生荒謬答案。更常見的狀況是，它開始漏掉前面說過的限制，把太多時間花在枝節上，混淆不同檔案的角色，重做已經完成的搜尋，或只記住部分設計決定。它仍然會回覆，也仍然會呼叫工具，卻越來越抓不住目前真正重要的事。

這就是 [[learn/ai-coding-crash-course/elements/attention-smart-zone|注意力退化與 Smart Zone]] 要解釋的現象。表面上看起來像模型今天狀態不好、某次 prompt 寫得不夠好，或只是偶發幻覺。更深層的原因常常是 context 太長，長到 agent 維持高品質判斷的能力開始下降。

這裡的關鍵不在於模型有沒有「看見」資訊。它通常看見了。問題是，當內容堆成一大團時，它不再像 session 初期那樣容易抓穩資訊之間的關係。你可以把它想成一張桌子上堆滿文件的人，眼睛還睜著，卻已經很難快速分辨哪幾張文件和眼前任務最相關。

### 💡 Attention 為什麼會隨內容快速變難

先從最小情境開始。畫面上只有兩個 token 時，模型要處理的不是兩個互不相干的點。它還要判斷 token A 和 token B 的關係。token 增加之後，每一個新 token 都可能和其他內容形成新的關聯，所以工作量不是單純多一份內容。

這裡的 attention 可以先理解成模型分配關注、判斷 token 彼此相關程度的核心機制。它會協助模型決定哪些資訊應該互相連結，哪些部分對目前判斷比較重要。輸入短時，重要訊號比較容易被抓住；輸入變長時，需要維持的可能關係數量大致以平方級成長。

若有 n 個 token，關係空間可以用近似 n² 的直覺理解。課程中的兩個數字很值得記住。

| Token 數量 | 需要處理的關係量級 |
| --- | --- |
| 1k tokens | 約 1M 級別 |
| 100k tokens | 約 10B 級別 |

這些數字的重點不是要求你把每一條邊精確算出來，也不是說模型真的會像人一樣逐條列出十億個關係。重點是成長型態。token 從 1k 增加到 100k，內容量增加約一百倍，但可能需要維持的關係規模會推到極其龐大的量級。

為什麼這很重要？因為長 context 帶來的問題通常不只是反應變慢。attention 要在更大的範圍內分配關注，重要資訊更容易被稀釋，遠距離但關鍵的依賴更容易被雜訊蓋住，模型維持穩定判斷的難度就會快速上升。這種品質下降就叫 attention degradation，也就是注意力退化。

### ⚡️ 注意力退化是一段下坡，不是一面牆

注意力退化通常不是到了某個 token 數就突然報錯。它更像一條 slope，而不是一個 cliff。session 可能在很長一段時間裡看起來仍然能用，卻逐步變慢、變散、變得不可靠。

這種情況特別容易誤判，因為 agent 仍然能執行命令，仍然能產生通順的答案，有時甚至能給出看似合理的程式碼。如果你只問「它還能不能回答」，可能會得到一個樂觀答案。但真正該問的是「它現在還適不適合做高價值推理」。

一個很長的 session 也許仍適合做以下工作：

- 查一個局部問題
- 修改幾個明確的文字
- 執行一個命令並回報結果
- 讀一個小檔案
- 回答只依賴眼前訊息的問題

這不代表它仍適合跨檔案設計、長鏈除錯、需求對齊、風險判斷、code review 或高依賴的實作。agent 可能不是完全不知道答案，而是已經不能可靠地維持答案、前提、約束和證據之間的關係。

### 🔧 Smart Zone 與 Dumb Zone

Smart Zone 和 Dumb Zone 是描述工作狀態的兩個實用名稱，不是模型種類，也不是 provider 規格表上的欄位。

**Smart Zone** 指 agent 仍能承擔高品質工作的區域。在這裡，它對脈絡的掌握夠穩，能進行複雜的規劃、推理、探索、實作與驗證。你讓它理解需求、串起多個檔案、追蹤先前決策、比較方案，它通常還撐得住。

**Dumb Zone** 不表示模型突然完全沒用。它表示 agent 已經不適合承接高可靠性的複雜工作。它可能仍能完成局部、明確、低風險且不太依賴歷史脈絡的任務，但只要你要求它連結較長的脈絡，或穩定處理一串前提，失真機率就會提高。

兩個概念的差異可以這樣看：

| 概念 | 它回答的問題 | 實務含義 |
| --- | --- | --- |
| Context window | 最多可以塞多少 token | 超過後請求可能失敗 |
| Smart Zone | 在多少內容以前仍值得做困難工作 | 需要保守管理，不能只看容量 |
| Dumb Zone | 何時仍可做局部工作，但不該做複雜推理 | 應清理、壓縮、handoff 或重開 |

為什麼這個區分很重要？因為「能放進去」和「放進去後仍然聰明」是兩件事。

### 📦 1M context window 不等於安全工作區

許多模型宣稱擁有 1M token context window，甚至更高。這代表請求在技術上可以容納大量資料，直到超過限制才會失敗。這項能力本身不是假的，但它很容易造成錯誤推論：你以為既然可以放 1M tokens，就可以放心把 coding session 維持在接近 1M 的規模。

想像你買到一張非常大的桌子。桌面確實能攤開很多文件，但工作品質取決於你能不能在文件變多後，仍然快速找到目前需要的幾張。桌面再大，若注意力和檢索能力沒有等比例提升，文件堆滿後，判斷品質仍會下降。

對 coding agent 也一樣。1M 是容量規格，是一個醒目的 headline feature；它不是你應該安心長駐的工作區。實務上更需要一個 paranoia number，也就是讓你提早警覺、提早安排退出或交接的保守數字。

### 📏 約 150k tokens 是目前的 paranoia number

這門課提供的當前經驗值是，大約 150k tokens 可以當作進入 dumb zone 的警戒位置。這句話有三個限定，不能省略。

1. **大約**：不是到了某一個精確 token 就一定翻車。
2. **警戒位置**：不是硬上限。接近它時，應該開始懷疑 session 是否仍值得承擔高品質工作。
3. **當前經驗值**：不是永遠真理。以前可能更接近 100k 到 120k，現在推到 150k 左右，未來也可能隨模型進步而改變。

因此，150k 比較像交通標誌，不像混凝土牆。看到標誌時不代表 agent 立刻壞掉，而是代表路況開始變危險。若接下來要做細緻、複雜的操作，就不該再假裝自己仍在最舒服的工作環境裡。

即使警戒線未來往後移，管理思路仍然相同。你需要的是保守的工作邊界，不能把規格上限直接當成安全線。

### 🧭 從關係數量推回提早退出的理由

把整個推理鏈按順序寫出來，就能知道為什麼不應該硬撐同一個 session。

1. agent 每次向 model provider 發送 request，都會攜帶一整包 context。
2. context 越長，包含的 token 越多。
3. token 越多，attention 需要處理的可能關係數量近似平方成長。
4. 關係數量暴增後，重要資訊更容易被稀釋，真正相關的部分更難被穩定抓住。
5. 品質下降之後，你可能要重做更多工作，也會繼續為低品質輸出支付 token 成本。

所以 session 變長時，不能只看「這次多花了幾萬 token」。還要看關係空間被撐大多少，以及你是否把複雜工作交給一個已經開始退化的工作區。真正昂貴的情況是，花更多錢取得更差的判斷，最後還要返工。

### 👀 進入 Dumb Zone 後，哪些症狀會先出現

你看不見 attention 內部如何運作，但通常看得見它退化後的結果。常見症狀有四類。

1. **優先順序感變差**
   
   agent 分不清主線與枝節。你要求先釐清需求，它先急著改碼；你要求先看測試，它先做格式化。它可能聽懂字面指令，卻抓不住整體判斷重心。

2. **跨段依賴接不穩**
   
   你前面說某檔案不能動、某 API 不能破壞，或某個假設已被推翻，後面它仍可能重新踩回去。這不只是忘記一句話，而是抓不穩多段資訊之間的約束關係。

3. **重複探索**
   
   它反覆搜尋已經搜尋過的內容，重問已經釐清的問題，重查已確認的檔案。這代表它無法有效保留已經收斂的問題空間。

4. **答案看似合理，卻脫離現場**
   
   它的說法可能通順且有自信，但與目前 repo、這次任務和 session 裡已建立的事實不一致。若把這種症狀當成偶爾胡扯，就容易錯過真正的病因。

### 🧩 Smart Zone 也取決於任務型態

150k 是好用的 paranoia number，但不能把 Smart Zone 變成只看 token 的死板公式。同樣的 context 規模，對不同任務的風險並不相同。

高耦合、高依賴、多步驟的工作需要更保守，例如：

- 先釐清需求，再拆設計，修改多個檔案，最後驗證回歸風險
- 追蹤跨模組 bug，同時保留多條證據鏈
- 做 code review，同時記住 PR 目標、既有約束、測試結果和細節差異

這類任務高度依賴 agent 維持遠距離關係。即使只有 120k tokens，也可能已經偏危險。

相反地，局部、低風險的工作比較不依賴長脈絡，例如改寫一段文字、補上明顯缺漏，或執行一個命令並回報結果。這時較大的 context 不一定立刻造成問題。

因此判斷是否仍在 Smart Zone，至少要同時問兩件事：目前 token 規模大概在哪裡？接下來的任務需要多強的跨脈絡推理？Dumb Zone 的意思是「不適合困難工作」，不是「完全不能使用」。

### 💰 成本為什麼和 Smart Zone 綁在一起

注意力退化與成本問題其實是同一個 session 管理問題的兩面。context 變大時，attention 負擔增加；同時，每次 request 也要攜帶更多 input tokens。你每次繼續對話、每次叫 agent 執行工具，都不是從零開始，而是帶著累積至今的 session 一起送出。

因此，長 session 會同時造成兩種惡化。

| 惡化方向 | 發生什麼事 |
| --- | --- |
| 品質惡化 | 重要訊號更難被穩定抓住，跨段關係更容易失真 |
| 成本惡化 | 每次 request 都攜帶更大內容，持續為歷史沉積物付費 |

為什麼這很重要？你整理 session 不只是為了節省幾個 token，而是避免花更多錢買到更差的判斷。若 session 已經離開 Smart Zone，再追加 prompt 有時只會把更多 token 塞進一個正在退化的工作區。

### ✅ 五個問題，幫你判斷是否該退出

實際工作中，可以用下面五個問題快速檢查。

1. **它還能維持主線嗎？** 先前定義的目標、限制和下一步，後續是否仍被穩定抓住？
2. **它還能連對關係嗎？** 它是否知道某個需求為什麼導致某個測試必須通過，某個檔案為什麼不能那樣改，以及某個 workaround 為什麼已被淘汰？
3. **它是否反覆走回頭路？** 重複探索、重複確認通常表示它對現場的壓縮掌握正在變差。
4. **接下來是否需要高強度推理？** 如果需要，就不該在已經可疑的 context 上賭一把。
5. **token 是否接近約 150k？** 這不是唯一判準，但它是一條很實用的保守界線。

如果主線、關係掌握和探索效率都穩定，通常仍在 Smart Zone。若 token 接近警戒線，同時出現主線感下降、重複探索增加或答案脫離現場，就應把它視為準備退出的訊號。

### 🚪 真正成熟的做法，是主動保住 Smart Zone

很多人不願意重開 session，因為已經投入不少時間，覺得重新交代很浪費，也相信再補一句 prompt 或許能把 agent 救回來。偶爾這樣做沒有問題，但如果根本原因是 attention degradation，繼續說更多話常常只會增加沉積物。

比較成熟的做法，是把 Smart Zone 當成需要保護的工作資產。

- session 還清爽時，用來探索、對齊、設計和進行困難實作。
- session 接近警戒線時，開始整理必要狀態。
- 把狀態濃縮、交接、重建，或直接重開新的工作區。
- 不要把所有歷史都拖進下一個高價值推理任務。

這不是拋棄 context，而是保住真正有價值的 context 密度。workflow 的問題也因此從「能不能讓同一個 session 活得更久」改成「能不能讓最困難的工作總是在 Smart Zone 裡完成」。前者容易變成戀棧，後者才是工程上的優化。

### 🎯 最後記住一條可以自己推回來的鏈

整課可以先濃縮成一句話：context 越長，attention 越難維持，agent 品質會慢慢下降；高品質工作應盡量留在 Smart Zone。

但真正值得帶走的是推理鏈，而不是口號。當有人拿 1M context window 當成品質保證時，你要知道容量不等於安全工作區。當你需要解釋長 context 為什麼會讓 agent 退化時，你要能從 token 關係數量近似平方成長開始推導。當專案做到一半，你要決定是否換 session 時，則可以把約 150k tokens 的 paranoia number、任務型態和實際症狀放在一起判斷。

只要這條鏈還清楚，你就不會把問題誤解成神秘的模型脾氣。你會知道，長 session 帶來的是可預期的工作區退化；對策也不是盲目重試，而是管理 context、保住 Smart Zone，讓 agent 在最需要高品質判斷的時候仍然可靠。
