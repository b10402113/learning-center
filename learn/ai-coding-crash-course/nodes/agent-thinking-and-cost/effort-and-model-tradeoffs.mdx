# Effort 旋鈕、Reasoning Tokens 與模型選擇

## Learning goal

學完這一步，你能根據任務在品質、延遲、成本與 smart zone 之間做選擇，知道何時應該調高或調低 [[learn/ai-coding-crash-course/elements/effort-reasoning|Effort、Reasoning Tokens 與 Chain-of-Thought]]，也能把 [[learn/ai-coding-crash-course/elements/attention-smart-zone|注意力與 Smart Zone]] 當成實際邊界，為自己的工作流設計簡單、可重複的模型與 effort A/B 測試。

## Lesson

### 📝 先看一個常見現象：同一個任務，結果為什麼差這麼多

你把同一類問題交給代理，可能得到兩種完全不同的結果。第一次，它十幾秒內就回覆，答案看起來可以交差，卻漏掉邊界條件，也沒有核對文件和實作的差異。第二次，它等得比較久，消耗更多 token，最後卻找出過時文件、分支行為，甚至指出命名和實際路徑不一致。

這不一定代表模型今天突然變聰明或變笨。更常見的原因，是兩個變因一起改變了：

1. **模型本身**，也就是負責推理與使用工具的模型。
2. **Effort**，也就是這次請求允許模型投入多少推理資源。

同一個模型，在低 effort 和高 effort 下，可能像兩位工作方式完全不同的同事。低 effort 傾向快速建立一個足以回答的結論，高 effort 則更願意展開檢查、比較與驗證。但 effort 絕對不是「越高越好」的單一品質開關。它同時影響四件事：品質、延遲、成本，以及這個 session 還剩多少上下文空間。

**為什麼先看這四個結果很重要？** 因為你真正要設計的是工作流，而不是追求永遠最強的設定。一次任務多花的計算，可能換來更好的答案，也可能讓後面的回合變慢、變貴、變得更容易失去重點。

### 💡 Effort 到底調整了什麼

第一次遇到 effort，可以先把它想成「模型願意在答案前多走幾步」的設定。低 effort 時，模型可能只讀取最直接相關的檔案，快速整理出一個看似合理的方向。高 effort 時，它可能追更多呼叫鏈、對照更多證據、檢查更多例外，才決定最後怎麼回答。

因此，當代理回得很快但內容很表面，原因可能是低 effort，而不一定是模型本身能力不足。當代理想得更久、工具呼叫更細、輸出內容更多，也不一定代表換了模型，可能只是 effort 提高了。

這個設定在短任務裡未必很明顯。改一個變數名、查一個局部 API、補一個容易判斷的測試，低到中等 effort 通常已經足夠。可是，若任務包含探索 repo、讀檔、比對規格、拆解需求、實作，再回頭執行測試，高 effort 的額外推理就會一起留在上下文裡。你可能因此得到更好的第一輪答案，卻讓第二輪和第三輪更快變鈍。

所以每次調整 effort，都應該問兩個問題：

- 這次多花的推理，會不會降低當前回合犯錯的機率？
- 這些額外內容，會不會讓後續工作更容易離開 [[learn/ai-coding-crash-course/elements/attention-smart-zone|注意力與 Smart Zone]]？

### 🔧 Reasoning Tokens：看不見的推理預算

Reasoning tokens 是模型在產生正式回答前，額外使用的推理 token。它們不等於你最後看到的文字，而比較像模型在內部走過的中間步驟。有些產品會把這些步驟顯示出來，有些產品會隱藏它們；即使你看不到，相關的計算成本與等待時間通常仍然存在。

它和 chain-of-thought 有關。Chain-of-thought 可以理解成「把中間推理步驟串起來」，讓模型不要一看到問題就直接跳到結論。它的價值不在於讓答案變長，而在於把複雜問題拆成幾個可以逐一檢查的部分。

用小學生的多步驟算術題來看最容易理解。若模型只被要求直接寫出答案，它可能跳過某個條件，或在中間計算出錯。若它有足夠空間先整理已知資訊、逐步計算，再輸出答案，正確率通常會提高。程式設計也一樣。以下任務常常值得更多 reasoning tokens：

- 跨檔案追蹤一條資料或呼叫鏈。
- 比較規格、文件與目前實作。
- 找出容易被忽略的邊界條件。
- 把模糊需求整理成可執行的方案。
- 審查 diff，判斷是否有競態、相容性或回歸風險。

因此，[[learn/ai-coding-crash-course/elements/effort-reasoning|Effort、Reasoning Tokens 與 Chain-of-Thought]] 控制的不是「回答要不要變長」，而是模型能不能保留足夠的中間推理，分辨那些表面相似、實際卻不同的可能路徑。

### ⚡️ 高 effort 為什麼常常真的比較好

假設你要代理判斷文件是否已經和程式碼脫節。低 effort 可能只看文件，再快速掃過一兩個相關檔案，最後回答「大致一致」。高 effort 則更可能追蹤實際資料流，對照多個檔案，確認測試與文件是否描述同一種行為，並列出矛盾的位置。

高 effort 的價值來自多做幾次推理與驗證。它把容易被一句話壓平的差異重新攤開來。對複雜工程任務而言，這些差異往往決定成敗：

- 實作功能時，既有測試可能藏著規格沒有寫出的前提。
- Code review 時，表面乾淨的 diff 可能仍然有競態條件。
- 規劃改動時，文件描述的資料流可能和實際分支已經不同。

如果任務的主要風險是「漏看」或「誤判」，提高 effort 通常是合理投資。你花費更多 token，換來的是更高機率在實作前發現深層錯誤。

但這並不代表高 effort 會讓所有答案都同樣進步。提升通常不是線性的。從太低調到中等，常常很有價值；從中等調到符合任務的高，也可能值得。再繼續推到極高，卻可能只增加少量品質，卻大幅增加成本和延遲。有些供應商提供 high 或 max 類設定，目的可能是替 benchmark 再擠出幾個百分點，未必是日常工程最划算的預設。

**為什麼 benchmark 上的進步不能直接當成工作流收益？** 因為日常 codebase 不是乾淨的測試集。它有過時文件、模糊需求、工具延遲、權限問題、測試慣例和團隊歷史包袱。排行榜上多 3% 的模型，不一定值得你在每個任務上付出 2 倍成本。真正該看的，是每一單位成本能換來多少有效進展。

### 📊 高 effort 的三項代價

高 effort 不是免費的品質增幅器。至少有三種成本需要一起計算：

| 代價 | 實際影響 |
| --- | --- |
| 成本 | 推理 tokens 增加，單次請求的費用上升 |
| 延遲 | 模型花更多時間探索、比較與驗證，等待變長 |
| 上下文壓力 | 更多中間產物留在 session，後續注意力更容易分散 |

第三項最容易被忽略。你不只是在買一次更好的答案，也在消耗工作桌上的空間。高 effort 可能讓當前回合更可靠，但它同時會讓整個 session 更接近 dumb zone。

### 🧠 Smart Zone：高 effort 可能把未來的聰明空間吃掉

可以把代理的上下文想成一張工作桌。低 effort 像是帶回一小疊必要草稿，高 effort 則像帶回完整推導、旁註、比較表和更多中間結果。桌面還寬裕時，代理能抓住真正重要的資訊，這是 smart zone。桌面逐漸堆滿後，它也許仍然看得到所有資料，卻更難穩定判斷哪些內容最重要，這就是滑向 dumb zone。

這個比喻不是說高 effort 一定會立即害你，而是提醒你區分兩種尺度：

- **單回合尺度**：高 effort 可能提高當前任務的推理深度。
- **整個 session 尺度**：高 effort 可能提前消耗後續回合的注意力餘裕。

如果是一次性、高風險的深度審查，這個交換可能值得。若是需要長時間、多輪工具呼叫的任務，則要保留上下文空間。當 session 已經很重時，繼續原地提高 effort，可能只是把問題往後延。先清理上下文、重開 session，或把深度工作拆到另一個 session，常常更有效。

**為什麼 Smart Zone 很重要？** 因為模型的能力不是只由單次回答決定。你要的是一段工作流程持續保持清楚，而不是第一輪很精彩、後面每一輪都在補救。

### 🔍 模型選擇其實是工作系統設計

理解 effort 之後，下一個問題通常是「到底該選哪個模型？」這個問題看起來像排行榜比較，實際上是在問你的工作環境能讓哪種模型最容易成功。

一個實用的判斷是：模型只負責成功的一部分，另一部分來自 harness 與環境。Harness 可以理解成代理使用的外殼與工作設施，包括：

- 檔案導航和上下文整理方式。
- 可使用的工具與權限。
- 測試、lint 和驗證命令。
- 文件品質與是否能把理解落盤。
- 何時繼續使用同一個 session，何時重開。

模型就像一位能力很強的工程師。如果公司的流程混亂、知識分散、權限不足、工具壞掉、文件過時，這位工程師仍然會被環境拖慢。相反地，整理好的工作環境能讓不同模型都比較容易發揮。這個視角能避免一個常見誤區：以為只要換一個更強的模型，所有工作流問題就會自動消失。

所以模型選擇不要從「哪個最強」開始，而應該從「我的系統讓哪個模型最容易交付可靠結果」開始。

### 💰 比較效率，不要只看 token 單價

只看每個 token 的價格，或只看一次任務用了多少 token，都可能得到錯誤結論。真正需要比較的是效率，也就是每單位成本換來多少可採用的產出。

某個模型可能每個 token 比較便宜，但常常講很多、走很多不必要的步驟；另一個模型單價較高，卻能更快收斂到正確方向。第一個模型的單次 token 數看起來很大，總帳單卻可能仍然較低。反過來，一個看似節省 token 的模型若常漏掉關鍵細節，就會迫使你反覆補 prompt、重新解釋、回頭修錯，最後的人機總工時反而更高。

比較模型時，至少記住三個問題：

1. 它在你常見任務上的成功率如何？
2. 達成可採用結果時，需要多少回合和多少總 token？
3. 它失敗時通常怎麼失敗，是太淺、太慢、太固執，還是很容易進入 dumb zone？

這三個答案合起來，才是模型真正的效率輪廓。工程工作的成本不只在帳單，也在錯誤方向消耗的人與機器時間。

### 🧭 不同任務，使用不同 effort 與模型

所有任務都套用同一個重裝設定，通常會同時帶來速度慢、成本高和 session 提早飽和。任務類型不同，合理的 effort 也不同。

| 任務類型 | 常見例子 | 通常的起點 | 判斷重點 |
| --- | --- | --- | --- |
| 探索 | 掃描 repo、摘要文件、找設定位置 | 低到中等 effort | 目標是建立地圖，速度、成本和可平行性較重要 |
| 規劃 | 拆 tickets、比較方案、評估風險 | 中等到偏高 effort | 是否能找出依賴、文實不一致與後續風險 |
| Review | 審查 diff、找競態與回歸問題 | 偏高 effort | 價值在於看見不容易看見的錯誤，而非產生摘要 |
| 實作 | 修改局部功能或跨模組功能 | 穩定中等，必要時提高 | 先判斷難點在寫程式，還是在理解程式 |

實作型任務尤其需要分辨範圍。規格清楚、改動局部、測試路徑明確時，中等 effort 通常足夠。若牽涉跨模組協調，或需要先確認許多隱含前提，再調高 effort。關鍵不是「實作永遠開高」，而是先找出真正的風險來源。

### ⚖️ 一致的基線，常常比每題最優更有用

進階使用者可能會做 per-task min-maxing，也就是每個任務都重新精算一次：探索用模型 A 的低 effort，規劃換模型 B 的高 effort，實作用模型 C，review 再切到模型 D。理論上，這可能找到局部最優；實務上，頻繁切換也會讓你把注意力花在配置，而不是工作本身。

如果你還在建立工作流，一個更穩的起點是：先選一個整體表現夠好、你熟悉其性格的主力模型，再配一個能接受的預設 effort，例如中等。持續使用這個組合，你才會知道它在哪些任務穩定、在哪些地方會漏細節、何時開始變慢，以及什麼情況下會讓 session 變重。

有了穩定基線，結果不好時才容易定位原因。你可以分辨問題究竟來自 prompt、環境、上下文、任務拆分，還是 effort，而不會每次都猜測是不是因為模型又換了。對學習者而言，先建立可預期的操作手感，通常比追求每一次理論最優更重要。

### 🔄 什麼時候調 effort，什麼時候換模型

Effort 和換模型解決的問題不一樣。若模型的失敗型態是太快收斂、略過證據、推理不夠深，先調高 effort 往往有效。你要補的是推理深度。

若模型始終抓不住你的程式碼風格，工具使用方式不順，經常誤解某種工作模式，或在某類任務上反覆表現不佳，問題可能是模型的傾向。這時候，讓同一模型多想一點未必能解決，應該考慮換一個性格或能力輪廓更合適的模型。

可以用「失敗是否重複」作為簡單判斷：

- 同一模型在不同任務中反覆規劃很強、落地很飄，這比較像模型輪廓。
- 只有某一次任務回答得太淺，可能是 effort 不足，或背景資料尚未準備好。

一句話總結就是：effort 比較常解決深度問題，換模型比較常解決傾向問題。

### 📈 Benchmark 只能篩選，不能替你選型

Benchmark 有用，因為它能提供相對方向，幫你先縮小候選集合，看看哪些模型大致位在品質和成本都具競爭力的區域。但 benchmark 很容易和你的實際工作脫節。你的 codebase 有自己的文件債、產品語境、測試習慣和歷史包袱，任務分布也通常和公開測試集不同。

成熟的做法不是全信 benchmark，也不是完全不看。先用它做初步篩選，再回到自己的 codebase 做實驗。排行榜可以告訴你從哪裡開始比較，卻不能代替最後的實際選型。

### 🧪 用簡單 A/B 測試建立自己的答案

最可靠的模型選擇，通常來自同一類真實任務的幾次簡單 A/B 測試。這不需要論文等級的實驗，但不能只靠一次印象。

可以選一個你確實會重複做的任務，例如：

- 閱讀規格後提出實作計畫。
- 對同一組 diff 做 review。
- 在陌生 repo 中找出 bug 的可能成因。
- 根據文件與程式碼找出不一致。

接著固定大部分條件，只改一個變因。你可以比較同一模型的 low effort 和 medium effort，也可以在相同 effort 下比較兩個模型。不要同時改模型、prompt、工具權限和輸入檔案，否則最後無法知道差異來自哪裡。

每次至少記錄四個結果：

1. **品質**：是否抓到真正重要的問題，是否有證據，結果能否直接採用。
2. **延遲**：從送出請求到拿到可用答案花了多久。
3. **成本**：記 token 或實際帳單即可，但每次使用同一種口徑。
4. **Smart Zone 壓力**：這輪之後，session 是否明顯變重，後續互動是否開始變鈍。

如果要更精準，再加上第五項「修正成本」。也就是答案距離真正可採用的狀態還有多遠，需要補多少 prompt、多少來回。有些模型第一眼看起來不錯，卻需要大量雕刻；另一些模型第一輪就更接近可交付結果。

### 🧾 一個夠用的 A/B 模板

你可以用下面的流程開始：

1. 寫下任務類型，例如「閱讀規格後產出實作計畫」或「review 一個中型 diff」。
2. 寫下固定條件，包括同一個 repo、同一組輸入檔案、相同工具和相同成功標準。
3. 只選一個變因，例如 low 對 medium effort，或模型 A 對模型 B。
4. 用 1 到 5 分快速記錄品質、延遲、成本、上下文壓力和修正成本。
5. 重複三到五次，再看整體輪廓，不要用單次結果下結論。

做完三到五次後，你通常會看出一些穩定模式。某個模型可能在規劃上一直比較穩，但實作沒有優勢。Low effort 可能已經完全足夠應付探索，medium 只是多花資源。High effort 可能確實在 review 找到更多問題，卻每次都把 session 壓得太重，因此更適合獨立開新 session 做一次性深審，而不適合放進長鏈路主流程。

這類測試最重要的產出不是公共排名，而是自己的操作地圖。你會從「聽說這個模型很強」進一步知道「它在我的工作裡什麼時候強、什麼時候弱、代價是多少」。

### ✅ 把決策接回每天的工作流

新任務進來時，可以先問四個問題：

1. 失敗的主要代價是什麼，是漏掉細節，還是等待太久？
2. 這是一次性深度思考，還是長鏈路、多輪互動？
3. 它比較像探索、規劃、實作，還是 review？
4. 目前 session 還在 smart zone，還是已經接近飽和？

若任務一次性、高風險，而且主要代價是漏掉細節，較高 effort 通常合理。若任務是長鏈路探索，低到中等 effort 往往更健康，因為你需要留下上下文餘裕。若 session 已經很重，即使任務重要，也不一定要在原地把 effort 開到最高。清理、重開，或把深度工作移到另一個 session，可能比繼續堆內容更可靠。

模型決策也遵循同一原則。先用穩定的主力模型當基線。只有當你反覆觀察到某類任務始終失手，才值得換模型。其他情況下，先改善環境、澄清任務、整理上下文或調整 effort，通常更划算。

### 🎯 最後的目標：駕馭取捨，而不是崇拜最強模型

成熟的 AI coding 使用者，不會把模型選擇當成永遠追逐第一名的競賽。他會先看工作條件：今天是在快速建立地圖、深挖風險、評論 diff，還是穩定搬運一個明確改動？他知道哪些任務值得投入 reasoning tokens，哪些任務只需要便宜、快速的探索；也知道高 effort 可能提高當前成功率，卻同時增加延遲、成本，並更快侵蝕 smart zone。

更重要的是，他不會把模型當成唯一答案。模型當然重要，但 harness、工具、權限、文件、測試和上下文管理，常常決定模型能不能把能力轉成成果。當你把 effort 和模型都當成可控制、可測量的變數，就能依任務選擇深度，依 session 狀態保護注意力，依真實結果做小型 A/B 測試。

你最後建立的會是一套可重複的選擇法：低 effort 先探索，中等 effort 維持日常工作，高 effort 用在真正需要深挖的規劃或 review；先保留一個穩定模型作為基線，再根據重複出現的失敗型態決定是否換模型。這比盲目追求最強設定更穩，也更接近把代理用成可以長期合作的工程夥伴。
