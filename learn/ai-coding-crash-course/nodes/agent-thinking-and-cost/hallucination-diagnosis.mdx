# 兩種幻覺與診斷決策樹

## Learning goal

能用 factuality/faithfulness decision tree 找出幻覺來源並採取正確修復。

## Lesson

### 📝 先把問題問對：不是「有沒有幻覺」，而是「錯在哪一層」

你在用 AI coding agent 時，最常見也最惱人的失敗之一，就是它用很穩的語氣給你一個錯的答案。它可能告訴你某個第三方 API 的價格，可能說某個 framework 在最新版本該怎麼寫，也可能很自信地解讀你專案裡的限制，最後卻和真實情況不一致。表面上看，這些都可以統稱成 hallucination，也就是幻覺。但如果你只停在這個層次，後面幾乎一定會修錯。

真正有用的做法，是把幻覺拆成兩種不同故障。第一種是它不知道真實世界現在是什麼樣子，卻還是硬回答。第二種是你其實已經把正確資料放到它眼前，它卻沒有照著資料走。這兩種錯看起來很像，修法卻剛好相反。一個要補資訊，一個要減資訊。這也是這篇要你真正掌握的能力：用 [[learn/ai-coding-crash-course/elements/hallucination-diagnosis|Factuality 與 Faithfulness 幻覺]] 這個框架，把模糊的抱怨變成可執行的判斷。

**為什麼這樣分很重要？**
因為如果你分錯型，後面的每一步都在浪費時間。它缺資料時，你一直重試 prompt 沒用。它明明有資料時，你再塞更多資料，反而會讓注意力更亂。你不是在解決問題，而是在把 session 往更難救的方向推。

### 💡 代理為什麼會「說得像真的」

先建立一個很重要的直覺：回答的流暢度，不等於答案的正確度。AI agent 的工作不是像研究員那樣停下來檢查每個主張的證據，而是持續產生下一串最合理的 tokens。這代表只要一條敘事在語言上成立，它就能講得很完整、很順、很像一回事。

這也是為什麼幻覺通常不是那種一眼就能看穿的胡言亂語。更常見的是半對半錯、舊知識冒充新知識，或把幾個真實片段拼成一個現在已經不成立的結論。像是價格頁曾經存在，某個 CLI flag 曾經可用，某個 SDK 寫法曾經正確，某個政策曾經那樣規定。模型不是完全虛構，而是把過去壓縮過的印象拿來補現在的空缺。

在 coding 工作裡，這特別危險，因為很多高風險資訊都會變。價格會變，版本會變，雲端權限會變，文件會變，SDK 行為會變，部署限制也會變。所以你不能因為代理聽起來像資深工程師，就把它的回答當成已查證的事實。這一點很殘酷，但非常實用。

### 🔧 第一種幻覺：factuality

先看第一類。factuality hallucination，可以先用白話記成「世界事實本身答錯了」。更精確地說，是代理說了一個錯的事實，而支撐正確答案的資訊，當時根本不在它的 context 裡。

這種情況下，代理通常是依靠 parametric knowledge，也就是模型參數裡壓縮過的知識。這份知識不是沒價值。沒有它，模型不可能懂一般語法、常見工具、常識結構，也沒辦法和你對談。但它不是可即時更新的資料庫，而是訓練後留在模型裡的一種壓縮記憶。

課程裡用了一個很好記的比喻：parametric knowledge 像 fuzzy JPEG。你把世界資訊高度壓縮，輪廓還在，細節卻會糊掉。模型可能知道某個產品有 tier、某個 API 有收費、某個 framework 改過 routing、某個平台有 rate limit，但它不保證知道今天的價格、最新的命名、最近廢棄的參數，或本週剛更新的限制。

再加上一個現實：knowledge cutoff。模型的訓練資料有時間截點，截點之後的新事實不會自動長進去。所以只要問題牽涉外部世界，而且答案是會隨時間改變的，你就要立刻提高警覺。

**factuality 的典型特徵有三個：**

- 問題在問外部世界的狀態，而不是你專案裡已提供的材料
- 代理沒有引用目前 session 裡實際存在的依據
- 一旦你補進權威來源，答案很快就會改正

這一類錯，不是靠代理「多想一下」就能修好，因為它一開始缺的不是推理深度，而是原始事實。

### ⚡️ 第二種幻覺：faithfulness

第二類叫 faithfulness hallucination，可以先記成「不忠實於手上已有的資料」。也就是說，正確資訊明明已經在 context 裡，代理卻沒有依照那些資訊回答、判斷或修改。

這種情況往往更令人火大，因為你會有很強的委屈感。你明明給了 spec、貼了錯誤訊息、讀了 schema、跑了測試，甚至才剛剛糾正過它，它還是沿用舊假設，或抓錯上下文裡真正重要的點。

faithfulness 問題的關鍵不是「它知不知道世界」，而是「它有沒有忠實使用眼前資料」。這和 [[learn/ai-coding-crash-course/elements/attention-smart-zone|注意力退化與 Smart Zone]] 直接連在一起。context 不是只要放進去就會被正確利用。對話太長、工具輸出太多、不同階段的資訊混在一起、無關歷史沉積太厚，都可能讓模型雖然理論上看得到資料，實際上卻沒有把資料放在正確權重上。

這就是很多人會掉進的陷阱：明明是 faithfulness 問題，卻直覺用 factuality 的修法，也就是再塞更多背景。結果上下文更大、更雜、更難聚焦，忠實度反而更差。你以為自己在幫忙，實際上是在把代理推進 dumb zone。

### 🧭 一棵真正能用的 decision tree

遇到疑似幻覺時，不要先問「它是不是又亂掰」。先走一棵簡單但非常實用的 decision tree。核心只問一件事：正確答案依賴的那份資訊，在不在當時的 context 裡？

你可以照下面四步走。

#### 1. 先把錯誤主張說成一句可檢查的句子

不要只說「這次答得怪怪的」。你要把問題落成可以核對的命題。

例如：

- 它說 X/Twitter API 的 basic plan 價格是多少
- 它說某個 framework 在最新版本要用某個 flag
- 它說這個 repo 用的是 Prisma，但實際 schema 並不是
- 它說未登入使用者可以看到留言，但需求明明限制只有 enrolled users

當你能把錯誤說成一句可驗證的話，診斷才開始有抓手。

#### 2. 檢查正確資訊是否真的進過 context

這一步是整棵樹的核心。請注意，不是檢查「你以為你有提過」，而是檢查模型在當下真的看得到什麼。

context 可能包括：

- 目前對話中的明確說明
- 你貼進去的文件片段
- 工具讀出的檔案內容
- 搜尋結果
- 命令輸出
- repo 裡實際被打開、讀入、提供給它的權威材料

如果正確資訊根本沒進來，代理就不可能忠實使用。這時候別急著批評它沒有遵循資料，因為資料根本不在桌上。

#### 3. 不在 context：判為 factuality

如果你檢查後發現正確資訊不在 context，先判成 factuality 問題。這表示模型是在資訊缺席的情況下，靠 parametric knowledge 補洞。

對應修法很直接：

- 補官方文件
- 做 web search
- 讀實際 repo 檔案
- 跑命令拿真實輸出
- 查看版本、測試、設定、migration

重點不是換一種說法重問，而是改變它手上可用的證據。

#### 4. 在 context：判為 faithfulness

如果正確資訊確實已在 context 裡，卻還是答錯，那就先判成 faithfulness 問題。這表示資料不是沒有，而是沒有被忠實使用。

這時優先修法通常不是補更多，而是：

- 清理上下文
- 開新 session
- 把重要限制壓成高密度摘要
- 拆開探索、設計、實作、QA 各個階段
- 把關鍵約束前置到新的上下文開頭

這棵樹之所以有用，不是因為它複雜，而是因為它把「LLM 又出錯了」拆成兩條完全不同的修復路徑。你不再只是生氣，而是知道下一步應該動哪個槓桿。

### 📌 用 X/Twitter API 價格例子走一次

課程裡有一個非常代表性的例子：問代理 X/Twitter API 的價格。這題之所以好，是因為它同時具備兩個高風險特性。第一，它問的是外部世界。第二，它問的是高變動資訊。這種題目如果沒有來源，幾乎就是 factuality 幻覺最容易發生的地方。

代理在沒有最新來源的情況下，還是可能給你一個很像真的答案。它也許記得 X/Twitter API 確實有不同方案，記得某些方案名稱，甚至記得歷史上的一組價格。但只要 pricing page 已經更新，或收費結構改過，它就可能把過去壓縮在參數裡的印象，誤當成現在的事實。

接著只要你做一次 web search，或把最新官方頁面帶進 context，錯誤通常就會立刻暴露。這說明了什麼？不是模型忽然變笨，而是你讓它回答一個本來就應該由來源支撐的問題，卻沒有先提供來源。

**為什麼這個例子重要？**
因為它可以抽象成一條非常實用的規則：對外部世界且高變動的資訊，never trust an unsourced LLM。沒有來源的回答，最多是草稿，不是證據。

### 🧱 為什麼「我已經給資料了」不代表安全

很多人學到 factuality 之後，會自然得到一個過度簡化的結論：那我只要多餵資料就好了。這個想法只對了一半。因為它完全忽略了 faithfulness 這一面。

在真實的 coding workflow 裡，最容易崩掉的往往不是資料太少，而是資料太多、太亂、太舊、太混。你可能先跟代理討論需求，再讀一堆檔案，接著跑測試、看 log、查文件、寫 spec，最後才進入實作。等到要它動手改 code 時，整個 session 可能已經混了探索、辯論、被推翻的假設、過期的方向、冗長的輸出和真正重要的限制。

這時即使正確資訊還在 context 裡，也不代表代理會用得好。它可能抓住半小時前的舊結論，忽略剛剛才更新的需求，也可能把早先的一段猜測當成最終事實。你如果看到這種情況，第一反應又是「那我再貼一次」「我再多補一段背景」，通常只會讓問題更糟。

**為什麼這樣很危險？**
因為 faithfulness 問題的本質不是缺資料，而是注意力分配失衡。當上下文密度太低、沉積物太多，重要資訊雖然存在，卻不再位於模型真正會優先使用的位置。

### 🔍 factuality 的修法：補進權威證據

如果你判定問題是 factuality，修法應該非常果斷。不要再讓模型靠模糊記憶回答，而是把權威資料帶進來。

#### 常見做法一：直接讀官方文件

只要問題涉及版本、API、CLI、SDK、價格、權限、政策、部署限制，最穩的做法就是把對應文件帶進 context。這等於把問題從「你記不記得」改成「請根據眼前文件回答」。

#### 常見做法二：讓工具去拿最新事實

在 agent 工作流裡，這通常包括：

- web search
- repo search
- 讀設定檔
- 執行命令
- 跑測試
- 看 migration
- 看 package manifest

只要真實輸出被帶回 context，模型就不必只靠舊知識猜。

#### 常見做法三：要求答案綁定依據

你可以要求代理說清楚，這個結論來自哪個檔案、哪個命令、哪段文件、哪個錯誤輸出。這不是形式上的龜毛，而是把無來源的猜測變成有依據的陳述。

#### 常見做法四：接受有些問題本來就該重查

不要因為模型平常很會講 Node、TypeScript、Git，就推論它對每個 SaaS 產品的本週收費或某個平台今天的限制也一樣可靠。世界知識和當前 repo 內知識，本來就不是同一種東西。

你可以把 factuality 的修法記成一句話：補證據。資料不在 context 時，任何重試都只是讓模型換一種方式猜而已。

### 🧹 faithfulness 的修法：整理 context，不是繼續堆 context

如果判定是 faithfulness，修法就完全不同。這時候資料已經存在，問題在於上下文品質和注意力結構。

#### 做法一：清掉沉積物，必要時直接開新 session

很多人不願意這樣做，因為會覺得前面聊那麼多很可惜。但如果 session 已經把代理拖出 smart zone，繼續帶著它走只會越來越差。保留所有歷史，換來的是持續偏航，通常不值得。

#### 做法二：把重要內容壓縮成高密度摘要

不要原封不動搬整段舊對話到新 session。你真正需要的是：

- 已確認的需求
- 不能違反的限制
- 目前觀察到的事實
- 還沒解決的問題
- 明確被否決的方向

少量但高密度的正確 token，通常比大量但混雜的歷史更有效。

#### 做法三：把階段切開

探索、設計、實作、QA 關心的資訊不同。把所有階段塞在同一段長上下文裡，代理就要同時面對太多彼此競爭的訊號。分階段開 session，常常比單純把 context window 拉大更有用。

#### 做法四：把關鍵約束前置

有些限制一旦違反，整個任務就歪掉。像是：

- 只有 enrolled users 可以看到留言
- 某個 API 只能 server-side 呼叫
- 某個欄位已 soft delete，不可真刪
- 需求指定只能修改某個模組

這種資訊不應該埋在幾十輪之前。它應該在新的上下文一開始就被清楚列出，成為代理工作的邊界。

你可以把 faithfulness 的修法記成另一句話：恢復專注。不是讓模型看到更多，而是讓它更容易忠實使用真正重要的東西。

### ⚖️ parametric knowledge 與 contextual knowledge，各解決哪一半問題

理解這一課，關鍵不只是背兩個名詞，而是知道 parametric knowledge 和 contextual knowledge 各自能做什麼，不能做什麼。

下面這張對照可以直接當成你的工作直覺。

| 面向 | parametric knowledge | contextual knowledge |
| --- | --- | --- |
| 白話意思 | 模型訓練後留在參數裡的壓縮知識 | 當前 session 明確帶入的任務資料 |
| 優點 | 廣泛、即時可用、能支撐一般理解與推理 | 接近當下真實情況、能補最新事實 |
| 弱點 | 可能過時、模糊、受 knowledge cutoff 限制 | 可能太長、太亂、太混，導致注意力失真 |
| 最常修正的問題 | 一般背景理解不足 | 當前任務的真實依據不足 |
| 對應幻覺風險 | 容易出 factuality | 若上下文失控，仍可能出 faithfulness |

**為什麼這張表重要？**
因為很多初學者會在兩個極端之間擺盪。一種是過度相信模型內建知識，覺得夠大的模型就應該自己知道一切。另一種是過度迷信 context，覺得只要把資料塞進去就沒事。真正成熟的用法，是知道兩者都重要，但作用完全不同。

### 🛠️ 把 decision tree 放回你的 coding workflow

現在把這套方法放回日常工作，你會發現它非常實用。

#### 情境一：代理回答第三方世界知識

當代理在回答第三方 API、價格、平台政策、部署限制、最新文件寫法時，先不要因為它語氣穩就相信。第一個反應應該是：它的來源是什麼？如果答案沒有來源，而且你也沒把權威資料送進 context，先視為 factuality 風險。

#### 情境二：代理在 repo 內改壞已明示的限制

如果它明明讀過 spec、schema、測試和錯誤訊息，卻還是沿用舊假設或違反剛剛才確認的需求，這更像 faithfulness。此時與其繼續補 prompt，不如先看 session 是否過長、是否同時混了太多階段、是否還保留大量已失效的探索內容。

#### 情境三：code review 時反過來診斷工作系統

你在 review 代理產出的 diff 時，也可以用同一棵樹來問：這個錯是因為它根本沒讀到必要檔案，還是因為它讀到了卻沒有忠實遵守？前者說明你的資料入口設計有問題，後者說明你的上下文管理有問題。這樣 review 就不只是抓 bug，而是在優化整個代理工作流。

#### 情境四：和代理溝通時改用更精確的語言

當你發現問題，不要只說「你又幻覺了」。可以更精確地說：

- 這個答案缺乏目前上下文中的來源，先查證再回答
- 正確資訊已在這兩份檔案，請依照它們重做
- 目前上下文過長，先根據這份精簡摘要重新規劃

這種說法的好處，是你在描述故障模式，而不是在情緒化地責備一個模糊現象。

### 📋 一套可以直接帶走的操作守則

最後，把整篇壓成一組你可以立刻用的守則。

#### 一，先分型，再修復

不要把所有錯都叫 hallucination，然後用同一招處理。先問：正確資訊在不在 context？這一步是後面所有動作的分水嶺。

#### 二，外部高變動事實，預設不信無來源回答

價格、政策、版本、權限、雲端限制、SDK 最新行為，只要沒有來源，就不要當成已驗證事實。never trust an unsourced LLM。

#### 三，資訊不在 context，就補證據

這是 factuality 的標準修法。查文件、跑搜尋、讀 repo、看真實輸出。不要空重試。

#### 四，資訊已在 context，卻還是錯，就減負載

這是 faithfulness 的標準修法。清 session、做摘要、拆階段、前置關鍵限制。不要再堆更多背景。

#### 五，把 smart zone 概念和幻覺診斷綁在一起

faithfulness 問題常常不是資料真假問題，而是注意力退化問題。所以 [[learn/ai-coding-crash-course/elements/attention-smart-zone|注意力退化與 Smart Zone]] 不是另一個獨立主題，而是這套診斷法的一部分。

#### 六，把來源管理和上下文管理變成 workflow

真正成熟的使用方式，不是等模型答錯才臨時補救，而是一開始就知道什麼資訊必須查證、什麼階段必須切開、哪些限制要被前置。這樣代理就比較容易一直留在可工作的區域，而不是每次都等出錯再救火。

### ✅ 你這一課真正要學會的是什麼

如果把這篇只留下一個核心句子，那就是：幻覺不是一團玄學，而是兩種不同的失敗模式。factuality 是缺證據時拿舊知識硬補，faithfulness 是有證據時卻沒照證據走。前者靠補來源修，後者靠整理上下文修。

一旦你把這棵 decision tree 用熟，AI agent 出錯時，你就不會只是覺得它又在亂來。你會更快看出，這次是世界事實沒有進 context，還是 context 已經失去可用形狀。這種判斷力，才是把 agent 從聰明 autocomplete 變成可靠隊友的起點。
