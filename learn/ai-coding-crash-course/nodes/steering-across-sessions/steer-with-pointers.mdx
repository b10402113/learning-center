# 用 Push 與 Point 跨 Session 傳遞意圖

## Learning goal

學完這一課，你能在新的 session 裡穩定傳遞專案慣例與容易漏掉的陷阱，並能判斷哪些內容應該固定放進 `agents.md`，哪些內容應該放進文件後用 pointer 指向，哪些內容值得進一步封裝成可攜式 skill。你也能用資料庫 schema 變更與 `seed.ts` 不同步的案例，實際檢查引導是否在正確時機被載入，而沒有讓每一輪請求都背著整本操作手冊。

## Lesson

## 📝 這一課到底在解什麼問題

跨 session steering 的難點，不是「代理不夠聰明」，而是新的 session 本來就不會繼承昨天的對話。你昨天花了很多時間講清楚資料庫怎麼改、哪些檔案要一起更新、哪些步驟不能漏，今天開一個新 session，只丟一句「幫我加一個課程欄位」，代理看到的仍然只是這一輪被送進去的上下文。

這時很容易出現兩種失敗，而且兩種都很常見。

第一種失敗是資訊太少。代理只改了 schema，卻沒改 `seed.ts`。結果你一重新建立資料庫，測試資料的形狀跟欄位定義不一致，後面連鎖爆出一堆看起來像別處壞掉的錯誤。

第二種失敗是資訊太多。你怕代理再漏步驟，乾脆把整份資料庫操作手冊塞進 `agents.md`。從此之後，不管任務只是改按鈕顏色、修文案，還是調整排版，每次請求都背著 migration、seed、失敗情境與檢查流程。固定規則變多之後，代理甚至可能在不相干的工作裡也被資料庫規則分心。

**為什麼這很重要？**
因為跨 session 的真正工作，不是把所有知識都塞給模型，而是把知識放在對的地方，讓它在需要時被載入，不需要時不要一直佔位。這正是 [[learn/ai-coding-crash-course/elements/context-load-steering|上下文負載與 Push/Point 引導]] 的核心。

## 💡 先看清楚：新 session 裡到底有什麼

模型不會保留上一輪對話的內在記憶。新的 session 開始時，harness 會重新組一份上下文，再把它送給模型。這份上下文通常包含幾種東西：

- 系統提示
- 可用工具與工具規則
- 專案層級的引導檔，例如 `agents.md`
- 你的當前要求
- 後續透過工具讀回來的檔案內容與命令結果

模型就是根據這一包當下可見的文字往下生成。它昨天讀過什麼，不會自動留到今天。昨天知道 `seed.ts` 要跟 schema 一起改，今天如果沒有被重新提醒，模型就可能完全沒有把那個檔案列入考慮。

所以，跨 session 的知識必須外化到環境裡，最常見的載體就是檔案系統。你可以把 repo 內的指引檔、文件、技能資料夾，想成專案給代理準備的外部記憶。

但這裡有一個關鍵差別：

- 檔案「存在」不等於代理「一定會看到」
- 代理「看到」不等於代理「只在該用時才看到」

真正要設計的是載入時機。哪些內容要在 session 一開始就出現，哪些內容只在碰到特定任務時再讀。

## ⚡ 上下文負載不是抽象名詞，而是真成本

每一段被預先塞進上下文的文字，都會帶來固定成本。這個固定成本可以分成兩部分。

### 傳送與計費成本

只要某份引導是每次請求都會附帶的內容，那它就會反覆被送進模型。這代表 token 成本會累積，請求也會變重。

### 注意力成本

上下文不是越多越好。模型要在更多規則、更多背景、更多例外裡，判斷什麼跟眼前任務有關。無關文字越多，重要訊號越容易被稀釋。

這整體的固定消耗，就是 context load，也就是上下文負載。

**為什麼這很重要？**
因為問題從來不只是檔案大不大，而是「這份內容值不值得每一輪都出現」。一份短規則如果幾乎所有任務都適用，那它很可能值得常駐。反過來，一份只有幾百行、但大多數任務都不需要的流程說明，長期掛在每次請求裡，依然會造成干擾。

你真正要問的不是「這份文件有沒有價值」，而是：

- 它是否幾乎每次都會用到
- 它漏掉時風險是否很高
- 它是否短到足以常駐而不造成明顯膨脹

## 🔧 Push：把規則固定推進上下文

Push 的意思很直接，就是主動把規則推進模型的起始上下文。最典型的做法，就是在 repo 裡放一份 `agents.md`。不同的 harness 可能有自己的相容檔名，例如某些環境可能會用 `claw.md`，但概念是一樣的：session 啟動時，系統先把這些引導放進去。

Push 的優點是立即可見。代理一開始就知道一些底線，不用猜、不用找、不用先探索目錄。

### 什麼適合 Push

適合 Push 的，通常是這一類規則：

- 適用範圍非常廣
- 文字很短
- 漏掉時風險很高

例如：

- 先閱讀相鄰程式碼再編輯
- 不要提交秘密
- 修改後維持可測試
- 只在必要時動用危險指令

這種規則幾乎不分任務型態，屬於專案或工作方式的通用底線，很適合固定放在入口。

### 什麼不適合 Push

不適合 Push 的，是那種只在特定情境才有用、但內容又很長的程序。很多團隊的 `agents.md` 之所以越長越難用，就是因為每發生一次事故，就往裡面再加一段。

常見的累積方式是這樣：

1. 代理漏掉一個步驟，補一條提醒
2. 又漏另一種情況，再補一條例外
3. 某個人踩到特殊坑，把完整背景、命令、排查流程全貼進去

久而久之，`agents.md` 變成一份事故沉積層。內容不是沒有價值，而是出現時機錯了。

### Push 的典型副作用

當每一條規則都被標成「永遠重要」，代理就很難判斷哪些是當前任務真的 relevant。它可能只看到「migration」這個字，就在一個純前端 CSS 任務裡花力氣檢查資料庫流程。這不是因為資料庫規則本身錯，而是因為它被放進了過度寬泛的常駐位置。

所以，`agents.md` 最好扮演的是「小而關鍵的入口」，不是專案百科全書。你希望它留下的是高通用、高風險、低篇幅的規則，而不是把所有歷史經驗都永久推進模型腦中。

## 🧭 Point：只留下路標，需要時再讀全文

Point 是另一種思路。你不把完整流程常駐，而是在固定上下文裡留一個短 pointer，告訴代理：如果碰到某一類任務，請去讀哪一份文件。

也就是說：

- 短指標留在 `agents.md`
- 完整規則留在 `docs/` 或其他清楚命名的位置
- 只有任務命中那個情境時，才載入完整內容

這樣做的好處很直白。平常你不用讓每一個請求都背著整本手冊，但真正碰到那類工作時，又有明確入口可以走。

### 一個資料庫 pointer 的樣子

例如你可以在 `agents.md` 留一句很短的規則：當修改資料庫 schema 時，先閱讀 `docs/database-migrations.md`。

而真正厚的內容，像是下面這些，就放進那份文件裡：

- schema 要怎麼改
- migration 要怎麼產生
- 哪些情況 `seed.ts` 必須同步更新
- 重新 seed 的流程
- type-check 要不要跑
- 常見失敗情境怎麼判斷

這樣做前端文案時，代理不需要攤開整套資料庫流程。真的要改資料表時，它才沿著 pointer 去把完整步驟讀進來。

### Point 不是丟一句模糊提示就算完成

Point 的前提，是路標要真的能用。好的 pointer 至少要滿足幾件事：

- 觸發條件清楚，例如「修改 schema」而不是「有時候要看資料庫文件」
- 文件位置穩定、名稱清楚
- 文件內容是最新的
- 文件裡真的有可執行的完整流程

如果 pointer 很模糊，代理只會多一道探索成本。如果 pointer 指向過期文件，情況甚至比沒有 pointer 更糟，因為代理會很有信心地沿著錯誤路線做事。

### 怎麼判斷 Push 還是 Point

你可以用三個問題快速篩選：

| 問題 | 若答案多半是「是」 | 較適合 |
| --- | --- | --- |
| 這條規則幾乎每個任務都會用到嗎？ | 是 | Push |
| 漏掉它會造成高風險錯誤嗎？ | 是 | Push 或至少要有很強的 pointer |
| 它是不是短到可以常駐而不造成膨脹？ | 是 | Push |

如果某條規則只在資料庫、部署、特定測試、特定檔案變更時才 relevant，那通常就比較適合 Point，而不是硬塞進常駐引導。

## 🗂 用 schema、migration 與 `seed.ts` 看懂真正的 gotcha

資料庫是最適合拿來理解這件事的例子，因為它很常不是改一個檔案就結束，而是有多條同步線要一起成立。

假設你的專案裡：

- schema 檔描述資料表結構
- SQLite 檔案保存實際資料
- `seed.ts` 用來建立或重建示範資料

當你新增一個欄位，例如課程欄位，至少有兩條線要同步。

### 第一條線：schema 和 migration

你要先把 schema 改對，然後讓資料庫結構透過 migration 真正新增欄位。這一條線處理的是「結構有沒有變」。

### 第二條線：`seed.ts`

你還要檢查 `seed.ts` 裡建立資料的形狀是否跟新 schema 一致。這一條線處理的是「重新初始化後的資料是否跟新結構對得上」。

### 為什麼只改 schema 還是不夠

如果你只改 schema，migration 可能會讓現有資料庫看起來暫時正常，因為欄位確實多出來了。但只要 seed 流程仍然照舊邏輯建立資料，問題就會浮出來。

尤其在 seed 會刪除並重建資料表的情況下，這個問題會更明顯。你可能得到下面這種不一致：

- 資料表結構已經是新的
- 預設資料還是舊的形狀
- 應用程式和測試預期又是另一個版本

這時錯誤看起來可能不是「你忘了改 `seed.ts`」，而是一些下游行為開始失敗。也因為錯誤表面上很間接，代理只盯著 schema 很容易誤判成「migration 已完成，所以資料庫已經沒事了」。

### 這就是 repo-specific gotcha

這類問題不是一般語言知識，也不是靠看單一函式就能完整推導出來。它是這個 repo 的工作習慣、工具鏈和流程約定交疊出來的坑。新同事需要被告知，代理也同樣需要被告知。

因此，這份資料庫流程文件裡，合理的內容可能包括：

1. 修改 schema
2. 產生 migration
3. 更新 `seed.ts`
4. 重新 seed
5. 執行 type-check
6. 檢查預期會失敗的情境

注意這份流程很重要，但它不是每個任務都要帶在身上的知識。這正是 doc + pointer 最適合發揮的地方。

## 🔍 不要只寫文件，要驗證它會不會被正確載入

跨 session steering 不能只看文件有沒有寫，還要看代理在對的時機會不會真的讀它。判斷標準不是文檔漂不漂亮，而是行為有沒有改善。

### 一個實際的驗證方式

你可以分成兩輪測。

### 第一輪：無關任務測試

先做一個完全不碰資料庫的 dummy request，例如改一個 UI 文案或調整樣式。觀察兩件事：

- 固定上下文是不是變輕了
- 代理是不是沒有被資料庫規則干擾

如果前端任務裡它還在大談 migration，那表示你其實還是把資料庫規則 Push 得太重。

### 第二輪：觸發任務測試

再給一個明確會碰 schema 的小變更。這時你要檢查的不是它有沒有回一句「完成」，而是它是否真的做了對的載入與對的動作。

重點包括：

- 有沒有找到那份 migration 文件
- 有沒有同步想到 `seed.ts`
- 有沒有執行重新 seed
- 有沒有做 type-check
- 最後產出的檔案差異是否合理

### 驗證看的不是口頭，而是痕跡

真正要看的證據是：

- 檔案 diff
- migration 歷史
- seed 結果
- 測試或檢查輸出

因為 steering 設計的目的，是改變代理的實際工作流程，而不是只讓它在回答裡看起來比較懂。

## 📦 從 doc + pointer 再往前走一步，就是 skill

只靠 repo 內文件與 pointer，已經能大幅降低固定 context load。但它仍然有一個限制：這整套東西通常綁在某個 repo 的目錄結構裡。換一個專案、換一台機器、換一個支援不同工作流的 harness，原本的文件位置和觸發方式就未必還成立。

這時 [[learn/ai-coding-crash-course/elements/portable-skills|可攜式技能]] 就是在把「文件 + 路標 + 觸發條件」包成一個可搬動的單位。

### skill 的基本形狀

一個 skill 通常是自包含的資料夾，核心檔案常常叫 `skill.md`。這裡面至少會有兩層東西：

- skill 的名稱與 description
- 真正的操作步驟與參考資料

名稱與 description 很像是更正式的 context pointer。它先告訴 parent context：這個技能處理什麼類型的任務。等到任務真的符合條件，才載入完整的 `skill.md`，以及同資料夾裡的範例、補充說明或其他輔助檔案。

### skill 為什麼比散落文件更可攜

因為它是自包含的。你不只搬一份文字說明，而是把入口、規則、例子、附帶資源一起打包。這樣它可以被帶到另一個 repo、另一台機器，甚至另一個支援這套格式的 harness。

這裡的可攜性，不是把所有內容複製到每個 `agents.md`，而是用標準化結構與清楚 description，讓系統知道何時該載入什麼。

## 🤖 skill 也有載入策略：model-invoked 與 user-invoked

skill 並不是做出來就結束，還有一個重要設計：由誰來觸發它。

### Model-invoked skill

這類 skill 讓模型根據名稱和 description 自己判斷該不該用。好處是使用者不用記得太多技能名稱，代理有機會自動選到正確流程。

但代價也很明顯。為了讓模型有能力判斷，更多 skill 的名稱與 description 會出現在 parent context。這意味著固定負載會再上升一些。

### User-invoked skill

這類 skill 需要人明確呼叫。好處是平常幾乎不增加每輪固定負載，因為沒被叫到時，它就不出現。

代價則是：人必須知道何時該叫它。如果你忘了，它就不會自動發生。

### 真正的差別是判斷責任放在哪裡

這不是單純的「哪個比較自動化」。更準確地說，是你把判斷責任交給誰。

- 常見、容易辨認、錯過代價很高的流程，適合考慮 model-invoked
- 低頻、意圖明確、使用者本來就知道要用的流程，適合 user-invoked

例如把工作交接給另一個代理，通常就是一個很明確的人類意圖。這時讓使用者主動呼叫 skill，往往比讓每個 session 都背著它更省。

## 🏠 skill 放哪裡，也是在設計責任範圍

skill 還有一個維度是放置層級。不是所有流程都該進 repo，也不是所有流程都只該放在個人環境。

### user-level skill

如果某個流程主要服務你自己的快捷習慣、個人偏好或跨專案工作方式，它適合放在 user-level，例如 `.claude` 或 `.agents` 的 skills 資料夾。這樣你走到不同專案，仍然可以帶著它。

### project-level skill

如果某個流程屬於團隊共同依賴的規則，例如部署流程、資料庫程序、專案內標準工作方式，那它更適合放在 project-level，直接跟著 repo 走。這樣任何 clone 這個專案的人，拿到的都是同一套程序。

**為什麼這很重要？**
因為你放置的位置，其實在回答一個治理問題：這條規則屬於誰，缺了之後誰會受影響。如果規則本質上是團隊共同契約，卻只藏在某個人的 user-level skill，其他協作者就無法穩定受益。

## 🛠 一個實際可用的整理方法

如果你接手的是一份已經膨脹很久的 `agents.md`，最有效的做法通常不是直接重寫，而是先分類。

### 第一步：把內容分成三類

**第一類：通用短規則**

幾乎所有任務都會用到，且字數短。這類內容留下來，並盡量再壓短。

**第二類：條件式完整流程**

只在特定任務類型才 relevant，例如資料庫修改、部署、特殊測試。這類內容移到文件，然後在 `agents.md` 留 pointer。

**第三類：跨 repo 可重用流程**

如果某份程序會在別的專案也反覆出現，或你希望分享給其他 harness，那它適合被整理成 skill。

### 第二步：清理沉積物

分類之後，不要直接假設每條舊規則都該保留。你還要做三個檢查。

- 同一條規則是否在多份文件重複出現
- 規則是否早已過期，卻還留在舊位置
- 規則看似合理，但其實刪掉也不影響代理行為，只是 no-op

這一步很重要，因為很多 context load 都不是來自「必要知識」，而是來自歷史殘留。

### 第三步：做兩種任務測試

移動內容之後，再做兩種測試：

1. 無關任務測試，確認固定負載變小，代理不再被不相關規則分心
2. 觸發任務測試，確認代理真的能順著 pointer 找到完整流程，並完成 schema、migration、`seed.ts`、reseed 與檢查步驟

如果第二種測試失敗，先優先修 pointer 的位置、名稱和觸發條件，而不是立刻把整份文件重新 Push 回常駐上下文。只有在你確認代理穩定找不到入口時，才值得增加固定引導。

## ✅ 最後把三種工具放回同一張地圖

Push、Point 與 skill 不是互斥選項，而是三種不同的成本配置方式。

你可以把它們這樣理解：

| 方法 | 買到的東西 | 代價 |
| --- | --- | --- |
| Push | 立即可見性 | 每輪固定成本較高 |
| Point | 較低固定成本 | 需要正確觸發與讀取 |
| skill | 可分享、可攜、可封裝流程 | 需要設計觸發方式與放置層級 |

真正好的 steering，不是盲目偏好其中一種，而是根據任務頻率、風險與可重用性分配它們。

- 把最少但關鍵的規則固定 Push 進入口
- 把條件式知識放在清楚的 pointer 後面
- 把穩定、可分享、可跨環境帶走的程序整理成 skill

這樣一來，新的 session 雖然沒有昨天的對話記憶，仍然能在需要時找到昨天累積下來的判斷；同時，它也不用在每一輪請求裡都背著整本操作手冊前進。
