# 封裝與修剪可攜式 Skills

## Learning goal

學完這一課，你能從一個實際的跨 session 工作問題出發，判斷資訊應該直接推入 steering 檔案、留在文件並以導航指標延後載入，還是封裝成可攜式 skill。你能說明 skill 如何以 self-contained folder 保存一套可重複的工作程序，分辨 model-invoked 與 user-invoked 的載入責任，並依照 user-level 與 project-level 的範圍放置它。你也能對 `agents.md`、`CLAUDE.md` 或其他 steering 檔案逐條執行 single source of truth、sediment 與 no-op 測試，處理自動產生的引導與 auto-memory，最後用「刪除、改成 pointer、改成 skill」三種結果，讓跨 session 的知識既找得到又不會永久污染每次請求。

## Lesson

## 🧭 先處理一個跨 session 的兩難

假設你在一個 session 裡花了半小時，教代理完成一套部署流程。它要先檢查環境變數，再建立 migration，接著更新 seed，最後執行型別檢查。這次執行得很順利。隔天換了新的 session，你只說「把這個服務部署到 staging」，代理卻漏掉其中兩步，你只好重新講一次。

為了避免重講，你把完整流程貼進 `agents.md`。問題立刻換了一個方向：另一個只要求「把登入頁的間距調大」的 session，也會收到整套部署規則。每次請求都多出一批無關文字，代理還得先判斷這些部署規則和 CSS 工作有沒有關係。等到資料庫、測試、提交、文件與事故處理規則也一起加進來，這份檔案就從工作提示卡變成每天都要翻開的百科全書。

這個例子先給我們一個核心結論：跨 session 的知識要能找回來，但不應在不需要時永久佔據上下文。設計目標不是把所有資訊都推入，也不是把所有資訊都刪掉，而是按照資訊的頻率、風險、適用範圍與重用需求，選擇合適的保存方式。

可以先用三種結果理解這個分流：

| 保存方式 | 適合放什麼 | 主要代價 |
| --- | --- | --- |
| Push，直接推入 steering | 幾乎每次都適用、漏掉又有高風險的短規則 | 每個 session 都支付上下文成本 |
| Point，留下導航指標 | 只在特定任務才需要的詳細文件 | 代理必須在正確時機沿著指標前進 |
| Skill，封裝成技能 | 穩定、可分享、可重複執行的完整程序 | 要設計清楚入口、觸發條件和載入責任 |

固定而普遍的規則可以直接出現；條件式流程可以由短指標指路；值得在不同地方重用的程序，則可以封裝成 [[learn/ai-coding-crash-course/elements/portable-skills|可攜式技能]]。為什麼這個分流很重要？因為「永遠看得到」和「真正需要時找得到」是兩個不同的可靠性問題。

## 📦 從文件指標走向可攜式 skill

### 先留下入口，不要複製整本手冊

假設 repo 裡已有 `docs/database-migrations.md`，內容包含 schema、migration、seed 與驗證流程。這份文件對資料庫工作很重要，對每次按鈕樣式修改卻沒有幫助。steering 檔案可以只留下短短一句：「修改資料庫 schema 時，先閱讀這份文件。」這就是 pointer，也就是導航指標。

pointer 的價值在於保留可達性，卻不要求每個 session 預先載入完整流程。代理先看到觸發條件，任務真的涉及 schema 時才往文件走。這比把整份資料庫手冊固定貼在每次請求前面更節省，也更容易讓上下文聚焦。

但 pointer 有邊界。它依賴 repo 的目錄結構，換到另一個專案時，文件路徑可能完全不同；交給另一位同事或另一個 harness 時，也可能只複製了指標，沒有複製指標依賴的附件。如果一套程序只靠「請去某個 repo 的某個位置找文件」來描述，它還沒有真正被封裝。

### skill 的兩個入口責任

當一套流程要在多個 repo、不同 harness 或不同工作環境重用時，可以把它整理成一個自包含資料夾。skill 的核心通常是 `skill.md`，它同時負責兩件事：

1. 用名稱讓人和工具知道這個資料夾提供什麼能力。
2. 用 description 說明什麼時候適用，成為 parent context 裡的發現入口。

完整的操作步驟、範例、檢查清單、常見失敗與參考資料，則放在資料夾內。必要時，`skill.md` 再指向同一個資料夾裡的附帶檔案。外部先看見的是一張索引卡，任務吻合時才打開完整工具箱。

「自包含」不是說文件裡絕對不能出現路徑，而是使用這個 skill 所需的程序和支援材料，應該能作為一個清楚的單位一起搬動、閱讀與理解。部署 skill 如果只寫「請看某 repo 中一個沒有固定位置的文件」，使用者換環境後就不知道依賴在哪裡。反過來，若 skill 整理了觸發條件、執行步驟、常見失敗、驗證方式與必要參考，另一個環境才有機會按照同樣的意圖工作。

可攜性來自結構化的入口和清楚的依賴，不是來自把同一段文字複製到更多 steering 檔案。複製只會增加多份內容同時更新的責任；封裝則把程序、附件和使用條件綁成一個可辨認的工作單位。

## 🤖 決定由模型發現，還是由使用者呼叫

### Model-invoked：用自動發現換取低遺漏風險

Model-invoked skill 會把技能的名稱和 description 提供給模型，由模型根據當前任務判斷是否載入。這種方式適合三個條件同時成立的工作：常見、能從語意辨認，而且漏掉後代價很高。

例如，專案每次修改資料庫 schema 都必須同步 migration 和 seed，而任務文字通常會明確提到 schema 或 migration。讓模型自動發現這個 skill，可能比要求每一個人記住技能名稱更安全。只要 description 寫得準確，相關任務就有機會在正確時機取得完整程序。

它並不是沒有成本的自動化。即使完整的 `skill.md` 尚未載入，所有可供模型考慮的技能名稱與 description 仍會出現在 parent context。技能越多，這張索引卡越厚。description 太含糊，模型每輪都要猜是否相關；技能切得太細，每個小規則都變成一個候選入口。換句話說，model-invoked 把發現工作從使用者的記憶，轉移到每次模型請求。

### User-invoked：用明確呼叫換取低固定負載

User-invoked skill 只有在使用者明確指定時，harness 才載入完整程序，因此平時幾乎不增加固定上下文。它適合低頻、意圖清楚、使用者本來就知道何時需要的流程，例如「把目前工作交接給下一個代理」，或「依照發版檢查表產生交付包」。

這類任務不必讓每個 session 都掛著一張無關的索引卡。使用者知道自己要做交接或發版時，再明確呼叫對應 skill 即可。固定負載比較小，但代價是使用者必須記得技能存在，也必須知道它的名稱或呼叫方式。

### 四個問題幫你做選擇

不要只問「我希望它自動嗎」。可以依序問：

1. 漏掉這個流程的風險有多高？
2. 模型能否從任務文字穩定辨認它？
3. 使用者是否自然知道何時要呼叫它？
4. 每輪增加的發現負擔，是否值得換取自動化？

高風險且高頻的技能，通常偏向 model-invoked；低頻且意圖明確的技能，通常偏向 user-invoked。若 description 必須塞入一大段背景，模型才勉強知道何時使用，這可能表示 skill 的邊界還沒整理好。好的 description 應該讓觸發條件清楚，而不是用更多背景掩蓋模糊的範圍。

## 🗂️ 決定放在 user-level 還是 project-level

### 先問規則屬於誰

想像你有一套個人偏好的程式碼閱讀流程，包含喜歡的輸出格式、個人快捷指令和私人筆記位置。若把它提交到 repo，其他協作者每次 clone 都會得到它，卻不一定需要遵守。相反地，團隊要求所有 schema 變更都更新 migration 和 seed，若只放在你的家目錄，其他人和 CI 裡的代理就拿不到。

分界點不是資料夾名稱，而是規則的所有者，以及缺少它時誰會受影響。

| 範圍 | 放置位置 | 適合內容 | 分享方式 |
| --- | --- | --- | --- |
| User-level | 使用者自己的 `.claude` 或 `.agents` skills 資料夾 | 跨專案沿用的個人偏好與快捷流程 | 跟著同一台機器上的使用者走 |
| Project-level | repo 內並提交 | 團隊共同程序、專案特有工具鏈、專案工作規則 | 隨 repo 分享給協作者和其他 clone |

User-level skill 不應假裝是每個專案的共同契約；project-level skill 也不應變成某個人的私人設定。把個人偏好放在 project-level，團隊會誤以為那是專案要求；把團隊關鍵流程放在 user-level，流程就只在某一個人的環境有效。

如果一個 skill 同時包含個人捷徑和團隊必要步驟，可以拆開。共同部分放在 project-level，user-level skill 再提供個人化包裝。為什麼範圍很重要？因為它決定誰負責維護、誰應該看見、換一台機器或換一位協作者後，這套知識是否仍然存在。

## ✂️ 修剪 steering：三個測試先於三種處置

skill 封裝完成後，原本的 steering 檔案仍可能留著舊副本。更常見的情況是它只增不減：代理漏掉一次步驟，人就加一條提醒；專案發生事故，就把整段背景貼進 `agents.md`；工具改版後，卻沒有人回頭檢查原本的命令。幾個月後，檔案看似完整，裡面卻同時有重複內容、過時規則和不會改變行為的句子。這些累積物就是 [[learn/ai-coding-crash-course/elements/steering-file-pruning|steering 檔案修剪]] 要處理的對象。

修剪不是單純追求更短，而是確認每一條內容仍然值得在固定位置佔用上下文。可以對每一條規則做三個測試。

### 1. Single source of truth：權威版本在哪裡？

逐條問：「這份資訊的權威版本在哪裡？」答案可能是程式碼、README、專門文件、skill 或另一份受控設定。若完整規則已經存在，就不要在 steering 檔案再抄一份。

複製品表面上讓代理更容易看到，實際上卻增加同步風險。權威文件更新、steering 沒有更新時，代理會同時收到兩個版本，而且不一定知道哪一個才是新的。修剪的結果通常不是移除所有入口，而是把重複段落改成一句準確的 pointer，讓代理能找到真正的來源。

### 2. Sediment：這條規則還活著嗎？

sediment 指的是曾經有用、現在卻失去適用性的沉積規則，不只是「寫得很長」。檢查它提到的目錄、工具、命令與流程是否仍然存在。專案可能從一個測試框架換成另一個，部署平台可能已經改變，某個手動步驟可能早已由 CI 自動完成。

曾經在一次事故中有用，不代表它現在仍值得每次載入。過時內容應該更新或移除，不能只因為它有歷史價值，就永久佔據每個請求的位置。規則的現行價值要靠今天的 repo 和流程確認。

### 3. No-op：移除後行為會變嗎？

no-op 是最容易被忽略、也最需要實驗的測試。先選一個可重複的基準任務，記錄代理在有這條指示時的行為，例如它是否找到正確檔案、是否執行某項檢查、是否產生特定差異。接著暫時移除這條指示，在相同條件下重做任務。

如果行為沒有可觀察的變化，這條指示就是 no-op。它可能只是把常識說了一遍，也可能是代理本來就能從程式碼和工具結果推導出來。合理的句子不等於有效的句子；若它沒有影響決策，就不值得永久佔位。

### 把測試結果分成三種處置

三個測試的目的不是把 steering 變成空檔案，而是把不同價值的內容重新分流：

- 沒有現行價值，或測試證明是 no-op 的內容，刪除。
- 仍然重要，但只在特定任務使用的詳細程序，移到文件，留下短而準確的 pointer。
- 需要在不同 repo 或 harness 重用的程序，封裝成 portable skill。

只有幾乎每次任務都適用，而且漏掉會造成高風險的短規則，才適合留在固定推入的位置。為什麼這樣的限制很重要？因為固定上下文是一種每輪都要支付的成本，不能把所有「可能有一天有用」的內容都當成全域規則。

## 🧭 pointer 也需要維護

pointer 看起來比複製完整規則安全，但它不是免維護的魔法。它的任務是讓代理避開盲目掃描，直接前往不容易從檔名猜出的重要位置。例如技能清單、頂層 README、manifest、seed script 或特定部署文件，都可能需要一個明確路標，尤其當真正的依賴關係不會出現在目前正在修改的檔案中。

但目錄移動、文件改名或流程合併後，舊 pointer 仍可能留著。過時路標有時比沒有路標更糟，因為代理會把它當成可信資訊，沿著錯誤位置搜尋，浪費 token，甚至依照已失效的流程工作。

每次改變檔案結構或工具鏈，都應順手檢查相關 pointer。好的 pointer 應該符合三個條件：少、短、可驗證，而且要說清楚觸發條件。不要把一串「可能有關」的路徑全部列出來，否則導航指標本身也會變成另一份需要掃描的長文件。

## 🧹 審核自動產生的 steering 與 auto-memory

### 自動產生的檔案只是草稿

某個初始化命令可能掃描整個 repo，產生一份一百多行、數千 tokens 的 `CLAUDE.md`。它看起來像完整的專案摘要，很容易被直接提交或長期保留。然而，掃描器能找到檔案，不代表它能判斷哪些資訊值得在每個 session 固定載入。產生結果應視為草稿，而不是完成品。

審核這類檔案時，仍然用前面的分流方法：逐行找權威來源，刪除重複內容；確認規則符合目前的 repo，清掉 sediment；用基準任務測試可疑句子，移除 no-op；把有條件的詳細程序改成 pointer 或 skill。目標不是讓文件看起來完整，而是讓它成為小而可靠的入口。最後只剩幾條全域規則和幾個導航指標，也可能比原本的長摘要更有效。

### auto-memory 也會形成沉積

另一個容易漏看的來源是 auto-memory。某些 harness 會把代理收到的修正、使用者偏好，以及它認為重要的事實寫進本機記憶，之後的 session 再載入這些內容。短期看很方便，你不必每次重複同一個偏好；長期看，問題在於自動記憶通常沒有嚴格的淘汰週期。

專案改名、工具替換或偏好改變後，舊內容仍可能繼續被帶入。它像一個沒有園丁的沉積層，一次修正堆一層，最後變成 auto-sediment。處理時，先分清楚哪些是穩定的專案契約，哪些只是某次 session 的暫時狀態。

穩定的專案契約應回到可審核的 project-level 文件或 skill；暫時狀態不應無限期保存。如果 auto-memory 持續累積過時內容，而你希望 steering 的建立和生命週期由人掌握，可以評估關閉 auto-memory。這不是否定記憶的價值，而是承認自動寫入不等於自動整理。跨 session 的可靠性既需要可追蹤的來源，也需要刪除和更新的責任。

## 🔧 執行一次完整的整理循環

整理現有專案時，不要一開始就重寫全部文件。先做盤點，為每一條 steering 內容記下四個欄位：

1. 它在保護什麼行為？
2. 權威來源在哪裡？
3. 它適用於哪些任務？
4. 刪掉後預期會有什麼變化？

接著按順序處理五步：

1. **留下全域規則。** 保留真正全域且短小的內容，例如不要提交秘密、修改前先讀相鄰程式碼、完成後執行現有驗證。
2. **移出條件式流程。** 只在特定變更才需要的長流程，移到文件或 skill。
3. **驗證 pointer。** 檢查指向的檔案真的存在，名稱清楚，觸發條件也能讓使用者和模型辨認。
4. **實驗可疑內容。** 對重複、過時和可能是 no-op 的句子做測試，不要只靠直覺保留。
5. **重新決定 skill 邊界。** 確認它是 model-invoked 還是 user-invoked，以及應放在 user-level 還是 project-level。

### 用兩個任務驗證遷移是否成功

移動內容後，至少做兩種驗證。第一個任務要和資料庫、部署或那套特殊流程無關。觀察固定上下文是否變小，代理是否停止被無關規則牽引。第二個任務要確實會觸發被移動的流程。觀察代理能否找到 pointer 或自動發現 skill，能否載入完整步驟，並完成必要的檔案更新和檢查。

如果第二個任務失敗，不要立刻把整份程序塞回 steering。先檢查四件事：skill 的 description 是否說清楚觸發條件、pointer 是否指向正確位置、project-level skill 是否已隨 repo 提交，以及使用者是否其實需要明確呼叫。只有確認延後載入造成真正的發現問題，才增加固定推入內容。

### 用三種成本做最後判斷

Push 買的是立即可見性，代價是每次都支付上下文成本。Point 買的是較低的固定成本，代價是代理必須在正確時機沿著路標前進。Skill 買的是程序的封裝、分享與重用，代價是需要設計清楚的 description、範圍和載入責任。

成熟的 steering 不會把所有資訊都選成同一種形式。它會讓每一條知識按照頻率、風險、可發現性和分享需求，待在最適合的位置。新的 session 雖然沒有昨天的對話，仍能在需要時找回累積的判斷；同時，它不必每天背著整段歷史工作。這就是封裝與修剪共同要達成的結果：讓知識可重用，也讓上下文保持乾淨。
