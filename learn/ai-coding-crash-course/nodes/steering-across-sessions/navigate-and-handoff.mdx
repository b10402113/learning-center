# 用導航指標與交接文件延續工作

## Learning goal

學完這一課，你能分辨兩種常見但很不一樣的跨 session 延續手段：一種是用 [[learn/ai-coding-crash-course/elements/context-load-steering|Context Load 與 Push/Point 引導 (Context Load, Push vs Point)]] 裡的導航指標，把長篇規則留在文件外部，只在需要時拉進來；另一種是用 [[learn/ai-coding-crash-course/elements/handoff|Handoff 跨代理交接 (Handoff)]] 把當前工作狀態寫成可攜帶的交接文件，交給下一個 session、下一個代理，甚至下一個人。你也能判斷何時該新增導航指標、何時該更新或刪除它，理解過時指標如何誤導代理，以及為什麼把交接文件和指標配合起來，能讓工作在 session 中斷、代理切換、repo 切換後仍然延續，而不必每次重講整段歷史。

## Lesson

### 📝 先分清楚：延續工作其實是兩個問題

一個 session 結束後，下一個 session 要怎樣接著做？這個問題看起來像只有一件事，實際上至少包含兩種完全不同的資訊。

第一種是**穩定知識**。例如 repo 裡有哪些規則、資料庫 migration 要看哪份文件、部署要遵守哪些步驟、發版有哪些容易踩到的陷阱。這些資訊不只服務今天的任務，也可能在未來反覆被用到。問題是，代理不一定每次都需要它們，所以不適合全部塞進每一輪請求的固定上下文。

第二種是**當前狀態**。例如這次工作已經改了什麼、查過哪些文件、試過哪些方案、哪些方向已經證明不可行、還剩什麼風險，以及下一步最值得做什麼。這些資訊通常只對當前任務有用，卻是下一位接手者最需要知道的內容。

前者是導航，後者是交接。導航要解決「需要時找得到」，交接要解決「接手時接得上」。如果把兩者混在一起，通常會走向兩個極端：要嘛把所有暫時脈絡永久塞進 steering，要嘛每次換 session 都從頭解釋。兩種做法都會讓上下文和維護成本失控。

### 🧭 Navigation pointer：給穩定知識一個入口

新的 session 不會自動保留昨天的對話記憶，但 repo 還在。代理真正可靠的依據，不是「它以前看過什麼」，而是「它現在能不能在有限上下文中重新找到正確資料」。因此，跨 session 的長期知識不應該主要依賴聊天紀錄，而應該放在可重找的文件結構裡。

這正是 [[learn/ai-coding-crash-course/elements/context-load-steering|Context Load 與 Push/Point 引導 (Context Load, Push vs Point)]] 要處理的問題。**Push** 是把規則直接放進每一輪都可能看到的上下文；**Point** 則是留下導航指標，等任務真的需要時，再把外部文件拉進來。這不是單純的「多寫一份連結」，而是在決定不同知識應該用什麼方式進入模型的注意範圍。

可以把 pointer 想成高速公路上的方向牌。城市裡有機場、港口、醫院、工業區和倉儲中心，但我們不會要求每位駕駛出發前先背下整座城市的每條小路。我們會在主要幹道上放幾個高價值路標，讓駕駛真的要去某個區域時，能迅速切入正確路線。

代理也一樣。它不需要每個 session 一開始就讀完整的 migration 手冊、部署手冊、發版事故史和所有 gotcha。它需要的是，當工作真的碰到資料庫、部署或發版時，能看到一條清楚、可信、成本很低的入口，知道哪份文件值得讀、文件放在哪裡，以及它為什麼和當前任務有關。

一個好的 pointer 通常很短，但方向很準。它至少應該讓代理理解三件事：

1. **什麼情況要查看它**，例如修改 schema 或準備發版時。
2. **它會帶你去哪裡**，例如某份 migration 文件、manifest、README、skill 或檢查表。
3. **目的地能解決什麼問題**，避免代理只拿到一個孤零零的檔案路徑。

pointer 不是內容本身，也不是把原文件重新抄一遍。它只負責把代理送到正確方向。這樣做有兩個直接效果：平常固定進入上下文的字變少，穩態成本降低；低頻但重要的程序仍然有路可走，不會因為沒有常駐而消失。

### 💡 為什麼不能把所有規則都 Push？

假設我們把整份資料庫 checklist、所有部署要求、所有測試陷阱都永久寫進 `agents.md`。代理確實比較不容易完全漏看它們，但每一輪任務也都得背著同一本厚手冊。今天只是修改標題文案，它仍然要面對 schema 變更規則、reseed 程序和發版前檢查。

問題不一定在規則內容錯，而在規則出現的時機錯。當所有資訊都在同一個上下文裡，真正相關的內容會被大量不相關內容淹沒。就像把整座城市的路牌都堆在同一個交流道，路牌變多不代表方向更清楚，反而讓人更難判斷哪一塊與眼前旅程有關。

因此，可以用下面的簡單分工來判斷：

| 知識特性 | 較適合的做法 | 原因 |
| --- | --- | --- |
| 幾乎每個任務都需要 | Push 一條短的全域規則 | 不必每次重新找入口 |
| 只在特定任務需要 | 建立 pointer 指向外部文件 | 降低平時上下文成本 |
| 只對這次工作暫時有用 | 寫進 handoff | 任務結束後不必永久保留 |
| 已經失效或重複 | 更新或刪除 pointer | 避免錯誤與雜訊繼續擴散 |

為什麼這個區分很重要？因為上下文不是免費的倉庫。每一段固定出現的文字，都會佔用模型可注意的空間，也會和真正重要的指示競爭。pointer 的價值不是讓文件變多，而是讓知識在正確的時刻出現。

### 🔧 什麼時候值得新增 pointer？

「這份文件很重要」還不足以成為新增 pointer 的理由。更可靠的判斷是，以下四個條件是否大致同時成立：

1. **對某類任務關鍵，但不值得所有任務常駐。** 例如資料庫文件對 schema 變更很重要，卻和一般文案修改無關。
2. **自然探索容易漏掉。** 代理只看目前編輯的檔案、測試結果或一般目錄名稱時，不一定會想到它。
3. **已經有明確且可維護的落點。** 目的地應該是專門文件、manifest、README、skill 或檢查表，而不是散落在聊天室裡的經驗。
4. **pointer 可以保持短而精確。** 如果指標本身需要寫成第二本手冊，代表內容分層可能還沒有整理好。

符合這些條件時，pointer 能用很少的常駐文字，保留一條通往高價值知識的路。相反地，若資訊本來就會從相鄰程式碼、檔名、型別錯誤或測試失敗自然浮現，額外加 pointer 可能只是重複提醒。

如果目的地經常搬動、文件沒有穩定位置，或內容本身模糊不清，pointer 只會把不穩定性放大。若某條規則幾乎所有任務都需要，它更像應該成為短的全域規則，而不是每次都要繞路尋找的外部文件。導航指標是給**非顯而易見、低頻但高價值**的知識使用，不是要替所有資訊都蓋一塊路牌。

### ⚠️ 過時 pointer 可能比沒有 pointer 更危險

高速公路的方向牌之所以有用，是因為駕駛相信它。如果「機場」指標仍然指向三年前的舊位置，結果可能比完全沒有指標更糟。沒有路牌時，駕駛至少知道自己需要重新查地圖；錯誤路牌則會讓人快速而自信地走錯路。

過時的 pointer 也有相同風險。它可能把代理導向錯誤文件、錯誤目錄或已經失效的流程，而且會讓代理產生「我已經找到權威資訊」的錯覺。結果不只是多花一些 token，而是讓錯誤內容得到高速可達性，並因此更可能被採納。

這也是為什麼 [[learn/ai-coding-crash-course/elements/steering-file-pruning|Steering 檔案修剪 (Steering File Pruning)]] 不只是刪掉幾行文字，而是在維護整個路網。repo 目錄改名、文件搬家、流程改版或工具鏈更換後，相關 pointer 都應該一起檢查。最危險的情況有時不是沒有文件，而是留著一條曾經有用、現在卻把所有人送錯地方的快捷路。

修剪或審查 pointer 時，可以依序問三個問題：

1. 這條指標現在仍然指向**單一真實來源**嗎？還是內容已經在別處重寫，形成兩份互相競爭的說法？
2. 指標描述的流程仍然成立嗎？還是它只是過去留下的沉積物？
3. 暫時移除它，再用相同任務重跑，代理的表現是否真的變差？

如果移除後沒有明顯差異，它可能只是看起來合理的 no-op。pointer 再短也不是零成本，只要它會出現在 parent context，就會佔用模型被注意的機會。保留每一條路牌之前，都要確定它真的能改善抵達率或判斷品質。

### 📦 Handoff：把這次工作的活記憶交出去

pointer 解決的是「穩定知識怎樣重新找到」，卻無法完整回答「這次工作現在做到哪裡」。它不能代替以下資訊：你已經完成哪些步驟、查過哪些文件、試過哪些方案、哪些判斷已經排除、目前還有哪些未解問題，以及接手者下一步最值得做什麼。

這就是 [[learn/ai-coding-crash-course/elements/handoff|Handoff 跨代理交接 (Handoff)]] 的責任。handoff 可以理解為一份可攜帶的工作狀態文件，把這一次 session 的活記憶整理後交給新的 session、新的代理、另一個 repo，甚至另一個人。

它和幾個相似概念的分工不同：

- **compaction** 比較偏向在同一個環境裡壓縮或延續上下文。
- **pointer** 只負責帶路，指向穩定、可重複使用的資料。
- **handoff** 負責交代這次工作的現況與下一步。

因此，handoff 像交接單，不像道路指標。交接單應該讓接手者知道目前狀態、已完成步驟、待決問題、失敗嘗試和具體建議；pointer 則只需要告訴接手者，這一類長期知識要去哪裡找。兩者不是替代關係，而是不同層次的基礎設施。

一份實用的 handoff 至少應該回答以下問題：

1. **目前目標是什麼，已經完成到哪裡？**
2. **你實際查過或修改過哪些內容？**
3. **哪些方案試過但失敗，失敗原因是什麼？**
4. **哪些假設已經被排除，哪些風險仍然存在？**
5. **下一位接手者應該先做哪一步？**

這些欄位的共同目的，是避免接手者把已經走過的路再走一次，也避免把已經排除的原因重新當成主要假設。

### 🛣️ Pointer 與 handoff 要一起工作

可以把兩者想成物流系統。pointer 是城市高速公路，負責把接手者送到重要而穩定的設施；handoff 是隨車交接文件，說明這批貨從哪裡來、目前送到哪一步、有哪些特殊注意事項，以及下一站預計去哪裡。

只有高速公路，沒有交接單，接手者雖然找得到資料庫或部署文件，卻不知道這次工作已經做了什麼，也不知道哪一箱貨缺失。只有交接單，沒有高速公路，接手者雖然知道任務很急、目前卡在哪裡，卻可能在陌生 repo 裡花很久重新尋找權威規則。真正順暢的跨 session 延續，通常需要兩者配合。

看一個具體例子。你在一個 session 裡修改資料模型，查過兩份文件，最後確認 bug 不是 migration 缺失，而是 reseed 流程沒有更新。你也試過一種修法，結果會破壞測試資料。

如果只留下 pointer，下一個代理會知道「碰到 schema 變更要看資料庫文件」，卻不知道你已經走過哪些路，也不知道哪個失敗模式剛被排除。如果只留下 handoff，代理知道你做到哪裡，卻仍可能花很多時間摸索 repo 裡哪份規則才是權威。較好的交接方式是：handoff 說明現況、證據、失敗嘗試與下一步；既有 pointer 則固定長期規則的位置。新代理先用 handoff 建立當前局面的模型，再沿著 pointer 取用需要的背景知識，接手成本就會大幅下降。

### 🔄 跨代理與跨 repo 時，handoff 特別有用

當工作從一個 harness 轉到另一個 harness，或從一個專案目錄切換到另一個專案目錄時，原 session 的隱性脈絡不會自動跟過去。handoff 提供的是可攜帶、一次性的任務狀態；pointer 提供的是環境內、可以重複使用的導航結構。

前者讓你把「這次做了什麼」帶走，後者讓接手者抵達新環境後，不必從零開始探索。這使 handoff 很適合以下情況：

- 今天做到一半，要交給另一個代理 review。
- 臨時發現另一個 repo 的 bug，先停下目前工作，之後再回來處理。
- 要把目前工作交給同事，而對方不在原本的 session 裡。
- 代理能力、工具或執行環境改變，但任務狀態仍然需要保留。

這些場景需要的是攜帶當前狀態，而不只是保存長期規則。交接文件的內容可以隨任務結束而失效，這不是缺點，反而是它和 steering 分工清楚的證據。

### 🧹 不要把每次 handoff 都升格成永久規則

handoff 不是永久記憶體，而是一次性交班文件。它的價值在於讓脈絡跨越邊界，不在於成為 repo 的新長期規則。因此，不要把每次 handoff 的全文反過來塞進 steering 或 `agents.md`。

常見的失控路徑是這樣：某次交接提到一個特殊失敗情境，接手者覺得很有幫助，於是直接把它複製到全域規則。幾次之後，steering 檔案開始堆滿只對單一事故有意義的敘述。原本想保留經驗，最後卻製造出新的上下文噪音。

較好的做法是先判斷這項資訊的壽命：

| 資訊狀態 | 應該放在哪裡 |
| --- | --- |
| 只對本次任務有用的進度、嘗試與下一步 | handoff |
| 反覆驗證後確認會持續存在的專案 gotcha | 正式文件 |
| 正式文件不必每次常駐，但特定任務容易漏看 | pointer 指向正式文件 |
| pointer 已不正確、重複或無效 | 修剪、更新或刪除 |

如果同類任務的 handoff 一再暴露同一個穩定 gotcha，這才是把它提煉成正式文件與 pointer 的好時機。反過來，如果只是這次任務的暫時狀態，就讓它留在 handoff，任務結束後自然失效。

### ✅ 一個可直接套用的判斷流程

面對一段新資訊時，可以依照下面四步處理：

1. **先問它的壽命。** 它只對這次任務有用，還是未來會持續成立？
2. **再問它的出現頻率。** 幾乎每個任務都需要，還是只有某一類工作才需要？
3. **檢查自然可見性。** 代理從目前程式碼、測試、檔名或錯誤訊息能不能自己找到它？
4. **選擇最小但可靠的載體。** 暫時狀態用 handoff；穩定知識放正式文件；低頻知識用 pointer；所有任務都需要的短規則才直接 Push。

這個流程的重點不是製造更多文件，而是讓不同壽命、不同用途的知識待在正確位置。文件越多不代表系統越有記憶；如果入口失效、內容重複，文件數量反而會增加搜尋與判斷成本。

### 🎯 收束：找路與接班是兩種能力

跨 session 延續工作，不靠單一神奇機制，而靠兩套互補的基礎設施。navigation pointer 確保下一個 session 在陌生或半陌生環境裡，能快速找到權威知識；handoff 確保下一位接手者知道上一個 session 的具體進度、判斷、失敗嘗試和未完成工作。

可以把整體關係濃縮成下面四句話：

- **Push**：把幾乎每次都需要的短規則直接帶進上下文。
- **Pointer**：為低頻但高價值的穩定知識留下入口。
- **Handoff**：把這一次工作的暫時狀態交給下一位接手者。
- **Pruning**：移除失效、重複或已經沒有價值的 steering 與 pointer。

高速公路解決的是找路，交接單解決的是接班。當兩者一起維護，新的 session、另一個代理，甚至另一個人，都能在不重新背誦整段歷史的情況下，沿著正確路線從上一段工作接著做下去。這才是有效的跨 session steering：不是保存所有過去，而是讓每一種知識都用適合自己的方式，在需要的時候抵達正確的人或代理。
