# Phase Boundary 的五種選擇

## Learning goal

能在 grilling、實作、QA 等工作階段之間辨認 phase boundary，理解邊界上的五種處理方式，依照決策樹選擇繼續、清空、壓縮、交接或派出子代理，並避免讓 auto-compaction 在實作中途替自己做出高風險決定。

## Lesson

### 📝 先把問題講清楚：什麼叫 phase boundary

你在和代理合作時，常常不是只做一件事。前半段可能在釐清需求，確認真正要解的問題是什麼；中段開始讀檔、改檔、跑測試；後半段再進入 QA、review，或整理下一步。這些都可能發生在同一個 session 裡。

這裡的 session，可以先把它想成一塊有限的工作記憶。從對話開啟到現在，所有東西都堆在裡面：你講過的限制、代理讀過的檔案、工具輸出、失敗的嘗試、最後採用的方案，還有那些後來其實沒用上的探索痕跡。當工作越做越久，這塊空間會越來越擁擠。

所謂 phase boundary，就是你從一個工作階段轉到另一個工作階段的那個點。最常見的例子有幾種：

- 從 grilling 轉進實作
- 從實作轉進 QA
- 從一個問題切到另一個獨立問題
- 從自己繼續做，改成要交給別的代理或別的人

它不是系統保證會提醒你的事件，而是一個需要你主動辨認的決策點。你要問的不是「工具能不能繼續跑」，而是「現在這段脈絡，要怎麼帶去下一段工作」。

**為什麼這件事很重要？**
因為如果你不做這個判斷，系統通常還是會往前跑。表面上很順，實際上卻可能把一個應該由人決定的轉場，交給上下文壓力或系統預設值處理。當上下文越來越長，模型每次都要背著更多歷史前進，能專心處理眼前問題的空間就越少。

### 💡 先有一個核心觀念：五種做法不是功能表，而是取捨

站在 phase boundary 上，你通常有五種選擇：

| 選擇 | 你做的事 | 主要好處 | 主要風險 |
| --- | --- | --- | --- |
| 繼續 | 留在原 session 往下做 | 摩擦最低，保留完整主要史料 | 上下文越來越長，品質可能慢慢下降 |
| 清空 | 丟掉舊上下文，開全新 session | 最乾淨，立刻回到完整空間 | 容易丟掉實作理由與隱性限制 |
| 壓縮 | 先做 [[learn/ai-coding-crash-course/elements/compaction|Compaction 壓縮機制 (Compaction)]] 再開新 session | 留住重點，放掉過程噪音 | 壓縮本質上有損，可能漏細節 |
| 交接 | 做 [[learn/ai-coding-crash-course/elements/handoff|Handoff 跨代理交接 (Handoff)]] 文件 | 能跨代理、跨目錄、跨 repo、跨人、跨時間搬運脈絡 | 比壓縮多一步保存與載入，操作成本較高 |
| 派子代理 | 把獨立工作丟給另一個代理 | 適合 AFK 工作，主線不必被切碎 | 若邊界不清楚，會增加協調成本 |

這五種方法沒有固定排名。真正的判斷，要看四件事：

1. 現在的上下文還值不值得留。
2. 剩下的「聰明區」空間還夠不夠。
3. 下一步是否還需要剛才那堆細節。
4. 下一步是不是一定要由目前這個主代理親自完成。

下面我們把五種方法逐一拆開看，重點不是記名字，而是理解它們各自解什麼問題。

### 🔧 選擇一：繼續留在原 session

這是摩擦最小的選項。你不用重開 session，不用準備摘要，也不用重新向下一個代理解釋背景。所有主要史料都還在。這裡的主要史料，指的是原本完整的對話與工具活動紀錄，也就是最原始、最細的那份脈絡。

這種做法最適合兩種情況同時成立的時候：

- 上下文還不長，沒有明顯擁擠
- 下一步直接依賴剛才的細節

例如你剛完成一個小函式，只看了三個檔案，只跑過幾次測試，接著要補一個緊貼實作的邊界測試。這時候切出去再回來，通常只是徒增成本。因為你真正需要的資訊，還新鮮、集中，而且都在眼前。

但「繼續」最大的危險，是它太方便，所以很容易變成預設習慣。長 session 的問題不是某一刻突然全壞掉，而是輸出品質常常慢慢變差。模型可能開始漏掉限制、誤解錯誤訊息，或在沒必要的地方改更多檔案。這些偏差一開始都不大，所以最容易被忽略。

**為什麼繼續有時會變成壞選擇？**
因為每一次請求，模型都要再次面對前面的歷史。就算快取讓重複內容的成本比較低，長上下文本身仍然會把注意力拉散。你表面上省掉了切換成本，實際上可能在後面用更多修正成本還回去。

### ⚡ 選擇二：清空上下文

清空是最乾淨、也最激進的做法。你直接放棄舊 session，開一個全新的空間，沒有等待，也沒有摘要成本。新 session 可以只專注在新的問題，不必背舊對話留下的讀檔紀錄、試錯痕跡和討論分支。

從效率上看，這很有吸引力。但它的適用條件其實非常嚴格。只有在你確定舊內容真的可以丟掉時，清空才是好選擇。

比較適合清空的情況通常像這樣：

- 剛才只是做一個小實驗，而且結果不影響正式工作
- 剛才只問了一個短問題，後面不會延伸
- 接下來要談的事和前面完全無關
- 舊 session 裡沒有任何之後還要依賴的決策

例如你只是請代理確認某個函式是否存在，確認完之後，現在要開始一個完全不同的主題。這種情況下，清空會很俐落。

但只要你剛完成了一個功能，或剛走完一段完整的設計與實作，直接清空通常就太危險。你可能丟掉兩種很重要的東西：

- 實作細節：哪些檔案改過、哪個測試還有問題、哪個奇怪命名其實是為了相容舊資料
- 決策理由：為什麼最後選 A 不選 B，哪些看似自然的方向其實已被否決

程式碼可以讓下一個代理重新看見「做了什麼」，但不一定看得出「為什麼這樣做」。而後者，往往正是 QA 和後續迭代最需要的資訊。

### 🧭 選擇三：壓縮後再開新 session

這是最常用、也通常最平衡的策略。[[learn/ai-coding-crash-course/elements/compaction|Compaction 壓縮機制 (Compaction)]] 會把目前 session 的工作濃縮成摘要，然後用這份摘要作為新 session 的起點。

你可以把它理解成：不是把整間工地搬走，而是先畫一張施工地圖，再帶著地圖去下一個房間繼續做事。

它的好處很明確：

- 重要脈絡被保留下來
- 大量過程噪音被放下
- 新 session 有比較乾淨的工作空間
- 你不用完全從白紙重新開始

有些關鍵檔案內容可能會被完整保留；其他內容則可能只留下檔案指標，等到新 session 真的需要時再重新讀。這就是壓縮的價值：它讓你帶著一張可用地圖前進，而不是把整個舊世界硬塞進下一輪。

但要記得，壓縮本質上是有損的。它不是逐字搬運，而是由模型判斷什麼重要、什麼可以收斂。你留下的是整理過的次要史料，失去的是一部分原始細節與某些微妙脈絡。

這個代價通常在 phase boundary 最容易接受。特別是從實作轉到 QA 的時候，下一步需要知道的是：

- 功能規格最後長什麼樣子
- 哪些檔案被改過
- 測試目前是什麼狀態
- 已知限制與風險是什麼

但 QA 通常不需要把每一輪讀檔、每一版失敗輸出、每一次短暫試錯都一起背著走。

#### 壓縮時最重要的技巧：告訴它下一步要做什麼

壓縮最怕的不是資訊少，而是整理方向不明。你如果只說「幫我壓縮」，模型當然還是會產生摘要，但它只能自己猜哪些東西重要。

更好的做法是把下一個 phase 說清楚。比方說：

- 從實作轉 QA：要求保留功能規格、已改檔案、測試結果、已知限制與 QA 目標
- 從需求對齊轉實作：要求保留設計決策、不可違反的限制、預期改動範圍

這樣做的目的不是把摘要變長，而是讓摘要知道自己服務哪一段工作。

另外，壓縮後有時還能把下一則訊息排進佇列，讓新 session 一開場就直接進入下一個動作。當你還在同一個目錄、同一個代理裡工作，這會非常順手。你不必自己搬運文件，也不必把脈絡交給外部工具。只要你要處理的是同一項工作在不同階段之間的轉場，壓縮通常就是很好的預設選擇。

### 📦 選擇四：交接給別的代理或別的地方

交接和壓縮看起來很像，因為兩者都在做脈絡整理。但它們解的不是同一個問題。

壓縮主要是在同一條工作線上，替下一個 session 整理脈絡。交接則是把這份脈絡寫成可攜帶的 markdown 文件，讓它能穿過邊界。

這個邊界可能是：

- 從 Claude Code 交給 Codex
- 從一個目錄帶到另一個目錄
- 從一個 repo 帶到另一個 repo
- 交給同事 review
- 現在先停下，之後另一個時間點再接續

也可能是你在做目前功能時，順手發現一個不相干的 bug。這時候你不一定要把它硬塞進眼前的 session。你可以先整理成交接文件，之後另開一個 session 專門處理它。

**為什麼交接的判斷條件反而比較單純？**
因為它的關鍵問題只有一個：你是不是要跨代理、跨目錄、跨 repo、跨人，或跨時間搬運脈絡？只要答案是是，就該優先考慮交接。

如果你不需要跨這些邊界，交接通常沒有壓縮順手。因為交接文件需要保存路徑，之後還要在新的 session 裡用檔案引用把它讀回上下文。這些額外步驟，只有在可攜性真的有價值時才值得。

#### 交接不是永久記憶

還有一個很容易被忽略的點：交接文件通常放在作業系統的暫時目錄。這表示它更像中轉站，不像正式知識庫。電腦重開、系統清理暫存資料後，它可能就不見了。

所以交接不能停在「文件生成成功」。後面至少要做一件事：

- 立刻餵給下一個代理
- 立刻傳給下一位同事
- 或把其中需要長期保留的結論，另寫進正式文件

交接很適合搬運脈絡，不適合拿來取代專案記憶。

### 🤖 選擇五：派出子代理

前面四種做法，重點都在「怎麼處理現在這段 session 的脈絡」。派子代理則不太一樣。它不是把整個 session 搬走，而是把一個邊界清楚、可以獨立完成的工作，交給另一個代理去做。

它最適合 AFK 工作。AFK 的意思很簡單：你不需要一直守在那裡，不需要一路回答問題，也不需要每個小步驟都拍板。你可以把任務丟出去，暫時離開鍵盤，等結果回來再驗證。

典型例子包括：

- 自動化 review
- 一次性的程式碼檢查
- 輸入輸出界線很清楚的研究工作
- 依規範掃描問題的例行任務

例如主要功能已經完成，你可以派一個子代理去看測試結果、需求與程式碼規範是否一致。主 session 則保留給你安排下一步，而不是讓主代理在同一條長對話裡不斷切換注意力。

但派子代理也不是免費。你要先確認三件事：

1. 工作邊界夠清楚。
2. 輸入資料夠完整。
3. 結果能用明確方式驗證。

如果任務需要你頻繁回覆、一路拍板，或它會去改和主線同一批檔案，子代理就可能帶來更多同步成本。這種情況下，繼續或壓縮往往比較合適。

### 🌲 實際上怎麼選：用一棵決策樹走

五種方法看起來很多，但其實不需要一次把五個選項全部拿來比較。比較好的做法，是用一連串問題把範圍慢慢縮小。

#### 第一步：現在還能不能安全繼續

先看兩件事：

- 上下文還有沒有足夠的聰明區空間
- 原本的主要史料是不是仍然很有價值

如果對話還短，背景剛談完，下一步又緊貼前面的細節，而且代理輸出依然穩定，那就繼續。phase boundary 不是強制你一定要切換，它只是提醒你應該做判斷。

#### 第二步：如果不能安心繼續，舊內容能不能完全丟掉

如果答案是可以，就清空。但這一步要很小心。你要特別檢查那些只存在於對話裡、卻沒有完全寫進程式碼的東西，例如：

- 某個限制是不是剛剛才確認
- 某個自然方案是不是已經被否決
- 某次失敗嘗試是不是揭露了不能再重走的路

只要其中有一項會影響下一步，舊內容就不是可拋棄的。

#### 第三步：如果不能丟掉，是否需要跨邊界搬運

這裡的邊界包含另一個代理、另一個目錄、另一個 repo、另一位同事，或未來另一個時間點。只要答案是需要，就選交接。因為此時你要的不只是新 session，而是一份能被帶走的脈絡文件。

#### 第四步：如果不必跨邊界，任務能不能獨立在背景完成

如果可以 AFK，例如自動化 review、固定格式的檢查或界線清楚的研究，就派子代理。主線不必停住，你可以先做別的事，等結果回來再驗證。

#### 第五步：前面都不是，就壓縮

如果你不能安心繼續，不能直接清空，不需要把工作搬到別處，也不適合派給獨立子代理，那最平衡的做法通常就是壓縮。把重要脈絡整理後帶進新 session，然後把下一階段要做什麼說清楚。

你可以把整棵決策樹記成下面這五步：

1. 還能安全繼續，而且前面的細節仍然有用，就繼續。
2. 不能繼續，但舊內容真的可丟掉，就清空。
3. 不能丟，而且要跨代理、跨目錄、跨 repo、跨人或跨時間，就交接。
4. 不必跨邊界，但工作能 AFK 獨立完成，就派子代理。
5. 其他情況，通常就壓縮，並把下一個 phase 的意圖講清楚。

這不是數學公式。什麼叫「還能繼續」、多少內容算重要、什麼任務算 AFK，都需要人的判斷。但這棵樹提供了一套共同語言，讓你不是只靠模糊感覺說「對話太長了」，而是能說清楚自己為什麼現在選壓縮、清空，或交接。

### ⚠️ 為什麼 auto-compaction 不能代替你的判斷

模型的上下文視窗有上限。當內容太多，工具可能直接報錯，所以很多 harness 會在接近緩衝區時自動做壓縮，也就是 auto-compaction。它看起來像很方便的保護網，因為你不用時時盯著容量。

但問題是，auto-compaction 通常只知道一件事：快滿了。它不知道你現在是在 grilling 的中段、實作的中段，還是剛好完成一個自然收尾點。

這差很多。

如果壓縮發生在真正的 phase boundary，摘要可以圍繞一個清楚目標來整理，例如保留規格、改動、測試結果和下一步 QA 任務。這時候壓縮比較像整理行李。

如果壓縮發生在階段中間，摘要就得自己猜：

- 哪些半成品算重要
- 哪些限制是關鍵
- 哪些討論只是閒聊
- 某個功能到底完成了沒有

這種猜測最危險的地方，是錯誤不一定立刻爆炸。新 session 可能還是會產生看似合理的程式碼，但方向已經悄悄偏掉。等到後面測試失敗，或整體設計風格開始互相衝突時，你才發現壓縮丟掉了真正重要的那一小段脈絡。

#### 實作中途尤其危險

實作往往需要連續記憶。代理可能剛建立出一套一致的命名風格、錯誤處理方式與檔案組織；也可能剛讀完一個關鍵檔案，正準備把多個決策合併成下一步實作。

如果這時 auto-compaction 介入，新 session 只拿到部分整理後的資訊，卻沒有完整保留那條正在成形的脈絡，接下來就可能出現這些問題：

- 改用另一套命名方式
- 忽然換一種錯誤處理習慣
- 重新走回你已經否決的設計
- 把未完成的部分誤判成已完成

最後也許某個單一測試還是會過，但整體程式碼卻開始出現兩套互相衝突的邏輯。這不是因為壓縮本身錯，而是因為它發生在錯的時間點。

#### 手動壓縮和 auto-compaction 的真正差別

差別不只是誰按下按鈕，而是有沒有工作意圖。

手動壓縮時，你可以先讓當前 phase 收尾，也可以明確說出新 session 的目標，例如：

- 我要進 QA，請保留規格、改動、測試與已知限制
- 我要從設計進入實作，請保留確認過的決策與不可違反的限制

auto-compaction 通常做不到這件事。它服務的是容量，不是工作結構。

所以不要把 auto-compaction 當成 session 管理策略。它比較像最後防線。真正穩定的做法，是在接近 phase boundary 時由你主動整理，讓壓縮發生在你知道自己正在從哪裡走到哪裡的時候。

### 🧱 把這套判斷變成日常工作流程

成熟的做法，不是永遠待在同一個超長 session，也不是看到長度上升就機械地一直壓縮。真正重要的是：每次轉場時，你都留一個很短的停頓，主動決定現在是哪一種邊界。

你可以把它套進很實際的工作節奏裡：

- grilling 做完後，先問接下來是直接實作，還是要交給別的代理
- 實作做完後，先問現在是不是要進 QA，還是還有同一輪的小修補要在原 session 完成
- 中途發現不相干的 bug 時，不要硬塞進主線；要嘛交接，要嘛另開獨立工作
- 有些檢查不需要你一路參與時，就派子代理，讓主線保持乾淨

#### 每次轉場前，至少回答這幾個問題

不管你最後選哪一種方式，轉場前都值得先把下面幾件事想清楚：

- 現在已經完成了什麼？
- 還有哪些事情沒有完成？
- 哪些選擇已經拍板？
- 哪些選擇仍然開放？
- 下一個 session 或下一位代理第一件事要做什麼？

這不需要你寫成一篇長報告，但它能大幅降低壓縮、交接或清空之後只剩下一團模糊摘要的風險。

#### 如果你選壓縮

就讓摘要明確指向下一個 phase。從實作轉 QA，就保留功能規格、改動檔案、測試結果和已知風險。從需求對齊轉實作，就保留確認過的設計與不可違反的限制。摘要不是越長越好，而是要讓新 session 一開場就知道自己的站位。

#### 如果你選交接

就確認交接文件真的被帶到目的地。因為它通常是暫時檔，不能只看到文件生成就以為任務完成。要交給別的代理，就在新 session 讀入它；要交給同事，就把它真的傳出去；若是把 bug 先停車，也要記住檔案位置與預計處理時機。

#### 如果你選清空

就做一次反向檢查：假設下一個 session 只看現在的程式碼，它能不能知道所有仍然有效的要求？如果不能，清空就是太早。只有當程式碼和正式文件已經足以承接後續工作，而且舊對話真的不再重要時，清空才會發揮最大效率。

#### 如果你選繼續

也要把它當成有條件的決定。意思不是「這個 session 會一直用到底」，而是「就目前來看，空間還夠，前面的細節也仍然值得保留」。下一個 phase boundary 一出現，你還是要重新走一次判斷。

### ✅ 最後收束：把轉場的主導權拿回來

真正成熟的工作方式，不是迷信大上下文，也不是迷信自動工具。代理可以做很多事，但它不會可靠地知道哪一段討論對你最重要，也不會自然理解下一個 phase 的真正目的。

所以關鍵不是讓工具永遠不停地跑，而是讓人來決定階段什麼時候結束，再讓工具在對的時機幫你整理。當你開始主動辨認 phase boundary，你就比較不會在笨區裡硬撐，也比較不會讓一次隨機觸發的 auto-compaction，在實作中途悄悄改寫工作的方向。
