# Context 如何累積成 Session

## Learning goal

看懂 AI coding agent 在每次回應前實際拿到的資訊，分辨 context、context window、turn、model provider request 與 session，並能根據工作情境判斷何時清空、壓縮或切換 session。

## Lesson

你要一個 coding agent 幫你改一個按鈕。它先讀 `package.json`，再去看路由、元件、樣式檔，接著提出修改方案，最後跑測試。幾分鐘後，你又補一句，要求它保留手機版排版。表面上看，你只是多說一句話；但對 agent 來說，這一句話不是單獨存在。它會連同先前的要求、自己剛剛讀過的檔案、工具執行結果、工具規格，還有啟動時就帶著的規則，一起進入下一次判斷。

這就是為什麼同樣一句補充，在新開的對話裡很快，在工作了半小時之後卻可能變慢。也是為什麼你明明只多加一個小條件，成本卻像把整段歷史一起重送了一遍。更重要的是，這也解釋了另一個常見困惑：你沒明講某個工具，它卻知道能用；你講過某個限制，它卻像沒看見。真正決定行為的，不是你「曾經說過什麼」，而是模型在產生下一個 token 前，實際拿到了什麼。這個總和，就叫做 context。若你想把詞彙先分清楚，可以回看 [[learn/ai-coding-crash-course/elements/context-and-session|Context、Context Window 與 Session]]；這一課的重點，是把那些詞放回真實工作流裡，看它們怎麼一起運作。

### 🧭 先看一次請求裡到底裝了什麼

當你在終端機輸入要求時，真正送進模型的內容，通常不是只有你那一句話。中間會有一層 harness，也就是把模型、工具和工作環境接起來的控制程式。它會把不同來源的資料整理成一次 request，再送給 model provider。

常見的資料大致有下面幾類。

| 資訊 | 內容例子 | 對回應的影響 |
| --- | --- | --- |
| system prompt，系統提示 | agent 的角色、工作規則、可用工具 | 決定 agent 應該怎麼做事 |
| 目前訊息 | 你這一刻的要求與限制 | 決定這一輪的目標 |
| 訊息歷史 | 前面幾輪的提問、回應、補充 | 提供背景與延續的約束 |
| 工具定義 | 讀檔、寫檔、執行命令的名稱與參數格式 | 告訴模型可以做什麼、怎麼呼叫 |
| 工具呼叫 | 模型要求讀某檔案或執行某指令 | 表示模型下一步想採取的行動 |
| 工具結果 | 檔案內容、測試輸出、錯誤訊息 | 提供環境回饋，讓模型繼續推理 |
| harness 注入資料 | 目錄資訊、權限提醒、額外規則 | 補上工作時必須遵守的條件 |

### 🔤 Token 才是模型真正看到的東西

這些內容進模型前，並不是以「資料夾」「工作記憶」或「一段段獨立欄位」的方式存在。harness 會先把它們整理成文字結構，再轉成 tokens。Token 是模型處理文字的基本片段。它可能是一個中文字、一部分英文單字、標點符號，或其他短片段。

所以，context 不是一種模糊印象，也不是只放使用者問題的地方。它是一次 request 裡，所有可供模型利用的工作資料總和。你在 log 裡看到的 system prompt、工具 schema、歷史訊息、工具結果，都可能是 context 的一部分。

**為什麼這個區分很重要？**

因為 agent 的行為，是由「實際收到的資料」決定的，不是由你主觀以為它應該知道什麼決定的。你說過某條規則，不代表那條規則在每一次 request 中都顯眼可見。你沒主動提某個工具，也不代表 harness 沒把工具定義塞進去。要診斷 agent，最先該問的不是它「聰不聰明」，而是它「這一刻到底看到了什麼」。

### 🔧 一次回應，背後可能是很多次 request

很多人把畫面上看到的一次回應，直接想成一次模型請求。但對 agent 來說，往往不是這樣。你輸入一段任務後，harness 可能先把 system prompt、工具定義、歷史和你的訊息一起送給模型。模型看完後，不一定立刻回答；它也可能先發出一個 tool call，也就是工具呼叫，要求去讀檔、搜尋，或執行測試。harness 收到後，會在你的電腦上執行工具，再把結果包回下一次 request 裡。

這個循環通常長這樣。

1. 你提出要求，要求被加入目前訊息。
2. harness 把 system prompt、工具定義、歷史和目前訊息送給模型。
3. 模型回傳文字，或回傳一個工具呼叫。
4. harness 執行工具，例如讀檔、搜尋或跑測試。
5. 工具輸出被包成工具結果。
6. harness 把前面的內容連同工具結果，再送給模型。
7. 模型根據新資料繼續回應，必要時再次呼叫工具。

### 🔄 同一輪工作，可能重複很多次循環

這個流程可能重複很多次。模型每多想知道一件事，就可能多一次呼叫與回傳。讀一個大檔案，也許就多出數千個 tokens。跑測試，可能只回一行成功訊息，也可能回一大段錯誤堆疊。

你在畫面上看到的，只是 agent 持續工作。模型實際經歷的，卻是一次又一次「重新收到一大包 context」。這件事直接影響成本、速度和穩定性。因為後面的每一次 request，通常都不只是新增一小段內容，而是把前面還要保留的東西再一起送一次。

### 🪜 Turn 跟 request，不是同一層概念

這裡一定要把兩個詞分開：turn 與 request。

- turn：你交付一個任務，到 agent 完成這一輪工作的整段互動。
- request：其中某一次真正送給 model provider 的請求。

一個 turn 可能只有幾秒，也可能持續幾小時。裡面可能只用到幾個 request，也可能因為不斷讀檔、修改、測試、修正，而產生數十次甚至數百次 request。

**為什麼這個區分很重要？**

因為你在 request log 裡看到很多 request，並不代表你真的和 agent 進行了很多輪人工對話。它們可能只是同一個 turn 裡的內部工具循環。反過來說，你只打了一句很短的指令，也可能觸發多個 request，因為 agent 需要探索專案、確認環境、比對輸出，才能回到你面前給出答案。

### 📦 新 session 也不是從零開始，因為有 system prompt

很多人第一次開 agent，會以為在自己輸入第一句話之前，模型眼前是一片空白。其實通常不是。harness 往往會先放入 system prompt。這是給模型的高層指令，裡面會交代它扮演什麼角色、有哪些工具、應該怎麼輸出、哪些安全規則要遵守，也可能說明自己正工作在某個終端機代理裡，以及讀檔、寫檔、搜尋、執行指令分別需要什麼參數。

換句話說，你在輸入第一句「你好」之前，context 就已經存在了。它有時只有幾千個 tokens；也可能因為工具很多、技能很多、整合很多、專案設定很多，一開始就很大。

這也是為什麼兩個用同一個模型名稱的 agent，最後行為卻可能差很多。差異不一定在模型本身，也可能在 harness 送出的 system prompt、工具定義和環境資訊不同。

### 🏢 可以把 system prompt 想成入場說明

這裡有一個很實用的類比。想像一位工程師走進一間辦公室。桌上已經先擺好了團隊規範、設備清單、安全要求和工作流程。工程師還沒接到今天的具體任務，但他已經知道自己是什麼角色、可以用哪些工具、哪些操作必須先確認。

對 agent 來說，system prompt 就有點像這份入場說明。它不是今天的任務內容，但它決定了今天做事的方式。這些預先放進去的資料，就是新 session 的起始 context。

如果你真的想理解自己手上的 agent 是怎麼工作的，最直接的方法之一，就是去看 request logs 裡的 system prompt。你可以觀察幾件事：它有沒有完整工具 schema，會不會附帶專案資訊，有沒有額外載入技能，或是不是混進了一些和當前任務無關的規則。這比憑感覺猜 agent 的個性可靠得多，因為你看到的是實際送出去的內容。

### 📏 Context window 是容量，不是品質保證

接下來要把 context 和 context window 分開。context window 可以理解成單次 request 能容納的最大 token 數量。它像一張有固定大小的工作桌。桌子可以很大，但總有邊界。當 system prompt、訊息、工具定義、工具結果和歷史全部加起來超過這個容量，request 就可能直接失敗。

不同模型的容量可能差很多。有些模型的 context window 大約是 128k tokens，有些則標示成 1M 或 1.1M tokens。這些數字的意思，是「最多塞得下多少」，不是「塞到這個量時仍能維持同樣好的判斷」。桌子可以放更多紙，不代表人就能同時把每一張都讀清楚。

### 🧮 用一個簡單估算看容量怎麼被吃掉

假設某個模型的 context window 是 128k tokens。

- 起始 system prompt：8k
- 工具定義：12k
- 你的任務與歷史：10k

這時候，還剩下大約 98k 的空間。接著 agent 讀進幾個大型檔案，工具結果多了 45k；之後又經過多輪測試與修正，歷史再增加 35k。總量這時已經接近 110k。

你會發現，明明還沒超過 128k，看起來還有餘裕，但只要下一次再來一段很大的工具輸出，就可能一下子逼近硬上限。更麻煩的是，即使還沒撞到上限，模型也可能已經開始在很多資訊中抓不到真正重要的限制。

**為什麼這個估算很重要？**

不是要你每次都手算 token，而是要你養成容量感。每一個新檔案、每一段新輸出、每一次新回應，都在占空間。當你知道起始的 system prompt 其實已經先吃掉一部分容量，你就比較不會把所有剩餘空間都誤以為是任務可自由使用的空間。

### 🧱 Session 是一路累積出來的工作脈絡

Session 可以把它想成工作階段。它不是模型腦中永久存在的記憶，而是多個 turns 累積後形成的上下文歷史。

第一個 turn，也許加入的是你的任務描述和 agent 的初步回答。第二個 turn，又加入你的補充條件、上一輪的結果，以及新的工具操作。第三個 turn 可能再加上測試輸出、錯誤訊息、修正方案。這樣一輪一輪疊上去，形成的就是現在這個 session。

用前面的按鈕例子來看會更清楚。

- 第一輪：需求和檔案結構
- 第二輪：讀取元件之後的工具結果
- 第三輪：修改內容和測試輸出
- 第四輪：你要求保留手機版排版，外加 agent 讀到的樣式檔

你眼裡看到的是一條連續對話；模型眼裡看到的，則是一份越來越長、越來越複雜的 context。

### ⚖️ Session 的好處與代價，是一起出現的

長 session 有明顯好處。agent 可以保留決策背景，知道你為什麼選某個資料結構，也知道前面哪個測試失敗過、失敗原因是什麼。這讓它不必每次都從頭摸索。

但代價也很直接。

- 歷史越長，容量負擔越大
- 每次 request 的輸入量可能越來越高
- 不再相關的檔案與輸出，會繼續留在後續判斷裡
- 錯誤嘗試與過時決策，可能持續干擾新判斷

早期讀過但現在已經無關的檔案、很長的測試 log、途中失敗過的探索，都可能繼續待在後面的 request 中。這些內容不一定立刻造成錯誤，但它們會占容量、占注意力，也可能稀釋真正重要的限制。

### 📚 三個概念最好用三個問題記

要避免混淆，最簡單的方法，是用三個問題去對應三個詞。

| 你在問什麼 | 對應概念 | 判斷方式 |
| --- | --- | --- |
| agent 這一刻能看到哪些資料 | context | 看目前 request 的全部輸入 |
| 一次最多能裝多少資料 | context window | 看模型的 token 容量限制 |
| 這些資料怎麼在互動裡慢慢形成 | session | 回看多個 turns 的累積過程 |

這三個詞不能互換。Context 是當下內容，context window 是容量上限，session 是累積歷史。

如果你把 session 誤認成模型的永久記憶，就會誤以為清空對話之後，它還應該記得全部舊事。如果你把 context window 誤認成品質保證，就會只在快滿時才注意，而忽略中間其實早就開始變亂。如果你把 context 誤認成只有使用者訊息，又會漏掉 system prompt 與工具輸出這些真正影響行為的部分。

### 💰 為什麼長 session 會拖累成本與品質

每一次 request，都要把模型這一刻做判斷所需的 context 送出去。這些 token 依照供應商的計價方式，可能形成輸入成本。就算某些固定前綴能透過 cache 降低價格，內容本身還是得被管理。

當 session 一直長下去，後面的 request 輸入量通常也會一起變多。你可以把這件事想成：每次你要請同一位工程師回答新問題之前，都把整場專案會議的逐字稿、所有讀過的檔案、所有測試輸出再重新堆到他桌上。若裡面有很多已經結束、不再 relevant 的討論，他就得花更多注意力重新掃過它們。最後也許還是能答對，但會更慢，也更容易抓錯重點。

模型也一樣。相關資料和不相關資料混在一起時，真正重要的限制可能被淹沒在一大段工具輸出裡。早期某個暫時決定，可能和後來更新後的決定同時存在；模型得自己判斷哪個還有效。甚至連某個錯誤探索的結果，也可能因為留在歷史裡，而被後續回合繼續參考。

重點是，這些問題不需要等到 context window 爆滿才會出現。很多時候，還在上限以下，品質就已經開始下降。

### 🧹 管理 session，常見就是三種動作

當一段 session 變長，你通常會在三個動作裡選一個。它們都在回答同一件事：目前累積的 context，還值不值得完整帶著走？

#### 1. 清空 context

清空，意思是移除目前對話累積的內容，讓你從比較乾淨的起點重新開始。不過要注意，system prompt 通常仍然會被 harness 重新注入，所以清空不等於完全沒有 context。

它適合的情況，是舊歷史已經不重要，或者你接下來要處理的是另一個獨立問題。比如你剛做完一個資料庫欄位修改，接著想問一個完全不相干的 CSS 問題。若新問題根本不需要前面的資料庫背景，那麼清空通常比硬帶著整段歷史更乾淨。

代價也很明顯：agent 不會自動保留上一段工作的理由和細節。真正需要保留的結論，最好先寫進檔案，或在新 session 裡重新交代。

#### 2. 壓縮 session

壓縮 session，也就是 compaction，是把很長的對話整理成較短的摘要，然後用這份摘要延續後面的工作。它適合還需要保留任務方向、關鍵決策、重要檔案和未完成事項，但又不想把整段冗長歷史原封不動帶下去的情況。

壓縮的好處，是把大量探索痕跡濃縮成較小的脈絡，讓你重新回到比較寬鬆的容量範圍。壞處是，摘要一定有取捨。它不是逐字保存。某些細節可能被拿掉，某段推理可能被改寫，某個臨時結論也可能失去原本的上下文。

所以壓縮前，最好先明確知道哪些東西不能丟。

- 驗收標準
- 已修改的檔案
- 目前失敗的測試
- 尚未解決的疑問
- 不能違反的設計決定

如果你只是叫 agent「隨便幫我摘要一下」，最後拿到的可能是一份看似完整、實際卻少了關鍵理由的文件。

#### 3. 切換到另一個 session

第三種作法，是另外開一個獨立 session，處理完旁支問題後，再回到原本主線。這在你想暫時處理另一個問題，但又不想污染主要工作歷史時特別好用。比如主要功能正在實作中，突然冒出一個獨立的型別錯誤；這時你可以先開另一個 session 調查它，解完再回來。

要記得的是，新 session 不會自動繼承舊 session 的全部 context。它通常只會有自己的 system prompt 和新的訊息歷史。如果新 session 需要知道某些結論，你要透過檔案、摘要或明確訊息，把必要資訊帶過去。

兩個 session 是兩條分開的工作脈絡，不是同一條記憶流的分支畫面。

### 🧪 最可靠的學習法，是直接看 request log

這些概念最容易在抽象層混掉，所以最有效的學法，是拿真實 request 來對照。你可以在測試專案裡開 request logger，先送出一個很簡單的問候，再送出一個要求讀檔的任務。第一個 request，先去找 system prompt 和工具定義。第二個任務，再看歷史有沒有把第一次問候也帶進去。接著觀察 agent 發出的工具呼叫，以及工具結果怎麼出現在後續 request 裡。

可以按下面的順序檢查。

1. 找出第一個 request 的 system prompt，記下 agent 的角色和高層規則。
2. 找出工具定義，觀察每個工具需要哪些參數。
3. 找到你的第一則訊息，確認它怎麼被包進請求。
4. 如果 agent 使用工具，追蹤工具呼叫和工具結果的配對。
5. 找到下一個 request，確認前一輪內容是否被重新帶入。
6. 再送出一輪訊息，觀察 session 怎麼增加新的歷史。

### 🔍 看 log 之後，你會更精確地理解 agent

這個練習通常會揭開一件很關鍵的事：agent 不是直接讀你的腦，也不是直接連到整個專案知識庫。它只能根據 harness 在那一次 request 中提供的文字來判斷。

某個檔案沒有被讀取，模型就不該被假定知道裡面的內容。某個規則沒有被注入，它就不該被假定會遵守。某個結果沒有留在可用脈絡裡，它就不該被假定仍然記得。

而且，不同 harness 的 system prompt 會不同，同一個 harness 的 prompt 也可能隨版本更新而改變。這代表你在別人的示範裡看到的行為，不一定能直接套用到自己的環境。看 log 的價值，就在於把模糊的說法改成精確的問題：它是從哪份資料知道這件事？那份資料是在哪一次 request 出現的？它現在還留在 session 裡嗎？

### 🧠 實務上，建立幾個 session 判斷時機就夠了

日常工作裡，你不需要每一輪都手動分析整份 context，但可以在幾個固定時機停下來判斷。

第一個時機，是任務切換。你從設計討論切到測試修正，或從功能開發切到另一個獨立 bug 時，先問自己：新任務真的需要整段舊歷史嗎？如果不需要，清空往往比繼續背著它更乾淨。

第二個時機，是 phase boundary，也就是工作階段的邊界。完成需求釐清之後，接下來是實作；完成實作之後，接下來是 QA。不同階段需要的資料不同。需求釐清重視決策和限制，實作重視檔案與架構，QA 重視變更範圍、測試命令和驗收條件。階段一變，session 是否也該整理，通常就值得重問一次。

第三個時機，是 agent 開始反覆誤解明明已經說過的內容。這時先不要急著把問題全怪在模型能力上。更常見的情況，是 context 的組成開始出問題了。重要規則是否真的還在目前 request 裡？有沒有互相衝突的舊訊息？是不是歷史太長，讓真正重要的東西被埋掉了？

### 📋 一張簡單表格，幫你快速決定動作

| 情況 | 優先考慮的動作 | 需要留意的代價 |
| --- | --- | --- |
| 舊歷史與新任務無關 | 清空 context | agent 會失去舊工作的理由和細節 |
| 仍需保留方向與決策，但歷史太長 | 壓縮 session | 摘要可能遺漏細節 |
| 暫時處理獨立問題，之後回到主線 | 切換另一個 session | 新 session 不會自動取得主 session 的內容 |
| 還在同一階段，且歷史仍然高度相關 | 繼續目前 session | context、成本與干擾會繼續增加 |

這張表不是機械規則，但它提供了一套很實用的共同語言。當你說「這個 session 太長了」，下一步就該追問：哪些 context 必須保留？當你說「我要重新開始」，也要說清楚你是要完全清空，還是帶著摘要進新 session。動作說得越精確，你和 agent 的協作就越不容易失焦。

### ✅ 最後把三個層次放回同一個場景

最後用一個完整場景收束。你在一個 session 裡，要求 agent 實作課程評論功能。它先看專案結構，再讀資料庫 schema、API route 和畫面元件。每一次讀檔，都是工具呼叫和工具結果；這些內容會被加入後續 request 的 context。之後你補一句，星等只能顯示整數。這句新要求也會進入 context。agent 便根據整段資料繼續工作。對你來說，這是一整輪互動；對模型來說，裡面包含很多次 request。多個 turns 一路累積，就是 session。

這時，context window 決定的是：單次 request 最多能裝多少 token。若 system prompt 已先吃掉一部分容量，工具定義和歷史又再吃一部分，真正留給新檔案和新結果的空間就更少。就算還沒撞到硬上限，太多不相關內容也可能讓模型更難抓住「星等只能是整數」這種關鍵限制。

當工作進入 QA 階段，你可以保留和變更直接有關的決策，清掉不再需要的大量探索，或先做壓縮，整理成一份較短的工作脈絡。若接下來要請另一個 agent，或在另一個目錄裡接手，也得把必要內容透過檔案或摘要明確傳過去。所有這些操作，本質上都在管理同一個核心資源：模型下一次回應時，真正能使用的 context。

掌握 context，你才知道 agent 為什麼知道某些事，也知道它其實不知道什麼。掌握 context window，你才知道容量限制和品質限制不是一回事。掌握 session，你才知道在長時間工作裡，該怎麼延續、整理或切換脈絡。把這三層放在一起，你就不會把 AI coding agent 當成一個擁有無限記憶的聊天對象，而會把它看成一位需要你幫忙整理工作資料的協作者。
