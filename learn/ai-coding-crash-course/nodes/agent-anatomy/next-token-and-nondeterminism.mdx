# 次一 token 預測與代理輸出的變化

## Learning goal

看懂 AI coding agent 為什麼常常在看似相同的任務下給出不同輸出、走不同路徑，並建立一個夠實用的心智模型：模型不是先想完整答案再吐出來，而是在當下上下文裡逐步做次一 token 預測（next-token prediction）；只要其中某一步不同，後面的整段回答、工具使用方式、甚至程式修改策略都可能跟著分岔。理解這件事之後，你會更知道什麼時候該接受變化，什麼時候該用驗證與權限邊界補上可靠性。

## Lesson

### 📝 你看到的不是故障，而是生成系統的正常表現

如果你已經開始用 AI coding agent，大概看過這種情況。同一個需求，第一次它先讀檔，再補測試，最後才改實作。第二次它卻先全域搜尋，再去碰一個你原本沒想到的函式。第三次更明顯，需求明明一樣，它卻把注意力放在命名、型別，或某種測試寫法上，像是走進另一條路。

很多人遇到這件事，第一反應是覺得它不穩。好像哪裡壞了，或是哪個參數沒有設好。這個反應很自然，因為我們平常習慣的軟體大多是這樣：輸入一樣，輸出就應該一樣。

但語言模型不是這種工具。你不能把它想成先在腦中想完整份答案，再一次吐出來。更接近的說法是，它會看著現在手上的上下文，逐步決定下一小段該接什麼。這個基本單位就叫 token。token 不是一定等於一個字，也不一定等於一個單字，它只是模型切分文字後實際拿來運算的單位。

所以，所謂「次一 token 預測」，意思不是模型先找到全局唯一正解，而是它在每一個位置都回答一個局部問題：照現在這段脈絡，下一個最合適的 token 是什麼。

**為什麼這件事很重要？**
因為它會直接改變你怎麼理解代理。你表面上看到的是它在規劃、搜尋、推理、選策略，但底層真正一直在發生的，仍然是一步一步的次一 token 預測。

### 💡 token 預測怎麼變成代理行為

這裡最容易卡住的一點是：代理明明看起來像在做高階決策，為什麼說它底層只是逐 token 生成？

答案是，上下文裡裝的東西很多。系統提示、工具說明、你剛剛下的要求、專案檔案內容、工具執行後的回傳、前面已經生成出的文字，全部都會一起進入模型當下可見的脈絡。模型就在這個脈絡裡，繼續預測下一個 token。

當這種過程持續往前走時，某些 token 序列會長得像規劃，某些會長得像分析，某些會長得像操作指令。於是你看到的表面現象，就像它在「先想好策略再行動」。但如果往下拆，真正的機制還是一樣：

1. 讀取當前上下文
2. 預測下一個 token 的可能分布
3. 選出一個 token
4. 把它接回上下文
5. 繼續預測下一個 token

也就是說，代理的高階感，是從低階生成機制裡湧現出來的，不是另一套完全不同的引擎。

### 🔧 為什麼同一題會走出不同路

現在來看最核心的現象：為什麼同一個任務，代理常常不只「講法不同」，連做法都不同？

原因很簡單。模型在很多位置上，不只一個候選 token 說得通。它通常會算出一個機率分布，而不是只給一個絕對答案。你可以把它想成這樣：

| 當前位置 | 可能續寫 | 直覺含義 |
| --- | --- | --- |
| 開始做事前 | 先讀檔 / 先搜尋 / 先列計畫 | 不同起手式都合理 |
| 解釋問題時 | 改測試 / 改命名 / 改型別 | 不同重點都可能成立 |
| 呼叫工具前 | 看某個檔案 / 跑某個命令 / 問使用者 | 不同行動分支都可能被選到 |

接著，還有第二個角色會進來：sampler。sampler 是根據模型給出的機率分布，實際挑出要走哪個 token 的程序。

你可以把整個過程拆成兩步：

- 模型先算出「哪些 token 比較可能」
- sampler 再從這個分布裡選一個真正往下走

這就是為什麼輸出不一定完全固定。只要某個候選 token 的機率不是零，它就仍然有機會被選中。也只要某一步選到了不同 token，後面的上下文就變了。上下文一變，下一步的候選機率分布也跟著變。於是差異會一路往後傳。

### ⚡️ 小差異為什麼會長成大分岔

這種分岔一開始常常非常小。可能只是第一句寫成「我先檢查相關檔案」，而不是「我先搜尋相關定義」。可能只是多提到某個測試，少提到某個型別。你當下甚至不會覺得那有什麼差別。

但在逐 token 的系統裡，小差異不是留在原地。它會成為下一步的條件，而下一步又會再生成新的差異。

你可以把它想成走路時第一個岔口只偏了一點點：

- 前面 5 公尺，看起來還差不多
- 走到 50 公尺，路線已經有點不一樣
- 走到 5 公里，可能完全不是同一條路

這就是為什麼同一個 agent 有時會像「換了一個人」。不一定是它突然壞掉，而是它在前面幾步已經走上另一條同樣合理的續寫路徑。

### 🧭 示範不是腳本，重點是可行路徑

這個心智模型還會幫你重新看待教學影片或別人的 demo。很多人看到講師示範代理怎麼做事，就會默默期待自己也該得到幾乎一樣的步驟、一樣的檔案修改順序，甚至一樣的句子。

這種期待通常會失望，因為示範比較像是「某一次被走出來的可行路徑」，不是唯一正解。

當底層機制是次一 token 預測時，教學示範真正有價值的地方，通常有三個：

1. 它示範了怎麼組上下文
2. 它示範了怎麼讓代理使用工具
3. 它示範了怎麼驗證結果

反過來說，示範的價值通常不在於逐字可重播。你學的不是一份腳本，而是一套工作方式。

### 🌡️ temperature 會影響變化，但不能把世界變成完全固定

很多人走到這裡，下一個問題會是：那把 temperature 調低，不就比較穩了嗎？

是的，會比較穩，但要精確理解它做的是什麼。temperature 是用來調整取樣分布形狀的參數。

你可以先抓直覺：

| temperature | 分布效果 | 常見體感 |
| --- | --- | --- |
| 高 | 分布比較平 | 比較發散、比較敢探索 |
| 低 | 分布比較集中 | 比較收斂、比較保守 |

高 temperature 時，原本不是最熱門的候選也比較容易被選中。低 temperature 時，少數高機率候選會吃到更大的權重，行為通常看起來更一致。

但這裡有個關鍵限制：低 temperature 不等於「一定對」，也不等於「一定完全一樣」。

因為模型不是在玩單字填空，而是在連續生成一段要讓人感覺自然、有效、可接受的整體輸出。局部最可能的選擇，不一定能導向整體最好的結果。

### 🪤 為什麼不能永遠只選最可能的 token

課程裡有一個關鍵詞叫 likelihood trap。你可以把它理解成「局部最可能，不代表整體最好」這個陷阱。

如果你每一步都只追求當下最高機率的 token，表面上好像最穩，實際上可能掉進另一個問題：輸出變得過度僵硬、重複、平庸，甚至一路走進看似安全但其實不好用的解法。

**為什麼這很重要？**
因為人類真正喜歡的說明、推理和程式設計過程，通常不只是局部最穩。它還需要一些探索空間，需要有機會走到第二條、第三條也合理的路。

放到 coding agent 的情境裡，這代表：

- 第一個修法不一定最好
- 最保守的補丁不一定最乾淨
- 最常見的命名不一定最貼切
- 最直覺的測試切法不一定最可維護

所以，適度的非決定性不是純粹缺點。它有時也是模型提出替代解法、展現彈性、碰到更好抽象的來源。

### 🤖 為什麼在 agent 場景裡，非決定性更重要

如果只是聊天，輸出不同也許只是文風不同。但在 AI coding agent 裡，非決定性影響的不是只有語氣，還包括行動。

同樣一個任務，代理可能會：

- 選不同的搜尋策略
- 先讀不同的檔案
- 先改測試或先改實作
- 呼叫不同工具
- 決定不同的修補方案

如果它有權限改檔、跑測試、執行命令，這些差異就會直接落到真實世界。你面對的不是「回答 A」和「回答 B」，而是「工作流程 A」和「工作流程 B」。

這也是為什麼次一 token 預測聽起來很抽象，最後卻會變成很實際的工程問題。只要代理能動手，生成差異就不再只是文字差異，而是行為差異。

### 🧪 temperature 設成 0，還是不一定完全重現

這裡還有一個很常見的誤解：很多人以為把 temperature 設成 0，就等於把模型變成傳統 deterministic function，也就是完全決定性的函式。

事實不是這樣。temperature 0 通常會讓結果更集中，但不保證每次完全一模一樣。

一個重要原因是，大型語言模型的底層計算高度平行。很多矩陣運算和內部步驟不是單線程依序跑完，而是同時展開。這種平行計算在不同硬體、不同批次、不同執行時序下，可能出現非常細微的數值差異。

一開始這些差異可能小到幾乎看不出來，但只要它足以讓某一步的候選排序發生極小改變，後面逐 token 展開時就有機會被放大，最後形成不同輸出。

所以，temperature 0 比較像是：

- 壓窄可走的路
- 讓模型更常落在相似答案附近
- 降低變化幅度

但它不是把生成式模型退化成傳統完全可重播的函式。

### ✅ 好用的代理，不是每次都重播，而是結果能被檢查

一旦你接受這個事實，你評估 agent 的標準就會成熟很多。

新手最常用錯的指標是：昨天成功一次，今天就應該原封不動再成功一次。如果沒有，就覺得不可靠。

更成熟的判準不是「它是否逐步重演」，而是「它即使走不同路，最後能不能穩定到達可接受結果」。

這代表你要關心的是：

- 結果能不能驗證
- 偏差能不能及早暴露
- 高風險操作能不能被約束
- 不同路徑能不能收束到相同品質門檻

這也是為什麼在 agent workflow 裡，驗證通常比重現更重要。

### 🛡️ 驗證比重現重要，權限比信任重要

對寫程式來說，真正能提高可靠度的，通常不是逼模型每次講一模一樣的話，而是讓它不管走哪條路，都得通過同樣的檢查。

常見的檢查包括：

- 測試
- 型別檢查
- lint
- 靜態分析
- 建置
- 快照比對
- 關鍵輸出格式約束

只要每條路都要過同一組門檻，代理就算不完全可重播，整體可靠度仍然可以很高。

另一個直接結論是，不要把權限設計建立在「它通常都很合理」這種期待上。非決定性真正麻煩的地方，不是它每次都出錯，而是它永遠存在非零機率走出奇怪、偏題、笨拙，甚至有害的行動。

這裡的「非零」非常關鍵。只要任務夠多、上下文夠長、場景夠雜，你早晚會碰到一些不理想路徑。

所以在代理工程裡，最小權限原則不是額外加分，而是日常常識：

1. 能只給讀權限，就先不要給寫權限
2. 能先 ask-for-confirmation，就不要直接執行破壞性命令
3. 能先在沙盒試，就不要直接碰正式環境

### 🧰 harness 會決定非決定性是混亂還是可控探索

這也能解釋為什麼同一個模型，放進不同 harness，體感會差很多。

harness 可以理解成包住模型的一整層操作環境。它會決定很多事：

- 模型能看到哪些上下文
- 能不能使用工具
- 工具輸出怎麼回餵進上下文
- 哪些操作要先批准
- 失敗後怎麼回退

模型底層的非決定性不會消失，但系統設計可以決定，這種非決定性最後是被放大成混亂，還是被收束成可接受的探索。

好的代理系統，不是幻想把模型變成完美決定論機器。它做的事比較務實：承認模型會漂、會分岔，然後用流程、邊界、驗證和回退機制，把漂移控制在成本可接受的範圍內。

### 🧠 這個心智模型也會改變你怎麼寫提示

理解次一 token 預測，還有一個很實際的好處：你比較不會過度擬人化代理。

它不是像人一樣先完整思考，再突然改變心意。更多時候，是因為當下上下文把某條續寫路徑推高了，所以它就沿著那條路往前走。這不表示模型不能表現出規劃感或反思感，而是提醒你，那些高階表現仍然來自低階生成機制。

對使用者來說，這會直接影響你怎麼下指令。既然每一步都深受上下文影響，那你放進去的東西就很重要，包括：

- 成功標準寫得夠不夠清楚
- 限制條件有沒有說明白
- 工具輸出格式穩不穩定
- 禁止事項有沒有先講清楚
- 任務有沒有切成容易驗證的小步驟

這些東西都在塑造後面的 token 機率分布。你無法消滅非決定性，但你可以透過更好的上下文設計，把合理變化和危險漂移之間的距離拉大。

### 🌱 非決定性不是純負面，它也是彈性來源

最後要補一個很容易被忽略的平衡點。非決定性不是只有壞處。很多時候，它正是模型有創造性、能給替代方案、能跳出模板化答案的來源。

如果每一步都只能走最可能的 token，模型常常會變得過度保守。對寫作是這樣，對寫程式也常常是這樣。某些 bug 的好修法，未必是第一個最保守的補丁。有時候第二條、第三條略為不同的推進路徑，反而會帶來比較優雅的抽象、比較乾淨的測試切法、比較好的命名。

所以，成熟的做法不是要求 agent 永遠不要變，而是知道什麼時候應該容許它變，什麼時候應該嚴格卡住它。

你可以這樣理解：

| 任務類型 | 可接受變異 | 管理方式 |
| --- | --- | --- |
| 探索設計方案 | 較高 | 容許多條路並比較結果 |
| 重寫說明、發散修法 | 較高 | 鼓勵替代方案 |
| 批次修改、migration | 較低 | 強化驗證與審核 |
| 危險命令、正式資料操作 | 很低 | 嚴格權限、確認、沙盒 |

### 🎯 最後把它收束成一個實用結論

AI coding agent 不是在重播一條唯一正確的內部腳本。它是在當前上下文裡，一步一步續寫下一個 token。只要其中某一步不同，後面的解釋、計畫、工具使用方式，甚至程式修改策略，都可能跟著分岔。

一旦你真的接受這個事實，你就不會再把每次差異都當成神祕異常，也不會迷信只要把某個參數調到底，就能換來完美重現。你會把注意力放到更有用的地方：

- 提供更好的上下文
- 把任務拆成可驗證的小步驟
- 對高風險操作加上權限和確認
- 用測試與檢查當最後裁判

到這一步，非決定性就不再只是讓人焦躁的雜訊。它會變成你設計代理工作流時必須正視的基本條件，也是你在不同任務中必須學會管理、甚至有時可以善用的特性。
