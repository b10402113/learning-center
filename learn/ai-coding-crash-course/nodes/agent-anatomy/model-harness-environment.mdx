# 模型、外殼與環境如何組成代理

## Learning goal

學完這一課，你能從實際工作場景辨認模型、外殼、環境與代理四個層次，理解它們如何合作完成一次編程任務，並在代理表現不佳時判斷應該改善哪一層，而不是只憑直覺更換模型。

## Lesson

你在終端機或編輯器裡對 AI coding 工具下了一個要求：把購物車頁面的按鈕改成禁用狀態，順手補上測試。接著你看到它讀檔、搜尋、改程式、跑測試、再把 diff 顯示出來。整個過程很容易讓人用一句話概括：AI 在幫我寫程式。

但只要你開始排錯，這句話就不夠用了。

有時候，問題是模型其實理解了需求，卻根本沒有讀檔能力。有時候，問題不是理解，而是工具被權限擋住，無法真的執行測試。還有時候，工具和權限都正常，真正卡住的是專案本身缺依賴、測試壞掉，或工作區缺少必要檔案。這三種情況表面上都像「代理表現不好」，但修法完全不同。

所以這一課要做的，不是再介紹一串品牌名稱，而是給你一個更穩的拆解方式：把代理看成幾個合作中的層次，而不是把所有東西都混成一團。

### 📝 先從你真的看見的行為開始

我們先不要急著定義術語，先看一次常見的工作流程。當你要求代理修改某個功能時，它通常會經過下面幾步。

1. 讀取你的要求。
2. 判斷需要去哪些地方找資訊。
3. 呼叫讀檔、搜尋或列目錄工具。
4. 看工具回傳的結果，推測該改哪些檔案。
5. 產生新的內容，並呼叫寫檔工具。
6. 執行測試、型別檢查，或其他驗證命令。
7. 根據錯誤輸出繼續修改，或向你回報結果。

你在介面上看到的是一段連續對話，但底下其實是兩種事情在輪流發生。

- 一種是生成：系統在產生下一段文字或下一個動作。
- 一種是操作：系統真的去讀檔、寫檔、跑命令。

**為什麼這個區分很重要？**
因為「會說下一步是什麼」和「真的做得到那一步」不是同一件事。理解代理，第一個習慣就是把這兩件事分開看。

### 💡 模型是產生下一步的核心引擎

先看第一層：模型（model）。

模型的工作很單純，但也很關鍵。它接收輸入，根據目前看到的文字和上下文，推算接下來最合理的輸出。這個輸出可以是普通說明，也可以是結構化資料，例如某個工具名稱、參數、路徑，甚至一段準備寫入檔案的內容。

所以從功能上說，模型的核心任務就是一件事：**根據輸入，產生下一步輸出。**

你可以把模型想成汽車的引擎。引擎決定車子有多大馬力、爬坡有多穩、加速有多快。放到 AI coding 的世界裡，Opus、Sonnet、GLM 5.2、Fable 這些名稱，說的就是不同的模型。它們的差別可能在理解能力、推理能力、速度、成本，或對長上下文的處理方式。

但引擎不是整台車。

模型本身只處理輸入和輸出。它沒有天然的手去打開你的檔案，也沒有天然的眼去查看資料夾，更沒有天然的權限去執行 `npm test`。如果模型輸出一段像這樣的內容：請執行某個命令、請寫入某個檔案，那在它被外部系統接手之前，本質上仍然只是輸出文字。

### 🔧 模型不只會說話，也會輸出結構化動作

這裡有一個初學者很容易忽略的點：模型輸出的不一定是給人看的自然語言。

它也可能輸出像下面這樣的結構化內容。

```json
{
  "tool": "write_file",
  "path": "src/cart/button.tsx",
  "content": "..."
}
```

看到這種格式時，很多人會直覺覺得「它已經開始改檔了」。其實還沒有。對模型來說，這仍然只是輸出。真正的改檔要等另一層系統讀懂這段資料，確認工具存在、參數格式正確、路徑合法、權限允許，然後才會真的去動作業系統。

**為什麼這點很重要？**
因為當代理說自己改好了，但你的專案裡根本沒變化，問題不一定是模型在胡說，也可能是後面的工具流程沒有接上，或工具執行失敗後結果沒有正確回傳。

### ⚡ 模型還有一個根本限制：它本身是無狀態的

模型還有一個非常重要的限制，就是它本身是無狀態的，也就是 stateless。

這句話的意思不是它完全不能處理多輪對話，而是它不會在自己的內部永久保留記憶。一次請求結束後，模型不會自己記住剛才發生的事。下一次如果你還想讓它知道前面做過什麼，外部系統必須把相關上下文重新整理，再送回模型。

所以你以為它「一直記得」整段 session，實際上往往是外層系統把對話紀錄、工具結果、當前狀態重新打包，再餵一次給模型。

這個觀念很關鍵，因為它會影響你怎麼看待代理的失誤。

- 如果上下文沒有被重新帶回去，模型可能像第一次看到任務。
- 如果工具結果被截斷，模型可能只看到一半資訊。
- 如果 session 管理做得不好，模型即使夠強，也可能在第二十步開始迷路。

也就是說，很多看似是「模型忘了」的問題，其實不是模型層單獨造成的。

### 📝 環境是代理實際工作的世界

第二層是環境（environment）。

你可以把環境理解成代理真正工作的世界。對 AI coding 來說，這通常不是抽象空間，而是非常具體的東西：本機檔案系統、某個 git repository、可執行命令的 shell、專案依賴、測試腳本、設定檔、權限邊界，還有你允許它接觸的資料範圍。

如果模型像引擎，環境就像道路、地圖、車庫和交通規則的總和。引擎再強，沒有道路也跑不起來。

在實務上，環境常常至少包含下面幾類資訊。

| 環境中的部分 | 代理從中得到的東西 |
| --- | --- |
| 原始碼檔案 | 專案目前的實作、命名與結構 |
| 測試檔案 | 可驗證的行為與預期結果 |
| git 狀態 | 分支、未提交修改、近期變更 |
| package.json 或其他設定 | 可用腳本、依賴、工具入口 |
| shell 與作業系統 | 執行命令、查看輸出、啟動服務 |
| 權限與資料範圍 | 哪些路徑或服務可以被存取 |

**為什麼環境很重要？**
因為代理不是在真空裡寫程式。它永遠是在某個具體世界裡工作，而這個世界提供多少資訊、多少工具、多少可驗證性，直接決定它能做什麼。

### 💡 環境有持久性，這是它和模型很不一樣的地方

模型的輸出是一輪一輪生成的，但環境通常有持久性。

你把一個檔案寫進專案，結束這次對話後，檔案通常還在。你建立一個 git branch，關掉終端機後，分支也還在。你安裝了一個依賴，之後再跑測試時，它仍然會影響結果。

這些都說明了一件事：環境不是一段對話內容，而是一個會留下痕跡的工作場所。

這也是為什麼同一個模型放進不同環境，表現會差很多。假設你請代理修一個函式。

- 如果函式就在工作區裡，代理可以讀到它，事情就有機會順利進行。
- 如果函式只存在於你本機，但代理所在的環境根本看不到那份檔案，它再聰明也只能猜。
- 如果測試腳本不存在，代理改完之後就沒辦法驗證。
- 如果依賴沒裝好，即使改法是對的，驗證流程也可能報錯。

這些都不是抽象的「能力不足」，而是環境沒有提供足夠條件。

### 🔧 環境也可能是虛擬的，不一定是你的本機

很多人一想到環境，就只想到自己的 repository 和 terminal，但環境不一定是本機。

在某些產品裡，代理工作的地方可能是平台提供的虛擬空間。例如產品可能給它一個受控的檔案區、一個瀏覽器、一個程式執行沙箱，或有限的網路能力。這時代理面對的不是你的整台電腦，而是一個產品刻意設計出來的工作世界。

這種差異很實際。

- 本機環境通常更貼近真實專案，能看到你的 repository、shell 和 git 狀態。
- 虛擬環境通常更安全、可控，但看到的檔案、可用命令、網路範圍和保存方式都可能不同。

所以當兩個人都說「我在用同一個模型」時，實際成果仍然可能差很多，因為他們工作的環境未必一樣。

### ⚙️ 外殼是把模型接上環境的那一層

第三層是外殼（harness）。

如果模型負責產生下一步，環境負責提供真實世界，那外殼就是中間的接線層。它把模型和環境接起來，讓模型不只會輸出文字，還能透過規則化方式去使用工具、讀取資料、執行操作，再把結果拿回來繼續推進任務。

外殼通常是你實際接觸到的產品介面，例如一個命令列工具、一個編輯器整合、一個應用程式，或某種 session 管理系統。Claude Code 和 Codex 這類工具，就可以把它們看成外殼。

它們典型會做幾件事。

1. 整理要送進模型的上下文。
2. 告訴模型有哪些工具可用。
3. 定義每個工具要用什麼格式呼叫。
4. 接收模型產生的工具要求。
5. 檢查權限、格式和安全規則。
6. 真正呼叫工具去碰環境。
7. 把工具結果整理後再送回模型。

這一層非常像翻譯兼調度中心。模型說「我想讀這個檔案」，外殼把這句話翻成實際工具操作；環境回來說「檔案不存在」或「測試失敗」，外殼再把結果包成模型能理解的上下文。

### 📝 一次完整互動，其實是這樣流動的

把流程簡化後，可以寫成下面這樣。

```text
使用者要求
    ↓
外殼整理系統提示、工具描述與對話
    ↓
模型產生文字或工具呼叫
    ↓
外殼執行工具
    ↓
環境回傳檔案內容、命令輸出或錯誤
    ↓
外殼把結果加入上下文
    ↓
模型產生下一步
```

這張流程圖的重要性在於，它讓你看到代理不是「想一下就完成」，而是反覆在生成與操作之間來回。

**為什麼這個流程很重要？**
因為只要其中任何一段斷掉，整個代理行為就會失真。

- 外殼沒把正確工具宣告給模型，模型就只能空想。
- 工具執行失敗但結果沒回傳，模型可能以為動作成功。
- 工具結果太長被截斷，模型可能做出錯誤判斷。
- 權限規則太緊，模型會一直提出做不到的動作。

所以很多使用者感受到的「代理個性」和「代理工作能力」，其實有很大一部分是外殼塑造出來的。

### 🔧 外殼不只接線，還會帶入規則、工具與安全邊界

外殼通常不只是單純轉發。它還會加入一整套模型原本沒有的工作規則。

例如，它可以：

- 告訴模型有哪些工具可以用。
- 指定工具的輸入格式。
- 加入系統提示，規範回應方式。
- 保存目前的 session 狀態。
- 顯示修改 diff。
- 攔截危險命令。
- 要求某些動作先經過你確認。
- 限制可讀寫的路徑範圍。

這些設計會直接影響代理的表現。即使底層使用同一個模型，兩個不同外殼也可能讓它呈現完全不同的能力。

| 情況 | 模型一樣嗎 | 外殼能力 | 使用者感受到的結果 |
| --- | --- | --- | --- |
| 只有聊天輸入 | 可能一樣 | 沒有讀寫檔案與測試工具 | 只能回答問題，不能實作 |
| 有讀檔與搜尋工具 | 可能一樣 | 能探索專案內容 | 能分析專案並提出修改 |
| 有寫檔、shell、驗證流程 | 可能一樣 | 能操作環境並取得回饋 | 能完成多步驟開發任務 |

這也是為什麼同一個模型放在不同產品裡，使用體驗會差很多。差異不一定都來自模型本身，也常常來自外殼把什麼接上了、把什麼擋掉了。

### 💡 代理不是神祕新元件，而是三層組合後的整體

現在我們可以回到最重要的定義。

代理（agent）不是躲在模型後面的一個神祕盒子。它其實是模型、外殼、環境三者接起來之後，形成的一個可行動系統。

最短的公式就是：

```text
agent = model harnessed in an environment
代理 = 被外殼接到環境中的模型
```

這句話裡最關鍵的字是 harnessed。你可以把它理解成「被接上」「被裝配」「被賦予工具能力」。單獨一個模型只能產生輸出，但當它被外殼接入一個真實環境，就開始能探索、修改、驗證、回報，於是看起來像一個在工作的代理。

這三層的分工可以整理成一張表。

| 層次 | 它負責什麼 | 典型例子 |
| --- | --- | --- |
| 模型 | 根據輸入產生下一步輸出 | Opus、Sonnet、GLM 5.2、Fable、GPT 5.5 等模型 |
| 外殼 | 提供工具機制、上下文整理、權限與流程控制 | Claude Code、Codex、其他命令列或產品外殼 |
| 環境 | 提供檔案、命令、依賴、持久狀態與資料範圍 | 本機檔案系統、shell、git repository、產品虛擬工作區 |

### ⚡ 用常見產品來看，會更容易分清楚

這個拆解方式最有用的地方，是它能幫你穿透品牌名稱。你不用只記「我在用哪家 AI」，而是可以精準描述：模型是什麼、外殼是什麼、環境又是什麼。

例如：

| 例子 | 模型層 | 外殼層 | 環境層 |
| --- | --- | --- | --- |
| 終端機編程代理 | Opus 或 Sonnet | Claude Code | 本機檔案系統與 shell |
| 另一種 CLI 代理 | GLM 5.2 | Pi 或其他命令列外殼 | 專案檔案與可用命令 |
| 對話產品中的程式工作 | GPT 5.5 等模型 | ChatGPT 的產品外殼 | 產品提供的虛擬工作區 |

表格裡真正值得你記住的，不是品牌，而是三個問題。

1. 哪個部件負責產生輸出？
2. 哪個部件把輸出轉成工具操作？
3. 代理實際看到和修改的世界在哪裡？

只要能回答這三個問題，你對系統的理解就會比只記產品名稱穩很多。

### 🔧 真實世界的邊界不一定整齊，灰區很正常

現實系統裡，三層邊界不會永遠切得乾乾淨淨。`npm run test` 就是一個很好的例子。

從一個角度看，它屬於環境，因為命令定義在 `package.json`，是專案的一部分。從另一個角度看，它也和外殼有關，因為外殼要不要允許 shell、要不要幫模型呼叫它、要不要對某些命令做安全限制，都會影響它能不能被使用。

所以遇到灰區時，重點不是硬把每個東西塞進唯一分類，而是搞清楚它在流程裡扮演什麼角色。你可以問幾個更有用的問題。

- 這個能力是誰提供的？
- 誰負責真的執行它？
- 執行結果會回到哪裡？
- 它受哪一套權限和規則控制？
- 你修改它時，主要會影響模型、外殼，還是環境？

這種問法比爭論某個東西「到底算哪一層」更有工程價值。

### 📝 同一個症狀，可能來自不同層

這也是代理排錯最容易踩坑的地方。你看到的是一個症狀，但原因可能藏在不同層。

例如 `npm run test` 跑不起來，至少可能有三種完全不同的原因。

| 表面症狀 | 可能出問題的層 | 實際可能原因 |
| --- | --- | --- |
| 找不到 `npm run test` | 環境 | `package.json` 根本沒定義 script |
| 明明有 script 卻不能跑 | 外殼 | 外殼沒有提供 shell，或權限規則擋住命令 |
| 命令跑了但代理解讀錯誤 | 模型 | 模型誤判測試輸出的真正失敗原因 |

這張表的重點是：不要被表面現象騙了。你看到的是「測試沒過」，但追下去時，要沿著完整流程回溯，而不是直接把責任丟給模型。

### 💡 多數人能真正調整的，往往不是模型，而是外殼與環境

很多人一遇到代理失敗，第一反應就是換模型。這不是完全錯，因為模型能力確實重要。但在現實裡，大多數使用者很難自己訓練或重做一個大型模型。那需要龐大的資料、算力、工程團隊和評估流程。

對多數開發者來說，模型通常是你能選擇的東西，但不是你能深改的基礎設施。

相較之下，外殼和環境常常是你更有機會動手改善的地方。你可以：

- 清理工作區，讓專案結構更清楚。
- 補上 README，說明入口點與執行方式。
- 確保測試腳本存在而且可跑。
- 補齊依賴與設定。
- 調整權限，讓安全和可用性取得平衡。
- 改善工具描述，讓模型更知道哪些工具該怎麼用。
- 建立穩定的回饋迴路，讓代理能自己驗證修改。

這些改動不會直接改變模型參數，卻常常比單純換模型更有效。

### ⚙️ 一張實用的排錯表

下面這張表可以當作你日後診斷代理問題的起點。

| 你觀察到的問題 | 優先檢查的地方 | 可能的改善 |
| --- | --- | --- |
| 代理說看不到檔案 | 環境與工具範圍 | 確認工作目錄、路徑和讀檔工具 |
| 代理想執行命令卻被擋住 | 外殼權限 | 調整允許規則，保留危險操作的人工確認 |
| 代理寫完後無法驗證 | 環境回饋迴路 | 補上依賴、測試腳本和清楚的錯誤輸出 |
| 代理重複犯同一個流程錯誤 | 外殼提示與環境文件 | 提供穩定指引、技能或專案內規 |
| 代理掌握了資訊卻做出錯誤判斷 | 模型能力或上下文品質 | 改善任務拆解、提供關鍵資料、調整模型選擇 |

**為什麼這張表有用？**
因為它逼你把「代理不行」改寫成更精確的工程問題。只要問題問得更準，修正方向通常也會更快浮現。

### ⚡ 用四層語言描述自己的 setup，判斷會更準

當你之後描述自己的 AI coding 工作流時，可以養成一個很有用的說法：先講模型，再講外殼，再講環境，最後補上工具和限制。

例如你可以這樣說：我使用某個語言模型，透過命令列編程外殼，在一個 TypeScript repository 的本機檔案系統中工作；外殼允許讀寫檔案、搜尋內容和執行測試，但危險的 git 操作需要人工確認。

這種描述比「我在用某某 AI」有資訊得多。它讓別人知道問題可能出在哪一層，也讓你自己比較不容易把不同層的責任混在一起。

這也能讓比較變得更公平。兩個人即使用同一個模型，實際結果也可能差很多。

- 一個人的專案乾淨，有完整測試、清楚腳本和合理權限。
- 另一個人的 repository 缺依賴、目錄混亂，外殼還看不到關鍵路徑。

如果最後表現差很多，差異可能根本不在模型品牌，而是在整個系統被怎麼裝配。

### 📝 評估前先固定條件，比只看排行榜更有用

這也帶出一個很實用的做法：換模型之前，先做小型實驗。

讓兩套 setup 處理同一個真實任務，固定相同專案、相同需求、相同驗證方式，然後記錄幾件事。

1. 它探索了哪些檔案與路徑。
2. 它做了哪些修改。
3. 它能不能自己發現錯誤。
4. 它是否能完成驗證。
5. 最後需要多少人工介入。

這種比較方式會比只看模型排行榜更貼近你的日常工作，因為你比較的是整體代理系統，而不是把真實環境抽掉後的抽象能力。

### 🔧 一個可以直接使用的診斷順序

當代理下一次做錯事時，你可以按照下面的順序檢查。

1. 先看環境裡是否真的有它需要的檔案、資料、依賴和命令。
2. 再看外殼是否把這些能力暴露成模型可用的工具。
3. 確認工具呼叫有沒有真的執行，結果有沒有完整回到上下文。
4. 最後才判斷模型是否在正確資訊上做出錯誤推理。
5. 如果前面都正常，再考慮目前模型的能力、速度和成本是否適合這個任務。

這個順序看起來很普通，但實際上很有用。它能幫你避免一開始就跳到「是不是模型太弱」這個最昂貴、也最模糊的答案。

舉個例子，假設代理把按鈕改錯位置。

- 如果它根本沒讀過正確元件檔案，問題多半在環境可見性或探索工具。
- 如果它讀到了正確檔案，卻沒有寫入成功，問題可能在外殼權限。
- 如果它寫成功了，卻沒有執行測試，問題可能在命令、腳本或回饋迴路。
- 如果以上都正常，它還是誤解需求，這時才比較像模型、上下文品質，或任務描述出了問題。

這樣排錯的好處是，每一次修正都能累積到整個工作流上，而不是只解掉某一次對話。

### 💡 最後把它收成一個穩定的心智模型

現在把整件事收斂成一句最重要的話：**代理不是單一模型，而是模型、外殼、環境在一段任務中的組合運作。**

如果你喜歡用類比，可以這樣記。

- 模型像引擎，提供理解與生成的動力。
- 外殼像車身、方向盤、儀表板和傳動系統，把動力變成可控制的行動。
- 環境像道路、車庫、地圖和交通規則，決定你能去哪裡、能看到什麼，也決定會留下哪些痕跡。

只有引擎，車子開不起來。只有道路，也沒有東西能跑。把三者接起來，才會出現真正能工作的代理。

所以當你下次再聽到「這個代理不夠聰明」時，不要急著把它當成一句籠統評價。把它拆成更準的問題。

- 它是不是缺少專案資訊？
- 它是不是沒有合適工具？
- 工具是不是被權限或流程卡住？
- 環境是不是缺少測試、依賴或必要檔案？
- 還是模型在資訊完整的前提下，仍然做出錯誤判斷？

只要你會這樣拆，模糊抱怨就會變成可以檢查、可以實驗、可以改善的工程問題。這就是理解模型、外殼、環境與代理四個名稱的真正價值。
