# 中途改道與存檔 Spec

## Learning goal

學會中途改道（re-grill）與存檔 spec 的正確做法，避免 stale secondary source 陷阱。

## Lesson

### 🔄 發現方向不對怎麼辦

implement 到一半，你突然發現 spec 裡的假設不對。也許是 API 設計選錯了，也許是需求理解有落差，也許單純是寫到一半才看清真正該做的事。

這種時候，答案比你想的簡單：**丟掉還沒動手的 tickets，改 spec，再從新 spec 產生新的 tickets。** 不是打補丁，不是就地硬幹，而是直接改目的地。

### 🗺️ 為什麼 tickets 可以隨便丟

Tickets 從來就不是持久資產。它是 [[learn/ai-coding-crash-course/elements/tickets|Tickets]] 的衍生物，是「此刻怎麼走到目的地」的執行計畫。目的地都改了，舊的路線圖自然作廢。

用完即棄不浪費，留著才危險。這正是 [[learn/ai-coding-crash-course/elements/spec|Spec 文件]] 與 tickets 的 two-document design（雙文件設計）的價值所在：spec 是目的地，tickets 是路線圖。你換目的地，不用把整台車拆掉重建，只需要換張地圖。

### 📋 Re-grill 的三個步驟

1. 刪除尚未 implement 的 tickets。已經做完的不動，從你當前的位置繼續。
2. 把 [[learn/ai-coding-crash-course/elements/spec|Spec 文件]] 拿去 grill（審問），通常開一個新的 grilling session，把新理解帶進去，讓 grill 的火力重新塑形 spec。
3. 從新 spec 重新產生 tickets。

你不丟掉已完成的工作，你從現在的位置出發。中途改道和從零開始是兩回事。前者是迭代，後者才是失敗。大多數「方向不對」的時刻，你手上已經有半成形的東西可以繼續用，只需要修正方向。

---

### 📦 Spec 完成後怎麼處理

Implement 完成後，下一個容易踩的坑馬上出現：spec 要怎麼處理？

直覺會說把 spec 留在 repo 裡，下次需要的時候可以查。但這恰恰是最危險的做法。

### ⚠️ 為什麼 Spec 不能留在 Repo 裡

Spec 是 secondary source（二手來源）。它描述的是「程式碼該怎麼運作」，不是程式碼本身。而程式碼會 evolve，會 drift（漂移），會跟 spec 產生落差。

一旦 spec 留在 repo 裡，agent 會遇到一個誘惑：去讀那個比較小、比較好搜、看起來比較清楚的 spec，而不是去讀 primary source（一手來源）也就是程式碼本身。Agent 按照 stale secondary source 去理解系統，就像按照去年的地圖找今年才開的路。

**Spec-driven development（以 spec 為真）的陷阱在於它假設 spec 永遠正確。** 但軟體專案的本質就是不斷偏離初始計畫。如果你把 spec 當作 reference，你其實是在鼓勵 agent 把過時的文件當成權威。

### ✅ 正確做法：存檔到 Issue Tracker

把 spec 存到 issue tracker 裡，關掉、存檔。不要留在本地 markdown。Archived issue（已存檔的 issue）有四個好處：

1. 可被團隊成員 review 和留言
2. 可被搜尋到，不會消失在各個 work tree 和筆電之間
3. Agent 需要查 implement intent（實作意圖）的時候，仍然可以去 issue tracker 探索
4. 不會跟 repo 裡的程式碼混淆

Archived 的 spec 依然可讀，只是不再會被誤認為活文件。關掉、存檔、讓它離開程式碼的家，才是保護它的方式。

### 🔁 完整的 Spec 生命週期

```
寫 spec → grill → 產生 tickets → implement → 存檔 spec → tickets 歸零
```

每次新功能，從新的 spec 重新走一遍。Spec 是 disposable 的導航，不是永久的文件。它的價值在當下那一刻，不在於留在哪裡。

這跟上一篇講的 two-document design 是同一個邏輯的兩面：spec 和 tickets 分開，所以改路線不用改目的地，改目的地不用拆車。而 spec 存檔不用留 repo，所以二手來源不會污染一手來源。
