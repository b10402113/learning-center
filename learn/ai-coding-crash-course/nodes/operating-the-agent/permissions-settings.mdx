# 權限模型：代理能碰什麼

## Learning goal

用 allow once / allow forever / deny、wildcards 與 `settings.local.json` vs `settings.json`，控制代理可執行的命令

## Lesson

### ⚡️ 代理的力量需要一道閘門

一個 coding agent 可以讀寫你整個檔案系統、執行任何命令、呼叫各種工具。這些能力全開時，一次判斷錯誤就可能刪掉你的資料，或把沒檢查過的程式碼推上共用分支。你授權給它的每一分能力，都同時帶來一分破壞的可能。

所以外殼（harness）在「模型想做事」和「環境真的被改動」之間，放了一道閘門。這道閘門就是權限模型（Permissions Model），它回答的問題很簡單，代理在什麼條件下可以真的動手。這正是 [[learn/ai-coding-crash-course/elements/permissions-model|代理權限模型 (Agent Permissions Model)]] 講的核心內容。

權限模型的設計起點是嚴格預設（strict by default）。代理不能預設自動執行任何動作，每一次想跑命令、改檔案或存取網路，都得先經過你，或先經過你寫下的規則。

**為什麼值得為這道閘門多花心思？**
因為風險與報酬是一組取捨。每次都問，代理安全，但動作繁瑣。完全不問，代理跑得順，但一次誤判的破壞力沒有上限。日常使用需要中間的平衡點，常用的安全命令只問一次，真正危險的動作永遠被擋下。整課都在教你抓這個平衡點。

### 🛑 當代理想跑命令，畫面會停下來等你

用一個具體例子展開。假設你在一個 TypeScript 專案裡，代理想跑 `pnpm typecheck` 檢查型別。它不會直接執行，而是先把要執行的確切命令顯示給你看，附上一個理由，說明它為什麼想跑。畫面在這裡停下，等你決定。

畫面給你**三大選項**，這是權限提示（permission prompt）的核心。

**選項一，允許一次（allow once）**
這次放行只針對當下這條命令。代理跑完這次 `pnpm typecheck`，下次想跑同一條，畫面還是會再問一次。允許一次不會留下任何記憶。

**選項二，永遠允許（allow forever）**
意思就是「不要再問了」。你選它，外殼就把這條規則寫進專案，之後同樣的命令自動放行。以後代理想跑 `pnpm typecheck`，畫面不會停，命令直接執行。你省下的每一次確認，就是選這個選項的回報。

**選項三，拒絕（deny）**
這條命令這次被擋下，不會執行。拒絕可以只針對當下這一次，也可以搭配後面要講的規則語法，讓同類命令以後永遠被擋下。

還有一個常被忽略的動作，按 **tab**。當代理想跑的命令不合你意，你可以按 tab 輸入自己的替代命令，取代代理原本想跑的內容。代理想跑 `git push`，而你想先跑 `pnpm typecheck`，按 tab 改成你要的命令即可。這個技巧把拒絕變成取代，代理仍能繼續工作，只是用更安全的方式。

網頁搜尋與抓取（web search/fetch）同樣要經過權限檢查。代理要查資料或抓網頁時，畫面一樣會停下來等你批准。權限模型不只管本機命令，也管代理對網路的存取。

### 🔧 你的決定被寫進設定檔

你每次在權限提示裡的選擇，會被記錄下來，存放位置是 `.claude/settings.local.json` 這支檔案。裡面的 `permissions` 陣列，就是你所有權限規則的集合。

這支檔案可以直接用編輯器打開手動改，不必透過提示逐一授權。想預先放行常用命令，就寫進 `permissions` 陣列。想擋下危險命令，也寫進同一個陣列。語法只有幾種型態，整理成下面這張表。

| 型態 | 例子 | 效果 |
| --- | --- | --- |
| 精確命令 | `pnpm typecheck` | 只放行這條確切命令 |
| 萬用字元 | `npm run *` | 放行符合樣式的整類命令 |
| 拒絕清單 | `deny git push *` | 永久擋下所有 git push |

每一行都是一條規則。

- **精確命令（exact command）**。規則寫 `pnpm typecheck`，就只放行這條一模一樣的命令。多一個空格、多一個參數，都不算符合，代理想跑就得再問一次。
- **萬用字元（wildcard）**。規則寫 `npm run *`，星號代表任何字串，所以 `npm run dev`、`npm run test`、`npm run build` 全部放行。一條規則可以蓋住一整類命令，對常用腳本很實用。
- **拒絕清單（deny list）**。規則寫 `deny git push *`，任何以 `git push` 開頭的命令，後接什麼都不管，一律永久擋下。這條規則很常拿來保護共用分支，代理從此沒有能力把程式碼推上遠端。

一個實際的 `permissions` 陣列長這樣

```json
{
  "permissions": [
    "pnpm typecheck",
    "npm run *",
    "deny git push *"
  ]
}
```

外殼判斷一條命令時，會逐一比對清單裡的規則。你在清單裡寫了什麼，代理就能或不能跑什麼。手改這支檔案，比每次在提示畫面按選項更可控，因為你能一次看完整張規則表，不必靠記憶回想自己授權過哪些東西。

### 🔍 拒絕 git push，走一遍完整流程

把上面的規則串成一個完整場景。假設你在一個多人協作的分支上工作，不希望代理擅自把任何東西推上遠端。

1. **寫入規則**。在 `.claude/settings.local.json` 的 `permissions` 陣列裡加入 `deny git push *`。
2. **代理提出命令**。之後某個 session 裡，代理決定上傳程式碼，提出要跑 `git push origin main`。
3. **外殼比對規則**。命令以 `git push` 開頭，命中拒絕規則，動作在執行前就被攔下。因為這條規則已經代表你的決定，畫面不需要再問一次。
4. **代理收到結果**。它收到「這個動作被權限規則擋下」的結果，可能改用其他方式，例如先問你要不要手動推，或改推到你指定的分支。無論如何，`git push` 本身永遠不會被執行。

對照組是精確命令與萬用字元。`pnpm typecheck` 放行的是檢查本身，不影響其他 `pnpm` 命令。`npm run *` 放行整類腳本，但 `npm install` 不含 `run`，不在範圍內，代理想跑還是得問。這三種型態搭配使用，就能同時做到「常用的事別煩我」和「危險的事永遠不行」。

### 📁 兩支設定檔，一個給自己，一個給團隊

權限設定都放在 `.claude` 目錄下，但分成兩支檔案，用途完全不同。

| 檔案 | 給誰 | 是否進版本控制 | 適合放什麼 |
| --- | --- | --- | --- |
| `.claude/settings.local.json` | 個人 | 否，被 git 忽略 | 個人偏好的常用命令 |
| `.claude/settings.json` | 團隊 | 是，會被提交 | 全團隊都該遵守的安全規則 |

`.claude/settings.local.json` 只影響你這台機器上的代理，而且會被 git 忽略，不會被提交進版本控制，不會跟著程式碼庫傳給別人。你在這裡寫的權限規則，只有你自己看得到，也只有你自己會用到。適合放個人偏好的常用命令，例如你每天都會跑幾次的檢查腳本。

`.claude/settings.json` 會被提交進版本控制，跟著程式碼庫傳給所有協作者。任何在這個儲存庫上啟動的代理實例，都會讀取這支檔案。你在這裡寫的規則，會套用在每個人的代理上。適合放整個團隊都該遵守的安全規則，例如 `deny git push *`，讓每個人的代理都無法擅自推上共用分支。

**用一句話記住分工。** settings.local.json 留給自己，settings.json 交給團隊。兩支檔案都用同一套 permissions 語法，差別只在誰讀得到。

實務上常見的做法，是先把常用的安全命令放進團隊的 settings.json，讓整個團隊在同一支程式碼庫上自動通過這些檢查，不用每個人各自授權一次。個人再把偏好放進 settings.local.json。你的常用命令可能跟同事不同，但團隊的安全底線應該一致，兩支檔案剛好各管一層。

### 🧠 拒絕一個工具，順帶縮小上下文

權限模型有一個不直觀的副作用，跟上下文（context）有關。

代理運作時，每次請求都會把系統提示詞（system prompt）一起送給模型。系統提示詞裡列出了代理可用的一切，包括每個工具的定義。工具定義會佔用 token，也就是佔用空間。

**當你拒絕某個工具，外殼不只擋下執行。** 它還會把這個工具的定義從系統提示詞裡移除。定義不在了，模型就不知道有這個工具，自然不會去用它。這帶來一個連帶效果，每次請求攜帶的上下文變小了，因為少了那個工具的定義。

反過來也成立。你允許的工具越多，系統提示詞越長，每次請求背著的重擔也越重。**這解釋了為什麼權限設定不只是一道安全開關，也是上下文管理的一部分。** 拒絕你不用的工具，一方面防止誤用，另一方面也替你省下每次請求的 token。課程後面的系統提示詞瘦身章節，會把這個做法用到極致，一項一項關閉不用的工具，觀察上下文數字一步步往下掉。

### 👁️ 權限和可見性，兩個方向不同

上一步學的可見性控制，跟這裡的權限模型，常常被搞混。把它們分清楚很有用。**可見性決定代理看得到什麼，權限決定代理能做什麼。** 你可以把 bash 模式的輸出藏起來不讓代理看，那是可見性。你也可以允許或拒絕代理自己跑某條命令，那是權限。前者管資訊，後者管行動，兩者都用來控制代理的接觸範圍，但作用的位置不同。[[learn/ai-coding-crash-course/elements/bash-mode-visibility|Bash 模式與可見性控制 (Bash Mode & Visibility Control)]] 教你怎麼藏輸出，這一課教你怎麼管行動。兩者合起來，你就同時掌握代理的視線和手。

### 💡 放行什麼，放行到什麼程度

判斷一條命令該不該預先放行，可以問兩個問題。

**第一個問題，這條命令會不會造成無法挽回的後果。** 檢查型別、跑測試、啟動開發伺服器，這些動作失敗了重跑就好，值得放進清單省掉確認。刪除檔案、改動共用分支、推上遠端，這些動作一旦做錯就很難回頭，寧可每次都停下來問。

**第二個問題，這條命令的影響範圍有多大。** 只碰本機暫存資料的命令，風險低，適合預先授權。會改動專案結構、連上外部服務，或動到多人共用資源的命令，風險高，適合留給每次確認，或直接用 deny 擋掉。

**萬用字元要小心使用。** `npm run *` 看起來方便，但它同時放行了清單裡所有腳本，包括你可能不熟悉的 `npm run deploy` 或 `npm run db:reset`。如果你對整包腳本都有把握，再考慮用萬用字元。只想放行一兩條，用精確命令更安全。拿不準的命令，就先讓它每次問你，觀察代理一段時間，再把表現穩定的命令逐步升級成永遠允許。

**還有一個實用的節奏。** 先在互動裡觀察代理最常跑哪幾條命令，把這幾條放進 settings.local.json 預先授權。一段時間後，如果發現某些命令是整個團隊的例行公事，就把它們提升到團隊的 settings.json。個人檔案是試行的地方，團隊檔案是定案的地方，這個順序能讓權限規則跟著實際使用慢慢長出來。

### 🎯 風險與報酬的取捨，落在哪裡

把整課濃縮成一個判斷。權限模型是風險與報酬之間的取捨，這個平衡點可以靠**三件工具**達成。

- **允許一次**處理單次需求，不必動到任何設定。
- **永遠允許**把常用安全命令寫進規則，往後同類動作自動放行。
- **拒絕搭配萬用字元**，把真正危險的命令永久擋在門外。

再加一個 tab 的替代技巧，你連拒絕都可以變成比較安全的執行，而不必乾脆停擺。

最後把整個模型縮成一句話。代理想做事，外殼停下來問你，你的決定寫進 settings 檔案，之後同類動作照規則執行，不再打擾你。權限設定的品質，直接決定代理有沒有能力闖下不可挽回的禍。懂得用精確命令放行安全動作，用萬用字元覆蓋整類常用命令，用 deny 清單鎖死危險動作，再把個人偏好和團隊規則分層放好，你就把代理的能力關進了你能接受的範圍裡。
