# 自動模式：讓安全分類器把關

## Learning goal

理解 auto mode 的 LLM 分類器如何取捨安全與手動把關，並知道何時適合放手

## Lesson

自動模式（Auto Mode）是這套代理 CLI 現在預設的運作方式。上一節的權限模型（Permissions Model）靠你親手把關，每一條命令都停下來問你一次，安全，但一趟長任務會被中斷上百次。自動模式換了一種做法，把把關的責任交給一個會自動判斷的環節。它要回答的問題只有一個，如何在幾乎不需要你介入的前提下，仍然擋住真正災難性的動作。這一篇要拆開[[learn/ai-coding-crash-course/elements/auto-mode-classifier|自動模式與安全分類器 (Auto Mode & LLM Classifier)]]的內部，看它怎麼判斷、哪裡會失誤、要付出什麼代價，以及你該在什麼時候放手。

### ⚡️ 四種模式，一個循環

自動模式只是四種模式之一。代理 CLI 提供四種模式，你在同一次對話裡用 Shift+Tab 就能依序循環切換，隨時可以切，不需要重開對話。四種模式對「代理能不能動手」給出四種不同的答案。

| 模式 | 代理能不能動手 | 你要做什麼 |
| --- | --- | --- |
| 手動（manual） | 每次執行動作前停下 | 從 允許一次、永遠允許、拒絕 三個選項挑一個 |
| 接受編輯（accept-edits） | 改檔案直接套用 | 只盯住執行命令的環節 |
| 規劃（plan） | 只能讀取與思考 | 審完方案再切回能執行的模式 |
| 自動（auto） | 判斷後直接執行 | 幾乎不用介入 |

手動模式最嚴格，上一節的權限模型講的就是這一套。代理每次想執行任何動作，都會先停下，把確切命令與理由顯示給你，等你從允許一次、永遠允許、拒絕三個選項裡挑一個。安全，但每一條命令都要打斷你一次。

接受編輯模式放鬆一半。代理修改檔案時不再逐一問你，直接把編輯套用上去，執行命令時仍然會問。它適合你信任代理改檔的方式、但還想盯住命令的場合。

規劃模式往反方向收緊。代理只能讀取與思考，不能真的執行任何東西。它用在動手前先把方案想清楚，等你確認之後再切回能執行的模式。四種模式裡，它是唯一讓代理完全無法動手的。

自動模式把判斷整個交出去。代理提出命令，交給一個模型決定放不放行，幾乎不問你。它是目前的預設，也是這一篇的主角。

### 🔧 分類器是怎麼判斷的

自動模式不放行任何寫死的硬規則。它把每一條要執行的命令交給一個 LLM 分類器（LLM classifier）。這個分類器本身也是一個語言模型，規模不大，追求速度，很可能是一個像 Haiku 這樣的小型快速模型。主模型比它聰明得多，它只負責快速把關。它不會去比對一份固定黑名單，它的判斷來自閱讀整段對話。

**為什麼讀脈絡比讀規則強？** 分類器看的是整段脈絡。它知道你最初的要求，知道代理一路上做了什麼，看到代理剛跑過哪些命令、拿到什麼輸出，再拿眼前這條命令在整段脈絡裡評估風險。這就是它和硬規則最大的差別。規則只能寫死命令本身，看不到命令周圍發生的事。分類器讀得懂脈絡，因此同一條命令在不同場合可以得到不同的判斷。

舉例來說，`npm run build` 這條命令本身沒有好壞。在一個你正在修改編譯設定的對話裡，它是驗證改動的正常動作，分類器會放行。在一個代理剛接手陌生倉庫、正在四處摸索的對話裡，同樣的命令會讓分類器多想一層，可能要求你確認。判斷的結果帶有機率性。分類器不會給出非黑即白的答案，它給出的是一個「在目前脈絡下安不安全」的傾向，再依這個傾向放行或擋下。

評估一條命令時，分類器同時看四個訊號。命令本身的字面內容、參數指向什麼東西、這條命令和你的目標合不合、它是要改專案內部的檔案、還是動到外部系統。這些訊號加在一起，產生一個傾向分數。分數高就放行，分數低就擋下，落在中間時分類器傾向保守，寧可多問一次。同樣的命令配上不同的對話，讀到的訊號就不一樣，答案跟著變，所以這套判斷沒有一張可以事先背下來的規則表。

判斷完之後，結果只有兩個。安全，就直接執行。可疑，就擋下來回到你面前，你可以改命令、換方式、或自己動手，決定權回到你手上。整個過程裡你看不到的只有一件事，分類器到底讀了多少脈絡、怎麼讀的，它不會把每一次的推理過程攤給你看。

### 💰 每次判斷都要付費

每一次判斷都是一次完整的模型推論。推論要花 token，也要花時間。自動模式下，代理每跑一條命令，就先付一次分類器的開銷，再繼續往下走。命令越多，累積的開銷越明顯。一整趟任務跑下來，執行速度會比完全放手、或比用硬規則直接放行慢上一點。這是「幾乎不用你介入」換來的代價，你得知道它在哪裡，才知道自己付的是什麼。

把數字帶進來會更有感覺。一趟長任務可能跑掉幾百條命令，每一條都多付一次分類器的推論，累積下來就是一筆不小的 token 帳單，外加一路的等待時間。命令越頻繁，這筆開銷越明顯。好消息是它不會把你的用量限制推高太多，整體來說是一筆還算划算的交易。

**為什麼了解這筆開銷很重要？** 因為它直接決定了 allow-list 的價值。你放行過的命令不會進入分類器，也就不付這筆錢，跑起來自然快一些、也省一些。這正是上一節建議你維護 allow-list 的理由。

### 🎬 一趟自動模式跑完的完整樣子

把機制放回真實工作，畫面是這樣的。你叫代理替搜尋頁加上按日期篩選的功能。代理先讀頁面元件和查詢邏輯，接著提出要跑 `pnpm typecheck`。這條命令你事先放行過，harness 直接讓它通過，不進分類器。測試結果回來之後，代理改完程式，又提出要跑一次 build。這次沒有預先規則，命令被送進分類器，分類器讀到對話裡的改動脈絡，判斷這是驗證改動的正常動作，放行。整趟工作裡你幾乎沒被問過，代理一路做完，你在旁邊看著進度就好。

對比之下，同一個 session 裡你若請它建立 GitHub issue，`gh issue create` 一進來就被擋下，你得自己插手。這就是自動模式的日常，大部分動作順暢滑過，少數動作停下來等你。你真正需要認識的，是哪些動作會停、為什麼會停，以及停下來之後怎麼處理。

### 🎯 三種行為，看分類器的失誤

分類器不會每次都對。把它的失誤整理起來，大致是三種行為。

| 分類器的行為 | 實際例子 |
| --- | --- |
| 擋住多數「永遠不該做」的事 | `rm -rf` 整個檔案系統 |
| 漏放一些你不想要的事 | 資料庫遷移（migration） |
| 誤擋一些你想要的事 | 建立 GitHub issue |

第一種行為是它最主要的價值。刪掉整個檔案系統這種動作，無論對話脈絡怎麼圓，都找不到正當理由，分類器幾乎每次都會擋下。這類「永遠不該做」的事被擋住，代表底線還在，災難不會從這裡發生。

第二種行為是漏放。設想你正在改一個電商專案，要替訂單表加上一欄。你叫代理修正一處資料結構的 bug，代理翻完資料庫設定之後，判斷直接跑一次資料庫遷移（migration）最省事。遷移會改動資料庫結構，可能影響共用或正式環境，而你根本沒打算現在動資料庫。但分類器看到的脈絡是「調整資料結構是很平常的開發動作」，它判斷這條遷移命令可以接受，於是放行。你事後才發現資料庫已經被動過，而這根本不是你想讓它碰的部分。它知道遷移有風險，只是它在這個脈絡裡把風險估低了。

第三種行為是誤擋。設想你花時間整理出一個 bug，想讓代理幫你建立一張 GitHub issue。代理提出用 `gh issue create` 這條命令。這條命令要寫入外部系統，改動的是倉庫之外的狀態。分類器對這類動作天生保守，把命令擋了下來。建立 issue 正是你想要的，任務卻在這裡凍結，你得自己手動放行，或用別的方式把 issue 建立起來。誤擋不代表分類器讀不懂你的意圖。它寧可錯過一個合理的動作，也不願放過一個危險的動作，這就是保守的代價。

**為什麼這個取捨方向值得接受？** 把三種行為放在一起看，分類器的方向很清楚。它犧牲掉一些你想要的事，也漏掉一些你不想要的事，但把真正災難性的動作牢牢擋住。整體落在「on the right side of OK」，也就是站在可接受的一側。方向正確，不追求完美。誤擋的代價是你多花一點手動動作，漏放的代價是你可能遇到一次不想遇到的變更，兩者都遠小於代理把整個檔案系統刪掉。理解這個取捨，你才不會因為一次誤擋就認定它沒用，也不會因為它大部分時候放行就認定它什麼都放。

### ⚙️ 檢查順序，先看設定再看分類器

分類器不是第一道關。代理外殼（harness）在把命令交給分類器之前，會先檢查 `settings.json` 裡的規則。你先放行或先拒絕的命令會先被套用，根本不會進入分類器。

**為什麼這個順序很重要？** 常見又安全的命令，例如 `pnpm typecheck`，你可以事先放行，讓它們直接通過，省下分類器的 token 與延遲。高風險的命令，例如所有 git push，你可以事先拒絕，讓它們在分類器之前就被擋下，連被誤判的機會都沒有。分類器只管那些既沒有被放行、也沒有被拒絕的命令。

換句話說，你在上一節建立的 allow-list 和 deny 清單，在自動模式下依然有效，而且作用在分類器之前。你把設定做得越完整，分類器就只需要處理剩下的邊緣案例。自動模式的可靠性，有一半是你在 `settings.json` 裡決定的，不全是分類器的功勞。

### 🛠️ 預設模式與設定

自動模式是目前的預設。如果你希望每次開新的 session 都用別的模式，可以到 config 裡找「default permission mode」這個設定，把它改成你想要的那種模式，按 Enter 或空白鍵就能選。改好之後，新的 session 直接套用，不必每次重新切換。這是一個一次性的設定，值得你花三十秒決定一次，免得在每一次對話開頭重複切換。

### 🧭 何時放手，何時守住手動

把自動模式放開的前提，是你能判斷眼前這趟工作落在哪個風險等級。

先看高風險的一側。資料庫遷移、推上共用分支、刪除檔案、操作正式環境，這些動作的後果難以復原，值得保留人工確認。遇到這類工作，切回手動模式，或至少在 `settings.json` 把對應的命令拒絕掉，讓代理沒有能力自動執行。自動模式負責的是日常，不該替你決定這種等級的動作。

再看低風險的一側。只會碰專案內部檔案、可以被 git 還原、不會改動外部狀態的工作，例如重構、改元件、跑測試、調樣式，自動模式的失誤風險低。把常用命令事先放行之後，自動模式跑起來幾乎不用你管，這正是它存在的意義。

實務上可以把動作分成幾類來對照。改動專案內部檔案、執行測試、安裝套件、修改樣式，這些幾乎永遠可以交給自動模式。改動資料庫、推送分支、刪除目錄、呼叫外部 API 寫入，這些寧可先問。前者的共同點是能復原，後者的共同點是復原成本高。用「能不能復原」這一個標準來切，會比記住每一條命令容易得多。這個標準跟著你的情境走，你重視哪個資料夾、哪條分支，就自然知道該把哪一類動作守在手動裡。

遇到誤擋不必緊張。開不了 GitHub issue，就手動執行一次，或換一種方式完成，不值得為了單一誤擋關掉自動模式。遇到漏放，回想一下是不是有哪類命令其實可以提前拒絕，把教訓寫回 `settings.json`。自動模式的本質是一筆權衡，你在設定上花的每一點功夫，都是在調整這筆權衡的落點。

放手之前，可以依序問自己三個問題。這個動作改了什麼，能不能復原。它會不會動到專案之外、或正式環境。如果真的判斷錯，損失大不大。三個問題都過得去，就讓自動模式跑。任何一個答案讓你不安，就切回手動，保留最後的確認權。安全的最後一層確認權在你手上，分類器只是幫你擋住大部分，而且它擋住的是那些「永遠不該做」的事。
