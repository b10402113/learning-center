# 控制 Bash 命令的可見性

## Learning goal

用 `!` bash 模式、Ctrl+B 背景執行、Ctrl+Z 掛起三種方式，決定代理能看見哪些命令與輸出。

## Lesson

你在終端裡敲一條命令，按下 Enter。命令跑完，輸出一閃而過。這個畫面太普通，以至於你很少停下來想，這些輸出到底流向了哪裡。而這條流向，恰恰決定了代理接下來會做什麼。

代理（agent）不會看螢幕，它讀的是自己的上下文（context）。凡是落入它視線範圍的輸出，都會變成它下一步行動的材料。所以「讓代理看到什麼」是一道你可以主動調整的開關，這道開關就叫可見性控制（Visibility Control），意思是決定哪些命令、哪些輸出該被代理看見，哪些該留在你自己眼前。

這篇文章要把這個機制完整展開，講三種跑 bash 的方式，每一種底下代理到底看得到什麼，以及這個選擇怎麼影響合作品質。完整的概念條目見 [[learn/ai-coding-crash-course/elements/bash-mode-visibility|Bash 模式與可見性控制 (Bash Mode & Visibility Control)]]，本篇是它的實作面向。

### 📖 先弄清楚代理是怎麼「看」的

要控制可見性，得先知道代理的「看」是什麼意思。代理不盯著螢幕，它讀的是上下文。你在終端跑的每一條命令，只要落在代理看得見的範圍，輸出就會被當成工具結果（tool result），放回代理的上下文，成為它下一輪思考的材料。

代理跑命令的方式，本質是一次工具呼叫（tool call）。它決定要跑某條命令，就呼叫 bash 這個工具，工具執行完，把輸出當結果交回去。這份結果進了上下文，代理接著讀它、消化，然後決定下一步。輸出流向哪裡，等於代理知道什麼。

**為什麼這條管線很重要？**
可見性是一條務實的決策輸入管線。你想讓代理基於哪些事實行動，就把哪些輸出放進它的上下文。你不想讓它知道的事，就不能讓輸出進入這條管線。

兩種極端各有代價。如果代理看得到一切，dev server 噴出來的幾百行無關 log 會全數灌進上下文。代理還是會讀，還是會回應，只是有用的訊號被雜訊淹沒，決策品質下滑。反過來，如果你偷偷跑了某條命令卻完全不讓代理知道，代理之後的判斷就建立在殘缺的訊息上，它可能表現得離譜，根源只是它少了一段資訊。

可見性控制給你三個檔位，讓你在全看和全藏之間，按任務挑一個剛好的位置。

### 🎛️ 三大模式，先認名字

三種方式都叫 bash，但誰看得到輸出、命令怎麼跑、狀態怎麼保存，各不相同。

1. `!` 前綴，互動 shell，前景執行
2. Ctrl+B，背景執行
3. Ctrl+Z，把代理整個掛起

#### 💡 模式一｜`!` 前綴，互動 shell

第一種是 `!` 前綴，也就是 bash 模式（bash mode）。在提示列輸入 `!`，後面接命令，命令會在你眼前的互動 shell（interactive shell）裡以前景（foreground）方式執行。前景的意思是這個 shell 佔著你的終端，命令跑多久，你就得等多久。

輸出的去向是雙份的。一份出現在你的螢幕上，一份作為工具結果進代理的上下文。代理看到即時 log，看到就開始推斷、行動。你想讓代理盯著某個程式跑、拿它的輸出當除錯線索時，就用 `!`。

一個實際的例子。你正修一個 dev server 的問題，程式應該跑在本機的 localhost:5175。你輸入 `!` 再接啟動命令，server 開始跑，log 一行一行流過螢幕，同時流進代理的上下文。錯誤出現時，代理不需要你複述那條訊息，它已經讀到了，可以直接開始診斷。`!` 的價值就是把「跑」和「看」綁在一起，讓代理第一時間擁有全部事實。

#### 🔧 模式二｜Ctrl+B，背景執行

第二種是 Ctrl+B，把命令丟到背景執行（background）。這個模式是為長時間執行的命令設計的，最典型的是 dev server，它啟動之後就一直跑，不會自己結束。用 `!` 跑它，終端就被它佔住，你什麼都做不了。Ctrl+B 把命令移到背景，命令照跑，輸出寫進一個本機檔案，不再佔著終端。狀態列（status line）下方會出現一個背景任務指示器（background-task indicator），提示你有任務在跑，也讓你去管理它。

這裡的關鍵是，命令離開你眼前，不代表代理失去它。輸出寫進本機檔案，檔案的位置代理知道，需要的時候它可以去讀。所以 Ctrl+B 的效果是把命令放到不擋路的地方慢慢跑，同時保留代理取用輸出的路徑。你得到一個清空的終端，繼續做別的事，任務結束再看結果，或者讓代理自己查結果。

#### 🧊 模式三｜Ctrl+Z 掛起，`fg` 恢復

第三種的性質完全不同，它把代理整個程式暫停。按 Ctrl+Z，代理程式被掛起（suspend），你回到普通的 shell。注意這個 shell 在代理之外，是原始的終端，跟代理裡頭的那個不同。你在這裡輸入的任何命令，輸出都只到你眼前，代理一概看不到，因為它的程式整個停住了，根本沒有在讀東西。辦完事輸入 `fg`，代理恢復，狀態完好接續，就像暫停前一樣。

要把「狀態完好」講透。別把 Ctrl+Z 當成關掉代理再重開，重開會清空上下文。Ctrl+Z 用的是作業系統的工作控制（job control），把執行中的程式暫停，像按下暫停鍵，程式凍在現狀，記憶體裡的內容原封不動。`fg` 放開暫停鍵，程式從凍結的那一刻繼續。代理的上下文、它的工作進度，全部完好。唯一的不同，是你剛才在普通 shell 裡做的事，它一無所知。

這帶來一個很實際的用途。有時你不想讓代理看到某條命令，理由可以很簡單，你只想自己先確認狀況。例如你懷疑 git 工作區有未提交的變更，想先自己看一眼，再決定要不要告訴代理。你按 Ctrl+Z，跑 `git status`，確認完，`fg` 回來。代理不知道你查過，狀態卻完好，直接繼續原本的工作。

工作控制還有一層細節。同一個暫停的程式，`fg` 讓它回到前景繼續，你也可以用 `jobs` 列出背景的任務，用 `bg` 讓掛起的任務在背景繼續跑。這些是普通 shell 就有的能力。代理暫停期間，你面對的就是一個普通的終端，所有平常的 shell 技巧都還適用。

### 📊 三大模式並排比較

| 模式 | 誰看到輸出 | 命令怎麼跑 | 典型用途 |
| --- | --- | --- | --- |
| `!` 前綴 | 你加代理 | 前景互動 shell | 看 dev server log，讓代理一起診斷 |
| Ctrl+B | 你透過本機檔案 | 背景執行 | 長時間命令不佔終端，輸出保留給代理 |
| Ctrl+Z 加 `fg` | 只有你 | 完全隱藏，代理暫停 | 不想讓代理看見的命令 |

### ⚙️ 機制再往下推一層

把三種方式的機制理清，就能預測每一種的後果。

把 `!` 前綴拆開看，本質是同步廣播。命令輸出同時餵給兩個讀者，你和代理。你的眼睛看螢幕，代理的上下文收輸出。代理看到輸出就動起來，因為輸出是它行動的燃料。代價是沒有節流，輸出多大，代理就吞下多少，無論有沒有用。所以 `!` 適合輸出量可控、而且你真的希望代理立即反應的場合。

Ctrl+B 換個角度，本質是解耦，命令的執行和你的終端分開。命令自己跑，輸出寫成檔案，代理對輸出的取得變成按需的。它不會被即時塞進上下文，代理需要時才去讀那個檔案。這對長時間命令特別重要，因為它們的輸出往往無窮無盡，即時全塞進上下文只會把上下文灌爆。背景執行讓輸出待命，不佔上下文，要用再取。這是三種模式裡唯一的延遲曝光。

Ctrl+Z 的性質最不同，本質是隔離。它把代理整個從執行環境裡摘除，讓你在代理碰不到的地方做事。這是最徹底的可見性控制。它讓整個代理暫時不存在，比單單藏住輸出的內容更進一步。代價是你得手動暫停、手動恢復，過程裡代理幫不上忙。所以它適合短暫的、私人的命令。要跑很久的事，你多半還是想讓代理參與，就別用這招。

把三種方式放在可見性這條座標上看，輪廓就清晰了。

| 模式 | 曝光程度 | 代理什麼時候看 |
| --- | --- | --- |
| `!` 前綴 | 最大曝光 | 即時看見一切 |
| Ctrl+B | 延遲曝光 | 需要時才看 |
| Ctrl+Z | 零曝光 | 完全不看 |

每一條命令，你替它挑一個曝光程度。

### 🤝 可見性與信任

這套選擇的影響超出技術層面，直接牽動你和代理之間的信任。不信任通常來自兩種不確定，你不知道代理在幹嘛，或者代理不知道你在幹嘛，兩者都讓合作彆扭。可見性控制給你工具，把兩種不確定都收掉。

用 `!` 或 Ctrl+B 時，代理知道你跑了什麼，你也知道代理看到了什麼，雙方的資訊模型一致，它接著做的事你就放心讓它自己走。用 Ctrl+Z 時，是你主動選擇藏起一件事，理由你清楚，代理不曉得，而它的狀態完好，不會因為缺了一段訊息就推出奇怪的結論。信任不要求全知，要求的是每一方都曉得規則。你知道什麼被看見了，代理知道它該看什麼，合作就穩。

決策品質還有一層關係。代理的判斷直接取決於它手上的訊息完整度。假設你用 Ctrl+B 跑了一個長時間命令，卻沒意識到輸出可以被代理讀到，之後代理照著那個檔案的內容行動，你會一頭霧水。反過來，你以為 `!` 跑的命令代理看得到，它卻因為某種設定沒收到，你會誤會它在裝傻。理解每個模式的曝光規則，你就能預測代理的下一步，這份可預測性正是信任的來源。

### 🧪 三個工作實例

把流程走一遍，讓它變成直覺。

**實例一，除錯 dev server。** 你修的功能起不來，server 一啟動就報錯。你輸入 `!` 接啟動命令，server 在前景跑，錯誤訊息噴在螢幕上，同時進代理的上下文。代理讀到錯誤，推測原因，給出修法。你一邊看 log 流動，一邊看代理診斷，兩邊對得上。這是 `!` 最典型的用法，除錯需要雙方同時看到即時輸出。

**實例二，長時間命令不想佔終端。** 你有一段測試要跑很久，跑完才看結果。你按 Ctrl+B，命令進背景，輸出寫進本機檔案，狀態列下方浮現背景任務指示器。終端立刻空出來，你繼續做別的活。測試跑完，你讓代理去讀那個檔案，或者自己開來看。命令照樣在跑，代理知道檔案存在，它有機會用到，你的終端卻不被打擾。

**實例三，不讓代理看見的短命令。** 你不想讓代理知道你檢查過 git 狀態，或者你想自己確認某個環境變數，再決定要不要告訴它。你按 Ctrl+Z，代理掛起，回到普通 shell，輸入 `git status` 看清楚，再 `fg` 恢復。代理回來，上下文完好，不曉得你剛才動過手。這一招留給那些你只想自己掌握、不想成為代理決策材料的事。

### 🖥️ 平台差異

快捷鍵有平台差異，這點要特別記住。常見的示範以 Windows 的按法為主，Mac 和 Linux 的對應按鍵不同。這是最容易被忽略的一環，你可能照著按半天沒反應，功能其實還在，只是按錯鍵。Mac 有自己的一套對應鍵，各 Linux 終端也各有慣例。遇到快捷鍵沒生效，先懷疑平台，查自己系統的等價按鍵，再回頭確認機制。機制不變，變的只有按鍵。

### 🎯 怎麼選

回到選擇。每一條命令，都先問一句，它該被誰看見。

- **要代理一起看的**，用 `!`，讓輸出即時進上下文。
- **要跑很久、不想佔終端的**，用 Ctrl+B，輸出寫進檔案備用。
- **完全不想讓代理知道的**，用 Ctrl+Z，辦完事 `fg` 回來。

除錯 dev server 或長時間命令的問題，主要靠 bash 模式搭配背景，也就是 `!` 加 Ctrl+B 這個組合，因為這兩種場合你都需要代理保有看輸出的路徑。真正需要隔離的，留給短暫的、私人的檢查。

回顧整個機制。代理靠讀上下文認識世界，輸出進上下文，代理才等於知道。

- `!` 讓輸出即時進上下文。
- Ctrl+B 讓輸出待命在檔案裡，按需取用。
- Ctrl+Z 讓輸出完全不產生給代理。

這套選擇畫出了代理的視線範圍。讓它看見該看的，它有充分的訊息做對的決定。讓它看不見不該看的，你的私人操作不會污染它的判斷。每一條命令都有曝光程度可以選，挑對，合作就順。
