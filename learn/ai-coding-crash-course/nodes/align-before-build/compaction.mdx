# 把長 session 壓進新 session：compaction 壓縮機制

## Learning goal

能在長 session 逼近聰明區（smart zone）邊緣時，用 `/compact` 把它壓成摘要種子進新 session，並說出它「用資訊換效率」的代價與最穩妥的用途（QA）。

## Lesson

### 📝 開場，一場長 session 是怎麼走到邊緣的

先回到你熟悉的一幕。你跑完一趟完整的 [[learn/ai-coding-crash-course/elements/grilling|Grilling 對齊法 (Grilling)]]，代理在背景掃完程式碼庫，你逐題回答了四十幾題，把需求、取捨、每個「為什麼要做」都敲定，實作十四分鐘跑完。這一切發生在同一個工作階段（session）裡。從你開啟代理那一刻起，到你準備對成品做品質檢驗（QA）為止，所有對話、代理讀過的檔案、改過的程式碼，全部堆在同一個上下文（context）裡。

到這裡，上下文視窗（context window）裡已經塞了大約十五萬五千個 token。token 是模型處理文字的最小單位，可以粗淺地想成模型讀一段文字時的計價與思考單位，一段中文大概拆成幾個 token，一句話就有幾十個。十五萬五千個 token 聽起來很多，放在上下文的尺度上，剛好落在聰明區（smart zone）的邊緣，也就是模型仍保有完整思考品質的那段區域的最後一截。越過這條線，就進入笨區（dumb zone）。

一個長 session 幾乎必然走到這一步。Grilling 之所以省，是因為它把上下文維持得很便宜，全程大約只要兩萬到三萬三千個 token，等於把十幾萬 token 的聰明區空間留給真正的實作去燒。實作是吃 token 的大戶，它不停讀檔、改檔，每改一版就重跑一次測試，一場下來就把整段聰明區填滿。於是你正好在最需要繼續工作的時候，站在一條不舒服的分界線上。

### ⚠️ 繼續硬撐，要付兩筆帳單

最直覺的選擇是留在同一個 session 裡繼續幹，但這正是最不划算的選項。有兩個原因，都跟模型的運作方式綁在一起。

第一筆帳單是品質緩慢退化。笨區是一條漸進的斜坡，不會像斷電那樣突然變黑。每一輪的輸出都比上一輪差一點點，思考開始飄、細節開始漏，執行的指令也慢慢走樣。退化得慢，你就容易在不知不覺中接受品質下滑的輸出，還以為跟平常差不多。

第二筆帳單是成本持續堆高。每一次向模型供應商發出請求（request），都會把之前所有的 token 連同新的指令重新發送一遍。你每問一句話，代理就要把這十五萬五千個 token 從頭到尾再讀一次。這筆錢沒把你吃垮，只因為這些 token 之前都送過、被快取（cache）住了，重送有折扣。便宜不等於免費，而這十五萬五千個 token 裡，真正有用的又有多少？

大部分都是噪音。代理在實作中做了大量檔案讀取（file read）、檔案寫入（file write），同一個檔案在不同狀態之間來來回回。先讀進一個版本，改兩行，寫回去，再讀回來，又發現問題再改。這些過程在上下文裡留下的是做生意的痕跡，知識反而沒增加多少。你在笨區裡繼續工作，等於背著一大袋雜物慢跑，又累又沒效率。

### 🗑️ 清空上下文，同樣有損

那就把上下文整個清掉，重新開始。在 Claude Code 裡，清空（clear the context）隨時可以做，誤清了也能在介面裡把清掉的對話恢復回來。但清空有個致命傷，它有損（lossy）。

有損的意思是資訊一旦丟掉就找不回來。清空上下文後，代理回到一張白紙，它必須重新探索程式碼，重新建立上一段對話裡早就知道的東西。你可以重新提示它「我們要對剛做完的部分做 QA，你先去探索一下、理解它為什麼存在」，它也會照做，但那是完整的二次探索，等於把已經花過的 token 再花一遍。

更糟的是，它會丟失那些重新讀程式碼也找不回來的東西，也就是你在 grilling 階段反覆確認過的關鍵決策。為什麼這個留言功能只開放給已註冊學生，為什麼採用一層回覆而不是扁平列表，還有軟刪除的決定是怎麼來的。這些「為什麼」活在對話裡，不在程式碼裡。程式碼只告訴你做了什麼，不會告訴你為什麼這樣做。清空上下文，等於把整個 session 裡最貴重的那部分，也就是你在 grilling 裡拍板的每一項決策與理由，一起扔進垃圾桶。

所以長 session 逼近邊緣時，真正要解決的，是怎麼把這個 session 的知識帶進下一個 session，又不必拖著一大堆噪音。

### 🔧 壓縮，把知識種進一個全新 session

答案叫做壓縮（compaction）。它是我們看到的第一個真正能在 session 之間保留東西的交接（handoff）機制。

基本動作很單純。把目前 session 的內容總結成一份濃縮的摘要，再用這份摘要啟動一個全新的 session。新 session 帶著上一場的知識開始，你在裡面繼續工作，就像剛才那場對話沒有中斷過。

**為什麼需要壓縮？** 繼續硬撐會退化、清空會丟決策，壓縮是唯一能把知識完整帶走、又不拖著噪音的做法。

[[learn/ai-coding-crash-course/elements/compaction|Compaction 壓縮機制 (Compaction)]] 有個好用的心智模型，把之前看過的子代理（sub-agent）機制倒過來想。子代理是你派一個代理出去做雜事，它做完回報結果。壓縮是把這個 session 榨乾，遞交給另一個 session。差別在於，子代理那個回合、那個目的都是你派出去就放手的，而壓縮牽涉的兩個 session，舊的那個和新生的那個，都在你的控制之下。你從一個 session 換到另一個，卻沒有離開你的代理，沒有離開你的工作目錄。

### ⚡️ 操作三步，壓縮的實際用法

在 Claude Code 裡，操作方式是在輸入框打出 `/compact`。它可以帶一個選用的總結指示（summarization instruction），也就是你希望它往哪個方向總結的一句話。

**為什麼要附上總結指示？** 負責做總結的也是一個大型語言模型（large language model），它需要盡量多的脈絡，才知道哪些資訊重要、哪些可以丟。你不必寫得多詳細，一句「我們接下來要對這個區域做 QA」就夠了。有了方向，總結者就知道該把專案長什麼樣、做了哪些決定、改了哪些檔案留進摘要，保住這些重點。

啟動之後，代理會顯示一個壓縮中的介面。趁著它在跑，有一個小技巧值得記住。你可以先排入訊息（queue a message），把壓縮完之後要做的下一件事先打進去排隊。壓縮一完成，代理就會自動接著處理你排入的訊息，你完全不必坐在那裡乾等。很多人就是傻傻盯著壓縮介面等它跑完，這完全是多花的等待。

另外要知道，壓縮可以跨工具通用（harness-agnostic），意思是不管你用哪個代理工具都適用。它在 Claude Code 裡存在，在 claude.ai 裡也存在，在 ChatGPT 裡也存在。學會這一招，換工具照樣能用。

### 📊 壓縮之後，長什麼樣子

壓縮的實際效果可以直接用數字看。一趟約十五萬個 token 的 session 被壓到約三萬個 token，示範裡實際讀出 28.3k。一瞬間就贖回了約十二萬 token 的聰明區空間，可以繼續做真正的思考。

壓縮也不只是把對話縮短。它對檔案有一套聰明的處理策略，代理在壓縮時會判斷哪些檔案對下一個 session 重要，再分成兩種做法。

- **逐字保留（verbatim）**。挑出幾個關鍵檔案，直接把完整內容留在上下文裡，一檔不漏。
- **存成檔案指標（file pointer）**。其餘檔案只在上下文裡存一個指向這個檔案的指標，不讀進內容，等真正需要時再按指標去讀。

所以壓縮出來的摘要是一份地圖加重點檔案，關鍵細節完整保留，體積則靠檔案指標壓下來。你可以按快捷鍵切換去看完整摘要。裡面會寫明主要請求與意圖，也就是使用者呼叫了 grilling；也會收進雙方同意好的完整規格，保留關鍵的技術概念；改過的檔案則全部列出來，每一處改動都濃縮成一條極度精煉的記錄，例如 `app/lib/comments：最小留言長度 1、最大留言長度 5000`。整份摘要就是上一場 session 內容的超高密度壓縮。

### 🏛️ 代價，歷史學家寫史書也會漏細節

到目前為止，壓縮聽起來像免費午餐，但它有代價。在付這筆代價之前，你得先看懂帳單長什麼樣。

負責壓縮的代理，有點像一位歷史學家回頭檢視你過去的那場 session，再為它寫一份歷史總結。用史學的詞彙來說，原始 session 裡實際發生的事，也就是當時在場者的紀錄，叫做主要史料（primary source）。壓縮出來的摘要叫做次要史料（secondary source），是主要史料的一份有損壓縮（lossy compression）。

任何交接機制都逃不開同一個定律，只要你建立一份次要史料，就必然流失一些資訊。歷史學家寫史書，是從當事人凌亂的筆記裡篩選、濃縮、組織。史書好讀、有條理，但現場的某些細節、某些微妙之處，在篩選的過程中註定被捨棄。壓縮也一樣。

所以這本質上是一個取捨（trade-off），用資訊換效率。你面前有兩條路，各有利弊。

- 繼續使用主要史料，你保有全部的資訊，但也背著全部的噪音。
- 改用次要史料，你獲得更大的迴旋空間、更少的上下文占用，但可能丟失主要史料裡的細節與微妙之處。

壓縮省下來的每一分聰明區空間，都是從資訊完整度裡擠出來的。它拿你不那麼需要的細節去換空間，效率不會憑空變出來。

### ✅ 最穩妥的用途，對完成品做 QA

既然壓縮有代價，什麼時候付這筆代價最划算？答案幾乎總是在對已完成的工作做 QA 的時候。**為什麼 QA 是最穩妥的用途？**

原因很簡單。到了 QA 階段，程式已經寫完、決策已經落地。你需要的是一張可靠的地圖，也就是這個專案長什麼樣、做了哪些事、有哪些檔案、有哪些約定。代理不需要再從零想一遍當時為什麼要做軟刪除。這種地圖式的知識，壓縮出來的摘要正好提供，而且幾乎不會損失。

而 QA 階段上下文裡塞滿的，是實作過程的噪音，一次次檔案讀寫、一版版的改動，還有反覆的探索，這些對 QA 毫無用處。所以在成品剛完成、準備驗收的這個精準時刻做壓縮，是一筆幾乎穩賺的交易。你丟掉的全是噪音，換回的全是空間。

這正是整個流程的節奏所在。Grilling 用對話把設計磨清楚，實作把聰明區燒乾，然後在階段的交界處，也就是從實作轉進 QA 的那一刻，用壓縮把知識帶進新的 session。壓縮就是那個讓你跨越多個 session、一直待在聰明區裡工作、卻不間斷的逃生門（escape hatch）。它補上了 Grilling 留下的伏筆，Grilling 省下來的聰明區空間終究會被實作耗盡，壓縮正是在耗盡之後把你救回來的機制。

### 📋 三條路放在一起看

把繼續、清空、壓縮三條路放在一起，用一張表把它們的差異攤開。

| 做法 | 資訊 | 效率 | 適合時機 |
| --- | --- | --- | --- |
| 繼續在同一個 session 工作 | 保有全部資訊，但背著大量檔案讀寫噪音 | 低，每輪重送全部歷史，品質在笨區緩慢退化 | 聰明區還有餘裕、主要史料仍然便宜時 |
| 清空上下文 | 有損，連「為什麼」一起丟掉，必須重新探索 | 中，零等待、完整聰明區，但二次探索要重花 token | 上下文真的可拋棄時，例如只是隨手試東西 |
| 壓縮並開啟新 session | 有損但保留重點，關鍵檔案逐字、其餘存檔案指標，「為什麼」的決策留在摘要裡 | 高，一瞬間贖回約十二萬 token 的聰明區 | 階段交界處，尤其成品已完成、準備做 QA |

### 🧭 實戰清單

把上面的機制收斂成幾個可以直接套在自己工作上的動作。

1. **在階段的交界處壓縮**。最自然的兩個交界面是實作結束、準備 QA，以及對齊完成、準備實作。**為什麼不要在途中壓縮？** 中途壓縮很危險，代理可能迷失方向、忘掉剛討論過的事情，甚至在壓縮前後改變程式寫法。
2. **啟動 `/compact` 時，附上一句總結指示**。總結者是模型，它需要方向才知道什麼該留、什麼該丟。一句「接下來要做 QA」就夠了。
3. **排入下一則訊息，別乾等**。壓縮進行中先把下一個指令排進佇列，壓縮一完成代理就自動接手。
4. **對已完成的作品做 QA，是最穩妥的用法**。這個時刻壓縮幾乎不會損失 QA 需要的資訊，卻能清掉整袋實作噪音。
5. **想在同一個目錄、同一個代理裡繼續時，把壓縮當預設選項**。跟清空上下文比起來，壓縮保留了「為什麼」，也留下了空間。

記住那個核心交易。壓縮用資訊換效率，遺失細膩度就是付出去的價格。搞清楚自己在付什麼、換回什麼，你就能在長 session 逼近聰明區邊緣時，從容地按下 `/compact`，避開在笨區裡越陷越深。
