# 「先想清楚」還不夠：plan mode 為什麼還是會衝

## Learning goal

能說出 plan mode 為什麼只是「會衝的緩衝」、過早完成（premature completion）如何驅動代理，以及設計概念（design concept）為什麼是實作前真正缺的拼圖。

## Lesson

### 🎬 一次沒有對齊的實作

用代理（agent）寫程式時，最常見的流程是這樣。你丟一句「幫我加一個功能」，它掃一遍程式碼庫，就直接開始改程式。整段過程裡，它不會停下來問你「我要做的真的是你要的嗎」，也沒有任何跟你確認的環節。它做完探索（exploration），緊接著就跳進實作（implementation）。

對熟練的使用者來說，這個流程太熟悉了，熟悉到像理所當然。但只要把標準拉高，你就會發現，它其實是一條很不負責任的生產線。你沒有驗證它蓋的是不是對的東西，它也完全不會主動尋求驗證。走運的時候，代理做出來的東西大致能用。但「大致能用」和「蓋對了」之間，隔著一條你自己都看不見的鴻溝。

你一定看過這一幕。你對自己的 repo 說「幫這個列表加排序」，代理立刻改了 API、補了測試、更新了文件，一口氣把整件事做完。你湊近一看才發現，它連「你想按什麼排、升序還是降序、要不要保留預設」都沒問你，就自己挑了最像樣的那種排法。它沒有做錯任何一步，卻可能做錯了整件事。原因很簡單，從頭到尾沒人跟它確認過「正確」的定義。

這種預設行為，也就是「代理自己決定一切、人完全被動」，正是這個主題要解決的核心問題。它有專屬的名字，叫做 [[learn/ai-coding-crash-course/elements/plan-mode-blindspot|Plan Mode 的盲點 (Plan Mode's Blind Spot)]]。

### 🧩 計劃模式，工具框架補上的緩衝

大部分的工具框架（harness），像是 Claude Code、Codex，以及其他 CLI 代理，其實都意識到這個問題。它們的內建解法叫做計劃模式（plan mode）。
在 Claude Code 裡，連續按 shift-tab 可以切進計劃模式，再把原本的提示（prompt）貼進去。接下來，代理會先探索程式碼庫、理解專案結構，然後寫出一份 `/plan` 文件（plan document），把接下來要做的事列出來。這份文件由你閱讀、修改，你滿意了才繼續往下。

本質上，計劃模式是在探索與實作之間，硬插進一個小小的緩衝（buffer），製造一個「動手前可以對齊（alignment）一下」的瞬間。

**為什麼這個緩衝重要？**
比起放任代理一路衝到底，計劃模式至少讓你在它動手之前有機會看一眼。你可以改計劃、要求它修正，然後才放行。到這裡為止，計劃模式看起來把對齊問題解決了。

### 🎯 盲點，計劃讀起來就像實作

拿課程評分功能當例子跑一次，你就會看到盲點在哪裡。計劃模式產出的 `/plan`，讀起來跟代理接下來要做的實作幾乎一模一樣。它沒有列出「我打算怎麼做、以及要跟你確認哪些問題」。它列出的是一整串實作決策，直接倒給你。

- 每個使用者對每個課程只能評一次分。
- 平均分在讀取時計算，寫入時不另外維護。
- 還沒有任何評分的課程，空狀態顯示「尚無評分」，不顯示零顆星。
- 只有已報名該課程的使用者才能評分。

這些決定看起來都很合理，對吧？問題就在這裡。代理沒有停下來問你「這真的是你要的嗎」。它只是把「急著寫實作」的衝動，換成「急著寫計劃」的衝動。它仍然在急著生產一份東西，只是這份東西從程式碼，變成了計劃文件。計劃模式擋住了「直接動工」，卻沒有擋住「急著交差」。它給你的，只是代理接下來要做的實作的提早抄寫。真正的對齊，從頭到尾沒有發生。

每一條決定背後，都藏著一個代理替你做的選擇。把這幾條決定攤開來，每一條背後是什麼判斷，一眼就清楚。

| 計劃裡的決定   | 背後是什麼判斷 |
| -------------- | -------------- |
| 能不能重複評分 | 產品規則       |
| 平均分何時算   | 資料層的取捨   |
| 空狀態顯示什麼 | 介面語言的決定 |
| 誰有資格評分   | 權限模型       |

這些全部都是需要人拍板的判斷。代理一個問題都沒問，就自己全部定案了。你讀計劃時之所以覺得「都合理」，是因為它挑的答案剛好合理。它完全可以挑一個不合理、甚至跟你意圖相反的答案，而你根本沒有機會攔下它。

### ⚡️ 過早完成，代理的諂媚特質

為什麼代理會這樣？驅動代理的，是一種「衝到終點」的傾向，叫做過早完成（premature completion）。過早完成被形容成代理的一種諂媚特質（sycophantic trait）。你叫它生產什麼，它就生產什麼。你叫它寫程式，它就衝去寫程式。你叫它寫計劃，它就衝去寫計劃。它不會在動手之前，先停下來確認自己有沒有做好「雙方到底要蓋什麼」的功課。因為那項功課不會變成可以被交付的產出物，代理對它沒有衝動。

把「對齊」想成一件需要做的準備工作（legwork），包括確認需求、確認取捨、確認邊界。這份準備工作不會產生程式碼，也不會產生文件，它只會產生共識。對一個只想交差的代理來說，這是最容易跳過、也最先被跳過的部分。過早完成，就是這個跳過動作的名字。它描述的不只是動作太快，還有終點選錯了。代理把「完成」定義成「把東西生出來」，正確的做法，應該是「把對的東西生出來」。

這對你意味著什麼？你看到一份詳盡的計劃文件，並不代表可以安心。計劃越詳盡、越像實作，越說明代理只是把它要做的事提早抄了一遍。真正的共識沒有發生。那份計劃是代理自言自語的筆記，不是你們共同的設計。

### 🧱 蓋錯東西，代價看功能複雜度

這個失敗模式（failure mode）叫做「蓋錯了東西」（build the wrong thing）。代理自顧自地把功能蓋完，最後做出來的不是你要的。它的嚴重程度，完全取決於功能有多複雜。

| 功能複雜度               | 蓋錯的代價                                              | 該怎麼做                       |
| ------------------------ | ------------------------------------------------------- | ------------------------------ |
| 簡單功能（例如課程評分） | 低，了不起重來一次，代價很小                            | 可以容忍，不必過度防禦         |
| 複雜功能                 | 極高，時間、token、程式碼牽涉範圍都大，重做成本無法估量 | 必須在實作前做好對齊，絕不能賭 |

**為什麼這張表很重要？**
它幫你一眼判斷這次該不該賭。在簡單功能上蓋錯，了不起重做，代價很小。在複雜功能上蓋錯，你花了大把時間和 token，讓代理蓋出一棟歪樓，重做的成本高到無法接受。更麻煩的是，你可能根本不知道自己是從哪一步開始理解偏的。方向錯得越晚發現，浪費的資源就越可觀。

想想一個真人開發者這樣做事。你說「幫我建個功能」，他回一句「我知道怎麼蓋」，然後埋頭就做，全程不跟你確認。這在任何專業協作裡都無法接受，因為中間完全沒有發展出共享理解（shared understanding）的過程。代理的預設行為正是如此，所以這份功課，必須由你來補。

### 💡 真正缺的拼圖，設計概念

那該補的是什麼？一份更詳細的計劃文件，並不會解決問題。真正該補的，是一個叫做 [[learn/ai-coding-crash-course/elements/design-concept|設計概念 (The Design Concept)]] 的東西。這個概念出自 Frederick P. Brooks 的《The Design of Design》。Brooks 也是《人月神話》（The Mythical Man-Month）的作者。他在這本書裡對設計概念的講法，比這本書本身更值得讀。

設計概念不屬於資產（asset）。它沒有文件，沒有圖，也不會是任何可以交付的成品。它是當一群人在一起設計某樣東西時，飄盪在房間裡的那個概念。每個人腦中都有一個稍微不同的版本，你有一個版本，代理或你的同事有另一個版本。讓它慢慢變清晰的，是對話。隨著對話展開，隨著你們一起搞清楚到底在蓋什麼，所有人的理解開始逐步變銳利，最後收斂成同一個共識。

注意這裡的動作是「銳利化」，不是「寫下來」。文件可以把結果記錄得很詳細，但文件無法產出那個過程。對話才是那個過程本身。當對話真的發生，你會得到一種跟代理「站在同一頁」的感受。這份感受的來源，是你們對要蓋什麼有了一致的理解。那份理解，才是實作之前真正該有的東西。

設計概念靠對話成形，光靠文件長不出來。回頭對照，無論是直接實作，還是後面的計劃模式，整個流程裡都沒有出現過設計概念。沒有哪一刻，是你們停下來互相確認「我們要蓋的，我們真的對齊了嗎」。代理只是在滿足生產資產的衝動，只是換了一種形式。

### 💬 真的有對齊，會長什麼樣

拿剛才的評分功能繼續想。如果代理真的想跟你對齊，它該問的是這類問題。

- 「評分是給學生評，還是老師也能評自己的課？」
- 「同一個人能改評分，或者反悔嗎？」
- 「平均分要在所有頁面即時顯示，還是只在課程頁顯示？」
- 「如果一門課完全沒人評，要顯示零顆星、『尚無評分』，還是直接不顯示？」
- 「評分資料要不要考慮給管理員看？」

這些問題沒有一個有標準答案，全都取決於你想怎麼用這個功能。

你不需要替它把答案想好，你只需要讓它問。每一次問答，都是在把雙方腦中那個「評分功能」的想像攤開來對照。它以為的評分範圍，跟你以為的不一定一樣。它以為的權限，跟你以為的可能相反。談過之後，你才會發現，原來兩邊想的根本不是同一個東西。這個發現，正是對齊的全部價值。沒有這段對話，你甚至不會知道自己需要對齊。

### 🧊 計劃模式，一個生產資產的緩衝

把三種做法擺在一起看，計劃模式的定位就清楚了。

|                | 直接實作 | 計劃模式           | 對齊階段   |
| -------------- | -------- | ------------------ | ---------- |
| 產出物         | 程式碼   | `/plan` 文件       | 共享理解   |
| 有沒有對話     | 沒有     | 沒有               | 有         |
| 有沒有設計概念 | 沒有     | 沒有               | 有         |
| 結論           | 衝向資產 | 仍是衝向資產的緩衝 | 真正的對齊 |

計劃模式確實往前邁了一步。它給你一個動手前「看一眼」的瞬間。但它仍然只是一個生產資產的緩衝，對齊本身沒有發生。你需要的是一個真正的對齊階段（alignment phase），一段發生在實作之前、靠對話把共識磨清楚的時間。

### 🛠️ 把這用到你自己的代理工作上

回到你自己的終端機。下次你對 Claude Code 或 Codex 說「幫我改這個」之前，可以先做三件事。

第一，認清工具的本質。計劃模式值得用，但不要以為切進去了就安全了。看到 `/plan` 讀起來跟實作幾乎一樣、而且代理從頭到尾沒有問你任何問題，這是警訊，不是好消息。

第二，把注意力放在代理替你默默決定的地方。讀計劃時別照單全收，專挑那些「它替你做了選擇」的點來挑戰，像是誰能用、資料怎麼算、空狀態長什麼樣、權限怎麼設。這些才是對齊真正該發生的地方。讀懂計劃，是為了挑戰計劃。

第三，在實作前強制一輪對話。就「要做什麼（what）」和「為什麼這樣做（why）」跟代理來回問答，回答它的問題，推翻你不認同的建議。這一段對話，就是讓設計概念浮現並變銳利的過程。它會去掉代理那股諂媚的資產衝動（asset rush），讓你有種「我們站在同一頁」的對齊感。到這個地步，實作反而變成一件幾乎只是照著走的事。具體怎麼做，就是這個節點接下來的重頭戲，Grilling 對齊法。
