# 動手前把設計談清楚：grilling 對齊法

## Learning goal

能親自跑一場 grilling，用「做什麼（what）+ 為什麼（why）」的輪問把設計談清楚，在實作前把自己放在主導位置，並說出它為什麼那麼節省上下文。

## Lesson

### 📝 這節課要做什麼

Grilling 對齊法要解決一個非常具體的問題。動手寫程式之前，先讓代理（agent）把你腦中的設計一題一題問清楚、談明白，避免蓋出你不想要的東西。我們會先看一個失敗的場景，拆解 grilling 的兩個關鍵機制，跑一遍課程留言功能的完整案例，最後算一算它為什麼如此節省上下文，並把它搬回你自己的工作上。

### ⚠️ 先看一個失敗場景

你叫代理「幫我建一個課程評分功能」。它先探索（exploration）一下程式碼庫，接著二話不說開始寫程式。結果如何？運氣好一點，方向對、細節全錯；運氣差一點，整個概念都偏了。你拿到一個不想要的東西。這種失敗模式叫「蓋了錯的東西」（build the wrong thing），正是 [[learn/ai-coding-crash-course/elements/plan-mode-blindspot|Plan Mode 的盲點 (Plan Mode's Blind Spot)]] 指出的問題。就算你開了計劃模式（plan mode），代理也只是把「急著寫程式」換成「急著寫計劃」。那份計劃讀起來跟實作一模一樣，它仍然沒有停下來問你，這真的是你要的嗎。

問題的根源是，真正的對齊（alignment）缺席了。對齊的意思是，雙方對「要蓋什麼」有共同理解。[[learn/ai-coding-crash-course/elements/design-concept|設計概念 (The Design Concept)]] 把對齊講得很明白。對齊是「飄盪在房間裡」的那個共識，一種雙方都抓得到、卻無法打包交付的狀態。你腦中有一個版本，代理腦中有另一個版本，只有靠對話，共識才會逐步變銳利（sharpen）、收斂成同一個畫面。一份文件、一個計劃、任何可以交付的資產（asset）都放不下它。文件寫得再詳細，都取代不了這段對話。Grilling 對齊法，就是補上這段對話的技術。

### 🔍 Grilling 是什麼

[[learn/ai-coding-crash-course/elements/grilling|Grilling 對齊法 (Grilling)]]，中文可以叫「盤問式對齊」，是一種在實作（implementation）開始之前先進行對齊的技術。它的核心主張很直接。Grilling 把順序倒過來，要你一開始就讓代理當面試官，一題一題問你這個功能要做什麼、為什麼要做。你逐題口述答案，幾輪下來，雙方腦中對「要蓋什麼」的畫面逐步合而為一。等設計問清楚了，之後的實作只是照著這份共識走，順得像在抄答案。

Grilling 把前面兩個概念接到一起。它承認 plan mode 只是一道「生產資產的緩衝」，真正的對齊在那一階段還沒有發生。它也知道設計概念要靠對話成形，靠文件成形不了。於是它把那場對話變成一個明確的、放在實作之前的階段，用一整輪「做什麼（what）＋為什麼（why）」的問答，把設計概念逼出來、磨清楚。

### ⚙️ 機制一，探索與提問同時進行

grilling 的第一個關鍵機制是「探索與提問並行」。代理一進入 grilling，就啟動一個探索器（explorer）子代理（sub-agent）。掃描整個程式碼庫的工作，被丟給一個背景（background）任務去做。這個背景探索是非阻塞（non-blocking）的，它不會擋住代理向你丟問題，你也不用等探索完成才能開始回答。

為什麼要這樣設計？因為子代理可以「先走開，之後再帶資訊回來」。你回答第一輪問題的同時，探索器正在把程式庫翻過一遍。等它探索完，就帶著新發現回來，產生下一輪更深入的問題。例如「這裡有個重複的權限檢查」「這裡的渲染器沒消毒」。人的回答與程式的探索同步進行，整場對齊又快，又不會浪費等待時間。這就是所謂的子代理與協調者（orchestrator）分工模式。主代理當協調者，把探索這類髒活丟給子代理，等結果回報。

### 🔄 機制二，一輪一輪的問答

第二個關鍵機制是「輪問」（round）。代理不會一口氣把問題全倒給你，而是一輪一輪來。先問基礎的，等你答完、背景探索也完成一部分，再丟出下一輪更深入的問題。就留言功能這個案例來說，前後共約 40 題，分了好幾輪。

而且它不只在問「做什麼」，也在問「為什麼」。這個功能到底要幹嘛、為什麼要建、誰會用，資料又該怎麼存。每一題都在逼你把設計想得更清楚。

### 💬 你的工作，逐題口述答案

整場 grilling 最耗你心力的部分，也正是它價值所在的地方。你必須逐題口述答案。代理每丟回一輪，你就把每一題的回答打進輸入框，幾輪下來累積成一份完整的設計。

每一題你有三種合法的回答。

- **同意**。多數時候你會同意它的建議。代理探索過程式庫、知道現況，它的建議常常是合理的。
- **推翻**。該推翻時要真的推翻，實戰裡這也常見。
- **交給它決定**。「我不在乎，你決定」也是一種合法回答，代表你把某個不重要的小決定委託出去，它接著做就好。

很多人以為 grilling 就是要跟代理吵架。實際跑下來，多數時候你確實會同意它的建議。重點是，該推翻的時候你有權力推翻，不想決定的事情也有權力丟回去。三種回答交替使用，才是一場健康的對答。

結構上，代理做這件事的本質是「引出」（elicit）。它從你身上挖出更多資訊，而這些資訊會讓它產出更好的結果。你答得越具體，它越知道你要什麼。

### 🧪 完整案例，課程留言功能

把機制套進一個真實案例，看看整場 grilling 長什麼樣。初始提示很簡單，就是你直接打進輸入框的一段話。

> 我想建一個課程留言功能。學生應該可以對他們有權限存取的課程留言，講師也應該可以留言。就先從這裡開始吧。

代理載入 grilling，開始探索、丟問題。以下是幾輪下來產生的關鍵決定。

#### 第一輪，把功能說清楚

- **這個功能到底要幹嘛？** 用途是 Q&A 與支援，再帶一點社群討論。健康的留言區對學生很有用。
- **沒人留言時怎麼辦？** 代理建議「先不開放留言，直到流量能支撐為止」。人否決了這個建議，改成設計一個好看、鼓勵留言的空狀態（empty state），不要讓學生一進來就被澆冷水。
- **誰來管理留言？回應時間承諾是多少？** 代理假設「你」就是講師，這個假設是錯的，這個功能是給其他講師用的。回應的期待要有。
- **自己建還是買現成的？** 自己建。
- **為什麼要把留言門控（gating）在有權限的學生？** 對看不到的課程留言本來就很奇怪，而且這是付費權益的一部分。
- **講師留言是同一個功能嗎？** 代理把它列成第二個項目，但講師回覆學生問題需要在視覺上區分。人決定一張表、一個留言功能，講師掛徽章（badge）。

#### 背景探索完成後，問題更深入

第一輪答完，背景探索完成，代理帶著更多問題回來。

- **這是真實產品還是教材？** 是教材，但請把它當成真實產品對待，否則就不是好的教材。
- **存取用「已註冊」還是「已購買」判定？** 用已註冊（enrolment）。沒有第二道閘門（地區定價），看不到課程就等同未註冊。
- **未登入或未註冊的使用者，應該看到既有留言嗎？** 代理建議顯示，人強烈否決。留言只在課程內部保密，這是付費權益的一部分。
- **程式碼品質**。代理發現權限檢查內聯（inline）複製在很多地方，建議抽成共享 helper。這個改動併進這次的工作，但重構只限留言會碰到的路由。

到這裡，人已經感覺「非常對齊了，我可以看到那個東西正在被建出來」。這正是設計概念開始成形的時刻。實作感覺起來幾乎是小事一樁，因為所有困難的決定都做完了。

#### 第二輪，討論串與佇列

第二輪又來了十題，處理討論串模型（threading model）與佇列（queue）。

- **討論串模型**。先做扁平列表（flat list），V1 不需要明確的已解決（resolution）狀態。
- **講師佇列頁**。講師儀表板上有一個專門的佇列頁（queue page），列出所有「未回答的問題」，也就是有近期留言、而講師還沒看過沒回過的討論串。
- **留言支援語法高亮**。
- **編輯與刪除**。作者可以無限編輯自己的留言。採用軟刪除（soft delete）。擁有課程的講師和管理員，可以刪除任何人的留言。
- **排序**。留言舊在前（oldest first），分頁（pagination）先不做。
- **存取權到期**。留言保留，繼續標示原作者。
- **共享 helper 的形狀**。我不在乎，你決定。

#### 第三輪，代理自己抓出一個矛盾

第三輪處理通知、資料表結構（schema）與種子測試資料。正是在這裡，代理主動指出一個矛盾。

> 你選了「扁平列表＋不設已解決狀態」，又要一個「未回答問題佇列」。但在扁平列表裡沒有討論串的概念。每則留言都是頂層，誰也不指向誰，根本湊不出「某個討論串還沒被回答」。

人接受了這個指正，改成一層回覆（one-level replies）。學生留言是頂層，講師回覆掛在下面。也因此，軟刪除變得更重要。刪掉父留言時要能保留它的回覆，所以不能用真的把資料列刪掉的那種刪法。

第三輪還有兩個關鍵發現。

- **安全漏洞**。探索器回報，現有的 Markdown 渲染器完全沒有消毒（sanitization），原始 HTML 直接穿透。人同意代理的建議，用受限渲染器（restricted renderer）只對學生留言消毒。
- **通知**。學生怎麼知道自己的問題被回答了？V1 先延後，之後再處理。

#### 收尾，把細節敲定

收尾的一輪把剩餘細節敲定，約 40 題的總數也在這裡完成。

- 誰可以回覆，討論清楚。
- 什麼叫「已回答」，管理員回覆也算已回答。
- 佇列頁可以內嵌回覆。
- 佇列排序最新在前（newest first）。萬一誤標了不需要回答的回覆，它會自然沉下去，不會一直卡在頂端。

### 💰 為什麼它如此節省上下文

grilling 最漂亮的地方在它的成本。這裡先墊一個名詞。模型一次能看的文字量有個上限，叫做上下文視窗（context window），所有送進去的東西都以 token（模型讀寫文字的最小計價單位）計價。在視窗的某個深度以內，模型表現最好，那一段叫「聰明區」（smart zone）；超過之後就進入「笨區」，表現會慢慢退化。

**為什麼「聰明區」很重要？** 對齊和實作都想待在聰明區裡，模型的判斷力才全程在線。

grilling 進行到一半，上下文（context）大概只有 2 萬個 token。全部答完，也不過 3.3 萬個 token。對照之下，當時的模型在約 15 萬個 token 之後開始進入笨區。所以 grilling 結束時，上下文視窗裡還剩約 12 萬個 token 的聰明區，可以全部留給實作。

實作階段跑了 14 分 28 秒，衝到約 15.5 萬個 token，剛好壓在聰明區的邊緣。也就是說，對齊只花了很小的代價，卻讓整個工程階段都待在思考餘裕充足的聰明區裡。用下面的表格總結成本。

| 階段 | 花費 | 說明 |
|---|---|---|
| grilling 進行中 | ~2 萬 token | 純對話，探索藏在背景的子代理 |
| grilling 結束 | ~3.3 萬 token | 剩下約 12 萬 token 的聰明區給實作 |
| 實作結束 | ~15.5 萬 token（14 分 28 秒） | 剛好壓在聰明區邊緣 |

實作結束後，人沒有清掉上下文。因為那些「為什麼要這樣做」的對齊成果還留在工作階段（session）裡，清了就丟了。正確做法是直接續著實作，讓對齊的成果繼續在後續的每一個請求裡起作用。

### ✅ QA 結果，對齊了，沒有被坑

實作完畢後的 QA 大致順利。貼文、回覆、編輯（顯示「已編輯」）、刪除自己的留言都正常。軟刪除掉的父留言，它的回覆仍然顯示，父留言顯示「這則留言已刪除」，下面還掛著原本的回覆。講師的「未回答問題佇列」能列出問題，並在佇列頁內嵌回覆。只有幾個小視覺瑕疵，問題頁上兩個導覽連結同時亮著，空狀態不夠漂亮。

整個對齊的成果，可以用一句話總結。「aligned, not cheated」，也就是「對齊了，沒有被坑」。成品和人腦中的想法一致，不是代理擅自造出來的東西。它沒有猜你要什麼。它問了你，然後照著你的答案蓋。

### 🎯 哲學，把控制權還給人

grilling 刻意要求你動腦。它很耗你，一題接一題地回答，幾乎沒有偷懶的空間。而這正是它的目的。市面上很多技術框架傾向「降低人的參與、把權力交給代理」，結果人變成旁觀者，只能祈禱它做對。grilling 反過來走。它逼你逐題回答、為每個決定拍板。遇到不合理的建議，就直接反駁。最後你會覺得自己更像主導者，更理解整個進行的過程，而沒有被代理牽著走。

另一個值得記住的觀察是，每個人的 grilling 結果會不同。代理的行為是非確定性（non-deterministic）的。同樣的提示，它問你的問題可能完全不一樣，你做出的決定自然也不一樣。這個特性正好證明，這項技術把主導權還給了人。它產出的是「你的」設計，不是別人的，也不是一份標準答案。

### 🛠 搬回你自己的工作上

把 grilling 搬回你自己的代理工作（例如 Claude Code 或類似 harness），照著這六步走。

1. **把「對齊」變成實作前的固定階段**。不要一開口就「幫我建 X」。先要求代理探索程式庫，然後逐題問你。現成的 skill（例如 grill me）可以做這件事，自己來也行，讓代理讀完程式庫，向你提問。
2. **對每一題，明確說出「是什麼」和「為什麼」**。代理問的不只是功能規格，還包括動機、對象、取捨。你回答得越具體，後面實作越不會走偏。
3. **別照單全收**。看到代理附帶的建議，同意是合法的選擇。「我不同意，改成這樣」更常見。偶爾「我不在乎，你決定」也是合法的答案。案例裡幾個最重要的決定，留言只限課程內部、門控在已註冊學生、一張表加講師徽章，全是人推翻代理建議換來的。如果全程只會說「同意」，等於把主導權又還給了代理。
4. **讓代理主動抓矛盾**。案例裡「扁平列表 vs 未回答佇列」的衝突，是代理自己指出來的。遇到這種矛盾不要硬吞，把它當成設計變得更清楚的機會。
5. **用「實作前我是不是覺得很順」來驗收**。對齊成功的徵兆是，你覺得「接下來蓋起來很簡單」，因為難的決定都做完了。如果進入實作前你還有模糊感，還在想「它大概會幫我決定吧」，那代表還沒對齊夠。
6. **別急著清上下文**。grilling 結束後不要立刻清掉工作階段，那會把你和代理好不容易建立的共享理解丟掉。直接續著實作，讓那些對齊成果繼續留在上下文裡，餵給後續的每一個請求。
