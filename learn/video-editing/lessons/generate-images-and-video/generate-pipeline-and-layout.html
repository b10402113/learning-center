/generate 的四步管線與資料夾佈局

Step 2/5 · 用 /generate 生圖生影

學習目標

學完這一節，你能說出 `/generate` 從收到指令到存檔的四個步驟，並看懂工作區裡每個資料夾分別負責什麼、為什麼要這樣分。

前言：一句「幫我生張縮圖」之後，發生了什麼？

上一節說明了為什麼值得用自架的方式取代訂閱服務。但當你真的在對話框打下一句「幫我生一張影片縮圖」，中間到底發生了哪些事？如果是黑盒子，你只會看到最後跑出一張圖，中間怎麼選模型、用哪把金鑰、花了多少錢，一概不知。

這一節要把黑盒子打開。你會看到整個流程其實只有四個步驟，而且這四步全部寫在一份 Markdown 文件裡，你的 agent 每次動手前都會先讀它。先掌握這張全貌，後面幾節的設定與寫檔才不會像在背指令。

skill 是什麼：一份 agent 動手前會讀的 playbook

先釐清一個常被誤會的詞。這裡說的 skill，不是什麼需要編譯的程式，而是一個裝著 Markdown 檔案的資料夾，你的 agent 在採取行動之前會把它讀過一遍，就像照著一本作戰手冊（playbook）辦事。你的 `/generate` skill 就是一本「生媒體」的手冊：當你輸入「generate a thumbnail of X」，agent 會照著手冊跑完下面四個步驟。

因為它只是文件，所以你可以自由修改、加入硬性規則。這也解釋了為什麼後面會把成本護欄、資料夾規則寫進 skill 裡，agent 每次都會讀，寫一次就能一直生效。

四個步驟：Route → Prep refs → Generate → Log

整條管線的名稱與動作如下：

步驟做什麼關鍵原則
1. Route（路由）挑出適合這個任務的模型，以及能跑它、最便宜的供應商，然後讀該模型的 recipe 檔先看最便宜的路，不行再退到下一家
2. Prep refs（備妥參考）從 refs 資料夾載入真實的參考圖（logo、人臉、風格照）絕不用文字描述一個 logo
3. Generate（生成）照 recipe 呼叫 API；若是非同步任務就輪詢；把檔案扁平地存進 generations 資料夾async 要耐心輪詢，結果要立刻下載
4. Log（紀錄）在檔案旁寫一個小的 JSON 記事，記下是哪個 prompt、模型與設定做的可選，但價值極高

這四步裡，第一步與第二步是最容易被做錯的地方。Route 做錯，你可能用貴三倍的價格跑同一顆模型；Prep refs 偷懶用文字描述 logo，回來的圖幾乎一定走鐘。第三步的技術細節（尤其是非同步輪詢）留到 recipe 那一節再細講，這裡先建立順序感就好。

你會得到的資料夾佈局

這套系統最後會在你的工作區留下固定的結構，長這樣：

your-workspace/
├── .claude/skills/generate/
│       ├── SKILL.md               the brain: routing table + rules (page 4)
│       └── models/
│           ├── image-model.md     one recipe file per model (page 5)
│           └── video-model.md
├── generations/                   every output lands here, flat, no subfolders
│   └── refs/                      logos, faces, style references you reuse
└── .env                           your API keys (page 3)

看懂這個結構，你其實就看懂了整支 skill 的分工。其中三個設計決定特別值得記住：

  • 為什麼只有一個扁平資料夾？ 你所有生成成果都放在同一個地方，任何 gallery、儀表板或腳本都能零設定地讀取它，包括後面會做的 gallery 牆。資料夾位置隨你選，但選定後就不要移動。
  • 為什麼一個模型一個 recipe 檔？ 模型每個月都在換。當有更好的模型出現，你只要新增一個 Markdown 檔，skill 就學會它了，其他東西完全不用動。
  • 為什麼規則要寫進 skill？ 因為 agent 每次都會讀。成本護欄與資料夾規則只要寫一次，就會一直被執行。

這套流程怎麼運作：從路由到自動收進 gallery

把視角拉近到 agent 實際的行為：當你呼叫 skill，它先路由模型，預設去找來源裡最便宜的選項，例如先在 Kie 找，Kie 不可用再退到 fal，再退到 WaveSpeed。接著它載入參考圖並撰寫 prompt，因為用的是 Claude 這類模型，這一步很靈活，你甚至可以在真正生成之前先檢查 prompt。第三步才是實際生成媒體，呼叫模型把圖或影片做出來。

最後一個常被忽略的步驟是紀錄機制：把送給模型的 prompt 全部存下來，之後需要回頭查就有得查。成果則會自動載入到一個「generations」列表，一個像無限畫布的瀑布流網格，圖和影片都攤在同一處。這件事對設計很重要：你不能只活在終端機或對話視窗裡，得看得見 agent 到底生了什麼，才有辦法判斷好不好。

而當你擁有自己的素材庫，就能加上客製功能。例如一個 styles 區：點一下某個「電影感液態玻璃」風格，它就複製該風格的 prompt 加上參考圖檔路徑，你可以直接送給 Claude 重現這個風格。這讓「風格」變成可以重複套用的資產，而不只是一次性的 prompt。

把這張全貌放回腦中

`/generate` 是一份 Markdown 作戰手冊，agent 每次動手前都會讀。它跑四步：Route（挑最便宜的可用模型並讀 recipe）→ Prep refs（載入真實參考圖）→ Generate（照 recipe 呼叫 API、必要時輪詢）→ Log（在檔案旁寫 JSON 紀錄）。成果扁平地收進 generations 資料夾，再自動進 gallery。一個扁平資料夾、一模型一 recipe、規則寫進 skill 這三個選擇，就是整套系統耐用的原因。

知道了流程長什麼樣，接下來就輪到動手。下一節會從最實際的兩件事開始：把三個聚合商的 API key 寫進 `.env`，然後寫出那份掌管一切的 `SKILL.md`。
