# MEMORY — design-pattern

## Goal
在架構師/資深崗面試或晉升評審中，能講清楚設計模式的**權衡與適用邊界**：不只說得出某個模式的意圖和結構，還要能在「何時用、為何用、何時不該用、與相似模式怎麼選」這些層面講出深度。

## Why
職業成長需要。想從「會用框架、會寫業務」的工程師，往上走到「會設計、能扛架構」的位置——設計能力是這條路的必經門檻。學習偏概念導向（declarative），因為目標是要能「講得出來」，而不只是「會動手」。

## Prior experience
- Java 後端 + Spring 系列，日常寫業務 CRUD / 接口
- 用過框架（Spring、MyBatis 等）但**沒讀過框架原始碼**
- 有大型系統 / 微服務開發經驗，理解分布式、多服務協作
- 用過 Spring 的 DI / AOP / 自定義 starter 中間件
- 用過 Redis（緩存、可能含分佈式鎖/多級緩存）
- 發過 MQ / 事件，知道訂閱方通知、事件監聽

## Anchors
- 堆過「一個類幾千行、ifelse 分支堆出來」的業務大類型——「一坨代碼」的切身記憶
- 重構過：把 ifelse 拆成策略/狀態後，代碼明顯變好維護——**最深的切膚之痛也是最大的甜頭**，這是 WHY 的活例子
- Spring DI / AOP / starter 中間件都用過——講到工廠、代理、裝飾、外觀時可以掛
- MyBatis mapper 接口「沒實現類卻能調用」——代理模式的最佳鉤子（即使沒讀過源碼，行為體感是真實的）
- 發過 MQ / 事件——觀察者模式、事件監聽的直接經驗
- 用過 Redis 緩存——享元模式的「共享對象、外部狀態」可以掛上

## Habits & constraints
- 每週約 1–2 小時，**碎片化**學習——內容要能分成小塊讀完，不要一篇長文壓下來
- 有 IDE、能跑代碼，但碎片時間下不保證每次都動手——教學可配代碼對照，但不能要求「必須自己跑」才學得會
- 學習環境：工作機為主

## Knowledge type
mixed，但以 **declarative（概念為主）** 為重——面試要的是「講得出意圖、結構、適用邊界、與相似模式的取捨」；動手（procedural）是輔助驗證，不是主目標。

## How to teach me
- **好壞代碼對比**：一本書式的「一坨 ifelse 代碼 vs 模式重構後」對比最能讓我記住——每個模式先給壞味道，再給重構
- **場景→模式**：先講真實業務場景（發獎、支付、審批、搖號…），再抽象出模式，不要反過來先甩定義
- **帶問答自測**：學完要有自測/提問，否則碎片時間下看完就忘
- 最容易走神：**抽象概念轟炸**——沒有場景、沒有對比、純理論羅列（尤其開頭）會直接勸退
