# Part digest 1 — 前言, 工厂方法, 抽象工厂, 建造者

## Overview (L1)

- 前言+阅读建议+参考资料+目录 (preface / reading advice / references / TOC) — The book is a hands-on (not theory) Java design-pattern tutorial: 22 real internet business scenarios (trading, marketing, 秒杀, middleware, source code) from author 小傅哥, each chapter teaching one GoF pattern by contrasting a "ifelse pile" implementation with a pattern-refactored implementation in Maven projects (`itstack-demo-design-N-00/01/02`). Design patterns trace back to Christopher Alexander's 《建筑模式语言》 (253 patterns), applied to programming by the Gang of Four's 1994 《设计模式：可复用面向对象软件的基础》; readers who never studied patterns still converge on the same 高内聚、低耦合、可扩展、可复用 principles through experience.
- 目录/创建者模式 intro (TOC + creational intro) — The TOC organizes 22 patterns into three families (创建型×5, 结构型×7, 行为型×10), each table listing 类图稿 (diagram), 业务场景 (business scenario), and 实现要点 (implementation essence). Six principles govern the whole book: 单一职责 (one class/method does one thing), 里氏替换 (polymorphism, subclasses extend parents), 依赖倒置 (details depend on abstraction), 接口隔离 (single-purpose interfaces), 迪米特原则 (least knowledge, reduce coupling), 开闭原则 (abstract architecture, extend by implementation). The creational intro states these patterns provide object-creation mechanisms that improve flexibility and reusability of existing code. Suggested learning method: study each chapter alongside its code, run it, then reflect on how to apply the pattern in your own business; the reference sources are refactoringguru.cn and runoob.com.
- Teaching style — Every chapter follows: 开发环境 (JDK 1.8 + Idea + Maven), pattern intro with refactoringguru image, 场景模拟 (business scenario + the scenario-simulation project with third-party-style interfaces), 一坨代码实现 (the ifelse/直接实现 project), 设计模式实现 (the refactored project: 工程结构 tree + class diagram + code), 测试验证 (JUnit test + log output), 总结 (pattern summary: satisfied principles, benefits, and trade-offs).

## Sections (L2)

### factory-method (工厂方法模式)

- Locator: `[[sources/design-pattern/design_pattern#工厂方法模式]]`
- Summary: The first chapter uses a marketing 积分兑换 prize-awarding scenario. Three incompatible third-party prize interfaces exist — 优惠券 `CouponResult sendCoupon(uId, couponNumber, uuid)`, 实物商品 `Boolean deliverGoods(DeliverReq req)`, 第三方爱奇艺兑换卡 `void grantToken(bindMobileNumber, cardId)` — with different return types and params, and more product types will come as business grows. The ifelse version is a single `PrizeController.awardToUser(AwardReq)` that branches on `awardType` (1/2/3), calling each service inline and mapping results to `AwardRes`; it works and passes tests but each new product type means editing the controller, and maintenance/refactoring cost grows ("开发一时爽，重构火葬场"). The factory-method refactor defines interface `ICommodity.sendCommodity(uId, commodityId, bizId, extMap)` implemented by `CouponCommodityService`, `GoodsCommodityService`, `CardCommodityService` (each wraps one third-party service, unifies inputs/outputs, throws RuntimeException on failure), plus a `StoreFactory.getCommodityService(Integer commodityType)` that returns the right impl. Factory method = define a creation interface and let subclasses decide which factory class to instantiate, deferring creation to subclasses.
- Key claims: The pattern decouples the creator from concrete product logic, satisfies 单一职责 (each business logic lives in its own class), and satisfies 开闭原则 (new product types can be added without changing callers); its weakness is rapid subclass proliferation with many product types, which later pattern combinations mitigate; the factory can also use switch or map-configuration instead of if-chains; running the refactored project makes the whole prize-awarding flow visible as a unified, well-structured service.
- Learner-relevant: This is the book's canonical "ifelse → factory" before/after example; it can anchor the 开闭原则 and 单一职责 elements, and motivate why code structure (not just feature completion) matters for iterative business growth.

### abstract-factory (抽象工厂模式)

- Locator: `[[sources/design-pattern/design_pattern#抽象工厂模式]]`
- Summary: The scenario is upgrading a single-node Redis to clustered Redis without affecting running systems. The existing system hard-codes `RedisUtils` method calls everywhere; the upgrade introduces two cluster services — `EGM` (method `gain`) and `IIR` (method `get`) — which do the same job with different method names (like Mac vs Windows). The ifelse version adds a `redisType` param to every `CacheService` method (`get(key, redisType)` etc.), branching 1→EGM, 2→IIR, default→RedisUtils; it works but forces every caller to carry the type flag and becomes unmaintainable. The abstract-factory refactor adds adapter interface `ICacheAdapter` (get/set/set-with-timeout/del) implemented by `EGMCacheAdapter` (mapping gain/set/setEx/delete) and `IIRCacheAdapter` (mapping get/set/setExpire/del), plus `JDKProxy.getProxy(interfaceClass, cacheAdapter)` and `JDKInvocationHandler` which use JDK dynamic proxy + reflection to route cache operations to the chosen cluster without modifying the original `CacheServiceImpl` at all. Abstract factory is a "central factory creating other factories": it solves interface-selection problems across a product family (multiple Redis clusters, operating systems), where differing interface names need a factory-of-factories adapter.
- Key claims: Abstract factory addresses 接口选择 within a product family with multiple differently-named products; the proxy-based approach lets existing classes be reused unmodified, lowering change cost; it satisfies 单一职责, 开闭原则, and 解耦, though family growth can raise class complexity — mitigatable with proxies and auto-generated loading; the concrete lesson is that "your code is just buried under ifelse" when the upgrade scenario could be abstracted out.
- Learner-relevant: Extends factory method with the adapter + JDK proxy technique; useful to contrast 工厂方法 (one product hierarchy) vs 抽象工厂 (family of related products), and to anchor the real-world "upgrade infrastructure behind an interface without touching callers" migration lesson.

### builder (建造者模式)

- Locator: `[[sources/design-pattern/design_pattern#建造者模式]]`
- Summary: The scenario is a 装修公司 (renovation company) offering decoration packages (豪华欧式, 轻奢田园, 现代简约) that combine 物料 (materials): ceilings (一级顶/二级顶), coats (多乐士/立邦), floors (德尔/圣象), tiles (东鹏/马可波罗), each material implementing the `Matter` interface (scene/brand/model/price/desc), priced per square meter to produce an overall quote. The ifelse version is a single `DecorationPackageController.getMatterList(area, level)` that hard-codes each package's material combination and per-material pricing formulas in if-blocks and builds the detail string; it outputs a quote but each new package appends another if-block, growing toward thousands of lines ("贴膏药似的修修补补"). The builder refactor defines `IMenu` (appendCeiling/appendCoat/appendFloor/appendTile returning `this` for fluent chaining, plus getDetail), its implementation `DecorationPackageMenu` (accumulates materials, computes price per append, renders the quote), and `Builder` (`levelOne/levelTwo/levelThree(area)` returning configured menus). Builder separates a complex construction from its representation so the same construction process can create different representations; it fits when base materials are stable but their combinations change frequently.
- Key claims: Builder satisfies 单一职责 and enables reusable, independent, easily-extended construction while controlling detail risk; with many materials and combinations, class expansion itself becomes a maintenance burden — mitigated by moving repeated content to database configuration and generating it; the hard part of the pattern is not the code but clearly extracting which build modules fit the builder mindset, which needs repeated practice; the same quote output is produced by both versions, proving the pattern changes structure without changing behavior.
- Learner-relevant: This is the book's canonical fluent-API builder example (chained append methods returning the builder); useful for the 创建型 family comparison (builder vs factory) and for the "stable parts, variable assembly" construction-problem lesson.
