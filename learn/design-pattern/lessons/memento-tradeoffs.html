適用邊界與存儲選型

design-pattern › memento › memento-tradeoffs

學習目標：掌握備忘錄模式的適用邊界——何時該用、何時不該用、內存 vs 資庫的存儲取捨。

備忘錄模式的優勢

前面四課我們從意圖、場景、結構、代碼四個角度理解了備忘錄模式。它最大的優勢是在不破壞封裝性的前提下提供回滾能力。具體來說：

  • 職責分離：原物件不管存儲、管理者不管內部結構，每個角色只做一件事
  • 易於擴展：加 redo？只改 Admin。加壓縮？只改 ConfigMemento。加日誌？只改 ConfigOriginator
  • 原物件零侵入：ConfigFile 不需要加任何方法、暴露任何欄位

什麼時候該用備忘錄模式？

判斷標準很簡單：你需要保存物件的歷史狀態，並且支持回滾或恢復。具體場景：

場景保存什麼回滾到什麼典型特徵
IDE 撤銷（Undo/Redo）文件內容 + 光標位置某次操作前的狀態用戶可見的操作歷史
遊戲存檔角色狀態 + 場景存檔時的狀態即時保存、即時恢復
線上配置回滾配置文件版本某個歷史版本的配置版本化管理、緊急回滾
交易系統回滾交易狀態交易前的狀態事務一致性要求
設計工具的歷史記錄畫布狀態某次操作前的畫布大量快照、高頻保存

共同特徵：需要「時間旅行」能力——回到過去的某個狀態。

什麼時候不該用？

備忘錄不是萬能的。以下場景不適合：

  • 不需要回滾：如果系統只需要「當前狀態」，不需要歷史版本，備忘錄是多餘的複雜度
  • 狀態太大：如果每次快照都要保存幾個 GB 的數據（比如視頻文件的完整像素），內存和存儲成本會爆炸
  • 狀態是共享的：如果多個物件共享同一份狀態，快照的邊界不好定義（A 和 B 共享一個 Map，存 A 的快照時要不要把 Map 複製一份？）
  • 狀態頻繁變更：如果每秒鐘狀態變更幾百次，存快照的開銷可能比業務本身還大

內存 vs 資庫：存儲選型

備忘錄模式本身不決定存儲方式——Admin 可以把快照存在任何地方。選擇存哪裡，取決於兩個維度：

維度內存存儲資料庫存儲
速度極快（納秒級）較慢（毫秒級）
持久性進程重啟就丟持久保存
成本佔用 RAM佔用磁盤，成本更低
適用場景即時性場景（IDE 撤銷、遊戲存檔、Photoshop 歷史）需要持久化的場景（配置回滾、交易回滾、版本管理）

案例中的配置回滾場景：在線上環境，配置改錯了需要回滾，但如果服務重啟了，內存裡的快照就丟了。所以真實場景通常會把快照存到資料庫。但如果是 IDE 的撤銷功能，進程關了就不需要歷史了，內存就夠了。

內存存儲的風險

如果選擇內存存快照，要注意內存消耗。假設一份 ConfigFile 是 1 KB，存 1000 個版本就是 1 MB，還算可控。但如果快照對象是整個數據庫的狀態（幾百 MB），存 100 個版本就是幾十 GB——這會直接撐爆內存。

常見的應對策略：

  • 限制歷史數量：Admin 只保留最近 N 個快照，超出的自動刪除
  • 壓縮快照：ConfigMemento 在存儲時壓縮 ConfigFile 的內容
  • 增量快照：不存完整的 ConfigFile，只存與上一版本的差異（delta）
  • 混合存儲：最近的快照放內存，歷史快照存資料庫

與其他模式的邊界

備忘錄模式容易跟幾個模式混淆：

模式解決什麼與備忘錄的區別
策略模式算法互換策略是「選哪個算法」，備忘錄是「回到過去的狀態」
狀態模式狀態驅動行為狀態模式是「當前狀態決定行為」，備忘錄是「保存和恢復歷史狀態」
命令模式請求封裝成對象命令模式可以配合備忘錄做撤銷（命令對象保存 undo 快照），但它們解決的是不同的問題

小結

備忘錄模式的適用邊界：需要保存歷史狀態、支持回滾或恢復。不適合不需要回滾、狀態太大、狀態共享、或狀態頻繁變更的場景。存儲選型取決於是否需要持久化——即時性場景用內存（IDE 撤銷、遊戲存檔），需要持久化的場景用資料庫（配置回滾、交易回滾）。內存存儲要注意消耗，限制歷史數量或使用增量快照。記住：任何設計模式都不是萬能的，引入模式是為了更易擴展和維護，不能反而把結構搞複雜。
