单例模式的动机：为什么全局只要一个实例

单例模式

学习目标

理解单例模式解决什么问题、为什么多线程环境下"只要一个实例"这么难。

先看一个真实场景

你在 Spring Boot 项目里写了一个工具类 AppConfig，把数据库连接池的配置、Redis 地址、第三方 API Key 都放进去。整个应用里，不管哪个 Controller、哪个 Service，拿到的都应该是同一份配置。

如果每次 new AppConfig() 都创建一个新实例，问题来了：

// 问题：多个实例，配置不一致
AppConfig config1 = new AppConfig();  // 读了一次配置
AppConfig config2 = new AppConfig();  // 又读了一次，可能读到不同值
config1.setApiKey("abc");
// config2.apiKey 还是 null——两个独立的实例

两个实例各管各的，改了一个另一个不知道。这在单线程下已经够头疼了。

哪些东西天然只需要一个

有些对象在整个应用生命周期里，只需要一个实例。硬要创建多个，轻则浪费资源，重则数据不一致：

场景多个实例的后果
数据库连接池多个池各自占连接，总连接数超限
Spring Bean（默认 singleton）状态不一致，事务边界混乱
全局配置持有者各实例读到的配置值不同
日志 Logger重复初始化、文件句柄泄漏
线程池 / 缓存分散的缓存无法命中，线程池调度失效
单例的本质需求：一个类在整个 JVM 里只允许存在一个实例，所有调用方拿到的都是同一个对象。

两层挑战：懒加载 vs 线程安全

听起来很简单——new 一次不就行了？真正棘手的是两件事同时存在时的矛盾：

挑战一：懒加载（Lazy Loading）

有些对象创建成本很高——比如数据库连接池要建几十个连接、读取远程配置要发 HTTP 请求。如果应用一启动就全部创建，启动时间会很长，而且有些对象可能整个生命周期都用不到。

懒加载的意思是：用到的时候才创建，不用就不创建。这能节省启动时间和内存。

挑战二：多线程安全

现代 Java 应用几乎都是多线程的。Tomcat 的每个请求都跑在独立线程上。如果两个线程同时判断"实例还没创建"，同时 new，就会创建出两个实例：

// 两个线程同时进入这个 if，都判断为 true
if (instance == null) {
    instance = new Singleton();  // 两个线程各 new 了一次
}
// 结果：两个实例，线程不安全

核心矛盾

懒加载要求"延迟创建"，线程安全要求"同步访问"。同步会加锁，加锁会降低并发性能。7 种单例实现，本质上就是在不同位置、用不同手段解决这个矛盾。

一把钥匙的比喻

单例就像一栋楼的钥匙。整栋楼只有一把钥匙，谁拿着它谁就能开门。但如果两个人同时走到门口、同时掏钥匙——你得决定：是让一个人先开（加锁），还是提前把钥匙复制好放门口（饿汉），还是用指纹锁谁来都能开但只认一个人（CAS）？7 种实现就是 7 种不同的"发钥匙"方案。

你会学到的 7 种实现

本节点会带你走完从最朴素到最优的 7 种单例实现。先剧透一下演进路径：

#实现方式一句话评价
0静态类 + ConcurrentHashMap 缓存最简单，无实例状态
1懒汉（线程不安全）有 bug，不能用
2synchronized 方法安全但每次调用都加锁
3饿汉（static field）安全但不懒加载
4静态内部类 / HolderJVM 保证安全+懒加载——推荐
5双重检查锁（DCL）经典方案，要配 volatile
6CAS + AtomicReference无锁但有自旋风险
7枚举（Effective Java）最佳默认，但不能继承

下一步，你会从第 0 种开始，亲手写出每种实现的代码，看到它们各自的致命缺陷，然后一步步改进到最优方案。准备好了吗？
