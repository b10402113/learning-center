Lesson 1/4 · 訪問者模式

訪問者模式的意圖：穩定結構 + 易變訪問

Node: visitor · Step 1/4 · 行為模式

學習目標

講清訪問者模式解決什麼問題、為何「穩定數據結構 + 易變訪問邏輯」需要解耦，並能判斷何時該用這個模式。

同一份數據，不同人想看不同的東西

你在學校的系統裡存了學生和老師的基本信息：姓名、班級、身份（重點班/普通班、特級教師/實習教師）。這些信息不會變——學生就是那些學生，老師就是那些老師。

但不同角色想從中看到的東西完全不同：

  • 家長：只關心自己孩子的成績排名，以及老師的教學水平
  • 校長：關心整個班級的學生人數和升學率

如果你把這些訪問邏輯直接塞進學生/老師類裡，類會越來越大——每來一個新角色（比如教育局督導），就得改數據類本身。這就是訪問者模式要解決的核心問題：

穩定的數據結構不動，把「誰來看、看什麼」的訪問邏輯抽成獨立的模塊。

問題的本质：誰在變、誰不變？

軟件設計裡有一個黃金法則：把不變的部分和變的部分分開。

不變的一直在變的
數據學生/老師的基本信息結構訪問視角（家長、校長、督導……）
操作accept(Visitor) 入口每個視角要打印的字段組合

訪問者模式把「操作」從「數據」裡拆出來，讓操作可以自由擴展，而數據結構保持穩定。

不用訪問者模式會怎樣？

最直覺的做法是在每個數據類裡加方法：

// 學生類裡塞家長視角
class Student {
    void showForParent() { ... }
    void showForPrincipal() { ... }
    void showForSupervisor() { ... }  // 以後還要加？
}

問題很明顯：

  1. 違反開閉原則：每加一個視角，就得改學生類和老師類
  2. 類膨脹：學生類不是在管理學生數據，而是在管理所有人的訪問邏輯
  3. ifelse 泛濫：如果用一個方法通過參數判斷視角，代碼會變成一堆 if (role == PARENT) ...

訪問者模式的意圖一句話

在一個穩定的數據結構下，把易變的業務訪問邏輯抽成獨立模塊，實現數據結構與操作的解耦。

白話版本：數據結構不動，誰想來看、看什麼，各自實現自己的訪問者類。

記住這個判據：數據結構穩定 + 訪問邏輯多變 = 訪問者模式的舞台。

什麼時候該用？

適合用不適合用
數據結構穩定，不太會增刪類型數據結構本身經常變（加新節點類型）
需要多種視角去訪問同一批數據只有一兩種訪問方式
不想讓數據類承擔業務邏輯團隊對複雜模式接受度低

一句話：當你發現「同一份數據、不同人要看不同的東西」且數據結構穩定，就該考慮訪問者模式了。

自我檢測

Q1. 訪問者模式解決的核心問題是什麼？

  • 如何高效創建多種對象
  • 如何遍歷樹形結構
  • 穩定數據結構 + 易變訪問邏輯的解耦
  • 如何實現多線程安全

Q2. 以下哪個場景最適合用訪問者模式？

  • 數據結構經常增刪新類型
  • 學生信息固定，但家長、校長、督導要看不同字段
  • 只有一種訪問方式
  • 需要快速創建大量相似對象

Q3. 如果把訪問邏輯直接塞進數據類會怎樣？

  • 違反開閉原則，類膨脹，每加視角都要改數據類
  • 性能會提升
  • 代碼會更簡潔
  • 沒有任何問題

Q4. 訪問者模式的「穩定」指的是什麼？

  • 訪問邏輯穩定不變
  • 代碼行數不會增加
  • 數據結構（類型和屬性）穩定
  • 性能穩定

Q5. 判斷是否使用訪問者模式的關鍵判據是？

  • 代碼行數超過 500 行
  • 數據結構穩定 + 訪問邏輯多變
  • 需要多態
  • 團隊人數超過 5 人
