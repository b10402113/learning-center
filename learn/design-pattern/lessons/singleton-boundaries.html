單例的適用邊界與決策清單

學習目標：歸納何時該用、何時不該用單例，給出決策清單，並說出單例與靜態類的適用邊界。

什麼時候「不該」用單例

前面兩課我們一直在說單例的好處。但面試官問「何時不該用單例」時，才是真正的分水嶺。單例有幾個被低估的缺點：

1. 隱式依賴，難以測試

單例是全局可見的。任何類都可以直接訪問它，不需要聲明依賴關係。這意味著：

  • 你想單測一個依賴單例的類？你沒法 mock 掉那個單例——因為它是直接靜態調用的
  • 測試之間會互相干擾——上一個測試改了單例的狀態，下一個測試讀到的就是髒數據
經典反模式：一個 ConfigManager.getInstance().get("key") 散落在二十個類裡，你想改配置來源？二十個類全部要動。

2. 狀態共享帶來的耦合

單例實例在整個應用裡只有一個。如果它維持了狀態，任何修改這個狀態的代碼都會影響所有使用方。模塊 A 改了單例裡的某個值，模塊 B 立刻受到影響——但它們之間可能根本沒有任何依賴聲明。

這就是為什麼 Spring 裡很多人避免用 Singleton Bean 維持有狀態的數據：作用域太廣，出問題時很難追蹤是誰改的。

3. 分佈式環境的天然缺陷

單例的「一個實例」是在一個 JVM 裡的。如果你的應用部署了十台機器，每台機器裡都有一個單例——那就是十個實例。它們之間的狀態怎麼同步？單例模式本身解決不了這個問題，你需要 Redis、ZooKeeper 之類的分佈式協調。

4. 繼承和多態的限制

枚舉單例不能被繼承。其他幾種手動實現的單例雖然可以被繼承，但繼承單例本身就違反了「只有一個實例」的語義——子類也是一種類型，如果子類也能被實例化，單例的保證就被打破了。

什麼時候「該」用單例

說了這麼多壞處，單例什麼時候值得用？

場景為什麼適合典型例子
資源池/緩存創建成本高、需要統一管理資料庫連線池、線程池、本地緩存
全局配置啟動時加載一次、全局讀不寫配置中心拉取的配置對象
日誌記錄器單一入口、避免多個 logger 混亂Log4j Logger
框架核心組件容器/引擎只應有一個Spring ApplicationContext

決策清單：五問判斷法

拿到一個「要不要用單例」的需求時，問自己五個問題：

  1. 這個類全局只會有一個嗎？如果不是，不要用。比如「每個用戶的購物車」——多個實例才對
  2. 它需要維持狀態嗎？如果不需要（純工具），用靜態類更簡單，不需要單例模式
  3. 它需要被繼承或多態嗎？如果需要，單例的語義會被打破，考慮工廠方法或依賴注入
  4. 它的創建成本高嗎？如果不高（幾微秒），每次 new 也沒問題，不需要單例
  5. 它在分佈式環境嗎？如果是，單例只在一個 JVM 裡生效，需要分佈式方案

五個問題都過了，單例才是合適的選擇。哪怕只有一個不過，就應該重新評估。

面試怎麼答

面試官問「單例的缺點」時，不要只說「全局狀態」。一個完整的回答結構：

  1. 隱式依賴，難以測試——無法 mock、測試間狀態污染
  2. 狀態共享耦合——修改影響範圍不可控
  3. 分佈式失效——一個 JVM 一個實例，多機部署需要額外方案
  4. 違反單一職責——一個類既要管業務邏輯，又要管自己的實例化

然後補一句：「所以現代框架更推薦用依賴注入（DI）來控制對象的作用域，而不是讓類自己管自己。Spring 的 Bean 默認 singleton 作用域就是這個思路——容器管實例化，類只管業務。」

小結

單例模式不是萬能的。它適合「全局唯一、創建成本高、不需要被繼承」的場景（連線池、配置、日誌）。它不適合「多個實例才合理、需要容易測試、分佈式環境」的場景。記住五問判斷法，拿到需求時逐條過濾。面試答缺點時，從「隱式依賴→狀態耦合→分佈式失效→違反單一職責」四個角度展開，再用 DI 收束，就是一個完整的回答。
