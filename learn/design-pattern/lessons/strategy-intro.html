策略模式的意圖與痛點

design-pattern › strategy › strategy-intro

學習目標：能說出策略模式「定義一系列算法、封裝、可互換」的意圖，並用優惠券計算的 ifelse 爆炸場景說出為什麼需要這個模式。

先從一個真實場景說起

你在電商平台做後端，產品經理跑過來說：「我們要上優惠券功能。」需求很直白：用戶買了一件 100 元的商品，手上有張券，結帳時要算出折後價。

第一版很簡單，一種券，一個方法搞定：

public double discountAmount(double skuPrice, double couponValue) {
    return skuPrice - couponValue;
}

沒問題。但產品第二週又加了「滿 200 減 50」、第三週加了「8 折」、第四週加了「19.9 元購」……

ifelse 地獄長什麼樣

你開始在方法裡堆 if：

public double discountAmount(int type, double couponValue, double skuPrice, double typeExt) {
    if (type == 1) {
        // 直減
        return skuPrice - couponValue;
    } else if (type == 2) {
        // 滿減
        if (skuPrice < typeExt) return skuPrice;
        return skuPrice - couponValue;
    } else if (type == 3) {
        // 折扣
        return skuPrice * couponValue;
    } else if (type == 4) {
        // n 元購
        return couponValue;
    }
    return 0D;
}
壞味道：每加一種券，就要改這個方法。type 參數從哪來？怎麼知道 1 代表直減？如果有 20 種券呢？

幾個問題馬上浮現：

  • 修改成本高：加一種新券，就要在方法裡加 else if 分支，動到已有邏輯
  • 參數污染：為了滿減加了 typeExt，但直減和折扣根本用不到它——一個方法被所有券型的參數塞滿
  • 難以測試：想單獨測折扣邏輯？不好意思，得先走完所有 if 分支才能到那一行
  • 重複理解：新來的同事看這段代碼，要把所有 if 全讀一遍才知道「折扣是怎麼算的」

核心問題是：多種算法（券型）塞在同一個方法裡，它們之間互相干擾。

策略模式怎麼解決這個問題

策略模式的意圖一句話：定義一系列算法，把它們一個個封裝起來，使它們可以互相替換。

回到優惠券場景。四種券的計算邏輯，其實是四個獨立的算法。如果我們把每個算法包成一個獨立的類，再讓它們共享同一個接口，會發生什麼？

  • 加新券？寫一個新實現類，不動任何已有代碼
  • 改折扣邏輯？只改折扣那一個類，其他券型完全不受影響
  • 測試？每個券型的類可以獨立單測
  • 看代碼？想知道「折扣怎麼算」？打開 Discount 類就行了，不用在 ifelse 裡找

用一個類比來說：三國時期諸葛亮給劉關張三個錦囊。每個錦囊裡裝的是一套應對特定情境的策略，到了對應的關口就拆開執行。你不需要在一個超大的「如果遇到什麼就怎麼辦」清單裡翻找，而是按需取用、即拆即走。

關鍵概念：行為型模式

策略模式是 GoF（Gang of Four，四人幫）23 種設計模式中的行為型模式（Behavioral Pattern）。行為型模式關注的是「對象之間怎麼協作、算法怎麼分配」，而不是「對象怎麼創建」或「類怎麼組織」。

策略模式特別適合的場景是：同一個動作有多種算法實現，而且未來可能還會加新的。典型的例子包括：

場景動作可替換的算法
支付付款信用卡、支付寶、微信
排序排數據快速排序、歸併排序、插入排序
優惠券算折扣直減、滿減、折扣、n 元購
ID 生成生唯一 IDUUID、DB 自增、雪花算法

這些場景的共同點是：算法可以互換，而且客戶端不想知道具體的算法實現。

小結

策略模式的核心動機是消除 ifelse 分支堆砌。當一個方法因為不同算法而不斷膨脹時，策略模式讓每種算法獨立成類、通過統一接口互換。下一步我們會把那個 ifelse 的優惠券代碼，用策略模式完整重構一遍。
