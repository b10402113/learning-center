一把梭 ifelse 的痛

Node: state · Step 3/5

學習目標

能指出 ifelse 實現審核流轉的可維護性痛點，說清楚為什麼「狀態越多、分支越亂」。

最直覺的做法

大多數工程師第一次實現審核流轉時，都會寫出類似的代碼：一個大控制器方法，用 if 判斷 beforeStatus（當前狀態），再用嵌套 if 判斷 afterStatus（目標狀態），合法就執行，不合法就返回拒絕。

if (beforeStatus == 1) {
  if (afterStatus == 2 || afterStatus == 6) {
    // 合法：編輯中 → 待審核 or 關閉
    execStatus(activityId, beforeStatus, afterStatus);
    return "0000"; // 成功
  } else {
    return "0001"; // 拒絕
  }
} else if (beforeStatus == 2) {
  if (afterStatus == 3 || afterStatus == 4 || afterStatus == 6) {
    execStatus(activityId, beforeStatus, afterStatus);
    return "0000";
  } else {
    return "0001";
  }
} else if (beforeStatus == 4) {
  // ...
} // 繼續往下堆...

這個實現完全能跑。測試也通過了：編輯中→提交審核返回 0000，編輯中→直接開啟返回 0001。

問題出在哪？

代碼能跑，不代表代碼沒問題。問題不在「現在」，而在「以後」：

1. 加新狀態，所有分支都要改

假設產品加了一個「草稿」狀態，你要在所有 if 分支裡都加上判斷。漏改一個，就可能出現非法流轉。

2. 邏輯集中在一個方法裡，誰加了什麼都搞不清

三個月後有人改了「編輯中→待審核」的邏輯，但不知道這會不會影響「審核拒絕→撤審」的流程。因為它們全部在同一個方法裡。

3. 新人看到不敢動

新來的工程師打開這個文件，看到幾百行 if-else，根本不敢重構——誰知道改了哪裡會出 bug？

「越來越亂就是從點滴開始的」

一開始只有 4 個狀態、每個狀態 2-3 個分支，看起來還行。但狀態和需求是會成長的——等你有 10 個狀態、每個狀態 5 個分支時，這個方法就變成一個 50 行起步的怪物。

代碼壞味道

壞味道表現後果
嵌套 if 過深if 裡面再套 if，三層起步閱讀困難，分支邏輯看不清
重複判斷多處都判斷 beforeStatus == 1改一處漏一處
魔法數字0000、0001、狀態用數字不直觀，容易打錯
單一方法承擔所有邏輯一個方法裡塞了所有狀態轉換無法拆分測試、無法單獨修改

痛點小結

一把梭 ifelse 在不需要改動和迭代的場景下完全可用——如果這是一個寫完就再也不碰的腳本，隨便。但在業務系統中，狀態和規則幾乎一定會變，用 ifelse 堆出來的代碼只會越改越亂。

痛點不是「不能用」，而是「改不動」。

自我檢測

Q1. ifelse 實現的最大痛點是什麼？

  • 運行速度太慢
  • 不能存儲狀態
  • 加新狀態時所有分支都要改
  • 不支持並發

Q2. 以下哪個不是一把梭 ifelse 的壞味道？

  • 使用枚舉定義狀態
  • 嵌套 if 過深
  • 魔法數字
  • 單一方法承擔所有邏輯

Q3. 一把梭 ifelse 在什麼場景下可以接受？

  • 有 10 個以上狀態的系統
  • 不需要改動和迭代的腳本
  • 需要多人協作的大型項目
  • 狀態規則經常變化的業務
