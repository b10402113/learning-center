7 種單例實現逐一拆解

design-pattern › singleton › seven-implementations

學習目標：逐一拆解 7 種單例寫法的線程安全機制與懶載入取捨，能說出每種的優缺點與適用場景。

兩維度一張地圖

七種寫法聽起來多，但分野集中在兩個維度：懶不懶加載（用到時才建 vs 啟動就建）和線不線程安全（多線程同時獲取會不會建出多個）。先記住這張地圖，後面七個寫法只是在不同格子裡落位：

線程不安全線程安全
非懶加載—靜態類（第 0 種）、餓漢（第 3 種）
懶加載懶漢（第 1 種）懶漢 synchronized（第 2 種）、靜態內部類（第 4 種）、DCL（第 5 種）、CAS（第 6 種）、枚舉（第 7 種）

下面逐個拆解。每個寫法我會給出：代碼骨架、線程安全怎麼保證的、懶不懶加載、核心優缺點。

第 0 種：靜態類

最樸素的做法——不需要實例化，直接用 static 成員：

public class Singleton_00 {
    public static Map<String, String> cache = new HashMap<>();
    static {
        cache.put("key1", "value1");
    }
}

啟動時就把數據塞好，外面直接 Singleton_00.cache.get("key1") 就行。

維度評價
線程安全✅ 天然安全（類加載機制保證）
懶加載❌ 類加載時就初始化
繼承/多態❌ static 方法不能被重寫
適用場景：不需要維持狀態、純全局訪問的工具。如果你的「單例」只是個 Map 或工具方法集合，用靜態類就夠了，不需要單例模式。

第 1 種：懶漢模式（線程不安全）

終於進入正題。私有構造方法禁止外部 new，getInstance 裡判空後才創建：

public class Singleton_01 {
    private static Singleton_01 instance;
    private Singleton_01() {}
    public static Singleton_01 getInstance() {
        if (instance == null) {
            instance = new Singleton_01();
        }
        return instance;
    }
}

用到時才建，完美懶加載。但問題來了：

線程隐患：線程 A 判到 instance == null，還沒來得及 new，線程 B 也判到 null，也進去了。結果：兩個實例。就像一群人同時衝進廁所，發現門沒鎖，結果進了兩個人。
維度評價
線程安全❌ 多線程下會創建多個實例
懶加載✅ 用到時才建

第 2 種：懶漢模式（線程安全）

最直接的修復：在 getInstance 方法上加 synchronized：

public class Singleton_02 {
    private static Singleton_02 instance;
    private Singleton_02() {}
    public static synchronized Singleton_02 getInstance() {
        if (instance == null) {
            instance = new Singleton_02();
        }
        return instance;
    }
}

加了鎖，線程安全了。代價呢？

性能問題：每次獲取實例都要走 synchronized，哪怕實例早就創建好了。鎖的粒度太粗——好比為了防一個人遲到，把整棟大樓的門都鎖了。
維度評價
線程安全✅ synchronized 保證
懶加載✅
性能❌ 方法級鎖，所有訪問都排隊

第 3 種：餓漢模式（線程安全）

反其道而行：不等你用，類加載時就直接建好：

public class Singleton_03 {
    private static final Singleton_03 instance = new Singleton_03();
    private Singleton_03() {}
    public static Singleton_03 getInstance() {
        return instance;
    }
}

JVM 保證類加載時 static final 字段只初始化一次，天然線程安全，不需要任何鎖。

代價：不是懶加載。類一加載就建好，不管用不用。就像遊戲啟動就把全部地圖實例化，手機直接爆內存。
維度評價
線程安全✅ JVM 類加載機制保證
懶加載❌ 啟動即建
性能✅ 無鎖，直接返回

第 4 種：靜態內部類（線程安全）

一個巧妙的折中：用靜態內部類持有實例，既懶加載又線程安全：

public class Singleton_04 {
    private Singleton_04() {}
    private static class SingletonHolder {
        private static final Singleton_04 INSTANCE = new Singleton_04();
    }
    public static Singleton_04 getInstance() {
        return SingletonHolder.INSTANCE;
    }
}

關鍵在於 JVM 的類加載機制：SingletonHolder 只有在 getInstance() 被調用時才會被加載，加載時才創建 INSTANCE。而 JVM 保證類的靜態初始化在多線程環境下是安全的——只會執行一次。

推薦：既懶加載又線程安全，不加鎖，性能好。是大多數場景下的最佳手動實現。
維度評價
線程安全✅ JVM 類加載機制保證
懶加載✅ 第一次調用時才加載內部類
性能✅ 無鎖

第 5 種：雙重鎖校驗 DCL（線程安全）

方法級鎖太粗？那就把鎖縮到最小——只在第一次創建時加鎖：

public class Singleton_05 {
    private static volatile Singleton_05 instance;
    private Singleton_05() {}
    public static Singleton_05 getInstance() {
        if (instance == null) {           // 第一重：避免不必要的同步
            synchronized (Singleton_05.class) {
                if (instance == null) {   // 第二重：防止重複創建
                    instance = new Singleton_05();
                }
            }
        }
        return instance;
    }
}

兩重判空 + 類鎖。第一重判空讓大部分調用直接返回已有實例，不進 synchronized 塊。第二重判空在鎖裡面，防止多個線程同時通過第一重後重複創建。

volatile 的必要性：new Singleton_05() 在 JVM 裡不是原子操作——它分三步：分配內存、初始化對象、引用指向內存。JVM 可能做指令重排，把第三步排到第二步前面。如果不加 volatile，線程 B 可能拿到一個「引用已指向但還沒初始化完」的半成品對象。volatile 禁止了這種重排序。
維度評價
線程安全✅ synchronized + volatile
懶加載✅
性能✅ 只在第一次加鎖，後續無鎖
複雜度⚠️ volatile + 雙重判空，容易寫錯

第 6 種：CAS AtomicReference（線程安全）

Java 並發庫提供了一組原子類（AtomicInteger、AtomicBoolean、AtomicLong、AtomicReference），可以用 CAS（Compare-And-Swap）實現無鎖單例：

public class Singleton_06 {
    private static final AtomicReference<Singleton_06> INSTANCE = new AtomicReference<>();
    private Singleton_06() {}
    public static Singleton_06 getInstance() {
        for (;;) {  // 自旋
            Singleton_06 current = INSTANCE.get();
            if (current != null) return current;
            if (INSTANCE.compareAndSet(null, new Singleton_06())) {
                return INSTANCE.get();
            }
        }
    }
}

CAS 不依賴傳統加鎖，靠忙等算法與底層硬件保證線程安全。沒有線程切換和阻塞開銷，可支持較大並發。

缺點：忙等——如果一直獲不到鎖就陷入死循環（自旋），消耗 CPU。高並發下 CAS 競爭激烈時性能反而可能不如 DCL。
維度評價
線程安全✅ CAS 原子操作
懶加載✅
性能⚠️ 無鎖但有自旋開銷，高競爭時可能退化

第 7 種：枚舉單例（Effective Java 推薦）

Joshua Bloch（約書亞·布洛克），《Effective Java》作者、前 Google 首席 Java 架構師，推薦的終極方案：

public enum Singleton_07 {
    INSTANCE;
    public void test() {
        System.out.println("枚舉單例");
    }
}

調用方式：Singleton_07.INSTANCE.test()。就這麼簡單。但為什麼它是「最佳方法」？

  • 線程安全：JVM 保證 enum 的 values() 只返回定義好的實例
  • 防反射：Java 語言規範禁止通過反射創建 enum 實例——反射攻擊直接報錯
  • 防序列化：enum 天然支持序列化/反序列化，不會像普通類那樣通過反序列化創建新實例
  • 代碼量：一行搞定，不需要 private 構造、static 字段、getInstance 方法
最佳實踐：線程安全、防反射、防序列化、代碼最簡。唯一限制：enum 不能被繼承。如果你的單例不需要被繼承，這就是首選。

小結

七種寫法的核心分野是「懶不懶加載」×「線不線程安全」。實戰中記住三個結論就够了：**靜態內部類**是手動實現的首選（懶加載 + 無鎖 + 線程安全），**DCL**是面試常考的經典（volatile + 雙重判空），**枚舉**是 Effective Java 推薦的最佳實踐（防反射 + 防序列化 + 代碼最簡）。下一課我們會回答一個更實際的問題：什麼場景下根本不該用單例。
