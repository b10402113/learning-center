發獎場景的 ifelse 壞味道

design-pattern › factory-method › bad-smell-ifelse

學習目標：能從三種異構商品接口（優惠券/實物/兌換卡）的 ifelse 一把梭中，說出為什麼需要工廠方法模式來統一創建入口、屏蔽實現。

先從一個真實場景說起

你在電商平台做後端，公司搞了個營銷活動：用戶打卡、分享、邀請註冊都能賺積分，積分可以兌換商品。商品有三種：

商品類型接口方法返回值特殊參數
優惠券sendCoupon(uId, couponNumber, uuid)CouponResult（對象）防重 uuid
實物商品deliverGoods(DeliverReq req)Boolean（布爾）收貨地址
第三方兌換卡grantToken(bindMobileNumber, cardId)void（空）手機號、卡 ID

三個接口，返回類型不一樣，入參也不一樣。營銷場景的特點是「多變、臨時」——今天加個視頻會員，明天加個實物周邊，產品經理隨時會跑過來說「再加一種」。

ifelse 一把梭長什麼樣

最直覺的做法：一個 Controller 裡搞定所有邏輯，按類型分發。

public AwardRes awardToUser(AwardReq req) {
    if (req.getAwardType() == 1) {
        // 優惠券
        CouponService couponService = new CouponService();
        CouponResult result = couponService.sendCoupon(
            req.getuId(), req.getAwardNumber(), req.getUuid());
        if (!"0000".equals(result.getCode())) {
            return new AwardRes("0001", "發放失敗");
        }
    } else if (req.getAwardType() == 2) {
        // 實物商品
        GoodsService goodsService = new GoodsService();
        DeliverReq deliverReq = new DeliverReq();
        deliverReq.setuId(req.getuId());
        deliverReq.setGoodsId(req.getAwardNumber());
        // ... 拼裝收貨地址等
        Boolean success = goodsService.deliverGoods(deliverReq);
        if (!success) {
            return new AwardRes("0001", "發放失敗");
        }
    } else if (req.getAwardType() == 3) {
        // 第三方兌換卡
        CardService cardService = new CardService();
        String phone = queryUserPhoneNumber(req.getuId());
        cardService.grantToken(phone, req.getAwardNumber());
    }
    return new AwardRes("0000", "發放成功");
}
壞味道：一個方法裡塞了三種完全不同的業務邏輯，每加一種商品就要改這個方法。如果明天加一個「視頻會員」，你得在這裡再加一個 else if 分支。

這個代碼的四個問題

  1. 修改成本高：加一種新商品，就要在方法裡加 else if 分支，動到已有邏輯。即使你覺得「只是加一個分支」，但每次修改都要回歸測試所有已有的分支——改了優惠券的邏輯，實物商品會不會受影響？
  2. 參數污染：實物商品需要收貨地址，所以 req 裡加了 extMap。但優惠券和兌換卡根本用不到 extMap——一個方法被所有商品類型的參數塞滿。
  3. 難以測試：想單獨測兌換卡的邏輯？得先走完前面兩個 if 分支才能到那一行。三種業務邏輯耦合在一起，無法獨立單測。
  4. 接手痛苦：新同事接手這段代碼，要把所有 if 全讀一遍才知道「實物商品怎麼發放」。代碼沒有分層，沒有結構，可讀性極差。

問題的根源是什麼

把三種商品的發放邏輯塞在一個方法裡，本質是把「根據類型選擇哪個服務」和「執行服務」這兩件事混在一起了。

更深一層看：三個服務的接口完全不一樣——方法名不同、參數不同、返回值不同。這意味著你在 if 裡做分發時，每個分支的代碼結構都不一樣，沒法抽成一個統一的調用。

工廠方法模式要解決的核心問題就是：把「根據類型決定實例化哪個類」的邏輯，從調用方抽離出來，統一到一個地方。讓調用方不再關心「具體 new 哪個類」，而是說「我要的是某種商品的發放服務」，工廠幫你拿。

用一個類比：你開了一家餐廳，菜單上有川菜、粵菜、日料。如果每道菜你都要自己判斷「這是川菜師傅做的還是粵菜師傅做的」，那每加一道菜你就要改菜單系統。但如果你有一個前台，你只說「我要水煮魚」，前台幫你分配到川菜廚房——這個前台就是工廠。

工廠方法模式的意圖

工廠方法模式（Factory Method Pattern）是一種創建型設計模式（Creational Pattern）。創建型模式關注的是「對象怎麼創建」，而不是「對象之間怎麼協作」或「類怎麼組織」。

它的意圖一句話：定義一個創建對象的接口，讓子類決定實例化哪一個工廠類。工廠方法使一個類的實例化延遲到子類進行。

翻譯成白話：你給我一個「要什麼」，我幫你「造出來」。具體怎麼造，是哪個工廠造，調用方不需要知道。回到發獎場景——調用方只說「我要發一種商品」，工廠幫你判斷是優惠券、實物還是兌換卡，然後返回對應的發放服務。

這個模式特別適合的場景是：

場景「要什麼」工廠分發到
發獎商品類型 ID對應的發放服務
日誌日誌級別文件/數據庫/控制台 Logger
連接數據庫類型MySQL/PostgreSQL/Oracle Connection
通知通知渠道短信/郵件/推送 Service

這些場景的共同點：同一個動作有多種具體實現，而且未來可能還會加新的。

小結

發獎場景的 ifelse 代碼把三種異構接口塞在同一個方法裡，每次加新商品都要改已有代碼——這是「發散分支」的壞味道。工廠方法模式的核心是把「根據類型選擇實例」的邏輯從調用方抽離到工廠類，讓新增商品不需要動已有代碼。下一課我們會用這個模式完整重構發獎代碼。
