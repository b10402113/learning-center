枚举单例与七种实现的选择

单例模式

学习目标

掌握枚举单例的最佳实践，并能用决策树在 7 种实现中做出选择。

变体 7

枚举单例（Effective Java 推荐）

Joshua Bloch 在《Effective Java》中推荐的方案，也是最简单的：

public enum Singleton {
    INSTANCE;

    private int value;

    public int getValue() { return value; }
    public void setValue(int v) { this.value = v; }
}

使用时直接 Singleton.INSTANCE.getValue()，没有 getInstance() 方法——因为 enum 常量本身就是单例。

为什么枚举是"最好的"？

枚举单例自动具备三项能力，其他方案需要额外代码才能获得：

能力其他方案枚举
序列化安全 普通类序列化/反序列化会创建新实例，需要实现 readResolve() JVM 自动处理，反序列化返回同一个实例
反射攻击防御 反射可以调用私有构造函数创建新实例 JVM 禁止通过反射创建 enum 实例
线程安全 + 懒加载 需要手动实现（Holder/DCL/CAS） JVM 类加载机制天然保证
枚举单例的本质：它利用了 Java 语言规范对 enum 的特殊处理——enum 常量在类加载时创建一次，JVM 保证全局唯一，且序列化/反射攻击都被语言级防御。

唯一的限制：不能继承

Java 的 enum 天生是 final 的，不能被继承。如果你的单例需要继承某个父类，枚举方案就不适用了。不过在实际项目中，单例需要继承的情况非常少见。

枚举单例就像政府颁发的身份证——全国唯一、不可伪造、不可复制。你不需要自己保管，系统自动帮你维护唯一性。缺点是它不支持"定制"——你不能在身份证上加个性化信息（继承）。

七种实现的决策树

面对 7 种实现，实际选择时只需要回答两个问题：

Q1：单例需要序列化或防反射攻击吗？
→ 是：用枚举（变体 7）
→ 否：继续问 Q2
Q2：需要懒加载吗？
→ 不需要（对象创建开销小、一定会用到）：用饿汉（变体 3）
→ 需要：继续问 Q3
Q3：追求极致简洁还是极致性能？
→ 简洁优先：用 Holder 模式（变体 4）
→ 高并发场景、对锁开销敏感：用 CAS（变体 6）

变体 1（懒汉线程不安全）和变体 2（synchronized 方法）在实际项目中不应使用。变体 1 有 bug，变体 2 性能差。它们存在的意义是帮你理解演进过程。

2. 其他情况 → Holder 模式

什么时候不需要单例？

最后提醒一点：不要滥用单例。

  • Spring Bean 默认就是单例的——如果你用 Spring，不需要自己写单例类
  • 无状态的工具类用静态方法就够了，不需要实例
  • 需要测试替身（Mock）的类——单例很难 Mock，依赖注入比单例更容易测试

单例解决的是"全局唯一实例"的问题。如果你只是想要方便地共享数据，考虑用依赖注入或配置中心，而不是自己造单例。
