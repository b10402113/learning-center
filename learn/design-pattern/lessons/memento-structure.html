四角色分工：原物件、備忘錄、記錄者、管理者

design-pattern › memento › memento-structure

學習目標：記住四個角色的名稱與職責分工，形成理解任何備忘錄實現的結構地圖。

為什麼需要四個角色？

上一課我們看到了一把梭 ConfigManager 的問題：存配置、管歷史、回滾邏輯全混在一起。備忘錄模式的核心設計思路是把這些職責分離到不同的角色，每個角色只做一件事。

你可能想：「不就是存個快照嗎，至於拆成四個類？」拆開的好處是：每一層都可以獨立變化。存儲結構想從 List 換成 Map？只改 Admin。快照格式想加壓縮？只改 ConfigMemento。回滾邏輯想加日誌？只改 ConfigOriginator。原物件 ConfigFile 完全不用動。

四個角色一覽

角色Java 類核心職責遊戲類比
原物件ConfigFile承載被保存的狀態（版本號、內容、時間、操作人）遊戲角色（血量、裝備、經驗值）
備忘錄ConfigMemento快照的載體，把原物件包起來存檔檔（二進位格式，玩家不需要懂）
記錄者ConfigOriginator生成快照（saveMemento）和還原快照（getMemento）遊戲存檔系統（按按鈕就存/讀）
管理者Admin保存多個快照，提供 undo/redo/get 操作存檔管理器（存檔槽、歷史記錄列表）

角色之間的關係

四個角色的互動流程：

ConfigFile（當前狀態）
    ↓ saveMemento()
ConfigOriginator（記錄者）
    ↓ 生成
ConfigMemento（快照）
    ↓ 交給
Admin（管理者）← 保存多個快照
    ↓ undo/redo/get
ConfigOriginator（還原）
    ↓ getMemento()
ConfigFile（回到某個歷史狀態）

關鍵洞察：ConfigFile 從頭到尾不知道有人在存它的狀態。它不需要加任何方法、不需要暴露任何欄位。快照的生成和還原都在 ConfigOriginator 裡完成，ConfigFile 是被動的。

每個角色的「邊界」

ConfigFile（原物件）

  • 只管自己的業務邏輯（配置內容的讀寫）
  • 不知道備忘錄的存在
  • 不暴露內部狀態給外部（封裝性完好）

ConfigMemento（備忘錄）

  • 只管包裝原物件的狀態
  • 不知道誰會存它、誰會讀它
  • 相當於一個「密封的盒子」，裡面裝著某一時刻的 ConfigFile

ConfigOriginator（記錄者）

  • 知道 ConfigFile 的內部結構（它是唯一知道怎麼讀寫 ConfigFile 的角色）
  • saveMemento()：把當前 ConfigFile 的狀態包成一個新的 ConfigMemento
  • getMemento(memento)：把快照裡的狀態寫回當前的 ConfigFile

Admin（管理者）

  • 不知道 ConfigFile 的內部結構（它只操作 ConfigMemento）
  • 用 List 保序 + Map 按版本號索引，雙結構存放快照
  • 提供 undo（回滾）、redo（前進）、get（按版本號取）

「誰知道什麼」的封裝邊界

備忘錄模式最精妙的地方在於資訊的不對稱：

角色知道 ConfigFile 的內部結構？知道 ConfigMemento 的內部結構？
ConfigFile是（它自己）否
ConfigMemento是（包裝了 ConfigFile）是（它自己）
ConfigOriginator是（讀寫 ConfigFile）是（創建和還原 ConfigMemento）
Admin否是（存取 ConfigMemento）

Admin 是管理者，它只跟 ConfigMemento 打交道，完全不知道 ConfigFile 長什麼樣。這意味著：就算 ConfigFile 的內部結構改了，Admin 也不用動。這就是封裝性帶來的好處。

小結

備忘錄模式的四個角色：原物件（承載狀態）、備忘錄（快照載體）、記錄者（生成/還原快照）、管理者（保存歷史 + 提供 undo/redo/get）。核心設計是資訊不對稱——Admin 不知道 ConfigFile 的內部結構，ConfigFile 不知道有人在存自己的狀態。記住這張結構地圖，下一課我們用 Java 代碼逐類走讀，把每個角色落到真實程式碼上。
