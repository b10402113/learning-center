工厂方法的重构路径

工厂方法与抽象工厂

学习目标

掌握工厂方法的重构路径——从 ifelse 分发改为"创建接口 + 子类决定实例化哪个产品"，满足开闭原则和单一职责。

重构四步走

从上一步看到的 ifelse Controller 出发，工厂方法的重构可以拆成四步：

第一步：定义统一的产品接口

把三种奖品的差异封装掉，对外只暴露一个统一方法：

// ICommodity.java — 统一产品接口
public interface ICommodity {
    void sendCommodity(String uId, String commodityId,
                       String bizId, Map<String, String> extMap);
}

不管底层是优惠券、商品还是兑换卡，调用方只看到这一个方法。

第二步：每种产品实现自己的逻辑

每个实现类封装一种第三方调用，处理自己的参数映射和异常：

// CouponCommodityService.java
public class CouponCommodityService implements ICommodity {
    @Override
    public void sendCommodity(String uId, String commodityId,
                               String bizId, Map<String, String> extMap) {
        CouponResult result = couponService.sendCoupon(uId, ...);
        if (!result.isSuccess()) {
            throw new RuntimeException("优惠券发放失败");
        }
    }
}

// GoodsCommodityService.java
public class GoodsCommodityService implements ICommodity {
    @Override
    public void sendCommodity(String uId, String commodityId,
                               String bizId, Map<String, String> extMap) {
        Boolean ok = goodsService.deliverGoods(...);
        if (!ok) {
            throw new RuntimeException("商品发货失败");
        }
    }
}

注意每个类只关心自己的第三方接口，参数映射、异常处理、返回值转换都内聚在类内部。

第三步：工厂方法负责创建

工厂类根据 type 参数返回对应的实现：

// StoreFactory.java — 工厂方法
public class StoreFactory {
    public static ICommodity getCommodityService(Integer type) {
        if (type == 1) return new CouponCommodityService();
        if (type == 2) return new GoodsCommodityService();
        if (type == 3) return new CardCommodityService();
        throw new RuntimeException("未知奖品类型");
    }
}

工厂里的 ifelse 可以接受——它只做一件事：创建。后续可以用 Map 配置进一步消除。

第四步：调用方变干净了

Controller 不再包含任何业务逻辑，只做一件事——调工厂拿实例，调方法：

// PrizeController.java — 重构后
public AwardRes awardToUser(AwardReq req) {
    ICommodity commodity = StoreFactory.getCommodityService(req.getAwardType());
    commodity.sendCommodity(req.getUserId(), req.getCommodityId(),
                           req.getBizId(), req.getExtMap());
    return new AwardRes("兑换成功");
}

Before vs After 对比

Before（ifelse） After（工厂方法）
Controller 长度 10+ 种奖品，10 个 if 块 固定 2 行：拿实例 + 调方法
新增奖品 改 Controller + 加新分支 加一个实现类 + 改工厂一行
参数映射 全挤在 Controller 里 各自封装在实现类内部
异常处理 混在分发逻辑里 各自处理，互不干扰

满足的设计原则

单一职责：Controller 只负责分发，每种奖品的业务逻辑各自独立在自己的类里。

开闭原则：新增奖品类型时，只需要添加新的实现类和修改工厂的 switch，不需要修改任何已有的调用方代码。

工厂内部的进化

工厂方法里的 ifelse 也可以优化。常用方式是用 Map<Integer, Supplier<ICommodity>> 替代：

private static final Map<Integer, Supplier<ICommodity>> FACTORY = Map.of(
    1, CouponCommodityService::new,
    2, GoodsCommodityService::new,
    3, CardCommodityService::new
);

public static ICommodity getCommodityService(Integer type) {
    return FACTORY.getOrDefault(type, () -> {
        throw new RuntimeException("未知奖品类型");
    }).get();
}

Map 方式的好处是新增奖品只需往 Map 里加一行，不需要改 switch/ifelse，更符合开闭原则。

工厂方法的本质一句话

工厂方法 = 创建接口 + 子类决定实例化哪个产品。调用方依赖接口，不依赖具体类；创建的决定延迟到工厂方法里。这就是"把 new 的决定挪走"。
