何時該用設計模式

Step 4/4 · 設計模式與六大原則

學習目標：綜合六大原則與三分類地圖，說出設計模式該在什麼真實問題下用、如何對照框架的綜合運用，不為用而用。

現在把前兩步合起來。你手上有一把尺子（六大原則）和一幅地圖（三大分類）。這一步回答最關鍵的兩個問題：什麼時候該搬模式出來？什麼時候不該？

該用的信號：先有壞味道，再談模式

模式永遠是「解決問題的工具」，不是「炫技」。使用的順序是：

  1. 先聞到壞味道——又一個 ifelse 分支冒出來了、一個類又長胖了、又要複製貼上一段代碼了。
  2. 拿尺子量——這個壞味道違背了哪條原則？（分支太多 → 開閉；類太肥 → 單一職責；到處 new 具體類 → 依賴倒置）
  3. 對地圖找場景——哪個分類、哪個模式正好治這個病？

這就是你重構 ifelse 的完整複述：發獎類型一多就要改大方法（壞味道）→ 違背開閉（量尺）→ 用創建型的工廠方法 / 行為型的策略（地圖）→ 新獎品加新類，老代碼不動。

框架的「綜合運用」是怎麼回事

回頭看第一步的那句話：框架是多種模式綜合運用。這給你兩個啟示：

  • 讀源碼時，別指望一個模式對號入座。看到 Spring 的 Adapter 實現類，別急著說「這就是適配器模式」，它可能同時摻著工廠、代理、模板方法。作者的原話：任何設計模式都不是單獨使用的。
  • 寫代碼時，同一個場景可能需要幾種模式組合。一個「發獎服務」可以同時用工廠（創建）、策略（算法）、模板方法（流程骨架）。老手「綜合運用」的功力，就是靠這種組合經驗累積出來的。

    • 不該用的信號：三個剎車

    剎車一：為用而用（過度設計）

    書裡反覆強調：切忌為用而用導致過度設計。代碼已經高內聚、簡單直接，硬套橋接反而把結構搞複雜、難維護。引入模式的目的是更易擴展和維護——如果結果反過來，就是錯了。

    剎車二：類膨脹的帳沒算

    每個模式幾乎都有代價：狀態模式狀態多時會產生很多實現類，命令模式的命令×實現組合會讓類爆炸。書的建議是按投入回報評估——看這個邏輯是否經常修改、能否組件化、能否抽離業務與非業務。

    剎車三：違背原則也照用

    有些模式天生跟某條原則打架，比如訪問者模式違背迪米特。這不是「錯了」，而是「這個場景的收益 > 那條原則的損失」。用之前把這筆帳算清楚，面試時就能講出深度。

    判斷金句：設計模式是權衡的結果。該不該用，不是「這個模式很流行」，而是「這個真實問題，用這個模式，解決了哪條原則的痛、付出了什麼代價」。

    延伸閱讀

    主要來源：《重學 Java 設計模式》「目錄」（六大原則 + 三分類索引）與「Adapter: 开篇与设计模式观」（多模式綜合運用）。書中每個模式的「總結」都在回扣同一個句式——滿足哪些原則、代價是什麼、按場景評估。往後的每一節，都建議你用這四步來判斷一個模式：壞味道 → 量尺 → 地圖 → 帳單。
