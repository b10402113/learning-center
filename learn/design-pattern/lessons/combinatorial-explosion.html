笛卡爾積膨脹：ifelse 的壞味道

學習目標

理解「多支付渠道 × 多支付模式」的笛卡爾積膨脹問題，體會 ifelse 雙層嵌套的壞味道，並能說出這種結構為什麼不可維護。

一個真實的聚合支付場景

想像你是一家第三方聚合支付平台的後端工程師。商家不想讓用戶改變支付習慣，所以平台需要同時支援微信支付、支付寶等多個支付渠道。同時，每個渠道又要支援刷臉、指紋、密碼等多種支付方式。

業務需求很直觀：用戶選擇一個支付渠道（微信或支付寶），再選一種支付方式（刷臉、指紋或密碼），系統完成支付。

先看「一把梭」的寫法

如果你用最直覺的方式寫，大概會這樣：

PayController.doPay（壞味道版本） 
public String doPay(String uId, String tradeId, int amount,
                     int channelType, int modeType) {
    // 第一層：判斷支付渠道
    if (1 == channelType) {
        // 微信支付
        if (1 == modeType) {
            // 微信 + 密碼
            return "微信支付 + 密碼校驗：" + uId;
        } else if (2 == modeType) {
            // 微信 + 刷臉
            return "微信支付 + 刷臉校驗：" + uId;
        } else if (3 == modeType) {
            // 微信 + 指紋
            return "微信支付 + 指紋校驗：" + uId;
        }
    } else if (2 == channelType) {
        // 支付寶
        if (1 == modeType) {
            return "支付寶 + 密碼校驗：" + uId;
        } else if (2 == modeType) {
            return "支付寶 + 刷臉校驗：" + uId;
        } else if (3 == modeType) {
            return "支付寶 + 指紋校驗：" + uId;
        }
    }
    return "支付失敗";
}

問題在哪裡？笛卡爾積爆炸

現在只有 2 個渠道 × 3 種模式 = 6 個分支，還能勉強維護。但仔細算一筆帳：

維度目前數量如果增加…分支變化
支付渠道2（微信、支付寶）+ 京東支付、雲閃付2 → 4
支付模式3（密碼、刷臉、指紋）+ 指紋2.0、聲紋3 → 5
ifelse 分支64 × 5→ 20

每增加一個渠道，所有模式都要再寫一遍；每增加一種模式，所有渠道也要再寫一遍。分支數是兩個維度的乘積——這就是「笛卡爾積膨脹」。

更深一層的壞味道

ifelse 膨脹不只是代碼量的問題。它還帶來三個更深的麻煩：

1. 違反單一職責

一個方法同時承擔了「判斷渠道」和「判斷模式」兩件事。任何一邊的變更都要動這個方法。

2. 違反開閉原則

新增一種支付模式（比如聲紋），你需要修改所有渠道的 ifelse 分支——這是對「已有代碼」的修改，不是「擴展」。

3. 測試組合爆炸

2 × 3 = 6 組測試用例。如果變成 4 × 5 = 20，測試成本直線上升，而且每組之間高度重複。

核心洞察：當你發現代碼裡出現「if A then if B then …」的雙層嵌套，而且 A 和 B 是兩個獨立維度——這就是在警告你：這兩個維度不該攪在一起。

那該怎麼辦？

問題的根源是：渠道和模式是兩個獨立變化的維度，但它被塞進了同一個方法。解決思路是把它們「拆開」——讓渠道歸渠道、模式歸模式，需要組合的時候再「接」起來。

這正是橋接模式（Bridge Pattern）的核心思路：把「抽象部分」和「實現部分」分離，讓它們各自獨立變化。下一節我們會看到這個結構具體長什麼樣。

小結

  • 多維度組合如果用 ifelse 實現，分支數是維度的乘積——笛卡爾積膨脹
  • 壞味道不只是代碼量，更在於違反單一職責和開閉原則
  • 信號：看到「if A then if B」且 A、B 是獨立維度，就該警覺
