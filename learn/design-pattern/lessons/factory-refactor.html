工廠方法模式重構發獎代碼

design-pattern › factory-method › factory-refactor

學習目標：能用統一的 ICommodity 接口 + 三種實現類 + StoreFactory 工廠，替代發散的 ifelse 發獎分支，說清每一層的職責。

重構的第一步：統一接口

上一課看到的 ifelse 代碼，核心問題是三個服務的接口不一樣——方法名不同、參數不同、返回值不同。要消除分支發散，第一步是讓它們「看起來一樣」。

定義一個統一的發獎接口：

public interface ICommodity {
    void sendCommodity(String uId, String commodityId,
                       String bizId, Map<String, String> extMap) throws Exception;
}

所有商品都實現這個接口：方法名統一、入參統一（用戶 ID、商品 ID、業務 ID、擴展字段）、返回值統一為 void。異常直接拋出，讓調用方統一處理。實物商品的收貨地址放在 extMap 裡傳入，不再需要為它單獨加參數。

關鍵：接口統一之後，調用方不需要知道具體是哪種商品——只要拿到一個 ICommodity 實例，就能用同樣的方式調用 sendCommodity。

三種實現類：各管各的

每種商品在自己的實現類裡完成業務邏輯，互不干擾：

優惠券實現

public class CouponCommodityService implements ICommodity {
    @Override
    public void sendCommodity(String uId, String commodityId,
                              String bizId, Map<String, String> extMap) throws Exception {
        CouponService couponService = new CouponService();
        CouponResult result = couponService.sendCoupon(uId, commodityId, bizId);
        if (!"0000".equals(result.getCode())) {
            throw new RuntimeException("優惠券發放失敗");
        }
    }
}

實物商品實現

public class GoodsCommodityService implements ICommodity {
    @Override
    public void sendCommodity(String uId, String commodityId,
                              String bizId, Map<String, String> extMap) throws Exception {
        GoodsService goodsService = new GoodsService();
        DeliverReq req = new DeliverReq();
        req.setuId(uId);
        req.setGoodsId(commodityId);
        req.setBusinessId(bizId);
        req.setExtMap(extMap);
        Boolean success = goodsService.deliverGoods(req);
        if (!success) {
            throw new RuntimeException("實物商品發放失敗");
        }
    }
}

第三方兌換卡實現

public class CardCommodityService implements ICommodity {
    @Override
    public void sendCommodity(String uId, String commodityId,
                              String bizId, Map<String, String> extMap) throws Exception {
        CardService cardService = new CardService();
        String phone = queryUserPhoneNumber(uId);
        cardService.grantToken(phone, commodityId);
    }
}

三個類各自管各自的：優惠券調優惠券的接口、實物商品拼裝 DeliverReq、兌換卡查手機號。新增商品？加一個新的實現類就行，不動任何已有代碼。

工廠類：把分發邏輯收到一處

調用方不需要知道有幾種實現類。工廠類負責按類型返回對應的 ICommodity：

public class StoreFactory {
    public static ICommodity getCommodityService(Integer commodityType) {
        if (commodityType == 1) {
            return new CouponCommodityService();
        } else if (commodityType == 2) {
            return new GoodsCommodityService();
        } else if (commodityType == 3) {
            return new CardCommodityService();
        }
        throw new RuntimeException("不存在的商品服務類型");
    }
}
注意：ifelse 沒有消失，但它從調用方收斂到了工廠類這一個地方。以前每加一種商品要改 Controller，現在只需要在工廠裡加一行，再寫一個實現類。

調用方的代碼變得非常乾淨：

ICommodity commodityService = StoreFactory.getCommodityService(req.getAwardType());
commodityService.sendCommodity(req.getuId(), req.getAwardNumber(),
                                req.getBizId(), req.getExtMap());

兩行代碼：拿到服務、調用發放。不需要知道具體是哪種商品，不需要拼裝不同的參數，不需要判斷返回值類型。

對比：ifelse vs 工廠方法

維度ifelse 一把梭工廠方法模式
新增商品改 Controller 加分支，動已有代碼加一個實現類 + 工廠加一行
修改某種商品在大方法裡找到對應分支，怕影響其他分支只改對應的實現類
單元測試三種邏輯耦合，無法獨立測試每個實現類可以獨立單測
可讀性新同事要把所有 if 全讀一遍想知道哪種商品？打開對應的實現類
參數所有商品的參數混在一個方法裡extMap 統一處理，各實現類按需取用

小結

工廠方法模式的重構分三層：接口層統一調用約定（ICommodity），實現層各管各的業務邏輯，工廠層按類型分發實例。ifelse 沒有消失，但從散落在業務代碼裡收斂到了工廠這一個地方——新增商品只需要「加實現類 + 加工廠分支」，不動任何已有代碼。下一課我們會討論這個模式的收益和局限。
