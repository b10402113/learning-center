Lesson 2/3 · 觀察者模式

一把梭的耦合代價

Node: observer · Step 2/3 · 行為模式

學習目標

認知「一把梭」把輔助流程（簡訊/MQ）塞進核心方法的耦合代價，作為觀察者模式重構的動機。

什麼是「一把梭」？

「一把梭」是開發者對最粗暴實現方式的俗稱——把所有功能按順序寫在一個方法裡，不做任何分層或解耦。需求來了就加代碼，像梭子一樣直来直去。

在搖號場景中，一把梭的意思是：搖號、發簡訊、發 MQ，三件事全塞進一個 doDraw 方法裡。

一把梭的代碼長什麼樣？

搖號服務接口 MinibusTargetService.lottery(uId) 用 uId 的 hashCode 取絕對值後對 2 取模，偶數為中簽，返回拼接好的文案。這是被觀察的「事件源」。

一把梭的實現把三件事全塞進 doDraw 方法：

public LotteryResult doDraw(String uId) {
    // 1. 核心流程：搖號
    String lottery = minibusTargetService.lottery(uId);

    // 2. 輔助流程：發簡訊
    logger.info("給用戶 {} 發送簡訊通知：{}", uId, lottery);

    // 3. 輔助流程：發 MQ
    logger.info("記錄用戶 {} 搖號結果(MQ)：{}", uId, lottery);

    return new LotteryResult(uId, lottery, new Date());
}

三件事按順序執行，看起來沒什麼問題——測試也能跑通。

壞味道在哪？

代碼能跑不代表設計好。一把梭的問題在於：

輔助流程與核心流程耦合——簡訊和 MQ 的邏輯直接寫在核心方法裡，每加一種通知就要改這個方法。

具體來說有三個痛點：

痛點具體表現後果
修改風險改簡訊邏輯可能影響搖號結果不敢改、改了怕出事
擴展困難加一種通知就要改 doDraw方法越來越長、分支越來越多
職責不清一個方法做三件事後人看不懂、不知道該改哪裡

你可能見過更極端的情況：一個類幾千行，if-else 分支堆出來的業務大類型。一把梭就是這種「一坨代碼」的起點——從一個方法開始，慢慢長成一坨。

用生活類比理解耦合

想像你開了一家餐廳，廚師做完菜後，你親自跑去：

  1. 給每桌客人端菜
  2. 結算每桌的帳單
  3. 登記每個客人的會員積分
  4. 給外賣平台同步訂單狀態

你是廚師（核心流程），但你同時在做傳菜、結帳、積分、同步四件輔助的事。每來一個新需求（比如加一個「掃碼點評」），你就多一件事，廚房就沒人管了。

觀察者模式的做法是：廚師只管做菜，傳菜員、收銀員、積分系統、外賣平台各自訂閱「菜做好了」這個事件——你做你的菜，他們做他們的事。

一把梭 vs 觀察者——對比一覽

一把梭觀察者模式
核心流程與輔助流程混在一起只處理核心邏輯
輔助流程直接寫在核心方法裡各自獨立的監聽器
加新通知改核心方法新增監聽器類
風險改輔助可能影響核心互不影響
可讀性方法越來越長每個類只做一件事

這就是觀察者模式重構的動機：把輔助流程從核心方法裡「搬出來」，讓它們各自獨立。

一句話記住

一把梭 = 把所有事塞進一個方法，改一個怕動另一個；觀察者 = 各做各的，互不干擾。

自我檢測

Q1. 一把梭實現的搖號服務有什麼核心問題？

  • 輔助流程（簡訊/MQ）與核心流程耦合
  • 搖號算法不夠公平
  • 返回值類型定義錯誤
  • 沒有使用多線程

Q2. 在一把梭代碼中，如果要新加一個「郵件通知」功能，你必須改哪裡？

  • 新增一個郵件類就好
  • 修改 doDraw 方法，加一段郵件邏輯
  • 修改 MinibusTargetService
  • 重寫整個搖號算法

Q3. 為什麼說「輔助流程經常變化」是壞味道的根源？

  • 因為輔助流程更複雜
  • 因為輔助流程需要更多測試
  • 因為變化頻率高，耦合在核心方法裡會不斷增加修改風險
  • 因為輔助流程不應該存在
主要來源：一把梭實現需求——代碼實現、案例場景模擬——搖號通知
