秒殺場景痛點：固定信息為什麼每次都在重建？

design-pattern › flyweight › flyweight-problem

學習目標：識別秒殺活動查詢中「固定信息」與「變化信息」的分界，理解每次全量查詢帶來的冗餘浪費。

從一個秒殺系統說起

你在電商平台做後端，公司剛上線了一個圖書秒殺活動——「圖書嗨樂：圖書優惠券分享激勵分享活動第二期」。一開始日均十幾單，系統跑得很順。但隨著活動推廣，每個時段的秒殺量衝破十萬。

这时候問題來了：每次用戶打開秒殺頁面，後端都要查詢一次活動信息。

public Activity queryActivityInfo(Long id) {
    // 每次查詢都從數據庫/接口取全量數據
    Activity activity = new Activity();
    activity.setId(10001L);
    activity.setName("圖書嗨樂");
    activity.setDesc("圖書優惠券分享激勵分享活動第二期");
    activity.setStartTime("2024-06-01");
    activity.setStopTime("2024-06-30");
    activity.setStock(new Stock(1000, 1));  // 總量 1000，已用 1
    return activity;
}

看起來很乾淨對吧？但仔細想想：這個活動的名稱、描述、開始結束時間，從活動上線到結束，一個字都沒變過。變化的只有庫存數字。然而每次查詢，都在重新創建這些一模一樣的對象。

固定信息 vs 變化信息

把活動數據拆開看，很自然地分成兩類：

分類字段特徵
固定信息（內部狀態）活動名稱、描述、起止時間活動期間不變，所有用戶看到的都一樣
變化信息（外部狀態）庫存（已售數量）隨交易實時變化，每個時刻不同

這就是享元模式（Flyweight Pattern）的核心切入點：把不變的抽出來共享，把會變的分離出去單獨獲取。

全量查詢的代價

你可能會說：「new 一個對象能有多大開銷？」在日均十幾單的時候確實無感。但想像一下：

  • 每個時段十萬次查詢
  • 每次查詢都構建完整的 Activity 對象（含固定字段的字符串賦值）
  • 如果活動信息來自數據庫，就是十萬次相同的 SQL 查詢
  • 如果活動信息來自遠端接口，就是十萬次相同的 RPC 調用

十萬次重複構建完全相同的數據——這就是冗餘。

壞味道：每次查詢都「從零開始」構建不變的數據，就像每次做飯都重新買米、重新裝米缸，做完又倒掉。

一個直覺：緩存能解決嗎？

你的第一反應可能是「加個緩存」。沒錯，享元模式的本質就是一種針對性緩存——但不是把所有東西都丟進 Redis 那種通用緩存，而是從設計層面把「共享對象」和「外部狀態」的職責分清楚，用一個專門的工廠來管理共享。

用一個類比：你在公司印名片。名片上的公司名、地址、電話這些固定信息，不需要每次都重新排版——存一個模板就行。但每個人的姓名和職位是變化的，得臨時填進去。享元工廠就是那個「模板庫」。

小結

秒殺場景暴露的核心問題是：固定信息與變化信息混在一起查詢，導致不變的數據被反覆構建。這是享元模式要解決的起點。下一課我們會正式拆解享元模式的三個核心概念：內部狀態、外部狀態、享元工廠。
