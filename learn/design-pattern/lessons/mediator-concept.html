中介者模式的意圖與 ORM 場景定位

design-pattern › mediator › mediator-concept

學習目標：能說出中介者模式「集中協調、解耦網狀依賴」的意圖，並用 ORM / 中台場景解釋它解決什麼問題。

先看生活中的例子

機場塔台（Air Traffic Controller）是一個經典的中介者：

  • 飛機 A 要降落，飛機 B 要起飛，飛機 C 在滑行——如果三架飛機自己互相喊話協調，場面會很混亂
  • 塔台作為中介者，所有飛機只跟塔台通信，塔台統一協調誰先降落、誰等待、誰滑行
  • 每架飛機不需要知道其他飛機的存在，只需要聽塔台的指令

工程世界也一樣：當多個模塊之間的調用關係變成網狀（A 調 B、B 調 C、C 又調 A），每個人都要依賴其他人的接口——改一個就要改一圈。這時候就需要一個「塔台」。

中介者模式的定義

用一個中介者對象封裝一系列對象交互，使各對象不需要顯式相互引用，從而耦合鬆散且可獨立改變它們之間的交互。

白話翻譯：把「誰跟誰打招呼」這件事收進一個中間人，所有人只跟中間人說話。

這個模式要解決的具體問題：

沒有中介者有中介者
A 知道 B、C、D 的接口A 只知道 M（中介者）
改 B 的接口 → A、C、D 都要改改 B 的接口 → 只有 M 要改
N 個對象的交互 = N² 量級的依賴N 個對象的交互 = N 量級的依賴

工程中的典型應用

中介者在後端開發中隨處可見：

  • ORM 中間件（Mybatis、Hibernate）：封裝連接、SQL 解析、結果映射，業務方只寫 SQL 和 POJO
  • 公司中台：把 N 種獎品服務的接口統一收到一個獎品中心，對外只暴露一個通用接口
  • API 網關：所有微服務的路由、鑑權、限流收進網關，客戶端只跟網關通信
  • 消息中間件（Kafka、RabbitMQ）：生產者和消費者不直接對話，通過 Broker 中轉

本節的場景：手寫 ORM 框架

我們用「模仿 Mybatis 手寫 ORM 框架」來體現中介者模式。思路很直接：

  1. 先把痛點看清（上一課）：一把梭 JDBC 把連接、驅動、SQL 執行、結果映射全部暴露給業務方
  2. 用中介者包裝：把這些細節收進 SqlSession / Factory / Builder / Configuration 四層組件
  3. 外部只按「statement + 參數」調用：跟用 Mybatis 一樣簡單

模型結構預覽

中介者的整體分工分三大塊：

  • 查詢側：SqlSession（接口）定義 selectOne / selectList，DefaultSqlSession 實現具體的 JDBC 調用和結果映射
  • 工廠側：SqlSessionFactory（接口）定義 openSession()，DefaultSqlSessionFactory 持有 Configuration 並創建 Session
  • 装配側：SqlSessionFactoryBuilder 是啟動入口——解析 XML 配置、建立連接、構建 Configuration

小結

中介者模式的核心動機是把網狀依賴收成星型依賴——所有人只跟中介者說話。在 ORM 場景裡，中介者就是把 JDBC 的四步瑣事封裝起來，讓業務方只做「寫 SQL + 定義 POJO」兩件事。判斷「何時該引入中介者」的判據：對象交互複雜、重複調用多、需要統一入口。
