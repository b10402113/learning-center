装饰器模式的本质与结构

结构型

本课目标
说清装饰器模式的四个角色，以及"构造函数注入 + 接口转发"的包裹机制。

场景：SSO 拦截器要加方法级权限

你有一个 Spring SSO 登录拦截器 SsoInterceptor，负责检查用户是否已登录。现在新需求来了：除了登录检查，还要加方法级权限控制——某些接口只允许特定用户访问。

直觉做法：写一个子类继承 SsoInterceptor，在 preHandle 里加上权限逻辑。

问题：如果以后还要加日志、审计、限流……每个都继承一次，子类会爆炸。

装饰器的核心思路

装饰器的解法：不继承，而是包一层。用构造函数注入原始对象，调用时转发给它，转发前后可以加任意逻辑。

调用方
→
装饰器
转发前/后加逻辑
→
原始对象

这就是装饰器的全部秘密：构造函数注入 + 接口转发。

四个角色

Component（抽象组件） 定义接口，所有角色都实现它。原始对象和装饰器都实现同一个接口。
interface SsoInterceptor { boolean preHandle(...); }
ConcreteComponent（具体组件） 被装饰的原始对象，实现 Component 接口。
class SsoInterceptor implements SsoInterceptor { ... }
Decorator（抽象装饰器） 实现 Component，构造函数接收一个 Component 实例，调用时转发给它。
abstract class SsoDecorator implements SsoInterceptor { wrapped.preHandle(...); }
ConcreteDecorator（具体装饰器） 继承 Decorator，在转发前后加自己的逻辑。
LoginSsoDecorator 加权限检查

代码：SsoDecorator 实战

核心：Decorator 持有 wrapped 对象，转发调用；ConcreteDecorator 在转发前后加逻辑。

// Component — 所有拦截器都实现这个接口
public interface SsoInterceptor {
    boolean preHandle(HttpServletRequest request,
                      HttpServletResponse response,
                      Object handler);
}

// ConcreteComponent — 原始的 SSO 登录拦截器
public class SsoInterceptor implements SsoInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest request,
                             HttpServletResponse response,
                             Object handler) {
        // 检查用户是否已登录
        String token = request.getHeader("token");
        return token != null && validateToken(token);
    }
}

// Decorator — 抽象装饰器，持有被装饰对象
public abstract class SsoDecorator implements SsoInterceptor {
    protected SsoInterceptor wrapped;

    public SsoDecorator(SsoInterceptor wrapped) {
        this.wrapped = wrapped;  // 构造函数注入
    }

    @Override
    public boolean preHandle(HttpServletRequest request,
                             HttpServletResponse response,
                             Object handler) {
        return wrapped.preHandle(request, response, handler);  // 转发
    }
}

// ConcreteDecorator — 加方法级权限控制
public class LoginSsoDecorator extends SsoDecorator {

    public LoginSsoDecorator(SsoDecorator ssoDecorator) {
        super(ssoDecorator);
    }

    @Override
    public boolean preHandle(HttpServletRequest request,
                             HttpServletResponse response,
                             Object handler) {
        // ① 先调用被装饰对象（登录检查）
        boolean success = wrapped.preHandle(request, response, handler);
        if (!success) return false;

        // ② 转发后加自己的逻辑（方法级权限）
        String method = request.getMethod();
        String uri = request.getRequestURI();
        return checkMethodPermission(method, uri);
    }
}

使用时像套娃一样组装：

// 原始拦截器
SsoInterceptor sso = new SsoInterceptor();
// 加一层权限装饰
SsoInterceptor auth = new LoginSsoDecorator(sso);
// 再加一层审计装饰（假设以后有）
SsoInterceptor audited = new AuditDecorator(auth);

你已经用过装饰器了

JDK I/O 流就是最经典的装饰器：

// BufferedReader 装饰 FileReader
BufferedReader reader = new BufferedReader(new FileReader("data.txt"));
// InputStreamReader 装饰 FileInputStream
InputStreamReader isr = new InputStreamReader(new FileInputStream("data.txt"), "UTF-8");

FileReader 是 ConcreteComponent，BufferedReader 是 ConcreteDecorator——构造函数注入，转发 read() 调用，同时加了缓冲功能。

关键洞察

核心机制 装饰器的秘密只有两步：构造函数注入被装饰对象 + 接口转发调用。转发前后可以加任意逻辑。多个装饰器可以像套娃一样层层包裹。

本课小结

  1. 装饰器的四个角色：Component、ConcreteComponent、Decorator、ConcreteDecorator
  2. 核心机制：构造函数注入 + 接口转发
  3. 装饰器和原始对象实现同一个接口，调用方感知不到区别
  4. 多个装饰器可以层层嵌套（套娃），像 new BufferedReader(new FileReader(...))
  5. 装饰器用于动态添加功能，不修改原始类
