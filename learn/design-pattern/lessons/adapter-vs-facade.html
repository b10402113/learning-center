设计模式 · 适配器与外观 · 第 4/4 课

适配器还是外观：何时包接口、何时包子系统

结构型

这一课的目标

读完之后，面对一段需要"包一层"的代码，你能判断该用适配器（统一接口）还是外观（简化子系统入口）。

核心区别：一张图说清楚

适配器 调用方 适配器（翻译层） 不兼容的接口 A
包的是：一个接口
外观 调用方 外观（门面层） 子系统 A 子系统 B 子系统 C
包的是：一整个子系统

三个判断维度

选择适配器

  • 已有接口的格式/参数/返回值和你想要的不一致
  • 你需要翻译，不是简化
  • 通常包的是一个不兼容的接口

选择外观

  • 背后有多个子系统/步骤，调用方不该知道这些细节
  • 你需要简化，不是翻译
  • 通常包的是多个类/服务组成的子系统

场景判断练习

🎯 场景 1：一个 Service 要调三个第三方支付接口，各家入参格式完全不同。
→ 用什么？
点击查看答案

适配器——问题是"接口不兼容"，三个支付接口格式不同需要翻译成统一形态。适配器翻译的是接口格式。

🎯 场景 2：你写了一个自定义 Starter，把白名单、限流、日志都包装起来，业务代码只加一个注解。
→ 用什么？
点击查看答案

外观——问题是"调用方太复杂"，白名单/限流/日志是多个子系统组成的跨切面关注点，外观把它们包装成一个统一入口。

🎯 场景 3：系统要从单节点 Redis 升级到集群 Redis，但不想改业务代码。
→ 用什么？
点击查看答案

适配器——旧的 Redis 客户端接口和新的集群接口不兼容，需要适配器翻译。业务代码只认 ICacheAdapter 接口，背后切换 EGM/IIR 不受影响。

🎯 场景 4：一个 Controller 要查用户信息、订单列表、积分余额，背后分别是三个微服务。
→ 用什么？
点击查看答案

外观——三个微服务组成一个子系统，Controller 不该知道要分别调谁。外观提供一个 getUserProfile(uid) 方法一次性搞定。

🎯 场景 5：Spring 框架里 HandlerAdapter 要让 DispatcherServlet 支持多种 Handler 类型。
→ 用什么？
点击查看答案

适配器——不同类型的 Handler（Controller、HandlerFunction 等）接口不同，HandlerAdapter 把它们统一成 DispatcherServlet 能调用的格式。

关键洞察

一句话记住：

适配器翻译格式，外观简化路径。

如果你在说"这个接口的参数/返回值和那个不一样"，用适配器。
如果你在说"背后太复杂了，调用方不该知道这些"，用外观。

节点回顾

这一节一共四课，回顾一下学了什么：

  1. 第 1 课：识别两种结构问题——接口不兼容（适配器）vs 调用方太复杂（外观）
  2. 第 2 课：适配器模式——配置驱动的 MQ 字段映射、订单首单适配、框架中的 *Adapter
  3. 第 3 课：外观模式——自定义 SpringBoot Starter（注解 + AOP + 自动装配）、中间件的本质
  4. 第 4 课（本课）：对比两种模式，掌握判断标准——翻译格式用适配器，简化路径用外观

本课小结

  1. 适配器翻译格式（接口的参数/返回值不兼容）
  2. 外观简化路径（背后多个子系统，调用方只需一个入口）
  3. 两者都不修改原始代码，都属于结构型模式
  4. 判断标准：如果你在说"这个接口的参数和那个不一样"→ 适配器；如果你在说"背后太复杂了"→ 外观
  5. 框架识别：看到 *Adapter → 适配器；看到 Starter + AOP + 注解 → 外观
