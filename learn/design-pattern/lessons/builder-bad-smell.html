ifelse 實現的維護災難

設計模式 · 建造者模式 · Step 2/4
學習目標：識別 ifelse 實現套餐選擇的代碼壞味道，理解「一個類幾千行」的維護代價。

先用最直覺的方式寫

回到裝修套餐場景。你有四種物料、三種套餐，最直覺的寫法是什麼？——一個方法，裡面用 if 判斷等級，然後 new 出對應的物料組合。

public List<Matter> getMatterList(BigDecimal area, Integer level) {
    List<Matter> list = new ArrayList<>();
    if (1 == level) {  // 豪華歐式
        list.add(new LevelTwoCeiling());   // 二級頂 850
        list.add(new DuluxCoat());         // 多樂士 719
        list.add(new ShengXiangFloor());   // 聖象 318
    } else if (2 == level) {  // 輕奢田園
        list.add(new LevelTwoCeiling());
        list.add(new LiBangCoat());        // 立邦 650
        list.add(new MarcoPoloTile());     // 馬可波羅 140
    } else if (3 == level) {  // 現代簡約
        list.add(new LevelOneCeiling());   // 一級頂 260
        list.add(new LiBangCoat());
        list.add(new DongPengTile());      // 東鵬 102
    }
    // ... 然後計算價格、拼接清單文本
    return list;
}

看著還行？問題在後面。

壞味道一：重複邏輯

每個 if 分支裡做三件事：new 物料、加入清單、按面積乘以係數算價格。吊頂 ×0.2、塗料 ×1.4、地板和地磚 ×面積。這段價格計算邏輯在三個分支裡完全重複。

改一個計算係數？三個分支都要改。漏改一個？三種套餐的價格就不一致了。

壞味道二：清單拼接和業務邏輯混在一起

除了選料和算價格，這個方法還要拼接裝修清單的文本——把品牌、型號、單價、面積、總價串成一段可讀的字符串。業務邏輯（選什麼料）和展示邏輯（怎麼顯示）混在同一個方法裡，改顯示格式會影響業務計算。

壞味道三：一個類扛所有

整個工程只有一個核心類 DecorationPackageController。三種套餐的選擇、計算、展示全在一個類裡。作者說這就是「一個類幾千行代碼」的潛質——先能跑，再慢慢堆，堆到不可維護。

老闆說要加套餐

幾個月後，老闆說：「加一個『輕奢北歐』套餐！」你需要：

  1. 在 ifelse 裡加一個 else if (4 == level) 分支
  2. 複製一套物料 new + 價格計算 + 清單拼接的代碼
  3. 確認計算係數沒抄錯
  4. 確認清單格式沒漏改

十種套餐？二十種？每個套餐都要加一段幾乎相同的代碼。像膏藥一樣一塊塊貼上去，維護成本呈線性增長。

測試結果（功能是對的）

用單測跑三檔套餐：

套餐面積報價
豪華歐式132.52 m²198,064.39 元
輕奢田園98.25 m²119,865.00 元
現代簡約85.43 m²90,897.52 元

功能完全正確。但代碼結構已經埋下了維護地雷。功能對不等於結構好——這是判斷代碼質量的第一課。

小結：ifelse 的代價

問題具體表現
重複邏輯價格計算在每個分支裡複製粘貼
職責混雜選料、計算、展示全塞一個方法
擴展困難加一個套餐 = 加一段複製代碼
單類膨脹一個類扛所有，朝幾千行發展
