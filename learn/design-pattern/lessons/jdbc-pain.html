一把梭 JDBC 直連的痛點

design-pattern › mediator › jdbc-pain

學習目標：看到一把梭 JDBC 直連的四步流程，並說出它在業務擴展時的具體痛點。

場景：直接用 JDBC 查資料庫

假設你有一個簡單需求：從 MySQL 查出使用者列表並打印。最直覺的寫法就是寫一個 JDBCUtil 類，main 方法裡直接走完 JDBC 四步：

public class JDBCUtil {
    public static void main(String[] args) throws Exception {
        // 第一步：載入驅動
        Class.forName("com.mysql.jdbc.Driver");

        // 第二步：取得連接
        Connection connection = DriverManager.getConnection(
            "jdbc:mysql://localhost:3306/itstack_demo_design",
            "root", "root");

        // 第三步：建立 Statement 並查詢
        Statement statement = connection.createStatement();
        ResultSet resultSet = statement.executeQuery(
            "SELECT id, name, age, createTime, updateTime FROM user");

        // 第四步：遍歷結果
        while (resultSet.next()) {
            System.out.println(resultSet.getString("name")
                + "，年齡：" + resultSet.getInt("age"));
        }
    }
}

跑起來沒問題，輸出：

水水，年齡：18
豆豆，年齡：18
花，年齡：19

痛點在哪？

這段代碼「能跑」，但問題藏在它把所有東西都暴露給業務方：

暴露的細節為什麼是痛點
驅動類名 com.mysql.jdbc.Driver換 Oracle 或 PostgreSQL 要改業務代碼
連接字串、帳號密碼不同環境（dev/staging/prod）要硬切配置
SQL 字符串直接寫死改查詢就要改業務類，沒有複用空間
ResultSet 逐行手動取值每個查詢都要寫一遍 while loop，N 個查詢就是 N 個 while

一句話：業務代碼跟 JDBC 細節強耦合。一個查詢這樣寫還好，十個查詢、三種資料庫、五套環境呢？每個查詢都 copy 一遍這四步？

更深一層：無法複用

假設公司有三種獎品服務（金幣、優惠券、實物），每種都要查資料庫。如果每個服務都自己寫 JDBC 四步，你會得到：

  • 三份幾乎一樣的驅動/連接代碼
  • 三份不同的 SQL，但結果處理邏輯（列名→字段映射）完全重複
  • 連接池管理分散在各處，沒法統一控管

這就是「一把梭」的代價：重複、分散、難改。要消除這些痛點，就需要一層「中介者」把 JDBC 細節封裝起來，讓業務方只關心「查什麼、用什麼參數」。

小結

一把梭 JDBC 直連的本質問題：業務邏輯和基礎設施細節攪在一起。每多一個查詢，重複就多一份。下一課我們看看中介者模式怎麼把這些細節收進一個統一的包裝層。
