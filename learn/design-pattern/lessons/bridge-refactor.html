支付場景重構實戰

學習目標

透過支付渠道×支付模式的完整重構過程，體會從 ifelse 到橋接模式的轉變，掌握抽象類組合介面、構造注入的標準寫法。

重構前：一個方法搞定所有

回顧一下重構前的 PayController：所有支付渠道和支付模式的組合邏輯，全部堆在一個 doPay 方法裡。兩個 int 參數（channelType、modeType）控制一切，雙層 ifelse 嵌套。

重構前：PayController 一個類承擔所有支付邏輯 
public class PayController {
    public String doPay(String uId, String tradeId, int amount,
                         int channelType, int modeType) {
        if (1 == channelType) {
            if (1 == modeType) return "微信+密碼：" + uId;
            if (2 == modeType) return "微信+刷臉：" + uId;
            if (3 == modeType) return "微信+指紋：" + uId;
        } else if (2 == channelType) {
            if (1 == modeType) return "支付寶+密碼：" + uId;
            if (2 == modeType) return "支付寶+刷臉：" + uId;
            if (3 == modeType) return "支付寶+指紋：" + uId;
        }
        return "支付失敗";
    }
}

重構思路：拆成兩棵樹

橋接模式要求我們把兩個維度分開：

  • 抽象部分（渠道）：Pay 抽象類 → WxPay、ZfbPay
  • 實現部分（模式）：IPayMode 介面 → PayCypher、PayFaceMode、PayFingerprintMode

第一步：定義實現介面 IPayMode

先把「支付模式」抽成一個介面：

public interface IPayMode {
    String security(String uId);
}

每個模式實現自己的風控校驗邏輯：

// 密碼校驗
public class PayCypher implements IPayMode {
    public String security(String uId) {
        // 模擬密碼校驗
        return "密碼校驗通過";
    }
}

// 刷臉校驗
public class PayFaceMode implements IPayMode {
    public String security(String uId) {
        return "刷臉校驗通過";
    }
}

// 指紋校驗
public class PayFingerprintMode implements IPayMode {
    public String security(String uId) {
        return "指紋校驗通過";
    }
}

第二步：建立抽象類 Pay（橋的載體）

Pay 抽象類是整個橋接的核心——它持有 IPayMode 的引用：

public abstract class Pay {
    protected IPayMode payMode;  // 橋！

    public Pay(IPayMode payMode) {
        this.payMode = payMode;
    }

    public abstract String transfer(String uId, String tradeId, int amount);
}

注意 protected IPayMode payMode 這行。這就是橋。構造函數接收一個 IPayMode 的實現，存到 payMode 字段。子類在 transfer 中可以隨時呼叫 payMode.security(uId) 做風控。

第三步：實現具體渠道

WxPay 和 ZfbPay 各自實現自己的 transfer 邏輯，但風控校驗交給橋對面的 payMode：

public class WxPay extends Pay {
    public WxPay(IPayMode payMode) {
        super(payMode);
    }

    public String transfer(String uId, String tradeId, int amount) {
        // 1. 先走橋對面的風控
        String check = payMode.security(uId);
        // 2. 再做微信自己的轉賬邏輯
        return "微信支付成功。金額：" + amount + "，校驗：" + check;
    }
}

public class ZfbPay extends Pay {
    public ZfbPay(IPayMode payMode) {
        super(payMode);
    }

    public String transfer(String uId, String tradeId, int amount) {
        String check = payMode.security(uId);
        return "支付寶支付成功。金額：" + amount + "，校驗：" + check;
    }
}

第四步：客戶端組合

客戶端不需要關心具體實現，只需要「new 一個渠道 + 塞一個模式進去」：

// 微信 + 刷臉
Pay wxPay = new WxPay(new PayFaceMode());
System.out.println(wxPay.transfer("user001", "trade001", 100));

// 支付寶 + 指紋
Pay zfbPay = new ZfbPay(new PayFingerprintMode());
System.out.println(zfbPay.transfer("user002", "trade002", 200));

調用方式從 doPay("user001", ..., 1, 2) 變成了 new WxPay(new PayFaceMode()).transfer(...)。不再需要記住數字型的 type 參數，意圖一目了然。

重構前後對比

維度重構前重構後
文件數1 個 PayController7 個（1 抽象類 + 1 介面 + 5 實現）
新增渠道改 PayController 的 ifelse加一個 Pay 子類
新增模式改所有渠道的 ifelse加一個 IPayMode 實現
組合測試2 × 3 = 6 組全測各維度獨立測 + 少量組合驗證
客戶端調用傳數字 type語意化 new + 傳入模式

測試驗證

橋接版的測試覆蓋兩個典型組合：微信+刷臉、支付寶+指紋。兩側測試結果功能一致（支付都能完成），但橋接版調用方式更整潔、乾淨。正如原書所說：「內容一樣，但實現方式有了很大變化，不能只看結果還要看過程。」

重構的本質：不改外部可觀察結果，只改善內部結構。橋接模式讓渠道和模式各歸各位，組合關係從「代碼裡的 ifelse」變成「客戶端的 new + 傳參」。
