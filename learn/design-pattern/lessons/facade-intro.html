外觀模式的意圖與白名單痛點

design-pattern › facade › facade-intro

學習目標：能說出外觀模式「降低調用方複雜度」的意圖，並用白名單 ifelse 場景說出為什麼需要這個模式。

你感受到的容易，一定有人在背後扛

用戶登錄一個網站，現在只要一鍵微信登錄。但在早期，註冊一個賬號要填姓名、昵稱、手機號、QQ、郵箱、住址……一大堆信息。從用戶的角度看，操作變簡單了；從服務端的角度看，是有人把「從各渠道獲取用戶信息、獲取不到就引導補全、補全後發獎勵拉活躍」這些複雜邏輯包了起來，對前端只暴露一個簡單的接口。

這就是外觀模式（Facade Pattern）的核心直覺：在調用方與複雜子系統之間加一個統一的包裝層，讓調用方只關心「用什麼」，不關心「怎麼做」。

一個真實場景：白名單過濾

你在一個電商平台做後端，有一個查詢用戶信息的接口：

@RestController
public class HelloWorldController {
    @RequestMapping("/api/queryUserInfo")
    public UserInfo queryUserInfo(@RequestParam String userId) {
        return new UserInfo("蟲蟲:" + userId, 19, "天津市南開區旮旯胡同100號");
    }
}

很乾淨。但產品說：「上線前要先開白名單測試，只有白名單裡的用戶才能訪問。」

最直覺的做法——直接在方法裡加 if：

@RequestMapping("/api/queryUserInfo")
public UserInfo queryUserInfo(@RequestParam String userId) {
    // 白名單校驗
    List<String> userList = Arrays.asList("1001", "aaaa", "ccc");
    if (!userList.contains(userId)) {
        return new UserInfo("1111", "非白名單可訪問用戶攔截！");
    }
    // 正常業務
    return new UserInfo("蟲蟲:" + userId, 19, "天津市南開區旮旯胡同100號");
}
壞味道：白名單代碼佔了一大塊，但它不是業務邏輯。而且——你有多少個接口？

問題在哪裡

一個接口加一段 if，看起來很快。但想想實際的項目：

  • 接口不止一個：查詢用戶、查詢訂單、查詢商品……每個接口都要加白名單
  • 改一處就要改全部：白名單邏輯變了（比如從 userId 改成 userName），你要改多少個方法？
  • 白名單只是開始：將來可能還要加簽名校驗、限流、日誌審計——每種橫切需求都重複一遍？
  • 業務代碼被污染：原本乾淨的業務方法裡塞滿了「跟業務無關」的判斷，讀代碼的人要分清哪些是核心邏輯、哪些是輔助邏輯

核心問題是：橫切關注點（cross-cutting concern）——像白名單、簽名校驗、限流這類「所有接口都要做的事」——直接塞進每個接口方法裡，會導致大量重複、難以維護。

外觀模式怎麼解決

外觀模式的思路是：把這類通用邏輯從業務方法裡抽出來，放到一個統一的包裝層（facade）裡。業務方法不變，包裝層在外面攔截和處理。

一個生活類比：你去銀行辦業務，不用分別找櫃員、風控、會計、清算——大堂經理就是「外觀」，他幫你把複雜的內部流程包裝成「取號→辦理→走人」的簡單步驟。

沒有外觀有外觀
每個方法自己處理白名單白名單邏輯集中在一個包裝層
改白名單要改 N 個方法改包裝層一處即可
業務邏輯與橫切邏輯混在一起業務方法保持純淨
加新橫切需求（限流等）再重複一遍新需求加一個新的包裝層

在 Spring 生態中，這種包裝層最常見的落地形態就是自定義 starter 中間件——把通用邏輯封裝成一個 jar 包，業務方引入依賴、加一個注解就生效，完全不用改業務代碼。

關鍵概念：結構型模式

外觀模式是 GoF 23 種設計模式中的結構型模式（Structural Pattern）。結構型模式關注的是「類和對象怎麼組合、怎麼形成更大的結構」。外觀模式通過加一個包裝層來簡化調用方對子系統的訪問，是結構型模式中最直覺的一個。

它特別適合的場景是：

場景子系統外觀做什麼
白名單過濾多個 API 接口統一攔截、統一配置
第三方 SDK支付、短信、OSS封裝成一個方法調用
微服務網關多個下游服務統一入口、統一鑑權
ORM 框架JDBC 連接、SQL 解析、結果映射一個 selectOne 搞定

這些場景的共同點是：子系統內部很複雜，但調用方只想用一個簡單的入口。

小結

外觀模式的核心動機是降低調用方的複雜度。當多個接口都要做同一件「跟業務無關」的事情（白名單、簽名校驗、限流），與其在每個方法裡重複一遍，不如抽成一個統一的包裝層。下一步我們會把那個白名單的 ifelse 代碼，用外觀模式 + SpringBoot starter 中間件完整重構一遍。
