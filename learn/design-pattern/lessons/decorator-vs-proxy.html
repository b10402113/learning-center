设计模式 · 装饰器与代理 · 第 4/5 课

装饰器 vs 代理：什么时候用哪个

结构型

本课目标
从动机、意图、实现三方面区分装饰器和代理，并判断框架里的包裹结构属于哪一类。

它们长得一模一样

装饰器和代理的代码结构几乎相同——都是构造函数注入 + 接口转发：

// 装饰器
public class LoginSsoDecorator extends SsoDecorator {
    public LoginSsoDecorator(SsoDecorator wrapped) { super(wrapped); }
    @Override
    public boolean preHandle(...) {
        boolean ok = wrapped.preHandle(...);  // 转发
        if (ok) checkPermission(...);          // 加功能
        return ok;
    }
}

// 代理
public class JdkInvocationHandler implements InvocationHandler {
    private Object target;
    public JdkInvocationHandler(Object target) { this.target = target; }
    @Override
    public Object invoke(Object proxy, Method method, Object[] args)
            throws Throwable {
        // 前置逻辑
        Object result = method.invoke(target, args);  // 转发
        // 后置逻辑
        return result;
    }
}

代码结构一样，但动机完全不同。

核心区别：动机决定一切

装饰器代理
动机 给对象加功能 控制访问对象
意图 透明地扩展行为，调用方不关心 在调用方和真实对象之间加控制层
关注点 "我能做什么" "我怎么访问它"
典型场景 I/O 流加缓冲、拦截器加权限 MyBatis DAO、Spring AOP、RPC
调用方感知 不知道被装饰了 可能知道是代理（如 Spring AOP）
嵌套方式 多层套娃，自由组合 通常只有一层代理

场景判断：三个问题

问题 1：你的动机是加功能还是控访问？
加功能（缓冲、加密、压缩、权限增强）→ 装饰器
控访问（权限检查、日志审计、缓存拦截、远程调用）→ 代理
问题 2：调用方需要知道中间层的存在吗？
不需要，完全透明 → 装饰器
可能需要知道（比如 Spring AOP 的 @Aspect 切面）→ 代理
问题 3：会不会多层嵌套组合？
会，像 JDK I/O 那样层层套娃 → 装饰器
通常只有一层 → 代理

框架里的判断练习

场景装饰器还是代理？理由
new BufferedReader(new FileReader(...)) 装饰器 给 FileReader 加缓冲功能
MyBatis Mapper bean 代理 控制数据库访问，屏蔽 SQL 执行细节
Spring AOP 切面 代理 控制方法调用，织入切面逻辑
LoginSsoDecorator 装饰器 给 SSO 拦截器加方法级权限功能
RPC 框架的 Stub 代理 控制网络访问，屏蔽远程调用细节
BufferedInputStream 装饰器 给 InputStream 加缓冲功能

一个灰色地带

注意 有些结构既是装饰器又是代理。比如 LoginSsoDecorator——它给 SSO 拦截器加了权限功能（装饰器），同时也控制了对原始拦截器的访问（代理）。判断标准是主要动机：如果主要目的是加功能，归为装饰器；如果主要目的是控制访问，归为代理。

关键洞察

一句话区分 装饰器说："我给你加个能力。" 代理说："我替你去访问。" 代码结构一样，动机决定归属。框架里看到"包一层再转发"的结构，先问动机。

本课小结

  1. 装饰器和代理代码结构一样（构造函数注入 + 接口转发），但动机不同
  2. 装饰器动机：加功能（缓冲、加密、权限增强）
  3. 代理动机：控制访问（权限检查、日志审计、远程调用）
  4. 判断三个问题：动机是什么？调用方知不知道？会不会多层嵌套？
  5. 灰色地带看主要动机：加功能归装饰器，控访问归代理
