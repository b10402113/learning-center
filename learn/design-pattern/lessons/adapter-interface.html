接口適配：同義不同出參怎麼統一

設計模式 · 適配器模式 · Step 3/4

學習目標

能定義統一適配接口 OrderAdapterService，把兩個判斷首單方式完全不同的服務包裝成一致的 isFirst(uId) 調用。

業務場景：首單判斷的兩難

行銷系統升級了——不只是發獎勵，還要判斷「是不是首單用戶」才發。但你的系統有兩個來源可以查：

接口 方法 返回值 怎麼判斷首單
OrderService（內部訂單） queryUserOrderCount(uId) long（訂單數量） 數量 ≤ 1 就是首單
POPOrderService（第三方） isFirstOrder(uId) boolean（是否首單） 直接返回 true/false

兩個接口做的是同一件事（判斷首單），但：

  • 方法名不同（queryUserOrderCount vs isFirstOrder）
  • 返回值不同（long vs boolean）
  • 判斷邏輯不同（一個需要自己比較，另一個直接告訴你答案）

你的業務代碼不可能每次都判斷「這是內部訂單還是 POP 訂單，然後用不同方式調用」——那樣每加一種訂單來源就要改一次 if-else。

壞味道：if-else 硬判斷

public void giveReward(String uId, String source) {
    boolean isFirst = false;
    if ("inside".equals(source)) {
        long count = orderService.queryUserOrderCount(uId);
        isFirst = count <= 1;
    } else if ("pop".equals(source)) {
        isFirst = popOrderService.isFirstOrder(uId);
    }
    // 發獎勵...
}
壞味道：業務代碼裡塞滿了「如果是內部訂單就這樣調、如果是 POP 就那樣調」的判斷。每新增一種訂單來源，就要加一個 else 分支，代碼越寫越長。

適配器的做法：統一接口 + 包裝差異

第一步：定義統一適配接口

不管底下用什麼方式判斷首單，我們定義一個統一的接口：

public interface OrderAdapterService {
    boolean isFirst(String uId);
}

一個方法、一個入參、一個出參。所有判斷首單的邏輯都收在這個接口背後。

第二步：為每個來源寫一個適配實現

內部訂單適配器——包裝 OrderService，把「數量查詢」轉換成「是否首單」：

public class InsideOrderService implements OrderAdapterService {
    private OrderService orderService = new OrderService();

    @Override
    public boolean isFirst(String uId) {
        long count = orderService.queryUserOrderCount(uId);
        return count <= 1;  // 數量 ≤ 1 → 首單
    }
}

POP 訂單適配器——包裝 POPOrderService，直接轉發：

public class POPOrderAdapterServiceImpl implements OrderAdapterService {
    private POPOrderService popOrderService = new POPOrderService();

    @Override
    public boolean isFirst(String uId) {
        return popOrderService.isFirstOrder(uId);  // 直接轉發
    }
}

第三步：業務代碼只面對統一接口

// 業務代碼不再關心具體是哪個接口
OrderAdapterService adapter; // 可以是 InsideOrderService 或 POPOrderAdapterServiceImpl
boolean isFirst = adapter.isFirst("100001");
if (isFirst) {
    giveReward("100001");
}
注意 InsideOrderService 的實現：它把「查詢訂單數量 ≤ 1」的判斷邏輯封裝在適配器內部，業務代碼不需要知道「要先查數量再判斷」這個細節。這正是適配器的價值——差異被隔離在適配器裡。

測試結果

// 測試 POP 適配器
OrderAdapterService popAdapter = new POPOrderAdapterServiceImpl();
System.out.println("接口適配(POP)：" + popAdapter.isFirst("100001"));
// 輸出：接口適配(POP)：true

// 測試內部訂單適配器
OrderAdapterService insideAdapter = new InsideOrderService();
System.out.println("接口適配(自營)：" + insideAdapter.isFirst("100001"));
// 輸出：接口適配(自營)：false

同樣的 isFirst("100001") 調用，換一個適配器實例就能查不同來源，業務代碼完全一樣。

MQ 適配 vs 接口適配

MQ 消息體適配接口適配
適配什麼不同 MQ 的欄位名不同服務的方法名和返回值
映射機制映射表 + 反射統一接口 + 各實現類包裝
核心結構MQAdapter.filter + link MapOrderAdapterService 接口 + 兩個實現
共同目標調用方只面對統一接口，差異被隔離在適配器裡

兩條線說的是同一件事：把不兼容的接口通過適配做到統一。差別只在「適配的對象」不同——一個是 MQ 消息體的欄位，一個是 API 的方法簽名。

小結

接口適配的核心 = 定義統一接口 OrderAdapterService + 各實現類把差異邏輯包裝在内部。業務代碼只面對統一接口，不再關心底層用什麼方式查詢。
