適配介面 + 動態代理重構

design-pattern › abstract-factory › abstract-factory-refactor

學習目標：看懂 ICacheAdapter 適配介面 + JDK 動態代理的重構方案，理解「原類零修改接入兩套集群」的實現思路。

重構的核心思路

上一節的痛點是：選擇集群的邏輯和具體操作混在一起。重構的目標很明確——讓 CacheServiceImpl 不改一行代碼，就能接入 EGM 和 IIR 兩套集群。

實現這個目標需要兩步：

  1. 適配：把兩套集群的異名方法統一到一個介面上
  2. 代理：用 JDK 動態代理在運行時把調用轉發到具體集群

這兩步合在一起，就是抽象工廠的一種落地形態。

第一步：定義統一適配介面

先抽出一個 ICacheAdapter 介面，把所有集群都必須支持的操作定義成統一的方法名：

public interface ICacheAdapter {
    String get(String key);
    void set(String key, String value);
    void set(String key, String value, long timeout);
    void del(String key);
}

注意這個介面的方法名和原來的 CacheService 完全一致——業務代碼不需要做任何調整。

第二步：為每套集群寫適配實現

EGM 集群的適配器，把 gain → get、delete → del、setEx → set-with-timeout 映射過來：

public class EGMCacheAdapter implements ICacheAdapter {
    private EGM egm = new EGM();

    public String get(String key) {
        return egm.gain(key);      // gain → get
    }
    public void set(String key, String value) {
        egm.setEx(key, value, 0);  // setEx → set
    }
    public void set(String key, String value, long timeout) {
        egm.setEx(key, value, timeout); // setEx → set-with-timeout
    }
    public void del(String key) {
        egm.delete(key);           // delete → del
    }
}

IIR 集群同理：

public class IIRCacheAdapter implements ICacheAdapter {
    private IIR iir = new IIR();

    public String get(String key) {
        return iir.get(key);       // 方法名一致
    }
    public void set(String key, String value) {
        iir.set(key, value);       // 方法名一致
    }
    public void set(String key, String value, long timeout) {
        iir.setExpire(key, value, timeout); // setExpire → set-with-timeout
    }
    public void del(String key) {
        iir.set(key, null);        // 沒有 delete，用 set(null) 替代
    }
}

兩個適配器做的事一樣：把各自集群的「方言」翻譯成統一的「普通話」。業務方只跟 ICacheAdapter 打交道，不需要知道 EGM 和 IIR 的方法名差異。

第三步：JDK 動態代理連接一切

關鍵來了。我們不直接改 CacheServiceImpl，而是用 JDK 動態代理在運行時「攔截」方法調用，轉發到對應的適配器：

public class JDKProxy {
    public static <T> T getProxy(Class<T> clazz, ICacheAdapter adapter) {
        return (T) Proxy.newProxyInstance(
            clazz.getClassLoader(),
            clazz.getInterfaces(),
            new JDKInvocationHandler(adapter)
        );
    }
}

public class JDKInvocationHandler implements InvocationHandler {
    private ICacheAdapter cacheAdapter;

    public JDKInvocationHandler(ICacheAdapter cacheAdapter) {
        this.cacheAdapter = cacheAdapter;
    }

    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        // 通過方法名反射調用適配器的對應方法
        return MethodUtils.invoke(cacheAdapter, method.getName(), args);
    }
}

使用方式：

// 要用 EGM 集群？
CacheService cacheService = JDKProxy.getProxy(
    CacheServiceImpl.class, new EGMCacheAdapter());

// 要切到 IIR 集群？
CacheService cacheService = JDKProxy.getProxy(
    CacheServiceImpl.class, new IIRCacheAdapter());

// 業務代碼完全不變！
cacheService.set("user_name_01", "小傅哥", 60);
String value = cacheService.get("user_name_01");

重構前後對比

維度ifelse 方案抽象工廠方案
原類 CacheServiceImpl大改：每個方法加 ifelse零修改
方法簽名加了 redisType 參數保持不變
新增第三套集群每個方法加 else if 分支寫一個新適配器類
調用方要傳 type 參數只差傳哪個適配器
測試耦合所有集群每個適配器獨立測試

核心差異：ifelse 方案把「選擇」和「執行」綁在一起，每次調用都要判斷；抽象工廠方案把「選擇」提前到創建代理時一次性決定，之後的調用完全透明。

小結

重構方案的核心是「適配介面 + JDK 動態代理」。適配器抹平了兩套集群的方法名差異，代理類在運行時把調用轉發到對應的適配器。原類零修改，新增集群只需要加一個適配器。這就是抽象工廠「管理一整套兼容實現」的具體落地。下一節我們會總結這個模式的設計原則和選型邊界。
