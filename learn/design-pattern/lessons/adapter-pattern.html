适配器模式：让不兼容的接口变得统一

结构型

这一课的目标

读完之后，你能用适配器把多个不兼容的第三方接口统一成调用方想要的形态，并识别出框架源码中的适配器结构。

场景：营销系统对接多个第三方

你正在开发一个营销/返利系统，需要消费多种 MQ 消息，还要查询订单首单状态。三家的接口长这样：

来源消息体字段名
京东 MQ{"uid":"xxx", "couponId":"..."}uid, couponId
淘宝 MQ{"userId":"xxx", " discountId":"..."}userId, discountId
拼多多 MQ{"memberNo":"xxx", "skuId":"..."}memberNo, skuId

三个接口，三种字段名，三种参数格式。你的业务逻辑只需要一个统一的 RebateInfo 对象。

一坨代码：每个 MQ 一个 Consumer

最直觉的做法：为每种 MQ 写一个 Consumer 类，手写字段映射。

// 每种 MQ 都要手写一遍映射
@Service
public class JDRebateConsumer {
    public RebateInfo onMessage(String json) {
        JSONObject obj = JSON.parseObject(json);
        RebateInfo info = new RebateInfo();
        info.setUserId(obj.getString("uid"));        // 注意：京东用 "uid"
        info.setActivityId(obj.getString("couponId")); // 注意：京东用 "couponId"
        return info;
    }
}

@Service
public class TaobaoRebateConsumer {
    public RebateInfo onMessage(String json) {
        JSONObject obj = JSON.parseObject(json);
        RebateInfo info = new RebateInfo();
        info.setUserId(obj.getString("userId"));       // 注意：淘宝用 "userId"
        info.setActivityId(obj.getString("discountId")); // 注意：淘宝用 "discountId"
        return info;
    }
}

@Service
public class PddRebateConsumer {
    public RebateInfo onMessage(String json) {
        JSONObject obj = JSON.parseObject(json);
        RebateInfo info = new RebateInfo();
        info.setUserId(obj.getString("memberNo"));     // 注意：拼多多用 "memberNo"
        info.setActivityId(obj.getString("skuId"));     // 注意：拼多多用 "skuId"
        return info;
    }
}

问题很明显：每来一个新的 MQ 来源，就得新建一个 Consumer 类，手写一遍映射逻辑。5 个、10 个、20 个……代码膨胀得很快。

适配器重构：配置驱动的统一映射

核心思路：把字段映射关系从代码里抽出来，变成可配置的。

1 定义统一的消息体 
/**
 * 统一返利消息体 — 所有 MQ 消息最终都适配成这个形态
 */
@Data
public class RebateInfo {
    private String userId;      // 统一用 userId
    private String activityId;  // 统一用 activityId
    private String bizId;       // 业务ID
}
2 用配置 + 反射做通用适配器 
/**
 * MQ 适配器 — 通过配置映射字段名，一个类处理所有 MQ
 * 

 * "link" 里定义映射关系：
 *   key = 统一字段名（RebateInfo 的属性名）
 *   value = 原始 MQ 里的字段名
 */
public class MQAdapter {

    /**
     * 把任意 MQ JSON 适配成 RebateInfo
     *
     * @param json   原始 MQ 消息
     * @param link   字段映射配置 {"userId": "uid", "activityId": "couponId"}
     * @return 统一消息体
     */
    public static RebateInfo filter(String json, Map<String, String> link) {
        RebateInfo info = new RebateInfo();
        JSONObject obj = JSON.parseObject(json);

        // 遍历映射配置，用反射设值
        link.forEach((targetField, sourceField) -> {
            String value = obj.getString(sourceField);
            try {
                // 拿到 RebateInfo 的 setter 方法
                Method setter = RebateInfo.class.getMethod(
                    "set" + capitalize(targetField), String.class
                );
                setter.invoke(info, value);
            } catch (Exception e) {
                throw new RuntimeException("映射失败: " + targetField, e);
            }
        });

        return info;
    }

    private static String capitalize(String s) {
        return s.substring(0, 1).toUpperCase() + s.substring(1);
    }
}
3 用配置声明每种 MQ 的映射关系 
// 每种 MQ 只需要声明映射关系，不用手写 Consumer 类
Map<String, String> jdLink = new HashMap<>() {{
    put("userId", "uid");           // RebateInfo.userId ← JD 的 "uid"
    put("activityId", "couponId");  // RebateInfo.activityId ← JD 的 "couponId"
}};

Map<String, String> taobaoLink = new HashMap<>() {{
    put("userId", "userId");        // RebateInfo.userId ← 淘宝的 "userId"
    put("activityId", "discountId"); // RebateInfo.activityId ← 淘宝的 "discountId"
}};

Map<String, String> pddLink = new HashMap<>() {{
    put("userId", "memberNo");      // RebateInfo.userId ← 拼多多的 "memberNo"
    put("activityId", "skuId");     // RebateInfo.activityId ← 拼多多的 "skuId"
}};

// 一行搞定
RebateInfo jdInfo = MQAdapter.filter(jdJson, jdLink);
RebateInfo tbInfo = MQAdapter.filter(taobaoJson, taobaoLink);
RebateInfo pddInfo = MQAdapter.filter(pddJson, pddLink);

适配器的四个角色

角色在本例中职责
目标接口 Target RebateInfo 调用方期望的统一形态
适配者 Adaptee 京东/淘宝/拼多多的原始 MQ 已有的、不兼容的接口
适配器 Adapter MQAdapter.filter() 翻译层：把 Adaptee 的输出转成 Target
客户端 Client 业务 Service 只和 RebateInfo 打交道

订单首单判断的适配

同一个系统里，查询"是否首单"也需要适配——内部订单服务和外部 POP 接口的判断逻辑完全不同：

// 统一接口
public interface OrderAdapterService {
    boolean isFirst(String uId);
}

// 内部服务：查数据库订单数量
@Service
public class InsideOrderService implements OrderAdapterService {
    @Override
    public boolean isFirst(String uId) {
        int count = orderDao.queryOrderCount(uId);
        return count <= 1;
    }
}

// 外部 POP 服务：直接返回 boolean
@Service
public class POPOrderAdapterServiceImpl implements OrderAdapterService {
    @Override
    public boolean isFirst(String uId) {
        return popApi.queryFirstOrder(uId); // 外部接口直接返回 true/false
    }
}

// 业务方只认 OrderAdapterService，不关心背后是哪个实现
OrderAdapterService service = orderAdapterFactory.getService(source);
boolean first = service.isFirst(userId);

框架中的适配器

🔍 Spring 中的适配器
Spring 框架里大量使用适配器：UserCredentialsDataSourceAdapter（适配数据源认证）、HandlerAdapter（适配不同类型的 Handler 处理器）、JpaDialectAdapter（适配 JPA 方言）。当你看到 *Adapter 后缀的类名时，大概率就是在做接口翻译。

关键取舍

优点代价
不修改原始代码，符合开闭原则 增加了一个中间层，调试时多一层跳转
新增第三方只需加映射配置，不用新建类 配置驱动的反射有轻微性能开销
业务代码只认统一接口，干净 过度使用会导致适配器类爆炸

本课小结

  1. 适配器解决的问题：接口不兼容（A 的输出不是 B 能吃的格式）
  2. 核心思路：加一个翻译层，把不兼容的接口变成调用方期望的统一形态
  3. 四个角色：目标接口（RebateInfo）、适配者（各 MQ）、适配器（MQAdapter）、客户端（业务 Service）
  4. 框架中的识别信号：看到 *Adapter 后缀的类名
  5. 适配器不修改原始代码，只在外面加一层
