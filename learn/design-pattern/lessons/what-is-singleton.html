什麼是單例模式？

design-pattern › singleton › what-is-singleton

學習目標：能說清單例模式的本質——全局唯一實例加上全局訪問點，並用資料庫連線池、Spring Bean 等場景理解它解決什麼問題。

一個你每天都在用的模式

你在 Spring 裡寫過 @Service 或 @Component 吧？這些 Bean 默認就是單例的——整個應用裡只有一個實例，所有 Controller 注入的都是同一個對象。你可能從沒想過「為什麼只有一個」，但這個「只有一個」正是單例模式的核心。

單例模式（Singleton Pattern）是創建型模式中最直覺的一個，它的意圖一句話就能說清：保證一個類只有一個實例，並提供一個全局訪問點。

為什麼需要「只有一個」？

有些東西如果被反覆創建，會出大問題。舉三個你一定碰過的場景：

資料庫連線池

每次查詢都新建一個資料庫連線？TCP 三次握手、認證、釋放……一個簡單的 SELECT 可能比你的業務邏輯還慢。連線池的核心思路是：維護一组已建立的連線，用完歸還，而不是用完銷毀。但如果連線池被 new 了十個，每個池子各管各的連線，那連線總數就會失控——資料庫可能直接拒絕連接。

單例解法：整個應用只有一個連線池實例，所有模塊共用。連線數可控，資源不浪費。

Spring Bean（默認單例）

Spring 容器裡的 Bean 默認作用域就是 singleton。一個 UserService Bean 被 Controller A 和 Controller B 同時注入，它們拿到的是同一個實例。如果每次注入都 new 一個新的，那 Bean 裡緩存的數據、維持的狀態就會散落各處，完全無法共享。

全局配置讀取器

系統啟動時從配置中心拉一份配置，解析成對象放在內存裡。如果每次讀配置都重新拉一次、重新解析一次，不僅浪費網路 IO，還可能因為配置中心的暫時不一致導致不同模塊讀到不同版本的配置。

單例解決的本質問題

把上面三個場景抽象一下，單例模式解決的問題是：

  • 資源浪費：某些對象的創建成本很高（資料庫連線、大文件解析、遠端調用），反覆創建是不必要的開銷
  • 狀態不一致：如果多個實例各自維持狀態，誰是「真相」？單例讓所有使用者看到同一個狀態
  • 命名空間污染：全局變量太散，單例提供一個受控的「全局訪問點」，比到处散落的 static 變量更乾淨

單例 vs 靜態類：初識邊界

很多人第一次接觸單例時會問：「用 static 不就行了？」確實，一個全是 static 方法的工具類（比如 Math、Arrays）也能提供全局訪問，而且更簡單。但它們有本質區別：

維度靜態類單例模式
實例化不需要實例化，類加載即存在需要實例化，但只允許一次
狀態通常是無狀態的工具方法可以維持有狀態的實例
繼承/多態不支持（static 方法不能被重寫）可以被繼承、實現接口
可測試性難以 mock可以通過接口注入 mock

一句話記法：「不需要狀態、不需要繼承、純工具」用靜態類；「需要狀態、需要繼承、需要多態」用單例。後面的步驟會看到，七種單例寫法之間也有類似的取捨——只是維度換成了「懶不懶加載」和「線不線程安全」。

小結

單例模式的本質是兩個約束：只有一個實例＋一個全局訪問點。它解決的是資源浪費、狀態不一致、命名空間散亂這三類問題。資料庫連線池、Spring Bean、全局配置是最常見的三個場景。下一課我們會看到，光是「怎麼保證只有一個」這件事，Java 就能給出七種截然不同的答案。
