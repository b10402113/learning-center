创建型模式对比

Node: builder-prototype · Step 5/5

学习目标

能对比 Builder（分步组装）、Prototype（克隆模板）、Factory（类型分发）三种创建型模式的适用场景与取舍，在实际场景中做出选择。

快速回顾

前面四步分别学了 Builder 和 Prototype 的核心机制。在对比之前，先把三种模式的一句话定位摆出来：

模式 一句话定位 解决什么问题
Builder 分步组装复杂对象 构造参数多、组合方式常变，不想写一堆构造函数重载
Prototype 克隆已有模板对象 对象初始化涉及 DB/RPC/大量计算，重复创建代价高
Factory 定义创建接口，让子类决定实例化哪个类 有多种不兼容的实现，需要按类型分发创建逻辑

维度对比

对比维度 Builder Prototype Factory
核心动作 分步 set，最后 build clone 一个已有对象 调用工厂方法，返回子类实例
对象复杂度 高（多部件、多配置项） 中到高（初始化成本高） 不限，重点在类型选择
创建开销 每次构造，但 Builder 可复用 克隆快，但深拷贝集合有坑 每次 new，开销取决于具体实现
变化维度 部件组合方式常变 模板少变、克隆多 新增产品类型时扩展
扩展方式 加 set 方法 加新的原型对象 加新的工厂子类
典型坑 遗漏必填参数（编译期可防） 浅拷贝导致共享可变状态 类爆炸（子类太多）

场景决策规则：看到 X，想到 Y

Builder
看到：构造函数参数超过 4 个，且组合方式频繁变化
→ 用 Builder。装修套餐就是典型——基础材料稳定，但组合方式每次不同。
Builder
看到：对象需要分步构建，每一步都有可选配置
→ 用 Builder。Fluent API 让调用方像写配置一样直观。
Prototype
看到：对象初始化要查 DB、调 RPC、或做大量计算，但使用频率低
→ 用 Prototype。考卷生成就是例子——题库查一次，模板克隆多次。
Prototype
看到：需要大量相似对象，只有少数字段不同
→ 用 Prototype。从模板 clone 再微调，比从头构建省得多。
Factory
看到：多个不兼容的第三方接口，需要按类型分发调用
→ 用 Factory。营销抽奖对接三家不兼容支付接口就是这种情况。
Factory
看到：if-else 或 switch 根据类型 new 不同的子类
→ 用 Factory。把 new 的决定封装到工厂方法里，调用方不再关心具体类。

反模式：强行套用

不要为了用模式而用模式。如果对象只有一个构造函数参数、初始化不涉及外部调用、也没有多种实现需要分发——那就老老实实 new。过度设计比没有设计更难维护。

书中反复强调：选择模式要看场景，不要硬套。框架之所以强大，是因为它把多种模式组合在一起使用，而不是只靠某一个。

框架如何组合多种模式

Spring Boot 就是一个活教材。它同时用了 Factory（BeanFactory 按类型创建 Bean）、Builder（SpringApplicationBuilder 链式配置启动参数）、Prototype（@Scope("prototype") 每次请求创建新实例）——三种创建型模式各司其职，共同支撑整个框架的对象创建体系。

关键不是选哪个模式最"高级"，而是搞清楚每种模式最适合解决哪一类问题，然后在合适的地方用合适的模式。

本步小结

Builder、Prototype、Factory 三种创建型模式解决的是不同维度的问题：Builder 管"怎么组装"，Prototype 管"怎么复用"，Factory 管"由谁决定"。在实际项目中，它们经常组合出现——Spring Bean 创建走 Factory，启动配置走 Builder，Prototype scope 走 Prototype。能根据场景快速判断该用哪种，比死记类图有用得多。

场景自测

Q1. 你的服务要对接三家不兼容的支付渠道，每家的 SDK 接口完全不同。下单时根据用户选择的支付方式调用对应的 SDK。应该用哪个模式？

  • Builder — 把支付参数逐步 set 进去
  • Factory — 定义统一的支付接口，让子类决定用哪个 SDK
  • Prototype — 克隆一个支付模板对象

Q2. 你要生成一批考试试卷，每份试卷从题库查 50 道题，但题库查询很慢（2 秒/次）。试卷之间只有题目顺序和分值分布不同。应该用哪个模式？

  • Builder — 分步组装试卷的各个部分
  • Factory — 按试卷类型创建不同的试卷子类
  • Prototype — 查一次题库生成模板试卷，后续克隆模板再微调

Q3. 你在写一个 HTTP 请求构建器，请求有 URL、Method、Headers、Body、Timeout、Retry 等参数，其中 Headers 和 Body 是可选的，调用方经常只设其中几个。应该用哪个模式？

  • Builder — Fluent API 链式调用，只 set 需要的参数
  • Prototype — 克隆一个默认请求模板
  • Factory — 按请求类型创建不同的子类
