外觀模式的適用邊界與取捨

design-pattern › facade › facade-tradeoffs

學習目標：能說出外觀模式的適用邊界——何時用、何時不該用、與中介者/適配器的區別。

外觀模式的收益

回顧一下我們做了什麼：把散落在每個接口方法裡的白名單 ifelse，抽成了一個 SpringBoot starter 中間件。業務方加一個注解就生效，不用改一行業務代碼。

外觀模式的收益可以總結為三點：

收益怎麼體現
降低複雜度調用方只面對一個簡單入口，不用理解子系統內部細節
提高復用性白名單中間件可以被任何 SpringBoot 工程引入，不用每個項目重寫
隔離變化白名單邏輯改了只改中間件，業務代碼完全不受影響

什麼時候該用

外觀模式不是萬能藥。它的適用條件很明確：

  • 跨多個接口的共性需求：白名單、簽名校驗、限流、日誌審計——這些「所有接口都要做的事」
  • 子系統內部複雜，調用方只想簡單用：比如 ORM 框架把 JDBC 連接、SQL 解析、結果映射包裝成一個 selectOne
  • 需要統一治理：一個地方改，所有接口都生效

一句話判斷標準：如果你發現同一段邏輯在多個地方重複出現，而且它跟核心業務無關，就該考慮用外觀模式抽成中間件。

什麼時候不該用

反過來，以下場景不適合外觀模式：

  • 只有一兩個接口：為了兩個方法抽一個中間件，過度設計
  • 業務邏輯本身就需要在方法內部：外觀模式包裝的是「橫切關注點」，不是業務邏輯本身
  • 子系統很簡單：如果子系統本身就不複雜，加一層包裝反而多了一層間接調用
記住：設計模式是工具，不是信仰。「為用而用」比「不用」更糟糕——它會讓結構更複雜、更難維護。

外觀 vs 中介者 vs 適配器：三兄弟怎麼分

這三個模式都涉及「中間加一層」，但意圖完全不同：

模式核心意圖類比典型場景
外觀（Facade） 簡化調用方對子系統的訪問 大堂經理：你不用找各個部門，找我就行 白名單中間件、ORM 框架、SDK 封裝
中介者（Mediator） 集中協調多個對象之間的交互 塔台：飛機之間不直接通信，都通過我協調 ORM 框架（協調連接、SQL、結果映射）、聊天室
適配器（Adapter） 讓不兼容的接口能一起工作 轉換插頭：歐標插頭轉成國標 多 MQ 消息體統一、舊系統對接新接口

關鍵區分：

  • 外觀是「從外面看，子系統很複雜，我幫你簡化」——重點在簡化調用
  • 中介者是「多個對象之間交互太亂，我來集中協調」——重點在解耦交互
  • 適配器是「接口不匹配，我來轉換一下」——重點在接口轉換

實際項目中，這三個模式經常組合使用。比如 MyBatis 框架：SqlSession 是外觀（簡化 JDBC 調用），SqlSessionFactoryBuilder 是中介者（協調配置解析、連接建立、Session 創建），而 ResultMapper 是適配器（把 ResultSet 轉成 Java 對象）。

小結

外觀模式解決的是「調用方不想面對子系統複雜度」的問題。它的判斷標準很簡單：同一段橫切邏輯在多個地方重複 → 抽成統一包裝層。但不要為了兩個方法硬造一層——過度設計比不用更糟。和中介者、適配器的區別記住一個詞就够了：外觀是「簡化」，中介者是「協調」，適配器是「轉換」。
