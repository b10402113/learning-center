配置回滾場景：從一坨代碼到模式重構

design-pattern › memento › memento-scenario

學習目標：用系統上線配置回滾的真實場景，體驗「一坨代碼 → 備忘錄模式重構」的完整過程，理解重構前後結構差異。

場景：系統上線，配置改錯了

你在一個大廠做後端，系統要上線了。上線前要改配置文件——IP 地址、端口號、連接池大小，改完部署。結果配置改錯了，線上服務起不來。你需要緊急把配置退回上一次正常的版本。

這個需求聽起來很簡單：記錄每次改過的配置，需要的時候拿回來就行。但怎麼「記錄」和「拿回來」，正是備忘錄模式要解決的問題。

場景細節

大廠的配置管理通常要求：

  • 線上與本地隔離：配置文件不跟代碼一起提交到 Git，而是存在線上配置中心
  • 每次變更都記錄：版本號、時間、MD5、內容、操作人，五要素缺一不可
  • 緊急回滾：線上出問題時，能一鍵退回到某個歷史版本
  • 系統隨配置一起回滾：回滾不只是改文件，有時還要重啟服務讓新配置生效

我們聚焦在「記錄版本 + 支持回滾」這件事上。每次配置變更，我們把當前的完整配置狀態存一份快照；需要回滾時，從快照列表裡取出某個版本的配置，覆蓋當前配置。

一把梭實現：把所有邏輯塞進一個方法

最直接的寫法是怎樣的？在方法裡順序處理：存配置、查歷史、回滾配置。

public class ConfigManager {
    private ConfigFile currentConfig;
    private List<ConfigFile> history = new ArrayList<>();

    // 保存配置
    public void save(ConfigFile config) {
        currentConfig = config;
        history.add(config);
    }

    // 回滾到上一個版本
    public ConfigFile undo() {
        if (history.size() > 1) {
            history.remove(history.size() - 1);
            return history.get(history.size() - 1);
        }
        return currentConfig;
    }

    // 按版本號取
    public ConfigFile getVersion(String versionNo) {
        for (ConfigFile c : history) {
            if (versionNo.equals(c.getVersionNo())) return c;
        }
        return null;
    }
}
壞味道：ConfigManager 同時做了三件事——管理當前配置、管理歷史列表、處理回滾邏輯。如果未來要加 redo（前進）、按時間範圍查詢、導出歷史，全都要往這個類裡塞。

幾個問題：

  • 職責混雜：存配置、查歷史、回滾，三件事都混在一個方法裡
  • 回滾邏輯暴露：undo 方法直接操作 list，如果換一種存儲結構（比如 Map），undo 邏輯要重寫
  • 配置物件被直接暴露：history 直接存 ConfigFile，ConfigFile 的內部結構完全暴露在外面
  • 難以擴展：加 redo？加版本合併？每加一個功能就要改 ConfigManager

備忘錄模式重構：四個角色各司其職

備忘錄模式把這件事拆成四個角色：

角色職責類比
ConfigFile被保存的狀態（原物件）遊戲角色
ConfigMemento快照（備忘錄）存檔檔
ConfigOriginator生成快照、還原快照（記錄者）遊戲存檔系統
Admin保存多個快照、提供 undo/redo/get（管理者）存檔管理器

重構後的結構：

  • ConfigFile 不動：它還是那個配置類，不暴露任何內部狀態
  • ConfigMemento 包裝 ConfigFile：備忘錄把原物件包起來，作為快照的載體
  • ConfigOriginator 負責存檔和讀檔：saveMemento() 把當前狀態包成快照交出去；getMemento(memento) 把快照裡的狀態還原回來
  • Admin 負責管理歷史：用 List + Map 存多個快照，提供 undo（回滾）、redo（前進）、get（按版本取）

對比一把梭版本：

  • 一把梭：ConfigManager 同時管配置、管歷史、管回滾，三件事混在一起
  • 重構後：ConfigFile 管狀態、ConfigMemento 管快照、ConfigOriginator 管存取、Admin 管歷史——每個類只做一件事

測試驗證

測試類連續保存四份配置（1000001 到 1000004，內容各不相同），然後執行：

  1. undo 一次 → 回到 1000003
  2. 再 undo 一次 → 回到 1000002
  3. redo 一次 → 前進到 1000003
  4. get("1000002") → 定向取回 1000002

每一步都返回正確的 ConfigFile 物件，exit code 0。回滾、前進、定向取都符合預期。

小結

配置回滾場景展示了一個典型的備忘錄需求：保存歷史狀態、支持回滾和恢復。一把梭的寫法把所有邏輯塞在一起，難以維護和擴展；備忘錄模式把這件事拆成四個角色，每個角色只做一件事。下一課我們會詳細拆解這四個角色的分工邏輯。
