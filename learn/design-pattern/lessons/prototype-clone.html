原型模式与 clone 机制

Node: builder-prototype · Step 3/5

学习目标

理解原型模式的动机和 Cloneable 接口的实现机制，能用 clone() 克隆模板对象避免重复构建开销。

🎯 场景：在线考试系统

你需要为每个考生生成试卷。试卷包含选择题列表和简答题列表，数据来自题库数据库。每个考生拿到的试卷内容相同，但题目和选项的顺序需要打乱。

如果每次有新考生来考试，你都从头查数据库、组装题目、构建完整的试卷对象——200 个考生就是 200 次重复构建。

问题：每次都从零构建

最直觉的做法是在 Controller 里为每个考生构建一份试卷：

❌ 每个考生都重复构建
@RestController
public class QuestionBankController {

    @Autowired
    private QuestionBankMapper questionBankMapper;

    // 每次调用都查库、组装 → 200考生 = 200次重复构建
    @GetMapping("/exam/paper")
    public QuestionBank generatePaper(String candidateId) {
        // 1. 从数据库查出选择题列表
        List<ChoiceQuestion> choiceQuestions =
            questionBankMapper.selectChoiceQuestions();
        // 2. 从数据库查出简答题列表
        List<AnswerQuestion> answerQuestions =
            questionBankMapper.selectAnswerQuestions();
        // 3. 组装试卷对象
        QuestionBank paper = new QuestionBank();
        paper.setChoiceQuestions(choiceQuestions);
        paper.setAnswerQuestions(answerQuestions);
        // 4. 返回（这里甚至连 shuffle 都没做）
        return paper;
    }
}

这段代码有两个问题：

  • 性能浪费 — 数据库查询、对象组装对每个考生重复执行，而结果完全相同
  • 缺少打乱 — 所有考生拿到完全一样的题目和选项顺序，考试没有意义

重构：构建一次，克隆 N 次

原型模式的核心思想：把一个已经构建好的对象当模板，后续用 clone() 快速复制，而不是重新构建。

就像 Ctrl+C / Ctrl+V。你做了一份完美的试卷模板，然后每个考生进来，Ctrl+V 一份就行了——不用每次都重新写一遍。

具体实现：

✅ QuestionBank 实现 Cloneable
public class QuestionBank implements Cloneable {

    private List<ChoiceQuestion> choiceQuestions;
    private List<AnswerQuestion> answerQuestions;

    // getter / setter 省略

    @Override
    public QuestionBank clone() {
        try {
            return (QuestionBank) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new RuntimeException(e);
        }
    }
}
✅ Controller：模板构建一次，克隆 N 次
@RestController
public class QuestionBankController {

    @Autowired
    private QuestionBankMapper questionBankMapper;

    // 只构建一次的模板
    private QuestionBank template;

    @PostConstruct
    public void init() {
        // 启动时构建模板（或懒加载）
        List<ChoiceQuestion> choices =
            questionBankMapper.selectChoiceQuestions();
        List<AnswerQuestion> answers =
            questionBankMapper.selectAnswerQuestions();
        template = new QuestionBank();
        template.setChoiceQuestions(choices);
        template.setAnswerQuestions(answers);
    }

    @GetMapping("/exam/paper")
    public QuestionBank generatePaper(String candidateId) {
        // 克隆模板，打乱顺序，返回给考生
        QuestionBank paper = template.clone();
        TopicRandomUtil.randomChoiceQuestions(
            paper.getChoiceQuestions());
        TopicRandomUtil.randomChoiceItems(
            paper.getChoiceQuestions());
        TopicRandomUtil.randomAnswerQuestions(
            paper.getAnswerQuestions());
        return paper;
    }
}
关键对比：数据库查询只执行一次（@PostConstruct），每个考生进来只调用 clone() + shuffle。构建开销从 O(N) 降到 O(1) 次构建 + O(N) 次克隆（克隆比从头构建快得多）。

Cloneable 接口机制

Java 的 Object.clone() 是一个 native 方法，它执行的是浅拷贝（shallow copy）。而 Cloneable 是一个标记接口（marker interface）——它没有任何方法，只是告诉 JVM："这个类允许被 clone"。

你需要做的

  • 类实现 Cloneable
  • 重写 clone() 方法
  • 调用 super.clone()

clone() 做了什么

  • 逐字段复制原始值（int、boolean 等）
  • 引用类型只复制引用（浅拷贝）
  • 不调用构造函数
浅拷贝陷阱：如果 QuestionBank 内部的 List 字段没有在 clone() 中深拷贝，那么克隆出来的对象和原对象共享同一个 List。对克隆体调用 shuffle()，模板也被打乱了。深拷贝的处理细节在下一步详细讲解。

原型 vs Builder vs 工厂：什么时候用谁？

场景 首选模式 原因
对象构建步骤固定，参数组合多 Builder 流式 API 逐步设置，可读性好
每次构建都需要查库/RPC，开销大 Prototype 构建一次，克隆 N 次，省开销
根据类型创建不同实现类 工厂方法 封装创建逻辑，屏蔽具体类型

Prototype 模式的典型场景：

  • 在线考试、在线测评——每次构建开销大，内容相同，顺序打乱
  • 游戏中的技能模板——一套技能定义，多个实例各自独立冷却
  • 文档/报表模板——格式复杂，构建慢，克隆后填充不同数据

不要过度使用

Prototype 使用频率低。在实际项目中，你遇到的创建型问题大部分用 Builder 或工厂方法就能解决。Prototype 的适用面相对窄——只有当"构建成本高且多次构建结果相同"时，它才有明显优势。盲目到处 clone 会导致代码难以理解和维护。

判断标准：

  • 构建过程确实慢（涉及 I/O、数据库、复杂计算）？→ 考虑 Prototype
  • 构建过程很快（纯内存操作）？→ 用 Builder 或工厂方法就好
  • 克隆后需要大量修改？→ 构建可能更清晰，克隆反而增加复杂度

自我检测

Q1. 为什么在线考试系统适合用原型模式？

  • 因为试卷需要继承父类
  • 因为每个考生的试卷内容不同
  • 因为试卷构建涉及数据库查询，开销大，但所有考生拿到的内容相同
  • 因为需要使用抽象工厂创建试卷

Q2. Object.clone() 默认执行的是什么拷贝？

  • 深拷贝——所有字段都会递归复制
  • 浅拷贝——引用类型只复制引用，不复制对象
  • 序列化拷贝——通过 byte 数组重建对象
  • 不执行拷贝——clone() 和 new 完全等价

Q3. 下面哪种场景不适合用 Prototype 模式？

  • 一个简单的 POJO 对象，new 出来只需要设置两个字段
  • 每次构建需要查数据库的复杂试卷对象
  • 需要为多个用户生成相同结构但顺序打乱的报告
  • 从远程 RPC 获取的配置模板需要分发给多个服务
