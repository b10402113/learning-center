认识"一坨代码"的坏味道

design-pattern · code-smell

学习目标

能在一堆代码里认出按 type 字段堆叠的 ifelse/switch 分发，说出它为什么每加一个需求就越来越难维护。

一个你一定见过的形状

打开任何一个"做了一段时间"的业务 Controller 或 Service，你大概率会看到这种代码：

public AwardRes awardToUser(AwardReq req) { AwardRes res = new AwardRes(); if (req.getAwardType() == 1) { // 优惠券：调优惠券服务，拼参数，判结果 CouponResult cr = couponService.sendCoupon(...); if (cr.isSuccess()) { res.setCode("0000"); res.setInfo("发放成功"); } else { res.setCode("0001"); res.setInfo(cr.getInfo()); } } else if (req.getAwardType() == 2) { // 实物商品：调发货服务，拼完全不同的参数 Boolean ok = goodsService.deliverGoods(...); res.setCode(ok ? "0000" : "0001"); } else if (req.getAwardType() == 3) { // 兑换卡：又一套完全不同的调用方式 cardService.grantToken(...); res.setCode("0000"); } // 还没算每种类型内部的异常处理... return res; }

这段代码能跑。测试也能过。但它有病——一种叫做"坏味道"（code smell）的病。

这种形状的坏味道在哪里

把这段代码放在增长的业务里，问题一个一个冒出来：

  • 每加一个产品类型，就要改这个方法。开闭原则（对扩展开放、对修改关闭）直接违反。你不是在"加"代码，你是在"改"已有代码——而已有代码已经跑着、被别人依赖着。
  • 方法越来越长。三种产品各写一遍参数拼装、结果映射、异常处理，加到十种就是几百行。人的工作记忆只有 7±2 项，超过这个长度你读方法时已经忘了开头在干什么。
  • 产品逻辑全部耦合在一个方法里。优惠券的参数怎么拼、发货的异常怎么处理、兑换卡的返回值怎么映射——三种完全不同的业务逻辑挤在一起，改一个怕影响另一个。
  • 测试没法隔离。想单独测优惠券逻辑？这个方法绑着另外两种。Mock 成本高，覆盖难。

识别坏味道的模式

这种"一坨代码"有一个可识别的形状：

按一个 type/dispatch 字段，用 if/switch 把不同类型分发到不同逻辑块。每个逻辑块各自拼参数、调服务、映射返回值，但它们全挤在同一个方法或同一个类里。

它不只出现在奖品发放。你的代码里可能也有：

// 支付渠道分发 if (channelType == 1) { /* 微信支付 */ } else if (channelType == 2) { /* 支付宝 */ } // 消息类型分发 if (msgType.equals("ORDER")) { /* 订单消息处理 */ } else if (msgType.equals("PAYMENT")) { /* 支付消息处理 */ } // 审核状态分发 switch (status) { case EDITING: /* ... */ case PENDING: /* ... */ case APPROVED: /* ... */ }

形状一模一样：一个 type 字段，一堆 if/switch，每个分支一套独立逻辑。

为什么"能跑"不够

你可能觉得"反正现在只有三种，先这样呗"。但业务增长时这段代码的命运几乎是确定的：

  1. 3 个分支——还行，能读
  2. 5 个分支——开始觉得长，但还能忍
  3. 10 个分支——每次加需求都心惊胆战，改一个分支怕影响其他的
  4. 20 个分支——没人敢碰，重构成本已经高到不敢动

这就是"开发一时爽，重构火葬场"。代码不是一次性写的，它是要持续演化的。坏味道的真正代价不是今天的维护成本，而是未来每次变更的摩擦力。

坏味道不是 bug，它不会让你的程序崩溃。它是一种信号——告诉你这段代码在增长场景下会越来越痛苦。认出这个信号，就是学设计模式的起点。

本节要点回顾

  • "一坨代码"的典型形状：按 type 字段 if/switch 分发，每个分支一套独立逻辑
  • 四个坏味道：违反开闭、方法膨胀、逻辑耦合、测试困难
  • 这种形状在支付、消息、审核、奖品等场景反复出现
  • 坏味道不是 bug，是增长场景下的维护摩擦力信号
  • 认出坏味道 = 学设计模式的起点
