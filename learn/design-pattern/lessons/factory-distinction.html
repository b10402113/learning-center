工厂方法 vs 抽象工厂——辨析与取舍

工厂方法与抽象工厂

学习目标

区分工厂方法（单产品层级）和抽象工厂（产品族），讲清各自的适用场景和取舍。

一句话区分

工厂方法解决的是"一类东西有多个品种"——你只有一个接口（ICommodity），需要决定创建哪个实现。

抽象工厂解决的是"多个相关接口各自有多个实现"——你面对的是一整套接口（ICacheAdapter 的 get/set/del），需要切换整套实现。

结构对比

维度 工厂方法 抽象工厂
产品数量 一个接口，多个实现 多个相关接口，各自有多个实现
工厂职责 创建一个具体产品 创建一整套产品族
典型场景 优惠券/商品/兑换卡——都是"奖品" EGM/IIR 集群——get/set/del 整套缓存操作
新增产品的代价 加一个实现类 + 改工厂一行 加一个适配器类 + 改代理配置
复杂度 低——结构简单，容易理解 中——涉及适配器、代理、多接口协调
核心原则 开闭原则 + 单一职责 依赖倒置 + 开闭 + 解耦

决策树：什么时候用哪个？

工厂选择决策树

1
你要替换的是一种东西，还是一整套东西？ → 一种东西 → 工厂方法
2
如果是一整套，这些接口的方法名是否一致？ → 方法名一致 → 可能直接用工厂方法 + 策略模式就够了
3
方法名不一致，需要适配？ → 抽象工厂（适配器 + 动态代理）
4
已有代码不能修改，但需要切换底层实现？ → 抽象工厂（代理路由，零侵入）

真实工作中的判断

回到你的工作经验——一个 Controller/service 对接多个第三方集成，各家接口入参返回形态都不一样：

场景 用什么 理由
优惠券/商品/兑换卡，都是"奖品" 工厂方法 一个接口（ICommodity），多个实现
单机 Redis 换成 EGM/IIR 集群 抽象工厂 一整套 get/set/del 接口要切换，方法名还不一样
支付渠道：微信/支付宝，都是"支付" 工厂方法 一个接口（IPay），多个实现
数据库从 MySQL 换成 PostgreSQL 抽象工厂 连接/查询/事务一整套要切换，JDBC 已经帮你做了适配

取舍：不是越高级越好

常见误区

很多人觉得抽象工厂比工厂方法"高级"，所以什么都用抽象工厂。实际上：

  • 如果只替换一种产品，工厂方法就够了——简单、清晰、好维护
  • 抽象工厂的适配器 + 代理增加了间接层，调试时要多跳一层
  • 过度使用会导致"为模式而模式"——明明两行 ifelse 能搞定的事，非要搞出一套代理体系
选择标准：看你的问题到底是"一种东西有多个品种"还是"一整套东西需要切换"。前者用工厂方法，后者用抽象工厂。不要为了用模式而用模式。

总结：两个模式的定位

类比：工厂方法像是换灯泡——灯座不变，你换不同瓦数/色温的灯泡。抽象工厂像是换整套照明系统——灯座、开关、线路、光源全换了，但墙上的开关面板还是那个面板。

掌握了这两个模式的区别，你就拿到了面对"创建型问题"时的判断力：先看问题的规模——是一种东西还是一整套东西——再选工具。
