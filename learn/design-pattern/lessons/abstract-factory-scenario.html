Redis 雙集群升級場景

design-pattern › abstract-factory › abstract-factory-scenario

學習目標：理解 Redis 單機升級為雙集群的業務場景，看清「類型欄位 + ifelse」壞味道的痛點，為重構做鋪墊。

業務背景：從單機到集群

系統早期 QPS 低、並發小，一台 Redis 機器綽綽有餘。你和團隊用 RedisUtils 這個工具類封裝了所有 Redis 操作，各業務系統都依賴它：

public class RedisUtils {
    public String get(String key) { ... }
    public void set(String key, String value) { ... }
    public void set(String key, String value, long timeout) { ... }
    public void del(String key) { ... }
}

簡單、乾淨、夠用。業務跑了一年多，沒出過問題。

但隨著用戶量暴漲，單機扛不住了。架構組決定升級為 Redis 集群，而且不是一套——是兩套：EGM 集群和 IIR 集群。原因是：一套集群做主、一套做備，災備切換時需要無感切到另一套。

問題來了：兩套集群的方法名不一樣

EGM 集群的方法長這樣：

public class EGM {
    public String gain(String key) { ... }
    public void delete(String key) { ... }
    public void setEx(String key, String value, long timeout) { ... }
}

IIR 集群的方法長這樣：

public class IIR {
    public String get(String key) { ... }
    public void set(String key, String value) { ... }
    public void setExpire(String key, String value, long timeout) { ... }
}

注意到了嗎？做的事完全一樣——get、set、set-with-timeout、del——但方法名各異。就像你 mac 用 Finder、我用資源管理器，做一樣的事但操作方式不同。

而你的業務系統已經寫死了 RedisUtils.get()、RedisUtils.set()……數十個服務都依賴這些方法名。你不可能把所有調用方都改一遍——那等於停擺整個系統。

第一反應：加個 type 參數走 ifelse

最直覺的做法是在 CacheService 接口裡加一個 redisType 參數，然後在實現類裡用 if 判斷走哪套集群：

public interface CacheService {
    String get(String key, int redisType);
    void set(String key, String value, int redisType);
    void set(String key, String value, long timeout, int redisType);
    void del(String key, int redisType);
}

public class CacheServiceImpl implements CacheService {
    private RedisUtils redisUtils = new RedisUtils();
    private EGM egm = new EGM();
    private IIR iir = new IIR();

    public String get(String key, int redisType) {
        if (1 == redisType) {
            return egm.gain(key);
        } else if (2 == redisType) {
            return iir.get(key);
        }
        return redisUtils.get(key);
    }
    // set、del 同理...
}
壞味道：每個方法都要加 redisType 參數，每個方法裡都有一坨 ifelse。調用方被迫攜帶 type 參數，新增集群時每個方法都要改。

這個方案有什麼問題

看起來能跑，但幾個致命問題馬上浮現：

  • 方法簽名被汙染：原本 get(String key) 變成了 get(String key, int redisType)，所有調用方都要傳 type——數十個服務全部要改
  • 線性膨脹：現在只有 EGM 和 IIR 兩套集群。如果以後加第三套呢？每個方法裡再加一個 else if 分支，每個方法都要改
  • 所有集群耦合在一起：EGM、IIR、RedisUtils 三個對象全部塞在 CacheServiceImpl 裡，不管你用哪套集群，另外兩套的依賴都編譯進來了
  • 測試噩夢：想單獨測 IIR 的 set 邏輯？得先傳對 type 值，走完 if 分支判斷才能到那一行

最要命的是：這個方案功能上完全正確——JUnit 測試跑得通，set("user_name_01", "小傅哥", 1) 寫入 EGM，取回來也是「小傅哥」。但功能正確不等於結構良好，一旦上線運行，之後再想改就真的難了。

核心痛點總結

問題根因後果
方法簽名加了 type調用方需要知道集群類型數十個服務全部要改
每個方法都有 ifelse多套實現塞在一個類裡新集群要改每個方法
三個集群依賴共存沒有按集群隔離編譯耦合、測試困難

這些問題的根因是：把「選擇哪套集群」的邏輯和「具體操作」的邏輯混在了一起。選擇應該是一次性的（在啟動或注入時決定），而不是每次調用都判斷。下一節我們會用抽象工廠的思路，把這個選擇抽出去，讓原類零修改就能接入兩套集群。
