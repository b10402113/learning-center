適配器的直覺：把不兼容的「口」統一起來

設計模式 · 適配器模式 · Step 1/4

學習目標

能說出適配器模式的核心意圖——把原本不兼容的接口通過適配修改做到統一——並用生活直覺和業務場景說出「為什麼需要它」。

生活中的適配器

你到美國出差，帶了台灣的三孔插頭，發現旅館牆上只有兩孔扁插座。你不可能改旅館的牆，也不可能把自己的插頭鋸掉——你買了一個轉接頭。

轉接頭做的事情很簡單：把一個「口」翻譯成另一個「口」。兩邊的電都是一樣的，只是形狀不同，轉接頭讓它們能接上。

適配器模式（Adapter Pattern）就是程式世界裡的這個轉接頭。當你的系統想統一調用，但外來的接口各有各的命名、各有各的返回值，適配器在中間做一層翻譯，讓調用方只面對一個統一的口。

為什麼框架裡滿滿都是適配器

如果你去 Spring 的原始碼裡搜 Adapter，會跳出一堆實現類：`UserCredentialsDataSourceAdapter`、`HttpRequestHandlerAdapter`、`MessageListenerAdapter`……為什麼框架這麼愛用這個模式？

因為框架要整合各種第三⽅，每個第三⽅都有自己的 API 風格。Spring 的做法不是要第三⽅改接口，而是在中間加一層適配器，把差異抹平。就像你家的插座不用管你帶的是哪國的插頭——轉接頭負責翻譯。

適配器模式的核心：不改兩頭，改中間。不改你的系統，也不改第三方的接口，而是加一層翻譯。

業務場景：行銷系統的 MQ 困境

假設你負責一個行銷系統，需要接收各種 MQ（消息隊列）消息來觸發獎勵發放：

MQ 消息 用戶 ID 欄位 時間欄位 業務 ID 欄位
create_account（開戶） number accountDate number
OrderMq（內部訂單） uid createOrderTime orderId
POPOrderDelivered（第三方訂單） uId orderTime orderId

三個 MQ 傳遞的都是同一個意思：「某個用戶在某個時間做了某件事」。但欄位名完全不一樣——用戶 ID 分別叫 number、uid、uId。

你的系統不可能為每種 MQ 寫一套處理邏輯——那樣新增一個 MQ 就要改一次代碼，改到天荒地老。你需要的是一個轉接頭：不管外面傳進來的欄位叫什麼名字，進了系統之後全部映射到統一的結構。

不使用模式的壞味道

最直覺的做法：為每種 MQ 建一個消費類。

// 為 create_account 建一個類
public class create_accountMqService {
    public void onMessage(String msg) {
        JSONObject json = JSON.parseObject(msg);
        String number = json.getString("number");
        String address = json.getString("address");
        // ... 逐欄位取出處理
    }
}

// 為 OrderMq 建一個類
public class OrderMqService {
    public void onMessage(String msg) {
        JSONObject json = JSON.parseObject(msg);
        String uid = json.getString("uid");
        String sku = json.getString("sku");
        // ... 逐欄位取出處理
    }
}
壞味道：每新增一個 MQ，就新增一個手工類。MQ 少的時候還能忍受，一旦消息種類來到幾十個，這些類就會爆炸——每個類做的事情幾乎一樣（解析 JSON、取出欄位、轉成統一格式），差別只在欄位名不同。

這正是適配器要消滅的重複。

適配器的直覺

適配器做的事情可以用一句話概括：

把原本不兼容的接口，通過適配修改，做到統一輸出。

對應到 MQ 場景：不管外面的 MQ 欄位叫 number、uid 還是 uId，適配器把它們全部映射成統一的 userId。你的業務代碼只面對 userId，不再關心外面叫什麼。

下一個步驟我們會看到具體怎麼實現：用一張「映射表」加上 Java 反射，讓適配器自動完成欄位翻譯。

小結

問題 適配器的回答
多個第三方接口格式不同 不改第三方，加一層翻譯
新增一個接口就要改一次代碼 適配器把差異隔離在映射表裡
業務代碼和第三方接口耦合 業務只面對統一接口
