用門面中間件重構白名單

design-pattern › facade › facade-refactor

學習目標：理解外觀模式如何落地為 SpringBoot starter 中間件，用 @DoDoor 注解 + AOP 切面統一治理白名單。

回顧：那一坨 ifelse 代碼

上一節我們看到了白名單的 ifelse 版本——每個接口方法裡都塞一段 userList.contains(userId) 的判斷，改一個地方就要改全部。現在我們用外觀模式把它重構成一個 SpringBoot starter 中間件。

重構的核心思路：把白名單邏輯從業務方法裡抽出來，放到一個獨立的中間件 jar 包裡。業務方只需要兩步——引入依賴、加一個注解——白名單就生效了。業務代碼零改動。

整體結構：兩條線

重構後的中間件分兩條線，各管各的：

線負責什麼核心類
配置側從 application.yml 讀白名單配置StarterServiceProperties、StarterAutoConfigure
切面側攔截加了注解的方法，做白名單校驗@DoDoor 注解、DoJoinPoint 切面

第一步：配置側——讀配置

白名單的用戶列表不應該硬編碼在代碼裡，而是放在 application.yml 中：

itstack:
  door:
    enabled: true
    userStr: "1001,aaaa,ccc"

對應的配置類用 SpringBoot 的 @ConfigurationProperties 綁定：

@ConfigurationProperties("itstack.door")
public class StarterServiceProperties {
    private String userStr;
    // getter/setter
}

再用一個 StarterService 把配置值包裝一下：

public class StarterService {
    private String userStr;
    public List<String> split(String separator) {
        return Arrays.asList(userStr.split(separator));
    }
}

最後通過 StarterAutoConfigure 把 Bean 注冊到 Spring 容器：

@Configuration
@ConditionalOnClass(StarterService.class)
@EnableConfigurationProperties(StarterServiceProperties.class)
public class StarterAutoConfigure {
    @Bean
    @ConditionalOnMissingBean
    @ConditionalOnProperty(prefix = "itstack.door", name = "enabled", havingValue = "true")
    public StarterService starterService(StarterServiceProperties properties) {
        StarterService service = new StarterService();
        service.setUserStr(properties.getUserStr());
        return service;
    }
}
要點：條件注解（@ConditionalOnProperty）控制中間件是否生效。配置 enabled: false 就關掉，不用改任何代碼。

第二步：切面側——攔截與校驗

配置有了，怎麼讓白名單自動生效？答案是自定義注解 + AOP 切面（Aspect-Oriented Programming，面向切面編程）。

自定義注解 @DoDoor

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface DoDoor {
    String key();           // 要校驗的入參字段名，如 "userId"
    String returnJson();    // 攔截後返回的 JSON
}

業務方法只要加上這個注解，就被「掛」上了白名單治理：

@DoDoor(key = "userId", returnJson = "{\"code\":\"1111\",\"info\":\"非白名單可訪問用戶攔截！\"}")
@RequestMapping("/api/queryUserInfo")
public UserInfo queryUserInfo(@RequestParam String userId) {
    return new UserInfo("蟲蟲:" + userId, 19, "天津市南開區旮旯胡同100號");
}
業務代碼完全不變：方法體裡沒有一行白名單邏輯，全靠注解聲明。

切面 DoJoinPoint

切面是「門面」的核心——它定義了「攔截到加了 @DoDoor 的方法後做什麼」：

@Aspect
@Component
public class DoJoinPoint {
    @Autowired
    private StarterService starterService;

    @Around("@annotation(doDoor)")
    public Object doRouter(ProceedingJoinPoint jp, DoDoor doDoor) throws Throwable {
        // 1. 從注解拿到要校驗的字段名（如 userId）
        String fieldValue = getFiledValue(doDoor.key(), jp.getArgs());

        // 2. 空值直接放行
        if (fieldValue == null || fieldValue.isEmpty()) {
            return jp.proceed();
        }

        // 3. 從配置拿到白名單，做比對
        List<String> allowedUsers = starterService.split(",");
        if (allowedUsers.contains(fieldValue)) {
            return jp.proceed();  // 命中白名單，放行
        }

        // 4. 未命中，返回攔截信息
        return returnObject(doDoor.returnJson());
    }
}

流程很清晰：

  1. 取方法參數中的 userId 值
  2. 空值放行（防禦性編程）
  3. 跟配置的白名單比對
  4. 命中就放行（jp.proceed()），不命中就返回攔截信息

第三步：測試驗證

在業務工程引入中間件 jar，配置好白名單，啟動 SpringBoot：

請求userId結果
GET /api/queryUserInfo?userId=10011001（在白名單中）返回正常用戶信息（code 0000）
GET /api/queryUserInfo?userId=小團團小團團（不在白名單）返回攔截信息（code 1111）

白名單用戶正常訪問，非白名單用戶被攔截——整個過程業務方法沒有任何改動。

小結

整個重構路徑：配置側讀取白名單 → 自定義注解聲明治理需求 → AOP 切面統一攔截校驗。三步走完，白名單邏輯從業務方法裡完全抽離，變成一個可複用的中間件。新增橫切需求（比如簽名校驗、限流）？再加一個注解 + 一個切面就行，不動任何已有代碼。這就是外觀模式在 Spring 生態中的落地方式。
