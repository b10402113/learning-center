MQ 消息體適配：同值異名怎麼辦

設計模式 · 適配器模式 · Step 2/4

學習目標

能用字段映射 + 反射的機制，把三種結構不同的 MQ 消息體適配到統一的 RebateInfo，並說出這比「每個 MQ 建一個消費類」好在哪。

統一的目標結構

適配器的第一步是定義「你想要什麼」。在行銷系統中，不管你收到哪種 MQ 消息，最終關心的都是四個欄位：

欄位含義例子
userId用戶 ID100001
bizId業務 ID（訂單號/開戶號）ORDER_001
bizTime業務時間2026-09-02
desc業務描述開戶獎勵

我們把這個統一結構叫做 RebateInfo（返利信息）。不管外面的 MQ 欄位叫 number、uid 還是 uId，適配器負責把它們全部映射到 RebateInfo 的四個欄位。

壞味道：每個 MQ 一個手工類

// 為 create_account 寫一個類
public class create_accountMqService {
    public void onMessage(String msg) {
        JSONObject json = JSON.parseObject(msg);
        RebateInfo info = new RebateInfo();
        info.setUserId(json.getString("number"));   // number → userId
        info.setBizId(json.getString("number"));     // number → bizId
        info.setBizTime(json.getString("accountDate")); // accountDate → bizTime
        info.setDesc(json.getString("desc"));
        // ... 業務處理
    }
}

// 為 OrderMq 寫另一個類
public class OrderMqService {
    public void onMessage(String msg) {
        JSONObject json = JSON.parseObject(msg);
        RebateInfo info = new RebateInfo();
        info.setUserId(json.getString("uid"));        // uid → userId
        info.setBizId(json.getString("orderId"));     // orderId → bizId
        info.setBizTime(json.getString("createOrderTime")); // createOrderTime → bizTime
        // ... 業務處理
    }
}
壞味道：每個 MQ 一個類，每個類做的事情幾乎一樣——解析 JSON、取出欄位、映射到 RebateInfo。差別只在欄位名不同。新增一個 MQ 就要複製貼上改欄位名，代碼量線性增長。

適配器的做法：映射表 + 反射

核心思路：把「哪個源欄位對應哪個目標欄位」抽成一張映射表（link），讓適配器根據這張表自動完成翻譯。

第一步：定義映射表

對 create_account 消息，映射表是：

// link: 源欄位名 → 目標欄位名
Map<String, String> link = new HashMap<>();
link.put("number", "userId");      // number → userId
link.put("number", "bizId");       // number → bizId（同源欄位映射到不同目標）
link.put("accountDate", "bizTime");// accountDate → bizTime
link.put("desc", "desc");          // desc → desc（名字相同也要映射）

對 OrderMq 消息：

Map<String, String> link = new HashMap<>();
link.put("uid", "userId");         // uid → userId
link.put("orderId", "bizId");      // orderId → bizId
link.put("createOrderTime", "bizTime"); // createOrderTime → bizTime

第二步：MQAdapter 用反射自動映射

MQAdapter.filter 方法接收原始消息（JSON 字符串或 Map）和映射表，用 Java 反射自動把值塞進 RebateInfo：

public class MQAdapter {
    // 接收 JSON 字符串
    public static RebateInfo filter(String strJson, Map<String, String> link) {
        Map<String, String> map = JSON.parseObject(strJson, Map.class);
        return filter(map, link);
    }

    // 接收 Map（核心邏輯）
    public static RebateInfo filter(Map<String, String> map, Map<String, String> link) {
        RebateInfo info = new RebateInfo();
        // 遍歷映射表
        for (Map.Entry<String, String> entry : link.entrySet()) {
            String srcField = entry.getKey();   // 源欄位名（如 "uid"）
            String dstField = entry.getValue(); // 目標欄位名（如 "userId"）
            // 從原始 Map 取值
            String value = map.get(srcField);
            // 用反射調用 set 方法
            Method method = RebateInfo.class.getMethod(
                "set" + dstField.substring(0, 1).toUpperCase() + dstField.substring(1),
                String.class
            );
            method.invoke(info, value);
        }
        return info;
    }
}
核心機制：映射表描述「源叫什麼、目標叫什麼」，反射負責自動調用 set 方法。新增一種 MQ？只需要定義一張新的映射表，不需要寫新的消費類。

第三步：測試驗證

// 測試 create_account 消息
String json = "{\"number\":\"100001\",\"address\":\"北京\",\"accountDate\":\"2026-09-02\",\"desc\":\"開戶\"}";
Map<String, String> link = new HashMap<>();
link.put("number", "userId");
link.put("number", "bizId");
link.put("accountDate", "bizTime");
link.put("desc", "desc");
RebateInfo info = MQAdapter.filter(json, link);
// info.userId = "100001", info.bizId = "100001", info.bizTime = "2026-09-02"

// 測試 OrderMq 消息
String json2 = "{\"uid\":\"100002\",\"sku\":\"商品A\",\"orderId\":\"ORDER_001\",\"createOrderTime\":\"2026-09-02\"}";
Map<String, String> link2 = new HashMap<>();
link2.put("uid", "userId");
link2.put("orderId", "bizId");
link2.put("createOrderTime", "bizTime");
RebateInfo info2 = MQAdapter.filter(json2, link2);
// info2.userId = "100002", info2.bizId = "ORDER_001", info2.bizTime = "2026-09-02"

同樣的 MQAdapter.filter 方法，傳入不同的映射表，就能處理不同的 MQ。業務代碼始終只面對 RebateInfo，不關心外面的 MQ 長什麼樣。

好處對比

不使用適配器使用適配器
新增一個 MQ新增一個消費類（複製貼上改欄位名）新增一張映射表
業務代碼每個消費類裡都有解析邏輯只面對 RebateInfo
欄位名變更要改消費類的代碼改映射表配置
可維護性類數量線性增長，難以維護映射表可配置化，容易管理

配置化的進一步演進

在實際業務中，映射表不需要寫死在代碼裡。可以放到配置文件或資料庫中，實現零代碼接入新 MQ：配好映射關係，適配器自動完成翻譯。這也是為什麼適配器常和代理模式搭配使用——代理類根據配置自動路由到正確的映射表。

小結

MQ 消息體適配的核心 = 映射表描述欄位對應關係 + 反射自動調用 set 方法。新增 MQ 只需新增映射表，業務代碼零修改。
