六大原则各自管什么

design-pattern · six-principles

学习目标

能说出单一职责、里氏替换、依赖倒置、接口隔离、迪米特、开闭六大原则各自管什么，并说清它们如何共同指向高内聚、低耦合、可扩展、可复用。

为什么需要原则

上一步我们认出了"一坨代码"的坏味道——按 type 字段堆叠 ifelse。设计模式是重构这种代码的具体套路，但套路不是随便用的。你需要一组裁判规则来判断：这段代码哪里坏了？重构后真的变好了吗？好在哪？

六大原则就是这组裁判。它们不告诉你具体怎么写代码，而是告诉你一段代码"健康不健康"——共同指向四个终极追求：

高内聚一个类只干一件事
低耦合类之间尽量少互相依赖
可扩展加新功能不改旧代码
可复用写过的东西能在别的地方用

六大原则速览

1. 单一职责原则（SRP）

Single Responsibility Principle
管什么：一个类只干一件事。

如果一个类既要处理优惠券发放，又要处理实物发货，又要处理兑换卡——它就承担了三个职责。任何一个职责变化都可能影响另外两个。

违反的样子：一个 Service 类里塞了五种业务逻辑，方法之间互相调用。
类比：一个人同时当厨师、司机、会计——任何一个岗位出问题，其他工作都受影响。

2. 里氏替换原则（LSP）

Liskov Substitution Principle
管什么：子类能无缝替换父类，不破坏已有行为。

如果你有一个 Animal 类和 Cat、Dog 子类，任何用到 Animal 的地方传 Cat 进去，程序行为应该和预期一致。子类可以扩展父类，但不能改变父类已经定好的行为契约。

违反的样子：子类重写了父类方法，但改变了方法的语义（比如父类"返回非空"，子类返回 null）。
类比：父类承诺"所有鸟都会飞"，企鹅继承了鸟但不会飞——这就是里氏替换的违反。

3. 依赖倒置原则（DIP）

Dependency Inversion Principle
管什么：高层模块不依赖低层模块，都依赖抽象。

你的业务逻辑（高层）不应该直接依赖具体的 MySQL 实现（低层），而是依赖一个 Repository 接口。具体用 MySQL 还是 MongoDB，通过注入来决定。

违反的样子：Service 类里直接 new MyBatisMapper()，换数据库就得改业务代码。
类比：你写作文不依赖某支特定的笔——笔是接口，换一支也能写。

4. 接口隔离原则（ISP）

Interface Segregation Principle
管什么：接口要小而专，不要强迫实现用不到的方法。

如果一个 IUserService 接口有 20 个方法，但某个调用方只用其中 3 个——它仍然要实现另外 17 个空方法。应该拆成多个小接口。

违反的样子：一个"胖接口"，实现类被迫写一堆空方法或抛 UnsupportedOperationException。
类比：你去餐厅不需要被迫点全套套餐——单点你需要的菜就好。

5. 迪米特原则（LoD）

Law of Demeter · 最少知识原则
管什么：一个对象应该只跟"直接朋友"说话，不跟朋友的朋友说话。

你的 Controller 不应该知道 Service 内部调了哪个 DAO，再让 DAO 去查了哪张表。它应该只跟 Service 打交道。"我知道的越少，被影响的概率越低。"

违反的样子：order.getUser().getAddress().getCity()——链式调用穿越三层对象。
类比：你找同事借工具，不需要知道他家保险柜密码。

6. 开闭原则（OCP）

Open/Closed Principle
管什么：对扩展开放，对修改关闭。

加新产品类型时，应该新增一个类而不是改已有代码。已有代码已经在跑了、被别人依赖着，改它就有可能引入 bug。扩展 = 加新文件；修改 = 改旧文件。

违反的样子：每加一个产品类型，就在 awardToUser() 里加一个 else if。
类比：你家客厅的插座不够用，应该加一个插线板（扩展），而不是重新布线（修改）。

六大原则的共同指向

六个原则看起来各管一块，但它们的终极目标是一致的：

原则指向的追求
单一职责高内聚
里氏替换可复用（子类可替换父类，复用才安全）
依赖倒置低耦合 + 可扩展
接口隔离低耦合（不被迫依赖不需要的东西）
迪米特低耦合（减少对象间的知识传递）
开闭原则可扩展（加功能不改旧代码）
设计模式就是在具体场景下实现这些原则的"套路"。每学一个模式，问自己：它满足了哪个原则？代价是什么？

本节要点回顾

  • 六大原则是裁判规则——判断代码健康不健康
  • 单一职责 → 高内聚；开闭 → 可扩展；依赖倒置/接口隔离/迪米特 → 低耦合；里氏替换 → 可复用
  • 每个模式都在用具体方式满足这些原则，同时付出一定代价（更多的类、间接结构等）
  • 学模式时始终问：它满足了哪个原则？代价是什么？

推荐阅读：《重学 Java 设计模式》任意一个模式章节的"总结"部分——每个总结都会列出该模式满足了哪些原则。
