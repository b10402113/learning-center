裝飾器模式重構與適用邊界

設計模式 · 節點 16 · 步驟 3/3

這節課你要學會什麼

讀完這篇文章，你能用四角色模型重構 SSO 場景，並在繼承、裝飾器、AOP 之間做出適用判斷。

重構：從繼承到組合

上一節我們看到了用繼承擴展 SSO 的三個痛點。裝飾器模式的重構思路很直接：把「繼承 SsoInterceptor」改為「實現接口 + 持有 SsoInterceptor 實例」。拆成兩個類。

第一個類：抽象裝飾角色 SsoDecorator

public abstract class SsoDecorator implements HandlerInterceptor {

    // 持有被裝飾對象的引用——這是組合取代繼承的關鍵
    private final HandlerInterceptor handlerInterceptor;

    // 構造函數注入被裝飾對象
    public SsoDecorator(HandlerInterceptor handlerInterceptor) {
        this.handlerInterceptor = handlerInterceptor;
    }

    // 覆蓋接口方法，默認轉調被裝飾對象
    @Override
    public boolean preHandle(String request, String response, Object handler) {
        return handlerInterceptor.preHandle(request, response, handler);
    }
}

三個重點：

  1. 繼承接口（implements HandlerInterceptor）——保證與被裝飾對象的類型一致，可以互相替換
  2. 構造函數注入——把被裝飾對象作為參數傳入，存在自己的成員變量裡。這是「組合」的落點
  3. 覆蓋方法做轉調——默認行為就是「原封不動轉給被裝飾對象」。具體裝飾類只需要重寫需要擴展的部分

第二個類：具體裝飾角色 LoginSsoDecorator

public class LoginSsoDecorator extends SsoDecorator {

    private static final Map<String, String> authMap = new HashMap<>();
    static {
        authMap.put("huahua", "queryUserInfo");
        authMap.put("doudou", "queryUserInfo");
    }

    public LoginSsoDecorator(HandlerInterceptor handlerInterceptor) {
        super(handlerInterceptor);
    }

    @Override
    public boolean preHandle(String request, String response, Object handler) {
        // 第一步：先執行被裝飾對象的原有校驗
        boolean success = super.preHandle(request, response, handler);
        if (!success) return false;

        // 第二步：疊加自己的方法級訪問校驗
        String userId = request.substring(8, request.indexOf("success") + 7);
        String method = authMap.get(userId);
        if (method == null) {
            System.out.println("攔截：" + userId + " 無權訪問");
            return false;
        }
        System.out.println("放行：" + userId + " 訪問 " + method);
        return true;
    }
}

注意 super.preHandle(request, response, handler) 這行：它不是在「調用父類構造函數」，而是在調用被裝飾對象的原有校驗邏輯。這是裝飾器疊加職責的模板——先執行裡面那層，再執行自己的。

使用方式

// 原始的 SSO 校驗
HandlerInterceptor sso = new SsoInterceptor();

// 包一層：加上方法級訪問校驗
HandlerInterceptor loginCheck = new LoginSsoDecorator(sso);

// 再包一層（假設還有日誌裝飾器）
// HandlerInterceptor withLog = new LogDecorator(loginCheck);

loginCheck.preHandle("1successhuahua", response, handler);
// 輸出：模擬單點登錄方法訪問攔截校驗：huahua queryUserInfo
// 輸出：放行：huahua 訪問 queryUserInfo

每包一層，就多一個功能。想去掉某個功能，不包就行。運行時隨意增減，不需要改編譯。

裝飾器 vs 繼承：什麼時候選哪個

判斷維度選繼承選裝飾器
擴展需求數量只有 1–2 種，且固定3 種以上，或可能繼續增長
功能組合不需要排列組合需要「A + B」或「A + C」靈活搭配
運行時增減不需要需要在運行時動態開啟/關閉某功能
子類管理成本子類少、維護簡單子類多到難以維護
一句話判斷：如果新功能是原功能的「一種新變體」→ 繼承；如果新功能是「在原功能上面疊一層」→ 裝飾器。

裝飾器 vs AOP

兩者都能做到「不改原類、動態增強」，但它們的適用場景不同：

維度裝飾器AOP
實現層級純 Java 物件組合依賴 Spring 容器 + 動態代理
粒度方法級（你要包哪個方法就包哪個）切面表達式控制（可以按包/類/方法/註解）
適用場景少量功能的靈活組合、不依賴框架的純 Java 專案大批量統一切面治理（日誌、權限、事務）
複雜度低——純物件組合中——需要理解代理機制和切面表達式

簡單場景（SSO 加一層校驗）→ 用裝飾器，乾淨直覺。
複雜場景（整個專案所有接口統一加白名單、日誌、限流）→ 用 AOP 或外觀模式中間件更合適，因為切面表達式可以「一行配置管所有接口」。

生活類比

夏天穿短褲、冬天穿棉褲、雨天穿雨衣——你的身體（原類）從來沒被改過，穿上不同衣服（裝飾器）就適應不同場景。衣服之間可以任意搭配（組合），穿脫自如（運行時增減），不需要開一個「防水型身體」的子類（避免子類膨脹）。

小結

裝飾器模式通過「組合取代繼承」，在不改原類的前提下動態疊加功能。四角色模型（抽象构件、具體构件、裝飾角色、具體裝飾角色）是它的骨架。選型判斷：少量固定功能用繼承就夠了，頻繁橫向擴展或需要運行時增減就選裝飾器；純物件組合能搞定的小場景用裝飾器，大批量統一切面治理用 AOP。
