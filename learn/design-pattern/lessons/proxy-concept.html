什麼是代理模式？

學習目標

認識代理模式「給複雜服務提供簡單可控入口」的意圖，說出三種典型場景，並理解 MyBatis「只定義接口就能跑」背後的代理思想。

一個你每天都在用的代理

你家牆壁裡埋著 220V 的電線——裸露的銅線、強電流、直接摸會觸電。但你不需要懂電路，也不需要戴絕緣手套，你只需要按一下牆上的開關，燈就亮了。

這個開關就是你的「代理」。它不生產電力，不改變電壓，但它讓你用最安全、最簡單的方式接入了複雜的電力系統。

代理模式是什麼？

代理模式（Proxy Pattern）是一種結構型設計模式。它的核心思想是：在不寫實現類的情況下，通過一個「代理人」對象來間接訪問目標服務。代理人負責處理複雜的細節，調用者只需要跟代理人打交道。

用一句話記：

代理 = 給複雜服務提供簡單可控的入口。

代理人（Proxy）就像「老大和小弟」的關係——你找小弟辦事，小弟去對接老大的複雜服務。你不需要知道老大在哪裡、電話多少、什麼時候有空，小弟全搞定。

三種典型場景

代理模式在實際系統中有三個常見的應用場景：

場景代理做了什麼例子
數據庫連接池 減少應用服務擴容時數據庫連接數暴增 連接池代理管理連接的創建與回收
RPC 框架 拿到 jar 包接口描述後，服務啟動時生成對應代理類，調用接口實際是通過代理類發送 socket 信息 Dubbo、gRPC 的遠程調用
MyBatis Mapper 只定義接口不寫實現類，即可對 XML 或自定義注解裡的 SQL 語句做增刪改查 IUserDao 接口 + @Select 注解

這三個場景有一個共同點：服務本身很複雜（連接管理、網絡通信、SQL 執行），但代理讓使用者用最簡單的方式接入——你不需要親自處理底層細節。

MyBatis 的魔法：接口沒有實現類，為什麼能跑？

如果你用過 MyBatis，你一定寫過這樣的代碼：

// 只定義接口，沒有任何實現類
public interface IUserDao {
    @Select("select userName from user where id = #{uId}")
    String queryUserInfo(String uId);
}

然後你從 Spring 容器裡拿到 IUserDao 的實例，直接調用 queryUserInfo("100001")，它居然能正常返回結果。

你有沒有想過：這個接口沒有實現類，那 queryUserInfo 的方法體在哪裡？誰在執行那條 SQL？

答案就是代理。MyBatis 在你看不見的地方，用 JDK 動態代理為你生成了一個實現類——你拿到的 IUserDao 實例，其實是一個代理對象。

代理模式的模型結構

代理模式的中間件模型可以拆成兩層：

  • 上層：中間件實現——負責生成代理類、註冊到 Spring 容器（這是框架開發者寫的）
  • 下層：功能使用——定義接口、寫注解、從容器獲取實例並調用（這是業務開發者寫的）

兩層之間的分離，正是代理模式的價值所在：業務代碼完全不需要知道代理的存在，它只看到一個「有實現的接口」。

生活中的代理

一旦你注意到這個結構，會發現它無處不在：

  • 房產中介：你不直接找房東談價，中介幫你過濾、談判、簽約
  • 快遞驛站：你不需要在家等快遞員，驛站替你收件、保管、通知
  • VPN：你不直接連目標服務器，VPN 代理幫你轉發請求

這些場景的共同點是：真實的服務提供者很複雜或不方便直接訪問，代理提供了一個簡化、安全、可控的替代入口。
