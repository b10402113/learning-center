何時該用設計模式

Step 4/4 · 設計模式與六大原則

學習目標：綜合六大原則與三分類地圖，判斷設計模式適合解決哪些真實問題，也看懂框架如何綜合運用多種模式，避免為用而用。

現在，把前兩步合在一起。你手上有一把尺子——六大原則，也有一幅地圖——三大分類。這一步要回答兩個最關鍵的問題：什麼時候該搬出設計模式？什麼時候反而不該用？

該用的信號：先聞到壞味道，再談模式

設計模式是解決問題的工具，不是拿來炫技的收藏品。比較可靠的使用順序，可以分成三步：

  1. 先聞到壞味道——又冒出一個 if/else 分支、某個類別越長越胖，或是同一段程式碼又要複製貼上一次。
  2. 拿尺子量一量——這個壞味道違反了哪一條原則？例如分支太多，可能違反開閉原則；類別太肥，可能違反單一職責原則；到處直接建立具體類別，可能違反依賴倒置原則。
  3. 對著地圖找場景——確認哪個分類、哪個模式，剛好能處理眼前這個問題。

這也正是重構 if/else 的完整流程：發獎類型一增加，就得修改一大段方法，這是壞味道；再用尺子一量，發現它違反了開閉原則；接著對照地圖，選擇創建型的工廠方法，或行為型的策略模式。之後新增獎品時，只要增加新的類別，原本的程式碼就不用跟著改。

框架的「綜合運用」是怎麼回事

回頭看第一步提到的觀念：框架通常是多種設計模式的綜合運用。這裡有兩個重要啟示：

  • 讀源碼時，別期待一個模式能單獨對號入座。看到 Spring 的 Adapter 實作類別，不要急著下結論說「這就是適配器模式」。它可能同時混合了工廠、代理、模板方法等做法。書中的觀點是：任何設計模式都不是單獨使用的。
  • 寫程式時，同一個場景也可能需要組合幾種模式。例如一個「發獎服務」，可以同時使用工廠負責建立物件、策略負責處理演算法，模板方法則負責固定流程骨架。老手所謂的「綜合運用」能力，往往就是在這類組合經驗中累積出來的。

不該用的信號：三個剎車

剎車一：為用而用，也就是過度設計

書裡反覆強調：切忌為用而用，最後導致過度設計。如果原本的程式碼已經高內聚、簡單直接，硬套上橋接模式，反而可能讓結構變複雜、維護變困難。引入模式的目的，是讓程式更容易擴充與維護；如果結果正好相反，就代表方向錯了。

剎車二：別忘了計算類別膨脹的代價

幾乎每個模式都有代價。狀態模式在狀態很多時，可能產生大量實作類別；命令模式遇到許多命令與實作的組合，也可能讓類別數量快速增加。書中的建議是按照投入與回報評估：看看這段邏輯是否經常修改、能不能組件化，以及能不能把業務邏輯與非業務邏輯分開。

剎車三：即使違反原則，也要把理由算清楚

有些模式天生會與某條原則衝突，例如訪問者模式可能違反迪米特法則。這不代表它一定錯，而是表示你要確認：在這個場景裡，模式帶來的收益是否大於違反那條原則的損失。使用之前先把這筆帳算清楚，面試時也才能說出真正的設計考量。

判斷金句：設計模式是權衡的結果。該不該用，不是因為「這個模式很流行」，而是要問：「它解決了哪條原則帶來的痛點？又付出了什麼代價？」

延伸閱讀

主要來源是《重學 Java 設計模式》的「目錄」（六大原則與三分類索引），以及「Adapter: 开篇与设计模式观」（多種模式的綜合運用）。書中每個模式的「總結」，都會回到同一種思考方式：滿足哪些原則、付出什麼代價，再依照實際場景評估。

往後遇到任何設計模式，都可以用這四步檢查：先找壞味道，再拿尺子量，接著對照地圖，最後算清楚帳單。
