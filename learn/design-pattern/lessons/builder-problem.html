装修报价的 ifelse 堆砌

Node: builder-prototype · Step 1/5

学习目标

认识装修报价场景中 ifelse 堆砌的坏味道，理解"分步组装复杂对象"比"一次性创建"更灵活的动机。

场景：装修公司的报价单

想象你在一家装修公司做后端开发。公司有三种装修套餐：

  • 豪华欧式 — 一级顶 + 多乐士 + 德尔地板 + 东鹏瓷砖
  • 轻奢田园 — 二级顶 + 立邦 + 圣象地板 + 马可波罗瓷砖
  • 现代简约 — 一级顶 + 立邦 + 德尔地板 + 东鹏瓷砖

每种物料都实现了同一个 Matter 接口，提供场景、品牌、型号和每平米单价。客户选择套餐后，系统按面积计算总价。

想象你在点外卖。你不是把所有食材一起扔进锅里炒，而是先选主食、再选配菜、再选汤品，最后服务员把它们组合成一餐。装修套餐也是同样的道理——它是一个组合过程，不是一个瞬间完成的动作。

实际代码长什么样

你的同事写了一个 DecorationPackageController，用 if-else 把每种套餐的物料组合硬编码在方法里：

// 一个 if 分支 = 一个套餐
public static List<Matter> getMatterList(int area, int level) {
    List<Matter> list = new ArrayList<>();

    if (level == 1) {
        // 豪华欧式：一级顶 + 多乐士 + 德尔 + 东鹏
        list.add(new CeilingMatter("一级顶", "多乐士", "D-980", area * 140));
        list.add(new CoatMatter("多乐士", "金装五合一", area * 45));
        list.add(new FloorMatter("德尔", "强系列", area * 115));
        list.add(new TileMatter("东鹏", "玉石瓷砖", area * 145));
    } else if (level == 2) {
        // 轻奢田园：二级顶 + 立邦 + 圣象 + 马可波罗
        list.add(new CeilingMatter("二级顶", "立邦", "Y-660", area * 180));
        list.add(new CoatMatter("立邦", "竹炭净味五合一", area * 42));
        list.add(new FloorMatter("圣象", "N8系列", area * 128));
        list.add(new TileMatter("马可波罗", "真石大板", area * 160));
    } else if (level == 3) {
        // 现代简约：一级顶 + 立邦 + 德尔 + 东鹏
        list.add(new CeilingMatter("一级顶", "立邦", "Y-550", area * 120));
        list.add(new CoatMatter("立邦", "抗甲醛五合一", area * 38));
        list.add(new FloorMatter("德尔", "强化系列", area * 98));
        list.add(new TileMatter("东鹏", "全抛釉面", area * 135));
    }

    return list;
}

这段代码有什么问题？

贴膏药式的修修补补：每加一个新套餐，你就得在 getMatterList 里追加一个 else if 块。套餐种类越多，这个方法就越膨胀。你改了 100 行的代码，结果只为了让客户多一个选择——这不是好的修改比例。

具体来说，坏味道至少有三层：

  • 单一职责违反：一个方法同时决定"选什么物料"和"怎么创建物料对象"，两件事耦合在一起。如果物料的品牌或价格变了，你也要动这个方法；如果新增了物料种类（比如灯具），你还是得动这个方法。
  • 组合爆炸：4 种物料 × 3 个套餐 = 12 行。如果有 8 种物料 × 10 个套餐 = 80 行。如果物料种类或套餐种类再翻倍，代码量就按乘积增长。
  • 无法复用：如果另一个系统（比如装修预算小程序）也需要同样的套餐组合，你没法把"组合逻辑"单独拿出来用，因为它和 Spring Controller 写死在一起。
核心洞察：装修套餐不是一个"一次性完成"的动作，而是一个"分步组装"的过程——先选吊顶，再选涂料，再选地板，再选瓷砖。把组装过程从产品里拆出来，你才能灵活地替换任何一个步骤。

如果设计得好，应该是什么样？

理想情况下，每个套餐的物料组合应该由一个独立的"组装指南"来描述，而不是塞在控制器的 if-else 里：

// 好的方向：组装逻辑独立，每种套餐是一个独立的组装流程 public interface IMenu { List<Matter> getMatterList(); // 这个套餐要装哪些物料？ } public class LuxuryEuropean implements IMenu { @Override public List<Matter> getMatterList() { return Arrays.asList( new CeilingMatter("一级顶", "多乐士", "D-980"), new CoatMatter("多乐士", "金装五合一"), new FloorMatter("德尔", "强系列"), new TileMatter("东鹏", "玉石瓷砖") ); } }

这还不是建造者的最终形态，但方向已经对了：组合逻辑和业务逻辑分离，每种套餐独立管理自己的物料清单。

这和你平时写的代码有什么关系？

你在 Spring Boot 项目里可能见过类似的 if-else 堆砌：根据 type 字段走不同的处理分支，根据 region 选择不同的配置，根据 role 加载不同的权限组合。这些都和装修报价是同一类问题——组合逻辑被硬编码在决策入口。

Builder 模式的核心动机：当对象的构建过程涉及多个步骤、多种选择、且组合方式经常变化时，把构建过程从最终产品中独立出来。这不是为了"少写 if-else"（虽然效果如此），而是因为组装过程本身就是一个值得独立建模的领域概念。

在接下来的 step 2 里，你会看到如何用流式 API（fluent API）把这个组装过程写得既灵活又优雅。

快速自测

Q1. 如果公司新增一个"北欧极简"套餐，用 if-else 的代码需要改哪里？

  • 只需要新建一个北欧极简类
  • 必须在 getMatterList 方法里追加一个 else if 分支
  • 只需要修改物料类的构造参数
  • 不需要改任何代码，只需要加配置文件

Q2. 这段 if-else 代码最核心的坏味道是什么？

  • 变量命名不规范
  • 没有使用设计模式
  • 创建逻辑和决策逻辑耦合在一个方法里
  • 返回值用了 List 而不是数组

Q3. 建造者模式的核心动机是什么？

  • 把分步组装复杂对象的过程从产品中独立出来
  • 消除所有 if-else 语句
  • 让对象创建速度更快
  • 减少内存占用
