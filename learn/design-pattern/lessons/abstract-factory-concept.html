抽象工厂——从单产品到产品族

工厂方法与抽象工厂

学习目标

认识抽象工厂——从单产品升级到产品族（多接口、多实现），用 Redis 集群升级的场景理解"工厂的工厂"解决什么问题。

从工厂方法到抽象工厂：问题升级了

工厂方法解决的是"一类东西有多个品种"的问题——优惠券、商品、兑换卡，都是"奖品"这一个接口的多个实现。

但现实中有另一类问题：你需要替换的不是一种东西，而是一整套东西。比如：

  • 从单机 Redis 切换到集群 Redis
  • 从 Windows 文件系统切换到 macOS 文件系统
  • 从 MySQL 切换到 PostgreSQL

这些场景的共同特点是：你面对的不是一种产品，而是一组相关的接口（get/set/del/expire），它们各自有不同的实现。

场景：Redis 集群升级

现有系统用单机 Redis（RedisUtils），现在要接入两个集群方案：

方案 方法名 特点
EGM 集群 gain() 方法名叫 gain，不叫 get
IIR 集群 get() 方法名和原 Redis 一样，但内部实现不同

两个集群的接口方法名都不一样，但做的事情是一样的——读写缓存。

ifelse 升级版：每个方法都加 redisType

最直觉的做法是给每个 CacheService 方法加一个 redisType 参数：

// CacheServiceImpl.java — ifelse 版本
public String get(String key, Integer redisType) {
    if (redisType == 1) {
        return egm.gain(key);
    } else if (redisType == 2) {
        return iir.get(key);
    }
    return redisUtils.get(key);
}

public void set(String key, String value, Integer redisType) {
    if (redisType == 1) {
        egm.set(key, value);
    } else if (redisType == 2) {
        iir.set(key, value);
    }
    redisUtils.set(key, value);
}

问题

每个方法都膨胀了。get、set、setEx、del 四个方法，每个都要加 ifelse 分支。更严重的是——所有调用方都要额外传一个 redisType 参数，污染扩散到整个系统。

抽象工厂：适配器 + JDK 动态代理

抽象工厂的思路是：定义一个适配器接口，统一不同集群的方法名，然后用 JDK 动态代理把调用路由过去。

第一步：适配器接口统一方法名

// ICacheAdapter.java — 统一的缓存操作接口
public interface ICacheAdapter {
    String get(String key);
    void set(String key, String value);
    void setEx(String key, String value, long timeout);
    void del(String key);
}

第二步：每个集群各自适配

// EGMCacheAdapter.java — 把 gain 映射到 get
public class EGMCacheAdapter implements ICacheAdapter {
    private EGM egm = new EGM();

    @Override
    public String get(String key) {
        return egm.gain(key);  // EGM 叫 gain
    }

    @Override
    public void set(String key, String value) {
        egm.set(key, value);
    }
    // ... setEx, del 同理
}

// IIRCacheAdapter.java — 方法名刚好一致
public class IIRCacheAdapter implements ICacheAdapter {
    private IIR iir = new IIR();

    @Override
    public String get(String key) {
        return iir.get(key);  // IIR 方法名相同
    }
    // ...
}

第三步：JDK 动态代理路由调用

// JDKProxy.java — 动态代理工厂
public class JDKProxy {
    public static <T> T getProxy(Class<T> interfaceClass,
                                 ICacheAdapter adapter) {
        return (T) Proxy.newProxyInstance(
            interfaceClass.getClassLoader(),
            new Class[]{ interfaceClass },
            new JDKInvocationHandler(adapter)
        );
    }
}

// JDKInvocationHandler.java — 真正的路由逻辑
public class JDKInvocationHandler implements InvocationHandler {
    private ICacheAdapter adapter;

    @Override
    public Object invoke(Object proxy, Method method, Object[] args)
            throws Throwable {
        // 反射调用适配器的同名方法
        return method.invoke(adapter, args);
    }
}

第四步：原来的 CacheServiceImpl 完全不改

// CacheServiceImpl.java — 已有代码，零修改
private ICacheAdapter cacheAdapter;

public String get(String key) {
    return cacheAdapter.get(key);  // 代理自动路由
}

public void set(String key, String value) {
    cacheAdapter.set(key, value);  // 不需要 redisType 参数
}

为什么这叫"工厂的工厂"

工厂方法创建的是产品（一个接口的多个实现）。
抽象工厂创建的是工厂——或者说，它解决的是"选择哪个适配器/代理"的问题。你传入不同的 ICacheAdapter，JDKProxy 就给你一个能路由到对应集群的代理对象。这个代理对象本身就是"被工厂创建出来的东西"，而创建它的 JDKProxy 就是那个"工厂的工厂"。

核心价值：已有代码零修改

类比：工厂方法像是给餐厅换厨师——你还是去同一个窗口点菜，但背后做菜的人变了。抽象工厂像是给整个厨房换了一套设备——炉灶、刀具、锅全换了，但窗口的服务方式不变，厨师甚至不知道设备已经换了。

抽象工厂最大的价值是：不修改现有代码，就能切换底层实现。CacheServiceImpl 完全不知道自己现在调的是 EGM 还是 IIR，这就是依赖倒置和开闭原则的体现。
