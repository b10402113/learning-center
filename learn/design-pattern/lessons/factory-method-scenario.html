工厂方法要解决的问题

工厂方法与抽象工厂

学习目标

认识工厂方法要解决的"一坨 ifelse"问题——用营销积分兑换的真实场景，看到 type 分发代码为什么越来越难维护。

场景：营销积分兑换

假设你在做一套营销系统，用户完成任务后可以获得积分，积分可以兑换不同类型的奖品：

  • 优惠券 — 调用第三方 sendCoupon(uId, couponNumber, uuid)，返回 CouponResult
  • 实物商品 — 调用第三方 deliverGoods(DeliverReq)，返回 Boolean
  • 爱奇艺兑换卡 — 调用第三方 grantToken(bindMobileNumber, cardId)，返回 void

三家第三方接口的入参不同、返回类型不同、调用方式也不同。而且业务还在增长，未来还会接入更多奖品类型。

ifelse 实现：能跑，但代价越来越大

最直觉的做法是在 Controller 里按 awardType 分发：

// PrizeController.java — ifelse 版本
public AwardRes awardToUser(AwardReq req) {
    if (req.getAwardType() == 1) {
        // 优惠券
        CouponResult result = couponService.sendCoupon(...);
        return mapCouponResult(result);
    } else if (req.getAwardType() == 2) {
        // 实物商品
        Boolean ok = goodsService.deliverGoods(...);
        return mapGoodsResult(ok);
    } else if (req.getAwardType() == 3) {
        // 爱奇艺兑换卡
        cardService.grantToken(...);
        return mapCardResult();
    }
    throw new RuntimeException("未知奖品类型");
}

这段代码能跑，测试也能过。但问题藏在"每来一个新需求"的时刻。

三个越来越痛的问题

问题 表现 为什么痛
开闭原则被打破 每加一种奖品，就要改 Controller 奖品逻辑和分发逻辑混在一起，改一处可能影响所有分支
单一职责被违反 一个方法里塞了三种完全不同的业务逻辑 优惠券的参数映射、商品的异常处理、兑换卡的调用方式全挤在一起
分支越堆越多 10 种奖品就是 10 个 if 块，每个块的参数和返回值都不一样 维护成本随分支数量线性增长，新人看不懂，老人不敢改
核心矛盾：分发逻辑（根据 type 选实现）和业务逻辑（每个奖品怎么发）纠缠在同一个方法里。你改优惠券的参数映射时，一不小心就碰到了商品的异常处理。

类比：餐厅的菜单

类比：想象一家餐厅，所有菜都由一个厨师做。客人点川菜、粤菜、日料，都找同一个人。短期没问题，但当菜系变多，这个厨师既要会颠勺又要会切刺身，效率和质量都会下降。工厂方法要解决的就是"让不同菜系各归各的厨师"。

工厂方法的直觉

工厂方法的核心思想其实很简单：

  1. 定义一个创建接口（比如 ICommodity.sendCommodity()）
  2. 每种产品各自实现（CouponCommodityService、GoodsCommodityService、CardCommodityService）
  3. 用工厂方法决定实例化哪个（StoreFactory.getCommodityService(type)）

调用方不再需要知道具体是哪种奖品，只需要调统一接口。新增奖品？加一个实现类，改一行工厂配置，Controller 不动。

工厂方法 = 把 new 具体类() 的决定从调用方挪到工厂，调用方只依赖接口。这就是"创建接口 + 子类决定实例化哪个产品"的本质。
