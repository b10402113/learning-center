享元模式的適用邊界與局限

design-pattern › flyweight › flyweight-tradeoffs

學習目標：能說出享元模式的優點（減接口調用、減內存佔用）、通用手法（Map + id 存取）與缺點（內部/外部狀態難區分時工廠易混亂），以及與原型模式的共通思想。

優點：什麼時候該用享元

享元模式的設計重點是享元工廠。它在以下場景下特別有用：

  • 服務端減少接口調用：像秒殺場景，活動信息固定不變，用享元工廠緩存後，十萬次查詢只需要一次真正的數據庫/接口調用
  • 客戶端減少內存佔用：遊戲地圖上的樹木、花草模型共用一份，幾千個實例只需要一個對象的內存
  • 減少 ifelse 判斷：用 Map + 固定 id 存取對象，替代一長串的 switch/if 判斷不同 id 對應不同行為

一句話總結：**在有大量重複對象可復用的場景下，享元模式通過共享降低成本**。

通用手法：Map + 固定 id

享元模式的核心手法其實非常簡單：用一個 Map 結構，以固定 id 為 key，存放和獲取對象。

這種手法不只在享元模式中出現。工廠模式、適配器模式、組合模式中也可以用 Map 結構存放服務供外部獲取，減少 ifelse 判斷。關鍵是「用固定 id 存取」這個思想，它是一種通用的設計技巧。

// 享元模式
Map<Long, Activity> activityMap;

// 工廠模式
Map<String, Commodity> commodityMap;

// 適配器模式
Map<String, MessageConverter> converterMap;

本質都是：同一個 id 對應同一個對象，避免重複創建或重複查找。

缺點：狀態難拆的坑

享元模式最大的風險是：複雜業務中不容易區分內部和外部狀態。

在秒殺場景中，內部狀態（活動名稱、時間）和外部狀態（庫存）的邊界很清晰。但在更複雜的場景中呢？比如：

  • 一個用戶的行為日誌，哪些是固定的（用戶ID、設備型號），哪些是變化的（操作時間、內容）？
  • 一個商品的SKU信息，價格算內部狀態還是外部狀態？（不同渠道價格不同……）
  • 一個訂單的狀態機，哪些狀態轉換是固定的，哪些取決於外部條件？

如果拆分不好，享元工廠會變得非常混亂——Map 裡的對象忽共享忽不共享，外部狀態到處傳，最後比原來的一坨代碼更難維護。

警示：享元模式的前提是「內部狀態和外部狀態能被清晰地拆分出來」。如果拆不清楚，寧可不用。

與原型模式的共通思想

享元模式和原型模式（Prototype Pattern）都屬於結構型模式，都指向一個共同的設計目標：減少重複構建的成本。

維度享元模式原型模式
核心手段共享不變對象克隆已有對象
適用場景大量相同對象，大部分數據不變對象創建成本高，但結構相似
外部依賴享元工廠（Map 緩存）Cloneable 接口
變化處理外部狀態分離出去克隆後再修改差異字段

原型模式是「複製一份再改」，享元模式是「不變的直接共享」。兩者解決的問題不同，但背後的思想相通：能不新建就不新建，能複用就複用。

什麼時候不該用

  • 狀態難拆分：如果內部和外部狀態的邊界模糊，享元工廠會變成一團亂麻
  • 對象數量不多：如果系統中只有幾個實例，共享帶來的收益微乎其微，反而增加了複雜度
  • 內部狀態也在變化：如果「不變的」數據其實會變，共享就失去了意義，還需要處理緩存失效的問題

小結

享元模式的優點是減少接口調用和內存佔用，通用手法是 Map + 固定 id 存取。缺點是內部/外部狀態難區分時工廠易混亂。與原型模式思想相通（減少重複構建成本），但手段不同（共享 vs 克隆）。適用的前提是狀態能被清晰拆分。
