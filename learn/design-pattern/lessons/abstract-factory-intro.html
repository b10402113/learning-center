抽象工廠是什麼？

design-pattern › abstract-factory › abstract-factory-intro

學習目標：說清抽象工廠「創建工廠的工廠」的概念，能區別它與工廠方法模式在結構上的差異，並點出典型適用場景。

先回顧：工廠方法在做什麼

上一節我們學了工廠方法模式——當一個接口有多種實現時，用一個工廠類把 new 的動作封裝起來，讓調用方不需要知道具體是哪個類被創建。

比如「發獎」場景：金幣、優惠券、實物，三種商品各有一個工廠。調用方只管說「我要發獎」，工廠負責決定具體 new 哪個對象。

但工廠方法有個隱含假設：每個工廠只創建一種產品。如果業務升級了，不只是一個產品有差異，而是「一整套產品族」都有多套實現呢？

什麼是「產品族」

想象你同時要兼容兩套 Redis 集群——EGM 集群和 IIR 集群。這不是一個產品的問題，而是一整套操作（get、set、del、setEx……）都有兩種不同的實現方式。方法名不一樣，參數格式不一樣，但做的事完全相同。

類似的場景在業務開發中非常常見：

產品族成員 A成員 B
Redis 集群EGM（gain / delete / setEx）IIR（get / set / setExpire）
作業系統Windows（\n\r 換行）Mac / Unix（\n 換行）
資料庫MySQL 語法PostgreSQL 語法

每一列就是一個「產品族」——多個類型不同的產品，但它們來自同一個供應源或同一套技術方案。

抽象工廠的核心思想

抽象工廠的意圖一句話：提供一個創建一系列相關或相互依賴對象的接口，而無需指定它們具體的類。

翻譯成白話：不是讓你 new 一個具體對象，而是讓你拿到一個「工廠」，這個工廠能產出一整套相關的產品。你只管跟工廠打交道，不用管背後是 EGM 還是 IIR。

區別於工廠方法：工廠方法是「一個工廠創建一個產品」；抽象工廠是「一個工廠創建一組產品」。抽象工廠本質上是「創建工廠的工廠」——它管理的不是單個對象，而是一整套兼容實現。

一個直觀的類比

想像你要裝修房子。有一種方式是你自己跑建材市場，分別去瓷磚店買瓷磚、去衛浴店買馬桶、去燈具店買燈——這就是「每個工廠創建一個產品」，你自己要跑好多家店。

另一種方式是找一個家裝公司，它會給你出「北歐風全套方案」或「工業風全套方案」——瓷磚、馬桶、燈具全部配套好，你不用分別挑選，只要選一個風格，整套方案就到手。這個家裝公司就是抽象工廠，它不只提供一個產品，而是一整套產品族。

典型適用場景

什麼時候該想到抽象工廠？滿足以下條件：

  1. 多套實現：同一個功能有兩套以上的實現（兩套 Redis、兩套支付、兩套作業系統）
  2. 成套切換：切換不是只換一個類，而是整套相關操作都要一起換
  3. 調用方不想知道細節：業務代碼只想調 get()、set()，不想知道背後是 EGM 還是 IIR

如果你的場景只涉及一個產品的多種實現（比如只有「發獎」一個動作有多種商品），那工廠方法就夠了。只有當你面對的是一整套產品族的多實現，才需要抽象工廠。

小結

抽象工廠的核心動機是管理一整套兼容實現。它比工廠方法管得更寬——不只管一個產品的創建，而是管一族相關產品的創建。下一節我們會進入 Redis 雙集群升級的真實場景，看看不用抽象工廠時，代碼會有多糟糕。
