驗證中介者架構的收益與設計原則

design-pattern › mediator › mediator-validation

學習目標：能用測試結果證明中介者屏蔽了 JDBC 複雜度，並說出它滿足的三個設計原則（單一職責、開閉、迪米特）。

用測試驗證：手寫 ORM 跑通了

上一課我們把五個組件串了起來。現在用兩條查詢驗證它真的能跑：

測試 1：selectOne — 查單條記錄

User user = session.selectOne(
    "org.itstack.demo.design.dao.IUserDao.queryUserInfoById", 1L);
// 輸出：User{id=1, name='水水', age=18}

業務方只傳了一個 statement 字符串和一個 ID，框架內部自動完成：解析 XML → 準備 SQL → 執行查詢 → 反射映射成 User 對象。跟用 Mybatis 的體驗完全一致。

測試 2：selectList — 查集合

List<User> users = session.selectList(
    "org.itstack.demo.design.dao.IUserDao.queryUserInfoById", req);
// 輸出：[User{id=1, name='豆豆', age=18}, User{id=2, name='水水', age=18}]

帶參數的集合查詢也跑通了。說明 #{id} 占位符替換、參數綁定、結果集遍歷全部正常。

對比一把梭的收益

一把梭 JDBC中介者 ORM
業務代碼四步 JDBC 全寫一行 selectOne/selectList
連接管理自己寫 Class.forName + getConnectionBuilder 啟動時處理，業務方無感
SQL 定義硬編碼在 Java 裡XML 配置文件，改 SQL 不改 Java
結果映射while(resultSet.next()) 手動取值反射自動映射成 POJO
擴展性改一個查詢動整個類加一個 XML + POJO 就行

它滿足了哪些設計原則？

1. 單一職責原則（SRP）

每個組件只做一件事：

  • SqlSession → 只管查詢和結果返回
  • SqlSessionFactory → 只管打開會話
  • SqlSessionFactoryBuilder → 只管啟動構建
  • Configuration → 只管存配置

改 XML 解析邏輯？只動 Builder。改結果映射？只動 DefaultSqlSession。互不干擾。

2. 開閉原則（OCP）

新增一種查詢（比如 School）不需要改任何中介者組件的代碼：

  1. 加一個 School POJO
  2. 加一個 School_Mapper.xml（定義 SQL 和映射）
  3. 在 mybatis-config-datasource.xml 的 mappers 裡加一行引用

對擴展開放（加 XML + POJO），對修改封閉（不改 Java 類）。

3. 迪米特原則（LoD）

「越少人知道越好」——業務方只需要知道 SqlSession 的 selectOne / selectList，不需要知道：

  • 連接怎麼建立的
  • SQL 占位符怎麼替換的
  • ResultSet 怎麼映射成對象的

這些細節全部由中介者組件「合作服務平台」處理。業務方跟 JDBC 的距離被拉到了最遠。

不只是 ORM——中介者的更廣場景

中介者模式不只用在 ORM。想想公司裡的「獎品中心中台」：

  • 公司有 10 種獎品服務（金幣、優惠券、實物、積分……）
  • 如果每個業務方都直接對接 10 個服務，依賴就是 10×N 的網狀
  • 把 10 個服務統一收進「獎品中心」，業務方只跟獎品中心通信
  • 獎品中心就是中介者——屏蔽底層差異，對外提供統一接口

判斷標準：對象交互複雜、重複調用多、需要統一入口——就該考慮中介者。

小結

手寫 ORM 跑通查詢，證明中介者模式真的屏蔽了 JDBC 複雜度。從設計原則看，它滿足單一職責、開閉原則、迪米特原則。從場景看，中介者不只用在 ORM，任何「N 個服務需要統一包裝」的地方都適用。面試遇到「中介者模式」，你現在能講出意圖（集中協調）、場景（ORM / 中台）、結構（五個組件）和原則（SRP + OCP + LoD）了。
