優惠券場景的策略模式重構

design-pattern › strategy › strategy-refactor

學習目標：能走完「接口 → 四種券實現 → Context 控制類」的完整重構路徑，說出每個組件的職責。

回顧：那一坨 ifelse 代碼

上一節我們看到了優惠券計算的 ifelse 版本——一個方法裡塞了四種券的邏輯，參數髒、難擴展、難測試。現在，我們用策略模式把它重構一遍。

重構的核心思路：把每種券的計算邏輯抽成獨立的類，通過一個統一的接口讓它們互換。結構分三層：

組件角色類比
策略接口定義「算優惠」的統一契約錦囊的封面：寫著「拆開就能算折扣」
具體策略實現每種券一個類，各自封裝計算規則四個錦囊，各自裝不同的計算法
上下文控制類持有策略、統一入口錦囊的持有者：按需取出、統一調用

第一步：定義策略接口 ICouponDiscount

先抽一個泛型接口，聲明唯一的計算方法：

public interface ICouponDiscount<T> {
    /**
     * 計算折扣後的金額
     * @param couponInfo 券的折扣信息（不同券型結構不同）
     * @param skuPrice  商品原價
     * @return 折扣後金額
     */
    BigDecimal discountAmount(T couponInfo, BigDecimal skuPrice);
}

為什麼用泛型？因為不同券型的參數結構完全不同：

  • 直減、折扣、n 元購：券參數就是一個數字（Double）
  • 滿減：券參數是一個 Map，包含「滿多少」和「減多少」兩個值

泛型讓接口保持一個方法的簡潔，同時允許每種券用自己的參數類型。這是策略模式的關鍵一步：把可變的算法固定為統一接口，客戶端面向接口編程。

第二步：四種券各自的策略實現

每個券型一個類，各自實現自己的計算邏輯：

直減 ZJCouponDiscount

public class ZJCouponDiscount implements ICouponDiscount<Double> {
    @Override
    public BigDecimal discountAmount(Double couponInfo, BigDecimal skuPrice) {
        // 商品價 - 優惠價，最低支付 1 元
        BigDecimal subtract = skuPrice.subtract(new BigDecimal(couponInfo));
        return subtract.compareTo(BigDecimal.ONE) < 0 ? BigDecimal.ONE : subtract;
    }
}

滿減 MJCouponDiscount

public class MJCouponDiscount implements ICouponDiscount<Map<String, String>> {
    @Override
    public BigDecimal discountAmount(Map<String, String> couponInfo, BigDecimal skuPrice) {
        BigDecimal x = new BigDecimal(couponInfo.get("x"));  // 滿多少
        BigDecimal n = new BigDecimal(couponInfo.get("n"));  // 減多少
        if (skuPrice.compareTo(x) < 0) return skuPrice;    // 未達門檻，原價
        BigDecimal subtract = skuPrice.subtract(n);
        return subtract.compareTo(BigDecimal.ONE) < 0 ? BigDecimal.ONE : subtract;
    }
}

折扣 ZKCouponDiscount

public class ZKCouponDiscount implements ICouponDiscount<Double> {
    @Override
    public BigDecimal discountAmount(Double couponInfo, BigDecimal skuPrice) {
        // skuPrice × 折扣比例，保留兩位小數
        BigDecimal discount = skuPrice.multiply(new BigDecimal(couponInfo))
            .setScale(2, RoundingMode.HALF_UP);
        return discount.compareTo(BigDecimal.ONE) < 0 ? BigDecimal.ONE : discount;
    }
}

n 元購 NYGCouponDiscount

public class NYGCouponDiscount implements ICouponDiscount<Double> {
    @Override
    public BigDecimal discountAmount(Double couponInfo, BigDecimal skuPrice) {
        // 無論原價多少，都按固定金額購買
        return new BigDecimal(couponInfo);
    }
}
好處：每個類只關心自己的計算邏輯。滿減不用知道折扣的存在，n 元購不用理解「滿多少」的門檻。加新券型？新增一個類就行，不動任何已有代碼。

第三步：策略控制類 Context

客戶端不想直接面對四個具體策略類。我們需要一個統一入口：

public class Context<T> {
    private ICouponDiscount<T> couponDiscount;

    // 構造器注入：傳入哪個策略，就用哪個算法
    public Context(ICouponDiscount<T> couponDiscount) {
        this.couponDiscount = couponDiscount;
    }

    public BigDecimal discountAmount(T couponInfo, BigDecimal skuPrice) {
        return couponDiscount.discountAmount(couponInfo, skuPrice);
    }
}

Context 的設計要點：

  • 構造器注入：傳入哪個策略實現，Context 就用哪個算法——「可替換」從這裡來
  • 統一入口：客戶端只調 context.discountAmount()，不關心具體是哪種券
  • 可配置化：可以把各策略包裝成 Map 結構，按券型名稱取用，實現「服務配置化」

測試驗證：結果等價嗎？

重構的黃金標準：功能不變。用四組測試驗證——原價 100 元的四種券，折後都應該是 90 元：

券型券參數商品原價折後金額
直減10（減 10 元）10090
滿減滿 100 減 1010090
折扣0.9（9 折）10090.00
n 元購90（90 元購）10090

四種券在原價 100 元上折扣 10 元，最終支付 90 元——和 ifelse 版本的結果完全一致。重構沒有破壞任何功能，但代碼結構已經從「一個方法塞四種邏輯」變成「四個獨立類 + 一個統一入口」。

小結

整個重構路徑：接口定義契約 → 每種券一個實現類 → Context 控制類統一入口。三步走完，ifelse 被拆乾淨了。新增券型？寫一個新實現類，注入 Context 就行——不動已有代碼，不動已有測試。這就是策略模式「算法可互換」的落地方式。
