外观模式：用一层门面降低调用方复杂度

结构型

这一课的目标

读完之后，你能用外观模式把跨切面关注点（白名单、切量、灰度）包装成可复用的中间件，并识别出 SpringBoot starter 中的外观结构。

场景：每个接口都要做白名单检查

你有一个 SpringBoot 应用，里面有好几个 API 接口。每次上线都要做白名单切量——只有白名单里的用户才能访问新版本。

Controller A
→
白名单检查
+ 降级 JSON
→
业务逻辑
Controller B
→
白名单检查
+ 降级 JSON
→
业务逻辑
Controller C
→
白名单检查
+ 降级 JSON
→
业务逻辑

每个 Controller 都要写一遍白名单逻辑——重复、散落、难维护。

一坨代码：每个 Controller 里都粘一遍

最直觉的做法：在每个 Controller 方法开头复制粘贴白名单检查代码。

@RestController
public class UserController {

    // 白名单 — 每个接口都要写一遍
    private static final List<String> WHITE_LIST = Arrays.asList("uid-001", "uid-002");

    @GetMapping("/queryUserInfo")
    public String queryUserInfo(String uid) {
        // ⬇️ 这段代码在每个 Controller 里都重复
        if (!WHITE_LIST.contains(uid)) {
            return "{\"code\":\"9999\",\"info\":\"不在白名单内，拒绝访问\"}";
        }
        // ⬇️ 真正的业务逻辑
        return userService.queryUserInfo(uid);
    }
}

@RestController
public class OrderController {

    private static final List<String> WHITE_LIST = Arrays.asList("uid-001", "uid-002");

    @GetMapping("/queryOrder")
    public String queryOrder(String uid) {
        if (!WHITE_LIST.contains(uid)) {
            return "{\"code\":\"9999\",\"info\":\"不在白名单内，拒绝访问\"}";
        }
        return orderService.queryOrder(uid);
    }
}

问题：白名单逻辑散落在每个接口里，改一次要改 N 个地方。更别说以后还要加限流、日志、灰度……

外观重构：自定义 SpringBoot Starter

核心思路：把白名单检查包装成一个可复用的中间件，业务代码只需要加一个注解。

1. 自定义注解 @DoDoor(key="uid", returnJson="{...}")
标记哪些接口需要白名单检查
2. AOP 切面 DoJoinPoint 拦截所有带 @DoDoor 的方法，提取参数，比对白名单
3. 配置绑定 StarterServiceProperties 读取 yml 里的白名单配置
4. 自动装配 StarterAutoConfigure 条件注册 Bean，启动时自动生效 
// 业务代码 — 干干净净，只加一个注解
@RestController
public class UserController {

    @DoDoor(key = "uid", returnJson = "{\"code\":\"9999\",\"info\":\"不在白名单内\"}")
    @GetMapping("/queryUserInfo")
    public String queryUserInfo(String uid) {
        return userService.queryUserInfo(uid); // 业务逻辑一行不改
    }
}

@RestController
public class OrderController {

    @DoDoor(key = "uid", returnJson = "{\"code\":\"9999\",\"info\":\"不在白名单内\"}")
    @GetMapping("/queryOrder")
    public String queryOrder(String uid) {
        return orderService.queryOrder(uid); // 业务逻辑一行不改
    }
}

白名单检查的逻辑在哪里？在 AOP 切面里，只写一次：

@Aspect
@Component
public class DoJoinPoint {

    @Autowired
    private StarterService starterService;

    @Around("@annotation(doDoor)")
    public Object around(ProceedingJoinPoint point, DoDoor doDoor) throws Throwable {
        // 1. 从方法参数中提取 uid
        String uid = extractUid(point, doDoor.key());

        // 2. 查询白名单
        if (!starterService.isWhiteUser(uid)) {
            // 3. 不在白名单 → 直接返回降级 JSON
            return doDoor.returnJson();
        }

        // 4. 在白名单 → 放行
        return point.proceed();
    }
}

外观的架构

Controller A
Controller B
Controller C
↓
外观层：@DoDoor + AOP 切面
白名单检查 · 降级 JSON · 配置管理
↓
业务逻辑

调用方（Controller）只看到一个注解，不关心白名单怎么查、降级 JSON 怎么返回。所有横切关注点都被外观层统一管理。

外观 vs 适配器

外观适配器
包的是什么一整个子系统（多个类/服务）一个不兼容的接口
动机简化调用路径翻译接口形态
典型场景中间件、starter、统一入口对接多个第三方 API

关键洞察

🔍 中间件的本质就是外观
白名单、切量、灰度、限流、日志——这些都是跨切面的关注点，业务代码不该知道它们的存在。外观模式把这些逻辑包装成一个统一入口（注解/AOP/starter），让业务代码保持干净。

⚠️ 过度使用会反设计
如果一个外观只是简单转发，没有真正简化复杂度，那就没必要加。判断标准：调用方省掉的代码量是否值得多加一层。

关键取舍

优点代价
业务代码干净，只加注解 增加了一个中间层
跨切面逻辑只写一次，复用性强 调试时多一层跳转
符合开闭原则——新接口加注解即可 过度使用会导致反设计/过渡设计

本课小结

  1. 外观解决的问题：调用方太复杂（背后子系统太多，调用方不该知道这些细节）
  2. 核心思路：加一层门面，把跨切面的逻辑包装成统一入口
  3. 典型实现：自定义 SpringBoot Starter（注解 + AOP + 自动装配）
  4. 中间件的本质就是外观——白名单、切量、灰度、限流都是外观
  5. 判断是否该用外观：调用方省掉的代码量是否值得多加一层
