橋接模式的結構與核心機制

學習目標

掌握橋接模式「抽象類 × 介面、構造注入」的結構，理解「橋」是什麼、為什麼能讓兩個維度獨立變化。

從上一節的問題出發

上一節看到，微信/支付寶 × 密碼/刷臉/指紋的組合用 ifelse 寫，分支數是維度的乘積。解決思路是把兩個維度「拆開」——但怎麼拆？

兩棵繼承樹

橋接模式的核心思路是：把系統中兩個獨立變化的維度，拆成兩棵平行的繼承樹，然後用「組合」把它們連起來。

在我們的支付場景中：

維度角色結構
支付渠道（抽象部分）Pay 抽象類WxPay、ZfbPay 繼承 Pay
支付模式（實現部分）IPayMode 介面PayCypher、PayFaceMode、PayFingerprintMode 實作 IPayMode

「橋」是什麼？

關鍵在於：Pay 抽象類裡面持有一個 IPayMode 的引用，並且通過構造函數傳入。

public abstract class Pay {
    // 這就是「橋」——抽象類持有實現介面的引用
    protected IPayMode payMode;

    public Pay(IPayMode payMode) {
        this.payMode = payMode;
    }

    // 抽象方法：由子類實現具體渠道的轉賬邏輯
    public abstract String transfer(String uId, String tradeId, int amount);
}

這行 protected IPayMode payMode 就是整個模式的核心——它是一座「橋」，連接了抽象部分（支付渠道）和實現部分（支付模式）。

橋的本質：抽象類 A 中持有一個介面 B 的引用，通過構造函數注入 B 的實現。A 的子類負責「渠道」邏輯，B 的實現類負責「模式」邏輯。兩者各自變化，互不干擾。

為什麼叫「橋接」？

想像兩座獨立的大樓：左邊是「支付渠道大樓」（微信、支付寶），右邊是「支付模式大樓」（密碼、刷臉、指紋）。兩座大樓之間有一座橋——就是那個 IPayMode payMode 字段。

從渠道大樓出發，過橋，就能到達任何一個模式房間。從模式大樓出發，也能被任何一個渠道房間呼叫。兩邊各自蓋新樓（新增渠道或模式），橋不需要改。

目錄結構對比

橋接模式重構前後，工程的目錄結構會發生明顯變化：

PayController.java
所有邏輯堆在一個類 		channel/Pay.java（抽象類）
channel/WxPay.java

mode/IPayMode.java（介面）

從一個類變成兩個包、七個文件。看似「變複雜了」，但每個文件只負責一件事。新增渠道？只動 channel/。新增模式？只動 mode/。互不影響。

核心機制回顧

  • 抽象類 A（Pay）：定義抽象的業務行為（transfer），持有介面 B 的引用
  • 介面 B（IPayMode）：定義實現維度的行為（security）
  • 橋：A 中的 protected B b 字段 + 構造函數注入
  • 擴展方式：A 的子類只管渠道邏輯，B 的實現只管模式邏輯，組合在客戶端完成
一句話記法：橋接 = 抽象類裡放一個介面字段，構造函數傳進來，兩棵樹各長各的，橋不動。

適用場景的一般化

橋接模式不限於支付場景。凡是存在「兩個獨立維度需要自由組合」的場景，都可以用橋接：

  • JDBC：驅動程式（Driver）是抽象，數據庫（MySQL/Oracle）是實現
  • 同品牌產品線：台式機 vs 筆記本（產品類型）× 高端 vs 低端（市場定位）
  • 消息推送：推送渠道（App/短信/郵件）× 消息格式（文本/圖片/富文本）

如果組合中每個類都各自實現所有服務，就會出現笛卡爾積；用橋接模式，就只需要各自擴展再「橋接」。
