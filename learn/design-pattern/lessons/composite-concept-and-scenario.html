組合模式的思路與決策樹場景

設計模式 · 節點 17 · 步驟 1/3

這節課你要學會什麼

讀完這篇文章，你能說出組合模式「把相似邏輯組合成樹形結構、統一調用」的核心思想，並理解規則決策樹場景中 ifelse 直寫為什麼會失控。

你已經見過的痛

回想一下：一個 `process` 方法裡，外層按性別判斷，內層按年齡判斷，四個分支四個結果。需求方說「再加一個地區維度」——原本四個分支變成八個，再加一個「職業」維度就十六個。每次加維度，行數不是線性成長，而是指數膨脹。

更痛的是，需求方某天說「把年齡的分界線從 25 歲改成 30 歲」。你得在一堆 ifelse 裡找到對的位置改數字，改完還要擔心沒把其他分支的魔法值一起改。這種「值粘錯位置」的 bug，在真實專案裡就是客訴的來源。

一個真實場景：營銷規則決策樹

假設你在做一個營銷系統：根據用戶的性別和年齡，發放不同類型的優惠券。

性別年齡發放結果場景說明
男< 25果實 A年輕男性 → 遊戲類優惠券
男≥ 25果實 B資深男性 → 健康養生類優惠券
女< 25果實 C年輕女性 → 美妝類優惠券
女≥ 25果實 D資深女性 → 母嬰類優惠券

這棵決策樹的形態是性別 → 年齡 → 發券結果，每一層都是一次「分流」。你的同事可能很直覺地用 ifelse 寫出來：

public String process(String userSex, int userAge) {
    if ("man".equals(userSex)) {
        if (userAge < 25) {
            return "果實A"; // 遊戲類
        } else {
            return "果實B"; // 養生類
        }
    } else {
        if (userAge < 25) {
            return "果實C"; // 美妝類
        } else {
            return "果實D"; // 母嬰類
        }
    }
}

這段代碼能跑，新人也能看懂。但它有兩個致命問題：

  1. 每加一個維度，分支數量翻倍。加一個「地區」維度（一線/二線/三線），四個分支變成十二個。再加一個「職業」維度，二十四個。擴展性災難。
  2. 業務邏輯和判斷結構綁死。改一個分界線（25→30），要在所有相關分支裡找對應的魔法值。漏改一個就是 bug。

組合模式的解決思路

組合模式（Composite Pattern）的核心想法：把相似的邏輯節點（比如「性別判斷」「年齡判斷」）組合成一棵樹，對外提供統一的服務。

翻譯成日常經驗：

螺絲和螺母——每個螺絲是獨立的零件，每個螺母也是。但它們可以通過「螺紋鏈接」組合成不同結構：兩個螺絲串起來是一種結構，三個螺絲並排又是一種。重要的不是螺絲本身，而是它們按什麼關係組織在一起。

回到營銷場景：「性別判斷」是一個邏輯節點，「年齡判斷」是另一個。它們各自獨立，但可以按不同方式組合成不同的決策樹。調用方只需要說「用這棵樹做決策」，不需要關心樹裡面的判斷邏輯是什麼。

ifelse vs 組合模式：對比一覽

維度ifelse 直寫組合模式
新增判斷維度加一層 ifelse，行數翻倍新增一個過濾器節點，組進樹裡
改業務規則在 ifelse 裡找魔法值改改節點的配置參數
不同場景用不同規則複製一份代碼改參數用不同 treeId 指向不同樹
可配置性硬編碼在程式碼裡可存入資料庫、可圖形化配置
符合開閉原則❌ 每次都改現有代碼✅ 新增節點不改既有結構

最後一行是關鍵：開閉原則（Open-Closed Principle）——對擴展開放，對修改關閉。組合模式的樹結構一旦建好，新增判斷邏輯只需要加一個新的過濾器節點，不需要改動現有的樹結構或引擎代碼。而 ifelse 每次都是「改現有代碼」，完全違反開閉。

判別特徵

以後遇到類似場景，如果同時符合以下三個特徵，可以考慮組合模式：

  1. 同質邏輯：有多個相似的判斷/處理節點（性別、年齡、地區……都是「根據某個屬性做分流」）
  2. 不同組合：這些節點可以按不同方式串接成不同的決策路徑
  3. 統一調用：調用方不想關心內部結構，只想說「幫我做決策」

小結

組合模式的核心是把相似邏輯組合成樹形結構，對外統一服務。本節用營銷決策樹場景展示了 ifelse 直寫的擴展性災難——每加一個維度就指數膨脹，改規則要改程式碼。組合模式讓你把判斷邏輯拆成獨立節點、按需組合成樹，既符合開閉原則，又支持動態配置。下一節會拆解組合模式的四個角色：節點、鏈路、果實、過濾器，以及引擎是怎麼從根遍歷到果實的。
