秒殺場景重構：享元工廠 + Redis + 控制類的完整實現

design-pattern › flyweight › flyweight-implementation

學習目標：掌握享元模式在秒殺場景的完整重構：ActivityFactory（Map 緩存內部狀態）、RedisUtils（外部狀態）、ActivityController（組裝返回）的職責分離與協作。

重構前的工程結構

重構前只有一個類——ActivityController，所有查詢邏輯都塞在裡面：

itstack-demo-design-11-01/
└── org.itstack.demo.design/
    └── ActivityController.java  ← 全部邏輯在這裡
壞味道：一個類承擔全部職責——數據構建、查詢、返回，所有事情都在一個方法裡完成。

重構後的工程結構

享元模式重構後，職責開始分離：

itstack-demo-design-11-02/
├── util/
│   └── RedisUtils.java          ← 模擬 Redis（外部狀態來源）
└── org.itstack.demo.design/
    ├── Activity.java            ← 活動實體（內部狀態載體）
    ├── ActivityController.java  ← 控制類（組裝返回）
    ├── ActivityFactory.java     ← 享元工廠（緩存內部狀態）
    └── Stock.java               ← 庫存實體（外部狀態載體）

從單類到多類，每個類的職責清晰分離。

逐個拆解

1. 活動實體——內部狀態的載體

Activity 類承載活動的基礎信息：id、name、desc、startTime、stopTime、stock。這是享元要共享的「固定內容」載體。

public class Activity {
    private Long id;
    private String name;
    private String desc;
    private String startTime;
    private String stopTime;
    private Stock stock;
    // getter/setter ...
}

2. 庫存實體——外部狀態的載體

Stock 單獨成類，保存會變化的庫存數據：

public class Stock {
    private int total;   // 總量
    private int used;    // 已用
    // getter/setter ...
}

把變化數據從固定數據中剝離出來——這是享元建模的第一步。

3. 享元工廠——核心機制

ActivityFactory 是享元模式的靈魂：

public class ActivityFactory {
    private static Map<Long, Activity> activityMap = new HashMap<>();

    public static Activity getActivity(Long id) {
        Activity activity = activityMap.get(id);
        if (activity == null) {
            activity = new Activity();
            activity.setId(10001L);
            activity.setName("圖書嗨樂");
            activity.setDesc("圖書優惠券分享激勵分享活動第二期");
            activity.setStartTime("2024-06-01");
            activity.setStopTime("2024-06-30");
            activityMap.put(id, activity);
        }
        return activity;
    }
}

核心機制一句話：用一個固定 id 存放和獲取對象。第一次查詢創建並緩存，第二次及以後直接從 Map 取。在分佈式場景下，這個 Map 可以替換為 Redis——數據放 Redis 中，按需選擇。

4. 模擬 Redis——外部狀態來源

RedisUtils 用定時任務模擬庫存消耗：

public class RedisUtils {
    private AtomicInteger stock = new AtomicInteger(0);
    private ScheduledExecutorService scheduler = Executors.newSingleThreadScheduledExecutor();

    public RedisUtils() {
        // 每 100000 微秒（0.1 秒）庫存 +1，模擬消耗
        scheduler.scheduleAtFixedRate(() -> stock.addAndGet(1), 0, 100000, TimeUnit.MICROSECONDS);
    }

    public int getStockUsed() {
        return stock.get();
    }
}

AtomicInteger 保證並發自增安全，定時任務讓庫存在使用中持續變化。

5. 控制類——組裝內部 + 外部

ActivityController 是最終的入口：

public class ActivityController {
    private RedisUtils redisUtils = new RedisUtils();

    public Activity queryActivityInfo(Long id) {
        // 內部狀態：從享元工廠取（不變）
        Activity activity = ActivityFactory.getActivity(id);
        // 外部狀態：從 Redis 取（會變）
        activity.setStock(new Stock(1000, redisUtils.getStockUsed()));
        return activity;
    }
}

控制類的職責：工廠負責內部狀態複用，控制類負責疊加外部狀態。固定信息從工廠拿、變化信息從 Redis 拿，最後組裝返回。

    Thread.sleep(1200);

整體協作流程

把整個流程串起來：

  1. 調用方查詢 queryActivityInfo(10001L)
  2. ActivityFactory.getActivity(10001L)：查 Map，未命中則創建並緩存（內部狀態）
  3. RedisUtils.getStockUsed()：從模擬 Redis 獲取當前已用庫存（外部狀態）
  4. ActivityController 將庫存回填到 Activity，返回完整的活動信息

對比重構前：重構前每次查詢都從零構建 Activity；重構後，ActivityFactory 只在第一次創建，後續九次直接複用。固定信息零冗餘，變化信息實時獲取。

小結

享元模式的完整實現包含四個角色：Activity（內部狀態載體）、Stock（外部狀態載體）、ActivityFactory（享元工廠，Map 緩存）、ActivityController（控制類，組裝返回）。核心機制是「Map + 固定 id 存取對象」。下一課我們會分析這個模式的適用邊界與局限。
