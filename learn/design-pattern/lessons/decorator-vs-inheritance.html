为什么不用继承而用装饰器

结构型

本课目标
对比继承扩展与装饰器扩展的取舍，理解开闭原则在运行时的体现。

回到 SSO 拦截器的场景

上一课我们用装饰器给 SSO 拦截器加了方法级权限。但如果用继承呢？

继承方案 LoginSsoInterceptor extends SsoInterceptor

问题：每加一个功能就要一个子类。
权限检查 → 1 个子类
日志审计 → 又 1 个子类
限流 → 再 1 个子类
权限+日志+限流 → 又 1 个子类
子类爆炸！
装饰器方案 LoginSsoDecorator wraps SsoInterceptor

每个功能是一个独立的装饰器，自由组合：
权限 → 1 个装饰器
日志 → 1 个装饰器
限流 → 1 个装饰器
权限+日志+限流 → 套娃组合
按需组合，不爆炸

继承的三个致命问题

1. 编译时固定，运行时不能改

// 继承：编译时就决定了行为
SsoInterceptor sso = new LoginSsoInterceptor();  // 永远是登录+权限
// 想加日志？对不起，换一个子类重新 new
SsoInterceptor sso2 = new LoginAuditSsoInterceptor();

继承在编译时就锁定了功能组合。运行时想换组合？做不到。

2. 子类爆炸（组合爆炸）

如果有 M 个功能要扩展，用继承需要多少个子类？

功能组合需要的子类数
权限1
日志1
限流1
权限 + 日志1
权限 + 限流1
日志 + 限流1
权限 + 日志 + 限流1
合计7 = 2³ - 1

M 个功能需要 2M - 1 个子类。3 个功能就要 7 个类，5 个功能就要 31 个——典型的组合爆炸。

3. 违反开闭原则

开闭原则说：对扩展开放，对修改关闭。继承扩展看似满足，但每加一个功能就要创建新子类，而且子类之间可能有重复代码（每个子类都要重写 preHandle）。更麻烦的是，如果父类改了签名，所有子类都要改。

装饰器的三个优势

1. 运行时动态组合

// 装饰器：运行时自由组合
SsoInterceptor sso = new SsoInterceptor();              // 原始
sso = new LoginSsoDecorator(sso);                       // 加权限
sso = new AuditSsoDecorator(sso);                       // 再加日志
sso = new RateLimitSsoDecorator(sso);                   // 再加限流

// 运行时根据配置决定组合
if (config.isAuditEnabled()) {
    sso = new AuditSsoDecorator(sso);
}

装饰器在运行时通过构造函数组合，想加就加，想换就换。

2. 每个功能一个类，线性增长

功能需要的装饰器数
权限1
日志1
限流1
合计3 = M

M 个功能只需要 M 个装饰器类。线性增长，不爆炸。

3. 完美满足开闭原则

加新功能？写一个新的 ConcreteDecorator，不改原始类，不改已有装饰器。调用方按需组合。对扩展开放（新装饰器），对修改关闭（原始类不动）。

什么时候继承比装饰器好？

取舍判断 如果功能扩展是固定的、不会变的，用继承更简单直接。比如一个 abstract class 定义骨架，子类只实现固定数量的变体——这是模板方法模式的场景。

如果功能扩展是动态的、需要运行时组合的，用装饰器。比如 JDK I/O 的流组合、SSO 拦截器的多层扩展。

关键洞察

核心对比 继承是编译时的功能绑定，装饰器是运行时的功能组合。继承适合固定变体，装饰器适合动态组合。子类爆炸是继承扩展的信号——看到这个信号，考虑装饰器。

本课小结

  1. 继承的三个问题：编译时固定、子类爆炸（2M-1）、违反开闭原则
  2. 装饰器的三个优势：运行时动态组合、线性增长（M 个类）、完美满足开闭原则
  3. 取舍：固定变体用继承，动态组合用装饰器
  4. 看到子类爆炸的信号，考虑装饰器
