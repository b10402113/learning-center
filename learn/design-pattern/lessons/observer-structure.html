Lesson 3/3 · 觀察者模式

觀察者模式的三層結構

Node: observer · Step 3/3 · 行為模式

學習目標

掌握 EventListener + EventManager + 業務抽象類的三層結構，能對比前後代碼說出解耦收益與使用邊界。

重構後的地圖

上一課看到一把梭把簡訊和 MQ 全塞進 doDraw 方法。現在用觀察者模式重構，代碼分成三層：

層組件職責
第一層：事件監聽EventListener 接口 + 具體監聽器定義「收到通知後做什麼」
第二層：事件管理EventManager管理訂閱/取消/通知，按事件類型分組
第三層：業務流程LotteryService 抽象類 + LotteryServiceImpl核心業務邏輯，通知細節對調用方隱藏

這三層各司其職，下面逐層拆解。

第一層：EventListener 接口

觀察者的統一契約：所有監聽器都實現同一個接口。

public interface EventListener {
    void doEvent(LotteryResult result);
}

一個方法、一個參數、一個返回值。任何想「聽」搖號結果的輔助流程，只需實現這個接口。

具體實現很簡單：

  • MessageEventListener：收到結果後打印「給用戶 uId 發送簡訊通知」
  • MQEventListener：收到結果後打印「記錄用戶 uId 搖號結果(MQ)」

每個監聽器只做一件事，職責單一。真實場景會調用外部接口（簡訊 SDK、MQ Producer），這裡用 logger 模擬。

第二層：EventManager 事件管理器

事件管理器是一對多通知的中樞。它用 Map<Enum<EventType>, List<EventListener>> 按事件類型分組存放監聽器，提供三個方法：

方法作用類比
subscribe(type, listener)把監聽器加入對應類型的列表信號兵報到
unsubscribe(type, listener)從列表移除監聽器信號兵退伍
notify(type, result)遍歷該類型的所有監聽器，逐個調用 doEvent槍聲響了，所有人都聽到

用枚舉 EventType.MQ 和 EventType.Message 限定事件類型，防止外部亂傳。新增事件類型只需在枚舉裡加一個值。

第三層：業務抽象類 LotteryService

這是解耦的關鍵。把 LotteryService 改成抽象類，用模板方法（Template Method）的思想編排流程：

public abstract class LotteryService {
    private final EventManager eventManager;

    protected LotteryService(EventManager eventManager) {
        this.eventManager = eventManager;
    }

    // 對外暴露的統一入口
    public LotteryResult draw(String uId) {
        // 1. 子類實現核心流程
        LotteryResult result = doDraw(uId);
        // 2. 基類統一觸發通知
        eventManager.notify(EventType.MQ, result);
        eventManager.notify(EventType.Message, result);
        return result;
    }

    // 子類只實現核心邏輯
    protected abstract LotteryResult doDraw(String uId);
}

draw 是公開方法，先調子類的 doDraw 拿結果，再觸發通知。doDraw 是抽象方法，由繼承者實現核心搖號邏輯。

業務實現類 LotteryServiceImpl 只需重寫 doDraw：

public class LotteryServiceImpl extends LotteryService {
    private final MinibusTargetService minibusTargetService;

    @Override
    protected LotteryResult doDraw(String uId) {
        String lottery = minibusTargetService.lottery(uId);
        return new LotteryResult(uId, lottery, new Date());
    }
}

核心方法裡已經沒有任何簡訊或 MQ 的代碼——輔助流程全部交給事件管理器處理。

重構後的對比

測試用相同的 uId 調用 draw，輸出結果跟一把梭完全一致——簡訊通知照發、MQ 記錄照寫。但代碼結構天差地別：

一把梭觀察者模式
doDraw / draw 方法三段邏輯混在一起只有一行核心調用
新增通知改核心方法新增監聽器類 + subscribe
刪除通知從核心方法刪代碼移除 subscribe 調用
核心方法行數5+ 行（含輔助邏輯）1-2 行（純核心）
調用方感知知道所有輔助流程只看到 draw，不知道通知存在

開閉原則的實踐

觀察者模式結構上滿足開閉原則（Open/Closed Principle）：對擴展開放、對修改封閉。

  • 擴展：新增一種通知（比如郵件），只需新增一個 EventListener 實現類，在 EventManager 裡 subscribe 即可
  • 封閉：不需要修改 LotteryService、LotteryServiceImpl、EventManager 的任何現有代碼

這就是觀察者模式的價值：輔助流程的增減，完全不影響核心業務。

使用邊界——什麼時候不該用？

觀察者模式不是萬能的，有兩個已知的限制：

限制具體表現應對
難控調用順序多個監聽器的通知順序取決於 subscribe 的先後，不保證業務需要的順序用優先級或有序列表控制
結果回傳受限通知是單向的，觀察者處理完後很難把結果回傳給被觀察者如果需要回傳，考慮回調或 Promise

任何設計模式都不是單獨使用的，需要結合其他模式共同建設。引入模式是為了更易擴展和維護，不能反而把結構搞複雜、難維護。

一句話記住

觀察者模式 = EventListener（做什麼） + EventManager（怎麼通知） + 業務抽象類（只管核心）。

自我檢測

Q1. 觀察者模式的三層結構分別是什麼？

  • EventListener + EventManager + 業務抽象類
  • Subject + Observer + Publisher
  • Strategy + Context + Factory
  • Command + Invoker + Receiver

Q2. 在 LotteryService 抽象類中，draw 方法做了什麼？

  • 直接實現搖號算法
  • 管理所有監聽器的訂閱
  • 調用子類的 doDraw 拿結果，再觸發事件通知
  • 發送簡訊和 MQ 消息

Q3. 新增一種「郵件通知」，在觀察者模式下需要改哪裡？

  • 修改 LotteryServiceImpl 的 doDraw 方法
  • 新增一個 EventListener 實現類 + 在構造器裡 subscribe
  • 修改 EventManager 的 notify 方法
  • 重寫整個 LotteryService 抽象類

Q4. 觀察者模式满足哪個設計原則？

  • 開閉原則——對擴展開放、對修改封閉
  • 單一職責——一個類只做一件事
  • 里氏替換——子類可以替換父類
  • 接口隔離——接口要小而專

Q5. 觀察者模式的已知限制是什麼？

  • 性能太差，不適合高併發
  • 只能用在單機環境
  • 難控通知順序、結果回傳受限
  • 不支持泛型
