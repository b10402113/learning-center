Lesson 3/3 · 命令模式

三層重構：命令、實現者、調用者

Node: command · Step 3/3

學習目標

掌握命令模式五要素的 Java 落地寫法，能說出命令/實現者/調用者三層各自的職責邊界，並用測試輸出印證「請求與實現解耦」的收益。

工程結構：三大塊

重構後的工程按三大塊組織：

包放什麼對應角色
cook實現者接口 + 四個廚師實現廚師（ Receiver）
cuisine命令接口 + 四個菜品命令菜品（Command）
外層調用者 XiaoEr小二（Invoker）

拆解後可非常方便地擴展菜品與廚師，對調用者保持鬆耦合。

第一步：抽象命令 ICuisine

抽象命令只聲明一個接口方法——cook()：

public interface ICuisine {
    void cook();
}

這是「菜品」的公共接口。所有具體菜品都實現這個接口，承諾「我能烹飪」。

第二步：具體菜品命令

每個具體菜品在構造時注入對應的廚師（實現者），在 cook() 中調用廚師的烹飪方法：

public class GuangDongCuisine implements ICuisine {
    private ICook cook;

    public GuangDongCuisine(ICook cook) {
        this.cook = cook;
    }

    @Override
    public void cook() {
        cook.doCooking();
    }
}

四個菜品（廣東、四川、江蘇、山東）結構相同，只是注入的廚師不同。這就是「命令實現 + 實現者」兩兩組合形成具體命令對象。

第三步：抽象實現者 ICook

public interface ICook {
    void doCooking();
}

這是「廚師」的公共接口。每個具體廚師知道自己怎麼烹飪。

第四步：具體廚師

public class GuangDongCook implements ICook {
    @Override
    public void doCooking() {
        System.out.println("廣東菜廚師，烹飪粵菜");
    }
}

四個廚師（廣東、四川、江蘇、山東）各自實現 doCooking()，打印烹飪日誌。擴展新廚師只需加一個新類，不用動其他代碼。

第五步：調用者 XiaoEr

public class XiaoEr {
    private List<ICuisine> cuisineList = new ArrayList<>();

    public void order(ICuisine cuisine) {
        cuisineList.add(cuisine);
    }

    public synchronized void placeOrder() {
        for (ICuisine cuisine : cuisineList) {
            cuisine.cook();
        }
        cuisineList.clear();
    }
}

小二持有 List<ICuisine>，order() 添加菜品、placeOrder() 遍歷逐個執行後清空。調用者完全不關心具體是哪個廚師在做——它只持有命令對象。

測試驗證

測試類以「菜系 + 廚師」組合創建四個命令對象，再依次點單、下單：

XiaoEr xiaoEr = new XiaoEr();
xiaoEr.order(new GuangDongCuisine(new GuangDongCook()));
xiaoEr.order(new SiChuanCuisine(new SiChuanCook()));
xiaoEr.order(new JiangSuCuisine(new JiangSuCook()));
xiaoEr.order(new ShanDongCuisine(new ShanDongCook()));
xiaoEr.placeOrder();

輸出：

廣東菜廚師，烹飪粵菜
四川菜廚師，烹飪川菜
江蘇菜廚師，烹飪蘇菜
山東菜廚師，烹飪魯菜

每個具體命令都擁有一個對應實現類，可自由組合。點單把四種菜品對象添加給小二，下單等於把菜單傳遞給廚師。

收益 vs 代價

維度命令模式一把梭
加新菜加一個類，不動其他代碼改 order() 加 else if
換廚師加一個廚師類，菜品類不變改 order() 裡的描述
撤銷命令加 undo() 方法很難實現
類數量很多（每個菜 + 每個廚師各一個類）只有一個類

代價是在各種命令與實現組合下會擴展出很多實現類，需要專門管理。但對於菜品穩定、需要靈活組合的場景，命令模式的收益遠大於代價。

一句話記住

命令模式的三層拆分讓邏輯具備單一職責、便於擴展，代價是實現類膨脹。

自我檢測

Q1. 命令模式的五要素中，「調用者」的職責是？

  • 聲明執行命令的接口方法
  • 實現具體的烹飪邏輯
  • 持有命令列表，統一觸發執行
  • 定義菜品的公共接口

Q2. 重構後要加一道新菜（比如湘菜），需要改哪些文件？

  • 改 XiaoEr 類
  • 只加一個新的湘菜菜品类和一個新的湘菜廚師類
  • 改 ICuisine 接口
  • 改所有已有的菜品類

Q3. 命令模式的主要代價是什麼？

  • 命令與實現組合多導致實現類膨脹
  • 運行速度比 ifelse 慢
  • 不支持多線程
  • 無法實現撤銷功能
