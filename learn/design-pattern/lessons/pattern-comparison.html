策略 vs 命令/適配器/組合

design-pattern › strategy › pattern-comparison

學習目標：能說出策略模式與命令、適配器、組合模式「結構相似但意圖不同」的具體差異，給出選型判斷依據。

為什麼會搞混？

策略模式、命令模式、適配器模式、組合模式，這四個模式的類圖長得很像：都有一個接口、多個實現類、一個持有者/調用者。如果你只看結構，很容易分不清誰是誰。

但它們解決的問題完全不同。區分的關鍵不是「結構長什麼樣」，而是意圖是什麼。

策略模式 vs 命令模式

策略模式命令模式
意圖 定義一系列算法，封裝起來，使它們可互換 將請求封裝成對象，用於參數化、佇列化、記錄日誌、支持撤銷
核心問題 同一個動作有多種算法，怎麼讓它們可替換？ 請求的發送者和接收者怎麼解耦？
客戶端角色 選擇算法，注入策略 創建命令對象，設定接收者
替換機制 構造器注入，換策略即換算法 同一命令可以配不同接收者
典型場景 優惠券計算、支付方式選擇 菜單按鈕、操作佇列、撤銷/重做

結構上，兩者都有一個接口 + 多個實現。關鍵區別在綁定對象：

  • 策略模式的策略類是自包含的——它自己知道怎麼算，不需要外部接收者
  • 命令模式的命令類通常綁定一個接收者（Receiver），execute() 方法內部調用接收者的操作

一個簡單的判斷：你的類需不需要綁定一個「做事的人」（Receiver）？需要 → 命令模式。不需要，算法本身就是全部 → 策略模式。

策略模式 vs 適配器模式

策略模式適配器模式
意圖 讓算法可以互換 讓不兼容的接口能一起工作
核心問題 同一個動作有多種實現，怎麼替換？ 對方的接口跟我想要的不一樣，怎麼對接？
接口變化 接口是設計者自己定義的，統一而乾淨 適配器通常要把一個已有的、不兼容的接口「翻譯」成另一個接口
典型場景 支付方式選擇、排序算法替換 舊系統接口對接新系統、第三方 SDK 封裝

核心區別：策略模式的接口是你設計出來的，所有實現都遵守這個統一契約。適配器模式的接口是已有的、不兼容的，適配器的作用是做翻譯。

一個簡單的判斷：接口是你的設計還是對方的遺留？你設計的 → 策略模式。對方的不兼容 → 適配器。

策略模式 vs 組合模式

策略模式組合模式
意圖 讓算法可互換 讓個體和組合對象用統一接口調用（樹形結構）
核心問題 同一動作的多種算法 樹形結構中「葉子」和「組合」怎麼統一處理？
結構 平級的多個策略實現 遞歸的樹形結構（葉子 + 組合節點）
典型場景 優惠券計算、排序選擇 文件系統（文件 + 文件夾）、組織架構、菜單樹

這兩者差異最大。組合模式的核心是樹形結構的統一調用，策略模式是平級算法的互換。如果你的需求不是樹形結構，基本不會用到組合模式。

選型速查表

你要解決的問題選模式判斷依據
同一動作有多種算法，未來會加新的 策略模式 算法自包含，不需要綁定接收者
請求的發送和接收要解耦，需要撤銷/佇列 命令模式 命令對象綁定接收者，支持 execute/undo
對方的接口和我要的不一樣 適配器模式 接口是已有的、不兼容的，需要翻譯
樹形結構要統一調用個體和組合 組合模式 數據結構是遞歸的樹，不是平級列表

小結

這四個模式結構上都像「接口 + 多個實現」，但意圖決定一切：策略模式解決「算法可替換」，命令模式解決「請求可封裝」，適配器模式解決「接口不兼容」，組合模式解決「樹形統一調用」。面試被問到「策略和命令有什麼區別」時，不要從結構入手，從意圖和核心問題出發：你要封裝的是算法還是請求？
