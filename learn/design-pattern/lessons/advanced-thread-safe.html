三种进阶线程安全方案

单例模式

学习目标

理解 Holder 模式、双重检查锁、CAS 三种进阶方案的线程安全原理与取舍。

上一步看到的四种基础实现各有硬伤。现在要解决的核心问题是：同时做到线程安全 + 懒加载 + 高性能（不每次加锁）。三种进阶方案分别用了不同的底层机制来达成这个目标。

变体 4

静态内部类 / Holder 模式 — 推荐

这是最优雅的方案，利用了 JVM 类加载机制的一个保证：

JVM 保证：一个类只有在被主动使用时才会被加载（初始化）；类加载过程由 JVM 自己保证线程安全，不需要你加任何锁。 
public class Singleton {
    private Singleton() {}

    // 静态内部类，只有在被引用时才会加载
    private static class Holder {
        private static final Singleton INSTANCE = new Singleton();
    }

    public static Singleton getInstance() {
        return Holder.INSTANCE;  // 触发 Holder 类加载
    }
}

工作原理：

  1. 第一次调用 getInstance() 时，JVM 发现 Holder 类没加载过，触发类加载
  2. 类加载由 JVM 内部的 classloader 机制保证线程安全
  3. Holder 类加载时，INSTANCE 被初始化——只执行一次
  4. 后续调用直接返回已创建的实例，没有锁，没有 null 检查

三全其美：线程安全（JVM 保证）+ 懒加载（Holder 延迟加载）+ 高性能（零锁开销）。强烈推荐。

Holder 模式就像大楼的物业——你不用自己管钥匙，物业（JVM）在你需要的时候自动把钥匙给你，而且保证整栋楼只有一把。你甚至不需要知道物业是怎么管理的。

变体 5

双重检查锁（DCL）

只在第一次创建时加锁，后续调用只做 null 检查（无锁）：

public class Singleton {
    private static volatile Singleton instance;  // 必须 volatile

    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {              // 第一次检查（无锁）
            synchronized (Singleton.class) {  // 加锁
                if (instance == null) {          // 第二次检查（有锁）
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

为什么要两次检查？

第一次检查避免了每次都进 synchronized 块——实例创建之后，99.99% 的调用在外层 null 检查就返回了。第二次检查防止两个线程同时通过第一层检查后，排队进锁时重复创建。

为什么必须加 volatile？

instance = new Singleton() 这行代码在 JVM 层面分三步执行：① 分配内存 ② 初始化对象 ③ 把引用指向内存地址。JVM 可能会对 ② 和 ③ 做指令重排——先执行 ③ 再执行 ②。另一个线程在第一次检查时看到 instance != null，但对象还没初始化完，使用时就会出错。

volatile 禁止指令重排，保证写操作对所有线程立即可见。

陷阱：忘了 volatile 是最常见的 DCL bug。代码看起来完全正确，但在特定 CPU 架构和并发条件下会出诡异的 NPE。

变体 6

CAS + AtomicReference

用无锁的 CAS（Compare-And-Swap）操作替代 synchronized：

import java.util.concurrent.atomic.AtomicReference;

public class Singleton {
    private static final AtomicReference<Singleton> REF =
        new AtomicReference<>();

    private Singleton() {}

    public static Singleton getInstance() {
        Singleton instance = REF.get();
        if (instance == null) {
            instance = new Singleton();
            if (!REF.compareAndSet(null, instance)) {
                // CAS 失败，说明其他线程已经创建了
                instance = REF.get();  // 取已创建的
            }
        }
        return instance;
    }
}

原理：CAS 是 CPU 级别的原子操作，不需要线程切换和阻塞。多个线程同时尝试创建时，只有一个能成功 compareAndSet，其他线程拿到已创建的实例。

优点：完全无锁，没有线程阻塞/唤醒的开销，高并发下性能优秀。

风险：如果大量线程同时竞争，CAS 会反复失败并重试（自旋），占用 CPU 资源。极端情况下可能造成 CPU 空转。不过对于单例这种"只竞争一次"的场景，CAS 失败的线程立刻就能拿到结果，自旋风险很低。
