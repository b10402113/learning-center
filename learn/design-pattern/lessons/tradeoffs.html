工廠方法的收益與類爆炸風險

design-pattern › factory-method › tradeoffs

學習目標：能說出工廠方法模式的開閉原則收益和類擴張代價，理解它與抽象工廠模式的銜接關係。

重構帶來的三個收益

回頭看上一課的重構——從一個大方法拆成「接口 + 三個實現 + 工廠」——我們獲得了什麼？

1. 避免創建者與具體產品邏輯耦合

以前在 Controller 裡直接 new 具體的 Service 類，Controller 既要知道「有幾種商品」，又要了解「每種商品怎麼發放」。現在調用方只依賴 ICommodity 接口和 StoreFactory，不依賴任何具體的實現類。要換一種優惠券的發放邏輯？換實現類就行，Controller 完全不用改。

2. 滿足單一職責原則

每個實現類只管自己的業務邏輯——`CouponCommodityService` 只關心優惠券，`GoodsCommodityService` 只關心實物發貨。想改兌換卡的邏輯？打開 `CardCommodityService`，不影響其他任何商品。代碼的職責邊界清晰，修改範圍可控。

3. 滿足開閉原則

開閉原則（Open-Closed Principle）說的是：對擴展開放，對修改關閉。工廠方法完美體現了這一點——新增一種商品（比如視頻會員），只需要：加一個 `VideoCommodityService` 實現類，在 `StoreFactory` 裡加一行分發。不動 ICommodity 接口，不動任何已有的實現類，不動調用方的代碼。

這就是開閉原則的實踐：代碼的「擴展點」是工廠裡的分發和新的實現類，「穩定部分」是接口和已有的實現。加新功能不改已有代碼。

代價：類數量膨脹

工廠方法的缺點也很明顯：每新增一種商品，就要新增一個實現類。三種商品就是三個類，十種商品就是十個類。如果商品類型非常多（比如一個大型電商平台有幾十種虛擬商品），實現類的數量會急速擴張——有人稱之為「類爆炸」（Class Explosion）。

在發獎場景中，如果未來要支持：優惠券、實物商品、兌換卡、視頻會員、音樂會員、遊戲道具、紅包、積分、實物周邊……光實現類就有 9 個，加上接口和工廠就是 11 個類。而且每種商品的業務邏輯複雜度不同——有的需要防重，有的需要查手機號，有的需要拼裝快遞單——維護成本會隨著類數量線性增長。

怎麼降低類爆炸的影響？

工廠方法本身不解決類爆炸，但有幾種方式可以緩解：

  1. 用 Map 替代 ifelse：工廠內部可以維護一個 Map<Integer, ICommodity>，通過配置或掃描自動註冊，不需要每個類型寫一個 if 分支。這不減少實現類數量，但讓工廠本身更乾淨。
  2. 用反射或 Spring DI：在 Spring 環境中，可以用 @Autowired Map<String, ICommodity> 自動注入所有實現，工廠類甚至可以省掉。這是 Java 生態中工廠方法的常見落地形態。
  3. 結合其他模式：當商品類型非常多且有分組規律時，可以用抽象工廠（Abstract Factory）把一組相關的商品放在一起創建；或者用建造者模式（Builder）處理構建步驟複雜的商品。

與抽象工廠的銜接

抽象工廠模式（Abstract Factory Pattern）是工廠方法的「升級版」。如果說工廠方法是「一個工廠生產一種產品」，抽象工廠就是「一個工廠生產一族產品」。

回到發獎場景：假設未來不僅要支持發獎，還要支持「退款」——每種商品既有發放邏輯，又有退款邏輯。這時候如果繼續用工廠方法，你會有「發獎工廠 + 退款工廠」兩個工廠，每個都要維護一套 ifelse。抽象工廠的做法是：一個「商品工廠」接口同時定義 `getCommodityService` 和 `getRefundService`，優惠券工廠同時返回優惠券的發放和退款服務，實物工廠同時返回實物的發放和退款服務。

工廠方法是起點，不是終點。理解了它的意圖（統一創建入口、屏蔽實現）和代價（類數量膨脹），你才能在場景複雜時判斷：什麼時候繼續用工廠方法，什麼時候升級到抽象工廠。

小結

工廠方法模式帶來三個核心收益：避免創建者與具體產品耦合、滿足單一職責、滿足開閉原則。代價是實現類數量隨商品類型膨脹。緩解方式包括用 Map/Spring DI 簡化工廠內部、結合抽象工廠或建造者模式處理更複雜的場景。工廠方法是創建型模式的基礎，理解了它才能理解抽象工廠等後續模式。
