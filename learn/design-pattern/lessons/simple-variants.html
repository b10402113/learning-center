四种基础单例实现

单例模式

学习目标

掌握 4 种基础单例实现（静态类、懒汉、synchronized、饿汉）的代码结构与各自的致命缺陷。

变体 0

静态类 + ConcurrentHashMap 缓存

最简单的方案：把工具方法放在一个 final 类里，构造函数私有化，用 ConcurrentHashMap 做缓存。

public final class Singleton {
    private Singleton() {}

    private static final ConcurrentHashMap<String, Object> CACHE = new ConcurrentHashMap<>();

    public static Object getInstance(String key) {
        return CACHE.computeIfAbsent(key, k -> new Object());
    }
}

优点：线程安全，无锁竞争，简单直接。

缺陷：没有真正的实例状态——它更适合做"工具类"而不是"单例"。如果需要一个有状态的全局对象（比如持有连接池），这个方案就不合适了。

变体 1

懒汉模式（线程不安全）

第一次调用时才创建实例，看起来合理：

public class Singleton {
    private static Singleton instance;

    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {          // 线程 A 和 B 同时走到这
            instance = new Singleton();  // 各 new 了一次
        }
        return instance;
    }
}

致命缺陷：两个线程同时通过 null 检查，各自创建了一个实例。这不是"理论风险"——高并发下必然发生。

变体 2

synchronized 方法

给整个方法加锁，保证只有一个线程能进入：

public class Singleton {
    private static Singleton instance;

    private Singleton() {}

    public static synchronized Singleton getInstance() {
        if (instance == null) {
            instance = new Singleton();
        }
        return instance;
    }
}

优点：线程安全，逻辑清晰。

缺陷：每次调用都加锁。实例创建之后，后续 99.99% 的调用其实只需要读 instance，不需要锁。但在 synchronized 方法下，每次调用都要等锁——在高并发场景下性能损失严重。

类比：就像每次进门都要等保安查证件——哪怕你已经登记过了。安全，但烦。
变体 3

饿汉模式（static field）

类加载时就创建实例，不管用不用：

public class Singleton {
    private static final Singleton INSTANCE = new Singleton();

    private Singleton() {}

    public static Singleton getInstance() {
        return INSTANCE;
    }
}

优点：JVM 类加载机制保证线程安全，没有任何锁，性能最好。

缺陷：不支持懒加载。类一加载就创建，不管用不用。就像游戏启动时预加载全部地图——如果你只打一局，其他地图的内存全浪费了。

适用场景：如果对象创建开销不大，且一定会用到，饿汉是最简单可靠的选择。

四种实现的对比

变体线程安全懒加载性能结论
0 静态类✅—高不适合有状态的单例
1 懒汉❌✅高有 bug，不能用
2 synchronized✅✅低安全但每次调用都付锁代价
3 饿汉✅❌最高简单可靠，但不懒加载

下一课的方向

四种基础实现各有硬伤：要么不安全，要么不懒加载，要么性能差。下一步要解决的核心问题是：

能不能同时做到：线程安全 + 懒加载 + 高性能（不每次加锁）？

答案是可以的。JVM 的类加载机制（Holder 模式）、volatile + 双重检查锁（DCL）、以及无锁的 CAS，都能做到这一点。它们各自的原理和取舍，是下一步的内容。
