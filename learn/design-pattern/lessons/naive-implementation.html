一把梭實現：硬編碼試卷為什麼行不通

design-pattern › prototype › naive-implementation

學習目標：看出一把梭硬編碼實現的問題——順序固定、擴展性差，理解為什麼需要更好的方案。

先搭場景：上機考試

從紙質考卷演進到上機考試後，為了防作弊，同一套題庫對每位考生的試卷必須做到：題目順序不同、選項順序不同。這就是「試卷混排」的需求。

我們有兩種題目物料：

  • 選擇題（ChoiceQuestion）：題目文本 + 選項 Map（A→…, B→…）+ 正確答案 key
  • 問答題（AnswerQuestion）：問題文本 + 答案字符串

一把梭：所有邏輯塞進一個類

最直覺的寫法：QuestionBankController 裡硬編碼所有題目，直接拼裝成試卷字符串。

public class QuestionBankController {

    public String createPaper(String candidate, int number) {
        List<ChoiceQuestion> choiceQuestionList = new ArrayList<>();
        List<AnswerQuestion> answerQuestionList = new ArrayList<>();

        // 選擇題：硬編碼 5 道
        choiceQuestionList.add(new ChoiceQuestion("Java 的版本定義在哪個包？",
            Map.of("A", "java.lang", "B", "java.util", "C", "java.io", "D", "java.net"), "B"));
        choiceQuestionList.add(new ChoiceQuestion("Java 程式的入口是？",
            Map.of("A", "main 方法", "B", "start 方法", "C", "init 方法", "D", "run 方法"), "A"));
        // ... 更多選擇題 ...

        // 問答題：硬編碼 4 道
        answerQuestionList.add(new AnswerQuestion("Java 的面向對象特性是什麼？", "封裝、繼承、多態"));
        // ... 更多問答題 ...

        // 拼裝試卷字符串
        StringBuilder sb = new StringBuilder();
        sb.append("考生：").append(candidate).append("\n");
        sb.append("考號：").append(number).append("\n\n");
        sb.append("=== 選擇題 ===\n");
        for (int i = 0; i < choiceQuestionList.size(); i++) {
            ChoiceQuestion q = choiceQuestionList.get(i);
            sb.append(i + 1).append(". ").append(q.getName()).append("\n");
            q.getOption().forEach((k, v) -> sb.append("  ").append(k).append(". ").append(v).append("\n"));
            sb.append("答案：").append(q.getKey()).append("\n\n");
        }
        // 問答題類似...
        return sb.toString();
    }
}

測試暴露了什麼？

用 junit 為花花、豆豆、大寶三位考生各生成一份試卷：

// 花花的試卷：第 1 題 = "Java 的版本定義"，選項 A→java.lang, B→java.util...
// 豆豆的試卷：第 1 題 = "Java 的版本定義"，選項 A→java.lang, B→java.util...
// 大寶的試卷：第 1 題 = "Java 的版本定義"，選項 A→java.lang, B→java.util...
壞味道：三份試卷的題目順序、選項順序完全一樣。考生坐隔壁就能互抄——混排根本沒實現。

問題在哪？

兩個致命問題：

  1. 順序固定：所有題目從同一個 List 按索引順序輸出，沒有任何亂序機制。如果要加亂序，得在這個已經很長的方法裡再塞 shuffle 邏輯，複雜度指數上升。
  2. 擴展性差：新增一種題型（比如填空題）？你得在這個方法裡加新的 List、新的循環、新的拼裝邏輯。一個方法承擔了「建題 + 組卷 + 輸出」三件事，改一處動全身。

更深層的問題：這個方法每次被調用時，都在重新構造所有題目對象。題目是固定的，為什麼要每次 new 一遍？

這些問題正是原型模式要解決的：用克隆代替重複構造，把「建題」和「組卷」分離開。下一課看看怎麼用 Cloneable 重構。
