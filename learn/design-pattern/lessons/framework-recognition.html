框架里的装饰与代理

结构型

本课目标
认出 Spring、MyBatis、JDK I/O 里的装饰器和代理结构，并说明它们解决了什么问题。

JDK I/O 流：最经典的装饰器

装饰器

JDK I/O 流

你已经用过无数次了：

// FileReader 是 ConcreteComponent
// BufferedReader 是 ConcreteDecorator
BufferedReader reader = new BufferedReader(new FileReader("data.txt"));

// FileInputStream 是 ConcreteComponent
// InputStreamReader 是 ConcreteDecorator（加了字符编码转换）
// BufferedReader 再套一层（加缓冲）
InputStreamReader isr = new InputStreamReader(
    new FileInputStream("data.txt"), "UTF-8");
BufferedReader br = new BufferedReader(isr);

角色映射：Component = Reader/InputStream 接口，ConcreteComponent = FileReader/FileInputStream，Decorator = ReaderInputStream/BufferedReader，ConcreteDecorator = 带具体功能的子类。

为什么用装饰器：I/O 需要灵活组合功能（缓冲 + 编码转换 + 行读取），用继承会爆炸。装饰器让你像搭积木一样组合。

MyBatis Mapper：JDK 动态代理

代理

MyBatis Mapper bean

核心机制：定义接口 + @Select/@Insert 注解 → JDK 动态代理 → 读注解执行 SQL → 返回结果。

// 你写的：只有接口
@Mapper
public interface UserDao {
    @Select("select userName from user where id = #{uId}")
    String queryUserName(String uId);
}

// MyBatis 做的（简化）：
// MapperFactoryBean.getObject()
//   → Proxy.newProxyInstance(classLoader, new Class[]{UserDao.class}, handler)
//   → handler.invoke(): 读 @Select 注解 → 执行 SQL → 返回结果

角色映射：Component = UserDao 接口，InvocationHandler = JdkInvocationHandler（读注解+执行SQL），Proxy = JDK 动态代理生成的代理对象。

为什么用代理：控制数据库访问——屏蔽连接获取、SQL 解析、结果映射等细节，调用方只看到接口。

Spring AOP：代理 + 注解

代理

Spring AOP 切面

你写过这样的代码：

@Aspect
@Component
public class LogAspect {
    @Around("execution(* com.example.service.*.*(..))")
    public Object around(ProceedingJoinPoint point) throws Throwable {
        long start = System.currentTimeMillis();
        Object result = point.proceed();  // 调用目标方法
        long cost = System.currentTimeMillis() - start;
        log.info("方法 {} 耗时 {}ms", point.getSignature().getName(), cost);
        return result;
    }
}

背后发生了什么：Spring 为被切面覆盖的 Bean 生成代理对象（JDK 动态代理或 CGLIB）。调用方拿到的是代理，每次调用方法都经过 AOP 切面链。

为什么用代理：控制方法调用——在不修改业务代码的前提下，织入日志、事务、权限等横切逻辑。

Spring Security：过滤器链（装饰器风格）

装饰器 / 责任链

Spring Security FilterChain

结构：多个 SecurityFilter 依次处理请求，每个 filter 可以在转发前后加逻辑（认证、授权、CSRF 检查）。

// 每个 filter 包裹下一个
public class OncePerRequestFilter implements Filter {
    protected void doFilterInternal(request, response, chain) {
        // 前置逻辑（认证）
        if (!isAuthenticated(request)) { /* 拒绝 */ return; }
        chain.doFilter(request, response);  // 转发给下一个 filter
        // 后置逻辑（审计）
    }
}

判断：每个 filter 给请求加了新功能（认证、授权、CSRF），是装饰器风格。但整体是责任链模式——每个 filter 决定是否继续传递。

识别框架模式的技巧

看到什么想什么模式问自己
new A(new B(...)) 套娃 装饰器 是给 B 加功能吗？
接口 + @Select/@Insert，没有实现类 JDK 动态代理 是在控制数据库访问吗？
@Aspect + @Around/@Before 代理 是在拦截方法调用织入逻辑吗？
Filter + chain.doFilter() 装饰器 / 责任链 是加功能还是传递请求？
FactoryBean + getObject() 可能是代理 getObject() 返回的是代理对象吗？

关键洞察

框架 = 模式的容器 你每天用的框架里到处是设计模式。JDK I/O 是装饰器，MyBatis 是代理，Spring AOP 是代理，Spring Security 是装饰器/责任链。认出这些结构，读源码就不再是"看天书"——你知道它在做什么，只是不知道细节。

本课小结

  1. JDK I/O 流是最经典的装饰器——BufferedReader 装饰 FileReader，加缓冲功能
  2. MyBatis Mapper 是 JDK 动态代理——接口 + @Select 注解 → 代理执行 SQL
  3. Spring AOP 是代理——为 Bean 生成代理对象，拦截方法调用织入切面
  4. Spring Security FilterChain 是装饰器/责任链风格——每个 filter 给请求加功能
  5. 识别技巧：看到套娃想装饰器，看到无实现类的接口想代理，看到 @Aspect 想代理
