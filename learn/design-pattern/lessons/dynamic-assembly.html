動態編排與邊界

學習目標

學會用 appendNext 動態組裝審批鏈，理解時間範圍如何決定鏈長度，並說出責任鏈的適用邊界與代價。

動態組裝：一行代碼搞定一條鏈

責任鏈最強大的地方在於編排過程可以與節點實現分離。看看怎麼組裝這條審批鏈：

// 鏈式編排：三級 → 二級 → 一級
AuthLink authLink = new Level3AuthLink("1000013", "王工")
    .appendNext(new Level2AuthLink("1000012", "張經理",
        date("2020-06-01"), date("2020-06-25"))
    .appendNext(new Level1AuthLink("1000011", "段總",
        date("2020-06-11"), date("2020-06-20"))));

// 執行審批
AuthInfo result = authLink.doAuth(uId, orderId, authDate);

注意幾個要點：

  • 編排代碼只出現一次：在控制層（或配置類）中組裝，業務代碼不需要知道鏈的存在
  • 節點順序可以隨時調整：交換 appendNext 的順序就行，不需要改任何節點類
  • 可以動態增刪節點：加一個 Level0AuthLink 就多一級審批，刪掉就不審

配置化：從硬編碼到可配置

上例中鏈的編排還是在代碼裡寫死的。在實際業務中，責任鏈可以進一步配置化：

方式適用場景優缺點
代碼寫死鏈結構固定，很少變化簡單直接，但改動需要重新部署
XML 配置鏈結構偶爾調整改配置不用改代碼，但解析有開銷
數據庫/配置中心鏈結構經常變化（如審批流引擎）最靈活，但複雜度最高

核心思路：把「鏈上有誰、順序如何」從代碼中抽離出來，放到配置裡。這樣業務人員改個配置就能調整審批流，不需要開發介入。

收益：從 if-else 到責任鏈

對比重構前後：

結構清晰：每個審批級別是獨立的類，職責單一，一看就知道「王工負責三級」。
符合單一職責原則：每個類只管自己的審批邏輯，不混入其他級別的判斷。
符合開閉原則：加新審批級別只需加新類，不改動已有代碼。
外部調用方無感：控制層只需組裝鏈並調用 doAuth，不需要關心鏈內部怎麼運作。

總結來說：責任鏈把「流程編排」和「節點實現」分開了，就像把一坨 if-else 拆成了可插拔的模塊。

邊界：什麼時候不该用？

責任鏈不是萬能的。它有明確的適用邊界：

不適合簡單條件判斷
如果只是 A 或 B 或 C 三選一，用 if-else 或 switch 就夠了。責任鏈的價值在於「多個節點可能都要處理、處理順序可變、鏈可動態調整」的場景。
性能開銷
每個請求都要沿鏈傳遞，節點越多開銷越大。如果鏈上有十幾個節點，每個請求都要走一遍判斷邏輯——在高併發場景下可能成為瓶頸。
調試複雜度
請求在鏈上跳轉，出問題時你不知道是哪個節點的責任。不像 if-else 一眼能看到完整的判斷邏輯，責任鏈的執行路徑是動態的。

一句話總結：if 適合判斷，不適合做系統流程設計。在做判斷和行為邏輯處理中 if-else 非常可用，但當流程需要「順序傳遞、動態編排、節點可增刪」時，責任鏈才是正確的選擇。
