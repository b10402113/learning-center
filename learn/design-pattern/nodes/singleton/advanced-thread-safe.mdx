# 三种进阶线程安全方案

## Learning goal

<理解 Holder 模式、双重检查锁、CAS 三种进阶方案的线程安全原理与取舍>

## Lesson

静态内部类/Holder 模式（变体 4）是三种进阶方案中最优雅的，它利用 JVM 类加载机制的一个保证：一个类只有在被主动使用时才会被加载，类加载过程由 JVM 内部的 classloader 机制保证线程安全，不需要加任何锁。实现上是在单例类内部定义一个 `private static class Holder`，持有 `static final` 的实例。第一次调用 `getInstance()` 时触发 `Holder` 类加载，`INSTANCE` 被初始化且只执行一次，后续调用直接返回已创建的实例，零锁开销。它同时做到了线程安全（JVM 保证）、懒加载（`Holder` 延迟加载）和高性能（零锁开销），强烈推荐。

双重检查锁 DCL（变体 5）是经典的并发方案，核心思想是只在第一次创建时加锁。`getInstance()` 先做一次 `null` 检查（无锁），通过后进 `synchronized` 块再做第二次 `null` 检查。第一次检查让 99.99% 的调用在外层就返回了，第二次检查防止两个线程同时通过第一层后排队重复创建。关键陷阱是 `instance` 必须声明为 `volatile`——`new Singleton()` 在 JVM 层面分三步执行（分配内存、初始化对象、引用指向地址），JVM 可能对 ② 和 ③ 做指令重排，导致另一个线程看到非 null 引用但对象还没初始化完，使用时出错。`volatile` 禁止指令重排，保证写操作对所有线程立即可见。忘了 `volatile` 是最常见的 DCL bug，代码看起来完全正确但在特定 CPU 架构和并发条件下会出诡异的 NPE。

CAS + AtomicReference（变体 6）用 CPU 级别的原子操作替代 synchronized。多个线程同时尝试创建时，只有一个能成功 `compareAndSet(null, instance)`，其他线程拿到已创建的实例。完全无锁，没有线程阻塞/唤醒的开销，高并发下性能优秀。风险是大量线程同时竞争时 CAS 会反复失败并重试（自旋），占用 CPU 资源，但单例场景只竞争一次，自旋风险很低。三种进阶方案中，Holder 模式最简单最安全性能最好，是日常使用的首选；DCL 和 CAS 是理解并发机制的好教材但实际项目中 Holder 已经足够。
