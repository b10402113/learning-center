# 单例模式的动机：为什么全局只要一个实例

## Learning goal

<理解单例模式解决什么问题、为什么多线程环境下"只要一个实例"这么难>

## Lesson

有些对象在整个应用生命周期里只需要一个实例——数据库连接池、Spring 容器里的 Bean、全局配置持有者。如果每次都 `new` 一个新实例，多个实例各管各的状态，改了一个另一个不知道，配置不一致、事务边界混乱、连接池超限都是这么来的。单例模式的核心需求就是：一个类在整个 JVM 里只允许存在一个实例，所有调用方拿到的都是同一个对象。

但"只 new 一次"在多线程环境下远没有听起来那么简单，因为两件事会同时存在：懒加载（Lazy Loading）和线程安全。有些对象创建成本很高，比如数据库连接池要建几十个连接、读取远程配置要发 HTTP 请求，应用一启动就全部创建会让启动时间很长，而且有些对象可能整个生命周期都用不到。懒加载要求"用到才创建"。与此同时，现代 Java 应用几乎都是多线程的——Tomcat 的每个请求都跑在独立线程上。如果两个线程同时判断"实例还没创建"，同时 `new`，就会创建出两个实例，单例的约束被打破。

核心矛盾就在这里：懒加载要求延迟创建，线程安全要求同步访问。同步会加锁，加锁会降低并发性能。后续 7 种单例实现，本质上就是在不同位置、用不同手段解决这个矛盾——从最朴素的 `synchronized` 方法，到 JVM 类加载机制的巧用，再到无锁的 CAS 和枚举方案，每一种都在安全性和性能之间做了不同的取舍。
