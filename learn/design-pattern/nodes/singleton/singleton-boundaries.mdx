# 單例的適用邊界與決策清單

<LearningGoal>
歸納何時該用、何時不該用單例，給出決策清單，並說出單例與靜態類的適用邊界。
</LearningGoal>

## Lesson

單例模式有幾個被低估的缺點。**隱式依賴，難以測試**：單例是全局可見的，任何類都可以直接訪問它而不聲明依賴關係，你想單測一個依賴單例的類時沒法 mock 掉它，測試之間也會因為共享單例狀態而互相干擾。**狀態共享耦合**：單例實例整個應用只有一個，如果它維持了狀態，任何修改都會影響所有使用方，模塊 A 改了單例的值模塊 B 立刻受到影響但它們之間可能沒有任何依賴聲明。**分佈式環境天然缺陷**：單例的「一個實例」只在一個 JVM 裡，部署十台機器就有十個實例，狀態怎麼同步不是單例模式本身能解決的。**繼承和多態的限制**：枚舉單例不能被繼承，其他寫法繼承單例本身就違反「只有一個實例」的語義。

單例適合的場景是**資源池/緩存**（創建成本高、需要統一管理，如資料庫連線池、線程池、本地緩存）、**全局配置**（啟動時加載一次、全局讀不寫）、**日誌記錄器**（單一入口）、**框架核心組件**（容器/引擎只應有一個，如 Spring ApplicationContext）。拿到需求時用五問判斷法：全局只會有一個嗎？需要維持狀態嗎？需要被繼承嗎？創建成本高嗎？在分佈式環境嗎？五個都過才用單例。

面試答缺點時從四個角度展開：隱式依賴→狀態耦合→分佈式失效→違反單一職責，再用依賴注入（DI）收束——「現代框架更推薦用 DI 控制對象作用域，Spring Bean 默認 singleton 就是容器管實例化、類只管業務」。
