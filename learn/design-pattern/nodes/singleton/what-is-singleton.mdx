# 什麼是單例模式？

<LearningGoal>
能說清單例模式的本質——全局唯一實例加上全局訪問點，並用資料庫連線池、Spring Bean 等場景理解它解決什麼問題。
</LearningGoal>

## Lesson

你在 Spring 裡寫過 `@Service` 或 `@Component` 吧？這些 Bean 默認就是單例的——整個應用裡只有一個實例，所有 Controller 注入的都是同一個對象。你可能從沒想過「為什麼只有一個」，但這個「只有一個」正是單例模式的核心。

**單例模式**（Singleton Pattern）是創建型模式中最直覺的一個，它的意圖一句話就能說清：**保證一個類只有一個實例，並提供一個全局訪問點**。它解決的問題是：某些對象的創建成本很高（資料庫連線、大文件解析、遠端調用），反覆創建是不必要的開銷；多個實例各自維持狀態會導致誰是「真相」的混亂；全局變量太散，單例提供一個受控的「全局訪問點」。

三個你一定碰過的場景：**資料庫連線池**——每次查詢都新建連線，TCP 三次握手、認證、釋放，一個簡單的 SELECT 可能比業務邏輯還慢，連線池維護一组已建立的連線用完歸還，但如果池子被 new 了十個，每個池子各管各的連線，連線總數就會失控；**Spring Bean**——容器裡的 Bean 默認作用域是 `singleton`，一個 `UserService` 被多個 Controller 注入，它們拿到的是同一個實例，如果每次注入都 new，Bean 裡緩存的數據和維持的狀態就會散落各處；**全局配置讀取器**——啟動時從配置中心拉一份配置解析成對象放在內存裡，如果每次讀配置都重新拉、重新解析，不僅浪費網路 IO，還可能因為配置中心暫時不一致導致不同模塊讀到不同版本。

單例和靜態類的初識邊界：一個全是 static 方法的工具類（如 `Math`、`Arrays`）也能提供全局訪問且更簡單，但它們有本質區別——靜態類不需要實例化、通常無狀態、不支持繼承和多態、難以 mock；單例需要實例化但只允許一次、可以維持有狀態的實例、可以被繼承和實現接口、可以通過接口注入 mock。一句話記法：「不需要狀態、不需要繼承、純工具」用靜態類；「需要狀態、需要繼承、需要多態」用單例。

單例模式的本質是兩個約束：**只有一個實例**＋**一個全局訪問點**。後面的步驟會看到，光是「怎麼保證只有一個」這件事，Java 就能給出七種截然不同的答案。
