<LearningGoal>
說出抽象工廠滿足的設計原則、代價與選型邊界，能判斷「何時該用、何時不必」。
</LearningGoal>

## Lesson

回頭看 Redis 雙集群重構，它同時滿足了多條設計原則。單一職責——每個適配器只負責翻譯一套集群的方法名。開閉原則——新增集群只需加適配器類，不動已有代碼。依賴倒置——業務代碼依賴 `ICacheAdapter` 介面，不依賴具體集群。里氏替換——任何適配器都可以替換另一個，不影響調用方。其中開閉原則是最直接的收益，抽象工廠的核心價值就是「加新實現不用改老代碼」。

代價同樣存在。類數量增多——每加一套集群就要多一個適配器類。間接層增加——調用鏈從兩層變成三層，IDE 跳轉和調試要多追幾層。理解成本上升——新同事看到 JDKProxy、InvocationHandler、ICacheAdapter 一堆抽象，比看到 ifelse 更需要動腦。但這些代價是可被緩解的：類數量可以用代理類自動生成；間接層在調試工具裡追蹤並不困難；理解成本靠團隊規範和文檔解決。相比之下，ifelse 方案的膨脹和耦合是不可緩解的——越往後改越痛。

判斷標準很明確：一個產品有多實現（比如「發獎」有金幣、優惠券、實物）→ 工廠方法；一整套產品族有多實現（比如 Redis 集群、作業系統、支付渠道）→ 抽象工廠。如果場景很穩定、永遠不會加新實現，ifelse 也不算太壞；但只要「成套切換是常態」，抽象工廠就值得投入。
