# 一把梭實現：硬編碼試卷為什麼行不通

## Learning goal

看出一把梭硬編碼實現的問題：順序固定、擴展性差，理解為什麼需要更好的方案。

## Lesson

從紙質考卷演進到上機考試後，為了防作弊，同一套題庫對每位考生的試卷必須做到：題目順序不同、選項順序不同。我們有兩種題目物料：選擇題（`ChoiceQuestion`）由題目文本、選項 Map（A→…, B→…）、正確答案 key 三部分組成；問答題（`AnswerQuestion`）只有問題文本和答案字符串。

最直覺的寫法是把所有邏輯塞進一個 `QuestionBankController`：硬編碼 5 道 Java 選擇題（版本定義、main 方法、變量命名、標識符、表達式求值）和 4 道問答題，存入兩個 List，再遍歷拼裝出含「考生/考號/選擇題/問答題」的格式化字符串返回。作者點評：這類代碼易理解但不面向對象、不考慮擴展性，且「有這種潛質」——一個類幾千行的業務大類型就是這樣長出來的。

用 junit 為花花、豆豆、大寶三位考生各生成一份試卷，結果三份試卷的題目順序、選項順序完全一樣——考生坐隔壁就能互抄，混排根本沒實現。問題有兩個：一是順序固定，所有題目從同一個 List 按索引順序輸出，沒有任何亂序機制，加亂序會讓這個已經很長的方法更複雜；二是擴展性差，新增一種題型就得加新的 List、新的循環、新的拼裝邏輯，一個方法承擔了「建題 + 組卷 + 輸出」三件事，改一處動全身。

更深層的問題：這個方法每次被調用時都在重新構造所有題目對象。題目是固定的，為什麼要每次 new 一遍？這些問題正是原型模式要解決的：用克隆代替重複構造，把「建題」和「組卷」分離開。下一課看看怎麼用 `Cloneable` 重構。
