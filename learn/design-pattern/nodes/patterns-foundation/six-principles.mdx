# 六大原则各自管什么

<LearningGoal>
能说出单一职责、里氏替换、依赖倒置、接口隔离、迪米特、开闭六大原则各自管什么，并说清它们如何共同指向高内聚、低耦合、可扩展、可复用。
</LearningGoal>

## Lesson

上一步我们认出了"一坨代码"的坏味道。设计模式是重构这种代码的具体套路，但套路不是随便用的——你需要一组裁判规则来判断"这段代码哪里坏了、重构后真的变好了吗"。六大原则就是这组裁判，它们共同指向四个终极追求：高内聚（一个类只干一件事）、低耦合（类之间尽量少互相依赖）、可扩展（加新功能不改旧代码）、可复用（写过的东西能在别的地方用）。

单一职责原则（SRP）管"一个类只干一件事"——如果一个 Service 同时处理优惠券、实物发货、兑换卡，任何一个职责变化都可能影响另外两个。里氏替换原则（LSP）管"子类能无缝替换父类，不破坏已有行为"——子类可以扩展父类，但不能改变父类已经定好的行为契约。依赖倒置原则（DIP）管"高层模块不依赖低层模块，都依赖抽象"——你的业务逻辑不应该直接依赖具体 MySQL 实现，而是依赖 Repository 接口。接口隔离原则（ISP）管"接口要小而专，不要强迫实现用不到的方法"——一个 20 方法的胖接口让实现类被迫写一堆空方法。迪米特原则（LoD）管"一个对象只跟直接朋友说话"——Controller 不应该知道 Service 内部调了哪个 DAO。开闭原则（OCP）管"对扩展开放，对修改关闭"——加新产品类型应该新增一个类而不是改已有代码。

六个原则各管一块，但终极目标一致：SRP 指向高内聚；LSP 指向可复用（子类可替换父类，复用才安全）；DIP、ISP、LoD 共同指向低耦合；OCP 指向可扩展。设计模式就是在具体场景下实现这些原则的套路——每学一个模式，问自己：它满足了哪个原则？代价是什么？
