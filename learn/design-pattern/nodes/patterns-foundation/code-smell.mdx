# 认识"一坨代码"的坏味道

<LearningGoal>
能在一堆代码里认出按 type 字段堆叠的 ifelse/switch 分发，说出它为什么每加一个需求就越来越难维护。
</LearningGoal>

## Lesson

打开任何一个"做了一段时间"的业务 Controller 或 Service，你大概率会看到这种形状：一个方法里按 `type` 字段用 if/switch 分发到不同逻辑块，每个分支各自拼参数、调服务、映射返回值。比如奖品发放的 `awardToUser()` 方法里，`awardType == 1` 走优惠券、`== 2` 走实物商品、`== 3` 走兑换卡——每来一个新产品就加一个 else if。这段代码能跑、测试也能过，但它有病——一种叫"坏味道"（code smell）的病。

把这段代码放在增长的业务里，四个问题冒出来。第一，每加一个产品类型就要改这个方法，直接违反开闭原则——你不是在"加"代码，而是在"改"已有代码，而已有代码已经跑着、被别人依赖着。第二，方法越来越长，三种产品各写一遍参数拼装、结果映射、异常处理，加到十种就是几百行，超过人的工作记忆容量。第三，产品逻辑全部耦合在一个方法里，改优惠券怕影响实物商品。第四，测试没法隔离，想单独测一种逻辑得 mock 另外两种。

这种坏味道有一个可识别的形状：按一个 type/dispatch 字段，用 if/switch 把不同类型分发到不同逻辑块，每个逻辑块各自拼参数、调服务、映射返回值，但它们全挤在同一个方法或同一个类里。它不只出现在奖品发放——支付渠道分发、消息类型分发、审核状态分发，形状一模一样。

"能跑"不够。业务增长时这段代码的命运几乎是确定的：3 个分支还行，5 个开始觉得长，10 个每次加需求都心惊胆战，20 个没人敢碰。坏味道的真正代价不是今天的维护成本，而是未来每次变更的摩擦力。坏味道不是 bug，它不会让你的程序崩溃，它是一种信号——告诉你这段代码在增长场景下会越来越痛苦。认出这个信号，就是学设计模式的起点。
