# 怎么读懂一个模式章节

<LearningGoal>
能用"场景模拟 → 一坨代码 → 模式重构 → 总结"的框架去读任何一个模式章节，并带着"模式买扩展、付出类数量代价、要判断 ROI"的取舍意识。
</LearningGoal>

## Lesson

接下来要读 22 个模式章节。如果每个章节都从头摸索"该看什么、跳过什么"，效率极低。好消息是《重学 Java 设计模式》每个章节都遵循同一套结构，学会这套结构就能高效读任何一章。四步框架是：场景模拟（看业务场景，理解约束，让模式挂靠到你认识的业务上）→ 一坨代码（看 ifelse 实现，认出坏味道，关注按什么字段分发、每个分支在干什么、增长时会怎样）→ 模式重构（看设计模式实现，重点看结构变化——类图怎么变了、新增了哪些接口和类、原来 ifelse 里的分支逻辑跑到了哪里）→ 总结（满足了哪些原则、带来什么好处、付出什么代价、适合什么场景）。

每个模式都在做一笔交易：买到可扩展性（加新类型不改旧代码），付出更多类和接口；买到低耦合（模块互不影响），付出间接结构（调用链变长）；买到高内聚（每个类只干一件事），付出认知成本（要理解更多文件的关系）；买到可复用（写过的代码能在别处用），付出过度设计风险（简单场景用模式是杀鸡用牛刀）。ROI 判断是核心能力——不是所有场景都值得用模式，只有当"加新类型的频率"和"维护成本"高到一定程度时，模式才值得它的类数量代价。这本书 22 个模式都给了适合和不适合的场景，读总结时重点关注这个。

用工厂方法模式走一遍：场景是积分兑换、三种奖品、三家第三方接口不一样、以后还会加新产品；一坨代码是 `awardToUser()` 按 `awardType` 做 ifelse；重构是 `ICommodity` 接口 + 三个实现类 + `StoreFactory` 按类型选实现，ifelse 消失；总结是满足单一职责 + 开闭，代价是多出几个类，但新产品会持续加所以值得。后面 21 个模式每次都走这四步，读多了你会发现很多模式的"一坨代码"长得几乎一样，区别只在重构方向不同。
