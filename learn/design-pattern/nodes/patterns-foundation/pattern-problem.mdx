# 设计模式解决什么问题

<LearningGoal>
能说出设计模式是什么、解决哪一类反复出现的设计问题、从哪来，以及它作为沟通语言的作用。
</LearningGoal>

## Lesson

先看一个你大概率写过的场景。一个 Controller 里按 `type` 字段用 switch 或 ifelse 分发到不同逻辑，每来一个需求就往上堆一个分支。你写得难受，但不知道有什么更好的写法。关键的现象是：这不是你一个人的问题。隔壁团队做积分兑换也堆了几乎一模一样的 ifelse；读 Spring、MyBatis 源码时，你会发现框架里到处是"接口 + 一堆实现类 + 一个按条件挑实现的入口"这种形状。有经验的程序员，即使从没一起商量过，遇到类似的设计问题时也会收敛到几乎一样的解法。

把"反复出现的解法"称作模式（Pattern，设计模式）的想法，最早来自建筑学。Christopher Alexander 写了《建筑模式语言》（A Pattern Language），观察城市和建筑时发现，好的建筑里有一些反复出现、经过检验的空间安排——比如"临街的窗""入口的过渡空间"。这些不是图纸，而是一套描述"什么场景下该怎么布置"的经验语言。1994 年，四人组（GoF，Gang of Four）把这套思想搬进软件界，出版了《设计模式：可复用面向对象软件的基础》，系统整理了经典模式。《重学 Java 设计模式》用 22 个真实互联网业务场景（营销、秒杀、支付、ORM、中间件）逐个示范其中 22 个模式。

模式不是图纸、不是代码片段、不是可以复制粘贴的库。它是一段描述，回答四个问题：名字（怎么称呼）、问题（解决什么场景）、解法（结构上怎么搭）、权衡（付出什么代价、买来什么）。用奖品发放举例：工厂方法这个名字，解决的问题是按类型创建不同的奖品服务、且新类型还不断加；解法是一个创建接口 + 每种奖品一个实现 + 一个工厂按类型挑选；权衡是多出几个类，换来新奖品不改调用方。所有模式绕来绕去都在服务同一组追求：高内聚、低耦合、可扩展、可复用。本书 22 个模式按解决哪一类问题分成三族：创建型（5 个）管怎么造对象才灵活可复用；结构型（7 个）管怎么把类和对象组装成大结构；行为型（10 个）管对象之间怎么沟通、派活才高效。

学模式有两个实用价值。第一是沟通语言：与其花十分钟解释"我想把这段算法抽出来做成可以换的"，不如说一句"这里用策略模式"，对方脑子里立刻出现接口 + 一组实现类 + 一个挑选入口的结构。第二是认出问题：代码不会写"我是策略模式的场景"，它只会表现为一堆长得一样的 if 分支。你学过的模式越多，越能把眼前的烂代码对号入座到某个已知问题的变体上——认出来，重构方向就有了。记住一句话：模式是你认出来的，不是套上去的。后面的步骤会把这个"先写烂代码、再认出问题、再用模式重构"的方法拆开讲。
