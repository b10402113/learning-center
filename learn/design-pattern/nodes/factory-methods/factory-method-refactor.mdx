# 工厂方法的重构路径

<LearningGoal>
掌握工厂方法的重构路径——从 ifelse 分发改为"创建接口 + 子类决定实例化哪个产品"，满足开闭原则和单一职责。
</LearningGoal>

## Lesson

工厂方法的重构路径分四步。第一步，定义统一的产品接口 `ICommodity.sendCommodity(uId, commodityId, bizId, extMap)`，把三种奖品的差异封装掉，对外只暴露一个方法。第二步，每种产品各自实现：`CouponCommodityService` 封装优惠券调用，`GoodsCommodityService` 封装商品调用，`CardCommodityService` 封装兑换卡调用。每个类只关心自己的第三方接口，参数映射和异常处理内聚在类内部。

第三步，工厂方法负责创建。`StoreFactory.getCommodityService(type)` 根据 type 参数返回对应的实现类实例。工厂里的 ifelse 可以接受——它只做一件事：创建。后续可以用 `Map<Integer, Supplier<ICommodity>>` 进一步消除 switch，新增奖品只需往 Map 里加一行。第四步，调用方变干净了——Controller 不再包含任何业务逻辑，只做两件事：调工厂拿实例，调方法。

重构后对比：Controller 从十几行 ifelse 缩减到两行；新增奖品不再需要改 Controller；参数映射和异常处理各自封装在实现类内部，互不干扰。工厂方法满足单一职责（Controller 只分发，业务逻辑各自独立）和开闭原则（新增奖品只需加实现类和改工厂配置）。本质是把 `new 具体类()` 的决定从调用方挪到工厂，调用方只依赖接口。
