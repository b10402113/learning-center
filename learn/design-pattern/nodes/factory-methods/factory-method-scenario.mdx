# 工厂方法要解决的问题

<LearningGoal>
认识工厂方法要解决的"一坨 ifelse"问题——用营销积分兑换的真实场景，看到 type 分发代码为什么越来越难维护。
</LearningGoal>

## Lesson

营销积分兑换系统中，用户完成任务后获得积分，积分可以兑换不同类型的奖品——优惠券、实物商品、爱奇艺兑换卡。三者对接的第三方接口完全不同：`sendCoupon` 返回 `CouponResult`，`deliverGoods` 返回 `Boolean`，`grantToken` 返回 `void`。参数形态不同，返回类型也不同。

最直觉的写法是在 Controller 里按 `awardType` 加 ifelse 分支，每个分支调对应的第三方服务。这段代码能跑，测试也能过。但每来一个新奖品类型，就要在 Controller 里加一个 if 块——三种奖品三个分支，十种奖品十个分支，维护成本线性增长。

核心矛盾是分发逻辑和业务逻辑纠缠在同一个方法里。优惠券的参数映射、商品的异常处理、兑换卡的调用方式全挤在 Controller 的 ifelse 块中，改一处容易碰另一处。单一职责被违反，开闭原则被打破——新增奖品必须修改已有代码。这就是工厂方法要解决的"一坨 ifelse"问题：把"用哪个具体实现"的决定从调用方挪走，让每种产品的业务逻辑各自独立。
