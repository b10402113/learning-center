# 外觀模式的意圖與白名單痛點

## Learning goal

<能說出外觀模式「降低調用方複雜度」的意圖，並用白名單 ifelse 場景說出為什麼需要這個模式>

## Lesson

用戶登錄一個網站，現在只要一鍵微信登錄。但在早期，註冊一個賬號要填姓名、昵稱、手機號、QQ、郵箱、住址……一大堆信息。從用戶的角度看，操作變簡單了；從服務端的角度看，是有人把「從各渠道獲取用戶信息、獲取不到就引導補全、補全後發獎勵拉活躍」這些複雜邏輯包了起來，對前端只暴露一個簡單的接口。這就是外觀模式（Facade Pattern）的直覺：<strong>在調用方與複雜子系統之間加一個統一的包裝層，讓調用方只關心「用什麼」，不關心「怎麼做」</strong>。

你在一個電商平台做後端，有一個查詢用戶信息的接口，方法體裡直接返回用戶數據，很乾淨。但產品說：「上線前要先開白名單測試，只有白名單裡的用戶才能訪問。」最直覺的做法是直接在方法裡加一段 <code>userList.contains(userId)</code> 的判斷——不在白名單就返回攔截信息，在就放行。一個接口加一段 if，看起來很快。

但想想實際的項目：接口不止一個，查詢用戶、查詢訂單、查詢商品……每個接口都要加白名單。白名單邏輯變了（比如從 userId 改成 userName），你要改多少個方法？而且白名單只是開始，將來可能還要加簽名校驗、限流、日誌審計——每種橫切需求都重複一遍？業務代碼被塞滿了「跟業務無關」的判斷，讀代碼的人要分清哪些是核心邏輯、哪些是輔助邏輯。核心問題是：<strong>橫切關注點（cross-cutting concern）——像白名單、簽名校驗、限流這類「所有接口都要做的事」——直接塞進每個接口方法裡，會導致大量重複、難以維護</strong>。

外觀模式的思路是：把這類通用邏輯從業務方法裡抽出來，放到一個統一的包裝層（facade）裡。業務方法不變，包裝層在外面攔截和處理。一個生活類比：你去銀行辦業務，不用分別找櫃員、風控、會計、清算——大堂經理就是「外觀」，他幫你把複雜的內部流程包裝成「取號→辦理→走人」的簡單步驟。在 Spring 生態中，這種包裝層最常見的落地形態就是自定義 starter 中間件——把通用邏輯封裝成一個 jar 包，業務方引入依賴、加一個注解就生效，完全不用改業務代碼。

外觀模式是 GoF 23 種設計模式中的<strong>結構型模式</strong>（Structural Pattern），關注的是「類和對象怎麼組合、怎麼形成更大的結構」。它特別適合的場景是：子系統內部很複雜，但調用方只想用一個簡單的入口。白名單過濾、第三方 SDK 封裝（支付、短信、OSS）、微服務網關統一入口、ORM 框架把 JDBC 包裝成一個 selectOne——這些都是外觀模式的典型應用。判斷標準：如果你發現同一段邏輯在多個地方重複出現，而且它跟核心業務無關，就該考慮用外觀模式抽成中間件。
