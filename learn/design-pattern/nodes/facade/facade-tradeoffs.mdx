# 外觀模式的適用邊界與取捨

## Learning goal

<能說出外觀模式的適用邊界——何時用、何時不該用、與中介者/適配器的區別>

## Lesson

回顧一下我們做了什麼：把散落在每個接口方法裡的白名單 ifelse，抽成了一個 SpringBoot starter 中間件。業務方加一個注解就生效，不用改一行業務代碼。外觀模式的收益可以總結為三點：降低複雜度（調用方只面對一個簡單入口，不用理解子系統內部細節）、提高復用性（白名單中間件可以被任何 SpringBoot 工程引入，不用每個項目重寫）、隔離變化（白名單邏輯改了只改中間件，業務代碼完全不受影響）。

外觀模式不是萬能藥。它的適用條件很明確：跨多個接口的共性需求（白名單、簽名校驗、限流、日誌審計——這些「所有接口都要做的事」）、子系統內部複雜但調用方只想簡單用（比如 ORM 框架把 JDBC 連接、SQL 解析、結果映射包裝成一個 selectOne）、需要統一治理（一個地方改，所有接口都生效）。反過來，只有一兩個接口、業務邏輯本身就需要在方法內部、子系統本身就不複雜——這些場景不適合外觀模式。為兩個方法硬造一個中間件，是過度設計。記住：<strong>設計模式是工具，不是信仰。「為用而用」比「不用」更糟糕</strong>。

外觀、中介者、適配器這三個模式都涉及「中間加一層」，但意圖完全不同。外觀（Facade）的意圖是簡化調用方對子系統的訪問——類比大堂經理，你不用找各個部門，找我就行。中介者（Mediator）的意圖是集中協調多個對象之間的交互——類比塔台，飛機之間不直接通信，都通過我協調。適配器（Adapter）的意圖是讓不兼容的接口能一起工作——類比轉換插頭，歐標轉國標。關鍵區分：外觀是「簡化」，中介者是「協調」，適配器是「轉換」。實際項目中這三個模式經常組合使用，比如 MyBatis 框架：SqlSession 是外觀（簡化 JDBC 調用），SqlSessionFactoryBuilder 是中介者（協調配置解析、連接建立、Session 創建），ResultMapper 是適配器（把 ResultSet 轉成 Java 對象）。
