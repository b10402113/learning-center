# 觀察者模式

## Learning goal

講清觀察者「一對多通知」的意圖，用搖號中籤通知場景，能對照 MQ 事件經驗

## Steps

1. [[learn/design-pattern/nodes/observer/observer-intent|觀察者的意圖——一對多通知]] — 認識觀察者「一對多通知」的意圖，用搖號中籤場景理解核心流程與輔助流程的分離
2. [[learn/design-pattern/nodes/observer/observer-monolith|一把梭的耦合代價]] — 認知「一把梭」把輔助流程塞進核心方法的耦合代價（after step 1）
3. [[learn/design-pattern/nodes/observer/observer-structure|觀察者模式的三層結構]] — 掌握 EventListener + EventManager + 業務抽象類的三層結構，能對比前後代碼說出解耦收益與使用邊界（after step 2）

## Lesson

觀察者模式解決的核心問題是「一個動作發生後，要通知多個不相關的接收方」。生活中類似槍聲一響、信號兵傳達命令——槍聲（被觀察者）發生時，多個觀察者（信號兵、士兵）各自收到並處理，彼此之間沒有直接耦合。

在後端開發裡，你一定發過 MQ 消息、監聽過 Spring 事件——這些都是觀察者思路的落地。本節用「小客車搖號中籤通知」把這個模式從「概念」拉到「代碼結構」：先看一把梭把簡訊和 MQ 全塞進一個方法的痛苦，再看觀察者模式如何把核心流程與輔助流程解耦，讓新增通知方式只需新增一個監聽器、不用改核心代碼。
