# 觀察者的意圖——一對多通知

## Learning goal

認識觀察者「一對多通知」的意圖，用搖號中籤場景理解核心流程與輔助流程的分離。

## Lesson

戰場上，指揮官扣下扳機，槍聲一響——信號兵聽到後把命令傳達給各個部隊。信號兵不需要知道是哪把槍、什麼子彈，他只聽到「砰」，就知道該傳令了。

這就是觀察者模式（Observer Pattern）的直覺模型：<strong>一個動作發生時，自動通知多個接收方，雙方之間沒有直接耦合</strong>。槍聲不認識信號兵，信號兵也不需要綁定某把槍——只要有人在「聽」，槍聲就會被聽見。觀察者模式屬於行為模式，它的核心意圖用一句話說：

> 定義一對多的依賴關係，當一個對象（被觀察者）狀態改變時，所有依賴它的對象（觀察者）都會自動收到通知並更新。

你在後端開發裡早就接觸過它的落地形態：MQ 的 Producer 發一條消息、多個 Consumer 各自消費，就是一對多通知的經典實現；Spring 的 @EventListener 讓 ApplicationEventPublisher 發事件、多個方法各自處理，是進程內的觀察者；Redis Pub/Sub 讓 Publisher 發佈頻道、多個 Subscriber 各自收到，是分佈式觀察者。它們的共同點：一個「事件源」發生變化，多個「監聽方」自動響應，彼此不直接調用。

用「小客車指標搖號」來做具體場景：每次搖號結束後，你需要執行搖號算法判斷用戶是否中籤（核心流程），還需要給用戶發簡訊通知結果（輔助流程 A）、往 MQ 發消息讓外部系統同步數據（輔助流程 B）。核心流程（搖號算法）很少變化，輔助流程（簡訊、MQ）經常變化——今天發簡訊，明天可能加推送，後天可能加郵件。如果把輔助流程直接寫進搖號方法裡，每加一種通知就要改核心代碼，就像把信號兵綁在指揮官身上。觀察者模式的做法是：讓核心流程只管「發生」，輔助流程各自「訂閱」——你來聽我就通知你，你不來也不影響我。

理解觀察者模式的第一步，是學會區分「核心流程」和「輔助流程」：核心流程是業務主鏈路，不常變化，對應被觀察者（Subject）；輔助流程是通知、日誌、統計，隨需求增減，對應觀察者（Observer）。觀察者模式讓這兩類流程解耦——核心流程不需要知道有多少個輔助流程，輔助流程也不需要知道核心流程的內部細節。

> 觀察者模式 = 一個動作發生時，自動通知多個不相關的接收方，彼此沒有直接耦合。
