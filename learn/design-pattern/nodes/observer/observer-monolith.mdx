# 一把梭的耦合代價

## Learning goal

認知「一把梭」把輔助流程（簡訊/MQ）塞進核心方法的耦合代價，作為觀察者模式重構的動機。

## Lesson

「一把梭」是開發者對最粗暴實現方式的俗稱——把所有功能按順序寫在一個方法裡，不做任何分層或解耦。在搖號場景中，一把梭的意思是：搖號、發簡訊、發 MQ，三件事全塞進一個 <code>doDraw</code> 方法裡。

具體的代碼形態是這樣的：方法內部按順序執行三件事——先調用 <code>minibusTargetService.lottery(uId)</code> 拿到搖號結果，再用 logger 打印簡訊通知，再用 logger 打印 MQ 記錄，最後返回 <code>LotteryResult</code>。測試能跑通，結果也符合預期。

但代碼能跑不代表設計好。一把梭的問題在於輔助流程（簡訊、MQ）與核心流程（搖號）耦合——簡訊和 MQ 的邏輯直接寫在核心方法裡，每加一種通知就要改這個方法。具體有三個痛點：修改風險（改簡訊邏輯可能影響搖號結果，不敢改、改了怕出事）、擴展困難（加一種通知就要改 doDraw，方法越來越長）、職責不清（一個方法做三件事，後人看不懂、不知道該改哪裡）。你可能見過更極端的情況：一個類幾千行，if-else 分支堆出來的業務大類型。一把梭就是這種「一坨代碼」的起點。

生活類比：你是廚師（核心流程），但你同時在做傳菜、結帳、積分、同步四件輔助的事。每來一個新需求，你就多一件事，廚房就沒人管了。觀察者模式的做法是：廚師只管做菜，傳菜員、收銀員、積分系統各自訂閱「菜做好了」這個事件——你做你的菜，他們做他們的事。

一把梭 vs 觀察者的核心差異：一把梭把輔助流程與核心流程混在一起，加新通知要改核心方法，改輔助可能影響核心；觀察者讓核心流程只處理核心邏輯，輔助流程各自獨立為監聽器，加新通知只需新增類，互不影響。這就是觀察者模式重構的動機：把輔助流程從核心方法裡「搬出來」，讓它們各自獨立。

> 一把梭 = 把所有事塞進一個方法，改一個怕動另一個；觀察者 = 各做各的，互不干擾。
