# 觀察者模式的三層結構

## Learning goal

掌握 EventListener + EventManager + 業務抽象類的三層結構，能對比前後代碼說出解耦收益與使用邊界。

## Lesson

用觀察者模式重構搖號服務，代碼分成三層。第一層是事件監聽：定義 EventListener 接口，只有一個方法 <code>doEvent(LotteryResult result)</code>，任何想「聽」搖號結果的輔助流程都實現這個接口。具體實現有兩個：<code>MessageEventListener</code> 打印簡訊通知，<code>MQEventListener</code> 打印 MQ 記錄，每個監聽器只做一件事。

第二層是事件管理器 EventManager：用 <code>Map&lt;Enum&lt;EventType&gt;, List&lt;EventListener&gt;&gt;</code> 按事件類型分組存放監聽器，提供 subscribe（訂閱）、unsubscribe（取消訂閱）、notify（通知，遍歷該類型的所有監聽器逐個調用 doEvent）三個方法。用枚舉 EventType.MQ 和 EventType.Message 限定事件類型，新增事件類型只需在枚舉裡加一個值。

第三層是業務抽象類 LotteryService，用模板方法思想編排流程：公開方法 <code>draw(uId)</code> 先調子類的 <code>doDraw(uId)</code> 拿結果，再觸發事件通知；<code>doDraw</code> 是抽象方法，由繼承者 LotteryServiceImpl 實現核心搖號邏輯。業務實現類只重寫 doDraw，核心方法裡已經沒有任何簡訊或 MQ 的代碼，輔助流程全部交給事件管理器處理。

重構後測試輸出跟一把梭完全一致，但代碼結構天差地別：核心方法從三段邏輯混在一起變成只有一行核心調用；新增通知從「改核心方法」變成「新增監聽器類 + subscribe」；調用方從「知道所有輔助流程」變成「只看到 draw，不知道通知存在」。觀察者模式結構上滿足開閉原則——對擴展開放（新增監聽器即可）、對修改封閉（不改現有代碼）。

使用邊界：觀察者模式有兩個已知限制——難控調用順序（多個監聽器的通知順序取決於 subscribe 先後）、結果回傳受限（通知是單向的，觀察者處理完後很難把結果回傳給被觀察者）。任何設計模式都不是單獨使用的，引入是為了更易擴展和維護，不能反而把結構搞複雜。

> 觀察者模式 = EventListener（做什麼） + EventManager（怎麼通知） + 業務抽象類（只管核心）。
