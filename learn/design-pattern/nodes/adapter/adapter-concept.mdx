# 適配器的直覺：把不兼容的「口」統一起來

## Learning goal

能說出適配器模式的核心意圖——把原本不兼容的接口通過適配修改做到統一——並用生活直覺和業務場景說出「為什麼需要它」。

## Lesson

你到美國出差，帶了台灣的三孔插頭，發現旅館牆上只有兩孔扁插座。你不可能改旅館的牆，也不可能把自己的插頭鋸掉——你買了一個轉接頭。轉接頭做的事情很簡單：把一個「口」翻譯成另一個「口」。兩邊的電都是一樣的，只是形狀不同，轉接頭讓它們能接上。

適配器模式（Adapter Pattern）就是程式世界裡的這個轉接頭。當你的系統想統一調用，但外來的接口各有各的命名、各有各的返回值，適配器在中間做一層翻譯，讓調用方只面對一個統一的口。

如果你去 Spring 的原始碼裡搜 `Adapter`，會跳出一堆實現類：`UserCredentialsDataSourceAdapter`、`HttpRequestHandlerAdapter`、`MessageListenerAdapter`……框架這麼愛用這個模式，是因為它要整合各種第三⽅，每個第三⽅都有自己的 API 風格。Spring 的做法不是要第三⽅改接口，而是在中間加一層適配器，把差異抹平。就像你家的插座不用管你帶的是哪國的插頭——轉接頭負責翻譯。

來看一個具體的業務場景。假設你負責一個行銷系統，需要接收各種 MQ（Message Queue，消息隊列）消息來觸發獎勵發放。三個不同來源的 MQ 傳遞的都是同一個意思：「某個用戶在某個時間做了某件事」。但欄位名完全不一樣：

| MQ 消息 | 用戶 ID 欄位 | 時間欄位 | 業務 ID 欄位 |
| --- | --- | --- | --- |
| `create_account`（開戶） | `number` | `accountDate` | `number` |
| `OrderMq`（內部訂單） | `uid` | `createOrderTime` | `orderId` |
| `POPOrderDelivered`（第三方訂單） | `uId` | `orderTime` | `orderId` |

用戶 ID 分別叫 `number`、`uid`、`uId`，說的是同一件事，名字卻完全不同。你的系統不可能為每種 MQ 寫一套處理邏輯——那樣新增一個 MQ 就要改一次代碼，改到天荒地老。

最直覺的做法是為每種 MQ 建一個消費類，在 `onMessage` 裡用 `JSON.parseObject` 解析消息後逐欄位取出處理。三個 MQ 就是三個類，十個 MQ 就是十個類。每個類做的事情幾乎一樣——解析 JSON、取出欄位、轉成統一格式——差別只在欄位名不同。這種重複就是適配器要消滅的壞味道。

適配器的回答是：不管外面的 MQ 欄位叫 `number`、`uid` 還是 `uId`，在中間加一層翻譯，讓進了系統之後的欄位全部統一。不改你的系統，也不改第三方的接口，而是加一層適配。這就是適配器模式的核心意圖：把原本不兼容的接口，通過適配修改，做到統一輸出。
