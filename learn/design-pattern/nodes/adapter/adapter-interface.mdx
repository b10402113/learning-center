# 接口適配：同義不同出參怎麼統一

## Learning goal

能定義統一適配接口 OrderAdapterService，把兩個判斷首單方式完全不同的服務包裝成一致的 `isFirst(uId)` 調用。

## Lesson

行銷系統升級了——不只是發獎勵，還要判斷「是不是首單用戶」才發。但系統有兩個來源可以查首單：內部訂單服務 `OrderService` 提供 `queryUserOrderCount(uId)` 方法，返回 `long` 型的訂單數量，你需要自己判斷數量 ≤ 1 就是首單；第三方服務 `POPOrderService` 提供 `isFirstOrder(uId)` 方法，直接返回 `boolean`。

兩個接口做的是同一件事（判斷首單），但方法名不同、返回值不同、判斷邏輯也不同。業務代碼如果用 if-else 硬判斷——「如果是內部訂單就查數量再比較，如果是 POP 就直接取返回值」——每新增一種訂單來源就要加一個 else 分支，代碼越寫越長。

適配器的做法是定義一個統一適配接口 `OrderAdapterService`，只有一個方法：`boolean isFirst(String uId)`。不管底下用什麼方式判斷首單，業務代碼只面對這個接口。

`InsideOrderService` 實現這個接口，內部包裝 `OrderService`，在 `isFirst` 方法裡調用 `queryUserOrderCount(uId)` 然後判斷 ≤ 1——把「查數量再比較」的邏輯封裝在適配器內部。`POPOrderAdapterServiceImpl` 也實現這個接口，內部包裝 `POPOrderService`，直接轉發 `isFirstOrder(uId)`。

業務代碼只需要拿到一個 `OrderAdapterService` 實例，調用 `adapter.isFirst("100001")` 就能得到結果。不需要關心底下是用數量推導還是直接判斷——差異被隔離在適配器裡。

測試驗證：用 `POPOrderAdapterServiceImpl` 調用 `isFirst("100001")` 輸出 `true`（第三方首單），用 `InsideOrderService` 調用同一個方法輸出 `false`（內部已有訂單）。同樣的調用方式，換一個適配器實例就能查不同來源。

MQ 適配和接口適配說的是同一件事：把不兼容的接口通過適配做到統一。差別只在「適配的對象」不同——一個是 MQ 消息體的欄位名，一個是 API 的方法簽名和返回值。核心結構都是統一接口 + 各實現類包裝差異邏輯。
