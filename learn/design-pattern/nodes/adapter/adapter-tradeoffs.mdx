# 適配器的適用邊界與模式選型

## Learning goal

能說出適配器「何時該用、何時不該用」，並在面試中把適配器與策略、橋接、外觀做結構性的區分。

## Lesson

適配器模式的核心價值是「統一輸出」——把原本不兼容的接口通過適配修改做到統一，讓業務代碼只面對一個統一的口。使用適配器後代碼乾淨整潔、易於維護，減少大量重複的判斷和使用，更易於擴展。但適配器不是萬金油，它有明確的使用邊界。

問自己三個問題來判斷是否該用適配器：系統想統一調用，但第三方接口格式不同？不想改第三方的代碼，也不想改自己的業務代碼？需要在中間加一層翻譯？三個都是「是」，適配器就是候選。

如果問題不在「接口不兼容」，就該用其他模式。需要替換算法（如不同優惠計算方式）用策略模式（Strategy Pattern）；需要隔離兩個維度的變化（如支付渠道 × 支付方式）用橋接模式（Bridge Pattern）；需要簡化複雜子系統的調用（如白名單中間件）用外觀模式（Facade Pattern）。

面試最常問的是「適配器 vs 策略 vs 橋接 vs 外觀」。它們結構上都有「接口 + 多個實現」或「兩個部分組合」的相似之處，但思路完全不同。適配器的動機是「不得不做」——第三方接口格式不同，你沒得選，只能翻譯。策略的動機是「主動選擇」——算法都對，你選哪個取決於場景。橋接的動機是「預先分離」——你還沒寫代碼就決定把兩個維度拆開。外觀的動機是「由內向外簡化」——把內部的多個調用收成一個入口。

適配器在框架中無處不在。Spring 源碼搜 `Adapter` 能看到大量實現類：`UserCredentialsDataSourceAdapter`（數據源適配）、`HandlerAdapter`（Controller 適配）。MyBatis 的 `ResultSetHandler` 也在做結果集適配。工廠方法模式中不同種類獎品的處理其實也是適配器的應用——每種獎品有自己的創建和發放方式，工廠統一入口。當你讀框架原始碼看到 `Adapter` 這個詞，馬上可以意識到：這裡在做接口統一。

設計模式在實際使用中往往綜合運用、不會單一出現。適配器常和代理模式搭配（代理類根據配置自動路由到正確的映射表），也常和工廠方法配合（工廠根據類型返回對應的適配器實例）。掌握適配器的關鍵不只是記住它的結構，而是能在具體場景中判斷：這個問題是不是「接口不兼容」——如果是，適配器就是答案。
