# 組合模式的適用邊界

## Learning goal
知道何時該用組合模式、何時不該用，並能與裝飾器、代理等相似模式做區分。

## Lesson

組合模式的適用邊界可以用三個條件來判斷：**同質邏輯**（多個節點做的是同一種事，都是「根據某個屬性做分流」）、「不同組合」（這些節點可以按不同方式串接成不同路徑）、「統一調用」（調用方不想關心內部結構）。三個同時滿足才適合用組合模式。

書中明確指出一個邊界：**功能差異非常大的接口做包裝會比較困難**。如果節點有「性別判斷」「年齡判斷」「地區判斷」——同質，適合組合。但如果節點有「性別判斷」「支付處理」「發送郵件」——做的事完全不同，硬塞進一棵樹會很彆扭，因為過濾器的 `filter` 和 `matterValue` 接口無法統一。此外，只有一種固定組合、或調用方需要精細控制執行順序的場景，也不需要組合模式。

和裝飾器的區別是「平鋪的樹 vs 串起來的糖葫蘆」。組合模式是樹形結構（一對多），節點各自平行、按關係組織，引擎統一入口從根走到果實。裝飾器是鏈式包裹（一對一），外層持有內層引用、逐層疊加功能。和代理的區別是「樹形遍歷 vs 動態攔截」——MyBatis mapper 的 JDK 動態代理是接口實現+動態代理，和組合模式的「把判斷邏輯組合成樹」是完全不同的問題域。和策略的區別是「多層決策路徑 vs 扁平算法互換」——只是在 A/B/C 三個算法裡選一個用策略，需要 A 判斷完再走 B 或 C 的多層路徑才用組合。

服務包裝場景（把身份證/銀行卡/手機號校驗組合成不同流程）本質上也是組合模式：原子服務=節點，組合方式=樹結構，統一入口=引擎。掌握了這些邊界，面試時被問到「組合模式和 XX 模式怎麼選」就能講出深度。
