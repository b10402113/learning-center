# 組合模式的思路與決策樹場景

## Learning goal
能說出組合模式「把相似邏輯組合成樹形結構、統一調用」的核心思想，並用規則決策樹場景理解 ifelse 直寫為什麼失控。

## Lesson

你可能寫過這樣的方法：外層按性別判斷，內層按年齡判斷，四個分支四個結果。需求方說「再加一個地區維度」——原本四個分支變成八個，再加一個「職業」維度就十六個。每次加維度，行數不是線性成長，而是**指數膨脹**。更痛的是，改一個分界線（25→30），要到一堆 ifelse 裡找所有對應的魔法值，漏改一個就是客訴級的 bug。

用一個具體場景來看：營銷系統根據用戶**性別**和**年齡**發放不同優惠券。性別→年齡→發券結果，三層分流。ifelse 直寫能跑、新人也能看懂，但有兩個致命問題——每加一個維度分支數量翻倍，業務邏輯和判斷結構綁死在一起。

**組合模式（Composite Pattern）**的解決思路：把相似的邏輯節點（性別判斷、年齡判斷）組合成一棵樹，對外提供統一的服務。就像螺絲和螺母——每個零件是獨立的，但它們可以通過螺紋鏈接組合成不同結構。重要的不是螺絲本身，而是它們按什麼關係組織在一起。調用方只需要說「用這棵樹做決策」，不需要關心樹裡面的判斷邏輯是什麼。

| 維度 | ifelse 直寫 | 組合模式 |
| --- | --- | --- |
| 新增判斷維度 | 加一層 ifelse，行數翻倍 | 新增一個過濾器節點，組進樹裡 |
| 改業務規則 | 在 ifelse 裡找魔法值改 | 改節點的配置參數 |
| 不同場景用不同規則 | 複製一份代碼改參數 | 用不同 treeId 指向不同樹 |
| 可配置性 | 硬編碼在程式碼裡 | 可存入資料庫、可圖形化配置 |
| 符合開閉原則 | ❌ 每次都改現有代碼 | ✅ 新增節點不改既有結構 |

最後一行是關鍵：**開閉原則**（Open-Closed Principle）——對擴展開放，對修改關閉。組合模式的樹結構一旦建好，新增判斷邏輯只需要加一個新的過濾器節點，不需要改動現有的樹結構或引擎代碼。而 ifelse 每次都是「改現有代碼」，完全違反開閉。

判別特徵：遇到類似場景，如果同時符合「同質邏輯」（多個相似判斷節點）、「不同組合」（可按不同方式串接）、「統一調用」（調用方不想關心內部結構），可以考慮組合模式。下一節會拆解組合模式的四個角色——節點、鏈路、果實、過濾器，以及引擎從根到果實的遍歷流程。
