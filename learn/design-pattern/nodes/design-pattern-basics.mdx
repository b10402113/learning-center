# 設計模式與六大原則

## Learning goal

用六大原則建立「好代碼」的判斷基準，能說出設計模式解決什麼問題、何時該用

## Steps

1. [[learn/design-pattern/nodes/design-pattern-basics/what-is-design-pattern|設計模式是什麼]] — 用「擦屁屁紙 80% 保護手」的開篇意象，說出框架源碼難讀的根源與模式的定位
2. [[learn/design-pattern/nodes/design-pattern-basics/six-principles|六大原則：判斷好代碼的尺子]] — 逐一講清六大原則，建立好代碼的判斷基準（after step 1）
3. [[learn/design-pattern/nodes/design-pattern-basics/pattern-taxonomy|三大分類：23 個模式的全局地圖]] — 用目錄建立三分類與場景對應的地圖（after step 1）
4. [[learn/design-pattern/nodes/design-pattern-basics/when-to-use|何時該用設計模式]] — 綜合原則與地圖，說出何時該用、不為用而用（after steps 2–3）

## Lesson

這個節點是整門課的起點，先回答三個問題：設計模式是什麼、它靠什麼來判斷代碼好不好、什麼時候該搬出來用。開篇的意象是「擦屁屁紙 80% 的面積是保護手的」——你讀 Spring、MyBatis、Dubbo 覺得費勁，不是因為看不懂核心，而是因為框架裡真正核心的邏輯只佔約 20%，其餘是保證核心流程正常運行的輔助代碼。設計模式不只是一種「解法」，而是多年工程經驗沉澱下來、在框架中被綜合運用的設計思路。

沿著這條線，先用六大原則（單一職責、里氏替換、依賴倒置、接口隔離、迪米特、開閉）給「好代碼」裝上一把量尺，再照目錄把 23 個模式按創建型/結構型/行為型排成全局地圖，最後合流回答「何時該用」——模式是為了解決真實問題，不是拿來炫耀的技巧。走完這四步，你就有能力在後續每個模式章節裡，對著場景判斷它值不值得用、解決了哪一條原則。
