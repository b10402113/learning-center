# 创建型模式对比

## Learning goal

能对比 Builder（分步组装）、Prototype（克隆模板）、Factory（类型分发）三种创建型模式的适用场景与取舍。

## Lesson

三种创建型模式解决的都是"怎么造对象"，但切入角度完全不同。

**Builder（建造者）** 的核心是分步组装。当一个对象有多个部件、每个部件有多种选择、组合方式又经常变化时，把构建过程从最终产品中拆出来，用 Fluent API 让调用方像写配置一样逐步 set，最后调 `build()` 拿到完整对象。装修套餐就是典型——基础材料稳定，但组合方式每次不同。

**Prototype（原型）** 的核心是克隆模板。当对象的初始化涉及数据库查询、远程调用或大量计算，重复创建代价很高时，不如先造好一个模板对象，后续直接 `clone()` 再微调。考卷生成就是这种情况——题库查一次，模板克隆多次。

**Factory（工厂方法）** 的核心是类型分发。定义一个创建接口，让子类决定实例化哪个具体类。当你面对多个不兼容的第三方接口（比如三家支付渠道的 SDK），需要按类型选择调用哪个实现时，工厂方法把 `new` 的决定封装起来，调用方不再关心具体类。

### 维度对比

| 对比维度 | Builder | Prototype | Factory |
| --- | --- | --- | --- |
| 核心动作 | 分步 set，最后 build | clone 一个已有对象 | 调用工厂方法，返回子类实例 |
| 对象复杂度 | 高（多部件、多配置项） | 中到高（初始化成本高） | 不限，重点在类型选择 |
| 创建开销 | 每次构造，但 Builder 可复用 | 克隆快，但深拷贝集合有坑 | 每次 new，开销取决于具体实现 |
| 变化维度 | 部件组合方式常变 | 模板少变、克隆多 | 新增产品类型时扩展 |
| 扩展方式 | 加 set 方法 | 加新的原型对象 | 加新的工厂子类 |
| 典型坑 | 遗漏必填参数（编译期可防） | 浅拷贝导致共享可变状态 | 类爆炸（子类太多） |

### 场景决策规则：看到 X，想到 Y

**看到构造函数参数超过 4 个，且组合方式频繁变化** → 用 Builder。Fluent API 让调用方只 set 需要的参数，不必记住参数顺序。

**看到对象初始化要查 DB、调 RPC、或做大量计算，但使用频率低** → 用 Prototype。从模板 clone 再微调，比从头构建省得多。

**看到多个不兼容的第三方接口，需要按类型分发调用** → 用 Factory。把 `new` 的决定封装到工厂方法里，调用方不再关心具体类。

**看到 if-else 或 switch 根据类型 new 不同的子类** → 也是 Factory。这是最经典的重构信号——把分支逻辑下沉到工厂。

### 反模式：强行套用

不要为了用模式而用模式。如果对象只有一个构造函数参数、初始化不涉及外部调用、也没有多种实现需要分发——那就老老实实 `new`。过度设计比没有设计更难维护。

书里反复强调一个观点：选择模式要看场景，不要硬套。框架之所以强大，不是因为用了某个"高级"模式，而是因为它把多种模式组合在一起，各司其职。

### 框架如何组合多种模式

Spring Boot 就是一个活教材。它同时用了 Factory（BeanFactory 按类型创建 Bean）、Builder（SpringApplicationBuilder 链式配置启动参数）、Prototype（`@Scope("prototype")` 每次请求创建新实例）——三种创建型模式各解决一个问题，共同支撑整个框架的对象创建体系。能根据场景快速判断该用哪种，比死记类图有用得多。
