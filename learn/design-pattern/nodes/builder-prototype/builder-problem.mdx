# 装修报价的 ifelse 堆砌

## Learning goal

认识装修报价场景中 ifelse 堆砌的坏味道，理解"分步组装复杂对象"比"一次性创建"更灵活的动机。

## Lesson

一家装修公司提供三种装修套餐：豪华欧式、轻奢田园、现代简约。每种套餐由若干类物料组合而成——吊顶（一级顶/二级顶）、涂料（多乐士/立邦）、地板（德尔/圣象）、瓷砖（东鹏/马可波罗）。所有物料实现同一个 `Matter` 接口，对外暴露场景、品牌、型号和每平米单价，系统按客户选择的套餐和房屋面积计算总价。这个场景在结构上和你日常写的代码非常相似：多个部件各有一个可选集合，最终组合成一个完整的产品。

问题出在实现方式上。`DecorationPackageController.getMatterList(area, level)` 用 if-else 把每种套餐的物料组合硬编码在一个方法里——level == 1 走豪华欧式，level == 2 走轻奢田园，level == 3 走现代简约。每新增一个套餐，就得追加一个 else if 块。套餐种类越多，这个方法就越膨胀，变成"贴膏药式的修修补补"。具体来看，这段代码至少违反了三条原则：它把"选什么物料"和"怎么创建物料对象"这两件事耦合在一起（单一职责违反）；物料种类和套餐种类按乘积增长，代码量随之爆炸（组合爆炸）；组合逻辑写死在 Spring Controller 里，其他系统无法复用（无法复用）。如果涂料品牌从多乐士换成立邦，或者瓷砖从东鹏换成马可波罗，你都得动同一个方法——这不是好的修改比例。

核心洞察在这里：装修套餐不是一个"一次性完成"的动作，而是一个"分步组装"的过程——先选吊顶，再选涂料，再选地板，再选瓷砖。把构建过程从最终产品中独立出来，你才能灵活地替换任何一个步骤。这和你在 Spring Boot 项目里见过的 type 字段分派、region 配置选择、role 权限组合是同一类问题——组合逻辑被硬编码在决策入口。Builder 模式的动机不是为了"少写 if-else"，而是因为组装过程本身就是一个值得独立建模的领域概念。下一步，你会看到如何用流式 API 把这个组装过程写得既灵活又优雅。
