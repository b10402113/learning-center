# 为什么不用继承而用装饰器

## Learning goal

能对比继承扩展与装饰器扩展的取舍，理解开闭原则在运行时的体现。

## Lesson

继承扩展有三个致命问题：编译时锁定功能组合、子类爆炸（M 个功能需要 2^M - 1 个子类）、以及每加一个功能就要新建子类导致违反开闭原则。3 个功能要 7 个子类，5 个功能要 31 个——组合爆炸让代码越来越难维护。

装饰器用运行时组合替代编译时绑定。每个功能是一个独立的装饰器类，通过构造函数套娃组合——M 个功能只需要 M 个装饰器，线性增长不爆炸。加新功能就写新的 ConcreteDecorator，不改原始类，完美满足开闭原则。运行时可以根据配置动态决定组合哪些装饰器，继承做不到这一点。

取舍判断很简单：功能扩展是固定的、不变的变体（比如模板方法的骨架子类），用继承更直接；功能扩展是动态的、需要运行时组合的（比如 JDK I/O 流、SSO 拦截器多层扩展），用装饰器。看到子类爆炸的信号，就是装饰器登场的时机。
