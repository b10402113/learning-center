# 何時該用設計模式

<LearningGoal>
能綜合六大原則與三分類地圖，說出設計模式該在什麼真實問題下用、如何對照框架的綜合運用，不為用而用。
</LearningGoal>

## Lesson

現在合流：你手上有一把尺子（六大原則）和一幅地圖（三大分類）。該用模式的完整順序是——先聞到壞味道（又一個 ifelse、類又長胖、又要複製貼上），拿尺子量它違背了哪條原則（分支多 → 開閉、類肥 → 單一職責、到處 new 具體類 → 依賴倒置），再對地圖找哪個分類、哪個模式正好治這個病。你重構 ifelse 的經歷就是完整複述：發獎類型一多就要改大方法 → 違背開閉 → 用創建型的工廠方法或行為型的策略 → 新獎品加新類、老代碼不動。

框架的「綜合運用」給兩個啟示：讀源碼別指望一個模式對號入座——Spring 裡的 `Adapter` 實現類可能同時摻著工廠、代理、模板方法，作者原話是「任何設計模式都不是單獨使用的」；寫代碼時同一個場景常要幾種模式組合，一個發獎服務可同時用工廠（創建）、策略（算法）、模板方法（骨架）。老手「綜合運用」就是這種組合經驗的累積。

同時要踩住三個剎車。一，為用而用是過度設計：代碼已高內聚、簡單直接時硬套橋接反而把結構搞複雜，引入模式的目的是更易擴展和維護，結果相反就是錯了。二，算類膨脹的帳：狀態模式狀態多時實現類多、命令模式的命令×實現組合會讓類爆炸，按投入回報評估——是否經常修改、能否組件化、能否抽離業務與非業務。三，違背原則也照用：訪問者模式公然違背迪米特，不是錯了，而是「這個場景的收益大於那條原則的損失」。一句話總結：該不該用，不是「這模式很流行」，而是「這個真實問題，用這個模式，解決了哪條原則的痛、付出了什麼代價」。
