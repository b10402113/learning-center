# 六大原則：判斷好代碼的尺子

<LearningGoal>
能逐一講清單一職責、里氏替換、依賴倒置、接口隔離、迪米特、開閉六大原則，作為「好代碼」的判斷基準。
</LearningGoal>

## Lesson

書的目錄把六大原則放在 23 個模式之前——模式是「做法」，原則是「尺子」。你的切膚之痛正是最貼的入口：一個類幾千行、ifelse 堆出全部業務，重構成策略/狀態後明顯變好維護。六條原則就是把你那次重構「為什麼好」講清楚的語言。

六條逐一：**單一職責**——一個類只負責一件事，能一句話說清它幹嘛，說不清就是職責混了；**開閉**——擴展靠加新類、不靠改老代碼，發獎 ifelse 加一種商品要動大方法，拆策略後加新獎品只是加一個類；**里氏替換**——凡用父類/接口處換任意子類都不破壞行為，Spring 裡 bean 依賴接口、換實現不崩，就是它的前提；**依賴倒置**——依賴抽象不依賴具體，最熟的例子是 Spring DI，業務依賴 `UserRepository` 接口、實現由容器注入；**接口隔離**——客戶端不該依賴用不到的接口方法，肥接口逼實現類空實現就是不該；**迪米特（最少知道）**——只跟直接朋友打交道，中台把各種獎品接口收到「獎品中心」、外部只調一個入口，就是它的體現。

給六條一個記憶掛鉤：想像一個類的生命故事——單一職責決定它管一件事，里氏替換讓它能被同類頂替，依賴倒置讓它靠接口活著，接口隔離讓朋友只看到該看的，迪米特讓它不越界打聽，開閉讓它加了新功能也不變樣。但要記住：原則是尺子不是法律——書裡的訪問者模式就公然違背迪米特，特定場景下依然值得用。模式是權衡的結果，原則是判斷方向。
