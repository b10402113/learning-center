# 享元模式

## Learning goal

講清享元「共享內部狀態、外部狀態分離」的意圖，用秒殺活動場景，能掛上 Redis 緩存經驗

## Steps

1. [[learn/design-pattern/nodes/flyweight/flyweight-problem|秒殺場景痛點：固定信息為什麼每次都在重建？]] — 識別秒殺查詢中固定信息與變化信息的分界，理解全量查詢的冗餘
2. [[learn/design-pattern/nodes/flyweight/flyweight-concept|享元模式核心概念：內部狀態、外部狀態與享元工廠]] — 掌握享元模式的意圖、內部/外部狀態分離機制（after step 1）
3. [[learn/design-pattern/nodes/flyweight/flyweight-implementation|秒殺場景重構：享元工廠 + Redis + 控制類的完整實現]] — 完整重構代碼結構，理解工廠緩存 + Redis + 控制類的協作（after step 2）
4. [[learn/design-pattern/nodes/flyweight/flyweight-tradeoffs|享元模式的適用邊界與局限]] — 能說出優缺點、與原型模式的共通之處、狀態難拆的警示（after step 3）

## Lesson

秒殺系統從日均十幾單成長到每時段破十萬的過程中，查詢性能成為瓶頸。原始做法是每次查詢都從數據庫或接口取全量數據——活動名稱、描述、時間這些固定不變的信息，每次都重新構建一遍。享元模式的核心思想是把「不變的內部狀態」緩存起來複用，把「會變化的外部狀態」分離出去單獨獲取。這節課用秒殺活動查詢場景走一遍完整的問題→概念→重構→邊界四步。
