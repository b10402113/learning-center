<LearningGoal>
能指出 ifelse 實現審核流轉的可維護性痛點，說清楚為什麼「狀態越多、分支越亂」。
</LearningGoal>

## Lesson

大多數工程師第一次實現審核流轉時，都會寫出類似的代碼：一個大控制器方法，用 <code>if</code> 判斷 <code>beforeStatus</code>（當前狀態），再用嵌套 <code>if</code> 判斷 <code>afterStatus</code>（目標狀態），合法就執行，不合法就返回拒絕。

### 一把梭的樣子

<pre><code>if (beforeStatus == 1) {
  if (afterStatus == 2 || afterStatus == 6) {
    // 合法：編輯中 → 待審核 or 關閉
    execStatus(activityId, beforeStatus, afterStatus);
    return "0000"; // 成功
  } else {
    return "0001"; // 拒絕
  }
} else if (beforeStatus == 2) {
  if (afterStatus == 3 || afterStatus == 4 || afterStatus == 6) {
    execStatus(activityId, beforeStatus, afterStatus);
    return "0000";
  } else {
    return "0001";
  }
} // 繼續往下堆...</code></pre>

這個實現完全能跑。測試也通過了：編輯中→提交審核返回 <code>0000</code>，編輯中→直接開啟返回 <code>0001</code>。

### 問題出在哪？

代碼能跑，不代表代碼沒問題。問題不在「現在」，而在「以後」：

**1. 加新狀態，所有分支都要改。** 假設產品加了一個「草稿」狀態，你要在所有 <code>if</code> 分支裡都加上判斷。漏改一個，就可能出現非法流轉。

**2. 邏輯集中在一個方法裡，誰加了什麼都搞不清。** 三個月後有人改了「編輯中→待審核」的邏輯，但不知道這會不會影響「審核拒絕→撤審」的流程。因為它們全部在同一個方法裡。

**3. 新人看到不敢動。** 新來的工程師打開這個文件，看到幾百行 <code>if-else</code>，根本不敢重構——誰知道改了哪裡會出 bug？

> 「越來越亂就是從點滴開始的。」一開始只有 4 個狀態、每個狀態 2-3 個分支，看起來還行。但狀態和需求是會成長的——等你有 10 個狀態、每個狀態 5 個分支時，這個方法就變成一個 50 行起步的怪物。

### 代碼壞味道

| 壞味道 | 表現 | 後果 |
| --- | --- | --- |
| 嵌套 if 過深 | if 裡面再套 if，三層起步 | 閱讀困難，分支邏輯看不清 |
| 重複判斷 | 多處都判斷 beforeStatus == 1 | 改一處漏一處 |
| 魔法數字 | 0000、0001、狀態用數字 | 不直觀，容易打錯 |
| 單一方法承擔所有邏輯 | 一個方法裡塞了所有狀態轉換 | 無法拆分測試、無法單獨修改 |

### 痛點小結

一把梭 ifelse 在**不需要改動和迭代**的場景下完全可用——如果這是一個寫完就再也不碰的腳本，隨便。但在業務系統中，狀態和規則幾乎一定會變，用 ifelse 堆出來的代碼只會越改越亂。

痛點不是「不能用」，而是「改不動」。
