# 命令模式的意圖與角色映射

<LearningGoal>
說清命令模式「請求封裝成對象、解耦請求與實現」的意圖，並用「顧客→小二→廚師」場景映射出命令、實現者、調用者三層結構。
</LearningGoal>

## Lesson

提到命令模式，很多人會先想到「Ctrl+C / Ctrl+V」——確實，這就是命令模式最直覺的應用場景。但更本質地說，命令模式解決的問題是：**調用方不想關心「誰來做、怎麼做」，只想發出一個請求，並在需要的時候撤銷或排隊**。

它的做法是把「操作請求」封裝成一個對象。就像在餐廳裡，顧客把「廣東菜」這張點菜單交給小二，小二記錄下來轉交給廣東菜廚師。顧客不需要知道廚師是誰，廚師也不需要知道顧客是誰——中間的銜接由小二完成。

命令模式（Command Pattern）屬於行為模式，以數據驅動方式把「命令對象」通過構造函數傳給調用者，調用者再提供操作命令執行的實現方法，把邏輯實現與操作請求分離、降低耦合方便擴展。

### 三個核心角色

把餐廳場景映射到代碼，命令模式有三個核心角色：

| 角色 | 職責 | 餐廳對應 |
| --- | --- | --- |
| 命令（Command） | 封裝「要做什麼」的對象 | 菜品——廣東菜、四川菜、江蘇菜……每個菜品都是一張寫著「我要烹飪」的單子 |
| 實現者（Receiver） | 真正做事情的對象 | 廚師——廣東菜廚師、四川菜廚師……每個廚師知道自己怎麼烹飪 |
| 調用者（Invoker） | 接收命令並觸發執行的對象 | 小二——記錄所有點單，統一下單給廚師 |

### 五要素拆解

加上抽象層，一共五個要素：

| 要素 | 職責 | 餐廳對應 |
| --- | --- | --- |
| 抽象命令類 | 聲明執行命令的接口方法 | 「菜品」接口（聲明 `cook()` 方法） |
| 具體命令實現類 | 接口的具體實現，一組相似行為 | 廣東菜、四川菜等具體菜品 |
| 抽象實現者 | 為命令做實現的接口 | 「廚師」接口（聲明 `doCooking()` 方法） |
| 具體實現者 | 具體的行為實現 | 廣東菜廚師、四川菜廚師等 |
| 調用者 | 處理命令的操作者，對外提供服務 | 小二（持有菜單，統一執行） |

關鍵在於：**命令模式將邏輯實現與操作請求分離，降低耦合方便擴展**。調用者只持有命令對象，不關心具體是哪個廚師在做；實現者只關心自己的烹飪邏輯，不關心是誰點的菜。

### 與策略、狀態的區分

命令模式跟策略模式、狀態模式結構上有些相似，但思路完全不同：

- **策略模式**：「做同一件事的多種算法」——選哪種方式做，外部決定。關注的是「算法互換」。
- **狀態模式**：「同一個對象在不同狀態下表現不同行為」——狀態自己決定怎麼做。關注的是「狀態驅動」。
- **命令模式**：「把請求封裝成對象，解耦誰下單和誰做」——請求本身可以傳遞、排隊、撤銷。關注的是「請求封裝」。

一句話記住：策略管「怎麼做」，狀態管「什麼時候做什麼」，命令管「誰下單、誰執行」。
