# 一把梭實現：ifelse 的痛點

<LearningGoal>
通過「一把梭」ifelse 實現點單系統，理解命令模式要解決的核心問題：邏輯實現與操作請求耦合。
</LearningGoal>

## Lesson

不考慮設計模式時，一個 `XiaoEr`（小二）類就能實現整個點單系統：用 `ConcurrentHashMap<Integer, String> cuisineMap` 存菜品，`order(int cuisine)` 裡用多個 if 語句按菜系編號寫入「某廚師，烹飪某菜」的描述，`placeOrder()` 打印整個菜單。這類複雜場景直接開發也能達到目的，但後續菜品擴展、廚師實現與調用方式會變得非常耦合、難以擴展。

### 一把梭長什麼樣

```java
class XiaoEr {
    private Map<Integer, String> cuisineMap = new ConcurrentHashMap<>();

    public void order(int cuisine) {
        if (cuisine == 1) {
            cuisineMap.put(1, "魯菜廚師，烹飪魯菜");
        } else if (cuisine == 2) {
            cuisineMap.put(2, "川菜廚師，烹飪川菜");
        } else if (cuisine == 3) {
            cuisineMap.put(3, "蘇菜廚師，烹飪蘇菜");
        } else if (cuisine == 4) {
            cuisineMap.put(4, "粵菜廚師，烹飪粵菜");
        }
    }

    public void placeOrder() {
        for (String desc : cuisineMap.values()) {
            System.out.println(desc);
        }
    }
}
```

看起來還行——兩個方法，`order()` 點單、`placeOrder()` 展示菜品。但問題馬上就來了。

### 痛點一：加新菜要改老代碼

現在要加一道「湘菜」。你得在 `order()` 裡再加一個 `else if`。再加一道「浙菜」？又改。再加一道「閩菜」？又改。**每加一道菜，就要動已經穩定的 `order()` 方法**——這違反了開閉原則（對擴展開放、對修改關閉）。

### 痛點二：廚師換人也要改

如果「魯菜廚師」換人了，或者你想用不同的烹飪方式（大火爆炒 vs 小火慢燉），你得改 `order()` 裡對應的描述。烹飪邏輯和點單邏輯完全混在一起。

### 痛點三：無法排隊、無法撤銷

如果你想支持「排隊點單」或者「客戶取消某道菜」，這個 `XiaoEr` 類會變得更複雜——因為「點單」和「執行」是綁死在一起的。

### 一把梭的本質問題

> 單類 + if 判斷類型分支 = 耦合的溫床

大量 if 使代碼難以擴展、不好維護。實際業務邏輯更複雜時，都寫在單類裡會耦合非常嚴重。這就是命令模式要解決的核心問題：**把「點單」（操作請求）和「烹和「烹飪」（邏輯實現）拆開，各自獨立變化**。

建立「沒有模式時的痛點基線」，是理解命令模式解決什麼問題的關鍵。下一課會用三層結構重構這段代碼——加新菜只需加一個新的菜品類，不用動 `XiaoEr`；換廚師只需換一個新的廚師類，菜品類不用改。
