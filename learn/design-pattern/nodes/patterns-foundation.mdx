# 模式思想与六大原则

## Learning goal

能说出设计模式解决什么问题、六大原则各自管什么，并能从一堆代码里指出"一坨代码"的坏味道在哪里

## Steps

1. [[learn/design-pattern/nodes/patterns-foundation/pattern-problem|设计模式解决什么问题]] — 认识设计模式是什么、解决哪一类反复出现的设计问题、从哪来，以及它作为沟通语言的作用
2. [[learn/design-pattern/nodes/patterns-foundation/code-smell|认识"一坨代码"的坏味道]] — 认出按 type 字段堆叠的 ifelse/switch 分发，说出它为什么每加一个需求就越来越难维护（after step 1）
3. [[learn/design-pattern/nodes/patterns-foundation/six-principles|六大原则各自管什么]] — 说出六大原则各自管什么，以及它们如何共同指向高内聚、低耦合、可扩展、可复用（after step 2）
4. [[learn/design-pattern/nodes/patterns-foundation/pattern-refactor-loop|怎么读懂一个模式章节]] — 用"场景模拟 → 一坨代码 → 模式重构 → 总结"的框架去读任何模式章节，并带取舍意识（after step 3）

## Lesson

设计模式不是一本要背的公式集。它们是一批有经验的程序员在同一个设计问题上反复撞上、又反复收敛出来的"套路"——从建筑学里 Christopher Alexander 的《建筑模式语言》一路传到软件界，由 GoF 在 1994 年系统整理成 22 个模式。学它们的价值不在于记住类图，而在于遇到类似问题（比如又要在 Controller 里加一个 type 分支）时，能一眼认出问题、知道该从哪个方向拆解。所有模式都在服务同一组底层追求：高内聚、低耦合、可扩展、可复用，而六大原则就是给这些追求把关的裁判。

这个节点用四步把这套思想立起来：先想清楚设计模式到底解决什么问题（pattern-problem）；再从真实的"一坨代码"里认出它们要拆的坏味道——按 type 字段堆叠的 ifelse/switch（code-smell）；然后认识所有拆解背后的裁判——六大原则各自管什么（six-principles）；最后拿到一个能套用到后面 21 个模式章节的统一读法（pattern-refactor-loop）。从此每读一个新模式，都是同一套流程的重复：先看场景，再看烂代码，再看模式重构，最后看总结里的取舍。
