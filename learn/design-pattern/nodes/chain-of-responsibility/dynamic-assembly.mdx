# 動態編排與邊界

## Learning goal

學會用 appendNext 動態組裝審批鏈，理解時間範圍如何決定鏈長度，並說出責任鏈的適用邊界與代價。

## Lesson

責任鏈最強大的地方在於**編排過程可以與節點實現分離**。通過鏈式調用一行代碼就能組裝出一條完整的審批鏈：new Level3AuthLink("1000013","王工").appendNext(new Level2AuthLink("1000012","張經理", beginDate, endDate).appendNext(new Level1AuthLink("1000011","段總", beginDate2, endDate2)))。編排代碼只在控制層出現一次，業務代碼不需要知道鏈的存在；節點順序可以隨時調整，交換 appendNext 的順序就行；可以動態增刪節點，加一個 Level0AuthLink 就多一級審批，刪掉就不審。

在實際業務中，責任鏈可以進一步配置化。鏈結構固定時用代碼寫死最簡單直接；鏈結構偶爾調整時用 XML 配置，改配置不用改代碼；鏈結構經常變化（如審批流引擎）時放到數據庫或配置中心，最靈活但複雜度最高。核心思路是把「鏈上有誰、順序如何」從代碼中抽離出來，讓業務人員改個配置就能調整審批流，不需要開發介入。

對比重構前後的收益：結構變得清晰乾淨，每個審批級別是獨立的類、職責單一；符合單一職責原則，每個類只管自己的審批邏輯；符合開閉原則，加新審批級別只需加新類、不改動已有代碼；外部調用方無感，控制層只需組裝鏈並調用 doAuth。但責任鏈不是萬能的。**不適合簡單條件判斷**——如果只是三選一，用 if-else 就夠了，責任鏈的價值在於「多個節點可能都要處理、處理順序可變、鏈可動態調整」的場景。**有性能開銷**——每個請求都要沿鏈傳遞，節點越多開銷越大，高併發場景下可能成為瓶頸。**調試複雜度增加**——請求在鏈上跳轉，出問題時不知道是哪個節點的責任，不像 if-else 一眼能看到完整的判斷邏輯。一句話總結：**if 適合判斷，不適合做系統流程設計**。
