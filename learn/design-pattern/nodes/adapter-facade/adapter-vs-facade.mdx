# 适配器还是外观：何时包接口、何时包子系统

## Learning goal

面对一段需要"包一层"的代码时，能判断该用适配器（统一接口）还是外观（简化子系统入口）。

## Lesson

面对一段需要"包一层"的代码时，核心判断标准只有两个维度：包的是什么，动机是什么。

**适配器翻译格式**——如果你在说"这个接口的参数/返回值和那个不一样"，用适配器。适配器包的是一个不兼容的接口，动机是翻译接口形态。典型场景：对接多个第三方支付接口，各家入参格式完全不同；从单节点 Redis 升级到集群 Redis，旧接口和新接口不兼容需要适配器翻译；Spring 的 `HandlerAdapter` 把不同类型的 Handler 统一成 DispatcherServlet 能调用的格式。框架识别信号：看到 `*Adapter` 后缀的类名。

**外观简化路径**——如果你在说"背后太复杂了，调用方不该知道这些细节"，用外观。外观包的是一整个子系统（多个类/服务），动机是简化调用路径。典型场景：一个 Controller 要查用户信息、订单列表、积分余额，背后分别是三个微服务；白名单、限流、日志包装成一个 Starter 注解。框架识别信号：看到 Starter + AOP + 自定义注解。

两者的共同点是不修改原始代码，都属于结构型模式。完整对比：解决的问题（接口不兼容 vs 调用方太复杂）、包的是什么（一个接口 vs 一整个子系统）、动机（翻译格式 vs 简化路径）、新增来源时的做法（加映射配置 vs 加注解）、框架识别信号（`*Adapter` vs `*Starter`）。一句话记住：适配器翻译格式，外观简化路径。
