# 外观模式：用一层门面降低调用方复杂度

## Learning goal

能用外观模式把跨切面关注点（白名单、切量、灰度）包装成可复用的中间件，并识别出 SpringBoot starter 中的外观结构。

## Lesson

外观模式解决的核心问题是**调用方太复杂**——背后有五六个子系统，调用方不该知道这些细节。解法是加一层门面，把跨切面的逻辑包装成一个统一入口。

真实场景：SpringBoot 应用里每个 API 接口都要做白名单切量检查。最直觉的做法是在每个 Controller 方法开头复制粘贴白名单逻辑，但白名单代码散落在每个接口里，改一次要改 N 个地方，更别说以后还要加限流、日志、灰度。外观的解法是把白名单检查包装成一个自定义 SpringBoot Starter：自定义注解 `@DoDoor(key, returnJson)` 标记哪些接口需要检查，AOP 切面 `DoJoinPoint` 拦截所有带注解的方法提取参数比对白名单，`StarterServiceProperties` 读取 yml 里的白名单配置，`StarterAutoConfigure` 条件注册 Bean 启动时自动生效。业务代码只需要加一个注解，白名单逻辑只写一次。

中间件的本质就是外观——白名单、切量、灰度、限流、日志都是跨切面的关注点，业务代码不该知道它们的存在。外观把这些逻辑包装成统一入口（注解/AOP/starter），让业务代码保持干净。判断是否该用外观：调用方省掉的代码量是否值得多加一层。如果外观只是简单转发没有真正简化复杂度，就没必要加。

外观与适配器的区别：外观包的是一整个子系统（多个类/服务），适配器包的是一个不兼容的接口；外观简化的是调用路径，适配器翻译的是接口形态。
