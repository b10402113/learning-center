# 适配器模式：让不兼容的接口变得统一

## Learning goal

能用适配器把多个不兼容的第三方接口统一成调用方想要的形态，并识别出框架源码中的适配器结构。

## Lesson

适配器模式解决的核心问题是**接口不兼容**——拿到的接口格式不对，需要一个翻译层把不兼容的接口变成调用方期望的统一形态。

真实场景：营销/返利系统要消费多种 MQ 消息——京东 MQ 字段叫 `uid`/`couponId`，淘宝叫 `userId`/`discountId`，拼多多叫 `memberNo`/`skuId`。最直觉的做法是为每种 MQ 写一个 Consumer 类手写字段映射，但每来一个新来源就得多建一个类，代码膨胀很快。适配器的解法是把字段映射关系从代码里抽出来变成可配置的：定义一个统一消息体 `RebateInfo`（目标接口），用一个 `MQAdapter.filter()` 方法（适配器）通过配置 `Map<String,String>` + 反射设值，一行代码把任意 MQ JSON 适配成 `RebateInfo`。新增来源只需加一组映射配置，不用新建类。

四个角色：目标接口（`RebateInfo`，调用方期望的统一形态）、适配者（各 MQ 的原始 JSON，已有的不兼容接口）、适配器（`MQAdapter`，翻译层）、客户端（业务 Service，只和 `RebateInfo` 打交道）。同一个系统里"是否首单"的判断也需要适配——内部订单服务查数据库、外部 POP 接口直接返回 boolean，用 `OrderAdapterService` 接口统一后业务方不关心背后是哪个实现。

Spring 框架里大量使用适配器（`UserCredentialsDataSourceAdapter`、`HandlerAdapter`、`JpaDialectAdapter`），看到 `*Adapter` 后缀的类名大概率就是在做接口翻译。优点是不修改原始代码、符合开闭原则、新增来源只需加配置；代价是增加了一个中间层、配置驱动的反射有轻微性能开销。
