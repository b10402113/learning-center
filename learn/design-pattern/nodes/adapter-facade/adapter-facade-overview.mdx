# 接口不兼容的两种解法：适配器与外观

## Learning goal

识别"接口不兼容"和"调用方太复杂"这两种常见的结构问题，并能说出适配器和外观分别解决哪一种。

## Lesson

开发中一个高频出现的结构问题是：拿到的接口和自己想要的对不上。适配器和外观都是"包一层"的解法，但动机完全不同。

**接口不兼容**是最常见的一类——你的 Service 要对接优惠券接口（`sendCoupon`）、实物商品接口（`deliverGoods`）、爱奇艺兑换卡接口（`grantToken`），三个接口入参不同、返回值不同、错误处理方式也不同。每来一个新产品就得多写一堆 if-else。这类问题的解法是**适配器模式**：加一个翻译层，把不兼容的接口变成调用方想要的统一形态。日常类比：万能充电器把不同插头转成 USB，出国转换插头把不同电压标准统一。Spring 源码里到处是 `*Adapter` 类，说明这个模式在框架层面非常常见。

**调用方太复杂**是另一类——背后有白名单检查、权限校验、限流降级、日志记录等五六个子系统，但调用方不该知道这些细节。这类问题的解法是**外观模式**：加一层门面，把跨切面的逻辑包装成一个统一入口，业务代码一行都不用改。日常类比：酒店前台一个电话搞定所有事，导演让演员不用管灯光/摄影/收音。你写过的自定义 SpringBoot Starter 做白名单/切量/灰度，本质就是外观。

两者的共同点是**不修改原始代码**，都属于结构型模式。核心区别：适配器翻译的是*接口形态*（A 的输出变成 B 能吃的格式），外观简化的是*调用路径*（背后十个子系统，调用方只看到一个入口）。掌握这两个模式之后，面对第三方集成和中间件开发，能快速判断该包接口还是包子系统。
