# 秒殺場景痛點：固定信息為什麼每次都在重建？

## Learning goal

識別秒殺活動查詢中「固定信息」與「變化信息」的分界，理解每次全量查詢帶來的冗餘浪費。

## Lesson

你在電商平台做後端，公司上線了一個圖書秒殺活動——「圖書嗨樂：圖書優惠券分享激勵分享活動第二期」。一開始日均十幾單，系統跑得很順。但隨著活動推廣，每個時段的秒殺量衝破十萬。每次用戶打開秒殺頁面，後端都要查詢一次活動信息：

```java
public Activity queryActivityInfo(Long id) {
    Activity activity = new Activity();
    activity.setId(10001L);
    activity.setName("圖書嗨樂");
    activity.setDesc("圖書優惠券分享激勵分享活動第二期");
    activity.setStartTime("2024-06-01");
    activity.setStopTime("2024-06-30");
    activity.setStock(new Stock(1000, 1));
    return activity;
}
```

活動的名稱、描述、起止時間，從上線到結束一個字都沒變過。變化的只有庫存數字。然而每次查詢，都在重新創建這些一模一樣的對象。

把活動數據拆開看，很自然地分成兩類：

| 分類 | 字段 | 特徵 |
| --- | --- | --- |
| **固定信息**（內部狀態） | 活動名稱、描述、起止時間 | 活動期間不變，所有用戶看到的都一樣 |
| **變化信息**（外部狀態） | 庫存（已售數量） | 隨交易實時變化，每個時刻不同 |

十萬次重複構建完全相同的數據——這就是冗餘。十萬次查詢如果每次都從數據庫或遠端接口取全量數據，等於十萬次相同的 SQL 或 RPC 調用。享元模式（Flyweight Pattern）的核心切入點就是：**把不變的抽出來共享，把會變的分離出去單獨獲取**。這不是通用緩存的問題，而是從設計層面把「共享對象」和「外部狀態」的職責分清楚，用一個專門的工廠來管理共享。
