# 享元模式的適用邊界與局限

## Learning goal

能說出享元模式的優點（減接口調用、減內存佔用）、通用手法（Map + id 存取）與缺點（內部/外部狀態難區分時工廠易混亂），以及與原型模式的共通思想。

## Lesson

享元模式的設計重點是享元工廠。它在以下場景下特別有用：服務端減少接口調用（秒殺場景中活動信息固定不變，用享元工廠緩存後，十萬次查詢只需要一次真正的數據庫/接口調用）；客戶端減少內存佔用（遊戲地圖上的樹木、花草模型共用一份，幾千個實例只需要一個對象的內存）；減少 ifelse 判斷（用 Map + 固定 id 存取對象，替代一長串的 switch/if 判斷不同 id 對應不同行為）。一句話總結：**在有大量重複對象可復用的場景下，享元模式通過共享降低成本**。

享元模式的核心手法其實非常簡單：**用一個 Map 結構，以固定 id 為 key，存放和獲取對象**。這種手法不只在享元模式中出現——工廠模式、適配器模式、組合模式中也可以用 Map 結構存放服務供外部獲取，減少 ifelse 判斷。關鍵是「用固定 id 存取」這個思想，它是一種通用的設計技巧。

享元模式最大的風險是：**複雜業務中不容易區分內部和外部狀態**。在秒殺場景中，內部狀態（活動名稱、時間）和外部狀態（庫存）的邊界很清晰。但在更複雜的場景中呢？一個用戶的行為日誌，哪些是固定的、哪些是變化的？一個商品的 SKU 信息，價格算內部狀態還是外部狀態？如果拆分不好，享元工廠會變得非常混亂——Map 裡的對象忽共享忽不共享，外部狀態到處傳，最後比原來的一坨代碼更難維護。**享元模式的前提是「內部狀態和外部狀態能被清晰地拆分出來」。如果拆不清楚，寧可不用。**

享元模式和原型模式（Prototype Pattern）都屬於結構型模式，都指向一個共同的設計目標：**減少重複構建的成本**。原型模式是「複製一份再改」，享元模式是「不變的直接共享」。兩者解決的問題不同，但背後的思想相通：能不新建就不新建，能複用就複用。什麼時候不該用享元：狀態難拆分時、對象數量不多時（共享收益微乎其微反而增加複雜度）、內部狀態也在變化時（共享失去意義還需要處理緩存失效）。
