# 中介者模式的意圖與 ORM 場景定位

## Learning goal

<能說出中介者模式「集中協調、解耦網狀依賴」的意圖，並用 ORM / 中台場景解釋它解決什麼問題。>

## Lesson

機場塔台（Air Traffic Controller）是一個經典的中介者。飛機 A 要降落、飛機 B 要起飛、飛機 C 在滑行——如果三架飛機自己互相喊話協調，場面會很混亂。塔台作為中介者，所有飛機只跟塔台通信，塔台統一協調誰先降落、誰等待、誰滑行。每架飛機不需要知道其他飛機的存在，只需要聽塔台的指令。

工程世界也一樣。當多個模塊之間的調用關係變成**網狀**（A 調 B、B 調 C、C 又調 A），每個人都要依賴其他人的接口——改一個就要改一圈。這時候就需要一個「塔台」。

中介者模式的定義：**用一個中介者對象封裝一系列對象交互，使各對象不需要顯式相互引用，從而耦合鬆散且可獨立改變它們之間的交互。** 白話翻譯：把「誰跟誰打招呼」這件事收進一個中間人，所有人只跟中間人說話。沒有中介者時，N 個對象的交互是 N² 量級的依賴；有了中介者，變成 N 量級——改 B 的接口只有中介者要改，A、C、D 都不用動。

這個模式在後端開發中隨處可見。ORM 中間件（Mybatis、Hibernate）封裝連接、SQL 解析、結果映射，業務方只寫 SQL 和 POJO。公司中台把 N 種獎品服務的接口統一收到一個獎品中心，對外只暴露一個通用接口。API 網關把所有微服務的路由、鑑權、限流收進網關，客戶端只跟網關通信。消息中間件（Kafka、RabbitMQ）讓生產者和消費者不直接對話，通過 Broker 中轉。

本節用「模仿 Mybatis 手寫 ORM 框架」來體現中介者模式。思路很直接：先看清一把梭 JDBC 的痛點（上一課），再用中介者包裝——把連接、驅動、SQL 執行、結果映射收進 SqlSession / Factory / Builder / Configuration 四層組件，外部只按「statement + 參數」調用。對照工程 `itstack-demo-design-16-01`（一把梭 JDBC 直連）vs `itstack-demo-design-16-02`（手寫 ORM 中介者）。

模型結構預覽：中介者的整體分工分三大塊——查詢側（`SqlSession` 接口定義 `selectOne` / `selectList`，`DefaultSqlSession` 實現具體的 JDBC 調用和結果映射）、工廠側（`SqlSessionFactory` 接口定義 `openSession()`，`DefaultSqlSessionFactory` 持有 Configuration 並創建 Session）、装配側（`SqlSessionFactoryBuilder` 是啟動入口——解析 XML 配置、建立連接、構建 Configuration）。下一課逐個拆解這些組件。
