# 驗證中介者架構的收益與設計原則

## Learning goal

<能用測試結果證明中介者屏蔽了 JDBC 複雜度，並說出它滿足的三個設計原則（單一職責、開閉、迪米特）。>

## Lesson

用兩條測試驗證手寫 ORM 真的能跑。selectOne 測試：業務方只傳一個 statement 字符串和一個 ID，框架內部自動完成解析 XML → 準備 SQL → 執行查詢 → 反射映射成 `User` 對象。selectList 測試：帶參數的集合查詢也跑通了，說明 `#{id}` 占位符替換、參數綁定、結果集遍歷全部正常。跟用 Mybatis 的體驗完全一致。

對比一把梭的收益：業務代碼從四步 JDBC 全寫變成一行 selectOne/selectList；連接管理從自己寫 Class.forName + getConnection 變成 Builder 啟動時處理、業務方無感；SQL 定義從硬編碼在 Java 裡變成 XML 配置文件、改 SQL 不改 Java；結果映射從 while(resultSet.next()) 手動取值變成反射自動映射成 POJO；擴展性從改一個查詢動整個類變成加一個 XML + POJO 就行。

從設計原則看，它滿足三個。**單一職責原則（SRP）**：每個組件只做一件事——SqlSession 只管查詢、Factory 只管開 Session、Builder 只管啟動構建、Configuration 只管存配置，改 XML 解析只動 Builder，改結果映射只動 DefaultSqlSession，互不干擾。**開閉原則（OCP）**：新增一種查詢（如 School）不需要改任何中介者組件的 Java 代碼，只加 POJO + XML + 配置引用，對擴展開放、對修改封閉。**迪米特原則（LoD）**：業務方只需要知道 SqlSession 的 selectOne / selectList，不需要知道連接怎麼建立、SQL 占位符怎麼替換、ResultSet 怎麼映射，這些細節全部由中介者組件處理。

中介者不只用在 ORM。公司裡的「獎品中心中台」就是典型：10 種獎品服務如果每個業務方都直接對接，依賴就是 10×N 的網狀；把 10 個服務統一收進獎品中心，業務方只跟獎品中心通信，獎品中心就是中介者。判斷標準：**對象交互複雜、重複調用多、需要統一入口**——就該考慮中介者。面試遇到「中介者模式」，你現在能講出意圖（集中協調）、場景（ORM / 中台）、結構（五個組件）和原則（SRP + OCP + LoD）了。
