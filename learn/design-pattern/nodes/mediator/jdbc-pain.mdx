# 一把梭 JDBC 直連的痛點

## Learning goal

<能說出直接 JDBC 操作的四步流程及其在業務擴展時的具體痛點，並判斷何時需要引入中介者。>

## Lesson

假設你有一個簡單需求：從 MySQL 查出使用者列表並打印。最直覺的寫法就是寫一個 `JDBCUtil` 類，main 方法裡直接走完 JDBC 四步——載入驅動、取得連接、建立 Statement 並查詢、遍歷結果。

`Class.forName("com.mysql.jdbc.Driver")` 載入驅動，`DriverManager.getConnection(URL, USER, PASSWORD)` 拿到連接，`createStatement` + `executeQuery` 執行 SQL，最後 `while(resultSet.next())` 逐行取值打印。跑起來沒問題，輸出三條使用者記錄。

這段代碼「能跑」，但問題藏在它**把所有東西都暴露給業務方**。驅動類名硬編碼（換 Oracle 要改業務代碼）、連接字串和帳號密碼散落在業務類裡（不同環境要硬切配置）、SQL 字符串直接寫死在 Java 裡（改查詢就要改業務類）、`ResultSet` 逐行手動取值（每個查詢都要寫一遍 while loop）。一句話：**業務代碼跟 JDBC 細節強耦合**。

更深一層的問題是**無法複用**。假設公司有三種獎品服務（金幣、優惠券、實物），每種都要查資料庫。如果每個服務都自己寫 JDBC 四步，你會得到三份幾乎一樣的驅動/連接代碼、三份不同的 SQL 但結果處理邏輯完全重複、連接池管理分散在各處沒法統一控管。這就是「一把梭」的代價：重複、分散、難改。

要消除這些痛點，就需要一層「中介者」把 JDBC 細節封裝起來，讓業務方只關心「查什麼、用什麼參數」。下一課看看中介者模式怎麼把這些細節收進一個統一的包裝層。
