# JDK 三接口骨架：Iterator、Iterable、Collection

## Learning goal

理解自定義迭代器參照的 JDK 三接口骨架（Iterator、Iterable、Collection）各自職責，以及它們之間的繼承關係。

## Lesson

在 JDK 的 `java.util` 裡，迭代器的實現被拆成三個接口，各司其職：

| 接口 | 職責 | 核心方法 |
| --- | --- | --- |
| `Iterator<E>` | 定義遍歷行為——「怎麼一個一個取出來」 | `hasNext()`、`next()`、`remove()` |
| `Iterable<E>` | 聲明「我是可遍歷的」——提供獲取迭代器的入口 | `iterator()` |
| `Collection<E>` | 定義集合操作——增刪查改 + 遍歷 | `add()`、`remove()`、`iterator()`… |

三者之間的繼承關係是 `Collection<E> extends Iterable<E>`，而 `Iterable` 提供 `iterator()` 方法，`Iterator` 定義 `hasNext()` 和 `next()`。關鍵設計：`Collection` 繼承了 `Iterable`，所以任何 Collection 的子類（List、Set）都可以直接用增強 for 循環，因為它們天生就是「可遍歷的」。

**Iterator——遍歷的執行者。** `Iterator<E>` 是最底層的接口，只做一件事：逐個取出元素。三個方法的分工很清晰：`hasNext()` 在取之前先問「還有嗎」，避免 `NoSuchElementException`；`next()` 取出下一個元素，內部指針往前移一步；`remove()` 刪除剛才 `next()` 返回的那個元素——這是增強 for 做不到的。Iterator 是單向的、一次性的——從頭走到尾，走完就結束了，不能回頭。如果你想再遍歷一次，就得重新調用 `iterator()` 拿一個新的。

**Iterable——可遍歷的標記。** `Iterable<E>` 只有一個方法：`iterator()` 返回一個迭代器。它的作用是聲明：「我這個類是可以被遍歷的」。為什麼要單獨拎出這個接口？因為它讓遍歷能力和集合能力解耦了——一個類可以是 Iterable（可遍歷）但不是 Collection（不提供 add/remove）。比如文件系統的目錄結構：它是可遍歷的，但它不是一個「集合」。

**Collection——集合的全能管家。** `Collection<E>` 是最上層的集合接口，繼承了 `Iterable`，提供完整的增刪查改操作。你常用的 `ArrayList`、`HashSet` 都實現了這個接口。

**為什麼要拆成三個接口？** 答案是職責分離。如果只有一個接口，所有類都必須實現所有方法；拆開後，可遍歷的不一定是集合，集合不一定是可變的。更重要的是因為 Iterator 是獨立接口，同一個數據結構可以提供多種遍歷方式——正序、反序、深度優先、寬度優先——調用方只需要換一個 Iterator 就行。

當你要給自己的數據結構（比如組織架構樹）實現迭代器時，參照 JDK 的方式：定義自己的 `Iterator<E>` 實現 `hasNext()` 和 `next()`；定義自己的 `Iterable<E>` 提供 `iterator()` 方法；定義自己的 `Collection<E, L>`（兩個泛型：元素類型和鏈路類型）繼承 `Iterable`，加上增刪操作；在具體的數據結構類裡實現 `Collection`，把遍歷邏輯寫在匿名內部類或單獨類裡。三接口的骨架和 JDK 完全一致，這樣以後看 JDK 源碼時可以對照學習。
