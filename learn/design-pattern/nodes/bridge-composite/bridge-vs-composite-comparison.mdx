# 桥接还是组合：拆双维度还是建树

## Learning goal

对比桥接与组合的适用边界，判断什么时候拆双维度、什么时候建树，并辨析与适配器/策略的区别。

## Lesson

桥接和组合都是结构型模式，都用组合替代继承来降低复杂度，但拆解的结构形态完全不同。判断该用哪个，关键看 ifelse 嵌套的结构：两个维度是否独立，还是条件本身形成层级。

**桥接 vs 组合的决策流程：** 看到嵌套 ifelse 不可维护，先问两个维度是否独立。如果两个维度交叉形成矩阵（A × B），用桥接拆掉笛卡尔积。如果条件本身形成层级结构（if-else 树），用组合建递归树。关键判断：维度 A 的变化是否影响维度 B 的逻辑——如果互不影响，它们是独立的，适合桥接；如果一个维度是另一个的子条件，它们有层级关系，适合组合。

**桥接 vs 适配器 vs 策略的辨析：** 桥接拆开两个独立维度（M+N 个类替代 M×N 个分支），适配器翻译一个不兼容的接口（让 A 的输出变成 B 能吃的格式），策略替换同一行为的多种算法（ifelse 分发算法变成 Context 持有策略）。三个模式都用组合，但意图完全不同：桥接是设计阶段的维度拆分，适配器是对接已有接口时的翻译，策略是算法可替换时的分发。

**组合 vs 责任链 vs 策略的辨析：** 组合是树形递归（根→子节点→孙节点，结果汇总），责任链是链式传递（A→B→C，谁处理谁返回），策略是 Context 持有单个策略直接调用。组合适合层级决策（决策引擎、文件系统），责任链适合顺序处理（审批流、过滤器链），策略适合算法替换（定价、折扣计算）。

## Lesson body 2

真实场景判断练习：消息推送系统对接三个渠道（短信/邮件/App）× 三种类型（营销/通知/验证码）→ 渠道和类型是独立维度，交叉形成矩阵 → 桥接。电商促销规则按用户等级→商品品类→订单金额多级判断，条件形成 if-else 树 → 组合。对接三个第三方支付 API，入参格式不同 → 接口不兼容 → 适配器。优惠券按券类型用不同算法计算折后价 → 同类算法替换 → 策略。

识别信号总结：看到 channelType × modeType 这种双维度嵌套就想到桥接，看到条件判断形成 if-else 树就想到组合，看到格式不对要翻译就想到适配器，看到 ifelse 分发算法就想到策略。四个模式都满足开闭原则——新增维度值、新增过滤条件、新增第三方、新增算法，都不需要改已有代码。但它们的结构代价不同：桥接增加 M+N 个类，组合增加树节点类，适配器增加包装器类，策略增加策略实现类。选择时要权衡 ROI——场景复杂度是否值得这些额外的类。
