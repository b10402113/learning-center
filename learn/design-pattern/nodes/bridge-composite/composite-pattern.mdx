# 组合模式：用递归树结构替代深层 ifelse 嵌套

## Learning goal

用营销优惠券决策树场景，把嵌套 ifelse 重构为叶子/组合节点统一接口的树结构，理解递归遍历机制。

## Lesson

营销优惠券决策引擎要按多级条件过滤用户：先看性别，再看年龄，再看消费金额，最终决定发哪种券。每加一级过滤，ifelse 就多嵌一层。5 级条件就是 5 层嵌套，改一个条件要在整棵树里找对应的分支。这些条件判断的逻辑是相似的——都是"检查某个属性，通过则继续，不通过则拒绝"。真正不同的是：检查什么属性、用什么阈值。

坏代码的做法是一个 `EngineController`，用多层 ifelse 硬编码每条过滤路径。条件越多，嵌套越深，维护越难。而且这些路径之间有大量重复逻辑。

组合模式的重构分三步。第一步，定义统一接口 `LogicFilter`，包含 `filter(Object)` 和 `getKey()` 方法。第二步，实现叶子节点——`UserAgeFilter`、`UserGenderFilter`、`UserConsumeFilter`，每个只负责一个条件的判断。第三步，实现组合节点——`EngineBase` 遍历树节点（`TreeNode`/`TreeNodeLink`），递归调用子节点的 `filter` 方法，根据结果决定下一步。

调用方组装一棵过滤树，引擎从根节点开始递归遍历：叶子节点执行具体过滤逻辑，组合节点遍历子节点并汇总结果。新增一个过滤条件，只需要写一个新的叶子节点类，注册到树里——不需要改已有代码，满足开闭原则。树结构可以从硬编码提升到数据库/配置化，运营人员可以在界面上拖拽组装过滤规则，不需要改代码重新部署。

## Lesson body 2

组合模式有两个经典实现方式：透明方式和安全方式。透明方式让叶子和组合实现完全相同的接口——客户端不区分"这是一个单独的过滤器"还是"这是一个过滤器树"，调用方式完全一样。安全方式让叶子和组合有不同的接口——编译器可以在编译期防止叶子节点调用不该有的方法（如 `add` 子节点）。选择取决于叶子和组合的行为差异大小：行为一致用透明方式（客户端简单），行为差异大用安全方式（类型安全）。

组合模式的识别信号：条件判断形成 if-else 树，每级过滤嵌套越来越深。日常中文件系统（文件和文件夹都实现 FileSystem 接口）、UI 组件树（Button 和 Panel 都实现 Component 接口）、公司组织架构（员工和部门都实现 Entity 接口）都是组合的应用。组合与责任链的区别在于结构：责任链是链式传递（A→B→C），组合是树形递归（根→子节点→孙节点）。组合与策略的区别在于意图：策略替换的是同一行为的不同算法，组合组织的是同一接口的层级结构。
