# 裝飾器的概念與四角色結構

## Learning goal

<能說出裝飾器「不改原類、逐層包裹疊加功能」的意圖，並用四角色模型描述其結構。>

## Lesson

你可能寫過這行程式碼：

```java
BufferedReader br = new BufferedReader(new FileReader("data.txt"));
```

內層的 `FileReader` 負責讀檔，外層的 `BufferedReader` 在上面加了一層「緩衝」。如果再包一層 `InputStreamReader`，就多了一層「字元編碼轉換」。每一層都**沒有改動裡面那層的原始碼**，只是在外面包了一層新功能。這就是裝飾器模式（Decorator Pattern）的直覺模型。

**裝飾器模式**的核心意圖：在不改變原有類的前提下，動態地給對象新增功能。把它翻譯成日常經驗：冬天穿棉褲、雨天穿雨衣——你的身體（原類）從來沒被改過，但穿上不同的衣服（裝飾器）就能應對不同場景。穿脫自如，不需要「把身體改造成防水型」或「開一個雨天專用的身體子類」。

### 為什麼不用繼承

要新增功能，Java 裡最直覺的做法是**繼承**——寫一個子類、覆寫方法、把新邏輯塞進去。但以下場景下繼承會出問題：一個功能要加 5 種不同校驗時，要開 5 個子類，子類爆炸帶來維護噩夢；校驗要「有時要、有時不要」時，繼承結構寫死，無法運行時增減；功能要「隨意排列組合」時，Java 不支持多重繼承，結構會變得複雜。

**AOP（面向切面編程）**可以做到「不改原類、動態增強」，但引入了切面表達式、代理機制、依賴 Spring 容器等額外複雜度。裝飾器用純 Java 物件組合就能實現，不需要框架介入。三者的差異可以用一張表對照：是否改原類（三者都不改）、新增方式（繼承靠子類覆寫、裝飾器靠物件包裹、AOP 靠切面注入）、運行時增減（繼承不行、裝飾器可以、AOP 可以）、是否需要框架（繼承和裝飾器不需要、AOP 需要）、組合靈活度（繼承低、裝飾器高、AOP 中等）。

### 四角色模型

裝飾器模式有四個標準角色，記住這張表，後面的 SSO 場景會逐一套上：**抽象构件（Component）** 定義統一接口，所有角色都實現它，SSO 場景中對應 `HandlerInterceptor`（Spring 攔截器接口）；**具體构件（ConcreteComponent）** 實現抽象接口、提供基礎功能，對應 `SsoInterceptor`（SSO 登入校驗）；**裝飾角色（Decorator）** 是抽象類，繼承接口 + 持有被裝飾對象的引用，對應 `SsoDecorator`；**具體裝飾角色（ConcreteDecorator）** 實現具體的擴展功能，對應 `LoginSsoDecorator`（方法級訪問校驗）。

關鍵句：**裝飾器 = 繼承接口 + 持有原對象引用 + 在自己的方法裡先執行原對象邏輯、再疊加新邏輯。** 具體裝飾類的 `preHandle` 裡有一行核心——`super.preHandle(request, response, handler)`。這行就是「先執行被裝飾對象的原有校驗」，然後再執行自己的擴展邏輯。這是裝飾器疊加職責的模板。

### 判別特徵

以後看到一段程式碼，如果同時符合以下三個特徵，基本可以判定是裝飾器：（1）**多層包裹**——物件建構時像俄羅斯套娃，一層套一層；（2）**同一接口**——每一層都實現同一個接口（或繼承同一個抽象類）；（3）**逐層疊加**——每一層在執行自己邏輯的同時，會轉調裡面那層的邏輯。
