# 繼承方式擴展 SSO 的子類膨脹困境

## Learning goal

<能說出 SSO 校驗場景中「用繼承重寫擴展功能」的壞味道：子類膨脹、功能耦合、靈活度低。>

## Lesson

一個 ERP 系統的早期版本只需要做一件事：用戶帶上 SSO 票據（ticket）就能訪問全部資源。所有接口的校驗邏輯就一句——從 request 裡取 ticket，比對成功就放行。業務發展後，出現了運營、營銷、數據等不同角色，各角色對 ERP 的訪問需求不同——有些角色只能查不能改，有些角色只能看自己的數據。又要保證數據安全，不能把最高權限給所有人。

大多數人在這個場景下的第一反應是：**繼承 SSO 攔截器，重寫校驗方法，把自己額外的邏輯塞進去**。一個子類、一個覆寫，看上去挺乾淨。但問題出現在需求增長之後。

### 痛點一：子類膨脹

運營角色要「方法級校驗」，數據角色要「接口級限流」，營銷角色要「資料夾級數據隔離」，審計角色要「操作日誌記錄」。每加一種校驗需求就多一個子類。四種需求四個子類，八種需求八個。子類數量隨需求線性增長，維護成本呈超線性增長。

### 痛點二：功能耦合

如果某個角色既要「方法級校驗」又要「操作日誌」怎麼辦？Java 不支持多重繼承。你要麼寫一個「既校驗又記日誌」的新子類（職責混合），要麼讓一個子類繼承另一個子類（繼承鏈過長）。無論哪種，代碼都會變得混亂。

### 痛點三：無法運行時增減

繼承的結構在編譯時就寫死了。如果某個版本不需要方法級校驗了，你得改程式碼、重新編譯、重新部署。裝飾器可以在程式運行時隨意包裹或拆卸。

這些痛點的根源是同一件事：**用「類的繼承」去解決「功能的組合」**。繼承是「is-a」關係——子類是父類的一種。但「帶日誌的 SSO」不是 SSO 的一種，而是「SSO + 日誌」的功能組合。把 is-a 用在 has-a 的場景上，代價就是上面的三個痛點。

回到那段繼承寫法的 `LoginSsoDecorator`。它思路上沒錯——先調 `super.preHandle()` 執行原始校驗，再加自己的邏輯，這其實已經是裝飾器的雛形了。但形式上走錯了路：用繼承而非組合。如果把 `extends SsoInterceptor` 改成「實現接口 + 持有 SsoInterceptor 實例」，就從繼承走到了裝飾器。下一個步驟會完成這個重構。
