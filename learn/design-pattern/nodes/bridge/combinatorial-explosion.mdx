# 笛卡爾積膨脹：ifelse 的壞味道

<LearningGoal>
理解「多支付渠道 × 多支付模式」的笛卡爾積膨脹問題，體會 ifelse 雙層嵌套的壞味道，並能說出這種結構為什麼不可維護。
</LearningGoal>

## Lesson

想像你是一家第三方聚合支付平台的後端工程師。商家不想讓用戶改變支付習慣，所以平台需要同時支援微信支付、支付寶等多個支付渠道。同時，每個渠道又要支援刷臉、指紋、密碼等多種支付方式。

業務需求很直觀：用戶選一個支付渠道，再選一種支付方式，系統完成支付。

最直覺的寫法是把所有組合堆在一個方法裡：外層判斷渠道（微信 or 支付寶），內層判斷模式（密碼、刷臉、指紋），用兩層 ifelse 把 2 × 3 = 6 種組合全部列出來。

```
doPay(uId, tradeId, amount, channelType, modeType)
  if channelType == 微信:
    if modeType == 密碼 → 微信+密碼
    if modeType == 刷臉 → 微信+刷臉
    if modeType == 指紋 → 微信+指紋
  if channelType == 支付寶:
    if modeType == 密碼 → 支付寶+密碼
    if modeType == 刷臉 → 支付寶+刷臉
    if modeType == 指紋 → 支付寶+指紋
```

6 個分支還勉強能維護。但算一筆帳：如果新增京東支付、雲閃付兩個渠道（渠道從 2 變 4），再新增指紋 2.0、聲紋兩種模式（模式從 3 變 5），分支數就從 6 飆到 4 × 5 = 20。每增加一個渠道，所有模式都要再寫一遍；每增加一種模式，所有渠道也要再寫一遍。分支數是兩個維度的乘積——這就是「笛卡爾積膨脹」。

ifelse 膨脹不只是代碼量的問題。它帶來三個更深的麻煩：

第一，違反單一職責。一個方法同時承擔「判斷渠道」和「判斷模式」兩件事，任何一邊的變更都要動這個方法。

第二，違反開閉原則。新增一種支付模式（比如聲紋），你需要修改所有渠道的 ifelse 分支——這是對已有代碼的修改，不是擴展。

第三，測試組合爆炸。2 × 3 = 6 組測試用例，變成 4 × 5 = 20，測試成本直線上升，而且每組之間高度重複。

核心洞察：當你發現代碼裡出現「if A then if B」的雙層嵌套，而且 A 和 B 是兩個獨立維度——這就是在警告你：這兩個維度不該攪在一起。

問題的根源是：渠道和模式是兩個獨立變化的維度，但它被塞進了同一個方法。解決思路是把它們「拆開」——讓渠道歸渠道、模式歸模式，需要組合的時候再「接」起來。這正是橋接模式（Bridge Pattern）的核心思路：把「抽象部分」和「實現部分」分離，讓它們各自獨立變化。
