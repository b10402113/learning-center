# 發獎場景的 ifelse 壞味道

<LearningGoal>
能從三種異構商品接口（優惠券/實物/兌換卡）的 ifelse 一把梭中，說出為什麼需要工廠方法模式來統一創建入口、屏蔽實現。
</LearningGoal>

## Lesson

營銷場景搞了個積分兌換活動，用戶可以換三種商品：優惠券、實物商品、第三方兌換卡。三種商品的接口完全不一樣——優惠券返回 `CouponResult` 對象、實物商品返回 `Boolean`、兌換卡返回 `void`；入參也不統一，優惠券要防重的 uuid，實物商品要收貨地址，兌換卡要手機號和卡 ID。營銷場景的特點是「多變、臨時」，今天加個視頻會員，明天加個實物周邊，產品經理隨時會跑過來說「再加一種」。

最直覺的做法是搞一個 `PrizeController`，裡面按 `awardType` 做 ifelse 分支：type 等於 1 就 new 優惠券的 Service，等於 2 就拼裝 `DeliverReq` 調實物發放，等於 3 就查手機號再調兌換卡。代碼寫得快，三種情況都能跑通——但壞味道馬上浮現。**修改成本高**：加一種新商品就要在這個方法裡加 else if 分支，動到已有邏輯，每次修改都要回歸所有分支。**參數污染**：實物商品需要收貨地址，req 裡塞了 extMap，但優惠券和兌換卡根本用不到。**難以測試**：三種業務邏輯耦合在一個方法裡，無法獨立單測。**接手痛苦**：新同事要把所有 if 全讀一遍才知道「實物商品怎麼發放」。

問題的根源是把「根據類型選擇哪個服務」和「執行服務」這兩件事混在一起了。三個服務的接口完全不一樣，每個分支的代碼結構都不一樣，沒法抽成統一調用。工廠方法模式（Factory Method Pattern）要解決的核心問題就是：<strong>把「根據類型決定實例化哪個類」的邏輯從調用方抽離出來，統一到一個地方</strong>。它是 GoF 23 種模式中的創建型模式（Creational Pattern），意圖是定義一個創建對象的接口，讓子類決定實例化哪一個工廠類。翻譯成白話：你給我一個「要什麼」，我幫你「造出來」，具體怎麼造調用方不需要知道。回到發獎場景，調用方只說「我要發一種商品」，工廠幫你判斷是哪種，返回對應的發放服務——就像餐廳前台，你說「水煮魚」，前台幫你分配到川菜廚房。
