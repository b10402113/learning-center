# ifelse 實現的維護災難

<LearningGoal>
識別 ifelse 實現套餐選擇的代碼壞味道，理解「一個類幾千行」的維護代價。
</LearningGoal>

## Lesson

回到裝修套餐場景。四種物料、三種套餐，最直覺的寫法是什麼？一個方法，裡面用 if 判斷等級，然後 new 出對應的物料組合。每個 if 分支做三件事：new 物料、加入清單、按面積乘以係數算價格——吊頂 ×0.2、塗料 ×1.4、地板和地磚 ×面積。這段價格計算邏輯在三個分支裡完全重複。改一個計算係數？三個分支都要改。漏改一個？三種套餐的價格就不一致了。

除了選料和算價格，這個方法還要拼接裝修清單的文本——把品牌、型號、單價、面積、總價串成一段可讀的字符串。業務邏輯（選什麼料）和展示邏輯（怎麼顯示）混在同一個方法裡，改顯示格式會影響業務計算。整個工程只有一個核心類 DecorationPackageController，三種套餐的選擇、計算、展示全在一個類裡。這就是「一個類幾千行代碼」的潛質——先能跑，再慢慢堆，堆到不可維護。

幾個月後，老闆說加一個「輕奢北歐」套餐。你需要在 ifelse 裡加一個 else if 分支，複製一套物料 new + 價格計算 + 清單拼接的代碼，確認計算係數沒抄錯，確認清單格式沒漏改。十種套餐、二十種？每個都要加一段幾乎相同的代碼，像膏藥一樣一塊塊貼上去，維護成本呈線性增長。

用單測跑三檔套餐，結果功能完全正確：豪華歐式 198,064.39 元、輕奢田園 119,865.00 元、現代簡約 90,897.52 元。但代碼結構已經埋下了維護地雷。功能對不等於結構好——這是判斷代碼質量的第一課。ifelse 版本的四個核心問題：重複邏輯（價格計算在每個分支裡複製粘貼）、職責混雜（選料、計算、展示全塞一個方法）、擴展困難（加一個套餐等於加一段複製代碼）、單類膨脹（一個類扛所有，朝幾千行發展）。
