# 選用時機與權衡

<LearningGoal>
能說出建造者模式的選用時機、優缺點，以及何時不該用建造者模式。
</LearningGoal>

## Lesson

建造者模式的選用判斷可以用一句話概括：基本物料不變，而組合經常變化。裝修套餐就是典型案例——吊頂、塗料、地板、地磚這些物料是穩定的，但「哪些品牌組合成什麼套餐」會隨業務需求頻繁調整。這時候用建造者模式，新增套餐只需在 Builder 裡加一個方法，不用動其他代碼。

建造者模式的優點：單一職責（接口管契約、實現管計算、建造者管組裝，各司其職）、可復用（DecorationPackageMenu 可被多個 Builder 方法復用）、建造者獨立（新增套餐不影響已有代碼）、易擴展（加方法比改 ifelse 安全得多）、細節風險可控（每個建造方法獨立，出問題容易定位）。

但建造者模式不是萬能的。當物料和組合特別多時，類會不斷擴展——每種物料一個類、每個套餐 Builder 裡一個方法、接口有多個 append 方法。如果物料種類暴增到二十種、套餐組合上百種，代碼量依然會膨脹。此時可以考慮把重複內容抽象到數據庫按需配置，用配置驅動代替代碼硬編碼，但核心思路（構建與表示分離）仍然可以沿用。

何時不該用建造者模式：只有一兩種固定組合時，直接 new 就夠了，引入建造者是過度設計；構建過程很簡單時，一個構造函數能搞定的事不需要三個類；組合方式極度複雜且不穩定時，可能更適合用配置驅動或規則引擎。

建造者模式和工廠模式都解决「對象怎麼來」的問題，但思路不同：工廠模式一次性創建整個對象、隱藏創建細節；建造者模式分步驟構建、允許按需組裝。如果對象的構建過程是「一步到位」的用工廠，需要「逐步填充」用建造者。面試問建造者模式時，重點講三個：意圖（將複雜對象的構建過程與其表示分離）、適用場景（基本物料不變、組合頻繁變化）、代價（類數量增加，組合過多時可考慮配置化）。用裝修套餐場景串講這三點，比背誦 GoF 定義有說服力得多。
