# 四角色分工：原物件、備忘錄、記錄者、管理者

## Learning goal

記住四個角色的名稱與職責分工，形成理解任何備忘錄實現的結構地圖。

## Lesson

上一課看到了一把梭 ConfigManager 的問題：存配置、管歷史、回滾邏輯全混在一起。備忘錄模式的核心設計思路是<strong>把這些職責分離到不同的角色</strong>，每個角色只做一件事。拆開的好處是每一層都可以獨立變化：存儲結構想從 List 換成 Map？只改 Admin。快照格式想加壓縮？只改 ConfigMemento。回滾邏輯想加日誌？只改 ConfigOriginator。原物件 ConfigFile 完全不用動。

四個角色：<strong>ConfigFile（原物件）</strong>承載被保存的狀態（版本號、內容、時間、操作人），它只管自己的業務邏輯，不知道備忘錄的存在；<strong>ConfigMemento（備忘錄）</strong>是快照的載體，把原物件的狀態包起來，相當於一個密封的盒子，不知道誰會存它、誰會讀它；<strong>ConfigOriginator（記錄者）</strong>知道 ConfigFile 的內部結構，是唯一能讀寫 ConfigFile 的角色——`saveMemento()` 把當前狀態包成新的 ConfigMemento，`getMemento(memento)` 把快照裡的狀態寫回當前的 ConfigFile；<strong>Admin（管理者）</strong>用 List 保序 + Map 按版本號索引存放多個 ConfigMemento，提供 undo（回滾）、redo（前進）、get（按版本號取），但 Admin 完全不知道 ConfigFile 長什麼樣——它只跟 ConfigMemento 打交道。

備忘錄模式最精妙的地方在於<strong>資訊的不對稱</strong>：Admin 不知道 ConfigFile 的內部結構，ConfigFile 不知道有人在存自己的狀態。互動流程是 ConfigFile 的狀態經由 ConfigOriginator 的 `saveMemento()` 生成 ConfigMemento，交給 Admin 保存；需要還原時 Admin 取出某個 ConfigMemento 交給 ConfigOriginator 的 `getMemento()`，寫回 ConfigFile。整個過程 ConfigFile 是被動的，不需要加任何方法、不需要暴露任何欄位。記住這張結構地圖，下一課我們用 Java 代碼逐類走讀。
