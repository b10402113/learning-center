# 配置回滾場景：從一坨代碼到模式重構

## Learning goal

用系統上線配置回滾的真實場景，體驗「一坨代碼 → 備忘錄模式重構」的完整過程，理解重構前後結構差異。

## Lesson

你在一個大廠做後端，系統要上線了。上線前要改配置文件——IP 地址、端口號、連接池大小，改完部署。結果配置改錯了，線上服務起不來。你需要緊急把配置退回上一次正常的版本。大廠的配置管理要求線上與本地隔離（配置文件不跟代碼一起提交到 Git）、每次變更都記錄五要素（版本號、時間、MD5、內容、操作人）、出問題時能一鍵回滾。我們聚焦在「記錄版本 + 支持回滾」這件事上：每次配置變更，把當前的完整配置狀態存一份快照；需要回滾時，從快照列表裡取出某個版本的配置，覆蓋當前配置。

最直接的寫法是把所有邏輯塞進一個 ConfigManager 類：`save()` 方法把配置加進歷史列表、`undo()` 方法把列表最後一項移除並返回前一項、`getVersion()` 按版本號遍歷查找。這個寫法行得通，但有幾個問題：<strong>職責混雜</strong>——存配置、管歷史、回滾邏輯三件事都混在一個類裡；<strong>回滾邏輯暴露</strong>——undo 直接操作 list，換一種存儲結構就要重寫；<strong>配置物件被直接暴露</strong>——history 直接存 ConfigFile，內部結構完全暴露在外面；<strong>難以擴展</strong>——加 redo、加版本合併，每加一個功能就要改 ConfigManager。

備忘錄模式把這件事拆成四個角色：<strong>ConfigFile</strong>（原物件，被保存的狀態）、<strong>ConfigMemento</strong>（備忘錄，快照的載體，把 ConfigFile 包起來）、<strong>ConfigOriginator</strong>（記錄者，負責生成快照 `saveMemento()` 和還原快照 `getMemento()`）、<strong>Admin</strong>（管理者，用 List + Map 存多個快照，提供 undo/redo/get）。重構後 ConfigFile 完全不動，它不知道有人在存自己的狀態；ConfigMemento 只管包裝；ConfigOriginator 只管存取；Admin 只管歷史管理——每個類只做一件事。測試連續保存四份配置後執行 undo → undo → redo → get("1000002")，每一步都返回正確的 ConfigFile 物件，回滾、前進、定向取全部符合預期。
