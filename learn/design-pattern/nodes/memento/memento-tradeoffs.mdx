# 適用邊界與存儲選型

## Learning goal

掌握備忘錄模式的適用邊界：何時該用、何時不該用、內存 vs 資庫的存儲取捨。

## Lesson

備忘錄模式最大的優勢是<strong>在不破壞封裝性的前提下提供回滾能力</strong>：職責分離（原物件不管存儲、管理者不管內部結構）、易於擴展（加 redo 只改 Admin、加壓縮只改 ConfigMemento）、原物件零侵入（ConfigFile 不需要加任何方法）。判斷標準很簡單：<strong>你需要保存物件的歷史狀態，並且支持回滾或恢復</strong>。IDE 撤銷、遊戲存檔、線上配置回滾、交易系統回滾、設計工具的歷史記錄，這些場景的共同特徵是需要「時間旅行」能力——回到過去的某個狀態。

不適合的場景：不需要回滾時備忘錄是多餘的複雜度；快照太大（比如幾百 MB 的數據庫狀態存 100 個版本）會撐爆內存；多個物件共享同一份狀態時快照的邊界不好定義；狀態頻繁變更時存快照的開銷可能比業務本身還大。存儲選型取決於是否需要持久化——IDE 撤銷和遊戲存檔用內存（進程關了就不需要歷史），配置回滾和交易回滾通常存資料庫（進程重啟後快照不能丟）。內存存儲要注意消耗，常見的應對策略包括限制歷史數量（只保留最近 N 個）、壓縮快照、增量快照（只存 delta）、混合存儲（最近的放內存、歷史的存資料庫）。

備忘錄容易跟幾個模式混淆：策略模式是「選哪個算法」，備忘錄是「回到過去的狀態」；狀態模式是「當前狀態決定行為」，備忘錄是「保存和恢復歷史狀態」；命令模式可以配合備忘錄做撤銷（命令對象保存 undo 快照），但它們解決的是不同的問題。任何設計模式都不是萬能的，引入模式是為了更易擴展和維護，不能反而把結構搞複雜。
