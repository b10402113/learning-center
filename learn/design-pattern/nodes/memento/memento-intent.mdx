# 為什麼需要備忘錄模式？

## Learning goal

建立備忘錄模式的意圖錨點：看到「需要保存歷史狀態、可回滾」的需求，就聯想到備忘錄。

## Lesson

你打開 Word 寫了一段話，按了 Ctrl+Z 撤銷。你打了一局遊戲，按了存檔。你在 IDE 裡改了二十行代碼，覺得改壞了，想回到改之前的版本。這些操作有一個共同點：系統在你不注意的時候，偷偷保存了一份當時的狀態，等你反悔了就幫你還原回去。

如果讓你用代碼實現「撤銷」功能，你會怎麼做？最直覺的想法是：把物件的內部狀態複製一份存起來，需要的時候再把存起來的狀態塞回去。聽起來不難，但這裡有一個關鍵的矛盾。假設你有一個配置物件 `ConfigFile`，裡面有版本號、內容、時間、操作人。現在你想把它的狀態存一份快照，以便回滾。最粗暴的做法是直接讀它的內部欄位——`content = configFile.getContent()`、`version = configFile.getVersionNo()`。這行得通，但它破壞了物件的封裝性（Encapsulation）：ConfigFile 把自己的內部狀態全部暴露給了外部，外面的代碼知道它有什麼欄位、怎麼存取。如果 ConfigFile 有 50 個欄位、10 個關聯物件呢？如果 ConfigFile 改了內部結構，所有讀它狀態的外部代碼都要跟著改。核心矛盾是：<strong>保存狀態需要讀內部資訊，但讀內部資訊就破壞了封裝</strong>。

備忘錄模式（Memento Pattern）的意圖一句話：<strong>在不破壞封裝性的前提下，捕獲物件的內部狀態，並在物件之外保存，以便之後還原</strong>。它不把內部狀態暴露給外部，而是讓物件自己負責「存檔」和「讀檔」。外面只需要說「幫我存一份」和「幫我回到之前的某份」，不用知道內部有什麼欄位。用遊戲存檔做類比：你在遊戲裡按存檔，遊戲把角色的血量、裝備、經驗值全部包進一個存檔檔裡。你不知道也不需要知道存檔檔裡面的二進位格式是什麼。你想讀檔的時候，遊戲從存檔檔裡把狀態塞回去，角色回到之前的樣子——你全程不需要「打開角色的內部狀態」。

備忘錄模式是 GoF 23 種設計模式中的**行為型模式**（Behavioral Pattern），關注的是「物件之間怎麼協作來完成保存和恢復」。它特別適合的場景是：需要保存歷史狀態、需要回滾或恢復到某個歷史版本。Word 撤銷、遊戲存檔、Git commit、Photoshop 歷史記錄、線上配置回滾，這些都是同一個需求的不同面孔。核心判斷標準：看到「保存歷史、可回滾」的需求，就聯想到備忘錄模式。
