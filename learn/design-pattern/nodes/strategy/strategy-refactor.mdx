# 優惠券場景的策略模式重構

## Learning goal

能走完「接口 → 四種券實現 → Context 控制類」的完整重構路徑，說出每個組件的職責。

## Lesson

上一節我們看到了優惠券計算的 ifelse 版本——一個方法裡塞了四種券的邏輯，參數髒、難擴展、難測試。現在，我們用策略模式把它重構一遍。重構的核心思路是：把每種券的計算邏輯抽成獨立的類，通過一個統一的接口讓它們互換。結構分三層：策略接口定義「算優惠」的統一契約、具體策略實現類各自封裝計算規則、上下文控制類持有策略並提供統一入口。

第一步，定義泛型接口 `ICouponDiscount<T>`，聲明唯一的計算方法 `discountAmount(T couponInfo, BigDecimal skuPrice)`。為什麼用泛型？因為不同券型的參數結構完全不同——直減、折扣、n 元購的券參數是 `Double`，滿減的券參數是 `Map<String,String>`（包含「滿多少」和「減多少」兩個值）。泛型讓接口保持一個方法的簡潔，同時允許每種券用自己的參數類型。

第二步，四種券各自的策略實現。每個券型一個類：直減 `ZJCouponDiscount` 做 `skuPrice - couponInfo`，滿減 `MJCouponDiscount` 從 Map 取出滿減門檻和金額再判斷是否達標，折扣 `ZKCouponDiscount` 做 `skuPrice × 折扣比例`（保留兩位小數），n 元購 `NYGCouponDiscount` 直接返回固定金額。所有實現都用 `BigDecimal` 計算避免浮點精度問題，統一兜底「最低支付 1 元」。每個類只關心自己的計算邏輯，滿減不用知道折扣的存在。

第三步，策略控制類 `Context<T>`。持有 `ICouponDiscount<T>` 成員，通過構造器注入具體策略，對外提供統一的 `discountAmount` 方法轉調策略實現。客戶端只調 `context.discountAmount()`，不關心具體是哪種券。構造器注入實現了「可替換」——傳入哪個策略，Context 就用哪個算法。測試驗證四種券在原價 100 元上折扣 10 元、最終支付 90 元，和 ifelse 版本的結果完全一致，功能零破壞。新增券型？寫一個新實現類，注入 Context 就行。
