# 策略模式的意圖與痛點

## Learning goal

能說出策略模式「定義一系列算法、封裝、可互換」的意圖，並用優惠券計算的 ifelse 爆炸場景說出為什麼需要這個模式。

## Lesson

提到設計模式，很多人會想到「很抽象、很難用」。但策略模式的起點其實非常具體：你寫了一個方法，裡面堆滿了 ifelse，每加一種新情況就要動已有代碼。優惠券計算就是最典型的例子——直減、滿減、折扣、n 元購四種券，如果全塞在一個 `discountAmount` 方法裡，每次加新券型就要多一個 else if 分支，為了滿減加的 `typeExt` 參數其他券型根本用不到，參數越塞越髒。問題的根源是：多種算法（不同券型的計算邏輯）擠在同一個方法裡，彼此干擾。

策略模式的意圖一句話：**定義一系列算法，把它們一個個封裝起來，使它們可以互相替換**。回到優惠券場景，四種券的計算邏輯其實是四個獨立的算法。如果把每個算法包成一個獨立的類，讓它們共享同一個接口，加新券就只需要新增一個實現類，不動任何已有代碼；改某一種券的邏輯也不會影響其他券型。用一個類比來說：諸葛亮給劉關張三個錦囊，每個錦囊裡裝的是一套應對特定情境的策略，到了對應的關口就拆開執行——你不需要在一個超大的「如果遇到什麼就怎麼辦」清單裡翻找，而是按需取用、即拆即走。

策略模式是 GoF 23 種設計模式中的**行為型模式**（Behavioral Pattern），關注的是「對象之間怎麼協作、算法怎麼分配」。它特別適合的場景是：同一個動作有多種算法實現，而且未來可能還會加新的。支付方式（信用卡、支付寶、微信）、排序算法（快排、歸併、插入）、ID 生成策略（UUID、雪花算法）都是典型的例子。核心判斷標準：算法可以互換，客戶端不想知道具體的實現細節。這正是策略模式要解決的問題——把 ifelse 分支替換成可替換的算法對象。
