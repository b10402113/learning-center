# 模板方法的收益與邊界

## Learning goal

評估模板方法的收益（統一執行標準、提取公用代碼）與限制（繼承耦合、超場景慎用），能說出何時用、何時不用。

## Lesson

模板方法模式有明確的收益和邊界。搞清楚「什麼時候該用、什麼時候不該用」，比死記結構更有價值。

### 收益：三筆帳

**統一執行標準。** 骨架方法把「做什麼、按什麼順序做」寫死了。不管是京東、淘寶還是當當，所有子類都按照同一套流程跑。你不需要擔心某個子類忘了登錄就直接爬取，因為骨架方法 `generateGoodsPoster()` 已經替你排好了。對團隊來說：新人加入只需實現自己的子類，不用理解整套流程的上下文。

**提取公用代碼。** 骨架方法裡的控制流（登錄失敗返回 null、結果傳遞等）是所有子類共享的。你不需要在每個子類裡都寫一遍 `if (!login()) return null`。公用邏輯放在父類，子類只管自己的差異。這就是「行為由父類管理、可變部分交給子類」的設計。

**擴展方便。** 新增電商站只需要新建一個子類，實現三個方法。既不用動父類，也不用動其他子類。這符合開閉原則（對擴展開放、對修改關閉）。

### 限制：三條邊界

**繼承耦合。** 模板方法依賴繼承——子類必須 `extends` 父類。Java 單繼承限制了子類不能再繼承其他類；父類改動（比如骨架方法新增一步）會影響所有子類。如果場景需要更靈活的組合（而不是嚴格的繼承層次），可能需要考慮其他模式。

**骨架不宜過長。** 模板方法的骨架方法如果太長（比如有 10 步），子類實現起來會很困惑，維護也會困難。骨架越短越好——它應該只做「編排順序」這一件事。

**超場景慎用。** 模板方法適合「流程固定、步驟可變」的場景。如果算法之間沒有先後依賴（可以隨意切換順序），用策略模式；如果流程中每一步的實現會動態變化（運行時才決定），用策略模式加注入；如果需要在運行時組合多個行為（裝飾、混搭），用裝飾器模式。硬湊模板模式到不適合的場景，會讓代碼比不用模式還難維護。

### 決策速查

| 你的場景 | 推薦模式 | 理由 |
| --- | --- | --- |
| 多個子類流程相同、步驟不同 | 模板方法 | 骨架固定，子類填空 |
| 多種算法可互換、客戶端選擇 | 策略模式 | 算法族互換，無固定順序 |
| 對象有多種狀態、狀態驅動行為 | 狀態模式 | 行為隨狀態改變 |
| 多級處理鏈、動態編排 | 責任鏈模式 | 處理者可動態增減 |
| 需要在運行時動態組合行為 | 裝飾器模式 | 疊加功能、不改原類 |

### 面試必答

面試官問「模板方法和策略模式有什麼區別」時，核心回答是：模板方法的**執行順序是父類釘死的**，子類只能填空；策略模式的**算法可以隨意切換**，客戶端決定用哪個。模板方法靠繼承實現，策略模式靠接口加注入實現。追問「什麼時候用模板、什麼時候用策略」，關鍵看「順序是不是釘死的」。
