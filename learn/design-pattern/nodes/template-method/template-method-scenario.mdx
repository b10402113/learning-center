# 爬蟲海報場景：為什麼需要模板

## Learning goal

分析「模擬爬蟲電商→生成推廣海報」三步流程，判斷哪些步驟公共、哪些差異。

## Lesson

假設你做了一個營銷工具：用戶把自己的邀請碼嵌入商品推廣海報，分享出去，有人通過這張海報下了單就能拿返利。要自動生成這種海報，你需要做一件事——**爬取電商網站的商品信息，然後生成帶邀請碼的推廣海報**。

（這裡是「模擬爬取」，不是真的去爬京東淘寶，只是用代碼模擬這個過程。）

### 三步流程

不管是哪個電商平台，整個流程都分三步：

| 步驟 | 做什麼 | 公共or差異 |
| --- | --- | --- |
| 1. 模擬登錄 | 用用戶帳號登入電商網站 | **骨架相同**：都要登錄，但各站登錄方式不同 |
| 2. 爬取信息 | 抓取商品名、價格等數據 | **差異最大**：各站頁面結構不同、解析方式不同 |
| 3. 生成海報 | 把商品信息 + 邀請碼合成 base64 圖片 | **骨架相同**：邏輯基本一致，但會帶上商品來源標識 |

三步的**執行順序是固定的**：先登錄、再爬取、最後生成海報。你不可能先生成海報再去爬數據。

### 為什麼這場景適合模板模式？

有三個理由：

1. **執行順序固定**——「登錄→爬取→生成」三步的先後關係不能變，這是骨架
2. **各站差異在步驟內部**——京東的登錄、爬取、生成實現跟淘寶的完全不同，但調用順序一樣
3. **新增電商只需新增子類**——當當、拼多多、亞馬遜……每加一個站就寫一個子類，骨架不用動

如果用一把梭的方式寫，你會得到一個超大方法，裡面 `if (isJD) { ... } else if (isTaoBao) { ... }` 不斷堆疊。每新增一個站就多一個分支，這就是之前在策略模式、狀態模式裡反覆見過的 ifelse 擴展性災難。

### 模板模式怎麼拆它

用模板模式重構後，結構變成一個抽象類加上三個電商子類：

```
抽象類 NetMall（骨架）
├── generateGoodsPoster(skuUrl)  ← 模板方法：固定三步順序
│   ├── login()         ← 抽象方法：子類實現各站登錄
│   ├── reptile()       ← 抽象方法：子類實現各站爬取
│   └── createBase64()  ← 抽象方法：子類實現各站海報生成
│
├── JDNetMall       ← 京東子類
├── TaoBaoNetMall   ← 淘寶子類
└── DangDangNetMall ← 當當子類
```

骨架方法 `generateGoodsPoster()` 在父類中按順序調用三步，子類各自填入自己的實現。新增拼多多？寫一個 `PddNetMall extends NetMall`，實現三個方法就行。

### 跟你之前的經驗掛鉤

你用過 Spring 的 `JdbcTemplate`、`RestTemplate`——它們都是模板方法模式的典型應用：`JdbcTemplate` 固定了「獲取連接→執行 SQL→處理結果→關閉連接」的骨架，你只需填寫 SQL 和結果映射；`RestTemplate` 固定了「構建請求→發送→解析響應」的骨架，你只需填 URL 和參數。骨架相同、填空不同。
