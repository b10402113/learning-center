# 智能體可靠性模式 (Agent Reliability Patterns)

## Problem Statement

生產環境裡,工具會逾時、模型會卡住、TTS 服務會掛。每一次失敗都是一個岔路:把錯誤丟給使用者,還是找到一條降級但可用的路?把錯誤丟給使用者的 agent 侵蝕信任、使用量與接受度;在使用者看不見的地方失敗並自行恢復的 agent,建立的是營運信心。

## Why it matters

可靠性模式是「agent 是軟體,用工程紀律對待」的具體兌現。它與[[learn/ai-agents-in-action/elements/agent-observability|智能體可觀測性 (Agent Observability)]]互為表裡——模式需要指標告訴它何時觸發,指標需要模式產生可觀測的行為;也與發布工程相連:自動回滾就是一種大尺度的 fallback。

## How it works

四件工具,由小到大:

1. **時間預算(timeout budgets)**——每條關鍵路徑給一個時間預算,由呼叫端當 SLA 強制執行:快速回應約 1500ms,工具呼叫 15–60 秒。預算破了就 fallback,不無限等。
2. **Fallback(退路)**——失敗時回最佳努力答案、換小模型、或省略非必要裝飾(例如格式化潤色)。
3. **斷路器(circuit breakers)**——同一工具重複失敗就跳閘,後續呼叫直接快速失敗並優雅卸載流量,不讓一個壞工具拖垮整條鏈。
4. **優雅降級(graceful degradation)**——最高原則:別讓使用者看到錯誤。TTS 掛了就繼續用文字;圖片工具慢了就回一個「稍後查看」的連結。

配套的發布工程(release engineering)把同樣的紀律拉到版本軸上:版本化一切(提示、工具 schema、工具伺服器、安全開關、模型選擇——提示可獨立於程式碼版本化),帶閘門晉級:離線測試 → shadow 流量 → 小比例 canary → 全量, SLO 惡化自動回滾;並 pin 每一輪用的確切模型/工具端點以保證可復現(Phoenix 這類 tracing 工具自動處理)。

## In plain terms

時間預算是「等你三十秒,不來我就先走」;fallback 是「大餐沒了,先上白飯」;斷路器是「這部電梯連續故障三次,今天先貼停用告示,別再讓人進去關門夾三次」;優雅降級是「導覽語音壞了,改發你一張地圖——總比把你丟在大廳罰站好」。發布閘門則是新品先給員工試吃(shadow)、再上一個貨架試賣(canary)、賣壞了连夜下架(auto-rollback)。

## Practical use

每條關鍵路徑寫下時間預算與對應 fallback;工具呼叫包斷路器;每個失敗路徑問「使用者看到什麼?」——答案不允許是 stack trace。版本變更一律走 測試 → shadow → canary → 全量,並在 SLO 惡化時自動回滾。

## Questions

### Q1. 四種可靠性模式各是什麼?「別讓使用者看到錯誤」為什麼是最高原則?
A1. 時間預算、fallback、斷路器、優雅降級。把錯誤丟給使用者的 agent 侵蝕信任、使用量與接受度;在使用者看不到的地方失敗並自行恢復才建立營運信心。

### Q2. 斷路器與單純重試的差別是什麼?(關係題)
A2. 重試是對單次失敗的本地反應,工具持續壞掉時重試只會放大故障;斷路器看的是「重複失敗」的形態,跳閘後快速失敗並卸載流量,防止把整條鏈拖垮——是系統級自保,不是呼叫級固執。

### Q3. 「SLO 惡化自動回滾」為什麼必須自動而不是人工?(價值判斷題)
A3. Canary 全量之後,壞版本每分鐘都在傷害真實使用者與信任;人工決策的速度與上班時間都跟不上。自動回滾把「先止血、再查因」變成預設,寧可偶爾多回滾一次,也不讓壞版本過夜。
