# 智能體可觀測性 (Agent Observability)

## Problem Statement

Agent 上線後出了事——回應變慢、工具偶發失敗、成本翻倍——你打開日誌只看到幾行 print。哪一輪對話、哪個工具呼叫、哪個模型呼叫出的問題?誰也說不清。看不到的東西修不了;更糟的是,系統「正常運行」和「運行得有價值」是兩回事,後者也需要被量出來。

## Why it matters

可觀測性是所有運維判斷的儀表板:可靠性模式何時觸發、成本槓桿從哪裡下手、發布閘門看什麼指標自動回滾,全都依賴先看見。它也是發布工程的搭檔——版本晉級的每道閘都拿可觀測數據當判準。

## How it works

三個元素:**traces、metrics、logs**。

**Traces(追蹤)**——用 OpenTelemetry 標準加 Phoenix 這類工具,沿整條路徑(UI → Gateway → Agent → Tools → Model)佈 span:每一輪、每個工具呼叫一個 span,用 correlation IDs(session_id、turn_id、tool_call_id)串起來,並在 span 上掛使用者物件。Pin 模型與工具的確切版本到每一輪,保證可復現。

**Metrics(指標)**——分三層,回答三個問題:

| 層 | 問題 | 例子 |
| --- | --- | --- |
| 營運(operational) | 系統還活著嗎? | p50/p95 延遲、工具成功率、token 用量、錯誤率、每 session 成本 |
| 品質(quality) | 活得好不好? | grounding 率、幻覺率、評估器通過率、使用者回饋 |
| 產品(product) | 活著有意義嗎? | 任務完成率、升級到人工的比例、轉換/解決率、解決時間、KPI |

營運指標說系統在跑;品質與產品指標說跑得有沒有價值。

**Logs(日誌)**——結構化 JSON,帶 PII 遮蔽(redaction)。

## In plain terms

Traces 是行車記錄器——每段路程全程錄下,出事時倒帶看是哪個路口拐錯了。Metrics 是儀表板——時速(延遲)、油量(成本)、引擎警告燈(錯誤率)一眼掃完。Logs 是維修手冊的筆記欄——每次保養記一筆,人名車號先塗掉(PII 遮蔽)。

## Practical use

上線前先埋 OpenTelemetry + Phoenix,不要出事才補。每輪與每個工具呼叫都建 span、帶 correlation ID;指標按三層建 dashboard;日誌一律結構化 JSON 並遮蔽 PII。發布閘門(離線測試 → shadow 流量 → canary → 全量)的每一步判準都從這裡讀。

## Questions

### Q1. 指標三層各自回答什麼問題?舉一個每層的例子。
A1. 營運層:系統在跑嗎(p95 延遲、工具成功率、每 session 成本);品質層:跑得好嗎(grounding 率、幻覺率、評估器通過率);產品層:跑得有價值嗎(任務完成率、升級人工率、解決時間)。

### Q2. correlation IDs 在 trace 裡的作用是什麼?(關係題)
A2. 把跨服務、跨 span 的事件串回同一輪對話/同一個工具呼叫(session_id、turn_id、tool_call_id),出事時才能從症狀倒帶回確切的呼叫鏈,而不是面對一堆斷裂的日誌。

### Q3. 老闆只看營運指標就宣布「系統很健康」。你怎麼回應?(價值判斷題)
A3. 營運指標只證明「在跑」,不證明「跑得對、跑得有價值」——幻覺率照樣可以爆表、任務完成率可以是零。要下健康結論,必須把品質層與產品層指標一起放上桌。
