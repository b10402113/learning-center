# 智能體消費模式 (Agent Consumption Patterns)

## Problem Statement

Agent 在筆記本上跑通了,然後呢?使用者看不到你的終端機。要讓真正的使用者用上這個 agent,你得決定一件事:它住在哪裡、別人怎麼「消費」它。放瀏覽器?放後端?還是根本不給人用、給別的 agent 用?這個決定影響延遲、安全、成本控制,甚至決定你接下來要寫多少基礎設施程式碼。

## Why it matters

選錯消費模式,代價不是「重構一下」這麼溫和。把供應商 API key 一起打包進前端的 agent,等於把 key 貼在公告欄上——開發者工具一打,key 就在那裡。反過來,把所有東西都塞進後端,即時語音的延遲又會毀掉使用者體驗。消費模式是部署的第一個分岔路口,後面的容器化、runtime 選擇、通訊線全都從這裡長出來。

## How it works

消費模式有三種,沿著「誰執行 agent 邏輯、誰持有憑證」這條軸展開:

| 模式 | agent 邏輯在哪 | 憑證在哪 | 適合 | 不適合 |
| --- | --- | --- | --- | --- |
| 內嵌(Embedded) | 使用者的瀏覽器/App | 危險:前端可見即公開 | 薄的即時 agent,後端代管憑證 | 長時任務、多智能體、成本/安全敏感 |
| API 微服務(Hosted API) | 你的後端 | 後端,安全 | 對付費客戶、需要按 key 限流與計費 | 極低延遲的對話/語音 UX |
| 工具消費(MCP/A2A) | 你的伺服器,以 server 形式暴露 | 服務端 | 讓其他 agent 把它當工具调用 | 人類直接使用的介面 |

**內嵌模式**的殘酷事實有三條:前端的任何東西都能被開發者工具抽出來,所以 API key 實質上是公開的;瀏覽器直接呼叫 LLM 或工具 API 會撞上 CORS 限制;所有瀏覽器共享同一把 key 時,服務端根本無法按用戶限流。所以內嵌只適合「薄的 agent 跑在前端、真正的憑證與重活由後端代管」的形態——即時語音 agent 是典型,配合[[learn/ai-agents-in-action/elements/ephemeral-keys|短時效金鑰 (Ephemeral Keys)]]使用。

**API 微服務模式**把 agent 包成一個 HTTP 端點:例如把圖片生成 agent 包在 FastAPI 後面,提供一個型別清楚的 `POST /generate`,回傳 PNG bytes。用 POST 是因為圖片生成跑得久、請求文字可能超過 GET 的長度限制。這個模式可以推廣:任何 agent 或工具都能包成一個 POST 端點、回傳乾淨的 payload。

**工具消費模式**讓其他 agent 透過 MCP 或 A2A 把你的 agent 當工具呼叫——你的 agent 不再是產品,而是別人系統裡的一顆零件。

三種模式可以組合:瀏覽器裡的即時語音 agent(內嵌)把生成圖片的活兒交給後端的 FastAPI agent(API 微服務),使用者繼續講話、圖片在背景生成——這正是前端 agent 以工具形式消費後端服務的樣板。

## In plain terms

內嵌像是把廚師請到家裡煮飯——反應最快,但你得把家裡鑰匙(API key)給他,而這位廚師會把鑰匙別在胸前逛街。API 微服務像是中央廚房——你只打電話下單,食材、瓦斯、食譜全在別人的地盤,你的鑰匙從不出門。工具消費是中央廚房不接零售電話,只接其他餐廳的批發單(MCP/A2A)。

## Practical use

把你寫好的 agent 上線給付費客戶:後端 API 模式。要做瀏覽器即時語音:內嵌 + 後端鑄發短時效金鑰,重活代理回後端。要讓公司裡其他 agent 都能用你的分析能力:包成 MCP server。生產等級的長時任務(生成圖片、跑報表)後面具還有佇列(Redis/SQS)、GPU worker 池、物件儲存與通知系統在撐。

## Questions

### Q1. 為什麼「把 API key 打包進前端程式碼」不算一種可以接受的權衡?
A1. 瀏覽器前端的任何內容都能被開發者工具完整取出,key 實質上是公開的;加上 CORS 限制與共享 key 無法按用戶限流,內嵌模式只適合配合後端代管憑證與短時效金鑰的薄 agent。

### Q2. 內嵌模式與 API 微服務模式各自最不適合什麼場景?(關係題)
A2. 內嵌不適合長時任務與多智能體系統(後端處理重、狀態複雜),也不適合成本與安全敏感的對客戶 agent;API 微服務不適合追求極低感知延遲的即時對話/語音 UX,因為每一來回都經過網路與後端。

### Q3. 團隊想在網頁裡做即時語音助理,但又要求 key 絕不外洩、可按用戶限流——你會怎麼判斷與取捨?(價值判斷題)
A3. 兩者可以兼得:agent 邏輯內嵌在瀏覽器以保住低延遲,但供應商憑證由後端在認證後鑄發短時效金鑰、限流與計費在服務端執行——犧牲的是架構複雜度,而不是安全或延遲。
