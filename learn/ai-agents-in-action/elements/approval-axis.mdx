# 審批軸 (Approval Axis)

## Problem Statement

「它是不是 agent？」這個問題吵了三年沒吵出結果，因為大家拿特徵清單在比：有沒有用工具？有沒有記憶？會不會規劃？比到最後變成哲學辯論。真正能用的分類問題只有一個：**核准點落在哪裡？** 使用者按下批准的顆粒度——每一步都批，還是只批目標——把四種長得很像的系統一刀切開。

## Why it matters

這根軸是可遷移的判準。任何工具使用系統丟到你面前，你不用看它行銷文案，問一句「誰在什麼顆粒度上批准行動」就能定位它。對建造者更重要：它是你設計 human-in-the-loop 閘門時的刻度尺——你不是在「要不要人類介入」之間二選一，而是在軸上替每個行動挑位置。

## How it works

**審批軸（approval axis）**以核准顆粒度為座標，排開四種 LLM 互動模式：

1. **直接 LLM 對話（direct LLM chat）**：純問答，無工具，無行動。
2. **工具增強 LLM（tool-augmented LLM)**：模型可呼叫工具，但流程由使用者主導，工具服務單一請求。
3. **助理（assistant）**：替使用者操作工具，但**每個步驟都要求核准**——批准顆粒度是「步」」。
4. **智能體（agent）**：對**高層目標**取得一次核准後，自行推理、規劃、執行多步工作——批准顆粒度是「目標」。

助理與智能體之間不是牆，是**光譜**：production agent 標配**漸進式人類介入（graduated human-in-the-loop）**——低風險步驟自主執行，高風險行動（寄信、採購、刪資料）設核准閘。所以「有核准點就不是 agent」是誤讀：問題不是有沒有核准，而是核准落在哪個層次。

## In plain terms

學徒與師傅。助理是那種每鎖一顆螺絲就回頭問「師傅這樣可以嗎」的學徒；agent 是你交代「把這台車修好」之後自己判斷先換機油還是先檢查煞車的師傅——但動到引擎大修這種大事，他還是會先跟你報價。

## Practical use

拿你的 LangGraph RAG 分析流程練手：檢索、重排、彙總都是低風險讀操作，放手讓它自主跑；一旦流程末端要「寄報告給主管」或「寫入資料庫」，就在那裡設閘。一趟流程裡閘門的位置，就是你系統在審批軸上的實際座標。

## Questions

### Q1. 助理與智能體在審批軸上的差別，一句話怎麼說？
A1. 助理要求逐步核准（per-step approval），智能體對高層目標取得核准後自行執行多步工作（goal-level approval）。

### Q2. 關係題：審批軸與漸進式人類介入是什麼關係？
A2. 審批軸是分類用的座標軸，HITL 是落在軸上的機制：production agent 用漸進式閘門（低風險自主、高風險核准）在光譜上取一個務實位置，而不是站在兩端。

### Q3. 價值判斷題：「任何一步要求核准，系統就只是 assistant」——這個主張錯在哪？
A3. 錯在把光譜當二元開關。書中明說助理與 agent 之間是沿自主性軸的光譜，production agent 本來就以漸進式核准控制風險；分界在核准層次（步 vs 目標），不在有無核准。
