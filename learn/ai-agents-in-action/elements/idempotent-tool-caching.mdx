# 冪等工具快取 (Idempotent Tool Caching)

## Problem Statement

Agent 會重試。網路抖一下、恢復迴圈跑一圈、佇列訊息重播一次,同一個工具呼叫就會發出第二次、第三次。如果那個工具是「查天氣」,重複呼叫只是浪費錢;如果是「寄 email」,重複呼叫就是給客戶寄三封一樣的信。狀態管理失敗是大型多話輪系統最常見的死因。

## Why it matters

冪等(idempotency)是讓重試安全的性質,快取是讓重試便宜的副產品。它撐起[[learn/ai-agents-in-action/elements/runtime-choice|執行環境選擇 (Runtime Choice)]]裡的事件驅動 worker(佇列重播需要冪等),也直接餵進[[learn/ai-agents-in-action/elements/cost-control-routing|成本控制與模型路由 (Cost Control and Model Routing)]]的多層快取槓桿。狀態這一環失守,前面所有 runtime 與拓撲的努力都會被重複副作用拖垮。

## How it works

先切記憶的兩層:

- **短期對話記憶**:當前 session 的逐輪(turn)內容,存 Redis/PostgreSQL 這類服務。
- **長期知識**:跨 session 的語意檢索,靠向量儲存上的語意搜尋,作為專屬共享服務。

再處理工具呼叫的重複問題。**冪等**的定義:同樣輸入呼叫一次與呼叫多次,結果相同。查天氣是冪等的(查幾次都一樣);寄 email 不是(寄幾次寄幾封)。

讓工具冪等後,就能安全地**快取與重播**:對輸入做正規化(canonicalize),從正規化結果派生 SHA-256 雜湊當 cache key,同 key 的呼叫直接回快取結果。一個 FastAPI 工具代理就是這個模式的落地:收請求 → 正規化參數 → 算 key → 查快取 → miss 才真的呼叫工具並寫回快取。事件驅動 worker 用同樣的冪等快取換三樣東西:效能、可擴充性、可重播除錯。

## In plain terms

冪等操作像「查今天的日期」——問一百次答案都一樣,所以答案可以抄在便利貼上(快取),別人再問就拿便利貼給他。非冪等操作像「按門鈴」——按三次,屋主出來罵你三次。便利貼只能貼給門鈴以外的東西。

## Practical use

每個會被 agent 呼叫的工具都先問:它冪等嗎?冪等的(查詢、检索、計算、匯率快照、embedding)加上 SHA-256 key 快取層;不冪等的(寄信、下單、寫入)要嘛設計成冪等(帶請求 ID 去重),要嘛嚴格限制重試次數並在重試前確認。對話狀態放 Redis/PostgreSQL,長期知識走向量庫。

## Questions

### Q1. 冪等的定義是什麼?為什麼「查天氣」冪等而「寄 email」不冪等?
A1. 同樣輸入呼叫一次與多次結果相同即冪等。查天氣多次回同一結果(無副作用累積);寄 email 每寄一次多一封副作用,次數改變結果。

### Q2. SHA-256 cache key 是怎麼從工具呼叫產生的?正規化這一步為什麼必要?(關係題)
A2. 先把參數正規化(排序鍵、統一單位與大小寫等),再對正規化後的輸入算 SHA-256 當 key。正規化確保語意相同的呼叫(只是參數順序或格式不同)落到同一把 key,快取才命中得了。

### Q3. 隊友想把「建立訂單」工具的回應直接加進快取層「省錢」。你怎麼判斷?(價值判斷題)
A3. 危險:建立訂單非冪等,快取重播等於憑空「建立」或「吞掉」訂單;正確順序是先把它改造成冪等(如帶 idempotency key 去重),再談快取;查詢類工具才是無條件快取安全的。
