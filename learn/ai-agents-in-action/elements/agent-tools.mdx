# 智能體工具 (Agent Tools)

## Problem Statement

LLM 關在上下文窗裡，讀不到你的資料庫、碰不到你的程式碼。你給它接上工具，它開始能幹活——然後你發現真正的噩夢才開始：工具會失敗。API 超時、資料格式變了、額度用完。多數人寫 agent 的第一個版本，工具一失敗整條流程就崩，因為他們把失敗當「例外」，而沒想過：在 agent 的世界裡，**失敷是常態，不是意外**。

## Why it matters

工具是 agent 的手腳——感知-決策-行動裡的「行動」全靠它。工具層的工程品質（怎麼註冊、怎麼處理失敗、怎麼接線）直接決定 agent 是能上線的系統還是週末專案。而接線方式的选择，牽動後面整個生態：per-agent 客製 vs 標準化協定，是 MCP 登場前所有人共同的痛。

## How it works

**智能體工具（agent tools）**是函式的延伸（tool functions）：把 API、資料庫、外部應用包起來，讓 agent 能對程式碼之外的世界行動。兩個機制：

- **註冊與描述**：工具以 **JSON 定義**註冊進 agent——名稱、參數、用途描述。agent 靠這份描述知道**如何呼、何時呼**。
- **失敗處理**：建造良好的 agent 把工具失敗視為**正常控制流（normal control flow）**：有限重試（bounded retries）→ 退回替代方案（fall back）→ 求助使用者（ask user）→ 放棄該步（abandon）。失敷有階梯，不炸流程。

接線的歷史痛點：每個 agent 各自為每個工具寫客製 wrapper（per-agent bespoke tool wrappers），N 個 agent × M 個服務 = N×M 份接線程式碼，不可持續。**MCP（Model Context Protocol）**這類協定把整合移到服務端做一次（once per service）：工具變成標準化、可探索的外部工具伺服器，agent 用統一協定發現並呼叫。配套的安全姿態：MCP server 是**受信任依賴（trusted dependency）**——審原始碼、鎖版本、最小權限、高風險行動保留人類核准。

## In plain terms

工具箱裡每把工具都貼著一張說明標籤（JSON 定義）——老王不用真的會用電鑽，他讀標籤就知道「這把可以鎖螺絲、要插電」。電鑽插上去沒電？先換個插座（重試），再借鄰居的（fallback），都不行就問客戶要不要改用手鎖（ask user），真不行這面牆先不鑽（abandon）。而 MCP 就像全社區共用一個工具圖書館——每家不用自己買齊所有工具、寫自己的借還規則。

## Practical use

寫 agent 時把失敗階梯做成顯式程式碼：每個工具呼叫包在 retry（設上限）→ fallback 工具 → human-ask → skip 的四層裡，並把每層的選擇記進 log。清點你在多個專案裡重複寫過的 wrapper——那份清單就是你日後改用 MCP server 的第一批候選。

## Questions

### Q1. 工具失敗的處理階梯是哪四步？
A1. 有限重試 → 退回替代方案 → 求助使用者 → 放棄該步。失敷是正常控制流，不是炸掉流程的例外。

### Q2. 關係題：per-agent wrapper 與 MCP 的接線成本差在哪？
A2. per-agent 是每個 agent 對每個服務各接一次（N×M）；MCP 把整合移到服務端做一次（per-service），agent 以統一協定探索呼叫，新增 agent 邊際成本趨近於零。

### Q3. 價值判斷題：引入第三方 MCP server 最該新增的工程實踐是什麼，為什麼？
A3. 把 server 當受信任依賴管理：審原始碼、鎖版本、最小權限、高風險行動保留人類核准。因為工具一旦標準化、外來化，供應鏈風險就取代接線成本成為主要風險——信任要驗證，不是白給。
