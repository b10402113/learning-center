# 短時效金鑰 (Ephemeral Keys)

## Problem Statement

瀏覽器裡的 agent 要呼叫供應商的即時模型,就得有憑證。但長期 API key 一進前端就等於公開——被抽出來就能無限盜刷。可是不給憑證,agent 又動不了。這個死結需要一把「既能在前端用、被偷了也不心疼」的鑰匙。

## Why it matters

這是把[[learn/ai-agents-in-action/elements/agent-consumption-patterns|智能體消費模式 (Agent Consumption Patterns)]]裡的內嵌模式從 demo 推向生產的唯一安全路徑。沒有它,即時語音 agent 只有兩個壞選項:犧牲延遲把邏輯全搬後端,或者把長期 key 裸奔進前端。它也是「最小權限」原則在前端的具體化身。

## How it works

流程是「後端鑄幣,前端花錢」:

1. 使用者先向你的後端完成身份認證(登入、token)。
2. 前端向後端要一把短時效用戶端金鑰——ephemeral key。
3. 後端向供應商請求一把 TTL 很短的受限 key(只能連即時模型、幾分鐘內過期),回傳給前端。
4. 前端 agent 拿這把 key 直連供應商的即時模型,語音路徑不繞後端,延遲最低。
5. key 過期前,前端靜默刷新(silent refresh)換一把新的。

被偷的損失被三層限制夾住:壽命短(幾分鐘自動作廢)、權限窄(只授權特定服務)、可歸因(每個用戶一把,盜用可追蹤、可吊銷)。Demo 等級的寫法是在頁面裡直接 mint 一把金鑰;生產等級則把 mint 這一步放到後端、放在認證之後。

## In plain terms

長期 API key 是家裡的大門鑰匙,誰撿到誰能進屋搬東西。短時效金鑰是飯店的房卡:只開你自己那間房、明天中午自動失效、掉了就掉了——而發房的櫃檯(你的後端)會先核對你的身分證。

## Practical use

任何要在瀏覽器直連即時語音/串流模型的場景:即時語音助理、瀏覽器協作白板 agent、內嵌即時翻譯。搭配規則:工具保持簡單或代理回後端、TTL 越短越好、刷新全程靜默不讓使用者感知。

## Questions

### Q1. 短時效金鑰解決的核心問題是什麼?它靠哪三個限制控制被盜損失?
A1. 解決「前端需要憑證 vs. 前端憑證即公開」的死結;靠壽命短(TTL 幾分鐘自動過期)、權限窄(僅限特定服務)、可歸因(每用戶一把,可追蹤吊銷)控制損失。

### Q2. Demo 寫法與生產寫法在「鑄發金鑰」這一步的差別是什麼?(關係題)
A2. Demo 在頁面/腳本裡直接 mint(等于憑證管理形同虛設);生產把 mint 放到後端、置於身份認證之後——先證明你是誰,後端才向供應商換一把受限短 key 給你。

### Q3. 產品經理說:「與其搞後端鑄發,不如把長期 key 放前端再加前端限流。」你怎麼回應?(價值判斷題)
A3. 不可接受:前端限流是可被繞過的用戶端程式碼,key 本身仍在開發者工具裡可見;服務端無法對共享的單一長期 key 按用戶區分與計費。短時效金鑰把控制點拉回服務端,才是可營運的方案。
