# 執行環境選擇 (Runtime Choice)

## Problem Statement

同一個系統裡,「查個匯率」要秒回,「生成客製圖片」要兩三分鐘,「每夜跑完三千份報告」根本不在乎單次延遲。把它們全塞進同一種執行形態——全同步 API、或全丟佇列——總有一端的體驗或成本會壞掉。部署選擇在系統長過單一 POC 之後,重要性不亞於提示與工具。

## Why it matters

Runtime 選擇是進階部署的核心決策框架,而它的關鍵指標只有一個:**延遲**。延遲決定 agent 跑在哪、怎麼跑,回頭又決定通訊線怎麼拉、拓撲怎麼長。選對 runtime,後面的[[learn/ai-agents-in-action/elements/communication-wires|通訊線 (Communication Wires)]]與[[learn/ai-agents-in-action/elements/front-door-pattern|前門智能體模式 (Front-Door Agent Pattern)]]都是自然推論;選錯,怎麼調參數都救不回體驗。

## How it works

三種 runtime,按「可接受的延遲」對號入座:

| Runtime | 形態 | 最適合 | 約束 |
| --- | --- | --- | --- |
| 邊緣(Edge) | agent 邏輯在瀏覽器/手機客戶端,串流連即時模型 | 對話/語音 UX,極低感知延遲 | 工具保持簡單、無狀態或代理回後端;秘密用短時效服務端鑄發金鑰 |
| 同步 API | FastAPI 之類的 request/response 微服務 | 圖片生成、格式轉換、查詢、摘要等明確任務 | 受 HTTP 超時約束,任務不能跑太久 |
| 事件驅動 worker | 佇列後的 worker agent | 超過 HTTP 超時的長任務、需要重試、需要併發控制 | 要處理重試/重播,工具應冪等 |

決策的樞紐是延遲目標:逐 token 對話的感知延遲以百毫秒計,只有邊緣做得到;幾秒到幾十秒的任務,同步 API 最簡單;會超時、要重試、要排隊的,進佇列。實務原則:**從最簡單的開始**——先用 API,把熱路徑(延遲最敏感的互動)搬到邊緣,把重工具卸載給 worker。

## In plain terms

邊緣是櫃檯直接跟客人對話——最快,但櫃檯不能離開去倉庫搬貨;同步 API 是點餐後站著等出餐——十秒到幾分鐘可以,一小時不行;事件驅動是留電話號碼回家等——多久都行,做完了通知你。餐廳三種都有,因為客人對「等多久」的期待本來就分三檔。

## Practical use

規劃任何 agent 系統時先列延遲預算表:每條關鍵路徑標上可接受延遲,再逐條對映 runtime。混合形態是常態:語音助理(邊緣)+ 查詢工具(同步 API)+ 夜間報表(worker),彼此用[[learn/ai-agents-in-action/elements/communication-wires|通訊線 (Communication Wires)]]接起來。

## Questions

### Q1. 三種 runtime 各自的延遲檔位與典型任務是什麼?
A1. 邊緣:百毫秒級感知延遲,對話/語音 UX;同步 API:秒到數十秒,request/response 型任務(生成、查詢、摘要);事件驅動 worker:超過 HTTP 超時、需重試或併發控制的長任務。

### Q2. 「先從 API 開始」這條實務原則背後的理由是什麼?(關係題)
A2. 同步 API 是三者中最簡單、最熟悉的形態;先把系統跑起來,再依實測延遲把熱路徑搬去邊緣、把重工具卸載給 worker——避免一開始就為未出現的延遲問題付架構複雜度。

### Q3. 產品要求「每個回應都要在 500ms 內開始說話,但背景還要能跑五分鐘的分析」。單一 runtime 撐得住嗎?(價值判斷題)
A3. 撐不住也不必撐:500ms 開口是邊緣的活(前端串流即時模型),五分鐘分析是事件驅動 worker 的活(佇列+通知)。正確判斷是拆成兩個 runtime,而不是逼任何一種形態同時滿足兩檔延遲。
