# 前門智能體模式 (Front-Door Agent Pattern)

## Problem Statement

多智能體系統長大後,誰來面對使用者?如果每個 worker agent 都直接暴露給前端,使用者要自己判斷該找誰、系統的延遲特性各自為政、換一個後端服務前端就得改。需要一個「接待員」:使用者只認識它,它負責把活兒分派給後面各具延遲特性的 worker。

## Why it matters

這是編排器(orchestrator)模式往部署端的延伸,也是[[learn/ai-agents-in-action/elements/runtime-choice|執行環境選擇 (Runtime Choice)]]與[[learn/ai-agents-in-action/elements/communication-wires|通訊線 (Communication Wires)]]在拓撲層的落點:前門與 worker 各有自己的通訊與延遲要求,一個拓撲同時適配兩端。後續的發布工程與成本路由(把貴請求導給便宜模型)都以它為骨架。

## How it works

結構:一個面對使用者的**前門 agent**,把請求路由給後端的 **worker agents/服務**,每個 worker 有自己的通訊方式與延遲要求。

兩條設計規則撐起整個模式:

1. **適配兩端的延遲**:前門自己保持即時(低延遲的對話互動),重活交給延遲檔位各異的 worker——快的同步回、慢的進佇列事後回貼。
2. **前門越簡單越好**:把工作與控制儘量推進 worker agent。前門只做接待與路由,不做重活。胖前門是這個模式的反模式。

每個 worker 內部可以自由選用 flow(固定流程)、orchestrator(編排)、collaboration(協作)等工作方式——拓撲只管「誰面對使用者」,不管後面各服務內部怎麼組織。

## In plain terms

醫院掛號櫃檯:你不會自己衝進放射科。櫃檯(前門)聽你描述、決定你該去哪一科(路由);每個科別(worker)有自己的作業節奏——快診當場看完,檢驗報告三天後再來。櫃檯本身不看診,越快打發你去正確的科,整間醫院越順。

## Practical use

任何「一個入口、多種後端服務」的系統:語音助理當前門,圖片生成、知識查詢、報表分析各為 worker;公司內部 portal agent 當前門,各部門的 MCP server 當 worker。實作時前門用低延遲 runtime(邊緣或輕量 API),worker 按[[learn/ai-agents-in-action/elements/runtime-choice|執行環境選擇 (Runtime Choice)]]各自歸位。

## Questions

### Q1. 前門模式的兩條設計規則是什麼?
A1. 適配兩端延遲(前門即時、worker 各按各的延遲檔位);前門越簡單越好(工作與控制推進 worker,前門只接待與路由)。

### Q2. 前門模式與編排器模式的關係是什麼?(關係題)
A2. 前門模式是編排器往部署端的延伸:編排器管「多 agent 怎麼合作」,前門在此之上加上「誰面對使用者、如何適配部署端(延遲/通訊)」——拓撲視角而非工作流視角。

### Q3. 團隊想把「產生週報」的完整邏輯寫進前門,「因為反正它看得到所有請求」。你怎麼判斷?(價值判斷題)
A3. 反對:週報是慢任務,塞進前門會把接待與路由一起拖慢,違反「前門越簡單越好」。正確做法是週報作為 worker(事件驅動),前門只負責把需求路由過去並回報狀態。
