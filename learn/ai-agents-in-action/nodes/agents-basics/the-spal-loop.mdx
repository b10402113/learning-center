# SPAL 迴圈：agent 的運行時鐘

## Learning goal

能把 [[learn/ai-agents-in-action/elements/spal-loop|SPAL 迴圈 (Sense-Plan-Act-Learn Loop)]] 當成運行機制而不只是四個名詞：說出每一拍的輸入輸出、目標→任務→工具呼叫的分解鏈、狀態怎麼跨圈進化，並用長程／短程案例判斷內建推理何時夠用、何時仍需結構化推理。

## Lesson

你用 LangGraph 搭過一個 multi-agent 的 RAG（Retrieval-Augmented Generation，檢索增強生成）分析流程。它能跑。圖也畫得出來：幾個節點、幾條邊、一個條件分支。但老王想先問你一個有點討厭的問題——如果有人指著你那張圖問：「這個系統的『心跳』在哪裡？它每一輪到底在繞什麼圈？每圈進來什麼、出去什麼？」你八成會愣住。因為你搭它的時候，腦子裡想的是「節點接節點」，不是「一圈繞一圈」。

這一步，我們就把那個圈補上。它有個正式名字：**SPAL 迴圈（sense-plan-act-learn loop，感知—規劃—行動—學習循環）**。但按照老王的規矩，定義最後再說。我們先做個菜。

### 先做個菜

老王餓了。目標：一頓晚餐。

老王打開冰箱看一眼。半顆高麗菜、兩顆蛋、一小碗蝦仁。這是**感知（sense）**：輸入與上下文的處理——東西進來，變成可推理的資訊。

然後老王站在冰箱前想：炒蝦仁要蔥，沒蔥，那就改做蝦仁炒蛋；高麗菜清炒；飯是昨天剩的，加熱就行。這是**規劃（plan）**：推理「下一步做什麼」，把「晚餐」這個目標拆成任務，把任務排成順序。

接著開火、下鍋、翻炒。這是**行動（act）**：執行動作，產生輸出。輸出是一道一道的菜。

最後嘗一口。太鹹。老王記住：這個牌子的醬油，下一道要減半。這是**學習（learn）**：評估輸出，更新記憶。

一圈，四拍。下一道菜，從「醬油很鹹」這個新狀態再繞一圈。目標「晚餐」被拆成「三菜」，「三菜」再拆成「先熱飯，熱飯時切菜」——你已經看到那條分解鏈了：**目標（goal）→ 任務（task）→ 動作**。做菜時你天天在跑 SPAL，只是沒人給你發工資。

### 你可能會說：這不就是個 while 迴圈嗎

老王替你把心裡話說出來：「這不就是個循環嗎？LangGraph 的圖本來就會繞，我有裝重複啊。」

對，你裝了「重複」。但重複不等於迴圈有結構。差別在哪？在一個真正的 SPAL 迴圈裡，**每一拍有明確的輸入和輸出，拍與拍之間交接的是狀態**；而一個只有 while 的系統，四件事糊成一團，全塞在同一次 LLM 呼叫裡，你根本說不清哪一步出了問題。這不只是理論潔癖——它是你的 debug 地圖。系統卡住時，先問卡在哪一拍，比盲目換模型有效得多。

### 把四拍當機器拆開

現在我們把每一拍的輸入、輸出交代清楚。這是本課的地基。

**第一拍：感知（sense）。** 輸入：使用者訊息、工具回傳的結果、環境狀態、從記憶裡撈出來的舊經驗。輸出：一份整理過的、可以拿去推理的上下文（context）。注意，感知不是「收資料」而已，是「把資料變成上下文」——篩選、摘要、放進**上下文視窗（context window，模型一次能讀進的容量）**。同樣十段檢索結果，全塞進去和挑三段進去，是兩種完全不同的感知品質。

**第二拍：規劃（plan）。** 輸入：感知產出的上下文，加上目標。輸出：下一步的決定——通常是一個工具呼叫，或一串排好序的任務。這裡就是那條分解鏈所在：目標 → 任務 → **工具呼叫（tool call）**。「分析這批論文」是目標；「先摸清各論文的方法論」是任務；「呼叫向量檢索，查詢詞是 methodology」是工具呼叫。書裡講得很直白：目標分解成任務，任務分解成工具呼叫 [[sources/ai-agents-in-action/AI Agents in Action, Second Edi - Micheal Lanham.pdf#1.1.2]]。plan 階段做的事，就是在這條鏈上往下走、往旁邊換道。

**第三拍：行動（act）。** 輸入：plan 交下來的工具呼叫。輸出：工具執行的結果。關鍵性質是：工具呼叫之間的輸出是可**鏈接的（chainable）**——上一步的輸出，成為下一步的輸入 [[sources/ai-agents-in-action/AI Agents in Action, Second Edi - Micheal Lanham.pdf#1.1.2]]。第一個查詢撈回來的東西，決定第二個查詢該用什麼詞。工具讓 agent 能碰到它代碼庫以外的世界——API、資料庫、外部應用 [[sources/ai-agents-in-action/AI Agents in Action, Second Edi - Micheal Lanham.pdf#1.1.3]]。順帶說一句，工具會失敨是常態，好的 agent 把失敗當正常控制流：重試、換路、問人、放棄 [[sources/ai-agents-in-action/AI Agents in Action, Second Edi - Micheal Lanham.pdf#1.1.3]]。這件事下一課專門講。

**第四拍：學習（learn）。** 輸入：這一圈的行動結果，加上原目標。輸出：兩樣——對輸出的評估，以及更新後的記憶。這輪檢索結果好不好、哪個查詢是白費功夫，回寫成經驗。**記憶更新就發生在這一拍**，不在別處。這也是四拍裡最常被漏掉的一拍：很多系統繞圈，但從不學習，於是每一圈都是第一圈。

四拍交接的東西，統稱狀態。狀態跨圈存活，這才是迴圈和重複的真正區別。

### 拿你的 LangGraph RAG 分析器跑三圈

機制講完了，現在跑真的。把你那套 LangGraph 多智能體 RAG 分析器抓過來，給它一個故意模糊的目標，我們一圈一圈看狀態進化。

目標：「這批論文對『檢索品質』到底說了什麼？」

**第一圈。** 感知：目標進來，記憶是空的，上下文裡只有這句模糊的問題。規劃：LLM 推理——問題太泛，先廣撒網——決定查 "retrieval quality"。行動：向量檢索跑下去，回來二十段文。學習：評估——雜訊偏多，一堆在講 RAG 管線而不是品質本身；記憶更新——「查詢太寬，這批語料裡檢索品質的討論似乎集中在 reranking（重排序）附近」。

**第二圈。** 感知：上下文變厚了——有第一圈的檢索結果，還有剛寫進去的教訓。規劃：推理——上一圈的雜訊來自查詢太泛——決定改查 "reranking evaluation metrics"。行動：檢索，回來六段，四段相關。學習：評估——命中率上升；記憶更新——「這個語料的檢索品質討論集中在 rerank 與評估指標」。

**第三圈。** 感知：兩輪結果、兩條經驗，全在上下文裡。規劃：推理——材料夠了嗎？缺反方觀點——決定查 "limitations of reranking"。行動：檢索。學習：評估——正反都有了，狀態標記為「可收斂」，規劃下一圈輸出最終答案。

三圈下來，同一個系統，狀態完全不同。第一圈它什麼都不知道；第三圈它知道自己知道什麼。這就是迴圈的意義：**不是重複，是進化**。每一圈 learn 寫進去的東西，實實在在改變下一圈 plan 的品質。你在 LangGraph 裡寫的那個 state 物件，每圈被讀取、被改寫、再傳遞——它就是這個狀態的肉身。

### 這口鐘很老了：族譜

四拍鐘聽起來像是 LLM 時代的新發明？不是。它有族譜，而且族譜比我們都老。

軍事圈有 **OODA 循環（Observe-Orient-Decide-Act，觀察—導向—決策—行動）**，出自戰鬥機飛行員 John Boyd 的空戰理論：誰的觀察—判斷—決策—行動轉得比對手快，誰就活下來。你瞇眼一看：observe 對 sense，decide 對 plan，act 對 act——幾乎同構，SPAL 只是把最後補上一個明確的 learn 拍。

機器人學裡有經典的 **sense-plan-act 循環**：機器手臂先感知環境，規劃一條路徑，再執行動作。早期機器人就在這個圈裡活著。後來業界發現一個痛點：世界會動，規劃趕不上變化，於是長出各種反應式修正。這段歷史提醒我們：規劃永遠可能過期，所以圈必須繞、必須快。

**BDI 架構（Belief-Desire-Intention，信念—願望—意圖）**是另一門親戚，來自哲學再被軟體工程借走。信念是我相信什麼，願望是我想要什麼，意圖是我決定去做什麼。翻譯成 agent 的話：信念 ≈ 感知加記憶，願望 ≈ 目標，意圖 ≈ plan 的產出。

書裡直接點了這門親戚關係：SPAL 對應 OODA、BDI 和機器人學的 sense-plan-act [[sources/ai-agents-in-action/AI Agents in Action, Second Edi - Micheal Lanham.pdf#1.1.2]]，而 agent 這種「感知—決策—行動」的設計空間，早在 LLM 之前就存在 [[sources/ai-agents-in-action/AI Agents in Action, Second Edi - Micheal Lanham.pdf#1.1]]。所以 SPAL 真正「新」的地方只有一處：plan 這一拍換了引擎。以前是規則、是搜尋樹；現在是 LLM 的推理。圈的形狀，幾十年沒變過。你可以說 LLM 撿了個現成的架子，但不能說這架子是它發明的。

### 界線：內建推理 vs 結構化推理

好，來到本課真正要小心的地方。你可能聽人拍胸脯：「**前沿模型（frontier model）**都已經**內建推理（built-in reasoning）**了，誰還自己寫規劃邏輯？」

這話半對。書裡的說法是：前沿模型確實內建了推理，但對**長程任務（long-horizon task，需要很多步、跨越很多圈的任務）**和較弱的模型，明確的提示詞與**結構化推理（structured reasoning，用提示詞或代碼把推理步驟外顯地規定下來）**仍然關鍵 [[sources/ai-agents-in-action/AI Agents in Action, Second Edi - Micheal Lanham.pdf#1.1.2]]。我們用兩個案例把這條界線摸出來。

**案例一，短程。** 你的 RAG 分析器裡有一步：「判斷這次檢索結果相不相關」。一到三步、工具面小、錯了重來一次成本極低、又是模型最擅長的文字領域。這種場合，內建推理夠用。你硬要在中間塞一層結構化推理，多數時候是白燒 token、白加延遲。聽起來很爽的「一律上結構」，其實是一種過度醫療。

**案例二，長程。** 目標換成：「把這批論文整理成一份文獻綜述，二十個子主題，每個主題正反觀點都要」。這是幾十步、好幾十圈的活。矛盾來了：模型上下文視窗裡，第十七步的子目標，早就被前面十六步撈回來的檢索結果擠到邊緣。內建推理再強，它推理的原料本身在失真——不是模型不會想，是它想的時候忘了自己想幹嘛。這時你必須把子目標、進度、每圈的教訓明確寫進結構裡：外顯的任務清單、檢查點、狀態欄位。這就是結構化推理掙錢的場合：長程、多分支、錯誤昂貴或不可逆、跨出模型的主場、或者你在用較小的模型省錢。

界線一句話：**內建推理強在單圈之內的判斷，結構化推理強在跨圈的記憶。** 短程靠模型，長程靠結構。你那個 LangGraph 專案之所以要分好幾個 agent 節點、要傳 state，本質上就是在給一個長程任務上結構——只是當時沒人告訴你這件事的名字。

### 老王的收尾

我們繞了一大圈——對，這句話就是本課的內容。你以為你在學一個新概念，其實你是給手上已經能跑的系統，補上那張說明書：它有心跳，四拍一圈；它的狀態跨圈進化；它的病，先看卡在哪一拍。

說句老王自己的心裡話：第一次把 learn 拍當真——認真做輸出評估、認真回寫記憶——之後，老王寫的 agent 才第一次表現得像個「活的」東西，而不是一個會道歉的while迴圈。那一刻有點感動，也有點想笑：機器人學家四十年前就把圈畫好了，我們只是往裡面塞了一顆會講話的心。

下一課講工具：act 那一拍裡的螺絲釘，怎麼註冊、怎麼失敗、怎麼優雅地失敗。到時見。慢慢跑你的圈，別著急——老王先去把那道太鹹的菜重做了。
