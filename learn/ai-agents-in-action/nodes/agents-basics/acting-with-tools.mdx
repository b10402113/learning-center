# 工具：agent 的手，失敗是常態

## Learning goal

能解釋工具如何以 JSON 定義註冊進 agent、為什麼工具失敗要當成正常控制流來處理（重試、退回、問人、放棄），以及 per-agent 客製接線為什麼撐不下去——MCP 如何把整合工作移到服務端，一次做好。

## Lesson

凌晨兩點，你的手機響了。你上次交出去的那個 agent，那個會自動查資料庫、會發報表的自動化好幫手，炸了。原因很樸素：它呼叫的某個 API 超時了。就這樣。整條流程停在半空中，任務沒完成，錯誤日誌裡只有一句冷冰冰的 exception。你揉著眼睛爬起來看日誌，心裡想：白天測的時候明明是好的。

老王先把話放在這裡：這不是意外，這是宿命。在 agent 的世界裡，工具失敗不是「如果」，是「什麼時候」。這一課我們就來把這件事講透——工具是什麼、怎麼註冊、失敗了怎麼辦，以及最後那個大家都躲不掉的接線噩夢，和它的解法。

**工具：函式的延伸**

先別急著上定義，我們從你的痛講起。你在 LangGraph 裡搭過 multi-agent 做 RAG 分析，你知道 LLM 本身是個關在上下文窗（context window）裡的腦子：它讀不到你的資料庫，碰不到你的程式碼，寄不了一封郵件。它很聰明，但它沒有手。

工具就是那雙手。書裡的說法是：工具是**函式的延伸（tool functions）**——把 API、資料庫、外部應用包裝起來，讓 agent 能對它程式碼之外的世界行動（[[sources/ai-agents-in-action/AI Agents in Action, Second Edi - Micheal Lanham.pdf#1.1.3]]）。查一筆訂單、讀一個檔案、呼叫搜尋引擎，這些都是工具。回頭看上一課的 SPAL 迴圈（sense-plan-act-learn，感知-規劃-行動-學習）：sense 吃進上下文，plan 是 LLM 推理，而 **act 這一步，整個是由工具撐起來的**。沒有工具，agent 的「行動」是空的，它只能動嘴。

好，現在我們有了直覺，可以講機制了。

**註冊：一張給模型讀的標籤**

關鍵問題來了：模型怎麼知道有哪些工具可以用？它又怎麼知道什麼時候該用哪一個？

你可能會想：是不是工程師在程式碼裡寫死呼叫邏輯，模型只負責填空？不是。這裡的機制比你想的更「文字」：每個工具以一份 **JSON 定義（JSON definition）** 註冊進 agent。這份 JSON 裡主要有三樣東西：

第一，**名稱（name）**——這個工具叫什麼，模型用它來指名呼叫。第二，**參數規格（parameters schema）**——吃哪些參數、每個參數是什麼型別、哪些必填。第三，**用途描述（description）**——這個工具是幹嘛的、什麼場景該用它。這份描述通常還包括參數逐一的說明文字。

把這三樣東西想成一張貼在工具上的說明標籤。老王家的工具箱就是這樣：老王不用真的會用電鑽，他只要讀標籤——「電鑽：用於在牆上鑽孔，需插電，鑽頭直徑 6 至 12 公釐」——他就知道什麼時候拿它、怎麼拿它。工具不需要被「內建」進模型，模型也不用為了用電鑽去考一張證照。它讀標籤，就會用了。

而這正是整個機制最漂亮、也最容易被忽略的地方：**模型是「讀」這些標籤來決策的**。工具清單連同這些 JSON 描述會被送進上下文，模型在規劃下一步時，讀著標籤判斷：現在這一步，該叫電鑽還是叫螺絲起子？參數怎麼填？然後它輸出的不是執行結果，而是一個「我要呼叫某某工具、參數如下」的結構化請求。真正去執行的是你的 agent 執行環境，執行完把結果再餵回上下文，模型接著往下規劃。上一課說任務分解成一連串工具呼叫、輸出可以在呼叫之間串接，串接的膠水就是這個來回。

這也直接解釋了一件你寫 prompt 時一定遇過的事：工具的 description 寫得含糊，模型就會亂呼叫或者該呼叫時不呼叫。因為對模型來說，description 不是注釋，是**規格書**。標籤印錯了，拿錯工具不能怪手。這是很多人踩過才明白的坑：調工具呼叫行為，第一刀往往不是改程式碼，是改標籤。

**失敗：不是例外，是控制流**

好，工具註冊了，標籤貼好了，agent 開始幹活了。然後，凌晨兩點，那通電話來了。

工具會失敗，而且花式失敗：API 超時、回傳格式變了、額度用完、網路抖了一下、資料庫鎖住了。書裡給出的態度非常工程：建造良好的 agent 把工具失敗視為**正常控制流（normal control flow）**，而不是丟出例外就讓整條流程崩掉（[[sources/ai-agents-in-action/AI Agents in Action, Second Edi - Micheal Lanham.pdf#1.1.3]]）。

這句話你細品。「正常控制流」的意思是：失敗不是 if 的 else 分支裡那個理所當然不會發生的分支，它是你的程式裡和「成功」平起平坐的一等公民路徑。你要為它設計，就像你為成功設計一樣。

你可能會想：包一層 try-except 不就完了？

老王聽到這句話就想笑，因為老王年輕時也是這麼想的，然後被生產環境教育了。try-except 只回答了「炸了之後不要直接死」，它沒回答「炸了之後該怎麼辦」。except 裡面寫什麼？重試嗎？重試幾次？重試還是失敗呢？這些問題 try-except 一個都不會替你回答。

真正的答案是一條階梯，書裡把它列成四級，我們把它展開成近乎 pseudocode 的敘事：

第一級，**重試（retry）**，而且必須是**有限重試（bounded retries）**。超時了？等一下再試一次。但要設上限，比如三次。「有限」這兩個字是重點：不設上限的重試，等於花你的錢、消費者的耐心，去對一個已經死掉的服務反覆敲門。如果失敗的原因是額度用完，你重試三百次也不會生出額度來，只會生出一張帳單。所以重試要綁上限，常常還要配上退避（backoff）——每次重試之間等久一點，給對方喘口氣。

第二級，**退回替代方案（fall back）**。重試三次都失敗，別戀戰，換一條路。正式的 API 掛了，有沒有備用端點？這個搜尋工具不行，有沒有另一個查法？老王的電鑽沒電了，先換個插座；插座也沒電，去借鄰居的電鑽。任務的目標是「牆上要有個孔」，不是「必須用這把電鑽」。fallback 的設計關鍵，就是盯住目標而不是盯住工具。

第三級，**求助使用者（ask the user）**。替代方案也走不通，或者下一步行動有風險、需要人類判斷，就把決定權交出去。這一級你其實不陌生——還記得助理與 agent 的光譜嗎？低風險的步驟讓它自主跑，高風險的行動，比如發郵件、花錢，保留人類核准。失敗階梯的第三級和那條光譜在這裡接上了頭：**「問人」既是失敗的退路，也是風險的閘門**。

第四級，**放棄該步（abandon）**。問了人也沒轍，那就承認這一步走不通，優雅地跳過或中止，把「這步失敗了、原因是什麼」老老實實地回報出來，而不是讓整個 agent 當機在半空中。牆鑽不了，這面牆先不鑽，跟客戶說清楚，明天再想辦法。

四級階梯，一級一級往下走，每一級都有明確的進入條件和退出條件。把它寫成顯式的程式碼結構，而不是散落在各處的 ad-hoc 補丁——這就是「把失敗當控制流」的真正含義。而且別忘了 SPAL 的最後一課：失敗的紀錄餵回 learn 階段，哪個工具常失敗、哪種參數組合容易炸，這些是 agent 下次規劃時的養分。失敗處理得好，失敗就是資料；處理不好，失敗就只是凌晨兩點的電話。

**接線的噩夢：N 乘 M 的算術**

工具講完了？還沒。還有一個更大的坑，而且這個坑你本人就站在裡面。

你維護過不同框架的 agent——OpenAI Agents SDK 一套、LangGraph 一套，說不定 Dify 或 Coze 還有一套。而公司內部就那麼幾個 API：訂單系統、知識庫、通知服務。問題來了：每個框架接同一個內部 API，各接一次。LangGraph 的 wrapper 寫一份，Agents SDK 的又寫一份，格式還不一樣——這邊用 decorator，那邊用 JSON schema，第三個地方用 YAML。

書裡把這種做法叫做 per-agent 的客製工具包裝（bespoke tool wrappers），然後算了一筆帳（[[sources/ai-agents-in-action/AI Agents in Action, Second Edi - Micheal Lanham.pdf#1.1.3]]）。這筆帳我們一起算：N 個 agent 框架，M 個外部服務，每個 agent 對每個服務各接一條線，就是 **N × M** 份接線程式碼。聽起來還好？那是因為 N 和 M 都還小。三個框架五個服務，十五份，咬咬牙寫完了。明年框架換血、服務翻倍，帳單直接乘上去。更狠的是維護：服務改了一個欄位，你要記得去 N 個地方改 N 份 wrapper——漏一個，就是又一次凌晨兩點。這不是勤勞能解決的問題，這是**結構性**的浪費：同一件整合工作，被框架的差異逼著重做了 N 遍。不可持續，四個字就是為這種局面發明的。

**MCP：把整合搬到服務端，做一次**

所以，問題來了：能不能讓「接一次」這件事，對所有 agent 都算數？

能。這就是 **MCP（Model Context Protocol，模型上下文協定）** 登場的地方（[[sources/ai-agents-in-action/AI Agents in Action, Second Edi - Micheal Lanham.pdf#1.2]]）。它是 Anthropic 開發的開放標準，2024 年 11 月發布，建立在 JSON-RPC 2.0 這個訊息格式上。書裡給它起的外號流傳很廣：**「LLM 的 USB-C」**。你想想這個類比：USB-C 出現之前，每種設備一根線，抽屜裡纏成一團；USB-C 出現之後，一根線，到哪都能插。MCP 之於工具整合，就是這根線。

它換的正是那道算術題的算法：整合工作不再發生在 agent 端，而是**移到服務端，每個服務做一次（once per service）**。服務方——或你，為你的內部 API——把工具包成一個 MCP server（工具伺服器），講標準協定。任何一個講這個協定的 agent，都能連上來，用 list_tools 這樣的標準操作**探索（discover）**有哪些工具可用，拿到手的又是熟悉的 JSON 描述——對，就是我們前面講的那張標籤，標籤的格式也被標準化了。agent 不用為這個服務寫任何客製程式碼，接上，讀標籤，就會用了。

帳重算一遍：M 個服務各做一次整合，M 份；N 個 agent，零份客製接線。N 從算式裡消失了。新增一個 agent 的邊際成本，趨近於零。書裡還列了 MCP 連帶解掉的一串老毛病：工具存取方式不一致、資料回應不可靠、整合碎片化、程式碼擴充性有限、實作複雜——這些你今後會在第三章一條一條拆開講，這裡先記住主旋律就好。

**但是——信任要驗證，不是白給**

講到這裡，MCP 聽起來像銀彈。老王必須潑一盆冷水：**不是**。標準化把接線成本打掉了，但代價是，你的 agent 開始大量依賴「別人寫的工具伺服器」。風險沒有消失，風險換了一種形態：從接線成本，變成了**供應鏈風險**。

所以書裡給出的配套姿態是：把 MCP server 當成**受信任依賴（trusted dependency）**來管理（[[sources/ai-agents-in-action/AI Agents in Action, Second Edi - Micheal Lanham.pdf#1.2]]）。具體來說，四件事。第一，**審原始碼（vet the source）**——你接進來的 server 是誰寫的？開源的讀一遍關鍵路徑，不放心的別接。第二，**鎖版本（pin versions）**——不要讓它在你看不見的時候悄悄升級，今天的行為和明天的行為必須可預期。第三，**最小權限（least privilege）**——server 能拿到的憑證、能碰到的資料範圍，給它剛好夠用的，不多給一分。第四，**高風險行動保留人類核准**——就算工具再標準，刪資料、轉帳、對外發信這類動作，閘門要留在人類手裡。另外協定本身也提供了傳輸層認證、沙箱隔離、範圍受限的憑證這些機制，但機制是死的，姿態是活的：**信任要驗證，不是白給**。這句話你帶走，比記住任何 API 都值錢。

**收尾：一雙會發抖的手**

好，這一課我們走了很遠。盤點一下：工具是函式的延伸，靠 JSON 標籤註冊，模型讀標籤決定何時呼叫、如何呼叫；失敗是常態，要走「有限重試、退回、問人、放棄」的四級階梯，寫成顯式控制流而不是一層 try-except 了事；接線的 N × M 算術撐不久，MCP 把整合移到服務端做一次，但外來的工具伺服器要當受信任依賴來管。這些都收在 [[learn/ai-agents-in-action/elements/agent-tools|智能體工具 (Agent Tools)]] 這個條目裡，往後第三章我們會把 MCP 拆到螺絲那一層——親手寫一個 server，那才是你的交付物。

最後說句心裡話。這一課表面上是教工具，其實是教一個心態的轉變：新手把 agent 想成一個聰明的腦子，老手把 agent 想成一雙會發抖的手。腦子負責規劃，手負責執行，而手，是會抖的。你不會因為手會抖就不用手，你會給它戴上護具——那四級階梯就是護具。老王年輕時也迷信過「跑起來沒報錯就是穩了」，然後在某個凌晨兩點，穿著睡衣坐在螢幕前，看著一行 timeout，悟了。希望你不用親自接到那通電話。

去吧，把你手邊那個 agent 的工具呼叫，包上四級階梯。下一課見。
