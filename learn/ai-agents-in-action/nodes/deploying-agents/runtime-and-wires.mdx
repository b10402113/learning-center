# 執行環境與通訊線：延遲說了算

## Learning goal

能以延遲為關鍵指標選擇 runtime(邊緣/同步 API/事件驅動 worker),為每條連線匹配通訊線(WebRTC/WebSocket、HTTP+SSE、訊息匯流排),並用前門 agent 拓撲把不同延遲檔位的 worker 組成一個系統。

## Lesson

老王做了一個語音助理,叫阿福。功能不貪心:你說話,它回答;你問天氣,它查給你;你說「順便把這週的對話整理成週報」,它說好。提示詞調了三輪,工具接了五個,demo 漂漂亮亮,老王很得意。

然後上線。悲劇來了。

使用者喊一聲「阿福」,螢幕上的「等一下」轉了整整三秒。三秒,對文字聊天機器人也許還行,對語音助理就是一世紀——使用者話還沒說完,手指已經摸到掛線鍵了。提示詞沒變,工具沒變,模型也沒變。壞掉的不是智能,是延遲。

這一堂要講的就是這件事:**系統一旦長過單一 POC(Proof of Concept,概念驗證),部署選擇的重要性不亞於提示與工具。**而在所有部署決策裡,關鍵指標只有一個——延遲(latency)。延遲決定 agent 跑在哪、怎麼跑;agent 跑在哪,又回頭決定彼此怎麼通訊。把這條因果鏈走通,整個進階部署的骨架你都能自己推出來。老王把阿福的故事從頭到尾走一遍,你跟著走,三個決策會自然長出來。

### 第一個決策:agent 跑在哪——三種執行環境

先拆名詞。runtime(執行環境)聽起來很玄,它其實只問一件事:你的 agent 邏輯跑在哪台機器上、以什麼形態跑。答案有三種,每種對應一檔延遲。這就是[[learn/ai-agents-in-action/elements/runtime-choice|執行環境選擇]]的核心:不是問「哪種最好」,而是問「你的延遲目標是哪一檔」。

**第一種:邊緣。**agent 邏輯直接跑在客戶端——瀏覽器、手機——串流連上一個即時模型。阿福的「耳朵和嘴巴」就該住在這裡。語音對話的感知延遲是以百毫秒計的:你一開口,它就得開始聽;它一回話,聲音要一個字一個字流出來,而不是憋到整句算完才放音。這種體驗,只有邊緣給得起。代價也明白:客戶端是公開場所,工具要保持簡單、無狀態(stateless),或者代理回後端去跑;金鑰不能長期放在瀏覽器裡,要由服務端鑄發短時效的金鑰,用完即棄。

**第二種:同步 API。**就是你熟悉的 FastAPI 那類 request/response 微服務。天氣查詢、圖片生成、格式轉換、摘要,這類「一次請求、一個答案」的明確任務,秒級到幾十秒級,同步 API 最簡單、最順手。阿福查天氣就走這條:發一個請求,回一個答案,收工。約束也直白:HTTP 有超時,任務不能跑太久——你總不能讓一個請求掛在那裡五分鐘。

**第三種:事件驅動 worker。**佇列後面的 worker agent。週報這種活就是典型:要掃整週對話、跑分析、生成文件,五分鐘跑完算快的。這種任務有三個特徵——會超過 HTTP 超時、需要重試(失敗了重跑,而不是報錯了事)、需要併發控制(不能讓三百份報表同時壓垮資料庫)。三個特徵湊齊,答案就是佇列:任務丟進去,worker 慢慢消化,做完把結果貼回來。

整理成一張決策表:

| Runtime | 形態 | 延遲檔位 | 典型任務 | 主要約束 |
| --- | --- | --- | --- | --- |
| 邊緣 | 客戶端邏輯串流連即時模型 | 百毫秒級感知延遲 | 對話/語音 UX | 工具簡單、無狀態或代理;短時效服務端金鑰 |
| 同步 API | request/response 微服務 | 秒到數十秒 | 圖片生成、格式轉換、查詢、摘要 | 受 HTTP 超時約束 |
| 事件驅動 worker | 佇列後的 worker | 分鐘級,不在乎單次 | 超時長任務、需重試、需併發控制 | 要處理重試/重播,工具應冪等 |

實務原則一句話:**從最簡單的開始。**先用同步 API 把系統跑起來;實測發現哪條路徑對延遲最敏感(通常是對話),把它搬到邊緣;發現哪個工具拖慢全場(通常是重活),把它卸載給 worker。不要一開始就三種全上——架構複雜度是預付的,延遲問題卻可能根本不來。

這裡停一下,掛回你自己的經驗。你用 LangGraph 搭 multi-agent RAG 的時候,整張圖跑在同一個 Python process 裡:節點之間的「通訊」就是函式呼叫,微秒級,快到你從沒想過它的存在。部署改變了這件事——圖上的節點變成一個個獨立服務,函式呼叫變成網路呼叫,延遲第一次變成真實的敵人。所以「選 runtime」在 LangGraph 裡是隱形的,在部署裡是頭等大事。你在圖上畫的每一個節點,上線前都要重新回答一次:你跑在哪一檔?

### 第二個決策:連線走哪條線——三條通訊線

runtime 定了,線就跟著定了。通訊線就是 agent 跟 agent、agent 跟工具之間傳資料的方式。三種 runtime,對應三條線——這不是巧合,這是[[learn/ai-agents-in-action/elements/communication-wires|通訊線]]的鐵律:**線由延遲與部署需求決定。**

**第一條線:WebRTC/WebSocket——全雙工持久連線。**阿福跟使用者之間,就是這條。它給的是電話級的體驗:音訊和文字雙向同時流;你可以打斷它——這叫 barge-in——它一邊聽你糾正,一邊調整回應;回應的語音是串流合成的(TTS,Text-to-Speech,語音合成,一邊生成一邊念),文字是逐 token 吐出來的。所有「像人一樣對話」的體驗,都建立在這條持久雙向連線上。代價:連線管理複雜,拿它做簡單的請求/回應,是大砲打蚊子。

**第二條線:HTTP+SSE——請求/回應加串流輸出。**SSE 是 Server-Sent Events(伺服器推送事件):你發一個普通的 HTTP 請求,答案一邊生成、一邊串流回來。阿福呼叫天氣工具、查詢服務,走這條。它單純:容易代理、容易記錄、容易快取,中間要加閘道、加監控都不費勁。網頁客戶端要串流文字,也是它。這也是 MCP(Model Context Protocol,模型上下文協定)工具呼叫的標準姿勢。附帶一提:MCP server 不一定要走 HTTP——跑在本機的 MCP server 可以用 STDIO(標準輸入輸出)直接連,省掉整層 HTTP 開銷。部署形態可以降級線的選擇,這是個現成的例子。

**第三條線:訊息匯流排——非同步佇列。**Redis、NATS、Kafka 這類。阿福的週報走這條:前門把任務丟上匯流排,使用者的對話通道立刻空出來——你繼續跟阿福聊天,五分鐘後報表好了,結果貼回 session(工作階段)。這條線的價值就是**解耦慢工具**:工具多慢都不堵前端。代價也誠實:結果是最終一致的,不是立刻的;訊息會重試、會重播,所以工具最好冪等——同一個輸入跑一次和跑一百次,結果一樣。

| 線 | 機制 | 擅長 | 代價 |
| --- | --- | --- | --- |
| WebRTC/WebSocket | 全雙工持久連線 | 語音 UX:雙向流、barge-in、串流 TTS、逐 token 回應 | 連線管理複雜 |
| HTTP+SSE | 請求/回應+串流輸出 | 工具呼叫、網頁串流;易代理/記錄/快取 | HTTP 來回開銷;受逾時約束 |
| 訊息匯流排 | 非同步佇列(Redis/NATS/Kafka) | 解耦慢工具,結果事後回貼 session | 最終一致;重試/重播需冪等 |

用生活比一遍:WebRTC 是電話——兩邊同時講、隨時插話;HTTP+SSE 是簡訊——你問我答,我邊打字邊發給你看;匯流排是郵局——信丟進去,對方有空再處理,回信晚點到。跟朋友約吃飯用電話,跟客服回報問題用簡訊,寄合約用郵局。你不會把三件事統一成一種渠道——agent 系統也一樣,三條線對應三檔延遲需求,各走各的,才是真的簡單。

### 第三個決策:誰面對使用者——前門 agent 模式

三種 runtime、三條線都到齊了,最後一個問題:它們怎麼組成一個系統?誰面對使用者?

答案叫[[learn/ai-agents-in-action/elements/front-door-pattern|前門智能體模式]]:一個面對使用者的**前門 agent**,把請求路由給後面的 worker agents/服務,每個 worker 有自己的通訊方式與延遲要求。阿福本體就是前門:它住在邊緣,握著那條 WebRTC 線,跟你即時對話;聽到你問天氣,它路由給天氣 worker(同步 API,HTTP+SSE);聽到你要週報,它把任務丟上匯流排,交給報表 worker(事件驅動)。一個拓撲,同時適配前門的即時要求和 worker 們各自的延遲檔位。

用醫院比一遍:你不會自己衝進放射科。掛號櫃檯(前門)聽你描述、決定你該去哪一科(路由);每個科別(worker)有自己的作業節奏——快診當場看完,檢驗報告三天後再來領。櫃檯本身不看診;它越快打發你去正確的科,整間醫院越順。

這個模式有兩條設計規則,老王各配一個反面案例。

**規則一:適配兩端的延遲。**前門保持即時,worker 各按各的檔位——快的同步回,慢的進佇列事後回貼。反面案例:把週報邏輯寫進前門,理由是「反正它看得到所有請求」——前門一忙五分鐘,所有使用者的對話一起卡死。慢任務塞進前門,等於把醫院院長綁在手術台上,沒人掛號了。

**規則二:前門越簡單越好。**把工作與控制儘量推進 worker,前門只做接待與路由。胖前門是這個模式的反模式。這裡還有一層自由:每個 worker 內部愛怎麼組織就怎麼組織——flow(固定流程)、orchestrator(編排器)、collaboration(協作)都行。拓撲只管「誰面對使用者」,不管後面各服務內部怎麼幹活。你的 LangGraph 圖,將來很可能就是其中一個 worker 的內部實作——圖沒有消失,它被搬進了後廚。換句話說,LangGraph 教你的「編排」是前門模式的直系祖先:前門模式就是編排器長出部署視角之後的樣子——編排器管「多 agent 怎麼合作」,前門在這之上多管兩件事:誰面對使用者,以及每個服務用哪條線、哪檔延遲。

好,現在我們把阿福整個攤開:

| 組件 | Runtime | 通訊線 | 延遲檔位 |
| --- | --- | --- | --- |
| 阿福前門 | 邊緣(客戶端串流連即時模型) | WebRTC/WebSocket | 百毫秒 |
| 天氣/查詢 worker | 同步 API(FastAPI) | HTTP+SSE | 秒級 |
| 週報 worker | 事件驅動(佇列) | 訊息匯流排 | 分鐘級,事後回貼 |

順帶看阿福的升級路,這是「從最簡單的開始」的完整走法。第一天,整個系統只有一個同步 API:對話、查詢、週報全是請求/回應,自己玩夠用。第一週,拿給真人講話——發現對話路徑是熱路徑,「等一下」轉三秒——於是把對話搬到邊緣,拉起 WebRTC 線,三秒變三百毫秒。第二週,週報任務越來越重,開始撞 HTTP 超時,偶爾還失敗——於是把報表卸載到佇列後面的事件驅動 worker,前門只丟任務、收結果。三步,每一步都是被「實測出來的延遲問題」逼的,而不是第一天就畫好的宏大架構。好架構是長出來的,不是畫出來的。

最後替你把三個最可能冒出來的問題先問掉。

第一問:「我能不能全用同步 API,簡單到底?」能,如果你的系統永遠只有文字聊天和秒級工具——大多數內部工具確實如此。但語音一上場,感知延遲掉到百毫秒檔,同步請求/回應給不起;重工具一上場,HTTP 超時先跟你翻臉。不是同步 API 不好,是延遲檔位變了。

第二問:「那我把全部通訊統一上訊息匯流排,夠通用吧?」表面統一,實際更貴。簡單工具挂上匯流排,你平白多了重試、重播、冪等這整層負擔,而它們本來一個 HTTP 呼叫就能解決;語音塞進佇列更是直接毀掉即時性。三條線對應三檔延遲,讓每條連線按自己的檔位選線,才是真正可控的簡單。

第三問:「前門會不會成為單點?」會,所以它更必須簡單——簡單的東西才容易做高可用、容易水平擴展。把複雜度推進 worker,前門只剩接待與路由,壞了重拉一個就好。胖前門不只是反模式,還是可靠性事故的溫床。

### 收尾:誠實的帳單

老王要誠實:三種 runtime、三條線、一個前門,不是免費的。服務變多,部署、監控、重試邏輯都是真實成本。你可以說這套架構講究、燒運維,但你不能說它沒道理——使用者對「等多久」的期待本來就分三檔,硬用一種形態去滿足三檔,體驗和成本總有一端會先壞。這就像餐廳:櫃檯對話、點餐等出餐、留電話等外送,三種節奏本來就該並存,一家店三種全有,不是鋪張,是認真。

一句話總結這堂課:延遲說了算。先列延遲預算,再選 runtime;runtime 定了,線就跟著定;最後用前門把不同檔位的 worker 組起來,前門自己保持又輕又快。下次你的助理再「等一下」,你不會先去調提示詞——你會先看延遲預算表。老王掛線的手,也終於可以放下來了。
