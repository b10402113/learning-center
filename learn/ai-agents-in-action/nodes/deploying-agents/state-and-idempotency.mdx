# 狀態與冪等：重試為什麼不會炸

## Learning goal

能把 agent 記憶切成短期對話與長期知識兩層，判斷一個工具是否冪等，並用「正規化輸入 → SHA-256 cache key → 快取/重播」把查詢類工具變成可安全重試的快取單元。

## Lesson

老王上個月上線了一個客服 agent。功能很單純：客戶下單之後，agent 替客戶寄一封「您的訂單已成立」的確認信。本地測試的時候一切美好。上線第三天，機房網路抖了一下。agent 框架發現工具呼叫逾時，自動重試。又抖，再重試。半分鐘後，客戶的信箱裡躺著三封一模一樣的確認信。客戶把截圖貼到群組，還附上一個微笑。老王盯著那三封信看了一個下午：重試是框架的貼心功能，為什麼貼心的功能，炸的卻是我的生產環境？

好，這一課就是在回答這個問題。結論先講：炸掉的不是重試，是狀態（state）。一套大型、多話輪（chatty）的系統——agent、工具、模型你來我往幾十輪——最常失敗的位置，就是狀態這一環。這句話不是嚇你，是一次次部署事故換來的共識，而處方也只有四個字：保持簡單。狀態越簡單，能出錯的地方越少，復原的時候越救得回來。這一課我們拿三樣武器。第一，把記憶切成兩層的刀法。第二，判斷一個工具冪不冪等的直覺。第三，「正規化輸入 → SHA-256 快取鍵 → 快取/重播」的標準動作。三樣都拿到手，重試就從事故來源變成可靠性來源。

**第一刀：記憶切成兩層**

先處理「agent 記得什麼」這件事。這裡有個矛盾。狀態切得太細，一場對話的記憶散落在五個地方，系統崩潰之後你不知道先救哪一塊，復原遙遙無期；狀態通通塞進同一個地方，又什麼都記、什麼都撈不快，一個 session 的逐字稿和整座知識庫攪在一起，每次讀歷史都像搬一次家。所以共識是粗切兩刀，一刀管一個生命週期：

第一層，短期對話記憶（short-term conversational memory）。就是當前這場對話的逐輪（turn）內容：使用者說了什麼、agent 回了什麼、工具回傳了什麼。它生命週期短、讀寫頻繁，session 結束就可以退場，放 Redis 或 PostgreSQL 這類專門的服務。它的存在讓你敢於復原：worker 崩了，換一台機器，從 Redis 把對話狀態撈回來，從斷掉的那一輪繼續，客戶幾乎無感。這就是「狀態保持簡單」的第一個含義——狀態不在 worker 的記憶體裡，而在外頭一個可靠的服務裡，worker 本身保持可以隨時死、隨時換的狀態。順帶一提，逐輪紀錄最好是「只附加、不改寫」——附加式的紀錄本身就可以安全重播，這跟我們後面講的工具重播是同一個道理。

第二層，長期知識（long-term knowledge）。跨 session、要被反覆檢索的內容：產品文件、內部規範、歷史案例。它不是逐字稿，而是圖書館，靠向量儲存（vector store）上的語意搜尋（semantic search）來撈，而且應該做成一個專屬的共享服務——多個 agent、多個 session 共用同一座圖書館，而不是每個 agent 懷裡各揣一份，各自過期、各自打架。

| | 短期對話記憶 | 長期知識 |
| --- | --- | --- |
| 內容 | 這場對話的逐輪紀錄 | 跨對話的文件與事實 |
| 存放 | Redis / PostgreSQL | 向量儲存（共享服務） |
| 生命週期 | 隨 session 生滅 | 長期累積 |
| 撈法 | 按 session ID 直接讀 | 語意搜尋 |

一句話總結：短期記憶是逐字稿，長期知識是圖書館。逐字稿放 Redis，圖書館走向量庫，兩層不要混。老王的第一版 agent 就是反面教材：對話歷史和使用者文件塞在同一個 JSON 檔裡，每次要撈一段歷史，都得把整座圖書館搬一遍。你看，狀態不分層，連「記得什麼」這種小事都會變成效能事故。

**那麼，問題來了：重試**

記憶切好之後，回到那三封信。你要先接受一個事實：在 agent 系統裡，重試不是意外，是日常。它至少從三個地方冒出來。網路逾時，HTTP client 重試一次，這是第一個地方。工具伺服器重啟，框架的恢復迴圈（recovery loop）跑一圈，把沒有完成的工具呼叫重播（replay）一次，這是第二個地方。事件驅動的 worker——掛在訊息佇列後面的那種——天生就會把訊息重新投遞，因為佇列的哲學是寧可重複、不可丟失，這是第三個地方。三個地方你多半只控制得了第一個。重試是系統活著的證明，不是它壞掉的證明。

你可能會想：那把重試關掉不就得了？老王也想過，還真的關過一個晚上。結果 agent 變得比沒有 agent 還脆弱：查個天氣遇到一次抖動，就直接對客戶說「系統發生錯誤，請稍後再試」。客戶的第二個微笑比第一個更冷。所以矛盾在這裡，老王直接點破——重試讓系統活著，但重試會把副作用（side effect）乘上重試次數。寄 email 就是副作用：寄一次一封，重試三次，客戶收到三封。查天氣沒有這種副作用：查一次跟查三次，世界不會因此多下一場雨。

這條分界線有個正式的名字，叫冪等（idempotency）。照慣例先給直覺，再給定義。冪等的操作像「查今天的日期」：問一百次，答案都一樣，你甚至可以把答案抄在便利貼上，誰再問就拿便利貼給他。不冪等的操作像「按門鈴」：按三次，屋主出來罵你三次，便利貼救不了你。定義：同樣的輸入，呼叫一次和呼叫多次，結果相同，就是冪等。「查天氣」冪等；「寄 email」不冪等。匯率查詢冪等；扣款不冪等。文件檢索冪等；建立訂單不冪等。判斷方法樸素到不行：問自己一句——這件事做第二次，世界會不會多出什麼？

**冪等之後，快取是白拿的**

好，現在盤點一下手上有什么。查天氣這種工具，既然呼叫一次和呼叫一百次結果都一樣，那同一個問題被問第二次的時候，我們為什麼要真的再出一次門？把第一次的答案抄下來，下次直接遞過去——這就是快取（cache）。注意這個順序：是「因為冪等，所以敢快取」，不是「為了省錢，什麼都快取」。順序一旦反了，就會有人把「建立訂單」的回應也塞進快取，然後在重播的時候憑空生出一張訂單，或者吞掉一張真的訂單。這套「判斷冪等 → 快取 → 安全重播」的完整套路，整理在 [[learn/ai-agents-in-action/elements/idempotent-tool-caching|冪等工具快取 (Idempotent Tool Caching)]] 這個條目裡，值得整篇讀一遍。

落地的標準形狀，是一個 FastAPI 工具代理（tool proxy）：agent 不直接呼叫工具，而是呼叫這個代理；代理收下請求之後，做三件事。

第一步，正規化（canonicalize）。把工具名和參數整理成唯一一種寫法：鍵排序、單位統一、大小寫統一。這一步最常被跳過，也最不能跳過。因為語意相同的呼叫，表面上可能長得不一樣——`{"city": "Taipei", "unit": "c"}` 和 `{"unit": "c", "city": "Taipei"}` 是同一個問題，但字串不同。不先正規化，這兩次呼叫會落到不同的快取鍵，永遠命中不了，快取形同虛設。

第二步，算鍵。對正規化後的字串算 SHA-256 雜湊，當作快取鍵（cache key）。同一個問題，鍵必定相同；不同的問題，鍵幾乎不可能撞在一起——SHA-256 給你的保證，在快取這個場景綽綽有餘。

第三步，查快取。命中，直接回快取裡的結果，不出門；沒命中，真的去呼叫工具，結果寫回快取，再回給 agent。

程式碼長這樣，簡化到只剩骨架：

```python
import hashlib, json

def canonicalize(tool_name: str, args: dict) -> str:
    # 鍵排序 + 緊湊格式：讓語意相同的呼叫長得一樣
    return json.dumps(
        {"tool": tool_name.lower(), "args": args},
        sort_keys=True, separators=(",", ":"), ensure_ascii=False,
    )

def cache_key(tool_name: str, args: dict) -> str:
    return hashlib.sha256(canonicalize(tool_name, args).encode()).hexdigest()

async def call_tool(tool_name: str, args: dict):
    key = cache_key(tool_name, args)
    if (hit := await cache.get(key)) is not None:
        return hit                            # 命中：直接回，不出門
    result = await run_tool(tool_name, args)   # 沒命中：真的呼叫
    await cache.set(key, result, ttl=600)      # 寫回，十分鐘後過期
    return result
```

二十行不到。但就是這二十行，把「查天氣」從一個「每次都出門、出門就可能失敗、失敗就重試、重試就花錢」的操作，變成一個可安全重試的快取單元：第一次之後的每一次呼叫，要嘛命中快取瞬間回來，要嘛在恢復迴圈裡被重播，結果都一樣，錢只花一次。這個代理還附贈一個好處：所有工具流量都從同一個門口過，你要加日誌、限流、計量，都有一個集中的位置可下手，不用去改每一個工具。

**事件驅動 worker：同一招，三份收益**

如果你的 agent 跑在事件驅動的 runtime 上——掛在訊息佇列後面的 worker——這一招就不只是省錢，而是三份收益一次拿。上一課講過，訊息匯流排（message bus）把工具執行和使用者對話解開：使用者繼續講話，慢的工具在後面慢慢跑。但解耦是有代價的——佇列保證不丟訊息的方式，就是重新投遞。解耦給你彈性，重播給你責任。

第一，效能。佇列上大量重複的查詢類呼叫直接被快取吸收，worker 不用每次都去敲外部 API，延遲和帳單一起降。第二，可擴充性。多個 worker 同時上線，共享同一份快取，外部工具的壓力不會隨著 worker 數量線性膨脹；你從兩台加到二十台，天氣 API 那邊看到的還是同一份流量。外部服務有速率限制（rate limit），超過就鎖你——快取在這裡是替你擋子彈的那一層。第三，可重播與除錯。佇列為了不丟訊息會重新投遞；重播一條訊息時，冪等的工具呼叫可以放心重跑，查得回一模一樣的結果，你才能像倒帶一樣重現事故現場。這裡有個漂亮的順序：事件驅動的重播壓力，逼出冪等；冪等，順手成全了快取；快取，反過來讓重播更快。兩件事互為理由，這在工程上不多見，遇到了就整組抱走。反過來想：如果工具不冪等，你連「重播來除錯」都不敢做——一重播，客戶又收到一封信。可重播性是除錯的氧氣，而冪等是可重播性的門票。

**誠實的帳：這招不是免費的**

老王要把帳攤開講。這一招有三個邊界，裝作看不見，它們就會來看你。

第一，天氣會變。早上查的台北氣溫，晚上就不準了。所以快取一定要設 TTL（存活時間），過期就重新出門。TTL 設多長，取決於資料允許多舊：匯率快照幾分鐘，天氣幾十分鐘，embedding 這種確定性的計算可以更長。沒有 TTL 的快取不是快取，是謠言。

第二，不是所有「查詢」都能快取。跟使用者身分、授權、當下狀態綁死的結果，快取了就是事故：你會把 A 使用者的答案遞給 B 使用者。判斷標準一句話：答案只取決於輸入參數，才准進快取；答案取決於「誰在問」，一律不准。

第三，寄 email 永遠不會因為這二十行程式碼變冪等。要讓它安全，得走另一條路：讓每次寄信帶一個請求 ID（idempotency key），收信端看過這個 ID 就拒絕再收——把「按門鈴」改造成「按一次算一次，按第二次沒反應」。工程上做得到，但那是改造工具，不是快取工具。所以拿到一個工具箱之後，正確的動作是先掃一遍，分成三類：查詢類，直接掛快取代理；寫入類，先改造成冪等（帶請求 ID 去重），改造不了的，嚴格限制重試次數並在重試前確認；混合類，逐個參數看，別偷懶一刀切。快取只救得了本來就冪等的東西，沒有例外。

**收尾**

總結一下這一課。狀態是大型多話輪系統最常失守的一環，處方是保持簡單：短期對話記憶放 Redis/PostgreSQL，長期知識走向量庫的共享服務，兩層不要混。工具先問冪不冪等——查天氣冪等，寄 email 不冪等，判斷的方法是問「做第二次，世界會不會多出什麼」。冪等的查詢類工具，用「正規化 → SHA-256 → 快取/重播」包成可安全重試的單元；事件驅動的 worker 這樣做，還多賺效能、可擴充性、可重播除錯三份收益。至於老王，後來把確認信工具加上了請求 ID 去重，把查詢工具掛上了快取代理，從此再也沒有第二組三封信。那三封信成了他職業生涯裡最貴的一堂課——貴的是客戶的那個微笑，便宜的是學費。你的那一堂課也一定會來，希望你的學費，比老王的便宜。
