# 消費模式：你的 agent 住在哪裡？

## Learning goal

能用延遲、安全、成本三軸為 agent 選擇消費模式（內嵌瀏覽器 / 後端 API 微服務 / MCP-A2A 工具消費），並掌握內嵌模式赖以安全的短時效金鑰模式。

## Lesson

老王前陣子把一個 agent 跑通了:你對著麥克風說「畫一隻戴墨鏡的西瓜」,它就生成一張圖。筆記本上一切完美。然後朋友問了一句要命的話:「這東西能給我用用嗎?」

這一問,就把老王問到了部署的第一個分岔路口。你的 agent 在自己機器上跑得再漂亮,使用者也看不到你的終端機。要交貨,第一個問題不是選哪個框架,而是:這個 agent 住在哪裡?誰來執行它的邏輯?供應商的 API key 放在誰手上?這組選擇有個正式名稱,叫**消費模式(consumption pattern)**。它一口氣決定了延遲、安全、成本,還決定你接下來要寫多少基礎設施程式碼。這整套取捨整理成了 [[learn/ai-agents-in-action/elements/agent-consumption-patterns|智能體消費模式 (Agent Consumption Patterns)]] 這個概念,這一課就把它從頭走一遍。

路其實只有三條。第一,把 agent **內嵌(Embedded)**在使用者的瀏覽器裡,邏輯在前端跑。第二,把 agent 藏進你的後端,包成一個 **API 微服務(microservice)**,前端只打 HTTP。第三,你的 agent 根本不直接面向人類,而是讓別的 agent 透過 MCP 或 A2A 把它當工具呼叫。

首先,我們從最誘人的那條路開始:內嵌。

你可能會想:邏輯放瀏覽器,不就完了? 即時語音這種應用,最怕延遲。聲音每多繞一跳,對話就多一分機器感。把 agent 邏輯直接寫進網頁的 JavaScript,使用者的瀏覽器自己跑 agent、自己連模型,路徑最短,延遲最低。更何況 Agents SDK 本身就有 JavaScript 版,你筆記本上那套 agent 寫法可以直接搬進網頁。聽起來完美。

但瀏覽器會給你三個壞消息。

第一個壞消息:前端的一切都是公開的。你的網頁能拿到的任何東西,使用者打開開發者工具(dev tools)都看得到。把供應商的長期 API key 打包進前端程式碼,效果等於把 key 貼在社區公告欄上,而且是一個全世界都能路過的公告欄。前端可見,就是公開,沒有例外。

第二個壞消息:**CORS(跨來源資源共用,Cross-Origin Resource Sharing)**。瀏覽器有同源政策,CORS 是它的守門員。你的網頁想直接呼叫 LLM、或某個不認識你的工具 API?對方伺服器沒有明確允許你的來源,瀏覽器會直接把請求攔下來。同樣的呼叫,你在後端用 Python 跑得瀟灑自如,搬進瀏覽器,連門都進不去。

第三個壞消息:**限流(rate limiting)破產**。假設你硬著頭皮,把一把 key 給所有使用者的瀏覽器共享。服務端看到的所有請求都來自同一把 key,它根本分不清這是甲用戶的第一萬次呼叫,還是乙用戶的第一次。按用戶限流、計費、封鎖濫用,全部無從談起,成本也失去控制了。

所以很多人走到這裡,會下一個結論:「只要有 key,就不能內嵌。想安全,全部搬後端。」老王當年也是這麼想的。這個結論對了一半,也錯了一半。全盤搬進後端,安全是安全了,但即時語音的每一來回都要穿過你的伺服器,延遲又回來了。矛盾就擺在這裡:前端跑邏輯才有低延遲,後端管鑰匙才有安全。兩者看起來不可兼得。

**短時效金鑰(Ephemeral Keys)** 就是來解這個局的。它的直覺版本你早就認識:飯店房卡。你家大門鑰匙,誰撿到誰能進屋搬東西;飯店房卡只開你那間房,明天中午自動失效,掉了也就掉了。而發卡的櫃檯,會先核對你的身分證。

把房卡換成金鑰,流程是「後端鑄幣,前端花錢」,五步:

1. 使用者先向你的後端完成身份認證:登入,拿到 token。
2. 前端向後端要一把短時效的用戶端金鑰。
3. 後端向供應商換一把 **TTL(Time To Live,存活時間)**很短的受限金鑰,通常只能連即時模型(realtime model),幾分鐘內就過期,再回傳給前端。
4. 前端 agent 拿這把金鑰,直連供應商的即時模型,語音串流完全不繞你的後端,延遲最低。
5. 金鑰過期前,前端**靜默刷新(silent refresh)**,換一把新的,使用者全程無感。

就算金鑰被偷,損失也被三層夾住:壽命短,幾分鐘自動作廢;權限窄,只能做特定的事;可歸因,一個用戶一把,盜用追得到、吊銷得了。

所以正確的說法不是「有 key 就不能內嵌」,而是:內嵌可以,但長期 key 永遠不出後端,前端只花後端鑄發的短時效金鑰。這個組合形態長這樣:瀏覽器執行 agent 邏輯、串流直連即時模型,保住低延遲;後端只在認證通過之後鑄發短金鑰,保住安全;至於工具,保持簡單、**無狀態(stateless)**,或者把重活代理回後端做。這正是 [[learn/ai-agents-in-action/elements/ephemeral-keys|短時效金鑰 (Ephemeral Keys)]] 的完整用法。還有一個變體:前端 agent 透過存取權杖掛上一個遠端 MCP 伺服器,連工具都不必全寫在頁面裡。

demo 等級的寫法,是在頁面的腳本裡直接 mint 一把金鑰,圖個方便;生產等級,mint 這一步必須放到後端、放在認證之後。先證明你是誰,櫃檯才發卡。

老王還遇過一種反對意見:「與其搞後端鑄發,不如把長期 key 放前端,再在前端做限流。」這個方案聽起來省事,實際上站不住。前端限流是用戶端程式碼,使用者想繞就繞,開個無痕視窗、改個變數就過了。更根本的問題是:key 本身還躺在開發者工具裡,誰都抄得走;而服務端面對一把被所有人共享的長期 key,既分不清用戶,也沒法按用戶計費。控制點必須留在服務端,這是沒得談的底線。短時效金鑰的聰明之處,恰恰是把「發不發、發多久、發給誰」的決定權,全部拉回你自己的後端。

還要說清楚內嵌模式的邊界:它天生適合「薄」的 agent,邏輯不重、狀態不複雜、重活有人代管。長時任務放瀏覽器,使用者一關分頁,任務就死在半路;多智能體系統放瀏覽器,狀態同步和協調的複雜度會把你淹死;對客戶收費、成本敏感的 agent,更不該把邏輯送到使用者手上,那等於把商業邏輯開源。內嵌不是萬用鑰匙,它只在即時互動這類場景裡最划算。

**第二條路:把 agent 包成一個 API 微服務。**回到老王那個畫圖 agent。生成圖片這種活,又慢又重,跟即時語音是兩個世界。這種時候把它搬到後端,用 FastAPI 包起來,對外只露一個型別清楚的 `POST /generate` 端點:收一段文字描述,回一張 PNG 的位元組(bytes)。幾個設計細節值得停下來看:

- 為什麼用 POST 而不是 GET?兩個理由。第一,生成圖片是長時任務,請求可能跑很久;第二,使用者的描述文字可能很長,會超過 GET 對 URL 長度的限制。兩條各自成立,合起來更是非 POST 不可。
- 圖片在服務內部以 base64 編碼流轉,但對外回傳的是乾淨的 PNG bytes,呼叫端拿到的就是檔案本體。客戶端也可以選擇自己去解 base64,但那是客戶端的事,服務端把髒活內部消化掉了。

跑起來大概是這個樣子:uvicorn 把服務架在本機 8000 埠,然後用 curl 打過去:

```bash
curl -X POST http://localhost:8000/generate \
  -H "Content-Type: application/json" \
  -d '{"prompt": "a watermelon wearing sunglasses"}' \
  --output watermelon.png
```

一句話請求,一張圖落地。這個模式可以無限推廣:任何 agent、任何工具,都可以包成一個 POST 端點,回傳一個乾淨的 payload。憑證全部留在後端,限流和計費在服務端按用戶執行,前面那三個壞消息一個都不會遇到。代價是每個來回都過網路、過你的伺服器,所以對話和語音這種追求極低延遲的體驗,它不是首選。

現在把兩條路接起來。這是老王最喜歡的部分。瀏覽器裡有一個即時語音 agent(內嵌模式,拿短時效金鑰直連即時模型),它身上掛一個 `generate_image` 工具。使用者說「畫一隻西瓜」,這個工具不碰任何影像模型,它只做一件事:向後端那個 FastAPI agent 的 `POST /generate` 發一個請求。

請求發出去之後,語音 agent 立刻告訴使用者「好,畫好了叫你」,然後繼續陪你聊天。圖片在背景慢慢生成。使用者接著問「那再給它畫一頂草帽呢?」,生成照跑,聊天照聊,誰也不等誰。瀏覽器的即時 agent 一邊做工具呼叫、一邊跟使用者互動;換句話說,後端的 API agent 被前端的即時 agent 當成了一個工具來消費。這是一個可以反覆套用的樣板:即時互動留在前端,長時重活丟給背景。

真要上生產,這個 `/generate` 後面還有一整排基礎設施:請求先進**佇列(queue,如 Redis 或 SQS)**,**GPU worker 池**從佇列裡領活,畫好的圖存進**物件儲存(object storage)**,**通知系統**負責告訴使用者「圖好了」,再加一套**記憶系統**,讓 agent 有本事回答「我那張西瓜圖好了沒?」。這一課只講 agent 端的架構,這些基礎設施點到為止。

**最後一條路:不給人用,給 agent 用。**你的 agent 也可以不作為產品出現,而是包成一個 MCP 伺服器,或走 **A2A(Agent-to-Agent)**協定,讓別的 agent 把它當工具呼叫。你的畫圖 agent 變成公司裡每一個助理 agent 都能調用的一顆零件。人類永遠不直接看到它,但它的價值透過別的系統放大了十倍。

三條路擺在一起,沿延遲、安全、成本三個軸看:

| 模式 | agent 邏輯在哪 | 憑證在哪 | 延遲 | 適合 | 不適合 |
| --- | --- | --- | --- | --- | --- |
| 內嵌(Embedded) | 使用者瀏覽器 | 前端可見即公開,需後端鑄發短時效金鑰 | 最低,串流直連 | 薄的即時 agent,後端代管憑證 | 長時任務、多智能體、成本與安全敏感 |
| API 微服務(Hosted API) | 你的後端 | 後端,安全 | 每個來回過網路與伺服器 | 付費客戶、按 key 限流計費 | 極低延遲的即時對話與語音 |
| 工具消費(MCP/A2A) | 你的伺服器,以 server 形式暴露 | 服務端 | 取決於呼叫方 | 給其他 agent 當零件 | 人類直接使用的介面 |

換句話說:要低延遲的即時體驗,內嵌加短時效金鑰;要對客戶收錢、要按用戶限流,API 微服務;要讓能力到處被複用,包成 MCP/A2A。而真實系統往往是組合技:瀏覽器裡的即時語音 agent,把後端的 API agent 當工具用,後端後面再掛一排佇列和 GPU。三種模式不是三選一,可以互相組合。

最後說個老王自己的笑話。當年他第一次把長期 key 放進前端,還安慰自己:「反正沒人會看原始碼。」三天後帳單來了,一個陌生人在半夜用他的 key 生成了兩百張貓。從那天起老王明白:在瀏覽器裡,沒有「沒人會看」,只有「還沒有人看」。這一課如果你只帶走一句話,就帶這句。至於老王,他現在專門負責畫架構圖,畫得依然很醜,但至少,鑰匙再也沒離開過後端。
