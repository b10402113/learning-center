# REST vs RPC 比較

## Learning goal
理解 REST 與 RPC 兩種 API 架構風格的設計哲學差異，並能依場景選擇適合的風格

## Lesson

REST 和 RPC 是兩種不同的 API 設計哲學。

**REST（Representational State Transfer）** 是一種架構風格，核心思想是把伺服器上的資料視為資源（resource），每個資源有唯一 URL，透過標準 HTTP 方法操作：GET 讀取、POST 建立、PUT 更新、DELETE 刪除。REST 強制無狀態設計（每個請求包含所有必要資訊），支援 HTTP 快取，介面統一且易理解。劣勢是可能 over-fetching（拿太多）或 under-fetching（拿太少），且缺乏嚴格標準。

**RPC（Remote Procedure Call）** 是一種協議，讓程式像呼叫本地函數一樣遠端執行伺服器上的程式。客戶端定義明確的動作（procedure），伺服器執行後回傳結果。現代 RPC 框架如 gRPC 使用 Protocol Buffers 二進位格式，效能極高，函數定義就是 API 契約（類型安全）。劣勢是耦合度高、修改介面影響範圍大、通常無法利用 HTTP 快取。

核心差異：REST 圍繞資源操作（URL 代表 noun），RPC 圍繞動作呼叫（代表 verb）。REST 適合公開 API 和需要快取的場景；RPC 適合內部微服務通訊和效能敏感的場景。兩者互補，常常在同一個系統中搭配使用——對外用 REST，內部用 RPC。

面試時被問「該用哪個」，先問清楚是公開 API 還是內部通訊，以及是否有效能要求。
