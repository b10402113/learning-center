# Serverless vs 傳統部署

## Learning goal

比較 Serverless 架構與傳統伺服器部署的差異，理解各自的優缺點、成本模型與適用場景。

## Lesson

選擇部署架構是系統設計中最關鍵的決策之一。Serverless 和傳統伺服器代表了兩種截然不同的思維方式：一個把基礎設施完全交給雲端供應商，一個讓你完全掌控。理解它們的取捨，你才能在面試中解釋「為什麼選擇這個方案」。

**傳統伺服器架構（Traditional Server-based Architecture）** 是指應用程式部署在實體或虛擬伺服器上，開發或維運團隊需要負責伺服器的 provisioning、維護和擴展。想像你租了一間辦公室：你需要簽租約、買家具、請人維護空調、處理水電費。不管辦公室裡有沒有人在工作，這些成本和責任都在——這就是傳統伺服器架構。

傳統架構的核心特性包括：伺服器有固定的 CPU、記憶體、儲存空間（Fixed Resources）；伺服器全天候運行，不管有沒有流量（Continuous Operation）；流量增加時需要人工新增伺服器（Manual Scaling）；持續產生費用（伺服器租金、電費、維護費）（Billing Model）。典型的範例是傳統的 LAMP 架構（Linux + Apache + MySQL + PHP），伺服器全天候運行，即使凌晨三點只有幾個人在瀏覽網站。

**Serverless 架構（Serverless Architecture）** 是指雲端供應商動態管理伺服器的分配和配置。開發者只需撰寫和部署程式碼，不用擔心底層基礎設施。想像你去共享辦公空間：按小時付費，來了就有桌椅和網路，走了就停止計費。你不用管空調壞了找誰修、不用買家具、不用簽長期租約——這就是 Serverless。

Serverless 的核心特性包括：根據需求自動擴展或縮減（Dynamic Scaling）；只為實際使用的計算資源付費（Pay-as-you-go）；不用 patch、不用監控硬體、不用管理作業系統（No Server Management）；程式碼在事件觸發時才執行（Event-driven）；長時間閒置後的首次執行可能有延遲（Cold Start）。典型的範例是 AWS Lambda 函數：當用戶上傳圖片時觸發，圖片處理完成後函數自動終止，不產生任何費用。

| 維度 | 傳統伺服器 | Serverless |
| --- | --- | --- |
| 基礎設施管理 | 完全由團隊負責 | 雲端供應商負責 |
| 擴展 | 手動或自動（需設定） | 自動，幾乎無限 |
| 成本 | 持續產生（即使閒置） | 按執行次數和時間計費 |
| 延遲 | 穩定（伺服器一直運行） | 可能有冷啟動延遲 |
| 控制力 | 完全掌控環境 | 受限於雲端供應商的限制 |
| 適用場景 | 持續運行的服務、需要完全掌控 | 事件驅動、流量波動大、快速原型 |

很多人以為 Serverless 一定比較便宜，但這不一定是事實。低流量時 Serverless 通常更便宜（不執行就不付費）；高流量時傳統伺服器可能更划算（固定成本 vs 按量計費的累積）；持續運行的工作負載，傳統伺服器通常更便宜；突發流量時 Serverless 更划算（不用為峰值預留資源）。

Serverless 和傳統伺服器各有優劣。選擇的關鍵在於：你的流量模式、團隊能力、延遲要求、和預算。在面試中展示你能權衡這些因素，比單純選一個「最新潮」的方案更重要。
