# 有狀態 vs 無狀態架構

## Learning goal

理解有狀態與無狀態架構的核心差異，以及各自適用的場景與設計取捨。

## Lesson

提到系統架構時，一個最根本的問題是：伺服器要不要記住使用者的狀態？這聽起來像個技術細節，但它會直接影響你的系統怎麼擴展、怎麼容錯、怎麼部署。選錯了，系統可能在負載增加時崩潰；選對了，系統能輕鬆應對流量高峰。

**有狀態架構（Stateful Architecture）** 意味著伺服器保留了客戶端的會話資訊。每次請求的回應可能取決於之前的互動紀錄。想像你走進一家高級餐廳，服務生記得你上次點了什麼、你喜歡靠窗的位置、你不吃海鮮。下次你再來，他直接幫你安排好一切——這就是有狀態的服務。

有狀態架構的核心特性包括：伺服器記住過去的會話資料（Session Memory）、請求的回應可能取決於之前的互動（Dependency on Context）、使用者必須被導向到同一台伺服器實例（Instance Affinity）。典型的範例是線上銀行系統：當你登入後，系統記住你的身份和會話。你在轉帳頁面輸入金額後，下一步確認轉帳時，系統需要知道「剛才那個人要轉多少錢」——這就是狀態。

相對地，**無狀態架構（Stateless Architecture）** 是指每個請求都是獨立的，包含完成該請求所需的所有資訊。伺服器不會保留任何會話狀態。想像你去一家快餐店：每次排隊時，你都要重新說明你要什麼。店員不記得你上次點了什麼，但每次都能獨立完成你的訂單——這就是無狀態的服務。

無狀態架構的核心特性包括：伺服器不儲存任何客戶端的會話資料（No Session Memory）、每個請求都攜帶完成它所需的所有資訊（Self-contained Requests）、任何請求可以被導向到任何伺服器實例（Any-instance Routing）。典型的範例是 REST API：每個 HTTP 請求都帶有完整的資訊（包括認證 token），伺服器處理完請求後不保留任何狀態。這也是為什麼 JWT（JSON Web Token）如此流行——它讓無狀態架構成為可能。

| 維度 | 有狀態 | 無狀態 |
| --- | --- | --- |
| 擴展性 | 困難——需要會話複製或黏性路由 | 簡單——直接新增實例 |
| 容錯 | 複雜——狀態可能遺失 | 簡單——任何實例都能處理 |
| 記憶體使用 | 高——需要儲存會話資料 | 低——伺服器無需記住狀態 |
| 開發複雜度 | 較高——需要狀態管理邏輯 | 較低——每個請求獨立處理 |
| 適用場景 | 需要個人化、會話追蹤的應用 | API、微服務、高併發系統 |

大多數現代系統設計會**盡量讓服務無狀態**，把狀態移到專門的儲存層（如 Redis、資料庫）。這樣做的好處是：服務實例可以任意擴展和替換；故障轉移變得簡單——新實例不需要知道舊實例的狀態；負載均衡變得簡單——任何實例都能處理任何請求。但有些場景**必須有狀態**：WebSocket 連線需要維持連線狀態、遊戲伺服器需要知道玩家的位置和狀態、會話式應用需要知道「誰在跟誰說話」。

有狀態和無狀態不是好壞之分，而是取捨。現代系統設計的趨勢是**服務無狀態、狀態集中管理**。理解這個取捨，你就能在面試中做出明智的設計決策。
