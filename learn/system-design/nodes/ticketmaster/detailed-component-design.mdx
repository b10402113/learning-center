# 核心元件詳細設計

## Learning goal
設計 Ticketmaster 的核心元件：ActiveReservationsService 與 WaitingUsersService，說明訂票流程與等待隊列實作。

## Lesson

理解複雜系統的最好方法是先假設它跑在一台伺服器上。等單機邏輯想清楚了，再考慮分散式場景的挑戰。完整訂票流程是：搜尋電影 → 選擇電影查看場次 → 選擇場次查看座位 → 選座暫時鎖定（ReserveSeats，15 分鐘有效期）→ 確認付款完成訂單。暫時鎖定和確認付款之間的時間窗口需要專門的服務來管理「進行中」的狀態。

**ActiveReservationsService** 管理所有正在進行中的預訂。核心數據結構是 LinkedHashMap（鏈結哈希映射），它支持兩個關鍵操作：O(1) 跳轉（根據 reservationID 直接找到預訂，哈希表特性）和按時間順序遍歷（頭部永遠是最早建立的預訂，方便清理過期預訂，鏈表特性）。用戶付款完成後，根據 reservationID 移除條目並更新資料庫座位狀態。

**WaitingUsersService** 處理座位售罄時的等待隊列。同樣使用 LinkedHashMap：先到先得（鏈表頭部是最早的等待者），支援取消（根據 userID 直接刪除，O(1)）。當有人取消訂單或付款超時釋放座位時，從隊列頭部取出最早的等待者通知訂購。

ActiveReservationsService 和 WaitingUsersService 的數據放在 Redis 快取中，因為它們是熱數據（讀寫頻繁）、有過期時間（Redis TTL 天然支持）、需要原子操作（MULTI/EXEC 事務）。資料庫是持久化備份——快取掛了可以從資料庫重建。

面試中詳細設計是最能展示深度的環節，重點講清楚數據結構的選擇理由、暫時鎖定的時間窗口機制、等待隊列的先到先得邏輯、以及快取與資料庫的配合關係。
