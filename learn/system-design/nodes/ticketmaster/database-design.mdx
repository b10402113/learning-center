# 資料庫設計

## Learning goal
設計 Ticketmaster 系統的關聯式資料庫結構，包含城市、影院、電影、場次、座位與訂單實體。

## Lesson

在設計資料庫之前，先想清楚這個系統裡有哪些「東西」（實體），以及它們之間有什麼關係。訂票系統的數據結構有很清晰的層級關係：城市包含影院，影院包含大廳，大廳在不同時間有不同場次，每個場次有多個座位。同時，一部電影可以在多家影院的多個場次中放映。

核心實體包括六個：**City（城市）**有 ID 和名稱；**Cinema（影院）**有 ID、名稱和所屬城市外鍵；**Movie（電影）**有 ID、片名和片長；**Show（場次）**有 ID、所屬影院外鍵、播放電影外鍵和放映時間；**Booking（訂單）**有 ID、用戶外鍵、場次外鍵、訂購座位數、時間戳和狀態（Reserved / Booked / Cancelled）；**Seat（座位）**有 ID、場次外鍵、座位號和狀態（Available / Reserved / Booked）。

關係如下：City 1:N Cinema，Cinema 1:N Show，Movie 1:N Show，Show 1:N Seat，Show 1:N Booking，Booking N:1 User。

訂票系統有強一致性需求（不能超賣、不能重複訂座），關聯式資料庫的 ACID 事務特性恰好能保證這一點。NoSQL 在這裡不適合，因為我們需要跨表的原子性操作。

資料庫設計是面試中的加分項。畫出 ER 團（實體關係圖），清楚標註主鍵和外鍵，能展示你對數據建模的理解。記住：從實體開始，找關係，定約束。
