# 高層架構設計

## Learning goal
設計 Ticketmaster 的高層系統架構，定義各元件的職責與互動關係。

## Lesson

當用戶打開訂票網站，請求從外到內依次經過 Load Balancer（負載均衡器）、Web Server、Application Server，最後到達 Database + Cache。這是一個經典的三層架構，每一層都有明確的職責。

Load Balancer 在最外面，把用戶請求分散到多個 Web Server，常用 Round Robin 或 Least Connections 演算法。Web Server 負責管理 session（登入狀態）和提供靜態資源，不做業務邏輯。

Application Server 是系統的大腦，所有業務邏輯都在這裡：搜尋電影、查詢場次、檢查座位可用性、處理訂單。它設計為無狀態的——不存任何數據，所有狀態存在資料庫或快取中，這樣就能輕鬆水平擴展。Database 存所有持久化數據，Cache（通常是 Redis）存熱數據以減少資料庫壓力。

API 設計上，SearchMovies 按城市、關鍵字、時間搜尋電影；SearchShows 搜尋場次；ReserveSeats 是暫時鎖定操作，座位被鎖定 15 分鐘，超時自動釋放；MakeBooking 確認訂單並付款；CancelReservation 取消預訂。

快取策略上，電影列表（按城市）和場次資訊變化不頻繁，適合快取。座位狀態讀取最頻繁但變化也最頻繁，需要精細的失效策略，是最棘手的部分。

畫高層架構圖時，從外到內：Load Balancer → Web Server → Application Server → Database + Cache，每層標註職責和技術選型。
