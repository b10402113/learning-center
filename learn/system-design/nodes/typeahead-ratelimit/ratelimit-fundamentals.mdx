# API 限流基礎概念與需求

## Learning goal

理解 API 限流的作用、為什麼需要限流，以及系統設計的功能與非功能需求，認識不同類型的限流策略。

## Lesson

想像你經營一個電商網站，平時每秒處理 500 個請求。某天辦了限時搶購，流量瞬間湧入每秒 50,000 個請求。伺服器瞬間過載，所有用戶都看到 503。根源是系統沒有機制控制進入的流量——限流就是這道閘門。

### Rate Limiter 是什麼

從高層來看，Rate Limiter 控制一個實體（用戶、設備、IP 或 API Key）在時間窗口內能發送多少請求。超過上限的請求被拒絕，返回 `429 Too Many Requests`。兩個核心概念：**Rate**（長期速率，單位時間內允許的請求數）和 **Burst**（短期突發容量，系統短時間內能承受的超出量）。好的限流策略需要在兩者之間取得平衡。

### 為什麼需要限流

限流有四個關鍵作用。**保護後端資源**：確保後端永遠在安全負載範圍內運作。**防止惡意攻擊**：DDoS、暴力破解、假帳號注册都需要限流作為第一道防線。**控制成本**：雲端環境中每個請求都代表運算資源，限流等於給預算裝保險絲。**確保公平性**：多租戶系統中每個租戶都拿到公平配額，GitHub API 和 Twitter API 的 rate limit 就是例子。

### 系統需求

功能需求包括：限制每個實體在時間窗口內的請求數、限流應跨叢集生效（多台 API Server 共享限流狀態）、超限時返回清晰錯誤。非功能需求包括：低延遲（不增加請求處理時間）、高記憶體效率、容錯（限流器掛了不應阻斷正常請求）。跨叢集生效特別重要——限流狀態通常存在共享儲存（如 Redis）中。

### 節流類型

根據寬鬆程度，限流有三種節流類型。**Hard Throttling**：請求數絕對不能超過上限，適合嚴格的 API 配額。**Soft Throttling**：允許超過上限一定百分比（如 10%），適合需要彈性的場景。**Elastic Throttling**：在高需求時放寬限制，低需求時恢復，適合流量波動大的場景。

### 部署位置

限流可以部署在不同層級：用戶端（減少網路請求但可繞過）、API Gateway（集中管理最早擋住超量流量）、負載均衡器（分散限流壓力但設定複雜）、個別服務（粒度最細但管理成本高）。最常見做法是 API Gateway 粗粒度 + 個別服務細粒度的兩層防線。
