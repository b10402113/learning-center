# Typeahead 基礎設計與核心演算法

## Learning goal

理解 Typeahead 搜尋建議的基本概念、功能需求，以及核心的 Trie 資料結構設計與永久儲存方式。

## Lesson

你打開 Google 搜尋框，輸入「系」，瞬間彈出「系統設計面試」「系統分析」等建議。這就是 Typeahead Suggestion——搜尋自動完成。它的核心價值不是「加速搜尋」，而是**引導用戶表達意圖**。很多用戶其實不知道該搜什麼關鍵詞，好的建議能幫他們更快找到想要的東西。

### 需求分析

Typeahead 的需求分為功能和非功能兩塊。**功能需求**：用戶每輸入一個字元，系統返回 top 10 個以該字元開頭的搜尋建議。**非功能需求**：建議在 200ms 以內顯示。200ms 是人眼感知延遲的閾值（約 300ms）之內——超過這個時間用戶就會覺得「慢」，所以他打下一個字的時候你還沒返回結果，體驗就崩了。

問題可以抽象為：我們有一堆字串，要支援「前綴查詢」——給定前綴，找出所有匹配的字串。如果用 Array + 線性掃描，每個前綴查詢都要遍歷整個詞典，時間複雜度 O(n × L)，n 是詞數，L 是字串長度。詞典有 100 萬個詞？太慢了。

### Trie：專門解決前綴查詢的資料結構

**Trie（字典樹）**的核心思想：把字串的每個字元存為一個節點，共同的前綴共享路徑。假設詞典有 `cap`、`cat`、`captain`、`capital` 四個詞，Trie 的結構中從 root 沿 `c → a → p` 走下去，遇到標記為「詞尾」的節點就是一個完整詞。搜 `cap` 的前綴時，系統從 root 出發沿 `c → a → p` 走，收集所有帶詞尾標記的子樹節點，就得到 `cap`、`captain`、`capital`。

Trie 前綴查詢的時間複雜度是 O(L)，只跟前綴長度有關，跟詞典大小無關。代價是**空間換時間**：每個字元都是一個節點，空間開銷比純字串陣列大得多。在 Typeahead 這種 read-heavy 的場景下，查詢速度快了一個數量級，這個取捨完全值得。

### Trie 的持久化儲存

記憶體中的 Trie 很快，但伺服器重啟資料就沒了。做法是**定期對 Trie 做快照（snapshot）**，存到磁碟中：從 root 開始一層一層往下讀，每個節點存它包含的字元、子節點數量、以及是否為詞尾。伺服器掛了就從最新快照重建 Trie，幾秒鐘就能恢復服務。快照的頻率取決於資料更新頻率——Typeahead 的詞典更新通常來自離線分析（定期從搜尋日誌統計熱門詞），所以一天做一次快照就夠了。

Trie 的取捨很明確：用空間換時間，前綴查詢 O(L)。下一步要面對的問題是：當詞典有數十億條、每秒有數萬次查詢時，怎麼把這個 Trie 擴展到多台機器上。
