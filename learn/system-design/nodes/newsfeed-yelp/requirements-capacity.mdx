# 需求分析與容量估算
## Learning goal
瞭解 Newsfeed、Yelp 鄰近搜尋與 Uber 即時位置這三個系統的功能需求、非功能需求，以及如何進行容量估算。
## Lesson

三個系統設計題——Facebook Newsfeed、Yelp 鄰近搜尋與 Uber 叫車——看似都是「搜尋」問題，但从需求階段就開始分化。Newsfeed 搜尋的是追蹤者的最新內容，Yelp 搜尋的是附近的靜態地點，Uber 搜尋的是附近的動態駕駛。這三種搜尋的對象、更新頻率和讀寫比完全不同，决定了後續架構的走向。

功能性需求方面，Newsfeed 需要根據使用者追蹤的使用者、粉專和社團產生個人化的動態時間軸，支援文字、圖片和影片等多媒體內容。Yelp 需要根據使用者的經緯度搜尋指定半徑內的地點，支援 CRUD 操作、評論系統和類別篩選。Uber 需要讓乘客叫車、駕駛定期報告位置、系統即時匹配附近可用駕駛並追蹤行程。

非功能性需求的差異更為關鍵。Newsfeed 是讀取密集型系統，讀取量是寫入量的 17 倍，需要低延遲的快取層和推送/拉取混合架構。Yelp 是極度讀取密集型系統，讀寫比達 10,000:1，地點資料幾乎不變，適合建立靜態地理索引。Uber 則是寫密集型系統，讀寫比僅 1:33，因為每 50 萬名活躍駕駛每 3 秒報告一次位置，產生約 167K 次/秒的寫入。

容量估算的結果直接驅動架構決策：Newsfeed 的 17,500 讀取 QPS 需要快取和複製來分擔讀取壓力；Yelp 的 100K 搜尋 QPS 需要高效的地理空間索引來縮小搜尋範圍；Uber 的 167K 寫入 QPS 則要求索引能支援頻繁的增量更新，靜態的 QuadTree 方案在此場景下不夠用。
