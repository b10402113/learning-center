# 快取、複製與容錯設計
## Learning goal
整合三個系統的優化設計，包括快取策略、資料複製與容錯，確保系統能在高流量下保持可用性和性能。
## Lesson

快取、複製和容錯是三個系統共通的優化策略，但在不同場景下的應用方式各不相同。Newsfeed 使用預計算的 feed 快取（Memcache），將每個使用者的 feed 結果存儲在記憶體中，查詢時直接從快取讀取以避免每次查詢資料庫，淘汰策略使用 TTL（1-5 分鐘）。Yelp 的快取用於緩解熱門地點的查詢壓力，使用 Memcache 的 LRU 淘汰策略：當空間不足時優先淘汰最近最少使用的地點，應用伺服器在查詢資料庫前先檢查快取。Uber 的快取主要緩存熱門區域的駕駛位置，但由於位置每 3 秒更新，TTL 必須很短（幾秒級）否則會返回過時位置。

資料複製方面，三個系統都使用主從複製（Primary-Secondary）：主伺服器處理所有寫入，從伺服器處理讀取並從主伺服器同步資料。從伺服器可能有輕微延遲，但搜尋和讀取場景通常可以接受這種最終一致性。Newsfeed 的 feed 快取伺服器使用多副本分散讀取流量；Yelp 的 QuadTree 伺服器主從複製因資料很少變動而幾乎同步；Uber 的駕駛位置伺服器和通知伺服器都需要複製，同時同步到 SSD 作為持久化存儲以確保主從都宕機時能從磁碟恢復。

容錯設計遵循健康檢查（Heartbeat）、自動故障轉移（Failover）和資料恢復三個機制。Newsfeed 的混合架構提供了額外的容錯能力——推播失敗時可以退回到拉播模式從資料庫即時查詢。Uber 的容錯要求最高，因為位置資料的即時性直接影響叫車服務，需要處理駕駛網路斷線後的位置同步、乘客斷線時的計費持續、以及訊息遺失時使用訊息佇列確保至少一次投遞。

三個系統的可靠性設計遵循同一原則：讀取密集型系統（Newsfeed、Yelp）優化快取和複製來提高吞吐量，寫入密集型系統（Uber）優化持久化和故障恢復來確保資料不遺失。
