## Lesson

把前三課的概念組裝在一起：正向代理代表用戶端、反向代理代表伺服器、冗餘消除單點故障。反向代理本身也可能成為單點故障——如果只有一台，它掛了所有用戶都連不上來。解法是冗餘代理設計。

最常見的兩種冗餘模式是 Active-Passive 和 Active-Active。Active-Passive 用兩台代理，一台主動處理流量，另一台待命。待命的代理透過心跳檢測主動代理的健康，一旦偵測到故障就接管虛擬 IP（VIP），用戶端無感知。優點是架構簡單，缺點是被動代理閒置、資源浪費。

Active-Active 讓多台代理同時處理流量。用戶端的請求先到一層負載均衡器（DNS 輪詢、專用 LB、或雲端 LB），再分發到各台代理。優點是資源利用率高、天然支援水平擴展；缺點是架構更複雜，如果代理有快取或 session 等狀態，切換時可能丟失。

心跳和健康檢查是故障偵測的基礎。每台代理定期向其他代理發送心跳包，超時未收到就判定對方故障。Active-Passive 模式中觸發 VIP 切換；Active-Active 模式中從負載均衡器的後端列表中移除故障代理。心跳頻率的設定是一個取捨：太頻繁浪費資源，太稀疏偵測太慢。

常見的實作工具包括 Keepalived + Nginx（Active-Passive，VIP 漂移秒級切換）、HAProxy（Active-Active，高性能 L4/L7 負載均衡）、以及雲端 LB（AWS ALB/NLB、GCP Cloud Load Balancing，免運維）。選型依據場景：流量不大用 Active-Passive、高流量用 Active-Active、有狀態代理需要額外處理狀態遷移、雲端部署直接用雲端 LB。

在面試中，能指出反向代理層的單點故障並描述故障轉移機制，是展示系統設計深度的關鍵。很多人會設計後端伺服器的冗餘，卻忘記代理層也是單點故障。
