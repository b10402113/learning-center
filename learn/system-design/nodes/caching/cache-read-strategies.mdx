# 快取讀取策略

## Learning goal
掌握常見的快取讀取策略（read-through vs read-aside），理解兩者的差異與適用場景。

## Lesson

快取建好了，失效策略也選好了，但還有一個關鍵問題：當應用程式需要數據時，「誰負責去數據源取數據？」這個問題的答案決定了快取的讀取策略。常見的有兩種：read-through 和 read-aside（也叫 cache-aside 或 lazy-loading）。

**Read-through Cache（穿透式快取）** 的核心邏輯是：應用程式只跟快取打交道，快取層自己負責在未命中時去數據源取數據。

流程是這樣的：
1. 應用程式向快取請求數據
2. 快取命中 → 直接返回
3. 快取未命中 → 快取層自己去數據源取數據 → 存入快取 → 返回給應用程式

應用程式完全不需要知道數據源的存在，快取層封裝了所有取數據的邏輯。優點是應用程式代碼簡單、乾淨，不需要處理快取未命中的邏輯。缺點是第一次訪問某筆數據時延遲較高——因為快取層需要額外的處理時間來取數據並填充。此外，快取層的邏輯可能比較複雜，需要處理各種邊界情況。

**Read-aside Cache（旁觀式快取）** 的核心邏輯是：應用程式自己負責在快取未命中時去數據源取數據，然後放入快取。

流程是這樣的：
1. 應用程式先查快取
2. 快取命中 → 直接使用
3. 快取未命中 → 應用程式自己去數據源取數據 → 存入快取 → 使用

與 read-through 的差別在於「誰去取數據」：read-through 是快取去取，read-aside 是應用程式去取。read-aside 的優點是應用程式對快取邏輯有完全的掌控——可以決定什麼時候填充快取、用什麼格式存儲、是否跳過某些數據。缺點是每次快取未命中時，應用程式都要多做一次「取數據 + 寫入快取」的操作，代碼會比較重複。

兩種策略的對比：

| 面向 | Read-through | Read-aside |
| --- | --- | --- |
| 誰取數據 | 快取層 | 應用程式 |
| 應用程式複雜度 | 低（只跟快取互動） | 高（要處理取數據邏輯） |
| 控制力 | 低（快取層決定一切） | 高（應用程式完全掌控） |
| 首次訪問延遲 | 較高（快取層額外處理） | 取決於應用程式實現 |
| 適用場景 | 標準化、重複性的數據訪問 | 需要客製化快取邏輯的場景 |

在實際系統中，read-aside 是更常見的選擇，因為它提供了更大的靈活性。Redis + 應用程式的組合就是典型的 read-aside 模式：應用程式先查 Redis，未命中再去資料庫查詢，然後寫回 Redis。

面試中，你能清楚比較這兩種策略的差異，並解釋為什麼在特定場景下選擇某一種，會讓面試官看到你不只知道「要快取」，還知道「怎麼快取」。
