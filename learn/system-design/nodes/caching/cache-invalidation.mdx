# 快取失效機制

## Learning goal
理解快取失效的問題為什麼困難，並掌握常見的快取失效方法。

## Lesson

快取大幅提升了效能，但引入了一個新的問題：當底層數據改變了，快取中的舊數據怎麼辦？如果不及時處理，用戶就會看到過時的「髒數據」。業界常說「計算機科學有兩大難題：快取失效和命名」（Cache invalidation and naming things），可見這個問題有多棘手。

難點在於時機的把握：太早失效會增加不必要的快取未命中，浪費快取的效能優勢；太晚失效會讓用戶看到錯誤的數據。在分散式環境中，多個節點同時讀寫時，一致性問題更加複雜。

常見的快取失效方法有三種：

**清除（Purge）** 是最直接的方法：數據更新時，立刻把對應的舊快取刪除。下次有人請求這筆數據時，會發生快取未命中，從數據源取回最新版本。優點是一致性好——數據更新後，快取中不會有舊版本。缺點是需要額外執行一次失效操作，如果這個操作失敗了（網路斷了、快取服務暫時不可用），髒數據就會長期留存。

**過期（TTL，Time-To-Live）** 是最簡單的方法：每個快取數據都設定一個存活時間，到期自動失效。優點是實作簡單——不需要在數據更新時做任何額外操作，快取自己會「過期」。缺點是在過期時間到達之前，用戶看到的依舊是舊數據，一致性比較差。TTL 設太短會增加未命中率，設太長會讓髒數據留存更久。

**寫入更新（Write-update）** 是最積極的方法：數據更新時，同時更新快取中的對應數據。優點是快取永遠是新的，不會增加後續的未命中。缺點是在併發場景下容易出現競爭條件——兩個同時的更新操作可能互相覆蓋，而且如果更新失敗，快取和數據源會不一致。

實際生產環境中，絕大部分場景會採用「清除 + TTL」的組合策略：

1. 數據更新時正常執行清除操作
2. 同時給每個快取設定過期時間作為安全網

這樣做的邏輯是：正常情況下清除操作會讓快取及時更新；萬一清除失敗，最迟到 TTL 到期也會自動更新。這平衡了一致性、系統複雜度和可用性。

對一致性要求不高的場景（例如社群媒體的按讚數、文章瀏覽量），可以單純使用 TTL，開發最簡單。對一致性要求高的場景（例如金融交易、庫存管理），可能需要更複雜的策略，例如 write-through 或 subscribe-based invalidation。
