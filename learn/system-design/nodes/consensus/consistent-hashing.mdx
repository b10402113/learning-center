# 一致性雜湊

## Learning goal
掌握一致性雜湊的原理、虛擬節點優勢，以及如何解決動態節點增減時的資料移動問題

## Lesson

### 問題：資料該放哪台機器？

假設你有一個快取系統，100 萬個使用者的資料要分散在 3 台伺服器上。最直覺的做法是用雜湊取餘數：對使用者 ID 做 hash，再除以 3 取餘數。0 號放第一台，1 號放第二台，2 號放第三台。

看起來很完美——直到有一天，你要加一台伺服器。從 3 台變 4 台，除數從 3 變 4。結果是：**幾乎每一筆資料的放置位置都變了**。100 萬筆資料中，大約 75% 要重新搬遷。如果用快取系統，這意味著大量快取失效，所有請求瞬間打到後端資料庫——這就是「雷群效應（thundering herd）」。

### 一致性雜湊的解法

一致性雜湊（Consistent Hashing）的思路是：把雜湊值空間想像成一個**環**（從 0 到 2³²-1 的環狀結構）。

首先，對每台伺服器做雜湊，把它們映射到環上的某個位置。然後，對每筆資料做雜湊，沿著環**順時針**找到第一台伺服器，這筆資料就歸那台伺服器管。

**為什麼叫「一致性」？** 當你新增或移除一台伺服器時，只有**環上相鄰**的那段資料需要搬遷，其他資料的位置完全不受影響。從「幾乎全部搬」變成「只搬一小部分」。

| 方法 | 新增 1 台伺服器（從 3 到 4） | 搬遷比例 |
| --- | --- | --- |
| 雜湊取餘數 | 幾乎所有資料都移動 | ~75% |
| 一致性雜湊 | 只移動環上相鄰段的資料 | ~25%（1/N） |

### 虛擬節點（Virtual Nodes）

基本的一致性雜湊有一個問題：如果伺服器數量少，資料分佈可能很不均勻。比如 3 台伺服器，某台可能佔了環上 50% 的範圍，另一台只有 10%。

解決方案是**虛擬節點（Vnodes）**：每台實體伺服器在環上放多個位置，而不是只有一個。比如每台放 100 個虛擬節點。這樣資料會更均勻地分散在所有伺服器上。虛擬節點的優勢包括：負載更均勻（避免某台過載）、快速再平衡（新增伺服器時從多個現有節點各拿一些虛擬節點）、以及容錯更平滑（某台故障時，它的虛擬節點分散在環上各處，負載由多台伺服器分擔）。

### 資料複製

為了高可用，一致性雜湊通常設定一個**複製因子 N**（replication factor），每筆資料沿著環順時針存放到 N 台不同的伺服器上。這確保即使某台機器故障，資料仍有其他副本。

### 面試中的應用

在系統設計面試中，任何需要「高效能地動態分佈資料」的場景都適合用一致性雜湊：分散式快取（如 Memcached、Redis Cluster）、分散式資料庫的分片（如 DynamoDB、Cassandra）、CDN 的節點選擇、負載均衡器的分流。
