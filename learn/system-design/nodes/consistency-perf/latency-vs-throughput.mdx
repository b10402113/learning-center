# 延遲 vs 吞吐量

## Learning goal

理解延遲與吞吐量的定義、差異，以及兩者之間的取捨關係與優化策略。

## Lesson

在系統設計中，「快」這個字其實有兩種完全不同的含義。「使用者按下按鈕後很快就看到回應」說的是延遲低，「系統每秒能處理一百萬筆訂單」說的是吞吐量高。這兩件事看起來都是「快」，但它們的衡量方式、優化手段和適用場景完全不同。搞混這兩個概念是面試中最常見的錯誤之一。

<strong>延遲（Latency）</strong>衡量的是單個請求從發出到收到回應需要多少時間，單位是毫秒或秒。它關心的是「一個請求要等多久」。在分散式系統中，延遲不只是網路傳輸的時間，還包括 DNS 解析、TCP 握手、SSL 交握、伺服器處理、資料庫查詢、序列化等多個環節。延遲越高，使用者體驗越差——頁面載入慢、按鈕回應遲鈍。搜尋引擎、遊戲、即時通訊等場景對延遲極度敏感。

<strong>吞吐量（Throughput）</strong>衡量的是單位時間內系統能處理多少工作，單位是每秒請求數（RPS）或每秒位元組數（Mbps）。它關心的是「整體處理能力」。吞吐量不足會導致請求排隊、系統過載。批次處理、資料備份、圖片轉碼等場景最需要高吞吐量。用高速公路類比：延遲是限速（從 A 城到 B 城要多久），吞吐量是車道數量（每小時能通過多少輛車）。

兩者之間存在取捨關係。批次處理打包多個請求一起處理能提升吞吐量，但每個請求的等待時間增加了（延遲上升）。並行處理把一個大任務拆成多個小任務同時處理能降低延遲，但整體資源使用效率可能下降。不過快取是少數能同時改善兩者的手段——把熱資料放在記憶體中，讀取延遲降低，同時減輕後端壓力讓吞吐量也提升。

提升延遲的主要手段包括：CDN 把靜態資源放到離使用者最近的節點、快取避免重複查詢、非同步處理讓主請求快速返回、優化資料庫查詢減少處理時間。提升吞吐量的主要手段包括：水平擴展增加伺服器、平行處理充分利用多核心、快取減少重複計算、訊息佇列平滑突發流量。

面試中被問到「如何提升系統效能」時，一個好的回答應該同時涵蓋延遲和吞吐量兩個維度，並說明你為什麼選擇優化哪一個。例如：「這個系統的主要瓶頸是延遲，我會先用 CDN 和快取降低延遲。與此同時，我會監控吞吐量，確保在流量高峰期不會因為優化延遲而犧牲整體處理能力。」
