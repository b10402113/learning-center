# ACID vs BASE

## Learning goal

理解 ACID 與 BASE 兩種資料庫設計哲學的核心屬性、差異，以及如何根據場景選擇。

## Lesson

當你用銀行 App 轉帳時，你期望錢從 A 帳戶扣掉後，B 帳戶一定會收到——不會出現「錢扣了但對方沒收到」的情況。這就是 <strong>ACID</strong> 保證的事情。但當你在社群媒體上發了一則貼文，你不會期望全球所有人在同一毫秒看到——你接受「幾秒後大家都會看到」。這就是 <strong>BASE</strong> 的思路。ACID 和 BASE 代表了資料庫設計中兩種截然不同的哲學：ACID 優先保證正確性，BASE 優先保證可用性。

<strong>ACID</strong> 是四個屬性的縮寫，它們共同保證資料庫交易的可靠性。交易就是「一組操作」——比如轉帳涉及「扣款」和「入帳」，這兩個操作必須一起成功或一起失敗。原子性（Atomicity）保證交易要麼全部成功，要麼全部失敗，不能只做一半。一致性（Consistency）保證交易完成後，資料庫從一個合法狀態轉移到另一個合法狀態，所有約束條件都必須滿足。隔離性（Isolation）保證多個交易同時進行時互不干擾，一個交易的中間狀態不會被其他交易看到。持久性（Durability）保證交易一旦提交就永久保存，即使系統崩潰也不丟失。支援 ACID 的通常是關聯式資料庫（MySQL、PostgreSQL），廣泛用於銀行、電商交易、訂單管理。

<strong>BASE</strong> 是另一種設計哲學，主要用於 NoSQL 和分散式資料庫，跟 ACID 幾乎是反過來的。基本可用（Basically Available）保證系統大部分時間可用，故障時某些功能受限但核心功能運作。軟狀態（Soft state）允許系統狀態隨時間變化，即使沒有新寫入，「過時資料」是被允許的。最終一致（Eventually consistent）保證在一段時間後，所有節點的資料會收斂到一致狀態。支援 BASE 的通常是 NoSQL（DynamoDB、Cassandra、MongoDB），廣泛用於社群媒體、即時通訊、IoT 資料收集等高流量場景。

從 CAP 定理的角度看，ACID 偏向 CP（一致性 + 分區容錯），BASE 偏向 AP（可用性 + 分區容錯）。選擇的依據是你的業務能不能容忍暫時的不一致：金融系統、電商訂單、醫療紀錄等「不能出錯」的場景選 ACID；社群媒體、即時通訊、IoT 資料收集等高流量場景選 BASE。一個成熟的系統通常會同時使用兩種資料庫——用 SQL 處理核心交易，用 NoSQL 處理高流量、低一致性要求的場景，這就是所謂的多語言持久化（polyglot persistence）。
