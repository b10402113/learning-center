# 強一致性 vs 最終一致性

## Learning goal

理解強一致性與最終一致性的定義、保證、差異，以及各自適用的場景。

## Lesson

在分散式系統中，一份資料通常會存在多個地方（多個節點、多個機房），當有一個節點更新了這份資料，其他節點什麼時候可以看到這個更新？這就是一致性議題關心的問題。簡單來說，一致性模型就是在規範「讀取操作可以得到什麼樣的寫入結果」，不同的一致性提供不同的保證。

強一致性保證，只要寫入成功之後，任何後續的讀取都一定會得到剛才寫入的最新值，不會讀到舊的資料。這種模型符合人們的直覺，開發者不用處理髒讀，可以依賴讀取到的資料做任何業務判斷，但缺點是延遲比較高，可用性比較差，因為寫入需要等待多數節點同步完成。最終一致性則是保證，在一段時間之後，所有副本最終都會同步到最新值，但讀取可能不會馬上得到最新值。它的優點是寫入快、延遲低、可用性高，但缺點是開發者需要處理暫時不一致的狀況。

選擇哪種一致性模型，取決於你的業務場景需要什麼樣的保證：金融交易、餘額查詢、電商庫存這類業務需要強一致性，因為讀不到最新值會導致業務錯誤；而社群媒體貼文、產品評論、使用者大頭貼這類業務，可以接受最終一致性，因為延遲幾秒鐘不影響使用者體驗，但可以換來更好的效能和擴展性。
