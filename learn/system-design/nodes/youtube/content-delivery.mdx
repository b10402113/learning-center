# 負載均衡與內容分發

## Learning goal
設計適合影片串流的負載均衡策略、快取機制與CDN內容分發架構，提升全球使用者的觀看體驗。

## Lesson

前面五課我們已經設計了需求、估算了容量、畫了架構、建了資料模型、建了處理管線。但系統還差最後一塊拼圖：<strong>如何把影片高效地送到全球數億使用者面前</strong>。YouTube 的讀取流量是 TB 級的——每秒 1.38 TB 的資料要送到使用者的裝置上，這必須依賴<strong>負載均衡</strong>、<strong>快取</strong>和<strong>CDN</strong>三層機制。

<strong>負載均衡</strong>出現在兩個層面。API 層的負載均衡把搜尋、評論等請求分散到多台 API 伺服器，可以使用一致性雜﨑根據影片 ID 導向特定快取節點，提高命中率。影片串流的負載均衡把播放請求分散到多個 CDN 節點或快取伺服器。一致性雜﨑的問題是：如果某部影片突然爆紅，對應的邏輯副本會承受巨大壓力，解決方案是<strong>複製熱門影片</strong>到多個物理節點分散壓力。

<strong>快取策略</strong>是 YouTube 讀取效能的核心。<strong>元資料快取</strong>——把熱門影片的標題、觀看次數等放到 Redis 或 Memcached，資料量小但讀取頻率極高；<strong>影片快取</strong>——只快取最熱門的 20% 影片（它們貢獻了 80% 的流量，帕累託法則）；<strong>縮圖快取</strong>——每次搜尋結果頁面都要載入，必須快取到 CDN。快取的關鍵挑戰是<strong>快取失效</strong>——當資料更新時，快取中的舊資料需要被清除，常見策略是 TTL（存活時間）。

<strong>CDN</strong> 是 YouTube 全球內容分發的核心。CDN 由全球數千個節點組成，工作原理：<strong>DNS 導向</strong>根據使用者地理位置把他導向最近的邊緣節點；<strong>邊緣節點服務</strong>如果命中就直接回傳，未命中就向上游請求然後快取；<strong>內容推送</strong>——YouTube 主動把熱門影片推送到邊緣節點（預推送），確保隨時可用。CDN 帶來低延遲、減少源頭壓力、高可用三大好處。

一個完整的讀取流程：使用者點擊播放 → DNS 導向最近的 CDN 節點 → CDN 節點檢查快取 → 命中直接回傳影片串流，未命中向上游請求 → 元資料從 Redis 快取取得 → 使用者開始播放。整個流程的延遲目標是 200 毫秒以內開始播放。

你用過 Redis 做快取，YouTube 的快取策略本質上就是你熟悉的 Redis 快取的放大版。差別在於 YouTube 的快取是多層的（記憶體 → SSD → CDN 邊緣 → 源頭），而且需要處理全球分發的問題。一致性雜﨑在前面的課中學過，這裡直接用上了。
