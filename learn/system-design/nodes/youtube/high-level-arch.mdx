# 高層架構設計

## Learning goal
設計系統整體高層架構，定義核心元件與它們之間的交互關係。

## Lesson

有了需求和容量估算，現在可以開始畫架構圖。高層架構的目標是把系統拆成幾個<strong>核心元件</strong>，並說明它們之間如何互動。YouTube 的高層架構可以分成兩條主要的資料流：<strong>上傳流程（Write Path）</strong>和<strong>觀看流程（Read Path）</strong>。這兩條流程的設計完全不同——上傳是寫入密集的非同步流程，觀看是讀取密集的同步流程。

上傳流程中，使用者透過 API 上傳影片，API 伺服器負責驗證和限流，把影片推送到<strong>處理佇列</strong>（如 Kafka）。佇列的作用是解耦：上傳和處理可以獨立擴展。從佇列中，<strong>轉碼器</strong>把影片轉成多種解析度和格式（CPU 密集型工作），<strong>縮圖生成器</strong>自動產生候選縮圖，處理後的檔案儲存到分散式檔案系統（如 HDFS 或 S3）。

觀看流程中，使用者發送播放請求，API 伺服器從<strong>元資料庫</strong>中查詢影片資訊，同時把請求導向正確的影片來源。影片透過<strong>CDN</strong>從最近的邊緣節點分發，<strong>負載均衡器</strong>把請求分散到多台伺服器。一致性雜﨑確保同一部影片的請求導向同一個快取節點，提高快取命中率。

API 設計方面，核心 API 包括 <code>uploadVideo</code>（上傳影片，包含 API 金鑰、影片元資料、影片內容）、<code>searchVideo</code>（搜尋影片，支援分頁）、<code>getVideo</code>（取得影片元資料和播放 URL）。這些 API 要考慮認證、限流和版本控制。

幾個關鍵設計決策：<strong>上傳與處理分離</strong>——上傳 API 不直接處理轉碼，而是推送到佇列，讓上傳快速回應使用者；<strong>元資料與影片分離</strong>——影片存在物件儲存，元資料存在關聯式資料庫，兩者用不同的技術和擴展策略；<strong>讀取走快取和 CDN</strong>——幾乎所有讀取請求都先命中快取；<strong>寫入走佇列</strong>——寫入操作先進佇列再由後端工作者處理。

你做過 REST API，這些 API 設計你應該很熟悉。YouTube 的 API 本質上就是你做過的 API 的放大版。差別在於你需要加上佇列處理非同步工作、加上快取應對讀取壓力、加上 CDN 分發大檔案。
