# 資料建模與元數據分片

## Learning goal
設計影片與使用者資料的數據庫Schema，並選擇合適的元數據分片策略處理大規模數據。

## Lesson

高層架構告訴你「系統由什麼組成」，資料建模告訴你「資料怎麼組織」。在 YouTube 這種規模的系統中，資料庫的設計直接影響查詢效能和擴展能力。YouTube 的資料可以分成兩大類：<strong>影片元資料</strong>和<strong>使用者資料</strong>，兩者的存取模式不同，需要不同的儲存策略。

每部影片的元資料包含 VideoID、Title、Description、Size、Thumbnail URL、Uploader（UserID）、TotalLikes、TotalDislikes、TotalViews。評論需要獨立的 Schema：CommentID、VideoID、UserID、Content、CreatedAt。這些結構化資料通常存在關聯式資料庫（如 MySQL）中，因為需要 ACID 保證。使用者資料相對簡單（UserID、Name、Email、RegistrationDate），量遠小於影片資料。

當影片數量達到數十億，單台資料庫無法承擔壓力，就需要<strong>分片（Sharding）</strong>。常見策略：<strong>按 UserID 分片</strong>——同一個使用者的所有資料在同一台伺服器，查詢「我的頁面」很快，但熱門使用者會造成熱點問題；<strong>按 VideoID 分片</strong>——影片分散到不同伺服器，資料分布均勻，但查詢「某個使用者的所有影片」需要跨伺服器聚合；<strong>按地理位置分片</strong>——減少延遲，但跨區查詢複雜。實際系統通常混合使用多種策略。

分片鍵的選擇是最關鍵的決策。好壞標準：<strong>均勻性</strong>（資料要均勻分布，VideoID 比 UserID 更均勻）、<strong>查詢效率</strong>（常見查詢要能高效執行）、<strong>擴展性</strong>（新增分片時資料遷移成本要低）。一致性雜﨑可以減少資料遷移量。

你用過 MySQL 和 Redis，YouTube 的元資料庫本質上就是你熟悉的 MySQL 的放大版。差別在於你需要決定怎麼把一個巨大的 MySQL 表拆到多台機器上（分片），以及哪些資料放 MySQL、哪些放物件儲存、哪些放 Redis 做快取。
