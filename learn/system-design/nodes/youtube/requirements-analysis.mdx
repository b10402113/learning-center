# 需求分析與範圍定義

## Learning goal
定義YouTube串流平台的功能性與非功能性需求，明確設計範圍與目標。

## Lesson

拿到「設計一個 YouTube」這種開放式題目，第一件事不是畫架構圖，而是<strong>釐清需求</strong>。需求分析決定兩件事：<strong>功能性需求</strong>告訴你系統做什麼；<strong>非功能性需求</strong>告訴你系統做得怎麼樣。面試中先把這兩類需求攤開，面試官才會覺得你在「設計系統」而不是「堆砌技術」。

YouTube 的功能性需求要從最核心的使用場景開始。我們不需要列出 YouTube 的所有功能，而是挑出面試中最重要的幾個：<strong>上傳影片</strong>（最基本的寫入操作）、<strong>觀看與分享影片</strong>（包含搜尋和播放，是系統使用量最大的部分）、<strong>記錄影片統計</strong>（觀看次數、點讚數等）、<strong>評論功能</strong>（相對獨立的子系統）。這些功能的組合就是系統的「做什麼」。

非功能性需求則決定架構走向。<strong>高可用性</strong>（系統 24/7 運作，任何中斷都影響數億使用者）、<strong>低延遲</strong>（影片播放要快，這也是為什麼 CDN 和快取如此重要）、<strong>一致性</strong>（上傳的影片必須保證之後能被搜尋到和觀看到）、<strong>可擴展性</strong>（系統要能隨著使用者和影片數量的成長而水平擴展）。面試中這部分往往更決定架構決策。

YouTube 最重要的系統特性是<strong>讀取密集（read-heavy）</strong>。典型的讀寫比大約是 200:1——每上傳一部影片，就有 200 次觀看。這個特性直接影響架構：系統要優先優化讀取效能。另一個特性是<strong>影片檔案很大</strong>，動輒數十 MB 到數 GB，儲存和頻寬成本非常高。

面試中需求分析通常佔 3-5 分鐘。好的做法是：先列出 3-5 個核心功能性需求，再列出 3-4 個非功能性需求，然後詢問面試官「我們是設計完整版還是簡化版」，確認後才進入下一步。這樣做有兩個好處：讓面試官覺得你有系統性思考，以及避免在不需要的功能上浪費時間。

你做過 REST API，用過 Postgres 和 Redis。YouTube 的需求分析會用到你熟悉的概念：API 設計（REST vs RPC）、資料庫選型（SQL 存元資料、物件儲存存影片）、快取策略。差別在於規模——你之前可能只服務幾百個用戶，YouTube 要服務數億。但思考邏輯是一樣的。
