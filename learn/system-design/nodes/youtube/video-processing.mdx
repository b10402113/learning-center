# 影片處理與去重

## Learning goal
設計上傳影片的後續處理流程，包括轉碼、縮圖生成，並解決影片重複的問題。

## Lesson

上傳一部影片到使用者能流暢播放之間，還有很多工作。這個過程就是<strong>影片處理管線（Video Processing Pipeline）</strong>。影片處理是 CPU 密集型工作，一部 10 分鐘的 1080p 影片可能需要幾十分鐘的轉碼時間，所以 YouTube 必須建立一個非同步、可擴展的處理叢集。

<strong>轉碼（Encoding）</strong>是核心。原始影片通常只有一種格式和解析度，但使用者的裝置和網路條件千差萬別，所以同一部影片需要轉成多種版本：解析度（4K、1080p、720p、480p、360p）、編碼格式（H.264、H.265、VP9）、位元率（高畫質需要更高位元率）。一部原始影片可能需要轉成 10-20 個版本，這也是為什麼儲存需求會比原始檔案大好幾倍。<strong>自適應串流（Adaptive Streaming）</strong>讓系統根據使用者的網路條件動態選擇最合適的版本。

<strong>縮圖生成</strong>方面，系統從影片中均勻取幾個時間點的畫面作為候選縮圖，也允許創作者上傳自訂縮圖。縮圖通常儲存為 JPEG 或 WebP 格式，大小 100-200 KB，會被快取到 CDN。

<strong>影片去重</strong>是大規模平台的嚴重問題。重複影片的來源包括完全相同（同一影片被多次上傳）、近似相同（不同解析度或加了水印）、部分相同（長影片的片段被單獨上傳）。重複的影響有三：儲存浪費、搜尋體驗差、推薦品質低。

去重的方法：<strong>指紋比對（Fingerprinting）</strong>——為每部影片生成數學特徵，上傳新影片時比對指紋，YouTube 的 Content ID 就是基於此技術；<strong>雜.createParallelGroup比對</strong>——計算檔案雜﨑值，只能檢測完全相同的檔案；<strong>感知雜﨑（Perceptual Hashing）</strong>——能檢測視覺上相似的影片。實際系統通常組合使用多種方法。

整個處理管線拆成幾個獨立服務：上傳服務（接收影片、驗證格式、推送到佇列）、轉碼服務（並行轉成多種版本，能水平擴展）、縮圖服務、去重服務、儲存服務。這些服務之間透過訊息佇列（如 Kafka）連接，確保每個服務可以獨立擴展。

你用過 Redis 和 Postgres，但可能沒處理過大檔案的非同步處理。YouTube 的影片處理管線本質上是一個工作管線：接收任務 → 排隊 → 處理 → 儲存。跟你之前用過的 Background Job 概念一樣，只是 YouTube 要同時處理數千個任務，每個需要幾十分鐘的 CPU 時間。
