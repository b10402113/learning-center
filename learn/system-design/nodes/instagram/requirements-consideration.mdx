# 需求分析與設計考量

## Learning goal
能夠列出設計 Instagram 所需的功能性與非功能性需求，並針對系統特性（讀取密集、儲存效率）說明核心設計考量。

## Lesson

Instagram 是一個社交網路服務，使用者可以上傳、分享照片與影片，也可以選擇公開或私密分享。公開內容任何使用者都能看到，私密內容只有指定的人才能存取。使用者可以追蹤其他人的帳號，在自己的動態消息（News Feed）中看到追蹤對象的最新貼文。

在系統設計面試中，Instagram 是經典的「大型社交平台」題目。它的核心挑戰不是功能複雜度——功能其實很直覺——而是**規模**：數億使用者、每天數百萬張照片上傳、每次開啟 App 都要快速載入動態消息。

### 功能性需求

面試的第一步是把需求列清楚。功能性需求決定系統「做什麼」，通常從最核心的使用場景開始：

1. **上傳照片**——使用者可以上傳照片，系統要能儲存並在之後提供檢視。這是最基本的寫入操作。
2. **檢視照片**——使用者可以瀏覽任何公開照片或自己追蹤的帳號的照片。這是讀取操作，也是系統使用量最大的部分。
3. **追蹤使用者**——使用者可以關注其他帳號，建立「追蹤者 → 被追蹤者」的關係。這個關係是動態消息生成的基礎。
4. **搜尋照片**——使用者可以用照片或影片的標題來搜尋。注意這裡的搜尋範圍相對有限（標題搜尋），不是全文搜尋。
5. **產生動態消息**——系統要能為每個使用者產生個人化的動態消息，彙整追蹤對象的最新、最熱門的照片。這是整個系統最複雜的功能。

### 非功能性需求

功能性需求告訴你「做什麼」，非功能性需求告訴你「做得怎麼樣」。面試中這部分往往更決定架構走向：

- **高可用性（High Availability）**——系統 24/7 運作，不能有明顯的停機時間。對社交平台來說，任何中斷都會直接影響使用者體驗和信任。
- **低延遲（Low Latency）**——載入照片和動態消息的速度要快。使用者打開 App 後如果要等好幾秒才看到內容，很快就會流失。
- **一致性（Consistency）**——使用者上傳的照片，必須保證之後能被檢視到。系統不能丟失資料，這是基本的信任底線。
- **可擴展性（Scalability）**——隨著使用者和照片數量的成長，系統要能水平擴展（scale out），而不是靠升級單台伺服器（scale up）。

### 設計考量：讀取密集是關鍵

Instagram 最重要的系統特性是**讀取密集（read-heavy）**。原因是：**寫入（上傳照片）的頻率遠低於讀取（瀏覽照片）的頻率**。大多數使用者每天上傳零到幾張照片，但會瀏覽數十到數百張照片。

這意味著你的架構設計必須優先考慮**讀取效能**。快取（caching）會是核心策略——把熱門照片放在快取裡，避免每次都從硬碟讀取。

另一個重要考量是**儲存效率**。使用者可以無限上傳照片，照片檔案通常很大（平均 200KB），所以儲存空間的需求會非常龐大。系統需要高效的儲存管理策略。

此外，**資料可靠性**也是核心要求：使用者上傳的照片不能丟失。即使某台儲存伺服器壞了，照片也要能從其他副本中恢復。

你做過 REST API，用過 Postgres 和 Redis。Instagram 的設計其實會用到你熟悉的技術：Postgres 存元數據、Redis 做快取、物件儲存（類似 S3）存照片。差別在於規模——你之前可能只服務幾百個用戶，Instagram 要服務數億。但技術選型的邏輯是一樣的，只是要加上分散式的思考。
