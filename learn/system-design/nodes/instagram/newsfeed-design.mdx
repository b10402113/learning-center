# 動態消息生成設計

## Learning goal
能夠設計分片資料上的動態消息生成流程，說明如何高效獲取並排序追蹤使用者的最新照片。

## Lesson

Instagram 的動態消息（News Feed）是整個系統最複雜的功能。它的目標是：給定一個使用者，快速產生一頁包含追蹤對象最新、最熱門照片的列表。

假設要顯示 100 張照片。系統需要：

1. 查出這個使用者追蹤了哪些人
2. 對每個被追蹤的人，查出最新的 100 張照片
3. 把所有照片合併，按時間或熱門度排序，取前 100 張

如果一個使用者追蹤了 500 人，系統就要做 500 次查詢，每次拿 100 張照片，然後從 50,000 張中選出前 100 張。這在分片架構下尤其困難，因為這些照片分散在不同的資料庫分片上。

### 方案一：產生時計算（On-Read）

最直覺的做法是**在讀取時即時計算**。每次使用者打開動態消息，系統就即時查詢所有追蹤對象的最新照片，排序後呈現。

優點：實現簡單，資料永遠最新。

缺點：延遲高。每次載入都要查詢數百個使用者的照片，在分片架構下需要跨分片查詢，速度很慢。如果追蹤了 500 人，就要做 500 次查詢。

### 方案二：寫入時計算（On-Write）

另一種做法是**在寫入時預先計算**。每次使用者上傳一張新照片，系統就把這張照片推送到所有追蹤者的動態消息快取中。

優點：讀取時只需要從快取中取出預計算好的結果，延遲極低。

缺點：寫入時的計算量大。如果一個帳號有 1000 萬追蹤者，上傳一張照片就要更新 1000 萬個人的動態消息快取。這是**寫入放大**問題。

### 方案三：混合方案

實際的 Instagram 採用混合方案：對**大部分使用者**使用寫入時計算（預計算），對**追蹤者極多的帳號**（如明星）使用讀取時計算（即時查詢）。

具體做法：

1. 普通使用者上傳照片時，把照片 ID 推送到追蹤者的動態消息快取（一個 Sorted Set）
2. 明星帳號上傳照片時，不預計算——因為追蹤者太多，寫入放大不可接受
3. 載入動態消息時，先從快取取出預計算的結果，再即時查詢明星帳號的最新照片，合併排序

這種方案在延遲和寫入成本之間取得了平衡。

### PhotoID 的巧妙設計

為了高效查詢「最新照片」，Instagram 把**建立時間嵌入 PhotoID**。PhotoID 是一個 64-bit 的整數，高位是時間戳，低位是序列號。

這樣做的好處是：PhotoID 本身就包含了時間順序。查詢「最新照片」只需要找出最大的 PhotoID，不需要額外的時間欄位查詢。在分片架構下，這讓排序變得非常高效。

你之前做 REST API 時，可能每次請求都從資料庫即時查詢。Instagram 的動態消息設計展示了一個重要的模式：**預計算**。把昂貴的查詢在寫入時做完，讀取時只需要從快取取結果。這跟你之前用 Redis 做快取的經驗類似，但 Instagram 把這個模式推到了極致——快取本身就是預計算的結果。
