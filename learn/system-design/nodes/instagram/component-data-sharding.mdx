# 元件設計與資料分片

## Learning goal
能夠解讀讀寫分離的設計考量，並比較不同資料分片策略的優缺點，選擇適合 Instagram 場景的分片方式。

## Lesson

Instagram 的照片上傳（寫入）和照片瀏覽（讀取）有截然不同的特性。上傳是慢操作——照片要從使用者裝置傳到伺服器，再寫入磁碟。讀取是快操作——尤其是從快取中讀取時，延遲可以低到毫秒級。

問題在於：Web 伺服器有連線數上限。如果所有連線都被上傳請求佔滿，瀏覽請求就無法被服務。這就像一條高速公路，如果所有車道都被慢車佔滿，快車就過不去。

解決方案是**讀寫分離**：用一組伺服器專門處理寫入（上傳），另一組專門處理讀取（瀏覽）。兩組伺服器各自擴展，互不干擾。

### 讀寫分離的架構

具體做法：

1. **寫入路徑**：上傳請求到達寫入負載均衡器 → 分發到寫入應用伺服器 → 照片寫入物件儲存，元數據寫入主資料庫（Primary DB）
2. **讀取路徑**：瀏覽請求到達讀取負載均衡器 → 分發到讀取應用伺服器 → 先查快取（Redis），快取未命中再查從資料庫（Replica DB）

主資料庫（Primary）負責處理所有寫入，從資料庫（Replica）從主資料庫同步資料，專門服務讀取。這是**主從複製（Primary-Replica）**模式。

### 資料分片策略

當元數據量成長到單台資料庫無法承載時，就需要**分片（Sharding）**——把資料分散到多台資料庫伺服器上。Instagram 有三種主要的分片策略：

**策略一：按 UserID 分片**

把同一個使用者的所有照片存在同一個分片上。分片號 = UserID % 分片數。

優點：查詢「某個使用者的所有照片」只需要訪問一個分片，延遲低。

缺點：熱門使用者（如明星）的照片集中在一個分片，造成**熱點（hotspot）**問題。

**策略二：按 PhotoID 分片**

把照片分散到各個分片，不考慮使用者。分片號 = PhotoID % 分片數。

優點：資料均勻分散，沒有熱點問題。

缺點：查詢「某個使用者的所有照片」需要掃描所有分片，延遲高。

**策略三：按 PhotoID 的時間部分分片**

把 PhotoID 的建立時間作為分片依據。新照片自動進入新分片，舊分片不會有新資料寫入。

優點：動態消息需要查最新照片，這種分片讓查詢集中在少數幾個分片上，延遲低。

缺點：需要額外的機制來保證 PhotoID 的唯一性。

### Instagram 的選擇

Instagram 選擇**按 PhotoID 分片**，原因是：

Instagram 的核心查詢是「產生動態消息」——需要取得追蹤對象的最新照片。如果按 UserID 分片，產生一個動態消息需要查詢數百個使用者的照片，分散在不同分片上。如果按 PhotoID 分片，每個分片都有一部分最新照片，查詢可以並行化。

至於熱點問題，可以用**一致性雜湊（Consistent Hashing）**來動態調整分片映射，把熱點分散到多個分片上。

你用過 Redis 和 MongoDB，可能已經接觸過分片的概念。Instagram 的分片策略選擇展示了一個重要的設計取捨：沒有完美的分片方式，只有最適合你的查詢模式的方式。你之前可能根據「直覺」來選擇分片鍵，但面試中考的是你能不能分析不同方案的優缺點，並根據系統特性做出合理的選擇。
