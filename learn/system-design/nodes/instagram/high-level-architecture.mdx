# 高階系統架構設計

## Learning goal
能夠繪製並解釋 Instagram 的高階架構，區分上傳與觀看照片兩大核心流程，說明物件儲存與元數據資料庫的分工。

## Lesson

設計 Instagram 的高階架構時，先把系統拆成兩個獨立的場景來思考：**上傳照片**和**觀看照片**。這兩個場景的資料流完全不同，對系統的要求也不同。

上傳是寫入密集的操作——照片要從使用者裝置傳到伺服器，寫入儲存，元數據寫入資料庫。觀看是讀取密集的操作——照片要從快取或儲存讀取，元數據要從資料庫查詢，兩者在動態消息頁面中組合呈現。

把這兩個流程分開設計，是因為它們的瓶頸不同：上傳的瓶頸是**寫入吞吐量**和**儲存容量**，觀看的瓶頸是**讀取延遲**和**快取命中率**。

### 高階架構元件

整個系統可以分成四層：

1. **負載均衡器（Load Balancer）**——所有使用者請求先到負載均衡器，它把請求分發到後端的应用伺服器。負載均衡器隱藏了後端伺服器的數量和狀態，讓系統可以水平擴展。
2. **應用伺服器（Application Server）**——處理業務邏輯：驗證使用者身份、處理上傳請求、查詢元數據、產生動態消息。應用伺服器是無狀態的，可以隨意增加或減少。
3. **物件儲存伺服器（Object Storage）**——儲存照片和影片檔案。這是專門用來儲存大量非結構化資料的系統，類似 Amazon S3。物件儲存的特點是便宜、耐用、可以無限擴展。
4. **資料庫伺服器（Database Server）**——儲存元數據：使用者資料、照片資訊（標題、上傳時間、地理標籤）、追蹤關係。元數據是結構化資料，適合用關聯式資料庫。

### 上傳流程

使用者上傳一張照片時，資料流是這樣的：

1. 使用者選擇照片，點擊上傳
2. 請求到達負載均衡器，被分發到某台應用伺服器
3. 應用伺服器把照片檔案轉發到物件儲存伺服器，同時把元數據（標題、時間、使用者 ID）寫入資料庫
4. 上傳完成，系統回傳成功給使用者

關鍵點：照片檔案和元數據是**分開儲存**的。物件儲存管檔案，資料庫管描述。這種分離讓兩個系統各自發揮優勢。

### 觀看流程

使用者打開動態消息或查看某張照片時：

1. 應用伺服器先從資料庫查詢元數據（追蹤了誰、哪些照片最新）
2. 根據元數據中的照片 URL，從物件儲存（或 CDN 快取）載入照片檔案
3. 把照片和元數據組合後回傳給使用者

觀看流程的瓶頸在於：每次都要先查資料庫拿到元數據，再從物件儲存載入照片。如果動態消息要顯示 100 張照片，就要做 100 次物件儲存讀取。所以**快取**在這裡扮演關鍵角色。

### 為什麼這樣設計？

把照片和元數據分開儲存有幾個好處：

- **各自擴展**——照片檔案量成長時，擴展物件儲存；使用者量成長時，擴展資料庫。兩者不需要同步擴展。
- **各自優化**——物件儲存最佳化大檔案的順序寫入和批量讀取；資料庫最佳化小記錄的隨機查詢和索引查找。用同一個系統做兩件事，兩邊都做不好。
- **各自快取**——熱門照片可以放在 CDN 快取，熱門元數據可以放在 Redis 快取。兩層快取互不干擾。

你做過 REST API，可能把所有資料都存在同一個 Postgres 裡。Instagram 的架構其實是把「資料」拆成了兩種類型：結構化的元數據（適合 SQL）和非結構化的檔案（適合物件儲存）。這跟你之前把所有東西塞進一個資料庫的模式不同，但技術選型的邏輯是一致的——根據資料特性選擇最合適的儲存。
