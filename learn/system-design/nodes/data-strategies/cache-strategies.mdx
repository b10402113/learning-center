<LearningGoal>
理解不同快取讀寫模式（Read-Through、Write-Through、Write-Behind）以及伺服器端與用戶端快取的差異與適用場景。
</LearningGoal>

## Lesson

快取讀寫模式回答一個核心問題：資料在快取和底層數據源之間，以什麼順序流動？不同的順序帶來不同的一致性、效能和複雜度取捨。你在 Redis 上做過快取，但有沒有想過程式碼寫入資料時，資料是先到 Redis 還是先到資料庫？這個「先後順序」的不同，就是讀寫模式的本質。

**Read-Through（懶加載）** 是最常見的快取模式。當應用程式讀取資料時，先查快取：命中就直接返回；未命中時，快取層自動去數據源取回資料、存入快取、然後返回。應用程式不需要知道資料是從快取還是數據源來的，這簡化了程式碼。缺點是第一次讀取（cache miss）會有額外延遲，因為要多走一趟數據源。適合讀取頻繁、資料更新不頻繁的場景——電商商品目錄、新聞文章、使用者個人資料，這些資料被無數人反覆讀取但很少變更。

**Write-Through（同步雙寫）** 在寫入時同時更新快取和底層數據源，而且是同步的。寫入完成時兩邊一定一致。好處是強一致性，任何時候從快取讀取都是最新資料。缺點是寫入效能較差——每次寫入都要等兩個地方都寫完才返回。適合資料一致性要求極高的場景：金融交易、庫存管理、訂單系統，這些場景不能容忍短暫的不一致。

**Write-Behind（異步回寫）** 是 Write-Through 的「偷懶版」：寫入時只更新快取，不立刻寫數據源。快取層在背景異步、批量地把變更寫回數據源。好處是寫入極快——應用程式只等快取寫完（微秒級），不用等資料庫（毫秒級）。壞處是異步窗口期內如果快取節點崩潰，尚未寫回的資料會丟失。適合寫入量極大、能容忍短暫不一致的場景：社群媒體按讚計數、頁面瀏覽量統計、日誌收集。

除了讀寫模式，另一個重要維度是**快取放在哪裡**。伺服器端快取（如 Redis、Memcached）存在伺服器記憶體中，由伺服器集中控制，所有用戶共享。用戶端快取（如瀏覽器 HTTP 快取、App 本地存儲）存在用戶裝置上，由用戶端控制，僅限該用戶使用。伺服器端快取能統一管理資料新鮮度，適合降低伺服器負載；用戶端快取能減少網路請求次數，提升個別用戶體驗，並支援離線存取。生產系統通常兩者並用：伺服器端快取減少資料庫壓力，用戶端快取減少網路請求。例如你的 REST API 返回帶 `Cache-Control: max-age=3600` 的 response，瀏覽器會在一小時內用本地快取；同時伺服器端用 Redis 快取熱門資料，減少資料庫查詢。

面試中要能清楚解釋三種讀寫模式的資料流動順序，根據一致性需求和讀寫比例選擇合適的模式，並能比較伺服器端和用戶端快取的控制權、受益範圍、新鮮度差異。
