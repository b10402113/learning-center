<LearningGoal>
理解主從複製與對等複製兩種架構的差異，並能依場景選擇適合的複製策略。
</LearningGoal>

## Lesson

資料複製把同一份資料存到多台機器上，帶來兩個核心好處：讀取擴展（多台機器分攤讀取壓力）和容錯（一台掛了其他的還能服務）。但「怎麼複製」有兩種根本不同的架構，它們的資料流動方向、控制模式和適用場景截然不同。

**主從複製（Primary-Replica）** 的核心邏輯是：一個 Primary 節點負責所有寫入，多個 Replica 節點負責讀取。資料單向流動——從 Primary 同步到 Replica，反向不行。這是典型的讀寫分離架構：寫入集中在一台機器（Primary），讀取分散到多台（Replica）。你在用過的 Postgres/MySQL 就支援這種架構，多數 Web 應用都採用它。主從架構簡單可控，適合讀多寫少的場景。但它有一個根本問題：Primary 是單點故障。如果 Primary 掛了，整個系統無法寫入。解決方案是故障轉移（Failover）——從 Replica 中選一個升級為新 Primary，但這個過程可能造成短暫的寫入中斷，而且異步複製下新 Primary 可能缺少部分尚未同步的資料。

**對等複製（Peer-to-Peer）** 的核心邏輯是：每個節點都是平等的，任何節點都能讀和寫，資料在所有節點之間雙向同步。沒有中心化的控制點，任何節點掛了其他節點繼續服務，天然容錯。Cassandra、CouchDB 是典型的對等複製資料庫，適合全球分佈系統——任何地理位置的用戶都能就近寫入。但對等架構的代價是衝突處理：當兩個節點同時修改同一筆資料時，需要決定哪個版本是「正確」的。常見策略有 Last Write Wins、向量時鐘等，每種都有取捨，這也是多數中小規模系統寧願選主從架構的原因——簡單可控。

選擇時的關鍵維度：主從架構容易擴展讀取但寫入擴展困難，對等架構兩者都容易但複雜度高。主從適合傳統 Web 應用和讀多寫少的場景；對等適合全球分佈系統和高可用需求。面試中要能清楚解釋兩種架構的資料流動方向差異，以及各自的單點故障或衝突處理挑戰。
