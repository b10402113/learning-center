## Lesson

前兩課介紹了分片方法和分片標準，聽起來分片好像能解決所有問題。但分片在帶來擴展性的同時，也引入了新的複雜性。當資料分散在多個分片上，很多原本在單一資料庫上理所當然的操作，都會變得更困難。本節介紹分片後最常遇到的五大挑戰，以及每個挑戰的解決思路。理解這些挑戰，才能在面試中清楚解釋分片設計的完整取捨。

**挑戰一：JOIN 與反規範化。** 在單一資料庫中，`JOIN` 是最常用的操作之一。你可以輕鬆地把使用者表和訂單表 JOIN 在一起，一次查詢就能拿到完整的資料。但在分片資料庫中，不同表的資料可能在不同伺服器上，跨伺服器的 JOIN 需要大量網路傳輸，性能極差。

舉個例子：假設你按使用者 ID 分片了使用者表和訂單表。查詢「某個使用者的所有訂單及其商品名稱」，需要先從使用者分片取出使用者資訊，再從訂單分片取出訂單列表，再從商品分片取出商品名稱，然後在應用層做三次 JOIN。這在單一資料庫中只需要一條 SQL 就能完成，但在分片架構中，你需要跨三個分片做網路查詢，延遲可能從幾毫秒變成幾百毫秒。

解決思路有兩個方向：一是**反規範化（Denormalization）**，把需要 JOIN 的資料複製到同一個分片，用空間換取時間。例如把使用者的名字直接存在訂單表裡，查詢訂單時不需要跨分片 JOIN。反規範化的缺點是資料會有冗餘，更新時需要同步多個地方，增加了寫入的複雜度。如果使用者改了名字，你必須同步更新所有包含使用者名字的訂單記錄。二是**應用層 JOIN**，在應用程式中做 JOIN，先從各分片取出資料，再在記憶體中組合。這適合 JOIN 結果集不大的場景，但結果集很大時，記憶體和網路開銷會成為瓶頸。例如你要「查詢所有使用者及其訂單總額」，這需要跨所有分片取資料，然後在應用層做聚合，性能會很差。在這種情況下，你可能需要預計算聚合結果（例如用 MapReduce 或 Background Job），而不是在查詢時即時計算。

**挑戰二：重新分片（Rebalancing）。** 隨著業務成長，你可能需要新增分片、移除分片、或重新分配資料。這個過程叫做重新分片（Rebalancing）。在重新分片期間，系統需要保持可用，這是一大挑戰。

如果是雜湊分片，新增分片會導致幾乎所有資料需要重新搬移（因為 `hash % N` 的結果改變了）。例如從 4 個分片擴展到 5 個分片，幾乎所有資料的 `hash % 5` 結果都跟 `hash % 4` 不同，你需要把大部分資料從舊分片搬到新分片。如果是範圍分片，只需要搬移新分片對應範圍的資料，相對簡單。例如新增一個分片負責 ID 20001~25000 的範圍，只需要從原本負責 10001~25000 的分片中，把 20001~25000 的資料搬過去。

解決思路包括使用**一致性雜湊**（在新增或移除分片時，只需要搬移少量相鄰分片的資料，而不是全部重新分配），以及**漸進式搬移**（不一次搬完所有資料，而是分批搬移，期間同時從新舊分片讀取，確保可用性）。在實務中，很多大型系統（如 Cassandra、DynamoDB）已經內建了一致性雜湊和自動 rebalancing 的能力，減少了手動管理的負擔。

**挑戰三：跨分片查詢與交易。** 單一資料庫的交易（Transaction）可以保證 ACID 特性——原子性、一致性、隔離性、持久性。但在分片資料庫中，一筆交易可能涉及多個分片，這叫做**分散式交易**（Distributed Transaction）。分散式交易需要跨網路協調，性能差且複雜度高。

跨分片查詢也是一樣的道理。例如「查詢所有分片中，金額超過 1000 的訂單」，你需要掃描所有分片，然後在應用層合併結果。如果分片數量很多，這個查詢的延遲會隨著分片數量線性增長。

解決思路包括**尽量避免跨分片交易**（透過合理的分片鍵設計，讓相關資料在同一個分片。例如把使用者和他的訂單放在同一個分片，這樣處理訂單時不需要跨分片交易）、**最終一致性**（不追求即時一致，而是允許短期不一致，透過背景同步 eventually 達到一致。這在社群平台等場景中很常見——你發了一條動態，朋友可能晚幾秒才看到，但最終所有人都會看到），以及 **Saga 模式**（把大交易拆成多個小步驟，每個步驟有補償操作，失敗時可以回滾。例如「扣款→建立訂單→扣庫存」拆成三步，如果「扣庫存」失敗，就執行「退款」和「取消訂單」的補償操作）。

**挑戰四：熱分片（Hotspot）。** 即使分片設計良好，某些分片仍然可能因為業務特性而出現負載過高的情況。例如社群平台的「熱門使用者」，如果按使用者 ID 分片，某個大 V 的資料和請求全部集中在一個分片上。這個大 V 可能有 1000 萬粉絲，每次發文都會觸發大量的讀取和寫入，導致該分片的負載遠高於其他分片。

熱分片問題在範圍分片中更為常見。例如按時間分片，最新的分片會不斷接收新資料的讀寫，而舊分片幾乎沒有流量。按地理位置分片的話，人口密集的地區（如台北、東京）的分片負載會遠高於人口稀少的地區。

解決思路包括**拆分熱分片**（把熱門使用者的資料再拆分到多個子分片，例如大 V 的資料按粉絲地區分片）、**快取**（在分片前面加一層快取，把熱門資料放在記憶體中，減少對分片的直接訪問。例如把大 V 的最新動態放在 Redis 中，大部分讀取請求直接從快取返回），以及**重新設計分片鍵**（選擇更能均勻分布的鍵，避免某個鍵值過於集中）。

**挑戰五：分片命名與管理。** 當分片數量增多，管理分片元資料（metadata）本身也是一個挑戰。你需要記錄每個分片的範圍、位置、狀態等資訊。如果元資料管理不當，可能導致分片找不到、路由錯誤等問題。

想像一下：你有 100 個分片，每個分片的資訊（位置、負責的範圍、狀態）需要被所有應用程式知道。如果這些資訊分散在各個應用程式中，更新時就需要同步所有節點，這在分散式系統中是非常困難的。解決思路包括使用**配置服務**（如 ZooKeeper、etcd）把分片元資料存在專門的配置服務中，所有節點從配置服務讀取最新資訊。當分片資訊變更時，只需要更新配置服務，所有節點會自動感知。以及使用有內建分片管理的資料庫（如 MongoDB、Cassandra），讓系統自動處理分片的新增、移除和路由。這些資料庫內建了分片管理的能力，減少了手動管理的複雜度。

在系統設計面試中，能討論分片的挑戰是得分關鍵。面試官想聽到的是：你**知道分片會帶來什麼問題**，而不只是知道分片能擴展；你能根據場景提出**具體的解決思路**；你能討論**取捨**（例如反規範化用空間換時間、最終一致性用一致換性能）；你能指出**哪些操作在分片後會變難**（JOIN、交易、跨分片查詢）。理解這些挑戰，才能在面試中清楚解釋分片設計的完整取捨，而不只是停留在「分片能擴展」的表層認知。

在實務中，這些挑戰往往是相互關聯的。例如，你選擇了雜湊分片來均勻分布資料（解決熱分片問題），但雜湊分片不支持範圍查詢（引入新的查詢限制）。你選擇了反規範化來避免跨分片 JOIN（解決 JOIN 問題），但反規範化增加了資料冗餘和同步複雜度（引入新的維護成本）。所以分片設計本質上是一連串的取捨——你在解決一個問題的同時，往往會引入另一個問題。面試官追問的「為什麼選這個方案」，就是在考驗你是否理解這些連鎖反應。
