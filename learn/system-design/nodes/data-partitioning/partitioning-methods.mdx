<LearningGoal>
理解常見的資料分片方法，包括水平分片與垂直分片的差異與適用場景
</LearningGoal>

## Lesson

想像你有一個超大的圖書館，所有書都堆在一間房子裡。當書越來越多，找一本書要翻遍整間房子，效率極低。解決方法很直覺：把書分到多間房間，每間房間只放一部分書。這樣每個房間的書少了很多，找起來自然快。但接下來你會遇到新的問題：怎麼決定哪些書放哪間房間？不同房間的書怎麼保持一致？怎麼在房間之間搬書？這些問題在電腦世界裡同樣存在。

資料分片（Data Partitioning）就是這個道理。當單一資料庫無法容納整個資料集，或是單一節點的負載達到瓶頸時，我們需要將大型資料切割成多個較小、獨立的部分，分散到不同的節點上。每個節點只需要處理自己分區內的請求，系統的整體性能與可擴展性自然提升。但分片不是免費的午餐——它在帶來擴展性的同時，也引入了新的複雜性。選擇正確的分片方法，是設計可擴展系統的第一步。

在深入三種分片方法之前，先釐清一個常見的誤解：分片不只是「把資料分開」這麼簡單。分片是一種架構決策，一旦做了就很難回頭。錯誤的分片方法可能導致系統在後期需要大規模重構，成本極高。所以選擇分片方法時，要同時考慮當下的需求和未來的成長方向。

常見的分片方法主要分為三種：**水平分片**、**垂直分片**與**混合分片**。它們解決不同的問題，適用於不同的場景。理解這三種方法的核心差異，才能在面試中清楚地解釋你的設計選擇。

**水平分片（Horizontal Partitioning）** 也稱為 Sharding（分片），是最常見的分片方式。核心概念是：把同一張資料表的資料按列切割，每個分片包含完整的欄位結構，但只存放一部分的列。每個分片通常分配到不同的伺服器，達到平行處理分散負載的效果。

舉個具體的例子：假設你有一張使用者表 `users`，裡面有 1000 萬筆資料，包含 ID、名字、Email、手機號碼等欄位。你可以把 ID 1~500 萬放在分片 A，ID 500 萬~1000 萬放在分片 B。每個分片有自己的完整欄位結構（ID、名字、Email 等），但只存放一半的列。查詢某個使用者時，系統先判斷該使用者的 ID 在哪個範圍，然後只去對應的分片查詢，不需要掃描全部 1000 萬筆資料。

水平分片的優點是**容易擴展**：資料量再大，只要增加分片就能容納。1000 萬筆放不下？分成 10 個分片，每個分片只要放 100 萬筆。但缺點也很明顯：如果分片鍵（shard key）選擇不好，容易導致某些伺服器負載過高，而其他伺服器閒置。例如按使用者 ID 分片，但某個大 V 使用者的資料量是普通使用者的 1000 倍，那該分片就會成為瓶頸。此外，水平分片後，跨分片的 JOIN 和交易變得非常困難。在單一資料庫中，你可以輕鬆地用一條 SQL 做 JOIN 和交易。但在分片資料庫中，JOIN 需要跨網路傳輸資料，交易需要跨節點協調，性能和複雜度都會大幅增加。這在後續的「分片挑戰」中會詳細討論。

水平分片在實務中的應用非常廣泛。Twitter 按使用者 ID 分片推文，Instagram 按時間分片照片，很多大型電商平台按訂單 ID 分片交易記錄。這些系統的共同特點是：資料量巨大，單一資料庫無法容納，而且查詢模式相對簡單（通常只需要查單筆或小範圍的資料）。但水平分片也有一些陷阱：你需要選擇一個好的分片鍵（shard key），確保資料分布均勻；你需要處理跨分片的查詢和交易；你還需要考慮分片的管理——當分片數量從 10 增加到 100，管理 100 個分片的元資料本身就是一個挑戰。這些問題在後續的「分片挑戰」中會詳細討論，這裡先建立一個基本的認知：水平分片是擴展資料庫最直接的方法，但它帶來的複雜性不容小覷。

**垂直分片（Vertical Partitioning）** 則是依照「欄位」切割，每個分片存放一部分的欄位。主要目的是**優化查詢性能**，讓常用的欄位存在一起，減少查詢時需要掃描的資料量。

舉個具體的例子：假設你有一張商品表 `products`，裡面有「商品名稱」「價格」「描述」和「圖片 URL」四個欄位。大多數查詢只需要名稱和價格，很少需要完整的描述和圖片。如果你把所有欄位都放在同一個表裡，每次查詢都要掃描包含描述和圖片 URL 的大列，即使你根本不需要它們。垂直分片的解法是：把名稱和價格放在分片 A（列小，查詢快），描述和圖片 URL 放在分片 B（列大，但很少被查詢）。一般查詢只需要讀取分片 A，速度自然快很多。

垂直分片的另一個常見應用是把「熱資料」和「冷資料」分開。例如社群平台的使用者個人資料，名字和頭像（熱資料）放一個分片，登入歷史和操作日誌（冷資料）放另一個分片。熱資料的查詢頻率高，放在性能更好的 SSD 上；冷資料的查詢頻率低，可以放在成本較低的 HDD 上。這樣既優化了查詢性能，也降低了儲存成本。

垂直分片的缺點是**需要應用程式知道欄位位置**。如果你的查詢需要同時用到兩個分片的欄位，就得做 JOIN，這會帶來額外的網路開銷。在微服務架構中，垂直分片通常是自然而然的——每個服務管理自己的資料表，本質上就是一種垂直分片。但在單體架構中，垂直分片需要應用程式明確知道去哪個分片取資料，增加了開發複雜度。

**混合分片（Hybrid Partitioning）** 結合兩種方法，先垂直再水平（或反之）。這種方式在大型系統中很常見：先用垂直分片把不同功能模組的資料分開（例如使用者資料、訂單資料、商品資料），再對每個模組做水平分片（例如按地區切分訂單）。

例如，一個大型電商平台可能這樣設計：先用垂直分片把「使用者資料」「訂單資料」「商品資料」分到三個不同的資料庫。然後對「訂單資料」做水平分片，按地區（台灣、日本、美國）各分一個分片。使用者資料和商品資料因為量相對較小，不需要再做水平分片。這種混合方式既利用了垂直分片的查詢優化，也利用了水平分片的擴展能力。

混合分片的優點是能同時達到擴展性和性能優化，但缺點是架構複雜度高，維護成本也相對較大。你需要管理多個資料庫之間的一致性，處理跨分片的交易，以及確保應用程式正確地路由到對應的分片。在面試中，如果你能清楚地解釋為什麼選擇混合分片，以及它帶來的取捨，就能展現你的系統設計能力。

選擇哪種分片方法，取決於你的系統瓶頸在哪裡——是資料太多放不下（水平分片），還是查詢太慢需要優化（垂直分片），還是兩者都有（混合分片）。在面試中，不要死記硬背某種方法，而是根據具體的業務場景來分析和選擇。記住：沒有最好的分片方法，只有最適合當下場景的分片方法。面試官通常會問「為什麼你選水平分片而不是垂直分片」，你的回答應該基於具體的業務需求，而不是泛泛而談。

最後提醒一點：分片方法的選擇會直接影響後續的分片標準、查詢設計和擴展策略。水平分片後，你需要考慮雜湊或範圍分片來決定資料分配；垂直分片後，你需要處理跨分片的 JOIN；混合分片後，你需要管理多層的分片邏輯。所以在選擇分片方法時，不僅要考虑當下的需求，還要預見未來可能遇到的挑戰。例如，如果你預期資料量會快速成長，水平分片可能是更安全的選擇；如果你的查詢模式很複雜，垂直分片可能更合適。這也是為什麼在系統設計面試中，面試官會不斷追問「為什麼選這個方法」——他們想看到你能權衡取捨，而不只是知道有哪些方法。
