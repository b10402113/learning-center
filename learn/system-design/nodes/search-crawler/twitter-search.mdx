# Twitter Search 系統設計

## Learning goal
掌握 Twitter Search 系統的需求分析、容量估算、整體架構設計與最佳化策略

## Lesson

### 問題定義

Twitter 使用者可以隨時發推文（tweet），每條推文是一段純文字。我們要設計一個系統，讓使用者能在所有推文中快速搜尋關鍵字。這跟一般的 NoSQL CRUD 應用完全不同——搜尋的本質是「找出包含特定詞的所有推文」，需要一個專門的資料結構：倒排索引（Inverted Index）。

### 需求與目標

假設 Twitter 有 15 億使用者、8 億日活躍使用者，每天產生 4 億條新推文，平均每條 300 bytes。系統每天要處理 5 億次搜尋，查詢由多個詞以 AND/OR 組合而成。核心需求是高效儲存推文並支援快速查詢，搜尋延遲目標在數百毫秒內。

### 容量估算

每天新增推文的原始儲存量：4 億條 × 300 bytes = 120 GB/天，換算成每秒寫入速率約 1.38 MB/秒。五年規劃下，加上 80% 磁碟使用率上限，總共需要約 250 TB 儲存。搜尋流量方面，5 億次/天 ÷ 86400 ≈ 5,800 QPS，尖峰取 2 倍約 11,600 QPS。

### 倒排索引設計

倒排索引是搜尋引擎的核心。正向索引是「推文 → 包含哪些詞」，倒排索引反過來：「詞 → 出現在哪些推文」。例如三條推文 T1「我愛台北的天氣」、T2「台北今天下雨」、T3「我喜歡晴天」，建立倒排索引後，「台北」對應 [T1, T2]，「我」對應 [T1, T3]。搜尋「我 AND 台北」時取交集得到 [T1]。

### 儲存分區策略

250 TB 索引不可能放在單台機器上。常見策略是按推文 ID 做 Hash 分區，每台機器負責一部分推文 ID 範圍。搜尋時必須並行查詢所有分區再合併結果。也可以按時間分區：最近的推文放 SSD，較舊的放 HDD。另一種方式是按詞分區，但熱門詞會造成熱點。實務上常用混合策略。

### 快取與負載均衡

搜尋結果有明顯的時間局部性：熱門話題短時間內會被大量搜尋。用 Memcached 在應用層前方快取熱門搜尋結果，淘汰策略選 LRU。但搜尋查詢組合是天文數字，命中率通常只有 20-30%。負載均衡分兩層：使用者到應用伺服器用 Round Robin，應用伺服器到索引伺服器根據分區策略路由。

### 排名與容錯

排名因子包括相關性（TF-IDF 思路）、熱門度（按讚/轉推數）、時效性與社交關係。排名可以查詢時即時計算，也可以預先計算存到索引中加速查詢。容錯方面，每台索引伺服器有 secondary 副本，故障後自動 failover；若 primary 和 secondary 同時故障，需回放推文的寫入日誌重建索引——這就是原始推文儲存不能丟的原因。
