## Lesson

想像你經營一個電商網站，平時每秒處理 500 個請求。某天辦了一場限時搶購活動，流量瞬間湧入，每秒湧進 50,000 個請求。你的伺服器瞬間過載，CPU 跑滿、記憶體爆掉，結果所有用戶——包括那些正常瀏覽的人——全都看到 503 錯誤頁面。這個問題的根源是：系統沒有機制控制進入的流量。

**限流（Rate Limiting）** 就是解決這個問題的機制：它在請求進入後端之前設一道閘門，按照某種規則允許或拒絕請求，確保系統永遠不會被超出處理能力的流量打垮。

限流的本質很簡單：限制在一個時間窗口內，系統能處理的請求數量。超過上限的請求會被拒絕（返回 429 Too Many Requests）或排隊等待。這裡有兩個關鍵概念：**Rate（速率）** 是單位時間內允許通過的請求數，類比高速公路每個小時允許通過多少輛車；**Burst（突發容量）** 是系統短時間內能承受的最大超出量，類比高速公路匝道的 Metering 燈——短時間內可以放行一批車，但不能一直放。一個好的限流策略需要在兩者之間取得平衡：太嚴格，正常流量也被擋掉；太寬鬆，突發流量還是會壓垮系統。

限流在系統設計中有四個關鍵作用。第一是**保護後端資源**：每個請求都消耗 CPU、記憶體、網路頻寬或資料庫連線，限流確保後端永遠在安全的負載範圍內運作。第二是**防止惡意攻擊**：DDoS 攻擊的本質就是用大量請求癱瘓目標系統，限流是第一道防線；暴力破解登入密碼、大量註冊假帳號等惡意行為，也可以透過限流來控制。第三是**控制成本**：在雲端環境中，每一個請求都代表真金白銀的運算資源，限流等於給你的預算裝了保險絲。第四是**確保公平性**：多租戶系統中，限流可以確保每個租戶都拿到公平的配額，你用過的 GitHub API、Twitter API 都有 rate limit 就是這個道理。

限流可以部署在系統的不同層級：用戶端（減少網路請求但可被繞過）、API Gateway（最早擋住超量請求，集中管理）、負載均衡器（分散式部署）、個別服務（粒度最細但管理成本高）。實際生產環境中，最常見的做法是在 API Gateway 層做粗粒度的全局限流，再在個別服務做細粒度的限流，兩層防線互相補充。

限流有很多種具體的演算法：固定窗口計數器（Fixed Window Counter）在固定時間窗口內計數，超過上限就拒絕，但窗口邊界可能出現雙倍突發；滑動窗口計數器（Sliding Window Counter）改進版，用滑動時間窗口避免邊界問題；漏桶（Leaky Bucket）以固定速率流出，適合平滑流量；令牌桶（Token Bucket）以固定速率生成令牌，適合允許突發但需要控制長期速率的場景。下一課會深入比較 Token Bucket 和 Leaky Bucket 這兩種最經典的限流演算法。
