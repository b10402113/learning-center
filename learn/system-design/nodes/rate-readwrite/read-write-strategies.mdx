## Lesson

上一課我們學會了區分讀密集和寫密集系統。知道了系統的類型之後，下一步就是：怎麼設計才能讓它跑得好？不同的工作負載需要不同的設計策略。硬把讀密集的策略套在寫密集系統上，或者反過來，只會讓問題更嚴重。

**讀密集型系統的設計策略**有四大方向。第一是**重度快取**：把熱門資料從資料庫搬到更快的存取層（如 Redis、Memcached），讓大部分讀取請求根本不碰資料庫。快取可以部署在不同層級——應用層快取（速度最快但每個實例各存一份）、分散式快取（所有實例共用，最常見的選擇）、資料庫層快取（對應用透明但容量受限）、CDN 快取（適合靜態資源，距離用戶最近）。例如新聞網站，文章發布後快取層存儲文章內容和熱門文章列表，95% 的讀取請求從 Redis 返回，只有 5% 的冷門請求穿透到資料庫。第二是**讀取副本**：主資料庫負責寫入，多個從資料庫負責讀取，讀取請求被分散到多個副本。第三是**資料庫優化**：建立合適的索引（讀密集系統可以建立更多索引）、優化查詢語句、選擇適合的資料模型（反規範化 denormalization——用空間換時間，把常用資訊冗餘存儲以避免 JOIN）。第四是**CDN 分發**：對於靜態內容使用 CDN 將內容分發到全球邊緣節點，不僅速度更快，還大幅減輕源站壓力。

**寫密集型系統的設計策略**有五大方向。第一是**選擇高寫入吞吐量的資料庫**：Cassandra（分散式架構，寫入吞吐量可線性擴展，適合日誌、時序數據、IoT）、MongoDB（文檔模型，寫入不需要固定 schema，適合內容管理、即時數據）、Redis AOF 持久化（記憶體寫入，延遲極低，適合即時數據、計數器）。第二是**寫入分散 Sharding**：將資料分散到多台機器，每台機器只承擔一部分寫入壓力。例如按照用戶 ID 取模分片，每個 Shard 獨立處理寫入，整體寫入吞吐量等於所有 Shard 的總和。關鍵挑戰是選擇合適的分片鍵（shard key），避免熱點（hotspot）。第三是**非同步處理 Async Processing**：利用訊息佇列（如 Kafka、RabbitMQ）將非關鍵路徑的寫入延遲處理——用戶發送訊息後立即返回「已發送」，訊息進入佇列，後台消費者異步寫入資料庫。好處是使用者感知到的延遲降低，系統的寫入吞吐量可以水平擴展。第四是**批量寫入 Batch Write**：累積一批資料後一次性寫入，減少磁碟 I/O 次數和資料庫連線開銷，代價是增加少量延遲。第五是**資料庫寫入優化**：減少索引（每個索引都拖慢寫入速度）、使用 append-only 模型（資料只追加不修改，避免隨機寫入）、增大寫入批次。

面試中回答設計問題的模板：先判斷讀寫比例，再針對性選擇策略。例如「這是讀密集型系統——預估讀寫比 10:1。我的策略是：第一層用 CDN 分發靜態資源；第二層用 Redis 快取熱門資料；資料庫層使用讀取副本分散讀取壓力；索引建立在最常用的查詢欄位上。」或者「這是寫密集型系統——每秒寫入量達到 10,000 筆。我的策略是：使用 Cassandra 作為主資料庫；按用戶 ID 分片分散寫入壓力；非關鍵路徑的日誌通過 Kafka 異步寫入；減少索引數量以提升寫入速度。」
