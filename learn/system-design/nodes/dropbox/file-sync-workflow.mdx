# 檔案同步工作流程

## Learning goal
說明當用戶更新檔案後，同步機制如何將變更傳播到所有訂閱設備，處理離線情況與衝突。

## Lesson

### 場景：用戶 A 更新了一個共享檔案

假設用戶 A、B、C 共享一個資料夾。用戶 A 在筆電上修改了其中一個檔案。追蹤整個同步流程：A 的客戶端偵測變更，將檔案切成 4 MB 的分塊，比對本地元數據庫找出哪些分塊實際變了，只上傳這些分塊到雲端儲存。接著客戶端透過消息隊列的請求隊列向同步服務發送更新通知（包含新版本號、變更的分塊 ID）。同步服務從請求隊列拉取通知，更新元數據資料庫，然後將更新推送到 B 和 C 的響應隊列。B 和 C 的客戶端從各自的響應隊列中拉取更新，下載新的分塊，套用到本地檔案。

### 離線處理

如果 B 和 C 在 A 更新時不在线，更新通知留在各自的響應隊列中。當他們上線後，客戶端自動從響應隊列拉取所有待處理的更新，下載新分塊，套用到本地檔案。如果 A 在 B/C 離線期間又修改了，每次修改都產生新的版本，所有版本都記錄在元數據資料庫中。B/C 上線後會拉取所有中間版本。這就是為什麼需要消息隊列——它充當了離線設備的「收件匣」，確保更新不會丟失。

### 衝突解決

衝突發生在兩個用戶同時修改同一個檔案時。Dropbox 採用**「最後寫入者勝（Last-Writer-Wins）」**加上**保留衝突副本**的策略：兩個版本都上傳到雲端，系統保留兩個版本——一個是「衝突副本」（通常加上用戶名或時間戳作為檔名後綴），原始檔案保留最後一個成功上傳的版本，用戶手動決定保留哪個版本或合併。

為什麼不自動合併？因為檔案內容的合併很難自動化。文字檔案可以做行級合併（類似 Git），但圖片、影片、二進位檔根本無法自動合併。所以 Dropbox 選擇保留兩個版本，讓用戶自己決定。

### 版本控制

每次檔案修改都會產生一個新版本。元數據資料庫記錄了完整的版本鏈，用戶可以回滾到任何歷史版本。這也是元數據資料庫必須支援強一致性的原因之一——版本鏈不能出錯。
