# 需求分析與容量估算

## Learning goal
定義 Dropbox 類雲端儲存系統的功能與非功能需求，並完成容量估算。

## Lesson

### 為什麼需要雲端儲存？

過去我們把檔案存在單一電腦上。但現在一個人平均有三台設備——手機、筆電、平板——而且它們跑不同的作業系統。你需要在任何地方、任何時間存取同一份檔案。雲端儲存服務（如 Dropbox、Google Drive、iCloud）就是為了解決這個問題而誕生的。

設計這類系統的面試題，考的不只是「你知道哪些元件」，更是「你能不能在壓力下拆解需求、估算規模、做合理的取捨」。讓我們從需求開始。

### 功能需求

一個雲端儲存系統至少要做到這幾件事：

- **上傳/下載檔案**：用戶能從任何設備上傳和下載檔案
- **自動同步**：在一台設備上修改檔案後，其他設備自動同步更新
- **檔案分享**：用戶能將檔案或資料夾分享給其他用戶
- **檔案版本控制**：保留檔案的歷史版本，允許回滾
- **離線支援**：設備離線時仍能編輯，上線後自動同步

### 非功能需求

功能需求告訴系統「做什麼」，非功能需求告訴系統「做得多好」。雲端儲存系統的關鍵非功能需求包括：

- **可用性（Availability）**：系統要隨時可用，目標 99.99% 以上
- **可靠性（Reliability）**：上傳的檔案不能丟失或損壞
- **擴展性（Scalability）**：能處理從百萬到數億用戶的增長
- **一致性（Consistency）**：所有設備看到的檔案狀態要一致
- **效能（Performance）**：上傳/下載延遲要低，大檔案支援分塊傳輸

### 容量估算

面試中常見的估算場景：

| 指標 | 假設 |
| --- | --- |
| 總用戶數 | 5 億 |
| 日活用戶（DAU） | 1 億 |
| 每用戶平均設備數 | 3 台 |
| 每用戶平均檔案數 | 200 個 |
| 總檔案數 | 5 億 × 200 = 1,000 億個檔案 |
| 平均檔案大小 | 100 KB |
| 總儲存容量 | 1,000 億 × 100 KB = 10 PB |
| 每日新檔案/修改 | 100 萬次 |

這些數字不是考你算術，而是幫你決定後續設計的規模：10 PB 的儲存意味著不能用單一伺服器，必須分散儲存；100 萬次/天的寫入意味著需要高效的同步機制。

### 設計考量

在動手畫架構圖之前，有幾個關鍵取捨要先想清楚：

- **讀寫比**：雲端儲存的讀取和寫入量大致相當，不像社交媒體那樣讀遠大於寫
- **檔案分塊**：大檔案應該切成小塊（如 4 MB），這樣失敗時只需重傳一小塊，也能減少數據交換量
- **元數據與檔案分離**：檔案的實際內容（blob）和描述檔案的元數據（檔名、大小、版本、權限）應該分開儲存，方便獨立擴展
- **一致性模型**：強一致性代價高，最終一致性更實際——用戶修改檔案後，其他設備幾秒內看到更新即可
