# 核心元件設計

## Learning goal
詳細設計每個核心元件，說明其職責、互動方式與設計選擇取捨。

## Lesson

### 元件一：客戶端（Client）

客戶端是安裝在用戶設備上的應用程式，做三件事：監控工作區（持續監聽指定資料夾，偵測檔案變更）、分塊上傳（將變更的檔案切成 4 MB 的分塊逐塊上傳到雲端儲存）、以及維護本地元數據副本（用於快速比對哪些分塊需要同步）。

本地資料庫的存在有一個關鍵好處：**增量同步**。當用戶修改一個 100 MB 的檔案時，客戶端比對本地資料庫，發現只有第 3 個分塊變了，於是只上傳這一個分塊——而不是重新上傳整個檔案。客戶端有三種狀態：上線（即時同步）、離線（將變更記錄在本地隊列，等待上線後重播）、同步中（正在上傳/下載分塊，使用者看到進度條）。

### 元件二：元數據資料庫（Metadata Database）

元數據資料庫儲存所有檔案的描述資訊：檔案資訊（檔名、路徑、大小、建立/修改時間）、版本歷史（每個檔案的版本鏈，每個版本對應一組分塊 ID）、分塊索引（檔案由哪些分塊組成、每個分塊的雜湊值和儲存位置）、用戶資訊（帳號、設備列表、工作區設定）、以及共享與權限。

可以用關聯式資料庫（MySQL、PostgreSQL）或 NoSQL（DynamoDB）。關聯式適合複雜查詢和強一致性；NoSQL 適合高寫入吞吐和水平擴展。實際系統中可能混合使用：核心元數據走 MySQL（需要 ACID），分享/評論等社交功能走 NoSQL。

### 元件三：同步服務（Synchronization Service）

同步服務是整個架構最核心的元件，做三件事：從消息隊列的請求隊列中拉取客戶端的變更通知、將變更寫入元數據資料庫（新版本、新分塊索引）、以及將更新推送到響應隊列讓其他設備拉取。

客戶端使用**長輪詢（Long Polling）**得知有新更新：客戶端發送 HTTP 請求，服務端等到有新更新時才返回，而不是每秒輪詢一次。這比傳統輪詢更高效。

### 元件四：消息隊列（Message Queuing Service）

消息隊列是同步服務和客戶端之間的橋樑，有兩個通道。**請求隊列（Request Queue）**是全局共享的，所有客戶端往裡面寫更新通知；**響應隊列（Response Queue）**每個客戶端各一個，同步服務把屬於該客戶端的更新推送到這裡。消息隊列實現解耦（客戶端不需要直接連線同步服務）、可靠性（設備離線時更新不會丟失）、以及擴展性（可以水平擴展來處理更多客戶端）。

### 元件五：雲端/區塊儲存（Cloud/Block Storage）

儲存實際的檔案分塊，客戶端直接與雲端儲存互動上傳和下載。分塊的好處包括增量同步（只傳輸變更的分塊）、並行傳輸（多個分塊同時上傳/下載）、容錯（失敗只需重傳一個分塊）、以及去重（相同內容的分塊只存一份）。物件儲存（如 Amazon S3）是首選：幾乎無限擴展、低成本、高持久性。
