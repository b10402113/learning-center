# 高層級架構設計
## Learning goal
設計短網址與 Pastebin 服務的高層級架構，劃分應用層與儲存層職責，並比較兩種服務的架構異同。
## Lesson

有了資料模型之後，下一步是劃分系統組件並設計高層級架構。這一步不深入任何一個組件的內部實現，而是回答「系統由哪些部分組成？它們之間怎麼通訊？」。高層級架構是你在白板上畫的第一張圖，也是面試官評估你系統化思考能力的主要依據。

## 兩個服務的共同架構

無論是短網址還是 Pastebin，高層級架構都可以拆成兩層：應用層（Application Layer）和儲存層（Storage Layer）。

應用層包含一組無狀態的應用伺服器，負責處理所有讀寫請求。無狀態意味著任何一個伺服器都能處理任何請求，所以你可以輕易地水平擴展——加機器就行。應用伺服器前面放一個負載均衡器（Load Balancer），把流量分發到不同的伺服器。

儲存層則根據資料類型做分離：結構化的元資料存到資料庫（如 MySQL、PostgreSQL 或 NoSQL），大物件存到物件儲存（如 Amazon S3）。這種分離讓兩種資料各自有最佳的存取路徑。

## 短網址的資料流

**寫入流程：**
1. 使用者提交長網址到 `POST /shorten`
2. 負載均衡器把請求分發到一個應用伺服器
3. 應用伺服器生成短金鑰（用 KGS 或雜湊方式）
4. 寫入資料庫：`{shortKey, originalURL, createdAt}`
5. 回傳短網址給使用者

**讀取流程：**
1. 使用者點擊短網址，瀏覽器發出 `GET /{shortCode}`
2. 負載均衡器分發到一個應用伺服器
3. 應用伺服器用 `shortKey` 查詢資料庫，拿到 `originalURL`
4. 回傳 HTTP 301（永久重導向）或 302（暫時重導向）

301 和 302 的選擇是一個取捨：301 會讓瀏覽器緩存重導向，減少伺服器負載，但你無法追蹤點擊次數；302 不緩存，每次都會經過伺服器，方便做分析但負載較高。

## Pastebin 的資料流

Pastebin 的寫入流程比短網址多一步：內容的分離儲存。

**寫入流程：**
1. 使用者提交 paste 內容和元資料
2. 應用伺服器把元資料寫入資料庫
3. 應用伺服器把內容上傳到物件儲存（S3），拿到 `contentKey`
4. 把 `contentKey` 寫回資料庫的 paste 記錄
5. 回傳 paste URL 給使用者

**讀取流程：**
1. 使用者存取 paste URL
2. 應用伺服器用 `pasteKey` 查元資料
3. 用 `contentKey` 從 S3 拉取實際內容
4. 回傳給使用者

Pastebin 的讀取比短網址多一次儲存存取（S3），所以延遲可能稍高。這也是為什麼 Pastebin 特別強調快取的重要性——大內容的重複讀取非常浪費資源。

## 兩者的架構對比

| 組件 | 短網址 | Pastebin |
| --- | --- | --- |
| 應用層 | 無狀態伺服器 + 負載均衡 | 相同 |
| 元資料儲存 | NoSQL（大量、簡單查詢） | NoSQL 或關聯式 |
| 內容儲存 | 不需要（資料全在 DB） | S3 物件儲存 |
| 讀取流程 | 1 次 DB 查詢 | 1 次 DB + 1 次 S3 |
| 關鍵優化 | 快取（80/20 法則） | 快取 + CDN |

短網址的架構更簡單，因為所有資料都很小，一個資料庫就能搞定。Pastebin 因為內容大小差異巨大，必須把資料拆開，架構也就更複雜一些。

## 為什麼這個架構有效？

這個架構的核心優勢是<strong>分離關注點</strong>（Separation of Concerns）。應用層只管業務邏輯，不負責持久化細節；儲存層只管存取，不關心請求從哪來。每一層都可以獨立擴展：流量大了加伺服器，資料多了加儲存節點。這就是為什麼大多數成功的網路服務都採用類似的分層架構。
