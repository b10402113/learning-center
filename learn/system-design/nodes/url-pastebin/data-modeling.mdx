# 資料建模與金鑰生成
## Learning goal
掌握短網址與 Pastebin 服務的資料庫設計，以及各種短金鑰生成策略的優缺比較。
## Lesson

需求澄清完之後，下一步是把需求轉化成資料模型。資料庫的設計不只是「放什麼欄位」，它決定你的系統能不能擴展、查詢快不快、金鑰生成會不會撞車。這一步會從資料表結構開始，再深入討論短網址的核心問題：怎麼生成一個短且唯一的金鑰。

## 短網址的資料庫設計

短網址的資料有幾個特徵：需要儲存數十億筆記錄、每筆很小（< 1 KB）、記錄之間幾乎沒有關聯。這些特徵指向 NoSQL 儲存（如 DynamoDB、Cassandra 或 Riak），而不是傳統的關聯式資料庫。原因很簡單：NoSQL 天然支援水平擴展，而關聯式資料庫在數十億筆資料面前會遇到單點瓶頸。

核心資料表只需要三個欄位：

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| `shortKey` | string | 短網址的唯一金鑰（主鍵） |
| `originalURL` | string | 原始長網址 |
| `createdAt` | timestamp | 建立時間（用於過期清理） |

如果要支援使用者帳號，再加一個 `userID` 欄位。但核心的重導向查詢只需要根據 `shortKey` 拿到 `originalURL`，非常簡單。

## Pastebin 的資料庫設計

Pastebin 的資料結構稍微複雜。Paste 的元資料（metadata）很小，但內容（content）可能達幾 MB。把這兩種大小差異巨大的資料塞在同一個表裡不划算，所以 Pastebin 把元資料和內容分開儲存。

**元資料表：**

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| `pasteKey` | string | 短網址的金鑰（主鍵） |
| `contentKey` | string | 指向物件儲存中的內容 |
| `userID` | string | 建立者 |
| `createdAt` | timestamp | 建立時間 |
| `expireAt` | timestamp | 過期時間 |

**使用者表：**

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| `userID` | string | 使用者 ID |
| `userName` | string | 使用者名稱 |
| `email` | string | 電子郵件 |
| `apiDevKey` | string | API 開發者金鑰 |

內容本身存在物件儲存（如 Amazon S3）中，`contentKey` 是指向該物件的指標。這個設計把「查元資料」和「讀大檔案」拆成兩個獨立的存取路徑，各自可以獨立擴展。

## 金鑰生成策略

這是最關鍵的設計決策之一。你需要一個短且唯一的金鑰（通常是 6-8 個字元），不能太長（使用者不便輸入），也不能重複。

### 方案一：編碼實際網址

對網址做雜湊運算（如 MD5 或 SHA256），再用 Base62 編碼（`[a-z, A-Z, 0-9]`）截取前 6-8 個字元。Base62 編碼的 6 位金鑰有 62⁶ ≈ 568 億種組合，對大多数場景夠用。

**問題：** 不同的網址可能產生相同的雜湊值（雜湊衝突）。你需要在寫入時檢查是否已存在，如果衝突就用不同策略重新生成。此外，使用 MD5 有安全疑慮（已知碰撞攻擊），實際建議用 SHA256。

### 方案二：預生成金鑰服務（Key Generation Service, KGS）

單獨部署一個金鑰生成服務，事先生成大量隨機金鑰並存入資料庫。當需要新金鑰時，直接從「可用金鑰表」取一個，移入「已使用金鑰表」。這個方案完全避免了衝突，且速度極快——只需要一次簡單的查詢。

**問題：** KGS 本身是一個單點故障。如果 KGS 掛了，整個短網址服務就沒辦法產生新金鑰。解法是部署多個 KGS 實例，每個實例分配不同的金鑰範圍（range），即使一個掛了，其他的還能運作。

### 方案三：資料庫自增 ID

用資料庫的自增 ID（auto-increment）作為金鑰的基礎，再轉成 Base62 編碼。優點是保證唯一性，缺點是把金鑰生成的責任綁死在資料庫上，資料庫變成了瓶頸。

### 方案四： Multi-Server ID 生成

如果不想綁定單一資料庫，可以用多台伺服器各自維護一個 ID 範圍。例如伺服器 A 負責 1-1000 萬，伺服器 B 負責 1000 萬-2000 萬。但這個方案引入了伺服器之間的協調成本，且 ID 範圍用盡時需要動態分配。

## 如何選擇？

| 方案 | 唯一性保證 | 速度 | 單點故障 | 適用場景 |
| --- | --- | --- | --- | --- |
| 雜湊 + Base62 | 需碰撞處理 | 快 | 無 | 中小規模 |
| 預生成 KGS | 完全保證 | 極快 | 有（需多實例） | 大規模、高可用 |
| DB 自增 ID | 完全保證 | 中等 | 有（資料庫瓶頸） | 小規模原型 |
| Multi-Server ID | 完全保證 | 快 | 低 | 大規模、分散式 |

在面試中，推薦預生成 KGS 方案——它在大規模場景下表現最好，且能展示你對分散式系統的理解。把衝突處理、唯一性保證和可用性講清楚，就已經比大多數候選人強了。
