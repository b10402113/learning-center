# 索引如何運作

## Learning goal

理解索引背後常見的資料結構（B-tree、雜湊索引）以及它們如何實現快速查找。

## Course

[↗ 課程頁面](../../lessons/how-indexes-work.html)

## Lesson

上一課說索引用額外空間換取查詢速度，但索引底層到底是什麼資料結構？為什麼它能做到 O(log n) 甚至 O(1) 的查找？

### 為什麼不是排序陣列？

最直覺的索引方式是把資料排好序存在陣列裡，用二分查找找目標——O(log n)。但有一個致命問題：**插入和刪除太慢**。在有序陣列中插入一個新元素，要把後面所有元素往後移動一位，O(n)。如果每天幾百萬筆寫入，這種方案根本不可行。資料庫需要一種既能快速查找、又能高效插入刪除的結構——這就是 B 樹被選為預設索引結構的原因。

### B 樹與 B+ 樹

B 樹是一種**平衡多路搜索樹**。「平衡」意味著所有葉子節點在同一層，查找路徑長度一致；「多路」意味著每個節點可以有多個子節點，所以樹的高度很低。為什麼高度很重要？因為資料庫索引通常存在磁碟上，**每一層節點對應一次磁碟讀取**。一棵 3 層的 B 樹，查找時最多只需 3 次磁碟讀取——哪怕底下有幾億筆資料。

B+ 樹是 B 樹的改進版，也是絕大多數關聯式資料庫（MySQL InnoDB、PostgreSQL）實際使用的索引結構。它做了兩個關鍵改進：

1. **資料只存葉子節點**：非葉子節點只存索引鍵（導航路標），不存實際資料。每個非葉子節點能塞更多鍵，樹更矮，查找更快。
2. **葉子節點用鏈表串聯**：所有葉子節點串成有序鏈表，範圍查詢（如 `WHERE age BETWEEN 20 AND 30`）可以直接沿鏈表掃描，不用回到樹的上層。

用類比來說：B 樹像一本書的正文——每一頁都有內容。B+ 樹像目錄 + 正文——目錄只有標題和頁碼（導航），正文全在最後的頁面裡，而且頁面之間有裝訂線可以順序翻閱。

### 雜湊索引

雜湊索引用完全不同的思路：對索引鍵做雜湊運算（Hash Function），直接算出資料的存放位置。等值查詢的時間複雜度可以達到 O(1)——比 B+ 樹的 O(log n) 更快。但雜湊索引有嚴重限制：不支援範圍查詢（`WHERE age > 20`）、不支援排序（`ORDER BY`）、可能發生碰撞。所以它只適用於純等值查詢的場景，例如 Redis 這類記憶體資料庫。

### 查找效率對比

- **全表掃描**：等值查詢 O(n)，範圍查詢 O(n)
- **B+ 樹**：等值查詢 O(log n)，範圍查詢 O(log n + k)，排序直接利用葉子鏈表
- **雜湊索引**：等值查詢 O(1)，範圍查詢不支援，排序不支援

B+ 樹是大多數場景的最佳選擇，因為它兼顧了查找、範圍查詢和排序。雜湊索引只在純等值查詢的記憶體場景中有優勢。
