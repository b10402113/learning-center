# 會話持久化：IP Hash

## Learning goal
理解 IP Hash 演算法如何實現會話持久化，其工作原理、範例、優缺點與適用場景

## Lesson

前面介紹的演算法（Round Robin、Least Connections 等）都有一個共同前提：每次請求可以被任意分配到任何一台後端伺服器。但有些應用場景需要「同一個用戶的請求始終打到同一台伺服器」，這就是<strong>會話持久化（Session Persistence）</strong>的核心需求。

### 為什麼需要會話持久化？

典型的例子是購物車。用戶把商品加入購物車後，這個購物車的資料可能暫存在後端伺服器的記憶體裡。如果下一個請求被負載均衡器分到了另一台伺服器，新伺服器找不到購物車資料，用戶的購物車就「消失」了。Session persistence 透過確保同一客戶端的請求總是路由到同一台伺服器，避免了這類問題。

實現會話持久化有幾種方式：Session Stickiness（負載均衡器記住 session ID 直接路由）、外部 Session Store（把 session 存在 Redis 等共享儲存裡），以及 IP Hash。

### IP Hash 的工作原理

IP Hash 是最簡單的會話持久化實現方式。它的做法是：

1. 負載均衡器取得客戶端的 IP 地址
2. 用一個雜湊函數（hash function）把 IP 地址轉換成一個雜湊值
3. 用雜湊值對伺服器數量取模，決定路由到哪台伺服器

假設有三台伺服器 S0、S1、S2，客戶端 IP 是 192.168.1.10：

```
hash("192.168.1.10") % 3 = 2  → 路由到 S2
```

因為同一個 IP 會產生同一個雜湊值，所以同一個客戶端的每次請求都會被路由到同一台伺服器，實現了會話持久化。

### 優缺點分析

IP Hash 的優點很明確：

| 優點 | 說明 |
| --- | --- |
| 實作簡單 | 只需要一個雜湊函數，無需額外的狀態管理 |
| 無需額外儲存 | 不需要像 Session Stickiness 那樣在負載均衡器上維護 session 表 |
| 天然持久化 | 同一 IP 自動路由到同一伺服器 |

缺點也不少：

| 缺點 | 說明 |
| --- | --- |
| 負載不均 | 如果某個 IP 背後有大量用戶（例如公司出口 IP），該伺服器會過載 |
| IP 變化 | 手機切換 WiFi/4G、NAT 後方的用戶 IP 會變，導致 session 中斷 |
| 不考慮負載 | 不管伺服器當前負載如何，同 IP 的請求永遠導到同一台 |

### 適用場景

IP Hash 適合**需要會話持久化但不想引入外部 Session Store**的場景。一個常見的組合是：把 IP Hash 用在**登入後的 API 服務**，因為登入態通常由 token（如 JWT）管理，session persistence 主要解決的是短暫的本地快取或速率限制的問題。

如果伺服器異質或負載波動大，IP Hash 不是最佳選擇——它不考慮伺服器容量。這時候更好的做法是用 IP Hash 作為一級路由，再在伺服器內部用 cookie 或 token 來做更精細的 session 管理。總之，IP Hash 是一個「夠用但不完美」的方案，在不需要引入外部儲存時可以考慮，但生產環境中更推薦用 Redis 等外部 Session Store 配合任何一種負載均衡演算法。
