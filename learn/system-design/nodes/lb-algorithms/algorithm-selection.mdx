# 演算法選擇與取捨

## Learning goal
能夠依據不同的系統環境（同源還是異構、靜態還是動態負載、是否需要會話持久化）選擇合適的負載均衡演算法

## Lesson

前面介紹了五種主要的負載均衡演算法：Round Robin、Weighted Round Robin、Least Connections、Weighted Least Connections 和 IP Hash。在實際的系統設計中，你不會只記得它們的定義，更要能根據場景條件做出選擇。

### 選擇維度一：伺服器是否同質？

**同質伺服器**（所有伺服器硬體規格相同）是一個關鍵前提。如果伺服器是同質的，Weighted 系列的演算法就失去了意義，因為權重差異不存在。

- 同質 + 請求處理時間相近 → Round Robin（最簡單，開銷最小）
- 同質 + 請求處理時間差異大 → Least Connections（根據即時負載動態調整）

### 選擇維度二：負載是否穩定？

「負載穩定」指每台伺服器在任何時刻承受的壓力大致相同。如果負載波動大（例如某些時段會有尖峰），靜態演算法就無法及時應對。

- 負載穩定 + 異質伺服器 → Weighted Round Robin（手動設定權重即可）
- 負載波動大 + 異質伺服器 → Weighted Least Connections（自動平衡）

### 選擇維度三：是否需要會話持久化？

如果你的應用需要「同一用戶始終路由到同一台伺服器」（例如購物車、登入態等），你需要在上述演算法之外額外考慮 IP Hash 或其他持久化機制。IP Hash 提供最簡單的持久化，但會導致負載不均。更好的做法是用外部 Session Store（如 Redis）配合任何一種負載均衡演算法。

### 決策速查表

| 場景條件 | 推薦演算法 |
| --- | --- |
| 同質伺服器 + 請求處理時間相近 | Round Robin |
| 同質伺服器 + 請求處理時間差異大 | Least Connections |
| 異質伺服器 + 負載穩定 | Weighted Round Robin |
| 異質伺服器 + 負載波動大 | Weighted Least Connections |
| 需要會話持久化 | Weighted Least Connections + 外部 Session Store |

### 面試中的應用

在系統設計面試中，負載均衡演算法的選擇通常是一個「順帶討論」的小環節，但它能體現你的全面性。當你畫出架構圖標註了 Load Balancer 時，面試官可能會問「你會選什麼演算法？」這時候不要只回答「Round Robin」，而是要反問或補充：

1. 伺服器是同質的嗎？→ 決定是否需要 Weighted
2. 請求處理時間差異大嗎？→ 決定是否需要 Least Connections
3. 需要會話持久化嗎？→ 決定是否需要 IP Hash 或外部 Session Store

一個完整的回答能把一個簡單的「選 Round Robin」變成一個展示系統設計思維的亮點。

### 補充：現今生產環境的趨勢

大多數現今的負載均衡器（如 Nginx、HAProxy、AWS ALB）預設使用 Least Connections 或 Weighted Least Connections 的變體，因為它們在多數場景下表現最佳。Round Robin 仍然被廣泛使用，但主要是在**無狀態、短請求**的場景（例如 CDN 的邊緣節點）。在面試和生產環境中，了解這些演算法的區別比死記定義更重要——關鍵是能根據場景條件做出合理的選擇並說出理由。
