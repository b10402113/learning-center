# 靜態演算法：Weighted Round Robin

## Learning goal
理解 Weighted Round Robin 如何改進 Round Robin，其權重分配機制、優缺點與適用場景

## Lesson

Round Robin 有一個明顯缺點：它不考慮後端伺服器的性能差異。如果後端伺服器有不同的硬體規格（比如一台是 8 核 16GB 記憶體，另一台是 2 核 4GB），Round Robin 仍然會給兩台伺服器分配同樣數量的請求，這會導致性能差的伺服器過載，而性能好的伺服器資源閒置。

### Weighted Round Robin 的工作原理

Weighted Round Robin（加權循環分配）在 Round Robin 的基礎上加入了<strong>權重（weight）</strong>。權重越高的伺服器，分配到的請求越多。例如三台伺服器 S0（權重 5）、S1（權重 3）、S2（權重 2），總權重是 10。10 個請求的分配結果是：

| 伺服器 | 權重 | 分配到的請求數 |
| --- | --- | --- |
| S0 | 5 | 5 個（佔 50%） |
| S1 | 3 | 3 個（佔 30%） |
| S2 | 2 | 2 個（佔 20%） |

性能越好的伺服器承擔越多請求，集群整體資源利用率更高。

### 兩種實作方式

實作上有順序輪詢和平滑加權兩種常見方法。順序輪询按照權重比例重複列出伺服器順序再循環，例如生成序列 [S0, S0, S0, S0, S0, S1, S1, S1, S2, S2]。這種方式簡單，但分配不夠平滑——可能連續 5 個請求都打到 S0。

平滑加權輪詢（Smooth Weighted Round Robin）是 Nginx 使用的演算法。每次分配後更新權重，讓分配更均勻。S0 的 5 個請求不會連續打到 S0，而是分散在整個序列中，實測效果明顯優於順序輪询。

### 優缺點分析

Weighted Round Robin 保留了 Round Robin 實作簡單、開銷小的優點，同時解決了性能異質的問題，但仍然沒有解決「不考慮即時負載」這個根本缺點：

| 優點 | 說明 |
| --- | --- |
| 保留 Round Robin 的簡單性 | 不需要收集伺服器即時狀態 |
| 按容量分配 | 性能好的伺服器承擔更多請求 |
| 靈活可調整 | 新增或移除伺服器只需更新權重 |

| 缺點 | 說明 |
| --- | --- |
| 不考慮即時負載 | 伺服器當下忙不忙，它不知道 |
| 權重需要手動維護 | 伺服器性能變化時需要更新權重 |

### 適用場景

- **異質伺服器集群**：新舊伺服器混用、不同規格的伺服器
- **可預測的負載模式**：伺服器性能差異穩定，不需要即時調整
- **資料庫集群**：不同節點有不同的處理能力，但查詢負載相對穩定
- **混合使用新舊伺服器的生產集群**：新伺服器性能更好，權重自然更高

### 面試中的應用

Weighted Round Robin 是從 Round Robin 自然延伸的討論。當面試官問「如果伺服器性能不同怎麼辦？」時，回答 Weighted Round Robin 就是標準答案。然後再追問：「但如果有即時負載波動，該怎麼辦？」——這就自然過渡到 Least Connections 或 Weighted Least Connections。這種層層遞進的討論方式比直接給出最終答案更能展現你的系統設計思維。記住，面試中考的不只是「你知不知道答案」，更是「你能不能在壓力下做出合理的取捨分析」。
