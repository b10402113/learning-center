# 即時通訊模式比較
## Learning goal
理解並比較 Polling、Long Polling、Server-Sent Events (SSE) 與 WebSocket 這幾種常見即時通訊模式的運作原理、優缺點與適用場景
## Lesson

在分散式系統中，客戶端與伺服器之間的通訊模式選擇直接影響延遲、資源消耗和使用者體驗。面試中被問到「怎麼設計即時通知系統」或「怎麼讓多個客戶端同步更新」時，你需要在幾種通訊模式之間做出正確的取捨。

最直覺的做法是客戶端每隔幾秒問一次伺服器「有新資料嗎？」——這就是 **Polling（輪詢）**。客戶端每隔固定時間發一次 HTTP 請求，伺服器有新資料就回傳，沒有就回傳空的響應。實現簡單、所有瀏覽器都支援，但大量空請求造成 HTTP 開銷，延遲等於輪詢間隔。適用於對即時性要求不高的場景，如定期刷新的儀表板。

**Long Polling（長輪詢）** 是 Polling 的改良版。客戶端發出請求後，如果伺服器沒有新資料，不會立即回應空的，而是 hold 住這個連線，等到有新資料時才回應。回應後客戶端再發一個新請求，重複這個過程。比 Polling 減少空請求，伺服器主動推送資料，但每個客戶端都佔用一個持久連線，伺服器資源消耗大。適用於中等即時性需求，如通知系統。

**SSE（Server-Sent Events，伺服器推送事件）** 是一種伺服器單向推送的機制。客戶端與伺服器建立一個持久的 HTTP 連線，伺服器可以主動把新資料推給客戶端，但客戶端不能透過這條連線向伺服器發資料。基於 HTTP 協議，易於穿越防火牆，支援自動重連，延遲低。但只能伺服器→客戶端單向，連線數量受限（HTTP/1.1 下瀏覽器限制）。適用於單向即時推送，如股票行情、新聞推送。

**WebSocket** 提供全雙工（Full Duplex）通訊。客戶端透過一個 HTTP 握手過程將連線升級為 WebSocket 連線，之後雙方都可以隨時主動發送資料，不受「誰先請求」的限制。延遲最低、連線 overhead 低（無重複 HTTP header），但實現複雜度高，需要處理連線管理、斷線重連，某些代理/防火牆可能阻擋。適用於雙向即時通訊，如聊天室、多人遊戲、協作編輯。

選擇哪種模式取決於三個問題：第一，需要雙向通訊嗎？只需要伺服器推資料選 SSE，需要雙向選 WebSocket。第二，對延遲的容忍度？延遲敏感（如遊戲、聊天）用 WebSocket，延遲不敏感可以用 Long Polling。第三，客戶端數量和伺服器資源？大量客戶端用 SSE 或 WebSocket（連線數少），少量客戶端 Long Polling 也可以接受。
