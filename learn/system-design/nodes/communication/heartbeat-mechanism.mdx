# Heartbeat 存活偵測機制
## Learning goal
理解 Heartbeat 機制如何檢測節點存活、維護連線狀態，並認識常見實作考量
## Lesson

在分散式系統中，工作和資料分散在多台伺服器上。為了有效地路由請求，伺服器需要知道哪些伺服器還活著。更關鍵的是，當某台伺服器掛掉時，系統要能快速偵測到並把它的負載轉移給其他伺服器。

**Heartbeat（心跳）** 是一種定期發送的短訊息，用來告知其他節點「我還活著」。就像你每分鐘拍一下胸口說「我還在呼吸」——如果某次沒拍了，就知道出事了。

具體來說，每台伺服器會定期（例如每 5 秒）向其他節點發送 heartbeat 訊息。在有中心節點的架構中，所有伺服器向中心監控伺服器發送 heartbeat，中心伺服器追蹤所有節點的 heartbeat，超時未收到就判定為故障。在無中心節點的去中心化架構中，每個節點隨機選擇一組其他節點發送 heartbeat，每個節點追蹤它負責的節點，超時未收到就判定為故障。

運作流程以有中心節點的架構為例：正常運作時，每台伺服器每 5 秒向中心伺服器發送一次 heartbeat，中心伺服器記錄「上一次收到 Server A 的 heartbeat 是 10:00:30」。故障偵測時，如果中心伺服器在 15 秒內沒有收到 Server A 的 heartbeat，就判定 Server A 可能掛了。故障處理時，中心伺服器把 Server A 從可用列表中移除，將原本送往 Server A 的請求轉發給其他伺服器。恢復處理時，如果 Server A 重新啟動，它會再次發送 heartbeat，中心伺服器會把它加回可用列表。

關鍵設計參數包括：Heartbeat 間隔太短（如 100ms）會消耗大量頻寬和 CPU，太長（如 60 秒）會導致故障偵測延遲，常見選擇是 1~10 秒。超時閾值通常是 heartbeat 間隔的 3~5 倍，太短會造成誤判（網路暫時延遲被當成故障），太長會延遲故障偵測。心跳內容通常只包含節點 ID 和時間戳，但也可以捎帶輕量資訊如負載狀態、節點角色。

Heartbeat 與 Ping 的主要區別在於方向：Heartbeat 由被監控節點主動發送「我活著」，Ping 由監控方主動詢問「你活著嗎？」實務上很多系統兩者並用：Heartbeat 用於日常存活偵測，Ping 用於深入的健康檢查。
