# 擴展與容錯設計

## 學習目標
掌握即時通訊系統如何透過資料分片、快取、負載均衡與複製來實現擴展與容錯。

## Lesson

前面的設計可以撐住幾百萬用戶，但要撐住 5 億日活用戶，你需要三把利器：**分片（Partitioning）、快取（Caching）、負載均衡（Load Balancing）**。

**資料分片**的目標是將 3.6 PB 的數據分散到多台機器。最直覺的做法是對 UserID 做 hash，hash 值決定數據在哪台機器上，好處是同一個用戶的所有訊息都在同一台機器上。假設每台資料庫分片承載 4 TB，五年 3.6 PB 需要約 900 個分片。分片的挑戰包括熱點（某些用戶訊息量特別大，如名人）、跨分片查詢（兩個不在同一分片的用戶的聊天記錄需跨機器）、再平衡（新增或移除分片時的數據遷移開銷）。

**快取**的目標是讓用戶打開對話時，最近的訊息從記憶體讀取，延遲從百毫秒降到個位數毫秒。策略是快取每個活躍對話最近 15 條訊息，對每個用戶快取最近 5 個對話的最近 15 條訊息。因為數據按 UserID 分片，每個用戶的快取也應該在同一台快取伺服器上。新訊息到達時的快取更新有 Write-through（寫入資料庫同時更新快取，一致性好但寫入延遲增加）和 Write-behind（先更新快取、資料庫異步更新，寫入快但有短暫不一致）兩種策略，即時通訊通常選 Write-behind。

**負載均衡**分兩層。Chat Server 層的負載均衡需要**一致性雜湊（Consistent Hashing）**，因為 Server 記住了用戶連線，同一用戶的請求必須落到同一台 Server，一致性雜湊在節點增減時只影響少量映射。資料庫層的負載均衡相對簡單——根據 UserID 的 hash 決定路由到哪個分片，是確定性的。

**容錯設計**覆蓋三個場景。Chat Server 宕機時，客戶端偵測到連線斷開後自動嘗試連線到其他可用的 Chat Server——不要嘗試遷移 TCP 連線，那極其複雜。資料庫故障時，每個分片有主從副本，主節點故障時從節點提升為主節點，讀取走從節點也分散了負載。訊息可靠性透過端到端確認（B 收到訊息後回 ACK，A 沒收到 ACK 就重發）、客戶端重試、持久化保障（訊息先寫入資料庫或 WAL 再推送給用戶）來確保不丟。
