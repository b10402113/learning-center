<LearningGoal>
能夠為 Twitter 生產環境設計複製架構、容錯機制、多層次負載均衡與關鍵指標監控。
</LearningGoal>

## Lesson

單點故障是生產環境的大忌。Twitter 是全球性服務，任何一台機器故障都不能影響使用者體驗。複製和冗餘是容錯的基礎。

資料庫複製方面，每個分片配置一個主節點和多個從節點。所有寫入先到主節點，讀取請求分散到從節點。主節點故障時，從節點可以提升為新的主節點（failover）。主從複製是異步的，從節點可能有短暂延遲——在讀取密集型系統中，這種短暂不一致是可接受的。

負載均衡在 Twitter 架構中出現在三個層級。第一層在客戶端和應用伺服器之間，初期可以用 Round Robin，如果伺服器規格不同或請求處理時間差異大，可以改用 Least Connections。第二層在應用伺服器和資料庫從節點之間，確保讀取負載均勻。第三層在聚合伺服器和快取伺服器之間。負載均衡器本身也要冗餘——部署兩個負載均衡器，一主一備，用 VIP 或 DNS 輪詢實現切換。

監控是生產環境的眼睛。關鍵指標包括：每日/每秒新推文數（寫入負載）、時間軸遞送統計（每秒遞送多少推文）、推文延遲（從發布到追蹤者可見的時間）、快取命中率（低於 80% 要警示）、錯誤率（超過 1% 要警示）、伺服器健康度（CPU/記憶體/磁碟使用率超過 85% 要警示）。常用工具包括 Prometheus（收集指標）、Grafana（視覺化）、ELK Stack（日誌分析）、AlertManager（警報）。

整個 Twitter 設計從需求到生產環境的決策鏈是：讀取密集 → 多層快取和複製 → 按 UserID 分片加熱點處理 → 混合時間軸模型 → 三層負載均衡加全面監控。面試結尾時，面試官問「還有哪些進階議題」，你可以提 CAP 定理、機器學習推薦、CDN 策略等，展示你對系統的全面思考。
