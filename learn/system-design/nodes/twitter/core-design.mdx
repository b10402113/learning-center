<LearningGoal>
能夠定義 Twitter 系統的核心 API，繪製高層架構，並設計適合的資料庫綱要。
</LearningGoal>

## Lesson

需求釐清之後，下一步是定義系統的 API、繪製高層架構、設計資料庫綱要。API 是系統的合約——明確了系統提供什麼功能、需要什麼輸入、回傳什麼輸出。

Twitter 的核心 API 包括：發推文（`tweet`），需要 API key、推文內容、可選的位置和媒體 ID；讀取時間軸（`getTimeline`），支援游標分頁（`since_id` 增量載入、`max_id` 向前翻頁）；以及追蹤/取消追蹤。API 設計時要區分必填和可選參數——例如位置資訊不是每條推文都需要。

高層架構方面，由於讀取量是寫入的 280 倍，架構的重心放在讀取路徑的優化。核心組件包括：客戶端（Web/App/SMS）、負載均衡器、應用伺服器、聚合伺服器、快取層、資料庫。寫入流程是客戶端 → 負載均衡器 → 應用伺服器 → 寫入資料庫主節點 → 複製到從節點。讀取流程是客戶端 → 負載均衡器 → 應用伺服器 → 先查快取 → 快取未命中則查聚合伺服器 → 從多個分片讀取並合併。

資料庫綱要分四張核心表：User 表（user_id、name、email）、Tweet 表（tweet_id、user_id、tweet_text、media_url、created_at）、Follow 表（followee_id、follower_id）、Favorite 表（tweet_id、user_id）。追蹤關係是圖形結構，用關聯式資料庫的 JOIN 查詢效率不高。實務上 Twitter 使用混合方案：MySQL 儲存推文和使用者資料，Memcache/Redis 快取熱門資料，圖形資料庫或自訂結構儲存 social graph。

資料庫綱要的設計會直接影響後續的分片策略。按 UserID 分片讓查詢某使用者的推文很快，但熱門使用者會造成熱點；按 TweetID 分片讓推文均勻分散，但查詢某使用者的推文需要跨多台機器。這些取捨在下一步深入討論。
