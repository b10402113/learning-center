資料庫設計

Step 3/6 · Ticketmaster 系統設計 · 約 12 分鐘

學習目標

設計 Ticketmaster 系統的關聯式資料庫結構，理解城市、影院、電影、場次、座位與訂單之間的實體關係。

先觀察數據的自然結構

在設計資料庫之前，先想清楚這個系統裡有哪些「東西」（實體），以及它們之間有什麼關係。訂票系統的數據結構有很清晰的層級關係：

城市 → 影院 → 大廳 → 場次 → 座位
                     ↘
                      電影

一個城市有多家影院，一家影院有多個大廳，一個大廳在不同時間有不同的場次，每個場次有多個座位。同時，一個電影可以在多家影院的多個場次中放映。

核心實體與資料表

City（城市）

欄位類型說明
IDINT, PK城市唯一識別碼
NameVARCHAR城市名稱

Cinema（影院）

欄位類型說明
IDINT, PK影院唯一識別碼
NameVARCHAR影院名稱
CityIDINT, FK所屬城市

Movie（電影）

欄位類型說明
IDINT, PK電影唯一識別碼
TitleVARCHAR電影名稱
DurationINT片長（分鐘）

Show（場次）

欄位類型說明
IDINT, PK場次唯一識別碼
CinemaIDINT, FK所屬影院
MovieIDINT, FK播放電影
ShowTimeDATETIME放映時間

Booking（訂單）

欄位類型說明
IDINT, PK訂單唯一識別碼
UserIDINT, FK用戶 ID
ShowIDINT, FK場次 ID
NumberOfSeatsINT訂購座位數
TimestampDATETIME訂單建立時間
StatusENUMReserved / Booked / Cancelled

Seat（座位）

欄位類型說明
IDINT, PK座位唯一識別碼
ShowIDINT, FK場次 ID
SeatNumberVARCHAR座位號（如 A1、B3）
StatusENUMAvailable / Reserved / Booked

關係說明

  • City 1:N Cinema — 一個城市有多家影院
  • Cinema 1:N Show — 一家影院有多個場次
  • Movie 1:N Show — 一部電影有多個場次
  • Show 1:N Seat — 一個場次有多個座位
  • Show 1:N Booking — 一個場次有多筆訂單
  • Booking N:1 User — 一個用戶有多筆訂單

為什麼用關聯式資料庫？

訂票系統有強一致性需求（不能超賣、不能重複訂座），關聯式資料庫的 ACID 事務特性恰好能保證這一點。NoSQL 在這裡不適合，因為我們需要跨表的原子性操作。

面試技巧

資料庫設計是面試中的加分項。畫出 ER 圖（實體關係圖），清楚標註主鍵和外鍵，能展示你對數據建模的理解。記住：從實體開始，找關係，定約束。
