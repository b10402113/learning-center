冗餘負載均衡設計

system-design · load-balancing · Step 4/4

學習目標

理解如何解決負載均衡器本身的單點故障問題，掌握冗餘叢集的設計方法。

問題：負載均衡器本身就是單點故障

負載均衡器解決了後端伺服器的單點故障問題，但它自己也是一個伺服器——如果它掛了，所有流量都進不來，整個系統就會對外中斷。這就像餐廳領班請假了，新客人進來沒人接待，所有服務生都閒著也沒用。

這就是單點故障（Single Point of Failure，SPOF）：系統中有一個元件，一旦它故障，整個系統就無法運作。負載均衡器位於流量入口，它的單點故障影響範圍最大。

三種冗餘設計模式

主-備架構（Active-Standby）

最簡單的冗餘方式：準備两台負載均衡器，一台是主（Active），負責處理所有流量；另一台是備（Standby），平時閒著，但持續監控主 LB 的健康狀態。一旦主 LB 掛了，備 LB 自動接管。

正常狀態：
  用戶端 → 主 LB → 後端伺服器
          備 LB（待命，監控主 LB）

故障轉移：
  用戶端 → 備 LB → 後端伺服器
          主 LB（故障）

優點：實現簡單，容易理解，故障轉移邏輯清晰。

缺點：備 LB 平時閒著，資源利用率低（50% 的硬體在睡覺）。而且故障轉移時可能有短暫的服務中斷。

主-主架構（Active-Active）

两台 LB 同時處理流量，各自分擔一部分。每台都監控對方的健康狀態，一旦某台掛了，另一台自動接管所有流量。

正常狀態：
  用戶端 → LB-1 → 後端伺服器（一半流量）
  用戶端 → LB-2 → 後端伺服器（一半流量）

故障轉移：
  用戶端 → LB-1 → 後端伺服器（全部流量）
          LB-2（故障）

優點：資源利用率高（两台都在工作），故障轉移更無縫（因為本来就在處理流量）。

缺點：架構複雜，需要處理两台 LB 之間的會話同步（例如用戶的 session 資料要同步），否則故障轉移時用戶會被登出。

Anycast 路由

Anycast 是一種網路路由技術：让多台 LB 宣告同一個 IP 位址，BGP 路由協定會自動把用戶端導到網路距離最近的 LB。如果某台 LB 故障，BGP 會自動重新路由到下一個最近的 LB。

台北用戶 → Anycast IP → 台北 LB
東京用戶 → Anycast IP → 東京 LB
倫敦用戶 → Anycast IP → 倫敦 LB

優點：自動容錯（BGP 自動重新路由）、就近服務使用者（降低延遲）、不需要額外的故障偵測機制。

缺點：需要大型網路基礎設施，通常只有大型廠商（如 Google、Cloudflare）才用得起。

冗餘設計的注意事項

不管選哪種模式，設計冗餘架構時需要注意三個關鍵問題：

問題 什麼是它 怎麼解決
會話一致性 用戶的 session 資料在多台 LB 之間同步 Session affinity 或外部 Session Store（如 Redis）
節點健康檢查 LB 之間互相偵測對方是否正常 Heartbeat（心跳）機制，定期交換健康狀態
配置同步 多台 LB 的路由規則保持一致 共享配置儲存或自動同步機制

實際案例

大型系統通常會組合使用多種冗餘模式。例如：

  • Cloudflare：使用 Anycast 在全球多個資料中心部署 LB，每個資料中心內部再用主-主架構
  • 大型電商：通常使用主-主架構，因為流量大、不能有任何中斷
  • 中小型服務：主-備架構通常就夠了，簡單且成本低

面試中的關鍵

在面試中，當你提到負載均衡時，面試官很可能會追問：「那負載均衡器 itself 掛了怎麼辦？」這時候你需要能解釋：

  • 負載均衡器本身也是單點故障
  • 解決方案是冗餘叢集（主-備、主-主、Anycast）
  • 不同方案的取捨（簡單 vs 效率 vs 成本）

這展示了你不只會加 LB，還會考慮 LB 本身的可靠性——這是系統設計面試中加分的關鍵思維。

小結

負載均衡器本身也是單點故障，需要透過冗餘設計來解決。三種常見模式：主-備架構簡單但資源利用率低；主-主架構效率高但複雜；Anycast 適合大型廠商。設計時要注意會話一致性、健康檢查和配置同步。面試中要能主動指出 LB 的單點故障問題並提出解法。
