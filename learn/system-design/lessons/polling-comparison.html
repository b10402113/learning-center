通訊模式比較：Polling vs LongPolling vs WebSockets vs Webhooks

system-design · arch-patterns · Step 5/5

學習目標

比較不同的客户端-服務器通訊模式，理解各自的延遲、資源消耗和適用場景。

四種「問答」方式

想像你要知道某個網站有沒有新文章：

  • Polling：你每 5 分鐘刷新一次頁面，看有沒有新文章。
  • Long-Polling：你發送一個請求，如果沒有新文章，伺服器不回覆，一直等到有新文章才回覆。
  • WebSockets：你跟網站建立一條「專線」，有新文章時網站主動推給你，不用你問。
  • Webhooks：你告訴網站「有新文章時打電話給我」，網站有新文章時主動通知你的伺服器。

四種模式的核心差異在於：誰主動問、多久問一次、能不能即時收到。

Polling（輪詢）

Polling 是最簡單的方式：客戶端定期向伺服器發送 HTTP 請求，問「有新資料嗎？」伺服器立即回覆，不管有沒有新資料。

客戶端 ──每5秒──→ 伺服器：「有新資料嗎？」
客戶端 ←──立即──── 伺服器：「沒有」或「有，資料在這裡」
面向 Polling
連線方式 重複的短 HTTP 請求，固定間隔
資料傳遞 延遲——新資料在下次請求時才收到（拉取模式）
資源消耗 高——即使沒有新資料，也要不斷發送請求
適合場景 更新不頻繁、不需要即時性的應用

舉例：一個天氣應用每 10 分鐘 Polling 一次天氣資料。雖然不即時，但天氣本來就不會每秒鐘變化，所以夠用。

Long-Polling（長輪詢）

Long-Polling 是 Polling 的聰明改良版：客戶端發送請求後，如果伺服器沒有新資料，不立即回覆，而是hold 住連線直到有新資料或超時。收到回覆後，客戶端再發送下一個請求。

客戶端 ──→ 伺服器：「有新資料嗎？」
           （連線 hold 住... 等待中...）
客戶端 ←── 伺服器：「有了！資料在這裡」
客戶端 ──→ 伺服器：「又有新資料嗎？」（重新 hold）
面向 Long-Polling
連線方式 客戶端發送請求，伺服器 hold 住直到有資料
資料傳遞 比 Polling 快——有新資料就立即回覆
資源消耗 中等——比 Polling 少，但每次收到資料後要重新建立連線
適合場景 更新較頻繁但不需要完全即時的應用

舉例：一個聊天應用用 Long-Polling。用戶發送請求後，如果有新訊息就立即收到；如果沒有，伺服器會 hold 住幾秒鐘再回覆「沒有」，然後用戶再問一次。比純 Polling 省了很多無意義的請求。

WebSockets

WebSockets 完全不同：它在客戶端和伺服器之間建立一條持久的雙向連線。連線建立後，雙方可以隨時互相傳送資料，不需要重複建立 HTTP 請求。

客戶端 ←──────持久雙向連線──────→ 伺服器
        「推送新訊息」 ←              → 「推送新訊息」
面向 WebSockets
連線方式 一條持久的 TCP 連線，雙向通訊
資料傳遞 即時——伺服器可以主動推送，不需要客戶端問
資源消耗 低——連線建立後，後續通訊幾乎零開銷
適合場景 聊天、即時遊戲、股票行情、協作編輯

舉例：一個即時聊天應用。用戶 A 發送訊息時，伺服器透過 WebSocket 連線立即推送到用戶 B 的設備，不需要用戶 B 的客戶端去問。延遲極低，體驗最好。

Webhooks

Webhooks 是完全不同的模式——它是伺服器對伺服器的事件驅動通訊。一個系統定義一個 URL（endpoint），當某個事件發生時，另一個系統會主動打這個 URL 通知。

系統 A（訂閱者）設定 Webhook URL → 系統 B（發布者）
當系統 B 發生事件 → 主動 POST 到系統 A 的 URL
面向 Webhooks
連線方式 事件驅動——事件發生時主動 HTTP POST 到訂閱者的 URL
資料傳遞 即時——事件發生就通知，不需要等待
資源消耗 低——只有事件發生時才有流量
適合場景 伺服器間事件通知（支付完成、訂單狀態更新）

舉例：你在電商平台下單付款後，付款系統會透過 Webhook 通知訂單系統「付款成功」，訂單系統再通知倉庫系統「可以出貨了」。不需要輪詢，有事件就通知。

四種模式對照

模式 連線方式 資料傳遞 資源消耗 典型場景
Polling 固定間隔 HTTP 請求 延遲（下次請求時） 高（無用請求多） 天氣、新聞（低頻更新）
Long-Polling 伺服器 hold 連線直到有資料 較快（有資料就回） 中等 聊天（中頻更新）
WebSockets 持久雙向連線 即時（主動推送） 低 即時聊天、遊戲、股票
Webhooks 事件驅動 HTTP POST 即時（事件觸發） 低 伺服器間事件通知

如何選擇？

  • 更新不頻繁、不需要即時 → Polling（最簡單）
  • 更新較頻繁但不需要完全即時 → Long-Polling（比 Polling 省資源）
  • 需要雙向即時通訊 → WebSockets（體驗最好）
  • 伺服器間事件通知 → Webhooks（事件驅動，無需輪詢）

面試中的關鍵點

  • Polling 是「拉」（pull），WebSockets 和 Webhooks 是「推」（push）
  • Polling 資源消耗最高（大量無用請求），WebSockets 和 Webhooks 最低
  • WebSockets 是客戶端-伺服器的雙向連線；Webhooks 是伺服器-伺服器的事件通知
  • 面試時被問「該用哪個」，先問清楚是哪種場景（用戶端即時、伺服器間通知、低頻更新）

小結

四種通訊模式的核心差異在於：Polling 是定期問、Long-Polling 是問了等著、WebSockets 是建一條專線雙向通訊、Webhooks 是有事主動通知。選擇哪種取決於更新頻率、即時性需求和通訊方向。理解這些差異後，你就掌握了系統設計中最常見的通訊模式選擇框架。
