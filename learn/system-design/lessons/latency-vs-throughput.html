延遲 vs 吞吐量

系統設計面試 · 一致性與效能 · 步驟 3/4

學習目標：理解延遲與吞吐量的定義、差異，以及兩者之間的取捨關係與優化策略。

兩種完全不同的「快」

在系統設計中，「快」這個字其實有兩種完全不同的含義。你說「這個系統很快」，可能是在說「使用者按下按鈕後很快就看到回應」（延遲低），也可能是在說「這個系統每秒能處理一百萬筆訂單」（吞吐量高）。這兩件事看起來都是「快」，但它們的衡量方式、優化手段和適用場景完全不同。

搞混這兩個概念是系統設計面試中最常見的錯誤之一。面試官問你「如何提升系統效能」，如果你只回答其中一個，就暴露了你對效能問題的理解不夠全面。

延遲（Latency）

延遲衡量的是延遲時間——一個請求從發出到收到回應要多久。用速食店來類比：延遲就是你從排隊點餐到拿到漢堡要等多久。不管有多少人在排隊，你關心的是「我的那一份要等多久」。

面向說明
衡量單位毫秒（ms）、秒（s）——時間單位
核心問題一個請求要等多久？
影響延遲越高，使用者體驗越差——頁面載入慢、按鈕回應遲鈍
典型場景搜尋引擎（<100ms）、遊戲（<50ms）、即時通訊

在分散式系統中，延遲不只是網路傳輸的時間，還包括：DNS 解析時間、TCP 握手時間、SSL/TLS 交握時間、伺服器處理時間、資料庫查詢時間、序列化/反序列化時間。每一個環節都可能成為延遲的瓶頸。

吞吐量（Throughput）

吞吐量衡量的是單位時間內能處理多少工作。同樣用速食店類比：吞吐量就是這家店每小時能賣出多少個漢堡。你不在意個別客人等多久，你在意的是整體的產出量。

面向說明
衡量單位每秒請求數（RPS）、每秒位元組數（Mbps）——數量/時間單位
核心問題系統每秒能處理多少請求？
影響吞吐量不足會導致請求排隊、系統過載、回應變慢
典型場景批次處理、資料備份、圖片轉碼、資料管線

核心差異

面向延遲吞吐量
關注點速度——單個請求的等待時間容量——整體處理能力
使用者感受「這個 App 好慢」「這個系統處理不了我的大量資料」
優化方向減少每個請求的處理時間增加同時處理的請求數量
類比高速公路的限速高速公路的車道數量

一個直觀的類比：高速公路。延遲是「從 A 城到 B 城要開多久」（限速決定），吞吐量是「每小時能通過多少輛車」（車道數決定）。你可以提高限速（降低延遲），也可以增加車道（提高吞吐量），但兩者的優化手段完全不同。

兩者之間的取捨

延遲和吞吐量並非總是矛盾的，但它們有時會互相影響：

  • 批次處理提高吞吐量但增加延遲：把多個請求打包一起處理，整體吞吐量提升，但每個請求的等待時間增加了。例如：資料庫的 batch insert 比逐條 insert 快很多，但每筆資料要等批次完成才能確認。
  • 並行處理降低延遲但可能降低吞吐量：把一個大任務拆成多個小任務同時處理，單個任務的完成時間縮短，但整體的資源使用效率可能下降（context switching 的開銷）。
  • 快取可以同時改善兩者：把熱資料放在記憶體中，讀取延遲降低，同時減輕後端壓力，吞吐量也提升。這是少數能「兩全其美」的優化手段。

怎麼提升延遲？

  1. CDN（內容分發網路）：把靜態資源放到離使用者最近的節點，減少網路傳輸時間。
  2. 快取：把頻繁存取的資料放在記憶體中，避免每次都去資料庫查詢。
  3. 非同步處理：把不影響使用者體驗的操作（如發送通知、記錄日誌）放到背景執行，讓主請求快速返回。
  4. 優化資料庫查詢：建立索引、避免 N+1 查詢、使用連線池減少連線建立的開銷。

怎麼提升吞吐量？

  1. 水平擴展：增加更多伺服器來分擔負載，比升級單台伺服器的硬體更有效。
  2. 平行處理：把大任務拆成多個小任務同時處理，充分利用多核心和多機器。
  3. 快取：減少重複計算和查詢，讓伺服器能處理更多有效請求。
  4. 訊息佇列：把突發流量暫存在佇列中，讓後端按自己的節奏處理，避免瞬間過載。

面試中的應用

面試官問「如何提升系統效能」時，一個好的回答應該同時涵蓋延遲和吞吐量兩個維度，並說明你為什麼選擇優化哪一個。例如：

「這個系統的主要瓶頸是延遲——使用者等待搜尋結果的時間超過了 2 秒。我會先用 CDN 和快取降低延遲。與此同時，我會監控吞吐量，確保系統在流量高峰期不會因為優化延遲而犧牲了整體處理能力。」
