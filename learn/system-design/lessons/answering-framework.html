7 步驟回答框架

Step 2/4 · 系統設計面試入門

為什麼需要框架？

系統設計面試是開放式的，但不代表你可以隨便講。你需要一套可複用的流程，讓你在任何題目下都能有序地推進。這套 7 步驟框架是業界最常見的做法，從需求澄清一路走到瓶頸分析。

七步走

步驟 1：需求澄清（Requirements Clarification）

拿到題目先別急著畫圖。問問題：

  • 這個系統的核心功能是什麼？（Functional Requirements）
  • 規模多大？日活用戶、QPS、資料量？（Non-functional Requirements）
  • 需要支援哪些裝置？Web、Mobile、Both？

為什麼重要：需求決定設計。一個給 100 人用的內部工具和一個給一億人用的社交平台，設計完全不同。你clarify的過程本身就在展示你的經驗。

步驟 2：粗估（Back-of-the-envelope Estimation）

花 2-3 分鐘估算關鍵數字：

  • 日活用戶數 → 峰值 QPS
  • 每筆資料大小 → 總儲存量
  • 讀寫比 → 決定快取和複製策略

為什麼重要：數字幫你做後續決策。如果你算出峰值 QPS 是 10 萬，你就知道一台伺服器扛不住，需要 Load Balancer 和水平擴展。

步驟 3：API 定義（System Interface Definition）

定義系統對外暴露的 API。不需要寫完整個 API spec，但要清楚：

  • 輸入是什麼、輸出是什麼
  • 用 REST 還是 RPC

例如短網址服務：POST /shorten(url) → short_url、GET /:short_url → redirect(long_url)

步驟 4：資料模型（Data Model）

決定資料怎麼存、怎麼組織：

  • 有哪些核心實體？（User、Post、URL Mapping...）
  • 用 SQL 還是 NoSQL？為什麼？
  • 索引怎麼建？

跟你經驗的連結：你用過 Postgres，知道 table schema 的概念。這裡的思考是「這張表要存什麼欄位、用什麼當 primary key、查詢模式是什麼」。

步驟 5：高階設計（High-level Design）

畫一個 5-6 個方塊的架構圖：

  • Client → Load Balancer → Application Servers → Database
  • 加上 Cache、CDN、Message Queue 等（視需求）

這一步畫骨架，不要急著深入任何一個方塊的內部。

步驟 6：詳細設計（Detailed Design）

面試官會指定 2-3 個組件深入討論。你根據面試官的興趣深入：

  • 快取策略：Read-through vs Write-through？
  • 資料分片：按什麼 key 分？
  • 訊息佇列：用 Kafka 還是 RabbitMQ？

每深入一層，都要說明取捨。

步驟 7：瓶頸分析（Bottleneck Identification）

回頭審視你的設計：

  • 有沒有單點故障（Single Point of Failure）？
  • 資料備份夠不夠？
  • 擴展性瓶頸在哪？

這一步最容易被忽略，但面試官很看重。它展示你能自我批判。

實戰範例：用 Netflix 走一遍步驟 1

拿到「設計 Netflix」這道題，需求釐清分三層問：

第一層：功能性需求（做什麼）

  • 核心功能有哪些？播放影片、搜尋、推薦、下載離線觀看？
  • 支援哪些裝置？手機、平板、電視、瀏覽器、遊戲機？

第二層：非功能性需求（怎麼跑）

  • 什麼最重要？可用性（99.99%）優先於一致性（推薦可以延遲）
  • 延遲要求？影片開始播放要在 2 秒內
  • 認證需求？用戶登入、付費驗證

第三層：規模（做多大）

  • DAU？2 億和 2000 萬的設計完全不同
  • 讀寫比？約 200:1（看的人遠多於上傳的人）
  • 峰值在哪？週五晚高峰？世足賽直播？

收斂心法：問 3-4 個最關鍵的問題後，就說「我先假設 X、Y、Z，如果不對再調整」。用最少的問題收斂最多不確定性，才是面試官想看到的。

七步驟口訣

需A資，高詳瓶
諧音：「需要 A 紙，高級詳評」

🧑‍🎨 想像一個人拿著 A 紙到高級廁所做詳細評估，蹲太久遇到瓶頸。
越荒謬越好記。前四步（需、A、資）定義「做什麼」，後三步（高、詳、瓶）定義「怎麼做」。
