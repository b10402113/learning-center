Twitter · 第 2 步（共 5 步）

核心系統設計與資料庫綱要

學習目標

能夠定義 Twitter 系統的核心 API，繪製高層架構，並設計適合的資料庫綱要。

1. 系統 API 設計

需求釐清之後，下一步是定義系統的 API。API 是系統的「合約」——它明確了系統提供什麼功能、需要什麼輸入、回傳什麼輸出。

Twitter 的核心 API 可以定義為：

發推文

tweet(api_dev_key, tweet_data, tweet_location, user_location, media_ids)
參數類型說明
api_dev_keystringAPI 開發者金鑰，用於身份驗證
tweet_datastring推文內容（限 280 字元）
tweet_locationstring推文關聯的位置（經緯度），可選
user_locationstring使用者當前位置
media_idslist附帶的媒體 ID 列表（圖片/影片）

讀取時間軸

getTimeline(api_dev_key, user_id, since_id, count, max_id)

時間軸 API 支援分頁：since_id 用於增量載入，max_id 用於向前翻頁，count 控制每頁數量。

追蹤/取消追蹤

followUser(api_dev_key, user_id, follow_user_id)
unfollowUser(api_dev_key, user_id, unfollow_user_id)
設計要點：API 設計時要考慮哪些是必填參數、哪些是可選參數。例如 tweet_location 是可選的——不是每條推文都需要位置資訊。

2. 高層架構

從容量估算我們知道：每秒 1,150 次寫入、325,000 次讀取。這是一個讀取密集型系統。高層架構要能高效處理這兩種截然不同的流量模式。

架構組件

組件職責
客戶端Web 瀏覽器、行動 App、SMS 介面
負載均衡器將請求分配到多個應用伺服器
應用伺服器處理業務邏輯（發推、追蹤、時間軸生成）
聚合伺服器從多個資料庫分片收集資料並合併
快取層儲存熱門推文和使用者資料，加速讀取
資料庫持久化儲存推文、使用者、追蹤關係

請求流程

發推文（寫入）：客戶端 → 負載均衡器 → 應用伺服器 → 寫入資料庫（主節點）→ 複製到從節點 → 可選：更新追蹤者的快取

讀取時間軸（讀取）：客戶端 → 負載均衡器 → 應用伺服器 → 先查快取 → 快取未命中則查聚合伺服器 → 聚合伺服器從多個分片讀取 → 回傳合併結果

關鍵決策：因為讀取量是寫入的 280 倍，架構的重心要放在讀取路徑的優化——快取層和多副本讀取是核心。

3. 資料庫綱要

資料庫綱要（schema）定義了資料的結構。Twitter 的核心資料可以分為四張表：

User 表

欄位類型說明
user_idbigint使用者唯一 ID（主鍵）
namevarchar(200)使用者名稱
emailvarchar(200)電子郵件（唯一）
last_logindatetime最後登入時間

Tweet 表

欄位類型說明
tweet_idbigint推文唯一 ID（主鍵）
user_idbigint發文者 ID（外鍵）
tweet_textvarchar(280)推文內容
media_urlvarchar(200)附帶媒體 URL，可為空
created_atdatetime發文時間

Follow 表

欄位類型說明
followee_idbigint被追蹤者 ID
follower_idbigint追蹤者 ID
created_atdatetime追蹤時間

Favorite 表

欄位類型說明
tweet_idbigint推文 ID
user_idbigint最愛者 ID
created_atdatetime最愛時間

SQL vs NoSQL？

Twitter 的追蹤關係是典型的圖形結構（使用者 A 追蹤 B、B 追蹤 C），用關聯式資料庫的 JOIN 查詢效率不高。但推文本身是結構化的表格資料。實務上，Twitter 使用混合方案：

  • MySQL——儲存推文和使用者資料
  • Memcache / Redis——快取熱門推文和時間軸
  • 圖形資料庫或自訂結構——儲存 social graph

4. 設計取捨

資料庫綱要的設計會直接影響後續的分片策略：

  • Tweet 表按 user_id 分片——同一使用者的所有推文在同一台機器，讀取個人推文很快，但熱門使用者會造成熱點
  • Tweet 表按 tweet_id 分片——推文均勻分散，但查詢某個使用者的推文需要跨多台機器
  • Follow 表的雙向索引——同時維護「我追蹤了誰」和「誰追蹤了我」，查詢效率更高但寫入成本翻倍

這些取捨在後續的「資料擴展」步驟中會深入討論。
