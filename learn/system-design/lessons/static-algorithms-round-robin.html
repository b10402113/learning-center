Round Robin：最基礎的靜態負載均衡

system-design · lb-algorithms · Step 1/6

負載均衡器面對的第一個問題是：怎麼把用戶請求分配到多台後端伺服器？最直覺的答案就是「輪流來」——這就是 Round Robin。

什麼是 Round Robin？

Round Robin（循環分配）是最簡單的負載均衡演算法。它把請求按照順序依次循環分配給每一台伺服器。假設有 3 台伺服器 S0、S1、S2，分配流程是：

請求編號分配到
第 1 個請求S0
第 2 個請求S1
第 3 個請求S2
第 4 個請求S0
第 5 個請求S1

依此類推，到最後一台伺服器後又從第一台開始。整個過程不需要記錄任何伺服器狀態——它是一個靜態演算法。

為什麼「靜態」是關鍵特點？

靜態意味著 Round Robin 不會收集伺服器的即時負載資訊。它不會問「哪台伺服器比較閒？」——它只是機械地按照順序分配。這帶來兩個直接後果：

  • 優點：實作極簡單，幾乎零額外開銷，不需要在負載均衡器上維護任何狀態
  • 缺點：不考慮伺服器的硬體差異，也不考慮每台伺服器的即時負載

什麼時候用 Round Robin？

Round Robin 在以下條件全部滿足時效果最佳：

  • 伺服器同質：所有後端伺服器的硬體規格相同
  • 請求處理時間相近：每個請求消耗的計算資源差不多
  • 無狀態應用：每次請求可以獨立處理，不需要依賴之前的請求結果

典型的適用場景：純靜態資源的 Web 伺服器集群（如提供 HTML/CSS/JS 的 CDN 節點）、無狀態的 API 閘道。

什麼時候不要用 Round Robin？

如果以下任一條件不滿足，Round Robin 就不是好選擇：

  • 伺服器性能不同（異質集群）→ 應考慮 Weighted Round Robin
  • 請求處理時間差異大 → 應考慮 Least Connections
  • 需要會話持久化 → 應考慮 IP Hash 或外部 Session Store

面試提示

在系統設計面試中，Round Robin 通常是預設選項。當你畫架構圖標註 Load Balancer 時，可以先說「這裡用 Round Robin，因為伺服器同質且請求處理時間相近」——但最好同時補充一句：「如果伺服器異質，我會改用 Weighted Round Robin 或 Least Connections。」這能展現你理解了背後的取捨。

小結

Round Robin 是所有負載均衡演算法的起點。它簡單、快速、公平，但不考慮伺服器差異和即時負載。記住它的核心適用條件：伺服器同質 + 請求處理時間相近 + 無狀態。
