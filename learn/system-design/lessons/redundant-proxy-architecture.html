冗餘 Proxy 架構設計

system-design · proxy-redundancy · Step 4/4

學習目標

將冗餘與複製概念應用到 Proxy 設計，認識常見的冗餘 Proxy 架構模式與故障處理方式。

把零件組裝起來

前三課分別介紹了：正向代理（代表用戶端）、反向代理（代表伺服器）、冗餘與複製（消除單點故障）。這一課把這三個概念組裝在一起，設計一個不會因為一台代理掛掉就中斷的架構。

問題：反向代理本身也是單點故障

在前面的課程中，我們設計了這樣的架構：

用戶端 ──→ 反向代理（一台）──→ 伺服器 A
                           ├→ 伺服器 B
                           └→ 伺服器 C

後端伺服器有冗餘，但反向代理只有一台。如果它掛了，所有用戶都連不上來。反向代理本身變成了系統的單點故障。

解法很直覺：多加幾台反向代理。但「多加幾台」這四個字背後有很多細節需要回答。

模式一：主動-被動（Active-Passive）

用戶端 ──→ 虛擬 IP (VIP)
              │
         主動代理 ──→ 伺服器群
         被動代理（備援）

兩台代理，一台負責處理所有流量（主動），另一台待命（被動）。被動代理定期心跳檢測主動代理是否健康。如果主動代理掛了，被動代理接管虛擬 IP（VIP），用戶端無感知。

優點 缺點
架構簡單，容易理解 被動代理閒置，資源浪費
切換時沒有流量分散的複雜度 故障轉移有短暫中斷（VIP 切換需要時間）
資料一致性容易處理 被動代理長期不處理流量，切換時可能有問題

模式二：主動-主動（Active-Active）

              ┌──→ 反向代理 A ──→ 伺服器群
用戶端 ──→ LB ─┤
              └──→ 反向代理 B ──→ 伺服器群

多台代理同時處理流量。用戶端的請求先到一層負載均衡器（可以是 DNS 輪詢、專用 LB、或 Keepalived VIP），再分發到各台反向代理。

優點 缺點
資源利用率高，兩台都在工作 架構更複雜，需要額外的負載均衡層
一台掛了，另一台繼續服務 如果代理有狀態（快取），切換時可能丟失
天然支援水平擴展 需要確保所有代理的設定一致

常見的冗餘代理實作

工具 模式 特點
Keepalived + Nginx Active-Passive VIP 漂移，故障轉移秒級，最常見的組合
HAProxy Active-Active 高性能 L4/L7 負載均衡，適合大流量場景
DNS 輪詢 Active-Active 多個 A 記錄指向不同代理 IP，最簡單但最粗糙
雲端 LB Active-Active AWS ALB/NLB、GCP Cloud Load Balancing，免運維

故障轉移的關鍵：心跳與健康檢查

不管是 Active-Passive 還是 Active-Active，代理之間都需要知道彼此的健康狀態。這靠心跳（Heartbeat）機制實現：

  • 每台代理定期（例如每秒）向其他代理發送心跳包
  • 如果一段時間沒收到心跳，判定對方故障
  • Active-Passive：故障時觸發 VIP 切換
  • Active-Active：故障時從負載均衡器的後端列表中移除

心跳的頻率和超時設定是一個取捨：太頻繁浪費資源，太稀疏故障偵測太慢。

架構選型：什麼時候用哪種？

場景 推薦模式 原因
流量不大，預算有限 Active-Passive 兩台伺服器，一台閒置但架構簡單
高流量，需要水平擴展 Active-Active 所有代理都在工作，天然可擴展
代理有狀態（快取、session） Active-Passive + 共享狀態 避免狀態不一致，切換時需要狀態遷移
雲端部署 Active-Active + 雲端 LB 雲端 LB 已經處理了冗餘和故障轉移

面試中的關鍵點

冗餘 Proxy 架構是面試中討論「高可用性」時的經典話題。面試官期望你能：

  • 指出反向代理本身也是單點故障——很多人會設計後端冗餘但忘記代理層
  • 描述 Active-Passive 和 Active-Active 兩種模式，並說出各自的取捨
  • 提到心跳和健康檢查機制
  • 能根據場景推薦適合的模式
  • 知道常見的實作工具（Keepalived、HAProxy、雲端 LB）

這就是「冗餘」在系統設計中的實際應用：不只是多加一台機器，而是要思考故障怎麼偵測、流量怎麼切換、狀態怎麼遷移。

小結

反向代理本身也是單點故障，需要冗餘設計。Active-Passive 模式用 VIP 漂移實現故障轉移，簡單但資源浪費；Active-Active 模式讓多台代理同時工作，高效但架構更複雜。心跳和健康檢查是故障偵測的基礎。在面試中，能指出代理層的單點故障並描述故障轉移機制，是展示系統設計能力的關鍵。
