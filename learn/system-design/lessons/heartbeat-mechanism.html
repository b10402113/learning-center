Heartbeat 存活偵測機制

系統設計面試 · 通訊與可靠度 · 步驟 2/3

學習目標：理解 Heartbeat 機制如何檢測節點存活、維護連線狀態，並認識常見實作考量。

問題背景

你的系統有 100 台伺服器，某天其中一台掛了。問題是：系統怎麼「知道」它掛了？如果不知道，請求還會繼續往那台送，使用者就會看到錯誤。

在分散式系統中，工作和資料分散在多台伺服器上。為了有效地路由請求，伺服器需要知道哪些伺服器還活著。更關鍵的是，當某台伺服器掛掉時，系統要能快速偵測到並把它的負載轉移給其他伺服器。

什麼是 Heartbeat？

Heartbeat（心跳）是一種定期發送的短訊息，用來告知其他節點「我還活著」。就像你每分鐘拍一下胸口說「我還在呼吸」——如果某次沒拍了，就知道出事了。

具體來說，每台伺服器會定期（例如每 5 秒）向以下其中一方發送 heartbeat 訊息：

架構Heartbeat 發送對象偵測方式
有中心節點中心監控伺服器中心伺服器追蹤所有節點的 heartbeat，超時未收到就判定為故障
無中心節點（去中心化）隨機選擇的一組節點每個節點追蹤它負責的節點，超時未收到就判定為故障

Heartbeat 的運作流程

以有中心節點的架構為例：

  1. 正常運作：每台伺服器每 5 秒向中心伺服器發送一次 heartbeat。中心伺服器記錄「上一次收到 Server A 的 heartbeat 是 10:00:30」。
  2. 故障偵測：如果中心伺服器在 15 秒內沒有收到 Server A 的 heartbeat，就判定 Server A 可能掛了。
  3. 故障處理：中心伺服器把 Server A 從可用列表中移除，將原本送往 Server A 的請求轉發給其他伺服器。
  4. 恢復處理：如果 Server A 重新啟動，它會再次發送 heartbeat，中心伺服器會把它加回可用列表。

關鍵設計參數

Heartbeat 間隔

間隔太短（如 100ms）會消耗大量頻寬和 CPU；間隔太長（如 60 秒）會導致故障偵測延遲。常見的選擇是1~10 秒，具體取決於系統對故障偵測速度的要求。

超時閾值

超時閾值通常是 heartbeat 間隔的 3~5 倍。例如 heartbeat 每 5 秒發一次，超時閾值可以設為 15~25 秒。太短會造成誤判（網路暫時延遲被當成故障），太長會延遲故障偵測。

心跳內容

Heartbeat 訊息通常很短，只包含節點 ID 和時間戳。但也可以捎帶（piggyback）一些輕量資訊，如：

  • 節點的負載狀態（CPU 使用率、記憶體使用量）
  • 節點的角色（是 Leader 還是 Follower）
  • 節點的健康指標

Heartbeat vs Ping

比較HeartbeatPing
目的告知「我活著」確認「你活著嗎？」
方向由被監控節點主動發送由監控方主動詢問
頻率高頻定期發送按需發送或低頻
資訊量可捎帶狀態資訊通常只有 ping/pong

實務上，很多系統會兩者並用：Heartbeat 用於日常存活偵測，Ping 用於深入的健康檢查（如測試資料庫連線是否正常）。

常見應用場景

  • 負載均衡器：透過 heartbeat 偵測後端伺服器是否存活，自動移除故障節點。
  • 叢集管理：如 Kubernetes 的 kubelet 定期向 API server 發送 heartbeat（ lease ），告知節點狀態。
  • 分布式快取：如 Redis Cluster 節點之間透過 gossip 協議交換心跳，偵測故障節點。
  • 微服務：服務之間透過 heartbeat 確認彼此可用，避免向已死掉的服務發請求。

在面試中怎麼用？

當你被問到「怎麼偵測伺服器故障」或「負載均衡器怎麼知道後端掛了」，你可以：

  1. 先說問題：分散式系統中，節點故障是常態，系統需要快速偵測並處理。
  2. 引入 Heartbeat：定期發送存活訊息，超時未收到就判定為故障。
  3. 討論參數：heartbeat 間隔和超時閾值的取捨——太快浪費資源，太慢延遲偵測。
  4. 延伸：提到可以捎帶負載資訊，為後續的負載均衡討論鋪路。
