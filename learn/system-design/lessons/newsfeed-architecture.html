Facebook Newsfeed 架構設計

學習目標

掌握 Newsfeed 系統的整體架構，了解推播（push）與拉播（pull）模式的取捨，以及動態消息生成、排名和資料分片的設計。

1. Newsfeed 的核心挑戰

Facebook 的動態消息（Newsfeed）是使用者打開 Facebook 首先看到的內容——它是一個不斷更新的列表，包含來自追蹤者、粉專和社團的貼文、照片、影片和連結。

設計 Newsfeed 的核心挑戰是：如何在數百萬來源中快速聚合最新內容，並以低延遲遞送給數億使用者？

要回答這個問題，我們先從資料模型開始。

2. 資料模型

Newsfeed 涉及三個核心實體：

實體說明
User（使用者）可以追蹤其他使用者和實體，可以發布貼文
Entity（實體）粉專、社團等，可以發布貼文
FeedItem（貼文）包含文字、圖片或影片，由使用者或實體發布

關鍵關係：每個使用者都有一個「追蹤清單」（UserFollow），記錄他追蹤了哪些使用者和實體。每個 FeedItem 都有一個 UserID 指向發布者。

3. 推播（Push）vs 拉播（Pull）

Newsfeed 的架構設計有兩種基本策略：

拉播模型（Pull Model）

使用者打開 Newsfeed 時，系統才即時從資料庫拉取追蹤者的最新貼文，合併後返回。

  • 優點：資料永遠最新，不需要預計算
  • 缺點：每次都要查詢所有追蹤者的貼文，延遲高

推播模型（Push Model）

當使用者 A 發布貼文時，系統將這篇貼文推送到所有追蹤者 A 的 feed 快取中。使用者打開 Newsfeed 時，直接從快取讀取。

  • 優點：讀取延遲極低（直接查快取）
  • 缺點：寫入成本高——一篇貼文可能要推送到數千人的 feed 中

混合模型（Hybrid）

實際的 Facebook Newsfeed 使用混合模型：

  • 大部分使用者：使用推播模型（write fan-out），貼文發布時預先計算並寫入追蹤者的 feed 快取
  • 追蹤者極多的帳號（如名人、大型粉專）：不預先推送，改為使用者查詢時即時拉取（on-read pull），再與快取中的預計算結果合併
面試技巧：推播/拉播的選擇是 Newsfeed 設計的核心取捨。面試中你要能清楚解釋：推播以寫入成本換取讀取低延遲，拉播以讀取延遲換取即時性。混合模型是折衷方案。

4. Feed 生成流程

當使用者打開 Newsfeed 時，系統執行以下步驟：

  1. 取得追蹤清單：查詢使用者追蹤的所有使用者和實體 ID
  2. 取得最新貼文：從快取或資料庫中取得這些追蹤者的最新貼文
  3. 合併與排序：將所有貼文合併，根據排名演算法排序
  4. 過濾與分頁：返回最前面的 N 條，支援分頁載入

Pre-computed Feed（預計算 feed）

在推播模型下，系統在貼文發布時就將 FeedItem 的 ID 寫入追蹤者的 feed 快取（一個 sorted set，以時間或排名分數為 score）。查詢時直接從快取中取出前 N 條，再批量查詢貼文詳細資料。

混合 Feed

對於追蹤了大量名人或大型粉專的使用者，系統需要額外執行 on-demand 的拉取：從這些高流量來源即時取得最新貼文，與預計算的 feed 合併後排序。

5. Feed 排名

最簡單的排序方式是按時間順序（最新的排最前面）。但現代的排名演算法更複雜——它需要確保「重要的」貼文排在最前面。

排名的核心思路是：先選出影響貼文重要性的訊號（signals），再找出如何組合這些訊號計算最終分數。常見的訊號包括：

訊號說明
親密度（Affinity）使用者與發布者的互動程度（留言、按讚、瀏覽頻率）
內容類型影片、圖片通常比純文字貼文獲得更多互動
時間衰減越新的貼文通常越重要
互動率該貼文獲得的按讚、留言、分享數量

這些訊號會透過一個機器學習模型（或簡單的加權公式）組合成一個排名分數。面試中你不需要深入機器學習，但要能解釋排名的取捨：精準排名需要更多計算資源和延遲。

6. 資料分片

Facebook 每天新增數億條貼文，讀取負載極高，單機無法承擔。

貼文和元資料的分片

貼文可以按 UserID 進行水平分片（hash partitioning）。同一個使用者的貼文在同一個分片上，寫入和查詢同一個使用者的貼文都只需要訪問一個分片。

Feed 資料的分片

Feed 快取（每個使用者的預計算 feed）也可以按 UserID 分片。查詢時只需訪問對應的分片。

挑戰

  • 熱點使用者：某些使用者（如名人）有數千萬追蹤者，一篇貼文的 fan-out 寫入量巨大
  • 快取大小：每個使用者的 feed 快取可能包含 500+ 條貼文 ID，總快取量巨大
  • 一致性：推播模型中，寫入快取和寫入資料庫的時間差可能導致短暫不一致
