訊息儲存與檢索

Facebook Messenger 系統設計 · Step 4/6

學習目標

設計高效能的訊息儲存機制，理解非同步寫入與連線管理的重要性。

核心挑戰

每秒有數千萬條訊息湧入系統，每條都要持久化。如果寫入太慢，會拖垮整個系統；如果寫入太快但沒做好並發控制，資料會出錯。這裡的核心挑戰是：如何在高吞吐下保持可靠性？

兩種寫入策略

當 Chat Server 收到一條新訊息，需要寫入資料庫。有兩種做法：

策略一：同步寫入（開新線程）

為每條訊息開一個新線程來處理資料庫寫入。這種做法的問題很明顯：

  • 線程建立和切換有開銷
  • 大量並發時，線程數暴增，伺服器資源被耗盡
  • 資料庫連線不夠用

策略二：非同步寫入（推薦）

使用非同步請求來寫入資料庫。訊息先推送到目標用戶，資料庫寫入在背景進行。這是更好的選擇：

  • 不阻塞用戶體驗：訊息推送和資料庫寫入解耦
  • 可控制並發：透過消息隊列控制寫入速率
  • 失敗可重試：寫入失敗時可以重試，不會丟失訊息

資料庫設計

訊息資料庫需要回答的核心查詢是：「給定兩個用戶，找出他們之間最近的 N 條訊息」。這是一個典型的範圍查詢。

表結構

欄位類型說明
message_idBIGINT訊息唯一 ID（可用 Snowflake 等分散式 ID 產生器）
sender_idBIGINT發送者用戶 ID
receiver_idBIGINT接收者用戶 ID
contentTEXT訊息內容
created_atTIMESTAMP發送時間

索引建立在 (sender_id, receiver_id, created_at) 上，這樣查詢兩個人之間的聊天記錄就是一次高效的範圍掃描。

連線池管理

資料庫連線是稀缺資源。如果每條訊息都新建一個連線，資料庫很快就會被打爆。解決方案是連線池（Connection Pooling）：

  • 預先建立一批資料庫連線，放在池子裡
  • 需要寫入時從池中取一條連線，寫完後歸還
  • 池子的大小根據資料庫的承載能力設定

連線池還需要處理連線的健康檢查（定期 ping）、超時回收、以及連線數達上限時的排隊機制。

訊息序號的生成

每條訊息需要一個唯一的、遞增的 ID。在分散式環境下，如何做到？

  • 資料庫自增 ID：簡單，但單點瓶頸
  • Snowflake ID：Twitter 開發的分散式 ID 產生方案，由時間戳+機器 ID+序列號組成，全局唯一且大致遞增
  • 號段模式：每台機器從中心服務領取一段 ID，用完再領

面試中選 Snowflake 即可——它是業界標準，解釋清楚原理就能加分。
