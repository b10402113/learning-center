Twitter Search 系統設計

Step 1/4 · Twitter Search & Web Crawler

學習目標

掌握 Twitter Search 系統的需求分析、容量估算、倒排索引設計、儲存分區、快取與負載均衡策略，並能在面試中從零畫出完整架構圖。

問題定義

Twitter 使用者可以隨時發推文（tweet），每條推文是一段純文字。我們的目標是設計一個系統，讓使用者能在所有推文中快速搜尋關鍵字。

跟一般的 NoSQL CRUD 不同，搜尋的本質是「找出包含特定詞的所有推文」，這需要一個完全不同的資料結構——倒排索引（Inverted Index）。

需求與目標

指標數值
總使用者數15 億
日活躍使用者（DAU）8 億
每日新推文數4 億條
平均每條推文大小300 bytes
每日搜尋次數5 億次
搜尋查詢格式多個詞，以 AND/OR 組合

核心需求：系統要能高效地儲存推文，並支援快速查詢。搜尋延遲目標在數百毫秒內。

容量估算

儲存容量

每天新增推文的原始儲存量：

4 億條 × 300 bytes = 120 GB/天

換算成每秒的寫入速率：

120 GB ÷ 24 ÷ 3600 ≈ 1.38 MB/秒

如果規劃五年儲存，考慮 80% 磁碟使用率上限：

120 GB × 365 天 × 5 年 ≈ 200 TB
200 TB ÷ 0.8 ≈ 250 TB

搜尋流量

每天 5 億次搜尋，假設均勻分佈：

5 億 ÷ 86400 ≈ 5,800 QPS（查詢/秒）

尖峰時段取 2 倍，約 11,600 QPS。

系統 API

搜尋 API 的基本介面：

search(api_dev_key, search_terms, max_results, sort, page_token)

參數說明：

  • api_dev_key：開發者金鑰，用於限流與配額管理
  • search_terms：搜尋關鍵字，多個詞以 AND/OR 連接
  • max_results：單頁回傳的最大結果數
  • sort：排序方式（時間、相關性、熱門度）
  • page_token：分頁用的 token

高層次架構

系統有兩個核心資料流：

  1. 寫入路徑：推文產生 → 寫入儲存 → 建立/更新索引
  2. 讀取路徑：搜尋請求 → 查詢索引 → 回傳結果

高層次架構圖：

使用者 → 負載均衡 → 應用伺服器 → 索引伺服器 → 儲存層
                          ↓
                       快取層（Memcached）

關鍵洞察：我們需要一個倒排索引，記錄每個詞出現在哪些推文中。這是搜尋系統的核心資料結構。

細部元件設計：儲存與倒排索引

倒排索引的結構

倒排索引是搜尋引擎的靈魂。它的邏輯是：正向索引是「推文 → 包含哪些詞」，而倒排索引反過來，是「詞 → 出現在哪些推文」。

例如，假設有三條推文：

推文 ID內容
T1我愛台北的天氣
T2台北今天下雨
T3我喜歡晴天

建立倒排索引後：

詞出現的推文 ID 列表
我[T1, T3]
愛[T1]
台北[T1, T2]
天氣[T1]
今天[T2]
下雨[T2]
喜歡[T3]
晴天[T3]

搜尋「台北」時，直接查索引表拿到 [T1, T2]，再從推文儲存中取出完整內容。搜尋「我 AND 台北」則取交集：[T1, T3] ∩ [T1, T2] = [T1]。

儲存分區策略

250 TB 的索引不可能放在單台機器上。按推文 ID 分區（Hash 分區）是最直觀的方式：

  • 每台機器負責一部分推文 ID 範圍
  • 搜尋時必須查詢所有分區，再合併結果
  • 也可以按時間分區：最近的推文在 SSD，較舊的在 HDD

另一種策略是按詞分區（Partition by term）：把不同詞的倒排索引放在不同機器。搜尋時只需查詢相關詞所在的分區。缺點是熱門詞（如「的」）會造成熱點。

實務上常見的混合策略是：先按推文 ID 分區建立索引，搜詢時並行查詢所有分區，再在應用層合併排序。

快取策略

搜尋結果有明顯的時間局部性（temporal locality）：熱門話題在短時間內會被大量搜尋。

  • 快取什麼：熱門搜尋的結果集
  • 快取在哪：應用伺服器前方的 Memcached / Redis 集群
  • 淘汰策略：LRU（Least Recently Used）最適合搜尋場景
  • 快取失效：新推文寫入時，相關搜尋的快取需要失效（invalidate）
快取不是萬靈丹。搜尋查詢的組合是天文數字，命中率通常只有 20-30%。快取的價值在於降低那 20-30% 熱門查詢的延遲，而非減少整體後端壓力。

負載均衡

系統有兩個負載均衡層：

  1. 使用者 → 應用伺服器：Round Robin 分配請求，簡單有效
  2. 應用伺服器 → 索引伺服器：需要根據分區策略路由，確保查詢到正確的分區

排名機制

搜尋結果的排序直接影響使用者體驗。常見的排名因子：

  • 相關性：關鍵字在推文中的出現頻率（TF-IDF 思路）
  • 熱門度：按讚數、轉推數、回覆數的綜合分數
  • 時效性：越新的推文排名越靠前
  • 社交關係：使用者關注的人發的推文加分

排名計算可以在查詢時即時做（query-time ranking），也可以預先計算好（pre-computed ranking）存到索引中。預先計算能加速查詢，但需要額外的儲存和更新成本。

容錯設計

索引伺服器故障時：

  • 每台索引伺服器都有 secondary 副本（replica）
  • Primary 故障後，secondary 自動接管（failover）
  • 如果 primary 和 secondary 同時故障，需要從頭重建索引

重建索引的方法：回放所有推文的寫入日誌（write-ahead log），從頭建立倒排索引。這就是為什麼推文的原始儲存不能丟——它是索引重建的唯一來源。

面試要點

在面試中，Twitter Search 的關鍵是先討論倒排索引的設計，再討論分區策略。很多候選人會跳過倒排索引直接談架構，這是本末倒置——沒有索引設計，架構無從談起。
