併發控制與容錯

Step 6/6 · Ticketmaster 系統設計 · 約 15 分鐘

學習目標

解決高併發場景下的座位重複訂購問題，保證訂票公平性，並設計容錯機制應對服務崩潰。

核心問題：兩個人同時搶一個座位

假設場次 A 的座位 10 號還剩一個。用戶甲和用戶乙同時點了「預訂」。如果系統沒有做好併發控制，兩個人都會看到「預訂成功」——但實際上只有一個座位。這就是超賣（Overselling）問題。

Solution 1：資料庫事務鎖定

最直接的方法是用 SQL 資料庫的事務隔離級別。在 SQL Server 中：

SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN TRANSACTION;

-- 檢查座位狀態
SELECT Status FROM Seat
WHERE ShowID = 123 AND SeatNumber = 'A10';

-- 如果可用，更新為 Reserved
UPDATE Seat SET Status = 'Reserved'
WHERE ShowID = 123 AND SeatNumber = 'A10'
  AND Status = 'Available';

COMMIT;

SERIALIZABLE 是最高的事務隔離級別。它確保在事務執行期間，其他事務無法修改被讀取的數據。這就解決了超賣問題——如果甲正在預訂座位 A10，乙的 SELECT 會被阻塞，直到甲的事務完成。

但 SERIALIZABLE 有代價：鎖定範圍大、併發度低。每個預訂操作都要鎖住相關行，高併發時會導致大量等待。這在流量尖峰時可能成為瓶頸。

Solution 2：使用 Redis 原子操作

另一個方案是利用 Redis 的原子操作來做座位鎖定：

-- 使用 Redis SET NX（Not Exists）原子操作
SETNX seat:show123:A10 "reserved" EX 900

-- 如果返回 1，表示鎖定成功
-- 如果返回 0，表示已被別人鎖定

SETNX（Set if Not Exists）是一個原子操作：如果 key 不存在，就設置它並返回成功；如果 key 已存在，直接返回失敗。整個操作在 Redis 中是原子的，不會有併發問題。

加上 EX 900（900 秒 = 15 分鐘），鎖定會自動過期。這就實現了「暫時鎖定 + 自動過期」的機制。

兩種方案的比較

特性SQL SERIALIZABLERedis SETNX
併發度低（鎖定行級）高（無鎖等待）
一致性強（ACID）最終一致
過期機制需要手動實現內建 TTL
適用場景低併發、強一致性高併發、可接受最終一致

實際系統中通常混合使用：Redis 做第一層快速鎖定（擋住 99% 的併發），SQL 事務做第二層持久化確認。

容錯：服務崩潰怎麼辦？

ActiveReservationsService 崩潰

如果管理預訂的服務掛了：

  • 方案 A：從資料庫重建——讀取 Booking 表中所有 Status = 'Reserved' 的記錄，重建預訂狀態
  • 方案 B：主從複製——ActiveReservationsService 部署為主從配置，主節點掛了從節點接管

WaitingUsersService 崩潰

等待隊列的容錯相對簡單：

  • 等待隊列是可重建的——用戶可以重新提交等待請求
  • 可以從 Booking 表的時間戳重建等待順序
  • 隊列丟失不會造成數據不一致（不像座位鎖定那麼關鍵）

面試技巧

併發控制和容錯是系統設計面試的「壓軸題」。講清楚：

  • 超賣問題的本質（兩個用戶同時讀到「可用」狀態）
  • SQL SERIALIZABLE 的原理和代價
  • Redis SETNX 的原子操作機制
  • 兩種方案的比較和混合使用
  • 各服務崩潰後的恢復策略
