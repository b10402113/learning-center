訊息傳遞模型

Facebook Messenger 系統設計 · Step 3/6

學習目標

比較 Pull 與 Push 模型的優缺點，選擇適合即時通訊的傳遞方式。

核心問題：訊息怎麼送到？

用戶 A 發了一條訊息給用戶 B，但 B 的設備怎麼知道有新訊息？這裡有兩種根本不同的思路：Pull（拉）和 Push（推）。選擇哪一種，直接決定了整個系統的延遲、資源消耗和複雜度。

Pull 模型（輪詢）

最直覺的做法：用戶的設備每隔幾秒就問一次伺服器「有沒有新訊息？」。這叫輪詢（Polling）。

優點

  • 實現簡單，就是一個定時 HTTP 請求
  • 不需要維持持久連線
  • 對伺服器來說，處理請求的邏輯很直覺

缺點

  • 延遲高：如果輪詢間隔是 5 秒，那訊息最壞情況要等 5 秒才收到
  • 資源浪費：大部分輪詢返回的結果是「沒有新訊息」，白白消耗頻寬和伺服器資源
  • 规模化困難：5 億用戶每 5 秒輪詢一次，每秒就是 1 億個請求——即使 99% 是空的

Push 模型（伺服器推送）

更好的做法：用戶的設備和伺服器之間維持一條持久連線，當有新訊息時，伺服器主動把訊息推送到用戶設備。

實現方式

  • WebSocket：最常用的選擇。建立一條全雙工連線，伺服器和客戶端可以隨時互相發送數據
  • Server-Sent Events（SSE）：伺服器單向推送，適合只需要伺服器→客戶端的場景
  • Long Polling：折衷方案。客戶端發請求，伺服器hold住不立刻回覆，有新訊息時才回應

優點

  • 低延遲：訊息一到伺服器就推送，幾乎即時
  • 資源高效：不需要空輪詢，只在有新訊息時才傳輸數據
  • 用戶體驗好：真正的「即時」感

缺點

  • 連線管理複雜：要處理連線斷開、重連、負載均衡等問題
  • 伺服器資源消耗：每條持久連線都佔用一個伺服器連線槽

實際系統怎麼選？

Facebook Messenger 使用 Push 模型。在面試中，你也應該選 Push——即時通訊的核心價值就在於「即時」，Pull 的延遲是不可接受的。

具體實現上，通常採用 WebSocket。一個典型的架構是：

  • 用戶打開 App，和 Chat Server 建立 WebSocket 連線
  • 連線建立後，用戶發訊息走這條連線
  • 收到訊息時，伺服器也走這條連線推送
  • 連線斷開時，客戶端自動重連

訊息序號與離線

Push 模型還需要處理兩個問題：

  • 訊息序號：多條訊息同時到達，如何保證顯示順序？每條訊息分配一個遞增的 Sequence ID，客戶端按序號排序
  • 離線處理：用戶離線時，新訊息存到資料庫。用戶上線後，從上次的位置開始拉取 missed messages
