演算法選擇：從五種方案中做出決策

system-design · lb-algorithms · Step 6/6

前面介紹了五種負載均衡演算法：Round Robin、Weighted Round Robin、Least Connections、Weighted Least Connections、IP Hash。在實際系統設計中，你不會只記得定義——更要能根據場景條件做出選擇。

維度一：伺服器是否同質？

同質伺服器指所有伺服器硬體規格相同。這是決定是否需要 Weighted 系列演算法的關鍵前提。

  • 同質 + 請求處理時間相近 → Round Robin（最簡單，開銷最小）
  • 同質 + 請求處理時間差異大 → Least Connections（根據即時負載動態調整）

維度二：負載是否穩定？

負載穩定指每台伺服器在任何時刻承受的壓力大致相同。如果負載波動大（例如尖峰時段），靜態演算法無法及時應對。

  • 負載穩定 + 異質伺服器 → Weighted Round Robin（手動設定權重即可）
  • 負載波動大 + 異質伺服器 → Weighted Least Connections（自動平衡）

維度三：是否需要會話持久化？

如果你的應用需要「同一用戶始終路由到同一台伺服器」（購物車、登入態），你需要在上述演算法之外額外考慮會話持久化機制。IP Hash 提供最簡單的持久化，但會導致負載不均。更好的做法是用外部 Session Store（如 Redis）配合任何一種負載均衡演算法。

面試中的應用

負載均衡演算法的選擇通常是一個「順帶討論」的小環節，但它能體現你的全面性。當你畫架構圖標註了 Load Balancer 時，面試官可能問「你會選什麼演算法？」不要只回答「Round Robin」，而是反問或補充：

  1. 伺服器是同質的嗎？→ 決定是否需要 Weighted
  2. 請求處理時間差異大嗎？→ 決定是否需要 Least Connections
  3. 需要會話持久化嗎？→ 決定是否需要 IP Hash 或外部 Session Store

一個完整的回答能把「選 Round Robin」變成一個展示系統設計思維的亮點。

生產環境的趨勢

大多數現今的負載均衡器（Nginx、HAProxy、AWS ALB）預設使用 Least Connections 或 Weighted Least Connections 的變體。Round Robin 仍然廣泛使用，但主要在無狀態、短請求的場景（CDN 邊緣節點）。了解這些演算法的區別比死記定義更重要——關鍵是能根據場景條件做出合理的選擇並說出理由。

小結

五種演算法從簡單到複雜排列：Round Robin → Weighted Round Robin → Least Connections → Weighted Least Connections → IP Hash（特殊用途）。記住兩個核心維度：是否考慮伺服器差異和是否考慮即時負載。有了這兩個維度，你就能在任何場景下做出合理的選擇。
