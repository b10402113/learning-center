Checksum 錯誤偵測

系統設計面試 · 通訊與可靠度 · 步驟 3/3

學習目標：理解 Checksum 如何檢測資料傳輸過程中的錯誤，認識其原理與常見應用場景。

問題背景

你從一台伺服器下載了一個 1GB 的檔案。但下載過程中，網路線被干擾了一下，某個位元（bit）從 0 翻轉成了 1。你怎麼知道檔案有沒有被損壞？你不可能逐位元比對原始檔案。

在分散式系統中，資料在節點之間傳輸時，可能因為儲存設備故障、網路干扰、軟體 bug 等原因而損壞。Checksum（校驗和）就是一種輕量級的機制，讓你能在不比對原始資料的情況下，快速判斷資料是否正確。

什麼是 Checksum？

Checksum 是對原始資料做一次數學運算後得到的固定長度的字串（包含字母和數字）。它的核心特性是：

  • 相同的資料 always 產生相同的 checksum
  • 不同的資料（哪怕只差一個位元）會產生不同的 checksum（機率極高）
  • 運算速度很快，即使資料很大也能快速計算

類比：Checksum 就像資料的「指紋」。每份資料有獨一無二的指紋，只要比對指紋就能判斷兩份資料是否相同。

Checksum 的運作流程

1. 儲存時

  1. 伺服器計算資料的 checksum
  2. 把 checksum 與資料一起儲存

2. 傳輸時

  1. 發送方計算資料的 checksum，與資料一起傳輸
  2. 接收方收到後，獨立計算一次 checksum
  3. 比對兩個 checksum：如果相同，資料正確；如果不同，資料已損壞

3. 讀取時

  1. 從儲存設備讀取資料和它對應的 checksum
  2. 獨立計算一次 checksum
  3. 比對兩者，判斷資料是否在儲存過程中損壞

常見的 Hash 函數

Checksum 通常使用加密雜湊函數（Cryptographic Hash Function）來計算。以下是常見的幾種：

演算法輸出長度安全性用途
MD5128 bits（32 hex）低（已發現碰撞）檔案完整性檢查（非安全性用途）
SHA-1160 bits（40 hex）中（已不建議用於安全性）程式碼簽章、Git commit ID
SHA-256256 bits（64 hex）高區塊鏈、安全憑證、系統設計首選
SHA-512512 bits（128 hex）極高高安全性需求場景

在系統設計面試中，你通常不需要深入討論 hash 函數的數學原理，但要知道SHA-256 是目前的標準選擇，MD5 和 SHA-1 已不建議用於安全性用途。

Checksum 的局限

Checksum 能偵測到大多數的資料損壞，但不是萬能的：

  • 碰撞（Collision）：兩份不同的資料可能產生相同的 checksum。但使用 SHA-256 時，碰撞的機率微乎其微（約 2-128）。
  • 無法修正錯誤：Checksum 只能告訴你「資料壞了」，但不能告訴你哪裡壞了，也無法修正。你需要重新傳輸或從備份恢復。
  • 計算成本：對超大檔案計算 SHA-256 需要時間，但通常可以接受（現代 CPU 每秒可計算數 GB）。

與其他機制的比較

機制用途能修正錯誤？成本
Checksum偵測資料損壞否低（只需計算 hash）
ECC 記憶體偵測並修正位元翻轉是中（硬體成本）
RAID硬碟故障時恢復資料是（透過冗餘）高（多顆硬碟）
副本複製節點故障時恢復資料是（從其他副本讀取）高（儲存空間）

Checksum 是最低成本的防線，通常與其他機制（如 RAID、副本）配合使用。

常見應用場景

  • 檔案下載：下載頁面提供 MD5/SHA-256 checksum，下載後比對確認檔案完整。
  • 資料庫：儲存頁面的 checksum，讀取時比對偵測儲存設備故障。
  • 網路傳輸：TCP/IP 協議本身就有 header checksum，偵測傳輸過程中的位元翻轉。
  • 區塊鏈：每個區塊的 hash 連結前一個區塊的 hash，確保資料不可被竄改。
  • 快取系統：儲存快取資料時附帶 checksum，命中快取時先比對，避免返回損壞的快取資料。

在面試中怎麼用？

當你被問到「怎麼確保資料完整性」或「怎麼偵測儲存故障」，你可以：

  1. 先說問題：分散式系統中，資料在傳輸和儲存過程中可能損壞。
  2. 引入 Checksum：儲存時計算 checksum，讀取時比對，偵測損壞。
  3. 討論選擇：SHA-256 是標準選擇，MD5 適用於非安全性場景。
  4. 延伸：提到 Checksum 是最低成本的防線，通常與 RAID、副本等機制配合使用。
