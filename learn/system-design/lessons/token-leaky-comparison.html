Token Bucket 與 Leaky Bucket 演算法比較

system-design · rate-readwrite · Step 2/4

學習目標

掌握 Token Bucket 與 Leaky Bucket 兩種限流演算法的運作原理、差異與適用場景。

為什麼要比較這兩種

上一課提到限流有好幾種演算法，其中Token Bucket（令牌桶）和Leaky Bucket（漏桶）是最經典、最常被面試問到的兩種。它們解決同一個問題——控制流量速率——但用完全不同的思維方式，適用不同的場景。

把它們搞清楚，你在面試中面對「怎麼設計限流器」這類問題時，就能清楚解釋為什麼選某一種而不是另一種。

Token Bucket：令牌桶

工作原理

想像一個桶子，裡面裝著一些「令牌（token）」。系統以固定速率（如每秒 10 個）往桶裡放令牌，桶有容量上限（如 100 個）。每來一個請求，必須從桶裡拿走一個令牌才能通過；如果桶裡沒令牌了，請求就被拒絕。

組件 行為
令牌生成器 以固定速率（如 R 個/秒）往桶裡放令牌
桶容量（B） 桶最多能存 B 個令牌，超出的令牌會被丟棄
請求 每來一個請求，取走一個令牌；有令牌→通過，沒令牌→拒絕

一個具體例子

假設桶容量 B = 10，令牌生成速率 R = 2 個/秒。

  • 系統空閒 5 秒後，桶裡累積了 10 個令牌（滿了）。
  • 突然湧入 10 個請求，一次性全部通過（消耗 10 個令牌）。
  • 接下來 2 秒內，桶裡只有 4 個令牌（2×2），所以只能通過 4 個請求。

這就是 Token Bucket 的核心特點：允許突發流量。只要桶裡有令牌，短時間內可以通過大量請求。但長期來看，平均速率不超過 R。

關鍵特性

  • 允許突發（Burst）：桶可以累積令牌，短時間內放行大量請求
  • 長期速率可控：令牌以固定速率補充，長期平均速率不超過 R
  • 實作簡單：只需一個計數器和一個計時器

Leaky Bucket：漏桶

工作原理

想像一個底部有小孔的桶子。請求像水一樣倒入桶中，桶以固定速率從底部「漏出」請求。桶滿了，新進來的水（請求）就溢出（被拒絕）。

組件 行為
桶（Queue） 緩衝區，存放等待處理的請求
漏出速率 固定速率（如每秒 R 個）從桶底處理請求
溢出 桶滿時，新請求被拒絕或丟棄

一個具體例子

同樣假設桶容量 B = 10，漏出速率 R = 2 個/秒。

  • 突然湧入 10 個請求，全部進入桶中排隊。
  • 系統以每秒 2 個的速率穩定處理，5 秒後全部處理完畢。
  • 期間如果有第 11 個請求進來，桶已滿，直接被拒絕。

Leaky Bucket 的核心特點是：輸出永遠是平滑的。不管輸入多麼波動，輸出速率始終是 R。

關鍵特性

  • 輸出平滑：不管輸入多不穩定，輸出速率恆定
  • 排隊機制：超量請求在桶中排隊等待，不會立刻被拒絕（除非桶滿）
  • 無突發：即使系統有空閒能力，也不能一次性處理大量請求

核心差異對比

維度 Token Bucket Leaky Bucket
突發處理 ✅ 允許突發（桶有令牌就放行） ❌ 不允許突發（輸出恆定）
輸出模式 可能波動（取決於桶裡剩餘令牌） 永遠平滑（固定漏出速率）
排隊 不排隊——有令牌就過，沒有就拒絕 有排隊——超量請求在桶中等待
適合場景 允許突發的應用（API、影片串流） 需要平滑流量的場景（網路流量整形）
複雜度 較簡單（計數器 + 補充邏輯） 較簡單（佇列 + 定時處理）

面試中怎麼選

面試官問你「怎麼設計限流器」時，選哪種取決於需求：

  • 選 Token Bucket：當系統需要允許突發流量。例如 API 服務器——用戶偶爾發一波請求是正常的，你不希望因為限流太嚴格而影響正常體驗。大部分 API 限流器（如 AWS API Gateway、Nginx）都用 Token Bucket。
  • 選 Leaky Bucket：當系統需要嚴格的流量整形（traffic shaping）。例如網路設備要確保輸出流量恆定，不影響下游服務。或者你需要把不穩定的輸入轉換成穩定的輸出。

一個常見的面試回答模板：

「我會選擇 Token Bucket，因為我們的場景允許短時間的突發——例如用戶打開 App 時會同時發多個 API 請求。Token Bucket 可以在長期控制速率的同時，容忍這種合理的突發。」

小結

Token Bucket 用令牌控制速率，允許桶累積令牌以支持突發；Leaky Bucket 用佇列排隊，以固定速率漏出，輸出永遠平滑。面試中根據是否需要支持突發來選擇：API 服務通常選 Token Bucket，流量整形通常選 Leaky Bucket。
