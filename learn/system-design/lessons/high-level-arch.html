高層架構設計

YouTube/Netflix · Step 3/6

學習目標

設計系統整體高層架構，定義核心元件與它們之間的交互關係。

從需求到架構

有了需求分析和容量估算，現在可以開始畫架構圖了。高層架構（High Level Design）的目標是把系統拆成幾個核心元件（Components），並說明它們之間如何互動。面試中這部分通常佔 10-15 分鐘，你需要在白板上畫出一個清晰的架構圖。

YouTube 的高層架構可以分成兩條主要的資料流：上傳流程（Write Path）和觀看流程（Read Path）。這兩條流程的設計完全不同——上傳是寫入密集的非同步流程，觀看是讀取密集的同步流程。

上傳流程（Write Path）

當使用者上傳一部影片，資料會經過以下步驟：

1. API 層——使用者透過 API 上傳影片。API 伺服器負責驗證、限流、並把影片推送到處理佇列。API 層不直接處理影片檔案，而是把大檔案的處理交給後端。

2. 處理佇列（Processing Queue）——每部上傳的影片會被推送到一個訊息佇列（如 Kafka）。佇列的作用是解耦：上傳和處理可以獨立擴展，即使處理叢集暫時過載，影片也不會丟失。

3. 轉碼器（Encoder）——從佇列中取出影片，轉成多種解析度和格式（4K、1080p、720p、480p，以及 H.264、H.265 等編碼格式）。轉碼是 CPU 密集型工作，需要專門的轉碼叢集。

4. 縮圖生成器（Thumbnail Generator）——自動為每部影片生成幾張縮圖。縮圖是使用者決定是否點擊觀看的關鍵。

5. 儲存——轉碼後的影片和縮圖被儲存到分散式檔案系統（如 HDFS 或物件儲存 S3）。

觀看流程（Read Path）

當使用者點擊播放一部影片，資料會經過以下步驟：

1. API 層——使用者發送播放請求。API 伺服器先從元資料庫中查詢影片資訊（標題、描述、觀看次數等），同時把請求導向正確的影片來源。

2. 快取層——熱門影片的元資料和影片片段會被快取。快取的命中率直接影響播放延遲。YouTube 的快取策略是多層的：記憶體快取 → SSD 快取 → CDN 邊緣節點 → 源頭儲存。

3. CDN——影片檔案透過 CDN 分發到全球各地。使用者從最近的 CDN 節點取得影片串流，而不是直接從源頭伺服器下載。這大幅降低了延遲和源頭伺服器的壓力。

4. 負載均衡器——把使用者的請求分散到多台伺服器。一致性雜湊（Consistent Hashing）可以確保同一部影片的請求導向同一個快取節點，提高快取命中率。

API 設計

在高層架構中，你需要定義幾個核心 API。YouTube 的 API 通常使用 REST 風格：

上傳影片——uploadVideo(api_dev_key, video_title, video_description, tags[], category_id, video_contents)。參數包含 API 開發者金鑰（用於認證）、影片元資料、以及影片內容。

搜尋影片——searchVideo(api_dev_key, search_query, page_size, page_token)。支援分頁搜尋，避免一次回傳太多結果。

觀看影片——getVideo(api_dev_key, video_id)。回傳影片的元資料和播放串流的 URL。

這些 API 的設計要考慮認證（限制濫用）、限流（防止 DDoS）、以及版本控制（未來功能擴展）。

關鍵設計決策

在高層架構中有幾個重要的設計決策：

上傳與處理分離——上傳 API 不直接處理影片轉碼，而是推送到佇列。這讓上傳流程快速回應使用者，轉碼在後端慢慢做。

元資料與影片分離——影片檔案存在物件儲存，元資料存在關聯式資料庫。兩者用不同的技術和擴展策略。

讀取走快取和 CDN——讀取密集的系統，快取是核心。幾乎所有讀取請求都應該先命中快取，只有快取miss才回源。

寫入走佇列——寫入操作（上傳、評論、統計更新）先進佇列，再由後端工作者處理。這提高了系統的彈性和可靠性。

你的經驗怎麼連結？

你做過 REST API，這些 API 設計你應該很熟悉。YouTube 的 API 本質上就是你做過的 API 的放大版。差別在於：你需要加上佇列來處理非同步工作（你之前可能是同步處理），加上快取來應對讀取壓力（你之前可能不需要），加上 CDN 來分發大檔案（你之前可能只處理小檔案）。
