動態時間軸生成優化

學習目標

能夠設計高效能的 Twitter 時間軸生成演算法，處理延伸需求如分頁與快取預生成。

1. 時間軸是什麼？

時間軸（Timeline）是 Twitter 的核心功能：當你打開 App，看到的是你追蹤的所有人的推文，按時間或相關性排序。這看起來很簡單，但背後的技術挑戰巨大——因為每個人的時間軸都不同，而且要即時更新。

假設你追蹤了 200 個人，每次載入時間軸時，系統需要從這 200 個人的推文中找出最新的、最相關的，合併排序後回傳給你。如果你的追蹤對象是名人，他們的推文被數百萬人同時讀取——這就是時間軸的效能瓶頸。

2. 兩種生成模型

拉取模型（Pull / Fan-out on read）

當使用者打開時間軸時，系統即時從所有追蹤對象的推文中拉取最新內容，合併排序後回傳。

優點缺點
即時性最高，永遠看到最新推文每次載入都要查詢大量資料，延遲高
寫入簡單，不需要額外處理追蹤數百人時，查詢成本呈線性增長

推取模型（Push / Fan-out on write）

當有人發布推文時，系統主動將這條推文推送到所有追蹤者的預生成時間軸中。

優點缺點
讀取極快，時間軸已經預先排好寫入成本高，需要更新所有追蹤者的時間軸
適合讀取密集型系統超級使用者發推時，需要推送給數百萬人

混合模型（Hybrid）

Twitter 實際使用的是混合模型：

  • 普通使用者的推文用推取模型（fan-out on write）——推文被推送到追蹤者的時間軸
  • 超級使用者的推文用拉取模型（fan-out on read）——讀取時才即時合併

這樣做的原因是：超級使用者有數百萬追蹤者，如果用推取模型，一條推文就要更新數百萬個時間軸，寫入成本不可接受。

面試重點：混合模型是 Twitter 時間軸設計的精髓。你必須能解釋為什麼純推取或純拉取都不夠好，以及如何根據使用者規模選擇策略。

3. 分頁與增量載入

時間軸不可能一次載入所有推文——使用者只看得到螢幕上的幾條。分頁（pagination）是必須的。

游標分頁

使用 since_id 和 max_id 進行游標式分頁：

  • 初次載入：不帶參數，回傳最新的 N 條推文
  • 向下捲動（載入更多）：帶上最後一條推文的 max_id，回傳更早的 N 條
  • 刷新（載入新推文）：帶上第一條推文的 since_id，回傳更新的推文

快取預生成

為了進一步加速，系統可以預先生成並快取時間軸的前 N 頁。使用者打開 App 時，直接從快取載入，延遲可以降到毫秒級。

4. 延伸需求

搜尋推文

除了時間軸，使用者還可以搜尋推文。搜尋需要全文檢索能力，通常用 Elasticsearch 等搜尋引擎實現，而非直接查資料庫。

趨勢話題（Trending）

趨勢話題需要即時分析大量推文，找出短時間內被大量討論的關鍵字。這通常用流處理（stream processing）實現，如 Apache Kafka + Flink。

推文通知

當你的推文被最愛或轉推時，你需要收到通知。這可以用訊息佇列（message queue）實現：推文互動事件被放入佇列，通知服務從佇列中消費並推送給使用者。

5. 設計取捨總結

決策選擇原因
時間軸生成混合模型平衡讀取延遲和寫入成本
分頁方式游標分頁支援增量載入，不會漏推文
搜尋Elasticsearch全文檢索不在關聯式資料庫的強項
趨勢流處理需要即時分析大量資料流
