索引類型與最佳實踐

system-design · indexes · Step 4/4

學習目標：認識常見索引類型（主索引/次要索引、叢集/非叢集索引）以及在系統設計中如何正確使用索引。

兩種分類方式

索引有兩種主要的分類方式，它們描述的是不同的維度：

分類維度 類型 A 類型 B
按角色分 主索引（Primary Index） 次要索引（Secondary Index）
按儲存方式分 叢集索引（Clustered Index） 非叢集索引（Non-Clustered Index）

主索引 vs 次要索引

主索引（Primary Index）

主索引建立在主鍵（Primary Key）上。每張表只能有一個主索引，因為主鍵是唯一的。在 MySQL InnoDB 中，主索引就是叢集索引——資料表的物理排序就是按照主鍵來的。

次要索引（Secondary Index）

次要索引建立在非主鍵欄位上。一張表可以有多個次要索引，每個次要索引的葉子節點存的是主鍵值（而不是資料的物理位置）。這意味著透過次要索引找到主鍵後，還需要一次額外的查找才能拿到完整資料——這就是所謂的回表查找（Lookup）。

類比：主索引就像書的正文頁碼——直接翻到那一頁就有內容。次要索引就像書的索引——先找到頁碼，再翻到那一頁看內容。

叢集索引 vs 非叢集索引

叢集索引（Clustered Index）

叢集索引決定了資料在磁碟上的物理排列順序。資料表的資料行本身就是按照叢集索引的鍵排序存放的。一張表只能有一個叢集索引（因為物理順序只有一種）。

  • 優點：範圍查詢極快，因為相鄰的資料在磁碟上也是相鄰的（順序讀取）
  • 缺點：插入時可能導致頁分裂（page split），因為要維持物理順序

非叢集索引（Non-Clustered Index）

非叢集索引是一種獨立於資料物理儲存的索引結構。它的葉子節點存的是指向資料的指針（或主鍵值），資料本身的物理順序不受影響。

  • 優點：可以建多個，不影響資料的物理儲存
  • 缺點：範圍查詢不如叢集索引快（資料在磁碟上可能不連續）

覆蓋索引（Covering Index）

覆蓋索引是一種優化技巧：當索引包含了查詢所需的所有欄位時，資料庫不需要回表查找，直接從索引就能返回結果。

例如，你有一個查詢：

SELECT name, email FROM users WHERE age > 25

如果你建了一個 (age, name, email) 的複合索引，這個查詢只需要掃描索引就能拿到所有需要的資料，完全不用讀取資料表——速度極快。

複合索引的欄位順序

當你建一個包含多個欄位的複合索引時，欄位順序非常重要。規則是：

  • 把等值條件（WHERE x = 1）的欄位放在前面
  • 把範圍條件（WHERE y > 10）的欄位放在後面

例如，查詢 WHERE status = 'active' AND created_at > '2024-01-01'，最佳索引順序是 (status, created_at)，而不是 (created_at, status)。

這是因為 B+ 樹先用第一個欄位定位範圍，再用第二個欄位進一步篩選。順序反了，第二個欄位的範圍條件就無法有效利用索引。

最佳實踐總結

原則 說明
只為高頻查詢建索引 不為低頻或一次性查詢建索引，維護成本不值得
優先建複合索引 一個複合索引可以服務多個查詢，減少索引數量
注意欄位順序 等值條件在前，範圍條件在後
利用覆蓋索引 索引包含查詢所有欄位，避免回表查找
避免過多索引 每多一個索引就多一份寫入和維護成本
定期監控索引使用情況 移除長期未使用的索引

面試中的關鍵點

在系統設計面試中，面試官期望你能：

  • 區分叢集索引和非叢集索引的差異和使用場景
  • 解釋回表查找是什麼，以及如何用覆蓋索引避免它
  • 討論複合索引的欄位順序對查詢效能的影響
  • 根據查詢模式判斷建什麼索引、建幾個

小結

索引類型的選擇和組合直接影響查詢效能。主索引是查詢的快速路徑，次要索引是輔助工具但有回表代價。叢集索引讓範圍查詢更快但限制了只能有一個。複合索引的欄位順序決定了它能服務哪些查詢。掌握這些，你就能在面試中自信地設計索引策略。
