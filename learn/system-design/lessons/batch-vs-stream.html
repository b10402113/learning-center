處理模式：批次與串流

system-design · data-strategies · Step 4/5

學習目標

區分批次處理與串流處理的差異，理解兩種處理模式的適用場景與取捨。

兩種完全不同的節奏

想像兩家餐廳。一家是自助餐——食材先累積到一定量，廚師一次煮一大鍋，所有人一起吃。另一家是現點現做——客人一下單，廚師立刻開始做，做好一份上一份。

自助餐就是批次處理，現點現做就是串流處理。兩者都在「處理資料」，但節奏完全不同。

批次處理（Batch Processing）

批次處理是把資料累積到一定量後，一次性處理。資料不是來一個處理一個，而是先收集，等到某個時間點或數量門檻，才整批處理。

資料收集（累積中...）→ [觸發] → 整批處理 → 輸出結果

實際例子：

  • 薪資計算：公司不會每秒計算員工的薪水，而是月底一次性處理所有工時和薪資
  • 報表生成：每天凌晨跑前一天的銷售報表，不需要即時
  • ETL（抽取-轉換-載入）：把多個資料庫的資料晚上抽出來、清洗、載入到資料倉儲
  • 備份：每天凌晨備份一次，不需要即時備份

批次處理的特點：

特點 說明
延遲處理 資料累積一段時間後才處理，結果有延遲
高吞吐量 一次處理大量資料，單位時間處理量大
資源效率高 可以安排在離峰時段運行，利用閒置資源
實現相對簡單 不需要處理即時資料流的複雜度

串流處理（Stream Processing）

串流處理是資料一到達就立刻處理，不需要等待。每一筆資料都是獨立即時處理的。

資料到達 → 立刻處理 → 立即輸出
資料到達 → 立刻處理 → 立即輸出
（持續不斷）

實際例子：

  • 信用卡詐欺偵測：每筆交易一發生就立刻分析，發現異常立即攔截
  • 系統監控：伺服器的 CPU、記憶體指標持續流入，異常時立即告警
  • 即時推薦：你在Netflix看了什麼，立刻影響你看到的推薦
  • 即時搜尋：你在 Twitter 搜尋時，結果需要包含幾秒鐘前才發的推文

串流處理的特點：

特點 說明
即時處理 資料一到達就立刻處理，延遲極低
複雜度高 需要處理資料排序、遺失、重複、背壓等問題
資源消耗大 需要持續運行，不能安排在離峰時段
容錯要求高 處理中斷會導致資料遺失或延遲

關鍵差異

維度 批次處理 串流處理
資料處理方式 整批累積後一次性處理 逐筆即時處理
延遲 分鐘到小時級 毫秒到秒級
吞吐量 高（批量處理效率高） 相對較低（逐筆處理）
複雜度 低 高（排序、遺失、背壓）
資源利用 可安排在離峰時段 需要持續運行
容錯 可以重新跑一次 中斷可能丟資料
適用場景 報表、備份、ETL、薪資 詐欺偵測、監控、即時推薦

選擇的判斷標準

核心問題只有一個：你的應用能接受多大的延遲？

如果你的使用者可以接受「明天早上看到昨天的報表」，用批次處理——簡單、便宜、高效。如果你的使用者需要「這筆交易有沒有詐欺，立刻告訴我」，用串流處理——複雜、昂貴，但不可或缺。

很多系統會兩者並用。例如一個電商平台：訂單處理用串流（即時確認庫存、發送通知），但銷售分析用批次（每天跑一次前一天的彙總報表）。

面試中的關鍵點

  • 能清楚解釋批次和串流的處理節奏差異
  • 能根據延遲需求和場景選擇處理模式
  • 能說明兩種模式的複雜度和資源消耗差異
  • 能指出為什麼生產系統常常兩者並用

小結

批次處理適合能容忍延遲的場景（報表、備份），效率高但結果有延遲。串流處理適合需要即時反應的場景（詐欺偵測、監控），延遲低但複雜度高。選擇的關鍵是應用對延遲的容忍度，很多系統會兩者並用。
