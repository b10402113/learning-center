複製策略：主從與對等

system-design · data-strategies · Step 3/5

學習目標

理解主從複製與對等複製兩種架構的差異，並能依場景選擇適合的複製策略。

為什麼需要資料複製？

假設你的系統只有一個資料庫。當使用者量暴增時，所有讀取和寫入都擠在一台機器上，很快就會過載。更糟的是，如果這台機器硬碟壞了，所有資料就消失了。

資料複製（Replication）就是把同一份資料複製到多台機器上。好處有二：一是讀取擴展——多台機器分攤讀取壓力；二是容錯——一台掛了，其他的還能提供服務。

但「怎麼複製」有兩種根本不同的架構：主從複製和對等複製。

主從複製（Primary-Replica）

主從複製也叫 Master-Slave Replication。核心邏輯：一個主節點負責所有寫入，多個從節點負責讀取。

寫入 → [Primary] → 同步 → [Replica 1]
                      → [Replica 2]
                      → [Replica 3]
讀取 ← [Replica 1/2/3]

用一個具體場景：你的電商網站有一個商品資料庫。所有商品資料的更新（新增商品、修改價格）都寫入 Primary。三台 Replica 從 Primary 同步資料。用戶查詢商品時，從任意一台 Replica 讀取。這樣讀取壓力分散到三台機器，寫入仍然集中在一台。

主從複製的關鍵特點：

特點 說明
單向資料流 資料只從 Primary 流向 Replica，反向不行
讀寫分離 Primary 處理寫入，Replica 處理讀取
中心化控制 Primary 是單點， Replica 的數量可水平擴展
同步/異步 同步複製強一致但慢，異步複製快但可能丟資料

你在用過的 Postgres/MySQL 就支援主從複製。多數 Web 應用都採用這種架構——寫入主庫，讀取從庫。

主從複製的問題

最大問題是 Primary 是單點故障。如果 Primary 掛了，整個系統無法寫入。解決方案是「故障轉移」（Failover）：從多個 Replica 中選一個升級為新的 Primary。但這個過程可能造成短暫的寫入中斷，而且如果異步複製有延遲，新 Primary 可能缺少部分資料。

對等複製（Peer-to-Peer）

對等複製的核心邏輯：每個節點都是平等的，任何節點都能讀和寫。

[Node A] ←→ [Node B]
  ↕            ↕
[Node C] ←→ [Node D]

沒有主從之分，每個節點維護自己的一份資料副本，資料在所有節點之間雙向同步。任何節點的寫入都會同步到其他節點。

對等複製的關鍵特點：

特點 說明
多向資料流 任何節點都能向其他節點同步資料
無中心化 沒有單一的控制點，每個節點自治
高可用 任何節點掛了，其他節點繼續服務
衝突處理 多個節點同時修改同一筆資料時需要解決衝突

Cassandra、CouchDB 是典型的對等複製資料庫。當你需要「任何地理位置的用戶都能就近寫入」時，對等架構很合適——例如全球分佈的社交網路。

對等複製的問題

最大問題是衝突處理。當兩個節點同時修改同一筆資料時，誰的版本算「正確」？常見策略有：最後寫入勝出（Last Write Wins）、應用層合併、向量時鐘（Vector Clock）。每種策略都有取捨，這也是為什麼多數中小規模系統寧願選主從架構——簡單可控。

兩種架構的選擇

維度 主從複製 對等複製
控制模式 中心化（Primary 控制） 去中心化（每個節點自治）
資料流 單向（Primary → Replica） 多向（任何節點 ↔ 任何節點）
讀取擴展 容易（加 Replica） 容易（加節點）
寫入擴展 困難（只有 Primary 能寫） 容易（任何節點能寫）
故障處理 需要 Failover 機制 天然容錯（掛一個不影響）
複雜度 低 高（衝突處理）
適用場景 傳統 Web 應用、讀多寫少 全球分佈系統、高可用需求

面試中的關鍵點

  • 能清楚解釋主從和對等的資料流動方向差異
  • 能說明主從架構的單點故障問題和 Failover 方案
  • 能解釋對等架構的衝突處理挑戰
  • 能根據讀取/寫入比例和可用性需求選擇架構

小結

主從複製簡單可控，適合讀多寫少的傳統 Web 應用；對等複製高可用但複雜，適合全球分佈系統。選擇時要權衡讀取擴展、寫入擴展、故障處理和衝突處理的取捨。
