Load Balancer vs API Gateway 比較

system-design · arch-patterns · Step 1/5

學習目標

理解 Load Balancer 與 API Gateway 的核心差異，以及何時該選擇哪一種架構。

從倉庫發貨說起

想像你經營一個網購平台。當訂單湧進來時，你需要做兩件事：

  1. 把包裹分配給不同的出貨站台——不要讓某個站台堆滿包裹，其他站台卻閒著。
  2. 在前台設一個接待員——客人進來說「我要退貨」「我要查訂單」「我要換貨」，接待員聽懂需求後把人帶到對應的櫃台。

負載均衡器（Load Balancer）就是那個分配包裹的系統；API Gateway（API 閘道）就是那個聽懂需求的接待員。兩者都在管理流量，但做的事完全不同。

Load Balancer：把工作分出去

Load Balancer（負載均衡器）的核心任務只有一個：把進來的網路請求分配到多個後端伺服器，避免任何一台過載。

面向 Load Balancer 做什麼
分配依據 根據連線數、回應時間、伺服器健康度等指標，決定把請求導到哪台伺服器
感知層級 工作在網路層（L4）或應用層（L7），但不管請求的「語意」
核心價值 高可用（high availability）、高效能（performance）、可擴展（scalability）
不做的事 不理解 API 語意、不做身份驗證、不做請求轉換

舉例：你的網購平台有 3 台 Web 伺服器。Load Balancer 每收到一個 HTTP 請求，就依 Round Robin（輪流）或其他演算法把請求導到其中一台。它不在乎這個請求是「查詢訂單」還是「新增商品」——它只管分發。

API Gateway：聽懂需求再分發

API Gateway（API 閘道）是一個 API 管理工具，坐在客戶端和一組後端微服務之間。它不只是「分發」，還會理解請求的語意，並做額外處理。

功能 做什麼 實際例子
請求路由 根據 API 路徑把請求導到正確的微服務 /api/orders → 訂單服務，/api/users → 用戶服務
API 聚合 一次請求同時呼叫多個微服務，合併結果回傳 客戶端要「我的訂單 + 用戶資料」，Gateway 同時叫兩個服務再合併
身份驗證 統一驗證 JWT token，微服務不用各自處理 所有 API 請求先過 Gateway 的 auth 層
限流 限制每個客戶端的請求頻率，防止濫用 免費用戶每分鐘最多 60 次請求
協議轉換 前端用 REST，後端微服務可以用 gRPC Mobile App 用 HTTP/JSON，Gateway 轉成 gRPC 給後端

核心差異一覽

面向 Load Balancer API Gateway
關注點 分散流量，避免伺服器過載 管理、路由、保護 API 調用
功能範圍 流量分配 + 健康檢查 路由 + 驗證 + 限流 + 聚合 + 轉換
感知層級 網路層 / 傳輸層 應用層（理解 API 語意）
典型部署 Web 伺服器前方 微服務架構的統一入口
面試常見場景 「如何讓系統支援高併發？」 「如何統一管理多個微服務的 API？」

兩者可以一起用嗎？

完全可以，而且這是最常見的架構。典型的安排是把 Load Balancer 放在 API Gateway 前面：

用戶端 → Load Balancer → API Gateway 伺服器叢集 → 微服務叢集

Load Balancer 負責把流量分散到多個 API Gateway 實例，避免 Gateway 本身成為瓶頸；API Gateway 則處理所有 API 級別的邏輯（路由、驗證、限流等）。

反過來把 API Gateway 放在 Load Balancer 前面也可以——Gateway 先做語意路由，再把請求導到內部的 Load Balancer，由 LB 分散到微服務的多個實例。選擇哪種取決於你的架構需求。

面試中的關鍵點

  • Load Balancer 的核心是分散流量，讓多台伺服器對外看起來像一台
  • API Gateway 的核心是統一入口，處理 API 級別的跨領域關注點
  • 兩者不互斥：LB 管「分發」，Gateway 管「語意」，常常搭配使用
  • 面試時被問「該用哪個」，先問清楚是純流量分散還是需要 API 管理能力

小結

Load Balancer 和 API Gateway 都在管理流量，但關注點不同：LB 專注於把工作分散到多台伺服器（不分語意），Gateway 則理解 API 語意並提供路由、驗證、限流等管理功能。兩者互補，常常一起使用。下一課會看看 API Gateway 跟「直接暴露微服務」有什麼差異。
