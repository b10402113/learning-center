需求分析與範圍定義

YouTube/Netflix · Step 1/6

學習目標

定義 YouTube 串流平台的功能性與非功能性需求，明確設計範圍與目標。

為什麼要從需求開始？

在系統設計面試中，面試官會拋出一個開放式題目，比如「設計一個 YouTube」。拿到題目後的第一件事不是畫架構圖，而是釐清需求。原因很簡單：你不知道系統要做什麼、做到什麼程度，就無法做出合理的架構決策。

需求分析決定兩件事：功能性需求（Functional Requirements）告訴你系統「做什麼」；非功能性需求（Non-functional Requirements）告訴你系統「做得怎麼樣」。面試中先把這兩類需求攤開來，面試官才會覺得你是在「設計系統」而不是「堆砌技術」。

功能性需求：系統做什麼？

設計 YouTube 時，功能性需求要從最核心的使用場景開始。我們不需要把 YouTube 的所有功能都列出來，而是挑出面試中最重要的幾個：

1. 上傳影片——使用者可以上傳影片到平台。系統需要接收影片檔案、儲存它，並在之後提供給其他人觀看。這是最基本的寫入操作。

2. 觀看與分享影片——使用者可以搜尋、觀看、分享影片。這包含了搜尋功能（根據影片標題）和播放功能。這是系統使用量最大的部分，也是讀取操作的核心。

3. 記錄影片統計——系統要能記錄和展示影片的觀看次數、點讚數、點踩數等統計資料。這些數據是使用者體驗的一部分，也是推薦系統的基礎。

4. 評論功能——使用者可以在影片下方留言，系統要能儲存和顯示這些評論。這是一個相對獨立的子系統。

非功能性需求：系統做得怎麼樣？

功能性需求告訴你「做什麼」，非功能性需求告訴你「做得怎麼樣」。面試中這部分往往更決定架構走向：

高可用性（High Availability）——系統 24/7 運作，不能有明顯停機。YouTube 是全球服務，任何中斷都會影響數億使用者。

低延遲（Low Latency）——影片播放的延遲要低。使用者點擊播放後如果要等好幾秒才開始播放，體驗會很差。這也是為什麼 CDN 和快取如此重要。

一致性（Consistency）——使用者上傳的影片必須保證之後能被搜尋到和觀看到。系統不能丟失資料。

可擴展性（Scalability）——系統要能隨著使用者和影片數量的成長而水平擴展。YouTube 每分鐘有數百小時的影片上傳，架構必須能應付這種規模。

YouTube 的關鍵特性：讀取密集

YouTube 最重要的系統特性是讀取密集（read-heavy）。原因是：影片觀看的頻率遠高於上傳的頻率。面試中可以假設一個典型的讀寫比（read:write ratio）大約是 200:1——每上傳一部影片，就有 200 次觀看。

這個特性直接影響架構決策：系統要優先優化讀取效能，而不是寫入效能。快取、CDN、負載均衡都是為了應對讀取密集而存在的。

另一個特性是影片檔案很大。不同於文字或圖片，影片檔案動輒數十 MB 到數 GB。這意味著儲存和頻寬成本會非常高，系統需要高效的儲存管理策略。

你的經驗怎麼連結？

你做過 REST API，用過 Postgres 和 Redis。YouTube 的需求分析其實會用到你熟悉的概念：你需要決定 API 設計（REST vs RPC）、資料庫選型（SQL 存元資料、物件儲存存影片）、以及快取策略（Redis 緩存熱門影片的元資料）。差別在於規模——你之前可能只服務幾百個用戶，YouTube 要服務數億。但思考邏輯是一樣的。

面試技巧：需求分析的節奏

在面試中，需求分析通常佔 3-5 分鐘。你不需要列出所有功能，而是要與面試官確認範圍。一個好的做法是：

1. 先列出 3-5 個核心功能性需求
2. 再列出 3-4 個非功能性需求
3. 詢問面試官：「我們是設計完整版 YouTube 還是簡化版？」
4. 確認後才進入容量估算和架構設計

這樣做有兩個好處：一是讓面試官覺得你有系統性思考；二是避免你在不需要的功能上浪費時間。
