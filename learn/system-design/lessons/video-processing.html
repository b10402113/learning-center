影片處理與去重

YouTube/Netflix · Step 5/6

學習目標

設計上傳影片的後續處理流程，包括轉碼、縮圖生成，並解決影片重複的問題。

影片上傳後發生什麼？

上一課提到，使用者上傳影片後，影片會被推送到處理佇列。但從「一部原始影片」到「使用者可以流暢播放的多種版本」，中間還有很多工作。這個過程就是影片處理管線（Video Processing Pipeline）。

影片處理是 CPU 密集型工作，一部 10 分鐘的 1080p 影片可能需要幾十分鐘的轉碼時間。所以 YouTube 必須建立一個非同步、可擴展的處理叢集，讓數千部影片同時被處理。

轉碼（Encoding）

轉碼是影片處理的核心。原始影片通常只有一種格式和解析度，但使用者的裝置和網路條件千差萬別：有人用 4K 電視，有人用 3G 手機。所以同一部影片需要轉成多種版本：

解析度——4K（2160p）、1080p、720p、480p、360p。高解析度適合大螢幕和高速網路，低解析度適合小螢幕和慢速網路。

編碼格式——H.264（相容性最廣）、H.265（壓縮效率更高，但支援度較低）、VP9（YouTube 自家格式）。不同格式有不同的壓縮效率和裝置相容性。

位元率（Bitrate）——同一解析度下，高畫質影片需要更高的位元率。系統需要根據網路條件動態調整位元率，這就是自適應串流（Adaptive Streaming）的基礎。

一部原始影片可能需要轉成 10-20 個版本。這也是為什麼儲存需求會比原始檔案大好幾倍。

縮圖生成（Thumbnail Generation）

縮圖是使用者決定是否點擊觀看的關鍵。系統需要為每部影片自動生成幾張候選縮圖：

自動截取——從影片中均勻取幾個時間點的畫面（如 25%、50%、75% 處），作為候選縮圖。

創作者上傳——允許創作者上傳自訂縮圖。這是最常見的方式，因為創作者最了解哪個畫面最能吸引觀眾。

縮圖通常儲存為 JPEG 或 WebP 格式，大小在 100-200 KB 之間。縮圖會被快取到 CDN，確保載入速度夠快。

影片去重（Video Deduplication）

在一個有數億使用者的平台上，影片重複是一個嚴重的問題。重複影片的來源很多：

完全相同——同一部影片被不同使用者多次上傳。可能是盗版，也可能是使用者不小心重複上傳。

近似相同——同一部影片的不同版本，比如不同的解析度、編碼格式、或加了水印/邊框。

部分相同——一部長影片的片段被單獨上傳，或者不同影片中包含相同的片段。

重複影片的影響有三方面：

儲存浪費——完全相同的影片不需要儲存多份。YouTube 每天上傳數百萬部影片，即使只有 5% 是重複的，也浪費了大量儲存空間。

搜尋體驗——搜尋結果中出現大量重複內容，使用者體驗很差。

推薦品質——推薦系統如果把重複影片推薦給使用者，會降低推薦品質。

去重的方法

指紋比對（Fingerprinting）——為每部影片生成一個「指紋」——一組代表影片內容的數學特徵。上傳新影片時，先與現有影片的指紋比對。如果指紋高度相似，就判定為重複。YouTube 使用的 Content ID 系統就是基於這種技術。

雜湊比對——計算影片檔案的雜湊值（如 MD5 或 SHA-256）。完全相同的檔案會有相同的雜湊值。但這種方法只能檢測完全相同的檔案，無法處理近似重複。

感知雜湊（Perceptual Hashing）——更進階的方法，能檢測視覺上相似的影片，即使編碼不同或經過裁剪。pHash（Perceptual Hash）是常用的一種。

實際系統通常組合使用多種方法：先用快速的雜湊過濾完全相同的檔案，再用指紋比對檢測近似重複。

處理管線的架構

整個影片處理管線可以拆成幾個獨立的服務：

上傳服務——接收使用者上傳的影片，驗證格式，推送到佇列。

轉碼服務——從佇列取出影片，並行轉成多種版本。轉碼服務需要能水平擴展——新增機器就能處理更多影片。

縮圖服務——生成影片縮圖。

去重服務——在轉碼前或轉碼後，比對影片指紋，決定是否跳過儲存。

儲存服務——把處理後的影片和縮圖寫入物件儲存。

這些服務之間透過訊息佇列（如 Kafka）連接，確保每個服務可以獨立擴展，不會互相阻塞。

你的經驗怎麼連結？

你用過 Redis 和 Postgres，但可能沒處理過大檔案的非同步處理。YouTube 的影片處理管線本質上是一個工作管線（Job Pipeline）：接收任務 → 排隊 → 處理 → 儲存。這跟你之前用過的 Background Job 概念一樣，只是 YouTube 要同時處理數千個「任務」，每個任務需要幾十分鐘的 CPU 時間。
