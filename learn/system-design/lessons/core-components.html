核心元件設計

Dropbox 系統設計 · Step 3/5

學習目標

詳細設計每個核心元件，說明其職責、互動方式與設計選擇取捨。

元件一：客戶端（Client）

客戶端是安裝在用戶設備上的應用程式，它是整個系統的入口。客戶端做三件事：

  • 監控工作區：持續監聽用戶指定的資料夾，偵測檔案的新增、修改、刪除事件
  • 分塊上傳：將變更的檔案切成 4 MB 的分塊（chunk），逐塊上傳到雲端儲存
  • 本地資料庫：維護一份本地的檔案元數據副本，用於快速比對哪些分塊需要同步

本地資料庫的存在有一個關鍵好處：增量同步。當用戶修改一個 100 MB 的檔案時，客戶端可以比對本地資料庫，發現只有第 3 個分塊變了，於是只上傳這一個分塊——而不是重新上傳整個檔案。

客戶端的狀態機

客戶端有三種狀態：

狀態行為
上線（Online）即時同步變更到雲端
離線（Offline）將變更記錄在本地隊列，等待上線後重播
同步中（Syncing）正在上傳/下載分塊，使用者看到進度條

元件二：元數據資料庫（Metadata Database）

元數據資料庫儲存所有檔案的描述資訊。它的設計選擇直接影响系統的查詢效能和一致性。

儲存什麼？

  • 檔案資訊：檔名、路徑、大小、建立/修改時間、 MIME 類型
  • 版本歷史：每個檔案的版本鏈，每個版本對應一組分塊 ID
  • 分塊索引：檔案由哪些分塊組成、每個分塊的雜湊值和儲存位置
  • 用戶資訊：帳號、設備列表、工作區設定
  • 共享與權限：誰可以存取哪些檔案/資料夾

資料庫選型

可以用關聯式資料庫（MySQL、PostgreSQL）或 NoSQL（DynamoDB）。關鍵考量：

  • 關聯式：適合複雜查詢（如「列出某用戶所有共享檔案」）、強一致性
  • NoSQL：適合高寫入吞吐、水平擴展

實際系統中，Dropbox 可能混合使用：核心元數據走 MySQL（需要 ACID），分享/評論等社交功能走 NoSQL。

元件三：同步服務（Synchronization Service）

同步服務是整個架構最核心的元件。它做三件事：

  1. 接收更新：從消息隊列的請求隊列中拉取客戶端的變更通知
  2. 更新元數據：將變更寫入元數據資料庫（新版本、新分塊索引）
  3. 通知訂閱者：將更新推送到響應隊列，讓其他設備拉取

長輪詢（Long Polling）

客戶端如何知道有新更新？同步服務使用長輪詢：客戶端發送一個 HTTP 請求，服務端不會立即回應，而是等到有新更新時才返回。如果一段時間沒有更新，服務端返回空回應，客戶端再發新請求。這比傳統輪詢更高效——不需要每秒打一次伺服器。

元件四：消息隊列（Message Queuing Service）

消息隊列是同步服務和客戶端之間的橋樑。它有兩個通道：

請求隊列（Request Queue）

全局共享。所有客戶端往裡面寫更新通知（「用戶 A 的檔案 X 的第 3 個分塊更新了」）。同步服務從這裡拉取所有更新。

響應隊列（Response Queue）

每個客戶端各一個。同步服務把屬於該客戶端的更新推送到這裡。客戶端上線後，從自己的響應隊列中拉取所有待處理的更新。

為什麼用消息隊列？

  • 解耦：客戶端不需要直接連線同步服務
  • 可靠性：設備離線時更新不會丟失
  • 擴展性：可以水平擴展消息隊列來處理更多客戶端

元件五：雲端/區塊儲存（Cloud/Block Storage）

儲存實際的檔案分塊。客戶端直接與雲端儲存互動上傳和下載，不需要經過同步服務。

為什麼要分塊？

  • 增量同步：只傳輸變更的分塊，不是整個檔案
  • 並行傳輸：多個分塊可以同時上傳/下載
  • 容錯：傳輸失敗只需重傳一個分塊
  • 去重：相同內容的分塊只存一份（用雜湊值比對）

儲存選型

物件儲存（如 Amazon S3、Google Cloud Storage）是首選：幾乎無限擴展、低成本、高持久性（99.999999999%）。也可以用自建的區塊儲存伺服器。
