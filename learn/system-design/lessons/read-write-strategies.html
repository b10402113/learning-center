讀寫密集系統的設計策略

system-design · rate-readwrite · Step 4/4

學習目標

掌握針對讀密集與寫密集系統分別適用的設計優化策略。

從上一課的問題出發

上一課我們學會了區分讀密集和寫密集系統。知道了系統的類型之後，下一步就是：怎麼設計才能讓它跑得好？

不同的工作負載需要不同的設計策略。硬把讀密集的策略套在寫密集系統上，或者反過來，只會讓問題更嚴重。這一課整理兩套完整的設計武器庫。

讀密集型系統的設計策略

策略一：重度快取

讀密集型系統最有效的武器就是快取（Caching）。核心思路：把熱門資料從資料庫搬到更快的存取層（如 Redis、Memcached），讓大部分讀取請求根本不碰資料庫。

快取層級 位置 特點
應用層快取 應用伺服器記憶體 速度最快，但每個實例各存一份，一致性難保證
分散式快取 Redis / Memcached 集群 所有實例共用，易擴展，最常見的選擇
資料庫層快取 資料庫內建緩衝池 對應用透明，但容量受限於資料庫配置
CDN 快取 邊緣節點 適合靜態資源，距離用戶最近，延遲最低

一個新聞網站的例子：文章發布後，快取層存儲文章內容和熱門文章列表。95% 的讀取請求從 Redis 返回，只有 5% 的冷門請求穿透到資料庫。資料庫壓力直接降到原來的 1/20。

策略二：讀取副本

當快取無法覆蓋所有讀取場景（如需要複雜查詢或資料即時性要求高），可以用讀取副本（Read Replica）。

原理：主資料庫（Primary）負責寫入，多個從資料庫（Replica）負責讀取。讀取請求被分散到多個副本，每個副本只需要承擔一小部分壓力。

適用場景：需要即時查詢最新資料的報表系統、搜尋引擎等。

策略三：資料庫優化

即使有了快取和副本，資料庫本身的查詢效能仍然重要：

  • 建立合適的索引：讀密集系統可以建立更多索引——索引佔空間，但換來查詢速度的大幅提升。
  • 優化查詢語句：避免 SELECT *，只查詢需要的欄位；使用 JOIN 而非多次單獨查詢。
  • 選擇適合的資料模型：反規範化（denormalization）在讀密集場景中很常見——用空間換時間，把常用資訊冗餘存儲以避免 JOIN。

策略四：CDN 分發

對於靜態內容（圖片、影片、CSS、JS），使用 CDN（Content Delivery Network）將內容分發到全球邊緣節點。用戶從最近的節點取得內容，不僅速度更快，還大幅減輕了源站的壓力。

寫密集型系統的設計策略

策略一：選擇高寫入吞吐量的資料庫

寫密集型系統的第一步是選對資料庫。傳統關聯式資料庫（如 MySQL、PostgreSQL）的 ACID 事務機制在高併發寫入下容易成為瓶頸。

資料庫 適合場景 寫入優勢
Cassandra 日誌、時序數據、IoT 分散式架構，寫入吞吐量可線性擴展
MongoDB 內容管理、即時數據 文檔模型，寫入不需要固定 schema
Redis（AOF 持久化） 即時數據、計數器 記憶體寫入，延遲極低

策略二：寫入分散（Sharding）

單台機器的寫入能力有上限。分片（Sharding）將資料分散到多台機器，每台機器只承擔一部分寫入壓力。

例如：按照用戶 ID 取模分片——用戶 A 的資料在 Shard 1，用戶 B 的資料在 Shard 2。每個 Shard 獨立處理寫入，整體寫入吞吐量等於所有 Shard 的總和。

分片的關鍵挑戰：選擇合適的分片鍵（shard key），避免熱點（hotspot）。如果所有寫入都集中在同一個 Shard，分片就失去了意義。

策略三：非同步處理（Async Processing）

寫密集型系統中，很多操作不需要即時完成。利用訊息佇列（Message Queue）將非關鍵路徑的寫入延遲處理：

  1. 用戶發送訊息 → 立即返回「已發送」→ 訊息進入 Kafka / RabbitMQ
  2. 後台消費者（Consumer）從佇列中取出訊息，異步寫入資料庫
  3. 如果消費者暫時處理不過來，訊息在佇列中排隊，不會丟失

好處：使用者感知到的延遲降低了（不用等資料庫寫入完成），系統的寫入吞吐量由消費者的處理能力決定，可以水平擴展。

策略四：批量寫入（Batch Write）

與其每筆資料都單獨寫入資料庫，不如累積一批後一次性寫入。例如：

  • 日誌系統：每 5 秒批量 flush 一次日誌到磁碟，而不是每條日誌都寫一次。
  • 數據收集：感測器數據每 10 秒批量上傳，而不是逐條寫入。

批量寫入減少了磁碟 I/O 次數和資料庫連線開銷，大幅提升寫入效能。代價是增加了少量延遲（最多等一個 batch 週期）。

策略五：資料庫寫入優化

  • 減少索引：每個索引都會拖慢寫入速度，寫密集場景中只保留必要的索引。
  • 使用 append-only 模型：像 Cassandra 一樣，資料只追加不修改，避免隨機寫入。
  • 調整批次大小：增大寫入批次（batch size），減少磁碟尋道次數。

策略總覽

策略類型 讀密集型 寫密集型
資料庫 關聯式 + 豐富索引 NoSQL（Cassandra / MongoDB）
快取 Redis / Memcached + CDN 作用有限（資料頻繁變動）
擴展方式 讀取副本（Read Replica） 分片（Sharding）
處理模式 同步讀取（要求低延遲） 非同步寫入（訊息佇列 + 批量）
索引 多建索引加速查詢 少建索引提升寫入速度
一致性 可接受最終一致性 依場景（金融需強一致性）

面試中怎麼回答

當面試官問你「怎麼設計一個 XX 系統」時，先判斷讀寫比例，再針對性地選擇策略：

「這是一個讀密集型系統——預估讀寫比 10:1。我的策略是：第一層用 CDN 分發靜態資源；第二層用 Redis 快取熱門資料；資料庫層使用讀取副本分散讀取壓力；索引建立在最常用的查詢欄位上。」
「這是一個寫密集型系統——每秒寫入量達到 10,000 筆。我的策略是：使用 Cassandra 作為主資料庫（高寫入吞吐量）；按用戶 ID 分片分散寫入壓力；非關鍵路徑的日誌通過 Kafka 異步寫入；減少索引數量以提升寫入速度。」

面試中的關鍵點

  • 能說出讀密集型的四大策略：快取、讀取副本、資料庫優化、CDN
  • 能說出寫密集型的五大策略：選對資料庫、分片、非同步處理、批量寫入、寫入優化
  • 能根據讀寫比例，組合多種策略回答設計方案
  • 能解釋每種策略的取捨（如快取增加一致性難度、分片增加複雜度）

小結

讀密集型系統用快取 + 讀取副本 + CDN 讓讀取更快；寫密集型系統用 NoSQL + 分片 + 非同步寫入 + 批量處理讓寫入更高效。面試中先判斷讀寫比例，再組合策略回答，並解釋每個選擇的取捨。
