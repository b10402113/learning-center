索引如何運作

system-design · indexes · Step 2/4

學習目標：理解索引背後常見的資料結構（B-tree、雜湊索引）以及它們如何實現快速查找。

為什麼不是簡單的排序陣列？

最直覺的索引方式是把資料排好序存在陣列裡，然後用二分查找（Binary Search）找目標——時間複雜度 O(log n)。看起來很快，但有一個致命問題：插入和刪除太慢。

在有序陣列中插入一個新元素，你需要把後面所有元素往後移動一位，時間複雜度 O(n)。如果你的資料表每天有幾百萬筆寫入，這種方案根本不可行。

資料庫需要一種既能快速查找，又能高效插入刪除的資料結構——這就是 B 樹（B-tree）被選為預設索引結構的原因。

B 樹與 B+ 樹

B 樹（B-tree）

B 樹是一種平衡多路搜索樹。關鍵詞是「平衡」和「多路」：

  • 平衡：所有葉子節點在同一層，查找路徑長度一致，不會有最壞情況
  • 多路：每個節點可以有多個子節點（不只是二元樹的左右兩個），所以樹的高度很低

為什麼樹的高度很重要？因為資料庫的索引通常存在磁碟上，每一層節點對應一次磁碟讀取。一棵 3 層的 B 樹，查找時最多只需 3 次磁碟讀取——哪怕底下有幾億筆資料。

資料量 B 樹高度（每節點 1000 個鍵） 磁碟讀取次數
1,000 筆1 層1 次
1,000,000 筆2 層2 次
1,000,000,000 筆3 層3 次

B+ 樹（B+ tree）——實際的王者

B+ 樹是 B 樹的改進版，也是絕大多數關聯式資料庫（MySQL InnoDB、PostgreSQL）實際使用的索引結構。它做了兩個關鍵改進：

  1. 資料只存葉子節點：非葉子節點只存索引鍵（作為導航路標），不存實際資料。這讓每個非葉子節點能塞更多鍵，樹更矮，查找更快。
  2. 葉子節點用鏈表串聯：所有葉子節點串成一個有序鏈表。這意味著範圍查詢（如 WHERE age BETWEEN 20 AND 30）可以直接沿著鏈表掃描，不用回到樹的上層。

用一個類比：B 樹像是一本書的正文——每一頁都有內容。B+ 樹像是一本書的目錄 + 正文——目錄只有標題和頁碼（導航），正文全在最後的頁面裡，而且頁面之間有裝訂線可以順序翻閱。

雜湊索引（Hash Index）

雜湊索引用完全不同的思路：它對索引鍵做雜湊運算（Hash Function），直接算出資料的存放位置。等值查詢（WHERE id = 42）的時間複雜度可以達到 O(1)——比 B+ 樹的 O(log n) 更快。

但雜湊索引有嚴重的限制：

  • 不支援範圍查詢——WHERE age > 20 沒法用雜湊索引，因為雜湊值不保留原始順序
  • 不支援排序——ORDER BY 無法利用雜湊索引
  • 可能發生碰撞——不同的鍵可能雜湊到同一個位置，需要額外處理

所以雜湊索引只適用於純等值查詢的場景，例如 Redis 這類記憶體資料庫。

面試中的關鍵點

在面試中談到索引時，你需要能解釋：

  • 為什麼 B+ 樹是預設選擇（平衡查找和寫入、支援範圍查詢）
  • 雜湊索引什麼時候有用（純等值查詢、記憶體資料庫）
  • 樹的高度為什麼重要（每一層 = 一次磁碟讀取）

這些是你從「用過索引」到「理解索引」的分水嶺。

小結

索引的快速查找來自底層資料結構的精心設計。B+ 樹用平衡多路搜索樹實現 O(log n) 的查找和高效的範圍查詢，雜湊索引用哈希表實現 O(1) 的等值查找。理解這些結構，你才能在面試中解釋為什麼某些查詢快、某些慢。下一步，我們看看索引帶來的寫入效能取捨。
