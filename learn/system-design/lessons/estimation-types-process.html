五種估算類型與估算流程

system-design › estimation › estimation-types-process

學習目標：能運用五種估算類型（Load / Storage / Bandwidth / Latency / Resource）並掌握估算的四步流程，完成面試中的容量估算。

四步流程：從問題到數字

上一課你學了四種技巧（Rule of Thumb、Approximation、Breakdown、Sanity Check），這一課把它們套進一個標準流程。面試估算的四步：

  1. 理解範圍：問清楚用戶量、讀寫比、資料保留期限——這些是你後續計算的輸入
  2. 簡單數學：用四則運算和上一課的技巧，快速計算
  3. 取整簡化：把 11,574 QPS 取整為 ~12K QPS
  4. Sanity Check：用常識驗證結果是否合理

這四步適用於所有題目。不管是設計 Twitter 還是設計 Uber，流程都一樣。接下來我們看五種具體的估算類型——它們是四步流程的「內容」。

類型一：Load Estimation（負載估算）

Load Estimation 算的是每秒多少請求（QPS/TPS）。它直接決定你的系統是否需要水平擴展。

假設你在設計一個社交媒體平台，面試官給了 1 億 DAU，每人每天發 10 篇貼文：

100M DAU × 10 posts/day = 1B posts/day
1B ÷ 86,400 sec ≈ 11,574 QPS
取整 ≈ 12K QPS

12K QPS 告訴你什麼？一台普通的 Web 伺服器（如 Nginx + Node.js）在不做任何優化的情況下，處理能力大約在 1K-5K QPS。12K QPS 意味著你至少需要 3-12 台伺服器的水平擴展。如果有讀寫分離，寫入端可能只有 ~120 QPS（假設 100:1 讀寫比），寫入壓力反而不大。

類型二：Storage Estimation（儲存估算）

Storage Estimation 算的是需要多少儲存空間。它告訴你能不能用單機資料庫，還是需要分散式儲存。

照片分享 App：5 億用戶，每人每天上傳 2 張照片，平均每張 2MB：

500M × 2 photos/day × 2MB = 2,000,000 MB/day
= 2 TB/day
一年 ≈ 730 TB

2 TB/天——這個數字直接淘汰了本機 SSD 的選項。你需要雲端物件儲存（如 AWS S3），並且需要規劃資料保留策略（保留多久？舊資料怎麼歸檔？）。

類型三：Bandwidth Estimation（頻寬估算）

Bandwidth Estimation 算的是網路需要多寬。它決定你需要 CDN、需要多少條骨幹網路連線。

影片串流平台：1,000 萬用戶同時觀看 1080p 影片，每路 4 Mbps：

10M users × 4 Mbps = 40,000,000 Mbps
= 40 Tbps

40 Tbps 是什麼概念？Netflix 的全球峰值帶寬大約是 100+ Tbps。你的估算在同一數量級，合理。但它告訴你：這不是一台伺服器能扛的，你需要全球 CDN 分發，把影片緩存到離用戶最近的邊緣節點。

類型四：Latency Estimation（延遲估算）

Latency Estimation 算的是回應時間。它影響你的平行化決策——哪些步驟可以並行，哪些必須串行。

假設你的 API 需要從三個資料來源抓取資料，延遲分別是 50ms、100ms、200ms：

執行方式總延遲計算
串行（Sequential）350 ms50 + 100 + 200
平行（Parallel）200 msmax(50, 100, 200)

差了 150 ms——這在使用者體驗上是顯著的差異。如果你的 SLA 要求回應時間 < 200ms，串行方案直接不及格。這就是 Latency Estimation 如何驅動平行化設計。

類型五：Resource Estimation（資源估算）

Resource Estimation 算的是需要多少硬體資源（CPU 核心、記憶體、伺服器數量）。它把前面四種估算的結果轉化為具體的基礎設施需求。

假設你的系統收到 10,000 QPS，每個請求需要 10ms 的 CPU 時間：

10,000 req/s × 10 ms/req = 100,000 ms/s
每個核心每秒能處理 1,000 ms
需要核心數 = 100,000 ÷ 1,000 = 100 核心
考慮冗餘（3 倍）= 300 核心
每台伺服器 64 核心 ≈ 5 台伺服器

5 台伺服器——這是一個可管理的規模。但如果每個請求需要 100ms CPU 時間，那就變成 50 台伺服器，你需要重新思考架構（加快取？減少計算量？）。

五種類型的互相關聯

五種類型不是孤立的——它們共同構成系統的「數字畫像」：

  • Load 決定 QPS → 影響 Resource（需要多少伺服器）
  • Storage 決定資料量 → 影響 Bandwidth（資料傳輸量）
  • Bandwidth 決定網路需求 → 影響 Resource（需要多少 CDN 節點）
  • Latency 決定回應時間 → 影響架構（平行化、快取策略）

你的專案經驗可以用來 Sanity Check：你用過 Postgres，如果估出 23 萬 QPS 而單機只能扛 1 萬 QPS，你就知道需要讀寫分離、分片或快取層。這就是估算是如何直接驅動架構決策的。

面試實戰：五分鐘估算

在面試中，整個估算過程不超過五分鐘。標準節奏：

  1. 第 1 分鐘：問清楚基本數字（DAU、讀寫比、資料量）
  2. 第 2-3 分鐘：用四種技巧估算 Load、Storage、Bandwidth
  3. 第 4 分鐘：根據前三個數字推導 Latency 和 Resource
  4. 第 5 分鐘：Sanity Check，然後用數字支撐你的架構設計

如果你花了 15 分鐘在算數字，面試官會覺得你抓不住重點。速度本身就是一種能力。

小結

五種估算類型覆蓋系統的不同面向：Load 算請求量、Storage 算資料量、Bandwidth 算傳輸量、Latency 算回應時間、Resource 算硬體需求。它們不是孤立的——一個數字會影響另一個數字，共同構成系統的「數字畫像」。掌握了四步流程和五種類型，你就能在任何系統設計面試中，五分鐘內產出一組合理的容量數字。
