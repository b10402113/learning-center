REST vs RPC 比較

system-design · arch-patterns · Step 4/5

學習目標

理解 REST 與 RPC 兩種 API 架構風格的設計哲學差異，並能依場景選擇適合的風格。

寄信 vs 打電話

想像你要跟朋友互動：

  • REST 風格：你寄一封信，信上寫「請把第 3 本書的第 2 章寄給我」。你用標準的信封格式（HTTP 方法），資源就是那本書（URL），操作就是讀/寫（GET/POST/PUT/DELETE）。朋友根據信的內容處理，然後回一封信。
  • RPC 風格：你直接打電話說「幫我複製第 3 本書的第 2 章到剪貼簿」。你在呼叫一個動作（procedure），對方執行後告訴你結果。

REST 是「圍繞資源操作」，RPC 是「圍繞動作呼叫」。兩者不是非此即彼——很多系統兩者混用。

REST（Representational State Transfer）

REST 是一種架構風格，核心思想是把伺服器上的資料視為資源（resource），每個資源有一個唯一的 URL，透過標準 HTTP 方法來操作這些資源。

HTTP 方法 操作 例子
GET 讀取資源 GET /users/123 → 取得用戶 123 的資料
POST 建立資源 POST /users → 建立新用戶
PUT 完整更新資源 PUT /users/123 → 完整更新用戶 123
DELETE 刪除資源 DELETE /users/123 → 刪除用戶 123

REST 的關鍵特性：

  • 無狀態（Stateless）：每個請求包含所有必要資訊，伺服器不保存客戶端狀態
  • 統一介面（Uniform Interface）：用標準 HTTP 方法，任何人一看就知道怎麼用
  • 可快取（Cacheable）：回應可以被快取，利用 HTTP 快取機制提升效能
  • 資源導向：URL 代表資源，操作對應 HTTP 方法

REST 的優缺點

面向 優勢 劣勢
可擴展 無狀態設計易於水平擴展 —
效能 可利用 HTTP 快取機制 —
簡單 標準 HTTP 方法，易理解和實作 —
資料傳輸 — 可能 over-fetching（拿太多）或 under-fetching（拿太少）
標準化 — 缺乏嚴格標準，不同實作可能有差異

RPC（Remote Procedure Call）

RPC 是一種協議，讓一個程式可以像呼叫本地函數一樣，遠端執行另一台機器上的程式。客戶端定義明確的動作（procedure），伺服器執行後回傳結果。

RPC 呼叫 動作 例子
getUser 取得用戶 getUser(123) → 回傳用戶 123 的資料
createUser 建立用戶 createUser({name: "Alice"}) → 回傳新用戶 ID
copyChapter 複製章節 copyChapter(book=3, chapter=2) → 執行複製動作

現代 RPC 框架：

  • gRPC：Google 開發，用 Protocol Buffers（二進位格式）序列化，效能極高
  • JSON-RPC：用 JSON 格式，比 REST 更輕量
  • Thrift：Apache 開發，支援多語言

RPC 的優缺點

面向 優勢 劣勢
效率 二進位格式（如 gRPC）比 JSON 更快 —
明確契約 函數定義就是 API 契約，類型安全 —
緊耦合 動作直接對應伺服器操作，直觀 客戶端和伺服器端耦合度高
靈活性 — 不像 REST 那樣靈活，修改介面影響範圍大
可擴展 — 可以維持狀態，可能影響可擴展性

核心差異對照

面向 REST RPC
設計哲學 圍繞資源（noun）操作 圍繞動作（verb）呼叫
URL 設計 /users/123（資源導向） /api/getUser（動作導向）
HTTP 方法 GET/POST/PUT/DELETE 對應 CRUD 通常只用 POST（所有動作都是一個 endpoint）
資料格式 JSON / XML 可選二進位（Protocol Buffers）或 JSON
無狀態 ✅ 強制無狀態 ❌ 可以有狀態
效能 中等（JSON 解析開銷） 高（二進位格式如 gRPC）
快取 ✅ 可利用 HTTP 快取 ❌ 通常無法利用 HTTP 快取
適合場景 公開 API、Web 服務、需要快取 內部微服務通訊、效能敏感

面試中的關鍵點

  • REST 是資源導向（圍繞 noun），RPC 是動作導向（圍繞 verb）
  • REST 適合公開 API 和需要快取的場景；RPC（如 gRPC）適合內部微服務通訊和效能敏感的場景
  • 兩者不互斥：一個系統可以對外用 REST（公開 API），內部用 RPC（微服務通訊）
  • 面試時被問「該用哪個」，先問清楚是公開 API還是內部通訊，以及是否有效能要求

小結

REST 和 RPC 是兩種不同的 API 設計哲學：REST 圍繞資源操作（URL 代表資源，HTTP 方法代表操作），RPC 圍繞動作呼叫（像呼叫本地函數）。REST 適合公開 API、需要快取的場景；RPC（如 gRPC）適合內部微服務通訊、效能敏感的場景。兩者互補，常常在同一個系統中搭配使用。下一課會看看客户端和伺服器之間的通訊模式選擇。
