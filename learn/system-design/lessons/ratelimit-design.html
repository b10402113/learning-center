API 限流演算法與系統架構

system-design · typeahead-ratelimit · Step 4/4

學習目標

學習常見的限流演算法（固定窗口、滑動窗口等），以及分散式環境下的限流系統高層設計、資料分片和最佳實踐。

演算法一：固定窗口計數器

最簡單的限流演算法。把時間切成固定大小的窗口（如每秒），為每個用戶維護一個計數器。每次請求來了，計數器 +1；如果計數器超過上限，拒絕請求。窗口結束時歸零重來。

// 固定窗口邏輯
key = "rate_limit:" + userID + ":" + currentWindow
count = redis.incr(key)
if count == 1:
    redis.expire(key, windowSize)  // 首次設定過期時間
if count > limit:
    return 429  // Too Many Requests

優點：實作極簡單，記憶體效率高（每個用戶每個窗口只存一個整數）。缺點：**窗口邊界問題**。假設限制每分鐘 100 次，用戶在第 59 秒發了 100 個請求，第 60 秒（新窗口）又發 100 個——瞬間 200 個請求，遠超限流意圖。

演算法二：滑動窗口計數器

改進固定窗口的邊界問題。核心思想：不用固定窗口，而是用一個「滑動的時間範圍」。每次請求來了，計算從「現在往前推窗口大小」的時間範圍內有多少請求。

實作方式：用 Redis 的 Sorted Set，每個請求存一個 timestamp 作為 score。收到新請求時：

  1. 移除 Sorted Set 中所有早於「現在 - 窗口大小」的 timestamp
  2. 計算 Sorted Set 中還剩多少個 timestamp
  3. 如果數量 < 上限，加入新請求的 timestamp，允許通過
  4. 如果數量 ≥ 上限，拒絕
// 滑動窗口邏輯
key = "rate_limit:" + userID
now = currentTimeMillis()
windowStart = now - windowSize

// 移除過期的 timestamp
redis.zremrangebyscore(key, 0, windowStart)

// 計算當前窗口內的請求數
count = redis.zcard(key)

if count < limit:
    redis.zadd(key, now, now)  // 加入新請求
    redis.expire(key, windowSize)
else:
    return 429

優點：精確解決窗口邊界問題。缺點：**記憶體消耗大**——每個請求都存一個 timestamp，如果限制每秒 10,000 次，每個用戶每秒要存 10,000 個 timestamp。

演算法三：滑動窗口計數器（混合版）

結合固定窗口的低記憶體和滑動窗口的精確度。做法：把大窗口（如 1 小時）切成多個小窗口（如每分鐘），為每個小窗口維護一個計數器。

假設限制每小時 500 次請求。當新請求在 10:35 到達時：

  1. 計算過去一小時內所有小窗口的計數器總和（10:00-10:34 的所有計數器 + 10:35 當前窗口的部分計數）
  2. 如果總和 < 500，允許通過，當前窗口計數器 +1
  3. 如果總和 ≥ 500，拒絕

優點：比純滑動窗口節省大量記憶體（只存 60 個計數器而不是每秒的 timestamp），精度也夠用。這是生產環境中最常用的限流演算法。

高層系統設計

Rate Limiter 在系統中的位置和互動流程：

用戶請求 → Web Server → 詢問 Rate Limiter
                         → [允許] → 轉發到 API Server
                         → [拒絕] → 返回 429

Rate Limiter 通常作為一個獨立服務部署，Web Server 收到請求後先詢問 Rate Limiter「這個用戶能不能發這個請求」，根據結果決定放行或拒絕。Rate Limiter 的狀態存在 Redis 等共享儲存中，確保多台 Web Server 看到一致的限流狀態。

資料分片與快取

當用戶量很大時，限流資料也需要分片。最常見的做法是按 UserID 做一致性雜湊分片：每個 Redis 節點負責一段 UserID 範圍，請求根據 UserID 路由到對應的節點。

如果不同 API 需要不同的限流規則（如 URL Shortener 的 createURL 和 deleteURL 限制不同），可以按 UserID + API Name 做分片。一致性雜湊確保在增減節點時，只有少量 key 需要重新分配。

IP vs 用戶限流

限流要按 IP 還是按用戶？兩種各有取捨：

維度 優點 缺點
按 IP 不需要登入就能限流，擋機器人效果好 共享 IP（如網咖、手機網路）會誤傷正常用戶
按用戶 精確控制每個用戶的配額，不會誤傷 需要用戶登入，匿名用戶無法限流

最佳實踐是兩者結合：按 IP 做粗粒度的全局限流（擋 DDoS），按用戶做細粒度的 API 配額管理。兩層防線互相補充。

面試中的關鍵點

  • 能解釋固定窗口的邊界問題以及滑動窗口如何解決
  • 能比較三種演算法的記憶體和精度取捨
  • 能畫出 Rate Limiter 的高層架構（Web Server → Rate Limiter → Redis → API Server）
  • 能說明為什麼用一致性雜湊做限流資料分片
  • 能比較 IP 限流和用戶限流的取捨，以及為什麼要兩者結合

小結

三種限流演算法各有取捨：固定窗口最簡單但有邊界問題，滑動窗口精確但記憶體消耗大，混合版（滑動窗口計數器）在精度和記憶體之間取得平衡，是生產環境首選。Rate Limiter 作為獨立服務部署在 Web Server 前面，狀態存在 Redis 中。限流資料按 UserID 做一致性雜湊分片。IP 限流和用戶限流結合使用，粗粒度擋 DDoS，細粒度管配額。
