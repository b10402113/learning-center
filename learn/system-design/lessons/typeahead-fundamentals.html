Typeahead 基礎設計與核心演算法

system-design · typeahead-ratelimit · Step 1/4

學習目標

理解 Typeahead 搜尋建議的基本概念、功能需求，以及核心的 Trie 資料結構設計與永久儲存方式。

你在哪裡見過它

你打開 Google 搜尋框，輸入「系」，瞬間彈出「系統設計面試」「系統分析」等建議。你在淘寶搜尋商品，打一個字就有一列候選。這就是 Typeahead Suggestion——搜尋自動完成。

它的核心價值不是「加速搜尋」，而是引導用戶表達意圖。很多用戶其實不知道該搜什麼關鍵詞，好的建議能幫他們更快找到想要的東西。

需求分析

設計任何系統都要從需求開始。Typeahead 的需求分為功能和非功能兩塊：

類型 需求
功能需求 用戶每輸入一個字元，系統返回 top 10 個以該字元開頭的搜尋建議
非功能需求 建議在 200ms 以內顯示（real-time）

200ms 是什麼概念？人眼感知到延遲的閾值大約是 300ms。如果超過 200ms 用戶就會覺得「慢」，所以他打下一個字的時候你還沒返回結果——體驗就崩了。

核心資料結構：Trie

問題可以這樣抽象：我們有一堆字串，要支援「前綴查詢」——給定前綴，找出所有匹配的字串。

如果你用 Array + 線性掃描，每個前綴查詢都要遍歷整個詞典，時間複雜度 O(n × L)，n 是詞數，L 是字串長度。詞典有 100 萬個詞？太慢了。

Trie（字典樹）是專門解決前綴查詢的資料結構。它的核心思想：把字串的每個字元存為一個節點，共同的前綴共享路徑。

舉個例子。假設詞典有 cap、cat、captain、capital 這四個詞，Trie 的結構長這樣：

        root
        |
        c
        |
        a
       / \
      p   t
     / \   \
    ✓   i    ✓
   /     \
  t       n
 / \       \
a   l        ✓
|   |
✓   ✓

從 c → a → p 這條路往下走，遇到 ✓ 的節點就是一個完整詞。所以搜 cap 的前綴，系統從 root 出發沿 c → a → p 走，收集所有帶 ✓ 的子樹節點，就得到 cap、captain、capital。

操作 時間複雜度 線性掃描
前綴查詢 O(L)，L = 前綴長度 O(n × L)
插入新詞 O(L)，L = 詞長度 O(1) 或 O(n)
空間 較大（每個字元一個節點） 較小

Trie 的取捨很明確：用空間換時間。每個字元都是一個節點，空間開銷比純字串陣列大得多，但查詢速度快了一個數量級。在 Typeahead 這種 read-heavy（讀取密集）的場景下，這個取捨完全值得。

Trie 的持久化儲存

記憶體中的 Trie 很快，但伺服器重啟資料就沒了。怎麼把 Trie 存到磁碟上？

做法是定期對 Trie 做快照（snapshot），存到檔案中。重建時從 root 開始，一層一層往下讀：每個節點存它包含的字元，以及有多少個子節點。伺服器掛了？從最新的快照重建 Trie，幾秒鐘就能恢復服務。

// 快照寫入示意
function snapshot(node, file) {
  file.write(node.char);
  file.write(node.children.length);
  if (node.isEndOfWord) file.write(1);
  else file.write(0);
  for (child of node.children) {
    snapshot(child, file);
  }
}

快照的頻率取決於資料更新的頻率。Typeahead 的詞典更新通常來自離線分析（定期從搜尋日誌中統計熱門詞），所以一天做一次快照就夠了。

面試中的關鍵點

  • 能解釋 Typeahead 的核心價值：引導用戶表達意圖，不是加速搜尋
  • 能說出功能需求（top 10 建議）和非功能需求（200ms 延遲）
  • 能畫出 Trie 的基本結構，解釋前綴查詢為什麼是 O(L)
  • 能說明 Trie 的空間換時間取捨，以及為什麼在 Typeahead 場景下值得
  • 能解釋快照機制如何讓 Trie 在伺服器重啟後恢復

小結

Typeahead 的核心是用 Trie 支援前綴查詢，以空間換時間，達到 O(L) 的查詢速度。Trie 透過定期快照實現持久化，伺服器重啟後可從快照重建。下一步要面對的問題是：當詞典有數十億條、每秒有數萬次查詢時，怎麼把這個 Trie 擴展到多台機器上。
