資料建模與元數據分片

YouTube/Netflix · Step 4/6

學習目標

設計影片與使用者資料的數據庫 Schema，並選擇合適的元數據分片策略處理大規模數據。

資料建模的重要性

高層架構告訴你「系統由什麼組成」，資料建模告訴你「資料怎麼組織」。在 YouTube 這種規模的系統中，資料庫的設計直接影響查詢效能、擴展能力和維護成本。一個設計不好的 Schema，在小規模時看不出問題，但一旦資料量膨脹到十億級別，整個系統就會崩潰。

YouTube 的資料可以分成兩大類：影片元資料（Video Metadata）和使用者資料（User Data）。這兩類資料的存取模式不同，需要不同的儲存策略。

影片元資料 Schema

每部影片需要儲存以下元資料：

欄位類型說明
VideoIDBIGINT / VARCHAR影片的唯一識別碼
TitleVARCHAR影片標題
DescriptionTEXT影片描述
SizeBIGINT影片檔案大小（位元組）
ThumbnailVARCHAR縮圖的 URL
UploaderBIGINT上傳者的 UserID
TotalLikesBIGINT總按讚數
TotalDislikesBIGINT總按踩數
TotalViewsBIGINT總觀看次數

評論（Comment）也需要獨立的 Schema：

欄位類型說明
CommentIDBIGINT評論的唯一識別碼
VideoIDBIGINT所屬影片的 ID
UserIDBIGINT留言者的 UserID
ContentTEXT評論內容
CreatedAtDATETIME建立時間

這些元資料通常存在關聯式資料庫（如 MySQL）中，因為它們是結構化資料，需要 ACID（Atomicity, Consistency, Isolation, Durability）保證。

使用者資料 Schema

使用者資料相對簡單：

欄位類型說明
UserIDBIGINT使用者的唯一識別碼
NameVARCHAR使用者名稱
EmailVARCHAR電子郵件
RegistrationDateDATETIME註冊日期

使用者資料的量遠小於影片資料，通常不需要分片。但當使用者達到數億級別時，仍然需要考慮分片策略。

元數據分片策略

當影片數量達到數十億，單台資料庫伺服器無法承擔讀取和寫入壓力，就需要分片（Sharding）——把資料分散到多台伺服器上。YouTube 的元資料分片有幾個常見策略：

按 UserID 分片——把同一個使用者的所有影片和評論放在同一台伺服器。優點是「我的頁面」查詢很快（所有資料都在同一台機器）。缺點是熱門使用者（如擁有一億追蹤者的創作者）會造成熱點問題（Hotspot）——某台伺服器承擔過多壓力。

按 VideoID 分片——把影片分散到不同伺服器，與使用者無關。優點是資料分布均勻。缺點是查詢「某個使用者的所有影片」需要跨多台伺服器聚合。

按使用者地理位置分片——把不同地區的使用者資料放在就近的伺服器。優點是減少延遲。缺點是跨區查詢複雜。

實際上，YouTube 可能會混合使用多種策略：影片元資料按 VideoID 分片（保證均勻），使用者資料按地理位置分片（減少延遲），評論按 VideoID 分片（查詢某部影片的所有評論）。

選擇分片鍵的原則

分片鍵（Shard Key）的選擇是分片策略中最關鍵的決策。好壞標準：

均勻性——資料要均勻分布在各分片上，避免某個分片承擔過多壓力。VideoID 比 UserID 更均勻，因為影片數量分佈比使用者活躍度分佈更平。

查詢效率——常見的查詢要能高效執行。如果查詢「某個使用者的所有影片」很頻繁，按 UserID 分片更好；如果查詢「某部影片的評論」很頻繁，按 VideoID 分片更好。

擴展性——新增分片時，資料遷移的成本要低。一致性雜湊可以減少資料遷移量。

你的經驗怎麼連結？

你用過 MySQL 和 Redis。YouTube 的元資料庫本質上就是你熟悉的 MySQL 的放大版。差別在於：你需要決定怎麼把一個巨大的 MySQL 表拆到多台機器上（分片），以及哪些資料放 MySQL（元資料）、哪些放物件儲存（影片檔案）、哪些放 Redis（熱門影片的快取）。這些你都用過，只是 YouTube 要求你在更大規模上思考。
