分散式系統：把一項大工作交給許多台機器

系統設計 · 分散式系統基礎 · Step 1/5

這一步要學會什麼？

先建立分散式系統的整體地圖：了解它是什麼、為什麼需要它，以及設計時最常拿來權衡的五個核心特性。後面深入學習每個特性時，你就知道它在整張地圖上的位置。

先從你熟悉的網站想起

想像你正在使用電商、社群媒體或雲端儲存服務。畫面看起來像是一個完整的「網站」，但背後可能是數百萬台伺服器，分散在全球各地的資料中心，透過網路彼此通信、一起完成工作。

這種由許多獨立節點組成，並透過網路協同完成共同目標的系統，就叫做分散式系統。

如果你之前做過單機程式，可以把它想成一次重要的升級：原本是一台機器自己處理所有事情，現在則是把工作拆開，交給多台機器合作。這樣做看似只是「多加幾台伺服器」，實際上也帶來了通信、故障與資料協調等新問題。

為什麼不直接使用一台超級電腦？

單機系統就像把所有貨物塞進一輛超大的卡車；當貨物和訂單不斷增加，卡車終究會遇到上限。主要困難包括：

  • 規模限制：單台機器的 CPU、記憶體與儲存都有物理上限，無法無限承載數億使用者的請求。
  • 單點故障：如果所有服務都依賴同一台機器，這台機器一壞，整個服務就可能一起停止。
  • 延遲問題：使用者在亞洲、伺服器卻在美洲時，即使訊號以光速傳輸，也可能需要 200ms 以上。
  • 成本：一台超級電腦的價格，可能遠高於一百台普通伺服器。

分散式系統採用的是「分而治之」：把工作拆成幾個部分，交給多台機器各自處理，再把結果彙整起來。這就像餐廳在尖峰時段增加多個廚師和工作站，不讓所有訂單都堵在同一個人手上。

什麼時候需要分散式系統？

當服務的使用者、流量或資料量持續變大，單機設計通常會逐漸碰到瓶頸。下面這張表可以把「問題」和「分散式解法」對在一起：

挑戰單機的困境分散式系統的解法
流量增長單台伺服器很快就無法承受所有請求增加更多伺服器來分擔流量
硬體故障機器一壞，整個服務可能停止採用冗餘部署，故障時仍有備份可接手
地理延遲使用者與伺服器距離太遠，請求需要長途傳輸把伺服器部署到更靠近使用者的位置
成本控制購買和維護超級電腦非常昂貴使用大量價格較低的普通機器

因此，是否使用分散式系統，不是「機器越多越先進」這麼簡單，而是要看需求：當規模、容錯、地理位置或成本成為問題時，分散式架構才真正有價值。

設計時要看哪五個面向？

分散式系統沒有一套能解決所有場景的標準答案。設計時，我們會圍繞五個核心特性做取捨。你可以把它們想成五個旋鈕：調高其中一個，往往會牽動成本、複雜度或其他特性。

1. 可擴展性（Scalability）
指系統應對成長的能力。當流量或資料量增加時，能不能透過增加資源，繼續維持可接受的效能？
2. 可靠性（Reliability）
指系統在故障環境下仍然正確運作的能力。部分節點故障時，系統能不能依然正確完成請求？
3. 可用性（Availability）
指系統在正常條件下保持可操作的時間比例。使用者需要服務時，能不能正常存取？
4. 效率（Efficiency）
用來衡量系統的反應速度與處理量，通常會觀察延遲（Latency）和吞吐量（Throughput）。前者關心一個請求要等多久，後者關心一段時間內能處理多少請求。
5. 可管理性（Manageability）
指系統維護和營運的難易程度，包括部署、監控、問題排查與升級是否方便。

這五個特性之間常常需要權衡取捨。例如，追求極高的可用性，通常要準備更多冗餘機器，成本也會增加；追求極低的延遲，可能需要在多個地區部署服務，讓系統更複雜。

所以，系統設計不是把每個旋鈕都調到最大，而是先了解使用情境，再決定哪些特性最重要。沒有完美的系統，只有更適合特定場景的取捨。

在系統設計面試中，怎麼用這套框架？

如果你之前做過功能開發，可能習慣先想「這個功能要怎麼實作」。但在系統設計面試裡，第一步通常不是立刻選資料庫或畫架構圖，而是先問清楚需求。需求不同，設計方向也會完全不同。

這五個特性可以幫你整理問題：

  1. 先確認規模：流量和資料量有多大？未來會不會持續成長？這會影響可擴展性。
  2. 確認可用性要求：服務最多能容忍多少 downtime？這會影響可用性。
  3. 確認資料與故障要求：能不能接受資料遺失？部分節點壞掉時，系統需要如何運作？這會影響可靠性。
  4. 確認速度要求：使用者能接受多久的等待時間？每秒需要處理多少請求？這會影響效率。
  5. 確認維護條件：有多少人負責部署、監控與排查問題？這會影響可管理性。

每個答案都會帶你走向不同的設計決策。後續步驟會逐一深入這五個特性，讓你不只知道名詞，也能理解它們為什麼重要、什麼時候該優先考慮，以及它們和實際系統設計的關係。
