ACID vs BASE

系統設計面試 · 一致性與效能 · 步驟 4/4

學習目標：理解 ACID 與 BASE 兩種資料庫設計哲學的核心屬性、差異，以及如何根據場景選擇。

先講結論

當你用銀行 App 轉帳時，你期望錢從 A 帳戶扣掉後，B 帳戶一定會收到——不會出現「錢扣了但對方沒收到」的情況。這就是 ACID 保證的事情。但當你在社群媒體上發了一則貼文，你會期望全球所有人在同一毫秒看到嗎？不會。你接受「幾秒後大家都會看到」。這就是 BASE 的思路。

ACID 和 BASE 代表了資料庫設計中兩種截然不同的哲學：ACID 優先保證正確性，BASE 優先保證可用性。它們不是好壞之分，而是不同場景下的最佳選擇。

ACID — 嚴格的正確性

ACID 是四個屬性的縮寫，它們共同保證資料庫的交易（Transaction）是可靠且正確的。交易就是「一組操作」——比如轉帳涉及「扣款」和「入帳」兩個操作，這兩個操作必須一起成功或一起失敗。

屬性全名含義類比
AAtomicity（原子性）交易中的所有操作，要麼全部成功，要麼全部失敗。不能只做一半。原子彈爆炸——你要麼全炸，要麼不炸，沒有「炸一半」。
CConsistency（一致性）交易完成後，資料庫從一個合法狀態轉移到另一個合法狀態。所有的約束條件（外鍵、唯一性等）都必須滿足。像遵守交通規則——過了路口後，你一定在合法的車道上。
IIsolation（隔離性）多個交易同時進行時，它們之間互不干擾。一個交易的中間狀態不會被其他交易看到。像在獨立的包廂裡吃飯——你不會看到隔壁桌正在點什麼菜。
DDurability（持久性）交易一旦提交，資料就永久保存了。即使系統崩潰、停電，資料也不會丟失。像寫在石頭上的字——提交了就擦不掉。

支援 ACID 的資料庫通常是關聯式資料庫（SQL）：MySQL、PostgreSQL、Oracle、SQL Server。它們被廣泛用於需要嚴格正確性的系統：銀行、電商交易、訂單管理、庫存系統。

BASE — 高可用的彈性

BASE 是另一種設計哲學，主要用於 NoSQL 和分散式資料庫。它跟 ACID 幾乎是反過來的：ACID 嚴格要求一致性，BASE 則優先保证可用性，接受暫時的不一致。

屬性全名含義類比
BABasically Available（基本可用）系統保證大部分時間可用。在故障時，可能某些功能受限，但核心功能仍然運作。便利商店：就算某些貨架空了，店門永遠開著。
SSoft state（軟狀態）系統的狀態可能隨時間變化，即使沒有新的寫入。這意味著「過時資料」是被允許的。黑板上的留言：今天的留言可能跟明天不一樣。
EEventually consistent（最終一致）在一段時間後，所有節點的資料會收斂到一致的狀態。群組訊息：不是所有人同時看到，但最後大家都會看到。

支援 BASE 的資料庫通常是 NoSQL：DynamoDB、Cassandra、MongoDB（某些配置）、Redis（非同步模式）。它們被廣泛用於高流量、全球分佈的系統：社群媒體、即時通訊、內容分發、IoT 資料收集。

怎麼選擇？

選擇的依據同樣回到那個核心問題：你的業務能不能容忍暫時的不一致？

選 ACID 的場景

  • 金融系統：轉帳、支付、股票交易——每一筆交易都必須精確無誤。
  • 電商訂單：扣款、庫存減少、訂單建立——這三個操作必須原子性完成。
  • 醫療紀錄：病人的資料不能有半吊子的更新。
  • 任何「不能出錯」的系統：預約系統、票務系統、人事系統。

選 BASE 的場景

  • 社群媒體：貼文、按讚、評論——差幾秒沒關係，但系統不能掛。
  • 即時通訊：訊息可能延遲幾毫秒到達，但不能因為等待確認而讓使用者覺得卡。
  • 內容分發：一篇文章的更新不需要在全球所有 CDN 節點同時生效。
  • IoT 資料收集：每秒數百萬個感測器資料點，丟失幾筆可以接受。

面試中的應用

面試中，當你被問到「選擇什麼資料庫」或「如何設計資料層」時，先判斷業務對一致性的要求，再選擇 ACID 還是 BASE 體系：

「這個系統是訂單交易相關的，每筆訂單涉及扣款和庫存操作，必須原子性完成，所以我選 PostgreSQL 來保證 ACID。而使用者的瀏覽紀錄和推薦資料，我會用 DynamoDB 的最終一致性來處理，因為它不需要即時精確。」

一個成熟的系統通常會同時使用兩種資料庫：用 SQL 處理核心交易，用 NoSQL 處理高流量、低一致性要求的場景。這就是所謂的 polyglot persistence（多語言持久化）。
