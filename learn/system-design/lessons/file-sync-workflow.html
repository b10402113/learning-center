檔案同步工作流程

Dropbox 系統設計 · Step 4/5

學習目標

說明當用戶更新檔案後，同步機制如何將變更傳播到所有訂閱設備，處理離線情況與衝突。

場景：用戶 A 更新了一個共享檔案

假設用戶 A、B、C 共享一個資料夾。用戶 A 在筆電上修改了其中一個檔案。讓我們追蹤整個同步流程：

  1. A 的客戶端偵測變更：客戶端監控程式發現工作區中有一個檔案被修改了
  2. 分塊並上傳：客戶端將檔案切成 4 MB 的分塊，比對本地元數據庫，找出哪些分塊實際變了，只上傳這些分塊到雲端儲存
  3. 更新元數據：客戶端透過消息隊列的請求隊列，向同步服務發送更新通知（包含新版本號、變更的分塊 ID）
  4. 同步服務處理：同步服務從請求隊列拉取通知，更新元數據資料庫（新版本、新分塊索引）
  5. 通知 B 和 C：同步服務將更新推送到 B 和 C 的響應隊列
  6. B 和 C 拉取更新：B 和 C 的客戶端從各自的響應隊列中拉取更新，下載新的分塊，套用到本地檔案

離線處理

如果 B 和 C 在 A 更新時不在线怎麼辦？

  • B 離線：更新通知留在 B 的響應隊列中。當 B 上線後，客戶端自動從響應隊列拉取所有待處理的更新，下載新分塊，套用到本地檔案
  • C 也離線：同理，C 的響應隊列保留所有待處理更新
  • A 在 B/C 離線期間又修改了：每次修改都產生新的版本，所有版本都記錄在元數據資料庫中。B/C 上線後會拉取所有中間版本

這就是為什麼需要消息隊列：它充當了離線設備的「收件匣」，確保更新不會丟失。

衝突解決

衝突發生在兩個用戶同時修改同一個檔案時。例如：A 和 B 都在離線狀態下修改了同一個檔案，然後同時上線。

Dropbox 的衝突解決策略

Dropbox 採用「最後寫入者勝（Last-Writer-Wins）」加上保留衝突副本的策略：

  1. 兩個版本都上傳到雲端
  2. 系統保留兩個版本：一個是「衝突副本」（通常加上用戶名或時間戳作為檔名後綴）
  3. 原始檔案保留最後一個成功上傳的版本
  4. 用戶手動決定保留哪個版本，或合併兩個版本

為什麼不自動合併？

因為檔案內容的合併很難自動化。文字檔案可以做行級合併（類似 Git），但圖片、影片、二進位檔根本無法自動合併。所以 Dropbox 選擇保留兩個版本，讓用戶自己決定。

版本控制

每次檔案修改都會產生一個新版本。元數據資料庫記錄了完整的版本鏈：

  • 版本 1：初始上傳
  • 版本 2：第一次修改（分塊 A、B、C → 分塊 A、D、C）
  • 版本 3：第二次修改（分塊 A、D、C → 分塊 A、D、E）

用戶可以回滾到任何歷史版本。這也是元數據資料庫必須支援強一致性的原因之一——版本鏈不能出錯。

完整流程圖

把所有步驟串起來：

用戶 A 修改檔案
    ↓
客戶端偵測變更 → 分塊 → 上傳到雲端儲存
    ↓
透過請求隊列 → 同步服務
    ↓
同步服務更新元數據資料庫
    ↓
推送到 B、C 的響應隊列
    ↓
B、C 客戶端拉取更新 → 下載新分塊 → 套用到本地

如果 B/C 離線，更新留在響應隊列，等他們上線後再拉取。

自我檢測

  • A 必須重新發送
  • 同步服務會重試直到成功
  • 後上傳的覆蓋先上傳的
  • 系統要求用戶重傳
  • 只記錄檔案大小
  • 只記錄修改時間
