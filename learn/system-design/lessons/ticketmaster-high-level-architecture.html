高層架構設計

Step 4/6 · Ticketmaster 系統設計 · 約 12 分鐘

學習目標

設計 Ticketmaster 的高層系統架構，定義 Web Server、Application Server、Database 和 Cache 各層的職責，並設計系統 API。

從用戶請求開始

當用戶打開訂票網站，他們的請求會經過哪些層？從最外面到最裡面，依次是：

用戶
  ↓
Load Balancer（負載均衡器）
  ↓
Web Server（網頁伺服器）— 管理 session、處理靜態資源
  ↓
Application Server（應用伺服器）— 處理業務邏輯、訂票流程
  ↓
Database + Cache（資料庫 + 快取）

這是一個經典的三層架構。每一層都有明確的職責，互不干擾。

各層職責

Load Balancer

在最外面，負載均衡器把用戶請求分散到多個 Web Server。這樣單一台伺服器掛了，其他伺服器還能繼續服務。常用的演算法有 Round Robin（輪詢）或 Least Connections（最少連接）。

Web Server

Web Server 負責兩件事：一是管理用戶的 session（登入狀態、購物車），二是提供靜態資源（圖片、CSS、JavaScript）。它不做業務邏輯，只做「門面」。

Application Server

這是系統的大腦。所有業務邏輯都在這裡：搜尋電影、查詢場次、檢查座位可用性、處理訂單。Application Server 是無狀態的——它不存任何數據，所有狀態都存在資料庫或快取中。這樣就能輕鬆水平擴展：需要更多處理能力？加機器就行。

Database + Cache

資料庫存所有持久化數據（城市、影院、電影、場次、座位、訂單）。快取（通常是 Redis）存熱數據：熱門場次的座位狀態、搜尋結果。快取能大幅減少資料庫壓力——讀取操作大部分走快取，只有寫入才打到資料庫。

系統 API

API 是 Application Server 對外的接口。一個訂票系統至少需要這些 API：

API參數說明
SearchMoviescity, keyword, datetime搜尋電影（按城市、關鍵字、時間）
SearchShowsmovieID, city, datetime搜尋場次（按電影、城市、時間）
ReserveSeatsshowID, seatIDs暫時鎖定座位（15 分鐘有效期）
MakeBookingreservationID, paymentInfo確認訂單並付款
CancelReservationreservationID取消預訂

關鍵設計：ReserveSeats 是一個暫時鎖定操作，不是最終訂購。用戶選座後，座位被暫時鎖定 15 分鐘。在這段時間內，其他用戶無法選這些座位。如果 15 分鐘內沒有完成付款，座位自動釋放。

快取策略

哪些數據適合放快取？

  • 電影列表（按城市）——變化不頻繁，快取命中率高
  • 場次資訊（按場次 ID）——讀取頻率遠高於寫入
  • 座位狀態（按場次 ID）——讀取最頻繁，但變化也最頻繁，需要精細的失效策略

座位狀態的快取是最棘手的——它讀取量大（每個用戶都在看），但寫入也頻繁（每次訂購都要更新）。這裡的取捨在後面的步驟會詳細討論。

面試技巧

畫高層架構圖時，從外到內：Load Balancer → Web Server → Application Server → Database + Cache。每一層標註職責和關鍵技術選型。記住：Application Server 是無狀態的，狀態存在 Database 和 Cache 中。
