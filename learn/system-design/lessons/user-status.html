在線狀態管理

Facebook Messenger 系統設計 · Step 5/6

學習目標

設計能夠追蹤大量使用者在線狀態並即時通知相關使用者的機制。

為什麼需要在線狀態？

你打開 Messenger，看到朋友名字旁邊有一個綠色圓點——這就是「在線」標記。這個看似簡單的功能，背後的挑戰比你想像的大：5 億日活用戶，每個人上線/下線都要追蹤，而且每次狀態變化都要通知相關的人。

基本實現

由於我們的 Chat Server 維護了每個用戶的持久連線，判斷用戶是否在線其實很直接：

  • 在線：用戶和某台 Chat Server 之間有一條活躍的連線
  • 離線：連線已斷開，且超過一定時間（如 30 秒）未重連

每台 Chat Server 都維護一個本地映射：user_id → connection。要查某個用戶是否在線，問一下哪台 Server 持有他的連線即可。

狀態廣播的挑戰

問題在於通知。當用戶 A 上線時，A 的所有好友中正在線的人要看到「A 上線了」的提示。如果有 500 萬用戶同時在線，每次狀態變化都廣播給所有相關用戶，流量會爆炸。

優化策略

  • 只通知好友：不是廣播給所有人，只通知 A 的好友列表中正在線的人。假設平均每人有 500 個好友，其中 10% 在線，就是 50 個通知
  • 可見性窗口：只通知當前在螢幕上看到好友列表的用戶。如果用戶沒打開對話列表，就不推送狀態更新
  • 批量推送：把短時間內的多次狀態變化合併成一次推送，減少通知數量

心跳機制

怎麼判斷用戶真的離線了？不能只依賴 TCP 連線斷開——有時候用戶的網路只是暫時中斷，TCP 連線還沒來得及超時。

解決方案是心跳（Heartbeat）：

  • 客戶端每隔幾秒發送一個微小的心跳包到伺服器
  • 伺服器收到心跳，確認用戶還活著
  • 如果超過一定時間（如 30 秒）沒收到心跳，判定用戶離線

心跳間隔是一個取捨：太短浪費頻寬，太長判斷離線的延遲太高。30 秒是一個常見的折衷值。

多設備場景

一個用戶可能同時在手機和電腦上登入。狀態管理需要處理：

  • 只要有一個設備在線，用戶就是「在線」：狀態是用戶級別的，不是設備級別的
  • 每個設備維護獨立連線：手機和電腦各有一條到 Chat Server 的連線
  • 訊息同步：用戶在一台設備上發的訊息，另一台設備也要能看到（透過推送或拉取）
