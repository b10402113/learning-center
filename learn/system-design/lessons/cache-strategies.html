快取策略：讀寫模式與快取位置

system-design · data-strategies · Step 1/5

學習目標

理解不同快取讀寫模式（Read-Through、Write-Through、Write-Behind）以及伺服器端與用戶端快取的差異與適用場景。

從你用過的 Redis 開始

你用過 Redis 做快取，但有沒有想過：當你的程式碼寫入資料時，資料是先寫到 Redis 還是先寫到資料庫？當你的程式碼讀取資料時，是先查 Redis 還是直接查資料庫？這些「先後順序」的不同，就是快取讀寫模式的核心差別。

快取讀寫模式回答一個問題：資料在快取和底層數據源之間，以什麼順序流動？不同的順序帶來不同的一致性、效能和複雜度取捨。

三種讀寫模式

模式 讀取流程 寫入流程 一致性 讀取效能
Read-Through 應用 → 快取 → 命中返回；未命中則快取自己去數據源取回 應用直接寫數據源 可能暫時不一致 極快（命中時）
Write-Through 應用 → 快取 → 命中返回；未命中則快取去數據源取回 同時寫快取和數據源（同步） 強一致性 寫入較慢
Write-Behind 應用 → 快取 → 命中返回；未命中則快取去數據源取回 只寫快取，稍後異步批量寫入數據源 最終一致性 寫入極快

Read-Through：懶加載模式

想像你在一家電商網站搜尋商品。第一次搜的時候，資料庫裡有這筆資料，但快取裡沒有（cache miss）。Read-Through 的做法是：快取系統自動去資料庫把資料取回來，存進快取，然後返回給你。下次再搜同一個商品，直接從快取返回（cache hit），非常快。

關鍵特點：數據的加載是由快取層自動處理的，應用程式不需要知道資料是從快取還是數據源來的。這簡化了應用程式碼。

適用場景：讀取頻繁、資料更新不頻繁的場景。例如電商商品目錄、新聞文章、使用者個人資料。這些資料被無數人反覆讀取，但很少變更。

Write-Through：同步雙寫

想像你在銀行轉帳。轉帳發生時，系統會同時更新快取和資料庫——兩個地方的資料永遠同步。你不會看到「轉帳成功但餘額顯示錯誤」的情況。

Write-Through 的核心是：每次寫入都同時更新快取和底層數據源，而且是同步的。寫入完成時，快取和數據源一定是一致的。

優點是強一致性——任何時候從快取讀取的資料都是最新的。缺點是寫入效能較差——每次寫入都要等兩個地方都寫完才返回。

適用場景：資料一致性要求極高的場景。例如金融交易、庫存管理、訂單系統。這些場景不能容忍短暫的不一致。

Write-Behind：異步回寫

Write-Behind 是 Write-Through 的「偷懶版」：寫入時只更新快取，不立刻寫數據源。快取層會在背景把變更異步、批量地寫回數據源。

好處是寫入速度極快——應用程式只等快取寫完（微秒級），不用等資料庫（毫秒級）。壞處是在快取寫完到數據源更新之間的窗口期，如果快取節點崩潰，那些還沒寫回的資料就會丟失。

適用場景：寫入量極大、能容忍短暫不一致的場景。例如社群媒體的按讚計數、頁面瀏覽量統計、日誌收集。這些資料偶爾丟一點點不影響核心功能。

伺服器端快取 vs 用戶端快取

除了讀寫模式，另一個重要的維度是快取放在哪裡。

維度 伺服器端快取 用戶端快取
位置 伺服器記憶體（如 Redis、Memcached） 用戶裝置（瀏覽器快取、App 本地存儲）
控制權 伺服器完全控制 用戶端控制，伺服器只能透過 HTTP header 引導
受益範圍 所有用戶共享 僅限該用戶的裝置
資料新鮮度 集中管理，容易保證 較難控制，可能展示過時資料
適用場景 降低伺服器負載、加速資料傳遞 提升個別用戶體驗、支援離線存取

你在用過的 Redis 就是典型的伺服器端快取——資料存在伺服器的記憶體中，所有用戶共享同一份快取。而瀏覽器的 HTTP 快取（例如 Cache-Control header 控制的快取）就是用戶端快取——資料存在你的瀏覽器裡，只有你能用。

實際系統通常會兩者並用：伺服器端快取減少資料庫壓力，用戶端快取減少網路請求次數。例如你的 REST API 返回的 response 帶上 Cache-Control: max-age=3600，瀏覽器會在一小時內直接用本地快取而不發請求。同時，伺服器端用 Redis 快取熱門資料，減少資料庫查詢。

面試中的關鍵點

  • 能清楚解釋 Read-Through、Write-Through、Write-Behind 的資料流動順序
  • 能根據一致性需求和讀寫比例選擇合適的模式
  • 能比較伺服器端和用戶端快取的控制權、受益範圍、新鮮度差異
  • 能說明為什麼生產系統通常同時使用兩種快取位置

小結

快取讀寫模式決定了資料在快取和數據源之間的流動方式：Read-Through 適合讀多寫少、Write-Through 適合一致性要求高、Write-Behind 適合寫入量大。快取位置則影響受益範圍和控制力：伺服器端快取降低伺服器負載、用戶端快取提升個別體驗。面試中要能根據場景需求做出選擇並解釋 trade-off。
