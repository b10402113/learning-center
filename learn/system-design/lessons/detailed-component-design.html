核心元件詳細設計

Step 5/6 · Ticketmaster 系統設計 · 約 15 分鐘

學習目標

設計 Ticketmaster 的核心元件：ActiveReservationsService 與 WaitingUsersService，理解訂票流程與等待隊列的實作方式。

先從單機場景開始

理解複雜系統的最好方法是先假設它跑在一台上伺服器上。等你把單機邏輯想清楚了，再考慮分散式場景的挑戰。

一個完整的訂票流程是這樣的：

1. 用戶搜尋電影（SearchMovies）
2. 用戶選擇電影 → 系統顯示場次（SearchShows）
3. 用戶選擇場次 → 系統顯示座位圖
4. 用戶選擇座位 → 系統暫時鎖定（ReserveSeats）
5. 用戶確認付款 → 系統完成訂單（MakeBooking）
6. 座位狀態更新為「已訂」

其中第 4 步「暫時鎖定」和第 5 步「確認付款」之間有一個時間窗口（15 分鐘）。在這段時間裡，被鎖定的座位不能被其他人選走，但如果用戶放棄了，座位需要自動釋放。這就需要一個專門的服務來管理這些「進行中」的狀態。

ActiveReservationsService

這個服務管理所有「正在進行中」的預訂。核心數據結構是一個 Linked HashMap（鏈結哈希映射）或 TreeMap（樹狀映射）：

// 簡化版資料結構
class ActiveReservationsService {
  // key: reservationID, value: { userID, showID, seatIDs, expiryTime }
  Map<String, Reservation> reservations;

  // 頭部指向最早建立的預訂（用於自動過期清理）
  // 尾部指向最新建立的預訂
}

為什麼用 LinkedHashMap？因為它支持兩個關鍵操作：

  • O(1) 跳轉——根據 reservationID 直接找到預訂（哈希表特性）
  • 按時間順序遍歷——頭部永遠是最早建立的預訂，方便清理過期預訂（鏈表特性）

當用戶付款完成後，根據 reservationID 從 LinkedHashMap 中移除對應條目，同時更新資料庫中的座位狀態為「已訂」。

WaitingUsersService

當所有座位都被佔滿時，新用戶怎麼辦？系統不能直接報錯，而是應該把用戶加入等待隊列。

// 簡化版資料結構
class WaitingUsersService {
  // key: userID, value: { showID, timestamp, requestedSeats }
  LinkedHashMap<String, WaitingUser> waitingQueue;
}

同樣使用 LinkedHashMap，因為：

  • 先到先得——鏈表頭部永遠是最早的等待者
  • 支援取消——用戶可以取消等待，根據 userID 直接刪除（O(1)）

當有人取消訂單或付款超時釋放座位時，系統從 WaitingUsersService 的頭部取出最早的等待者，通知他們可以訂購。

完整訂票流程（含等待隊列）

用戶選座
  ↓
有空位？
  ├─ 是 → ReserveSeats：建立預訂，座位鎖定 15 分鐘
  │        用戶付款？ → 成功：更新座位為「已訂」，移除預訂
  │                   → 超時：釋放座位，檢查等待隊列
  │
  └─ 否 → 加入 WaitingUsersService 等待隊列
           有人取消/超時？ → 通知最早的等待者

快取的配合

ActiveReservationsService 和 WaitingUsersService 的數據放在快取（Redis）中，因為：

  • 它們是熱數據——每個用戶的選座操作都會讀寫
  • 它們有過期時間——15 分鐘自動過期，Redis 的 TTL（Time To Live）天然支持
  • 它們需要原子操作——Redis 的 MULTI/EXEC 事務能保證

資料庫是持久化備份——預訂和等待狀態的最終來源。快取掛了可以從資料庫重建。

面試技巧

詳細設計是面試中最能展示深度的環節。重點講清楚：

  • 數據結構的選擇理由（LinkedHashMap 的兩個特性）
  • 暫時鎖定的時間窗口機制（15 分鐘過期）
  • 等待隊列的先到先得邏輯
  • 快取與資料庫的配合關係
