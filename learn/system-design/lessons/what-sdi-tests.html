系統設計面試在考什麼？

Step 1/4 · 系統設計面試入門

一個事實：沒有標準答案

系統設計面試跟演算法面試最大的不同：演算法有對錯，系統設計沒有。面試官給你一個開放式問題——「設計一個短網址服務」「設計一個聊天系統」——你不可能給出一個「完美」的答案，因為根本不存在。

那面試官到底在評什麼？

三個核心評估維度

1. 問題解決能力（Problem Solving）

你拿到一個模糊的問題後，能不能自己把它拆解成具體的、可設計的子問題。面試官不在乎你最終畫了什麼架構圖，他在乎的是你從哪裡開始、為什麼這樣拆、每一步的推理邏輯是什麼。

2. 溝通能力（Communication）

系統設計面試是一場對話，不是獨白。你需要一邊思考一邊講，讓面試官跟上你的思路。如果你默默畫了五分鐘圖再開口，面試官已經跟不上了。好的溝通意味著：

  • 先問對問題（澄清需求）
  • 解釋每一步的「為什麼」
  • 主動詢問面試官的偏好和反饋

3. 取捨判斷（Trade-off Judgment）

每個設計決策都有代價。選 SQL 就犧牲了水平擴展的便利，選 NoSQL 就犧牲了強一致性。面試官想看到的是你能意識到這些取捨，並且能根據場景做出合理選擇，而不是死記硬背「什麼場景用什麼技術」。

核心洞察：系統設計面試考的不是你知道多少技術名詞，而是你能不能在壓力下從零設計一個系統，並清楚解釋每個決策的為什麼。

它不是什麼

  • 不是背誦測驗——背熟 CAP theorem 不會幫你通過面試，理解它在什麼場景下影響你的設計才會。
  • 不是追求完美——面試官期待你犯錯、然後修正。一個在討論中不斷改進的方案，比一個看似完美但無法討論的方案好得多。
  • 不是只考技術——取捨判斷、溝通、適應性，這些「軟技能」在評分中佔比很高。

跟你之前經驗的連結

你做過 REST API，用過 Postgres 和 Redis。在系統設計面試中，這些經驗不是用來「炫耀」的，而是用來建立連結的——當你被問到「怎麼設計快取層」時，你可以說「我之前在專案中用 Redis 做 session cache，但那個場景是 X，這裡的場景是 Y，所以我會選擇 Z 方案」。這就是把個人經驗轉化為設計能力。
