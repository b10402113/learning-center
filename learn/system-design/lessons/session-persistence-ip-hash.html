IP Hash：用雜湊實現會話持久化

system-design · lb-algorithms · Step 5/6

前面介紹的演算法（Round Robin、Least Connections 等）都有一個前提：每次請求可以被任意分配到任何伺服器。但有些場景需要「同一個用戶的請求始終打到同一台伺服器」。這就是會話持久化（Session Persistence）的需求。

為什麼需要會話持久化？

典型的例子是購物車。用戶把商品加入購物車後，購物車資料可能暫存在伺服器的記憶體裡。如果下一個請求被分到了另一台伺服器，新伺服器找不到購物車資料——用戶的購物車「消失」了。會話持久化透過確保同一客戶端的請求總是路由到同一台伺服器，避免了這類問題。

其他需要會話持久化的場景：

  • 登入態依賴伺服器端 Session
  • 用戶的配置或臨時狀態存在伺服器記憶體
  • 速率限制需要追蹤單一用戶的請求

IP Hash 的工作原理

IP Hash 是最簡單的會話持久化實現方式。步驟如下：

  1. 負載均衡器取得客戶端的 IP 地址
  2. 用雜湊函數（hash function）把 IP 地址轉換成雜湊值
  3. 用雜湊值對伺服器數量取模，決定路由到哪台伺服器

假設三台伺服器 S0、S1、S2，客戶端 IP 是 192.168.1.10：

hash("192.168.1.10") % 3 = 2  →  路由到 S2

因為同一個 IP 產生同一個雜湊值，同一客戶端的每次請求都路由到同一台伺服器。

優缺點

說明
✅ 實作簡單只需要一個雜湊函數，無需額外狀態管理
✅ 無需額外儲存不需要像 Session Stickiness 那樣在負載均衡器上維護 session 表
✅ 天然持久化同一 IP 自動路由到同一伺服器
❌ 負載不均公司出口 IP 背後有大量用戶時，對應伺服器會過載
❌ IP 變化手機切換 WiFi/4G、NAT 後方的用戶 IP 會變，session 中斷
❌ 不考慮負載不管伺服器忙不忙，同 IP 永遠導到同一台

一個具體例子

假設公司有 200 名員工，所有人的流量都從同一個出口 IP（203.0.113.50）出去。負載均衡器用 IP Hash 會把這 200 人的所有請求全部導到同一台伺服器——嚴重的負載不均。這就是 IP Hash 最大的風險：多個客戶端共用一個 IP 時，hash 會產生「熱點」。

更好的替代方案

因為 IP Hash 的局限性，現代架構通常使用更精確的會話持久化方式：

  • 基於 Cookie 的持久化：負載均衡器在第一次回應中寫入 cookie，後續請求根據 cookie 路由
  • 基於 Session ID 的持久化：在 URL 或 header 中攜帶 session ID
  • 外部 Session Store：把 session 存在 Redis 等共享儲存中，任何伺服器都能取到

其中外部 Session Store 是最推薦的做法：它不綁定任何一台伺服器，任何伺服器都能處理任何用戶的請求，既实现了持久化又不影响负载均衡的灵活性。

適用場景

  • 需要簡單持久化且不想引入外部儲存的場景
  • 用戶的 IP 分散且穩定（例如面向終端用戶而非企業出口的服務）

面試提示

在面試中提到 IP Hash 時，要同時指出它的局限性。更好的做法是：先說明為什麼需要會話持久化（購物車、登入態），再提到 IP Hash 是最簡單的實現方式，最後補充「但在生產環境中，更推薦用 Redis 等外部 Session Store 配合任何一種負載均衡演算法」。這能展現你不只停留在理論，還了解實踐中的最佳做法。
