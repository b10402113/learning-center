CDN 基礎原理

部署與儲存 · 步驟 3/4 · 預計 10 分鐘

學習目標

理解 CDN 的運作原理，以及相較於直接源伺服器提供服務的優缺點與適用場景。

為什麼這很重要？

在系統設計面試中，CDN 是幾乎每個架構都會用到的組件。當面試官問「如何減少延遲？」或「如何處理全球用戶？」時，CDN 通常是第一個該提到的方案。理解它的運作原理，你就能在白板上畫出一個真正能擴展的架構。

什麼是 CDN？

想像你在台灣想看一部在美國伺服器上的影片。如果每次播放都要從美國拉資料，延遲可能高達 200-300 毫秒。但如果有人先把這部影片的副本放在台北的伺服器上，你從台北拉資料，延遲可能只有 10 毫秒——這就是 CDN 的核心概念。

CDN（Content Delivery Network，內容傳遞網路）是一個由分布在全球各地的伺服器組成的網路，它根據使用者的地理位置來提供網頁內容。CDN 在多個地點快取（cache）內容，讓使用者從最近的伺服器取得資料。

特性 說明
地理分布 伺服器遍布全球多個地理位置
內容快取 儲存網頁內容的副本（HTML、圖片、影片等）
邊緣節點 離使用者最近的伺服器節點
自動路由 根據地理位置自動選擇最近的節點

直接源伺服器服務（Direct Server Serving）

相對地，直接源伺服器服務就像：不管你人在哪裡，每次要看影片都要從美國的原始伺服器拉資料。所有請求都直接打到同一個位置。

在直接源伺服器服務中，所有使用者請求都由網站託管的主伺服器直接處理，沒有中間的 CDN 節點：

特性 說明
單一位置 伺服器通常位於單一地理位置
直接傳遞 所有內容直接從源伺服器傳送到使用者
簡單架構 不需要額外的基礎設施
延遲較高 離伺服器遠的使用者體驗較差

關鍵差異對比

維度 CDN 直接源伺服器
內容傳遞 分散到全球多個伺服器 依賴單一位置的伺服器
效能 延遲低、載入快 離伺服器遠的使用者延遲高
擴展性 能處理大量全球流量 受限於單一伺服器的容量
成本 有 CDN 費用，但減輕源伺服器壓力 架構簡單，但需要更強的源伺服器
使用者體驗 全球使用者都有快速體驗 本地使用者體驗好，遠端使用者體驗差
適用場景 全球用戶、靜態資源、媒體檔案 本地用戶、動態內容、小型網站

CDN 的運作流程

當使用者請求一個網頁時，CDN 的運作流程如下：

  1. 使用者發送請求（例如請求一張圖片）
  2. DNS 解析將請求導向最近的 CDN 邊緣節點
  3. 如果邊緣節點有快取（cache hit），直接回傳
  4. 如果邊緣節點沒有快取（cache miss），從源伺服器拉取並快取
  5. 邊緣節點回傳內容給使用者

什麼時候用 CDN？什麼時候不用？

適合使用 CDN 的場景：

  • 網站有全球用戶群
  • 網站提供大量靜態資源（圖片、影片、CSS、JavaScript）
  • 需要降低延遲、提升載入速度
  • 需要減輕源伺服器的流量壓力
  • 需要 DDoS 防護（很多 CDN 提供此功能）

不適合使用 CDN 的場景：

  • 用戶主要集中在同一個地理區域
  • 內容高度動態且無法快取
  • 預算有限且流量不大
  • 需要即時更新的內容（如即時股票行情）

面試技巧

在系統設計面試中，當你畫出架構圖時，主動在使用者和源伺服器之間加入 CDN 層。然後說明：「CDN 用來快取靜態資源，減少源伺服器的壓力，並為全球用戶提供低延遲的體驗。」這顯示你理解效能優化的基本原則。

小結

CDN 是現代系統設計的基礎組件。它的核心價值是把內容搬到離使用者最近的地方。在面試中，只要提到「全球用戶」、「靜態資源」、「延遲優化」，就應該想到 CDN。
