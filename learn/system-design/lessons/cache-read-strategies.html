快取讀取策略

system-design · caching · Step 4/4

學習目標

掌握常見的快取讀取策略（read-through vs read-aside），理解兩者的差異與適用場景。

問題：誰去取數據？

快取建好了，失效策略也選好了，但還有一個關鍵問題：當應用程式需要數據時，快取未命中了，「誰負責去數據源取數據？」

這個問題的答案決定了快取的讀取策略。兩種最常見的策略是 read-through 和 read-aside（也叫 cache-aside 或 lazy-loading），核心差異就在於「誰去取數據」。

Read-through Cache（穿透式快取）

應用程式只跟快取打交道，快取層自己負責在未命中時去數據源取數據。

應用程式 → 快取 → 命中？ → 是 → 返回
                    ↓ 否
              快取自己去數據源取 → 存入快取 → 返回

用書店比喻：客人問書在哪裡，你（店員）只管看陳列架。如果陳列架上沒有，倉庫管理員自動去倉庫找，找到後放到陳列架上，你再拿給客人。你完全不需要知道倉庫在哪裡。

面向 說明
優點 應用程式代碼簡單、乾淨，不需要處理快取未命中的邏輯
缺點 第一次訪問延遲較高（快取層額外處理）；快取層邏輯可能複雜
適用場景 標準化、重複性的數據訪問模式

Read-aside Cache（旁觀式快取）

應用程式自己負責在快取未命中時去數據源取數據，然後放入快取。

應用程式 → 查快取 → 命中？ → 是 → 使用
                      ↓ 否
            應用程式自己去數據源取 → 存入快取 → 使用

用書店比喻：客人問書在哪裡，你（店員）先看陳列架。如果沒有，你自己走去倉庫找，找到後放到陳列架上，再拿給客人。

面向 說明
優點 應用程式對快取邏輯有完全掌控——可以決定什麼時候填充、用什麼格式存儲
缺點 每次未命中時應用程式都要多做一次「取數據 + 寫入快取」操作，代碼較重複
適用場景 需要客製化快取邏輯的場景

兩種策略的對比

面向 Read-through Read-aside
誰取數據 快取層 應用程式
應用程式複雜度 低（只跟快取互動） 高（要處理取數據邏輯）
控制力 低（快取層決定一切） 高（應用程式完全掌控）
首次訪問延遲 較高（快取層額外處理） 取決於應用程式實現
典型實現 某些快取框架的自動模式 Redis + 應用程式邏輯

實際應用：Redis + 應用程式

在實際系統中，read-aside 是更常見的選擇。Redis + 應用程式的組合就是典型的 read-aside 模式：

// read-aside 範例（偽代碼）
data = redis.get(key)
if data is null:
    data = database.query(key)   // 應用程式自己去取
    redis.set(key, data, ttl=300) // 存入快取
return data

應用程式完全掌控快取邏輯：可以決定用什麼 key、設定什麼 TTL、是否跳過某些數據。這種靈活性是 read-aside 的最大優勢。

面試中的關鍵點

面試官想聽到的是：

  • 你能清楚比較兩種策略的差異（不只是列出來，要能解釋為什麼）
  • 你能根據場景選擇合適的策略
  • 你知道 read-aside 在實際系統中更常用
  • 你能手寫 read-aside 的基本邏輯（偽代碼或程式碼片段）

小結

Read-through 和 read-aside 的核心差異在於「誰負責在未命中時去數據源取數據」。Read-through 讓快取層負責，應用程式簡單但控制力低；Read-aside 讓應用程式負責，代碼較重但靈活性高。實際系統中 read-aside 更常見，Redis + 應用程式是典型實現。
