學習目標

理解即時通訊系統的核心元件與其分工，繪製高層架構圖。

Chat Server：系統的心臟

整個即時通訊系統的核心是一個或多個 Chat Server（聊天伺服器）。所有用戶的訊息都經過它：用戶發訊息時連線到 Chat Server，Chat Server 把訊息轉發給對方，同時寫入資料庫。

為什麼需要一個中央伺服器？因為即時通訊要求低延遲、高可靠。如果讓用戶之間直接 P2P 連線，你得處理 NAT 穿透、用戶離線、訊息亂序等一堆問題。Chat Server 作為中間人，簡化了整個模型。

高層架構

整個系統由四個核心區塊組成：

1. 用戶設備（Client）

手機 App 或網頁。用戶透過它發送和接收訊息，查看在線狀態。客戶端和 Chat Server 之間維持一個持久連線（Persistent Connection），這樣伺服器才能主動推送新訊息。

2. 聊天伺服器（Chat Server）

系統的核心。它的職責是：

  • 接收用戶發來的訊息
  • 將訊息轉發給目標用戶
  • 將訊息寫入資料庫（通常異步寫入）
  • 維護用戶的在線狀態
  • 處理用戶的連線生命週期（連線、斷線、重連）

3. 資料庫（Database）

儲存所有聊天記錄。因為五年要存 3.6 PB 的數據，所以不能用單一資料庫，需要分片。具體怎麼分，後面的步驟會詳談。

4. 快取（Cache）

緩存最近的訊息和用戶狀態。用戶打開對話時，最近的訊息從快取讀取，不用每次都查資料庫——這大幅降低了延遲。

詳細工作流程

當用戶 A 發訊息給用戶 B 時，具體發生了什麼？

  1. A 連線到 Chat Server：A 的設備和 Chat Server 之間有一條持久連線（WebSocket 或 long polling）
  2. A 發送訊息：A 把訊息發到 Chat Server
  3. Chat Server 處理訊息：
    • 把訊息寫入資料庫（異步，不阻塞）
    • 查找 B 的連線所在在哪台 Chat Server
    • 把訊息轉發給 B
  4. B 收到訊息：B 的設備收到推送，顯示新訊息

整個過程要在幾百毫秒內完成。如果 B 不在線，訊息先存到資料庫，等 B 上線時再拉取。

為什麼這樣設計？

這個架構有一個關鍵設計決策：Chat Server 是無狀態的還是有狀態的？

  • 有狀態：Chat Server 記住每個用戶的連線。這讓訊息轉發很快（直接查本地映射），但伺服器掛掉時需要處理連線遷移
  • 無狀態：Chat Server 不記住任何用戶狀態。這讓伺服器更容易擴展和替換，但每次轉發訊息都要查一次狀態儲存

實際系統（如 Facebook Messenger）通常選擇有狀態，因為即時通訊對延遲極度敏感。具體的容錯機制會在後面的步驟中討論。
