什麼是限流，為什麼需要限流

system-design · rate-readwrite · Step 1/4

學習目標

理解限流的基本概念、應用場景與為什麼它是高併發系統設計不可或缺的機制。

從一個真實的崩潰說起

想像你經營一個電商網站，平時每秒處理 500 個請求。某天辦了一場限時搶購活動，流量瞬間湧入，每秒湧進 50,000 個請求。你的伺服器瞬間過載，CPU 跑滿、記憶體爆掉，結果所有用戶——包括那些正常瀏覽的人——全都看到 503 錯誤頁面。

這個問題的根源是：系統沒有機制控制進入的流量。不管後端能消化多少，所有請求一股腦湧進去，最終把整台機器壓垮。

限流（Rate Limiting）就是解決這個問題的機制：它在請求進入後端之前設一道閘門，按照某種規則允許或拒絕請求，確保系統永遠不會被超出處理能力的流量打垮。

限流的核心思想

限流的本質很簡單：限制在一個時間窗口內，系統能處理的請求數量。超過上限的請求會被拒絕（返回 429 Too Many Requests）或排隊等待。

這裡有兩個關鍵概念：

概念 含義 類比
Rate（速率） 單位時間內允許通過的請求數 高速公路每個小時允許通過多少輛車
Burst（突發容量） 系統短時間內能承受的最大超出量 高速公路的匝道Metering燈：短時間內可以放行一批車，但不能一直放

一個好的限流策略需要在兩者之間取得平衡：太嚴格，正常流量也被擋掉；太寬鬆，突發流量還是會壓垮系統。

為什麼需要限流

限流不只是「防止伺服器崩潰」這麼簡單，它在系統設計中有四個關鍵作用：

1. 保護後端資源

這是最直覺的作用。每個請求都消耗 CPU、記憶體、網路頻寬或資料庫連線。如果不限流，一波突發流量可能瞬間耗盡所有資源，導致所有用戶都無法使用。限流確保後端永遠在安全的負載範圍內運作。

2. 防止惡意攻擊

DDoS 攻擊（分散式阻斷服務攻擊）的本質就是用大量請求癱瘓目標系統。限流是第一道防線：不管攻擊者從多少個 IP 發起請求，限流器都會按照規則拒絕超量的流量。

同樣地，暴力破解登入密碼、大量註冊假帳號等惡意行為，也可以透過限流來控制——例如同一個 IP 每分鐘最多嘗試 5 次登入。

3. 控制成本

在雲端環境中，每一個請求都代表真金白銀的運算資源。如果沒有限流，一波異常流量可能讓你的帳單暴增十倍。限流等於給你的預算裝了保險絲。

4. 確保公平性

多租戶（Multi-tenant）系統中，不同用戶或客戶端可能共用同一套後端資源。限流可以確保每個租戶都拿到公平的配額，不會因為某個租戶的異常行為影響其他人。你用過的雲端 API 服務（如 GitHub API、Twitter API）都有 rate limit 就是這個道理。

限流在哪裡發生

限流可以部署在系統的不同層級：

位置 說明 優缺點
用戶端 在 App 或瀏覽器端限制發送頻率 減少網路請求，但用戶可以繞過
API Gateway 在統一入口處攔截，最早擋住超量請求 集中管理，但需要額外基礎設施
負載均衡器 在 LB 層做限流，分散式部署 能分散限流壓力，但設定較複雜
個別服務 在每個微服務自己的入口做限流 粒度最細，但管理成本高

實際生產環境中，最常見的做法是在 API Gateway 層做粗粒度的全局限流，再在個別服務做細粒度的限流。兩層防線互相補充。

限流的常見策略

限流有很多種具體的演算法，不同的演算法適合不同的場景：

  • 固定窗口計數器（Fixed Window Counter）：最簡單——在固定時間窗口（如每秒）內計數，超過上限就拒絕。問題是窗口邊界可能出現雙倍突發。
  • 滑動窗口計數器（Sliding Window Counter）：改進版——用滑動時間窗口避免邊界問題。
  • 漏桶（Leaky Bucket）：請求進入一個桶，以固定速率流出。適合需要平滑流量的場景。
  • 令牌桶（Token Bucket）：系統以固定速率生成令牌，請求需要取得令牌才能通過。適合允許突發但需要控制長期速率的場景。

小結

限流是高併發系統的保險絲：它控制進入後端的請求速率，保護系統不被流量壓垮。核心概念是 Rate（長期速率）和 Burst（短期突發容量）的平衡。限流可以部署在 Client、API Gateway、負載均衡器或個別服務的不同層級。常見演算法包括固定窗口、滑動窗口、漏桶和令牌桶。
