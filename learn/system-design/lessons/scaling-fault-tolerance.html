擴展與容錯設計

Facebook Messenger 系統設計 · Step 6/6

學習目標

掌握即時通訊系統如何透過資料分片、快取、負載均衡與複製來實現擴展與容錯。

三大擴展策略

前面的設計可以撐住幾百萬用戶。但要撐住 5 億日活用戶，你需要三把利器：分片（Partitioning）、快取（Caching）、負載均衡（Load Balancing）。

資料分片

5 億用戶、每人 40 則訊息、五年 3.6 PB——一台資料庫根本扛不住。你需要把數據分散到多台機器上。

按 UserID 分片

最直覺的做法：對 UserID 做 hash，hash 值決定數據在哪台機器上。好處是同一個用戶的所有訊息都在同一台機器上，查詢兩個人的聊天記錄只需要訪問一台機器。

分片數量估算

假設每台資料庫分片承載 4 TB：

指標數值
五年總儲存3.6 PB
每分片容量4 TB
需要的分片數3.6 PB ÷ 4 TB ≈ 900 個

900 個分片聽起來很多，但這是五年增长的終態。初期可以少一些，隨增長逐步增加。

分片的挑戰

  • 熱點：某些用戶訊息量特別大（如名人），導致某個分片負載過高
  • 跨分片查詢：查詢兩個不在同一分片的用戶的聊天記錄，需要跨機器
  • 再平衡：新增或移除分片時，數據遷移的開銷

快取

快取的目標：讓用戶打開對話時，最近的訊息從記憶體讀取，延遲從百毫秒降到個位數毫秒。

快取策略

  • 快取最近 15 條訊息：對每個活躍對話，快取最近 15 條訊息
  • 快取最近 5 個對話：對每個用戶，快取最近 5 個對話的最近 15 條訊息
  • 按 UserID 分佈：因為數據按 UserID 分片，每個用戶的快取也應該在同一台快取伺服器上

快取失效

新訊息到達時，怎麼更新快取？有兩種策略：

  • Write-through：寫入資料庫的同時更新快取。一致性好，但寫入延遲增加
  • Write-behind：先更新快取，資料庫在背景異步更新。寫入快，但有短暫不一致

即時通訊通常選 Write-behind——先讓用戶看到新訊息，資料庫慢慢跟上。

負載均衡

系統中有兩層負載均衡：

Chat Server 負載均衡

用戶的連線請求先到負載均衡器，由它決定分配給哪台 Chat Server。關鍵要求：同一個用戶的請求必須落到同一台 Server（因為 Server 記住了用戶的連線）。這需要一致性雜湊（Consistent Hashing）或類似的有狀態負載均衡。

資料庫負載均衡

資料庫層的負載均衡相對簡單——根據 UserID 的 hash 決定路由到哪個分片。這是確定性的，不需要動態分配。

容錯設計

硬碟壞了、伺服器掛了、機房斷電——這些在大規模系統中不是「萬一」，而是「一定會發生」。

Chat Server 宕機

如果一台 Chat Server 掛了，上面所有用戶的連線都會斷開。怎麼辦？

  • 客戶端自動重連：偵測到連線斷開後，自動嘗試連線到其他可用的 Chat Server
  • 不要嘗試遷移連線：TCP 連線遷移到其他伺服器極其複雜，不如讓客戶端重連

資料庫故障

  • 主從複製：每個分片有主從副本。主節點故障時，從節點提升為主節點
  • 讀寫分離：寫入走主節點，讀取走從節點。這也分散了負載

訊息可靠性

  • 端到端確認：A 發訊息給 B，B 收到後回一個 ACK。A 沒收到 ACK 就重發
  • 客戶端重試：訊息發送失敗時，客戶端自動重試
  • 持久化保障：訊息先寫入資料庫（或 WAL），再推送給用戶。確保不丟
