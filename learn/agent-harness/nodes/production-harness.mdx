# 生產級 Harness 與下一步

## Learning goal

收斂 chat agent 的最小 harness 清單（tool calling + 自己掌握記憶 + 壓縮），判斷哪些能力是 table stakes、哪些 situational，並理解 durable 解耦、infinite/background agent 與 inbox、託管沙箱與 eval。

## Steps

閱讀順序（`deps` 標示哪些步驟必須先讀）：

1. [[learn/agent-harness/nodes/production-harness/minimum-harness-stack|最小可上線的 Harness 清單]] — tool calling、自己掌握的記憶、壓縮；durable 可延後、turn limit 防跑飛
2. [[learn/agent-harness/nodes/production-harness/table-stakes-vs-situational|Table stakes 與 situational：從目標體驗反推]] — 從交付體驗推導需求，分清哪些能力非有不可、哪些看情況（after step 1）
3. [[learn/agent-harness/nodes/production-harness/durable-decoupling|Durable 解耦：讓 run 不再依附 client]] — durable 如何切開 run 與 client，何時從延後項變成必要（after step 2）
4. [[learn/agent-harness/nodes/production-harness/infinite-background-agents|無限／背景 agent 與 inbox]] — 給任務或等事件、無限地跑、用 inbox 互動；難在 eval 與約束（after step 3）
5. [[learn/agent-harness/nodes/production-harness/production-hardening-and-eval|生產硬化：託管沙箱與 eval]] — 把工具執行移到託管沙箱，用 eval 驗證改進（after step 2）

## Lesson

前面十個節點把所有能力一層層疊了上去：工具、持久化迴圈、沙箱、記憶壓縮、handoff、階層式監督、審批。最後這個節點不再加新的機制，而是把整條線收乾淨——回答一個上線前必問的問題：**如果只能留三樣，留哪三樣？**

答案出乎意料地樸素：tool calling、由自己掌握的記憶、以及記憶壓縮。前三者在每個 SDK 裡幾乎免費，真正的分水嶺在「記憶存在誰那裡」。把歷史存進自己的資料庫（而不是模型供應商的對話狀態），你才能控制保留什麼、丟掉什麼，也才能在歷史變長時壓縮它。durable execution 反而可以延後：它解耦的是「run 活在哪裡」，對一個聊天型 agent 而言，先讓 SSE 重整不丟失工作就算過關。

但這份清單不是普世真理，而是「chat agent」這個體驗的答案。換一個體驗——例如 24 小時盯盤的 trading agent——需求會整個換一組：自癒、guardrail、approval、PII 保護、自評迴圈全部變成非有不可；反之，單純送訊息、收回應的 agent 根本不需要 durable。所以這個節點真正要練的判斷力是：**先想清楚要交付什麼體驗，再反推需要哪幾層 harness**，而不是照著任何一份 checklist 往下蓋。

收尾往兩個方向看。第一個方向是 agent 的下一步形態：無限／背景 agent——它不跟你對話，而是拿一個任務或等一個事件，然後用 inbox 把問題、審批、選項丟回來；在那個世界裡 durable 是入場券，messages API 反而多餘。第二個方向是生產現實：把沙箱換成託管服務、用 eval 驗證每一次改動、並認清多用戶的非寫程式產品終究得自己寫 programmatic agent。走完這五步，你不只完成了一個 harness，也拿到了判斷「下一個 agent 產品缺哪一層」的眼力。
