# Recovery 為什麼會重跑 workflow body

上一節把 tool call、`emit` 和回填都關進 step 了。但重啟之後，是誰決定哪些 step 要跳過？

當你關掉伺服器時，agent 可能正思考到一半，工具也可能剛執行了一部分。

按照一般程式的直覺，伺服器一關，記憶體裡的狀態就消失，只能從頭開始。但接上 durable engine 之後，即使重開伺服器、重新整理瀏覽器，流程仍然能接著剛才的進度繼續執行。

這一節要拆開看這個過程：

- 重啟後，哪些內容會重新執行？
- 哪些已完成的工作會被跳過？
- 「註冊 workflow」在其中扮演什麼角色？

## 先把名字改對：workflow 不是普通函式

整理程式碼時，可以先做一個小調整：把裝著 agent 迴圈的函式改名為 `agentWorkflow`。

不強制，但很有幫助。

在 durable engine 裡，workflow 是一種特殊的函式。它裡面可以放 step；寫在 step 外、沒有綁進任何 step 的程式碼，則有另一套行為規則要遵守。

在函式名稱裡放入 `workflow`，是在提醒自己：這不是一個想到什麼就寫什麼的普通函式。重啟時，這個函式會用另一套規則重新執行。

## 失敗通知也要只發生一次

原本程式最下面有一段 `emit`，用來通知 client：「workflow 失敗了。」

這段通知不能因為 workflow 重跑，就再次發送。因此，它也必須放進一個 step 裡。

做法是再包一個 `DBOS.runStep`，命名為 failed step。失敗時回傳空字串即可，回傳內容隨意，反正重點是這段通知已經進到 step 的保護範圍裡。

<!-- derived -->

```ts
// 最底下的失敗通知也放進 step，確保它不會被重跑第二次
DBOS.runStep("failed step", () => {
  emitWorkflowFailed();
  return "";
});
```

## 註冊，step 才有意義

前面已經把程式碼一段一段搬進 step。最後還要做一件事：別再直接 export 這個函式，把它註冊成 DBOS workflow。

<!-- derived -->

```ts
const runAgentWorkflow = registerWorkflow("agent workflow", agentWorkflow);
```

註冊不是走個形式。

沒有註冊，你寫的 step 就只是一般的函式呼叫。重啟時，沒有人會記得這些 step 是否已經執行過。所以必須先 register 這個 workflow，step 才真正有作用。

<!--image:1-->

註冊後，workflow 跑起來的結果和原本一樣。邏輯一點都沒變；我們只是把程式碼拆進 step，再把函式註冊給 DBOS。

## 重啟時到底發生了什麼

來看一個實際情境。

先給 agent 一些任務，讓它開始思考，也讓工具真正執行。趁它還在思考時，把伺服器關掉；接著重新啟動伺服器，回到頁面重新整理。

這時，agent 會從剛才中斷的地方繼續，甚至還能自行接著串流輸出。

為什麼它會自己繼續？

因為模型看到訊息陣列最後一則是懸空的 tool message 或 assistant message，就知道自己還欠一次 generation，於是會接著完成。整個過程中，我們只重新整理了瀏覽器，client 並沒有另外參與恢復流程。

重啟之後，workflow body 會從頭執行一次；已經完成的 step 會被跳過，剩下的 step 才會繼續執行。

這就是「recovery 會重跑 body」的意思：

- 會重新執行的是 workflow body 這個普通函式本身。
- step 則負責讓已完成的工作不必重做。

<!--image:2-->

放進 step 的內容，也因此有了持久化保障。重啟前已經完成的結果仍然存在；重新整理頁面看得到，關掉伺服器再回來也看得到。

以前做不到這件事，是因為根本沒有 persistence。當時這些結果會隨著伺服器關閉而直接消失。

## 為什麼一個 step 裡要放好幾件事

`call a tool` 其實包含好幾個動作：

1. 真的呼叫工具。
2. 更新訊息。
3. `emit` 給 client 顯示。

這些動作會全部放在同一個 step 裡，不再繼續往下拆。

因為 step 是重跑的最小單位：要嘛整組重新執行，要嘛整組都不執行。

這是刻意的設計。假設不小心只重做其中一個動作，例如 `emit` 發出去了，但工具其實沒有重新執行，client 就會顯示一個根本沒有發生過的結果。

所以要重跑，就得整組一起重跑。這幾個動作本來就屬於同一個單位。

<!--image:3-->

model turn 也是一樣。

串流文字、等整個 stream 結束，這兩件事必須一起成立，所以也共用同一個 step。

## 這整件事其實只是重構

回頭看，我們沒有增加任何新邏輯，做的只有重構：

1. 把程式碼搬進 step。
2. 把 step 放進一個普通函式。
3. 把這個函式交給 DBOS，讓它轉成 workflow。

就這樣。

完成這些調整後，重啟時 workflow body 會從頭執行，做完的 step 跳過，剩下的工作自動繼續。

這些行為不是因為你在每個地方另外寫了救援程式，而是「註冊過的 workflow」加上「清楚的 step 邊界」自然帶來的結果。
