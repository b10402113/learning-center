# Workflow body 可以重跑，step 的結果會被記住

上一節把三類不能重跑的動作包進 step。但 step 到底切出什麼邊界，還沒說清楚。

你的 agent 迴圈已經可以跑起來了。

但如果 server（伺服器）突然掛掉，重啟後，跑到一半的任務就會中斷。這時你可能只能從頭再跑一次整段程式。

問題來了：已經做過的事，會不會全部重做？打過的 tool 會不會再打一次？事件會不會重複寫進 log？

要回答這些問題，先把兩個名詞分開：**workflow** 和 **step**。

## step 是把工作包起來、結果記住的單位

step 就是把一段你希望被保存的工作包起來。

這裡的「保存」指的是持久化（persist）：把資料寫進資料庫，不能只丟在記憶體裡，process 結束就全沒了。

包進去之後，這個任務的輸入與輸出會被記在資料庫裡。

<!--image:1-->

所以，step 的重點是讓這一塊工作的結果有人記住。切成小塊比較好讀，不是主要目的。

負責這件事的引擎是 DBOS，一個 durable execution engine，直譯是「耐久執行引擎」。白話說，程式掛掉、重新啟動之後，它還能接回原本的進度。

## Workflow body 是每次都可以重跑的那段程式

一個 workflow，就是把多個 step 組合起來的流程。

如果執行失敗，需要重新嘗試，做法不是把整段程式改成「從中間接著跑」，而是讓 workflow body（也就是 step 外面的主程式）從頭再跑一次。

重跑的時候，做過的 step 會被直接跳過。

<!--image:2-->

引擎會回頭查詢資料庫裡這個 workflow ID 的紀錄。

如果發現某件事已經做過，就沿用之前保存的結果，不會再執行一次。workflow body 能重跑，靠的就是這個機制。

這也是為什麼每個 step 都必須是 idempotent 的。

idempotent 直譯是「冪等」，意思是重複執行不會改變結果：同一個動作跑兩次、三次，最後得到的結果都一樣。

這是分散式系統的基本觀念：在分散式環境裡，同一件事被執行兩次是常態，不是意外。所以動作要設計成可以安全重複執行。

## 該包進 step 的兩樣東西

想一下你現在的 agent runtime：哪些工作需要被保存，才能在失敗後繼續運作？

第一是 **tool call**。

每個 tool call 都可能需要重試、暫停，或是在 server 掛掉之後繼續保留。因此，每個 tool 都應該包進自己的 step。

<!--image:3-->

第二是 **事件發送**。

事件送出後，會被寫進 event log，並存在 Postgres 裡，成為一份完整的歷史紀錄。

你不希望同一個事件被重複寫進資料庫，所以發送事件也要包進 step：避免重複，也撐得過 server 失敗。

在目前的實作裡，這兩類工作交給 durable execution 處理。都轉成 step，組合起來就是一個 workflow。

<!-- derived -->
```text
workflow body（失敗就整段重跑）:
  組 prompt、決定下一步              ← 每次都一樣，留在 step 外
  step(() => 執行一個 tool call)     ← 輸入輸出記進 DB，重跑時跳過
  step(() => 發出一個事件)           ← 事件寫進 event log，不會重複
```

## 可以留在 step 外面的程式碼

那麼，workflow body 裡還剩下什麼？

答案是：每次執行都完全一樣的程式碼。

如果一段程式不依賴任何非決定性（nondeterministic）因素，也就是結果不受外部隨機性影響，那麼不管執行幾次都會得到相同結果。這類程式留在 step 外就好，也就是直接放在 workflow body 裡。

判斷方法很簡單：

這段程式碼重跑一百次，行為會不會每次都完全一樣？

會，就留在 step 外；不會，就包進 step，讓資料庫替你記住結果。
