# Code mode 的帳單：把算術外包給程式

上一課從「速度」談 code mode：一支程式跑完，勝過十幾輪工具往返。

這個說法沒錯，但只回答了「比較快」，還沒回答另一個更關鍵的問題：為什麼把算術交給程式，不只是更快，也更可靠？

這一課用一個實際的退款案例，看看「算對」在實戰中是怎麼發生的。

## 模型會寫程式，但不會數數

很多人都遇過這種情況：請模型算一個數字，結果算錯；把幾個日期交給它，日期也可能張冠李戴。

素材作者甚至說，他很不喜歡在 LLM 呼叫中放日期，因為模型常常會把日期搞錯。數字一多，就像桌上的彈珠開始滾動，總有一顆可能滾到錯的地方。

原因在於，模型的推理本質上是機率性的。模型做的事情，是預測下一個 token；而數字剛好是它很容易猜錯的內容。

給它十個數字，它可能九次答對，但只要有一次錯，就可能讓整個結果失效。

不過，同一批人通常也同意另一件事：LLM 寫程式，遠比它自己數數可靠。讓它寫一段算數的程式，它寫得很好；要它直接把答案數出來，它就開始亂猜。

把這兩件事放在一起，做法就很清楚了：精確的算術，交給程式執行，不要交給模型自己推算。

## 加一句 system prompt 就能開始

要讓模型改用程式，其實不必更動整個架構，只要在 system prompt 裡加上一句話。

素材作者現場示範的是：

> Oh, by the way, if you need to do arithmetic, please use the run code tool to create some JavaScript code and run it in an async wrapper function.

意思是：遇到算術問題，不要自己算；請使用 run code 工具，寫一段 JavaScript，並包在非同步包裝函式（async wrapper function）中執行。

作者也說，這句話沒有標準版本，實際上想怎麼寫都可以。重點只是讓模型知道，它有這個選項。

當時的 harness 裡還掛著兩個工具：get charges，用來取得扣款紀錄；search KB，用來查詢知識庫。

接下來，這兩個工具會變成程式可以使用的原料，而不是讓模型一輪又一輪地直接呼叫。

## 退款案例：被重複扣款的 $49

接著進入實戰。作者在 harness 裡放入一組假扣款紀錄，然後請模型找出應該退款的金額。

模型先進行分類，再決定使用 run code。它產生的程式做了三件事：

1. 使用 `await get charges` 取得扣款資料。
2. 找出重複的扣款。
3. 到知識庫查詢退款政策。

程式執行完後，輸出了一個數字：退款金額剛好是 **$49**。

作者回頭檢查假資料，發現同一個顧客在同一天被扣了兩次 $49。程式找出這兩筆重複扣款，查到相關政策，再算出退款金額，整個流程都正確。

## 為什麼這次不會錯？

如果沒有 code mode，模型可能會先呼叫 search charges 工具，讀取回傳資料，再自己在腦中比對重複扣款，最後自行計算退款金額。

每一個步驟都帶有機率性。資料越多，模型就越可能在其中一輪出錯。

改寫成程式後，情況就反過來了。

程式是 deterministic 的，也就是「輸入相同，輸出就相同」。只要把相同的資料餵給程式，它每次都會得到同樣的結果。

模型擅長寫程式，卻不擅長自己數數。那就讓模型負責寫程式，再把數數交給執行環境。

## 帳單：工具呼叫次數往下掉

最後來算總帳。

這個案例的另一個收穫，是工具呼叫次數下降了。原本的流程可能是「搜尋扣款、進行推理、查詢政策、計算金額」，中間需要好幾輪來回。

現在則變成一支腳本、一次執行，直接得到一個結果。作者形容這樣的方式是 **way faster**——比丟給模型一堆工具，再讓它自己慢慢推理，快得多。

這才是「外包」真正的意思：不是模型突然變聰明，而是把模型不擅長、卻有明確規則的工作，交給一段可以重複執行的程式。

模型負責寫，程式負責算，各自處理自己擅長的事。

## 誠實的但書

作者也承認，這項技術目前仍算是 bleeding edge，實際上還沒有多少人放進 production 使用。

而且，讓 agent 自己寫一段用完就丟的 throwaway code，再用這段程式回答自己的問題，本身確實有點 spooky——它寫出一段程式，再替自己把答案算出來。

不過，作為一種 optimization，這個做法仍然值得嘗試。

它也同時把下一課要面對的問題帶到檯面上：這段程式究竟要在哪裡執行？

模型寫出的程式屬於 untrusted code，也就是不可信任的程式碼。如果直接在 host 上執行，可能會造成問題。因此，下一步就是討論 sandbox。
