# 重啟後 replay：把斷線的時間軸接回來

你已經把事件先寫進 Postgres，再廣播給 client，也拿到了 `subscribe` 與 `history` 兩個介面。接著可以做個破壞性實驗：趁 agent 正在思考時，把 server 直接關掉。

這時 UI 上的串流會中斷，瀏覽器停在半空中，看起來就像災難現場。你第一個想到的問題可能是：剛剛那些事件還在嗎？

還在。它們會留在 event log 裡。

這一節來看 client 重新連線後，server 怎麼補回「斷線期間錯過的事件」，以及 agent 重啟後為什麼能自己接著跑。

## 連上來的第一件事：replay 歷史

前端每次連上 WebSocket，server 端的 `on connection` 不等新訊息，先把歷史事件倒出來。

`on connection` 裡做了兩件事：

1. 使用者送出新任務時，啟動 workflow。
2. client 連線後，將歷史事件 replay 給它。

第二件事的做法很簡單：呼叫 `history` 取得全部事件，再一則一則送出去，就像是在告訴 client：「這些是你斷線期間錯過的內容。」

<!-- derived -->
```ts
// on connection：把歷史一則一則補給連上的 client
for (const event of await history()) {
  socket.send(JSON.stringify(event));
}
```

<!--image:1-->

重點是「一則一則」送出。

事件不是打包成一大包後一次傳過去，而是逐則 stream in，形式和即時串流完全一樣。對前端來說，補回舊事件和接收新事件走的是同一條管線，UI 不需要分辨眼前這則訊息究竟是 replay，還是剛剛才發生的事件。

## 為什麼重連後是「同一條」時間軸

`history` 取回 event log 裡已經保存的事件，並依照 `seq` 順序排列。

client 重連後，會依序 replay 這些歷史事件，重建出和斷線前相同的時間軸。時間軸沒有從頭開始，也不是只剩斷線後的新事件，前後的內容都接了回來。

<!--image:2-->

`seq` 在這裡負責把事件順序固定下來。

不管斷線幾次、補 replay 幾次，每次都會照同一個順序播放。所以你在斷線後看到的對話，和斷線前是同一條時間軸，不是一條長得很像的替代品。

## Workflow 為什麼自己接下去跑

demo 裡最神奇的一幕是：趁 agent 正在 thinking 時把 server 關掉，接著重開 server、重新整理瀏覽器。結果不只原本的進度接回來了，workflow 還會繼續往下跑。

這件事和 client 沒有關係，你只要重新整理頁面就好。

原因在 server 這邊：重啟後會把事件還原成 `messages` 陣列，再餵回給 LLM。LLM 會根據最後一則訊息判斷自己是否需要生成內容。

如果最後一則是 `user` 訊息，LLM 會知道該回話了；如果最後一則是 `tool` 的結果，它會知道剛才呼叫的工具已經回傳，接下來輪到自己繼續處理。

也就是說，訊息陣列的尾端只要掛著一則還沒回覆的訊息，LLM 就會再做一次 generation。

<!--image:3-->

它根本不知道自己剛才被重啟過。對它來說，這只是一段「還沒回覆完成」的對話。

反過來，如果最後一則訊息是 assistant 自己說的話，LLM 就不會再回覆。否則就會出現兩則 assistant 訊息連在一起的奇怪對話。

demo 裡 server 被 kill 的時機，剛好是在「tool 結果已經餵進去，但模型還沒回覆」的狀態。因此重啟後，workflow 就會自然接著跑下去。

## 你現在去跑會看到什麼

先啟動 server，再給它一個會使用工具的任務，例如請它完成好幾件事。趁它正在 thinking 時，把 server 關掉。

接著重新啟動 server、重新整理瀏覽器。你會看到剛才的對話仍然存在，而且 workflow 還會繼續往下執行。

再整理一次，結果一樣。之後就算再殺掉一次 server，重開後也能接回來。

在沒有 persistence 的版本裡，這是不可能做到的。那些事件原本只存在記憶體中，一旦連線中斷，資料就會直接消失，畫面上也不會留下任何內容。
