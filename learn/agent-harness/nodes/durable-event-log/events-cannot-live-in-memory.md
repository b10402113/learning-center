# 事件只活在記憶體裡，斷線就沒了

你把 agent 迴圈跑起來了，事件也整理好，透過 WebSocket 推送給前端。

WebSocket 是一種讓伺服器和瀏覽器保持長連線、雙向傳送訊息的機制。看來事情就完成了。

直到某天連線斷掉，你才發現：斷線期間發生的事，前端從來沒收到，而且之後也拿不回來。

## 串流只有一次機會

只有 WebSocket 串流時，每個事件送出去就結束了，系統不會自動留下紀錄。這會在三個地方出問題。

第一種情況是前端根本沒有收到。

你雖然呼叫了 `emit`，但 client 端的介面可能出錯，或根本沒有消費這則訊息。事件就這樣消失在半路上，因為串流本身無法保證訊息一定送達。

第二種是連線中斷。

不論是伺服器重啟、client 重啟，還是網路斷線，事件都可能照常被送出。但這段時間另一端沒有人在接收，等連線恢復時，這些事件早就過去了。

第三種是使用者重新整理頁面。

前端畫面會重新載入，原本顯示的內容也會全部重來。先前發生過的事件，不會自己再次出現。

這三個遺失點有同一個原因：事件只活在記憶體裡，只存在於當下那一瞬間。沒有任何一份可以回頭查的紀錄。

## 錯過就是錯過

沒有儲存層時，答案很難聽，卻很誠實：如果出事了，你就是錯過了。事件不在了，就真的不在了。

「儲存層」指的是把事件寫到一個不會因為斷線就消失的地方，例如資料庫或檔案。

事件一旦存下來，就不只活在當下。之後你可以回頭查，也可以再送一次。

<!--image:2-->

這不是可有可無的額外功能。只要前端可能斷線、伺服器可能重啟，單靠串流，事件仍可能遺失。

你需要的是一個可重播（replay）的儲存層：先把事件存起來，之後才能從中斷的地方接著處理。即使中途出錯，只要事件還在，流程就有機會繼續往下走。

## 重連之後：先重播，再繼續

補上儲存層後，流程會變成這樣。

client 連回伺服器的那一刻，不論先前斷線的是伺服器還是 client，連線事件都會被觸發。

這時候別急著等新訊息，先把已經存下來的事件全部重播一次，讓前端一口氣追上進度。

<!-- derived -->
```js
onConnection((client) => {
  // 連線一建立，先把存下來的事件全部重播給這個 client
  for (const event of savedEvents) {
    client.send(event);
  }
});
```

重播完成後，才輪到 client 傳送新的訊息。

這則訊息會啟動 workflow：如果原本的 workflow 停在錯誤狀態，就從那裡接著跑；如果是使用者新交辦的任務，則會開始一個全新的 workflow。

回頭看，問題其實很單純。

你需要的不是一條比較不容易中斷的串流，而是一份事件紀錄。串流負責把訊息送到當下，儲存層則負責讓訊息在送出之後仍然找得回來。
