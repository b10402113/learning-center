# Messages 陣列就是 agent 的狀態

上一節把 while 迴圈的骨架立好了，但目前的 `run_agent` 其實還沒有真正執行工作：

它建立一個 workflow ID，發出「workflow 開始」的事件，然後就結束了。

接下來，要先組出這次要送給模型的訊息。這組訊息長什麼樣子，就代表 agent 目前知道哪些事情，也就是它的狀態。

## 先看 API 要的是什麼

大多數相容 OpenAI API 的 LLM 接收的都是一個 `messages` 陣列，裡面放著一則則 `ModelMessage`。

每則訊息都是一個物件，主要有兩個欄位：

- `role`：代表這是誰說的話
- `content`：代表說了什麼

常見的角色有四種：

- `system`：我們前面談過的 system prompt
- `user`：使用者送進來的訊息
- `assistant`：模型自己說的話
- `tool`：給 tool call 使用；如果你從頭實作 tool calling，就會遇到這個角色

角色應該還有其他幾種，只是現在的 SDK 通常已經幫你包好，平常不太需要自己處理。

## 組出這次的訊息

能進到 `run_agent`，就代表使用者剛送進來一則訊息。

因此，陣列的第一則放 system prompt，第二則放使用者這次的輸入：

<!-- derived -->
```ts
const messages: ModelMessage[] = [
  { role: "system", content: systemPrompt },
  { role: "user", content: input },
];
```

<!--image:2-->

到這裡，`messages` 就組好了。看起來很簡單。

真正的麻煩，出在模型回覆之後。

## 模型沒有記憶，你得替它記

模型把回應串流回來之後，你要把這個回應 append 回 `messages` 陣列。

如果不這麼做，下一輪請求時，模型就看不到自己剛才說了什麼。

聽起來很奇怪：模型明明才剛回覆過你，怎麼會不知道自己說了什麼？

但它就是不知道。這次互動不會留在伺服器的記憶體裡，所以每一輪都要把整段對話完整傳上去。

它不記得你，也沒有任何關於你的記憶。

<!--image:3-->

這就像網頁程式重新啟動後，原本放在記憶體裡的資料也跟著消失。

之所以這樣設計，是因為記憶體非常珍貴。記憶體要留給真正的推理，而不是用來保存某一段對話。

## 對話越長，代價越高

這就是為什麼對話越長，執行速度越慢，花費也越高。

你必須持續把新的內容加到陣列後面，token 越來越多，速度就越來越慢，成本也越來越高。

<!--image:4-->

所以，`messages` 陣列就是 agent 的狀態。

伺服器上沒有其他地方替你保存對話。你手上的這個陣列，就是目前唯一的真相。

至於對話越長、速度越慢也越貴的問題，後面會再處理。現在先記住一件事：

**每次模型回應之後，都要把它 append 回 `messages` 陣列。**

訊息送出去之後，模型會開始一個 token、一個 token 地回話。但 UI 一開始什麼都看不到——這是下一節要解決的問題。
