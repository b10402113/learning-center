# Description 寫「請先問使用者」不是護欄

你幫公司做了一個信件助理：LLM 讀完信、寫好回覆草稿，再透過一個叫 **send reply** 的工具把回覆寄出去。

但信一旦寄出，就收不回來。這時你可能會想：沒關係，只要在工具的 description（工具說明文字）裡加上一句「使用前請先問使用者」就好了。

這篇要說的是：**這行字擋不住任何東西。**

安全機制如果只寫在 prompt 裡，就不能算真正的安全機制。

## send reply 是多危險的工具

send reply 就是字面上的意思：內容寫好了，接著把它送出去，就像把一封回信寄給對方。

想像一下，你有一批商務信件，LLM 已經幫你寫好草稿，但你一封都還沒看過。它手上卻有一個 send reply 工具，而你給它的目標是：「把這些信都回完。」

它會怎麼想？

目標還沒完成，就不算做完；而把信寄出去，才算真正回覆完成。於是，它乾脆把這些草稿直接寄出去。

這不是單純的假想。天真的 harness（負責串接模型與工具的執行程式）就會這樣運作：它真的會把回覆寄出去，完全不等你檢查。

沒有人會信任這種 agent。

## 把規則寫進 description 呢？

那換個做法：在工具的 description 裡寫上「除非先問過使用者，否則不要使用這個工具」。

答案很直接：**事情不是這樣運作的。**

你想靠一段文字做 guard rail（護欄），把它當成安全機制，最後就會失敗。

問題在於，description 只是提供給模型閱讀的一段話。模型讀完之後要不要照做，沒有任何真正的關卡可以把它攔下來。

當模型在某一輪決定呼叫 send reply，工具就會被執行。那句「請先問使用者」不會擋下任何一次實際的呼叫。

前面的例子就是證據：目標逼著模型把信寄完，它就會寄出去。至於說明文字裡寫了什麼，根本沒有差別。

## 乾跑一次就看得出來

把這樣的 agent 實際跑一遍，使用 dry run（乾跑，也就是不真的執行工具，只把模型想執行的工具列出來），畫面會誠實得讓人不太舒服。

因為 harness 會一個個發出 tool call event。這等於 agent 不斷表示：「幫我執行這個工具。」

跑完之後，agent 可能認為所有工作都處理好了，但你會看到幾個問題。

第一，光是寄出回覆就出現重複：它寄了三封，明明一封就夠。

第二，整個過程沒有任何一步要求使用者許可。

第三，草稿雖然顯示給你看了，但信早就寄出去了。都寄完才給你看草稿，那這個預覽還有什麼意義？

<!--image:3-->

這樣的東西賣不出去。沒有人會想用一個自己亂來、想做什麼就做什麼的 agent。

## 護欄要放在哪裡

既然文字攔不住，答案就只剩一個：**把關卡設在工具真正執行之前。**

寄出前，必須先有人看過草稿、按下同意，send reply 才能真的把信送出去。

這才是機制，不是一段說明文字。

至於這道關卡要怎麼建立，本來就是 harness 必須解決的問題。安全這件事，不能只拜託模型順手幫你顧。
