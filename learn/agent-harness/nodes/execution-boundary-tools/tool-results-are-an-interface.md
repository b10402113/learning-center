# Tool result 也是給模型看的介面

設計 tool 時，多數人會把注意力放在參數上：要收哪些欄位、每個欄位是什麼型別，以及 schema 要怎麼寫才完整。

但工具執行完後，真正回到模型眼前的是回傳值。你的程式怎麼執行、中間發生了什麼事，模型都看不到；它只讀得到那段 result。

所以，回傳值也是一種介面，而且是專門給模型看的介面。

## 先問一個問題：你想要模型看到什麼？

素材裡的講者示範了一個很基本的搜尋工具。他特別說明，這只是示範，不是要教你打造生產環境等級的搜尋系統。

這個例子把問題講得很直接：回傳什麼，由你決定。你希望模型看到哪些資訊？對模型來說，什麼樣的內容才算合理？

這和型別是否正確無關。真正要問的是：模型讀完這段文字後，手上是否有足夠的資訊做決定。

你的程式怎麼執行、中間發生什麼事，模型都看不到；它只讀得到那一段 result。

## 有結果的時候：把內容和數量交回去

搜尋找到文章時，示範會回傳一個物件，裡面放著 `articles`，並另外說明找到幾筆結果。

文章內容可以讓模型繼續使用，結果數量則不用模型自己計算。

<!-- derived -->
```js
// 有找到：交回內容，順便說有幾筆
{ articles: [/* ... */], count: 2 }
```

## 查不到的時候：給訊息，不要給沉默

沒有搜尋結果時，如果只回傳一個空陣列，模型就只能自己猜。

示範中的做法，是在同一個物件裡放入一則訊息：`no exact match`，也就是沒有完全符合的結果。

模型至少知道兩件事：搜尋確實執行過了，只是沒有找到結果。

## 把下一步寫進 result

除了說明發生什麼事，也可以在回傳值裡加上一句 hint，例如：`use your best judgment`，意思是接下來由你自行判斷。

既然沒有找到符合的結果，下一步該怎麼做？讓模型自己想。

<!-- derived -->
```js
// 沒找到：明講發生什麼事，再給下一步的提示
{ articles: [], message: "no exact match", hint: "use your best judgment" }
```

你也可以給更具體的指示，例如告訴使用者知識庫裡的條目不夠，應該補上內容。

如果這是一個內部工具，這樣的下一步就很合理。回傳值裡可以寫什麼，彈性其實比想像中大。

## 有時候，回傳值只要證明「事情做完了」

另一個例子是起草回覆的工具。

工具執行完成後，回傳 `ok: true`，表示草稿已經建立；接著再附上一個 draft ID，作為這份草稿的識別碼。

<!--image:3-->

<!-- derived -->
```js
{ ok: true, draftId: "draft_..." }
```

在示範裡，這個 ID 是隨意產生的。重點不在 ID 從哪裡來，而在回傳格式：告訴 agent「我們已經做好一份草稿，這是它的識別碼」。

至於參數裡的 `message`，示範根本沒有用到，就不必放進結果裡。回傳值只要保留模型需要的資訊即可。

## 設計回傳值時，檢查三件事

下次撰寫 tool 的執行邏輯時，可以對著回傳值問自己：

- 模型知道這次是成功還是失敗嗎？
- 如果失敗，模型知道發生了什麼事嗎？
- 模型知道下一步可以做什麼嗎？

如果三個問題都有答案，這個介面才算設計完成。
