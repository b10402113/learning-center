Summarizer：用一次 LLM 呼叫把舊 turns 壓成摘要

Step 3/5 · 摘要的摘要，是怎麼累積出來的

學習目標

用 generateText 寫出 summarize：把舊 turns 攤平成文字、折入既有摘要（summaries of summaries）、保留 ID／類別／金額／已送事項，並用 maxOutputTokens 設上限。

摘要不是演算法，就是一次 LLM 呼叫

聽到「把對話壓縮成摘要」，很容易想像一套複雜的抽取規則：挑關鍵字、算權重、砍句子。這裡完全不是那樣。

summarize 的本質就是一次普通的 LLM 呼叫，只是餵給它的輸入是「快要被丟掉的舊內容 + 既有摘要」，並用一個專門的 system prompt 要求它吐出精簡的版本。你之後想加強它——換更便宜的模型、加更嚴的格式要求、甚至做成串流——都只是在調這一次呼叫。

用 generateText，不是 streamText

import { generateText } from "ai";

export async function summarize(
  oldTurns: ModelMessage[],
  priorSummary: string,
): Promise<string> {
  const history = oldTurns
    .map((m) => `${m.role}: ${typeof m.content === "string" ? m.content : JSON.stringify(m.content)}`)
    .join("\n")
    .slice(0, 8000);

  const { text } = await generateText({
    model,
    system: SUMMARIZER_PROMPT,
    prompt: [
      priorSummary ? `So far:\n${priorSummary}\n` : "",
      `Work log to compress:\n${history}`,
      "Write the updated running summary.",
    ].join("\n"),
  });

  return text;
}

第一個要停下來看的選擇是 generateText 而非 streamText。為什麼？因為摘要沒有要即時顯示給使用者看，而且後續流程必須等它完成才能繼續。串流是為了讓使用者感覺快，這裡沒有觀眾；硬要串流只是多繞一圈，還得自己把碎片拼回來。

判斷準則很簡單：內容要邊產生邊給人看 → 用 streamText；內容是內部流程的中間產物、完成後才用 → 用 generateText。

摘要器有自己的 system prompt

注意 system: SUMMARIZER_PROMPT：摘要器用的是一份跟任務 agent 完全不同的指示。任務 agent 的 prompt 在講「你是客服、要怎麼處理退款」；摘要器的 prompt 在講「你是壓縮器、只准留下事實、要短」。兩者混用會出問題——你不想讓摘要器以為自己也要去處理退款。

這份 prompt 的內容大致是要求它產出精簡的 running summary，並且明確保留具體事實：ID、類別、金額，以及「哪些事情已經送出去了」。這些是後面步驟最容易被壓掉、又最不能壓掉的東西——摘要一旦漏掉「已送出的項目」，agent 就可能重複動作。

摘要的摘要：把舊摘要折回來

真正的關鍵在參數 priorSummary。每次壓縮不是從零開始寫一份新摘要，而是把上一次的摘要一起餵進去，讓模型產出「更新後的版本」。

這就是 summaries of summaries（摘要的摘要）：第一次壓縮把 20 個 turns 壓成 5 行；第二次再把「那 5 行 + 新的舊 turns」壓成 6 行。歷史上所有被壓掉的內容，都還以濃縮的形式留在這條鏈上，不會因為被移出 turns 就消失。

時間點輸入輸出（State）
第一次壓縮舊 turns 1–8摘要 A
第二次壓縮摘要 A + 舊 turns 9–15摘要 B（A 的更新版）
第三次壓縮摘要 B + 舊 turns 16–22摘要 C（B 的更新版）

所以「State 會累積」不是說它一直變長，而是說它帶著過去的資訊一起往前走——每一步都吸收新內容、吐出更精簡的版本。

結尾還是要留一則 user

還記得 messages 陣列的規矩嗎？在這裡同樣適用，只是換成 generateText 的 prompt：最後一段必須是給模型的指令（「把更新後的摘要寫出來」），否則模型只是在讀一份沒有問題的報告，不知道自己該產出什麼。上面程式碼把那段指令放在陣列最後，就是為了這個。

用 maxOutputTokens 封住摘要的長度

摘要的長度也該有上限。做法不是寫在 prompt 裡拜託模型「請短一點」——那只是建議，模型不一定聽。真正可靠的是 inference 參數 maxOutputTokens：把它設在 summarize 呼叫上，模型產出的摘要就被硬性封頂。

const { text } = await generateText({
  model,
  system: SUMMARIZER_PROMPT,
  prompt,
  maxOutputTokens: 300, // 硬性上限，不靠 prompt 求情
});

這也回答了一個常見疑惑：為什麼我壓縮完之後，context 還是很肥？因為摘要本身也是一段會被塞回 system 的文字。摘要不封頂，等於壓縮效果被封頂。用參數封住，才是真有保證。

帶回自己的 runtime

這一步最有遷移價值的兩個決策：摘要是一次獨立的 LLM 呼叫（有自己的 prompt），以及摘要可累積（把舊摘要折回來）。前者讓你可以獨立調整成本與品質，後者讓壓縮不會造成資訊斷層。兩者都跟 TS 或 Java 無關。
