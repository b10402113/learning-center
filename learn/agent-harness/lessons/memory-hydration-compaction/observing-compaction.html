觀察壓縮：清空事件日誌，在 inspector 看 memory_compacted

Step 5/5 · 把 durable 日誌歸零，親眼看壓縮發生

學習目標

用 clearEventLog 與 POST /api/clear（含 CORS）清空 durable 日誌，在 inspector 上看到 memory_compacted 事件的 summarized turns 與 token 數，並解釋為何壓縮總發生在門檻略下方。

為什麼要先清空日誌

前面的壓縮都是寫進 durable event log 的，所以每次重跑 demo，日誌都還留著上一次的內容。想乾淨地觀察「這一輪到底發生了幾次壓縮」，得先把歷史歸零。

做法是在 db.ts 加一支 clearEventLog，直接把 event log 表 truncate 掉：

export async function clearEventLog() {
  await db.execute(sql`TRUNCATE TABLE event_log`);
}

這是純資料庫層的操作，export 出去讓 server 的入口檔跟 ensureSchema 一起 import。它的用途就只有一個：把 durable 狀態重設，讓你能從乾淨的起點重跑與觀察。

CORS：瀏覽器跨來源呼叫的前置檢查

清空動作要從瀏覽器介面（不同來源）打到 server，這就踩到 CORS（跨來源資源共享）。瀏覽器在真正送出 POST 之前，會先送一個 preflight（預檢）的 OPTIONS 請求；伺服器必須在回應裡明確允許，真正的請求才過關。

app.use((req, res, next) => {
  res.setHeader("Access-Control-Allow-Origin", "*");
  if (req.method === "OPTIONS") return res.sendStatus(204);
  next();
});

CORS 管的是「哪些非同一來源的客戶端可以存取這個伺服器」。沒有這道中介層，瀏覽器會在預檢階段就把請求擋掉，你連 server 的錯誤訊息都看不到——這是最常見的「明明程式沒錯卻打不通」之一。

POST /api/clear：把操作變成端點

有了清空函式、也給了瀏覽器許可，最後只要把它掛成一個路由：

app.post("/api/clear", async (_req, res) => {
  await clearEventLog();
  res.json({ ok: true });
});

介面上原本就有的 Clear 按鈕早就指向這個端點，所以前端一行都不用改。這也示範了一個模式：harness 的維運動作，用 HTTP 端點暴露給 inspector UI——清空日誌只是第一個，之後的審批之類的操作也是同一條路。

跑一次，看 inspector

重啟後不會有啟動錯誤，按下 Clear，貼上範例任務開始跑。event 串流上你會看到 agent 一次處理一個項目地工作，接著——memory_compacted 事件出現了。

每個事件帶著幾項關鍵資訊：

欄位範例你可以從它看出什麼
summarizedTurns3這次壓掉了幾個 turn
tokens619 / 674壓縮前後的 token 數，證明真的降了
summary一段精簡文字摘要品質：ID、金額、已送事項有沒有留住

一場跑完不只會出現一次。因為 agent 一邊工作、token 一邊長，每跨過門檻就再壓一次——所以你會看到壓縮反覆發生，這正是它作為持續機制（而不是一次性清理）的證據。實務上你有時只會瞥見它閃過一下，得回頭到 event log 裡才找得到完整內容。

為什麼壓縮總發生在門檻「略下方」

看事件時你可能會注意到一個怪現象：每次壓縮的 token 數都貼在限制下方不遠處，而不是大幅超標才觸發。原因在於第四步那個順序——檢查在每一輪迴圈的開頭、呼叫模型之前：

  1. 此刻的估算超過上限（例如 674 > 500）。
  2. 於是開始 shift 最舊的 turn，一路移到降回 keepContextTokens（200）以下為止。
  3. 然後才呼叫模型，所以模型看到的數字是被壓低後的結果。

換句話說，壓縮的觸發點由「上限」決定，但壓完的落點由「保留門檻」決定。兩個數字之間的那段差距，就是每次壓縮要清掉的量。課程用的 maxContextTokens 500、keepContextTokens 200 是刻意調得很激進的展示值，不是生產建議——真實系統的門檻會大得多，機制不變。

別忘了封住摘要的輸出

還有一個會影響觀察結果的旋鈕：摘要的輸出長度。如果摘要本身沒有上限，它會慢慢吃掉你省下來的空間。用 summarize 呼叫上的 maxOutputTokens 封頂，才是可靠的做法——比在 prompt 裡拜託模型「寫短一點」實在得多。

收尾：一條完整的記憶管線

走到這裡，你手上已經有完整的迴路：History 無限成長 → 每輪開頭量預算 → 超過就整 turn 滑出 → 摘要成 State（durable step）→ buildContext 把 State 注入這一輪 → 發出 memory_compacted → 繼續跑。

把它對照回自己的 runtime（OryxOS / Java），要換掉的只有 API 名稱：預算驅動、turn 對齊、摘要可累積、狀態可重放——這四個決策跟語言無關，也是最值得帶走的部分。
