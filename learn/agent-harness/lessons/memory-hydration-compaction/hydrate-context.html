Hydrator：估算 token 並組出這一輪的 context

Step 2/5 · 模型每一輪到底看到什麼

學習目標

實作 estimateTokens 與 buildContext：量整段 context 的大小，再把 system prompt（可夾帶 running summary）、當前任務、保留的 turns 組成模型實際看到的 messages。

第一步：量大小——estimateTokens

要管預算，得先有尺。壓縮的觸發條件是「這一輪的輸入太大了」，所以需要一個函式回答一個問題：我手上這整包 messages 大概有多少 token？

注意「整包」這兩個字。不是量最後一句、也不是量每則分開加總，而是把整個 messages 陣列攤平後一起量——因為模型是一次吃掉整段輸入的，預算也是以那整段為單位。

export function estimateTokens(messages: ModelMessage[]): number {
  const text = messages
    .map((m) => (typeof m.content === "string" ? m.content : JSON.stringify(m.content)))
    .join(" ");
  return Math.ceil(text.length / 4);
}

這個估算器是假的，但先夠用

上面除的「4」不是什麼神秘常數：英文裡平均大約四個字元換一個 token，所以 text.length / 4 是個便宜、夠接近的近似。

在生產環境這是不合格的。真正該做的是用跟模型相同的 tokenizer（分詞器／編碼器）去數——例如 TikToken 這一類標準工具。原因很簡單：如果你的尺跟模型實際的編碼方式不一致，你以為自己在 499，模型可能已經在 640 了，壓縮永遠慢半拍。課程用假的估算只是為了省下工具鏈的摩擦，機制完全一樣。

還有一個常被忽略的非對稱：輸入與輸出是分開的預算。通常輸出的預算比較小、單價比較高；輸入則是量大但便宜。談 token budget（token 預算）時，要講清楚是哪一邊。

第二步：組裝——buildContext

有了尺，接下來是這一步真正的核心：buildContext。它就是「這一輪模型看到什麼」的唯一出口，每次使用者送新訊息都會重新跑一次。它的輸出是一個全新的 messages 陣列，順序固定為三層：

順序內容作用
1. systemagent 的 system prompt，可選擇性夾帶先前的 running summary定調身份與規則；摘要讓模型知道「之前發生過什麼」
2. user這次要處理的任務告訴模型現在要做什麼
3. 保留的 turns還沒被壓縮的近期往返提供最近的細節與脈絡
 
export function buildContext(
  systemPrompt: string,
  task: string,
  summary: string,
  turns: ModelMessage[],
): ModelMessage[] {
  const system = summary
    ? `${systemPrompt}\n\n## Previous work (summarized)\n${summary}`
    : systemPrompt;

  return [
    { role: "system", content: system },
    { role: "user", content: task },
    ...turns,
  ];
}

摘要要併進 system，不要新增第二個 system

上面那段程式碼裡有個看似小、其實很重要的選擇：摘要是接在原本的 system prompt 後面，而不是再 push 一則 role: "system" 的訊息。

為什麼？因為 messages 陣列裡「只能有一則 system 訊息」是實務上的硬規則。有些 API 看到多個 system role 會直接報錯，有些則會警告。安全的做法是：把摘要文字附加到既有 system 內容的尾端，維持開頭只有一則 system。

// 好：摘要附加進同一個 system
`${systemPrompt}\n\n## Previous work (summarized)\n${summary}`

// 壞：變成兩則 system，可能報錯或警告
[{ role: "system", content: systemPrompt },
 { role: "system", content: summary }]

最後一則必須是 user 或 tool

messages 陣列的結尾也有規矩：它必須結束在一則 user（或 tool）訊息上，否則模型會「沒有事情可做」——它是在回應最後一則訊息，如果最後一則是 assistant 自己講的話，它沒有新的輸入可以接。

這也解釋了為什麼 buildContext 的順序是 system → user → turns：新的任務訊息先出現，模型才會有明確的當下目標；turns 是背景，不是要它回應的對象。

為什麼這一步是壓縮的檢查點

buildContext 每輪都被呼叫，而且它手上正好握有「即將送出的完整內容」。所以它自然就是回答「這次需不需要先壓縮」的地方——先量、再決定要不要壓、最後才把 context 交給模型。這個順序會在第四步接進 runtime 時變成核心約束。

帶回自己的 runtime

把這兩支函式翻成 Java 也毫無障礙：一個算大小、一個照固定順序組訊息。真正要帶走的是兩個設計直覺——用尺管預算、把每一輪的輸入當成即時重算的產物，而不是一份只增不減的對話檔。
