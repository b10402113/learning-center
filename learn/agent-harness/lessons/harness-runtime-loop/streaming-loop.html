streamText 與串流迴圈

Step 3/5 · 不 await 的串流，與逐 chunk 迭代

學習目標

能解釋 streamText 為何不 await、for-await 如何逐段迭代 fullStream，以及為什麼串流是不可讓步的體驗底線。

呼叫之後，你拿到一串流

迴圈裡最關鍵的一行，是這句：

const result = streamText({ model, messages, tools });

注意它沒有被 await。原因很直接：streamText 回傳的不是最終答案，而是一條「流」（stream）——一個可以訂閱的物件。模型開始產生 token，這些 token 一路流進來，你一路接。若你改用 generateText，那才是「等我全部生完、一次給你結果」，那種才能 await。

換句話說：streamText 是「邊生邊來」，generateText 是「生完再來」。我們要前者，因為後面所有 UI 體驗都建立在「token 一個一個出現」這件事上。

逐段迭代 fullStream

拿到流之後，用一個 async 迴圈把它一段一段吞掉：

for await (const part of result.fullStream) {
  // 每抵達一個 chunk，就在這裡處理它
}

這裡的 part 是流裡的一小塊（chunk）。別小看這個「一塊」——provider 送來的不是均質的純文字，而是好幾種不同的 chunk：可能是純 token，可能是一個工具呼叫，可能是工具結果，也可能是錯誤。迴圈每轉一次，你就得判斷「這一塊是哪一種」，再決定怎麼處理。判斷的細節是下一課的主角。

為什麼串流不可讓步

有人會問：把串流全砍掉、等最終結果再一次丟上畫面，不是更省事嗎？技術上可行，但你會得到什麼？

一個使用者等半天、畫面一片空白、最後「啪」地蹦出整段答案的產品。2026 年，沒有人會為這種體驗付錢，也沒有人會繼續用。串流之所以是全部這些 chunk 處理程式碼存在的理由，正是因為它把「等待」變成「正在發生」。若你不串流，這整段 chunk 處理的程式碼可以直接刪光——而刪掉的同時，你也把產品刪沒了。

所以把這條當成底線記住：不串流，就是在流失使用者。下一課，我們接手這些 chunk，把它們翻譯成客戶端看得懂的事件。
