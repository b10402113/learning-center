Harness 裡面有什麼：記憶、工具、持久化

Step 2/5 · 拆開那層基礎設施，看它到底要解決哪些問題

學習目標

能列出 harness 必須解決的三類問題——記憶（短期／長期／暫存／事實）、工具（自有實作或 MCP）、長程任務（持久化執行）——並各舉一個實例。

把 harness 的肚子打開

上一節我們說 harness 是「讓 LLM 在真實世界可靠運作」的那層。但「可靠運作」這四個字太抽象。把一個會壞給你看的 agent 攤開，你會發現它總是卡在三類問題上。這三類問題，就是 harness 的三大設計面。

第一類：記憶（memory）

模型本身沒有記憶。每一輪呼叫都是全新開始，除非你把歷史親手塞回 prompt 裡。一個能工作的 agent 需要四種記憶：

記憶類型存什麼例子
短期（short-term）這次對話的上下文剛剛那幾輪聊了什麼
長期（long-term）跨會話還得記住的事用戶的名字、偏好、歷史事實
暫存（scratchpad）工作中間的草稿正在算的算式、正在列的計劃
事實（facts）已被確認的既定資訊「這個客戶的保固期到六月」

這四種記憶如果不靠 harness 管理，全都要靠自己手寫 prompt 拼接，而且「記得住」和「記得住但不淹死脈絡」是兩回事——後者就是後面記憶章節要解決的 token 預算 問題。

第二類：工具（tools）

純靠生成的文字，模型做不了「查資料庫」「寄信」「退款」這種有副作用的事。它需要工具，而工具不會自己冒出來——得有人去引入並管理它們。這裡有兩個層次：

  • 工具呼叫的實作——自己定義工具（給名字、描述、參數 schema，讓模型知道何時該呼叫哪個），還是走 MCP（Model Context Protocol） 這類標準協定去接現成工具。
  • tool server 的管理——這些工具跑在哪、怎麼啟動、怎麼對外暴露，都得有人管。

工具是 agent 的手腳，handling 工具呼叫的「契約」會在 Tier 2 的節點專門講。這裡只要記住：工具是 harness 引入並代管的，不是模型自帶的。

第三類：長程任務（long-running）

假設你要 agent 做一件 十分鐘的深度研究：它要查十幾個來源、讀完、彙整。如果這個 agent 只是個裸迴圈，你關掉 app 的那一刻，它的一切進度就蒸發了。也不可能「跑完再通知你」——因為根本沒有東西在替你撐住這段時間。

這就需要 durable execution（持久化執行）：讓任務的每個檢查點都落到可靠儲存裡，這樣即使用戶關窗、server 重啟，它也能從斷點繼續，最後還能把結果通知用戶。這是第三個設計面，也是本課程 Tier 3 的主題。

一張圖記住三大設計面

harness
 ├─ 記憶   短期 / 長期 / 暫存 / 事實
 ├─ 工具   自有實作 or MCP + tool server 管理
 └─ 長程   持久化執行，撐過關窗與重啟

看到任何一個 agent 產品，你都可以先用這三格去套：「它的記憶怎麼處理？工具怎麼來？長任務會不會死？」能問出這三題，你就已經在 harness 的層次上思考，而不是被一句「我們有 agent」唬住。
