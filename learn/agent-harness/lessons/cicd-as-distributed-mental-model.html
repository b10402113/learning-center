CI/CD：一套早已熟悉的分散式系統

Step 2/4 · 用你每天都在用的 CI/CD，看懂 durable execution 的機制

學習目標

能用 CI/CD（Jenkins、GitHub Actions）當心智模型，把 durable execution 的 retry、replay、cache、非同步回報、斷線恢復對應到具體的分散式系統行為。

你其實早就在用分散式系統

上一節說 durable execution 把你推進了分散式運算，聽起來很遙遠。但其實你每天 push 一次 code，就是在操作一個分散式系統——它叫 CI/CD（持續整合與持續交付）。

你把 code push 上去，GitHub 上的 repo checks 開始跑。不管是 Jenkins 還是 GitHub Actions，那都是「跑在另一台機器上的另一個 process」。它跟你的本機、跟 GitHub 是三個不同的系統，靠著網路互相溝通，回報每個 check 的狀態讓你看。

CI/CD 有哪些 durable execution 的行為

把一個典型的 CI/CD pipeline（管線）拆開，你會看到它天生就有上一節講的那些特性：

CI/CD 行為對應的 durable execution 概念
一個 pipeline 有多個 stage一段執行被切成多個步驟（step）
某個 stage 失敗，可以單獨 retry 它retry——不重跑前面已完成的步驟
某些 stage 的結果被 cache 住replay——用上一次的結果，不用真的重算
status 非同步回報給 GitHub執行獨立於觀察者——你不看它也在更新
CI/CD 掛了能恢復、從斷點接續resilience——從 checkpoint 接續，不從頭來

挑最關鍵的一句：如果某個 stage 失敗，你只想 retry 那一個 stage，而不是回去把前面所有 stage 全部重跑一遍。這正是 durable execution 的核心思想——失敗時「跳過已經做過的，只補做沒做好的」。後面第四步選 DBOS 時，會看到一模一樣的機制：用 workflow ID 去查「這步我做過沒、做過就跳過」。

把 agent 想成一套 CI/CD

現在把視角切回 agent。上一節的結論是「執行要獨立於任何 consumer、任何 client」。CI/CD 給了我們一套具體的通路去達成這件事：

Agent 的執行必須像 CI/CD 一樣——分散、獨立、能處理 process 結束或錯誤。

也就是說，一個好的 agent 系統，應該具備三件事：

  • 執行獨立：client 在不在、看沒看，執行照跑，狀態照更新。
  • 能處理死亡：process 結束、連線中斷、出錯，都不會讓整件事歸零。
  • 能接續：像 CI/CD 斷線後恢復、從斷點接續一樣，而不是從頭來。

關鍵一句話

記住這條等價關係，後面每一層 durability 都用得上：

CI/CD 就是分散式運算；agent 的執行要「長得跟 CI/CD 一樣」。

這個類比之所以有力，是因為 CI/CD 的 retry／replay／cache／非同步回報／斷線恢復，你每天都親眼見過、親手用過。往後每當 durable execution 某個機制看起來抽象，就問自己：「在 GitHub Actions 裡，這對應到什麼？」答案就在手邊。
