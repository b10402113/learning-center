訊息陣列：模型的對話契約

Step 1/5 · 模型每次呼叫都得收下的一整段對話

學習目標

能說出 ModelMessage 的結構與四種 role，並解釋為什麼每一輪都得把整段對話重新送給模型。

開場：模型根本記不住你

我們要寫的是 harness 自己的 agent loop，而這顆 loop 的第一個原料，是那串要餵給模型的訊息。先建立一個關鍵事實：模型不做任何伺服器端的記憶。剛剛你跟它說了什麼、它回了什麼，模型一概不保留。下一次呼叫，你若沒把它自己說過的話再遞回去，它就像第一次見到你。

這跟直覺相反——「它剛剛才回我，怎麼會不知道？」答案是用記憶換效率：模型把所有記憶體都拿去跑推論（inference），不拿來記對話。所以「記得對話」這份工作，落在呼叫模型的那個人身上——也就是 harness，也就是你。

訊息陣列的形狀

幾乎所有 OpenAI API 相容的模型，都收同一種東西：一個 ModelMessage（模型訊息）陣列。陣列裡每一個元素都是一個物件，只有兩個欄位：role（角色）與 content（內容）。

最核心的骨架長這樣——開頭放 system prompt，接著放這一輪 user 送進來的輸入：

const messages: ModelMessage[] = [
  { role: "system", content: systemPrompt },
  { role: "user",   content: input },
];

陣列的順序就是時間順序：越早的對話越靠前。每一輪 model 讀到的都是這整串歷史，不是只有最新一句。

四種角色

對話會用到四種 role，各有各的意義：

role它是誰放什麼
system你對模型的全局設定system prompt（它該扮演誰、守什麼規則）
user使用者使用者送進來的那句話
assistant模型自己的回覆它上一輪講過的話
tool工具的執行結果某次工具呼叫的回傳值

這四種角色裡，system 幾乎總是在陣列的最前面——那層全局設定要一路壓在整串對話頭上。而 assistant 與 tool 是迴圈「轉起來」之後才陸續塞進去的：模型回一句，就多一條 assistant；跑一個工具，就多一條 tool。

多數 SDK 把這藏起來了

今天多數 SDK 都把訊息陣列抽象掉，你不必親手組它，甚至根本看不到它。這門課故意把這層掀開、自己一條一條組，原因是：等一下你自己寫的那顆 loop，每一步都要親手決定「現在該把誰句話推進陣列」。等講到記憶與壓縮時，你會直接在這串陣列上動手腳，那時候就非得懂它的形狀不可。

記住一句話：模型沒有記憶，對話契約就是你每一輪都完整複述一次歷史。下一課要做的，就是在這串陣列外面，包一顆會重複轉的迴圈。
