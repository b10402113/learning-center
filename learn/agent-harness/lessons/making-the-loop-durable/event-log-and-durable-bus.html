把事件寫進 Postgres：event_log 與 durable bus

Step 1/5 · 用 Drizzle 建出 event_log 表，把 bus 改成「先寫後廣播」，並能依 seq 重播

學習目標

用 Drizzle 建出 event_log 表（seq 主鍵 + jsonb data），把 bus 改成「先寫資料庫、再廣播給訂閱者」，並用 history() 依 seq 重播整條事件時間線。

先看故障：記憶體裡的 bus 一斷電就失憶

上一階段做出來的 runtime，事件是透過一個 in-memory event bus（記憶體中的事件匯流排） 轉發出去的：model 吐一個字，就呼叫 emit，把事件丟給一個存在於 process 記憶體裡的 listener。只要 server 還活著，這一切都很好——但「server 還活著」正是前面一整節課想要推翻的前提。

server 一掛、一重啟，那個 listener 陣列歸零，所有還沒被瀏覽器接住的事件全部消失。你重開 inspector，看到的是一塊空白，因為歷史根本沒被任何地方保存。

要讓執行活得比 server 久，第一個動作是：把事件的「真相來源」從記憶體搬到資料庫。這一課做三件事：接上 Postgres、定義存事件的表、把 bus 改成先落盤再廣播。

三樣新依賴

課程新增三個套件：@dbos-inc/dbos-sdk（持久化執行引擎）、drizzle-orm（型別安全的 SQL 查詢層）、postgres（Postgres.js 這個 Node 驅動）。這一步還不必懂 DBOS 怎麼用，只要知道它被裝進來備用；真正動手的是 Drizzle 和 postgres 驅動。

先寫 harness/db.ts，它是往後每一次持久化呼叫都倚賴的最小資料庫客戶端：

import { drizzle } from "drizzle-orm/postgres-js";
import postgres from "postgres";

const connectionString = process.env.DATABASE_URL;
if (!connectionString) {
  throw new Error("DATABASE_URL is not set");
}

const client = postgres(connectionString, { max: 5 });
export const db = drizzle(client);

幾個重點：process.env.DATABASE_URL 是 Node 讀環境變數的標準方式；連接字串不存在就 立刻 throw，不要等到第一個查詢才爆出更難懂的錯；max: 5 只是給個小連線池，課程情境沒真正併發到需要大池子。export 出來的 db 基本上就是一個查資料庫的 SDK。

定義 event_log：一張只靠兩欄的表

事件流的持久化落點叫 event_log。它的結構簡單到令人意外——只有兩欄：

import { pgTable, bigserial, jsonb } from "drizzle-orm/pg-core";

export const eventLog = pgTable("event_log", {
  seq: bigserial("seq", { mode: "number" }).primaryKey(),
  data: jsonb("data").$type<AgentEvent>().notNull(),
});
欄位型別它為什麼存在
seqbigserial全域遞增的順序，是「依序重播（replay）」與「去重（de-duplication）」的根據
datajsonb存一整個事件 payload；泛型 AgentEvent 只是編輯器體驗，資料庫看到的就是普通 JSON

注意 seq 的兩個用途：它讓事件有個不可偽造的順序（寫入先後），所以重播時能照原順序倒出來；同時同一件事若被寫兩次，seq 也能被抓出來。data 用 jsonb 而不是拆成一大堆強型別欄位，是因為事件種類繁多、每種長得不一樣，交給 JSON 最省事。這套「seq + jsonb」的模式，任何 DB 後端的 app 都長這樣，一點都不 agent 專屬。

另外加一個輕量的 ensureSchema，開機時用 Drizzle 的 tagged SQL 跑 create table if not exists event_log ...。它算是一種極簡的 runtime migration——正式系統會用真正的 migration 工具，這裡只是為了課程開跑時不被打斷。

把 bus 改造成 durable bus

接著把手上的記憶體 bus 搬進 harness、剝掉有狀態的 class，只留三個函式：subscribe、emit、history。關鍵轉變在 emit——它不再直接廣播，而是先寫進資料庫，再通知訂閱者：

export function subscribe(fn: Listener) {
  listeners.push(fn);
  return () => {
    listeners.splice(listeners.indexOf(fn), 1);
  };
}

export async function emit(input: EventInput) {
  const event: AgentEvent = {
    ...input,
    id: randomUUID(),
    ts: Date.now(),
  };
  await db.insert(eventLog).values({ data: event });
  listeners.forEach((fn) => fn(event));
}

export async function history(): Promise<AgentEvent[]> {
  const rows = await db.select().from(eventLog).orderBy(eventLog.seq);
  return rows.map((r) => r.data);
}

要不要把廣播放在寫入之後，是整套持久化的合約核心。先寫、後廣播代表：就算廣播到一半 server crash，那條事件也已經躺在資料庫裡，重啟後靠 history() 就能把它救回來。倒過來（先廣播、後寫）的話，crash 在兩者之間就會「通知出去了、但沒存下來」。

subscribe 回傳一個 cleanup 函式，把這個 listener 從陣列移除——這跟 React 的 useEffect cleanup 是同一個道理：避免 listener 越疊越多造成記憶體洩漏。history() 則依 seq 選出所有列、映射回 data payload，供離線或重連的 client 重播整條時間線。

這一步之後，你擁有什麼

你現在有一張會永久保存事件的表、一個寫入即真相的 bus，以及一個能把過去倒出來重播的 history()。事件不再隨 process 生死而存亡。但這只解決了「事件」的持久化，還沒解決「工作過程」的持久化——model 那通昂貴的呼叫、工具那些不可逆的動作，仍然會重跑。下一步，我們要決定哪些東西該被包成 durable step。
