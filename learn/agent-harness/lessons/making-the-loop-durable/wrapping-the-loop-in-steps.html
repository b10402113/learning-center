把迴圈包成 DBOS workflow

Step 4/5 · 用 DBOS.runStep 包住各副作用，判別哪些能留在 step 外，並 registerWorkflow 啟動持久化

學習目標

用 DBOS.runStep 把 model turn、tool step、多種 emit 與失敗 emit 包成 step，用「是否非確定 / 昂貴」判別哪些能留在 step 外，再用 registerWorkflow 啟動持久化語意。

整個機制只有一個動詞：wrap

前面準備了那麼多，現在來到整堂課的收網時刻。DBOS 的用法驚人地簡單——你要做的就只有一件事：把既有的程式碼包進 DBOS.runStep。

import { DBOS } from "@dbos-inc/dbos-sdk";

await DBOS.runStep(async () => {
  // 既有的程式碼照寫，一行都不用改
  return emit({ type: "modelDone", workflowId });
}, { name: "model-done" });

DBOS.runStep(callback, { name }) 會把 callback 的輸入與輸出持久化，這樣它就可以被 retry、可以 suspend、在 crash 之後不會重新執行。原來的邏輯原封不動——正因為不用改邏輯、只加一層包裝，DBOS 是作者用過最簡單的 durable execution 引擎。

什麼該留、什麼該包：判別標準是「非確定」

先定一條規則，防止你不分青紅皂白把所有東西都包進去。純淨、無副作用、每次跑結果都完全一樣的初始化程式碼，可以留在 step 外面——像是把 agents 清單、system prompt 組出來這種事。它每次執行都長一個樣，包進 step 只會徒增簿記。

判斷標準不是「大不大」，而是「是否非確定（nondeterministic）或昂貴」。凡是依賴網路、時間、亂數、外部狀態，或者會花大錢（呼叫 LLM）、會造成外部副作用（發事件、執行工具）的，都該包。記住這把尺，它比死記「哪幾行要包」有用得多。

三個必須包進 step 的東西

把迴圈掃一遍，有三樣東西會被包進 step：

1. model turn —— 別讓模型被重複計費

const turn = await DBOS.runStep(
  async () => modelTurn(workflowId, messages),
  { name: `model-turn-${stepCount}` }
);

如果讓 streamText 留在 step 外，workflow 一重啟它就會重新執行——換句話說，每一輪 resume 都要多燒一次 LLM 的錢和 token。包成 step 後，重啟會接著上次的結果走，而不是重新呼叫。

一個常見的混淆要澄清：await 一個 step 不等於 await 那條串流。step 內部仍然在 await 自己的 stream，所以瀏覽器照樣能看到字一個一個吐出來；外面這個 await 只在等整個 step 完成。持久化沒有犧牲串流體驗。

2. emit —— 別讓重播重複寫列

「模型完成」和「工作完成」這兩個會寫進資料庫的 emit，也都包進 step：

await DBOS.runStep(() => emit({ type: "modelDone", workflowId }), { name: "model-done" });
await DBOS.runStep(() => emit({ type: "completed", workflowId }), { name: "completed" });

emit 本身是非冪等的——它每跑一次就往 event_log 多寫一列。留著不包，retry 時就會冒出重複事件、UI 出現幽靈訊息。包成 step 後，這些副作用就變成冪等，不可能同一件事發兩次。

3. tool call —— 自己逐個執行、自己組結果

因為前面已經透過刪掉 execute 放棄了 SDK 的自動執行，現在迴圈要自己迭代 turn.toolCalls，把每一個工具呼叫跑進 durable step，然後把結果組回 messages：

for (const call of turn.toolCalls) {
  const output = await DBOS.runStep(
    () => toolStep(workflowId, call),
    { name: `tool-${call.toolCallId}` }
  );

  messages.push({
    role: "tool",
    content: [{
      type: "tool-result",
      toolCallId: call.toolCallId,
      toolName: call.toolName,
      output: { type: "json", value: output },
    }],
  });
}

注意回填給模型的 message 形狀有嚴格要求：role 要是 tool、content 的 type 要是 tool-result、要帶 toolCallId 與 toolName、產出要用 { type: "json", value: output } 包一層。這些手動工作之所以出現，純粹是因為我們把執行權從 SDK 手上拿了回來——自主權的代價就是要把細節自己填對。

連失敗也要包起來

最容易漏的一支是失敗路徑。迴圈底部的 workflow-failed emit 也要有自己的 step：

await DBOS.runStep(() => emit({ type: "workflowFailed", workflowId }), { name: "failed" });

失敗訊號同樣不能發兩次——重試時如果它裸奔在 workflow 裡，就可能重複記錄失敗。給它一個 step，失敗的簿記就只會發生一次。

最後一把鑰匙：registerWorkflow

包完一堆 step，它們其實還只是一堆普通函式。除非把包住它們的外層函式註冊成 workflow，否則這些 step 一點意義都沒有。做法是把 runtime 函式改名為 agentWorkflow，交給 DBOS：

export const runAgentWorkflow = DBOS.registerWorkflow(agentWorkflow);

命名上有個約定：結尾加 Workflow 後綴，是刻意要讓讀程式的人一眼看出「這個函式有特殊的 durable 語意」，不是普通 function。註冊之後，行為不變、邏輯不變，唯一多出來的是 step 之間的邊界與持久化能力。

這一課完成後

runtime loop 的邏輯一行沒改，但它現在每一個昂貴的、有副作用的動作都被包成了可救回、不重跑的 step，而且整條 workflow 已經註冊生效。workflow 有了 durable 語意，剩下的就是把 server 接上它——讓使用者按下送出、讓崩潰後重開的瀏覽器能看到完整歷史。那是最後一課。
