把 model turn 與 tool call 抽成函式

Step 3/5 · 抽出 modelTurn 與 toolStep 兩個可被單獨包進 step 的函式

學習目標

把舊 runtime 裡的串流與工具執行抽成 modelTurn（emit modelDelta → 回傳 Turn）與 toolStep（toolRequested → runTool → toolCompleted）兩個獨立函式，讓每段副作用都能被單獨包進 durable step。

重構，不是重寫

上一課我們把工具執行收回自己手上，也畫好了 step 邊界。現在要做的是把原本混在 runtime loop 裡的一大段程式碼，抽成兩個「可以被包進 step」的獨立函式。請注意一件重要的事：這一步只搬程式碼的位置，不改任何行為——純粹是 refactor。

為什麼要抽？因為 DBOS.runStep 需要一段「可被描述、可被單獨重試」的程式碼當參數。原來一整陀的 inline 邏輯沒有清楚的邊界，就沒辦法精準地只包住想要的片段。抽成函式，就是給每一段副作用一個名字和一條清楚界線。

modelTurn：一次 model 呼叫的完整產物

第一個函式 modelTurn 包住「叫模型、把回傳串流出去」這整件事：

async function modelTurn(workflowId: string, messages: Message[]) {
  const result = streamText({ model, messages, tools });

  for await (const chunk of result.fullStream) {
    if (chunk.type === "text-delta") {
      emit({ type: "modelDelta", text: chunk.textDelta, workflowId });
    }
  }

  const toolCalls = (await result.toolCalls).map((call) => ({
    toolCallId: call.toolCallId,
    toolName: call.toolName,
    inputs: call.input,
  }));

  const response = { messages: await result.response.messages };
  return { text: "", toolCalls, response };
}

它的運作拆成三段：

  1. 串流——迭代 result.fullStream，每遇到一個文字片段 text-delta，就 emit 一個 modelDelta 事件，讓瀏覽器即時看到字一個一個冒出來。
  2. 收集工具呼叫——串流結束後 await result.toolCalls，把模型要求的工具呼叫映射成乾淨的 ToolCall 物件（只有 toolCallId / toolName / inputs 三欄）。
  3. 回傳 Turn——把 response messages 一併 await 出來，包成 Turn 回傳。

注意每個函式都吃一個 workflowId 參數，並把它放進事件裡。這是為了讓 event log 裡的每一條事件都能追溯到它屬於哪一次 workflow 執行——將來重播或除錯時，才能把同一回合的事件聚在一起。

toolStep：一次工具呼叫的完整產物

第二個函式 toolStep 包住「執行一個工具」這整件事，並用兩條事件把原因和結果框起來：

async function toolStep(workflowId: string, call: ToolCall) {
  emit({
    type: "toolRequested",
    toolCallId: call.toolCallId,
    toolName: call.toolName,
    inputs: call.inputs,
    workflowId,
  });

  const output = await runTool(call.toolName, call.inputs);

  emit({
    type: "toolCompleted",
    toolCallId: call.toolCallId,
    output,
    workflowId,
  });

  return output;
}

這裡的 correspondence（對應關係）是整個設計的重點：toolRequested 帶著 toolCallId、工具名稱與參數，toolCompleted 帶著同一個 toolCallId 與產出。有了這個 id 當關聯鍵，任何觀察者都能把「模型請求了什麼」和「工具回傳了什麼」精確對起來——這正是 inspector 能做到「看到每一通工具呼叫的前因後果」的原因。

這份「request → execute → completed」的三段式，就是工具進度變得可見、可重播的事件契約。未來任何工具——打資料庫、發訊息、跑沙箱——都套這同一個契約。

抽完之後，迴圈骨幹更清楚了

抽完這兩個函式，runtime loop 的骨架反而變得更乾淨：loop 每回合呼叫 modelTurn 拿到 Turn，若 Turn 有 toolCalls 就逐個跑 toolStep，把結果塞回 messages，再進入下一回合。原本糾纏在一起的「串流、工具執行、事件發送」現在各自有名有姓，正好各自對應一個可以包進 step 的單位。

但到目前為止，它們還只是普通函式——重跑仍然會重跑，crash 仍然會 crash。下一課，就是把它們真正丟進 DBOS.runStep，讓持久化生效。
