接上 server：重啟續跑與 history replay

Step 5/5 · 接 server、startWorkflow 啟動、連線重播 history，並看懂重啟續跑的示範

學習目標

用 env loader、main bootstrap、DBOS.launch 把 server 接上 durable bus，讓 submit_task 經 startWorkflow 啟動 workflow、連線時重播 history，並看懂「殺掉 server 重啟後續跑」的示範與其背後的訊息陣列機制。

開機順序，一步都不能亂

現在 workflow 已經註冊好了，剩下的就是把它接上真正會跑的 server。這裡最要緊的是初始化的先後順序——資料庫在讀環境變數當下就需要 DATABASE_URL，所以順序錯了，啟動當下就會炸。

第一步，env.ts 用 dotenv 載入 .env，而且必須是 server 的第一個 import，搶在任何會讀 env 的模組（例如 harness/db.ts）之前執行。之前 AI SDK 會自己默默載入環境變數，現在有資料庫了，這個時機得由我們自己掌握、往前挪一步。

第二步，把所有東西包進一個 async main()，依序做三件事：

async function main() {
  await ensureSchema();                              // 1. 建立/補全 event_log 表
  DBOS.setConfig({
    name: "harness",
    database: { hostname: "localhost", ... }         // 2. 指向 Postgres
  });
  await DBOS.launch();                               // 3. 啟動 durable 引擎
  // 接著才啟動 Express + WebSocket server
}
main().catch((err) => {
  console.error(err);
  process.exit(1);
});

ensureSchema 開機時自動建表（正式系統會改成真正的 migration，但課程先求能跑）；DBOS.setConfig 傳入 app 名稱和資料庫連線；DBOS.launch() 才真正啟動 durable 引擎——它同時也負責找回上次 crash 時進行到一半的 workflow。關鍵約束：server 的 listen 必須發生在 DBOS.launch() 之後，否則 workflow 還沒準備好就接流量。

把 durable bus 接上 WebSocket

server 起來後，把上一課寫的 bus 接進 WebSocket：subscribe 一個回呼，等 bus 有任何事件，就 JSON.stringify 後廣播給所有還開著的 client：

subscribe((event) => {
  const payload = JSON.stringify(event);
  clients.forEach((client) => {
    if (client.readyState === WebSocket.OPEN) client.send(payload);
  });
});

檢查 readyState === OPEN 是必要防護——對一個已經斷裂的連線發訊息會直接拋錯。這麼一來，之前那個「先寫後廣播」的 durable bus 就成了 durable workflow 與 live client 之間的橋樑：workflow 落盤的每一條事件，都會即時推給線上看的人。

一個動作 = 一次 workflow

使用者按下送出，對 server 來說就是一條 submit_task 訊息。handler 裡做的事情，是把這個使用者動作變成一次 durable、可恢復的 workflow：

if (message.type === "submit_task") {
  await DBOS.startWorkflow(runAgentWorkflow)(message.input);
}

DBOS.startWorkflow(runAgentWorkflow) 回傳一個「接受 workflow 參數的函式」，於是在同一個表達式裡立刻呼叫它、把輸入餵進去。這一行取代了原本直接 in-process 呼叫 runtime 的寫法——就這麼一個整合點，使用者動作從「一次性、會蒸發」變成了「持久化、可恢復」。

history replay：替重連的人補回錯過的部分

當一個 client 重新連上（不管是它斷線，還是 server 重啟），on connection 會做一件重要的事——把整段歷史倒出來、一條一條送回去：

ws.on("connection", (socket) => {
  // 逐條重播，而非一次整包送出
  const events = await history();
  for (const event of events) {
    socket.send(JSON.stringify(event));
  }
});

注意是逐條傳、不是一次打包。這讓 client 端能像看直播回放一樣，依序重建出「過去發生過什麼」。這就是為什麼你可能隨時重整瀏覽器，畫面上已發生過的對話都還在——它們不是存在前端，而是從 event_log 倒回來的。

最終示範：殺掉 server，然後讓它自己接著跑

組裝完成後，課程用一場 live demo 驗證一切：送出一個任務，趁 agent 還在「想」的時候，把 server 做掉。重啟 server、重整瀏覽器——工作流並不會從頭再來，反而從中斷處自己接下去繼續串流。

這不是魔法，背後有個可解釋的機制。回想 agent loop 的 messages 陣列：只要最後一則訊息的 role 是 user 或 tool，模型就知道自己必須回話；反過來，如果最後一則要是 assistant，模型不會回——那只會變成「自己回自己」，冒出兩條連續的 assistant。demo 裡，取消的時機恰好留下了一則還沒被回應的工具結果（role 是 tool），所以重啟後模型很自然地看出「還欠它一筆回應」，就自己接著產生了。

整堂課收束成一句話：runtime 的邏輯一行都沒改，我們只是把 emit、tool call、streamText 三個副作用包成了 durable step，讓它們落盤、可救回、不重複。那些「看起來像重寫」的大段 diff，本質上只是包裝。現在這個 agent 已經可以從崩潰中活下來了。
