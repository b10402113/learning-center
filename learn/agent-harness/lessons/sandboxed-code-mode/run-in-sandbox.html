實作 runInSandbox：用 node:vm 劃出沙箱邊界

Step 2/4 · 用最小 context 執行 agent 寫的程式

Agent 會產生程式碼，也可能要求呼叫工具。問題是：這段程式碼不能直接在 server 的環境裡奔跑，否則它可能碰到不該碰的 API，甚至一直執行不回來。這一步要做的，就是替它準備一間「只有必要物品的房間」：只放進允許使用的 tools、攔截輸出的 console.log，再加上執行時間限制。

學習目標

完成 runInSandbox 的完整流程：建立 context、只注入 tools 與 console.log、用 async IIFE 包住程式碼，再以 Promise.race 加上 timeout，最後回傳帶有 ok 的結果。

函式的契約：三個輸入

沙箱只有一個入口函式：runInSandbox。它的簽名先把邊界畫清楚，定義哪些東西能進來：

runInSandbox(code: string, api: SandboxApi, options?: { timeoutMs?: number })
  • code：模型產生的程式碼。對 runInSandbox 來說，它只是一段字串。
  • api：sandbox API，也就是一張函式白名單。沙箱內的程式只能呼叫這裡提供的能力。
  • options.timeoutMs：逾時毫秒數，預設為 2 秒（2000）。這是避免模型寫出無窮迴圈或其他長時間不結束的程式。

函式也會維護一個 logs: string[]，把沙箱內所有 console.log 的內容收集起來，最後一併回傳。因為沙箱裡的輸出不應該直接混進 server 的終端機。

建立 context：白名單之外，一無所有

先用 vm.createContext 建立隔離的執行環境。這裡最重要的規則是：context 裡放了什麼，沙箱裡才看得到什麼。

因此，這個最小 context 只提供兩樣東西：

const context = createContext({
  tools: api,                // 白名單能力，暴露成 sandbox 內的 global `tools`
  console: {
    log: (...args: unknown[]) => {
      logs.push(args.map((a) => String(a)).join(" "));
    },
  },
});

這一層存在的原因，是把「能做什麼」從模型的程式碼裡抽離，改由 harness 明確決定。

  • 能力注入（capability injection）：沙箱能使用的東西，只有你主動放進去的東西。這裡沒有 require、process 或 fetch，所以模型即使寫出 require("fs")，也找不到這個能力。
  • 攔截 console：這裡沒有使用真正的 console.log，而是放入一支假的 console。它會把每個參數轉成字串，用空白串起來，再推進 logs。

args 的型別是 unknown[]，所以必須先用 String() 轉換，才能交給 join。跑到這裡，你已經完成第一層邊界：沙箱只能看見白名單能力，輸出也會被 harness 收回來。

async IIFE：讓模型可以寫頂層 await

模型很可能會寫出 await tools.getCharges(...)。但我們拿到的是一段程式碼字串，不是一個已經宣告好的 async 函式；如果直接把它交給 runInContext(code)，頂層 await 就會造成語法錯誤。

做法是把程式碼包進一個立即執行的 async 函式（async IIFE）：

const wrapped = `(async () => { ${code} })()`;

這樣模型不需要自己補函式外殼，直接在程式碼裡使用 await 即可。這一層只負責改善執行介面，不是安全機制；它只是把一段字串包成可以非同步執行的形式。

執行與 timeout：讓程式和倒數計時器競賽

接著用 vm.runInContext 執行包好的程式碼，並把 context 與 timeout 一起交給它。

這裡不能直接無限期地 await 執行結果。假設程式進入無窮迴圈，或非同步工作一直沒有完成，呼叫端就可能永遠等下去。因此再加上一個 withTimeout helper，讓「程式結果」和「計時器」比賽，誰先完成就採用誰：

function withTimeout<T>(promise: Promise<T>, ms: number): Promise<T> {
  return Promise.race([
    promise,
    new Promise<never>((_, reject) =>
      setTimeout(() => reject(new Error("Timed out")), ms),
    ),
  ]);
}

程式先完成，就正常取得結果；計時器先觸發，就以 reject 結束等待，進入錯誤處理路徑。這層的重點不是讓程式「消失」，而是避免 harness 永遠卡在等待結果的狀態。

用 ok 標記成敗：讓 AI 不必猜結果

最後把執行結果包成清楚的成功／失敗 union：

try {
  const result = await withTimeout(runInContext(wrapped, context, { timeout: timeoutMs }), timeoutMs);
  return { ok: true, result, logs };
} catch (error) {
  return { ok: false, error: error instanceof Error ? error.message : String(error) };
}

為什麼要明確放一個 ok？因為讀取結果的可能不是人，而是下一個 AI 步驟。與其讓它自行猜測「有 error 欄位是否代表失敗」，不如直接用 ok: true 或 ok: false 標示狀態。成功時讀 result 與 logs；失敗時讀 error。

整支 runInSandbox 可以記成一個簡單模型：把程式碼字串放進只有 tools 和 console.log 的空房間，限制它的等待時間，再用 ok 回報成敗。 到這裡，沙箱的入口、能力白名單、輸出收集與結果判定都已經具備。
