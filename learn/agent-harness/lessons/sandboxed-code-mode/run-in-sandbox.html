實作 runInSandbox：用 node:vm 劃出沙箱邊界

Step 2/4 · 沙箱與 Code Mode

前言：上一課講了「為什麼」，這一課把房間蓋出來

上一課說明了兩件事：agent 產生的程式碼不能直接跑在伺服器上，而 code mode 的價值，是用一段程式取代多次工具往返。不過那還停在「為什麼」。要讓這個做法真的成立，得有人把那個邊界實際蓋出來，一個能執行模型程式、卻又關得住它的地方。

這一課的工作就是把這個地方寫出來，也就是一支 runInSandbox 函式。做完之後，它會接收一段字串形式的程式碼，在幾乎空的環境裡執行，只讓它碰得到你允許的工具，限制它的等待時間，最後回傳一個模型看得懂的成敗結果。

動手前，先確認前置條件：你的 Node 版本要夠新，node:vm 才匯得進來；harness 是 TypeScript 專案，沿用之前的設定即可；另外，你心裡要先有一份「打算開放給沙箱的能力清單」。這一步還不需要真正的 API，下一步才會組出 sandboxApi，現在只要知道它是一張函式白名單就夠了。

一、開檔、匯入 vm，先把型別定好

在 harness 資料夾新增一個 sandbox.ts，先從 Node 匯入 vm，並定義兩個型別。這一步還沒寫任何執行邏輯，但函式的輸入與輸出長什麼樣子，已經在型別裡定案。

import vm from "node:vm";

export type SandboxResult =
  | { ok: true; result: unknown; logs: string[] }
  | { ok: false; error: string; logs: string[] };

export type SandboxApi = Record<string, (...args: any[]) => unknown>;

預期看到什麼：一個可以編譯、但還沒有函式的檔案。三個關鍵行分別是：

  • import vm from "node:vm"：vm 是 Node 內建模組，不需要安裝。如果這一行就編譯不過，通常代表你的 Node 版本太舊。
  • SandboxResult：用 union 描述兩種結局。成功時一定是 ok: true 配上 result 與 logs；失敗時一定是 ok: false 配上 error 與 logs。兩邊都留 logs，因為就算程式最後失敗，過程中印出的訊息也該留給模型看。
  • SandboxApi：一張「函式名稱 → 函式」的對照表。沙箱能呼叫的每一支工具，都會是這張表上的一項。

二、函式簽名：三個輸入，先把邊界畫清楚

接著寫 runInSandbox 本身。先只看最上面幾行，因為它們就是這個沙箱的合約。

export async function runInSandbox(
  code: string,
  api: SandboxApi,
  opts: { timeoutMs?: number } = {},
): Promise<SandboxResult> {
  const timeoutMs = opts.timeoutMs ?? 2000;
  const logs: string[] = [];
  • code：模型產生的程式碼。對這個函式來說，它只是一段字串。
  • api：白名單。沙箱裡看得到哪些工具，完全由它決定。
  • opts.timeoutMs：逾時上限，單位毫秒，預設 2000（兩秒）。寫法是 ??，代表呼叫端沒給就用預設值；第三個參數有預設值，所以實際呼叫時可以只傳兩個參數。
  • logs：先開一個空陣列，之後攔截 console.log 時會往裡面塞東西。

預期看到什麼：函式目前還是空的，但它的形狀已經固定：進去的是字串與白名單，出來的一定是 SandboxResult。

三、建立 context：只有 tools 和 console 的空房間

現在蓋房間。用 vm.createContext 建立隔離的執行環境；這裡放進去的東西，就是沙箱裡看得見的全世界。

  const context = vm.createContext({
    tools: api,
    console: { log: (...args: unknown[]) => logs.push(args.map(String).join(" ")) },
  });
  • vm.createContext({ ... })：建立一個新的 context。傳進去的物件會成為沙箱裡的全域物件；沒傳進去的，沙箱裡就不存在。
  • tools: api：把白名單掛成沙箱的 tools。所以當模型寫 await tools.getCharges(...)，它呼叫到的就是你在 api 裡給的那一支。
  • console.log：這裡刻意不放真正的 console，而是自己寫一支。它把傳進來的參數逐個 String() 轉成字串，再用空白 join 起來，最後 push 進 logs。沙箱的輸出因此被 harness 收回來，不會混進伺服器的終端機。
  • args 標成 unknown[]：因為 console.log 什麼都能收，型別上得老實說不知道是什麼，所以才需要先 String() 再 join。

預期看到什麼：context 建立之後，沙箱裡看得見的名字就只有兩個：tools 和 console。沒有 require、process，也沒有 fetch。模型就算寫出 require("fs")，也會因為找不到 require 而立刻報錯。

這裡有一個可以用來檢查自己的判準：你把某支工具放進 api，它就會在沙箱裡存在；沒放進去的，就不存在。白名單的精神就這一句。

四、用 async IIFE 包住模型程式

模型很可能直接寫 await tools.getCharges(...)，但我們手上只有一段字串，不是一個已經宣告好的 async 函式。如果直接執行，頂層 await 會是語法錯誤。解法是把程式碼包一層。

  const wrapped = `(async () => { ${code} })()`;
  • 這行把整段 code 塞進一個立即執行的 async 函式（async IIFE），最後的 () 讓它一建立就馬上被呼叫。
  • 模型因此不必自己補函式外殼，就能在程式裡使用 await，也能用 return 交回結果。
  • 要說清楚：這只是使用介面上的方便，不是安全機制。真正的邊界在上一段的 context，不在這裡。

五、執行，並和 timeout 賽跑

接著把包好的程式送進 context 執行，並替它加上時間限制。

  try {
    const pending = vm.runInContext(wrapped, context, { timeout: timeoutMs }) as Promise<unknown>;
    const result = await withTimeout(pending, timeoutMs);
  • vm.runInContext(wrapped, context, { timeout: timeoutMs })：在剛剛的 context 裡執行 wrapped，並帶上 timeout。因為外層是 async IIFE，回傳的是一個 promise，先命名為 pending。
  • 這裡不要直接 await pending。如果模型寫出永不結束的程式，直接 await 會讓 harness 一起卡死，所以改成把它交給 withTimeout 去等。

withTimeout 是一支獨立的小 helper，做的事情就是讓「程式」和「計時器」賽跑：

function withTimeout<T>(promise: Promise<T>, ms: number): Promise<T> {
  return Promise.race([
    promise,
    new Promise<T>((_, reject) =>
      setTimeout(() => reject(new Error(`execution timed out after ${ms}ms`)), ms),
    ),
  ]);
}
  • Promise.race：同時等兩個 promise，誰先完成就採用誰的結果。
  • 第一個是程式本身；第二個是一顆定時器，時間一到就 reject，錯誤訊息裡帶上毫秒數。

這裡有幾種情況，值得分開講清楚：

  • 如果程式在時限內正常結束：race 拿到結果，繼續往下走。
  • 如果程式是同步無窮迴圈（例如 while (true) {}）：vm 的內建 timeout 會直接把它終止，這裡會進到 catch。
  • 如果程式是非同步卡死（例如 await 一個永遠不 resolve 的 promise）：vm 的 timeout 攔不到它，會改由 withTimeout 的計時器結束等待，回報逾時。

最後這點要誠實：vm 沒辦法真的「殺掉」已經外洩的非同步工作，它只是不讓 harness 繼續等下去，並把乾淨的錯誤交回給模型。完整的取捨留到第 4 步再談。

六、用 ok 標記成敗，把結果交回去

    return { ok: true, result, logs };
  } catch (err) {
    return { ok: false, error: err instanceof Error ? err.message : String(err), logs };
  }
}
  • ok: true 這條路：程式正常結束，回傳 result 與收集到的 logs。
  • catch 這條路：任何錯誤（語法錯、執行期錯、逾時）都被收斂成同一種形狀，ok: false，error 是訊息字串。
  • err instanceof Error ? err.message : String(err)：丟出來的東西不一定是 Error 物件，先檢查再取值，才不會讀到 undefined。
  • 為什麼要特別放一個 ok：讀這個結果的常常不是人，而是下一個 AI 步驟。與其讓模型自己判斷「有 error 欄位是不是代表失敗」，不如直接給它 true 或 false。這是刻意對模型「講白話」。

預期看到什麼：整支函式此時已經完整。無論成功或失敗，呼叫端拿到的永遠是同一種形狀的物件。

組起來：完整的 sandbox.ts

把上面幾段接起來，就是這個檔案最後的樣子：

import vm from "node:vm";

// The harness is the security boundary. When the agent writes code (Code Mode),
// it runs HERE — never with raw access to the process.
//
// This is `node:vm`, which is deliberately minimal:
//   · the context has NO `require`, `process`, `fs`, `fetch`, ... — only what we
//     hand in (a small `tools` API + `console.log`)
//   · the `timeout` option kills runaway SYNCHRONOUS code (e.g. `while(true){}`)
//
// Be honest about the limit: `vm` is NOT a true security sandbox, and its
// timeout can't interrupt async code. That's exactly why production systems run
// untrusted code in a hosted sandbox (e2b, Cloudflare's Sandbox SDK, Fly,
// Vercel, Daytona). The harness's job is to MEDIATE the boundary; the strength
// of the boundary is a deployment choice.

export type SandboxResult =
  | { ok: true; result: unknown; logs: string[] }
  | { ok: false; error: string; logs: string[] };

export type SandboxApi = Record<string, (...args: any[]) => unknown>;

export async function runInSandbox(
  code: string,
  api: SandboxApi,
  opts: { timeoutMs?: number } = {},
): Promise<SandboxResult> {
  const timeoutMs = opts.timeoutMs ?? 2000;
  const logs: string[] = [];

  // The ENTIRE global the code can see. Frozen so the code can't add to it.
  const context = vm.createContext({
    tools: api,
    console: { log: (...args: unknown[]) => logs.push(args.map(String).join(" ")) },
  });

  // Run the model's code as the body of an async function so it can `await`
  // tool calls and `return` a result.
  const wrapped = `(async () => { ${code} })()`;

  try {
    // `timeout` bounds the SYNCHRONOUS portion (a sync infinite loop dies here).
    const pending = vm.runInContext(wrapped, context, { timeout: timeoutMs }) as Promise<unknown>;
    // Backstop for async hangs. (vm can't actually KILL the leaked async work —
    // a real isolate can. We surface a clean error to the model regardless.)
    const result = await withTimeout(pending, timeoutMs);
    return { ok: true, result, logs };
  } catch (err) {
    return { ok: false, error: err instanceof Error ? err.message : String(err), logs };
  }
}

function withTimeout<T>(promise: Promise<T>, ms: number): Promise<T> {
  return Promise.race([
    promise,
    new Promise<T>((_, reject) =>
      setTimeout(() => reject(new Error(`execution timed out after ${ms}ms`)), ms),
    ),
  ]);
}

怎麼確認它真的能跑

先用一段最單純的程式，確認三個環節都到位：

const r = await runInSandbox(`console.log("hi"); return 6 * 7;`, {});
// r = { ok: true, result: 42, logs: ["hi"] }

預期看到什麼：ok 是 true，result 是 42，logs 裡有 "hi"。這代表程式真的被執行了（return 的數字拿得到），console.log 也真的被攔截了（訊息進了 logs）。

再故意弄壞一次，看看錯誤怎麼被回報：

const bad = await runInSandbox(`while (true) {}`, {});
// bad = { ok: false, error: "Script execution timed out after 2000ms", logs: [] }

預期看到什麼：ok 是 false，error 是一段類似 Script execution timed out after 2000ms 的訊息，而不是整個 process 卡住。看到這個結果，就代表 timeout 那條防線確實在運作。

小結

沙箱的邊界由 context 決定：只有你放進去的 tools 與攔截式的 console，沙箱裡才看得見。程式碼再包一層 async IIFE，讓模型能寫頂層 await。執行時不直接 await，而是用 Promise.race 和 timeout 賽跑。最後用 ok 明確標示成敗，讓讀結果的模型不必猜。

這支函式回答的是「模型寫的程式在哪裡跑、跑多久、結果長什麼樣」。至於「怎麼把模型導到這個工具」，那是下一步的事。
