實作 runInSandbox：node:vm 的沙箱邊界

Step 2/4 · 用最小 context 執行 agent 寫的程式

學習目標

能用 node:vm 寫出 runInSandbox 的完整流程：建立 context、只注入 tools 與 console.log、用 async IIFE 包住程式碼、再以 Promise.race 對上 timeout，返回 { ok } 結果。

函式的契約：三個輸入

沙箱只有一個入口函式 runInSandbox。它的簽名就是這道邊界的全部定義——什麼進得來、什麼傳得出去：

runInSandbox(code: string, api: SandboxApi, options?: { timeoutMs?: number })
  • code —— 模型寫的那段程式碼，就只是個字串。
  • api —— sandbox API，一個「函式對照表」。沙箱裡的程式只能呼叫這裡白名單列出的函式，別的全都碰不到。
  • options.timeoutMs —— 逾時毫秒數，預設 2 秒（2000）。這是防止模型寫出無窮迴圈、把 server 卡死的那道保險。

它還維護一個 logs: string[]，把沙箱裡所有 console.log 都收起來，最後一起回傳——因為沙箱裡的輸出不會直接印到你的終端機。

建立 context：白名單之外，一無所有

接著用 vm.createContext 造一個隔離的執行環境。關鍵在於：你往這個 context 裡放什麼，沙箱裡就只看得到什麼。這裡只放兩樣東西：

const context = createContext({
  tools: api,                // 白名單能力，暴露成 sandbox 內的 global `tools`
  console: {
    log: (...args: unknown[]) => {
      logs.push(args.map((a) => String(a)).join(" "));
    },
  },
});

兩點值得停下來想：

  • 能力注入（capability injection）：沙箱能用的東西「只有你給它的」。沒有 require、沒有 process、沒有 fetch——它們根本不在 context 裡，模型寫的程式想 require("fs") 也拿不到。
  • console 被偷換了：真正的 console.log 會印到你的終端機。這裡用一支假 console 攔截，把每個參數轉成字串、用空白接起來，推進 logs。參數型別是 unknown[]，所以要先 String() 再 join。

async IIFE：讓模型可以寫頂層 await

模型寫程式時，很可能想用 await tools.getCharges(...) 這種非同步語法。但我們執行的是一段「函式主體」，不是一個 async 函式——直接 runInContext(code) 會因為頂層 await 而爆掉。

解法很輕巧：把這段程式碼包進一個立即執行的 async 函式（async IIFE）：

const wrapped = `(async () => { ${code} })()`;

這樣模型就不用自己寫包裝，程式碼裡想用 await 就能用。注意：這純粹是方便模型，跟安全無關。

執行 + timeout：Promise.race 對決

真正執行是用 vm.runInContext，把包好的 code、context、還有 timeout 一起丟進去。但這裡有個關鍵細節：不直接 await 那個 pending promise——如果程式卡死（例如 while (true) {}），await 就永遠回不來。

所以外加一個 withTimeout helper，用 Promise.race 讓「程式」和「倒數計時器」比賽，誰先完成誰贏：

function withTimeout<T>(promise: Promise<T>, ms: number): Promise<T> {
  return Promise.race([
    promise,
    new Promise<never>((_, reject) =>
      setTimeout(() => reject(new Error("Timed out")), ms),
    ),
  ]);
}

程式先做完 → 正常回傳；計時器先觸發 → reject，走進錯誤路徑。這樣一個掛住的程式就無法無限期地卡在伺服器上。

用 ok 標記成敗：因為讀結果的是 AI

最後把結果包成一個清楚的成功／失敗 union：

try {
  const result = await withTimeout(runInContext(wrapped, context, { timeout: timeoutMs }), timeoutMs);
  return { ok: true, result, logs };
} catch (error) {
  return { ok: false, error: error instanceof Error ? error.message : String(error) };
}

為什麼要多一個 ok 布林值？因為讀這個回傳值的不是人，是模型。與其讓模型自己去猜「有 error 欄位就是失敗」，不如大字標出 ok: true/false，模型一眼就能分辨，拿起 result 或是 error 繼續下一步。

統整一下整支 runInSandbox 的心智模型：給它一段字串，它在一座只有 tools 和 console.log 的空房間裡執行，綁著 timeout，最後用 ok 跟你回報成敗。這就是整道沙箱邊界的全部。
