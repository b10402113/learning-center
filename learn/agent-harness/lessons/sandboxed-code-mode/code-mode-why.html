Code Mode：用一段程式取代多次工具往返

Step 1/4 · 為什麼 agent 產生的程式不能直接在機器上執行

先看 agent 為什麼會變慢、變脆弱

你已經有一個能呼叫工具的 agent：它描述需求、呼叫工具、等待結果、推理下一步，再呼叫下一個工具。簡單任務通常沒問題；但只要工作需要一連串計算，「呼叫─等待─推理─回傳」的迴圈就會變得又慢又容易出錯。

例如，客服 agent 要找出重複扣款的客戶，並算出應退款金額。它可能要查訂單、計算筆數、加總金額、查退款政策，再逐筆比對。整段流程可能產生十幾次 sequential 的工具往返；每一次都會消耗一個 model turn 的 token 與時間。即使加入平行化，仍然擺脫不了許多 small round-trip。

這正是 code mode 要解決的問題：把一連串操作交給一支程式一次完成，而不是讓模型逐步盯著每個結果來回處理。

Code mode：一個回合內串起工具

與其讓模型在十幾次往返中逐步呼叫工具，不如讓它直接寫一支程式，把需要的工具串在一起，一次執行，最後只回傳結果。

code mode = 讓 LLM 寫一支程式來串工具，用「一個回合」取代「多次工具往返」，最後只回傳結果。

英文叫 code mode。這個詞最早由 Claude 使用，業界也有其他等價說法，例如 Small-Agents，以及 HuggingFace 的 CodeActs。

它的核心不是讓模型變得更聰明，而是換一種工作方式：把複雜、跨多個步驟的計算交給一支確定性（deterministic）的程式完成。

這種做法有效，是因為模型很擅長「寫程式」，卻不擅長「在心裡算數」。例如，求解二次方程式時，讓模型反覆呼叫計算器函式，容易在中途出錯；讓它寫一支 Python 腳本，再一次執行，通常更可靠。code mode 正好把「寫程式強、算術弱」這兩項特性對齊。

但模型寫的程式要在哪裡跑？

這是沙箱最核心的問題：程式是模型寫的嗎？是。那你信得過它嗎？

coding agent 可能想執行 Bash，分析 agent 可能想執行 SQL 或計算。這些由模型生成的程式碼，絕不該直接跑在開發機或生產伺服器上。它可能寫錯、讀取不該讀的檔案，或連到不該連的地方。

把 agent 直接放進生產環境，就像把陌生人請進機房：程式在筆電上出錯，和在生產伺服器上出錯，後果完全不同。

因此，agent 可以保有生成並執行程式碼的能力，但執行位置必須是沙箱（sandbox）。沙箱的硬性要求只有一句話：

沙箱必須「逃不出去」。它是一道邊界，模型寫的程式只能碰沙箱裡提供給它的東西。

課堂做法與生產做法

市面上有許多沙箱方案，例如託管的隔離環境、獨立 process，以及專用 runtime。這門課先選擇容易理解、能快速實跑的做法：使用 Node 內建的 node:vm，在離線且最小的 context 中執行程式。

但要記住一個重要的誠實聲明：vm 不是真正的安全邊界。它過去曾經出現過可以被逃逸的漏洞。

所以，vm 很適合在課堂上示範「邊界」這個概念；真正部署到生產環境時，應改用託管的沙箱產品或獨立 process。課堂與生產之間的這條界線，是本節點最後要驗證的重點。

這一課的交付物

本節點要在 harness 裡加入一個沙箱，並定義一個 run_code 工具。它負責讓 agent「寫一支程式、在沙箱裡執行、回傳結果」，再把這個工具暴露給 agent 使用。
