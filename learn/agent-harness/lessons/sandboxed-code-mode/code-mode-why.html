Code Mode：用一段程式取代多次工具往返

Step 1/4 · 為什麼 agent 產生的程式碼不能直接執行

前言：一個回合，還是一打回合？

你手上有一個能呼叫工具的 agent。當任務只是「查一下這筆訂單的狀態」時，它很好用：呼叫工具、拿到結果、回答你，一氣呵成。可是當任務變成一串需要計算的流程，例如「找出重複扣款的客戶，算出每個人該退多少錢」，情況就不一樣了。它得先查訂單，再數筆數，再把金額加總，再核對退款政策，然後一筆一筆比對。

每一步都要走一次「呼叫、等待、推理、回傳」。結果整件工作被拆成十幾次往返，每一次都吃掉一個 model turn 的時間與 token。就算把能並行的呼叫接在一起，往返的次數還是降不下來，流程一樣拖。

這一課要回答兩個綁在一起的問題：有沒有一種做法，能讓 agent 一次就把這種工作做完？以及，如果 agent 開始自己寫程式，那段程式該在哪裡執行？

Code mode：讓模型寫一支程式，而不是一直敲單一工具

Code mode 的做法很直接：與其讓模型在十幾次往返裡逐步呼叫工具，不如請它直接寫一支程式，把需要的工具在程式裡串起來，執行一次，最後回傳結果。

換句話說，工具沒有消失，只是被包進程式裡。模型不再一個一個呼叫它們，而是在一個回合內寫出一段會呼叫它們的程式。這個詞最早由 Claude 使用，業界也有幾個等價的說法，例如 Small-Agents，以及 Hugging Face 的 CodeActs。

它處理的場景有明確的輪廓：一件必須更快得出答案、而且橫跨多個步驟的決策。如果只是單一次的查詢，用不著它。

它不是什麼

要說清楚 code mode，得先排除幾個容易混淆的想像。

它不是讓模型變聰明。模型本身的能力沒有改變，改變的是工作方式：把複雜的計算交給一段確定性的程式，而不是交給一次次的推理。它也不是平行化的另一種說法。平行化能讓往返從十幾次縮到幾次，但「呼叫、等待、推理、回傳」的迴圈還在；code mode 是把整串動作壓進一個回合，兩者解決的是不同層次的問題。

最後，它不是每個 agent 的標配。這是一種工具箱裡的選項，不是硬性架構。很多 agent 用單一工具呼叫就綽綽有餘，Claude Code 本身就是一個沒有這些東西、卻運作良好的單一 agent。只有當問題真的需要時，才值得為它加上這一層。

對照一：多次往返 vs. 一段程式

先看沒有 code mode 的樣子。假設一個客服 agent 要處理「找出重複扣款、算出退款金額」：它會依序呼叫查詢訂單、計算筆數、加總金額、查退款政策、逐筆比對等工具，中間每一次都要停下來等下一個推理步驟。十幾次往返累積起來，時間與 token 都花在來回溝通上。

再看有 code mode 的樣子。同一件事，模型寫出一支程式，在程式裡依序或並行呼叫那些工具，跑完直接把最終數字回傳。整段工作從「十幾次往返」變成「寫程式、跑、拿結果」。

沒有 code mode有 code mode
工作單位一次工具呼叫一支程式
往返次數十幾次，平行化後仍要數個回合一次
工具怎麼用模型逐步呼叫做決定程式把工具串起來
適合的任務單一步驟、單純查詢跨多步驟、需快速得答案的決策

對照二：反覆呼叫計算函式 vs. 一支腳本

另一組對照更能看出差別：數學計算。要解一個二次方程式，如果讓模型反覆呼叫一堆計算函式、每算一步就來回一次，很容易在某一步出錯。改成請它寫一支 Python 腳本，把計算寫成一個函式、執行一次，通常更可靠。一樣的工具能力，換成「一段程式」的形式，結果就穩定了。

機制：為什麼「寫程式」比「心算」可靠

這背後有一個關鍵、也有點反直覺的事實：模型很會寫程式，卻不擅長在心裏算數。

模型的推理是機率性的。當它遇到數字，很容易把某個數字當成熟悉的樣式，再生成另一個看起來合理、實際卻錯誤的值。日期又比數字更容易出錯，因為它牽涉多個位數和多種格式，生成過程只要偏了一點，整個值就變了。

程式正好補上這個缺口。同一段程式、同樣的輸入，永遠得到同樣的輸出，可以重跑、可以檢查，這就是所謂的確定性。code mode 的價值，不是把模型變強，而是把它的強項和弱項分開：需求交給模型，精確計算交給程式。

你可以把 code mode 想成這樣：不要讓一個人在櫃檯邊查資料邊心算，而是請他先把規則寫成一張試算表公式，按下執行，讓表格把答案算出來。人負責決定「要算什麼」，公式負責「算得準」。

不過這個類比有它的極限。試算表只會算你寫進去的公式，程式也只會做白名單裡提供給它的能力；它不會幫你判斷需求對不對，也不保證模型寫的程式沒有 bug。它只保證「一旦寫對了，執行結果穩定且可重現」。至於能力邊界要怎麼劃，就是後面幾步的事。

第二個問題：模型寫的程式要在哪裡跑？

這就帶到開頭的第二個問題，而且它比第一個更敏感。coding agent 可能想執行 Bash，分析 agent 可能想跑 SQL 或做計算。這些程式是模型寫的，你信得過它嗎？

答案是不該直接信。這段程式可能寫錯、可能讀取不該讀的檔案，也可能連到不該連的地方。所以有一條規則很硬：模型寫的程式，不該直接跑在開發機或生產伺服器上。

把 agent 直接放進生產環境，就像把陌生人請進機房。程式在筆電上搞砸，和在生產伺服器上搞砸，代價完全不同。生產伺服器一出錯，受影響的是所有使用者。

因此，agent 可以保有「生成並執行程式碼」的能力，但執行的地方必須是一個沙箱。而沙箱的硬性要求只有一句：它必須逃不出去。模型寫的程式只能碰到沙箱裡主動提供給它的東西，其他一概看不到、搆不著。

取捨：課堂的沙箱與生產的沙箱

這裡有個務實的取捨。市面上有許多沙箱方案，例如託管的隔離環境、獨立的 process，也有專用的 runtime。這門課為了能快速、離線地實跑，選的是 Node 內建的 node:vm，在一個最小的 context 裡執行程式。

但必須誠實說清楚：vm 只是個方便的中介點，不是真正的安全邊界。它過去出現過可以逃逸的漏洞（也許已經修補）。用它來理解「邊界」這個觀念很好，真的要部署，就該換成專門的沙箱產品或獨立 process。這條課堂與生產之間的線，會在本節點最後再收一次。

小結

Code mode 讓模型一次寫出一支串接工具的程式，把十幾次「呼叫、等待、推理、回傳」壓成一次「寫程式、跑、拿結果」。它之所以可靠，是因為模型擅長寫程式卻不擅長心算，而程式是確定性的、同一輸入必得同一輸出。它只適用於需要快速得答案的多步驟決策，不是每個 agent 的標配。至於模型產生的程式碼，不能直接跑在你的機器或伺服器上，必須關進一個逃不出去的沙箱。

把這兩件事收在一起看：code mode 是「怎麼用」的問題，沙箱是「在哪裡跑」的問題。前者讓 agent 用一段程式取代多次往返，後者確保那段程式碰不到不該碰的東西。兩者合起來，才是一個能放心交給 agent 執行程式碼的環境。

複習題
