什麼時候讓 agent 寫程式？而 vm 為什麼不是安全邊界

Step 4/4 · 沙箱與 Code Mode

學習目標

這一課要做的決定有兩層。第一層是面對一個任務時，該讓模型用推論直接回答，還是讓它寫一段程式丟進沙箱去跑；第二層是當你選了「寫程式」之後，這段程式該在哪裡執行：node:vm 這種輕量做法什麼時候夠用，什麼時候非換成託管沙箱不可。

前言

客服丟來一句話：「幫我找出重複的扣款，告訴我確切的退款金額。」模型面前有兩條路：在腦中想一想直接回答，或者寫一段程式去算。前一個做法可能吐出一個漂亮卻錯誤的數字；後一個做法則得先有個地方，能讓那段程式安全地跑起來。

上一課把 run_code 接進了 harness：模型看得到這支工具，runTool 也知道要把程式交給 runInSandbox。工具備好了，真正的難題才浮上來：模型什麼時候該用它？

如果模型對每個問題都先「想一想」再回答，前面蓋的那間沙箱等於白做；但如果每件小事都丟進去寫程式，又會為了一點計算而多背一份執行的風險。這裡有兩股力量在拉扯：一邊是推論的彈性，另一邊是程式碼的可靠。更麻煩的是，就算你決定讓模型寫程式，底下還藏著一個問題：那段程式跑的地方，真的安全嗎？

接線的事上一課做完了。這一課要把兩個決定講清楚：什麼時候該讓 agent 寫程式、什麼時候不該，以及選了「寫程式」之後，node:vm 什麼時候會不夠用。

一、選項只有兩個，取捨卻很具體

面對一個任務，能走的路大致就兩條。

第一條是推論（inference）：模型在對話裡直接思考、直接給答案。它擅長理解語意、抓重點，也能對模糊的需求靈活應對。

第二條是寫程式（code）：模型把解法寫成一段 JavaScript，交給沙箱執行，再從回傳的結果裡拿答案。模型的強項正好在這裡：讓模型寫程式，比讓它數數可靠得多。

兩條路沒有絕對的好壞，差別在任務的性質。把常見的差異並排出來，會看得比較清楚：

面向靠推論直接回答寫程式交給沙箱跑
最擅長的事語意理解、模糊判斷精確算術、日期比對、資料整理
算術可靠度機率性生成，可能出錯輸入固定，輸出就固定
日期處理位數一多就容易失手交給程式計算，不受生成偏移影響
能不能重現難以保證同一個答案同一份輸入可重跑、可驗證
多步驟任務拆成多次工具往返一段程式一次串完
額外成本幾乎不用設施需要沙箱與 timeout
失敗的長相悄悄給出一個錯數字回傳 ok:false 與錯誤訊息

這張表不是抽象的。回到開頭那個客服問題，讓 agent 走 code 模式，它會先分類，接著呼叫 run_code，寫出一段真的程式：用 await tools.getCharges(...) 取回扣款紀錄、用 console.log 把資料印出來檢查、找出同一名顧客在同一天被扣兩次的紀錄、再 searchKnowledgeBase 查一次退款政策，最後把算好的數字 return 回去。

結果是49 美元。這個金額來自程式回傳的結果，而不是模型憑印象猜的；對照假資料也對得上：同一名顧客，在同一天，因同一筆 49 美元被扣了兩次。如果改成讓模型一邊呼叫工具、一邊在對話裡自行拼湊與心算，除了比較慢，還多了「哪一步算錯」的風險。

問題出在推論的本質。模型有時會把你給的任何數字當成一個模板，然後代入隨機的值；算術一旦交給推論，遲早會在某一步幻覺，因為整個生成過程是機率性的。日期尤其不可靠，因為它牽涉的位數更多。把輸入強制交給程式執行，結果才會固定下來。

二、怎麼當場判斷：幾個可以問自己的問句

與其背那張表，不如記住幾個可以立刻問自己的問句。只要有一題答「是」，就值得讓模型寫程式。

「這個結果需要精確的算術或金額嗎？」需要就交給程式。連人的心算都會出錯，模型在腦中做算術更是機率性的。

「結果裡有日期嗎？需要比對、加減，或判斷是不是同一天嗎？」有就交給程式。日期是推論最容易失手的地方。

「同一份輸入重跑一次，答案必須一模一樣嗎？」必須就交給程式。可重現是程式的基本性質，卻正是推論給不了的保證。

「這個任務是不是一連串的組合：查資料、比對、計算、再查規則？」是的話，用一段程式一次串完，會比十幾次「呼叫、等待、推理、回傳」的往返快得多。

「答案需要留下來讓人稽核嗎？」需要就交給程式。程式本身就是一份可以被讀、被重跑的解說。

反過來說，如果這只是一次性的語意判斷，沒有精確數字要顧，那直接推論就好，不必為了一件小事蓋一座沙箱。

三、規則會翻轉的時候：vm 不是安全邊界

走到這裡，一切看起來很順：runInSandbox 擋掉了模組載入（context 裡根本沒有 require、fs、process、fetch），timeout 殺得掉寫壞的同步迴圈，錯誤也被包成模型讀得懂的結構化結果。測試腳本 test-sandbox.ts 就把這四道護欄直接展示了出來：

  1. code mode：程式透過 tools.getCharges() 取得資料並完成計算。
  2. 無窮迴圈：while (true) {} 到達時間上限後被終結。
  3. 禁止載入模組：require("fs") 失敗，因為 context 裡沒有 require。
  4. 程式有 bug：例如讀取不存在的變數，錯誤會變成結構化結果回傳，模型能讀了再修。

但這裡有一個必須誠實面對的限制：node:vm 不是真正的安全邊界，它只是一個中介點。這行字就寫在 sandbox.ts 的註解裡。

原因在於：vm 的 timeout 只能中斷同步的程式，殺不掉已經「漏出去」的 async 工作。也就是說，如果模型在沙箱裡啟動一個非同步任務，而主流程被 timeout 終止了，背景那個任務不一定會一起消失。withTimeout 只是用 Promise.race 做一個後備煞車，讓模型收到乾淨的錯誤訊息，但它沒辦法真的把那段工作殺掉。

一個能被繞過的隔離層，就不算真正的邊界。而且這不是理論上的擔心。來源裡提到，vm 過去真的出現過可以逃逸的漏洞（可能已經修補，但這正說明它本質上不是拿來當安全邊界用的）。

那什麼時候「丟進沙箱跑就好」這個規則會翻轉？當你要執行的是真正不受信任的輸入，或者你要把這個能力對外提供服務的時候。來源的判斷很直接：暴露一個 agent 到 production，就跟暴露一個陌生人到 production 一樣不明智；一旦出錯發生在 production 伺服器上，後果會比在自己的筆電上嚴重得多。

正式部署的答案，是把邊界交給託管的隔離沙箱，用真正的 process 或容器隔離，例如 e2b、Cloudflare Sandbox SDK、Fly、Daytona、Vercel 這類產品。在課堂裡用 node:vm，是因為它拿來學機制又快又好。harness 的責任是站在邊界上調解，至於這道邊界要多強，是一個部署選擇。

重點回顧

  • 先判斷，再選路：結果牽涉精確算術、日期或可重現性，就讓模型寫程式；只是語意判斷，就直接推論。
  • 為什麼要這樣分：推論是機率性的，數字會被當模板代換、日期特別容易錯；同一份輸入交給程式，輸出就固定。
  • $49 demo：模型寫出真的程式，算出 49 美元退款，金額來自 return 的結果，也比多次工具往返更快。
  • timeout 設定點：預設值是兩秒；實際生效要在 runTool 呼叫 runInSandbox 時，用 options.timeoutMs 傳入。
  • 規則會翻轉：node:vm 殺不掉漏出的 async 工作，只是中介點；要跑真正不受信任的程式或上線服務，就換成託管的隔離沙箱。

複習題

到這裡，「沙箱與 Code Mode」整節就完成了。你手上有一個能在 node:vm 裡執行模型程式的 runInSandbox、一支接進 harness 的 run_code 工具，心裡也多了一套判斷依據：知道什麼時候該相信推論、什麼時候該讓程式去算，以及這層隔離能保證什麼、不能保證什麼。如果還有哪個環節不清楚，隨時回來問我。
