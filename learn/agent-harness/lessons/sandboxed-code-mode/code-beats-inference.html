為何 code 勝 inference，與 vm 不是真正的邊界

Step 4/4 · 用一個 $49 的 demo 驗證，然後誠實面對邊界的極限

學習目標

能解釋為什麼讓模型「寫程式再執行」比「用推論做算術」可靠（算術跟日期會幻覺），並說得出 node:vm 只是中介點、不是真正的安全邊界，生產環境該用託管沙箱。

先把工具「說給模型聽」

工具建好了，模型不會自動知道要去用它。得在 system prompt 裡「廣告」一下：告訴 agent，凡是需要算術，就呼叫 run_code，在一個 async 包裝裡寫 JavaScript，可以用 getCharges、searchKnowledgeBase 這兩個 helper。

有趣的是：這段 prompt 沒有所謂標準答案。怎麼寫都可以，重點是讓模型知道「有 run_code 這個工具、何時該用」。這是個關於探索的小提醒——工具描述是給模型看的護欄，措辭是自由的。

Demo：算出精確退款

拿一個 billing prompt 來實測，故意設計成「不用 code mode 就很痛苦」的題型：

「幫我找出重複扣款的客戶，告訴我該退多少錢（美元，精確數字）。」

agent 接了這個任務，走完一整輪：classify → 呼叫 run_code → 真的寫出一支程式，await tools.getCharges(...) 把帳單撈進來、console.log 打印、找出同一客戶同一天重複扣款的那筆、再問知識庫退款政策、最後 return 出結果。

出來的數字是——精確的 $49。而且這個 $49 是從「return 的回傳值」來的，不是從 log 裏猜的。整件事「遠比讓模型在幾十次搜尋+算術的工具往返裡慢慢推理」快多了。

為什麼 code 勝過 inference

這是本節點最深的一課，也是它最反直覺的地方。多數人會想：「讓模型直接算不就好了，為什麼還要寫程式？」答案是：模型做算術是不可靠的，它做的是機率性的推理。

具體兩大地雷：

  • 算術幻覺：模型有時把任何出現的數字當成模板，隨機代入別的數值。算術只要走推論路線，某個地方就一定會幻覺——因為這整個過程是機率性的。
  • 日期特別糟：日期尤其不可靠，因為位數多、模型常記不住或弄錯。

解法就是那句口訣：模型擅長寫程式，不擅長數數，那就讓它寫程式。把輸入「強行餵給」一段確定性的程式碼，出來的結果是可重複、可驗證的。程式不會因為同一個輸入而偶爾給出不同的答案。

timeout 能設在哪？

回到一個實際的運維問題：萬一模型寫了支掛住的程式，要怎麼擋？答案是 timeout 可以在呼叫層或 runtime 層控制：

  • 預設是 2 秒，但目前預設值「擺在那沒被用」。
  • 你也可以在 runTool 的 switch 裡呼叫 runInSandbox 時，把 options.timeoutMs 傳進去。
  • 背後的 withTimeout 會 promise 出一個「計時到就 reject」的新 promise，跟程式 Promise.race——先完成的贏。
  • 程式若超時，reject 就順勢掉進錯誤路徑，掛住的程式無法無限期卡住 server。

把邊界「打出來看」：test-sandbox

課程還附了一支 test-sandbox.ts，直接驅動 runInSandbox（不需要 agent），把這道邊界的三種護欄實地演一遍：

  1. 正常計算——透過 tools API 撈資料、算出結果。
  2. 同步無窮迴圈 while (true) {}——被 timeout 攔下來。
  3. require("fs")——被封鎖，因為 context 裡根本沒有 require。
  4. 一支有 bug 的程式——回傳一個結構化錯誤，模型可以拿它來自我修正。

第四點尤其重要：錯誤要是結構化的（有明確的 error 訊息、清楚的 ok: false），模型才有辦法「讀懂自己錯在哪、再寫一次」。這正是讓 code mode 可以自癒的基礎。

誠實的最後一課：vm 不是真正的安全邊界

整節最該帶走的一句話：node:vm 是個中介點（mediation point），不是真正的安全邊界。

它做得到「攔住 require、綁 timeout、只給白名單」，但做不到真正的隔離——例如它殺不掉外洩出來的非同步工作，而且歷史上真出現過可被逃逸的漏洞。課堂上用它是因為簡單、離線、一看就懂；但要真的部署，答案是換掉它：用託管沙箱 / 隔離產品（e2b、Cloudflare Sandbox SDK、Fly、Daytona 這一類），或至少一個獨立 process。

把這幾課收斂成一個判斷：在學習、prototype 階段，用自己的 node:vm 沙箱又快又好；一旦要把 agent 放上生產，沙箱這層就該外包給專門的託管產品。這跟你自己的 runtime（OryxOS / Java）是同一套邏輯：先自己推導出邊界的雛形，真要到生產時，就換算成平台職責。
