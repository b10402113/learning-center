run_code 工具：把沙箱接進 harness

Step 3/4 · 沙箱與 Code Mode

前言：房間蓋好了，但還沒有門牌

上一節把沙箱蓋好了。runInSandbox 現在能接下模型寫的程式字串，在只有白名單 tools 與假 console 的最小 context 裡執行，綁上兩秒 timeout，再回傳帶 ok 的結果。房間是蓋好了，但對 agent 來說，它目前還沒有門牌：模型不知道有哪支工具可以寫程式、程式裡能呼叫哪些函式，也不知道送出之後由誰負責執行。

這一節要把這間房間接進 harness，補上三條線。第一條是沙箱 API，也就是沙箱裡允許呼叫的函式白名單；第二條是工具本身，也就是模型看到的使用說明書；第三條是 runTool 的 switch，把模型送來的程式真正導向 runInSandbox。接完之後，agent 就能用一段程式取代一連串工具往返。

動手前請先確認兩件事：你已經完成上一節的 runInSandbox，而且熟悉 harness 加新工具的老規矩：先在 tool() 定義模型看得到的介面，再到 runTool 處理實際執行。這一節要做的就是照這個節奏，把沙箱也變成一支工具。

三個接點，照順序做

  1. 先定義沙箱 API，決定沙箱能拿到哪幾把鑰匙。
  2. 再定義 runCode 工具，把「怎麼寫程式、能呼叫什麼」講給模型聽。
  3. 最後在 runTool 的 switch 接上 runInSandbox，讓呼叫真的落地執行。

一、定義沙箱 API：只交出必要的鑰匙

先從沙箱 API 開始。這個物件的每一個鍵，就是沙箱裡程式能呼叫到的 tools.*；沒列進去的，沙箱完全碰不到。所以寫這份清單時，你其實是在決定「這段外來程式被允許做什麼」。這個退款客服用例真正需要的，只有「查扣款」與「查知識庫」兩件事，那就只給這兩把鑰匙。

import { runInSandbox, type SandboxApi } from "./sandbox";

type Charge = { id: string; amount: number; date: string; description: string };

// 示範用假資料：ch_001 與 ch_002 是同一筆重複授權（金額單位為分）
export const CHARGES: Record<string, Charge[]> = {
  cus_88121: [
    { id: "ch_001", amount: 4900, date: "2026-05-01", description: "Pro plan — monthly" },
    { id: "ch_002", amount: 4900, date: "2026-05-01", description: "Pro plan — monthly" },
    { id: "ch_003", amount: 1500, date: "2026-04-18", description: "Extra seats" },
  ],
};

// 沙箱能呼叫的函式白名單
const sandboxApi: SandboxApi = {
  getCharges: async (customerId: string) => CHARGES[customerId] ?? [],
  searchKnowledgeBase: async (query: string) => searchKB(query),
};

逐鍵看它在做什麼：

  • getCharges 收一個 customerId，回傳 CHARGES 裡對應的扣款紀錄，找不到就回空陣列。沙箱裡的 await tools.getCharges("cus_88121") 走的就是這一條。
  • searchKnowledgeBase 收一個查詢字串，直接轉呼叫 searchKB(query)。
  • CHARGES 只是一份示範用的假資料，重點是它刻意埋了一筆重複授權（ch_001 與 ch_002），讓後面有真的算術可以驗證。金額單位是「分」，所以 4900 代表 49 美元。

注意第二個鍵：searchKB 不是新寫的，而是從原本的工具函式裡抽出來的共用 helper。在此之前，知識庫搜尋的比對邏輯只存在原本那支工具裡；現在沙箱也要用同一套邏輯，與其複製一份，不如抽成獨立函式，讓兩邊都呼叫它。

export function searchKB(query: string): string[] {
  const q = query.toLowerCase();
  const hits = Object.entries(KNOWLEDGE_BASE)
    .filter(([key]) => q.includes(key))
    .map(([, article]) => article);
  return hits.length ? hits : ["No exact match — use your judgment."];
}

這個重構看起來很小，卻擋掉一種常見的災難：同一段邏輯複製成兩份之後，某天只改了其中一份，另一邊就悄悄走鐘。抽成 helper，兩條路徑永遠走同一份實作。

這一步做完的預期結果：存檔後，sandboxApi 的鍵會原封不動變成沙箱裡的 tools。想確認白名單真的有效，可以在呼叫 runInSandbox 時刻意傳一個空物件 {}，這時沙箱裡任何 tools.xxx 都會是 undefined，因為沙箱只認得你交出去的那幾個鍵。

二、定義 runCode 工具：把使用說明書寫給模型

接著定義模型看得到的工具。它跟 harness 裡其他工具一樣，用 tool() 包裝，交出 description 與 inputSchema 兩個欄位：

import { tool } from "ai";
import { z } from "zod";

export const tools = {
  runCode: tool({
    description: [
      "Run a JavaScript program (an async function body) to fetch and analyze data.",
      "Available inside the program:",
      "  • await tools.getCharges(customerId) → [{ id, amount (cents), date, description }]",
      "  • await tools.searchKnowledgeBase(query) → string[]",
      "  • console.log(...) for debugging",
      "Use `return` to return your result (any JSON value).",
    ].join("\n"),
    inputSchema: z.object({ code: z.string() }),
  }),
  // …其他工具（classifyItem、draftReply、sendReply 等）
};

模型的工具清單裡，runCode 就長這個樣子。逐個欄位看它的作用：

  • description 是模型判斷「要不要用這支工具」、「該怎麼寫」的主要依據。這裡刻意用陣列一行一行寫，再 join("\n") 接起來，是為了讓模型讀到的說明有清楚的換行斷點。
  • 說明裡交代了三件事：這支工具適合做什麼（fetch and analyze）、程式要寫成什麼形式（async function body）、以及沙箱裡有哪些函式可以呼叫（tools.getCharges 與 tools.searchKnowledgeBase）。
  • inputSchema 只有一個欄位 code，型別是字串。整段程式就是塞在這個字串裡送進來，不需要其他參數。

其中第三件事最容易漏，也最致命。沙箱裡的函式全都掛在 tools 底下，所以模型必須寫成 await tools.getCharges(...)。要是說明沒把 tools. 前綴講清楚，模型很可能直接寫成 getCharges(...)：

漏講的後果。 模型寫下 getCharges("cus_88121")，但沙箱裡只有 tools.getCharges，沒有裸露的 getCharges。這一呼叫會直接丟出 ReferenceError，而模型只收到一個 { ok: false, error }，卻不知道是自己少了前綴。
寫對的做法。 說明裡連前綴一起列：await tools.getCharges(customerId) 與 await tools.searchKnowledgeBase(query)。模型照著這個介面寫，就不會憑自己的印象拼出錯的名字。

這一步做完的預期結果：存檔後，模型手上的工具清單會多出 runCode，而且它知道要送進來的是一段 async 函式主體。不過到這裡它還只是「看得到工具」，實際執行還沒有著落。

三、在 runTool switch 接上 runInSandbox

工具定義只是菜單，還需要廚房真正出菜。這個 harness 把所有工具的執行集中在一支 runTool，用 switch 分派；只要補上對應的 case，模型送來的呼叫才有地方落地。

export async function runTool(
  name: string,
  args: Record<string, unknown>,
): Promise<Record<string, unknown>> {
  switch (name) {
    case "runCode":
      return runInSandbox(String(args.code ?? ""), sandboxApi);
    case "getCharges":
      return { charges: CHARGES[String(args.customerId)] ?? [] };
    case "searchKnowledgeBase":
      return { articles: searchKB(String(args.query ?? "")) };
    // …其他工具（classifyItem、draftReply、sendReply 等）
    default:
      throw new Error(`unknown tool: ${name}`);
  }
}

關鍵就在 runCode 這一個 case，逐段拆開看：

  • String(args.code ?? "") 先把模型送來的 code 取出、轉成字串。萬一模型漏帶欄位，?? "" 會讓它變成空字串，而不是把 undefined 傳進沙箱。
  • 接著把這段程式和 sandboxApi 一起交給 runInSandbox。這正是沙箱邊界的入口：程式只在沙箱裡跑，永遠不會在主行程裡執行。
  • 回傳值就是沙箱的結果：{ ok: true, result, logs } 或 { ok: false, error, logs }。

runInSandbox 的第三個參數 options 是選填的，所以這裡只傳兩個參數是合法的，timeout 會自動套用預設的兩秒。如果某個任務你想把上限收得更短，再補上第三個參數就好：

// 高風險又要求快，就在執行入口指定上限
case "runCode":
  return runInSandbox(String(args.code ?? ""), sandboxApi, { timeoutMs: 500 });

把限制放在執行入口，好處是每次接線都能單獨決定這個工具的容忍度，不必回頭去改沙箱本身。三個 case 的差別也很清楚：getCharges 與 searchKnowledgeBase 是單一動作工具，模型一次呼叫一支；runCode 是組合工具，模型只呼叫一次，程式裡卻能串起多個動作。三條路最後都使用同一份 sandboxApi，因為它們共享的就是同一組能力。

這一步做完的預期結果：模型一旦呼叫 runCode，runTool 就會把 code 連同 sandboxApi 交給沙箱，你會在結果裡看到 ok 與 logs。到這裡，沙箱對模型來說才算真的有了門牌。

重點回顧

把沙箱接進 harness，就是補三條線：sandboxApi 決定沙箱能呼叫哪些函式（getCharges、searchKnowledgeBase，搜尋邏輯抽成共用的 searchKB）；runCode 工具用 description 把「怎麼寫程式、能呼叫什麼」講給模型聽；runTool 的 switch 再把 runCode 導向 runInSandbox。整個過程也可以縮成一句口訣：定義工具，處理工具。

現在模型有了一間能執行程式的房間，也知道工具入口在哪裡。下一步要用一個真實的退款情境來驗證這條路：看看模型是否會主動寫程式，以及為什麼讓程式實際算出數字，會比單靠模型自行推論可靠得多。這一節也會說清楚 node:vm 的極限：它是一個方便的中介點，卻不是真正的安全邊界。
