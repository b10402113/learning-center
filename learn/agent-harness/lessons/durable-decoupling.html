Durable 解耦：讓 run 不再依附 client

Step 3/5 · 從「可以延後」到「非有不可」的那條線

學習目標

能解釋 durable execution 如何把 agent run 與 client 解耦（SSE 重整、關頁面都不丟失），並判斷何時該把它從「可延後的下一步」升級成非有不可的一層。

症狀：重整頁面，工作就死了

最直觀的故障長這樣：agent 正在跑一段十幾秒的推理，使用者重新整理頁面——然後一切重來。剛剛的工具呼叫、剛剛想好的計畫，全沒了。或者 server 換一個 instance、重啟一次，進行中的工作直接消失。

原因不是模型不穩，而是run 的生命週期綁在發出請求的那個 client 上：工作活在 request handler 的堆疊裡，連線一斷，堆疊就散了。durable execution 要修的就是這件事。

解耦的是什麼：run 與 client 的生命週期

解耦之後，run 有自己的身分（一個 workflow id）與自己的持久狀態（寫進資料庫的事件日誌）；client 不再是 run 的宿主，只是它的訂閱者。連線斷了，頂多少了一個觀眾，run 照樣往前跑；使用者重連，只是重新訂閱同一條事件流，把中間漏掉的事件補回來。

畫一條線：線的一邊是「工作」，另一邊是「看工作的人」。durable 就是讓這兩邊分開，誰都不必等誰。

你已經有的機制

前面幾個節點其實已經把解耦的四塊積木都做好了。把他們排在一起看，就會發現 durable 不是一個新功能，而是這些機制的合成結果：

機制它解耦了什麼
event_log 資料表把「發生過什麼」從記憶體搬到資料庫，成為真相來源
durable bus（先寫後廣播）事件先落地再推送，訂閱者來去不影響歷史
DBOS steps（model turn / tool call）每一步都 checkpoint，重啟後從最後一步接續而不是重來
server bootstrap + history replay重連時回放事件，把畫面補到最新狀態

什麼時候可以延後

回顧 step 1 的結論：對一個 chat agent，durable 可以晚點再補。判斷的標準是「斷掉重問一次的代價大不大」：

  • 工作很短（一兩次模型呼叫就回覆）。
  • 斷了重來，使用者不會真的損失什麼。
  • 只有單一 client、單一使用者盯著畫面。

在這些條件下，把力氣先花在記憶與壓縮上，投報率更高。

什麼時候變成必要

但只要體驗換一下，durable 就從選配變成地基：

情境為什麼 durable 變必要
工作壽命超過一次連線深研究跑十幾分鐘，使用者不可能一直盯著分頁
需要背景完成與通知關掉頁面也要跑完，完成後再主動通知
不可逆動作的審批等待approval gate 要能無限期待機、跨天跨重啟
多裝置 / 多使用者同時看run 不屬於任何一個連線，任何人都能訂閱

代價：它不是免費的一層

durable 換來的是可靠，付出的是複雜度：你要有一個 durable store（課程用 Postgres / Neon，連線字串記得去掉 -pooler）、要把 workflow 與 step 註冊好、還要小心選擇 step 邊界——尤其是不可逆的動作（退款、出貨）絕不能被重跑，必須包在正確的 step 與冪等設計裡。環境設定有摩擦，但這是把 agent 從「玩具」推向「產品」時最值得付的一筆。

轉折：durable 是無限 agent 的入場券

對 chat agent，durable 可以延後；但對另一種形態的 agent——在背景無限地跑、等事件、做完再通知你的那種——durable 不是選配，而是入場券。它同時也是理解那個形態最好的起點，因為那裡的每一個互動都建立在「run 活得比連線久」之上。
