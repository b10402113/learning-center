平行 dispatch、fan-in 容錯與 supervised 路由

Step 5/5 · allSettled 平行子 agent、記錄失敗、註冊與路由

學習目標

能用 plan.steps.map 對每個子 agent 起一個平行 DBOS step、以 allSettled 收集 fulfilled 的 findings、對失敗的發 SubagentFailed 事件並繼續，將 synthesize 包成 step，最後註冊 workflow 並用 mode === 'supervised' 路由。

為什麼全部塞進「一個 step」

dispatch 的做法是：計畫裡每一個 step，各自啟動一個平行的 DBOS step。但這裡有一個刻意的設計——所有子 agent 被放在同一個上層步驟的邏輯範圍內一起啟動，因為它們必須同時跑，所以當其中一次重試時，是整批一起重試。

這不是理論上最優的設計（最優會讓每個子 agent 各自擁有獨立的重試生命週期），但在這裡是刻意選擇：簡單、便宜，且對「一次有界調查」的工作負載足夠。你應該知道這個取捨，而不是誤以為它是唯一解。

另一個重點是 context：每個子 agent 有自己的 context window。它們不共用 supervisor 的對話，各自在乾淨的 context 裡讀資料，這正是我們要的隔離。

平行派工：plan.steps.map

const settled = await Promise.allSettled(
  plan.steps.map((s) =>
    DBOS.runStep(
      async () => {
        await emit({
          type: EventType.SubagentStarted,
          workflowId,
          stepId: s.id,
          agent: s.agent,
          objective: s.objective,
        });
        const findings = await runInvestigator(s.agent, s.objective);
        await emit({
          type: EventType.SubagentCompleted,
          workflowId,
          stepId: s.id,
          agent: s.agent,
          findings,
        });
        return { agent: s.agent, findings };
      },
      { name: `subagent-${s.id}` },
    ),
  ),
);

每個 callback 的節奏是：發開始事件 → 跑調查 → 發完成事件 → 回傳 findings。發事件是為了讓 GUI 逐步看到每個子 agent 的狀態；step 名稱用 subagent-{id} 讓每次執行在 DBOS 裡可辨識。plan.steps.map 一次把計畫中所有項目變成進行中的 promise。

fan-in：收成功的、記失敗的、繼續走

const findings: { agent: string; findings: string }[] = [];
for (let i = 0; i < settled.length; i++) {
  const result = settled[i];
  const step = plan.steps[i];
  if (result.status === "fulfilled") {
    findings.push(result.value);
  } else {
    await DBOS.runStep(
      () =>
        emit({
          type: EventType.SubagentFailed,
          workflowId,
          stepId: step.id,
          agent: step.agent,
          error: String(result.reason),
        }),
      { name: `subagent-failed-${step.id}` },
    );
  }
}

Promise.allSettled 是關鍵：它不會因為一個 promise 失敗就整批掛掉，而是回傳每一項的狀態。於是 fan-in 可以很單純地：fulfilled 的把 findings 收進陣列；rejected 的發一個 SubagentFailed 事件、記下它死掉的原因，然後繼續迴圈。整條 workflow 因此能局部降級——少一個調查員，答案仍能產出，只是會承認那一塊沒查到。

課堂上點出一個更進階的選項：把失敗餵回 supervisor，讓它決定要不要補救（例如換個 objective 重派、或直接告訴使用者）。這被明確延後——先掌握最小可行的降級模式就夠了。

synthesize 也要包 step、也要發事件

const reply = await DBOS.runStep(() => synthesize(task, findings), { name: "synthesize" });
await DBOS.runStep(
  () => emit({ type: EventType.ModelCompleted, workflowId, text: reply }),
  { name: "synth" },
);
await DBOS.runStep(
  () => emit({ type: EventType.WorkflowCompleted, workflowId, output: reply }),
  { name: "completed" },
);
return reply;

這再次套用同一條規則：synthesize 是非決定性又昂貴的模型呼叫，所以包進 step。跑完後發 ModelCompleted，最後發 WorkflowCompleted 並回傳答案。

這裡藏著一個真實的教訓：原本程式忘了 return reply，而這個 bug 之所以被發現，是因為那行 ModelCompleted 的 emit 期待收到一段 stream 型別的文字，型別檢查當場指出「你沒有把結果傳出來」。持久化 workflow 裡的每個 emit，同時也變成一道型別護欄。

註冊 workflow

最後把整條函式註冊進 DBOS，給它一個穩定的名字：

export const runSupervisorWorkflow = DBOS.registerWorkflow(supervisorWorkflow, {
  name: "supervisorWorkflow",
});

路由：mode === 'supervised'

最後一塊拼圖是把 supervisor 接進 server，讓它成為使用者可以主動選的模式。server 的 index 匯入 runSupervisorWorkflow，提交任務的處理器檢查訊息上的 mode：

if (message.mode === "supervised") {
  // 啟動 supervisor workflow
  await runSupervisorWorkflow(message.input, ...);
} else {
  // 預設走原本的 agent workflow
}

這就是「plan mode 由使用者明示開啟」在程式裡的落點——沒有自動推斷，只有一個明確的旗標決定走哪條 workflow。

端到端：一次監督模式執行長什麼樣

跑一次 supervised 模式，事件流會依序出現：

  • 產生的 plan 物件——一個 steps 陣列，標明哪個 agent 做哪個 objective。
  • 三個子 agent 各自的 start / complete 事件（billing 找到重複收費、technical 搜了知識庫、sales 處理 50 人座的定價需求）。
  • 每個調查員的 findings。
  • 最後 synthesize 出的回覆。

另外兩個值得記住的觀察：第一，handoff 只存在於 agent workflow，supervisor workflow 不知道 handoff，所以兩者不能任意合併；第二，課堂建議之後可以再補一個「investigation completed」的 step，讓 inspector 的軌跡更完整。

至此你走完了 supervisor 的完整生命週期：計畫 → 平行派工 → 容錯收斂 → 導向使用者的路由。這也是整個 harness 系列裡，「控制權留在主管手上」這條路線的終點。
