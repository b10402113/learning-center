唯讀 investigators：註冊表與最小權限

Step 2/5 · 用資料描述 sub-agent、限制工具、單次有界執行

學習目標

能用 Record<string, investigator> 註冊 billing / technical / sales，各自只拿職責內的 getCharges 或 searchKB，並用 generateText 讓 runInvestigator 以有界步數單次執行。

工人是什麼：唯讀的調查員

supervisor 派出的工人叫做 investigator（調查員），它們的定義性特徵是唯讀：只查資料、只讀知識庫，不改任何狀態、不產生副作用。

唯讀帶來一個非常關鍵的好處——重跑是安全的。如果一個調查員執行到一半掛掉，直接重跑它不會造成重複扣款、重複寄信之類的災難。也因為這樣，investigator 不需要被升級成第一級的 DBOS step；它可以安穩地活在 supervisor 的某個 step 裡面，用 AI SDK 的工具迴圈 inline 跑完。

打個比方：investigator 分到的是辦公室的「小隔間（cubicle）」，不是主管的「獨立辦公室（corner office）」。它有自己的 context window，但沒有自己的持久化生命週期。

兩個唯讀工具

先用 AI SDK 的 tool() 把兩個唯讀能力包成工具，輸入都用 zod 描述：

const getCharges = tool({
  description: "Look up a customer's charges.",
  inputSchema: z.object({ customerId: z.string() }),
  execute: async ({ customerId }) => CHARGES[customerId] ?? [],
});

const searchKnowledgeBase = tool({
  description: "Search the support knowledge base.",
  inputSchema: z.object({ query: z.string() }),
  execute: async ({ query }) => searchKB(query),
});

這裡用了兩堂課前的模式：工具就是資料（名稱、description、inputSchema、execute）。因為有 execute，工具迴圈由 AI SDK 內聯處理，整個 sub-agent 就成為「一次有界的互動」，可以被塞進單一 step。

註冊表：agent 是一筆資料

三個調查員用一個型別化的 註冊表（registry）描述。每筆資料只有兩個欄位：一段 system prompt 和一份工具清單。

type Investigator = { systemPrompt: string; tools: ToolSet };

const INVESTIGATORS: Record<string, Investigator> = {
  billing: {
    systemPrompt:
      "You are a billing investigator. Use getCharges to find duplicate or erroneous charges. Report the charge ids, the amount, and the refund you'd recommend — concisely.",
    tools: { getCharges },
  },
  technical: {
    systemPrompt:
      "You are a technical investigator. Use searchKnowledgeBase to find known bugs and workarounds. Report the issue, any ticket, and the workaround — concisely.",
    tools: { searchKnowledgeBase },
  },
  sales: {
    systemPrompt:
      "You are a sales investigator. Use searchKnowledgeBase for pricing guidance, then state the relevant numbers and next step — concisely.",
    tools: { searchKnowledgeBase },
  },
};

這正是 agent 當資料的極致：一顆 sub-agent 就是一個字串加一個工具集。要新增一個領域的調查員，只要在註冊表加一筆，supervisor 的程式完全不用改。

最小權限：各自只拿該拿的工具

注意工具是分開的：billing 只拿 getCharges，technical 和 sales 只拿 searchKB。沒有任何一個調查員同時握有兩種能力，更不會碰到像退款那種有破壞性的操作。

investigator工具職責
billinggetCharges找重複或錯誤的收費，報 charge id、金額與建議退款
technicalsearchKB找已知 bug 與 workaround，報 issue、ticket
salessearchKB查定價資訊，prompt 調成偏價格與下一步

給每個調查員寫一段「有自信」的 system prompt，是刻意的手法：角色越明確，它回報的格式越穩定、越貼近你要的欄位。sales 的 prompt 特別往 pricing 調，就是同一個註冊表、不同角色的一例。

執行一次：runInvestigator

export async function runInvestigator(agent: string, objective: string): Promise<string> {
  if (process.env.CHAOS_FAIL === agent) {
    throw new Error(`investigator '${agent}' crashed (CHAOS_FAIL)`);
  }

  const investigator = INVESTIGATORS[agent];
  if (!investigator) throw new Error(`unknown investigator: ${agent}`);

  const { text } = await generateText({
    model,
    system: investigator.systemPrompt,
    prompt: objective,
    tools: investigator.tools,
    stopWhen: stepCountIs(5),
  });
  return text;
}

三個設計決定值得記住：

  • 查表 + 防呆：先看註冊表有沒有這個名字，沒有就丟錯。這讓計畫裡打錯的 agent 名稱立刻爆出來，而不是默默跑出一個沒有工具的空殼。
  • 用 prompt 不用 messages：這是背景的一次性任務，沒有來回對話，所以直接給一個 objective 字串即可。
  • 步數有界：stopWhen: stepCountIs(5) 把工具迴圈限制在五步內。sub-agent 是拿來做有界調查的，不是讓它無限探索。

失敗是設計的一部分：CHAOS_FAIL

開頭那行 CHAOS_FAIL 是一個刻意留的混亂開關：只要啟動時設定 CHAOS_FAIL=technical npm run dev，technical 調查員就一定會丟錯。這不是惡作劇，而是把「某個子 agent 掛掉」變成可重現的場景，好在下一步看到整條 supervisor 如何優雅降級——少一個調查員，答案仍能送達。
