階層式監督何時划算：隔離與 fan-out

Step 1/5 · 何時該用 supervisor、plan mode 為何要使用者開啟

學習目標

能判斷何時該用 supervisor 與 sub-agents（隔離邊界如 git worktree、研究型 fan-out 與 context 切分），並說明 plan mode 為何由使用者明示開啟而非自動判斷。

開場：接在 handoff 之後的下一種拓撲

上一節課的 handoff 是「橫向」的控制權轉移：櫃台把你轉給鬍鬚專家之後，櫃台就退場了，任務不再回頭。這一節要學的是另一種拓撲——階層式監督（hierarchical supervision）：主管 Agent 自己不動手做細活，而是把子任務派給一群工人，工人在各自的角落做完回報，主管再把結果整合成一份答案。

差別就在控制權：handoff 是「換聯絡人」，監督是「我派工人、我整合、我還是我」。整個過程裡，對使用者負責的始終是同一個 supervisor。

supervisor 的四個動作

整條架構可以用四個動詞記住：

動作做什麼
plan把使用者的需求拆成一份具體計畫：誰（哪個 agent）去做哪一件（objective）
dispatch把計畫裡的每個項目平行丟給對應的 sub-agent
fan-in收集成功的結果、記錄失敗的、然後繼續走
synthesize把散落的發現收斂成一份連貫、直接回給使用者的答案

後面四步就是在把這四個動作一步步寫出來。

什麼時候扇出才划算？

先打一劑預防針：不是每個需求都該開 sub-agents。花力氣拆 agent 要有明確回報，而回報來自兩種具體條件。

條件一：隔離邊界（isolation boundary）

典型場景是寫程式。如果每個 sub-agent 都在自己的 git worktree（同一份 repo 的獨立工作目錄）裡改檔，彼此就不會踩到對方的變更，也不會有 merge conflict。平行工作之所以安全，不是因為模型聰明，而是因為底層把隔離做好了。

條件二：fan-out 與 context 切分

典型場景是研究。並行跑多個調查可以換到速度；更重要的是，有些題目需要的資料量超過單一 agent 的 context window（模型一次能看見的輸入上限）。把它切成幾個子題、各自在獨立的 context 裡讀，最後再合併，是單一 agent 體質上做不到的事。

反例：不要做成全自動 swarm

相對的陷阱是讓一堆 sub-agent 和 supervisor 無限期地互相溝通。這種「自主 swarm」會大量產生幻覺——每一輪對話都可能累積並放大錯誤，而且沒有人能確定最終答案從哪裡來。這裡明確不採用這種架構：工人只做一次有界的工作、回報、結束，supervisor 保留控制權並負責收斂。

判斷口訣：找得到一條清楚的隔離邊界，或題目真的塞不進單一 context，才值得扇出。否則一個頂級模型加一個像樣的 harness 通常就夠了。

plan mode：為什麼是使用者決定，而不是 agent 自己判斷

這門課把「階層式監督」做成一個使用者可以主動開啟的模式（plan mode，也稱 supervised mode），而不是讓 agent 自行揣測什麼時候該用 sub-agents。

理由很務實：要讓 agent 準確判斷「這個需求該不該拆」需要 evals（系統性的評估資料與量測），而那不是這門課要處理的範圍。與其做一個沒被驗證過的自動判斷，不如把決定權交給使用者——你想用監督模式就跑監督模式，這是明示的 toggle。

這也牽動一個關鍵設計：plan 是一級產物（first-class artifact）。它不是在對話執行緒裡閃過的一段文字，而是被產生、被存下來、能通過 schema 驗證、崩潰後還能重讀的一份物件。正因為它被明示建立、結構化儲存，後面的 dispatch 才能穩定地照著它跑。

兩種拓撲的對照

控制權對使用者來說典型用途
handoff完整轉移，原 agent 退場聯絡人換人權限邊界、職責劃分
supervisor主管保留，派工人再收斂聯絡人始終同一人隔離平行、context 切分

同一個問題可以用其中任一種解，選的是拓撲，不是「哪個 agent 比較強」。接下來四步都用「主管保留控制權」這一半。
