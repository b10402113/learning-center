脈絡為何膨脹：History、State、Context

Step 1/5 · 先看清楚問題，才有後面兩個積木

學習目標

說出脈絡無限成長為何讓模型變笨、變慢、變貴，並分辨 History（持久事件日誌）、State（壓縮摘要）、Context（這一輪送進模型的內容）三者的角色。

一個所有人都看過的假象

打開任何一個聊天產品，你都會看到完整的對話歷史：從第一句到剛剛那句，一字不漏地往上滑。於是你很自然地以為，模型也看得到這一切。

它沒有。模型看到的，永遠是 harness 特別為這一輪組出來的一個子集。前面那些你以為它記得的內容，可能早就被壓成幾行摘要，甚至完全不在這次送出的訊息裡。

使用者看到的是 History；模型看到的是 Context。兩者之間的落差，就是這一課要蓋的橋。

脈絡一直長，模型會怎樣

如果 harness 什麼都不做，讓對話歷史原封不動地一直往後接，會發生三件事——而且它們是同時發生的：

代價發生什麼為什麼
變笨中間的內容等於被遺忘模型對 context 的注意力不是均勻的：開頭與結尾最可靠，夾在中間的東西最容易被忽略
變慢每一輪的回應時間拉長每一輪都得重新處理整段輸入，輸入越長、越快不了
變貴帳單跟著 context 一起長輸入 token 是要計費的，而且每多一輪就往後累加一次

「中間被遺忘」這點特別反直覺。你可能會想：都已經放進 context 了，模型怎麼可能沒看到？但 attention（注意力）不是資料庫查詢——它是一種會被長度稀釋的加權。文件放在中段，就像簡報夾在中場休息後的那一頁，最容易滑過去。

換一個更大的視窗，並不是解方

面對這個問題，第一個冒出來的念頭通常是「那我用 context window 更大的模型就好」。這條路走不通，理由有兩個：

  • 更多不等於更好。視窗變大並沒有讓中間內容的注意力問題消失，反而常常更嚴重。把更多東西塞進去，只是讓被稀釋的範圍更大。
  • 它只是把懸崖往後移。對話總有一天會超過任何固定的上限。超過的那一刻，錯誤不是慢慢變差，而是直接爆掉——請求被拒絕、整段流程中斷。

所以真正的問題不是「視窗夠不夠大」，而是「誰決定模型此刻需要看到什麼」。這個決定不能交給模型自己，因為它根本不知道自己沒看到什麼。

三種記憶：History、State、Context

要把這件事想清楚，得先分開三個常被混為一談的東西：

名稱它是什麼壽命誰在看
History（歷史）持久化的事件日誌：每一件事都留在 durable 儲存裡永久，除非主動清空系統、審計、重放
State（狀態）被壓縮後的那份 running summary：舊內容的結晶跟著工作流累積harness 自己
Context（脈絡）這一輪真正送進模型的 messages 陣列只活一輪模型

三者的關係是這樣的：History 會無限膨脹，所以需要被壓縮成 State；State 加上最近還沒被壓縮的 turns，再被組裝成 Context。每一次使用者送出訊息，Context 都重新組一次——它不是一份持續累積、從不重建的檔案，而是每輪即時重算的產物。

這也正是為什麼「context assembly（脈絡組裝）」在某些團隊裡是一個專職角色：模型每一輪看到什麼，直接決定了它的行為與成本。

這一課要蓋的兩個積木

接下來會做兩個可重用的積木，各自對應上面的一個環節：

  • Hydrator（脈絡注入器）：在每一輪即時組出 Context——該帶哪份摘要、該帶哪個任務、該留哪幾個 turns。
  • Compactor（壓縮器）：當預算快滿時，把最舊的內容從 turns 裡移出來、餵給 summarizer，把 History 的成長煞住。

兩個積木都放進 harness/memory.ts。你會在這支檔案裡看到兩個旋鈕：maxTokens 與 keepContextTokens。課程裡會把它們故意設得很小（例如上限 500、保留 200），這樣跑一次 demo 就能看到壓縮真的發生；真實系統的值當然會大得多，但機制完全一樣。

// harness/memory.ts 的兩個旋鈕（課程中故意調小，讓壓縮看得見）
const maxTokens = 500;         // 超過就該壓縮
const keepContextTokens = 200; // 壓到低於這裡為止

順帶記一個往後會用到的細節：課程的 token 估算很粗糙，因為它只是把字數除以四左右來逼近。真實系統要換成跟模型相同的 tokenizer（分詞器／編碼器），否則你估算的數字跟模型實際看到的會對不上。

帶回自己的 runtime

把這一課的模型對照回自寫的 ReAct loop，問題會很具體：你的 loop 是不是把所有歷史都無腦往 messages 裡塞？如果是，那它不是「還沒壞」，而是「還沒長到會壞」。這一層的決策——預算驅動、舊內容壓縮、每輪重組 context——跟語言無關，Java runtime 一樣要面對。
