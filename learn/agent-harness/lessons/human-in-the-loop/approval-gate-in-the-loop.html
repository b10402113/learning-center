把 approval gate 接進 durable loop

Step 3/4 · Human-in-the-Loop 審批

學習目標

能在 runtime loop 的 tool call 分派處加上 NEEDS_APPROVAL 檢查：發 ApprovalRequested 事件、用 DBOS.recv 等待決定、發 ApprovalResolved，approve 就執行、拒絕就塞進「不重試」的 tool 結果。

接在哪裡：第三個分支

兩個原語有了，現在把它接進 runtime。回顧 agentWorkflow 的 tool 迴圈：它逐一走過 model 提議的 tool calls，對每個 call 決定要做什麼。原本有兩條路——handoff 被攔截、其餘照常執行。審批就插在中間，成為第三條：

for (const call of turn.toolCalls) {
  if (call.toolName === "handoff") {
    // 攔截、切換當前 agent
  } else if (NEEDS_APPROVAL.has(call.toolName)) {
    // 人類審批閘門  ← 新增
  } else {
    // 直接執行
  }
}

為什麼一定要放在這裡？因為這是「模型提議」與「工具執行」之間唯一的瓶頸。放在這裡，任何被標記的工具都繞不過；模型再怎麼想自己動手，也得先過這關。

四個動作：發事件、等待、回事件、執行或拒絕

進到這個分支之後，流程是固定的四步。

1. 發 ApprovalRequested。先告訴外界「有人在等批准」。注意它被包進 DBOS.runStep——因為發事件也是副作用，必須 durable、只發一次：

await DBOS.runStep(
  () => emit({
    type: EventType.ApprovalRequested,
    workflowId,
    toolCallId: call.toolCallId,
    action: call.toolName,   // "issueRefund"
    args: call.input,        // 金額、chargeId 等
  }),
  { name: `approval-req-${call.toolCallId}` },
);

這則事件就是 UI 收到後跳出批准卡片的來源。

2. 暫停等決定。接著整個 workflow 停在 recv 上：

const decision =
  await DBOS.recv<{ approved: boolean }>("approval", APPROVAL_TIMEOUT_S);
const approved = decision?.approved ?? false;

那個 ?? false 很重要：如果等到 timeout 都沒人回、或 payload 沒有 approved 欄位，預設是拒絕。特權動作的閘門要 fail closed——沒人明確同意，就不放行。

3. 發 ApprovalResolved。拿到決定後，再發一則事件把結果廣播出去，UI 收到就翻牌：

await DBOS.runStep(
  () => emit({ type: EventType.ApprovalResolved,
              workflowId, toolCallId: call.toolCallId, approved }),
  { name: `approval-res-${call.toolCallId}` },
);

4. 執行或拒絕。最後依決定分岔：

if (approved) {
  const output = await DBOS.runStep(() => toolStep(workflowId, call), {
    name: `tool-${call.toolCallId}`,
  });
  turnMessages.push(toolResultMessage(call, output));
} else {
  turnMessages.push(toolResultMessage(call, {
    approved: false,
    message:
      "A human did NOT approve this action. Do not retry — tell the customer it needs manual review.",
  }));
}

批准時，才真的跑 toolStep 把錢退出去（一樣包在 DBOS.runStep 裡，確保只執行一次）。

被拒絕也要回一則 tool 結果

看 else 分支：拒絕的時候，我們不是直接把工具跳過，而是回一則 approved: false 的 tool result 給模型。這牽涉到之前講過的 message 陣列完整性——模型既然提議了這個 tool call，就必須收到對應的 tool result，否則下一輪的訊息序列不合法。

而且那句話不是寫給人看的，是寫給模型看的：Do not retry、tell the customer it needs manual review。它在明確告訴模型「這件事被否決了，別繞路再試一次，直接改用人工複審的說法」。這比單純讓工具失敗更安全——否則模型很可能換個參數再提議一次。

和 durability 的組合

整段邏輯都在 agentWorkflow 裡，所以它自動繼承 durable 的性質。回想那段 demo：批准卡彈出時把 server 砍掉、重啟，DBOS 會恢復這個 workflow；因為 recv 的訊息被 checkpoint，恢復後它要嘛繼續等、要嘛拿到已收到的決定。人類的批准可以在 crash 之後才送達，流程照樣接著跑——錢也只有在「是」之後才會動。

模型提議、harness 攔截、人類決定、durable 恢復——四個動作把不可逆的動作牢牢鎖在人的同意之後。
