送審端：/api/approve、UI 按鈕與 plan 審批練習

Step 4/4 · Human-in-the-Loop 審批

學習目標

能用 server 的 /api/approve/:workflowId 透過 DBOS.send 把決定送進被暫停的 workflow、配合 UI 的 approve 按鈕閉合雙向流程，並把「plan 先批準再執行、可來回調整」當成串起整段的結尾練習。

缺的另一半：誰來按按鈕

前三節做的都是 workflow 內部：標記、暫停、等待、執行。但它停在那裡等，總要有人把決定送進來。這節做送審端——從瀏覽器按下按鈕，到喚醒那個睡在 Postgres 裡的 workflow。

server：一個 route 就夠

送決定的入口是一個普通的 Express route：

app.post("/api/approve/:workflowId", async (req, res) => {
  const approved = Boolean(req.body?.approved);
  await DBOS.send(req.params.workflowId, { approved }, "approval");
  res.json({ ok: true });
});

三個細節：

  • :workflowId 從 URL 拿——你要叫醒的是哪一個 workflow。
  • Boolean(req.body?.approved) 把 body 轉成布林值。
  • DBOS.send(workflowId, { approved }, "approval") 的第三個參數 "approval" 必須和 workflow 裡 recv("approval", ...) 的 topic 完全一致，否則訊息送不到那個等待點。

因為 DBOS.send 是寫進 Postgres，這個 route 可以在完全不同的 process 上執行——「甚至幾天後、甚至重啟之後」，照樣喚醒那個 workflow。

兩個必要的管線設定

route 本身很簡單，但要讓瀏覽器打得進來，還得補兩個設定：

app.use(express.json());          // 解析 POST 的 JSON body

app.use((req, res, next) => {
  res.setHeader("Access-Control-Allow-Origin", "*");
  res.setHeader("Access-Control-Allow-Headers", "Content-Type");
  res.setHeader("Access-Control-Allow-Methods", "GET,POST,OPTIONS");
  if (req.method === "OPTIONS") return res.sendStatus(204);  // preflight
  next();
});

express.json() 是為了讀 req.body.approved；CORS 與 OPTIONS preflight 則是因為 inspector 跑在不同的 port，屬於跨來源請求。少了任何一個，批准按鈕都會打不進來——這是那種「程式沒錯、但就是不通」的典型設定坑。

UI：批准卡片早就準備好了

課程不自己刻 UI，inspector 已經內建 approval card。它的行為完全由事件驅動：

收到的事件UI 的反應
approval.requested跳出待批准動作，附 Approve / Reject 按鈕
approval.resolved卡片翻成 ✓ Approved 或 ✗ Rejected

按下按鈕時，它把 { approved } POST 到 /api/approve/:workflowId——正是上一段那個 route。於是迴圈閉合了：harness 發請求事件 → UI 顯示 → 人類決定 → route 送 send → workflow 醒來。

端到端 demo：連 crash 都要活著

送一筆退款：「Customer cus_88121 was charged twice, refund the duplicate.」 triage 先分類，hand off 給 billing，billing 用 runCode 查重複扣款，然後呼叫 issueRefund——閘門觸發：

classifyItem → HANDOFF → runCode → approval.requested

此時 inspector 彈出 Approval required，workflow 暫停。錢還沒動。

現在做那個最關鍵的實驗：在等待時把 server 砍掉。

↓ [Ctrl-C，process 消失]
↓ [npm run dev → "Recovering 1 workflows from application version …"]
↓ [按下 Approve]
approval.resolved → issueRefund → draftReply → sendReply → workflow.completed

被暫停的 workflow 熬過了 crash：DBOS 在重啟時恢復它，人類的批准（可能好幾天才到）把它喚醒。而 issueRefund 只在人類說「是」之後才執行。這就是第二課 durability 的紅利，套用在一個人類身上。

結尾練習：先批 plan，再執行

課程把這整段留成一個很值得做的延伸：能不能改成先批准 plan？

現在的 supervisor 是「做出 plan，然後立刻執行」。更好的設計是：

  1. 先產出 plan，暫停等批准（同一套 recv／send）。
  2. 允許使用者來回討論、調整這份 plan。
  3. 只有明確按下「批准」，才開始執行。
  4. UI 上要有一顆 approve 按鈕。

這個練習之所以好，在於它把今天學的全部接在一起：plan 是階層式監督那段的產物、durable 的暫停與恢復、以及 UI 事件。同一個原語只是換了要被守護的對象——從「一支工具」換成「一份計畫」。

審批的對象可以是工具，也可以是計畫；機制完全相同——決定性的暫停，加上一個人類的決定。

而這也正是把整套 harness 收束起來的一句話：你有的不是某個 agent，而是一個能持久地跑任何 agent 的 runtime——包含在必要時，停下來等人。
