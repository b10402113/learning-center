DBOS recv/send：無限期暫停與恢復

Step 2/4 · Human-in-the-Loop 審批

學習目標

能用 DBOS.receive 無限暫停一個 workflow、用 DBOS.send 攜帶 payload 與 tag 喚醒它，並解釋 durable 為什麼讓「等一個人類、甚至等很多天」不必燒任何 compute。

問題：到底要等多久？

上一節決定了「要暫停」。但要暫停多久？答案是不確定——人類可能三十秒後批准，也可能三天後才看到。而我們不可能讓一個 process 撐開三天：沒有那麼多資源，而且 crash 一次就全沒了。

所以需要一種暫停，是「把狀態寫進資料庫、然後 process 可以自由結束」的暫停。DBOS 的 recv 就是這個原語（primitive）。

DBOS.recv：把 workflow 停進 Postgres

DBOS.recv 會暫停執行——compute 完全停止——直到它等的那個變數改變為止。改變的方式，是從外界送一則訊息進來。Scott 的說法是：它「可以無限期暫停，幾年都行」。

const decision =
  await DBOS.recv<{ approved: boolean }>("approval", APPROVAL_TIMEOUT_S);

參數有兩個重點：

  • 第一個字串 "approval" 是 topic（頻道）。送訊息的人要送到同一個 topic。
  • 第二個是 timeout（秒）。課程給 APPROVAL_TIMEOUT_S = 86_400，也就是一天——但這只是「最多願意等一天」，等待長度本身可以拉到年。

關鍵在於：當 workflow 停在 recv，它不是一個卡住的 thread。它被寫進 Postgres，process 可以退出、可以重啟、可以換一台機器。沒有任何 compute 在為這個等待買單。

DBOS.send：從外界叫醒它

另一半是送訊息的人。用 DBOS.send 把 payload 送到指定 workflow 的指定 topic：

await DBOS.send(workflowId, { approved: true }, "approval");

這會把訊息寫進 Postgres，並喚醒那個正在 recv("approval") 上等待的 workflow。它可以在不同的 process、不同的時間點送達——課裡的說法是「甚至幾天後、甚至重啟之後」。workflow 醒來後，recv 的 promise resolve 成送進來的 payload，於是它知道人類的決定是什麼，繼續往下跑。

recv 是原語，不是 step

課程特別點出一個容易混淆的地方：recv 是 durable workflow 的原語，不是一個 step。差別在哪？收到的訊息會被 checkpoint 起來。所以當 workflow 因為 crash 被 DBOS 恢復時，它只有兩種可能：

要嘛拿到「它先前已經收到的那個決定」，要嘛繼續等——不會漏掉、也不會重問。

這正是 durable 的價值：暫停與恢復都是狀態，而不是記憶體裡一個懸著的 promise。

白話對照

原語做什麼誰呼叫
DBOS.recv(topic, timeout)暫停 workflow，等 topic 上的訊息workflow 內部
DBOS.send(workflowId, payload, topic)送訊息到 workflow，喚醒它的 recvworkflow 外部（server）

換句話說：recv 是「我在等」、send 是「我來了」。兩者透過 Postgres 對接，中間可以隔著好幾天、隔著一次 crash、隔著不同的 process。

順帶一提，這不是 DBOS 獨有的把戲。生產上等價的東西有 Temporal 的 signal、Inngest 的 waitForEvent、durable promises，以及專門處理 human-in-the-loop 的 HumanLayer——它們都在做同一件事：把人類的決定變成一個第一級、durable、可恢復的 workflow 狀態。
