不可逆的動作為何不能重跑

Step 3/4 · 冪等（idempotency）與 exactly-once：動作只能發生一次

學習目標

能解釋兩個具體危害——訊息全放在記憶體會在重啟時消失、send_reply／轉帳這類不可逆動作不能 undo——並用冪等（idempotency）與 exactly-once 語意說出不可逆動作為何必須「只做一次」。

第一種危害：記憶體一關就歸零

回到課程到目前為止的 runtime loop。每個 agent 的訊息、對話、狀態——全都放在記憶體（in-memory）裡。這代表一件事：只要 process 一重啟，agent 對「剛剛發生過什麼」就一無所知。

對使用者來說，這是致命的體驗：你等 agent 跑了半天，某個環節出錯、或只是 server 例行重啟，agent 醒來之後彷彿失憶，完全不記得你交代過什麼、它已經做到哪。這不是「等一下就好」的暫時卡頓，而是整段進度憑空蒸發。

所以 durable execution 的第一個動機非常具體：把執行狀態從記憶體搬到一個能活過重啟的地方。這是上一節「checkpointing」要落地的地方。

第二種危害：不可逆的動作

第二種更危險。agent 不只「想」，它會出手做事情——而且有些事情一旦做了，就收不回來。課程裡把它叫做 destructive action（破壞性／不可逆動作）。

想像兩個場景：

場景一：send_reply 發出到一半，系統壞了。訊息到底寄出沒？你不知道，於是你再跑一次——結果同一封信被寄了兩次。
場景二：轉帳轉到一半，系統壞了。你又跑一次——結果錢被轉了兩次。

關鍵是：你不能 undo。訊息已經寄出去了，你沒辦法把手伸進別人的信箱、在他打開之前把信抽回來；轉帳也是一樣。這些動作只要重跑，就會重複發生——而重複一次都可能是災難。

解法：冪等與 exactly-once

面對不可逆動作，正確的做法不是「祈禱不要出錯」，而是在結構上保證「出錯重跑也不會重複」。這就帶出分散式系統裡最重要的兩個詞：

概念白話它保證什麼
idempotency（冪等）同一件事做兩次 = 做一次，結果不變動作重跑是安全的
exactly-once（恰好一次）整個系統最終只執行一次不會被重複觸發

兩者的關係是：exactly-once 靠冪等的 step 堆出來。如果每個動作本身冪等（多跑一次結果一樣），那麼即便失敗重試、甚至整個 workflow 重播，最終效果也像是「只做了一次」。反過來，一個不冪等的動作，你永遠無法保證 exactly-once——因為重試一定會造成重複副作用。

用轉帳來體會：如果「轉帳」這個動作被設計成冪等的（例如帶上一個唯一的轉帳編號，系統看到編號就知道這筆處理過、直接跳過），那麼無論系統壞幾次、重播幾次，這筆錢最終都只會轉一次。

關鍵一句話

不可逆的動作，必須冪等；冪等，才談得上 exactly-once。

記住這個因果鏈：**動作不可逆 → 不能重跑 → 必須冪等 → 冪等才保證 exactly-once**。下一節選 DBOS 時會直接用到它——DBOS 要求你把 runtime 包成「冪等的 step」，就是為了讓失敗重播時能安全地跳過已經做過的步驟。
