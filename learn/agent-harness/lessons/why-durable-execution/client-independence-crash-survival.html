執行要活得比任何觀察者久

Step 1/4 · durable execution 的定義與三件事：checkpointing、fault tolerance、resilience

學習目標

能說出 durable execution 的定義——執行要能抗故障、獨立於任何觀察者而存活——並用「ChatGPT 回覆到一半斷線」的場景拆出 checkpointing、fault tolerance、resilience 三個要件。

先想像一個中斷的對話

你正在跟 ChatGPT 對話，它正在「想」——模型吐字吐到一半，你的 Wi-Fi 突然斷了。幾秒後連線回來，你希望發生什麼事？

答案幾乎是直覺的：接續剛才那段對話（resume that session）。你不會期待它從頭開始、也不會期待它假裝剛才沒問過。你會預期：對話被「存」在某個地方，斷線只是暫時看不到，它一直在繼續。

再把場景翻轉一次：這次不是你的 Wi-Fi 斷，而是 OpenAI 自己的 server 掛了，然後重啟。你的期待還是一樣——接續那段對話。

這兩個場景指向同一個核心需求：那段執行的存在，不該取決於有沒有人在看它。不管是 client 先走、還是 server 先走，執行本身都該繼續活著。

這就叫 durable execution

上面這些需求，通通落在一個詞底下：durable execution（持久化執行）。它的意思是：

我們在執行一段東西，而這段執行必須「持久」——要有韌性（resilient），要能容忍故障（fault tolerant）。

拆成三個具體要件：

要件白話對應前面哪個場景
checkpointing（檢查點）把「做到哪一步」定期存下來，掉了才知道去哪接回覆到一半斷線，重連後知道接到哪
fault tolerance（故障容忍）出錯、當機也不會讓整件事歸零server 掛掉重啟後照樣能繼續
resilience（韌性）系統壞了能自己恢復、自己站起來斷電 / 斷網後自動回到正常狀態

三個詞常常一起出現，但各有各的職責：checkpointing 回答「記錄在哪裡」，fault tolerance 回答「壞了還能活」，resilience 回答「壞了怎麼自己好」。合起來，就是「執行要活得比任何觀察者都久」。

這一步把你推進分散式運算

一旦你要做到「client 死了不算數、server 死了也不算數」，你就踏進 distributed computing（分散式運算） 的領地了——多個系統跑在多個 process 上，彼此互相依賴。一台機器上的 process 死了，必須不影響另一台機器上的結果；彼此透過網路溝通，而網路本來就是不可靠的。

對一個 agent 來說，這不是可選的額外加分，而是它「能不能被人放心使用」的分水嶺。一個 agent 的執行如果綁死在某個 client 身上——client 一關網頁、一斷線，agent 就停擺、失憶、甚至半途而廢——那它就只能當玩具。

關鍵一句話

整個持久化設計的總需求，可以在這裡定下來：

Execution should be independent of any consumer, any client.

執行獨立於任何消費者、任何 client。記住這句話。後面三步——CI/CD 類比、冪等／exactly-once、選 DBOS——都是在替「怎麼做到這件事」找方法，而這句話是它們共同的源頭。
