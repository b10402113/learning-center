審批是 harness 的責任，不是 LLM 的請求

Step 1/4 · Human-in-the-Loop 審批

學習目標

能解釋為什麼 human-in-the-loop 審批必須是決定性的 harness 層行為——用工具選項或 map 標記「哪些工具要審批」、在 harness 內按名稱查配置並暫停——而不是在 prompt 裡求 LLM 照做。

一個回不去的動作

課程到這裡，billing agent 手上有一支 issueRefund：它會真的把錢退出去。這是 irreversible（不可逆）的動作——一旦執行就回不來。前面幾節把它的副作用包成 durable step，確保它不會被重複執行；但 durable 只保證「只做一次」，不保證「該不該做」。錢要動，還是得有人點頭。

這就帶出 human-in-the-loop 的問題：某些工具在執行前，必須先取得人類批准。

天真的版本：把 process 掛在那裡等

第一直覺通常是直接 await：

const approved = await askUser(); // 把 process 撐開等；重啟就死；等不了幾天

這在 demo 能用，在生產會壞。一個人類可能三十秒後批准，也可能三天後才看到。你不可能讓一個 process 撐開三天；而且只要中途 crash，整段任務就跟著消失。人類的暫停必須是一個第一級的、durable 的 workflow 狀態，而不是一個卡住的函式呼叫。

決定性：像 handoff 一樣寫進 harness

那審批該長在哪裡？答案和 handoff 一模一樣：harness 層，而且是決定性的。

回顧 handoff 的做法——不是寫一段 prompt 拜託模型「要換手時請自己換」，而是 harness 看到模型呼叫了 handoff 這支工具，就攔截它、切換當前 agent。模型只負責提議，harness 負責執行。審批也是同一招：

不是「拜託 LLM 在動錢之前先問人」，而是「harness 偵測到這支工具要審批，就直接暫停」。

Scott 在課裡講得很直白：這「非常像我們讓 handoff 變成決定性的」——它是 harness 的一部分，「不是你在求 LLM 做某件事」，而是「我在 harness 層偵測到這個 tool call，因此我得做點什麼」。

怎麼標記「這支工具要審批」

要讓 harness 能決定性地判斷，你需要一份「哪些工具有特權」的清單。兩種常見做法：

做法長相備註
harness 端的 map／Setconst NEEDS_APPROVAL = new Set(["issueRefund"]);課程採用；清單集中在 harness，一眼看盡
SDK 的 tool 層設定工具自帶 needsApproval 之類的旗標很多 SDK 支援；配置跟著工具走

不論哪種，偵測的邏輯都一樣：你有這支工具的名字，去查它的配置，問一句「這支需要審批嗎？」——是，就暫停。課程的程式碼就寫在 runtime 的工具分派處：

if (call.toolName === "handoff") { /* 攔截、切換 agent */ }
else if (NEEDS_APPROVAL.has(call.toolName)) { /* 人類審批閘門 */ }
else { /* 直接執行 */ }

注意那個位置：它和 handoff 是同一個分支結構。這不是巧合——「模型提議、harness 決定」正是這整門課的主旋律。把關卡放在工具分派處，模型就不可能繞過：它只能提議呼叫 issueRefund，而 harness 永遠是那隻真正執行的手。

關鍵一句話

審批是 harness 的承諾，不是 prompt 的請求。特權動作的閘門要寫在程式裡，不能拜託模型自律。
