Stream Part 轉成 Harness 事件

Step 4/5 · 把 provider 的 chunk 翻譯成客戶端的事件

學習目標

能把 stream part 的類型對應到 harness 事件（modelDelta / toolRequest / toolCompleted / workflowFailed），並說出為什麼要一併送出工具參數。

問題：一堆亂流，各要不同待遇

上一課看到，fullStream 流出來的是各種不同的 chunk。問題來了：你的 UI 不能把這些 chunk 原封不動地丟上畫面——純 token 要「逐字長出文字」，工具呼叫要「跳出一張卡片」，錯誤要「紅字警示」。三種 chunk，三種待遇。

所以迴圈裡要做一件翻譯工作：根據 part.type，把 provider 的原始 chunk，轉成 harness 自己的事件。這個轉換用一個 switch 完成：

for await (const part of result.fullStream) {
  switch (part.type) {
    case "text-delta":
      emit({ type: "modelDelta", workflowId, text: part.text });
      break;
    case "tool-call":
      emit({ type: "toolRequest", workflowId, toolCallId: part.toolCallId, name: part.toolName, args: part.input });
      break;
    case "tool-result":
      emit({ type: "toolCompleted", workflowId, toolCallId: part.toolCallId, result: part.output });
      break;
    case "error":
      emit({ type: "workflowFailed", workflowId, error: String(part.error) });
      break;
  }
}

四種 part，四個事件

part 類型它是什麼轉成的事件UI 拿它做什麼
text-delta一個 token（正在生文字）modelDelta在畫面上一字一字長出回覆
tool-call模型要求執行某個工具toolRequest跳出工具呼叫卡片，秀出工具名與參數
tool-result工具跑完的回傳值toolCompleted把結果填回卡片、標記完成
errorprovider 出錯（限流、掛掉等）workflowFailed紅字告知這趟工作失敗了

這裡的 emit 在概念上就是把這些事件一路推到感興趣的客戶端。至於底層用 WebSocket、輪詢（polling）還是第三方服務，課程明說不重要——那是傳輸層的實作細節，隨平台而變。唯一必要的核心是：你呼叫了模型，而有一群客戶端關心這個進行中的非同步過程，你得持續更新他們。

為什麼要把參數也送出去

有一個細節很容易被當成「多餘」：toolRequest 事件裡，除了工具名，還順手塞了參數 args。為什麼？想一個場景：

假設 agent 有個「寄出回覆」工具，而這工具日後要接上「人類審批」——要先問過使用者、批准了才准發。試想審批畫面只跳出「agent 想寄回覆，同意嗎？」卻不顯示它想寄的那句話，你敢批嗎？不敢。你連內容都不知道，怎麼判斷要不要放行。

這就好比一封「要轉帳 5000 元」的確認信，卻不告訴你金額是多少——你不可能批准。所以參數要一起送：讓審批的人真的看得到「這一步會發生什麼」。把參數送出去，是把審批從「盲目」變成「知情」的前提。
