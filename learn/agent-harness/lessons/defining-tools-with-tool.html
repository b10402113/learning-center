用 tool() 定義工具：description、schema、execute

Step 2/4 · 工具與 Agent 的契約

學習目標

能用 AI SDK 的 tool() 寫出一個工具——寫清楚 LLM 會看到的 description、用 Zod 定義帶 .describe() 的 input schema、以及拿到驗證後參數的 execute——並實作 search_knowledge_base 與 classify_item。

一支工具的三段式結構

上一節看到模型靠「描述文字」認識工具。現在把這個認識落到程式碼：AI SDK 的 tool() 幫我們把一支工具定義成一個物件，它有三個關鍵部分，各司其職：

部分給誰看做什麼
description模型一段文字，模型據此決定要不要叫這支工具、該怎麼用它
inputSchema模型 ＋ 執行期用 Zod 定義的 schema，是「被強制的契約」——執行函式永遠收到符合規格的參數
execute執行期真正動手的地方；收到驗證過的參數，回傳的結果會被餵回模型

先看第一支工具——搜尋一個知識庫。課程裡做了一個假的知識庫，放著退款、帳單、匯出、定價等條目，工具用最土的方式（記憶體內的關鍵字比對）去查：

import { tool } from "ai";
import { z } from "zod";

export const tools = {
  search_knowledge_base: tool({
    description: "在支援知識庫中搜尋與顧客問題相關的條目",
    inputSchema: z.object({
      query: z.string().describe("要搜尋的關鍵字或短語"),
    }),
    execute: async ({ query }) => {
      const results = searchKB(query); // 小寫子字串比對
      if (results.length === 0) {
        return { note: "沒有精確配對，請用你的最佳判斷", articles: [] };
      }
      return { articles: results, count: results.length };
    },
  }),
};

注意 inputSchema 裡那一行 .describe("要搜尋的關鍵字或短語")：這跟 description 一樣，是另一條「讓模型讀得到」的線索。schema 欄位上的描述，是專門針對單一參數的說明——當欄位名稱和實際資料對不上時特別重要。例：某欄位叫做 item_id，模型多半猜得出是什麼，就不用寫；但要是資料裡那個 ID 其實叫別的，就得用 .describe() 把對應關係講清楚。

用 Zod enum 把參數限死在幾個值

第二支工具把參數限制得更緊。Zod 不只能聲明「這是字串」，還能聲明「只能是這幾個值之一」：

classify_item: tool({
  description: "把一個工作項目分類到 billing / technical / sales / other",
  inputSchema: z.object({
    item_id: z.string(),
    category: z.enum(["billing", "technical", "sales", "other"]),
  }),
  execute: async ({ item_id, category }) => {
    return { ok: true, item_id, category }; // mock：讓 agent 以為事情發生
  },
}),

這裡 category 被限在四個值之一。若模型想給一個不在清單裡的值，這份 schema 會在執行前就把它擋掉——這就是「被強制的契約」的意思：execute 永遠只看得到合法參數。

另一個重點：execute 的回傳值會被完整地餵回模型，成為它下一步判斷的依據。所以 execute 裡其實做什麼都行——查資料、算數字、甚至呼叫另一個 LLM——只要最後回傳，模型就看得到。這是你和模型之間的「回傳契約」。

為什麼這支 agent 故意做得很鳥

你可能注意到了：classify_item 的 execute 只是回個 { ok: true }，根本沒真的分類；工具名稱、分類值也都取得隨隨便便。這不是偷懶，而是刻意如此。這門課的主角是 harness，不是 agent——agent 只是一個拿來「測試 harness」的假利器（fixture）。它表現超爛也沒關係，重點是包住它的那層環境。分類值要跟知識庫對得上、工具語句要順不順，都只是為了讓這個假利器在測試時好觸發而已。

把工具能寫出來之後，下一節會碰一支真正有後果的工具——它真的會寄出一封回覆。到那時你就會看到：這些「description 文字」和「schema 欄位」是多麼容易被繞過，真正的強制不能寫在文字裡。
