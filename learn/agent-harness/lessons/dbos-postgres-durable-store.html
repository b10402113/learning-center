選擇 DBOS + Postgres 與取得資料庫

Step 4/4 · database-backed 的 DBOS，跟 service-based 引擎比一比，再拿一個 Postgres

學習目標

能說出 DBOS 如何用 workflow ID 記錄/重播 step 的輸入輸出、讓失敗的工作流跳過已完成的工作、且 step 必須冪等；比較 DBOS 與 Temporal／Cloudflare／Inngest／Upstash／Vercel Workflows，並用 Neon 取得一個 Postgres 資料庫。

把 runtime 包成「被記錄的 step」

前面三步把需求講透了：執行要獨立、要能從斷點接續、不可逆動作要冪等。現在要選一個工具來落地。課程選的是 DBOS——一個用 Postgres 當骨幹、讓你能建立「持久化 workflow（工作流）」的框架。

它的運作方式，就是本章要實現的合約：

把 runtime 的每一步，包成 DBOS 的 step；每個 step 的輸入、輸出都被記錄進資料庫。

這樣一來，如果某個工作流跑到一半失敗了，要重跑的時候，DBOS 不需要從頭來——它會查閱每個 step 的記錄，發現「這個 workflow ID 的這一步，我已經做過了」，就直接跳過。這正是第二步 CI/CD 那套「單獨 retry 一個 stage、不重跑前面 stage」的機制，只是現在由資料庫來背書。

你的責任：讓 step 冪等

注意一句關鍵分工：

DBOS 負責記錄與重播；你負責讓每個 step 冪等。

如果某個 step 被重跑，它必須給出一樣的結果——這是上一步講的冪等。DBOS 把「跳過已完成的 step」這件事做得很方便，但它無法替你保證你寫的 step 本身不會產生重複的副作用。讓 step 冪等，是分散式系統裡通用的功課，也是接下來實作時你每一條 step 都要過腦的檢查。

除了記錄 step 的輸入輸出，DBOS 還會幫你記一份 event log（事件日誌）：你 fire 出去的每一個事件都留底，形成一份歷史紀錄。用 Drizzle（一個 ORM／SDK，負責跟 Postgres 對話）把這些全部寫進 Postgres。

為什麼選 DBOS，而不是那一票 service

「持久化執行」這個需求，市場上有一大堆選擇，而且它們做的事本質上都是同一件事——給你 durable execution。差別在於你用起來的成本：

引擎性質對你的摩擦
Temporal獨立服務，業界最大咖要另起服務、概念重，沒後端經驗很吃力
Cloudflare / Inngest / Upstash / Vercel Workflows託管服務要付費、要接額外一個 service
DBOSdatabase-backed 框架幾乎不用改 code，直接掛上你的 Postgres

選擇 DBOS 的兩個理由非常務實：

  • 不用改 code：你幾乎不用重構現有的 runtime，把動作標成 step 就行。
  • backed by database：它不是另一個要你付費、要你跑 Docker 的獨立服務，就是掛在你已經有的 Postgres 上。

對「大部分心思想放在 harness 本身、不想陷在後端基礎設施」的學習者來說，DBOS 用最少的摩擦，換來持久化——這正是課程挑它的原因。

取得一個 Postgres：Neon

DBOS 需要一個 Postgres 資料庫。你本機已經有 Postgres 的話，直接拿來用就好。沒有的話，最快的管道是 Neon：

  • 到 neon.new，點「try it in the browser」。
  • 它會給你一段連線 URL——免費、可用 72 小時、不用註冊帳號。
  • 把這段 URL 貼進 .dev.vars 或 .env，命名為 DATABASE_URL。

有一個小坑要特別標出來：貼之前，把 URL 裡的 -pooler 拿掉。

DATABASE_URL 去掉 -pooler：那是資料庫連線池（pooling），跟 DBOS 一起用會變複雜。

-pooler 那段代表 Neon 的 connection pooling 版本；DBOS 直接連非 pooling 的版本才簡單。去掉它，你就拿到能跟 DBOS 合作的資料庫連線了。

把四步收起來

到這裡，「為什麼需要持久化執行」這條線就打通了：執行要獨立於任何觀察者（第一步）→ 用 CI/CD 當心智模型看懂 retry/replay/斷線恢復（第二步）→ 不可逆動作逼出冪等與 exactly-once（第三步）→ 選 database-backed 的 DBOS、用 workflow ID 記錄重播、拿一個 Postgres 開工（第四步）。下一步就能真的動手，把 runtime loop 接上 event log 跟 DBOS workflow。
