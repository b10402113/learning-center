何時用 Claude Code、何時自己建

Step 4/5 · 買現成的 coding harness，還是自己寫 programmatic agent

學習目標

能在「用現成的 coding harness（Claude Code / Codex）還是自己寫 programmatic agent」之間做判斷，並說出「最好的 harness 勝過最好的模型」這條理由。

兩種同桌的「harness」

你可能天天在用 Claude Code、Codex、opencode 這類工具。它們其實不是「模型」，而是包在模型外面的 harness。把裡面的模型拆掉，剩下的就是 harness：終端機 UI、skills 實作、檔案標記（file-mention）的互動、對話變長時的自動壓縮（auto-compaction）、以及不問你就自己開 sub-agent 的能力。

同樣一套底層模型，外面可以長出完全不同的工具：OpenCode、OpenClaw、Hermes、Pi——這些全都是同一批模型的 harness。這就是下一段要講的重點：差別不在模型，在 harness。

第一原則：最好的 harness 勝過最好的模型

一個用「比較差的模型」但「比較好的 harness」的產品，可以打敗「頂級模型配爛 harness」的產品。因為模型只能決定「單次回答有多好」，harness 卻決定「這件事能不能被可靠地完成、記住、執行、復原」。業界裡，harness 工程和 eval 是兩個最有價值的 AI 技能，大約佔了九成的工作量——而不是「換一顆最新的模型」。

判斷框架：什麼時候伸手拿現成的

如果任務是跟寫程式相關、而且需要一台機器——Bash、檔案系統、終端機、repo——那直接用現成的 coding harness，別自己造一個。它們最好用的場景是：寫程式、資料分析、做原型。這幾件事對應的 harness 已經被磨得很成熟。

但注意它的天花板：Claude Code 這類工具的 harness 是固定的，你能動的桿子只有三個——prompt、skills、MCP server——而且這三樣本質上都只是「塞不同的 context（上下文）」。你改不動它的執行機理。

判斷框架：什麼時候自己寫

反過來，以下訊號出現時，你大概需要一個 programmatic agent（用 SDK／API 自己寫的 agent）：

  • 做的是產品而非腳本——有很多用戶、要在生產環境跑、而且不是 coding 用途。
  • 需要確定性的工作流——現成 harness 太通用，你無法強制它走一條固定流程。
  • prompt 難以 eval——現成工具的 prompt 你動不了多少，也量不出來它有沒有變差。

最後一招：你有什麼就優先做什麼

自己建 harness 時，不必一次做齊全部能力。一切取決於你想交付的目標體驗：

你想交付的體驗優先補的能力
常駐在線的交易機器人自癒、護欄、審批、PII／資安、自我評估迴圈
簡單問答機器人可能連持久化都不用

真正不可少的地基只有兩樣：記憶 + 工具呼叫。持久化執行在很多場景需要、但不是每個 agent 都要（一個純「訊息進、回覆出」的 agent 就不要）。一句話收斂：模型能發揮多少，是由 harness 允許的範圍決定的。
