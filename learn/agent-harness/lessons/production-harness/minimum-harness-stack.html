最小可上線的 Harness 清單

Step 1/5 · 三樣非有不可，一樣可以延後

學習目標

能排出 chat agent 上線的最小 harness 清單與建置順序——tool calling、自己掌握的記憶、記憶壓縮——並說明 durable 解耦為何可以延後、turn limit 如何防止迴圈跑飛。

問題：只能留三樣，留哪三樣？

前面幾堂課你已經把整個 harness 蓋起來了：持久化迴圈、沙箱、記憶壓縮、handoff、監督、審批。現在換一個更現實的問題——如果今天就要把一個聊天型 agent 推上線，哪些層是非有不可、哪些可以晚點再補？

答案出乎意料地樸素：tool calling、由你自己掌握的記憶、以及記憶壓縮。剩下的能力不是不重要，而是它們的優先序取決於你要交付的體驗；其中 durable execution 是最常被高估、也最該被延後的一項。

第一樣：tool calling——免費，但只是入場券

工具呼叫在現在每個 SDK 裡幾乎都是免費附帶的。以 AI SDK 為例，你用 tool() 定義名稱、description、schema 與 execute，把工具集交給 streamText，它就會自動幫你跑工具迴圈，把模型的工具呼叫、執行結果、下一輪回應串起來。

免費不代表不重要——它是 agent 能「動手」的前提。正因為免費，它也不是差異化的地方：你不會因為用了工具呼叫就打贏別人，只會因為沒有它而根本做不出 agent。

第二樣：記憶——免費的是「有」，貴的是「存在哪」

SDK 大多會幫你維護一個 messages 陣列，感覺像免費的記憶。但那個陣列只活在單一 process 的記憶體裡：server 一換、process 一重開、或同時有多個使用者，它就不見了。

真正要花力氣的是把歷史持久化到你自己控制的儲存——課程裡就是 event_log 資料表加 Postgres（Neon），用 Drizzle 讀寫。控制權在你手上，你才能決定要保留什麼、丟掉什麼、什麼時候壓縮。這也解釋了為什麼「用供應商的對話狀態」和「自己存歷史」是兩種完全不同的產品成熟度。

記憶的分水嶺不是「有沒有記憶」，而是「記憶的主人是誰」。

第三樣：壓縮——歷史一定會長到爆

對話只會越來越長，context 只會越積越多。沒有壓縮，遲早撞到 context 上限，agent 不是變笨就是直接壞掉。

做法是把太舊的輪次交給 LLM 摘要成一段短記憶，只保留最近幾輪的原文——也就是以「輪（turn）」為單位的滑動視窗。課程把摘要包成一個 durable step，並發出 memory_compacted 事件，讓你能在 inspector 上親眼看到壓縮真的發生了、壓掉了多少。

可以延後的那一樣：durable execution

durable execution 解耦的是「run 活在哪裡」：run 不再依附發出請求的那個 client。最直觀的症狀是 SSE——使用者重整頁面時，如果 run 綁在那條連線上，工作就斷了；durable 之後，重連只是重新訂閱事件流，run 照樣往前跑。

這件事很重要，但對一個聊天型 agent 來說，可以晚一點再加。先把記憶與壓縮做對，使用者的體驗損失有限；等你要做「關掉頁面也要完成、完成後通知我」的工作時，它才會從選配變成必備。

別忘了最低成本的保險：turn limit

大約十步的上限。模型偶爾會卡在工具迴圈裡來回鬼打牆，一個 turn limit 就能讓它停下來，不至於無限燃燒 token。在 AI SDK 裡就是 stopWhen / maxSteps 這類設定。

把清單排成建置順序

順序能力為什麼在這裡
1tool callingSDK 免費附帶，是 agent 能動手的前提
2記憶持久化到自己控制的儲存唯一能決定保留與丟棄的地方
3記憶壓縮歷史必然長過 context 上限
3.5turn limit（約十步）防止工具迴圈跑飛的最低成本保險
4（可延後）durable execution解耦 client；聊天型 agent 可先不做

AI SDK 已經幫你準備了大半

tool calling、工具迴圈、串流、結構化輸出，AI SDK 都給你了。真正要自己動手的不多：把記憶搬進自己的資料庫、寫壓縮、設一個 turn limit。這也是為什麼「會 harness engineering」比「會挑最新模型」值錢——模型大家都叫得到，harness 才是你自己的。

但這份清單是「chat agent」這個體驗的答案，不是普世真理。下一步要學的是：換一個體驗，這份清單會怎麼整個換一組。
