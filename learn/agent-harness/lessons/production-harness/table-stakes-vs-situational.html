Table stakes 與 situational：從目標體驗反推

Step 2/5 · 先寫下體驗，再決定要哪幾層

學習目標

能從要交付的體驗反推 harness 需求，分辨 table stakes（tool calling、記憶）與 situational（durable、guardrail、approval、PII、自評迴圈），並用 trading agent 的例子說明同一份清單為何不能套用到所有 agent。

為什麼不能照抄清單

前一步給了 chat agent 的最小清單。但如果把那份清單原封不動套到每一個 agent 上，很快就會出事：有些能力你根本用不到，有些能力少一個就拿不出門。問題不在清單本身，而在「清單是果，不是因」。

決定 harness 要長什麼樣的，其實是你要交付的體驗。先想清楚使用者會經歷什麼，再回頭列出「為了讓那個體驗成立，系統必須做到哪些事」——harness 的需求是這樣推出來的，不是從一份 checklist 抄下來的。

先寫體驗，再列需求

實務上可以照三步走：

  1. 描述體驗：使用者會怎麼用這個 agent？用多久？可以等嗎？會出錯的代價是什麼？
  2. 找出會壞的地方：在這個體驗下，系統在哪裡斷掉、出錯、或讓使用者失望？
  3. 反推需要的層：每一種壞法對應一層 harness 能力，只補真的會用到的。

例子：24 小時盯盤的 trading agent

設想一個「一直開著、幫你盯盤甚至在條件成立時自動出手」的 trading agent。這個體驗立刻逼出一整組需求，而它們多半不在聊天型 agent 的清單上：

需求這個體驗為什麼逼出它
自癒（self-healing）它必須 24 小時活著，掛掉沒人會在旁邊按重啟
護欄（guardrails）不能讓它做出災難性的交易，能力邊界要能強制
審批（approvals）不可逆的動作要有關卡，由人放行
PII / 安全它會碰到帳務與個資，外洩的代價極高
自評迴圈（eval loop）長期自動運作需要它能自判、自我改進

注意這些能力之間不是並排的選項：自癒要 durable execution 當底，審批要用 durable 的暫停／恢復來實作。也就是說，體驗會連鎖地決定一整串需求，而不是讓你挑幾個形容詞。

Table stakes 與 situational

把所有 agent 攤開來看，可以粗略分成兩堆：

分類能力判準
Table stakes（非有不可）tool calling、記憶幾乎任何 agent 少了它就不成立
Situational（看情況）durable execution、sandbox、approval、PII、自評迴圈取決於體驗：誰在用、跑多久、錯了會怎樣

最容易搞錯的是 durable execution：它不是普世的 table stakes。對一個「送一則訊息、拿一則回應」就結束的 agent，durable 完全是多餘的；但對 trading agent 這種長時、不可逆、不能斷的體驗，它卻是其他能力的必要地基。同一層能力，在不同體驗裡的地位天差地遠。

自評迴圈：把 eval 接進來

trading agent 那份清單裡藏了一個容易被忽略的項目：讓 agent 自己判斷「這次做得好不好」，再據此調整。這不是要模型自言自語，而是把評測（eval）接進系統：先定義什麼叫好、用可重複的方式量測、再把量測結果回饋給改進。有了自評迴圈，你才不是憑感覺調 prompt，而是有一個訊號告訴你改動到底有沒有效。

一句話帶走

模型能發揮到什麼程度，取決於 harness 允許它做到什麼。
——而 harness 允許什麼，取決於你要交付的體驗。

所以看到任何一個 agent 產品，不要問「它有沒有 durable」；要問「它承諾什麼體驗，而那個體驗需要哪幾層」。這正是這個節點要練的判斷力。

小練習：三個情境

  • 客服 FAQ bot：單輪問答、答案錯了頂多重問一次——table stakes 只有工具＋記憶，durable 不必。
  • 退費助理：會動到錢、動作不可逆——table stakes 之上一定要加 approval 與審計（event log）。
  • 研究型背景 agent：跑數十分鐘、跨頁面、跨重啟——durable 從選配直接升為必備。
