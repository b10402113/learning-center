無限／背景 agent 與 inbox

Step 4/5 · 沒有對話的 agent，要怎麼跟人互動

學習目標

能描述無限／背景 agent 的運作模型——給一個任務或等一個事件、無限地跑、用 inbox 對外交互——並說明為何它不需要 messages API，以及真正難的是 eval 與約束。

把「對話」拿掉之後

我們習慣的 agent 都長在同一個框架裡：你一句、它一句，messages 陣列越來越長，這就是「對話」。但 agent 不一定要這樣運作。

無限／背景 agent 是完全不同的形態：你不是跟它聊天，而是給它一個任務，或讓它待命等一個事件，然後它就一直跑下去，需要你的時候才來找你。它沒有「對話」可言，因此整個 chat 的框架——messages 陣列、逐輪回應、SSE 串流——大多用不上。

兩種啟動方式：給任務，或等事件

  • 任務驅動：你丟一個目標進去（「監控這批服務」、「研究這個市場並持續更新」），它就自己去跑，跑到完成或持續維持。
  • 事件驅動：它平常待命，等外部事件叫醒它——webhook、告警系統、佇列訊息。事件一到才開始工作。

兩者的共同點是「無限」：這類 agent 的生命週期不是一次問答，而是持續存在、反覆被喚醒的存在。

durable 是入場券，不是選配

因為它活在背景、活得比任何連線都久，durable execution 在這裡不是可以延後的那一項，而是入場券：workflow 要能接受任務、暫停、被事件喚醒、繼續跑，而且每一步都要能跨重啟存活。

換句話說，前一步那條「durable 什麼時候從選配變必要」的線，在這裡被直接跳過——背景 agent 沒有「先不做 durable」的選項。這也讓 durable 成為理解這個形態最好的切入點。

不需要 messages API

一般 agent 靠 messages API 維護對話歷史：你送一則、模型回一則。但背景 agent 沒有來回對話，也就不需要那套 API。它需要的不是「對話歷史」，而是任務狀態：這個任務現在跑到哪、上次事件處理的結果是什麼、下一步要做什麼。

如果硬把對話 API 套上去，你會得到一個假裝在聊天的東西，反而把真正的狀態管理藏起來。正確的做法是讓事件日誌與 durable workflow 當狀態的家，而不是逼 agent 演一場對話。

互動模型：inbox

那它要怎麼跟人互動？答案是 inbox（收件匣）：agent 主動把東西投遞到你的 inbox，你從 inbox 回覆，它再繼續。投遞的內容通常是這幾類：

投遞內容什麼時候出現
問題它缺一個只有你知道的資訊
審批它要執行一個不可逆的動作，需要你放行
選項有多條路，它要你挑一條

注意這正是前面 human-in-the-loop 的 approval gate 的泛化：DBOS 的暫停／恢復機制，原本用來等一個批准，現在變成一個通用的「投遞—等待—回覆」通道。訊息方向也反了過來——從「使用者在聊天框打字」變成「agent 主動來敲你」。

難的不是做，是做好

把這套拼起來並不難：durable workflow 是地基，approval gate 是互動通道，事件日誌是狀態的真相。真正難的兩件事是：

  • 約束（constraining）：一個無限跑、會自己動手的 agent，如果沒有護欄與審批，出錯的幅度也會是無限的。
  • 評測（evaluating）：沒有對話可以讓你看懂它為什麼這樣做，你必須靠 eval 才能知道它到底做得好不好。
把它做出來很容易，把它做好很難。

所以這個形態的門檻不在「能不能跑」，而在你有沒有能力衡量它、約束它。這也是為什麼前一步的 eval 迴圈、這一路學的 guardrail 與 approval，到了這裡全部變成核心議題，而不是附加功能。

回頭看：這是你已經有的積木

有趣的是，背景 agent 不需要任何新技術——它是你已經做過的東西換一個組裝方式：durable workflow 當心臟、approval 的暫停／恢復當 inbox、event_log 當狀態、guardrail 當煞車。你缺的只是把「對話」這個前提拿掉，然後重新想清楚人與 agent 的互動該長什麼樣。

如果你手上有一個自己的 agent runtime，這一步其實是最好遷移的：它要的不是新的函式庫，而是把 durable 執行與暫停／恢復的語意做對。
