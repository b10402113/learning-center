送出的工具：護欄不能只寫在 prompt

Step 3/4 · 工具與 Agent 的契約

學習目標

用 send_reply 這個真的會寄出草稿的工具，說出為什麼「未經使用者同意前不要使用」這類護欄寫在 description 或 prompt 文字裡必然失效，以及真正的強制必須落在 harness 層。

一支真的會寄信的工具

前兩節的工具都無害——搜尋知識庫、分類，就算跑錯也不會怎樣。現在加一支有真實後果的工具：它會把草擬好的回覆真的寄出去：

send_reply: tool({
  description: "把草擬好的回覆寄給顧客",
  inputSchema: z.object({
    item_id: z.string(),
    message: z.string(),
  }),
  execute: async ({ item_id, message }) => {
    await sendEmail(item_id, message); // 真的寄出，不是 mock
    return { ok: true };
  },
}),

問題立刻浮現：一個 agent 如果同時有「草擬回覆」和「寄出回覆」兩支工具，而它的任務又要求它「處理完這件事」，那麼它很可能自己決定寄出——因為寄出才能滿足目標。使用者根本沒機會review那封信，信就出去了。沒有人會信任這樣的 agent，可是我們的裸迴圈就是會真的把它寄出去。

寫在文字裡的護欄，必然失效

你第一直覺可能是：那我在 description 裡加句警告不就好了？

description: "寄出回覆。⚠️ 除非使用者明確同意，否則絕對不要使用這支工具"

這行字不會有任何用。原因很根本：對模型而言，description 只是文字，不是限制。它是機率性的推理引擎，會權衡「這段警告」和「把任務做完」哪個更重要——而當它的目標就是要寄出才算完成時，警告會被它合理地忽略掉。把護欄或安全規則實作在文字裡，最終都會失效。這不是模型不聽話，而是你把一道必須是「硬性強制」的閘門，交給了只會「軟性建議」的媒介。

真正的強制，要寫進 harness

那這道閘門該長在哪裡？答案是：harness 層。harness 是介於模型和工具執行之間的程式，它可以在模型「說出要叫 send_reply」和「send_reply 真的執行」之間，插進一道硬性的檢查。

可以這樣想：模型永遠只負責「提議」要叫哪支工具，harness 永遠是「執行」的那隻手。當模型提議寄出時，harness 可以先看清楚這是哪一類工具——是唯讀的搜尋，還是會造成後果的寄出——再決定放行、暫停、或必須等人類批准。這正是工具清單可以做成的樣子：把「安全工具」和「危險工具」分開放，runCode 走沙箱、sendReply / issueRefund 這類有副作用（side effect）的工具，由 harness 擁有的執行器（executor）去跑，而不是讓模型說的算。

後面課程正是沿著這條線補下去的：dangerous 工具會被擋在一個「人類批准」的閘門後面（human-in-the-loop），而那些「寄出／退款」的副作用會被包成不可重複執行的持久化步驟（durable step），確保它只會發生一次、且崩潰後不會重來。所有這些，都不是靠某段好聽的 prompt 文字，而是靠harness 裡的程式邏輯。

到這你應該能總結出這節最關鍵的一句話：prompt 是建議，harness 是承諾。能造成後果的動作，永遠不能只拜託模型「不要亂用」。
