runtime 攔截 handoff：橫向控制權轉移

Step 3/4 · handoff 工具、currentAgent、攔截、交換與 durable event

學習目標

能定義 handoff 與 issueRefund 工具，說明為何 handoff 必須由 runtime 攔截（agent 無法把自己換掉），並追蹤 currentAgent 的攔截、event 與交換流程。

開場：handoff 是一個 agent 做不到的動作

前一步有了兩個 agent，但沒有任何機制讓 triage 把控制權交給 billing。這裡有個很反直覺的重點：這不是 agent 自己能完成的動作。agent 活在「自己的」context 與迴圈裡，它無法把自己從這段 context 移除、再換另一個 agent 進來。能決定「現在跑的是哪個 agent」的，只有外面那一層——runtime。

所以 handoff 要拆成兩半：agent 那一半只負責表達意圖（呼叫一個工具），runtime 那一半負責真的換人。控制流的原語住在 harness，不住在 LLM。

先造兩個工具：issueRefund 與 handoff

兩個工具都用 zod 定義輸入 schema，但結局完全不同。

issueRefund 是一個標準工具——它有 schema、有 description，但刻意沒有 execute：

issueRefund: tool({
  description: "Issue a refund to the customer. Irreversible. Moves real money.",
  inputSchema: z.object({
    customerId: z.string(),
    chargeId: z.string(),
    amountCents: z.number(),
  }),
  // 沒有 execute —— 實際執行在 runtime 的 switch 裡，
  // 這樣才能被包進 workflow step（持久化）。
});

沒有 execute 是為了把執行權收回 runtime：只有 runtime 能把它包進 workflow step，於是「退款」變成一個可被記錄、可被跳過重播的 durable 動作。

handoff 則記錄「要轉給誰」與「為什麼轉」：

handoff: tool({
  description: "Hand the conversation off to another agent.",
  inputSchema: z.object({
    to: z.string(),      // 目前只有 "billing"
    reason: z.string(),
  }),
});

為什麼非得做成工具？因為沒有工具，agent 就沒有「說出我要轉」的管道。你只能另外做一個什麼都看、什麼都管的 micromanager agent 在旁邊盯場——一個把所有工具呼叫都拿來審核的監工。handoff 工具讓轉移變成 agent 主動、明確的一個動作。

為什麼 handoff 不能在 tools 的 switch 裡處理

runtime 有一份工具執行的 switch：呼叫 issueRefund 就在那裡回一個硬編碼的結果。但 handoff 故意不放進去。

如果 handoff 在工具層處理，結果只會回到「同一個 agent」的 context，那個 agent 仍然在場。

換句話說，在工具層處理的 handoff 根本不是 handoff，只是「同一個 agent 自言自語說我轉給別人了」。真正的轉移必須被拉到上一層——由 runtime 攔截，因為只有 runtime 掌握「哪個 agent 的迴圈正在跑」。這條原則不只用於 handoff：approval（人工核准）也一樣，不能讓 LLM 自己決定要不要走核准流程，而必須由 harness 在確定性的地方攔下來，這樣才會每次都一樣，不受模型幻覺影響。

currentAgent：唯一一顆可變狀態

Runtime 新增一個可變變數，預設指向入口 agent：

let currentAgent = triageAgent;

整個多 agent 的「現在是誰在跑」就靠這一行。handoff 要做的事，本質上就是改這顆變數的指向。同時，因為每個 agent 有自己的 prompt 與工具，迴圈裡兩處 buildContext 都要改傳 currentAgent.systemPrompt，modelTurn 也要多收一個 currentAgent.tools 參數往下傳給 streamText。漏改任何一處，每個 agent 就會共用同一份 prompt 或同一套工具。

攔截點：在執行任何工具之前先看名字

Runtime 在迭代這回合的 tool calls、要執行 step 之前，先做一次檢查：

for (const call of toolCalls) {
  if (call.toolName === "handoff") {          // 先攔截
    const to     = call.input.to ?? "";
    const reason = call.input.reason;
    const from   = currentAgent.name;
    // ...durable step + 換人 + 回填工具結果
  } else {
    // 原本的工具執行路徑
  }
}

因為 handoff 從來沒有註冊執行函式，這個檢查必須早於一般工具執行。小提醒：實務上會把 "handoff" 抽成常數或 enum，避免哪天打錯字就整條路由失效。

Durable event 與 agent 交換

攔到之後，按順序做三件事。

一、把 handoff 本身持久化。用 DBOS.runStep 包一個名為 handoff_step 的步驟，發出一個 agent_handoff 事件，帶著 workflow ID、from、to、reason：

await DBOS.runStep(async () => {
  emit({
    type: "agent_handoff",
    workflowId,
    from,
    to,
    reason,
  });
}, { name: "handoff_step" });

這樣 handoff 不是藏在某段記憶體裡的暗轉，而是一條 durable、可被 inspector 看到、UI 可訂閱的事件。誰轉給誰、為什麼轉，全部留底。

二、換人。就是一次查表：

currentAgent = agents[to] ?? currentAgent;

目的地存在就切過去；不存在（例如 to 打錯或空字串）就留在原地——一個安全、不會把工作流弄死的 fallback。

三、立刻回填工具結果。別忘了 handoff 對模型來說仍然是一次 tool call，而 tool call 的規定是：下一則訊息必須是同一個 tool call ID 的結果。這個放在下一步細講。
