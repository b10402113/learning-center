把 agent 變成資料：三個欄位

Step 2/4 · name + systemPrompt + toolSet，triage 與 billing，最小權限

學習目標

能把 agent 收斂成 name + systemPrompt + toolSet 三個欄位，做出 triage 與 billing 兩個 agent，並解釋最小權限（退款只給 billing、triage 只靠 handoff）為何勝過把每個工具發給每個 agent。

開場：從「一顆寫死的迴圈」到「一筆資料」

第一步決定了「要拆」，但拆的動作在程式碼裡長什麼樣？如果每個 agent 都要自己一套 runtime、自己的迴圈、自己的持久化，那拆 agent 就是一場重構災難。

這裡的做法是把「agent」降格成一筆資料。原本那個寫死的 workflow loop 被抽成一個 agent 定義，於是新增一個 agent 不是新增機械，而是新增一筆設定——runtime 那一層完全不用動。

Agent 的三個欄位

整份型別就只有這樣：

export type Agent = {
  name: string;
  systemPrompt: string;
  tools: ToolSet;
};

export const agents: Record<string, Agent> = {
  triage: triageAgent,
  billing: billingAgent,
};

三個欄位各有分工：

欄位它是什麼決定 agent 的什麼
name識別字，也是路由的鍵handoff 的 to／from，事件與 UI 都靠它
systemPrompt這個角色的職責與禁令它的行為、語氣、能做與不能做
tools（tool set）它被允許呼叫的工具子集它真正能造成什麼副作用
runtime、loop、DBOS 持久化、工具處理全部共用；每個 agent 只在這三個欄位上不同。

最後那個 agents 物件是關鍵：它把每個 agent 用 name 當 key 收在一張表裡。之後 runtime 只要拿一個字串去查表，就能切換「現在是誰在跑」——這正是下一步 handoff 的機制。

triageAgent：永遠的入口，但沒有退款權

第一個 agent 是 triageAgent。它是入口 agent（point of entry）：每一筆請求都先到它手上，它能處理的就處理，不能或不該處理的就轉出去。

export const triageAgent: Agent = {
  name: "triage",
  systemPrompt: `You are a support triage agent.
...
IMPORTANT: you are NOT allowed to issue refunds. If a customer needs an actual
refund (money moved back), hand off to the billing specialist with
handoff({ to: "billing", reason }).`,
  tools: {
    classifyItem: tools.classifyItem,
    runCode: tools.runCode,
    draftReply: tools.draftReply,
    sendReply: tools.sendReply,
    handoff: tools.handoff,
  },
};

注意它的工具清單裡沒有 issueRefund。它能「聊」退款，但碰不到錢。而 system prompt 裡那句 NOT allowed to issue refunds 不是裝飾——它是一個強制函式：把「退款」這件事從 triage 的能力範圍裡拿掉，逼它只能走 handoff。也就是說，「能不能做」同時被兩層鎖住：工具集不給它，prompt 再明白禁止。

billingAgent：持有特權工具的專家

第二個 agent 用同一套模式複製出來，只是換了名字、prompt 與工具集：

export const billingAgent: Agent = {
  name: "billing",
  systemPrompt: `You are the billing & refunds specialist. issueRefund is
IRREVERSIBLE and moves real money, so be careful — but it IS your job.`,
  tools: {
    runCode: tools.runCode,
    issueRefund: tools.issueRefund,
    draftReply: tools.draftReply,
    sendReply: tools.sendReply,
  },
};

對照兩個 agent 的工具表，差異一目了然：

工具triagebilling為什麼
classifyItem✓✗分類是入口的職責
issueRefund✗✓能動錢的高風險工具，只給專家
handoff✓✗轉出的能力；這一步只做 triage → billing 單向
runCode / draftReply / sendReply✓✓每個 agent 都需要的共用能力

共用能力：reply 工具為什麼每個人都有

仔細看：draftReply 與 sendReply 兩個 agent 都有。這不是偷懶，而是刻意的設計判斷——agent 必須能直接跟使用者收尾。如果沒有這兩個工具，agent 想回一句話都得先 hand off 給「專門回話的 agent」，那 handoff 就被濫用了。

當然有另一個選項：把「回覆」獨立成一個專門調校的 agent。理由是專注——當一個 agent 只要管草稿與發送，prompt 更好調、也比較不容易被其他任務分心。代價是 agent 數量變多、路由變複雜。兩種拆法都對，端看你要的是「每個 agent 都能自己收尾」還是「回覆品質被集中調到最好」。

最小權限：不是把每個工具發給每個人

這一步真正的收穫是一個安全原則：特權只給需要它的那個 agent。退款工具只出現在 billing 的工具集裡；triage 想退款，唯一的辦法是把手上的案子轉出去。

把它跟「一個百寶箱 agent」對比就懂了：

全能 agent拆成 triage + billing
退款工具的可及範圍整個 agent 都能呼叫只有 billing 拿得到
誤用的風險任何情境都可能被觸發被限制在職責範圍內
prompt 複雜度一份 prompt 要講所有事、塞滿禁令每個 prompt 只講一件事
擴充方式往同一顆 agent 繼續加新增一筆 name + prompt + tools
安全不是靠 prompt 說「請不要」，而是靠工具集讓它「做不到」；prompt 只是第二道鎖。

對照你自己寫的 OryxOS ReAct loop：以前你可能會把「所有工具」一次丟進同一份 tool 清單，靠 prompt 提醒模型小心使用。拆 agent 之後，這份清單變成依角色裁剪的——同一顆 runtime，餵不同工具集，就得到不同權限邊界的 agent。這就是「agent 是資料」真正換來的東西。
