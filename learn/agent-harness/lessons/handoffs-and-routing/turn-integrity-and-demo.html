訊息序列完整性與端到端示範

Step 4/4 · toolResultsMessage、message 陣列的鐵律、triage → billing 全流程

學習目標

能解釋 toolResultsMessage 為何要立刻回填同 ID 的結果以維持 message 陣列有效，並看懂 triage → billing 的端到端 handoff 事件流。

開場：tool call 之後只能接同一個 ID 的結果

模型說「我要呼叫這個工具」，會附上一個 tool call ID。接著的鐵律是：message 陣列裡的下一則訊息，必須是帶著同一個 ID 的工具結果。不是使用者訊息、不是 system prompt、也不是另一個 tool call。

下一則不是這個 tool call 的回應，API 就會壞掉。

問題來了：一般工具有 execute，SDK 會自動幫你把結果包成正確格式。但 handoff 沒有 execute——runtime 只是攔截它、換了 agent、發了事件。那誰來回那則 tool call？答案是 runtime 自己，用一個小工具函式。

toolResultsMessage：手動合成一則工具結果

這個 helper 把「一次 tool call」加上「一個任意值」，轉成模型看得懂的 tool result 訊息：

function toolResultsMessage(call, value) {
  return {
    role: "tool",
    content: [
      {
        type: "tool_result",
        toolCallId: call.toolCallId,   // 必須跟原本的 call 同一個 ID
        toolName: call.toolName,
        output: { type: "json", value },
      },
    ],
  };
}

四個欄位各有任務：

欄位作用
role: "tool"宣告這是一則工具結果
type: "tool_result"內容型別
toolCallId對上被回應的那次呼叫——最容易出錯、也最關鍵
toolName + JSON output工具名與回傳值

然後在 handoff 的攔截分支裡立刻呼叫它，回一句「成功，已轉給 billing」：

turnMessages.push(
  toolResultsMessage(call, { success: true, handedOffTo: to })
);
SDK 平常幫你做的事，這裡只是拆開來手寫一遍——沒有 SDK 時，你就得自己回這個格式。

為什麼這條鐵律會逼出「以 turn 為壓縮單位」

違反鐵律的後果不只是這個 request 失敗。想像你的 message 陣列停在一個「有 tool call、沒有回應」的狀態，然後你硬塞一則不相容的訊息進去——陣列就壞了。接下來你要遞迴爬過整段對話歷史，找出它是從哪一則開始壞、違反了你哪一條規則，再想辦法自癒。那是個很難收拾的處境。

所以壓縮（compaction）的單位選在 turn（一個完整的來回：模型呼叫工具 → 工具回結果 → 模型再回應），而不是零碎的單則訊息。以 turn 為界，你永遠是最終狀態合法地切開，不會切出半個 tool call。這條設計決策的起點，就是「tool call 必須立刻有同 ID 的回應」。

端到端示範：triage → billing

把工具註解取消、重跑範例訊息，整條路徑就跑起來了。事件流依序是這樣：

#發生什麼觀察點
1triage 分類這筆工單，查出重複收費它用了 runCode / 分類工具
2它判斷需要帳務專家，決定轉出原因是「customer 88121 有重複的 pro plan 月費」
3呼叫 handoff({ to: "billing", reason })runtime 攔截，不是當一般工具執行
4發出 durable 的 agent_handoff 事件事件日誌寫下 from: triage、to: billing
5回填同 ID 的 tool result，記憶被壓縮陣列維持合法，turn 乾淨收尾
6billing 接手，呼叫 issueRefund 並回覆特權工具終於上場

從使用者的角度看，只是同一段對話被另一個更適合的角色接手繼續；從系統的角度看，則是一條可被 inspector 完整重播的事件鏈。

讓 handoff 在 UI 上看得見

功能通了，但使用者怎麼知道「換人了」？兩個簡單做法：

  • 看事件裡的 to——當它改變時，切換代表當前 agent 的圖示或樣式，視覺上就分得出現在是 triage 還是 billing。
  • 叫新 agent 自我介紹——在 system prompt 裡要求「被 handoff 進來時先表明身分」，使用者就知道自己正在跟帳務專家對話。

還有一個示範裡的小插曲值得記住：agent 產生過一個參數／URL 的 typo，但整條流程照樣走完。也就是說，handoff、事件、交換都不需要模型完美無誤——harness 那層的確定性把流程撐住了，模型的偶發小錯不會直接弄垮系統。這正是把控制流從 LLM 搬進 runtime 的價值。
