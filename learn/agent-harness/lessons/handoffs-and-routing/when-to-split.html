判斷：何時拆 agent，handoff 到底是什麼

Step 1/4 · 權限邊界、控制權轉移、避開 swarm 陷阱

學習目標

能判斷何時才該把功能拆成多個 agent（權限邊界而非工具數量），區分 handoff 是「完全交出控制權」而 subagent 是「委派並回報」，並識破 swarm 陷阱。

開場：一個 agent 常也夠用

我們已經有一個單一 agent：一個 loop，一套工具，會搜知識庫、分類、回覆。現在的問題是，什麼時候該把它拆成兩個以上的 agent？

先建立一個反直覺的底線：一個 agent 管所有事，通常是夠用的。工具變多並不等於該拆 agent。如果你高興地把二十個工具都丟給同一個 agent，只要你的 architecture 撐得住、metrics 沒超標、它也沒犯重複的錯，那就繼續用。拆 agent 不是 scale 的預設動作，而是針對特定約束做的決定。

真正讓你「該拆」的理由

那什麼約束才會逼你拆？四件事，而且都跟「工具數量」無關：

理由它解決什麼
敏感 / 破壞性工具退款、刪除、發錢這類動作不該每個 agent 都摸得到——只給需要的那一個
不同護欄（guard rails）有的情境要嚴格、有的要寬鬆，塞進同一個 agent 會打架
不同團隊歸屬一段邏輯歸 A 組、另一段歸 B 組，拆開才好各自 ship
職責劃分讓每個 agent 只專注一件事，prompt 好寫、行為好預測

其中第一條——敏感或破壞性工具——是最強、也最常被引用的理由。這門課的完整例子就是它：一個「退款」工具，只有該管錢的 agent 能拿，其他 agent 一律碰不到。

Swarm 陷阱：別在還沒問題前就拆

反向的錯誤是過早 multi-agent。還沒真的有問題，就先架出一堆 agent 群集（swarm），理由是「聽起來比較先進」。這就像還沒有顧客，就先買了最貴的 AWS 機台。

要看得穿這股風氣：swarm 很大一部分是 labs 賣的敘事——多 agent 就是多張帳單，他們有動機鼓吹這件事。實務上，如果一顆頂級 LLM 加上一個像樣的 harness 都解不掉某個問題，堆十個 agent 多半也解不掉，你只是燒更多錢而已。

判斷口訣：等你真的遇到問題，再引入 routing / handoff；不要因為「工具變多了」就動作。

Handoff 是什麼：理髮店的類比

那 handoff 具體在「轉移」什麼？用一間理髮店想：你走進去，櫃台的人聽完你的需求，判斷你要的是鬍鬚造型，於是把你轉給鬍鬚專家。從那一刻起，櫃台的人就不再參與——他不監督鬍鬚專家，任務也不會再回到他手上。控制權完整地、永久地轉移了。

這就是 handoff 的三個關鍵特徵：

  • 完整轉移——第一個 agent 收到任務後完全交棒，不再插手
  • 不監督——不是「我派一個人去、我來盯」
  • 不收回——任務不會回頭找第一個 agent

handoff 的本質不是「找個更聰明的 agent 來算」，而是「routing 到一個更有資格、或更有權限的 agent」。

Handoff vs Subagent：兩種拓撲

handoff 常被拿去跟 subagent 對比，因為兩者都用了「多個 agent」，但控制關係完全不同。

subagent 像專案經理帶分包商：你永遠只跟一個聯絡窗口說話，他悄悄派出工人、把工人的成果整合好，再跟你回報。工人對你是隱形的，你對口的那個人始終沒換。

handoff 則是把對口的人整個換掉：你從櫃台被轉到鬍鬚專家手上，之後你就只跟鬍鬚專家打交道。

關鍵洞察：同一個 agent 既能當 handoff 的接棒者，也能當 subagent 的工人——差別在拓撲，不在 agent 的能力。沒有哪個天生比較好，只看你的情境要「換聯絡人」還是「保持單一窗口」。

記住這張對照表，後面三課都是在實作「換聯絡人」這種半邊：

控制權對使用者來說
handoff完整轉移，原 agent 退場聯絡人換人
subagent主 agent 保留、派工人聯絡人始終同一人
