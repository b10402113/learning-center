決定哪些要持久化，並把工具執行收回來

Step 2/5 · 判定該包進 durable step 的邊界、移除 execute、集中成 runTool，並定義 ToolCall/Turn 型別

學習目標

用「重跑會不會造成傷害」判定該包進 durable step 的邊界（tool call、emit、streamText），移除工具的 execute、集中成單一 runTool switch，並定義 ToolCall 與 Turn 兩個型別。

一個決定性的問題：哪些要持久化？

裝好 DBOS 之後會出現一個誘惑：把一切都包起來。但持久化不是免費的，每包一個 step 就多一份紀錄的簿記。所以先問一個尖銳的篩選問題——如果這段程式因為重啟而重跑一次，會不會造成傷害？

帶著這個問題掃一遍現有 runtime，會浮出三個答案很明顯的候選：

動作重跑會發生什麼該不該包
個別 tool call工具真的執行第二次——寄兩封信、發兩條訊息該，各自一個 step
emit 事件bus 已經寫資料庫了，重跑會多出重複的事件列該，避免重複行
streamText 呼叫模型模型被呼叫第二次，多燒一輪錢和 token該，避免重複計費

DBOS 的規則是：凡是被包進 DBOS.runStep 的東西，它的輸入和輸出都會被持久化，所以可以 retry、可以 suspend、可以在 server 失敗後存活。把上面三個候選各自包成 step，再把這些 step 串起來，就組成一個 workflow（工作流）。這一步是在「劃邊界」——決定耐用性的界線畫在哪裡，這是整個 durable workflow 設計裡最核心、最能遷移的判斷力。

把工具執行從 AI SDK 手上收回來

這裡有個阻礙：Vercel AI SDK 的預設行為是「你只要給工具一個 execute 函式，它就自動幫你跑」。這聽起來貼心，卻正好擋在持久化前面——如果 SDK 自己把工具跑完，你就沒有機會在「工具執行」這件事上包 step 了。

解法很直接：把每個工具的 execute 欄位刪掉。刪掉之後 SDK 不會自動執行，工具只變成一紙描述（名稱、schema），真正執行得靠我們自己。接著寫一個單一的 runTool，用 switch 把工具名稱對應回原本那些 mock 邏輯：

export async function runTool(name: string, args: unknown) {
  switch (name) {
    case "searchKB":
      return searchKB(args as SearchKBArgs);
    case "classify":
      return classify(args as ClassifyArgs);
    // ...其他工具
    default:
      throw new Error(`Unknown tool: ${name}`);
  }
}

為什麼集中成一個函式、而不是留著每個工具各一個 execute？兩個理由：第一，控制權——執行發生在我們寫的程式裡，才可能在它外面套 durable step，也才可能有審計軌跡；第二，可獨立匯出——runTool 檔案裡沒有任何 DBOS import，將來這個檔案可以被其他地方重複使用，不只服務於這一個 workflow。

step 邊界畫在呼叫端，不畫在工具檔

一個容易踩錯的點：該在哪裡包 DBOS.runStep？答案是——在 workflow 裡「呼叫 runTool 的地方」包，而不是在 tools 檔裡包。

如果把 DBOS import 加進 tools 檔，等於讓一個純邏輯的模組依賴上執行引擎，未來想獨立重用就綁手綁腳。反之，把包裝放在 workflow 的呼叫端，所有 step 就集中在同一個 workflow 裡，不會散落在整個 repo 各處——這是要刻意避開的散落模式。這是一個「cross-cutting concern（橫切關注點）該落在哪一層」的模組邊界判斷：持久化是 workflow 的責任，不是工具檔的責任。

兩個新型別：ToolCall 與 Turn

一旦自己接管工具執行，就得自己描述「一次工具呼叫」和「一回合」長什麼樣。定義兩個 TypeScript 型別：

type ToolCall = {
  toolCallId: string;
  toolName: string;
  inputs: unknown;
};

type Turn = {
  text: string;
  toolCalls: ToolCall[];
  response: { messages: Message[] };
};

ToolCall 帶著三個欄位：toolCallId（把請求與結果對起來的關聯鍵）、toolName、inputs。Turn 則描述一次 model 呼叫的產物：要麼請求工具呼叫，要麼答案完成，再加上回傳的 response messages。之所以要把「turn」當成一個可追蹤的單位，是因為它正是 durable workflow 的進度單元——把 turn 記進 event log，才能在重啟後知道「上一回合進行到一半」，從中斷的那回合接續，而不是從頭開始。

這一步的收穫

你現在有了三個判斷工具：(1) 用「重跑會不會造成傷害」劃 step 邊界；(2) 用「控制執行」去決定工具該不該給 SDK 自動跑；(3) 用「呼叫端 vs 模組內」決定包裝落在哪一層。下一步就是真的把 model turn 和 tool call 抽成兩個可被套進 step 的函式。
