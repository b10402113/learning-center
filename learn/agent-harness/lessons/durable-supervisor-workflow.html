持久化的 supervisor workflow 與 synthesize

Step 4/5 · 第二條 DBOS workflow、plan 包進 step、fan-in 收斂

學習目標

能建立第二條 DBOS workflow（supervisorWorkflow），把 makePlan 包進 runStep 讓 plan 只計算一次並成為可持久化的一級產物，用 event 當 checkpoint，並實作 synthesize 把多份 findings 收斂成單一回覆。

第二條 workflow：為什麼不塞進原本的 agent loop

原本已經有一條 runtime 的 agent loop workflow。supervisor 是另一種執行形狀——它不跑對話式工具迴圈，而是 plan → dispatch → fan-in → synthesize——所以它被獨立成一條新的 DBOS workflow：

async function supervisorWorkflow(task: string): Promise<string> {
  const workflowId = DBOS.workflowID ?? "unknown";
  await DBOS.runStep(
    () => emit({ type: EventType.WorkflowStarted, workflowId, input: task }),
    { name: "started" },
  );

  // PLAN.
  const plan = await DBOS.runStep(() => makePlan(task), { name: "plan" });
  await DBOS.runStep(
    () => emit({ type: EventType.PlanCreated, workflowId, steps: plan.steps }),
    { name: "plan-emit" },
  );
  // ...
}

兩個前置動作：用 DBOS.workflowID 取得這條 workflow 的 ID，然後發一個 WorkflowStarted 事件。

規則一：event 永遠在 step 裡發

注意每個 emit 都被包在 DBOS.runStep 裡。原因是 emit 會碰資料庫，而訂閱者（GUI inspector）正在監聽這條事件流。凡是會產生副作用、或結果需要被持久記錄的動作，都該是 step。

規則二：把非決定性、昂貴的工作包進 runStep

這是持久化執行最實用的一條規則，套用在這裡就是：makePlan 必須包進 DBOS.runStep。

  • 呼叫模型是非決定性的——同樣的輸入，每次可能給出不同的計畫。
  • 呼叫模型是昂貴的——要花時間與錢。

DBOS 在復原或重新評估 workflow 時，會重播已完成的 step 而不是重跑它們。把 makePlan 包成 step，就代表這份 plan 只會被建立一次，然後被永久保存（immortalized）；之後 workflow 無論被重新評估幾次，讀到的都是同一份 plan，而不是又重新生成一份。

這正是「plan 是一級產物」的落地方式：不是靠記憶體裡的變數，而是靠 DBOS 的 step 邊界，讓它成為跨崩潰可重讀的資料。

事件就是 checkpoint

每個 emit 同時扮演 checkpoint 的角色。事件（WorkflowStarted、PlanCreated、後面的 SubagentStarted / SubagentCompleted / ModelCompleted / WorkflowCompleted）依序記錄下來，就構成了「執行到哪裡了」的可重建軌跡。當 workflow 需要復原時，這些 checkpoint 讓它能確定地接回斷點，而不是從頭瞎猜。

把這三件事連起來：非決定性工作 → 包 step → 發事件當 checkpoint。這條鏈就是 supervisor 能「崩潰後還活著」的原因。

synthesize：fan-in 的另一半

計畫產生、工人跑完之後，最後要把散落的發現收斂成一個連貫回覆。synthesize 的任務是：把各調查員的 findings 總結到一處，讓 supervisor 能據此寫出對客戶的回答。

async function synthesize(
  task: string,
  findings: { agent: string; findings: string }[],
): Promise<string> {
  const { text } = await generateText({
    model,
    system:
      "You are a support lead. Using your investigators' findings, write ONE clear, friendly reply to the customer that addresses every point they raised. If an area's investigation is missing, acknowledge it briefly and say you'll follow up.",
    prompt: `Customer escalation:\n${task}\n\nInvestigator findings:\n${
      findings.map((f) => `[${f.agent}] ${f.findings}`).join("\n\n") || "(none)"
    }`,
  });
  return text;
}

幾個關鍵點：

  • 用 generateText，不是 generateObject：這裡的目標是摘要出一段自然語言，不是產出要被程式消費的結構化資料，所以不需要 schema。
  • 角色是 support lead：system prompt 讓模型以「客服主管」的身分，寫一則清楚、友善、涵蓋所有客戶提問點的回覆。
  • 承認缺口：如果有某個領域的調查缺失（例如某個 sub-agent 失敗），prompt 要求它簡短承認並承諾跟進——這就是優雅降級在使用者眼中的樣子。
  • prompt 帶入原始客訴與 findings：把 escalation task 和調查員的發現一起餵進去，收斂才有依據。

至此 plan 有了持久化的家、fan-in 有了收斂函式。下一步是把 plan 裡的每個項目真的平行派出去，並且讓失敗的子 agent 不拖垮整條 workflow。
