# L1 overview

- The deck's scorecard is context, reliability, and cost, illustrated with a career product that helps users pick a career, find education, and pay for it.
- Tools let LLMs act on their environment through information APIs, code execution, and other models, with read-only or read/write access; MCP standardizes how a client reaches an MCP server and gets tool results back to the LLM.
- Skills are folders with a required SKILL.md, load in a context-protecting way, bundle scripts, complement MCP, and should only come from trusted sources because they can contain executable code.
- RAG ingests, chunks, embeds, stores, retrieves, and augments; memory splits into short-term (running state in the context window) and long-term (semantic, episodic, procedural).
- Planning decomposes a goal (plan-then-execute or ReAct); reflection (self-refine, Reflexion) evaluates and revises output, trading accuracy for latency and cost.
- Workflows are where the developer writes the arrows: prompt chaining, routing, parallelization (sectioning/voting), evaluator-optimizer, and orchestrator-workers.
- Single-agent patterns are ReAct, plan-and-execute, Reflexion/self-refine, and CodeAct; they gain adaptability but cost more context, reliability, and money than workflows.
- Multi-agent patterns are sequential, parallelization, supervisor, dispatcher, evaluator-optimizer, and peer-to-peer, each with a scorecard and a distinct control trade-off; the deck closes with evaluations and a selection guide.

# L2 detail

- `#L1-L19` — Title and contact links; today's scorecard defines context (less is better), reliability (how often 100 runs get the right answer), and cost (money, latency, engineering effort); product flow is career choice, then education, then funding.
- `#L20-L45` — Agent foundations: what an agent is versus a reasoning LLM, what it can do, tools (environment interaction, API/code/model calls, read-only or read/write with guardrails, usable by non-tool-trained LLMs with prompting), and MCP (standard transport/format, MCP server/client, results fed back to the LLM, works with any client such as Claude or Copilot).
- `#L46-L58` — Skills: instructions loaded in a context-protecting way, scripts bundled, anatomy is a folder with required SKILL.md and optional subfolders; an open industry standard that complements MCP and can contain executable code, so trust the source.
- `#L59-L81` — RAG and context: ingest/chunk/embed/store/retrieve/augment, similarity search for relevance, memory without supplying everything, reduced hallucinations, RAG at query time versus fine-tuning for retraining (often combined); context is finite and expensive, re-rankers do a second selection pass, and memory has short- and long-term forms.
- `#L82-L97` — Short-term and long-term memory: LLMs are stateless and the context window is all the model knows on a call; agents keep running state of goal, conversation, tool results, and notes and must choose what fits; semantic memory is docs/knowledge bases/catalogues (RAG's usual target), episodic memory is past conversations/logs/lessons, procedural memory is trained weights plus system prompt and behavioral instructions.
- `#L98-L120` — Planning and reflection: without planning agents lose goals on multi-step tasks; planning decomposes a goal, with plan-then-execute and ReAct patterns, reasoning models plan better, plans are hypotheses, and complex goals split into subtasks; reflection evaluates and revises before finishing, self-refine critiques its own output, Reflexion writes a lesson after failure, and more reflection buys accuracy with latency and cost.
- `#L121-L139` — Workflows versus agents and prompt chaining: control is developer-written arrows (workflow), model picks from developer-defined arrows (single agent), or model picks arrows and the next decision-maker (multi-agent); prompt chaining feeds one call's output into the next, suits clean decomposition, beats one large prompt, can put a validation gate between steps, and pays latency for accuracy.
- `#L140-L179` — Workflow patterns: routing classifies input and sends it down one path (topic/intent, cost/complexity, confidence escalation), is a fork not a sequence, and deepens specialization; parallelization runs calls simultaneously and aggregates, with sectioning for independent subtasks and voting for repeated runs, improving speed and redundancy; evaluator-optimizer loops generation and critique when criteria are clear, costing more calls for quality; orchestrator-workers has a central LLM split and delegate subtasks then synthesize, differing from chaining because the orchestrator decides subtasks and fitting unpredictable subtasks such as code.
- `#L180-L190` — Workflows scorecard: context is bounded because each step sees only what the workflow gives it, reliability is testable step by step in isolation, and cost is controlled because the developer controls the number of calls.
- `#L191-L239` — Single-agent systems: ReAct (Reasoning and Acting, think-act-observe-think, 2022 chain-of-thought plus acting), plan-and-execute (full plan up front, fewer calls and cheaper, worse adaptation, with the question "if we know the steps, why not a workflow?"), Reflexion/self-refine (external or self-detected failure, write down what went wrong, carry it into the next attempt), and CodeAct (actions are executable code rather than JSON tool calls, code is in training data while custom tools are not, so sandbox it); scorecard says worse context, reliability, and cost than workflows but better than multi-agent, with adaptability as the gain.
- `#L240-L281` — Multi-agent intro and ordering: sequential makes each step a full independent agent with its own model/prompt/toolset, same topology as prompt chaining, and steps can retry/reflect; its scorecard is good context, compounding errors requiring validation, cheapest multi-agent but high linearly stacking latency. Parallelization splits a request across agents at once, with sectioning and voting subtypes, and mirror-image latency/cost tradeoffs; its scorecard is good context, subtype-dependent reliability (voting better), high money and low latency.
- `#L282-L305` — Supervisor: one main agent breaks the query into subtasks and delegates to subagents, receives their output, and subagents need not know each other; can be nested. Scorecard: excellent context because the supervisor holds the big picture and subagents hold narrow context, strong reliability from focused chunks and redirection, very high cost because the supervisor must be capable and many agents/supervisors may run.
- `#L306-L326` — Dispatcher: a classification step examines input and picks which agent handles it, the multi-agent version of routing, great for clear distinct categories; unlike supervisor delegation only one path executes, so it is a fork not a decomposition, and bad routes are hard to recover from. Scorecard: good small per-agent context, good/bad reliability bottlenecked on the classifier, potentially the cheapest multi-agent pattern by routing simple inputs to smaller models.
- `#L327-L353` — Multi-agent evaluator-optimizer: an optimizer does the work and an evaluator checks and critiques in a loop until satisfied or stopped; each step is its own agent with reasoning and tools, and safety needs an explicit stop condition such as a max-iteration cap or timeout. Scorecard: bad context because every round adds the prior attempt and critique, strong reliability from repeated dedicated critique, and very high cost that can grow fast or loop forever without a stop condition.
- `#L354-L377` — Peer-to-peer: no central coordinator, agents communicate directly and every agent can talk to any other, requiring awareness of every other agent; information passes until a stop condition, there is no direct workflow equivalent, and it fits problems with no natural hierarchy and unknown decomposition. Scorecard: bad context scaling with relationships rather than agents, unreliable without a central checker plus easy coordination failures, very expensive with compounding rounds, hardest to debug, and a last resort.
- `#L378-L430` — Wrap-up and evaluations: benchmarks hide cost and context, show final answers rather than trajectories, make trajectory checks too rigid, and often run once; pass@k means at least one success in k tries and rises with k, pass^k means all k succeed and falls with k; build evals from 20-50 simple tasks drawn from real failures, clear pass/fail, tests for expected and unexpected behavior, and clean near-production environments; selection guide is LLM-powered workflow when steps are known with one hard step, single agent when the path is unknown but the set of paths is known, and multiple agents for independent subproblems.
