# L1 overview

- `workflows/` — Five self-contained scripts where developer code fixes the control flow: prompt chaining, routing, parallelization (voting + sectioning), orchestrator-workers, and evaluator-optimizer. Each calls a faked `callLLM` and returns the same career-advice answer, so the only variable is how the LLM calls are arranged. Takeaway: a workflow is a hard-coded graph of LLM calls, with plain code for gates, aggregation, and loop limits.
- `single-agents/` — Two scripts where one LLM controls its own steps: a ReAct loop that alternates Thought/Action/Observation with tools, and a plan-and-execute agent that writes a full plan once, executes it, then responds. Same fake LLM and tools; the contrast is per-step adaptation versus an up-front plan. Takeaway: an agent, not a workflow, is what you get when the model chooses the next action.
- `multi-agent-systems/` — Six scripts coordinating multiple self-contained ReAct agents through a shared `state` or shared conversation history: sequential, parallel fan-out/merge, supervisor, dispatcher hand-off, writer/reviewer loop, and peer-to-peer swarm. Orchestration is plain code except where an LLM decides delegation. Takeaway: multi-agent designs differ mainly in who chooses the next agent and whether results flow back.

# L2 detail

- `#L1-L126` — `multi-agent-systems/careerSequentialMultiAgent.js` — Header contrasts sequential agents with a prompt-chain workflow and a single ReAct agent; `callLLM` returns scripted replies by agent name and loop count, and `createAgent({name, role, tools, task, outputKey})` builds a ReAct agent with its own system prompt, own tool table, own `messages` memory, `MAX_LOOPS = 5`, and regex parsing of `Final Answer:` / `Action:` / `Action Input:`. Learner concept: each unit is a full agent (internal Thought/Action/Observation loop), not one LLM call.
- `#L127-L184` — `multi-agent-systems/careerSequentialMultiAgent.js` — Defines Career Matcher (`search_careers`, writes `state.career`) and Roadmap Advisor (`get_career_requirements`, reads `state.career`, writes `state.roadmap`). `runSequential(agents, state)` is a plain-code `for` loop that runs agents in a fixed order and stores each `run` result under its `outputKey`; no LLM orchestrator. Sequential pattern: fixed order, state passed forward.
- `#L1-L145` — `multi-agent-systems/careerParallelMultiAgent.js` — Header explains fan-out/gather and contrast with parallel LLM calls; faked `callLLM` scripts four named agents, and the same `createAgent` factory gives each agent its own role, tools, memory, `MAX_LOOPS = 5`, and ReAct parsing. Each agent reads only `state.userInput` and writes its own `outputKey`, so parallel branches never share intermediate work.
- `#L146-L260` — `multi-agent-systems/careerParallelMultiAgent.js` — Three independent specialists run at once: Interest Matcher (`interests`), Work Style Analyst (`workStyle`), Job Market Analyst (`jobMarket`). `runParallel` uses `Promise.all` then writes results only after all finish; merger agent Career Advisor reads all three reports and writes `state.plan`. Parallel pattern: fan out then gather into a synthesizing agent; a rejection fails the whole run unless `Promise.allSettled` is used.
- `#L1-L154` — `multi-agent-systems/careerSupervisorMultiAgent.js` — Header describes "subagents as tools": the supervisor is a ReAct agent whose tools are delegation calls to workers. Faked `callLLM` scripts Supervisor, Career Matcher, Job Market Analyst, and Roadmap Advisor; `createAgent` gives each worker its own description, role, tools, memory, `MAX_LOOPS = 6`, and ReAct loop. Workers start fresh per delegation and cannot see the user or each other.
- `#L155-L242` — `multi-agent-systems/careerSupervisorMultiAgent.js` — Builds the three workers, converts them with `Object.fromEntries` into `delegate_to_<snake_name>` tools whose `run(task)` calls `worker.run(task)`, and gives the supervisor only those delegation tools plus instructions to place everything a worker needs in its task. The worker's final answer returns as the supervisor's Observation; the supervisor decides order, repetition, and stopping. Supervisor pattern: hub-and-spoke control by an LLM.
- `#L1-L153` — `multi-agent-systems/careerDispatcherMultiAgent.js` — Header contrasts dispatcher with supervisor and routing; faked `callLLM` keyword-classifies a specialist for "Dispatcher", then scripts Career Explorer, Roadmap Advisor, and Career Change Coach. `createAgent` again builds full independent ReAct specialists (`MAX_LOOPS = 5`) with per-agent `description`, role, tools, and memory; `run(input)` takes plain text.
- `#L154-L262` — `multi-agent-systems/careerDispatcherMultiAgent.js` — Defines three specialists with domain tools (`search_careers`, `get_career_requirements`, `get_transferable_skills`); `DISPATCHER_PROMPT` lists them and asks for `Action: transfer_to_agent` with an exact specialist name. `dispatch` makes one LLM call, then a code gate matches the name against `specialists` and falls back to `careerExplorer`; only the chosen specialist runs, receives the original message, and answers directly. Dispatcher pattern: one-way hand-off with no result returned.
- `#L1-L161` — `multi-agent-systems/careerEvaluatorOptimizerMultiAgent.js` — Header explains a writer/reviewer agent loop versus single-call evaluator-optimizer; faked `callLLM` chooses scripts by agent name and whether the input contains reviewer feedback or "Lab Researcher". `createAgent` builds ReAct agents with own memory and `MAX_LOOPS = 5`; both `state.draft` and `state.review` flow through the shared state. Key point: because these are agents, both sides can call tools.
- `#L162-L261` — `multi-agent-systems/careerEvaluatorOptimizerMultiAgent.js` — Career Writer (tools `search_careers`, `get_career_requirements`; reads prior draft+feedback) and Career Reviewer (tool `get_work_environment`; judges likes, dislikes, roadmap completeness) alternate. `passed` requires the review to start with `PASS`; `runEvaluatorOptimizer` loops up to `MAX_ROUNDS = 3`, writes each `outputKey`, and returns `approved` true/false. Evaluator-optimizer pattern: code, not the LLM, controls the loop and limit.
- `#L1-L166` — `multi-agent-systems/careerPeerToPeerMultiAgent.js` — Header describes a swarm with no boss or router; faked `callLLM` counts each agent's own assistant turns in the shared history. `createAgent` differs from the other files: `agent.step(history)` runs exactly ONE Thought/Action/Observation turn and returns `{type: "final"}`, `{type: "handoff", to}`, or `{type: "continue"}`; system prompt is rebuilt each step and the conversation history is shared.
- `#L167-L268` — `multi-agent-systems/careerPeerToPeerMultiAgent.js` — Defines Career Matcher, Job Market Analyst, and Roadmap Advisor; `connectPeers` adds a `transfer_to_<peer>` tool with `handoffTo` to every agent for every other agent. `runSwarm` keeps one shared `history`, tracks the active agent, follows handoffs, logs the path, and stops on a final answer within `MAX_STEPS = 10`. Peer-to-peer pattern: agents choose the next agent; code only remembers who is active.
- `#L1-L150` — `workflows/careerRoutingWorkflow.js` — Routing workflow: `ROUTER_PROMPT` classifies input into JSON `{route, reason}` for `explore`/`roadmap`/`switch`; `ROUTES` is a lookup table from route name to a specialized prompt call; `gate` replaces unknown routes with `explore`. Only one route runs, so each prompt stays focused and cost stays bounded. Learner concept: LLM classifies, code routes.
- `#L1-L155` — `workflows/careerEvaluatorOptimizerWorkflow.js` — Evaluator-optimizer workflow: `GENERATOR_PROMPT` writes or rewrites a recommendation, `EVALUATOR_PROMPT` checks it against three explicit criteria and returns JSON `{verdict, feedback}`, and `passed` requires exactly `"PASS"`. `runCareerWorkflow` loops up to `MAX_ROUNDS = 3`, feeding `previousDraft` and feedback back into `generate`, and returns `{draft, rounds, approved}`. Code owns the loop; the evaluator only judges.
- `#L1-L154` — `workflows/careerParallelWorkflow.js` — Parallelization workflow using both variants: `pickCareerByVote` fires `NUM_VOTERS = 3` identical `PICK_CAREER_PROMPT` calls with `Promise.all` and `majority` tallies votes (earliest first vote wins ties); `describeCareer` fires roadmap, outlook, and day-to-day prompts concurrently. `runCareerWorkflow` runs voting, then sectioning, because sectioning needs the chosen career. Parallelism happens inside a stage, never across dependent stages.
- `#L1-L117` — `workflows/careerOrchestratorWorkersWorkflow.js` — Orchestrator-workers workflow: `ORCHESTRATOR_PROMPT` asks for 2–`MAX_SUBTASKS` JSON subtasks chosen for the input; the faked orchestrator returns transferable-skills/skill-gaps for a career switcher and three different subtasks otherwise. `WORKER_PROMPT` is one generic prompt specialized by each subtask instruction; `SYNTHESIZER_PROMPT` combines results without adding facts. Learner concept: the LLM, not code, decides which subtasks exist.
- `#L118-L177` — `workflows/careerOrchestratorWorkersWorkflow.js` — `plan` parses `subtasks`; `gate` drops malformed entries and caps at `MAX_SUBTASKS = 4`; `runWorkers` uses `Promise.all` with each worker seeing the original message plus only its own subtask; `synthesize` concatenates `type: result` lines and calls the synthesizer. `runCareerWorkflow` fixes the plan → delegate → synthesize shape in code while the plan content varies at runtime.
- `#L1-L104` — `workflows/careerPromptChainWorkflow.js` — Prompt-chain workflow: `chooseCareer` calls `CAREER_PROMPT` and parses JSON `{career, reason}`; `gate` throws if `career` is empty; `buildRoadmap` feeds the career and reason into `ROADMAP_PROMPT`; `runCareerWorkflow` runs the two fixed steps in order and returns `{career, reason, roadmap}`. No tools, no loops, no model-chosen control flow. Learner concept: output of one call becomes input to the next.
- `#L1-L145` — `single-agents/careerPlanAndExecuteAgent.js` — Plan-and-execute setup: `PLANNER_PROMPT` asks for JSON `{"plan": [...]}`, `EXECUTOR_PROMPT` handles one step at a time and may return `{"tool", "input"}` or `{"result"}`, and `RESPONDER_PROMPT` writes the final answer from all step results. Fake `callLLM` branches on which system prompt was used; `MAX_STEPS = 6` bounds plan length. Learner concept: one agent wears planner, executor, and responder hats but shares one memory.
- `#L146-L207` — `single-agents/careerPlanAndExecuteAgent.js` — `makePlan` parses and `limitPlan` filters empty steps and slices to `MAX_STEPS`; `executeStep` includes earlier step results in the message, runs the chosen tool or returns an inline result, and never revises the plan; `runCareerAgent` plans once, executes every step in order into `pastSteps`, then calls `respond`. Plan-and-execute pattern: cheaper and faster than ReAct, but no replanning when a step fails.
- `#L1-L146` — `single-agents/careerReActAgent.js` — Single ReAct agent: `tools` holds `get_career_requirements` with a faked database, `SYSTEM_PROMPT` teaches the exact `Thought` / `Action` / `Action Input` / `Final Answer` format, and `callLLM` returns a tool-requesting turn before any Observation and a final answer afterward. `runCareerAgent` keeps a `messages` array as memory and loops to `MAX_LOOPS = 5`, extracting `Final Answer:` or parsing and running the chosen tool. ReAct pattern: reason, act, observe, repeat.
