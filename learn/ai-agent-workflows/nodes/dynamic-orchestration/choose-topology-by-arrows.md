# 誰在畫箭頭？四種多代理拓撲，選最簡單可用的那一個

四種拓撲都看完了，最後要把它們放回同一張圖上選。設計多代理（multi-agent）系統時，很多人直覺會想讓多個 AI 自由溝通、各司其職。但在系統架構中，最核心、也最常被忽略的問題其實是：「誰在畫箭頭？」

箭頭代表控制流向，決定了當前任務結束後，下一個接棒的 agent 是誰。多代理系統並非一律都要把控制權拱手讓人；從完全由工程師寫死流程，到完全交給模型自由對話，這之間是一道清晰的控制光譜。了解誰在決定下一步，並搭配成本與除錯難度評估，才能挑出最簡單且可行的架構。

## 控制權光譜：誰在決定下一步？

依據「誰在畫箭頭」，常見的工作流程與多代理拓撲可以劃分出不同的控制層級：

<!--image:1-->

1. **循序（Sequential）與平行化（Parallelization）**  
   箭頭完全由工程師在程式碼中寫死。每個步驟的先後順序、哪些任務平行觸發，全都由系統邏輯固定，模型只負責執行單點任務，沒有決定流向的權力。
2. **分派器（Dispatcher）**  
   工程師畫好所有可能的分支箭頭，但把「走哪一條路」的分類選擇權交給模型。模型判斷輸入意圖後，挑選預設好的其中一組箭頭往下執行。
3. **評估者-優化者（Evaluator-Optimizer）**  
   工程師建構出反覆修改的迴圈箭頭，並把「何時停止跳出迴圈」的決定權交給模型評估者，由模型判斷成果是否達到標準。
4. **監督者（Supervisor）**  
   這是系統第一次在執行時期（runtime）把畫箭頭的權限交給模型。中樞的監督者 agent 會根據目前的進度與狀態，動態決定下一步要把任務交給哪一個子 agent。
5. **點對點（Peer-to-Peer）**  
   完全去中心化，模型在執行時期自由畫箭頭。各個 agent 之間可以直接相互溝通、發派工作，工程師無法在事前預測對話路徑。

隨著架構往後推進，我們讓渡給模型的控制權越來越多，系統的自主性越高，但相對地，不確定性也隨之暴增。

## 多代理的上下文優勢與致命盲點

將任務拆分給多個 agent，最大的好處在於上下文（context）管理。

過去讓單一 agent 包辦所有事情時，它必須在同一個上下文內完成所有推理、資料蒐集與統整，產出的文字與思考軌跡非常冗長。換成多代理架構後，我們可以為特定任務配置專門的小型語言模型。每個 agent 只做自己專屬的推理與資訊檢索，各自產出的 context 與最終答案都更短小精準。

此外，多代理系統理論上很容易擴充與維護。你可以隨時在系統中新增、移除 agent，或抽換特定節點的底層模型，通常不必擔心整套系統因此全面癱瘓，也不需要把整體成敗押在單一模型上。

多代理架構也能實現互相審查（reviewers）、批評（critics）與尋求第二意見的機制。然而，這也是此類系統最常見的崩潰主因：**沒有人查核驗證（no one verified it）**。

如果沒有在架構中明確建立驗證步驟，agent 之間通常會無條件盲信彼此傳遞的內容。後面的 agent 拿到前面的產出，往往預設對方是正確的，並在這個基礎上繼續推論，導致錯誤一路放大。

## 成本與可除錯性的現實考驗

多代理系統聽起來分工明確，但在工程落地時必須面對成本與除錯兩大挑戰：

<!--image:2-->

* **成本通常更高**：即便能將部分工作切給小型模型，多代理架構通常依然需要至少一個大型模型擔任協調或主力推理。如果架構設計得當，精準利用小模型確實可能省下運算花費；但若倉促上線、設計不良，反覆呼叫與長鏈條互動會讓 API 成本急遽飆升。
* **除錯軌跡極其複雜**：追蹤單一 agent 的思考軌跡（trajectory）本來就不容易，追蹤一群各自擁有獨立軌跡的 agent 更是惡夢。當最終產出出錯時，表面上壞在最後一個 agent，但真正的原因往往出在前兩步某個 agent 的搜尋被帶偏、或是輸出夾帶了微小錯誤，導致後續 agent 全盤走樣。在缺乏對話流向管制的點對點系統中，要在正式生產環境中理清脈絡與 trace 追蹤，得耗費大量時間與精力。

## 業務型態決定架構：Cognition 與 Anthropic 的分歧

多代理領域目前發展極快，各方觀點也常出現交鋒。先前開發 AI 軟體工程師 Devin 的 Cognition 曾公開呼籲「不要打造多代理系統」，但沒過幾天，Anthropic 卻發布文章分享他們的多代理系統在正式環境表現多麼優異。

這兩方的結論都是真實且嚴謹的經驗，關鍵在於彼此處理的「工作型態」完全不同：
* Anthropic 的場景是**資訊研究（research）**：需要廣泛蒐集不同來源、多角度分析與統整，這種型態非常適合多代理分頭探索與審查。
* Cognition 的場景是**寫程式碼（writing code）**：程式碼要求極高的精確性與邏輯一致性，狀態一多就容易出錯，因此傾向依賴嚴謹單一的執行流程。

在評估是否採用多代理之前，必須先看清自己的業務情境更接近哪一種。

## 高度確定性需求下的取捨

如果你的系統高度要求確定性（deterministic）結果，該如何選擇？

當業務需要高度可靠時，多代理拓撲中首選的是**平行化搭配投票子類型（voting subtype）**。藉由將同一任務平行發送給多個實例執行 3 次、5 次甚至 10 次，最後再聚合（aggregation）多數決的結果，可以在機率模型中拉出一定程度的確定性。

<!--image:3-->

不過，如果應用場景屬於**醫療照護（healthcare）**或**金融銀行（banking）**這類直接關乎人命安全或財產生計的領域，就必須極為謹慎，通常不建議冒然採用自主性過高的多代理架構。若既有的生產程式庫已經在使用語言模型，且能用確定性高的工作流程（workflow）解決，優先採用明確的流程控制會穩妥得多。

此外，在參數設定上，調低 `temperature` 與調整 `top_p` 確實有助於壓制隨機性、讓輸出盡可能接近確定性，但永遠要記住：語言模型本質上依然是在預測下一個 token，不可能達到百分之百的傳統確定性。

## 選最簡單可用的那一組箭頭

在正式生產環境中，多代理模式很少單獨存在，通常是層層嵌套。你可能會看到一個協調者（Orchestrator）外層包著評估者-優化者迴圈，而聚合（Aggregation）機制更是能嵌入在任何拓撲之中。往下一層看，個別的單一 agent 本身也可能是 ReAct、程式碼執行（code execution）或計畫與執行（plan-and-execute）架構。

面對眼花撩亂的選項，選型標準始終應回到「控制權」與「複雜度」：能由人畫箭頭的循序與平行流程，除錯成本永遠低於由模型在 runtime 自主畫箭頭的動態架構。從最能掌握箭頭流向、最簡單可用的拓撲開始，只有在單一流程確實無法應付任務複雜度時，再逐步把畫箭頭的權力交出去。
