# 工作流就是控制流

在談論語言模型應用時，大家往往急著把系統包裝成「AI Agent」（代理人）。但在真正跳進去讓模型自行決策之前，必須先退一步釐清一個根本問題：到底什麼是工作流（Workflow）？

最簡單的工作流，本質上就只是程式碼。它可以是一段腳本、一個函式、一個無伺服器架構上的 Lambda，甚至單純就是幾行 `if-else` 判斷式。它是一組寫在程式碼裡的指令集，也就是開發者早就非常熟悉的控制流（Control Flow）。

在整個流程中，可能只有某一個步驟因為特別困難，或者需要生成自然語言，我們才決定呼叫大型語言模型（LLM）。但整體架構依然是「先做這件事、接著做那件事、然後再做第三件事」。當我們把模型放進工作流時，模型本身並沒有權力決定下一步該往哪裡走；它只是既定流程中的一個環節，走的是開發者預先在程式碼裡寫死的路徑。

這不是隨意給出的定義，Anthropic 官方也是用同樣的方式來描述工作流：一切路徑都由開發者預先規範。

## 控制權的光譜

理解工作流的關鍵，在於「控制權」在誰手上：

<!--image:1-->

- **工作流（Workflows）**：流程中的所有箭頭（連線與分支），全部由開發者自己寫死。控制權完全在開發者手上。
- **單代理人系統（Single-agent systems）**：開發者預先定義好一組箭頭，讓模型自己從這組選項中挑選下一步。
- **多代理人系統（Multi-agent systems）**：模型不只自己挑選箭頭，還決定下一步由哪個代理人來挑選箭頭。

建構 LLM 系統的第一步，應該是把控制權牢牢留在自己手中，先用確定性最高的工作流來解決問題，直到明確需要模型自主判斷時，才考慮讓出部分或全部的控制權。

## 最基礎的工作流：提示詞鏈結

最常見的工作流模式是「提示詞鏈結」（Prompt Chaining）。它的運作邏輯非常直接：前一次模型呼叫的輸出，直接轉化為下一次模型呼叫的輸入。

<!--image:2-->

面對複雜任務時，將流程拆開往往比塞進一個龐大的單一提示詞（One large prompt）更有效。原因在於：

1. **模型更容易處理小型提示詞**：把任務拆細，模型不需要在單次生成中同時顧及多個互相衝突的目標，輸出品質通常更穩定。
2. **可在步驟之間設置檢驗閘門（Gates）**：前一個步驟完成後，你可以先用既有的程式碼驗證格式或內容是否正確，合格了才放行到下一個模型呼叫；若不合格，就能提早攔截或重新處理。

## 用延遲換取準確度

採用提示詞鏈結時，必須清楚意識到它的核心取捨：你是在用延遲（Latency）來換取準確度（Accuracy）。

因為後一步完全依賴前一步的輸出，在邏輯上你必須先等待第一個 LLM 呼叫回傳結果，才能把它組裝進下一個提示詞交給第二個 LLM；等第二個呼叫完成，才能交給第三個。這些等待時間會線性疊加。如果你的應用情境要求極低的反應時間，例如需要即時流暢互動的場景，鏈結可能就不適合；但如果你追求的是每一步推論的精確度，這會是極佳的解法。

## 什麼任務適合拆成鏈結？

提示詞鏈結最適合「任務可以乾淨拆解」的情境。

一個很好的思考範例是工程師在正式環境排查問題（Debug）的過程：

當系統出錯時，你通常會先去撈取第一份資料；但你必須等資料調閱回來，看清楚裡面的數值，才能判斷這是不是異常發生的原因、需不需要往別的方向追查。當你有了第一份資料的結論，才會決定接下來該看哪一份第二層資料。在拿到第一步的結果之前，你根本不可能直接跳去查第二步。

像這種「前一步的結果決定下一步的素材，且每一步都能獨立驗證」的工作，就是最適合寫成提示詞鏈結的典型任務。
