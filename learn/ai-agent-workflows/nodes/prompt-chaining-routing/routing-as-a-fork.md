# Routing 是分岔，不是序列

Chain 只走一條路；當請求類型不只一種，入口就需要分岔。當使用者送來各種類型的請求時，如果全部丟給同一個昂貴的模型或同一段通用邏輯處理，往往會浪費成本，回應速度也難以提升。在建構 LLM 工作流程時，常見的做法就是加入 Routing（路由）機制：先將輸入進行分類，再把它導向適合的特定路徑。

## 什麼是 Routing？

Routing 的核心本質是「分岔」（fork），而不是「序列」（sequence）。

<!--image:1-->

這兩者的差別在於控制流程：
- **序列（Sequence）**：任務有前後相依性，先走第一步處理完，再交給第二步接著做。
- **分岔（Fork / Routing）**：在起點做完分類後，只挑選其中一條控制流走下去，並不會先執行路徑 A 又接著執行路徑 B。

一旦分岔選定，請求就會順著該路徑執行完畢。每個獨立路徑都可以依需求專門化設計，進而針對延遲（latency）與成本（cost）做最佳化。分岔之後可以導向的目標非常彈性，常見的路徑包括：

- 導向不同的大型語言模型（例如簡單任務走小型模型，複雜任務走旗艦模型）
- 導向不同設定的 Prompt
- 導向傳統、確定性的程式碼（deterministic code）

## 常見的路由依據

在決定請求該走哪條路時，分類步驟通常成本很低，可以依據不同的標準來判斷：

<!--image:2-->

- **主題或意圖（Topic or Intent）**：判斷使用者的問題屬於技術支援、退費申請還是產品諮詢。
- **成本與複雜度（Cost and Complexity）**：評估問題是否需要動用高成本的進階模型，或是簡單的規則就能解決。
- **信心水準（Confidence）**：如果模型判斷該請求時信心度不足，系統就能觸發升級機制，直接將案件轉交給人工處理（escalate to a human）。

## 從複雜決策到選擇題：分類模型的優勢

在規劃 Routing 工作流程時（這項技巧未來在多 Agent 系統中也會用到），過去開發者往往希望有一個極度聰明的模型來幫忙帶路，因為即使只有少數幾個路徑可選，要準確判斷走向依然相當棘手。

然而，現在除了文字生成模型之外，還有能量模型（energy-based models）與專門的分類模型。在這類分類場景中，Routing 本質上就像是在做一張「選擇題清單」：你給模型一組選項，模型從中挑出一個最符合的答案。它不需要產出落落長的對話文字，只需要輸出選項結果。這類模型在分類任務上表現極佳，讓我們能以非常低廉的成本完成路由判斷。

<!--image:3-->

在這種由 LLM 驅動的工作流程中，LLM 扮演的角色十分單純：它只負責判斷並挑選路由，而後續每條專屬的固定路徑，都是由開發者預先定義好的。這也是它與自主 Agent 最大的差別。
