# CodeAct：動作是可執行的程式碼，而不是 JSON

反思解決了「錯了再試」，CodeAct 則改寫「一次動作」的單位。在建構單一代理人（single-agent）系統時，最常見的做法通常是像 ReAct 那樣，讓模型輸出特定格式的 JSON 來呼叫工具。然而，這種做法在處理複雜任務時，往往會面臨呼叫次數過多、流程繁瑣的問題。

CodeAct 提供了一種截然不同的思路：代理人的「動作」（Action）不再是一段 JSON 物件，而是一段**可以直接執行的程式碼**。這個架構非常強大且受到大量關注，但實際實作時也相當具有挑戰性。

## 為什麼傳統的 JSON 工具呼叫成本高昂？

如果代理人的動作必須透過 JSON 來觸發工具，每一次動作通常都需要經歷三個步驟，也就是一次完整的往返（round trip）：

<!--image:1-->

1. 模型先生成符合格式的 JSON 工具呼叫內容。
2. 應用程式解析 JSON，呼叫對應的工具或函式。
3. 等待執行結果出爐，再把結果塞回提示詞（Prompt）送回給模型，讓模型決定下一步。

如果任務需要接連呼叫三、四個工具，這樣的流程就必須重複好幾次，不僅耗時，也消耗大量 token。

相對地，如果動作直接用程式碼表示，模型就能把一整連串的查詢、過濾與資料處理寫在同一段程式碼區塊內，直接在一個步驟中全部完成。

## 模型擅長寫程式碼，而不是你自訂的工具規格

從預訓練（pre-training）資料的角度來看，大型語言模型在訓練階段看過天文數字等級的程式碼：開源專案、軟體系統、技術書籍、學術論文，程式碼無處不在。

但當你替代理人定義工具規格（Tool Schema）並丟給模型時，那是它這輩子第一次看到這套規格。因此，在理論上，CodeAct 的核心假設在於：**模型自行寫出程式碼來取得答案的能力，遠比它嘗試理解並拼湊你剛發明的一組工具規格來得更純熟。**

## 執行程式碼的代價：沙箱與安全防護欄

既然 CodeAct 這麼有效率，為什麼大家不直接全面改用？因為它伴隨著極大的權衡取捨（trade-off）：**你正在執行模型即時生成的程式碼**。

<!--image:2-->

執行隨機、未曾審查過、且由模型動態生成的程式碼，本質上具備危險性或破壞性。要實作 CodeAct，就必須建立具備安全防護欄（guardrails）的隔離執行環境（Sandbox，沙箱）。這會大幅增加整體系統架構的複雜度。

相較之下，寫一個傳統的 ReAct 代理人可能不到半小時就能搞定；但要安全地跑 CodeAct，通常需要有能力架設與維護受控沙箱的企業團隊，這也是它目前在企業級應用中逐漸普及的原因。

## CodeAct 的運作流程

CodeAct 的整體迴圈與 ReAct 十分相似，差別在於動作的型態與執行方式：

<!--image:3-->

1. **思考與寫出程式碼（Thought & Code Act）**：代理人接收問題後進行推理，並寫下一段可執行的程式碼，而不是輸出 JSON 工具呼叫。
2. **在沙箱中執行（Sandbox Execution）**：這段程式碼直接在受控的沙箱環境內執行。模型可以在沙箱中直接發出網路請求或呼叫 API，不用等待主程式在外面一個個轉發工具。
3. **觀察結果（Observation）**：沙箱回傳這段程式碼執行後的輸出結果。
4. **生成解答或接續執行**：代理人觀察輸出，如果需要，可以再寫一段程式碼繼續在沙箱中執行，直到獲得足夠的資訊，最後輸出最終答案。

### 實際情境範例

假設使用者提出一個複合問題：「我很有創意，而且喜歡幫助他人。哪些職業生涯適合我？有哪些進修課程能幫我達成目標？我又該如何支付這筆費用？」

如果採用傳統工具呼叫，模型得先呼叫職業查詢工具、等回傳、再呼叫課程查詢工具、等回傳、最後呼叫助學金工具。

在 CodeAct 中，沙箱環境已經配置了職業資料庫 API、教育課程 API 與助學貸款 API 的存取權限。代理人可以直接寫出一整段程式碼：
- 同時發送請求查詢適合的職業。
- 根據撈出來的職業名稱接著搜尋對應的訓練課程。
- 一併尋找可行的資助與補助方案。

這段程式碼在沙箱的受控環境內一次執行完畢，單次執行就回傳多項查詢結構化整合後的結果。最後，代理人觀察沙箱結果，直接給出完整的推薦生涯路徑、推薦課程與資金規劃建議。
