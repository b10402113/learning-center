# Agent 沒有記憶：working、semantic、episodic、procedural

把每一次對話都當成一次性的 context，就無法解釋跨 session 的記憶從哪裡來。當你跟線上客服機器人對話時，它如果能記住你上週反映過的問題，甚至提到「上次答應在 5 到 7 天內退款給您」，多數人會直覺認為「這個 AI 有記憶」。

事實上，大型語言模型（LLM）本身完全是無狀態的（stateless）。每當你送出一條訊息，模型把目前上下文（context）裡的所有文字讀過一遍，產生回覆，接著就把剛才的一切忘得一乾二淨。如果一般聊天機器人看起來記得你們的對話，背後的原理只是應用程式在每一次對話回合，都把整份歷史對話紀錄重新塞回提示詞裡送給模型。

但打造一個自主運作的 Agent（智慧代理）時，要處理的細節遠比單純轉傳聊天紀錄複雜得多。2024 年有一篇名為 COALA（Cognitive Architectures for Language Agents）的論文，提出了一套描述 Agent 的架構語彙。COALA 不是一套具體的軟體，也不是某種特定的 Agent 類型，而是用來從三個面向描述任何 Agent 的框架：記憶（memory）、行動（actions），以及決定採取何種行動的決策機制。

要讓 Agent 真正具備跨回合、跨階段的工作能力，必須先釐清它身上運作的四種記憶類型：working memory（工作記憶），以及三種 long-term memory（長期記憶）——semantic memory（語意記憶）、episodic memory（情節記憶）與 procedural memory（程序記憶）。

## 短期運作的核心：Working Memory

在一般的對話紀錄之外，Agent 的程式碼必須隨時維護一份正在變動的狀態（running state）。這份狀態包含了：

- 使用者最初設定的目標
- Agent 到目前為止嘗試過哪些步驟
- 呼叫工具後回傳的結果
- 使用推理型模型（Reasoning LLM）時所留下的內部思考筆記

在研究文獻中，這份即時狀態被稱為工作記憶（working memory）。

每次向語言模型發送請求前，Agent 的程式碼都會從這份工作記憶狀態中，重新拼裝出一個乾淨的上下文（context）。等模型產生回覆後，Agent 再將新的輸出存回狀態中，供下一次呼叫使用。換句話說，上下文只是窺探 Agent 工作記憶的一扇暫時性視窗，每一個對話回合都會被重新建立一次。

<!--image:1-->

工作記憶最大的限制在於上下文視窗（context window）的大小。把視窗塞滿不僅會碰到 token 上限，每一次呼叫也都在消耗額外的時間與金錢。因此，Agent 設計的核心工作之一，就是決定哪些內容該放進工作記憶：摘要舊的對話回合、丟棄不再相關的工具輸出、確保使用者的目標始終清晰可見。

當某次互動結束、上下文視窗被清空之後，還需要保留下來的東西，就屬於長期記憶（long-term memory）。長期記憶可以細分為三種型態。

## 長期記憶之一：Semantic Memory（事實知識）

語意記憶指的是事實與知識，也就是「Agent 知道了什麼」。

<!--image:2-->

以客服 Agent 為例，網站上的說明中心文章、公司的退款規範，都屬於這類事實資料。通常大家在討論系統導入 RAG（檢索增強生成，Retrieval-Augmented Generation）時，指的就是語意記憶：Agent 透過搜尋資料庫，找出關聯度最高的事實碎片，並將它們塞進當前的工作記憶上下文中供模型參考。

## 長期記憶之二：Episodic Memory（過去經歷）

情節記憶記錄的是經驗與歷程，也就是「過去發生了什麼事」。

這包括客戶先前與系統互動的歷史：以往開過的客服工單、上一通電話的通話紀錄，或是客服曾經對該客戶做過的補償承諾。

除了與外部使用者的互動，情節記憶也包含 Agent 留給自己的經驗筆記。例如一個專門做文獻研究的 Agent 在嘗試某條搜尋路徑失敗後，寫下一則紀錄：「這份檔案裡沒有相關內容」，之後就不會重複去翻同一篇研究論文。當使用者重新登入系統，助理能主動說出「記得你上次下的訂單嗎？」或是「上次我們承諾要退款給您」，背後依靠的都是情節記憶。

### 情節記憶該存放在哪裡？

業界目前沒有單一標準，常見的存放策略有以下幾種：

<!--image:3-->

1. **一般資料庫儲存完整逐字稿（Full Transcripts）**：把每次對話無損地記錄在傳統關聯式或文件資料庫中，以 session ID 作為索引鍵。這種方式結構簡單且資訊完整，缺點是整篇對話篇幅通常太大，下一次對話時無法全盤塞回新的上下文視窗。
2. **對話結束時產生摘要（Summaries）**：COALA 論文特別建議在互動結束時沉澱學習成果——先摘要再儲存。在客服場景中，系統不需要保留來回幾十句的閒聊，只需要在結尾存下一段簡短摘要：「上次對話答應客戶會在 5 到 7 天內收到退款，但客戶現在反映尚未入帳」。只保留關鍵需求與結果，大幅減輕後續檢索的負擔。
3. **過去訊息或摘要的向量資料庫（Vector Database）**：將過往的事件片段或對話摘要轉為向量嵌入（embedding）。這本質上就是將 RAG 技術應用在「自身經歷」而非「外部文獻」上，讓 Agent 能藉由語意相似度檢索過去相關的情節。
4. **Agent 執行日誌（Logs of Agent Runs）**：記錄 Agent 處理複雜任務時的每個步驟以及最終成敗。如果 Agent 偶爾會走入死胡同，保留執行日誌能讓它在後續任務中辨識並避開曾經失敗的路徑，隨著時間逐步優化執行表現。
5. **純文字筆記檔案（Plain Notes Files）**：許多程式碼輔助 Agent（例如 Cursor 等整合環境中的開發工具）會將本次 session 的摘要與工作狀態直接寫進本機的隱藏筆記檔案中，並在下次啟動 session 時讀取。使用者如果要求它回顧上一次的討論進度，它往往就是去翻閱這些本機純文字紀錄。

## 長期記憶之三：Procedural Memory（技能與步驟）

程序記憶指的是技能，也就是「事情該怎麼做」。

其中一部分能力早已內建在模型訓練完成的權重裡，這也是它具備基本讀寫與邏輯推理能力的原因。剩下的部分，則是由 Agent 的開發者負責提供：

- 系統提示詞（system prompt）中規範的工作流程
- 工具的定義與呼叫規範
- 專為特定任務撰寫的控制邏輯程式碼

部分進階的研究型 Agent 甚至具備為自己編寫新技能的能力。例如在 Minecraft（當個創世神）環境中運作的自主 Agent，能夠將打造鐵劍的動作序列寫成程式碼儲存下來，日後遇到相同需求時直接重複呼叫這項新技能。

## 跨 Session 的檢索與載入機制

無論存放了多少事實、經歷或技能，如果資料無法順利進入當前運作的上下文視窗，這些記憶就無法對 Agent 產生任何實質影響。把長期記憶帶回上下文的主要途徑有兩種：

<!--image:4-->

- **常駐載入（Always Loaded）**：如果資料量很小（例如簡短的使用者個人偏好，或是前兩三次對話的最終摘要），可以在每次開啟對話時直接放進系統上下文。這種做法實作極為簡單，但缺點是無論這段記憶與當前對話是否相關，它都會固定佔用寶貴的上下文空間。
- **依需求檢索（Retrieve on Demand）**：平時不主動塞入記憶，直到程式邏輯觸發，或是模型主動呼叫特定的「記憶搜尋工具」（Search Memory Tool）時才動態查詢。當使用者提到「上次我們聊到那件事但沒有下文」時，模型可以主動決定發動工具搜尋歷史情節。這種做法在規模化時表現較佳，但強烈依賴檢索精準度；一旦檢索失敗或找錯片段，模型就無法取得正確資訊。

大型語言模型本身具備隨機性（non-deterministic），開發者能做的，就是建立一套穩固的工程架構來提升確定性。一個具備完整生命週期的 Agent，必須在背後持續重複這樣的運作循環：檢索相關記憶到工作空間、進行推理思考、採取外部行動，最後在對話結束時，主動把值得留下的經歷摘要歸檔，存入下一輪互動能讀取的長期記憶中。
