# RAG 六步：ingest、chunk、embed、store、retrieve、augment

當你打算讓 AI Agent 處理大量內部文件、學術論文或公司規定時，最直覺的想法可能是把所有資料一股腦全塞進對話的 context（上下文視窗）。但現實往往行不通：資料量可能高達數萬甚至數百萬份，context 空間一下就被擠爆，超出的內容只會直接被切掉。即使勉強塞得下，過多無關的雜訊也會讓大型語言模型（LLM）更容易產生幻覺（hallucination），而且每一次 API 呼叫的成本都會直線飆升。

RAG（Retrieval-Augmented Generation，檢索增強生成）正是為了解決這個問題而生。它就像給 Agent 一套外掛的外部記憶體，既能調閱大量資料，又不會耗盡 context。整個運作流程可以拆解成清晰的六個步驟：**ingest、chunk、embed、store、retrieve、augment**。

## 準備階段：把文件切塊並轉為向量

在使用者發送任何問題之前，系統需要先預先處理並儲存好外部資料：

<!--image:1-->

1. **Ingest（攝取）**：蒐集所有可能含有相關資訊的文件資料。
2. **Chunk（切塊）**：把龐大的文件切成較小的文本片段。這些片段通常只是一個短語或幾句話。實務上切塊的大小會視需求而定，但通常不會切得太長，因為一旦片段過大，檢索時就很難快速且精準地命中關鍵內容。
3. **Embed（嵌入／向量化）**：把切好的文字片段轉換成數值組成的向量（vector）。
4. **Store（儲存）**：將產生的向量與對應文本存入專門的資料庫中。

### 為什麼不直接儲存純文字做關鍵字搜尋？

如果把文字原封不動存進傳統資料庫，我們就只能依賴關鍵字搜尋。但關鍵字搜尋非常沒有效率，而且很難找出「意思相關但用詞不同」的內容。

<!--image:2-->

舉例來說，如果使用者想找跟「沙發（couch）」有關的資料，用關鍵字搜尋時，系統或開發者就必須主動列出所有同義詞與延伸詞：couch、sofa、chair、upholstery 等等，光是一個詞就有成千上萬種可能性。

Embedding 模型解決的正是這個問題。這類模型雖然多半採用與 LLM 相同的 Transformer 架構，但它們的目標不是「生成文字」，而是「將文字轉換為數值向量」。在向量空間中，語意相近的詞彙（例如 couch 與 sofa），它們的數值表示會非常接近；而與它們毫無關聯的詞彙（例如 horse 或 pizza，除非訓練資料裡有大量的「披薩沙發」），在數值上就會相差極遠。透過向量，系統就能直接用「語意關聯性」來找資料，不再受限於字面上的關鍵字。

## 查詢階段：動態檢索並擴充提示詞

當使用者提出問題時，後續的兩步就會在執行時（query time）即時觸發：

5. **Retrieve（檢索）**：使用者送出 query 後，系統使用同一個 embedding 模型將該 query 也轉成向量，接著向資料庫比對關聯性，挑出與 query 最相關的少數片段。
6. **Augment（增強）**：把檢索出來的相關片段，連同使用者的原始 query 一起包裝進 prompt，組合成最終的 context 送交 LLM 生成回答。

### 以職涯產品為例：保護 Context 與降低成本

假設你正在打造一個推薦獎學金與就學貸款的職涯輔助產品。市面上有成千上萬種獎學金，每種獎學金都有極為繁瑣的申請資格條件。

<!--image:4-->

我們不可能把 100 所學校、底下的所有獎學金項目，以及全部的資格條款一股腦全塞進 context，這在容量上限上完全放不下。

採用 RAG 的做法是：預先把所有獎學金的資格文件切塊並 embed 存進資料庫。當一位使用者說「我是住在德州的第一代軟體工程系大學生」時，系統只會從資料庫檢索出真正與他條件吻合的 20 個相關片段。

這時送到 LLM 的 context 只有使用者的問題加上這 20 個片段。我們只花了一次 query 的 embedding API 呼叫和一次向量資料庫查詢，就以極低的成本保護了 context 空間，同時大幅降低模型胡言亂語的機率，精準給出基於事實的答案。

## 常見疑惑釐清

### RAG 與 Fine-tuning（微調）有何不同？

Fine-tuning 是在模型訓練或預訓練之後進行的參數調整，適合用在特定風格或專業格式的重新訓練，但它是發生在「查詢之前」的靜態修改。

相對地，RAG 是完全運作在「查詢當下（query time）」的機制。在多數 Agent 開發情境中，我們未必會天天微調模型，但 RAG 卻是隨時能掛載即時資料、最新事實的必備工具。兩者並不衝突，也常常搭配使用。

### LLM 如何看待 RAG 帶進來的資料？

在執行時，LLM 其實感受不到「這是檢索系統送來的外部資料」。LLM 本質上就是接收輸入文字並輸出文字。

整個流程是由程式碼在背後串接：LLM 輸出查詢需求（類似呼叫 Tool），程式碼將需求送交 embedding 模型並向資料庫檢索，最後將撈回來的相關資訊包回 context 餵給 LLM。對 LLM 來說，所有送進去的文字都是一體的，它只是依據 prompt 裡更有針對性、更具事實根據的內容來產出回答。

### RAG 就像一本書的索引嗎？

這是一個非常貼切的比喻。如果把整座資料庫比喻成一本書，RAG 就扮演了書末索引的角色。

兩者唯一的差別在於：傳統書末索引通常只精確指向某個單一詞彙出現的頁碼；而 RAG 的關聯向量檢索，則像是更智慧的索引，能一次找出整本書中與你的提問相關的 3 到 5 處段落，把這些精華內容挑出來攤在模型眼前，既省時又不容易出錯。
