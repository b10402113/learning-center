# Context 有限：re-ranker、compaction 與 MMR

檢索能把相關片段挑出來，但挑多少、怎麼塞，才是下一個問題。建置 AI Agent 時，許多人一開始都會以為 context window 越大越好，甚至誤以為有了幾十萬甚至上百萬 token 的視窗，就再也不必為空間發愁。然而在實際運作中，特別是多 Agent 協作的架構下，context 空間很快就會被各種資訊塞滿；伴隨而來的，還有呈指數級暴增的 API 成本與模型注意力渙散的問題。

Context 本質上是有限的資源。要讓 Agent 穩定且經濟地運作，就必須學會規劃 context 預算，並透過 re-ranker、compaction 與 MMR 等技術，在有限的視窗內精準保住最關鍵的資訊。

## Context 裡到底塞了什麼？

在 Agent 的工作流程中，光是基本設置就會佔用大量 context 空間：

<!--image:1-->

- **System Prompt**：裡面包含模型的任務說明、行為邊界、哪些事情不能對使用者透露、哪些機密不能外洩。如果使用的是原生不支援 tool calling 的 LLM，系統提示詞中還得額外寫入工具呼叫的格式規範與範例。
- **工具與技能定義（Tools & Skills）**：提供給 Agent 呼叫的所有函式介面與參數描述，都會原封不動進駐 context。
- **其他 Agent 的資訊**：在多 Agent 系統中，各個 Agent 必須對彼此的角色、職責與狀態有所了解，這部分資訊也必須寫進視窗。
- **對話歷史**：除了使用者與 Agent 的對話之外，多 Agent 彼此之間也會相互交談。Agent 的產出往往非常冗長，多個 Agent 自主往返討論幾輪，就會產生驚人的 token 量。

如果多 Agent 系統為了控制延遲與成本而選用較小型的 LLM，context window 本身就更狹小。多 Agent 的呼叫次數疊加後，token 消耗與花費會以極快速度上升。這正是檢索增強生成（RAG）變得如此普及的原因：我們希望只抓取和當前查詢直接相關的資料，不要把所有內容通通硬塞進去。

## RAG 的盲點：語意相似不等於有幫助

雖然 RAG 能幫我們過濾資料，但標準的向量檢索很容易帶進兩大問題：資料內容高度重複，以及「看似相關卻毫無用處」。

假設在向量資料庫中放了許多深度的學術論文與書籍，當系統檢索出 10 份文件時，很可能其中有 5 份都在引用同一個論點或講述重複的內容。這些重複內容一旦全部灌進 context，就是在浪費寶貴的空間。

此外，向量檢索依賴的是語意相似度（semantic similarity），它只負責找出文字上接近的片段，卻無法分辨這段文字對回答問題有沒有幫助。

<!--image:2-->

舉例來說，當使用者詢問「如何進行馬匹展覽（showing horses）」時，向量檢索可能會把名馬「海餅乾（Seabiscuit）」的歷史資料抓出來。從語意上看，海餅乾確實是一匹贏得許多大獎的名馬，向量維度上彼此高度相關；但海餅乾是一匹純種賽馬，這段生平對於回答「如何展覽馬匹」沒有任何實質幫助。

這就是需要引入 **re-ranker（重新排序器）** 的原因。RAG 負責撈出候選文件，re-ranker 則作為第二道關卡，進一步評估：「這份文件到底能不能回答使用者的具體問題？」唯有真正具備解答價值的片段，才會被放行進入 context。

## Compaction：有損與無損的壓縮策略

當 Agent 運作了一段時間，context 空間即將見底時，就必須執行壓縮（compression）或壓實（compaction）。Compaction 是壓縮的一種具體形式，核心目的就是縮減 context 內的 token 數量。

實務上可以根據情境選擇無損或有損作法：

<!--image:3-->

- **無損做法（Lossless）**：將完整的對話歷史移出當前視窗，存入外部快取或資料庫。這類似於在社群上討論的 AI 伴侶應用，系統會將大量累積的對話記錄保存在外部儲存區，需要時才調用，讓模型能在不佔用當前 context 的前提下，維持長期關係的時空脈絡。
- **有損做法（Lossy）**：當 context 達到特定容量閾值時，呼叫原本的模型或另一個較便宜的 LLM，將先前的對話與執行過程摘要化。摘要過程會要求保留核心細節，將原本龐大的對話壓成精簡的文字，藉此清出大量空間。

採用摘要會損失細節，但能換取大幅減少的 token 量。每個應用場景都必須自己評估：失去某些上下文是否會影響任務執行？如果任務必須完整掌握每一次工具調用的原始輸入輸出，就不能貿然依賴有損摘要。

## MMR：用 1990 年代的老演算法消除重複

在壓縮 context 時，最有效卻常被忽略的手段，就是剔除檢索結果中的重複資訊。如果你抓出了 10 篇論文，其中 5 篇內容實質雷同、互相引用，就應該把多餘的副本移除。

這個概念並非現代 Agent 的新發明，而是源自 1990 年代的經典演算法：**最大邊際相關性（Maximal Marginal Relevance，簡稱 MMR）**。

MMR 的核心運算邏輯非常直覺：它在替候選文件評分時，會計算「該文件與當前查詢的相關性」，再減去「該文件與已經入選之文件的相似度」。

<!--image:4-->

如果一份文件雖然和使用者的問題很相關，但它跟已經挑選出來的文件太過相似，它的整體分數就會被扣低，進而被排除在外。

如何調校 MMR 的權重平衡，至今在軟體工程界依然存在不同觀點。這完全取決於使用者的場景：保留部分重複資訊是否能提供某種確認冗餘？還是 context 空間極為吃緊，必須極致乾淨？你可以根據系統預算自由決定調校方向。

## 成本權衡、資料上限與「迷失在中間」

在規劃 RAG 與 context 管理時，常有人詢問儲存資料量是否有建議的上限。

技術上沒有絕對的上限數值，真正的上限取決於預算結構：
1. 資料轉成向量（embedding）的 API 成本。
2. 向量資料庫檢索搜尋的運算成本。
3. 長期運作與維護該資料庫的基礎設施成本。

另外，資料庫中堆積越多高度相似的文本，檢索時就越容易一股腦抓出過多重複內容進 context。

更重要的是，當多個 Agent 自主對話、往返交互時，大量內容會堆積在 context 的中間位置。這會引發嚴重的**「迷失在中間（Lost in the middle）」**現象——語言模型通常對 context 的開頭與結尾記憶最深，夾在正中間的重要事實極容易被忽略。因此，主動壓縮中段內容、剔除無關資訊，不只是省錢，更是為了防止模型注意力失焦。

從整體架構的計分卡來看：
- **成本付出**：引入 RAG、re-ranker、MMR 與 compaction，代表系統必須額外執行 embedding 呼叫、re-ranking 模型調用、LLM 摘要運算，以及外部資料庫的讀寫。
- **效益換取**：大幅節省後續的主模型 context 空間，顯著降低長文本的推理費用，並確保最重要的文件留在視野內，提高推論可靠度。

最後必須注意的是檢索失敗的風險。當檢索與過濾機制出錯、把錯誤的片段當成唯一事實送入 context 時，模型往往會極度自信地給出完全錯誤的答案。在打造 context 保護機制的同時，持續監控並評估檢索結果的正確性，是整套系統不可或缺的防線。
