# Metrics：pass@k 與 pass^k

挑選模型時，很多人第一步是去看各大評測排行榜（Leaderboard）。排行榜上的分數看起來很直接：這個模型在基準測試（Benchmark）裡答對了幾題？最終答案正確的頻率有多高？

但光看答對率，往往無法反映真實產品的運作成本。假設排行榜第一名的模型答對率是 98%，第二名是 97%，第一名雖然高出 1%，調用成本卻貴了整整五倍。如果你的預算無限，選第一名當然沒問題；但如果要把可靠性（Reliability）、成本（Cost）與上下文長度（Context）這張評分卡（Scorecard）綜合起來看，第一名往往不是最合理的選擇。

排行榜通常只呈現這張評分卡中的其中一欄——可靠性，另外兩欄（成本與上下文）則幾乎被完全隱藏。回顧不同架構的取捨：引入工具會消耗上下文，RAG 能幫忙省回一些空間；Supervisor 架構能換回上下文容量，成本卻極為高昂；改用 Dispatcher 則能有效壓低花費。建立評測（Evaluations，簡稱 evals）的價值，正在於把這三項指標完整加總，讓團隊依據數據做決策，而不是憑感覺猜測哪種架構比較好。

### 基準測試只跑一次夠嗎？

回到評測本身，許多基準測試在評估模型或 Agent 時，通常只跑一次——也就是只給它一次解題機會。這種評估方式很難反映系統的真實表現。要理解測試結果，必須分清兩個經常讓人混淆的評估指標：`pass@k` 與 `pass^k`。

<!--image:2-->

#### pass@k：只要成功一次就算數

`pass@k` 衡量的是：在 $k$ 次嘗試中，Agent 至少產出一次正確解答的機率。

因為只要猜中一次就算成功，所以嘗試次數 $k$ 越增加，`pass@k` 的分數就越高。舉例來說，`pass@1` 是 50%，代表在評測任務中，模型在第一次嘗試時成功解開了一半的問題。

這個指標常見於程式碼生成（Coding）的基準測試中。在寫程式的情境下，我們通常很在意模型能否在第一次嘗試就寫對，或者在給定幾次機會內能不能給出一個可運行的版本。只要工具情境重視的是「單次成功」，`pass@k` 就非常適用。

#### pass^k：每一次都必須成功

另一種指標是 `pass^k`（也有人寫成 pass hat k，代表 $k$ 次方）。它衡量的是：在連續 $k$ 次嘗試中，每一次測試全部成功的機率。

隨著測試次數 $k$ 增加，`pass^k` 的分數會迅速下滑，因為它對模型與 Agent 的一致性（Consistency）要求極高。讓模型答對一次不難，但要連續跑三次、五次甚至五十次都完全正確，難度就會倍增。

假設單次成功的機率是 75%（0.75），連續跑三次都成功的機率就會掉到：

<!--image:3-->

$$0.75^3 \approx 42\%$$

這個指標對於面對使用者（Customer-facing）的 Agent 極為關鍵。使用者要求的是穩定、一致且符合規則的行為。以客服退款為例，如果公司政策不允許退款，就不能出現跑十次有九次拒絕、卻有一次答應退款的狀況。只要系統需要對外提供穩定的服務，就必須依賴 `pass^k` 來檢驗一致性。

### 依產品需求選擇評估指標

這兩個指標沒有優劣之分，而是取決於產品的使用情境：

- **pass@k**：適合以工具為導向、只要拿到一次正確解答就算過關的情境（例如程式碼生成輔助）。
- **pass^k**：適合直接面對客戶、絕不允許行為失控或不一致的 Agent。

以生涯諮詢產品為例，使用者因為不清楚未來的方向而來尋求協助。在這種情境下，`pass@k` 毫無意義——Agent 在十次嘗試裡猜中一次方向，對當前的使用者沒有任何幫助，除非他剛好是撞上正確答案的幸運兒。

相對地，如果系統在 `pass^k` 能維持 97% 的準確率，這個數字才真正具備參考價值。不過即使達到 97%，團隊也必須清楚意識到：這仍然代表每 100 位進線的使用者中，會有 3 個人拿到完全錯誤的生涯建議。單看一個百分比很容易讓人過度樂觀，換算成實際受影響的使用者比例，才能看清產品真正的可靠性風險。
