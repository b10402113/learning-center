# 建立自己的 eval

公開指標只看得到可靠性，要看見自己的場景，得自己出題。在挑選模型時，各大實驗室公布的公開評測（Benchmark）排行榜看起來很吸引人，但直接照著排行榜選模型，往往在實際業務中踩坑。這並不是廠商刻意造假或心懷不軌，各家實驗室確實都在認真跑測試，只是公開評測的變因太多，很難直接對應到你自己的應用情境。

要讓自己的 AI Agent 穩定運作，最可靠的方法不是盯著外部排行榜，而是從現有的手動測試長出一套專屬的最小評測集（eval）。

## 為什麼公開評測不能直接代表實際表現？

公開評測過去主要比對最終答案，但評測 Agent 時，越來越多基準開始檢驗「執行軌跡」（trajectory）——也就是 Agent 如何一步一步得到答案、中間的步驟合不合理。

然而，軌跡評測很容易變得過度僵化。例如，你原本預期 Agent 要「先搜尋、再抓取頁面、最後摘要」，但 Agent 實際上可能找到了一條你沒想過卻同樣有效的路徑。如果我們當初設計 Agent 是為了保留彈性，評測框架卻毫無彈性地硬性規定步驟，就會誤判合理的解答。

<!--image:1-->

除了評測指標本身的限制，公開評測難以重現還有幾個核心原因：

### 評測環境與測試框架（Harness）差異

評測框架內部包含大量的 prompt、防護欄（guardrails）與規則，這些設定會大幅改變 Agent 的行為。如果你在 Cloudstack 這種框架跑測試，就無法把 OpenAI 的模型放進同一個框架公平比較。只要測試框架不同，跑出來的分數就會失真。

維護評測環境也是巨大的工程。Epic AI 曾深入探討評測有多困難，其中最頭痛的就是環境建置與維護。即使是 OpenAI，在測試 o3 與 o4-mini 模型時，面對 SWE-bench Verified 的 500 道題目，也因為基礎架構的挑戰而只跑了 477 題。若環境有漏洞，不僅會引發嚴重錯誤，還可能讓 Agent 找到作弊（hack the eval）的漏洞——也就是摸透評測機制的檢查方式來得分，而不是真正解開問題。

### 計分方式與端點（Endpoint）的落差

不同評測題目的計分機制各有極限：

*   **正規表達式解析**：像 GPQA Diamond 常用 regex 來比對答案，試圖涵蓋所有邊界狀況，例如抓出答案究竟是單純的數字「42」、句子「答案是 42」，還是寫了一長串推論後的結尾。
*   **測試套件執行**：程式碼評測（如 SWE-bench Verified）則是直接跑測試套件，檢驗模型產生的程式碼能否通過。
*   **第二個 LLM 模擬對話**：像 TauBench 會用第二個 LLM 來模擬使用者與待測模型互動。但作為對手的那顆 LLM 選誰，會對跑分產生非常巨大的影響。

就連呼叫 API 的接口端點不同，成績也會完全變樣。OpenAI 表示自家模型在新的 responses 端點跑出來的成績比傳統的 chat completions 更好；Anthropic 在 chat completions 端點上只開放了部分功能；而 Minimax 甚至回報自家 API 與 chat completions 接口在 TauBench 上的分數差距高達 23%。

此外，底層託管商也有影響。Epic AI 曾在 GPQA Diamond 上測試多款開源模型，分別透過 Fireworks 和 Cerebras 等不同服務商呼叫，結果發現各家的準確度存在落差。有些服務商頻繁回傳 rate limit 錯誤、有些出現空回應，甚至實際最大 token 數低於官方宣稱的規格。

而且新推出的模型在評測上的表現，往往會比已發布一陣子的成熟模型差，因為成熟模型的底層錯誤多半已經修復。測試框架私下幫我們做了非常多雜事，換了一個框架，同一個模型用起來可能完全判若兩人。

## 從 20 到 50 題開始建立專屬 eval

既然不能完全仰賴外部榜單，就得自己做實驗。建立自己的評測集不需要一開始就追求成百上千題，Anthropic 建議，從 20 到 50 個簡單的任務開始，就是很好的起步。

<!--image:2-->

在早期開發 Agent 時，系統的每一個改動都會帶來明顯的影響。這時候最適合建立資料集：

1.  **取材自手動測試與真實錯誤**：把你平常手動測試的項目、系統曾經出現過的 bug、使用者回報的問題，以及上線前 QA 的驗收項目全部記錄下來。
2.  **標準必須是非黑即白的通過或失敗（Pass/Fail）**：好的評測任務必須能夠清楚判定是「通過」還是「失敗」。模糊不清的評分規章（vague rubrics）只會帶來飄忽不定的評測結果。
3.  **正向與反向行為都要測**：測試時不能只確認「該發生的行為有沒有發生」，也要確認「不該發生的行為有沒有被觸發」。例如，如果 Agent 具備工具呼叫能力，你不僅要測它在該用工具時有沒有呼叫，更要測在不該用工具的情境下，它會不會隨便亂叫。

<!--image:3-->

執行評測時，環境要盡可能貼近正式生產環境，但環境內部額外加入的特殊設定要減到最少，確保測試結果純粹反映 Agent 本身的表現。

## 使用 LLM-as-a-judge 的三大偏誤

當任務沒有單純的標準答案，越來越多人會選擇使用「模型當裁判」（LLM-as-a-judge），讓另一個 LLM 來打分。這確實方便，但 LLM 裁判存在幾個明顯的偏誤：

<!--image:4-->

*   **同家族偏好**：模型往往偏好來自同一家公司或同一個模型家族的回答。如果你評測的是 Anthropic 的 Agent，最好避免只用 Anthropic 的模型當裁判。
*   **自信偏誤**：LLM 裁判非常容易被「自信的語氣」吸引。如果待測模型給出了一個完全錯誤、但文字讀起來極具說服力且極其自信的答案，裁判模型很容易忽略錯誤而給出高分。
*   **順序偏誤**：如果你把兩個模型的答案同時送給裁判比較誰比較好，LLM 對答案呈現的先後順序非常敏感。進行兩兩比較時，必須多跑幾次評測，並在每一次測試時對調候選答案的順序（A 與 B 互換），避免順序干擾評分。

評測不是訂完標準就永遠不變的靜態作業，它的本質是持續規劃、實驗、驗證，並在發現盲點時勇敢打掉重來。藉由小規模、確定性高的自建評測，你才能在模型更新與提示詞調整的過程中，清楚掌握系統到底有沒有真正變好。
