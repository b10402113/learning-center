# 挑最簡單、做得到的那個系統

有了自己的 eval，才有辦法比較候選系統。當你著手設計一個 AI 應用時，最常遇到的困擾往往不是「該用什麼技術」，而是「到底要不要用 Agent？如果要，該用單一 Agent 還是多 Agent 系統？」

事實上，這根本不是一個非黑即白的二分法選擇，而是一道連續的光譜。在這一端，是你完全掌控的確定性程式碼（deterministic code）；在另一端，則是高度自主、結構複雜的多 Agent 系統。

做架構設計時，最健康的起手勢，永遠是盡可能從光譜的最左端出發——先挑最簡單、完全在掌握之內的做法，等發現走不通時，再一步步往右推。

## 從最左端出發：一次只加一個 LLM

一開始，最好的做法是完全不要放進任何大型語言模型（LLM）。你可以自己寫程式碼，或者讓 Copilot、Claude 替你生成，重點在於這是百分之百確定性的邏輯，由你掌控系統的每一步。

<!--image:1-->

接著，當你發現其中某個步驟需要自然語言處理的能力，傳統程式碼很難處理時，才在那個環節補上一個 LLM。要是後續又有另一個步驟需要，再視情況加入第二個。

如果單純呼叫 LLM 無法滿足需求，甚至直接換成更頂級的前端模型（frontier model）也解決不了問題時，下一步該考慮的就是單一 Agent（single agent）。藉由反思迴圈（reflective loop）與自我調整，單一 Agent 可以嘗試在反覆摸索中找出更精確的答案。此時，你的流程裡就有了一個 Agent，負責處理最困難的步驟，並將結果傳給後續的環節。

## 什麼時候該往光譜右側移動？

決定要把架構推到哪一個階段，主要看你對「路徑」的掌握程度：

<!--image:2-->

- **知道每一次的步驟，但中間有一步特別困難**：使用 LLM 驅動的工作流程（LLM-powered workflow）。
- **路徑未知，但所有可能走向的集合是已知的**：使用單一 Agent（single agent）。你定義好所有可能的箭頭與路徑，讓模型在執行期（runtime）自行決定要走哪一條。典型的例子就是客服聊天機器人（chatbot）——你無法預測使用者會問什麼，但你明確知道機器人能做什麼（例如介紹產品或公司資訊），也清楚它不該做什麼（例如解高等數學方程式）。
- **問題可以拆解為獨立的子問題，且各自需要大量上下文**：此時單一 Agent 已經無法負荷，多 Agent 系統（multi-agent systems）才會自然浮現。

多 Agent 系統的成本非常高昂，除非系統真的非它不可，否則不用急著引入。許多時候，最樸實的架構反而最管用。例如一個職涯諮詢系統（career advisor），如果核心需求只是做簡單的意圖分類，搭配一個分發器（dispatcher）就足以維持極小的上下文與極低的成本，即便它看起來不如多 Agent 炫目，卻是最精準切合問題的解法。

## 三欄成績單：權衡 Context、Reliability 與 Cost

評估架構時，可以用三個維度組成的「成績單」來衡量：

<!--image:3-->

1. **上下文（Context）**：
   每交給模型一個工具，輸入與輸出都在消耗寶貴的上下文視窗。雖然檢索增強生成（RAG）能買回一些空間，但要付出額外代價；子 Agent（sub-agents）能替主系統換回大量上下文，代價則是翻倍的成本。因此，當你面臨龐大的上下文壓力，必須把它切小才能維持輸出品質時，才是考慮多 Agent 系統的最強烈理由。

2. **可靠度（Reliability）**：
   系統的可靠度變化往往反直覺——越複雜、越先進的架構，不等於越可靠。加入回饋迴圈（feedback loops）通常能大幅拉高可靠度；但只要一引入模組交接（handoffs），錯誤就可能像滾雪球般層層放大，讓可靠度急遽下降。

3. **成本（Cost）**：
   除了極少數經過精細規劃的多 Agent 系統外，架構越往光譜右端靠攏，花費幾乎只會一路上升。你必須評估這個代價是否在合理範圍內。

## 沒有絕對定律，一切以量測為準

這些經驗法則——例如「交接會降低可靠度、回饋能提高可靠度」——是一般情況下的趨勢，但絕非不可撼動的定律。在你的特定業務情境下，情況可能完全不同。

像 Uber、Netflix 等大型企業，都公開分享過他們建構 AI 系統的架構選擇與權衡過程。你可以從別人的成敗中吸取養分，但不要照單全收。因為你的使用者不同、使用情境不同，適合他們的架構，套在你身上完全可能碰壁。

最踏實的做法，就是同時跑一個無聊的基礎工作流程，以及一個設計精巧的多 Agent 系統，多測幾次，算出它們的平均可靠度與花費，把各欄數字填上成績單。不管是透過自動化評估、手動點擊，還是請朋友把產品點過一百次，實測都是確認系統體質的唯一途徑。

<!--image:4-->

隨著 AI 技術逐漸成熟，未來的技術面試將不再只停留在「用過哪些工具」，而是會深入探討「為什麼選工作流程？為什麼選 Agent？你在上下文、可靠度與成本之間做了什麼取捨？」

先挑選光譜上最簡單、能把事情做好的方案，建立足夠的測試案例來驗證你的假設，並且隨時做好「發現自己徹底猜錯」的心態準備。這才是打造 AI 系統最扎實的途徑。
