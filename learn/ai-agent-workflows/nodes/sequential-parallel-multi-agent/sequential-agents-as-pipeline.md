# Sequential：每一步都是一個完整 agent 的管線

如果把所有任務、工具和規則全塞進同一個單一 agent 裡，系統很快就會不堪負荷：上下文（context）塞得太滿、容易遺忘重要資訊，也大幅提高幻覺與出錯的機率。解決這個問題的方式，就是轉向多 agent 架構（multi-agent systems），讓具備特定專業的 agent 各自負責明確的工作。

在各種多 agent 架構中，最基礎也最直觀的模式就是 **Sequential**。在文獻、研究論文或書籍中，這種架構常被稱為 prompt chaining、pipeline、chain、waterfall 或 cascade。這裡統稱為 sequential。

## 看似 prompt chaining，骨子裡是完整的 agent

從流程圖的角度來看，sequential 的拓撲結構（topology）與 prompt chaining 幾乎一模一樣：前一個環節的輸出，直接變成下一個環節的輸入，形成一條直線。

<!--image:1-->

兩者最大的差異在於：**管線中的每一個節點，都是一個功能完整的獨立 agent。**

在一般的 prompt chaining 工作流程中，單一步驟往往只是一次性的 LLM 呼叫，產出結果後就立刻往下傳；一旦那次呼叫失敗或產出不佳，錯誤就直接順流而下。

但在 sequential 架構中，每個步驟本身都是一個單 agent 系統（例如 ReAct 或 CodeAct 迴圈）。這意味著每個節點都能夠：

<!--image:2-->

* **自主規劃（Planning）**：決定達成目標所需的步驟。
* **呼叫工具（Tool use）**：使用專屬於該步驟的工具集查詢資料或執行動作。
* **自我反思與重試（Reflection & Retry）**：檢查自己的輸出是否符合要求。如果第一次執行失敗或結果不如預期，agent 可以在自己的內部迴圈中自我修正、再次嘗試，直到產出滿意為止，而不是把錯誤的半成品直接丟給下一步。

不同步驟的 agent 完全可以採用不同的模型（LLM）、不同的 system prompt，以及不同的工具集。各個 agent 甚至不需要知道彼此的存在，只要把輸入處理好、產出約定格式的結果即可。

## 何時使用：當下游任務嚴格依賴上游的產出

Sequential 架構的適用情境非常明確：**當某個 agent 的工作，必須建立在前一個 agent 的成果之上時。**

舉個具體的例子：如果你想替使用者規劃就學方案，但連他究竟想當「黑手黑手技師（mechanic）」還是「機械工程師（mechanical engineer）」都還不清楚，後續的學校推薦就根本無從做起。

以職涯諮詢服務為例，整個 sequential 管線可以這樣分工：

1. **職業推薦 Agent（Career Agent）**：
   * **輸入**：使用者的個人特質、興趣與職涯目標。
   * **內部運作**：它擬定規劃，呼叫資料庫搜尋工具找出合適的職業方向，反思搜尋結果是否契合使用者背景，持續在迴圈中調整，直到確認推薦名單。
   * **輸出**：建議的職業方向。
2. **培訓規劃 Agent（Training Agent）**：
   * **輸入**：接收上游傳來的職業方向。
   * **內部運作**：以自己的專屬 prompt 與工具，規劃出達成該職業目標所需的訓練課程、學校或學習路徑。
   * **輸出**：具體的培訓管道。
3. **資金補助 Agent（Funding Agent）**：
   * **輸入**：接收選定的培訓路徑。
   * **內部運作**：針對所需費用，尋找獎學金、就學貸款或政府補助方案。
   * **輸出**：最終的資金配套建議。

使用者最終得到的完整回覆，一樣涵蓋了職業推薦、培訓選擇與付款方案，但背後是由三個各司其職、各具專屬 prompt 與模型的獨立 agent 依序串聯完成。

## 表現評估：Context、Reliability、Cost、Latency

評估 sequential 架構時，可以從四個維度來看它的取捨：

<!--image:3-->

* **Context（表現提升）**：原本又臭又長的巨大 prompt，被拆解成各個專屬 agent 的小型 prompt。每個 agent 只接觸與自己任務相關的 context，記憶負擔大幅減輕，有效降低混亂與遺忘的機率。
* **Reliability（需注意錯誤累積）**：最大的風險在於**錯誤會在鏈條中向下累積（errors compounding）**。語言模型往往非常信任前一個模型傳過來的內容。如果上游 agent 給出了一個充滿自信卻完全錯誤的輸出，下游 agent 通常不會主動質疑「這真的對嗎？」，而是照單全收並在此基礎上繼續推導，導致後續結果嚴重走偏。因此，在 sequential 架構中，各步驟之間的驗證（validation）機制至關重要。
* **Cost（通常最低）**：在各類 multi-agent 架構中，sequential 通常是花費最便宜的配置之一。每一步的呼叫次數與流程是固定的，不會產生無窮發散的額外溝通成本（雖然隨著分類模型與 GPT 等技術演進，某些架構的成本也持續在下降）。
* **Latency（偏高且呈線性疊加）**：因為這是一條嚴格依序執行的管線，下一個 agent 必須苦等上一個 agent 完全執行完畢才能啟動。每個 agent 內部可能還包含多輪規劃與反思迴圈，每增加一個 agent，等待時間就會以線性方式（linear）直接往上疊加，整體的延遲相當高。
