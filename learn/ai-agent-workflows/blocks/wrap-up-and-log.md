# Wrap Up and Log（倒數收尾與記錄）

## 問題

工作流設有迴圈次數上限或超時機制，但系統還沒產出滿意答案就快觸及上限。直接中斷會浪費已經跑完的工作，把殘缺內容當答案又不可信。需要一個介於「成功」與「報錯」之間的收尾方式。

## 前置條件

- 流程有一個可預測的迭代上限，例如最大輪數 $N$。
- 系統能在倒數階段主動插入額外指令。
- 有一個可寫入的日誌、資料表或儲存位置。

## 步驟

1. 在接近上限時（例如第 $N-1$ 輪）介入，告訴模型：「請在下一輪做總結，給出目前最好的摘要作為結束。」
2. 取得這份摘要，將它寫入日誌或資料庫。
3. 下次同一位使用者重新執行時，把這份紀錄當作上下文參考。
4. 開發團隊定期檢視哪些情境容易觸發終止條件，據此調整 system prompt 或重新界定任務範圍。

## 例子

一個反覆生成職涯建議的 evaluator-optimizer 在第三輪仍未通過時，程式碼在最後一輪改送「請整理目前最佳版本」的指令，拿到摘要後寫入紀錄。使用者下次回來時，系統可以把上次的摘要接進新一輪，而不是從零開始。

## 失敗模式

- **太晚介入**：等到最後一輪才要求總結，模型可能沒有足夠回合完成，摘要品質低落。
- **摘要被當成通過**：收尾結果仍應標記為「未通過」，否則會掩蓋系統極限。
- **只記錄不分析**：日誌若沒有回頭調整 prompt 或範圍，就只是堆資料，不會讓流程變好。
- **與 fail early 混淆**：這裡回傳的是盡力而為的摘要，不是錯誤；兩者的適用情境不同。

## 進階

Wrap up and log 與 [[fail-early]] 是同一組終止條件的兩種收尾策略：一個選擇誠實失敗，一個選擇保留部分成果。成熟系統會依任務性質切換，甚至在同一流程的不同步驟使用不同策略。
