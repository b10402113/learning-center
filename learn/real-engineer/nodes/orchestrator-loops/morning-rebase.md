# 設計 Auto Rebase 迴圈：用確定性腳本與 Agent 自動化清理落後 PR

不論是日常的功能開發還是前述的棘輪流程，活躍的專案中常常會看到 PR 被晾在清單上好幾天甚至兩週。這段時間底層的程式庫不斷頻繁變動，PR 很快就落後於目標分支，最後甚至沒有人說得清楚該怎麼收拾衝突才能讓它順利合入。

為了解決這個問題，可以在軟體工廠中建立一條「自動 Rebase（Auto Rebase）」的自動化任務：每天半夜定期把所有開啟中的 PR 與基底分支進行一次 rebase。工程師早上開工時，清單上的 PR 就不會留下一堆衝突，而是早就被處理得乾乾淨淨。

在設計這套流程時，核心關鍵在於「確定性（determinism）」，絕不能一遇到問題就盲目地動用 AI 代理人。

## 堅持確定性優先：能用腳本就不要叫 Agent

在開始處理 rebase 時，最重要的一點是：有很高的機率根本不需要動用代理人。

<!--image:1-->

有時候 GitHub 等平台顯示衝突或狀態落後，純粹只是 PR 分支太久沒有同步。只要用一般的 Git 指令跑一次 rebase，直接接受變更，就能順暢完成。因此在流程設計上，必須先走確定性的腳本處理：

1. **先用腳本嘗試 Rebase**：完全不引入代理人，直接在環境內執行標準的 rebase 指令。
2. **確定性成功就直接推送**：如果腳本順利跑完沒有衝突，立刻將結果強制推回 Git 託管平台，任務就此結束。這個流程一個模型 token 都不會消耗，成本極低。
3. **遇到衝突才喚醒代理人**：只有當確定性的腳本失敗、確定出現合併衝突時，才在那個當下啟動代理人來修復衝突。
4. **代理人修復成功後推送**：如果代理人能順利解開衝突，同樣把結果推回 Git 託管平台。

無論是腳本還是代理人成功解決衝突，推回分支時都必須使用帶租約的強制推送（`--force-with-lease`）。這能確保只有在執行期間沒有其他人推送新程式碼的前提下才會寫入，避免不小心覆蓋掉工程師最新的改動。

這就是整個自動 rebase 的快樂路徑（happy path）。

## Runner 的分配與兩種觸發時機

當面對大量 PR 時，執行環境的架構也需要仔細考量。如果手上有上百個 PR 需要處理，不應該讓單一執行器扛下所有工作。

即使是跑確定性的腳本，環境中依然需要拉下程式碼才能驗證 rebase 是否可行。考慮到現代 CI 環境建立執行器的成本相當低廉，最簡單清晰的做法就是「一個 PR 分配一個執行器」。由中央的協調器計算出需要處理的 PR 數量，再為每個 PR 各自排程一個專屬的執行器同步處理。

在觸發條件上，可以設計雙軌機制：

<!--image:2-->

* **定時批次排程**：預設在每天半夜執行一次。如果團隊成員都在同一個時區，半夜是安全且 CI 負載較低的時段。
* **手動標籤觸發**：只有半夜跑一次，對某些快節奏的工作流程來說可能不夠頻繁。例如剛合入一個核心 PR，導致其他幾個開啟中的 PR 立即產生衝突時，開發者只要在這些 PR 上貼上指定標籤，協調器就會馬上排程執行器進行 rebase。

## 非快樂路徑：衝突解不開就標記 Blocked 交回人手

設計這套系統不能只考慮順利修完的情形，更要妥善處理失敗的非快樂路徑。

當代理人接手修復衝突時，很可能會遇到無法輕易解決的僵局；或者更常見的是，這張 PR 的修改範圍其實已經被目前 `main` 分支上的其他改動取代（superseded），再硬解衝突也沒有意義。

這時系統必須有一套把工作交還給人類的退場機制：

<!--image:3-->

1. **在工單追蹤系統建立 Issue**：前往團隊平常用來追蹤工作的工單追蹤系統（例如 Linear、Jira 或 GitLab Issues），開一張票指派給人類工程師查看與裁決。
2. **在 Git 託管平台標記為 `blocked`**：在 PR 上掛上 `blocked` 標籤，讓團隊成員在掃視 PR 清單時，一眼就能看出哪幾張已經卡住、哪幾張仍處於最新狀態。
3. **協調器過濾封鎖狀態**：協調器在抓取待處理 PR 時，除了只挑出與基底分支有衝突或落後的 PR 之外，還必須主動排除帶有 `blocked` 標籤的 PR，避免系統每天重複浪費資源去跑已經卡住的項目。

## 系統節流與雙邊狀態同步

如果想要調整整個自動化迴圈的運作節奏，可以透過幾個控制點來加速或減速。例如調整定時排程的頻率（改為兩天一次、每週一次），或是加入門檻條件（累積滿一定數量的落後 PR 才啟動），也可以在協調器抓取時限制單次處理的 PR 數量上限。

最後，務必注意 Git 託管平台與工單追蹤系統之間的狀態同步。如果團隊使用的是 GitHub，PR 與 Issue 都在同一個平台上，資訊相對好整合；但如果團隊使用的是 GitLab 搭配 Linear，兩邊的狀態若失去同步，工程師查閱時就會非常困擾。因此在自動化腳本中，標記 PR 狀態與建立追蹤 Issue 的動作必須一氣呵成，確保雙邊資訊隨時對齊。

透過「先腳本、後代理人、解不開交還人類」的三層防線，既能守住 token 成本與執行速度，又能讓團隊每天早晨打開專案時，面對的都是已經處理好衝突、隨時可以合入的整潔程式庫。

前面討論的架構改善、棘輪規則與晨間 rebase，全都是協調器主動發起或依賴 Git 事件推動的受控迴圈。然而，一旦把自動化延伸到即時監控系統時，協調器面對的就不再是可預期的排程，而是外部高頻湧入的警報衝擊。
