# 用 Ratchet Loop 逐步升級程式碼庫的 Lint 規則

在前面建立架構改善迴圈時，重點在於透過標籤與門檻防範重複提案。同樣的控制邏輯，在提升程式碼品質規範時也能發揮關鍵作用。

當你為專案新增一條程式碼檢查（lint）規則時，往往會面臨一個難題：如果新規則只檢查準備提交的檔案（staged files），負責實作功能的 AI 代理人在日常開發時，就會在寫程式的過程中冷不防被這些既有的舊錯誤絆倒；但若直接對整個程式庫一次強制套用，又會產生海量的錯誤需要修復，導致整個開發流程卡死。

理想的做法是一口氣讓整個程式庫符合標準，解放實作代理人的負擔。要做到這件事，可以使用一種稱為「棘輪」（ratchet）的自動化流程。棘輪的物理特性是只能往前轉、不能往後退。套用在 lint 規則上，就是一步步鎖緊標準，只讓程式庫變得更嚴格、更安全，直到新規範完全落實。

## 核心架構：兩桶規則與畢業機制

要建立棘輪流程，首先要在專案中將 lint 規則分成兩種等級。以常見的 npm 指令為例，可以定義出兩桶規則：

<!-- derived -->
```json
{
  "scripts": {
    "lint:all": "eslint . --rule '...'",
    "lint:strict": "eslint . --rule '...'"
  }
}
```

- `npm run lint:all`：包含所有規則，包含那些目前已知專案中還會失敗的新規則。
- `npm run lint:strict`：只包含預期全數通過的嚴格規則，也就是現行主分支必須百分之百遵守的規範。

棘輪的最終目的，就是把規則從「全部（all）」這桶逐一搬移到「嚴格（strict）」這桶，直到兩者完全等價，最終就能直接刪除 `lint:all`。

<!--image:1-->

流程中的關鍵在於「畢業檢查」（graduation）：
當流程執行規則檢查並尋找錯誤時，如果發現某條規則已經**沒有任何違規**，系統就會發起畢業步驟，把該規則正式加入 `lint:strict` 的清單中，並為此建立一個畢業 PR。經過工程師審查合併後，這條規則就再也不允許被違反。

## 棘輪迴圈的運作流程

整個流程由協調器（orchestrator）來驅動，具體步驟如下：

<!--image:2-->

1. **定時啟動執行器**：協調器預設每天定時執行一次，啟動一個執行器（runner）。
2. **查詢現有 PR**：從 Git 託管平台抓取目前所有標有 `ratchet` 標籤的 PR，傳入執行器中，避免重複修復相同的規則。
3. **檢查堆積上限**：如果目前尚未合併的 ratchet PR 超過 5 個（避免人類審查者來不及看而讓 PR 大量堆積），執行器就先停止本次運作。
4. **執行檢查並修復**：
   - 執行規則並找出所有違規。
   - 如果某條規則已經零失敗，直接提 PR 將其「畢業」升級至 strict 規則組。
   - 如果仍有失敗，則挑選其中「一個」失敗案例進行修復。
5. **建立 PR**：將修復成果推送到 Git 託管平台並建立 PR，打上 `ratchet` 標籤，等待人類工程師審查與合併。

## 調校節奏的加速器

這個流程不是僵化的，有許多參數可以根據團隊的節奏上下調整：

- **啟動頻率**：協調器可以從每天一次調高到每天四次。
- **堆積上限**：若審查速度跟得上，可以把上限從 5 個 PR 放寬到 10 個。
- **單次修復量**：執行器不必一次只修一個問題。它可以同時挑選 5 個失敗案例，指派給 5 個子代理人分別修復，各自發起獨立的 PR 讓工程師分開審查。

## 透過 Merge 事件打造即時迴圈

除了固定的時間排程，協調器還可以監聽 Git 託管平台發出的事件。

一個極具彈性的做法是監聽「PR 合併（merge）」事件：當人類審查並合併了一個 ratchet PR，協調器隨即接收到該事件，並立刻啟動下一個執行器進行下一輪修復。

<!--image:3-->

這種觸發機制能自動契合開發者的節奏：如果工程師當天很有空、想加速推進程式庫的標準，只要持續審查合併，系統就會源源不絕地產生下一個修復 PR；反之，若工程師忙於其他工作沒有合併 PR，流程就會自然暫停，不會無止境地產生待審查程式碼。

藉由協調器監聽事件、代理人彈性判斷分支條件（修復失敗或直接升級規則），搭配自動化或人工審查，整個程式庫就會隨時間自動邁向更嚴格的架構標準。

然而，當棘輪迴圈與日常開發持續產出大量 PR 時，若這些 PR 在主機上擱置數天，底層程式庫的變更很快就會引發衝突。如何讓這些排隊中的 PR 每天自動保持最新狀態，就是下一個關鍵問題。
