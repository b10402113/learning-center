# 從 Push 到 Pull Queue：用分組與嚴重度門檻控制 Alert 處理節奏

在前面幾種情境中，協調器都能從容掌握啟動的時間點。但當系統串接外部監控來源時，情況就完全不同了。應用程式拋出錯誤時會發送錯誤回報、系統出現特定狀況時會觸發告警，其中一種特別實用卻高頻的監控，就是掛在資料庫上的慢查詢監控（slow query monitor）。

如果不是專職的資料庫專家，往往需要工具輔助，才能判斷到底該加哪些索引（index），或是該如何調整資料庫設計以發揮最佳效能。假設把慢查詢監控串接到系統的協調器，每當資料庫出現慢查詢，協調器就會收到警報（alert）。

這時會面臨一個棘手的挑戰：慢查詢監控觸發的頻率無法預測。如果資料庫負載驟增、警報頻繁觸發，絕對不能每收到一次警報就啟動一個執行器。要是照單全收，瞬間就會把大型語言模型的 token 額度全部燒光，拖垮整個系統。

## Push 架構的失控問題

這個任務的最終目標，是讓執行器針對慢查詢找出潛在的修復方案，並發起 PR。同時，執行器也應該在工單追蹤系統發布工單說明修復內容。

最直覺卻最危險的做法，是讓協調器單純扮演被動接收端：一旦收到監控警報，就立刻啟動一個執行器去分析並修復。

這種「推送（push）」架構的問題在於，協調器完全喪失了節奏控制權。當系統瞬間湧入 100 個警報，協調器就會一口氣啟動 100 個執行器。處理速度完全被外部事件綁架，節奏徹底失控。

## 改用 Pull Queue 掌控處理節奏

要解決節奏失控，核心是把被動的 push 改為主動的拉取（pull）。

<!--image:2-->

先把警報放進佇列（queue）中，再由協調器依照設定的節奏定期去拉取——例如每天拉取一次。改成 pull 模式之後，協調器就能重新拿回節奏的主導權：
- 改成一天檢查兩次或三次。
- 設定累積數量門檻，例如「佇列累積超過 40 個警報時」才啟動批次處理。

這裡的佇列不一定要自己架設額外的訊息佇列服務。可以讓協調器把警報存入一般的關聯式資料庫，甚至可以直接利用第三方監控服務的既有功能。舉例來說，若資料庫託管在 PlanetScale，協調器可以每天呼叫一次 PlanetScale API，詢問「最近出現了哪些慢查詢？」。透過定時向外部 API 拉取資料，就能完全省去自建警報轉發與佇列架構的負擔。

## 用分組 Runner 避免重複工單

一次拉取大量警報後，不能把每筆警報都視為獨立問題，因為其中許多警報通常都指向同一個根本原因。

這時需要啟動第一階段的分組 runner（grouping runner）：
1. **聚合分析**：分組執行器負責分析拉進來的所有警報，將彼此相關的慢查詢歸納成同一個群組。
2. **比對既有工單**：為了避免在工單系統建立大量重複的工單，分組執行器會先拉取工單追蹤系統中既有的慢查詢工單。如果某些警報對應的問題已經被記錄過，就可以直接忽略。
3. **建立代表工單**：確認不是重複問題後，分組執行器再針對各個群組建立相應的工單，並回報給協調器。

<!--image:3-->

完成分組並建立工單後，協調器再針對「尚未發起 PR」的工單，啟動負責修復的執行器。修復執行器產出 PR 後，直接回頭更新原本的工單進度，而不需要每次都開新工單來說明解法。

## 引入嚴重度門檻避免工單淹沒

引入分組執行器之後，仍有一個潛在隱憂：工單系統可能很快就被海量的慢查詢工單塞滿，變成難以維護的雜訊。

解決方法是在分組 runner 分析群組時，加入「嚴重度檢查（severity check）」。分組執行器在分析時，會對每個警報群組做出裁決，標註為「嚴重（severe）」或「輕微（mild）」。

<!--image:4-->

評估嚴重度帶來了兩大好處：
- **動態升級**：有些問題初期影響很小（mild），但隨著系統資料量增加，查詢延遲可能惡化，該工單後續就能被提升為嚴重（severe）。
- **修復門檻**：協調器可以設定過濾條件，只針對被標記為「嚴重」的慢查詢啟動修復執行器。

在這個流程中，工單追蹤系統承載了大量的中間狀態，而標籤則是不可或缺的過濾依據。透過標籤，系統可以精準挑選需要處理的項目，不讓無關緊要的小問題打亂步調。

## 總結整個處理迴圈

將所有環節串聯起來，整個健全的監控自動化迴圈如下：

1. **Pull（拉取）**：協調器依照設定的週期（或累積門檻）從佇列或第三方 API 主動拉取警報。
2. **Group & Rate（分組與評級）**：分組執行器將相關警報合併、過濾既有工單，並評定嚴重度（如 severe 與 mild）。
3. **Filter & Fix（過濾與修復）**：協調器只針對達標的嚴重問題啟動修復執行器，建立 PR 並回寫工單。

這套架構不只適用於資料庫慢查詢，任何反映應用程式健康狀況的外部數據——無論是效能監控指標、系統日誌還是錯誤回報——都可以套用相同模式，打造出一套能自動讀取指標並持續改善系統品質的穩定流程。
