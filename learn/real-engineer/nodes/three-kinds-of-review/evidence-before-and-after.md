# 在 PR 中提供硬證據：用 Before 與 After 證明改動有效

Summary 講清楚 why 之後，下一個問題是怎麼確認它真的改對了。

審查同事或 AI Agent 提交的 Pull Request（PR）時，最耗時的往往是驗證過程。

你必須把分支拉回本機、安裝依賴，還要親自執行並點擊測試，才能確定改動是否有效。

要解決這個問題，PR 內文必須附上足夠的「硬證據」（hard evidence）。

當內文附帶具體且無可爭議的證明時，審查者就不需要親自 clone 專案下來驗證。

這能大幅加快審查速度，也能提高對程式碼的信心。

## 為什麼必須同時提供 Before 與 After？

有效的硬證據，核心在於對比：

<!--image:1-->

1. **Before 證據（失敗狀態）**：呈現修改前的錯誤或缺失。
2. **After 證據（成功狀態）**：呈現修改後順利運作的結果。

很多人在寫 PR 時只附上改完後的正常畫面，但單有 After 並不足夠。

附上 Before 證據，才能證實原本的系統確實處於損壞或未支援的狀態。

無論是修復 Bug 還是開發新功能，要求提供 Before 證據都是關鍵門檻。

這要求提交者（尤其是 AI Agent）必須明確重現問題。

這樣才能確認「原本真的不行、改完後確實可行」，而不是碰巧通過測試。

## 區分 S-tier 與 A-tier 證據

在建立 PR 規範或設計 Agent 的 PR 技能時，具體證據可以分為兩個等級：

<!--image:2-->

### S-tier：畫面截圖（Screenshots）

改動涉及視覺介面或排版，且執行環境支援時，截圖是最高等級（S-tier）的證據。

一組修改前與修改後的截圖對照，能讓審查者一目了然。

審查者能在幾秒鐘內確認畫面改動完全符合預期。

### A-tier：執行導向的證據（Execution-based Evidence）

如果改動不涉及前端介面，就必須提供執行導向的證據（A-tier）。

這代表必須實際執行程式碼，擷取終端機的 Console 輸出或測試報告。

內容需要清楚標示：

- 修改前，哪一個具體測試失敗了（附上失敗的報錯訊息）。
- 修改後，該測試如何轉為成功通過。

有了這些紮實的對照證據，審查者就能確信改動確實發揮了作用，省去反覆拉程式碼除錯的時間。
