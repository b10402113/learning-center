# 用 Show Me 風格的摘要，在看程式碼前先搞懂 PR 的「為什麼」

三層煞車裡，人工審查最貴，所以第一件事是讓每則 PR 在看 code 之前就自己說清楚。

讓 AI Agent 協助開發時，人工審閱（code review）通常是最大瓶頸。

改善審查流程有兩個核心目標：
第一是加快速度，讓審查者能最快看懂 PR。
第二是排定審查時間的優先順序。
並非所有 PR 都需要同等心力，有些改動可以快速帶過，有些則必須嚴格把關。

和 Agent 協作常會遇到一個痛點：Agent 很不擅長寫 PR 描述（PR description）。
產出的 PR 內文常充斥冗長且無意義的廢話。
這類文字讀起來相當吃力，甚至讓人完全不想點開審查。
過去這個問題常讓人覺得無解，彷彿 Agent 寫出來的說明注定就是難以控制的文字垃圾（slop）。

解決這個困境的關鍵做法，是採用「Show Me」skill。

Show Me 的核心概念，是引導 Agent 用視覺化方式幫助讀者理解當前主題。
它對 Agent 有明確的要求：
- 略過客套開場白（skip preamble）。
- 文字說明保持極簡（keep prose brief）。
- 大量運用視覺化的「虛擬碼解說」（visual pseudocode explainers）。

這種虛擬碼解說效果驚人地好。
不論是檢視 UI 變更、釐清檔案職責，或是用 Mermaid 圖表呈現元件互動與時間流程，都能一目了然。
在表達元件變更、檔案結構調整、呼叫樹（call tree）或呼叫堆疊（call stack）的 diff 時，效果也遠比純文字清楚。

審查者不用大海撈針找意圖，理解速度就會大幅提升。
在看進具體程式碼之前，就已經先掌握這份改動背後的「Why」：為什麼要改這段程式碼。

只要把 Show Me 稍微修改，就能直接套用在 PR 上。
在專案中執行 `npm run reset add pr skill` 即可使用這個改編版本。
它的本質是一份撰寫 PR 內文的範本（template），附帶一段簡短的觸發說明：「use when writing a PR body」。

<!--image:2-->

這份範本最頂端是 Summary 區塊，完全沿用 Show Me 的視覺指示與結構。
頂端 Summary 的唯一目的，是讓審查者用最短時間掌握改動的核心原因。

審查速度還有另一個面向。
理解「為什麼要改」之後，還必須確認「改得對不對」。
這時 Agent 必須提供扎實的客觀證據（hard evidence），證明改動確實符合預期。
審查者就不需要每次把分支拉回本機，手動啟動專案逐一測試驗證。
