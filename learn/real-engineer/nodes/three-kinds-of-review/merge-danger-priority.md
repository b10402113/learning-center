# 用單雙向門與爆炸半徑決定 PR 審查深度

有了摘要和證據，還剩一個問題：這則 PR 值得你花多少時間？

談到 pull request（PR）的審查優先順序，很多人第一時間很難接受：難道不是每則 PR 都該仔細審？甚至有些 PR 真的能不用審嗎？

分配審查資源時，可以用「合併危險度（merge danger）」這個框架來評估。這個架構主要由兩個維度組成：門的方向（door）與爆炸半徑（blast radius）。

## 單向門與雙向門

「門」的概念來自 AWS 的決策模型。在軟體開發裡，每則 PR 都能歸類為單向門（one-way door）或雙向門（two-way door）。

雙向門代表你可以走過去，需要時隨時能走回原處。把這種 PR 合併（merge）進主分支後，就算發現問題，也能隨時直接退回（unmerge 或 revert），不會留下無法挽回的後果。

<!--image:1-->

單向門則不同，穿過就只能往前，無法直接回頭。程式碼一旦合併且部署，就會立刻產生實質影響。

例如：
- 資料遺失
- 產生額外雲端費用
- 牽涉資安隱患
- 觸發外部動作，像是直接寄信給五萬名使用者
- 公開函式庫出現破壞性變更（breaking change）

面對單向門的變更，審查必須比雙向門嚴格許多。

## 什麼是爆炸半徑？

評估合併危險度的第二個維度，是變更的「爆炸半徑（blast radius）」。這代表萬一程式碼真的出事，潛在的波及範圍有多廣、影響程度有多深。

<!--image:2-->

爆炸半徑與門的類型是各自獨立的概念：
- 有些變更是雙向門，出事當下可能很慘，但因為能輕鬆退回，風險仍在可控範圍。
- 如果 PR 是單向門，又帶有極大的爆炸半徑，就必須用最高規格逐行徹底審查。

把這兩個維度合在一起，就能清楚排定每則 PR 該花多少時間與精力審查。

## 專案性質決定整體風險分布

這兩個維度不僅取決於變更內容本身，也和專案類型高度相關。

在使用者還不多的個人專案裡，大概 95% 的變更都是雙向門，隨時想改什麼都能改。

如果專案屬於醫療或金融領域，背負龐大的資安與合規責任，許多變更自然會落在單向門。

即使在要求嚴格的領域，也不代表每則 PR 都是危險的單向門。依然能透過門的方向與爆炸半徑，分出哪些需要深入審查、哪些能快速通關。

爆炸半徑很小的雙向門變更，甚至能考慮直接跳過人工審查，合併到 main 分支觀察即可。

要省下真人審查的時間，前提是團隊具備扎實的自動化檢查與自動化審查機制，隨時守住基本品質底線。
