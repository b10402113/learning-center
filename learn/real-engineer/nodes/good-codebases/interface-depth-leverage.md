# 用五個核心詞彙判斷模組的深與淺

戰略思考的責任交到你手上之後，第一步是先能跟 agent 講同一種語言。

社群上常有人討論一個問題：到底該不該讓 AI agent 寫測試？

許多人反對的理由，是 agent 常常寫出品質低劣的測試。最常見的狀況就是寫出一堆「套套邏輯測試」（tautological tests），也就是測試只把上面的程式碼原封不動抄一次。例如程式裡定義了一個常數 `maxRetries = 3`，agent 寫的測試就命名為「重試三次」，裡面的斷言僅僅是驗證 `maxRetries === 3`。

這種測試毫無價值。它沒有驗證任何實際行為，只驗證了程式碼的表面外形。真正該測試的是拿 `maxRetries` 來執行重試邏輯的函式，而不是確認這個設定值是不是 3。

與其責怪 agent 產出爛測試，更該檢討的是為什麼程式庫允許這種測試被寫出來。如果程式庫的架構設計能讓爛測試根本無法寫出，agent 自然只能寫出好測試。

要做到這件事，關鍵在於替程式庫建立一套清晰的設計語彙。當你和 agent 討論架構時，agent 常常在不同對話裡東拼西湊，這次提六角架構、下次又拋出領域驅動設計（DDD）的術語。一套固定的詞彙能鎖定討論範圍，掌握其中五個核心詞彙，就能明確判斷一個模組究竟是「深」還是「淺」。

## 介面（Interface）與實作（Implementation）

任何規模的程式碼通常都會被切分成不同區塊，這些互相溝通的區塊就是模組（module）。每個模組都由兩部分組成：

<!--image:1-->

1. **介面（Interface）**：呼叫端為了正確使用這個模組，所必須知道的一切資訊。
2. **實作（Implementation）**：模組為了達成自身職責，在內部實際執行的所有程式本體與細節。

以 JavaScript 內建的 `JSON.parse` 為例，它的介面非常單純。呼叫端只要知道傳入一段 JSON 字串，它就會轉成 JavaScript 物件；如果傳入不合法的 JSON，它會拋出錯誤。

在這層介面背後的實作，處理了極其龐雜的工作。例如詞法分析（tokenizing）、字串跳脫、代理對（surrogate pairs）、數字格式、錯誤位置標記，以及 reviver 回呼函式等。呼叫端完全不需要知道這些實作細節，就能直接使用它。

## 深度（Depth）

有了介面與實作的劃分，就能定義什麼是好模組、什麼是壞模組。衡量標準就是「深度」。

`JSON.parse` 就是典型的「深模組」（deep module）。深度指的是呼叫端每學習一個單位的介面，能觸發多少行為。呼叫端幾乎不需要投入學習成本，就能換取龐大的功能價值，投資報酬率極高。

相反地，「淺模組」（shallow module）又是什麼樣子？

假設有一個處理 Git 相關操作的模組，介面暴露了一堆細碎的函式：`ensureIsGitRepo`、`fetch`、`merge`，每個函式內部只是單純轉呼叫底層指令。這就是淺模組。呼叫端必須同時記住這三個函式，而且必須自己保證每一次都按照正確的順序呼叫。

<!--image:2-->

如果改寫成深模組，介面只需要暴露一個函式 `pull`。呼叫端只要記得呼叫 `pull`，模組內部就會依序檢查是否為儲存庫、抓取遠端更新、合併分支。

實務專案中的權限檢查也很常見這種封裝方式：

```typescript

  return {
```

## 槓桿（Leverage）

深模組帶給呼叫端的好處，稱為「槓桿」。

使用深模組時，呼叫端以極小的介面成本，撬動了龐大的內部實作與行為。淺模組則幾乎沒有槓桿。呼叫端學了半天，只是在呼叫一些直接穿透到底層的細碎函式。

當模組在程式庫裡被呼叫的次數越多，槓桿的差距就越明顯。如果程式庫裡有 12 處都在自行組合那些淺模組函式，agent 遲早會在某個地方搞錯順序而引發錯誤；而深模組每一次被呼叫，行為都完全一致。

<!--image:3-->

槓桿效益同樣會反映在測試上。面對淺模組，agent 會傾向替每一個細碎的單一函式各自寫單元測試，確保它們各自能動，卻往往測不到串連起來的真實流程。

面對深模組，agent 沒有細碎函式可測，只能針對暴露出來的完整流程寫測試。這讓測試本身的槓桿也跟著提升，能測到真正重要的流程，抓出更多潛在問題。

## 局部性（Locality）

如果說槓桿是深模組送給「呼叫端」的禮物，那麼「局部性」就是深模組送給「維護者」的禮物。

當你需要修改拉取更新（pull）的行為時，如果過去到處都是淺呼叫，維護者就必須搜尋全域、逐一修改十幾個呼叫點。

在深模組的架構下，行為的先後順序與實作全部收納在同一個地方。只要修改該函式的實作一次，所有呼叫端就會同時生效。這就是高局部性。

<!--image:4-->

局部性大幅減輕了人類與 agent 的心智負擔。當程式庫主要由深模組構成時，平常只需要把介面記在腦中，不用隨時把龐大的實作細節放在心上。只有在深入某個模組內部維護時才需要看實作，工作完成後又能退回介面層次思考。

回到最一開始的測試問題：在良好的深模組設計裡，類似 `maxRetries` 這類設定常數，會被完全封裝在模組內部，介面根本不會把它暴露出來。外部拿不到它，agent 自然不可能寫出那種只驗證 `maxRetries === 3` 的套套邏輯測試。把實作藏得夠深，爛測試自然沒有生存空間。

有了這五個詞，下一個問題就是：在真實程式庫裡，怎麼把該刪和該加深的模組挑出來？
