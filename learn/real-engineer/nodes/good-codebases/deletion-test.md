# 用 Deletion Test 揪出淺模組：該刪除還是加深？

有了 deep 與 shallow 的詞彙，下一個問題是：在真實程式庫裡怎麼把它們挑出來？

在維護專案時，常會遇到看似做了封裝、實際上卻沒做什麼事的淺模組（shallow module）。單純理解名詞沒有太大意義，關鍵是放到實際的程式碼庫裡檢驗。

要判斷模組偏淺還是偏深，最直接有效的方法是**刪除測試（deletion test）**。

## 什麼是 Deletion Test？

deletion test 的核心問題很簡單：**如果直接刪掉這個模組，改由呼叫端直接呼叫底層實作，系統會變差嗎？**

<!--image:1-->

假設程式碼裡有一個自訂函式叫 `stringify`。點進去查看，它內部就只是呼叫 `JSON.stringify`，沒有任何額外處理：

1. 如果直接刪除這個自訂函式，把所有呼叫處都換回標準的 `JSON.stringify`。
2. 程式的行為完全不變，系統整體複雜度也沒有增加。
3. 程式碼的維護性反而提升。後續維護的人不用再去查這個自訂函式有何特殊邏輯，直接仰賴語言內建 API 即可。

只要刪除一個模組不會帶來任何損失，反而讓程式碼更直覺，它就是通過 deletion test 的候選對象，應該直接刪除。

## 另一個選擇：何時該將模組「加深」（Deepen）？

面對淺模組，刪除不是唯一的做法。

另一種常見情況，是呼叫端反覆出現特定的使用模式：

如果呼叫端每次呼叫該模組時，總是伴隨著相同的周邊邏輯、重複的功能組合，或是固定順序的操作。這代表介面切得太薄，暴露了過多實作細節。此時不該刪除它，而是該**加深（deepen）**它。

<!--image:2-->

加深的做法，是把呼叫端反覆自行處理的邏輯收進模組內，封裝在單一介面背後。介面維持精簡，背後承載的實作更完整，就能大幅減輕呼叫端的負擔。

## 搭配 Agent 找出改善候選

實務上運用 codebase design 技巧時，可以讓 AI Agent 協助偵查。撰寫提示詞時，可以要求它調用 codebase design 能力，並給出明確指令：

> 請利用 deletion test 找出適合刪除的淺模組，或是找出呼叫模式重複、值得加深（deepening）的候選名單。

在這個階段，先不要急著動手修改任何程式碼。第一步的重點是觀察與評估：

<!--image:3-->

* **評估候選品質**：Agent 挑出來的函式或模組，是否真的符合 deletion test 的標準，還是誤判了封裝的價值。
* **檢視核心詞彙的理解**：仔細觀察 Agent 在回覆中如何使用核心概念，包括介面（interface）、實作（implementation）、槓桿率（leverage）與區域性（locality）。

準確分辨哪些該刪、哪些該加深，並留存挑選出的候選清單，後續的程式碼重構才會有清楚的方向。
