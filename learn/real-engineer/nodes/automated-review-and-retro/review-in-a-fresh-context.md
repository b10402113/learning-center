# 讓實作與審查分工：為什麼程式碼品質該交給獨立的 Code Review 補齊

三層煞車裡，automated review 站在中間：比自動化檢查多花一點 token，卻能換掉人類最貴的那段工。

在軟體開發流程中，程式碼通常會先經過自動化檢查、自動化審查（automated review），最後才交給真人進行 code review。
這個設計的核心，是讓程式碼品質在每個階段逐步堆疊。

程式碼送到工程師面前時，品質應該已經盡可能拉到最高。
最差的情況，就是讓人花時間去審查一堆充滿低級錯誤的半成品。

多數團隊在自動化審查上的投入仍遠遠不足。
自動化審查能大幅節省人力時間，在 Token 的使用效益上也很有優勢。
為什麼需要特地拆出獨立的自動化審查步驟？為什麼不要求負責實作的 Agent（implementer）一開始就一次寫對？

## 實作 Agent 的負擔已經太重

負責實作的 Agent 手上的工作非常繁重。
它必須探索整個專案的 codebase、思考並修改程式碼，遇到問題時還要反覆 debug。

如果還要它同時兼顧每條瑣碎的編碼規範與風格細節，Context 就會被探索過程與 debug 資訊塞滿。
在多重目標並行的情況下，模型很容易顧此失彼。

相對地，如果我們在實作完成後清空 Context，改由審查 Agent 單獨針對剛產生的 diff 進行 review，情況就會完全不同：

<!--image:1-->

1. **不用大海撈針**：diff 已經明確框出受影響的程式碼範圍，審查 Agent 不需要耗費心力探索整個專案。
2. **專注於比對與修剪**：審查階段不需要漫無目的地修改檔案，目標非常聚焦。
3. **能載入大量審查規則**：因為 Context 很乾淨，可以直接提供大量具體的審查規則，例如找出特定壞味道並移除、標註違規寫法，或是調整特定語法架構。

在實際運作上，通常會在一個 session 裡完成實作。
實作完成後，再從該環境呼叫 code review。
這個 code review 會在獨立的 sub-agent 中啟動，立刻拿到一個全新且乾淨的 Context 視窗。

## 「先讓它能動，再讓它變好」

審查 Agent 該依據什麼來挑出問題？在這套流程中，code review 技能會主動讀取專案內的 `codingstandards.md`。
只要是希望自動化審查把關的細節，都可以寫進這份規範文件。

<!--image:2-->

常見的檢查規則包含：

- **禁止寫 `any` 與 `!`（驚嘆號斷言）**：避免模型在 TypeScript 中偷吃步、繞過型別檢查。遇到可能缺失的值必須做型別收窄（narrowing），型別指不出來就回去調整資料的 shape。
- **遇到錯誤直接 throw 回應，不回傳錯誤值**：讓 loader 或 action 失敗時直接拋出例外，維持單純的成功路徑，元件層就不需要另外拆解錯誤物件。
- **未受信任的外部輸入必須用 Schema 解析**：表單資料或查詢參數在進入資料庫查詢前，都要先經過如 Zod 的驗證，不能直接型別轉型（cast）硬套。

就算不寫這些規則，模型狀況好時也可能寫出類似水準。
但自動化審查多設了一道防線，確保這些標準一定會被落實。

許多人習慣把這類規範直接寫進全域的 `agents.md`，讓專案中所有 Agent 都能讀取。
但刻意不讓實作 Agent 看到這些規範，反而是更好的做法。

不讓實作 Agent 背負這些包袱，實作 Agent 就能全力處理核心邏輯，快速產出一份初稿（rough draft）。
隨後，獨立運作的 code review 帶著 `codingstandards.md` 裡的完整規範進場，接手將初稿修飾乾淨。

<!--image:3-->

實作 Agent 的任務是「把功能做出來」（make it work）。
獨立的 code review 才是負責「把品質做好」（make it good）。
把 Context 與職責分開，自動化審查才能發揮最大的效益。
