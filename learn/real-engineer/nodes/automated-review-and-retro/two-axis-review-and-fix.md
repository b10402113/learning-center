# 雙軸審查：讓 Agent 比對規範與規格並直接修復 PR

上一節說明了為什麼要讓獨立的 review agent 接手；這一節看它實際怎麼審、怎麼修。

收到品質不佳的 PR 時，最直覺的做法往往是打開檔案比對，一行一行挑毛病。但如果自動化審查只丟出幾十條留言，把問題全推回給人類，審查流程反而會拖得更長。

自動化審查的核心價值在於速度。它必須主動修好所有能確定解法的問題，只有遇到模稜兩可的情況，才停下來交給人類判斷。當人類接手時，面對的就已經是修整完畢、品質大幅提升的成果。

要讓 Agent 做到這件事，關鍵在於提供兩個對照基準：程式碼規範（Standards）與功能規格（Spec）。

## 為什麼需要雙軸審查？

寫程式的過程相當複雜，實作時難免會為了省事而走捷徑。單看程式碼本身，很難察覺某些功能其實做錯了方向。審查必須依賴兩個軸向並行驗證：

<!--image:1-->

1. **規範軸（Standards Review）**：檢查程式碼是否符合團隊約定的架構習慣、專有名詞與基本品質，例如專案內的 `codingstandards.md`，以及業界通用的壞味道（Code Smells）。
2. **規格軸（Spec Review）**：檢查程式碼是否完整且正確地滿足原始需求。

有時候專案討論完就立刻動手做，手邊不一定有現成的規格文件。只要有任何書面規格，就務必提供給 Agent。例如把規格整理成一份 Issue（假設編號為 35），再把 PR 編號（假設為 34）交給審查 Agent。

送出審查時，指令不能只停在「幫我審查」，還要明確加上「修復你發現的問題（and fix what you find）」。這能讓 Agent 直接進入「把它做好（make it good）」的階段，而不是把零碎修改丟回給人類。

## 雙軸審查的執行過程

當 Agent 收到 PR 與規格 Issue 後審查啟動時，會先鎖定比對的基準點（Fixed point），也就是 PR 的基底分支（例如 `main`）。接著，系統會在背景同時啟動規範審查與規格審查兩條線。

<!--image:2-->

在實際案例中，兩軸審查分別抓出了不同層次的問題：

### 1. 規範軸抓到的問題

規範審查會比對專案的 `codingstandards.md` 與通用壞味道：

- **違反明確規則**：當課程不存在時，程式碼直接回傳錯誤物件，而不是依規定拋出（throw）回應。這違反了規範中「找不到資源必須 throw response」的要求。
- **名詞不一致**：詞彙表（Glossary）規定使用 `student`，程式碼卻寫成 `learner`。
- **違背詞彙定義與權限**：詞彙表定義「筆記（Note）」屬於學生個人私密內容，實作卻開放給授課講師查看。
- **註解與程式碼矛盾**：有十幾處註解寫的內容跟實際程式碼完全相反。
- **通用的程式碼壞味道（Code Smells）**：審查工具內建許多源自 Martin Fowler《重構》（Refactoring）一書的通用指標。就算專案完全沒有規範文件，依然能抓出問題。例如 `save.tsx` 裡的重複程式碼、讀取已儲存內容時的 N+1 查詢、放在路由檔案且缺乏測試的書籤與筆記邏輯，以及在兩處重複宣告 `body` 與 `updatedAt` 結構的資料泥團（Data Clumps）。

### 2. 規格軸抓到的問題

規格審查會逐條核對 Issue 裡的使用者故事（User Stories），並將落差分類：

- **遺漏或未完成（Missing / Partial）**：課程頁面完全沒有顯示筆記的最後編輯時間；筆記本 UI 被排在課程內容下方，而不是規格要求的影片下方。
- **規格沒要求卻多寫（Not asked for）**：介面上多做了一個「講師檢視學生筆記」的區塊。
- **實作錯誤（Implemented wrong）**：筆記字數上限在規格中是 2000 字，程式碼卻設定成 5000 字；儲存筆記與書籤的動作完全沒有檢查存取權限，導致任何登入的使用者都能對任何課程建立筆記或加入書籤。

## 主動修復與人類裁決

產出報告後，Agent 不會乾等，而是主動動手修復。它建立了新的邏輯模組、把書籤與筆記邏輯移出路由並補上完整測試，還在路由的 Action 補上內容權限檢查（如 `requireContentAccess`）。

當遇到需要權衡的裁決（Judgment Calls）時，Agent 會整理出清單與人類確認：

<!--image:3-->

- **空筆記的處理**：儲存空筆記時應該拒絕還是清除？確認策略後直接補進驗證邏輯。
- **外鍵約束問題**：針對資料庫外鍵設定為 `ON DELETE NO ACTION` 的疑慮，若討論後決定暫不更動，可維持現狀或日後開立追蹤 Issue。

人類確認處理方向後，Agent 會一併更新 PR 的說明內文（PR description）。它會改寫摘要以如實反映變更，並清楚條列儲存筆記的驗證規則：去除頭尾空白；若為空則拒絕；若超過 2000 字則拒絕；發生衝突時更新內容並更新編輯時間。此外，內文也會附上新測試的執行證據。

## 審查成果：大幅降低風險

當 Agent 將修復推送回 PR 後整份 PR 的品質已經與最初截然不同：

<!--image:4-->

- 程式碼具備完整的自動化測試保護。
- 嚴重的隱私漏洞被徹底封堵，講師或平台管理員無法隨意查看學生的私人筆記，大幅縮小了合併時的影響範圍（Blast radius）。
- 程式碼排版、架構壞味道與規格缺漏一次補齊。

在整個過程中，人類審查者完全不需要逐行檢查那份一開始品質低落的 Diff。透過規範與規格雙軸並行，並讓 Agent 主動修復，人類只要在關鍵決策上點頭給方向，就能在極短時間內把 PR 推到隨時可以安全合併的狀態。
