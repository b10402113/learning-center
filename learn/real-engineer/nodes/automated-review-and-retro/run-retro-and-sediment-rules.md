# 用 Retro 將人工審查沉澱為編碼規範

上一節把 retro 裝好了，這一節把它真的跑起來，並決定哪些建議要收。

讓 AI 寫完程式並建立 Pull Request（PR）後，通常會面臨兩難。完全不看程式碼就合併，系統很快會累積隱形債務；每次都逐行抓細節，又違背了交給 AI 開發的初衷。

解決問題的關鍵在於改變審查視角。審查不是要在 PR 裡當人工 linter 挑單次實作的小毛病，而是要找出能寫進規範的模式。透過 `retro`（回顧）指令消化開發歷程與審查意見，能將這些經驗轉化為未來的自動化審查標準。

## 審查的目標是規範，不是單次實作

準備執行 retro 的第一步，是複製目標 PR 的編號（例如 PR 34），把人工審查的重點聚焦在流程與編碼標準上。

<!--image:1-->

在 GitHub 上瀏覽 PR diff 時可以留下行內留言。隨手寫下「這裡改用 bookmarks」這種留言太偏向當下单次實作，對未來開發沒有長遠幫助。遇到這類留言不如直接刪掉，換成規範層級的陳述。目標是寫出能放進編碼規範（coding standards）的原則，確保以後不必再留同樣的意見。

不常看大量程式碼也沒關係，這是認真讀懂程式碼的好機會。對程式碼有疑問時，可以使用 `teach` 技能發問，搞清楚脈絡後再留評論。

審查 PR 時可以留下聚焦在規範上的具體回饋，例如以下幾個方向：

1. **詞彙表一致性**：側邊欄（sidebar）元件中的標籤寫著「saved」，點擊後卻導向書籤（bookmark）頁面。UI 上的文字應嚴格遵循專案詞彙表（glossary）。詞彙表定義的是 bookmarks 或 notes，介面就不該自創「saved」這樣的詞。
2. **型別的全域共用**：在 `bookmarks.server.test` 裡，測試程式自行建立了 `testdb` 型別。這種測試用型別應該抽離出來放在全域共用位置，不該散落在各測試檔中。
3. **測試 setup 的模組封裝**：在測試的 `beforeEach` 區塊裡，測試資料不是透過模組本身的公開函式建立，而是直接呼叫底層資料庫的 raw 操作（例如直接呼叫 `db.insert`）。測試準備應一律透過受測模組自身的已知函式進行，避免碰底層資料庫。未來抽換資料庫實作時，測試程式碼才不會受影響。
4. **程式碼自明優於逐行註解**：相對單純的函式上方不該留下重述函式行為的說明註解。這類註解極容易隨時間脫節過時。更好的做法是清楚命名程式碼，讓結構更直觀。
5. **善用型別系統（Branded Types）**：型別定義上應明確區分純文字（plain text）與 Markdown。利用 branded types 做出區分，能讓每個函式清楚辨別接收的格式，發揮型別系統最大的輔助效益。

## 執行 Retro：聚合多個 Session 與審查意見

留完這些留言後，即可下達 retro 指令，回顧促成 PR 34 的所有 session，並指示抓取 PR 上的所有留言。

執行 retro 時會立刻載入 `writing-for-agents` 技能。這項技能定義了如何設計出好的技能、如何撰寫 `AGENTS.md`，以及如何客觀評判倉庫裡的程式碼與結構。

接著，retro 會找出背後關聯的所有對話記錄。以 PR 34 為例，它抓出全部 6 個 session，涵蓋建立 PR、撰寫 PR 內文、程式碼審查（code review）以及後續的修復執行。這些 session 也包含 code review 過程中衍生啟動的 sub-agents。retro 會同時分析這些 sub-agents 的軌跡，比對 PR 留言與相應程式碼。

<!--image:2-->

執行時需要注意 token 的消耗成本。retro 必須分析極大量的前後文資訊，非常耗費 token。要回顧的對話數量龐大時（例如超過 25 個 session），務必將工作切分，交由 4 到 5 個 sub-agents 分批讀取 transcripts。

## 讀懂 Retro 報告：為什麼不能全盤盲信

Retro 跑完後會產出一份龐大的報告。面對這份報告，不能偷懶直接讓 AI 自動套用所有修改建議。

讓 retro 自行診斷並直接改 code 到底，很容易陷入無窮優化的循環。它會不斷嘗試把事情改得更完美，反而越改越偏，最後把專案搞糟。人為介入審閱報告是必要的防線。

以這份報告為例，AI 提出了一個建議（項目 1）：執行 code review 時，系統找出了問題並完成修復，但修復後沒有重新跑一次 code review 確認。因此 retro 建議修改 `code-review` 技能本身，加上修復後強制重跑標準檢查的步驟。

<!--image:3-->

這個觀察屬實，但以實務流程來說過於繁瑣。現階段不需要為此改動基礎流程技能，可以忽略這項建議。

## 採納沉澱為規則的判斷題

報告中最有價值的部分，通常是偏好未明文化、且現有程式碼反而教壞 AI 的問題（項目 2）。

PR 留言希望程式碼自明、減少說明性註解。agent 之所以寫了一堆註解，是因為專案既有多個伺服器模組頂部都有巨大的 banner header 註解區塊。agent 模仿了專案既有慣例，導致修復 commit 反而額外增加了 32 行註解。自動化審查目前的產出與人類預期的風格並不一致。

同樣的問題也發生在測試 setup 上。留言要求透過模組函式設定測試，現有測試卻到處都是直接呼叫 `db.insert` 的寫法。

因為這兩點都屬於團隊架構風格的「判斷題」（judgment calls），retro 建議將它們沉澱進 `codingstandards.md`：

<!--image:4-->

- **讓程式碼自我解釋**：持續命名與重構，直到註解變得多餘。只有在程式碼無法表達「為什麼（why）」時，註解才有存在的理由。（若程式碼真的表達不出 why，通常代表需要撰寫架構決策紀錄 ADR，而非寫註解，但這條規則本身完全可以採納。）
- **透過受測模組排定測試**：測試準備階段必須呼叫受測模組本身的函式。需要的函式不存在時，應優先在模組中補上，而不是直接在測試裡插入資料庫資料列。

此外，retro 也建議補上 Martin Fowler 著作中提及、但當初沒寫進 code review 技能的概念。更重要的是，retro 建議直接從專案現存的 5 個模組中刪除 banner 註解。不把舊程式碼的壞習慣清掉，往後每建立新模組都會盲目複製。實作者會自認模仿得當，審查者則必須重複抓同樣的錯誤。

## 執行精準採納

梳理完報告後，只要給予 agent 精確的指示，指定採納與略過的項目：

- 忽略項目 1，不改動 `code-review` 技能。
- 完整採納項目 2 的建議：在 `codingstandards.md` 加入兩條新規則，並刪除 5 個模組中的 banner 註解。
- 順便採納項目 5（建立單一共享的 `testdb` 型別）與項目 6（針對純文字與 Markdown 引入 branded types）。

執行這項指令後，agent 會依序完成修改。在型別定義中加入 branded types（明確標註內文為 markdown）、收攏出全域共享的 `testdb`、清空所有模組頂部的 banner 註解，並在 `codingstandards.md` 寫入兩條全新的判斷準則。

原本只存在個人腦中的審查標準，就此正式變成專案倉庫的公用資產。下一次執行自動化程式碼審查時，agent 就會依照貼近團隊偏好的標準來把關。

這改變了人工審查的心態。人工審查不再只是抓 bug 的苦工，而是強化自動化審查機制的過程。日後某個 session 寫出 bug 時，能立刻對該 session 跑一次 retro，確保團隊與 AI 不會在同一個坑裡跌倒第二次。
