# 將規格切成帶阻擋關係的 Tracer-Bullet 工單

當你寫好一份完整的規格（spec），準備交給自動化工具（例如 `implement spec`）執行時，最常遇到的問題不是任務做不出來，而是工單（ticket）切得太細或太粗。如果切出 12 張甚至更多的小工單，管理負擔太大；但如果只切成兩三張大工單，自動化工具又無法發揮平行處理的威力。

拿捏顆粒度並排定工單之間的相依順序，是規格能順利轉成程式碼的關鍵。

## 用 Tracer Bullet 破局，再依平行度調節顆粒度

自動化實作規格的流程，通常依賴工單之間的阻擋關係（blocking relationships）來排程。在決定工單數量與結構時，有兩個核心原則：

<!--image:1-->

1. **先打出一條 Tracer Bullet**：第一步通常是一張貫穿端到端流程的「曳光彈」（tracer bullet）工單。它用最精簡的骨架打通關鍵路徑，確認整體架構可行，並作為後續任務的基礎。
2. **依平行度微調顆粒度**：完成基礎後，剩下的功能就能展開平行開發。例如，如果一次切出 12 張小工單可能顯得過於破碎，這時可以憑開發手感適度合併，收斂到大約 8 張工單。只要這 8 張工單中有 5 張（例如第 3 到第 7 張）可以同時平行執行，就比保留過大且無法拆開的任務有效率得多。

透過這種切法，規格主工單底下會掛出一組子工單（sub-issues），既有起頭的驗證任務，又有後續能同時跑起來的平行任務。

## 建立阻擋邊與子工單架構

這些工單的排程邏輯與決策工單（decision tickets）相同，全靠阻擋邊（blocking edges）來控制執行順序。在底層運作上，通常會以一張代表規格地圖的主工單為核心，將各任務掛為子工單：

<!--image:2-->

- **子工單關聯**：每張子工單都透過 GitHub 的 sub-issues 機制關聯到規格主工單；如果環境未啟用 sub-issues，則退回在主工單內文以 task list 追蹤，並在子工單開頭標註所屬主工單。
- **阻擋關係（Blocking）**：使用 GitHub 原生的 issue 相依性 API。加入阻擋邊時，需提供阻擋者（blocker）的資料庫數字 ID（`database id`，而非 issue 的 `#編號`），在系統中建立阻擋邊。若原生功能無法使用，則在子工單內文開頭寫入 `Blocked by: #<編號>`。
- **前沿查詢（Frontier Query）**：自動化工具隨時在查詢未被阻擋、未被指派的第一線工單（`blocked_by` 數量為 0）。一旦前面的 tracer bullet 任務關閉，被阻擋的後續任務就會解除鎖定，進入可執行的前沿。

## 放手讓自動化工具執行

切好帶有阻擋關係的子工單後，就能立即啟動執行流程：

<!--image:3-->

1. 清除目前的對話環境（clear the context），避免殘留的決策脈絡干擾實作。
2. 呼叫 `implement spec` 並傳入規格工單的編號。
3. 讓自動化工具依照阻擋邊逐步推進，無須全程在一旁人工監看。

工具會自動認領沒有被阻擋的工單、發送解答並在完成時關閉 issue；當所有阻擋工單依序完成、平行任務全數跑完後，再回到工作現場檢視結果，進行事後覆盤即可。
