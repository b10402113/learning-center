# 從決策地圖到規格書：用 to-spec 收斂架構並確認測試接縫

當探索與雛型驗證告一段落，整個決策地圖（Wayfinder map）已經清完霧、結構完整，下一步就是把它轉化為可以讓代理人（Agent）接手實作的規格書（spec）。

整體流程非常明確：先執行 `to-spec` 並傳入完成的地圖來產生規格書；規格書完成後，接著執行 `/to-tickets` 把規格拆成一張張工作票；建立好票券後，再次清空對話上下文（context），並執行 `/implement-spec`。順利的話，代理人會完成整個實作並在儲存庫開出 Pull Request，讓我們可以直接檢驗與測試。因為代理人握有最完整的脈絡——整份地圖、連回地圖的規格書，以及連回地圖與雛型分支（prototype branches）的票券——這些通知功能理應能一次就正常運作。

## 執行 to-spec 與確認測試接縫

執行 `to-spec` 時，我們需要傳入整份決策地圖。工具會開始逐一讀取地圖中的每一張決策票券。

`to-spec` 本身其實完全不理解探索流程的內部原理，但它看得懂「這裡有一整批決策票券」，並知道要把裡面的討論與決定全部抓取出來。在這個階段，它會做一件關鍵的事：提議後續測試要鎖定的「接縫」（seams）。

<!--image:1-->

這些測試接縫基本上勾勒出即將被建立的各個模組邊界，讓你在程式碼真正動工前，先看清楚整體的架構模組劃分。檢查這些接縫，確認模組邊界符合設計預期後放行，工具就會接著把所有資訊收整成正式的規格書。

## 規格書的內容與結構

以 Cadence 應用的站內通知功能為例，壓製出來的規格書開宗明義點出問題：Cadence 的使用者目前無法得知與自己相關的事件，應用程式內也沒有任何機制可以告知使用者發生了什麼事。

這份規格書會包含極為完整的細節：

<!--image:2-->

- **使用者故事（User Stories）**：完整整理出多達 61 個具體的使用者故事。
- **實作決策**：明確記錄團隊選定的廠商與架構原則，例如決定採用 NOC 作為廠商、通知資料僅留存在 NOC 端、完整的通知目錄清單、觸發通知的各項服務、通知偏好設定（preferences）、使用者資料同步（user sync）、客戶端動態接口（client feed port）以及動態介面（feed UI）。
- **底部的參考資料與補充筆記**：完整列出所有相關 issue、地圖來源，並明確標記各項功能的雛型分支所在。

## 為什麼不直接把地圖餵給代理人？

在技術上，你確實可以直接把整份未經整理的地圖丟給代理人，直接叫它「把這個做出來」。

但把地圖壓成一份規格書，最大的好處是將發散的討論與所有分支決策完全攤平。這就像把食物切好一口一口餵給代理人（spoon feeding），所有它需要的邊界、邏輯與參考依據都在同一份文件裡清楚展開，省去在大量討論票券中反覆拼湊脈絡的成本。

<!--image:3-->

確認規格書產出無誤後，就可以回到代理人介面，準備執行下一步的 `to-tickets` 拆解工作票。
