# 從決策地圖到規格書：用 to-spec 收斂架構並確認測試接縫

探索與雛型驗證告一段落後，決策地圖（Wayfinder map）已經釐清所有未知，結構也完整了。下一步就是把地圖轉化為規格書（spec），交由代理人（Agent）接手實作。

整體流程很單純。先執行 `to-spec` 並傳入完成的地圖，用來產生規格書。規格書產生後，接著執行 `/to-tickets`，把規格拆成一張張工作票。建立好票券後，清空對話上下文（context），再執行 `/implement-spec`。順利的話，代理人會完成所有實作，並在儲存庫開出 Pull Request 供檢驗與測試。代理人掌握了最完整的脈絡，包含整份地圖、連回地圖的規格書，以及連回地圖與雛型分支（prototype branches）的票券，因此這些通知功能理應可以一次就正常運作。

## 執行 to-spec 與確認測試接縫

執行 `to-spec` 時需要傳入整份決策地圖。工具會開始逐一讀取地圖中的每一張決策票券。

`to-spec` 本身其實完全不理解探索流程的內部原理，但能識別這裡有一整批決策票券，並抓出其中的討論與決定。這個階段有一件關鍵任務：提議後續測試要鎖定的「接縫」（seams）。

<!--image:1-->

這些測試接縫勾勒出即將建立的各模組邊界。在程式碼真正動工前，可以先看清楚整體的模組架構。檢查並確認模組邊界符合設計預期後放行，工具就會把所有資訊收整成正式的規格書。

## 規格書的內容與結構

以 Cadence 應用的站內通知功能為例。產出的規格書直接點出問題：Cadence 的使用者目前無法得知與自己相關的事件，應用程式內也沒有任何機制告知使用者發生的事。

這份規格書會包含極為完整的細節：

<!--image:2-->

- **使用者故事（User Stories）**：整理出多達 61 個具體的使用者故事。
- **實作決策**：明確記錄選定的廠商與架構原則。這包含採用 NOC 作為廠商、通知資料僅留存在 NOC 端、完整的通知目錄清單、觸發通知的各項服務、通知偏好設定（preferences）、使用者資料同步（user sync）、客戶端動態接口（client feed port）以及動態介面（feed UI）。
- **底部的參考資料與補充筆記**：完整列出所有相關 issue、地圖來源，並標記各項功能的雛型分支位置。

## 為什麼不直接把地圖餵給代理人？

技術上，確實可以直接把未整理的地圖丟給代理人，要求它直接實作。

但把地圖壓成一份規格書，最大好處是能把發散的討論與分支決策完全攤平。這就像把食物切好一口一口餵給代理人（spoon feeding）。所有需要的邊界、邏輯與參考依據，都在同一份文件裡清楚展開。這能省去代理人在大量討論票券中反覆拼湊脈絡的成本。

<!--image:3-->

確認規格書產出無誤後，即可回到代理人介面，準備執行下一步的 `to-tickets` 來拆解工作票。
