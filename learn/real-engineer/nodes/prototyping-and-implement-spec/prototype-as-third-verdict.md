# Feature Request 的第三條分支：為什麼要把 Prototype 早早部署上線？

在軟體工廠的工作流中，處理錯誤回報（bug report）或改善現有程式庫通常有很明確的步驟。但當系統開始面對使用者提出的新功能需求（feature request）時，工廠該如何協助團隊探索與推進？

在過去的設計裡，當專責探索新功能需求的 agent 介入分析時，通常只有兩種判決：

<!--image:1-->

1. **太過複雜**：agent 會在工單（ticket）上留下一段分析與說明，交由團隊接手討論。
2. **相對單純**：agent 會直接觸發實作執行器（implement runner），在追蹤系統（tracker）留言，並讓程式碼走完後續的實作審查流程。

但實務上常常會遇到第三種情況：這個需求既不算單純，也不能單純歸類為太複雜，而是需要先看到畫面與互動，團隊才能把討論聚焦並繼續往下推。

## 認出第三條分支：需要視覺化的 Prototype

這就是探索功能需求時的第三條分支——判定為「需要 Prototype」。

在需求還沒完全定案前，及早把原型做出來的價值非常巨大。這類工作非常適合交給 agent，讓它們在初步探索功能時就自行啟動原型製作。這麼一來，團隊在追蹤系統上看到的就不只是一串抽象文字或長篇留言，而是一個看得見、摸得著的具體產物。

這套機制的運作方式是：一旦判定需要原型，工廠就會啟動 prototype runner 來建立原型程式碼。

原型的程式碼通常會以草稿 Pull Request（draft PR）的形式存在，並且打上特定標籤，清楚告知團隊其他人這只是原型，切勿直接合併進主分支。更重要的是留言的時機：系統應該等到原型實際產生、處理完畢後，再把帶有原型連結的留言貼回追蹤系統，避免大家點進去卻撲空。

## 為什麼要把 Prototype 早早部署上線？

在最理想的流程中，prototype runner 產生程式碼之後，應該要直接把它部署到某個環境上線。

<!--image:2-->

這個步驟的關鍵在於打破技術門檻。如果原型只是一包程式碼或一個 PR 分支，團隊裡非技術背景的成員（例如產品經理、設計師或行銷夥伴）就無法輕易預覽。一旦原型被自動部署成可以點擊的網頁，任何人只要點開連結，就能親自操作原型所提供的各項互動效果，直接體驗操作流程並給予具體回饋。

把原型早早推上線，能讓所有人站在同一個具體畫面上對話，省去在文字討論中雞同鴨講的時間。

## 為什麼不能光靠 Agent 寫出完美的 UI？

有人可能會問：為什麼需要反覆做原型看畫面，而不直接讓 agent 產出最終設計？

這牽涉到 agent 目前在處理介面設計上的限制。agent 是以文字為核心的工具，它們沒有人類的眼睛。雖然 agent 對圖像的理解能力正逐漸進步，但介面設計往往不是純文字邏輯，而是視覺感受的綜合體。

<!--image:3-->

設計畫面時，必須考慮視覺排版、元件間距（spacing）、文字視覺階層（textual hierarchy），以及畫面上各種元素彼此對應的相對重要性。這些微調高度依賴手感與直覺。

即使是具備前端或全端開發背景的人，也往往只能仰賴過去累積的經驗法則與直覺，在 Wayfinder 等工作流程中，依照引導經歷好幾輪原型製作，邊做邊看才能摸索出正確方向。雖然目前市面上開始出現一些強大的設計技能擴充——例如 Impeccable、Emil Kowalski 的技能組，或是設計工程師 Vojta 開發的相關技能——但最根本的解法依然是「多做原型」。藉由自動化流程及早做出原型並部署上線，搭配這些設計工具輔助，才是讓團隊最快找到介面解答的捷徑。
