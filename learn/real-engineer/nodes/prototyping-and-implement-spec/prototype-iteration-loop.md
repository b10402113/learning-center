# 設計 Prototype 迭代迴圈：讓留言串成為 Agent 的對話歷史

在以 AI agent 為核心的自動化流程裡，丟出一個需求並讓 agent 產生初始原型（prototype）並不難。真正的挑戰在於「迭代」：任何原型都需要反覆修改，才能貼近真實需求。

在本地開發時，工程師可以隨意改動程式碼、即時預覽；但如果要讓沒有本地開發環境、不具備工程背景的非技術同仁也能參與這個過程，就必須仰賴精心設計的迭代迴圈。讓非技術人員產出這類「拋棄式原型」（throwaway prototype）具有極高的價值，因為這些原型能成為後續整個軟體生產線極為豐富的輸入訊號。

整個流程依然可以從需求探索（Agent Explore）開始，但必須替它加入能夠持續滾動的迭代機制。

## 留言串就是天然的對話歷史

當 Agent 產生出原型並部署完成後，人類會透過某種方式看到結果。非技術人員通常不會去看 Git 託管平台上的程式碼，而是點開部署出來的網頁或產物（deployed asset）。同時，系統也會在工單追蹤系統（ticket tracker）中發布通知，提醒關注這項功能的人前來檢視。

<!--image:1-->

這時，人類檢視完畢後的反應必須能夠回傳給系統，重新啟動另一輪原型建置：

1. **人類在工單下留言反饋**：提出修改意見，並在留言中明確標註（tag）agent。
2. **啟動下一輪 Runner**：runner 被喚醒時，會同時取得「既有的原型程式碼」以及「該工單目前為止的所有留言紀錄」。
3. **留言串化為 Context**：工單裡的留言串直接充當了對話歷史（conversation history），runner 依靠這些上下文理解人類的喜好與改動理由，進而調整原型。

因此，原型 runner 的職責不能只停留在「建立原型」，而是要能同時處理「建立或更新（Create / Update）」。

## Orchestrator 的分流與人類捷徑

要讓這套迴圈運作順暢，負責調度的 Orchestrator 必須具備分辨訊號的能力。它至少要能識別兩種不同的情境：

<!--image:2-->

- **初次建立**：目前完全沒有原型，需要從零產生骨架。
- **後續更新**：已有現存的原型與相關 PR，需要讀取歷史留言進行增量修改。

雖然這會讓 orchestrator 的邏輯增加一點複雜度，但實務上並不難實作，而且是維持對話連續性不可或缺的機制。

此外，觸發原型的入口也需要雙軌設計。原本的流程可能是由 agent 在探索功能需求時，自行判斷是否需要做原型；但在實際的工作流設計中，**只要規劃了 agent 自動觸發的路徑，就應該同時補上一條人類手動觸發的捷徑**。

最直接的做法是在工單追蹤系統上加入監聽機制（watcher）：當人類判定某個需求需要驗證時，直接在工單貼上例如 `needs prototype` 的標籤，就能立刻啟動這套流程，不必等待 agent 慢吞吞地完成前置探索。

## 拋棄式原型的定位：極度詳細的互動規格

這套機制讓完全不懂技術的人，僅僅透過在工單裡不斷留言「我喜歡這個、不喜歡那個」，就能完全在追蹤系統內雕琢出一個可互動的原型。他們不需要配置本地環境，也不需要專業開發技能。

<!--image:3-->

當他們對原型滿意時，Git 託管平台上已經有一份 draft PR，裡面包含具體的實作程式碼。接手的正式工程師不僅有現成程式碼可以參考，更重要的是，可以在工單追蹤系統中完整看到決策過程、偏好轉折與所有意見的歷史紀錄。

這也釐清了一個常見的爭論：該不該讓非技術人員「寫程式碼」？

答案是肯定的，但必須建立在正確的認知之上——這裡產出的拋棄式原型是「極度詳細的規格書」，而不是直接上線的正式程式碼。這些原型不能直接丟進生產環境，而是要進入正規的工程體系，經歷嚴謹的程式碼審查（Code Review）、深入審查（Grilling Session），或是作為後續架構定錨（Wayfinding Session）的基石。

把工單追蹤系統當作人與 agent 溝通的介面，搭配能夠理解建立與更新狀態的 orchestrator，就能將零散的人類意見，轉化為驅動軟體工廠穩定運作的高品質規格。
