# 把 Implement Spec 寫成 Orchestrator：自動開票、共享探索筆記與平行 Runner 設計

在打造自主運作的離席（AFK）agent 時，處理錯誤修復或建立原型相對單純。但如果要讓 agent 自主執行長時間任務、產出大量功能程式碼，就需要一個能把文字規格（spec）轉化為確定性執行的排程核心——這就是 `implement spec`。

在軟體工廠的架構中，這個機制就像運作的心臟。工程師可以在「白天班」完成規格定義與路徑探尋（wayfinding），到了「夜班」，整個系統就會自動把這份規格拆解、實作，源源不絕地把程式碼交付出來。

要讓這個流程自動運轉，我們會把整個任務交給 orchestrator（協調器）排程，並由一系列 runner 負責執行。

## 減少人工作業：直接從規格自動開票

過去的流程往往需要人類同時提供規格文件與切好的任務工單（tickets）。但在實務上，當工程師把規格的目的地與細節想清楚後，通常只想轉身離開，不想再花時間手動拆票，去煩惱票開得太多還是太少。特別是在程式碼架構優化（improved codebase architecture）的自動循環中，如果每產生一份規格都要人工 clone 到本地、手動跑切票工具，整個自動化流程就會卡住。

因此，更好的體驗是讓 Orchestrator 只接收規格輸入：

<!--image:1-->

1. 規格被存放在工單追蹤系統中，並被加上特定標籤（例如 `agent implement`），或直接指派給 agent。
2. orchestrator 被觸發後，先檢查這份規格底下是否已經有子票券。
3. 如果完全沒有票，orchestrator 就先啟動一個 runner 執行切票（to-tickets），由 agent 自動把任務圖拆解並建立在追蹤系統上。

雖然嚴格來說，如果外部本來就已經備妥工單，這段切票迴圈可以完全跳過；但加入這個防呆機制，能幫工程師省下大量無意義的雜務。

## 前置步驟：探索 Runner 與遠端筆記共享

規格與所有任務票券就緒後，不能直接盲目開工。流程的第一步，是啟動一個專門負責探索的 runner（exploration runner）。

探索 Runner 會先通讀規格、探索整個專案程式庫的架構，並將調查到的上下文資訊存成數個 Markdown 筆記。這些筆記是後續所有實作 agent 的關鍵指引，但這類資訊並不適合硬塞進工單的內文或開成隨後就得關閉的 draft PR。

<!--image:2-->

最好的做法，是讓探索 runner 把這套 Markdown 檔案推送到一個獨立的「遠端分支」（remote branch），規劃在規格生命週期徹底結束後的某個時間點再統一清理。接著，runner 在工單追蹤系統的規格主票上留言，附上該分支與筆記的路徑。

這樣一來，後續被派發出去的每一個實作 runner，都能透過規格上的留言，同時讀取到三大資訊：
- 整體規格的完整內容
- 該 runner 自己負責的單張任務票
- 探索階段留下的共用 Markdown 筆記集

## 用確定性邏輯計算 Frontier，不需依賴 AI

許多人以為分析任務先後順序需要呼叫大語言模型，但其實完全不需要。

任務票券不是一條筆直的待辦清單，而是一個任務相依圖（task graph）。票與票之間存在著「阻擋」（blocking）關係，就像在 Wayfinding 操作中，子任務之間會用系統原生相依性或相依標記指明誰卡住了誰。

<!--image:3-->

這些阻擋關係是可以「確定性計算」的：只要一張票的所有前置阻擋票都已經被關閉（完成），而且目前沒有人認領，這張票就屬於隨時可以被領取的「Frontier」（前沿任務）。

orchestrator 只需要查詢目前狀態，把所有未受阻的 frontier 票券撈出來，就能直接觸發執行。

## 平行執行的兩種架構選擇

撈出當前的 Frontier 之後，面對這批可以同時開工的票券，在架構上有兩種排程設計：

<!--image:4-->

### 設計一：單一 Runner 內包 Sub-agents

這個做法是讓 orchestrator 只啟動一個 runner，並把當前 frontier 的所有票券交給它。接著，該 runner 在自身的沙盒（sandbox）環境內部，啟動多個 sub-agent 同時平行撰寫程式碼。

- **優點**：所有分支都在同一個 runner 的本地環境中。各 sub-agent 完工後，可以直接在本地把所有票券的分支合併回整合分支（integration branch），合併成功就直接推送到遠端並關閉工單追蹤系統上的票。
- **缺點**：極度消耗運算資源。如果一個 frontier 同時有 5 張票，這個 runner 的機器就必須承受同時跑 5 套應用程式或 5 套測試套件的負載。現實中大部分的 runner 節點規格都沒有這麼高。

### 設計二：每張票獨立 Runner（推薦方案）

為了避免單一 runner 被資源吃垮，實務上更穩健的做法是把規格降到「一個 runner 只要能跑一套應用程式就好」：

1. **平行發派**：orchestrator 針對 frontier 裡的每一張票，各自啟動一個獨立的 runner 與沙盒。
2. **獨立推分支**：每個 runner 只在自己的沙盒裡建置單一票券，完成後把程式碼推送到遠端的 Git 分支。
3. **集中等待**：orchestrator 負責追蹤這批平行 runner 的進度。
4. **專屬 Merge Runner**：當本輪 frontier 的所有 runner 都順利完成並推上分支後，orchestrator 啟動一個專屬的 merge runner，一口氣抓取這些遠端分支進行合併，推回整合分支並更新工單狀態。

這個設計雖然讓 orchestrator 的追蹤狀態與分支管理變得較繁瑣，但對底層 runner 的硬體負擔小很多，也具備更高的平行擴展能力。

## 迴圈推進與自動審查

無論採取哪一種平行架構，當這一輪 frontier 的程式碼完成合併、票券關閉之後，orchestrator 都會重新檢查整體任務圖：

- **若尚有未完成票券**：隨著上一批票被關閉，原本被阻擋的後續票券現在會被解鎖，成為新的 frontier。orchestrator 會帶著更新後的圖再次進入迴圈，啟動下一輪 runner。
- **若所有票券皆已完成**：跳出實作迴圈，啟動自動審查關卡（Agent Review），進行最後的品質把關並開出審查完成的 PR。

將實作規格交給 orchestrator 運作的關鍵，在於狀態的切割與存放位置：分支與探索筆記等細節要與 Git 遠端協同，而任務依賴與開票則透過工單追蹤系統維護。透過確定性計算 frontier 並搭配平行 runner，就能組裝出一台全自動把規格快速推進為程式碼的軟體工廠生產線。
