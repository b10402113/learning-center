# L1 overview

- `app/routes.ts` — 路由總表：`index`、一個 `layout("routes/layout.app.tsx")` 包住幾乎所有頁面，login / signup / 四支 `api/*` 留在 layout 之外。沒有任何 loader 或 service 層，只有 URL 與檔案的對應，所以「哪些頁面共享側邊欄與 DevUI」是靠這裡的 nesting 決定的，不是靠程式碼結構。
- `app/routes/courses.$slug.tsx` — 課程銷售頁：`loader` 一次撈課程、模組、進度、評分、PPP 價格與「取消購買」資格，`action` 只處理星等評分。它把查詢函式全部寫在檔案內（`getCourseBySlug`、`getCourseWithDetails`、`calculateProgress`…），因此成為整個 route 層的複製來源；同一段進度計算在 `courses.tsx`、`dashboard.tsx`、`layout.app.tsx` 各有一份。
- `app/routes/courses.$slug.purchase.tsx` — 結帳頁與 `action`：`confirm-purchase` 先 `createPurchase` 再 `enrollUser`（兩次獨立寫入、沒有 transaction），`confirm-team-purchase` 產生 N 張 `coupons` 並導向 `/team`。`enrollUser` 的 `sendEmail` 參數只有空註解，是「假裝有寄信」的典型縫口。
- `app/routes/courses.$slug.refund.ts` — 只有 `action`、沒有 UI 的退款端點。它在這裡叫 refund、`refundableAmount`、`REFUND_WINDOW_DAYS`，但同一段規則在課程頁叫 cancel、在寄出的信裡叫 **Reversal**、在使用者設定頁叫 **Chargeback**；四種名字指同一件 `refunds` 資料列。
- `app/routes/courses.$slug.welcome.tsx` — 購買後的歡迎頁，只驗證「已登入且已 enrolled」，然後給 Discord 邀請連結與第一課入口。`getCourseBySlug`/`getCourseWithDetails`/`isUserEnrolled` 三份查詢是前一個檔案的逐字複本。
- `app/routes/courses.$slug.$moduleId.tsx` — 單一模組頁：驗證模組屬於該課程（`moduleWithLessons.courseId !== course.id`），算模組層級完成百分比並列出課程。`paramsSchema` 用 `z.coerce.number().int()` 解析 `moduleId`，是這一層少數有做參數驗證的地方。
- `app/routes/courses.$slug.lessons.$lessonId.tsx` — 全檔最大（1714 行）的學習頁：內容、YouTube 播放、續看位置、留言串、測驗、上下課導覽全在同一檔。存取控制終於走共享模組 `getAccess` / `requireContentAccess`，但 `loader` 內直接呼叫 `markLessonInProgress` 對 DB 寫入——用 GET 改狀態。
- `app/routes/courses.tsx` — 課程目錄：`buildCourseQuery` 支援搜尋、分類、排序、分頁，`loader` 再補每門課的課數、進度與評分彙總。這裡把 schema 匯入改名成 `coursesTable` / `enrollmentsTable`，和其他檔案直接叫 `courses` 的慣例不一致。
- `app/routes/dashboard.tsx` — 我的學習儀表板：`loader` 要求登入（401 文案指向 DevUI 面板），把報名分成「進行中」與「已完成」，並用 `getNextIncompleteLesson` 給續看按鈕。`calculateProgress`、`getCompletedLessonCount`、`getCourseLessonIds` 又一次逐字重複。
- `app/routes/home.tsx` — 行銷首頁：精選課程、統計數字、深淺色切換、DevUI 面板。它自己複製了 `buildCourseQuery` 與 `getLessonCountForCourse`，而且在這裡再渲染一次 `DevUI`，與 `layout.app.tsx` 的 DevUI 並存。
- `app/routes/settings.tsx` — 個人資料編輯：`action` 只准改 `name` / `bio`，email 顯示為不可編輯。下半部把 `refunds` 查詢結果命名為 `pendingChargebacks` 並以「Pending Chargeback」呈現——與 refund / reversal / cancel 是同一組資料。
- `app/routes/team.tsx` — 團隊席位管理：列出 `coupons`（呼叫它 seats）、已領取狀態與 `/redeem/<code>` 複製連結。`getTeamForAdmin` 與 `purchase.tsx`、`layout.app.tsx` 三處同名同內容重複；「claimed」與 coupon 欄位 `redeemedByUserId` / `redeemedAt` 用詞不一致。
- `app/routes/login.tsx` — 只有 email、沒有密碼的登入：查 `users.email` 存在就 `setCurrentUserId` 發 cookie，`redirectTo` 只接受以 `/` 開頭的值。這個檔案定義了全站 session 的實際語意——登入等於「選一個使用者」。
- `app/routes/signup.tsx` — 註冊：email 已存在時**靜默登入該帳號**（不報錯），否則以 `UserRole.Student` 建立使用者。與 login 同樣的 `redirectTo` 白名單邏輯被複製了一份。
- `app/routes/redeem.$code.tsx` — 兌換優惠碼：`loader` 先算 `alreadyRedeemed` / `alreadyEnrolled` / `countryMismatch` 三種狀態，`action` 再走 `redeemCoupon` 標記 coupon 並建立 enrollment。國家限制（`purchase.country !== userCountry`）在這裡重寫了一次，與 PPP 存取模組是兩套判斷。
- `app/routes/layout.app.tsx` — 應用外殼：`Sidebar`、`Outlet`、`Toaster`、`DevUI`，`loader` 另外算「最近學習的課程」與 `isTeamAdmin`。它同時持有第三份 `getTeamForAdmin` 與 `calculateProgress` 副本，讓一個純版面檔案背了商業查詢。
- `app/routes/api.logout.ts` — 11 行的 `action`：`destroySession` 後 302 回 `/` 並帶 `Set-Cookie`。整個 repo 最乾淨的檔案，可作為其他 api route 的對照組。
- `app/routes/api.set-dev-country.ts` — DevUI 切換國家：`country` 必須是 2 碼或空字串（空字串轉 `null`），解析失敗時**靜默**寫成 `null`，然後導回 `redirectTo`。與隔壁的 switch-user 對錯誤的處理相反。
- `app/routes/api.switch-user.ts` — DevUI 切換使用者：`userId` 經 `z.coerce.number().int().positive()` 驗證，失敗丟 400 `Response`，成功寫 cookie 後導回 `redirectTo`。與 `api.set-dev-country.ts` 幾乎同構，只差錯誤策略。
- `app/routes/api.video-tracking.ts` — 觀看事件寫入端點：`action` 驗登入、用 `parseJsonBody` 驗 `{lessonId, eventType, positionSeconds}`，直接 insert `videoWatchEvents`。**沒有**驗證該 lesson 是否屬於使用者已報名的課程，而退款資格正是靠這張表的 `positionSeconds` 計算。
