# L1 overview

- `drizzle/0000_dizzy_fenris.sql` — 第一支遷移，一次建出 Cadence 的 14 張核心表：`users`、`categories`、`courses`、`modules`、`lessons`、`enrollments`、`lesson_progress`、`purchases`、四張 quiz 表、`video_watch_events`。它把「課程—模組—單元」的階層與「使用者—購買—註冊—進度」的關係固定下來，之後所有遷移都只是在這組骨架上加欄位或補索引。`purchases` 一開始記的叫 `price_paid`，`courses` 的 `sales_copy` 允許 NULL。
- `drizzle/0001_cynical_sunspot.sql` — 單行 `ALTER TABLE lessons ADD github_repo_url text`。它讓每個單元可以掛一個程式碼範例 repo，是 `seed.ts` 之後能為 TypeScript、REST、設計系統課程填入 `githubRepoUrl` 的前提。
- `drizzle/0002_lying_shriek.sql` — 引入 `teams`、`team_members`、`coupons` 三張表，把「團購」變成第一級 domain：一筆 `purchases` 可以產生多張 `coupons`，`coupons.redeemed_by_user_id` / `redeemed_at` 記錄兌換者與時間。`coupons.code` 有唯一索引，`coupons` 同時 foreign key 到 `teams`、`courses`、`purchases`、`users` 四個維度。
- `drizzle/0003_lean_hex.sql` — 單行 `ALTER TABLE courses ADD notes text`。這是講師對課程的內部備註欄位，與面向學生的 `description` / `sales_copy` 分開。它的重要性在於下一支遷移會把 `notes` 一起搬進重建後的新表。
- `drizzle/0004_reflective_genesis.sql` — 建 `course_ratings`，並用 `course_ratings_user_course_unique` 唯一索引表達「一個使用者對一門課只能有一筆評分」。這條約束是 domain 規則寫進資料庫的典型例子：評分是 upsert 而不是累加列。
- `drizzle/0005_tricky_spyke.sql` — 建 `comments`，`parent_id` 自參照形成無限層的留言樹，`edited_at` 與 `deleted_at` 讓「編輯過的留言」與「作者已刪但仍有回覆的墓碑」都能保存。附帶 `comments_lesson_idx` 與 `comments_parent_idx` 兩個索引，對應「列出某單元的問題」與「展開某串回覆」兩種查詢。
- `drizzle/0006_condemned_norman_osborn.sql` — SQLite 的標準 table rebuild：建 `__new_courses`、`INSERT ... SELECT` 複製資料、`DROP` 舊表、`RENAME`、重建唯一索引，前後以 `PRAGMA foreign_keys=OFF/ON` 包住。實質變更是把 `sales_copy` 從可為 NULL 收緊成 `NOT NULL`，並把 0003 加的 `notes` 正式納入表定義。
- `drizzle/0007_absurd_black_tarantula.sql` — 單行 `ALTER TABLE purchases RENAME COLUMN "price_paid" TO "amount_paid"`。這是整個 schema 裡唯一一次真正的欄位改名，也是本段最值得注意的 domain 詞彙遷移：同一個欄位在 0000 叫 `price_paid`，從 0007 起叫 `amount_paid`。
- `drizzle/0008_perpetual_radioactive_man.sql` — 純效能遷移，補三個索引：`enrollments_course_idx`、`lesson_progress_user_lesson_idx`（複合）、`purchases_course_idx`。改動的是查詢計畫而非 domain，反映「按課程統計註冊／營收」與「查某人某單元進度」是高頻路徑。
- `drizzle/0009_clear_professor_monster.sql` — 建 `refunds` 表：`purchase_id`、`status`（預設 `'requested'`）、`reason`、`amount_refunded`、`requested_at`、`resolved_at`、`resolved_by_user_id`，外加 `refunds_purchase_idx`。退款在這裡是「掛在購買上、有狀態機與處理人」的獨立實體，而不是刪掉一筆 `purchases`。
- `drizzle.config.ts` — 10 行的 drizzle-kit 設定：`schema` 指向 `./app/db/schema.ts`（TypeScript schema 是唯一真相來源）、`out` 指向 `./drizzle`（遷移檔輸出處）、`dialect: "sqlite"`、資料庫檔案 `./data.db`。它解釋了為什麼 `drizzle/` 底下是 `0000…0009` 的循序 SQL，而型別定義長在 app 內。
- `scripts/seed.ts` — 2782 行的種子腳本：先用 `better-sqlite3` 開 `data.db`、開 WAL 與 `foreign_keys`，手動 DROP 所有表後呼叫 `migrate()` 套用 `drizzle/` 的遷移，再灌入使用者、五門課、測驗、註冊、評分、留言、進度、觀看事件、購買、團隊與優惠碼。資料分兩層：前面是手寫的敘事資料（五個具名學生擁有所有留言／測驗／評分），後面是用固定 PRNG（`mulberry32`，seed `20260731`）生成的約十二個月 bulk 歷史，供分析功能對照。
- `scripts/allow-scripts.test.ts` — 50 行的 vitest 測試，不測應用邏輯而測安裝設定：用 zod 解析 `package-lock.json` 與 `package.json`，斷言每個帶 `hasInstallScript` 的套件都以 `name@version` 形式出現在 `allowScripts` 裡。理由寫在檔頭：漏掉 `better-sqlite3` 的 install script 會在執行期以 "Could not locate the bindings file" 爆掉——正好是本課程持久層的依賴。
