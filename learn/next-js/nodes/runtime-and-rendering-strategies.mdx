# 執行環境與渲染策略：Node / Edge、SSG / ISR / SSR / PPR

## Learning goal

能依「內容多久變一次、需不需要即時」選出 SSG / ISR / SSR / PPR，並判斷一段 route 該跑 Node 還是 Edge runtime、理由是什麼。

## Steps

閱讀順序（deps 決定誰必須先出現）：

1. [[learn/next-js/nodes/runtime-and-rendering-strategies/rendering-axes|渲染的三條軸線：環境、時間、runtime]] — 先建立定位用的座標系：誰渲染（client／server）、什麼時候渲染（build time／run time）、在哪個 runtime（Node／Edge）。
2. [[learn/next-js/nodes/runtime-and-rendering-strategies/server-rendering-strategies|三種伺服器渲染策略：SSG、ISR、SSR 與 PPR]] — 把 SSG／ISR／SSR 與 PPR 放進座標系，看它们各自在什麼時間點產生內容（需先完成 step 1）。
3. [[learn/next-js/nodes/runtime-and-rendering-strategies/choosing-a-rendering-strategy|挑渲染策略：內容多久變一次、要不要即時]] — 用兩問決策流程選策略，並認出 AI 的預設踩雷（需先完成 step 2）。
4. [[learn/next-js/nodes/runtime-and-rendering-strategies/node-vs-edge-runtime|挑 runtime：Node 還是 Edge]] — 從延遲、API 限制與資料距離判斷 route 該跑哪個 runtime，並分清 edge 與 serverless（需先完成 step 1）。
5. [[learn/next-js/nodes/runtime-and-rendering-strategies/strategy-and-runtime-in-code|用程式碼打開策略與 runtime]] — 查表：`revalidate`、`cache`、`next.revalidate`、`Suspense` 與 `export const runtime` 各把開關切到哪裡（需先完成 steps 3–4）。

## Lesson

渲染不是一個開關，而是一組座標。這個節點要回答的，其實是每個 Next.js 開發者每天都在面對的兩個決定：這段內容「**什麼時候**」被產生，以及這段程式碼「**在哪裡**」被執行。

第一個決定是時間軸。Next.js 提供三種伺服器渲染策略：SSG 在 build time 就把頁面做成靜態檔，之後原封不動地從 CDN 送出去；SSR 每次請求都在 server 重新算一次；ISR 介於兩者之間，先靜態、過一段時間或收到指令再更新。PPR 更進一步，讓同一個頁面裡靜態的外殼與動態的區塊並存，不用整頁一起選邊站。要選哪一種，靠的是兩個問題：這個頁面每次請求的內容一樣嗎？需要秒級更新嗎？答案會直接把你推向其中一種策略。

第二個決定是 runtime。同一個 server 可以跑在預設、功能完整的 Node.js runtime，也可以切成輕量的 Edge runtime。Edge 的賣點是「離使用者近」——程式在離使用者最近的節點執行，所以延遲低；代價是環境受限、部分 Node API 不支援、有 25 秒與 4 MB 的上限，而且如果資料源很遠，省下的延遲會被抵銷。這不是「Edge 一定比較快」的升級題，而是「這個任務是否對延遲敏感、是否踩到限制」的取捨。

把這兩個決定分開之後，最後再合起來看：策略決定內容的生命週期，runtime 決定執行的地點，而兩者最後都落在一行或一個選項的程式碼上。讀完這五步，你應該能在看到一段 route 時，先說出「它該用哪種策略、跑在哪個 runtime、為什麼」，再去檢查 AI 給的預設值是不是把內容放錯了地方。
