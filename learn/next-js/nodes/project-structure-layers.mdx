# 專案結構與分層：feature 放哪裡

## Learning goal

能指出一個 App Router 專案的每個資料夾對應架構的哪一層，並判斷一段新 feature code 該放在哪一層、放在哪個檔案。

## Steps

閱讀順序（deps 決定誰必須先出現）：

1. [[learn/next-js/nodes/project-structure-layers/top-level-scaffold-layers|頂層檔案與資料夾：一個新專案先看懂哪幾層]] — 把 `npx create-next-app` 產生的頂層檔案分成設定／依賴、靜態資源、應用原始碼三層，知道每個檔案存在的原因。
2. [[learn/next-js/nodes/project-structure-layers/app-folder-conventions|app/ 裡的檔案公約：page、layout 與 globals]] — 看懂 `app/` 內每個檔案的固定角色，尤其是 root layout 如何用 `children` 包住所有路由（需先完成 step 1）。
3. [[learn/next-js/nodes/project-structure-layers/route-groups-and-shells|route group 與分層 shell：URL 不變，版面重組]] — 用 DevFlow 的 `(root)` 與 `(auth)` 看懂 route group 如何在不改 URL 的前提下分層並套上不同 layout（需先完成 step 2）。
4. [[learn/next-js/nodes/project-structure-layers/where-feature-code-goes|新 feature 該放哪裡：一層一層問下去]] — 把前三步變成決策流程：一段新 code 該放頂層設定、`app/` 路由、可重用元件，還是資料／工具層（需先完成 steps 1–3）。

## Lesson

一個 App Router 專案不是一堆隨機生成的檔案，而是一疊有名字的層。最底層是設定與依賴：`package.json`、`package-lock.json`、`tsconfig.json`、`next.config.ts`、`postcss.config.mjs`、`eslint.config.mjs`、`next-env.d.ts` 這些檔案決定專案怎麼被編譯、檢查與啟動，你幾乎只在需要改工具設定時才動它們。往上一層是靜態資源，`public/` 放圖片、字型、favicon 這類原樣被服務的檔案，`node_modules/` 則是 npm 依賴的倉庫，不進版控、不手改。最上層、也是你真正每天改的，是 `app/` 這個資料夾：它同時是路由表、畫面骨架與全域樣式所在。

`app/` 的運作靠「檔案即公約」：`page.tsx` 是某個路由要顯示的內容，`layout.tsx` 是包住子路由的共用外框，`globals.css` 是全站樣式，`fonts/` 與 `favicon.ico` 是資源。最頂層的那個 `layout.tsx` 是 root layout，它用一個 `children` 插槽把所有路由塞進 `html`／`body` 之間，這也是字型、metadata、provider（例如 DevFlow 的 `SessionProvider`、`ThemeProvider`）唯一該放的位子。

真實專案會再往上一層：把 `app/` 拆成 route group，例如 DevFlow 的 `(root)` 與 `(auth)`。括號資料夾不會出現在 URL 裡，卻能讓兩區各自擁有自己的 `layout.tsx`——`(root)` 掛上 navbar 與側邊欄，`(auth)` 只留置中的登入卡片。分層的目的就是這個：每一層只負責一種橫切關注點，換版型或換登入狀態時不必動到頁面本身。

最後一步把這些層變成判斷力。當 AI 丟來一段新 feature，你要能依序問：這是全域設定還是單一路由？需要包住一整個區塊，還是只在這一頁？是 shared UI 還是資料存取？問完之後位置自然浮現。這個節點教的不是背目錄，而是看到陌生 codebase 時，能用「每一層在做什麼」快速定位，並在 AI 把檔案放錯層時一眼看出來。
