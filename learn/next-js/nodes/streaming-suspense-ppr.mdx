# 串流、Suspense、PPR 與 after()

## Learning goal

能用 Suspense 串流獨立資料、把 pending 的 promise 傳給 client 用 use() 解，並判斷何時該用 after() 把副作用延到回應之後。

## Steps

閱讀順序（deps 決定誰必須先出現）：

1. [[learn/next-js/nodes/streaming-suspense-ppr/rsc-ssr-streaming|從整頁等待到串流：RSC、SSR 與 Suspense 的角色]] — 從傳統 SSR 為什麼要等整頁講起，說明串流、選擇性 hydration 與 Suspense 邊界如何縮短等待，並帶到 PPR 的靜態外殼。
2. [[learn/next-js/nodes/streaming-suspense-ppr/suspense-boundaries|用 Suspense 切出可串流的邊界]] — 動手把慢的區塊包進 Suspense、給 fallback，判斷該用檔案式 loading 還是行內邊界，並看懂 PPR 的洞怎麼被填滿（需先完成 step 1）。
3. [[learn/next-js/nodes/streaming-suspense-ppr/promise-props-and-use|傳遞 promise：server 不 await、client 用 use() 解]] — 把尚未 await 的 promise 當 prop 傳給 client，用 `use()` 解開；對照 `await` 為什麼會阻塞 server 渲染（需先完成 steps 1–2）。
4. [[learn/next-js/nodes/streaming-suspense-ppr/after-post-response-effects|after()：把副作用延到回應之後]] — 用 view counter 當案例，在直接 await、Promise.all、client useEffect 與 `after()` 之間做取捨（需先完成 step 1）。

## Lesson

這個節點處理的是「一個頁面明明每個區塊都對，為什麼還是轉圈圈轉很久」。前一個節點把資料抓取的位置畫對了，但當頁面上同時有主內容、側邊欄、投票狀態、答案列表，只要其中一個慢，傳統做法就會讓整個頁面一起等最慢的那一個。這一節要拆解的，是 Next.js 面對這種「部分慢」時提供的三種手段：把慢的區塊用 Suspense 串流出來、把還沒解開的 promise 交給 client 自己解、以及把不需要擋住回應的副作用用 `after()` 延到回應之後。

四步走完之後，你應該能講清楚一條從請求到互動的時間軸：伺服器先送出不必等待的外殼，慢的區塊用 Suspense 標成「之後補上」，React 收到一塊就 hydration 一塊（選擇性 hydration），而 PPR 更進一步把整頁做成靜態外殼、只把動態的洞串流進去。你也會親手寫出 DevFlow 裡真實的兩個模式：一是把 `hasVoted` 這種「還沒 await 的 promise」當 prop 交給 client component，用 React 19 的 `use()` 解開，避免 `await` 把 server 渲染整條鎖住；二是用 `after()` 把瀏覽數、analytics 這類「不該擋住使用者」的工作排到回應送出之後。最後，面對任何一個副作用，你都能在「直接 await、`Promise.all`、client 端、`after()`」之間，依它該不該擋住回應選出正確的位置。
