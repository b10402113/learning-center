# Fetch 快取與 request dedup

## Learning goal

能解釋 Next.js 擴充的 fetch 為何自動快取、request dedup 發生在哪一層，並判斷一段 fetch 的快取行為是否符合預期。

## Steps

1. [[learn/next-js/nodes/fetch-caching-and-dedup/extended-fetch-and-auto-cache|為什麼 Next.js 的 fetch 會自動快取]] — 認出 Next.js 擴充過的那層 fetch，以及預設快取與 `no-store`、`force-cache`、`revalidate` 如何切換行為
2. [[learn/next-js/nodes/fetch-caching-and-dedup/request-dedup-in-one-render|Request dedup：同一次 render 內的請求只發一次]] — 弄清 dedup 的範圍與 key，並和持久化的 Data Cache 分清楚（after step 1）
3. [[learn/next-js/nodes/fetch-caching-and-dedup/memoize-non-fetch-with-react-cache|用 React 的 cache() 幫 server action 去重]] — 當來源不是 fetch 時，用 `cache()` 手動把重複呼叫收斂成一次（after step 2）
4. [[learn/next-js/nodes/fetch-caching-and-dedup/diagnose-cache-behavior|這段 fetch 的快取行為符合預期嗎？]] — 用判別問句找出「資料不更新／重複請求」卡在哪一層，選對修正（after steps 1–3）

## Lesson

快取在 Next.js 裡不是單一開關，而是好幾層疊起來的機制，這也是 AI 產出的程式碼最容易「看起來對、行為卻不對」的地方。這個節點先把最常撞到的兩層拆開講：一層是 Next.js 擴充過的 `fetch` 預設會把回應存進持久化的 Data Cache，所以同一段程式在別的框架可能沒快取、在 Next.js 卻會快取；另一層是 request dedup，也就是在同一次 render 內，相同 URL 加相同 options 的請求只會真的發出去一次。

這兩層的壽命天差地遠：fetch 快取可以跨請求、跨使用者存活到你指定它過期；dedup 卻只活在單一輪 render 裡，render 一結束就忘光。搞混這兩者，就會把「這次 render 為什麼打兩次資料庫」和「為什麼資料隔了幾分鐘還是舊的」誤判成同一個問題。更麻煩的是，一旦資料來源不是 `fetch`（例如直接呼叫 server action 或 ORM 查詢），`fetch` 的那層保護完全不會生效，你得自己用 React 的 `cache()` 補上同一次 render 內的去重。

把這幾層的職責與壽命分清楚之後，最後一步要練的是反向能力：拿到一段會「資料不更新」或「重複抓同一份資料」的程式碼，判斷它究竟卡在哪一層，並挑出正確的修正，而不是憑感覺亂加 `no-store`。
