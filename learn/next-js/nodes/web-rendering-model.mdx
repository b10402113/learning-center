# The Web-Rendering Model

## Learning goal

畫得出 vanilla → React CSR → Next 三種渲染模型，並解釋 hydration 與 hydration mismatch 從何而來。

## Steps

1. [[learn/next-js/nodes/web-rendering-model/vanilla-rendering-baseline|傳統模型：伺服器送檔、瀏覽器幹活]] — 看懂一次請求往返，以及「伺服器送完整檔案、瀏覽器負責渲染」的三個代價
2. [[learn/next-js/nodes/web-rendering-model/react-csr-and-virtual-dom|React 的 CSR：薄薄的 HTML 加一大包 JS]] — 解釋最小 HTML＋打包 JS 的客戶端渲染、Virtual DOM diffing 與 SPA 導航，以及它留下的 SEO 洞（after step 1）
3. [[learn/next-js/nodes/web-rendering-model/nextjs-ssr-and-hydration|Next.js 的 SSR：先畫出來，再 hydration 接上互動]] — 分兩段說清楚伺服器渲染 HTML 與客戶端 hydration 各自在做什麼（after step 2）
4. [[learn/next-js/nodes/web-rendering-model/hydration-mismatch|Hydration mismatch：伺服器與瀏覽器為什麼會對不上]] — 指出兩次渲染不一致時錯誤從何而來（after step 3）
5. [[learn/next-js/nodes/web-rendering-model/birth-of-server-components|Server Components 的誕生：React 為什麼往伺服器走]] — 補上歷史動機與時間線，收束整個渲染模型的轉向（after steps 2–3）

## Lesson

這一節要回答的問題是：同一個網頁，為什麼會有「伺服器送檔」「瀏覽器自己畫」「伺服器先畫一半」這麼多種做法？如果你只是把 Next.js 當成「比較新的 React」來用，就看不出它到底在哪裡省下了什麼、又把哪些成本搬到了哪裡。

課程沿著一條時間線推進。第一步先回到最原始的模型：伺服器把完整的 HTML、CSS、JS 檔送給瀏覽器，由瀏覽器解析、套樣式、跑互動——這個「伺服器送檔、瀏覽器幹活」的分工，是後面每一種做法都要拿來對照的基準。第二步看 React 的改變：伺服器只送一個薄薄的 HTML 殼和一大包 JavaScript，畫面改由瀏覽器端渲染，再用 Virtual DOM 只更新有變動的部分；好用，但首屏要等 JS，搜尋引擎也不一定看得懂。

第三步是這個節點的核心：Next.js 讓伺服器先執行 React 元件、直接回傳已經畫好的 HTML，瀏覽器可以立刻顯示內容，然後 JavaScript 才下載進來，由 hydration 把事件處理逐一接回這些 HTML。第四步專門處理 hydration 最常咬人的地方——當伺服器畫出來的結果和瀏覽器第一次畫的結果對不上，就會出現 hydration mismatch。最後一步把鏡頭拉遠，看整個 React 生態為什麼在 2020 年之後集體往伺服器移動（Server Components 的誕生），並連到下一節的 server/client 元件邊界。
