# 在 RSC 裡抓資料：何時 server、何時 client

## Learning goal

能在 RSC 裡直接 async 抓資料，說出與 useEffect fetch 相比在 FCP / SEO / dedup / 金鑰安全上的差異，並辨認 N+1 與 network waterfall。

## Steps

閱讀順序（deps 決定誰必須先出現）：

1. [[learn/next-js/nodes/server-data-fetching/rsc-vs-client-fetching|兩種抓資料的方式：useEffect 還是 RSC？]] — 對照 client 的 useEffect fetch 與 RSC 的直接 async 抓資料，建立「為什麼要在 server 抓」的理由。
2. [[learn/next-js/nodes/server-data-fetching/fetching-in-rsc|在 server component 裡抓資料：async、await 與直接查 DB]] — 動手把上一課的理由寫成程式碼：async component、`await searchParams`、呼叫 server action 或直接查 DB（需先完成 step 1）。
3. [[learn/next-js/nodes/server-data-fetching/waterfalls-and-n-plus-one|瀑布與 N+1：資料為什麼抓得慢]] — 辨認 sequential await 的 network waterfall 與 N+1 query，用 `Promise.all` 與 `.populate()` 收掉（需先完成 step 2）。
4. [[learn/next-js/nodes/server-data-fetching/when-server-when-client|何時 server、何時 client：畫出資料邊界]] — 用互動需求、SEO、金鑰安全與即時性做取捨，認出兩種常見踩雷（需先完成 steps 1、3）。

## Lesson

這個節點要回答的，是 Next.js 開發者最常寫錯的一件事：**資料到底該在哪裡抓**。很多人從 React 過來，反射動作就是在 client component 裡 `useEffect` 加 `useState`，畫面先空著、轉圈圈，等資料回來再填。這個寫法沒有壞掉，但它把資料推到使用者的瀏覽器才開始抓，於是首屏變慢、搜尋引擎看不到內容、API 金鑰可能外洩，也不會自動去重。Next.js 的 App Router 預設所有元件都是 React Server Component（RSC），可以像寫一般 async function 一樣，直接在 server 上 `await` 資料或查資料庫，再把結果交給元件渲染。

四步走完之後，你應該具備一套完整的判斷：先知道為什麼 server 抓資料在 FCP、SEO、request dedup、金鑰安全與 network waterfall 上都佔優勢；再知道怎麼把它寫出來（async server component、`await searchParams`、呼叫 server action、查不到就 `redirect` 到 404）；再能認出拖慢資料的兩個兇手——一條條 `await` 排成的 network waterfall，以及先抓清單再逐筆查關聯的 N+1；最後把這些收斂成一張判斷表，能一眼看出 AI 產出的程式碼是把資料線畫在對的位置，還是反射性地全部丟給 client。
