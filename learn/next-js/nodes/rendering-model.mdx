# 渲染模型：CSR / SSR / RSC / hydration

## Learning goal

能用 CSR / SSR / RSC / hydration 四個詞解釋一個頁面從請求到互動的完整生命週期，並指出任一元件是在 server 還是 client 執行、為什麼。

## Steps

1. [[learn/next-js/nodes/rendering-model/web-rendering-models|從請求到畫面：三種送頁面的模型]] — 用「server 送什麼、browser 做多少」比較 vanilla / React CSR / Next.js
2. [[learn/next-js/nodes/rendering-model/csr-and-virtual-dom|CSR：最小 HTML、JS bundle 與 virtual DOM]] — CSR 的運作鏈與首次載入、SEO 代價（after step 1）
3. [[learn/next-js/nodes/rendering-model/ssr-and-hydration|SSR 與 hydration：先送 HTML，再接手互動]] — server 先渲染完整 HTML，client 再 hydration 接上事件（after step 1）
4. [[learn/next-js/nodes/rendering-model/server-and-client-components|RSC 與 Client Component：`"use client"` 邊界]] — 預設 server、`"use client"` 劃界、import 進 client 就變 client bundle（after steps 2–3）
5. [[learn/next-js/nodes/rendering-model/deciding-where-to-render|判斷元件該在 server 還是 client 執行]] — 用互動性判準與常見踩雷決定每個元件的落點（after step 4）

## Lesson

同一個頁面，用三種不同的方式送到瀏覽器，就會有三種完全不同的生命週期。這個節點要建立的，是一條從「請求」到「互動」的完整時間線：你按下 enter 之後，server 到底送了什麼給瀏覽器？瀏覽器又自己動手做了多少事？畫面什麼時候能看到？事件什麼時候才真的能點？

先從三種送頁面的模型開始：vanilla 是 server 把完整的 HTML / CSS / JS 檔送過來，React 是只送最小 HTML 加一大包 JavaScript、由瀏覽器自己把畫面組出來（這就是 CSR），Next.js 則是在 server 先把 React 元件跑成完整 HTML 送出去（SSR），再讓瀏覽器接手互動（hydration）。這三者的差別，本質上是「誰在什麼時候做渲染」的分配問題。

有了這條時間線，才能往下回答每個 Next.js 開發者每天都得做的決定：這個元件到底該在 server 還是 client 執行？App Router 預設所有元件都是 Server Component，你要用 `"use client"` 明確劃出 client 邊界。搞懂這個邊界，你才有辦法看懂 AI 產出的專案為什麼這樣切、以及它切錯了哪裡。
