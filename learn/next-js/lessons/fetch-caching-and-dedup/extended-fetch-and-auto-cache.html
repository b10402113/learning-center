為什麼 Next.js 的 fetch 會自動快取？

Step 1/4 · Fetch 快取與 request dedup

前言：我沒寫快取，資料為什麼還是舊的？

你請 AI 寫了一個頁面，裡面只有一行 fetch，用來抓某個 API。功能正常，畫面也成功顯示。幾天後，你更新了後端資料，重新整理頁面，看到的卻還是舊內容。

你回頭檢查程式碼：沒有快取套件、沒有 CDN，也沒有任何熟悉的快取設定。這時很容易懷疑，是不是後端其實沒有更新。

如果把同一段程式碼放進純 React 專案，通常不會有這種落差。瀏覽器原生的 fetch 每次呼叫都會真的送出請求；但在 Next.js 裡，fetch 多了一層 Next.js 的處理。這一層會改變它的預設行為，也正是「明明沒寫快取，資料卻是舊的」的原因。

先看大圖：Next.js 在 fetch 外面加了一層什麼？

可以把瀏覽器原生的 fetch 想成一個每次都會跑到郵局寄信的人：你呼叫一次，它就送出一次網路請求，拿回回應，工作結束。它不會主動記住上一封信的內容，也不會替你判斷下次能不能重用。

Next.js 則像是在郵局門口加了一個收發櫃檯。你送出 fetch 前，它會先檢查 Data Cache 裡有沒有相同請求的結果。如果有，就直接把結果交給你；如果沒有，才真的送出請求，並把回應存起來。

所以兩者的差別可以這樣看：

環境fetch 的直覺行為是否會主動使用 Next.js 的 Data Cache
瀏覽器原生 fetch每次呼叫都送出網路請求不會
Next.js 的 fetch先檢查快取，有需要才送出請求會

這也是為什麼在 Next.js 專案裡，大家常用 fetch 而不是 axios。重點不是 fetch 的語法比較漂亮，而是 Next.js 能攔截並擴充它，讓它和自己的快取系統合作。axios 是第三方套件，Next.js 管不到同一層，因此用 axios 抓取的資料不會進入這套快取機制。

AI 常犯版 vs 正解版：不要把 Next.js fetch 當成瀏覽器 fetch

AI 常犯版：看到 fetch(url)，就直接套用瀏覽器的直覺，認為每次重新整理都會重新向 API 要資料。

正解版：先問自己：「這個 fetch 是在哪裡執行的？」如果它是在 Next.js 中執行，就要把 Data Cache 算進來。相同請求可能不會再次打到來源，而是直接拿到先前存下來的回應。

這個判斷是後面所有設定的起點。你如果把 Next.js 的 fetch 當成原生版本，遇到舊資料時，就會一直在 API、瀏覽器或 CDN 之間猜原因，卻漏掉真正的快取層。

預設行為：什麼都不寫，也可能快取

最容易讓人踩到的地方是：你不需要寫任何快取設定，這層機制就可能生效。

一個沒有選項的 fetch，Next.js 會把它視為可以重複使用的資料。第一次請求時，快取裡還沒有內容，所以它會真的去呼叫來源，並把回應存起來。下一次頁面或元件呼叫相同 URL 時，就可能直接從快取取回，不再重新打來源。

觀察開發者工具或伺服器 log 時，通常會看到兩種狀態：

  • cache skip：跳過快取，真的去抓資料。
  • cache hit：命中快取，直接回傳既有結果。

「第一次 miss，後面 hit」就是 Next.js Data Cache 運作時的典型樣子。它之所以朝這個方向設計，是因為 Next.js 預設會把頁面視為適合重用的內容。部落格、文件、商品列表這類不常變動的頁面，使用快取通常能讓回應更快，也能減少不必要的來源請求。

但如果頁面要求每次都顯示最新資料，這個預設值就會變成陷阱。AI 常犯版是把「我沒有寫快取」理解成「一定不會快取」；正解版則是先確認 Next.js 的預設策略，再依資料的新鮮度需求明確設定。

三個旋鈕：決定是否快取，以及可以舊多久

快取設定其實在回答兩個問題：

  1. 這份資料要不要存進快取？
  2. 如果要存，可以保留多久？

cache 主要處理第一個問題。revalidate 則是在資料可以被重用的前提下，處理第二個問題。

cache: 'no-store'：每次都拿最新資料

no-store 的意思是完全不要使用這層快取。Next.js 不從自己的快取取資料，也不把這次拿到的結果存起來；每次請求都直接到來源取得最新內容。

這適合即時股價、聊天訊息等不能接受舊資料的情境。當然，代價是每次都要重新發出請求，來源也必須承擔相應的流量與處理成本。

cache: 'no-store',

cache: 'force-cache'：有可用快取就先重用

force-cache 的方向相反：只要有可用的快取，就優先使用。快取不存在或已經過期時，Next.js 才會回到來源取得新資料，並把新結果存回去。

這種行為和「什麼都不寫」的預設方向幾乎一樣，因為 Next.js 預設就是盡量重用能重用的資料。

AI 常犯版：看見 force-cache 就以為它是某種額外的特殊快取功能。

正解版：把它理解成清楚寫出的意圖：「這份資料可以重用，有快取就先用。」它特別適合不常變動的內容。

revalidate：讓快取定期更新

有些資料不需要每秒都是最新，但也不能永遠停留在第一次抓到的版本。這時就需要第三個維度：快取多久後重新取得資料。

revalidate 有兩種寫法。一種放在頁面或 route 的最上層，會影響整個路由；另一種放在單一個 fetch 的選項裡，只影響那一次請求。

export const revalidate = false | 0 | number;
fetch(`https://...`, { next: { revalidate: false | 0 | number } });

這三種值可以想成三種不同的保鮮策略：

  • false：盡可能一直保留快取。實際上，HTTP 快取仍可能在很久以後被清除。
  • 0：不使用快取，每次重新產生，行為上接近 no-store。
  • 數字：把快取保留指定的秒數。時間到了，Next.js 才回來源取得新版本，再把新版本存回快取。

因此，數字型的 revalidate 不是「每隔幾秒主動更新一次」，而比較像一個保鮮期限：有人再次需要這份資料，而且期限已到時，才會進入更新循環。

把三個設定放在一起比較

設定行為適合的資料
cache: 'no-store'完全不快取，每次都打來源即時、不能舊的資料
cache: 'force-cache'有新鮮快取就用，沒有才去抓不常變的資料，也是預設方向
next: { revalidate: N }快取 N 秒後才更新一次偶爾變動、容許幾分鐘延遲的資料
next: { revalidate: 0 }等同不快取，每次重算需要即時資料，但仍使用 fetch 的場景
next: { revalidate: false }盡量永久保留快取幾乎不變的資料

選設定時，不要只問「哪一個最好」。真正要問的是：「這份資料最多可以舊多久？」如果答案是完全不能舊，就選擇不快取；如果幾分鐘的延遲可以接受，就用指定秒數的 revalidate；如果內容幾乎不變，就讓它盡量被重用。

這層機制叫 Data Cache，但不要和 request dedup 混在一起

這整層機制通常稱為 Data Cache，也常被口語地叫作 fetch 快取。它有兩個重要特徵。

第一，它是由 Next.js 擴充過的 fetch 驅動。只有透過這個 fetch 抓取的資料，才會使用這套機制。

第二，它可以跨請求、跨使用者存活。只要資料還沒有過期，不同次瀏覽、不同使用者的請求，都可能共用同一份快取資料。

這裡先記住「跨請求、可持久保留」這兩個關鍵字。下一節會介紹另一層看起來很像、但範圍完全不同的機制：request dedup。它只在單一次 render 內避免重複請求，不是用來長期保存資料的 Data Cache。

AI 常犯版：看到同一個 URL 沒有被打兩次，就直接說那是 Data Cache。

正解版：先分辨問題的範圍：資料是否跨請求、跨使用者保存？如果是，談的是 Data Cache；如果只是在同一次 render 中合併重複請求，才是 request dedup。

把這個觀念掛回整體架構

Next.js 把瀏覽器原生的 fetch 換成擴充版，讓它自動和 Data Cache 合作。所以一個沒寫任何設定的 fetch，預設就會快取：第一次去來源抓，之後直接命中快取。要控制它就調三個地方：cache: 'no-store' 完全不快取、cache: 'force-cache' 有快取就用、next: { revalidate } 決定快取活多久。也因為只有擴充版 fetch 吃得到這層，Next.js 專案才偏好 fetch 而非 axios。

現在可以把這個觀念放回整體架構裡：Next.js 的 fetch 不是單純把請求送出去，而是先經過 Data Cache 這道門。cache 決定要不要使用這道門，revalidate 決定快取內容能保留多久。

接下來的問題則不同：如果同一次 render 裡，兩個地方不小心呼叫了相同 URL，Next.js 會打兩次，還是只打一次？那不是 Data Cache 在處理，而是另一層叫做 request dedup 的機制。把這兩層分開，才不會再把「資料被保存」和「重複請求被合併」混成同一件事。
