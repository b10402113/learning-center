用 React 的 cache() 幫 server action 去重

Step 3/4 · Fetch 快取與 request dedup

先確認目標與前置條件

這一節要處理的情境很具體：同一個問題詳情頁中，generateMetadata 為了組出頁面標題查了一次資料，頁面元件又為了顯示內容查了一次。最後畫面雖然正確，資料庫卻多做了一次工作。

完成後，你會知道如何用 React 的 cache() 包住 server action 或資料庫查詢，讓同一次 render 中、使用相同參數的第二次呼叫直接重用第一次的結果。

開始前，請先確認你理解兩件事：自動 request dedup 只發生在同一輪 render 內，而且這裡的資料來源是 server action 或直接的資料庫查詢，不是遠端 fetch。動手修改前，先找出重複查詢，再加上快取。

先看全貌：哪裡重複、要改哪裡

整個修正流程可以想成三步：

  1. 找出同一輪 render 中，使用相同參數重複呼叫的函式。
  2. 從 react 匯入 cache。
  3. 用 cache() 包住原本的函式，呼叫端維持不變。

這次要包起來的是 getQuestion。它原本是 server action，不是 fetch，所以 React 不會自動幫它去重。

步驟一：先把重複的地方指出來

不要一看到資料庫查詢就急著加快取。先確認同一份資料到底被誰拿了幾次。

打開問題詳情頁，第一個呼叫點在 generateMetadata。它需要問題資料來組出 metadata 的 title：

export async function generateMetadata({
  params,
}: RouteParams): Promise<Metadata> {
  const { id } = await params;

  const { success, data: question } = await getQuestion({ questionId: id });

接著往下看頁面元件。頁面本身也用同一個 id 呼叫 getQuestion：

const QuestionDetails = async ({ params, searchParams }: RouteParams) => {
  const { id } = await params;
  const { page, pageSize, filter } = await searchParams;
  const { success, data: question } = await getQuestion({ questionId: id });

這兩次呼叫有兩個關鍵特徵：

  • 呼叫的是同一個函式：getQuestion。
  • 傳入的是相同參數：{ questionId: id }。

因此，同一輪 render 中，這份資料會被查兩次。上一節提過，React 會自動合併重複的 fetch，但不會自動處理 server action 或直接的資料庫查詢。這就是本節要補上的缺口。

步驟二：從 react 匯入 cache

cache 是 React 內建的工具，不是 Next.js 專屬 API。請在 server action 檔案的頂端加入：

import { cache } from "react";

這一步只是把工具準備好，還不會改變查詢行為。真正的去重會發生在下一步：把原本的函式交給 cache() 管理。

步驟三：用 cache() 包住原本的函式

原本的寫法是直接 export 一個 async 函式：

// 改動前：直接匯出，沒有去重
export async function getQuestion(params: GetQuestionParams) {
  // …
}

這是常見的「AI 常犯版」：函式本身可以正常執行，但 React 不知道它的結果能在同一輪 render 中重用。

正解不是重寫驗證、資料庫查詢或錯誤處理，而是在函式外面多包一層 cache()。專案中的完整寫法如下：

export const getQuestion = cache(async function getQuestion(
  params: GetQuestionParams
): Promise<ActionResponse<Question>> {
  const validationResult = await action({
    params,
    schema: GetQuestionSchema,
  });

  if (validationResult instanceof Error) {
    return handleError(validationResult) as ErrorResponse;
  }

  const { questionId } = validationResult.params!;

  try {
    const question = await Question.findById(questionId)
      .populate("tags", "_id name")
      .populate("author", "_id name image");

    if (!question) throw new Error("Question not found");

    return { success: true, data: JSON.parse(JSON.stringify(question)) };
  } catch (error) {
    return handleError(error) as ErrorResponse;
  }
});

請特別看第一行的變化：

  • 原本是 export async function getQuestion。
  • 現在改成 export const getQuestion = cache(async function getQuestion。

也就是把原本的 async 函式傳進 cache()，再把包裝後的結果 export 出去。函式裡的參數驗證、Question.findById、資料 populate，以及錯誤處理都不用改。

可以把它想成在查詢門口放了一個小記事本：第一次用某個參數查詢時，照常執行；同一輪 render 又拿著相同參數來一次，就直接拿前一次的結果，不必再次走進資料庫。

步驟四：呼叫端不用改，直接確認結果

這次修改的好處是，generateMetadata 和頁面元件都不需要調整。它們仍然照原本的方式呼叫：

await getQuestion({ questionId: id })

差別藏在 getQuestion 內部：

  1. 同一輪 render 中，第一次呼叫會真的執行資料庫查詢。
  2. 第二次以相同參數呼叫時，React 會直接回傳第一次的結果。
  3. metadata 的 title 與頁面內容仍然可以正常取得。

最直接的驗證方式，是觀察資料庫 log 中的查詢次數，或暫時在函式內印出訊息。相同問題在同一輪 render 中應該只查詢一次，而畫面上的 title 與內容仍然存在。

也可以用更直觀的方式觀察去重效果：讓一個函式產生隨機數，分別測試「有包 cache」與「沒有包 cache」的版本，各呼叫兩次。有包的版本兩次會拿到同一個數字；沒有包的版本則會拿到不同數字。

步驟五：確認 cache() 的使用邊界

cache() 解決的是「同一輪 render 裡不要重複做同一件事」，不是永久保存資料。它的有效範圍是：

  • 同一輪 render。
  • 同一個 route。

它不會跨請求，也不會跨 route 共用結果。換到另一個 route 後，前一輪的記憶就清空，函式會重新執行。若需求是跨 route 共用同一份結果，那是另一種快取問題，需要使用像 unstable_cache 這類工具；這會留到 revalidation 與多層快取的主題再處理。

另外，也不要因為擔心重複就把所有函式都包上 cache()。如果函式只會被呼叫一次，包起來不會帶來效果；如果每次傳入的參數都不同，也沒有相同結果可以重用。

判斷方式很簡單：若某個函式在同一輪 render 中，被多個地方用相同參數呼叫，就適合考慮 cache()。

做完後，你應該看到什麼

完成修改後，getQuestion 的函式本體與所有呼叫端都維持原本的邏輯。不同的是，同一個問題在同一輪 render 中只會觸發一次資料庫查詢；generateMetadata 和頁面元件則共同重用那次查詢的結果。

當資料來源是 server action 或直接的資料庫查詢時，React 不會自動去重，同一次 render 裡呼叫兩次就是查兩次。修法很簡單：從 react 匯入 cache，用它包住原本的 async 函式，再匯出包好的版本，函式本體與所有呼叫端都不用改。這樣同參數的第二次呼叫就會直接拿到第一次的結果。但要記得，這個記憶只在同一輪 render、同一 route 內有效，跨 route 共用要換另一種工具。

到這裡，你已經把三層機制串起來：跨請求的持久 fetch 快取、單輪 render 內的 request dedup，以及用來補上非 fetch 查詢缺口的手動 cache()。

下一節會把這些機制放進同一個判斷流程：當你遇到「資料不更新」或「同一份資料被重複抓取」時，先判斷問題卡在哪一層，再選對工具。
