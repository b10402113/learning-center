這段 fetch 的快取行為符合預期嗎？

Step 4/4 · Fetch 快取與 request dedup

先看整張地圖：你要做的是哪個決定？

遇到「資料明明改了，頁面卻還是舊的」，或是 log 裡出現「同一份資料被抓了兩次」，你可能會直覺認為快取壞了，然後立刻在 fetch 加上 no-store。這個做法有時有效，卻也可能像是為了治頭痛，直接把整間診所拆掉：原本可以快取的內容，從此每次請求都重新計算、重新打來源。

真正要做的決定不是「要不要快取」，而是問題發生在哪一層，以及那一層原本該不該快取。你可以先把問題分成三層來看：跨請求的持久快取、同一輪 render 的 request dedup，以及不同資料來源本身的行為。先定位，再選旋鈕，通常就不必反射性地關掉快取。

學習目標

拿到一段「資料不更新」或「同一份資料被重複抓」的程式碼時，能逐層判斷它卡在哪一層快取，選出對的修正，並判斷眼前的症狀是不是預期行為。

兩股張力：新鮮度，還是成本與速度？

調整快取時，你其實一直在兩個目標之間取捨。

一邊是新鮮度：使用者希望越快看到最新資料越好。另一邊是成本與速度：快取能省下重複的運算與請求，讓頁面更快顯示，也減少來源服務的負擔。

預設值通常站在成本這一邊，因為多數內容不會每秒改變。但如果你的資料真的要求即時，這個預設值就可能反過來造成困擾。判斷重點不是哪個選項「最好」，而是這份資料多久會變一次，以及你容不容許它延遲一段時間。

選項比較：先定位，再開藥

先把常見症狀、可能出問題的層級，以及對應修正並列起來。這張表適合在看到症狀後先查，不要一看到舊資料就直接加上 no-store。

症狀大概卡在哪一層對應的修正
改了後端資料，跨請求後畫面仍是舊的fetch 快取（Data Cache）cache: 'no-store'，或設 revalidate
API route 加了新資料，GET 卻拿到舊結果route handler 的 GET 預設快取export const dynamic = 'force-dynamic'

最容易被誤判的是 route handler 的 GET。它預設就會被快取，所以你即使改了資料庫，再重新呼叫 API route，仍可能拿到舊結果。這不一定是程式壞掉，而是 Next.js 對 GET 的預設行為。若你確定這個 route 不應該使用這種快取，可以在 route 檔案最上方加上 force-dynamic：

export const dynamic = 'force-dynamic'

如果你的需求不是「完全不要快取」，而是「隔一段時間更新一次」，就使用 revalidate。它可以寫在頁面頂端，也可以寫在單一個 fetch 的選項裡。數字代表快取存活幾秒；0 等同不快取，false 則近乎永久保留。

export const revalidate = false | 0 | number;

三個判別問句：不要先猜，先問

表格適合快速對照；真正除錯時，請依序問下面三個問題。順序很重要，因為第一題就能先把問題切成兩大類。

第一問：舊資料是跨請求都舊，還是只有這一次 render 裡重複？

如果重新整理，或隔幾分鐘再看仍然是舊資料，問題比較可能在持久快取，例如 fetch 的 Data Cache 或 route handler 的 GET 快取。

如果只有某一次 render 裡出現重複呼叫，重新開始後就正常，那比較像是 request dedup 的問題。這時不要急著調整跨請求快取，因為你找錯層了。

第二問：資料來源是 fetch，還是 server action、直接查資料庫？

這個差異很關鍵。若來源是非 fetch 的函式，例如 server action 或直接查資料庫，而同一輪 render 又重複呼叫，React 的自動去重不會因此啟動。正解是用 React 的 cache() 手動包住它，而不是在完全無關的 fetch 選項上亂加設定。

第三問：這份資料本來該不該快取？

在動手改設定前，先問資料能不能稍微舊一點。如果它是不常變的內容，快取其實是正確行為。你不該只因為想立刻看到更新，就犧牲整體效能；可以等待快取自然過期，或在資料改動時主動讓它失效（revalidate）。

反例：規則什麼時候會翻轉？

判別問句很有用，但不是每個症狀都能用同一把扳手處理。以下幾個反例，正是 AI 很容易寫錯、人工驗收時也要特別留意的地方。

反例一：濫用 no-store。

如果你只是「偶爾想看到新資料」，卻把整個頁面設成 no-store，那每次請求都會重新運算、重新打來源。對高流量頁面來說，這等於把原本可以免費取得的效能主動送掉。

真的要求即時資料時，才使用 no-store。如果只是「幾分鐘後更新也可以」，通常設一個 revalidate 秒數會更划算。

反例二：把開發環境的現象當成正式環境的答案。

在 npm run dev 底下，Next.js 有自己的開發快取與 HMR 機制。本機看到的「快取命中」或「資料沒有更新」，未必等於正式環境的行為。

如果行為對不上，請用正式建置（production build）再驗一次。不要只憑 localhost 的觀察，就斷定 production 一定會用同樣的方式執行。

反例三：把沒有設定的 fetch 當成即時資料。

你把 fetch 完全不寫設定，卻期待它每次都回來源抓最新資料，這不是 Next.js 的 bug，而是它的 SSG 預設行為在發揮作用。這種寫法容易讓人誤以為「沒有設定」就代表「不快取」，實際上並不是。

比較可靠的習慣是：每寫一個 fetch，就問自己這份資料能不能舊。如果不能舊，就明確寫 no-store，或給一個很短的 revalidate；如果能舊，就讓預設值替你省下成本。

一句決策規則帶著走

先看壽命：是跨請求，還是單輪 render？再看來源：是 fetch，還是非 fetch？最後看新鮮度需求：這份資料該不該快取、最多能舊多久？

照這個順序判斷，你就能把「資料不更新」和「重複請求」分開處理，而不是兩種症狀都用 no-store 一次解決。

小結

遇到快取問題，不要反射性地加上 no-store。先用三個判別問句定位：跨請求還是單輪 render、來源是 fetch 還是 server action、這份資料本來該不該快取。跨請求且是 fetch 的舊資料，往 Data Cache 找，用 revalidate 或必要時才 no-store；route handler 的 GET 舊資料，用 force-dynamic；非 fetch 的同輪重複，用 React 的 cache()；要跨 route 共用，才輪到 unstable_cache。判斷的順序本身就是答案。
