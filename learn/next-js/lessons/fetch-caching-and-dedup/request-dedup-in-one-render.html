Request dedup：同一次 render 裡，同一個請求只發一次

Step 2/4 · Fetch 快取與 request dedup

先看全貌：兩種「記住資料」不是同一件事

上一節談到 Next.js 擴充過的 fetch：它會把回應放進 Data Cache，讓之後的請求，甚至不同使用者的請求，都有機會重用同一份資料。

但還有另一種常見情境：在同一次 render 裡，頁面和 generateMetadata 都需要同一份資料。這時候，應該打兩次 API 或資料庫，還是只打一次？

這就是 request dedup（請求去重）要解決的問題。它會把同一輪 render 裡重複出現的相同請求合併，避免相同工作被做兩遍。不過，它和 fetch 快取的外表很像，實際上卻是兩層不同的機制：一層把資料留給未來使用，另一層只負責讓眼前這一輪不要重複。

先看一個場景：頁面和 metadata 都要同一份資料

假設你正在做一個問題詳情頁。頁面本身需要問題資料來顯示標題與內容；同時，generateMetadata 也需要同一份資料來組出頁面的 title 和 description。

在沒有去重的情況下，兩個地方各自呼叫一次 getQuestion，看起來就會查詢兩次。這代表多一次資料庫或 API 呼叫，也多一份不必要的網路與處理成本。

request dedup 的作用，就像有人在廚房門口幫忙登記：「這份零食已經有人拿了。」第一個人真的走進廚房取餐；後面來拿同一份的人，直接分享已經拿回來的那份，不必再跑一趟。

AI 常犯版：看到兩個呼叫，就以為一定執行兩次

只看程式碼表面，很容易得出這個結論：

「generateMetadata 呼叫一次，頁面元件又呼叫一次，所以資料來源一定會被打兩次。」

這個判斷忽略了兩個呼叫發生的時間點。它們都在同一次 render 裡，而且請求的條件相同，因此 React 有機會把它們視為同一個請求，讓後面的呼叫共享前一次的結果。

正解版：key 相同，這一輪 render 只真正執行一次

request memoization（請求記憶化）的規則可以精確地說成：

在單一輪 render 裡，如果有兩個以上的地方發出相同 URL 且相同 options 的請求，React 只會真的執行一次，其餘呼叫會共享那一次的結果。

這裡的 key 是「URL 加上 options 的組合」，不是只看 URL。換句話說，下面兩個請求可以被視為相同：

  • fetch('/api/user')
  • fetch('/api/user')

但只要 options 不同，就不一定能合併。例如其中一個多了 cache: 'no-store'，或兩個請求的 method、headers 不同，React 就會把它們當成不同請求，各自執行。

用真實的 metadata + page 看清楚

先看 generateMetadata。它需要問題資料來組出 title 與 description，因此呼叫了 getQuestion：

從程式碼看，getQuestion 確實出現了兩次。不過，只要這兩次呼叫在同一次 render 裡、請求條件也相同，React 的 request memoization 就會把它們合併成一次實際的請求。

這裡有一個容易混淆的地方：這不是因為 getQuestion 自己內建了快取，而是因為它背後使用的請求能被 request dedup 處理。換句話說，看到兩段相同的呼叫，不要立刻把它們等同於兩次真正的資料來源請求；先確認它們是否落在同一輪 render，以及 key 是否完全相同。

request dedup 的邊界：它只活在這一輪

request dedup 的記憶範圍很短。它只在同一個 route、同一輪 render 裡有效。把同樣的邏輯放到另一個 route，請求就會重新執行一次，因為 React 不會把上一個 route 那一輪 render 的記憶一直保留著。

可以把它想成會議室裡的白板：會議進行時，大家知道「這件事剛剛已經做過了」；會議結束、換到另一間房間，白板就清空了。它的目的不是長期保存資料，而是避免同一場會議裡重複做同一件事。

兩層快取的好／壞判斷

這兩層機制的 key 規則很接近，所以很容易被混為一談。真正需要分辨的是：誰在管理、能活多久，以及它要解決哪一種問題。

fetch 快取（Data Cache）request dedup（memoization）
由誰驅動Next.js 擴充版 fetchReact 在同一輪 render 內比對
壽命跨請求、跨使用者，直到過期只在單一輪 render 內
合併的 key同 URL 加同 options同 URL 加同 options
換 route 之後快取還在，仍可能命中記憶清空，重新執行
典型症狀資料過了好久還是舊的這次 render 為什麼打了兩次

AI 常犯版：看到資料重複使用，就在 Data Cache 和 request dedup 之間隨便加設定。

正解版：先依照症狀找層級。資料隔了好一段時間仍然是舊的，通常要檢查 Data Cache；如果是同一次 render 裡「明明只該抓一次，卻好像抓了兩次」，才要檢查 request dedup。

簡單說，Data Cache 是「把結果存起來，之後還能用」；request dedup 則是「這一輪已經有人做過了，其他人直接共用」。前者在意資料能保存多久，後者在意同一輪裡不要重複工作。

這層不是萬靈丹：非 fetch 請求不會自動去重

request dedup 並不是所有資料來源都會自動套用。它之所以能運作，是因為 React 能辨識並處理 fetch 這類請求。

如果資料不是透過 fetch 取得，而是直接呼叫 server action，或直接使用 ORM 查詢資料庫，那麼 React 不會自動幫你去重。同一次 render 裡呼叫兩次，就可能真的執行兩次查詢。

這就是一個重要的反例：

AI 常犯版：只要兩段程式碼取得的是同一份資料，React 就一定會自動合併。

正解版：要先確認資料來源是否屬於 React 能自動去重的請求。對不是 fetch 的資料來源，必須另外處理。

React 提供了 cache() 這個工具，讓你可以把非 fetch 的請求包進同一層去重機制。下一節會接著說明，當資料來自 server action 或資料庫查詢時，如何用它把 metadata 和頁面之間的重複查詢收斂成一次。

把這個觀念放回整體架構

現在可以把兩種機制放在同一張心智地圖上：

  • request dedup：只處理同一次 render 裡的重複工作，重點是不要在當下打兩次。
  • Data Cache：把 fetch 的結果保存下來，讓後續請求有機會重用，重點是資料能跨請求保留。
  • cache()：補上非 fetch 資料來源的缺口，讓這些呼叫也能被包進去重邏輯。

所以，request dedup 不取代 Data Cache，也不是另一種長期快取。它比較像 render 過程中的臨時共用站：只要大家在同一輪、拿著相同的 URL 與 options 來取資料，就共用同一份結果；一旦換了 route 或進入下一輪，這份記憶就不再負責。

小結

request dedup 是 React 在同一輪 render 內做的請求去重：相同 URL 加相同 options 的請求，只會真正執行一次，結果再分享給所有需要它的元件。它的 key 規則和 fetch 快取相近，但壽命短得多，只在該 route 的那一輪 render 裡有效。Data Cache 負責跨請求保存資料；request dedup 則只負責讓當下這一輪不要重複工作。另外，這種自動去重主要針對 fetch；server action 或直接查資料庫的呼叫，還需要透過 React 的 cache() 另外處理。

掌握這條界線後，看到重複資料請求時，就能先判斷問題在哪一層：是資料保存太久、造成 Data Cache 命中舊資料，還是同一次 render 裡沒有把重複工作收斂。下一節會補上非 fetch 請求的缺口，看看如何用 React 的 cache()，讓 metadata 和頁面不再各自查一次資料庫。
