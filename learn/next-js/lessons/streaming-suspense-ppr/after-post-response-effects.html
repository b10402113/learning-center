after()：副作用該不該擋住回應？

Step 4/4 · 串流、Suspense、PPR 與 after()

先做這個決定：使用者真的需要等嗎？

前三節處理的是畫面上看得到的資料，例如標題、內文、答案和投票狀態。這些內容如果還沒準備好，使用者就不知道頁面要做什麼，因此值得放在渲染路徑上。

但有些工作雖然重要，卻不會改變使用者眼前的畫面。最典型的例子就是瀏覽數加一：使用者點進文章時，通常先看到的是「上一次」的數字，而不是剛剛這次瀏覽立刻加總後的結果。

既然瀏覽數不會影響使用者當下的操作，為什麼要讓整頁渲染停下來等資料庫寫入？這一節要判斷的，就是副作用應該放在哪裡：留在回應之前，還是排到回應送出之後。after() 正是處理後者的工具。

學完後，你應該能判斷一個副作用該用 after()、直接 await、Promise.all，還是交給 client 端執行，並說明以 view counter 為例時，各種選擇的取捨。

四種放法，差別在於誰要等

同樣是「瀏覽數加一」，可以放在四個不同位置。把它們攤開比較，選擇就不再像猜謎：

做法放在哪裡使用者感受到的代價
client 端 useEffect畫面載入後由 client 呼叫 action內容先出現，但數字是舊的開發模式下會觸發兩次，還多兩趟 POST
server 直接 await渲染頁面時 await 計數能看到最新數字等待時間被加進整頁渲染
Promise.all與其他查詢平行送出時間縮成最慢那一項仍要等它完成才開始渲染
after()回應送出後才執行頁面最快出現，但數字稍後才更新數字不是即時的（類似 YouTube）

client 端用 useEffect 呼叫 action，優點是頁面不用等計數完成；缺點是使用者看到的永遠是上一筆瀏覽數，而且還要多發一次請求。開發模式下，StrictMode 甚至可能讓這個動作觸發兩次。

server 端直接 await 則把最新數字放在回應之前準備好。代價也很直接：整頁渲染會被這個計數動作拖住。

Promise.all 能處理另一種問題。如果計數和抓取頁面資料彼此沒有依賴，就可以平行送出，總時間從「兩者相加」縮短成「等待較慢的那一項」。不過，平行不代表不等待。所有 promise 都完成後，頁面才能繼續組裝，所以它解決的是「不該排隊卻排隊」，不是「這件事根本不該擋路」。

判別問句：這個副作用該不該擋路？

面對一個副作用，可以依序問自己三個問題：

  1. 它會改變使用者當下看到的畫面嗎？如果會，就不能任意延後，必須留在渲染路徑上；若它和其他查詢互不相依，可以考慮用 Promise.all 平行執行。
  2. 它需要修改這次的回應嗎？如果需要改 header、set cookie，或決定回傳哪些內容，就必須在回應完成前處理。after() 已經來不及介入。
  3. 使用者會根據它的結果做決定嗎？結帳金額、權限判斷等結果需要即時可用；瀏覽數、推薦模型的回饋和寫 log，通常不需要使用者等待。

以瀏覽數為例：它不會改變使用者當下看到的主要畫面，也不需要修改這次回應，使用者更不會盯著它來決定下一步。三個答案都指向同一處：把它交給 after()。

after()：回應送出後再做事

after() 從 next/server 匯入。它接受一個回呼，等這次回應或預渲染完成、內容已經送給使用者後，才執行回呼。

在 DevFlow 的問題詳情頁，原本需要 await 的計數工作可以改成：

after(async () => {
  await incrementViews({ questionId: id });
});

這段程式碼雖然寫在頁面程式裡，卻不代表它會先執行。它標記的是「回應完成後要做的事」。使用者先拿到頁面，這個回呼才開始處理，因此不會影響使用者感受到的回應時間。

after() 還能讀取這次回應的相關資訊，因此適合用來寫 log、送 analytics、做清理，或像這個例子一樣更新資料庫。不過要記住一個界線：它可以讀取回應，不能修改回應。內容既然已經送出去，就不能事後重寫。

它也不只適用於頁面渲染。after() 可以使用在 server component（包含 generateMetadata）、server action、route handler 和 middleware。只要 server 邏輯已經完成，而後續副作用可以晚一點處理，就有使用它的空間。

反例：什麼時候不該用 after()？

這套判準不是「只要是副作用就延後」。如果你很在意某個數字必須立刻正確，例如儀表板要即時反映操作次數，after() 的延遲就不符合需求。此時應該直接 await，或用其他方式降低等待感。

如果副作用的結果會決定這次回應要送出什麼內容，也不能延後。例如根據權限決定回傳哪些欄位，這件事本質上就是渲染的一部分。

另外，若資料庫寫入失敗時必須立刻通知使用者，也不適合使用 after()。因為回呼執行時，使用者早已拿到回應，你已經沒有正常的管道把失敗結果送回去。after() 比較適合「失敗了最多記一筆 log，不會中斷使用者任務」的工作。

最後的決策規則

把副作用放在哪裡，先看它是否該擋住回應。會改變當下畫面，或需要修改回應的工作，必須留在渲染路徑上；彼此獨立的請求可以用 Promise.all 平行化，但仍然要等它們完成；只有「不改變畫面、不修改回應、使用者也不需要等結果」的副作用，才適合交給 after()。以 view counter 為例：想讓頁面最快出現，選 after()；想要數字即時，直接 await；想要數字即時又減少排隊時間，則用 Promise.all。

這也串起了本節的三個重點：用 Suspense 切出慢的區塊，用 promise prop 與 use() 讓 client 接手等待，再用 after() 把看不到的副作用移出等待路徑。每次看到 AI 產出的程式碼，都可以先問一句：使用者到底需不需要等這一塊？答案會幫你決定，這段工作該留在回應之前，還是放到回應之後。
