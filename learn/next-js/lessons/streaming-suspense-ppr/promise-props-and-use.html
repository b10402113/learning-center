傳遞 promise：server 不 await，client 用 use() 解開

Step 3/4 · 串流、Suspense、PPR 與 after()

這一節要完成什麼？

你會把尚未 await 的 promise，從 server component 傳給 client component，再由 client 使用 React 19 的 use() 解開。完成後，頁面可以先顯示已經準備好的內容，較慢的資料則在 Suspense 的 fallback 後補上，而不必讓整個 server 渲染停在原地。

動手前，先確認你已經理解上一節的 Suspense 邊界：慢的子樹需要有一個可以暫時顯示 fallback 的位置。否則 promise 傳下去之後，畫面沒有地方接住等待狀態。

先看整體資料流

這個模式可以拆成四步：

  1. server 呼叫 server action，取得 promise，但不要 await。
  2. 把 promise 當成 prop 傳給 client component。
  3. 在 client component 的 props 型別中宣告這是一個 promise。
  4. 用 React 19 的 use() 解開 promise，讓元件取得結果。

可以把它想成把一張「取貨單」交給 client：server 先把取貨流程啟動，自己不用站在櫃台前乾等；client 拿到取貨單後，再在需要資料的地方讀取結果。等待期間，Suspense 負責顯示 fallback。

第一步：在 server 建立 promise，但不要 await

先看 server 端的寫法。在問題詳情頁裡，投票與收藏狀態各自透過 server action 取得。這裡只呼叫 action、接住它回傳的 promise，完全不使用 await：

const hasVotedPromise = hasVoted({
  targetId: question._id,
  targetType: "question",
});

const hasSavedQuestionPromise = hasSavedQuestion({
  questionId: question._id,
});

變數名稱刻意加上 Promise，因為它現在還不是投票結果，也不是最後的布林值。這兩行執行完時，請求才剛啟動，資料可能還在路上。

這裡最重要的效果是：promise 沒有被 await，就不會讓 server 渲染停下來等待它。頁面可以繼續處理標題、內文與標籤，先把已經能渲染的內容送出去。

壞寫法：讓整頁陪著慢

如果把程式改成下面這樣，語意看起來直接，卻會讓 server 停在這一行，直到投票狀態回來：

// 不要這樣：這裡的 await 會讓整頁卡住
const hasVoted = await hasVotedAction({
  targetId: question._id,
  targetType: "question",
});

正解：只讓慢的資料自己慢

前一段程式與這段程式的差別，幾乎只有一個 await，結果卻完全不同：

  • 使用 await：整頁要等投票狀態回來，才能繼續渲染。
  • 不使用 await：server 先啟動請求，頁面繼續渲染其他內容。

簡單說，一種寫法讓慢的部分自己慢；另一種寫法則讓全頁陪著慢。

第二步：把 promise 當 prop 傳下去

promise 接住之後，把它透過 props 傳給真正會使用資料的 client component。上一節的 Suspense 區塊中，hasVotedPromise={hasVotedPromise} 就是在做這件事。

這裡傳下去的不是解開後的結果，而是「尚未完成的 promise」。React 允許 server component 把這個 promise 傳遞給 client component，因此 server 不需要為了等結果而重新停住。

server 的工作到「把 promise 交出去」為止。接下來由 client 負責讀取結果；在結果尚未準備好時，Suspense 顯示 fallback。這就是整頁可以先往前走的原因。

第三步：在 client 宣告型別，並用 use() 解開

接著換到 client 端。接收 promise 的元件必須是 client component，檔案最上方會有 "use client"，例如 DevFlow 的 Votes.tsx。

先在 props 型別中，清楚標示這個欄位是一個 promise：

interface Params {
  targetType: "question" | "answer";
  targetId: string;
  upvotes: number;
  downvotes: number;
  hasVotedPromise: Promise<ActionResponse<HasVotedResponse>>;
}

這裡的 Promise<...> 表示：這個 prop 目前不是最後的資料，而是未來會產生 ActionResponse<HasVotedResponse> 的 promise。

型別準備好後，用 React 19 的 use() 讀取它：

const { success, data } = use(hasVotedPromise);

use() 不是一般意義上只能放在元件頂端的 hook。它是用來讀取資源的 API：傳入一個 promise，取得 promise 解開後的值。

這段程式執行後，data 裡就是 server 算好的投票狀態。元件可以根據它，決定箭頭是否顯示成已投票的樣式。

到這裡，完整資料流就接起來了：

  1. server 啟動 promise，但不等待。
  2. server 把 promise 當 prop 交給 client。
  3. client 用 use() 讀取 promise。
  4. 等待期間由 Suspense 顯示 fallback，完成後再顯示實際內容。

為什麼不用 useEffect？

看到「client 取得資料」，很容易立刻想到 useEffect 加 useState。但在這個場景中，use() 的位置不一樣。

常見想法：等 client 掛載後才請求

如果讓 client 在 useEffect 裡才呼叫 server action，請求要等到 client 掛載後才會啟動。這會多一個往返，也可能形成請求瀑布。

正解：server 先啟動，client 後讀取

現在的做法是 server 先啟動 promise，再把它交給 client。因此 client 不需要自己重新發出一次請求，能省掉一趟往返，也避開 useEffect 常見的請求瀑布。

另外，use() 能自然地和 Suspense 及 error boundary 配合：

  • promise 尚未完成時，交給 Suspense 顯示 fallback。
  • promise 解開失敗時，交給 error boundary 處理。

還要記住一件事：use() 不是「發起請求」，而是「讀取已經存在的資源」。這個資源可以是 promise，也可以是 context。這正是它適合「server 先啟動、client 後解開」模式的原因。

如果改成由 client 在 useEffect 中呼叫 server action，promise 就會等到 client 才啟動，server 提早開始處理、讓工作並行的優勢也就消失了。

第四步：投票之後，讓畫面即時更新

首次顯示正確只是第一關。使用者按下投票後，畫面也應該立刻反映新的狀態，而不是等重新整理才更新。

DevFlow 的做法是在投票的 server action 中呼叫 revalidatePath，重新驗證該問題頁面的資料。這樣頁面不用整頁重載，也能顯示更新後的狀態。

這和前面的「不 await」並不衝突：

  • 不使用 await，是為了讓首次渲染不要被慢資料卡住。
  • 使用 revalidatePath，是為了讓資料變更後的畫面保持正確。

小心欄位命名不一致

這個模式本身不複雜，但兩端的資料契約一定要對齊。DevFlow 整合時曾遇到一個很實際的錯誤：投票成功後畫面沒有即時更新，還出現「action type / action ID / author is required」。

原因是 server action 內部期待的欄位名稱是 actionId、actionType、author，但元件實際傳入的是 targetId、targetType。同一件事在兩端使用不同名稱，直到 runtime 才爆出錯誤。

因此，若遇到類似問題，請依條件檢查：

  • 若 server action 期待 actionId，client 就必須傳送同名欄位。
  • 若 server action 期待 actionType，不要只因為 client 端習慣而改成 targetType。
  • 若 server action 需要 author，請確認 client 傳入的資料中確實有這個欄位。

promise 傳遞與 use() 本身不難；真正容易出錯的地方，往往是 server 與 client 之間的欄位契約沒有對齊。

做完後，你應該能驗證什麼？

完成後，可以用以下結果檢查實作是否正確：

  1. server 端變數保留的是 promise，而不是使用 await 後的結果。
  2. promise 透過 props 傳給 client component。
  3. client component 的 props 型別寫成 Promise<...>。
  4. client 使用 use() 取得解開後的資料。
  5. promise 尚未完成時，Suspense 顯示 fallback，而不是讓整頁卡住。
  6. 投票後，revalidatePath 讓頁面在不整頁重載的情況下更新。
  7. server action 需要的欄位名稱，與 client 傳送的欄位名稱一致。
模式只有四步：server 呼叫 action 但不 await，把 promise 接住；把 promise 當 prop 傳給 client component；client 宣告 Promise<...> 型別；用 use() 解開。關鍵理由是 await 會阻塞 server 渲染，而不 await 的 promise 把等待移到 Suspense 邊界上。用 use() 而非 useEffect，還能省掉一趟往返、避免請求瀑布。

這一節處理的是「畫面上要顯示的資料」。但有些工作使用者根本看不到，卻也不該讓他等，例如增加瀏覽數、寫入 analytics，或記錄互動 log。下一節會以 view counter 為例，判斷這類副作用應該放在哪裡，以及 after() 什麼時候才是正解。
