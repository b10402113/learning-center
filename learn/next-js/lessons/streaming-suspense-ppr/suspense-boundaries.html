用 Suspense 切出可串流的邊界

Step 2/4 · 串流、Suspense、PPR 與 after()

先確認目標與前置條件

這一節要完成的事情很具體：找出頁面裡真正需要等待資料的區塊，用 Suspense 包住它，提供合適的 fallback，讓其他已經準備好的內容先顯示，慢的區塊再透過串流補上。

完成後，你也要能判斷兩種邊界該怎麼選：頁面只有一小塊比較慢時，使用行內 Suspense；整個 route segment 都要等待同一批資料時，使用檔案式的 loading.tsx。此外，你會看懂 PPR 裡的靜態外殼與動態洞，如何對應到頁面中的 Suspense 邊界。

開始前，先確認你知道兩件事：Suspense 會先顯示 fallback，等內容準備好後再替換；而慢的子樹通常是需要等待 async 資料的元件。如果這兩點還不熟，先回到上一節複習；本節會直接從找出慢的子樹開始。

整體流程：先找慢點，再切邊界

  1. 找出真正需要等待非同步結果的子樹。
  2. 用 Suspense 圈住這個子樹，並準備貼近版型的 fallback。
  3. 確認畫面與 HTML 是否真的分段到達。
  4. 依照等待範圍，選擇行內 Suspense 或 loading.tsx。
  5. 如果使用 PPR，讓這些邊界成為動態內容會被填入的洞。

第一步：找出真正慢的那一段

不要看到元件就一律包進 Suspense。切得太碎，畫面會像很多拼圖同時跳動，反而讓人難以掌握。先問一個問題：「這塊內容需要等待非同步結果嗎？」需要等待的區塊，才值得切出自己的邊界。

常見的慢子樹包括：

  • 要呼叫 server action 才知道結果的內容，例如「目前使用者投過票了嗎」。
  • 要等待外部 API 或資料庫查詢的內容，例如答案列表。
  • 要等權限判斷完成後才能顯示的內容。

AI 常犯版：看到元件就全部包起來

這種寫法沒有先分辨資料是否真的需要等待。結果是頁面被切成許多小塊，每一塊都可能顯示自己的載入狀態，畫面反而更凌亂。

正解版：沿著獨立資料來源切

如果元件只是把父層已經取得的資料重新排版，它本身不會變慢，包進 Suspense 只是多加一層沒有必要的 fallback。動手前，先列出這一頁有哪些區塊需要各自等待資料，再從這些區塊下刀。

第二步：用 Suspense 圈起慢子樹

找出慢子樹後，用 <Suspense> 包住它，並透過 fallback 指定內容尚未準備好時要先顯示的畫面。

在 DevFlow 的問題詳情頁中，Votes 需要先知道登入者目前的投票狀態，因此用下面的方式包起來：

<Suspense fallback={<div>Loading...</div>}>
  <Votes
    targetType="question"
    upvotes={question.upvotes}
    downvotes={question.downvotes}
    targetId={question._id}
    hasVotedPromise={hasVotedPromise}
  />
</Suspense>

這段程式碼可以拆成三個重點來讀。

  1. <Suspense> 圈住的是 Votes 這個慢子樹，而不是整個頁面。
  2. fallback 是內容尚未完成時的替代畫面。伺服器開始渲染時，它可以先被送到瀏覽器。
  3. hasVotedPromise 是一個尚未解開的 promise。當 Votes 等待它時，這個 Suspense 邊界就能先顯示 fallback，等結果準備好再把真正內容串流補上。

AI 常犯版：先在父層 await 完，再繼續渲染

直覺的寫法是先在頁面上 await 出投票狀態，再把結果傳給 Votes。看起來直接，卻會讓整個頁面卡在那一行 await：其他不需要投票狀態的內容，也得等結果回來才能繼續渲染。

正解版：把等待限制在需要它的邊界內

把慢的 Votes 放進 Suspense，資料還沒好時先顯示 fallback，頁面的其他部分則照常往下走。這就是 Suspense 的實際價值：不是讓資料變快，而是避免一小段慢資料拖住整個頁面。

第三步：確認畫面真的分段出現

包好之後，重新載入頁面，打開 DevTools 的 Network 面板，觀察 HTML 是否分段到達，而不是所有內容一次出現。

正常情況下，你應該先看到頁面的外殼與 fallback，慢的區塊稍後才被補上。如果畫面仍然卡住，直到資料回來後才整頁顯示，通常表示 await 還留在 Suspense 外面的父層。這是實作時最常見的錯誤之一。

AI 常犯版：fallback 放空白或不明轉圈

空白畫面無法告訴使用者發生了什麼；一個沒有對應內容的轉圈，也可能讓人不知道究竟是哪一區正在載入。

正解版：讓 fallback 接近最後的版型

fallback 的任務是告訴使用者「這裡正在準備中」。可以使用貼近最終版型的骨架，或簡短的載入文字。它不必非常精緻，但要讓使用者知道內容即將出現，也知道目前正在等待哪一區。

第四步：選擇行內 Suspense 或 loading.tsx

除了手動放置 <Suspense>，Next.js 也提供檔案式的載入邊界：只要在 route segment 底下放置 loading.tsx，框架就會自動把整個 segment 包進 Suspense，並把這個檔案當成 fallback。

選擇時，先看等待範圍。

情境 建議做法 特點
只有頁面中的一小塊需要等待 行內 Suspense 能精準包住慢區塊，也能同時存在多個彼此獨立的邊界。
整個頁面都要等待同一批資料 loading.tsx 程式碼較少，但會讓整個 segment 一起進入 fallback，範圍比較粗。

AI 常犯版：所有情況都只用 loading.tsx

loading.tsx 很方便，但它的範圍是整個 route segment。若其實只有投票區塊需要等待，卻讓整頁一起進入 fallback，就會失去其他內容可以先顯示的機會。

正解版：依等待範圍搭配使用

小範圍使用行內 Suspense，大範圍使用 loading.tsx。兩者也可以並存：先用 loading.tsx 作為整頁的第一層緩衝，再用行內 Suspense 把頁面內部的慢區塊繼續切細。

第五步：把邊界對應到 PPR 的動態洞

PPR 可以把整頁分成兩部分：先準備好的「靜態外殼」，以及等請求或資料到來後再填入的「動態洞」。這些洞的位置，正好對應到頁面中的 Suspense 邊界。

因此，這不是另一套完全不同的 API。你仍然是在判斷：「哪一塊需要等資料？」需要等待的區塊，外圍就是一個可能被串流補上的洞；其餘不變的部分則留在可以預先準備好的外殼裡。

AI 常犯版：邊界切得太粗或太細

邊界切得太粗，靜態外殼會很小，動態洞卻很大，PPR 能帶來的好處就會減少。切得太細，則可能讓畫面東一塊、西一塊地跳動。

正解版：跟著獨立資料切邊界

好的切法通常跟著「一份獨立的資料」走：需要單獨查詢一次的內容，就適合成為一個獨立的洞。這樣既能讓外殼先出現，也能讓各個慢區塊在準備好後各自補上。

完成後，你應該看到什麼？

重新載入頁面並觀察 Network 面板後，預期結果是：

  • 頁面的靜態外殼先出現。
  • 被 Suspense 包住的慢區塊先顯示 fallback。
  • 資料準備好後，慢區塊被串流補上並替換 fallback。
  • 不需要等待這份資料的其他內容，不會被同一個 await 拖住。
實作順序是：先找出真正需要等待資料的慢子樹，再用 <Suspense> 包起來並提供貼近版型的 fallback，最後透過瀏覽器工具確認 HTML 是否分段到達。範圍小就用行內 Suspense，範圍大就用 loading.tsx；而 PPR 的動態洞，正是這些 Suspense 邊界的位置。

邊界切好後，下一個問題就是：被 Suspense 等待的資料，該怎麼從 server 傳進 client？下一節會把「把尚未解開的 promise 當成 prop 傳入，再由 client 使用 use() 解開」這個手法拆到每一行。
