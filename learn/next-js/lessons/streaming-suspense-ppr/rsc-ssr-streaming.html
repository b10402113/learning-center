從整頁等待到串流：RSC、SSR 與 Suspense 的角色

Step 1/4 · 串流、Suspense、PPR 與 after()

學習目標

這一節會帶你看懂：傳統 SSR 為什麼常常要等整頁完成，串流與選擇性 hydration 如何讓畫面更早出現、更早互動，以及 Suspense 在串流與 PPR 中究竟負責哪一段工作。

先看整張地圖：為什麼一個慢區塊會拖住整頁？

想像你打開一個問題討論區的詳情頁。問題標題和內文早就從資料庫拿到了，但畫面還是白白的，一直轉圈。打開 DevTools 後才發現，右側的投票狀態正在等待登入 session，下面的答案列表還在查資料庫，側邊欄也正在計算統計資料。

這些區塊裡只要有一塊比較慢，整個頁面就可能陪它一起等。就算你已經知道怎麼在 RSC 裡抓資料，也避開了 waterfall 與 N+1，只要頁面上還有一個必須等待第三方 API 或權限判斷的區塊，傳統渲染方式仍然可能讓使用者先看到一片空白。

這一節要處理的問題很集中：當頁面只有部分區塊比較慢時，Next.js 能不能讓快的內容先出現，慢的內容稍後再補上？關鍵答案是串流（streaming）與 Suspense。更進一步的 PPR（Partial Prerendering，部分預渲染），則把這個想法推得更遠。

先分清楚三層：SSR、RSC 與 Suspense

這幾個名詞常常一起出現，很容易被混成同一件事。可以先把它們想成三個不同位置的角色：

概念 主要處理什麼 可以怎麼理解
RSC 在伺服器上抓資料、計算結果 負責準備元件內容，不會送到瀏覽器做 hydration
SSR 在伺服器上把元件渲染成 HTML 把畫面先做成瀏覽器看得懂的 HTML
Suspense 切出可能較慢的子樹 替慢區塊畫出邊界，先顯示 fallback，再補上真正內容

AI 常犯版會把 RSC 和 SSR 當成同義詞，好像只要「在伺服器渲染」就全都叫 SSR。正解版則要分開看：RSC 只在伺服器上執行，負責抓資料、計算結果，最後交給前端一段序列化的描述；SSR 則是在伺服器上產生 HTML，送到瀏覽器後還需要 hydration，才能接上事件與狀態。

Next.js 的價值，就是把這些階段接在一起：頁面可以先由 RSC 在伺服器上組合，再由 SSR 產生 HTML。接下來談串流時，焦點會放在「RSC 渲染出來的內容如何分段送到瀏覽器」；談選擇性 hydration 時，則是在看「HTML 到了瀏覽器後，React 如何分段接手」。兩者處理的是不同階段，但都能透過 Suspense 來切出界線。

傳統 SSR：最慢的區塊決定整頁速度

當瀏覽器送出請求，傳統的 server-side rendering（SSR）會在伺服器上渲染整個頁面，組出完整的 HTML 字串。在這份 HTML 完成以前，瀏覽器通常拿不到可顯示的完整內容。

等頁面送達後，瀏覽器才下載 JavaScript，接著開始 hydration（注水）：React 會把伺服器產生的靜態 HTML 接上事件與狀態，讓頁面真正能互動。

AI 常犯版會把這件事想成「伺服器只要先產生一點 HTML，瀏覽器就能自由使用整頁」。但傳統 SSR 的關鍵限制是：整份頁面往往要先準備好，瀏覽器才收到它。頁面中最慢的區塊等多久，整頁就可能跟著等多久。

這就像訂一桌合菜。廚房堅持所有菜都煮好才一起上桌，其中一道佛跳牆燉了三小時，其他已經炒好的菜也只能留在廚房裡慢慢變涼。正解版會改成「做好一道，就先端一道」：不必等最慢的那道菜，客人也能先吃到已完成的部分。

串流：做好一塊，就送一塊

串流的想法很直接：不要等整頁完成，而是邊渲染、邊把已完成的內容送出去。伺服器開始執行元件後，只要某個區塊準備好了，就先以 HTML 的形式串流給瀏覽器；還沒完成的區塊則先保留，完成後再補上。

這樣一來，使用者可以先看到問題標題、內文或其他已經準備好的內容，而不是只能盯著一整片空白。串流不是把慢區塊變快，而是避免慢區塊把所有內容綁在一起。

它對網路狀況也比較有韌性。可以把串流想成一條塞車的公路：道路沒有空間時，伺服器就暫停送出；等有空間了，再繼續傳送下一段。與其一次把所有內容硬塞出去，不如讓伺服器與瀏覽器按照彼此能處理的速度逐段傳遞。

選擇性 hydration：先到的區塊先互動

傳統 hydration 比較像是「整棵樹到齊後，從頭到尾一次注水」。如果頁面上有一個很大的元件，而它需要的 JavaScript 還沒下載完成，其他較小的元件也可能只能一起等待，整個頁面都還不能互動。

React 18 的選擇性 hydration（selective hydration）改變了這個規則。React 不必等所有內容都到齊，而是可以收到一塊，就先把那一塊 hydration 起來。哪個區塊先準備好，哪個區塊就能先開始互動。

AI 常犯版會把選擇性 hydration 說成「所有內容同時變成互動」。正解版是：不同區塊可以依照抵達與準備完成的時間分段接手。至於 React 如何知道哪些地方可能比較慢、可以先跳過？這就是 Suspense 負責標記的範圍。

Suspense：替慢區塊畫出邊界

Suspense 是一個 React 元件，用來替某個子樹畫出一條清楚的界線。當你知道某個元件可能需要等待，就可以用 Suspense 把它包起來，並提供一個 fallback：真正內容準備好以前，先顯示的替代畫面。

伺服器渲染時遇到 Suspense，會先把 fallback 放進 HTML 並送出，接著繼續處理其他部分。等慢元件完成後，真正內容再透過串流補上；前端則會用一段腳本，把畫面上的 fallback 換成正式內容。

AI 常犯版會把 Suspense 當成單純的載入動畫。正解版是：載入畫面只是 fallback 的一種呈現方式，Suspense 真正重要的工作，是把可能等待的子樹切出來，讓其他內容不必跟著一起停下來。

在 DevFlow 的問題詳情頁裡，投票元件需要先知道目前登入者是否投過票。這個判斷要呼叫 server action，因此可以把 Votes 放進 Suspense，並指定 Loading... 作為 fallback：

<Suspense fallback={<div>Loading...</div>}>
  <Votes
    targetType="question"
    upvotes={question.upvotes}
    downvotes={question.downvotes}
    targetId={question._id}
    hasVotedPromise={hasVotedPromise}
  />
</Suspense>

這段程式的邊界很清楚：問題的標題、內文、標籤等已經拿到資料的部分，可以先送出；投票狀態還沒準備好時，先顯示 fallback。使用者不必因為投票區塊還在等待，就連問題本身也看不到。

PPR：靜態外殼裡的動態缺口

如果說串流是「邊做邊送」，那麼 PPR（Partial Prerendering，部分預渲染）就是把頁面更細緻地拆開。整頁會被分成一個靜態外殼（static shell）與幾個動態的洞。

靜態外殼是不會隨請求變動的部分，可以在建置時先準備好，再直接從 CDN 送出。動態的洞則是用 Suspense 標記出來的區塊，等請求進來後，才由伺服器即時算好並串流填入。

AI 常犯版會把渲染策略想成二選一：整頁靜態，或整頁動態。正解版則是把界線畫在頁面內部：同一個頁面可以同時擁有靜態外殼與動態區塊，不必因為幾個區塊需要即時資料，就讓整頁每次請求都重新渲染。

當然，動態的洞要切在哪裡，取決於你把 Suspense 邊界放在哪裡。邊界放得好，快的內容就能先出現；邊界放得太大，可能又把不必等待的內容一起包住。這也是下一節要實際動手看的部分。

把這些概念接回同一條時間軸

傳統 SSR 是整頁生成完才送出，因此最慢的區塊會決定整頁的等待時間。串流讓伺服器做好一塊、送出一塊；選擇性 hydration 讓瀏覽器收到一塊、就能先接手一塊。Suspense 則是標記「這裡可能比較慢，先顯示 fallback」的邊界。PPR 再把這個想法往前推：先送出靜態外殼，再用 Suspense 串流填滿動態的洞。

現在可以把它們掛在同一條時間軸上理解：請求進來後，靜態外殼與已完成的內容先送出；可能較慢的區塊由 Suspense 標成缺口，先顯示 fallback；等資料與元件準備完成，正式內容再串流補上，前端也在適當時機接手互動。

所以，這些概念不是互相競爭的替代品。RSC 負責在伺服器準備內容，SSR 負責產生 HTML，串流負責分段傳送，選擇性 hydration 負責分段接手，而 Suspense 負責畫出「哪些地方可以先等」的界線。下一節會把這條關係變成實際的元件切分，觀察 fallback 何時出現，以及正式內容何時取代它。
