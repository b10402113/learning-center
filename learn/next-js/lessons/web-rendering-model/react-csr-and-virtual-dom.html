React 的 CSR：薄薄的 HTML 加一大包 JS

Step 2/5 · The Web-Rendering Model

學習目標

能解釋 React 為何只回傳最小 HTML 與打包後的 JS、客戶端渲染在做什麼、Virtual DOM diffing 的角色，以及 CSR 留下的複雜度、效能與 SEO 問題。

前言：換頁不再重新整理，但代價換到哪裡去了？

上一節看到傳統模型的麻煩：每換一頁，伺服器就重送完整檔案，而且從 HTML 到 CSS 到 JavaScript 全部要在瀏覽器裡重新跑一遍。既然瀏覽器已經下載過一次程式碼，為什麼換頁還要再來一趟？React 就是把這個流程反過來想。

它讓伺服器只送一份很薄的 HTML 殼，真正的畫面則交給一大包 JavaScript 在瀏覽器裡「當場畫出來」。這樣換頁不用重新整理，體驗像在用應用程式。但這種「客戶端渲染」也把工作、等待和一個新的風險，全都搬到了瀏覽器這一側。這一節要把這個模型拆開，看清它到底換到了什麼。

React 到底改了什麼

React 改善了開發流程，主要靠三樣東西：元件（components）、Virtual DOM（虛擬 DOM），以及 client 與 server 之間的分工機制。

當你造訪一個 React 網站，瀏覽器照樣先送請求給伺服器。但伺服器這次回的不再是完整的 HTML、CSS、JS，而是兩樣東西：一個最小的 HTML 檔，以及一個打包好的 JavaScript 檔。那個 HTML 檔的角色只是「整個應用程式的進入點」，本身幾乎沒有畫面內容。

<!DOCTYPE html>
<html>
  <body>
    <div id="root"></div>
    <script src="/bundle.js"></script>
  </body>
</html>

真正把畫面生出來的是那個 JavaScript 檔。它裡面裝著整個應用程式的程式碼，也就是所謂的 bundle（打包檔）。

客戶端渲染：畫面是在瀏覽器裡當場畫出來的

瀏覽器下載 JavaScript 之後，React 會用這包程式碼啟動「客戶端渲染」（client-side rendering，簡稱 CSR）。它並不是直接動手改真實的 DOM，而是先操作 Virtual DOM：先在這個輕量的虛擬版本上算出畫面該長什麼樣，再把新舊版本一比，只把真正有變動的部分套用到真實 DOM 上。

這個「先比對、再只改必要的部分」的過程叫 diffing（差異比對）。它的好處是：不必把整個畫面重畫一遍，只更新需要變的地方，效能比每次都大興土木來得好。

用生活譬喻：想像你要改家裡的裝潢。你不會每次都把整間房子拆掉重做，而是先在紙上畫出新的配置，比對哪裡真的不同，確定只有一面牆要動，才真的去敲那面牆。Virtual DOM 就是那張草稿紙，真實 DOM 才是你最後動工的地方。

換頁不重新整理：React Router 的角色

React 還有一個客戶端路由工具叫 React Router。它讓你在應用程式內部切換頁面時，不需要向伺服器送出完整的頁面請求，也就不會發生整頁重新載入。

當新的路由被觸發，React Router 會依照新的 URL 重新渲染對應的元件；如果這個新頁面需要從伺服器拿資料，則由對應的元件自己發請求去抓。對使用者來說，整個換頁過程就像在同一個應用程式裡切換畫面。

那代價是什麼？

React 這條路換來了流暢的換頁體驗，但也留下三個成本。

成本一：複雜度變高

做一個 React 應用，會比傳統的 HTML、CSS、JavaScript 網站複雜。你得學會用「元件」的方式思考，還要管理 state（狀態）和 props（屬性），並理解 Virtual DOM 的運作。對剛接觸 React 的開發者來說，這是一段學習曲線。

成本二：主要還是靠客戶端渲染，慢裝置會延遲

跟傳統做法類似，React 主要還是客戶端渲染。首次渲染與後續更新都高度依賴 JavaScript，而且全都在瀏覽器上處理。當使用者的處理器較慢、裝置資源有限時，這份依賴就會拖慢畫面的出現與可互動的時間。

成本三：SEO 有風險

搜尋引擎的爬蟲可能無法完整取得網站內容，因為一切都靠 JavaScript、而且只在客戶端渲染。爬蟲抓不到內容，自然就影響網站在搜尋結果裡的曝光。

一張表看懂 CSR

面向React 的客戶端渲染
伺服器回傳最小 HTML 殼 ＋ 一包打包 JS
誰把畫面畫出來瀏覽器執行 JavaScript 後才畫

換頁React Router 前端切換，不重新整理
首頁載入要等 JavaScript 下載並執行完
SEO爬蟲可能抓不到 JS 渲染的內容

小結

React 把渲染工作搬到瀏覽器：伺服器只回一個最小 HTML 殼和一大包 JavaScript，由 React 在客戶端渲染（CSR），透過 Virtual DOM 的 diffing 只更新有變動的部分，再用 React Router 做到不重新整理的換頁。換來的是流暢體驗，代價是更高的複雜度、對 JavaScript 與裝置效能的依賴，以及爬蟲可能抓不到內容的 SEO 風險。

看到這裡會發現，傳統模型和 React 各有一半的缺點：一個是「伺服器全部送、瀏覽器全部重做」，一個是「瀏覽器全部自己畫、首頁載入和 SEO 吃虧」。那有沒有一種做法，能讓伺服器先幫你畫好畫面，瀏覽器一收到就能顯示，之後再默默把互動接上去？這就是 Next.js 的答案，下一節來看。
