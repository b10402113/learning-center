Next.js 的 SSR：先畫出來，再 hydration 接上互動

Step 3/5 · The Web-Rendering Model

學習目標

能分兩段說明 Next.js 的伺服器渲染流程：伺服器執行 React 元件回傳已渲染 HTML，客戶端先畫出畫面，接著 hydration 把事件處理接上去。

前言：能不能「畫面先到、互動後補」？

前一節把兩條路都走過一遍：傳統模型是伺服器把完整檔案送過來、瀏覽器自己組裝，React 則是把畫面全部交給瀏覽器當場畫。兩者各有一半的遺憾：前者要等檔案到齊，後者要等 JavaScript 執行，而且搜尋引擎還可能看不懂。

於是問題變成：能不能讓伺服器先把畫面畫好、讓瀏覽器一收到就顯示，但同時保留 React 那種流暢的互動？Next.js 的做法正是把兩者接起來。它先用伺服器把 HTML 生出來，等 JavaScript 到了，再把互動「接」上去。這個「先畫出來、再補互動」的兩段式流程，就是這一節的主角。

先講結論：渲染地點可以自己選

在了解兩者的優點與限制之後，Vercel 的開發者讓使用 Next.js 的人可以自己選擇：內容要在 client 還是 server 上渲染。這個「可以選」是 Next.js 的核心特色，也是它被形容為「兩者混合」的原因。

先看最典型的情況：使用者第一次造訪一個 Next.js 網站。

第一段：伺服器先把 HTML 畫好

使用者造訪時，client 一樣先送請求到伺服器。差別在於，伺服器這次不是回一個空殼，而是開始執行 React 元件。它會產生 HTML、CSS、JavaScript 檔，並把已經渲染完成的 HTML 當作回應送回 client。

這份 HTML 裡裝了什麼？它包含初始內容、已經抓好的資料，以及 React 元件的 markup（標記結構）。因為畫面內容已經在裡面了，client 收到就能立刻把它畫出來，不必等 JavaScript 下載並執行完。這就是為什麼 Next.js 網站的首頁通常能很快顯示內容。

這種「由伺服器先渲染出完整 HTML 再回傳」的流程，就是 SSR（server-side rendering，伺服器端渲染）。

第二段：JavaScript 到了，用 hydration 接上互動

畫面先出現，不代表 JavaScript 就不送了。伺服器還是會依使用者互動的需要，把 JavaScript 程式碼送過來。等這些 JavaScript 到位，Next.js 就接手做客戶端的 hydration。

hydration（補水／注入互動）的意思是：把 JavaScript 的事件處理與互動能力，接到那些已經預先渲染好的 HTML 上。你可以把它想成分成兩段交屋：伺服器先送來一間「長得完全正確」的房子（HTML，你眼睛看得到、也能先住），工程師（JavaScript）之後才到場，把可動的抽屜、開關、電燈開關一一裝上，讓這間房子真的能「用」。

所以 hydration 是讓畫面從「看得到」變成「可以操作」的關鍵一步。在 JavaScript 到位、hydration 完成之前，你看到的內容是死的，長得像最終畫面，但點了沒反應。

三個階段一次看

階段誰在做發生了什麼
1. 請求Client → Server瀏覽器送出請求，伺服器開始執行 React 元件
2. 回傳Server回傳完整的 HTML（含內容、資料、元件 markup）
3. 畫出Client立刻顯示畫面，不必等 JavaScript
4. 互動Client（hydration）JavaScript 到位後，把事件處理接到 HTML 上

至於後續的請求，Next.js 讓你對「頁面內容要在 server 或 client 渲染」有完整的控制權。第一次造訪走的是 SSR，之後則可以依需求選擇在伺服器或瀏覽器渲染。

小結

Next.js 把兩種模型接起來：第一次造訪時伺服器先執行 React 元件，回傳已經渲染好的完整 HTML，讓瀏覽器立刻顯示內容（這就是 SSR）。JavaScript 之後才依互動需求送達，由 hydration 把事件處理與互動接回這份 HTML。畫面先到、互動後補，是這個模型最大的特徵。

不過這個「先畫好、再接上」的設計有一個隱含前提：伺服器畫出來的東西，和瀏覽器第一次畫出來的東西，必須對得起來。如果兩邊畫得不一樣，hydration 就會出錯。下一節專門來看這個常見的坑：hydration mismatch。
