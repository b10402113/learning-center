傳統模型：伺服器送檔、瀏覽器幹活

Step 1/5 · The Web-Rendering Model

學習目標

能說出傳統 HTML/CSS/JS 模型一次請求的往返流程，以及它在處理、頻寬、載入時間上的三個代價。

前言：你在網址列按下 Enter 之後，發生了什麼？

想像你在瀏覽器輸入一個網址、按下 Enter，畫面先是空的，過一下才長出文字和圖片。對你來說只是「等了一下」，但在這短短幾百毫秒裡，其實有一整套分工正在跑：你的瀏覽器向某台電腦要東西，那台電腦把檔案送回來，你的瀏覽器再把這些檔案變成你看得見的畫面。

要聽懂後面 React 和 Next.js 在改什麼，得先弄清楚這個最原始的版本怎麼運作。因為後面每一種做法，其實都在回答同一個問題：這些工作，到底該由誰來做？這一節先把「傳統模型」拆開，看清它的流程，還有它三個躲不掉的代價。

一次請求，一趟來回

傳統網站是用 HTML、CSS、JavaScript 這三個 web 的基本元素做出來的。它的運作方式，跟後來的新技術很不一樣。

當你造訪這種網站，瀏覽器（也就是 client，客戶端）會送出一份「請求」（request）到伺服器（server）。伺服器是另一台電腦，網站檔案就放在那裡，而這份請求要的是「請把我要看的內容給我」。

依照傳統做法，伺服器收到請求後會回傳三個檔案：HTML、CSS、JavaScript（只有當這個頁面需要 JavaScript 時才送）。瀏覽器收到之後，會照固定順序處理：

  1. 先解析 HTML 檔，把頁面的骨架讀出來。
  2. 再套用 CSS 檔的樣式，讓頁面長得好看。
  3. 最後執行 JavaScript 檔，把需要互動的部分（例如點了按鈕要做什麼）裝上去。

如果網站有很多頁，那每換一頁，瀏覽器就要再送一次請求，伺服器也要再回一次那三個檔案。換句話說，每一個頁面都是獨立的一趟來回。

三個躲不掉的代價

這個做法直覺、簡單，但代價也很明確，可以拆成三件事：處理、頻寬、載入時間。

代價一：大部分的活都壓在瀏覽器身上

頁面要怎麼畫、JavaScript 要不要跑，主要都是 client 端的工作，也就是你手上這台裝置的瀏覽器在負責。如果網站很複雜，而使用者的裝置效能又沒那麼好，瀏覽器就會被操得很吃力，甚至超出它能負荷的範圍。

代價二：每一頁都送完整檔案，頻寬用量大

因為每個頁面請求，伺服器都送完整檔案，整體的頻寬用量就會被拉高。當網站頁數多、又散落著影片和音訊時，這個問題特別明顯，同樣的共用資源可能被重複傳送。

代價三：要等全部檔案到齊才看得到畫面

首頁載入的時間也比新技術來得長。原因是伺服器必須把所有需要的檔案都送完，瀏覽器也必須全部解析完，你才看得到網站內容。在那之前，畫面就是空的。

用生活一點的說法：這像是你去圖書館查資料，每翻一本書都得重新跑一趟櫃檯借還；書越多、每本越厚，等待的時間就越長。

一張表看懂傳統模型

面向傳統 HTML/CSS/JS 模型
送出請求每換一頁就送一次 request
回傳內容每個請求回傳完整的 HTML、CSS、JS
誰負責渲染瀏覽器（client）
頻寬每頁重送完整檔案，用量大
首頁載入速度要等全部檔案送達並解析完
適合情境頁面少、互動單純的網站

小結

傳統模型的分工是「伺服器送檔、瀏覽器幹活」：瀏覽器送出請求，伺服器回傳完整的 HTML、CSS、JS，瀏覽器再自己解析、套樣式、跑互動。好處是單純，代價是工作多壓在客戶端、每頁重送完整檔案讓頻寬吃緊，而且必須等檔案全部到齊才看得到內容。

既然「每頁重送、全部自己畫」這麼累，有沒有一種做法能讓瀏覽器只下載一次、之後換頁也不必再向伺服器要整份檔案？React 就是往這個方向走的。下一節看它怎麼用「薄薄的 HTML 加一大包 JavaScript」改寫這個流程。
