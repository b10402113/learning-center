Server Components 的誕生：React 為什麼往伺服器走

Step 5/5 · The Web-Rendering Model

學習目標

能說出 React Server Components 的動機與時間線：React 原本只活在瀏覽器、Instagram 撞上 bundle 極限、2020 年 React 團隊提出 RSC、Next.js 於 2022 導入並在 Next.js 13 的 App Router 中把它變成預設。

前言：這不只是 Next.js 的花招，而是整個生態的轉向

前幾節我們看的是「技術怎麼運作」：伺服器先渲染 HTML、瀏覽器再 hydration。但如果把鏡頭拉遠一點，會發現這背後其實是一個更大的轉向：React 這個原本「完全活在瀏覽器裡」的框架，開始把工作往伺服器搬。

為什麼要搬？不是因為誰覺得新潮，而是因為有一家大公司在真實產品上撞到了牆。看懂這段歷史，你才會知道 Server Components 不是突然冒出來的名詞，而是為了解決一個具體到不能再具體的問題。這一節就把這條故事線講完，也順便釐清一個很多人搞混的地方。

一開始，React 只活在瀏覽器裡

React 的起點很簡單也很強大：用元件來打造使用者介面，而這些元件「活在瀏覽器裡」。每一個 React 應用都遵循同一套模式：

  1. 首次載入時，下載一整包 JavaScript（bundle）。
  2. React 在瀏覽器裡啟動自己。
  3. 元件渲染出來，並且變得可以互動。
  4. 之後所有的使用者互動，都在本地（瀏覽器）處理。

換句話說，整個應用程式會被下載成一包 JavaScript 送到瀏覽器。作者用了一個很傳神的比喻：這就像把一整盒樂高，一次全部倒在你桌上。

轉折點：Instagram 撞上了 JavaScript 的天花板

事情在 Meta 自家團隊開發 Instagram 網頁版時出現變化。他們發現自己送給使用者瀏覽器的 JavaScript 量越來越大，而這不只是個技術問題，它直接影響使用體驗，尤其在網路較慢、或裝置效能較弱的地區更是明顯。

當時的做法把太多東西都塞進瀏覽器：應用程式的邏輯、資料處理、畫面渲染，全部都得先下載、再執行。當這包越長越大，使用者就得先等更久，才看得到、才用得到。

Server Components：讓元件可以在伺服器上跑

於是有了 Server Components。它代表 React 應用運作方式的根本轉變：元件不再只能在瀏覽器裡跑，而是可以在伺服器上執行，只把必要的 HTML 送到使用者手上。這已經不只是最佳化，而是對 React 架構的一次重新思考。

這裡要澄清一個很常見的誤會：很多開發者以為 Server Components 是 Next.js 的功能。這並不正確。React Server Components（RSC）是 React 的核心功能，只是 Next.js 把它實作得特別好，才讓大家誤以為那是 Next.js 的東西。

2020 年 12 月：React 團隊提出 RSC

React 團隊在這時提出了一個新概念：React Server Components。Dan Abramov 與 Lauren Tan 透過一場名為「Data Fetching with React Server Components」的演講介紹它。

它的核心概念是：元件可以被拆成client components 與server components，兩者在同一個應用裡各司其職。Server Components 負責應用中資料密集、但不需要互動的部分；只有真正需要互動的元素，才交給 client components。這樣一來，React 應用會更像傳統的伺服器渲染網站，同時又保留 React 動態 UI 的好處。

2022 年：Next.js 把它帶進主流

當 React 社群還在實驗 Server Components 時，像 Next.js 這樣的框架創作者率先把它實作進既有的工具鏈。到了 2022 年中，Next.js 整合了早期的 RSC 支援，讓開發者可以在真實專案裡試用，同時 React 也持續調整 API。

2022 年底，Next.js 13 推出，帶來了 App Router：一套對「React 應用該怎麼蓋」的完整重新想像。而 Next.js 13 做了一個很大膽的決定：把 Server Components 變成預設。這個決定把整個生態翻了過來。

一條時間線看懂整件事

時間事件
React 初期元件只活在瀏覽器，整個應用打包成一包 JS 下載

2022 年 中Next.js 導入早期 RSC 支援，讓開發者實測試用

弄懂 RSC，別和 SSR 混在一起

看到這裡，很容易把 Server Components 和前一節的 SSR 當成同一件事。它們確實常常一起出現，但講的是不同的層次：SSR 談的是「伺服器先把 HTML 渲染好、再回傳」；RSC 談的是「元件本身可以在伺服器上執行」。一個是渲染的時機，一個是元件執行的位置。把這個區別記牢，你才不會在讀架構時把兩件事糊在一起。

這股轉向帶來的效果很實際。對小團隊來說，Server Components 讓應用更有效率，也因為送給瀏覽器的 JavaScript 變少而省下主機成本。對想在競爭市場裡被看見的獨立開發者來說，Next.js 讓他們能做出又快、對 SEO 又友善的網站，不必再處理一堆複雜的設定。也難怪 Next.js 會變成「現代 React 開發」的代名詞。

小結

React 原本只活在瀏覽器，整個應用被打包成一大包 JavaScript 下載。Meta 開發 Instagram 網頁版時撞上這個模式的極限，催生了 Server Components：讓元件可以在伺服器上執行，只把必要的 HTML 送到使用者。2020 年 12 月 React 團隊提出 RSC，2022 年中 Next.js 導入，2022 年底 Next.js 13 的 App Router 更把它設為預設。要注意的是，RSC 是「元件在哪執行」，和 SSR 的「何時渲染 HTML」是不同層次的事。

走完這一節，你手上就有完整的渲染地圖：從伺服器送檔的年代，到瀏覽器自己畫，再到伺服器先畫、hydration 後補，最後是元件本身往伺服器移動。下一步就是把這張地圖收窄到元件層級：哪些元件該留在伺服器、哪些該送到瀏覽器，以及那條 `"use client"` 邊界怎麼畫。下一節見。
