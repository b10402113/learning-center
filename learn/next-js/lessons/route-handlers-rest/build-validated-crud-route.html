一步步建出經過驗證的 CRUD route

Step 4/5 · Route Handlers 與 REST API 設計

先確認目標與前置條件

這一節要實作的是一組真正能工作的 users API：讀取使用者清單、建立新使用者、操作單筆使用者，並在資料寫入前完成輸入驗證與重複檢查。做完後，你會知道每一段 route handler 在做什麼，也能看出一個「看似能跑」的寫法，和一個比較可靠的正解差在哪裡。

動手前，你應該已經能用資料夾與 route.ts 建出固定端點（step 1）、用 [id] 讀取路徑參數（step 2），也知道狀態碼和 response 信封的基本形狀（step 3）。

本節的程式碼來自 DevFlow 的 app/api/users/route.ts。我們會先看整體骨架，再依序拆解 GET、POST、錯誤處理，以及單筆資源的 CRUD 寫法。

第一步：先看完整骨架

先不要急著鑽進某一行。整個 route handler 可以先看成一條固定流水線：連線資料庫、讀取或驗證資料、執行查詢，最後回傳一致的 JSON；只要中途出錯，就交給同一個錯誤處理器。

這個檔案匯出兩個函式：GET 與 POST。兩者都包在 try / catch 裡。

import { NextResponse } from "next/server";

import User from "@/database/user.model";
import handleError from "@/lib/handlers/error";
import { ValidationError } from "@/lib/http-errors";
import dbConnect from "@/lib/mongoose";
import { UserSchema } from "@/lib/validations";

export async function GET() {
  try {
    await dbConnect();

    const users = await User.find();

    return NextResponse.json({ success: true, data: users }, { status: 200 });
  } catch (error) {
    return handleError(error, "api") as APIErrorResponse;
  }
}

export async function POST(request: Request) {
  try {
    await dbConnect();
    const body = await request.json();

    const validatedData = UserSchema.safeParse(body);

    if (!validatedData.success) {
      throw new ValidationError(validatedData.error.flatten().fieldErrors);
    }

    const { email, username } = validatedData.data;

    const existingUser = await User.findOne({ email });
    if (existingUser) throw new Error("User already exists");

    const existingUsername = await User.findOne({ username });
    if (existingUsername) throw new Error("Username already exists");

    const newUser = await User.create(validatedData.data);

    return NextResponse.json({ success: true, data: newUser }, { status: 201 });
  } catch (error) {
    return handleError(error, "api") as APIErrorResponse;
  }
}

先從 import 讀出這個端點的分工：

  • User 是資料庫模型，負責查詢與寫入使用者。
  • dbConnect 負責建立資料庫連線。
  • UserSchema 是 Zod 驗證 schema，用來檢查輸入資料。
  • ValidationError 是自訂錯誤類別，專門表達驗證失敗。
  • handleError 是集中式錯誤處理器。
  • NextResponse 負責組出 HTTP response。

把這些角色先攤開來，後面每一段程式碼就不會像一堆互不相干的零件。

第二步：完成 GET——連線、查詢、回傳信封

GET 是最短的一條路徑。它的核心只有三個動作：確認資料庫可用、取得所有使用者、回傳結果。

await dbConnect();

const users = await User.find();

return NextResponse.json({ success: true, data: users }, { status: 200 });

第一行 await dbConnect() 先確保資料庫連線已經就緒。實務上，dbConnect 內部會快取連線，因此每次請求都呼叫它，不代表每次都會重新建立連線。

第二行 User.find() 取出所有使用者，並把查詢結果放進 users。第三行則用 NextResponse.json 回傳固定形狀的 response：

  • success: true 表示請求成功。
  • data: users 放入使用者清單。
  • status: 200 表示成功取得資料。

預期看到的結果，是一個 JSON 陣列放在 data 裡。

AI 常犯版：查詢成功時直接回傳陣列，查詢失敗時每個 route 各自組一種錯誤格式。這樣短期看起來省事，前端卻得猜每個端點的 response 長什麼樣子。

正解版：成功回應統一包成 { success: true, data: ... }；查詢過程發生例外，就讓 catch 交給同一個 handleError 處理。

如果查詢途中丟出例外，程式不會繼續往下執行，而是跳到這段：

} catch (error) {
  return handleError(error, "api") as APIErrorResponse;
}

這裡的 as APIErrorResponse 是型別斷言，讓回傳值符合這個 route handler 預期的回傳型別。

第三步：完成 POST——先驗證，再查重，最後寫入

POST 的順序很重要。可以把它想成資料進入資料庫前的三道門：先檢查格式，再檢查是否撞名，最後才允許寫入。不要把建立資料放在驗證前面，否則錯誤資料可能已經進入資料庫。

3.1 讀取 body 並用 Zod 驗證

const body = await request.json();

const validatedData = UserSchema.safeParse(body);

if (!validatedData.success) {
  throw new ValidationError(validatedData.error.flatten().fieldErrors);
}

第一行把 request body 解析成 JavaScript 物件。接著用 UserSchema.safeParse(body) 檢查資料是否符合 schema。

這裡特別使用 safeParse，而不是 parse。parse 驗證失敗時會直接丟出例外；safeParse 則會回傳一個物件，讓你自行檢查 success。這樣就能把 Zod 的錯誤整理成自訂的 ValidationError。

validatedData.error.flatten().fieldErrors 會把錯誤依欄位分組，例如：

{ email: ["Invalid email address"] }

接著，handleError 就能把這些欄位錯誤轉成一致的 400 response。

AI 常犯版：收到 body 後直接把 body 傳給 User.create，希望資料庫替自己檢查格式。

正解版：先用 UserSchema.safeParse 驗證；驗證失敗就丟出 ValidationError，讓錯誤處理器回傳使用者看得懂、而且能對應到欄位的訊息。

3.2 檢查 email 與 username 是否重複

只有驗證通過，程式才會往下解構需要檢查的欄位：

const { email, username } = validatedData.data;

const existingUser = await User.findOne({ email });
if (existingUser) throw new Error("User already exists");

const existingUsername = await User.findOne({ username });
if (existingUsername) throw new Error("Username already exists");

這裡先查 email，再查 username。如果其中一個已經被使用，就停止流程，不進行建立。

這種「先查再寫入」的做法，能在可預期的情況下先擋住重複資料，並提供比較容易理解的錯誤訊息。代價是多了兩次查詢，但這是常見的取捨：用額外查詢換取更清楚的錯誤。

要注意，這段範例使用的是一般的 Error。因此它進入 handleError 後，會被當成一般錯誤處理，回傳 500。如果希望 email 或 username 重複時回傳 403 或 409，就應該改用能表達衝突的自訂錯誤類別，而不是直接使用裸的 Error。

3.3 只寫入已驗證的資料

所有檢查都通過後，才真正建立使用者：

const newUser = await User.create(validatedData.data);

return NextResponse.json({ success: true, data: newUser }, { status: 201 });

這裡傳給 User.create 的是 validatedData.data，不是原始的 body。這個差別很重要：資料已經通過 schema 驗證，才會進入資料庫；body 裡額外夾帶、但 schema 沒有定義的欄位，也不會直接被當成可信資料寫入。

建立成功時回傳 201 Created。response 信封和 GET 相同，只是 data 改成新建立的那一筆使用者。

第四步：讓所有錯誤走同一個出口

GET 和 POST 的 catch 完全相同：

} catch (error) {
  return handleError(error, "api") as APIErrorResponse;
}

handleError 收到錯誤和 "api"。這個字串表示目前要組的是 HTTP response，而不是給 server action 使用的物件。

錯誤處理器會依錯誤型別決定回應方式：

  • 如果是自訂的 RequestError，例如 ValidationError，就使用它提供的 statusCode 與錯誤訊息。
  • 如果只是一般的 Error，就回傳 500。

這樣每個 route 不需要各自重複撰寫錯誤 response，也能讓前端面對一致的錯誤形狀。

AI 常犯版：每個錯誤分支直接在 route 裡組 response，結果驗證錯誤、查不到資料、資料庫錯誤各自長得不一樣。

正解版：route 專心處理成功流程；只要發生例外，就交給集中式的 handleError。route handler 像把所有壞球丟進同一個收球袋，錯誤格式由一個地方統一管理。

第五步：處理單筆資源的 CRUD

清單端點之外，還需要讀取、更新和刪除單一使用者。這時使用 step 2 的動態 segment，檔案放在 app/api/users/[id]/route.ts。

5.1 讀取單筆使用者

export async function GET(
  _: Request,
  { params }: { params: Promise<{ id: string }> }
) {
  const { id } = await params;
  if (!id) throw new NotFoundError("User");

  try {
    await dbConnect();

    const user = await User.findById(id);
    if (!user) throw new NotFoundError("User");

    return NextResponse.json({ success: true, data: user }, { status: 200 });
  } catch (error) {
    return handleError(error, "api") as APIErrorResponse;
  }
}

這段和清單端點的形狀相同，只多了兩個步驟：

  1. 先 await params，取得路徑中的 id。
  2. 用 User.findById(id) 查詢；如果找不到，就丟出 NotFoundError。

因此，GET /api/users/[id] 成功時回傳單筆使用者，查不到時則由集中錯誤處理器回傳 404。

5.2 更新部分欄位

更新資料時，使用者通常只會送出想修改的欄位，例如只改 bio。這時不能要求整份使用者資料都重新提交，因此要使用 UserSchema.partial()：

const body = await request.json();
const validatedData = UserSchema.partial().parse(body);

const updatedUser = await User.findByIdAndUpdate(id, validatedData, {
  new: true,
});

.partial() 會把 schema 中的欄位全部變成可選。完整的 UserSchema 適合建立新使用者，但如果更新時只送出部分欄位，使用完整 schema 會因為缺少其他必填欄位而失敗。

findByIdAndUpdate 的第二個參數是要更新的資料。選項中的 { new: true } 則要求 Mongoose 回傳更新後的新版本；少了這個選項，拿到的可能是更新前的舊資料。

AI 常犯版：更新時沿用建立資料的完整 schema，要求 request body 帶齊所有欄位。

正解版：若是部分更新，就用 UserSchema.partial() 驗證部分資料，並在 findByIdAndUpdate 加上 { new: true }，確保回傳的是最新內容。

刪除則遵循同一套結構，使用 DELETE 搭配 findByIdAndDelete。無論是讀取、更新或刪除，都應該先取得並確認 id，再把例外交給同一個錯誤處理器。

做完之後，結果應該長這樣

完成後，你會得到一組形狀一致的小型 REST API：

  • GET /api/users → 回傳使用者陣列，狀態碼為 200。
  • POST /api/users → 合法輸入時回傳新使用者與 201；欄位錯誤時回傳 400 與逐欄位訊息；email 或 username 重複時丟出錯誤。
  • GET /api/users/[id] → 找到時以 200 回傳單筆使用者；查不到時回傳 404。
  • DELETE /api/users/[id] → 刪除使用者，並回傳被刪除的資料。
  • PUT /api/users/[id] → 使用 partial 驗證後，更新部分欄位。

你可以用瀏覽器或 Postman 呼叫這些端點，確認成功和失敗時的狀態碼、response 信封與錯誤訊息。這一節的重點，是把 route handler 的手法做出來；狀態碼為什麼要分成 200、201、400，以及為什麼要集中錯誤處理，已經在 step 3 說明過。

小結

一個標準的 CRUD route handler，可以依照固定順序實作：先在 try 裡呼叫 dbConnect；POST 讀取 body 後，用 Zod 的 safeParse 驗證，失敗就丟出 ValidationError；接著檢查唯一性，最後才呼叫 create 並回傳 201。所有例外都交給 handleError，讓錯誤形狀保持一致。單筆資源放在 [id]/route.ts，更新時使用 UserSchema.partial()，而 findByIdAndUpdate 要帶上 { new: true }，才能取得更新後的資料。

你現在已經能做出對外提供服務的 REST 端點。不過，並不是每個寫入操作都值得做成 API route；如果只有自家 UI 會使用，Next.js 還有更輕量的選項：server action。下一篇會用可測試的判準，幫你判斷什麼時候該用 route，什麼時候該用 server action。
