要端點還是要 action？Route Handler vs. Server Action 怎麼選

Step 5/5 · Route Handlers 與 REST API 設計

先看全局：同樣是寫入，為什麼有兩條路？

前四步你已經能做出完整、帶驗證的 REST 端點。但當你打開一個真實的 Next.js 專案，可能會發現：很多寫入功能根本沒有對應的 route.ts。它們是標上 "use server" 的函式，也就是 server action，直接從表單或元件呼叫。

於是，當你要做「建立一篇文章」時，就會遇到一個實際的選擇：要寫一個 route.ts 端點，還是寫一個 server action？兩種做法都能把資料寫進資料庫，但它們面對的使用情境不同。

這一節不教你怎麼實作 server action，那是下一個 node 的內容。我們先建立一把判斷用的尺，知道什麼時候需要對外的 HTTP 端點，什麼時候只要一個自家 app 內部使用的伺服器函式。

學習目標

學完後，你可以用「這個介面需要對外暴露嗎？」、「有沒有外部呼叫者？」等可測試的判準，決定一個查詢或寫入該使用 route handler，還是 server action。

核心抉擇：對外暴露，還是少一點儀式？

Route handler 和 server action 的差異，可以先濃縮成一句話：route handler 是對外的 HTTP 端點；server action 是只有自家 app 能呼叫的伺服器函式。

Route handler 走標準 HTTP。只要能發出 HTTP 請求的工具都能呼叫它，包括瀏覽器、fetch、手機 App、第三方服務、Postman 和 curl。代價是你需要自己處理路徑、HTTP 方法、狀態碼、驗證，以及錯誤回應的格式。

Server action 則把這些儀式收起來。當 client 端呼叫它時，Next.js 會在背後把呼叫轉成 POST 請求，送到伺服器執行。你不用自己定義路由，也不用自己組裝 HTTP 回應。

這讓 server action 寫起來很輕，也因為沒有公開的對外介面，暴露面比較小。但另一面是，外部系統無法像呼叫一般 API 那樣使用它，也很難直接用 Postman 測試。

選項比較：兩條路各自付出什麼代價？

面向Route HandlerServer Action
對外是否暴露是，標準 HTTP 端點否，入口不公開
誰能呼叫任何 HTTP 客戶端只有自家 Next.js app
HTTP 方法GET / POST / PUT / DELETE 都有語意一律轉成 POST
用 Postman 測可以，直接打端點很難，沒有公開入口
接收 webhook可以不支援（需要持續監聽的場景）
寫入的儀式感較多：路徑、方法、狀態碼較少：一個 async 函式

先從外觀感受兩者的差異。Route handler 是你前幾步做過的形式：建立檔案、匯出對應的 HTTP 方法函式，再回傳帶有狀態碼的回應。

Server action 則是一個標上 "use server" 的 async 函式：

// server action：一個檔案，一個 async 函式
"use server";

export async function createQuestion(data: CreateQuestionParams) {
  // 驗證、授權、寫入資料庫
  return { success: true };
}

它看起來像普通函式，但因為標上了 "use server"，client 呼叫它時，Next.js 會在背後把這次呼叫轉成 POST 請求，送到伺服器執行。你不用自己定義路徑，也不用自己組裝回應。

判別問句：三個問題就能決定

不要只憑「這看起來比較簡單」來選。依序問自己下面三個問題。只要有一題答案是「是」，就走 route handler。

  1. 有「不是自家 Next.js UI」的呼叫者嗎？例如手機 App、另一個後端服務、第三方合作方，或未來可能要開放的公開 API。只要有這類呼叫者，server action 就不是合適的入口，應該使用 route handler。
  2. 需要外部系統主動打進來嗎？典型例子是 webhook：金流、LINE、GitHub 這類服務會主動 POST 到你的某個網址。這需要一個持續存在、對外公開的接收點，而 server action 不支援這種場景。
  3. 需要用 Postman、curl 或自動化測試直接打它嗎？如果這個介面會成為團隊或整合測試的對象，有一個公開 URL 的端點會容易測試許多。

如果三題都是「否」，而且這個操作只有自家表單或元件會使用，那 server action 通常是更輕、更快的選擇。

反例：什麼時候判準會翻轉？

這套規則不是把所有情況切成黑白兩色，因為需求可能會變。第一種翻轉是：你一開始認為「這是內部功能，所以用 server action」，後來卻多了一個行動 App 要呼叫。這時就必須改成 route handler。

因此，除了問「現在誰會呼叫」，也值得多問一句：「未來有沒有可能被自家以外的東西呼叫？」如果答案很可能是有，早點看清楚介面邊界，通常比事後搬家省事。

另一種翻轉則相反。如果你習慣「所有寫入都做成 REST 端點」，也要留意純自家表單的情況。把它做成 route handler，會多出一層其實用不到的 HTTP 介面，增加程式碼，也讓原本未公開的入口變成公開端點。

這時，server action 反而更符合「只暴露必要範圍」的安全直覺。

還有一個與 HTTP 語意有關的反例：server action 一律以 POST 執行，連「更新」和「刪除」也會包成 POST。如果你很在意 HTTP 方法的語意，例如更新使用 PUT、刪除使用 DELETE，並且希望 API 對外呈現標準 REST 形式，讓第三方能依照方法語意使用，那 route handler 才是正確選擇。純內部使用時，這點通常沒有那麼重要。

決策檢查表：當場就能套用

把前面的問題收斂成一張清單。看到符合的情況，就選對應的工具：

一句可以直接拿來用的規則是：只要有一個「非自家 app」的呼叫者，或需要一個對外公開、能主動被呼叫的位址，就做 route handler；否則 server action 更輕。

AI 產出的專案很容易在這裡選反：把明顯應該對外的 API 做成 server action，結果行動端接不上；或把純內部表單硬做成 REST 端點，平白增加公開面。用上面的問題和表格掃過一次，通常就能抓出這兩類錯誤。

小結

Route handler 是對外的 HTTP 端點，任何 HTTP 客戶端都能呼叫，支援完整的方法與狀態碼語意，適合需要被多方使用、測試或接收 webhook 的情境。Server action 是只有自家 app 能呼叫的伺服器函式，從 client 呼叫時會被轉成 POST、入口不公開，寫起來更輕、暴露面更小，適合純自家 UI 的變更與查詢。判準是：有沒有非自家 app 的呼叫者、需不需要對外公開的接收點。

到這裡，這個 node 的五步就走完了：從檔案式端點、動態路徑與參數、回應合約，到實作，最後進入選型判斷。現在你應該能讀懂 AI 專案裡的每個 app/api/**/route.ts，也能判斷一段查詢或寫入到底該做成端點，還是做成 action。
