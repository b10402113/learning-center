route.ts 就是你的後端：用檔案建立 API 端點

Step 1/5 · Route Handlers 與 REST API 設計

學習目標

學完這一節，你應該能說明為什麼「一個資料夾加一個 route.ts」就能形成一個 API 端點，也能看懂它比傳統 Express 後端少了哪些設定，以及 HTTP method 對應的匯出函式慣例。

先從一個熟悉的困惑開始

你請 AI 產生一個 Next.js 專案，打開檔案樹，看到 app/api/ 底下有好幾個資料夾，而且每個資料夾裡都放著一個 route.ts。你大概猜得到這些檔案和「後端」有關，卻可能忍不住問：

伺服器程式在哪裡？要在哪裡啟動？為什麼找不到熟悉的 server.js？

如果你以前寫過 Node，Next.js 的答案可能會讓你有點意外：這個專案沒有另一個需要獨立啟動的後端。Next.js 把後端能力收進同一個框架裡。一個資料夾，加上一個 route.ts，就代表一個 API 端點。

這是整個檔案式 API 的地基。後面會遇到的動態路徑、狀態碼與驗證，都會建立在這條規則上。

先看傳統後端：多一支 API，就多一套管理工作

在沒有 Next.js 後端功能的世界裡，如果你想多做一支 API，通常要先安裝 Express，再寫伺服器程式，啟動一個 process 監聽某個埠，最後還要另外部署它。

程式大概會長這樣：

// 傳統 Express：另開一個 server、自己管路由與埠
import express from "express";
const app = express();

app.get("/api/users", (req, res) => {
  res.json([{ id: 1, name: "Ada" }]);
});

app.listen(3000);

這支 Express 伺服器是前端之外的另一個東西。它有自己的啟動指令、自己的部署流程，也有自己的監控與埠號設定。

換句話說，前端和後端像兩間各自有水電帳單的房子：要分開設定，也要分開部署。

正解版：資料夾就是 API 路徑

Next.js 的 Route Handler 把這些額外設定收進框架裡。它的規則可以濃縮成兩句話：

資料夾代表一段 API 路徑，裡面的 route.ts 匯出對應 HTTP method 的函式。

如果要建立 /api/users，只要在 app/api/users/ 放入一個 route.ts：

// app/api/users/route.ts —— 對外路徑就是 /api/users
export async function GET() {
  return Response.json({ message: "Hello from the server" });
}

就這麼多。你不需要在這裡寫 app.listen，也不用自己指定埠號，更不用另外啟動一個 process。

當使用者拜訪 /api/users 時，Next.js 會依照檔案位置找到 route.ts，再根據這次請求使用的 HTTP method，呼叫對應的函式，最後把函式回傳的內容送出去。

AI 常犯版：檔名和函式名稱隨意取

AI 有時會把檔案命名成 users.ts，或把函式寫成小寫的 get。程式看起來似乎很合理，但 Next.js 並不會把它辨認成這個 API 端點。

正解版：遵守兩個固定公約

第一，檔名必須是 route.ts 或 route.js。這是框架用來辨識 Route Handler 的固定公約，換成其他檔名，Next.js 就不會把它當成 API 端點。

第二，匯出的函式名稱必須使用大寫的 HTTP method，例如 GET、POST。框架會靠這些名稱判斷：「這種請求進來時，應該執行哪一段程式？」

一個檔案，可以接住多種 HTTP method

同一個 route.ts 可以同時匯出多個函式，每個函式處理一種 HTTP method。

這也正好對應 REST API 的常見設計：同一個 /api/users 路徑，可以用 GET 讀取使用者清單，再用 POST 建立一筆新資料。

匯出的函式對應的 HTTP 方法典型用途
GETGET讀取資料（清單或單筆）
POSTPOST建立一筆新資料
PUT / PATCHPUT / PATCH整筆或部分更新資料
DELETEDELETE刪除資料

如果檔案裡只有 GET，使用者卻對同一路徑發出 POST，就會得到「方法不被允許」的錯誤。因為這個端點根本沒有匯出一個負責接住 POST 的函式。

這反而讓端點的能力變得很清楚：打開 route.ts，看它匯出了哪些函式，就知道這個路徑允許哪些操作。

檔案位置，就是對外網址

這套規則和 App Router 的頁面路由使用相同的心智模型。資料夾多一層，網址就多一段；唯一的差別是，API 端點用 route.ts 表示，而不是頁面檔案。

檔案位置對外路徑
app/api/users/route.ts/api/users
app/api/accounts/route.ts/api/accounts
app/api/ai/answers/route.ts/api/ai/answers

不過，api 這個資料夾名稱只是常見的社群約定，不是 Next.js 的硬性規定。真正決定網址的是資料夾的巢狀結構，不是資料夾是否叫做 api。

AI 常犯版：以為一定要自己啟動伺服器

看到沒有 app.listen，你可能會以為少了某個關鍵步驟：「這段程式到底跑在哪裡？」

如果照傳統 Express 的思路，這個疑問很合理。但 Route Handler 的執行方式不同。

正解版：Next.js 與部署平台管理執行環境

Route Handler 會跑在 Next.js 為你準備的執行環境裡。部署到 Vercel 這類平台時，每個 Route Handler 會被當成一個 serverless function 執行：有請求時才被叫起來，執行完成後就結束。

你不需要自己開機器、維持 process，或處理埠號。這些工作交給平台管理。

實際的好處也不只是少寫幾行設定，而是前端和後端可以放在同一個 repo，使用同一次部署。當你同時修改 API 和畫面時，可以一起送上線，不必另外協調兩邊的部署版本。

前端怎麼呼叫 Route Handler？

端點建立好之後，前端可以直接用瀏覽器內建的 fetch 呼叫它。使用方式和呼叫其他 API 沒有本質上的不同：

// 前端元件裡：用一般的 fetch 呼叫自家端點
const res = await fetch("/api/users");
const data = await res.json();

當專案規模變大，通常不會讓每一個呼叫位置都自行處理網址、標頭、錯誤與逾時。實務上，專案可能會再包一層共用工具。

例如 DevFlow 會使用 fetchHandler 統一合併標頭、透過 AbortController 設定 5000 毫秒逾時、檢查錯誤、記錄 log，最後把回應整理成一致的形狀。再往上包成 API 物件後，呼叫端只需要寫一行 API.users.getAll()。

這層不是 Route Handler 的必要條件，但它把兩件事分開了：呼叫端只關心「要呼叫哪個 API」，共用工具則負責「API 要怎麼被呼叫」。這是專案變大後很實用的整理方式。

三個常見陷阱：看 AI 產出的 route.ts 時先掃一遍

AI 常犯版正解版
把查資料、計算、寄信等商業邏輯全部塞進 route.ts。Route Handler 只負責解析請求、呼叫對應的 service 或 model，再回傳結果；真正的邏輯放到其他模組。
檔案命名成 users.ts，或把 method 函式寫成小寫的 get。使用固定檔名 route.ts，並匯出大寫的 GET、POST 等 HTTP method 函式。
只實作 GET，卻讓前端直接發 POST。先確認同一路徑支援哪些 HTTP method，再讓前端呼叫相符的操作。

第一種錯誤最容易讓檔案越長越難維護。Route Handler 應該像櫃檯，而不是整間工廠：它負責接收請求、把工作交給正確的服務，再把結果交回去；不需要把所有工作都親自做完。

把這個觀念掛回整個架構

Route handler 是 Next.js 的檔案式後端：app/ 底下一個資料夾代表一段 API 路徑，裡面的 route.ts 匯出對應 HTTP method（GET／POST／PUT／DELETE）的函式。它不需要你另外啟動一台伺服器，部署時每個端點由平台當成 serverless function 執行。前端用一般的 fetch 就能呼叫它。

所以，Route Handler 可以和前面的頁面路由使用同一張地圖來理解：資料夾結構描述網址，檔案名稱決定這個位置扮演的角色，而匯出的 HTTP method 決定端點能做哪些事。

固定路徑只是第一步。真實的 API 通常還會遇到「路徑裡有變動的值」，以及「可選的搜尋與分頁條件」。下一篇會介紹動態 segment 與 params，把每一位使用者的詳情頁、帶有查詢條件的列表等需求，也收進同一套檔案式路由模型裡。
