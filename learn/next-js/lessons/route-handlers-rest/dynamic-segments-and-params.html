動態 segment 與 params：路徑參數和查詢參數怎麼分

Step 2/5 · Route Handlers 與 REST API 設計

先看整張地圖：一個 API，兩種參數

上一節你學會了用資料夾對應端點：放一個 route.ts，就能做出 /api/users。但實際需求很快會多一層：除了列出所有使用者，還要查詢某一位使用者的詳細資料。

這時網址可能是 /api/users/123。其中 123 不是固定文字，而是會隨著使用者改變的值。你不可能為 users/1、users/2、users/3……每個 id 都建立一個資料夾。id 可以不斷增加，資料夾卻不該跟著無限膨脹。

動態 segment 就像一個可伸縮的抽屜：同一個資料夾可以接住一整類不同的路徑。接著還要分清楚另一個常見問題：路徑上的變動值，和問號後面的查詢條件，究竟各自該放在哪裡？

本課學完，你要能判斷三件事

  • 用巢狀資料夾與 [id] 動態資料夾，建立參數化端點。
  • 從 params 讀取路徑上的變動值。
  • 分辨路徑參數與查詢參數（searchParams）各自適合的用途。

先複習：巢狀資料夾就是巢狀路徑

動態 segment 並不是另一套規則，而是建立在原本的資料夾對應網址上。資料夾多一層，網址就會跟著深一層：

app/
└── api/
    └── tickets/
        └── route.ts   → /api/tickets

這個 route.ts 匯出的 GET 可以回傳整份票券清單。可是，如果要取得單一票券，例如 /api/tickets/5，就需要讓 tickets 底下再接一個代表「某個 id」的資料夾。

用中括號表示「這一段會變」

做法是把下一層資料夾的名稱包在中括號裡，例如 [id]，再在裡面放入 route.ts：

app/
└── api/
    └── tickets/
        ├── route.ts          → /api/tickets
        └── [id]/
            └── route.ts      → /api/tickets/123

[id] 裡的中括號是一個記號，表示這一層不是固定字串，而是一個會變動的參數。當使用者拜訪 /api/tickets/123 時，Next.js 會把 123 捕捉起來，交給你的程式使用。

這裡有一個很關鍵的對應關係：中括號裡的名字，就是之後讀取參數時使用的鍵。寫成 [id]，就用 params.id 取得值；寫成 [userId]，就用 params.userId。名稱可以自己決定，但資料夾名稱和程式裡的鍵必須前後一致。

AI 常犯版 vs 正解版：名稱不是裝飾品

AI 常犯版：資料夾叫做 [id]，程式卻讀 params.userId。看起來只差一個名字，實際上卻像拿錯了門牌，當然找不到對應的值。

正解版：資料夾名稱和讀取鍵保持一致。[id] 對應 params.id；[userId] 對應 params.userId。

怎麼把路徑參數讀進來？

動態 segment 的 route.ts 會多收到第二個參數 params。在較新的 Next.js 版本裡，params 是一個 Promise，因此要先 await，才能解構出裡面的值：

// app/api/tickets/[id]/route.ts —— 讀取路徑上的 id
export async function GET(
  request: Request,
  { params }: { params: Promise<{ id: string }> }
) {
  const { id } = await params;

  // id 是字串，例如 "123"
  return Response.json({ id });
}

如果你熟悉 Express，可以這樣對照：Express 通常從 req.params.id 讀取；Next.js 則把 params 放在 route handler 的第二個參數裡，而且依照框架設計，需要先 await。

兩者的核心直覺是一樣的：網址中那段可變的部分，要用一個參數物件接住它。

另一個地雷：params 讀到的一律是字串

從網址來的資料，本質上都是文字。拜訪 /api/tickets/5 時，讀到的 id 是字串 "5"，不是數字 5。

因此，如果資料庫裡的 id 是數字，而你使用嚴格等於比較，就可能永遠比對不到。這時要自己轉型別：

const { id } = await params;
const ticket = tickets.find((t) => t.id === Number(id));

反過來，如果資料庫使用的是字串 id，例如 MongoDB 的 _id 或 slug，就不需要轉成數字。要記住的是：型別轉換由你負責，不要假設框架會自動替你處理。

路徑參數 vs 查詢參數：先看它們站在哪裡

現在加入另一種常見需求：搜尋票券。網址可能是 /api/tickets/search?query=hello。問號後面的部分叫做查詢參數（query parameters），也常稱為 searchParams。

它和路徑參數不只是外觀不同，扮演的角色也不同：

路徑參數（params）查詢參數（searchParams）
在 URL 的位置嵌在路徑裡，例如 /tickets/5在問號後面，例如 ?query=hello
通常必填或選填多半是資源的身分，通常必填多半是選項，通常選填
典型用途指名「哪一筆」資源篩選、排序、分頁
Next.js 讀法await paramsrequest.nextUrl.searchParams

可以用一句話記住兩者的分工：

路徑參數回答「你要哪一個東西」；查詢參數回答「你要怎麼看這批東西」。

沒有 123，你就不知道要查哪一筆票券，因此它適合放在路徑裡。沒有 ?query=hello，你仍然可以列出全部票券，只是少了一個篩選條件，因此它適合放在問號後面。

AI 常犯版 vs 正解版：不要把兩種參數混成一鍋

AI 常犯版：把資源身分寫成 /api/user?id=5。這在技術上可以運作，但「哪一個 user」被藏在查詢參數裡，路徑不再直接呈現資源本身。

正解版：把資源身分放進路徑，例如 /api/users/5；把搜尋、排序、分頁等可選條件放到問號後面，例如 /api/tickets?query=hello。

反過來也一樣。若把分頁和排序硬塞進路徑，例如 /api/tickets/page/2/sort/desc，路徑會隨著選項增加而越來越膨脹。讓路徑負責指出資源，讓查詢參數負責調整觀看方式，API 會更容易閱讀和使用。

怎麼讀取查詢參數？

在 route handler 裡，查詢參數要從請求物件上取得。若使用 NextRequest 型別，可以這樣寫：

// app/api/tickets/search/route.ts —— 讀取查詢參數
import { NextRequest, NextResponse } from "next/server";

export async function GET(request: NextRequest) {
  const searchParams = request.nextUrl.searchParams;
  const query = searchParams.get("query");

  if (!query) {
    return NextResponse.json({ success: true, data: tickets });
  }

  const filtered = tickets.filter((t) => t.title.includes(query));
  return NextResponse.json({ success: true, data: filtered });
}

這裡還有一個小地雷：searchParams 不是普通物件，而是特殊的 URLSearchParams。不能寫成 searchParams.query，必須使用 .get("query") 取值。否則可能只得到 undefined，卻看不出問題出在哪裡。

做決定的判準：少了它，請求還成立嗎？

設計 API 時，最常卡住的通常不是語法，而是判斷某個資訊該放在路徑，還是放在問號後面。這時可以問自己一句話：「少了它，這個請求還成不成立？」

如果少了它，請求就失去意義，例如少了 id，根本不知道要操作哪個資源，那就把它放在路徑裡，做成動態 segment。

如果少了它，請求仍然可以合理執行，只是會回傳全部資料、沒有篩選，或採用預設排序，那它就是可選的修飾條件，應該放在查詢參數裡。

問題適合放置的位置例子
要指名哪一個資源？路徑參數/api/tickets/5
要用什麼條件篩選？查詢參數/api/tickets?query=hello
要採用哪種排序或分頁？查詢參數?page=2、?sort=desc

把觀念掛回整體架構

動態 segment 負責把「一整類可能的 URL」對應到同一個 route handler。中括號裡的名稱會成為 params 的鍵，而從 URL 讀出的值一律是字串；在 Next.js 15 中，params 是 Promise，所以要先 await。

查詢參數則不負責指出資源是誰，而是替既有的資源集合加上篩選、排序或分頁等觀看條件。它從 request.nextUrl.searchParams.get(...) 讀取。

動態 segment 用中括號命名一個資料夾，例如 [id]，讓它接住一整類不確定的路徑。值從函式的 params 讀出，在 Next.js 15 中要先 await，而且讀到的一律是字串。查詢參數則放在 URL 的問號後面，從 request.nextUrl.searchParams.get(...) 讀取。判準是：少了它就說不出「要哪一筆」的，放路徑；只是篩選、排序、分頁的，放問號。

到這裡，你已經能做出路徑正確、參數讀對的端點。請記住這兩種參數在整個 API 架構中的位置：params 負責定位資源，searchParams 負責調整查詢方式。下一篇會用查閱的形式，整理常用的狀態碼與一致的 response 信封，因為端點不只是路徑，前端真正依賴的還有它回傳的狀態碼與資料形狀。
