server shell + client island：一個畫面是怎麼拼起來的

Step 1/4 · 元件組合模式：server shell + client island

先看全貌：一個畫面不必整頁都交給 client

你請 AI 生一個問答平台的側邊欄，它回傳的檔案第一行寫著 "use client"。功能看起來沒問題，畫面也能正常跑，但你可能會開始懷疑：這行真的必要嗎？還是 AI 只是習慣性地加上去？如果整頁都掛著它，又會發生什麼事？

這不是小題大作。在 App Router 裡，"use client" 會影響元件樹裡有多少程式碼需要送進使用者的瀏覽器。放對位置，頁面可以又快又輕；放錯位置，整個頁面的 JavaScript 可能一起塞進瀏覽器，讓首屏變慢、bundle 變大，而且問題不一定會立刻浮現。

可以先把畫面想成一棟房子：大部分是穩固的外框，由 server component 組成；只有少數需要操作的地方，才像房間裡的小島一樣使用 client component。這就是 server shell + client island 的核心模型。先看懂這張地圖，之後才有辦法判斷 AI 產生的元件樹到底合理不合理。

學習目標

這一節要建立一個清楚的心智模型：一個畫面通常由 server component 當大範圍外框，只在需要互動的地方放入小塊的 client component。你也要能解釋，為什麼不應該為了幾個互動按鈕，就讓整頁都掛上 client。

App Router 的預設：元件先是 server component

先記住最重要的規則：在 app/ 目錄底下，除非你明確宣告，否則每個元件預設都是 server component。它的程式碼會在伺服器上執行，不會整份送進瀏覽器。

這和過去「React 元件預設都在瀏覽器執行」的直覺不同，所以剛接觸 App Router 時，很容易把「沒有寫 "use client"」誤認成「這個元件少了設定」。其實剛好相反：server component 才是預設狀態。

server component 能做的事情其實很多。它可以宣告成 async，直接在元件裡使用 await 抓資料；可以讀取環境變數與資料庫連線等不應外洩的資源；也可以 import 體積很大的套件，因為這些程式碼不會被送到瀏覽器。

它不能直接處理的，是需要瀏覽器互動的工作，例如綁定 onClick、使用 useState 或 useEffect，以及存取 window 這類瀏覽器 API。

當某個元件真的需要這些能力時，才在檔案最上方加上 "use client"。這行不是普通的註解，而是一條分界線：從這個模組開始，相關程式碼會被當成瀏覽器端程式碼打包。

server shell 與 client island：整間房子不用都插電

把一個頁面想成一間房子。牆壁、地板和家具占了大部分空間，這些東西可以先在工廠做好，再直接搬到現場。它們不需要等使用者進門後才開始組裝，這就是 server shell。

房間裡真正需要插電、需要人操作的，可能只有一盞檯燈或一台音響。這些小範圍的互動區，就是 client island。

合理的做法，是整間房子照常蓋好，只在檯燈所在的位置拉一條電線。你不會因為要讓一盞檯燈亮起來，就把每面牆都埋滿電線。同樣地，在 Next.js 裡，應該讓大部分元件留在 server，只把需要互動的葉節點標成 client。

實際上，一個頁面可能有九成是 server component，只有幾個按鈕、篩選器或編輯區是 client component。這種「把 client 推到最外圍」的習慣，正是 server shell + client island 模式的重點。

AI 常犯版：為了互動，把整個外框都變成 client

AI 很容易看到側邊欄裡有一個「展開更多標籤」的按鈕，就直接把整個 RightSidebar 加上 "use client"。這樣通常能跑，卻把不需要互動的資料抓取、標題、清單和卡片也一起推進了 client bundle。

問題不在於 client component 不能出現在側邊欄，而在於它的範圍太大。你只是需要一個可以點擊的按鈕，卻讓整個房間都接上電。

正解版：外框留在 server，只把互動區切成 island

較好的分法是，側邊欄本身繼續當 server shell；只有「展開更多標籤」這類真正需要互動的按鈕或區塊，才獨立成 client component。這樣，server shell 仍然負責取得資料與安排版型，而 client island 只負責那一小段互動。

這個切法也讓元件的責任更清楚：不需要互動的部分，不必為了其他元件一起付出瀏覽器 JavaScript 的成本。

用真實專案的側邊欄看 server shell

DevFlow 的 RightSidebar 是一個很標準的 server shell。它負責取得「熱門問題」和「熱門標籤」兩份資料，再把資料排成右側欄位。

注意這段程式碼有兩個特徵：它是一個 async 函式，而且整個檔案沒有 "use client"：

const RightSidebar = async () => {
  const [
    { success, data: hotQuestions, error },
    { success: tagSuccess, data: tags, error: tagError },
  ] = await Promise.all([getHotQuestions(), getTopTags()]);

這段開頭已經透露出 shell 的工作方式：它直接呼叫 server action 取得資料，等 await 完成後，再繼續組出畫面。查詢邏輯在伺服器上執行，瀏覽器看不到這些細節，也不需要為了抓資料再多繞一次請求。

後面的 JSX 只要把資料排成標題、清單和卡片。當畫面送到瀏覽器時，這部分已經可以先以 HTML 呈現出來。

為什麼 shell 要留在 server？

第一個原因是瀏覽器不用下載不必要的程式碼。沒有送到瀏覽器的程式碼，就不會佔用頻寬，bundle 也會比較小；在慢速網路下，這種差異尤其明顯。

第二個原因是伺服器產生的 HTML 對搜尋引擎與社群預覽比較友善。使用者提出請求後，內容可以直接出現在回應裡，而不是先等一大包 JavaScript 下載、執行，畫面才慢慢長出來。

第三個原因是安全性。資料庫連線、API 金鑰和其他 secret，本來就應該只留在伺服器。讓 shell 留在 server，可以避免把這些東西帶進瀏覽器。

第四個原因是資料取得與畫面渲染可以在伺服器附近完成，少掉瀏覽器與伺服器之間的一趟來回。

一個容易混淆的地方：client component 也會先在 server 出現

這裡有一個常見誤會：client component 並不是「完全不在伺服器上執行」。為了讓首屏更快，Next.js 會先在伺服器把 client component 預先渲染成 HTML，送到瀏覽器後，再進行 hydration，也就是補上互動能力。

因此，client component 裡的 console.log 可能會同時出現在終端機和瀏覽器；server component 裡的 log 則只會出現在終端機。

預先渲染的目標是讓使用者先看見畫面；hydration 的目標，才是讓這個畫面開始可以操作。兩者是不同階段，不要把「先在 server 產生 HTML」誤認成「它就是 server component」。

組合方向是單向的

server component 和 client component 並不是完全對等的兩種零件，它們的組合方向有明確限制。

server component 可以 import client component，也可以把資料當成 props 傳進去，或把一段 JSX 當作 children 傳進去。這就像房子的外框可以容納一座需要插電的小島。

反過來，client component 不能直接 import server component。因為一旦 server component 被 import 進 client 模組，那段程式碼就會被當成 client code 打包，原本的 server component 身分也就失去了。

這條單向規則，是之後判斷 AI 元件樹是否合理的關鍵。到了 Step 4 談「邊界該畫在哪裡」時，還會再回頭使用它。

把判斷掛回整體模型

在 App Router 裡，每個元件預設都是 server component；只有真的需要互動時，才在檔案頂端加上 "use client"，把它變成一塊 client island。理想的畫面是一大片 server shell 加上少數 client island：shell 負責抓資料與決定版型，island 只負責互動。這樣能讓瀏覽器收到的 JavaScript 盡量少，首屏更快，也能讓秘密留在伺服器。組合方向是單向的：server 可以包 client，client 不能反過來包 server。

現在可以把這些關係放在同一張圖裡理解：server component 是頁面的主要外框，負責資料與結構；client component 是嵌在外框裡、專門處理互動的小區域。下一節會把鏡頭再拉近，看看構成 shell 的那些「磚塊」——只接收 props、輸出 JSX 的純展示元件，以及它們為什麼能安穩地留在 server。
