用一個泛型 renderer 收斂列表畫面：DataRenderer 的 render prop

Step 3/4 · 元件組合模式：server shell + client island

這一節要完成什麼

你會做出一顆泛型 DataRenderer，把列表常見的四種情況集中處理：請求成功、有資料、資料為空，以及請求失敗。完成後，列表頁只需要描述「有資料時要怎麼畫」，不必每次重新撰寫狀態判斷。

開始前，請先具備兩個前置概念：server shell，以及負責純展示的元件。接下來的 DataRenderer 就像一個小型 server shell，負責把資料狀態與畫面組合起來。

先看整體架構：誰負責什麼

可以把這顆元件想成列表頁的交通指揮。它先確認請求是否成功，再確認資料是不是空的；只有真的有資料時，才把「資料要長什麼樣」的決定交給呼叫端。

  1. 若請求失敗，顯示錯誤狀態。
  2. 若請求成功但沒有資料，顯示空狀態。
  3. 若請求成功且有資料，呼叫 render 畫出列表。

狀態處理集中在 DataRenderer，版面呈現則留在各個列表頁。這樣既能避免重複，也不會讓 renderer 變成只能服務某一種資料的專用元件。

第一步：定義元件要接收的資料

先從對外介面開始。這是一個泛型元件，型別參數 T 代表列表中的資料型別，因此同一顆元件可以套用在問題、標籤、使用者或其他資料上。

interface Props<T> {
  success: boolean;
  error?: {
    message: string;
    details?: Record<string, string[]>;
  };
  data: T[] | null | undefined;
  empty: {
    title: string;
    message: string;
    button?: {
      text: string;
      href: string;
    };
  };
  render: (data: T[]) => React.ReactNode;
}

這五個 props 各自負責不同工作：

  • success：告訴元件請求是否成功。
  • error：提供錯誤訊息與可選的錯誤細節。
  • data：提供資料陣列，也可能是 null 或 undefined。
  • empty：描述沒有資料時要顯示的標題、訊息與按鈕。
  • render：描述有資料時要如何產生畫面。

其中最關鍵的是 render。它接收 T[]，回傳一段 React 節點。換句話說，DataRenderer 不需要知道 T 究竟是問題、標籤還是使用者；資料的實際型別與呈現方式，由呼叫端決定。

第二步：依序處理失敗、空資料與成功

接著把三種狀態排進元件。順序不能隨意調換：先攔截請求失敗，再處理空資料，最後才進入有資料的畫面。

const DataRenderer = <T,>({
  success,
  error,
  data,
  empty = DEFAULT_EMPTY,
  render,
}: Props<T>) => {
  if (!success) {
    return (
      <StateSkeleton
        image={{
          light: "/images/light-error.png",
          dark: "/images/dark-error.png",
          alt: "Error state illustration",
        }}
        title={error?.message || DEFAULT_ERROR.title}
        message={
          error?.details
            ? JSON.stringify(error.details, null, 2)
            : DEFAULT_ERROR.message
        }
        button={empty.button}
      />
    );
  }

  if (!data || data.length === 0)
    return (
      <StateSkeleton
        image={{
          light: "/images/light-illustration.png",
          dark: "/images/dark-illustration.png",
          alt: "Empty state illustration",
        }}
        title={empty.title}
        message={empty.message}
        button={empty.button}
      />
    );

  return <div>{render(data)}</div>;
};

逐段看這份實作：

  1. 若 success 是 false，!success 會成立，元件就回傳錯誤狀態。標題優先使用 error.message；如果有 error.details，就用 JSON.stringify 把細節整理成可顯示的文字。

  2. 若請求成功，接著檢查 !data || data.length === 0。這會同時處理資料不存在，以及資料陣列存在但長度為零的情況。

  3. 前兩個條件都沒有成立，代表目前有資料。這時才呼叫 render(data)，把實際的畫面交給呼叫端產生。

empty 也有預設值 DEFAULT_EMPTY，因此呼叫端即使沒有傳入自訂空狀態，也能正常執行。

這裡的 StateSkeleton 是共用版型，負責排列「插圖、標題、訊息與可選按鈕」。錯誤狀態與空狀態共用同一套排版，列表頁就不會各自長出不同風格。插圖則分成 light 與 dark 版本，配合專案的深淺色主題。

第三步：用 render prop 把版面交給呼叫端

render prop 的做法，是把「如何產生一段畫面」包成函式，再透過 prop 傳入。DataRenderer 只判斷狀態；確認有資料後，就呼叫 render(data)。

這裡可以用兩種寫法對照理解：

AI 常犯版：把資料版面也硬寫進 renderer

如果 DataRenderer 內部直接寫死問題卡片、標籤或使用者的 JSX，它很快就會變成某一種列表的專用元件。每次遇到不同資料型別，都得再複製一顆。

正解版：renderer 處理狀態，呼叫端處理版面

把錯誤與空資料這些共通邏輯集中在 renderer；把有資料時的排列方式留給 render。這就像餐廳只負責確認訂單是否成功、餐點是否供應，至於餐點要怎麼擺盤，交給真正知道需求的人決定。

第四步：在 server shell 中實際使用

接著看同一顆 DataRenderer 如何在側邊欄中渲染「熱門問題」。呼叫端會把 server action 回傳的狀態與資料傳入，再用 render 描述有資料時的畫面。

        <DataRenderer
          data={hotQuestions}
          empty={{
            title: "No questions found",
            message: "No questions have been asked yet.",
          }}
          success={success}
          error={error}
          render={(hotQuestions) => (
            <div className="mt-7 flex w-full flex-col gap-[30px]">
              {hotQuestions.map(({ _id, title }) => (
                <Link
                  key={_id}
                  href={ROUTES.QUESTION(_id)}
                  className="flex cursor-pointer items-center justify-between gap-7"
                >
                  <p className="body-medium text-dark500_light700 line-clamp-2">
                    {title}
                  </p>

                  <Image
                    src="/icons/chevron-right.svg"
                    alt="Chevron"
                    width={20}
                    height={20}
                    className="invert-colors"
                  />
                </Link>
              ))}
            </div>
          )}
        />

這段使用方式可以拆成兩個動作：

  1. 把 data、success 與 error 直接傳給 DataRenderer。這些值代表 server action 取得的實際結果。

  2. 透過 render 描述有資料時的畫面。真正負責排列列表的是 hotQuestions.map(...)，而不是 DataRenderer。

如果要改成標籤列表、使用者列表或留言列表，只需要替換資料、empty 內容與 render 函式。同一顆 renderer 可以重複使用，狀態判斷不用再抄一次。

做完後要確認的結果

完成後，你會得到一個可重複套用的列表外殼：

  • 請求失敗時，顯示錯誤狀態。
  • 請求成功但沒有資料時，顯示空狀態。
  • 有資料時，使用呼叫端傳入的 render 函式產生列表。
  • 需要客製空狀態時，只要替換 empty。
  • 需要調整錯誤或空狀態插圖時，修改共用的 StateSkeleton 設定。

分頁與排序仍可維持獨立，不必和錯誤、空資料的狀態處理綁在一起。

另外，DataRenderer 沒有 "use client"，所以它本身可以留在 server，直接放進 server shell 並接收 server 取得的資料。若某個列表需要互動，例如點擊卡片後展開，就把互動放在 render 回傳的 client 子元件裡。renderer 留在 server，client island 則只出現在真正需要互動的地方。

小結

把每個列表頁都會遇到的「錯誤／空／有資料」三分支，集中到泛型 DataRenderer。用 success、error、data 與 empty 描述狀態，再用 render 這個 render prop 把版面交還給呼叫端。判斷順序是：失敗 → 空 → 有資料。

現在你已經有 server shell、純展示磚塊，以及一顆能處理列表狀態的 renderer。下一步要把這些判斷力放到整棵元件樹上：當元件需要互動時，"use client" 到底應該畫在哪一條線上？最後一節會整理成可以直接套用的判別問句，並對照兩種常見的錯誤切法。
