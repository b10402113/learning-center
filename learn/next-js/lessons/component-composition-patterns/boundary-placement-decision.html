邊界該畫在哪裡：哪些元件留在 server、哪些下沉成 client island

Step 4/4 · 元件組合模式：server shell + client island

先決定一件事：互動邊界要放多高？

前三節你已經看過整間房子的結構：外層是 server shell，裡面嵌著需要互動的 client island。現在換成真實頁面，問題會變成：面對一整棵元件樹，"use client" 到底該放在哪一層？

把它放得太高，做法很省事，卻可能把整頁的 JavaScript 一起送進瀏覽器；連靜態卡片和側邊欄也得跟著下載。把它放得太低，雖然能減少瀏覽器負擔，卻可能讓元件拆得過細，props 和狀態在多個小島之間傳來傳去。

這一節不背抽象規則，而是把這個取捨整理成幾個可當場使用的判別問句。你會知道什麼時候該保留 server、什麼時候該建立 client island，也會看見兩種常見的錯誤畫法。

學習目標

拿到一個元件時，能用判別問句決定它該留在 server，還是下沉成 client island；同時認出「在整棵樹頂端掛上 "use client"」與「把 server component 塞進 client」這兩種邊界畫錯的後果。

三種畫法放在一起比較

同一個頁面，邊界可以畫在不同高度。功能未必因此改變，但送進瀏覽器的 JavaScript 量會差很多：

邊界高度進瀏覽器的 JSserver 好處適用時機
整頁最頂端掛 "use client" 整棵子樹，包含純展示卡片 幾乎全放棄 整頁都是互動元件，例如純客戶端的編輯器
畫在互動區塊的邊界 只有那個區塊 外框、資料、純展示內容都留在 server 外框靜態，但中間有一大塊需要互動
畫在最靠近互動的葉節點 最少，只有那顆按鈕或輸入框 其餘內容全部留在 server 頁面大部分是靜態內容，只有零星互動

多數頁面比較接近第三種：外框負責抓資料和排版，真正需要 state 或事件的，可能只有幾顆小元件。邊界壓得越低，server 能保留的範圍通常越大，因此這是預設可以先考慮的方向。

第二種是折衷方案，適合一整塊區域都需要互動的情況。第一種則要有充分理由，例如整頁本來就是互動密集的編輯器，才值得讓整棵子樹進入 client。

用四個問題決定邊界

與其一看到互動就把父元件標成 client，不如依序問下面幾題。答案通常會把邊界的位置指得很清楚。

  1. 這個元件自己需要事件、state、effect 或瀏覽器 API 嗎？如果都不需要，它就沒有理由成為 client component，可以留在 server。這是第一道，也是最常通過的一關。
  2. 需要互動的是整個元件，還是裡面某一小塊？大多數時候是後者。若只有一小塊需要互動，就不要標記整個父元件，改把那一小塊抽出來，讓它成為 client island。
  3. 這個元件要讀取只存在伺服器上的東西嗎？例如資料庫連線、API 金鑰或 auth() 的 session。若需要，它就必須留在 server，不能跨到 client。
  4. 我是不是因為某個子元件需要互動，才想標記這個父元件？如果答案是是，這通常就是把邊界往下推的訊號：讓真正需要互動的子元件自己成為 client。

把這四題濃縮成一句話就是：先假設元件是 server，只有它自己真的需要互動時才下沉，而且沉到最貼近需求的那一層。

反例一：把 "use client" 掛在整頁最頂端

最常見的偷懶寫法，是在頁面的根元件補上一行 "use client"，心想「先讓它能跑再說」。問題在於，這行設定會沿著 import 鏈影響整個子樹。結果是，連完全沒有互動的卡片，也會一起被打包進瀏覽器：

"use client"; // 掛在整頁最頂端

export default function QuestionsPage() {
  return (
    <main>
      <Navbar />           {/* 其實不需要 client */}
      <QuestionCard />     {/* 純展示，也被打包進瀏覽器 */}
      <Votes />            {/* 只有它真的需要 client */}
    </main>
  );
}

正確方向是讓頁面維持 server，只把真的需要互動的 Votes 做成 client island：

// 頁面沒有 "use client"，留 server
export default async function QuestionsPage() {
  const questions = await getQuestions();

  return (
    <main>
      <Navbar />
      {questions.map((q) => (
        <QuestionCard key={q._id} question={q} />
      ))}
    </main>
  );
}

兩種寫法可能都能完成畫面，但成本不同。第二版讓外框和卡片留在伺服器，瀏覽器只需要下載真正互動的那一小塊。差異就藏在 "use client" 放在哪裡。

反例二：把 server component import 進 client

另一種常見錯法，是在已經標記 "use client" 的檔案裡，直接 import server component：

"use client";

import QuestionCard from "./QuestionCard"; // server 元件被拉進 client 模組

export default function ClientShell() {
  return <QuestionCard question={someQuestion} />;
}

一旦 server component 被 client 模組 import，它就不再保有原本的 server 身分。連同它想讀取的伺服器資源，也會被當成 client code 處理。結果可能是 bundle 變大，也可能因為使用只能在伺服器執行的功能而直接編譯失敗。

如果你需要「client 的互動」加上「server 的內容」，不要在 client 裡 import server component。正確做法是由外層的 server component 把內容傳進 client 容器：

// 父層是 server component，把 server 元件當 children 傳給 client 容器
<ClientShell>
  <QuestionCard question={someQuestion} />
</ClientShell>

這遵循前一節的單向規則：server 可以包住 client，但 client 不能反過來直接包住 server。需要混合兩者時，讓 server 當外層，再把內容當成 children 送進 client 容器。

反例不一定適用：互動太密集時，邊界可以往上提

「把邊界壓到最低」不是永遠不能違反的鐵律。如果一整塊區域幾乎每個元素都需要互動，例如完整的富文字編輯面板，裡面同時有工具列、下拉選單和即時預覽，那麼把 "use client" 放在整個面板的邊界，可能比拆成許多小島更合理。

原因是拆得太細之後，狀態和事件可能要在多個 client 元件之間反覆傳遞，程式反而更難維護。實際判準是：當需要互動的葉節點又多又密，把它們的共同父層一次標成 client，可能比較划算。

但這是例外，不是預設。先確認那一整塊真的「大部分都在互動」，而不是只有其中一個小地方需要互動。

可操作的檢查表

下次拿到一棵元件樹，可以直接照下面的順序檢查：

  1. 先把所有元件都當成 server component。
  2. 逐一問：「這個元件自己需要事件、state、effect 或瀏覽器 API 嗎？」
  3. 不需要的，保持 server；需要的，抽成最小的一塊，並在它的檔案頂端加上 "use client"。
  4. 如果父元件底下只有某一小塊需要互動，不要標記父元件，改標記那一小塊。
  5. 只有當一整塊區域幾乎都在互動時，才把邊界往上提到那一塊。
邊界的預設畫法很簡單：先留在 server，只有元件自己需要互動時才下沉，而且沉到最靠近需求的位置。不要把 "use client" 掛在頁面頂端，讓整棵樹一起被打包；也不要在 client 裡直接 import server component，改用 children 從外部傳入。只有當一整塊區域的互動又多又密時，才值得把邊界往上提。

做到這裡，你已經能看懂 AI 產出的元件樹：哪裡是 shell、哪裡是純展示的磚塊、哪裡該成為 island，也能判斷那一行 "use client" 是否放在合適的位置。接下來可以把同一套判斷力用在第三方套件上；有些瀏覽器專屬套件，例如所見即所得的編輯器或主題切換器，必須隔離成 client island 或動態載入。
