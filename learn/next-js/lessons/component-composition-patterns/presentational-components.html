props-in / JSX-out：不需要「use client」的純展示元件

Step 2/4 · 元件組合模式：server shell + client island

先看整張地圖：功能多，不代表需要 client

想像你正在做一個問答平台。畫面上的 QuestionCard 會顯示標題連結、標籤、作者頭像、發問時間，還有按讚、回答與瀏覽數字。看起來像一張「很忙」的卡片，但它從頭到尾都沒有 "use client"。

這不是漏寫，而是正確的設計。上一節把整個畫面分成一大片 server shell，再放進幾座需要互動的 client island。現在把鏡頭拉近：shell 裡的許多元件，其實只是把資料排成畫面。它們不需要記住狀態，也不需要回應點擊，因此可以留在 server。

這一節要建立的判斷力是：不要看元件「顯示了多少東西」，要看它「自己有沒有互動行為」。

什麼是 props-in / JSX-out？

純展示元件的形狀很單純：接收 props，回傳 JSX。你可以把它想成一台印表機：餵進一份資料，它就按照固定版面印出畫面。它不會自己保存資料，也不會因為使用者點擊而改變狀態。

因此，這種元件不需要被送到瀏覽器執行，也就不需要 "use client"。它在伺服器完成渲染，將 JSX 轉成 HTML 後，工作就告一段落。

判斷時，可以先檢查幾個訊號：

  • 有沒有自己的 useState？
  • 有沒有使用 useEffect？
  • 有沒有處理 onClick 等事件？
  • 有沒有直接呼叫 window 或 document？

如果都沒有，它很可能就是純展示元件。相反地，使用 .map() 把陣列排成清單、使用 Link 建立超連結、用條件判斷決定要不要顯示某個區塊，這些都只是渲染資料，不代表元件本身需要互動。

AI 常犯版 vs 正解版

AI 常犯版 正解版
看到 Link、.map() 或許多子元件，就在檔案頂端加上 "use client"。 先檢查元件自己是否使用 state、事件或瀏覽器 API；只有需要互動時才成為 client component。
把「畫面看起來很動態」誤認成「必須在瀏覽器執行」。 分清楚資料呈現與使用者互動：渲染當下能算完的內容，可以留在 server。
只要子元件是 client component，就把整個父元件也標成 client。 讓 server component 包住需要互動的 client island；父元件不必因此改變身分。

用 QuestionCard 看清楚這個模式

以下是 DevFlow 的 QuestionCard。它接收一個 question 物件，以及一個可選的 showActionBtns，接著回傳卡片的 JSX：

import Link from "next/link";
import React from "react";

import ROUTES from "@/constants/routes";
import { getTimeStamp } from "@/lib/utils";

import TagCard from "./TagCard";
import Metric from "../Metric";
import EditDeleteAction from "../user/EditDeleteAction";

interface Props {
  question: Question;
  showActionBtns?: boolean;
}

const QuestionCard = ({
  question: { _id, title, tags, author, createdAt, upvotes, answers, views },
  showActionBtns = false,
}: Props) => {
  return (
    <div className="card-wrapper rounded-[10px] p-9 sm:px-11">
      <div className="flex flex-col-reverse items-center justify-between gap-5 sm:flex-row">
        <div className="flex-1">
          <span className="subtle-regular text-dark400_light700 line-clamp-1 flex sm:hidden">
            {getTimeStamp(createdAt)}
          </span>

          <Link href={ROUTES.QUESTION(_id)}>
            <h3 className="sm:h3-semibold base-semibold text-dark200_light900 line-clamp-1 flex-1">
              {title}
            </h3>
          </Link>
        </div>

        {showActionBtns && <EditDeleteAction type="Question" itemId={_id} />}
      </div>

      <div className="mt-3.5 flex w-full flex-wrap gap-2">
        {tags.map((tag: Tag) => (
          <TagCard key={tag._id} _id={tag._id} name={tag.name} compact />
        ))}
      </div>

      <div className="flex-between mt-6 w-full flex-wrap gap-3">
        <Metric
          imgUrl={author.image}
          alt={author.name}
          value={author.name}
          title={`• asked ${getTimeStamp(createdAt)}`}
          href={ROUTES.PROFILE(author._id)}
          textStyles="body-medium text-dark400_light700"
          isAuthor
          titleStyles="max-sm:hidden"
        />

        <div className="flex items-center gap-3 max-sm:flex-wrap max-sm:justify-start">
          <Metric
            imgUrl="/icons/like.svg"
            alt="like"
            value={upvotes}
            title=" Votes"
            textStyles="small-medium text-dark400_light800"
          />
          <Metric
            imgUrl="/icons/message.svg"
            alt="answers"
            value={answers}
            title=" Answers"
            textStyles="small-medium text-dark400_light800"
          />
          <Metric
            imgUrl="/icons/eye.svg"
            alt="views"
            value={views}
            title=" Views"
            textStyles="small-medium text-dark400_light800"
          />
        </div>
      </div>
    </div>
  );
};

export default QuestionCard;

先看元件的外形：它是一個普通的同步函式，沒有 async、沒有 hook，也沒有事件處理器。傳入的 question 已經包含 title、tags、author、upvotes 等資料，元件只需要把它們排成卡片。

這就是 props-in / JSX-out：資料從 props 進來，畫面以 JSX 出去。卡片不需要知道資料從哪裡取得，也不在乎這筆資料來自首頁清單、標籤頁，還是使用者的個人頁。

看起來動態，仍然可以留在 server

這張卡片裡有幾個地方，很容易讓人誤判。

  • Link 負責建立標題連結。
  • tags.map() 把標籤陣列展開成多個 TagCard。
  • getTimeStamp() 把時間轉成容易閱讀的文字。
  • 條件判斷決定是否顯示 EditDeleteAction。

這些工作都能在渲染當下完成。它們沒有要求瀏覽器持續保存狀態，也沒有等待使用者操作後才執行某個事件。因此，這些「看起來有變化」的內容，並不等於 client 互動。

判斷的重點不是「畫面上有沒有連結或清單」，而是「這個元件自己是否需要在瀏覽器裡持續運作」。QuestionCard 沒有這個需求。

props 就是元件的合約

純展示元件的價值，在於它把「資料來源」和「畫面呈現」切開。QuestionCard 只認得自己的 props：給它一個 Question，它就負責把資料排成一張卡片。

至於資料是首頁清單抓來的、標籤頁篩出來的，還是某個使用者的個人頁撈到的，卡片一概不處理。這就像餐廳的固定餐盤：廚房從不同地方送來食材，但餐盤只負責按照同一套方式呈現。

因此，同一個 QuestionCard 可以在首頁、標籤頁、個人檔案頁與收藏頁重複使用。每個頁面負責取得資料，再把資料交給卡片；卡片則用同一套版面呈現。這種「一個元件、多處重用」，正是 server shell 能維持一致的原因。

server 元件裡，也能放一座 client island

仔細看程式碼，QuestionCard import 了 EditDeleteAction。這個子元件需要開啟對話框並處理點擊，所以它是 client component。

但 QuestionCard 本身仍然沒有 "use client"。只有在 showActionBtns 為真的時候，它才會把 EditDeleteAction 渲染出來。這就是「server 包 client」：卡片這層殼留在 server，只有編輯／刪除那顆小按鈕跨到 client。

所以，純展示元件不是指「底下整棵樹都不能有 client」。它只表示這個元件自己不需要 client 身分。真正會讓卡片需要 client 的，是卡片本身加入了互動，例如滑鼠移過去時用 JavaScript 改變顏色，或點擊卡片任何地方都要觸發行為。

只要這些需求存在於子元件，就把互動收進子元件；不要因為樹上有一座 client island，就把整個 server shell 一起改造成 client。

一個常見的錯誤：為了保險而加上 use client

新手看到 QuestionCard 使用了 Link、.map()，又 import 了好幾個子元件，很容易在檔案頂端補上一行 "use client"，心想「先標起來比較保險」。

問題是，這會讓卡片以及它 import 的 TagCard、Metric 一起被打包進瀏覽器，即使它們沒有任何互動程式碼。原本可以在 server 完成的資料呈現，反而被推到 client。

比較可靠的做法，是把兩件事分開看：資料呈現是一回事，互動能力是另一回事。QuestionCard 只負責前者，所以不需要 "use client"。

把這個觀念掛回整體架構

純展示元件只做兩件事：接收 props、回傳 JSX。它沒有 state、沒有事件，也不碰瀏覽器 API，因此不需要 "use client"，可以留在 server。QuestionCard 會把 question 排成標題、標籤與 metrics，靠 props 這份合約在不同頁面重複使用。它本身是 server 元件，卻可以在需要時渲染一顆 client 子元件；判斷關鍵永遠是「這個元件自己需不需要互動」。

現在可以把兩種零件放回同一張圖裡：server shell 由許多純展示磚塊組成，互動需求則集中在少數 client island。下一步，這些零件會被組成完整的列表畫面，並用一個泛型 renderer 把「有資料、沒資料、出錯」三種狀態收進同一個元件，避免每個列表頁都重新撰寫一次狀態 UI。
