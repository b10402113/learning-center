非 fetch 的資料也要自己包：分清楚 unstable_cache 與 React.cache

Step 4/5 · Revalidation 與多層快取

先從一個常見場景開始

你用 Mongoose 查 MongoDB，頁面也確實拿到了資料，卻發現每次 render 都重新查一次。更麻煩的是，當資料更新時，你想用 revalidateTag 精準作廢快取，卻找不到可以掛 tag 的地方。

這不是資料庫查詢寫錯，而是資料根本沒有走過 Next.js 會自動管理的 fetch 快取。這一節要補上的，就是非 fetch 資料的快取方式，並分清楚兩個名字很像、實際壽命卻差很多的工具：React.cache() 與 unstable_cache。

學習目標

學完後，你應該能比較 unstable_cache（跨請求、可用 tag 作廢）與 React.cache()（只活在單輪 render）的壽命與適用時機，並用 tag 把 unstable_cache 接上 revalidateTag。

先回顧：自動快取只認得 fetch

在 Data Cache 這一層，Next.js 只會自動介入擴充版 fetch。它會攔下請求、儲存結果、掛上 tag，並套用 revalidate 設定。

但這套機制的邊界也很清楚：它只對 fetch 生效。如果資料來自 ORM、資料庫查詢，或直接呼叫一個 server action，Next.js 不會自動替你建立同樣的快取。這時候，快取和作廢都得自己設計。

常見的 AI 常犯版是：看到「要避免重複查詢」，就把所有東西都包進 React.cache()。正解要先問的是：你要避免的是同一輪 render 內的重複呼叫，還是要讓結果跨請求保存？答案不同，工具就不同。

React.cache()：只處理同一輪 render 的重複呼叫

第一種工具是 React 內建的 cache()，從 react 匯入。它的工作很單純：在同一輪 render 裡，如果同一個函式收到同一組參數被呼叫多次，就把重複工作合併成一次。

例如，generateMetadata 和頁面本身都需要同一筆資料。這時候 React.cache() 可以像在同一輪會議裡共用筆記，避免兩個人各自再查一次。

看看專案裡實際的寫法，這裡把一個查詢資料庫的 server action 包了起來：

export const getQuestion = cache(async function getQuestion(
  params: GetQuestionParams
): Promise<ActionResponse<Question>> {
  // …查詢、驗證、錯誤處理…
});

這段程式的重點不是「資料會被長期保存」，而是「這一輪 render 不要重複執行同一個查詢」。render 結束後，這份記憶也就結束；下一個請求進來，函式仍然會重新執行。

AI 常犯版：把 React.cache() 當成跨請求快取

如果你的問題是「資料庫太遠，每個請求都要重查」，只使用 React.cache() 並不能解決它。它不會跨請求，也不會跨使用者，更不會把結果放進 Data Cache。

所以，React.cache() 適合處理的是「同一輪 render 的重複呼叫」，不是「讓查詢結果在下一個請求繼續使用」。

unstable_cache：讓非 fetch 的結果也能跨請求保存

第二種工具是 unstable_cache，它從 next/cache 匯入。它的角色，是把原本不是 fetch 的資料結果也放進 Data Cache，讓結果可以跨請求、跨 route 保存。

它也能設定多久過期，並掛上 tag。用法是把原本的 async 函式包一層，再匯出包好的版本：

import { unstable_cache } from "next/cache";

export const getCachedPosts = unstable_cache(
  async () => {
    return db.post.findMany();
  },
  ["posts"],                              // 這份快取的識別 key
  { revalidate: 3600, tags: ["posts"] }  // 多久過期、掛上什麼 tag
);

這裡有三個部分。第一個參數是要被快取的函式；第二個是一組識別用的 key，Next.js 會用它辨認這份快取；第三個是選項，可以設定 revalidate 的過期時間，也可以用 tags 掛上名牌。

有了這個 tag，資料變動時就能呼叫 revalidateTag("posts")，把這一整份快取作廢。這正是上一節學到的 API，只是這次的 tag 不是寫在 fetch 選項裡，而是由你掛在 unstable_cache 上。

正解版：依照資料來源與壽命選工具

第一次呼叫時，unstable_cache 會真的查詢資料庫；之後，只要 key 相同，其他請求就能使用快取結果。即使切換到另一個 route，只要使用相同的 key，也能取得同一份快取資料。

它和 fetch 快取的效果相近，差別在於：fetch 的快取由 Next.js 自動處理，而 unstable_cache 是你為 ORM、DB 或其他非 fetch 資料來源手動包出來的。

三個工具放在一起比較

工具匯入來源壽命／範圍能不能用 revalidateTag適合解決
擴充版 fetch全域跨請求、跨使用者（Data Cache）可以，tag 寫在 fetch 選項遠端 API 的資料
React.cache()react只在一輪 render、一個 route 內不能，它不進 Data Cache同一輪 render 的重複呼叫
unstable_cachenext/cache跨請求、跨 route（Data Cache）可以，tag 寫在選項裡DB／ORM／server action 的結果

判斷時，先看你要的壽命，而不是先看工具名稱。如果你要的是「同一輪 render 不要查兩次」，用 React.cache()；如果你要的是「查詢結果可以跨請求重複使用，資料變動時還能精準作廢」，用 unstable_cache。

這兩個工具不是互相取代的關係。很多時候，它們可以一起出現：外層用 unstable_cache 保存跨請求的結果，內層再用 React.cache() 避免同一輪 render 重複呼叫。

name 裡的 unstable 代表什麼？

看到 unstable_cache 這個名字，很多人會以為它不能放進正式環境。這個前綴確實表示 API 還在演進，未來可能改名或調整，Next.js 團隊也仍在持續開發。

但「API 還在演進」不等於「完全不能使用」。它在實務上已經被採用，連 Next.js 官方相關人士也在正式站台上使用。比較務實的做法是：知道它的穩定性仍在演進，升級 Next.js 時留意 API 是否有變化；不要把它誤解成只能放在實驗室裡的玩具。

小結：把「去重」和「快取」掛在不同位置

Next.js 的自動快取只認擴充版 fetch；當資料來源是 DB、ORM 或 server action 時，得自己包。兩個工具壽命不同：React.cache() 從 react 匯入，只在同一輪 render 內去重；unstable_cache 從 next/cache 匯入，把結果存進 Data Cache、跨請求存在，還能掛 tag，讓 revalidateTag 作廢它。選哪個，看你要的是「去重」還是「快取」。

把這個觀念放回整體架構來看：React.cache() 解決的是單一 render 裡的重複工作，unstable_cache 解決的是跨請求保存非 fetch 資料。前者像同一張桌上的共用筆記，後者像可以被不同請求取用的資料櫃。

到這裡，你已經湊齊診斷所需的零件：四層快取、兩種 revalidation，以及三種快取工具。最後一節不再介紹新東西，而是把它們放回實際程式碼裡——當資料不更新，或同一份資料被重複抓取時，你要能判斷問題卡在哪一層，再選出正確的修正方向。
