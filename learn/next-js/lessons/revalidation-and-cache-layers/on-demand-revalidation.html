事件一發生就更新：revalidatePath 與 revalidateTag

Step 3/5 · Revalidation 與多層快取

這一節要完成什麼？

你會在 server action 中使用 revalidatePath 與 revalidateTag，並從 next/cache 匯入它們。完成後，你能依照資料變動的範圍，選擇要作廢某一個路徑的快取，或是一整類資料的快取。

動手前，請先準備一個會寫入資料的地方，通常是 server action 或 route handler。這裡的重點不是重新建立資料寫入流程，而是在寫入成功後，補上正確的 revalidation API。

先看全貌：資料寫入後，快取要怎麼更新？

上一節的 time-based revalidation 很方便，但它有一個明顯限制：只能等。假設你設定了 revalidate: 1200，使用者剛發布一篇文章，回到列表頁時可能仍然看到舊資料，因為距離快取到期還有十幾分鐘。

這一節要補上的，就是「資料一改，快取立刻標記為失效」這條路。Next.js 提供兩支 API：

  • revalidatePath：指定某個路徑，適合知道哪一頁需要更新的情況。
  • revalidateTag：指定某個標籤，適合同一類資料散落在多個頁面的情況。

可以把它們想成兩種通知方式：revalidatePath 像是直接叫某一間房間的人換資料；revalidateTag 則像是廣播「所有掛著這個名牌的資料都要更新」。

步驟一：從 next/cache 匯入 API

兩支 API 都位於 next/cache。它們不是從 react 或 next/server 匯入。先確認專案中的匯入方式：

import { revalidatePath } from "next/cache";

如果同一個檔案兩支 API 都會用到，就一起匯入：

import { revalidatePath, revalidateTag } from "next/cache";

這一步看似簡單，卻是常見的卡點。若從錯的模組匯入，後面自然找不到函式可以呼叫。

步驟二：用 revalidatePath 點名要更新的路徑

當你很確定「就是這一頁要更新」，就使用 revalidatePath。它會讓指定路徑對應的快取失效，下一次有人請求這個路徑時，Next.js 會重新產生內容。

例如收藏功能中，使用者收藏或取消收藏一則問題後，該問題的詳情頁都必須立刻反映最新狀態：

    if (collection) {
      await Collection.findByIdAndDelete(collection._id);

      revalidatePath(ROUTES.QUESTION(questionId));

      return {
        success: true,
        data: {
          saved: false,
        },
      };
    }

    await Collection.create({
      question: questionId,
      author: userId,
    });

    revalidatePath(ROUTES.QUESTION(questionId));

這段程式有兩個資料變動分支：

  1. 如果已經收藏，就用 findByIdAndDelete 取消收藏。
  2. 如果尚未收藏，就用 Collection.create 建立收藏。

兩條路徑最後都呼叫同一個 revalidatePath。這是關鍵：只要某個分支會改資料，就必須在寫入成功後作廢對應的快取。少掉其中一個分支，畫面就可能出現「新增收藏會更新，取消收藏卻不更新」這種不一致的結果。

ROUTES.QUESTION(questionId) 會把動態 segment 填入路徑。例如，若 questionId 是 abc123，最後得到的路徑可能是 /questions/abc123。

若是固定路徑，也可以直接傳入字串：

revalidatePath("/posts")

差別只在於動態路徑需要由你自己組合出正確的值。

AI 常犯版 vs 正解版：不要只更新其中一個分支

AI 常犯版：只在取消收藏的分支加入 revalidatePath，卻忘了新增收藏的分支也會改變同一份資料。

正解版：每一個會成功寫入資料的分支，都在寫入完成後作廢同一個對應路徑。上面的收藏 action 兩個分支都呼叫 revalidatePath，就是為了讓兩種操作的結果一致。

步驟三：用 revalidateTag 作廢一整類資料

revalidatePath 適合目標明確的頁面。但有些資料會同時出現在很多地方，例如一篇文章的標題可能出現在首頁、分類頁與作者頁。這時候逐一列出所有路徑，不只麻煩，也容易漏掉。

這種情況可以使用 tag，也就是資料的標籤。抓資料時先替它掛上一個名牌；資料變動後，再作廢這個名牌。所有掛上相同 tag 的資料，都會一起失效。

名牌掛在 fetch 的選項中，作廢則寫在 server action 裡：

// 抓資料時，替這份資料掛上 "posts" 這個 tag
fetch("https://api.example.com/posts", {
  next: { tags: ["posts"] },
});

// 資料變動後，在 server action 裡作廢這個 tag
"use server";
import { revalidateTag } from "next/cache";

export async function createPost() {
  // …把新文章寫進資料庫…
  revalidateTag("posts");
}

這裡靠的是兩端對同一個字串的約定：

  • 抓資料時使用 next: { tags: ["posts"] }。
  • 資料變動後使用 revalidateTag("posts")。

只要兩邊的 "posts" 完全一致，之後不管這份資料被多少頁面使用，都可以透過一次 revalidateTag("posts") 一起作廢。你不需要逐一追蹤它出現在哪些頁面，這就是 tag 相對於 path 的主要價值。

AI 常犯版 vs 正解版：tag 不是隨手寫的備註

AI 常犯版：抓資料時使用一個 tag，例如 "posts"，寫入後卻呼叫另一個名稱，例如 revalidateTag("articles")。兩個字串不同，這份資料就不會被正確作廢。

正解版：把抓資料和作廢資料視為一組約定，兩邊使用完全相同的 tag 字串。tag 就像門牌號碼，貼錯門牌，通知自然送不到正確的資料。

步驟四：path 還是 tag？照資料的形狀選

這兩支 API 不是哪一支「比較正確」的競賽，而是看你能不能明確指出更新範圍：

  • 若你能說出「就是這一頁要更新」，使用 revalidatePath。
  • 若你只知道「這一類資料變了」，但資料可能散落在多頁，使用 revalidateTag。
情境選哪個理由
更新一則問題後，只要更新它的詳情頁revalidatePath目標頁面明確
新增文章後，首頁、分類頁、作者頁都要變revalidateTag資料散落在多頁，用 tag 一次掃
改動會影響一個目錄下的多個路徑revalidatePath（可指定目錄）路徑有共同前綴
同一份資料用 fetch 與 DB 兩處都在讀revalidateTag用同一個名牌統管

步驟五：把 API 放在正確時機

這裡有一個容易誤解的地方：revalidatePath 與 revalidateTag 做的是「作廢標記」，不是立刻把資料重新算一遍。呼叫完成的當下，資料不一定已經重新產生；它只是被標記成「下次請求時要重做」。

因此，請遵守兩個時機原則：

  1. 放在寫入成功之後。 如果寫入失敗，或整段交易被 rollback，就不要作廢快取。否則快取會白白重做一次。在交易流程中，通常要等 commit 成功後才呼叫。
  2. 放在回傳回應之前。 讓同一個請求週期內完成作廢，使用者接到下一個畫面時，才有機會看到新的內容。

許多「資料庫明明寫進去了，畫面卻沒變」的問題，原因就是漏了這一行、把它放在寫入之前，或放進錯誤的分支。例如，取消收藏的分支有 revalidatePath，新增收藏的分支卻沒有，就會造成兩種操作的行為不一致。

AI 常犯版 vs 正解版：不要在資料寫入前作廢

AI 常犯版：先呼叫 revalidatePath 或 revalidateTag，再嘗試寫入資料。若寫入最後失敗，快取仍然被標記為失效。

正解版：先完成資料寫入，確認成功後，再呼叫對應的 revalidation API，最後回傳回應。

驗證：怎麼確認作廢真的生效？

可以用以下流程做最小驗證：

  1. 先開啟目標頁面，讓它進入快取。
  2. 從另一個地方觸發會呼叫這支 action 的操作。
  3. 回到原本的頁面，或重新整理頁面。
  4. 確認內容是否跟著資料變動。

如果內容有更新，代表 revalidatePath 或 revalidateTag 已經發揮作用。如果沒有更新，先檢查三件事：

  • 是否正確從 next/cache 匯入 API。
  • 是否放在資料寫入成功之後。
  • 傳入的路徑或 tag 字串，是否與原本設定的值完全一致。

小結：把「只能等」改成「事件發生就更新」

on-demand revalidation 會在資料變動的時刻主動作廢快取，補上 time-based revalidation 只能等待到期的缺口。兩支 API 都從 next/cache 匯入：revalidatePath 點名一個路徑，適合目標明確的更新；revalidateTag 作廢一個標籤，適合同一類資料散落在多個頁面的情況。使用時要記住兩個原則：只在寫入成功後呼叫，而且每個會改資料的分支都要處理。它們做的是「標記下次要重做」，不是立刻重新計算。

做到這裡，你已經能處理有被快取資料的主動更新。但如果資料根本沒有進入快取，例如不是用 fetch 抓取，而是直接查詢資料庫，那麼 revalidateTag 就沒有可作廢的名牌。下一節會處理這個缺口：如何把非 fetch 的資料也包成可以快取、可以作廢的形式。
