資料不更新，到底卡在哪一層？

Step 5/5 · Revalidation 與多層快取

先決定：你要修的是哪一層？

你可能遇過這些場景：資料庫明明改了，頁面卻沒有反應；使用者站內切換頁面，看到的還是舊內容；同一輪 render 裡，同一份資料卻被查了兩次。

這些症狀看起來都像「快取壞了」，但真正卡住的地方可能完全不同。前四節已經介紹四層快取、時間式與 on-demand revalidation、revalidatePath／revalidateTag、unstable_cache 與 React.cache()。這一節要做的，是把它們串成一套診斷方法：先找出症狀在哪一層，再選正確的修正。

別一看到舊資料就急著加設定。那就像家裡停電時，先把所有電器都拔掉：看似有動作，卻不一定找到真正的斷點。

選項比較：症狀、層與修正

你看到的症狀最可能卡住的層典型修正
同一輪 render 裡，同一份資料被查了兩次Request Memoization（對非 fetch 無效）用 React.cache() 包住函式
DB／API 改了，過了一陣子仍是舊資料，而且所有人看到的都一樣Data Cache設定 revalidate，或在寫入後使用 revalidatePath／revalidateTag
靜態頁面改了資料後完全不動Full Route Cache在寫入後呼叫 revalidatePath，或把該 route 改為動態

某個 API route 的 GET 一直回傳舊資料Route Handler 的預設 GET 快取export const dynamic = "force-dynamic"

這張表不是要你死背，而是用來縮小範圍。先看症狀，再問它發生在哪一輪、哪一端，以及資料從哪裡來。

判別問句：先問哪一層，再決定怎麼修

  1. 這個「重複」發生在同一輪 render 內嗎？ 如果同一次渲染中，同一份資料被查了兩次，這屬於 Request Memoization 的範圍。不過它只認 fetch；如果來源是 DB 或 server action，就要自己用 React.cache() 補上。
  2. 換一個人、重新整理，看到的仍是同一份舊資料嗎？ 如果重新整理甚至換裝置後都一樣舊，問題多半在伺服器端，方向是 Data Cache 或 Full Route Cache。
  3. 只有站內切換時是舊的，重新整理就正常嗎？ 這種「重新整理就好了」的症狀，通常要先檢查瀏覽器裡的 Router Cache。
  4. 資料是用 fetch 抓的，還是查資料庫／呼叫 server action？ fetch 可以使用 revalidate 或 tag；非 fetch 的來源則要先用 unstable_cache 包起來，否則它根本沒有進入這個快取流程，也就沒有可作廢的快取。
  5. 有沒有寫入動作，卻沒有對應的更新或作廢？ 回頭檢查寫入成功後，是否呼叫了作廢 API；也確認它是不是在寫入成功之後執行，以及路徑或 tag 字串是否和原本設定的一字不差。
  6. 這是 API route 的 GET 嗎？ 如果是，先檢查 Route Handler 的 GET 預設快取；需要即時資料時，通常要明確使用 force-dynamic 關掉它。

例如，你做了一個部落格，發表新文章後首頁一直沒有更新。先問「是不是同一輪 render 重複查詢」——不是。再問「重新整理後還是舊嗎」——是，因此問題在伺服器端。接著確認首頁是用什麼取得文章列表——如果是 fetch，方向就是 Data Cache。

最後打開 createPost 這個 server action，發現它寫完資料庫就直接回傳，沒有 revalidateTag("posts")。這時答案就很清楚了：不是快取選錯，而是少了寫入後的作廢步驟。

反例：AI 常犯版 vs 正解版

AI 常犯版：看到舊資料就加 no-store。

正解版：先確認症狀屬於哪一層。no-store 只動得到伺服器端的 Data Cache，而且會讓該 route 走向每次重新產生，等於放棄 CDN 與快取的效能好處。如果真正的問題是「站內換頁才看到舊資料」，卡住的是瀏覽器裡的 Router Cache，加再多 no-store 也不會解決。

AI 常犯版：用時間式 revalidation 處理事件型資料。

正解版：如果需求是「使用者一存檔，就要看到新資料」，這是事件驅動的更新，應該在寫入後作廢對應快取。若只設定 revalidate: 60，使用者接下來一分鐘內仍可能看到舊資料。時間式 revalidation 沒有錯，只是不能拿來處理所有場景。

AI 常犯版：只要寫了 revalidatePath，就一定會更新。

正解版：作廢 API 必須同時滿足幾個條件：路徑字串正確、執行時機正確，而且每個需要處理的分支都有呼叫。路徑傳錯、動態 segment 沒組好，或只在其中一個 if 分支裡呼叫，都可能讓你以為修好了，實際上作廢根本沒有觸發。

還有一個容易混淆的地方：不要把 React.cache() 當成跨請求快取。它只活在單輪 render；下一個請求進來，資料仍會重新查詢。如果你的問題是「資料庫距離遠，每次請求都要重查」，該考慮的是 unstable_cache，不是 React.cache()。

反例之外：Route Handler 的 GET 是另一個判斷點

Route Handler 有一組獨立的症狀。假設你用 route.ts 建立 GET 端點，內容改了，端點卻持續回傳舊資料。這時要記得，Route Handler 的 GET 在 Next.js 裡預設會被快取；光看資料查詢本身，不一定看得出問題。

如果這個端點確實需要反映即時資料，才明確關掉快取：

// app/api/posts/route.ts
export const dynamic = "force-dynamic";

export async function GET() {
  const posts = await db.post.findMany();
  return Response.json(posts);
}

不過，force-dynamic 不是萬用膠帶。它代表這個 route 每次都重新執行，只有端點真的需要即時資料時才適合使用，不要無差別貼到所有 route。

最後的決策規則

遇到「資料不更新」時，照這份檢查表走：

  • 同一輪 render 重複查詢：檢查 Request Memoization；非 fetch 就看 React.cache()。
  • 跨請求都看到舊資料：檢查 Data Cache 或 Full Route Cache。
  • 只有站內換頁時舊：檢查 Router Cache。
  • 資料來自非 fetch 的 DB 或 server action：確認是否使用 unstable_cache。
  • 寫入成功後畫面沒更新：確認是否在正確時機呼叫 revalidatePath／revalidateTag。
  • API route 的 GET 回傳舊資料：確認是否需要 force-dynamic。

先問「舊資料活在哪一層」，再問「那一層用什麼更新」，最後才動手改設定。不要從「要加哪個選項」開始猜，要從「症狀卡在哪裡」開始排除。

小結

「資料不更新」不是單一問題，而是一組可能發生在不同快取層的症狀。先分辨是同一輪 render 的重複，還是跨請求的舊資料；再確認問題在伺服器端還是瀏覽器端；接著查明來源是 fetch 還是 DB；最後檢查寫入後是否作廢，以及 API GET 是否被預設快取。常見的錯誤修正包括無腦加 no-store、用時間式 revalidation 處理事件型資料，以及呼叫了作廢 API 卻因路徑或時機錯誤而沒有生效。

走完這五步，你就把前面學到的內容串成一張完整的圖：四層快取是地圖，兩種 revalidation 是更新路線，unstable_cache 與 React.cache() 是補上非 fetch 缺口的工具，而反向診斷則讓你能從症狀一路追到根因。
