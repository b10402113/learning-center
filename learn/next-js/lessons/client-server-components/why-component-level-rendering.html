為什麼選擇要落到元件層級？

Step 1/5 · Server vs Client Components

學習目標

能說出 Next.js 13 之前「伺服器渲染只能做在整個路由頁面」的限制，以及 app directory 為什麼要把渲染環境的選擇權下放到單一元件。

前言：為什麼一顆小按鈕，要把整頁拖下水？

想像你在做一個商品頁。畫面上大部分是商品資訊，右上角有一顆「加入收藏」的愛心按鈕。這顆按鈕得記住「已收藏／未收藏」的狀態，也要在使用者點下那一刻立刻有反應。問題來了：如果整頁只有這顆按鈕需要這種互動，那其他九成只負責顯示的內容，為什麼也得跟著被推進瀏覽器一起處理？

要回答這個問題，得先弄清楚 Next.js 是從什麼時候開始，讓我們可以「挑元件」決定它要在哪裡執行。這一節要回到 Next.js 13 之前，看舊版把伺服器渲染綁在「整個頁面」上時會發生什麼事，以及 app directory 為什麼要把這個選擇權拆到單一元件。搞懂這個轉折，你才看得懂後面兩種元件為什麼會存在。

先定義兩個角色：client 與 server

client（用戶端）指的是你手上正在用的裝置，例如手機或電腦。它負責送出請求，並把伺服器回傳的結果顯示成一個可以互動的介面。

server（伺服器）則是一台持續運轉、規格較強的機器，應用程式的程式碼就放在這裡。當 client 送出請求，server 執行必要的運算，再把結果回傳。

在網頁世界裡，這兩端各自擅長不同的事：server 離資料近，也能替你把秘密保管好；client 離使用者近，能處理即時的互動。真正困難的從來不是選哪一邊，而是在哪個層級上做這個選擇。

Next.js 13 之前的限制：選擇只能做在整頁

在 Next.js 13 之前，伺服器渲染（server-side rendering）被限制在「一個個路由頁面」上。也就是說，只有像 /、/about、/projects 這種整頁的層級，才有機會先在伺服器端渲染好。

這個限制聽起來好像沒什麼，實際開發起來卻很折磨。假設某個藏在深處的小元件需要一份資料，但資料只能在頁面層級取得，你就得一路把這份資料當成 prop 往下傳，穿過好幾層根本不需要它的元件，這種做法叫做 prop drilling（屬性鑽取）。另一種常見的解法，是讓每個需要資料的元件自己再呼叫一次 API，結果同一份資料被重複抓了好幾次。

換句話說，舊模型逼你在「整頁」這個粗糙的顆粒度上做決定，偏偏真正需要不同對待的，往往只是頁面裡的某幾個小零件。

app directory 帶來的轉折：元件層級的伺服器渲染

app directory 改變了這件事。它最關鍵的設計，就是讓伺服器渲染可以做到「元件層級」（component-level server-side rendering）。用白話說，就是我們現在有能力決定「某個特定元件、某一段程式碼」要在哪裡渲染。

用一個例子就能感受到差別。假設有一個叫做 Navbar.jsx 的導覽列元件，在新模型下，我們可以自己決定要把它放在伺服器端渲染，還是放在使用者的瀏覽器裡渲染。這個選擇一旦存在，就會自然分裂出兩種元件：Client Component 與 Server Component。

你可以把它想成裝潢房子。以前的規則是「整棟房子只能挑一種風格」，現在則進步到「可以一間一間房間分別決定」。靈活度大幅提升，但同時，每一間房間的選擇都得自己負責。

小結

Next.js 13 之前，伺服器渲染只能綁在整個路由頁面上，因此造成 prop drilling 與重複呼叫 API。app directory 把選擇權下放到單一元件，讓我們可以針對每個元件決定在哪裡渲染。這正是 Server Component 與 Client Component 兩種身分誕生的原因。

現在你知道「為什麼要有這個選擇」了。但 Server Component 與 Client Component 這兩個當事人，到底各自在哪裡執行、預設又是哪一種？下一節會把它們請出來，並用一個 console.log 實驗，讓你親眼分辨日誌出現在終端機還是瀏覽器。
