這個元件該放 Server 還是 Client？

Step 4/5 · Server vs Client Components

學習目標

能用「它需不需要瀏覽器互動？」這一個問題，對任一元件做出 Server 或 Client 的可辯護判斷。

前言：每天都在做的那個決定

前兩節把機制講完了：我們知道兩種元件在哪裡執行，也知道 "use client" 是一道會往外擴散的模組邊界。但你真正每天要面對的工作，其實是某個很具體的瞬間：你打開一個新檔案，準備寫一個元件，然後停下來想：「它到底該放哪一邊？」

這一節要把這個判斷變成一個可以反覆操作的問題，並附上一張對照表。你不需要背住所有情況，只要記住一個問句，再搭配表格確認，就能對絕大多數元件做出站得住腳的決定。

先看選項：什麼需求該配哪一種元件

與其從「元件叫什麼名字」去猜，不如從「這個元件要做什麼事」去對照。下面這張表把常見需求分成兩欄：左邊列出你打算完成的工作，右邊是它通常該落在哪一種元件。

這個元件需要做什麼？該用
抓取資料（fetch data）Server Component
直接存取後端資源Server Component
把敏感資訊留在伺服器（存取權杖、API 金鑰等）Server Component
把大型依賴套件留在伺服器，或減少送到瀏覽器的 JavaScriptServer Component
加入互動與事件監聽（onClick()、onChange() 等）Client Component
使用狀態與生命週期效果（useState()、useReducer()、useEffect() 等）Client Component
使用只有瀏覽器才有的 APIClient Component
使用依賴狀態、effect 或瀏覽器 API 的自訂 hookClient Component
使用 React 的 class componentClient Component

這張表的結構其實很有規律：凡是跟「資料、秘密、大套件」有關的，留在伺服器；凡是跟「互動、狀態、瀏覽器」有關的，交給用戶端。前者是伺服器擅長的事，後者只有瀏覽器做得到。

一個問句就能判別

如果你不想每次翻表，那就記住這一個問題：

這個元件需不需要使用者的互動？

需要互動，例如點擊按鈕、在輸入框打字、觸發事件、使用 React hook，那它就是 Client Component。不需要互動，只是抓資料、顯示靜態內容，或做一些伺服器端的運算，那它可以是 Server Component。

這個問句之所以好用，是因為互動是「只有瀏覽器才辦得到」的事。反過來說，一個元件如果完全不碰互動與瀏覽器功能，那就沒有理由把它送到用戶端，留在伺服器反而更省。Yes — Client Component，No — Server Component，就是這麼簡單。

規則會在什麼時候翻轉？

不過，只靠這一句話還不夠，因為有幾種情況會讓它失準。知道這些反例，你的判斷才不會在真實專案裡翻車。

第一，你其實沒有「選 Server」的動作。Server Component 是預設值，你唯一要主動做的，是在需要時加上 "use client"。所以問題的正確問法不是「該選哪個」，而是「有沒有必要把它變成 client」。沒有必要，就什麼都別加。

第二，問句要問「這一個元件」，不是「它底下的子元件」。一個只負責排版、把子元件拼起來的外層容器，本身可能完全不需要互動，於是它能安穩地留在 server，讓底下需要互動的子元件自己去當 client。很多人誤把整個區塊都標成 client，只因為其中一小角有顆按鈕，這是不必要的浪費。

第三，規則會被 import 方向綁架。還記得上一節的實驗嗎？一個原本不需要互動的元件，只要被 client 檔案 import 進去，就會被迫跟著變成 client。也就是說，判斷不能只看元件自己做了什麼，還要看它被誰 import。這也是為什麼把 "use client" 盡量往葉節點（最內層、真正需要互動的那個元件）推，通常是比較好的做法。

第四，有些東西天生就得在 client。第三方套件如果內部用了 state 或瀏覽器 API，使用它的元件就跟著非 client 不可；React 的 class component 也一樣，一律屬於 client。遇到這種情況，問句的答案不是「需不需要互動」，而是「它有沒有用到只有用戶端能提供的東西」。

小結

判斷元件該放哪裡，先問一個問題：這個元件需不需要使用者互動？需要就加上 "use client"，變成 Client Component；不需要就保持預設的 Server Component。但要記得三個例外：Server 是預設，你不用主動選；判斷要看單一元件而不是整個區塊；而且 import 方向會左右結果，所以 "use client" 要盡量往真正需要它的最內層推。資料、秘密、大套件留在 server；互動、狀態、瀏覽器功能交給 client。

到這裡，你已經能判斷「單一元件」該放哪一邊了。可是真實的架構不是一堆互不相干的元件，而是一整棵元件樹，"use client" 的邊界只要往上一格，被拉進瀏覽器的東西可能就多一大包。下一節要把鏡頭拉遠，看看這條線畫在不同位置，對 bundle、SEO、安全與依賴各自會付出什麼代價。
