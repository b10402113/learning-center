邊界畫在哪，會付出什麼代價？

Step 5/5 · Server vs Client Components

學習目標

能說出 "use client" 邊界的位置如何影響 bundle 大小、SEO、安全性與依賴，並用這四個角度檢查 AI 生成的元件拆分。

前言：判斷對一個元件，不等於把整條線畫對

上一節你學會了對「單一元件」問一個問題。但在真實專案裡，元件不是各自獨立的，而是一整棵彼此 import 的樹。同一組元件，你只要把 "use client" 從某一層往上搬一格，被拉進瀏覽器的東西可能就從一小撮變成一整包。

這也是審查 AI 生成的架構時最常抓到問題的地方：每個元件單看都「合理」，但整條邊界畫得太高，於是 bundle 膨脹、秘密外洩、大套件被一起下載。這一節要把邊界兩側的代價攤開，讓你從「元件對不對」升級到「整條線對不對」。

四條軸線：邊界畫在哪，代價就落在哪

Server Component 這一側的價值，可以拆成四個具體好處：送到瀏覽器的 JavaScript 更少、SEO 更好、初次載入更快、伺服器資源利用更有效率。反過來說，當你把邊界往上推、讓愈來愈多東西變成 client，這四項好處就會一項一項流失。

軸線邊界留在 server 側邊界推到 client 側
Bundle 大小只送出 HTML，瀏覽器要下載的 JS 少元件的程式碼與其依賴都被送進瀏覽器，bundle 變大
SEO伺服器產生完整 HTML，搜尋引擎看得到內容client 仍會預先渲染，但依賴互動的片段只是佔位符
安全存取權杖、API 金鑰等敏感資訊留在伺服器秘密一旦進入 client 模組，就等於送到使用者手上
依賴大型套件留在伺服器，不進瀏覽器被拉進 client 的大套件一起被下載，拖慢頁面

這四條軸線其實是同一個道理的四個面向：凡是被劃進 client 那一側的東西，都會被送到使用者的裝置上。程式碼送過去，就下載得動；秘密送過去，就不算秘密；大套件送過去，就佔頻寬。所以邊界的每一格移動，都要問「被多拉進來的是什麼」。

看一個實際的擴散：server 元件怎麼被拖進 bundle

還記得前面那個把 Server Component 塞進 Client Component 的實驗嗎？它不只是日誌跑錯地方，而是整個元件的程式碼都被拉進了 client 模組：

"use client";

import ExampleServer from "./ExampleServer";

const ExampleClient = () => {
  console.log("I'm Client Component :)");

  return (
    <>
      <div>
        <p>This an example client component</p>
      </div>
      <ExampleServer />
    </>
  );
};

export default ExampleClient;

在這段程式碼裡，ExampleServer 被 ExampleClient import 進來。結果是它不再是伺服器端的元件，而是跟著 client 一起被送到瀏覽器。如果這個被拉進來的元件裡藏著資料庫存取、讀取檔案或任何只該在伺服器執行的邏輯，那麼這條邊界的代價就不只是「多下載幾 KB」，而是安全與正確性一起出問題。

邊界的高低，連大套件都會被波及

同樣的道理也適用在第三方套件上。假設你想在畫面上顯示一個格式化日期，於是在一個標了 "use client" 的檔案裡 import 了一個體積不小的日期函式庫：

"use client";

import { format } from "date-fns";

export default function PrettyDate({ date }) {
  return <span>{format(date, "yyyy-MM-dd")}</span>;
}

這個元件本身沒什麼問題，但它把整個 date-fns 的相關程式碼一併帶進了瀏覽器。如果這個格式化其實可以在 server 端先做好，把算好的字串當 prop 傳進來，那麼這條邊界就畫得完全沒有必要，白白讓使用者多下載了一個套件。這正是「把大型依賴留在伺服器、減少 client 端 JavaScript」這條原則在真實專案裡的長相。

反過來也要小心：不是把所有東西推回 server 就沒事

看到這裡，你可能會想：「那我乾脆什麼都留在 server，不就最省？」事情沒那麼簡單，有兩個地方會翻車。

第一，真正需要互動的元件，硬留在 server 是行不通的。事件處理、state、瀏覽器 API 只有用戶端能執行，這些需求會逼你把元件的某一層切成 client。你能做的是「把邊界推到最內層」，而不是「完全不要邊界」。

第二，加了 "use client" 並不等於這個元件在 HTML 裡完全消失。Next.js 還是會先在伺服器端預先渲染 client 元件，做出靜態外殼。所以「內容爬不到、首屏空白」這種說法並不精確；真正的差別在於，需要互動的部分在預渲染階段只是佔位符，要等瀏覽器接手才補上。

小結

"use client" 的邊界畫在哪，決定了四件事：多少 JavaScript 被送進瀏覽器（bundle）、搜尋引擎能看到多少內容（SEO）、敏感資訊會不會離開伺服器（安全）、以及大套件會不會被一起下載（依賴）。凡是劃進 client 的東西都會被送到使用者裝置上，所以每一格移動都要問「多拉進來的是什麼」。實務上把 "use client" 盡量往真正需要互動的最內層推，其餘交給 server；但也要記得，需要互動的元件終究得當 client，而 client 元件仍會被預先渲染成靜態外殼。

到這裡，你手上已經有一整套判斷：知道兩種元件、知道邊界的擴散方式、知道怎麼挑選、也知道代價落在哪裡。下一次 AI 丟給你一份元件樹時，你可以沿著 "use client" 的位置走一遍，用這四條軸線問它：被多拉進瀏覽器的是什麼？該不該往下移一層？這就是從「看得懂」跨到「抓得出問題」的第一步。
