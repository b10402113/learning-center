頂層檔案與資料夾：新專案先看懂哪幾層

Step 1/4 · 專案結構與分層：feature 放哪裡

先別急著改檔案，先看懂它們各自站在哪一層

你請 AI 用 npx create-next-app@latest 生了一個 Next.js 專案。編輯器一打開，左邊的檔案樹立刻長出十幾個檔案：tsconfig.json、next.config.ts、postcss.config.mjs、package-lock.json……每個名字看起來都很重要，卻很難判斷哪個能改、哪個改了可能讓整個專案出問題。

這種卡住，通常不是檔案本身太難，而是你還沒看出它們分屬不同層次。先把頂層拆開，你會發現它其實主要包含三類東西：負責專案如何執行的設定與依賴、存放原物料的地方，以及你每天真正會寫 feature 的應用程式碼。

這一節先建立整張地圖。之後不管看到哪個 App Router 專案，你都能先判斷自己正在看的，是工具設定、資源與依賴，還是應用程式本身。

把頂層想成一間剛交屋的房子

可以把 create-next-app 交給你的專案想成一間已經牽好水電、附上基本家具的房子。它不只是一個空殼，還包含了管線、原物料，以及真正讓你動工的主房間。

頂層檔案與資料夾，大致可以這樣看：

my-app/
├── tsconfig.json          → 設定與依賴層：TypeScript 怎麼檢查
├── tailwind.config.ts     → 設定與依賴層：Tailwind 怎麼擴充
├── postcss.config.mjs     → 設定與依賴層：CSS 怎麼被處理
├── package.json           → 設定與依賴層：有哪些依賴、能跑哪些指令
├── package-lock.json      → 設定與依賴層：鎖住每個套件的確切版本
├── next.config.ts         → 設定與依賴層：Next.js 功能怎麼開
├── next-env.d.ts          → 設定與依賴層：Next.js 的型別宣告（不要改）
├── eslint.config.mjs      → 設定與依賴層：程式碼規範
├── .gitignore             → 設定與依賴層：哪些東西不進版控
├── public/                → 靜態資源層：圖片、字型、favicon 原樣被服務
├── node_modules/          → 依賴倉庫：npm 裝好的套件（不手改、不進版控）
└── app/                   → 應用原始碼層：路由、畫面、樣式都在這裡

設定與依賴層：專案的控制面板

先看頂層那一整排設定檔。它們決定專案如何被編譯、檢查與啟動，但通常不是你平常放 feature 的地方。

tsconfig.json 定義哪些檔案要接受 TypeScript 型別檢查、哪些檔案可以忽略，以及檢查時採用的規則。next.config.ts 則用來調整 Next.js 本身的功能，例如實驗性選項、圖片設定與建置設定。

postcss.config.mjs 是 CSS 的處理設定。裡面掛上 Tailwind 這個 plugin 之後，你才能在元件裡使用 utility class。eslint.config.mjs 則負責程式碼規範，幫助你檢查全專案的寫法是否符合設定。

.gitignore 也屬於這個管理區域。它列出哪些檔案或資料夾不應該進入版控，避免把不需要共享的內容提交到 Git。

AI 常犯版：把每個頂層檔案都當成「可以直接改的程式碼」

當 AI 看到一個新專案時，很容易把所有檔案都混成一團：想加功能，就隨手改設定檔；覺得檔案太多，就刪掉看起來不像程式的檔案；遇到型別問題，甚至把自己的型別宣告塞進 Next.js 自動產生的檔案。

這種做法的問題，不是每次都會立刻報錯，而是你把「專案怎麼運作」和「應用程式要做什麼」混在一起了。像是為了換一盞燈，先去拆牆裡的電線；燈也許暫時亮著，但下一次出了問題，就很難知道是哪裡被動過。

正解版：先分清楚「工具怎麼跑」和「功能寫在哪裡」

package.json 是這一層的心臟。它記錄專案依賴，以及可以執行哪些 scripts。

dev 會用開發模式啟動 Next.js，並提供熱模組替換（Hot Module Replacement，簡稱 HMR）。也就是說，存檔後瀏覽器能立即更新，並顯示開發期間的錯誤；這是你平常最常使用的指令。

build 會產生最佳化的正式版本，start 會用正式模式啟動，而 lint 則會執行 ESLint，檢查整個專案的程式碼。

這樣分辨之後，判斷就會清楚很多：如果你是在調整 TypeScript、Next.js、CSS 或 ESLint 的運作方式，才需要看設定層；如果你是在實作頁面、路由或共用版型，目標通常應該是 app/。

兩個檔案要特別小心

設定與依賴層裡，有兩個檔案特別容易被誤處理。

第一個是 next-env.d.ts。它是 Next.js 專用的 TypeScript 宣告檔，檔案裡已經明寫不要編輯。你自己的型別不要往這裡塞，否則會把自動產生的內容和自己的程式碼混在一起。

第二個是 package-lock.json。它會把每個依賴，以及依賴底下的子依賴版本鎖定，讓所有協作者安裝到完全一致的版本。

AI 常犯版：覺得 package-lock.json 很吵，直接刪掉

package-lock.json 看起來內容很多、更新也可能很頻繁，因此有人會把它當成暫存檔刪掉。但刪除之後，其他人的機器可能安裝到更新版本，甚至是帶有 bug 的版本；這樣一來，你遇到的問題就可能無法在別人的環境重現。

正解版：把 package-lock.json 當成環境一致性的保險

它不是多餘的雜訊，而是讓大家使用同一組依賴版本的依據。就像一群人要一起組裝同一件家具，不能每個人都自行拿不同尺寸的螺絲；版本鎖定，才能讓專案在不同機器上維持一致。

資源與依賴：原物料放哪裡，工具又放哪裡

public/ 是靜態資源層，專門存放圖片、字型與 favicon 這類不需要經過打包、要原樣提供給瀏覽器取用的檔案。它們的網址會直接對應到這個資料夾。

node_modules/ 則是依賴倉庫，裡面放著 npm 安裝好的套件，由 npm 自動管理。你不需要手動進去修改任何內容；它通常也會被 .gitignore 排除，不進入版控，避免把整個儲存庫撐得過大。

這兩個資料夾都不是你日常實作 feature 的主要場所。public/ 放的是要被取用的原物料，node_modules/ 放的是工具依賴；它們和應用程式碼扮演的是不同角色。

最後，你真正每天會動的那一層

把工具設定、靜態資源與依賴先放到正確的位置後，剩下的 app/ 就是這間房子的主房間。

app/ 是整個專案最重要的資料夾。之後要實作的頁面、API 路由與共用版型，絕大多數都會落在這裡。設定層的檔案可能一週才打開一次，但 app/ 通常會是你每天工作的地方。

因此，面對一個陌生專案時，先把頂層的 *.json、*.config.* 與 *.d.ts 視為工具設定；把 public/ 和 node_modules/ 分別看成資源與依賴；真正想理解這個 app 在做什麼，就進入 app/。

小結：先分層，才知道下一步該往哪裡看

一個 App Router 專案的頂層，可以先分成三層：設定與依賴層（tsconfig.json、next.config.ts、package.json、package-lock.json、postcss.config.mjs、eslint.config.mjs、next-env.d.ts）決定專案怎麼跑；資源與依賴區域（public/ 與 node_modules/）存放原物料與已安裝套件；應用原始碼層（app/）才是你每天寫 feature 的地方。其中 next-env.d.ts 不要改、package-lock.json 不要刪、node_modules/ 不要手動編輯。

這三層的關係，就像房子的控制面板、儲藏空間與主房間：前者決定整間房子如何運作，中間放工具和原物料，最後才是你真正生活與工作的地方。先把這張地圖掛在腦中，下一步再鑽進 app/，理解 page.tsx、layout.tsx，以及包住所有路由的 root layout 各自負責什麼。
