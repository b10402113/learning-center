route group 與分層 shell：URL 不變，版面各自成家

Step 3/4 · 專案結構與分層：feature 放哪裡

先看整張地圖：同一個網站，可以有不同外框

你可能遇過這種情況：主站頁面需要 navbar、左右側邊欄，登入頁卻只想顯示一張置中的卡片。若把所有元件都塞進同一個 layout，登入頁就會被迫穿上主站的外套；若把 layout 分散寫在各個頁面，又會開始複製貼上，日後維護像在不同房間各修一面同樣的牆。

這一課要解決的，就是「不同區塊共用不同版型，但 URL 不要跟著變醜」的問題。App Router 的 route group 讓你可以用資料夾整理頁面，卻不把整理用的名稱放進網址；nested layout 則讓不同區塊各自擁有自己的 shell。

學習目標

看完後，你應該能解釋 (root)、(auth) 這類 route group 如何在不改變 URL 的前提下替 app/ 分層，也能說明 nested layout 如何為不同區塊組成各自的 shell。

前言：登入頁不想長得跟主站一樣

上一節你已經知道，layout.tsx 會用 children 包住底下的頁面。但接著就會遇到一個很實際的難題：主站首頁、問題列表、個人頁面都需要同一組 navbar 和左右側邊欄，登入與註冊頁卻完全不需要這些。它們只想要一張置中的卡片。

如果把 navbar 寫在 root layout，登入頁也會被迫掛上它；如果只在前幾個頁面各自處理，又會產生重複程式碼，維護起來很麻煩。

理想的狀態是：兩種版型沿著不同分支共用，而 URL 仍維持乾淨的 /sign-in，而不是多出一段 /auth/sign-in。route group 就是用來處理這件事的工具：資料夾名稱用括號包起來，它不會出現在網址裡，卻可以擁有自己的 layout。

route group：括號資料夾不會進 URL

route group 的規則很短。資料夾名稱用一對括號包住，例如 (root) 或 (auth)，它就只是一個整理用的分組，不會成為網址的一段。

因此，app/(auth)/sign-in/page.tsx 對外的網址是 /sign-in，不是 /auth/sign-in。括號的作用，就像檔案櫃裡的分類標籤：方便你整理內容，但不會被印在寄出的信封上。

更重要的是，每個 route group 都可以擁有自己的 layout.tsx。在 DevFlow 裡，(root) 放需要主站外框的頁面，(auth) 放登入與註冊頁。兩邊使用不同的 layout，網址卻維持原本的樣子。

AI 常犯版 vs 正解版：資料夾名稱不一定等於 URL

寫法 結果 問題或優點
AI 常犯版：app/auth/sign-in/page.tsx /auth/sign-in auth 是一般資料夾，也會成為 URL 的一部分。
正解版：app/(auth)/sign-in/page.tsx /sign-in (auth) 只負責分組，不會出現在 URL，還能提供自己的 layout。

判斷時不要只看資料夾名稱，要先問一句：這個資料夾是要代表網址路徑，還是只想把相關頁面整理在一起？如果只是後者，就可以考慮 route group。

兩組 layout，兩種 shell

主站和登入頁雖然同屬一個應用程式，卻像兩棟用途不同的建築：主站需要完整的導覽系統，登入區則需要簡潔、集中的入口。先看主站這一組的 app/(root)/layout.tsx：

import { ReactNode } from "react";

import Navbar from "@/components/navigation/navbar";
import LeftSidebar from "@/components/navigation/LeftSidebar";
import RightSidebar from "@/components/navigation/RightSidebar";

const RootLayout = ({ children }: { children: ReactNode }) => {
  return (
    <main className="background-light850_dark100 realtive">
      <Navbar />

      <div className="flex">
        <LeftSidebar />

        <section className="flex min-h-screen flex-1 flex-col px-6 pb-6 pt-36 max-md:pb-14 sm:px-14">
          <div className="mx-auto w-full max-w-5xl">{children}</div>
        </section>

        <RightSidebar />
      </div>
    </main>
  );
};

export default RootLayout;

這個 layout 的骨架很清楚：navbar 在最上方，左右側邊欄分立兩側，中間則放入 children。而 children 就是每一個 (root) 底下的頁面。

它還把頁面內容放進有寬度限制的 <section>，所以主站每一頁都會自動套上相同的導覽與側欄。未來不論是問題列表、個人頁或標籤頁，只要放進 (root)，就能共用這套 shell。

再看登入區的 app/(auth)/layout.tsx：

import Image from "next/image";
import { ReactNode } from "react";

import SocialAuthForm from "@/components/forms/SocialAuthForm";

const AuthLayout = ({ children }: { children: ReactNode }) => {
  return (
    <main className="flex min-h-screen items-center justify-center bg-auth-light bg-cover bg-center bg-no-repeat px-4 py-10 dark:bg-auth-dark">
      <section className="light-border background-light800_dark200 shadow-light100_dark100 min-w-full rounded-[10px] border px-4 py-10 shadow-md sm:min-w-[520px] sm:px-8">
        <div className="flex items-center justify-between gap-2">
          <div className="space-y-2.5">
            <h1 className="h2-bold text-dark100_light900">Join DevFlow</h1>
            <p className="paragraph-regular text-dark500_light400">
              To get your questions answered
            </p>
          </div>
          <Image
            src="images/site-logo.svg"
            alt="DevFlow Logo"
            width={50}
            height={50}
            className="object-contain"
          />
        </div>

        {children}

        <SocialAuthForm />
      </section>
    </main>
  );
};

export default AuthLayout;

這裡同樣接收 children，但版型完全不同。它沒有 navbar，也沒有側邊欄，而是用一張有邊框與陰影的卡片把內容置中，最後再放上共用的社群登入按鈕。

因此，sign-in 與 sign-up 放進 (auth) 後，就會共用這張卡片。它們對外的網址仍然分別是 /sign-in 與 /sign-up。

AI 常犯版 vs 正解版：不要把共用版型複製到每一頁

寫法 思考方式 後果
AI 常犯版 在每個主站頁面各自放 navbar、左右側邊欄；登入頁再另外處理。 重複程式碼增加，版型調整時要修改多個地方，也容易出現不一致。
正解版 用 (root) 集中主站頁面，用 (auth) 集中登入頁面，分別交給不同的 group layout。 同一區塊共用同一個 shell，版型責任清楚，URL 也不必配合資料夾改名。

這不是二選一，而是三層疊起來

這裡很容易產生一個誤解：有了 (root) 和 (auth) 的 layout，是不是就代表 root layout 被取代了？不是。它們不是互相競爭，而是一層一層套起來。

使用者進到 /sign-in 時，畫面會先被 root layout 包住。root layout 負責提供 <html>、字型與登入 provider 等全站都需要的內容；接著再套上 (auth) 的 layout，提供登入區的置中卡片；最裡面才是 sign-in 頁面本身。

可以把它想成洋蔥，也可以想成建築物的樓層：

層次 負責內容 範例
root layout 全站都需要的外層設定 <html>、字型、登入 provider
group layout 某個區塊共用的版型 (root) 的 navbar 與側欄、(auth) 的置中卡片
page 實際頁面內容 sign-in、sign-up 或主站各頁面

這正是分層的價值：每一層只處理一種範圍的責任。要換全站字型，就改 root layout；要換主站版型，就改 (root)；要換登入頁外觀，就改 (auth)。你改哪一層、會影響哪些頁面，界線都很清楚。

而且，這些資料夾分組不會污染 URL。檔案系統可以有自己的整理方式，網址則維持使用者熟悉的樣子，兩者各自做好自己的工作。

把觀念掛回整體架構

route group 用括號命名，例如 (root)、(auth)，只做檔案分組，不會出現在 URL。每個 group 都能有自己的 layout.tsx，所以不同區塊可以共用不同的 shell：(root) 掛上 navbar 與側欄，(auth) 則只保留置中的登入卡片。這些 group layout 不是取代 root layout，而是疊在它下面。全站關注點在最外層，區塊版型在中間，頁面內容在最裡面。

到這裡，你已經能看懂 App Router 專案裡的三種層次：頂層的三類檔案、app/ 的檔案公約，以及 route group 分出的不同 shell。下一步要做的，就是把這套架構轉成實際判斷：當 AI 丟來一段新 feature 時，依序問自己該放在哪一層，才能讓功能和版型各自待在適合的位置。
