app/ 裡的檔案公約：page、layout 與 globals

Step 2/4 · 專案結構與分層：feature 放哪裡

學習目標

學完這一節，你應該能分辨 app/ 裡幾個固定角色：page、layout、globals.css、fonts/ 與 favicon。你也會看懂 root layout 如何透過 children，把所有路由內容放進同一個全站外框。

先看大圖：app/ 是靠檔名工作的

上一節我們把頂層檔案分成三層，知道 app/ 是每天開工的主房間。現在走進這個房間，你通常會看到幾個名字很固定的成員：page.tsx、layout.tsx、globals.css，以及 fonts/ 和 favicon.ico。

不論你新增幾條路由，這些檔名都不太會變。因為 App Router 採用的是「檔案即公約」：它不需要另外一份設定檔，來說明哪個檔案對應哪個畫面。只要檔名正確、位置正確，Next.js 就知道它該扮演什麼角色。

可以先把整體關係想成一棟房子：

  • page.tsx 是某個房間真正展示的內容。
  • layout.tsx 是共用的牆面、走道與門框。
  • globals.css 是整棟房子的共同裝潢規則。
  • fonts/ 是專案自己攜帶的字型資源。
  • favicon.ico 是瀏覽器分頁上那塊小招牌。

接下來分別看它們如何合作。

page 與 layout：一個負責內容，一個負責外框

page.tsx 代表「這個路由要顯示什麼」。放在 app/page.tsx，它對應網站根路由 /，也就是首頁；放在 app/about/page.tsx，它就對應 /about。

換句話說，資料夾路徑決定網址，資料夾裡的 page.tsx 決定這個網址要畫出什麼。資料夾像地址，page.tsx 則像送到那個地址的內容。

layout.tsx 的任務不同。它是包住底下路由的共用外框，並且會收到一個 children 參數。這個 children 就是目前路由該顯示的頁面內容。

例如，你可以把 navbar 寫在 layout 裡，再把 {children} 放在 navbar 後面。如此一來，所有子路由都會自動出現在 navbar 下方。共用的東西只要寫一次，版型更新時也只要改一個地方。

AI 常犯版 vs 正解版：navbar 到底該放哪裡？

AI 常犯版：每一頁都各自 import navbar。

這種寫法表面上能跑，但每一頁都得重複寫 import。新增頁面時，還可能忘記補上 navbar；將來要改整體版型，也得逐頁修改。就像每間房子都各自蓋一扇相同的門，門的設計一改，就要跑遍整棟房子。

正解版：把 navbar 放進對應的 layout.tsx，讓頁面內容透過 children 放到它下面。

判斷方式可以很簡單：先問自己「這個東西是這一頁專屬，還是這一區所有頁面共享？」前者放在 page.tsx，後者放在 layout.tsx。這個問題比死記規則更實用。

用真實專案看 root layout

最頂層的 layout.tsx 稱為 root layout，是所有路由共用的最外框。以下是 DevFlow 專案的 root layout：

import type { Metadata } from "next";
import localFont from "next/font/local";
import { SessionProvider } from "next-auth/react";
import { ReactNode } from "react";

import "./globals.css";
import { auth } from "@/auth";
import { Toaster } from "@/components/ui/toaster";
import ThemeProvider from "@/context/Theme";

const inter = localFont({
  src: "./fonts/InterVF.ttf",
  variable: "--font-inter",
  weight: "100 200 300 400 500 700 800 900",
});

const spaceGrotesk = localFont({
  src: "./fonts/SpaceGroteskVF.ttf",
  variable: "--font-space-grotesk",
  weight: "300 400 500 700",
});

export const metadata: Metadata = {
  title: "DevFlow",
  description:
    "A community-driven platform for asking and answering programming questions. Get help, share knowledge, and collaborate with developers from around the world. Explore topics in web development, mobile app development, algorithms, data structures, and more.",
  icons: {
    icon: "/images/site-logo.svg",
  },
};

const RootLayout = async ({ children }: { children: ReactNode }) => {
  const session = await auth();

  return (
    <html lang="en" suppressHydrationWarning>
      <head>
        <link
          rel="stylesheet"
          type="text/css"
          href="https://cdn.jsdelivr.net/gh/devicons/devicon@latest/devicon.min.css"
        />
      </head>
      <SessionProvider session={session}>
        <body
          className={`${inter.className} ${spaceGrotesk.variable} antialiased`}
        >
          <ThemeProvider
            attribute="class"
            defaultTheme="system"
            enableSystem
            disableTransitionOnChange
          >
            {children}
          </ThemeProvider>
          <Toaster />
        </body>
      </SessionProvider>
    </html>
  );
};

export default RootLayout;

從外到內讀這個檔案

讀 root layout 時，可以先不要急著逐行看。先抓住它的骨架：它回傳最外層的 <html> 與 <body>，而 {children} 被放在這些外框裡。這代表所有路由頁面，最後都會被放進同一個 HTML 結構中。

接著看它集中處理了哪些全站共用的事情。

  • import ./globals.css，載入整個網站共用的樣式。
  • 透過 next/font/local 載入專案內的字型。
  • export metadata，設定瀏覽器分頁標題、描述與 icon。
  • 使用 SessionProvider 提供登入狀態。
  • 使用 ThemeProvider 提供深色與淺色主題。
  • 使用 Toaster 顯示全站可用的通知訊息。

這些功能之所以適合放在 root layout，是因為它們不是某一頁的專屬內容，而是多數甚至所有頁面都可能需要的基礎設施。root layout 就像大樓的總電箱：各房間不必自己再裝一套，接上同一套供應就能使用。

children 為什麼是關鍵？

在這段程式中，RootLayout 接收的參數是 { children }: { children: ReactNode }。其中 children 不是固定寫死的某一頁，而是 Next.js 根據目前 URL，放進來的路由內容。

這也是 provider 常見的包法：

SessionProvider 包住 body，ThemeProvider 再包住 {children}。因此，任何頁面都能取得登入狀態與主題設定；頁面本身不需要一再建立相同的 provider。

AI 常犯版：把 provider 分散貼到各個 page.tsx，或只包住某一個頁面。

正解版：只要狀態是全站或某個路由區域共用，就放到相應的 layout，讓 children 自動繼承這層環境。provider 的位置決定它能影響哪些頁面。

一個檔案也能同時描述資料與畫面

這個檔案還示範了另一個重要觀念：同一個 layout.tsx 可以同時 export metadata 與預設的 RootLayout。

Next.js 會把它們分開理解：metadata 是這個 layout 的中繼資料，預設 export 的 RootLayout 則是這個 layout 要呈現的畫面結構。你不需要另外註冊它們，檔名、所在位置與 export 方式就是框架辨認角色的線索。

其餘三個配角：樣式、字型與網站招牌

globals.css 是全站樣式的入口。Tailwind 的匯入、全站變數與通用 utility class 都可以放在這裡。因為 root layout 會 import 它，所以整個網站都能使用這些規則。想改全站的字體、顏色或共用樣式，通常先從這個檔案找起。

fonts/ 用來存放字型檔。DevFlow 把需要的字型放在專案裡，再用 next/font/local 載入，而不是每次向 Google Fonts 這類外部服務請求。這樣可以少一次外部請求，載入更加穩定，也就是自己 host 自己的字型。

favicon.ico 則是瀏覽器分頁上的小圖示。它的面積很小，卻像店門口的招牌；換掉它，就等於換了網站在瀏覽器分頁上的門面。

把角色放回正確的位置

檔案或資料夾 負責什麼 判斷方式
page.tsx 顯示某個路由的頁面內容 這個內容是不是這一頁專屬？
layout.tsx 包住一個路由區域的共用外框 這個元件是不是同一區頁面共享？
globals.css 提供全站共用樣式 這條樣式是不是整個網站都可能使用？
fonts/ 存放專案使用的字型檔 這是網站共用的字型資源嗎？
favicon.ico 設定瀏覽器分頁圖示 這是網站的識別圖示嗎？

把觀念接起來

app/ 靠檔名決定角色：page.tsx 是某個路由要顯示的內容，資料夾路徑決定網址；layout.tsx 是包住子路由的共用外框，透過 children 把底下內容嵌進來；globals.css 是全站樣式；fonts/ 與 favicon.ico 是資源。root layout 是唯一的全站最外框，字型、metadata、provider 這些跨頁面的東西都該放在這一層，而不是每一頁重貼一次。

到這裡，可以把 page 與 layout 放在同一張心智地圖上：page 提供內容，layout 提供內容所處的環境；資料夾則把這份內容和 URL 接起來。知道這三者的關係後，下一個問題自然會出現：同一個 app 裡，能不能讓登入頁與問答主站使用完全不同的版型，卻不改變 URL？這就要靠 route group 了。
