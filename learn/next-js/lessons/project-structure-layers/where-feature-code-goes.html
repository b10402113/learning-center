新 feature 該放哪裡：一層一層問下去

Step 4/4 · 專案結構與分層：feature 放哪裡

前言：AI 寫完了，但檔案放對了嗎？

前三步你已經會讀 App Router 專案的結構。現在換一個更常見的情境：你請 AI 加一個新功能，它很快就產出程式碼；但到了 review，你卡住的可能不是邏輯，而是「這段東西為什麼放在這個檔案？」

AI 可能把全站都需要的 provider 塞進某一區的 layout.tsx，也可能為了一個只用一次的卡片建立完整資料夾。更常見的是，所有東西一路堆進 page.tsx，最後頁面像塞滿雜物的抽屜，能動，但沒人敢整理。

所以這一課要練的不是背資料夾名稱，而是做判斷。放得太集中，檔案會變得臃腫；放得太分散，一個小功能又會散落五、六個資料夾。接下來我們會先比較各層的用途，再用幾個可測試的問句判斷位置，最後看規則什麼時候會翻轉。

學習目標

看到一段新 feature code 時，你能判斷它應該放在頂層設定、app/ 路由、可重用元件，還是資料與工具層；同時也能用「AI 常犯版 vs 正解版」檢查自己的決定。

先攤開選項：每一層各自負責什麼？

App Router 專案裡，程式碼通常會落在以下幾層。先把差異並列，之後遇到新功能，就比較不會只憑直覺亂放。

層典型位置什麼時候放這裡放錯的代價
設定與依賴層next.config.ts、tsconfig.json要改整個專案如何建置、啟動或檢查時把應用邏輯塞進來，責任不清楚，也難以測試
路由內容層app/.../page.tsx畫面只屬於某一條 URL 時頁面專屬的內容被硬抽出去，閱讀時要多繞好幾層
區塊外框層app/.../layout.tsx同一區的多個頁面都要共用外框時版型重複貼在多個頁面，修改一次要改很多地方
共用元件層components/...UI 已經會跨頁面或跨區塊重用時可能重複實作、樣式不一致；也可能太早抽象，反而增加負擔
邏輯與資料層lib/、database/、actions/不碰畫面，只處理資料存取、驗證或商業邏輯時查詢與規則散落各頁，重複又難維護、難測試
靜態資源層public/圖片、字型、favicon 等要原樣提供的檔案把需要經過打包的程式碼放進來，程式取用不到

判別問句：從外圍一路往內問

這些問題要依序回答。前面的層比較像專案的外圍，一旦符合，就不必再往下猜。

第一問：這東西會影響整個 app 如何建置、啟動或檢查嗎？

如果會，它屬於頂層設定層。例如新增 webpack 別名、調整圖片網域，都會影響整個專案。這一層平常不常修改，但每次修改的影響範圍都很大。

第二問：它會出現在畫面上嗎？如果會，只屬於一條 URL，還是同一區的多個頁面？

只屬於某一條網址，就放在該路由的 page.tsx。如果同一個區塊的多個頁面都需要，就放在那一層的 layout.tsx。前一節提到的 navbar，就是適合放在共用 layout 的例子。

第三問：它是純 UI，而且已經在別的頁面或區塊出現了嗎？

如果確實會被重用，就可以抽到 components/。注意判準是「已經有第二個使用場景」，不是「未來可能會用到」。先有真實的重複，再抽象化，通常比預先猜測更穩妥。

第四問：它完全不碰畫面，只處理資料、驗證或商業邏輯嗎？

如果是，就放到 lib/、database/ 或 actions/。資料庫查詢、Schema 驗證與共用 helper，都不應該混在頁面元件裡。

反例：規則什麼時候會翻轉？

這套問句可以幫你快速定位，但不能機械式套用。以下幾種情況，正是規則需要翻轉的地方。

只有「可能」重用，不代表現在就要抽。如果一個卡片目前只有一個頁面使用，先留在該頁的檔案裡。等第二個地方真的需要它，再抽到 components/。太早抽象，等於要維護一個只有單一使用者的「共用」元件，還可能多出 props 與邊界處理，成本反而更高。

可以用這句話檢查：現在有第二個真實的使用場景嗎？有，才抽；只有想像中的未來需求，先不要。

抽成共用元件後，它就不該認識特定頁面的資料。共用元件比較健康的形狀是「接收 props，輸出畫面」，由呼叫它的頁面負責準備資料。如果一個號稱共用的元件裡寫死某支 API 的回應格式，它其實只是被搬到另一個資料夾的頁面專屬程式碼。

全站都需要的東西，不能降級到某一區。登入狀態、主題這類每個頁面都需要的 provider，如果放進 (root) 以外的區域 layout，(auth) 底下的頁面就可能拿不到。這種跨全站的關注點，必須放在 root layout，而不是某個局部區塊。

資料存取也不要用「各頁自己處理」當作理由散落各處。如果好幾個 page.tsx 都寫了一段一模一樣的資料庫查詢，那不是保持頁面自足，而是把 lib/ 應該負責的工作複製了好幾份。查詢與驗證應該集中在邏輯層，頁面只負責呼叫並呈現結果。

AI 常犯版 vs 正解版：navbar 該放哪裡？

拿最常見的 navbar 來看，會更容易判斷 AI 產出的結構是否合理。以下是常見的 AI 寫法：把 navbar 分別放進每一個頁面。

// AI 常犯版：每一頁各自 import 一次
// app/(root)/page.tsx
import Navbar from "@/components/navigation/navbar";
export default function Home() {
  return (
    <>
      <Navbar />
      <main>...</main>
    </>
  );
}

// app/(root)/questions/page.tsx
import Navbar from "@/components/navigation/navbar";
export default function Questions() {
  return (
    <>
      <Navbar />
      <main>...</main>
    </>
  );
}

這段程式碼不一定會立刻壞掉。真正的問題是：每新增一頁，就要記得再貼一次；navbar 要改版時，也得逐頁檢查。重複像是水槽裡慢慢累積的碗，第一個不麻煩，數量一多就很難收拾。

如果 navbar 是這一區所有子頁面都需要的外框，就應該放到該區的 layout：

import Navbar from "@/components/navigation/navbar";

const RootLayout = ({ children }: { children: ReactNode }) => {
  return (
    <main>
      <Navbar />
      {children}
    </main>
  );
};

同一個 navbar，放到正確層次後，重複消失，修改一處就能影響整個區域。這就是「feature 放哪裡」的實際價值：不是為了讓資料夾看起來整齊，而是讓責任範圍和重用關係清楚。

帶走一條可直接使用的規則

看到新 code 時，依序問：它會影響整個 app 的建置嗎？會的話放頂層設定；它只屬於一條 URL，還是整區共用？前者放 page，後者放 layout；它是純 UI 且已經被第二處使用嗎？是才放 components/；它完全不碰畫面嗎？放到 lib/、database/ 或 actions/。最後再檢查四個反例：只有一個使用者先別抽、共用元件只吃 props、全站關注點不能放進局部區塊、資料查詢不要散落各頁。
