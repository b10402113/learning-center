新程式碼該放哪？檔案配置的抉擇

Step 4/4 · App Router Anatomy

學習目標

拿到一個新需求時，能判斷它該放進 layout、page、app/ 子資料夾、public/ 還是設定檔，並說出這樣放的理由。

前言：需求來了，第一個問題不是怎麼寫，而是放哪裡

想像你接手一個專案，PM 丟來三個需求：加一個全站都看得到的通知鈴鐺、加一張首頁的活動主視覺、加一個只有登入後才進得去的個人頁面。你打開編輯器，游標在檔案樹上游移，心裡冒出一個很現實的掙扎：隨便找個檔案塞進去，五分鐘就能交差；但要放對位置，得先想清楚它屬於誰。

這個「放哪裡」的決定，往往是 AI 生成架構最常做錯、也最難第一眼看出來的地方。放錯位置不是語法錯誤，程式照樣會跑，但代價會在後面慢慢顯現：一個只有某頁需要的東西被塞進 root layout，讓每頁都多背一段程式碼；一個本來該是元件的檔案被命名成 page.tsx，意外多出一條網址；一張圖放錯資料夾，導致它沒辦法被最佳化。這一節要把這個決定變成一條你可以當場套用的規則。

選項比較：需求型態對應的放置位置

先看全貌。下面這張表把常見需求對應到正確的位置，以及背後的理由。你可以把它當成遇到新東西時的第一站查詢。

需求型態放哪裡為什麼
每頁都出現的 UI（Navbar、Footer、Toaster）app/layout.tsxlayout 套用到它底下的所有路由
全站共用的 Provider（主題、Session）app/layout.tsx，包住 {children}所有頁面才拿得到這層 context
某一條路徑的內容該路徑的 page.tsxpage 只代表那一條路徑
全新的頁面或網址app/ 下開新資料夾加 page.tsx資料夾結構就是路由
靜態素材（圖片、logo、字型、影片）public/不需編譯、自動最佳化、全站可引用
全站樣式app/globals.cssCSS 變數與主題集中在全域檔
單一元件專屬樣式該檔案旁的 *.module.css作用範圍被鎖在那個元件
可重用的 UI 元件專案根目錄的 components/放 app/ 外才不會被當成路由
Next.js 或建置設定next.config.ts 等設定檔設定是專案層級的行為開關
密鑰與環境變數.env（已被 .gitignore 排除）避免機密被提交進版本控制

附帶一個常見的誤解：不是所有共用元件都該放在app/裡面。App Router 會把app/內的檔案和資料夾解讀成路由的一部分，所以一個單純的 Button.tsx放進去，可能讓結構變得混亂、甚至被誤認為路由。慣例是把可重用元件放在專案根目錄的components/，讓app/專心處理路由與頁面。

判別問句：拿到需求時先問這幾句

當你不確定該放哪裡，別急著憑感覺。問自己這四個問題，答案會把位置逼出來。

第一句：這個東西會出現在幾條路由上？如果每一頁都要它（導覽列、頁尾、全站通知），那是 layout 的責任。如果只有某一頁要，那它屬於那一頁的 page。這是最有殺傷力的一個問題，因為範圍判斷錯了，後面全錯。

第二句：它是一條「網址」，還是一塊「畫面零件」？如果你希望使用者能輸入某個路徑、或點連結跳過去，那就是一條路由，該在app/下建立資料夾與page.tsx。如果它只是被別的頁面拿來組裝的零件（按鈕、卡片、表單），那它是元件，不該變成網址。

第三句：這個檔案會不會被 Next.js 當成路由？在app/裡，每個資料夾都可能對應一段網址。所以不要把工具函式、型別定義或元件隨手丟進app/，更不要把它們命名成page.tsx，否則你就憑空多出一條沒人預期的路由。

第四句：改了它，會影響誰？如果影響的是全站，它該在 layout 或globals.css；如果只影響一個元件，就留在它自己的檔案或*.module.css裡。這個問題幫你確認「影響半徑」有沒有放對層級。

反例：這些看似合理的做法，其實是陷阱

規則講完了，但真正會讓你踩雷的，往往是那些「聽起來很合理」的做法。以下三個是 AI 產出裡最常見的配置錯誤。

反例一：把「所有共用」都丟進 root layout

既然 layout 是全站共用，那把每個頁面可能用到的東西都塞進去不就好了？不行。root layout 是最外層，塞進去的每個 client 元件、每個 Provider，都會被綁進所有頁面的渲染路徑。更常見的情境是：登入頁不需要 Navbar，但你把 Navbar 寫死在 root layout，於是登入頁也長出了導覽列。正確做法是用路由群組（資料夾名用括號，例如(auth)）替不同群組各自安排 layout，讓登入頁有自己的乾淨外框，而不是硬改 root layout。

// 反例：登入頁被迫帶著全站 Navbar
app/layout.tsx        // 放了 ，所有頁面都吃
app/sign-in/page.tsx  // 結果登入頁也出現 Navbar

// 正解：用路由群組分開外框
app/(root)/layout.tsx // 有 Navbar 的主應用
app/(auth)/layout.tsx // 乾淨的登入註冊外框

反例二：把 helper 命名成 page.tsx

你寫了一個格式化日期的小函式，想說「放在app/裡比較好找」，就存成app/formatDate.tsx。多數情況下它不會變成路由，但只要你手滑命名成page.tsx又放進某個資料夾，Next.js 就會認真把它當成一條頁面路由。工具函式、型別、常數請放在app/之外，例如lib/或utils/。

反例三：把全站 Provider 只放在某個 page

反過來，如果你需要全站共享的主題或登入狀態，卻只把它包在某個 page 裡，其他頁面就拿不到這層 context，會出現「這一頁正常、另一頁報錯」的詭異現象。判斷原則很簡單：只要它是跨頁面共享的狀態，就該包在 root layout 的{children}外層，而不是某一頁裡面。

小結

面對「東西該放哪」，依序問四個問題：一、它會出現在幾條路由上（範圍）？二、它是一條網址還是一塊零件（身分）？三、它會不會被當成路由（命名）？四、改了它會影響誰（影響半徑）？全站共用放 layout、單頁內容放 page、可重用元件放 components/、靜態素材放 public/、全站樣式放 globals.css、機密放 .env。切記兩個反例：別把所有共用都塞進 root layout，也別把全站狀態只包在單一 page 裡。

這條「先問範圍、再問身分」的規則，正是你之後審查 AI 架構時最有用的第一把尺。當你能指著一個陌生的專案，說出「這個東西放錯層級了、因為它只在某一頁用到」，代表你已經有能力從檔案結構讀出設計意圖。整個 App Router Anatomy 節點到這裡結束，你手上已經有了專案頂層地圖、layout／page／children 的渲染樹、跑起來驗證的開發迴圈，以及這份配置決策表。
