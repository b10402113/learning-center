渲染的三條軸線：環境、時間與 runtime

Step 1/5 · 執行環境與渲染策略：Node / Edge、SSG / ISR / SSR / PPR

先想一個問題：這個頁面到底在哪裡、什麼時候算出來？

打開一份 AI 產出的 Next.js 專案，你可能會在某個 route 檔案頂端看到一行孤零零的設定：export const runtime = 'edge'。另一個頁面則可能寫著 export const revalidate = 60。

這些設定看起來只是幾個字，卻會影響頁面「在哪裡被算出來」以及「什麼時候被算出來」。如果不知道它們正在切換哪個開關，你只能照抄 AI 的答案，卻無法判斷這個選擇是否合理。

這一節先把整張座標圖攤開來：第一條軸線是環境，第二條軸線是時間，第三條軸線則是 runtime。後面不管要選 SSG、ISR、SSR，還是決定使用 Node 或 Edge，本質上都是把渲染放到這張圖的不同位置。

學習目標

學完這一節，你應該能說明 rendering 是什麼，並用三條軸線定位任何一段渲染：

  • 環境：client 或 server，誰負責渲染？
  • 時間：build time 或 run time，什麼時候渲染？
  • runtime：Node 或 Edge，程式在哪一種執行環境中運作？

你也會知道 SSG、ISR、SSR 與 PPR 各自落在這些軸線的什麼位置。

渲染是什麼：把程式碼變成畫面

渲染（rendering）就是把我們寫的程式碼，轉換成使用者眼前看得見的介面。你寫的是 React 元件、資料與樣式；使用者看到的，則是瀏覽器裡的一個頁面。中間那個「把程式碼變成畫面」的過程，就是渲染。

關鍵在於：這個過程可以在不同的地方、不同的時間發生。同樣一份程式碼，如果在 build 時就先算好，和每次有人打開網頁才重新計算，結果、速度與成本都會不同。

Next.js 的價值，就在於它讓你可以針對同一份 code，選擇渲染要在哪裡、何時發生。

第一條軸線：環境——誰來渲染？

第一個問題是：渲染發生在哪裡？基本上有兩個選項：client 與 server。

在 client 渲染時，使用者的瀏覽器會先拿到程式碼，再自行把畫面組出來。Server 渲染則是由部署程式碼的 server 先算好畫面，再把結果送到瀏覽器。

可以把它想成兩種出餐方式：client 渲染像是把食材與食譜送到客人家裡，客人自己完成料理；server 渲染則像是廚房先把餐點做好，再把成品送出去。兩種方式都能端出餐點，但負擔與等待時間落在不同地方。

面向Client 渲染Server 渲染
渲染過程在使用者的瀏覽器上發生在 server 上發生，算完才把頁面送給瀏覽器
互動性與載入時間動態、互動體驗好送出完整 HTML，首次載入更快
抓資料與 SEO換頁順、能即時抓資料完整內容有助搜尋排名與社群分享預覽
負載與效能降低 server 負載、可能降低主機成本在慢裝置上也跑得好，因為計算發生在 server
一致性相容性與效能取決於使用者的裝置跨裝置較一致，減少相容性問題
安全有 XSS、程式碼注入、資料外洩的風險送到瀏覽器的 JavaScript 較少，風險較低

AI 常犯版：只要互動，就全部丟給 client

這種判斷把「互動性好」當成唯一標準，卻忽略了 SEO、首次載入速度與使用者裝置差異。它看起來很直覺，但不一定適合每一種頁面。

正解版：先看頁面的優先事項

如果 SEO、安全與裝置規格都不是優先事項，而你只想把互動功能做好，client 渲染可能就足夠。典型例子是 B2B 產品：使用者是特定、已知的一群人，不需要對大眾曝光，也不一定需要花力氣在 SEO 上，因此可以把資源集中在互動體驗。

反過來，如果你在意搜尋排名、社群分享預覽、首次載入速度，以及不同裝置上的一致性，判斷通常會往 server 渲染靠近。重點不是 client 或 server 永遠誰勝出，而是先問：這個頁面最需要解決什麼問題？

第二條軸線：時間——什麼時候渲染？

第二個問題是時機。Next.js 應用程式在編譯完成後，可以從兩個時間點來理解：build time 與 run time。

Build time 是開發者準備上線的階段。這時會編譯程式碼、打包、最佳化，並可能先產生頁面。你熟悉的 npm run dev 或 npm run build，就是在處理這個階段。可以把它記成：「你在編譯的時間」。

Run time 則是應用程式已經部署、實際服務使用者的階段。這時程式會處理使用者輸入、回應事件、存取資料，以及呼叫外部 API。換句話說，run time 是「使用者在跑你的程式」的時間。

AI 常犯版：看到 runtime，就當成 run time

這是很常見的混淆。兩個詞只差幾個字母，中文也都常翻成「執行」，但它們指的不是同一件事。

正解版：一個是時間，一個是平台

Run time 指的是應用程式正在執行的那段時間；runtime environment 則是程式執行時所依賴的平台，也就是提供函式庫、服務與執行元件的那套系統。

可以把它想成拍電影：run time 比較像「電影正在拍攝的時段」；runtime environment 則像「拍攝所使用的攝影棚與設備」。一個回答什麼時候發生，一個回答在哪種環境裡發生。

第三條軸線：runtime——程式在哪個環境執行？

你可能已經認識其中一個 runtime environment：Node.js。它是一個 JavaScript 執行環境，讓我們可以在瀏覽器之外執行 JavaScript。

Next.js 提供兩種 runtime 可以選擇：

  • Node.js runtime：預設值，能存取完整的 Node.js API 與生態系。
  • Edge runtime：輕量版，以 Web API 為基礎，只支援一部分 Node.js API。

切換方式很簡單，只要修改這一行：

export const runtime = 'edge' // 'nodejs' (default) | 'edge'

這行放在檔案頂端後，整個 route 的執行環境就會切換。預設是 Node.js，寫上 'edge' 才會改用 Edge。

AI 常犯版：runtime 只是部署平台的偏好

如果把 runtime 當成部署時隨手挑的設定，就會漏掉它真正影響的事情。同一段程式碼放在不同 runtime 中，能使用的 API 與延遲表現可能完全不同。

正解版：先確認程式需要哪些能力

runtime 決定程式可以依賴哪些執行能力。Node.js 能提供完整的 Node.js API 與生態系；Edge 則比較輕量，主要建立在 Web API 上，只支援一部分 Node.js API。

因此，export const runtime = 'edge' 不是裝飾性的設定，而是在告訴 Next.js：「這個 route 要放到 Edge runtime 執行。」至於兩者在能力與延遲上的取捨，會在第 4 步專門說明。

把四種渲染策略放上座標

現在把三條軸線疊起來，就能定位 Next.js 常見的伺服器渲染策略。它們主要都落在 server 這一側，差別在於頁面何時產生，以及之後如何更新。

策略什麼時候產生更新方式一句話定位
SSG（Static Site Generation）build time重新建置先做好、快取後，原封不動送出
ISR（Incremental Static Regeneration）build time，之後可再生成時間到或收到指令時先做好，但可以事後補更新
SSR（Server-Side Rendering）每次請求每次都是新的每個 request 現算
PPR（Partial Prerendering）build time 先做外殼，動態部分再串流混合同一頁裡同時存在靜態與動態部分

AI 常犯版：四種策略是四選一

如果把 SSG、ISR、SSR 與 PPR 當成互斥開關，就會以為整個應用程式只能選一種策略。但渲染策略描述的是頁面或區塊如何產生，不一定要整個應用程式統一使用同一種方式。

正解版：依頁面與區塊放到不同位置

這四種策略可以依頁面、依區塊分別套用。同一個應用程式裡，首頁使用 SSG、文章列表使用 ISR、會員專區使用 SSR，完全可以成立。PPR 則讓同一頁裡的靜態外殼與動態內容並存。

此刻先記住它們在座標上的相對位置即可。各自的運作機制、快取位置與適用情境，會在下一節再逐一拆開。

小結：把觀念掛回同一張地圖

渲染是把程式碼變成介面的過程，而 Next.js 讓你決定它發生的地點與時機。地點有 client 與 server；時間分成 build time（開發者建置時）與 run time（使用者執行時）；程式執行的平台則有 Node 與 Edge 兩種 runtime。把這三條軸線疊起來，SSG、ISR、SSR 與 PPR 就各自有了位置。它們都是 server 側的策略，差別在於什麼時候產生，以及之後怎麼更新。

所以，看到 runtime 時，先問它指的是哪一種執行平台；看到 SSG、ISR、SSR 或 PPR 時，則回到同一張座標圖，確認頁面是在什麼環境、什麼時間產生，以及內容如何更新。座標畫好之後，後面的技術取捨才有地方可以掛上去。
