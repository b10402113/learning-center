挑選渲染策略：內容多久變一次，要不要即時更新？

Step 3/5 · 執行環境與渲染策略：Node / Edge、SSG / ISR / SSR / PPR

先想像你正在決定一頁怎麼送出去

同樣是一個 Next.js 頁面，有些內容幾個月都不會變，有些資料卻可能每秒更新；有些區塊對所有人都一樣，有些則是登入後才看得到的個人資料。把它們全部用同一種方式產生，就像不管食材熟不熟，都只用同一個火候：不是浪費資源，就是把內容煮錯。

這一節要處理的決定很明確：一個頁面該用 SSG、ISR、SSR，還是 PPR？判斷的兩股拉力是內容多久變一次，以及是否需要即時、甚至秒級更新。

學習目標

學完後，你應該能依照「這頁每次請求的內容是否相同」與「是否需要秒級更新」這兩個問題，選出 SSG、ISR、SSR 或 PPR，說明選擇理由，也能看出 AI 一律使用預設 SSG 或一律使用 SSR 時，問題會出在哪裡。

先攤開選項：四種策略怎麼取捨？

上一節已經介紹過四種策略的機制。現在先不要背名詞，把它們放在同一張表裡，看清楚每一種策略要付出的代價：

策略產生時間內容新鮮度server 負載最適合
SSGbuild time上線後固定，內容變更時需要重新建置最低幾乎不變的內容
ISRbuild time，之後可以再次生成依時間或需求更新低到中偶爾變動的內容
SSR每次請求永遠取得最新內容最高即時、因人而異的內容
PPR外殼在 build time 產生，動態內容再串流靜態部分固定，動態部分即時中同一頁混合靜態與動態內容

這張表可以先濃縮成一個方向感：內容越固定，就越靠近 SSG；內容越即時、越因人而異，就越靠近 SSR。 如果一頁裡同時有這兩種內容，PPR 通常更符合實際情況。

先比較兩種常見寫法

AI 常犯版：所有頁面都套預設 SSG。

這種寫法看起來簡單，也能讓頁面很快送出，但只要頁面包含登入後的使用者資料，就可能把某個人的內容快取住，接著原封不動送給另一個人。這不是單純「資料晚一點更新」而已，而是正確性與安全問題。

正解版：先看資料的變動方式，再選渲染策略。

幾乎不變的內容用 SSG；偶爾變動的內容用 ISR；需要即時或因人而異的內容用 SSR；同一頁混合靜態與動態區塊時，則考慮 PPR。策略不是頁面的裝飾，而是跟資料本質綁在一起的選擇。

兩個判別問句

Next.js 官方的選擇流程，可以化成兩個問題。請把它們當成做決定時的分岔路口：

  1. 這個頁面或內容，每次請求顯示的資訊都一樣嗎？ 如果是，使用 SSG；如果不是，進入下一題。
  2. 這個頁面或內容需要頻繁更新，甚至可能每秒都在變嗎？ 如果是，使用 SSR；如果不是，使用 ISR。

這套問法的好處是，它不會把你帶進「哪種技術比較潮」的討論，而是直接回到資料本身：資料是否固定？多久可以接受一次更新？

如果同一個頁面同時有「幾乎不變」和「隨時在變」的區塊，就不要硬把整頁塞進 SSG 或 SSR。這時可以考慮 PPR，先送出靜態外殼，再補上動態區塊。

把判斷套進真實情境

以高流量的電商平台為例。它的頁面通常不是一種資料從頭撐到底，而是好幾種不同速度的資料拼在一起：

  • 商品詳情頁的標題、描述、圖片：幾乎不變，適合用 SSG，甚至可以放到 CDN。
  • 價格、庫存、銷量：會隔一段時間變動，適合用 ISR，並設定合理的重新驗證時間。
  • 購物車、推薦、個人化區塊：每位使用者都不同，而且需要即時資料，適合用 SSR。
  • 如果以上區塊都在同一頁：使用 PPR，讓靜態外殼先送達，動態區塊再串流補上。

再看兩個對照案例：

登入後的會員儀表板內容因人而異，也需要即時更新，因此答案偏向 SSR。如果想讓儀表板外框保有較快的回應速度，可以考慮 PPR。

相反地，一篇發布後幾乎不會修改的技術文章，適合使用 SSG。文章列表則可能偶爾增加新文章，因此可以讓列表使用 ISR。

反例：什麼時候規則會翻轉？

判準不是背熟後就能無條件套用。以下幾種情況，正是 AI 很容易判斷錯的地方。

反例一：SSG 最快，不代表永遠該用 SSG。

需要登入、內容因人而異的頁面，如果使用 SSG，就可能把 A 使用者的資料快取起來，再送給 B 使用者。這時候問題已經不是效能，而是內容正確性與安全性。速度再快，資料送錯人仍然是失敗。

反例二：SSR 永遠最新，不代表它是萬靈丹。

行銷頁或文件頁如果根本不會變，卻每次請求都使用 SSR，就等於不斷重跑沒有必要的工作，也讓快取失去作用。它確實能保證內容最新，但如果內容本來就不需要更新，這份「最新」並沒有帶來價值。

反例三：runtime 不是渲染策略。

選擇 Edge runtime，不會自動讓頁面變成 SSG；選擇 SSG，也不會自動決定程式要跑在 Edge。這是兩條不同的軸：

  • 渲染策略決定內容什麼時候產生。
  • runtime 決定程式在哪個執行環境運作。

把兩者混在一起，就可能寫出「使用 Edge，所以這是 SSG」或「用 Edge 加速 SSR」這類看似合理、實際上沒有回答渲染策略的判斷。

反例四：ISR 的重新驗證時間不能隨便填。

如果資料半小時才變一次，卻把 revalidate 設得非常短，就會頻繁重新生成，失去 ISR 原本想節省資源的意義。設得太長，使用者又可能看到明顯過期的內容。

重新驗證時間應該對齊一個實際問題：你最多能接受資料舊多久？ 這個答案才是設定數值的依據，而不是隨手填一個看起來合理的數字。

可操作的決策規則

做決定時，可以依序檢查下面幾項：

  • 每次請求的內容都一樣嗎？是的話，用 SSG。
  • 需要秒級即時更新嗎？是的話，用 SSR。
  • 內容介於兩者之間、只是偶爾變動嗎？用 ISR，並依照資料能容忍的過期時間設定重新驗證。
  • 同一頁同時有靜態與動態區塊嗎？考慮使用 PPR。
  • 渲染策略選定後，再另外判斷程式碼該跑在 Node 還是 Edge；這是下一節要處理的問題。

小結

選渲染策略時，先問兩件事：每次請求的內容都一樣嗎？需要秒級更新嗎？前者指向 SSG，後者指向 SSR；如果內容會變、但不需要即時更新，就使用 ISR。同一頁同時混有靜態與動態區塊時，則考慮 PPR。最常見的錯誤，是把因人而異的內容用 SSG 快取、把永不改變的頁面用 SSR 硬算，以及把 runtime 誤當成渲染策略。

到這裡，你已經能處理「內容什麼時候產生」這條軸。接下來還有另一個決定：同一段 route，究竟該讓它在功能完整的 Node 上執行，還是搬到離使用者更近的 Edge？
