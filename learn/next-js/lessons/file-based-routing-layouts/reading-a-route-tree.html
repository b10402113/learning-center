由 URL 反推檔案樹：抓出 AI 路由結構的錯

Step 5/5 · 檔案式路由、layout 與 route groups

學習目標

你將能在「URL」與「app/ 檔案樹」之間雙向推理，找出會造成錯誤網址、404、路徑衝突或重複 layout 的結構問題。

前言：驗收 AI 專案，先確認網址和檔案樹對不對

前面四步，你已經看過資料夾如何對應網址、動態段如何表示不固定的值、layout 如何一層層套上去，以及 route group 如何分區卻不改變網址。現在把這些規則放在一起，處理一個很實際的場景：驗收 AI 產出的 Next.js 專案。

AI 很會補出程式邏輯，卻常在路由結構上踩雷。它可能把括號用錯、漏掉 page.tsx，或把同一條路徑放進兩個 route group。這些問題未必會讓 build 失敗，網站甚至還能正常啟動；但網址可能和需求不同，畫面也可能莫名多出一層外框。

所以真正要做的決定是：看到一個路徑時，這裡該用一般資料夾、動態資料夾，還是 route group？而看到一棵檔案樹時，它實際會產生哪些 URL？接下來用兩個方向互相驗證，讓錯誤像藏在地圖上的岔路一樣，自動浮出來。

先比較：三種資料夾，各自該負責什麼

寫法會不會出現在 URL適合用在什麼情況判斷方式
一般資料夾，例如 questions/會這一段本身就是網址的一部分，例如 /questions問自己：需求中的 URL 是否真的需要這個名稱？
動態資料夾，例如 [id]/會，但內容可變每次 URL 都可能不同，例如 /questions/123問自己：這一段是不是每次都不同的值？
route group，例如 (auth)/不會想把頁面分區或共用外框，但不想讓區域名稱出現在網址問自己：這個名稱只是給檔案結構和 layout 使用嗎？

這三種寫法外表只差一對括號或中括號，結果卻完全不同。一般資料夾會把名稱帶進 URL；中括號代表「這裡是一個可變值」；圓括號則像檔案樹裡的透明隔板，只影響分組與 layout，不會留下網址痕跡。

從 URL 反推檔案樹：先決定每一段要不要留下

拿到需求或 API 清單裡的網址時，可以逐條還原。先看 URL 的每一段，在 app/ 底下依序建立同名資料夾；最後在該路徑最內層放入 page.tsx。

如果某一段是每次都不同的值，例如 /tags/react 裡的 react，或 /questions/123 裡的 123，就不要為它建立實際名稱的資料夾，而是用 [id] 這種動態資料夾表示可變的一段。

如果某一整區的頁面需要共用外框，但區域名稱不該出現在網址，就使用 route group，把名稱放進括號。假設需求是：

  • 首頁、問題列表、問題詳情共用主站外框。
  • 網址分別是 /、/questions、/questions/123。
  • 登入與註冊不使用主站外框。
  • 登入與註冊的網址是 /sign-in、/sign-up。

從這些 URL 和 layout 需求反推，檔案樹會是：

app/
├── layout.tsx
├── (root)/
│   ├── layout.tsx
│   ├── page.tsx
│   └── questions/
│       ├── page.tsx          → /questions
│       └── [id]/page.tsx     → /questions/123
└── (auth)/
    ├── layout.tsx
    ├── sign-in/page.tsx      → /sign-in
    └── sign-up/page.tsx      → /sign-up

這裡的 (root) 和 (auth) 都不會出現在網址中。它們像收納盒的標籤，只用來整理頁面與安排外框；真正的 URL 只由一般資料夾和動態資料夾組成。

從檔案樹反推 URL：沿路往上讀

反過來看一棵檔案樹時，找到每個 page.tsx，再把它所在路徑由外到內讀一遍。一般資料夾名稱照抄；有括號的 route group 直接跳過；有中括號的動態資料夾，還原成一個可變的值。

例如看到：

app/(root)/questions/[id]/page.tsx

就可以判斷它對應的是 /questions/任意值。前面的 (root) 是 route group，因此不會出現在 URL 裡。

熟悉這個反推動作後，拿到任何一份 AI 產出的 app/ 樹，都能很快列出它實際提供哪些頁面，再逐條和需求單比對。這比只看資料夾名稱、猜 AI 原本想做什麼可靠得多。

判別問句：看到 AI 的結構，先問這幾件事

驗收時不要只問「這棵樹看起來像不像正確答案」，而要問一些可以直接驗證的問題：

  1. 這個資料夾名稱應該出現在 URL 嗎？ 如果應該出現，就不能誤用 route group；如果不該出現，才考慮使用括號。
  2. 這一段是固定名稱，還是每次都不同的值？ 固定名稱用一般資料夾；可變值用 [id] 這類動態資料夾。
  3. 這條路徑的最內層有 page.tsx 嗎？ 資料夾存在，不代表它本身就是可拜訪的頁面。
  4. 同一條 URL 是否被兩個檔案同時解析？ 特別要檢查不同 route group 裡是否各放了一個對應同一路徑的頁面。
  5. navbar 或其他外框是否在兩層 layout 都出現？ layout 是往下疊加，不是二選一；同一個元件放在 root layout 和區塊 layout，畫面就可能重複。
  6. 動態資料夾的名稱和程式讀取的 key 一致嗎？ 資料夾叫 [id]，程式卻讀 params.slug，就可能拿到 undefined。

常見的 AI 路由結構錯誤

症狀錯誤結構實際結果 / 問題
網址多了一段或少了一段想要 /auth/sign-in，卻寫成 (auth)/sign-in/括號讓 auth 消失，實際變成 /sign-in
整條網址 404資料夾存在，但裡面沒有 page.tsx那一層不是可拜訪的網址，單獨進去會 404
同一條路徑衝突首頁 page.tsx 同時出現在兩個 route group兩個檔案都想對到 /，路徑解析衝突
動態值讀不到資料夾叫 [id]，程式卻讀 params.slugkey 名稱對不上，取到 undefined
外框重複套了兩層navbar 同時放在 root layout 與區塊 layout畫面出現兩份 navbar 或版型互相擠壓

其中 layout 的問題特別容易被忽略。layout 是「疊」上去的，不是「二選一」。如果 AI 在 app/layout.tsx 放了一次 navbar，又在 app/(root)/layout.tsx 放一次，主站頁面就會同時吃到兩層 layout，結果自然出現兩份 navbar。

比較穩妥的分工是：全站都需要的關注點放在 root layout；只有某個區塊需要的外框，才放在區塊 layout。不要讓同一個 navbar 兩邊都負責。

反例：看起來有分區，其實把 URL 段吃掉了

假設 AI 想讓登入頁位於 /auth 底下，同時又想讓登入區和主站使用不同的外框。它可能寫成：

app/
├── layout.tsx
├── (root)/
│   ├── layout.tsx
│   └── page.tsx
└── (auth)/                 ← 用 route group 想表達 "auth"
    └── sign-in/
        └── page.tsx

問題在於，auth 被包成了 (auth)，所以它不會出現在網址裡。這棵樹實際產生的是 /sign-in，不是 AI 以為的 /auth/sign-in。

但這不代表這棵樹永遠是錯的。如果需求要的是乾淨的 /sign-in，這份結構反而是對的；如果需求要的是帶有 auth 的網址，就必須拿掉括號，改成一般資料夾 auth/sign-in/。

同一棵檔案樹是否正確，取決於它是否符合原本要的 URL。這也是驗收時最重要的順序：先確認「我要的網址長什麼樣子」，再回頭檢查資料夾結構，而不是看到括號就直接判定對或錯。

結尾：用一條規則驗收整棵路由樹

驗收路由結構時，先列出需求中的每一條 URL，再由 URL 畫出檔案樹：可變段用 [id]，只想分組與共用外框、又不想改變網址時用 (group)。接著反過來從每個 page.tsx 推回 URL，確認兩邊完全吻合。最後檢查三個地雷：括號是否吃掉了該保留的路徑段、某一層是否缺少 page.tsx、同一條路徑是否被兩個檔案解析。

你也可以把這套檢查濃縮成一句話：先問「這個檔案實際會產生哪個 URL？」再問「它的 layout 會和哪些父層疊在一起？」 只要這兩題答得出來，AI 的路由樹就很難躲過驗收。

這個節點的五步到這裡結束。你已經能從資料夾讀出網址、用動態段表示不確定的路徑、用 layout 疊出不同外框、用 route group 分區而不弄髒網址，最後把這些規則合在一起檢查 AI 的架構。接著的節點會往「元件」那條線走，繼續判斷 server shell 和 client island。你可以回到課程目錄選下一個節點，或先跑 /tackle 驗收這幾步。
