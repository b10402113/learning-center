route group：何時該分組、何時不該

Step 4/5 · 檔案式路由、layout 與 route groups

先看你要解的衝突

登入頁通常不需要 navbar 和左右側欄，只想顯示一張置中的卡片；但它的網址又應該保持乾淨，使用 /sign-in，而不是被迫變成 /auth/sign-in。這時，你要在兩件事之間做選擇：

  • 檔案要分區管理，而且不同區塊要套用不同的 layout。
  • 網址結構不能因為檔案分組而被改亂。

一般資料夾會把名稱直接帶進 URL；什麼都不分，又無法替不同區塊套上不同外框。Next.js 的 route group 就是用來處理這個拉扯的：它能把檔案分成不同區塊，卻不把分組名稱放進網址。

學習目標

看完這篇，你應該能判斷一個區塊該使用一般巢狀資料夾，還是 route group，並說明 route group 為什麼能在不改變 URL 的情況下，讓每個區塊擁有自己的 layout。

選項比較：要讓名稱進 URL 嗎？

面對「想把幾個頁面歸成一區」的需求，你主要會在兩種資料夾之間選擇。把它們並列比較，差異就很清楚：

選項寫法名稱會不會進 URL能不能有自己的 layout適用時機
一般巢狀資料夾auth/sign-in/會，網址是 /auth/sign-in可以你確實想要這段出現在網址裡
route group(auth)/sign-in/不會，網址是 /sign-in可以只想分堆、不想改網址

route group 可以想成「只給開發者看的資料夾標籤」。它的名稱用一對括號包住，例如 (auth) 或 (root)，因此不會成為 URL 的路徑段。不過，它和一般資料夾一樣可以放自己的 layout.tsx。

也就是說，route group 把兩件事拆開處理：檔案在專案裡怎麼整理，以及使用者在網址列看到什麼。

DevFlow 就是這樣切分的。整個 app/ 底下只留兩個 route group：(root) 放需要主站外框的頁面，(auth) 放登入與註冊頁。兩邊各自使用不同的 layout，但登入頁的網址仍然是 /sign-in。

app/
├── layout.tsx          ← root layout（全站：字型、主題、session）
├── (root)/
│   ├── layout.tsx      ← 主站外框（navbar + 左右側欄）
│   ├── page.tsx        → /
│   └── questions/...   → /questions/...
└── (auth)/
    ├── layout.tsx      ← 登入外框（置中卡片）
    ├── sign-in/page.tsx → /sign-in
    └── sign-up/page.tsx → /sign-up

兩個 group 的 layout 差異有多大，看程式碼就知道。主站的 (root) layout 把 navbar 與左右側欄放進外框：

const RootLayout = ({ children }: { children: ReactNode }) => {
  return (
    <main className="background-light850_dark100 realtive">
      <Navbar />

      <div className="flex">
        <LeftSidebar />

        <section className="flex min-h-screen flex-1 flex-col px-6 pb-6 pt-36 max-md:pb-14 sm:px-14">
          <div className="mx-auto w-full max-w-5xl">{children}</div>
        </section>

        <RightSidebar />
      </div>
    </main>
  );
};

而 (auth) 的 layout 完全沒有 navbar，只把 children 放進一張置中的卡片：

const AuthLayout = ({ children }: { children: ReactNode }) => {
  return (
    <main className="flex min-h-screen items-center justify-center bg-auth-light bg-cover bg-center bg-no-repeat px-4 py-10 dark:bg-auth-dark">
      <section className="light-border background-light800_dark200 shadow-light100_dark100 min-w-full rounded-[10px] border px-4 py-10 shadow-md sm:min-w-[520px] sm:px-8">
        …
        {children}
        <SocialAuthForm />
      </section>
    </main>
  );
};

同樣是接收 children，一個負責放入 navbar、左右側欄與中間內容，另一個則負責把登入內容放進置中的卡片。route group 讓這兩套外框各自服務一個區塊，卻不用犧牲網址結構。

判別問句：你要的是分堆，還是那段路徑？

遇到要使用 (group) 或一般資料夾的情況，可以先問自己：

這個資料夾名稱，我希望它出現在使用者的網址列上嗎？

如果答案是「要」，例如你想要 /auth/sign-in 這種能看出區塊層次的網址，就使用一般巢狀資料夾。因為一般資料夾的名稱會成為路徑的一部分。

如果答案是「不要」，你只是想把幾個頁面收在同一區，方便管理或掛上共用 layout，就使用 route group。把資料夾名稱用括號包起來，讓它在 URL 上隱形。

接著再問第二個問題：

這一區需要跟其他區塊使用不同的 layout 嗎？

如果兩區的版型完全相同，其實不一定需要分 group，把頁面放在一起就好。route group 的主要價值，是替一整組頁面掛上專屬 layout，同時不改動網址結構。

反例：route group 什麼時候會咬你一口？

route group 很方便，但用錯時，通常不一定會立刻看到 build error；更麻煩的是，程式可能能跑，行為卻和你預期不同。常見有兩種情況。

第一種是兩個路由解析到同一條路徑。因為 route group 名稱不會進 URL，如果你把首頁的 page.tsx 同時放進 (root) 和某個 (dashboard) group，兩個檔案都會對應到 /。這在 Next.js 裡會造成衝突，頁面不會照你想的方式運作。

所以要記住：group 不進 URL，不代表可以任意重複頁面。最後解析出來的路徑仍然必須唯一。

第二種是把 route group 當成一般資料夾，用來表達網址層次。例如你真正想要的是 /auth/sign-in，卻寫成 app/(auth)/sign-in/page.tsx。最後得到的其實是 /sign-in，因為括號讓 auth 消失了。

這是驗收 AI 產出時很常見的錯誤：檔案結構看起來合理，網址卻已經悄悄偏掉。看到括號時，要立刻想到「這一段不會進 URL」。

route group 也不能拿來當路徑的一部分，而且必須和同層的其他路由避免衝突。你可以把它想成「給人看的資料夾標籤」，而不是「給瀏覽器看的路徑」。

最後的決策規則

要決定使用一般巢狀資料夾還是 route group，先問：這個名稱要出現在 URL 裡嗎？要，就用一般資料夾（auth/sign-in/ → /auth/sign-in）；不要，只是想分堆或掛專屬 layout，就用括號把它隱形（(auth)/sign-in/ → /sign-in）。route group 讓「檔案組織」與「網址結構」分家，但同一條路徑不能被兩個頁面解析，也不能把 route group 當成網址的一段。

到這裡，你已經掌握這個節點的四塊能力：路徑、動態段、layout，以及 route group。下一步不會再加入新的概念，而是把這四塊合起來，變成一個驗收動作：拿到 AI 產生的檔案樹或一串網址時，能在兩者之間互相反推，並抓出「路徑衝突」或「網址被 route group 吃掉」這兩種結構錯誤。
