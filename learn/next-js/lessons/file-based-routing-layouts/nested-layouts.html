layout.tsx 疊層：root layout 與區塊外框

Step 3/5 · 檔案式路由、layout 與 route groups

先看全貌：頁面不是一張張獨立拼出來的

你已經能用資料夾表達網站路徑了，但網站還有一些不屬於單一頁面的共同元素：navbar、側欄、字型、登入狀態與主題。這些東西如果各自塞進每個 page.tsx，就像每間房子都重蓋同一段走廊；一開始看似簡單，等版型一改，就得逐頁修正。

Next.js 的 layout.tsx 就是解決這個問題的外框。頁面負責自己的內容，layout 則負責包住一群頁面共用的結構。從外到內，可以把它想成俄羅斯娃娃：最外層是全站共用的 root layout，裡面可以再套某個區塊的 layout，最後才放進實際頁面。

學習目標

學完這一課，你應該能說明 root layout 為什麼是必要的、children 插槽如何把頁面接進來，以及巢狀 layout 為什麼會由外到內一層層套上去。

場景：navbar 貼在每一頁，改一次要改十次

首頁、問題列表、個人頁面都需要 navbar，但 navbar 並不是任何一條網址專屬的內容。AI 常犯的寫法，是在每個 page.tsx 裡都 import 一次 navbar，再把它放到頁面上方。

這種方式在只有一兩頁時不容易察覺問題。可是每新增一頁，就得再貼一次；哪天要調整 navbar 的版型，又得逐一修改每個頁面。這正是上一節專案結構課提過的「AI 常犯版」：把共用結構複製到各頁，而不是把它集中在應該負責的地方。

正解是把 navbar 放進 layout.tsx。layout 像一個固定好的舞台外框，頁面只要把自己的內容放進舞台中央，所有共用的導覽與側欄就能自動出現。

layout 用 children 把頁面接進來

layout.tsx 的核心角色，是一個接受 children 的元件。它先畫好自己的外框，再把 children 放到指定位置。看 DevFlow 主站區塊的 layout：

import { ReactNode } from "react";

import Navbar from "@/components/navigation/navbar";
import LeftSidebar from "@/components/navigation/LeftSidebar";
import RightSidebar from "@/components/navigation/RightSidebar";

const RootLayout = ({ children }: { children: ReactNode }) => {
  return (
    <main className="background-light850_dark100 realtive">
      <Navbar />

      <div className="flex">
        <LeftSidebar />

        <section className="flex min-h-screen flex-1 flex-col px-6 pb-6 pt-36 max-md:pb-14 sm:px-14">
          <div className="mx-auto w-full max-w-5xl">{children}</div>
        </section>

        <RightSidebar />
      </div>
    </main>
  );
};

export default RootLayout;

注意 {children} 出現的位置。上方是 navbar，左右兩側是側欄，中間的 children 才是目前頁面的內容。這個 layout 不需要知道子頁面究竟是首頁、問題列表，還是其他頁面；它只提供固定的外框，讓子頁面插進中間區域。

這就是正解版和 AI 常犯版的差別：

寫法 做法 結果
AI 常犯版 每個 page.tsx 都各自放入 navbar 與側欄 結構重複，改版時要逐頁修改
正解版 把共用結構放進 layout，透過 {children} 接入頁面 外框集中管理，底下頁面自動共用

root layout：唯一必要的最外層

App Router 規定至少要有一個 root layout，位置是 app/layout.tsx。它位在所有 layout 的最外層，並且負責產生整個頁面的 <html> 與 <body>，所以也是唯一不套在其他 layout 裡的那一層。

全站只需要出現一次的東西，例如字型、metadata、主題 provider，就適合放在 root layout。DevFlow 的 root layout 如下：

const RootLayout = async ({ children }: { children: ReactNode }) => {
  const session = await auth();

  return (
    <html lang="en" suppressHydrationWarning>
      …
      <SessionProvider session={session}>
        <body className={`${inter.className} ${spaceGrotesk.variable} antialiased`}>
          <ThemeProvider
            attribute="class"
            defaultTheme="system"
            enableSystem
            disableTransitionOnChange
          >
            {children}
          </ThemeProvider>
          <Toaster />
        </body>
      </SessionProvider>
    </html>
  );
};

export default RootLayout;

這一層同樣透過 {children} 接住底下的內容，但它包住的是整個網站的共同關注點：Session、主題與字型。無論頁面位於哪個區域，都會先經過這一層。

巢狀 layout：一層疊一層，不是互相取代

root layout 不是唯一可以使用的 layout。任何資料夾都可以再放一個 layout.tsx，替那個資料夾底下的頁面樹加上專屬外框。

當使用者進入某個頁面時，layout 會從最外層一路往內套，最後才放入頁面本身。它不是後面的 layout 把前面的 layout 蓋掉，而是每一層都保留自己的責任，像俄羅斯娃娃一樣一層包著一層：

  • root layout：處理整個網站都需要的外框與設定。
  • 區塊 layout：處理某個網站區域共用的版型。
  • 頁面：提供這條路徑自己的內容。

以 DevFlow 來說，拜訪 /（主站首頁）時，包裝順序是：root layout（提供 <html>、字型、登入 session、主題）→ (root) 的 layout（navbar 與左右側欄）→ 首頁的 page.tsx。

這裡的分工很清楚：root layout 管「全站都要的事」，區塊 layout 管「這一區的版型」。要換全站字型或主題，就修改 root layout；要換主站區塊的導覽，就修改 (root) 的 layout。每一層只影響自己底下的頁面，其他區塊不會被牽連。

把 layout 想成分層的責任範圍

layout 最實用的地方，不只是少寫幾次 navbar，而是讓「改哪裡、影響到誰」變得清楚。共用內容放在正確的層，就像把工具放回對應的工具箱：全站設定不必散落在各頁，主站版型也不必污染登入頁或其他區塊。

layout.tsx 是一個接受 children 的元件，用外框把子頁面包起來；子頁面透過 {children} 插進 layout。root layout（app/layout.tsx）是唯一必要的 layout，負責最外層的全站關注點，例如 <html>、字型、provider。資料夾可以再放自己的 layout，套疊順序由外到內是：root layout → 區塊 layout → 頁面。每一層只負責一種橫切關注點。

現在可以把兩塊拼圖接起來：資料夾描述「頁面位在哪條路線上」，layout 描述「這個頁面被哪些外框包住」。下一個常見需求是，主站與登入頁需要完全不同的外框，但網址仍想保持乾淨。這時就會用到另一種資料夾型別：route group。下一篇會再看它，以及什麼時候適合使用、什麼時候不該使用。
