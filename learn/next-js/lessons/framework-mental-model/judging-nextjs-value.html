怎麼看出專案「多做了事」：Next.js 與純 React 的判斷法

Step 4/4 · Next.js 作為 framework：加在 React 上的那一層

學習目標

拿到一段 code 或一棵檔案樹時，你要能判斷：哪些是 Next.js 額外提供的能力？哪些其實只是一般 React？更重要的是，你要說得出自己的判斷理由。

先看大圖：你要決定的是「誰負責這件事」

前三節已經把地圖攤開：先分清楚 library 與 framework 的角色，再看 React 留下哪些空間，最後整理 Next.js 加上的六個區塊。現在把這張地圖拿來處理真實專案。

想像一下，AI 交給你一份專案。檔案很多、元件很多，裡面既有 React code，也有 Next.js 的慣例。你需要快速看出：哪幾行是 Next.js 幫你完成的？哪些事情如果沒有 framework，就得自己補上？

這件事容易混淆，是因為兩種 code 常常黏在一起。看到 useEffect 抓資料，可能只是純 React 的常見寫法；看到 export default async function Page()，則可能是 Next.js 的頁面慣例。更麻煩的是，AI 有時會把 framework 已經處理好的事再做一次，例如在 Server Component 裡又包一層 useEffect，或在每個檔案開頭反射性地加上 "use client"。

所以今天的核心不是背更多 API，而是學會一個判斷：這件事的責任，落在 Next.js 身上，還是落在你自己身上？

選項比較：純 React 做什麼，Next.js 又多做什麼？

同一個功能，放在純 React 與 Next.js 裡，寫法可能完全不同。但差異不在於哪邊的 code 比較短，而在於 framework 是否替你接手了一部分工作。

功能純 React 的做法Next.js 多做的事
抓資料useEffect + useState，等資料回來才顯示async Server Component 直接 await，自動快取與去重
頁面路由安裝 React Router，手寫路由表資料夾即路由，page.tsx 就是頁面
後端 API另開一台 Express 或獨立服務route.ts 就是端點，部署為 serverless function
SEO 標籤手動操作 document 或依賴其他工具metadata 匯出或檔案式慣例自動產生
互動元件本來就在瀏覽器執行要加 "use client" 才會在瀏覽器執行

看這張表時，可以把判斷濃縮成一句話：

如果沒有 Next.js，我是不是得自己寫這件事？

如果答案是「要」，那通常就是 Next.js 額外接手的工作；如果搬到純 React 後仍然照樣能跑，而且本來就會這樣寫，那多半只是一般 React。

判別問句：讀 code 時依序問自己四件事

下面四個問題像是 code review 時的手電筒。先照檔名，再照自動行為，最後檢查是否有重複施工。

  1. 這個檔名是不是 Next.js 的慣例？ 只要是 page.tsx、layout.tsx、route.ts、loading.tsx、error.tsx、not-found.tsx，它就不是單純被其他檔案 import 進來的元件，而是 framework 依照檔名與位置找到並執行的入口。看到這些檔名，可以先歸類成「框架多做的事」。
  2. 這行是不是 framework 自動處理的？ 例如 Server Component 預設在 server 執行、fetch 自動快取與去重、依路由自動 code splitting，以及 next/font、next/image 提供的最佳化。這些事情不需要你另外下指令，framework 就會接手。
  3. 把這段搬到純 React，還能不能跑？ 如果拿掉 "use client"、拿掉 app/ 慣例後，程式仍然可以運作，那它很可能只是一般 React 元件或 hooks。反過來，如果離開 Next.js 就失去意義，例如 route.ts 裡的 handler，那就是 framework 專屬能力。
  4. AI 有沒有把 framework 已經做好的事再手動做一次？ 這通常是最有價值的一問。在 Server Component 裡用 useEffect 再抓一次資料、明明有 route handler 卻又架一層自製 API，或每個檔案都反射性地加上 "use client"，都可能是 AI 把舊習慣搬進新架構的結果。

這四問的順序很重要。前兩問先找出 Next.js 的入口與自動行為，第三問用「搬家測試」區分通用能力與 framework 專屬能力，第四問則專門找重複工作與架構問題。

反例：規則什麼時候會翻轉？

這套判斷法很好用，但不能只看表面。以下三種情況，最容易讓你把 code 歸錯類。

第一，有些 code 看起來像普通 React，其實受到 Next.js 深度影響。最典型的是 "use client"。它看起來只是一個放在檔案頂端的字串，實際上卻是 Next.js 的 framework 指令，用來決定這個元件是否在瀏覽器執行。拿掉它，同一個元件可能改在 server 執行，行為也會跟著改變。

第二，有些 code 看起來很像 Next.js，其實只是通用 React。普通函式元件、useState、props，在純 React 裡也一樣存在。它們不是 Next.js 額外提供的能力，不要把一般 React 的功勞算到 framework 頭上。

第三，辨認出「這是 Next.js 多做的事」，不代表目前寫法就是好寫法。AI 常見的架構錯誤，是讓 Server Component 退化成 Client Component，把原本可以留在 server 的抓資料工作丟回瀏覽器。下面兩段都能取得資料，但它們使用 Next.js 能力的方式差很多。

// AI 常犯版：把 server 能做的事丟回 client
"use client";

import { useEffect, useState } from "react";

export default function Page() {
  const [data, setData] = useState(null);

  useEffect(() => {
    fetch("/api/questions")
      .then((res) => res.json())
      .then(setData);
  }, []);

  return <h1>{data ? data.title : "載入中…"}</h1>;
}
// 正解版：Server Component 直接抓，少一趟往返
import { db } from "@/database";

export default async function Page() {
  const question = await db.question.findOne();
  return <h1>{question.title}</h1>;
}

左邊不是單純「寫法比較舊」。它把工作推回 client，也因此放棄了 Next.js 這一層原本能提供的服務：自動去重、直接存取資料庫，以及首屏就有內容。

這也是判讀 AI 產生的架構時，不能只停在「我認得這些符號」。你還要繼續追問：這段 code 有沒有使用 framework 的優勢？還是只是把純 React 的舊習慣，套上一層 Next.js 外衣？

最後的決策規則：四問就能開始檢查

拿到一個檔案或一段 code 時，依序檢查下面四件事：

  • 檔名是不是 Next.js 的框架慣例？
  • 這行是不是 Next.js 自動處理的行為？
  • 把它搬到純 React，還能不能運作？
  • AI 有沒有把 framework 已經做好的事重做一次？

前三問用來把 code 分成「Next.js 多做的」與「一般 React」；第四問則用來抓出多餘的工作與架構陷阱。最後記住兩個容易翻轉的判斷："use client" 是 framework 指令，不是普通字串；普通元件與 hooks 是通用 React，不是 Next.js 的專屬功勞。
