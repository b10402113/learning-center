Library 還是 framework？看懂 Next.js 加在 React 上的那一層

Step 1/4 · Next.js 作為 framework：加在 React 上的那一層

學習目標

學完這一節，你應該能說出 library 與 framework 的差別，理解「誰呼叫誰」以及「控制反轉」是什麼，並解釋 Next.js 為什麼是「加在 React 上」，而不是拿來取代 React。

先從一個問題開始：這個檔案到底是誰在管？

你打開一個 AI 產出的 Next.js 專案，看到 app/ 底下放著 page.tsx、layout.tsx、route.ts，旁邊還有一些看不懂為什麼要放在那裡的檔案。這時你可能會問：

這些到底是 React 的東西，還是 Next.js 的東西？如果想修改功能，應該改哪裡？又有哪些檔案不是你想怎麼改就怎麼改？

這個問題之所以容易卡住，是因為你還沒把兩個角色分開：

  • React 是 library，提供元件等零件，讓你組出使用者介面。
  • Next.js 是 framework，替整個專案安排流程，規定檔案放法與執行方式。

如果把這兩者混在一起，你就會拿「我主動呼叫工具」的心態，去閱讀一個「由框架回頭呼叫你的程式碼」的專案。結果每個檔案都像案件現場，找不到它們為什麼會被執行。

這一節要做的，就是把 library 與 framework 的分界線畫出來。線畫對了，你才看得出 AI 產出的架構裡，哪些事情是 Next.js 幫你處理，哪些事情仍然需要你自己負責。

先看大圖：兩個角色，差在誰掌握流程

Library 和 framework 最大的差別，不是誰的功能比較多，而是誰掌握整個流程的主導權。

可以把 library 想成一座工具箱。你決定什麼時候打開它，要拿螺絲起子還是扳手，也決定先做哪一步。工具箱不會自己叫你做事，是你主動拿工具來用。

React 就像這座工具箱。你會先 import 它，再決定在哪個元件裡使用它，以及什麼時候讓它 render。React 負責在你指定的地方處理 UI，但整體流程仍然由你的程式碼安排。

Framework 則比較像一棟已經牽好水電的房子。牆壁在哪裡、插座設在哪裡、水管怎麼走，早在你搬進去之前就規劃好了。你可以把傢俱放進指定房間，卻不能把整棟房子的管線當成空白畫布，想怎麼重拉就怎麼重拉。

Next.js 就是這種角色。它規定 app/ 底下的檔案如何命名、哪個檔案會成為頁面、某些程式該在 server 還是 client 執行，也決定你的元件會在什麼時機被呼叫。

AI 常犯的理解：Next.js 是另一套 React

看到 Next.js 專案裡多了許多檔案與規則，常見的誤解是：Next.js 好像取代了 React，或者它是另一個和 React 平行的 UI 系統。

這個想法不太準確。Next.js 不是把 React 重寫一遍，也不是把 React 丟掉不用。它比較像是在 React 外面加上一層專案規則與預建功能。

正確的理解：Next.js 是建立在 React 上的 framework

Next.js 會把 React 包在自己的流程裡，提供路由、檔案慣例，以及其他預先做好的解決方案。換句話說，它是建立在 React 之上、擴充 React 能力的 framework。

因此，一個 Next.js 專案其實是兩層疊在一起：

  • 底層是你熟悉的 React：元件、hooks、props 等 UI library 的能力仍然存在。
  • 上層是 Next.js 的框架慣例：檔案放在哪裡、怎麼命名，以及框架何時找到並呼叫它們。

這就像在工具箱外面再蓋一間有固定格局的工作室：工具本身還是原來那些工具，但工作室規定了工具放哪裡、什麼時候使用，以及整個工作流程怎麼走。

「誰呼叫誰」：控制反轉到底是什麼？

軟體工程裡，這種主導權的轉換稱為控制反轉（inversion of control）。名稱聽起來很抽象，其實只要問一句話就能判斷：

這段程式是我主動呼叫工具，還是框架在特定時機回頭呼叫我？

使用 library 時，控制權通常在你手上。你的程式碼主動呼叫 library 提供的函式，決定什麼時候用、在哪裡用。

使用 framework 時，控制權則交出去一部分。你先按照框架的規則寫好檔案與函式，等框架在適當的時機找到它們並呼叫。你不是每次都親自發號施令，而是在框架預留的位置填入自己的應用邏輯。

比較點Library（例如 React）Framework（例如 Next.js）
誰呼叫誰你的程式碼呼叫它它呼叫你寫的元件與函式
流程主導權你決定何時、在哪裡使用框架規定檔案與執行時機
你要負責的事把零件組起來，並自行選擇其他工具專注在應用邏輯，其餘流程交給框架
換掉它的成本相對低，個別零件可以替換相對高，因為整個專案的慣例都綁在一起

為什麼 Next.js 的檔案看起來像「自己會動」？

Next.js 常用一個概念叫做慣例優先於設定（convention over configuration）。意思是，與其要求你一項一項設定路由、打包與資料抓取，框架不如先訂好一套慣例，讓你照規則放檔案就能運作。

這也是 Next.js 能省下許多工具設定時間的原因。你不必把大量時間花在編譯、打包、壓縮、格式化與部署設定上，而可以把心力放在真正的商業邏輯。

對閱讀 AI 產出的 Next.js 架構來說，這個概念尤其重要。專案裡有些檔案不是被其他檔案明確 import 進來，而是被 Next.js 依照慣例找到並執行。

例如：

  • page.tsx 因為檔名符合規則，所以會被當成一個路由頁面。
  • layout.tsx 因為放在正確的位置，所以會自動包住底下的頁面。

如果你只用 React 的「誰 import 誰」思維去追蹤，就可能找不到這些檔案之間的連結。換成「這是框架依照慣例來呼叫我的檔案」的角度，整棵架構就會接起來。

React 的部分，仍然是 React

框架接手流程，不代表 React 的元件、hooks 與 props 消失了。這些仍然是 library 層的能力，你依舊會主動使用它們。

所以，看到一段 Next.js code 時，可以先問自己兩個問題：

  • 這是在使用 React 提供的 UI 零件嗎？
  • 還是在遵守 Next.js 的檔案慣例，等框架來呼叫？

能分清楚一段 code 屬於哪一層，就是後續判斷專案架構的起點。你不必把所有檔案都當成同一種東西閱讀；有些是你主動拿來用的工具，有些則是框架預留給你的插槽。

小結：把這兩層掛回正確的位置

Library 是你主動呼叫的工具，控制權在你手上；framework 掌握流程，會回頭呼叫你寫的檔案，控制權因此交出去一部分。React 是負責 UI 的 library，Next.js 則是在 React 上加上框架慣例與預建功能的 framework。它不是取代 React，而是把 React 放進一套更完整的專案流程裡。閱讀 Next.js 專案時，先問：這個檔案是「我要呼叫的」，還是「框架會來呼叫的」？
