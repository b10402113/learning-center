React 不夠用在哪裡？Next.js 為什麼會出現

Step 2/4 · Next.js 作為 framework：加在 React 上的那一層

學習目標

這一節會帶你看清楚：單獨使用 React 時，路由、資料、後端、首屏、SEO 與 bundle 分別留下了哪些缺口，以及 Next.js 為什麼會出現、又替你補上了什麼。

先問一個實際問題：純 React 專案，要自己拼多少東西？

上一節我們分清楚了：React 是需要由你主動呼叫的 library；Next.js 則是會回過頭主導流程的 framework。可是，如果 React 已經能把整個畫面做出來，為什麼還需要另一個框架來接管流程？React 到底在哪裡不夠用？

想像你要用純 React 做一個有首頁、文章頁和後台的網站。你可能得先選一套路由工具，例如 React Router；再挑一套狀態管理方案；另外架一台 Express 當後端；設定編譯與打包工具；處理表單；最後還要想辦法讓搜尋引擎看見首頁內容。

這些事情單獨看，都不一定困難。麻煩的是，它們全部都和產品的商業邏輯沒有直接關係，卻又是網站要正常運作時不能少的零件。你像是在組一台車：引擎可以自己做，但輪胎、方向盤、煞車和儀表板也得一個個挑、裝、調整。

這一節會把這些「非做不可的拼裝工作」逐一攤開。當你能具體指出 React 留下的洞，就會明白 Next.js 的出現不是單純追逐潮流，而是為了補上 React 在真實產品裡遇到的限制。

先看大圖：每一代工具都在修上一代的洞

把時間拉長來看，這條脈絡其實很清楚。JavaScript 在 1995 年由 Brendan Eich 在 Netscape 開發；到了 2000 年代，Google 用 JavaScript 在網頁上做出互動式地圖，讓它大幅流行。之後，開發者陸續迎來 jQuery、Angular、Node.js、React，一直到最近的 Next.js。

這些工具不是隨意堆在一起。它們背後有一條共同邏輯：每一代工具，都是為了解決上一代的限制而出現。

  • jQuery 處理了原生 JavaScript 操作 DOM 時的繁瑣。
  • React 改善了 jQuery 在大型專案裡越來越難維護的問題。
  • Next.js 則進一步處理 React 留下來的全端整合、渲染與工具鏈問題。

所以，學習新工具不一定是在趕時髦。很多時候，是因為舊工具放大到某種規模後，真的會開始卡住。

React 給了你什麼，又刻意不給你什麼？

React 的定位其實很克制：它主要負責把元件描述的 UI 畫出來，並在狀態改變時有效率地更新畫面。

它用兩個主要優點說服了整個業界。第一是元件化架構：像按鈕這類 UI 元件可以做一次、重複使用，讓專案更容易維護與擴充。第二是Virtual DOM：React 會比對新舊兩棵輕量的樹，只更新真正發生變動的真實 DOM，藉此改善效能。

但 React 的優點，也同時畫出了它的邊界。它專注在 UI，就不會順手替你決定路由、後端、資料取得、伺服器渲染或部署方式。這不是 React 做錯了，而是它刻意維持的定位。

AI 常犯版：把 React 想成 正解版：React 實際負責
一套涵蓋網站所有需求的完整解決方案 負責描述 UI，並在狀態改變時更新畫面
只要安裝 React，就自動擁有路由、後端、SEO 與部署設定 這些部分仍需要你另外選工具、做整合與設定
畫面能顯示，就代表產品架構已經完成 畫面只是產品的一層，真實網站還需要資料、伺服器、渲染與工具鏈

原文也提到，React 要發揮得好，需要應用程式「每一個部分之間深度整合」，而這正是 framework 登場的地方。

Vercel 副總裁 Lee Robinson 曾用一個具體例子說明差異：從 React + Express + Webpack 換成一個 framework 後，砍掉了 20,000 多行程式碼與 30 多個相依套件，同時把熱更新（HMR）從 1.3 秒降到 131 毫秒。那些被砍掉的內容，正是原本需要自己手動配置與維護的部分。

把這些留白整理起來，React 主要留下三類缺口。

缺口一：首屏與 SEO——搜尋引擎看不到你的內容

純 React 的預設做法，是把內容全部放到瀏覽器端渲染。伺服器先回傳一份很精簡的 HTML，再附上一大包 JavaScript；瀏覽器必須先把這包 JavaScript 執行完，畫面才會真正長出來。

這會同時影響使用者與搜尋引擎。使用者可能要等更久，才能看到第一個完整畫面；搜尋引擎的爬蟲來抓頁面時，內容卻可能還沒有生成，結果就像走進一間還沒開燈的店，裡面的商品明明存在，卻什麼也看不到。

AI 常犯版 正解版
只要瀏覽器最後能把畫面渲染出來，搜尋引擎自然也能看見 純 React 預設主要在瀏覽器端渲染，搜尋引擎抓取時可能還拿不到完整內容
首屏只是視覺問題，對產品沒有太大影響 首屏速度與可索引內容會影響使用者體驗、網站能否被找到，以及排名表現

Next.js 提供了靜態生成（SSG）與伺服器端渲染（SSR）。伺服器可以直接送出完整 HTML，只把少量真正需要互動的 JavaScript 留到瀏覽器執行。

這樣一來，搜尋引擎一來就能讀到完整內容，每一頁也能被正確索引。SEO 值得在意，並不是因為它只是行銷名詞，而是因為它會直接影響網站能不能被找到、排名好不好，進而影響流量、信任感與競爭力。

缺口二：後端——你得另外開一台伺服器

傳統的全端做法，通常是前端一套、後端一套：React 負責畫面，Express 負責 API，中間還要處理路由設定與部署。這種分工當然可以運作，但也代表你必須維護兩套相鄰的系統。

Next.js 被稱為「全端 React framework」，讓你可以把後端程式碼寫在前端旁邊，不必另外設定傳統後端的那一整套路由。你不需要為了做一個 API，就先大費周章架起一台獨立伺服器。

AI 常犯版 正解版
React 本身就是完整的前後端框架 React 主要處理 UI；後端與 API 通常要另外選工具、建立與整合
做一個 API，就一定要先架一套完全分開的後端 Next.js 讓後端程式碼能放在前端旁邊，降低傳統後端的設定負擔

這也是 Next.js 宣稱「學習曲線平緩」的原因之一：後端不一定像想像中那麼複雜。當前端與後端由同一個 framework 串起來，開發者就能少花一些力氣在系統接縫處，專心處理真正的產品需求。

缺口三：工具鏈與 bundle——編譯、打包、部署都要自己配

前端開發的每一個環節都在持續演進：編譯、打包、壓縮、格式化與部署，全部都有不同工具可以選。純 React 並不會替你把這些決定好，因此你得自己挑工具、自己設定，也得自己處理它們彼此之間的相容與維護。

每多加入一個工具，就像在工作桌上多放一台需要調校的機器。單一工具也許不麻煩，但工具一多，設定與維護成本就會一起增加。

Next.js 把這些能力納入 framework 內建。你不必為了讓專案跑起來，先花半天配置工具鏈，可以把時間留給真正的 React 程式碼。

一個反直覺的觀察：framework 的程式碼看起來可能更多

有人會問：如果新 framework 比較好，為什麼同樣是一個「Hello World」按鈕，用新工具寫出來反而可能有更多行？

這個疑問很合理。原文也老實承認，單看行數，原生寫法確實比較少。但問題在於，真實專案不是只有一個按鈕。當系統需要路由、資料、後端、工具鏈與多人維護時，單一範例的行數就不能代表整體成本。

AI 常犯版 正解版
程式碼越少，工具就一定越好 要看專案放大後，能不能維持開發效率與可維護性
Hello World 的行數可以代表真實產品的複雜度 Hello World 只能展示最小案例，不能代表大型系統需要的整合工作
framework 增加的程式碼都是多餘負擔 有些程式碼是在表達元件結構，換來較好的維護與擴充能力

書中把同一個按鈕用四種寫法並列，正好能看出這件事。原生 JavaScript 與 jQuery 版本比較簡短，但功能有限；Angular 與 React 版本看起來比較囉嗦，卻把「元件」當成基本單位來思考。

以 React 為例：

import React from 'react';

class ExampleComponent extends React.Component {
  showMessage() {
    alert('Hello, World!');
  }

  render() {
    return <button onClick={this.showMessage}>Click Me</button>;
  }
}

這段程式碼比 jQuery 版本長得多，但它示範了另一種思考方式：UI 被拆成可重複使用的元件，行為（showMessage）與畫面（render）綁在同一個單位裡。

當專案變大，這種結構帶來的維護性與擴充性，才是真正拉開差距的地方。就像整理房間時，先買收納櫃可能會讓房間多出一些家具；但東西一多，這些結構反而能讓你更快找到、修改與重複使用內容。

React Server Components：React 後來的補洞，Next.js 把它變成預設

React 自己也看見了「全部在瀏覽器執行」所帶來的限制，因此推出了 React Server Components（RSC）。這個想法來自很實際的問題：Meta 團隊在開發 Instagram 網頁版時，發現送給瀏覽器的 JavaScript 越來越大，對網路速度慢或裝置效能較弱的使用者尤其痛苦。

於是，在 2020 年 12 月，React 團隊的 Dan Abramov 與 Lauren Tan，於「Data Fetching with React Server Components」演講中提出這個概念：元件可以分成 client 與 server 兩種。

  • 資料密集、但不需要互動的部分，留在 server。
  • 只有真正需要互動的元素，才交給 client。

這裡也有一個容易混淆的地方：

AI 常犯版 正解版
Server Components 是 Next.js 自己發明的功能 Server Components 是 React 的核心功能，Next.js 只是把它整合得特別好
只要用了 React，就會自動得到 Next.js 的預設行為 Next.js 在 framework 層把 React 的能力整合成一套實際開發流程

2022 年中，Next.js 率先整合了早期支援；到了 2022 年底，Next.js 13 推出 App Router，更直接把 Server Components 設為預設。這個決定翻轉了整個生態，也讓 Next.js 幾乎成為「現代 React 開發」的代名詞。

把這些關係放回同一張圖

React 的核心工作，是用元件描述 UI，並有效率地更新畫面。可是，真實產品還需要處理首屏與 SEO、後端 API、編譯打包、部署，以及如何把不需要互動的內容留在 server。

如果只看 React 的單一職責，這些都像是「額外問題」；如果把網站當成一個完整系統，它們卻是每天都會遇到的基本需求。Next.js 的角色，就是把這些分散的需求接在 React 上，提供一個已經整合好的 framework。

React 只負責把 UI 畫出來，其他真實產品需要的東西全留給你：搜尋引擎看得見的首屏（SSR / SSG）、不用另開伺服器的後端、編譯打包部署的工具鏈，以及後來才補上的 Server Components。Next.js 就是為了把這些缺口一次補齊而出現。它不是取代 React，而是把 React 放進一個已經幫你補好洞的框架裡。
