瀑布與 N+1：資料為什麼抓得慢

Step 3/4 · 在 RSC 裡抓資料：何時 server、何時 client

學習目標

學完這一節，你應該能辨認 sequential await 造成的 network waterfall 與 N+1 query，也能說明如何用 Promise.all 和 .populate() 消除它們。

前言：程式碼都對，頁面卻慢慢轉圈圈

上一節已經把抓資料的骨架接好了：頁面是 async，用 await 取得資料，再交給元件渲染。功能看起來一切正常，頁面卻總是慢半拍，載入畫面像卡在轉圈圈。

打開 DevTools 的 Network 面板後，通常會看到兩種不太妙的景象：請求一個接一個、像階梯一樣往右排；或者明明只要顯示幾筆資料，資料庫卻收到一長串查詢。

這一節要處理的兩個兇手，就是 network waterfall（網路瀑布）與 N+1 query。它們都不一定會報錯，也不會立刻讓頁面崩潰，卻會默默拖慢整個系統。因此，它們特別容易出現在「能跑」的 AI 產出程式碼裡。

先看大圖：兩種慢，其實都是依賴關係判錯

把整體架構攤開來看，問題其實很像兩種排隊方式：

  • network waterfall：明明互不相干的請求，卻排成一列，一個完成後才換下一個。
  • N+1 query：明明可以一次取回的關聯資料，卻先抓清單，再逐筆查詢。

前者讓時間一段一段累加，後者讓查詢數量隨資料筆數增加。兩者背後都該先問同一個問題：「這些動作之間，真的有依賴關係嗎？」

兇手一：network waterfall

network waterfall 指的是請求一個接一個排隊，後面的請求必須等前面的請求完成才能出發。它就像一條只有單線道的路：前車不走，後車就只能全部停在後面。

回想上一節第一個版本的資料抓取，就是典型例子：

const totalQuestions = await Question.countDocuments(filterQuery);

const questions = await Question.find(filterQuery)
  .populate("tags", "name")
  .populate("author", "name image")
  .lean()
  .sort(sortCriteria)
  .skip(skip)
  .limit(limit);

第一行會先等待 countDocuments 回來，第二個查詢才會開始執行。於是總時間大約是兩個查詢時間相加。

但仔細看，這兩個查詢其實互不相干。一個負責計算總數，另一個負責取得目前頁面的資料；它們都只需要同一個 filterQuery，沒有誰需要誰的結果。既然沒有依賴關係，就不必一個等一個。

AI 常犯版：把所有事情依序 await

這種寫法很直覺，也很容易被 AI 產生出來：先做第一件事，等它完成，再做第二件事。對需要前一個結果的流程來說，這是正確的；但對彼此獨立的查詢來說，就像讓兩台可以同時出發的車，共用同一個發車時間。

在 client 端，瀑布通常會更明顯。例如流程是「先抓題目，知道作者後再抓作者資料，再抓這題的答案」，三個請求就會排成一條鏈。每個請求都要等前一個結果，總時間自然變成全部加總。

正解版：把獨立請求平行送出

當兩個請求彼此獨立、誰都不需要誰的結果時，就應該讓它們一起出發。Promise.all 會接收一個 Promise 陣列，等所有 Promise 完成後，再回傳一個結果陣列；結果的順序會對應原本傳入的順序。

const [totalQuestions, questions] = await Promise.all([
  Question.countDocuments(filterQuery),
  Question.find(filterQuery)
    .populate("tags", "name")
    .populate("author", "name image")
    .lean()
    .sort(sortCriteria)
    .skip(skip)
    .limit(limit),
]);

改寫後，兩個查詢會同時送出。總花費時間不再是兩者相加，而是取兩者之中較慢的那一個。原本像兩段接力賽，現在比較像兩條跑道同時起跑。

判斷該不該使用 Promise.all，可以先問一句：「B 需要等待 A 的結果嗎？」

  • 如果不需要，就可以放進同一個 Promise.all，讓它們平行執行。
  • 如果需要，就必須維持先後順序，因為那是真正的依賴關係。

平行執行也不代表可以隨意把所有動作塞在一起。例如「先寫入、再讀取」有明確的先後意義，硬要平行處理就可能形成競態條件（race condition），最後讀到的資料可能還是舊的。

兇手二：N+1 query

第二個兇手不是請求排隊，而是查詢數量突然膨脹。假設頁面要顯示 10 題問題，而且每題都要顯示作者姓名，最直覺的寫法可能是先抓題目，再逐題查作者：

const questions = await Question.find(query);

for (const question of questions) {
  question.author = await User.findById(question.author);
}

這段程式碼的查詢次數是：先用 1 次查詢抓題目清單，再為每一題各查 1 次作者。

  • 10 題會產生 11 次查詢。
  • 100 題會產生 101 次查詢。

這個「1 + N」的形狀，就是 N+1 query。資料量很小時，問題不一定明顯；一旦清單變長，查詢次數就會跟著線性增加，資料庫和整體延遲也會一起承受壓力。

AI 常犯版 vs 正解版：不要逐筆追著關聯資料跑

AI 常犯版是先取得主資料，再在迴圈裡逐筆查詢關聯資料。程式碼看起來容易理解，代價卻是每多一筆資料，就多一次查詢。

正解版是讓資料庫一次帶回需要的關聯。Mongoose 的 .populate() 就是為此而存在：原本欄位裡存的是 ID，populate 會把它換成真正的文件，讓你不必自己寫迴圈逐筆查詢。

回到真實專案中的寫法：

const questions = await Question.find(filterQuery)
  .populate("tags", "name")
  .populate("author", "name image")
  .lean()
  .sort(sortCriteria)
  .skip(skip)
  .limit(limit);

這裡同樣要顯示每一題的作者，但不需要自己對每一題呼叫 User.findById。.populate("author", "name image") 會把作者關聯帶回來，而且只取 name 和 image 這些需要的欄位。

這個欄位選擇也很重要。既然畫面只需要作者名稱和頭像，就不必把整份使用者文件都塞進回傳結果。換句話說，這裡同時處理了兩個效率問題：避免逐筆查詢，也避免回傳不需要的資料。

兩個兇手的對照

症狀AI 常犯寫法代價正解
network waterfall無依賴的請求卻一條條 await時間變成各段相加用 Promise.all 平行送出
N+1 query先抓清單，再逐筆查關聯查詢次數膨脹成 1 + N用 .populate() 一次帶回需要的關聯

不是所有事情都該平行或合併

看到效能問題後，另一個常見誤區是反過來把所有事情都平行化，或把所有關聯資料都一次載入。這同樣可能造成錯誤或浪費。

如果兩個請求之間真的有先後依賴，B 需要 A 的結果，那麼硬要平行只會拿到錯的資料。如果關聯資料很龐大，而目前畫面又不需要全部內容，把它們全部 populate 進來也會增加不必要的負擔。

所以判準不是「平行一定比較好」，而是先確認兩件事：

  • 這些動作之間有沒有真正的依賴？
  • 目前真的需要這些關聯資料嗎？

沒有依賴的工作，可以平行；需要的關聯資料，可以一次帶回；有明確先後關係的工作，則應該保留順序。

小結：把這個觀念掛回依賴關係

network waterfall 是「無依賴的請求卻排隊」，把總時間變成各段相加，用 Promise.all 平行化後，時間可以縮成取最慢的那一段；N+1 query 是「先抓清單、再逐筆查關聯」，讓查詢次數變成 1 + N，用 .populate() 就能讓資料庫一次帶回需要的關聯。兩者的判準其實相同：先問「這兩個動作有沒有真正的依賴」，再決定要平行、要合併，還是維持順序。

到這裡，你已經能分辨「抓得對」和「抓得快」之間的差別。下一節會把視角拉回最上層：面對一段資料，到底該讓它在 server 抓，還是交給 client？那不只是效能問題，更是邊界與取捨的判斷，也是 AI 最常畫錯的一條架構線。
