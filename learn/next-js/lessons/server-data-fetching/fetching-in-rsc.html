在 Server Component 裡抓資料：從 async、await 到直接查 DB

Step 2/4 · 在 RSC 裡抓資料：何時用 server、何時用 client

這一節要完成什麼

你會建立一個能正常抓資料的 App Router 頁面：在 server component 裡使用 async/await 取得查詢參數，呼叫 server action 或直接查詢資料庫，最後把結果交給子元件渲染。

單筆資料頁還要多做一步：如果查不到資料，就轉到 404，而不是讓頁面一路往下執行，直到存取不存在的欄位時才崩潰。

動手前需要什麼

你需要一個 App Router 頁面，例如 app/page.tsx，以及一個資料來源。這個資料來源可以是直接查資料庫的 ORM 或 Mongoose，也可以是像 getQuestions 這樣的 server action。

只要頁面是 server component，也就是沒有加入 "use client"，這兩種資料來源都可以直接使用 await。

先看整體骨架：資料怎麼從網址走到畫面

server component 抓資料的流程，可以先記成一條清楚的路徑：

  1. 把頁面元件宣告成 async。
  2. 先解開 searchParams 或 params。
  3. 把網址中的字串參數轉成查詢需要的型別。
  4. 呼叫 server action 或直接查詢資料庫。
  5. 確認查詢成功，查不到單筆資料時轉到 404。
  6. 把結果交給子元件渲染。

這套骨架就像餐廳的出餐流程：先拿到客人的訂單，再整理成廚房看得懂的格式，接著查資料、確認餐點存在，最後交給畫面端端上桌。任何一步漏掉，最後看到的可能就是空白、錯誤，或一個不該出現的頁面。

步驟一：把頁面元件宣告成 async

先從頁面元件本身開始。打開首頁，你可能會看到這樣的寫法：

async function Home({ searchParams }: RouteParams) {
  const { page, pageSize, query, filter } = await searchParams;

  const { success, data, error } = await getQuestions({
    page: Number(page) || 1,
    pageSize: Number(pageSize) || 10,
    query,
    filter,
  });

  const { questions, isNext } = data || {};

第一行的 async function Home(...) 是整個流程的起點。因為這是 server component，Next.js 允許元件函式回傳 Promise；它會等待函式裡的資料準備完成，再進行渲染。

這和 client component 的處理方式不同。若頁面是 client component，通常要等元件掛載後，再透過 useEffect 抓資料。那樣就像先把空盒子送到畫面上，再從遠方補寄內容；server component 則能在渲染前先把資料準備好。

步驟二：先解開 searchParams

接著處理網址上的查詢參數。這一行是關鍵：

async function Home({ searchParams }: RouteParams) {
  const { page, pageSize, query, filter } = await searchParams;

  const { success, data, error } = await getQuestions({
    page: Number(page) || 1,
    pageSize: Number(pageSize) || 10,
    query,
    filter,
  });

  const { questions, isNext } = data || {};

searchParams 代表網址上的查詢參數，例如 ?page=2&filter=popular。在新版 Next.js 中，searchParams 和動態路由的 params 都是 Promise，所以必須先 await，才能取得裡面的值。

常見的錯誤寫法，是直接把它當成普通物件解構。這樣拿到的不是參數內容，而是一個還沒解開的 Promise；後續的欄位就可能全都變成 undefined，查詢條件也會跟著失效。

還要注意，searchParams 裡的值全部都是字串。網址寫成 ?page=2 時，取得的是字串 "2"，不是數字 2。因此範例才會使用：

async function Home({ searchParams }: RouteParams) {
  const { page, pageSize, query, filter } = await searchParams;

  const { success, data, error } = await getQuestions({
    page: Number(page) || 1,
    pageSize: Number(pageSize) || 10,
    query,
    filter,
  });

  const { questions, isNext } = data || {};

Number(page) || 1 會把頁碼轉成數字；如果沒有頁碼，就使用第 1 頁。pageSize 也用同樣方式，沒有值時預設為 10。少了這層轉換，分頁運算可能會出現把字串接起來，而不是進行數字加減的怪結果。

步驟三：await 資料來源

參數整理好後，才進入真正的查詢。範例裡呼叫的是 getQuestions：

async function Home({ searchParams }: RouteParams) {
  const { page, pageSize, query, filter } = await searchParams;

  const { success, data, error } = await getQuestions({
    page: Number(page) || 1,
    pageSize: Number(pageSize) || 10,
    query,
    filter,
  });

  const { questions, isNext } = data || {};

這裡把剛剛整理好的參數傳給 getQuestions，再用 await 等待結果。回傳值固定採用 { success, data, error } 這種形狀，因此可以直接解構成 { success, data, error }，接著從 data 取出 questions 和 isNext。

如果資料來源是資料庫，也可以直接等待查詢。單筆詳情頁通常會使用像 getQuestion 這樣的 action；它的底層可能直接查詢一筆資料，並且一併帶出相關資料：

const question = await Question.findById(questionId)
  .populate("tags", "_id name")
  .populate("author", "_id name image");

if (!question) throw new Error("Question not found");

return { success: true, data: JSON.parse(JSON.stringify(question)) };

這段查詢有兩個重點。

第一個是 .populate()。資料庫裡的 author 欄位可能只存著使用者 ID，populate 會依照這個 ID 找到真正的作者文件。第二個參數 "_id name image" 則限制只取作者的 ID、名字和頭像。

限制欄位就像打包行李：詳情頁只需要這幾樣東西，就不要把整個使用者文件都塞進回傳結果。資料量較小，傳輸就不會白白變肥、變慢。

第二個重點是：

const question = await Question.findById(questionId)
  .populate("tags", "_id name")
  .populate("author", "_id name image");

if (!question) throw new Error("Question not found");

return { success: true, data: JSON.parse(JSON.stringify(question)) };

JSON.parse(JSON.stringify(question)) 會把 Mongoose 的複雜物件轉成純資料。當結果要透過 server action 傳給畫面時，先做這個轉換，可以避免大型 payload 傳遞時出現問題。

步驟四：查不到資料就轉到 404

單筆查詢最容易被 AI 漏掉的，不是 await，而是「查不到怎麼辦」。正解會在拿到結果後立刻檢查：

const { success, data: question } = await getQuestion({ questionId: id });

if (!success || !question) return redirect("/404");

這裡先等待 getQuestion 回傳，再檢查兩件事：

  • 如果 success 是 false，代表查詢沒有成功。
  • 如果 question 不存在，代表找不到這筆資料。

只要其中一項成立，就執行 redirect("/404")。若漏掉這個判斷，使用者輸入不存在的 ID 時，頁面可能繼續往下渲染，等到程式存取 question.title 等欄位才崩潰。對使用者來說，看到的就不是清楚的 404，而是一個難以理解的錯誤頁。

這裡的 id 也要先透過 await params 取得，規則和 searchParams 相同：它們都是新版 Next.js 中需要等待解開的 Promise。

data: question 是解構時的重新命名。它把回傳物件中的 data 欄位命名為 question，讓後續程式更容易閱讀。判斷也要放在取用資料之前：先確認資料真的存在，再去解構或存取 title、author 等欄位。

步驟五：把資料交給子元件渲染

資料抓好後，頁面本身通常不需要塞滿各種成功、錯誤和空資料的 if。可以把結果交給可重用的 DataRenderer：

<DataRenderer
  success={success}
  error={error}
  data={questions}
  empty={EMPTY_QUESTION}
  render={(questions) => (
    <div className="mt-10 flex w-full flex-col gap-6">
      {questions.map((question) => (
        <QuestionCard key={question._id} question={question} />
      ))}
    </div>
  )}
/>

DataRenderer 負責處理成功、錯誤和空資料等狀態。頁面只需要把查詢結果、錯誤資訊、空資料提示，以及「一筆資料要怎麼畫」的 render 函式交給它。

這樣頁面的職責就很清楚：先 await 資料、確認資料狀態，再把資料交給元件渲染。資料取得和畫面呈現各自負責自己的工作，程式就不會像把廚房、櫃檯和送餐路線全部擠在同一張桌子上。

做完之後，應該看到什麼

完成後，你應該得到一個 async 的 server component，並且具備以下流程：

  1. 使用 await searchParams 或 await params 取得網址參數。
  2. 把需要計算的字串參數轉成數字。
  3. 使用 await 呼叫 server action 或直接查詢 DB。
  4. 用 { success, data, error } 的形狀處理回傳值。
  5. 單筆資料不存在時，轉到 404。
  6. 查詢成功後，把資料交給子元件渲染。

打開瀏覽器時，首屏應該直接帶著資料出現。若在網址後面放入不存在的 ID，應該看到 404，而不是頁面當掉。這兩個結果都符合預期，就代表資料抓取的骨架接對了。

小結

在 server component 抓資料的骨架是：把元件宣告成 async，先 await searchParams／await params 拿到（並轉型）參數，再 await 資料來源（server action 或直接查 DB），用 { success, data, error } 的形狀解構，查不到就 redirect 到 404，最後把資料交給子元件渲染。單筆查詢常用 .populate() 帶出關聯並限制欄位，跨 server action 傳大物件時用 JSON.parse(JSON.stringify(...)) 轉成純資料。

現在先把「能正確抓到資料」這副骨架站穩。下一節會再處理速度問題：一條條 await 排成直線形成的 network waterfall，以及先抓清單、再逐筆查關聯造成的 N+1。這些問題在 AI 產出的程式碼裡很常見，學會辨認後，才能把不必要的等待收掉。
