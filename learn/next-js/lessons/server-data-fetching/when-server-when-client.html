何時用 server、何時用 client：畫出資料邊界

Step 4/4 · 在 RSC 裡抓資料：何時 server、何時 client

學習目標

完成這一節後，你能根據互動需求、SEO、金鑰安全與即時性，判斷一段資料應該在 server 還是 client 抓取，也能辨認兩種常見陷阱：什麼都交給 useEffect，或什麼都硬塞進 server。

先看清楚：你要做的決定是什麼

前面三節已經說明如何在 server 抓資料，但真正的架構判斷還沒結束。實際檢查 AI 產出的專案時，你很可能遇到兩個極端。

第一種極端，是幾乎每個元件開頭都寫著 "use client"，接著 useEffect、useState 滿天飛，整個專案像是又寫回了純 React。另一種極端則相反：連搜尋框、即時驗證這類需要立即回應的互動，都硬留在 server，結果使用者每打一個字，整頁就重新請求一次。

這兩種做法都把資料邊界畫錯了。問題不是「server 一定比 client 好」，而是要看每段資料和互動的需求。server 在首屏、SEO、金鑰安全與請求去重上有優勢；client 則負責瀏覽器 API、使用者操作當下的即時反應，以及元件狀態。

接下來，我們先並排比較兩邊的能力，再用幾個可以實際檢查的問題做判斷。

選項比較：server component 與 client component

把兩種執行環境放在同一張表裡，差異就像廚房和餐桌：server 適合準備資料，client 適合接住使用者的操作。

需求server component（RSC）client component
直接查資料庫、使用 secret 金鑰可以不行
首屏就要有內容、需要 SEO擅長需要搭配其他機制，才看得到內容
使用者操作後即時更新，而且不換頁不行擅長
使用瀏覽器 API，例如 localStorage、geolocation不行可以
事件處理，例如 onClick、onChange不行可以
元件狀態，例如 useState、useEffect不行可以

關鍵差異在於：server component 沒有互動能力。它不在瀏覽器裡執行，因此不能綁事件、不能使用 hook，也不能讀取 localStorage。

反過來，client component 拿不到資料庫與 secret，也不適合獨自承擔 SEO 和首屏內容。把 secret 放進 client，就像把鑰匙直接掛在門外：程式送到瀏覽器後，使用者就有機會取得它。

四個判別問句：把線畫在正確的位置

實際面對一段資料或一個元件時，可以依序問自己以下四個問題。每個「是」，都代表一種明確的方向。

  1. 這段資料會用到資料庫或 secret 金鑰嗎？ 如果會，放在 server。金鑰一旦放進 client，就等於公開。
  2. 這頁需要被搜尋引擎索引，或首屏就要看到內容嗎？ 如果需要，優先放在 server。內容先抓好再送出，使用者和爬蟲才能及早看見。
  3. 使用者操作後，資料要在不換頁的情況下立即更新嗎？ 如果要，這段互動邏輯必須放在 client。
  4. 會使用瀏覽器 API 或事件處理嗎？ 例如 localStorage、位置、媒體裝置、onClick 或 onChange。如果會，就交給 client。

多數真實情境不是二選一，而是兩者一起使用。比如一個問題列表，清單內容要在首屏出現、也可能需要 SEO，因此可以由 server 抓取；清單上方的「投票」按鈕，點下去後要立刻變色並送出請求，則適合切成一個小型的 client component。

這就是 server shell + client island：server 負責外層資料與頁面骨架，client 只負責像島嶼一樣、零星但需要互動的區域。

反例一：什麼都用 useEffect

AI 常犯版：一個明顯只是「讀取並顯示」的頁面，例如文章、商品或問題列表，元件開頭卻寫著 "use client"，再用 useState 和 useEffect 抓資料。

這樣做會讓首屏先空著，SEO 也會吃虧。如果資料請求需要 secret，還可能造成金鑰外洩；多個元件各自抓資料時，也可能把請求排成一條瀑布，讓頁面更慢。

正解版：先問：「這一頁真的需要互動與狀態嗎？」如果答案是不需要，就把資料抓取移回 server component，不要為了熟悉的 React 寫法，硬套上整套 client hook。

這種錯誤通常不是刻意選擇，而是把純 React 的肌肉記憶直接搬進 RSC。看到整頁都標成 "use client" 時，先不要急著接受，先檢查它是否真的需要互動。

反例二：什麼都塞進 server

AI 常犯版：為了維持 server component，把所有事情都留在 server，甚至讓需要即時反應的互動變成「每次操作都重新請求整頁」。

這會讓使用者感覺頁面反應遲鈍，也讓伺服器承擔不必要的重新請求。以下情境都不是 server component 能獨立完成的：

  • 搜尋框要「邊打邊給建議」：需要在使用者輸入的當下觸發更新，server component 綁不了 onChange。
  • 表單要「即時驗證每個欄位」：需要持續保存欄位狀態，server component 沒有 useState。
  • 主題切換、展開收合、輪播：這些是瀏覽器端互動，server component 沒有能力直接處理。

正解版：把互動部分獨立成 client island，讓它自己管理狀態與事件；不要讓整頁陪著一個小按鈕或輸入框重新渲染。

反例三：server component 裡用了 client 的功能

這是比較直接、也很容易被抓到的錯誤：在沒有 "use client" 的元件裡使用 useState、useEffect 或 onClick。由於 server component 不支援這些功能，程式會直接報錯。

AI 常犯版：只要遇到一個互動需求，就把整個大型頁面標成 "use client"。這雖然可能暫時避開錯誤，卻會把原本可以留在 server 的部分也一起送進瀏覽器。

正解版：把真正需要互動的那個小子元件切出去，為它加上 "use client"，其餘 server 部分維持原樣。切得越精準，送進瀏覽器的 JavaScript 就越少。

規則會翻轉的情況：不要把「server 優先」當成鐵律

server 適合抓資料，不代表所有資料都應該由 server 處理。只要需求包含「使用者操作後立即改變畫面」，判斷就會翻轉。

例如，問題列表本身可以由 server 抓取，但「投票」按鈕需要在點擊後立刻變色，也需要送出請求。這時不能因為列表在 server，就把按鈕也硬留在 server；正確做法是保留 server 的資料外殼，再把按鈕拆成 client island。

同樣地，搜尋頁的初始結果可以由 server 提供，但搜尋框的輸入、建議顯示與欄位狀態仍需要 client。不要用一條規則蓋住整個頁面，要沿著資料和互動的邊界逐塊判斷。

最後的決策檢查表

  • 要使用資料庫或 secret 金鑰 → 放在 server。
  • 需要 SEO，或首屏就要看見內容 → 放在 server。
  • 使用者操作後要即時更新 → 放在 client。
  • 需要瀏覽器 API、事件處理或元件狀態 → 放在 client。
  • 同時需要兩者 → 使用 server shell，再把互動葉節點切成 client island。
  • 看到整頁的 "use client" → 先問它是否真的需要互動；如果不需要，就把資料抓取移回 server。
  • 看到需要即時互動的功能卻硬留在 server → 把那一小塊拆成獨立的 client component。

小結

資料邊界不是 server 或 client 的二選一，而是一道取捨題。資料庫、secret、SEO 與首屏內容交給 server；即時互動、瀏覽器 API、事件與元件狀態交給 client。要避開兩種極端：不要把讀取顯示的頁面全寫成 "use client" 加 useEffect，也不要把需要即時互動的功能硬塞進 server。多數時候，正解是由 server shell 抓好資料，再把互動的葉節點切成 client island。

走完這四步，你就有一套可以檢查資料邊界的方法：先看資料是否需要 server 的能力，再看互動是否需要 client 的能力，最後把兩者交會的地方切成清楚的小元件。下次打開 AI 產出的頁面，先找它把線畫在哪裡，再問一句：「這條線畫對了嗎？」
