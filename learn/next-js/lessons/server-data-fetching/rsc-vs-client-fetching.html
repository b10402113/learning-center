抓資料要放哪裡？比較 client 的 useEffect 與 RSC

Step 1/4 · 在 RSC 裡抓資料：何時 server、何時 client

先看全貌：資料是在瀏覽器抓，還是在 server 先準備好？

你請 AI 生一個 Next.js 首頁，打開瀏覽器後，畫面先是一片空白，或是中間出現一個轉圈圈的 spinner；過了一兩秒，內容才一筆一筆跳出來。看起來像是「有在跑」，但如果這時按右鍵檢視網頁原始碼，會發現 HTML 裡幾乎什麼都沒有。把瀏覽器的 JavaScript 關掉再看一次，頁面甚至會直接失去作用。

這種情況通常來自同一個熟悉模板：元件開頭加上 "use client"，用 useState 管理資料，再用 useEffect 在畫面掛載後執行 fetch。它之所以常見，是因為我們從純 React 轉過來時，往往就是這樣寫。

但 Next.js 預設提供了另一條路。每個元件原本就是 React Server Component（RSC，也就是在伺服器上執行的元件），你可以像寫一般的 async 函式一樣，直接在 server 把資料抓好，再交出一段已經有內容的 HTML。

這一節要回答的不是「哪種寫法比較潮」，而是：為什麼資料常常應該先在 server 準備好？答案牽涉到好幾件事：首屏顯示速度、SEO、request dedup、金鑰安全，以及 network waterfall。先把這些關係看清楚，後面才知道什麼時候不該反射性地加上 "use client"。

AI 常犯版：先讓 client render，再用 useEffect 補資料

先攤開最熟悉的寫法。這是一個 client component：元件掛載後才抓資料，並用 loading 與 error 兩個狀態控制畫面。

import React, { useState, useEffect } from 'react';

function App() {
  const [data, setData] = useState(null);
  const [isLoading, setIsLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    const fetchData = async () => {
      try {
        const response = await fetch('https://api.example.com/data');
        const jsonData = await response.json();
        setData(jsonData);
      } catch (error) {
        setError(error);
      } finally {
        setIsLoading(false);
      }
    };

    fetchData();
  }, []);

  if (isLoading) {
    return <div>Loading...</div>;
  }

  if (error) {
    return <div>Error: {error.message}</div>;
  }

  return (
    <div>
      <h1>Data from API:</h1>
      <pre>{JSON.stringify(data, null, 2)}</pre>
    </div>
  );
}

export default App;

這段程式碼的順序是：

  1. 元件先渲染一次，但此時還沒有資料。
  2. 瀏覽器先把這個空殼或 loading 畫面顯示出來。
  3. useEffect 在元件掛載後執行，送出網路請求。
  4. 等回應回來後，setData 觸發重新渲染。
  5. 畫面最後才出現真正的內容。

換句話說，資料像是搬家工人：頁面先把空房子交到使用者眼前，資料才從瀏覽器裡慢慢搬進來。這不一定完全不能用，但它會讓使用者第一眼看到空白或 spinner，也會把資料抓取責任全部推到 client。

正解版：讓 RSC 在 server 先把資料準備好

同樣的事情換成 RSC，可以直接把元件寫成 async 函式。不需要 hook，也不需要自己維護 loading 狀態。

import React from 'react';

async function App() {
  const response = await fetch('https://api.example.com/data');
  const jsonData = await response.json();

  return (
    <div>
      <h1>Data from API:</h1>
      <pre>{JSON.stringify(jsonData, null, 2)}</pre>
    </div>
  );
}

export default App;

這裡的關鍵差異，不只是程式碼少了幾行，而是資料抓取的位置不同。RSC 會先在伺服器上取得資料，等元件準備好之後才渲染成 HTML。HTML 送到瀏覽器時，內容已經在裡面了。

因此，使用者看到的第一版畫面就有資料，搜尋引擎爬蟲收到的也會是完整內容。原本由 client 管理的 useEffect、useState、loading 與 error 狀態，在這個簡單情境中都不再需要。

RSC 的邊界：不只可以呼叫 API，也能查資料庫

RSC 跑在伺服器上，所以它能接觸的資料來源不只有 HTTP API。你也可以直接呼叫 ORM（例如 Prisma）或 MongoDB／Mongoose，省掉「先開一支 API，再由自己的 server component fetch 那支 API」的中間層。

import React from 'react';
import prisma from './prisma';

async function App() {
  const users = await prisma.user.findMany();

  return (
    <div>
      <h1>Data from Prisma:</h1>
      <pre>{JSON.stringify(users, null, 2)}</pre>
    </div>
  );
}

export default App;

這件事在 client component 裡做不到，因為瀏覽器不應該直接連到資料庫，也不該拿到資料庫連線字串。把資料抓取邏輯和資料源留在 server，就像把保險箱放在辦公室內，而不是搬到街上讓每個路人都能碰到：程式碼更短，敏感資訊也不會跟著送進瀏覽器。

把 AI 常犯版與正解版放在一起比較

兩種寫法的差異，可以從幾個面向一起看。左邊是 client 的 useEffect 抓法，右邊是 RSC 在 server 抓資料。

為什麼 server 抓資料通常更有利？

首屏：不要先把空殼交給使用者

FCP（First Contentful Paint，首次內容繪製）指的是畫面第一次出現內容的時間。server 抓資料時，頁面在被渲染的時候，資料就已經包在裡面，因此使用者更快看到真正的內容。

client 抓資料則要等瀏覽器載入 JavaScript、執行元件、送出請求，再等回應回來。這一連串工作完成之前，使用者通常只能看到空畫面或 spinner。

SEO：爬蟲收到的是完整頁面，還是空殼？

搜尋引擎爬蟲比較容易索引伺服器渲染好的內容，因為它收到的就是已經成形的 HTML。client 抓資料時，爬蟲一開始可能只看到空殼，必須等抓取與渲染完成後才看得到內容，這對排名不利。

request dedup：同一份資料不要重複搬運

request dedup，也就是請求去重，指的是把同一時間、對同一份資料發出的重複請求合併起來。Next.js 在 server 抓資料時，會自動合併同一時間對同一份資料的重複請求，只送出一次。

少了這層處理，如果不同元件各自需要同一份資料，就可能各送各的請求，像是同一箱貨被不同卡車重複運送。

金鑰安全：放在 server 才不會變成公開資訊

把 API 呼叫留在 server，API 金鑰這類敏感資訊就能留在伺服器，不會出現在瀏覽器裡。client 端的程式碼對使用者是透明的，因此任何寫進 client 程式碼的金鑰，都等於公開。

network waterfall：不要讓請求排成一條長隊伍

network waterfall（網路瀑布）描述的是請求一個接一個排隊的情況。client 抓資料時，常常要先等畫面掛載，接著送出第一個請求；等第一個回應回來，才知道下一步要抓什麼，整體就容易串成一條鏈。

server 端則能把彼此不相關的請求平行送出，縮短整條等待鏈。這也是後續內容會再展開的重點。

這個觀念要記在哪裡？

傳統 React 的 useEffect 抓資料，會讓首屏先空著、SEO 吃虧、請求容易重複、金鑰可能外洩，還可能排成一條 network waterfall。RSC 讓你在伺服器上直接 async 抓資料（甚至直接查資料庫），HTML 送出時內容已就緒，同時解掉 FCP、SEO、dedup、安全與瀑布這幾個問題。這也是為什麼在 Next.js 裡，預設應該讓 server component 負責資料，而不是反射性地加 "use client" 再 useEffect。

這裡的核心連結是：資料抓取的位置，會連動影響首屏、SEO、安全與請求效率。client component 並不是永遠不能使用；但如果元件只是為了抓資料而加上 "use client"，就應該先問自己：這份資料是否可以在 RSC 裡先準備好？
