什麼是 Framework？React 留下的坑與 Next.js 的角色

Step 2/4 · Why Next.js

學習目標

能分辨 framework 與 library 的差別，說出 React 自己留下了哪些坑，以及 Next.js 如何用「蓋在 React 之上的框架」補起這些坑。

前言：React 給你零件，卻沒給你說明書

上一節我們看到工具鏈一代一代演進，Next.js 接在 React 後面登場。但「React 之後」這句話還太模糊，得先回答一個更基本的問題：React 到底給了你什麼、又沒給你什麼？

想像你剛學會 React，想替網站多加一個「關於我們」頁面。你會發現，React 本身居然不管「網址對應到哪個頁面」這件事，你得自己挑一個路由套件、自己設定打包工具、自己決定資料要在哪裡抓。每個決定都合理，但全部加起來，你花在「決定基礎設施」的時間，可能比寫應用邏輯還多。這個落差，就是「函式庫」與「框架」的分界，也是 Next.js 存在的理由。

什麼是框架？

在軟體開發裡，框架（framework）是一套帶著預先定義好的規則與慣例的工具，讓你有章法地把應用程式搭起來。它會先替你決定好整體架構、設計模式與工作流程，你只要專心寫應用邏輯，不用煩惱底層設計。

說得更白話一點，框架替常見功能準備好了現成解法，例如連接資料庫、管理路由、處理身分驗證等等。你不需要從零決定「路由要怎麼設計」、「資料庫連線要放哪」，框架已經有一套公認的作法，你只要照著填上自己的商業邏輯。

框架與函式庫，差在「誰在主導」

很多人會把這兩個詞混著用，但它們其實分得開。關鍵差別在於控制權在誰手上：用函式庫時，是「你呼叫它」；用框架時，是「它呼叫你」。函式庫像一組工具，你決定什麼時候拿出來用；框架則像一棟已經蓋好的房子，你只能決定家具怎麼擺，管線和隔間照它的規矩來。

面向函式庫（library）框架（framework）
誰在主導你決定何時呼叫它它定義流程，你照規矩填內容
提供的範圍通常只解決單一問題整體架構、慣例與工作流程
你還得自己處理路由、打包、資料抓取、認證…多半只剩應用邏輯
例子React 本身偏向這個角色Next.js

很多人以為 Next.js 是一門新語言，或是一個跟 React 打對台的函式庫。都不是。React 專注在把畫面用元件組起來，比較像函式庫；Next.js 則是在它之上，補上框架該有的架構與慣例。

React 留下的坑，正是框架登場的地方

React 把前端開發往前推了一大步。它鼓勵你用元件思考，把使用者介面拆成一小塊一小塊的程式碼；你用 state 描述互動，再把這些元件彼此連接起來，形成整個應用的資料流。這套思維很棒，但它只涵蓋了「畫面」這一塊。

問題出在，要真正實現一整套 React 架構，需要應用程式各個部分深度整合：路由要接、資料要在對的時機抓、伺服器渲染要處理、認證要另外想辦法。這些 React 沒有預設答案，於是就出現了大量「每個專案都自己拼一次」的基礎建設工作。框架登場，正是為了終結這種重複造輪子。

Next.js 的角色：蓋在 React 之上的那一層

Next.js 就是 React 的延伸：它建立在 React 之上，把預先做好的解法、即用的功能，以及一些額外的能力疊上去，藉此擴充 React 的能耐。這也是為什麼學 Next.js 不需要打掉重練，你原本的 React 知識完全沿用。

反過來說，Next.js 也有一個明確的前提：你最好先懂 React。熟悉 React 的人（知道怎麼建立元件、管理 state、組織程式碼與資料夾結構），走 Next.js 這條路會順暢很多；如果完全沒碰過 React，建議先把元件、state、程式碼結構這些基本功補起來，再回來學框架。把這個前提記牢，後面談「代價」時才不會覺得被突襲。

小結

框架是帶著預先定義規則與慣例的工具，替你鋪好整體架構、設計模式與工作流程，還內建路由、資料庫、認證等常見功能的解法。它與函式庫最大的差別是控制權：函式庫由你呼叫，框架則反過來主導流程。React 本身偏函式庫，只負責用元件組畫面，卻沒內建路由、渲染、資料抓取等整合工作；Next.js 就是蓋在 React 之上、把這些洞補起來的框架，而且不需要你放棄原本的 React 知識。

把「Next.js 是 React 的框架」這個定位釘好之後，下一步就能問得更具體：它到底替你買到了哪些回報？下一節會把四類價值（省下工具配置、全端能力、效能、SEO）一一拆開來看。
