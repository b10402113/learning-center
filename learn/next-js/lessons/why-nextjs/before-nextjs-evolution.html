Next.js 之前：Web 工具鏈怎麼一路演進

Step 1/4 · Why Next.js

學習目標

能說出 Next.js 之前 web 工具鏈的演進順序，以及每一代是為了解決上一代的什麼問題而出現。

前言：為什麼每隔幾年就要重學一套？

你可能遇過這種事：幾年前學的 jQuery，現在拿去面試卻被說「這很舊了」；好不容易把 React 摸熟，又聽人說「現在都用 Next.js」。工具一直換，難免讓人心裡犯嘀咕：這些新東西到底是真的解決了問題，還是只是大家趕流行？

要判斷 Next.js 值不值得學，光看它的功能列表不夠。你得先把它放回時間線上，看看它前面站了哪些工具、每一個是踩著誰的痛點站起來的。一旦發現每一代都是為了解決上一代的極限，Next.js 為什麼出現就不再是廠商行銷，而是一條講得通的因果關係。這一節就把這條線拉出來。

1995 年的一門小語言，怎麼變成整個 Web 的骨幹

故事從 1995 年開始。那一年，Brendan Eich 在 Netscape 寫出了一門原本只是拿來做網頁小互動的語言，也就是 JavaScript。它一開始並不受重視，真正讓它竄紅的是 2000 年代初期：Google 用 JavaScript 做出了可以拖曳、縮放、即時載入的地圖探索體驗，讓整個業界看見「原來網頁可以不只換頁，而是像應用程式一樣互動」。

從那之後，JavaScript 從配角變成主角。但語言本身只給你最基本的零件，真正讓開發者能規模化寫應用的，是一代又一代疊上去的工具與框架。這條線大致是：jQuery → Angular → Node.js → React.js → Next.js。每一次接棒，都不是因為前一代一無是處，而是因為它走到了自己的極限。

每一代都在補上一代的洞

先講最早期。用純 JavaScript（俗稱 vanilla JavaScript）操作畫面，你得自己找出元素、綁事件、手動改內容，程式碼又長又容易出錯。jQuery 的出現把這些動作包成簡潔的方法，大幅簡化了 DOM 操作，成為那個年代的事實標準。

但當網頁從「一堆頁面」變成「一個大型應用」，jQuery 這種以「直接操作畫面元素」為中心的寫法開始撐不住。於是有 Angular 這類框架，把畫面拆成一個個有結構的元件。接著 Node.js 問世，讓 JavaScript 能跑在瀏覽器之外，前端工程師也能寫伺服器端程式。再來是 2015 年登場的 React.js，它用元件化加上 Virtual DOM 重新定義了前端開發方式。而 React 自己也有沒解決好的地方，於是 Next.js 接棒，它正是 Meta（React 的創造者）現在明確推薦的開發工具。這就是這一節要建立的視角：Next.js 不是天上掉下來的新玩意，而是這條演化線的最新一站。

用「Hello World」比較，新工具看起來反而更囉唆？

這裡有個很容易讓人誤會的現象。同一個「點按鈕跳出 Hello World」的功能，用愈新的工具寫，程式碼反而愈長。先看最原始的 vanilla JavaScript：

// HTML: <button id="btn">Click Me</button>

document.getElementById('btn')
    .addEventListener('click', function () {
        alert('Hello, World!');
    });

換成 jQuery，選取按鈕變得簡單許多：

// HTML: <button id="btn">Click Me</button>

$('#btn').click(function () {
    alert('Hello, World!');
});

到了 Angular，你得先宣告一個元件、定義它的 template、再寫一個方法：

<!-- HTML: <button (click)="showMessage()">Click Me</button> -->

import { Component } from '@angular/core';

@Component({
    selector: 'app-example',
    template: `<button (click)="showMessage()">Click Me</button>`
})
export class ExampleComponent {
    showMessage(): void {
        alert("Hello, World!");
    }
}

React 也差不多，一個 class、一個方法、一個回傳按鈕的 render：

import React from 'react';

class ExampleComponent extends React.Component {
    showMessage() {
        alert('Hello, World!');
    }

    render() {
        return <button onClick={this.showMessage}>Click Me</button>;
    }
}

看到這裡，你可能會想：「等等，程式碼明明變多了，這跟前面說的『提升效率』不是矛盾嗎？」如果只看這個最小範例，確實如此。但我們真正在寫的從來不是 Hello World，而是有幾十上百個畫面、要不斷擴充的專案。比較的單位一旦換成大專案，結論就反過來了。

新工具在大專案上贏在哪裡

為什麼規模一大，現代框架就勝出？原因主要有三：

第一是元件化架構（component-based architecture）。React 和 Angular 鼓勵你把畫面拆成可重複使用的小元件。舉例來說，你做了一個 Button 元件，之後整個應用程式任何地方都能重複使用它。這種重用性讓程式更好維護，也更容易隨需求長大。

第二是Virtual DOM（虛擬 DOM）。它是真實 DOM 的輕量替身。當應用程式狀態改變，框架會先在虛擬 DOM 上算出新舊版本的差異（這個比對過程叫 diffing），再只把真正有變動的部分更新到真實 DOM，而不是整個畫面重畫一遍，因此效能更好。

第三是生態系與社群。像 React 這樣的主流工具，背後有龐大活躍的社群，提供了大量資源、完整文件、可重複使用的套件，以及即時的錯誤修正與支援。你遇到問題時，多半已經有人踩過同一個坑。

把這三點放在一起看，就能理解那句常被引用的話：「唯一不變的就是改變。」工具會一直換，而每一代之所以能取代上一代，是因為它在大規模情境下更有效率。這不是流行，而是規模逼出來的演化。

小結

JavaScript 在 1995 年誕生，2000 年代靠 Google 地圖走紅。之後工具一代接一代：jQuery 補 vanilla JavaScript 的不足，Angular 帶入元件化，Node.js 讓 JS 能寫後端，React 用元件與 Virtual DOM 改變前端，Next.js 則接手處理 React 留下來的問題。單看 Hello World，新工具程式碼更長；但專案的規模一大，元件化、Virtual DOM 與社群生態帶來的效率就會勝出。

知道了工具是怎麼一代一代補洞的，下一個問題就具體了：React 到底留下了哪些洞，讓 Next.js 有機可趁？下一節會把「框架」與「函式庫」分清楚，看看 Next.js 蓋在 React 之上，究竟補了什麼。
