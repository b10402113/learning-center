「use client」的傳染性：邊界是怎麼擴散的？

Step 1/4 · Client 邊界陷阱與 client-only 套件

先看全貌：一行指令，可能讓整棵元件樹改變身分

你請 AI 做一個首頁，結果畫面能顯示、按鈕也能操作，看起來一切正常。可是打開瀏覽器的載入檔案一看，整頁的 JavaScript 都被送過來了，連完全不互動的問題列表和側欄也沒被放過。

問題往往不是功能寫錯，而是 "use client" 放錯位置。它不是只替某個元件貼上的小標籤，而像是在模組樹上畫出一條邊界：從這個檔案開始，往下引入的模組都可能被帶進 client bundle。

上一課提過，理想的畫面應該像一大片 server shell，中間只點綴幾座 client island。這一課要進一步看清楚：邊界為什麼會擴散、哪些寫法最容易出錯，以及如何把 client 範圍縮回真正需要互動的葉節點。

學習目標

學完這一課，你應該能解釋 "use client" 為什麼是一個「子樹標記」：被它引入的模組，包括原本的 server component，都可能被打包進 client bundle；也能辨認兩種常見錯誤——把 "use client" 掛得太高，以及在 client component 裡 import server component。

"use client" 標的是模組，不是單一元件

在 App Router 裡，每個檔案預設都是 server component。當你在檔案最上方寫下 "use client"，標記的是整個模組，而不是其中某個函式或某個 JSX 區塊。

從這個檔案開始，它本身以及它 import 的模組，都會被歸類成 client code，最後一起進入瀏覽器需要下載的 client bundle。這就像一列火車換了軌道：前面的車廂一旦駛上 client 的軌道，後面掛著的車廂也會跟著走。

也可以把它想成一座圍籬。"use client" 是在模組頂端畫下的界線；client 這一側的程式碼會送到使用者的瀏覽器，server 這一側的程式碼才有機會留在伺服器。圍籬畫得越高，裡面被一起搬到瀏覽器的東西就越多。

錯法一：把 "use client" 掛得太高

如果 page.tsx、layout.tsx，或包住整個畫面的父元件被標成 client，底下的子元件就可能一起被拉進 client。即使它們只是負責顯示內容、完全不需要互動，也逃不出這個範圍。

AI 常犯版：頁面本身只是把幾個區塊排在一起，卻在第一行加上 "use client"。結果 HomeFeed、RightSidebar 和 QuestionList 都被拖進 client code。

"use client";

import { HomeFeed } from "./HomeFeed";
import { RightSidebar } from "./RightSidebar";
import { QuestionList } from "./QuestionList";

export default function Page() {
  return (
    <main>
      <HomeFeed />
      <RightSidebar />
      <QuestionList />
    </main>
  );
}

正解版：拿掉 page 上的 "use client"，讓它維持 server component。每個子元件再依照自己的需求決定身分；真正需要互動的 VoteButtons，才在自己的檔案頂端標記。

import { HomeFeed } from "./HomeFeed";
import { RightSidebar } from "./RightSidebar";
import { QuestionList } from "./QuestionList";
import { VoteButtons } from "./VoteButtons";

export default function Page() {
  return (
    <main>
      <HomeFeed />
      <RightSidebar />
      <QuestionList />
      <VoteButtons targetId="123" />
    </main>
  );
}

// VoteButtons.tsx 的第一行才是 "use client"

這兩種寫法的畫面可能一模一樣，但邊界完全不同。前者像把整棟房子都接上發電機，只因為其中一個房間需要開燈；後者則只把電接到真正需要互動的房間。

錯法二：在 client component 裡 import server component

另一個常見誤區，是以為 server component 可以隨意被 client component import。實際上，import 會把模組拉進相同的 bundle；當 client component 直接 import server component 時，後者就會失去原本的 server 身分，改以 client code 的形式被送出。

這會帶來兩個問題：它不能再安全地碰資料庫或密鑰，也不能再宣告 async。因此，組合方向是單向的：server 可以 import client，但 client 不能直接 import server。

組合方向 結果
server import client 可以，互動元件可以作為 server 畫面中的 client island。
client import server 不應該這樣做，server component 會失去 server 身分，並可能被帶進 client bundle。

真實專案中的正確小島：DevFlow 的 Votes

DevFlow 的 Votes 元件就是一座切得乾淨的 client island。它需要綁定點擊事件、讀取登入狀態，還要處理 loading state，所以在檔案頂端明確標上 "use client"。

先看它引入的內容：

"use client";

import Image from "next/image";
import { useSession } from "next-auth/react";
import { use, useState } from "react";

import { toast } from "@/hooks/use-toast";
import { createVote } from "@/lib/actions/vote.action";
import { formatNumber } from "@/lib/utils";

這裡有一個容易混淆的例外：createVote 是 server action，卻可以被 client 元件 import。這不代表 server action 的實作會整段被塞進 client bundle。Next.js 會在編譯時把這個 import 換成一個可呼叫伺服器的參照，因此真正執行在伺服器上的邏輯不會被打包送出。

所以，client island 仍然可以透過 server action 修改資料；關鍵在於這不是把一般的 server component 直接 import 進 client，而是使用 server action 提供的特殊呼叫方式。

別搞混：client component 仍可能先在 server 預先渲染

加上 "use client"，不代表這個元件的程式碼「絕對不會」在伺服器上執行。為了讓首屏更快，Next.js 會先在伺服器把 client component 渲染成 HTML，送到瀏覽器後，再 hydrate，也就是補上互動能力。

因此，client component 裡的 console.log，可能同時出現在終端機和瀏覽器的 console。

不過，「先在 server 預先渲染」和「以 server component 的身分執行」是兩件事。前者只是先把畫面畫出來；一旦這段程式碼被歸類為 client，它的互動邏輯、狀態，以及它 import 的整個 bundle，終究都要送到瀏覽器。

這也是下一課的伏筆：有些套件連預先渲染都無法承受，因為它們在 server 上根本碰不到 window。

把這個觀念掛回整體架構

"use client" 是模組層級的指令，標記的是一整棵子樹。被它 import 的模組，包括原本的 server component 與第三方套件，都可能被打包進 client bundle。最常見的兩個錯誤，是把指令掛得太高，拖著整個畫面一起變成 client；以及在 client component 裡 import server component，讓對方失去 server 身分。較穩妥的做法，是把 client 邊界推到最外圍的葉節點，讓需要互動的部分保持小而集中。

現在可以把前一課的「server shell + client islands」看得更精準：server shell 不只是外框，它也負責把 client 邊界控制在最小範圍；client island 則只承擔瀏覽器互動。下一節會接著處理另一種陷阱：有些套件天生只認瀏覽器，連在 server 上被預先渲染都撐不住。
