驗收 AI 的 client 邊界：一張檢查表

Step 4/4 · Client 邊界陷阱與 client-only 套件

學習目標

拿到一份 AI 產出的 Next.js 元件樹時，你能判斷三件事："use client" 是否放得太多、browser-only 套件是否漏了 ssr: false，以及原本應該留在 server 的 component 是否被拉進了 client bundle。

前言：看到邊界，先問「為什麼在這裡」

你可能遇過這種情況：AI 產出的頁面功能完全正常，測試也都通過，卻讓頁面變慢、bundle 變大，甚至把不該送到瀏覽器的程式碼一起打包出去。

這類問題很難靠功能測試抓出來，因為按鈕還是能按、畫面還是能顯示。真正的驗收方式，是沿著元件樹檢查每一條 client 邊界，問清楚它為什麼畫在這裡。

前三節已經準備好三個零件：client 邊界會往下傳染、有些套件只認瀏覽器，以及可以用 next/dynamic 搭配 ssr: false 把它們隔離。這一節要把零件組起來，變成 code review 時可以直接使用的判斷方法。

三種處理方式：先把選項攤開比較

面對一個元件，你通常有三條路：留在 server、標成 client island，或是動態載入並跳過 SSR。它們不是同一種寫法的不同外觀，而是三種不同的取捨。

處理方式適用時機代價
留在 server（不加指令）不需互動、不碰瀏覽器 API，或需要抓資料、讀取密鑰不能使用 state、事件與 effect
標成 client island（"use client"）需要互動、state、effect 或瀏覽器 API，而且套件支援 SSR該元件子樹的 JavaScript 會進入瀏覽器 bundle
動態載入 + ssr: false第三方套件完全不支援 SSR，例如需要 DOM 的編輯器該元件不會有 server 產生的 HTML

可以把它想成建築物的分區：server 是成本最低的主體；client island 是靠近葉節點的小房間，只在真正需要互動的地方開門；dynamic import 則像最後的逃生門，只有套件根本無法在 server 求值時才使用。

因此，預設應該先留在 server。需要 client 時，邊界要盡量小、盡量往葉節點推。只有 browser-only 套件無法在 server 執行時，才使用 dynamic import。

判別問句：沿著元件樹逐層檢查

  1. 這個元件真的需要互動、state、effect 或瀏覽器 API 嗎？ 如果不需要，就不該有 "use client"。這是第一道濾網，可以先抓出 AI 無差別標記的 server component。
  2. "use client" 掛在哪一層？ 如果它出現在 page.tsx、layout.tsx，或是一個包住大半畫面的父元件第一行，通常代表邊界掛得太高。繼續問：能不能把它往下移到真正需要互動的葉節點？
  3. 這個 client 元件 import 了什麼？ 逐一查看 import。是否整包載入工具庫？是否引入 server-only 模組，例如資料庫連線或密鑰讀取？這些內容一旦被 client 元件 import，就可能被打包送到瀏覽器。
  4. 它是否 import 了 server component？ 如果 client component 直接 import 原本的 server component，對方會以 client code 的形式被送出，失去原本的 server 身分。看到 async 函式被塞進 client 檔案時，就要特別小心。
  5. 第三方套件在 server 執行時，會不會碰 window 或 document？ 如果會，只有 "use client" 還不夠，因為元件仍可能在伺服器預先渲染而失敗。這時要確認是否搭配 next/dynamic 與 ssr: false。

正解版：小而準的 client island

先看 DevFlow 的 Votes。它是一個嵌在 server 卡片裡的葉節點，需要綁定點擊事件、讀取登入狀態，並管理 loading 狀態。因此，它使用 "use client" 是合理的。

"use client";

import Image from "next/image";
import { useSession } from "next-auth/react";
import { use, useState } from "react";

import { toast } from "@/hooks/use-toast";
import { createVote } from "@/lib/actions/vote.action";
import { formatNumber } from "@/lib/utils";

把判別問句套上去，答案很清楚：它需要互動嗎？需要。邊界在葉節點嗎？是。import 裡有 server-only 模組嗎？沒有。它有直接 import server component 嗎？沒有。是否使用了必須避開 SSR 的 browser-only 套件？沒有。

這就是健康的 client island：範圍小，理由明確，沒有順手把整棵元件樹拖進瀏覽器。

AI 常犯版一：把 server component 拉進 client

下面這種寫法看起來很直覺：卡片需要投票按鈕，所以 AI 乾脆把整張卡片標成 client，順手 import 顯示統計資料的元件。

"use client";

import { QuestionStats } from "./QuestionStats"; // 原本是 async server component

export function QuestionCard({ id }: { id: string }) {
  return (
    <article>
      <QuestionStats id={id} />
      <VoteButtons targetId={id} />
    </article>
  );
}

QuestionStats 原本是 async、會自行抓資料的 server component。但它被 client 檔案 import 後，就會以 client code 的形式處理。它不能再照原本的方式 await 抓資料，也不能碰密鑰，相關程式碼還會被送往瀏覽器。

正解是讓 QuestionCard 保持 server component，讓 QuestionStats 繼續留在 server；只有真正需要互動的 VoteButtons 才標成 client。不要為了一片互動的小葉子，把整棵樹砍成 client。

AI 常犯版二：只加指令，忘了隔離 browser-only 套件

另一個常見錯誤，是遇到編輯器或其他需要 DOM 的套件時，只補上一行 "use client"，卻沒有處理 SSR。

這樣做仍可能在 build 時遇到 window is not defined。原因是 "use client" 並不代表套件完全不會在 server 預先求值或渲染。遇到這類 browser-only 套件，應該檢查是否使用 next/dynamic，並設定 ssr: false。

反例翻轉：什麼時候掛高一點反而合理？

「client 邊界越低越好」是判斷方向，不是不能違反的鐵律。當整塊畫面高度互動，或整棵子樹都必須使用某個 hook-based 狀態庫時，在較高層標上 "use client" 可能是合理的。關鍵是這要經過刻意判斷，而不是 AI 順手加上後就不再檢查。

ssr: false 也不能看到 browser-only 就一律使用。內容為主、需要 SEO 的區塊如果跳過 SSR，首屏可能缺少內容，也可能造成版面跳動。

例如 next-themes 這類 provider，通常使用一個薄的 client 包裝就足夠，不需要把整個 layout 都拉成 client，也不需要動用 dynamic import。

檢查表：review 時直接照著問

① 每個 "use client"：這個元件真的需要互動、state、effect 或瀏覽器 API 嗎？不需要就刪掉。
② 邊界層級：它掛在葉節點，還是拖著整棵子樹？能往下推，就往下推。
③ import 清單：有沒有 server-only 模組或 server component 被 client import？有就拆開。
④ browser-only 套件：它會不會在 server 碰 window 或 document？會就確認是否搭配 ssr: false。
⑤ 代價檢查：使用 dynamic 的元件，是否真的不依賴首屏 HTML 撐起主要內容？

最後的決策規則

驗收 client 邊界時，先用這句話做判斷：能留在 server，就不要加 client；需要互動，就把 client island 壓到最小；只有無法支援 SSR 的 browser-only 套件，才使用 dynamic import + ssr: false。

接著逐一確認：它需要互動嗎？邊界掛在哪一層？import 了什麼？有沒有把 server component 拉進 client？browser-only 套件有沒有正確隔離？這套問句能讓你從「功能對不對」再往前一步，檢查「邊界畫在哪裡，以及這樣畫要付出什麼代價」。
