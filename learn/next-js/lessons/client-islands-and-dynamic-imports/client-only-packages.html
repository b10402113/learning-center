client-only 套件：為什麼 MDX editor 與 next-themes 不能直接在 server 跑？

Step 2/4 · Client 邊界陷阱與 client-only 套件

先看整張地圖：問題不只在 use client

你把 Markdown 編輯器放進表單，檔案頂端也加上了 "use client"，原本以為它已經被送進瀏覽器。結果執行 next build，終端機卻冒出 ReferenceError: window is not defined。

這個錯誤很容易讓人誤會：既然元件是 client component，為什麼 server 還會碰到它？關鍵是，client component 仍然可能先在伺服器上預先渲染一次。"use client" 是在元件邊界上做標記，不是貼上一張「禁止 server 接近」的封條。

因此，這一節要建立的是一張清楚的架構圖：

  • 需要瀏覽器能力的套件，不能直接放進 server render 流程。
  • 像 next-themes 這類 provider，適合用一層很薄的 client wrapper 隔離。
  • 像 MDX editor 這類依賴真實 DOM 的元件，除了 "use client"，還需要用 next/dynamic 搭配 ssr: false，直接跳過 server render。

可以把它想成一棟建築：大樓主體仍然可以在 server 端蓋好，只有必須接上瀏覽器設備的房間，才另外做成小型的 client island。不要為了裝一盞需要電力的燈，就把整棟大樓改成發電廠。

學習目標

完成這一節後，你應該能辨認哪些第三方套件是 browser-only，例如 MDX editor 與 next-themes；說明它們為什麼會在 server render 時出錯；也知道該如何把這些 client-only 部分隔離成一個小而清楚的 client island。

什麼是 client-only 套件？

有些第三方套件從設計開始，就假設自己正在瀏覽器裡執行。它們可能在模組載入時讀取 window，在渲染時量測 DOM 節點，或把資料寫進 localStorage。

這些能力在瀏覽器裡很自然，但伺服器上的 Node.js 環境沒有 window、document 或真實的 DOM。當 Next.js 嘗試在 server 上載入或渲染這些套件時，就像要求沒有游泳池的地方量測水深，最後只能得到 is not defined 或類似的錯誤。

遇到陌生套件時，可以先問三個問題：

  1. 它有沒有直接使用 window 或 document？
  2. 它是不是需要真實 DOM 才能運作的編輯器、圖表或地圖？
  3. 它有沒有讀寫 localStorage，或使用 matchMedia 偵測瀏覽器狀態？

只要其中一題答案是「有」，就要提高警覺：它不能直接在 server tree 裡被渲染。這不是套件好不好用的問題，而是它依賴的環境根本不在 server 上。

案例一：MDX editor 是瀏覽器限定的編輯器

DevFlow 的問答表單使用 @mdxeditor/editor 作為內容編輯器。它是所見即所得的 Markdown 編輯器，底層使用 CodeMirror，需要真實的 DOM 節點、游標與選取範圍。這些都是瀏覽器中的互動概念，伺服器沒有可以讓它附著的畫面，因此它不支援 SSR。

案例二：next-themes 的 provider 必須隔離

第二個案例的形狀不太一樣。next-themes 是一個 provider，用來提供明暗主題切換。它需要讀寫瀏覽器的 localStorage、偵測系統偏好，也要在頁面載入時避免主題短暫閃動。因此，這個 provider 必須放在 client component 裡。

但這不代表整個 root layout 都要變成 client。DevFlow 的作法是建立一個非常薄的 client wrapper，只負責包住 next-themes 的 provider，其他內容照原樣往下傳：

"use client";

import { ThemeProvider as NextThemesProvider } from "next-themes";
import { ThemeProviderProps } from "next-themes/dist/types";
import React from "react";

const ThemeProvider = ({ children, ...props }: ThemeProviderProps) => {
  return <NextThemesProvider {...props}>{children}</NextThemesProvider>;
};

export default ThemeProvider;

這個檔案幾乎沒有額外邏輯，只有一個 client 邊界。當它被放進 root layout 時，整個 app 的頁面樹仍然可以在 server 上渲染；被隔離出去的，只有真正需要瀏覽器能力的 provider。

這就是「薄 client 邊界」：把 "use client" 壓在最小範圍，讓這個檔案只做一件事，其他頁面與 layout 繼續留在 server。

不過，next-themes 仍會帶來一個預期中的副作用：伺服器與瀏覽器一開始算出的主題可能不同，造成一層 hydration mismatch。DevFlow 會把 suppressHydrationWarning 放在 <html> 上來處理這個情況。

這裡的重點是，正確隔離 provider 之後，還是要處理它本身帶來的瀏覽器差異；但這不代表你要把整個 layout 一起改成 client。

AI 常犯版 vs 正解版

現在把兩個案例放在一起比較，就能看出真正的判斷關鍵：不是看到瀏覽器套件就把整棵樹標成 client，而是先確認它需要哪一種隔離。

AI 常犯版：以為 "use client" 就能包辦一切

常見的錯誤寫法，是在一個 client component 裡直接靜態 import browser-only 的編輯器：

"use client";

import { MDXEditor } from "@mdxeditor/editor";

export function ContentEditor() {
  return <MDXEditor markdown="# hi" onChange={() => {}} />;
}

這段程式看起來已經有 "use client"，但在 build 或首次請求時，仍可能因為 server-side pre-render 而失敗。問題不在於它忘了標記 client，而在於它仍然讓 server 接觸到不支援 SSR 的套件。

正解版：依照套件角色選擇隔離方式

如果是像 next-themes 這樣的 provider，使用一個薄薄的 "use client" wrapper，把 provider 單獨隔離起來即可。

如果是像 MDX editor 這樣需要真實 DOM 的元件，則要同時做到兩件事：元件本身位於 client 邊界，並使用 next/dynamic 設定 ssr: false，確保它不會在 server 上預先渲染。

next-themes provider 把整個 layout 標成 client 用薄的 client wrapper 只包住 provider
MDX editor 只加 "use client"，直接靜態 import 使用 client 邊界，再搭配 next/dynamic 與 ssr: false

把這個觀念掛回整體架構

有一類第三方套件是 browser-only：它們在模組載入或渲染時，就需要 window、document、localStorage 這些瀏覽器才有的東西，因此無法直接在 server 上被渲染。"use client" 只會把檔案標成 client code，不會阻止伺服器預先渲染，所以單獨使用仍然不夠。正解是把 client-only 的部分隔離成一座小小的 client island：provider 使用薄的 client wrapper，需要 DOM 的元件則使用 next/dynamic 搭配 ssr: false。整體原則是，把 "use client" 的範圍壓到最小。

因此，這一節和上一節的「client 邊界會擴散」是接在一起的：你不是要逃避 client，而是要把它放在真正需要瀏覽器的葉節點上。provider 是一種隔離方式，完全跳過 SSR 的 DOM 元件則是另一種隔離方式。
