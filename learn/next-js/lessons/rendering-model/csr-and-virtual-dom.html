CSR：瀏覽器如何用 JavaScript 組出畫面

Step 2/5 · 渲染模型：CSR / SSR / RSC / hydration

學習目標

學完這一節，你應該能說明 CSR 的完整運作鏈：server 先送出最小 HTML 與 JavaScript bundle，瀏覽器執行 React，再由 virtual DOM 比對差異、更新畫面，最後透過 React Router 在 client 端切換頁面。同時，你也要看得出 CSR 在首次載入與 SEO 上付出的代價。

先看全貌：為什麼畫面要等 JavaScript？

上一節我們把三種送頁面的模型攤開，看到 React 的客戶端渲染（CSR）把組畫面的工作交給了瀏覽器。這種做法讓後續互動與換頁很流暢，但也留下兩個問題：第一次打開頁面時，使用者可能要先等一段空白；搜尋引擎也不一定能讀到真正的內容。

你可能看過這種情況：React 網站第一次開啟時，畫面先閃過一片空白，接著內容才一次冒出來。這不一定只是網路慢，而是因為 server 送來的東西，本來就不是「已經看得見的畫面」。它比較像一間剛蓋好的空屋：地址、入口和施工材料都到了，但家具還要等瀏覽器自己搬進來。

要理解這個現象，可以沿著 CSR 的運作鏈往下看：第一個請求拿到什麼、瀏覽器接著做什麼，以及 React 如何處理後續更新。

第一個請求：server 只送空殼與一包 JavaScript

當你造訪一個 React CSR 網站，client 會把請求送到 server。server 回應的核心內容有兩樣：一個最小的 HTML 檔，以及一包打包好的 JavaScript，也就是 bundle。

這個 HTML 檔的工作很單純。它是整個應用的進入點，通常只有一個掛載點，例如空的 <div id="root">，再加上一個引入 JavaScript 的 script 標籤。第一個請求拿到的內容大概長這樣：

<!-- index.html：React CSR 的進入點 -->
<!DOCTYPE html>
<html>
  <body>
    <div id="root"></div>
    <script src="/bundle.js"></script>
  </body>
</html>

注意這個 HTML 裡沒有標題、清單或卡片。它只準備好一個位置，等 React 把內容放進去。也就是說，HTML 雖然已經抵達瀏覽器，真正的畫面卻還沒有被組出來。

AI 常犯版 vs 正解版：把「拿到 HTML」當成「看得到畫面」

看法問題在哪裡
AI 常犯版：server 回傳 HTML，所以瀏覽器一拿到回應就能顯示完整內容。CSR 的 HTML 通常只是空殼，實際內容要等 JavaScript 執行後才會出現。
正解版：server 先送出掛載點與 bundle，瀏覽器執行 bundle 後，React 才把畫面組進掛載點。這能解釋為什麼首次載入可能先空白，也能連到 CSR 的首次渲染代價。

瀏覽器接手：React 在 client 端渲染

瀏覽器下載並執行 bundle 後，React 才開始做客戶端渲染。它會依照元件的定義，把畫面一層一層組起來，最後掛到剛才那個空的掛載點上。到了這個時刻，使用者才真正看到標題、清單與其他介面內容。

這裡的關鍵在於：CSR 把「組畫面」這件事交給了 client。server 的工作先告一段落，後續的渲染與互動則要依賴瀏覽器的處理器和 JavaScript 執行環境。

核心機制：virtual DOM 先比對，再套用

React 能有效率地更新畫面，靠的是 virtual DOM，也就是虛擬 DOM。你可以把它想成一份畫面的草稿。

當資料改變時，React 不會立刻拿著工具到真實 DOM 上到處施工。它會先產生新版的 virtual DOM，再拿新版和上一版比對，找出真正不同的地方。比對完成後，React 只把必要的變更套用到真實 DOM。

這樣做是因為直接修改真實 DOM 的成本可能很高。假設一個清單只有一筆資料改變，如果每次都把整份清單刪掉重建，瀏覽器就得重新處理許多其實沒有變動的內容，還可能觸發不必要的重排與重繪。

有了 virtual DOM，React 可以把注意力集中在那一筆變動上，其餘內容維持原樣。它就像校對一份文件：不會因為第十行改了一個字，就把整份文件重新打掉，而是先找出差異，再只修正需要修改的地方。

AI 常犯版 vs 正解版：virtual DOM 不是「完全不碰 DOM」

看法正確理解
AI 常犯版：React 使用 virtual DOM，所以完全不會修改真實 DOM。React 仍然會更新真實 DOM；virtual DOM 的作用是先比對差異，再把必要變更套用上去。
正解版：virtual DOM 是更新前的比較層，協助 React 避免把沒有改變的內容全部重建。重點不是「完全不更新」，而是「只更新需要變動的部分」。

換頁：React Router 不整頁重新載入

一個網站通常不只一頁。CSR 的換頁方式，是使用 React 的客戶端路由庫 React Router。

當你在應用程式內點擊連結時，React Router 會根據新的 URL 改變目前的路由，並讓對應的元件重新渲染。它不需要向 server 重新索取一整份 HTML，因此瀏覽器也不會整頁重新載入。

如果新頁面需要資料，對應的元件可以在瀏覽器裡另外向 server 發出請求。整個換頁過程主要在 client 端完成，頁面不必重新白閃一次，這也是單頁應用（SPA）讓人覺得切換流暢的原因。

AI 常犯版 vs 正解版：SPA 不是「完全不和 server 溝通」

看法正確理解
AI 常犯版：React Router 讓 SPA 完全不需要 server。React Router 避免的是整頁重新載入；新頁面的資料仍可能由元件向 server 發出請求取得。
正解版：路由切換主要由 client 處理，必要資料仍可從 server 取得。因此「不整頁重載」和「不需要 server」是兩件不同的事。

代價：CSR 把工作全壓在 client

CSR 把後續互動與換頁交給瀏覽器，換來了流暢的 SPA 體驗。但這份便利不是免費的，主要有三個代價。

複雜度提高。 開發 React 應用比撰寫傳統 HTML、CSS、JavaScript 複雜。你需要用元件的方式思考，也要理解 state、props 與 virtual DOM。對新手來說，這會形成一段學習曲線。

首次渲染與互動被延後。 CSR 主要依賴 JavaScript 在瀏覽器中執行。初始渲染和後續更新都落在 client；如果使用者的處理器較慢或裝置資源有限，畫面出現與變得可互動的時間就可能拉長。這正是「先白一下，接著才跳出內容」的來源。

SEO 有風險。 因為內容全靠 JavaScript 在客戶端渲染，搜尋引擎的爬蟲不一定能完整執行 JavaScript，也不一定能讀到頁面內容。當內容被讀取得不完整，網站在搜尋結果中的能見度就可能受到影響。

把 CSR 掛回整體渲染模型

CSR 的核心不是單一技術，而是一條彼此相連的鏈：server 先送出最小 HTML，瀏覽器下載並執行 JavaScript bundle，React 在 client 端組出畫面；資料改變時，React 透過 virtual DOM 找出差異；使用者換頁時，React Router 在 client 端切換對應元件。

CSR 的運作鏈是：server 只送最小 HTML 與一包 JavaScript，瀏覽器執行 bundle，React 用 virtual DOM 比對差異、只更新必要部分來組出畫面；換頁則由 React Router 在 client 端處理，不整頁重新載入。它把渲染工作從 server 搬到了 client，換到流暢的互動，代價是首次畫面必須等 JavaScript，以及 SEO 的風險。

所以，CSR 的優勢與代價其實來自同一個選擇：把更多工作放到瀏覽器。這讓後續互動與換頁更靈活，卻也讓首次畫面必須等待 JavaScript。下一節要看的 Next.js，正是從這個缺口出發：先用伺服器端渲染把完整 HTML 送出去，再用 hydration 把互動接回來。
