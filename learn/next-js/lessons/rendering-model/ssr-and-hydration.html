SSR 與 hydration：先送 HTML，再接手互動

Step 3/5 · 渲染模型：CSR / SSR / RSC / hydration

學習目標

能解釋 Next.js 首次請求時，server 如何執行 React 元件、回傳完整 HTML，再由 client 進行 hydration，接回事件處理器與互動能力；也能說明 hydration mismatch 是怎麼發生的。

先看全貌：畫面可以先到，互動稍後再接

想像使用者打開一個 Next.js 網站。如果採用 CSR，瀏覽器一開始拿到的可能只是最小 HTML 和 JavaScript，必須等 bundle 下載並執行後，畫面內容才真正出現。這會讓首次畫面變慢，也可能讓搜尋引擎爬蟲讀不到完整內容。

那能不能先把畫面送到使用者眼前，互動能力再稍後補上？Next.js 的 SSR 就是在處理這個問題：先由 server 執行 React 元件，把結果算成 HTML 送出去；瀏覽器收到後立刻畫出內容。接著，JavaScript 到達 client，再透過 hydration 把按鈕、輸入框等互動能力接回去。

整條流程可以先記成兩個階段：

階段主要工作使用者看到的結果
SSRserver 執行 React 元件，產生並回傳 HTML畫面先出現，搜尋引擎也能讀到內容
hydrationclient 將 JavaScript 的事件處理器接回 HTML按鈕、輸入框等互動開始生效

這不是「server 和 client 各做一半、隨便拼起來」，而是先由 server 交付第一版畫面，再由 client 接手互動。真正的難題也藏在這裡：兩邊對第一版畫面的理解必須一致。

首次請求：server 先跑一次 React 元件

當使用者造訪 Next.js 網站，client 會把請求送到 server。這時的流程和 CSR 很不一樣：server 會開始執行你的 React 元件，產生 HTML、CSS 與 JavaScript，接著把一份已經渲染完成的 HTML 回傳給瀏覽器。

這份 HTML 不是只放著一個空殼。它已經包含初始內容、抓好的資料，以及元件的標記。因此，瀏覽器一收到 HTML，就可以先把畫面畫出來，不必等 JavaScript 下載並執行完成。

這就是 server-side rendering（SSR，伺服器端渲染）的重點：使用者能更早看到內容，搜尋引擎爬蟲也能直接讀到完整 HTML。

AI 常犯版 vs 正解版：SSR 不是「完全不送 JavaScript」

說法問題或重點
AI 常犯版：SSR 把所有東西都在 server 做完，所以 client 不需要 JavaScript。SSR 只代表首次畫面由 server 產生，不代表互動程式碼消失。
正解版：server 先送出已渲染的 HTML，互動需要的 JavaScript 之後仍會送到 client。畫面先出現靠 HTML；按鈕能不能按、輸入框能不能互動，則要等 JavaScript 接手。

所以，SSR 解決的是「內容何時出現」；它沒有單獨解決「互動何時生效」。這兩件事要分開看。

hydration：把互動接回已渲染的 HTML

HTML 送達、畫面出現之後，Next.js 會在 client 做 hydration（注水）。它的工作，是把 JavaScript 的事件處理器和互動能力，接到那份已經預先渲染好的 HTML 上。

可以把 server 送來的 HTML 想成一尊已經雕好的石膏像。你看得到它的形狀，但它本身不會動。hydration 就像接上神經與肌肉：石膏像沒有被整尊換掉，而是從這一刻開始具備反應能力。

因此，在 hydration 完成前，頁面雖然已經看得見，卻可能還不能按按鈕或在輸入框打字。畫面「先出現」和互動「已經生效」是兩個不同時間點。

AI 常犯版 vs 正解版：hydration 不是重新畫一張完全無關的頁面

說法正確理解
AI 常犯版：hydration 就是 client 收到 HTML 後，重新做一份新的畫面。hydration 的核心是把 client 的互動能力接到既有 HTML 上。
正解版：server 先產生 HTML，client 再用 JavaScript 接回事件處理器。兩邊必須認得同一份第一版畫面，互動才能穩定接上。

hydration mismatch：兩邊算出的第一版畫面不一致

hydration 要順利，前提是 server 算出的 HTML，和 client 重新渲染時預期的結果必須一致。如果兩邊對不上，就會出現 hydration error，也就是 hydration mismatch（注水不一致）。

Next.js 在 server 渲染時，對於依賴瀏覽器或需要互動的部分，會先留下佔位元素，例如 div、form 或 span。當 client 重新渲染的結果，和 server 留下的內容對不起來，錯誤就會出現。

最容易理解的例子，是把「現在時間」直接印進畫面：

// server 渲染時算出的 HTML
<time>2026-10-04 10:00</time>

// client 重新渲染時，時間已經往前走了一點
<time>2026-10-04 10:00:01</time>

server 算出的是 10:00，client 重新渲染時卻變成 10:00:01。對人來說只差一秒，對 hydration 來說卻是兩份不同的第一版畫面。

時間只是其中一個例子。只要某段邏輯讓 server 和 client 算出不同結果，就可能造成 mismatch。要掌握這個問題，不必先背下所有錯誤訊息；先記住 hydration 的基本假設就好：server 和 client 的第一版畫面應該長一樣。

AI 常犯版 vs 正解版：問題不在「有兩邊」，而在「兩邊結果不同」

說法正確理解
AI 常犯版：只要用了 SSR 和 hydration，就一定會發生 mismatch。SSR 與 hydration 本身是正常的分工；問題出在 server 和 client 算出的內容不一致。
正解版：只要兩邊的第一版結果一致，client 就能把互動能力接回 server 產生的 HTML。依賴當下時間、瀏覽器狀態等會變動結果的邏輯，特別容易破壞這個前提。

首次請求之後：渲染位置可以由開發者選擇

SSR 主要描述首次請求時發生的事。到了後續請求，Next.js 把選擇權交回開發者：內容可以繼續在 server 渲染，也可以改由 client 渲染。

因此，一個應用程式裡可以同時存在 SSR 與 CSR。不是整個網站只能選一種模式，而是要依照內容與互動需求，決定哪些部分由 server 處理、哪些部分由 client 處理。

SSR 與 CSR 的首次載入差在哪？

面向CSRSSR
第一個請求拿到什麼最小 HTML + JavaScript已渲染完成的 HTML + 之後補上的 JavaScript
首次畫面等 JavaScript 執行完HTML 一到就能畫
SEO爬蟲不一定讀到內容爬蟲直接讀到完整 HTML

把這些概念掛在一起

Next.js 首次請求時，server 執行 React 元件、產生並回傳完整的 HTML，讓瀏覽器立刻畫出畫面；互動所需的 JavaScript 隨後才到，並由 client 的 hydration 把事件處理器接到那份已渲染的 HTML 上。如果 server 與 client 算出的第一版畫面不一致，就會發生 hydration mismatch，尤其當內容依賴瀏覽器或當下時間的時候。之後的請求，開發者可以自行選擇在 server 或 client 渲染。

到這裡，渲染還停留在「整個頁面」的層級：server 負責先算出畫面，client 再接回互動。但 Next.js 的 App Router 把這種分工推進到了元件層級，每個元件都可以自己決定要在 server 還是 client 執行。下一節就來看，這條界線是怎麼劃出的。
