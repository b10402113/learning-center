RSC 與 Client Component：看懂「use client」畫出的邊界

Step 4/5 · 渲染模型：CSR / SSR / RSC / hydration

先看整張地圖：一個頁面，為什麼要分兩邊算？

想像一個網站頁面：導覽列需要點擊互動，內容區只要讀資料，側邊欄則只是顯示廣告。如果整頁都交給瀏覽器處理，使用者得下載更多 JavaScript；如果整頁都只在 server 處理，又無法回應按鈕點擊和輸入事件。

上一節介紹的 SSR，是先由 server 算好整頁 HTML，再交給 client 做 hydration，接上後續互動。App Router 再往下細分一步：渲染不必以整頁為單位，也可以細到元件層級。

這代表同一個頁面裡，不同元件可以各自選擇適合自己的執行位置。需要瀏覽器互動的部分留在 client；適合抓資料、讀取伺服器資源的部分則留在 server。這條分工線，就是 "use client"。

先分清楚：client 與 server 各自負責什麼

client 是使用者手上的裝置，負責送出請求、顯示介面，以及處理可互動的操作。server 則是一台持續運作、規格通常較強的機器，應用程式碼放在那裡，收到請求後執行運算，再把結果傳回去。

在 Next.js 13 之前，伺服器端渲染主要是「頁面」層級的能力。像 /、/about、/projects 這些頁面可以在 server 渲染，但頁面內的元件沒有同樣細緻的分工。

這會帶來兩個常見麻煩：資料需要一層一層往下傳，也就是 prop drilling；同一份 API 呼叫則可能在不同層重複發生。App Router 將渲染推進到元件層級，讓每個元件可以依照自己的工作，選擇在 server 或 client 執行。

兩種元件：先看它需要什麼能力

假設有一個 Navbar.jsx。它可以是 Server Component，也可以是 Client Component。判斷的重點不是元件名稱，而是它需要做什麼。

Server Component（伺服器元件，RSC） 是在 server 執行的 React 元件。它產生的 HTML 輸出會送到 client。因為程式碼在 server 執行，它可以直接存取資料庫或檔案系統等伺服器端資源，也能減少送到 client 的 JavaScript。

Client Component（客戶端元件，RCC） 則是在 client，也就是瀏覽器中執行的 React 元件。要在 Next.js 裡使用它，必須在元件檔案最上方加上 "use client"。

需要點擊按鈕、在輸入框打字、觸發事件，或使用瀏覽器 API 的元件，通常需要放在 client。只需要抓資料、顯示靜態內容，或執行伺服器端運算的元件，則可以留在 server。

AI 常犯版：看到互動就把整頁標成 client

這種寫法的問題是，為了讓一小塊互動元件能在瀏覽器執行，連同不需要互動的內容也一起被送進 client。好比為了開一盞桌燈，把整間房子的電器都搬到門口，當然能用，但運送成本變高了。

更好的思考方式，是先把頁面拆成不同元件，再只讓真正需要瀏覽器能力的部分成為 Client Component。資料抓取、伺服器端資源與靜態內容，則盡量保留在 Server Component。

App Router 的預設值：所有元件都是 Server Component

App Router 的重要規則是：所有元件預設都是 Server Component。 除非你明確標記，否則元件會被當成 server 元件，並在 server 上執行。

可以用一行 console.log 觀察這件事。在首頁元件裡加入 log，然後查看執行 npm run dev 的終端機：

export default function Home() {
  console.log("Which component am I?");

  return (
    <main>
      <h1 className='font-bold text-3xl'>Welcome to Next.js</h1>
    </main>
  );
}

這行 log 不會出現在瀏覽器的 console，而會出現在終端機。原因很單純：這個元件是 Server Component，程式碼在 server 執行，log 也就留在 server。

正解版：需要 client 能力時，才畫出邊界

現在在檔案最上方加上 "use client"，再觀察一次：

"use client";

function Hello() {
  console.log("I am a Client Component");

  return (
    <div>
      <h1>Hello</h1>
    </div>
  );
}

export default Hello;

這次的 log 會跑到瀏覽器裡，因為這個檔案已經被標記為 Client Component，元件會在 client 執行。

一個容易誤會的地方：Client Component 也可能在 server 出現 log

如果你發現加了 "use client" 之後，log 不只出現在瀏覽器，終端機也看得到，先別以為邊界失效了。

Next.js 會在 server 上預先渲染 Client Component，先產生一個靜態外殼，之後再交給 client 做 hydration。這就像先搭好舞台，等演員到場後才補上真正的互動。

因此，Client Component 裡不依賴瀏覽器的部分，可能會先在 server 預渲染；真正需要瀏覽器的部分，則等到了 client 再接上互動。這也是為什麼同一個 Client Component 的 log 可能同時出現在 server 終端機與瀏覽器 console。

AI 常犯版：把「use client」當成元件自己的標籤

很多人會把 "use client" 理解成「只有這個元件變成 client」。但它的作用範圍比這更大。

"use client" 是一條檔案層級的分界線：一旦某個檔案標上 "use client"，所有被 import 進這個檔案的模組，包括子層的 Server Component，都會被視為 client 模組的一部分。

例如，下面的 Client Component import 了 ExampleServer：

"use client";

import ExampleServer from "./ExampleServer";

const ExampleClient = () => {
  console.log("I'm Client Component :)");

  return (
    <>
      <div>
        <p>This an example client component</p>
      </div>
      <ExampleServer />
    </>
  );
};

export default ExampleClient;

即使 ExampleServer 原本是 Server Component，只要它被 import 進這個 client 檔案，就會成為 client 模組的一部分，相關 log 也會跑到瀏覽器。

正解版：把「use client」當成程式碼邊界

請把 "use client" 想成一條畫在程式碼之間的線。線的上方或外側仍可保留在 server；但一旦模組被 import 進標記為 client 的檔案，就跨進了 client 的範圍。

因此，實務上的判斷很明確：需要互動的元件才標記為 Client Component；不需要互動、需要直接存取伺服器資源的元件，則留在 Server Component。不要把 Server Component 放進 Client Component 裡面。

把這個觀念掛回整體渲染模型

App Router 裡的元件預設都是 Server Component，在 server 執行並產生 HTML，因此可以存取伺服器資源，也能減少送到 client 的 JavaScript。當元件需要事件處理、state、生命週期或瀏覽器 API 時，才在檔案頂端加上 "use client"，把它標記為 Client Component。Client Component 仍可能先在 server 預渲染，之後再由 client hydration 接上互動。"use client" 同時也是檔案層級的邊界：被它標記的檔案所 import 的模組，都會進入 client 程式碼範圍，因此不要把 Server Component 放進 Client Component。

現在可以把這個觀念和前一節的 SSR、hydration 接起來：SSR 說明 server 可以先產生畫面，hydration 說明 client 如何補上互動，而 RSC 與 Client Component 則進一步決定每個元件該在哪一邊工作。下一節會把這個邊界轉成實際判準，協助你判斷一個元件到底該留在 server，還是標成 client。
