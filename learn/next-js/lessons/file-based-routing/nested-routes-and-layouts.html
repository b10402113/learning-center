巢狀路由與巢狀 layout

Step 2/5 · Routing as a Filesystem

學習目標

由巢狀資料夾推出巢狀 URL，並說明每一層 layout 如何包住它的子樹、透過 children 串成一條外框鏈。

前言：每一頁都要有導覽列，你會怎麼做？

上一節我們確定了第一條規則：一個資料夾就是一條路由，裡面的 page 檔就是那條路由的畫面。現在想像你要做一個有十幾頁的網站，每一頁左上角都要有同一個導覽列、底部都要有同一份頁尾。最直覺的反射動作，是每一頁的元件裡都 import 一次導覽列，反正上一節教的就是「每個 page 檔案就是一個元件」。

這樣做會遇到的麻煩很具體：Navbar 改一次，你得改十幾個檔案；而且這正是 React 時代的老習慣，Next.js 特地設計了一套機制讓你不用這樣做。這一節要講兩件事：多層路徑怎麼用巢狀資料夾表達，以及 layout 如何成為「一包就套用到整段子樹」的共用外框。

巢狀資料夾就是巢狀路由

先解決多層路徑。假設我們要一條 /projects/list。在檔案路由裡，這條路徑就寫成資料夾的巢狀結構：projects 底下再放一個 list，然後在 list 裡放 page.tsx。路徑上的斜線，對應的就是資料夾之間的從屬關係：

export default function ProjectsList() {
    return (
        <main>
            <p>ProjectsList</p>
        </main>
    )
}

只要把這個檔案放在 app/projects/list/page.tsx，就得到 /projects/list。想再深一層，就再往裡放一個資料夾；想淺一層，就往外移一層。URL 的每一段斜線，就是資料夾樹的每一層。這就是巢狀路由，它不是額外的功能，而是第一條規則往深處自然長出來的結果。

問題：Navbar 難道每頁都要 import？

回頭處理共用外框。假設我們做了導覽列元件，最天真的做法是在每個 page 裡都引入它。這是課本特別標成「錯誤方法」的寫法：

import Navbar from '@/components/Navbar'

export default function Home() {
  return (
    <main>
      <Navbar />
      <h1>Home</h1>
    </main>
  )
}

這頁沒問題，但每一頁都要複製這三行。一旦頁面變多，就變成你剛才想像的那場災難。

正確的做法，是把導覽列放進這些頁面共同的父層：layout.tsx。root layout 接收一個 children 參數，你只要把 <Navbar /> 放在 {children} 前面，它就自動出現在底下所有路由上：

import './globals.css'
import { Inter } from 'next/font/google'

import Navbar from '@/components/Navbar'

const inter = Inter({ subsets: ['latin'] })

export const metadata = {
    title: 'Create Next App',
    description: 'Generated by create next app',
}

export default function RootLayout({ children }) {
  return (
    <html lang="en">
      <body className={inter.className}>
        <Navbar />
        {children}
      </body>
    </html>
  )
}

關鍵在最後那個 {children}。它不是你自己傳進去的，而是 Next.js 依照當前造訪的路徑，把對應的 page 放進這個插槽再交給你。於是你只要維護一份 Navbar，所有頁面都會跟著更新。

layout 的管轄範圍：它所在的子樹

要把 layout 用對，得記住一句話：一個 layout 管的是它所在資料夾的那棵子樹。最外層的 root layout 管全部；某個資料夾裡的 layout 只管那個資料夾底下的所有路由，出了這個資料夾就不管。用一張表對照 layout 與 page 這兩種檔案的角色：

layout.tsxpage.tsx
角色包住子樹的共用外框單一路由的畫面內容
影響範圍它所在資料夾底下的所有路由只有它對應的那一條路徑
怎麼接起來把 children 插進自己的外框被當成 children 交給上層 layout
根目錄的必要性root layout 是必要的有路由才需要

真實專案會把這個機制用到極致。以下是一個 Next.js 15 問答平台 DevFlow 的 app/(root)/layout.tsx，它為底下所有問答頁面包上導覽列與左右側邊欄：

import { ReactNode } from "react";

import Navbar from "@/components/navigation/navbar";
import LeftSidebar from "@/components/navigation/LeftSidebar";
import RightSidebar from "@/components/navigation/RightSidebar";

const RootLayout = ({ children }: { children: ReactNode }) => {
  return (
    <main className="background-light850_dark100 realtive">
      <Navbar />

      <div className="flex">
        <LeftSidebar />

        <section className="flex min-h-screen flex-1 flex-col px-6 pb-6 pt-36 max-md:pb-14 sm:px-14">
          <div className="mx-auto w-full max-w-5xl">{children}</div>
        </section>

        <RightSidebar />
      </div>
    </main>
  );
};

export default RootLayout;

注意它叫 RootLayout，其實不是整個應用的根，而是 (root) 這個資料夾的 layout，它只包住 (root) 底下那些問答頁面。這是巢狀 layout 的第一層應用：不只全域可以有一層外框，任何一段子樹都能自己再加一層。

多層 layout 疊成一條外框鏈

layout 不只能有一層。當你造訪一條比較深的路由，Next.js 會把從最外層一路到目標頁面之間的每一層 layout 都套上去，一層包一層，最後才把 page 放進最內層。你可以把它想成套娃娃：最外層是 root layout，往內是各段路徑的 layout，最裡面那顆小娃娃才是這條路由的 page。

在同一個 DevFlow 專案裡，登入與註冊頁放在另一個 route group (auth)，它們共用一個完全不同的外框，置中的卡片、logo、下方的第三方登入按鈕：

import Image from "next/image";
import { ReactNode } from "react";

import SocialAuthForm from "@/components/forms/SocialAuthForm";

const AuthLayout = ({ children }: { children: ReactNode }) => {
  return (
    <main className="flex min-h-screen items-center justify-center bg-auth-light bg-cover bg-center bg-no-repeat px-4 py-10 dark:bg-auth-dark">
      <section className="light-border background-light800_dark200 shadow-light100_dark100 min-w-full rounded-[10px] border px-4 py-10 shadow-md sm:min-w-[520px] sm:px-8">
        <div className="flex items-center justify-between gap-2">
          <div className="space-y-2.5">
            <h1 className="h2-bold text-dark100_light900">Join DevFlow</h1>
            <p className="paragraph-regular text-dark500_light400">
              To get your questions answered
            </p>
          </div>
          <Image
            src="images/site-logo.svg"
            alt="DevFlow Logo"
            width={50}
            height={50}
            className="object-contain"
          />
        </div>

        {children}

        <SocialAuthForm />
      </section>
    </main>
  );
};

export default AuthLayout;

把兩者並排看就清楚了：走 /questions/123 這種問答頁，外框鏈是「root layout → (root) layout → page」，你會看到導覽列和側邊欄；走 /sign-in，外框鏈換成「root layout → (auth) layout → page」，畫面變成置中的登入卡片。兩段子樹共用最外層的 root layout，但從第二層開始各走各的。這就是巢狀 layout 真正的威力：你可以在任一段子樹換掉外框，而不必動到裡面每一個 page。

這對審查 AI 架構的意義

當 AI 幫你生了一整個頁面，先別急著讀裡面的邏輯。花十秒看它的 layout：一個頁面如果重複在自己的 page.tsx 裡 import 導覽列，通常代表它沒用到 layout，或是把 layout 放錯了層級。反過來，如果你看到兩個功能上完全不同的區塊（例如官網和後台）各自有一個 layout，那多半是刻意的巢狀 layout 設計，是好架構的訊號。判斷的關鍵，就是你剛剛學到的「layout 管的是它所在的那棵子樹」。

小結

巢狀資料夾產生巢狀 URL，路徑上的每一段斜線就是資料夾樹的一層。而共用外框交給 layout.tsx：每個 layout 只管它所在資料夾的那棵子樹，並透過 children 把裡面的內容插進自己的外框。多層 layout 會從 root 一路套到目標頁，疊成一條外框鏈，所以不同子樹可以有完全不同的外框，卻共用同一個根。

到這裡，路由和 layout 的地形都清楚了。但我們造出來的路由名稱都是固定的：/projects/list、/contact。如果今天有上千個商品，每個都要一條專屬路徑呢？下一節的動態區段，就是讓一個 page 同時服務無限多條 URL 的關鍵。
