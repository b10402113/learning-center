實戰：從資料夾樹推導完整路由樹

Step 5/5 · Routing as a Filesystem

學習目標

拿到一棵真實的 app/ 資料夾樹，能逐步推導出每一條路由、每個 URL 區段對應的檔案，以及每層 layout 的包覆關係。

前言：零件都會了，但拼得起來嗎？

前四節分別教了四塊積木：資料夾即路由、巢狀路由與巢狀 layout、動態區段與 params、以及 route group。單獨看每一塊都不難，但真實專案的 app/ 樹是一團混在一起的東西：括號、方括號、巢狀好幾層、每個資料夾裡還有 layout 或 page。這一節不再加新語法，而是給你一套固定的推導流程，讓你能對著任何一棵 app/ 樹，在腦中還原出完整路由表與每一條路由的 layout 鏈。

前置條件：動手前你該有的東西

這個流程會一直用到前四節的規則，所以先確認你記得三件事：資料夾名等於 URL 區段（除非被括號包住）、方的動態區段對應 params 的 key、以及每一層 layout.tsx 管它所在的那棵子樹。接下來的推導不需要終端機、不需要真的跑起來，只要看檔案樹就能做。

你要推導的樹

我們拿 DevFlow 問答平台的 app/ 資料夾當素材。先把它完整攤開（省略 api/ 底下的細節，因為那些是 API 端點、不是頁面路由）：

推導流程：五個步驟

照著這五步走，任何 app/ 樹都能拆解。重點是先只看資料夾，再處理括號，最後才對 page 檔，不要一開始就被檔名干擾。

  1. 列出所有 page 檔。每找到一個 page.tsx，就代表一條路由。這一步先不管 URL 長怎樣，只是把「有哪些頁面」框出來。
  2. 處理括號資料夾。看到 (auth)、(root) 這種被括號包住的，在心中把它從 URL 拿掉，但保留它在樹上的分類位置。它不會貢獻任何路徑區段。
  3. 把路徑拼出來。對每一個 page 檔，從 app/ 一路往下、經過的每一層資料夾接成 URL，括號層跳過；動態區段先標成 :變數名。
  4. 往上收集 layout。對同一條路由，把從 app/ 到它所在的資料夾之間、每一層的 layout.tsx 依序列出，就是它的外框鏈。
  5. 標記動態區段。凡是方括號資料夾，在 URL 上標成變數，並記住它的名字就是之後 params 的 key。

有兩個地方值得停下來看。第一，/profile/edit 和 /profile/:id 同時存在：edit 是個靜態區段，[id] 是動態區段，Next.js 會優先匹配靜態的那一個，所以打 /profile/edit 不會被誤當成某個人的 id，而打 /profile/abc123 才會落到動態頁。第二，profile/、tags/ 這些資料夾本身沒有 layout.tsx，所以它們的頁面只沿用 (root) 那一層外框，layout 不是每一層都必須有。

layout 鏈是怎麼疊出來的

第二步的「收集 layout」為什麼能得到「root → (root)」？因為 app/layout.tsx 是整個應用的最外層，而 app/(root)/layout.tsx 又剛好位在這些路由的上方。來看看這一層外框的內容：

import { ReactNode } from "react";

import Navbar from "@/components/navigation/navbar";
import LeftSidebar from "@/components/navigation/LeftSidebar";
import RightSidebar from "@/components/navigation/RightSidebar";

const RootLayout = ({ children }: { children: ReactNode }) => {
  return (
    <main className="background-light850_dark100 realtive">
      <Navbar />

      <div className="flex">
        <LeftSidebar />

        <section className="flex min-h-screen flex-1 flex-col px-6 pb-6 pt-36 max-md:pb-14 sm:px-14">
          <div className="mx-auto w-full max-w-5xl">{children}</div>
        </section>

        <RightSidebar />
      </div>
    </main>
  );
};

export default RootLayout;

這個檔案的檔名是 RootLayout，但它其實是 (root) group 的 layout，不是整個應用的根。這正是很多人第一次讀真實專案會卡住的地方：不要被元件的名字騙了，要看它位在哪個資料夾。它位在 (root)/，所以只包住 (root) 底下的問答頁面。至於真正的應用根，是 app/layout.tsx。

相對地，(auth) group 用的是完全不同的外框，置中的登入卡片：

import Image from "next/image";
import { ReactNode } from "react";

import SocialAuthForm from "@/components/forms/SocialAuthForm";

            <h1 className="h2-bold text-dark100_light900">Join DevFlow</h1>
            <p className="paragraph-regular text-dark500_light400">
              To get your questions answered
            </p>
          </div>

            src="images/site-logo.svg"
            alt="DevFlow Logo"

        <SocialAuthForm />

所以當使用者打開 /sign-in，外框從外到內是「app/layout.tsx → app/(auth)/layout.tsx → (auth)/sign-in/page.tsx」；打開 /questions/123，換成「app/layout.tsx → app/(root)/layout.tsx → (root)/questions/[id]/page.tsx」。兩者共用最外層，卻從第二層起分道揚鑣。

做完長什麼樣：一張可以核對的檢查表

推導完成後，你應該能對這棵樹講出三件事：有幾條頁面路由（這棵樹是 13 條）、每一條的 URL（例如 /tags/:id）、以及每一條經過哪些 layout。用底下這幾條快速自我檢查：

  • 括號資料夾有沒有被我從 URL 裡拿掉？
  • 每個方括號都標成變數了嗎？它的名字對得上未來 params 的 key 嗎？
  • 每一個 page 都對應到一條路由，沒有漏、沒有多嗎？
  • 我的 layout 鏈是不是從 app/ 一路往上收集，而不是只看目標資料夾那一層？

把這個流程練熟，你就能在幾分鐘內看透一份 AI 生成的專案：它到底做了哪些頁面、路由結構合不合理、外框有沒有放對層級。這正是這個節點一開始設定的目標：由資料夾結構推導出完整路由樹，並解釋 params 的來源。

小結

推導路由樹的固定流程是：先列出所有 page 檔，把括號資料夾從 URL 移除，逐層拼出每條路徑（動態區段標成變數），再從 app/ 往上收集每一層 layout.tsx 得到外框鏈。真實專案像 DevFlow 就用兩組 (auth) 與 (root)，各自套不同外框、共用同一個 app/layout.tsx；而 /profile/edit 與 /profile/:id 的並存，則提醒你靜態區段會優先於動態區段被匹配。

到這裡，「Routing as a Filesystem」這個節點就完整了。你已經能把一棵 app/ 樹翻譯成路由表與外框鏈。接下來在課程裡，這些路由會開始接上真正的資料抓取、載入與錯誤邊界，讓每一條路由不只是路徑，而是能運作的一頁。
