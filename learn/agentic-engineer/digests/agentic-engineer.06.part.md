# Digest — agentic-engineer (part 6) — Skills — The System You Needed

## Overview (L1)
- Skills: The Discipline You Did by Hand — Names the problem this part solves: everything taught so far is a discipline you must remember to run every feature, and discipline slips exactly when you're busiest (tired, late). A skill is that procedure written down once so the agent runs it the same way every time. Crucially, a skill does not make the model smarter — it removes the procedural overhead so your attention is free for the judgment calls that were always yours. Thesis of the part: the skill runs the procedure, you make the calls.
- How to Read a SKILL.md file — Proves a skill is readable by opening Anthropic's public skills repo on GitHub (the PDF skill). A `SKILL.md` is ordinary markdown with frontmatter (name + description) plus a body. The description is the trigger: the agent reads only names and descriptions to decide which skill applies, loading a body only if it picks that one. The anatomy: root `SKILL.md` (only required file), and optional on-demand helpers — `scripts/`, `references/`, `assets/`.
- Build Your Own Skill — Builds a real "teach me" skill end to end using Anthropic's official skill-creator (installable in Claude Code with `/plugin install skill-creator@anthropic-agent-skills`). Because the creator writes the description for you, the prompt you give it becomes the most important part. Also distinguishes personal skills (`~/.claude/skills/`, all projects) from project skills (`.claude/skills/`, shared with the team on clone). The real lesson: making a skill is easy, making one you'd stake a project on takes iteration.
- Skills vs. MCP: Which to use and when — Distinguishes the two tool-specific mechanisms on one example, Supabase. A skill carries a tool's real, current conventions (how auth, row-level security, and the current API actually work), so the agent stops guessing from half-remembered training data. An MCP connects the agent to your live instance of the tool (your real tables, data, queries). Different jobs; a real project often wants both. The workflow finds the relevant skills/MCPs for your stack automatically but asks before installing and leaves real-account sign-ins to you.

## Sections (L2)
### 1-skills-the-discipline-you-did-by-hand
- Locator: `[[sources/agentic-engineer/20261014/6. Skills — The System You Needed/1. Skills The Discipline You Did by Hand.srt#1-skills-the-discipline-you-did-by-hand]]`
- Summary: Argues that knowing a discipline and actually running it on every feature are two different things — the routine slips exactly when you're busiest, which is when you need it most. The fix is to stop carrying the procedure in your head and capture it in a file so the agent runs it identically every time. That captured procedure is a skill, and it is deliberately less magical than the word sounds.
- Key claims: The discipline isn't one action but a stack of little procedures (decide the decision that must be made before code, write it down so it won't get lost, size the work so the change is small enough to review, check it against what you actually asked for) that must be remembered and ordered on every single feature; people cut corners on the feature they're sick of, so the discipline slips precisely when busiest; a skill is just "a procedure you kept having to do by hand, captured in a file, so it runs the same way every time"; every skill has two parts — a short name and description at the top, and the real (long) instructions in the body; the agent only reads the top part, scanning names and descriptions of every skill to decide which fits, and only then loads the full body of the one it picked, so the others never enter the conversation; this is the opposite of always-on rent — 10 procedures sitting available cost you only the one you're using, and two lines each for the rest, which is why you can have a whole system of procedures without crushing the context window; a skill does not think for you, is not a smarter agent, and does not change how capable the model is — the model is exactly as capable as before; what a skill changes is where your attention goes, running the procedure/remembering/ordering/checklist so your attention is free for the decisions, judgment, and calls that were always yours; over-brief-then-catch details: he attributes the buried judgment to having to remember "15 procedural things" in the right order on every feature.
- Learner-relevant: Sets the thesis line for the whole part — "The skill runs the procedure. You make the calls." Core vocabulary: skill = a captured procedure; name + description (top, always read) vs body (loaded only when picked). Anchors the always-on-context lesson (rent) and sets up the next lesson's file walkthrough and the build in lesson 3.

### 2-how-to-read-a-skillmd-file
- Locator: `[[sources/agentic-engineer/20261014/6. Skills — The System You Needed/2. How to Read a SKILL.md file.srt#2-how-to-read-a-skillmd-file]]`
- Summary: A read-along walkthrough of a real skill from Anthropic's public skills repo on GitHub — the PDF skill. It shows that a `SKILL.md` is just markdown with structured frontmatter on top, explains that the description is the trigger the agent reads to decide whether the skill fires, and reveals that a skill is a whole folder, not a single file, where heavy pieces load only on demand.
- Key claims: `SKILL.md` is ordinary markdown (a readme with a little structured info at the top) — if you can read a readme you can read it, no special skill syntax; at the very top, between the three-dash frontmatter fences, two things matter: name and description; the description is the most important line in the entire file and the one developers are most careless about, because the agent reads the name and description of every skill to decide which fits — it is the trigger, what makes the PDF skill fire on a PDF and stay quiet otherwise; everything below the description (the instructions) the agent does not even look at until that line convinced it the skill is relevant; a lazy description like "helps with documents" fires on the wrong tasks or misses the right ones, so a good description says in plain words exactly when to use the skill and when not to — that precision is the difference between a skill that works and one that just sits there; the body is plain instructions written the way you'd brief a good teammate — here's the job, here's how to do it, here are the things that trip people up (what the skill is for, when to use which approach, and the steps) — you don't read a skill back to back, and neither does the agent; a skill is a whole folder, not one file: alongside `SKILL.md` sit `forms.md`, `reference.md`, and a `scripts/` folder with actual code; `SKILL.md` points at the other files (e.g. the quick-reference points to `forms.md`), so the agent opens `forms.md` only when actually filling out a form (pulling text out of a PDF never touches it), and `reference.md` is loaded only when a task needs the deep details; scripts are the best example of exactness — when a job must be done exactly (pulling every field out of a form) the skill runs a script instead of describing it in English and hoping the model gets it right, and only the result comes back, the code itself never enters the conversation; a skill can be big and capable while costing nothing until the moment it's used — you don't pay for the whole skill, you pay for the exact piece the task touches; extra files in skills (like skill-creator) are almost always one of three kinds: scripts (code the agent runs when a job must be exact), assets (templates or images the skill drops into its output), or on-demand docs; the full anatomy: name + description that triggers it, the body of instructions, and optionally the helper files loaded on demand.
- Learner-relevant: This is the core "how to read a skill" reference. Concrete file names/fields: `SKILL.md`, three-dash frontmatter with `name` and `description`, `forms.md`, `reference.md`, `scripts/`; the three optional helper kinds are `scripts/`, `references/`, `assets/` (also described in the companion slide). Establishes the principle reused all module: description = trigger, body = how, heavy parts load only when reached for.

### 4-skills-vs-mcp-which-to-use-and-when
- Locator: `[[sources/agentic-engineer/20261014/6. Skills — The System You Needed/4. Skills vs. MCP： Which to use and when (9_11_2026 1：37：53 PM).html#4-skills-vs-mcp-which-to-use-and-when]]`
- Summary: Uses Supabase to make the skill-vs-MCP distinction concrete. A skill carries a tool's real, current conventions so the agent stops guessing from outdated training data; an MCP connects the agent to your live instance of that tool. They do different halves of the same job, and a real project often wants both. The workflow can find and wire the relevant ones for your stack — but asks before installing and leaves real-account sign-ins to you.
- Key claims: Most skills you'll actually use are built for a specific tool — a Supabase skill teaches how Supabase really works right now (how auth is set up, how row-level security is done, its current API, the patterns the Supabase team recommends) so the agent follows the real thing instead of whatever it half-remembers, which for a fast-moving tool is often out of date; same for a Next.js skill, a Stripe skill, a Prisma skill — each carries that tool's real, current way of doing things; MCPs are also tool-specific but do the other half — a Supabase MCP doesn't teach conventions, it connects the agent to your actual Supabase project (your real tables, real data, real queries) instead of assumptions; on one tool you see the whole picture: the skill knows how to write correct Supabase code, the MCP reaches into your live Supabase and works with what's actually there — one is knowing how the tool works, the other is having a line into your real instance of it; normally assembling this is a chore (for every tool you'd find the right skill, then the right MCP, then wire each up by hand), but the workflow looks at the tools and stack you're actually using and finds the relevant skills and MCPs automatically; it doesn't silently install everything — it asks before installing, and for MCPs that connect to real accounts (authenticating into your actual Supabase) that step is yours (you sign in, you approve the access); the recurring pattern: the system does the tedious part, you make the calls.
- Learner-relevant: The decision rule for the whole part — "Skills give the agent a tool's real conventions. MCPs give the agent live access to your real instance of that tool." Concrete tool examples: Supabase (auth, row-level security, current API), Next.js, Stripe, Prisma. Explains the workflow's automatic skill/MCP discovery with approval gating and real-account sign-in left to the learner. Closing pointer: next you'll see why such a system matters at all — a real build done the old way and with the workflow side by side.
