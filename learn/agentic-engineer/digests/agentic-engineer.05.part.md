# Digest — agentic-engineer (part 5) — Context Engineering

## Overview (L1)
- What Context Engineering Means — Reframes the real lever for AI coding: not prompt engineering but context engineering. Your prompt lands on top of everything the agent already knows in that moment (files read, conversation so far, always-on setup); that environment, not the exact wording, decides output quality. Context engineering is deliberately deciding ahead of time what gets loaded always, what is reached for on demand, and what is never carried — systems architecture, not wording, with prompting as the last and smallest step.
- The Three Types of Context — Categorizes project context into three types with one defining distinction: always-on is paid every session, on-demand and reference are paid only when used. Always-on (the AGENTS.md standing brief) loads automatically before you type; on-demand is the agent pulling files/skills/grep results itself mid-task; reference is material that enters only when explicitly pointed at (specs, design docs, the wider codebase on disk). The lesson teaches why always-on must stay ruthlessly small and gives a one-question test for it.
- CLAUDE.md AGENTS.md How They Load — Makes always-on context concrete with the mechanics of how rule files reach the agent, demonstrated on a freshly created Next.js repo. Rules arrive two ways: exploration (a maybe — the agent might open and follow a file while looking around) and always-on context (a guarantee, loaded before you type). The key trap: Claude Code reads exactly one file at startup, CLAUDE.md, not AGENTS.md — AGENTS.md loads only via an import pointed at from CLAUDE.md.
- Code Structure That Makes Agents Work Better — Argues your code is context, so code structure is a standing context cost paid every session. Three structural choices move the cost most: file size (big files drag unrelated code into the window), predictable naming and location (cut the search the agent has to pay for), and colocation (things that change together live together, turning a scavenger hunt into a single read).

### 1-what-context-engineering-means
- Locator: `[[sources/agentic-engineer/20261014/5. Context Engineering/1. What Context Engineering Means.srt#1-what-context-engineering-means]]`
- Summary: The instructor revisits the Module 1 root cause "no real context" and argues that reaching for prompt engineering when output is bad is the wrong lever. A prompt does not land in a vacuum — it lands on top of everything the agent already knows (files read, conversation so far, the always-on setup), and that environment determines quality far more than the wording of the one line typed. The skill is designing what the agent knows before it ever reads a prompt.
- Key claims: The trap is that when output is bad, developers reach for prompt engineering ("word it better, add more detail, find the phrasing"), but the prompt is only one small thing arriving into the context; a beautiful prompt into an empty context still forces guessing, while a rough prompt into a context with the right file/convention/constraint loaded gets it right the first time — same agent, same model; context engineering is design, not wording: deciding deliberately ahead of time what gets loaded and what doesn't, what the agent should always know, what it should only reach for when needed, and what it should never carry; it is systems architecture (an architect sets up everything known before the first brick goes down); prompting still matters but is the last and smallest step in the chain — the leverage lives upstream in the context; every failure named in Module 1 traces back to a context decision somebody didn't make on purpose.
- Learner-relevant: Establishes the module's core thesis and vocabulary ("context engineering"). ### 2-the-three-types-of-context
- Locator: `[[sources/agentic-engineer/20261014/5. Context Engineering/2. The Three Types of Context (9_11_2026 1：34：51 PM).html#2-the-three-types-of-context]]`
- Summary: Lays out the three types of context. Type 1, always-on context, is loaded every session automatically before you type a word; in this workflow it lives in `AGENTS.md`, the project's standing brief (the stack, core conventions, rules true no matter the task — e.g. money stored as integer cents, never floating-point dollars). Type 2, on-demand context, is what the agent pulls in itself mid-task (a file opened after a search, a skill whose body loads once its trigger matches, grep results). Type 3, reference context, exists in the project but enters only when explicitly pointed at (specs, design docs, the wider codebase on disk).
- Key claims: The one distinction that matters is cost cadence — always-on is paid every session; on-demand and reference are paid only when used; always-on loads whether or not it is relevant, which is both the point and the catch; on-demand is the agent reaching for something as it works, while reference is loaded because it was pointed to (a spec handed to a task, a doc a file links in) — deliberate, directed, and only then; always-on has to stay small because every line is rent paid on this conversation and every one after, and a bloated file burns tokens and causes context rot (irrelevant material competing for attention measurably pulls the model off the current task); the named failure is the "nine-files mistake" — wiring nine documents (style guide, API conventions, folder-structure doc, testing philosophy) into always-on builds nine files of rent that crowd the window and dilute attention on the one or two facts that mattered; the test for any line before it earns a place is "Is this true for every task?" — if only some tasks, it belongs in on-demand or reference; the discipline can later be maintained by the workflow's own skills that build and trim `AGENTS.md` automatically, from what the project actually is.
- Learner-relevant: Core mental model for the module, plus concrete terminology and file name `AGENTS.md` as the standing brief. The "money in cents, never float dollars" example and the "nine-files mistake" are the memorable anchors. Sets up the next lesson's mechanics: how the always-on file loads, which file governs what, and a subtle mistake that looks like it loads context but silently loads nothing.

### 3-claudemd-agentsmd-how-they-load
- Locator: `[[sources/agentic-engineer/20261014/5. Context Engineering/3. CLAUDE.md AGENTS.md How They Load.srt#3-claudemd-agentsmd-how-they-load]]`
- Summary: A practical walkthrough (creating a new project repo and a new Next.js application inside it) of how rule files actually reach the agent. There are two completely different ways: exploration, where the agent may or may not open a rule file while looking around (a "maybe" that depends on the task, what looks relevant, and whether it pokes around at all), and always-on context, loaded at the very start of every session before you type anything regardless of exploration (a guarantee).
- Key claims: The real question is how to know for sure what is in the always-on channel — the `/context` command shows exactly what is loaded into the current session (ignore token counts, look at the "memory files" line), and `/memory` opens/lists the memory files by name; Claude Code reads exactly one file at startup for its always-on context — the `CLAUDE.md` file, not `AGENTS.md` — which surprises developers because `AGENTS.md` is the shared file most other tools read natively, and there is no fallback; `AGENTS.md` only loaded because `CLAUDE.md` points directly to it via an import that tells Claude Code to pull that file into the loop when loading always-on context; removing the import and reloading drops the memory files to none, so `AGENTS.md` falls from the guaranteed channel down to a "maybe" reachable only if the agent happens to open it while exploring; re-adding the reference makes those rules guaranteed but not free — everything in it loads at the start of every session, so keep it to only the handful of rules the agent must never get wrong; a bloated always-on file is a tax paid on every conversation forever, so a rule that matters only for part of the project belongs closer to where it's used or in a file the agent loads only when relevant; the audit skill will continuously update `AGENTS.md` to keep only what truly matters.
- Learner-relevant: Concrete mechanics, commands, and file names: `CLAUDE.md` (the one file Claude Code reads at startup), `AGENTS.md` (the shared/imported version), the import mechanism, and the `/context` and `/memory` commands. Two takeaways: exploration is a maybe and always-on within those files is a guarantee, achieved via the import; `/context` shows which files were loaded and `/memory` shows exactly which — never assume, just look.

### 4-code-structure-that-makes-agents-work-better
- Locator: `[[sources/agentic-engineer/20261014/5. Context Engineering/4. Code Structure That Makes Agents Work Better (9_11_2026 1：35：43 PM).html#4-code-structure-that-makes-agents-work-better]]`
- Summary: Makes the case that your code is context — every time the agent works on a feature it reads the actual source (files, functions, folder layout), and that reading lands in the window and is paid for like everything else. So code structure decides whether the agent's context is cheap or expensive to load and whether it finds what it needs in one read or ten. Three structural choices move that cost the most.
- Key claims: File size is a context cost — to touch one function in a 600-line file the agent brings a lot of unrelated code along (imports, surrounding functions) because it reads the file whole or the wanted part is buried; a project split into small, focused files lets it load close to just the piece it needs, so "keep files small" matters because big files drag in code the task never needed (self-inflicted context rot); predictable naming and location cut the search — the agent has no index of the project, so how hard the thing is to find decides the cost: `auth.ts` is found in one search and one file, while the same logic in `utils2.ts` behind a `handleThing` function forces wider searches and pays for wrong guesses; colocation means one read instead of a scavenger hunt — when a feature's pieces (model, handler, validation) live together the agent reads one neighborhood, but scattered across five distant folders it reads five neighborhoods, pays for adjacent irrelevant code, and carries the noise forward; the one idea under all three is that a structural choice is a context cost paid every session the agent works in that codebase, not once — good structure is a standing discount, bad structure a tax; the governing question is "When someone comes back to change this, how much will the agent have to load to find it and touch it safely?" — if the answer is "a lot," that is not a clean result no matter how well it runs.
- Learner-relevant: Explains why the later workflow keeps producing small, focused files instead of one growing blob — you are writing the environment your agent works inside. Concrete examples: 600-line file cost, `auth.ts` vs `utils2.ts`/`handleThing` naming, create-order feature colocated vs spread across five folders. Closing checkpoint: a handful of quick real situations where the right move is a judgment call, drawing on the first four modules.
