# L1 overview

- **The Experiment: One App, Two Builds** — Same developer, same day, same models, one movie recommendation app built twice: build one by pure vibe coding (prompt, watch it appear, "now add this") with no plan on disk, no written decisions, no tests; build two through the agentic workflow (scope first, every load-bearing decision captured before code, agent gated from inventing unapproved things). The vibe build is not bad — it works and would impress in a demo — so the honest question is what happens after the demo, at 100 users, at 5,000, or six weeks later when you try to change something.
- **The Vibe Build: A Working App in One Session** — One prompt, one session, about 2,000 lines of code: Next.js scaffold, Supabase auth, swipe onboarding, feed, CSV import, and an LLM that generates 18 recommendations per feed with reasons, validated against TMDB so nothing hallucinated slips through. The validation is genuinely clever and the output feels impressive — which is the trap: a demo hides concurrency behavior, page-load cost, and the mid-file decisions that become a monthly bill.
- **Watch It Break** — Opening the feed takes 40 seconds, every time, because each page load calls the most expensive model live in the request path and regenerates recommendations from scratch, then fires a batch of TMDB validation requests. Refresh and it is 40 seconds again with a different set; three tabs on the same account at the same instant return three different answers, sometimes the same movie with contradictory reasons. The feed is a slot machine with no stable opinion about the user, and every one of those behaviors was invisible in the demo.
- **Autopsy: Reading the Vibe Codebase** — Four "killers": Opus hardcoded at one line (16,000 max tokens, adaptive thinking) wired into a mount-time effect with no cache, so the most expensive operation in the app runs on every page view at about 35 cents each; an unthrottled `Promise.all` over roughly 24 TMDB validations with no rate limit, backoff, or retries, whose catch returns `null` so failures vanish silently; an import route that deletes all prior ratings then inserts 500 items with no transaction, so a mid-way failure leaves no rollback; and zero tests plus 85 lines of raw SQL with no migrations folder. The lines are clean — the failures are architectural, i.e. undecided.
- **Workflow-First: Decide Before You Build** — The same prompt goes into a scope skill that interviews instead of coding (MVP boundary, who it is for, what is explicitly out) and writes an ordered plan with stack, data model, and design system before any feature. An architect skill then asks one decision at a time with real options and a recommendation, including the caching decision the vibe build made silently — and the chosen answer becomes an acceptance criterion in a spec file in the repo. Then develop, verify (real requests, optionally Playwright MCP), review (another agent cross-checks the spec), test, and sync.
- **Autopsy: The Workflow Codebase** — Every vibe failure is answered structurally: the feed is a taste vector matched by one vector-index database call into a cached recommendations table, so the read path has no model call and costs effectively nothing; reasons come from one batched Sonnet call with thinking off, only when taste changes or on explicit refresh, behind a named `feed-stale` function backed by a written option that rejected live generation with its cost stated. Import chunks 100 rows, resumes on retry, upserts by movie ID so nothing is deleted, and dedupes so a retry cannot wedge forever; vibe search parses intent with a cheap model, retrieves real candidates by embedding, and constrains selection to a schema the model cannot escape. Tests are named by acceptance-criteria number (AC7), six migrations exist, and the larger codebase is larger only in load-bearing lines.
- **The Two Bills** — Two bills: running it and building it. Runtime: 35 cents per feed open and ~30 cents per vibe search in the vibe build versus effectively zero and ~1.5 cents in the workflow build — roughly $5 per user per month against under a dime, about 60x, scaling to ~$25,000 vs ~$400 at 5,000 users and ~$5,000,000 vs ~$70,000 at a million. Build cost honestly ran the other way: the workflow used meaningfully more tokens, but on one Claude Max subscription in one day, and most of the excess was waste (stale uncleared context at premium prices, premium models doing grunt work) now fixed by session hygiene, model routing, and subagents.
- **The experiment's verdict** — The vibe build's problem is not that it is expensive but that it is architecturally unfundable: costs scale with page views while consumer revenue cannot, so every new user deepens the hole, and none of it was chosen by a person. The workflow's obvious win is cheap runtime because expensive decisions were made on purpose; its quieter win is that it now polices its own build cost, a lesson the build itself taught and the tools encode.

- `#L1-L237` — `2. The Vibe Build A Working App in One Session.srt` — A single session compressed to a couple of minutes. One prompt and nothing else: "build me a movie recommendation app — users sign in, import Letterboxd CSV ratings or swipe through movies to onboard, get a personalized feed with reasons, and a vibe search." That is the entire specification. The agent scaffolds Next.js, wires Supabase auth, builds the swipe cards, feed page, and import endpoint; when it needs recommendations it does the obvious thing — asks the smartest model to generate 18 movies with reasons for this user's taste — then validates each suggestion against the TMDB database so nothing hallucinated slips through. Credit where due: the validation step is clever. Result: about 2,000 lines of code in one session, and it works — sign-in, swipe onboarding, feed generation, genuinely good recommendations including deep cuts because a quality model knows more movies than any seeded database, a vibe search that understands "something like Blade Runner but funnier," and a taste profile that is a little too accurate. The author names the seduction explicitly: posted on X this is "I one-shotted a full movie recommendation app," potentially thousands of likes, a tweet he has seen a hundred times. He then refuses the expected move of declaring vibe coding bad and everything shown wrong, because everything shown is real — the app works, the speed is real, the feeling that you can build a full working app is real. What a demo cannot show: what happens when a few more users load the app at once, what a page load costs, and the decision the agent made in the middle of the engine file that becomes a costly monthly bill at scale. Nobody decided it; it just happened, while the time lapse looked amazing. Demos hide economics — load times, token costs, and more — so the lesson stops demoing and goes to real behavior.

- `#L1-L213` — `3. Watch It Break.srt` — The single most basic user action, opening the feed, exposes everything. It takes 40 seconds, and the explanation is the architecture: every time anyone opens the feed, the app calls Opus — the most expensive model available — live in the request path and asks it to generate recommendations from scratch, then fires a batch of parallel TMDB validation requests. Every single page load. Refresh and it is another 40 seconds, and although the recommendations might look similar, they are not: a newly fetched, from-scratch set each time, so the feed is basically a slot machine. The reproducible test needs no special tools: open the same app in three tabs on the same account and taste profile, refresh within seconds of each other, and get three different answers; look closer and the same movie recommended in two tabs seconds apart carries completely different reasoning, and neither is exactly wrong. That is the tell — both are plausible, but this is not a lookup and no fixed answer is being retrieved. Each tab triggered a fresh generation, a fresh generation is a fresh guess, and a guess means the AI does the thinking for every movie it recommends, which costs a lot of tokens. Worse than cost: the app has no stable opinion about you, only a new one every time you ask. All of these behaviors were invisible in the previous lesson's demo. The hand-off to the next lesson: open the code and find where each error was born; the spoiler is that none of them were decided — all of them were defaults, the choices the AI made instead of the author.

- `#L1-L168` — `4. Autopsy Reading the Vibe Codebase.srt` — Reads the vibe build like a reviewer, starting with killer one under `lib/engine.ts`, the matching engine. The design sounds right: the model proposes candidates (title, year, one-line personal reason) and everything returned is treated as unverified and must pass `tmdb.ts` validation before display. Then the single line that ruins it: line 16 selects Claude Opus 4.8 — a very expensive model to run many times. Around line 68, "generate feed candidates" uses that Opus model with 16,000 max tokens and adaptive thinking to produce the user's taste profile. In the feed page, line 34's `useEffect` calls the loading function on mount, so recommendations are fetched on every load, and there is no cache anywhere in the file — every visit and every reload fires it. Fine for one user; catastrophic for tens, hundreds, or thousands doing the same, or for someone playfully trying to break the app. Fixing it is simple, but because the author was vibe coding and let the agent lead, he trusted it to do it properly and it never did. So the most expensive operation in the entire application, using one of the most expensive models, runs on every page view at about 35 cents each time — a number to remember for the scaling lesson. The structural note that closes the section: none of this is a bad-line problem, it is a placement problem — the expensive call sits in the request path and no named decision ever put it there.

- `#L169-L432` — `4. Autopsy Reading the Vibe Codebase.srt` — Killers two through four. Killer two, in `tmdb.ts`'s `validate-candidates`: a `Promise.all` mapping over every match — about 24 at once — with no rate limiter, no backoff, no retries, and a catch block that just returns `null`, so a rejected validation vanishes and, when TMDB pushes back, candidates silently disappear; the catch works exactly as written. Scroll up to line 44 and the API key is set as a query-string parameter on the request URL, so the key is now in every log and every proxy between the app and TMDB. Killer three, in the import route's `route.ts` line 35: the agent wrote the comment "replace any previous import wholesale, the export is the source of truth," then line 36 deletes all of that user's previous ratings, and lines 45–48 manually loop over 500 items with nothing wrapping the deletes and inserts — a chunk that fails partway has already deleted, with no rollback. The agent even documented exactly what it was doing, but nobody checked whether that was acceptable because no decision was ever visibly being made. Killer four is what is missing: no test anywhere in the repo, and no migrations folder — just 85 lines of raw SQL schema — while the untested code is full of edge cases (Letterboxd parsing, fuzzy title matching), pure functions with no test on them. The lesson: it is not that the AI writes bad code — any 10 lines are clean, readable, seemingly meaningfully named, and line by line the codebase is good. The failures are all architectural: where the expensive call sits, what happens under concurrent load, what happens mid-failure, what is true at 400 ratings instead of 40. Those are not line-level properties but big decisions, and every one was made implicitly by a code generator optimizing for "it runs in the demo," mid-timelapse. Vibe coding does not produce bad lines; it produces undecided architecture. Sets up build two, where all four decisions are made on purpose before the code.

- `#L1-L285` — `5. Workflow-First Decide Before You Build.srt` — The highlights of build two, with the promise that each skill gets its own full lesson in the next two modules; what matters here is the shape of the flow. It starts with the scope skill, fed the exact same prompt as the vibe build. Instead of writing code it interviews: what is the MVP boundary, who is this for, what is explicitly out. It writes the plan to a file with features ordered, foundations first — and notice what is on the plan before any feature: the stack decision, the data model, and the design system, the ground before the house. Then the big one, the architect skill pointed at the data system: it does not invent choices, it asks one question at a time with real options and a recommended pick, and these are the decisions that matter. The pivotal example is the caching decision — the 35-cent one the vibe build made silently in the middle of a huge file — here it is a question on screen with trade-offs, the author chooses, and that answer becomes an acceptance criterion in a written spec that lands in the repo, so the decision now exists as a file that a future self, a team, and the agent can read and be held to. Next is develop, which builds what the architect planned and specced and leads the process while the author stays in charge; it will never invent undecided things, which is exactly the disease seen in the vibe build. After the build comes verify, which launches the actual app and proves features against the spec's criteria with real requests, and with Playwright MCP real browser testing; review, where another agent cross-verifies the spec the current agent wrote; test, which writes the suite for what changed; and sync, which records what shipped so the next session can start smart. The whole flow is scope → architect → develop → check → test → sync: more steps than "please build me an app, no questions," and the next lesson shows what those steps bought, side by side with the vibe build on the same three features but opposite engineering.

- `#L1-L246` — `6. Autopsy The Workflow Codebase.srt` — Holds the vibe numbers in view (40 seconds, 35 cents per page load) and then shows the same app actually engineered, feature one: the feed. Your ratings become a taste vector; in the feed candidates file, around line 46, is the entire retrieval — one database call and a vector index finds the movies closest to your taste out of a real catalog, and the result is written to a recommendations table. Opening the feed runs the `get-feed` action in feed actions, which simply reads that table: that is the whole read path, with no model call anywhere in the file, so page cost is effectively zero and speed is instantaneous — just the time to get data back from Supabase. The AI still shows up, but for one small job: `feed-reasons` writes one short "why this fits you" line per pick in a single batched Sonnet call — Sonnet, not Opus or Fable — one call for the whole feed, thinking switched off because a one-sentence reason does not need it, and it runs only when taste actually changed or the user hits refresh, never on page load. The cache refresh is a decision with a name: `feed-stale`, near line 61 of generate. Then the part that matters: the scope's `007` markdown documents the options the architect skill asked about — whether to cache the recommendation set, how to retrieve movies, who writes the reasons — and both answers are written down. Option one, chosen: cache it and regenerate only when the profile changes. Option two, rejected with its cost stated next to it: compute live on every load without cache, paying a multi-second Sonnet call and its cost on every page load, reshuffling picks and reasons each time so the feed is never stable (expensive and a worse experience), and risking the serverless duration limit on every render. That rejected option is the app whose code was read earlier, present here not as code but as a rejected opinion.

- `#L247-L609` — `6. Autopsy The Workflow Codebase.srt` — Features two and three, plus the verdict. Import: the browser parses the CSV and uploads 100 rows at a time, so hitting retry resumes the same import instead of starting over; in the import action there is a retry helper, and every chunk already retries with backoff before it gets that far; nothing existing is ever deleted because matching rows are upserted by movie ID, which removes the window where your ratings do not exist (the delete-then-insert of the vibe build). The dedupe handling is the senior detail: if two rows in the export resolve to the same movie (a re-release or alias) and both hit the database in one statement, Postgres throws, the chunk fails, and because a retry replays the same input the import is wedged forever — solved here, and present not because someone hit the bug and patched it but because the architecture's acceptance criteria said an import can never lose data before any code existed to break. Vibe search is a pipeline readable in five lines: get the profile, figure out what they want, shortlist, log, return. A small cheap model parses the query into structured intent (year, runtime, mood, theme, tone, feel), a vector embedding search pulls real candidates out of the catalog, and a mid model picks three to five only from the list it was handed. `select.ts` tells it not to invent movies, but that is just asking — the difference is that the movie schema is enforced throughout, so it cannot hallucinate a movie: not because it is told to behave but because the architecture gives it no way to misbehave. That is the difference between a rule and a guarantee. Around it, Vitest is configured with tests for taste math and CSV parsing — the other repo had zero — and the tests are named by acceptance-criteria number (e.g. AC7), so tests point back at decisions. Six versioned migrations show how the data system upgraded with each feature. The build is much larger than the vibe one, but none of the extra lines is decoration: every one is load-bearing and traces back to a question a skill asked before the build. Verdict: the vibe codebase is made of defaults, this one of decisions.

- `#L1-L52` — `7. The Two Bills (9_11_2026 1：40：21 PM).txt` — Two bills, the running one everybody forgets and the building one people expect the author to hide. Bill one, per action: the vibe build pays about 35 cents in AI spend every time the feed opens — not the first time, every time, because the model call sits in the request path with nothing cached — plus about 30 cents per vibe search. The workflow build's feed open costs effectively nothing (a cached table read) and its vibe search about a cent and a half, because the expensive part is a database query and the model only picks from what the database found. Monthly, for an active user with a couple of feed opens and a search or two a week: about $5 per user per month versus under a dime, roughly 60x before anyone does anything clever. Scale: 100 users ~$500 vs ~$30 per month; 5,000 ~$25,000 vs ~$400; 50,000 ~$250,000 vs ~$4,000; 1,000,000 ~$5,000,000 vs ~$70,000. The workflow column's floor is fixed infrastructure, database and hosting, not AI; the vibe column has no floor and no ceiling, just a multiple of pages viewed. At 100 users the vibe build is annoying and the workflow one basically free; at 5,000 it is a salary; at 50,000 a funding round paid to a model provider — though the vibe app never reaches 5,000 because nobody waits 40 seconds for a movie list twice. The sentence that matters more than any row: the vibe build costs about $5 per user per month to run, and no consumer movie app earns $5 per user per month — it is not expensive (fixable) but architecturally unfundable, costs scaling with page views while revenue cannot, so every new user deepens the hole, and nobody chose it: no meeting weighed live generation against a cache; a code generator optimizing for "runs in the demo" decided mid-file, mid-timelapse, while the same decision sits in the workflow repo as a rejected option with its cost stated. Bill two, building: the workflow build used meaningfully more tokens — scoping, interviewing, specs, verifying are real work — yet both apps were built in one day on a single Claude Max subscription, the only real cost being hitting the five-hour limit a couple of times, no surprise invoice. More important, most of those extra tokens were not thinking but waste: long uncleared sessions re-reading stale history at premium prices, and premium models doing grunt work a mid-tier model handles — the price of doing it properly without session hygiene, exactly what an earlier module warned about. The shipped workflow differs from the one that built these repos, and three changes target the token bill: session hygiene is the workflow's job (skills tell you when to clear; scope, architect, and develop run in fresh sessions, which works because state lives in files, so clearing costs nothing); model routing (big models for decisions, mid-tier for execution); subagents draft long documents so the main session never carries them — a different order of magnitude in the wasteful parts with all the benefit intact. Also a naming warning: what these early repos call an ADR is now called a spec. Takeaway: the workflow makes the app cheap to run because expensive decisions get made on purpose by a person, and less obviously it polices its own build cost — not a day-one design feature but a lesson this build taught and the tooling encoded. You get the lesson; you skip the receipt.
