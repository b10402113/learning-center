# Digest — agentic-engineer (part 18) — Greenfield: Data Model

## Overview (L1)
- **Architecting the Data Model Spec** — With coding standards/tooling done, the `data model` scope item is pending; the lesson runs the `architect data model` flow (feature design on the existing text stack, tracer-bullet approach, workflow tier `full`) which proposes decisions and asks the human to choose. The bar: entities and relationships must carry ratings from both onboarding paths, store a taste profile, and generate picks with reasons without a later breaking change.
- **Full Target Model vs Thin Thread** — The agent asks how much of the model to design now; the author chose "full target model, migration sliced": design every entity all 11 features need as one coherent target, then land migrations slice by slice, keeping the tracer bullet thin.
- **Taste Profile Storage Choice** — Chose a `taste vectors` table (n rows per user, one row per taste facet with label + vector), starting with a single average row for the tracer bullet and growing to clustered facets later with no schema change; rejected a single vector column because broad averages go mushy and moving facets later is a breaking change.
- **Ratings and User Profile Tables** — Ratings arrive from two paths (swipe deck, Letterboxd export) and normalize into one numeric scale with a `rating` column plus a `source` column; app user data hangs off a `profiles` table keyed by `auth.userId` since Supabase owns `auth.users` and Drizzle does not.
- **Nine-Table Target Model, One Migration** — First migration stands up the whole target model: `profiles, movies, ratings, taste vectors, picks, model usage, watchlist entries, import runs, audit events`; the four idle tables are marked until their features turn.
- **Scoped Query Helper (Ownership)** — Rule one: a helper must apply the user ID itself, not trust the caller; a generic registry of user-owned tables plus a typed registry that closes the "forgot to register a table" gap, and Postgres row-level security set to deny-all.
- **Schema Layout, Enums, Movie Identity** — One Drizzle file per entity (`source/db/schema`) re-exported from an index; fixed value sets (rating source/state, big state) as Postgres enums; movie = UUID primary key + unique TMDB ID + embedding column, with nullable embedding plus a partial index for rows created before their embedding exists.
- **State, Starter Deck, Cold Start** — Swipe gives like/dislike/skip (a skip is a rating row with a skipped state; score null, real value stays a Feature-6 scoring decision); ratings are one row per user+movie updated in place; starter deck is a boolean flag; missing taste-vector row means onboarding is incomplete. Auth row creation via a Postgres trigger on `auth.users` insert.
- **Cross-Check by a Second Model** — Because the data model is critical, the spec is cross-checked by another model, which surfaces 10 findings (3 blocking, 6 real/cheap, rest minor) — e.g. nothing writes the account-deleted audit row, the migration role may lack trigger privilege on `auth.users` needing a `security definer` with pinned search path, and RLS Drizzle/Supabase confusion.
- **Building and Verifying Against a Live DB** — Development blocks on a live Supabase project; the Supabase MCP is authorized (encountering a bad MCP.json URL, a wrong account, restart-to-gain-tools) then the migration applies in one transaction and Drizzle journals it, seeds the starter deck, and proves acceptance criteria against the live database (20 movies, 2 auth users → 2 profiles, deny-all returns zero rows). Region discrepancy (EU West vs EU Central pinned) is the only flag.

### taste-profile-storage
- Locator: `[[sources/agentic-engineer/20261014/13. Idea to First Ship — Greenfield/3. Data Model.srt#taste-profile-storage]]`
- Summary: How a user's taste profile should be stored is debated. Options: a taste-vector table with n rows per user (one row per facet, label + vector) starting with a single average row; or a single vector column on the profile row.
- Key claims: the taste-vectors table keeps the cheap path open and the good path free — it can grow to clustered facets later with no schema change; a single vector column is simplest to read and teach but broad taste averages collapse into a mushy center, and moving to facets later is a breaking change; the author "much prefers the taste vectors table, with n rows per user."
- Learner-relevant: Decided schema shape: a `taste vectors` table keyed per user, one row per facet (label plus vector), seeded with one average row for the tracer bullet. Concrete example of designing for future growth without a breaking change.

### scoped-query-helper-ownership
- Locator: `[[sources/agentic-engineer/20261014/13. Idea to First Ship — Greenfield/3. Data Model.srt#scoped-query-helper-ownership]]`
- Summary: Rule one requires the query helper to apply the user ID itself rather than trusting the caller to. The chosen shape is generic operations over a registry of user-owned tables, with a typed registry the helper is the only consumer of, plus a documented step.
- Key claims: the helper must own the user scoping so no later feature can write a query that forgets whose data it reads; the remaining gap (nothing checks a new user-owned table was registered) is closed by a typed registry with a documented step; the project has no test suite and on this stack the database cannot check ownership, so the only real defense is removing the unsafe path rather than relying on remembering to avoid it.
- Learner-relevant: The security core of the feature. Explains why: no test suite, DB cannot verify ownership, so a mandatory scoped helper + typed registry is the defense. Ties to "row-level security deny all" and the generic helper shape.
