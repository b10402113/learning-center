# Digest — agentic-engineer (part 14) — Workflow: Find the Root Cause

## Overview (L1)
- The Three Kinds of Broken — Reframes the first move on a broken project as a question, not a technique: "What kind of broken is this?" Names three kinds — a normal code bug, an AI-specific failure mode, and an agent that lost the path — and argues each needs a completely different response. Sets the governing rule: a fix you cannot explain is a bug you haven't caught, so take evidence over intuition.
- The Method That Works on Any Code — Teaches the single method for the first kind (a plain code bug): the scientific method applied to a broken program. Defines debugging as observe → hypothesize → test → let evidence decide, with the core habit of changing one thing at a time. Notes the six steps are written below the video and that the debug skill automates them but never replaces your judgment about whether the cause was actually proven.
- Demo Running debug — A hands-on demo of the debug skill. Shows how to use it well: give it the three things up front (what you observed, what you expected, steps to reproduce), or let a prior check verify supply them. Watches for one hypothesis at a time, judges success by the small size of the fix, and contrasts it with "vibe debugging." Ends on the extra difficulty when an agent wrote the code: you cannot reason from author intent; you must recover it.
- Debugging Code You Didn't Write — Covers the second kind of broken (AI-written code fails). Because author memory is gone, read it like a stranger wrote it and treat a guessed intent as something to prove, not assume. Recovers intent from the spec's acceptance criteria, the surrounding code, and the running behaviour; if there is no spec, the "bug" may be a decision that was never made (that's /architect, not /debug). Names four failure patterns and their tells.
- Recover a Broken Session — Covers the third kind of broken: not the code, the agent. Recognize looping by repetition without progress, then make one judgement — is this session's context worth keeping (compact) or a liability (clear)? Lays out a five-step escalation (stop, ask what it believes, give it less, roll code back, clear and bring evidence forward), prevention via planning before editing, the three ways a stuck session ends, and a cross-tool reference card of recovery actions.

## Sections (L2)
### the-three-kinds-of-broken
- Locator: `[[sources/agentic-engineer/20261014/11. Workflow Find the Root Cause/1. The Three Kinds of Broken.srt#the-three-kinds-of-broken]]`
- Summary: Opens the module by arguing that the most useful first move when something breaks is not a debugging technique but the question "What kind of broken is this?" It distinguishes three kinds that look like versions of the same problem but need completely different responses, and explains why each wrong answer is expensive.
- Key claims: the three kinds are (1) a normal code bug — a real fault with observable, reproducible behavior that behaves the same whoever wrote the code; (2) an AI-specific failure — calls a library function that doesn't exist, writes convincing but quietly wrong logic, makes a real decision mid-file without telling you, misses an access rule or edge case, or fails only with real data (the happy path looks finished; the first unusual input exposes everything the agent never considered); (3) the agent lost the path — it repeats the same action, changes the same files back and forth, every attempt makes the project slightly worse, and it stays confident while moving further from the cause. Telling it to fix the problem won't help because the thing you're asking to solve the failure is now part of the failure.
- Learner-relevant: Each wrong answer costs differently: you can keep prompting an agent to fix a bug it genuinely cannot see when you should have stopped and reproduced it yourself; you can clear a confused session too early and throw away the evidence it already gathered; or you can spend an hour changing code when the real problem is that the agent lost track of the task 10 turns ago. The second kind is uniquely hard to investigate because you can't reason with the author's intent (you weren't the author) — even if you watched it being written, you don't know why every line is there. The governing rule under all three: a fix you cannot explain is a bug you haven't caught — if the error disappears and you can't say why it happened, you haven't proved the cause is gone; you may have hidden the symptom, moved it, or made the code temporarily harder to reach. A bug is a case you prove, not a message you silence.

### the-method-that-works-on-any-code
- Locator: `[[sources/agentic-engineer/20261014/11. Workflow Find the Root Cause/2. The Method That Works on Any Code.srt#the-method-that-works-on-any-code]]`
- Summary: Teaches the one method for the first kind of broken (a plain bug in the code). It states what debugging is not, defines it as the scientific method on a broken program, and stresses the single most important habit.
- Key claims: the method works in any language, on any codebase, whether the code came from you, a colleague, or an agent; debugging is NOT changing things until the error disappears (that is what everyone does and why bugs come back); it is the scientific method applied to a broken program — observe the failure, form one specific explanation, test it, and let the evidence tell you what to do next; the most important habit is change one thing at a time, so every result teaches you something.
- Learner-relevant: The six steps are written out below the video and are meant to be re-read rather than memorized ("I'd rather you read them than remember them"). You still need the method even though the debug skill can run it: the skill can reproduce, localize, test, fix, and protect faster than you can, but it cannot decide whether it actually proved the cause or just made the symptom disappear — that judgment is yours, and you can't make it if you don't know the method yourself. The method belongs to you; the skill is just a faster way to apply it.

### demo-running-debug
- Locator: `[[sources/agentic-engineer/20261014/11. Workflow Find the Root Cause/3. Demo Running debug.srt#demo-running-debug]]`
- Summary: A hands-on demo of using the debug skill well rather than re-explaining the method. It shows what to feed the skill at the start, what to watch for when reviewing its output, and how to judge whether it found the true root cause. It closes by pointing at the extra difficulty of debugging agent-written code.
- Key claims: running `debug` on its own asks you to provide the bug details to start; the most important part is what you give it at the start — the three things: what you observed, what you expected instead, and the steps needed to reproduce it (if you only say "this is broken," it has to stop and ask you for evidence, often the whole difference between a fast and slow investigation); if it cannot reproduce, it stops and tries to add additional instruments to make itself capable of reproducing it, then tells you what it came up with; when a prior check verify run already gathered the info, you can run `debug next data model` and it already has the three things (referencing the earlier `check verify data model` session that found real issues); the thing to watch for is one hypothesis — if you ever see an agent changing several unrelated things hoping the failure disappears, stop it, do one experiment with one piece of information, and only fix once it confirms the hypothesis; you'll know it's right by the size of the fix — most often fixes are super small when it found the root cause.
- Learner-relevant: Concrete worked example: ENV was never loaded — the smoke test imported dotenv config, which only reads a file literally named `.env`, but secrets were kept in `.env.local`, so `DATABASE_URL` and the values in `.env` were always empty; all seven tests ran every time with no failure signal. Fixed by loading `.env` explicitly into the smoke tests — literally a single line — then rerunning the full test suite. Contrasts the skill with "vibe debugging": a normal fix prompt encourages keeping changes until the red turns green, sometimes works, and finishes with no explanation of what was wrong. Debug instead requires a reproduction, one hypothesis, evidence, a minimal fix, and a regression test; its advantage isn't fewest moves but that you can explain why the result works. Review rule (from lesson 1): don't accept a fix you can't explain. Debug runs on code written by you, a colleague, or an agent, but agent-written code adds one extra difficulty — you can't reason from the author's intent because it was never yours; you have to recover it (next lesson).

### debugging-code-you-didnt-write
- Locator: `[[sources/agentic-engineer/20261014/11. Workflow Find the Root Cause/4. Debugging Code You Didn't Write (9_11_2026 1：51：47 PM).html#debugging-code-you-didnt-write]]`
- Summary: The second kind of broken — AI-written code that fails. It explains that the six-step method still works but one thing you normally lean on (author memory) is missing, and shows how to recover intent and recognize common failure patterns.
- Key claims: when you debug your own code you're remembering why you wrote it, and that memory does half the work without you noticing; on agent-written code that memory doesn't exist, and watching it generate isn't a substitute (you saw the output, not the reasoning); read it like a stranger wrote it — that's a technique, not just advice, because it prevents the mistake of deciding what a line "*probably* meant to do" and then debugging against that guess (you end up investigating your theory about the code, not the code); intent is recovered from the spec's acceptance criteria (what this was *supposed* to do / promised, turning a vague investigation into a comparison: here's what was promised, here's what happens, find the gap), the surrounding code (the conventions the file was supposed to follow), and the running behaviour (what actually happens vs. what the code appears to say); when there's no spec — common on AI-written code — a behaviour with no recorded decision behind it isn't a bug you can fix but a decision that was never made, which is `/architect`, not `/debug`.
- Learner-relevant: The four failure patterns, by name: (1) Invented function — calls something that doesn't exist or existed two versions ago — easy, loud failure; (2) Plausible but wrong logic — reads correctly, passes review, wrong with real data — hardest, the shape is right and the reasoning isn't; (3) A decision made mid-file — not strictly a bug, something was chosen by a generator and unreviewed — invisible until it conflicts with something; (4) The unconsidered edge case — happy path complete, first unusual input goes through a gap — easy once you feed it real data. The tell: the bug is almost never in the line that failed; it's in a decision made earlier that nobody wrote down, so your investigation carries the extra question "was this ever decided?". What doesn't change: same six steps, same discipline — one difference, you recover intent from the spec, surrounding code, and running behaviour instead of from memory; and when there's no intent to recover, you've found something worth more than the bug.

### recover-a-broken-session
- Locator: `[[sources/agentic-engineer/20261014/11. Workflow Find the Root Cause/5. Recover a Broken Session (9_11_2026 1：52：08 PM).html#recover-a-broken-session]]`
- Summary: The third kind of broken — not the code, the agent. It shows how to recognize a looping session, make the one judgment that determines recovery, and escalate through five ordered steps, plus how to prevent it and how stuck sessions end.
- Key claims: the signal is repetition without progress — same function rewritten five times barely differently, same files reopened, the diff getting messier, contradicting its own earlier decisions; a hallucination gives you wrong content, a loop gives you a broken process, and adding instructions makes a loop worse because the thing you're instructing is part of the failure; then make one judgment — is the context worth keeping? Productive but low on room → the context is an asset, **compact** it; full of failed attempts and repeated assumptions → the context is a liability, **clear** it (getting this backwards is expensive: clearing a productive session throws away gathered evidence; compacting a poisoned one carries the failed reasoning forward in compressed form, which is worse because it's harder to see). The five-step escalation in order: (1) Stop it — `Esc` halts the response, not `Ctrl+C` (which exits the session), costs nothing so never skip it; (2) Ask what it believes — "What do you think the problem is, and what are you assuming that might be wrong?" — a stuck agent is usually circling one false assumption and making it state that often breaks the loop; (3) Give it less, not more — most loops start because the task was too broad (e.g. "Refactor the authentication module" → "Extract the token refresh function from this file and touch nothing else"), shrink the task and put a hard boundary around what it may change; (4) Roll the code back — don't ask a confused agent to clean up its own mess; one limit that matters: checkpoints may not restore files changed through shell commands, so Git is the universal fallback — `git restore` for working-tree changes, `git reset` when the repository itself has to move; (5) Clear, and bring the evidence forward — don't repeat the original prompt (that recreates the loop), start fresh with the exact error, the failing test, and the one fact the old session kept missing (a clean session opening with strong evidence solves in two turns what a poisoned one couldn't in ten; clearing costs you the conversation, not the work — scope, specs, and AGENTS.md are still on disk).
- Learner-relevant: Prevention is to plan before editing — before a large change, have the agent plan without editing anything, so you can reject a bad approach while it's still a few lines of text rather than after it rewrote ten files. Every stuck session ends one of three ways: Steer out (you exposed the wrong assumption and narrowed the task), Reset to good (restore the code or clear the context), or Rethink (the repeated failure is telling you the plan is wrong, so back to `/architect` or `/scope`) — when the plan is wrong another prompt won't save it, and recognizing which of the three you're in is the actual skill. Cross-tool reference card (dated, goes stale fast; verify before publishing): Stop the response → Claude Code `Esc`, Codex `Esc`, Cursor `Stop or Esc`; Restore the code → Claude Code `Esc Esc or /rewind`, Codex `git restore`, Cursor `Restore Checkpoint`; Restore the conversation → Claude Code `Esc Esc or /rewind`, Codex `Esc backtrack`, Cursor `Edit an earlier message`; Start fresh → `/clear` (Claude Code and Codex) or `New chat` (Cursor); Preserve useful context → `/compact, /context` (Claude Code), `/compact` (Codex), `Summarise` (Cursor); Plan before editing → `Plan mode` (Claude Code), `/plan` (Codex), `Ask mode` (Cursor); Universal recovery → `git restore or git reset`.
