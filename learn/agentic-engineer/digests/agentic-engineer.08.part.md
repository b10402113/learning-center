# Digest — agentic-engineer (part 8) — Workflow: Ship Something Real (skills system + scope)

## Overview (L1)
- **Installing the JSM Skills System** — Opens the workflow module, the reason the course was taken. The skills are open source and install in one command (`npx skills@latest add js-mastery-pro-skills`), no account and no API key because a skill is just a markdown file of agent instructions. At recording there are nine skills (architect, audit, check, debug, develop, scope, sync, test) installed globally; the hard part is not installing them but knowing when to use each one, so the lesson sets the canonical new-project order: scope the idea, architect the stack, set up the project, audit what was created, then enter the develop loop.
- **Why the Workflow Is Structured This Way** — Pre-empts the objection that a workflow with named steps and required documents is "one guy's preferences dressed up as engineering." It comes straight from the software development lifecycle (requirements → design → implementation → verification, every stage feeding the next) and from architecture decision records, which exist because reasoning that lives only in a head disappears and later changes reintroduce solved problems. Agents make this worse because their instinct is to sprint at the code and silently fill in every missing decision; the skills do not invent a new process, they force the agent to follow the one a good engineering team already follows. GitHub ships Spec Kit and Amazon ships Kiro on the same premise; the real question is what happens to the documents on day 30.
- **Nine Skills: Finding Your Entry Point** — The orientation map: the full agentic loop (`idea → /scope → /architect → /develop (scaffold) → /audit → /develop → /check verify → /test → /check review → /document → /sync`, returning) with `/debug` available anytime something breaks. Explains why `/audit` moves: on an existing codebase it runs first, on a new project fourth (after stack choice and scaffold), because `/audit` writes `AGENTS.md` by reading the project that actually exists — pointed at an empty folder it would invent conventions. Also notes Spec Kit, Kiro, and BMAD as parallel systems, and that the interesting question is keeping living specs current, which `/sync` handles.
- **/scope: Challenge the Idea Before Any Code** — Every project runs on defaults (build order, care level per change, the answer when nobody has decided) that you either choose deliberately or the agent chooses for you — exactly what happened in the vibe build. `/scope` gives one place to define the project's shape before code and writes a tool-agnostic plan into `docs/scope/` (a slim index plus the plan; no library, database, host, or provider named). It takes two decisions out of the agent's hands: the build approach (Tracer Bullet, Skateboard, Facade, Journey) and the workflow tier (Prototype, Alpha, Beta, GA). It is a recommendation, not a track — every box is a suggestion you can skip, and `/sync` keeps the plan current against what actually shipped.

### why-the-workflow-is-structured-this-way
- Locator: `[[sources/agentic-engineer/20261014/8. Workflow Ship Something Real/2. Why the Workflow Is Structured This Way.srt#why-the-workflow-is-structured-this-way]]`
- Summary: Answers the obvious objection that a named-step, required-document workflow is just one person's preferences dressed up as engineering, by tracing it to the long-standing software development lifecycle and architecture decision records — and explains why it matters even more with an agent than with a person.
- Key claims: long before agents could write code, serious projects already followed the same path — work out what you're building, make the important technical decisions and write them down, set conventions everyone follows, build one feature at a time, and prove it works before calling it finished; that is the software development lifecycle: requirements into design, design into implementation, implementation into verification, each stage producing something the next needs; writing decisions down is not new either — engineers have kept architecture decision records for years because reasoning that lives only in someone's head eventually disappears, and months later someone changes the decision without knowing why and brings back the exact problem it prevented; an agent's instinct is to sprint at the code (as seen in the vibe build, where it got an idea, quietly filled in every missing decision itself, and started implementing within seconds, looking productive while building on decisions you never made); the skills do not invent a new way to build software, they just make the agent follow the process a good team should already follow, one stage at a time with each decision feeding the next; GitHub's Spec Kit and Amazon's Kiro share the same core premise (write requirements and decisions down before asking the agent to build), so "does writing things down help" is settled — the interesting question is what happens to those documents on day 30; these skills are not shortcuts for writing code faster but boundaries that stop the agent from skipping the parts of software development that matter most.
- Learner-relevant: Core framing for the whole module: named steps and required documents are the SDLC and ADRs, not personal preference. Key mental model — the agent's failure mode is sprinting past undecided decisions and filling them silently. Named comparators: GitHub Spec Kit, Amazon Kiro; the day-30 document-rot question is the thread carried through every later skill lesson.

- Key claims: the full loop is `idea → /scope → /architect → /develop (scaffold) → /audit → /develop → /check verify → /test → /check review → /document → /sync`, looping back, with `/debug` run any time something breaks; the chain is the full path but you rarely run all of it, and where you start depends on what you're starting with; on an existing codebase `/audit` runs first, on a new project it runs fourth (after the stack is chosen and the project scaffolded) — deliberate, because `/audit` writes `AGENTS.md` by reading the project that actually exists, and pointed at an empty folder it would have to invent your conventions from assumptions, which is the exact failure the workflow exists to prevent; GitHub ships Spec Kit, Amazon ships Kiro, and BMAD coordinates a cast of role-based agents — all put written structure in front of implementation and are right to; a specification written once and forgotten is worse than no specification because it is confidently wrong and slow to discover; `/architect` splits the decision from the reasoning, `/develop` reads only the build-facing half, and `/sync` reconciles all of it against what shipped.

### scope-challenge-the-idea-before-any-code
- Locator: `[[sources/agentic-engineer/20261014/8. Workflow Ship Something Real/4. scope Challenge the Idea Before Any Code.srt#scope-challenge-the-idea-before-any-code]]`
- Locator: `[[sources/agentic-engineer/20261014/8. Workflow Ship Something Real/4. scope： Challenge the Idea Before Any Code (9_11_2026 1：42：02 PM).html#scope-challenge-the-idea-before-any-code]]`
- Summary: The first boundary. `/scope` takes an idea before any code and writes a tool-agnostic plan into `docs/scope/` (a slim index plus the plan, naming no library/database/host/provider), then forces two decisions out of the agent's hands: the build approach and the workflow tier. It also works on existing repos, stays current via `/sync`, and is a recommendation rather than a rigid track.
- Key claims: every project runs on defaults (the order features get built, the level of care each change gets before shipping, and the answer when nobody has decided yet) — you either choose these deliberately or they get chosen for you, one feature at a time, by whatever the agent reaches for, which is exactly what happened in the vibe build (no build order decided so the agent built in whatever order it reached for; nothing decided out of scope so nothing was; no proof level decided so the agent picked the cheapest answer, none); `/scope` writes a plan into `docs/scope/` that names no library, database, host, or provider, deliberately kept tool agnostic so it does not rot when you change a dependency — those calls belong to `/architect`, one feature at a time; the plan stays high level (what needs building, what foundations must exist first, what depends on what, the order the project should grow in), is two parts (a slim index then the plan), and puts foundations before product features (stack, coding standards, data model, design system are listed above the features, "the ground before the house"); each feature gets a section with a line or two of intent, one `Done when:` line, and checkbox steps, with build order just the section order; run `/scope` with no argument on an existing project and it reads the repo to work out what shipped, what's in progress, and what's waiting, then plans the next idea around what's actually there; it is a recommendation, not a track — every box it writes is a suggestion, you can run any of them, skip any of them, and mark a feature done when you decide it's done, and the workflow records what you actually did including what you skipped; the plan stays current because as features ship `/sync` reconciles the scope against the repo, updating statuses and flagging what a change made stale.
- Learner-relevant: Build-approach decision (four long-standing engineering ideas): **Tracer Bullet** (walking skeleton, associated with Alistair Cockburn and *The Pragmatic Programmer* — one narrow path through the whole system, works end to end, then thicken); **Skateboard** (MVP, from Henrik Kniberg's skateboard-to-bicycle-to-car illustration — smallest version a real person could genuinely use); **Facade** (build the interface with temporary data before committing to the backend — right when the product must be seen/tested/approved first); **Journey** (finish every part of one complete user path — happy path, loading, empty, failure, edge cases — before starting the next). Workflow-tier decision (four tiers, each adds to the last): **Prototype** = `/develop` implements and self-checks and marks complete (experiments/spikes/personal tools); **Alpha** adds `/check verify` (must run in the real app and demonstrate expected behaviour); **Beta** adds `/test` (a real suite before closing — right level for most production products); **GA** adds `/check review` on a different model than the one that wrote the code, then `/document` (payments, auth, permissions, compliance, shared team work). Rules to remember: one project default recorded on the scope header's `**Workflow:**` line; individual features override with a tag beside their heading, e.g. `### 7. Payments · GA` (no tag means inherit); a higher tier makes a feature more likely to be marked `Needs spec: yes` (at Beta and GA the spec's cross-model decision critic runs automatically, Prototype/Alpha are often `Needs spec: no`), so the tier decides how much design happens, not just verification; Prototype closes on `/develop`, Alpha on `/check verify`, Beta and GA close on `/test` (GA's review and documentation run as the tail); an `Assumed` spec blocks `done` at every tier; at GA the agent that wrote the implementation is not allowed to be the only agent deciding whether it is safe. Concrete example scope file — `Scope: ReelA movie recommendation app that learns your taste from your ratings`, `Build approach: Tracer Bullet (one narrow path, working end to end, then thickened)`, `Workflow: Beta (after /develop: /check verify, then /test)`, with an at-a-glance feature table (e.g. `Stack & architecture`, `Coding standards & tooling`, `Data model`, `Design system & UI foundation`) and per-feature sections. Key mindset: `/scope` reads the idea, recommends an approach and a tier from the risk and size of the feature mix, and records what you choose — it's a workflow, not a process.
