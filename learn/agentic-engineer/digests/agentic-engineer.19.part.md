### architect-the-movie-catalog-and-cache
- Locator: `[[sources/agentic-engineer/20261014/13. Idea to First Ship — Greenfield/7. Architect the Movie Catalog and Cache.srt#architect-the-movie-catalog-and-cache]]`
- Summary: Runs the `architect` skill to design the spec for the movie catalog and cache feature before developing it. The workflow reads it as a new feature implementation on the existing web stack with no UI yet, and interviews the learner through scope, matching, execution location, fields, freshness, TMDB client choices, rate limits, and post-matchers, then writes the spec.
- Key claims: The feature must fetch and store the 20-film starter deck from real TMDB data plus expose a reusable title+year lookup returning a stored movie row; when a title+year match is uncertain, score/accept else record/refresh-on-read-when-stale; matching compares normalized title similarity against both title and original title, takes the better, and penalizes year distance against one threshold; TMDB stays the source and a fetched record becomes a permanent row rather than a cache with an expiry, with a lookup checking Postgres first by normalized title so a repeat lookup costs no network call.
- Learner-relevant: Introduces the `architect <feature>` skill and the sparring-partner interaction. Concrete decisions: anything talking to TMDB runs as an ingest background job (first install of ingest), jobs for writes / requests for reads, a rare miss path so an inline fetch on cache miss is acceptable; stored fields normalized title, original title, IMDb ID, popularity, vote average, vote count, keywords, tagline, and refreshed-at column; staleness = 30 days; TMDB auth via V4 access token as a bearer header (env name `TMDB_READ_ACCESS_TOKEN`); client = plain fetch plus Zod schemas; rate limit ~50 requests/second with no daily cap, controlled by ingest concurrency plus retries on 429; posters store path only and add `image.tmdb.org` to the Next image remote pattern; normalization strips case, accents, punctuation, and leading articles; storing one film takes one search plus one detail call that pulls credits and keywords with a pending response; 404s delete the row and treat the film as gone; embeddings stay null for feature 6; a film with no overview is a distinct matched-but-unusable result; concurrent same-film writes use upsert; a mid-deck failure keeps per-film successes but fails the run; reads are signed-in only and jobs verified by an Inngest signature. Spec completeness pass: all required sections present across index MD and rationale, all 16 acceptance criteria trace to build tasks and back, value-sourcing table names a source for every value. Next step is `clear` then "develop the movie catalog and cache."
