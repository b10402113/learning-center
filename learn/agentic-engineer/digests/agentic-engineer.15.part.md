# Digest — agentic-engineer (part 15) — Workflow: Code You Didn't Write

## Overview (L1)
- **Nobody Starts from Scratch** — The framing lesson for the module: most professional engineering is changing an existing system, not building from zero, and the real reason agents fail on legacy code is that they have no map. The agent can read what the code says but not why it exists (why three versions of a service exist, why one strange line prevents a production failure), so without context it guesses. Names two risk directions (what the agent puts into the project — insecure code, exposed secrets, weakened access rules, unapproved decisions; and what you give the agent — source, credentials, customer data, private business logic leaving the org) and shows how the workflow maps onto the problem: `/audit` builds the map, `/architect` reads existing implementation before deciding, `/develop` reads before writing and follows existing patterns, `/check verify` proves it works inside the real app without breaking behaviour, `/check review` gives it to another model. Two jobs in order: understand first, then change safely.
- **Demo: Running audit on a Real Open-Source Project** — Runs the `audit` skill on a real, two-year-old codebase the author did not write (BookWise, a university library app). Because the repo is already established (62+ source files, DB migrations, auth), audit routes to phase two (whole-repo scan) instead of asking convention questions like on a new project, then writes `AgentsMD`/`CLAUDE.md` maps, installs agent skills, recommends MCP servers, and drops nested `AgentsMD` files only where an area genuinely has its own conventions. The lesson's punchline: the generated map is evidence, not truth — you must read it against the actual project, run at least one command, and check for missed conventions before writing any code.
- **Demo: Your First Change in Legacy Code** — Makes a real, smallest-safe change to the BookWise repo using the same familiar skills (`scope`, `architect`, `develop`) that behaved differently on a new project. Scope reads the audit map and plans the "return a book" slice (existing vs planned vs deferred); architect reads how the feature currently works, follows the request through existing files, checks what depends on it, then decides where the change fits; develop reads the surrounding files, matches the existing patterns, and changes only what the spec required. The change was migration-free and touched only four files. Lesson: the skills began with the existing map, code, dependencies and behaviour instead of imagination — the difference between helping inside a mature system and letting an agent guess its way.

## Sections (L2)
### nobody-starts-from-scratch
- Locator: `[[sources/agentic-engineer/20261014/12. Workflow Code You Didn't Write/1. Nobody Starts from Scratch (9_11_2026 1：52：40 PM).html#nobody-starts-from-scratch]]`
- Summary: Argues that the job in a real company is usually changing code someone else wrote and users depend on, not greenfield building — and that this is where people try AI, get poor results, and wrongly conclude it cannot handle real software. The actual problem is that the agent has no map: it can read what the code says but not why it does it, so it guesses, sometimes in clean-looking ways that break a rule the project has depended on for years.
- Key claims: most professional engineering is changing an existing system without breaking what already works, usually joining a project years old with authors gone and real users dependent on it; generating a clean project is easy but understanding a large codebase with unwritten conventions, hidden assumptions and years of history is much harder; when context is missing the agent guesses — it may look clean and confident while breaking a long-standing rule; the stakes are higher in a company (bad change can affect customers, revenue, private data, production systems, versus costing you an afternoon on your own project); there are two risks to control — what the agent puts into the project (insecure code, an exposed secret, a weakened access rule, an unapproved important decision) and what you give the agent (source code, credentials, customer data, private business logic leaving the organisation depending on tool/settings); AI on a real codebase is therefore a business and security decision, not only a coding decision.
- Learner-relevant: This is the module's thesis and the mental model for the two demos. Frames the workflow as "the agent guesses because it has no map, so `/audit` creates one" — recording architecture, conventions, commands, boundaries, and rules the agent cannot safely invent, then handing the agent the map plus only the small part it needs for the current task. Names the skills as a control system: `/audit` (build the map), `/architect` (read existing implementation before deciding), `/develop` (read before write, follow existing patterns), `/check verify` (prove the change works inside the real application without breaking existing behaviour), `/check review` (a second model catches what the author missed). The working order: understand first, then touch. Notes the workflow cannot decide which company information the model may see — that depends on provider, account settings, company policies, security requirements; the workflow controls how the agent works, your settings control what leaves the org. Article description: "why AI agents guess on legacy code, how to manage security risks, and how to use codebase maps." Published 2026-05-21, modified 2026-08-10 on jsmastery.com.

### demo-running-audit-on-a-real-open-source-project
- Locator: `[[sources/agentic-engineer/20261014/12. Workflow Code You Didn't Write/2. Demo Running audit on a Real Open-Source Project.srt#demo-running-audit-on-a-real-open-source-project]]`
- Summary: A screen-share demo of running the `audit` skill on a real open-source project the author didn't write. Watches the skill detect that the repo is already established and route into a whole-repo scan, write the `AgentsMD`/`CLAUDE.md` maps, install agent skills, discover/recommend MCP servers, and create nested agent-map files only where needed — then stresses the human validation step.
- Key claims: the demo repo is called **BookWise**, a university library application with 140 file changes during development and real source code more than two years old — so at that time an `agents.md` file "wasn't a thing" and the project was written fully by hand; the app lets you sign up with a random university ID number, a password, and a university ID-card image upload, browse books/summaries, and only borrow after admin approval (there is a real admin side); `audit` inspects code, history, and existing project files, and because the repo is established (**62+ source files**, database migrations, auth) it routes to **phase two, the whole-repo scan**, unlike on a new project where it asks about preferred conventions; it reads important files until it has enough to write `AgentsMD`, then before writing docs it checks for agent skills / MCP consent decisions and peeks at components, forms and a few more files; asked "Do you want me to build agent skills and MCP servers?" it spawns a **sub-agent** to discover them while it writes the map in the background — so the main conversation keeps only the useful result instead of every file opened; it records what a senior engineer would explain on day one: the stack, the daily-work commands, the patterns the code follows, and surprising details a newcomer would miss; it identifies the stack as **Next.js**, **Drizzle ORM**, **PostgreSQL/Neon**, **Tailwind** for styling, **Zod** for validation, and **Auth.js/NextAuth v5**, plus **Upstash**; it installs the relevant agent skills (Neon, Drizzle, Auth.js/NextAuth v5, Upstash) and recommends MCP servers (**Neon**, **Upstash**, **ImageKit**); it flags an Auth.js skill package as looking like plain documentation but "GenScanner flagged it as critical risk, while this one called it low risk" and leaves the judgment to the author, who removes it.
- Learner-relevant: Concrete artifact names and behaviours to expect. Produces a **root `AgentsMD` and `CLAUDE.md` pointer**, a **database `AgentsMD`** (Drizzle ORM schema, Neon Postgres connection, Redis client, dev/seed script; `schema.ts` is the single source of truth for the data model — users, books, borrow records with Postgres enums for role, status, borrow status; `drizzle.ts` and `redis.ts` set up the runtime client; `seed` is a standalone dev script, not part of app runtime; it names key files, what they own, commands, conventions), and an **app `AgentsMD`** (layouts: auth layout for sign-in/sign-up, root layout, admin layout, another page, plus documented conventions). Key rule: audit only creates a nested `AgentsMD` when an area genuinely needs it — different conventions, its own commands, external integration, or important local risks — and it created one only for `database` and `app`, not every folder. The map matters because **every new prompt starts by reading the root file first**, which now knows language/runtime, framework with version, key dependencies, package manager, build approach, test commands, where specs are stored, and all codebase rules. It noted the scope doesn't exist yet, so it suggests running `scope` next for a tracked roadmap or going straight to `develop`. Your job after audit: read the generated map against the actual project, verify the stack is correct, run at least one command to check it really works, and check whether it missed a visible convention or gave a reason the code doesn't support. The same skill adapts to monorepos (short root file plus agent files per workspace) under one rule: read what exists, add only what's missing, protect what people already wrote — "that restraint is what allows a team to trust the map."

### demo-your-first-change-in-legacy-code
- Locator: `[[sources/agentic-engineer/20261014/12. Workflow Code You Didn't Write/3. Demo Your First Change in Legacy Code.srt#demo-your-first-change-in-legacy-code]]`
- Summary: The follow-up demo that makes the first real change inside the now-mapped BookWise repo without breaking existing behaviour, using the familiar skills `scope`, `architect`, `develop` in the same order but with behaviour changed because the project is no longer empty. Every skill begins by reading what is real before suggesting what should change.
- Key claims: the chosen slice is the **book return and renewal flow** — students can return borrowed books and renew due dates, and admins see the updated status (return-only for now, deferring overdue and other constraints); `scope` reads the `AgentsMD` produced by `audit` to get project structure, commands, conventions and warnings, then identifies which parts of the repo are involved, the order of work, and how much verification the change deserves; it kicks off a scan of the existing codebase to inventory built-in features and writes the plan to `docs/scope.md`, marking existing features (some in progress) and adding the one new planned feature (return a book, numbered "1" while others start with letters); `architect` works differently than on a new project — before proposing anything it reads how the feature currently works, follows the request through existing files, finds the data it uses, checks which other parts depend on it, and only then decides how the change should fit; the codebase already has most pieces the return flow needs to hook into (the schema's return status, admin borrow records, the reminder workflow's book-return check), so the design is "enhancement on your existing stack, not a new feature" — building on the existing borrow-a-book feature; architect surfaces an important risk: had they skipped audit/scope/architect, other agents would create everything from scratch, most likely with mismatching libraries; the spec (`specs/1. return a book`) explains where the change belongs, which existing behaviour must remain unchanged, which files are expected to move, and how you'll prove the result — and architect does not remove behaviour just because it cannot immediately see why it exists ("don't touch the sketchy code that you're not sure what it does").
- Learner-relevant: Concrete workflow mechanics and file/skill names. Skills and order: `scope → architect → develop`, with `check verify` and `check review` offered at the end, and a `clear` between sessions (run `scope`, `clear`, then `architect`, then `clear` then `develop`) — a small correction or single feature may skip `scope` and go straight to `develop`; if `develop` discovers a missing important decision it checks and sends the work back to `architect`. Artifacts: `docs/scope.md` (feature inventory + plan) and `specs/1. return a book` (spec with full build plan, consequences, follow-ups; can optionally be cross-checked with another model, as in the review lesson). The change-application principle: update one existing function if that suffices, or add a new implementation beside the old one and migrate callers gradually, removing the old path only after nothing depends on it; if stored data is affected the spec explains how existing records keep working and whether migration is required (here architect determined atomic was impossible and it was done in two goes). `develop` reads the files around the change and follows existing patterns — how similar features are structured, how errors are returned, how data is accessed, how tests are written — and reuses existing utilities instead of duplicating, follows local naming/file structure, and keeps the change inside the spec's boundary; deeper scans can run in a read-only helper so the main session only receives findings, not every inspected file; before replacing old code it searches for every reference to prevent old and new paths coexisting with divergent results; it keeps unrelated cleanup out. Result: the return-a-book feature (admin action, admin dropdown wired, migration-free) touched only **four files** — a new server-side admin action with admin check, an `on item select` callback replacing the old dummy `console.log`, and a new client row component that calls `return book` and renders the borrow-record row per record. It checked types (all good), found **pre-existing** lint issues (not from the change) and fixed them anyway, and updated the spec and scope. Closing model of the whole pattern: understand what exists, find the smallest safe place to change it, match the project around it, and prove both what changed and what stayed the same — using the amount of process the change deserves.
