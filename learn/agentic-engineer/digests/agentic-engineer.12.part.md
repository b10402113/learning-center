# Digest — agentic-engineer (part 12) — Workflow: Prove it Runs

## Overview (L1)
- Walkthrough — Prove it Runs — Reorients the learner on where the demo project stands after running the architect/develop loop four more times (data model, design system, live preview, comment pinning). Runs the app on localhost:3000, walks the client-facing review flow (project, URL, iframe preview, comment pin, dashboard), and surfaces the real X-Frame-Options / CSP constraint that blocks embedding sites you don't own. Ends by pointing at the check/test skills as the next step to make the codebase less error-prone and more scalable.
- Two Kinds of Proof — Introduces proof as an upgrade over "prototype, done." Distinguishes the two questions proof answers: does the feature work today (check verify) versus will it keep working later (test skill). Frames check verify as alpha tier and test as beta tier, argues they do not replace each other, and states the ordering rule: verify first, then test.
- Demo Running check verify — Demonstrates running `check verify <feature>` on a feature from the scope checklist. Shows the skill loading the verify.md contract from the spec, working through acceptance criteria with four possible result states, and finding real bugs against a live Supabase database. Confirms check verify passes a feature only when every criterion is met and every required surface exists, and recommends the debug skill to fix failures.
- Demo Running test — Demonstrates running `test` (and `test <spec/feature>`) to convert one-time verification into lasting regression protection. Shows the skill scanning the codebase, discovering the current test suite, writing new unit tests for untested data-model logic, running `npm test` to green, and creating a test preferences file so future runs skip straight to writing.

### two-kinds-of-proof
- Locator: `[[sources/agentic-engineer/20261014/9. Workflow Prove it Runs/2. Two Kinds of Proof.srt#two-kinds-of-proof]]`
- Summary: A conceptual lesson that raises the bar from "prototype, done" to proof. It splits proof into two kinds answering two different questions — does the feature work today, and will it keep working later — and maps each to a skill and a tier.
- Key claims: check verify answers "does the feature work today" by opening the app and testing the feature against its acceptance criteria, checking promised behavior in the running product rather than merely whether the code builds or a test file passes — this is the alpha tier; the test skill answers "will it keep working later" because code keeps changing and a future change can quietly break something that worked before, the way any engineering team protects real software — this is beta tier; the two steps do not replace each other (a green test suite proves neither that the real feature works, since tests can be incomplete, test the wrong thing, or miss a real user's path, nor that it won't break next month), so order matters: verify first (prove in real time), then test (protect as code changes).
- Learner-relevant: Gives the mental model for the module's two skills and the tier vocabulary. Both skills work from the acceptance criteria the architect wrote: develop builds them, check verify proves them in the running app, and test turns the important ones into lasting protection. Tier definitions: prototype = built and self-checked; alpha = built and proven; beta = built, proven, and protected.

### demo-running-check-verify
- Locator: `[[sources/agentic-engineer/20261014/9. Workflow Prove it Runs/3. Demo Running check verify.srt#demo-running-check-verify]]`
- Summary: A hands-on demo of the check verify skill. Opening the scope shows features in progress (design system and UI, core review loop) whose verify boxes are still unchecked. The instructor copies a `check verify data model` command into a Claude Code window and observes the skill load the verify contract, work the acceptance criteria, and flag real failures.
- Key claims: run bare `check` and the skill stops to ask "verify, review, or both" and which part of the app; run `check verify <feature>` (e.g. `check verify data model`, `check verify core review loop`) and it first loads the contract — the spec's acceptance criteria from the `verify.md` checklist that the develop skill saved, where every step is already tied to the criterion it proves; the spec lives at `specs/0003-data-model/` (index, rationale, verify) and `verify.md` was created by develop; each acceptance criterion can get one of four results — met, specced but missing, specced but not applied, blocked; check verify passes a feature from the scope only when every criterion is met and every required surface exists (one unapplied migration fails it even with a fully green test suite).
- Learner-relevant: Demonstrates the skill's real mechanics and output. On the data model run it reported: one spec check did not run as documented, and one of seven smoke test assertions failed — real evidence against a real Supabase database — and it recommended the `debug data model` skill to fix the two issues, then rerun. Work it did: used a bash command to learn the spec, learned which acceptance criteria apply, checked env vars are present, wrote and executed a smoke test, confirmed vars loaded, ran the data-model smoke test from lines 220 to 300, and confirmed `ac10`. Data model criteria included the pin insert assertion and the two check constraints in the smoke test and constraint query, plus one image attachment per comment stored by reference. Prerequisites (data model), `debug` skill (a later module). On the `check verify core review loop` run it used Supabase's MCP to talk to the DB directly, ran lint, built, confirmed sign out / sign in / sign up pages, used grep and bash, ran curl requests modifying cookies (`check verify.ts`, example email), and executed Supabase SQL queries; result: 9 of 15 behaviors met with cited evidence, 1 confirmed bug, 3 blocked (no browser tool), 1 not ran (needs a Vercel deploy). The confirmed bug traced to the earlier localhost/http change (accepting `http://localhost:3000` instead of only `https` as originally scoped) — an easy fix. Notes: if you chose `prototype` there is no scope box to tick, but you can still verify a feature manually; verification is only as strong as the tools available — without browser, database, or MCP access more results come back blocked and captured proof isn't kept as permanent history, so more access yields better tests.

### demo-running-test
- Locator: `[[sources/agentic-engineer/20261014/9. Workflow Prove it Runs/4. Demo Running test.srt#demo-running-test]]`
- Summary: A hands-on demo of the test skill. Because check verify's proof only describes the work today, and the next feature built could break the same code silently, the test skill turns that one-time proof into durable protection. The instructor runs `test` with no argument, then narrows to a specific spec.
- Key claims: run `test` with no argument and the skill scans all files to gauge the extensiveness of the current testing suite and whether it exists; with 40 files it asks how to focus (logic and API first, test everything in batches, or narrow by files); running `test data model` targets a feature and it identifies the data logic to test (`assign next pin number`, `compute unread pins`, and so on), then asks whether to run the suite after writing; choosing "yes, run it and fix it to green" executes `npm test`, fixes test mistakes, and flags real bugs the tests catch; it did not ask which test types to run — comment logic gets unit tests, endpoints get integration tests, and the thread component gets rendered and driven the way a person would use it.
- Learner-relevant: Concretely shows the skill's file outputs and workflow. It created three new unit tests targeting untested data-model parts: odds invariant, client identity signing, and shared token creation/resolution; the existing smoke test already covers pins, regenerate, revoke, and delete against the database. Result reported as `15 passed, 0 failed`. It also created a test preferences file explaining which tools are used to test, so future test runs skip straight to writing. On marking the feature finished, the verify box was still unchecked (verify was run earlier; debug still needs to finalize it), but testing was done. The test skill is flexible: run bare to test everything, with a specific spec, or on a specific feature (a smaller part of a spec) — "anything test related, use the test skill, and tell it what you want to do."
