# L1 overview

- **The Three Kinds of Broken** — The first move when something breaks is not a technique but a question: what kind of broken is this? There are three — a normal code bug, a defect specific to AI-written code, and the agent itself losing the task while staying confident — and they look alike but need opposite responses. Use it before you touch anything, because each misclassification costs differently: prompting a bug the agent cannot see, clearing a session that had already gathered evidence, or editing code when the real fault is a task lost ten turns ago. The rule underneath all three: a fix you cannot explain is a bug you have not caught.
- **The Method That Works on Any Code** — For the first kind there is exactly one method, and it is the scientific method: observe the failure, form one specific explanation, test it, and let the evidence choose the next move. Debugging is not changing things until the error disappears — that is why the bugs come back. Change one thing at a time so every result teaches you something. Even though `/debug` runs the six steps faster than you can, the judgment of whether it proved the cause or merely silenced the symptom stays yours, and you cannot make that call without knowing the method.
- **Demo: Running /debug** — How to drive the skill well, shown live. The part that matters is the input: what you observed, what you expected, and the exact steps to reproduce. "This is broken" forces the agent to stop and interrogate you, and that is the whole difference between a fast and a slow investigation. If it cannot reproduce, it stops and adds instrumentation until it can. When reviewing, watch for one hypothesis at a time — several unrelated edits hoping the failure vanishes is the thing to stop. The payoff is fix size: a one-line change reads `dotenv` explicitly instead of a file literally named `.env`, and that smallness is the proof it found the root cause rather than vibe-debugging until red turned green.
- **Debugging Code You Didn't Write** — With your own code, memory of why you wrote each line does half the investigation; with agent-written code that memory does not exist, and watching it being generated is not a substitute because you saw output, not reasoning. So read it like a stranger wrote it — one did — and never debug against your guess about intent, or you end up investigating your theory instead of the code. Recover intent from three places: the spec's acceptance criteria (the gap between promised and actual is the bug), the surrounding code's conventions, and the running behaviour. Four named failure patterns: invented function (loud and easy), plausible but wrong logic (hardest — right shape, wrong reasoning, passes review), a decision made mid-file by a generator and never reviewed, and the unconsidered edge case. When there is no spec, you have found something bigger than a bug: an undecided decision, which is `/architect`, not `/debug`.
- **Recover a Broken Session** — Recognise the third kind by its signal: repetition without progress, the same function rewritten five times, the same files reopened, a messier diff, contradicting its own earlier decisions. A hallucination gives wrong content; a loop gives a broken process, and more instructions make it worse because the thing you are instructing is part of the failure. One judgement decides everything after it: is this session's context an asset (productive, low on room → compact) or a liability (failed attempts and repeated assumptions → clear)? Then escalate in order: stop with Esc (not Ctrl+C), ask what it believes and what it is assuming that might be wrong, give it less instead of more with a hard boundary, roll the code back with git rather than asking the confused agent to clean up, and finally clear while carrying the exact error, the failing test and the missing fact into the fresh session. Prevention: plan before editing, so a bad approach is rejected while it is still a few lines of text.

# L2 detail

- `#L1-L142` — `1. The Three Kinds of Broken.srt` — Real projects stop going to plan, and the most useful first move is a question rather than a debugging technique: what kind of broken is this? The three look like versions of the same problem and each needs a completely different response. Kind one is a normal code bug — a calculation returns the wrong result, a request crashes, a total is off by one — a real fault producing observable, reproducible behaviour that behaves the same whether you, a colleague, or an agent wrote the code; you find it the way engineers always have. Kind two is specific to AI-written code: it calls a library function that does not exist, writes convincing logic that is quietly wrong, makes a real decision mid-file without telling you, or misses an access rule, an edge case, or a failure that only appears with real data. The happy path looks finished and the first unusual input exposes everything never considered; what makes it different to investigate is that you cannot reason from the author's intent, because you were not the author — even if you watched it being written, you do not actually know why each line is there. Kind three is not the code at all: the agent has lost the path, repeats the same action, changes the same files back and forth, and every attempt makes the project slightly worse while it stays completely confident and moves further from the cause. Telling it to fix the problem will not help, because the thing you are asking to solve the failure is now part of the failure.
- `#L143-L276` — `1. The Three Kinds of Broken.srt` — Why spend time classifying at all: each wrong answer costs you differently. You can keep prompting an agent to fix a bug it genuinely cannot see when you should have stopped and reproduced it yourself; you can clear a confused session too early and throw away the evidence it had already gathered; or you can spend an hour changing code when the real problem is that the agent lost track of the task ten turns ago. One rule sits under all three — a fix you cannot explain is a bug you have not caught. If the error disappears and you cannot say why it happens, you have not proved the cause is gone; you may have hidden the symptom, moved it somewhere else, or changed the code so it is temporarily harder to reach. Hence evidence over intuition: a bug is a case you prove, not a message you silence. When something breaks, do not start by fixing it; start by deciding which of the three you are facing. The next lesson covers the method for the first kind, which works on any codebase no matter who wrote what.
- `#L1-L104` — `2. - `#L1-L180` — `3. Demo Running debug.srt` — The skill runs the six steps with discipline, so the lesson is how to use it well rather than re-explaining the method. Run `/debug` bare and it asks for the bug details; the most important part is what you give it at the start — the three things: what you observed, what you expected instead, and the steps needed to reproduce it. Give those and it starts investigating; tell it only "this is broken" and it has to stop and ask you for evidence, and that is often the entire difference between a fast and a slow investigation. If it cannot reproduce, it stops and adds instrumentation until it can, then tells you what it came up with. Demo: a prior `check verify data model` session had already found real issues, so the debug run inherits those three things from the verification instead of asking again — but on your own, be precise: not "something is wrong with the database" but specific enough that the next experiment can prove it right or wrong. Then you have to actually review it. You will know it is right from the size of the fix: usually tiny, as when the smoke test's `dotenv` config read a file literally named `.env` while the secrets lived in `.env.local`, so all seven tests ran with empty values and no failure signal; the fix is a single line loading `.env` explicitly, and its smallness is the evidence the root cause was found.
- `#L181-L343` — `3. Demo Running debug.srt` — The contrast with a normal fixing prompt: that encourages the agent to keep changing things until red turns green, which sometimes works and leaves you with no explanation of what was wrong — call it vibe debugging, and you know how that ends. `/debug` instead requires a reproduction, one hypothesis, evidence, a minimal fix, and a regression test; its advantage is not fewest moves but that you can explain why the result works, so the review rule is the first lesson's rule — do not accept a fix you cannot explain. - `#L1-L40` — `4. Debugging Code You Didn't Write (9_11_2026 1：51：47 PM).txt` — The six-step method works on any code, but the thing you normally lean on is missing here. Debugging your own code, you are not only reading it, you are remembering why you wrote it, and that memory does half the work without you noticing; on agent-written code it does not exist, and watching it get generated is not a substitute because you saw the output, not the reasoning. So the first move is to stop pretending you know what it was for: read it like a stranger wrote it, because one did. That is a technique, not just advice, because it prevents a specific mistake — looking at a line, deciding what it probably meant, and then debugging against that guess, which means you are investigating your theory about the code instead of the code. Intent comes from three places instead: the spec's acceptance criteria (what this was supposed to do; the gap to reality is the bug), the surrounding code (the conventions this file was supposed to follow), and the running behaviour (what actually happens, versus what the code appears to say). The spec matters most — that is where writing things down pays off least glamorously, turning a vague investigation into a comparison of what was promised against what happens. When there is no spec, which is the honest answer for a lot of AI-written code, you have found something more important than the bug: a behaviour with no recorded decision behind it is not a bug you can fix but a decision that was never made, and you cannot tell whether the code is wrong until somebody decides what right looks like — that is `/architect`, not `/debug`. The four patterns, worth knowing by name: an invented function (calls something that does not exist or existed two versions ago — easy, loud failure); plausible but wrong logic (reads correctly, passes review, wrong with real data — hardest, because the shape is right and the reasoning is not); a decision made mid-file (not strictly a bug: something was chosen by a generator and never reviewed, invisible until it conflicts with something); and the unconsidered edge case (happy path complete, first unusual input goes through a gap, easy once you feed it real data). The tell: the bug is almost never in the line that failed — it is in a decision made earlier that nobody wrote down. So the investigation carries one extra question you would never ask about your own code: was this ever decided? Same six steps, same discipline, one difference — you recover intent from the spec, the surrounding code and the running behaviour instead of from memory, and when there is no intent to recover you have found the third kind of broken: not the code, the agent.
- `#L1-L37` — `5. Recover a Broken Session (9_11_2026 1：52：08 PM).txt` — First, recognise it: the signal is repetition without progress — the same function rewritten five times, barely different each attempt, the same files reopened, the diff getting messier, contradicting its own earlier decisions. A hallucination gives you wrong content; a loop gives you a broken process, and adding instructions makes a loop worse because the thing you are instructing is part of the failure. Then make one judgement on which everything else depends: is the context this session built worth keeping? Productive but running low on room means the context is an asset — compact it. Full of failed attempts and repeated assumptions means it is a liability — clear it. Getting this backwards is expensive both ways: clear a productive session and you throw away evidence it had already gathered; compact a poisoned one and you carry the failed reasoning forward in compressed form, which is worse because now it is harder to see. The escalation, in order: (1) stop it with Esc, which halts the response — not Ctrl+C, which exits the session — costs nothing, so never skip it; (2) before changing anything, ask what it believes: "What do you think the problem is, and what are you assuming that might be wrong?" A stuck agent is usually circling one false assumption, and making it state that assumption often breaks the loop outright, or at least tells you what the next attempt has to correct; (3) give it less, not more — most loops start because the task was too broad, so shrink "refactor the authentication module" to "extract the token refresh function from this file and touch nothing else" and put a hard boundary around what it may change; (4) roll the code back, because if the failed attempts already damaged things you should not ask the confused agent to clean up its own mess — note that checkpoints may not restore files changed through shell commands, so git is the universal fallback: `git restore` for working tree changes, `git reset` when the repository itself has to move; (5) clear and bring the evidence forward — never repeat the original prompt, which recreates the loop, but open the fresh session with the exact error, the failing test and the one fact the old session kept missing, because a clean session that opens with strong evidence solves in two turns what a poisoned one could not solve in ten, and clearing costs you the conversation, not the work — the scope, the specs and `AGENTS.md` are still on disk.
- `#L38-L76` — `5.
