# L1 overview

- **Reading a Spec: What the Build Sees and What You Keep** — a spec is a plain Markdown file under `docs/specs/` with two shapes: single file by default, directory (`index.md` + `rationale.md`) only for foundational or bulky decisions. The split exists because there are two readers: the build needs the decision, you need the argument. Feature specs go Proposed → In Progress → Accepted (shipped); standalone decisions go Proposed → Accepted on ratification; shipped-late documentation is born Accepted; `Assumed` specs block done until `/architect` clears them; reversed decisions are superseded, never edited.
- **Demo: Running architect** — one decision per run, the stack. In a fresh session `/architect` reads the skill, the repo file list, the scope, AGENTS.md and existing specs, checks git state, then asks permission to research the current landscape with read-only sub-agents. Six rounds of questions (app shape, framework, data platform, preview strategy, auth, ORM, hosting, API shape, client identity, share link, uploads, styling, validation, testing, rate limiting, package manager, local DB, migrations, code organization, email, CI, monitoring) end with the skill proposing Agent Skills and MCP servers, then writing `docs/specs/0001-stack/index.md` and `rationale.md`, optionally cross-checked by a second model.
- **Challenge: Scope Your Own Real Idea** — no answer key by design: run your own idea through `/scope`, then its first load-bearing decision through `/architect`. Because the agent is not neutral, watch three training-induced tendencies: it wants to agree with your premise (`/architect`'s premise challenge is the counter), it reaches for the median-project answer (demand the reasoning behind each recommendation and test it against your constraints), and it wants to look finished (a short tidy interview means gaps were silently filled). Deliverables: a living plan plus a first Accepted decision.
- **Demo: Planning a Feature with develop** — greenfield `/develop` scaffolds the real project from the Accepted spec using the framework's own initializer, installing only what the first slice needs, then proving it runs. Then the lesson's real point: you may point `/develop` at work not in the plan (a home page with a reference mock-up); the build gate asks how to handle the missing spec, writes a minimal `Assumed` spec naming the git author, derives a `design.md` design system rather than copying one screenshot, and `/scope` with no arguments later reconciles the plan with what shipped.
- **Demo: Running audit** — without a repository instruction file every skill must re-study the project or guess. `/audit` detects greenfield vs gap-fill, scans real code, and writes a deliberately short root `AGENTS.md` (stack, commands, build approach from scope, conventions, skill list) with `CLAUDE.md` pointing at it; nested per-area files appear only when an area earns lasting conventions. It absorbs decisions from the accepted spec and living scope rather than reopening them, reports conflicts by naming both files, and is safe to rerun.
- **sync: Understand It, Then Automate It** — code and guiding files drift until the repo and its description are two different projects. `/sync` runs at the end of work, before merge: it initializes the baseline if needed, then reads `git diff`/`git log` (added vs deleted vs changed), discards docs, tests, configs and generated output as product evidence, and updates scope and spec statuses to match what actually shipped. Lightweight enough to run every time; it closes the plan → decision → code → memory loop.
- **Install Supabase MCP** — a short practical interruption during the data-model build: `/develop` pauses and asks whether to wire env vars to Supabase or connect the MCP, and waits. The walkthrough creates the Supabase project (with a GitHub repo for traceability, saving the DB password), copies the project-scoped, client-specific MCP command from Supabase's hosted MCP docs, adds it as an HTTP MCP server, authenticates through `/mcp`, and reruns `/develop data model` so migrations and checks happen against the real schema. Connecting an MCP is a deliberate privilege grant done in your own settings.
