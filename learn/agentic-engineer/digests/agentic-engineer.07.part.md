# Digest — agentic-engineer (part 7) — Vibe Coding vs Agentic Engineering

## Overview (L1)
- **The Experiment: One App, Two Builds** — Sets up a controlled experiment: one movie recommendation platform built twice, same day, same developer, same AI models. Build one is pure vibe coding (one prompt, no plan on disk, no decisions written down, no tests, given the most powerful model); build two is the agentic-engineering workflow (scope first, every load-bearing decision captured before code, agent gated from inventing things, tests and migration). The vibe build works and would impress in a demo; the question is what happens after the demo — at 100 users, at 5,000, or six weeks later when you reopen the code. Both repos are attached so the learner can verify every claim.
- **The Vibe Build: A Working App in One Session** — Compresses the single vibe-coding session into minutes: one prompt produces a Next.js app with Supabase auth, swipe onboarding, a feed, and an import endpoint (~2,000 lines). Recommendations come from asking the smartest model to generate 18 movie suggestions with reasons, validated against TMDB so nothing hallucinated slips through. It genuinely works and looks great, but the demo hides economics — concurrent load, page-load cost, and an agent decision made silently in the middle of the engine file that becomes a costly monthly bill at scale.
- **Watch It Break** — Opens the feed in the working vibe app and exposes the invisible behavior: every page load calls Opus live in the request path to regenerate recommendations from scratch, then fires parallel TMDB validation calls — 40 seconds per feed, every refresh, never cached. The feed is a slot machine: three tabs of the same account at the same instant return three different answers, and the same movie gets different reasoning. Nothing here was decided; all of it was defaults the AI chose instead of the developer.
- **Autopsy: Reading the Vibe Codebase** — Reads the vibe repo like a senior reviewer and locates four "killers": the expensive Opus call with 16,000 max tokens inside the engine file, fired uncached on every feed mount (~35 cents a page view); a `Promise.all` TMDB validation with no rate limit/backoff/retries whose catch silently drops candidates, plus an API key passed as a query-string parameter; an import that deletes-then-inserts with no transaction (partial failure = data loss, no rollback); and the absence of any tests or migrations (85 lines of raw SQL). The lesson: line by line the code is clean — the failures are architectural, and vibe coding produces undecided architecture.
- **Workflow-First: Decide Before You Build** — Walks the agentic-engineering flow on the same prompt: `scope` interviews you (MVP boundary, who it's for, what's out) and writes an ordered plan with foundations first (stack, data model, design system); `architect` asks one question at a time with real options and a recommended pick, and each answer becomes an acceptance criterion in a written spec that lands in the repo (e.g. the 35-cent caching decision). Then `develop` builds what was specced, `check`/`verify` proves features with real requests (and Playwright MCP browser testing), `review` cross-verifies the spec with a second agent, `test` writes the suite, and `sync` records what shipped.
- **Autopsy: The Workflow Codebase** — The side-by-side payoff. The feed is a taste vector retrieved by a vector index in one database call and written to a recommendations table, so the read path costs effectively nothing; AI is limited to one batched Sonnet call writing one "why this fits you" line per pick, only when taste changed, never on page load (the caching decision named as `feed stale`, with the rejected live-generation option recorded in `007.md`). Import retries per chunk with backoff, upserts by movie ID so no data window exists, and dedupes aliases so a retry can't wedge the import — because "an import can never lose data" was an acceptance criterion before any code. Vibe search is a five-line pipeline where a small model parses intent, embeddings pull real candidates, and a mid model only picks from the provided list. Tests named by acceptance-criteria numbers (AC7) and six version migrations exist. The codebase is larger, but every extra line is load bearing and traces to a decision.
- **The Two Bills** — The receipt. Bill one (running it): the vibe feed costs ~35 cents every open plus ~30 cents per vibe search, versus effectively nothing for a cached table read and ~1.5 cents per search in the workflow build — roughly a 60x gap, about $5/user/month versus under a dime, scaling to $5M vs ~$70K/month at a million users. The vibe build is not just expensive, it is architecturally unfundable: costs scale with page views while revenue cannot. Bill two (building it): the workflow build actually used more tokens than the vibe build, but most of that extra was waste — long uncleared sessions re-reading stale history at premium prices, and premium models doing grunt work — not the price of scoping/specs. Three fixes (session hygiene as the workflow's job, model routing, subagent-drafted documents) cut the waste by an order of magnitude. Warning: early repos use old names (ADR → now "spec").

### watch-it-break
- Locator: `[[sources/agentic-engineer/20261014/7. Vibe Coding vs Agentic Engineering/3. Watch It Break.srt#watch-it-break]]`
- Summary: Demonstrates the vibe app's production behavior by doing the single most basic user action — opening the feed — and finding it takes 40 seconds and is unstable. Exposes three invisible costs: latency, token spend, and an opinion about the user that changes every request.
- Key claims: every single time anyone opens the feed, the vibe app calls Opus — the most expensive model available — live in the request path and asks it to generate recommendations from scratch, then fires a batch of parallel requests at the TMDB API to validate them, on every page load; that yields 40 seconds for a feed, and refreshing takes 40 seconds again, regenerating from scratch rather than caching, so the feed is a slot machine; opening the app in three tabs on the same account and refreshing within seconds returns three different answers, with the same movie carrying completely different reasoning — neither exactly wrong, both plausible, because there is no fixed answer being retrieved, only a fresh generation (a fresh guess) each time; every guess makes the AI think for every recommended movie, costing many tokens, and means the app has no stable opinion about you — it has a new one each time you ask.
- Learner-relevant: A test the learner can run without special tools — open the same app in three tabs on the feed and refresh within a few seconds with the same account and taste profile; three answers come back. Ties each behavior back to the next lesson: "none of them were decided. All of these were defaults, the choices that AI made instead of me." Concrete numbers: 40 seconds per feed, Opus (most expensive model), parallel TMDB validation batch.

### autopsy-reading-the-vibe-codebase
- Locator: `[[sources/agentic-engineer/20261014/7. Vibe Coding vs Agentic Engineering/4. Autopsy Reading the Vibe Codebase.srt#autopsy-reading-the-vibe-codebase]]`
- Summary: Reads the vibe codebase like a senior reviewer and locates the four architectural failures ("killers") behind the behaviors seen when the app broke, then draws the module's central claim: vibe coding does not produce bad lines, it produces undecided architecture.
- Key claims: Killer 1 — in `lib/engine.ts` (the matching engine; Claude proposes candidates as title/year/one-line reason, all treated as unverified and passed through `tmdb.ts` before display), line 16 sets the model to Claude Opus (transcribed "Opus 4.8"), and around line 68 "generate feed candidates" runs Opus with 16,000 max tokens and adaptive thinking; the feed page's useEffect (line 34) fetches recommendations on mount with no cache, so the most expensive operation in the app runs on every page view and costs about 35 cents each time. Killer 2 — `tmdb.ts` `validateCandidates` uses a `Promise.all` mapping ~24 candidates with no rate limiter, no backoff, and no retries; its catch block just returns null, so a rejected validation silently vanishes when TMDB pushes back; line 44 fetches the API key as a query-string parameter on the request URL, putting the key in every log and proxy. Killer 3 — the import `route.ts` line 35 comment ("Replace any previous import wholesale. The export is the source of truth.") is followed on line 36 by deleting all of that user's previous ratings, then lines 45–48 loop over 500 items manually with nothing wrapping the deletes and inserts, so if a chunk fails partway the delete already happened and there is no rollback. Killer 4 — what's missing: no test anywhere in the repo and no migrations folder, just Supabase schema (85 lines of raw SQL); CSV parsing and fuzzy title matching are pure functions full of edge cases with not a single test. The lesson: any 10 lines in isolation are fine — clean, readable, meaningfully named — but the failures are architectural (where the expensive call sits, concurrent load, mid-failure, 400 ratings vs 40); those are big decisions, and every one was made implicitly by a code generator optimizing for "it runs in the demo."
- Learner-relevant: Concrete file/line locators to study — `lib/engine.ts` (line 16 model, ~line 68 generate candidates, feed page useEffect line 34), `tmdb.ts` (validateCandidates, catch returns null, line 44 API-key-as-query-param), import `route.ts` (line 35 comment, line 36 delete, lines 45–48 loop over 500 items), Supabase schema (85 lines SQL, no migrations). Cost figure to remember: ~35 cents per page view, flagged to scale terribly with users. Core takeaway: "Vibe coding doesn't produce bad lines. It produces undecided architecture."

### workflow-first-decide-before-you-build
- Locator: `[[sources/agentic-engineer/20261014/7. Vibe Coding vs Agentic Engineering/5. Workflow-First Decide Before You Build.srt#workflow-first-decide-before-you-build]]`
- Summary: The highlights of the agentic-engineering approach on the identical prompt. Each skill gets a full lesson later; here the point is the shape of the flow, where every load-bearing decision is surfaced, made by a person, and written down before code exists.
- Key claims: the flow starts with the `scope` skill, given the same prompt as before ("build me a movie recommendation app…"), but instead of writing code it interviews you — what's the MVP boundary, who is this for, what's explicitly out — and writes that plan to a file, features ordered with foundations first (stack decision, data model, design system) before any feature ("the ground before the house"); next the `architect` skill is pointed at the data system and does not invent choices but asks one question at a time, each with real options and a recommended pick — including the 35-cent caching decision the vibe build made silently in the middle of a huge file, now a question on screen with trade-offs; the chosen answer becomes an acceptance criterion in a written spec that lands in the repo, so the decision exists as a file the future self, the team, and the agent can all read and be held to; then `develop` builds what the architect planned and specced, leading the process but never inventing undecided things (the exact disease of the vibe build); then `check`/`verify` launches the actual app and proves features work against the spec's criteria with real requests, sometimes using Playwright MCP to test directly in the browser; `review` reviews the written spec with a second agent to cross-verify; `test` writes the test suite for what changed; and `sync` records what's shipped so the next session can start.
- Learner-relevant: Named skills and total flow — `scope → architect → develop → check → test → sync` (with `review`). More steps than "please build me an app" with no questions, but the next lesson shows what those steps bought in the code side by side with the vibe build, on the same three features with opposite engineering. Key mental model: decisions become written acceptance criteria, making them auditable by the human and enforceable against the agent. Foreshadows the spec/ADR artifact (see The Two Bills rename note).

### autopsy-the-workflow-codebase
- Locator: `[[sources/agentic-engineer/20261014/7. Vibe Coding vs Agentic Engineering/6. Autopsy The Workflow Codebase.srt#autopsy-the-workflow-codebase]]`
- Summary: The side-by-side payoff: the same app, same three features, engineered instead of vibed. Each of the four vibe failures is now solved by a decision that was made on purpose, and the extra code is shown to be load bearing rather than decoration.
- Key claims: Feature 1 (feed) — `candidates.ts` (~line 46) turns ratings into a taste vector and does the entire retrieval in one database call plus a vector index, finding the movies closest to your taste out of a real catalog and writing the result to a recommendations table; the `get feed` action in `feed-actions` simply reads that table with no model call anywhere, so the page costs effectively zero and is as fast as Supabase returns data. The AI still shows up, but for one small job: `feed-reasons` writes one short "why this fits you" line per pick in a single batched Sonnet call (Sonnet, not Opus or fable), one call for the whole feed, thinking switched off, and only runs when your taste actually changed or you hit refresh — never on page load; `generate.ts` (~line 61) has a `feed stale` function, "the cache refresh is a decision with a name." In `007.md` the scope options show the architect asked whether to cache and how to retrieve and who writes reasons: option 1 (chosen) caches and regenerates only when the profile changes; option 2 (rejected) computes the feed live on every load without cache, paying a multi-second Sonnet call and cost per page load, reshuffling pics and reasons so the feed is never stable, and risking the serverless duration limit on every render — the vibe app's failure, preserved here as a rejected opinion rather than shipped code.

  Feature 2 (import) — the browser parses the CSV and sends 100 rows at a time (visible in the chunk sizes), so a retry resumes the same import instead of starting over; `actions.ts` has a retry helper and every chunk retries on its own first with backoff; nothing existing is ever deleted and matching rows are upserted by movie ID, so unlike the vibe delete-then-insert there is no window where your ratings don't exist; deduping handles two export rows resolving the same movie (a re-release or alias) — if both hit the database in one statement Postgres throws, the chunk fails, and because a retry replays the same exact input the import would be wedged forever; this is senior-level code, present because an acceptance criterion in the architecture states an import can never lose data — written before there was any code to break.

  Feature 3 (vibe search) — a pipeline readable in five lines in `search-actions`: get the profile-based data, figure out what they want, shortlist, log, and return; a small, cheap model parses the query into structured intent (year, runtime, and things like mood, theme, tone, and the feel the viewer is after), then a vector/embedding search pulls the real candidates out of the catalog, then a mid model picks three to five and is only allowed to pick from the list it was handed; `select.ts` tells it not to invent movies but only choose from the real provided movies — which is just asking it (the same thing the vibe build did) — so the code also specifies the movie schema, making it structurally impossible to hallucinate a movie: "the architecture gives it no way to misbehave. That's the difference between a rule and a guarantee."

  Also — vitest is configured with a test file for the taste logic (CSV parsing, taste math); tests are named by acceptance-criteria number (e.g. "compute taste profile below the floor, AC7"), so the tests point back at the decisions; there are six version migrations showing how the data system upgraded with each feature. The codebase is much larger than the vibe one, but none of it is decoration — every extra line is load bearing and traces back to a question a skill asked before the build. "The vibe codebase is made of defaults. And this one is made of decisions."
- Learner-relevant: Concrete files/functions to study — `candidates.ts` (line ~46 retrieval), `feed-actions` `get feed`, `feed-reasons`, `generate.ts` `feed stale` (~line 61), `007.md` (caching options), import flow file (100-row chunks), `actions.ts` (retry helper, backoff), `search-actions` (five-line pipeline), `select.ts` (movie schema / anti-hallucination), vitest config + taste test (`AC7`), six migrations. Cost/speed contrast: feed effectively zero vs the vibe 40 seconds / 35 cents. The rule-vs-guarantee distinction (prompting good behavior vs removing the ability to misbehave) is the transferable engineering idea.

### the-two-bills
- Locator: `[[sources/agentic-engineer/20261014/7. Vibe Coding vs Agentic Engineering/7. The Two Bills (9_11_2026 1：40：21 PM).html#the-two-bills]]`
- Summary: The receipt for the experiment, in two bills. Bill one is what it costs to run each build at scale and why the vibe build is architecturally unfundable; bill two is the honest admission that the workflow build used more tokens, and why most of that extra was waste rather than the price of doing it properly. Also notes the repos are early builds where some names (notably ADR → spec) have since changed.
- Key claims: Bill one (running it) — in the vibe build opening the feed costs about 35 cents in AI spend every time (not just the first time), because the model call sits in the request path with nothing cached in front of it, and a vibe search costs about 30 cents on top; in the workflow build opening the feed costs effectively nothing (a cached table read) and a vibe search costs about a cent and a half, because the expensive part is a database query and the model only picks from what the database already found; an active user doing a couple of feed opens and a search or two a week is about five dollars per user per month in the vibe build versus under a dime in the workflow build — roughly sixty times apart before anyone does anything clever. The scale table: 100 users ≈ $500/month (vibe) vs ~$30/month (workflow); 5,000 ≈ $25,000 vs ~$400; 50,000 ≈ $250,000 vs ~$4,000; 1,000,000 ≈ $5,000,000 vs ~$70,000. The workflow column's $30 at 100 users is mostly fixed infrastructure (database and hosting), "the floor you'd pay for any app," whereas the vibe column has no floor and no ceiling — it is just a multiple of how many pages got looked at. The key sentence: the vibe build costs about five dollars per user per month to run, and no consumer movie app on this planet earns five dollars per user per month — so the build is not merely expensive (fixable) but architecturally unfundable: costs scale with page views while revenue never can, every new user deepens the hole, and the decision was made silently by a code generator optimizing for "runs in the demo."

  Bill two (building it) — honestly, the workflow build used more tokens than the vibe build, meaningfully more, because scoping, interviewing, writing specs, and verifying against them are real work; but on actual cost, both apps were built in one day on a single Claude Max subscription, with the only real cost being hitting the five-hour limit a couple of times and waiting for the reset — no surprise invoice and no per-token bill ("AI coding costs a fortune" was not his experience here). The real lesson: most of those extra tokens were not thinking but waste, and it was not the interviews or specs — it was context: long sessions that never got cleared, re-reading their own stale conversation history over and over at premium model prices to decide something that needed three files, and premium models doing grunt work a mid-tier model handles fine; that is the price of doing it properly without session hygiene, which Module 4 warned about and he walked into anyway. After this receipt, three changes matter for the token bill: session hygiene is now the workflow's job (the skills tell you when a conversation has run too long and to clear it — scoping runs in its own session, architecting in a fresh one, developing in a fresh one after that — which works because state lives in files on disk, not chat history); model routing (big models for decisions, mid-tier for execution); and subagents drafting the long documents so the main session never pays to carry them. Result: a large drop in tokens for the same output — not a trim, an order-of-magnitude drop in the wasteful parts with all the benefit intact. Warning: these are early builds for the workflow, so some names differ from what you'll install — most notably what the repos call an ADR (architecture decision record) is now called a spec (same artifact, same job, clearer name), and a few other renames exist; if a folder name doesn't match a skill name, the current name is correct.
- Learner-relevant: Concrete costs and the scale table (35¢/feed and 30¢/search vibe; ~nothing/feed and ~1.5¢/search workflow; ~$5 vs under a dime per user/month; 100 → $500 vs $30; 5,000 → $25k vs $400; 50,000 → $250k vs $4k; 1M → $5M vs $70k). Concrete build economics: both apps in one day on a single Claude Max subscription, cost only a couple of five-hour-limit resets. The three token-saving changes (session hygiene as the workflow's job with state on disk; model routing — big for decisions, mid-tier for execution; subagents drafting long docs) are the practical carry-forward. Repo caveat for verification: the downloaded repos are early builds, and "ADR" in them is now "spec." Takeaway: the workflow does two things — it makes the app cheap to run because expensive decisions are made on purpose by a person, and (less obviously) it polices its own build cost, a lesson encoded into the tools after this build taught where the tokens actually go. "You get the lesson. You skip the receipt."
