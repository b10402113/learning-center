# Digest — agentic-engineer (part 9) — Workflow: Ship Something Real (scope demo + reading a spec)

## Overview (L1)
- Demo Running scope — a full greenfield run of the `scope` skill: a single sentence ("build a client feedback app, where I share a link, the client pins comments to a live preview, and I manage them from a dashboard") is turned into an ordered, 10-feature project plan (14 deferred) through batched Q&A that decides MVP scope, pin target, access, rigor tier, and build approach (tracer bullet). Shows the resulting `docs/scope/scope.md` file and how scope adapts to brownfield, monorepo, mid-build, and argument-less re-runs.
- Reading a Spec: What the Build Sees and What You Keep — how to read a spec markdown file in `docs/specs/`: the single-file vs directory shape rule, the audience split between `index.md` (decision, read by `/develop`) and `rationale.md` (argument, skipped by `/develop`), what each `Status` value means across two lifecycles, `Assumed` specs and how to clear them, and why decisions get superseded rather than edited.

## Sections (L2)
### demo-running-scope
- Locator: `[[sources/agentic-engineer/20261014/8. Workflow Ship Something Real/5. Demo Running scope.srt#demo-running-scope]]`
- Summary: Scope sets up two project decisions — the build approach (how work gets sliced) and the workflow tier (how much verification each feature needs). This lesson demos both on a new folder ("agentic engineering") by running the `scope` skill from a CLI (`claude`), VS Code extension, or any agentic system, then walking through every question scope asks and the plan it writes.
- Key claims: A single sentence (or a full brain dump / client brief) is enough input — the more scope has, the better the output; scope reads only the files it needs (it detected a greenfield project, then read the scope template, and only read the approach file `tracer bullet.md` after the approach was chosen); questions arrive in small batches with real choices and a recommended answer, and ask only about what the idea could not tell; the final plan went to `docs/scope/scope.md`.
- Learner-relevant: Concrete run details to reuse — command is `scope` with a free-text idea; MVP options were "one project pin and resolve", "pin, thread, and notify", or "full review round" (open, in progress, fixed, won't fix, with screenshots, browsers, screen size captured, and client approval of round). Pin target = a live site in a frame (paste a URL, app loads the page inside a frame with a comment layer on top; works for any URL with no code added to the client site). Access = secret link without login (client types a name once, link can be revoked); no billing yet. Capability checkboxes: own sign-in, email notifications, live updates, image attachments on comments, dashboard-badge-only notify. Cross-cutting concerns: error monitoring, public marketing page with SEO, product analytics, accessibility. Rigor choices: real product / quick prototype / heavy team grade. Slicing offers four approaches — `tracer bullet` (recommended here: one thin path through the complete system, because the risky part is a pin surviving the frame page → dashboard round trip), `skateboard` (smallest usable whole product), `journey` (complete every state of the user path), `facade` (screens against fake data first); tracer bullet is "popularized by The Pragmatic Programmer". Rigor tiers after `develop`: prototype = done; alpha = verify the code; beta = test on top; GA = a fresh model reviews the initial model's work and documents features — each tier adds slower but heavier verification. Result summary: 10 features planned, 14 deferred, build tracer approach, workflow chosen as beta. The plan (`docs/scope/scope.md`, previewed with Cmd+Shift+V via the Markdown Preview extension) lists foundations, thin threads, features that follow, and current state, and deliberately omits library names (architecture belongs to the `architect` skill). Scope adapts by entry point: brownfield → run the `audit` skill first; monorepo → run scope from the workspace you're changing; new mid-build feature → run scope with one feature idea; return later → run scope with no arguments to reconcile plan vs. what shipped and surface the next action (always the first unchecked box).

### reading-a-spec-what-the-build-sees-and-what-you-keep
- Locator: `[[sources/agentic-engineer/20261014/8. Workflow Ship Something Real/6. Reading a Spec： What the Build Sees and What You Keep (9_11_2026 1：42：57 PM).html#reading-a-spec-what-the-build-sees-and-what-you-keep]]`
- Summary: A spec is a markdown file in `docs/specs/` with no special format (same as a skill). This lesson explains how to read one: shape follows the size of the decision (single file by default; a directory like `docs/specs/0001-stack/` with `index.md` + `rationale.md` only for foundational decisions), the two-reader split, what each `Status` value actually means, and how assumed/superseded specs are handled.
- Key claims: The audience split is the core idea — the build agent needs the decision (`index.md`, what `/develop` reads), while the human needs the argument (`rationale.md`, what `/develop` skips); the reasoning is kept permanently beside the spec but "doesn't ride along on every build," and the split only appears on heavy specs. On a feature-linked spec, `Accepted` means shipped, not approved: `/architect` writes `Proposed` and never touches status again, `/develop` moves it `Proposed → In Progress → Accepted` once built and verified; a standalone decision spec goes `Proposed → Accepted` on ratification and `/develop` never advances it, while a spec documenting already-shipped work is born `Accepted`. When `/develop` hits an undecided thing mid-build and you choose to keep going, it writes an `Assumed` spec (four sections: `Owed decision` · `Assumption built on` · `Code area` · `Requirements`, plus the git author) that blocks the feature from being called finished until cleared.
- Learner-relevant: Reading rules to apply — naming rule: never `0001-stack/0001-stack.md`, the directory carries the number and the top file is always `index.md`; clear an `Assumed` spec by running `/architect` on that decision (if the assumption held it fills in the real content and clears the flag, if not it writes a corrected spec, marks the assumed one superseded, and says the feature must be rebuilt before it can close); reversed decisions are replaced, not edited — the old spec gets a `Superseded by [NNNN]` status and a link to its replacement so the old reasoning stays readable; go to `rationale.md` only when you want to challenge the decision rather than follow it. The lead-in notes "you've watched two specs get written" and the closer tees up turning the plan and decision on disk into a project.
