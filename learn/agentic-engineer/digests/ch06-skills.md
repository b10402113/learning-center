# L1 overview

- **Skills: The Discipline You Did by Hand** — The previous modules taught a discipline (engineer context first, make the real decisions on purpose, keep always-on small, check what comes back) but a discipline is a stack of little procedures you have to remember to run in order on every feature, and it slips exactly when you are busiest. A skill is that procedure written down once in a file so the agent runs it the same way every time whether you are fresh or fried. It has two parts: a short name and description at the top, and a long body below; the agent scans only the descriptions of all your skills and lazy-loads the one body it picks, so unused skills cost two lines instead of a file of rent. A skill does not make the model smarter — it moves your attention off remembering and ordering and onto judgment: the skill runs the procedure, you make the calls. Slide card for this lesson: `1. Skills The Discipline You Did by Hand.png` (has its own image digest).
- **How to Read a SKILL.md file** — Proof by reading a real one: Anthropic's public skills repo, the PDF skill. SKILL.md is ordinary Markdown with structured frontmatter between `---`, holding `name` and `description`; the description is the trigger the agent reads for every skill to decide relevance, and everything below it is ignored until that line fires — a lazy description ("helps with documents") fires wrong or never. Below the frontmatter the body briefs the agent like a good teammate (the job, how to do it, where people trip), and a skill is really a folder that points at lazy-loaded helpers (`forms.md`, `reference.md`, `scripts/`) instead of holding everything itself. Slide card for this lesson: `2. How to Read a SKILL.md file.png` (has its own image digest).
- **Build Your Own Skill** — Build a "teach me" skill with Anthropic's skill-creator: install the plugin, describe the behavior in plain English, answer the Q&A, get a working skill folder in minutes. Because skill-creator writes the description, your prompt becomes the most important part — state exactly when to ask the learner's level, what to do with no topic, and when to verify instead of guessing. Install location is a decision: `~/.claude/skills/` is personal (every project), `.claude/skills/` in the repo travels with the code and reaches the whole team. The written lesson `3. Build Your Own Skill (9_11_2026 1：37：32 PM).txt` is a thin 23-line summary of this .srt.
- **Skills vs. MCP: Which to use and when** — Use one tool (Supabase) to split the job: a skill carries the tool's real current conventions (auth, row-level security, current API, recommended patterns) so the agent stops guessing from stale training; an MCP opens a line into your actual instance (real tables, real data, real queries). Knowing how the tool works versus having a line into your real one — a real project often wants both, for every tool in the stack. The workflow finds the relevant skills and MCPs for your stack and asks before installing; you do the real-account sign-ins. The system does the tedious part, you make the calls.

# L2 detail

- `#L1-L200` — `1. Skills The Discipline You Did by Hand.srt` — Recaps the module's discipline (engineer context before you build, make the real decisions on purpose, keep always-on small, check what comes back) and names the gap: knowing a discipline and running it on every feature are different things. The discipline is a stack of small procedures — find the decision that must be made before code, write it down so it is not lost, size the work so the change is reviewable, check it against what was asked — each of which must be remembered, in order, on every feature; it slips exactly when you are busiest, which is when you need it most. Definition of a skill: a procedure you kept having to do by hand, captured in a file, so it runs the same way every time — less magical than the word sounds, which is the point, because you can understand it completely and build your own. Two parts: a short name and description at the top, the real instructions in a long body below; the agent reads only the top, scans the names and descriptions of every skill it has, decides whether any fits the request, and only then loads that one full body — the others never enter the conversation. Ties back to always-on context rent: ten procedures loaded that way would be ten files of rent on every task, whereas here ten procedures sit available and you pay for the one in use, everything else costing two lines.
- `#L201-L391` — `1. Skills The Discipline You Did by Hand.srt` — The warning: a skill does not think for you, is not a smarter agent, is not a magic prompt that makes the model better at engineering — the model is exactly as capable as before, and nothing about the skill changes how good the AI is. What it changes is where your attention goes: it runs the remembering, the ordering, the did-I-actually-do-the-checklist part, freeing your attention for the decisions, judgment, and calls that were always yours. The one sentence for the module: the skill runs the procedure, you make the calls. Pushes back on the idea that this is less than hoped for — your judgment gets wasted not because it is weak but because it is buried under remembering fifteen procedural things in order on every feature forever; remove that overhead and what remains is the work you are actually good at. Sets up the next two lessons: open a real skill so it stops being a black box, then build your own, because there is no magic in any of it.
- `#L1-L240` — `2. How to Read a SKILL.md file.srt` — Opens Anthropic's public skills repo on GitHub and picks the PDF skill as a clean, well-written example. SKILL.md looks ordinary: Markdown, maybe a command or snippet, no special skill syntax — the same Markdown as a README with a little structured info at the top. In a code view, the frontmatter sits between three dashes and holds two things that matter: a name and a description — and the description is the single most important line in the entire file, the one developers are careless about. It is the trigger: the agent reads the name and description of every skill and uses them to decide which fits the task, which is what makes the PDF skill fire when you ask about a PDF and stay quiet otherwise; everything below it is not even looked at until that line convinced the agent the skill is relevant. A lazy description ("helps with documents") means the agent cannot know when to reach for it — it fires on wrong tasks or misses right ones; a good description says in plain words exactly when to use the skill and when not, and that precision is the difference between a skill that works and one that just sits there. This is the line you will spend most time on when writing your own.
- `#L241-L477` — `2. How to Read a SKILL.md file.srt` — The body is not read back to back, by you or the agent: watch its shape — what the skill is for, when to use which approach, the steps to follow, written the way you would brief a good teammate (here is the job, here is how, here are the things that trip people up), plain instructions. The part many developers miss: a skill is not just one file — the folder holds SKILL.md plus `forms.md`, `reference.md`, and a `scripts/` folder with real code. The clever bit is how they load: SKILL.md does not try to hold everything, it points at the others, saying in effect "if the task is filling out a form, go read forms.md" — so forms.md is touched only when filling a form, reference.md only when a task needs deep details, and scripts run as code so only the result comes back while the code never enters the conversation. So a skill can be big and capable while most of it costs nothing until used — the previous lesson's idea one level deeper: you do not pay for the whole skill, only the exact piece the task touches. The anatomy closes as: a name and description that trigger it, the body of instructions, and optionally three kinds of helpers loaded on demand — scripts (code the agent runs when a job must be exact), assets (templates or images the skill drops into what it produces), and references (deep docs). A skill is a folder with a SKILL.md at its root; the description decides when it fires, the body tells the agent how, and anything heavy loads only when the task reaches for it.
- `#L1-L280` — `3. Build Your Own Skill.srt` — Builds a skill the author actually wants: a "teach me" skill that, when asked to teach a topic, first asks how much you already know (beginner, medium, or pro) and explains at that level, asks what you want to learn if invoked with no topic, and checks the web before teaching something that might be out of date. Note the scope: this is not something the workflow does — the workflow builds software; this is about how I learn, which is exactly the gap your own skill fills. Built with Anthropic's official skill-creator, installed in Claude Code with one plugin install line, then invoked either from the CLI or the extension with the skill described in plain English (its own description — "create new skills, modify and improve existing skills, use when users want to create a skill from scratch, edit, or optimize an existing skill" — would usually fire on its own, but typing the invocation manually is how you are sure). Key insight: the description is normally the most important part, but skill-creator writes it, so your creation prompt becomes the most important part — do not rush it. Instead of "build me a teach me skill", state exactly when to ask the level, what to do when given nothing, and exactly what to do to verify instead of guessing, because the description is the trigger and skill-creator needs that behavior spelled out to fill it. Running it, skill-creator does not generate blindly: it walks the decisions one at a time and asks for input, matching the house style of your existing skills.
- `#L281-L560` — `3. Build Your Own Skill.srt` — Result: the skill is built, installed as `teach` alongside the others, matching their style. Behavior check — run bare, it asks what you want to learn with an open question, not a menu of its own guesses; then checks the level, then verifies. Two decisions it made that were not specified, both worth knowing: it skips the level question when you already stated one ("I'm a 5, what's a closure?", "I'm a senior dev, explain X") and just confirms in half a sentence, because asking right after you told it reads as not listening; and with no topic it asks topic and level in one question round rather than two, so you answer once. Then the install-location lesson: `ls` the global Claude skills folder shows `teach` in the personal skills folder, not the project that was open — correct here, because a teach-me skill is about how I learn and should be in every project, not tied to one repo. A team convention every developer should follow belongs in the project's own skills folder instead, so it travels with the repo and everyone who clones gets it; personal folder is just you, project folder means everybody has it — the exact mechanism by which workflow skills get shared with a team later. Moving one is just copying the folder and file. Demo: asking for database indexes, it asks the level with an explanation of what counts as medium or pro, checks the web, then teaches — index as a separate sorted copy of some columns kept in sync with the table so the database can jump to rows instead of reading all of them, everything surprising falling out of "sorted"; then the common wrong model (a hash map) and where it breaks, the mistakes, how to prove it to yourself, and where to go next. Useful for concepts, for explaining parts of a codebase, or for explaining the agentic engineering workflow to yourself.
- `#L561-L806` — `3. Build Your Own Skill.srt` — The real lesson: making a skill is easy — a couple of minutes, one conversation, and you should feel you can do it right now, because you can. Making a skill that is actually good is a different thing: what was built is a solid first draft. Will the teaching be consistently great every time? Probably not yet. Does the level question fire at exactly the right moments? It did this time, maybe not next time — that needs a lot more testing. Getting a skill from "works" to "I trust this in real work" takes iteration, testing, tightening the description, and reshaping the instructions whenever it does something you did not want; that is the craft, and it is not a couple of minutes. That tells you something about the workflow you are about to use: the nine skills in it have already been through the research, the tuning, and the "this fired wrong, fix the description" loop hundreds of times — anyone can generate a skill, but building ones you would stake a project on is the hard part, and that part is already done for you. Keep two things in mind: whether something even deserves to be a skill in the first place, and how much work it takes to make it genuinely good — you build a skill when it is a procedure you will repeat and you want it done the same way every time. Chapter recap (know what a skill is, read one, built your own) and the hand-off to a side-by-side case study of the same codebase built the old way and through the workflow.
- `#L1-L18` — `4. Skills vs. MCP： Which to use and when (9_11_2026 1：37：53 PM).txt` — The practical split, shown on one tool. Skills carry a tool's real conventions: a Supabase skill teaches how Supabase really works right now — how auth is set up, how row-level security is done, the current API, the patterns the Supabase team recommends — so the agent follows the real thing instead of guessing from half-remembered training that is often out of date; same for a Next.js, Stripe, or Prisma skill. MCPs do the other half: a Supabase MCP does not teach conventions, it connects the agent to your actual project — real tables, real data, real queries against the real thing instead of assumptions. One is knowing how the tool works, the other is having a line into your real instance; different jobs, and a real project often wants both. Normally assembling this is a chore (find the right skill and the right MCP for every tool and wire them up by hand); the workflow looks at your actual stack, finds the relevant skills and MCPs, and asks before installing — you approve what goes in and handle the real-account sign-ins (authenticating into your actual Supabase). The course's recurring pattern: the system does the tedious part, you make the calls.
