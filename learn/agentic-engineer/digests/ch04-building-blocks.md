# L1 overview

- **The Four Primitives** — The whole module is four things an agent can reach for: tools, skills, MCP, and subagents. Nothing else. Every new product will rename these four, so learn the primitives once and a new tool becomes a new accent rather than a new language.
- **Tools** — A tool is a defined action the agent is allowed to perform and get a real result from — not a description of what it might do. The five core tools (read, write, edit, search, run a command) cover nearly everything an agent does, and because the model only requests a call while something else executes it, reasoning and execution fail separately.
- **MCP** — An MCP server turns an outside service's capabilities into tools the agent can call, using one standard that Claude Code, Cursor, and Codex share. It is worth connecting only when the task needs live, changing data you could not simply paste in; otherwise it adds breakage and access for nothing. Once it is worth it, scope it to the project unless the tool is genuinely general-purpose.
- **Subagents** — A subagent is a worker with its own context window: it does the heavy reading and searching and returns only the result, so the main window stays clean, and several can run in parallel. Spend one when the work is heavy and you only want the answer, or when the job splits into independent parts — not for a task the main agent could settle in a file read or two.
- **Configuring a Subagent** — In Claude Code a subagent is a Markdown file with four frontmatter fields (name, description, tools, model) plus a system prompt, built with `/agents` or by hand and stored under `.claude/agents/` or `~/.claude/agents/`. The description is the trigger that decides automatic delegation; the tool list is a real safety boundary, not a formality.
- **Mapping Primitives Across Tools** — Check the four primitives against a second tool and the table barely changes: the same tools, the same `SKILL.md` file copied byte for byte, the same MCP protocol, the same subagent mechanism. The one real divergence is the always-on file — Codex reads `AGENTS.md` directly, Claude Code needs `@AGENTS.md`.
- **Choosing a Model** — The model is roughly 20% of the result and the harness is the other 80%, so stop chasing the biggest model. Cost, speed, and reasoning are a spectrum, not a ranking: send deciding work (specs, architecture, hard debugging) to the deep tier and execution to the fast tier, and dial reasoning effort the same way.

# L2 detail

- `#L1-L61` — `1. The Four Primitives Your Vocabulary Map.srt` — Bridges from the previous module (how agents think: read, decide, act, observe) to this one (what they can reach for). States the promise up front: exactly four primitives, and new tools launching monthly will each invent their own names for the same four, so learning them once here means every future tool is only "learning somebody's accent."
- `#L1-L32` — `2. Tools： What the Model Can Call (9_11_2026 1：31：10 PM).txt` — Defines a tool as a specific, defined action the agent can trigger and get a real result from, like a function or API call; a web search for the current Next.js version is the model doing, not talking. Separates the model from execution (the model requests, something else runs and returns), notes that a correct decision can still fail on a malformed call or a missing file, and lists the core five — read, write, edit, search (grep/glob), run a command — which cover nearly every action in the course. A chatbot can only talk; an agent acts because it has tools.
- `#L1-L68` — `3. MCP： Extending the Agent (and When It's Worth It) (9_11_2026 1：32：13 PM).txt` — MCP in one line: a service builds a server, the agent connects, and everything that service can do becomes a tool call shaped like reading a file; it is a standard, not a Claude feature, so Cursor, Codex, and Claude Code share the same server. The decision test: does the task need live, current data from an outside service you could not paste into the chat yourself (database, calendar, ticket status = worth it; a doc, a static value = skip). Then the scope decision (`local` default, `--scope user`, `--scope project` writing a committed `.mcp.json`), the same two levels in Cursor, Codex, and Copilot configs, and why the rule is general tools global, project data project-scoped. Closes on the three real costs: security blast radius (least access, read-only where possible), context (three common servers at ~81 tools ate over 20,000 tokens, ~16% of a 128k window, before typing), and maintainability.
- `#L1-L100` — `4. Subagents Agents with Their Own Context.srt` — Poses the same "when does it earn its place?" question asked of MCP, now for the fourth primitive. States the problem: every file read and search run piles into one context window, and a full window is a real problem. Frames the target job — lots of reading and searching where all you want is the short answer — and notes that if the main agent does it, all that reading sits in the window for the rest of the session. Sets up the demo project and shows `/context` starting at 4% spent, 93% free.
- `#L101-L200` — `4. Subagents Agents with Their Own Context.srt` — Asks a deliberately broad question (summarize how error handling is done across the API routes). The main agent does not open files; it sends off an `Explore` subagent, visible as its own row, working in a completely separate context, so none of its files and searches land in the main window. The return is a few sentences summarizing the pattern, not the 20 files behind it, and rechecking context shows it barely moved: the reading happened somewhere else and stayed there.
- `#L201-L300` — `4. Subagents Agents with Their Own Context.srt` — Names the two things a subagent buys. First, isolation: heavy work happens in its own space and only the result comes back, so the main window stays clean. Second, speed: because each agent has its own space, the main agent can fan out several subagents on different parts of a job at once, parallel code execution instead of one step after another, so the whole thing finishes faster.
- `#L301-L386` — `4. Subagents Agents with Their Own Context.srt` — The caveat and the test: subagents are not free and not always the answer. Two questions — is the work heavy in a way where you only care about the result, and can the job be split into parts that do not depend on each other? A yes to either makes a subagent a good fit; a small exact task the main agent could answer in a file read or two just gains an extra step. Same judgment as MCP: not "can I use one here?" but "does this job actually need its own space?" Notes the later agentic-engineering workflow leans on this to stay fast with a clean context, and previews the cross-tool mapping.
- `#L1-L109` — `5. Configuring And Using A Subagent (9_11_2026 1：33：02 PM).txt` — The practical follow-up, assuming the decision is already made. Two creation paths in Claude Code: `/agents`, a guided setup (you can literally ask Claude to draft "a read-only code-review subagent that runs on a cheaper model"), or writing the Markdown file by hand — four frontmatter fields plus a system prompt. Explains each field: `description` is the most important line because it is the trigger for automatic delegation (write when-to-use, not what-it-is); `tools` is an optional but real judgment lever (Read, Grep, Glob makes a reviewer physically unable to edit); `model` lets cheap work route to Haiku while the main thread keeps the expensive model. Project (`.claude/agents/`) versus personal (`~/.claude/agents/`) placement, the two ways to run it (automatic by description match, or naming it in a plain message — never `/agents`), the built-ins (Explore, Plan, general-purpose), and the cross-tool table: Cursor and Codex are nearly identical, Gemini uses TOML, Copilot uses agent profiles.
- `#L1-L34` — `6. Mapping Primitives Across Tools (9_11_2026 1：33：34 PM).txt` — Delivers the module's opening promise by testing it against Codex: tools are the same actions with no brand name, MCP is the same protocol and term, subagents are the same mechanism and word, and skills are literally the same `SKILL.md` file copied untouched into a Codex skills folder and used as-is. The one meaningful divergence is the always-on file: Codex reads `AGENTS.md` directly while Claude Code reads `CLAUDE.md` and needs the one line `@AGENTS.md`. Closes with the transferable checklist for any new tool — what actions can it take, does it support on-demand instructions, can it reach outside the codebase, can it hand work to its own context — and the line "learn the primitive once; the tool is just the accent it's spoken in."
- `#L1-L40` — `7. Choosing a Model： Harness vs. Reasoning (9_11_2026 1：33：59 PM).txt` — The layer under everything: which model to run. The model is about a fifth of output quality; the other four fifths is the harness (spec, context management, skills, session hygiene), so a top model with no harness still vibe-codes while a modest model in a good harness ships reviewable work. Cost, speed, and reasoning are a spectrum, not a ranking; the matching rule is decide versus execute — deep tier for specs, architecture, and hard debugging, fast tier for implementing a written plan (Opus decides, Sonnet executes; roughly Sonnet-at-high-effort or Opus-at-medium is the floor). Reasoning effort is the same trade-off one level down, and none of it expires because the harness, not the model name, is what you are learning.
