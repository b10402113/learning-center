# Digest — agentic-engineer (part 4) — The Building Blocks

## Overview (L1)
- **The Four Primitives: Your Vocabulary Map** — Reframes the module: after Module 2's read-decide-act-observe thinking loop, this module covers the four things an agent can reach for. Names the four up front and argues you should learn them once, because every new tool invents its own names for the same four concepts.
- **Tools: What the Model Can Call** — Defines a tool as a specific, defined action the agent is allowed to perform, analogous to a function or API call. Lists the core set every coding agent exposes (Read, Write, Edit, Search/grep-glob, Run a command) and stresses that the model decides to call a tool but something else executes it.
- **MCP: Extending the Agent (and When It's Worth It)** — Explains MCP as a bridge letting the agent reach outside the repo to live services, demonstrated by connecting Prisma over MCP and seeding a database. Covers when MCP earns its place, global-vs-project scoping across tools, and the security/context costs.
- **Subagents: Agents with Their Own Context** — Introduces subagents as isolated-context workers that absorb heavy reading/searching and hand back only the result, keeping the main context clean. Covers the parallel-speed benefit and the two-part test for when to use one.
- **Configuring And Using A Subagent** — Shows the two ways to create a subagent in Claude Code (`/agents` guided setup or hand-writing a markdown+YAML file), its file locations, and how it is actually used (automatic delegation or explicit mention). Maps the concept across Cursor, Codex, Gemini, and Copilot.
- **Mapping Primitives Across Tools** — Delivers the tool-independence promise by checking the four primitives against Codex, showing a skill file copied literally works byte-for-byte in both. Flags the one real divergence (AGENTS.md vs CLAUDE.md) and the four questions to ask of any new tool.
- **Choosing a Model: Harness vs. Reasoning** — Argues the model is only ~20% of output quality while the harness is the other 80%, so model choice is a spectrum (cost/speed/reasoning) rather than a ranking. Gives the rule: the deep tier decides, the fast tier executes.

### tools-what-the-model-can-call
- Locator: `[[sources/agentic-engineer/20261014/4. The Building Blocks/2. Tools： What the Model Can Call (9_11_2026 1：31：10 PM).html#tools-what-the-model-can-call]]`
- Summary: Explains that a tool is a specific, defined action the agent is allowed to perform — the agent acting, not describing — and that this is what separates a coding agent from a chatbot. Enumerates the five core tools every coding agent provides and clarifies the model/execution split.
- Key claims: a tool is "a specific, defined action the agent is allowed to perform," analogous to a function or API call (`read("auth.ts")` returns the file contents); the core set is Read (open a file), Write (create or fully replace a file), Edit (change a specific part), Search (grep/glob for text or file paths), and Run a command (e.g. a test suite or build); the model does not read files or run commands itself — it makes a structured tool call and something else executes it, so reasoning and execution are two separate steps and problems can happen in either; "a chatbot can only talk. An agent can act."
- Learner-relevant: Frames every operation the learner will watch — reading, writing, searching, running a command — as a tool call underneath, tying back to Module 2's token lesson: a tool call is not free, it has real cost and a real result. Built-in tools (read a file, web search) vs add-on tools are distinguished. Ends pointing to MCP as the standard way to reach a specific outside service (calendar, database, third-party API).

### mcp-extending-the-agent-and-when-its-worth-it
- Locator: `[[sources/agentic-engineer/20261014/4. The Building Blocks/3. MCP： Extending the Agent (and When It's Worth It) (9_11_2026 1：32：13 PM).html#mcp-extending-the-agent-and-when-its-worth-it]]`
- Locator: `[[sources/agentic-engineer/20261014/4. The Building Blocks/3. MCP Extending the Agent and When Its Worth It.srt#mcp-extending-the-agent-and-when-its-worth-it]]`
- Summary: Presents MCP (Model Context Protocol) as the standard bridge between an agent and outside services: a service ships a server, the agent connects, and everything the service can do becomes a tool the agent can call. Demonstrates live by connecting a Prisma Postgres MCP server and having the agent seed a real database, then covers when MCP is worth it and how to scope it.
- Key claims: "A service builds a server, your agent connects to it, and everything that service can do becomes a tool your agent can call" — backing up a database is then a tool call "the same shape as reading a file"; MCP is an open standard, not a Claude feature, so Cursor, Codex and Claude Code connect to the same server ("build once, every agent can use it"), which is why Prisma, Neon, Clerk and PostHog ship servers; connecting a server is not free — each is another dependency that can break and a real live connection to something that matters, so ask "does this task need live, current data from an outside service that you can't just paste into the chat yourself?"; scope matters (see scopes below) and a globally-connected sensitive server is reachable from every session, including throwaway experiments, so shrink the blast radius and give the least access (read-only DB role unless writes are needed); context cost is real — a benchmark measured a stack of three common servers (~81 tools) eating over 20,000 tokens up front, roughly 16% of a 128k window before the session starts.
- Learner-relevant: Concrete commands — connect with `claude mcp add --transport http prisma https://mcp.prisma.io/mcp`, then `/mcp` to sign in the first time. Prisma's server also exposes a docs-search tool, so Prisma questions get answered from current official docs with citations instead of training data (solving the cutoff problem from lesson 2); it blocks destructive commands like wiping a database unless you explicitly confirm. Three Claude Code scopes via `--scope` on the same command: Local (default, private, current project only), `--scope user` (everywhere), `--scope project` (writes `.mcp.json` at the repo root, committed so the team gets it on clone; Claude Code asks each teammate to approve on first use). Other tools' config: Cursor `~/.cursor/mcp.json` (global) and `.cursor/mcp.json` (project, wins if both present); Codex `~/.codex/config.toml` and `.codex/config.toml`; Copilot `~/.copilot/mcp-config.json` and repo settings on GitHub (does not read VS Code's `.vscode/mcp.json`). Best practice: default to project scope for anything tied to one project or holding real access, reserve global for a small set of genuinely general-purpose tools; scope to project when in doubt. Demo details: a no-data app with users and posts, asked to "seed my database with realistic sample data, but create a backup first"; the agent inspects the workspace/schema, finds two databases, reads the Prisma config, determines the `.env` matched no existing project, creates a new Prisma Postgres database, writes its ID into `.env`, creates a backup and migration, seeds data, then independently verifies it; viewable at localhost 3000 and in Prisma Studio (migrations, posts, users, schema visualizer).

### subagents-agents-with-their-own-context
- Locator: `[[sources/agentic-engineer/20261014/4. The Building Blocks/4. Subagents Agents with Their Own Context.srt#subagents-agents-with-their-own-context]]`
- Summary: Explains the fourth primitive: subagents run in their own separate context, do heavy reading/searching, and hand back only the result so the main context window stays clean. Adds the speed benefit of running several subagents in parallel and the test for when one is warranted.
- Key claims: every file the agent reads and every search it runs piles up in one context window, and a full window is a real problem; a subagent "does heavy work in its own space and then hands you back only the result," so your main window stays clean; because each agent runs in its own space, the main agent can send several subagents off at the same time on independent parts ("parallel code execution"), so the whole task finishes faster; subagents are "not free, and not always the answer" — if the task is small and exact (answerable in a file read or two), sending a subagent just adds an extra step for no reason.
- Learner-relevant: The two-question test for when a subagent earns its place — (1) is the work heavy (a lot of reading/searching) where you only care about the result, and (2) can the job be split into parts that don't depend on each other? Yes to either makes a subagent a great fit; the same judgment as MCP ("does this job actually need its own space?" not "can I use one?"). Demo details: run the `context` command in a terminal Claude session — system prompts ~1%, system tools ~2%, 93% free (4% spent); asking it to "look through this project and summarize how error handling is done across the API routes" spawns an **Explore** subagent in a separate context; it returns a few sentences of summary, not the ~20 files it read, and the context barely moves. Forewarns that the course's later agentic-engineering workflow leans on this exact idea to stay fast and keep context clean.

### configuring-and-using-a-subagent
- Locator: `[[sources/agentic-engineer/20261014/4. The Building Blocks/5. Configuring And Using A Subagent (9_11_2026 1：33：02 PM).html#configuring-and-using-a-subagent]]`
- Summary: Shows how to create a subagent in Claude Code (guided or by hand), what each frontmatter field does, where the file lives, and how it is actually invoked. Then maps the same concept across other tools.
- Key claims: there are two creation paths — the easy way is the `/agents` command, which gives a guided setup and writes the file with the right structure (you can even ask Claude to draft it, e.g. "create a read-only code-review subagent that runs on a cheaper model"); the manual way is a markdown file with a bit of YAML at the top ("four bits of frontmatter and a system prompt"); the `description` field is the most important line — it is the trigger Claude reads to decide when to delegate on its own, so write it as when to use it, not just what it is (vague = fires wrong or never); `tools` is an optional safety boundary, omitting it inherits everything while listing specific tools restricts the subagent (a reviewer with only `Read, Grep, Glob` physically cannot modify your code); `model` is optional, routing heavy cheap work to a faster model like Haiku while keeping the expensive model for the main thread, so subagents save money as well as context; a lot of the benefit comes from Claude Code's auto-invoked built-ins.
- Learner-relevant: Frontmatter fields — `name` (how you refer to it), `description` (the trigger), `tools` (optional restriction), `model` (optional, e.g. Haiku for searching), and the body is the system prompt (example: a senior code reviewer that reads the diff, flags security/error-handling/convention issues, reports by severity, and fixes nothing). Locations mirror skills: `.claude/agents/` (project, travels with the repo) and `~/.claude/agents/` (personal). Two ways to use it — **automatic** (a normal task matches the description and Claude delegates on its own) and **explicit** (name it in a plain message, e.g. "Use the code-reviewer agent on these changes") — and neither is the `/agents` command: `/agents` is where you build it, a normal message is where you use it. Built-in auto-invoked subagents: **Explore** (fast, read-only, runs on Haiku, for searching a codebase), **Plan** (read-only, for gathering context during planning), and **general-purpose** (the catch-all). Across tools: subagents are not Claude-only and are configured almost the same way (markdown frontmatter dropped in an `agents` folder, project or user scope); Cursor even reads Claude's and Codex's agent folders directly, so it transfers almost unchanged; Gemini CLI uses TOML rather than markdown; Copilot uses its own agent profiles plus built-in specialists.

### mapping-primitives-across-tools
- Locator: `[[sources/agentic-engineer/20261014/4. The Building Blocks/6. Mapping Primitives Across Tools (9_11_2026 1：33：34 PM).html#mapping-primitives-across-tools]]`
- Summary: Validates the tool-independence promise by checking the primitives against Codex, showing that a skill file is quite literally the same file across tools. Highlights the single meaningful divergence between Claude Code and Codex and the four questions to ask of any new agentic tool.
- Key claims: mapping the primitives against Codex reveals "nothing new to learn — the names barely change, and in most rows they don't change at all"; skills is the row worth pausing on because it's not "the same idea," it's the same file — a skill in Codex is a folder with a `SKILL.md` inside, same structure, same frontmatter, same behavior (agent reads name and description first, loads the full instructions only once it decides to use it); the `code-reviewer` skill folder in `.claude/skills/` can be copied untouched into a Codex project's skills folder ("a plain copy") and Codex uses it the same way; the one real divergence is the always-on file — Codex reads `AGENTS.md` directly, while Claude Code reads `CLAUDE.md` and needs one line, `@AGENTS.md`, to pull in that shared context; every time a new tool launches you already know what to look for.
- Learner-relevant: The four questions to ask of any new tool — what actions can it take; does it support on-demand instructions in this shape; can it reach outside the codebase; can it hand heavy work off to something with its own context. Framing to carry forward: "Learn the primitive once. The tool is just the accent it's spoken in." Verified against Codex as of the recording date; if a tool changes how it reads these files, the `@AGENTS.md` line is the only thing to update.

### choosing-a-model-harness-vs-reasoning
- Locator: `[[sources/agentic-engineer/20261014/4. The Building Blocks/7. Choosing a Model： Harness vs. Reasoning (9_11_2026 1：33：59 PM).html#choosing-a-model-harness-vs-reasoning]]`
- Summary: Argues that model choice matters far less than people think because the model is only about a fifth of output quality — the harness (spec, context management, skills, session hygiene) is the other four fifths. Reframes model selection as a cost/speed/reasoning spectrum, not a worst-to-best ranking, and gives the decide-vs-execute rule.
- Key claims: "the model is maybe a fifth of your output quality" and the other four fifths is everything around it — the spec you wrote, how you managed context, the skills doing procedural work, and resetting a session before it rots — that whole apparatus is the harness; a top-tier model with no harness still vibe-codes, while "a modest model inside a good harness produces solid, reviewable work," so the model is a dial you set, not the engine of quality; every provider gives a trade-off along three axes (cost, speed, reasoning depth) and you pick a point based on what the task needs — a cheaper, faster, lighter-reasoning model isn't the "worse" choice; the rule is "the deep tier decides, the fast tier executes"; effort ("thinking level" / "reasoning effort") is the same trade-off one level down — higher effort = longer, harder, slower, pricier; the rule holds across every tool and doesn't go stale, since a better model with the same workflow just gives better results with zero changes on your end.
- Learner-relevant: Decide vs execute in practice — **deciding** (writing the spec, planning module boundaries, debugging something you don't understand yet) is where a bad call costs the whole build, so send it to the deep tier; **executing** (implementing a feature once the spec is written) is the bulk of the work and goes to the fast tier. The workflow front-loads deciding: once `/scope` and `/architect` have done their job, implementation is genuinely just execution. In this course's Claude setup the deep tier is **Opus** and the fast tier is **Sonnet**, so architecture goes to Opus and implementation to Sonnet; from testing the workflow holds down to roughly Sonnet at high effort or Opus at medium effort (about the floor, as of now). Codex, Copilot, and Gemini each have their own fast and deep tiers and take the exact same rule; check tool docs for current model names and effort settings because those move — the rule doesn't. Turn effort up for deciding work (architecture, a spec, a nasty bug) and down for routine execution.
