# L1 overview

- **A second mind, and the record it leaves** — the last open problem from the earlier tiers is that one model builds, verifies, tests and then judges its own work, so the same mistake can ride through every stage unnoticed. GA (general availability, the public-shipping tier) closes it by handing the finished code to a *different* model that took no part in writing it: `/check review` judges how the feature was built, not whether it runs. `/document` then writes the PR description, changelog, release note or postmortem from artifacts already on disk (diff, spec, review, tests), so the record travels with the change. The builder keeps judgment: the skills carry state and process, the human decides fit, honesty, evidence, and who reviews.

# L2 detail

- `#L1-L91` — `1. Why a Second Mind Matters.srt` — Recap of the open problem: the same model designs, builds, tests and judges, so it can carry one mistake through every stage without noticing. GA is defined as the highest verification tier = shipping publicly. The argument for a reviewer who didn't write the code: authors read what they meant to write, not what is there; models share this weakness and favour their own output, especially when judging a decision already made, and a stronger version of the same model does not fix it.
- `#L92-L195` — `1. Why a Second Mind Matters.srt` — What `/check review` is and is not: run after build, verify and test, the code goes to a model with no part in writing it, read from a clean start, looking for what the author missed. It does not run the app (verify already proved behaviour) and does not write tests (test already protects it); it judges design soundness, safety and maintainability, security risk nobody put in spec or tests, and whether the next developer can follow it. The tier ladder — prototype self-check, alpha proof it runs, beta tests, GA a different model reviewing — all share one move: the check moves further from the author.
- `#L1-L87` — `2. Demo - Running check review.srt` — Running the skill: `/check` asks verify or review, and on what scope; the data model is chosen because the whole app depends on it. Before reading a line, it must work out which model wrote the code, and it reads that from project settings rather than asking the current model to self-identify (a name in a conversation goes stale on model switch), then asks one confirmation question — "is this the model that wrote the code?" That confirmation is the whole guarantee. Handing work back to the author defeats the point.
- `#L88-L245` — `2. Demo - Running check review.srt` — Mechanism and inputs: it picks a different model and runs in a separate read-only helper, so the diff and file reads stay out of your session and it structurally cannot edit the code — it is judging. It starts from the diff but then reads each touched file completely, unlike most review tools, because surrounding code usually decides whether a change is safe; here that means the source database folder, server, drizzle and the spec — 23 files scoped to the data model feature, reviewed on Opus against Sonnet authorship.
- `#L246-L420` — `2. Demo - Running check review.srt` — The output and how it ranks: five major fixes before merge (a dev-dependency that is a runtime peer, so a pruned production install breaks auth entirely; JWTs with no expiry against the 90-day rule in specs 1 and 5; unguarded transactions that throw instead of returning a failure when a project is deleted mid-flight; the only test covering AC1–AC9 is `describe.skip` and never ran), plus 10 minor, 8 nitpicks, strengths (schema faithfully implements the spec) and a test-coverage read. The report records reviewer, verdict and scope, summary, majors, minors, nitpicks, strengths. Fixes are then implemented by telling the agent to work from that document, with `/debug` for bugs and `/test` for the test gaps — the skills compose.
- `#L1-L26` — `3. document： The Record That Travels With Your Code (9_11_2026 1：49：59 PM).txt` — `/document` exists because after build, prove, test and review the code is ready but the people around it are not: it writes the record that travels with the change, and it is the natural partner to review, since a reviewer trusts a change faster when the description tells the story first. The four document types and their audiences: PR description (what changed, in product language), changelog entry (what was added or fixed), release note (what users can now do, breaking changes flagged), postmortem (the facts, unknowns marked unknown). It infers which fits from where you are — on a feature branch ahead of base it suggests a PR description and asks to confirm — and the postmortem pairs with `/debug`.
- `#L27-L52` — `3. document： The Record That Travels With Your Code (9_11_2026 1：49：59 PM).txt` — What it reads is the whole argument: commits and diff give what changed, the spec why it exists, the review findings what the risks are, the tests how it can be checked — the two hardest parts, reason and risk, are already on disk instead of reconstructed from memory a week later. Code beats commit message: a performance claim with nothing measuring performance is dropped; it will not invent a benefit, a number nobody measured, or a timeline. PR body anatomy: what changed, why, changes grouped by purpose, testing steps from the real suite, risks including what review found and how it was fixed. It asks before pushing or updating a PR, writes prose only, and admits its limits — a vague spec yields a thin document, and truthfulness is a discipline rather than a technical guarantee. Unlike tools that read only commit messages or only the diff, every claim traces to an artifact.
- `#L1-L47` — `4. The Loop Youll Actually Run.srt` — The division of labour in the loop you actually run: the skills carry the state and the process, you carry the judgment. You decide whether a recommendation fits your product, clear the session when the conversation turns to mud, reward an honest red result over a convenient green one, ask for the evidence, and pick reviewers who don't share the author's blind spots. The agent only works fast, never tires, and has no stake in whether what you build is successful, safe or worth maintaining.
