# Digest — agentic-engineer (part 10) — Workflow: Ship Something Real (architect demo + challenge)

## Overview (L1)
- Demo Running architect — A full screen-recorded run of the Architect skill on a fresh Next.js/Supabase project, showing how it reads scope/specs/git state, spawns Haiku research sub-agents, walks six rounds of load-bearing questions, offers agent skills and MCP servers, writes the stack spec plus rationale, and cross-checks the spec with an independent model.
- Challenge: Scope Your Own Real Idea — A no-answer-key exercise asking the learner to run their own idea through `/scope` then `/architect`, framed around three LLM tendencies (agreeing blindly, reaching for the common answer, wanting to look finished) and a self-check list for judging whether the run went well.

## Sections (L2)
### demo-running-architect
- Locator: `[[sources/agentic-engineer/20261014/8. Workflow Ship Something Real/7. Demo Running architect.srt#demo-running-architect]]`
- Summary: The presenter opens a fresh Claude Code session for each skill run (so the chat history does not pollute context) and points Architect at the single decision of stack and architecture. Architect first reads the architect skill, lists project files, reads the scope, checks for `agents.md`, reads existing specs, and checks git state — exhausting what the repo can answer before spending questions on the user. It then runs a six-round interview, resolves every load-bearing choice, installs agent skills, suggests MCP servers, and writes the spec.
- Key claims: Architect obeys one rule — one decision per run, not a backlog; the references step asks permission to verify the current tech landscape with low-level sub-agents (e.g. Haiku) rather than recommending from stale memory; skills teach the agent a tool's real conventions while MCP servers give live access to the real system (both optional, both usually improve the build); a different model cross-checks the spec because a load-bearing gap is the most expensive kind and a different model catches what the author model is blind to; a reviewer never silently patches a missing decision — only harmless wording and mechanical inconsistencies are auto-fixed, anything changing behavior/ownership/risk/architecture needs approval.
- Learner-relevant: Supports the workflow's "ship something real" stage and the `/architect` run. Concrete details: new chat per skill run; questions grouped into six rounds (app shape → framework/data platform/auth → API shape & client identity → build surface/styling/testing → setup decisions/package manager/migrations → last three: email, CI/CD, monitoring); verified landscape findings: Next.js 16 with App Router stable, TanStack Start at release candidate, Better Auth 1.6, Drizzle nearing 1.0, iframe header rules. Stack chosen: one full-stack Next.js app + Supabase (Postgres, auth, storage) + Drizzle ORM on the server + Vercel hosting + Tailwind/ShadCN + Zod + Vitest only (Playwright deferred) + pnpm + DrizzleKit migrations. Client identity: signed cookie holding generated ID and name scoped to the link; share link stored as a long random token in the URL hashed; email/password sign-in using Supabase's rate-limited built-in sender, moving to Resend before launch; no rate limiting or CI/CD at launch; error boundary now, monitoring deferred. Research sub-agents are read-only and never fill the main conversation (source links preserved in the spec); a self-set budget for the researcher skill can cause it to report running out before verifying some tools. Skills: five official ones installed (Supabase agent skills, Supabase Postgres best practices, ShadCN/UI, Vercel Labs React/Next.js best practices, Vitest); repos install as bundles (four repos dropped 31 skills) so 20 irrelevant skills were pruned, keeping 11. MCP servers (optional, configured in own settings, not by the agent, because they grant broad privileges): Supabase (highest value — whole backend lives there), Vercel (auto-deploy), Next.js dev tools (real render/route info) — all three installed. Artifacts: `specs/0.0.0.1-stack-architecture/index.md` (summary, decision, proposed stack, security model, configuration, consequences, follow-up) and `rationale.md` (context, options considered, rationale, evidence, references); index directly links the rationale. No build plan or acceptance criteria yet — Developer skill derives scaffold steps. Cross-check found real gaps: concrete values left unset that two later specs would disagree about, and incorrect claim that row-level security protects the upload flow (signed upload URLs are authorized by service role at mint time and token at fetch time, never table policies); presenter disagreed that five gaps (pin coordinate reference frame, pin numbering, read state, soft vs hard delete, foreign key behavior) belong to this spec — they are owed to feature three (the data model spec). The architect session spent ~150,000 tokens. Scope was updated to move "stack and architecture" to in progress and add steps after the architect. Next: clear the session and use the Developer skill to scaffold, then check and test.
### challenge-scope-your-own-real-idea
- Locator: `[[sources/agentic-engineer/20261014/8. Workflow Ship Something Real/8. Challenge： Scope Your Own Real Idea (9_11_2026 1：44：36 PM).html#challenge-scope-your-own-real-idea]]`
- Summary: A deliberate no-answer-key challenge: pick a real idea you want to exist, run it through `/scope`, take the first important decision it identifies, and run it through `/architect`. Rather than a finished solution to copy, it teaches how to judge whether a run went well by understanding the grain of the agent, which is not neutral.
- Key claims: Three LLM tendencies come from training and each can steer the product away from what you intended — (1) the agent wants to agree with you, so a leading premise ("Uber for dog walkers") gets accepted and every later decision grows on top of it (premise drift); (2) the agent reaches for the common answer, calibrated to the most typical project, so recommendations aimed at the average project miss your commercial risk, team pressure, personal constraint, or doubt; (3) the agent wants to look finished, naturally closing gaps and smoothing uncertainty into a tidy plan built on shortcuts you no longer remember taking. The counters: let `/architect` challenge your premise instead of overriding the warning; make it show its reasoning (a recommendation, concise explanation, and credible runner-up per layer) and test that reasoning against your situation; allow the interview to take the time it needs, especially cross-cutting questions (access, ownership, privacy, failure behaviour, permissions, lifecycle rules).
- Learner-relevant: Supports the `/scope` → `/architect` handoff exercise and calibrates expectations for how the agent behaves while being directed. Concrete details: build-approach example — Tracer Bullet is often a strong default (proves one thin path through the whole system early), but if the greatest risk is whether anyone wants the product at all, Skateboard may be better (reaches the smallest usable version sooner); you know whether the real danger is technical feasibility, product demand, visual approval, or completeness of one critical user journey. A short interview should make you cautious, not impressed. Self-check questions: does the chosen build approach attack your greatest risk or is it just the first recommendation; is the workflow tier honest about what you're building (weekend experiment, personal tool, or real product others depend on); did you understand the reason behind every architectural recommendation or wave choices through on familiar tool names; does every value/state/permission/behaviour in the spec have a named source or would `/develop` have to invent it. Deliverables: two artifact files on disk — a living plan (`/scope`) and the first Accepted decision the plan depends on (your first spec). Next: create the accepted stack, then run `/audit` against what was actually created so it writes the convention file every later skill reads.
