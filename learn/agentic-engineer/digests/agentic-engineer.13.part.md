# Digest — agentic-engineer (part 13) — Workflow: Ship It Like a Team

## Overview (L1)
- Why a Second Mind Matters — Closes the "same model builds, tests, and judges its own work" gap at the GA (general availability) tier: the author and the judge must not share assumptions, so implementation's code is handed to a different model that reads it cold and judges how it was built — design, safety, maintainability, security, and readability for the next developer.
- Demo - Running check review — A screen-recorded run of `check review` on the data model: it determines the author model from project settings, asks one confirmation question, then dispatches a read-only reviewer on a different model that checks the diff and every file in full, producing five major fixes, 10 minor notes, 8 nitpicks, and strengths.
- document: The Record That Travels With Your Code — `/document` writes the record that travels with the change (PR description, changelog entry, release note, or postmortem) by extracting factual context from four inputs — diff, spec, review findings, and tests — so the reason and the risk come from disk, not memory.
- The Loop You'll Actually Run — The closing framing: the skills carry the state and the process, but the human carries the judgment — deciding fit, clearing a muddy session, rewarding honest red over convenient green, asking for evidence, and picking reviewers who do not share the author's blind spots.

## Sections (L2)
### why-a-second-mind-matters
- Locator: `[[sources/agentic-engineer/20261014/10. Workflow Ship It Like a Team/1. Why a Second Mind Matters.srt#why-a-second-mind-matters]]`
- Summary: The tier before GA left one problem open — the same model can build a feature, test it, and then judge its own work, carrying the same mistake through every stage unnoticed. GA (general availability, the highest tier of verifications and checks, shipping the app public) closes it by adding the requirement engineering teams have always imposed before important code ships: a review from someone who did not write it — here, a different model.
- Key claims: You cannot reliably review your own work because you read what you intended to write, not what is actually there; models share that weakness and tend to favor their own output, especially when judging a decision already made; using a stronger version of the same model does not fix it — you need a separate reviewer that arrives without sharing the author's assumptions. `check review` hands built/verified/tested code to a different model that had no part in writing it; it does not run the app (`check verify` already proved behavior) and writes no tests (test already protects it) — its job is to judge how the feature was built. Every tier moves the check further away from the model that wrote the feature: prototype = builder checks its own work; alpha = prove the feature runs; beta = protect it with tests; GA = a different model reviews before it ships.
- Learner-relevant: Frames the fourth and final workflow tier (GA) and the `/check review` skill. Review questions it answers: Is the design sound? Is the code safe and maintainable? Is there a security risk nobody put in the spec or the tests? Will the next developer understand what is happening? Supports the "ship it like a team" stage and sets up the demo lesson that runs `check review`.

### demo-running-check-review
- Locator: `[[sources/agentic-engineer/20261014/10. Workflow Ship It Like a Team/2. Demo - Running check review.srt#demo-running-check-review]]`
- Summary: The presenter runs `check review` on the data model (the entire database setup, the part the whole application depends on). Before reading a line of code it works out which model authored the code — not by asking the current model, whose self-identification can be wrong and whose name in a conversation goes stale on switching, but by reading project settings — then asks the single confirming question ("Is this the model that wrote the code?"). It then picks a different model and runs the review in a separate read-only helper that cannot edit the code.
- Key claims: `check review` checks the diff and then examines every file completely, because a diff shows changed lines while the surrounding code is usually what decides whether the change is safe. It confirms the author model because handing the work back to the author defeats the point; that confirmation is the whole guarantee. In this run: author on Sonnet, reviewed on Opus, 23 files scoped to the data model feature, and five major fixes before merge.
- Learner-relevant: Concrete workflow for the `/check review` skill (`check verify` vs `check review`, and scope — e.g. `check review data model`). Files/folders scoped in the review: source database folder, source server, the drizzle, and the spec. Findings: (1) `supabase.js` in `package.json` `devDependencies` but is a runtime peer dependency of Supabase, so a pruned production install breaks owner auth entirely; (2) client identity JWT has no expiry, contradicting the 90-day expiry both spec 1 and 5 require (capture token stays valid forever); (3) server actions pin unguarded transactions that can throw instead of returning `{ ok: false }`, reachable if a project is deleted between token resolve and transaction; (4) the only test covering AC1–AC9 is `describe.skip` (gated) and has never run. Totals: 5 major, 10 minor, 8 nitpicks, plus strengths ("schema faithfully implements the spec"). Note: this app was not set to the GA tier, so the feature-scope row has no reviewer checkbox, but the review can still be run on demand. Output is written to a review document; the agent can then implement all fixes from it, and the `debug` skill can address bugs or the `test` skill can fix the test issues — showing how the skills compose.

### document-the-record-that-travels-with-your-code
- Locator: `[[sources/agentic-engineer/20261014/10. Workflow Ship It Like a Team/3. document： The Record That Travels With Your Code (9_11_2026 1：49：59 PM).html#document-the-record-that-travels-with-your-code]]`
- Summary: Once a feature is built, proven, tested, and reviewed, `/document` writes the record that travels with the change — PR description, changelog entry, release note, or postmortem — picking the type that fits from where you are (e.g. on a feature branch ahead of base it suggests a PR description and asks you to confirm). It is the natural partner to review, because a reviewer trusts a change faster when the description explains the story before they open files.
- Key claims: It reads four inputs and this is the whole argument — the commits and diff (→ what changed), the spec (→ why the change exists), the review findings (→ what the risks are), and the tests (→ how it can be checked). The two hardest parts of a good PR description, the reason and the risk, are already on disk, captured while the work was happening, so you are not reconstructing them from memory a week later. Code beats commit message: if a commit message claims a performance improvement but the diff contains nothing that measures performance, the claim is dropped — commit messages are hints, not evidence. It will not invent a benefit the implementation does not provide, a number nobody measured, or a timeline that never happened; the document is less exciting than it could be, and it is also true.
- Learner-relevant: Supports the `/document` GA step and how it chains with review/`debug`. Type → audience → leads-with table: PR description → reviewers → "what changed, in product language"; changelog entry → developers → "what was added or fixed"; release note → users → "what they can now do, breaking changes flagged"; postmortem → the team after an incident → "the facts, with unknowns marked as unknown". Anatomy of the PR body: what changed (product language, not edited filenames); why (from the spec); the changes (grouped by purpose, not copied from the git log); testing steps (from the real suite and verified flow); risks (including what review found and what you changed). It asks before it pushes: opening/updating a PR sends info to a shared system, so it shows the full body and asks first regardless of project settings, updates an existing PR on the branch instead of duplicating, and writes prose only — it does not commit, push, or merge. When to run: before a PR, on merge for a changelog, when a version is ready for release notes, or after an incident for a factual postmortem (pairs with `/debug`, met in the recovery module). Honest limits: only as good as the trail behind it — a vague/missing spec yields a thin but still honest document; its truthfulness is a discipline, not a technical guarantee. Different from the field because gathering correct information, not writing, is the hard part: a tool reading only commit messages repeats stale claims, and one reading only the diff misses why it mattered. Next: use all four GA steps on one feature yourself and run an experiment on what independence buys.

### the-loop-youll-actually-run
- Locator: `[[sources/agentic-engineer/20261014/10. Workflow Ship It Like a Team/4. The Loop Youll Actually Run.srt#the-loop-youll-actually-run]]`
- Summary: The closing lesson of the workflow: the skills carry the state and the process, but you carry the judgment. The agent works fast, never gets tired, and has no stake at all in whether what you build is successful, safe, or worth maintaining — so the human decides what fits the product and what to trust.
- Key claims: You decide whether a recommendation fits your product; you clear the session when the conversation turns to mud; you reward an honest red result over a convenient green one; you ask for the evidence and pick the reviewers who do not share the author's blind spots. The agent's speed and tirelessness are not a substitute for judgment because it holds no stake in the outcome.
- Learner-relevant: Summarizes the human role across the whole ship-it-like-a-team workflow and models the habit of treating review/testing signals honestly (prefer truthful failure over false pass). Supports the GA tier's emphasis on independent review and on asking for evidence.
