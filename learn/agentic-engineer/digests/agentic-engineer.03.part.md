# Digest — agentic-engineer (part 3) — How Coding Agents Work

## Overview (L1)
- The Agent Loop — Every coding agent, whatever the tool, runs the same Read → Decide → Act → Observe loop repeated until the task is done. Walks a live login-button bug through all four phases, shows the loop as the atomic unit (a 5-minute task ≈ 8 loops, a feature ≈ 80), and warns that one bad read or decision compounds into every later loop. Teaches the architect's job: control what it reads, how clearly you help it decide, and how closely you check what it observes.
- What the Agent Sees — Names the gap between what you assume the agent knows and what is actually loaded in its context window. The window holds only the current conversation, files it explicitly read via tools, always-on context you configured (e.g. a CLAUDE.md), and system instructions — nothing else. "If you didn't say it, and it didn't read it, it doesn't know it," which explains most "it should have known that" failures and sets up context engineering.
- How Agents Read Your Codebase — There is no index, no embeddings database, no pre-built map. The agent finds things the way a new hire would: grep to search text, glob to match filenames, read to open a file, on demand every time. A live "where is auth handled" search shows one grep, one filtering decision, and four file reads to answer. Concludes that clear naming and predictable structure directly reduce searching, wasted context, and wrong guesses.
- Context Windows and Why They Fill — Everything read, typed, and returned lands in one container with a hard limit: the context window (some tools reach ~1,000,000 tokens). Rebuilding the auth question shows search results, whole files, and a wrong guess all stay in the window unrefunded while the actual answer is one small segment at the end. The key insight: most of what fills the window is the cost of finding the useful part, and exploration is expensive by nature.
- Context Rot: Quality Slips Before The Window Fills — 2025 research across 18 frontier models found output quality drops as more tokens go in, and degradation starts well before the window is full (a 200,000-token window can measureably degrade at 50,000). Splits this into positional degradation (a U-shape; middle content used 20–30 points worse) and length degradation (reasoning accuracy 92%→68% as input grew; reworded facts fall below half short-context accuracy by ~32,000 tokens).
- Topic Switching: When Unrelated Work Pulls Focus — A single session drifting across unrelated topics is a worse environment than several short focused sessions. A study found accuracy fall from 100% to ~75% once eight unrelated topics were folded into one growing conversation; this is named "contextual distraction." Day to day this shows up as repeating rejected fixes, forgetting settled decisions, and contradicting earlier answers — the model is equally capable, only the competing-vs-relevant ratio changed.
- Clearing vs. Compacting — Two ways to reset: clearing wipes the window empty, compacting summarizes the conversation and keeps the summary going forward. Compacting is efficient but lossy and unreviewable — a subtly reworded summary is by definition no longer there to check — while clearing is predictable because you know exactly what's in the window (nothing). Gives rules for when to use each, keyed on whether the next step depends on precise earlier details.
- Tokens What Costs What — Makes the context budget concrete: reading is expensive and reasoning is cheap. Expensive: reading files (a 300-line file costs ~300 lines whether 10 or all were needed), search results, long conversation histories (60-message session carries the cost of all 60), and verbose output. Cheap: short targeted reasoning, precise questions, and small scoped reads. Ends with the habit of asking whether a task forces broad or targeted reading, and the Claude Code `/context` command for a live breakdown.

### the-agent-loop

### what-the-agent-sees
- Locator: `[[sources/agentic-engineer/20261014/3. How Coding Agents Work/2. What the Agent Sees (9_11_2026 1：22：42 PM).html#what-the-agent-sees]]`
- Summary: Explains that an agent does not "know" the codebase the way a teammate does — it only knows what is currently loaded into its context window, which is much smaller and more fragile than knowing the project. The lesson enumerates exactly what the window holds and argues the gap between your mental model and the agent's actual context is the single biggest source of "it should have known that" frustration.
- Key claims: The agent knew none of what you knew going in about the login bug — it had to grep, open, and read its way to the same place you started from mentally; the context window holds only the current conversation, files it explicitly read via tool calls (not the whole codebase), any always-on context you've configured (like a CLAUDE.md file, if one exists and is set up correctly), and the tool's system instructions — nothing else; the four common causes of context gaps are: you mentioned it in a different session, you assumed a file being in the repo meant it had been read, you told a teammate or wrote a doc but never told the agent, or it was said early in a long session and fell out of the window; the countermeasure is asking before every prompt "Does it actually have what it needs to get this right?" and this instinct is what context engineering (Module 4) is built around.
- Learner-relevant: Grounds the whole module's premise that context is explicit, not inferred; supports prompt-writing and handing-off decisions. Tool/config mentioned: a `CLAUDE.md` file as always-on context. Forward reference: "context engineering" is built properly in Module 4.

### how-agents-read-your-codebase
- Locator: `[[sources/agentic-engineer/20261014/3. How Coding Agents Work/3. How Agents Read Your Codebase.srt#how-agents-read-your-codebase]]`
- Summary: Corrects the common assumption that the agent searches an index (like Google indexes the internet). There is no index, no embeddings database, and no pre-built map — the agent finds things the same rough way you would in an unfamiliar codebase, by searching and opening files. A live demo asks "where is auth handled in this project" and traces the search, filtering, and reads that get to the answer.
- Key claims: The real toolkit is grep (search text across files), glob (find files matching a pattern), and read (open one file) — no shortcuts, no magic, just on-demand calls; on a fresh context the agent doesn't answer but first runs a bash grep for "auth" casting a wide net because it has no idea where to look; it filters the many matches by filename and matching context before opening, correctly guesses `auth.ts` holds the real implementation, then reads files referenced from it; the final answer describes auth split across four layers — credentials and handler registry in `lib.ts`, plus sessions, actions, and the proxy; getting there cost one search, a filtering decision, and four file reads. Naming matters: `auth.ts` is found in one grep, whereas `utils2.ts` with an exported `handleThing` forces more searches, more files opened, more guessing, and more context burned; clear naming and predictable structure directly reduce searching, so you're writing code for something that navigates by search like a new hire on day one — except it does it from zero every session.
- Learner-relevant: Explains why repository structure and naming are functional levers on agent performance, not just style; sets up the token-cost argument in lesson 8. Tools named: grep, glob, read, bash. Concrete example: `auth.ts` vs `utils2.ts`/`handleThing`; four auth layers (lib.ts credentials + handler registry, sessions, actions, proxy).

### context-windows-and-why-they-fill
- Locator: `[[sources/agentic-engineer/20261014/3. How Coding Agents Work/4. Context Windows and Why They Fill.srt#context-windows-and-why-they-fill]]`
- Summary: Frames the context window as a single container with a hard limit that holds everything the agent has read, everything you've typed, and everything it has responded with, for the length of the session. Rebuilding the auth question shows exactly how the container fills, and the surprising conclusion is that most of what fills it is the cost of finding the useful part, not the useful part itself.
- Key claims: Some tools support windows as large as a million tokens, but they still fill faster than developers expect; your question goes in small, then every search match, file path, and line of surrounding text is real tokens sitting in the window — "that's not free"; opening a file loads the whole file (every import, comment, and unrelated piece of code above and below the needed part), and a second file it opened was a wrong guess that still sits in the window, "not getting refunded"; the answer you wanted is one small segment at the very end, so most of what fills the window is exploration, searching, guessing, and over-reading; stretched across a real session (a whole feature over 30 or 40 exchanges), each exchange repeats search → open → sometimes guess wrong → extract, so even a huge window fills — not because the project is large but because exploration is expensive by nature; as the architect, filling up isn't automatically a problem but isn't free, since every wasted segment is space that could have gone to later work, and good structure means fewer wrong guesses and more window left for the real work.
- Learner-relevant: Quantifies why structure and naming pay off in tokens and why the window turns on you; bridges into context rot. Concrete numbers: windows up to 1,000,000 tokens; features over 30–40 exchanges.

### context-rot-quality-slips-before-the-window-fills
- Locator: `[[sources/agentic-engineer/20261014/3. How Coding Agents Work/5. Context Rot： Quality Slips Before The Window Fills (9_11_2026 1：26：48 PM).html#context-rot-quality-slips-before-the-window-fills]]`
- Summary: Explains context rot: measured, repeated degradation of output quality as more tokens enter the context window, beginning well before the window is full. The lesson separates two distinct effects — positional degradation (where information sits) and length degradation (how much surrounds it) — and argues longer context does not mean more reliable results.
- Key claims: In 2025 researchers tested frontier models across context length and all 18 models studied showed the same pattern — as more tokens went in, output quality went down; a model advertising a 200,000-token window can show real, measurable degradation at 50,000 tokens (a quarter of the way in), because the number on the box is the technical ceiling, not where quality starts to slip; positional degradation has a consistent U-shape where information at the very beginning or end is used well and information buried in the middle is used 20 to 30 points worse in controlled tests, which is why a decision stated twenty exchanges ago can feel "lost" though it's still in the window; length degradation is separate — even when important information is placed favorably, accuracy drops as surrounding context grows, with one controlled study showing reasoning accuracy falling from 92% to 68% as input grew from a few hundred to a few thousand tokens, and another finding that when a fact is reworded rather than repeated verbatim, most models tested fall below half their short-context accuracy by around 32,000 tokens; so it's not just "don't bury things in the middle" but also "don't assume more room means more reliable" — length itself has a cost independent of placement.
- Learner-relevant: Motivates resetting strategies and precise prompting. Cited research: (1) Chroma, "Context Rot: How Increasing Input Tokens Impacts LLM Performance" (2025), the 18-model study, `https://www.trychroma.com/research/context-rot`; (2) Liu et al., "Lost in the Middle: How Language Models Use Long Contexts" (2023), the positional U-shape research, `https://arxiv.org/abs/2307.03172`. Concrete numbers: 200,000 vs 50,000 tokens; 20–30 points; 92%→68%; ~32,000 tokens. Next: a second problem that isn't about volume but about what kind of thing is in the window.

### topic-switching-when-unrelated-work-pulls-focus
- Locator: `[[sources/agentic-engineer/20261014/3. How Coding Agents Work/6. Topic Switching： When Unrelated Work Pulls Focus (9_11_2026 1：27：19 PM).html#topic-switching-when-unrelated-work-pulls-focus]]`
- Summary: Covers the case where one session drifts across several unrelated topics instead of staying on one, and why that is worse than several shorter focused sessions. It presents the research behind "contextual distraction," names the day-to-day symptoms, and reframes them as a ratio problem rather than a model-capability problem.
- Key claims: Researchers tested topic switching directly — a model answering correctly 100% of the time when each topic had its own clean context fell to around 75% once eight unrelated topics were folded into one continuously growing conversation, with nothing about the model changing, only how much unrelated material competed for attention; this is named "contextual distraction," the finding that irrelevant earlier material measurably pulls a model's attention away from the current question even when the earlier material is topically related, not just random noise; the practical translation is that a single long session drifting across a bug fix, then a design discussion, then an unrelated feature, then back to the bug is a worse environment than several shorter focused sessions; three recurring patterns are Repeating (a rejected fix proposed again because the earlier rejection now competes with everything since), Forgetting (an early settled decision asked about again, buried and out-competed, not gone), and Contradicting (the same question answered two different ways as grip on earlier reasoning weakens); none of these mean the model got worse — it is exactly as capable in message eighty as message one, what changed is the ratio of competing to relevant context.
- Learner-relevant: Justifies session hygiene and splitting work into focused sessions; feeds directly into the clear-vs-compact decision. Cited research: (1) Coleman et al., "In-context Interference in Chat-based Large Language Models" (2023), the bAbI-based study, `https://arxiv.org/abs/2309.12727`; (2) Huang et al., "Breaking Focus: Contextual Distraction Curse in Large Language Models" (2025), `https://arxiv.org/abs/2502.01609`. Concrete numbers: 100%→~75% accuracy with eight unrelated topics.

### clearing-vs-compacting
- Locator: `[[sources/agentic-engineer/20261014/3. How Coding Agents Work/7. Clearing vs. Compacting.srt#clearing-vs-compacting]]`
- Summary: Distinguishes the two ways to reset a session — clearing and compacting — and argues that picking the wrong one costs more than it should. Clearing wipes the window completely; compacting summarizes the conversation and keeps the summary. The lesson explains the hidden risk in compaction and gives decision rules for each.
- Key claims: Clearing wipes the window completely (empty conversation, nothing carried over, start from zero) while compacting summarizes the current conversation into a condensed version that stays in the window going forward (not empty, but smaller and reshaped); the catch with compacting is that the summary is generated by the model and you don't get to review it before it becomes your new context, so if something important was compressed out or subtly reworded in a meaning-changing way you won't necessarily notice, because the thing that got lost is by definition no longer in front of you to check; clearing has no such risk since there's nothing to lose track of — you know exactly what's in the window (absolutely nothing until you put something there yourself); use clear when starting a genuinely new unrelated task, when the session has drifted and you see repeating/forgetting/contradicting behavior, or when you'd rather restate the two or three facts that matter than trust a summary to have kept them; use compact when you're deep in a long continuous task and stopping to re-explain would cost more time than the risk of a lossy summary, when the conversation history itself has value going forward (e.g. a long design discussion), or when losing the shape of that discussion would hurt more than a slightly imperfect summary; the underlying pattern is that the more the next step depends on precise details from earlier, the more you should lean toward clearing, and the more it depends on general direction and momentum, the more you should compact.
- Learner-relevant: Practical reset decision rules usable in any agent tool; complements context rot/topic switching. No specific tools named; terms: clear, compact.

### tokens-what-costs-what
- Locator: `[[sources/agentic-engineer/20261014/3. How Coding Agents Work/8. Tokens What Costs What.srt#tokens-what-costs-what]]`
- Summary: Makes the context budget concrete by separating what is expensive from what is cheap in token terms. The core rule is "reading is expensive and reasoning is cheap," with reading files, search results, long conversation histories, and verbose output as the expensive items and targeted reasoning, precise questions, and small scoped reads as the cheap ones. It ties the numbers back to naming/structure and the clearing-vs-compacting decision.
- Key claims: Everything the agent reads, writes, and reasons through is measured in tokens, roughly a couple of characters each, so you don't need precise counts — just know which activities burn tokens; reading files is the big one because every file opened is loaded in full (a 300-line file costs roughly 300 lines' worth of tokens whether the agent needed 10 of those lines or all of them); search results are expensive because every grep match, glob result, file path, line number, and surrounding context lands in the window, and a broad search returning dozens of matches is all paid for even when irrelevant; long conversation histories are expensive because every exchange stays until cleared or compacted, so a session with 60 back-and-forth messages carries the token cost of all 60, not just the recent ones; verbose output is expensive because an agent explaining its reasoning at length or returning large code blocks spends tokens on the response itself; the cheap things are short targeted reasoning (the quick in-loop judgment between tool calls — which file next, does this match — not a claim that all reasoning is free, since extended thinking on a hard problem or complex design trade-off can legitimately spend real tokens), precise questions (e.g. "what does the validateSession function do?" costs far less than "explain how authentication works in this project," which forces broader searching and more files opened), and small scoped file reads (a 20-line utility costs a fraction of opening a 400-line file to find the same function); the habit to build is asking, before handing off a task, whether it forces broad or targeted reading — "refactor the payment module" is broad and requires lots of reading first, whereas "update the calculateTax function in the payments file to handle the new rate" knows exactly where to go and is dramatically cheaper because it skips almost all the expensive exploration.
- Learner-relevant: Converts structure and prompt-precision into token economics; supports the clearing-vs-compacting choice and ties the earlier naming lesson to concrete costs. Tool named: Claude Code's `/context` command shows a live breakdown of exactly where tokens are going in the current session and how much free space is left. Concrete numbers/examples: 300-line file; 60-message session; 20-line vs 400-line read; `validateSession`; `calculateTax`; "refactor the payment module."
