- **Architect the Movie Catalog and Cache** — Because the feature is large, it is architected before it is built. The architect asks about scope, matching, staleness, execution, auth, rate limits, and posters, and the learner answers in-flight, using the agent as a sparring partner when torn between inline fetch on cache miss and an ingest job. - `#L1-L137` — `7. Architect the Movie Catalog and Cache.srt` — Invokes `architect movie catalog and cache`; the workflow reads the request as a new feature on the existing stack (web, no UI yet) and starts asking. Scope: the feature must serve the deck plus a title-and-year lookup — fetch and store the 20-film starter deck from real TMDB data plus a reusable lookup that takes a title and year and returns a stored movie row. Matching: when a title-and-year lookup is uncertain, score, accept, else record unmatched. Staleness: refresh on read when stale. Execution: where do TMDB fetches run — job for writes, requests for reads, so reading an already stored movie happens in the request while anything that fetches from TMDB runs as an ingest function, honoring architecture rule 3 and keeping a slow or rate-limited TMDB from holding a page open. The learner hesitates between that and an inline fetch on cache miss or everything in one job.
- `#L138-L340` — `7. Architect the Movie Catalog and Cache.srt` — The learner tells the agent it is unsure between option one and two and asks it to help decide, demonstrating that the agent can be used as a sparring partner. The deciding question is how often a request actually misses; on the design, almost never — the starter deck is pre-stored by the deck job, feature 6 generates a pick in the job and the route just reads stored rows, so a user-facing request hitting an unstored movie is a rare edge case. With the miss path understood as rare, the ingest approach is accepted. Related answers: do not persist the unmatched-title-and-year record at all; 30 days is the staleness threshold; check the local movies table before calling TMDB; keep matching fields (normalized title, original title, IMDb ID, popularity, vote average, vote count) and vibe-search fields (keywords, tagline) but defer presentation fields; track freshness with a dedicated refreshed-at column; keep the checked-in TMDB ID list as the curated starter-deck source; use the v4 access token as a bearer header, plain fetch plus Zod schemas for the client, and install ingest for background jobs; no extra skills or MCP servers needed.
- `#L341-L600` — `7. Architect the Movie Catalog and Cache.srt` — Rate control: TMDB allows roughly 50 requests a second with no daily cap, so ingest concurrency plus retries on 429 is enough. Posters: the feature settles the image question without rendering — keep storing only the poster path, put the image base URL and chosen size in one place in code, and add `image.tmdb.org` to the Next image remote patterns so images can be rendered properly later. Normalization: strip case, accents, punctuation, and leading articles — aggressive enough to cover what a Letterboxd export produces, but not so aggressive that two genuinely different films collapse into one key. Match confidence: weighted title similarity and year distance against one threshold, comparing the normalized title to both the title and original title, taking the better and penalizing year distance. The learner waves off the finer detail as not mattering much and takes the first option. Fetch shape: storing one film costs one search to find candidates plus a single detail call that pulls credits and keywords in the same response.
