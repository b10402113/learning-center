# L1 overview

- **Walkthrough: Prove it Runs** — Sets the stage for the module: the earlier loop (architect interviews you, develop builds from the spec) produced a working app with auth, a dashboard, projects, and a comment-pinning review overlay, but those four features were built and only self-checked. The walkthrough shows a real constraint the agent had already flagged — an iframe cannot load a third-party site because the site's own `X-Frame-Options` / CSP `frame-ancestors` headers refuse framing — so it swaps in a localhost 3000 project by having the agent drop the "must be an absolute URL" validation, then posts a comment and sees it land on the dashboard. Ends by asking you to arrive at this point with uncommitted features and a stale `CLAUDE.md`/`AGENTS.md`.
- **Two Kinds of Proof** — Names the two questions proof answers and the two mechanisms, and why neither replaces the other. Does the feature work today → `/check verify`; will it keep working later → `/test`. Verify is the alpha tier, test is beta: prototype = built and self-checked, alpha = built and proven, beta = built, proven, and protected. The order is verify first, then test, and both work off the same acceptance criteria the architect wrote.
- **Demo: Running check verify** — Runs `/check verify <feature>` against two scope boxes and shows what the skill actually does: it loads the contract (the `specs/<n>-<feature>/verify.md` checklist develop wrote, every step already tied to the criteria it proves), then proves behavior against a live Supabase database with bash, env vars, smoke tests, SQL, and the Supabase MCP — not just a build or a passing test file. Each criterion returns one of four results: met, specced but missing, specced but not applied, or blocked. It produces a PASS/FAIL report with cited evidence and recommends the debug skill for the failures.
- **Demo: Running test** — Turns the one-time proof into lasting protection. `/test` first surveys the existing suite and the scope, then writes tests for a targeted slice (unit tests for invariants and logic, integration for endpoints, rendered component tests for UI), runs `pnpm test`, fixes test mistakes, and flags real bugs the tests catch. Result: 15 passed, 0 failed, plus a test-preferences file so future runs skip straight to writing.

- `#L1-L142` — `2. Two Kinds of Proof.srt` — "Prototype, done" meant the agent built the feature and checked its own work; this module raises the bar by adding proof, and there are two kinds answering two different questions: does the feature work today, and will it keep working later? The first is answered by `/check verify`, which opens the app and tests the feature against its acceptance criteria — not merely whether the code builds or a test file passes, but whether the promised behavior actually happens in the running product. That is the alpha tier. The second is answered by the test skill, because code keeps changing and a future change can quietly break something that worked before; that is how any engineering team protects real software, and it is the beta tier. They do not replace each other: a green test suite does not prove the real feature works, because tests can be incomplete, test the wrong thing, or miss the path a real user takes; and proving the feature works today does not protect it from breaking next month. Hence the order — verify first, then test. Both work from the acceptance criteria the architect wrote: develop builds them, check verify proves them in the running app, and test turns the important ones into lasting protection. Closing ladder: prototype = built and self-checked, alpha = built and proven, beta = built, proven, and protected.
