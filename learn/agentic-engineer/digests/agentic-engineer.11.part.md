# Digest — agentic-engineer (part 11) — Workflow: Ship Something Real (develop, audit, sync, Supabase MCP)

## Overview (L1)
- Demo Planning a Feature with develop — demos the `develop` skill both following the scope's beta workflow in order (architect → develop → check → verify → test) and aiming it directly at unplanned work, showing that the agent stays inside the workflow's design rules while the learner remains in control.
- Demo Running audit — explains why a repo needs a shared instruction file, and demos `/audit` writing a short, evidence-grounded `agents.md` (plus optional nested files) so every later skill inherits the project's real stack, commands, and conventions.
- sync: Understand It, Then Automate It — demos `/sync` at the end of a work session, reconciling `agents.md` and `scope.md` against git-verified changes so the docs stop drifting from the shipped code; the skill is idempotent and safe to run before every merge.
- Install Supabase MCP — a short intermediary lesson on creating a Supabase project linked to a GitHub repo, connecting the Supabase MCP server to Claude Code, authenticating it, then resuming `develop` with database migration access.

## Sections (L2)
### demo-planning-a-feature-with-develop
- Locator: `[[sources/agentic-engineer/20261014/8. Workflow Ship Something Real/9. Demo Planning a Feature with develop.srt#demo-planning-a-feature-with-develop]]`
- Summary: Shows how the `develop` skill is the step after architecting the tech stack. On a greenfield project the first build is the architectural foundation: `develop` reads `scope.md` and a spec's index file (which records the stack decision), then scaffolds a Next.js 16 project with pnpm and TypeScript strict mode using the framework's own initializer. It then demonstrates a second, flexible use: aiming `develop` at work not yet listed in the scope (the home page) by passing a reference image.
- Key claims: The agent installs dependencies just-in-time — only what the first slice needs, not every library named in the architecture spec, so the repo doesn't carry unused dependencies. Before declaring the foundation complete it proves the generated project actually runs (dev server, clean build, or framework checks). When pointed at unplanned work, `develop` recognizes it as interface work, flags the feature as "needs a decision," and offers options; choosing "build now" writes a minimal "assumed" spec capturing the design source and records who proceeded without first documenting architectural decisions (later the git email). It reads the reference image into an entire design system (not a static imitation), including theme, components, and empty/loading/error/disabled states, recording design rules in `design.md` with colors/spacing/types in `globals.css` under the "define each source of truth once" rule.
- Learner-relevant: Teaches two first-class routes for `develop` — the disciplined route (follow the scope in order) and the flexible route (aim it at a screen, screenshot, sentence, or isolated piece of work). Running `scope feature` with no arguments reconciles the plan with the repo's current state rather than pretending the original plan is accurate. Practical limit: `develop` is the heaviest skill in the suite, appropriate for a real shippable screen but excessive for changing a single sentence or adjusting a space value. Concrete commands referenced: `develop`, `architect`, `check`, `verify`, `test`, `scope feature` (no args), `pnpm dev` (localhost 3000); files `scope.md`, `design.md`, `globals.css`, `verify.md`, `package.json`, `example.env`; Next.js 16, pnpm, TypeScript strict.

### demo-running-audit
- Locator: `[[sources/agentic-engineer/20261014/8. Workflow Ship Something Real/10. Demo Running audit.srt#demo-running-audit]]`
- Summary: Argues that a project without shared context forces every future skill to re-study the whole repo or guess conventions differently each session. The `audit` skill solves this by creating or updating the `agents.md` (and `CLAUDE.md`) files — the one file an agent reads before anything else — so every skill starts with a shared understanding of the repo.
- Key claims: `audit` first determines the repository type (e.g. "gap fill" mode when the codebase and a root `agents.md` already exist) because the wrong path changes both the questions asked and the instructions written; the producer of the workflow's "write everything in plain simple language" rule. The generated `agents.md` is deliberately short: it carries the stack, the commands to run the app, the selected conventions, the build approach inherited from the scope, and pointers to deeper context — nothing more. `CLAUDE.md` simply points to `agents.md`, so only one file must be kept updated. The stack comes from the accepted architecture specification while the build approach comes from the living scope; on conflict `audit` reports the difference and names both files rather than silently deciding. Nested `agents.md` files exist only where an area has enough distinct, lasting conventions to justify its own context (e.g. a payments folder with retries/security rules), avoiding loading everything on every message.
- Learner-relevant: Run with `/audit` in a new Claude Code window; it works in gap-fill mode, scans the codebase, and proposes missing content derived from architecture specs, scope, and code found. It can also be re-run to add specific rules or to be asked to choose a coding-style pattern (e.g. functional immutable — recommended; clean architecture; DDD; SOLID + OOP). The root file stays short and global; a long generic `agents.md` can actually make the agent perform worse. Repository instruction files are tool-specific (Claude uses `CLAUDE.md`; Cursor, Copilot, Kiro differ), and using `agents.md` as the main source reduces duplication. Once set up, `develop`, `check`, `test`, and `sync` all read `agents.md` before working.

### sync-understand-it-then-automate-it
- Locator: `[[sources/agentic-engineer/20261014/8. Workflow Ship Something Real/11. sync Understand It Then Automate It.srt#sync-understand-it-then-automate-it]]`
- Locator: `[[sources/agentic-engineer/20261014/8. Workflow Ship Something Real/11. sync： Understand It, Then Automate It (9_11_2026 1：45：40 PM).html#sync-understand-it-then-automate-it]]`
- Summary: Explains documentation drift — code and its guiding files slowly diverge as conventions appear in code but never reach `agents.md`, or a spec says "proposed" after a feature already shipped. The `/sync` skill closes that gap: run at the end of the work, just before merging, it reconciles git-verified changes against `agents.md`, `scope.md`, and specification states.
- Key claims: `/sync` relies on `git diff` and `git log`, so it needs a git repo (in the demo git is initialized first, and on the empty first commit the change set is empty — "nothing to sync"). It reads git file *states* (added, changed, deleted), not just filenames, because each tells a different story about how complete its view is; scope boxes get ticked from implementation, never from a commit message or a model's summary. Docs, tests, config, lockfiles, and generated output are excluded as evidence (a docs-only change produces no reconciliation). It writes policy only when the change showed enough of an area: if every file in a folder was newly added it can describe that folder's conventions; if even one was merely modified, it writes nothing so a single implementation detail isn't mistaken for a lasting rule. "Context is what happened in this change; policy is what should always happen from now on."
- Learner-relevant: The loop order is architect → develop → (clear session) → sync; `/sync` is super lightweight, safe to run every single time, idempotent (a second run on an unchanged project does nothing), and prefers no change while reporting anything needing judgement. At higher tiers it also reconciles verification, testing, and review steps and reports features built before their required decisions existed as work still owed. The HTML adds the heading structure and rationale sections: "The evidence rule," "When to run it" (before every merge; after several features shipped quickly; after work continued across cleared sessions), "More surfaces at higher tiers," and "Why it's narrow on purpose." Demo details: after git init + first commit (`.gitignore` properly excludes node_modules), re-running `/audit` added pnpm lint to `agents.md`; a homepage card-height UI fix and two changes (`agents.md`, `scope.md`) gave sync something to reconcile, marking "stack and architecture" done in both the scope and the plan.

### install-supabase-mcp
- Locator: `[[sources/agentic-engineer/20261014/8. Workflow Ship Something Real/12. Install Supabase MCP.srt#install-supabase-mcp]]`
- Summary: A short intermediary lesson recorded while developing the data model. When `develop` asked whether to add Supabase ENV values or connect the MCP, the author chose to connect the MCP immediately; the lesson shows that setup and then how the resumed `develop` build gains database migration access.
- Key claims: `develop` itself recognized it needed to pause and asked the user which path to take, then told the user to re-run `develop data model` after connecting the MCP ("I'll pick up the build"). The Supabase project should be linked to a GitHub repo so the agent's code is tracked; a new database password must be saved and not lost. The Supabase MCP server is configured for Claude Code by copying the server command from the Supabase docs and pasting it into the terminal to add an HTTP MCP server (platform-hosted project, selecting the specific project and access). Authentication requires running Claude and using `/mcp` (just pressing enter to authenticate Supabase), authorizing Claude Code; the extension's MCP-servers search may error ("resource must be a valid MCP endpoint"), so the terminal `/mcp` path is shown working. After reloading, Supabase shows as connected, and `develop data model` can then run migrations on its own.
- Learner-relevant: Concrete setup steps — create a Supabase project named e.g. `client feedback app agentic` (public repo), push code to GitHub, add the Supabase MCP server command in the terminal, run `/mcp` to authenticate, reload the Claude window to confirm the connected status. With MCP access, `develop` handles data-model migrations more smoothly and precisely. The lesson closes by directing the learner to continue architecting/developing a few more features (the data model, the design system and UI, then the first real slice) before moving to the next module of agentic engineering skills.
