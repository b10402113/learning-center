# /architect：把 Load-bearing 決定寫成 Spec

## Learning goal

跑 /architect，用一輪一輪帶建議選項的決策訪談，把 load-bearing 決定寫成 docs/specs 的 spec（index／rationale／verify），並用第二個模型 cross-check。

## Steps

1. [[learn/agentic-engineer/nodes/skill-architect/architect-role-and-rule|/architect 是什麼：一輪一個 load-bearing 決定，寫成可驗的 spec]] — 認出這個 skill 的職責、唯一規則與在 workflow 的位置
2. [[learn/agentic-engineer/nodes/skill-architect/run-the-decision-interview|跑一場決策訪談：先榨乾 repo，再一問一維度]] — 走完先讀後問、一問一維度、每題帶建議的訪談流程（after step 1）
3. [[learn/agentic-engineer/nodes/skill-architect/read-the-spec-artifact|讀懂 /architect 寫出的 spec：形狀、section、狀態與 Assumed]] — 看懂 index／rationale／verify 的形狀與 Status 生命週期（after step 2）
4. [[learn/agentic-engineer/nodes/skill-architect/judge-the-architect-run|判斷這場 architect run 好不好：三個傾向與第二個模型]] — 用三個 LLM 傾向與 self-check 驗收一場 run，並決定何時 cross-check（after step 3）

## Lesson

`/scope` 交出一份 what-to-build 的計畫，但計畫裡沒有工具、平台、資料模型——那些是 load-bearing 決定，任何一個選錯，後面的程式碼就長在錯的地基上。`/architect` 就是那個把地基先談清楚、再寫下來的 skill：它一次只解決一個決定，透過一輪一輪的決策訪談，把決定寫成 `docs/specs/` 裡的 build spec。

這一課的四步就是這個 skill 的完整形狀：先搞懂它是什麼、唯一規則是什麼（一輪一個決定，不是清 backlog，而且 spec 是 `/develop` 建置、`/check verify` 驗收共同指向的契約）；再實際跑一場訪談，看它如何先讀 scope／specs／`AGENTS.md`／git 把能自己答的答案榨乾，才把問題花在你身上，並在每題附上一個建議選項與可信的 runner-up；接著讀懂它落地的產物——單檔與 directory（`index.md`／`rationale.md`／`verify.md`）的形狀規則、AC 編號與 Status 生命週期，以及 `Assumed` 這個「先做、之後再 ratification」的逃生口；最後學會驗收——三個 LLM 傾向會把產品推離你的本意，第二個模型則負責抓作者模型看不見的洞，而 reviewer 永遠不會默默補上缺的決定。

走完之後，你應該能在自己的專案上跑一次 `/architect`，判斷這場 run 到底好在哪、哪裡只是「看起來很完整」。
