# 除錯方法：三種壞法與科學方法

## Learning goal

用「這是哪一種壞」分流，並對一般 code bug 套用 observe→hypothesize→test 的科學方法、一次只改一件事。

## Steps

1. [[learn/agentic-engineer/nodes/debug-method/three-kinds-of-broken|三種壞法：先問「這是哪一種壞」]] — 認出三種壞法各自長什麼樣，並守住「無法解釋的修好等於沒抓到 bug」這條規則
2. [[learn/agentic-engineer/nodes/debug-method/triage-which-kind|分流：認出是哪一種壞，選對回應]] — 用徵兆判斷是哪一種壞、選出對應的回應，並說出選錯的代價（after step 1）
3. [[learn/agentic-engineer/nodes/debug-method/scientific-method-for-bugs|一般 code bug 的科學方法：observe → hypothesize → test]] — 對可重現的一般 bug 一次只改一件事，讓證據決定下一步（after step 2）
4. [[learn/agentic-engineer/nodes/debug-method/run-debug-skill|實跑 debug skill：餵它三件事、一次一個假設]] — 餵它觀察／預期／重現，盯它只下一個假設，用「修得夠小」判斷是否真的找到根因（after step 3）

## Lesson

東西壞掉時，多數人的第一反應是直接跳進修法——改到錯誤消失為止。這個節點要先把這一步擋下來：真正有用的第一個動作不是技巧，而是一個問題——**「這是哪一種壞？」**。同一個錯誤訊息背後可能是三種完全不同的處境：一段誰寫都一樣、可以重現的普通 code bug；一個 AI 特有的失敗（呼叫不存在的函式、看似正確卻悄悄算錯、中途替你做了決定、漏掉邊界情況，或只有真實資料才會爆）；以及 agent 自己迷失了路徑（原地重複、來回改同一批檔案、越改越糟，卻始終很有自信）。三種要的回應完全不同，用錯方法的代價也不一樣。

把「是哪一種」分流清楚之後，這個節點只先深入第一種——一般 code bug——的解法：把科學方法套到壞掉的程式上，observe → hypothesize → test，讓證據決定下一步，而且**一次只改一件事**，這樣每個結果都能教你一點東西。除錯不是「改到錯誤不見」，那是所有人都會做、也正是 bug 會回頭的原因。最後一個步驟把這套方法落到實際操作：跑 debug skill，一開始就餵它觀察到什麼、預期什麼、怎麼重現這三件事，過程中盯著它一次只下一個假設，並用「修得夠小」當作真的找到根因的訊號，而不是用「紅燈變綠燈」當作成功。

貫穿這個節點的是同一條規則：**你無法解釋的修好，就是還沒抓到的 bug**。錯誤消失、你卻說不出它為什麼發生，那就沒有證明原因已經被移除——你只是把症狀藏起來、搬到別處，或讓程式暫時碰不到它。debug skill 可以把重現、定位、測試、修復、保護做得比你快，但它無法替你判斷「這是否真的證明了原因」，那個判斷是你的。這也是為什麼方法要留在你身上——skill 只是更快套用它的方式。
