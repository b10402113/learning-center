# 像團隊一樣交付：check review 與 document

## Learning goal

用不同模型跑 check review 拿到第二個視角，並用 /document 從 diff／spec／review／tests 產出 PR／changelog／release-note／postmortem。

## Steps

1. [[learn/agentic-engineer/nodes/ship-it-like-a-team/why-a-second-mind|為什麼需要第二個視角：GA tier 的獨立 review]] — 認出「同一個模型建、測、又自審」的缺口，以及為什麼換更強的同款模型不算解法
2. [[learn/agentic-engineer/nodes/ship-it-like-a-team/run-check-review|跑一次 check review：換模型、讀全檔、拿 findings]] — 作者模型判定、一句確認、唯讀 reviewer 讀 diff 加全檔（after step 1）
3. [[learn/agentic-engineer/nodes/ship-it-like-a-team/document-four-inputs|/document 為什麼讀四份材料：讓理由與風險從磁碟來]] — 四輸入對應四個問題、code beats commit message、不編造（after step 2）
4. [[learn/agentic-engineer/nodes/ship-it-like-a-team/choose-document-type|選文件類型：PR／changelog／release-note／postmortem]] — 用讀者與場合挑型，並說出每型的開頭（after step 3）
5. [[learn/agentic-engineer/nodes/ship-it-like-a-team/run-document|跑一次 /document：PR body、何時跑、只寫 prose]] — PR body 結構與邊界：推前先問、不 commit／push／merge（after step 4）

## Lesson

交到 GA tier 之後，剩下一個每個人都會中的問題：同一個模型把功能寫出來、自己測過、又自己當評審，於是同一個誤解會一路穿過建置、驗證、測試而不被發現。這一節的兩支 skill 就是工程團隊早就行之有年、只是換成模型來做的兩件事——**找一個沒寫過這段碼的人來 review**，以及**為這個變更留下一份會跟著走的紀錄**。

`check review` 把已經建置、驗證、測試過的碼交給另一個不曾參與撰寫的模型，它不重跑流程（`check verify` 已經證明行為、`test` 已經保護它），只判斷「這東西是怎麼被造出來的」：設計合不合理、安不安全、好不好維護、有沒有 spec 與測試都沒抓到的安全風險、下一個開發者看不看得懂。它先讀專案設定判斷作者模型，問一句確認，再換一個唯讀的模型讀 diff 與全檔，回一份排好序的 findings。`/document` 則是它的天然搭檔：一份寫清楚故事的 PR 描述，讓 reviewer 在打開檔案前就信任這個變更。它從四個輸入取材料——commits 與 diff 講「改了什麼」、spec 講「為什麼存在」、review findings 講「風險在哪」、tests 講「怎麼檢查」——而 PR 描述最難的兩塊（理由與風險）早已寫在磁碟上，不必一週後靠記憶重建。誠實是它的紀律：程式碼優先於 commit message、不編造一個沒人量過的數字或一段沒發生的時間線，文件因此比想像中平淡，卻是真的。

走完之後，你應該能在自己的專案上：換一個模型對某個功能跑一次 `check review` 並讀懂它的發現，再依場合用 `/document` 產出 PR 描述、changelog、release note 或 postmortem。
