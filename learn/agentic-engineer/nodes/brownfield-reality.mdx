# 沒有白紙：Brownfield 的風險

## Learning goal

說出 agent 在舊碼庫為什麼會失敗（沒有地圖）與兩個風險方向，並用 workflow 的「先理解、再安全地改」兩步對應。

## Steps

1. [[learn/agentic-engineer/nodes/brownfield-reality/why-agents-fail-on-legacy|agent 為什麼在舊碼庫失手]] — 改別人寫的舊系統才是常態，agent 失手的根因是它只有 what、沒有 why
2. [[learn/agentic-engineer/nodes/brownfield-reality/two-risk-directions|兩個風險方向]] — agent 放進專案的東西 vs 你交給 agent 的東西，這是商業與安全決策（after step 1）
3. [[learn/agentic-engineer/nodes/brownfield-reality/workflow-understand-then-change|把 workflow 對上問題]] — /audit、/architect、/develop、/check verify、/check review 如何拼成「先理解、再安全地改」（after steps 1–2）
4. [[learn/agentic-engineer/nodes/brownfield-reality/who-decides-what-leaves|誰決定什麼能離開公司]] — workflow 治「agent 怎麼工作」，設定與政策治「什麼離開組織」（after steps 2–3）

## Lesson

真實的工程很少有白紙。你多半是加入一個兩年前就開始、作者早就離職、而且真的有人在用的系統，接著改它——新增下一個功能、修一個沒人敢碰的 bug。這正是很多人拿 AI 來試、結果失望、於是下結論「它做不了真軟體」的地方。會失手不是因為模型不會寫程式，而是因為**它沒有地圖**：它能讀出程式碼「寫了什麼」，卻讀不出「為什麼存在」——為什麼同一個服務有三個版本、為什麼某一行看起來沒用的程式碼其實在擋一個正式環境的故障。少了這層脈絡，agent 只能猜；而它猜得往往很乾淨、很有自信，卻違反了一條專案依賴多年的規則。

風險有兩個方向。一個是 **agent 放進專案裡的東西**：不安全的程式碼、外洩的密鑰、被放寬的存取規則、沒被批准的關鍵決定。另一個是**你交給 agent 的東西**：原始碼、憑證、客戶資料、私有商業邏輯離開組織。所以「在舊碼庫上用 AI」不只是寫程式的決定，它同時是商業與安全的決定。

這門課的 workflow 就是對這個問題的控制系統，工作順序只有兩步：**先理解，再安全地改**。`/audit` 先建出那張缺失的地圖，`/architect` 在決定之前先讀現況，`/develop` 先讀再寫、沿用既有模式，`/check verify` 在真實 App 內證明改動沒有破壞行為，`/check review` 交給第二個模型抓作者漏掉的東西。但有一條線 workflow 自己跨不過去：它管的是「agent 怎麼工作」，至於**哪些公司資訊可以讓模型看見**，取決於供應商、帳號設定、公司政策與安全要求——那是你的設定與政策在管，不是 workflow 在管。
