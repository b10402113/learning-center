# 在舊碼庫裡工作：先 audit，再最小變更

## Learning goal

在一個真實舊專案上跑 /audit 建地圖，再用 /scope→/architect→/develop 做一個最小安全變更，並記住地圖是證據不是真相。

## Steps

1. [[learn/agentic-engineer/nodes/working-in-legacy-code/audit-builds-the-map|在成熟舊專案上跑 /audit：它怎麼建出一張地圖]] — 認出整庫掃描的路由與 root／nested 地圖的內容
2. [[learn/agentic-engineer/nodes/working-in-legacy-code/map-is-evidence-not-truth|地圖是證據不是真相：動手前先驗證它]] — 用讀、跑一個指令、檢查漏掉慣例來驗地圖（after step 1）
3. [[learn/agentic-engineer/nodes/working-in-legacy-code/scope-and-architect-on-existing-code|用 /scope 與 /architect 規劃最小變更：先讀現況再決定]] — 讀地圖與現有實作後才決定變更落點（after step 2）
4. [[learn/agentic-engineer/nodes/working-in-legacy-code/develop-the-minimal-safe-change|用 /develop 下手：跟著既有模式改，只動該動的地方]] — 沿用既有模式、換路徑前搜尋引用、做出最小成果（after step 3）
5. [[learn/agentic-engineer/nodes/working-in-legacy-code/verify-and-work-across-sessions|收尾：check verify／review 與跨 session 的節奏]] — 選對證明方式、clear 時機與跳過 /scope 的條件（after step 4）

## Lesson

在舊碼庫裡工作，跟在一片空白上開新專案是兩件不同的事。真實的公司工作，多半是改別人寫的、使用者正在依賴的程式碼；這裡也是最多人試了 AI、拿到差結果、就下結論「它處理不了真軟體」的地方。問題不在模型，而在 agent 手上沒有地圖：它讀得到程式碼「寫了什麼」，卻讀不出「為什麼存在」——為什麼同一個服務有三個版本、為什麼某一行看起來多餘卻在擋一個線上事故。少了這些，它只能猜，而且可能猜得很乾淨、很自信，卻打破了專案依賴多年的規則。

這個節點用兩個真實 demo（在 BookWise 這個兩年多的大學圖書館專案上操作）走完「先理解、再安全地改」：第一步用 `/audit` 對一個已成熟的 repo 建出地圖——因為專案已經有結構、migration 與 auth，它不再問慣例問題，而是整庫掃描，寫出 root `AGENTS.md` 與 `CLAUDE.md` 指標，只在真正有自己慣例的區域（這裡是 `database` 與 `app`）放 nested 檔，並記下新人第一天會被交代的東西：stack、每天要跑的指令、程式碼遵循的模式，以及那些不講就會踩到的細節。

但地圖不是真相，是證據。第二步是動手前的人為驗證：把生成的地圖對著實際專案讀一遍、確認 stack 正確、至少跑一個指令證明它真的能用、檢查有沒有漏掉看得見的慣例或給了一個程式碼支撐不起來的理由。接著才是變更本身——用同一套熟悉的 `/scope → /architect → /develop`，只是這次它們的行為變了：`/scope` 先讀 audit 產出的地圖，把「還書」這個 slice 規劃成 existing／planned／deferred 並寫進 `docs/scope.md`；`/architect` 不再從零提議，而是先讀功能現在怎麼運作、把請求追過現有檔案、查誰依賴它，才決定變更該落在哪裡，並且不因為一時看不懂就拆掉既有行為；`/develop` 讀周邊檔案、沿用既有模式與工具、換路徑前先搜尋所有引用，把變更收在 spec 邊界內。

走完之後，你應該能在一個陌生、別人寫的、正在被使用的專案上，先建地圖、驗證地圖，再用最小的安全變更交出一刀——這個 demo 的結果是一個不必 migration、只動四個檔案的還書功能。最後一步把收尾也講清楚：用 `check verify`（今天能不能跑）與 `check review`（換一個模型給你第二個視角）證明它沒破壞既有行為，拿捏 skill 之間 `clear` 的時機，並判斷什麼情況一個小修正可以跳過 `/scope` 直接進 `/develop`。
