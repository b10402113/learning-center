# 實跑 check verify 與 test

## Learning goal

實跑 check verify 對照 verify.md 的驗收條件找出真 bug，再跑 test 把一次性驗證變成回歸保護。

## Steps

1. [[learn/agentic-engineer/nodes/check-verify-and-test/check-verify-contract|check verify 讀什麼：verify.md 合約與四種判定]] — 認出驗收合約的來源、四種判定與證據閘門
2. [[learn/agentic-engineer/nodes/check-verify-and-test/run-check-verify|跑一次 check verify：在真 App 上對驗收條件找真 bug]] — 跑 `check verify <feature>`、讀報告、把失敗分流到 /debug（after step 1）
3. [[learn/agentic-engineer/nodes/check-verify-and-test/test-skill-scoping|test 掃什麼：branch 變更、檔案分類與 AC 追溯]] — 看懂 test 的 git 範圍、檔案分類策略與拒絕上鎖規則（after step 2）
4. [[learn/agentic-engineer/nodes/check-verify-and-test/run-test-to-green|跑一次 test：把一次性驗證變成回歸保護]] — 跑 `test`／`test <feature>`、寫測試補到 green、存下 test-preferences.json（after step 3）

## Lesson

前面的章節把功能做出來了，但「建好了」不等於「證明它會跑」。這一課是兩種證明的實作面：`check verify` 負責證明這功能**今天真的能跑**，`test` 負責把它變成**以後還會不會跑**的回歸保護。順序固定是先 verify、後 test——先用真 App 對照驗收條件抓到真 bug，再把該守住的行為寫成測試。

`check verify` 不是「跑跑看測試有沒有綠」。它會讀 `develop` 留下的驗收合約 `verify.md`：那份 checklist 把 spec 的每一條驗收條件（`AC-N`）連到一個可觀察的行為，skill 就照著它開真的 App、觀察真結果，每一條只給 met／specced but missing／specced but not applied／blocked 四種判定之一。它的鐵律是「沒有證據就不打勾」——所以一條沒被套用的 migration，就算測試全綠也照樣讓整個功能過不了。判定是 blocked 還是 met，取決於你給它多少工具（browser、database、MCP），這也是為什麼同一份合約在不同環境跑出來的把握程度不一樣。

`test` 接手把一次性的驗證沉澱成耐久資產。它只掃這條 branch 上還沒 commit 的變更，依檔案類型（component／page-flow／api-server／logic／cli）挑對應的測試策略，把該守住的條件追回到 `AC-N`，並拒絕替 scaffolding 這種會一直變的東西寫測試上鎖。跑的時候可以直接測全部、指定某個 spec，或縮到某個 feature；第一次跑會問清楚技術棧，把選擇寫進 `test-preferences.json`，下次就直接進寫測試。

走完這一課，你應該能在自己的專案上，用 `check verify` 把一個功能證明到能交出去，再用 `test` 讓它在之後的每次改動裡都被保護住。
