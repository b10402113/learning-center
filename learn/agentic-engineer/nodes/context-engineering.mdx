# Context Engineering：Always-on／On-demand／Reference

## Learning goal

把 always-on／on-demand／reference 三種 context 分清楚，並寫出一個夠小、每次 session 都付得起的 AGENTS.md（知道 Claude Code 只讀 CLAUDE.md、要靠 import 帶進 AGENTS.md）。

## Steps

1. [[learn/agentic-engineer/nodes/context-engineering/context-not-prompt|真正的槓桿是 Context Engineering，不是 Prompt Engineering]] — prompt 不是重點，它落點的環境才是
2. [[learn/agentic-engineer/nodes/context-engineering/three-types-of-context|三種 Context：Always-on、On-demand、Reference]] — 用成本節奏區分三種 context（after step 1）
3. [[learn/agentic-engineer/nodes/context-engineering/how-always-on-loads|Always-on 檔案怎麼載入：CLAUDE.md、AGENTS.md 與 import]] — 搞懂 exploration 與保證的差別、Claude Code 只讀一個檔（after step 2）
4. [[learn/agentic-engineer/nodes/context-engineering/what-earns-always-on|什麼才配放進 Always-on？一個判準與九份文件的教訓]] — 用一個問句決定規則該放哪裡（after steps 2–3）
5. [[learn/agentic-engineer/nodes/context-engineering/write-a-small-agents-md|親手寫一個夠小的 AGENTS.md]] — 在真專案上寫一份每次 session 都付得起的 always-on 檔（after steps 3–4）

## Lesson

前面幾課已經把 agent 的「機器」看清楚了：它怎麼跑迴圈、怎麼在你的程式庫裡找路、它的 context window 為什麼會滿、以及 context 品質為什麼在填滿視窗之前就開始劣化（context rot）。這一課回到最源頭的那個根因——「沒有真的 context」——並且直接修它。

多數人在輸出變差時的第一個反應，是把 prompt 寫得更漂亮。但 prompt 並不是落在真空裡，它是落在 agent 當下已經載入的一切之上。同樣的模型、同樣一句話，放進不同的 context 就會得到完全不同的結果；所以真正的槓桿不在那一行字，而在你事先決定「它會知道什麼」。這就是 context engineering：不是措辭，是設計，是系統架構。

要設計，就得先把專案的 context 分成三種。always-on 每個 session 都付錢、on-demand 是它自己伸手去拿、reference 是被明確指到才進來；三者只差一個東西——成本節奏。因為 always-on 每次都要付，它必須小到「只放每個任務都成立、絕不能錯的規則」。而要知道哪些檔真的進了這條保證通道，不能憑感覺，要用 `/context` 和 `/memory` 去看。

這一課的五步就是這個順序：先建立「context 才是槓桿」的觀念，再分清三種類型與成本節奏，接著搞懂 always-on 檔案的載入機制（Claude Code 只讀 `CLAUDE.md`，`AGENTS.md` 要靠 import），學會一條規則該放哪裡的判準，最後親手寫出一份夠小的 `AGENTS.md`。
