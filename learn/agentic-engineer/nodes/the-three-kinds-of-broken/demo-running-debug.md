# Demo：跑一次 /debug

六步都學會了，skill 也照著跑了，這一課只談一件事：怎麼把它用得漂亮。開頭要提供什麼、過程中要留意什麼、結束後要如何驗收——這三件事，決定一場調查是迅速收斂，還是拖著你一起繞圈子。

## 開頭提供三項資訊：observed、expected、repro

直接執行 `/debug`，它會先要求你提供 bug 的細節，才開始調查。整場調查是快是慢，往往取決於你一開始提供了什麼。

這三項資訊是：你觀察到什麼、原本預期會發生什麼，以及重現問題所需的步驟。提供這些資訊後，它就能開始調查。

<!--image:1-->

只說「這壞了」，它就得停下來向你索取證據；這往往就是調查快慢的全部差別。如果它無法重現問題，就會先停下來，加入 instrumentation，讓自己能夠重現，接著告訴你目前的推測。

這三項輸入不是表格欄位，而是讓第一個實驗一開始就有意義的必要條件。

## 這次的三項輸入由 `/check verify` 提供

前一個 check verify data model 的 session 找到了確實需要修正的問題，因此它已經掌握所有資訊，只要接著執行 debug 即可。

這次你不必另外提供那三項資訊，因為它會從上面的 check verification 中取得。

但如果你是自行執行，手邊沒有 verification 提供材料，就必須描述得非常精確：不要只說「database 有問題」，而要具體到足以讓下一個實驗驗證它對不對。verify 的失敗結果已經包含 observed 與 repro，你只要把那項證據指給 `/debug` 看，不必再用自己的話重述一遍。

不要重複敘述檔案裡已有的證據；把它指向證據所在的位置。

## 過程中只盯一件事：它是否一次只驗證一個假設

接著，你必須確實 review 它的工作。

要留意的是它一次只驗證一個假設。如果你看到 agent 同時改動好幾個無關項目，只希望藉此讓錯誤消失，就立刻停下來。一次只做一個實驗，才能一次只取得一份有用資訊。確認假設之後，它才能開始修正。

<!--image:2-->

如果 diff 裡同時出現時區、排序和快取三類改動，那就不是調查，而是 shotgun。停下來，要求它明確說出目前要驗證的假設。

一次只驗證一個假設，不是風格偏好，而是讓每個結果都有意義的必要條件。

## 修正幅度是事後判準：一個 `.env` 檔名的例子

你可以從修正幅度判斷方向是否正確。多數時候，修正會非常小，而且能直接對應到找到的根因。

這次的根因是 `.env` 從來沒有被載入。Smoke test 匯入 dotenv config，而它只會讀取一個檔名剛好是 `.env` 的檔案。但 secrets 放在 `.env.local`，database URL 也在其中。`.env` 的值一直是空的，因此七個 test 每次執行時都沒有失敗訊號。

修正方式是讓 smoke tests 明確載入 `.env`。現在可以重新執行，整個 suite 也會正常跑完。我們知道修正有效，因為改動只有一行。

一個檔案、一行載入 `.env`，就能解釋「七個 test 都沒有失敗訊號」這個症狀。修正小到足以完整說明問題，才算真正找到根因。

## Vibe debugging 與 `/debug` 的差別，以及驗收時要問的那一句

這就是這個 skill 和「直接叫 agent 盲目修錯」之間的差別。

一般的修 bug prompt 會鼓勵它不斷改動，直到紅燈變綠。有時候它確實會成功，但你結束時仍然說不出問題出在哪裡。這就是 vibe debugging。

Debug 要求的是 reproduction、one hypothesis、evidence、minimal fix，最後再加上 regression test。它的優勢不在於步數最少，而在於你能解釋結果為什麼有效。

Review 的原則承襲自第一課：不要接受自己無法解釋的修正。

兩份 diff 都能讓 test 變綠：vibe debugging 的版本，結束時你說不出問題出在哪裡；`/debug` 的版本，結束時你能指出 root cause、那一行修正，以及用來防止問題重現的 regression test。

驗收時只問一句：你能不能解釋這個修正為什麼能消除根因？如果不能，就代表問題還沒真正查清楚。

如果那段 code 是 agent 寫的，還有另一層工作——你並不掌握它的 intent，必須回到第二課把它釐清。這個 node 到此告一段落。下一次 `/check verify` 紅掉時，先問「這是哪一種錯誤」，再決定是否要把 observed／expected／repro 交給 `/debug`。
