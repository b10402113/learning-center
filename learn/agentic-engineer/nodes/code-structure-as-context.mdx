# 程式結構即 Context

## Learning goal

用檔案大小、可預測命名與 colocation 三個結構選擇，降低 agent 每次讀取的固定 context 成本。

## Steps

1. [[learn/agentic-engineer/nodes/code-structure-as-context/code-is-context|你的程式碼就是 context]] — 為什麼每次 agent 讀你的原始碼，都是在付 context 的錢
2. [[learn/agentic-engineer/nodes/code-structure-as-context/file-size-as-context-cost|檔案大小就是 context 成本]] — 大檔案把不相關的程式碼一起拖進 window（after step 1）
3. [[learn/agentic-engineer/nodes/code-structure-as-context/naming-and-colocation|可預測命名與 colocation：把尋寶變成一次讀取]] — 命名決定搜尋成本，colocation 決定要讀幾個鄰居（after step 1）
4. [[learn/agentic-engineer/nodes/code-structure-as-context/structure-as-standing-cost|結構是每次 session 都在付的固定成本]] — 用一句檢查問句，判斷一個結構提案值不值得接受（after steps 2–3）

## Lesson

前面幾節講的 context，大多是「你主動餵給 agent」的東西：always-on 的簡報、按需求抓的檔案、被指到的規格與文件。這一節要補上最後一種、也是最容易被忽略的一種 context——你的程式碼本身。

每當 agent 要改一個功能，它就得讀你的原始碼：檔案、函式、資料夾結構。這些讀進去的東西，跟其他任何 context 一樣，都要佔 window、都要付 token。也就是說，程式碼的結構不只是「整潔工程」的品味問題，它直接決定 agent 的 context 是便宜還是昂貴、它要一次讀到還是讀十次。

這一節把「結構即 context 成本」拆成三個可以下手的選擇：檔案大小、可預測的命名與位置、以及 colocation（把會一起改的東西放在一起）。三個講完，最後收成一個心態——結構是每次 session 都在付的固定成本，不是付一次就好——並給你一句可以當場用的檢查問句。
