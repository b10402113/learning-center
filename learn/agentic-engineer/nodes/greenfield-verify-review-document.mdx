# Greenfield：Verify、Review、Document

## Learning goal

對資料模型跑 check verify、check review（換模型）、document，走完一次完整交付。

## Steps

1. [[learn/agentic-engineer/nodes/greenfield-verify-review-document/check-verify-data-model|對資料模型跑 check verify]] — 讀 verify.md 的驗收清單、解開缺 .env.local 的阻塞、把 11 條 acceptance criteria 全部跑過
2. [[learn/agentic-engineer/nodes/greenfield-verify-review-document/check-review-data-model|換模型跑 check review]] — 判定作者模型、換一個唯讀模型讀全檔、找到一個 major 與四個 minor 並用新 migration 修（after step 1）
3. [[learn/agentic-engineer/nodes/greenfield-verify-review-document/document-data-model|用 document 產出交付紀錄（PR）]] — 選對文件類型、從 branch commits 與 diff 組 PR body、commit／開 PR／merge（after step 2）
4. [[learn/agentic-engineer/nodes/greenfield-verify-review-document/architect-catalog-cache|為 movie catalog 與 cache 跑 architect]] — 走完決策訪談、把 matching／cache／rate limit 寫成 spec、確認 16 條 acceptance criteria 對得上（after step 3）

## Lesson

資料模型寫完、對 live DB 驗過之後，Greenfield 這條路線還差最後一哩：把它當成一次真正的交付走完。這一節的四步就是同一份碼在「驗證 → 審查 → 交付紀錄 → 下一個功能的設計」上被四支不同 skill 依序推過一遍，每一步都把上一階段留下的狀態交給下一支 skill。

第一段是 `check verify`：就算功能早就 develop 完，`verify.md` 裡的 checkboxes 還沒全部打勾就不算數。它讀 verify.md、發現缺 `.env.local` 卡住了 migrate／seed／跑 app，於是用 Supabase MCP 把公開變數填上、把帶密碼的連線字串留給人，最後跑出 11 條 acceptance criteria 全數通過、零 unexercised、零 blocker、零 fail。

第二段是 `check review`：驗證證明「今天會跑」，review 問的卻是「這東西是怎麼被造出來的」。它先從專案設定判斷作者模型（不是問當前模型，那會過時），再換一個沒參與撰寫的唯讀模型讀 diff 加全檔。這一輪在 37 個檔案裡挑出一個 major（ratings schema 沒有 DB constraint 把 score 的可為空性綁在 state 上）與四個 minor；修法是新增一筆 migration，而不是回頭改舊的 `000`——因為 migrator 依 timestamp 判斷，改了不會重跑，等於偷偷讓狀態對不上。

第三段是 `document`：把 branch 上的 commits 與 diff 交給 skill，選 PR description，讓它組出「實作了什麼／設計理由／驗證紀錄／串接方式／怎麼測／給 reviewer 的提醒」的 PR body，再 commit、開 PR、merge 進 main。第四段則是把鏡頭轉到下一個功能：對 movie catalog 與 cache 跑 `architect`，用一輪帶建議選項的決策訪談把 matching 演算法、永久存 row 而非快取、30 天 staleness、TMDB 授權與 rate limit 等決定寫成 spec，並確認 16 條 acceptance criteria 全部對得上。

走完之後，你應該能在自己的 greenfield 專案上，把一個剛寫完的功能依序用 `check verify`、`check review`、`document` 交付出去，再直接用 `architect` 接下一個功能的設計。
