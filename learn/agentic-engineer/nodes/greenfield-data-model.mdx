# Greenfield：設計資料模型

## Learning goal

跑 architect data model，在 full target model 與 thin thread 之間選定、寫出九表遷移，處理 ownership 與 RLS，並對 live DB 驗證。

## Steps

1. [[learn/agentic-engineer/nodes/greenfield-data-model/data-model-as-spec|資料模型即 Spec：architect data model 產出什麼]] — 只產出設計／規格，以及「完成」的判準
2. [[learn/agentic-engineer/nodes/greenfield-data-model/full-target-vs-thin-thread|完整目標模型 vs Thin Thread]] — 一次設計完整目標、遷移切片落地（after step 1）
3. [[learn/agentic-engineer/nodes/greenfield-data-model/entity-and-taste-model|實體與 Taste 模型：taste_vectors、ratings、profiles 與九表]] — 儲存形狀與九表情境、cold start 與 auth trigger（after step 2）
4. [[learn/agentic-engineer/nodes/greenfield-data-model/ownership-and-rls|Ownership 與 RLS：scoped query helper 自己套用 user ID]] — rule one、typed registry、RLS deny-all（after step 3）
5. [[learn/agentic-engineer/nodes/greenfield-data-model/schema-artifacts|Schema 產物：一檔一表、enums 與 movie 身分]] — 實際 schema 的排版與欄位決定（after step 3）
6. [[learn/agentic-engineer/nodes/greenfield-data-model/cross-check-and-live-verification|Cross-check 與對 live DB 驗證]] — 第二模型 cross-check、Supabase MCP、遷移套用並用驗收條件證明（after steps 4–5）

## Lesson

資料模型是整個 app 其餘部分站上去的地基，所以這一課刻意**先規格、後實作**：`architect data model` 這一輪只產出設計——需求、決策與理由、資料模型草圖、關聯、欄位、enum 與 build plan——真正的建置留給 `develop`。判斷「完成」的標準不是表格長得漂亮，而是**實體與關聯能不能承載兩條 onboarding 路徑（swipe 與 Letterboxd 匯入）的評分、存下一個 taste profile、並在之後不破壞 schema 的前提下產生帶理由的 picks**。

地基一旦打歪，代價是之後每個功能都要遷移。所以這一課的核心張力是「現在設計多少」：是只做 tracer bullet 需要的實體，還是把 11 個功能都需要的**完整目標模型**一次設計完、再讓遷移切片上線。選定之後，剩下的是一連串具體的 schema 決策——taste profile 存成 `taste_vectors` 表（每 facet 一列）而非單一向量欄、ratings 用 rating＋source 正規化、`profiles` 以 `auth.userId` 為鍵、第一次遷移就把九張表立起來。

但「表建對了」不等於「資料安全」。這個 stack 沒有測試套件、資料庫本身也無法驗證 ownership，唯一真正的防線是**移除不安全的寫法**：一個自己套用 user ID 的 scoped query helper、一份 typed registry、加上 RLS deny-all。最後，因為資料模型太關鍵，spec 會交給第二個模型 cross-check，再實際接上 Supabase、把遷移套進 live DB，用驗收條件把行為「跑」出來而不是「讀」出來——包含 2 個 auth user 觸發 2 個 profiles、以及 anon key 對九張表回零列。
