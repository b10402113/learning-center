地圖是證據不是真相：動手前先驗證它

Step 2/5 · 在舊碼庫裡工作：先 audit，再最小變更

學習目標

用讀一遍、跑一個指令、檢查漏掉的慣例、檢查站不住腳的理由這四項檢查，判斷一張生成地圖能不能拿來當變更依據；並守住「只補缺、不動既有」的界線。

前言：地圖畫得很漂亮，但你還沒走過

上一節結束時，你手上有一份看起來很完整的地圖：stack 寫得清清楚楚、指令列得整整齊齊、連 database 和 app 的區域規則都補上了。這時候最容易發生的失手，是把「檔案存在」當成「事情已經確認」。

打個比方：導航 App 幫你規劃了一條路，不代表那條路今天沒有施工。地圖是根據它讀到的證據推出來的，證據可能有解讀錯誤，也可能漏掉一個只有實際走過才知道的細節。課程對這件事的說法很直接：/audit 是從證據做出謹慎的選擇，但那些從證據得到的想法，仍然需要你的判斷。

所以這一節要回答的是一個選擇題：你現在要直接拿這張地圖去開工，還是先花一點時間驗它？驗到什麼程度才算夠？

三個選項，代價不同

面對一張生成地圖，你其實有三種做法，不是只有「信」或「不信」。

第一種是直接開工。把地圖當規格，讓 /scope 或 /develop 接手。省時間，但如果地圖某一句是錯的，錯誤會被後面的每一個 skill 繼承，而且會在很後面才爆出來。

第二種是先做重點驗證，再開工。不用逐字校對整份文件，只驗那些會影響這次變更的敘述：stack 對不對、你要用的指令跑不跑得動、你要動的區域有沒有被地圖漏掉。這是課程要你在舊碼庫上採取的做法。

第三種是退回補地圖。當你發現缺的是一個區域的規則，而不是一句話寫錯，就先讓地圖補上那塊，再開始變更。這個選項存在的理由，是因為地圖的價值在於「後面的 skill 都會讀它」；你現在不補，下一個 session 還是會踩同一個洞。

做法你付出什麼擋掉什麼風險什麼時候適用
直接開工幾乎不花時間沒有擋掉任何東西，錯誤會被下游繼承變更很小，而且你本來就熟這個區域
重點驗證再開工讀一遍加上跑一個指令的時間stack 誤判、指令失效、區域慣例被漏掉要動的是既有功能，或你會碰到資料與 auth

四項檢查，一項一項看

課程把驗證拆成四個可以實際執行的動作，不是「感覺一下對不對」。

一、把地圖對著實際專案讀一遍

不是只看檔案內容順不順，而是拿著它去對照 repo。它說框架是 Next.js，目錄裡就該看到對應的結構；它說 spec 放在某個資料夾，你點進去就該有東西。這一步的目標是抓「明顯對不上」的地方，不需要逐字審稿。

二、至少跑一個指令，證明它真的能用

這是四項裡最容易被跳過、也最有用的一項。地圖上寫的指令是它從 package.json 或設定檔讀出來的，讀對不代表跑得動：可能少了一個環境變數、可能某個 script 早就壞了、也可能它寫的是文件上的舊指令。挑一個你這次工作一定會用到的指令，實際跑一次。

# 先確認安裝與開發伺服器能不能起來（指令依專案實際 package.json）
npm install
npm run dev

# 若這次會動資料庫，再加驗一個資料庫相關指令
npm run db:migrate

預期結果是伺服器起得來、沒有立刻噴錯。如果失敗，先檢查是不是缺環境變數，再檢查指令本身是不是地圖寫錯了。這一步的價值不只是驗指令，而是驗「這個專案在你的機器上真的能跑」。後面所有驗證都建立在這個前提上。

三、檢查有沒有漏掉一個「看得見」的慣例

課程用的詞是 visible convention：一個你打開資料夾就看得到、而且全專案都照著做的模式。例如所有變更資料的請求都走同一種 server action、所有錯誤都回傳同一種形狀、所有頁面都放在同一層 layout 底下。如果地圖完全沒提，而這個慣例又正好落在你要動的區域，那就是一個會讓你寫出「不像這個專案」的程式的缺口。

四、檢查有沒有一個「程式碼支撐不起來」的理由

地圖裡有時會出現解釋性的句子，例如「這個檔案單獨存在是因為部署環境不同」。這類句子最需要驗，因為它是在解釋 why，而 why 最容易被腦補。做法很簡單：去程式碼裡找支撐。找不到，就把那句話當成待確認的假設，而不是事實。

示範一次判斷：什麼時候可以直接進 /scope

把四項檢查放進一個具體情境。假設你要做的是 BookWise 的還書功能，地圖上寫著 stack 是 Next.js、Drizzle、Neon、Tailwind、Zod，指令區寫了安裝、開發、測試與 migration。

你先跑 npm run dev，首頁起得來，登入頁也看得到，於是「這個專案能跑」這一項通過。你翻了一下 app/AGENTS.md，裡面寫了 auth layout 管登入與註冊、另有 root layout 與 admin layout，跟你看到的資料夾結構一致。你這次要動的借閱紀錄列表在 admin 底下，屬於那份 nested 地圖涵蓋的範圍。最後你檢查地圖對資料庫的描述：schema.ts 是唯一真相來源，這句話你在程式碼裡找得到對應的 import 與使用方式。

四項都過，判斷是：可以直接進 /scope，不需要重跑 audit。你接受了什麼代價？你沒有逐字校對整份地圖，所以地圖裡與這次變更無關的部分仍然是未驗證的。這是合理的取捨，因為那些部分不會影響你這次的決定。

現在把一個條件改掉：你發現 app/AGENTS.md 只寫了 layout，卻完全沒提「所有表單送出都走 server action、並在同一個檔案回傳錯誤形狀」這個明顯的慣例，而你這次要寫的正是表單。這時候四項檢查的第三項沒過。判斷就翻轉了：不要直接開工，先在這個區域補上那條慣例，再進 /scope。因為你現在寫下去，/develop 會用它的預設方式處理錯誤，而那個方式跟專案其他表單不一樣。

如果連「去哪裡找證據」都不確定，那就代表條件不足。例如地圖說某個清理任務每天半夜執行，但 repo 裡只有那支腳本、沒有任何排程設定。你無法從程式碼判斷它有沒有真的在跑，這時候正確的動作是去問人、去看部署設定，或至少把這件事標成未確認，而不是用「應該是這樣吧」把它補成事實。條件不足時，先承認不足，比硬做一個判斷安全。

驗證不是把 audit 再跑一次

發現地圖有問題時，很多人的第一反應是「那就再跑一次 /audit」。這不一定有用，因為它會從同一批證據再推一次，你得到的可能是一份措辭不同、但同樣漏掉那個慣例的檔案。真正的驗證是去碰它沒碰的東西：打開那個資料夾、跑那個指令、搜尋那個引用。重跑適合用在地圖整體已經過期、或專案結構大幅變動的情況；如果你只是要確認某一句話，直接查那個地方最快。

只補缺，不動既有

補地圖的時候，界線要拿捏好。/audit 自己的原則是「讀已經存在的東西，只補缺少的，保護人們已經寫下的內容」。你手動修地圖時也該照同一條規則：補上漏掉的慣例、修正與程式碼對不上的敘述，這些都是「讓地圖更接近真相」。但不要因為寫法跟你習慣不同，就把它重寫成你喜歡的樣子。

這條界線的實際判準是：你的修改能不能指向一個證據？如果理由是「這個專案所有表單都這樣寫，地圖沒寫」，那是補缺；如果理由是「我覺得這樣寫比較清楚」，那是重寫，不在這裡的範圍。團隊願意信任地圖，靠的就是這個克制：不用擔心每次有人進來就把它改一遍。

小結

生成的地圖是證據，不是真相。動手前的四項檢查是：對著實際專案讀一遍、至少跑一個指令、找有沒有漏掉看得見的慣例、找有沒有一個程式碼支撐不起來的理由。四項都過，可以直接進 /scope；缺的是區域規則而不是一句話，就先補地圖再開工。補的時候只補缺、不動既有，修改要能指向證據。

地圖驗過了，接下來才是真正的變更。下一節會用同一套熟悉的 /scope 與 /architect，看它們在一個已經有功能的專案上，行為跟新專案差在哪裡。
