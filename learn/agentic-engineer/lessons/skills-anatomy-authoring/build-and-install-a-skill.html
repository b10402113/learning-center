親手做一個 skill：用 skill-creator 產出第一版，再決定它該裝在哪

Step 3/4 · 幾分鐘做出雛形，然後開始檢查它夠不夠好

學習目標

做完這一節，你會得到兩件事：一個用 Anthropic 官方 skill-creator 做出來、真的能觸發的 skill，以及一個明確的判斷——它該放進個人的 ~/.claude/skills/，還是專案的 .claude/skills/。

前言：你看得懂了，現在換你做

前兩步把 skill 是什麼、SKILL.md 裡面長什麼樣都講清楚了。到這邊為止，你手上只有知識，沒有東西。這一節就是把知識換成實物：動手做一個你真的會想用的 skill，然後確認它裝在對的位置。

範例用的是 skill-creator，因為它是 Anthropic 官方做 skill 的工具，等於原廠附的開模機器。而我們要做的東西是一個「教我」的 skill：當你請它教一個主題，它會先問你對這個主題熟到什麼程度，再照那個程度講解；如果它不確定、或內容可能過時，它會先上網查證，而不是硬教你錯的東西。這種 skill 跟任何 workflow 都無關，它管的是「我怎麼學」——正好是那種你會想在每一個專案都帶著走的個人工具。

動手前你要先準備好

前置條件只有一條：一套能跑的 Claude Code，CLI 版或 IDE 擴充功能都可以。接下來所有動作都在裡面完成，不需要另外裝別的東西。

步驟一：安裝 skill-creator

在 Claude Code 裡下一行指令，把官方的 skill-creator 裝成 plugin。

/plugin install skill-creator@anthropic-agent-skills

影片示範的是終端機版本，寫法長得像 claude plugin install skill-creator claude-plugins official，做的是同一件事。裝好之後，你就多了一個專門幫你開模做 skill 的工具。

步驟二：叫它起來，用白話描述你要的 skill

接著把 skill-creator 叫起來，像跟人講話一樣，用白話描述你想做的 skill 就好。不用先寫正式規格，這一步只是把你腦中的需求講出來。

步驟三：把「什麼時候觸發、怎麼表現」寫進 prompt

這是整節最關鍵的一步，值得多花一點時間，不要草草帶過。原因是這樣的：description 會由 skill-creator 幫你寫，但 description 就是觸發器，決定這個 skill 平常會不會醒過來。換句話說，你的 prompt 是它填那一行的唯一原料。

所以與其說「幫我做一個教我東西的 skill」，不如把該在什麼時候啟動、啟動後該怎麼表現，一次講具體。影片裡的 prompt 是這樣寫的：

建立一個幫我學習的 skill。
在解釋之前，先問我的程度（beginner、medium 或 pro），再照那個程度講。
如果我用它時沒給主題，就先問我想學什麼。
如果它不確定、或內容可能過時，先上網查證，而不是教我錯的東西。

對照一下就會發現，這個 prompt 指定了三個具體行為：什麼時候問程度、沒給主題時怎麼辦、不確定時要先查證而不是亂猜。你把行為講得越明確，skill-creator 越有機會把 description 的那一行填對；那一行填對了，skill 才會在對的時機醒過來。

步驟四：跟著它一輪一輪把決定走完

送出去之後，skill-creator 不會閉著眼睛直接生出成品，而是一次一個決定帶你走過；遇到它拿不準的地方，它會先問你的意見。所以別以為按下送出就沒你的事了。

這一步它通常會先去看你現有 skill 是怎麼寫的。以影片作者為例，它掃過他的所有 skill，抓到他慣用白話、不用破折號，於是生成的內容就配合了同樣的風格。你自己跑的時候它可能會多問幾題才動手，這很正常。跑完之後 skill 就做好了，命名為 teach，跟其他 skill 擺在一起。

兩個 prompt 沒指定、卻被這樣設計的行為

做完之後，作者注意到有兩個行為他根本沒在 prompt 裡講，是 skill-creator 自己補上的。這兩點很值得記，因為它們正是「一個 skill 好不好用」的細節。

第一個：你已經先講過程度，它就跳過那個問題。例如你說「我是 5 級，closure 是什麼」，或者「我是 senior，解釋一下 X」，它從你的話裡讀出程度了，只會用半句話確認，然後直接開始。反過來講，你才剛講完程度它又問一次，讀起來就像根本沒在聽你說話。

第二個：你沒給主題時，它會把「主題」和「程度」兩個問題合成一輪問完，讓你只回答一次，而不是分兩次煩你。

步驟五：確認它裝在哪裡

skill 做好之後別急著用，先花一秒鐘看它裝到哪去了。這個位置決定了它是「只有你有」還是「整個團隊都有」。

若它出現在你個人（全域）的 Claude skills 資料夾，例如執行 ls ~/.claude/skills 看得到 teach，那它就是一個 personal skill。它不綁任何專案，你開哪一個專案都有它。對這個教我的 skill 來說，這正是對的歸宿——它管的是「我怎麼學」，你會希望它在每一個專案都在。

但如果你做的是團隊要用的東西，例如每個開發者都該遵守的慣例，那就要放進專案自己的 .claude/skills/ 資料夾。那它就是一個 project skill，跟著 repo 一起走，誰 clone 到誰就有。後面那九個 workflow skill 要分享給團隊時，走的就是這條路。記住這條分界：個人資料夾只屬於你，專案資料夾代表大家都拿得到。

種類位置誰拿得到適合放什麼
personal skill~/.claude/skills/只有你，每個專案都有關於你個人怎麼工作（例如教我）
project skill專案的 .claude/skills/每個 clone 這個 repo 的人團隊慣例、共享的 workflow

放錯位置也不用重做。想從個人搬到專案（或反過來），把資料夾和檔案複製貼過去就行。

做完長什麼樣

到這裡，你手上有一個能觸發、能跑的 skill。可以直接驗收：請它教你一個主題，看它有沒有先問你的程度、再照程度講。

但要先講清楚邊界：這是一個很穩的第一版，僅此而已。做一個 skill 很容易，你剛剛就看到了，幾分鐘、一段對話就能生出一個還不錯的雛形；做一個你願意把專案押上去的 skill，完全是另一回事。它的教學每次都那麼好嗎？程度問題每次都在對的時機問嗎？這些要靠反覆測試、收緊 description、在它做了你不要的事時回頭改指示。那才是工藝，而且絕對不是幾分鐘的事。

所以往後看到那九個現成的 workflow skill，你可以這樣理解它們：人家已經把研究、調校、還有那個「這次觸發錯了，那就改一下 description」的循環跑過幾百遍。任何人都能生成一個 skill；難的是做出一個你真正信得過的。

小結

做出一個 skill 的流程：用 /plugin install skill-creator@anthropic-agent-skills 裝官方工具，叫它起來、用白話描述你要的 skill，並在 prompt 裡把「什麼時候觸發、怎麼表現」講具體（因為 description 由它幫你寫，而那一行就是觸發器）。做完之後確認安裝位置：個人 ~/.claude/skills/ 是你到哪都有的，專案 .claude/skills/ 是跟著 repo 走的。最後記住：做一個很容易，做一個好用的需要迭代。

現在你能做出 skill 了。但「做得出來」和「寫得精簡、寫得讓人放心」之間還有一段距離。下一節我們拉回 JSM 自己的 skill 庫，看它的撰寫準則，以及那支會自動檢查你的 skill 有沒有犯規的守門腳本。
