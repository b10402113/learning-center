寫得精簡：skill 撰寫準則與自動守門

Step 4/4 · 一個 skill 要寫到多精簡才算及格

學習目標

能查閱 skill 的撰寫準則，包括哪一行值得留、什麼時候該拆檔案、commit 前要跑什麼；並且說得出 check-portability 這支守門腳本總共檢查哪些規則。

前言：寫得出來，不代表寫得精簡

上一節你已經做出一個能跑的 skill 了。接下來馬上會撞到另一個問題：內容到底該寫多少？

直覺上多寫一點比較保險，把所有可能用到的都塞進去。但你已經知道一件事：skill 每次執行都會整份載入。這代表每一行都不是「寫完就免費」，而是你每一次使用都要重新付一次的成本。寫得越滿，agent 每次讀到的噪音就越多，真正該做的事反而被淹掉。

這一節交給你兩個可以隨時回來查的東西。它們不是新的觀念，而是把「怎麼寫才算收斂」變成像查表一樣的事。以後你要動手寫或改 skill 之前，回來翻一下就好。

兩個實體

這兩個實體各管一件事：

  • docs/conventions.md：skill 的撰寫準則，定義一個 skill 該寫多少、哪一行才值得留下來。
  • scripts/check-portability.mjs：把跨工具慣例變成機械化檢查的守門腳本。它走過 skill 底下每一個 .md，任何一條違規就讓整個指令以失敗作結。

準則的前提：每一行都是每次要付的成本

整份準則立在一個前提上。skill 檔案在每次被執行時都會整份載入，所以每一行都是在每次使用時要重新付一次的成本。

因此寫 skill 的目標只有一句話：寫出「能產生行為的最少內容」。先砍，砍到不能再砍，再看還缺什麼。

哪一行值得留：五條判準

準則內容
一行必須改變行為如果 agent 本來就會那樣做，這行就是純成本，直接刪掉整句，而不是改幾個字。像「be careful」「be thorough」「think it through」這種模型本來就會遵守的模糊鼓勵，是最常見的違規。
下指令，不要講道理skill 只說「做什麼」。理由、替代方案、歷史，屬於 commit message 與 PR，不屬於 skill 本文。頂多留一個短句的理由，而且只在它能阻止 agent 做錯事的地方。
命名概念，別解釋概念模型已經懂的標準術語直接用，例如 idempotent、invariant、race condition、YAGNI、tracer bullet。只有這個 repo 自創的術語才展開，例如 Assumed spec、workflow tier，而且只寫一次、寫在一個地方。
步驟是指令，不是敘事不要有串接的段落。每一步一到三行，結尾落在可檢查的條件，形如 if X → do Y，或是一個 [ ] 檢查點，而不是描述接下來會發生什麼。
規則只說一次同一條規則出現兩次，就砍掉一個、指向另一個。唯一例外是 output style 這類共享區塊：每個 SKILL.md 必須能獨立散布，所以它被刻意重複，不抽出去。

其他幾條慣例

一種 house voice，只定義一次

每個 skill 都用同一種聲音說話，而它只定義在一個地方：每個 SKILL.md 裡的共享 output style 區塊。

這個區塊對使用者以「你」相稱，語氣溫暖、直接，並把每一步都框成可以跳過的建議，而不是命令。它管的是 skill 產出的一切，不管是摘要，還是 skill 生成的檔案（scope、spec、verify.md），都一律適用。

完成摘要的固定形狀

skill 最後印給人看的那份報告，讀者是要快速掃描的人，所以領著重點走就好，其餘細節一律指向檔案。形狀固定成四欄。

欄位內容
Headline一行：發生了什麼，以及唯一重要的那個結果。
Next要跑的那一個指令，或是那個還待決定的選擇。
Heads up阻塞點，或工程師必須檢視、必須決定的事。只有真的存在時才寫。
Pointer指向存放細節的檔案名稱，不要重述內容。

什麼時候才准加一個檔案

只有當某段內容同時滿足兩個條件，才准搬到另一個檔案：很少用到，而且很長。一次大型遷移上線、一個罕見的邊緣案例，就屬於這一類。

拆出去的目的是讓 skill 只在該情況發生時才讀它，把這段內容挪離常見路徑。短的或常見的內容不要拆，直接內嵌。真的要拆的時候，把觸發條件寫明白，形如「如果 X，繼續之前先讀 Y」，讓 agent 絕對不會漏掉。

提交 skill 編輯之前

  • 跑 npm run check，它同時做跨工具可攜性檢查與 hot path 大小預算。路徑接近預算時，該做的是先砍內容，而不是把上限調高，或再加一個檔案。
  • 重看一次 diff，找出「什麼都沒有改變的行」，以及「現在被說了兩次的規則」。
  • 一次修剪不應該改變行為。如果有可能改變，講出來，並用一次驗證跑來確認。

關於大小

這些預算是為了讓 skill 在長大的過程中保持精簡。一個警告代表「該修剪了」，不代表「限制訂得太低」。目標永遠是「砍到剛好夠用」，而不是達到某個固定的行數。

守門腳本檢查的 11 條規則

check-portability.mjs 走過 skill 底下每個 .md，違規就結束並回傳失敗。它檢查的規則，原始碼開頭的註解就列得清清楚楚。

//  1. Every skill declares `allowed-tools` in frontmatter.
//  2. No skill hardcodes a Claude-only model alias as a spawn directive
//     (`model: "haiku|sonnet|opus|fable"`) — use role words instead.
…
// 10. No em or en dash in any instruction file or `description` (the skills teach
//     the no-dash rule, so their own prose follows it).
// 11. No hyphen in prose. Compounds become simple words (read only, not read-only).
//     Code, paths, flags, ALL CAPS keywords, and the parsed artifact literals
//     (in-progress, gap-fill, whole-repo, Follow-up, pre-flight) keep theirs.

把這 11 條攤成表格，方便你查。

#規則
1每個 skill 都要在 frontmatter 宣告 allowed-tools。
2不准把 Claude 專屬的模型別名硬寫成 spawn 指令，例如 model: "haiku|sonnet|opus|fable"。要用角色詞代替，例如「一個又快又便宜的分層」「一個強模型」。否則 subagent 會直接繼承那個常很貴的主 session 模型。
3不准在散文裡指名 subagent 工具，例如 the Agent tool、spawn an Agent、the Task tool。保持 capability first。
4SKILL 本文不准出現會在 PowerShell 壞掉、又非 git 的 shell 黏著寫法，例如 >/dev/null、&& BASE=、|| BASE=。base branch 的選擇要用散文表達。
5SKILL.md 與打包的 prompt assets 要落在 byte 預算內。
6frontmatter 的 description 要壓在 400 字元以內，因為每個已安裝 skill 的 description 在每次 session 都會載入。
7每個 skill 都要附上自己的 OpenAI Codex adapter（agents/openai.yaml），而且裡面的 interface: 欄位要在。
8allowed-tools 要用 Agent，不要用舊的 Task。
9標記過的 contract block 若在多個 skill 之間重複，必須保持逐位元一致（byte identical）。
10任何指令檔或 description 都不准出現 em dash 或 en dash（U+2014、U+2013）。
11散文裡不准用連字號，複合詞要改寫成簡單詞，寫 read only，不寫 read-only。程式碼、路徑、旗標、全大寫關鍵字，以及被解析的產物字面值（in-progress、gap-fill、whole-repo、Follow-up、pre-flight）可以保留連字號。

規則 5 的預算不是隨便定的，原始碼裡有明確的數字。

const WARN_AT = 0.9;
const SKILL_BYTE_BUDGET = 32 * 1024;
const SKILL_BYTE_OVERRIDES = {};
const SUPPORT_MD_BYTE_BUDGET = 24 * 1024;
…
const DESCRIPTION_CHAR_CAP = 400;

把數字翻成白話：單一 SKILL.md 的預設上限是 32 KB，其他打包的 markdown 檔是 24 KB，description 是 400 字元。用量超過預算的九成（WARN_AT = 0.9）就會先跳警告，讓你在還便宜的時候就看到它在長大。

除了逐檔預算，腳本還會加總出幾個「實際執行路徑」的 hot path 預算。原因是，一次真實的執行會把好幾個檔案一起載進主對話，所以只看單檔會低估實際成本。

最小使用範例

把這一切接起來的其實就是一條指令。專案的 package.json 把 check 指到那支腳本，所以你在提交 skill 編輯之前跑它就夠了。

npm run check
# 等同於 node scripts/check-portability.mjs
# 全部通過會列出最重的檔案與 hot path 預算使用率；有違規則以失敗結束

它會走過 skills/ 底下的每個 .md，把所有違規一次列出來。原始碼還附帶一份加總的預算報表，所以你不只會知道「有沒有過」，還會看到每個真實路徑用了預算的百分之幾。這樣你能在動手加內容之前，就先察覺它正在逼近上限。

小結

撰寫準則圍繞一個前提：skill 每次跑都整份載入，每行都是每次要付的成本，所以要寫「能產生行為的最少內容」。哪一行值得留看五條判準：必須改變行為、下指令不講道理、命名概念不解釋、步驟結束在可檢查的條件、規則只說一次。另外還有 house voice 只定義一次、完成摘要的四欄形狀、只在「少用且長」時才拆檔、以及提交前跑 npm run check。守門腳本檢查 11 條跨工具規則，預設上限是 SKILL.md 32 KB、其他 markdown 24 KB、description 400 字元。

到這裡，這一節的四步就走完了：你知道 skill 是什麼、看懂它的內部、做出一個，也知道怎麼把它寫精簡。

接下來把 skill 拿來跟 MCP 對照。要看清楚的是「帶慣例」和「連你的實例」這兩種機制的分工，以及什麼時候該用哪一個。需要動手時，回頭找建立與編輯 skill 的操作步驟；想理解 skill 為什麼用 description 觸發、為什麼 context 會越塞越笨，就去看對應的原理章節。
