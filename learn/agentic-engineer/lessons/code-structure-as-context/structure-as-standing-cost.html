結構是每次 session 都在付的固定成本

Step 4/4 · 用一句檢查問句，替未來的每次改動買單

學習目標

把結構選擇看成每次 session 都在付的固定成本，並用「當有人回來改它，agent 得載入多少才能安全地找到並改動？」這句檢查問句，判斷一個結構提案乾不乾淨。

前言：這一堆結構決定，最後該怎麼拍板？

想像你走進一間陌生的房間要換燈泡。開關可能在門邊、可能在床頭、也可能三個開關各控一盞燈，你得一個個試。換燈泡本身只要三十秒，找開關卻花掉你十分鐘。程式碼裡的結構問題，就是這種「找開關」的成本。

前三節我們把三個結構選擇拆開看過了：檔案大小決定讀得多貴，命名與位置決定找得多累，colocation 決定它要跑幾個地方。拆開來看都很清楚，可是真正動手時，你面對的是一連串具體的抉擇：這支函式要不要抽出去？這個資料夾要不要重組？agent 提案的這個結構，我要不要接受？

你會猶豫，是因為兩股力量在拉扯。一邊是「現在」：這個結構跑得動、看起來沒問題，重構它要花時間，還可能弄壞東西。另一邊是「以後」：這個結構如果就這樣擺著，之後每一次回來改動，都要再付一筆代價。

所以真正的問題不是「這個結構好不好看」，而是「我該不該現在付出代價，去換掉未來每一次的負擔」。這一節把三個選擇背後的同一句話講出來，再給你一句能當場用的檢查問句，讓你下次不再猶豫。

三個選擇，其實是同一個道理

檔案大小、命名與位置、colocation，看起來是三招，但它們是同一個想法戴著三頂帽子：一個結構選擇本身就是一筆 context 成本，而且這筆錢不是付一次就結束。你每次讓 agent 進到這塊程式碼工作，它就被重新收一遍。

換個說法，結構像是某段路的收費站。路鋪得好，通行費低；路鋪得爛，你每次經過都得繳一次。差別在於，這條路你會走很多趟。

所以「好結構」的意義要重新定義。它不是送給未來自己的禮物，也不只是讓同事好讀，它是對「agent 之後要在這裡跑的每一個任務」的長期折扣。反過來，壞結構就是對這些任務全部課稅。同一個地方，你只要結構差一次，之後每一次改動都在繳稅，一直繳到你把結構改掉為止。

把這個取捨拆成「現在」和「以後」兩欄，事情就具體了。下面兩種處置方式的對照，依課程主張整理：

你的選擇你現在付的之後每次改動付的適合的情況
現在花力氣整理結構當下的時間與改壞的風險之後每個任務都變便宜這個地方會被反覆回來改
先接受現狀繼續往下做當下省下時間之後每個任務都變貴用完即丟、之後不會再回來的程式

這張表的重點不是「整理永遠比較好」，而是：這筆交換划不划算，取決於這個地方會不會被反覆回來改。會被反覆改的，值得現在投資；只會碰一次的，就不必勉強。

判別問句：接受一個結構之前，先問這一句

那要怎麼知道某個結構值不值得接受？課程給了一句可以直接拿來用的檢查問句：

「當有人回來改這個地方，agent 得載入多少，才能找到它、並安全地改動它？」

這一句話把三個選擇全包了。「載入多少」牽涉檔案大小，「好不好找到」牽涉命名與位置，「要跑幾個地方才能拼出整個功能」牽涉 colocation。你可以把它當成自己問自己的測試：如果答案聽起來像「很多」，就要提高警覺。

這裡有一個很容易被忽略的標準：如果答案真的是「很多」，那不管它現在跑得多順、多漂亮，它都不是一個乾淨的結果。因為那張帳單不是消失了，而是被延後到未來，你每一次回到這個地方改東西，都會被收一次。跑得動，只代表它這次過了關，不代表它便宜。

反例：什麼時候這條規則會翻轉？

這條規則不是鐵律，它有翻轉的時候。最典型的是「用完即丟」的程式：一次性的實驗腳本、跑過就刪的 spike、臨時驗證某個想法的 prototype。這些東西之後不會再回來改，「之後每次都要付」的成本根本不會發生。這時候你花力氣去整理它的結構，反而是浪費。

另一個要注意的反例，是把「跑得動」誤當成「結構沒問題」。很多專案當下確實能跑，功能也都對，但結構已經開始散開，於是每一次加新功能、每一次修 bug，都先花一大段時間在找路、在載入一堆無關的程式碼。這種專案短期看不出問題，長期卻是最貴的。跑得動是必要條件，不是乾淨的證明。

為什麼這件事被放在「context」這一章

最後回答一個位置問題：為什麼談結構，不是放在一般軟體工程，而是放在 context 這一章？答案是：你現在寫程式碼，已經不只是寫給人類讀了，你是在打造一個 agent 要在裡面工作的環境。

當這個環境小而聚焦、命名可預測、東西都放在一起，agent 跑起來又便宜又可靠。當它散亂、四處分散，每一個任務都得從「先花錢找到路」開始。課程後面那套 workflow 之所以一直堅持產出小而聚焦的檔案、而不是一個持續長大的大檔，正是因為它在替你經營這個環境。到這裡，你已經知道那份紀律買到的到底是什麼了。

小結

檔案大小、命名、colocation 是同一個道理的三種面貌：結構是一筆 context 成本，而且不是付一次，是每次 session 都重付。好結構是每次任務的長期折扣，壞結構是對每次任務課稅。接受任何結構之前，問一句「當有人回來改它，agent 得載入多少才能找到並安全地改動它？」答案若是「很多」，那就不算乾淨，不管你現在跑得多順。唯一的例外是用完即丟的程式，那時就別為它勉強投資結構。
