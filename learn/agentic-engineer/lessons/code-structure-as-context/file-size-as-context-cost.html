檔案大小就是 context 成本

Step 2/4 · 大檔案會把不相關的程式碼一起拖進 window

學習目標

解釋為什麼大檔案會把不相關的程式碼一起拖進 window、形成自找的 context rot，並說出拆成小檔案如何讓 agent 只載入真正需要的那一小塊。

前言：只是改一個函式，為什麼要賠上整份檔案？

上一節我們定下了一個前提：程式碼本身就是 context，而 context 有一筆帳要付，其中一半取決於「讀得多貴」。

這一節來看這筆帳裡最直觀、也最容易動手調整的一項：檔案的大小。你可能覺得檔案長一點短一點沒什麼差，反正邏輯都寫在裡面就好。但對 agent 來說，差別很大，而且理由非常具體。

想像一個情境：你只要它改一個很小的函式，把某段金額計算多乘一個稅率。結果它為了改這幾行，得先把一整份六百行的檔案讀進來，上面一堆跟這次任務無關的 import，旁邊還夾著七八個完全用不到的函式。它並不需要那些東西，卻得整個吞下去。

這一節就講清楚兩件事：這種情況為什麼會發生，以及你可以怎麼讓它少吞一點。

讀取是昂貴的，而且經常多讀

先回想 token 那一節的結論：讀取很貴。檔案被打開就是整份載入，不會因為你只需要其中十行，就只收十行的錢。三百行的檔案就算只用到三行，付出的代價還是接近三百行。

更麻煩的是，agent 打開檔案時往往沒辦法精準切出它要的那一段。它讀進來的通常是整份檔案，或者它想改的那一段被埋在一個很大的檔案裡，得連同前後文一起撈出來才看得懂。於是那些 import、上下夾著的不相干函式、整個檔案的脈絡，全都跟著進來了。

所以結論很清楚：檔案越大，一次讀取被迫帶上的「無關程式碼」就越多。這些無關程式碼一樣佔 window、一樣付錢，卻對這次任務毫無幫助。

小檔案讓它只載入真正需要的那一塊

反過來說，當專案被切成許多小而聚焦的檔案，agent 就能載入「接近它真正需要的那一小塊」。同樣的邏輯、同樣的功能，只是放法不同，工作起來的成本就完全不一樣，而且這個差別在每一次 session 都會重演。

課程用一句很直接的話收斂這件事：大檔案讓你付出的代價，往往遠超過那個改動本身應得的份量。你要改的明明只是一個小地方，卻得把整份大檔一起扛進來。

下面這個對照，把「同樣的程式碼、不同的切法」具體畫出來（示意結構，非課程原始碼）：

// 切法 A：一個大檔
lib/utils.ts        (約 600 行)
  ├─ formatCurrency()
  ├─ parseDate()
  ├─ validateEmail()
  ├─ slugify()
  └─ ... 還有十幾個不相關的函式

// 切法 B：拆成聚焦的小檔
lib/format/currency.ts   → formatCurrency()
lib/format/date.ts       → parseDate()
lib/format/slug.ts       → slugify()
lib/validation/email.ts  → validateEmail()

在切法 A 裡，agent 要改 formatCurrency()，就得把整個 utils.ts 連同十幾個用不到的函式一起讀進來。在切法 B 裡，它只需要打開 lib/format/currency.ts，幾乎就只載到它要的那個函式。同樣是改一行金額計算，切法 B 的 window 乾淨得多。

這才是「檔案要小」真正的原因

很多人以為「檔案不要太大」只是老工程師的美感潔癖，或者是為了人類好讀。但對 agent 來說，理由硬得多：大檔案會把本次任務根本不需要的程式碼一起拖進來。

這正是前面講過的 context rot 壓力，而且是你自己造成的。context rot 指的是，window 裡塞進越多與當前任務無關的內容，模型就越容易被拉離現在要做的事。那些不需要的程式碼不會安靜地躺在角落，它們會佔位、會干擾，讓模型更容易看錯、更容易跑偏。

所以「把檔案切小」不是在追求漂亮，而是在替每一次任務減少這種自找的干擾。

「檔案要小」的原因不是大檔案很醜，而是大檔案會把本次任務從來不需要的程式碼一起拖進 window。那是自找的 context rot：你親手把雜訊塞進它的工作檯，再期待它專心。

小心反過來切過頭

這裡要提醒一個反直覺的地方：把檔案切小，不等於切得越碎越好、檔案越多越好。如果切得太散，agent 為了理解一個完整的功能，反而得把五、六個小檔案一個一個找出來、一個一個打開，搜尋與跳躍的成本又回來了。

真正的目標不是「檔案最小」，而是「檔案聚焦」：讓它打開一個檔案時，裡面的東西大致都是為了同一件事，不會拖著一堆無關的程式碼。切到多大算剛好，取決於這個單位本身是不是一個完整、可理解的東西。

這個判斷會在下一節，以及最後一節的檢查問句裡，變成你手上可以直接用的準則。

小結

讀取很貴，而且打開檔案往往會多讀：import、周圍的函式、整份檔案的前後文。所以大檔案會讓 agent「只改一個小函式」卻賠上一大堆無關的程式碼，這是自找的 context rot。把專案切成小而聚焦的檔案，它就能載入接近真正需要的那一塊。但切記：目標是「聚焦」，不是「越小越好」，切過頭反而多出搜尋與跳躍的成本。

檔案大小處理的是「讀進來的東西」，但成本還有另一半沒解決：agent 是怎麼「找到」那個檔案的？下一節會看到，命名與位置如何直接決定它要搜幾次、開錯幾個檔案，而 colocation 又怎麼把一場尋寶遊戲變成一趟單次讀取。
