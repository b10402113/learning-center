你的程式碼就是 context

Step 1/4 · 結構不是品味，是每次都重付的 context 帳單

學習目標

說明為什麼 agent 每次讀你的原始碼都算一次 context 成本，並指出程式結構決定了它「讀得多貴」與「找得多累」這兩件事。

前言：還有一種 context，是你每天都在生產的

前面幾節談 context，談的都是「你主動餵給 agent」的東西。always-on 的專案簡報、它依需求自己抓的檔案、被明確指到的規格與文件，全都是你刻意安排、放進它腦袋裡的內容。你能控制放什麼、放多少。

但你有沒有想過，還有一種 context，你每天都在生產，卻從來沒把它當成 context 在看？那就是你自己的程式碼。

每當 agent 要動一個功能，它並不會「記得」你的專案長什麼樣。它會真的去讀原始碼：打開檔案、看函式、順著資料夾結構一路找路。這些讀進去的內容，跟你親手餵給它的任何一份文件一樣，都要佔掉 context window，都要付 token。

既然讀程式碼要錢，那程式碼怎麼擺，是不是也會決定它每次要付多少？這一節先把這層關係講清楚。看懂它，你之後才會明白：為什麼課程後面的 workflow 一直堅持產出小而聚焦的檔案，而不是一個持續長大的大檔。

你的程式碼，也是餵給它的一種 context

我們講 context 的三種類型時，分成三類。always-on 是每次 session 都自動載入的背景資料。on-demand 是 agent 工作途中自己去抓的檔案。reference 是被明確指到才進場的規格與文件。這三類聽起來已經涵蓋 agent 會知道的一切，但它們都在講「檔案、文件、規格」這一類外掛材料。

漏掉的是最貼身的那一種：agent 每次動手改功能，讀的其實是你真正的原始碼。檔案怎麼切、函式怎麼分、資料夾怎麼擺，這些全是它要載進 window 的內容。它讀得越多，佔的位子越多、付的錢越多，這跟讀一份規格文件沒有兩樣。

換句話說，你寫的程式碼本身就是它工作時必須吃掉的一種 context。這帶出一個很容易被忽略的結論：程式碼的結構不是「整潔工程」的品味問題。它直接決定兩件事——agent 的 context 是便宜還是昂貴，以及它能不能一次就讀到需要的東西，還是要試十次才找到。

成本分兩種：讀得多貴、找得多累

把程式碼當成一筆要付的代價之後，就會發現這筆代價由兩個問題決定。

第一個是「讀得多貴」。當 agent 打開一個檔案，會順便帶進多少它這次根本用不到的程式碼？這有點像走進超商只想買一瓶水，卻被迫把整排貨架都搬回家。

第二個是「找得多累」。在找到正確的那個檔案之前，它得搜尋幾次、打開幾個錯的檔案？這就像在圖書館找一本書：如果書名不清楚、書又亂放，你會先抽錯好幾本才找到對的那本。

成本白話問法主要被什麼決定
讀得多貴打開這個檔案，會夾帶多少用不到的程式碼？檔案大小
找得多累找到正確檔案前，要搜幾次、開幾個錯檔？命名與位置、colocation

這兩個成本加起來，就是「在你的專案裡工作，順手還是吃力」的差別。同樣的一段邏輯、同樣乾淨的程式，只要放的位子和切法不同，agent 每次進來的代價就可能差好幾倍。

更關鍵的是：這個代價不是付一次。agent 每次回到這塊程式碼工作，都要重新讀一遍，也就是重新付一次。

你的程式碼不只是給人看的作品，它同時是 agent 每天要讀進 window 的 context。既然是 context，就有一筆要付的帳：檔案大小決定「讀得多貴」，命名與 colocation 決定「找得多累」。結構好，等於替它每一次任務打折；結構差，就是對每一次任務課稅。

小結

always-on、on-demand、reference 談的都是你主動餵的 context，但還漏了一種：agent 每次改功能都會讀你的原始碼，而讀進 window 的東西都要付費。所以程式結構不是審美，是經濟——它決定 agent 讀得多貴（檔案大小）以及找得多累（命名與 colocation）。而且這筆錢每次回到同一塊程式碼都要重付。

這也把前面的觀念接了起來：context engineering 管的是你放進去的內容，程式結構管的是它自己吃進去的內容，兩者其實是同一本帳。而在這兩種成本裡，最直接、最容易立刻下手的是第一個——檔案大小。下一節我們就看懂，為什麼一個大檔案會讓 agent「只是改一個函式」，卻得賠上一大堆它根本不需要的程式碼。
