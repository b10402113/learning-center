實作 Movie Catalog 與 Cache：develop → check verify → sync

Step 1/6 · Greenfield：Catalog、Design System 與第一個 Slice

學習目標

用 spec 0003 的 catalog + cache 這條 feature 走完 develop → check verify → sync，並能指出 verify 必須打到真服務、真 defect 要當場修完再 sync。

前言：資料庫有了，但 app 還看不見東西

前面幾個節點已經把地基鋪好：scope 決定了、技術棧選定了、專案 scaffold 起來了，資料模型也跑過一輪 check verify、check review、document。可是到這個階段為止，你的 app 其實還「看不到東西」——它有一張張空的表，卻沒有資料填進去，也還沒有任何畫面能證明這些表真的能用。

這一節要跨過那條線。Movie catalog 與 cache 是第一條真的去打外部服務的資料 feature，它要把 TMDB 的電影抓進來、存進 catalog、再供後面的功能讀取。因為它會碰到網路、憑證、快取時效這些真實世界的東西，驗證的重點就不再是「型別有沒有過」，而是「它有沒有真的打到服務、拿回真的資料」。這也是整套 workflow 第一次逼你面對「驗證要對真的東西做」的紀律。

動手前先備齊的事

這條 feature 的規格是 spec 0003，它早就在 architect 那一輪寫好了，所以這裡不用重新設計，只要把它交給 develop。會缺的是環境變數：TMDB 的 API key，加上 ingest 的 signing key 和 event key。

你可以選先把整條 feature 建完、稍後再補 key，也可以現在停下來把 key 填好再動工。課程選擇前者——讓它邊建、你邊去把 key 生出來，這樣等待的時間不會浪費。要記住的是：key 沒填，feature 還是建得起來，但驗證那一段會走不到，所以補 key 不能拖太久。

步驟一：跑 develop，讀懂它的產出

除了 spec 之外，develop 開頭會自己確認它已經載入了三樣東西：spec 本身、專案的 conventions，以及這次要用的 ingest skill。載入完成後，它會照 spec 裡那份 build plan 一條條實作。以這條 feature 為例，build plan 切成 10 個 task，跑完之後你會拿到一個分支和對應的 commit。

產出的內容包含 TMDB 的設定、movies catalog 的資料層、一個 normalizer，以及 ingest client。這裡有個容易忽略但很關鍵的描述：這些檔案是「對真的東西證明過，不只是過型別檢查」——因為它真的打了一次服務，所以型別對不對只是最低標準。

步驟二：跑 check verify，看它打到真服務

接著跑 check verify。這一輪會很久，課程裡講師離開電腦大約十分鐘，回來才看到結果。它做的是把 spec 的驗收條件一條條拿去對真服務操作，而不是在腦內模擬。驗證報告長這樣：

53 of 62 checklist steps
exercised and passed,
9 non-exercised, we
are verified and live.

62 條裡有 53 條被實際操作過並通過，9 條沒有被操作到（多半是工具沒接上，或需要本機環境配合）。重點在「exercised」這個字：它沒有把沒跑過的算成通過。裡面有幾個 blocker 是正常的，但驗證也留下一條真正的 defect。

步驟三：把真 defect 當場修完

被留下來的那條 defect 很典型，它發生在把 TMDB 的 ID 合進回傳物件的時候。catalog refresh 會把 TMDB ID 傳進來，但 create 回傳的物件自己身上也有一個 id 欄位，於是當程式碼用物件展開（spread）覆蓋時，剛剛帶進來的自訂 ID 被蓋成 undefined，事件層的去重就整個失效了。修法很單純：把自訂 ID 放到 spread 之後，讓它蓋回去。

// 壞掉：spread 在後面，回傳物件自帶的 id（undefined）蓋掉了自訂 ID
return { id: tmdbId, ...catalogItem };

// 修好：把自訂 ID 放到 spread 之後，讓它最後生效
return { ...catalogItem, id: tmdbId };

修完之後，課程做了一個很值得學的動作：它直接叫它修掉，然後「跳過 review」，把這個 feature 標成完成，馬上 sync。理由是 review 不必對每一條 feature 都做——當 verify 已經抓到並證明了修正，這條線就可以往前走。真 defect 的處理順序因此是「當場修完 → 跳過 review → 標記完成 → sync」，而不是先記帳、留到以後。

步驟四：sync 對帳

最後一步是 sync，它負責把專案文件（例如根目錄的 AGENTS.md）和實際狀態對齊。這一輪它回報 spec 的三種狀態都已經一致，但抓到文件裡兩件真的過時的事：一個是「目前裝了哪些東西」的描述，另一個是指令區塊漏掉了每一個 DB script。這些不是程式錯誤，卻是會誤導下一個人的文件債——sync 的工作就是把它們改回真的。

develop catalog-and-cache      # 依 spec 0003 的 build plan 實作
check verify catalog-and-cache # 對真服務操作每個驗收條件
# 修掉 verify 留下的真 defect
sync                           # 把文件與現況對齊

這套流程沒有看起來那麼硬

課程特別強調一件事：workflow 不是死板的一條線。等到地基打穩、你對接下來要做什麼有完整的想法之後，你可以叫它「一起 develop 幾條 feature」，而不是永遠一條一條來；也可以把幾條功能先 architect 好（例如 CSV import 和 core taste loop），再一起交給 develop。但不管你怎麼批次，你仍然要坐在駕駛座上回答問題——批次換到的是吞吐量，不是把判斷權交出去。

小結

一條打外部服務的資料 feature，走法是：develop 依 build plan 實作並留下分支 → check verify 真的去打服務、逐條操作驗收條件 → 留下來的真 defect 當場修到被證明 → 跳過不必做的 review、標記完成 → sync 把文件對齊。驗證的價值不在「型別過關」，而在它真的碰了真服務。

走完這一步，你手上有了第一條真的在動的資料路徑，但畫面仍然是素的。下一節要換到完全不同的尺度：把「這個 app 長什麼樣」從口頭偏好變成一條正式的 architect 訪談，產出 design.md 和 spec 0004。
