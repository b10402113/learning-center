Architect Design System：把視覺方向定成 design.md 與 spec 0004

Step 2/6 · Greenfield：Catalog、Design System 與第一個 Slice

學習目標

跑一輪 design system 的 architect 訪談，把 register、type、color、spacing、card shape、native-fill、accessibility、icons 定成 design.md 與 spec 0004。

前言：功能寫完了，但沒人決定它長什麼樣

上一節把第一條資料 feature 做出來，app 總算會動了。但只要一打開畫面，你馬上會碰到下一個問題：它不難看，卻也說不上好看，因為根本沒有人決定過它應該長什麼樣子。之前的每一步都在處理「資料對不對、邏輯通不通」，視覺則是東拼西湊來的預設值。

如果你放任下去，之後每加一條 feature，就會有人（或 agent）各自發明自己的按鈕圓角、自己的間距、自己的錯誤顏色，整個 app 會慢慢散掉。這一節要做的，就是在還只有幾頁畫面的時候，用一次 architect 訪談把「視覺語言」釘下來，變成一份可被之後所有 feature 重複使用的 design.md 加一份 spec 0004。

前置：這一步需要什麼

這是全新的一輪 architect，開一個乾淨的 Claude Code 視窗，直接叫它 architect 設計系統與 UI foundation 就好。它會先去讀 agentic engineering workflow 裡那份 design 對話文件，確認兩件事之一：這個專案已經有現成的設計可用，還是要從零開始、用產品願景生出一個方向。

它做完 preflight 之後會回報：已經和 origin/main 同步、spec 放在 docs/specs、下一個編號是 0004，可以開始。它還會自己推斷出這個 stack 用的是 Tailwind v4 加 ShadCN，所以不用為了用什麼工具再問你一輪。

步驟一：先決定 design source

第一個、也是最關鍵的一個問題是：視覺設計從哪裡來？課程把選項講得很清楚，而且刻意不幫你選，因為它決定了整個系統是「照著一份真設計做」還是「照著提案的方向做」。

來源它會怎麼處理適合什麼情況
Figma 設計（或截圖）接上設計或吃截圖，照著把 type、color、spacing 讀出來你手上已經有正式設計稿
自備參考圖讀圖裡的排版與配色，生出方向你有喜歡的 mockup 或他牌 app
還沒有設計自己提一整套視覺方向：type scale、palette、spacing、圓角、卡片形狀想先看它會把 app 帶去哪

課程裡講師先上 Dribbble、Awwwards 找了一輪 movie app 的設計，也挑了幾個參考圖，但最後還是選了「還沒有設計、讓它提方向」這一條，理由是這個 app 的主題（電影口味與推薦）很特定，他想先看看 agent 自己會提出什麼，再決定要不要餵參考圖去修。

同時他也順手定了一件架構層級的事：這個 app 以手機為主。他的判斷是大多數人會在沙發上用手機找片，所以 foundation 要行動優先（mobile-first），並保留之後做成離線 PWA 的空間。

步驟二：回答 register，這題定了其他都會跟著定

接著它開始問方向。其中最重要的一題是「這個介面要落在什麼 register」，課程形容這是「其他一切都掛在上面的那個決定」，所以講師選擇明白講，而不是讓它自己猜。答案是一組很有畫面的描述：

Quiet cinema.
Poster scurried.
Near black surfaces.
Restrained neutral text.
Almost no chrome.
One accent used sparingly.
The artwork is the only
saturated thing on screen.

翻成白話：整體像安靜的電影院，接近純黑的底色、收斂的中性文字、幾乎沒有多餘裝飾，只用一個重點色，而且用得很省。畫面上唯一色彩飽和的東西是電影海報本身——因為這個產品的內容就是海報與劇照，讓內容當主角最合理。這個方向之所以撐得住，是因為它耐看，不會跟著流行過時。

定了 register 之後，其餘幾題就順著解：字體用一套幾何無襯線（geometric sans）貫穿整個 app；中性色之外只留一個功能性重點色；形狀與密度上，刻意在每部電影之間留一點呼吸空間，讓海報不至於擠成一團。

步驟三：把兩個核心卡片與 shell 定清楚

方向定了，接著是元件層級的追問。這個產品活在兩個形狀上：swipe card（滑動評分卡）與 feed pick card（推薦卡）。課程有兩題很值得記：

  1. Swipe card 上要顯示什麼？海報、片名、年份、類型；按鈕是主要操作，拖曳與鍵盤是同樣可用的路徑。這裡它還順手確認了一件容易被忽略的事：一筆評分存的是三種狀態之一（like、dislike、skipped），沒有分數。所以 deck 有三種結果，不是兩種，手勢因此是右滑 like、左滑 dislike、上滑 skip。
  2. Feed pick card 上要顯示什麼？重點是那句「為什麼推薦」的理由句，加上可以直接採取的動作（save 或 dismiss）。

App shell 也定了：桌機是頂部導覽列，手機收成底部 tab bar。它甚至自己說了一句講師很愛的推論——「這是一個以手機為優先、用來滑動的產品，底部 bar 剛好把 deck 放在拇指能碰到的地方」。而且它明確指出：行動優先與原生體感現在是寫進 spec 的硬性限制，不是加分項；拖曳是主要路徑，按鈕與鍵盤是通往同一個 handler 的平等入口。

步驟四：native-fill、a11y、icons、states

接下來它把「像不像原生 app」拆成具體可做的清單，逐一確認：safe area insets 與動態視窗單位（處理瀏海與工具列的高度變化）、手機用 sheet、桌機用 dialog、滑動提交時給 haptic feedback、以及壓掉瀏覽器的「網頁感」（tap highlight、overscroll、文字選取）。PWA 的部分定成「現在可安裝、離線之後再說」。

Accessibility 它建議沿用網際網路的通行基線（WCAG 那一套），課程直接採用。圖示用 Lucide，搭 ShadCN UI 的預設。狀態設計上，講師特別否決了「轉圈圈 spinner 加一行純文字」這種做法，選擇 loading 用 skeleton、空狀態用插畫、錯誤用行內提示——因為這些細節正是讓 app 看起來「有打磨過」的地方。

步驟五：確認產物——design.md 加一個 live design route

最後它問到交付物要長什麼樣子。scope 原本就要一份 design.md，作為「寫下來的真實來源」；除此之外它提議再加一個 live design route，把每一個 token 與元件用真的 app 渲染出來，方便一眼看出哪個元件壞了。它的代價是「一條路由加上一份持續維護的義務」。

講師選了兩者都要：既拿到文件，也拿到一個可在瀏覽器裡檢查的頁面。這一節的所有決策就收束成 spec 0004，裡面有 user stories、acceptance criteria，以及一個關鍵的決策選擇——走 token-first 的系統。它產出後會問你要不要用第二個模型 cross-check；因為這是設計工作，課程選擇先自己看過 spec 就好，等之後能真的看到畫面再自己把關。

做完長什麼樣

走完這一輪，你手上會有一份 spec 0004，加上一份 design.md，把 register、字體、顏色、間距、圓角、兩個卡片、shell、native-fill、a11y、icons、狀態全部寫死。它的價值不是「設計得很漂亮」，而是之後每一條 feature 都有同一套語言可以依循，不會各自發明。至於這份規格怎麼被蓋成真的程式碼與一條可檢查的 /design 路由，那是下一節的事。

小結

architect 設計系統是一連串決策，不是畫圖：先決定 design source（真設計、參考圖、還是讓它提案），再定 register（其餘視覺決定都掛在這題上），接著把兩個核心卡片、shell、native-fill、a11y、icons、狀態逐項問清楚，最後收成 spec 0004 與 design.md。它的產物是「之後所有 feature 共用的語言」。

方向已經白紙黑字寫下來了，但寫在文件裡還不等於看得見。下一節要把這份 spec 交給 develop，把 tokens、字體、元件、swipe deck 到 PWA 全部蓋出來，並用 Playwright 親自驗一遍。
