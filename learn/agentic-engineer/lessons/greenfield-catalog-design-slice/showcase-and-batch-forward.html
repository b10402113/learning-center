Showcase 收尾與批次推進：一次一個，還是先 batch architect

Step 6/6 · Greenfield：Catalog、Design System 與第一個 Slice

學習目標

跑完整條 slice（評 ~20 部、debug runtime error、拿到 12 個帶理由的 pick、收掉 feature），並判斷何時該先批次 architect 再一起 develop 來換吞吐。

前言：路通了，但你還得決定下一步怎麼走

上一節把 core taste loop 接通，也修掉了海報時有時無的 bug。現在你手上是一個真的能用的 app：Google 登入、滑一輪 starter deck、拿到一份會說「為什麼推薦你」的 feed。這一節要做兩件事。第一，把它真的跑完、收掉，示範一次完整的 showcase；第二，正面回答一個你之後每次開發都會再遇到的分岔：剩下的功能，你是要一條一條慢慢來，還是先把好幾條一次 architect 好、再一起 develop？

這兩件事看起來一個是操作、一個是策略，但它們其實扣在一起。因為當你確認了「一條 feature 的完整週期」長什麼樣之後，才有能力判斷哪些部分可以壓縮、哪些不能。

先把它跑完：一次真實的 showcase

登入之後進到 onboarding，就是一張張評分。你可以用畫面上的按鈕，也可以直接拖拉卡片。課程裡講師滑了大約 20 部（像是 Shawshank、Godfather、Star Wars、Whiplash、Amélie 這些），過程中還會跟你分享他對每部片的看法——這是設計成「像真的在用 app」的展示。

滑到最後，冒出兩個錯誤：一個是 console 的「cannot update component」，另一個是「fetch failed」。他當下的處境是：「這發生在我評完 onboarding 最後一部片的時候，現在我按不下 build my feed。」處理方式很標準化：把兩個錯誤一起複製，開一個新的 Claude 視窗，用 debug 功能把它們丟進去。附帶說明一下，當時 app 是由 agent 在跑，不是他自己在終端機跑的，所以他先把它停掉、自己重跑一次，好取得更完整的終端機訊息。

結果很有意思：他只是把 app 重跑一次，錯誤就不見了，按下「build my feed」也成功進入「building your feed」。他還是用 debug cross verify 了一次，確認這不是巧合。feed 建置要花一點時間，終端機可以看到它正在把相關電影與推薦一條條長出來。最後 feed 送進來，第一條是 Reservoir Dogs：「你不會反感它那種不留餘地的緊繃與道德曖昧，一如 Whiplash 帶給你的心理壓力。」——而這一切，就只是評了 20 部片換來的。講師補了一句：如果餵進整份 Letterboxd 清單，結果會好上更多。

接著就是收尾的固定動作：把這個 feature 標成 completed，然後前往下一條。你可以看到早先某條 feature 是被「手動關閉」的，因為它已經檢查並驗證過。到這裡，你已經把 core loop 走過好幾輪了——architect 完就 develop，剩下的功能也都走同一條迴圈，所以課程從這裡開始把重複的段落快轉掉。

核心抉擇：一次一條，還是先批次 architect

現在進入這一節真正要你帶走的判斷。課程把選擇講得很清楚：這套 workflow 可以「既快又徹底」，關鍵在於你有沒有善用批次。核心的兩股張力是——你想保留多少「每一步都親眼看著」的控制感，跟你願意投入多少「先集中回答大量問題」的前置成本。這兩者互換，換到的就是吞吐量。

面向一次一條先批次 architect，再一起 develop
流程每條 feature 各自 architect → develop → verify → sync先一次 architect 多條（或讓它自答、採用建議答案），再一次 develop 全部
你的角色每條都親自回答每一題在你有空時把問題集中答完，之後放手讓它跑
優點控制最細，每個決定你都親眼看過吞吐高，能把零碎等待與空檔填滿
代價慢，而且需要你一直在場要一次答很多題、前期較累；多條同時動可能需要協調
適合高不確定、或關鍵地基（資料模型、auth、core loop）方向已明、彼此相依低、而你手上剛好有整塊時間

課程把批次的好處說得很直白：當你「在有空的時候」先把好幾條 feature architect 好，agent 之後就能順著那些 spec，自行走完並交出專業的成品。因為它已經有了那條「飛行的路徑」——也就是清楚的方向與邊界。你依然拿到工程化的做法，依然可以檢查每一份 spec，只是把「問答」集中到你有空的時候，而不是被它隨時打斷。

判別問句：可以用這四題自己判斷

  1. 這條 feature 的決定，我能不能大致預測它會問什麼？能，代表你已有足夠方向，適合批次；不能，留給它一對一的訪談。
  2. 我接下來有沒有一整段時間可以一次回答很多題？有，就先批次 architect；沒有，就別硬撐，一條一條來不會出錯。
  3. 這幾條 feature 會不會改到同一塊程式碼、需要互相協調？會的話，批次時要特別留意衝突，或把它們錯開。
  4. 這條是不是關鍵地基（資料模型、auth、core taste loop 這種）？是，就還是自己一條一條看著走，別放飛。

反例：這些時候批次會反咬你一口

反例一：把關鍵地基也批次放飛。課程自己在資料模型那一段就是一條一條走、還交給第二個模型 cross-check，因為地基一旦定錯，之後每條功能都要付代價。這種 feature 的價值來自「每一個決定都被想過」，不是速度。

反例二：以為批次就等於不用在場。批次只是把問題集中，不是把判斷權交出去。你仍然是架構師，還是要回答問題、還是要檢查 spec。把它想成「離線」會讓你在關鍵處漏掉該做的決定。

反例三：把「重跑就沒事」的錯誤當成不存在。showcase 裡那兩個 runtime error 重跑後消失，很容易讓人鬆一口氣就算了。但課程仍然用 debug cross verify 過——因為「現在看不到」不等於「原因不存在」。這一條的教訓是：批次可以壓縮流程，但不能壓縮對異常的追查。

小結

把一條 slice 收尾的固定動作是：實際滑完 onboarding、遇到 runtime error 就把它當證據餵進 debug、確認 feed 真的產出帶理由的 picks、然後把 feature 標成 completed。至於剩下要怎麼推進，判斷規則很簡單——方向已經清楚、彼此相依低、而且你手上有整塊時間，就先把幾條 architect 好再一次 develop；如果是關鍵地基或高度不確定，就一條一條自己看著走。批次換到的是吞吐，不是把判斷權交出去；你永遠還是那個架構師。

走到這裡，第 13 章的 greenfield 全流程就到一個段落了：從一個點子，到 scope、stack、scaffold、資料模型，再到 catalog、design system，最後是這條真的能操作的 core taste loop。接下來你可以把同一套 workflow 帶回自己的專案，或照著課程繼續把剩下的 feature 一條條接上去。
