Develop Design System：tokens、components 與 /design 契約

Step 3/6 · Greenfield：Catalog、Design System 與第一個 Slice

學習目標

用 develop 把 design system 蓋成 tokens、fonts、ShadCN、swipe deck、PWA，用 Playwright 驗證，並讀懂 /design route 為何是可重用的設計契約。

前言：規格寫好了，但它還只是一份文件

上一節把視覺方向定成 spec 0004 和 design.md，register、字體、顏色、卡片、shell 全部白紙黑字寫清楚了。可是打開 app，畫面還是跟昨天一模一樣——因為寫在文件裡的決定不會自己變成程式碼。這一節就是把那份規格交給 develop，讓它真的長成畫面。

不過在此之前，有一個很少人提、但課程特別點出來的工作流細節：architect 跑完之後，會反過來去改 scope，把剛剛訪談出來、原本沒有的資訊與任務補上去。課程甚至明說，以前的版本試著一開始就把所有東西塞進 scope，後來發現那是錯的——因為真正的決定只有在訪談之後才會出現，先塞只是猜。

步驟一：spec 批准後，先 clear 再 develop

確認 spec 0004 沒問題、按下批准之後，這個功能會進到 in progress，接著用 develop skill 開始建置。課程這裡執行了一個固定動作：clear 掉 context，再叫它 develop。理由跟前面幾個節點一樣——真正的狀態都在檔案裡，聊天室的上下文留著只會增加噪音。

clear
develop the design system and the UI foundation

步驟二：讀懂 develop 把它拆成哪些工作

這個 design system 不小，develop 把它切成大約十個步驟依序做。課程把清單念了一遍，值得你逐項對照：

Tokens in globals.css,
the fonts, and design.md.
Then, ShadCN, init against the tokens, button, design route gated, accessibility
baseline, focus ring, reduced motion, layout primitives, base component set, native
fields global, swipe deck with motion, server rendered pick card, installability,
manifest icons, theme color, close the docs, every component visible on the design.

把這段拆開看，順序其實有邏輯。它先把 token（顏色、間距、圓角等變數）定義進 globals.css、把字體與 design.md 準備好，這是地基；接著才 ShadCN init，讓元件庫是「長在這些 token 上」，而不是各元件自己帶一套顏色。再往下是還不太起眼但很重要的基礎：focus ring、reduced motion（尊重使用者的減少動態偏好）、版面的 layout primitives。然後才是真正的元件：native fields、帶動畫的 swipe deck、server rendered 的 pick card。最後收尾在 installability（PWA 可安裝）、manifest icons、theme color，以及把每一個元件都放上 design 頁面。

跑完之後它交出的是整個 app 的 theme 與一組元件，連手機 app 要用的可下載圖示都一起做了。這些元件接著會在你開發每一條後續 feature 時被重複使用。

步驟三：看它自己用 Playwright 驗證

develop 不會只把程式碼寫完就交差，它會用 Playwright 把 app 開起來，自己操作一遍。課程形容這個畫面：「它開了一個真的瀏覽器、跑起來、到處定位、點擊」。驗證過程裡它抓到一條真的 defect，而且自己修掉了：

It found a real defect on
the full height deck page.
The instructions line sits under the fixed
tab bar, fixing the shell height model.

這個 bug 的意思是：在滿版高度的 deck 頁面裡，固定在下方的 tab bar 蓋住了上面那行操作說明。這不是型別問題，也不是邏輯錯誤，而是「真的把它排在畫面上才會看到」的錯位——正是為什麼它要用瀏覽器實測，而不是只在腦內推理。它同時確認了 focus ring 是琥珀色、2px（跟 spec 一致），也測了鍵盤操作能不能走完整條 deck。

步驟四：自己開起來看，桌機與手機都看

機器驗證的同時，你也可以自己開終端機把 app 跑起來：

pnpm dev   # 跑在 http://localhost:3000（或 3001）

打開後會看到 feed 頁：「films picked for you」，下面是幾部熱門片（Shawshank、Godfather、Dark Knight）。search、watch list、import、account 這幾頁雖然還沒真的做，但畫面上已經看得到它們之後會長什麼樣。接著用瀏覽器的裝置模式切到手機（例如 iPhone 14 Pro Max），如果沒看到底部 tab bar，把寬度再收窄一點，那一條拇指列就會出現——這正是 spec 裡「行動優先」那條限制的實際結果。

步驟五：打開 /design，讀懂它是什麼

這個 design system 最容易被忽略、卻最有價值的產物，是那條 /design 路由。打開 localhost:3000/design，你會看到整個 app 的視覺語言攤在一個頁面上：不同的表面（surfaces）、文字層級、重點色的三種用途（good、danger、brand）、你選的那套字體、各種圓角、間距與動態，還有一整排元件——meta line、海報、沒有海報時的替代圖、pick card、swipe card 與 deck、rail、chips、按鈕、表單控制項、loading 的 skeleton、插畫式空狀態、錯誤、成功 toast、背景 toast、responsive overlay。

它的意義不只是「一張元件預覽圖」。課程把重點講得很清楚：

not just the initial design
that it created, but the
design language that
lives within your application, that all the future
developed skills are going to use when developing
additional features.

也就是說，這個頁面同時是「設計語言住在 app 裡」的證據。因為每個元件都共用同一組 token、同一組圓角、同一組顏色、同一組 accessibility 規則，之後 develop 每一條新 feature 都會自然沿用它們，不會有人自己發明一套。課程用「fully uniform」來形容——整個 app 會維持一致的視覺，而不是拼貼出來的。當某個元件在真實頁面上壞掉時，這條路由也是最容易一眼看穿的地方。

要提醒的是，這條路由是開發用的，會 gate 在 dev 環境，不會跟著上正式站。

做完長什麼樣

走完這一節，你的 app 第一次有了完整的視覺外觀：一套定義在 globals.css 的 token、一致的字體與元件庫、兩個核心卡片、可安裝的 PWA 設定，以及一條可以隨時檢查的 /design 路由。而且它不是「看起來能用」而已，是經過 Playwright 實際在瀏覽器裡操作、連版位錯位都抓出來修過。至於之後看到成品想改方向時，該用 compact 還是 clear、要改到什麼程度，那是下一節的判斷題。

小結

develop 把 design.md 的規格變成真的畫面：先立 token（定義在 globals.css）與字體，再讓 ShadCN 長在 token 上，補齊 focus ring、reduced motion、layout primitives 這些基礎，最後做出元件、swipe deck、PWA 設定，並把每個元件放上 /design。它會用 Playwright 實測並自行修掉像「tab bar 蓋住說明文字」這種只有排上畫面才看得到的 defect，而 /design 這條路由就是之後所有 feature 共用的設計契約。

視覺總算看得見了。但看得見之後，往往就會出現新的意見。下一節要處理一個很真實的狀況：看到成品後想改方向，這時你是該 clear 掉重來，還是 compact 保留它記得的東西？
