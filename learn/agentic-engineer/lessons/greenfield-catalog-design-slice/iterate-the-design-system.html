改主意時：compact 而非 clear，重跑 architect→develop

Step 4/6 · Greenfield：Catalog、Design System 與第一個 Slice

學習目標

在已經看到成品後要改方向時，判斷該 compact 還是 clear，並用「重新 architect → develop → verify」把 design system 改版而不弄丟先前狀態。

前言：你不愛它，然後呢？

上一節把設計系統蓋出來了，你打開 /design、打開 feed、切到手機看底部列，第一次真正「看見」這個 app。然後很現實的事情發生了：你不太滿意。可能覺得太素、可能剛好看到一個更現代的參考，總之你想改方向。

這時你面對的其實不是「怎麼改」，而是兩個更前面的問題。第一，你現在這個對話已經跑很久了，接下來要它改版本，你是該把它忘掉（clear）還是讓它記得（compact）？第二，既然要改，是只換個顏色就好，還是整個重新調一輪？這兩個決定會直接影響改版的品質，也影響你要不要從頭回答一次那些問題。

決定一：compact 還是 clear

先講清楚這兩個動作差在哪。clear 是把整個對話上下文丟掉，只留下檔案；compact 是把前面的對話壓成一份摘要，保留「做過什麼、關鍵概念是什麼」，細節則會掉。兩者都不是「重置專案」——真正的狀態一直都在檔案裡，spec 也還在。差別只在於 agent 手上有沒有關於「剛剛發生的事」的記憶。

面向clearcompact
對上下文做什麼全部丟掉壓縮成一份摘要
之後它記得什麼什麼都不記得，只能從檔案重建摘要與關鍵概念，約略記得做過什麼
適合的下一步只依賴檔案、跟先前對話無關的新工作要修改「才剛做好的東西」，需要知道它做了什麼
成本幾乎沒有壓縮本身要花一段時間

課程這次選了 compact，理由是：接下來的指令是「重新 architect 你剛剛做的那個系統」，而 agent 必須知道你改了什麼主意，才有辦法把舊的決定對應到新的方向。如果你把它 clear 掉，它就不知道「之前是什麼」，你也就無法用「把原本的琥珀色重點改成白色」這種相對說法。當時的 context 也還有空間（課程顯示約 275，尚未撐爆），所以壓縮是可行的。壓縮確實花了一些時間，但壓完之後，上下文幾乎空了，只留一份包含原始想法與關鍵概念的摘要。

怎麼判斷你自己該選哪個？動手前先問一句話：我接下來要講的話，是不是在指涉剛剛做的那些決定？如果你的下一句是「re-architect 你剛剛建的系統」「把上一版的重點色換掉」，那你就需要 compact。如果你要開的是一條全新的、檔案裡已經寫清楚脈絡的工作，那就 clear，讓它輕裝上路。

決定二：只換顏色，還是整輪重調

第二個決定是改版的幅度。architect 重跑之後會問你要改到什麼程度，這裡有兩個選項：

幅度做什麼結果
只換顏色把重點色、品牌色調一調，其餘不動改動小，但通常無法還原參考圖的整體感覺
完整重調重新調色，並加上參考圖的組構模式：full-bleed hero 加漸層遮罩、橫向 rail、pill、浮動 tab bar、glass 面板、星等改動大，但這是唯一真的能落地那個 look 的選項

課程選了完整重調，而且它的理由值得記住：光換顏色沒辦法重現參考圖的樣子。因為參考圖之所以像那個樣子，很大一部分來自它的版面組構——海報滿版當 hero、垂直的理由清單、浮動的底部列——這些不是調色盤能解決的。於是原本已經做好的每個元件都保留、但重新對到新配色，同時新增幾種形狀（hero、rail、pill、floating tab bar、glass panel、star rating），讓它們成為之後 feature 可以沿用的新 primitive。

這個決定裡還夾著一個小取捨：glass（毛玻璃）要用在哪裡。它建議只用在 tab bar 和 overlay 上，理由是：如果讓可拖曳的卡片也鋪滿 glass，在中階手機上拖動時容易掉影格。所以「玻璃只在這裡、不在那裡」不是美感偏好，而是效能取捨。

反例：這些判斷什麼時候會翻轉

反例一：全新方向卻捨不得 clear。如果你根本不是要改這條系統，而是要開一條跟前面完全無關的工作，卻還留著一堆舊脈絡，那只是在拖慢它。這種情況 clear 才是對的，因為你的下一步只依賴檔案。

反例二：以為 compact 完就萬無一失。compact 得到的是一份摘要，不是原封不動的記憶，細節終究會掉。所以真正關鍵的決定要落在檔案裡（spec、design.md），而不是只存在於對話。摘要幫你接得上話，但別把它當成紀錄。

反例三：只換顏色卻期待看起來一模一樣。如果你心裡的標準是「要跟參考圖一樣」，那「只換顏色」幾乎一定會讓你失望。要嘛接受它是相近色系、要嘛就選完整重調，兩者要對得上期待。

改完方向之後的完整動作

定案之後，流程回到你熟悉的那條線：重跑 architect（它會說 spec 0004 直接保留、就地更新就好）→ 產出新 spec → 這次因為是設計工作，不必再用第二個模型 cross-check，等能看見畫面時自己把關 → clear → 重跑 develop → 最後 verify。課程在這裡的順序是：

# 1. 保留它記得的東西
/compact

# 2. 把改變講清楚，附上參考圖
re-architect the design system, then redevelop it

# 3. spec 更新後，重跑
clear
develop the design system and the UI foundation

重跑之後的成品明顯更現代：有 hover 動畫、推薦會說明為什麼、有真的登入、feed 的 hero 多了背景大圖、手機底部也有一條可以切換的導覽列。改版後 spec 的功能狀態會停在 in progress，因為還沒驗過——你可以跑 check verify，也可以自己看過覺得沒問題就說「我驗過了」。課程為了保險，選了跑一次 check verify。

小結

看到成品想改方向時，先用一句話判斷上下文：下一句如果是在指涉剛剛做的決定（「把上一版改掉」），就 compact 保留記憶；如果是接一條跟對話無關的新工作，就 clear。改版幅度上，光換顏色通常重現不了參考圖的整體感，要真的落地那個 look，就得完整重調、加入新的組構 primitive。定案後別只在聊天室口頭改，要重跑完整的一輪 architect → develop → verify。

視覺的方向定下來、也重新蓋好了。接下來要驗收的，是這個 app 最核心的一件事：使用者能不能真的登入、滑一輪、然後拿到一份有理由的推薦。下一節就是那條貫穿整個產品的 thin slice。
