/architect 是什麼：一輪只解一個承重決定，並寫成可驗收的 spec

Step 1/4 · /architect：把 Load-bearing 決定寫成 Spec

學習目標

了解 /architect 負責什麼、唯一規則是什麼，以及它在 workflow 中的位置。你也會看到，為什麼它寫出的 spec 是 /develop 建置與 /check verify 驗收共同依循的契約。

前言：上一章留下的那個洞

上一章的 /scope 已經把「產品要做什麼」整理成計畫，卻刻意留下了一個更根本的問題：整個產品要用什麼 stack 和架構？每個功能都要依賴這個答案，但答案還沒確定，就無法開始建置。

這就像房子的隔間、水電和動線都畫好了，卻還不知道地基要打在哪種地質上。計畫雖然完成了，工程還是動不了。

/architect 負責把這個地基問題談清楚、寫下來。它不是用來做簡報，也不是用來寫程式，而是陪你完成一輪決策，並把結論存成檔案，讓後續階段都依循同一份答案。

唯一規則：一輪只解一個 load-bearing 決定

課程用一句話說明 /architect 的核心規則：

Architect 遵守一條會影響所有工作的規則：每次執行只處理一個決定。不是整理整份 backlog，也不是一次決定專案未來所有技術選擇，而是在程式碼依賴某個承重決定之前，把它仔細檢視並寫下來。

這裡有兩個概念需要分清楚。「一輪只處理一個決定」，意思不是一次把專案所有技術選擇談完，而是挑出一個會支撐後續工作的問題，把它問清楚、想透，再寫成文件。

所謂 load-bearing（承重），指的是選錯之後，後續功能或改動都可能受到影響的決定。像是 stack 與架構、auth 的方式、核心資料模型，以及整個 codebase 共用的錯誤處理標準，都是典型例子。

相反地，只改一行 CSS 樣式，就不需要動用這整套流程。課程特別提醒，這種深入討論應該用在「選錯會很貴」的地方，而不是每次小修改都做一輪架構審查。

它的職責：先做結構化探索，再寫下 build spec

/architect 的核心設定寫在自己的 frontmatter 裡，直接看內容最清楚：

---
name: architect
allowed-tools: Bash, Read, Grep, Glob, Write, Edit, Agent, AskUserQuestion
description: "Run /architect when choosing between approaches, designing a feature or page, picking a tech stack, or when /develop says a decision is owed, anytime a load bearing technical decision is unmade. Asks deep questions, recommends an answer, and writes a build spec to docs/specs/. Owns all spec files."
---

這幾行說明了它什麼時候該出場：你需要在不同做法之間選擇、設計功能或頁面、挑選技術棧，或是 /develop 指出還有決定尚未完成時，都可以執行 /architect。

它會深入提問、提出建議，最後把 build spec 寫進 docs/specs/，並負責管理所有 spec 檔案。allowed-tools 則列出它能做的事：讀取與搜尋檔案、寫入與編輯檔案、派出 sub-agent，以及向你提問。

所以，它的產物不是程式碼，而是一份文件。這也是它和其他 skill 最清楚的分工：/architect 負責做決定，不負責建置。

四種模式：取決於「這東西存不存在」

/architect 會依照你要處理的情況，切換工作模式：可能是設計新功能、替新專案選架構、改造既有程式，或制定整個 codebase 共用的標準。

| Mode | When | Design behaviour |
|---|---|---|
| `FEATURE` | Designing a new feature from scratch, with or without existing code | First principles design, best practices, minimal code reading |
| `ARCHITECTURE` | Choosing a tech stack or foundational architecture for a new project | Comprehensive stack evaluation, industry patterns, no code to read |
| `ENHANCEMENT` | Improving, replacing, or scaling something that already exists | Read existing code + specs, focused option comparison |
| `CROSS-CUTTING` | Standardising a pattern across the whole codebase (error handling, logging, auth, naming) | Sample current state, define the standard precisely, recommend enforcement |

判斷時可以先問：「我要處理的東西，現在已經存在於程式碼裡了嗎？」設計新功能，使用 FEATURE；替新專案挑選技術棧或基礎架構，使用 ARCHITECTURE；改善、替換或擴充既有功能，使用 ENHANCEMENT；要統一整個 codebase 的錯誤處理、logging、auth 或命名方式，則使用 CROSS-CUTTING。

接下來示範的決策是選擇 stack 與架構，因此會使用 ARCHITECTURE 模式。

四種操作：create／update／supersede／ratify

除了選擇工作模式，還要決定這次要怎麼處理 spec。操作方式有四種：

- **Create**: new decision → new spec with status `Proposed`
- **Update**: evolving an existing decision → edit existing spec in place
- **Supersede**: replacing a past decision → new spec + update old spec's status line
- **Ratify**: deliberating an `Assumed` spec that `/develop` recorded when the engineer chose to build before deciding → see *Ratify an assumed decision* below

前三種分別是：替新決定建立 spec、直接修改仍在演進的既有決定，以及用新決定取代舊決定，同時更新舊 spec 的狀態。

第四種 ratify 則是確認一項先前暫時採用的假設。如果工程師選擇先建置、之後再決定，/develop 會留下狀態為 Assumed 的 spec。這表示當初先假設事情是這樣，還不代表已經仔細討論並作成決定。

/architect 不會自行建立 Assumed spec，而是針對已存在的假設重新討論，再確認它是否成立、把它補成正式決定，或是推翻它。

為什麼 spec 是契約：狀態反映的是「這功能有沒有 ship」

spec 不只是寫完就放著的企劃書。在這個 workflow 裡，它更像是一份契約，而它的狀態會依照實作進度變化。變化方式取決於 spec 是否連到一個可建置的 scope feature：

Spec status behaves one of two ways, decided by whether a buildable scope feature links the spec (a `docs/scope/` row whose `spec` cell points to it):

- **Feature linked spec** (typical FEATURE/ENHANCEMENT, or an ARCHITECTURE foundation that has a scope row): status mirrors the feature lifecycle. /architect creates it as `Proposed` and owns its content but never advances the status; /develop advances it to `In Progress` when the feature goes in-progress, then `Accepted` when built and verified (scope `done`). Engineer confirmation ratifies content only; `Accepted` means shipped.
- **Standalone decision spec** (foundational/stack or cross cutting standard, no scope row links it): decision status. `Proposed` when written, `Accepted` once the engineer ratifies it on confirmation (the decision is then in force). /develop does not advance it.

有 scope feature 連結的 spec，通常對應一項功能。它的狀態會跟著功能的生命週期前進：/architect 建立 spec，並負責內容，但不推進狀態；/develop 在功能開始動工時將狀態改成 In Progress，等功能建置並通過驗證，也就是 scope 標記為 done 時，再改成 Accepted。工程師確認內容，只代表認可 spec 的內容；Accepted 才表示功能已經交付。

獨立決策 spec 則沒有對應的 scope row，例如基礎架構或跨領域標準。它的狀態代表決定本身：建立時是 Proposed，工程師確認後成為 Accepted，表示決定正式生效。這種 spec 的狀態不會由 /develop 推進。

關鍵分工在這裡：/architect 建立 spec、負責內容，但不推進狀態；功能是否完成，則由 /develop 的實作進度反映。這讓同一份 spec 成為不同階段共同依循的契約：/develop 依它建置，/check verify 依它驗收。三者看的是同一份文件，就能減少「文件寫 A、程式做 B、驗收看 C」的落差。

它不是什麼：三條清楚的界線

先把 /architect 不負責的事記清楚，會更容易理解它的定位。第一，它不寫產品程式碼：

Writes no code. Never updates `AGENTS.md`/`CLAUDE.md` (/sync owns that).

第二，它不是用來一次清掉所有技術債的工具。它每輪只處理一個決定，把討論集中在真正重要的問題上。

第三，它會提出建議，但不會替你默默拍板。它可以研究和比較不同選項，也可以清楚說明自己推薦哪一個；最後的選擇仍由你決定。

把幾個 skill 放在一起看，分工就很清楚：/scope 決定要做什麼（what to build），/architect 決定要用什麼基礎、怎麼設計（on what and how），/develop 負責建置，最後由 /check verify 依照契約驗收。

小結

/architect 負責把承重的技術決定仔細檢視並寫成 spec；每次執行只處理一個決定，不是清 backlog，也不是一次決定所有技術選擇。它會先做結構化探索，再把 build spec 寫進 docs/specs/。它有四種模式：FEATURE、ARCHITECTURE、ENHANCEMENT、CROSS-CUTTING；也有四種操作：create、update、supersede、ratify。

它不寫程式碼，也不更新 AGENTS.md；只有在需要處理「選錯會很貴」的問題時，才需要啟動這一輪決策。它寫出的 spec 是 /develop 建置與 /check verify 驗收共同依循的契約：/architect 建立 spec 並負責內容，但不推進狀態；spec 的生命週期則反映功能是否已經交付，或決定是否已正式生效。
