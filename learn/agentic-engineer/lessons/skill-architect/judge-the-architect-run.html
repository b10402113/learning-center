怎麼判斷一場 architect run 好不好：三個傾向與第二個模型

Step 4/4 · /architect：把 Load-bearing 決定寫成 Spec

學習目標

學會辨認 LLM 的三種傾向，以及各自的反制方法；用 self-check 檢查一場 architect run，並決定何時該讓它挑戰你的前提、何時值得請第二個模型交叉檢查。也要知道 reviewer 可以直接修什麼，以及哪些缺少的決定絕不能由它默默補上。

前言：一份看起來完整的 spec，也可能很危險

前三步帶你認識了 /architect、操作方式和產物。接下來要回答一個更難的問題：run 結束後，怎麼判斷它做得好不好？課程的挑戰單元提醒我們，危險的失敗不一定是計畫明顯出錯；也可能是一份整齊的計畫，建立在你早已忘記的捷徑上。問題不只是有沒有交出文件，而是 agent 是否在你沒注意到的地方，替你做了決定。

判斷之前，先記住：agent 不是中立的。它有自己的「紋理」（grain），會悄悄把產品推向看似合理、卻不完全符合你想法的方向。這一節要做的抉擇是：什麼時候該引導它、什麼時候該讓它挑戰你，以及什麼時候值得請第二個模型檢查。

先看三種傾向：效率與誠實的拉扯

我們希望 run 快速順利，拿到一份乾淨的計畫；但如果計畫太順、太短、太完整，也可能代表模型把不確定的地方直接填平了。以下三種傾向會讓它偏向「看起來順利」，右欄則是把它拉回來的方法。

傾向它怎麼把你帶偏反制方法
想同意你（wants to agree）人類偏好合作、認同既有信念的回答，模型因此容易接受你的前提。你若說「這基本上就是 Uber 版的遛狗服務」，它可能就照 Uber 的樣子規畫，即使這個比喻掩蓋了產品真正不同的地方。當 /architect 挑戰你的前提，可能正是在抵抗它想同意你的本能。別只因為它拖慢進度，或質疑你喜歡的點子，就直接推翻它；先看清楚顧慮，再判斷哪些是真的。
伸手拿常見答案（reaches for the common answer）模型從大量既有作品中學習模式，因此第一個建議往往適合「最典型的專案」。它能理解你說的話，卻感受不到你的商業風險、團隊壓力、個人限制，或尚未釐清的疑慮。要求它說明每一層的建議、簡短理由，以及可信的 runner-up（次佳選項）。別只看工具名稱，要檢查理由是否符合你的處境，還是只在描述「平均專案」適合什麼。
想看起來完成（wants to look finished）乾淨完整的計畫看起來比較有幫助，所以模型容易補上缺口、抹平不確定，交出一份彷彿能立刻採用的方案。危險之處在於，它可能用看似合理的選擇填滿空格，讓人以為那個決定早已做過。讓訪談花足夠時間，特別是那些常被拖到上線前才處理的跨領域問題：存取、所有權、隱私、失敗行為、權限和生命週期規則。這些事在第一個 demo 裡不吸睛，卻會影響後續設計。

這三種傾向也說明了：訪談短得出奇時，應該提高警覺，而不是急著稱讚它有效率。

spec 寫完後，何時要 cross-check？

spec 寫完後，/architect 會問你是否要請另一個模型獨立檢查。它會依功能的 workflow tier 提出建議，但有一條原則不變：它會問你，絕不替你決定要跑還是跳過。要不要交叉檢查，仍然由你選擇，才能讓承重決定保持在你的注意範圍內。

tier建議判斷理由
GA 或 Beta強烈建議選「Another model」承重缺口可能造成真實傷害；促使你想做這項檢查的 bug，通常也屬於 Beta 級功能。
Alpha基礎或高風險的 spec 建議選「Another model」，其他情況不強推依這份決定有多關鍵而定。
Prototype（或沒有 scope row）建議選「Skip」；基礎 spec 可考慮「Same model」這個階段出錯的代價還不高，通常不值得多跑一輪。

可選的方式有四種：

  - `Another model`: a read only critique pass on a different, capable model, which catches what the model that wrote the spec is blind to.
  - `Same model`: a read only critique pass on this same model (a fresh eyes critique of its own work).
  - `I'll review it myself`: no AI critique; show the spec and let the engineer scrutinise it.
  - `Skip`: go straight to accept.

用幾個問題做判斷

決定要不要 cross-check 時，可以先問自己：

  • 這是 GA 或 Beta 功能，承重缺口可能造成真實傷害嗎？如果是，建議請另一個模型檢查。
  • 這是 Alpha 功能嗎？如果是，它的 spec 是否基礎或高風險？這會影響是否值得多跑一輪。
  • 這是 Prototype，或沒有 scope row 嗎？如果是，錯誤代價較低，通常可以跳過；基礎 spec 則可考慮讓同一個模型重新檢查。
  • 你是否希望由自己檢查，或直接接受 spec？選項分別是「I'll review it myself」和「Skip」。

Another model 適合用在專案基礎的 spec：後續每個切片都會繼承它，因此這裡的承重缺口代價很高。寫 spec 的模型也不容易看見自己的盲點，換一個模型，就像請一位從不同角度切入的審查者。這項檢查是唯讀的：它只讀 spec、回傳評論，不會直接修改內容；真正的修正仍由主線處理。

reviewer 要檢查什麼？哪些事不能替你做？

如果你選擇 cross-check，reviewer 有兩項明確任務：

  1. **Decision completeness (the primary job).** List every value each action, endpoint, or read path must produce, compute, or display to satisfy the acceptance criteria whose **source the spec does not name**, and every decision the builder will have to make that this spec does not settle. This is the check that catches a load bearing gap the spec author's own introspection missed (e.g. an AC that needs "the user's local day" with no timezone source named). Report each as a gap to close before build, not a nitpick.
  2. **Soundness.** Does the design hold up? Is there a materially simpler option? What failure mode is missed?

第一項是主要工作：檢查決定是否完整。reviewer 會列出每個為了符合驗收條件而必須產生、計算或顯示的值，尤其是 spec 沒有交代來源的值；也會找出建置者仍得自行決定的事項。舉例來說，驗收條件要求「使用者的本地日期」，spec 卻沒說時區從哪裡來，這就是必須在建置前補上的缺口。

第二項是檢查設計是否健全：設計撐得住嗎？有沒有明顯更簡單的做法？漏掉了什麼失敗模式？

不過 reviewer 有一條底線：絕不默默補上缺少的決定。否則只是用一個模型沒說出口的選擇，取代另一個模型沒說出口的選擇。它會列出每個重要缺口、提出建議，再問你如何處理：

   Brief it to NOT fetch the spec's reference links, now or later (human facing). Surface its findings as a short "Cross check" note. **Do NOT silently resolve or auto edit a decision completeness gap** (each one is a load bearing decision, and those are the engineer's, not yours): list every gap with the resolution you recommend (the source you would name, or the answer you would pick, always give your best recommendation, do not just present options), then ASK how to proceed, `Apply the recommended fixes` (recommended) · `Let me answer each one` · `Leave them, I'll decide later`. Edit the spec only on the engineer's pick. Pure soundness nitpicks (not a decision, e.g. a clearer wording) you may fix directly and note. No subagent capability → do the same model pass inline on the main thread (weaker, note that the independent check did not run).

因此，只有無害的措辭問題和機械性的不一致可以直接處理。凡是會改變行為、所有權、風險或架構的內容，都要留給你決定。示範中，講者選擇套用所有建議修正；面板也提供逐題回答的選項。

反例：reviewer 找到的缺口，不一定屬於這份 spec

示範中的 reviewer 確實抓到一個該修正的問題：spec 把上傳流程描述成受 row level security 保護，但實際上，已簽署的上傳 URL 是在簽發時由 service role 授權、取用時由 token 授權，並不是靠 table policy。這裡是講者把保護方式說得太滿，因此應該修正措辭。

但 reviewer 也提出五個缺口：pin 的座標參考框架、pin 編號、已讀狀態、soft／hard delete，以及 foreign key 行為。講者判斷，這些屬於資料模型 spec，而不是目前這份 spec 的責任。它們應記成「欠給資料模型那個 feature」，而不是硬塞進來。這是個重要的反例：不是每個被指出的缺口都要在眼前這份文件裡解決，否則一份 stack spec 可能膨脹成無所不包的巨型文件。

另一個反例是 tier。若功能屬於 Prototype，或根本沒有 scope row，正確選擇往往是 Skip，並非每次都要請第二個模型出場。缺口是承重決定，應由你來做；而正因為它們重要，是否 cross-check 也必須是經過判斷的取捨。

接受 spec 前，做一份 self-check

按下接受之前，可以問自己幾個問題。檢查的不只是 agent，也包括你是否真的在指揮它，而不只是使用它：

  • 你選的 build approach，真的針對了最大的風險嗎？還是只採用了 agent 推薦的第一個選項？
  • workflow tier 符合你正在建的東西嗎？它是週末實驗、個人工具，還是別人會依賴的真實產品？
  • 你理解每個架構建議背後的理由嗎？還是因為工具名稱熟悉，就輕輕帶過了幾個選擇？
  • spec 產生的值、狀態、權限和行為，都有交代來源嗎？還是描述模糊到讓 /develop 得自己發明？

決策規則：先看 tier，再守住決定權

用三個問題檢查一場 /architect：它有沒有抵抗「想同意你」的傾向，真正挑戰你的前提？每層建議有沒有附上理由和可信的 runner-up，讓你能對照自己的處境？訪談有沒有花足夠時間處理跨領域問題，而不是把缺口抹平？cross-check 則依 tier 決定：GA／Beta 強烈建議請另一個模型；Alpha 視 spec 是否基礎或高風險而定；Prototype 或沒有 scope row，通常建議 Skip。最後由你選擇是否執行。reviewer 只檢查決定完整度與設計健全度；它可以直接修無害措辭和機械性不一致，但會把任何影響行為、所有權、風險或架構的缺口留給你決定。漂亮完整的 spec，不代表過程中沒有走過捷徑。

到這裡，/architect 的流程就走完了：從了解它的用途、執行方式與產物，到判斷如何驗收。下一步是把決定交給 /develop，依照 spec 真正建立專案。
