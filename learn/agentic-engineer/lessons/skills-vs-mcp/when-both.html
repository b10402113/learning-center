何時只要 skill、何時要接 MCP、何時兩個都要

Step 3/4 · Skills vs MCP：何時用哪個

學習目標

用一條可操作的規則，判斷某個工具你該帶一個 skill、接一個 MCP，還是兩個都要。

前言：兩半都懂了，但你還缺一把尺

前兩節你把兩半都看過了：skill 帶的是這個工具現在真正的慣例，MCP 連的是你自己那個實例。分開講都清楚，可是當你面對一個具體的工具——Supabase、Stripe、Next.js——心裡還是會冒出那句：那我到底該帶哪一個？

這裡有兩股力量在拉扯。一邊是「兩個都有最強」：知道怎麼寫、又碰得到真的東西，agent 自然最好用。另一邊是成本：接一條 MCP，就多一個會壞的依賴，也多交付一份通往你真實系統的權限。所以答案不會是「能接就接」。這一節給你的，是一把可以自己問自己的尺。

先把四個選項並排看清楚

面對一個工具，你其實有四種姿勢，不是二選一。先把它們攤開來比：

你的選擇你得到什麼什麼時候這樣就夠／該這樣
只要 skillagent 用這個工具現在正確的慣例寫程式你只需要寫對，不需要碰任何真實實例
只要 MCPagent 碰得到你真實的資料與實例很少單獨足夠：連得上，卻可能用過期做法操作
兩個都要知道怎麼寫，也碰得到真的東西這個工具的資料是活的，而且它的做法常改
都不要省下依賴與權限，靠模型自己的記憶工具穩定、你也不需要碰真實實例

看這張表你會發現，「只要 MCP」幾乎不是一個好答案。因為連線解決的是「有什麼」，一旦 agent 要用過期的做法去操作你真正的資料，反而更危險。實務上，你通常是在「只要 skill」「兩個都要」「都不要」之間選。

兩個判別問句，問自己就好

把上面的表濃縮成兩個可以當場問自己的問句：

第一問：我需要 agent 寫出這個工具「現在正確」的程式碼嗎？尤其是它改得快、模型記憶容易過期的時候。是，就帶一個 skill。
第二問：我需要 agent 碰到你自己那一份活的資料或實例嗎？你的表、你的資料、當下的狀態。是，就接一個 MCP。

兩個都是「是」，答案就是兩個都要——這也是真實專案最常出現的情況。第一問是「是」、第二問是「否」，帶 skill 就好。兩問都是「否」，那就什麼都不用加。

規則什麼時候會翻轉

這條規則有幾個會翻過來的地方，要特別小心。

第一，當工具很穩定、模型記憶也夠、你又沒有真實實例要碰，那兩個都不必。別因為「skill 聽起來很新」「這個 MCP 很有名」就裝——你沒有要用到它解決的問題，加了只是負擔。

第二，也是最常見的翻車方式：因為「可以接」而接。很多人看到某個服務有 MCP，就順手接上一條通往真實系統的線，但其實根本不需要裡面的資料。結果只換到一個會壞的依賴、一份要顧的權限，什麼都沒得到。要接，是因為你的任務真的需要活的、會自己變的資料，不是因為它存在。

第三，反過來也成立：如果你明明需要碰真實資料，卻只帶了 skill，agent 會很有自信地照著官方慣例，去操作一個它其實沒看過的系統。這種錯最難抓，因為程式碼看起來完全正確。

小結

面對一個工具，先問兩個問題：我需要 agent 寫出它現在正確的程式碼嗎（要 skill）？我需要 agent 碰到我自己那份活的資料或實例嗎（要 MCP）？兩個都「是」就兩個都要，這最常見。只要其中一個「是」，就只需要那一個。兩個都「否」，就都不要加。切記不要因為「可以接」而接——線要開，是因為任務真的需要活的資料，不是因為它存在。

規則有了，但把它套到整個技術棧上，是一件很煩的苦工：每個工具都要找 skill、找 MCP、再一個一個手動接。下一節要講的，就是那套 workflow 怎麼替你接走這件苦工——以及它刻意留下、要你親自動手的兩個動作。
