MCP 連的是「你自己那個實例」

Step 2/4 · Skills vs MCP：何時用哪個

學習目標

說出 MCP 連的是「你自己那個實例」，並在 Supabase 這個例子上，分辨它與 skill 各自負責哪一半。

前言：知道怎麼寫，不等於知道裡面有什麼

上一節講完 skill，問題看似解決了：agent 現在知道 Supabase 的正確做法，總該可以放心交辦了吧？還不行。

因為就算它寫得出完全正確的 Supabase 程式碼，它仍然不知道一件事：你自己那個 Supabase 專案裡，到底有哪些表、有哪些資料、現在是什麼狀態。它掌握的是一門語言的文法，不是你手上那份資料的內容。

打個比方：一個人把菜譜背得滾瓜爛熟，不代表他知道你家冰箱裡還剩什麼。這一節要處理的，就是那台冰箱。

MCP 不教慣例，它接上你真實的專案

MCP（Model Context Protocol）同樣綁在特定工具上，但它做的事和 skill 完全不同。一個 Supabase 的 MCP server 不會教你 Supabase 的慣例，它做的是把 agent 接到你真正的那個 Supabase 專案：你真實的表、你真實的資料、對著真實物件下的查詢，而不是「我猜裡面應該長這樣」的假設。

換句話說，skill 給你的是「怎麼寫才對」，MCP 給你的是「你手上到底有什麼」。一個是知識，一個是連線。

在同一個工具上，一次看到全貌

Supabase 這個例子好懂，是因為在同一個工具上就能看清楚兩半的分工：skill 知道怎麼寫出正確的 Supabase 程式碼，MCP 則伸進你那個還活著的 Supabase，對著真正存在的東西工作。

用一個日常的譬喻記住它。skill 像一位熟悉會計準則的會計師，他知道帳怎麼記才合規；MCP 則像你把家中帳本的鑰匙交給他，他因此能翻到你真正的帳目，而不是憑空猜你的收支。會計準則再熟，少了那把鑰匙，他還是看不到你家帳本。兩者缺一，故事就講不完整。

為什麼要把它們分成兩件事看

分開看，你才不會把「agent 寫得出正確的程式碼」誤當成「agent 懂我的系統」。前者是慣例問題，後者是連線問題，兩者的解法完全不同。

只顧其中一個都會撞牆。只給 skill，它寫得再對也碰不到你的資料，只能憑假設；只給 MCP，它連得上你的實例，卻可能拿過期的做法去操作你真實的資料。很多時候你需要兩個一起上，這正是下一節要做的決定。

小結

MCP 也綁在特定工具上，但它不教慣例，它把 agent 接到你自己那個實例：你真實的表、真實的資料、真實的查詢。在同一個工具上，例如 Supabase，你可以清楚看到兩者的分工：skill 負責「知道這工具怎麼運作」，MCP 負責「有一條通往你實例的線」。一個是知識，一個是連線，做的是不同的事。

把這兩個觀念掛在一起記：skill 是「文法書」，MCP 是「鑰匙」。既然它們是兩件事，「什麼時候只要一個、什麼時候兩個都要」就成了你必須做對的決定，下一節給你的，就是判斷這件事的一把尺。
