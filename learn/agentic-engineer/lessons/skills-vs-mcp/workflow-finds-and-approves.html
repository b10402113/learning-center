讓 workflow 幫你找，但你來放行

Step 4/4 · Skills vs MCP：何時用哪個

學習目標

說出 workflow 如何自動找出並接上你 stack 需要的 skills 與 MCPs，以及為什麼安裝與真實帳號登入這兩個動作要留給你。

前言：規則有了，但整件事做起來很煩

上一節你拿到了一把尺：用兩個問句，就能判斷一個工具該帶 skill、接 MCP，還是兩個都要。一把尺很好用，但它一次只量一個工具。真實的專案不會只有一個工具，而是一整排：Supabase、Stripe、Next.js，還有你自己加進來的那幾個。

於是把規則老老實實套到整個技術棧上，就變成一件煩人的苦工：對每一個工具，你都要先找到對的 skill，再找到對的 MCP，然後把它們一個一個手動接起來。這一節要講的，就是那套 workflow 怎麼替你接走這件苦工，以及它刻意留下、要你親自動手的兩個動作。

原本這是一件純手工的苦工

先看清楚這件事原本有多瑣碎。你的 stack 裡每多一個工具，就多一份工：去找這個工具對應的 skill、去找它的 MCP server、確認兩者都沒問題、再逐一設定接上。工具一多，光是把這一排張羅齊，就足以吃掉你半天的注意力。更糟的是下一次換 stack，一切重來。

這正是 workflow 賺到它存在價值的地方。你在一個專案上跑它，它會去看你實際在用的工具與技術棧，然後自動找出這些工具對應的 skills 與 MCPs。你不必自己一個個逛、一個個搜。

它幫你找，但不會偷偷全裝

這裡有一條很重要的分界，也是這一節真正要你記住的：它幫你找，但不會背著你把所有東西裝上去。它會在安裝之前先問你，由你決定哪一些要真的進來。

而對那些需要連上你真實帳號的 MCP，例如登入你真正的 Supabase，那一步更是明確屬於你的。你得親自登入、親自批准它存取。workflow 可以幫你找到它、把線牽到門口，但推門進去、交出權限的那個動作，是你做的。

為什麼要留這兩個動作給你

把「找」和「決定」分開，不是多此一舉。這兩件事的性質本來就不同。

找，是繁瑣、可重複、機器做得又快又不會累的部分，而且答案不因你是誰而改變：Supabase 的 skill 在哪裡，對誰來說都是同一個答案。決定要不要把某個東西裝進你的環境、要不要把通往真實系統的權限交出去，則是帶著後果的判斷。你的 stack、你的資料、你願意承擔的風險，恰恰只有你知道。

所以這套 workflow 的形狀是：系統做繁瑣的部分，你做決定。它不會偷偷替你把所有東西裝好，也不會替你按下授權。它還把狀態存在檔案裡，而不是存在某一次對話的記憶中，所以它認得你的專案、跨 session 都還在，換個人接手也讀得到同一套設定。

小結

對整個技術棧手動張羅 skills 與 MCPs 是一件苦工。workflow 會看你實際在用的工具與 stack，自動找出對應的 skills 與 MCPs，替你省下這一段。但它不會偷偷全部裝上去：安裝前會先問你，而對需要連上你真實帳號的 MCP，登入與授權那一步由你親自完成。分工很清楚：系統做繁瑣的部分，你做決定。

走到這裡，skills 與 MCPs 的全貌就拼完了：它們各自是什麼、怎麼讀與寫一個 skill、以及它們在真實專案上、面對每一個工具時怎麼現身。接下來鏡頭要拉遠：一個真實的 build，用舊方法和用這套 workflow 各做一次，並排放在一起，你會親眼看到，為什麼這樣一套系統值得存在。
