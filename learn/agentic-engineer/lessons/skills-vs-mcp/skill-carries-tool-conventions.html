Skill 帶的是工具「現在真正的做法」

Step 1/4 · Skills vs MCP：何時用哪個

學習目標

說出 skill 為什麼能讓 agent 跟著某個工具「現在真正的做法」走，以及它補的是訓練資料過期造成的哪個缺口。

前言：模型腦中的 Supabase，可能停在兩年前

上一節你把 skill 本身摸清楚了：它是一份按需載入的操作說明書，description 決定它什麼時候啟動，body 才是真正的工作指示。但那份說明書，絕大多數時候不是為「通用的程式設計」而寫，而是為「某一個特定工具」而寫。

想像你請 agent 幫你寫一段 Supabase 的登入流程。它會動手，而且看起來有模有樣。問題出在，它腦中那套「Supabase 該怎麼用」的印象，是你訓練它那一刻的樣子，不是今天的樣子。Supabase 這類工具改得快，auth 的設定方式、row-level security 的寫法、當下的 API，這幾年都動過。模型半記得的東西，很可能早就過期了。

這一步要講的就是 skill 在這裡扮演的角色：它不是讓模型變聰明，而是把「這個工具現在真正的做法」補給它。先把這件事講清楚，下一節才分得出 MCP 做的是完全不同的另一半。

模型靠記憶，但工具不會停下來等它

每個模型都有一個訓練資料的截止點。截止點之前，它讀過大量的程式碼與文件；截止點之後發生的事，它一概不知道。對變化慢的東西，例如一門語言的基本語法，這沒什麼大不了；但對一個每幾個月就改版一次的工具，這個落差會直接變成錯誤的程式碼。

所以「模型半記得」才是一件危險的事。它不是在亂猜，而是很有自信地寫出一段「以前正確、現在已經不是那樣」的程式碼。你如果對這個工具不夠熟，根本看不出哪裡過期了，還可能照著它一路錯下去。

Skill 把「現在真正的慣例」直接帶進來

一個為某個工具而寫的 skill，做的事情很單純：它把這個工具現在真正的慣例，用文字寫清楚，交給 agent。以 Supabase 為例，這份 skill 會說明現在的 auth 該怎麼設、row-level security 該怎麼寫、當下的 API 長什麼樣，以及 Supabase 團隊實際推薦的做法。

裝上它之後，agent 寫 Supabase 程式碼時，參照的就不再是它半記得的舊印象，而是這份跟著工具一起更新的說明。它從「猜」變成「照著現在的做法寫」。

同樣的模式套在整個技術棧上：一個 Next.js skill、一個 Stripe skill、一個 Prisma skill，每一個都是把「那個工具現在真正的用法」寫下來，讓 agent 不再對那些可能早就改過的 API 憑記憶下手。

反過來看：不是每個工具都值得寫一份 skill

skill 的價值，和「這個工具變化有多快」成正比。如果某個工具很穩定、官方文件好找、模型在訓練時也讀得很熟，那你補一份 skill 能得到的差距就有限。真正值得為它寫 skill 的，是那種「用的人多、改得快、又有明確官方推薦做法」的工具。因為在這種工具上，模型的記憶最容易過期，而你最需要它跟著現況走。

換句話說，skill 補的不是「模型不懂這個工具」，而是「模型的認知停在過去」。它是一份會跟著工具一起更新的現況說明，不是一本通用的教科書。

小結

很多你真正會用到的 skill，都是為某個特定工具而寫的。它把這個工具現在真正的慣例——auth 怎麼設、row-level security 怎麼做、現在的 API、官方推薦的模式——直接交給 agent，補上模型訓練資料過期造成的那個缺口。工具改得越快，這份 skill 越有價值；它的作用不是讓模型更聰明，而是讓它照著現況做事，而不是憑半記得的舊印象。

到這裡為止，skill 負責的是「知道這個工具怎麼運作」。但還有另一半沒解決：就算 agent 知道怎麼寫正確的 Supabase 程式碼，它仍然不知道你自己的資料庫裡有什麼。下一節要看的，就是補上這另一半的 MCP。
