兩個風險方向：agent 放進來的、你交給它的

Step 2/4 · 沒有白紙：Brownfield 的風險

學習目標

分辨在舊碼庫上用 AI 的兩個風險方向——agent 放進專案裡的東西，以及你交給 agent 的東西——並說明為什麼這是商業與安全決策，不只是寫程式決策。

前言：安全的問題有兩個門

上一節我們看到 agent 在舊碼庫失手的根因：它沒有地圖，只能猜。但那還只解釋了「改出來的東西可能不對」。真正的公司在意的，往往不只對不對，還包括「有沒有東西跑錯方向」。

想像公司大樓的兩道門。一道是進貨門，所有東西從這裡進來；另一道是出貨門，所有東西從這裡出去。多數人談 AI 風險時只盯著其中一道，另一道卻常常沒人看。而在舊碼庫上用 AI，剛好兩道門同時開著。

這一節就把這兩道門分開講清楚。看清楚之後，你會發現「在真實碼庫上用 AI」根本不是單純的寫程式決定。

方向一：agent 放進專案裡的東西

第一個風險方向，是 agent 往你的專案裡加進了什麼。常用的 coding agent 會寫程式碼、改設定、動資料庫與權限，所以它有機會在不經意之間放入這些東西：

  • 不安全的程式碼，例如沒有檢查輸入、或用了已知有問題的寫法。
  • 外洩的密鑰，例如把一組金鑰直接寫死在原始碼裡，然後被 commit 進版控。
  • 被放寬的存取規則，例如原本該擋的權限被順手打開了一點。
  • 沒人批准的重要決定，例如它自己選了一個服務架構或資料模型，而那個選擇從此留在系統裡。

這些東西的共同點是：當下看起來都像「順手做的小事」，但每一個都會留在專案裡，跟著之後的每一次部署活下去。在你自己專案上，這頂多讓你不舒服；在公司專案上，它會變成一個沒人記得為什麼存在的風險點。

值得注意的是，workflow 本身對其中一類已經內建了防線。例如在處理外部服務時，它規定密鑰要從環境讀取，而不是寫進程式碼：

- It wires any outside service the spec chose, reads secret keys from the environment rather than writing them into the code, and adds logging at the edges.

這條規則管的是「進貨門」：它降低 agent 把密鑰寫進去的機會。但它管不到後面要講的另一道門。

方向二：你交給 agent 的東西

第二個方向反過來：不是 agent 放進來什麼，而是你把什麼交出去。當一個 agent 服務在遠端跑，你送進去的內容會經過供應商。在真實專案裡，你交出去的可能是：

  • 原始碼——整包私有邏輯。
  • 憑證——金鑰、權杖、連線字串。
  • 客戶資料——真實使用者的姓名、聯絡方式、任何個資。
  • 私有商業邏輯——那些「為什麼這個服務有三個版本」之類的內部知識。

這些東西會不會離開你的組織、離開之後被怎麼處理，取決於你用哪個工具、以及你的帳號與環境怎麼設定。換句話說，這一方向的閘門不在 workflow 手上，而在你的供應商選擇與公司政策手上。

把兩欄放在一起看，就會發現它們的性質完全不同。左邊那欄是「工程品質」問題：這裡寫得對不對、有沒有違反既有規則，可以靠流程與審查慢慢收緊。右邊那欄是「治理」問題：東西該不該交出去、交出去之後誰負責，這不是把程式寫好就能解決的。

所以這是商業與安全決定

課程下的結論很直接：在真實碼庫上用 AI，是一個商業與安全的決定，不只是寫程式的決定。因為它同時牽涉到「改壞東西要付出的成本」（方向一），以及「資訊離開組織要付出的代價」（方向二）。前者影響交付，後者影響的是信任、合約與法規。

這個區分之所以重要，是因為它會決定你該去問誰。純粹的程式問題，你可以自己判斷；但「哪些公司資訊能讓模型看見」，你通常得回去問公司的資安政策或法遵要求，而不是自己想辦法。

小結

在舊碼庫上用 AI，有兩個方向的風險要分開看。方向一是 agent 放進專案裡的東西：不安全的程式碼、外洩的密鑰、被放寬的存取規則、沒被批准的決定——這靠 workflow 的流程與審查來管。方向二是你交給 agent 的東西：原始碼、憑證、客戶資料、私有商業邏輯——這靠供應商選擇、帳號設定、公司政策與安全要求來管。因為兩者同時存在，所以這是一個商業與安全的決定，不只是寫程式的決定。

分清了兩個方向，下一節就可以回來看 workflow 到底修好了什麼。它主要治的是方向一：用「先理解、再安全地改」把 agent 從猜測變成有地圖、有邊界、有證據的工作方式。至於方向二，workflow 自己跨不過去，那是再下一步要談的界線。
