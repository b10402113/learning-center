agent 為什麼在舊碼庫失手

Step 1/4 · 沒有白紙：Brownfield 的風險

學習目標

說明「改別人寫的舊系統」才是工程常態，並指出 agent 真正失手的原因是它只有程式碼（what）、沒有地圖（why），所以只能猜。

前言：那個不是你蓋的系統

你到目前為止動手的專案，幾乎都是自己的。開一個空資料夾、選一套技術棧、自己訂規則，然後照你的意思把東西蓋起來。這種專案很舒服，因為整張圖都在你腦子裡：哪個模組在幹嘛、哪一行是為了繞過什麼鳥問題而寫的，你都記得。

但這種專案其實是例外。真正的公司裡，你多半是被丟進一個已經跑了好幾年的系統：別人在幾年前設計的、當初的幾位作者早就離職了，而且現在真的有使用者在依賴它。你的工作通常不是重寫，而是改它——加下一個功能、修一個沒人敢碰的 bug。

前面幾節我們學會了九個 skill 的 workflow，也看過 agent 怎麼讀你的程式庫：它沒有索引，靠著 grep、glob、read 在現場找路。不過那些討論都還站在「自己的專案」上。這一節要把鏡頭轉到真實世界的預設情境——舊碼庫——因為很多人正是在這裡試了 AI、拿到了不理想的結果，然後下結論說「它做不了真軟體」。問題通常不在它不會寫程式，而是另一件事。

生成一個乾淨專案很簡單，讀懂一個舊系統很難

先把兩件事分開看。從零生成一個乾淨的專案，對 agent 來說並不難：沒有歷史包袱、沒有隱藏假設、沒有互相牽制的慣例，它只要照著你選的技術棧產出一套合理的結構就好。這也是為什麼「demo 看起來超神」的那種影片，通常都在空資料夾上表演。

真正困難的是另一邊：讀懂一個大型、寫了很多年、充滿沒寫下來的慣例與隱藏假設的既有碼庫。這種系統的難度不在檔案數量，而在於那些「大家都知道、但沒人寫在文件裡」的規則。它們只存在於某些人（而且可能已經離職）的記憶裡。

它有的是「程式碼」，缺的是「地圖」

agent 在舊碼庫失手的根因，課程用一句話講得很清楚：它沒有地圖。

它能讀出程式碼「寫了什麼」（what），卻讀不出「為什麼存在」（why）。課程給了兩個很典型的例子：同一個服務為什麼同時存在三個版本？某一行看起來沒用、甚至有點怪的程式碼，為什麼其實是在擋一個正式環境的故障？這些問題的答案，沒有一行寫在程式碼裡。

你可以把這想像成接手一棟別人的大樓。你手上有每一間房間的照片，看得到每個房間長什麼樣子，卻沒有那張平面圖。於是你不知道哪面牆是承重牆、哪條走道其實是逃生動線、哪裡絕對不能敲。照片再清楚，也不能取代平面圖——而 agent 在舊碼庫裡的處境就是這樣：房間（程式碼）它看得一清二楚，平面圖（為什麼）它手上沒有。

沒有地圖，它就只能猜

少了這層脈絡，agent 不會停下來說「我不知道」，它會猜。麻煩的是，它猜得往往很乾淨、很有自信。一份看起來很合理、通過你眼睛掃描的改動，可能在不知不覺中違反了一條這個專案依賴多年的規則。它不知道有這條規則，所以也不會告訴你它踩了。

這正是它跟「能力不足」的差別。問題不是模型不會寫程式，而是它在一個自己只看到一半的系統裡做決定。這也是為什麼同一套 agent，在空專案上像個高手，進了舊碼庫就開始出包。

代價也不一樣了

在你自己那個 side project 上，改壞一個東西最壞的結果，大概就是花掉你一個下午去收拾。但在公司裡，同一個改動可能影響到客戶、營收、私有資料，或是一整條正式環境的服務。分母變了，風險的尺度也就跟著變了。

所以「在舊碼庫上用 AI」這件事，不能只看它像不像會寫程式。後面幾節會把它拆成兩個方向的風險來處理——那才是它真正需要被管的地方。

那張缺失的地圖，workflow 幫你補上

既然根因是「沒有地圖」，那第一步自然是先把地圖建出來。課程的 workflow 裡，負責這件事的是 /audit：它讀這個專案真實的程式碼、歷史與既有檔案，把資深工程師在第一天會跟你講的那些事寫下來——技術棧、常用的指令、程式碼遵循的模式，以及新人容易漏掉的細節。而這張地圖會落地成什麼檔案，官方指南寫得很具體：

| `audit` | Writes the context files that tell every other skill how your project works. |

這些「context files」之所以能當成一張地圖，是因為它們是給任何 coding agent 讀的純文字檔，而且會分層擺放——根目錄放全專案的規則，特定資料夾再放只有那區要遵守的規則。當某個 skill 要走進某個區域時，它讀最靠近的那一份，於是同時看到全專案與當地的規則。換句話說，那個「為什麼」如果被寫進地圖，agent 就不用再猜。

**The context files, named `AGENTS.md`.** These describe how your project actually works, its stack, its commands, its conventions. They are written in plain text that any coding agent can read. On a project that uses Claude Code there is also a tiny `CLAUDE.md` that does nothing but point at `AGENTS.md`, so there is only ever one real source and no copy to drift.

這張地圖的細節，以及它怎麼跟後面幾個 skill 接起來，留到下一節再展開。這裡先記住它的角色就好：它是對「agent 只看到一半系統」的直接回應，把 agent 猜不出來的那些架構、慣例、指令與邊界，事先寫成檔案。

小結

真實的工程很少有白紙，改別人寫的舊系統才是常態。agent 在舊碼庫失手，通常不是因為它不會寫程式，而是因為它沒有地圖：它讀得出程式碼「寫了什麼」（what），卻讀不出「為什麼存在」（why）。少了這層脈絡，它只能猜，而且猜得乾淨又有自信。workflow 的第一個動作，正是用 /audit 把這張缺失的地圖補上。

不過在談「workflow 怎麼救」之前，得先看清楚它要處理的是什麼問題。下一節會把風險拆成兩個方向：一個是 agent 放進專案裡的東西，另一個是你交給 agent 的東西。看懂這兩個方向，才知道為什麼整件事不只是寫程式的決定。
