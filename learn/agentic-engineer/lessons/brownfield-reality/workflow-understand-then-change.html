把 workflow 對上問題：先理解，再安全地改

Step 3/4 · 沒有白紙：Brownfield 的風險

學習目標

用「先理解、再安全地改」兩個工作把 workflow 對上舊碼庫問題：/audit 建地圖、/architect 決策前先讀現況、/develop 先讀再寫並沿用既有模式、/check verify 在真 App 內證明不破壞行為、/check review 交給第二個模型。

前言：同一套流程，換一個起點

前兩節把問題的兩面都攤開了：agent 在舊碼庫失手，是因為它沒有地圖；而在真實專案上用 AI，又同時牽涉交付風險與資訊外流的風險。這一節要回頭看那套你已經學會的 workflow，問一個很實際的問題——它在舊碼庫上到底修好了什麼？

先回想一下新專案的流程：你決定這個系統該長成什麼樣，然後把它建出來。起點是一張白紙，你先想、再做。可是在既有專案上，起點完全相反：系統已經存在了，而且不是照你的意思長的。所以你的第一責任不是「決定它應該是什麼」，而是先搞清楚「它現在是什麼」。

課程把這件事收束成兩個工作，而且順序不能顛倒：先理解，再安全地改。這一節就把 workflow 的每個 skill 對上這兩個工作，看看它們各自補上了哪一段。

第一個工作：理解它（先把地圖建出來）

既然 agent 猜測的根因是「沒有地圖」，那麼 workflow 的第一步就是把地圖建出來。負責這件事的是 /audit。它讀真實現有的程式碼、歷史與專案檔案，把 agent 不可能安全地自己發明的東西寫下來：架構、慣例、指令、邊界與規則。

地圖建好之後，還有一個關鍵的用法：不要把整個 repo 一次丟給 agent 去理解。課程的說法是，你交給它那張專案地圖，再加上這次任務真正需要的那一小塊。這聽起來像是省成本，其實更重要的是省注意力——一次讀進整個大型碼庫，反而會讓它抓不到重點。地圖加上一小塊的組合，才是它在大型系統裡能好好工作的形狀。

而地圖之所以能分塊使用，是因為 AGENTS.md 這類 context file 會分層擺放。某個 skill 走到哪一區，就讀最靠近那一區的那一份：

The key idea is that these files nest. There is one at the root of the project for rules that apply everywhere. There can be more inside folders for rules that apply only to that area. For example a project might have a root `AGENTS.md` and also a `src/payments/AGENTS.md` that records rules only the payments code follows. When a skill works on the payments code, it reads the nearest one, so it sees both the project wide rules and the local ones. `audit` creates these files. Every other skill reads them. `sync` keeps them current as the code changes. No skill guesses your conventions when a context file already states them.

最後一句話很值得停下來想：「當 context file 已經寫明慣例，就沒有 skill 需要去猜你的慣例。」這就是整節的核心——把「猜」換成「讀」。

第二個工作：安全地改它（讓每個動作都有依據）

地圖存在之後，改動就可以開始了。但「安全地改」不是一句口號，它是由幾個 skill 各管一段拼起來的。課程把這幾段講得很清楚：

Skill在「安全地改」裡負責哪一段
/architect在做決定之前，先讀現有的實作，而不是憑空設計
/develop先讀再寫，並沿用專案裡已經在用的模式
/check verify在真實的應用程式裡證明改動有效，而且沒有破壞既有行為
/check review把程式碼交給另一個模型，抓作者自己漏掉的東西

這個順序藏著一個設計意圖：/architect 之所以要先讀現有實作，是因為在別人的系統裡，你任何一個決定都得先服從「它現在怎麼運作」。它同時扮演一個決策閘門，避免 agent 悄悄替別人決定這個系統該怎麼長。/develop 的「先讀再寫」則是同一件事往下一層：它不是先想一個漂亮的新寫法，而是先看看這個專案原本怎麼寫，然後照著做。

驗證之所以要用真實的 App，是因為「測試檔通過」跟「功能真的能用」是兩件事。/check verify 是去驅動真的跑起來的應用程式，證明每一個承諾的行為真的成立。/check review 再補上另一個角度：它刻意跑在跟寫程式的模型不同的模型上，理由很簡單——同一個模型審自己的作品，容易跟自己意見一致，找不出盲點。

這兩個 skill 的官方描述是這樣的：

| `architect` | Makes a real decision (a stack, a data model, a page design) and writes it as a spec. |
| `develop` | Builds a feature, user interface or backend, from its spec. |
| `check` | Confirms a change before merge, by running the real app and by a second review. |

你可能會覺得這些步驟在乾淨的專案上顯得又慢又重。但在舊碼庫裡，它們反而是讓 AI 真的能派上用場的原因。課程的講法是：這套紀律讓 agent 拿到的是邊界、證據與審查，而不是放任它在一個自己沒完全搞懂的系統裡自由行動。

整條線拉起來看：對既有碼庫的入口有變

把新專案和既有碼庫放在一起比，最明顯的差別是入口。新專案是「先決定、再建」，既有碼庫則是「先讀、再決定、再改」。課程的指南自己也把這個入口寫得很明白：

On an existing codebase, run `audit` first. It reads your real code and writes the context files, so every later skill understands your stack and conventions before it touches anything. Then `scope` enrolls what already exists and plans the new slice on top. From there the loop is the same.

所以整段可以這樣理解：/audit 先建出那張缺失的地圖；/architect、/develop、/check 接著在「先讀現況」的前提下推動改動。兩個工作——理解、安全地改——就是這樣被拆進 skill 裡的。

小結

在既有碼庫上，workflow 對上問題的方式只有兩步：先理解，再安全地改。理解靠 /audit 建出那張缺失的地圖，然後把地圖加上這次任務需要的一小塊交給 agent，而不是要它一次讀完整個 repo。安全地改則靠後續幾個 skill 各管一段：/architect 決策前先讀現況、/develop 先讀再寫並沿用既有模式、/check verify 在真實 App 內證明沒破壞行為、/check review 交給第二個模型複審。它的重點是把「猜」換成「讀」，把「自由發揮」換成「邊界、證據與審查」。

不過這套 workflow 有一條界線它自己跨不過去：它管的是「agent 怎麼工作」。至於哪些公司的資訊可以讓模型看見、什麼東西能離開組織，則是另一組設定與政策在管。下一節就要把這條界線畫清楚——因為在你把真實碼庫交出去之前，這是最後一個、也最不能被略過的決定。
