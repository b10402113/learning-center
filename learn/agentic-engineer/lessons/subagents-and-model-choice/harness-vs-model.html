挑模型：deep 決定、fast 執行

Step 3/4 · Subagents 與模型選擇

學習目標

用「harness 佔 80%、model 佔 20%」與 deep／fast 分層，替一個任務挑對模型與 reasoning effort。

前言：到底該用哪一顆模型？

這是大家第一個問、也最常問的問題：我該用哪一顆模型？很多人花大量力氣追最新、最大的那一顆，覺得換上它就等於升級。於是每個任務都掛著最貴的模型，帳單一路往上跑，產出卻不見得變好。

這一節要拆掉的，正是這個直覺。你會看到一個剛好相反的事實：模型其實只占產出品質的一小部分，真正決定成敗的，是它周圍那一整套東西。想通這一點，挑模型就從一道每個人都在煩惱的難題，變成一條簡單、而且不會過期的規則。

模型大概只占結果的兩成

最有用的說法是這樣：模型大概只占你產出品質的五分之一。另外五分之四，是它周圍的一切：你寫的 spec、你怎麼管理 context、承擔程序工作的 skill，以及「趁 session 還沒爛掉就重置它」的那份紀律。這一整包東西，叫做 harness（外圍框架），它才是決定你拿到的是生產級程式碼、還是一團很有自信的混亂的關鍵。

這句話直接翻轉了我們平常的直覺。一顆頂級模型，如果沒有 harness，照樣只是在 vibe coding；一顆普通的模型，放在好的 harness 裡，產出的東西扎實、可審查。因為真正在做關鍵思考的是 harness，模型只是照著它執行。所以模型比較像一個你可以轉動的旋鈕，而不是品質的引擎。引擎，是這門課教你圍繞它建起來的那一整套東西。

成本、速度、推理：這是一條光譜，不是排行榜

第二個常見誤解，是把模型想成一條「最差到最好」的排行榜。它們其實不是。每個供應商都沿著三個軸給你一個取捨：成本、速度、推理深度。你要做的，是依照當下任務真正需要什麼，在這條光譜上挑一個點。

一顆更便宜、更快、推理更輕的模型，並不是「比較差」的選擇。對很多工作來說，它才是對的選擇，因為那個任務根本不需要深度推理，它需要的只是一個又快又便宜的東西，照著你已經做好的計畫執行。每個任務都伸手拿最強的模型，就像為了掛一幅畫去租一台起重機：它當然做得到，但你為一個任務根本用不到的能力付了錢。

所以真正要練的不是「永遠用最強的模型」，而是「把模型配到任務上」。

選項比較：deciding 還是 executing

怎麼配？收斂成每個任務開始前都要問的一個問題：這件事是在做決定（deciding），還是在執行（executing）？

Deciding（決定）Executing（執行）
是什麼判斷所在的地方照著已經做好的計畫走
例子寫 spec、規劃模組邊界、debug 一個你還不懂的東西spec 寫完後把功能實作出來
選錯的代價一步走錯，整個建置都賠進去通常容易發現、也容易改
配哪一層deep tier（深度推理）fast tier（快速執行）

Deciding 是判斷所在的地方：寫 spec、規劃模組邊界、debug 一個你還不明白的問題。這裡一旦做錯，代價是整個建置，所以深度推理在這裡才划得來。這種工作送到你的 deep tier。

Executing 是照著一份已經做好的計畫走：spec 寫好之後把功能實作出來。決定都已經做完、也寫下來了，模型只是把它們執行出來。這是工作量的大宗，但不需要昂貴的模型。這種工作送到你的 fast tier。

一句話收斂：deciding 交給 deep tier，executing 交給 fast tier。

這個規則跟一套真正把決定前移的 workflow 搭配起來特別順。一旦 /scope 與 /architect 把該定的都定好，實作就真的只是執行，fast tier 完全夠用。你只在真的有決定要做的地方花昂貴的推理，其餘全都用便宜的執行。這不是妥協，是把工具配到任務上。

判別問句：三個問題，決定要送哪一層

拿到一個任務，依序問自己：

  • 這件事有沒有需要「發明」一個還沒決定的東西？ 有，就是 deciding，往 deep tier 送。
  • 決定已經寫下來了嗎？ 寫在 spec 或計畫裡了，就是 executing，fast tier 就夠。
  • 做錯的代價有多大？ 會賠掉整個建置的，多給一點推理；容易發現、容易改的，省下來。

Effort：同一套取捨，再往下一層

多數工具還讓你調整推理的 effort（投入程度），有時叫 thinking level 或 reasoning effort。它其實是同一種取捨的縮小版：effort 調高，模型想得更久、更用力，也比較慢、比較貴；調低，就是快又便宜。

用法跟挑模型一樣。把 effort 調高給那些「決定」的工作：架構、spec、一個難纏的 bug；調低給日常的執行。這個設定在每個工具裡名字都不同、也常改，所以不用去背層級，只要帶著這個習慣：判斷重要的地方多給一點，機械性的地方少給一點。

反例：規則什麼時候會翻轉

這條規則好用，但有幾種情況要想一下，免得套錯。

第一種，是「看起來像執行、其實是決定」的任務。如果一個實作任務裡藏著一個你還沒定案的設計選擇，那它其實還是 deciding，不該丟給 fast tier 硬幹。辨認的方法很簡單：這件事有沒有需要「發明」一個還沒決定的東西？有，就往 deep tier 送。

第二種，是硬體能力的下限。這套 workflow 實際測過，往下大約撐到 Sonnet 配高 effort、或 Opus 配中等 effort 就是底了。換句話說，deep tier 也不是非要最頂規的那顆，只要推理夠深就好；更強的配置當然也可以用。

還有一個更根本的提醒：因為模型只占兩成，所以「換一顆更貴的模型」永遠不會替你補上缺掉的 harness。如果你連 spec 都還沒寫、context 也沒管，換模型救不了你。這也是為什麼下一步該投資的地方是 harness，而不是型號表。

小結

模型大概只占你結果的兩成，另外八成是 harness：spec、context 管理、skill、session 衛生。成本、速度、推理深度是一條光譜，所以重點是「把模型配到任務」：deciding（spec、架構、難纏的 debug）交給 deep tier，executing（實作）交給 fast tier。effort 是同一套取捨再往下一層。這條規則在每個工具都成立，換的只是型號名稱。在這門課的 Claude 設定裡，就是 Opus 負責決定、Sonnet 負責執行。

動手前用這張檢查表過一次：

  • 這個任務是在決定還是在執行？先定性，再選層。
  • 決定有沒有寫下來？寫下來了才算執行。
  • deep tier 給 deciding，fast tier 給 executing，effort 跟著同一條線走。
  • 卡住時先回頭看 harness，不要先想換模型。
