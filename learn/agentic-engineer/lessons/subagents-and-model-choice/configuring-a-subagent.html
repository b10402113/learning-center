設定並使用一個 subagent

Step 2/4 · Subagents 與模型選擇

學習目標

這一節做完，你會得到一個放在 agents 資料夾裡、可重複使用的 subagent 設定檔，並且知道怎麼用自動與指名兩種方式真的把它派出去工作。

前言：想用，但檔案到底怎麼寫？

上一節講完了「什麼時候值得派一個 subagent」。這一節假設你已經決定要用，所以直接把原理放一邊，只回答一個很實際的問題：我到底要怎麼把它做出來，然後真的叫它去工作？

好消息是，一個 subagent 的定義檔非常小。小到你讀得完，也小到你可以放心動手改。做完之後，你就有一個跟著專案走、可以分享給整組人的小幫手。

先確認前置

動手之前，先確認兩件事：

  1. 你用的是支援 subagent 的工具，這裡以 Claude Code 示範。
  2. 你已經判斷過這個任務值得一個獨立的空間。如果只是讀一兩個檔就能答的小問題，那還不需要往下做。

方法一：用 /agents 引導建立

最快的方式，是在 session 裡直接跑 /agents。它會給你一個引導式的設定流程，你把想要的 subagent 描述清楚，它就會幫你把檔案寫好，結構也是對的。這是官方建議的預設做法，也是拿到一個正確 subagent 最省事的路徑。

你甚至可以請 Claude 幫你起草。例如對它說：

create a read-only code-review subagent that runs on a cheaper model

它就會把整份定義生出來，你只要做兩件事：檢查內容對不對、微調到合你的專案。

方法二：自己寫那個檔案

subagent 說穿了就是一個 markdown 檔，上面加一小段 YAML（就是開頭那塊夾在 --- 中間的欄位區）。就算你打算用 /agents，也值得知道它的長相，因為你之後會想讀懂它生出來的東西，並且動手改。

下面是一個完整的例子，一個只讀不寫的程式碼審查員：

---
name: code-reviewer
description: Reviews code for quality, security, and best practices. Use after writing or changing code, before a commit.
tools: Read, Grep, Glob
model: sonnet
---

You are a senior code reviewer. When invoked:
1. Look at what changed and focus only on the diff.
2. Flag security issues, missing error handling, and anything that breaks project conventions.
3. Report findings by severity. Do not fix anything yourself.

整份東西就這樣：四行 frontmatter，加一段系統提示。沒有別的隱藏結構。

每一個欄位在做什麼

這四行看起來不起眼，但每一行都是一個可以操作的旋鈕。

name 是你之後稱呼它的名字。

真正要用心寫的是 description，它是整個檔最重要的一行。理由是：這一行就是「觸發器」。Claude 會讀它來決定，什麼時候該自動把工作交給這個 subagent，就像門口的感應器讀到正確的關鍵字才會開門。description 寫得含糊，它就會在錯的時機跳出來，或者永遠不出現。所以要寫成「什麼時候該用它」，而不是只寫「它是什麼」。上面那行寫了 Use after writing or changing code, before a commit，就是在講時機。

tools 是選填的，而且是一個很實在的安全界線。不寫，這個 subagent 就繼承你所有的工具權限；一旦列出特定工具，它就只被限制在這些工具裡。上面那個審查員只給了 Read, Grep, Glob，意思是：不管它自己怎麼決定，它都沒辦法改動你的程式碼。這不是走形式，是你刻意設下的一道牆，等於只給它一張唯讀的門禁卡。

model 也是選填的。你可以把大量、便宜的工作（例如搜尋）路由到更快的模型，把貴的模型留給主線。這是 subagent 除了省 context 之外，另一個能省錢的地方。

最後，frontmatter 底下那段就是它的系統提示，寫清楚這個 subagent 是做什麼的、該怎麼工作。上面那段用三條指令把範圍限死：只看 diff、只報問題、不動手修。

檔案放在哪，為什麼有差

放置的位置跟 skills 的邏輯一樣，分成兩種：

位置路徑適合什麼
專案層級.claude/agents/（在 repo 裡）跟著程式碼走，整組人 clone 下來就拿到。適合共享、專案專屬的 subagent。
個人層級~/.claude/agents/你自己的，跨每個專案都能用。適合你自己的通用小幫手。

怎麼真的把它叫出來

這裡有一個很多人會卡住的點，先講清楚：/agents 只用來「管理」subagent（建立、編輯、刪除）。它不是執行 subagent 的方式。你要把它想成設定畫面：進去把它做出來，然後就離開。真正派它工作的方式有兩種，而且都不是那個指令。

  1. 自動。你給 Claude 一個普通的任務，如果它符合某個 subagent 的 description，Claude 就自己把工作交過去，不需要你下任何指令。這也是為什麼 description 就是觸發器。寫對了，你常常根本不用手動叫它，它該出現時就出現了。
  2. 指名。你在一般訊息裡直接點名它，例如：「Use the code-reviewer agent on these changes.」這依然不是斜線指令，只是在你的請求裡提到這個 agent，Claude 就會把工作路由過去。當你需要它、但它沒有自動接手時很有用。

所以心智模型只有一句：/agents 是「做」subagent 的地方，一般訊息是「用」subagent 的地方。

不用自己寫的那些內建 subagent

你也不是只能自己寫。Claude Code 本身內建了幾個會自動被叫用的 subagent：Explore（快、唯讀、跑在 Haiku 上，用來搜尋 codebase 而不動它）、Plan（唯讀，在規劃階段收集 context），以及 general-purpose（通用的那一個）。很多時候你享受到的好處，其實就是這些內建的在自動接手，完全不需要你設定。

小結：做完長什麼樣

做完之後，你手上應該有兩樣東西可以驗證：

  1. agents 資料夾裡有一個 markdown 檔，開頭是四行 frontmatter（name、description、可選的 tools 與 model），底下是一段系統提示。
  2. 你丟一個符合 description 的任務出去，它會自動接手；或者你點名它，工作會路由過去。兩種都跑得通，才算真的設定好。
一個 subagent 就是一個小設定檔：name、當觸發器用的 description、可選的 tools 與 model 限制，加上一段系統提示，放進 agents 資料夾（專案共享或個人）。建立有兩條路：跑 /agents 引導，或親手寫 markdown + YAML。description 就是觸發器，tools 是一道真實的安全界線。/agents 只負責建，真正派它工作靠一般訊息：符合 description 就自動接手，或你直接指名。

設定講完了，subagent 這半邊也告一段落。接下來把視角拉遠，換談藏在所有原語底下的那顆旋鈕：模型。它到底影響多少結果？該怎麼挑？下一節會給你一個反直覺、但很好用的答案。
