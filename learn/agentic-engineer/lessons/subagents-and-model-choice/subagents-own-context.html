Subagent：把重讀取隔離到自己的 context

Step 1/4 · Subagents 與模型選擇

學習目標

說出 subagent 為什麼要用自己的 context、它替你省下什麼，以及哪一種任務才值得派一個出去。

前言：查到一半，它怎麼就變笨了？

你可能遇過這種情況。你請 agent 做一件需要翻很多檔案的事，例如「把整個 API 層的錯誤處理方式整理給我」。它一開始很順，grep 一次、開一個檔、再開一個檔，回覆也還算準。

可是愈到後面，它的回答開始飄：忘記前面讀過什麼、把兩個函式的行為混在一起，甚至回頭做出你早就講過不要的選擇。

你沒換模型，prompt 也沒改，為什麼品質會下滑？因為那些它讀過的檔案、跑過的搜尋，全部堆進了同一個 context window，把桌子塞滿了。而桌子一滿，它的表現就會開始掉。

這一節要介紹的 subagent，就是為了處理這件事而存在的四大原語之一。它的做法很簡單：把大量閱讀與搜尋搬到另一個地方去做，只把結論帶回來。搞懂它，你就能讓主線的 context 一直保持清爽，也才判斷得出什麼時候該派它、什麼時候派了反而多餘。

問題：所有讀取都堆在同一張桌子上

先回到上一課的結論：agent 只知道 context window 裡的東西。它讀的每一個檔案、跑的每一次搜尋，都會留在那個視窗裡。即使那份檔案已經用不上了，也不會自動消失。任務做完之前，它們全都佔著位子。

這件事在「重讀取」的任務上特別致命。假設你只想要一個簡短的答案，但為了拿到它，agent 得先讀二十個檔案。等它終於拼出答案，那二十個檔案也已經全部躺在它的 window 裡了，接下來的每一輪對話都得背著它們。

你要的只是最後那幾句結論，卻付了整條探索路徑的成本。而且視窗愈滿，它就愈容易做出糊塗的判斷——前面那個「愈查愈笨」的現象，就是從這裡來的。

換句話說，你真正需要的是「結果」，卻被迫連「過程」一起吞下去。

解法：讓它在自己的地盤做完重活

subagent（子代理）是一個有自己獨立 context 的工人。你派它去做那些需要大量閱讀與搜尋的粗活，它在自己的空間裡把過程全部做完，最後只把你要的結果交回主線。

所有中間讀過的檔案、跑過的搜尋，都留在它那邊，不會進到你眼前的 window。就像你把一份資料整理工作外包出去，對方在自己的辦公室翻完整箱文件，寄回來的只有那一頁摘要。

課程裡有一個現場示範，把這件事講得非常清楚。先在終端機的 Claude session 裡跑 /context，會看到當下的分解：系統提示約占 1%、系統工具約占 2%，剩下 93% 是可用空間，也就是只花了 4%。記住這個「4% 已用」。

接著故意丟一個範圍很大的問題：「look through this project and summarize how error handling is done across the API routes.」這種問題正是那種需要到處翻找的類型。

一送出去，主 agent 並沒有自己開始一個檔一個檔地開。它派了一個 subagent 出去，畫面上會出現一列寫著 Explore 的項目，那就是在獨立 context 裡工作的子代理，跟我們正在看的主線完全分開。它在那邊讀了多少檔、搜了多少次，都不會落到主線的 window。

結果回來時，只有幾句話——它找到的錯誤處理模式摘要，而不是它為了得到這個結論所讀的那二十個檔案。你再跑一次 /context，會發現「已用」幾乎沒動。

所有重活都發生在別的地方，而且就留在那裡。這就是 subagent 的第一個價值：重活在它的空間裡做完，主線只收結果，保持乾淨。

第二個好處：可以同時派好幾個

subagent 帶來的不只是乾淨，還有速度。因為每個 agent 都在自己的空間裡跑，主 agent 可以同時把好幾個 subagent 派出去，各做一件互相獨立的事。原本要一步一步排隊做完的大任務，現在可以平行進行。

你可以把它想成「平行的程式執行」：不是把每件事接在同一條線上跑，而是拆開來同時跑，整體自然更快完成。

這也預告了後面 workflow 為什麼能維持速度——很多時候是把互不依賴的探索同時丟出去，各自在各自的桌子上忙。

但它不是免費的，也不是萬用解答

講到這裡很容易變成「什麼都派 subagent」。這正是要小心的地方：開一個 subagent 是有額外成本的。多一層派發、多一次來回，任務小的時候，這個成本划不來。

所以判斷的標準是兩個問題：

  1. 這件工作重不重？也就是有大量的閱讀或搜尋，而你只在乎最後的結果，不在乎中間那條路。
  2. 這件工作能不能拆成互不依賴的幾塊？彼此之間不需要等對方，就能各自進行。

只要有任何一個答案是「是」，subagent 就是很適合的選擇。兩種情況對照起來大概是這樣：

情況該不該派 subagent
要讀很多檔、搜很多次，但你只要結論該派，重活留在它那邊
能拆成幾塊互不依賴的工作該派，可以同時派好幾個
主 agent 讀一兩個檔就能回答的小問題別派，多繞一步沒有幫助

反過來說，如果任務又小又精確，那派一個 subagent 出去只是多繞一步，對結果沒有任何幫助。

有趣的是，這跟上一課判斷 MCP 用的是同一句話。你問的不該是「我這裡能不能用一個 subagent」，而是「這個任務是不是真的需要一個屬於它自己的空間」。問對了問題，才不會養了一個你根本不需要的幫手。

順帶提一件事，先放在心裡就好：課程後面的 agentic engineering workflow，正是靠這個觀念保持快速與乾淨的——重活都發生在主線旁邊。等你走到那裡，會一眼認出來。

小結

subagent 是一個有自己獨立 context 的工人：它把大量閱讀與搜尋在自己的空間裡做完，只把結果交回主線，所以主線的 window 不會被重讀取塞滿。因為每個 agent 各有空間，還能同時派好幾個，平行加速。但它不是免費的，也不總是答案——當工作夠重、而你只要結果，或工作能拆成互不依賴的幾塊時，才值得派它出去。判斷的方式跟 MCP 一樣：問「這個任務需不需要自己的空間」，而不是「我能不能用」。

知道了「什麼時候該用」，下一個問題自然是「怎麼把它做出來」。下一節會帶你在 Claude Code 裡實際建立一個 subagent：用 /agents 引導，或親手寫一個小小的 markdown 檔。
