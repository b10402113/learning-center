還原意圖：從 spec、周邊程式與執行行為找線索

Step 2/6 · 除錯 AI 寫的碼與救回卡住的 Session

學習目標

從 spec 的驗收條件、周邊程式與執行行為三個地方還原 AI 碼的意圖，並在沒有 spec 時判斷這是「沒做過的決定」而非 bug。

前言：少了記憶，線索要從別的地方來

上一節我們確認了：面對 AI 寫的碼，你沒有作者記憶，而且「看著它生成」補不上這個缺口。既然當初的意圖不在你腦子裡，那它還能從哪裡來？

答案是有三個地方。它們都不是「問 agent 它當初在想什麼」——那只是又一次叫它生成說法，你無從驗證真假。三個來源都寫在你身邊的檔案與系統裡，可以查、可以比對，也正因為如此，它們可以被驗證。這一節就是帶著你依序走過這三個來源；如果三個都沒有，你會在最後撿到一個比 bug 更重要的東西。

動手前：先確認你查的是哪一種壞

這一步有前置條件。你面對的必須是第二種壞——agent 寫的程式碼本身出錯——而不是第三種壞——agent 自己卡住了、在那裡打轉。如果症狀是「同一個函式被重複改、越改越亂」，那你要的是後面兩節的內容，不是這一節的還原流程。

另外，能跑起來的環境是必要的。這一節的第三個來源要你實際觀察程式的行為，光讀程式碼看不出來。如果你手上有一份規格或驗收條件，也先把它找出來，它是最重要的那一個。

意圖來源一：讀 spec 的驗收條件

先看 spec。這裡看的不是「它實際上做了什麼」，而是「它當初承諾要做什麼」。原文的措辭很關鍵：驗收條件告訴你的，是這段程式碼當初被要求做到的事，是它的承諾，而不是它現在的表現。

這個轉換會把你原本模糊的調查，變成一場具體的比較。你不再需要漫無目的地猜哪裡有問題，而是把兩份東西並排：一邊是當初承諾的行為，一邊是實際發生的行為，然後找出中間的落差。落差在哪裡，bug 就在哪裡。

這也是前面那一大段「把東西寫下來」的功夫，報酬最低調的一次兌現。平常你會覺得寫下驗收條件很囉唆，但在這裡，它直接把一個沒有方向感的調查，變成一個有明確答案的比對工作。

意圖來源二：讀周邊程式

第二個來源是這段程式碼四周的東西。原文的說法是：周邊程式給你的是「這個檔案当初應該遵循的慣例」。

用白話說，就是先看同一份檔案、同一個資料夾裡的其他函式怎麼寫。如果整份檔案都習慣把錯誤往上丟、都用同一個命名風格、都走同一種資料格式，只有你正在看的那一行偏偏不一樣，那個「不一樣」就是一條線索。它不一定就是 bug，但它是一個值得優先檢查的偏離點。

要注意的是，周邊程式只告訴你「這裡通常怎麼做」，它不會告訴你「你眼前這一行為什麼這樣做」。所以它適合拿來縮小範圍，不適合拿來當成最終答案。

意圖來源三：觀察執行行為

第三個來源是實際跑起來的行為。原文的說法是：它給你的，是「實際發生了什麼，而不是程式碼看起來說了什麼」。

這一點很值得停下來想。程式碼「看起來的樣子」和它「實際運作的樣子」經常是兩件事。一段讀起來很合理的判斷，可能因為單位、順序或某個隱藏的轉換而做出完全不同的結果。你讀的是意圖的草稿，執行的才是事實，而比對這兩者，正是找到落差的方法。所以不要只讀，要真的把程式跑起來，看你觀察到什麼。

三個來源的總表

來源它給你什麼
spec 的驗收條件這段程式碼當初被要求做什麼。它與現實之間的落差，就是 bug 所在
周邊程式這個檔案原本應該遵循的慣例。偏離慣例的那一行值得先看
執行行為實際發生了什麼，而不是程式碼看起來說了什麼

當三個來源都沒有：你找到的是決定，不是 bug

現在講那個分岔。很多 AI 寫的碼，根本沒有 spec，這是很誠實、也很常見的答案。這時候如果你在三個來源裡都找不到意圖，你找到的東西比一個 bug 更重要。

原文的邏輯是：一段行為，如果背後沒有一個被記錄下來的決定，那它就不是一個「你可以修好的 bug」。它是一個從來沒被做過的決定。在有人先決定「正確應該長什麼樣」之前，你根本無從判斷這段程式碼是對還是錯——因為「對」的標準還沒被定義出來。

這種情況不屬於除錯。除錯的前提是有個已知的正確行為可以對照；這裡缺的正是那個正確行為。所以它屬於設計決策的範疇。原文用兩個工具名稱把這個分界講得很清楚：

/debug
/architect

當你發現「這段行為沒有意圖可還原」，別急著把它硬塞進除錯流程裡改。先退一步，把「正確應該是什麼」這件事決定下來——那才是此刻真正該做的工作。

小結

意圖有三個可查的來源：spec 的驗收條件（它承諾了什麼）、周邊程式（它應該遵循什麼慣例）、以及執行行為（它實際做了什麼）。把承諾與實際並排，調查就變成一場找落差的比較。若三個來源都沒有，你找到的不是 bug，而是一個從沒被做過的決定，那不是 /debug 而是 /architect。

現在你有了還原意圖的流程。但要在現場快速認出「這裡不對勁」，你還需要一份辨認清單。下一節會把反覆出現的四種 AI 失敗模式列出來，讓你一眼就能叫出它們的名字。
