四種 AI 失敗模式與它們的破綻

Step 3/6 · 除錯 AI 寫的碼與救回卡住的 Session

學習目標

認出 Invented function、Plausible but wrong logic、A decision made mid-file、The unconsidered edge case 四種失敗模式，並記住 bug 幾乎不在出錯的那一行。

前言：一份可以叫得出名字的清單

上一節你學了怎麼把意圖還原出來。但要在現場快速行動，你還缺一份辨認清單：當你盯著一段 AI 寫的碼，能不能一眼看出它「是怎麼壞的」？

值得把這四種模式背下名字，因為看過一次之後，你認出它們的速度會快很多。這一份是查閱用的清單——四個條目、它們各自的破綻，以及一條貫穿全部的通則。它是後面所有除錯判斷的參照點。

四種模式

模式它怎麼壞多難抓
Invented function（發明函式）呼叫一個不存在的東西，或是兩版之前才存在的東西容易。失敗得很吵
Plausible but wrong logic（貌似合理的錯誤邏輯）讀起來正確、能過審查，遇到真實資料才出錯最難。形狀是對的，推理不是
A decision made mid-file（檔案中途做出的決定）嚴格說不算 bug。某個東西被選定了，選它的是生成器，沒人審過在它和別的東西衝突之前都看不見
The unconsidered edge case（沒被考慮到的邊界情況）happy path 全部完成，第一個不尋常的輸入就穿過破洞餵真實資料進去就容易抓到

逐項描述

Invented function

程式碼呼叫了一個函式，而那個函式在專案裡與套件裡都不存在；或者它曾經存在，但在兩個版本之前就被移除了。這一類的錯誤會直接拋出，錯誤訊息明白指出找不到那個名字，所以它失敗得很吵，抓到不難。

// 專案與相依套件裡都找不到這個函式
const user = await getUserBySessionId(sessionId);

Plausible but wrong logic

程式碼讀起來正確，也能通過審查，因為它的形狀是對的——該有的判斷、該有的迴圈、該有的回傳值都在。問題出在形狀內部的推理。它往往要等到真實資料進來才會出錯，所以是最難抓的一種。原文特別點名它是危險的那一個。

A decision made mid-file

這一項嚴格說起來不算 bug。某個東西在過程中被選定了，做選擇的是生成器，而且沒有人審過。它一直隱形，直到和專案裡的其他東西產生衝突。它屬於前一節講的那個分岔：一個沒有人記錄下來的決定。

The unconsidered edge case

happy path（一般正常輸入會走的路徑）全部完成，看起來功能齊全。但第一個不尋常的輸入進來，就從某個沒被想到的縫隙穿了過去。這一種只要餵真實資料進去，就相對容易抓到。

共同的破綻

Bug 幾乎從來不在出錯的那一行。它在更早、某個沒有人寫下來的決定裡。

所以你的調查要比查自己的碼時多帶一個問題：這件事，當初到底有沒有被決定過？

這一句就是整份清單的通則。出錯的那一行只是症狀露出來的地方；真正的原因通常埋在上游某個沒被記錄的選擇裡。這也是為什麼前面要不厭其煩地回頭還原意圖，而不是盯著錯誤訊息那一行猛看。

小結

四種模式是：發明函式（吵，好抓）、貌似合理的錯誤邏輯（形狀對、推理錯，最難）、檔案中途做出的決定（不算 bug，衝突前隱形）、沒被考慮到的邊界情況（用真實資料就抓得到）。四者共用同一條破綻：出錯的那一行幾乎從來不是原因，真正的原因在更早、某個沒被寫下來的決定。

到這裡，第二種壞——AI 寫的碼出錯——就講完了。接下來要換一條線：當壞掉的不是程式碼，而是 agent 本身。它會用一種很不一樣的方式失控，下一節先教你怎麼認出它。
