認出 agent 在打轉：迴圈與幻覺的差別

Step 4/6 · 除錯 AI 寫的碼與救回卡住的 Session

學習目標

用「重複但沒有進展」認出 agent 卡住的 session，並說明為什麼在這個時候加指示，只會讓迴圈更糟。

前言：壞掉的不是程式，是流程

前面三節講的都是第二種壞——agent 寫出來的程式碼本身有問題。但還有第三種壞，它更難處理，因為壞掉的根本不是你的程式碼，而是 agent 這個過程本身。

你想像一下這個畫面：你請 agent 修一個登入的 bug，它改了同一個函式五次，每一次只差一點點；它一再打開同樣幾個檔案；diff 越滾越大、越改越亂；更奇怪的是，它有時候還會推翻自己前面才做過的決定。你看不出哪裡「錯了」，因為它給你的每一句說明聽起來都很有自信。但整個 session 就是沒有往前推進。

這一節要教你認出這個狀態。認出來之後，你才有辦法做後面兩節的事——判斷該留還是該丟，然後照順序把它救回來。

徵兆：重複，但沒有進展

原文給的判準只有一句話：重複，卻沒有進展。這句話之所以好用，是因為它同時抓到了兩個必要條件——只重複，不算迴圈（也可能只是任務本來就需要反覆迭代）；只沒進展，也不算迴圈（也可能只是還沒輪到它）。要「又重複、又沒進展」，才是那個卡住的訊號。

它在現場長這樣：

  • 同一個函式被重寫了五次，每次只差一點點。
  • 同樣幾個檔案被反覆打開。
  • diff 越變越亂。
  • 開始和它自己先前的決定互相矛盾。

其中最後一項最值得注意。當一個 agent 開始推翻自己前面才做出的決定，代表它已經沒有一個穩定一致的內在狀態，只是在你眼前不斷重新開機。

迴圈和幻覺，是兩件不同的事

這裡要分清楚一個很容易混在一起的差別。原文的說法是：幻覺給你的是錯誤的內容，迴圈給你的是壞掉的流程。

幻覺壞在產出。它可能把一個不存在的函式說得煞有介事，或把一段錯誤的邏輯寫得頭頭是道——但那個錯誤是「內容層面」的，只要你能辨認出內容錯了，就能處理。迴圈壞的是過程：它可能每一句內容都不算太離譜，可是它整體在打轉，沒有累積任何進展。

面向幻覺迴圈
壞在哪裡產出的內容是錯的整個過程停滯不前
你看到什麼一段說得很有自信的錯誤內容一再重複、每一次都更亂
怎麼處理指出內容的錯，修正它修法不在內容，要處理流程本身

為什麼要分得這麼細？因為如果你把迴圈誤認成幻覺，你就會用對付幻覺的方式去處理它——也就是繼續加指示、繼續下更清楚的 prompt。而那正是下一段要說的地雷。

為什麼加指示只會更糟

面對錯誤的內容，最直覺的動作就是糾正它：「你這裡錯了，應該要這樣做。」這個動作對幻覺有效。但對迴圈，原文的說法是：加指示會讓它更糟。

原因在於，你正在指揮的那個東西，本身就是故障的一部分。這是一個很違反直覺的處境——你以為你在修一個壞掉的產出，實際上你是在對一個已經失去方向、卻又充滿自信的過程下指令。它會把你新給的指示也吸收進那個失序的狀態裡，然後繼續打轉，甚至轉得更亂。你把更多燃料倒進一具已經失控的引擎，不會讓它變好。

換個比喻：一個人在森林裡迷了路，一直繞著同一棵樹打轉。你這時候給他一張更詳細的地圖，並不會幫上忙——因為他真正的問題不是資訊不足，而是他判斷方向的那個機制已經壞了。你愈是疊加指示，他只是拿著更多資訊繼續繞同一圈。

把它掛回「三種壞」

現在你可以把這一節接到前面那個大分類上：這就是第三種壞——agent 自己丟失了路徑。它和第一種（普通 code bug）、第二種（AI 寫的碼出錯）的關鍵差異在於，前兩種的故障都在程式碼這一側，你有可以拿去比對、重現、修正的實體；第三種的故障在流程那一側，程式碼可能根本沒有錯，錯的是「產生程式碼的這個過程」。

正因為故障不在程式碼上，第三種壞的第一步永遠不是「再去改一行程式」，而是先認出它、然後決定怎麼處理這個已經壞掉的過程。這也是接下來兩節要做的事。

小結

認出 agent 卡住的唯一訊號是「重複，但沒有進展」——同一個函式反覆重寫、同樣的檔案反覆打開、diff 越滾越亂，甚至開始推翻自己先前的決定。它和幻覺不同：幻覺給你錯誤的內容，迴圈給你壞掉的流程。所以面對迴圈，加指示只會更糟，因為你正在指揮的那個東西，本身就是故障的一部分。這是三種壞裡的第三種：壞掉的不是程式碼，是過程。

認出迴圈之後，你不能立刻動手修——還有一個更根本的判斷要先做：這個 session 累積下來的 context，到底該留，還是該丟？這個判斷錯了，代價很高，下一節專門講它。
