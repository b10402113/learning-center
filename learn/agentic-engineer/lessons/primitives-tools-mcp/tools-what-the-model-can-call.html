Tools：模型能真正呼叫的動作

Step 2/4 · 四大原語：Tools 與 MCP

學習目標

定義 tool 是什麼，說出每個 coding agent 都有的五個核心工具，並講清楚「模型決定」與「工具執行」是分開的兩件事，以及每一次 tool call 都有真實成本。

前言：它說「我讀一下這個檔案」，然後呢？

上一節把四大原語攤開，其中最快被你看到的是 tools。你幾乎每一個 session 都在看它發生：agent 說一句「我先看一下 auth 相關的檔案」，畫面上一行字閃過去，然後它就開始針對內容回答你。

但那一行字底下到底發生了什麼？多數人對這件事的想像是錯的。很容易以為「模型自己去讀了檔案」，好像模型有一雙眼睛，能伸手翻開你硬碟裡的檔案。實情不是這樣，而這個誤會的代價不小——它會讓你搞錯「問題出在哪」。這一節就把一個 tool 到底是什麼、以及誰在做什麼，講清楚。

Tool 是什麼：一個被允許執行的具體動作

先把定義放上來：一個 tool，是 agent 被允許執行的一個具體、定義明確的動作。它不是一個建議，也不是一句「它也許可以做什麼」的描述，而是一個它真的能觸發、並且拿回真實結果的操作。

如果這個說法有點抽象，用你已經熟的東西比喻就好：把 tool 想成一個函式或一次 API 呼叫。它是一個定義好的東西，只做一件事，需要時被呼叫，然後回傳一個結果。agent 呼叫 read("auth.ts")，拿回檔案的內容——就像任何一個函式回傳一個值一樣。工具就是它的「手」，是它從嘴巴跨到動作的那一步。

一個 chatbot 只會說話。一個 agent 能做事，因為它有被允許伸手去拿的工具。這條線，就是「聊天」和「coding agent」真正的分界。

有些工具是內建的，例如讀一個檔案、搜尋網頁；有些則可以之後再加。但不論哪一種，它們都共用同一個性質：是被定義好的動作，不是隨口的描述。這也是為什麼回頭看第二個模組裡那個登入 bug，你會發現當時那一句 grep、那一次開檔，其實全都是 tool call——都是 agent 在做，不是在講。

每個 coding agent 都有的五個核心工具

不管你用的是哪一款產品，一個 coding agent 幾乎都會給模型這五個工具。它們覆蓋了你在這門課裡會看到、絕大多數 agent 的動作：

工具做什麼
Read打開一個檔案，看裡面有什麼
Write建立新檔案，或整份取代一個檔案
Edit修改現有檔案裡的某一個特定部分
Search（grep／glob）找出符合某個樣式的文字或檔案路徑
Run a command在終端機執行某個東西，例如測試套件或建置

注意這五個的分工其實很整齊：Read 和 Search 負責「看」，Write 和 Edit 負責「改」，Run a command 負責「跑」。從第二個模組的登入 bug，到之後你自己要做的每一個功能，拆到最底層，都是這幾個操作的某種排列組合。你看到 agent 在做一件複雜的事，其實只是它把這五個動作排了一串。

真正重要的那條線：模型決定，別的東西執行

這是這一節最容易被誤會、也最值得記住的一件事：模型本身不會去讀檔案，也不會去跑指令。它做的是「決定下一步該讀一個檔案」，然後發出一個 tool call——一個結構化的請求，裡面寫清楚它想要什麼。真正去執行這個請求、把結果拿回來的，是模型以外的另一個東西。

把這件事拆成兩個步驟看，你會發現「推理」和「執行」是分開的，而問題可能出在其中任何一邊。模型可能完全正確地判斷「這裡該讀檔」，卻還是拿到一個爛結果，因為它發出的 tool call 本身寫壞了、因為它要讀的檔案根本不存在、或者因為它想跑的指令在你的環境裡沒有。它想對了，不代表它做對了。

理解這條線，你在看 session 時的解讀會完全不同。當你看到一次 tool call 發生，那不是 agent 在自言自語、也不是它「想」了什麼，而是一個真實的操作正在被執行——帶著一個真實的結果，而這個結果會幫助或拖累後面發生的每一件事。

Tool call 不是免費的背景動作

最後要把這件事接回上一節的帳。Tool call 不是「背景免費的小事」。因為每一次呼叫都會產生內容——讀進來的檔案、搜尋的結果、指令的輸出——而這些內容全都會落進 context window，佔掉額度，並且一直留在那裡等著影響後面的每一輪。

所以在這門課裡，當你看到 agent 讀一個檔案，請記得那不是在背景安靜地發生，而是在呼叫一個工具：每一次呼叫都有重量。這個重量，就是你之後在 workflow 裡要管理、要省的那筆帳。

小結

一個 tool 是 agent 被允許執行的一個具體、定義明確的動作——不是描述，而是真的能被觸發、拿回結果的操作，像一個函式或一次 API 呼叫。每個 coding agent 都給模型五個核心工具：Read、Write、Edit、Search（grep／glob）與 Run a command，它們負責看、改、跑，覆蓋了絕大多數動作。但模型本身不執行，它只發出結構化的 tool call，執行是另一件事，問題可能在推理端也可能在執行端。而每一次 tool call 都會產生內容、落進 context，所以它不是免費的背景動作。

知道了工具是「專案內」的手，下一個問題就自然浮現：那專案外面的東西呢？你的資料庫、你的日曆、某個第三方 API，都不在你的 repo 裡，工具碰不到。下一節要講的 MCP，就是那個把外部服務接成可呼叫工具的標準辦法——以及什麼時候你根本不該接它。
