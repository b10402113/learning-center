什麼才配放進 Always-on？一個判準與九份文件的教訓

Step 4/5 · Context Engineering

學習目標

用「我在大多數任務上都會需要它嗎？」這個判準，決定一條規則該進 always-on、on-demand 還是 reference，並認出把九份文件塞進 always-on 這種肥檔造成的稅。

前言：兩股力量在拉扯

現在你面前有一個很具體的決定：手上這條規則，到底該放進哪一種 context？

這個決定之所以難，是因為有兩股力量朝著相反方向拉你。

一股是安全感。當你學到「agent 只知道自己被載入了什麼」，心裡很自然會想：那我什麼都塞進去，讓它永遠不缺 context，不是最保險嗎？

另一股是成本。上一節你已經看到，always-on 檔案裡的每一行，都會在每個 session 開頭被載入、被讀進來，而你每次都要為它付費。

這一節要幫你判斷的就是：哪些東西值得付這筆「每次都付」的錢，哪些不值得。

三個可能的去向，先擺在一起看

任何一條規則，其實只有三個去處。把它們並排，你就知道自己在選什麼。

去向什麼時候放這裡成本
Always-on每個任務都成立、agent 絕不能錯的常備事實每個 session 都付
On-demand某類工作會用到，讓 agent 在需要時自己去拿用到才付
Reference存在於專案、由你或某個檔明確指到才載入用到才付

看出來了嗎？只有第一格是「每次都付」。所以你真正在下的決定，不是「這條規則重不重要」，而是「這條規則是不是每個任務都需要」。

判別問句：一句話就夠

你不需要什麼公式。在一行文字「賺到它的位置」之前，對它問一句就好：

我在大多數任務上都會需要它嗎？

把這個問句套到幾個具體的東西上，答案就會自己浮出來。

  • 技術棧是什麼（例如 Next.js + TypeScript）：幾乎每個任務都會碰到，答案是「會」。→ always-on。
  • 金額用整數的「分」來存、絕不用浮點數的「元」：任何碰到錢的任務都不能錯，而且這種錯會安靜地發生，等到對帳才爆開。答案是「會」。→ always-on。
  • 某個功能專屬的 spec：只有做那個功能時才相關，答案是「不會」。→ 放 reference，等那個工作出現時再指給它。
  • 資料夾結構說明文件：某些探索類任務有用，但不是每個任務都要背。→ 大概率是 on-demand 或 reference。

整理成一句可以照著做的規則：只要是「大多數任務都需要」的，進 always-on；只在「某些任務」相關的，就放 on-demand 或 reference，等那個工作真的出現再載入。

反例：九份文件的錯誤

現在來看最常見的坑。它剛好跟直覺相反。

有個人為了周延，把九份文件全接進了 always-on：風格指南、API 慣例、資料夾結構說明、測試哲學，全部接進去。這看起來很負責任：「確保 agent 什麼都知道」。

但他真正做出來的，是九份檔案的租金。這九份文件裡，大部分對任何一個特定任務都無關，可是它們從第一則訊息開始就卡在視窗裡，在每個任務上都存在，擠滿了空間，還稀釋了 agent 的注意力。

結果是：那「一兩條真正重要的事實」，反而被埋在一堆噪音裡。他沒有給 agent 更多 context，他給的是更多噪音，而且讓 agent 每次都替這些噪音付錢。

另一個容易看錯的地方

還有一種反例更細微：一條規則「很有用」，不代表它就該進 always-on。

假設你有一份寫得很好的 API 慣例文件，你覺得它太有價值了，想讓 agent 每次都想著它。但如果你的專案有一半的任務根本不碰 API，這份文件對那另一半任務就是純粹的噪音。

它很優秀，但「優秀」不是判準，「大多數任務都需要」才是。所以這個判準會翻轉你的直覺：不是「越重要越該進」，而是「越普遍才越該進」。重要但只跟部分任務相關的規則，就該待在那個部分旁邊。

一個當場能用的檢查表

下次你準備往 AGENTS.md 裡加一條規則之前，快速跑過這幾問：

  1. 它對「大多數任務」都成立嗎？不是的話，就別放進來，把它指到該去的地方。
  2. 它是 agent 絕不能搞錯的事實嗎？會安靜出錯的（例如錢的單位）特別該進來。
  3. 它只跟專案的某個部分相關嗎？如果是，讓它靠近那個部分，或放在只在相關時才載入的檔案。
  4. 它有沒有可能被之後的 /audit 之類的 skill 修剪掉？如果有，那可能代表它本來就不該一直待在那裡。

還有一個好消息：你之後不用永遠靠手工維護這份檔案。這個 workflow 自己的 skill 會自動從專案實況建立、修剪 AGENTS.md。你現在把這套紀律練熟，是為了當那一天到來，你能判斷它做對了沒有。

小結

一條規則只有三個去向：always-on（每個 session 都付）、on-demand、reference（用到才付）。唯一的判準是那一句「我在大多數任務上都會需要它嗎？」會，就進 always-on；只在某些任務相關，就放 on-demand 或 reference。把九份文件全塞進 always-on，換來的不是更多 context，而是九份租金加一堆噪音。它會擠滿視窗、稀釋注意力，讓真正重要的那一兩條被埋掉。

判準有了，機制你也懂了，那就該動手了。下一節我們會真的開一個新專案，寫出一份夠小的 AGENTS.md，並用 import 讓它保證載入、用指令驗證它真的進來了。
