三種 Context：Always-on、On-demand、Reference

Step 2/5 · Context Engineering

學習目標

分辨 always-on、on-demand、reference 三種 context，並用「成本節奏」（每次都付 vs 用到才付）說出它們的差別。

前言：context 不是一種東西

上一節我們把界線畫出來了：context 就是你按下 enter 那一刻，agent 已經知道的一切，而設計它才是真正的槓桿。

但「context」這個詞聽起來像一整塊東西，好像它等於「agent 知道的所有事」。其實不是。它比較像一個工具箱，裡面混了幾種行為完全不同的材料。你要動手設計，就得先知道自己在動的是哪一塊。

而它們之間最重要的差別，說出來你可能會有點意外：不是「重要程度」，而是什麼時候要付錢。

這一節把 context 拆成三種。這三種弄清楚了，這個模組剩下的部分，基本上都只是在應用它們。

Type 1：Always-on context（永遠在場）

第一種，是 agent 在每個 session 都自動擁有的 context，而且是在你打任何字之前就已經載好。你不需要開口要它，它就是在那裡，每段對話開始時就被載入。

在多數工具裡，這件事住在一個檔案裡。以我們要建立的 workflow 來說，那個檔案是 AGENTS.md，也就是專案的「常備簡報」：技術棧、核心慣例，還有那些不管你當天在做什麼都成立的規則。

課程裡舉的例子很具體。如果你的專案把金額存成整數的「分」（integer cents），而絕對不用浮點數的「元」（floating-point dollars），那這條就是一條 always-on 的事實。因為 agent 在每個任務上都需要知道它，否則它會在你沒發現的情況下把錢算錯。

它的定義特徵是：不管跟你當下在做的事有沒有關係，always-on context 都會被載入。這是它的存在意義，但同時（我們馬上會看到）也是它的陷阱。

Type 2：On-demand context（需要時才拉）

第二種，是 agent 自己在任務進行中拉進來的 context，因為當下的工作需要用。它可能是一個搜尋之後才打開的檔案、一個 skill 在觸發條件對上之後才載入的內容、或它讀過的一堆 grep 結果。

你在前面「agent 怎麼讀程式庫」那一課已經看過這一整套：它靠搜尋、開檔、讀檔，一步一步爬向答案。那些每一次的讀取，都是 on-demand context，在需要的那一刻才載入，而不是事先。

它的定義特徵是：用到才付錢。agent 伸手去拿、拿來用，用過之後它就在這個 session 裡待著；但那些不需要它的任務，從來就不必把它載進來。

Type 3：Reference context（被指到才進來）

第三種，是你專案裡存在、但不會進入 context 的東西，直到有東西明確指到它為止。你的 spec、一份設計文件、還有就躺在磁碟上的那一大片程式庫。

它是「可取得」的，但沒有被載入；而且這也不是 agent 自己亂逛撞到的，它是你、或某個檔案，刻意把 agent 指向它，它才進來。

這裡有個容易混淆的地方，要特別講清楚它跟 on-demand 的分界：on-demand 是 agent 在工作時自己伸手去拿；reference 是因為被指到才被載入。你交給某個任務的一份 spec、某個檔案裡連進來的一份文件，都是「刻意、有方向、然後才進來」。

三種排在一起看

類型誰決定它進來典型例子成本節奏
Always-on工具自動，每個 session 開始就載入AGENTS.md（技術棧、核心慣例）每個 session 都付
On-demandagent 自己在任務中伸手去拿搜尋後打開的檔、觸發後載入的 skill用到才付
Reference你或某個檔案明確指到它spec、設計文件、磁碟上的程式庫用到才付
真正關鍵的那一個區別：always-on 每個 session 都付錢；on-demand 和 reference 只在用到時才付。就是這個差別，讓這節課的後半段變得重要。

為什麼 always-on 必須保持很小

這裡有個陷阱，而且它剛好跟多數人的直覺相反。

當你學到「agent 只知道被載入的東西」之後，最自然的反應是：那就多載一點啊。把所有東西都塞進 always-on 檔案，每一條慣例、整份風格指南、所有架構筆記、完整的踩雷清單。確保它永遠不缺 context。更多 context，更好的 agent，對吧？

這個方向是反的，而且它失敗的原因，你其實已經懂了。

always-on 檔案裡的每一行，都會在你還沒打字之前，被載入到每個 session 裡。它不是一次性的設定成本，它是租金。你在這場對話付它、下一場付它、之後每一場都付它，不管你眼前這個任務用不用得上其中任何一行。

把它接回上一課的兩件事，你就會懂為什麼。第一是 token：閱讀是昂貴的，而 always-on 檔案是在每個 session 開頭就被讀進視窗；一份肥大的檔案，還在你開始工作之前就先燒掉你的預算。

第二件更糟，是 context rot。模型的掌握力會隨著視窗被填滿而減弱，而那些跟當前任務無關、卻在搶注意力的材料，會實實在在地把模型拉離你正在做的事。一份巨大的 always-on 檔案，就是一大坨多數無關的資料，從第一則訊息開始、在每個任務上都卡在視窗裡，拖著所有任務一起變差。

九份文件的錯誤

課程幫這個失敗取了一個名字，叫「九份文件的錯誤」（the nine-files mistake）。有個人，為了周延，把九份文件全都接進 always-on：風格指南、API 慣例、資料夾結構說明、測試哲學，全部接進去。這感覺很負責任。

但他真正做出來的，是九份檔案的租金，其中大部分對任何特定任務都無關；它們擠滿了視窗、稀釋了 agent 的注意力，反而讓那「一兩條真正重要的事實」被埋掉。他沒有給 agent 更多 context，他給的是更多噪音，而且讓 agent 每次都為這些噪音付費。

一個問句，決定一條規則的歸屬

你不需要什麼公式，只需要在每一行文字「賺到它的位置」之前，問它一個問題：

我在大多數任務上都會需要它嗎？

如果答案是「會」（例如技術棧、一條核心慣例、金額用「分」存這條規則），那它就是 always-on。如果它只在「某些」任務上相關，那它就不是 always-on context。它是一份 spec、一份文件，是 agent 在特定工作出現時才會去讀的東西。把它指過去就好，別讓它進來付租金。

這就是紀律。而且有個好消息：你之後不需要永遠靠手工維護它。我們現在把它練熟，是為了當這個 workflow 自己的 skill 之後自動幫你建立、修剪 AGENTS.md 時，你知道它做對了沒有。你沒辦法監督一套自己不懂的紀律，而現在你懂了。

小結

context 分三種。always-on 每個 session 自動載入、不管相不相關，住在專案的 AGENTS.md 裡；on-demand 是 agent 在任務中自己伸手去拿；reference 是被明確指到才進來。三者只差一個東西：成本節奏，always-on 每個 session 都付，另外兩種用到才付。也因為如此，always-on 必須很小，只留「大多任務都成立、絕不能錯」的那幾條；判斷歸屬，就問一句：我在大多數任務上都需要它嗎？

三種類型你都知道了，也知道 always-on 那條必須精簡。但我們還沒看的是機制：那個 always-on 檔案到底「怎麼」被載入？當專案裡有好幾個檔案時，哪一個說了算？還有一個看起來有載入、其實什麼都沒載進去的細微錯誤。這些留到下一節。
