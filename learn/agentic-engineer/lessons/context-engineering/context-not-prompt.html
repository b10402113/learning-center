真正的槓桿是 Context Engineering，不是 Prompt Engineering

Step 1/5 · Context Engineering

學習目標

說明為什麼把 prompt 寫得更漂亮是「錯的槓桿」，並講清楚 context engineering 是在 agent 讀到 prompt 之前，就先設計好它會知道什麼。

前言：是不是又想回去改 prompt 了？

先承認一件事。當 agent 給的答案很爛的時候，多數人第一個動作都一樣：回去把 prompt 再改一次。多加一點細節、換一種說法、把需求寫得更清楚，然後期待下一次它終於會懂。

這個反應很自然，因為我們被教了好久「prompt 才是關鍵」。市面上一整堆指南都在講同一件事：只要話說對了，agent 就會做對。

但這裡有一個多數人沒注意到的落差。你按下 enter 的那一刻，你打的那句話並不是落在一個空房間裡，而是落在 agent 當下腦中已經裝著的一大堆東西上面。這一段落差，就是這一節要講的東西，也是整個 context engineering 模組的起點。

你的 prompt 不是落在真空裡

想一想你按下 enter 的那個瞬間，agent 眼前其實已經擺了什麼：這次對話前面聊過的內容、它剛剛用工具真的打開來讀過的檔案、你設定好的 always-on context，還有工具本身出廠就附帶的系統指令。

這一整包環境，叫做 context（情境）。你打的那句話，只是「新進來的一小樣東西」。真正決定答案品質的，是那個早就擺在它眼前的環境，而不是你那一行字寫得多精準。

這件事在上一課已經講過一次：agent 只知道它被載入了什麼。現在把這條規則推到極端，你就會看到一個很荒謬的對比。

兩個對照，看出槓桿在哪

第一種情況：你寫出世間最漂亮、最詳細的 prompt，然後把它丟進一個空空的 context。它還是得猜。你給了它完美的措辭，卻沒給它任何可以拿來工作的事實。

第二種情況反過來：你只用一句粗糙、平鋪直敘的話，但那個 context 裡，對的檔案、對的慣例、對的限制都已經載好了。它第一次就把事情做對。

同樣的 agent，甚至是同一個模型。兩者的差別不在 prompt，在它周圍被擺了什麼。

把力氣花在 prompt把力氣花在 context
你在調整的那一行字的措辭、細節、語氣它讀到 prompt 之前，已經知道什麼
效果上限字再漂亮，環境空就還是得猜環境對，粗糙的話也能第一次就做對
出手的時機事後補救，輸出不好才回頭改事先設計，在它讀 prompt 之前就決定好

所以真正的技能是什麼

答案就藏在上面那張表的右欄：真正的技能，從來不是「把 prompt 寫得更好」，而是在 agent 讀到 prompt 之前，就設計好它會知道什麼。這就是 context engineering。

這個詞裡，真正在做事的是 engineering（工程） 這個字。它講的不是措辭，是設計。你在做的事是：刻意地、事先決定什麼東西要被載入、什麼不要；什麼是 agent 應該永遠知道的、什麼是它需要時才去拿的、還有什麼是它根本不該一直背在身上的。

講到底，這件事比較像系統架構，不像寫文案。一個好的建築師不會丟一句含糊的 brief 給工班，然後祈禱大家自己猜對；他會在第一塊磚放下去之前，就把所有已知條件都安排好。context engineering 就是你對 agent 做這件事的方法。

prompt 還是重要，但它是整條鏈上最後、也最小的一步。真正的槓桿在上游，在 context 裡。

回到 Module 1 的那些崩壞

還記得課程一開始提到的兩個根因嗎？「沒有真的計畫」和「沒有真的 context」。從那之後的每一課，其實都在繞著第二個根因打轉，只是先帶你認識機器怎麼運作。這一課開始，我們直接動手修它。

因為回頭看 Module 1 那些崩壞的案例，幾乎每一件都能追到某個人「沒有刻意做的一個 context 決定」。不是模型不夠聰明，而是沒有人把對的東西放到它面前。

這一課要做的，就是把這件事從「碰運氣」變成「刻意設計」。

小結

輸出變差時，多數人會去改 prompt，但那不是槓桿。你的 prompt 落在 agent 已經載入的一整包環境之上，答案品質取決於那個環境，而不是那一行字。所以真正的技能，是在它讀到 prompt 之前，就刻意決定它會知道什麼——這就是 context engineering，是設計，不是措辭。prompt 仍然重要，但它是鏈上最後、最小的一步。

既然要「設計 context」，下一個問題自然就來了：context 只有一種嗎？還是其實有好幾種，而且它們的行為差很多？下一節會把 context 拆成三種類型，並用一個關鍵差異——什麼時候付錢——把它們分開。
