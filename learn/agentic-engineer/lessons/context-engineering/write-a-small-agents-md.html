親手寫一個夠小的 AGENTS.md

Step 5/5 · Context Engineering

學習目標

照著做，在一個新專案裡寫出一份只收「每個任務都成立」規則的 AGENTS.md，用 CLAUDE.md 的 import 讓它保證載入，最後用 /context 證明它真的進來了。

前言：做出一個每次都付得起的小檔

前面四節把道理講完了：context 才是槓桿、它有三種類型、always-on 每次都要付代價、只有「大多數任務都成立」的規則才配進去。這一節不講新道理，只做一件事：把這些道理收成一個你手上真的有的檔案。

成果很具體：一個新專案裡，一份夠小的 AGENTS.md；一份 CLAUDE.md 用 import 讓它每個 session 都保證載入；還有一條指令，能讓你看著畫面說「它進來了」。

動手前只要準備兩樣：一個可以建專案的資料夾，一個跑得動 Claude Code 的環境。其他照下面四步走。

動手：四步做出來

  1. 建立專案，放進一個 Next.js app。沿用上一節的方式開一個新 repo，在裡面建一個新的 Next.js 應用。這一步只是給你一個真實的落地場景，沒有特別技巧。

  2. 寫 AGENTS.md，只放「每個任務都成立」的規則。課程示範的這份檔案短到不行，但每一條都是 agent 絕不能搞錯的常備事實：

    # Project context

- Stack: Next.js (App Router) + TypeScript.
- Money fields are named with a `Cents` suffix and typed as integer cents (e.g. totalCents), never a plain dollar amount.
- API responses use snake_case keys.

    逐條看它在做什麼：

    • Stack：技術棧幾乎每個任務都會碰到，是最典型的 always-on 事實。
    • Money fields 用 Cents 後綴、存整數分：這就是前面說的「會安靜出錯」的那種規則。金額單位寫錯，程式不會報錯，只會默默算錯錢。正因如此，它值得每次 session 都載入。
    • API responses 用 snake_case：跨所有 API 的命名慣例，對多數任務都成立。

    同樣要留意它沒有放什麼：沒有整份風格指南、沒有架構筆記、沒有踩雷清單。那些只在某些任務才相關的東西，本來就不屬於這裡。

  3. 用 import 把它接進保證通道。Claude Code 啟動時只讀 CLAUDE.md，所以你要在 CLAUDE.md 裡寫一行，把 AGENTS.md 拉進來：

    @AGENTS.md

    這一行就是上一節講的 import。少了它，你剛剛寫的 AGENTS.md 對 Claude Code 只是磁碟上一個「也許會被逛到」的檔案，不會每次都進 context。

  4. 驗證它真的進來了。重新載入 Claude Code，然後跑兩條指令：

    • /context：看「memory files」那一行，它應該顯示這個 session 有載入檔案。
    • /memory：它會列出檔名，你的 AGENTS.md 應該在清單裡（CLAUDE.md 底下的 project memory 也會一起列出來）。

    看到它出現在清單裡，這一步才算過。別憑感覺，眼睛確認一次再往下走。

順帶看一眼：規則放檔案，程式碼放 repo

那實際的程式碼呢？AGENTS.md 放的是「規則」，具體的型別與實作則留在 repo 的檔案裡，agent 需要時才去讀，那是 on-demand 或 reference，不是 always-on。

課程示範裡就有一個很小的型別檔：

export type OrderStatus = "pending" | "fulfilled" | "cancelled";

export interface Order {
  id: string;
  customerName: string;
  status: OrderStatus;
}

它的角色剛好跟 AGENTS.md 互補。AGENTS.md 把「金額用什麼單位」這種跨任務的常備事實寫成規則，讓 agent 每次都記得；這個 order.ts 則是具體的領域型別，agent 真的動手時才讀。規則進 always-on，實作留在專案裡等它來拿。

做完長什麼樣

做完你手上應該有：一份三行上下的 AGENTS.md、一個只有 import 的 CLAUDE.md，而且能在終端機跑 /context 或 /memory，指著清單說「這份 AGENTS.md 有被載入」。

之後你不必永遠手工維護它。這個 workflow 的 audit 相關 skill 會持續更新 AGENTS.md，只留下真正重要的內容。正因如此，你得先自己會寫，才判斷得出它改得對不對。

小結

做出一份夠小的 AGENTS.md 只有四步：建專案、只寫「每個任務都成立」的規則（技術棧、金額用整數分、API 用 snake_case 這一類）、在 CLAUDE.md 寫 @AGENTS.md 讓它保證載入、再用 /context 與 /memory 驗證它真的進來。具體程式碼（像 order.ts 這種型別檔）留在 repo 裡等 agent 來拿，不要塞進 always-on。這樣你就有一份每次 session 都付得起、又不會被噪音淹沒的常備簡報。

到這裡，agent 的機器你看懂了，手上的槓桿（原語、context、接下來要學的 skill）也差不多備齊。下一步是把這些零件組起來，回答一個新問題：為什麼光有槓桿還不夠，還需要一套 workflow。這正是下一章「Vibe Coding vs Agentic Engineering」要做的對照實驗。
