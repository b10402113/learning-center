跑一次 /develop：即時安裝依賴、確認功能跑得起來，再推進 scope

Step 2/5 · /develop、/audit、/sync：建置、建圖、對帳

學習目標

這一節要走完 /develop 的建置流程：讀取 scope 與 spec，只安裝這一刀需要的依賴；在宣告完成前，先證明功能跑得起來；最後推進 scope 的核取方塊，並產生 verify.md。

你也會看到兩條彈性路線：把工作直接交給一張截圖、一句話，或一段尚未正式規劃的內容；以及依工作內容選擇 UI 軌、Logical 軌，或兩者並行。

前言：先確認目標與前置條件

做完這一節，你會得到一個真的能啟動的功能，scope 裡對應的項目也會往前推進；視情況還會多一份可以重新執行的驗證清單。

動手前，先確認專案已經 scaffold 完成。也就是說，/architect 已決定 stack，專案也已經存在磁碟上；即使目前只有空骨架也可以。接著，你需要一份對應功能的 spec。若沒有，也可以走彈性路線，直接以一張截圖、一句話，或一段尚未規劃的內容作為輸入。上一節提到的 Step 0 閘門，就是這一步的入口。

閘門通過後，先讀建置流程

Step 0 判定「沒有欠下的決定」，或你選了「不需要」與「先做、記成 Assumed」之後，/develop 才會讀取 flow/build.md，並依照裡面的 Step 1 到 Step 4 建置。

如果閘門要你回到 /architect，它就不會讀這份流程，也不會開始動工。兩種情況會清楚分開。

Step 1：把任務分到對應軌道

先判斷這次要處理哪一類工作。系統會根據任務中的訊號字分類：出現「page」「component」「screen」等字眼，通常是 UI 軌；出現「api」「service」「logic」「data」等字眼，則是 Logical 軌。若兩種訊號都有，例如「auth」同時包含登入頁面與 session 邏輯，就要兩條軌都跑。

| Signals | Track |
|---|---|
| "page", "component", "screen", "layout", "ui"; a screenshot is attached; visual work against `design.md` | **UI** → `ui-guide.md` |
| "api", "endpoint", "service", "functionality", "logic", "data", "job", "webhook", "integration" | **Logical** → `logical-guide.md` |
| Both present (e.g. "auth": pages + session logic) | **Both**: run each track for its part |

如果仍然無法判斷，它只會問一次：「這是 UI、背後的邏輯，還是兩者都要？」這就是它和 /architect 的節奏差異：只在必要時停下來確認，其他時間就繼續動手。

Step 2：載入決定與慣例

分類之後，系統會讀取建置需要的四種資訊：這次功能的 spec（只讀取 build spec 需要的段落，不讀決策歷史）、離目標程式碼最近的 AGENTS.md、UI 軌才需要的 design.md，以及專案的建置風格（build approach）。

建置風格回答的是「這一刀要怎麼組起來」，至於功能裡要有什麼，則由 spec 決定。風格的優先順序是：功能在 scope 中宣告的覆寫優先，其次是 root AGENTS.md 的專案預設，最後才是 scope 檔案的檔頭。

建置風格有四種：垂直的端到端切片、最薄但可用的完整體、先做 UI 外殼再接資料，還有每個階段完成一條完整的使用者旅程。

Strategies: vertical end to end slice, thinnest usable whole, UI shell first prototype wired later, full user journey per phase.

接著還有兩件較耗 context 的事會交給唯讀子代理處理，避免把大量檔案內容都塞進主對話。

第一個是探索用的 scout：它會找出需要建立或修改的檔案、可沿用的既有 pattern，以及可能遇到的地雷。第二個是 researcher：只有在需要查某項工具的最新用法時，才會派它上網查詢。兩者都使用最便宜的模型，只帶回精簡摘要，不會把原始內容整批送回主對話。

Step 3：開始建置，依需要即時安裝依賴

開始寫程式前，先確認這是接續既有工作，還是從頭開始。系統會找到 spec 中 ## Build plan 的第一個未勾選項目；標記為 [x] 的部分代表已完成，不會重做。接著，它會告訴你目前的進度，例如：「這個功能已完成 4/10，從資料整合這裡接續」。

寫程式由主執行緒負責，不會另外派子代理代寫；即使建置規模很大，也是一段一段按順序完成。

如果是 greenfield scaffold 任務，系統不會憑印象拼出一個「現代專案」的樣子，而是使用該框架自己的初始化工具，把專案建到磁碟上。這樣做是為了讓專案地基符合社群實際出貨的樣子。

Read the ARCHITECTURE spec's `## Proposed stack`; run the framework's own project initializer for the stack the spec names; install base dependencies (framework, core runtime, only what the first slice needs); lay out directories; confirm a dev server or build runs.

依賴採取「即時安裝」：spec 可能一次列出 email、監控、分析等工具，但系統不會在第一天就全部裝好。它只安裝第一刀切片真正需要的依賴，以及 lint、format、型別嚴格度等跨切面工具。其他函式庫等做到需要它的功能時，再隨功能一起安裝，並一併設定、建立慣例。

Install just in time: NOT every library the spec names (email, monitoring, and so on); each later feature installs its own when built; only cross cutting tooling (lint, format, type strictness) comes early, via `/audit` + the tooling task.

這種做法的代價，是專案一開始看起來可能「不完整」。好處則是不用讓十個尚未用到的依賴閒置一個月；每個工具都會在真正需要時才加入，也能在那時設定好，並建立相應慣例。課程將這描述為專業團隊實際採用的做法。

資料層建置的隱藏條件：migration 必須真的跑過

如果這一刀包含資料層，有個很容易誤判的地方：產生 migration 檔，不代表工作已完成。你必須把 migration 實際套用到目標資料庫，並確認 schema 已經上線，例如查詢資料庫或使用 introspection。只檢查 migration 檔案是否寫得正確還不夠；「產生了但沒有套用」就不算完成。

**A data layer build isn't done until its migration is applied and verified**: generate the migration, run it against the target DB, confirm the schema is live (tables/columns/relationships exist; query the DB or its introspection, not just the migration file) before ticking. Generated but unapplied = not done. (`logical-guide.md`, Phase 2.)

替換舊做法時，也要清掉舊程式碼

如果這一刀要替換既有實作，例如重構或更換 pattern，移除舊程式碼也是建置的一部分。死掉的函式、無法到達的 branch、沒人引用的檔案與 import，都要清理，並確認沒有其他地方還在引用它們。新舊做法並排留著，就表示工作尚未完成。

Step 4：推進 scope，並產生驗證步驟

建置完成並通過自我檢查後，才更新 scope。檢查可能包括型別檢查或建置通過、UI 確實有渲染，以及資料層的 migration 已套用。原則很簡單：只勾選真的完成的項目。若工作中斷或只完成一部分，就先不要勾選，讓功能維持 in-progress，並清楚說明尚未完成的部分。

也要分清勾選的層次：spec 中 ## Build plan 的細項是原子任務，scope 裡的功能框則是里程碑的彙總。系統會勾選里程碑的框，並在功能列的 code in <path> 記錄程式碼位置。

至於是否把功能標成 done，由你決定，不會由系統代替你決定。標成 done 後，對應 spec 的 **Status**: 才會從 In Progress 推進到 Accepted。

最後，系統會依驗收條件整理出具體的驗證步驟，並詢問你是否要存成 verify.md。這份檔案可以交給之後的 /check verify 執行，也能讓 /test 接手，把適合長期保留的步驟鎖成測試。

# Verify: <feature> · spec NNNN · updated <date>
_Steps derived from spec NNNN acceptance criteria. `/check verify` runs these; `/test` locks the durable ones._
## UI / manual
- [ ] <action> → <expected>        → AC-N
## Commands
- [ ] `<command>` → <expected>     → AC-N
## Acceptance-criteria coverage
- AC-1 … covered by step … · AC-2 … · …

彈性路線：不照計畫走也可以

前面的步驟走的是依照 scope 順序建置的紀律路線。課程也強調另一種選擇：彈性路線。你可以直接把一張截圖、一句話，或一段尚未正式規劃的工作交給 /develop，它仍會用同樣的標準建置。

課程示範的情境是：scope 裡沒有「首頁」這個項目，使用者直接把一張視覺稿交給 /develop，要求它製作首頁。系統沒有跳出 workflow，而是辨認出這是 UI 軌，並自動把工作歸到 scope 裡的「feature 10 marketing page and seo」之下。

它不只把截圖照樣做成靜態畫面，還會從視覺稿推導出整套設計系統：design.md 記錄視覺方向與設計規則，實際的顏色、間距和字體則放在 globals.css。每個設定只定義一次，不在多個檔案裡重複，避免日後互相矛盾。

接著只要執行一次不帶參數的 /scope，它就會用實際存在的畫面和計畫對帳，把已完成的工作補進 scope，而不是假裝原本的計畫仍然準確。也就是說，離開計畫不會弄壞 workflow；計畫會跟上產品實際的狀態。

小結

閘門通過後，/develop 讀取 flow/build.md，依序完成 Step 1 到 Step 4：先分類為 UI、Logical 或兩者；再載入 spec、最近的 AGENTS.md、design.md 與建置風格；接著派唯讀子代理探索程式碼或查詢文件，並在主執行緒上建置，依需要即時安裝依賴。

資料層建置要以 migration 已套用、schema 已上線為準；替換舊做法時，也要清除舊程式碼。完成後，只勾選真的做完的項目、推進 scope，並依驗收條件產生可交給 /check verify 與 /test 使用的 verify.md。你也可以直接把截圖或一句話交給 /develop，再讓 /scope 對齊實際完成的工作。

功能跑得起來之後，接下來要整理的是相關文件。專案裡已經有實際的程式碼、指令與慣例，卻還沒有文件把這些資訊寫給 agent 看。下一節會介紹 /audit 如何將專案現況整理成一份短而準的 AGENTS.md。
