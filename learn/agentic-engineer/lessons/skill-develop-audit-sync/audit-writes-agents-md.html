/audit：寫出短而準的 AGENTS.md

Step 3/5 · /develop、/audit、/sync：建置、建圖、對帳

學習目標

理解為什麼每個後續 skill 都需要一份共享的 context 檔，並了解 /audit 如何依 repo 型態（greenfield、whole-repo、area、gap-fill）寫出簡短且有依據的 AGENTS.md（root 與 nested），只留一行指標的 CLAUDE.md。如果 spec 與 scope 的值互相衝突，/audit 會指出兩個檔案，不會自行判定誰對誰錯。

前言：每個 skill 都得重新認識一次專案嗎？

上一節結束時，專案裡已經有實際的程式碼、框架、設定、依賴與指令。但還少了一份能快速回答「這個專案該怎麼跑」的說明：用哪個指令啟動、型別檢查要多嚴格、資料庫改動走哪條路、資料夾是按功能還是技術層分類，這些資訊都散落在程式碼裡，還沒有人整理在一起。

缺少這份說明，後續每個 skill 都得重新研究專案。有些資訊掃描程式碼就找得到，但要花時間；有些則無從確認，只能每一輪都猜，而且可能每次猜得不一樣。就像同一個專案今天被認為資料庫走 A，明天又被認為走 B，因為 agent 不知道三天前已經有人做過決定。/audit 要解決的，正是這種反覆摸索和前後不一致的問題。

AGENTS.md：agent 讀其他檔案前先讀的說明

/audit 會產出 AGENTS.md。這份檔案會在 agent 讀其他檔案之前先載入，記錄 repo 的全域事實，例如使用的技術、可用指令，以及適用於整個專案的慣例。

AGENTS.md 刻意採用不綁定特定工具的檔名。過去各種 AI 工具各有偏好的說明檔：Claude Code 認 CLAUDE.md，Cursor、Copilot 等工具則可能讀取其他檔案。團隊因此容易同時維護好幾份重複內容，久了還可能互相矛盾。把 AGENTS.md 當成唯一正本，可以減少這種重工。這套做法中的 CLAUDE.md 只留一行，使用 Claude Code 的 @ import 指向旁邊的 AGENTS.md，不會在兩份檔案裡重複維護內容。

- [<area>/AGENTS.md](<area>/AGENTS.md) (<one-line description>)

新增 nested 說明檔時，這一行會放在 root AGENTS.md 的 ## Context files 底下，指向該區域的說明。agent 進入那個區域後，就能沿著指標讀取更貼近程式碼的資訊。

root 短而全域，nested 只給有獨特規則的區域

把每個資料夾都放一份說明，看起來很完整，實際上卻會增加載入成本。一份塞滿內容的 root 說明，會在每則訊息裡反覆佔用 context，很快就把空間擠滿。因此，root 檔案應該保持簡短，只記錄整個 repo 都適用的規則，而不是把所有慣例通通塞進去。

只有當某個區域有穩定而獨特的規則時，才值得在那裡新增一份 AGENTS.md。例如 payments 區域可能有自己的重試策略、供應商失敗處理、安全規則與重複請求處理方式。若把這些規則放在 root，就會干擾正在處理公開網站的 agent。root 可以留一條指標，告訴 agent「payments 相關內容請看 payments 的 AGENTS.md」；處理 payments 的 skill 就會同時讀到 root 與區域說明。判斷依據是「這個區域是否有足夠獨特、長期適用的慣例」，而不是「這個資料夾是否存在」。

為什麼說明要短：長而通用，反而容易拖累 agent

講師分享一項實務觀察：又長又通用的 AGENTS.md，反而可能讓 agent 表現更差。真正重要的規則會被常識、重複解釋，以及不符合這個 repo 的通用 pattern 淹沒。

因此，/audit 的核心原則是根據專案裡實際存在的細節，寫出一份精簡說明。判斷標準很直接：每一行都應該能改變 agent 在這個 repo 裡的行為；做不到的，就不該寫進去。

它怎麼選模式：先看訊號，再判斷 repo 型態

開始寫檔之前，/audit 會先收集訊號，判斷目前的 repo 屬於哪種情況。只看檔案數量容易看走眼，因為剛 scaffold 出來的骨架也可能有不少檔案，所以它會合併多種證據來判斷。

1. Context files: root AGENTS.md present → `ROOT_EXISTS`; a CLAUDE.md with content only → `ROOT_LEGACY`; neither → `ROOT_MISSING`.
2. Source count across common ecosystems (extensions like `.ts/.tsx/.js/.jsx/.py/.go/.rs/.java/.rb/.swift/.kt/.php/.cs/.dart/.ex/.exs/.scala/.c/.cpp/.h/.lua/.clj`), excluding vendored/generated dirs (`node_modules`, `.git`, `dist`, `build`) and config files (`*.config.*`).
3. Established signals: `git log --oneline` for commit history depth; a real manifest (`package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `composer.json`, `*.csproj`, `pubspec.yaml`, `mix.exs`, `Gemfile`).
4. Monorepo signal: workspace markers (`pnpm-workspace.yaml`, `turbo.json`, a `"workspaces"` field in `package.json`) or any `apps/*/package.json` / `packages/*/package.json` near the root.
5. **Workflow setup signal (`WORKFLOW_SETUP`)**: root AGENTS.md is MISSING while the workflow has already decided the stack, i.e. a `docs/specs/` architecture spec exists (a `## Proposed stack` section), and/or `docs/scope/` has a "Stack and architecture" (or similar foundational scaffold) feature. This is the intended greenfield order (`/scope` → `/architect` decides the stack → `/develop` scaffolds it → `/audit`): freshly scaffolded, still needs coding standards captured. When it fires, the manifest and scaffold source that now exist are the scaffold, not a existing codebase.

這份清單裡的第五項 WORKFLOW_SETUP 要特別注意。它用來辨認一種容易誤判的情況：專案已經依 workflow scaffold 出 manifest 和起始程式碼，但它其實仍是 greenfield，只是還沒記錄 coding standards。若只看程式碼數量，可能會把它誤認成 brownfield，跳過該詢問標準的步驟。WORKFLOW_SETUP 的優先序高於單純的程式碼數量，就是為了避免這種誤判。

收集訊號後，/audit 會依下表選擇模式。判斷順序很重要：有提供區域參數時走 Phase 3；已經有 root 說明檔時走 Phase 4；其他情況再判斷是否為 greenfield。若仍無法分辨，就進入 Phase 0 詢問，而不會直接把可能是 greenfield 的專案當成 brownfield。

| Condition | Phase |
|---|---|
| Area path given as argument | Phase 3 |
| `ROOT_EXISTS` (or `ROOT_LEGACY` after migration) | Phase 4 |
| `ROOT_MISSING` and `WORKFLOW_SETUP` (stack spec and/or scope stack feature) | **Phase 1**, even though a manifest and scaffold source now exist. Ask the coding standards; seed root from the spec's stack. Never treat a just scaffolded workflow project as brownfield. |
| `ROOT_MISSING`, no `WORKFLOW_SETUP`, no source files AND no manifest | Phase 1 |
| `ROOT_MISSING`, no `WORKFLOW_SETUP`, has code (source ≥ 10 or a manifest), ≥ 2 commits and clearly real feature code (not just scaffold) | Phase 2, any language |
| `ROOT_MISSING`, no `WORKFLOW_SETUP`, has code but it looks like untouched scaffold, or ≤ 1 commit, or you can't tell greenfield from brownfield | Phase 0, ask |

四種主要模式可以這樣理解：greenfield 會先詢問 coding standards，再根據答案和 scope 的 build approach 建立 root 說明；whole-repo 會掃描整個既有專案，建立 root 說明，以及它判斷有必要的 nested 說明；area 只處理指定區域；gap-fill 則拿既有說明檔和整份程式碼比對，只補上缺少的內容，不覆蓋別人已整理好的部分。

承接既有決定，不重新開一場辯論

課程示範中的 AGENTS.md 承接了兩種來源：stack 取自已接受的架構 spec，build approach 則取自仍在使用的 scope。/audit 要做的是整理並沿用已經存在的決定，而不是重新辯論，或暗中把它們換掉。

如果 spec 和 scope 後來出現不一致，重新執行 /audit 時，它會指出差異，並標明涉及的兩個檔案；它不會自行判斷哪一份才對，也不會偷偷選一個作為答案。這讓 workflow 不必完全依賴「每個指令都得照完美順序執行」：無論什麼時候跑 audit，它都會整理當下已有的決定，並揭露尚未解決的衝突。

/audit 也有清楚的工作邊界：它不建立 spec（那是 /architect 的工作），不在變更後維護這些檔案（那是 /sync 的工作），也不負責撰寫功能範圍（那是 /scope 的工作）。

小結

AGENTS.md 是 agent 讀其他檔案前先讀的專案說明，也是後續 skill 共用的底座；CLAUDE.md 只留一行指向它。root 說明保持簡短、記錄全域規則；nested 說明只放在確實有獨特且長期慣例的區域。每一行都應該能影響 agent 在這個 repo 裡的行為，否則就不該寫進去。/audit 會根據 pre-flight 訊號選擇 greenfield、whole-repo、area 或 gap-fill 模式，其中 WORKFLOW_SETUP 能避免把剛 scaffold 的專案誤判為 brownfield。它承接既有決定；若 spec 和 scope 不一致，就指出兩個檔案，而不自行裁決。

有了這份共享說明，後續 skill 就能從一致的專案理解出發。不過專案會持續變動，文件也可能逐漸和實況脫節。下一節會介紹 /sync 如何只以 git 的檔案狀態為證據，讓文件重新對上程式碼的實際樣貌。
