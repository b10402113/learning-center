/develop 是什麼：spec gate 與 Assumed 逃生口

Step 1/5 · /develop、/audit、/sync：建置、建圖、對帳

學習目標

認識 /develop 的職責與它在 workflow 中的位置，並掌握 Step 0 spec gate 的機械判準（input coverage），以及它提供的三個選項。尤其要理解其中的逃生口：先做，再把假設記成一張 Assumed stub。

前言：那個決定後來去哪了？

功能做到一半，你可能會碰上一個非決定不可的岔路：session 要存在哪裡、金額的小數點怎麼進位，或使用者的「今天」要依哪個時區計算。你憑直覺選了一個，程式也跑起來了，於是繼續往下做。

三個星期後，有人問：「為什麼這裡是這樣算的？」你記得當時做過選擇，卻想不起理由；對話紀錄也早就清掉了。大家只好重新討論，而這次挑出的答案，可能又跟上次不同。於是整個團隊在同一個決定上反覆來回。

上一節提過，/scope 把要做的事整理成清單，/architect 則把重要決定寫成 spec，存進 docs/specs/。這一節要接著看：清單上的第一項開始動工時，會發生什麼事？負責動手的是 /develop，而它最重要的設計，是用一道關卡避免建置時默默自行做決定。

/develop 的職責：建置者，不是決策者

/develop 是整套 skills 裡負責建置的 builder：它把 spec 和專案慣例轉成能跑的東西。開始開發前，它會先把任務分成三條軌道之一：UI（頁面、元件、版面）、Logical（API、服務、資料層、商業邏輯、整合），或兩者都需要。像「auth」這類前後台都要修改的任務，就會同時走兩條軌道。

它和 /architect 最大的差別，是誰負責做決定。/architect 會透過訪談釐清重要選擇，再寫進 spec；/develop 不會這樣做。它讀取決定並直接建置，只有遇到設計本來就留白的地方，才會回頭詢問。簡單說，/architect 負責決定，/develop 負責動手。這樣分工，是為了避免建置的人一邊做、一邊猜本該先決定的事。

Step 0：一道機械的 spec gate

既然 /develop 不該負責決策，它怎麼知道自己是不是正要偷偷做出一個決定？關鍵在於：它不靠主觀感覺判斷。

模型很容易把自己的選擇合理化。只要它覺得「這只是一般的接線工作」，就可能順手略過一個真正重要的決定。為了避免這種情況，/develop 使用一個正向、可檢查的判準，叫做 input coverage（輸入覆蓋）。它先列出這次建置必須產生、計算或顯示的每個值，再逐一確認 spec 有沒有說明值的來源。只要有一個必要值沒有明確來源，就代表還欠下一個決定，閘門便會關閉。

> **Enumerate every value this build must produce, compute, or display (from the acceptance criteria and the spec's design). For each, does the spec name where it comes from (an input, a DB column, a derivation from a named value, a prior decision)? Any required value with no named source is an owed decision.**

判斷一個選擇是否重要，不能只看它表面上小不小，而要看它會不會決定某個值的來源，或影響驗收條件所約束的行為。比如「用使用者最後一筆讀取紀錄上的時區，計算他今天的日期」，聽起來像是接一條線，實際上卻是在決定驗收條件涉及的值從哪裡來，因此仍是欠下的決定，不是單純的實作細節。

只有 spec 已經完全約束的選擇，才算純實作：像是更換變數名稱、選用哪個 helper、採用哪種迴圈寫法，或修正單純的小 bug。

閘門關起來之後：三個選項

發現有決定尚未做出時，/develop 不會默默停下，也不會自行猜答案。它會指出具體缺少的選擇，並提供三個選項，其中一個會明確標為建議。

  1. `Architect it first`: "Recommended. Capture the decision in a spec before building, so the build has a spec." → **end here** with the handoff below. Do not build.
  2. `No, not needed`: "I've judged there's no real decision here; build directly." → proceed to the build flow (`flow/build.md`).
  3. `Build now, record it as an assumed spec`: "Build it, but write the assumption down first so the decision lives in the repo, not just this chat. The `Assumed` spec stays flagged as owing ratification (`/architect`), but that never blocks marking the feature `done`." → write an `Assumed` spec (below), then proceed to the build flow (`flow/build.md`), leaving the feature `in-progress` with an `assumed decision (spec NNNN)` note in the scope (`docs/scope/`).

第一個選項是先回到 /architect，把決定寫進 spec，再開始建置；這是建議做法。第二個選項是確認這裡沒有真正需要做的決定，直接往下建置。第三個選項最適合暫時無法深入討論、但仍需要繼續推進的情況。

Assumed 逃生口：決定要寫下來，但不一定要現在想清楚

有時你已經知道要接哪家的認證，或想採用哪種資料模型，只是眼下沒有時間仔細討論。第三個選項允許你先做，但必須先把採用的假設寫成規格，存進 repo。

建置前，/develop 會建立一份最小規格，狀態標成 Assumed。它像一張「先開的白條」：決定會留在檔案裡，不只存在這輪對話中。即使對話被 /clear 清掉，隊友仍能讀到；下一次 /develop 也能依照這份規格建置，不必再猜一次。

# NNNN · <feature>

**Status**: Assumed
**Date**: <today>
**Authorized by**: <engineer>, during /develop

## Owed decision
<the specific load bearing choice that was not made>

## Assumption built on
<the concrete assumption this build will use>

## Code area
<the paths this build will touch>

## Requirements
<acceptance criteria seeds carried from the scope Done when, if any>

## Ratify
This decision was recorded by /develop, not deliberated. Run `/architect <feature>`
to deliberate and ratify it. Until then it stays flagged as an owed decision; it does not block marking the feature `done`.

最後的 ## Ratify 說明了這張白條的性質：它是把決定記錄下來，不代表已經經過充分討論。要真正討論並追認這個決定，必須交由 /architect 處理；這個追認動作稱為 ratification。

有兩條規則容易混淆。第一，只有 /develop 會建立這類 spec，而且只能建立 Assumed 狀態的規格，內容也只限於範本列出的欄位。它不會補寫 rationale，也不會把 Assumed 規格改成其他狀態。第二，尚未追認的 Assumed 規格，不會阻止功能標記為完成。workflow 要求的是把決定記錄下來，不是規定沒想清楚就不能交件；是否追認，仍由你決定。

小結

/develop 是 builder：它讀取 spec 與專案慣例，把功能建置成能跑的程式碼，並依任務走 UI、Logical 或兩條軌道。它不負責做決定，因此 Step 0 會用機械的 input coverage 判準把關：必要值若沒有明確來源，就是欠下的決定。遇到這種情況，它提供三個選項：回到 /architect 補上決定、判斷不需要決定而直接建置，或先做並把假設寫成 Assumed 規格。這張白條會讓決定留在 repo，等待 /architect 事後追認，而且不會阻止你把功能標記為完成。

spec gate 的作用，是把「先決定再建置」和「先記下假設再建置」清楚分開。下一節會接著依序走過 /develop 的建置流程：它如何只載入這次任務需要的依賴、如何在宣告完成前驗證成果，以及如何推進 scope；最後也會介紹那條彈性的建置路線。
