決定測試策略與 ownership 護欄

Step 3/6 · Greenfield：Scaffold、Tooling 與規範

學習目標

在「只做 type check 加手動驗證、不寫測試套件」與 spec 既有的測試承諾之間的衝突上做決定並走 reconciliation，並說出 scoped query helper 如何替代測試守住 user-owned 資料的 ownership。

前言：這一題沒有標準答案，只有你的答案

上一節的 /audit 訪談裡，有一題被輕輕帶過：測試慣例要選什麼。你選了「只做 type check 加手動驗證」，當下聽起來很合理，因為你只是想證明 app 能跑，不想為一個雛形背上一整套測試套件的 overhead。問題是，這個選擇跟你先前說過的話、以及 spec 裡白紙黑字的承諾互相打架。

這一節要處理的不是「該不該寫測試」這種泛泛之談，而是一個很具體的處境：你已經做了跟文件相反的決定，接下來該怎麼讓它變成「真的」。同時還有一個更深的問題躲在後面——如果沒有測試，那到底是什麼在替你守住資料不會外洩？這一節把這兩個問題一起解決。

決定的張力在哪裡

兩股力量在拉扯。一邊是成本：測試套件要寫、要維護，而且每加一個功能就要多照顧一批測試，對一個還在抓方向的專案來說是實實在在的負擔。另一邊是安全：測試平常看起來很多餘，直到某個地方漏了一個條件、把不該給人看的資料送出去。

課程的 agent 在示範時把這個風險講得非常具體。它反問：少了測試套件，那麼「ownership 的範圍」由什麼來保護？例如某個 server action 忘了加 where userId，就會把另一個人的評分歷史整個露出來，而背後沒有任何東西擋著。

it pushes further, saying that without a test suite, what protects the ownership scoping? Like a forgotten where user ID in one server action exposes another person's rating history with nothing behind it.

這就是決定的核心：你不是在「寫測試」和「不寫測試」之間選，你是在「用測試守住」和「用別的機制守住」之間選。看不見這個差別，就會誤以為選了不寫測試等於接受風險。

三個選項擺在一起看

選項你付出什麼你換到什麼
Unit + integration（加框架）寫與維護測試的持續成本行為被自動鎖住，改壞會當場失敗
只有 type check + 手動驗證每次改動靠人工複查沒有測試負擔，迭代最快
TDD（先寫測試）最高的前置成本與紀律設計被測試逼出來，最嚴謹

課程把這三個選項定義在 audit 的 tooling 問題裡，並且特別註明：這裡選的是「慣例」，真正把測試框架裝起來的是後面的 /test。

- Testing gate (captured as the convention, the runner is set up by `/test`): unit + integration with a framework (suggested) · typecheck + manual `/check verify` only · tests first (TDD).

示範裡選的是中間那條路。但這裡要先岔開講一件重要的事，因為選擇本身還不是全部。

先 reconciliation，再往下走

你做的決定跟 spec 原本寫的不一樣，而且你也跟自己前面說過的話矛盾了。在這種情況下，不能就這樣假裝沒事繼續開發，否則文件跟現實各說各話，下一個功能就會踩到錯誤的假設。課程的原則是：這時候要讓「什麼是真的」重新對齊。示範者的做法是重跑 architect，明確告訴它「不要測試套件、不要 Playwright CLI」，讓 spec 的 rationale 改寫成反映最新決定。

這個動作有個冠冕堂皇的名字叫 reconciliation，其實就是一句話：你的決定變了，就讓記錄你決定的那份文件也跟著變。不急著 reconcile 的結果，就是之後某個 agent 讀到舊的 spec，照著它寫出一套你根本不想要的測試，而你要花更多時間收拾。

判別問句：你到底需不需要測試

在選擇之前，先問自己三個可以當場回答的問題。

  1. 這個專案裡，有沒有任何資料是「只該讓本人看到」的？ 如果所有資料都是公開的，漏加條件的代價很低；如果涉及到個人資料、金流、多租戶，防線就不能只靠記憶。
  2. 有沒有任何一個地方，漏掉一行條件就會把別人的資料送出去？ 這正是課程舉的例子。只要有這種點，你就要問「誰在守它」。
  3. 你能接受「靠人工每次複查」嗎？ 手動驗證不是不行，但它是人力的成本，而且會隨著功能變多而稀釋。

如果前兩題的答案都是「有」，那麼完全不設防的風險就太高了。示範者走的路是：不寫測試套件，但引入一個別的機制來守住 ownership。

那個替代機制：scoped query helper

課程把這個機制叫做 scoped query helper——一個所有 user-owned 資料的讀與寫都必須經過的函式。它的想法很單純：與其指望每一處程式碼都記得加上 where userId，不如把「一定要帶上 userId」這件事封裝進唯一一個入口，讓所有讀寫都從這個入口進去。這樣一來，就算你在其他地方寫得很隨性，也很難繞過這個把關。

Or maybe introduce scoped query helpers, a function that every read and write of user owned data goes through.

用程式碼來對照會更清楚。下面左邊是「靠自制力」的寫法，危險點在於每個呼叫端都得記得帶條件；右邊是把條件收進 helper，呼叫端拿不到「不帶 userId 的查詢」。

// 危險：每個呼叫端都要自己想起來帶 where userId
export async function getRatings(movieId: string) {
  return db.select().from(ratings).where(eq(ratings.movieId, movieId));
}
// scoped query helper：user-owned 資料的唯一入口
export function scopedRatings(userId: string) {
  return {
    list: (movieId: string) =>
      db.select().from(ratings)
        .where(and(eq(ratings.userId, userId), eq(ratings.movieId, movieId))),
  };
}

要注意它的定位：它不是測試，它是在原始碼層面把規則收斂到一個地方。測試是在事後抓出「你寫錯了」，helper 是讓「寫錯」這件事比較不容易發生。兩者防的是同一件事，只是攔截的時機不同。示範裡這個 helper 沒有馬上做，而是被排進第三個 feature，跟資料模型一起處理。

反例：什麼時候這個選擇會翻轉

「不寫測試」不是永遠錯的。如果這個專案只是一個一次性的探索、資料全部公開、壞掉的代價只是重跑一次，那選擇型別檢查加手動驗證完全合理，硬塞一套測試只是浪費。反過來說，如果專案有金流、有多租戶隔離、有法規要求，那麼就算有 scoped query helper，多半還是會加上整合測試或資料庫層的 row-level security，因為這種系統錯一次就賠一次。

還有一個更隱蔽的翻轉條件：scoped query helper 之所以有效，前提是「所有 user-owned 資料都真的從它進出」。只要有幾處是繞過它直接查資料庫的，這個防線就出現缺口。所以工具層面還需要一條規則來協助，這也正是下一個步驟 /develop tooling 要處理的事。

小結

測試策略是一個取捨，不是一個是非題。你在「用測試守住」和「用別的機制守住」之間選；示範裡選了不寫測試套件，改用 scoped query helper——一個所有 user-owned 資料讀寫都必須經過的函式，來守住 ownership。做了跟 spec 相反的決定，就要透過 reconciliation 讓 spec 重新對齊真實，否則舊文件會讓下一個功能踩到錯誤假設。選擇是否成立，取決於資料敏不敏感，以及那個防線有沒有被繞過。

你現在有一份規範、一個資料防線的決定，但它們都還只是文件。下一節要看 /develop tooling 如何把這些點名的規則變成機械檢查——裝上 Biome 與 Lefthook pre-commit，讓「忘了帶條件」這類錯誤在提交前就被擋下來。
