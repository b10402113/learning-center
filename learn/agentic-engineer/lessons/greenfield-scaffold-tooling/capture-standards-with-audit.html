/audit：把專案規範捕捉進 AGENTS.md

Step 2/6 · Greenfield：Scaffold、Tooling 與規範

學習目標

說出 greenfield 的 /audit 是 standards capture 而不是 codebase scan，認得它訪談的每個維度（架構風格、資料夾切法、coding standards、lint／format、pre-commit、testing 慣例、CI、Git），並知道產物是一份短小的 AGENTS.md 加一行指標的 CLAUDE.md。

前言：專案能跑了，但它還不知道你的規矩

上一節結束時，你的專案已經 build 得過、伺服器起得來、首頁回 200。骨架有了，但裡面對「這個專案該怎麼寫」一無所知。接下來的每一個功能，agent 都會自己決定要用函式還是類別、檔案放哪、錯誤怎麼處理。它每次的決定可能都合理，但合在一起就是風格各異的一堆程式碼。你需要的，是在開始疊功能之前，先把規矩一次講清楚。

/audit 就是負責建立這套規矩的 skill。不過它在這裡有一個很容易誤會的地方：很多人以為 audit 是「掃描整個程式庫、把既有慣例讀出來」，那是 brownfield 的用法。在 greenfield 上，它做的完全是另一件事——問你。搞懂這個差別，你才不會在一個全新專案上期待它變魔術。

greenfield 的 audit 是 standards capture，不是掃描

課程把觸發條件寫得很清楚。當一個專案已經有 stack spec、卻還沒有根目錄的 AGENTS.md 時，就算它已經有 manifest、有 scaffold 產生的原始碼，它仍然算 greenfield。這些檔案是「剛生出來的骨架」，不是「別人寫了好幾年的系統」，所以 audit 不會去猜你的慣例，而是直接問。

Trigger: greenfield, including the workflow setup case (a stack spec exists but no root AGENTS.md), or Phase 0 → `New project`. A manifest and scaffold source may exist; that is the scaffold, not a existing codebase, so still ask the standards.

這個設計有它的道理。brownfield 的慣例藏在程式碼裡，所以要用讀的把線索挖出來；greenfield 還沒有慣例可言，你問它也沒得讀，不如直接從你腦中把標準拿出來。這也是為什麼 audit 在 greenfield 這條路上，產出品質幾乎完全取決於你回答得夠不夠具體。

輸入你的選擇，加上真實的 scaffold程式碼本身呈現的慣例

它會問你哪些維度

這份訪談問得很廣，因為這是慣例與 tooling 唯一一次被定下來的地方。課程要求它把每一題都問清楚，而不是假設一個預設值。問題分成兩大類：架構與程式碼慣例，以及 tooling。

架構那一類，它會要你在四種風格中選一個——Clean Architecture、Functional、Domain Driven Design、SOLID OOP。示範裡選的是 Functional，也就是用單純的函式、不可變的資料。接著是型別嚴格度（若語言有型別系統）、資料夾要按層切還是按功能切（示範選按功能切），以及其他程式碼標準：只用 named export、統一的錯誤處理模式、無障礙基線、公開函式要有文件。

- Linting & formatting (adaptive): the standard linter + formatter for this stack (suggested; list an already installed one first) · a specific alternative · minimal for now.
- Checks before commit: lint + format + typecheck on every commit (suggested) · format only · none.
- Testing gate (captured as the convention, the runner is set up by `/test`): unit + integration with a framework (suggested) · typecheck + manual `/check verify` only · tests first (TDD).
- Continuous integration: a basic CI check on push (lint, typecheck, test) (suggested) · not yet · already configured.

示範裡的選擇是這樣：lint 與 format 用 Biome，因為它把兩個設定合成一份設定檔，勝過 ESLint 加 Prettier 的組合；提交前跑 lint、format、type check；測試慣例選「只做 type check 加手動驗證」（這個決定下一節會單獨拆開來看）；CI 先不加，之後再說。最後一題是 Git——要不要讓 workflow 在每個功能自動開分支、自動提交，示範裡選了要。

這裡有一個容易搞混、但很關鍵的分工。/audit 只負責「決定與記錄」，它什麼都不會安裝。真正把套件、設定檔、pre-commit hook、CI 裝上去的是下一個步驟 /develop tooling。但問題要在此刻問，因為這裡才是記錄選擇的地方。

`/audit` records the choices, installs nothing; installing (packages, config, `pre-commit` hooks, CI) is the `/develop tooling` sub task that follows, but ask the tooling questions here where the choice is recorded.

產物：一份短的 AGENTS.md 加一行指標的 CLAUDE.md

這些回答最後會落地成一份可被任何 coding agent 讀取的純文字檔，叫做 AGENTS.md。它的定位是「這個專案實際怎麼運作」的說明書：技術棧、指令、慣例。因為它是一個通用格式，不管是哪一套 AI 工具都能讀，所以它才是唯一真實的來源。

**The context files, named `AGENTS.md`.** These describe how your project actually works, its stack, its commands, its conventions. They are written in plain text that any coding agent can read. On a project that uses Claude Code there is also a tiny `CLAUDE.md` that does nothing but point at `AGENTS.md`, so there is only ever one real source and no copy to drift.

在 Claude Code 上，它旁邊還會放一個極短的 CLAUDE.md，內容只有一行「真正的內容在 AGENTS.md」，然後用 import 把它拉進來。這樣兩份檔案不會各有一份內容、互相漂移。

# CLAUDE.md

This project's context for all AI tools lives in [AGENTS.md](./AGENTS.md).
Claude Code loads it via the import below:

@AGENTS.md

至於「短的」是什麼意思——課程的示範者講了個原則：根目錄的 AGENTS.md 只放全專案通用的規則，維持精簡。當某個區域有自己一套慣例時，才在該資料夾再放一份。skill 工作到那個區域時，會讀最靠近的那一份，於是同時看到全專案與當地的規則。

小結

greenfield 的 /audit 是 standards capture，不是 codebase scan。它不掃程式庫，而是讀真實的 scaffold、然後訪談你，把架構風格、資料夾切法、coding standards、lint／format、pre-commit、testing 慣例、CI 與 Git 的選擇捕捉下來。產物是一份短小的根目錄 AGENTS.md，旁邊配一個只有一行指標的 CLAUDE.md；區域性的慣例才在該資料夾放巢狀的一份。它的關鍵分工是「只記錄、不安裝」，把規矩寫下，安裝留給下一個步驟。

訪談裡有一題，值得單獨停下來想清楚：測試。示範時選了「只做 type check 加手動驗證」，但這個選擇跟 spec 原本的承諾互相衝突。下一節就專門處理這個取捨，以及當規範跟文件打架時該怎麼辦。
