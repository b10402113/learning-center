維持 agent 效能：skills、context 衛生與交棒

Step 6/6 · Greenfield：Scaffold、Tooling 與規範

學習目標

依 /audit 回報的 skill 缺口只安裝官方 skills、在每個 feature 之間用 /clear 保持 context 乾淨，並說出交棒給資料模型 feature 時要先解決的 open follow-ups。

前言：同樣的 agent，為什麼有時聰明有時變笨

你可能已經注意到一件事：同一套 agent，在一段對話的開頭往往表現得很好，但當對話拉長、你丟進去的檔案愈來愈多，它的判斷就開始走鐘。這不是你多心，而是 context 被塞滿之後的必然結果。而在 greenfield 這種一次要蓋很多功能的專案裡，這個問題會被放大。

還有一個更根本的問題：agent 雖然很會寫程式，但它不一定知道你的工具「真正」的慣例。它可能照著訓練資料裡的印象去寫 Drizzle 或 Zod，而那些印象可能已經過時。你要用兩件事來處理這兩個問題：在前端給它對的 skills，在後端保持 context 乾淨。這一節也順便把交棒給資料模型前必須先確認的清單交代清楚。

為什麼要花時間裝 skills

audit 在跑的時候，除了問你規範，還順手盤點了目前裝了哪些 agent skills。示範裡它回報已經有八個 skill 安裝著，同時點出還有哪些工具「還沒有對應的 skill」——Drizzle、Zod、Vitest、Resend、TMDB。它接著問你要不要去搜尋這些缺口。

It says that eight agent skills are already installed. An agent skill teaches me tools, real conventions. But there's gaps with no skills yet, such as Drizzle, Zod, Vtest, recent TMDB. Do we want to search for them?

為什麼要多花這道工？課程的紀錄給了一個很值得記住的定義：一個 agent skill 的作用，是教 agent「這個工具真正的慣例」。少了它，agent 只能靠猜；有了它，它會照那套工具社群真正在用的方式寫。示範者說得直白——這是在前期多花一點時間，但之後會非常有用。

只裝官方 skills

搜尋之後，agent 找到幾個候選：Resend（email 供應商）、Vitest、以及 Drizzle。課程的判斷是：Resend 的 skill 裝起來，Vitest 現在用不到，而 Drizzle 那個是社群版、品質較弱，因為「不是官方 skill」所以不裝。最後只安裝了 Resend 這一個。

It found some additional skills, such as for recent, our email provider, for Vtest, which we don't need right now, Drizzle, Community, Weak, we don't need those as they're not official skills. So we'll just install the recent skill.

這條「只裝官方」的原則有它的道理。skill 會直接影響 agent 產出的程式碼風格，一個品質不明的社群 skill 可能把錯誤的慣例教給 agent，反而比沒有 skill 更糟。而且安裝本身有成本：每一份 skill 都會占掉 context，裝了愈多，真正重要的資訊就愈容易被稀釋。所以選擇的標準是「官方、可靠、而且現在用得到」。

搜尋與安裝用的指令是固定的。搜尋用 skills find，安裝前可以先 --list 確認內容，確定要裝才用 -y 直接安裝。

- For each item not already covered by an installed skill or connected MCP (`npx skills list`, your connector list) or recorded as declined in `AGENTS.md`: detect Agent Skills with `npx skills find <tool-or-package>`; if weak, retry aliases from package or org names; collect every credible candidate and confirm with `npx skills add <owner>/<repo> --list` when practical.
- Install each selected skill: `npx skills add <owner>/<repo> -y`.

context 衛生：在 feature 之間 /clear

第二件事是 context 的管理。隨著工作推進，對話愈來愈長，示範裡在準備架構資料模型之前，已經累積到接近 13 萬 tokens。課程的紀錄說得很清楚：現在正是清掉它的時機。因為重要的狀態——scope、spec、AGENTS.md——都已經寫進檔案裡，對話本身不再是唯一的記憶，所以清掉 context 不會丟掉進度。

So now is the right time to clear it, and start architecting, maybe the most important part of our application.

這套 workflow 把「每個 feature 之間清一次」當成例行公事。原因不只是省錢：對話一長，前面不相關的細節會佔住注意力，讓 agent 在處理新問題時被舊脈絡干擾。因為狀態都在檔案裡，所以「清掉對話、從檔案重新載入」是最乾淨的作法。課程的建議也很直接：在每個新 feature 之前都先 /clear。

Always advise `/clear` before the next feature (state lives in files; long sessions cost more even when cached). Suggest `/compact` mid build if this feature runs long.

注意它同時給了另一半的建議：如果是「同一個 feature 蓋到一半、但這一段太長」，那不要清掉，而是用 /compact 壓縮。原則是：跨 feature 要清，單一 feature 內太長才壓縮。

交棒前的清單：資料模型

前兩個 feature 都完成、也推上 GitHub 之後，下一個要動的是資料模型。課程把它形容成整個應用最重要的部分，因為其他所有東西都站在它上面。它牽涉到的核心實體是：users、movies、ratings、taste profiles、feed pics（連同它們的理由）、watchlist entries、以及 import runs。

This is huge because it touches all the core entities. Everything else stands on users, movies, ratings, taste profiles, feed pics with their reasons, watch list entries, and import runs.

交棒之前，有幾件被延後的決定要先確認。第一，scoped query helper 被排進 feature 3，跟資料模型一起做；第二，Supabase 的 region 也要在 feature 3 處理——確認專案的 region，並讓它跟 Vercel 一致。第三，Resend 的 custom SMTP 留到 feature 6。第四，也是課程特別強調的一點：error tracking 要從「deferred」拉出來，變成一個真的計畫。因為 spec 寫著要在上線前決定，而不是等到第一次無聲故障之後才想起來。

Spec one says decide error tracking before launch, not after the first silent failure. Currently sits in deferred as analytics and error monitoring, make it a real plan. Now, not needed quite yet.

小結

要讓 agent 在整個專案裡保持有效，靠的是兩件日常習慣：一是 skills，依 audit 回報的缺口只安裝官方、現在用得到的 skill，因為 skill 教 agent 工具的「真實慣例」，而品質不明的社群版可能教錯；二是 context 衛生，在每個 feature 之間 /clear，因為狀態都在檔案裡，清掉對話不會丟進度，反而讓 agent 不被舊脈絡干擾。往下交棒時，記得先確認被延後的決定：scoped query helper 與 Supabase region 排在 feature 3，custom SMTP 排 feature 6，而 error tracking 要提早上線前的計畫。

回頭看這一整條路：你從 spec 0001 生出一個能跑的 scaffold，用 /audit 把規範捕捉進 AGENTS.md，做了一個關於測試與 ownership 的取捨，用 tooling 把規範變成機械檢查，把專案推上 GitHub，最後用 skills 與 context 衛生讓 agent 繼續保持戰力。這套順序——先讓它跑起來，再把標準固定下來，最後把標準變成機械檢查——就是 greenfield 從點子到第一個可交付專案的全部。
