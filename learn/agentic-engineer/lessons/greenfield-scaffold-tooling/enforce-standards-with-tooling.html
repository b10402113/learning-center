用 tooling 把規範變成機械檢查

Step 4/6 · Greenfield：Scaffold、Tooling 與規範

學習目標

跑 develop tooling 裝上 Biome 與 Lefthook pre-commit hook，把點名的架構規則（禁止在指定路徑外 import raw DB handle）變成機械檢查，並知道 /scope 與 /sync 要怎麼把新增的指令與規則對回文件。

前言：寫在文件裡的規則，靠什麼真的被遵守？

你已經有一份 AGENTS.md，裡面明明白白寫著「每次提交前要跑 lint、format、type check」，也寫著「不要在指定路徑之外直接 import 原始資料庫 handle」。問題是，這些話寫在文件裡，並不會自動發生。文件是給 agent 讀的提醒，它可能照做，也可能在某一次趕進度時忽略。真正要讓規則「一定會被執行」，得靠工具，而不是靠記憶。

這一節要把規範從「文件上的承諾」變成「跑得動的檢查」。動手前你需要兩樣東西：一份 /audit 已經寫好的、含 tooling 選擇的 AGENTS.md，以及那個選擇是「決定好了、但還沒安裝」的狀態。這一節只負責安裝與設定，不重新決定。

第一步：跑 develop tooling

觸發的指令是 develop tooling。它的角色很單純：把 audit 記錄下來的 tooling 選擇實際裝上。課程把這兩個 skill 的分工寫得很清楚——audit 決定並記錄，develop 負責安裝。

3. **Coding standards & tooling**: two sub tasks: `/audit` (greenfield) captures conventions AND tooling choices into root `AGENTS.md` from the real scaffolded project, not guesses; then `/develop tooling` installs the chosen tooling (packages, config files, `pre-commit` hooks, CI) per what audit captured. `/audit` decides and records, never installs; `/develop` installs.

所以你在這裡不應該被問「要用哪個 linter」——那個問題在上一節就答完了。如果 agent 又問一次，代表 audit 的記錄不夠清楚，先回頭把 AGENTS.md 的 tooling 段落補齊再繼續。

第二步：把 pre-commit 從承諾變成檢查

agent 一讀 AGENTS.md 就會發現一個矛盾：文件說每次提交前要跑 lint、format、type check，卻沒有任何東西在執行它。解法是加一個 pre-commit hook。課程的示範選擇了 Lefthook，因為它本身就是一個「依階段篩選檔案」的工具，內建了這個能力，所以不需要再額外寫一個 lint 階段。另一條路是 Husky，但它更複雜，示範沒有選它。

It's saying that the agents MD file says lint format and type check must pass before each commit, but not what enforces that. So we can enforce that with a left hook dot YAML file, which is a stage file filtering built in, so no lint stage is needed. Or we can introduce something more complex like Husky. In this case, I'll go with left hook.

設定檔大致長這樣，它把三件事綁在提交之前：

# lefthook.yaml — 提交前把規範變成機械檢查
pre-commit:
  parallel: true
  commands:
    lint:
      run: pnpm biome check {staged_files}
    format:
      run: pnpm biome format {staged_files}
    typecheck:
      run: pnpm tsc --noEmit

這裡的關鍵是 {staged_files}：hook 只檢查這次準備提交的檔案，而不是整個專案，所以速度不會隨著專案變大而拖垮。type check 沒辦法只挑檔案，因為型別是跨檔案的，所以它仍然是整包跑。

第三步：把架構規則也變成機械檢查

接下來是這一節的重點。spec 裡點名了一條架構規則：禁止在指定路徑之外 import 原始的資料庫 handle。示範裡指定的路徑是 src/lib/db 與 src/db。這條規則必須在資料模型 feature 建立 DB handle 的那一刻就生效，否則就太晚了。

And the spec notes a biome rule banning the raw DB handle import outside the source lib DB and source DB. So we can immediately add it now to restrict the import rule against the paths, the spec names. So it is live the moment the data model feature creates the DB handle.

把它寫成 Biome 的禁止匯入規則，看起來像這樣：

{
  "linter": {
    "rules": {
      "nursery": {
        "noRestrictedImports": {
          "level": "error",
          "options": {
            "paths": {
              "~/db/handle": "Raw DB handle is only allowed in src/lib/db or src/db. Use the scoped query helper elsewhere."
            }
          }
        }
      }
    }
  }
}

這條規則的價值，正好接上上一節的決定。你選擇用 scoped query helper 來守住 user-owned 資料，但那個防線成立的前提是「沒有人繞過它直接查資料庫」。這條 import 禁令就是那個前提的機械保證：它不靠你記得，而是讓那條不合規的 import 直接編不過。

第四步：把新指令與新規則對回文件

工具裝好之後，還有一個容易漏掉的收尾。示範裡的 AGENTS.md 仍然只列著 install、dev、build、type check 這幾個指令，但這次新增了一支腳本，理當被記進去。問題是那份檔案是設計給 /sync 去改的，不是讓這次的執行隨手改的。所以要跑 /sync 讓它對齊。

agents MD still lists only installed dev build and type check. The new script belongs there, but that file is synced to edit, not mine. So we have to run sync. We also have to run scope to reconcile that tier contradictions, which will likely turn features to last box, check verify and close it, and then sync the new commands.

同時也要跑 /scope。原因是這次的變動讓 spec 跟 scope 出現了一些不一致，scope 會把 feature 2 的最後一格標成完成，收掉這個 feature。跑完之後，scope、架構文件與 AGENTS.md 三者會有一致的資訊，告訴後續的開發「我們打算怎麼繼續做」。示範者特別提醒，如果你中途沒有改變主意，其實不需要這麼頻繁地跑 sync 與 scope；這些額外動作是你自己改決定換來的成本。

做完之後長什麼樣

驗收的方式很具體：Biome 裝好了、Lefthook 就定位、腳本都在，而且三條架構規則已經被機械強制執行。feature 2 的 install-the-tooling 那一格被打勾，接著 scope 收掉最後一格，feature 2 完成。

這一節只講「怎麼把規則裝成檢查」，至於 Biome 與 Lefthook 到底還支援哪些旗標與設定，屬於查閱性質，留給它們各自的官方文件。你只要記得這條原則：文件負責說明，工具負責執行；只有被機械檢查的規則，才算真的存在。

小結

/audit 只記錄選擇，/develop tooling 才負責安裝。它讀 AGENTS.md 發現「提交前要檢查」只是承諾、沒有東西執行，於是裝上 Lefthook 的 pre-commit hook，把 lint、format、type check 綁在提交前，並且立刻把 spec 點名的架構規則（禁止在指定路徑外 import 原始 DB handle）寫成 Biome 的禁止匯入規則，讓它在資料模型建立 DB handle 的那一刻就生效。收尾要用 /sync 把新指令補進文件、用 /scope 收掉這個 feature，讓三份文件的資訊一致。

規範有了、檢查也裝上了，這個專案現在已經是一個「有紀律」的專案。接下來要把這一切推上 GitHub，讓它進版控、可以被 review。下一節走的就是自動 Git 與第一次推送。
