從 spec 0001 生出可跑的 scaffold

Step 1/6 · Greenfield：Scaffold、Tooling 與規範

學習目標

跑 develop the stack and architecture（scaffold subtask）依 spec 0001 生出第一個可跑的專案，產生 example .env 讓需要的變數提早現形，並用 build、啟動、抓首頁 200 證明它真的能跑。

前言：spec 寫完了，然後呢？

你花了幾輪對話，終於讓 /scope 排出建置順序、讓 /architect 把技術棧寫進 spec 0001。文件看起來很完整，但你打開專案資料夾，裡面什麼都沒有，只有一份規格和幾份文件。規格不會自己變成程式，下一步得有人真的把專案生出來。

這個「把決定變成可執行的空殼」的動作，就是 scaffold。它看起來好像只是跑一行初始化指令，但真正決定成敗的是後面那件事：你怎麼知道它真的能跑，而不是生出一堆看起來很漂亮、實際上起不來的檔案。這一節就從頭走一遍，讓你在自己的專案上能照著做出一個可驗收的 scaffold。

動手前需要具備什麼

開始之前，你手上應該要有兩樣東西。第一，一份已經被接受的 stack spec，也就是 spec 0001，裡面記著這個專案要用什麼框架、什麼套件管理器、什麼資料庫。第二，一個已經被 /scope 排進計畫、標成第一個 foundation feature 的項目。如果還沒有 spec，先回頭跑 /architect；scaffold 是把決定落地的動作，不是拿來做決定的地方。

還有一點要記住：這個階段不要一次把所有會用到的套件都裝進來。課程的 scope 規則講得很清楚，scaffold 只裝「第一個切片真的需要」的東西，其他套件等到對應的功能被建置時再各自安裝。你先把骨架立起來，不在這一節把整棟房子蓋完。

Scaffold installs only the runnable skeleton the first slice needs (framework, language, core runtime), never every eventual library: deciding the full stack up front is correct (the spec's job), installing it all is not; each later feature installs its own dependencies when built (e.g. the billing SDK when billing is built).

第一步：說出那句觸發指令

你對 agent 說的是 develop the stack and architecture。這句話會讓 /develop 進入一個特別的分支：平常它只把功能建進一個已經存在的專案，但如果這個專案根本還不存在，而且任務就是 scaffold，那「建立專案」本身就是它的工作。課程的 skill 把這個例外寫得很明確。

Exception: if this IS the scaffold sub task of the Stack and architecture foundation feature (prompt says `scaffold`, or the step initializes the project from the stack spec), creating the project IS the job. Read the ARCHITECTURE spec's `## Proposed stack`; run the framework's own project initializer for the stack the spec names; install base dependencies (framework, core runtime, only what the first slice needs); lay out directories; confirm a dev server or build runs.

注意裡面的順序：先讀 spec 的 ## Proposed stack，再用框架自己的初始化工具去生專案。這代表 agent 不會憑記憶亂猜要用哪個模板，而是照著你已經決定好的那份規格走。

第二步：確認它先檢查了什麼

在這個階段，專案連 Git 都還沒初始化，所以沒有「你是不是落後隊友幾個 commit」這類新鮮度檢查要跑。agent 唯一該做的前置動作，是去確認那個脚手架工具「真正支援哪些參數」——不是憑印象下旗標，而是先查清楚再跑。課程的紀錄特別點出這件事，因為它決定了後面那個 scratchpad 的做法合不合理。

接著它會照 spec 選定的棧動手。這個示範裡用的是 Next.js 16，而且預設就開 Turbopack；套件管理器用 pnpm。這些選擇不是 agent 現場發明的，它們來自 spec 0001。

第三步：為什麼先建在 scratchpad，再搬進來

這裡有個很容易被忽略的細節。專案的根目錄此時已經有 docs/ 和 agents 相關的檔案了，而框架的初始化工具拒絕寫進一個已經有東西的資料夾。所以課程的做法是：先在一個 scratchpad 目錄把專案生出來，再把它搬進正式的專案路徑。

你要牢記一個原則：如果初始化工具在建專案的過程中順手建了一個 repo，那個 repo 要留著，不要在搬移時把它丟掉。骨架連同它的版本控制一起搬，之後才不會缺東缺西。

第四步：讓 example env 提早現形

專案一建好，agent 立刻產生一份 example .env。這份範例檔不是裝飾品，它的用途是把你「之後一定會需要」的變數提早列出來，讓你可以在 agent 繼續往下做的同時，去申請這些金鑰。

變數來源用途
Supabase 的 database URL 與 direct URL（還有其他 Supabase 值）應用的主要資料庫
Anthropic 與 OpenAI API key呼叫模型
TMDB API key電影資料
ingest keys背景工作的資料匯入
Resend API key寄送電子郵件

課程的示範者說得很直接：趁 agent 還在忙的時候先去拿這些金鑰很划算，因為早晚都會用到。這是一個把等待時間並行化的小技巧——你申請金鑰，agent 建置程式。

第五步：用三件事證明它真的能跑

scaffold 的驗收不是「agent 說做完了」，而是實的。做法是依序做三件事：先讓 build 過，再啟動伺服器，最後實際抓一次首頁，確認回傳 200。課程的紀錄就是在這裡看到「movie recommendation app 的首頁回 200」，才判定骨架是可執行的。

pnpm install
pnpm build
pnpm dev   # 啟動後在 localhost:3000 抓首頁，預期回 200

這三個指令各有分工。pnpm install 把依賴裝齊，pnpm build 證明專案在正式模式下編得過，pnpm dev 則是把伺服器真的跑起來。只過 build 還不夠，因為有些錯誤只在伺服器啟動、路由實際被請求時才會出現；反過來，只跑 dev 也不夠，因為開發模式比 build 寬鬆。兩個都做，才叫可執行。

做完之後長什麼樣

專案結構會長出 app、components、DB、jobs、一個給 Supabase 用的 library，以及 server。這些資料夾不是隨手分的，而是跟著 spec 的架構決定走。

同時，spec 0001 的狀態會從 proposed 推進到 in progress，其中的 develop 步驟被標成完成。因為 feature 1 的四個步驟都完成了，所以它在 scope 裡正式變成 fully done。這一步你只驗證「它能跑」，不需要跑 check-verify 或 test；課程的示範者自己在瀏覽器打開看過，就把這兩格標成已檢查。原理的部分（為什麼要先立骨架、為什麼要提早拿金鑰）留給這一節說明，操作細節你照上面的順序做就會得到結果。

小結

scaffold 是把 spec 0001 變成可執行空殼的動作。你用 develop the stack and architecture 觸發它，它會先查清楚工具的真實旗標，照 spec 選定的棧（這裡是 Next.js 16 加 Turbopack、pnpm）生出專案。因為根目錄已經有 docs 與 agents 檔案，所以先建在 scratchpad 再搬進來，並保留初始化工具建的 repo。它會立刻產生 example .env，把 Supabase、Anthropic、OpenAI、TMDB、Resend 等金鑰提早列出來。驗收是實的：build 過、伺服器起得來、首頁回 200，才往下走。

專案現在能跑了，但它還沒有任何「這個專案該怎麼寫」的規範。下一節要看 greenfield 的 /audit 如何在這裡扮演一個特別的角色——它不掃程式庫，而是用訪談把你的規範捕捉成一份短小的 AGENTS.md。
