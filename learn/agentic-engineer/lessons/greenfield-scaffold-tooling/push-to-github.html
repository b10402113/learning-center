把 scaffold 推上 GitHub

Step 5/6 · Greenfield：Scaffold、Tooling 與規範

學習目標

走完自動化的 Git（每個 feature 一個 branch 與 commit）、建立新的空 GitHub repo、加上 remote origin 並把 main 與 feature branch 推上去，理解第一顆 commit 作為乾淨 diff baseline 的用途。

前言：程式碼不進版控，等於沒有備份

到目前為止，feature 1 的架構與技術棧、feature 2 的 coding standards 與 tooling 都完成了。你的專案能跑、有規範、也有機械檢查，但它還躺在你本機。只要硬碟壞了、或是你想換一台電腦繼續，這些進度就得重來；而且沒有遠端，也沒有人能 review 你的程式碼。

這一節要把這個專案送進 GitHub。動手前你只需要一個 GitHub 帳號、以及一個已經完成前兩個 feature 的專案。整個流程其實會比你預期的自動很多——課程的示範者甚至說，他最喜歡 agentic engineering workflow 的一點，就是 Git 是「內建」處理的，他不太需要自己去想推上去這件事。

第一步：讓 workflow 自己照顧 Git

這套 workflow 的預設是替你處理 Git，而且是在你還沒開口之前就已經在背景運作。當 audit 那一步把 Git integration 設成 on 時，如果專案當時還不是一個 repo，它就會先跑 git init，讓 repo 從啟用整合的那一刻就存在。之後每個 feature 都會自動開一條對應的分支、照里程碑提交。

It's handling Git out of the box. So it's asking, should I handle Git for you as features are built? Yes, the workflow will branch and commit for us automatically.

這條規則被寫進 AGENTS.md 的一個小區塊裡，內容只有幾行設定值。後續的 /develop 讀到它，才知道要開分支、要在什麼時機提交。

**`## Git`** (from the git integration question): write the engineer's choice as a small block, e.g. `- integration: on` / `- branch prefix: feat/` / `- commit: per-milestone`, or just `- integration: off`. Absent means off. A recorded preference, not a mirrored source of truth; `/develop` reads it to branch and commit, `/document` to gate the PR.

第二步：第一顆 commit 是乾淨的比較基準

在這個時間點，專案裡還沒有任何 commit。agent 會問你要不要做第一顆提交，把 scaffold、文件、已安裝的 skills、以及新的 AGENTS.md 一起放進去。這顆 commit 的用途，課程講得比「備份」更精準：它提供一個乾淨的起點，讓之後每一個 feature 都能拿來做 diff。

So should we make that first commit with the scaffold, the dock, the installed skills, and the new agents MD, which gives us a clean starting point to diff every later feature against.

為什麼 baseline 這麼重要？因為 review 的時候，你不想在一堆與本次改動無關的檔案裡撈重點。有一顆「一開始就長這樣」的 commit，之後任何一次改動的 diff 都只包含這次真正動到的東西，你一眼就能看出這個 feature 加了什麼。這也是善用版控的基本功：先建立基準，再開始動。

第三步：每個 feature 一條自己的分支

workflow 不會讓你直接在 main 上開發。課程的 Git 規則寫得很明確：在預設分支上，它會提議開一條以 feature 命名的分支，並且「永遠不要在預設分支上建置」。

- On the default branch (`main`/`master`) → **offer to branch** (recommended): `<prefix><feature-slug>` from the scope feature name (kebab case; e.g. `feat/accounts-sign-in`). Never build on the default branch.

在示範裡，feature 2 的 coding standards tooling 因此落在自己的分支上，名稱類似 feat/coding-standards-tooling。當里程碑落地、而且該里程碑的 type check 通過時，agent 會提議為那個里程碑提交。提交訊息有固定格式——一行 Conventional Commit，加上必要的 Co-Authored-By 標註。

feat(auth): add session persistence

Co-Authored-By: Claude Opus 4.8 (1M context) <noreply@anthropic.com>

有兩件事它絕對不會自作主張。第一，它不會提交一個還沒通過 type check 的半成品；第二，push 與開 PR 屬於對外動作，一律先跟你確認，而且開 PR 是 /document 的職責，不是這裡隨手做的事。分支與 commit 是本機操作，會提議；推上遠端則要你點頭。

第四步：建一個空的 GitHub repo

本機的 commit 有了，接著要一個遠端。做法是到 github.com/new，在你自己的帳號底下建一個新的 repo。示範裡命名為 agentic-engineering-workflow-movies，你可以照自己的專案命名。關鍵是：建立時保持它是空的，不要勾選自動產生 README 或 .gitignore，否則遠端會先有一顆 commit，之後推送時還得處理衝突。

因為你的環境已經連著 GitHub，所以通常只要把 repo 的連結貼給 agent，它就知道要推到哪裡。

第五步：加上 remote 並推送兩條分支

agent 收到連結之後，會做三件事：確認目前有哪些分支（main 與 feature 分支）、加上 remote origin、然後把兩條分支都推上去。課程的紀錄裡，因為遠端 repo 是空的，所以它加完 origin 就順利推了兩條分支。

It's checking the current branches, both the main and feature branches, adding the remote origin by running the command, and then pushing the main and feature branch. Very quickly, that's done. The repo was empty, so it added the origin and pushed both branches.

對應的三個指令大致是這樣。第一行告訴本機這個遠端叫 origin，位置在哪；後兩行分別把 main 與 feature 分支推上去，並用 -u 記住 upstream，之後你在該分支直接打 git push 就會推到正確的地方。

git remote add origin https://github.com/<you>/agentic-engineering-workflow-movies.git
git push -u origin main
git push -u origin feat/coding-standards-tooling

第六步：自己開 PR、自己 merge

推上去之後，遠端會看到你的完整程式碼，以及一條額外的 feature 分支。agent 會問你要不要順手開一個 PR。示範者的選擇是「這一步我不想偷懶」，自己開、自己 merge。他的理由值得記下來：因為到目前為止，所有程式碼他都仔細看過，技術棧與 tooling 的每個決定也都參與了，所以他有信心自己 review 完直接合併。

這也點出一個常被誤解的地方：workflow 幫你把分支與 commit 自動化，不代表它幫你把 review 也省掉。自動化的部分是把重複的機械動作包好，判斷的部分——這個改動對不對、要不要合——仍然是你的事。

做完之後長什麼樣

打開 GitHub 的 repo 頁面重新載入，你應該看到完整的程式碼，而且分支列表裡除了 main 之外，還有一條這次的 feature 分支。PR 開好、review 過、merge 回 main 之後，這個專案就正式進了版控，也準備好進入下一個 feature。

小結

Git 在這套 workflow 裡是預設就開著的：audit 設成 on 時就替你 git init，之後每個 feature 自動開一條分支、在里程碑落地且 type check 通過時提交。第一顆 commit 把 scaffold、文件、已安裝的 skills 與 AGENTS.md 一起收進去，當作之後每個 feature diff 的乾淨基準。你要做的是建一個空的 GitHub repo、把連結給 agent，讓它加上 remote origin 並推送 main 與 feature 分支，然後自己開 PR、review、merge。分支與 commit 是提議，push 與 PR 一定先跟你確認。

專案進版控了，前兩個 feature 也正式收尾。但在往下一個大功能前進之前，還有兩件事會決定你的 agent 接下來表現好不好：它有沒有裝到對的 skills，以及你的對話 context 是不是還乾淨。下一節把這兩件事和資料模型的交棒一起講清楚。
