為什麼動工前要先 /scope：不決定，agent 就替你決定

Step 1/5 · /scope：動工前先挑戰想法

學習目標

看懂每個專案都默默帶著的三個預設值：功能先做哪個、每項變更要檢查到什麼程度，以及沒人決定時該怎麼辦。也要理解，為什麼你不主動決定，agent 就會在每一輪工作中替你決定。

前言：你有沒有只丟一句話就開工？

想像你打開 agent，輸入：「幫我做一個客戶回饋的 App。」它立刻開始動手：先建資料庫，再拉出幾個畫面，還順手加了一項你沒想過的功能。進度看起來很快，成果也開始出現。

但有幾個問題一路都沒人問：功能為什麼照這個順序做？做完後要檢查到什麼程度，才算完成？如果某個決定懸而未決，專案要預設往哪個方向走？你沒問，agent 也沒問；可是它每一輪都在替這些問題做選擇。

這一節要談的，就是這些「你不決定，就有人替你決定」的預設值。看懂它們，才能知道 /scope 這個 skill 要防的是什麼，也才能分清楚「有東西做出來了」和「專案走在對的軌道上」並不是同一件事。

每個專案都帶著一組預設值

課程一開始用一句話點出重點：每個專案都跑在一組預設值上。這組預設值大致有三個：

  • 功能先做哪個：也就是建置順序。誰先誰後，會影響你多快能驗證核心想法。
  • 每項變更要檢查到什麼程度：一項功能要經過多少驗證，才算「完成」。
  • 沒人決定時的答案是什麼：遇到還沒定案的選擇，專案預設採取哪個方向。

可以把這些預設值想成一間店的規矩：出菜順序、每道菜的品管標準，以及「菜單沒寫的客製需求該怎麼回」。老闆如果從沒定下規矩，店還是開得下去；只是每次都由當班店員臨場決定，而且往往會選最省事的做法。

不刻意選，它就替你選

這三個預設值不會空著等你。你不處理，它們一樣會被填上，只是做決定的人不是你。

課程的說法是：你要嘛刻意選這些預設值，要嘛它們就會被替你選掉，一個功能接著一個功能，由 agent 當下順手拿起的選項決定。 關鍵在「順手拿起」：那通常不是經過比較後的決定，而是當下最方便、最省力、最快能做出成果的選項。

所以，預設值好不好，關鍵在於「有沒有真正做過決定」，而不只是 agent 聰不聰明。Agent 很會把眼前的工作做出來，但不會自動停下來問：「這真的是你想要的順序嗎？」它只會繼續往前跑。

一個真實案例：vibe build 裡的三個「沒人決定」

課程用一段 vibe build 的過程作為對照。過程中沒有人做過幾個關鍵決定，於是出現了三種情況：

  1. 沒人決定建置順序，agent 就從自己最先想到的東西開始做。
  2. 沒人決定哪些內容不在範圍內，結果什麼都能加，功能便一路增加。
  3. 沒人決定功能需要多少證明才算完成，agent 就選了最省力的答案：不需要任何證明。

第三點尤其值得留意。當「完成」的標準沒人設定，預設值就可能一路降到最低：不是「做到剛好」，而是「什麼都不用做」。對只想把功能標記為完成的工作迴圈來說，不驗證正是最省力的路。

最容易忽略的地方：你看到時，它可能已經變成程式碼

這些預設值的危險，不只是可能選錯，而是它們常常無聲無息地生效。課程指出，這些事從未被討論，也沒有被寫下來；等你注意到時，它們可能早已成了程式碼的一部分。

也就是說，等你發現「怎麼先做了這個功能？」或「怎麼沒測過就上線了？」，那就不再只是改一個決定，而可能得拆掉已經做好的東西。這也是為什麼 /scope 要放在程式碼動工之前：在這個時間點，還來得及釐清方向，修改成本也還低。

那 /scope 到底在防什麼

把想法交給 /scope，它不會一開始就寫程式，而是先讓你面對並選定前面提到的三個預設值。最基本、也最常見的用法，是提供你手上已有的一句話：

/scope 建立一個客戶回饋 App：分享連結給客戶，客戶在即時預覽上釘選留言，我從儀表板管理。

這一行是你起步時要提供的內容。接下來的幾節會說明，/scope 如何從這句話推論出已經講清楚的部分、只針對無法推論的地方提問，最後把整組預設值整理成一份你看得懂、也能修改的計畫。

小結

每個專案都帶著一組預設值：功能先做哪個、每項變更要檢查到什麼程度，以及沒人決定時該怎麼辦。你不刻意選，agent 就會在每一輪工作中替你選，而且通常會挑當下最省事的做法。這些選擇往往沒被討論、也沒被寫下來；等你看見時，它們可能已經變成一整片程式碼。執行 /scope，就是在動工前把這些預設值講清楚，不讓它們默默替你決定。

知道預設值可能帶來什麼代價後，接下來就要看 /scope 實際怎麼運作：它會從你手上取得什麼、中間會問哪些問題，又會產出什麼檔案。下一節就把整段流程走一遍。
