跑一次 /scope：把一句話變成 docs/scope/scope.md

Step 2/5 · /scope：動工前先挑戰想法

學習目標

本節會帶你跑一次 /scope：從一句話或一份 brain dump 開始，回答分批提出的問題，最後產出 docs/scope/scope.md。你也會認得 plan、replan、add 三種模式。

前言：你手上只有一句話，然後呢？

上一節談到預設值的代價：如果你不主動決定，agent 就會替你決定。但知道「該做決定」，不代表知道「要決定哪些事」。很多人卡在這一步：手上只有模糊的想法，要先回答哪些問題？難道得把整份產品規格想好才能開始嗎？

這一節會實際跑一次 /scope。它接受的起始輸入可以很少，一句話就夠；當然，提供的資訊越多，產出的計畫通常也越好。你先說出已經知道的部分，/scope 再分辨哪些還不清楚，只追問那些問題，最後把答案整理成一份檔案。

動手前你需要什麼

開始前，準備好以下三樣東西：

  • 一個能讓 agent 工作的專案資料夾；新建的空資料夾也可以。
  • 已安裝 JSM Skills System 的資料夾，其中要有 /scope 這個 skill。你已在前面的節點安裝過。
  • 一個想法。至少用一句話說明產品要做什麼、給誰使用。

不用先寫規格、選技術，或設計資料表。這些留給後面的 /architect。

步驟一：把想法交給 /scope

在專案資料夾裡打開 agent，輸入以下內容。課程示範的想法是一款客戶回饋 App：

/scope build a client feedback app, where I share a link, the client pins
comments to a live preview, and I manage them from a dashboard.

這就是它一開始拿到的全部資訊。不過，你也可以提供更多：把腦中的想法一次倒出來（brain dump），或直接貼上客戶提供的需求簡報。提供給 /scope 的材料越多，產出的計畫就越有依據。 即使你只從一句話開始，它也會透過提問協助你把想法整理成合適的規模，無論是小工具，還是有機會發展成企業產品的服務。

步驟二：它先判斷這是哪一種專案

執行後，/scope 不會立刻寫計畫，而是先讀取幾個檔案，判斷專案類型。課程示範的是 greenfield，也就是從零開始的新專案，因此它會讀取 scope 的格式範本，再進入問答。

這裡也能看到 skill 模組的做法：它只載入當下需要的檔案，不會把整個 skill 一次全部讀進來。判斷出專案是從零開始後，它就知道要從頭規劃。

如果專案類型不同，流程也會跟著改變。對已經有程式碼的 brownfield 專案，通常會先跑 /audit，確認實際的技術棧、指令、結構與慣例，再回到 /scope 規劃新的切片。若是 monorepo，就從正在修改的 workspace 開始；計畫與規格會留在該 workspace，不會影響其他無關的應用程式。

步驟三：回答分批的決策面板

問答是整個流程的核心。問題會分批出現，每一批都提供可選的答案，並標出建議選項。這樣你不必從空白輸入框開始，獨自設計整個產品。

/scope 會先推斷能從描述中得知的資訊，只追問無法推斷的部分。課程示範的原始描述已經提到使用者、專案、預覽和留言，因此它不會再問這些，而是聚焦在描述裡還沒有答案的問題：

  • 最小可行產品（MVP）要包含什麼？這是第一個、也是最重要的問題；若不先劃出界線，功能很容易不斷增加。
  • 客戶要把留言釘在哪裡？示範選擇把網址載入 iframe，並在上面疊一層留言。
  • 沒有帳號的客戶要怎麼開啟共享專案？如果權限來自網址，又要如何避免不該開啟的人進入？示範選擇先使用不需登入的祕密連結，降低客戶操作上的阻力。
  • 現在要不要收費？示範選擇先不收費。
  • 第一批建置要包含哪些能力？這是多選題。示範勾選登入和留言圖片附件，並把 email 通知與即時更新延後。
  • 哪些跨領域的需求要從第一天就納入？示範勾選公開行銷頁與 SEO，並把錯誤監控、產品分析和無障礙延後。

每一輪最多提出四個問題，答完才會進入下一輪，直到關鍵面向都確認完畢。這些問題之所以要先問，是因為答案會改變產品本身，不該等程式寫到一半才由 agent 順手決定。

例如，客戶要怎麼開啟共享連結，不只是實作細節，而是權限設計。趁著改答案還很容易時先確認，會比等到做法已經散落在路由、資料庫、資料表和介面裡才修改，容易得多。

步驟四：選 build approach 與 workflow tier

問答後段會出現兩個由 /scope 提出建議、但必須由你決定的選項：build approach，也就是怎麼切分這份工作；以及 workflow tier，也就是每個功能要採用多嚴謹的流程。這是整個 skill 裡不會交給 agent 代答的兩項決定。這裡先記得它們會在流程中出現，後續會再分別說明。

步驟五：它把結果寫進 docs/scope/scope.md

問答完成、必要決定也都由你拍板後，/scope 才會把計畫寫入 docs/scope/scope.md。課程示範完成後，終端機回報「10 features planned, 14 deferred」，並顯示 build approach 是 tracer bullet、workflow 是 beta。

檔案上半部是專案總覽，包含 foundations、後續切片，以及各功能目前的狀態；下半部則是詳細計畫。

還有一個重要的設計：檔案裡不會列出函式庫或工具名稱。課程提到，資料模型、核心回饋迴圈等條目都沒有指定技術，因為那是 /architect 負責的架構決定，不屬於專案計畫。如此一來，計畫就不會因為更換函式庫而過期；工具可能改變，但帳號、留言、權限、預覽和儀表板仍是產品需要處理的功能。

認得三種模式：plan、replan、add

你只需要輸入 /scope，不必使用子指令。它會依照是否已有 scope、以及你有沒有提供參數，判斷目前要執行哪種模式。官方 skill 對三種模式的定義如下：

- **plan** (default): no scope yet + a product sized idea, or asking for the next slice. Full pass: ask → decompose into coarse feature sections → order + phase → write.
- **replan**: scope exists + no argument. Opens with a short where things stand readout (git branch and ahead/behind the remote, feature counts by status, and each in-progress feature's resume point) so a bare `/scope` doubles as the "where was I, what is safe to pick up" orientation, then reconciles what shipped, surfaces plan vs reality drift (code or specs with no scope row), enrolls needs surfaced during the build, reorders, and queues the next slice. The normal living rhythm, not rare: run bare `/scope` again.
- **add**: scope exists + argument names a single feature. Enroll one coarse row (intent + order + tier + Needs spec) without planning again: `/scope `.

用白話來看，三種模式分別適用於以下情境：

  • plan（預設）：還沒有 scope，但手上已有產品規模的想法。它會完整走過提問、拆分功能、排序與分階段，最後寫入檔案。
  • replan：已經有 scope，而且你只輸入空白的 /scope。它會先整理目前狀態，包括 git 分支、各狀態的功能數量，以及每個進行中功能的接續點。接著核對已完成的工作，找出計畫與實際進度的落差，把建置中出現的新需求納入計畫，再重新排序並安排下一個切片。這是日常會反覆使用的流程，不是少見的例外：完成出貨後，再跑一次空白的 /scope。
  • add：已經有 scope，並在指令後指定單一功能。它不會重新規劃整份內容，而是新增一列粗粒度的功能資訊，包含意圖、順序、tier，以及是否需要 spec。建置途中想到新功能時，可以使用這種模式。

做完長什麼樣

成功執行一次 plan 後，你會得到 docs/scope/scope.md。檔案分成兩部分：上半部是一張精簡的專案總覽，下半部則是按階段分組的功能計畫。終端機的完成訊息大致如下：

## /scope plan · build a client feedback app

**10 features planned (0 already on the scope, 14 deferred), build approach Tracer Bullet, workflow Beta.**
Next: /clear, then /architect stack & architecture
Scope written to docs/scope/scope.md.

你可以用以下條件檢查結果：檔案確實存在；上半部有總覽表，下半部有分組的功能段落；每個功能都包含一行意圖和一行 Done when:；而第一個尚未勾選的項目，就是下一步要處理的工作。至於為什麼要分階段、為什麼計畫不列工具名稱，屬於概念層面的說明；在這個步驟裡，先確認產物符合條件即可。

小結

/scope 可以從一句話或一份 brain dump 開始。它會判斷專案類型、讀取格式範本，再透過分批提問確認描述中還沒有答案的部分。你拍板 build approach 與 workflow tier 後，它會將結果寫進 docs/scope/scope.md：上半部是精簡總覽，下半部是分階段的功能計畫，而且不列出工具名稱。你只需要輸入 /scope；它會依照是否已有 scope、是否帶參數，自動判斷要執行 plan、replan 或 add。

跑完一次 plan 後，接下來要拍板的是那兩項決定。先看比較容易理解的一項：這份工作要怎麼切分。下一節會介紹 Tracer Bullet、Skateboard、Facade、Journey 四種 build approach，以及各自適合的判斷方式。
