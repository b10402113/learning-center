學習目標

本節整理 /scope 的計畫與後續 spec 檔案：區分 build 讀取的 index.md 和供人閱讀的 rationale.md、查閱各種 Status 的意義，以及辨認 Assumed 與 Superseded 兩種狀態。

前言：接下來你會一直讀這些檔案

前面四節，你已經跑過一次 /scope，也選好了 build approach 與 workflow tier。這條 workflow 會把重要內容記錄在檔案裡，而不是只留在對話中。接下來，你會經常打開 docs/scope/ 和 docs/specs/ 底下的檔案。

以下整理 spec 的檔案形式、兩種讀者、各種 Status 的意義，以及 Assumed、Superseded 兩種特殊狀態，供查閱時對照。

Spec 是什麼

spec 是放在 docs/specs/ 底下的 Markdown 檔案。它有單一檔案與目錄兩種形式，依決定的規模選擇，不依專案規模選擇：

形式適用情況範例
單一檔案（預設）多數功能的 specdocs/specs/0002-data-model.md
目錄（重的 spec）基礎性、之後每個功能都會讀到的決定docs/specs/0001-stack/，內含 index.md 與 rationale.md

課程建議以單一檔案作為預設形式。示範中的 stack 決定屬於基礎性決定，每個未來的功能都會讀取，因此使用目錄；多數功能 spec 不需要採用這種形式。

目錄形式的 spec 採用以下命名規則：編號放在目錄名稱上，目錄裡最上層的主檔固定叫 index.md。例如使用 0001-stack/index.md，而不是 0001-stack/0001-stack.md。

docs/specs/
  0001-stack/
    index.md        # 決定本身，/develop 讀這個
    rationale.md    # 論證與理由，/develop 會跳過
  0002-data-model.md  # 多數功能的 spec 就是這種單一檔案

兩種讀者：index 給 build，rationale 給你

目錄形式的 spec 分成兩份文件，分別提供建置時需要的決定，以及決定背後的論證。

index.md（/develop 讀取）rationale.md（/develop 跳過）
內容決定本身與限制條件決定背後的理由與證據
讀者build 的 agent人類讀者，包括日後回頭檢視架構的人
讀取時機每次動手建置時檢視或挑戰決定時

理由保留在 spec 旁邊，不會隨每次 build 一起讀取。實作 agent 讀取決定與限制條件，不必每次新增路由時都重新讀取當初的論證。

這項分工可概括為：推理時載入理由，建置時載入決定。這種拆分用於重的 spec；小決定的理由若只有兩行，拆成兩份文件的成本可能高於省下的成本。

Status：兩種生命週期

每份 spec 都有一行 **Status**。依 spec 類型不同，Status 的生命週期也不同：

spec 類型ProposedIn ProgressAccepted
綁定某個 scope 功能的 spec/architect 寫下時/develop 開始建置時功能建好並驗證後，由 /develop 推進
獨立的決定 spec（沒有對應的功能列）寫下時不適用批准時；/develop 不會推進這個狀態
補記已出貨工作的 spec不適用不適用建立時即為 Accepted

對綁定功能的 spec，Accepted 代表「已出貨」，不是「已批准」；這個狀態由 /develop 在功能建好並驗證後推進。對獨立決定的 spec，Accepted 代表決定已獲批准，/develop 不會再更新它。用來補記早已出貨工作的 spec，建立時即為 Accepted。

**Status:** Accepted   # 綁功能的 spec：代表已出貨
**Status:** Proposed   # 獨立決定 spec：代表已寫下、待批准
**Status:** Assumed    # 建置中途先擱著的決定，等待回頭批准

Assumed specs

/develop 在建置途中遇到尚未決定的事項，而流程選擇先繼續時，會寫下一份 Assumed spec。這類 spec 包含四節：

  • Owed decision：尚待決定的事項。
  • Assumption built on：目前採用的假設。
  • Code area：受影響的程式碼區域。
  • Requirements：這次建置的需求。

這份 spec 也會記錄 git 作者。若要清除 Assumed 狀態，需在該決定上執行一次 /architect。如果原先的假設成立，/architect 會補上正式內容並清除旗標；如果假設不成立，則會建立修正後的 spec，將原本的 spec 標為 Superseded，並指出該功能必須依修正內容重建才能完成。

Assumed spec 不會阻擋 done。它會保留為尚待批准的決策紀錄；在正式決定完成前，不能宣稱相關工作已完成。

Superseded：決定是被換掉，不是被改掉

決定被推翻時，舊 spec 不會被改寫，而會標記為 Superseded by [NNNN]，並附上連往取代它的新 spec 的連結。

**Status:** Superseded by [0007]   # 舊決定保留，連向取代它的新 spec

舊 spec 的理由仍可讀取。日後檢視時，文件會保留當初的決定，以及後來取代它的 spec。

小結

spec 是 docs/specs/ 底下的 Markdown 檔案，預設採用單一檔案；基礎性的重決定可使用目錄，內含 index.md（build 讀取的決定）與 rationale.md（保留理由與證據）。綁定功能的 spec 由 /architect 寫成 Proposed，再由 /develop 推進到 In Progress 與 Accepted；此處的 Accepted 代表已出貨。獨立決定 spec 在獲批准時即為 Accepted。建置途中暫時擱置的決定記為 Assumed，包含待決事項、假設、程式碼區域與需求；它不會阻擋 done，但需執行 /architect 才能清除。決定被推翻時，舊 spec 保留原文，標記為 Superseded 並連向取代它的新 spec。

需要查閱流程細節時，可回到本節點的第一步查看預設值，第二步查看實際流程，第三步查看四種 build approach，第四步查看四個 workflow tier。讀懂計畫與 spec 後，下一步是把第一個決定交給 /architect。
