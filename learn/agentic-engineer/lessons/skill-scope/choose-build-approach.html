選 build approach：Tracer Bullet、Skateboard、Facade 還是 Journey？

Step 3/5 · /scope：動工前先挑戰想法

學習目標

用「這個想法最大的風險是什麼？」當判準，在 Tracer Bullet、Skateboard、Facade、Journey 四種 build approach 之間，選出此刻最適合的切法。

前言：先切哪一刀，決定你多快知道行不行

上一節跑完 /scope，問答進入後段時，你會遇到一個會改變整份計畫的決定：這項工作要怎麼切？

產品裡有很多東西可以做，但不可能同時全部完成。先做哪一塊，也代表你先押注哪一種風險。切錯了，可能花兩週把不重要的部分做得很完整，卻還沒碰到真正可能讓產品不成立的問題。切對了，就能盡快知道「這東西到底行不行」。

四種 build approach 提供四種切法。沒有哪一種比較高級，差別在於你想先排除哪一種風險。

選項比較：四種切法

先看課程對四種切法的簡要說明：

Approach一句話適合優先處理的風險第一刀長什麼樣
Tracer Bullet用一條細線穿過整個系統，從頭到尾都真的能動系統各層接不起來，無法整合一條範圍很窄、但每一層都實際接通的使用者路徑
Skateboard做出整個產品最小、但真的能用的版本根本沒有人需要這個產品小到不能再小，卻能上線給人使用的完整產品
Journey先完成一整條使用者旅程，再開始下一條體驗不完整，每條路徑都只做到一半完整收尾一條主旅程，包括邊界、空狀態、錯誤與確認
Facade先用假資料把畫面做出來需要先讓人看到、測試並認可體驗，才值得投入後端關鍵畫面都能點、能操作，但底層使用假資料

課程示範的客戶回饋 App，/scope 推薦使用 Tracer Bullet：先用一條細線貫通整個系統。它不急著完成每個畫面、每種留言狀態或儀表板上的所有工具，而是先端到端驗證產品最核心的承諾：客戶打開連結、看到即時預覽、釘上一則留言，而那則留言會出現在你的儀表板上。

這條路徑雖然窄，卻是完整而真實的。課程也提醒，Tracer Bullet 是《The Pragmatic Programmer》推廣的軟體工程方法，目的是用一條細小的端到端切片測試架構、取得早期回饋並降低風險。

Skateboard 不只是做出一條可行的路徑，而是做出一個能實際使用的完整產品，只是規模很小。如果你最擔心的是「做了半天，結果根本沒人想用」，這種切法能最快把產品交到真人手上，驗證是否有人願意使用。

Journey 則是一條路徑一條路徑地完成。如果你最擔心的是「每條路都只做一點，體驗始終不完整」，就先把一條主旅程收好：邊界狀態、錯誤狀態都要納入，完成後再開始下一條。

Facade 刻意先假後真：先用假資料做出所有關鍵畫面，讓人能點、能操作，也能先看見和測試整體體驗；等體驗獲得認可後，再接上後端。課程特別提醒，Facade 做出來的是原型，不是正式產品，這點要說清楚。

判別問句：問「最大的風險是什麼」

四種切法都有適用的時機，不能只憑喜好選。課程的判準是：/scope 會根據藏在想法裡的風險，推薦 build approach。你可以把它化成一個自問句：

如果這個產品最後失敗，最可能是在哪裡出問題？

接著對照答案：

  • 最可能是「各部分接不起來，核心互動跑不通」→ Tracer Bullet。
  • 最可能是「其實沒有人需要它」→ Skateboard。
  • 最可能是「體驗不完整，每條路徑都只做到一半」→ Journey。
  • 最可能是「體驗還沒驗證，就先投入資源做後端」→ Facade。

回到示範中的 App，最大的風險是「核心互動本身」：使用者釘選的留言，能不能從 iframe 裡的頁面一路傳到儀表板。課程說得很直接：如果這個互動不成立，產品其他部分幾乎都不重要了。

因此，/scope 推薦先用一條細線打通這段來回，盡早排除最大的不確定性。這就是 Tracer Bullet。

還有一條方便記的預設規則：正式的生產級產品，預設採用 Tracer Bullet，除非目標明確要求另一種切法。要快速驗證核心迴圈，就選 Skateboard；如果體驗與漏斗本身就是產品，就選 Journey；只想先做出能操作的快速原型，就選 Facade。

反例：規則什麼時候會翻轉

這些判準不是固定配對，有幾種情況需要特別留意。

第一，四種切法都可能適合，關鍵是你現在要排除哪一種風險。課程明確指出：「All four can be right.」不要問「哪一種最好」，而要問「現在最該先排除哪個不確定性」。同一個產品在需求尚未驗證時，可能適合 Skateboard；等需求確定、開始整合真實系統時，也可能改用 Tracer Bullet。

第二，Journey 和 Facade 都跟體驗有關，但完成的東西不同。Journey 做的是正式產品等級的一條完整路徑；Facade 做的是使用假資料的原型畫面。如果目的是先給人看、取得回饋，之後再重做，那是 Facade；如果這條路徑現在就必須真的能用，那是 Journey。

第三，專案可以有預設，個別功能也可以覆寫。課程示範中，整個專案採用 Tracer Bullet；但如果某項功能明顯適合另一種切法，可以加上自己的標籤，例如 · Facade，覆寫專案預設。沒有標籤的功能則沿用預設。這和下一節的 workflow tier 使用相同概念，先記住這個關係即可。

最後，approach 決定「怎麼切」，不決定「用什麼工具」。這四種切法都沒有指定函式庫、框架或主機。工具選擇是 /architect 的工作；先在這裡決定切法，計畫就不會因為更換工具而失效。

決定結果會寫在 scope 檔的標頭，格式如下：

**Build approach:** Tracer Bullet (one thin path through the complete system).

小結

四種 build approach 對應四種風險：擔心系統接不起來，用 Tracer Bullet；擔心沒人需要，用 Skateboard；擔心路徑不完整，用 Journey；要先驗證體驗再投入後端，用 Facade。正式生產級產品預設採用 Tracer Bullet，除非目標明確要求其他切法。選擇時先問「產品最可能在哪裡失敗？」；同一個專案也可以讓個別功能覆寫預設。Build approach 決定怎麼切，不決定用什麼工具。

動手前，先用這張檢查表確認選擇：

  • 先找出最大的風險，再選切法；不要先挑自己喜歡的方式。
  • 如果沒有明確理由換一種切法，正式生產級產品就先用 Tracer Bullet。
  • 確認沒有混淆：Journey 是正式等級的完整路徑，Facade 是使用假資料的原型畫面。
  • 只有個別功能明顯適合不同切法時，才加標籤覆寫專案預設。
