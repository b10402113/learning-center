選 workflow tier：Prototype／Alpha／Beta／GA

Step 4/5 · /scope：動工前先挑戰想法

學習目標

根據「這東西是什麼、出錯會有多嚴重」，替專案選擇合適的 workflow tier（Prototype／Alpha／Beta／GA），並掌握專案預設與單一功能覆寫之間的關係，例如用 · GA 標籤調整某個功能的等級。

前言：要多嚴謹，還是要多快？

上一節決定了工作要怎麼切。這一節要決定另一件事：每個功能要經過多少流程驗證。這是 /scope 裡唯二必須由你做決定、不能交給 agent 代答的事。

速度和穩定性正在拔河：想快一點，就少做驗證；想穩一點，就多做驗證。但「多」或「少」不能只靠感覺，因為這個選擇會一路影響後續每個指令。選得太輕，重要功能可能沒測就上線；選得太重，用完就丟的實驗也得跑完整套審查，時間全花在流程上。這一節要幫你找出適合的力道。

這顆旋鈕在調什麼

workflow tier 就像一顆調整流程嚴謹程度的旋鈕，共有四個等級。專案會先設定一個預設等級，個別功能則可以覆寫。官方 skill 的定義如下：

Workflow tier (one rigor dial per feature, `Prototype` · `Alpha` · `Beta` · `GA`): how much process a feature warrants. ONE project default (recommended once, plan Step 5b, recorded on the scope header `**Workflow:**` line) and a per feature override (a tag beside the heading, e.g. `· GA`, only when a feature differs from the default; no tag = inherit). What the tier drives:
- **Design time**: higher tier → more likely `Needs spec: yes`, and the spec's cross model decision critic runs (auto at `GA`/`Beta`). `Prototype`/`Alpha` features are often `Needs spec: no`.
- **After `/develop`** (the verification tail): `Prototype` = nothing (rely on `/develop`'s own build time self check); `Alpha` = `/check verify`; `Beta` = `/check verify` + `/test`; `GA` = adds a fresh model `/check review` + `/document`.
- **What closes `done`** (the last required stage marks it): `Prototype` → `/develop` (build + self check); `Alpha` → `/check verify`; `Beta`/`GA` → `/test`. An `Assumed` spec never blocks `done`; it stays flagged as owing ratification (`/architect`) at every tier.

這段定義很長，先記住最重要的一點：tier 決定的是 /develop 之後還要跑哪些流程。它不會改變前面是否需要做架構決定。功能若有關鍵決定要處理，無論選哪個等級，都要先跑 /architect，或至少記下一筆 assumed 的決定。

選項比較：四個等級

把原文整理成表格，四個等級的差異就容易比較了：

Tier/develop 之後跑什麼什麼算完成（done）適合什麼
Prototype不再跑其他流程，只靠 /develop 自己的檢查/develop 完成就算用完就丟的原型、實驗、個人專案
Alpha/check verify/check verify 通過低風險功能、想經過驗證的內部工具
Beta先跑 /check verify，再跑 /test/test 通過大多數正式產品
GA再加上使用另一個模型的 /check review，最後跑 /document/test 通過金流、登入、PII、法遵、受監管的功能，或需要團隊協作的專案

課程示範的客戶回饋 App，最後選了 Beta。一般正式產品用這個等級，會先確認功能在真實 App 中能正常使用，再替重要部分補上測試。課程沒有推薦 GA，因為這個產品沒有金流、法規要求，也沒有其他大型系統；如果之後加入收費或登入功能，就該重新檢視預設等級。

相反地，如果只是快速做個原型，用完就不打算保留，選 Prototype 就好：少跑一些流程，換取更快的速度。每個等級都是在時間與驗證、審查之間取捨，沒有不花時間又能增加嚴謹度的捷徑。

判別問句：問「這東西是什麼」

/scope 選 tier 時，重點不是問「想不想做得嚴謹」，而是問「這東西是什麼」。功能的性質，會決定它承受得起多少風險。你可以先問自己：

如果這個功能有 bug，而且沒被發現就上線，會發生什麼事？

接著對照以下情況：

  • 反正會丟掉，或只有自己在用 → Prototype。
  • 低風險產品，或想經過驗證但出錯不致命的內部工具 → Alpha。
  • 要交給真實使用者使用的一般產品 → Beta。
  • 牽涉金流、登入、個資、法遵、受監管，或要交給團隊長期維護 → GA。

出錯後越容易承受，越適合輕一點的等級；出事代價越高，就越該往嚴謹的等級選。課程給的判斷方向也是如此：用完就丟的原型、實驗和個人專案選 Prototype；低風險產品或想經過驗證的內部工具選 Alpha；一般正式產品選 Beta；金流、登入、PII、法規、受監管或團隊協作則選 GA。

專案預設與單一功能覆寫

選好的等級會寫在 scope 檔標頭，作為整個專案的預設。示範 App 的標頭會像這樣：

**Workflow:** Beta (check verify, then test). The project default level of rigor.

不過，專案預設不代表每個功能都得一視同仁。當某個功能明顯比專案其他部分更需要、或更不需要嚴謹時，可以在功能標題旁加標籤覆寫，例如 · GA 或 · Prototype。沒有標籤的功能就沿用專案預設。這和上一節的 build approach 覆寫方式相同：有標籤就照標籤，沒有就繼承預設；只有確實不同時才需要加標籤。

課程特別提醒，選定專案 tier 不代表每個功能都得用同一等級。簡單的功能可以用 Prototype 或 Alpha 的流程；特別重要的功能，則可以用出貨等級的標準對待。這個設定的用途，就是建議每個功能完成 /develop 後還要跑哪些流程。

反例：哪些情況會讓判斷翻轉

第一個常見誤會，是把 tier 當成是否需要架構決定的開關。選了輕量等級，不代表可以跳過 /architect。tier 只管 /develop 之後的流程，不會取消架構決定這道門檻。任何有重要架構決定的功能，無論等級如何，都要先跑 /architect，或至少記下 assumed 的決定。輕量功能比較少需要自己的 spec，不等於架構門檻消失了。

第二個要留意的是，專案預設不是永久判決。它只是目前的初步判斷，專案性質改變時就可以重新檢視。課程舉例，如果專案之後加入金流或登入，就應重新評估預設等級，別把標頭上的設定當成刻在石頭上的規則。

第三個情況，是原本以為「沒被測到也沒關係」，後來才發現功能一出錯就會牽動很多地方。這時就該替它升級，而不是硬套專案預設。反過來說，即使專案預設是 GA，某個確實無關緊要的小功能也可以標上 · Prototype，降低它的流程要求。

小結

workflow tier 是調整每個功能流程嚴謹程度的旋鈕，決定 /develop 之後還要跑什麼：Prototype 不再跑其他流程；Alpha 跑 /check verify；Beta 再補 /test；GA 則加上使用另一個模型的 /check review 與 /document。選擇時，先問「這東西是什麼、出錯代價有多高」：會丟掉的用 Prototype，低風險或內部工具用 Alpha，一般產品用 Beta，金流、登入、個資、法遵或團隊維護用 GA。專案有一個寫在標頭的預設，單一功能可以用 · GA 這類標籤覆寫。無論選哪個 tier，都不能因此跳過 /architect 的架構門檻。

動手前，照這張檢查表確認一次：

  • 先問「這東西出錯會有多大代價」，再選等級，不要只挑自己喜歡的。
  • 不確定時先用專案預設；一般正式產品預設為 Beta。
  • 只有某個功能確實需要更嚴或更鬆的流程時，才加標籤覆寫。
  • 記住 tier 只管 /develop 之後的流程，架構門檻始終存在。

定好 build approach 和 workflow tier，/scope 的產出就完成了。下一節會帶你讀懂這些產出：計畫要怎麼看，以及後續的 spec 檔如何區分「給 build 流程讀的部分」和「留給你讀的部分」。
