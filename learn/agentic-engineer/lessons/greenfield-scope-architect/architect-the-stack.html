跑 /architect：把 stack 決定寫成 spec

Step 3/6 · Greenfield：Scope 與架構技術棧

學習目標

跑 /architect stack and architecture，走完多輪帶建議選項的決策訪談（需要時並行 web 查證），把 load-bearing 的 stack 決定寫成一份帶 index 與 rationale 的 spec，並知道它不產 build plan。

前言：地基要先定，才輪到牆

上一節你替專案選好了切法。以電影 App 為例，這個 build 一共有 11 個部分，排在第一位的就是「stack 與架構」。它為什麼非要第一個做？因為後面每一個 slice 都會站在這層決定上：資料模型用哪個資料庫、UI 用哪個框架、背景工作跑在哪裡。這些一旦選錯，要改就得把上面全部拆掉。

這一節的目標很具體：跑一次 /architect，讓它用多輪問答把決定收齊，最後寫出一份你以後可以當成 source of truth 的 spec。動手前的前置條件只有一個——上一節的 scope.md 已經在磁碟上，因為 /architect 要靠讀 scope 才知道你在做什麼產品。

第一步：開新 session，指定一件事

先回到你的 Claude Code，開一個新的視窗，然後指定要架構的東西：

/architect stack and architecture

只給它一件事，是這個 skill 的設計原則：一輪處理一個 load-bearing 的決定。啟動後它會先讀過 scope，並讀一份設計對話檔，確認這個專案是不是已經有一個 design system、還是不是需要新建。示範裡的資料夾目前只有一個無關的 demo，所以它把這當成一個單純的架構決定來處理，接著開始問你問題。

第二步：references 同意閘——綠地專案建議開 web 查證

第一組問題跟 scope 那時一樣，是問要不要 references。但綠地的 stack 決定多了一層意義：如果你選擇包含 web，這個選項會同時查詢目前的工具生態，讓選項不會過時。原文這樣描述這個選項的差別：

Sources plus web verified links (fetches pages to confirm the links, costs some extra tokens) → sources+links (for a greenfield stack decision this also runs the current landscape check)

課程強烈建議在綠地專案打開它，理由有兩個。第一，綠地的 stack 選擇是最快過時的東西；第二，agent 的知識有截止日（knowledge cutoff）。多花的 token 換來的，是它會去查最新的版本與實務建議，而不是憑記憶推薦。示範裡它就並行開了幾組搜尋，例如「Drizzle 還是 Prisma，在 Next.js production 下怎麼選」、「Neon 還是 Supabase Postgres」、「pgvector 的 serverless 方案」，以及「Vercel AI SDK 做語意搜尋」。

這些網頁查詢是由唯讀的 sub-agent 去做的：它只讀不寫，讀到的頁面不會灌進你的主對話，你只會收到精簡的摘要。來源連結會保留在 spec 的 references 裡，日後回來查得到。

第三步：一題一個決定，收齊 load-bearing 的選擇

接下來是整場訪談的主體。它會分成好幾輪，一題一個決定地問你。每一題的做法都一樣：列出當下真的可行的選項，恰好一個標記為建議選項並附一句理由，最後保留自由輸入讓你覆寫。它不會把整包決定丟給你一次接受或修改，而是逐題組裝。

示範裡最後定案的 stack 決定，大致長這樣。你可以把這張表當成「一份 stack spec 大概要回答哪些問題」的樣板：

面向示範的決定
這個 build 是做什麼的課程示範、要在鏡頭前教，但我仍要它是真的能上線、有人能用的產品
預期規模數百到低數千名使用者
App 形狀單一 fullstack Next.js app（Next.js 16 app router + TypeScript）
資料庫Supabase Postgres（一般資料表 + pgvector + 檔案上傳）
ORMDrizzle（在 TS 新專案上已超越 Prisma）
AuthSupabase Auth
LLM 呼叫Vercel AI SDK（provider-agnostic）；較難的 vibe query 用 Sonnet 5，短的推薦理由用 Haiku
相似度每部電影從 synopsis、genres、crew 各 embed 一次，向量存在電影那一列旁邊，用 HNSW index 找鄰居；vibe search 就是把查詢 embed 後跑同一個搜尋
HostVercel
背景工作Inngest（免費方案足以支撐規模；匯入的可靠性是 demo 與產品的分界）
CSV 上傳Supabase storage
快取Postgres 當快取，加上 Next.js 的快取
樣式Tailwind v4 + shadcn/ui；整個專案用單一 app、PNPM
驗證與測試Zod 做驗證；Vitest + Playwright 做測試
授權server actions 當閘門，RLS 當第二道防線
配額Postgres 裡一張 per-user usage table，記錄每個帳號每天的使用量
環境變數用 Zod 在啟動時驗證
電影資料來源TMDB（免費、有 synopsis／genres／cast／crew／海報，Letterboxd 匯出可轉成 TMDB ID）
Embedding 模型OpenAI Text Embeddings 3 Small（Anthropic 沒有 embedding 模型，所以這一定是第二個供應商）

注意兩件事。第一，像「配額」這種題目，看起來跟「選 stack」無關，但如果你不決定，build 就會自己替你發明一個。這些「不決定就會被默默猜掉」的小題，正是這個流程在保護你的地方。第二，課程特別點出 embedding 這題：因為 Anthropic 不提供 embedding 模型，向量這一側無論如何都得引入第二個供應商，而 AI SDK 讓這件事變成換一行的事。

課程也趁這一段反覆對比 vibe coding：如果只是讓模型自由發揮，上面這張表每一個選擇都會被它替你決定。而這裡，決定權留在你手上，這才叫做工程架構師，而不是只是寫 prompt。

第四步：它寫出 spec，而且刻意不寫 build plan

所有承重決定收齊後，/architect 會寫出一份 spec 當作 source of truth。這份 spec 通常是目錄形式，第一個檔案是 index.md，裡頭帶著 summary、decision、proposed stack、consequences 與 follow-up：

docs/specs/NNNN-/
  index.md      → Summary / Decision / Proposed stack / Consequences / Follow-up
  rationale.md  → 前提說明 + 四個完整 stack 選項，各有 real cons、rationale 與 web-verified references</pre>

<p>如果是一個單檔 spec（非目錄形式），它的檔名規則則是：</p>

<pre data-source="sources/agentic-engineer/20261014/skills/skills/architect/spec-template.md">File path: `docs/specs/NNNN-kebab-case-title.md`</pre>

<p>寫完之後它會跑一個完成度檢查，確認 <code>index.md</code> 真的帶了那五個部分。這裡有一個很容易看漏、但很重要的設計：<strong>這份 spec 沒有 build plan，也沒有自己發明的 acceptance criteria。</strong>因為這是一份「決定規格」，而 scaffold 的步驟屬於 <code>/develop</code>。如果你在這一步就要求它生出 build plan，其實是把兩件事混在一起了。</p>

<figure class="lesson-figure"><img src="./architect-the-stack-assets/image-3.png" alt=""><figcaption>AI 生成示意圖</figcaption></figure>
<p>示範裡還附帶更新了 scope：原本寫著「跑 architect 與 stack」，跑完後變成「依產生的 spec 去 develop、verify、test」。scope 的架構規則也會跟著補上，例如「應用程式是使用者資料的唯一閘門」、「任何可能超過幾秒的事都不放在 request 裡，而是丟給 Inngest function」。這些規則之後會被其他功能讀到。</p>

<h2>做完長什麼樣</h2>
<p>這一步結束後，可以驗證三件事：<code>docs/specs/</code> 底下多了一份 spec（<code>index.md</code> 帶 summary／decision／proposed stack／consequences／follow-up，<code>rationale.md</code> 帶四個選項與 web 驗證過的來源）；scope 裡對應的功能狀態已更新；終端機最後會顯示一句簡短收尾摘要，說明決定了什麼、理由是什麼、下一步該跑哪個 skill。原理的部分——spec 的形狀與狀態怎麼流動——留到別的節點講；這一節的目標是把這一輪跑對。</p>

<h2>小結</h2>
<blockquote>
<p><code>/architect stack and architecture</code> 是 11 個 build 部分的第一個，也是地基。它先讀 scope，再問 references（綠地建議開 web 查證，因為 stack 最快過時、agent 知識有 cutoff），接著用多輪「一題一個決定、各附一個建議選項」的訪談收齊 stack 的承重選擇，最後寫出目錄形式的 spec：<code>index.md</code> 帶 summary／decision／proposed stack／consequences／follow-up，<code>rationale.md</code> 帶四個完整選項與來源。它刻意不產 build plan，因為 scaffold 屬於 <code>/develop</code>。</p>
</blockquote>
<p>stack 定案之後，還有一個問題：這些工具要怎麼讓 agent 用對？下一步要依你選的 stack，把對應的 agent skills 與 MCP servers 接上，讓 build 跟著真實慣例走，也能直接檢查真實系統。</p>
