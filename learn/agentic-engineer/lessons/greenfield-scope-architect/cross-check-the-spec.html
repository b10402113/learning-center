用第二個模型 cross-check spec

Step 5/6 · Greenfield：Scope 與架構技術棧

學習目標

用第二個模型 cross-check 基礎 spec 的 decision completeness，判斷哪些 finding 值得接受，並只在批准後套用修正。

前言：寫的人，看不見自己的盲點

stack spec 寫完了，你可能覺得該決定的都決定了。可是寫下這些決定的人和檢查這些決定的人，如果可以共用同一套假設，那他就檢查不出什麼。同一個模型讀自己剛寫的東西，傾向讀到「我打算寫的」，而不是「我實際寫的」。這不是模型特別笨，人類也一樣。

所以在正式開工之前，這套 workflow 會問你一個問題：要不要用另一個模型來 cross-check 這份 spec？這一節要讓你能判斷什麼時候該做、第二個模型到底在找什麼，以及面對它提出的 findings 時，怎麼決定要接受哪些。

這是一個什麼樣的決定

張力很單純：做 cross-check 要多花一些時間與 token，但可能抓到一個你自己看不到的地基錯誤；不做則省下這些成本，換一個「先相信這份 spec」的風險。關鍵在於這份 spec 是不是地基——如果不是，錯一點之後再補就好；如果是，那它下面的東西全部會繼承這個錯。

做與不做的比較

選擇換到什麼付出什麼適合的情況
不做 cross-check省時間、省 token，維持節奏地基錯誤會傳染給後面所有功能規格已被充分驗證、影響範圍有限
用第二個模型做抓到作者盲點、補上會自己長出來的決定多一趟讀取與檢視的時間這份 spec 是地基，很多東西建在它上面

課程示範裡的判斷是「強烈建議做」。理由有兩層。第一，architecture 是整個應用程式的架構，一個地基錯誤會被後面 11 個功能全部繼承。第二，這是一個 medium-tier 的 feature，而第二個模型能看見寫的人看不見的東西。它回來時留下了一個很直接的評語：目前還不足以安全地在上面建 11 個功能。

第二個模型到底在檢查什麼

它不是來重寫 spec，也不是來挑錯字。它的主要工作是 decision completeness：找出那些如果現在不定，build 就會自己發明的決定。換句話說，它檢查的不是「這段文字寫得好不好」，而是「這裡有沒有一個被默默跳過的承重決定」。

示範裡的做法是：同一個 agent，但用另一個模型，去讀剛剛寫好的 spec。這趟只花了約 17 秒。回來之後，它給了六個 findings，其中兩個是真正的 production gap——而且都落在 spec 聲稱「不是選配、是保證」的地方。

六個 findings，哪些是真錯、哪些只是補細節

這六個 finding 本身很值得一看，因為它們示範了「什麼叫做改變推理」與「什麼只是補細節」的差別：

#Finding性質
1RLS backstop 根本不會運作：Supabase policy 靠 auth.uid() 讀一個由 Supabase client 每請求設定的 JWT claim，但 Drizzle 直連不會設，於是 auth.uid() 是 null，policy 形同虛設真正的錯誤，不是 nitpick
2pooling 規則只寫了一半：Supabase 的 transaction pooler 不支援 server-side prepared statements，而 Postgres driver 預設會 prepare，併發時丟出「prepared statement already exists」，而且本機重現不出來改變推理
3session wiring 被聲稱，卻從未指名怎麼接缺一項指名
4Supabase 內建的 email sender 不是 production-grade（預設有速率限制、官方明說不適合 production），而這正是原本選 Supabase Auth 的理由之一，理由被過度宣稱了改變推理
5Inngest 的資料庫連線從未被處理缺一項決定
6vector 的距離度量沒有指名（minor）補細節

findings 1 和 4 為什麼特別重要？因為它們改變的是推理本身，而不是多補一段說明。以第 1 個為例，它連帶改變了整個安全模型：修法是保留 RLS 開啟，但改成 deny-by-default 的 policy——公開的 anon key 什麼都讀不到，應用程式一律走 server-side 連線。這樣一來，一份外洩的 public key（它本來就會出現在每一個瀏覽器裡）就變得無害，而 spec 也誠實承認：應用程式才是使用者資料的唯一閘門。以第 2 個為例，修法是在 driver 上設定：

// 讓 Postgres driver 不要使用 server-side prepared statements
prepare: false

這設定本身只有一行，但如果沒寫進去，就會在併發量上來時炸掉，而且你在本機永遠測不出來。第 4 個的修法也類似：不是換掉 Supabase Auth（換成 Better Auth 也一樣需要 email 供應商），而是更正理由，並把 custom SMTP（例如 Resend）加成一列 stack 決定。

怎麼問自己：哪些 finding 該接受

面對一整排 findings，你可以依序問這幾個問題，來決定要不要套用：

  1. 這個 finding 改變推理，還是只補細節？改變推理的（像 RLS、email sender）要認真對待，因為它會連動其他決定。
  2. 它是不是落在「spec 聲稱是保證」的地方？是的話，這就是真錯，不是建議。
  3. 在我目前這個階段、這個規模下，它會發生嗎？例如池化問題在高併發才炸，但既然規模設定到低數千，它就值得現在處理，因為本機測不到、上線才痛。
  4. 我接不接受？每一個 finding 都是 load-bearing 的決定，所以在你看過、同意之前，它不會自動套用。

反例：什麼時候不必照單全收

「第二個模型說的都對」是一種危險的預設。課程在這裡特別強調套用要經過批准，因為 findings 也是由模型生成的，一樣可能有誤或過度反應。幾種要小心的情況：

  • 它可能只是換一種寫法，而不是真的缺口。如果一項 finding 只是把你已經說清楚的事換句話說，那不值得動 spec。
  • 它可能超出你目前的階段。某個「缺口」也許在你的規模或 tier 下根本不成立；把它寫進 spec 反而讓地基背了一堆用不到的複雜度。
  • 你不必一次全收。它提供的選項包含「逐一走完六個」「只套最重要的前兩個」或「全部套用」。示範裡講者同意全部六個，但那是因為他逐一看過、也同意理由，而不是因為預設要全收。

小結

Cross-check 用另一個模型檢查同一份 spec，主要找的是 decision completeness——那些 build 會自己發明的決定。判準是：這份 spec 是不是地基、有多少東西建在上面。示範因為它是整個應用的架構、又會影響 11 個功能，所以強烈建議做。第二個模型 17 秒回來，給了六個 findings，其中兩個（RLS、email sender）改變推理，是真錯而非 nitpick。每一個 finding 都是 load-bearing，因此只在你看過並批准後才套用；你可以逐一決定，不必照單全收。

到這裡，地基相關的決定都收斂了：spec 寫好、cross-check 過。接下來要做的，是把這一長串對話收乾淨，讓下一個階段的 agent 從檔案開始，而不是從聊天紀錄開始。
