接上 agent skills 與 MCP servers

Step 4/6 · Greenfield：Scope 與架構技術棧

學習目標

從選定的 stack 比對出要安裝的 agent skills 與 MCP servers，看得懂風險等級與 consent 閘門，並用 npx skills@latest add 與 claude mcp add 把它們接上。

前言：stack 定了，agent 怎麼知道正確做法

上一節你把 stack 決定寫成 spec。可是隔天 agent 開始動工時，它未必「知道」Supabase 的 RLS 怎麼設、Tailwind v4 的 class 怎麼寫、Drizzle 的慣例長什麼樣。如果你不給它依據，它就會憑訓練資料裡的平均值去猜，而平均值往往不是你的版本的正確做法。

這就是 agent skills 與 MCP servers 存在的理由。前者教 agent 某項工具的真實慣例，後者讓 agent 直接連到真實系統、親自看一眼，而不是靠假設。這一節要做的，就是把你的 stack 拿去比對出該裝哪些，接上，並且看懂它標的風險等級。

第一步：讓 workflow 用你的 stack 去比對

stack 確定之後，這套 workflow 會主動提出：要不要幫你找出正好對應這個 stack 的 agent skills 與 MCP servers。示範裡的 stack 是 Next.js、Supabase、Drizzle、Tailwind、shadcn/ui、AI SDK、Inngest、Zod、Playwright、Vercel，它就會拿這串去比對。

這裡有一條貫穿整個 workflow 的核心規則：詢問是必要的，搜尋不是。在你明確同意之前，它不會去搜尋、抓取或安裝任何東西。這道同意閘門不是形式，因為安裝 skill 等於允許 agent 依據新的指令行動，而接上 MCP 等於給它一條通往真實系統的通道。

它建議了哪些

示範跑完比對後，提出了一組核心 skills 與三個 MCP servers。你可以把這個清單當成「一份 stack 對應的工具地圖」的例子：

  • 核心 skills：Supabase 的 agent skills 加上 Postgres best practices（課程標為 must-have，因為很多安裝說明由 Supabase 自己維護）；Vercel React best practices、shadcn/ui、Vercel AI SDK。
  • 支援性 skills：Inngest 如何設定與執行 durable functions；Playwright CLI 用來寫與跑瀏覽器測試；Tailwind v4 docs；Drizzle patterns（社群維護，體積小，示範認為可能不必裝）。
  • MCP servers：Supabase（價值最高，可以即時檢查資料庫）、Vercel（追蹤部署狀態與 build log）、Playwright（讓 agent 真的驅動一個瀏覽器）。

兩個 MCP 在這條 workflow 裡的角色特別清楚：Supabase MCP 讓 agent 之後在設計資料模型時，能對著真實的 schema 設計，而不是猜；Playwright MCP 則是之後 /check verify 要拿來「真的證明滑卡與 feed 能動」的工具。

第二步：讀懂風險等級

安裝時，agent 會替每一個 skill 標上風險等級，這是它主動替你做的安全檢查。示範裡有幾件事值得注意：

  • Playwright CLI 被標成 high risk。
  • 其他好幾個被標成 medium risk。
  • Playwright CLI 本身「來自 Microsoft、只是驅動瀏覽器」，看起來沒問題，但高風險幾乎可以確定來自它 SKILL.md 第 4 行的 allowed-tools：playwright-cli, Bash, npx。這些是範圍很廣的事前授權。

這條規則值得記住：風險等級看的不是工具「善不善意」，而是它要求的授權範圍。一個合法工具一旦被授予 Bash 與 npx，它就能在你機器上執行很多事。示範的處理方式是：Playwright CLI 移除，因為 Playwright MCP 能做同一件事，卻不需要這份授權。這就是「用同樣的功能換更小的權限」的判斷。

第三步：安裝 skills，再移除被標記的那一個

確定清單後，它會逐一安裝你挑的 skills。安裝指令就是你第一步用過的那一條，只是後面接的目標不同：

# Claude Code (installs into .claude/skills, then restart Claude Code)
npx skills@latest add jsmastery-pro/skills -a claude-code

示範裡總共裝了九個 skill，是一個一個完成的。裝完之後，若有被標成 high risk 的項目想移除，就在終端機裡執行移除指令。示範的做法是開啟終端機，cd 到正確的資料夾，然後：

npx skills remove playwright-cli

這一步要在你自己的工作資料夾執行，因為 skill 是裝在專案的 skills 目錄裡。移除之後，功能上你並沒有失去 Playwright——因為下面的 MCP 會補上同一件事。

第四步：接上 MCP servers（一定要在真的終端機做）

三個 MCP servers 要逐一接上。這裡有一個硬性限制：這些指令必須在真正的互動式終端機裡執行，不能透過 agent 代跑。原因跟前面的同意閘門一樣：接上 MCP 等於授權一條通往真實系統的連線，這個動作應該由你親自做。示範從 Supabase 開始：

claude mcp add supabase

接著是 Vercel，然後是 Playwright。三個都接完後，可以做最後的確認——列出目前所有的 MCP servers：

claude mcp list

示範列出來的結果同時包含既有與新接的項目（例如 Supabase、Playwright、Vercel，以及其他本來就有的）。看到預期的清單，就代表這一步接對了。

做完長什麼樣

這一步結束後，你的環境會多出兩樣東西：專案裡裝好的 agent skills，以及三條 MCP 連線。驗證方式也很直接——skills 用 / 加名稱確認它認得，MCP 用 claude mcp list 確認它出現在清單裡。要注意的是，這些都是選配，兩者通常會讓 build 更好，但不是非有不可；如果某個工具對你的專案價值不高，跳過它完全合理。示範裡就主動砍掉了被標高風險的 Playwright CLI，只因為它有更小權限的替代品。

小結

stack 定案後，workflow 會拿它去比對該裝哪些 agent skills 與 MCP servers。Agent skill 教 agent 用真實慣例做事，MCP server 讓它連上真實系統親自檢查。核心規則是「問是義務、搜尋不是」，未經同意不搜不裝。安裝 skills 用 npx skills@latest add …，移除用 npx skills remove …，接 MCP 用 claude mcp add … 且必須在真實終端機執行。風險等級看的是授權範圍，不是工具善不善意；示範就因為 Playwright CLI 要求 Bash 與 npx 的廣泛授權，改用它 MCP 版本。

到這裡，你的 stack 與工具鏈都就緒了。但在把 11 個功能都開始建之前，還有一件事要做：請第二個模型來檢查這份基礎 spec，看看有沒有你與第一個模型都看不到的洞。
