clear context，準備進 /develop

Step 6/6 · Greenfield：Scope 與架構技術棧

學習目標

在 spec 落地後 clear 或開新視窗，理解檔案才是狀態、clear 與 compact 的時機，並把下一步接上 /develop stack and architecture。

前言：地基畫完了，先把桌面清乾淨

前面五步，你從一句話的點子走到一份寫好的 stack spec：scope、build approach、stack 決定、agent skills 與 MCP、cross-check 都完成了。此刻你可能會想直接接下去叫它開工。但這條 workflow 反而要你先做一件事——把這個很長的對話丟掉。

聽起來違反直覺：好不容易聊出這麼多結論，為什麼要清掉？答案正是這整套流程的重點——真正重要的東西已經不在對話裡了，而是在磁碟上的檔案裡。這一節要讓你把「檔案才是狀態」這件事看透，知道什麼時候該 clear、什麼時候該 compact，然後乾乾淨淨地接上 /develop。

第一步：clear，或直接開一個新視窗

spec 寫到磁碟之後，執行：

clear

clear 會把當前 session 的 context 清空。如果你更習慣，也可以直接關掉舊視窗、開一個全新的。兩種做法效果一樣：你換到一個乾淨的起點。重點是，什麼都不會掉，因為所有的決定都還在 docs/scope/scope.md 與 docs/specs/ 的檔案裡，不在聊天紀錄裡。

這件事的價值很具體。這一長串對話，從現在起立刻停止花你的 token；而你剛剛做出的每一個選擇，仍然完整地留在檔案裡。課程形容這正是 agentic engineering workflow 漂亮的地方：你可以 clear、換模型、隔天再回來，工作不會斷。

第二步：搞清楚 clear 與 compact 的時機

這兩個動作常被混用，但用途不同。你可以用一條簡單規則記住：

動作什麼時候用結果
clearunits 之間、每個 architect 之後、features 之間完全清空，功能之間從檔案重新讀狀態
compact同一個 unit 之內，某一次執行變得很長把長對話壓縮，保留上下文繼續做同一件事

課程把它講成兩句話：units 之間一律 clear，unit 之內跑太久才 compact。但示範也補了一句：以這個流程的節奏，一個 unit 內通常不會長到需要 compact。反過來說，如果你發現自己在同一個功能裡愈聊愈糊、答案開始前後矛盾，那通常不是要 compact，而是你把兩個 unit 混在一起了——這時該做的是把它收乾淨、clear，讓它以檔案狀態重新開始。

第三步：如果你沒 clear 就往下跑，workflow 會擋你

這裡有一個實用的保護機制。/develop 在開始之前會確認你是不是已經 clear 過；如果你還在同一個長對話裡就想跑，它會提醒你必須先 clear。課程裡講者也很直接地說：如果你試著跑 develop，我相信它會告訴你必須先 clear session。

這道閘門不是找麻煩，而是把「用檔案延續工作」變成流程的紀律，而不是靠你自制。當狀態真的都在檔案裡時，先 clear 再開工的成本是零；不清就開工，才是把一堆用不到的上下文一起帶進新階段。所以示範的順序就是先 clear，再輸入下一步：

/develop stack and architecture

接下來 /develop 要做的是：依剛剛那份 decision spec 把專案 scaffold 出來，並讓空的骨架能在本機啟動、通過 production build。這正是 /architect 刻意不做的部分，現在由 /develop 接手。

第四步：迷路的時候，回到 docs/scope

clear 之後，你唯一需要記得的不是「剛才聊到哪」，而是「檔案在哪」。如果你忘記目前進度、不知道下一步要跑什麼，就回到 docs/scope/：scope 裡的功能會標明每個部分的狀態，以及它有沒有一個待完成的框。示範裡打開 scope 就能看到目前在第一個 feature「stack and architecture」，狀態是 in progress，架構已經完成，接下來要從那份決定 scaffold。課程甚至說：每當你不知道下一步做什麼，就回到 docs/scope 看自己在第幾個 feature。

順帶看一個數字：這一段花了多少

講者在 clear 前秀了一次用量，值得看一眼，因為它說明這套流程的成本落在哪裡。這次 run 用的是 Claude Max plan，總共只佔 5 小時限制的 6%、每週限制的 1%；其中 14% 的用量發生在較高的 context，17% 來自 architect skill。用 Opus 5 總共花了約 162,000 個 token，換到的是這個應用程式、乃至未來可能長在上面的一門 SaaS 生意，最重要的那一批決定。

講者的重點不是數字本身，而是：即使只花了這些，workflow 仍然在保護你——它會在你想繼續往下跑時，提醒你先把這個長對話 clear 掉。換句話說，省錢不等於可以省略 clear；clear 是紀律，不是備案。

做完長什麼樣

這一步結束後，你會得到一個「乾淨的起點」：終端機停在一個全新的 session，磁碟上有 docs/scope/scope.md 與 docs/specs/ 的 stack spec，而你已經輸入 /develop stack and architecture。可以驗證的結果是——/develop 讀得到那份 spec，開始 scaffold；而如果你忘了 clear 就動手，它會先請你回去清乾淨。至於 scaffold 的細節，屬於下一個階段的內容；這一節的目標是把「結束一個單位、乾淨地交棒」這個動作做對。

小結

spec 落地後的第一個動作是 clear（或開新視窗），因為檔案才是狀態，clear 不會掉任何東西，卻能立刻停止這個長對話的 token 成本，並讓工作能跨 session、跨模型延續。時機規則是：units 之間一律 clear，unit 之內跑太長才 compact。沒 clear 就想跑 /develop 會被擋下來；清乾淨之後，下一步是 /develop stack and architecture，從那份 decision spec 把專案 scaffold 出來。迷路時回 docs/scope 看自己在第幾個 feature。

六步走完，你已經親手演練了整條九步驟 workflow 最完整的一次開場：先把點子寫成 scope，選定切法，用多輪訪談把 stack 決定寫成 spec，接上工具，讓第二個模型檢查地基，最後把對話收乾淨、只留檔案。接下來就是 /develop 接手，把那個空的骨架真的建起來。
