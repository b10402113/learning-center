選 build approach：Tracer Bullet／Skateboard／Journey／Facade

Step 2/6 · Greenfield：Scope 與架構技術棧

學習目標

用「最大的風險在哪」在 Tracer Bullet、Skateboard、Journey、Facade 之間選出這一刻的切法，並知道 scope 選完後會據此讀哪一個 approach 檔。

前言：同樣的功能，切的順序不一樣

上一節你得到了 scope.md，裡面列出一串功能。但列表不會自己告訴你「先做哪一塊、每一塊做到什麼程度」。同樣是登入、資料庫、UI 這三件事，你可以把每一層各自做完整，也可以先做一條細細的、但真的能跑的路。這兩種切法會導致完全不同的開發節奏，也適合不同的風險。

所以 /scope 在規劃功能之前，會先問你一個決定：這份工作要用哪一種 build approach 來切與排。這一節要讓你能看著自己的產品，指出「現在最大的風險在哪」，然後據此選出切法。選對了，後面的 slice 順序自然會浮現；選錯了，你可能花很多時間在做一個其實不需要那麼早做的東西。

這是一個什麼樣的決定

這裡的張力在兩股力量之間拉扯：一邊是「我想趕快確認這東西是對的」，另一邊是「我想趕快確認這東西真的是做得成的」。這兩件事通常不能同時最早完成，所以你必須先賭一個風險最大的地方，先把它退掉。四種 approach 就是四種不同的「先退掉哪個風險」的答案。

四個選項並排比較

這套 skills 給的四個選項，各有它要對付的最大風險，切法與代價也不同：

Approach它假設的最大風險第一塊交付物代價
Tracer Bullet各層接不起來（auth、DB、API、UI、部署）一條真實、貫穿每一層的最細線路進度慢，廣度先放一邊
Skateboard做出沒有人要的東西最薄、但真的有人願意用的完整產品之後為了長大得付出重做的成本
Journey每一段都淺淺的、不夠精緻一條完整的使用者路徑，含各種狀態其他路徑要等很久才存在
Facade做錯整個體驗全部關鍵畫面都能點、能走，但用假資料第一版是 prototype 等級，不是 production

這四個選項在原始 skills 檔裡各自寫成一句「指導原則」，而不是步驟。原文字這樣定義：

- **Tracer Bullet**: vertical slices; each feature built end to end through every layer, working.
- **Skateboard**: MVP first; ship the thinnest usable whole first, then grow it.
- **Facade**: UI first; a clickable shell on placeholder data, then wire the back. Prototype grade (fast to demo, not production complete).
- **Journey**: a complete user path end to end per phase.

把定義攤開來看，差別的關鍵在「第一塊要證明什麼」。Tracer Bullet 證明的是連接：它保留真實的結構，只是把廣度切掉，auth、schema、UI 都用真的，不假造。Skateboard 證明的是有人要用：它願意砍掉結構本身，只求第一天就交出一個真的能用的完整小產品。Journey 裡每個 phase 是一條完整的使用者路徑，連 edge、empty、error、確認狀態都要做完。Facade 先做的是介面：所有關鍵畫面在假資料上先能走，看起來很真，但什麼都不會存。

怎麼問自己：三個判別問句

不要憑感覺挑。你可以依序問自己這幾個問題，第一個答「是」的，通常就是它：

  1. 最大的風險是不是「各層接不起來」？例如你不確定 auth 串資料庫、部署到主機這條路真的能通。是的話，選 Tracer Bullet。它的第一條線路會讓一個真實的使用者動作從 DB 走到邏輯、再走到畫面。
  2. 最大的風險是不是「做了沒人要的東西」，你需要很快拿到真實使用者的回饋？是的話，選 Skateboard。它會把「不要太早做」的結構（例如團隊、角色）也先砍掉。
  3. 產品本身就是那個體驗或漏斗，每一段都要夠精緻才算數？是的話，選 Journey。
  4. 你只是要先驗證「長相對不對」、給人點一點看感覺？是的話，選 Facade，但你必須明講這是 prototype 等級。

課程的示範為什麼選 Tracer Bullet？理由很具體：這是一個好好做、沒有 deadline 的 build，而且推薦迴圈只有在真的跑在真實資料上、端到端跑一遍之後，才會告訴你任何有意義的事。在這種情況下，先把整條管線接通的價值最高。原始檔也提醒一個預設值：一個認真的 production build，預設就是 Tracer Bullet，只有當目標真的需要時才換。

順帶一提：process rigor 是另一個問題

/scope 在問完切法之後，還會問一個獨立的問題：每個功能做完後要跑多少流程。示範選了它建議的「medium」。這跟 build approach 是兩件事：一個決定「怎麼切」，一個決定「做完要驗證到什麼程度」。不要把它們混在一起。

反例：什麼時候這個規則會翻轉

選錯的典型狀況，是你把「退掉風險」和「做得快」搞混了。幾個會翻轉判斷的情況：

  • Tracer Bullet 不適合「體驗就是產品」的東西。如果使用者要的是整個流程順不順、好不好用，而你卻只交付一條細線，你會證明「技術接得起來」，卻完全沒有回答「這體驗行不行」。
  • Skateboard 不適合「結構本身就是風險」的專案。如果你砍掉結構才做出來的東西，之後要長回來得整個重做，那它換來的速度可能不值得。這時 Tracer Bullet 保留真實結構反而更省。
  • Journey 不適合還在驗證整合的階段。如果你連「這條路到底跑不跑得動」都還不確定，就先把一條路徑做得精緻，很可能把心力花在一個之後要大改的基礎上。
  • Facade 永遠不能被當成可以上線的東西。它的價值在快速拿到回饋；一旦有人把它當 production 交付，代價就是「看起來能動、實際不能存」的落差。

選完之後會發生什麼

這個決定不只記在 scope 標題裡，還會一路傳下去。選定之後，agent 才會去讀對應的那一個 approach 檔，並採用那個工程師的角色來切功能。示範裡選了 Tracer Bullet，agent 才去讀 tracerbullet.md（34 行）——注意，這個檔一直在 .agents 資料夾裡，但它是等你選了才讀。這是刻意的：沒選之前沒必要佔用 context。

這個決定也會成為專案層級的慣例：/audit 與 /sync 會把它寫進根目錄的 AGENTS.md，而 /architect、/develop、/check verify 都會讀它、遵守它。它同時決定每個功能屬於哪個 phase，出現在 scope 的 At a glance 表與段落分組裡。原始檔把這件事寫得很清楚：

**Once the approach is chosen, read its persona file and adopt that engineer's role for decomposition** (`approaches/tracer-bullet.md`, `approaches/skateboard.md`, `approaches/facade.md`, or `approaches/journey.md`). Read only the chosen one.

也就是說，你不是在挑一個標籤，而是在挑接下來負責切功能的那個「角色」。後面所有 slicing 與 sequencing，都會跟著這個角色走。

小結

Build approach 決定的是「先退掉哪個風險」，不是「哪個比較高級」。判準是問自己：最大風險是各層接不起來（Tracer Bullet）、是沒人要（Skateboard）、是體驗本身（Journey），還是要先驗證長相（Facade）。認真的 production build 預設 Tracer Bullet；示範的電影 App 因為推薦迴圈必須真的端到端跑起來才有意義，所以選了它。選定之後，agent 才會讀對應的 approach 檔並採用那個角色。

切法定了，接下來要處理的是整個專案的地基：用什麼技術棧、什麼架構。這會是 11 個 build 部分裡的第一個，也是後面所有東西都站在上面的那一層。
