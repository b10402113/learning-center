安裝 skills，並把點子 /scope 成一份 plan

Step 1/6 · Greenfield：Scope 與架構技術棧

學習目標

在一個乾淨的 greenfield 視窗裝好 skills package 並驗證可用，接著用一句話跑 /scope，走完 greenfield 偵測與分批問答，產出 docs/scope/scope.md。

前言：一句話的點子，先別急著寫程式

你心裡有個想做很久的東西，例如「一個會依你的口味推薦電影的 App」。你打開對話視窗，第一個念頭大概是直接叫 agent 開始寫。可是接下來就會碰到熟悉的困境：agent 很熱心地做出一個資料庫、幾張漂亮頁面，卻跟你想象中的產品不太一樣；你改了 prompt，它又整組重來，昨天的結論今天找不到。

這條 workflow 的第一個動作，是把「腦中的點子」變成「磁碟上的檔案」。這樣一來，agent 換了、session 關了、隔天再回來，決定都還在。這一節要做的有兩件事：先把這套 skills 裝進你的環境，再對你的點子跑一次 /scope，讓它問你一輪問題，最後吐出一份 scope.md。搞懂這兩步，後面五節才有起點。

第一步：開一個乾淨的視窗，裝好 skills package

先開一個新的 Claude Code 視窗，用 CLI 或 VS Code extension 都可以。整個 agentic engineering workflow 的起點，就是把這套 skills 裝進來。課堂上示範的是從課程 GitHub repo 的 installation 區塊複製安裝指令，實際內容長這樣：

# Claude Code (installs into .claude/skills, then restart Claude Code)
npx skills@latest add jsmastery-pro/skills -a claude-code

npx 會去抓一個套件，接著進入一個小小的安裝精靈。它會問你要裝哪幾個 skill（這門課一共九個），以及你要裝在「這個專案裡」還是「全域所有專案」。示範裡是全選九個。裝完以後，精靈就結束了。

安裝完成後有一個容易漏掉的步驟：要重啟 Claude Code session，新的 skill 才會生效。驗證方式很簡單，輸入 /，看看 skill 名稱有沒有出現在選單裡，例如打 /scope 看看它認不認得。如果沒有，通常是忘了重啟。

第二步：用一句話跑 /scope

裝好之後，整個流程從 /scope 開始。你交給它的東西可以很簡短，短到只有一句話就夠了：

/scope build me a movie recommendation app

這一句話之所以夠用，是因為 /scope 不是叫你一次寫完需求，而是它會反過來訪談你。按下 enter 之後，它會先讀 plan.md，判斷這是一個 greenfield 專案——工作資料夾裡只有一個無關的 demo，而且還沒有任何 scope。判定完，它就走 scope 的 greenfield 路線，開始一輪一輪問你問題。

下面是示範裡它問的幾個關鍵題目。你可以從中看出，每一題都在改寫這個產品最後的樣子，而不是可有可無的寒暄：

  • MVP line：這個產品能保住核心價值的最小版本是什麼？示範回答「onboard，然後 feed with reasons」——登入、一條 onboarding 路徑、CSV 匯入或滑卡、個人化 feed，每一則推薦都附一句短理由。
  • App shape：純 web app、web app 加行銷站、手機 app，還是先 web 之後再手機？示範選「web app 加行銷站」，理由是能被搜尋引擎找到。
  • 推薦引擎要多聰明：示範選「taste profile + LLM 寫理由」——把評分變成口味模型，從中挑候選片，再讓語言模型寫一句人類看得懂的理由。不訓練任何模型。
  • 要不要收費：這一版先不做 billing，之後再說。
  • 額外能力：watchlist／儲存／看過／隱藏放進這一版；完整目錄瀏覽與社交追蹤延後。
  • 橫切關注點：行銷頁的 SEO 要真的做；analytics、錯誤監控、無障礙、隱私頁與 cookie consent 之後再處理。
  • 限制條件：示範回答「沒有，好好做」。

每題的回答都可以很短。這裡有一個值得記住的觀點：這些問題對 agent 來說很便宜，對你來說也很便宜，但回答它們需要的思考，才是讓你成為架構師的東西。也在這個階段，你要練習說出「這一版先不做」——示範裡把完整目錄、社交追蹤、email 通知全部往後推。課程把這件事講得很直白：在專案一開始，你決定「不做」的功能，比你決定「要做」的功能更重要。

references 是可選的，先想清楚再答應

/scope 會另外問一個問題：要不要幫這份 scope 加上 references 區塊。這裡有兩條路。示範選擇不加，因為 scope 只保留意圖與理由，短、好讀，不需要引用連結。但如果你在做的是很細、要到 enterprise 等級的東西，就會想加上來源，而且連結要經過 web 驗證，之後 agent 回來還知道資料是從哪來、有沒有更新。兩種都合理，差別在你這個專案的等級。

做完長什麼樣

這一步結束後，你的工作資料夾會多出一份 docs/scope/scope.md。它通常分兩層：開頭是一個精簡的 At a glance 表格，讓你一眼掃過有哪些功能；下面是依 phase 分組的功能段落，而段落順序本身就是建置順序，不需要另外維護一份「build order」清單。

示範裡的 scope 開頭會寫清楚這個產品是什麼、build approach 是什麼、以及專案的預設 workflow rigor tier。以這次的電影推薦 App 為例，它認出整個 build 有 11 個部分，前幾個是 stack 與架構、coding standards 與工具鏈、data model、movie catalog 與 cache、design system 與 UI foundation，這些都屬於「地基」，地基之後才切進具體功能。

你可以用一個 markdown 檢視器把它讀得舒服一點，但真正重要的不是排版，而是這份檔案從現在開始就是你這個專案的「狀態」。聊天視窗可以關掉，這份檔案會留下來。

小結

Workflow 的第一步是先裝 skills package（npx skills@latest add … -a claude-code），重啟 session，並用 / 確認可用。然後對一句話的點子跑 /scope；它會偵測這是 greenfield，再用一輪輪問答把點子逼成一份 docs/scope/scope.md。過程中你要做的關鍵動作，是替每一題做決定，尤其是決定哪些功能先不做。這份檔案不是聊天紀錄，而是接下來每一步都要回來讀的專案狀態。

有了 scope，下一步要回答的是「這些功能要怎麼切、怎麼排」。/scope 接著會問你一個問題——要用哪一種 build approach。選哪一種，會決定後面每一個 slice 的形狀。
