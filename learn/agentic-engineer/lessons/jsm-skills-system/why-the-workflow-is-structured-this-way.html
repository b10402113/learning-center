這套流程為什麼長這樣

Step 2/5 · JSM Skills System：安裝與九步驟地圖

學習目標

理解這套「具名步驟加必要文件」的流程，如何連結到軟體開發生命週期（SDLC）與架構決策紀錄（ADR）。你也會看見 agent 最危險的失敗模式，以及文件能不能一路維持到第 30 天，為什麼才是真正的難題。

前言：這是不是某個人的個人偏好？

上一節你裝好了九個 skill。打開一看，裡頭是一串有名字的步驟，還規定要在哪裡寫下哪些文件。這時很自然會冒出一個疑問：這套流程聽起來很有一套，但會不會只是某個人把自己的習慣包裝成「工程方法」？

這個疑問值得認真回答。要是流程只是個人偏好，就沒有理由非得照著做。講師在介紹這些 skill 之前，先用一整節處理這個質疑。答案是：這套流程的根源，早在 agent 會寫程式之前，就已經是軟體業的標準做法。

它的來源一：軟體開發生命週期

早在 AI 能寫程式之前，認真的軟體專案就已經沿著一條熟悉的路前進：先想清楚要做什麼，再做重要的技術決定並記錄下來；接著訂好大家共同遵守的慣例，一次完成一個功能，最後在宣告完成之前，確認它真的能運作。

這條路叫做軟體開發生命週期，簡稱 SDLC。它的基本架構很清楚：需求成為設計，設計成為實作，實作再進入驗證。每個階段都會產出下一階段需要的材料。這套做法比 Cursor 以及其他 AI 寫程式工具都早得多，是一副行之有年的工程骨架，不是什麼新發明。

它的來源二：把決定寫下來（ADR）

把決定記錄下來也不是新招。工程師寫架構決策紀錄（ADR）已經很多年，理由很實際：如果重要選擇背後的原因只留在某個人的腦中，遲早會消失。幾個月後，可能有人想修改這個選擇，卻不知道當初為什麼這樣決定，於是又把原本好不容易避開的問題帶了回來。

所以，謹慎的團隊不把記憶當成唯一的保存方式，而是讓證據留在現場。文件不是拿來裝飾的，而是要讓「為什麼」不會隨著某人離職、忘記或換了職位，就跟著消失。

為什麼換成 agent，這件事變得更要緊

到這裡談的還是老道理。讓這套流程變得格外重要的，是 agent 的本能。

agent 的直覺是直接衝進程式碼。在 vibe coding 的實驗裡，你已經看過這種情況：它接到一個想法後，會默默地替每個尚未決定的地方填上答案，接著幾秒內就開始實作。整個過程看起來勤奮又有效率，但仔細一看，它其實是在一連串你從來沒做過的決定上蓋房子。

危險就在這裡。agent 不會停下來提醒你「這裡還有個決定沒做」，而是自己挑一個答案，卻不告訴你。等問題浮現時，你就得在一棟地基不是你打的房子裡收拾殘局。

所以這些 skill 其實在做什麼

這些 skill 沒有發明一套新的軟體開發方法。它們做的事簡單得多：逼 agent 沿著好的工程團隊本來就該走的路前進。一次走一個階段，讓每個階段的決定成為下一階段的依據，避免 agent 偷偷跳過最重要的部分。

你可以把這些具名步驟想成護欄。護欄不一定讓車開得更快，但能避免它為了抄近路而衝出道路。

不是只有這套在這樣做

如果這真的只是個人偏好，理應只有一家在這麼做。事實上，大家都在往同一個方向走：GitHub 推出 Spec Kit，Amazon 推出 Kiro，BMAD 則讓一群分工不同的 agent 彼此協調。它們的核心前提相同：叫 agent 動手之前，先把需求和決定寫下來。

所以，「寫下來有沒有用」其實已經不是爭論的重點。

真正有趣的問題：第 30 天

既然寫下來有用已經確定，真正的問題就變成：到了第 30 天，文件會變成什麼樣子？尤其程式碼已經繼續往前走，卻再也沒有人回頭打開那份規格時。

講師的答案很直接：一份寫完就被遺忘的規格，比沒有規格還糟。它會讓人「自信地錯」：你以為文件還在把關，實際上它講的卻是早已不成立的故事，而且你可能過了好一陣子才發現。

後面幾節會看到，這套 workflow 有不少設計正是在回應這個問題。/architect 會把「決定」和「理由」分開；/develop 只讀面向建構的那一半；/sync 則把這些內容對回實際上線的狀態。

小結

這套具名步驟加必要文件的流程，其實是把兩個早已存在的方法帶進 agent 的世界，不是誰的個人偏好：軟體開發生命週期（需求→設計→實作→驗證，每個階段都為下一階段提供依據），以及架構決策紀錄（把決定寫下來，因為只留在腦中的理由終究會消失）。agent 更需要這些護欄，因為它會直接衝進程式碼，默默替你補上還沒做的決定，看起來還很勤奮。這些 skill 沒發明什麼新方法，只是逼 agent 沿著好團隊本來就該走的路前進，同時面對「文件能不能活到第 30 天」這個難題。

現在你已經知道這套流程為什麼存在。接下來要看的是地圖：九個 skill 各自負責什麼、會產出什麼，以及該按什麼順序呼叫。下一節會帶你看完整條迴圈。
