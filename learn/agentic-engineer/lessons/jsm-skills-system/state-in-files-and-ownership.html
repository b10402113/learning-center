狀態存檔案，不存對話

Step 4/5 · JSM Skills System：安裝與九步驟地圖

學習目標

理解「狀態活在檔案、不活在 chat」：四種檔案（context／scope／specs／design.md）各由哪個 skill 負責，以及 /sync 如何讓文件到了第 30 天仍然有用。

前言：對話關掉之後，還剩下什麼？

上一節的地圖上，幾乎每一格都在寫東西：scope 寫計畫、architect 寫規格、audit 寫 context、sync 把學到的內容寫回去。這些產物有個共同點：它們不是留在對話裡，而是存進檔案。

這值得特別停下來看，因為它回答了整套流程最關鍵的問題。agent 對話可以結束，session 可以清掉，同事也可以把分支拉過去。如果重要資訊只留在對話裡，對話一關，工作就像沒發生過一樣。這一節要說明的是：這套系統如何讓工作延續到對話結束之後。

對話是一個會消失的地方

把重要知識放在對話裡，問題不只是關掉就會消失。對話會越滾越長、成本越來越高；長到某個程度，agent 也更容易漏掉前面說過的事。你可能遇過這種情況：同一件事講了三遍，它還是忘了。

這套 workflow 的解法很直接：該記下來的資訊，一律寫進專案檔案。即使對話結束、session 清空，或隊友拉到分支，知識都還在，因為它從來沒有被困在對話裡。也因此，每個階段之間，官方甚至會建議清掉 session：新對話會從磁碟重新讀取現況，不會因此漏掉工作狀態。

四種檔案，各有明確的主人

一、context 檔：AGENTS.md

AGENTS.md 記錄專案實際如何運作，例如使用的技術棧、執行指令與開發慣例。它是純文字，任何 coding agent 都能讀。如果專案使用 Claude Code，旁邊還會有一個極短的 CLAUDE.md，只負責指向 AGENTS.md。這樣真正的資訊來源就只有一份，不會出現兩份內容各自變動的情況。

它還有一個重要特性：可以巢狀。專案根目錄的檔案可以記錄全專案適用的規則，特定資料夾也能放一份只管那一區的規則。skill 處理 payments 程式碼時，會讀取最近的那份檔案，因此能同時掌握全專案規則與該區域的在地規則。

AGENTS.md                 ← 根目錄：適用全專案的規則
src/payments/AGENTS.md    ← 只有 payments 這一區要遵守的規則

/audit 負責建立這份檔案，其他每個 skill 都會讀它，程式碼變動後則由 /sync 維持更新。原則很簡單：context 檔已經寫明的慣例，就不需要任何 skill 再靠猜測補上。

二、scope：docs/scope/

scope 是「要做什麼、先後順序如何」的粗略計畫，由 /scope 建立。/develop 建功能時會推進這份計畫，例如標記功能正在進行、勾選里程碑；但它不會自行把功能標成完全完成，因為「建好了」不等於「驗證過了」。不帶參數執行 /scope，或在合併時執行 /sync，都會把 scope 和程式碼的實際狀態對齊。

三、specs：docs/specs/

一份 spec 是「一個真實決定」的書面紀錄，也是建構時必須遵守的合約。決定做出的當下，由 /architect 寫下 spec，初始狀態是 Proposed，意思是「已決定，但還沒建」。建構期間，/develop 只會更新狀態那一行：先從 Proposed 推進到 In Progress，功能建好並完成驗證後，再改為 Accepted。如果某個決定真的被推翻，/architect 會寫一份新 spec，將舊 spec 標成 Superseded，並指向取代它的新版本，讓決策歷史仍然清楚可查。

還有一種特殊狀態叫 Assumed。如果選擇「先建再說」，而當中的決定又確實重要，/develop 不會默默猜下去，而是寫一份簡短的 Assumed spec，記下採用的假設、授權者，以及受影響的程式碼。這表示「已記錄，但還沒想透」。這些功能會一直帶著「待批准」的旗標，直到你再次執行 /architect，正式批准這項決定。

四、design 系統：design.md

這份檔案記錄使用者介面的美術方向，也就是頁面的整體氣質與組裝規則。精確數值，例如確切的顏色與尺寸，則存放在專案 CSS 裡；design.md 只指向這些數值，避免同一個數值被記在兩個地方。第一次建置介面時，由 /develop 建立這份檔案，也可以從既有畫面萃取內容。

每個檔案只有一個主人

這些檔案能持續讓人信任，關鍵在於擁有權固定：誰建立、誰讀取、誰能修改，都有明確規定。每個 skill 都不會修改另一個 skill 擁有的檔案。

/sync 讓文件活到第 30 天

回到第二節留下的問題：到了第 30 天，文件會變成什麼樣子？關鍵角色是 /sync。它會在接近合併時執行，檢查程式碼的實際狀態，再把耐久檔案對齊：如果這次建構引入了新慣例，它會更新 context 檔；它會校正 scope；如果某項改動讓 spec 過期，也會把它標記出來。

/sync 只做外科手術般的小修改：只新增內容，或修改自己負責的行，絕不改寫你寫的文字。這是整套系統的保證。每種檔案都有固定主人，/sync 不需要、也不被允許重新詮釋別人的內容；它只負責讓文件與事實對齊。正因為有這份紀律，文件才不會隨時間變得混亂，甚至「很有自信地寫錯」。

小結

這套 workflow 的狀態活在檔案裡，不活在對話裡，因此工作可以跨 session、跨人延續。四種檔案各有明確的用途與主人：AGENTS.md（audit 建立、所有 skill 讀取、sync 更新，而且可以巢狀）、docs/scope/ 的 scope（scope 建立、develop 推進）、docs/specs/ 的 specs（architect 擁有內容、develop 只改狀態行；狀態從 Proposed 推進到 Accepted，另有待批准的 Assumed），以及 design.md（develop 建立，數值則存在 CSS）。擁有權固定，各 skill 不會碰別人的檔案，/sync 才能用小幅修改讓文件與實際程式碼保持一致，讓它們到了第 30 天仍然可信。

到這裡，你已經有了整張地圖，也知道狀態存在哪裡。最後一個實務問題是：面對真實專案，該從這個迴圈的哪裡開始？新專案、既有程式碼庫和單一小改動，入口各不相同。下一節會從 /audit 的位置切入，說明如何選擇起點。
