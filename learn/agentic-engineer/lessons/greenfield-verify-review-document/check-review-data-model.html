換模型跑 check review

Step 2/4 · Greenfield：Verify、Review、Document

學習目標

上一節的 check verify 證明了資料模型「今天這樣跑會動」。這一節要跑 check review，回答另一個問題：這份碼是怎麼被造出來的，有沒有作者自己看不見的盲點。做完之後，你會拿到一份依嚴重度排序的 findings，並且親手用一筆新 migration 修掉一個真正的 major 問題。你會看懂：它怎麼判斷作者模型、為什麼換一個不同家族的模型、為什麼明明只看 diff 不夠、以及為什麼修法是新增 migration 而不是改舊的。

前言：同一個模型審自己，等於沒審

驗證過關之後，還有一種錯誤是驗證抓不到的：那種「跑起來正常，但設計上有個洞」的問題。例如一個欄位在某些狀態下不該是空的，而這個規則只寫在應用層的程式碼裡，資料庫層完全沒有把關。這種洞在 happy path 上永遠不會浮現，卻會在真正上線、遇到非預期的寫入時出事。

問題是，寫這段碼的模型自己看不到這個洞——因為那就是它當時的思考盲點。所以要找一個沒寫過這段碼的模型來看。前置條件跟上一節一樣：功能已建置、處在相對 base 有差異的分支上，而且你已經跑過驗證。

Step 1：它先判斷「這段碼是誰寫的」

輸入 check review data model。它還沒讀第一行程式碼，就先處理一件事：這段碼是哪個模型寫的。原因是如果把作品交還給作者本人審，整個跨模型的價值當場消失。

判斷的方式值得記住。它不會問目前正在跑的模型「你是誰」，因為那個答案本身就不可靠，而且一段對話裡寫死的模型名稱，在你中途換模型之後立刻過時。它改為去讀專案裡不會說謊的設定檔。

**1a: Detect the author model (best effort).** The author model is whatever is generating code in this session. Using your file tools, read `ANTHROPIC_MODEL` from the env if set, and check `.claude/settings.local.json`, `.claude/settings.json`, and the user-level `.claude/settings.json` in the home directory for a `"model"` value. Map ids to families: `claude-opus-*` → `opus`, `claude-sonnet-*` → `sonnet`, `claude-haiku-*` → `haiku`, `claude-fable-*` → `fable`. Use the system-prompt value only as a last-resort weak hint, possibly stale.

換句話說，它把「我是誰」換成「這個專案設定成用誰」。設定檔是持久的，不會因為你在對話中途切換模型就說謊。

Step 2：只問你一句確認，再換模型

偵測完之後，它只給你一個問題：「這是寫這段碼的模型嗎？」這一句確認看起來很小，卻是整個機制的保證。因為偵測只是盡力而為，一旦猜錯，就會默默用同一個模型審同一份碼，跨模型的好處當場消失。課程示範裡偵測到的是 Opus，你確認之後，它就用 Sonnet 來審。

對照關係是固定的，核心規則只有一條：reviewer 永遠不能和作者同一個家族；而且 review 是需要推理的工作，所以不會用最便宜的模型來審。

| Author model | Reviewer model to spawn |
|---|---|
| `opus` | `sonnet` |
| `sonnet` | `opus` |
| `fable` | `opus` |
| `haiku` | `sonnet` |

Step 3：review 在一個唯讀的子代理裡跑

接著它把 review 放進一個獨立的子代理。這個子代理拿到的工具裡沒有 Edit，也就是說，它結構上根本無法修改要審的程式碼。它只能讀、只能判斷、只能把發現寫進 findings 檔。

- `model`: the reviewer model chosen in Step 1 (different family from the author)
- `description`: `"Review: <N> changed files on <reviewer-model>"`
- Tools: `Read`, `Bash`, `Grep`, `Glob`, `Write`, no `Edit` (the reviewer reports, it does not change code)

這樣安排還有第二個好處：大量的檔案內容留在那個子代理裡，不會擠進你的主對話。你的 session 只收到最後的濃縮結論，context 不會被撐爆。

Step 4：它不只看 diff，還把整個檔案讀完

很多 review 工具只看 diff，它偏不。它先看 diff 找出你改了哪些檔案，然後做一件大多數工具沒做的事：把涉及的檔案從頭到尾讀一遍。課程示範這一輪總共讀了 37 個檔案。

為什麼要多花這個成本？因為 diff 只顯示「你改了哪幾行」，但真正決定這個改動安不安全的，往往是那幾行周圍的程式碼。只看改動的行，你會看不清它在整體裡造成的影響。示範者自己說得很直接：這樣做省下了另外請第三方 reviewer 的成本，而且能在合併到 main 之前就把問題攔下來。

Step 5：讀懂那個 major 問題

跑完之後，findings 回來，結果是一個 major 加四個 minor。那個 major 值得你仔細看，因為它正好是「作者自己不容易抓到」的典型：

在 ratings 這張表的 schema 裡，沒有任何資料庫層的 constraint 把 score 的可為空性綁在 state 上。也就是說，「score 什麼時候可以是 null」這條不變量，只存在於應用層的程式碼裡。

翻譯成白話：應用層的程式碼小心翼翼地遵守「某個 state 底下 score 一定有值、另一個 state 底下才可以為空」的規則，但資料庫完全不知道這條規則。只要有任何一次寫入繞過應用層——例如手動 SQL、腳本、或未來另一段沒注意到的程式碼——就能寫進一筆不該存在的資料，而且不會有任何錯誤。這不是今天會爆的 bug，而是埋在結構裡的洞，正是獨立視角才看到的那一類。

Step 6：修法是新增 migration，不是改舊的

它很快就把 major 修好了。你可以叫它只修 major，也可以連 nitpicks 一起修，示範這一輪是連小問題一起處理。真正要學的是為什麼修法是一筆新 migration，而不是回頭改編號 000 的那一筆。

原因是 migration 的執行器是依 timestamp 判斷「跑過沒」的。如果直接改已經跑過的 000，執行器會認為那一筆早就完成了、不需要重跑，於是你改的內容永遠不會被套用到資料庫上。表面上你「修好了」，實際上資料庫的狀態跟你宣稱的不一致，而且是悄悄地不一致——這比原本的洞更危險。

所以正確做法是新增一筆 migration。它把 constraint 補上，然後再跑一次 migration 當作證據，證明這筆真的生效了。這個「為什麼不能改舊的那一筆」的判斷，是你之後每次修 schema 都會用到的。

Step 7：讀 findings 與它的邊界

findings 回來時，它會先給結論，再列出需要行動的項目。格式大意如下：

## /check review <feature> · <Approve | Approve with nits | Changes requested | Blocked>

Blockers (<count>) · fix before merge:
- <file:line · one line>
Major (<count>):
- <file:line · one line>
<count> minor/nits · strengths: <one line> · reviewed by <reviewer-model> over <N> files. Full findings in docs/reviews/<date>-<branch>.md.

讀的時候先抓兩層：blockers（合併前一定要修）與 major（嚴重但不必擋住合併），這兩層才是真正的行動項目；minor 與 nitpicks 收斂成一行，完整內容看檔案。

最後記得它的邊界：check review 在轉述完之後就結束了。它不修 findings（那是實作端的事），也不會去呼叫其他 skill。它的工作只是評估。修完之後，資料模型這條線就只剩最後一哩：把它當成一次正式交付記錄下來。

小結

check review 從專案設定檔判斷作者模型，而不是問目前模型自己是誰；只問一句確認，因為猜錯就會讓跨模型的好處消失。接著它換成一個不同家族的模型，在沒有 Edit 權限的唯讀子代理裡跑 review。

它先看 diff，再把涉及的每個檔案整份讀完，因為決定改動安不安全的是周圍的程式碼。這一輪在 37 個檔案裡找到一個 major 與四個 minor；major 是 ratings schema 沒有把 score 的可為空性用資料庫 constraint 綁在 state 上，規則只活在應用層。

修法是新增一筆 migration 而不是改舊的 000，因為執行器依 timestamp 判斷是否跑過，改舊的不會重跑、只會讓狀態悄悄對不上。review 只負責判斷，不負責修改。

程式碼有了第二個視角，接下來要把這次交付變成一份會跟著走的紀錄。下一節要用 document，從分支上的 commits 與 diff 組出一份 PR 描述，然後 commit、開 PR、merge。
