對資料模型跑 check verify

Step 1/4 · Greenfield：Verify、Review、Document

學習目標

這一節要帶你第一次跑 check verify。做完之後，你會拿到一份依驗收標準逐條打勾的驗證報告；資料模型的每一條 acceptance criteria 都真的被跑過，而不是只看程式碼「應該會動」。你會依序看懂：它怎麼從 verify.md 決定要驗什麼、缺 .env.local 時怎麼解開阻塞、Supabase 的四個變數哪兩個可以交給 agent、最後那份「11 條 checked、零 unexercised、零 fail」的報告是怎麼讀的。

前言：功能早就寫完，但驗證還沒做

想像你花了兩個晚上把資料庫 schema 寫好，migration 也寫了，seed 也跑了，心裡覺得「這塊完成了」。於是你打開 scope 檔，看到資料模型那一列還停在 in progress，底下幾個子項有一個沒打勾。那個沒打勾的項目是「Verify it」。很多人會在這個地方停住，因為功能看起來明明能動，為什麼還要再驗一次？

原因是：綠色測試與「我剛才手動看過」只證明你想到的那些路徑會動，不證明規格裡承諾的每一條都真的成立。正式的驗收必須由一支會被逼著「動手跑真東西」的 skill 來做。這一步就是那支 skill。前置條件只有兩件事：這個功能已經 /develop 完、處在一條相對 base 有差異的分支上，而且你有辦法連到一個真的資料庫。沒有這個前置，先回去把功能建起來。

Step 1：先讓它選模式，不要讓它猜

打開 Claude Code，輸入 check。注意，它不會預設幫你跑 verify，而是先停下來問你要跑哪一種。這是刻意的：跑錯模式會浪費整個 run，所以這一步被放在所有事情之前。

Which check do you want to run? Type one:
  • verify  run the real app and prove the change works against its spec (usually right after /develop)
  • review  a fresh model senior read of the diff, ranked findings (usually right before a PR)
  • both    verify first, then review

課程示範選的是 verify，對象是 data model。兩個模式的時機不同：verify 接在 /develop 之後，證明行為真的發生；review 通常發生在開 PR 之前，換一個模型讀 diff。這一節只跑前者，後者留到下一節。

Step 2：它讀 verify.md，找出還沒打勾的項目

選定模式之後，它做的第一件事不是打開程式碼，而是去讀這個功能旁邊的 verify.md。這份檔案是 /develop 階段留下的驗收清單，把每一條 acceptance criterion 翻譯成一個「可以觀察」的動作加預期結果，並標上它對應哪一條 AC。

# Verify: <feature> · spec NNNN
## UI / manual
- [ ] <action> → <expected>   → AC-N
## Commands
- [ ] `<command>` → <expected> → AC-N
## Acceptance-criteria coverage
- AC-1 … · AC-2 … · …

課程示範裡，這份清單上的框框有些已經打勾、有些還沒，而資料模型那一項正卡在半途。你要注意的地方是：它的工作範圍不是「只驗你改過的檔案」，而是「把 spec 承諾的每一條都驗一遍」。就算某條 AC 根本還沒實作，它也會留在清單上被標出來，因為那正是這道關卡要抓的漏。

Step 3：缺 .env.local 卡住了，先解開它

跑了一陣子，它回報一件事：repo 裡沒有 .env.local。少了這個檔案，`pnpm db migrate`、`pnpm db seed`，以及任何要啟動 app 的動作都跑不起來。它沒有硬闖，而是問你：「執行階段的步驟你想怎麼處理？」

這裡是整節最值得學的操作判斷。Supabase 需要四個變數，但它們的敏感度不同：

  • NEXT_PUBLIC_SUPABASE_URL 與 NEXT_PUBLIC_SUPABASE_ANON_KEY：這兩個是公開值，本來就會送到瀏覽器端，所以 agent 可以透過 MCP 直接幫你填好。
  • 兩條連線字串（database URL 與 direct URL）：裡面帶著你的資料庫密碼。沒有任何 API 會把密碼交出去，所以這兩個一定要你自己去 dashboard 複製。

它的處理正是照這條界線切開：公開的兩個自己填，帶密碼的兩個留給你。這樣你既省下最容易填錯的部分，又不會把密碼交給工具。填好之後，.env.local 大概長這樣（實際值依你的專案而定）：

# .env.local
NEXT_PUBLIC_SUPABASE_URL=https://<project>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon-key>
DATABASE_URL=postgresql://...:6543/postgres   # transaction pooler
DIRECT_URL=postgresql://...:5432/postgres     # direct connection

兩個連線字串的來源在 dashboard 的 connect 區：transaction pooler 走 port 6543，direct connection 走 port 5432，把 dashboard 給的字串貼進去、換上你自己的密碼即可。這裡有個很容易踩的坑：要填進 .env.local，不是 .env.example。後者只是給人看的範本，填在裡面不會生效。

Step 4：IPv6 不通時，改用 session pooler

你以為填完就能一路順跑，結果它又回報一件事：你用的是 IPv4 的 session pooler，但這台機器沒有全域 IPv6 位址，所以原本的 direct URL 連不上。它的處理是把 direct URL 換成 session pooler——這是官方支援的替代路徑，不是隨便亂改。

這件事的價值不在於「換一個字串」，而在於它先連線、發現不通、才回頭換路徑。它沒有假裝連得上，也沒有叫你自己去想辦法。遇到連線層的問題時，這種「先用可觀察的事實確認、再換方案」的節奏，正是你要學的手感。

Step 5：它真的去操作 app，而不是讀程式碼

環境通了之後，它開始執行驗證。關鍵在於它做的是「驅動真實的 app」：更新 profiles、把 onboarding 設成 complete、從 auth.users 刪除使用者、再刪一次，跑完整條流程後把資料庫留在乾淨狀態。

它為什麼非跑不可？因為這支 skill 有一條不能繞過的規則：沒有證據，就不能給過。它必須在當下記下「我執行了什麼、看到什麼」，這些紀錄才撐得起後面的結論。

| Behavior kind | The evidence to record |
|---|---|
| UI | the URL you loaded, the screenshot path you saved, and what you saw rendered |
| API | the exact request line, the HTTP status, and the key fields of the body |
| CLI / job | the exact command, its exit code, and the stdout/stderr excerpt |
| Data layer | the query you ran against the live schema, and its result |

對資料模型來說，最有力的一條證據就是「真的對活著的資料庫下了查詢、並且看到結果」。這也是為什麼缺 .env.local 會是阻塞而不是小事：沒有它，資料層這一格根本填不出來。

Step 6：讀最後那份報告

跑完之後，它會輸出一份格式固定的報告。標題先給結論，下面才是細節：

## /check verify <feature> · <PASS | FAIL | BLOCKED>

**<PASS: all N behaviors met, every specced surface built · FAIL: M of N failed · BLOCKED: K couldn't be exercised>.**   (never PASS or ✅ if you did not actually run the app; say "not started")

課程示範這一輪的結果是：pnpm db migrate、pnpm db seed、pnpm verify dev 三個指令都正常運作，11 條 acceptance criteria 全數 checked、零 unexercised、零 blocker、零 fail，而且是一次通過。另外它特別註明「one segment carried forward by the design」——意思是有一段是刻意留給後續設計承接的，不是漏掉，別把它誤讀成缺失。

你要抓的讀法是：先看總結論落在 PASS／FAIL／BLOCKED，再看有幾條沒被真正執行。零 unexercised 的意義很大——它代表沒有任何一條是「因為沒跑而不知道」，全部都有證據。

Step 7：知道它的邊界，然後 clear

最後要記得這支 skill 不修東西。它只負責判斷：通過就開綠燈，失敗就把你指向 /debug 或 /develop。它不會、也不應該順手改你的程式碼——因為一旦它開始改，這份驗證就再也不是獨立的了。

示範的最後一個動作是輸入 clear。驗證的狀態已經寫回 spec 與 scope，開一個乾淨的 session 不會丟掉任何東西，反而讓下一步更便宜。接著才進入第二種檢查：check review。

小結

功能寫完不等於驗收完成。check verify 先路由模式、再讀 verify.md 找出還沒打勾的項目，把 spec 承諾的每一條 AC 都排進清單。

缺 .env.local 時它會停下來解開阻塞：公開的 Supabase 變數由 MCP 代填，帶密碼的連線字串留給你自己去 dashboard 複製；IPv6 不通就改用 IPv4 的 session pooler。接著它驅動真實的 app 跑過整條流程，並且遵守「沒有證據就不給過」，最後產出「11 條 checked、零 unexercised、零 blocker、零 fail」的單次通過報告。

它只判斷、不修改；跑完之後用 clear 開一個乾淨的 session，把狀態交給下一支 skill。

驗證回答了「今天這樣跑會動嗎」。但還有一個問題沒回答：這份程式碼是怎麼被造出來的，有沒有作者自己看不見的盲點。下一節要把同一份碼交給一個沒寫過它的模型，跑 check review。
