用 document 產出交付紀錄（PR）

Step 3/4 · Greenfield：Verify、Review、Document

學習目標

驗證與審查都完成了，這一步要把整段工作變成一份留得下來的紀錄。做完之後，你會得到一份以 PR 描述形式呈現的交付紀錄，內容是從分支上的 commits 與 diff 組出來的，而不是靠你事後回想；接著你會把未提交的工作 commit 進去、開出 PR、merge 進 main。你會看懂：四種文件類型怎麼選、PR body 的骨架長什麼樣、這個 skill 的產物邊界在哪、以及為什麼「開 PR」這種對外動作一定要先過你這一關。

前言：一週後還會記得理由的紀錄

你有沒有過這種經驗：一個功能做完、merge 進去，兩週後回頭看某一段程式碼，完全想不起當初為什麼要那樣寫？程式碼本身會留下「做了什麼」，但幾乎不會留下「為什麼這樣做、驗證到什麼程度、reviewer 該注意哪裡」。這些東西如果沒有人當下寫下來，就永遠消失了。

前置條件是：你剛跑完 check review，人在功能分支 feat/data-model 上，比 main 領先三個 commits、而且還沒有開 PR。這個狀態很重要，因為 PR 描述正是要從這三個 commit 與它們的 diff 生成——如果 PR 已經存在，它的動作就會變成「更新既有的 PR 內容」，而不是建立新的。

Step 1：它先確認你現在站在哪裡

輸入 document。它在動手寫之前，會先用幾個 git 指令把現況摸清楚：base 分支是哪個、現在在哪條分支、這條分支相對 base 有哪些 commit 與檔案。這些是它後面寫 PR 的「原料」。你不需要自己跑，但知道它讀了什麼很重要——因為這決定了 PR 內容能不能追溯回真實的歷史。

# base branch: use `main` if it exists, otherwise `master`
git rev-parse --verify main
# current branch
git rev-parse --abbrev-ref HEAD

# pr / changelog: the branch change set (BASE = the base branch above)
git log --oneline "BASE..HEAD"
git diff --name-only "BASE...HEAD"

示範這裡的狀態是：分支 feat/data-model、三個 commits ahead、沒有開 PR。所以它接下來的任務很清楚——用這些 commit 與 diff 寫出 PR 的 title 與 body。

Step 2：選文件類型，它會推薦 PR 描述

它很快會問你一個問題：這次的變更要寫成哪一種文件？四種選項各有它服務的對象。示範的選擇是「PR description」，也就是被標記為 recommended 的那一項。

"What should I write?"
  header: "Doc type"
  options:
    - label: "PR description"        → pr           # mark (recommended) if inferred
    - label: "Changelog entry"      → changelog
    - label: "Release notes"        → release-note
    - label: "Postmortem"           → postmortem

四個選項的差別說穿了就是「寫給誰看」與「素材從哪來」：PR 描述寫給 reviewer，素材是 branch 的 commits 加 diff；changelog 給開發者，來源是已 merge 的變更；release notes 給使用者，以 tag／版本為範圍；post-mortem 給團隊，用在你出了事故、需要把事實寫下來的時候。示範這一輪一切順利，所以一份 PR 描述就很夠了。

Step 3：它從 commits 與 diff 寫出 title 與 body

選定之後，它會去讀分支上的 commits、讀 diff、看 review 的 findings、確認 scope，然後把這次變更的來龍去脈拼出來。它的原則是明確的：不從想像寫，只從紀錄寫。每一個句子都要能追回某個實際發生過的事——一個 commit、一段 diff、一條 finding。

產出的 PR body 有固定骨架，照這個結構讀，你就知道 reviewer 會看到什麼：

## What

<1 to 3 sentences: what this PR does, in plain terms.>

## Why

<The motivation. Link the spec if one governs this change, e.g. "Implements docs/specs/0007-rate-limiting.md". Reference the issue/ticket if known.>

## Changes

- <key change, grouped logically, not a raw commit dump>
- <key change>

## How to test / verify

- <the steps or commands a reviewer runs to confirm it works>
- <what they should observe>

## Risk & rollout

<Blast radius, migrations, feature flags, or rollback notes. Write "Low risk, no migrations, no flags." when that's true.>

## Notes for reviewers

<Anything that helps the review: a tricky decision, a deliberate tradeoff, an area wanting extra eyes. Omit if nothing.>

課程示範產出的 body 就把這幾個區塊都填滿了：它實作了什麼、設計理由、驗證紀錄、所有變更、串接方式、怎麼測、怎麼驗，以及給 reviewer 的提醒。有兩個細節值得記住：變更是依意圖分組的，不是把 git log 原封不動貼上；測試步驟是從真實的測試或行為推出來的，不會憑空發明。

Step 4：確認還有一個未提交的檔案，然後 commit

寫完 body 之後，它發現還有一個未提交的檔案。這件事的意義是：如果你這時候直接開 PR，那個檔案就不會包含在裡面。所以順序一定是先 commit、再看 PR。課程示範 commit 之後，PR 的內容就完整了。

Step 5：開 PR、merge，但每一步都先過你

這裡有個必須講清楚的界線。這個 skill 的產物是文字：PR 的 title 與 body，加上把 scope 上的 Document it 打勾。它本身不 commit、不 push、也不 merge。

This skill does not commit, push, or merge; it produces the prose (and ticks the `Document it` box per the closing gate above, the only scope edit it makes).

那示範裡最後 PR #2 是怎麼被合併的？是你在看完 body 之後，再請 agent 去執行的 git 動作。開 PR 是對外的、不可逆的一步，所以規則很清楚：只有在環境裡有 gh、專案有 remote、而且既有 PR 不存在時，它才會先show 出 body、問過你，才去建立 PR；要 push 之前同樣會先確認。如果沒有 gh 或 remote，它就只把文字給你，完全不碰對外動作。

課程示範的結果是：PR #2 合併進 main、分支被刪除、你回到 main 且是 up-to-date 的狀態。整條資料模型的路線到此正式結束（feature three closed）。

Step 6：盤點這次交付了什麼

收尾時，示範做了一次很值得抄下來的盤點——不是抽象的「做完了」，而是具體的清單：

  • 四個 commits、33 個檔案。
  • 九張表、五個 enum。
  • 手寫的 migration SQL、scoped query helper、seed script，以及 Drizzle 的串接。

這種盤點有兩個作用：一是讓你知道這次的 blast radius 有多大，二是幫你決定下一個動作。示範也在這裡誠實地留下兩個「not a big deal」的待辦——Vercel functions 的 region 問題、以及某條具體的 acceptance criterion，兩者都留給 feature 6 去驗。留待辦不是失敗，假裝沒有才是。

小結

document 從分支上的 commits 與 diff 生成文字，先確認你在哪條分支、領先幾個 commit、有沒有開 PR，再問你要寫哪一種文件；四種選項的差別是「給誰看、素材從哪來」，而在功能分支上開 PR 之前，PR 描述就是推薦的選擇。

PR body 的骨架是 What、Why、Changes、How to test / verify、Risk & rollout、Notes for reviewers；變更依意圖分組，測試步驟從真實行為推出來。這個 skill 只產文字、只打勾 Document it，不 commit、不 push、不 merge；開 PR 與 push 是另一段由你確認的動作。

示範的結果是 PR #2 合併進 main、分支刪除。收尾要用具體清單盤點交付內容，並誠實留下待辦給後續的功能。

到這裡，資料模型已經完整交付。鏡頭要轉向下一個功能：movie catalog 與 cache。它是一個規模更大的功能，不能直接 /develop，得先設計規格——下一節要用 architect 走完一輪決策訪談，把它寫成 spec。
