執行帳單：一次開 feed 的三毛五

Step 1/4 · 兩份帳單：Token 與 Runtime 經濟學

學習目標

用數量級講清楚 vibe 與 workflow 的執行成本差在哪裡，並說明為什麼 vibe build 並不是「太貴」，而是「架構上無法資助」。

前言：demo 過了，然後呢？

想像你剛把一個 app 推上線。demo 很漂亮，朋友都說酷，你貼到社群上也有人按讚。接著使用者真的來了，不是三五個，是幾百、幾千個。你打開雲端帳單那一刻，才發現有一筆錢是你從來沒算過的：不是主機、不是資料庫，而是每一次有人打開頁面時，你的 app 偷偷打出去的那幾通 AI 呼叫。

這筆帳的可怕之處，在於它在 demo 裡完全看不出來。demo 只有你一個人、開一次頁面，成本小到不值得注意。可是同一個動作被乘以每天的瀏覽量、再乘以每個使用者的使用次數，就會從「一杯咖啡」變成「一個薪水」。

這一節要做的，就是把這筆帳算清楚。它是判斷兩種 build 誰能活下來的關鍵證據：一個是什麼都現場算的 vibe build，一個是把計算結果先存起來的 workflow build。

先看單一動作：開一次 feed 要多少錢

先把範圍縮到最小：一個使用者「打開 feed」這一個動作，在兩種做法下各要花多少 AI 費用。

在 vibe build 裡，打開 feed 大約要花 0.35 美元。注意，是每一次，不是只有第一次。原因在於那個昂貴的模型呼叫就坐在請求路徑（request path）上，前面沒有任何快取擋著。所謂請求路徑，就是「使用者按下去」到「畫面出現」之間會經過的所有步驟；只要模型呼叫是其中一步，它就會隨著每一次開頁面被重新付一次錢。如果這個人還用了 vibe search，那又是另外 0.30 美元。

在 workflow build 裡，打開 feed 幾乎不花錢，因為它只是一次快取好的資料表讀取：結果先前就已經算好、存在資料庫裡，現在只是把它撈出來。同一個 vibe search，在那邊大約只要 0.015 美元，因為這條流程裡真正花時間的是資料庫查詢，模型只負責從資料庫已經找出來的清單裡挑選，工作輕得多。

單一動作vibe buildworkflow build
打開 feed約 0.35 美元，每次重算幾乎為零（快取資料表讀取）
vibe search約 0.30 美元約 0.015 美元

把這兩個數字並排看，差距已經很明顯了。不過它們還只是「一次」的價錢。真正讓人心涼的，是把它換算成月費。

換算成月費：一個普通使用者的用量

想像一個很普通的使用者：他不是很瘋，只是一個禮拜開個幾次 feed、搜尋個一兩次，也就是隨手 poke around 的程度。在 vibe build 裡，這樣的用量換算下來，大約是每個使用者每月 5 美元。在 workflow build 裡，同樣的用量不到十分之一美元，也就是幾個美分。

兩者大約差六十倍。而且這是在還沒有人動任何手腳、還沒有人做任何酷炫優化的情況下，純粹是架構選出來的結果。光是「每個使用者每月 5 美元」這一句，就已經寫好了 vibe build 的命運，原因我們稍後會講。

放大到規模：一百人、五萬人、一百萬人

單一使用者的錢看起來也許還能忍，但把它乘上使用者數，兩條線會岔得非常開。

使用者數vibe buildworkflow build
100約 500 美元 / 月約 30 美元 / 月
5,000約 25,000 美元 / 月約 400 美元 / 月
50,000約 250,000 美元 / 月約 4,000 美元 / 月
1,000,000約 5,000,000 美元 / 月約 70,000 美元 / 月

這張表有兩個地方值得停下來看。

第一，workflow 那一欄在 100 人時不是零。它本來就不能是零，因為那 30 美元主要是固定的基礎設施費用，也就是資料庫和主機，而不是 AI。這筆錢是「任何 app 都得先付的地板」，跟你會不會 vibe coding 沒有關係。地板的意思是：再便宜也有下限，但不會因為使用者變多就跟著失控。

第二，vibe 那一欄沒有地板，也沒有天花板。它不是一筆固定成本，而是「有多少頁面被看過」的倍數。看的人越多，它就一路線性往上，沒有停下來的理由。

換句話說，在 100 人的時候，vibe build 只是「有點煩」，workflow build 基本上免費。可是到了 5,000 人，那筆錢是一個人的薪水；到了 50,000 人，那是一個直接匯給模型供應商的募資輪。喔，而且老實說，vibe app 根本活不到 5,000 人，因為沒有人會願意為了看一份電影清單等四十秒，而且還要等第二次。

真正的重點：架構上無法資助

講到這裡，很容易下一個結論：vibe build 太貴了。但「貴」其實是可以修的問題：找到貴的地方、換掉它就好。真正致命的是另一句話：

vibe build 每個使用者每月要花大約 5 美元來跑。而地球上沒有任何一個消費者電影 app，能從每個使用者身上收到每月 5 美元。

把這句話想透，你就明白為什麼它不是「貴」，而是「架構上無法資助」（architecturally unfundable）。它的成本隨著頁面瀏覽量成長，營收卻永遠追不上那個速度，所以不存在任何一條成長曲線能把它救回來。每多一個新使用者，只是把這個洞挖得更深一點。

這種結構性的錯，不是把模型換便宜一點、把快取加上去就能在事後輕鬆補救的。它是在蓋的時候就已經注定了，就像房子的水管從一開始就埋在牆的錯誤那一側，之後再怎麼省水，牆還是得敲開。

最讓人不舒服的部分：沒有人做過這個決定

還有一件事要記得。那筆 0.35 美元的帳，不是誰開會拍板要花的。沒有任何人坐下來，把「即時生成」和「快取」放在一起衡量，然後選了即時生成。

這個決定，是一個以「demo 能跑」為目標在優化的程式產生器，在某個檔案的中間，在一個看起來很順的時間軸裡，默默替你做完的。

同樣一個決定，在 workflow build 裡卻是以另一種方式存在的：它被寫下來，當成一個「被否決的選項」，而且旁邊還註明了它的成本。同一個決定，一邊由機器默默做掉，一邊由人明確寫下，差別就在這裡。

小結

執行帳單算的是「跑起來要多少錢」。vibe build 每開一次 feed 花約 0.35 美元，而且每次都重算；workflow build 只是一次快取讀取，幾乎免費。換算到每月每人，是約 5 美元對不到十分之一美元，差約六十倍。放大到規模，差距只會更大，因為 workflow 有一筆固定的基礎設施地板，vibe 卻沒有上限。真正的問題不是貴，而是架構上無法資助：成本隨頁面瀏覽成長，營收永遠追不上。而這個決定沒有人做過，是程式產生器在「demo 能跑」的目標下默默做掉的。

這筆帳講的是「跑起來」的成本。但還有第二筆帳，而且它的結論跟直覺完全相反：workflow build 蓋起來的時候，其實用了更多 token。下一節就來拆那一筆，並說清楚多出來的 token 到底花在哪裡。
