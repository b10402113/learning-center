建置帳單：workflow 反而更耗 token

Step 2/4 · 兩份帳單：Token 與 Runtime 經濟學

學習目標

說出建置帳單的違直覺結論，並分辨那些多出來的 token 裡，哪些是真正的思考、哪些只是浪費。

前言：如果 workflow 更好，它應該更便宜吧？

上一節算的是「跑起來」的帳：vibe build 每開一次 feed 就要 0.35 美元，兩個版本差了大約六十倍。這一節換個方向，算「蓋起來」的帳。

這時候很多人腦中會冒出一個下意識的假設：既然 workflow build 在執行上那麼省，那在建置上應該也比較省吧？畢竟它更有效率、更制度化。

這個假設是錯的，而且剛好錯在相反的方向。你去看蓋的過程就會發現，workflow build 用的 token 明顯更多。這一節要誠實面對這件事，再把它拆開來看：多出來的那些，到底是必要成本，還是白花的。

老實話：workflow 真的用了更多 token

先把話說清楚，不閃躲：workflow build 用的 token 比 vibe build 多，而且多得不是一點點。

原因很直白。vibe build 的建置過程就是「打一句 prompt，讓 agent 自己跑」，幾乎沒有額外的來回。workflow build 不一樣：你要先 scope、要被訪談、要寫 spec、再拿 spec 去驗證實作。每一步都是實實在在的工作，也都花實實在在的 token。

所以問題來了：課程花了七節課推銷這個比較重的選項，結果它更貴？聽起來像在自我打臉。面對這個質疑，有兩件事必須分開講。

第一件事：實際上它花了我多少錢

先看帳面。兩個 app，都在一天之內做完，用的是一個 Claude Max 訂閱。就這樣。

唯一的「成本」，是撞到五小時使用上限幾次，然後去做別的事，等它重置。沒有意外帳單，沒有需要跟誰解釋的按 token 計費明細。

這件事值得講白，因為「AI coding 很燒錢」是個被反覆傳誦的恐怖故事，但在這次實際經驗裡它並不成立。建置階段的痛點不在現金支出，而在 token 花去哪裡，那才是會複利的東西。

第二件事，也是真正的重點：多出來的 token 多半是浪費

回頭追那些多出來的 token 跑去哪，答案不是「訪談」，也不是「spec」。是 context（上下文）。

具體來說有兩種浪費：

  • 有些 session 一直開著沒清，它就坐在那裡反覆重讀自己過期的對話歷史，而且是付最貴的模型價格，只為了做一個其實看三個檔案就能下的決定。
  • 有些最貴的模型在做粗活。那些交給中階模型就能做一樣好的事，偏偏用了推理能力最強、也最貴的那一顆。

這兩件事加起來，就是額外 token 的主要去向。關鍵在於：這不是「把事做對」的代價，而是「在沒有 session 衛生的情況下把事做對」的代價。

這正好是 Module 4 早就警告過的坑。談 context window 與 context rot 的那一節就說過：session 不清，品質會掉、成本會漲。結果這一節的作者自己還是踩了進去。

把這句話記牢：那筆帳不是 scoping 和 spec 造成的，是沒有清 session 造成的。兩者症狀長得很像，但解法完全不同。

讀那兩個 repo 時的小提醒

你下載的那兩份 repo，是這套 workflow 很早期的測試專案。很多東西，包括那些貴的部分，都是在那裡被摸出來的。它們不是你接下來要安裝的那一版；現在這套 workflow 之後又迭代了很多輪，而迭代的重點剛好就是上面這個問題。

也因為它們是早期版本，有些名字跟你之後會裝的對不上。最大的一個：repo 裡叫 ADR（architecture decision record，架構決策紀錄）的東西，現在改叫 spec（規格）。同一份產物、同一份工作，只是換了個更清楚的名字。你還會發現其他幾處改名。如果 repo 的資料夾名稱跟你終端機裡的 skill 名稱對不上，原因就在這裡，一律以現在的名字為準。

小結

建置帳單的結論跟直覺相反：workflow build 用了更多 token，因為 scope、訪談、寫 spec、驗證都是真工作。但實際支出並不痛：兩份 app 都在一天內、用單一 Claude Max 訂閱做完，只撞了幾次五小時上限。真正的教訓是：多出來的 token 大多不是思考，而是浪費，來源是沒清的長 session 反覆重讀過期歷史、以及最貴的模型在做粗活。這不是把事做對的代價，而是沒做好 session 衛生的代價。

既然問題出在「token 花去哪」，下一步就是學會自己看明細：哪一種 token 最貴、哪一種其實很便宜、該先從哪裡下手砍。下一節會帶你把課程附的分析工具跑起來，讀懂它印出來的帳單。
