三個降本修正：session 衛生、模型路由、subagent 起草

Step 4/4 · 兩份帳單：Token 與 Runtime 經濟學

學習目標

說出三個降本修正各砍掉哪一種浪費，並用可測試的判準決定什麼時候該套用哪一個。

前言：帳單看懂了，然後要改哪裡？

上一節你學會了打開帳單，看清楚每一種 token 值多少錢。但看懂明細本身不會讓帳單變小。真正的問題是：看到那筆浪費之後，你到底要動手改什麼？

這裡有兩股力量在拉扯。一方面，你不想放棄 workflow 帶來的東西——scope、spec、驗證，正是它們讓 app 便宜又好維護。另一方面，你也不想為了這些好處，去付那筆「沒清 session」的冤枉錢。這兩個願望聽起來衝突，但其實不衝突，因為它們處理的是不同的浪費。這一節把課程實際採用的三個修正攤開來，讓你用判準決定：面對眼前這個 session，該套用哪一個。

三個修正，各砍一種浪費

先把三個修正並排看清楚。重點不是背下它們，而是看懂「每一個各自負責哪一種浪費」。

修正它砍掉的浪費為什麼有效
Session 衛生長 session 反覆重讀自己過期的對話歷史狀態存在磁碟上的檔案，不在對話歷史，所以清掉不損失東西
模型路由最貴的模型跑去做粗活做決定需要深度推理，照著做不需要，兩者可以分流
Subagent 起草主線一直背著一份很長的文件長文件在 subagent 自己的 context 裡生成，只把摘要帶回主線

第一個修正是 session 衛生，而且它現在是 workflow 的責任，不再靠你的記憶。工具會判斷一段對話是不是已經跑得夠長、該清了，然後提醒你。做法是把每個階段拆進自己的 session：scoping 跑在自己的 session，architecting 開一個全新的，developing 再開一個。這件事之所以可行，是因為狀態活在磁碟上的檔案裡，而不是活在聊天歷史裡——所以清掉對話，你什麼都不會少。

第二個修正是模型路由：大模型留給決定，中階模型留給執行。那筆帳裡有一大塊，是最貴的模型在做它根本不需要那麼聰明就能做的事。把「照著已定方向執行」的工作交給中階模型，決策品質不受影響，帳單卻明顯下降。

第三個修正是讓 subagent 起草長文件。一份長文件如果待在主 session 裡寫，主線就得一路背著它、每次互動都重新讀它。交給 subagent 去寫，長文件在它自己的 context 裡成形，只把結果帶回來，主線就輕了。

怎麼決定該用哪一個

三個修正不是三個都要同時上，而是看眼前這個情境，問對應的那一題：

  1. 「這個對話是不是已經橫跨了不只一個階段？」——如果是（例如 scope 完接著 architect、又接著 develop），就該清 session，把下一階段拆出去。
  2. 「我現在要做的是「做一個決定」，還是「照著已定的方向執行」？」——是決定，就用大模型；是執行，就交給中階模型。
  3. 「接下來要產出的，是一份會很長的文件嗎？」——是，就派 subagent 起草，別讓主線背。

把這三題記住，你就不需要死背規則：每次動手前，先問這個當下的工作屬於哪一種浪費，那個對應的修正自然就會浮出來。

什麼時候這些規則會翻轉

三個修正都有它們不成立的時候，硬套反而更貴。

Session 衛生：如果你接下來還要密集地讀寫同一個檔案，清掉 session 反而逼你重新讀一次，那就不值得清。清 session 的前提是「狀態已經落到檔案」，而不是「先清了再說」。

模型路由：如果那個看起來像「執行」的工作，其實藏著判斷——例如你得先摸清一個函式庫的實際行為才能下手——那用中階模型可能做錯，重做的成本比省下的還高。判斷藏在執行裡的時候，就別省這顆模型。

Subagent 起草：如果產出很短，只有幾行，派一個 subagent 出去的來回成本，會比它幫你省下的還多。它是為了長文件而生，不是為了每一份小輸出。

小結

三個修正各自砍一種浪費：session 衛生砍「長 session 重讀過期歷史」，因為狀態在磁碟檔案裡、清掉不損失；模型路由砍「貴模型做粗活」，大模型決定、中階執行；subagent 起草砍「主線背長文件」。判準是三個問句——對話是否跨階段、這步是決定還是執行、產出是否長文件。合起來的結果是：同樣的產出，token 大幅下降，浪費的部分掉一個數量級，而好處全部保留。但要記住反例：同一檔案還要密集讀寫、執行裡藏著判斷、產出很短，這三種情況下硬套反而更貴。

這一課把兩份帳單講完了——一筆是 app 跑起來的成本，一筆是你蓋它的成本。而課程真正的轉折也在這裡：這三個修正後來被寫進了你即將安裝的那套 workflow 裡。下一節開始，你會親手把它裝起來，正式走進九步驟的 workflow 系統。
