Cross-check 與對 live DB 驗證

Step 6/6 · Greenfield：設計資料模型

學習目標

跑完這條收尾流程：把 spec 交給第二個模型 cross-check、消化它的發現，授權 Supabase MCP 接上 live 專案，把遷移在單一交易內套用，再用驗收條件把行為「跑」出來——包括 2 個 auth user 觸發 2 個 profiles、anon key 對九張表回零列、以及刪除使用者清空七張 owned 表。

前言：這一輪要得到什麼、動手前需要什麼

前面幾節把 spec 寫完、也自我檢查過了。但資料模型是整個 app 最重要的東西之一，所以課程不會就此收工，而是再做兩件事：讓第二個模型 cross-check 這份設計，然後把它真的套進一個 live 資料庫，用驗收條件證明行為。

動手前需要先具備的東西有三樣：一份已經寫好並自我檢查過的 spec；一個可以用的 Supabase 專案；以及已經安裝好的 Drizzle 與 Drizzle Kit。另外，因為 develop 會卡在 build plan 的第一步——「確認 region 與 DB 存取」被標成 blocking——所以這條流程的起點，其實是先解決「agent 碰不到真資料庫」這個問題。以下照著做。

步驟 1：把 spec 交給第二個模型 cross-check

spec 寫完後，agent 會自我檢查，然後問你：要不要讓另一個模型 cross-check 這份設計？因為資料模型太關鍵，答案是「要」。這一步要找的是那些「這個 spec 從沒指名、但建置的人會自己發明」的地方——也就是規格裡的空白與矛盾。

交出去之後，這一輪的收穫比預期大：它找到十筆發現，其中三筆是 blocking、六筆是真實但修起來很便宜的問題。幾個具體例子：

  • 沒有東西會寫入「帳號已刪除」的 audit 列：AC4 要求這筆紀錄要留著，但當時只規劃了一支 insert trigger。建議的修法是把它留在 TypeScript 裡寫，而不是再加一支隱藏的 trigger。
  • 遷移用的角色可能沒有權限在 auth.users 上掛 trigger：而函式需要 security definer，並且把 search path 釘住。作者坦言自己一開始也不確定這在指什麼，但接受「在 build plan 裡把函式的確切形狀寫清楚，並在第一步確認角色權限」這個做法。
  • RLS 在 Drizzle 與 Supabase 之間到底怎麼處理，第二個模型仍在追問。
  • 還有一些便宜的小修：numeric 2.1 的四捨五入、以及要維護 updated_at。

同意之後，就把十筆全部套用。課程的處理是「apply all ten」，三筆 blocking 與其餘一起在 spec 裡解決掉，然後才進入建置。

為什麼這裡一定要換一個模型？回想前面學過的 第二個視角：同一個模型會偏愛自己的輸出，也讀不出自己預期的版本沒寫、但其實存在的空白。十筆發現裡的那些坑，正是原作者看不見的那一類。

步驟 2：授權 Supabase MCP，讓 agent 碰得到 live DB

要套用並驗證遷移，agent 必須能操作真實的 Supabase 專案。它一開始會停下來說：「我碰不到真的 Supabase，apply 與 confirm 這些步驟我做不了。」這時候把 Supabase MCP 接上，它就能自己確認。

先看看目前 MCP 的狀態：

claude mcp list
# Supabase … pending approval

如果它指向錯的 URL、或還帶著 read-only 旗標，就先修設定檔，把 URL 改對、並拿掉 read-only：

// MCP.json
{
  "mcpServers": {
    "supabase": {
      "url": "https://mcp.supabase.com/mcp?project_ref=<project-ref>"
      // 拿掉 read-only，讓 agent 能寫入與套用遷移
    }
  }
}

接著開一個新的終端視窗跑 Claude，進 MCP 選單，選 Supabase 進行授權。瀏覽器會打開，登入後選好 organization、授權 Claude Code，這樣就算完成。授權成功後，用 claude mcp list 再確認一次狀態應該變成 connected。

有一個容易卡住的地方：即使 MCP 已連上，某些工具還沒有載入，這時需要重開 Claude Code，再重跑一次，新工具才會生效。課程特別提醒，重開不會讓你失去進度——因為 scope 與 spec 把狀態都存在外面，agent 能從上次停下的地方繼續。

如果連的是錯的帳號（登入時選錯了），organization 會找不到。課程的做法是：先讓它把 Drizzle、Drizzle Kit、Postgres 這些裝好，之後再重新授權、重新連線。

最後把專案接起來。MCP 需要的其實只是專案名稱——建一個新專案（或選既有的），把專案名稱交給 agent，它就能自己連結。

幾個成本與限制值得先知道：免費專案在所有 organization 加起來最多兩個，所以想開免費專案時，可能需要先開一個免費的 organization；付費大約每月 10 美元。建立資料庫時產生的密碼要立刻存好，弄丟會很麻煩。

步驟 3：把遷移套用到 live DB

連線就緒後，agent 會把遷移套用上去。這裡有兩個觀察點：一是它會在單一交易內，照著已 commit 的那份 SQL 檔原樣套用；二是套用成功後，它會把這件事記進 Drizzle 自己的 journal，並當場驗證 schema 是否 live 且正確。

預期會看到的回報是：applied、schema is live and correct。如果中途有錯，單一交易這一點很重要——它保證要嘛全成功、要嘛全不變，不會留下改到一半的資料庫。

步驟 4：seed starter deck

接著從已 commit 的 deck 檔把 starter deck 種進去，這裡是 20 部電影，帶著它們的 TMDB ID。課程的驗收條件之一（AC10）是：跑兩次之後，資料表裡仍然只有 20 列——也就是說這個 seed 是重複執行也安全的。看到「20 rows after both runs」就代表過關。

步驟 5：用驗收條件證明行為，而不是用讀的

接下來才是真正的重頭戲：把 spec 裡的 acceptance criteria 一條一條對 live 資料庫跑出來。課程反覆強調這一步的性質——是 proven by exercise, not by reading，用做來證明，不是用看來說服自己。

要看到的結果依序是：

  1. 透過真的 Supabase auth signup 路徑建立使用者，確認 trigger 會不會觸發。結果是 2 個 auth user 對上 2 個 profiles，兩邊的 ID 彼此吻合，而且中間沒有任何應用程式碼參與——這證明的是那支 trigger 真的在做事。
  2. 拿 anon key 去查九張表，每一張都回傳零列，包括明明有 20 筆資料的 movies。這證明 RLS deny-all 真的在擋。
  3. 刪除一個使用者，七張 owned 表會被清空，而 audit_events 不會跟著 cascade。這對應 AC4 的「證明 cascade、也證明 audit 不被 cascade」。

過程中很可能會遇到一個要修的地方。課程裡 advisor 指出其中一段 revoke 有可能弄壞 trigger，於是先修掉、再確認 trigger 仍然會 fire；修完之後，兩則 security definer 的警告也都消失了。

注意：刪除使用者與 revoke 權限這類操作會動到真實資料與權限，屬於不可逆或高風險的步驟。做完之後務必重新驗證那支 trigger 還會不會 fire——不要只看指令有沒有回成功。

步驟 6：收尾——存下驗證步驟、commit、修正 region

驗證跑完，把「由驗收條件推導出來的驗證步驟」存進這個 feature 專屬的 VerifyMD，因為這個功能大部分條件只能在 live 資料庫上證明，之後才回來逐條確認。然後把這些改動 commit 進 git。

最後剩一個小地方：spec 原本把專案 region 釘成 EU Central，但實際上開起來是 EU West。課程作者的處理很直接——回去告訴 architect data model「專案是 EU West，不是 EU Central」，把 spec 修正，免得之後每次都被這個不一致卡一下。

做完之後，scope 上會看到 data model 是 in progress、build 幾乎完成，剩下最後的 review 與 document。

小結

收尾流程有六個動作：先讓第二個模型 cross-check 並套用它的十筆發現；授權 Supabase MCP、修好 MCP 設定並把專案連起來；把遷移在單一交易內原樣套用並確認 schema live；seed 20 部電影且跑兩次仍是 20 列；用驗收條件把行為跑出來（2 auth user → 2 profiles、anon 回零列、刪 user 清空七張 owned 表、audit 不 cascade）；最後把驗證步驟存進 VerifyMD、commit、並把 region 修成 EU West。

這一輪的精神是「proven by exercise, not by reading」——資料模型有沒有做對，不是靠讀 spec 說服自己，而是靠對 live 資料庫跑出來給你看。

至此，資料模型從規格到 live 驗證整條走完。接下來這個功能要進入最後的 review 與 document，並在之後的 check verify 與 test 裡被長期保護起來——因為這是一個大功能，課程會第一次動用 check verify 把它從頭到尾檢查一遍。
