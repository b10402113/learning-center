實體與 Taste 模型：taste_vectors、ratings、profiles 與九表

Step 3/6 · Greenfield：設計資料模型

學習目標

走過五個具體的 schema 決定：taste profile 用一張 taste_vectors 表（每個 facet 一列）而不是單一向量欄；兩條來源不同的評分合進一張 ratings 表，用 rating 加 source 欄正規化；profiles 以 auth.userId 為鍵；第一次遷移就把九張表的目標模型立起來；並得知 cold start（缺 taste vector 列＝onboarding 未完成）與 auth.users → profiles 的 trigger 機制。

前言：決定「一次設計完整」之後，要真的把每一格填滿

上一節做了第一個大決定：一次設計完整目標模型，讓遷移切片落地。方向定了，但真正的難題才剛開始——因為「完整」是一格一格的具體選擇堆出來的。

這一節要走的就是那幾格。每一格看起來都只是「這個欄位要不要拆成另一張表」這種小問題，但每一格的選擇都會決定之後的形狀，而形狀一旦進到 live 資料庫，改起來就是一次遷移。所以課程裡的 agent 不是自己拍板，而是把每一格連著選項與理由一起丟回給作者確認。以下五個決定，就是這一輪對話裡最關鍵的幾個。

決定一：taste profile 存成一張表，不是一個欄位

第一個問題是：使用者的 taste profile 該怎麼存？

方案 A：taste_vectors 表方案 B：profile 上一個向量欄
形狀每個使用者有 n 列，每個 facet 一列（label 加 vector）一列一欄，profile 上放一個總體向量
起步tracer bullet 先只放一列「平均」直接放那一個向量
之後長大可以長成多個 cluster 的 facets，不需要改 schema要拆成 facets 時，得動既有表
代價讀寫要處理多列，多一層 join讀起來最簡單、最好教

課程選了方案 A，理由有兩層。第一層是品質：把口味攤成一個大平均，會「消融成一個糊掉的中心」——你很難從一個平均向量身上看出這個人同時喜歡兩種很不一樣的東西。第二層是變更成本：從「一個總體向量」改成「多個 facets」，那是一次 breaking change。

課程對方案 A 的評語很精煉：它「keeps the cheap path open and the good path free」——便宜的路還留著，好品質的路也不用多付錢。做法是 tracer bullet 階段先只存一列平均，之後要長成 clustered facets 時，再把列數長出來就好，schema 完全不用動。原文明確表態：「I much prefer the taste vectors table, with n rows per user.」

把這個決定寫進 schema，大概長這樣：

// source/db/schema/taste-vectors.ts
export const tasteVectors = pgTable("taste_vectors", {
  id: uuid("id").primaryKey().defaultRandom(),
  userId: uuid("user_id").notNull(),   // 對應 profiles.userId
  label: text("label").notNull(),      // 一個 facet，tracer bullet 先放 "average"
  vector: vector("vector"),            // 維度留給之後選定 embedding 模型的那個功能
});

注意關鍵在於「一個使用者可以有多列」這個形狀。label 這一欄就是之後長出 facets 的空間：今天只有一列 label 是 average，明天可以是好幾列不同 cluster 的 label，而 schema 不用改。

決定二：兩條評分來源，合進同一張表

第二個問題更常遇到：評分會從兩條路進來——一條是 swipe deck，另一條是 Letterboxd 的匯出，這兩條要怎麼存？

課程先問「所以該怎麼存？」，然後給出選擇：一個 rating 欄加一個 source 欄。核心理由是——這兩條路進來的東西，本質上是同一件事：「這個使用者對這部電影評了多少」。既然語意相同，就該落在同一張表，用 source 欄標記它是從哪條路來的。而且兩邊的分數尺度不同（swipe 是 like／dislike／skip，Letterboxd 是 0.5 到 5 星），所以要把兩條路都正規化成同一個數值尺度。

判斷這類問題的問句是：「這兩個東西在語意上是同一件事嗎？」是的話，一張表加標記欄，勝過開兩張形狀相似的平行表。平行表會讓之後每一個「讀這個人的所有評分」的功能，都得多寫一次兩表合併。

決定三：app 自己的使用者資料，掛在 profiles，鍵是 auth.userId

下一個問題是：app 自己的使用者資料要掛在哪裡？課程給的答案建立在一件事實上——auth.users 這張表是 Supabase 管的，Drizzle 管不到它。所以 app 不該把欄位直接塞進 Supabase 的地盤，而是自己開一張 profiles 表，並用 auth.userId 當鍵去對應。

這是一個值得記住的邊界：誰擁有那張表，就由誰決定它的形狀。Supabase 擁有 auth.users，所以 app 只讀它的 id，把其他所有 app 專屬的欄位放到自己的 profiles 裡。

決定四：第一次遷移就立起九張表

因為前面已經決定「完整目標模型、遷移切片」，所以第一次遷移的答案也順著定了下來。thin thread 是「登入 → 滑 starter deck → 拿到一組帶理由的 picks」，最少需要 profiles、movies、ratings、taste vectors、picks。至於 model usage（feature 6）、watchlist entries（feature 10）、import runs（feature 7），當下不必有，但既然之後一定會加，作者決定一起做進去——「so I'll just take all of them」。再加上 spec 0001 要求 import 與帳號刪除都要有 audit logging，所以又多一張通用的 audit events。加起來九張：

表它服務的功能第一次遷移的狀態
profilesapp 自己的使用者資料啟用（thin thread）
movies電影快取與身分啟用
ratings兩條路徑的評分啟用
taste_vectorstaste profile啟用
picks帶理由的推薦啟用
model_usagefeature 6 每日額度閒置，等 feature 6
watchlist_entriesfeature 10 收藏閒置，等 feature 10
import_runsfeature 7 匯入閒置，等 feature 7
audit_eventsspec 0001 的稽核紀錄先立起來

還有兩個順手一起做的決定：picks 表現在就帶上 state 欄，因為 feature 8 之後要用它記 seen／dismissed、feature 10 要用它記已收藏；而 audit 的紀錄則集中放進那張通用表，之後的 import 與帳號刪除共用同一套。

決定五：cold start 用「缺列」表示，不加布林旗標

模型快定型時，剩下一個場景問題：如果 feed 要用的 taste vector 還不存在或已經過期，該怎麼辦？課程的答案是把它當成一種狀態：沒有 taste vector 那一列，就代表 onboarding 還沒完成。使用者得先走過 onboarding，或先做一次匯入，那條向量才會被建出來。

這裡有一個容易走錯的岔路：多開一個 onboarding_done 布林欄。那樣做等於讓同一件事有兩個真相來源——布林說完成、但向量列不存在，兩者哪天不同步就麻煩了。用「那一列在不在」表示「完成了沒」，只有一個來源，不會說謊。

決定六：auth.users → profiles 用一支 Postgres trigger

最後一輪問題是：Supabase auth 在 auth.users 建立一列之後，誰負責建立對應的 profiles 列？答案是：在 auth.users 的 insert 上掛一支 Postgres trigger。這樣兩張表就永遠同步，而且不需要任何應用程式碼在中間插手。

課程還問了一句「那需不需要 foreign key／references？」，答案是「現在這個時間點不需要」。這也是完整目標模型下的一個刻意留白：不是所有關聯現在都要用資料庫層的約束綁死，先把應用層需要的形狀立起來，之後再視情況補。

小結

taste profile 存成一張 taste_vectors 表（每 facet 一列），因為單一向量欄一旦要拆成 facets 就是破壞性變更；兩條評分來源合進一張 ratings 表，用 rating＋source 正規化；app 的使用者資料掛在 profiles，鍵是 auth.userId；第一次遷移就立起九張表，四張先閒置；cold start 用「缺列」表示 onboarding 未完成；auth.users 的 insert 由一支 trigger 負責生出對應的 profiles。

九張表立起來了，但其中七張是「某個使用者擁有的資料」。這就帶出下一節的問題：在一個沒有測試套件、資料庫也無法幫你驗證 ownership 的專案裡，你要怎麼確保沒有一個功能會不小心讀到別人的資料？
