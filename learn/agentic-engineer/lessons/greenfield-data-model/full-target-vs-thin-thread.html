完整目標模型 vs Thin Thread

Step 2/6 · Greenfield：設計資料模型

學習目標

面對「現在要設計多少模型」這個岔路，你會在兩個選項之間做出有理由的選擇：一次把 11 個功能都需要的完整目標模型設計完、再讓遷移一片片落地，還是只先做 tracer bullet 需要的實體、其餘之後再補。你會說得出這個選擇對「後續速度」與「不破壞性變更」的取捨，也知道它在什麼情況下會翻盤。

前言：第一個丟回給你的設計問題

agent 把需求讀完、把模型的形狀摸清楚之後，它不會自己悶著頭決定，而是把第一個岔路丟回給你：這份 spec 現在要設計多少？

這個問題之所以為難，是因為兩股力量在拉扯。一邊是「現在就想看到東西動」——tracer bullet 的整個精神就是趕快打通一條最薄的線，先證明這條路走得通。另一邊是「之後不想回頭改地基」——資料模型是別的東西站上去的地方，現在少設計一塊，之後就得回頭動它。前一節講過，判準裡有一條是「之後不需要 breaking change」，所以這個決定其實直接關係到那段判準過不過。

兩個選項攤開來看

完整目標模型（migration sliced）只做 tracer-bullet 實體
現在設計什麼一次設計 11 個功能都會用到的所有實體，當成一個連貫的目標只設計 users、movies、ratings、taste profiles 這一輪用得到的
遷移怎麼落設計一次到位，遷移切片上線先落這一輪要的，其餘之後再開一個遷移
換到什麼之後新增功能時 schema 已經撐得住，跑得比較快最快看到 thin thread 動起來，前期工作最少
代價前面多花一點工，且第一版會有幾張暫時閒置的表之後補功能時，可能要動既有表、做遷移

課程裡的 agent 把這個選項說得很完整：「Full target model, migration sliced」，意思是要把 11 個功能都需要的每個實體，當成一個連貫的目標一次設計完，然後再讓遷移一片一片落地。課程提醒，這個做法剛好對上 scope 裡「之後不破壞性變更」的那條標準，同時又能保持 tracer bullet 很薄。另一邊的選項則是只做 tracer bullet：先有 users、movies、ratings、taste profiles，watchlist、imports、quotas 之後再補。

課程選了哪一邊，為什麼

課程的作者選了完整目標模型，理由講得很白：既然這些功能之後都會加，為什麼不現在就把資料模型設計成從一開始就支援它們？他的說法是「I'll just take all of them」，然後補一句——前面會多一點工作，但之後會跑得更快。

注意這裡藏著一個關鍵前提：他之所以敢一次設計完整目標，是因為 11 個功能已經列清楚了，scope 是穩的。完整目標模型的成本，是「現在多做的那些設計之後如果白做就浪費了」；但如果需求已經大致確定，這筆錢就花得值得。這也是為什麼這個決定不是無條件的好選擇，而是有前提的。

怎麼判斷該選哪一邊

把這個決定化成幾個可以直接問自己的句子：

  1. 「這個實體是不是某個一定會做的功能要用，而且現在不設計，之後得改既有表才塞得進去？」 如果是，就現在放進目標模型。會逼你改既有表的東西，正是要提早處理的。
  2. 「它是不是純外加？」 如果之後只要多開一張表、或多加一個 nullable 欄位，完全不用動既有表，那就可以延後。純外加的遷移不是 breaking change，不急。
  3. 「需求穩不穩？」 如果 11 個功能的方向還在漂、你根本還不確定要做哪些，那麼一次設計完整目標就是過早最佳化。先做 thin thread，等方向定了再擴。

第一、二句是判斷「之後補會不會變成破壞性變更」；第三句是判斷「你有沒有資格現在就賭這一把」。三者合起來，就把這個決定從「哪個聽起來比較厲害」變成「我的需求穩不穩、這個東西補起來痛不痛」。

反例：什麼時候「完整目標」反而是錯的

如果這是一個用完就丟的 prototype，或你正在做產品探索、根本還不知道 11 個功能是什麼，那「先設計完整目標」就不是穩健，而是把資源押在未知上。課程之所以選完整目標，是因為它有一套已經定案的 11 功能清單；少了這個前提，同一個選擇就會變成另一種錯誤。

還有一個容易誤會的地方：選完整目標模型，不等於現在把所有功能都實作完。它只是「設計」完整，「落地」仍然切片。第一次遷移會把整組目標模型立起來，但其中幾張表會先被標成閒置，等它的功能輪到時才啟用。課程原文的說法是，要設計成「which tables sit idle until it's their features turn」。所以這條路線其實是：一次設計到位，實作仍然一片片來。

那個「閒置標記」長起來大概像這樣——第一批遷移裡，兩組表並排，只是其中一組先不接線：

-- 0001_initial.sql（遷移切片）
-- thin thread: sign in → swipe starter deck → feed of picks
create table profiles       ( ... );
create table movies         ( ... );
create table ratings        ( ... );
create table taste_vectors  ( ... );
create table picks          ( ... );

-- idle until their feature turns
create table model_usage       ( ... );
create table watchlist_entries ( ... );
create table import_runs       ( ... );
create table audit_events      ( ... );

「設計完整」與「遷移切片」在這裡同時發生：表全部先立起來，但不是每張都有程式碼在用它。

小結

設計多少，取決於兩個條件：需求穩不穩，以及延後補起來會不會變成破壞性變更。需求已定、且這個實體以後補會逼你動既有表，就現在進完整目標模型；需求還在漂、或它只是純外加，就先做 thin thread。

課程選的是完整目標模型，但只設計完整，實作仍然切片——第一次遷移把整組目標模型立起來，其中幾張表先標成閒置，等對應的功能輪到才啟用。

既然決定一次把完整目標模型設計完，接下來就是把它填滿。下一節要走進幾個具體的 schema 決定：taste profile 到底該存成一張表還是一個欄位、兩條來源不同的評分怎麼合進同一張表、以及第一次遷移要立起哪九張表。
