資料模型即 Spec：architect data model 產出什麼

Step 1/6 · Greenfield：設計資料模型

學習目標

這一節要講清楚兩件事：一是 architect data model 這一輪只產出設計與規格、不產出程式碼；二是課程用什麼判準說「這個資料模型設計完了」。你會認出那條判準不是「表格長得漂亮」，而是「實體與關聯能不能承載兩條 onboarding 路徑的評分、存下一個 taste profile、產生帶理由的 picks，而且之後不必破壞性地改 schema」。

前言：為什麼不直接開始建表？

打開 scope 清單，你會看到 coding standards 和 tooling 都打勾了，只剩 data model 這一項還亮著 pending。看到這一格的直覺反應，通常是馬上打開編輯器開始寫 schema，恨不得五分鐘後就能看到第一張表。

但課程在這裡先停了一下，請 agent 跑 architect data model，也就是先產出設計，什麼都還不建。為什麼要忍住不寫？因為資料模型是整個 app 其餘部分站上去的地基，地基一旦打歪，之後每個功能都得付遷移的代價。這一節要先把「這一輪到底在產出什麼」與「怎麼算設計完了」講清楚，後面幾節才有共同的座標可以對照。

這一輪只交設計，不交程式碼

課程對這一步的界定非常直白。scope 上此刻唯一要打勾的東西，是「設計」或「規格」，而且是交給 architect 生成的那一份；真正的建置是下一步 develop 的事。

原文這樣說：

the only checkbox right here is the design or the specification for it that the architect will generate

不要把這讀成「先寫文件、之後再照著做」的官僚流程。它真正的作用，是把最貴的錯誤擋在最便宜的階段。建模的錯誤要改，是在關聯、欄位、enum 這一層改；但這些東西一旦散進程式碼、再灌進正式資料庫，同一個錯誤的代價會放大好幾倍——你得寫 migration、處理既有資料、還要祈禱沒有別的服務正依賴那個形狀。所以「先規格」不是為了流程好看，而是選一個修改成本最低的時間點來改。

「完成」的判準不是表格漂亮

那麼，什麼叫做設計完了？課程給的判準由一句話組成：這個模型只有在「實體與它們的關聯能承載兩條 onboarding 路徑的評分、能存下一個 taste profile、能產生帶理由的 picks，而且之後不需要 breaking change」的時候，才算完成。

把它拆成四個可檢核的條件：

  1. 兩條 onboarding 路徑都能落成評分。這個 app 的評分會從兩邊進來：一個是滑卡片的 swipe deck，另一個是使用者從 Letterboxd 匯出的歷史。
  2. 能存下一個 taste profile。系統要有一塊地方放「這個人的口味長怎樣」。
  3. 能產生帶理由的 picks。推薦不只要能推，還要推得出「為什麼推這部」，理由要存得下。
  4. 之後不必破壞性變更。現在設計的形狀，要能一路長到後面的功能，而不需要回頭改既有表。

這四條之所以有用，是因為它們可以拿來「否定」一個設計，而不只是「感覺差不多」。比方說，如果 picks 這張表只有 movie 而沒有放理由的欄位，那第 3 條就沒過。又比如，如果未來想把一個總體口味向量拆成好幾個 facets，結果發現那是一次 breaking change，那第 4 條就沒過。有這種能當掉設計的判準，比「看起來差不多」可靠得多。

先點名九個實體

課程在開場就把核心實體唸了一輪：users、movies、rating、taste profiles、帶理由的 feed picks、watchlist entries、以及 import runs。後面又補上 model usage 與一顆通用的 audit events 表，最後收斂成九張表：

profiles、movies、ratings、taste vectors、picks、model usage、watchlist entries、import runs、audit events。

先把它們點名，是為了讓後面幾節有對照表可以比。你現在只要記得：這九個名字會貫穿整個節點，之後每一節都會回來說其中幾張表該長什麼樣。

architect 的起手式

當你叫它 architect data model，它做的第一件事不是寫設計，而是先確認自己站在哪個版本上。它認出上一個 PR 已經合併回 main，於是在動手之前先 pull 最新變更。這一步的理由很單純：設計要站在最新的程式碼上，否則你設計的是一個已經落後的版本。

接著它把任務定位成三件事：一份建立在既有文字 stack 上的 feature design、採 tracer bullet 這種薄切片做法、workflow tier 設為 full。因為資料模型對應的是 scope 裡的第三個 feature，所以它也會把對應的 spec feature 連結起來。這些定位不是在填表格，而是決定它接下來要產出多厚的一疊設計。

產出物長什麼樣

最後交出的是那份 spec 檔。依課程裡的說明，它包含以下幾個部分：

Data model spec
├── Summary              # 這次要做什麼的總覽
├── Requirements         # 需求
├── User stories         # 使用者故事
├── Acceptance criteria  # 驗收條件
├── Decisions + rationale# 做過的決策，以及每個決策的理由
├── Data model sketch    # 模型草圖
├── Relationships        # 表與表之間的關聯
├── Columns              # 各表的欄位
├── Enums                # 固定的值集
└── Build plan           # 之後照著施工的計畫

這份 spec 不只是「一次性文件」。它裡面的 decisions 與 rationale 會記錄「為什麼是這樣而不是那樣」，所以之後接手的人不必重新推導一遍；而 build plan 則是下一步 develop 的施工順序，裡面的步驟之後會被標上 blocking 或 non-blocking，決定哪些非得先解決不可。換句話說，spec 是把「決定」與「還沒做的事」一起存下來的地方。

為什麼先規格、後實作，對 agent 特別有幫助

除了「便宜地改」之外，還有一個很實際的好處：中斷也接得回來。課程在講完這段之後，直接把對話視窗 clear 掉、重開一個新的，然後只說一句「develop the data model」，agent 就從它上次停下的地方繼續。

它為什麼接得回來？因為狀態不是記在對話裡，而是記在 scope 與 spec 裡。課程的說法是「nothing is lost」——因為有 scope、有 spec、有它一路在追蹤的東西，所以即使對話紀錄被清空，它還是能繼續。你可以把 spec 想成不只是給人看的文件，它同時是 agent 的記憶體：把「做到哪、決定了什麼」存在對話之外，下一次從這裡接上。

小結

architect data model 這一輪唯一的產出是設計與規格，程式碼留給後面的 develop。之所以先規格，是因為建模錯誤在這一層最便宜，而且狀態存在 spec 裡，對話清空也接得回來。

判準不是表格好看，而是四條：兩條 onboarding 路徑都能落成評分、存得下一個 taste profile、產生得出帶理由的 picks、而且之後不必破壞性變更。用這四條去當掉不完整的設計，比憑感覺可靠得多。

既然判準是「能不能承載所有功能、而且之後不必破壞性變更」，那下一個問題就無法迴避：這份模型現在到底要設計多少？是把 11 個功能都需要的完整目標模型一次設計完，還是只先做 tracer bullet 需要的那幾張表？下一節就在這兩個選項之間做決定。
