同一句 Prompt，兩個版本：這場實驗在測什麼

Step 1/5 · A/B 實驗：Vibe Build vs Agentic Build

學習目標

說出這場 A/B 實驗的受控條件（同一天、同一個人、同一批模型）與兩個版本的差別，並解釋為什麼「demo 會動」不等於「上線撐得住」。

前言：那則讓你心動的推文

你一定看過這種推文：貼一段時間縮時影片，畫面裡一個 App 從無到有，配上一句話——「我用一句 prompt 生出了一個完整的電影推薦 App」。幾個小時的活，看起來幾分鐘就做完了。底下的讚數很高，你自己看了也有點被燒到，想說「原來現在可以這樣寫程式」。

這股心動是真的，而且它不是錯覺。但有一件事，那些推文永遠不會告訴你。它不會告訴你，當同時有幾十個使用者打開這個 App 時會發生什麼；也不會告訴你，每開一次頁面要燒掉多少錢；更不會告訴你，六週後你想改一個小功能、重新打開這份程式碼時，會有多痛苦。

這門課接下來要面對的，就是那個沒人願意用資料回答的問題：當 AI 才是寫程式的那一方時，認真的工程還重要嗎？還是那只是老習慣在拖慢你？每個人都有意見，卻幾乎沒有人做過對照實驗。所以講師自己做了一個——這一節先讓你看清楚這個實驗是怎麼設計的，以及它到底在測什麼。

一個 App，建兩次

實驗的對象是一個電影推薦平台。功能很具體：你匯入 Letterboxd 的評分、或滑過 20 部電影來完成 onboarding，它給你一份個人化的推薦 feed；另外還有一個「Vibe 搜尋」，你打一句像「適合下雨的星期天看的慢節奏科幻片」，它就給你真的片單。

App 只做一個，但建兩次。而且條件是刻意對齊的：同一天、同一個開發者（就是講師本人）、兩個版本都能用到同一批 AI 模型。這樣設計的目的，是把「工程方法」以外的變數壓到最低，讓最後的差異只剩下一件事——你怎麼用這些工具。

第一個版本是純粹的 vibe coding：他把想要的講一遍，agent 把它生出來，他說「不錯，再加這個」，agent 就再加。整個過程沒有任何計畫被留在磁碟上、沒有任何決定被寫下來、也沒有測試。這正是多數人每天使用這些工具的方式，而且他還把當時最強的模型給了這個版本。第二個版本，則是課程後面要安裝的那套 agentic-engineering workflow：先 scope，在寫任何程式之前把每一個 load-bearing 的決定捕捉起來，並且不讓 agent 自己發明他沒選過的東西，另外還有測試與 migration，整套紀律都在。

關鍵在於：vibe 版沒有爛

如果 vibe 版生出一團垃圾，這個實驗就沒什麼好看的。但事實剛好相反——它做出來的是一個能跑的 App，功能都對，而且如果講師拿它來 demo 給你看，你會覺得很厲害。他自己也說，他其實有被說服。

這就是整個實驗最有趣的地方。問題從來不是「它會不會動」，而是「demo 之後會怎樣」。100 個使用者的時候呢？5,000 個的時候呢？或者，當你六週後回來、想改動某個東西的時候呢？

Vibe 版的問題不在那一場 demo 裡，而在 demo 之外的那些時刻。它能在你面前流暢地跑完一遍，但你沒辦法從那一遍裡看出它撐不撐得住真實世界的重量。這就是為什麼「demo 會動」是一個這麼危險的證據——它證明的是最容易證明的那件事。

Demo 藏起來的三件事

那 vibe 版確實在做的事情裡，有哪些是 demo 遮住的？至少有三件。

Demo 裡看不到的背後其實是什麼問題
同時有更多人載入 App 時併發負載下，每個人的請求都在搶同一份昂貴資源
每開一次頁面要花多少錢看不到 token 成本，只看得到畫面漂亮
agent 在檔案中間偷偷做的決定一個沒人拍板的選擇，會變成上線後每個月都付的帳單

第三件事尤其關鍵，因為那個決定不是「講師決定要多花錢」，而是 agent 在生成檔案的過程中自己選的，只是當時沒有任何人停下來問「這樣好嗎」。它就在那裡發生了，而縮時影片看起來還是很棒。

Demos hide economics. They hide load times, token costs, and more.

所以講師決定停止 demo，改成讓你看它真實跑起來的樣子。這就是下一節要做的事。

小結

這一課設定了整場對照實驗：一個電影推薦 App，同一天、同一個人、同一批模型，建兩個版本。Vibe 版是純 vibe coding——描述、生成、再追加，沒有寫下來任何決定或測試；workflow 版則是先 scope、把每個 load-bearing 決定在動手前捕捉起來、用測試與 migration 護住。關鍵不是 vibe 版會不會動（它會動，而且 demo 起來很帥），而是 demo 藏住了併發負載、每次載入的成本，以及一個 agent 偷偷做下、沒人拍板的決定。評斷一個 build，要看它在生產環境和未來改動下的樣子，不是看 demo。

實驗的規則你已經知道了。接下來的問題是：當你把 vibe 版放到真實使用情境裡，它到底會怎麼壞？下一節我們就打開它，看那個 40 秒的 feed 與「三開分頁三個答案」是怎麼發生的。
