Workflow-First：先決定，再讓它動手

Step 4/5 · A/B 實驗：Vibe Build vs Agentic Build

學習目標

照著 scope → architect → develop → check/verify → review → test → sync 的順序走一遍。走完你能說出每一層為什麼存在、產出什麼，並看到一個 load-bearing 的決定如何變成一條寫進 repo 的驗收條件。

前言：要換的是流程，不是模型

上一節我們在 vibe 版裡抓到四個殺手，也下了結論：問題不在 AI 打錯字，而在那些「該有人拍板的大決定」從來沒被做過。那要怎麼讓決定真的發生？

換一顆更聰明的模型是沒用的。vibe 版拿到的已經是最強的模型了，它照樣把該問的問題默默吞掉。要換的是流程：把每一個該由人拍的決定，在寫任何一行程式之前就浮出來、做出來、寫下來。

這一節看的是同一個 prompt、同一個 App，套上 agentic-engineering 的流程後長什麼樣。講師刻意只講概要，因為每個 skill 後面都有一堂完整的課；這裡要抓的是整個流程的形狀。

前置條件很單純：你手上有一句和 vibe 版一模一樣的 prompt（電影推薦 App 那句），再加上這套 workflow 的 skill。做完之後，你會多出一份落在 repo 裡的 spec，而程式碼能一路對得回那份 spec。

流程全貌：七個動作

把流程攤開，它比「幫我建一個 App」多了好幾步，但順序是有理由的。底下七步就是它實際跑的順序。

  1. scope：把同一句 prompt 丟進去。它不寫程式，先訪談你：這個 MVP 的邊界在哪、做給誰用、什麼是明確不做的。然後把你講的內容寫成一份計畫檔，功能排了先後順序，而且地基優先：技術棧、資料模型、設計系統，全都排在功能之前。先有地，才輪得到蓋房。
  2. architect：把焦點對準資料系統。它不自己發明選擇，而是一次問你一個問題，每題附上真實的選項和一個它推薦的答案。那個「35 分錢的快取決定」（vibe 版在一個巨大檔案中間默默做掉的那個），在這裡重新變回一題擺在你面前的問題，連同取捨一起攤開。
  3. develop：照 architect 規劃、已經 spec 化的內容來建置。它帶你走流程，主導權還在你手上；它不會去發明還沒被決定的東西，那正是 vibe 版的病根。
  4. check / verify：把真正的 App 跑起來，用真實的請求證明每個功能對得上 spec 的驗收條件。若設定了 Playwright MCP，還能讓 agent 直接在瀏覽器裡點給你看。
  5. review：把寫好的 spec 交給另一個 agent 交叉驗證，取得第二個視角。
  6. test：替這次的改動寫測試套件，讓一次性的驗證變成以後都還有效的保護。
  7. sync：記錄這次交付了什麼，讓下一個 session 能從這裡接上。

關鍵的一步：決定變成驗收條件

七步裡真正扭轉局面的是第二步，以及它後面那句話：你選的答案，會變成一條驗收條件，寫進一份落在 repo 裡的 spec。

這句話為什麼值錢？因為它把一個「決定」從某個人腦中的念頭，變成一份檔案。變成檔案之後，就有三個對象讀得到它：未來的你、你的團隊、還有 agent 本身。

前兩者拿它來回答「當初為什麼這樣做」。第三者則能被要求照著做，它不再是自己猜，而是有一條明文寫下的條件等著被兌現。

回頭看 vibe 版的失敗，差別就清楚了。那個快取決定其實不算「做錯」，而是從來沒被當成一題問題問出來。它在一個大檔案的中間被默認掉，沒有任何地方記錄「我們討論過、我們選了這個、這是理由」。workflow 版把同一題搬到桌面上，讓它有個名字，也有個去處。

Vibe build：預設值Workflow build：決定
快取問題檔案中間默默默認，沒人討論螢幕上一題附選項與取捨的問題
決定去處不存在，只是程式碼的一個行為寫進 spec，成為驗收條件
誰讀得到只能從程式碼反推，常常推不出來未來的你、團隊、agent 都讀得到
agent 的角色自己填滿沒人決定的空位被綁在那條明文條件上

做完之後長什麼樣

走完這一輪，可以驗證的結果很具體：

  • repo 裡有一份 spec，上面是有編號的驗收條件。
  • 程式碼不是憑空長出來的，每一段都對得回某條條件。
  • 測試是照著那些編號命名的。
  • 有一份 sync 記錄說明這次交付了什麼。

這比「一句話生一個 App」多了很多步。這些步數買到的東西，下一節會攤開來看：同一句 prompt、同樣三個功能，兩邊的工程結果擺在一起會差多少。

小結

Workflow-first 的順序是 scope → architect → develop → check/verify → review → test → sync。scope 先訪談你、把計畫寫成檔，地基（技術棧、資料模型、設計系統）排在功能之前；architect 一次一題、附選項與推薦，把 vibe 版默默默認掉的快取決定逼上檯面；你選的答案會變成一條寫進 spec 的驗收條件，未來的你、團隊與 agent 都讀得到、也都得兌現；develop 只做被決定的事，check/verify 用真實請求證明它會跑，review 交給另一個 agent 交叉驗證，test 把驗證變成回歸保護，sync 記下交付內容。步數是多了，但每一步都在把事情從「預設值」換成「決定」。

流程的形狀你看過了。真正要說服你的是它實際買到了什麼。下一節把兩份程式庫並排攤開，同一句 prompt、同樣三個功能，看看那些多出來的決定，在程式碼裡長成什麼樣子。
