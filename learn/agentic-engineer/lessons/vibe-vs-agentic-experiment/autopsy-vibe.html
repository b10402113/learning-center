驗屍 Vibe 版：四個架構級殺手

Step 3/5 · A/B 實驗：Vibe Build vs Agentic Build

學習目標

從 vibe 版程式庫指出四個架構級殺手（請求路徑中的貴模型呼叫、沒有退避又吞錯的 TMDB 平行驗證、沒有交易的先刪後插、完全沒有測試與 migration），並說明「每一行單看都乾淨、失敗卻在架構層」是什麼意思。

前言：症狀看過了，現在看病因

上一節我們看到 vibe 版 feed 的症狀：開一次要 40 秒、三個分頁三個答案、每開一次都在燒錢。但症狀不是原因。同一種症狀可以來自很多地方，要真的修它，你得知道它是在哪一行被寫出來的。

這一節我們就把 vibe 版的程式庫打開，像一位資深審查者那樣讀它——不是讀「有沒有排版錯誤」，而是讀「這些壞掉的行為，各自住在哪個檔案、哪一行」。講師把找到的東西分成四個，直接叫它們「殺手」。我們一個一個看。

殺手一：貴模型被放在請求路徑裡

第一個殺手在 src/lib/engine.ts，這是整個 App 的媒合引擎。它的設計很合理：Claude 先提出候選（片名、年份、一句話理由），回傳的一切都被當成未經驗證，一定要先過 tmdb.ts 驗證才能顯示。檔案最上面的註解把這個意圖寫得很清楚，而且還特別點出「保證是放在驗證層，不是放在 prompt 裡」——這其實是一個很好的想法。

/**
 * The Reel matching engine.
 *
 * Claude proposes candidates (title, year, one-line personal reason);
 * everything it returns is treated as UNVERIFIED and must pass through
 * tmdb.ts validation before display. The engine is prompted to recommend
 * real films it is confident exist — but the guarantee lives in the
 * validation layer, not in the prompt.
 */

const MODEL = "claude-opus-4-8";

問題出在第 16 行那個 MODEL 常數。它被硬編成一顆最貴的模型。而真正在生成 feed 的 generateFeedCandidates，用的就是這顆模型，再加上 16,000 的 token 上限與開啟「adaptive thinking」（讓模型自己決定要不要多想一輪）。單看這一段，沒有任何一行是錯的：變數命名清楚、結構乾淨、連註解都寫得很負責任。

要看到殺手，得把鏡頭拉遠。feed 頁面有一個 useEffect（大約在第 34 行），它在 component 掛載時就呼叫這個函式、而且整支檔案裡沒有任何快取。於是「整個 App 最貴的一次運算」被放在「每一次頁面載入」的路徑上，跑一次大約 35 分錢。

這個 35 分錢的數字，下一節會看到它在規模上有多可怕。此刻先記住一件事：貴不是問題，「貴 × 每次都跑」才是。

殺手二：沒有退避、還會吞錯的平行驗證

第二個殺手在 src/lib/tmdb.ts 的 validateCandidates。它的工作是拿一批候選去 TMDB 驗證片名是否真實存在。做法是一個 Promise.all，把大約 24 個候選全部平行丟出去。

三個毛病疊在一起。第一，沒有 rate limiter（速率限制），一次打這麼多請求出去，等於在挑釁對方的 API。第二，沒有 backoff（退避）也沒有 retries（重試）——對方一旦回「你太快了」，這裡不會等一下再試。第三，也是最陰的：它的 catch 區塊只是回傳 null。這代表一次被拒絕的驗證會無聲無息地消失。當 TMDB 開始推回請求時，你看到的不是錯誤，而是候選「變少了」——catch 區塊其實完全照著它被寫的樣子在工作。

同一個檔案往上數到第 44 行，還有一個獨立的問題：API key 被當成 query string 參數串在請求 URL 上。這意味著這把 key 會出現在它到 TMDB 之間每一份 log 與每一個 proxy 裡。這跟架構無關，是單純的資安失誤，但同樣是「沒有人停下來檢查」的產物。

殺手三：沒有交易的先刪後插

第三個殺手在 import 流程的 route.ts。第 35 行有一句註解，寫得理直氣壯：

Replace any previous import wholesale. The export is the source of truth.
（整批取代上一次的匯入。匯出檔才是真相來源。）

緊接著第 36 行，它真的把這個使用者先前的所有評分全部刪掉；然後第 45 到 48 行，手工迴圈處理 500 筆資料，逐一插入。問題是：沒有東西包住這串刪除與插入。它不是一個交易（transaction）。所以如果跑到一半、某一塊失敗了，刪除早就已經發生，而且沒有任何 rollback 可以把資料還原——使用者的評分就這麼不見了。

更耐人尋味的是，agent 甚至寫了一句註解，精準描述了它正在做的事。它知道自己在做什麼，但沒有人檢查這是不是可接受的，因為從頭到尾沒有人在做「決定」這個動作。

殺手四：找不到的東西——測試與 migration

第四個殺手最特別：它不在任何檔案裡，而在「缺少的東西」裡。試著在整個 repo 找一個測試——沒有，一個都沒有。再找一個 migration 資料夾——也沒有，Supabase 底下只有 schema，85 行手寫 SQL，沒有版控的遷移紀錄。

而偏偏被漏掉的，正是最該被測的那種程式碼：Letterboxd 的 CSV 解析、片名的模糊比對。這些都是純函式（pure function），邊界情況多到數不完，卻一個測試都沒有。CSV 裡多一個逗號、片名大小寫不同、別名對不上——每一種都可能出錯，而沒有任何一個被護住。

每一行都乾淨，失敗卻在架構層

把四個殺手攤在一起，會浮現一個很重要的結論：不是 AI 寫了爛程式。你隨便挑十行程式碼單獨來看，它們都是乾淨、可讀、命名有意義的。逐行來看，這份程式庫是好的。

但失敗全部發生在架構層：那個貴的呼叫被放在哪裡、併發負載下會怎樣、跑到一半失敗會怎樣、使用者是 40 筆評分還是 400 筆。這些不是「某一行寫對寫錯」的問題，它們是大決定。而在這個 build 裡，每一個大決定都被一個「為了讓 demo 跑起來」的程式碼產生器，隱含地做掉了。

Vibe coding doesn't produce bad lines. It produces undecided architecture.
（vibe coding 不會產出壞的單行，它產出的是「沒有被決定過的架構」。）

這句是整個模組的中心。它的意思是：你看到的問題，不是打字打錯了，而是根本沒有人坐下來決定「這顆貴模型該放在哪」「匯入可不可以丟資料」。程式碼只是把那些沒做的決定，用預設值填滿而已。

小結

Vibe 版的四個架構級殺手：一、最貴的模型被放在 feed 的請求路徑上、每次載入都跑約 35 分錢；二、TMDB 驗證用沒有速率限制、沒有退避重試的平行請求，catch 又直接吞錯讓候選消失，API key 還串在 URL 上；三、匯入是沒有交易的先刪後插，中途失敗就丟資料、無法回滾；四、整個 repo 沒有任何測試、也沒有 migration，只有 85 行手寫 SQL。但重點是：每一行程式單看都乾淨，失敗全在架構層——那些「大決定」沒有人做過。這就是「vibe coding 不產出壞的單行，它產出未決的架構」。

看到這裡你應該很不舒服：這些都是明擺著的工程失誤，為什麼會發生？答案不是「AI 不夠聰明」，而是「流程裡沒有讓人做決定的位置」。下一節我們換一個做法——在同一個 prompt 上，看看一個把人放進決策迴圈的流程，長什麼樣子。
