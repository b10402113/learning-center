驗屍 Workflow 版：每一行都是某個決定的結果

Step 5/5 · A/B 實驗：Vibe Build vs Agentic Build

學習目標

對照 vibe 版逐項說明 workflow 版同三個功能各自用哪個決定解掉哪個殺手，並分辨「用 prompt 要求它乖」與「用結構讓它不可能亂來」這兩種防線的差別。

前言：把兩份程式庫擺在一起

前面三節，我們先看了 vibe 版怎麼壞（40 秒、三個答案、約 35 分錢），再打開它的程式找出四個殺手，然後看過 workflow-first 那條「先決定、再動手」的流程。現在是最後一步，也是整個實驗的兌現時刻。

講師把兩份程式庫並排攤開，同一句 prompt、同樣三個功能——feed、匯入、Vibe 搜尋——一邊是 vibe 版，一邊是工程過的版本。他要回答的問題只有一個：那些多出來的步數，到底在程式碼裡買到了什麼？

先把答案說在前面：workflow 版的程式庫明顯更大。但這節要你判斷的，不是「行數多寡」，而是那些多出來的行，到底是裝飾，還是承重。

功能一：feed——貴的呼叫根本不在路徑上

還記得 vibe 版的 feed 嗎？每一次載入都在請求路徑裡即時呼叫最貴的模型。workflow 版把它整個翻過來。評分被轉成一個「口味向量」，然後用一次資料庫呼叫加上向量索引，在真實的電影目錄裡找出跟你口味最接近的片，結果寫進一張 recommendations 表。

那開啟 feed 的時候發生什麼事？get feed 這個 action 就只是讀那張表——整條讀取路徑裡沒有任何模型呼叫。所以這一頁的成本實質上是零，速度就是 Supabase 把資料回傳給你的時間。跟 vibe 版的 40 秒比，這是兩個世界。

AI 還在，但它只負責一件小事：替每個推薦寫一句「為什麼這適合你」。關鍵在細節——這是一顆 Sonnet（不是 Opus 或最貴那顆），而且是一次批次呼叫寫完整份 feed、思考功能關掉，並且只在你口味真的變了、或你自己按重新整理時才跑，絕不在頁面載入時跑。

讓這一切成立的那段程式，在 src/lib/feed/generate.ts，它把「什麼時候該重算」寫成一個有名字的函式：

// The feed is stale when there is no cached feed yet, or the taste profile was recomputed since
// the feed was built. Compared at read time in getFeed; nothing is stored for it.
export function isFeedStale(computedAt: string | null, maxGeneratedAt: string | null): boolean {
  if (!maxGeneratedAt) return true; // no cached feed
  if (!computedAt) return false;
  return Date.parse(computedAt) > Date.parse(maxGeneratedAt);
}

講師對它的評語是「the cache refresh is a decision with a name」——快取更新變成一個有名字的決定。它不再是散落在某個檔案中間、沒人看過的一行行為，而是一個明明白白、可以被指著討論的函式。

那個被否決的選項，現在住在 repo 裡

這個「有名字的決定」是從哪來的？答案是 architect 問的那一題，而兩個答案都被寫下來了。在 ADR 0007 的「Options considered」裡，你可以看到選項一（被選中的）是快取、只有在 profile 改變時才重新生成；選項二是每次載入都即時算，不設快取。選項二的代價被老老實實寫著：

- Con: pays a multi-second Sonnet call and its cost on every single page load, and reshuffles the picks and reasons each time so the feed is never stable, which is both expensive and a worse experience. It also risks the serverless duration limit on every render, not just on regeneration.

把這段話讀一遍，你會發現它描述的正是 vibe 版的下場。差別在於：在 workflow 版裡，它不是被出貨的程式碼，而是一條被否決的意見。vibe 版用 40 秒和 35 分錢親身示範了這個選項；workflow 版把它留在文件裡，當成「我們考慮過、而且拒絕了」的紀錄。

功能二：匯入——「永不丟資料」是先寫下來的條件

vibe 版的匯入是沒有交易的先刪後插。workflow 版完全不一樣。瀏覽器端先解析 CSV，然後一次送 100 筆（你可以在 chunk 大小裡看到這個數字）。這樣做的好處是：按重試時，它會接續同一份匯入，而不是從頭再來。在 import 的 actions.ts 裡有一個 retry helper，每一塊在往上報錯之前，自己就會先帶退避重試一次。

更關鍵的是它什麼都不刪。符合的資料用 movie ID 做 upsert（有就更新、沒有就插入），所以跟 vibe 版的先刪後插相比，這裡沒有任何一段時間你的評分是不存在的。它甚至處理了一個很細的邊角：如果匯出檔裡有兩筆資料指向同一部電影（例如重映或別名），兩筆若在同一句 SQL 裡撞上，Postgres 會拋錯、整塊失敗，而因為重試會重播一模一樣的輸入，這份匯入就會永遠卡死。workflow 版先做了去重（dedupe）來避開這個。

講師說，這是資深工程師水準的程式碼，而且不是因為有人踩過這個坑才補上的。它之所以在這裡，是因為架構的驗收條件裡早就寫著一條：「匯入永遠不能丟失資料」——而且那條條件是在任何會被弄壞的程式碼存在之前就寫下的。

功能三：Vibe 搜尋——從「要求它乖」到「讓它無法亂來」

Vibe 搜尋在 workflow 版裡是一條管線，整個讀得完的長度只有五行：先拿 profile 相關的資料，判斷使用者想要什麼，挑出候選，記錄，回傳。拆開來看：一顆便宜的小模型把使用者的查詢解析成結構化的意圖（年份、片長，甚至 mood、theme、tone 這種「感覺」）；接著用向量／embedding 搜尋，從真實目錄裡拉出真的候選；最後一顆中等模型挑出三到五部——而它只被允許從剛剛交給它的那份清單裡挑。

這裡有一個很值得停下來看的細節。select.ts 裡告訴模型「不要發明電影，只能從提供給你的真實電影裡挑」。但講師點出：這只是在「請求」它乖，跟 vibe 版做的事情一模一樣。真正不同的是——這裡同時定義了「一部電影的 schema 長什麼樣子」。因為在整個程式路徑上，movie 的結構被固定下來，模型在結構上就不可能捏造出一部電影。

… the architecture gives it no way to misbehave. That's the difference between a rule and a guarantee.
（架構讓它根本沒有辦法亂來。這就是「規則」與「保證」的差別。）

這一句是整個模組最值得帶走的工程觀念。「規則」是你用文字拜託它別亂來，它大多數時候會聽；「保證」是你把結構設計成它即使想亂來也做不到。vibe 版有的是前者，workflow 版給的是後者。

原本缺的那兩樣，這裡都有

還記得 vibe 版的殺手四是「缺少的測試與 migration」嗎？workflow 版兩樣都在。專案設定了 Vitest，替最容易壞的邏輯——CSV 解析、口味計算——寫了測試檔。而且注意測試怎麼命名：像「compute taste profile below the floor, AC7」這樣，用驗收條件的編號來命名，讓每一個測試都能指回當初那個決定。另外，資料庫有六個版本的 migration，可以看到資料系統是怎麼隨著每個功能升級的。

比較大的程式庫，但不是裝飾

把所有東西收在一起，workflow 版的程式庫比 vibe 版大上不少。但如果你跟著講師把那些多出來的行走一遍，你會發現沒有一行是裝飾。每一行多出來的程式碼都是承重的，而且每一行都追得回一個「在動手之前，某個 skill 問過我的問題」。

小結

同一個 App、同樣三個功能，workflow 版把每個 vibe 殺手都換成一個「刻意做下的決定」。feed：口味向量用一次資料庫呼叫檢索、結果寫進 recommendations，讀取路徑零模型呼叫；Sonnet 批次寫理由、只在口味變了才跑，而那個快取決定有了名字（isFeedStale），被否決的即時生成則留在 ADR 007 裡當成「拒絕過的意見」。匯入：分塊加退避重試、upsert 加去重，因為「匯入不能丟資料」是動手前就寫下的驗收條件。Vibe 搜尋：便宜模型解析、向量檢索、中等模型只從清單裡挑，而真正防幻覺的不是那句 prompt，是固定下來的 movie schema——這就是「規則（rule）」與「保證（guarantee）」的差別。程式庫更大，但每一行都承重、都追得回一個決定。

兩份程式庫都看完了，這一課的對照也完成了。你可能會想：好吧，工程版比較好，但它到底貴多少？多出來的那些步數、那些 token，該算進哪一本帳？下一課我們就來結這筆帳——分開算「執行成本」與「建置成本」兩份帳單。
