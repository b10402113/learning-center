驗屍 Workflow 版：每一行都是某個決定的結果

Step 5/5 · A/B 實驗：Vibe Build vs Agentic Build

學習目標

把 workflow 版和 vibe 版的三個功能逐一對照，看看每個工程決定如何解掉一個問題，也分清楚「用 prompt 要求它乖」和「用結構讓它無法亂來」有什麼不同。

前言：把兩份程式庫擺在一起

前面三節，我們先看 vibe 版怎麼出問題：花了 40 秒、給出三個答案，還花了約 35 分錢。接著，我們打開程式找出四個殺手，再看過 workflow-first 的流程如何「先決定、再動手」。現在來到最後一步：看看那些多出來的步驟，究竟在程式碼裡換到了什麼。

講師把兩份程式庫並排比較，使用同一句 prompt，實作同樣三個功能：feed、匯入和 Vibe 搜尋。一邊是 vibe 版，另一邊是經過工程設計的版本。問題只有一個：workflow 版多出來的程式碼，實際解決了什麼？

先說答案：workflow 版的程式庫明顯大得多。但重點不是行數，而是那些多出來的行究竟只是裝飾，還是程式運作時真正需要的承重結構。

功能一：feed 的昂貴模型呼叫不在讀取路徑上

還記得 vibe 版的 feed 嗎？每次載入頁面，都會在請求路徑中即時呼叫最貴的模型。workflow 版則把做法整個反過來：先把評分轉成代表使用者口味的「口味向量」，再透過一次資料庫呼叫和向量索引，從真實電影目錄中找出最符合口味的電影，並把結果寫進 recommendations 表。

那開啟 feed 時會發生什麼事？get feed 這個 action 只會讀取資料表，整條讀取路徑完全不呼叫模型。因此，這一頁的成本實質上是零，速度則取決於 Supabase 回傳資料要多久。這和 vibe 版的 40 秒，完全是兩種體驗。

AI 仍然會出場，但只負責替每個推薦寫一句「為什麼這適合你」。細節也有經過設計：使用的是一顆 Sonnet，不是 Opus 或最貴的模型；它一次批次寫完整份 feed 的理由，關閉思考功能，而且只有在使用者口味真的改變，或使用者手動按下重新整理時才執行，不會在頁面載入時執行。

在 src/lib/feed/generate.ts 裡，可以看到程式把「什麼時候該重新計算」寫成一個有名字的函式：

// The feed is stale when there is no cached feed yet, or the taste profile was recomputed since
// the feed was built. Compared at read time in getFeed; nothing is stored for it.
export function isFeedStale(computedAt: string | null, maxGeneratedAt: string | null): boolean {
  if (!maxGeneratedAt) return true; // no cached feed
  if (!computedAt) return false;
  return Date.parse(computedAt) > Date.parse(maxGeneratedAt);
}

講師形容這個設計時說：「the cache refresh is a decision with a name」，快取何時更新，成了一個有名字的決定。它不再是藏在某個檔案中、沒人特別留意的一行程式，而是可以明確指出、拿出來討論的函式。

被否決的選項，也留在 repo 裡

這個「有名字的決定」從哪裡來？答案是 architect 提出的問題，而且兩個選項都留下了紀錄。在 ADR 0007 的「Options considered」中，選項一是實際採用的做法：把結果快取起來，只有使用者的 profile 改變時才重新生成。選項二則是每次載入都即時計算，完全不設快取。文件也清楚寫下了這個選項的代價：

- Con: pays a multi-second Sonnet call and its cost on every single page load, and reshuffles the picks and reasons each time so the feed is never stable, which is both expensive and a worse experience. It also risks the serverless duration limit on every render, not just on regeneration.

讀完這段，就能看出它描述的正是 vibe 版的結果。差別在於，workflow 版沒有把這個選項做進產品，而是把它記成一個被否決的方案。vibe 版用 40 秒和 35 分錢實際示範了這個選項的代價；workflow 版則把它留在文件裡，作為「我們考慮過，最後決定不採用」的紀錄。

功能二：匯入：「永不丟資料」先寫成驗收條件

vibe 版匯入資料時，沒有使用交易保護，而是先刪除、再插入。workflow 版的做法不同：瀏覽器先解析 CSV，再每次送出 100 筆，這個數字可以在 chunk 大小設定中看到。分批處理也讓重試可以接續同一份匯入，不必從頭開始。import 的 actions.ts 裡還有一個 retry helper：每個資料區塊在回報錯誤之前，都會先自行退避重試一次。

更重要的是，這個流程不會刪除資料。它使用 movie ID 做 upsert：資料已存在就更新，尚未存在就新增。因此，和 vibe 版的先刪後插相比，這裡不會有任何一段時間讓你的評分資料消失。

流程也處理了一個容易忽略的邊角情況：匯出檔可能有兩筆資料指向同一部電影，例如重映或別名。如果這兩筆在同一段 SQL 中撞在一起，Postgres 會拋錯，整個區塊就會失敗。由於重試會再次送出完全相同的輸入，匯入便可能永遠卡住。workflow 版先對資料去重（dedupe），避免這種情況。

講師說，這是資深工程師水準的程式碼，而且不是等到有人踩過坑，才補上修正。這些設計之所以存在，是因為架構驗收條件早就寫明：「匯入永遠不能丟失資料。」這條條件是在任何可能弄壞資料的程式碼出現之前就訂下的。

功能三：Vibe 搜尋：從「要求它乖」到「讓它無法亂來」

workflow 版的 Vibe 搜尋是一條管線，整段流程可以用五行讀完：先取得和 profile 有關的資料，再判斷使用者想找什麼，接著挑選候選電影、記錄結果並回傳。拆開來看，第一顆便宜的小模型會把使用者的查詢轉成結構化意圖，例如年份、片長，或 mood、theme、tone 這類描述「感覺」的條件。接著，系統透過向量或 embedding 搜尋，從真實目錄中找出候選電影。最後，一顆中等模型從候選清單中挑出三到五部，而且只能從提供給它的清單裡挑選。

這裡有個值得注意的細節。select.ts 會告訴模型：「不要發明電影，只能從提供給你的真實電影裡挑。」但講師提醒，這仍然只是請求模型乖乖遵守，和 vibe 版採用的做法一樣。真正的差別在於，workflow 版也定義了「一部電影的 schema 長什麼樣子」。整條程式路徑都固定了 movie 的資料結構，因此模型在結構上就無法捏造出一部電影。

… the architecture gives it no way to misbehave. That's the difference between a rule and a guarantee.
（架構讓它根本沒有辦法亂來。這就是「規則」與「保證」的差別。）

這是整個模組最值得記住的工程觀念。「規則」是用文字要求模型別亂來，它通常會照做；「保證」則是把系統結構設計好，讓模型就算想亂來也做不到。vibe 版主要靠前者，workflow 版則用後者把防線築進程式裡。

vibe 版缺少的兩樣東西，workflow 版都有

還記得 vibe 版的第四個殺手嗎？缺少測試與 migration。workflow 版兩者都具備：專案使用 Vitest，並替最容易出錯的邏輯（CSV 解析和口味計算）建立測試檔。

也可以留意測試的命名方式，例如「compute taste profile below the floor, AC7」。測試名稱會使用驗收條件的編號，讓每個測試都能追溯到當初對應的決定。此外，資料庫也有六個版本的 migration，記錄資料系統如何隨著功能逐步升級。

程式庫比較大，但不是為了好看

把所有內容放在一起看，workflow 版的程式庫比 vibe 版大了不少。但跟著講師逐一檢視那些多出來的程式碼，就會發現它們不是裝飾。每一行都在支撐某個功能或防線，而且都能追溯到「動手之前，某個 skill 曾經問過我的問題」。

小結

同一個 App、同樣三個功能，workflow 版把每個 vibe 殺手都換成一個「刻意做下的決定」。feed 使用口味向量和一次資料庫呼叫檢索，並把結果寫進 recommendations；讀取路徑不呼叫模型。Sonnet 批次撰寫推薦理由，只在口味改變時執行。快取更新的條件有了名字（isFeedStale），而被否決的即時生成方案則留在 ADR 007，記錄這是「考慮過、但拒絕採用的做法」。匯入改成分塊處理、退避重試、upsert 和去重，因為「匯入不能丟資料」是動手前就寫下的驗收條件。Vibe 搜尋則用便宜模型解析意圖、用向量檢索候選，再讓中等模型從候選清單中挑選。真正防止模型幻覺的不是 prompt，而是固定下來的 movie schema，這就是「規則（rule）」和「保證（guarantee）」的差別。程式庫變大了，但每一行都在承重，也都追得回一個決定。

兩份程式庫都看完了，這場對照也告一段落。接下來的問題是：工程版到底多花了多少？多出來的步驟和 token，應該算進哪一筆成本？下一課會把帳分成兩部分來算：一份是「執行成本」，另一份是「建置成本」。
