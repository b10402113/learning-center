# L1 overview

- `build-notes.mjs` — Generates the six lesson pages from `lesson-data.json` by diffing each lesson's start/solution git branches, pairing every diff hunk with an edit cue, and splicing in the prose files; `--check` fails when notes drift.
- `check-ports.mjs` — Verifies that the workshop's fixed ports (3001 operator API, 3002 agent, 3004 checkout, 5173 dashboard, 5174 notes, 8288 Inngest) are free on both `127.0.0.1` and `::1`, reporting the owning service by name.
- `lesson-data.json` — The course spine: six lessons, each with slug, start/solution branch, promise, opening, edit, verify, experiment, mistakes, challenge, plus per-lesson `editCues` that name the intended code edits.
- `preflight.mjs` — Startup gate: checks Node ≥ 22, a real `OPENAI_API_KEY`/`OPENAI_MODEL`, an optional HTTP(S) `OPENAI_BASE_URL`, and a reachable PostgreSQL `DATABASE_URL` that already has the `labs` schema.
- `stop.mjs` — macOS/Linux-only teardown: scans `ps` for workshop commands run from this repo, resolves each PID's cwd with `lsof`, then SIGTERMs (and escalates to SIGKILL) each matching process group to free the workshop ports.
- `wait-for.mjs` — Polls a health URL up to 100 times at 100 ms intervals with a 500 ms per-request timeout, exiting 0 on the first 2xx so scripts can block until a service is listening.
- `lesson-prose/01.md` — Lesson 1 idea: background agent as a lifecycle (not a chat UI); the `observe → choose → harness validates/executes → observe` loop, and the four kinds of information (world state, run state, execution history, event history).
- `lesson-prose/02.md` — Lesson 2 idea: durable execution splits the opaque loop into named Inngest steps; replay reconstructs a path from saved results, so a checkpointed model choice must not be recomputed, and replay is not restoring a suspended stack.
- `lesson-prose/03.md` — Lesson 3 idea: events are doorbells, not snapshots; one active run per service instance, durable `waitForEvent` with an `eventSequence` recheck, fresh observation after every wake, and superseding runs when the instance changes.
- `lesson-prose/04.md` — Lesson 4 idea: human-in-the-loop as the intended middle of the workflow; persist proposal → wait for correlated decision → reread → re-observe → act, with approval modeled as a scoped capability (run, action, version, expiry).
- `lesson-prose/05.md` — Lesson 5 idea: safe retries need a stable intent key derived from run, cycle, and action, backed by the effect owner's idempotency ledger and a version fence; cancellation stops future steps but is not compensation.
- `lesson-prose/06.md` — Lesson 6 idea: `request_help` reaches a person through the inbox and resumes the same run, but an answer is context, not recovery evidence; evaluate world state, action sequence, and human boundary separately.

- `#L446-L463` — `wait-for.mjs` — Reads the health URL from `argv[2]`, loops 100 times calling `fetch(url, { signal: AbortSignal.timeout(500) })`, exits 0 on `response.ok`, sleeps 100 ms between attempts, and exits 1 with a timeout message otherwise. Learner concept: startup ordering matters — dependent processes must block until the operator API actually serves health.
- `#L464-L478` — `lesson-prose/01.md` — Frames the agent as an outcome-owning lifecycle that survives the conversation; states the `observe → choose → act (harness validates) → observe` loop, warns that a validated JSON action is a suggestion not authorization, and separates world state, run state, execution history, and event history. Names the small tool catalog (`inspect_logs`, `inspect_changes`, `disable_feature`, `rollback_release`, `wait`, `request_help`, `complete`) and treats logs as untrusted evidence, not instructions.
- `#L479-L505` — `lesson-prose/02.md` — Explains that one `whole-agent-loop` step repeats work on crash, so state-read, model-choice, tool-effect, and report each get named steps; replay re-runs the function body but skips completed step callbacks, so a checkpointed `choose-action-*` must drive the following tool step; teaches "replay is not restoring a suspended stack," two clocks/two stores (checkout+Postgres vs Inngest), step-granularity tradeoffs, and step-ID versioning risk for sleeping runs.
- `#L506-L516` — `lesson-prose/03.md` — Treats events as doorbells and mandates re-observation; chooses one active run per service instance with an application-level correlation rule (not an LLM or Inngest decision); parks `wait` and an interim `request_help` on a durable `waitForEvent` guarded by a persisted `eventSequence` recheck and a reconciliation timeout; covers the producer failure window (transactional outbox, stable event IDs) and superseding old-instance runs/approvals after restart.
- `#L517-L541` — `lesson-prose/04.md` — Defines the agent inbox as where unattended work returns; orders the flow persist-proposal → correlated wait → reread decision → re-observe → act; treats approval as a scoped capability (subject, run, action, state precondition, expiry, audit) and closes the time-of-check/time-of-use gap with a version recheck in the operations API; distinguishes read-only inspection from disruptive actions, recommends decision packets over bare "Approve?", and warns that approval is not a universal safety shield against prompt-injected evidence.
- `#L542-L552` — `lesson-prose/05.md` — Explains the effect-then-lost-acknowledgement gap; the effect owner stores `actionId`→result so a same-ID, same-argument retry returns the saved result while a mismatched reuse is rejected; the stable ID is derived from run, cycle, and checkpointed choice; the version fence plus the service's own check remains the final boundary; `cancelOn` stops future steps but already-committed operations persist, so high-impact effects need an effect ledger or compensation and an explicit `unknown outcome` state.
- `#L553-L565` — `lesson-prose/06.md` — `request_help` persists a question and waits for a correlated answer that resumes the same run as new context (not recovery proof); lists the readable Activity story (alert → observation → evidence → question → pause → answer → observation → wait → recovery → observation → report); argues to score world state, action sequence, and human boundary separately rather than trusting a polished final report; discusses a context policy that preserves goal snapshot, commitments, approval scopes, action IDs, and evidence links while summarizing old narrative.
