# L1 overview

- src/App.tsx — Single-file React operator dashboard: types for Run/Approval/ActivityEntry/ServiceEvent, a `request()` fetch wrapper over the operator API, three hash-free routes (Inbox `/`, Activity `/activity`, Events `/events`) rendered by conditionals on `window.location.pathname`, plus `ActivityFeed`/`EventFeed` subcomponents and a 1.5s polling refresh.
- src/styles.css — All styling for the dark "checkout ops" UI: shell/sidebar/topbar layout, inbox two-pane mailbox + reading pane, run list + activity timeline rails with per-phase color variables, event accordion, error/notice banners, and two responsive breakpoints. No logic.
- index.html — Vite entry document: dark theme-color meta, `<title>Checkout Ops · Background Agents</title>`, `#root` div, module script pointing at `/src/main.tsx`.
- src/main.tsx — React 18 bootstrap: `createRoot` on `#root`, StrictMode wrapping `<App />`, imports global `styles.css`.

# L2 detail

- `#L1-L713` — web/src/App.tsx — The whole dashboard in one component file. Types mirror the backend domain: `Run` (goal, status, iteration, `waitReason`, `report`, `eventSequence`), `Approval` (action, `input` payload, status, `reason`, `expiresAt`, `decidedAt`), `ActivityEntry` (kind like `agent:predict`, message, detail), `ServiceEvent` (type, data, runId), and `Dashboard` bundling `service` snapshot + events + runs + approvals. Helpers: `request<T>()` (POST/JSON, friendly "start npm run dev:operator" error), `label()`, `terminal()` (completed/cancelled/failed/escalated/superseded), `pretty()`, and a custom `Link` that does pushState + synthetic `popstate` for client-side routing — so `NAV` (`/` Inbox, `/activity` Activity, `/events` Events) plus a `useEffect` popstate listener is the entire router; unknown paths fall back to `/`. `PHASE_ICONS`/`phaseOf()`/`activityDetail()` map each `agent:<phase>` activity kind (start, observe, predict, act, pause, resume, human, terminal, policy, event) to an icon and a human one-liner. `ActivityFeed` renders the timeline with expandable JSON payloads; `EventFeed` renders service events as `<details>` accordions. In `App()`: `refresh()` polls `/api/dashboard` every 1500ms and, on the Activity route, also fetches `/api/runs/{id}/activity`; `act()` wraps mutations (decide approval, cancel run) and re-poll. Route `/` (Inbox): filters approvals into `pending` = status pending AND its run is non-terminal (i.e. only surface questions for runs actually alive), lists them as messages, and the reading pane surfaces the paused run's request — for `action === 'request_help'` it shows `input.question` and a required reply, otherwise it shows the full `PROPOSED TOOL INPUT` JSON before approval. The composer posts to `/api/approvals/decide` with `decision: 'approved' | 'rejected'` plus the typed `reason`, with "Approve action"/"Deny" or "Send answer"/"Cannot help" — proving a human gate is a durable approval record answered over HTTP, not an in-memory promise. Route `/activity`: run list with status dots, then per-run detail header (status, goal, iteration, event count, `waitReason`), a Cancel run button while non-terminal, the persisted `ActivityFeed` ("persisted per incident · newest first") and the final `report` — proving the run's loop, prediction, tool calls, pauses and resume all survived as replayable events. Route `/events`: the checkout service's raw events plus a "Current checkout state" snapshot, with copy explaining that alerts join an open incident and "the agent reads current state over HTTP rather than trusting an event payload" (event-vs-state reconciliation). Learner-relevant concept: an explicit human-in-the-loop operator surface over a durably paused agent loop — pending approvals, wait reasons, and an event log are the observable contract of background execution.
