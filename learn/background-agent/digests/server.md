# L1 overview

- `agent-workflow.ts` + `agent.ts` + `inngest.ts` — The durable agent loop: a single Inngest function `incidentAgent` that runs a bounded 24-cycle observe/decide/act loop, with every side effect wrapped in `step.run` for checkpointing, `step.waitForEvent`/`step.sleep` for pauses, and approval gating before writes. This is the spine of the workshop: durable execution turns an LLM loop into something that can pause for minutes across human decisions and service events.
- `agent-data.ts` — The harness's state machine over Drizzle: `getRun`/`setRun` (with terminal-status guards), `setIteration`, `agentState` (observation assembly plus environment/instance validation), `goalSatisfied` (deterministic goal path/equals check), derived action IDs, approval propose/get/decide/stale lifecycle. Teaches that the harness — not the model — owns status transitions, idempotency, and authority.
- `incident-data.ts` + `operator.ts` — Ingestion and human surface: idempotent service-event ingest inside one serialized transaction that opens/updates/supersedes runs, dispatches Inngest events with a derived send ID, plus the Express operator API (dashboard, cancel, approvals, activity). Teaches event-sourced wake-ups, instance-restart supersession, and the operator inbox.
- `schema.ts` — Drizzle/Neon Postgres schema: `runs` (status, iteration, eventSequence, goalCondition, instanceId), `events`, `actions`, `approvals` (pending/approved/rejected/expired/stale, expiresAt), `timeline`. Each table exists to make a specific durability guarantee inspectable (terminal status, decision count, idempotency key, human decision record).
- `agent-brain.ts` + `tool-policy.ts` — The model adapter and the policy table. `chooseAction` returns a strict Zod-typed decision (action/reason/detail) via `Output.object`; `writeReport` produces the final report. `actionPolicy` maps each action name to read/write/approval/help/terminal/wait, so the harness enforces authority without branching on service internals.
- `agent-log.ts` + `environment.ts` + `observe.ts` — Supporting seams: `timeline`-backed activity logging with a fixed phase enum; environment bootstrap and configurable goal/goal-condition; HTTP-only state observation from the checkout service. Teaches observability-as-data, external state as the source of truth (never the event payload), and config-driven goals.
- `db.ts` + `seed.ts` — Thin infrastructure: pooled `postgres` client + Drizzle instance, and a seed script that idempotently ensures the single workshop environment exists.

# L2 detail

- `#L1-L216` — server/agent-workflow.ts — **The durable loop.** `executeAction` POSTs to `${checkoutServiceUrl}/operations` with a derived `actionId` and optional `expectedVersion`, records the action only when `result.stale !== true`. `incidentAgent = inngest.createFunction({ id: 'incident-agent', triggers: { event: 'incident/opened' }, retries: 2, cancelOn: [{ event: 'agent/run.cancelled', match: 'data.runId' }], concurrency: { limit: 1, key: 'event.data.environmentId' } })` with an `onFailure` that marks the run failed. The loop `for (let cycle = 1; cycle <= 24; cycle++)` is the decision limit; the terminal fallthrough `setRun(runId, 'escalated', 'Decision limit reached')` at `stop-at-limit` is the cap's terminal status. Every effect is a checkpoint: `observe-state-N`, `choose-action-N` (the only LLM call), `set-iteration-N`, `record-decision-N`. Early guard returns if instance mismatch or status ∈ {completed, failed, cancelled, escalated, superseded}. `goalSatisfied` short-circuits to `write-report-N` + `complete-run-N`. Waits: the `wait` branch sets status `waiting` then polls `eventSequence` and uses `step.waitForEvent('wait-for-service-N-M', { event: 'incident/updated', if: 'async.data.runId == "..."', timeout: '10s' })` — the timeout doubles as reconciliation for events that landed just before the wait. Approval path: `actionId = `${runId}:${cycle}:${decision.action}`` (derived, idempotent), policy from `actionPolicy`; `approval`/`help` policies call `propose-action-N`, then loop `step.waitForEvent('wait-for-human-N-M', { event: 'agent/approval.decided', timeout: '10s' })` and `reconcile-human-N-M` until non-pending; non-approved → `escalated` + return; `help` → continue. **Version precondition:** after approval, `recheck-approved-state-N` re-reads state and if `fresh.world.version !== input.expectedVersion` it calls `invalidate-approval-N` (staleProposal) and continues instead of acting on a stale approval. Execution passes `expectedVersion = state.world.version` for all non-read actions; `result.stale === true` logs and continues. After a successful write, `settle-status-N` sets `waiting` and `step.sleep('settle-N', process.env.AGENT_SETTLE_DELAY ?? '1s')` so the next cycle observes the effect. Also blocks model-proposed `complete` when a deterministic `goalCondition` exists (`reject-completion-N`).
- `#L217-L504` — server/agent-data.ts — **Harness-owned state discipline.** Exports `getRun`, `setRun`, `setIteration`, `cancelRun`, `agentState`, `AgentState` type, `goalSatisfied`, `recordDecision`, `recordToolAction`, `proposeAction`, `getProposal`, `decideProposal`, `staleProposal`. `setRun` is the terminal-status guard: it refuses to overwrite a run already in `completed/cancelled/failed/escalated/superseded`, and derives a log `phase` (`terminal`/`pause`/`human`/`resume`). `setIteration` only writes while the run is in an active status (conditional `inArray` update). `cancelRun` sets `cancelled` then sends `agent/run.cancelled` to trigger `cancelOn`. `agentState` builds the observation bundle (latest world snapshot, last 8 events, last 8 actions matched by derived ID prefix `${runId}:%`, last 4 non-pending approvals) and validates `run.environmentId === environmentId` and `world.instanceId === run.instanceId` — throwing "Checkout service restarted during this incident" so a stale run never acts on a new world. `goalSatisfied` resolves `condition.path` against `state.world.state` and compares `equals`: deterministic termination without trusting the model. `recordToolAction` inserts with `onConflictDoNothing()` on the derived `actionId` — the idempotency key that makes `step.run` retries safe. `proposeAction` inserts an approval with `expiresAt = now + 10min`, sets run to `needs_approval`/`needs_help`, returns the proposal. `getProposal` lazily expires pending proposals. `decideProposal` is the authority check: no-op if not pending, marks `stale` if the run is terminal, requires a non-empty answer for approved `request_help`, performs a conditional `eq(approvals.status, 'pending')` update (no double-decide), logs, then best-effort sends `agent/approval.decided` — and if the send fails it warns that the run "will reconcile on timeout," the non-negotiable fallback of the wait-with-timeout design. `staleProposal` marks an approved proposal as `stale: 'State changed before this action ran'`.
- `#L505-L691` — server/incident-data.ts — **Idempotent ingest and run lifecycle.** `ingestServiceEvent({ id, serviceId: 'checkout', instanceId, type, data })` rejects events from an older `instanceId`, then in a single `db.transaction` takes `SELECT ... FOR UPDATE` on the environment row to serialize concurrent event deliveries. Duplicate `events.id` short-circuits and replays the same dispatch decision (`opened` if the run's `eventId` matches, else `updated`) — deduplication made visible. Any ACTIVE run from a different instance is marked `superseded` with reason "Checkout service restarted with fresh state", its pending approvals go `stale`, and each gets a timeline entry; the resulting `agent/run.cancelled` events are sent after commit. Otherwise it finds an ACTIVE run for the instance → `updated` and `eventSequence + 1`, or opens a new run (`randomUUID`, `goal: configuredGoal()`, `goalCondition: DEFAULT_CONDITION`, status `running`, `eventSequence: 1`) when the service is unhealthy and the event isn't `service.started`; a `service.started` event with healthy state opens no run. Every event increments `eventSequence`, which is exactly what the workflow's wait-loop polls. Dispatch uses a derived Inngest send id `${input.id}:incident`, so retries cannot double-trigger the function. `dashboard()` returns service snapshot (tolerating downtime), 400 events, 100 runs, 100 approvals for the operator UI.
- `#L692-L811` — server/schema.ts — **Durability made inspectable.** Drizzle `pgTable`s: `environments` (physical table `labs`, keeping legacy columns so an instructor's Neon DB survives the migration unscathed — `state: jsonb<WorldState>`, `version`, `goal`, `goalCondition`, plus unused legacy columns agent code never reads), `eventPlans`/`observations` (unused historical tables, retained non-destructively), `events` (client-supplied `id` as primary key + `runId` + `instanceId` → the dedup key), `actions` (text `id` = `runId:cycle:action` idempotency key, `input`/`result` jsonb), `runs` (`status`, `iteration`, `eventSequence`, `goalCondition`, `instanceId`, `waitReason`, `report`, `startedAt`), `approvals` (`actionId`, `status`, `reason`, `expiresAt`, `decidedAt`), `timeline` (`kind`, `message`, `detail`). Teaching point: the run row's `status` + `iteration` + `eventSequence` columns are the durable memory that replaces in-process loop variables after a restart.
- `#L812-L877` — server/operator.ts — **The human surface.** Express app on `127.0.0.1:3001` with Zod validation (`id = z.string().uuid()`). Routes: `GET /api/health`, `GET /api/dashboard`, `POST /api/service/events` (the endpoint the separate checkout process retries with a stable event ID until accepted — the comment makes explicit that no simulated service behavior lives in the agent app), `POST /api/runs/cancel` → `cancelRun`, `GET /api/runs/:runId/activity` → `activityForRun` (after `getRun` existence check), `POST /api/approvals/decide` → `decideProposal`. Error middleware maps `ZodError` → 400 and everything else → 500 with the message. Boots by awaiting `ensureEnvironment()` before `listen` — schema/env readiness precedes serving traffic.
- `#L878-L928` — server/agent-brain.ts — **The model adapter, with the harness holding the leash.** `decisionSchema = z.object({ action: z.enum(ACTIONS), reason: z.string(), detail: z.string() })`; `model()` reads `OPENAI_MODEL` and throws unless `OPENAI_API_KEY` and the model id are set; `chooseAction(goal, state)` calls `generateText({ model, output: Output.object({ schema: decisionSchema }), system, prompt })` and returns `result.output` — structured output guarantees a legal action name, but the system prompt states plainly "Choose exactly one action. The harness validates it and controls execution," "An alert is a trigger, not authoritative evidence," "An answered help request does not prove recovery," and "Choose the service action you think is justified; the harness applies its own policy before execution." `writeReport(goal, state)` produces the final report with "Do not invent facts." Teaching point: the LLM proposes; policy, goal checks, and version preconditions dispose.
- `#L929-L969` — server/agent-log.ts — **Observability as rows, not stdout.** `AgentActivityPhase` = `start | observe | resume | loop | predict | act | pause | human | terminal`; `logAgentActivity(environmentId, runId, phase, message, detail)` inserts into `timeline` with `kind: agent:${phase}`; `activityForRun(runId)` returns the last 200 entries newest-first for the operator UI. Because logs are durable table rows written inside `step.run`s, the agent's reasoning trail survives restarts and is replay-safe.
- `#L970-L1006` — server/environment.ts — **Config-driven goals and a single environment.** `DEFAULT_GOAL` describes the incident-response charter; `DEFAULT_CONDITION = { path: 'health.status', equals: 'healthy' }` is the deterministic goal condition consumed by `goalSatisfied`; `configuredGoal()` prefers `process.env.AGENT_GOAL`. `ensureEnvironment()` returns the latest `environments` row or creates one (legacy columns filled with placeholders, `state: {}`, the default goal and condition) — idempotent bootstrap so every process can start safely.
- `#L1007-L1034` — server/agent.ts — **The agent process / Inngest serve endpoint.** Throws at boot if `OPENAI_API_KEY` or `OPENAI_MODEL` is missing (fail fast, no silent fake mode), creates an Express app with `express.json({ limit: '10mb' })` because "Inngest replays prior step results to this local endpoint; long incident runs exceed Express's 100 KB default" — a concrete lesson in how big checkpoint payloads get. Serves `GET /api/health` reporting `mode: 'openai'` and the model, and mounts `/api/inngest` via `serve({ client: inngest, functions: [incidentAgent] })` on port 3002.
- `#L1035-L1051` — server/observe.ts — **External state as truth.** `checkoutServiceUrl` from `CHECKOUT_SERVICE_URL` (default `http://127.0.0.1:3004`); `snapshotSchema` Zod-validates `{ instanceId: uuid, version: int, state: record }`; `getLatestState()` fetches `/state` over HTTP and parses it. The comment is the teaching point: the agent "does not share the service's memory or use an event payload as a state snapshot" — observations must be re-read, never inferred from the trigger. `version` is the token the workflow later uses as its `expectedVersion` precondition, and `instanceId` detects service restarts.
- `#L1052-L1066` — server/tool-policy.ts — **Policy as data, not model judgement.** `actionPolicy: Record<ActionName, 'read' | 'write' | 'approval' | 'help' | 'terminal' | 'wait'>` mapping `inspect_logs`/`inspect_changes` → read, `disable_feature` → write, `rollback_release` → approval, `request_help` → help, `complete` → terminal, `wait` → wait. The workflow reads this table to decide whether to require a human, whether to pass `expectedVersion` (read actions don't), and whether to skip execution entirely. Comment: "The harness reads policy metadata; it does not branch on checkout fault flags" — authority is declarative and separate from fault logic.
- `#L1067-L1076` — server/db.ts — **Connection seam.** Loads `dotenv/config`, requires `DATABASE_URL` (throws with neon.new guidance), creates a pooled `postgres` client (`max: 5, connect_timeout: 10`) and exports `db = drizzle(client, { schema })`. Small but load-bearing: every durable guarantee in the digest ultimately lands in this Neon Postgres.
- `#L1077-L1082` — server/seed.ts — **Idempotent bootstrap script.** Calls `ensureEnvironment()`, logs the environment id, and closes the pool via `client.end()` — a reusable pattern for one-shot scripts against a pooled driver (otherwise the process hangs).
- `#L1083-L1086` — server/inngest.ts — **The durable execution client.** `new Inngest({ id: 'background-agents-workshop' })`, shared by `agent.ts` (`serve`/function registration), `agent-workflow.ts` (function definition), and `agent-data.ts`/`incident-data.ts` (`.send` for wake-up and cancellation events). The single client instance is what ties triggers, checkpoints, waits, and cancellations to one app id.
