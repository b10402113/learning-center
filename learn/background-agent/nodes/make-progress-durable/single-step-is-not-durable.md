# 全部都在一個 step 裡

在設計長時間運行的 AI Agent 時，許多人會導入像 Inngest 這類持久化執行（durable execution）框架，希望伺服器重啟或斷線時，工作流程能自動恢復。然而剛開始接軌時，最常見的做法是直接把整個代理人迴圈包進單一執行步驟中：

<!-- derived -->
```typescript
return step.run('whole-agent-loop', async () => {
  for (let cycle = 1; cycle <= 8; cycle++) {
    // 讀取日誌、呼叫模型、執行工具、產生回報
  }
})
```

這樣寫雖然讓程式跑在框架內，但在工程上，這等於把所有雞蛋放在同一個籃子裡。

## 外部歷史與步驟記憶的原理

持久化執行的核心機制，是在伺服器行程（process）之外保留一份獨立的執行紀錄。當一個 `step.run` 執行成功時，框架會將它的回傳結果持久化儲存下來。如果主機重啟，工作流程會重新載入，並比對先前已記錄的步驟結果；凡是已經記錄的步驟就會直接跳過，直接從第一個尚未完成的步驟接續執行。

<!--image:1-->

這意味著：**系統能夠復原的最小單位，就是一個 step。**

如果你把整整八輪的「檢查日誌、呼叫模型、呼叫工具執行變更」全都寫在同一個名為 `whole-agent-loop` 的步驟裡，框架眼中的檢查點就只有這一個。只要這個函式沒有完全執行完畢並回傳，外部系統就完全沒有任何已儲存的進度。

## 崩潰窗口在哪裡？

長時間執行的代理人不可能保證 Node 行程永遠不死。伺服器可能被重新部署、底層基礎設施可能中斷、或者記憶體超限被系統強制終止。在單一巨型步驟裡，整個執行期都處在危險的「崩潰窗口」（crash window）中：

<!--image:2-->

1. **模型輸出儲存前崩潰**：代理人讀取了狀態、向模型發送請求，模型也產生了回應，但行程在下一步之前中斷。因為整個步驟沒有完成，重啟後必須重新讀取日誌、重新呼叫模型，平白浪費 Token 與等待時間。
2. **工具生效後、步驟記錄前崩潰**：這是最嚴重的狀況。模型決定關閉某個故障功能，工具也確實對外部系統送出請求並生效。但在這個大步驟回傳結果前，行程突然中斷。外部服務的狀態已經改變，可是工作流程系統裡「沒有任何步驟完成紀錄」。
3. **整套流程接近尾聲時崩潰**：就算代理人已經執行到第 7 輪迴圈，只要在最後一步崩潰，整個步驟依然算作未完成。

## 為什麼重啟會整包重做？

當伺服器重新啟動、框架嘗試重試（retry）時，它查詢歷史紀錄，只會看到 `whole-agent-loop` 尚未成功儲存結果。

框架別無選擇，只能從這個步驟的第一行程式碼從頭執行。這會導致三個層面的重複：

<!--image:3-->

- **重做觀察（Observation）**：代理人重新去撈取日誌或讀取環境狀態，而此時環境可能早已因為之前的操作發生改變。
- **重做模型呼叫（Model Call）**：重新發送提示詞給 LLM，耗費雙倍成本，而且模型的非確定性可能給出完全不同的下一步決策。
- **重做副作用（Side Effect）**：工具操作會再次被執行。如果該工具不具備等冪性（idempotency），重複執行可能導致功能被切換兩次、重複發送通知，甚至重複扣款。

持久化執行本身並不能神奇地保證外部副作用「剛好發生一次」（exactly once）。如果一個外部變更已經生效，但在系統記下該步驟前連線斷開，該操作就存在重複風險。

但如果我們把單一大步驟拆開，將「狀態讀取」、「模型決策」、「工具副作用」與「進度回報」各自劃分為具名的小步驟，就能將崩潰窗口切到最小。重啟時，系統可以精確跳過已經儲存成果的日誌檢查與模型推論，直接從真正中斷的那一步繼續往前走。
