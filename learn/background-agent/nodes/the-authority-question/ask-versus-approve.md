# 它比較像收件匣

既然模型不該知道自己需要批准，那這些請求最後會去哪裡？當你讓背景代理（background agent）在背後自己跑任務時，最不適合的互動方式其實是聊天視窗。

背景代理平時在背景運作，不需要你盯著對話紀錄，也不需要維護即時的訊息串流。更好的做法是把它當成一個「收件匣」：代理平時自己忙自己的，一旦卡住了，就把一項待辦事項丟進你的收件匣。你抽空打開收件匣處理掉這些事項，代理就能繼續往下跑。

不過，收件匣裡的項目看起來都是「請人類處理」，背後的來源卻有本質上的不同。

## 求助與批准的本質差別

收件匣裡的待辦事項大致可以分成兩類：

第一類是**求助**（Help）。代理在執行任務途中遇到了模糊不清的狀況，或者缺少必要資訊，因此自己決定呼叫「我需要協助」的動作，把問題丟給你，例如：「這筆帳單該歸類在哪個部門？」

第二類是**批准**（Approval）。代理選定了一個特定動作（例如刪除資料或扣款），但這個動作在執行前必須先經過人類點頭同意。

這兩者的關鍵差異在於：是誰決定要找人類的？

<!--image:1-->

- **求助來自語言模型本身的判斷**：模型自己意識到資訊不足或無法做決定，主動選擇發出求助。這屬於機率性、非確定性的行為，系統評估時必須針對模型的決策品質做評測（eval）。
- **批准來自外圍框架（harness）的硬性規則**：模型本身根本不知道、也不該知道這個動作需要審批。它只是選了一個它想執行的動作，而系統框架攔截了該動作，硬性規定「只要是這類動作，就必須先放入人類收件匣」。這完全是確定性（deterministic）的程式碼邏輯，不需要也不屬於對模型的評測。

一般我們所說的「代理」，其實是「語言模型加上系統框架」。收件匣裡的項目雖然都來自代理，但有的源自模型的自主判定，有的源自框架的規則攔截。

## 為什麼代理不該知道哪個動作需要批准？

把「批准」的規則寫死在系統框架中，而不是交給模型自己判斷，是為了確保安全性不會被模型的心智狀態動搖。

如果由模型自己決定何時該「請求批准」，只要提示詞受到污染，或是模型在讀取不受信任的日誌、外部資料後產生偏見，它就可能誤以為當前情境很安全，跳過請求直接執行敏感動作。

因此，安全邊界必須設在模型之外。框架把任何具有變更性（mutative）、寫入權限的動作直接鎖在批准門檻之後。模型只負責決定「我想做動作 X」，框架則在動作 X 執行前強行煞車，把審批單丟給人類。

<!--image:2-->

這同時也提醒了一件事：批准不是萬靈丹。即使寫入動作需要批准，模型依然可能在讀取惡意日誌後，提出了一個看似合理卻有害的寫入請求。不過，將批准權交由外圍框架嚴格把關，至少能確保高風險動作絕對不會在人類不知情時直接落實。

## 當收件匣變成新的瓶頸

在系統建置初期，把所有具寫入權限的動作全部放進批准流程，是最安全的起手式。但如果一個背景任務每天都需要執行幾十次寫入，你的收件匣一天就會多出幾十個批准請求。

頻繁審批會讓你重新被綁在螢幕前，失去背景代理原本帶來的生產力，甚至退化成某種變相的「聊天視窗等待狀態」。

這時該做的不是放寬模型權限讓它自由發揮，而是降低動作本身的爆炸半徑（blast radius）：

<!--image:3-->

- 為敏感操作建立快速復原（rollback）機制，就算出錯也能立刻還原。
- 採用漸進式生效（例如先變更 10%，再逐步放大），限制單次失敗的衝擊。
- 拆分權限，把安全且無害的部分獨立出來自動執行。

唯有將環境風險降到足夠低，才能安全地把批准門檻移開，讓收件匣真正只留給極少數需要人類智慧介入的時刻。
