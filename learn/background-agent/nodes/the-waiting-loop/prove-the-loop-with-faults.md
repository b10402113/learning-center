# 故意弄壞它

等待迴圈能跑通之後，最後要用幾個刻意設計的故障情境驗證它。測試自動化維運代理人（Agent）時，只測「問題發生、修復、成功結束」的順利流程，往往會掩蓋架構上的死角。真正考驗外圍控制層（Harness）穩定度的，是把時序拉長、連續重發告警，甚至是故意把恢復時間歸零。

透過三種邊界情境，可以驗證等待與恢復迴圈的行為，並理解 Agent 為何會中途改走求助，又為何會在特定條件下徹底卡住。

### 延遲恢復：為什麼 Agent 會改走求助？

在測試中模擬外部依賴故障（例如付款閘道請求逾時、累積 42 次錯誤），並設定 30 秒後才恢復正常：

<!--image:1-->

<!-- derived -->
```bash
npm run dev agent -- --start-checkout --fault-dependency --recover-after 30
```

當告警觸發並開啟事件單（Incident）後，Agent 讀取當前狀態，發現 `upstream_healthy` 為 `false`。結帳服務本身沒有程式碼缺陷，問題出在外部第三方服務，本地端無法自行修復。

這時 Agent 會做出符合邏輯的決策：請求外部協助（ask for help）。它不會無止境地在本地嘗試重試，而是意識到「這不是我管轄的服務，我需要其他人處理」。

如果系統內的求助處理工具尚未就緒，控制層會讓 Agent 進入暫停等待狀態，標記等待原因為求助尚未就緒。這段時間 Agent 會處於耐久等待迴圈中。

30 秒後，模擬環境發送了上游恢復的事件（例如 `health.recovered`）。這個事件進入系統後喚醒了暫停中的 Agent。Agent 脫離等待的 `while` 迴圈，回到主迴圈頂端重新進行觀察（re-observe）。當它確認最新狀態中的 `upstream_healthy` 已經變回 `true`，便判定問題已解決，直接結束執行（Run completed）。原本發出的求助需求，也因為事件被消化而自然解除。

這裡有一個關鍵觀念：通知不是狀態快照（A notification is not a state snapshot）。喚醒事件的唯一作用是告訴 Agent「該重新觀察了」，控制層絕不能直接把事件內容當作系統已經健康的證據，必須重新讀取真實環境的狀態。

### 重複告警：避免重複開工

系統發生故障時，監控往往會在短時間內連續觸發多次警報。測試時可以使用 `--alerts 3` 同時送出三筆告警。

<!--image:2-->

如果系統採用「一告警一執行個體（one-run-per-event）」的策略，就會同時啟動三組 Agent 試圖修復同一個問題，造成操作互相踩踏。

健全的控制層必須具備事件單彙整機制。當第一筆告警開啟 Incident 後，後續進來的兩筆相同告警，應當直接附加到同一個 Incident 下，而不是產生三個獨立的 run。

### 零秒恢復：為什麼等待迴圈會卡死？

想把系統故意弄壞，最直接的方法是將恢復時間設為零秒：

<!-- derived -->
```bash
npm run dev agent -- --recover-after-ms 0
```

執行後會發現：Agent 竟然卡在等待狀態，永遠沒有結束。

這背後是事件時序的競態問題（race condition）。當恢復時間是 0 毫秒，上游依賴在故障發生的瞬間就已經恢復，恢復事件在 Agent 判定需要等待、並向系統註冊耐久監聽之前，就已經發送完畢。

<!--image:3-->

等到 Agent 真正進入等待迴圈，開始聆聽「未來的恢復事件」時，那筆事件早就成為過去式。沒有新的事件進來觸發喚醒，Agent 就會一直卡在佇列中。這正是在設計事件驅動架構時，必須提供「註冊前狀態對帳（reconciliation rule）」或逾時重檢的原因。

如果在此時手動重啟健康的結帳服務，舊的 run 應該被標記為廢棄（superseded）。因為服務實例已經改變，沿用舊 run 的審批授權或先前的觀察數據極度不安全——舊實例上的環境上下文與狀態版本，已經無法對應到重啟後的新環境。

### 決定系統穩定的是 Harness，不是模型

在這些測試情境中，核心語言模型（LLM）的推論邏輯完全不需要更動。決定系統能否正確等待、防範重複告警、在外部故障時改走求助、以及能否在喚醒後重新確認狀態的，全部取決於包覆在模型外圍的控制代碼（Harness）。沒有這層嚴謹的狀態與時序控制，再聰明的模型也無法在真實的生產環境中自主運作。
