# 非同步的事放進 step，而且一次只放一件

知道 replay 會重用 step 的結果之後，切點問題就變成：哪些程式碼該包進 step？在寫這類具備持久化執行（durable execution）能力的工作流程時，許多人常卡在同一個問題：到底哪一段程式碼需要包進 `step`？一個 `step` 裡面又該塞多少行邏輯？

判斷的起點其實很直接：如果這件事是非同步的（asynchronous），它通常就該放進一個獨立的 `step`。

## 為什麼非同步操作該進 step

在 Inngest 或 Temporal 這類工作流引擎中，概念都是相通的（Temporal 稱之為 activity，Inngest 稱之為 step）。工作流程本身需要保持確定性（deterministic），而真正與外部世界互動、耗時較長或結果不確定的操作，就該由 step 承擔。

呼叫大語言模型（LLM）生成分析報告、寫入資料庫變更執行狀態、呼叫第三方 API 發送通知，這些操作都有幾個共同特徵：

1. 它們是非同步的，需要等待網路或運算完成。
2. 它們的代價通常很高，例如花費 API token 或時間。
3. 系統如果當機，你希望重啟後能從中斷的地方繼續，而不是全部重來。

當你把一個非同步操作放進 `step.run`，工作流引擎就會記錄該步驟的回傳值。這就像是把執行結果存進快取一樣。下次流程重新執行到這一步時，引擎看到已經有記錄，就會直接回傳快取的值，跳過實際的程式碼執行。

## 一個 step 只做一件事

既然非同步操作要包進 step，很自然會有人想把連續幾個非同步呼叫寫在同一個 step 裡。例如在同一個 step 內先扣款、再發送確認信、最後更新資料庫狀態。

這樣的寫法隱藏了嚴重的重試代價。

工作流系統的重試機制是以 step 為單位。假設你在一個 step 裡放了三件非同步的事：第一件成功了，第二件因為網路短暫中斷而失敗拋出錯誤。此時工作流程觸發重試，它沒辦法從第二件事直接開始，而是整個 step 從頭重跑一次。

這意味著：原本已經執行成功的第一件事，會被再次執行。

如果第一件事具有副作用（例如發送信件或扣款），重跑就會導致重複扣款或重複寄信。除非同一個 step 裡的所有操作即使全部重放也完全沒有負面影響（具備冪等性且無額外成本），否則絕對不要把多個非同步操作綁在同一個 step 內。維持「一個 step 只做一件事」，失敗時重試的範圍就只會局限在那件失敗的事上。

## 拿捏 step 的粒度

原則是「async 放 step、一個 step 一件事」，但這不代表要在每行程式碼周圍都加上 step。

切分邊界時有兩端極端需要避免：

<!--image:2-->

- **把整個大迴圈包在一個 step**：這會掩蓋程式執行的局部進度。迴圈跑到第十圈失敗時，整個迴圈十圈都得重跑，完全失去持久化執行的意義。
- **連單純的記憶體計算都包成 step**：純粹的資料轉換或變數指派不需要外部 I/O，把它們包進 step 只會產生大量雜亂的追蹤紀錄（trace history），增加系統負擔，卻換不來任何崩潰恢復的好處。

最適當的做法，是把 step 放在重啟時真正重要的關鍵點：讀取外部狀態、做出決策、執行具體動作、寫入報告與更新狀態。每個非同步步驟各自獨立，既清楚呈現工作進度，也能在失敗重試時把代價降到最低。
