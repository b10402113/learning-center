# 門鈴，不是房間

在打造自動化調查事件的代理（agent）時，很多人會直覺地把「事件通知」當成「系統現況」。當結帳服務發出警報，包含一包錯誤資訊的負載（payload），代理就立刻根據這份負載開始下診斷、採取行動。

但真實世界的運作不是這樣。外部世界不會停下來等代理跑完迴圈，依賴的第三方服務可能在代理閒置的幾秒內就自我修復了，多個接踵而來的警報也可能只是在描述同一場故障。

把事件當成「門鈴」，而不是「房間」。

門鈴響了，只代表有人按鈴，通知你該醒來看一下；門鈴本身並不是房間裡的現況。當結帳程序發出訊號、API 將它記錄並關聯到當前的事件時，代理被喚醒的第一件事，是重新去讀取結帳服務的即時狀態，而不是把事件負載當成不可質疑的狀態快照。如果當下看不到問題的全貌，最合理的反應可能是什麼都不做，回去睡覺並繼續觀察。

這引出了一個關鍵的設計問題：什麼時候該等待，這個決定該由誰來下？

## 為什麼框架不能代替代理決定等待

在系統架構中，包裝代理的外部執行框架（harness）可以強制執行硬性策略。舉例來說，如果要執行具有破壞性的重開機或修改設定，框架可以硬性規定「必須等待人類批准」，這種權限絕對不能交給代理自由發揮。

但回到事件調查本身，決定「現在要不要再等等看」，卻必須由代理自己判斷。

外部框架無法預先寫死確定性的規則來決定何時等待。框架沒有讀過日誌，沒有呼叫各種診斷工具，自然沒有掌握當下的上下文。只有代理經歷了整個推理過程，知道目前看到了什麼、缺少了什麼。

舉個常見的情境：結帳伺服器頻繁當機，代理調閱日誌後發現，是因為打到某個第三方 API 遭到限流（rate limit 或 throttling）。錯誤回應中甚至帶有限流標頭，這不是修改內部程式碼能解決的問題，最合理的處置就是等待額度重置，觀察相依服務是否自行恢復。

在這種狀況下，代理可能會得出兩個推論：
1. 「這是外部相依服務的問題，我無能為力，需要向人類發出求助。」
2. 「這是暫時性的限流，我應該先等待幾分鐘，看看它會不會自己好轉。」

<!--image:2-->

選擇「等待」或「請求協助」本身是完全沒有破壞性的。我們不需要在框架層把行為寫死，而是應該提供相應的工具，讓代理在缺乏足夠資訊做出明確動作時，有權利選擇主動等待。

## 聚合事件，拼出完整全貌

除了等待的決策權，事件進入系統的方式也決定了代理能不能看懂局勢。

如果系統架構是「每來一個新事件就開啟一個全新的代理執行個體（run）」，很快就會遇到災難。想像同一個根本原因引發了三處警報，系統開了三個互不相通的代理各自調查。每個代理都只看到三分之一的拼圖，誰也無法拼出全貌，最終誰也解決不了問題。

<!--image:3-->

比較合理的做法，是在應用層建立關聯規則（correlation rule），將事件分組：同一個結帳服務實例在一段時間內只維持一個活躍的調查流程。第一個異常警報開啟調查，後續相關警報加入同一個上下文，而服務恢復正常的事件則再次喚醒代理進行確認。

門鈴只是提醒，調查需要親自開門查看，而決定要站在門口等多久，只有看見屋內狀況的人才知道。
