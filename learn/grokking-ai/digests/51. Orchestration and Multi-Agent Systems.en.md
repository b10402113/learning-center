# L1 overview

- Default to one competent agent (one capable model looping under limits on steps, cost, and time) with a few tools, each doing one whole job, and a context limited to the current step; a multi-agent design should be a conclusion, not a starting point.
- Each added agent multiplies three things — cost (it re-reads its own instructions), latency, and failure surface (each handoff is another place to break) — and extra agents often run the same model, so they aren't smarter.
- Only three cases earn a second agent: context isolation (a fresh worker holds only one subtask, so a fifth competitor's fee can't be mixed up with the first's), parallelism (fan out / fan in, a.k.a. scatter-gather, valid only when subtasks are independent), and specialization by configuration (own prompt, own tools, own model tier).
- Two production shapes: orchestrator-workers (the orchestrator decomposes, hands out scoped subtasks, integrates, and owns the outcome; workers stay stateless, bounded, and never talk to each other) and a pipeline with agentic stages for fixed order (triage → resolution → QA check, revising at most twice before a person takes over, with code deciding when the loop stops) — most production systems are sequential handoffs like the latter.
- Every handoff is a contract with five parts: one goal with a definition of done, scoped context, the smallest tool menu, a budget of steps/tokens/time, and a report schema — designed like an API boundary; example worker budget is 20 steps, 60,000 tokens, 5 minutes, and it never sees the other four competitors.
- Report schemas with named fields (findings + evidence pointer, confidence, artifacts, and a status/gaps field) beat free prose, because "delivery is free" means "free for members only" and integration quality is lost in paragraphs the orchestrator must interpret.
- Progress and spending live in a task state store the orchestrator owns, so a crashed worker resumes from the same contract and saved artifacts; a worker with a refund tool also needs idempotency keys.
- Budgets are hierarchical: a 400,000-token top-level splits into 80,000 for the orchestrator (kept for integration), 60,000 per worker, and a 20,000 reserve for one retry; a worker that runs out returns a partial report and never fails silently.
- Walked run: five contracts at 10:00, five workers fan out, competitor B's worker crashes after saving two notes and a fresh worker resumes, competitor E reports a missing commission rate as partial, a verification pass checks every number against its evidence pointer, and the manager gets the table at 10:09 — about 280,000 tokens; a published result reports multi-agent runs used roughly 4× the tokens of single-agent runs, buying time (about 9 minutes instead of 25).
- Errors compound one level up: five workers at 95% each are all correct only ~77% of the time, a bad report becomes a false fact the orchestrator builds on, and five agents mean roughly five times the trace — so record the contract and report at every handoff.
- Fixes for an integration that dropped a condition: tighten report schemas so every claim carries its conditions, add a verification pass at integration, and force the orchestrator to reconcile conflicting numbers rather than quietly pick one — none of these is a bigger model; also reject free-form agent debate, emergent negotiation, and agent chat as coordination by name, since none limits its rounds.
