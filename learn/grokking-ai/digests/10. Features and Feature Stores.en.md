# L1 overview

- A **feature** is an input value the model can know at prediction time; one request's features form a **feature vector**. A feature is not a raw table row (a raw signal is a recorded fact, and "orders in the last 30 minutes" is computed from many events), and it must never contain the **label** — a 38-minute real delivery time cannot be an input.
- Instead of listing features ad hoc, walk five **signal sources** — **content** (dishes in the cart), **actor** (the courier), **behavioral** (what actors did recently), **graph** (how actors connect; this courier picked up here 40 times), **context** (conditions now) — naming two per source yields ~10 in under a minute.
- Then sort into four **buckets** by how often the value changes: **entity** (slow property like vehicle type), **behavioral aggregates** (counts or averages over a window — the hardest engineering, needing second-level updates rather than nightly jobs), **contextual** (time of day), **cross** (this courier's past deliveries from this restaurant).
- Preprocessing: many counts have a **heavy tail** (most restaurants 5 orders/hour, a few 500), so use **log scaling**, **bucketing** (ranges like 0–10), and **normalization** after log scaling. **Cardinality** drives encoding: low-cardinality fields use **one-hot encoding** (vehicle type → 3 yes/no inputs); high-cardinality IDs need **embeddings** (a learned row in an embedding table), and the **hashing trick** fixes table size at the cost of collisions and slightly lower accuracy.
- Two ingestion **arms**: the **batch path** (scheduled jobs over stored data, cheapest per value but only as fresh as its last run) and the **streaming path** (reads an event log like Kafka and keeps windowed aggregates current within seconds via a processor like Flink, costing more). Both write into the **feature store**; two arms meeting at one store is a **lambda architecture** — put each feature on the cheapest arm that meets its freshness need (kitchen queue → streaming).
- The store has two faces: the **offline store** keeps every past value with its write time for training, the **online store** keeps only the latest value per entity (a key-value store, target under ~10 ms per read). One feature **definition** writes both faces to prevent **training-serving skew** — e.g. a nightly batch job counting canceled orders while the Flink job does not makes training numbers larger with no error; a **registry** (name, code, owner, freshness) stops another team rebuilding its own version.
- **Point-in-time correctness**: for a 6.02 p.m. example, the offline store holds 9 orders at 6.01 and 14 at 6.05 — the join must take 9 (what serving saw) and skip 14, or the model looks better offline than in production (**leakage**). **Request-time features** (exact route distance) must be computed while the user waits and come out of the **latency budget** — e.g. 100 ms total with 80 ms for a routing call leaves 20 ms; the common trap is calling that service with no plan. Three options when one call eats the budget: **cache** it (~1 ms), **approximate** it (straight-line distance × city ratio), or **default** it with a strict timeout plus a missing-value flag the model also saw in training, and state how you measure the accuracy lost.
- **Stale features**: if the streaming path falls 20 minutes behind, the online store keeps returning its last value with no error and the ETA comes out too short. Defend with a **freshness monitor** (alert when the latest value is older than the feature's limit, e.g. under a minute for kitchen queue) and by feeding the model the feature's **age** so it trusts old values less — **graceful degradation**.
