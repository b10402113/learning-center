# L1 overview

- Search is built like a recommendation system, but adds one input: the **query**. A recommender must guess what you want from history; in search you typed it — "that is the single biggest difference." The query is short (two or three words), may be misspelled, and must be understood (example: "red running shoes SZ10" for product search at a large online store).
- Three jobs in order: **query understanding** cleans up the query, **retrieval** pulls a few hundred possible matches (candidates) from the catalog, **ranking** sorts them, and a **business layer** applies store rules to the final page. Scale example: 100 million products, 10,000 QPS peak, P95 under 300 ms — no model can score 100M products that fast, so search uses a funnel where cheap stages narrow the list for expensive ones.
- Two offline graders on past queries before users ever see a model: **recall at 500** for retrieval (how many of a query's good results made the 500 candidates — a product missed here can never be ranked) and **NDCG** (Normalized Discounted Cumulative Gain) for ranking (each result has a grade and lower results count less; perfect order = 1.0; NDCG at 10 checks only the top 10). Grades come from a **judged set** of queries human reviewers graded, which avoids position bias. Real users decide which model ships.
- Online metrics: the primary is often **search conversion** (share of searches ending in a purchase). Guardrails include P95 latency and **reformulation** (retyping right after seeing results — a quick retype means the results failed, though some users add a size on purpose, so read the whole session). A search with no click is ambiguous: nothing found, or saw the price and chose not to buy.
- Data: product catalog details, search logs of each query and what the user did next, and judged sets. Query frequency is **Zipfian** — a few **head queries** worth **caching** (storing ranked results so the next user is faster) and a long tail of rare queries, many appearing once, where search fails most often.
- Clicks and purchases are labels but carry **position bias**: people click the top result partly because it is first, so a ranker learns to keep first whatever was already first. The fix is **preference pairs** from one session — the user skips results 1 and 2 then buys result 3, so result 3 beats each skipped result. Pairs reduce position bias but do not remove it.
- Baseline is **lexical retrieval**: products containing the query's words, scored by **BM25**. Query understanding has three jobs: fix spelling (SZ → size), add synonyms (sneakers), and extract intent (category = running shoes; attributes = red, size 10). Attributes like red and size 10 become **hard filters** that remove every non-match — a size 9 shoe is not slightly worse, it is wrong — but if the parser is unsure they become ranking hints instead.
- Lexical retrieval uses an **inverted index** (word → every product containing it) and catches exact terms like model number HX200, but suffers **vocabulary mismatch** ("something to keep coffee hot" shares no words with "insulated travel mug"). **Semantic retrieval** matches by meaning using **embeddings** from a **two-tower model** (one embedding for the query, one per product) with an **ANN index** for fast nearest neighbors — but HX200 filter may return the HX250 filter, so run both engines at the same time.
- Ranker is typically **gradient-boosted trees** over three feature kinds: **query features**, **product features** (rating), and **pairwise features** (one product with one query, like the BM25 score) — pairwise matter most because a popular product can still be wrong. Scoring all 500 with the best ranker is too slow, so an **L1 ranker** (cheap) trims to ~100 and an **L2 ranker** (heavy) orders those. An **LLM** is too slow and costly while the user waits.
- Latency trace: ~2 ms cache check (a cached head query skips ahead to step 6), ~15 ms query understanding, ~50 ms retrieval (the index is too large for one machine so it is split into **shards**, the query goes to every shard, and one service merges — **scatter gather**), ~20 ms L1 plus ~60 ms L2, ~10 ms business layer, then fresh price and stock fetched at **render time** (the moment the page is built) — total under 180 ms.
- Business layer removes products that cannot ship and places paid **sponsored products** in fixed slots, each passing a **relevance floor** (a minimum relevance score for this query) — without the floor, revenue slowly replaces relevance and users stop trusting results. Personal features (a user's usual size) can move a result a few places, but personalization is capped and never overrides relevance.
- Zero-result queries need a diagnosis: no inventory (store doesn't sell it) or vocabulary mismatch (sells it under other words). The first fallback relaxes the least confident hard filter; logging every zero-result query turns mismatches into new synonyms. Freshness differs: the inverted index updates in a second or two, so lexical retrieval finds a product added an hour ago; the ANN index refreshes on a cycle (nightly) because each new embedding must be computed.
- Shipping and cost: rankers retrain daily or weekly from new preference pairs, and each new ranker passes three gates — NDCG on the judged set must not drop, then shadow mode on live queries, then an A/B test on search conversion. Three cost levers: **cache hit rate** (at 30%, retrieval and ranking run for only 7,000 of 10,000 searches/s), the **L1/L2 split** (L2 scores 1 million candidates/s, not 5 million), and no LLM call per item (at a made-up price, those calls would cost over $40 million/day even at half peak). Failures are independent: if L2 times out the page shows the L1 order; the most dangerous failure is a **silent, stale cache** showing sold-out shoes at yesterday's price, so cache only the ranking (the ordered list of product IDs).
