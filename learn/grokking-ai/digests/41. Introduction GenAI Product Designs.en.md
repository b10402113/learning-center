# L1 overview

- **The model meets none of these needs; the system around it meets all of them**: cross-session memory, thousands of simultaneous users, customers trying to break the rules, and a predictable bill. A **Gen-AI product** is a generative model plus delivery that is safe, fast, and affordable. The team usually **buys the model**, so design work happens in three parts — the **request path** (serves one request while the user waits), the **state stores** (remember for a stateless model), and the **feedback loop** (logs every request; a **golden set** gates each change).
- **State stores**: a **conversation store** (every message) and **user memory** (lasting facts like preferred language). The model keeps nothing between requests, so a Gen-AI product is not a model, not one model (most products use a small and a large one, with small classifiers running the gates), and not automatically safe because its model was trained to refuse — that is a tendency, not a guarantee. Real enforcement comes from **guardrails outside the model plus permissions and code**.
- **Six request-path stages**: (1) **gateway** — identity, **rate limits** (~20 messages/min), **token budget**; (2) **input gate** — often a **moderation classifier**, a small fast model scoring for abuse, run before the expensive call so a rejected request costs nothing; (3) **context assembly** — build the prompt from recent messages, a summary of older ones, and only documents this user may see; (4) **router and model** — routine requests to a small cheap model, hard requests to a larger one; (5) **output gate** — check for unsafe content, another person's private data, and unsupported claims; (6) **delivery** — stream the result. **Background jobs** (e.g. rewriting a long conversation's summary) update state without making the user wait.
- **Worked message trace**: 0 ms gateway checks session + 20/min limit + token budget; ~20 ms moderation passes; the message is saved **before any answer exists** so a later failure cannot lose it; ~0.2 s context assembly builds ~3,000 tokens from yesterday's summary and the customer's credits; a status question whose answer is on record routes to the small model; the output gate holds **each sentence** until it contains no other customer's data and any credit amount ($6.40) matches the record; first sentence at ~0.9 s — slower, but "text on the screen cannot be taken back". Only step 5 used the model; the rest was product work.
- **Four product archetypes, each pushing one constraint to an extreme**: **chat assistant** → state and scale (100M weekly users; a **fallback model** and second provider answer if generation fails); **code assistant** → **latency** (inline completion uses a small specialized model; on failure no suggestion appears, because a slow editor loses developers); **AI-powered search** → must not degrade existing search (~300 ms baseline) so the generated answer fills an optional box when ready, gated by a trained **trigger** model (answering every query at ~1¢ would cost ~$8.6M/day); **text-to-image** → compute per request (~10 s GPU time, an **asynchronous** queue job; 2M images/day keeps 200+ GPUs busy; **utilization** decides much of the cost).
- **Shared weakness and defense**: instructions, user text, and retrieved documents share one prompt and the model cannot reliably tell instructions from data. **Prompt injection** — **direct** (user types instructions, e.g. a **jailbreak**) or **indirect** (instructions hidden in content the system reads; the user is the victim; most dangerous when it could trigger an action). No training or prompt wording closes it, so defenses layer: input gate before the model and output gate after, understanding that the input gate sees only what the user typed and cannot catch hidden instructions; the model sees only what the request needs; code outside the model decides whether an action is allowed. The image service checks the finished image because a harmless prompt can still produce an unsafe image — **an input check cannot replace an output check**.
- **Common mistakes and method**: drawing only the model call (draw the six stages, the state stores, the loop from the start); expecting the model to remember (say where the conversation is stored); sending everything to the largest model (route routine requests to a small model, measure quality on each route); run new AI features beside the old path with their own timeouts; check the output, not only the input; price one request then multiply by daily volume.
