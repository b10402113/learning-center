# L1 overview

- Lesson 7, Introduction: ML Systems Foundations — The model is the smallest part of the request; an ML system is an offline plane that builds models, an online plane that serves them, and a feedback loop that keeps them accurate, joined by the model registry, the logs, and the feature store; follows one 100 ms ETA prediction from checkout through label arrival, nightly training, and shadow/canary rollout.
- Lesson 8, Training vs Serving — Training optimizes throughput (nightly, spot instances, checkpoints, soft failure) and serving optimizes latency (always-on replicas, hard failure); only the model flows forward and only logs flow back; the four training stages; the serving latency budget where feature fetch usually dominates; training-serving skew from two code paths (local vs UTC hour) and time travel (leaky averages) and its cures.
- Lesson 9, Where Training Data Comes From — Three label sources (natural outcomes, user behavior, human annotation) with their cost, delay, and bias; versioned guidelines, inter-annotator agreement (Cohen's kappa), and gold questions; LLM labeling with human audit slices; downsampling/reweighting and recalibration for rare positives; four negative types for retrieval; temporal splits, a four-item leakage checklist, and mature-window-plus-provisional labels for slow chargebacks; data rights and lineage.
- Lesson 10, Features and Feature Stores — A feature is an input value knowable at prediction time; five signal sources (content, actor, behavioral, graph, context) and four buckets (entity, behavioral aggregate, contextual, cross), with bucket 2 as the hard one; numeric/categorical/sparse-id recipes; batch vs streaming vs request-time computation in a lambda shape; the offline/online feature store with one definition, point-in-time correctness, and a registry; request-time latency plans; freshness monitoring and letting the model see a feature's age.

- `#L426-L490` — Part 2: Different jobs, different rules — throughput vs latency, nightly vs always-on, minutes-hours vs 10–100 ms, spot instances with checkpoints vs always-on replicas behind a load balancer; a late model is a soft failure while a serving outage hits users at once.
- `#L491-L554` — Part 3: What crosses between the planes — exactly two artifacts: the model flows forward through the registry, the logs flow back with exact features and model version; the feature store is shared infrastructure, not a third artifact.

- `#L666-L760` — Part 6: Training-serving skew — two code paths (a New York restaurant's hour 19 vs UTC hour 23) cured by one shared definition plus parity tests; time travel through a leaky "average today" feature cured by a point-in-time join; the structural cure of training on logged serving features; skew vs distribution shift.
- `#L761-L805` — Part 7: Using this in an interview — the two-plane 30-second answer, rolling back and reading lineage when complaints rise, and how to detect feature disagreement.
- `#L806-L831` — Lesson 9 header and vocabulary: training example, natural/behavioral label, human annotation, guideline, inter-annotator agreement, gold question, class imbalance, calibration, temporal split.
- `#L832-L850` — Part 1: Labels do not arrive by themselves — four models at the delivery company need four different labels; a label is a design decision with a source, cost, delay, and error type.
- `#L851-L989` — Part 2: Three sources of labels — natural outcomes (direct but delayed 2–8 weeks, sometimes censored), user behavior (free and instant but noisy and position-biased), human annotation (controllable but cents-to-dollars and hours-to-days); a label is a measurement of truth, not truth, and not always the goal.
- `#L990-L1027` — Part 3: Making human labels trustworthy — versioned guidelines so old labels keep their meaning, inter-annotator agreement on ~10% of items with Cohen's kappa, gold questions mixed into queues to audit reviewers continuously; the analyst review queue is itself a label source.
- `#L1028-L1102` — Part 4: Labeling with an LLM — the LLM labels everything, humans check a random sample plus every uncertain/disagreeing case, gold questions check the humans, and each label records source and guideline version; LLM errors are systematic, so human-labeled audit slices per dialect and per adversarial pattern are required.
- `#L1103-L1133` — Part 5: When positives are rare — 0.2% fraud makes accuracy useless; downsampling (keep all 20k fraud, 1-in-50 legitimate) or reweighting (a fraud mistake counts 50×) teaches the pattern, but both inflate scores and require recalibration.
- `#L1134-L1209` — Part 6: Choosing negatives for a retrieval model — random negatives are too easy, in-batch negatives are the default (free and realistic but popularity-biased), popularity-corrected sampling removes that bias in training, and a small share of hard negatives teaches the boundary but can collapse the model.
- `#L1210-L1285` — Part 7: Splitting data without leaking the future — a temporal split instead of a random one; the four-item leakage checklist (future data, post-label features, label-adjacent features, near-duplicates); training this week's fraud model on a mature 7–26-week window plus provisional proxies for the last six weeks, judged on final labels only.
- `#L1286-L1301` — Part 8: Whose data it is — may you use it, how long may you keep it, and what happens on account deletion (derived sets, feature tables, embeddings); lineage is what makes deletion findable.
- `#L1302-L1350` — Part 9 and Part 10 — the 30-second label answer, three follow-ups (correlated LLM errors, slow chargebacks, excellent offline vs poor production), and six common mistakes.
- `#L1351-L1373` — Lesson 10 header and vocabulary: raw signal, entity, window, aggregate, batch/streaming path, request-time feature, offline/online store, point-in-time correctness.
- `#L1374-L1426` — Part 1: What a feature is — one input value knowable at prediction time, read as a feature vector (prep time 14 min, kitchen queue 9, route 2.1 miles, 6:02 PM, bicycle); features change at different speeds; a feature is not a raw row, not the label, and not free.
- `#L1427-L1497` — Part 2: Finding features — walk five signal sources (content, actor, behavioral, graph, context) to get about ten features in a minute, then sort into four buckets; behavioral aggregates are the hard bucket because they must be fresh and need streaming compute.
- `#L1498-L1549` — Part 3: Turning raw signals into model inputs — log-scaling/bucketing/normalization for heavy-tailed numerics, one-hot or small embeddings for low-cardinality categories, learned embedding tables (with optional hashing) for sparse ids.
- `#L1550-L1633` — Part 4: Where features are computed — batch path (cheap, hours old), streaming path (fresh within seconds, costlier), request-time inline computation; the lambda shape writes both arms into the feature store, and each feature goes on the cheapest arm that meets its freshness need.
- `#L1634-L1713` — Part 5: The feature store — offline store (full history, point-in-time joins) and online store (latest value per entity, sub-10 ms target); one definition feeds both faces to prevent skew (the Spark-counts-cancellations vs Flink example); the 5:55/6:01/6:05 kitchen-queue join; a feature registry prevents cross-team skew.
- `#L1714-L1759` — Part 6: Request-time features — values knowable only now (route distance); the 80-of-100 ms trap and three fixes (cache zone-to-zone, approximate with straight-line distance, strict timeout with a trained-in default and missing-value flag); why not to compute everything at request time.
- `#L1760-L1810` — Part 7, Part 8, Part 9 — stale features fail silently (a 20-minute lagging stream reads 3 orders while 15 wait), so monitor feature age and add age as an input for graceful degradation; the 30-second serving answer and three common mistakes.
