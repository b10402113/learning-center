# L1 overview

- A choice is hard not because you don't know the options but because you can't say what makes one right: two candidates both pick RAG, but only "the failures are missing facts, so RAG" shows judgment — the deciding variable is named before the tool, and interviewers grade the reason, not only the option.
- Each cheat sheet is one compact table that leads with the deciding variable, has rows mapping a signal in the question to the option it picks and the reason, and ends with a default (the option you start with when the question gives no variable); say it out loud as "the variable here is X, so Y" and say what evidence would change it, turning "it depends" into an answer — don't memorize rows, the variable still applies when one number changes.
- Step 1 (family): deciding variable is what the model mainly outputs — score → predictive, content → generative, actions through tools → agentic; design centers follow (predictive on the logs-to-retraining loop, generative on evaluation since content has no single correct label, agentic on what the system may do because actions change the world); the support assistant is generative until it issues refunds, which becomes agentic.
- Step 2 (offline metric): two facts pick it — output shape and base rate; when fraud is rare, accuracy fails (it rewards always saying no), and compare against the incumbent model in use today.
- Step 3 (data mapping): a feature's required freshness decides where it's computed — restaurant average prep time on the batch path, current kitchen orders on the streaming path, this-orders route at request time.
- Step 4 (model): build vs buy turns on whether quality lives in your own data (fraud logs have no vendor, so build in-house; writing skill is easy to buy, so call a hosted model); then improve in order — prompting changes what you tell it, RAG what it can read, fine-tuning its weights — starting with prompting and sorting failures (missing facts → RAG, wrong tone → fine-tuning); never put facts or permissions in the weights.
- Workflow vs agent: a workflow runs code-fixed steps (transcribe/summarize/extract action items is a workflow); an agent lets the model choose each next step while running (diagnosing a customer issue that depends step-to-step) and needs budgets on steps, time, and cost; the default is a hybrid — a workflow shell for known paths, a small agent core for the open part, and every proposed action through a code gate; a second agent multiplies cost and failure modes, so keep one without a clear gain.
- Step 5 (serving): batch inference runs ahead when a slightly old answer is fine, online runs per request when it needs request-time information, streaming starts when an event arrives with nobody waiting; how the user waits decides sync vs async (a chat reply streams word by word, four images queue a job) and streaming makes waiting feel shorter without reducing the work.
- Retrieval: the deciding variable is query shape — an identifier like "what does error E4022 mean?" favors lexical (BM25), a paraphrase like "I'm locked out of my account" favors vector, and real traffic mixes both so run both and merge with Reciprocal Rank Fusion (merges by rank so score scales need not match); a few million chunks can live in your existing DB (pgVector on Postgres).
- Grounding and gating: an answer is grounded when retrieved text supports every claim; checks cost time so the deciding variable is the stakes — low-stakes tracking needs citations and sample checks, a refund amount is checked claim-by-claim, and legal research refuses rather than guesses; when a check can't run, fail open or closed by which error costs more (a long-time customer's small payment fails open, a large payment fails closed), and write the policy before an outage plus alert whenever a fallback runs.
- Post-launch and release: three evaluation layers chosen by whether code can assert the check or it needs judgment — programmatic checks (almost free), an LLM judge with a written rubric, human review of a small sample that finds new failures; every change climbs offline evaluation → shadow (logs only) → canary (small slice) → ramp, with a rollback trigger named in advance (e.g. "rollback if checkout conversion drops 2%").
- Drift: the deciding variable is measured decay rate — slow steady decay gets a measured schedule (~every week or two); fraud has an adversary so retrain faster and keep fast rules beside the model; a sudden change (new city launch) triggers a retrain, but check the data pipelines first since many drift alerts are broken pipelines; pure online learning updates non-stop with no evaluation gate, so one bad batch becomes a bad model.
- Step 7 (cost): every large call is billed by token, so the cheapest call never happens — a semantic cache reuses an answer for the same meaning but never cache personal answers like "where is my order"; route easy requests to a small model, or cascade (small first, failed answers move up); at high steady volume consider self-hosting, finding break-even by dividing the fleet's daily cost by the API cost of one request and adding staff costs.
- The one rule with no variable: permissions live in code — inside retrieval and inside the tool runtime, not in the prompt (a user can persuade the model to ignore it), not after generation (the model already read the restricted text), not in the waits (identical for every user); when group lookup fails, fail closed to public content — with no check nothing stops a leak, so there is nothing to trade off.
- Practice: 10 minutes a day beats one long session the night before; cover the summary table and say each reflex sentence, counting a missed variable as a miss even with the right option (the support assistant giving an old refund window is missing knowledge, fixed by RAG over the policy pages).
