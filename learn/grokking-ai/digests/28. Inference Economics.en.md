# L1 overview

- A delivery-time model ran on four small CPU machines at a few milliseconds per prediction; an LLM writes text answers that take seconds, and its price grows with length. So an LLM design has **two meters on every request**: a latency meter (how long the user waits) and a cost meter (money, counted in **tokens**, not requests — a long chat and a short question are each one request, but the chat can cost many times more).
- The latency meter has two readings — **time to first token** and **time until the answer is done**. **Streaming** sends the answer word by word so the first words appear sooner, but it writes the same tokens and saves no money. A **GPU batch** is a group of requests one GPU processes together: a bigger batch saves money but can make each user wait longer, and "one combined number would hide both effects."
- Counters: **input tokens** are what you send (instructions, conversation history, the new question); **output tokens** are what the model writes back. A **provider** is a company that sells model access; a **frontier model** is one of its largest, most capable, usually most expensive models. Example frontier prices are **$3 per million input** and **$12 per million output** tokens — output costs four times as much, commonly **3 to 5 times**. A **small model** has far fewer learned numbers and often costs a tenth of the frontier price or less; real prices change, so in an interview say you'd check the current price list.
- Each request runs in two stages. **Prefill** reads all input tokens together, keeping the GPU's many cores busy so each input token costs little GPU time. **Decode** writes output one token at a time, each depending on the ones before it so each needs its own step, and every step reads **all the model's weights** — which is why output costs more and the bill follows the tokens. A typical chat turn (3,000 in, 300 out) is about **$0.013**, around a cent on a frontier model.
- Use the **unit economics** habit: price one conversation, then multiply by the count. One support conversation has 10 turns, each with ~200 customer tokens and ~300 bot tokens, plus **550 tokens of fixed instructions** per request, and the model keeps no memory so each turn resends the whole conversation. Turn 1 sends ~750 tokens, turn 10 ~5,250 — about **30,000 input tokens** per conversation plus **3,000 output**, about 33,000 total: input $0.09 + output $0.036 ≈ **$0.13 per conversation**. At 100,000 conversations a day that's ~**$13k/day** and ~**$400k/month**.
- Output was only 3,000 of the 33,000 tokens, and most input was old history resent again and again — so a 10-turn chat costs far more than 10 times its first turn. A human-handled ticket costs about **$4**, and when the bot can't resolve a chat the customer still reaches a human at $0.13 + $4, so compare **total support costs per correctly resolved issue**.
- Three levers follow from the unit: **summarize the history** (later turns send a short summary instead of the full earlier text, which could cut the 30,000 input tokens by about half but can drop details, so test it); **route easy turns** (like "where is my order") to a small model at a tenth of the price, after measuring its quality; and **cache what repeats** (some providers reuse the shared start of each request, like the 550 tokens of fixed instructions, at less cost than processing them again).
- Hosted API vs self-hosting is a **break-even you calculate, not a preference**. Self-hosting means paying for GPU hours, so you must know what limits one GPU — often **memory**. At 16-bit precision each **parameter** (each weight) takes 2 bytes, so a 70-billion-parameter model (**70B**) needs about **140 GB** for weights alone, while a large data-center GPU often has **80 GB** — more than one GPU just to load.
- During decode the model stores its work on earlier tokens in the **KV cache** (key-value cache) in GPU memory so it doesn't redo that work each step; every active request has its own KV cache, which grows as the chat lengthens — one long chat can need a gigabyte or more. So the memory left after the weights, not raw compute, often limits how many requests a GPU serves. **Quantization** stores weights with fewer bits per number (e.g. 8 instead of 16): the 70B model then needs about 70 GB, and on two 80 GB GPUs free memory grows from about 20 GB to about 90 GB; lower precision can reduce quality, so test it.
- **Memory bandwidth** is how fast data moves from memory to the GPU's cores; with one request each step makes one token so the cores mostly wait. **Batching** packs many requests onto one GPU so their decode steps run together and one pass over the weights makes a token for every request — cost per token drops, and more free memory allows bigger batches. **Utilization** is the share of a fleet's capacity doing useful work; idle GPUs cost the same per hour so low utilization raises cost per token, but a fully busy fleet has no headroom for a spike, so requests queue and latency jumps — aim for roughly **60 to 80 percent at peak**, leaving headroom for spikes and failures.
- Self-host sizing example (a high-volume small open model, not the support bot): peaks at **50 requests/second** with 500 output tokens each = **25,000 output tokens/second**; a load test shows one node sustains about **2,500**, so the math says 10 nodes. Ten would run at full load at peak, so run **14 nodes** — about 70 percent at peak and the fleet can lose a node and keep serving. At $2–$4 per GPU hour that's roughly **$245k–$490k per year**, before networking, storage, monitoring, and the engineers who run it.
- Guidance: low or spiky volume favors a **hosted API**; high, steady volume favors **self-hosting** because the fixed fleet cost spreads over many tokens. Find the **break-even point** where both options cost the same: a provider hosts the same small model at a tenth of frontier prices, so one request (1,000 in, 500 out) costs $0.0009; at $3 per GPU hour the 14 nodes cost about $1,008/day, giving break-even at about **1.1 million requests/day**, or **13 per second all day**. Real traffic averaging 20 requests/second would cost the API about $1,555/day, and the fleet saves about **$200k a year** before people costs — and most real systems use **both**.
- For the support bot a **router** picks the model per turn (refund disputes to a frontier model, order status to a small one). A hosted API has a **rate limit** (the most requests or tokens per time window, e.g. one minute) and providers fail sometimes, so: **client-side budgeting** tracks your own token use and gives each feature a share; **back pressure** slows or queues new work near the limit instead of sending requests the provider will reject; **graceful degradation** still gives users something (a shorter answer or a human agent); and **blind retries** add load at the worst moment, so retry a few times, wait longer each time, then degrade.
- Closing habit: when an interviewer asks about cost, price one conversation out loud, then say these are orders of magnitude and you'd verify current prices.
