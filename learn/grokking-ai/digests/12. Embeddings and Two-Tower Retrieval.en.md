# L1 overview

- Why retrieval exists: with 100 million products and a page that must load in a few hundred milliseconds, scoring everything fails (even at 1 microsecond per product, 100 seconds). The **funnel** narrows the catalog to ~500 candidates first, then a richer model **ranks** them, then business rules pick the final 20; retrieval only needs good items to be somewhere in the 500, measured as **recall** — a miss is lost forever because no later stage sees it.
- **Embeddings** replace IDs: an ID is a name, not a measurement (nearby IDs are not similar), and one-hot vectors (100 million positions) make every pair look equally different. An embedding is a learned 64- or 128-number vector stored as a table row, trained until IDs that behave alike get similar vectors; the **dot product** scores the match (two hiking boots 1.1 and 1.05, a toaster 0.1).
- Four training routes by available **signal**: **matrix factorization** (a huge user×item engagement table), **two-tower contrastive training** (pulls matching pairs together, pushes non-matching apart, can read many features), **graph embeddings** (from edges like follows/saves; fits a social app with little click history), and **pre-trained content encoders** (title or photo to a vector even with no clicks). With lots of click history, use two-tower.
- Two-tower mechanics: the **user tower** reads the user ID embedding, session products, and time of day; the **item tower** reads the item ID embedding, category, price, and content-encoder vectors. The towers never see each other's features and meet only at the dot product, so each runs alone. Negatives: **in-batch negatives** are the default (other shoppers' items in the batch), with a **popularity correction** so popular items are not penalized for being popular; **hard negatives** (shown but not clicked) sharpen the boundary but too many hurt because some are items the shopper would have liked.
- Serving split by time: each night a batch job pushes all 100 million products through the item tower and builds an **ANN index** (**Approximate Nearest Neighbor**, finds closest stored vectors without checking everyone); the user tower runs per request (~5 ms), then the index returns the 500 closest in ~10 ms. **User vectors must be fresh** (intent changes within a session); item vectors can be a day old. The index is fast but nearly right — tune it until the recall loss is acceptable — and memory-hungry: 100 million vectors of 128 × 4-byte numbers ≈ 51.2 GB.
- **Cold start**: a new item's ID embedding has learned nothing, but the item tower reads the title and image, so a new product gets a sensible vector on day one where retrieval can find it. A **cross network** (sees user and item together) is more accurate and can learn crossed features, but its output depends on both, so it cannot be precomputed and would run 100 million times per request — it belongs at ranking.
- **Version skew**: the towers are trained together, so vectors only match within one version. Deploying only a new user tower against the old item index is a **silent outage** — latency normal, error rate zero, candidates wrong, engagement drops quietly. Safe upgrade: run all products through the new item tower, rebuild the index beside the old one, test the pair's recall on recent logs, then promote both **atomically** and keep the old pair for rollback (at 20,000 products/second, the first step takes ~83 minutes for 100 million).
- When not to use it: a smaller city with ~2,000 restaurants can score all of them exactly, so skip embeddings and the ANN index; inputs already numeric (a $40 price) need no embedding; regulated decisions (a bank declining a loan) need explainable reasons, not vector distances. The same nearest-vector search later powers LLM retrieval over text passages.
