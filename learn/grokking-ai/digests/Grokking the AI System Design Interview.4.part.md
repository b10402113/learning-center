# L1 overview

- Lesson 11, Batch vs Online Inference — Batch precomputes last night's 500 dishes per customer into a key-value store (a 1 ms lookup); online runs the model while the user waits (10–100 ms). One question decides: does the prediction need information that exists only at request time? Covers the cost table, the price of precomputing (25M customers × 500 dishes = 12.5B nightly rows, fixed by active-only, shorter lists, coarser segments), the precompute-then-re-rank hybrid, streaming inference behind a queue, and each mode's failure behavior.
- Lesson 12, Embeddings and Two-Tower Retrieval — A 100M-item catalog needs a funnel (retrieval → ranking → rules) because scoring everything would take 100 seconds; IDs mean nothing so they become learned embeddings; four training routes (matrix factorization, two-tower contrastive, graph, pretrained content encoders); the two towers meet only at the dot product, so the item tower runs nightly into an ANN index while the user tower runs per request (~5 ms + ~10 ms); version skew as a silent outage and the paired up-grade; when not to use embeddings.
- Lesson 13, Model Serving Basics — A stateless model server loads one registry version and any replica can answer; the ~100 ms latency budget split by stage (feature fetch is the usual bottleneck) and set on p99; three speed/cost tools (feature caching, micro-batching, compression via distillation/quantization/pruning) and "compress before you change hardware"; shipping through offline → shadow → sticky canary (1%) → 5/25/50/100% ramp with named rollback triggers; the four-rung fallback ladder and fail open vs fail closed.
- Lesson 14, Offline Evaluation: Choosing the Metric — Offline metrics only pick which models deserve an online test; the output shape picks the metric family (classification, ranking, regression) and the base rate decides whether accuracy or ROC-AUC can be trusted. Covers precision/recall and the threshold as a business decision (0.9 → 90%/45%, 0.5 → 60%/75%, 0.2 → 30%/90%), PR-AUC vs ROC-AUC at 0.2% fraud, recall@k / NDCG / MRR, MAE vs RMSE plus p90 and per-city reporting, calibration (Platt scaling, isotonic regression), and comparing against both a naive baseline and the incumbent.

# L2 detail

- `#L1-L22` — Lesson 11 header and vocabulary: streaming inference, request-time information, key-value store, candidate, re-rank, hybrid precompute-then-re-rank, queue, cadence.
- `#L23-L112` — Part 1: Two ways to run the same model — the 2 AM job stores 500 dishes per customer and the 7 PM request only looks them up (~1 ms) vs checkout running features and model in 10–100 ms; batch is not request batching and not a cache.
- `#L113-L132` — Part 2: The deciding question — does the prediction depend on information that exists only at request time? ETA and fraud must run online, the "videos you might like" shelf can batch, search ranking is hybrid.
- `#L133-L232` — Part 3: Batch and online side by side — when the model runs, which inputs it can use, work at request time, cost shape (off-peak vs peaks with traffic), freshness, failure behavior, and wasted work.
- `#L233-L263` — Part 4: The price of precomputing — 25M customers × 500 dishes is 12.5B stored rows nightly while 80% never open the app; fixes are active-only precompute (5M → 2.5B), shorter lists (200 instead of 500), and coarser segments; tie cadence to measured freshness value.
- `#L264-L330` — Part 5: The hybrid — precompute, then re-rank — nightly 500 candidates per active customer; at request time look up in ~1 ms, fetch live context, let a light model re-rank 500 with location/time/open restaurants, show and log the top 20; falls back to the stored order if the re-ranker fails.
- `#L331-L390` — Part 6: Streaming inference — online inference with a queue in front instead of a waiting caller (uploaded menu photo, video upload, transaction review); the queue absorbs bursts (3,000 photos at once); differs from the hybrid because nobody waits; the three modes in one line.
- `#L391-L443` — Part 7, Part 8, takeaways — batch fails soft (yesterday's predictions, versioned swaps, alert on row age), online needs a planned fallback, hybrid falls back to the stored order, streaming alerts on oldest-event age and moves poison events to a dead-letter queue; the dishes-shelf 30-second answer.
- `#L444-L470` — Lesson 12 header and vocabulary: ID, vector, dot product, one-hot encoding, tower, two-tower model, positive/negative pair, retrieval, ranking, ANN index, cold start, version skew.
- `#L471-L493` — Part 1: 100M items, a few milliseconds — scoring every product at 1 µs each would take 100 seconds, so a three-stage funnel (retrieve 100M → ~500, rank, apply rules → 20) with retrieval judged on Recall@500.
- `#L494-L557` — Part 2: Why IDs need embeddings — an ID is a name, not a measurement, and one-hot vectors at 100M positions say nothing about similarity; a learned 64/128-number embedding puts two hiking boots close (dot 1.1, 1.05) and the toaster far (0.1); embeddings are for meaningless raw forms, not for price/distance.
- `#L558-L626` — Part 3: Four ways to train embeddings — matrix factorization (IDs only, needs rich logs), two-tower contrastive (features plus interactions, the retrieval route), graph embeddings (edges, social apps), pretrained content encoders (cold-start bridge); teams often combine content vectors into the item tower.
- `#L627-L693` — Part 4: The two-tower model — user tower reads the user embedding, session views, and time of day; item tower reads the item embedding, category, price, and title/photo vectors; the towers never see each other and meet only at the dot product; training pushes positive pairs together and uses in-batch, popularity-corrected, and a few hard negatives.
- `#L694-L776` — Part 5: Serving: split the towers — the item tower embeds 100M products nightly into an ANN index (128 numbers × 4 bytes × 100M ≈ 51.2 GB), the user tower runs per request (~5 ms) and the index returns ~500 candidates (~10 ms); item vectors can be a day old, user vectors must be fresh; cold start through content features.
- `#L777-L814` — Part 6: Why not one network that sees both — a cross network can learn crossed features and is more accurate, but its output cannot be precomputed, so it belongs at the ranking stage over a few hundred survivors.
- `#L815-L884` — Part 7: Version skew: the silent outage — deploying a v2 user tower against a v1 item index leaves latency normal and errors at zero while candidates are wrong; the safe upgrade re-embeds the catalog, rebuilds the index beside the old one, tests recall, and promotes both atomically with version tags (~83 minutes to embed 100M products at 20k/s).
- `#L885-L897` — Part 8: When not to use embeddings — a small catalog (2,000 restaurants) can be scored exactly, already-numeric inputs need none, and decisions that must be explained to a regulator favor interpretable features.
- `#L898-L940` — Part 9, Part 10, takeaways — the same nearest-vector idea carries to text retrieval, with the same paired-version rule; the two-tower 30-second answer and three common mistakes.
- `#L941-L958` — Lesson 13 header and vocabulary: model server, stateless service, replica, batching, model compression, canary release, sticky assignment, fail open/closed.
- `#L959-L1019` — Part 1: What it means to serve a model — the ETA gradient-boosted tree; a stateless server loads one version and any replica can answer, a readiness check keeps first-request slowness off users; separate model service (extra hop but independent deploys/scaling) vs model inside the application.
- `#L1020-L1132` — Part 2: The latency budget — 10–100 ms end to end, set on p99; per-stage ranges (routing 1–5, feature fetch 5–20, request-time features 0–15, inference 1–10, response 1–2, logging off the critical path); the feature fetch is the usual bottleneck and runs concurrently with the route call; every stage gets a timeout and at most one bounded retry.
- `#L1133-L1190` — Part 3: Making serving faster and cheaper — feature caching for hot entities (short expiry, still stateless), micro-batching to raise throughput (a small wait that must fit the budget), compression by distillation/quantization/pruning; choose CPU for tabular trees and compress before buying GPUs; four CPU replicas across two data centers because failure, not load, sets the count.
- `#L1191-L1279` — Part 4: Shipping a new version safely — offline evaluation, shadow mode (doubles inference cost, so sample it), sticky canary at 1% by user-id hash, then 5/25/50/100% ramp; a named rollback trigger (checkout conversion −2% or p99 > 100 ms) with the previous version kept warm; retrieval models promote with their index; canary asks "is it broken," A/B asks "is it better."
- `#L1280-L1343` — Part 5: When the model fails — the four-rung fallback ladder (previous version, cached recent prediction, simple heuristic, product default), each tested in advance and counted; fail open vs fail closed for a timed-out fraud model; a dead-letter queue for jobs that keep crashing workers.
- `#L1344-L1380` — Part 6, mistakes, takeaways — the deploy-and-serve 30-second answer, CPU-not-GPU for a tree model, naming metric and threshold instead of "watching dashboards."
- `#L1381-L1398` — Lesson 14 header and vocabulary: offline evaluation, test set, metric, base rate, score, threshold, proxy.
- `#L1399-L1428` — Part 1: What offline evaluation decides — it filters which candidates earn a shadow run and an A/B test; it never decides the launch; a report states the metric, the base rate, the baselines, and per-group results.
- `#L1429-L1507` — Part 2: Two facts decide the metric — the problem family (classification/ranking/regression) picks the metric family and the base rate decides whether accuracy and ROC-AUC can be trusted; quote every number against two baselines.
- `#L1508-L1663` — Part 3: Classification: precision, recall, and the threshold — accuracy fails at 0.2% fraud (99.8% by predicting "not fraud"); 1,500 of 2,500 flags and 1,500 of 2,000 frauds give 60% precision and 75% recall; three thresholds trade blocking good customers against missed fraud and the risk team owns the row; PR-AUC across all thresholds (random ≈ 0.002), and why ROC-AUC's false-positive rate is diluted by millions of easy negatives.
- `#L1664-L1734` — Part 4: Ranking: Recall@k, NDCG, and MRR — candidate generation is judged on recall@500 (3 of 4 ordered restaurants = 75%), the final order on NDCG (graded relevance, position discount where slot one counts ~3.5× slot ten, normalized 0–1), and navigation queries on MRR (1, 0.5, 0.25); judged sets vs behavioral labels, with position bias in the latter.
- `#L1735-L1808` — Part 5: Regression: MAE, RMSE, and the tail — MAE treats early and late equally (both models 4.0) while RMSE squares misses so one 16-minute miss lifts Model B to 7.2; report the p90 error (one order in ten misses by more than 12 minutes) and every city so a bad segment cannot hide.
- `#L1809-L1840` — Part 6: Calibration — a calibrated 0.10 means about 10% real fraud; AUC checks only order, so halving every score changes nothing there; calibration matters when a score multiplies money ($10 review rule, expected loss, ad auction); fix with Platt scaling or isotonic regression on held-out data and check by score bucket per segment.
- `#L1841-L1931` — Part 7: Compare against baselines — the naive baseline (majority class, popularity, yesterday's value) says whether a model is needed at all; the incumbent says whether the switch is worth it; a 6.0 vs 6.2 minute MAE is 12 seconds for a whole pipeline; when offline improves but the A/B is flat, the proxy drifted from the goal.
- `#L1932-L1963` — Part 8, mistakes, takeaways — the fraud 30-second answer (classification, 0.2% base rate, PR-AUC, risk-owned threshold, calibration for the dollar rule), MRR for one-right-answer search queries, and one metric per ranking stage.
