# L1 overview

- The question is designing a home feed for a social app (Instagram/LinkedIn). Say the recommendation funnel transfers, then spend the interview on the four things that change — rebuilding the funnel takes 10 minutes, the new problems need the rest.
- What changes: (1) the candidate pool is **social** — most candidates come from accounts the user follows, so hundreds to thousands of posts, not millions; (2) **good is plural** — a good video was one you watched, a good post gets comments and doesn't get hidden; (3) **integrity sits inside ranking** — a feed ranked purely on engagement fills with **bait** (posts built to provoke reactions), so quality checks belong in the ranker.
- Decide how you'll know the feed is better: the primary/North Star metric is usually **daily sessions per user**; guardrails are the **hide rate** and **report rate** (share of impressions ending in that action), either able to block a launch even when sessions rise. Engagement doesn't show whether people were glad, so **continuous surveys** ask a small daily sample "was this post worth your time?" and train a p-of-worthwhile head, graded offline by AUC on held-out data.
- Retrieval uses three sources: **fan-in** (recent posts from all followed accounts — most candidates), **spillover** (posts from unfollowed accounts your network engaged with), and **suggestions** (stranger posts matching your interests, usually via embeddings). For Maya: 400 followed accounts ≈ 1,500 unseen posts, +300 spillover, +200 suggestions ≈ 2,000 candidates.
- Labels: log every impression with screen position; later events become yes/no labels, e.g. dwell time over a 10-second cutoff. **Negative events** (a hide) are rare and deliberate — most impressions end in a scroll, and a missing like means little because people skip liking posts they enjoyed — so weight them heavily in training and include them in evaluation, or a model that misses hides looks good offline.
- Baselines ascend: chronological → (recency score × **affinity**, how often the user interacts with the author) → a **multitask model**: a shared body learns a user+post summary and small **heads** each turn it into one probability (p like, p hide, p worthwhile). This lets rare events like reports learn from common ones, gives every prediction in one call, and needs no new model to add a head.
- Sorting needs one number, so a **value formula** sums each prediction × a **weight**, with negative terms subtracting predicted harm. Example: post A (a friend's trip photo) vs post B (an angry argument) — without negatives B ranks first, but people are 10× more likely to hide the argument, so with negatives A scores 0.53 and B 0.20. The model does not learn the weights: **product leadership sets them** because they state what the product values (comment weight 4, like weight 1 means one comment counts as four likes), and they are tuned through A/B tests so a policy change needs no retrain. This works only while each head stays **calibrated** (probabilities match how often events really happen).
- Serving at 8am, 200 ms budget: ~30 ms to gather ~2,000 unseen candidates, then a **light ranker** (a small **distilled** model copying a larger one, using a few cheap features) keeps the top 500 in ~20 ms, then the **heavy ranker** (multitask) scores the 500 in ~60 ms, then the value formula sorts — about 120 ms total, leaving room for the network. Each stage handles fewer posts so it spends more work on each.
- Fan-out: **push** (fan out on write) copies a new post ID into every follower's **inbox** — one inbox read but an account with 100 million followers triggers 100 million writes per post; **pull** (fan out on read) stores the post once but reads every followed account, slow for users following thousands. The standard fix is a **hybrid**: push ordinary accounts, pull the few very large ones at open, then merge.
- The **integrity layer** runs after the value formula — engagement alone pushes outrage and clickbait up, and negative terms are not enough, so it adds product rules: push bait down ("comment YES if you agree"), limit one author to two of the top 10 slots for variety, and honor "see less like this" for weeks. Its scores come from classifiers that run **once at write time** (~1,200 posts/s), tiny next to the heavy ranker's tens of millions.
- Three update speeds: session changes in seconds, per-post counts in minutes, model retrains daily. A 10-second-old post has no counts, so the ranker uses author and content features plus a small fresh-content boost. The risk is a **feedback loop** where the feed trains on engagement it caused and slowly favors bait with nothing crashing — guardrails, surveys, the integrity layer, and a **holdback group** (a few users kept on simpler ranking) catch it. Tag sessions where the heavy ranker failed so training doesn't learn from them.
- Capacity: 500 million daily users × 5 sessions × 3 ranking calls ≈ 7.5 billion calls/day ≈ 86,800/s — say "on the order of 100,000 ranking calls per second." Three tools make it affordable: the light ranker leaves the heavy ranker a quarter of the candidates, **microbatching** groups many small scoring requests into one model call (filling a batch adds delay, so test against the 200 ms), and **feature caching** keeps popular posts' features in memory near the ranker. If the heavy ranker times out, Maya gets the light ranker's order. If asked whether one metric can run the feed, say no: one engagement number drifts toward bait.
