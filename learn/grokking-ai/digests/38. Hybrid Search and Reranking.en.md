# L1 overview

- **Two complementary failures**: semantic search finds "I'm locked out of my account" → "how do I reset my password?" but misses exact tokens — "what does error E4022 mean?" lands near E4021, E4220 and every other payment error, so the right chunk may rank 15th or vanish, silently giving the wrong error's answer. **Lexical search** has the opposite weakness, **vocabulary mismatch**. Each fails where the other succeeds.
- **Lexical mechanics**: an **inverted index** maps each word to every chunk containing it (built in the background, so no full scan); **BM25** ranks matches — more matching words score higher, **rare words count more** (E4022 in 3 chunks vs "mean" in 260,000), each repeat adds less, and long chunks get a small penalty.
- **Hybrid retrieval** runs both in parallel (each returns its own top ~50; the slower one sets total time — 10 ms BM25 + 15 ms semantic ≈ 15–20 ms, not 25). Naively adding scores fails because scales differ (BM25 unbounded, at most 4 for one question and 30 for another; cosine 0–1). Min-max rescaling only partly helps (each list's top becomes 1 even when it found nothing useful). **Reciprocal rank fusion (RRF)** ignores raw scores and uses rank only: each chunk gets 1/(60 + rank) from each list, missing chunks get nothing from that list, and the **constant 60** is a common default that keeps 1st and 2nd close so one list cannot overrule the other. For E4022 (1st in BM25, 2nd in semantic) the chunk scores 0.0325, about twice any chunk found by only one list — **agreement is RRF's strongest signal**. Start with equal weights, change only when the golden set demands it.
- **Recall vs precision**: hybrid retrieval improves **recall** (is the right chunk among the candidates) but only the top few reach the context. Example: "my order came 40 minutes late, can I get a refund?" — the merged list puts "Why is my order late" at rank 1 and the late-delivery refund policy at rank 14: recalled but not chosen. **Precision** asks whether the top few are right.
- **Bi-encoder vs cross-encoder**: semantic search uses a **bi-encoder** that embeds question and chunk separately (fast, precomputable, but the chunk embedding cannot anticipate a future question). A **cross-encoder** reads question and chunk together in one pass, compares every token, and nothing is precomputed — so scoring 10M chunks means 10M passes, limiting it to a few dozen to ~100 candidates. A **re-ranker** is usually a cross-encoder: hybrid retrieval finds 50–100 candidates in ~10–50 ms, the re-ranker scores each on a GPU in ~50–100 ms and keeps the best 3–8, moving the refund policy from rank 14 to rank 1. Precise chunks also mitigate **lost in the middle**.
- **Funnel principle**: each stage keeps fewer items but spends more effort per item (recommenders send ~500 of 50M videos to a careful ranker). Hybrid retrieval is tuned for **recall**, the re-ranker for **precision**; a chunk hybrid retrieval misses never comes back. Add a re-ranker when **evals** show good recall but poor precision; if the right chunk is missing, fix hybrid retrieval.
- **Filters and structured questions**: a **metadata filter** keeps only chunks passing rules on stored facts (e.g. audience = customers). "Open tickets about billing errors filed since March" — a status and a date are exact facts, not meanings, so filters handle open/on-or-after-March-1 while hybrid retrieval handles the topic; a count like "how many refunds last week" goes to **SQL generation** (a read-only query run with the user's permissions). Tool-to-failure mapping: exact tokens missed → add BM25; reworded questions missed → add semantic search; right chunk retrieved but not chosen → add a re-ranker; status/date/count questions fail → add filters or a structured source. Semantic alone suits chat with few codes; lexical alone suits log search for exact error strings. Test the re-ranker's 50–100 ms on the golden set with and without it; when both searches already rank the same chunk first, re-ranking seldom changes anything and a hard latency path can skip it.
