# L1 overview

- **Vocabulary mismatch** is the core problem: "I'm locked out of my account" and "how do I reset my password?" share almost no words, so keyword search ranks the password article badly. An **embedding** is a **vector** (list of numbers) from an embedding model that captures meaning — e.g. 1,024 **dimensions** — with similar meanings pushed to close vectors, scored by **cosine similarity** (near 1 = related, near 0 = unrelated; password chunk 0.82 vs restaurant-hours chunk 0.08). Embedding models are far smaller and cheaper than LLMs, so 10M chunks can be embedded in one batch and each new question costs ~10 ms.
- **Embeddings are frozen meaning**, which yields three rules: (1) embed the question with the **corpus's model** — mixing two models produces near-random scores with no error; (2) **re-embed a chunk when its text changes** (a 30→14 day policy edit leaves the old vector saying 30); (3) a **new embedding model is a migration**, not a setting — re-embed the corpus, build a second index alongside, test both on real questions, switch question model and index together, and keep the old pair to roll back (switching one causes **version skew**). Embeddings are not summaries and not safe to share — text can often be partly reconstructed from them.
- **Exact vs ANN search**: ExactSearch compares the question vector to every stored vector (always true best matches, ~1,024 multiplications each), which is fine at 100k chunks but at 100M chunks each query reads ~400 GB. An **ANN index** (Approximate Nearest Neighbor) organizes vectors in advance, checking only a small part — much faster but may miss a few true matches. **Recall** measures the loss: if exact search names 10 and the index returns 9, recall is 90%.
- **HNSW** (Hierarchical Navigable Small World) links each vector to a few nearest neighbors, forming a graph: the bottom layer holds every vector with short links, higher layers hold random samples, the top has long links. Search starts at a top-layer entry point, moves to whichever neighbor is closer, and drops a layer when none is — big hops find the region, small hops find the answer. A tuned in-memory index answers in single-digit ms finding **95–99%** of true matches; measure recall on **your own corpus** (sample a few thousand real questions, run exact search offline as ground truth, compare the ANN index, repeat after every change).
- **Funnel math and cost**: retrieval is the first funnel stage; a chunk lost here never returns (95% pass × 90% later ≈ 85% survive). HNSW keeps vectors and links in memory: 1,024 numbers × 4 bytes ≈ 4 KB per vector × 10M ≈ 40 GB plus links and copies; **quantization** (32→8 bits) drops 40 GB to ~10 GB at some recall loss, and **sharding** splits an index across machines with every query hitting every shard (120M chunks ≈ 490 GB → shard).
- **Vector database vs extension**: a vector database wraps an ANN index with metadata and filters, accepts edits/deletes live, and survives crashes. **Post-filtering** (return 100 nearest then drop failures) breaks on selective filters (1% payments → ~1 survivor, sometimes none, silently). **Filtered HNSW** checks the filter while walking the graph and keeps going until enough chunks pass. The **document store** holds the latest text and is the **source of truth**; the index is derived from it. Deletes: tombstone in the store → remove from the index and all caches → search to confirm nothing returns and record proof. Choose a **vector extension** (e.g. pgVector) for a few million chunks and simple filters; a **dedicated database** (Qdrant, Pinecone) at tens of millions with selective filters, or hundreds of millions — decided by scale and filter complexity, not brand. Size memory as chunks × dimensions × bytes and run the permission filter during the search, not after.
