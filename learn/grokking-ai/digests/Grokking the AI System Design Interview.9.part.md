# L1 overview

- Lesson 26 — Introduction: LLM Serving & Inference — The model becomes the largest part of the system: seconds per answer and about a cent per turn. Prefill (parallel prompt read) sets time to first token, decode (one token per step) sets completion time, and the model is stateless so repeated history grows cost. A support message costs ~$0.0126 and takes ~10 s, too slow against a 5 s target.
- Lesson 27 — LLMs at Interview Altitude — Treats the LLM as one component with inputs, outputs, latency shape, price, and failure modes. Explains compute-bound prefill vs memory-bandwidth-bound decode, quadratic history growth, why a big context window is a limit not a strategy, and the six properties (sampled output, hallucination, shared instruction/data channel, per-token pricing, finite context, seconds of latency) that force design choices.
- Lesson 28 — Inference Economics — Prices tokens (about a cent per chat turn, output ~4× input) and builds the unit-economics habit: price one conversation, then a day and a month. Covers GPU memory limits (weights vs KV cache, quantization, batching, 60–80% utilization), fleet sizing, and the calculated breakeven between a hosted API and self-hosting.

# L2 detail

- `#L1-L25` — Lesson 26 vocabulary: context window, context assembly, prefill, decode, TPOT, GPU, weights, KV cache, hallucination; the food-delivery support assistant running example.
- `#L26-L45` — Part 1: the cost flips over — in Module 2 the model took 1–10 ms and the pipelines dominated, but an LLM answer takes seconds, costs about a cent, and runs on expensive GPUs; interviewers ask about first-word latency, cost, scale, and quality.
- `#L46-L136` — Part 2: what an LLM call is — a prompt in and generated text out; three facts (input built fresh each call, two phases, two meters of latency and cost); why output tokens cost more; what the GPU must hold (70B at 16-bit needs ~140 GB, shared with a growing KV cache that batching amortizes); what a call is not (no fixed price, not a database, not repeatable).
- `#L137-L224` — Part 3: follow one support message — 3,000-token prompt in ~0.2 s, prefill ~0.5 s giving ~0.8 s TTFT, 300 tokens at 30 ms TPOT giving ~10 s completion, ~$0.0126 cost, then nightly quality checks and safe canary rollout; noting a 150-token cap would cut decode to ~4.5 s and halve output cost.
- `#L225-L239` — From one turn to one day — 10 turns × 3,000-in/300-out with repeated history gives ~$0.126 per conversation and ~$12,600/day at 40,000 conversations; compare total cost per correctly resolved issue, not one bot conversation against one $4 ticket.
- `#L240-L300` — Part 4: what carries over and what changes — serving discipline (latency budget, fallback, logging, careful rollout) transfers, but units change (seconds, cents, GPUs, whole context resent, no single correct label); three new questions: what goes in the prompt, which model and where, and how to test answers with no correct label.
- `#L301-L338` — Part 5: the seven module lessons mapped to the questions they answer — latency behavior, economics, back-of-envelope math, optimizations, prompting vs fine-tuning vs RAG, evaluation, and the inference-bill capstone.
- `#L339-L394` — Part 6: where the module fits the framework — steps 2–7 gains: TTFT/finish/cost/quality targets, prompt data, model choice, serving path (streaming, limits, caching, routing, batching), golden sets, and cost × volume plus GPU fleet.
- `#L395-L410` — Part 7: what the rest of the course reuses — retrieval fills the prompt (RAG spends input tokens), products judge by TTFT and cost, safety starts from the shared prompt (prompt injection), and agents multiply calls so cost sums over steps.
- `#L411-L451` — Part 8: six mistakes — one latency number, pricing per request, filling the context window because it fits, fine-tuning to add facts, optimizing before pricing, and shipping prompt changes without tests; plus key takeaways (price one conversation in tokens, then give a TTFT target and a test plan).
- `#L452-L464` — Lesson 27 vocabulary: parameters, transformer, temperature, embedding model.
- `#L465-L522` — Part 1: the LLM as one component — five things to name (inputs, outputs, latency shape, price, failure modes); tokens in and tokens out with a five-part prompt; model size is a design decision (hosted API vs own GPUs); the embedding model is a cheaper sibling with no decode; what an LLM is not (a database, a memory, or guaranteed truth).
- `#L523-L649` — Part 2: two phases in every call — prefill reads all prompt tokens in parallel and is usually compute-bound; decode writes one token per step and is usually memory-bandwidth-bound; prefill sets most of TTFT and decode sets completion time; KV caching and speculative decoding speed decode but cannot remove the sequential order.
- `#L650-L715` — Part 3: follow one answer — 3,000-token prompt prefill ~0.5 s, 500-token answer decode ~15 s at 30 ms/token; why streaming exists (the answer does not finish sooner), why capping output helps (150 tokens → ~4.5 s), token pricing (~$0.009 in, ~$0.0036 out, output 40% of price from one seventh of tokens), and a table for reading a slow call by which phase is slow.
- `#L716-L889` — Part 4: the model remembers nothing — calls are stateless, so context assembly is your subsystem (conversation store, policy search, order lookup, prompt builder); resent history grows quadratically (20 turns ≈ 57,000 tokens, 40 turns ≈ 234,000) and is tamed by keeping the last few turns plus a summary; a 200,000-token window is a limit not a strategy; three ways to add knowledge (put it in context, retrieve on demand, train it in).
- `#L890-L1026` — Part 5: six properties — sampled output (temperature zero is only nearly deterministic), fluent and wrong (quality as a rate), instructions and data sharing one channel (prompt injection; keep permissions outside the model), per-token pricing, finite context, and seconds of latency; then the 30-second interview answer and five mistakes including swapping the phases.
- `#L1027-L1046` — Lesson 28 vocabulary: input/output tokens, frontier model, small model, utilization, quantization, breakeven point, rate limit.
- `#L1047-L1101` — Part 1: two meters on every request — latency (TTFT and finish) and cost (tokens, not requests); four common changes move the meters differently (streaming helps latency only, small models cut cost, bigger batches cut cost but slow each request, shorter answers help both).
- `#L1102-L1142` — Part 2: how tokens are priced — separate input and output rates; output costs more because each output token needs its own decode step (frontier output ~3–5× input, small models ~a tenth); the memorable anchor of ~1 cent per typical chat turn.
- `#L1143-L1243` — Part 3: price one conversation first — 10 turns, ~30,000 input and 3,000 output tokens ≈ $0.13 per conversation, ~$13K/day and ~$400K/month at 100,000 conversations; most input is resent history; three levers are summarizing history, routing easy turns to a small model, and caching repeated prefixes.
- `#L1244-L1323` — Part 4: what a GPU runs out of — weights must fit (70B at 16-bit ≈ 140 GB, more than one 80 GB GPU), the KV cache takes the rest and usually caps concurrency, quantization frees memory (8-bit ≈ 70 GB), and batching turns one weight read into many tokens; utilization target is ~60–80% at peak.
- `#L1324-L1353` — Part 5: size and price a fleet — output tokens per second at peak (50 rps × 500 = 25,000), divided by one node's 2,500 gives 10 nodes, rounded to 14 for ~70% peak load, then priced at ~$3–4 per GPU-hour for roughly $245K–$490K per year.
- `#L1354-L1504` — Part 6: hosted API or self-host — six factors (volume, quality, data rules, engineering, latency control, risk); a breakeven calculation (~1.1M requests/day, ~13 rps) shows when the fleet wins; the end state is usually a router splitting easy high-volume turns to a small model and hard turns to a frontier API, with client-side budgets, backpressure, and graceful degradation for rate limits and outages.
- `#L1505-L1553` — Part 7: the 30-second answer, follow-ups on when to self-host and hitting rate limits, and six mistakes (pricing per request, multiplying one turn, starting from the daily total, sizing GPUs by weights alone, choosing self-hosting by preference, aiming for full utilization); key takeaways price one unit first and treat API vs self-host as a calculated breakeven.
