# L1 overview

- **Framing**: explaining transformers or spending 10 minutes choosing a model both miss the question. Open with "The model is bought, not built; I will design the system around it" (called through an **API**), then say "This is a chat product, so **state and cost** will drive the design." Follow one user who plans meals in a long chat, cooks for two, and avoids nuts.
- **Numbers**: 10M conversations/day × ~8 **sends** each = 80M sends/day ≈ 930/s, peak ~2× average ≈ 2,000 model calls/s. The model is **stateless** — it sees only the **context window** for one call; a **context assembler** writes every window from stores that do remember.
- **Success metrics**: the business cares about **retention** (share returning next week), but retention moves over weeks, so daily work watches **proxies** — **regeneration rate** (share of replies where the user clicks regenerate) and **rephrase rate** (asks the same question in other words). Proxies can mislead (a shorter reply might lower regeneration and still lose users), so launches use an **A-B test** with retention deciding. Guardrail metrics that must not worsen: **TTFT** (time-to-first-token, target under ~1 s for nearly all requests, since a 300-token reply takes seconds and is **streamed**), cost per conversation, and safety in both directions (misses hurt people, false blocks make the product useless).
- **Three state stores**: the **conversation store** (every message for months or years, **partitioned by conversation ID** so one conversation loads from one machine, +2 rows per turn ≈ 4,000 new rows/s at peak), **user memory** (lasting facts like `isVegetarian`), and the context window itself for one call only. Only the context window reaches the model — everything the model knows about the user arrives through the assembler.
- **Why not resend everything (quadratic growth)**: with 1,000 fixed instruction tokens and ~300 per turn, turn 20's prompt holds 6,700 tokens; all 20 turns total ~57,000, and 40 turns ~234,000 — doubling history roughly quadruples whole-conversation compute, and a long prompt slows **prefill**, delaying the first token. So the assembler **packs** the window to stay near 3,000 tokens even at turn 50: fixed instructions first (least-changing content first enables **prefix caching**), then a few user-memory facts, then a **running summary** of older turns (a background job rewrites it every six turns), then **pinned facts** (e.g. "cooking for two, no nuts" from turn two, which a summary might drop), then the last six turns **verbatim**, then the new message.
- **User memory is a small RAG system**: a background step reads finished conversations and proposes lasting facts; each call, the assembler searches with the new message and adds the few most relevant. "Forget that I live in Denver" needs **lineage** — a record of where each piece of data came from — because summaries and caches hold copies, and only lineage lets the system find and remove every copy.
- **Routing and gates**: a **router** (a small classifier adding a few ms) picks **small or frontier** before any model writes; reports route 70–80% to the cheaper tier, and only the small tier is **fine-tuned** on good replies from real traffic (so the router sends it more each round). Each tier has a **fallback** (e.g. a second provider). Every send enters through the **gateway**, which is both a security device (**rate limits** per account) and a **spend governor** (daily token budget per user, smaller on the free tier), using **device fingerprinting** against account farms. The **input gate** runs a moderation classifier in ~10–50 ms so a blocked message never costs a full generation. The **output gate** checks the reply **as it streams**, holding only a small buffer; only a real **trip** (a failed check) stops the stream.
- **Worked trace**: gateway admits in ~10 ms, input gate passes, message saved, assembler builds ~3,000 tokens including the pinned fact, router picks small tier, first token ~0.6 s, output gate streams with a small buffer, first words ~0.7 s (inside one second), reply saved to the store **as it is written** — the store is the truth and the stream is just transport, so a dropped connection loses nothing.
- **Post-launch and cost**: every change passes the **golden set** (a few hundred test conversations with known good behavior; long chats check summaries keep the no-nuts limit). A new **system prompt** ships in steps: gate on the golden set → **canary at 1%** → keep rollback one switch away. Debug slow TTFT by splitting **queue time** (waiting for a free server → too little capacity) from **prefill** (longer prompts). At example rates one frontier turn (3,000 in / 300 out) costs ~$0.0126, and all 80M daily sends cost ~$1,800/day; routing 75% of sends to a small model at a tenth of the price cuts the bill to ~$327,600 (the transcript's stated annual-scale figure). Prefix caching and history summarization lower it further, and semantic caching reuses a stored reply for generic first messages. When the free tier runs over budget, pull **invisible levers** first and lower visible token budgets last (users notice and retention falls).
- **Failure responses written in advance**: if a store write fails, no model call runs because the truth is saved first.
