# L1 overview

- The strongest opening line for an ML design question is "this is two systems that share one model" — not one box labeled ML service, which leaves open when training runs and which model version answered a request.
- The **training plane** builds the model from months of past orders in background jobs, optimizing **throughput** (a two-hour run is fine), using **spot instances** with **checkpoints** since it is a bounded batch job whose failure is **soft** — yesterday's model keeps serving while an alert fires. The **serving plane** answers live requests, optimizing **latency** (10–100 ms), running on **replicas** behind a load balancer; its failure is hard, so it runs on durable machines with spares.
- Exactly two artifacts connect them: the **model** flows forward through the **model registry** (versions), and the **logs** flow back (each prediction with its exact features and model version, later joined to the real outcome). No live request reaches training and no raw training data reaches serving.
- The **training pipeline** has four fixed stages: data preparation (joins orders to labels, must use features as they were at checkout; holds most of the code and bugs), training (default a **gradient-boosted tree** that trains quickly on CPUs), evaluation (candidate vs. production on **held-out** recent orders — newer is not automatically better), and registration (store the winner with **lineage** so **rollback** is possible, e.g. version 42 → 41).
- Latency budget for ~100 ms: receiving and routing ~5 ms, reading stored features ~10 ms, computing request-time features ~15 ms, inference ~5 ms, logging and returning ~2 ms; logging runs asynchronously. When slow, check features first. Distinguish a **fallback** (a default or saved prediction for a timed-out request) from a rollback (replacing a bad version for everyone); for fraud, **fail open** vs. **fail closed** is a product and risk call.
- **Training-serving skew** is any gap between training and serving features with no crash and passing health checks. Causes and cures: two code paths (Python/Spark vs. Java, local time vs. UTC — 7 p.m. New York summer is hour 23 not 19) cured by one shared definition, a **feature store**, and **parity tests**; **label leakage** (a whole-day average including later deliveries) cured by a **point-in-time join**; the strongest cure is training on the feature values serving already logged. **Distribution shift** (new restaurants, weather) is a normal condition to monitor and retrain for, not a defect like skew.
- Scaling notes: large models need **distributed training** — **data parallelism** (full copy per GPU plus a batch slice) or **model parallelism**; a tabular model needs neither. Give a **retraining cadence** with a reason (fraud daily, delivery weekly) rather than training continuously, which burns compute on near-identical models that cannot be checked and rolled back in order.
