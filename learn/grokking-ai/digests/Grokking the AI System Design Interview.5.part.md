# L1 overview

- Lesson 15, Monitoring, Drift, and Retraining — A model decays from 4 to 6 minutes of error with no code change and no alert; data drift changes the inputs while concept drift changes what they mean; four monitoring layers (system health, input distributions with PSI, prediction distributions, outcome quality) with segment splits because label delay sets how much the early layers matter; debug pipelines before the model; scheduled + triggered retraining with windows sized for seasonality; every candidate passes offline → shadow → canary under "auto-retrain, human-promote"; the model shapes its own training data, so keep a 1–5% exploration slice.
- Lesson 16, Online Experiments and A/B Testing — An offline AUC gain from 0.78 to 0.80 is only a filter because the label is a proxy, the model changes the world it measures, and serving is not scoring; the two-gate ladder (offline gate → shadow → A/B → ramp with a ~2% holdback); design the test by randomizing on a hash of user ID and writing primary/guardrail/diagnostic metrics plus the decision rule first; power it and run at least a full week; check the split, avoid peeking (fixed horizon or sequential test), measure the novelty effect; interleaving, switchback tests, bandits, and low-traffic sensitivity levers.
- Lesson 17, Capstone: An ML Platform for ETA Prediction — The full seven-step reference answer for a 500k-order/day delivery ETA: regression framed with ~100 ms p99 and ~1.5M estimates/day; MAE, p90 MAE, and on-time rate as quality; three feature buckets each with its own pipeline and two stores written from one definition; a nightly per-restaurant baseline plus distance term that doubles as fallback and first-day answer; a CPU GBDT with a product-owned calibration layer turning 32 minutes into "30 to 40 min"; per-dependency timeouts and fallbacks; four monitoring layers by segment, daily plus triggered retraining, and per-segment promotion gates; costs sit in the streaming pipeline and routing calls, not the model.

# L2 detail

- `#L1-L20` — Lesson 15 header and vocabulary: data drift, concept drift, distribution, incumbent, retraining window, feedback loop, exploration, segment.
- `#L21-L39` — Part 1: A model can get worse while nothing breaks — launch-day 4 minutes becomes 6 minutes three months later because new restaurants, a new bridge, and batched couriers changed the world; a deployed model needs answer-checking monitoring, retraining, and safe promotion.
- `#L40-L102` — Part 2: The two kinds of drift — data drift is a new input distribution (a new city makes long trips common) and is visible without labels; concept drift is the same feature values implying a new outcome (a kitchen got faster but its prep-time feature still says 18 minutes) and usually needs fresh labels; drift is not a crash, a deploy bug, skew, or retraining.
- `#L103-L213` — Part 3: Four layers of monitoring — system health (latency, errors, freshness; seconds), input distributions (PSI, null/default rates; minutes to hours), prediction distributions (average estimate, score shape, flagged rate; no labels needed), outcome quality (ETA error, recall on confirmed fraud; waits for labels); label delay of an hour vs 2–8 weeks decides how much the early layers carry; split every layer by segment.
- `#L214-L246` — Part 4: When an alert fires — about half of "drift" alerts are someone else's broken pipeline; a null rate jumping from 1% to 30% could be new restaurants or a failed job, and those need opposite responses; the debug order is pipelines, predictions, segments, then the model, because retraining is the most expensive response.
- `#L247-L309` — Part 5: Three ways to retrain — scheduled (cadence derived from measured decay: 4.0 → 4.6 minutes over four weeks with a 0.2-minute tolerance means about every two weeks), triggered (a confirmed Layer 2/3 alert or a Layer 4 threshold breached for two days), and online learning (freshest but no gate between data and users; only with safeguards); the retraining window must cover seasonality but let old patterns fade, with optional recency weighting.
- `#L310-L389` — Part 6: Every retrain passes the same gates — data checks, offline evaluation against the incumbent (win overall, lose in no important segment), shadow mode, then a canary release with a named rollback metric; "auto-retrain, human-promote" automates steps 1–3 and has a person approve step 4 because only step 4 changes what users see.
- `#L390-L460` — Part 7: When the model writes its own training data — a feed only learns from what it showed, and a blocked fraud payment never produces a chargeback, so a wrongly blocked customer is never learned from; exploration spends 1–5% of traffic on items outside the top choices and logs selection probabilities to correct the bias; for fraud, exploration stays inside risk-approved rules and a daily loss budget.
- `#L461-L527` — Part 8, Part 9, takeaways — the four-layer 30-second answer, how to know a fraud model still works while labels take six weeks, and why a drift alert should not auto-retrain; five common mistakes.
- `#L528-L561` — Lesson 16 header and vocabulary: online experiment, A/B test, primary/guardrail/diagnostic metric, statistically significant, power, novelty effect, holdback group.
- `#L562-L644` — Part 1: Why an offline win is not enough — AUC 0.78 → 0.80 on past clicks; the label is a proxy (a click is not an order), the model changes the world it is measured in, and serving is not scoring (timeouts, stale caches, fallbacks); offline evaluation remains the filter that decides what reaches an experiment.
- `#L645-L783` — Part 2: The two-gate ladder — offline gate (beat the incumbent on held-out data, lose in no segment), shadow mode (catches latency, feature skew, and live crashes but cannot show orders), the online A/B gate starting as a ~1% canary, then a 10/50/100% ramp with rollback triggers and a ~2% holdback; cheap checks come first because the A/B test costs real customers.
- `#L784-L822` — Part 3: Designing the A/B test — randomize by a hash of user ID so a person never sees both lists; write the primary metric (order rate), guardrails (late-delivery rate, cancellation rate, home-screen p99), diagnostics (click rate, list position, distance), and the decision rule before the test; power the test for the smallest effect that matters (perhaps several hundred thousand users per group) and run at least a full week for the weekday/weekend cycle and the novelty effect.
- `#L823-L953` — Part 4: Reading the result honestly — check the group split first (52/48 signals an assignment or logging bug); peeking makes fourteen daily looks produce far more false winners, so use a fixed horizon or a sequential test; a lift that fades in a month is a novelty effect, which a 2% holdback measures along with slow goals like three-month repeat orders; an A/B test is a planned measurement, not a dashboard, not proof forever, and not a safety check.
- `#L954-L1002` — Part 5 and Part 6 — interleaving blends two rankers into one list (far more sensitive, needs less traffic, but shows preference not business effect), switchback tests alternate a whole city over time for marketplaces with shared couriers, bandits shift traffic toward the winner for short-lived choices, and low-traffic teams raise sensitivity via interleaving, sharper metrics, longer runs, bigger changes, or past-behavior adjustment; the ranker 30-second answer and five mistakes.
- `#L1003-L1037` — Lesson 17 header, vocabulary (ETA, MAE, p90 error, on-time rate, GBDT, streaming aggregate, calibration layer) and the exercise: design the checkout ETA for 500k orders/day that stays accurate as the company grows into new cities, in about 40 minutes.
- `#L1038-L1052` — Part 1: Frame the problem — a predictive regression outputting one number; "at checkout" sets a strict time limit and "as the business grows" requires a feedback loop from day one; in scope is the estimate at checkout in every city, out is live updates, courier assignment, and other screens; the platform parts could later serve fraud too.
- `#L1053-L1073` — Part 2: Define success — MAE under 5 minutes, p90 MAE for the bad tail (4-minute average with a 20-minute p90), the on-time rate for the promise, and 100 ms at p99; 500k orders become ~1.5M estimates a day, about 17/s average and ~70 at dinner peak.
- `#L1074-L1155` — Part 3: Map the data — the label is the real delivery time, arriving about an hour later, cleaned by dropping canceled and scheduled orders and watching early "delivered" marks; three freshness buckets (entity features nightly, streaming aggregates within seconds via Flink/Kafka, request-time context inline); log prediction ID, exact features, model version, predicted minutes, and shown window, with the ID making retries idempotent and the offline store supplying point-in-time values for new features.
- `#L1156-L1191` — Part 4: Pick the model — the baseline is a per-restaurant average plus distance/speed that also serves as the number to beat, the outage fallback, and the new-city first-day answer; the upgrade is a GBDT over all three buckets that can learn interactions like a kitchen slowing after 15 open orders when it rains, scoring a row in under a millisecond on CPU; the calibration layer outside the model turns 32 minutes into "30 to 40 min" and is a product-owned knob.
- `#L1192-L1383` — Part 5: Design the serving path — it needs the live kitchen queue and route, so it is online inference; the ETA service fires a batched feature-store read and a routing call concurrently, runs the GBDT, calibrates, returns, and logs in the background; the stage budget totals ~36 ms even when every slice is used; each dependency has a timeout and fallback (routing → cached zone-to-zone estimates plus a wider buffer, stale features → trained-in defaults plus a freshness alert, model down → a warm versioned per-restaurant heuristic table), and a bad new version rolls back in the registry.
- `#L1384-L1456` — Part 6: Keep it working — four monitoring layers here (pipeline freshness in seconds, inputs and predictions in minutes, true error about an hour later); segment everything by city, restaurant type, and weather; retrain daily because labels arrive within an hour and training is cheap, plus an hourly-MAE trigger after checking pipelines; promotion gates add a per-segment offline check (a candidate that drops global MAE 5.0 → 4.7 but worsens Manhattan dinner 6 → 9 is blocked), shadow, canary, and an A/B test for larger changes.
- `#L1457-L1519` — Part 6 continued: a storm, signal by signal — input drift fires within minutes at 6:00 PM, prediction drift next, then the hourly MAE around 7:00 PM once storm orders deliver; the fastest response is the streaming aggregates and a wider calibration buffer, not retraining, which helps most when the change lasts.
- `#L1520-L1552` — Part 7: Count the costs — model serving is the smallest line; the streaming pipeline, feature stores, batch/training jobs, and routing calls dominate, with routing at ~1,500/day easy to forget; LLM-based systems invert this, where the model call is often the largest cost.
- `#L1553-L1613` — Part 8, Part 9, takeaways — what mid, senior, and staff answers cover (staff separates the model from the promise and names the cost regime); five follow-ups (feature-read p99, 100× restaurant-list traffic → batch precompute, a zero-history city → baseline plus borrowed priors, a churn model → batch with a month-lagged error layer, ride-hailing prices → seconds-granularity streaming features).
