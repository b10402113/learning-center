# L1 overview

- The critique form tests the real job — diagnosing an inherited design — and a critique is a review that finds problems, ranks them by severity, and proposes a fix for each; the interviewer already knows the problems and listens for three things: do you raise the most dangerous first, can you say what each does to real users, and can you say what to fix first (six well-ranked findings beat 10 in random order).
- The subject co-pilot answers HR and IT questions: an offline nightly job rebuilds a vector-database index of the company wiki, the online path pulls the top 10 chunks and sends them plus the question to a frontier model, and a SQL tool lets the model query the HR database through one shared service account.
- Method step one (findings): list the parts, walk the seven-step framework one question per step, then ask what must never happen here to get the invariants ("no one sees data they may not see", "no one reads another person's records"); a complete finding states problem, consequence, and fix.
- Severity tiers: 1 violated invariants (leaked permissions — irreversible), 2 missing feedback loops (no evaluation — hides every other problem), 3 reliability gaps, 4 economics, 5 quality opportunities; delivery has three moves — lead with what the shape gets right, attach a consequence and a fix to every finding (without a consequence it sounds like taste, without a fix it's a complaint), end with a sequenced plan (blockers before rollout, week-one fixes, then the rest); reach tier one around minute 8 of 45.
- Findings: (1) retrieval has no permission filter, so an employee asking about a reorg gets restricted HR chunks — fix by carrying each chunk's ACL into the index query and failing closed if groups can't be looked up (telling the model to hide pages is not a control, it already read the text); (2) the model writes the whole SQL including the WHERE clause under an all-row service account — fix with a task-shaped get-my-record tool that takes fields only, identity from the session, query under the caller's own credentials; (3) no defense against indirect prompt injection from employee-edited wiki pages — fix with a guardrail sandwich (input gate, tag retrieved chunks as untrusted data, action gate) plus the scoped tool.
- Remaining findings: (4) "works great in the demo" means no evaluation — fix with a golden set of a few hundred questions including refusal cases, scoring faithfulness; (5) no live feedback — add thumbs, an escalation path to the help desk, and traces storing chunk IDs not text; (6) one nightly full rebuild leaves the index up to 24 hours stale, so a deleted page stays searchable — fix with incremental idempotent updates and a freshness SLO (99% of edits searchable within 15 minutes); (7) no fallback ladder — smaller model then plain wiki links when the model API is down; (8) a frontier model on every query (~15,000/day × ~1.7 cents ≈ $94,000/year) — fix with routing once the golden set shows quality holds, a small bill next to one leaked reorg plan; (9) vector-only retrieval misses exact strings like outage ticket numbers — fix with hybrid search plus a re-ranker picking the best five.
- Sequenced plan bends tier order deliberately: the fallback ladder is a small tier-three fix that protects the pilot so it ships early, while incremental updates wait as larger work; if forced to fix only one thing before launch, say the launch should be smaller, and if the interviewer insists, turn the SQL tool off (minutes) and ship the permission filter because it protects every question.
