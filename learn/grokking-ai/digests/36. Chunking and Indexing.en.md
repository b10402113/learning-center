# L1 overview

- **Two motivating failures, both in ingestion**: a missing answer (the per-person team-dinner limit lived in a PDF table that parsing scattered into numbers) and a retired answer (the refund window changed 30→14 days but the old chunk stayed). A better model cannot fix a broken chunk. Ingestion is a six-stage background pipeline, always in order: **connectors** (fetch new/changed/deleted) → **parse and clean** → **chunk** → **enrich metadata** → **embed** (same model version as the questions) → **index**. It is never a one-time load because the vector database never notices an edit on its own.
- **Document store = source of truth**: a record of every document, its parsed text, and its chunks, kept outside the vector database. The index is derived from it, so a lost index or a new embedding model is rebuilt from the store.
- **Parsing is the hardest stage and fails silently**: PDF tables come out as scattered numbers (fix: a layout-aware parser that keeps rows together), scanned docs need **OCR**, and web pages carry **boilerplate** (shared menus push thousands of article vectors together and dilute real content). Measure parsing quality — weekly samples checking headings/tables/lists survived, plus alerting on chunks with almost no text or mostly symbols. Diagrams may hold the only answer; route each content kind to its own handler (e.g. an image model) and scope the first version.
- **Why not one vector per document**: a handbook vector averages many topics and matches everything weakly. **Chunk size trade-off** — small chunks (1–3 sentences, under ~100 tokens) point sharply at one idea but can lose the heading context ("the limit is $50" with no idea what limit); big chunks (1,000+ tokens) keep context but mix topics. Common start **300–500 tokens** (an example, not a rule), chosen by a **sweep** over a **golden set**: chunk at 200/400/800, define a hit as the answering passage in the top 5, compute **recall**, and weigh memory (smaller = more vectors) against per-request tokens (bigger = more). **Structure-aware chunking** (the production default) cuts along headings and paragraphs, keeps tables and lists whole, adds a small **overlap** (last sentence or two repeated), and **contextual enrichment** prepends the heading breadcrumb ("expense policy, team events, meals") so the vector says what the number is for. **Small-to-big retrieval** indexes small chunks storing their section ID and returns the full section to the model, resolving the size trade-off at the cost of a larger context (so cap section size).
- **Metadata fields each power something**: document ID (replace/delete a whole document's chunks), source link (clickable citations), version (freshness checks and swaps), owning team (who fixes a bad page), access-control identifiers (applied as a filter during search).
- **Sync contract, five promises**: (1) **incremental sync** via webhooks, change feeds, or scheduled content-fingerprint checks; (2) **idempotent** re-indexing (running twice = running once; a repeat webhook sees a matching fingerprint and stops); (3) **atomic replacement** (delete old + insert new as one action, never a mix that answers 30 days to one agent and 14 to the next; if the store cannot do both, write version N+1 beside N and flip the current version); (4) **fast, ordered deletes** (tombstone in the store → remove from the index → clear caches last, so a request cannot refill them); (5) **freshness lag as an SLO** (e.g. 99% of edits searchable within 15 minutes, deletes within 5). A mixed old/new answer in an interview means a job inserted new chunks without removing the old: make per-document re-indexing atomic.
