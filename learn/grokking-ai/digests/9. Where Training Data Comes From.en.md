# L1 overview

- A **label** is a design decision, not something you simply have; "we use historical data" is a weak answer. Three sources: **natural outcomes** (cheap but delayed — a chargeback takes two to eight weeks, and a blocked payment produces no label at all, which is **censored**), **user behavior** (free and instant but noisy and **biased toward what the app showed**, i.e. position bias), and **human annotation** (controllable meaning but costs a few cents for a yes/no label and a few dollars for an expert one, with hours-to-days latency).
- Human labels need process: **versioned guidelines** (moderation v3 counts any sarcastic insult as abusive, v4 only when it targets a person — store the version with every label), **inter-annotator agreement** (Cohen's kappa removes chance agreement; low agreement usually means an ambiguous guideline), and **gold questions** (known-label items mixed into queues to continuously check reviewer accuracy and catch fatigue).
- Active learning with an LLM: label everything in seconds, then human-review a random sample to estimate overall error plus every uncertain or disagreeing case; humans move to hard cases rather than being removed. But **LLM errors are systematic** (a regional-dialect phrase read as rude, missed **adversarial content**), so repeated labels teach the same mistake — fix with **audit slices** and keep the **test set** human-labeled.
- **Class imbalance**: at 0.2% fraud, an all-legitimate model is 99.8% accurate yet catches nothing. Fixes: **downsampling** (keep all 20,000 fraud plus 1-in-50 legitimate from 10M payments → about 1 in 11 training examples is fraud, not 1 in 500) then **recalibration** (a post-training map from score to real chance using the known sampling rate; a 0.5 score matches ~2% real chance) so the business can set its **block threshold** from expected costs; or **reweighting** (keep all data but count a fraud mistake ~50× more) with recalibration too.
- Retrieval negatives: random catalog dishes are too easy; **in-batch negatives** (dishes other customers in the batch ordered) are free and realistic but over-represent popular items, so use **popularity-corrected sampling**; **hard negatives** (near misses like opened-but-not-ordered) sharpen the boundary — use only a small share because many are items the customer would have liked.
- Honest splitting: a **random split** lets a fraud ring that started in March land in both sets and makes the test too easy; use a **temporal split** (train Jan–Apr, validate May, test Jun) — scores often drop and the lower number is the honest one. **Leakage** is any way the future gets into training: random splits, features computed after the prediction moment, **label-adjacent features** (a refund flag set only after fraud is confirmed), near duplicates across sets.
- Fresh-label problem: chargebacks take ~6 weeks but the team needs a model this week, so train on a **mature window** (weeks 7–26, labels final) and add **proxies** (analyst decisions) for the last six weeks, marked provisional; judge quality on final labels only. Also: use data only for agreed and lawful purposes, keep it for a set retention period, and use **lineage** to find every copy when a user deletes their account.
