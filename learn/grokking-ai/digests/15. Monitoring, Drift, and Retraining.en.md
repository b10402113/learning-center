# L1 overview

- Drift is the decay of model quality as the world changes: a delivery ETA model goes from 4 minutes of error at launch to 6 minutes three months later with no code change and no alert fired, because past data ages every day and drift produces no errors.
- Two kinds need different responses: **data drift** is a shift in input distributions (a new city with long trips — the model just needs more examples, "not a new rule"), while **concept drift** is a change in the input→outcome relationship (a restaurant's prep time feature still says 18 minutes when the kitchen now takes 11) and does more harm because the learned rule is now wrong; only new labels can teach the new rule. Neither is a crash, a deployment bug, or training-serving skew (a day-one defect where training and serving compute a feature differently).
- Watch four layers, fastest to truest: L1 system health (error rate, freshness — how old a feature value is when read), L2 input distributions vs training (PSI, the population stability index), L3 prediction distributions (share of estimates over 60 minutes), L4 outcome quality (ETA error). Only L4 measures quality directly and only L4 needs labels; label delay is about an hour for delivery but 2–8 weeks for a fraud chargeback, so L2/L3 are the early warning. Every layer reports by segment, since one city's error jump barely moves the global average.
- An alert says something changed, not what: roughly half of drift alerts are broken pipelines, so debug pipelines first, then predictions, then segments, then the model — retraining comes last because it costs most and only helps real drift.
- Retraining has three styles, usually the first two combined: **scheduled** (cadence set by measuring how error grows week by week — 4.0 min at week 1, 4.3 by week 3, a 0.2-minute tolerance gives about every two weeks), **triggered** (a confirmed L2/L3 alert, or error above 5 minutes two days running), and **online learning** (only when freshness is worth the risk, e.g. ad click prediction, with input checks and update-size limits because no gate stands between data and users). Every retrain picks a **retraining window** long enough for seasonality but short enough that old patterns fade, optionally with recency weighting.
- Every candidate must pass gates identical to a new model's: data checks → offline eval on held-out data (must win overall and lose in no important segment) → shadow mode → canary (a rollback metric named in advance). "Auto-retrain, human-promote": automation runs the first three steps, a human approves the canary. Exploration (1–5% of feed traffic, a tiny sampled slice of small payments within a daily loss budget) keeps the training data honest against feedback loops where the model's own decisions shape what it can learn.
