# L1 overview

- A stored model answers nobody; **serving** is making it answer live requests. A **model server** loads one version from the registry into memory at startup, takes **features**, and returns a prediction; the ETA model is a **gradient-boosted tree** that must answer within ~100 ms.
- The server is **stateless** (no memory of past requests; other data comes from the feature store), so any replica can answer any request, more traffic means more replicas, and a crash loses nothing. A new replica runs a **readiness check** with test predictions so real users never get its slow first requests.
- Separate model service vs. in-process: in-process avoids a **network hop** (often a few milliseconds) but couples deploys (the model ships and scales only with the application), so most teams start with a separate service and move the model inside only when it is tiny and every millisecond counts.
- **Latency budget** of 10–100 ms end to end, split by stage: routing and checks, feature fetch, request-time features (route distance up to ~15 ms), inference, response. Target **P99**, not the average — the average can look fine while 1 in 100 customers waits far longer, which is many real people at high traffic.
- The **feature fetch is the usual bottleneck**; each store adds network time, but the feature fetch and the route call are independent so they run in parallel and the request waits only for the slower. **Logging stays off the critical path** (a background writer, so a slow log store cannot slow checkout). Every call gets a **timeout** (straight-line distance if the route service is late), and you never retry past the budget; measure each stage first because the fix depends on which is too large.
- Fixes by target: **feature caching** for the feature fetch (a **hot entity**'s features kept in memory a few seconds — only if a few seconds old is safe); **batching** for inference (several requests per model run raises **throughput**; **micro-batching** waits a few milliseconds to collect them, and that wait must fit the budget); **model compression** — **distillation** (small student copies a large teacher) and **quantization** (weights in 8 bits instead of 32, saving memory for a small quality cost), with pruning less common. A GPU suits large neural networks but is costly; a tree on **tabular** data runs well on CPUs, so compress before changing hardware.
- Sizing: 500,000 orders and ~1.5 million estimates a day is ~17 requests/second, ~70 at the dinner peak; if a load test shows one CPU replica serves 150/second within budget, one replica would do — but run four replicas, two in each of two data centers, because **failure, not load, sets the replica count**.
- **Rollout ladder**, every step able to stop the climb: (1) offline evaluation on held-out data, (2) **shadow deployment** scoring a copied sample of live requests whose predictions never reach a user (doubles inference cost), (3) **canary release** to ~1%, (4) **ramp** through 5/25/50/100%. A **hash** of the user ID makes the split **sticky** so one customer never sees two versions. Write the **rollback trigger** in advance — e.g. checkout conversion down 2% or P99 over 100 ms — and keep the previous registry version loaded so rollback takes seconds. A canary asks whether anything is broken; an **A-B test** (one service holding both versions, sticky split) asks whether the model is better on the business metric, and waits for statistical significance, which is why shadow mode filters weak candidates first.
- **Fallback ladder** from best to worst, taking the highest working rung: previous version, a recently cached prediction, a **heuristic** (restaurant's average delivery time), a product default (40–55 minutes). Each lower rung is worse but in time; a rising fallback rate is an early warning. For fraud, **fail open** vs. **fail closed** is a product and policy call (many systems pass small payments and add a check for large ones). For event-driven work with no waiting user, a job that crashes a worker twice goes to a **dead letter queue** and the other jobs keep flowing.
