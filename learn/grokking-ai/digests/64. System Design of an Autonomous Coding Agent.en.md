# L1 overview

- Question: engineers spend too long on small tickets (e.g. "receipts show wrong tax when the order has a promo code"), so design an agent that fixes the ticket, runs the tests, and opens a pull request — with one rule above all: it must never be able to break production.
- Shape is the bounded agent loop — model picks a step, a tool runs it, model reads the result, hard limits make it always stop — and this agent is easier than most because three things already exist: free verifiers (compiler, tests), a solved sandbox (CI already runs untrusted code in isolation many times a day), and a natural approval gate (every change already passes human review).
- Scope at v1: ~400 engineers, one large repo, ~200 tickets/day assigned; small work (bug fixes, missing tests) in; architecture changes (e.g. splitting a service, which no test can check) and production access out.
- Metrics: primary is merge rate (a merge means a human accepted the change); four guardrails that must not get worse — CI failure rate, revert rate, cost per task, and reviewer burden (review minutes per agent PR), because code can pass tests and still be subtly wrong and only review minutes show that cost.
- Context instead of training: the ticket and its acceptance criterion ("tax is computed after the discount") sit in the context window every step, a repo index finds the tax code and its callers, notes live in the working tree, and durable task state outside the sandbox lets a new sandbox resume after a crash; start with one agent and a few tools, add nothing until past-ticket tests show a need.
- Model routing: a frontier model plans and writes code, a cheaper model writes the PR description (~10× less per token), and prefix caching reuses the repeated long opening text; five tools, none touching a database or cloud console, but `run command` is a general shell — which is safe only because each task gets a fresh throwaway container with no production credentials and egress allowed only to the company package mirror.
- Central idea: the sandbox converts an agent safety problem into a code review problem — only a diff leaves, so "is this agent safe" becomes "is this diff good?", a question teams already answer daily with code review and CI; blast radius is one container, one task, one hour, and the design never relies on the model behaving well (the runtime is ordinary code outside the sandbox checking budgets before every step).
- Budgets and gates: at most 80 steps, $10 of model spend, 60 minutes real time; when a budget runs out the runtime stops and leaves a partial artifact (draft PR marked not ready, or a findings comment — never silence); three gates in order — tests plus linter (inner, failures loop back, existing tests protected from weakening), CI (outer machine gate, agent cannot change or skip it, no lighter lane), and human review with branch protection blocking any merge without approval.
- Walkthrough and economics: ticket assigned 9am, fresh container, four-step plan, a failing test written at 9:10 to prove the bug, fix by 9:25, CI at 9:45, reviewer comment at 11 reruns the loop, merged at 14:00 after 41 steps and ~$2.40 — most of the 5 hours was waiting for a human; typical task ~30 steps ≈ $3.75 before savings, ~$1–$2 with prefix caching and routing, ~$600/day at 200 tasks, but a careful 15-minute senior review can cost more than the whole task's compute.
- Evaluation and autonomy: offline suite of real pass tickets with hidden tests, reporting outcome metrics (hidden test pass rate) beside trajectory metrics (path taken) because a change can keep pass rate flat while doubling cost; in production a rise in steps per task often precedes a merge-rate fall; the autonomy ladder places this agent at stage 2–3 (acts alone in the sandbox, a person approves each merge), with auto-merge a distant stage 4; prompt injection hiding in a code comment cannot exfiltrate because there are no secrets to send and no outside address to send them to.
