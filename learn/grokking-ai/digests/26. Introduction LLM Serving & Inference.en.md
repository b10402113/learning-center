# L1 overview

- In a delivery ETA model the model is the smallest part (1–10 ms); add a support assistant that answers order-status and refund questions with an **LLM** (a model that reads and writes text) and one answer takes several seconds and about a cent on **GPUs** (chips running many calculations at once, costing far more per hour than an ordinary server). Now the model is often the largest part, and interviewers ask how long the user waits and what a day costs.
- One **LLM call** sends a **prompt** (the full text the model reads) and returns generated text, in small pieces called **tokens**. The **weights** never change while you talk to it, so the model **remembers nothing** between calls — your application resends the conversation and adds facts like order status, a design decision called **context assembly**.
- Every call has two phases. **Prefill** reads every prompt token together, in parallel; **decode** writes the answer one token at a time and cannot write the 50th token before the 49th. A long prompt mostly lengthens prefill; a long answer lengthens decode. The user sees nothing until prefill ends, then **streaming** shows each token as decode writes it, so the user starts reading long before the answer is complete.
- Two meters: **TTFT** (time to first token, the wait until the first token appears) and **TPOT** (time per output token, the average per token after that); and cost, counted as input tokens and output tokens. With a hosted API the **provider** runs the model and you pay per token; when you **self-host** you pay for GPU hours and the token count decides how many GPUs you need.
- GPU memory is fixed and two things compete for it: the **weights** (at 16-bit precision each **parameter** takes 2 bytes, so a 70B model needs about 140 GB for weights alone, often split across several GPUs) and the **KV cache** (key-value cache, the model's work on earlier tokens so each decode step doesn't repeat it), which grows with every token of every active conversation. Memory therefore often limits how many conversations one GPU serves at once; running many together is **batching**, "a main reason a fleet of GPUs can be cost effective."
- An LLM call is not a fast function call: its price isn't fixed because it depends on tokens. It is not a database lookup: the model can **hallucinate** (give a confident false answer), doesn't know private data unless it is in the prompt, and is not repeatable by default (each token is picked with some randomness, so the same prompt can produce different words) — so tests must check what an answer **means**, not its exact words.
- Worked support message (made-up numbers): the third turn, "My order is 20 minutes late. Where is it?" Context assembly builds about 3,000 tokens (system instructions, order status, late-delivery policy, two earlier turns) in ~0.2 s; prefill reads them in ~0.5 s; with queue and network the first token lands at ~0.8 s (**TTFT**); decode streams ~300 tokens at ~30 ms **TPOT** ≈ 9 s, completing around 10 s. At $3 per million input and $12 per million output tokens, input ≈ 0.9 cents and output ≈ 0.36 cents, about **1.3 cents** total.
- The example target was ~5 s, so the answer is too slow: a limit of about **150 tokens** cuts decode to ~4.5 s and halves output cost. Evaluation runs nightly — code checks format and policy rules, a second model grades answers against a written guide, people review a smaller sample, and logs show whether each issue was resolved or handed to a person. To introduce a smaller, cheaper model for order-status questions, run it on a **golden set** (a fixed set of past conversations with the behavior a good answer must show), then a **canary** on a small share of live traffic.
- Context assembly resends earlier turns, so turn 10 carries far more input tokens than turn 1 unless history is summarized or trimmed. At 10 turns per conversation averaging 3,000 input and 300 output tokens, one conversation costs about 12.6 cents; at 40,000 conversations a day that is about **$5,040/day** (at 100,000, $12,600). A human ticket costs $4, and a conversation that still reaches a person pays for both — so compare **total support cost per issue resolved correctly**.
- Serving practices carry over from the ETA model (a latency budget, a fallback such as a provider, logged versions, careful staged releases) but the units change: one number on plain CPUs versus ~300 tokens on memory-heavy GPUs, and **many good answers exist**, so there is no single correct label. Three new questions follow: what goes into the prompt, which model answers (hosted API or own GPUs), and how do you test answers with no single correct label.
- **RAG** (Retrieval Augmented Generation) looks up relevant passages and puts them in the prompt; every passage spends input tokens, and the **context window** is the most tokens one call can handle — pick how many passages by cost and latency, not by window size. Instructions, user messages, and retrieved documents all reach the model as one text prompt, so a message or document can try to override your instructions — **prompt injection**. An **agent** calls the model many times for one task, so its cost is the sum of tokens in every step.
- Interview habits: don't give one latency number — give TTFT and time to finish because they have different causes; don't price per request — size one unit in tokens, price it, multiply by volume; don't fill the context window because it fits, since every extra token adds cost and time. Don't fine-tune to add facts — fine-tuning further trains the model to change its **behavior** (format, tone); facts that change often or that only some users may see belong in the prompt through retrieval. Compute the bill before optimizing, and run a golden set on every prompt and model change "like unit tests on every code change."
