# L1 overview

- **Why RAG exists**: an LLM trained on pre-cutoff text has three gaps — **private facts** (never saw the company refund policy), **fresh facts** (can't know it changed last Tuesday), and **permissions** (can't tell who may see which document) — so it fills gaps with confident wrong guesses (**hallucinations**). Pasting every policy page fails once docs exceed the **context window**; fine-tuning is poor at storing facts that change weekly; **retrieving** the facts is the usual answer.
- **RAG has three parts**: **ingestion** (runs in background on add/edit/delete: clean, **chunk**, attach **metadata** and **embedding**, write to the **index**); the **request path** (answers while the user waits); and the **feedback loop** (logs every answer with its chunks, tests changes on a **golden set**). An index usually offers two searches — **semantic** (vector database, finds by meaning) and **lexical** (keyword index, finds exact words). The request path can only find what ingestion put there.
- **Five request stages, one job each**: **query processing** (rewrite into a searchable query, check the corpus can answer at all), **retrieval** (return top k chunks, e.g. 5–20), **re-ranking** (a slower, more accurate model reorders a short list), **context assembly** (pick for the token budget, dedupe, label with source and date), **generation** (answer only from the chunks and cite them), plus **post checks** for high-risk cases. A **citation** maps a claim to the supporting chunk.
- **Two systems in series**: retrieval then generation. **Retrieval sets the ceiling** (a chunk never in context cannot be used), **generation decides how close** the answer gets (the model can misread or add detail). Track two numbers: **retrieval recall** (were the answering chunks retrieved) and **faithfulness** (is every claim supported). RAG is not a vector database, not a guarantee of truth, and not training — it does not change weights — so Tuesday's edit reaches answers only after ingestion processes it and cached answers are cleared.
- **Worked timeline**: policy edited Tuesday → ingestion replaces chunks within minutes → 7:15pm customer asks about a 50-minute-late order → query rewritten in ~150 ms → semantic + lexical searches run in parallel with metadata permission and freshness filters → re-ranker keeps 5 of ~20 by ~300 ms → context assembly dedupes one paragraph found twice, fits 4 chunks in a 2,000-token budget and labels them by ~310 ms → small model answers with citation by ~2.5 s → groundedness post check by ~3 s → trace logged. If ingestion had missed the edit, every check would still pass and the answer would still be wrong: **freshness belongs to ingestion**.
- **Seven common mistakes**: draw only a vector database (draw both paths + loop); index documents once (say how fast edits/deletes reach the index); trust semantic search with exact codes like order IDs (run lexical too); fill the context window (set a token budget); assume retrieved means correct (require citations and a useful "I don't know"); check permissions after the answer (filter during retrieval); measure only the final answer (measure recall and faithfulness separately).
