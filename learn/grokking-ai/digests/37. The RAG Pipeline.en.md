# L1 overview

- **Motivating failure**: an employee asks "what dental plan do we offer?" (correct) then "does that cover my spouse too?" — the naive design searches the raw text, which has no idea what "that" refers to, so it returns spouse chunks from any page (e.g. travel rules) and the model answers from the wrong pages. The fix is a **five-stage pipeline** in order: **query processing → retrieval → context assembly → generation → post checks**. The writing model appears only in stage four, so much of quality is decided before it reads anything.
- **Query processing** handles three problems: (1) **conversation dependence** — **query rewriting** has a small LLM read recent chat + new question and emit one standalone question (~100–200 ms); often the single highest-value RAG fix in multi-turn chat and the most common cause of retrieval failure. (2) **query–document vocabulary gap** — **expansion** (a paraphrase, both searches merged) or **HyDE** (hypothetical document embeddings: draft a pretend policy-page answer and search with it); both add cost, so use only when the golden set shows they help. (3) **unanswerable questions** — classify whether the **corpus** can answer; skip retrieval and generation (saving cost and stopping fabrication) and link the right tool instead. It can also extract a filter like a date.
- **Retrieval and K**: embed the rewritten question with the **same model as the corpus**, find nearest chunks the user may read, re-rank, return **top K** with score and source. K is a trade-off (too few misses evidence, too many adds noise, cost, and latency); common start is retrieve 10–20, re-rank, keep 3–5, then sweep K (3, 5, 8) on the golden set and pick the smallest K that keeps quality.
- **Context assembly** sets a **token budget driven by cost and latency, not the window** — a full 200k-token window at $3/M is ~60¢ per question versus under a cent at ~3,000 tokens — and avoids **lost in the middle** (models read start and end more reliably). Then **selection and dedupe** (drop repeats like a dental summary copied into an onboarding guide; cap each source at ~2 chunks), then **ordering and framing** (best chunk first, second best last, each labeled e.g. "dental plan summary, HR, updated April 1").
- **Generation and routing**: simple lookups (one fact in one chunk) go to a small model at ~1/10 price; synthesis across chunks (comparing plans for a family of four) goes to the frontier model; a **router** can follow the query-processing classification.
- **Post checks gate release**: (1) **citations must resolve** (citing source 7 when only four chunks were sent is an invented citation); (2) **groundedness** — an **entailment model** judges whether each claim is supported by its cited chunk. On failure a **fallback ladder** runs: retry once with tighter instructions, then degrade honestly ("no supported answer found", link to the HR portal) — an honest refusal is a correct result, a confident wrong answer is among the most harmful.
- **Metrics and debugging**: **retrieval recall** (share of test questions where the right chunks reached top K) and **faithfulness** (share of claims the context supports) measured separately. High recall + low faithfulness = model had facts and misused them; high faithfulness + low recall = model was careful but had wrong evidence. "Most RAG problems are retrieval problems, so I measure recall first." Debugging matrix: right chunks in context + wrong answer → generation; right chunks missing from context → retrieval; right chunks missing from the corpus → corpus gap; good chunks + correct answer + unhappy user → product. Example: a road-closure refund with no citation — no document covers it, so add the policy and find why post checks let it through. At 10M→100M chunks, retrieval precision drops (re-ranker and filters matter more, re-measure recall), the index grows ~40 GB→~400 GB (quantization or sharding), and duplicates rise (de-dupe and per-source caps matter more).
