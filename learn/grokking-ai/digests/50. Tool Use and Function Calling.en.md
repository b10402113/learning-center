# L1 overview

- Function calling is how an agent acts, in three steps run by the runtime: the application sends a tool menu (each tool has a name, description, and schema of typed inputs), the model emits a structured request naming a tool and filling its inputs, then the runtime checks it at the action gate and runs the real function, putting the result back in the model's context.
- The one-sentence design rule: the model proposes, and the runtime decides. Capability (knowing which tool helps and filling inputs) is the model's job; authority (permission to act, checked against who the user is and what policy allows) must live outside the model — a tool call is a request, not an authorization.
- MCP (Model Context Protocol) is an open standard for describing tools so one tool server serves many applications, but permissions still stay in the runtime.
- The tool menu is an API for a distractible caller: attention spreads across all input and there is no memory between calls, so every description is re-read every step and billed (40 tools × ~150 tokens = 6,000 tokens per call, ~72,000 over a 12-step task, ~22 cents at $3/M input; prompt caching helps but a long menu still divides attention).
- Prefer a few coarse, task-shaped tools over a granular menu: a granular refund needs four tools (check eligibility, create record, update ledger, notify customer), so one refund becomes four calls with four chances to fail; three course tools (get customer orders, search policies, issue refund) mean fewer tokens, fewer lookalike names, and rules enforced inside issue refund (order belongs to this session's customer, amount within the $30 cap, claim within 24 hours) that the model cannot skip.
- Reject one powerful RunSQL-style tool: then only a prompt instruction would stop a bad query, and injected text can override it — policy must live in code.
- Descriptions are prompts: a strong one says when to use the tool and when not to, names the input (8-digit order ID), and says what comes back; errors steer the model too, so a legible error ("not found, IDs have 8 digits, did you mean this order?") beats a raw stack trace or a bare 500 that invites the same retry.
- Write tools must be idempotent, keyed on an idempotency key derived from the case and order and saved with the outcome in the same transaction; add timeouts (~2 s), rate limits (10 order lookups per task) to stop thrashing, and scoped short-lived credentials (minted per task, expiring in ~15 minutes) instead of a shared admin credential, with every tool running under the user's own permissions.
- Consequence tiers set how carefully to check: reads run freely within rate limits, reversible writes run and are logged with an undo path, consequential writes check policy inside the tool with sampled human review (the $30 cap limits one wrong refund), and irreversible actions (an over-cap refund, an email to an outside address) always wait for human approval.
- The action gate does four jobs in order: validate against the schema, check policy and rate limits, check the tier and route (irreversible waits for a person), and log every request with five things including the model's stated reasoning — treated as a clue for audits, not proof.
- The worked message (order 4,711, $24, 40 minutes late, missing a $3 drink) shows a 15-minute credential, an illegible first error followed by a good lookup, a timed-out refund retried on the same key so the customer is refunded once, and an indirect injection in a pasted receipt that the gate holds; fixes for wrong tool choices go cheapest-first — check the golden set (~200 labeled past requests), sharpen descriptions and rerun, merge overlapping tools, and fine-tune last (a description change took correct choices from 82% to 95%) — and the closing line for SQL questions: a model can be talked out of a prompt but not out of code.
