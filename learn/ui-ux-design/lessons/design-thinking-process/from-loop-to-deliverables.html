學習目標

能把抽象的設計思維迴圈對照到真實交付流程，說出每個階段產出什麼、為什麼順序是這樣，以及後面的階段為什麼建立在前面的成果上。

前言：抽象迴圈有了，但真實專案長什麼樣？

上一節我們把設計思維拆成五個階段，那是一套思考的順序。但當你真的接到一個產品專案，你不會只跟別人說「我現在在發想階段」。你手上會有一份 brief、一張 sitemap、幾張 user flow、一批 wireframe，最後是 UI 與測試報告。這些具體的東西，才是別人看得見、可以交接的成果。

這一節要做的，就是把抽象的五階段，對照到真實專案的交付流程上。看完之後，你應該能在任何一步停下來，回答兩件事：我現在在整個流程的哪裡，以及我為什麼要在這裡做這件事。這張地圖會陪你走完接下來所有的模組。

設計師不只是把畫面推出去

先破除一個常見的誤解：UX 設計師的工作不是「把畫面做出來」而已。專案的起點通常是理解——理解研究、理解 brief、理解這個技術概念要怎麼變成一個解法。整段前期工作，都是為了建立對專案的情境理解（contextual understanding）。少了這一層，你畫出來的畫面再漂亮，也只是在猜。

把這件事想成寫後端服務。你不會一打開編輯器就開始刻 API，而是先讀需求、想清楚資料模型與模組邊界，再動手。前期沒想清楚，後面改起來就是災難。設計流程的前半段，扮演的就是這個角色。

真實交付流程的順序

一個完整的產品設計專案，大致會走過下面這些階段。它們不是硬性規定，但順序背後有很實在的道理：前面的成果是後面的輸入，跳過前面，後面就只能靠猜。

階段產出什麼它在解什麼問題
Brief 與前期理解對專案、使用者與問題的共同理解我們到底要為誰、解什麼問題
Sitemap頁面清單與層級關係這個產品需要哪些頁面、怎麼分層
User flow頁面之間的互動路徑使用者完成一個目標要怎麼走
Wireframe無樣式的版面與資訊架構每一頁的內容怎麼排、放在哪
Lean branding色彩與視覺方向這個產品給人什麼感覺
Foundational styles在 Figma 裡建立的樣式系統整套 UI 共用的規則長怎樣
Technical concepts設計前該懂的技術認知數位介面有哪些技術限制與可能
UI design高保真、可交付的介面把結構與樣式合成最終畫面
Usability testing測試計畫、回饋與迭代設計真的能用嗎、要改哪裡

為什麼是這個順序

看這張表，你會發現一條很清楚的主線：先決定「有哪些東西」，再決定「怎麼走」，然後才決定「長什麼樣」，最後拿真人來驗。

Sitemap 決定有哪些頁面與層級，是整個產品的骨架。骨架定了，才有辦法畫 user flow——因為流程圖上每一個節點，基本上就是 sitemap 上的一個頁面或一個狀態。流程定了，wireframe 才有東西可以排：你要在每一頁安排哪些內容、哪個區塊放哪裡、使用者從上到下會依序看到什麼。這裡同時處理了資訊架構（information architecture），也就是把資訊有條理地組織起來。

結構全部穩定之後，才輪到視覺。先是 lean branding，也就是用一套快速的方法決定品牌方向與色彩；這一步不需要你是品牌或平面設計師，重點是幾個小時內把方向定出來。接著把這個方向變成 Figma 裡的 foundational styles，例如決定主色是藍色，就把整套跟藍色搭配的樣式都設定好。等到結構與樣式都齊了，UI design 就是把兩者合成最終的畫面。

最後才是 usability testing：拿真使用者來測，收斂回饋，然後迭代。你會發現這一步，正好對應到設計思維裡的測試階段。

對照回五階段

現在把交付流程疊回上一節的五階段，你會看到兩者其實是同一件事的兩種說法。抽象的那邊講的是「怎麼想」，具體的這邊講的是「做出什麼」。

設計思維階段對應的交付工作
Empathize（同理）讀 brief、研究、理解使用者與市場
Define（定義）把研究收斂成問題與目標，決定要解什麼
Ideate（發想）用 sitemap、user flow、wireframe 探索結構性的解法
Prototype（原型）從 wireframe 到 UI design，做出可測試的版本
Test（測試）usability testing，收斂回饋後迭代

這個對照的用處，是讓你不會把方法和成果搞混。你可以隨時問自己：我現在做的這張 wireframe，是為了解決哪個階段的問題？如果答案是「不知道，反正先畫」，那通常代表你的問題還沒定義清楚。

這張地圖怎麼用

接下來課程裡的每一個模組，都對應到表上的某一格。當你覺得迷失，就回到這張表，找出自己站在哪個階段、手上應該有什麼產出。這比死背流程有用得多，因為你記的是「這個產出解決什麼問題」，而不是一串沒有意義的階段名稱。

小結

設計思維是「怎麼想」，交付流程是「做出什麼」，兩者是同一件事的兩種視角。真實專案的順序是：先理解（brief、研究），再決定結構（sitemap、user flow、wireframe），然後定視覺（branding、styles、UI），最後測試與迭代。之所以是這個順序，是因為每一步的產出都是下一步的輸入——沒有骨架，就畫不了流程；沒有流程，就排不了版面；沒有版面，UI 也只是空殼。

地圖有了，但這條流程的起點是一個外部輸入：brief。它是別人交給你的需求文件，裡面藏著專案的目的、問題、研究與限制。下一步，我們就專門來學怎麼讀懂一份 brief，並且把它轉成一份可以動手的初步策略。
