# L1 overview

- **OpenSpec 規劃流程（`openspec-propose`、`openspec-explore`）** — `propose` 一次產出 proposal / specs / design / tasks，並嚴格把「規劃」與「實作」切開；`explore` 則是沒有固定步驟的思考夥伴模式，可以讀 code、畫 ASCII 圖、追線索，但不得寫應用程式碼。
- **OpenSpec 執行與收尾（`openspec-apply-change`、`openspec-archive-change`、`openspec-sync-specs`）** — `apply` 依 `openspec instructions apply --json` 的 `contextFiles` 逐項完成 task 並即時勾選；`archive` 在歸檔前檢查 artifact/task 完成度並可先同步 delta specs；`sync-specs` 是 agent 驅動的智慧合併，把 ADDED/MODIFIED/REMOVED/RENAMED 併入 main spec。
- **共同的 CLI 契約** — 五個 skill 都要求先 `openspec status --change <name> --json` 取得 `planningHome`、`changeRoot`、`artifactPaths`、`actionContext`，並以 artifact 的 `requires` 邊（而非 `status`）判斷必要產物；store 一旦選定，`--store <id>` 就成為整段流程的 sticky flag。
- **專案設定與品質工具** — `.openspec-target` 指向 `codex`；`.env.example` 定義 `DATABASE_URL`、`OPENAI_API_KEY`、`OPENAI_MODEL` 與選用 `OPENAI_BASE_URL`；`.gitignore`、`.oxfmtrc.json`、`.oxlintrc.json` 定義忽略清單、格式與 lint 規則。`sources/` 是唯讀輸入，此處只做摘要，不重現 `.env` 的任何值。

# L2 detail

- `#L1-L1` — .agents/skills/.openspec-target — 單行內容 `codex`，指定這組 OpenSpec skill 的目標 agent 平台；影響指令前綴（`$openspec-*` 而非 `/openspec-*`）與提示文字。
- `#L2-L150` — .agents/skills/openspec-propose/SKILL.md — 「一次生成全部規劃產物」的 skill。Frontmatter 宣告 `allowed-tools: Bash(openspec:*)`、MIT、需 OpenSpec CLI、`generatedBy 1.10.0`。核心是 **Planning boundary**：觸發請求只授權規劃，不得改專案碼，產物完成後必須停下等新的請求。步驟：釐清需求並推導 kebab-case 名稱（有重大歧義才問）、決定 schema（預設或 `--schema`）、`openspec new change`、`openspec status --json` 取得 `applyRequires` 與 `requires` 邊、依賴順序逐一 `openspec instructions <artifact-id> --json` 並寫到 `resolvedOutputPath`、最後再顯示 status。特別強調 `status` 只反映檔案存在，`tasks.md` 先寫會讓 `tasks` 顯示 done 但 `specs` 仍缺；`context`/`rules` 是給 agent 的約束，不可抄進產物。
- `#L151-L458` — .agents/skills/openspec-explore/SKILL.md — 探索模式。「This is a stance, not a workflow」：好奇而不制式、開多條線而非單一路徑、多用 ASCII 圖、貼著 codebase 思考。會先 `openspec list --json` 看有沒有 active change，再讀 `openspec/config.yaml` 的 `context` 與 `rules`（只當約束、不複述）。沒有 change 時可自由思考，若要捕捉洞察則必須先 `openspec new change`（不可手動建目錄），再依 status/instructions 產生被要求的產物；有 change 時先讀既有 artifact，再依「新需求→spec、設計決定→design、範圍變動→proposal、新工作→tasks」建議捕捉位置，但不自動寫入。Guardrails：不實作、不假裝懂、不催結論、不強加結構。內含多個入口範例（模糊想法、具體問題、卡在實作、選型比較）示範如何用圖與問題推進。
- `#L459-L646` — .agents/skills/openspec-apply-change/SKILL.md — 實作 skill。選定 change（名稱、對話推斷或 `openspec list` 詢問）後，`openspec status --json` 確認 schema 與 planning scope，再 `openspec instructions apply --json` 取得 `contextFiles`、進度、task 清單與動態指令。狀態處理：`blocked` 先補 artifact、`all_done` 建議 archive、其餘開始實作。逐項修改程式、即時把 `- [ ]` 改成 `- [x]`，遇到不明確、設計問題、超出 spec 範圍、錯誤或使用者中斷就暫停並回報；明確禁止「為了讓 task 過而靜默縮減、延後或簡化既定行為」。`context` 是必要輸入、`operationGuidance` 是選擇性建議，兩者都不得當成完成證據，也不得覆寫 CLI 狀態。
- `#L647-L828` — .agents/skills/openspec-archive-change/SKILL.md — 歸檔 skill。先選 change，再（可選地）`openspec instructions archive --json` 取得 `context` 與 `operationGuidance`；舊版 CLI 失敗時直接略過、不報錯。接著用 `openspec status --json` 檢查 artifact 是否 `done`/`skipped`，讀 tasks 檔統計未完成項，兩者都只警告並要求確認，不阻擋。若 `artifactPaths.specs.existingOutputPaths` 有 delta specs，先比對 main spec 並顯示合併摘要，選項為「Sync now」「Archive without syncing」或（已同步時）「Archive now / Sync anyway / Cancel」。同步必須 inline 執行 `openspec-sync-specs` 並在搬動 `changeRoot` 前完成驗證，避免 change 已被歸檔但 main spec 沒更新。歸檔時建立 `changes/archive/`，必要時加上 `YYYY-MM-DD-` 前綴且不重複疊日期。
- `#L829-L1090` — .agents/skills/openspec-sync-specs/SKILL.md — delta → main spec 的智慧合併（不歸檔也能單獨跑）。以 `artifactPaths.specs.existingOutputPaths` 為唯一 delta 來源，呼叫端可指定子集但不可再放大；每次寫入 main spec 前只取一次 `openspec instructions specs --json` 的 rules 快照。規則：ADDED 不存在就新增、已存在視為隱式 MODIFIED；MODIFIED 整塊帶入但必須保留 delta 未提及的 scenario；REMOVED 要刪整個 requirement，只有同時滿足「本次刪完已無 requirement、仍有 Purpose、原本不是空的、檔案其他行都可歸類、`.openspec.yaml` 宣告 `retire_capabilities: true`、路徑在真正的 specs root 內」才能刪檔，且永不留下空的 `## Requirements`；RENAMED 依 FROM→TO 改名；delta 的 `## Purpose` 不覆寫既有 main spec。最後 `openspec validate --specs` 驗證，並輸出每個 capability 的變更摘要。內含 Delta 與 Main Spec 的格式範例，強調 main spec 不得殘留 ADDED/MODIFIED 等 delta 標頭。
