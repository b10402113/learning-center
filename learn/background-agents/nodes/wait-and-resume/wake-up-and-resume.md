# 等待之後能不能自己接回來

我們來測一下。

這次要跑的流程，是先啟動一個帶有延遲恢復機制的故障（fault with delayed recovery）。預期結果是：同一個 run ID 會先進入等待；收到 `health.recovered` 後，再觀察一次，接著 checkout，最後 complete。

還有一件事要驗證：我們用 `-3` 連續送出多筆 alert。這幾筆 alert 應該都會掛在同一個 incident 上，而不是建立 3 個 run。

## 預期路徑：等待、恢復、重新觀察、完成

接著，我們等的事件來了。

你在畫面上看不到事件本身，因為它是在 server 端發生的。總之，`health.recovered` 就是我們正在等的事件。

這裡有兩份格式不太一樣的事件：一份是我自己寫的假 server 送出的，名稱使用點號；另一份來自 ingest，名稱裡有斜線。不過它們代表的是同一件事，只是我把兩種名稱對應起來了。

結果就是：上游依賴恢復了，checkout 也恢復了。

事件進來之後，我就讓它 resume。resume 的意思是讓 run 回到外層迴圈，重新讀取目前的 state。

一恢復，它就會走到下一行，也就是 `continue`。

<!--image:1-->

注意，這裡的 `continue` 指的是外層的 `for` 迴圈，不是剛才那個 `while`。我們現在已經跳出 `while`，但還在 `for` 裡面，所以它會回到 `for` 的最上方，重新取得目前的 run，再執行一次那些檢查。

它觀察到最新狀態：upstream healthy 已變成 true，條件符合，於是 run 就 completed 了。

整段流程都發生在同一個 run ID 上。這就是它被 resumed，而不是重新啟動一個 run 的證據。

而 `health.recovered` 之所以能滿足一個名稱不同的等待，是因為那兩份事件原本就代表同一件事。假 server 使用點號命名，ingest 使用斜線命名；雖然名稱不同，指的都是上游恢復。

## 弄壞它：把恢復延遲設為 0

如果你想看看它出錯時的樣子，也可以把恢復延遲設成 0 毫秒，然後看著那個 run 卡住。

<!--image:2-->

它不會成功。我們沒有實作任何解除暫停的機制，也不會有事件進來讓它繼續，所以它會卡在一個 `while (true)` 裡。

所以不要真的這樣跑。我覺得這可能會讓你的電腦整個 freeze 掉。

但這就是「弄壞它」的方法：先預測它會卡在哪個迴圈、永遠到不了哪個狀態，再去看結果。這比單純看它成功一次更有用。

## 這個 run 剛剛證明了什麼

老實說，它做得比我預期的好。

它求救的理由很充分：這是我無法介入的上游依賴，不是我的責任。而且你告訴過我，需要幫忙時就要開口，所以它真的開口了。

接著，它本來會在那裡等 10 秒，甚至可能無限期地等下去，因為我們根本沒有實作 help 流程，也沒有任何東西能讓它繼續。嚴格來說，它會一直卡在那裡。

最有趣的是，它自己取消了求救，而且就像真人一樣：它喊了救命，等 Slack 回覆的時候，新的 alert 進來了，它馬上就說：「喔，等等，沒事了，我好了。」

它就是這樣。

最後我要強調一件事：我們剛才完全沒有動到任何 LLM 相關的東西。

這整段流程跟 AI 無關，我們一行 AI 程式碼都沒碰。從第一課到現在，AI 相關的程式碼完全沒有改變。這是 harness，也就是包在 AI 外面的那些程式。

<!--image:3-->

這也是為什麼我根本懶得深入講 LLM。它就只有四行程式碼，而且我們之後再也不會動它。跟控制 LLM 的這一大堆東西比起來，它微不足道。LLM 本身沒有這些東西，什麼也做不了。

這種以對帳為基礎的等待機制，正是 approval inbox 的基礎。差別在於：proposal 會被存下來，而做決定的是人，不是 health check。
