# 門鈴，不是整個房間

## 前言

一個 run 要能「關掉後仍然活著」，靠的不是讓伺服器一直撐著，而是有人記得它停在哪裡，等世界有了變化，再把它叫醒。這件事沒做好，暫停就等於死亡。你闔上筆電，run 也跟著結束。

你會在什麼情況下遇到這個問題？alert 進來，agent 醒了，卻發現眼前的資訊已經過期。或者，agent 判斷現在還不該採取行動，應該等一筆尚未出現的資料。這時，它需要一種方式說：「我先停在這裡。」而且之後真的有人能把它叫醒。

這個 node 會依序回答四個問題：event 為什麼只是門鈴，而不是房間的快照？agent 要怎麼表達「我要等」？一次等待只會喚醒一次，那麼是誰在外面持續守候？事件真正發生時，控制權又會回到哪裡？很多人以為暫停中的 workflow 仍占著一個 server process 或 call stack。接下來這四篇會拆解這個假設。

先從最簡單的問題開始：agent 收到事件後，為什麼不能直接相信 event 帶來的內容？

## 那則已經過期的 alert

世界不會等 agent 跑完一個 loop。

這是我們最先得接受的事實。依賴可能在 agent 閒著時自行恢復，也可能有好幾個 alert 其實都在描述同一次故障。

想像付款閘道發出一則 alert。API 收到後，把它掛到目前的 incident 上。等 agent 真正醒來時，checkout 可能早已恢復。如果它把 payload 當成當下的狀態，就可能對過期的訊號採取行動。

<!--image:1-->

訊號是真的，只是它描述的那個時刻已經過去了。

## 門鈴，不是整個房間

你可以把每個 event 想成門鈴，而不是整個房間。

checkout process 發出訊號，API 把它存下來，掛到目前的 incident 上。接著，agent 醒來，重新讀取 checkout process 的狀態。

<!--image:2-->

agent 不會把 event 的 payload 當成快照。那只是一個事件，不是全貌。

因此，agent 會因為事件而醒來；但如果資訊還不完整，它就會說：「這裡沒有我能處理的事，我需要看到更多。」然後回去睡，等著看看接下來會發生什麼。

回去睡不是放棄，而是承認：門鈴響了，但房間裡目前沒有我能處理的事。

## 誰有權決定要等

我們要讓模型也有「選擇等待」的能力，就像你會選擇等待一樣。你想看看接下來會怎樣，模型也應該有這個自由。

有些等待則由 Harness 強制執行，例如等待人類核准。

<!--image:3-->

還有一種等待，是 agent 自己推理後得出的結論。這類情況沒辦法用確定性的方式處理：我們沒有讀過那些 log，也沒有像 agent 一樣跑完所有 tool call。

所以，有些情況應該由 Harness 決定等待；有些情況則該由 agent 自己判斷何時等待、何時求救。只有 agent 掌握了那些 context。若不給它這些工具，我們又要怎麼用確定性的方式處理？

目前已有 policy，像是 approval 這類情況，可以讓 agent 等待。但我們沒辦法替「尚不存在的資料」寫 policy，因為只有 agent 能判斷何時需要等它。

而且，這是非破壞性的選擇。agent 說「我需要幫忙」或「我等一下」，不會造成損害，所以我願意把這個權限交給它。但「要不要請人核准」這件事，我不願意讓 agent 自行決定；那應該由 Harness 這一層負責。

既然等待成了 agent 可以做的選擇，「等待」本身就必須成為 workflow 能精確表達的狀態。下一個問題是：decision 說「等」的時候，它究竟在等什麼？
