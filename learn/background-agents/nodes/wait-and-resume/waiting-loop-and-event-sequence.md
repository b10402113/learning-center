# 每一輪都去讀事件序列

誰在外面持續監看？又怎麼知道真的有新事件進來？

答案是一個 `while` 迴圈。而且在這個迴圈裡，每執行一個動作之前，都要先確認一次：這個 run 還是我負責的嗎？

## 等待是一個迴圈，不是只呼叫一次 wait

我們現在已經身處另一層迴圈裡了。因此，除了 `cycle` 這個游標，我還多記了一個 `check`，用來追蹤目前是第幾次檢查。

我把每一次檢查稱為一個 check，也就是每一輪都巡視一次，看看有沒有新事件。

在迴圈裡，第一步是讀取事件序列。我把 `cycle` 傳進去，呼叫 `step.run`，再把結果存進 `latest`。

<!--image:1-->

讀完事件後，下一步是取得目前的 run，確保手上的資料是最新的。因此，我們呼叫 `getRun`，並傳入 run ID。

為什麼需要迴圈？因為單次 `step.waitForEvent` 只會回報一次。但事件會持續進來，incident 的狀態也會一直變化。單次等待只能告訴你「有東西進來了」，卻無法告訴你「接下來發生了什麼」。

迴圈的目的，就是查看下一拍。

## 先讀取序列，再確認這個 run 是否仍由你負責

取得 `latest` 之後，接下來的處理方式和前面一樣：如果這個 run 已經進入某些狀態，我們就不再做任何事。

這裡檢查的是 `latest.status`，而不是 `run.status`。

簡單來說，如果我們正在輪詢的 run 已經 completed、failed、canceled、escalated，或是因為其他原因被 superseded，就直接停止。

這類檢查會寫很多次，因為整個系統是非同步的。同一個 run ID 可能同時有另一個 workflow 在處理，甚至早已由它結束。因此，每次動手之前都要先問一句：這個 run 還有效嗎？

這不是 request-response 模型。在分散式系統裡，狀態可能在你不知情的情況下改變。你開始處理時，它還是原來的狀態；但等你走到這一步，它可能早已不同。

所以，每個步驟開始前都要重新確認。這確實很煩，但如果不做，就得準備面對一堆 bug。

確認完之後，我們再判斷 `latest.eventSequence > state.eventSequence`。

`eventSequence` 的意思很直接：這是我們的服務送出的事件，依序排列後所得到的序號。

如果最新的序號大於一開始傳入的序號，就代表期間有新事件發生。我們便跳出這個 `while` 迴圈，並將 `check` 加一。

## 帶條件的等待，勝過直接睡一覺

接下來是重頭戲：我們要在這裡等待事件，也就是撰寫 `await step.waitForEvent(...)`。

為什麼要等？因為最新的事件序號已經大於原本的序號，表示有新事件進來了。這裡其實是在 harness 裡直接寫下這樣的邏輯：好，那就看看接下來會發生什麼。既然事件會持續進來，我們想看的就是下一拍，而這段程式表達的正是這件事。

所以，我把 `step.waitForEvent` 命名為 wait for service，並一併傳入 `cycle` 和 `check`，方便追蹤。

它接收的是一個物件。第一個問題是：我們在等哪個事件？

答案是 `incident/updated`。這個名稱沒有什麼特別的，就是我們自己取的；你想怎麼命名都可以。中間的斜線只是官方建議的命名慣例，當然也可以不加，只是大家習慣這樣寫。

第二個問題是：這個事件是不是屬於我們這個 run？

因此，我在 `if` 裡寫上 `async.data.runId === runId`。文件對 `async` 的說明有點繞，我自己的理解是：`async` 就是這筆事件所帶資料的把手。因此，我要比對的是事件資料中的 run ID 是否與目前的 run ID 相同；只有相同時，我才會接收這個事件。

最後，再設定一個 10 秒的 timeout。也就是說，接下來 10 秒內，如果 incident 有更新，而且 run ID 相符，我們就繼續往下執行；如果 10 秒到了，也一樣繼續。

你可以把它想成一種帶條件的 `setTimeout`，條件就是「順便留意有沒有事件」。

<!--image:3-->

為什麼不直接 `step.sleep` 10 秒？

當然可以，`step.sleep` 也能達到類似的效果。但問題是，睡醒之後，我們要怎麼知道事件是否發生了？我們就得假設有一個 event store，等 10 秒後再查一次，確認這段時間內是否有 incident 更新，以及 run ID 是否相符。

這樣做並非不可行，只是我們得等到 10 秒後才能查看。如果事件在第 2 秒就發生，我們仍要等到第 10 秒才會知道。

這就是兩者的差別，也是優化所在。10 秒在調查流程裡不算長，但想像一下，如果要等的是 30 分鐘呢？你絕對不會想「先睡 30 分鐘，醒來再查一次」，而是會希望事件一發生就能繼續處理。

等待結束後，我們就 `continue`，回到外層迴圈，開始下一輪。

最後還有一件事：把下面那段 `decision.action === "requestHelp"` 判斷拿掉。為什麼？因為上面已經處理過了，這段邏輯重複了，沒有必要保留。
