# 光是拆 step 還不夠

## 前言

背景 agent 執行到一半時，伺服器掛了。重啟後，runtime 從上次停下的地方接續執行。看起來什麼都沒遺失，這正是 durable execution 所做出的承諾。

問題是，它承諾的是 checkpoint，不是 effect。恢復過程中，如果把已經生效的 mutation 再送一次，你可能會把同一個 feature 關兩次、送出同一筆轉帳兩次，或向同一個使用者收兩次錢。這個 node 要補上的，正是這段落差。

你可能會在這些情況遇到問題：部署進行到一半、API timeout 但不確定對方是否已經完成操作、同一個觸發事件被送進來兩次，或 workflow 執行到一半時換版。只要 agent 會改變世界，這些情況就難以避免。讀者手上應該已經有 `step.run`、replay、checkpoint 這些概念，接下來就沿著這條路繼續往下看。

這個 node 會依序回答五個問題：為什麼拆分 step 還不夠？要讓第二次呼叫不造成影響，需要什麼？識別碼由誰產生，重播時還能不能取得同一個識別碼？識別碼正確，但世界已經改變時，該由誰來阻止操作？如果兩個 run 使用相同的 run ID，或 ack 在 commit 後消失，又會怎樣？讀到最後，你應該能看著一個被重試的 mutation，說出是哪一道防線擋住了第二次效果。

先從最根本的誤解談起：crash 之後，runtime 究竟從哪裡接續執行？

## 你實際買到的保證

durable execution 的做法很簡單：每個 step 的結果都會被 memoize 下來。resume 時，runtime 會檢查哪些 step 已經有結果，並跳過它們。

接著，它會從第一個尚未產生結果的 step 繼續執行。這不是重播 JavaScript 的 stack，也沒那麼複雜；它只是查看記錄，跳過已經做過的事。

因此，crash 前已經執行完畢的 step，resume 時不會再執行。這一點很可靠。

但執行到一半的 step，就沒有這種保障了。它尚未完成，也沒有回傳結果，因此會重新執行。而且是從第一行重新開始，不是從中斷的那一行接著執行。

差別就在這裡：checkpoint 記錄的是 step 的邊界，而不是 step 內每一行的執行進度。

如果一個 step 裡只有一次 mutation，這個模型看起來似乎夠用；但如果裡面有三次，就不夠了。

## 三個動作，一個 step

假設同一個 step 裡有三個會改變世界的動作。第一個成功，第二個也成功，第三個失敗。step 沒有完成，並回傳錯誤。

重跑時，runtime 不會跳過前兩個動作。因為它們都在同一個 step 裡，沒有各自的 checkpoint。於是，第一個動作會再執行一次，第二個也會再執行一次，接著才輪到第三個。

<!--image:2-->

把它們拆開，就能解決一半的問題。將三個動作分別放進三個 step；如果第一個失敗，就只重跑第一個。第二個成功後，結果就會被記錄下來，因此不會再執行一次。

這也是「不要把多個非同步的破壞性操作塞進同一個 step」的原因。全部塞在一起，若想分開重試，就得自行在裡面處理 transaction。拆開之後，分開重試的能力就有了。

但拆開只解決了重試範圍的問題，沒有解決重試內容的問題。

## 重跑又建立了一個 user

現在來看一個已經拆分好的 step。step 裡只有一行：呼叫你的 API route。

route 裡有 50 行商業邏輯。執行到一半時，程式掛了。step 尚未完成，也沒有回傳結果，因此會重新執行。

可是，前面那 50 行已經建立了一個 user，也做了幾件其他的事。第二次執行會從 route 的第一行開始，接著再次執行建立 user 的那一行。資料庫發現這個 email 已經有對應的 user，於是整個流程就出錯了。

這個錯誤不是第一次執行失敗的原因。第一次執行時，你根本不知道程式為什麼掛掉；第二次卻在一個新的地方失敗，因為程式並非 idempotent。

如果程式是 idempotent，第二次執行時就會說：「user 已經存在，跳過。」然後從上次中斷的地方繼續。這就是兩者的差別。

Stripe 對這個問題的解法是 idempotency key。同一個 key 再次送出時，Stripe 會先查詢，確認這件事已經做過，然後回傳 200；mutation 不會再次發生。我們做的事情也一樣，只是把它稱為 action ID。

既然 runtime 會再次呼叫，第二次呼叫就必須不造成影響。這就是下一個問題。
