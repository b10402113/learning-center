# run 是 agent 被一個 event 叫醒的一次執行

你可能習慣把 agent 做完一件事，稱為「跑了一次」。但設計會自行醒來工作的背景 agent 時，得先弄清楚：這裡說的「一次」到底是什麼？

先看看 dashboard。上面每一筆紀錄，其實都是一個 run。

## Run 不等於一次調查

把 run 大致想成「一次調查」很方便，但嚴格來說，兩者並不相等。

一次調查可能花好幾週才解決。這段期間，你一直在查同一件事，卻可能經歷好幾個 run。也就是說，一次調查不一定只對應一個 run。

<!--image:1-->

## Run 是 agent 被 event 叫醒的一次執行

更準確地說，agent 被某個 event 叫醒，就開始一次 run。

<!--image:2-->

每次有新的 event 進來，都可能開啟一個新 run；如果它和正在進行的 run 有關，也可能接到既有的 run 上。要怎麼處理，取決於你的 harness。

## 什麼時候該開新 run

假設上游有個服務會自動建立 incident，例如 SEV-0 或 SEV-1。agent 收到 event 時，這個 incident 已經分類好了。

接著就要判斷：該開一個新 run，還是把 event 接到既有的 run？

如果它只是同一件事的另一個 event，而且 incident 已經開啟，就不該再開新 run。

但在我們的情境裡，每件事都會開新 run，因為沒有上游服務替我們分類。至於要採取哪種做法，並沒有什麼限制。

要特別注意，這不是 AI 或 LLM 要做的決定，因為 LLM 最後都會看到這些內容。開新 run 還是接續既有的 run，應該由 harness 在接收 event 時決定。

<!--image:3-->

## Event 進來後，先確認有沒有既有的 run

agent 被叫醒、進入程式後，第一件事是確認：是不是已經有一個 Agent run 在進行？

做法很直接：呼叫 `getRun`，並傳入 `runId`。如果查到既有的 run，就能帶著原本的上下文，從上次停下的地方接著做。

<!--image:4-->

這一步其實只是在資料庫查詢：這個 `runId` 是否已經有對應的 run？這次是新的呼叫，還是同一個 run 的延續？

透過這個檢查，我們可以避免為同一次調查開出重複的 run。就像用 user ID 查使用者一樣，這裡是用 `runId` 查 run，確認沒有重複。
