# run 是什麼？

## 前言

這組文章要釐清一個看似細小、卻會影響後續每張表該如何解讀的定義問題。background agent 的服務可能會關閉或重新部署，記憶體中的資料也無法保留。如果沒有清楚定義「run」，你就可能把一次調查當成一個 run，進而把「接續」誤寫成「重新開始」。

你會在許多情境中遇到這個問題：一個 incident 調查了兩週，期間 agent 被喚醒好幾次；上游已將事件分類為 SEV-0 或 SEV-1；同一個故障又收到第二個 alert；服務重新啟動後，工作流再次收到事件。每次你都得回答同一個問題：這是新的 run，還是原本那個 run？

這幾篇文章會依序回答四個問題：run 是什麼？一次調查為什麼可能包含多個 run？由誰決定要開新 run 還是接續既有的 run？為什麼執行動作前要先查詢？讀完之後，你會知道 run 只是一次喚醒，因此尚未完成的工作必須存放在某個耐久的地方。這個地方其實有兩個，而它們各自負責什麼，會決定 schema 的設計。

先從第一個問題開始：run 到底是什麼？

## 一次喚醒，不是一份案卷

一個 incident 調查了兩週，期間 agent 被喚醒了很多次。

如果你在 dashboard 上把它看成一筆「調查」，就會以為有一個執行單位從頭跑到尾。這種對應方式並不準確，還可能造成誤解。

Dashboard 上的一筆資料就是一個 run。更精確地說，run 是 agent 因某個 event 而被喚醒並執行的一次過程。

一次調查可能包含多個 run。也許一項調查需要好幾週才能完成；你始終在處理同一件事，卻跨越了多個 run。把 run 等同於「一次調查」，就等於把兩種不同的界線混為一談。

<!--image:1-->

調查的界線是問題解決的時刻；run 的界線則是這次喚醒結束的時刻。兩週的 incident 留下好幾個 run，並不代表工作重複執行，而是同一件事讓 agent 被喚醒了好幾次。

## 開新或接續，由 harness 決定

每次新的喚醒都可能開啟一個全新的 run，原因很簡單：這個 event 與目前正在執行的 run 無關。也可能將 event 附加到既有的 run。這個判斷邏輯由你決定。

假設上游有一個服務，會自動建立 incident，並順手將它標記為 SEV-0 或 SEV-1。agent 收到事件時，事件已經完成分類。這時，你就可以直接判斷要開啟新的 run，還是將這個 event 附加到既有的 run。

判斷依據是 incident 是否已經建立。如果第二個 alert 只是同一事件的另一個通知，而 incident 也已經建立，就不應該開啟新的 run。

課程中的情境則不同：每件事都會開啟新的 run，因為這裡沒有上游服務替事件分類。這不是唯一的做法，也沒有任何機制限制你這麼做。這個決定與 AI 或 LLM 無關。決定者是你，不是 LLM；不論怎麼決定，LLM 最後都會看到這些資料。

## 先查，再動作

工作流啟動後，第一件事是確認是否已經有一個 agent run 正在執行。

做法是呼叫 `getRun`，並傳入 `runId`。這個 `runId` 由呼叫端提供。你在上一節做出的判斷，最後會轉化成要查詢的識別碼。

如果資料庫中已經有這個 run，就從上次中斷的地方繼續，並沿用原有的上下文。

這只是一項資料庫查詢：這個 `runId` 是否已經有資料？這次是新的呼叫，還是同一個 run？

如果不查詢就直接建立新 run，就可能產生重複的 investigation。同一件事會留下兩份紀錄，各自朝不同方向進行，之後也沒有人能說清楚哪一份才是準確的。查詢的成本很低，重複紀錄造成的代價卻很高。

<!--image:2-->

這件事與 AI 或 harness 無關。就像你用 user ID 查詢使用者一樣，我們只是在用 `runId` 查詢 run，確保不會產生重複紀錄。

run 只是一次喚醒，所以尚未完成的工作不能只存在那次喚醒的過程中，而必須存放在某個耐久的地方。接下來你會看到，這個地方其實有兩個：一個是我們的 Postgres，另一個是 Inngest 的 checkpoint。問題在於，兩者各自應該存放什麼？
