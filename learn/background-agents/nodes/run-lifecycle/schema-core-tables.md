# schema 核心表：events、actions、runs

上一步說，business state 由我們自己寫進 Postgres，workflow state 交給 Inngest。既然業務資料落在 Postgres，那這張資料庫的 schema 長什麼樣子？有沒有什麼特別的設計？

答案可能會讓你意外：它非常簡單，真正用到的大概只有三張表。

## 三張表各存什麼

- **events** 表：存放事件資料，並標記每筆資料對應的 run ID。
- **actions** 表：存放動作名稱和參數。在 Postgres 裡，這些內容都是 JSON blob。
- **runs** 表：保存定義一個 run 所需的資料，是三張表中最重要的一張。

簡單來說，events 記錄「發生過什麼事」，每筆事件都會標明所屬的 run。actions 記錄「agent 想做什麼」，內容是動作名稱和參數，整包存成 JSON blob。

runs 則是這三張裡最重要的一張。

## 為什麼 runs 最重要

runs 為什麼最關鍵？等我們開始處理暫停與恢復時，事情會稍微複雜一些：你需要一份完整的 snapshot，讓 run 可以帶著它移動。

例如，今天在某個狀態下啟動一個 run，一週後再啟動一個一模一樣的 run。名義上是新的，但虛擬上完全是同一件事，因為 snapshot 完全一樣。

<!--image:2-->

關鍵在於，定義一個 run 的所有資料都存在資料庫裡。因此，有沒有啟動一個新的 Inngest workflow，其實並不重要。只要狀態相同，它就能從上次停下的地方精準接續，即使這次是全新的執行。

## 把一切都序列化進 state

這就是可以開始採用進階做法的地方。可能是為了節省成本，也可能有其他原因，你可以選擇這樣做。

更徹底的方式，是盡可能把所有東西都序列化進 state。這樣一來，就不必再糾結「要不要接回原本的 run、開一個新的，還是重用同一個」。

因為一切都由你提供的 state 輸入來定義，所以即使開了新的 run，本質上仍是同一件事——就像一個狀態機。
