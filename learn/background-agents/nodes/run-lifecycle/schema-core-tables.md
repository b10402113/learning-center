# 資料庫 schema：簡單到會讓你意外

上一節提到，state 有兩個保管人。現在來看看 Postgres 負責的那一半。

有人問過 durability：既然所有東西都寫進資料庫，schema 裡有沒有什麼特別有趣的設計？答案很簡單，簡單得讓人意外。

## 三張表，一句話拆開

實際用到的表大致有三張：events、actions 和 runs。

events 存放資料，以及對應的 run ID。actions 存放動作名稱和參數，兩者都是 Postgres 裡的 JSON blob。runs 則是記錄 run 本身的表。

用一句話來拆解：「agent 在 14:02 關掉一個 flag。」事件本身和對應的 run ID 會存進 events；動作名稱和參數會存進 actions；而這兩者所屬的 run，則記錄在 runs 裡。

<!--image:1-->

這三張表都很小，沒有什麼複雜的設計，也沒有為了 durability 額外加上一層。durability 靠的是資料確實寫進資料庫，而不是 schema 設計得多漂亮。

## 為什麼 runs 是最關鍵的一張

作者說，runs 是最重要的一張表。原因不難理解。

events 的每筆資料都帶有 run ID，因此一定能指回某個 run。actions 只有名稱和參數，描述的是「做了什麼」，而不是「這是哪一次執行」。定義「這是哪一次執行」的，是 runs。

如果只能留一張表，就留 runs。沒有它，events 就是一堆沒有歸屬的資料，動作名稱和參數也失去了執行脈絡。

## 一個可以帶著走的 run

等到要處理暫停與恢復時，事情會變得複雜一些。你需要完整的 snapshot，才能讓 run 帶著走。

今天在某個狀態下開啟一個 run，一週後，你可以再開一個「一模一樣」的 run。名義上它是新的，但在邏輯上完全是同一件事，因為 snapshot 完全相同。

<!--image:2-->

定義一個 run 所需的所有資訊都在資料庫裡。因此，你是否開啟新的 Inngest workflow，其實並不重要。只要狀態相同，它就能從上次停下的地方精確接續，即使這次是全新的執行。

再進一步，就是把所有東西都序列化進 state。這麼做可能是為了降低成本，也可能另有原因。作者的做法是盡可能把所有東西都序列化進 state。如此一來，以後就不必煩惱「要接續原本的 run、開一個新的，還是重用同一個？」因為一切都由你提供的 state 輸入決定。即使開啟新的 run，本質上也還是同一件事，就像一個狀態機。

反過來說，要做到這種精確接續也有條件：只要改動 state 輸入中的一個欄位，接續的就不再是同一個 run，而是另一個 run。只有 snapshot 相同，行為才會相同。

runs 這一列是關鍵。接下來的問題是：run 裡哪個欄位會告訴剛醒來的 run，世界在它睡著時發生了變化？
