# 弄壞它：run 失敗時該修哪一層，與多 region 設計

上一節教你用三個維度替一個 run 評分。評完之後，下一個問題是：不及格的那一維，該去哪裡修。

一個 run 跑失敗了。你的第一個反應，八成是去改 prompt：把措辭講清楚一點、多加幾句指示，再塞一個例子。

但多數時候，這是錯的方向。

run 會失敗，通常是因為某一層出了問題。你得先診斷是哪一層壞了，才知道該動哪裡。只有在「邊界和證據本來就正確」的情況下，prompt 才輪得到當候選修法。

所以這一課會做兩件事：

1. 先學會定位到底是哪一層出了問題。
2. 把同一套判斷帶到多 region 設計，思考兩個 region 同時出事時，該怎麼設計 incident key、alert 合併規則、run 的關閉與重開規則，以及「state 已經改了，但 alert 還沒送出去就掛掉」時，如何保住事件。

## 失敗先問四個問題，定位壞在哪一層

每次 run 失敗，不要急著動 prompt。先依序問四個問題：

1. 這份證據，有沒有真的進到模型的 context？
2. 工具契約（tool contract）是不是含糊？模型有沒有可能用錯工具，或誤解某個參數的意思？
3. harness 是不是放行了一個本來不該放行的動作？
4. 事件對應（event correlation）是不是把不該接在一起的工作，接到了同一個 run？

這四個問題，對應的是四個不同的層：context、工具介面、harness 的權限邊界，以及事件對應。

只要定位出是哪一層，就知道該去改哪個檔案、哪個函式。反過來說，如果證據根本沒進 context、工具契約本身含糊，或 harness 沒擋住危險動作，這些都不是 prompt 修得動的。

這時候改措辭，只會讓你以為問題修好了；實際上，問題還好好地留在系統裡。

## 為什麼「改 prompt」通常不是答案

課程刻意把程式碼做得很小。重點不在程式碼有幾行，而在幾個工程判斷：

- 分清楚「通知」和「狀態」的差別。
- 決定一個 incident 的生命週期。
- 把權限放在正確的邊界。
- 從含糊的副作用裡恢復。
- 設計可以用來評估的證據。

這幾件事，沒有一件是 prompt 能直接修好的。

通知和狀態分不清，代表你把 event 當成了 state 快照；incident 生命週期沒有定義，代表你不知道什麼時候該關、什麼時候該重開；權限放錯邊界，是 harness 的問題；要從含糊副作用中恢復，靠的是 idempotency 與 action ID；評估證據不足，則是因為你沒有留下可以對照的紀錄。

這些都是系統層的判斷，不是一句更漂亮的指示就能解決。

所以，「該改哪一層」這個問題，問的其實是：這次失敗，究竟是證據、契約、權限，還是事件對應出了問題？

prompt 只是候選修法之一，而且通常排在最後。

## 換一個模型：比 trajectory，不比文筆

有一個延伸練習值得做：挑一個 trial，換第二個模型再跑一次。

重點是比較 trajectory，而不是比較報告的文筆。不要看哪一份報告寫得比較順、比較有說服力；要看的是行動軌跡：

- 它走了哪些步驟？
- 使用了哪些工具？
- 在哪裡停下來觀察？

這裡有個反直覺的地方：一個走了比較多「唯讀步驟」的 agent，可能反而更安全，因為它在做決策前多觀察了幾次。

另一個很快達標的 agent，也可能在過程中踩過 approval 邊界，只是報告寫得很漂亮，把這件事蓋掉了。

所以你要看的，是過程，不是結論的措辭。

看完兩個模型的差異後，練習做兩個決定：

第一，哪些差異在 production 可以接受，哪些不能接受。

第二，替未來的 evaluation suite 寫下一條自動化 assertion。把剛才「用眼睛看 trajectory 才看得出來」的事情，變成一條機器每次都會檢查的規則。

## 多 region：兩個 checkout region 會同時出事

接下來把設計搬到紙上。

下一版的世界是這樣：有兩個 checkout region，而它們的 outage 可能重疊。不是「一個掛掉、另一個撐著」，而是兩個同時出事。

<!--image:3-->

這種情況下，你要設計三件事。

**選一個 incident key。**

你要決定什麼可以代表「這是同一個 incident」。依據可以是 region、服務，或某種症狀組合。

這個 key 會決定後續收到的 alert 要往哪裡合併。

**訂出一條把新 alert 併進來的規則。**

當新 alert 進來時，什麼情況下應該併進現有的 incident？什麼情況下應該開一個新的？

當兩個 region 的 outage 重疊，這條規則會直接影響你面對的是「一個大 incident」，還是「兩個小 incident」。

**訂出一條關閉或重開 run 的規則。**

什麼時候算 incident 結束，可以把 run 關掉？如果關掉後又出現新的 alert，要重開同一個 run，還是另起一個？

這條規則沒有想清楚，就會遇到「以為結束了，其實還沒」的窘境。

這三個決定，說到底還是同一組老問題：通知和狀態怎麼分、incident 的生命週期怎麼定、事件對應該怎麼接。

只是這次多了兩個 region，難度被放大了。

## 改完 state、還沒發 alert 就掛掉：事件怎麼保住

多 region 設計裡，最刁鑽的一段是這個：

如果 checkout process 在「改完 state 之後、發 alert 之前」掛掉了，事件要怎麼保住？

<!--image:4-->

這是典型的「含糊副作用」：state 已經變了，但對外通知還沒有發生。

如果沒有處理，你就會落在一個誰都不知道發生過什麼的狀態：世界已經改變，卻沒有任何 alert 把這件事傳出去。

因此，設計時要先分清楚：哪些部分該放在 service、哪些放在 operator API、哪些放在 durable workflow，以及哪些才屬於 model prompt。

- **service**：負責變更 state，也要可靠地記下「這個事件要發出去」。重點是，state 變更和「待發事件」不能分開做，否則就會出現上面那個斷點。
- **operator API**：作為對外的操作入口，接收動作並回報結果；它必須是可被信任、也可被驗證的。
- **durable workflow**：撐住「等待事件、被喚醒、重試、恢復」這些跨時間的流程，讓 process 掛掉後仍能接回來。
- **model prompt**：只放模型決策需要的內容，例如它能看什麼、能選什麼。不要拿 prompt 去補系統層的漏洞。

這四個位置放對，才有機會在 process 崩潰後，還原出「應該發出、但尚未發出」的事件。

## 為什麼 simulator 的 outbox 故意放在記憶體

課程裡的 simulator 有個刻意的設計，值得特別說明，免得你誤會。

這個 service 在 process 還活著時，會重試 event delivery。但它的 state 和 event outbox 都故意放在記憶體裡。

也就是說，只要重啟，整個世界就會被重置。

這不是 bug，而是教學上的選擇。它讓「instance 邊界」在課堂上清楚可見：你可以親眼看到 process 一停，記憶體裡的東西就全部消失，於是明白「把狀態放在記憶體」和「真的有 durability 保證」是兩回事。

但這種設計明確不是 production 的 durability 保證。

一個真正的 service，會把 outbox 和 state change 放在同一個 transaction 裡儲存：state 改了，待發事件也一起寫進去，中間不會留下斷點；同時，還會使用 authenticated 的呼叫，確保對外溝通是可信的。

<!--image:5-->

這正是上一節「改完 state、還沒發 alert 就掛掉」問題，在真實系統裡的解法。

弄壞它，是為了看清楚那條界線在哪裡。看懂 simulator 哪裡故意偷懶，你才知道換成自己的場景時，哪一塊非補不可。
