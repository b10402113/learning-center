# 哪些東西該進 step

上一篇已經講完兩條規則。現在回到 loop body，問題變得很具體：這裡有十幾個呼叫，哪些要包進 `step.run`，哪些要留在外面？

## 每一行都要問的問題

每一圈開始時，先問一個問題：哪些東西需要被 checkpoint？

換個問法會更容易回答：如果 server 現在掛掉，哪些事情是我不想再做一次的？

把這個問題套用到每一行，答案就會自然分成兩邊。

## 留在外面的：新鮮度

首先要取得目前的 run：`await getRun(...)`。

你可能會覺得這應該放進 step，但我不這麼做。原因是我不希望它被 memoized：我永遠都想取得最新的 run，不管怎樣都不想快取它。我要看到的是 run 現在的狀態，所以它要留在 workflow 裡，每一圈都重新讀取。

<!--image:1-->

每一圈開始時，也要再檢查一次 run 的狀態，看它是否處於那幾種終止狀態。如果是，就 return。

第一次進入時，這個判斷一定是 false，不可能觸發。真要觸發的話，上面的檢查早就先攔下來了。但 agent 做完一個動作後，run 的狀態可能會變成 completed。回到下一圈時，就需要再次檢查。少了這段，你就只會在 run 剛開始時檢查一次，之後便不再確認。

goal 也一樣。檢查 goal 是否達成時，我不會把它放進 step。每次都要重新檢查，不希望結果被快取；否則它就永遠不會再執行。

這幾個東西的共同點是新鮮度：它們的答案會隨時間改變，而你要的是當下的答案。把它們快取起來，等於問錯了問題。

## 變成 step 的：副作用與觀察

取得 state 是第一個 step。

<!--image:2-->

使用 `step.run`，名稱設為 `observe-state`，並帶上目前的圈數，也就是 cycle。這樣一看就知道 state 是在哪一圈觀察到的。callback 裡的內容很簡單：return `agentState`，並傳入 environmentId 和 runId。

為什麼要把這個放進 step？因為 state 的結果可能會改變，而且這裡也包含 cycle 的變化。我希望它被 memoized：取得一次後就保留下來，不要再執行。workflow resume 時，這段程式就不會再次執行。

原則可以這樣記：大部分非同步操作都會放進 step，只有少數例外。`getRun` 其實也可以放進 step，但我認為結果不會有差別，所以放不放都可以。

反過來說，會改變外部世界的呼叫不能留在 workflow 裡。只有 step 的結果會被記錄下來。若把會寫入資料的呼叫留在 workflow 裡，重播時它就會再次執行。

## 一個 step 只做一件事

大多數情況下，一個 step 只做一件事，不要一次塞進太多工作。

當然也有例外。你可以在一個 step 裡放多個非同步操作，前提是你能接受這樣做的後果：其中一個操作失敗，整個 step 就會重跑，所有操作都得重新執行，而你也確認這樣沒問題。

但如果你在一個 step 裡做了 38 個非同步操作，第 2 個操作失敗，而第 1 個會產生副作用、你又不希望它再次執行，那第 1 個就應該有自己的 step。不要把它們全塞在同一個 step 裡；step 一旦失敗，retry policy 就會重新執行整個 step，第一個非同步操作也會跟著重跑。

<!--image:3-->

所以我的建議是：把非同步操作放進 step，並遵循單一職責原則，讓每個 step 只做一件事。除非這些操作彼此相關，而且全部重播也不會造成任何後果，才適合放在一起。之後再依照應用程式的需求，調整拆分或合併的方式。

現在，你已經能判斷 loop body 裡的每個呼叫該放在哪裡了。下一個 node 要探討的是另一件事：你一直重新讀取的那個 run，到底是什麼？它的狀態、schema，以及 business state 和 workflow state 之間的落差。
