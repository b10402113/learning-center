# 哪些該進 step、哪些留在 workflow：單一職責

兩條規則懂了之後，回到實際的 loop：把每一圈攤開，第一個要決定的是，哪些呼叫要進 step、哪些留在 workflow。

你已經有一個會反覆執行的 Loop。接下來要決定的是：每一圈一開始要做什麼，以及哪些結果要 checkpoint，留著下次接續使用。

最常見的錯誤有兩種，方向剛好相反。

第一種是把每個非同步呼叫都塞進 `step.run`。這樣一來，有些值可能永遠停在第一次取得的快照。你以為自己在看最新狀況，其實讀到的是舊資料。

第二種是把一整段流程塞進同一個 step。假設第二件事失敗，整個 step 重跑，第一件事也會再執行一次。如果第一件事有副作用，就可能多做一次。

要避開這兩種錯誤，可以先問自己一個問題：

如果 server 掛掉，哪些事情是我們不想再做一次的？不想重做的，就交給 step 記住結果；每次都要重新做的，就留在 workflow。

## 大部分非同步操作會放進 step

有一個大原則：非同步操作通常適合放進 step。

非同步的意思是，必須等待外部回應，結果不會立刻出現。取得 run、讀取 state、呼叫外部服務，都屬於這一類。

把它們放進 step，是因為 step 的結果會被記住。workflow 從中斷處接續執行時，就不會再跑一次已完成的操作。

不過，「大部分」不代表「全部」。有些操作應該留在 workflow，因為我們不希望結果被記住。

## 拿到最新的 run，為什麼不放進 step

先看每一圈一開始要做的事：取得目前的 run。

<!-- derived -->

```ts
// 留在 workflow：每次都讀最新的，不快取
const run = await getRun(runId);
```

你可能會想把這段也包進 step，但我不會這麼做，因為我不希望它被記住。我想拿到的是最新的 run，而不是快取的舊資料。

所以，拿到最新的 run 這件事，我會留在 workflow。

在這段程式碼和這個情境裡，實際差異可能不大。但我就是不想讓它被快取。

## 每一圈開頭，都重新檢查終止狀態

拿到 run 之後，檢查它的狀態是否已經是終止狀態。如果是，就直接 `return`，不用繼續執行。

這個檢查也要留在 workflow，因為每一圈都要重新看一次。如果把它放進 step，第一次檢查的結果就會被記住，後面不再執行。即使 run 的狀態已經改變，流程也可能繼續跑，停不下來。

第一次進來時，這個判斷一定是 false，因為如果 run 當時已經該停止，前面的檢查早就會攔下來。但 Agent 完成一個動作，或發生其他事情後，run 的狀態可能變成 `completed`。因此，下一圈開始時要再檢查一次。

少了這段，你就只會在 run 剛開始時檢查一次，之後不再確認。把檢查放在每一圈開頭，才能每一輪都看最新狀態。

## 取得 state 是第一個 step

接著取得 state。

取得 state 是第一個 step。我們希望這個結果被記住：如果 state 已經取得，就保留它，不要再跑一次。

因此，使用 `step.run`，並把 step 命名為 `observe-state`，再加上目前的圈數，也就是 `cycle`。這樣在 Inngest 或其他工具中查看時，就能知道這是第幾圈取得的 state。

<!-- derived -->

```ts
// 放進 step：結果會被記住，resume 時不再執行
const state = await step.run(`observe-state-${cycle}`, async () => {
  return agentState(environmentId, runId);
});
```

第一個 step 完成後，我們就取得 state 了。workflow 恢復執行時，這段不會再跑一次。

## 檢查 goal 是否達成，也留在 workflow

取得 state 之後，檢查 goal 是否達成。這個檢查也不放進 step。

理由和前面一樣：我希望每次都重新檢查，不希望結果被快取。如果被記住，之後就不會再執行這個檢查。

到這裡，判斷方式就很清楚了。要不要放進 step，不是看這件事是否非同步，而是看你要不要把結果記住。

要記住的，放進 step；每次都要重新確認的，留在 workflow。

## 一個 step 只做一件事

決定把操作放進 step 之後，還要考慮一個問題：一個 step 裡可以放幾件事？

大多數情況下，一個 step 只做一件事，不要把很多件事塞在一起。

原因是重試以 step 為單位。step 失敗時，retry policy 會讓整個 step 從頭執行。裡面有幾件事，就會重跑幾件。

假設一個 step 裡有 38 個非同步操作。第二個操作失敗了，但你不希望第一個操作再跑一次，因為它可能會造成副作用。這時，第一個操作就該有自己的 step。

如果把它們放在同一個 step 裡，step 一失敗、retry policy 一重跑，第一個非同步操作也會跟著再執行一次。

一個 step 只做一件事，除非你接受它整個重跑。

## 什麼情況可以放在同一個 step？

有一種情況可以例外：你可以把多個非同步操作放在同一個 step 裡，但前提是你能接受重跑的後果。

也就是說，其中一個操作失敗時，整個 step 會重跑、所有操作都會再執行一次，而你不介意這件事。

因此，要把多個操作放在一起，必須同時符合兩個條件：它們彼此有關，而且全部重跑也不會造成任何後果。兩個條件都成立，才適合放在同一個 step。

這是我的思考方式：先依照單一職責拆開，再視應用程式的需要，把操作拆細或合併。

## 檢查自己的 Loop，可以先問三個問題

把每一圈開頭的程式碼攤開，逐一檢查每個呼叫：

1. **它是非同步的嗎？**  
   如果不是，就留在 workflow。

2. **它的結果可以一路沿用到最後嗎？**  
   如果可以，就放進 step，讓結果被記住。

3. **它和同一個 step 裡的其他操作，有沒有「重跑會出事」的關係？**  
   如果有，就拆成各自的 step。

問完這三個問題，大致就能判斷 Loop 裡的操作該放在哪裡。
