# 為什麼要把 loop 拆成 step：一個失敗不能整段重做

想像你的 agent 正在處理一件 incident：讀 log、呼叫模型，判斷某個 feature 出了問題，接著把 feature 關掉。就在這時，伺服器掛了。

多數人會期待伺服器重啟後，agent 能從「關掉 feature」之後接著做。實際上它會從頭開始：重新讀一次 log、再呼叫一次模型，也重新做一次判斷。

這跟運氣無關，問題出在工作流程的結構。

## 一個 step 就是一個 durable 的單位

到目前為止，我們的 agent 只有一個 step。

step 可以想成 agent 留下執行成果的單位。durable 指的是 step 的結果會被記住，這種做法叫 **memoized**。中斷後恢復時，已完成的 step 直接沿用結果，不必重做。

step 的邊界，其實就是重跑時哪些工作可以跳過的邊界。

## 全部塞在同一個 step 裡會怎樣

第一個 agent 有一個 goal，放在 loop 裡執行，但所有工作都擠在同一個 loop：檢查 log、呼叫模型，再把出問題的 feature 關掉。

伺服器若在這個 step 完成前掛掉，恢復時 agent 會把整套流程從頭做一遍。

代價不是多花一點時間，而是全部重來：讀過的 log 再讀一次，想過的判斷再想一次，關掉的 feature 再處理一次。

<!--image:2-->

## 拆開之後，resume 有地方可回

做法是把這些工作拆成各自的 step。

拆開之後，不管是遇到 outage，還是基礎設施出問題要恢復，workflow 都從下一個還沒完成的 step 接下去，前面已完成的 step 不用再跑。

儲存 state 之後，恢復時什麼資訊都不會掉，就像沒失敗過一樣。

<!--image:3-->

## 下次寫 loop 之前

下次寫 loop 時，先問自己一句：如果這裡失敗，重跑一次會付出什麼代價？

答案如果是「全部重來」，這段工作就不該跟其他工作擠在同一個 step，該拆。拆 step 不是為了讓程式看起來整齊，它真正的作用，是失敗時只需要從上一個完成的 step 之後接著跑。

Inngest 這類工具能把這件事變得很簡單，但前提是你先想清楚哪裡該切。切分的位置想好了，工具才派得上用場。
