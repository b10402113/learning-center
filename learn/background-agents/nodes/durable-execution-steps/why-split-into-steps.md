# 為什麼要拆步驟

## 前言

背景 agent 是指 request 結束後仍持續執行的程式。它可能執行幾分鐘，也可能跑上幾小時，但 server 不保證能一直運作。一次 outage 或基礎設施問題，就可能讓 process 結束，連同記憶體中的狀態一起消失。如果沒有妥善處理，重啟後就只能從頭開始：已完成的工作得再做一次，已經發生的副作用也可能再次發生。

你可能遇到的情境很具體：你已經有一個 loop，負責檢查 log、呼叫 model，並關閉出問題的功能。這個 node 要處理的，就是 loop 被終止後如何接續執行，而不是把做過的事再做一遍。

這個 node 會依序回答四個問題：為什麼一個大 step 在 crash 時無法保留進度？拆開之後，resume 究竟會讀取什麼？這種讀取方式對程式碼提出了哪兩項要求？最後，在實際的 loop body 裡，哪些呼叫應該放進 step，哪些應該留在 workflow？讀完之後，你應該能指著每個 step 說明：「如果這裡中斷，狀態會去哪裡？」下一個 node 則會接著探討 run 這個物件本身：它的狀態、schema，以及 business state 和 workflow state 之間的落差。

這篇文章先處理第一個問題：run 執行到一半時，server 掛了。究竟有哪些事情會再跑一次？

## 你遇到的 crash

第一個 agent 有一個 goal，並把所有工作都放在同一個 loop 裡：檢查 log、呼叫 model，然後關閉出問題的功能。

<!--image:1-->

整個 loop 就是一個 step。

執行時，step 會開始檢查 log、詢問 model，接著關閉出問題的功能。然後 server 掛了。原因可能是 outage，也可能是基礎設施問題。不管是哪一種，process 都會消失，存在記憶體裡的 state 也會一起消失。

這裡沒有任何接縫：沒有地方記錄「log 已讀取」，也沒有地方記錄「model 已詢問」。因此 run 恢復時，沒有可供接續的進度。系統唯一知道的，就是這個 step 尚未完成。

## 為什麼重試單位是整個 step

step 是 agent 能保存進度的地方，原因很簡單：step 會被 memoize。結果會被記錄下來，而這些紀錄正是 run 能從中斷處 resume 的依據。

這個機制很簡單，但界線也很明確：step 是最小的記錄單位，step 裡的個別操作不會另外記錄。

所以，如果你把所有事情都塞進同一個 step，就等於用一個記錄單位涵蓋整段 run。需要恢復時，runtime 會重跑整個 step，因為所有工作都在裡面。重試的單位是 step，不是某一行程式碼，也不是你剛好執行到的那個 function call。

把前面的 crash 說得更精確一點：server 在 step 關閉出問題的功能之後、step 回傳之前掛了。resume 時，整個 step 都會重跑：再次檢查 log、再次呼叫 model，也再次關閉該功能。最後這件事明明已經發生過，現在卻又發生了一次。

這就是把所有事情放進單一 step 的代價：故障可能只發生在一個小地方，重做的範圍卻是整個 step。設計中沒有任何地方能讓 run 說：「關閉功能這件事，我已經做過了。」

## 從最後一個完成的 step 接續執行

把同一份工作拆成各自獨立的 step：一個 step 讀取 log，一個 step 詢問 model，另一個 step 關閉出問題的功能。每個 step 完成後，結果都會被記錄下來。

run 還是在同一個地方掛掉，但系統現在能指出最後完成的是哪個 step。如果詢問 model 的 step 已經完成，關閉功能的 step 還沒完成，resume 就會從關閉功能開始。讀取 log 和詢問 model 的 step 都已經完成，不必重跑。

<!--image:2-->

這個特性值得記住：resume 時，run 會從上次停下的位置接續執行，workflow 則從下一個尚未完成的 step 繼續。保存 state 的方式讓這件事成為可能，而且不會丟失資訊。這樣一來，run 的行為就像從未中斷過。

「資訊」這個詞有實際含義：不只是 process 重啟了，已完成 step 的結果也能保留下來。前一次呼叫 model 得到的答案，恢復後仍然是同一個答案。你不必再次呼叫 model，也不會因此拿到不同的答案。

Inngest 這類工具能讓這種拆分方式更容易實作。重點不在工具，而在於接縫：只要把工作切分在適當的位置，crash 就不再代表「從頭開始」，而是「接續執行」。

接下來的問題是：resume 跳過那些已完成的 step 時，究竟在讀取什麼？
