# 背景 agent 的介面不是聊天，是收件匣

## 前言

你想要的是一個即使筆電關了也會繼續運作的背景 agent。它能自己 observe、自己 decide、自己 act，一輪接著一輪。

它唯一不能自行決定的事，就是改變 production 的狀態。

這件事如果沒解決，就只剩兩條爛路可走。一條是讓每個危險動作直接執行，出了事再回滾；另一條是每個動作都停下來等人批准，而你就坐在那裡一個個按下批准。第二條路會讓背景 agent 變成一個比較慢的 chat agent。

這個 node 採取的是中間那條路。第一篇先回答：為什麼它的介面是收件匣，而不是聊天窗？一件卡住的事，是由誰決定要放進收件匣的？第二篇會問：批准之前，那個動作存在哪裡？醒來之後，又要怎麼接回同一個 run？第三篇則會問：如果批准期間世界變了，該怎麼辦？

讀完之後，你的 harness 會多出一條批准（approval）分支。它能暫停、續跑，也能拒絕一份過期的提案。先從最前面那個問題開始：為什麼這裡沒有聊天窗？

## 沒有訊息歷史，就沒有聊天窗

你請 coding agent 執行一個指令，它回你：「我需要你的批准才能執行。」

聽起來像是 human-in-the-loop（HITL），但迴圈已經跑完一輪了。你並不在迴圈裡；它只是把一個請求丟回給你。你關掉電腦，那個請求就會被擱在那裡。

Chat agent 也可以設定成「執行前先問我」。它會停下來，等你按下 yes 或 no。這確實是 HITL：迴圈停在中途，那個動作還沒完成，就無法繼續。差別在於，它綁定在你的電腦上。電腦一關，它就不會再跑。

背景 agent 要做得更進一步：它直接進入迴圈，並把迴圈暫停下來。

麻煩的是，背景 agent 沒有任何訊息歷史。它不記錄聊天內容，什麼都沒有。因此，chat 這種介面在這裡行不通。

它更像是一個收件匣：agent 自己去做事，需要你的時候，就往收件匣裡放一件事。你清掉這件事，它就能解除封鎖。

<!--image:1-->

所以，你的工作不是聊天，而是清掉卡住它的事。

還有一個關鍵差別：你回覆之後，它要恢復原本的迴圈。它不該把「我需要幫忙」當成這一輪的結論，等你回覆後再開一輪新的；它應該留在同一個迴圈裡繼續跑。

## 收件匣裡的兩種事，只有一種由模型決定

收件匣裡有兩種事。

第一種是「幫我回答這個問題」。這是 agent 自己決定的：上一輪它會選擇「I need help」這個 action。相關能力已經提供，只是還沒實作。

第二種是「我需要批准」。這句話不是 agent 說的，而是 harness 說的。

<!--image:2-->

agent 並不知道自己需要批准。這條規則是直接寫在 harness 裡的。

因此，收件匣裡的內容不一定來自 LLM。它可能來自 harness，也可能來自 LLM，但兩者都算是 agent 提出的，因為 agent 是由 LLM 和 harness 組成的。

這裡要想清楚：不是每件事都由 agent 決定，有些事情是 harness 裡的確定性邏輯。

這個差別很實際。第一種要寫 eval，因為你測的是模型的判斷；第二種則是程式碼，直接寫測試就好，沒什麼需要 eval 的。

## 把 policy 藏起來，選擇才誠實

這次拿 `rollback release` 當作第一個需要批准的動作。

policy 早就寫好了，在 lesson 4 的分支上。rollback 那邊也已經有 approval。我們沒有把 policy 暴露給 agent；它只看得到一個叫 `rollback release` 的 action，不知道 policy 要求批准。

為什麼要藏起來？

假設 agent 知道這個工具需要等人批准。它可能開始盤算：我很想把事情做完，但這個工具得等人，而那個人回覆很慢，所以我換個做法。這些資訊就會影響它的選擇。

我不希望它因為知道「這需要批准」而改變決策，所以把這項資訊留在 harness 裡。

還有一個理由：測試已經顯示，模型很會替自己找理由：「我沒問你，是因為我不需要問，原因如下。」你只能回：「好吧，你說得對，但我明明就叫你不要這樣做。」

不要給它為這件事推理的機會。

當然，你也可以告訴它。這是偏好問題。我選擇不說，因為它不需要知道。知道了又能做什麼？

## 是煞車，不是盾牌

先把話講清楚：approval 不是萬用的安全盾牌。

模型仍然可能在讀到一行不可信的 log 後，提出錯誤的動作。讀 log 不需要批准；讀完之後選錯動作，是另一回事。不要把這兩件事混為一談。

我一開始的做法是：凡是會改變狀態、具有寫入權限的動作，都先放到批准流程後面，再盡可能降低風險。

也要反過來想。如果你的背景 agent 監控的系統需要大量寫入，而每次寫入都要你批准，你一天可能得在收件匣裡按二十幾次。

這時候你該花時間思考的，是怎麼讓 AI 不用每次都問你，也能安全地執行。

例如，建立一套出錯時能快速回滾的機制；或是把爆炸半徑縮到最小；也可以採用灰度發布，先發布 10%，再到 20%，最後到 40%。

否則，你只是在回到 chat agent 的模式，坐在那裡等它回覆。生產力根本無法充分發揮。

我相信，對大多數人來說，未來的工作就是看著一個收件匣，回一句：「你為什麼要這樣做？」或是：「好啊，不過不是 12 號，是 13 號。」

下一篇要處理這條 approval 分支的內部運作。agent 不知道自己被擋下來，那麼被擋住的動作在等待期間存在哪裡？收件匣只是一個畫面，背後讀取的是資料庫裡的一張表。那張表什麼時候寫入？agent 醒來之後，又怎麼知道要接回哪個 run？
