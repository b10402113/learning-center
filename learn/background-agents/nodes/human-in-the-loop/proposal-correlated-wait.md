# 資料庫是唯一的真相來源

上一篇提到，approval 是 harness 的確定性邏輯，agent 不知道自己被擋下來了。那麼，被擋下的動作在等待期間放在哪裡？

答案是資料庫。收件匣只是一個畫面，讀取的是資料庫中的一張表。

這篇就沿著 `rollback release` 走一遍。從 policy 要求批准，到 action 真正執行，中間會經過好幾個 step。每一個 step，都是為了解決特定問題。

## 動作先存成資料庫裡的一列，才輪到人來看

有些 action 需要經過批准。即使 AI 已經決定「這就是我要做的動作」，它仍須先經過批准，因此會成為一個待審核的動作（proposed action），也就是一筆 proposal。

這筆 proposal 一定要存進資料庫。為什麼？

當你回到收件匣按下 approve 時，總得有地方可以找回那個 action 原本的樣子：它要帶哪些參數、要如何執行。這些狀態必須存在某個地方，之後才能讓收件匣中的按鈕對應到它。

沒有這個 reference，你也許可以靠 workflow runtime 的 state 回到那個位置，但我不覺得這是好主意。這屬於應用邏輯。

應用邏輯應該存在你自己的資料庫裡，讓 runtime 專心處理 workflow 邏輯。

當然，你也可以偷懶，仰賴 runtime。但有一筆 proposal 存在那裡，我會比較安心。而且哪天你想做一個畫面，查看「AI 目前要求我做的所有動作」、瀏覽歷史紀錄，或同時管理一群人、以及每個人手上的多個 agent，就會需要它。

## 存版本號，不存快照

proposal 要記下它是在什麼狀態下提出的。

在我們這個假 server 上，每次狀態改變，我都會記錄一筆，將 snapshot 存進資料庫，並給它一個新的 `version`。因此，agent 不必到處傳遞 snapshot，只要傳一個版本號，server 就能用它找到真正的快照。

換句話說，它傳的是快照的 reference，而不是快照本身。

建立 proposal 時，`proposedAction` 需要傳入 environment ID、run ID、action ID，也就是 `decision.action`，以及當下的 state。這裡比對的是 `state.world.version`。

為什麼不直接把整份 snapshot 塞進去？因為你現在需要的，只是一個足夠精簡的資訊，讓你之後能判斷它是否仍然有效。版本號就是這個資訊。

## 建立 proposal、回傳 id，再讀回來

建立 proposal 的 step 完成後，只會回傳 `proposal.id`。

接著，我們再開一個 step，叫 `get proposal`，用剛才回傳的 id 從資料庫把 proposal 讀回來。

你可能會問：為什麼不直接把這個 proposal 往下傳、直接使用就好？

可以，但這是非同步流程，資料可能會被覆寫（override）。

我不知道什麼時候會有人處理這筆 proposal，所以不希望在這裡使用快取。我還是透過 step 來讀取，因此它可能會被快取；但我不想把這裡的變數帶到下一行，而是要直接從資料庫讀取。

一來，我不知道資料庫中的資料是否可能被覆寫；二來，我要的是以資料庫為唯一真相來源，而不是依賴某個可能存在、也可能早已失效的快取值。這個 workflow 會執行很多次，從這裡到那裡的這段時間，資料可能早就變了。

這個坑我踩過兩次。

我知道這點，是因為自己踩過很多次。寫課程時，我又踩了一次，卡了兩個小時，完全找不出原因。我太固執，不想問 Codex，只想自己搞懂。結果我拿到的是一份已經過期的 proposal，因為我用了這裡的 proposal 變數。寫課程的工作隔幾天才進行一次，中間隔了太久，等我回去查看時，它們早就過期了。

所以我才說：要從資料庫讀取最新資料。

你可能會說：這是一個 step，服務可能執行到一半就停止，之後再重新啟動。在這段期間，可能有人已經處理完這筆 proposal，甚至把它清理掉了。沒錯。proposal 從建立到讀取，可能已經發生很多變化。唯一能確定它目前狀態的方法，就是從資料庫讀取，不要相信上面那個變數。

這跟資料庫交易的道理一樣。寫得正確的交易，通常不會只說「我就用這個值」，而會等到寫入真正完成後，再讀取資料。這裡也是一樣。

## 等待這筆 proposal，不然下一個批准事件會叫醒所有人

接下來是等待。

`check = 0`。然後 `while (proposal.status === "pending")`，只要還在等待，就繼續。每次進入迴圈，先 `check++`，再 `step.waitForEvent("wait for human", ...)`，把 `cycle` 和 `check` 帶進去。接著再從資料庫讀取一次 proposal。

為什麼每一輪都要重新讀取？因為我們在迴圈裡，每次檢查時，proposal 都可能已經不同，所以每次都要取得最新資料。這個 while 並非必要，我只是用它來模擬人一直沒有回覆的情況。實務上不一定要這樣寫。

事件的名字是 `agent.approval.decided`。有人按下 yes 或 no，服務就會送出這個事件。

接著要加上過濾條件：`async.data.proposalId` 必須等於我們手上的 proposal ID。

<!--image:2-->

為什麼一定要過濾？不然，只要系統裡有任何一個人批准了任何一個任務，所有任務都會被當成已批准。這樣你就會把工作搞丟。

通過這一關，代表 proposal 已經收到回覆。因此，我們開一個 step，叫 `reconcile human`，把 `cycle` 和 `check` 帶進去，然後再讀取最新的 proposal。能執行到這裡，代表它已經更新過了。我們還不知道收到的是 yes 還是 no，但可以確定它有更新。

跳出 while 迴圈後，我們就要問：對方到底說了什麼？

如果 `proposal.status !== "approved"`，我們就開一個 step，叫 `stop after human`，把 cycle 帶進去，然後將 run 的狀態設為 escalated。

為什麼是 escalated？你不批准，但我認為這件事必須做，所以就把它標記為升級處理。它不是 completed，因為我沒有執行；也不是 failed。它的意思是：「我沒有別的辦法了：我告訴你我要做這件事，你說不要，那就由你自己處理。」

被拒絕之後要怎麼做，可以由你自行決定。有些 agent 的做法是：人類拒絕之後，就把它當成「好，我不能走這條路，但還是得把事情做完，所以我要另找方法」。我們目前的做法比較簡單，一被拒絕就放棄。

接著記錄人類的決定，`humanDecision = proposal.status`，存下他們填寫的內容，最後 return。

走到這裡，流程就分成兩條路：approve 會繼續往下，reject 則會把 run 標記為 escalated。

不過，approve 之後還沒結束。這筆 proposal 撐過了等待，正確的 run 也醒來了。但它建立時所對應的版本，可能已經是另一個世界——甚至是一個禮拜前的狀態。下一篇要問的是：如果批准期間世界變了，該怎麼辦？
