# 會話維持：Cookie、登入、代理與驗證碼

## Learning goal

用 `Session` 維持登入、正確帶 Cookie，並用代理池與驗證碼辨識突破頻率與人機限制，判斷何時該用哪一招。

## Steps

1. [[learn/js-reverse2/nodes/cookie-session-login-proxy/cookie-session-basics|Cookie 與 Session：HTTP 無狀態怎麼維持登入？]] — 看懂 Cookie 為何存在，以及 Session 如何自動承接狀態
2. [[learn/js-reverse2/nodes/cookie-session-login-proxy/manual-vs-session-cookie|Cookie 要手動帶還是用 Session 自動帶？]] — 依 Cookie 是否變動、是否跨請求，選對帶法（after step 1）
3. [[learn/js-reverse2/nodes/cookie-session-login-proxy/simulated-login|模擬登入：用 Session 走完帳密登入流程]] — 送出帳密、讓 Cookie 自動存入、再存取登入後頁面（after step 2）
4. [[learn/js-reverse2/nodes/cookie-session-login-proxy/proxy-anonymity-and-pool|代理伺服器：匿名度、類型與代理池]] — 用代理輪換 IP，突破高頻請求的封鎖（after step 2）
5. [[learn/js-reverse2/nodes/cookie-session-login-proxy/captcha-ocr|驗證碼辨識：接上圖鑑平台解圖形驗證碼]] — 把驗證碼圖片外包給 OCR 平台取回文字（after steps 3–4）

## Lesson

前兩個節點你學會了送出請求、偽裝標頭、解析頁面，但只要目標需要「先登入才看得到」或「請求太頻繁就被擋」，那套單次請求的寫法就會立刻失效。這一節處理的正是這種目標：網站靠 Cookie 認得你，靠 IP 記錄你的行為，靠驗證碼確認你是人。三者其實是同一件事的三個面向——伺服器如何在沒有記憶的 HTTP 上，認出「你是誰、你來過幾次、你是不是機器」。

這條線上有兩種帶 Cookie 的做法、兩種突破限制的手段。手動把 Cookie 塞進標頭最快，但一旦 Cookie 有有效期或含即時變動的片段就會失效；`requests.Session` 會自動承接伺服器發的 Cookie，代價是你至少要發兩次請求。代理則是把請求的來源 IP 從自己換成代理伺服器，用來避開高頻封鎖；驗證碼辨識則把「證明自己是人」這關外包給第三方 OCR 平台。五個步驟依序建立這條線：先懂 Cookie 與 Session 的原理，再學會在「手動或自動」之間選擇，接著實際跑一次登入，最後補上代理與驗證碼這兩個突破限制的工具。
