斷點怎麼下：行、事件監聽與 XHR 斷點

Step 3/5 · DevTools：斷點、請求堆疊與呼叫堆疊

學習目標

依「值在什麼時機、什麼位置產生」選對斷點種類，讓執行停在能觀察到加密值的地方。

前言：程式不會因為你盯著它就停下來

你已經用上一節的方法，找到了幾段疑似處理加密值的程式。你把那段程式打開，從頭到尾看了一遍，卻發現它寫得很順、一眨眼就跑完了，你根本來不及看某個變數在中途變成什麼。程式不會因為你盯著它就停下來。你必須在對的地方設一個斷點，強迫它在那一行暫停，把當下的狀態攤在你面前。

但斷點不是只有「在某一行插一根旗子」這一種。DevTools 提供了好幾類斷點，用在不同的時機。下錯了種類，輕則程式根本不停，重則停在一個莫名其妙的時間點，讓你誤判方向。這一節要做的，就是讓你看著手上的線索，挑出正確的那一類斷點。

前置條件：你已經知道加密值可能在哪（Step 1），也知道怎麼用請求堆疊或關鍵字找到候選程式（Step 2）。你會打開 Sources 面板、看得到原始碼的行號。

你手上有哪些斷點可以用

這一節要比較的是三類最常用的斷點。它們的差別，用一句話講就是「你希望程式在什麼時機、什麼條件下停下來」。

斷點種類什麼時候停典型適用時機
行斷點（Line breakpoint）執行到某一行時你已經知道（或強烈懷疑）處理這個值的那一行
事件監聽斷點（Event listener breakpoint）某個事件（如 click、腳本載入）發生時你需要在頁面程式執行之前就先停住、插旗
XHR／Fetch 斷點送出或收到非同步請求時你知道這個值是由哪個 XHR／Fetch 請求送出的

三者的起點不同：行斷點從「位置」出發，事件監聽斷點從「事件」出發，XHR 斷點從「請求」出發。你的線索是哪一種，就優先選哪一種。

行斷點：當你知道大概在哪一行

行斷點是最直覺的一種。你在原始碼左邊的行號上點一下，那一行就出現一個藍色標記；之後程式每次執行到那一行，都會暫停。它適合你已經用關鍵字搜尋或請求堆疊，縮小到某一段程式時使用。

下面這個小檔案就是最單純的示範。它依序做三件事：把 x 設成 1、印出來，然後換 y、再換 z。如果你在第二行 console.log(x) 按下行斷點，重新載入後程式就會停在那一行，你可以在 Console 或滑鼠移上去看到 x 此刻等於 1。

var x = 1
console.log(x)

var y = 2
console.log(y)

var z = 3
console.log(z)

行斷點的限制也很明確：你必須先知道「哪一行才值得停」。如果整份檔案被壓縮成幾萬行、好幾段程式擠在同一行，那麼在那一行下斷點會顯得太粗，你得改用條件式斷點（只在此條件成立時才停），或改用下面兩類從事件或請求出發的斷點。

事件監聽斷點：在頁面程式跑之前先停住

有些時候，你要處理的值在頁面一載入的瞬間就被算好了。等你手動打開 Sources、找到地方、設好斷點，一切早就結束了。這種情況下，行斷點幫不上忙，你需要的是「在事件發生時就停住」的斷點。

事件監聽斷點掛在「某個事件」上。例如示範頁面把一段程式綁在標題的點擊事件上，只要有人點標題就會執行：

<h3 onclick="test01()">断点的使用和请求堆栈</h3>

如果你想在「點擊發生、但還來不及執行裡面的程式」時就停住，可以在 Sources 面板的 Event Listener Breakpoints 裡勾選對應的事件。這樣一來，事件一被觸發，程式會先停在事件處理的入口，你再一步一步往下走。

這一類斷點還有一個關鍵用途：站在「頁面自己的程式開始執行之前」。當你想要攔截、改寫某個原生 API（例如 atob）時，必須在頁面程式還沒用到它之前就先動手；而這個時機點只有靠事件監聽斷點才抓得住。切記，一旦你重新整理頁面，剛剛設好、還沒生效的改動就會全部重來，所以這類操作通常是「設斷點、暫停、動手、然後不再重整」。

XHR／Fetch 斷點：當你知道是哪個請求送出的

如果那個值是由某個非同步請求送出去的，最省事的做法是直接在「請求送出」這件事上設斷點。DevTools 可以設定在每次發出 XHR／Fetch 時暫停，甚至在網址符合某個片段時才暫停。當程式停在送出請求的那一刻，你就可以往上讀呼叫堆疊，看看這個請求的參數是被誰組出來的（這正是下一節要練的動作）。

這一類斷點特別適合搭配 Step 2 的請求堆疊追蹤：你知道值在請求資料裡，卻不確定是哪段程式組的，那就讓「送出請求」這個動作自己把程式停下來，你就不必先猜是哪一行。

判別問句：該下哪一種？

  1. 你已經知道（或大概知道）處理這個值的那一行在哪嗎？知道，就下行斷點，最快。
  2. 這個值是在頁面載入的瞬間就被算好的嗎？是，就用事件監聽斷點，搶在頁面程式執行前停住。
  3. 這個值是某個 XHR／Fetch 請求送出的嗎？是，就在那個請求上設 XHR 斷點，從發送點往回追。

如果三個問題都沒有明確答案，通常表示你還沒定位到候選程式，該回去把 Step 2 的搜尋再收窄一點，而不是隨便下一根斷點碰運氣。

反例：這些時候選項會翻轉

行斷點最適合「你知道那一行」的情境，但當檔案被壓縮成超長的一行、或程式被混淆到處都是 && 串接時，它會變得很不精準，此時改用 XHR 斷點或條件式斷點更實際。

事件監聽斷點雖然能在事件發生時停住，但它的代價是「時機很難重現」：如果你設好之後重新整理了頁面，很多還沒生效的狀態就會消失。所以在做需要在「頁面程式之前」插旗的操作時，動作要一次到位，不要中途重整。

XHR 斷點也不是萬靈丹。它只對「由 XHR／Fetch 送出的請求」有效；如果值是由頁面載入時的 <script> 帶出、或是使用者操作 DOM 後即時寫入某個欄位，那它就不會觸發，你得改用事件監聽或行斷點。

小結

斷點要對應你的線索：知道「哪一行」就用行斷點；值在頁面載入瞬間就產生、需要搶在頁面程式前停住，就用事件監聽斷點；值由某個請求送出，就用 XHR／Fetch 斷點。混淆的長行會讓行斷點失準，重新整理會讓事件監聽的前置動作失效，非 XHR 送出的值則不吃 XHR 斷點。選錯種類，等於在錯的時間點按了暫停鍵。

斷點讓你停下來了，可是停下來只是開始。真正要緊的是：程式暫停的這一刻，你要怎麼從它身上問出「這個值是誰算出來的」？答案在右邊那個你一暫停就會亮起來的面板：Call Stack。下一節要把讀呼叫堆疊這個核心動作，一步步練起來。
