整套跑一遍：有道翻譯 sign 與 mysticTime 的定位

Step 5/5 · DevTools：斷點、請求堆疊與呼叫堆疊

學習目標

對一個真實請求，標出哪些欄位是動態而必須重現的，並說明如何用請求堆疊／關鍵字搜尋把它們定位到產生它們的 JS。

前言：把前四步接回一個真的請求

你已經練過單一動作：知道值可能在哪（Step 1）、會選入口定位的方法（Step 2）、會依情境下對斷點（Step 3）、也會讀呼叫堆疊追回函式（Step 4）。但真實工作不會把這些拆開來考你，而是丟給你一個完整的請求，要你在腦中把整套流程跑一遍、規劃出「我接下來要怎麼追」。

這一節就拿有道翻譯的一個實際請求當素材。它不是一個要你當場打開 DevTools 操作的練習，而是一道「紙上兵推」：看著這份被保存下來的請求，標出哪些欄位需要重現，再說明你會用哪條路去找出它們的產地。做完之後，你面對工作上任何一個被保護的請求，都能先用同樣的方式規劃，再動手。

前置條件：你已看完 Step 1 到 Step 4，知道請求資料／請求頭／Cookie 三個位置，也知道請求堆疊追蹤與關鍵字搜尋兩條路，以及行、事件監聽、XHR 三種斷點的差別。

第一步：看清這個請求長什麼樣

下面是重放這個請求的核心部分。它是一個 POST，送到 https://dict.youdao.com/webtranslate，內容型別是 application/x-www-form-urlencoded，也就是欄位用「&」串接的形式放在請求資料裡（而不是 JSON）。

wd = "apple"

data = {
    'i': wd,
    'from': 'auto',
    'to': '',
    'domain': '0',
    'dictResult': 'true',
    'keyid': 'webfanyi',
    'sign': '1be3315fc3cd8097a033646862b6e5db',
    'client': 'fanyideskweb',
    'product': 'webfanyi',
    'appVersion': '1.0.0',
    'vendor': 'web',
    'pointParam': 'client,mysticTime,product',
    'mysticTime': '1704288976618',
    'keyfrom': 'fanyi.web',
    'mid': '1',
    'screen': '1',
    'model': '1',
    'network': 'wifi',
    'abtest': '0',
    'yduuid': 'abcdefg',
}

response = requests.post('https://dict.youdao.com/webtranslate', cookies=cookies, headers=headers, data=data)

這段程式是「攻擊方已經把答案寫好」的版本，它直接帶著一個現成的 sign 去請求。但這正是逆向要面對的問題：那個 sign 是怎麼生出來的？如果你只是把這一串固定的 sign 抄下來重複用，只要換一個查詢的字、換一個時間，伺服器就會拒絕你。所以我們要先把「哪些欄位會變」找出來。

第二步：標出固定的與動態的欄位

把上面那串欄位逐一分類。分完，你的目標就清楚了。

欄位範例值性質
iapple要查的字，由使用者決定，會變但不需還原
sign1be3315fc3cd8097a033646862b6e5db32 位十六進位，需重現的目標
mysticTime1704288976618毫秒時間戳記，每次不同，需重現的目標
clientfanyideskweb固定字串
productwebfanyi固定字串
keyidwebfanyi固定字串
pointParamclient,mysticTime,product一個很好的線索，見下段

先看 sign。它的長度是 32 個十六進位字元，這正是 MD5 這類摘要演算法的典型輸出格式。看到這種長度與字元集，第一懷疑就是「某幾個欄位被串起來後取了摘要」。再看 mysticTime，是一個十三位數字，符合毫秒級時間戳記的特徵，會隨時間改變，難怪換了時間就過不了。

最有意思的是 pointParam，它的值是 client,mysticTime,product。這個欄位幾乎是在明示：這次簽名與 client、mysticTime、product 這三個欄位有關。它等於是把自己的配方洩漏了一半。這也是真實網站常見的疏忽。所以你的目標可以更精確地寫成：「找出把 client、mysticTime、product（可能還加上一個固定 key）串起來、再取摘要的那段程式。」

第三步：規劃入口定位：該走哪條路？

現在把 Step 2 的判別問句拿出來套。

第一問：我看得到這個值被送出的請求嗎？看得到，就是這個 webtranslate 的 POST，而且它是由頁面的 JavaScript 用非同步請求送出的。所以請求堆疊追蹤可行：在 Network 找到這個請求，順著它的發送來源跳到發出請求的那段 JS，再往上追參數是怎麼被組出來。

第二問：我知不知道任何相關的字？知道好幾個。參數名有 sign、mysticTime、pointParam；API 路徑片段是 webtranslate；演算法特徵是 md5。任何一個都值得直接在 Sources 全站搜尋。尤其是 pointParam 這個不常見的欄位名，往往一搜就命中。

第三問：我知不知道大概用了哪種演算法？從 32 位十六進位猜是 MD5，所以直接搜 md5 也很合理。

三問都有答案，實務上會兩條並用：先搜關鍵字（sign、pointParam、md5）快速把範圍縮到那幾段程式；如果搜不到（例如被打包工具改過名），再回到請求堆疊，沿著 webtranslate 這個請求的發送鏈硬把組裝點挖出來。

第四步：下斷點、讀堆疊

定位到候選程式之後，接著把 Step 3、Step 4 接上。因為這個值是 XHR 送出的，最省事的做法是在送出 /webtranslate 的那個請求上設 XHR 斷點；一送出請求，程式就會停在發送的那一刻。停下來之後，讀右邊的 Call Stack：往上一層層看，哪一層把 client、mysticTime、product 組進同一個字串，那一層就是簽名的入口。如果你偏好先掌握位置，也可以在搜到的那行 sign = ... 上設行斷點，直接停在賦值的那一刻。

整個動作的節奏和 Step 4 的練習靶場一模一樣：從「值被送出去」的地方暫停，沿呼叫鏈往上游走，觀察值到哪一層才變成那串 32 位十六進位。那裡的函式，就是你要還原的目標。

第五步：怎麼確認你追對了

逆向不是找到一段「看起來像」的程式就算數，你得能驗證。驗證的方式是：假設你已經用 Python 重現了簽名邏輯，那就準備兩組不同的輸入（換一個 i、換一個 mysticTime），一組在瀏覽器裡讓它現算，一組用你的 Python 算，兩串 sign 若完全一致，才算真正追對。

這一步之所以重要，是因為前面那份重放腳本剛好示範了錯誤的做法，它把一個固定的 sign 寫死。只要你不重現產生 sign 的邏輯，換個查詢字或換個時間就失效。能自己生出合法的 sign，才是這個節點真正要達成的能力。

做完長什麼樣：可驗證的結果

跑完這五步的規劃，你手上應該有一份清楚的清單：這個請求的動態欄位是 sign 與 mysticTime；sign 是 32 位十六進位、疑似某幾個欄位串接後的 MD5；定位走「先關鍵字搜 sign／pointParam／md5，必要時再請求堆疊追 webtranslate」；斷點用 XHR 或行斷點；確認方式是用 Python 重算並比對。你能說出這整份計畫，就代表這個節點的目標達成了。剩下的工作，是把真正的簽名公式還原出來，那會留給後面的案例節點。

小結

面對一個真實的被保護請求，先做紙上兵推：把欄位分成固定的與動態的，動態的才是目標。有道翻譯的 sign 是 32 位十六進位、疑似 MD5，mysticTime 是毫秒時間戳記；pointParam 這個欄位幾乎把「client、mysticTime、product 參與簽名」的線索直接送上門。定位時先關鍵字搜 sign、pointParam、md5 縮小範圍，必要時再用請求堆疊沿 webtranslate 追發送鏈；斷點選 XHR 或行斷點；最後一定要用 Python 重算並比對，確認自己真的追對。這套「先規劃、再動手、最後驗證」的節奏，就是你之後面對工作上任何目標網站的第一步。
