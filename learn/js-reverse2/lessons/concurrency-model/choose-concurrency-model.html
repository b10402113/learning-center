選對工具：Process、Thread、Pool 還是協程？

Step 5/5 · 行程、執行緒與協程：併發為何存在

學習目標

面對一批 IO 密集的爬取任務，依「隔離需求、切換可控性、建立開銷」判斷該用行程、執行緒、執行緒池還是協程。

前言：工具都在手上了，問題變成「這一題該用哪個」

前面四步，你依序認識了行程、執行緒、執行緒池，也埋下了協程的伏筆。現在桌上擺著四種工具，每一種都能讓程式「同時處理多件事」。真正的問題不再是「怎麼寫」，而是「什麼時候該用哪一種」。

這正是實際工作中的痛點。抄了一段別人用多執行緒的爬蟲，套到自己的站卻沒有變快，甚至更慢；或者相反，明明只是抓幾百張圖片，卻開了幾百個行程把機器拖垮。這一節不教你新的 API，而是把取捨講清楚，讓你在下手前就知道該挑哪一把。

兩股張力：隔離與共享、可控與不可控

四種工具的差別，可以濃縮成兩股張力。第一股是隔離與共享：行程之間記憶體互相隔離，安全但不好互通；執行緒與協程在同一塊記憶體裡工作，方便但容易互相干擾。第二股是切換由誰決定：行程與執行緒的切換節奏由作業系統掌控，你無法干涉；協程則是由你自己的程式在阻塞點主動讓出，掌握權回到你手上。

了解這兩股張力，選工具就不再是憑感覺。下面先把四個選項並排看清楚。

選項比較

工具建立開銷記憶體切換由誰決定適合的場景
行程 Process較大彼此隔離作業系統需要隔離，或任務本身偏計算
執行緒 Thread較小同行程共享作業系統任務偏等待，且需要共享狀態
執行緒池 Pool一次建好、重複利用同行程共享作業系統一大批相似的 IO 任務
協程最小，不另開行程或執行緒單一行程／執行緒內共享我們自己的程式IO 密集，想把 CPU 留在自己的任務裡

先講最直覺的判斷。如果任務是實打實的計算，那要靠多核才能真正加快，得往行程的方向走；但爬蟲幾乎都屬於 IO 密集（大部分時間在等網路，不是在算），所以我們在意的通常不是「多核」，而是「等待時能不能去做別的」。這也是為什麼執行緒、執行緒池、協程在爬蟲裡比行程更常見。

判別問句：四個問題決定用哪個

不確定時，對著手上的任務問自己這四題：

  1. 這批任務是「等待」為主，還是「計算」為主？ 等待為主就往執行緒／協程想，計算為主才考慮行程。
  2. 任務之間需要共享記憶體嗎？ 需要共享，執行緒很方便；要的正好是彼此隔離，行程更合適。
  3. 是少量任務，還是一大批結構相似的任務？ 一大批相似的 IO 任務，交給執行緒池 Pool(5).map 最省事。
  4. 你在意「切換節奏無法由自己掌控」這件事嗎？ 在意，而且想盡量把 CPU 留在自己的任務上，那就往協程走。

反例：這些情況下，上面的規則會翻轉

反例一：CPU 密集的任務用協程幾乎沒用。 協程的加速來自「主動在阻塞點讓出」，它需要阻塞點存在才有東西可以讓。如果整段任務都在扎扎實實地計算、沒有等待環節，協程就沒有地方可以切換，單一行程／執行緒的限制依然卡在那裡。

反例二：執行緒共享記憶體，不等於安全。 共享很方便，但如果多個執行緒同時改同一份資料，就可能互相干擾。需要共享狀態時，不能只想著「反正看得到」，還要多想一步「同時改會不會出事」。

反例三：行程隔離是保護，也是不便。 行程之間記憶體獨立，子行程改了變數主行程看不到，這在大多時候是保護；但當你真的需要它們互通，就得動用管線、信號量這類行程通訊機制，成本比執行緒直接共享高。

反例四：執行緒和行程的切換，不保證輪到你。 這是協程真正要解的痛點。在傳統多執行緒／多行程模型裡，我們為每個網址開一個執行緒或行程，目的是在它阻塞時，讓 CPU 去處理別的網址。但你的電腦上不會只有這幾個下載任務，還有 Pycharm、音樂播放器、微信、雲端硬碟等一堆行程與執行緒。問題是：CPU 每次切換，一定會切回你的下載任務嗎？ 不一定，因為這個切換由作業系統決定，人沒辦法干涉，於是下載任務實際被分到的時間就少了，效率跟著被拉低。

協程為什麼存在：想辦法把 CPU 留在自己的程式裡

協程的解法很直接：既然切成很多個行程／執行緒會讓作業系統把注意力分散掉，那就把所有下載任務全部塞進同一個行程／執行緒裡，基於單行程／單執行緒來完成這批下載。

在這個單行程／單執行緒裡，我們自己主動監測出所有的阻塞環節，讓 CPU 在這些阻塞環節切換執行。這樣做會發生什麼事？這個下載任務的行程／執行緒處在「就緒」狀態的時間變多了，作業系統便以為它是一個阻塞比較少的行程／執行緒，於是盡可能多分配 CPU 給它。結果就是：在單行程或單執行緒的模式下，程式的執行效率被大幅拉高。

把這句話換成最白話的版本：協程的一切設計，就是想盡辦法把 CPU 留在我們自己的程式裡。這裡先建立動機就好，協程的具體寫法（async、await、事件迴圈）留到下一個節點專門處理。

決策檢查表

拿到一批任務，先問兩件事：
① 是「等待」為主還是「計算」為主？等待為主 → 執行緒／協程；計算為主 → 行程。
② 中途需要共享記憶體嗎？需要 → 執行緒；要隔離 → 行程；一大批相似 IO 任務 → 執行緒池 Pool(5).map。
最後補一問：看不慣「切換節奏被作業系統決定」嗎？如果是，而且想在單執行緒內把效率榨出來 → 協程。

小結

四種工具的分野，看「隔離與共享」和「切換由誰決定」兩股張力。行程隔離、開銷大，適合計算或需要隔離；執行緒共享、開銷小，適合等待且需要共享狀態；執行緒池適合一大批相似的 IO 任務，靠重複利用省下建立開銷；協程不另開行程或執行緒，由程式自己在阻塞點讓出，把 CPU 盡量留在自己的任務裡。協程只在有阻塞點時才有效，任務若全在計算則幫不上忙。
