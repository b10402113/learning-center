把瀏覽器 JS 搬到 Node 執行

Step 4/5 · Node 執行、execjs 與 JS 前置知識

學習目標

說明瀏覽器 JS 在 Node 執行會壞在哪（window 對 global、Node 專屬符號外洩），並用假物件與 toString 標籤把環境補起來的起手式。

前言：同一段程式碼，換個地方跑就爆了

前面幾節我們把語言層面的工具備齊了：原型鏈幫你判斷成員掛在哪，描述符讓你讀懂並改寫屬性的讀寫行為。現在回到第一節留下的那條線：execjs 會把 JS 丟到 Node 執行，可是當你真的把網站上那段加密程式搬過去，十之八九會直接報錯。

它報錯不是因為你抄錯，而是因為那段程式碼預設自己活在瀏覽器裡。它會去摸 window、去呼叫 document、去讀 navigator，而這些東西在 Node 裡根本不存在。這一節要講清楚這個落差從哪來，以及面對它時最標準的第一招：用手刻的假物件把瀏覽器環境「補」出來。

落差一：頂層物件不一樣

在瀏覽器裡，所有在全域寫下的變數、函式，最後都掛在 window 這個頂層物件上；window 就是瀏覽器的全域物件。到了 Node，這個頂層物件換成了 global，而 Node 裡並沒有 window。

所以一段在瀏覽器裡理所當然的程式，搬到 Node 後只要寫到 window.xxx，就會立刻因為「window is not defined」而停擺。最常見的修補方式，是先宣告 window 這個名字，讓它指向 Node 的全域物件，這樣原本寫給瀏覽器的全域變數，就會落在同一個地方。

落差二：Node 專屬的符號會外洩

反過來，Node 也有瀏覽器沒有的東西，例如 global、process、Buffer、__dirname、__filename。這些符號在瀏覽器環境下應該是不存在的。網站的偵測程式碼很常拿它們來反問一句：「如果 process 存在，那你就不是在瀏覽器，而是在自動化工具裡。」

要躲過這種檢測，最直白的一招就是把它們刪掉。這正是最小的 Node 環境清理範例在做的事：

delete global

delete process

刪掉之後，腳本再怎麼探測 global 或 process，都會得到「不存在」的結果，於是它願意相信自己在瀏覽器裡。要注意的是，這只是把最顯眼的兩個符號藏起來，真實網站可能還會檢查更多東西，這就是完整的補環境要處理的事了。

落差三：裸賦值會長成全域變數

還有一個容易誤會的地方。在 JS 裡，如果你不寫 let、const 或 var，直接寫 x = 100，這個 x 會變成全域變數，掛在當下的頂層物件上。在瀏覽器裡它掛到 window，在 Node 裡它掛到 global。

也就是說：一旦你把 window 接到 global，那些裸賦值行為就會跟瀏覽器一致，因為兩邊其實是同一個頂層物件。這也是為什麼「先補一個 window」幾乎是每個補環境流程的開場白。

起手式：手刻一個 window 假物件

把 window 接到 global 是省事的做法，但有時候你想更精準地控制它，只給出腳本真正需要的那幾個成員。這時就手刻一個物件來冒充瀏覽器的 window。最小的版本可能長這樣：

window = {
    addEventListener() {
    },
    toString: function () {
        return '[object Window]'
    }
}

這裡放了兩樣東西。一個是空的 addEventListener，因為瀏覽器程式很愛用它註冊事件，先給一個什麼都不做的版本，避免它呼叫時報錯。另一個是 toString，這個才是關鍵，下面會單獨講。

另外，瀏覽器裡 window 還有一堆別名：self、top 其實都指向同一個 window。程式碼可能用其中任何一個名字去摸它，所以補的時候要讓它們全部指向同一個物件：

// window = self = top = {}
self = top = window

少了這一行，腳本喊 self.xxx 時就會找不到東西。這類「別名要一起接上」的細節，是補環境裡最容易被忽略、卻最常導致失敗的地方。

toString 標籤：最常見的檢測點

為什麼前面那個假 window 要特地覆寫 toString？因為網站偵測環境時，很常用上一節學過的類別標籤來判斷真假。真正的瀏覽器 window，呼叫 window.toString() 會得到 '[object Window]'；你手刻的物件如果回傳別的東西，立刻就會露餡。

if (window.toString() === '[object Window]') {
    // 正常走
    console.log("正常走")
} else {
    // 返回一个假值
    console.log(window.toString())
    console.log("返回一个假值")
}

這段檢測的邏輯很單純：標籤對了就照正常流程走，標籤不對就刻意回傳一個假值，讓你後續拿到的資料全部是錯的。所以補環境時，把每個物件的 toString 標籤調到跟真瀏覽器一致，是必做的基本功。

小結

瀏覽器 JS 搬進 Node 會壞，是因為頂層物件不同（window 對 global）、Node 專屬符號（global、process 等）會外洩。修補的第一步是把 window 接上或手刻一個假物件，讓 self、top 一起指向它，並覆寫 toString 讓類別標籤回傳 '[object Window]'，最後刪掉 Node 專屬符號來通過檢測。

這一節示範的是「最小可用的假物件」。真實網站要補的東西更多，後面有一個專門的節點會把八個前端物件與 Proxy 監測完整走一遍。現在你手上有 execjs 這座橋、有讀屬性的語言工具、也知道環境落差在哪，下一步就把這些全部湊起來，跟著微信公眾平台的密碼加密案例跑一次完整流程。
