注入三件套、執行 JS、收割 cookie2

Step 3/5 · 案例：動態 cookie 與風控

學習目標

把三件套字串替換進補好環境的 JS 模板佔位符，用 execjs 呼叫 get_cookies，並解析出要帶走的 cookie 鍵值。

前言：原料有了，答案在 JS 裡算

上一節把三件套挖到了手：meta content、ts 腳本、auto 腳本，三個一次性原料。但它們本身不是 cookie，只是題目。這一節做五段迴圈的第二、三、四段——把題目注入 JS、在 Node 裡跑出答案、把答案收割起來——做完，session 裡就會多出一組 cookie2，離資料只剩最後一發請求。

先講目標與前置條件。做完這一步，你會有一個 gen_cookie2() 函式：丟三件套進去，它把 cookie2 寫進 session.cookies，之後用這個 session 發的請求都會自動帶上它。動手前需要四樣東西：上一節的三個原料、Python 的 JS 執行橋 execjs（pip install PyExecJS，背後要掛一個 Node 環境）、一支補好環境的 JS 模板，以及知道這支模板的入口函式叫什麼。模板裡的補環境功夫——window、document、navigator 這些假物件怎麼補——是前面節點的內容，這裡直接拿成品來用。

先看模板的長相：三個佔位符與一個入口

模板（歐冶案例裡叫 ouyeel.js）不是網站原始碼，是你整理出來的工作底稿，長相大致是這樣：

// 補好的環境：window / document / location / navigator 等假物件
// ...
var meta_content = meta_content        // 佔位符一：meta content 的值
var t = 'ts_js'                        // 佔位符二：ts 腳本原文（以字串字面值出現）
var a = 'auto_script_js'               // 佔位符三：auto 腳本原文（以字串字面值出現）

function get_cookies() {
    // 依序執行注入進來的腳本，結果寫進 document.cookie
    return document.cookie
}

三個佔位符的長相不一樣，這一點很重要：meta_content 是裸的識別字，而 'ts_js'、'auto_script_js' 連同前後的單引號一起是佔位符的一部分。這種差異不是隨意的——注入用的是純字串替換，replace() 的第一個引數必須跟模板裡的樣子一字不差才能對得上。

另一個主角是入口函式 get_cookies()。它是整份模板對外的唯一窗口：呼叫它，它就把注入進來的腳本跑完，然後回傳 document.cookie。「定位 VM/TS 腳本的入口」聽起來很神祕，在這裡其實就是一句話——Python 端 call() 呼叫的那個函式名，就是入口；入口內部的呼叫序列，就是網站腳本的啟動順序。

步驟一：讀模板，把三件套替換進去

def gen_cookie2(meta_content, ts_js, auto_script_js):
    with open("ouyeel.js", encoding='utf-8') as fp:
        js_code = fp.read()
    js_code = js_code.replace("meta_content", meta_content).replace("'ts_js'", ts_js).replace("'auto_script_js'",
                                                                                              auto_script_js)

把整份模板讀成字串，然後連續三次 replace。注意第一個參數的寫法差異：替換 meta content 時寫 "meta_content"，替換另兩支腳本時寫 "'ts_js'"——連引號一起換，正是配合模板裡佔位符的長相。替換之後，ts 腳本與 auto 腳本的原文就以程式碼的身分（不是字串）被拼進 JS 裡，接下來整份檔案會被當成一支完整的程式執行。

一個要留意的細節：replace 會換掉字串裡「所有」出現處。佔位符名字取得太普通（例如就叫 t），可能誤傷模板其他角落；所以模板裡的佔位符名字要夠獨特，替換才是安全的。

步驟二：編譯執行，呼叫入口取答案

    js_compile = execjs.compile(js_code)
    js_cookie = js_compile.call("get_cookies")

execjs 是 Python 驅動 JS 執行環境的橋，compile() 把整份注入後的腳本載進 JS 執行環境（通常是 Node）；call("get_cookies") 指名呼叫入口函式。腳本一跑，補好的假物件騙過環境檢測，ts 腳本解開 meta content，auto 腳本接著把結果寫進 document.cookie——這就是 cookie2 的誕生過程。

預期看到什麼：js_cookie 是一串 cookie 字串，形如 鍵=值; path=/; ...。每次執行值都不同，因為題目（三件套）每次不同。如果 call 抱怨找不到函式、或執行期噴出「某某物件未定義」，問題通常在模板的補環境有缺口——回前面節點的 Proxy 監測法補洞。

步驟三：解析 cookie，寫進 session

    cookie_key_value = js_cookie.split(";")[0].split("=")
    session.cookies.update({cookie_key_value[0]: cookie_key_value[1]})

cookie 字串的格式是分號分隔的多段鍵值，但真正要帶走的只有第一段：先 split(";")[0] 把 path=/ 之類的尾巴切掉，再 split("=") 把鍵和值分開。最後 session.cookies.update() 把這對鍵值寫進 session——之後這個 session 發出的任何請求，requests 都會自動把它掛上。

一個工程上的小提醒：split("=") 會把整段切成好幾塊，如果 cookie 值本身含有 = 號（base64 結尾就常常有），[1] 只拿得到值的前半截。要更穩，改成 split("=", 1) 只切一刀，或用 partition("=")。這不影響理解流程，但會影響你的成功率。

做完長什麼樣

可驗證的結果長這樣：gen_cookie2(...) 跑完後，session.cookies.get_dict() 裡多出一組新的鍵值；同一組三件套再跑一次會得到同一組值，換一組三件套就換一組值。到這裡，五段迴圈已經完成四段——題目抓了、注入了、答案算出來也收好了。答案怎麼兌換成真正的資料，就是下一節的重放。

小結

注入是純字串替換：佔位符在模板裡長什麼樣，replace 的第一個引數就要長什麼樣（meta_content 裸名、'ts_js' 連引號）。替換後整份腳本交給 execjs 編譯，呼叫入口 get_cookies——Python call 的函式名就是 VM/TS 腳本的入口——拿到 document.cookie 字串後取第一對鍵值寫進 session。

cookie2 已經掛在 session 上了，下一節帶著它與查詢資料打第二發請求，把資料抓回來，順便處理分頁與「每頁重置」的節奏。
