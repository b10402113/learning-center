抓三件套：從第一發回應挖出 meta、ts 腳本與 auto 腳本

Step 2/5 · 案例：動態 cookie 與風控

學習目標

用 XPath 從第一發回應抓出 meta content、ts 腳本內文與 auto 腳本三件套，並理解三者每次請求都會變、不能寫死。

前言：考卷拿到了，先把題目抄下來

上一節把全貌立了起來：第一發請求只拿得到考卷——cookie1 加上三件套，資料鎖在帶 cookie2 的第二次請求後面。從這一節開始動手，把五段迴圈的第一段做實：從考卷裡把三件套穩穩地挖出來。

先講清楚目標與前置條件。做完這一步，你會得到一個函式，打一次第一發請求、回傳三個值：一段 meta content 文字、一支 ts 腳本原始碼、一支 auto 腳本原始碼。這三個值就是下一節要注入 JS 模板的原料。動手前需要 Python 的 requests 與 lxml（pip install requests lxml），以及會寫基礎 XPath——這個節點假設你已經會用 XPath 定位 HTML 節點與屬性。

步驟一：打第一發請求，拿回考卷 HTML

第一發請求本身沒有任何玄機，一個不帶查詢資料的 POST 就夠了。用 requests.Session() 而不是裸的 requests.post，是因為 session 會自動幫你記住伺服器種下的 cookie1，之後兩次請求才接得起來：

session = requests.Session()

headers = {
    "Accept": "*/*",
    "Content-Type": "application/x-www-form-urlencoded; charset=UTF-8",
    "Origin": "https://www.ouyeel.com",
    "Referer": "https://www.ouyeel.com/search-ng/queryResource/index",
    "User-Agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/127.0.0.0 Safari/537.36",
}

list_url = "https://www.ouyeel.com/search-ng/commoditySearch/queryCommodityResult"

請求標頭照瀏覽器抄：這個站的查詢介面是表單型的，所以 Content-Type 帶 application/x-www-form-urlencoded，再加上 Origin 與 Referer 表明你從查詢頁過來。發出去之後，response.text 就是考卷 HTML——不是商品資料，這一點跟上一節講的一致。

步驟二：挖 meta content——第一樣動態輸入

把 HTML 交給 lxml 解析，然後用 XPath 把三樣東西一樣一樣挖出來。第一樣是 meta content：

def fetch_1():
    response = session.post(list_url, headers=headers)
    tree = etree.HTML(response.text)
    meta_content = tree.xpath('//meta[2]/@content')[0]

逐段拆這條 XPath。//meta 找文件裡所有 <meta> 標籤；[2] 取其中第二個——注意 XPath 的位置索引從 1 開始，跟 Python 的 0-based 不一樣；/@content 不要節點本身，只要它的 content 屬性值。最後的 [0] 是 Python 的事：xpath() 回傳清單，取第一個結果。

預期看到什麼：一串動態產生的文字，每次請求都不同。它不是給人看的，是接下來要餵給腳本的參數——先拿到手就好，它怎麼被用掉是下一節的事。

步驟三：挖 ts 腳本——第二樣動態輸入

第二樣是頁面裡第一段 <script> 的內文：

    ts_js = tree.xpath('//script[1]/text()')[0]

//script[1] 取第一個 script 標籤，/text() 取它的文字內容（不是標籤、不是屬性，是包在開闔標籤中間的原始碼）。預期看到什麼：一支被壓縮成單行的 JavaScript，通常長達數千位元組、完全讀不懂。它是這個站的解密腳本，代號 ts，內部是個小型虛擬機，所以逆向圈子常直接叫它 VM 腳本。讀不懂是正常的——我們的任務是忠實地把它搬到下一節去執行，不是現在就還原它。

步驟四：挖 auto 腳本——第三樣動態輸入，要多跑一趟

第三樣藏得比較遠。它不是內嵌在 HTML 裡，而是一個外部腳本，所以只能先拿到它的路徑，再自己去下載：

    auto_script_url = 'https://www.ouyeel.com' + tree.xpath('//script[@src]/@src')[0]
    auto_script_js = session.get(auto_script_url).text

    return meta_content, ts_js, auto_script_js

逐行看：//script[@src] 找「帶 src 屬性的 script 標籤」，/@src 取那個路徑。路徑是站內相對路徑，前面要自己補上網域，拼出完整 URL；接著再發一次 GET 把腳本原文抓回來。注意這一趟也要走同一個 session，讓 cookie1 繼續掛著。

函式最後回傳三元組：meta_content, ts_js, auto_script_js。到這裡，五段迴圈的第一段完成——原料齊了。

警告：三件套是消耗品，而且 XPath 很脆

兩個陷阱先講在前面。第一，三個值都不能寫死。它們是伺服器每次請求現發的題目，貼上一次的值重用，下一節算出來的 cookie2 就是舊答案，第二發請求會被擋。正確的用法是每次要重放資料前，都先重跑一次 fetch_1()。

第二，meta[2]、script[1] 這種位置式 XPath 是結構依賴的。網站前端改版、多插一個 meta 標籤，你的索引就整個錯位，抓到別的東西甚至直接噴 IndexError。跑不起來時，先把 response.text 存成檔案用眼睛看一遍，確認三樣東西現在排在哪裡，再回來改 XPath——這比反覆試值快得多。

做完長什麼樣

可驗證的結果長這樣：fetch_1() 回傳三個非空字串；meta_content 是一串短文字，ts_js 看起來像壓縮成一行的 JavaScript，auto_script_js 是一份讀得懂或讀不懂的腳本原文。三個值每次執行都不同——看到「跟上次不一樣」別慌，那正是它們是一次性題目的證據。至於這三樣東西進了 JS 之後怎麼被消化、cookie2 怎麼長出來，那是下一節的任務。

小結

三件套藏在第一發回應的三個位置：第二個 meta 的 content 屬性、第一段 script 的內文（ts 腳本）、帶 src 的外部 script（要補網域再下載原文）。抓它們用三條 XPath 就夠，但它們每次請求都變、不能寫死，而且位置式 XPath 隨時可能被改版弄斷。

原料到手了，下一節把它們注入 JS 模板、在 Node 裡跑出 cookie2，順便收割那枚通關章。
