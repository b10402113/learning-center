anti_content 的入口：模組熱載入、對時與 dt()

Step 5/5 · 案例：動態 cookie 與風控

學習目標

認出 env＋mod1＋mod2＋loader 的四檔組合，照 get_anti_content 的三步呼叫序列定位入口、產出 anti_content 並帶進請求。

前言：另一種形態——不是每發重抓，而是算一次、限時有效

前四節跑完了歐冶的五段迴圈，那條迴圈的節奏是「每發請求都重抓三件套、重算一組 cookie」。但風控參數還有另一種形態：拼多多的 anti_content 就是例子——它不是每次從回應裡抓來的，而是本地一組靜態的腳本檔案算出來的，靠一個「對時」動作保鮮。問對問題，才知道走哪條路：「這個參數每次都從回應現抓嗎？」是，走前四節的迴圈；「是一組固定腳本算的、而且帶時間戳嗎？」是，走這一節的路。

先講目標與前置條件。做完這一步，你會有一個 get_anti_content() 函式：每呼叫一次就吐出一串新鮮的 anti_content，塞進請求參數就能通過風控。動手前需要 Node 環境與 Python 的 execjs，以及 webpack 模組定位的基本功——知道 window.loader、模組 id 這些東西是什麼（前面 webpack 案例節點的內容）。

步驟一：認出四檔組合——這組合會一再出現

這個案例的 JS 側是四支檔案，入口檔的開頭就是四行 require：

require("./01 env")
require("./02 mod1")
require("./03 mod2")
require("./04 loader")

四支檔案各司其職，這種「四檔組合」在真實站台的 bundle 逆向裡一再出現，值得認得：

  • 01 env.js — 補環境：把 window、document、navigator 這些瀏覽器物件補齊，順手種下風控會檢查的種子——document.cookie 裡放一組 _nano_fp、navigator.webdriver 設成 false（打掉自動化偵測）、screen 的寬高補上。缺了這些，腳本跑不出值，或者跑出來的值一送就被識破。
  • 02 mod1.js、03 mod2.js — webpack 模組包：兩大包模組（合計三萬多行，只需知道它們是模組倉庫，不必逐行讀），以 window.webpackJsonp.push 的形式把模組註冊進 runtime。
  • 04 loader.js — webpack runtime：管理模組的載入與執行，並把 window.loader 這個函式掛到全域，讓你可以用模組 id 把任意模組「點名上場」。

四檔依序 require 的順序不能亂：先有環境、再有模組、最後才是 runtime——runtime 起來才有人管理模組。

步驟二：入口的三步呼叫序列——熱載入、對時、產值

入口函式 get_anti_content() 只有三步，每一步都不能少：

function get_anti_content() {
    // 初始化
    window.loader("fbeZ")
    // 更新操作
    window.lt['updateServerTime'](new Date().getTime())
    // 调用dt
    return window.dt()
}

逐行拆：

  1. window.loader("fbeZ") — 熱載入模組。"fbeZ" 是模組 id，這一呼叫把負責產值的模組初始化、拉進執行狀態。少了它，後面兩步要嘛找不到物件、要嘛算出垃圾值。
  2. window.lt['updateServerTime'](new Date().getTime()) — 對時。把「當下的毫秒時間戳」餵給簽名模組。anti_content 跟時間綁定：用舊時間戳算出來的值就像過期票券，伺服器一驗就拒。所以每次執行都要重新對時，不能省。
  3. return window.dt() — 產值。dt 是腳本執行後掛上 window 的產值函式，呼叫它拿到 anti_content 字串。

這就是「定位 VM/TS 腳本入口」的實務做法：入口不在原始碼的第幾行，而在驅動端的呼叫序列裡。Python 端 call 的函式名告訴你入口是誰，入口內部的三步告訴你網站腳本的啟動順序；而 window.dt、window.lt 這種「跑完才出現在 window 上的函式」，就是腳本掛上去的產物——追它們，就追到了真正算值的地方。

步驟三：Python 端驅動——call 入口，把值塞進參數

Python 側的驅動短到只剩一行核心：

anti_content = execjs.compile(open("05 pdd.js").read()).call("get_anti_content")
print("anti_content:::", anti_content)

open("05 pdd.js").read() 把入口檔整個讀進來——注意 require 的四個檔案會被 Node 一起載入，所以五支檔案要放在同一個工作目錄；execjs.compile 交給 JS 執行環境；.call("get_anti_content") 呼叫入口、拿到值。

接著把值放進請求參數，就像一般查詢欄位一樣帶上：

params = {
    'tf_id': 'TFRQ0v00000Y_13400',
    'page': '1',
    'size': '100',
    …
    "anti_content": anti_content
}

res = response = requests.get('https://apiv2.pinduoduo.com/api/gindex/tf/query_tf_goods_info', params=params,
                              headers=headers)

（省略的那行是一段被註解掉的寫死 anti_content 值——正好當反面教材，下一段就講它為什麼死。）

注意這跟歐冶形態的差異：anti_content 不是 cookie，是查詢參數，所以它放進 params 而不是 session.cookies。風控值不一定要叫 cookie，「帶上才算數」的本質是一樣的。

警告：最常見的死法——寫死 anti_content

把某一次跑出來的 anti_content 貼進程式裡寫死，是最常見也最沒救的錯誤。它跟時間綁定，有效期一過就是一串廢字；而且你從被註解的舊值根本看不出它什麼時候過期——只會看到昨天還好好的、今天突然全軍覆沒。正確的用法永遠是：每次要發請求前，現呼叫一次 get_anti_content() 拿新值。

第二個坑在環境補齊：navigator.webdriver 沒設成 false、_nano_fp 沒種進 document.cookie、screen 寬高沒補，都可能讓腳本產不出值、或產出的值一送就被識破。報錯訊息如果是「某某物件未定義」，回補環境的章節補洞；如果值產得出來但被擋，往「環境檢測」方向查。

做完長什麼樣

可驗證的結果長這樣：呼叫 get_anti_content() 回傳一長串像亂碼的字串，每次呼叫都不同；把它塞進 params 發 GET 請求，伺服器回正常的 JSON 商品資料。把值換成寫死的舊值再發一次，被擋——這一正一反，就是「對時有生效」的證明。

小結

anti_content 是「靜態 bundle＋對時」形態：env＋mod1＋mod2＋loader 四檔組合（補環境、模組包、runtime），入口 get_anti_content 的三步是熱載入模組（loader("fbeZ")）、對時（updateServerTime 當下毫秒）、產值（window.dt()），值放進查詢參數帶上。入口定位靠驅動端呼叫序列與 window 上跑完才出現的函式；值不能寫死，時間戳過期就失效。
