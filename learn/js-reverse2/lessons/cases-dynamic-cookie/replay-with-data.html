帶資料重放：分頁迴圈與每頁重置

Step 4/5 · 案例：動態 cookie 與風控

學習目標

帶著 cookie 與查詢資料重放第二次請求，跑分頁迴圈取回資料，並在每頁結束清 cookie、整套重跑。

前言：通關章在手，怎麼把資料兌換出來

上一節結束時，cookie2 已經掛在 session 上了——五段迴圈做完四段，就差最後的重放。這一節把它做實：組好查詢資料、打第二發請求、解析回應，然後把整條流程排成分頁迴圈，一口氣撈完你要的頁數。

先講目標與前置條件。做完這一步，你會有一支能跑完整五頁的抓取程式：每一頁都走一遍「抓三件套、算 cookie2、帶資料重放」，把商品一筆一筆印出來。動手前需要 cookie2 已經在 session 裡（上一節的 gen_cookie2()），以及知道查詢 API 的表單欄位長什麼樣——這從 DevTools 的 Network 面板抄，跟著瀏覽器實際送出的表單走。

步驟一：組查詢資料——整串照抄，不要精簡

def fetch_2(page_index):
    data = {
        "criteriaJson": '{"pageIndex":%d,"pageSize":50,"industryComponent":null,"channel":null,"productType":null,'
                        '"sort":null,"warehouseCode":null,"key_search":null,"is_central":null,"searchField":null,'
                        '"companyCode":null,"inquiryCategory":null,"inquirySpec":null,"provider":null,'
                        '"packCodes":null,"shopCode":null,"steelFactory":null,"resourceIds":null,"jsonParam":{},'
                        '"excludeShowSoldOut":null}' % page_index
    }

這個站的查詢介面把整包條件塞在一個叫 criteriaJson 的表單欄位裡，內容是一整段 JSON 字串。pageIndex 控制翻頁、pageSize 控制每頁筆數，其他一堆 null 是查詢表單的預設欄位。

為什麼其餘欄位一個都不刪？因為風控多半會檢查欄位齊不齊。瀏覽器送出的表單長什麼樣，你就照抄什麼樣——刪掉看起來沒用的欄位，請求可能直接被判定為非瀏覽器而擋下。逆向的原則在這裡很務實：能跑比精簡重要。

步驟二：帶著 cookie 打第二發請求

    response = session.post(list_url, headers=headers, data=data)
    logger.info(f"第{page_index}页产品列表: ", response, response.text)

注意一個漂亮的細節：第一發和第二發打的是同一個 list_url。伺服器怎麼分辨你在領考卷還是在換資料？靠兩個訊號——有沒有帶查詢資料（data=data）、以及 cookie 裡有沒有 cookie2。你這邊只要記得：session.post 會自動把 session 裡的 cookie1、cookie2 一起掛上，不用手動組標頭。

步驟三：解開回應——雙重編碼的 JSON

    ret_list_str = response.json().get("resultList")
    ret_list = json.loads(ret_list_str)
    for item in ret_list:
        print(item)

回應本身是 JSON，但其中的 resultList 欄位值不是清單，而是一段 JSON 字串——JSON 裡再包一層字串化的 JSON，這種雙重編碼在 Java 後端很常見。所以要解析兩次：response.json() 拆外層，json.loads() 拆內層，最後得到商品清單逐筆印出。

預期看到什麼：一筆一筆的商品字典。如果 resultList 拿到 None，先別動這段解析——那通常代表第二發請求根本沒通過，回的是錯誤頁，要回頭檢查前三段。

步驟四：排成分頁迴圈，每頁整套重跑

把五段迴圈排起來的程式很短，而且每一段都有它存在的理由：

def main():

    for page in range(1,6):
        # (1) 发起第一次请求，获取cookie1以及源码三件套：meta_content, ts_js, auto_script_js
        meta_content, ts_js, auto_script_js = fetch_1()
        # print(session.cookies.get_dict())
        # (2) 基于源码三件套制作cookie2
        gen_cookie2(meta_content, ts_js, auto_script_js)
        # (3) 发起第二次请求，获取数据
        fetch_2(page)
        session.cookies.clear()
        time.sleep(1)

迴圈體就是五段迴圈的前三段加最後一段：fetch_1() 抓三件套，gen_cookie2() 注入執行並收割 cookie2，fetch_2(page) 帶資料重放。最後兩個動作是成績單與公德心：

  • session.cookies.clear() — 每頁結束把 cookie 清乾淨。cookie2 是一次性的通關章，帶著舊章跑下一頁，輕則被擋、重則整組 cookie 都被標記。寧可每頁多花幾秒重算，也不讓任何舊答案混進來。
  • time.sleep(1) — 頁與頁之間停一秒。這是節流：全速狂打是風控眼裡最明顯的爬蟲特徵，被鎖 IP 之後換代理都救不回來。

迴圈的範圍（這裡是 1 到 5 頁）照你的需求改；但「每頁重跑」的節奏不要改，那是這個案例能穩定跑完的關鍵。

做完長什麼樣

可驗證的結果長這樣：終端機依序印出「第 1 頁產品列表」到「第 5 頁產品列表」，每一頁下面一筆一筆的商品資料；每一頁開頭都重新抓了三件套、重新算了 cookie2。若某一頁突然吐不出資料，把 session.cookies.get_dict() 印出來看——cookie2 沒掛上或已被清掉，就是前三段出問題的訊號。

小結

重放就是「同一個端點＋查詢資料＋cookie2」：criteriaJson 整串照抄不要精簡，session 自動把兩組 cookie 帶上；回應的 resultList 是雙重編碼要解兩次。分頁迴圈每頁把五段整套重跑，結束清 cookie、中間停一秒——cookie2 是一次性消耗品，這兩件事保證整批抓得穩。

到這裡，歐冶案例的五段迴圈完整閉合了。但不是每站都長這樣——下一節看拼多多的 anti_content：輸入不是每次抓，而是一組靜態腳本加一次對時，入口在哪、呼叫順序怎麼排。
