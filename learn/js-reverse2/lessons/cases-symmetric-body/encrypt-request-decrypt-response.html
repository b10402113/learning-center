加密請求 body、解密響應：一次跑通完整對

Step 5/5 · 案例：對稱與串流加解密

學習目標

能打通「加密請求 body、解密響應」的完整對，用兩把不同的 key 各自完成加解密並驗收結果。

目標與前置條件

前面幾步都在處理單向的解密：響應是密文，我們把它解開。但有些網站把保護拉滿，連你送出去的請求 body 都必須先加密才能送——伺服器不接受明文 JSON，收到就直接拒絕。毛毛租的列表介面 index/build.json 就是這樣：請求體要先過 AES 加密再 base64，響應回來又是一包要用另一把 key 解的密文。這一節把這個完整對從頭跑到尾。

動手前需要具備：pycryptodome 與 execjs 都裝好；第二步的 AES-CBC 加解密骨架已經在手上；第三步的 key==iv 觀念也清楚——這個案例的請求方向就是 key==iv。另外先建立一個關鍵認知：請求方向和響應方向用的是兩把不同的 key，請求用 55b3b62613aef1a0，響應用 0a1fea31626b3b55。兩把都要找齊，缺一把這個對就閉合不起來。

第一步：組出請求明文，照抄前端的補齊規則

請求的明文是一段 JSON。要加密的第一件事是把它補齊到分組大小的整數倍，而這個案例的補齊規則有點特別：

data = '{"Type":0,"page":2,"expire":1704547824158}'
# aes加密
data += (16 - len(data) % 16) * "\b"
data = pad(data.encode(), 16)

逐行看它做了什麼。第一行組出請求 JSON，Type、page、expire 是這個介面要的欄位。第三行是關鍵：先補上若干個退格字元 \b，把字串湊到 16 的整數倍。第四行再走一次標準的 PKCS7 填充。也就是說，這個站的前端把「補 \b」和「PKCS7 填充」疊在一起用。

看到這種寫法，正確的反應不是「這也太醜了，我來優化成一行 pad 就好」，而是照抄。重現加密的第一原則是逐位元組一致：伺服器的解密程式期待的就是這種補齊結果，你把中間任何一步「整理」掉，產生的密文就對不上。這就像抄一份古老的食譜，裡頭寫「先加半匙鹽、再加半匙鹽」——你可以嫌它囉嗦，但不能改成一匙，味道就是不同。若解密端驗證失敗，回頭逐行比對補齊行為永遠比重新設計有效。

第二步：key==iv 加密，再 base64

明文補齊後，就是熟悉的 AES-CBC 加密——只是 key 與 iv 是同一個值：

key = '55b3b62613aef1a0'.encode()  # 必须是16个字节
iv = '55b3b62613aef1a0'.encode()  # 必须是16个字节
aes = AES.new(key=key, mode=AES.MODE_CBC, iv=iv)
# 基于aes算法对象对数据做加密
encrypt_data = aes.encrypt(data)
print("encrypt_data:::", encrypt_data)

# base64编码
b64encode_encrypt_data = base64.b64encode(encrypt_data)
data = b64encode_encrypt_data.decode()

四個動作：16 位元組的 key 與 iv 取同一個字串（第三步講過的 key==iv）；建立 CBC 加密物件；encrypt 產生二進位密文；最後 base64.b64encode 轉成可運送的字串。到這裡，請求 body 就準備好了——它是加密方向的完整流程：pad → AES.new → encrypt → b64encode，正是第二步解密流程的鏡像。

第三步：送出請求

response = requests.post('https://www.maomaozu.com/index/build.json', cookies=cookies, headers=headers, data=data)

注意 data=data 傳的是剛才那串 base64 字串本身，不是表單字典——伺服器期待的請求體就是這串密文。若這一步收到錯誤回應，先確認請求體沒有被 requests 再編碼一次（例如誤用 json= 參數把字串又包了一層 JSON），再檢查補齊規則有沒有抄對。

第四步：用另一把 key 解開響應

響應回來是一包新的密文。解密走的是 JS 裡現成的函式：

data = execjs.compile(open("04 mmz.js").read()).call("decrypt_data", response.text)
print("data:::", data)

把 04 mmz.js 整份編譯起來，呼叫入口 decrypt_data。拆開這個 JS 函式看，它的結構和第三步看過的 key==iv 一模一樣，只是換了一把 key：

function d(e, a) {
    e = cryptoJs.enc.Utf8.parse(e);
    var l = cryptoJs.AES.decrypt(a, e, {
        mode: cryptoJs.mode.CBC,
        padding: cryptoJs.pad.Pkcs7,
        iv: e
    });
    return cryptoJs.enc.Utf8.stringify(l).toString()
}

function decrypt_data(data) {
    e = '0a1fea31626b3b55'

}

decrypt_data 把寫死的 key 0a1fea31626b3b55 交給 d()，而 d() 裡 iv: e 沿用同一個值——響應方向也是 key==iv。對照請求方向的 55b3b62613aef1a0，兩把 key 並不相同。「請求一把、響應一把」是真實網站很常見的配置：兩個方向分開保護，一把洩漏不至於全破。實戰時的提醒很直接——解不開的時候，先確認自己拿的是不是這個方向的 key，用錯方向的 key 解出來必定是亂碼，而且你會誤判成演算法錯了。

這裡選擇 execjs 呼叫而不是純 Python 重現，也是刻意的取捨：響應解密的 JS 只有十來行、沒有瀏覽器環境依賴，改寫成 Python 並不難；但只要 JS 能跑，呼叫原檔永遠是最快閉環的路徑。先用 JS 把流程驗證通了，之後要移植成純 Python 再動工——這正是「先 Python 重現、失敗再 execjs 兜底」的反向運用：這裡用 execjs 開路，Python 重現留給效能或封裝的需求。

做完長什麼樣：驗收這個完整對

驗收分三層，一層一層確認：

  1. 請求被接受。伺服器沒有回錯誤訊息，而是回了一包結構正常的密文——這表示你的加密請求 body 格式正確。若收到明文的錯誤 JSON，多半是補齊規則或 key 抄錯。
  2. 響應解得開。decrypt_data 的輸出是可讀的 JSON，不是亂碼。若解不開，先檢查是不是用了請求方向的 key 去解響應。
  3. 內容合理。解出來的 JSON 欄位符合這個介面的預期（例如列表資料的欄位齊全），這一步確認的是整條管線而不只是解密本身。

三層都過，這個「加密請求、解密響應」的完整對就算閉合。之後遇到同類型的網站，你已經有完整的模板：找出兩個方向各自的 key、確認各自的補齊與填充規則、加密請求、解密響應、逐層驗收。

最後補一個常見的誤判：有的站會在 Cookie 裡塞一堆看起來很機密的鍵值（名字裡帶 SECKEY 之類），讓人以為那就是加密用的 key。這個案例裡這類 Cookie 和 body 的加解密完全無關——真正的 key 寫死在 JS 裡。判斷 key 的位置永遠以「解密函式實際吃的參數」為準，名字唬人的變數不算數。

小結

完整的加解密對是「pad → AES.new → encrypt → b64encode」送出請求、再用另一把 key 解密響應。這個案例的補齊規則是先補 \b 再 PKCS7，照抄不要優化；請求與響應各用一把 key（55b3b62613aef1a0 與 0a1fea31626b3b55），都是 key==iv。驗收分三層：請求被接受、響應解得開、內容合理。
