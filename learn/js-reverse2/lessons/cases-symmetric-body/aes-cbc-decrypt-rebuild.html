用 Python 重現 AES-CBC 解密：Pkcs7 與 ZeroPadding

Step 2/5 · 案例：對稱與串流加解密

學習目標

拿到 key、iv、mode、padding 之後，能用 Python 的 pycryptodome 重現 AES-CBC 解密，並分別處理 Pkcs7 與 ZeroPadding 兩種填充。

目標與前置條件

上一節已經把密文洗成乾淨的位元組。這一節要完成的事很具體：把 JavaScript 裡的 AES-CBC 解密搬到 Python，跑出可讀的原文。做完你會有一份可以對接任何 AES-CBC 介面的解密程式，並且知道解出來是亂碼時該往哪裡查。

動手前需要具備三樣東西。第一，Python 環境裝好 pycryptodome（pip install pycryptodome），它是 Python 端實作 AES 的標準選擇。第二，上一節的成果——一包乾淨的 base64 字串或已解碼的密文位元組。第三，從 JavaScript 找到的四個參數：key、iv、mode、padding。參數找尋是下一節的主題，這一節假設它們已經攤在桌上；mode 這邊固定是 CBC，padding 則會遇到 Pkcs7 與 ZeroPadding 兩種，這是本節的真正重點。

第一步：建立 AES-CBC 解密物件

先看福建電子交易平台的完整解密流程。它的 key、iv 是固定字串，直接照抄即可：

key = "EB444973714E4A40876CE66BE45D5930".encode()
iv = "B5A8904209931867".encode()
aes = AES.new(key, AES.MODE_CBC, iv)
data_encrypt = base64.b64decode(data_encrypt_bas64)
data = aes.decrypt(data_encrypt).decode()

逐行拆開來看：

  1. key = "EB444973714E4A40876CE66BE45D5930".encode() 把 key 從字串轉成位元組。注意這個 key 是 32 個字元，也就是 32 位元組的 AES-256——不要因為它長得像十六進位就以為是 16 位元組，AES 的規則是 key 只能是 16、24、32 位元組，這裡剛好是最大的那種。iv 則固定是 16 位元組。
  2. aes = AES.new(key, AES.MODE_CBC, iv) 建立解密物件。第三個參數就是 iv；CBC 模式必須給 iv，少了它程式會直接報錯。
  3. data_encrypt = base64.b64decode(data_encrypt_bas64) 把上一節洗乾淨的 base64 字串解碼成密文位元組。如果上一節已經解過了，這裡直接用位元組即可。
  4. aes.decrypt(data_encrypt) 執行解密，得到明文位元組；最後的 .decode() 把它轉成文字。

這五行就是 AES-CBC 解密的骨架：準備 key／iv → 建物件 → 解 base64 → 解密 → 轉文字。接下來的問題都出在最後一步與「填充」的關係上。

第二步：處理填充——Pkcs7 與 ZeroPadding 的差別

AES 是分組加密，每次只吃固定大小的區塊（16 位元組）。明文長度不是 16 的倍數時，就要補上一些位元組把最後一塊填滿，這就是填充（padding）。解密端必須把填充拿掉，才能還原真正的原文。填充方式不同，拿掉的方法也不同——這是解出來像亂碼卻找不到原因的常見陷阱。

Pkcs7：補幾個就填幾號。缺 N 個位元組，就補 N 個值為 N 的位元組。缺 5 格就補五個 0x05；剛好對齊時補一整塊 16 個 0x10。解密端看最後一個位元組的值，就知道要拿掉幾個。有道翻譯的解密程式把這個動作寫得很標準：

data = aes.decrypt(encrypt_data)
print("data:", data)
data = unpad(data, 16)
print("source data:", data.decode())

unpad(data, 16) 就是把 Pkcs7 填充拿掉的動作，16 是區塊大小。拿掉之後再 decode()，得到的才是乾淨的原文。

回頭看福建那份程式，它其實跳過了 unpad，直接 aes.decrypt(data_encrypt).decode()。這樣為什麼也能跑？因為 Pkcs7 填充的位元組多半是不可見的控制字元，解碼不會報錯，只是明文尾巴多了幾個看不見的垃圾。要是你後續要做字串比對或 JSON 解析，這些殘渣就會出來搗亂。所以正確的習慣是解密後一律補上 unpad，別依賴「看起來沒事」。

ZeroPadding：用零位元組填滿。另一種填充是直接補 0x00 填滿最後一塊，解密端把尾端的零位元組拿掉。招標搜索接口用的就是這種。它的 JavaScript 端明確指定：

    var nContent = CryptoJS.AES.decrypt(str, variate.key, {
        iv: variate.aceIV,
        mode: CryptoJS.mode.CBC,
        padding: CryptoJS.pad.ZeroPadding
    })

Python 端的對應版本在原檔裡以註解形式保留，內容正是標準的「解 base64 → 建 CBC 物件 → 解密」：

# Python逆向
# encrypt_data = base64.b64decode(response.text)
# key = '3zKzyf6eEfuDjAG3'.encode()
# iv = 'fyUANZ0qSNZhhNCV'.encode()
# aes = AES.new(key, AES.MODE_CBC, iv)
# data = aes.decrypt(encrypt_data)
# print("data:::", data.decode())

ZeroPadding 沒有 Pkcs7 那種「最後一位元組告訴你拿掉幾個」的規則，所以 Python 端要自己把尾端的零位元組剝掉：

data = aes.decrypt(encrypt_data)
plaintext = data.rstrip(b"\x00").decode()

這裡有個要留意的邊界：ZeroPadding 分不清「填充的零」和「原文結尾本來就有的零」。如果明文剛好以零位元組結尾，剝掉後會少一個位元組。實務上明文多半是 JSON 或文字，不太會以零結尾，所以照剝沒問題；但心裡要記得這件事，別在二進位資料上盲抄這個做法。

大多數網站用 Pkcs7，ZeroPadding 相對少見但真實存在。看到 padding 設定就照抄，是最省事的原則——填充選錯，key、iv、mode 全對也解不出乾淨的原文。

第三步：解出來是亂碼時，依序檢查這幾項

程式跑起來不報錯、解出來卻是亂碼，是這個階段最常見的狀況。用條件式的方式分流排查，不要亂改一通：

  • 若亂碼只有尾巴不乾淨、前面都是可讀文字——是填充問題，檢查 unpad 有沒有做、填充方式有沒有抄對。
  • 若整段亂碼但長度合理——優先懷疑 key 或 iv 抄錯。iv 錯的典型症狀就是「第一塊正確、後面全亂」，因為 CBC 只有第一塊直接吃 iv。
  • 若長度不合或程式直接報錯——檢查有沒有拿錯資料去解，例如忘了 b64decode，或密文裡還殘留引號、URL-safe 字元。
  • 若以上都對還是亂碼——mode 可能根本不是 CBC（下一節會遇到 ECB），或演算法不是 AES。

做完長什麼樣

驗收標準很明確：解出來的字串是可讀的原文——招標列表是一段合法 JSON，翻譯結果是看得懂的文字。再進一步，可以把同一包密文交給 JavaScript 的解密函式（用 execjs 呼叫原檔），兩邊輸出一字不差，就代表 Python 重現完全正確。程式跑通之後，你可以把這份骨架套用到任何「AES-CBC + base64」的介面，換掉 key、iv、填充設定就能用。至於 key 與 iv 到底藏在 JavaScript 的哪裡、要用什麼方法把它們挖出來——原理的部分交給下一節，那裡會拆解三種最常見的藏法。

小結

AES-CBC 解密的骨架是「準備 key／iv → AES.new(key, MODE_CBC, iv) → b64decode → decrypt → 處理填充」。填充有兩種：Pkcs7 用 unpad(data, 16) 拿掉，ZeroPadding 用 rstrip(b"\x00") 剝掉，看到 JS 的 padding 設定就照抄。解出亂碼時依序檢查：填充、key／iv、資料預處理、mode 與演算法。

骨架有了，原料也有了，但 key 與 iv 在真實網站上不會像範例那樣乖乖寫在引號裡。下一節看三種最常見的藏法：CryptoJS 的整數陣列、MD5 派生的摘要，以及偷懶的 key==iv。
