不是 AES 的對稱加密：DES／ECB 與 RC4 串流

Step 4/5 · 案例：對稱與串流加解密

學習目標

能認出不是 AES 的對稱加密：DES 的 8 位元組 key 與 ECB 模式，以及 RC4 串流加自定 UTF-8 解碼的混合管線。

前言：流程都對，解出來還是亂碼

前兩節建立了一套可靠的流程：洗乾淨密文、找齊 key 與 iv、用 Python 重現 AES-CBC 解密。這套流程在多數網站都管用——直到你遇上招標網或極簡壁紙。同樣照著做，參數也確認過，解出來還是一團亂碼。問題不在流程，而在一個沒被質疑的假設：演算法是 AES。這個假設在大多數時候成立，所以它悄悄變成反射動作；而這兩個案例就是專門來打破反射的。

這一節看兩個非 AES 的分支。第一個是招標網的 DES／ECB——key 變短了、iv 消失了，分組大小也不同。第二個是極簡壁紙的 RC4 串流——它連「分組」這個概念都沒有，是一個位元組一個位元組 XOR 過去，後面還掛著一個自定的 UTF-8 解碼。看完你會知道：判斷演算法要看特徵，不能靠習慣。

分支一：DES／ECB——key 變短、iv 消失

招標網的響應解密函式長這樣：

function decryptByDES(ciphertext) {
    var keyHex = CryptoJS.enc.Utf8.parse("1qaz@wsx3e");
    //  ctpstp@custominfo!@#qweASD
    // direct decrypt ciphertext
    var decrypted = CryptoJS.DES.decrypt({
            ciphertext: CryptoJS.enc.Base64.parse(ciphertext),
        },
        keyHex, {
            mode: CryptoJS.mode.ECB,
            padding: CryptoJS.pad.Pkcs7,
        }
    );
    return decrypted.toString(CryptoJS.enc.Utf8);
}

一眼就能看到三個和 AES 不一樣的地方。第一，呼叫的是 CryptoJS.DES，不是 CryptoJS.AES。第二，key 是一個短字串 "1qaz@wsx3e"，不是 AES 常見的 16 或 32 字元。第三，模式是 CryptoJS.mode.ECB，設定物件裡找不到 iv——因為 ECB 根本不需要 iv。

DES（Data Encryption Standard，資料加密標準）是 AES 的前輩，1970 年代就已定案。它和 AES 的體質差異用一張表對照最快：

特徵AESDES
key 長度16／24／32 位元組8 位元組
分組大小16 位元組8 位元組
常見模式CBC（有 iv）ECB（無 iv）或 CBC
JS 呼叫特徵CryptoJS.AESCryptoJS.DES

ECB（Electronic Codebook，電子密碼本）是分組加密最直覺的模式：把明文切成一塊塊，每塊各自加密，塊與塊之間互不相干。問題也出在這裡——相同的明文塊會加密出相同的密文塊，就像同一枚印章蓋多少次，印記都一模一樣。所以 ECB 的密文會保留明文的重複圖樣，安全性弱，現在多數系統都改用 CBC。不過對逆向者來說重點不是它的安全性，而是它的行為：沒有 iv、不需要填充之外的額外參數，看到 mode.ECB 就知道解密程式裡不會出現 iv。

Python 端怎麼處理這個案例？它走的是「呼叫原始 JS」的路線——把整個 JS 檔編譯起來，直接呼叫 decryptByDES：

with open("02 招标网.js") as f:
    js_code = f.read()
js_compile = execjs.compile(js_code)

ret = js_compile.call("decryptByDES", response.text.strip('"'))
print(ret)

這個選擇本身就是個判斷：DES 的 Python 重現（用 pycryptodome 的 DES.new）完全可行，但既然 JS 函式是現成的、參數也單純，直接呼叫省去翻譯成本。若你之後要把 DES 改寫成純 Python，記得三個要點：key 用 DES 的 8 位元組、模式 MODE_ECB 不傳 iv、填充仍是 Pkcs7 一樣要 unpad。

分支二：RC4 串流——沒有分組，一位元組一位元組 XOR

極簡壁紙的圖片列表介面回傳一個 result 欄位，是一串 base64。把 JavaScript 的解密管線拆開，它由三個函式串起來：

function _0x58b5da(_0x512f6f) {
    return _0x300484(_0x476691(_0x4176cc(_0x512f6f)));
}

從內往外讀：先把 base64 解成位元組陣列，跑一次解密核心，再把結果解碼成文字。混淆後的函式名（_0x58b5da 這種）是這個 bundle 的常態，不用害怕，照著資料流讀就好。

第一層 _0x4176cc 是 base64 解碼：呼叫 window.atob，把字元逐一轉成位元組：

這段是 RC4 風格的串流加密。RC4 的運作方式可以想成一台不斷吐出亂數的發牌機：先用一把 key 把一張 256 張牌的牌堆洗牌（程式裡的交換迴圈），接著每加密一個位元組，就吐一張牌和它做 XOR。解密是同一個動作——XOR 是對稱的，再跑一次就還原。串流加密沒有分組概念，所以沒有填充、也不需要 iv；密文長度和明文一樣長。辨認特徵也就在這裡：256 長度的陣列、交換洗牌的迴圈、最後一個 XOR 推入結果，三者同時出現，幾乎可以斷定是 RC4 一類的串流密碼。

第三層 _0x300484 是一段自定的 UTF-8 解碼，把 XOR 還原後的位元組翻成文字。它自己實作了 UTF-8 的多位元組規則，而不是呼叫現成的 TextDecoder——這種「連編碼都自己寫」的風格在混淆 bundle 裡很常見。對 Python 重現來說，這一段通常直接沿用 bytes.decode('utf-8') 即可，不必逐行翻譯。

Python 端怎麼對接？和招標網一樣，直接呼叫整條管線的入口：

result = response.json().get("result")
…
data = execjs.compile(open("08 极简壁纸.js").read()).call("_0x58b5da", result)

解出來是圖片列表的 JSON，之後逐張組出圖片網址下載即可。注意混淆的入口函式名（_0x58b5da）要從管線組合的那支函式認起，不要在一堆 _0x... 裡亂猜。

分流判斷：看到什麼特徵，走哪條路

把兩個分支放回判斷流程裡，演算法的分流其實有固定的觀察點：

  • 若 JS 呼叫 CryptoJS.AES——走前兩節的 AES-CBC 流程。
  • 若 JS 呼叫 CryptoJS.DES，或 key 明顯偏短、模式寫著 ECB——這是 DES，記住 8 位元組 key、無 iv。
  • 若程式裡有 256 長度的陣列加 XOR 迴圈、沒有 encrypt/decrypt 字樣——這是 RC4 一類的串流密碼，解密後多半還要過一次自定編碼。
  • 若演算法特徵不明——先用 execjs 呼叫原函式把資料解出來，確認內容正確後，再決定要不要花時間改寫成純 Python。

另一個共通的教訓是：不要把「對稱加密」和「AES」畫上等號。對稱加密是一個家族，AES、DES、RC4 都是家族成員；你抄參數時抄的是這個家族的哪一位，決定了 Python 端要用哪個模組、要不要 iv、要不要填充。

小結

不是所有對稱加密都是 AES。DES 的 key 是 8 位元組、分組 8 位元組，ECB 模式沒有 iv、相同明文塊加密出相同密文塊，JS 特徵是 CryptoJS.DES 加 mode.ECB。RC4 是串流密碼，用 256 長度的牌堆洗牌後逐一 XOR，沒有分組也沒有填充，解出來常掛一層自定 UTF-8 解碼。分流看特徵：呼叫名稱、key 長度、有無 iv、有無 XOR 迴圈。

四個步驟下來，認密文、重現 AES、還原 key／iv、分辨非 AES 分支，零件都齊了。最後一步把它們組成一個完整的實戰迴圈：一個連請求 body 都要加密的網站——毛毛租——從加密請求一路跑到解密響應。
