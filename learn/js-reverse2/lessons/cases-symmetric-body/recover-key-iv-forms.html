key 與 iv 的三種藏法：words 陣列、MD5 派生、key==iv

Step 3/5 · 案例：對稱與串流加解密

學習目標

能從 JS 裡三種常見的藏法還原 key 與 iv：CryptoJS 的 words 整數陣列、MD5 派生的摘要位元組，以及 key 直接當 iv 用的捷徑。

前言：key 不會乖乖待在引號裡

上一節的解密程式裡，key 與 iv 都是現成的字串，照抄就好。但那是教學範例才有的待遇。真實網站的開發者知道自己寫在前端的 key 遲早會被看光，所以多少會做點手腳：把字串拆成一組看不懂的數字、拿某個秘密字串過一次雜湊、或者乾脆偷懶只用一把 key。於是你的 DevTools 停在解密函式上，看到的不是 '0123456789abcdef'，而是一團 {"words":[863652730, ...]} 之類的東西，一時之間根本不知道從哪裡下手。

這一節把三種最常見的藏法攤開來看。它們的手法不同，但目的都一樣——把 key 的真面目從你眼前移開；也都有一套固定的還原動作。認得出藏法、知道還原程序，你就能把上一節缺的原料補齊。

藏法一：整數陣列（CryptoJS 的 WordArray）

招標搜索接口的 JavaScript 端，key 與 iv 長這樣：

        key: {"words": [863652730, 2036741733, 1164342596, 1782662963], "sigBytes": 16},
        aceIV: {"words": [1719227713, 1314533489, 1397643880, 1749959510], "sigBytes": 16},

這是 CryptoJS 內部的資料格式，叫做 WordArray。CryptoJS 不直接用 JavaScript 的字串存金鑰，而是把位元組打包成一組 32 位元的整數，每個整數容納 4 個位元組。sigBytes: 16 表示實際有效的長度是 16 位元組——正好 4 個整數乘以 4。所以這組數字其實就是 16 個字元的 key，只是換了件外衣。

還原的方法很機械：把每個整數拆回 4 個位元組（大端序，高位元組在前），依序接起來。用 Python 表達就是：

import struct
words = [863652730, 2036741733, 1164342596, 1782662963]
key = b"".join(struct.pack(">i", w) for w in words)   # b'3zKzyf6eEfuDjAG3'

四個整數還原出 3zKzyf6eEfuDjAG3，16 個 ASCII 字元，正是這個案例的 AES key；iv 的那組數字同樣還原出 fyUANZ0qSNZhhNCV。對照 Python 版解密程式裡寫死的字串，兩邊完全一致——這也順便驗證了還原方法沒錯。

有個細節別被騙了：陣列裡可能出現負數（例如 -1123456），那不是異常，只是 32 位元帶號整數的表示方式，把它當位元組模式處理、照樣拆成 4 個位元組就好。另一個快速心法是：看到 words 裡正好 4 個整數、sigBytes: 16，幾乎可以立刻斷定這是一把 16 位元組的 AES-128 key，拆開就有答案。這就像看到有人把一百元鈔票折成四折藏在口袋——形狀變了，價值沒變，拆開就是錢。

藏法二：MD5 派生的摘要

有道翻譯更進一步，key 與 iv 根本沒有以原貌出現過。JavaScript 端定義了一個小函式，把某個秘密字串過一次 MD5：

function y(e) {
    return cryptoJs.createHash("md5").update(e).digest()
}
…
    const a = y(o)
        , i = y(n)
        , r = cryptoJs.createDecipheriv("aes-128-cbc", a, i);

y() 回傳的是 digest()——MD5 的原始摘要位元組，16 個位元組——而不是平常看到的 32 字元十六進位字串。這個差別是整段的關鍵：AES-128 的 key 恰好要 16 位元組，所以直接把 MD5 摘要的位元組當 key 用。如果誤把十六進位字串拿去當 key，長度 32 位元組會變成 AES-256，解出來必然是亂碼。可以這樣記：digest() 是摘要的「本體」，hexdigest() 是把本體印成可讀字串的「發票」；當 key 要的是本體，不是發票。

Python 端的重現寫法完全對稱——注意 return m.digest() 這一行：

def get_md5(s):
    m = hashlib.md5()
    m.update(s.encode())
    return m.digest()


o = 'ydsecret://query/key/B*RGygVywfNBwpmBaZg*WT7SIOUP2T0C9WHMZN39j^DAdaZhAnxvGcCY6VYFwnHl'
n = 'ydsecret://query/iv/C@lZe2YzHtZ2CYgaXKSVfsb7Y4QWHjITPPZ0nQp87fBeJ!Iv6v^6fvi2WN@bYpJ4'
key = get_md5(o)
iv = get_md5(n)

整條還原路徑是這樣：在 JS 裡找到傳給 y() 或 md5() 的那串秘密字串（這裡是兩串 ydsecret://query/... 開頭的網址樣式字串，一串給 key、一串給 iv），照抄到 Python，過一次 MD5 取 digest，key 與 iv 就到手了。秘密字串通常藏在函式的參數或附近的變數裡，順著呼叫往回找一層就能看到。

藏法三：key==iv，偷懶的捷徑

第三種藏法連藏都算不上，卻出奇地常見——iv 直接用 key。毛毛租的請求加密程式這樣寫：

key = '55b3b62613aef1a0'.encode()  # 必须是16个字节
iv = '55b3b62613aef1a0'.encode()  # 必须是16个字节

兩行一模一樣。JavaScript 端的解密函式也是同一個套路，把同一個值同時當 key 和 iv 用：

function d(e, a) {
    e = cryptoJs.enc.Utf8.parse(e);
    var l = cryptoJs.AES.decrypt(a, e, {
        mode: cryptoJs.mode.CBC,
        padding: cryptoJs.pad.Pkcs7,
        iv: e
    });

參數 e 進來先變成 key，設定物件裡 iv: e 又指回同一個值。為什麼有人這樣做？因為 iv 本來就不是秘密，它的功能只是讓相同的明文加密出不同的密文；開發者若懶得另外生成一串 iv，直接複製 key 最省事。從逆向的角度看這是好消息：找到一把 key 就等於找到兩把。反過來說，這也是安全性上的警訊——key 一旦外洩就全盤皆輸，對我們是便利，對站方是漏洞。

辨認特徵很簡單：JS 裡 iv 指向的變數和 key 是同一個，或 Python 裡兩行賦值的字串完全相同。看到這種情況，別懷疑自己抄錯，照抄就對了。

三種藏法的對照與還原順序

藏法你在 JS 看到什麼還原動作案例
words 整數陣列{"words":[...], "sigBytes":16}每個整數拆 4 位元組（大端序）接起來招標搜索接口
MD5 派生md5(秘密字串).digest()照抄秘密字串，過 MD5 取 digest有道翻譯
key==iviv 與 key 指向同一個值找到一把就等於兩把毛毛租

實戰時的判斷順序建議這樣走：先看解密呼叫的參數型別——是 words 物件就走還原程序，是函式呼叫就往回追一層看輸入，是變數就跟著變數找到賦值處；找到賦值處再分辨是明文常數、MD5 派生，還是 key==iv。多數網站只用其中一種，少數會混用（例如 key 用 MD5 派生、iv 直接抄 key）。

這三把鑰匙要送去哪裡

把這一節接回前面的脈絡：第一節負責把密文洗乾淨，第二節負責用 key、iv 執行解密，這一節補上「key、iv 從哪來」。三塊拼起來，AES 這條路就通了——不管藏法怎麼變，最後都只是把還原出的值填進 AES.new(key, AES.MODE_CBC, iv)。不過故事還沒結束：有些網站的演算法根本不是 AES，用同樣的流程去解只會得到亂碼。下一節就來看兩個這樣的分支——DES／ECB 與 RC4 串流。

小結

key 與 iv 有三種常見藏法：CryptoJS 的 words 整數陣列，把 16 位元組拆成 4 個 32 位元整數，大端序拆回來就還原；MD5 派生，把秘密字串過 MD5 取 digest（不是 hexdigest）當 key；以及 key==iv 的偷懶寫法，找到一把就等於兩把。辨認靠看解密呼叫的參數型別，還原動作都是固定的。
