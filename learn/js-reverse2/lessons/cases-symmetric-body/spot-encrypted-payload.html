認出密文在哪裡：整段 base64、欄位 base64 與傳輸變體

Step 1/5 · 案例：對稱與串流加解密

學習目標

看到響應或請求裡的字串，能判斷密文藏在哪個位置，並把整段 base64、欄位 base64、加引號、URL-safe 等傳輸變體還原成乾淨的密文位元組。

前言：Response 打開是一串看不懂的字母

你在 DevTools 裡追一個招標網站的列表介面，點開 Response，預期會看到整齊的 JSON，結果畫面上是一大串沒有空白、沒有結構的字母數字，像有人把整頁文章揉成一團丟出來。這時候多數人的直覺是立刻去 JavaScript 裡找解密函式——但其實還有更前面的問題沒有回答：這團密文到底藏在哪裡？它本身就是整個響應，還是躲在某個欄位裡？它需不需要先做一點字串處理，才有辦法交給解密函式？

這個問題比想像中重要。解密流程的第一步永遠是「把密文洗成乾淨的位元組」，就像洗菜是下廚的第一步；菜沒洗乾淨，後面火候調味再精準也做不出能吃的東西。只要這一步弄錯——拿錯欄位、忘了去引號、用了錯的 base64 字元集——就算 key、iv、mode 全部抄對，解出來還是一團亂碼，而且你會誤以為是演算法找錯，浪費整個下午。這一節把三個真實案例的密文擺在一起看：福建電子交易平台、招標網、有道翻譯。看完你會認出密文的三種常見藏身處、三種傳輸變體，以及一條「先洗乾淨、再解密」的固定順序。

密文藏在哪裡：三種常見位置

先看位置。同樣是「響應被加密」，密文放在哪裡卻有三種典型長相，對應三種不同的取出手法。

第一種：整段響應體就是密文。招標搜索接口 GetSearchProHandler.ashx 就是這種型態——伺服器回傳的不是 JSON，整段 response.text 本身就是一串 base64，把它整個拿去解碼解密就對了。這種情況最單純，你不需要找欄位，密文就是響應本體。

第二種：密文躲在 JSON 的某個欄位裡。福建電子交易平台的招標列表介面回傳的是正常 JSON，但真正的內容被塞在 Data 欄位，必須先取出這個欄位再解密：

data_encrypt_bas64 =response.json().get("Data")

這行做的事很簡單：把 JSON 解開、取出 Data 的值。但這一步是整個解密流程的真正起點——如果拿整個響應體去解，或者取錯欄位，後面的程式一行都不會跑對。順帶一提，欄位名不一定叫 Data，也可能是 result、rows、content 之類的名字，所以判斷的依據是「這個欄位的值是不是一串能解開 base64 的亂數字串」，而不是欄位叫什麼。

第三種：連請求都要加密。有的站不只把響應加密，你送出去的請求 body 也必須先加密才能送——毛毛租的列表介面就是這樣，請求體是一串 base64 密文，響應也是密文，兩個方向都要處理。這種「加密請求、解密響應」的完整對會留到最後一步實際跑一次，這裡先知道有這種型態就好。

三種傳輸變體：洗乾淨再解

找到密文之後，還不能直接丟給解密函式。密文在網路上運送時，偶爾會被套上一層「運輸包裝」——最常見的是被引號包住，或是換成 URL 安全的 base64 字元集。包裝本身不是加密，但不解掉它，解碼就會出錯或解出錯的位元組。

變體一：被雙引號包住。招標網的響應是一整段 base64，但字串前後各多了一個雙引號。直接解碼會因為引號不在 base64 字元集裡而失敗，所以要先剝掉外層：

ret = js_compile.call("decryptByDES", response.text.strip('"'))

strip('"') 把字串頭尾的雙引號去掉，剩下的才是能解碼的密文。這種「加了引號的密文」通常來自伺服器把密文當字串序列化輸出，是很典型的運輸變體。

變體二：URL 安全的 base64。標準 base64 的字元集裡有 + 與 /，這兩個字元在 URL 裡各有特殊意義，所以有些站會把它們換成 - 與 _，變成 URL-safe base64。有道翻譯的響應就是這種長相，解碼前要先換回來：

b64encode_encrypt_data = response.text.replace("-", "+").replace("_", "/")
# 进行base64的解码
encrypt_data = base64.b64decode(b64encode_encrypt_data)

先把 - 換回 +、_ 換回 /，還原成標準 base64 的字元集，再交給 base64.b64decode。少做這個替換會發生什麼事？b64decode 遇到不在字元集裡的字元可能直接報錯；就算勉強解開，得到的位元組也是錯的，解密後自然是亂碼。

變體三：標準 base64，直接解。福建電子交易平台的 Data 欄位就是最標準的形態，取出後直接 b64decode 即可。大多數站屬於這種，但你必須先確認過它沒有前兩種包裝，才能這麼放心。

判斷的邊界：不是每串 base64 都是密文

看到 base64 就喊「這是加密」是新手最常犯的錯。base64 是編碼，不是加密——它的作用只是把二進位資料換成可以安全運送的字元，任何人都能解回去，就像把信裝進透明信封寄出。網站用 base64 包裝的東西很多：小圖示、檔案內容、壓縮過的資料、token，都是常客。

那要怎麼分辨「只是編碼」和「編碼後的密文」？解碼之後看位元組的長相：如果解出來是可讀的文字或有規律的二進位格式，那只是一層編碼；如果解出來是一團高熵亂數——沒有可辨識的結構、每個位元組的值分布很均勻——那才大概率是加密的產物。當然，最可靠的判斷還是回到 JavaScript：找到那個解密呼叫，比在猜測裡打轉快得多。

還有一個邊界值得先講清楚：本節說的「洗乾淨」只處理運輸層，不處理加密本身。引號、URL-safe 字元集都是運輸時套上的包裝；真正的鎖是加密演算法，那是後面幾步的事。把兩層分開看，你就不會在解不出東西時，錯把運輸問題當成演算法問題。

這一步的輸出，就是下一步的輸入

把整節收攏成一條流程：先看位置——整段 body、JSON 欄位，還是連請求都要加密；再看包裝——引號要剝掉、URL-safe 要換回標準字元集；最後把得到的字串 b64decode 成乾淨的密文位元組。這包位元組就是下一節的原料。

三個案例其實是同一條流水線上的三個檢查點：福建示範「欄位密文」，招標網示範「整段密文加引號」，有道示範「URL-safe 變體」。真實網站頂多是這些變體的組合——例如「欄位密文 + URL-safe」——只要按位置、包裝、解碼的順序逐項檢查，組合再多也不會亂。

小結

解密的第一步是把密文洗成乾淨的位元組。先判斷位置：整段響應體就是密文、密文躲在 JSON 欄位裡，或連請求 body 都要加密；再清掉運輸包裝：被引號包住的用 strip('"') 剝掉，URL-safe base64 把 -、_ 換回 +、/；最後才 b64decode。注意 base64 只是編碼不是加密，判斷是不是密文要看解碼後的位元組像不像亂數。
