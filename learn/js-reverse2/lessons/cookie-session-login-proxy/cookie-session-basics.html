Cookie 與 Session：HTTP 無狀態怎麼維持登入？

Step 1/5 · 會話維持：Cookie、登入、代理與驗證碼

學習目標

能說出 Cookie 為何存在、它以什麼形式在客戶端與伺服器之間流動，並解釋 requests.Session 如何自動承接這條狀態線。

前言：同一個網址，瀏覽器認得你、程式卻不認得

你有沒有遇過這種落差：在瀏覽器裡登入一個網站，把分頁關掉、過一陣子再打開，你還是處於登入狀態；但改用 requests 抓同一個頁面，伺服器卻像完全不認識你，回傳的是「請先登入」。明明送出的網址一模一樣，為什麼結果差這麼多？

答案不在網址，而在一個每次請求都悄悄跟著你的小東西：Cookie。這一節要把 Cookie 與 Session 這條「伺服器怎麼認得你」的線講清楚。搞懂之後，你才會知道為什麼爬蟲只要少帶了它，就會被當成陌生人。

HTTP 是一套沒有記憶的協定

先從問題的根源講起。HTTP 有個很根本的設計：每一個請求都是獨立的，伺服器處理完就忘。第一個請求說「我是小明」，第二個請求如果不重講一次，伺服器不會記得第一個請求講過什麼。這種「不記得前一次」的特性，叫做無狀態（stateless）。

無狀態其實是優點，伺服器不用為每個使用者保留一條連線，要擴充機器也很容易。但它的副作用對登入來說是致命的：你剛剛送了帳號密碼、登入成功，下一個請求想要抓自己的訂單列表，伺服器卻完全不知道你是誰。如果每個請求都要重送一次帳密，那這個網站根本不能用。

Cookie：櫃檯發給你的一張號碼牌

網站的解法，是在你登入成功的那一刻，由伺服器建立一組資料回傳給客戶端，瀏覽器把它存在本機，之後你再造訪同一個伺服器時，瀏覽器會自動把這組資料一起送出去。伺服器比對一下，就知道「是你回來了」。這組由伺服器建立、存在客戶端的鍵值對，就是 Cookie。

你可以把 HTTP 想成一間沒有記憶的櫃檯，每次去都得重新報一次身分。Cookie 則是櫃檯在你第一次驗證身分後發的號碼牌：之後每次上門，只要亮出號碼牌，櫃檯就認得你，不必再報一次帳號密碼。最典型的效果就是網站的「免密碼登入」，你關掉瀏覽器再回來，仍然是登入狀態。

這裡有兩個一定要記住的重點。第一，Cookie 是伺服器建立的，不是你高興就能自己捏一組有效的值出來。第二，它存在客戶端，也就是你的瀏覽器裡；不同瀏覽器的 Cookie 各自獨立、不會互通，所以你在 Chrome 登入，不會讓你 Safari 也自動登入。

Session：伺服器端的登入狀態，與爬蟲端的皮夾

伺服器要認人，靠的是 Cookie 裡那組識別資訊，實際上通常是一個 session id，對應到伺服器端保存的登入狀態。「Session」這個詞在這裡指的就是伺服器端的「這次工作階段」，也就是你登入之後的那段狀態。但爬蟲沒有瀏覽器，不會自動幫你存 Cookie，也不會自動帶。

requests.Session() 就是拿來模擬「瀏覽器那個皮夾」的角色。它是一個工作階段物件，會追蹤並保存伺服器發給你的 Cookie：你用同一個 Session 發請求，伺服器若在回應裡透過 Set-Cookie 發下 Cookie，Session 就自動收進口袋；之後你再用同一個 Session 發請求，它會自動把口袋裡的 Cookie 帶上。存 Cookie、帶 Cookie 這兩件雜事，它都幫你自動化了。

有一個關鍵限制要特別注意：Session 至少要發兩次請求。第一次請求的目的是讓伺服器把 Cookie 發下來、存進 Session；從第二次起，才是真正「帶著 Cookie」的請求。如果你只發一次就想拿到登入後的資料，通常會失敗，原因就在這裡。

小結

HTTP 是無狀態的，所以網站用 Cookie 當識別證來維持登入。Cookie 由伺服器建立、存在客戶端，之後的請求會自動帶上；伺服器端則靠 session id 對應到你的登入狀態。requests.Session 是爬蟲端的皮夾，幫你自動存下與送出 Cookie，代價是至少要先發一次請求把 Cookie 收進來。

理解了 Cookie 與 Session 的原理，下一個問題很實際：既然兩種方式都能把 Cookie 帶上，那我到底該自己手動把 Cookie 塞進標頭，還是直接交給 Session 自動處理？下一節會把這兩條路攤開來比較，給你一條清楚的判準。
