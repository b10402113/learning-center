這行是在加密還是在簽章？認出 bundle 裡的 RSA

Step 1/5 · 案例：非對稱（RSA）

學習目標

看到一段 bundle 程式碼，能分辨它是 RSA 加密還是 RSA 簽章、認出鑰匙的兩種呈現形態，並讀懂加密參數在說什麼。

前言：找到加密入口，卻看不懂它在做什麼

你在 DevTools 裡追了半小時，終於在一個 webpack 模組裡找到產生加密參數的函式。畫面上有 encrypt、有一長串 MIIBIjANBgkqhkiG9w0BAQEF… 開頭的字串、還有一個寫著 10001 的變數。你把函式抄下來，卻在下一個岔路卡住：這段程式碼到底是在「把內容藏起來」，還是在「替內容蓋章」？如果是加密，鑰匙在哪裡？如果是簽章，伺服器又在驗證什麼？

這個判斷決定了整條逆向路線的方向。把簽章當成加密的人，會花半天尋找「解密函式」——簽章根本沒有解密這回事，方向錯了永遠找不到。把加密當成簽章的人，會試圖「還原」一段其實只有伺服器私鑰能解開的密文，同樣注定失敗。所以在動手重現之前，先練一雙眼睛：看懂 RSA 在真實 bundle 裡的長相。

這篇文章會用三個真實案例的片段——外貿電商平台、沃郵箱、理財網——帶你練這雙眼睛。三個案例分別代表 RSA 的兩種任務與鑰匙的兩種呈現形態，之後四個步驟會各挑一個實際跑通。

先看三段真實的呼叫長什麼樣

與其先背定義，不如直接看程式碼。下面三段分別來自三個真實網站的 bundle，都是一行就完成加密或簽章的呼叫。

第一段來自外貿電商平台的 loader 尾端。作者在檔案最後留了一行測試碼，呼叫模組 MuMZ 的 a 方法：

三段都跟 RSA 有關，但做的事不一樣。第一、二段是「拿鑰匙把內容鎖起來」，第三段是「拿鑰匙替內容蓋章」。要分辨它們，看的不是函式叫什麼名字——encrypt、a、get_sign 都只是作者取的名——而是兩件事：哪把鑰匙進去了，以及伺服器收到後做什麼。

RSA 的兩種任務：上鎖與蓋章

非對稱加密（asymmetric encryption）的核心是一對鑰匙：公鑰（public key）和私鑰（private key）。這對鑰匙的關係很特別——公鑰鎖起來的東西只有私鑰打得開，反過來私鑰蓋的章只有公鑰驗得了。兩把鑰匙角色完全不同，因此同一套 RSA 數學可以用在兩種任務上。

第一種任務是加密：前端拿公鑰把要送出的內容鎖起來，網路攔截者看到的只有一團密文，伺服器收到後用自己的私鑰解開。公鑰人人可得，所以你可以在 bundle 裡大方找到它——公開公鑰不會造成洩漏，這正是它設計上的美感。

第二種任務是簽章：前端拿私鑰替請求內容算出一組「印章」，伺服器用公鑰驗章。驗得過，代表這份內容確實出自持有私鑰的人、而且中途沒被改過。這裡的重點不是「藏」，而是「證明」——就像合約上的簽名，內容本身是公開的，簽名證明的是來源與完整性。

把兩種任務放在一起比較，差異就清楚了：

公鑰加密私鑰簽章
前端持有的鑰匙公鑰（可公開）私鑰（本應保密）
前端做的事把內容鎖成密文替內容算出簽章
伺服器做的事用私鑰解開密文用公鑰驗證簽章
保護的目標內容的機密性內容的完整性與來源
逆向者能做什麼只能加密，解不開伺服器的資料若私鑰在前端，可偽造任意簽章

一個好記的譬喻：公鑰加密像掛鎖。鎖（公鑰）可以發給所有人，任何人把東西鎖進箱子都行，但只有持鑰匙的人（私鑰）開得了。私鑰簽章像印章。印章本該鎖在抽屜裡，蓋出去的章人人都能拿公鑰比對真偽；如果印章被複製了，街上每個人就都能蓋出「真跡」——這正是後面第五步要談的失效模式。

鑰匙的兩種呈現形態

知道了任務分兩種，接著要認的是「鑰匙長什麼樣」。在真實 bundle 裡，RSA 鑰匙以兩種形態出現，看到哪一種，找鑰匙的方法就不一樣。

第一種是 PEM 格式——一段用 -----BEGIN …----- 和 -----END …----- 夾住的 Base64 文字。外貿電商平台的公鑰就是這樣直接寫死在模組裡的：

第二種是拆開的兩個數字：模數（modulus，一個很長的十六進位字串）和指數（exponent，幾乎總是 10001）。沃郵箱的測試碼就是這個形態——變數 o 是模數，變數 n 是指數。10001 是十六進位，換算成十進位是 65537，也就是 RSA 公鑰最常用的指數。你可以在心裡把它當成「公鑰被拆成兩半存放」：模數決定鑰匙的長度（那串十六進位有 256 個字元，代表 1024-bit），指數是固定慣例。

為什麼有的站用 PEM、有的站用模數加指數？取決於前端用哪套加密庫。喜歡用 JSEncrypt 這類輕量庫的站，往往直接存 setPublicKey 要吃的兩個字串；用 jsrsasign 這類完整套件的站，則習慣整段 PEM 丟給 getKey。認得兩種形態，就不會在「找不到 BEGIN 字樣」時誤判成沒有鑰匙。

參數在說什麼

認出鑰匙之後，最後一塊拼圖是加密參數。RSA 只是一組數學，真正決定「怎麼填、怎麼混、輸出長什麼樣」的是包在它外面的參數。三個案例的參數都寫在呼叫點上，白紙黑字：

參數意思在哪裡看到
"RSA-OAEP"加密的填充模式：OAEP，帶隨機性，每次輸出都不同外貿電商平台
{md: sha256, mgf1: {md: sha1}}OAEP 內部的雜湊用 SHA-256，遮罩產生函式用 SHA-1外貿電商平台
"SHA256withRSA"簽章配方：先算 SHA-256 雜湊，再用 RSA 私鑰簽它理財網
'10001'公鑰指數，十六進位的 65537沃郵箱

外貿電商平台的參數是這樣出現的——在剛剛那行 PEM 的結尾接續著：

            var t = i.pki.publicKeyFromPem("-----BEGIN PUBLIC KEY-----\n …\n  -----END PUBLIC KEY-----").encrypt(e, "RSA-OAEP", {
                md: i.md.sha256.create(),
                mgf1: {
                    md: i.md.sha1.create()
                }
            });
            return window.btoa(t)

這些參數不是裝飾。填充模式若抄錯（例如用 PKCS#1 v1.5 重現 OAEP），伺服器解開會直接失敗；雜湊若抄錯（SHA-256 換成 SHA-1），OAEP 的遮罩就對不上，同樣解不開。所以正確的逆向流程是：參數照抄，一個都不放過。

另外注意最後那行 window.btoa(t)——RSA 加密出來是二進位資料，塞進 HTTP 參數前還要再包一層 Base64。真實站的加密結果幾乎都是「加密 → 編碼」的兩層包裝，拆的時候要記得剝到底。

一條判讀路徑

把上面的線索串成一條能在幾分鐘內走完的判讀路徑。看到一段疑似 RSA 的程式碼，依序問自己四個問題：

  1. 呼叫的名字不重要，看它「進什麼、出什麼」。明文進、一團固定長度的亂碼出，是加密；字串進、簽章出且同一份資料結果固定，是簽章。
  2. 找鑰匙形態。有 BEGIN … KEY 字樣就是 PEM；有長十六進位字串加 10001 就是模數加指數。
  3. 看鑰匙的身分。BEGIN PUBLIC KEY 是公鑰；BEGIN PRIVATE KEY 是私鑰。這一行決定後面所有事情。
  4. 抄下全部參數。填充模式、雜湊、指數、輸出包裝，一個都不漏。

這條路徑跟前面學過的觀念直接相連：鑰匙的公私角色來自「對稱與非對稱加密」那節的兩把鑰匙模型；window.loader("MuMZ") 這種呼叫方式，則是 webpack 拆解那節留下的模組定位手法——作者把測試碼留在 loader 尾端，等於直接告訴你加密模組的 ID。

小結

RSA 在 bundle 裡做兩種事：公鑰加密（把內容鎖起來給伺服器解）與私鑰簽章（替內容蓋章給伺服器驗）。鑰匙有兩種形態：PEM 字串與模數＋指數（10001 就是 65537）。判讀順序是：看進出、找鑰匙形態、認鑰匙身分、抄全參數——填充模式與雜湊抄錯，重現一定失敗。
