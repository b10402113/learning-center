外貿電商平台：把公鑰抽出來，用 Python 重現 RSA-OAEP

Step 2/5 · 案例：非對稱（RSA）

學習目標

從外貿電商平台的 bundle 抽出 2048-bit 公鑰 PEM，在 Python 重現 RSA-OAEP（SHA-256、MGF1-SHA1）加密與 base64 包裝。

前言：一團只有伺服器解得開的密文

上一步練的是眼睛——認出 bundle 裡的 RSA 在做什麼。這一步開始動手，而且是三個案例中最乾淨的一個：外貿電商平台把整把公鑰、整個加密流程都寫在同一個模組裡，沒有混淆、沒有藏，簡直像靶場。

先講清楚目標與前置條件。做完這一步，你會得到一支 Python 函式：丟進任何字串，吐出這個平台伺服器收得下的加密欄位——伺服器用自己的私鑰解開後能拿到你指定的內容。動手前需要三樣東西：webpack 的模組定位基本功（知道 window.loader 是什麼）、能跑的 Node 環境（用來驗證）、以及 Python 的 cryptography 套件（pip install cryptography）。

順帶一提這個平台的設計：它把「公鑰加密」用在請求上——前端把要送出的內容鎖起來，只有伺服器的私鑰開得了。這代表你永遠解不開別人的密文，但也代表你可以對伺服器偽造任何內容。這條界線第五步會再回來談，現在先把重現跑通。

步驟一：從 loader 尾端的測試碼鎖定模組

作者在 loader 檔案的最後留了一行測試碼。逆向時這種「作者自己留下的煙火」價值連城——它直接告訴你加密入口在哪：

// console.log(window.loader)
console.log(window.loader("MuMZ").a("123"))

這行話說得很明白：加密模組的 ID 是 "MuMZ"，呼叫的導出方法是 a，丟字串進去、拿加密結果出來。用上一節的判讀法看「進什麼、出什麼」——字串 "123" 進去，一團亂碼出來，這是加密。

預期看到什麼：把這行放進 Node 跑（先載入 loader 與模組檔、補上 window 等環境），會印出一長串 Base64。同一個輸入 "123"，每次跑結果都不一樣——這是 OAEP 的隨機性，不是你哪裡做錯。

步驟二：打開模組，讀加密配方

用模組 ID 在應用程式主檔（mod1.js）裡搜尋，找到 MuMZ 的定義。整個模組不到三十行，加密配方全寫在臉上：

            return o

        n.d(t, "b", function() {
            return r

            var t = i.pki.publicKeyFromPem(

逐行拆開看：n.d(t, "a", …) 把函式 o 導出成 a、r 導出成 b（b 是另一個 MD5 雜湊小工具，這一步用不到）；var i = n("XBrZ") 是依賴注入——模組 XBrZ 就是著名的加密庫 jsrsasign，一個純 JavaScript 實作的 RSA 與 X.509 工具組。認出這點很關鍵：jsrsasign 的 API 形狀是固定的，看到 pki.publicKeyFromPem、md.sha256.create 就知道該查它的文件。

三個重點。第一，OAEP 的雜湊 md 是 SHA-256。第二，遮罩產生函式（MGF1，mask generation function，OAEP 內部用來擴充隨機數的機制）用的雜湊是 SHA-1——兩個雜湊不一樣，這是 jsrsasign 的預設組合，也是最容易抄錯的地方。第三，加密結果還要過 window.btoa(t)，也就是 Base64 編碼後才送出去，因為 RSA 輸出是二進位，塞進 HTTP 欄位前必須轉成文字。

步驟四：在 Python 重現同一個流程

配方齊了：2048-bit 公鑰、RSA-OAEP、SHA-256 雜湊、MGF1-SHA1、最後 Base64。用 cryptography 套件照抄：

import base64
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric import padding
from cryptography.hazmat.primitives import hashes

PEM = b"""-----BEGIN PUBLIC KEY-----
MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEAsy4xppPDUT2eAOR5h0cyydzxtKB9O80A

IMElxYAVvmsDy0I7RCUTrajetKjX94Q+JuQUxnIHNC3IVtYsl1x0lNRtb93IhlRCkZ9djOu350eq
hZIOXQIDAQAB
-----END PUBLIC KEY-----"""

public_key = serialization.load_pem_public_key(PEM)


def encrypt(plaintext: str) -> str:
    ciphertext = public_key.encrypt(
        plaintext.encode(),
        padding.OAEP(
            mgf=padding.MGF1(algorithm=hashes.SHA1()),
            algorithm=hashes.SHA256(),
            label=None,
        ),
    )
    return base64.b64encode(ciphertext).decode()

三個參數跟 JS 端一一對應：algorithm=hashes.SHA256() 是 md: sha256，MGF1(SHA1) 是 mgf1: {md: sha1}，label=None 對應 jsrsasign 沒傳 label 的預設。少一個、錯一個，伺服器解開就失敗。

另一條路是直接重用 bundle 內建的庫：把 loader 與模組檔載入 Node、補上 window 之類的環境，然後照作者的測試碼呼叫 window.loader("MuMZ").a(明文)。這條路勝在「不可能抄錯參數」，缺點是每次執行都要拖著整包模組跑。兩條路怎麼選，第五步會給完整的抉擇表；眼下先確保 Python 路能獨立跑通。

警告：別用「密文比對」當驗證

這一步最常見的挫折是：Python 跑出來的密文跟 Node 跑出來的對不上，於是開始懷疑自己抄錯參數。先別急著改參數。RSA-OAEP 的填充自帶隨機數，同一段明文每次加密的輸出必然不同——這是設計，不是 bug。你拿兩團密文直接比字串，永遠不會相等。

正確的驗證方式有兩種。最實在的一種：把 Python 加密出來的欄位送進真實請求，看伺服器收不收、回不回正常資料。另一種是自己生成一組測試金鑰，用私鑰解開 Python 的輸出，確認解得回原文。參數錯了會在「伺服器解不開」時立刻現形；參數對了則每一團密文都能解回原文。

做完長什麼樣

可驗證的結果長這樣：encrypt("123") 回傳一串 344 個字元左右的 Base64（2048-bit 密文固定 256 位元組，Base64 後約 344 字元），丟進請求欄位後伺服器正常回應；再送一次請求，密文不同但伺服器同樣正常回應。至於 OAEP 內部的數學為什麼要兩個雜湊、MGF1 在擴充什麼，那是密碼學理論的地盤——重現只需要照抄，理解它不是這一步的任務。

小結

外貿電商平台把 RSA 公鑰加密寫在模組 MuMZ：jsrsasign 的 publicKeyFromPem 載入寫死的 2048-bit 公鑰，用 RSA-OAEP（SHA-256 雜湊、MGF1-SHA1）加密，最後 window.btoa 包一層 Base64。Python 重現就是照抄這四件事；驗證要看伺服器收不收，不能比密文字串，因為 OAEP 每次輸出都不同。

這個案例的鑰匙是整段 PEM。但不是每個站都這樣大方——下一個案例沃郵箱連 PEM 都沒有，只給你一串十六進位長字串和 10001，得先把「拆開的公鑰」拼回來才能動手。
