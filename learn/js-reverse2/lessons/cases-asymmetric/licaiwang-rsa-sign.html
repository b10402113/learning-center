理財網：RSA-SHA256 簽章與一個必須對齊的 JSON 細節

Step 4/5 · 案例：非對稱（RSA）

學習目標

對理財網重現 RSA-SHA256 簽章，對齊 JSON 序列化細節，並把簽章放進 signature header 送出請求。

前言：換一個查詢條件，簽章就換一張臉

前兩個案例都是同一種任務：拿公鑰把要送出的內容鎖起來。理財網（中國理財網的產品清單 API）把方向反了——請求內容是明文可見的，但每個請求都得附上一張「印章」放在 signature 標頭裡。你在 DevTools 裡換個頁碼重新發請求，那串簽章就整個換掉；把簽章設成固定值，伺服器直接拒絕。

這就是簽章任務的長相：它不藏內容，它證明內容出自持有私鑰的人、而且沒被改過。而這個案例最值得玩味的地方在——那把「本該保密」的私鑰，就明文寫在 bundle 裡。這件事的意義第五步專門收網，眼下先把它當成一把好用的鑰匙，把簽章流程完整跑通。

前置條件：會用 webpack 模組定位找函式、Node 與 execjs 環境就緒、Python 裝了 cryptography。做完會得到一支 get_sign(payload)：丟進請求參數的字典，吐出伺服器驗得過的簽章字串。

步驟一：從 Python 端看整條呼叫鏈

這個案例的原始碼附了完整的 Python 重現腳本，直接從它讀起最清楚。簽章、標頭、請求體三件事一次看全：

sign = execjs.compile(open("04 理财网.js").read()).call("get_sign", data)
print("sign:::", sign)

headers["signature"] = sign

話說得很明白：簽章函式叫 get_sign，吃一份參數字典 data；算出的字串放進 signature 標頭。請求體的寫法也有玄機：

response = requests.post(
    'https://xinxipilu.chinawealth.com.cn/lcxp-platService/product/getProductList',
    cookies=cookies,
    headers=headers,
    # params: GET请求的查询数据
    # data=data,  # data默认将字典处理成form表单的字符串格式（a=1&b=2）
    # json=data,  # json=data是将字典处理成json字符串格式（{"a":1,"b":2}）
    data=json.dumps(data, separators=(",", ":"))
)

作者特別註解了 data=、json= 兩種寫法都不能用，最後選 data=json.dumps(data, separators=(",", ":"))。原因下一步揭曉——簽章簽的是「這份 JSON 字串」，而 requests 的兩種自動序列化都可能產出跟 JavaScript 不同的字串（多空白、多逗號），字串不同，簽章就對不上。

步驟二：讀簽章配方——SHA256withRSA

打開 04 理财网.js，拉到檔案最尾端（大約七萬九千行之後），有一段人工追加的程式碼——這就是逆向者自己從 bundle 抽出來的簽章核心：

function Me(e, t) {
    const o = He.KEYUTIL.getKey(t)
        , n = new He.KJUR.crypto.Signature({
        alg: "SHA256withRSA"
    });
    return n.init(o),
        n.updateString(e),
        He.hextob64(n.sign())
}

五個動作，每個都對得上 jsrsasign 的標準 API（這裡的 He 就是 bundle 裡的 jsrsasign 實例）：

  1. He.KEYUTIL.getKey(t)：把引數 t 解析成金鑰物件——傳 PEM 字串進去，它自動認出是公鑰還是私鑰。
  2. new He.KJUR.crypto.Signature({alg: "SHA256withRSA"})：建立簽章器，配方是 SHA256withRSA——先對訊息算 SHA-256 雜湊，再用 RSA 私鑰簽那個雜湊。
  3. n.init(o)：用剛才解析出的金鑰初始化。
  4. n.updateString(e)：送入要簽的字串。
  5. He.hextob64(n.sign())：sign() 吐出十六進位的簽章，hextob64 轉成 Base64 後回傳。

對照第一步的判讀法：字串進、簽章出，同一份資料結果固定——這是簽章不是加密。SHA256withRSA 這個參數白紙黑字寫在那裡，等於作者直接告訴你配方，剩下的是照做。

步驟三：get_sign 與寫死的私鑰

呼叫端 get_sign 把配方和金鑰組合起來：

function
get_sign(data) {
…
    i = JSON.stringify(data)
    r = Me(i, n);
    return r
}

（原本夾在中間的那行是 let n = "-----BEGIN PRIVATE KEY----- … -----END PRIVATE KEY-----"——一把寫死的 2048-bit 私鑰 PEM，字串太長，這裡省略。）

兩個細節決定成敗。第一，被簽的不是「參數」這個抽象概念，而是 JSON.stringify(data) 產出的那個具體字串。伺服器驗章時拿的是它自己組出來的 JSON 字串，兩邊字串必須逐字元一致。第二，getKey 收到的是 BEGIN PRIVATE KEY——私鑰。簽章流程本該由私鑰持有者執行，而這裡私鑰隨著前端程式碼發給了每一個訪客。

步驟四：序列化細節必須逐字元對齊

簽章對不上，十次有九次不是 RSA 算錯，而是 JSON 字串不一樣。回到第一步那行 json.dumps(data, separators=(",", ":"))，三個細節缺一不可：

  • 不能有空白。JSON.stringify 的預設輸出是緊湊格式 {"a":1,"b":2}；Python 的 json.dumps 預設卻是 {"a": 1, "b": 2}（多了空格）。separators=(",", ":") 就是為了把冒號和逗號後的空格去掉。
  • 鍵的順序要一致。簽的是字串，鍵順序不同字串就不同。Python 的字典保留插入順序，所以腳本裡字典的書寫順序要跟 JS 端一致。
  • null 要對得上。JS 的 null 對 Python 的 None，json.dumps 會正確輸出 null——但若是日期、浮點數之類的型別，兩邊格式可能有細微差異，要逐一核對。

可以把它想成對照兩張紙的影本：簽章蓋在「這張紙的內容」上，影本差一個空格就是另一張紙，印章自然驗不過。

步驟五：不走 execjs 的 Python 重現

execjs 路線是最快驗證想法的方式，但長期維護可以乾脆用 Python 直接算。配方是標準的 PKCS#1 v1.5 簽章加 SHA-256：

import base64
import json
from cryptography.hazmat.primitives import hashes, serialization
from cryptography.hazmat.primitives.asymmetric import padding

private_key = serialization.load_pem_private_key(
    PRIVATE_KEY_PEM,  # bundle 裡那把 -----BEGIN PRIVATE KEY----- 字串
    password=None,
)


def get_sign(payload: dict) -> str:
    message = json.dumps(payload, separators=(",", ":")).encode()
    signature = private_key.sign(message, padding.PKCS1v15(), hashes.SHA256())
    return base64.b64encode(signature).decode()

private_key.sign 吃的是原始訊息位元組，內部自己算 SHA-256 再簽——跟 jsrsasign 的 SHA256withRSA 是同一件事。輸出的簽章位元組直接 Base64，對應 JS 端的 hextob64。

驗證比前兩個案例舒服得多：PKCS#1 v1.5 簽章是確定性的——同一份資料、同一把私鑰，簽出來的字串每次都一樣。所以你可以拿同一份 payload 分別餵 JS 和 Python，逐字元比對簽章；相等就代表重現正確。最後把簽章放進 signature 標頭、請求體用緊湊 JSON 送出，附上 JSESSIONID cookie 與 Content-Type: application/json;charset=UTF-8，伺服器就會正常回產品清單。

做完長什麼樣

可驗證的結果：get_sign(payload) 回傳一串 344 字元左右的 Base64（2048-bit 簽章 256 位元組）；同一 payload 重算結果恆定；貼進 signature 標頭送出請求，拿到 200 與產品清單 JSON。改任何一個參數——換頁碼、換關鍵字——簽章跟著變，因為被簽的字串變了。

小結

理財網用 RSA-SHA256 對 JSON.stringify(data) 的字串簽章，簽章放進 signature 標頭。配方是 jsrsasign 的 SHA256withRSA：SHA-256 雜湊加 PKCS#1 v1.5 簽名，輸出從 hex 轉 Base64。重現的成敗在序列化：緊湊 JSON、鍵順序、null 都要跟 JS 逐字元對齊。簽章是確定性的，可以直接比對驗證——但別忘了，簽章用的私鑰就寫死在 bundle 裡。

三個案例跑完了：外貿的公鑰 PEM、沃郵箱的模數加指數、理財網寫死的私鑰。同樣是 RSA，站方把哪把鑰匙放上前端，決定了這層保護到底擋住了誰——也決定了你的重現該走哪條路。下一步把三案並排，做最後的判斷與抉擇。
