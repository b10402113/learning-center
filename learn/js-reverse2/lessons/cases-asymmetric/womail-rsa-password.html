沃郵箱：沒有 PEM 的 RSA——從 modulus 與 exponent 還原公鑰

Step 3/5 · 案例：非對稱（RSA）

學習目標

從沃郵箱的 bundle 抽出 modulus 與 exponent，在 Python 重現 PKCS#1 v1.5 密碼加密與 #! 前綴包裝。

前言：找不到 BEGIN 字樣，就沒有金鑰嗎

上一步的外貿電商平台很客氣：整段 PEM 公鑰明文寫在模組裡，複製貼上就完事。這一步的沃郵箱（中國聯通的信箱服務）就沒這麼好說話——你在 bundle 裡搜尋 BEGIN、搜尋 KEY，什麼都找不到，只看到一串兩百多字元的十六進位字串，和一個孤零零的 10001。

這是鑰匙的第二種形態：模數（modulus）加指數（exponent）。公鑰被拆成兩個數字存放，等你要自己把它拼回來。這個案例的任務也換了——不是加密一般請求參數，而是登入密碼：使用者輸入的密碼在送出前先用公鑰鎖起來，連站方內部的人從網路流量上也看不到明文密碼。重現它，你的爬蟲才能登入。

前置條件同步驟二：webpack 模組定位基本功、Python 的 cryptography 套件。做完會得到一支 hash_password()：丟進密碼字串，吐出這個平台登入表單收得下的欄位值。

步驟一：讀 loader 尾端的環境測試

入口又在 loader 的尾巴。作者留下的環境測試顯示了完整呼叫形狀：

// 环境测试
let t = "asdasdasd"
let o = 'e3873eb7dea99b6c0c85f9e543a7dfaa7e6f90f5794c99dadf04326673437258174a2489fe12c75f4b81af37e60f152a0bd1180e9b959784dfbdc2e95ee48e927a6c09fa0037275290b2d475bd574dcbade9492181c6f5f56b96d74148498deae93d5b7ae3b8eb965ffc4c71efa671accda941db64d3e29907c2b42e0b365e0d'
let n = '10001'
console.log(window.loader(437).encrypt(t, o, n))

讀出三件事。第一，加密模組的 ID 是 437（數字 ID，不是上一個案例那種字串 ID）。第二，呼叫的是 encrypt，吃三個參數：明文 t、一長串十六進位的 o、以及 n = '10001'。第三，第三個參數是十六進位寫法的 65537——RSA 公鑰指數的標準值。

把這三個參數對回上一步學的形態判讀：長十六進位字串加 10001，就是模數加指數，一組公鑰被拆開存放。這串 e387… 是測試用的金鑰，作者拿它驗證環境跑得動；真正登入要公鑰長什麼樣，得打開模組才看得到。

步驟二：打開模組 437，看密碼怎麼被包起來

用 ID 437 搜尋模組檔，定義不到三十行：

    437: function(t, e, n) {
        var i = n(595)
          , o = 'C4E3F7212602E1E396C0B6623CF11D26204ACE3E7D26685E037AD2507DCE82FC\n28F2D5F8A67FC3AFAB89A6D818D1F4C28CFA548418BD9F8E7426789A67E73E41';
        function r(t, e, n) {
            var r = new i;
            return r.setPublic(e, n),
            r.encrypt(t)
        }
        t.exports = {
            encrypt: r,
            hashPassword: function(t) {
                return t ? '#!' + r(t, o, '10001') : ''
            },

逐行拆開。var i = n(595) 注入模組 595——一個 JSEncrypt 風格的 RSA 類別（下一節看它的 API 就知道）。變數 o 是站方真正的公鑰模數：一串 256 字元的十六進位（1024-bit），原始碼折行處夾了換行符號。r(t, e, n) 是三步流程：建立 RSA 物件、setPublic(e, n) 設定公鑰、encrypt(t) 加密。

重點在 hashPassword：登入時呼叫的是它，不是裸的 encrypt。它做了兩件事——用寫死的模數 o 與指數 '10001' 加密密碼，然後在密文前面拼上 #! 兩個字元。空密碼直接回傳空字串（t ? … : ''），這是短路保護，避免送出 #!null 之類的怪東西。

所以密碼欄位的完整格式是：#! 加密結果。這層前綴是「包裝」不是「加密」——就像上一節說的，加密做完後外面常常還要再裹一層運輸格式，拆的時候要剝乾淨。

步驟三：認填充模式與輸出格式

模組 595 的 RSA 類別是經典的 jsbn／JSEncrypt 實作。看兩個方法就知道加密細節：

        r.prototype.setPublic = function(t, e) {
            if (!(null != t && null != e && 0 < t.length && 0 < e.length))
                throw new Error('Invalid RSA public key');
            this.n = u(t, 16),
            this.e = parseInt(e, 16)
        }

setPublic 吃的就是上一步認得的那對數字：模數字串以十六進位解析（u(t, 16)），指數字串也以十六進位解析（parseInt(e, 16)）——所以 '10001' 是 65537，不是一萬零一。再看 encrypt 的填充與收尾：

        r.prototype.encrypt = function(t) {
            var e = function(t, e) {
                …
                n[--e] = 0;
                for (var o = new l, s = new Array; 2 < e; ) {
                    for (s[0] = 0; 0 == s[0]; )
                        o.nextBytes(s);
                    n[--e] = s[0]
                }
                return n[--e] = 2,
                n[--e] = 0,
                new c(n)
            }(t, this.n.bitLength() + 7 >> 3);
            …
            var r = n.toString(16);
            return 0 == (1 & r.length) ? r : '0' + r
        }

中間那段是 PKCS#1 v1.5 的填充（encryption padding type 2）：明文後面補一個 0 分隔、一串不為零的隨機位元組、再補上 2 與 0 兩個標記位元組。這種填充也帶隨機數，所以跟 OAEP 一樣，同一段明文每次密文都不同。

結尾兩行是格式關鍵：加密結果用 toString(16) 轉成十六進位字串輸出，長度若是奇數就補一個 0。這代表 #! 後面跟的是 hex，不是 Base64——跟外貿案例剛好相反。辨認特徵很明確：只有 0-9a-f、長度固定（1024-bit 金鑰的密文是 128 位元組，hex 後 256 字元）。

步驟四：在 Python 重現

配方：1024-bit 公鑰（模數 C4E3… 加指數 65537）、PKCS#1 v1.5 填充、輸出 hex、加上 #! 前綴。Python 照抄：

from cryptography.hazmat.primitives.asymmetric import rsa, padding

N = int(
    "C4E3F7212602E1E396C0B6623CF11D26204ACE3E7D26685E037AD2507DCE82FC"
    "28F2D5F8A67FC3AFAB89A6D818D1F4C28CFA548418BD9F8E7426789A67E73E41",
    16,
)
E = 0x10001

public_key = rsa.RSAPublicNumbers(E, N).public_key()


def hash_password(password: str) -> str:
    if not password:
        return ""
    ciphertext = public_key.encrypt(password.encode(), padding.PKCS1v15())
    return "#!" + ciphertext.hex()

三個細節決定成敗。第一，模數在 JS 原始碼裡是折行的（字串中夾著換行），搬到 Python 時要把換行去掉再轉整數——int() 碰到換行會直接報錯。第二，指數用 0x10001 或 65537 都行，但不能寫成十進位的 10001。第三，填充是 PKCS1v15() 不是 OAEP()——上一案例的參數不能沿用，這就是為什麼「參數照抄、不憑印象」是鐵則。

另一條路是重用 bundle：載入 loader 與模組檔後呼叫 window.loader(437).hashPassword(密碼)，一步到位，連前綴都幫你加好。或者照作者測試碼的形狀呼叫 encrypt(明文, 模數, 指數) 自己組合。三條路的取捨第五步統一談。

警告：兩件會讓你白忙的事

第一，別拿密文字串互相比對。PKCS#1 v1.5 填充自帶隨機位元組，同一個密碼每次加密結果不同——驗證要看登入成不成、或自己生成測試金鑰解回原文。

第二，別把輸出當 Base64 處理。這個案例的密文是 hex；你若照外貿案例的慣性套上 base64.b64encode，伺服器只會回你一個登入失敗。包裝格式永遠從程式碼裡讀，不從習慣裡推。

做完長什麼樣

可驗證的結果：hash_password("asdasdasd") 回傳一個以 #! 開頭、總長 258 字元的十六進位字串（#! 加 256 字元）；把它填進登入表單的密碼欄位送出，伺服器驗得過、登入成功。空密碼回傳空字串，跟 JS 的短路行為一致。

小結

沃郵箱的公鑰沒有 PEM，只有模數加指數：256 字元十六進位的 modulus 配 '10001'（65537）。模組 437 的 hashPassword 用 JSEncrypt 風格的 setPublic 組回公鑰，以 PKCS#1 v1.5 加密密碼，輸出是 hex 且前面加 #!。Python 用 RSAPublicNumbers 組公鑰、PKCS1v15 填充即可重現，注意換行與十六進位指數兩個陷阱。

兩個案例都是「公鑰加密」——你只能鎖、不能開。下一個案例理財網把方向反過來：它拿私鑰對請求簽章，而那把私鑰就大剌剌寫在 bundle 裡。任務換了，眼睛要重新對焦。
