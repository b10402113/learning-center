私鑰在前端：這層保護到底擋住了誰？

Step 5/5 · 案例：非對稱（RSA）

學習目標

判斷一個 RSA 保護真正擋住了什麼——特別是「私鑰在前端」的失效模式——並在重用 bundle、execjs、Python 重寫三條重現路線中做選擇。

前言：你手上有三把鑰匙，但它們的價值天差地遠

三個案例跑完，你的戰利品攤在桌上：外貿電商平台的一段公鑰 PEM、沃郵箱的一組模數加指數、理財網的一整把私鑰。同樣是「逆向成功、參數到手」，三把鑰匙能做的事完全不同——前兩把只能讓你加入合法流量，第三把卻讓你能偽造任何簽章，地位跟站方一模一樣。

這就是這個節點要收的網：面對一個 RSA 保護，你得先判斷站方把哪把鑰匙放上前端、這層保護在防什麼，才能決定該期待什麼、該走哪條重現路線。判斷錯了，輕則白費力氣去找不存在的「解密」，重則誤把橡皮圖章當成銅牆鐵壁。

三個案例並排：誰在保護什麼

先把差異放到同一張表上。看的重點有四欄：前端拿的是哪把鑰、它執行的是加密還是簽章、伺服器拿什麼檢查、以及——最重要的——這個設計「真正」擋住了誰：

案例前端持有的鑰任務伺服器的檢查你到手後能偽造什麼保護真正擋什麼
外貿電商平台公鑰 PEM加密請求內容私鑰解開密文任意內容的合法密文擋偷看，不擋偽造
沃郵箱公鑰（模數＋指數）加密登入密碼私鑰解開密碼任意密碼的合法密文擋偷看；另有殘留私鑰
理財網私鑰 PEM對請求簽章公鑰驗章任意請求的合法簽章名義上擋篡改，實際擋不住

讀表的方法是「兩股張力」：加密類保護的是機密——內容不能被第三者看見；簽章類保護的是完整性與來源——內容不能被改、必須出自持有私鑰者。公鑰放前端，洩漏的只是「加密能力」，機密性不受影響：你加密得了，卻永遠解不開伺服器手上的密文。私鑰放前端，洩漏的是「簽署能力」：完整性保證當場蒸發，因為每個訪客都能蓋出驗得過的章。

一個譬喻把三案串起來：公鑰像掛鎖，鎖可以發給每個人，別人拿你的鎖鎖箱子你開不了、也不需要開；私鑰像印章，印章一旦複製出去，滿街都是「真跡」。理財網把印章跟著網頁發出去，等於請每位訪客都替自己保管一份。

「私鑰在前端」的兩種樣貌

失效模式不長得都一樣。跑過的案例裡就有兩種：

第一種是設計性的洩漏——簽章流程本來就需要私鑰，而站方選擇在前端簽。理財網是標準樣本：get_sign 裡那把 BEGIN PRIVATE KEY 不是意外，是流程的一環。這種設計下，「簽章驗證」只能擋住不看 JavaScript 的人；對任何會打開 bundle 的人，它是一張橡皮圖章，想蓋多真就多真。

第二種是殘留的洩漏——主流程沒洩漏，但開發工具忘了清。沃郵箱就是這樣：hashPassword 只用公鑰，設計正確；但同一個模組裡留著一個開發用的 loadPassword，把私鑰指數也打包了進來：

            loadPassword: function(t) {
                var e, n, r = /^#!(\w+)$/.exec(location.hash);
                r && t.val((e = r[1],
                (n = new i).setPrivate(o, '10001', '7cd1745aec69096129b1f42da52ac9eae0afebbe0bc2ec89253598dcf454960e\n3e5e4ec9f8c87202b986601dd167253ee3fb3fa047e14f1dfd5ccd37e931b29d'),

setPrivate 收的第三個引數就是私鑰指數。這個函式的用途是從網址的 # 片段撈回密碼原文——大概是開發時「忘記自己設的密碼」的自救工具。功能無害，洩漏有害：任何人讀到這行，就拿到了這把公鑰對應的私鑰，不但能偽造密文，還能解開所有用這把公鑰加密的密碼欄位。主流程守住了，雜物間沒鎖。

判別問句：四個可測試的問題

把上面的觀察收斂成四個問題。它們的特點是都能對著程式碼當場回答，不靠感覺：

  1. 呼叫點吃的是哪種鑰？看到 getKey、setPrivateKey，或 PEM 開頭是 PRIVATE，前端就持有私鑰；看到 publicKeyFromPem、setPublic，或 PEM 開頭是 PUBLIC，前端只有公鑰。
  2. 被保護的欄位要的是機密還是完整？密碼、支付資料這類「不能被看見」的內容，合理的設計是公鑰加密；請求標頭的簽章這類「不能被改」的內容，合理的設計是伺服器持私鑰簽、或前端持私鑰簽但私鑰不得外流。
  3. 伺服器檢查的是「內容正確」還是「來路正確」？解密失敗 = 機密通道；驗章失敗 = 完整性通道。兩者的失效模式完全不同。
  4. 模組裡有沒有解密路徑？搜尋 setPrivate、decrypt、loadPassword 這類字樣。主流程用不到的解密函式，往往就是殘留洩漏的藏身處。

反例：規則會翻轉的三個情況

規則說「私鑰在前端 = 保護失效」，但有三個情況會翻盤，值得逐一記住。

第一，公鑰在前端不等於保護無效。外貿與沃郵箱的設計就是這樣，而且它們是正確的設計：你拿到公鑰，能偽造合法密文混進去，卻解不開伺服器的資料、也解不開別人的流量。「能重現」只是加入流量，不是打穿防護——別把兩件事混為一談。

第二，「有簽章」不等於「有防篡改」，但反過來說，若私鑰真的只在伺服器（前端手上的公鑰純粹用來驗章），簽章就是實打實的強保護，你的重現也就只能止步於「照規則算出合法請求」。一句話：規則的翻轉點就是私鑰在哪，不是有沒有簽章這個表面特徵。

第三，失效模式也要看你的目的。爬蟲要的是「穩定發出合法請求」，私鑰在不在前端對你其實夠用——反正簽章算得出來就好。只有當任務升級成「替別人驗證」或「評估這網站能不能擋住偽造」時，私鑰洩漏才從「方便」變成「致命」。同一件事，對爬蟲是順風，對站方是災難。

重現路線抉擇：三條路怎麼選

攻防判斷定案後，剩最後一個決定：重現走哪條路。三個案例其實各自示範了一條：

路線做法勝場代價適用時機
重用 bundleNode 載入 loader 與模組，直接呼叫（window.loader("MuMZ").a(...)）參數不可能抄錯，最快看到結果要補瀏覽器環境，執行慢、部署重演算法看不懂、先求驗證時
execjs 橋接Python 抽出簽章函式餵給 Node 執行（理財網腳本的路線）Python 主導流程，JS 只算簽章依賴 Node，JS 檔要能獨立跑函式已抽好、不想重寫演算法時
Python 重寫讀懂參數後用 cryptography 重現快、穩、可測試、好維護必須讀懂每一參數，抄錯就死標準演算法、要長期爬取時

抉擇問句有三個。演算法標準嗎？RSA、AES 這類標準演算法，Python 庫的支援又快又穩，重寫划算；自家 hash、自創編碼就別硬寫，直接搬 JS。要長期維護嗎？一次性的資料抓取用 execjs 就好；每天跑的排程爬蟲值得投資重寫。庫搬得動嗎？jsrsasign、JSEncrypt 都是純 JS，抽出來容易；若加密流程跟幾十個模組纏在一起，重用整包反而省事。

實務上三條路會混著用：先用重用 bundle 把結果驗證出來、確認參數抄對，再決定要不要重寫成 Python。驗證先行、重寫在後，是成本最低的順序。

決策規則

最後收斂成一張能貼在螢幕邊的檢查表：

  1. 先認鑰匙身分——PEM 開頭或 setPublic／setPrivate，決定這是加密通道還是簽章通道，以及失效模式會長什麼樣。
  2. 再定攻防目標——只要加入流量（爬蟲）夠用，還是要評估偽造風險（資安視角）。
  3. 最後選路線——標準演算法長期爬就 Python 重寫；看不懂或趕時間就重用 bundle 或 execjs，驗證後再說。

小結

RSA 保護的強弱取決於鑰匙放在哪：公鑰在前端是正確設計，只能加密不能解，擋偷看不擋偽造；私鑰在前端則讓簽章變成橡皮圖章——理財網是流程性的洩漏，沃郵箱的 loadPassword 是殘留性的洩漏。判別看四件事：鑰的身分、保護的目標、伺服器的檢查、有沒有殘留解密路徑。重現路線按「演算法是否標準、是否長期維護」在重用 bundle、execjs、Python 重寫之間選，驗證先行、重寫在後。
