财联社：在真實 loader 插探針、呼叫 W2Yj 簽名模組

Step 2/5 · 案例：webpack 打包站實戰

學習目標

在财联社這種自帶 try/finally 快取管理的真實 loader 上找到探針插入點、鎖定簽名模組 W2Yj，並用 window.loader("W2Yj")(data) 呼叫取得簽名。

前言：分發器長得不一樣，探針該插哪裡？

上一節在四川补贴上跑通了完整流程，那支 loader 是標準的 webpack 引導檔，探針插在模組執行前，一切照教科書走。但真實站點的打包檔是各家前端工程師跟版本不同的打包工具一起長出來的，分發器（負責依 id 取出並執行模組的那個函式）的寫法會變形。當你打開财联社（Cailianpress，財經新聞平台的網頁版）的入口檔，第一個發現就是它的分發器自帶一套 try/finally 的快取管理——模組丟出例外時會把快取清掉。這種寫法下探針要插哪裡？快取什麼時候被清？呼叫簽名模組的寫法又跟四川补贴差在哪？

這一節就把這三件事練熟：讀懂一個「變形版」分發器、把探針插在正確的位置、認出簽名模組的匯出形狀並呼叫它。至於簽名本身「排序序列化 → SHA1 → MD5」的兩層雜湊管線，那是簽名與雜湊案例節點的功課；這裡的重點是怎麼從外面把它叫出來。

目標與前置條件

做完這一節，你會有一支呼叫财联社簽名模組的小程式：餵參數物件進去，拿回 32 位十六進位的簽名。動手前需要四川补贴那一節跑通的經驗，也就是「先 loader 再模組檔」的載入順序與 window.loader 的呼叫手感；另外要能讀懂 JavaScript 的 try／finally 在做什麼。

步驟一：入口檔本身就是驅動

财联社的入口檔 05 财联社的loader.js 有個方便的地方：它本身就是一支寫好的驅動程式。檔案開頭先載入三個模組檔：

require("./06 财联社的mod1")
require("./07 财联社的mod2")
require("./08 财联社的mod3")

接著是分發器與 webpackJsonp 的接線，最後尾端還留著一支叫 get_sign 的測試函式。所以這一節不用自己從零寫載入程式，讀懂這支檔案、照它的寫法呼叫就對了。這種「loader 即驅動」的檔案在課程教材裡很常見，因為它把「怎麼用」直接寫在檔案裡，逆向時等於有人先幫你寫好範例。

步驟二：在分發器裡插探針，讀懂 try/finally

分發器叫 u(r)，r 是模組 id。這是它的完整長相：

    function u(r) {
        if (n[r])
            return n[r].exports;
        var t = n[r] = {
            i: r,
            l: !1,
            exports: {}
        }
            , o = !0;
        try {
            console.log("r:::", r)
            e[r].call(t.exports, t, t.exports, u),
                o = !1
        } finally {
            o && delete n[r]
        }
        return t.l = !0,
            t.exports
    }

    window.loader = u

先看骨架：一開始的 if (n[r]) return n[r].exports 是快取命中就直接回傳，避免重複執行；接著把模組的快取紀錄 t 建起來，裡面有 id（i）、載入旗標（l）與結果容器（exports）。然後才是執行：探針 console.log("r:::", r) 就插在 e[r].call(...) 的前一行——這就是探針的正確位置，模組每次真的要被執行時印出它的 id。最後回傳 t.exports。

跟四川补贴不同的地方在中間的 try/finally。變數 o 是一個「有沒有正常跑完」的旗標：進 try 前設為 true，模組執行成功才設為 false。於是 finally 裡的 o && delete n[r] 讀起來就是「如果例外跳走了、旗標還是 true，就把這筆快取刪掉」。為什麼要刪？因為快取裡存的是執行到一半的半成品，留著會讓下一次呼叫誤以為模組載入過了。清掉之後，下一次呼叫同一個 id 會重新執行模組，乾乾淨淨。

這個設計對逆向者其實是好消息：當你在實驗中把模組搞壞了、它丟出例外，快取不會被污染，修好後重跑就好。另外要留意一個細節：四川补贴的教學版 loader 回傳的是 o.exports.exports，這裡回傳的是 t.exports。差異來自模組體怎麼寫匯出——有的模組把東西掛在 this.exports 上，有的直接改寫 module.exports。所以「拿到 id 之後，回傳值長什麼樣」要看模組的寫法，這就是後面要練的匯出形狀辨認。

步驟三：認出懶載入的區塊對照表

分發器後面掛著一個 u.e 函式，負責載入「懶載入區塊」（lazy chunk）——不是一開始就載入、而是使用者點到某個功能才去抓的 JavaScript 檔。它長這樣：

                    c.src = function (e) {
                        return u.p + "static/chunks/" + ({
                            24: "bd6b8a80f74adbac385e379d09a6b580e83c6f0f",
                            25: "d6e1aeb5"
                        }[e] || e) + "." + {
                            24: "a14451ee233660bd07bf",
                            25: "e040c1fdb2dde09b1dd5",

兩張對照表把區塊編號映到檔名雜湊，組出 static/chunks/... 的下載路徑。逆向時要記住的只有一件事：簽名模組不在這些懶載入區塊裡，它已經在開頭載入的模組檔裡了。我們直接用 window.loader 呼叫，根本不會走到 u.e 這條路。所以看到這段不需要害怕，知道它是「瀏覽器才需要的額外載入機制」就好。

步驟四：呼叫簽名模組 W2Yj

探針跑起來後，在終端機的 id 清單裡找簽名模組。入口檔尾端的測試函式已經把答案寫好了：

function get_sign() {
    // 测试环境
    let data = {
        "os": "web",
        "sv": "7.7.5",
        "app": "CailianpressWeb"
    }
    return window.loader("W2Yj")(data)
}

console.log(get_sign())

簽名模組的 id 是字串 W2Yj。注意呼叫寫法跟四川补贴不一樣：這裡是 window.loader("W2Yj")(data)——先用 id 換回模組的匯出值，然後「直接把匯出值當函式呼叫」，參數是一包欄位物件。為什麼可以這樣寫？看 W2Yj 模組的匯出就明白了。它在模組檔裡長這樣：

    W2Yj: function (e, t, n) {
        var r = n("p0XB")
            , o = n("pLtp")
            , i = n("KjvB")
            , u = n("aCH8")
            , a = !0;

模組體開頭用 n(...) 依 id 取用四個鄰居模組：p0XB 是陣列判斷、pLtp 是取物件鍵、KjvB 是 SHA-1、aCH8 是 MD5。這是讀真實模組的第一課：模組體裡的 n（也就是 __webpack_require__）讓你能順著 id 把整個依賴鏈拉出來看。再看它的匯出段：

        e.exports = function (e) {
            var t = e && f(c(e).map((function (t) {
                    return p(t, e[t])
                }
            )));
            return t = i.sync(t),
                t = u(t)
        }
    },

答案就在 e.exports = function (e) {...} 這行：模組直接把「一個函式」賦給 exports，所以 window.loader("W2Yj") 換回來的不是物件，而是這個函式本身，後面接括號就是呼叫它。函式內部做三件事：先把參數物件排序序列化成規範字串（鍵排序、巢狀展開、用 & 連接），丟給 i.sync 取得 SHA-1，再丟給 u 取得 MD5，最後回傳 32 位十六進位的簽名。兩層雜湊的細節與辨識手法在簽名與雜湊的案例節點裡拆；在這一節，你只要能把這條管線「叫出來」就完成任務。

把呼叫端寫成一支小程式：照 get_sign 的樣子組一包參數、呼叫、印出簽名，就是完整的重現。若要換成自己的請求參數，就把 data 換成該介面實際送出的欄位——簽名模組照單全收，欄位一變簽名就變。

做完長什麼樣

執行後終端機會吐出兩種訊息：探針的 r::: W2Yj 一類的 id 序列，跟最後一串 32 位十六進位的簽名。把這串簽名放進真實請求送出、伺服器接受，就驗證了整條路是對的。若呼叫時丟出「不是函式」之類的錯誤，先檢查匯出形狀是不是看錯——這正是下一節要整理的功課。

小結

真實 loader 的分發器會變形，但骨架不變：快取命中先回傳、建快取紀錄、執行模組、回傳 exports。探針永遠插在「模組即將被執行」那一行前面，财联社的版本裡就是 e[r].call 的前一行。try/finally 的快取清理讓失敗的呼叫可以乾淨重試。簽名模組 W2Yj 是「可呼叫的匯出」——e.exports = function，所以呼叫寫法是 window.loader("W2Yj")(data)，餵參數物件、拿回簽名。

四川补贴的 dd88 是「物件上掛方法」，财联社的 W2Yj 是「匯出即函式」。匯出形狀還不止這兩種：沃邮箱的登入加密模組掛的是具名方法，模組 id 還從字串換成了數字，呼叫端甚至把 RSA 公鑰參數直接寫在測試程式裡。下一節去沃邮箱，把「數字 id＋具名匯出」這種形狀也練起來。
