學習目標

用一張對照表認清四個真實站點的 loader 變形與模組匯出形狀，接到新的 webpack 站時能對號入座決定探針插哪、入口怎麼呼叫。

前言：手上換了新站，又要從頭讀一支 loader 嗎？

前面三節分別在四川补贴、财联社、沃邮箱跑完了定位與呼叫。每次換站，你都重複了一樣的動作：讀分發器、找探針位置、認模組 id、看匯出形狀、寫呼叫。第四個案例 aerfa 的檔案包裡還有另一種長相——一支幾萬行的打包檔，簽名器卻另外寫成十行的小檔。當目標網站一個換一個，把「變形的規律」記成表格，比每站從頭讀一支六百行的 loader 快得多。

這一頁就是那張表格：四個真實站點的 loader 變形一覽、四種模組匯出形狀一覽，各附一行最小呼叫範例。它是查閱用的對照表——只描述各站的形狀與寫法，不重教原理。要動手的步驟在前三節，取捨的判準在下一節。

loader 變形對照

四站的 loader 都是「分發器＋快取＋webpackJsonp 接線」的同一副骨架，變形集中在四個欄位：分發器的寫法、探針訊息、快取清理策略、懶載入機制。全表如下。

站點入口檔分發器與探針訊息快取清理懶載入機制全域洩漏
四川补贴01 loader.js（JSONP 引導檔，約 600 行）__webpack_require__，探針 moduleId:::建立後不主動清理webpackJsonp 佇列，模組檔 push 合併window.loader
财联社05 财联社的loader.js（loader 與驅動合一）u(r)，探針 r:::try/finally，例外時刪快取u.e＋static/chunks 雜湊對照表window.loader
沃邮箱09 沃邮箱的loader.js（loader 與驅動合一）c(e)，探針 e:::無清理c.e＋loginCommon/login 命名對照window.loader
aerfa08 loader.js（runtime 與模組同檔）webpack require（壓縮後變數名），未插探針webpack 標準快取runtime helpers 與 window.webpackJsonpwindow.loader

全表讀完的重點有三個。第一，探針訊息每站不同（moduleId:::／r:::／e:::），但插的位置永遠是「模組即將被執行」那行的前面。第二，快取清理只在财联社出現，而且只影響「模組丟出例外後能不能乾淨重試」，正常呼叫不受影響。第三，四站的 require 函式都洩漏在 window.loader——這個名字是逆向社群的慣例，不是 webpack 的規定，遇到別的名字（例如 window.webpack_require）照樣用同樣方式呼叫。

模組匯出形狀對照

拿到模組 id、呼叫 window.loader(id) 之後，回傳值的形狀決定下一行怎麼寫。真實站點出現過的形狀有四種。

形狀代表站點模組 id呼叫寫法回傳值
物件方法四川补贴 dd88字串 "dd88"window.loader("dd88")["b"](payload)密文；["c"] 回傳 {sign, timestamp, source}
可呼叫函式财联社 W2Yj字串 "W2Yj"window.loader("W2Yj")(data)32 位十六進位簽名
具名方法物件沃邮箱 437數字 437window.loader(437).encrypt(t, o, n)RSA 密文
default 互操作aerfa 1／141數字 1、141window.loader(1).default.parseURLSearchParams(...)依方法而定

前兩種的區別在「匯出值本身能不能直接呼叫」：dd88 把方法掛在 exports 物件上，所以呼叫要多一層 ["b"] 取方法；W2Yj 直接把函式賦給 e.exports，所以換回來的值後面接括號就是呼叫。第三種跟第一種同族，只是方法名有語意、模組 id 是數字。第四種是 ES module 語法的打包結果：匯出被包成一層 default 屬性，呼叫時要先點 .default 再點方法名，有時 .default 本身就是可呼叫的函式。

四行最小呼叫範例

四種形狀各留一行真正的呼叫程式，供抄寫比對。

物件方法——先取模組，再取方法：

parameter = window.loader("dd88")["b"](JSON.stringify(i))

可呼叫函式——匯出值直接接參數：

    return window.loader("W2Yj")(data)

具名方法物件——數字 id，點方法名：

console.log(window.loader(437).encrypt(t, o, n))

default 互操作——先點 .default 再點方法：

console.log(window.loader(1).default.parseURLSearchParams("a=1&b=2"))

同一站的另一種寫法見同一支檔案的註解段——.default 本身就是函式的形狀：

/*
user = "yuan"
pwd = "123456"
e = `/WebApi/Users/Login?username=${user}&password=${pwd}DUE$DEHFYE(YRUEHD*&`

console.log(window.loader(141).default(e))*/

小結

loader 的變形集中在四欄：分發器寫法、探針訊息、快取清理、懶載入機制，骨架與 window.loader 洩漏點四站一致。匯出形狀共四種：物件方法、可呼叫函式、具名方法物件、default 互操作。判定順序是先看 id 是字串還是數字、再看回傳值是物件還是函式、最後看要不要點 .default。

表格解決的是「怎麼呼叫」，還有一個每次都要回答的問題沒解決：這段演算法到底該呼叫原 bundle，還是乾脆用 Python 重寫？aerfa 的檔案包正好是這道題的最佳教材——同一個簽名器，一邊是十行的小檔，一邊是幾萬行的打包檔。下一節就用它建立抉擇的判準。
