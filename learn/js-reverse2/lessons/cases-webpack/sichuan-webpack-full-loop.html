四川补贴：跑通一個多檔 webpack 站的完整流程

Step 1/5 · 案例：webpack 打包站實戰

學習目標

把四川补贴這類多檔 webpack 站完整跑過一次：載入 loader 與模組檔、補上瀏覽器環境、用探針印出模組 id 找到 dd88，再呼叫它的 b/c/a 取得加密參數與簽名。

前言：四個檔案擺在面前，然後呢？

在 webpack 拆解的節點裡，你已經在最小模型上看過打包檔的骨架：一個 require 函式、一袋用 id 編號的模組、一個印模組 id 的探針。可是當你從真實網站把 JavaScript 另存下來，擺在面前的往往是好幾個檔案——一個 loader、兩個幾百 KB 甚至幾 MB 的模組檔、還有一個看不出用途的小檔。這時候第一個卡住的問題通常不是「簽名演算法長什麼樣」，而是「這堆檔案到底要怎麼跑起來」。

四川补贴（農機購置補貼的查詢系統）是很好的第一個真實靶場。它把整個查詢介面打包成多檔的 webpack 應用，簽名邏輯藏在應用層的模組裡，以一個叫 dd88 的模組對外提供三個方法：一個加密請求參數、一個產生簽名、一個解密伺服器回應。這一節會把完整流程走過一遍：先看懂四個檔案的分工，再讀 loader 已經被動過哪些手腳，接著補上瀏覽器環境、照順序載入、用探針找到模組 id，最後呼叫簽名模組拿到結果。加密演算法本身的拆解交給對稱加密的案例節點；這裡練的是把一個真實打包站「跑起來」的手感。

目標與前置條件

做完這一節，你手上會有一支能跑的驅動程式：餵查詢參數進去，拿回加密的 parameter 與簽名物件，還能把伺服器的回應解回來。動手前需要三樣東西：一是 webpack 打包檔的心智模型，也就是 loader 分發器、模組 id、還有 window.loader 這個常見的洩漏點；二是補環境的基本觀念，知道 Node 裡沒有 document 也沒有瀏覽器的計時器；三是一個能跑 JavaScript 的 Node 環境。

步驟一：先看懂四個檔案的分工

拿到四川补贴的檔案包，裡面有四支 JavaScript。它們的角色分工是固定的，認清楚之後你就知道每支檔案該讀到多細。

  • 01 loader.js：webpack 的引導檔（webpack runtime）。它負責定義模組分發器與快取，並把 webpackJsonp 這個全域陣列的 push 動作換成自己的 callback，等模組檔把模組「推」進來。整支檔案約六百行，是唯一需要完整讀懂的一支。
  • 02 mod01.js：應用層模組檔，幾千行。裡面是網站自己的程式碼，包括介面元件，還有我們要找的簽名模組 dd88。
  • 03 mod02.js：函庫模組檔，好幾 MB。裡面是打包進來的第三方函庫，包括做國密演算法的函式庫。這支檔案不需要讀，載入就好。
  • 04 sichuanbutie.js：驅動檔，這是逆向者自己寫的入口。它負責依序載入前三支檔案，組好參數，然後呼叫 dd88 的三個方法。

你可以把這個組合想成一間公司的總機系統：loader 是總機，知道每個分機號碼（模組 id）對應哪個單位；兩個 mod 檔是把各部門的分機一次裝設完畢；驅動檔則是拿起話筒、撥號碼、跟對方講話的人。

步驟二：讀 loader——它已經被動過手腳

01 loader.js 打開來第一行就是一個訊號：

window = global

這是逆向者加的接軌線。瀏覽器裡的全域物件叫 window，Node 裡叫 global，把兩者接起來，打包檔裡讀 window 的程式碼才不會直接崩掉。這種手法就是補環境的第一步。

接著往下讀，會看到 webpack 的核心：一個叫 __webpack_require__ 的函式，負責依模組 id 取出模組、執行它、把結果放進快取。這支 loader 最關鍵的兩處改動就在它身上。第一處是探針——在「模組即將被執行」的那一行前面插進一個 log：

        console.log("moduleId:::",moduleId)
        modules[moduleId].call(module.exports, module, module.exports, __webpack_require__);
…
    window.loader = __webpack_require__

第一行是探針，每次有模組被執行就印出它的 id，讓你看到整支程式到底碰過哪些模組。第二行才是真正執行模組的地方，模組體拿到的 module、module.exports 與 __webpack_require__ 三個參數都是從這裡傳進去的。最後那行 window.loader = __webpack_require__ 是第二處改動：把 require 函式洩漏到全域，之後你就能在外部用 window.loader(模組 id) 直接呼叫任何模組。

檔案的結尾是多檔版特有的接線邏輯：loader 把 webpackJsonp 這個全域陣列的 push 動作換成自己的合併函式。

    var jsonpArray = window["webpackJsonp"] = window["webpackJsonp"] || [];
    /******/
    var oldJsonpFunction = jsonpArray.push.bind(jsonpArray);
    /******/
    jsonpArray.push = webpackJsonpCallback;

為什麼要換掉 push？因為模組檔載入時做的就是 webpackJsonp.push([[區塊], {模組表}])：把一批模組推進佇列。loader 先把 push 換成自己的合併函式 webpackJsonpCallback，於是模組檔一推，模組就被合併進 modules 這張大表裡。這就是多檔版「先 loader、再模組檔」鐵則的由來——順序反了，模組就推給了原始的陣列 push，永遠進不了分發器。

步驟三：補上瀏覽器環境

打包檔是在瀏覽器裡長大的，它會理所當然地讀 window、document、計時器這些宿主環境的東西。四川补贴的 loader 裡就有現成的例子，它的區塊載入路徑會建立 script 標籤：

                var script = document.createElement('script');

在 Node 裡這行只要被執行到就會噴錯，因為 Node 沒有 document。處理原則是「缺什麼、補什麼」：模組初始化時會碰的屬性要補，例如 document、setTimeout、setInterval 這些計時器；純粹為了載入額外檔案的路徑則可以不理，因為我們不會觸發它。這支 loader 開頭的 window = global 已經做了最小接軌，實際跑起來若再遇到缺屬性的錯誤，就照錯誤訊息一個個補上。更系統化的補環境手法——用 Proxy 攔截來偵測打包檔讀了哪些屬性——在補環境的節點裡練，這裡先求「跑得起來」。

步驟四：照順序載入，用探針看模組 id

驅動檔開頭就是三行 require，順序完全照鐵則走：

require("./01 loader")
require("./02 mod01")
require("./03 mod02")

第一行先架起模組系統與 webpackJsonp 的合併函式，後兩行才把模組表推進來。載入完成後，隨便用 window.loader 呼叫一個模組，終端機就會開始吐探針訊息 moduleId::: 加一串 id。這串 id 清單就是你的尋寶地圖：呼叫 dd88 時會看到 moduleId::: dd88 出現，接著它依賴的國密函庫模組也會一個個被印出來，整個依賴鏈攤在你眼前。

步驟五：呼叫 dd88 的三個方法

打開 02 mod01.js 搜尋 dd88，會看到這個模組的開頭。它透過 webpack 的 n.d（定義匯出屬性的輔助函式）把三個內部函式註冊成三個對外方法：

    dd88: function (e, t, n) {
        "use strict";
        n.d(t, "b", (function () {
                return d
            }
        )),
            n.d(t, "a", (function () {
                    return u
                }
            )),
            n.d(t, "c", (function () {
                    return p
                }
            ));

讀法是：t 就是模組的 exports 物件，n.d(t, "b", ...) 意思是「exports 上的 b 屬性，值取內部函式 d」。所以對外的三個方法分別是 b（加密）、a（解密）、c（簽名）。加密與解密這對函式長這樣：

        function d(e) {
            var t = l.encrypt(e, o);
            return t
        }

        function u(e) {
            var t = l.decrypt(e, o);
            return t
        }

兩個函式都是對同一把金鑰 o 做對稱式加解密，加密走 d、解密走 u，也就是匯出的 b 與 a。第三個方法 c（內部的 p）負責簽名：它把請求參數解開、補上時間戳記、拼成規範字串後產生簽名，最後回傳的物件長這樣：

                {
                    sign: d(r(t).toLocaleUpperCase()),
                    timestamp: d(n.toString()),
                    source: "ZRCSL7V0JIRK1PHY"
                })

三個欄位各有用途：sign 是簽名本身、timestamp 是加密後的時間戳記、source 是固定的來源碼。知道每個欄位「是什麼」就夠了，它們怎麼算出來是對稱加密案例節點的功課。

最後看驅動檔怎麼把三個方法串成一個完整的請求循環。先組查詢參數，呼叫 b 加密成 parameter：

parameter = window.loader("dd88")["b"](JSON.stringify(i))

再把 parameter 包成請求體，呼叫 c 取得簽名：

e = {
    "parameter": parameter
}
console.log(window.loader("dd88")["c"](e))

伺服器回應回來後，把加密的內容丟給 a 解密：

console.log(window.loader("dd88")['a'](t))

注意呼叫的寫法：window.loader("dd88") 先用模組 id 換回 exports 物件，["b"]、["c"]、['a'] 再從物件上取方法。這種「物件上掛好幾個方法」的匯出形狀，是真實站點常見的一種，後面的對照表會把它跟其他三種並排比較。

做完長什麼樣

把驅動檔用 Node 跑起來，終端機會依序吐出四種東西：一串 moduleId::: 探針訊息、一段十六進位的 parameter 密文、一個含 sign／timestamp／source 的簽名物件、最後是解開後的明文 JSON。四種輸出齊了，就代表這條「載入 → 補環境 → 定位 → 呼叫 → 解密」的完整迴圈已經打通。若中途噴出「xxx is not defined」之類的錯誤，那就是環境缺口，照錯誤訊息補上缺的屬性再跑。

小結

一個多檔 webpack 站就是四個角色：引導檔 loader、應用模組檔、函庫模組檔、自己寫的驅動檔。跑通的鐵則是先 loader 再模組檔，讓 webpackJsonp 的合併函式把模組收進大表。loader 上通常已經留好兩把手術刀——印模組 id 的探針、洩漏到 window.loader 的 require 函式。簽名模組以一個 id 掛在模組表裡，dd88 這種物件式匯出只要按方法名呼叫就能取得加密、簽名與解密的完整循環。

四川补贴的 loader 是完整的 webpack 引導檔，模組表、快取、callback 一應俱全。但真實站點的 loader 有各種變形：有的自己管理快取、有的探針插在例外處理裡、有的簽名模組匯出的直接是一個可呼叫的函式。下一節就到财联社，看一個自帶 try/finally 快取管理的分發器，並用 window.loader("W2Yj")(data) 這種寫法直接呼叫簽名。
