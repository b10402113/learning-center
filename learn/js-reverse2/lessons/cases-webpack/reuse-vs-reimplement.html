抉擇：呼叫原 bundle 還是用 Python 重寫？

Step 5/5 · 案例：webpack 打包站實戰

學習目標

以 aerfa 的 get_s 與打包版呼叫為例，建立「直接呼叫原 bundle 還是用 Python 重寫」的判準，並知道各選項什麼時候失效。

前言：同一個簽名器，兩條路都通

上一節的對照表解決了「怎麼呼叫」的問題。現在換個角度想一件事：aerfa（一個作品分享平台）的檔案包裡，登入簽名的演算法被提供了兩份。一份是獨立小檔 07 aerfa.js，連註解加空白十幾行，任何人花一小時就能翻成 Python；另一份是幾萬行的打包檔 08 loader.js，呼叫它只要一行 window.loader(141).default(e)。兩條路都能產生一模一樣的簽名。

這就帶出每接一個站都要回答一次的問題：這段演算法，要用 Python 重寫，還是直接呼叫原 bundle？兩股張力在拉扯。重寫這邊，程式碼乾淨、部署單純、跑得快，但保真度全看你有沒有讀懂每一個位元，站方一改規格你不會收到通知。呼叫那邊，永遠跟瀏覽器一致、不用理解演算法，但要把整套打包檔搬進 JS 執行環境、補齊它要的環境，改版時還要重新定位模組。這一節就把這道選擇題拆成可以照問的判準。

選項比較

先把兩個選項並排放，差異才好比較。第三列是常見的混合路線，本質上是「呼叫」的一種實作方式。

面向呼叫原 bundle（window.loader）Python 重寫混合：呼叫原 JS（execjs）
保真度與瀏覽器永遠一致取決於重現的精確度，錯一位元全盤皆輸與瀏覽器一致
理解成本不需要讀懂演算法，只要讀懂呼叫面要把演算法完整讀懂並翻譯只需讀懂匯出與參數
環境成本要補環境、載入整包模組純 Python，無 JS 相依要一個 JS 執行環境（Node 或 execjs）
執行速度每次呼叫走 JS 執行環境，較重最輕最快比直接呼叫輕，但仍相依 JS
改版風險站方改打包檔要重新定位模組 id站方改規格要重新推導，且無從察覺同「呼叫原 bundle」
適用情境演算法複雜、有環境依賴、規格看不透演算法短小、只用標準演算法、能對拍驗證想留在 Python 生態系但演算法不宜重寫

aerfa 的兩條路，長什麼樣

先看重寫這條路的原料。獨立小檔裡的簽名器全部內容就是這樣：

const Sha1 = require("sha1")

function get_s(e, t) {
    var n = (new Date).getTime() + 2592e6 + (t || 3e4)
        , r = (e || "") + "&t=" + n;
    return {
        t: n,
        s: Sha1(r)
    }
}

翻譯成 Python 幾乎是逐行對應：時間戳取當下毫秒加上 2592e6（三十天，讓簽名在一段時間內有效），再加可選的偏移量；輸入字串接上 &t= 與時間戳；最後對整串取 SHA-1。檔案尾端的使用範例把整個情境也寫好了：

user = "yuan"
pwd = "123456"
e = `/WebApi/Users/Login?username=${user}&password=${pwd}DUE$DEHFYE(YRUEHD*&`
console.log(get_s(e))

再看呼叫這條路。同一個簽名器在打包檔裡是模組 141 的預設匯出，另一個模組 1 帶著 parseURLSearchParams 工具方法：

require("./08 loader")
…
console.log(window.loader(1).default.parseURLSearchParams("a=1&b=2"))
console.log(window.loader(141).default(e))*/

這行在原始檔案裡位在註解區塊的最後一行，取用時把註解拿掉即可。兩行的差別就是這次抉擇的縮影：呼叫路線不碰演算法內部，只要知道模組 id 與參數形狀；重寫路線要從程式碼裡讀懂「時間戳怎麼來、字串怎麼拼、雜湊是哪一種」，但讀懂之後連 JS 執行環境都不需要。

判別問句：照著問，答案會自己浮出來

表格給的是全貌，真正做決定時用的是下面五個可以當場測試的問題。按順序問，通常問到第二、三題就有答案了。

  1. 「這段邏輯我讀得懂嗎？十行內說得清楚嗎？」讀得懂、說得清，重寫的門檻就低。aerfa 的 get_s 是標準答案：一行取時間、一行拼字串、一行 SHA-1。
  2. 「它只用標準演算法嗎？」MD5、SHA 系列、AES、RSA 這些有現成 Python 實作的，重寫可行；遇到自創配方（自己發明的位元運算迴圈、私有編碼表），重寫就變成二次逆向工程。
  3. 「輸入裡有時間戳、隨機數或伺服器互動嗎？」有動態輸入時，呼叫原碼比較不會漏——重寫者最常漏掉的就是「時間戳要加 30 天」這種隱藏常數，而 aerfa 的 2592e6 就寫在眼前。
  4. 「模組的依賴鏈有多深？」簽名模組若拉著一串函庫（國密、RSA、編碼工具），呼叫就是把整條依賴鏈載進來跑；重寫則要把每一環都翻譯一遍。依賴越深，呼叫越划算。
  5. 「我能對拍驗證嗎？」重寫的結果必須跟原 JS 產出對拍到逐位元相同才能上線。沒有對拍手段，重寫就是在賭運氣。

反例：規則會翻轉的三種情況

判準不是萬靈丹，下面三種情況會讓看似合理的選擇翻車。

演算法很小，卻選了呼叫。只為了 get_s 這十行，把七萬行的 08 loader.js 搬進 Node、補齊它要的 window、document、計時器，還要處理它初始化時的各種環境檢查——補環境的成本遠遠超過十行的 Python 重寫。這時候呼叫是被自己的工具鏈拖著走。

演算法很大或看不懂，卻硬要重寫。自創的雜湊配方（比方說一串看不懂的位元運算加私有編碼表）錯一個位元，整串簽名就全錯，而錯誤不會告訴你是哪一步錯的。看不懂就不要翻譯，呼叫它。

規格會漂移，卻高估了某條路的安全性。重寫最怕站方換掉金鑰、改掉拼接順序——你不會收到通知，爬蟲會在某天突然全數被拒。呼叫路線則相反：站方一改版，打包檔的模組 id 可能重新洗牌，你要重新定位一次。兩條路都有維護成本，差別在於重寫的成本是「無聲失敗」，呼叫的成本是「明著重新定位」。要穩定爬取，兩條路都要留下驗證機制——定期拿同一筆輸入對拍一次。

小結與決策規則

回顧這一節：呼叫原 bundle 買的是保真度與省下的理解成本，付出的是補環境與改版後重新定位；Python 重寫買的是乾淨、快速與無 JS 相依，付出的是逐位元的精確度與規格漂移的無聲風險；混合路線則是在 Python 生態系裡借 JS 的保真度。哪條路划算，取決於演算法本身。

把整節壓成一條可以帶走的規則：

先問三句：讀得懂嗎、驗得了嗎、跟得上改版嗎？三句都是「是」——用 Python 重寫，部署最單純；任何一句是「否」——呼叫原 bundle（或用 execjs 呼叫原 JS），把保真度交給原碼，把力氣花在補環境與重新定位上。
