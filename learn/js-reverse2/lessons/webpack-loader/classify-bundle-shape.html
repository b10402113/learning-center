判斷 bundle 型態：陣列、物件與多檔 JSONP

Step 2/4 · webpack 拆解與模組定位

學習目標

拿到一份打包檔時，能判斷它屬於陣列、物件（hash key）或多檔 JSONP 哪一型，並說出各型的模組 id 長什麼樣、該從哪裡接上 require 函式。

前言：櫃子的形式不只一種

上一節我們認出了 webpack 的共同骨架：外層 IIFE、裡面的 require 函式、加上一櫃子編號模組。但實際拆站點時，你會發現這座櫃子有三種常見的長相，而且它們決定了兩件對你很實際的事：模組 id 要用什麼形式報，以及載入器該去哪裡找。

用錯判斷，就會發生很典型的卡關：你對著一個多檔 bundle，一直想找它自己的模組陣列，卻不知道模組其實躺在旁邊另外兩支檔案裡；或者你把物件版當成陣列版，用 n(0) 呼叫，結果當然是 undefined。這一節要練的就是「一眼歸類」，把辨認型態變成反射動作。

前置條件：你已經看懂上一節的 require 函式與 IIFE 骨架。辨認型態不需要新工具，只需要知道往哪裡看。

三種型態並排比較

三種型態的差別，濃縮在這張表。先掃一遍，再往下逐一拆解。

型態IIFE 尾端傳入什麼模組 id 形式載入器怎麼露出典型情境
陣列版一個陣列 [ fn0, fn1 ]數字索引 0、1、2IIFE 內自訂 n，常寫 window.loader = n小型單檔、教學最小模型
物件版一個物件 { "1001": fn }字串 hash key同上，window.loader = n模組多、想要穩定 id
多檔 JSONP空陣列 ([])，另有 bootstrap數字或字串window.loader = __webpack_require__大型 SPA、程式切成多個 chunk

型態一：陣列版，模組按順序排隊

陣列版最好認，因為它把模組一個接一個排進陣列，IIFE 尾端一定是中括號。模組的身分就是它在陣列裡的位置，所以 id 是 0、1、2 這種數字索引。

}([
    function () {
        console.log("foo");
        this.exports = 100;
    },
    function () {
        console.log("bar");
    }
]);

看到 }([ … ]) 就結束了，沒有第二句話。要呼叫第一個模組，就是 n(0)；第二個是 n(1)。缺點是只要插入或刪掉一個模組，後面所有索引都會位移，所以大專案很少用，多半出現在教學範例或小工具裡。

型態二：物件版，模組掛在字串編號下

物件版把模組掛在一張「編號對函式」的表上，IIFE 尾端是大括號。編號是字串，常長得像 "1001"、"1002" 或 "56d7"、"dd88" 這種看似隨機的 hash。

}({
    "1001": function () {
        console.log("foo");
        // 前端操作
        let ele = document.createElement("span")
        console.log(navigator.userAgent)

        this.exports = 100; // 直接修改 exports 变量
    },
    "1002": function () {
        console.log("bar");
        // window.loader("1003")
        this.exports = 200;
    }
});

window.loader("1002")

這種型態有個很方便的特點：模組之間可以互相呼叫。原始碼裡那行被註解掉的 // window.loader("1003") 就在提示，模組內想用別的模組，透過同一把 window.loader 報上對方的編號就行。物件版的 id 不會因為插入模組而位移，穩定性好，是實務上最常見的單檔型態。

型態三：多檔 JSONP，模組由別的檔案送進來

前兩型都是「一個檔案自給自足」，多檔版則把 loader 和模組拆開。loader 檔本身只有幾百行，尾端傳入一個空陣列；真正的模組在旁邊其他 JS 檔裡，靠一個叫 webpackJsonp 的機制送進 loader。

!(function (modules) { // webpackBootstrap
    …
    function webpackJsonpCallback(data) {
        var chunkIds = data[0];
        var moreModules = data[1];
        var executeModules = data[2];
        …
        for (moduleId in moreModules) {
            if (Object.prototype.hasOwnProperty.call(moreModules, moduleId)) {
                modules[moduleId] = moreModules[moduleId];
            }
        }
        …
    };
    …
    function __webpack_require__(moduleId) {
        …
        console.log("moduleId:::", moduleId)
        …
        modules[moduleId].call(module.exports, module, module.exports, __webpack_require__);
        …
    }
    window.loader = __webpack_require__
    …
    var jsonpArray = window["webpackJsonp"] = window["webpackJsonp"] || [];
    var oldJsonpFunction = jsonpArray.push.bind(jsonpArray);
    jsonpArray.push = webpackJsonpCallback;
    …
})
…
/******/ ([]);

這段有幾個專屬記號，看到就幾乎能確定是多檔版：webpackBootstrap、webpackJsonpCallback、__webpack_require__、還有 window["webpackJsonp"]。機制是這樣的：loader 把全域的 window.webpackJsonp 準備成一個陣列，並把它原本的 push 換成 webpackJsonpCallback。之後每一支模組檔執行時，都會呼叫 window.webpackJsonp.push([ … ])，把一批模組丟進來。由於 push 已經被換掉，這些模組就會被 callback 併進 loader 的 modules 裡。等多檔都載完，模組才齊全。

這個 loader 尾端是 ([])，也就是一個空陣列。它自己沒有任何模組，所有模組都是後來被 push 進去的。這是最容易被誤判的地方：看到 [ 別急著歸類成陣列版。

怎麼判？四個問句

  1. IIFE 尾端括號裡放的是 [、{，還是空陣列 ([])？
  2. 檔案裡有沒有 webpackJsonp、webpackJsonpCallback、jsonpScriptSrc 這幾個字？
  3. 呼叫模組時用的是 n(0) 這種數字，還是 n("1001") 這種字串？
  4. 這支檔是不是只有幾百行的 loader，而旁邊還躺著好幾支幾萬行的 JS？

前兩題分型態，後兩題確認 id 形式。通常看到第二題的關鍵字，就可以直接判成多檔版；沒有的話，就看第一題是陣列還是物件。

幾個會翻盤的反例

規則講完了，但有幾種情況會讓你判錯，先講清楚：

  • 別把多檔 loader 當成陣列版。多檔 loader 尾端是 ([])，確實有中括號，但它不含模組。關鍵差別是有沒有 webpackJsonp 機制。
  • 單檔也可能內建 webpackJsonp。有些站點把整包模組都塞進同一支檔，卻仍保留 JSONP 機制的程式碼。這種看起來像多檔，其實只有一支，判準是「模組是不是靠另一支檔的 push 才出現」。
  • 物件版的 key 是字串，不代表值是字串。看到 "1001" 別誤以為是陣列索引，它的本質是物件的字串鍵。
  • 型態看的是容器，不是大小。陣列版也能塞幾百個模組，物件版也能只有兩個。別用檔案大小或模組數量來猜。

帶走這條決策規則

先看 IIFE 尾端傳進來的容器：[ 是陣列版、{ 是物件版、[] 加上檔案內有 webpackJsonp 是多檔版。再用模組 id 是數字還是字串，決定呼叫時要報什麼 key。

型態判斷清楚了，你就知道要去哪裡接載入器、要拿什麼鑰匙開櫃子。下一節要把上一節的「把手」加上這一節的「編號」，做出一套能在任何網頁上都通用的定位流程：把 require 函式接到 window.loader，插一行 log 記錄模組 id，再逐一呼叫，直到找到產生簽名參數的那個模組。
