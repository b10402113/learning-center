暴露 require 函式並記錄模組 id

Step 3/4 · webpack 拆解與模組定位

學習目標

把 bundle 內的 require 函式接到 window.loader、在模組執行處插一行 console.log 印出模組 id，再用 window.loader(id) 逐一呼叫模組，直到鎖定產生簽名參數的那一個。

前言：把手在手上，卻不知道要轉哪個號碼

前兩節你已經知道 webpack bundle 的骨架，也學會分辨陣列、物件、多檔三種型態。你也知道那行 window.loader = n 是入口。但真正的問題是：簽名參數是由哪一個模組算出來的？那個模組的編號是多少？

如果你在 DevTools 的斷點上停下來，只會看到 window.loader 收到一個參數 r，但你不知道 r 是什麼、它來自哪個呼叫。這一節要做的就是裝一個「行車記錄器」：在模組即將被執行的位置插一行 log，讓每一次呼叫都留下「編號」的紀錄。有了這份紀錄，你就能從「哪個模組產生了我關心的值」反推回去。

前置條件：你手上的打包檔已經能載入 Node 執行（最小情況是先寫 window = global，再把 loader 檔 require 進來）。若那段 JS 依賴瀏覽器物件而報錯，那是補環境的範圍，先跳過，專注在「接把手、插 log、呼叫」這三件事上。

步驟一：確認 require 函式有沒有露出來

打開你手上的 loader 檔，先在裡面搜 window.loader。多數 webpack 打包檔已經幫你寫好了這一行，例如物件版的 loader 直接把 n 指給它：

!function (e) {
    var t = {};

    // 加载函数
    function n(r) {
        if (t[r])
            return t[r].exports;
        var o = t[r] = {
            i: r,
            l: !1,
            exports: {}
        };
        e[r].call(o.exports, o, o.exports, n);
        return o.exports.exports; // 返回 o.exports.exports，而不是整个 o.exports 对象
    }

    n.a = function () {

    }
    n.b = function () {

    }

    window.loader = n

看到最後那行 window.loader = n，就代表把手已經在門口了，你不用動它。多檔版的 bootstrap 也一樣，只是名字不同，它會在建立 __webpack_require__ 之後寫下 window.loader = __webpack_require__。

如果搜不到，代表這份打包檔沒有主動洩漏載入器，這時你自己在 require 函式定義之後補一行 window.loader = n;（n 換成實際的函式名）即可。這一步的成果很單純：確認或建立 window.loader 這個全域變數，之後所有呼叫都靠它。

步驟二：在模組執行處插一行 log

接著是整個手法的核心。找到 require 函式裡「呼叫模組」的那一行，在它前面插一行 console.log 把編號印出來。物件版的做法是這樣，log 加在 e[r].call(...) 的正上方：

        console.log("moduleID:::", r)
        e[r].call(o.exports, o, o.exports, n);

多檔版的位置一模一樣，只是變數名從 r 換成 moduleId：

        console.log("moduleId:::", moduleId)
        modules[moduleId].call(module.exports, module, module.exports, __webpack_require__);

為什麼偏偏插在這裡？因為這一行是「某個模組即將被執行」的唯一關口。不管模組是被誰、從哪裡、用什麼順序叫起來的，都一定得穿過這一行。把 log 放在快取判斷之後、模組執行之前，好處是：已經執行過的模組不會再被記錄，log 印出來的就是「本次真正被叫起來的新模組」，乾淨不重複。

前綴字串（"moduleID:::" 或 "moduleId:::"）是刻意的，方便你在 DevTools 的 Console 用關鍵字過濾，把所有模組軌跡一次撈出來。

步驟三：用 window.loader 呼叫目標模組

log 裝好後，就可以開始報編號了。物件版原始碼裡示範了最直接的呼叫：

window.loader("1002")

執行之後，Console 會依序出現兩行：先是我們自己插的 moduleID::: 1002，接著是模組 "1002" 內部的輸出 bar。若把回傳值印出來，還能看到它 this.exports 交出的結果：

console.log(window.loader("1001"))

這裡就是判讀的訣竅：你報哪個 id，第一個 log 就會印出哪個 id，緊接著是那個模組自己的輸出。於是「我呼叫了 1001」和「1001 的 log 是 foo」這兩件事就對上了。下一步就是靠這個對應關係，把你想找的那個值與產生它的模組編號綁在一起。

步驟四：逐一呼叫，縮小到目標模組

真實站點的模組編號是幾十上百個，你不可能一個一個手動試。這時可以用一個迴圈，把可能的編號全部點過一遍，讓 log 自己排出一張軌跡表。下面這段是為了方便而寫的輔助迴圈，不是原始碼的一部分：

for (let id = 0; id < 200; id++) {
    try {
        window.loader(id);
    } catch (e) {
        // 不存在的編號會報錯，略過
    }
}

跑完後，Console 裡會依序出現每個存在的模組編號。你把「產生簽名參數的那段邏輯」對照 log 找出來（例如某個模組執行後，你關心的那個參數就出現在視窗或全域變數上），就能鎖定它的編號。之後只要針對那個編號反覆呼叫、觀察輸入輸出即可。

要提醒一件事：逐一呼叫會把很多模組的初始化邏輯都跑起來，可能觸發網路請求或改動全域狀態。實際操作時，最好在乾淨的頁面或獨立的 Node 環境裡做，並把 log 當成觀察工具而不是無條件信任的結果。

做完長什麼樣

完成這一節後，你應該得到兩樣可驗證的成果。第一，Console 裡有一份清楚的模組軌跡：每一行 moduleID::: 後面跟著一個編號，對應到一個模組被執行的時刻。第二，你能用 window.loader("某個編號") 精準地重跑那個模組，並看到它交出的值。

接把手（window.loader）、插 log（模組執行前一行）、報編號（window.loader(id)）。這三步就能把「哪個模組產生了我關心的值」這件事，從猜測變成有紀錄可查。

單檔 bundle 到這裡就夠用了。但如果是上一節那種多檔 JSONP 版，光載入 loader 還不夠，模組還躺在別的檔案裡，得先把那些檔案載進來，模組才會齊全。下一節就把整套搬進 Node，把多檔 bundle 完整跑一次。
