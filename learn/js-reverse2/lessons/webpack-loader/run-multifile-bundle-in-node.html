在 Node 跑多檔 bundle、呼叫簽名模組

Step 4/4 · webpack 拆解與模組定位

學習目標

把多檔 JSONP bundle 的 loader 與各模組檔載進 Node、讓 webpackJsonp 的 callback 把模組合併起來，最後用模組 id 呼叫簽名模組並取得結果。

前言：一堆檔案，到底誰先誰後

上一節你在單檔 bundle 上練會了接把手、插 log、報編號。但真實的大型網站很少把東西放在一個檔案裡。你在 DevTools 的 Network 面板會看到好幾支 JS：一支只有幾百行、名字像 loader 或 runtime；接著一兩支幾萬行的 chunk-libs、app；HTML 用 <script> 把它們依序掛上去。

問題來了：你把這些檔案全部下載下來，該怎麼擺、用什麼順序載入？如果順序錯了，會出現「window.loader is not defined」，或者呼叫某個編號時告訴你模組不存在。這一節要講清楚多檔版的組裝順序，並把整套流程搬進 Node 跑一次：載入 loader、載入各模組檔、再用一個編號把簽名模組叫出來。

前置條件：你的 JS 已經能在 Node 執行（最簡單是先寫 window = global，再把檔案 require 進來）。若 bundle 依賴 document、navigator 等瀏覽器物件，得先補環境，否則一載入就報錯。

步驟一：先載入 loader 檔，把機制架起來

順序的第一條鐵則是：loader 永遠最先。它負責建立整個模組系統：快取、require 函式、以及接收模組的 JSONP 機制。看它關鍵的幾個部分：

function webpackJsonpCallback(data) {
    var chunkIds = data[0];
    var moreModules = data[1];
    var executeModules = data[2];
    …
    for (moduleId in moreModules) {
        if (Object.prototype.hasOwnProperty.call(moreModules, moduleId)) {
            modules[moduleId] = moreModules[moduleId];
        }
    }
    …
};

var installedModules = {};
…
function __webpack_require__(moduleId) {
    …
    console.log("moduleId:::", moduleId)
    …
    modules[moduleId].call(module.exports, module, module.exports, __webpack_require__);
    …
    return module.exports;
}

window.loader = __webpack_require__

var jsonpArray = window["webpackJsonp"] = window["webpackJsonp"] || [];
var oldJsonpFunction = jsonpArray.push.bind(jsonpArray);
jsonpArray.push = webpackJsonpCallback;

這段做了三件鋪路的工作。第一，建立 webpackJsonpCallback，它的工作是把某個檔案送來的模組（moreModules）逐一搬進 loader 內部的 modules 物件。第二，建立 __webpack_require__ 這支 require 函式，並把它指定成 window.loader。第三，也是多檔版最巧妙的一步：把全域的 window.webpackJsonp 準備成陣列，然後把它原本的 push 換成 webpackJsonpCallback。

為什麼要換 push？因為後面每一支模組檔都會「把模組 push 進 webpackJsonp」。但既然 push 已經被換成 callback，這個 push 動作實際上就等於「請 loader 把這些模組收進去」。檔案之間不需要互相 import，全靠這個被改造過的 push 當作通道。

步驟二：再依序載入每個模組檔

loader 就緒後，接著載入模組檔。每一支模組檔執行起來，幾乎都長這個樣子：把一批模組 push 給 window.webpackJsonp：

!(window["webpackJsonp"] = window["webpackJsonp"] || []).push([["app"], {
    0: function (e, t, n) {
        e.exports = n("56d7")
    },
    "1001": function () {
        console.log("1001 fn ....")
    },
    "1002": function () {
        console.log("1002 fn ....")
    }
}, [[0, "runtime", "chunk-elementUI", "chunk-libs"]]]);

另一支模組檔形式完全一樣，只是帶進來的編號不同：

!(window["webpackJsonp"] = window["webpackJsonp"] || []).push([["app"], {
    0: function (e, t, n) {
        e.exports = n("56d7")
    },
    "1003": function () {
        console.log("1001 fn ....")
    },
    "1004": function () {
        console.log("1002 fn ....")
    }
}, [[0, "runtime", "chunk-elementUI", "chunk-libs"]]]);

讀懂這一行，多檔版就通了。陣列的第一格 ["app"] 是這批模組所屬的 chunk 名稱；第二格是「編號對函式」的模組表，也就是真正被搬進 loader 的 moreModules；第三格是執行清單。因為 loader 早就把 push 換成了 callback，這兩支檔案被載入時，等於連續兩次呼叫 webpackJsonpCallback，把 "1001" 到 "1004" 這幾個模組搬進 loader 的 modules 裡。

所以載入順序是：先 loader，再所有模組檔。loader 一個人先來把櫃子與管理員備好，模組檔之後一個一個把書送進來。順序顛倒的話，模組檔執行時發現沒有被改造過的 push，模組就進不了 loader。

步驟三：串起驅動檔，呼叫目標模組

把整件事收攏成一支小小的驅動檔：先 require loader，再 require 兩支模組檔，最後呼叫 window.loader。原始碼裡的驅動檔就長這樣：

require("./03 多文件的webpack")
require("./04 mod1")
require("./05 mod2")

window.loader("1001")
window.loader("1003")

前兩行的 require 是 Node 的載入語法，用來把「本機這幾支檔案」依序執行。順序正是上一段說的鐵則：先 loader，再模組。等三支都跑過，模組已經全部進櫃，最後兩行才用 window.loader("1001")、window.loader("1003") 報編號呼叫。

因為步驟二插的 console.log("moduleId:::", moduleId) 還在，執行後你會看到 log 依序印出 1001、1003，緊接著是對應模組自己的輸出。這就是「模組齊全 → 依編號呼叫」的完整軌跡。

步驟四：把編號換成簽名模組

前面的 demo 用 "1001"、"1003" 只是為了示範。真實站點的做法一模一樣，差別只在兩件事：把模組檔補齊，把編號換成簽名模組的 id。

  1. 在 DevTools 的 Network 面板抓下所有參與的 JS：loader 一支，模組檔可能有好幾支。
  2. 依「loader 在前、模組檔在後」的順序載入 Node。
  3. 用步驟三的手法插 log、逐一呼叫，找出產生簽名參數的那個模組編號。
  4. 用 window.loader("簽名模組的 id") 拿到它匯出的函式，餵入需要的參數，取得簽名結果。

之後就能像單檔那樣，把這個值接進 Python 的請求流程裡。多檔版比起單檔版，真正多出來的只有「按順序把模組檔餵進來」這一步。

做完長什麼樣

跑完這一節，你會得到一份能在 Node 獨立重現目標模組輸出的組裝流程：三支以上的檔案依序載入，Console 印出一條清楚的模組執行軌跡，最後一行是你用某個編號呼叫後拿回的簽名值。這個流程與上一節的定位手法合起來，就是一套對任何 webpack 站點都適用的搬移方法。

這裡刻意不深談「為什麼瀏覽器環境要補齊、缺了會怎樣」，那是補環境那個節點的主題。這一節把重點放在「檔案組裝的順序」，因為那是多檔 bundle 最容易失敗的地方，也是它與單檔版本唯一的關鍵差異。
