webpack bundle 的骨架：IIFE、require 函式與快取

Step 1/4 · webpack 拆解與模組定位

學習目標

看懂一段 webpack bundle 的最小骨架：最外層的 IIFE、內部的 require 函式、模組快取，並認出 window.loader 就是逆向時要接上的那把把手。

前言：為什麼網站的 JS 裡找不到一個叫 getSign 的函式

你在 DevTools 的 Sources 面板點開目標網站的 JS，想搜「sign」、「token」這類關鍵字，結果看到的是一坨沒有名字、層層包起來的程式。你想找的那個加密函式明明存在（參數就是它算出來的），但它不叫 getSign，而是被編到某個編號裡，藏在一個巨大的檔案深處。

這不是網站故意混淆，是打包工具的日常。現在的網站幾乎都用 webpack 這類工具把幾百個模組打包成一個或幾個檔案。打包之後，程式不再是「一連串函式與變數」，而是「一位圖書館員，加上一櫃子用編號排好的書」。你要找的加密邏輯，就是其中一本書，它只有編號，沒有書名。

這一節先把這個骨架拆給你看：書櫃怎麼蓋起來、那位圖書館員怎麼依編號取書、以及你之後要靠哪個開關把它叫出來。看懂這一層，後面才有辦法在櫃子裡精準地抽出你要的那一本。

骨架一：最外層是一個立即執行函式

webpack 打包出來的檔案，外型通常長這樣：一個用括號包起來的匿名函式，後面緊接著一組括號把它當場執行掉，再把「所有模組」當參數傳進去。這種寫法叫立即執行函式運算式（IIFE，Immediately Invoked Function Expression），寫成 !function (形參) { … }(功能模組) 的形式。

為什麼要用 IIFE？因為它替包好的程式開了一個私密空間。裡面宣告的變數不會漏到全域去，也就不會跟別人打架。整個 bundle 對外只露出極少數東西，通常是刻意設定的那一個。

把參數的位置看清楚，是判斷型態的第一步。這個「功能模組」的位置，可能是用中括號包起來的陣列，也可能是用大括號包起來的物件，後面講型態時會專門分辨。現在先記住：看到一個被當場執行的匿名函式，把一大包東西當參數吃下去，這就是 webpack 的門面。

骨架二：核心是那個 require 函式

真正的主角在 IIFE 裡面。它通常叫 n（陣列版常叫 n，多檔版叫 __webpack_require__），做的事就一件：你報一個模組編號，它把對應的模組執行起來，並回傳結果。這就是那位圖書館員。

看一段最小的、物件版的載入器。這段是逐字引自原始碼的：

!function (e) {
    var t = {};

    function n(r) {
        if (t[r])
            return t[r].exports;
        var o = t[r] = {
            i: r,
            l: !1,
            exports: {}
        };
        e[r].call(o.exports, o, o.exports, n);
        return o.exports.exports;
    }
    window.loader = n

逐行看。外層的 e 就是「模組的集合」，也就是那一櫃子書。var t = {} 是快取，下面會單獨講。function n(r) 是 require 函式，參數 r 就是模組編號，它可能是索引或 key。

進到函式裡，第一件事是查快取：if (t[r]) return t[r].exports;。如果這個編號先前跑過，直接把它上次的結果交出去，不再重跑。這就是為什麼同一個模組不管你呼叫幾次，它的初始化邏輯只會執行一遍。

沒跑過的話，就幫它建一筆新紀錄 var o = t[r] = { i: r, l: !1, exports: {} }，其中 i 記編號、l 記「有沒有載入過」、exports 是這個模組要交出東西的地方。

接著是關鍵那一行：e[r].call(o.exports, o, o.exports, n)。它把 e 裡編號 r 的那個模組函式叫起來執行，同時把三樣東西綁進去當參數：它自己的 exports、它自己的紀錄 o、以及 require 函式本身 n（這樣模組內部才能再去要別的模組）。

最後 return o.exports.exports;。注意這個尾巴：回傳的是 o.exports.exports，不是整個 o.exports 物件。這是這份原始碼特別標記的細節：模組是用 this.exports = 值 把結果塞在 exports 這個位置，所以再取一層才拿得到真正要的東西。

骨架三：模組怎麼被存、怎麼被叫

上面那位圖書館員，服務的書櫃長什麼樣？物件版的書櫃是一張「編號對函式」的表：

}(
    {
        "1001": function () {
            console.log("foo");
            this.exports = 100;
        },
        "1002":
            function () {
                console.log("bar");
                this.exports = 200;
            }
    }
);

console.log(window.loader("1001"))

你可以看到模組的編號是字串，像 "1001"、"1002"，而不是名字。這就是為什麼你在檔案裡搜不到函式名：模組的身分被編號取代了。呼叫的方式也很直白，window.loader("1001")，報上編號，拿回該模組 this.exports 交出的值。

陣列版的書櫃則是把模組依序排進一個陣列，編號就變成 0、1、2 這種索引：

!function (e) {
    var t = {};

    function n(r) {  // r:索引或key
        if (t[r])
            return t[r].exports;
        var o = t[r] = {
            i: r,
            l: !1,
            exports: {}
        };
        e[r].call(o.exports, o, o.exports, n);
        return o.exports.exports;
    }

    // 调用模块函数
    console.log(n(0))
    console.log(n(0))
    console.log(n(1))
}([
    function () {
        console.log("foo");
        this.exports = 100;
    },
    function () {
        console.log("bar");
    }
]);

注意 n(0) 被叫了兩次。第一次進去執行、把結果放進快取；第二次直接命中快取、原封不動回傳。這正是快取存在的意義：模組只初始化一次。

骨架四：那把被刻意留在門口的把手

如果 require 函式只存在 IIFE 裡面，外面的人根本碰不到它，那逆向就無從下手。所以 webpack 幾乎都把它洩漏到全域，最常見的寫法就是一行 window.loader = n。多檔版的 bootstraps 也一樣，只是名字換成 window.loader = __webpack_require__。

這一行，等於把圖書館員請到櫃檯外面站著。你在 Node 或 DevTools 裡只要喊 window.loader(編號)，就能直接驅動整個 bundle，不必重寫任何演算法。整個 webpack 逆向的起點，就是找到這一把把手。

把觀念串起來

用一句話整理 webpack bundle 的骨架：外層是 IIFE，負責把一切包進私密空間；裡面是一個依編號取模組的 require 函式，搭配一份快取；模組的集合以參數的形式餵進來，可能是陣列、物件或更複雜的機制；而 require 函式通常會被丟到 window.loader，成為你唯一需要接上的介面。

webpack 把程式變成「載入器 + 一櫃子編號模組」。你要做的不是讀懂整包，而是認出那個 require 函式、找到它洩漏出來的把手（window.loader）、再依編號把加密模組抽出來。

骨架看懂了，下一步要處理一個現實問題：櫃子的形式不只一種。同樣是「載入器加模組」，陣列版、物件版、多檔版長得都不太一樣，模組編號的形式也不同。下一節就來學怎麼一眼判斷手上的打包檔屬於哪一型。
