非對稱加密：公鑰加密、私鑰解密的 RSA 模型

Step 3/5 · 對稱與非對稱加密：AES/DES、RSA、國密

學習目標

能說明非對稱加密為什麼需要公鑰與私鑰兩把 key，講清楚「公鑰加密、私鑰解密」的方向，並認出 jsencrypt 的 setPublicKey／setPrivateKey 特徵。

前言：登入頁那串密碼，前端竟然沒有 key

你盯著一個登入介面的請求，看到送出去的 password 已經變成一長串 Base64，於是很自然地往上一節的路線走：找對稱加密的 key。可是搜遍了整包 JS，怎麼找都找不到那 16 個位元組的密鑰。奇怪的是，明明沒有 key，密文卻還是能產生出來。

這不是找漏了，而是這一站用的根本不是對稱加密。你想想：對稱加密的加密與解密共用同一把 key，如果前端要能加密，那把 key 就非得放在前端不可，那不就等於把鑰匙貼在保險箱上嗎？正是為了避開這個矛盾，站台改用另一套模型：前端只放一把可以公開的鑰匙用來加密，真正能解開的鑰匙留在伺服器。這就是非對稱加密。

為什麼需要兩把 key

非對稱加密需要兩個金鑰，一組是公開金鑰（public key，簡稱公鑰），一組是私有金鑰（private key，簡稱私鑰）。公鑰與私鑰是一對，兩者互相搭配。它的核心規則只有一句：用公鑰把資料加密之後，只有對應的私鑰才能解開。因為加密與解密用的是兩把不同的 key，這種做法就叫做非對稱加密，RSA 是最廣為使用的代表。

這個設計解決了對稱加密在前端場景的死結：公鑰可以大方地公開，寫在 JS 裡也沒關係，因為它只能加密、不能解密；私鑰則留在伺服器端，不曾出現在前端。所以逆向這類加密時，你找的「金鑰」其實是公鑰，而且它本來就攤在那裡給你看，你要做的是把它撈出來，重現加密過程。

使用流程與方向

使用時的方向固定是「公鑰加密、私鑰解密」，不能反過來當成日常用途。可以這樣想像：公鑰像是一個只有投遞口的信箱，任何人都能往裡面投信（加密），但只有握有私鑰的人能打開信箱把信拿出來（解密）。

  • 假設 A、B、C 三方要互相加密通訊，大家各自把自己的公鑰公開，其他人就用該公鑰加密訊息，只有持有對應私鑰的那一方能解讀。
  • 公鑰可以公開分享，私鑰必須自己妥善保留。
  • 典型場景是使用者輸入的支付密碼會先經過 RSA 加密才送出，密碼在前端就被公鑰鎖上，即使封包被攔截，沒有私鑰也解不開。

另外要記住一個實務上的取捨：非對稱加密的演算法強度較高、安全性依賴演算法與金鑰，但正因為運算複雜，它的加解密速度比對稱加密慢。所以真實系統很少整段資料都用 RSA 處理，更常見的是拿它來保護體積很小的東西（例如密碼），或是在開頭先交換一把對稱加密用的 key，之後才用對稱加密處理大量資料。

jsencrypt：前端最常見的 RSA 實作

前端要做 RSA，最常見的套件是 jsencrypt，用 npm install jsencrypt 安裝。它把操作濃縮成幾個方法，認得這幾個名字，你就能在混淆過的程式碼裡很快定位：

  • RSA：出現在套件名或註解裡，是最直接的線索。
  • setPublicKey：設定公鑰，看到它就代表接下來要做的是「加密」。
  • setPrivateKey：設定私鑰，代表接下來要做的是「解密」，如果這個出現在前端，本身就是一個警訊，後面會再提。
  • encrypt、decrypt：加解密函式名。

還有一個很容易忽略的細節：jsencrypt 原本是設計給瀏覽器用的，它會去讀取瀏覽器才有的 window 與 self 這兩個全域物件。當你想把它搬到 Node 環境執行時，必須先補上這兩個東西，否則一載入就報錯。課程裡的示範就是先用兩行把它們指向 globalThis：

window = globalThis;
// 添加这行
self = globalThis;

const JSEncrypt = require('jsencrypt');

補完之後，jsencrypt 就能在 Node 下正常呼叫。典型的使用長相如下，公鑰與私鑰都是字串，格式是介於 -----BEGIN PUBLIC KEY----- 與 -----END PUBLIC KEY----- 之間的一大段 Base64，稱為 PEM 格式：

window = globalThis;

const JSEncrypt = require('jsencrypt');

//使用公钥加密
var encrypt = new JSEncrypt();//实例化加密对象
encrypt.setPublicKey(PUBLIC_KEY);//设置公钥
var encrypted = encrypt.encrypt('hello bobo!');//对指定数据进行加密
console.log(encrypted);//使用私钥解密

公鑰與私鑰可以線上生成，也可以自己用工具產生。前端程式裡如果出現了一段完整的私鑰（-----BEGIN PRIVATE KEY-----），通常只有兩種可能：一種是開發者拿它來做本機測試的輔助功能，另一種則是設計失誤：把應該留在伺服器的私鑰直接送到了瀏覽器。後者等於門鎖連鑰匙一起交給對方，是整個加密流程失效的經典失誤。

小結

非對稱加密用一對金鑰：公鑰可以公開、負責加密，私鑰留在伺服器、負責解密，方向固定是「公鑰加密、私鑰解密」。它解決了對稱加密在前端「要加密就得先洩漏 key」的矛盾，代價是速度較慢，因此常用來保護密碼、授權啟用這類小量資料，而不是整段 body。前端最常見的實作是 jsencrypt，認得 setPublicKey、setPrivateKey、encrypt、decrypt 與那段 window = globalThis; self = globalThis; 的 Node 補丁，你就能在混淆的程式碼裡找到它。

知道模型之後，下一步就是把這套流程親手做一遍：用 Python 產生一對公私鑰、匯出成 PEM，再用它把資料加密、base64 傳出去，最後用私鑰解回來，並對照 jsencrypt 的 Node 寫法。
