被偵測到了：toString 檢測與它的兩層破解

Step 3/5 · Hook 與 Proxy 攔截

學習目標

判斷網站用的是哪一層 toString 檢測，並選對應的破解（改實例的 toString，還是改 Function.prototype.toString）。

前言：hook 成功了，網站卻說「環境異常」

上一節你把 atob hook 起來，Console 也確實印出了每次的參數與回傳。但你送出請求後，網站卻回你「環境異常，請稍後再試」，或乾脆卡在驗證頁不讓你往下。你的程式沒錯，錯的是你被發現了。

很多網站會主動檢查自己的函式有沒有被別人動過手腳。最常見的檢查方式，就是去比較一個函式的 toString() 在「還沒被你 hook 之前」和「被你 hook 之後」長得不一樣。這一節要做的決定很單純：面對這種檢測，你要攔到什麼程度的偽裝才夠？是只把自己動過的 atob 遮起來，還是把整個函式家族的 toString 都換掉？兩者成本與風險不同。

網站怎麼檢查：比較 toString 的前後

先搞清楚它在比什麼。在瀏覽器裡，內建函式的實作不會顯示真正的一堆程式碼，而是顯示一段固定的標記 [native code]。所以原生的 atob.toString() 會回傳類似 function atob() { [native code] } 這樣的字串。

當你把它換成自己寫的包裝函式之後，atob.toString() 回傳的就變成你那段包裝的原始碼，一串帶著 console.log 的實際程式碼。網站只要把「預期是 [native code]」跟「現在拿到的是實際程式碼」一比，就知道 atob 被人動過了。這就是最根本的 toString() 檢測法。

問題是，這個檢測有兩個層次。最直覺的是直接呼叫 atob.toString()；但更狡猾的網站會改用 Function.prototype.toString.call(atob)，也就是借函式原型上的 toString 來檢查，而不是用 atob 自己的。這兩層你的破解方法不一樣。

三個選項並排比

選項做法擋得住 atob.toString()擋得住 Function.prototype.toString.call(atob)影響範圍
不處理直接放著否否無
改實例層atob.toString = …是否只影響 atob
改原型層Function.prototype.toString = …是是影響所有函式

選項一：改實例層的 toString

最省事的做法，是在 hook 完 atob 之後，順手把它自己的 toString 也改掉，讓它回傳那個看起來很「原生」的字串：

_atob = atob;//保存原函数

atob = function (str){
    console.log("正在执行atob方法, 参数:", str);
    let result = _atob(str);
    console.log("正在执行atob方法, 返回值:", result);
    return result;
}
//重写atob函数的toString方法
atob.toString = function(){
    return 'function atob() { [native code] }'
}

這樣一來，任何直接呼叫 atob.toString() 的檢查，看到的都會是 function atob() { [native code] }，跟原生的一模一樣。它成本低、影響範圍只有 atob 一個函式。但它有個破口：如果網站不是用「atob 自己的 toString」，而是繞到原型上去檢查，這個改法就攔不住了。

選項二：改原型層的 toString

先看它為什麼能繞過你：

Function.prototype.toString.call(atob)
//调用函数原型对象中的toString进行的检测，而不是atob实例对象的toString了。

Function.prototype.toString 是所有函式共用的那個 toString。call(atob) 的意思是「把這個共用的 toString 借來、以 atob 的身分執行」。所以它根本不會去看你掛在 atob 身上的那個 toString，實例層的偽裝當場失效。

要擋這一層，就得直接換掉共用的那個原型方法：

_atob = atob;//保存原函数

atob = function (str){
    console.log("正在执行atob方法, 参数:", str);
    let result = _atob(str);
    console.log("正在执行atob方法, 返回值:", result);
    return result;
}
//重写原型链上的toString方法
Function.prototype.toString = function(){
    return `function ${this.name}() { [native code] }`
}

關鍵在 ${this.name}：this 是呼叫 toString 的那個函式，this.name 就是它的名字。這樣不管是 atob、還是別的函式來呼叫，都會回傳「自己的名字 + [native code]」，看起來都很正常。

反例：為什麼不能把名字寫死

你可能會想：那我直接把回傳字串寫死成 function atob() { [native code] } 不是更省事？不行。因為你改的是全體函式共用的 toString，一旦寫死名字，之後任何函式呼叫它，回傳的函式名都會變成 atob。例如網站去檢查 Location.toString()，結果拿到的卻是 function atob() { [native code] }，這種牛頭不對馬嘴的回應，本身就是一個強烈的可疑訊號，反而更容易被抓。用 this.name 動態取值，才能讓每個函式都回報自己的名字。

該選哪一層：判別問句

決定之前，先問自己兩個問題：

  • 網站只是呼叫 atob.toString() 嗎？如果是，改實例層就足夠，範圍小、副作用最少。
  • 網站有沒有用 Function.prototype.toString.call(atob) 這種從原型借方法的寫法？如果有，實例層擋不住，必須改原型層。

如果當下無法確定對方用哪一種，實務上會直接改原型層並用 this.name，因為它同時涵蓋兩種情況。代價是影響範圍最大，所有函式的 toString 都被你換掉了，所以要更小心不要讓回傳格式露餡。

小結

網站偵測 hook 最常見的手法，是把函式的 toString() 拿去跟原生的 [native code] 比對。破解分兩層：只改 atob.toString（實例層）範圍小、但擋不住 Function.prototype.toString.call(atob)；改 Function.prototype.toString（原型層）兩層都擋得住，但影響所有函式，而且回傳名字必須用 this.name 動態取，寫死會露餡。判準就是：對方用哪一層檢查，你至少要能擋到那一層。

到這裡，hook 這條線就走完了：會攔、會選對時機、也懂得怎麼不被抓。接下來要換另一件工具。hook 攔的通常是「某一個」函式或屬性，但當你要面對的是整個 window、整個 document，一個個 hook 就太慢了。下一節要看的 Proxy，能替整個物件套一層代理，讓所有讀寫自動被記錄。
