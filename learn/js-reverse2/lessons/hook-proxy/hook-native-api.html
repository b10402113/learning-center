攔住原生函式：在頁面載入前 hook atob 與 document.cookie

Step 2/5 · Hook 與 Proxy 攔截

學習目標

照著瀏覽器操作順序，在頁面程式碼執行前把原生的 atob 與 document.cookie hook 起來，並確認攔得到每一次讀寫。

前言：要攔的不是你的函式，是瀏覽器自己的

上一節你已經會 hook 頁面裡的函式了：存下原函式、換上包裝，就能看到它被誰、用什麼參數呼叫。但你會遇到的目標站，關鍵的編碼、解碼往往不是自己寫的，而是直接呼叫瀏覽器原生的函式。例如很多站會用 atob（原生 base64 解碼函式）把一段字串解開，或反過來把 cookie 讀進來再加工。

攔截這些原生 API 的困難，跟上一節不一樣：它們不是你定義的，而且很可能在你打開 DevTools 之前就已經被呼叫過了。所以這一節的重點不是新的程式碼技巧，而是一套操作順序：你必須搶在頁面自己的程式碼之前把 hook 裝好，而且中途不能重新整理頁面。搞懂這個時機，你才能真的攔到。

前置條件：你已經知道怎麼在 DevTools 裡開斷點、使用事件監聽器（DevTools 那個節點），也理解上一節「存下原函式、換上包裝」的骨架。

你要得到的結果

做完這一節的操作之後，當頁面每次呼叫 atob，或每次讀寫 document.cookie，Console 都會印出當下的參數與回傳值。你不需要一行一行讀它的原始碼，就能知道原生 API 被餵進什麼、又吐出了什麼。

動手前要先懂的兩件事

第一，時機。原生函式在頁面一開始載入時就可能被用到。如果你是在頁面跑完之後才裝 hook，那段早期的呼叫你根本攔不到。所以我們要用「事件監聽器斷點」讓瀏覽器在執行任何腳本之前先停下來，趁這個空檔把 hook 裝好。

第二，不能重新整理。你 hook 的是「現在這個頁面」裡的函式。一旦重新整理，瀏覽器會重新載入一份全新的文件，你剛才在 Snippets 裡執行的 hook 就隨之消失，回歸成原生的函式。所以裝好之後，只能繼續執行、不能按重新整理。

操作步驟：先攔住執行，再裝 hook

  1. 開一個空白頁，並在這個空白頁上打開開發者工具。從空白頁開始，是為了不讓任何目標站的腳本提前跑掉。
  2. 在 DevTools 的 Sources 面板裡，開啟事件監聽器斷點（Event Listener Breakpoints）中的 Script 類別。它的作用是：讓瀏覽器在執行腳本的第一行之前就暫停。
  3. 造訪你要分析的目標頁。因為上一步的斷點，執行會停在頁面腳本開始之前，此時你有一個乾淨的空檔可以動手。
  4. 在 Sources 面板的 Snippets（程式碼片段）區新增一段 hook 程式碼，替它打上一個斷點，然後執行它。這樣 hook 就裝好了。
  5. 取消剛剛的 Script 事件監聽器，因為此時 atob 已經成功被 hook，不需要再靠斷點攔人了。切記不可重新整理頁面。
  6. 放行讓頁面繼續執行，觀察 Console，確認每次 atob 被呼叫時都被記錄下來。

步驟 4 的內容：hook 原生 atob

要放進 Snippets 的程式碼如下。atob 是瀏覽器內建、用來解碼 base64 資料的函式，這裡把它包起來：

 _atob = atob;//保存原函数

atob = function (str){
    console.log("正在执行atob方法, 参数:", str);
    let result = _atob(str);
    console.log("正在执行atob方法, 返回值:", result);
    return result;
}

逐段看：_atob = atob 先把原生的 atob 存起來；接著把全域的 atob 換成一個新函式，它先印出收到的參數 str，用存起來的 _atob 算出結果，再印出回傳值，最後把結果 return 出去。對頁面來說，呼叫 atob(str) 的結果完全沒變，只是中間多了一層記錄。

同樣的手法：hook document.cookie

cookie 不是函式，而是一個屬性，所以換成用屬性 hook 的寫法：用 Object.defineProperty 攔它的讀取（get）與設定（set）。操作步驟跟攔 atob 完全一樣。

_cookie = document.cookie;
Object.defineProperty(document,'cookie',{
    get(){
        console.log("正在获取cookie:", _cookie);
        return _cookie;
    },
    set(value){
        console.log("正在设置cookie:", value);
        _cookie = value;
    }
});

_cookie 存下原本的 cookie 值；之後任何人讀 document.cookie 就會走 get，把當前值印出來再回傳；任何人寫 document.cookie = ... 就會走 set，把要寫入的值印出來。這樣一來，網站是什麼時候、寫了什麼 cookie 進去，你一目了然。

為什麼一定要用「頁面載入前」的斷點

你可能會想：直接在頁面跑完後，於 Console 貼上 hook 不行嗎？可以，但只能攔到「之後」的呼叫。原生 API 常常在頁面初始化的最早期就被使用，那時你的 hook 還沒裝上，最關鍵的那一次就被漏掉了。事件監聽器斷點的作用，正是把時間軸往前挪到頁面腳本執行之前，讓你在它第一次用到原生 API 之前就把包裝裝好。

預期結果與驗證

放行之後，只要頁面一用到 atob，Console 就會出現類似「正在執行 atob 方法，參數: ……」與「回傳值: ……」兩行。如果什麼都沒印，通常是三個原因之一：斷點開得太晚（頁面已經跑過）、中途重新整理了頁面、或這段腳本根本沒用到 atob。逐項回頭檢查就能定位。

小結

要攔截瀏覽器原生 API（例如 atob、document.cookie），靠的不是新語法，而是時機：先用 Sources 裡的 Script 事件監聽器斷點讓頁面在執行腳本前暫停，趁空檔把 hook 裝進 Snippets 並執行，再取消斷點放行，而且全程不能重新整理。函式用「存原函式、換包裝」，屬性用 defineProperty 的 get／set，跟上一節一模一樣，只是這次對象是瀏覽器自己的東西。

攔得進去之後，新的問題馬上浮現：網站會不會察覺自己被攔了？會。而且最常見的檢查方式，就是比較函式的 toString 有沒有被動過手腳。下一節要講的就是這場貓捉老鼠，以及破解檢測時該改哪一層。
