瑞數 cookie 流程：兩次請求與三個動態輸入

Step 5/5 · 補環境與環境檢測

學習目標

講出瑞數的兩次請求、cookie1／cookie2 的角色，以及 meta、ts、大自執行函式三個動態輸入如何共同生成 cookie2。

前言：頁面還沒看到，就先被回了 412

你打開 DevTools，輸入你要爬的那個網址。第一個請求送出去，回來的不是頁面，而是一個 202 或 412，沒有你要的內容，卻帶著一個 cookie。重新送一次，這次才拿到真正的頁面。往 Scripts 面板一看，多出好幾個以「VM」開頭的檔案，點開來是密密麻麻、每個人看到的都不太一樣的程式碼。

這就是瑞數。它在你和網站之間插了一道「先證明你是真的瀏覽器」的關卡，而前面四節學的補環境，正是通過這道關卡的三種方法之一。這一節把整個流程拆開：為什麼要請求兩次、兩個 cookie 各由誰產生、那三個每次都不一樣的動態輸入又在做什麼。

瑞數在防什麼

瑞數是一家做動態應用安全防護的公司，它的產品核心是「動態安全」：透過動態封裝、動態驗證、動態混淆、動態令牌等技術，讓伺服器回傳的底層程式碼持續變換，增加行為的不可預測性，替網站提供從用戶端到伺服器端的防護。對爬蟲來說，它可以理解成進入 JS 逆向世界的一道代表性門檻。

要通過它，實務上主要有三條路：

  1. 自動化工具：讓真正的瀏覽器（或自動化瀏覽器）去執行，繞過人工補環境。
  2. 補環境：把那段 JS 搬回 Node，補齊前端物件後自己跑出結果。這正是這個節點在教的路線。
  3. 純算：完全看懂演算法後，用 Python 等語言自己重寫。

兩次請求與兩個 cookie

瑞數的網站會對同一個頁面網址（文件請求）請求兩次，流程如下：

  1. 第 1 次請求頁面網址，回來的不是內容，而是一個 cookie1，加上一段 HTML 原始碼，以及 202 或 412 的回應碼。
  2. 這段 HTML 原始碼裡藏著三個要素，它們在本地一起算出 cookie2：
    • 一個 meta 標籤，它的 content 內容很長，而且是動態的，每次請求都不一樣，會在 eval 執行第二層 JS 時被用到。
    • 一段 ts 程式碼，它後面的自執行函式會解密檔案內容，生成 eval 執行時需要的 JS 原始碼，也就是第二層的 vm 程式碼。
    • 一個大自執行函式，每次請求首頁都會動態變化，它會給 window 加上一些屬性（例如 $_ts），這些屬性會在 vm 裡被使用。
  3. 第 2 次請求頁面網址，這次同時帶著 cookie1 與 cookie2，才取回真正的頁面內容。

換句話說，cookie1 是伺服器在第 1 次請求時發的，而 cookie2 是第 1 次回應裡那三個動態要素在本地算出來的。沒有 cookie2，第 2 次請求就拿不到真頁面。

cookie 的版本與後綴

那三個要素每次都變，所以 cookie2 也不可能寫死，這正是必須補環境、把那段 JS 跑起來的原因。不同的瑞數世代，cookie 的名字與後綴也不一樣：

世代兩個 cookie 的後綴後綴 S／O後綴 T／P
瑞數 3、4 代 以 S 與 T 結尾 第 1 次請求回傳 由 JS 生成、動態變化
瑞數 5、6 代 以 S 與 T 結尾（部分特殊 5 代用 O 與 P） 第 1 次 412 請求回傳 由 JS 生成

幾個判讀線索：S／T 前面通常會跟著 80 或 443 這樣的數字；而 cookie 值的第一個數字，就是瑞數的版本。所以在實際站點上，你光看 cookie 的名字與格式，就能大致判斷面對的是哪一代。

VM 檔案與入口

DevTools 裡那些以「VM」開頭的檔案，很容易讓人以為是專案原始碼。其實 VM 是 Virtual Machine（虛擬機）的縮寫，這些檔案代表的是由瀏覽器動態生成並執行的臨時腳本：它們不是專案的一部分，也不是實際存在的實體檔案，而是存在於瀏覽器記憶體中。

它們之所以出現，是因為程式碼用了 eval 或 new Function 去動態執行一段字串。當你在這種動態生成的程式碼上設斷點時，Chrome 就會在一個 VM 開頭的檔案裡顯示它，例如 VM111.js，這個檔案只為了除錯而存在。

那要怎麼找到入口？因為第 1 次回應的 index.html 是動態的，通常先把檔案替換成本地版本方便除錯，接著在 index.html 裡直接搜尋 .call。這個位置通常就是分析瑞數時的入口：圖中的 _$jL 實際上就是 eval，它傳入的第一個參數（如 _$iC）是 Window 物件，第二個參數（如 _$eB）就是 VM 虛擬機裡的 IIFE 自執行程式碼。在入口處單步除錯，就能進入 VM 環境，後續的斷點都在這個環境裡下。

補環境在瑞數流程裡的角色

把這些連起來看，這個節點前面學的補環境，就是在做「第 1 次請求之後、第 2 次請求之前」那段本地計算：把從 HTML 拿到的三個動態要素餵進補好的環境，讓那段 ts／vm 程式碼跑起來，產出 cookie2。實際開始補時，起手式通常長這樣，先把 metaContent 填進去、把最上層物件對齊、把計時器與事件補成不做事的方法：

小結

瑞數用「兩次請求、兩個 cookie」擋人：第 1 次頁面請求回傳 cookie1 與一段 HTML（狀態碼 202／412），HTML 裡的動態 meta content、ts 解密程式碼、大自執行函式三個要素，在本地一起算出 cookie2；第 2 次請求帶著 cookie1＋cookie2 才拿回真頁面。VM 檔案是 eval／new Function 產生的臨時腳本，可從 .call 找到進入 VM 的入口。補環境是通過瑞數的其中一條路：把三個動態要素注入補好的環境，讓 JS 跑出 cookie2。

這個節點走到這裡，你已經把「補環境」從原理、工具（Proxy）、清單（八大物件）、檢測（是不是瀏覽器／是不是 Node）到代表性場景（瑞數）串成一個完整迴圈。之後當你在真實站點上遇到動態 cookie，就是把這個迴圈再跑一次：抓第一批動態輸入、注入、執行 JS、取回 cookie、帶資料重放。
