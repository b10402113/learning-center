瀏覽器 JS 搬進 Node 就壞掉：window 與 global 的分岔

Step 1/5 · 補環境與環境檢測

學習目標

說出瀏覽器加密 JS 在 Node 執行失敗的兩個根因（頂級物件不同、Node 專屬識別字外洩），並認出「補環境」要解決的正是這件事。

前言：複製貼上之後，第一行就爆了

你在 DevTools 裡追到了一個網站的加密入口，把那段 JS 整整一段複製下來，存成 sign.js，回到終端機敲下 node sign.js。結果程式連加密函式都還沒跑進去，第一行就丟出 ReferenceError: window is not defined。你回頭看瀏覽器，同樣這段程式碼在 DevTools 的主控台裡跑得好好的。

這不是你的程式寫錯，也不是 Node 壞了。原因是那段 JS 從一開始就不是為 Node 寫的：它是為瀏覽器寫的，隨手就會用到 window、document、navigator 這些只有瀏覽器才有的東西。當你把它搬到 Node，這些東西一個都不存在。所謂「補環境」，就是在本機把這些缺少的前端物件補到「夠這段程式碼用」，讓它以為自己還待在瀏覽器裡。這一節先把「為什麼會壞」講清楚，因為如果只是照抄別人的補環境範本，換一個網站你又會卡住。

兩種執行環境：瀏覽器與 Node

瀏覽器與 Node 都能跑 JavaScript，但它們給 JS 的「家」不一樣。在瀏覽器裡，最外層的那個物件是 window；你在全域宣告的任何變數或函式，都會自動變成 window 的屬性。比如你寫 var yuan = 10;，之後就能用 window.yuan 讀到它。

到了 Node，最外層的物件換成了 global。Node 裡根本沒有 window 這個東西，也沒有 document、navigator、location。所以那段瀏覽器 JS 只要一讀 window.xxx，就是讀一個不存在的東西，直接拋錯。

比較項目瀏覽器Node
最外層的物件windowglobal
DOM 物件（document 等）有沒有
navigator、location、screen有沒有
Node 專屬識別字沒有global、process、Buffer、__dirname、__filename

注意最後一列。它看起來只是「Node 多了幾個東西」，但這其實是第二個根因的來源，而且是補環境裡最容易被忽略的一環。

根因一：頂級物件不同，window 根本不存在

第一個根因很直觀：那段 JS 假設自己活在 window 底下，但 Node 把它放進了 global。最常見的補法是直接在 Node 裡宣告一個 window，讓它指向 global，這樣一來全域變數就會同時落在兩邊，程式碼讀 window.xxx 也讀得到。

window = global
window.window = window
window.self = window
window.top = window

這四行是很多補環境檔案的開頭。第一行把 window 接到 global，後三行則是讓 window 自己指向自己，因為前端程式碼有時會透過 window.window、self 或 top 去取用「最上層的那個視窗」。在瀏覽器裡這三者本來就都指向同一個 window，所以補環境時也要把它們對齊到同一個物件，否則檢查會露餡。

根因二：Node 專屬識別字會出賣你

第二個根因沒那麼直觀，卻更關鍵。網站不一定只檢查「你是不是瀏覽器」，它也可能反過來檢查「你是不是 Node」。而判斷你是不是 Node 的方法很簡單：看你有沒有那些只有 Node 才有的識別字，例如 process 或 global。

於是在補環境時，光是把 window 接上去還不夠，還得把這些 Node 專屬的痕跡處理掉，讓那段程式碼就算主動去找，也找不到自己是 Node 的證據。這正是為什麼很多補環境檔案在 window = global 之後，會接著 delete 掉一串 Node 的識別字。要注意的是，delete 有副作用，刪錯對象會連 Node 自己都跑不動，所以順序和對象都要照著已知可行的範本走，不要憑感覺刪。

補環境在做什麼，以及不是什麼

把上面兩件事合起來看，補環境的定義就清楚了：當你把瀏覽器的加密或解密入口找到、把那段 JS 拷到本機交給 Node 執行時，因為程式碼裡用了只有瀏覽器能呼叫的 API，直接跑會報錯；你要做的，是在 Node 這邊模擬、補齊它會用到的前端物件，讓它跑得下去。

這裡有個重要的邊界：補環境不是把整段加密演算法用 Python 重寫一遍。那條路（純算）當然可行，但你得完全看懂演算法；補環境走的是另一條，不去理解演算法本身，只把環境「餵」得夠像，讓原本那段 JS 自己把結果算出來。代價是你得知道它到底用了哪些前端物件、哪些成員，而這正是後面幾節要處理的事。

小結

瀏覽器 JS 搬進 Node 會壞，有兩個根因：一是頂級物件不同，瀏覽器是 window、Node 是 global，所以 window、document 這些物件在 Node 裡根本不存在；二是 Node 有一批專屬識別字（process、global、Buffer 等），會讓反過來檢查「你是不是 Node」的程式碼抓到證據。補環境就是補上前者、清掉後者，把環境「餵」得像瀏覽器，而不是重寫演算法。

只知道「會壞」還不夠，真正的問題是：那段黑盒子的程式碼到底用了哪些物件、哪些屬性？你不可能一行行讀完幾萬行的混淆碼。下一節要學會用 Proxy 對整個 window、document 掛上一層監控，讓程式自己把它讀了什麼、缺了什麼，全部印到你的日誌裡。
