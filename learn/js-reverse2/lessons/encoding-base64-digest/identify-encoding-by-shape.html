一眼判型：從長度與字母表認出編碼

Step 5/5 · 編碼與摘要：URL、Base64、MD5/SHA

學習目標

面對一段陌生字串，依長度與字母表判斷它是 URL 編碼、Base64（標準或 URL-safe）還是十六進位摘要，並選對還原方式。

前言：先判型，再動手

前面的四個步驟，你已經分別認識了 URL 編碼、Base64、它的變體，以及摘要演算法。現在把場景換成真實工作：你在封包裡複製了一段參數，值是 aGVsbG8=。接下來你要做什麼？直接丟進 Base64 解碼器？還是先補 =？還是它其實是某種摘要，根本解不回來？

這裡有一個很現實的取捨。如果你判斷它是「可逆的編碼」，那你的力氣就花在還原上，解出來就結束了，不必找什麼金鑰。但如果你判斷它是「摘要」，那再多解碼器也沒用，你得把方向轉去「找出它的輸入字串」。判錯方向，輕則白忙一場，重則誤以為這個參數沒有保護、實際上後面還藏著一層。所以真正該先練的，不是怎麼解，而是怎麼看。

一張表看懂差異

這幾種東西的差別，其實都寫在兩件事上：字元集（字母表）和長度。把它們並列起來，判型就變成照表比對：

類型字母表特徵長度特徵還原方式
URL 編碼含 % 加上兩位十六進位長度不定unquote
標準 Base64只用 A-Z a-z 0-9 + / =去掉 = 後是 4 的倍數b64decode
URL-safe Base64只用 A-Z a-z 0-9 - _ =4 的倍數先 -→+、_→/ 再解
十六進位摘要只落在 0-9 a-fMD5 32、SHA-1 40、SHA-256 64、SHA-512 128不可逆，重算或找輸入
自訂字母表 Base64安全字元但順序被重排4 的倍數需先取得對方字母表

依序問自己這幾個問題

實戰時不一定要每次都查表，把下面的問題照順序問一遍，通常兩三個就能鎖定：

  1. 字串裡有沒有出現 % 開頭、後面接著兩位十六進位的序列？有的話，先當它是 URL 編碼，用 unquote 還原看看。
  2. 字串是不是落在 A-Z a-z 0-9 + / = 這幾類字元裡？去掉尾端的 = 之後，長度是不是 4 的倍數？兩個都成立，就高度可能是標準 Base64。
  3. 裡面有沒有 - 或 _？有，就是 URL-safe 變體，替換回 +、/ 再解。
  4. 字串是不是只由 0-9 和 a-f 組成？長度是不是剛好 32、40、64 或 128？符合的話，它比較可能是十六進位摘要，別浪費時間想「解開」它。
  5. 明明很像 Base64、字母表也對，但解出來是一坨看不懂的東西？那可能只是第一層，真正的內容還包在裡面。

反例：這些判斷會在什麼時候翻車

規則講完，更要知道它什麼時候不成立。下面三個反例，是判型最常出錯的地方。

反例一：長度是 4 的倍數，不代表就是 Base64

十六進位摘要的常見長度 32、40、64、128，剛好全都是 4 的倍數。所以單看「長度是不是 4 的倍數」根本分不出 Base64 和 MD5 摘要。真正能分開它們的是字元集：十六進位只會出現 0-9 和 a-f，不會有 g 之後的字母，也不會有 + / =。兩個條件要一起看，不能只看一個。

反例二：解出一層，不代表結束

一段 Base64 解出來的東西常常還是亂碼，因為它裡面包的可能是一段 AES 密文。這時候正確的反應不是「我解錯了」，而是「我解對了，這裡是第二層」。很多逆向案例的結構就是「Base64 外層、對稱加密內層」，看到外層解得開，只能證明你走對方向，不能停下來。

反例三：摘要也可能被包成 Base64 的樣子

摘要算完通常是十六進位字串，但也有程式把它再轉成 Base64 才傳出去。這種情況下，你在封包裡看到的是一段 Base64，但它真正代表的內容是一串十六進位摘要，外表和本質不一樣。這提醒我們：判型是為了決定「先做哪一步」，不是給出「它一定是什麼」的結論，要邊做邊驗證。

把它寫成一段檢查程式

把上面的判別問句寫成程式，就是一個簡單的初判函式。它只做初步分類，最後的「自訂字母表」還是得靠人工判斷：

import re, base64

def guess_shape(s: str) -> str:
    if re.search(r"%[0-9A-Fa-f]{2}", s):
        return "url-encoding"
    if "-" in s or "_" in s:
        return "base64-url-safe"
    if re.fullmatch(r"[0-9a-f]+", s) and len(s) in (32, 40, 64, 128):
        return "hex-digest"
    if re.fullmatch(r"[A-Za-z0-9+/=]+", s) and len(s.rstrip("=")) % 4 == 0:
        return "base64-standard"
    return "unknown"

這段程式的順序是刻意的：先攔最明確的 URL 編碼，再攔 URL-safe，然後才判斷是不是十六進位摘要，因為 0-9a-f 是標準 Base64 字元的子集，如果不先檢查摘要，一個剛好的十六進位字串會被誤判成 Base64。

小結

判型看兩件事：字母表和長度。看到 %XX 就是 URL 編碼，用 unquote；字母表是 A-Z a-z 0-9 + / 且長度是 4 的倍數就是標準 Base64；出現 - 或 _ 就是 URL-safe；只有 0-9 a-f 且長度是 32／40／64／128 就偏向十六進位摘要，別再想怎麼「解」，要去把它重算出來。但記得兩個反例：長度是 4 的倍數不代表就是 Base64，解出一層也不代表結束。

把五步收進來看，這條線其實是一組「認字 → 還原 → 重算」的基本功：URL 編碼和 Base64 幫你把可逆的包裝拆開，摘要演算法幫你判斷哪些地方該改用重算而不是還原。有了這套眼力，後面遇到真正的加密（對稱、非對稱）時，你才分得出哪一段能解、哪一段要去找金鑰，那正是下一個節點要講的事。
