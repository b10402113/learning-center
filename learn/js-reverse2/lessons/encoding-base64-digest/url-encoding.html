URL 編碼：查詢參數為什麼要跳脫

Step 1/5 · 編碼與摘要：URL、Base64、MD5/SHA

學習目標

看得懂查詢字串裡的 %XX，並用 Python 的 quote／unquote／urlencode 還原與重建 URL 參數。

前言：一個 & 就把參數切斷了

假設你要抓一個搜尋頁，參數是 keyword 和 page。你照著 DevTools 抄下網址，準備用 requests 重打一次。其中一個參數的值剛好是 &apple123。看起來沒什麼問題，但送出去之後，伺服器回給你的資料完全不對。

問題就出在那個 &。查詢字串用 & 分隔參數、用 = 分隔鍵和值，這些符號是「保留字」，有固定的職責。當它們出現在某個值裡面，伺服器會把它們當成分隔符號來解讀，於是一個參數被硬生生切成好幾個。要讓這些字元乖乖當作「內容」而不是「語法」，就得先經過 URL 編碼。這一節講的就是這道手續。

查詢字串的語法，以及它撞到的問題

一個 URL 的查詢字串長得像這樣：?k1=v1&k2=v2&k3=v3。它遵循三個規則：問號之後開始、& 分隔每個鍵值對、= 分隔鍵與值。這些規則讓 URL 可以被機器精準拆解，但也表示 &、=、?、#、空格這些字元不能隨便出現在鍵或值裡面。

更麻煩的是中文。假設你要傳的值是「苑」，它根本不在 URL 允許的字元表裡；而且 URL 本質上是位元組的世界，非 ASCII 字元得先轉成 UTF-8 位元組才能上路。所以只要值裡有中文、有空格、有保留字，就必須先編碼。

解法：百分比編碼

URL 編碼（percent-encoding，百分比編碼）的做法很單純：把不能直接放的字元，換成一個 % 加上該字元 UTF-8 位元組的十六進位值。例如 & 的位元組是 0x26，編碼後就是 %26；「苑」的 UTF-8 位元組是 E8 8B 91，編碼後就是 %E8%8B%91。十六進位字母通常用大寫。

所以原本會壞掉的 k1=&123，正確寫法要變成 k1=%26123。這樣伺服器拆解時，遇到的第一個分隔符號是 %26123 之後的那個 &，就會正確地把 k1 的值還原成 &123。

Python 裡怎麼做

Python 的標準函式庫 urllib.parse 提供三個常用工具：quote() 把單一值編碼、unquote() 還原，而 urlencode() 一次處理整個字典，把鍵值對接成 k=v&k2=v2 的形式。下面這段程式碼用一個含保留字與中文的字典示範 urlencode()：

import urllib.parse

data = {
    "k1": "&123",
    "k2": "苑"
}
new_data = urllib.parse.urlencode(data)
print("new_data:", new_data)

執行後會印出：

new_data: k1=%26123&k2=%E8%8B%91

可以看到兩個值都被編碼了：&123 變成 %26123，苑 變成 %E8%8B%91。反過來，如果你在封包裡看到 %E8%8B%91，用 urllib.parse.unquote() 就能還原成「苑」；quote("苑") 則可以得到 %E8%8B%91。

什麼時候要自己編，什麼時候不用

多數情況下，用 requests 時你不需要手動編碼。只要你把參數放進 params={...} 字典，套件就會自動幫你編好。真正需要你親手處理的，是「要跟 JS 產生的字串對齊」的時候。例如某個網站的簽名（sign）是把 encodeURIComponent 編碼過的參數拼接起來再雜湊，那你在 Python 端重算時，也得跟著做一次相同的編碼，否則拼出來的字串不一樣，簽名當然對不上。

另一個常見的坑是「編了兩次」（double encoding）。有些參數在 JS 端先被 quote 過一次，放進 URL 時又被瀏覽器編了一次，於是你會看到 %25，那是 % 本身被編碼的結果。解讀時要記得還原兩層，不要只看一層就下結論。

小結

查詢字串用 &、=、? 這些保留字來切分參數，所以值裡面只要有保留字、空格或中文，就必須先做百分比編碼：把字元換成 % 加上它 UTF-8 位元組的十六進位。%26 是 &，%E8%8B%91 是「苑」。在 Python 用 quote／unquote 處理單一值、urlencode 處理整個字典；只有在要跟 JS 對齊簽名輸入時，才需要自己動手編碼。

URL 編碼處理的是「幾個特殊字元」。但如果你手上那串東西不只是幾個特殊字元，而是一整段長得像英數混合的亂碼呢？那通常是下一種編碼：Base64。下一節就來看它怎麼把任意位元組塞進一串安全的文字裡。
