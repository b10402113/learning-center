不一定是 MD5：辨識雜湊與選擇重現路線

Step 4/5 · 案例：簽名與雜湊演算法

學習目標

從雜湊實作判斷它是標準演算法還是自家配方，並決定翻成 Python 還是直接用 execjs 呼叫。

前言：sign 看起來都像 MD5，直到你遇到不像的

前兩節的配方都以 MD5 收尾，32 位十六進位看久了，你的手指會比大腦先做出反應——看到 sign 就開始寫 hashlib.md5()。丁香網的病例搜尋介面會立刻糾正這個習慣：它的 sign 是 40 位十六進位，翻開 JS 一看，是一坨手寫的位元運算迴圈，不是任何函式庫。而百度翻譯更狠，它的 sign 乾脆長這樣：228742.198315。兩個數字、一個小數點，連十六進位都不是。

這時候你面對的不再是如何拼字串，而是一個岔路口的抉擇：左邊是把這坨演算法翻譯成 Python（hashlib 或手寫迴圈），右邊是放棄翻譯、用 execjs 直接呼叫網站的原 JS。兩股力量在拉扯——純 Python 路線好整合、跑得快、不需要 Node 環境，但翻譯有成本、細節容易抄漏；execjs 路線保證原汁原味、上手快，但每台跑爬蟲的機器都要多帶一個 JS 執行環境。這一節給出判斷的規則，用丁香網和百度翻譯兩個極端案例各走一次。

兩條路線的取捨

翻成 Pythonexecjs 呼叫原 JS
保真度靠自己對齊細節，可能抄漏演算法原封不動，輸出保證一致
執行需求只要 PythonPython ＋ Node 執行環境
整合難度容易併進 asyncio、多緒爬蟲每次呼叫跨越語言邊界，較慢
適合的演算法標準雜湊（MD5／SHA 系列）自家 hash、或實作與環境糾纏太深
翻車方式字串化或編碼細節不一致JS 依賴瀏覽器物件，載入就報錯

表裡最值得記的是最後兩列的對照：兩條路各有各的死法。翻譯派死在「以為翻對了其實差一個字元」，呼叫派死在「JS 一載入就喊 window is not defined」。所以抉擇不是誰碾壓誰，而是看眼前這個演算法的長相，選活路比較長的那條。

四個判別問句

拿到雜湊實作時，依序問自己下面四個問題。每一句都是可以當場測試的，不需要猜：

  1. 輸出的形狀像標準雜湊嗎？32 位十六進位像 MD5、40 位像 SHA-1、64 位像 SHA-256；像 228742.198315 這種「數字．數字」的，絕對不是標準雜湊的直接輸出。
  2. 實作裡找得到標準常數嗎？看到 1732584193 幾乎可以確定是 MD5 的初始值；看到 String.fromCharCode 現拼對照表、自訂的移位加減迴圈，那是自家配方。
  3. 輸入字串完整可見嗎？拼接字串整個攤在程式裡（像有道那樣），翻譯成本很低；輸入由多層函式東拼西湊出來，翻譯容易漏。
  4. 實作跟瀏覽器環境糾纏多深？純計算的函式好翻；碰到 window、document、計時器，翻譯前得先補環境，不如直接呼叫。

還有一句話要先放在心上：輸出形狀只告訴你最後一層雜湊是什麼。32 位十六進位只能說明「最外面是 MD5 或同長度的東西」，裡面可能還套了好幾層——下一節的財联社就是「SHA1 再 MD5」的雙層結構。

案例一：丁香網的 40 位 SHA-1

丁香網的病例庫搜尋要在查詢參數裡帶一個 sign。Python 端把要簽的字串拼好，交給 JS 的 u 函式算簽名：

nonstr = str(random.randint(0, 100000000)).rjust(8, '0')
# nonstr = ''.join([str(random.randint(0, 9)) for _ in range(8)])
timestamp = int(time.time() * 1000)

params = {
    'keyword': '新冠',
    'sectionCode': '0',
    'pageSize': '10',
    'pageNum': '1',
    'serverTimestamp': timestamp - 2,
    'timestamp': timestamp,
    'noncestr': nonstr,
}

data = f'appSignKey=4bTogwpz7RzNO2VTFtW7zcfRkAE97ox6ZSgcQi7FgYdqrHqKB7aGqEZ4o7yssa2aEXoV3bQwh12FFgVNlpyYk2Yjm9d2EZGeGu3&keyword={params["keyword"]}&noncestr={params["noncestr"]}&pageNum={params["pageNum"]}&pageSize={params["pageSize"]}§ionCode=0&serverTimestamp={params["serverTimestamp"]}×tamp={params["timestamp"]}'
sign = execjs.compile(open("02 丁香网.js").read()).call("u", data)
print("sign", sign)
params["sign"] = sign

配方本身是熟面孔：固定順序拼接＋固定金鑰——appSignKey=… 那串 80 位的亂碼就是金鑰，排在第一位，欄位照 keyword、noncestr、pageNum、pageSize、sectionCode、serverTimestamp、timestamp 的順序拼上去。兩個欄位值要照抄：noncestr 是 8 碼補零的隨機數（rjust(8, '0')），serverTimestamp 偏偏要是 timestamp - 2——比當下時間少 2 毫秒，這種小動作只能照抄，想不通就先抄。

變的是雜湊：JS 裡的 u 是一整套手寫的 SHA-1 實作（位元分組、輪迴圈、十六進位輸出），不是 crypto-js、也不是 Node 的 crypto。輸出 40 位十六進位，正是 SHA-1 的形狀。對照判別問句：輸出像標準雜湊（SHA-1），但實作是獨立的一坨純計算 JS、輸入字串完整可見。這站的選擇是 execjs 呼叫 u——函式已經是孤立的純函式，呼叫它比逐行翻譯更穩，還省掉驗證翻譯正確性的成本。

案例二：百度翻譯的自家 hash

百度翻譯的 v2transapi 也要 sign，Python 端只做一件事：把要查的單字丟給 JS：

wd = 'banana'

sign = execjs.compile(open("04 百度翻译.js").read()).call("get_sign",wd)
print("sign:", sign)

逐項對照判別問句：輸出形狀「數字．數字」，不是任何標準雜湊；移位與 XOR 的指令表用 String.fromCharCode 現拼出來（w、k 兩串指令），沒有任何標準常數；種子來自頁面上的 window.gtk，跟瀏覽器環境有牽連。三條全部指向同一個結論：不要翻譯，直接 execjs 呼叫 get_sign。翻譯它理論上做得到，但你要重現 surrogate pair 處理、指令表編碼、32 位元溢位遮罩每一個細節，錯一處輸出就全變——投入產出比極差。

規則會翻轉的三個情況

判別規則不是死的，下面幾種情況會翻盤：

  • 標準雜湊，卻選了呼叫派：丁香網的 SHA-1 是標準演算法，用 hashlib.sha1 也重現得出來；但它的 JS 已經是孤立的純函式，呼叫它零翻譯成本。當「原 JS 已經很好呼叫」時，保真派直接勝出，不必為了純 Python 而純 Python。
  • 輸入拼接才是難題：有時候雜湊是標準的，真正難的是拼接字串的組裝邏輯（條件欄位、巢狀序列化）。這時把力氣花在重現字串組裝、雜湊交給 hashlib，比整包呼叫 JS 更好整合。
  • 形狀欺騙：百度的輸出雖然長得完全不像雜湊，內部其實還是一輪輪的雜湊式運算；反之 40 位十六進位只能保證「最外層像 SHA-1」。認形狀是為了決定先查什麼，不是結案。

決策規則

把整節收斂成一張當場能用的檢查表：

  1. 先看輸出形狀，猜「最外層」是哪種雜湊，把它當假設不當定論。
  2. 讀實作找常數：有 1732584193 之類的標準初始值就是標準雜湊家族；String.fromCharCode 拼表、自訂移位迴圈就是自家配方。
  3. 輸入字串完整可見＋雜湊標準 → 翻成 Python（hashlib），好整合。
  4. 自家 hash、或實作與 window／document 糾纏 → 直接 execjs 呼叫，別翻譯。
  5. 原 JS 已是孤立純函式時，呼叫派是省力的預設值。
  6. 不論哪條路，最後都要用「相同輸入 → 與瀏覽器相同輸出」驗證至少兩組。

小結

sign 不一定是 MD5：丁香網是手寫 SHA-1（40 位十六進位），百度翻譯是種子來自 gtk 的自家 hash（輸出「數字．數字」）。抉擇的判準是四個問句——輸出形狀、標準常數、輸入可見度、環境糾纏深度；標準雜湊且好拼就翻 Python，自家配方或糾纏深就 execjs。記住輸出形狀只反映最後一層，別被它騙了。

說到「最後一層」，下一節正好把它坐實：財联社把「排序序列化 → SHA1 → MD5」兩層雜湊疊在一起，而且整條管線埋在 webpack 打包檔的某個模組裡——先找到簽名模組，再一層層認出配方。
