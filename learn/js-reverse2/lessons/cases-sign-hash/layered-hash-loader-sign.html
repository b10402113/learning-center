打包檔裡的雙層雜湊：財联社的排序→SHA1→MD5 簽名

Step 5/5 · 案例：簽名與雜湊演算法

學習目標

在 webpack 打包檔裡定位簽名模組，拆出「排序序列化 → SHA1 → MD5」的管線並用 window.loader 呼叫它。

前言：簽名藏在打包檔裡，一層還不夠，要兩層

上一節收尾時留了一句話：輸出形狀只反映最後一層雜湊。財联社（Cailianpress，財經新聞 App 的網頁版）就是這句話的實體教材。它的介面請求要帶一個 32 位十六進位的簽名——形狀像 MD5，但如果只按 MD5 去猜輸入，你會算到懷疑人生，因為這個 MD5 的輸入不是原始參數，而是先經過 SHA-1 的另一串雜湊。整條配方是「排序序列化 → SHA1 → MD5」兩層雜湊串接。

更麻煩的是棲身環境：這套邏輯不在一個乾淨的 JS 檔裡等你，而是埋在 webpack 打包檔的數百個模組中。所以這個案例要先走完「在打包檔裡找到簽名模組」這條路——用的正是 webpack 拆解那個節點練過的功夫——再把模組裡的管線一層層拆開認證。做完這節，排序拼接、SHA-1、MD5、模組定位四項功夫就全部串起來了。

目標與前置條件

做完這一節，你會有一支能跑的簽名產生器：餵參數進去、呼叫財联社的簽名模組、拿到 32 位簽名。動手前需要三樣東西：一是 webpack 打包檔的心智模型（loader 分發器、模組 id、window.loader 這個常見的洩漏點）；二是上一節的雜湊辨識功夫；三是能在 Node 裡跑 JS——因為這次的重現路線是呼叫原 JS，不是翻譯。

步驟一：載入 loader，認出分發器

財联社的入口檔 05 财联社的loader.js 是一個標準的 webpackJsonp 引導檔：開頭 require 三個模組檔把模組表灌進來，中間是分發器。分發器長這樣：

    function u(r) {
        if (n[r])
            return n[r].exports;
        var t = n[r] = {
            i: r,
            l: !1,
            exports: {}
        }
            , o = !0;
        try {
            console.log("r:::", r)
            e[r].call(t.exports, t, t.exports, u),
                o = !1
        } finally {
            o && delete n[r]
        }
        return t.l = !0,
            t.exports
    }

    window.loader = u

逐行讀它。u(r) 就是 webpack 的 __webpack_require__：傳進模組 id，回傳模組的 exports。if (n[r]) return n[r].exports 是快取——同一個模組只執行一次。中間的 try／finally 有個貼心細節：模組執行丟出例外時會把快取刪掉（o && delete n[r]），所以載入失敗後可以直接重試，不會留下半初始化的殘骸。而 console.log("r:::", r) 顯然是逆向者自己插的探針——每次有模組被載入就印出它的 id，這樣跑一次流程就知道簽名模組的 id 是哪個。最後 window.loader = u 把分發器掛上全域，這就是呼叫任何模組的把手。

步驟二：找到簽名入口

檔案的最底下有一段測試程式，直接把答案寫在臉上：

function get_sign() {
    // 测试环境
    let data = {
        "os": "web",
        "sv": "7.7.5",
        "app": "CailianpressWeb"
    }
    return window.loader("W2Yj")(data)
}

console.log(get_sign())

簽名模組的 id 是 "W2Yj"，輸入參數是一包固定的識別欄位（作業系統 os、版本 sv、應用名 app），回傳值就是簽名。在真實作業裡，這段測試程式通常是你自己寫的驗證腳本——但模組 id 這個情報，來自步驟一那行探針印出的紀錄。呼叫鏈是 window.loader("W2Yj") 先拿模組的匯出函式，再 (data) 執行它。

步驟三：拆開模組裡的三段管線

W2Yj 模組的內部結構非常乾淨，匯出函式就是整條管線的摘要——先序列化、再過兩層雜湊：

    W2Yj: function (e, t, n) {
        var r = n("p0XB")
            , o = n("pLtp")
            , i = n("KjvB")
            , u = n("aCH8")
            , a = !0;
        …
        e.exports = function (e) {
            var t = e && f(c(e).map((function (t) {
                    return p(t, e[t])
                }
            )));
            return t = i.sync(t),
                t = u(t)
        }
    },

管線三段，對照第三節的「拼接規則＋雜湊」框架剛好一一對位：

  1. 序列化（拼接規則）：f(c(e).map(...)) 負責把參數物件變成規範字串。c(e) 把鍵名排序（實作是 o(e).sort()），p(t, e[t]) 把每一對鍵值遞迴展開——巢狀物件和陣列加上方括號層級（key[0]、key[sub] 這種形式）、假值被過濾掉、最後用 & 連接。這是配方家族一的「排序拼接」，只是序列化規則比福建那套更講究。
  2. 第一層雜湊：t = i.sync(t)——i 是模組 KjvB，負責 SHA-1。
  3. 第二層雜湊：t = u(t)——u 是模組 aCH8，負責 MD5。SHA-1 的十六進位輸出直接當 MD5 的輸入，所以最終簽名是 32 位的 MD5 形狀。

注意模組依賴是用 n("KjvB")、n("aCH8") 這種 id 互相呼叫的——webpack 的世界裡沒有函式名字，只有模組 id。這也是為什麼步驟一的探針是整套手法的地基：不知道 id，你知道配方也叫不到人。

步驟四：用常數認出兩層雜湊

兩個雜湊模組的名字是混淆過的（KjvB、aCH8 說明不了任何事），認它們的身分要用第四節的第 2 條判準：找標準常數。先看 KjvB：

    KjvB: function (e, t, n) {
        var r = new (n("c4+4"))
            , o = "undefined" !== typeof window ? window : self
            , i = o.crypto || o.msCrypto || {}
            , u = i.subtle || i.webkitSubtle;

        function a(e) {
            return r.digest(e)
        }

        try {
            u.digest({
                name: "sha-1"
            }, new Uint8Array).catch((function () {
                    u = !1
                }
            ))
        } catch (s) {
            u = !1
        }

一目了然：它優先走瀏覽器的 crypto.subtle（WebCrypto），而且探測用的正是 name: "sha-1"；不可用時退到 c4+4 這個純 JS 實作模組（a(e) { return r.digest(e) } 就是後備路線）。e.exports.sync = a 那類匯出別名讓它可以同步取回十六進位字串——這就是管線裡 i.sync(t) 呼叫的東西。

再看 aCH8，MD5 的身分藏在初始值裡：

    aCH8: function (e, t, n) {
        !function () {
            …
                for (var a = t.bytesToWords(e), s = 8 * e.length, c = 1732584193, f = -271733879, p = -1732584194, l = 271733878, d = 0; d < a.length; d++)
                    …
                var h = u._ff
                    , y = u._gg
                    , v = u._hh
                    , m = u._ii;

1732584193 與它旁邊那三個負數常數，正是 MD5 四個累加器的標準初始值；_ff、_gg、_hh、_ii 是 blueimp 這支經典 JS MD5 函式庫的招牌命名。兩個模組、兩層雜湊，身分確認完畢：排序序列化之後先 SHA-1、再 MD5。

步驟五：呼叫、驗證、記下配方

剩下就是把管線接出來用。在 Node 裡載入 loader 與三個模組檔（JS 依賴瀏覽器的 document、計時器時要先補環境），然後照測試程式的寫法呼叫：

    return window.loader("W2Yj")(data)
}

console.log(get_sign())

驗證方式和前幾節相同：同一包 {os, sv, app} 參數，你的實作與瀏覽器 DevTools 裡看到的簽名逐字元一致；換一包參數再比一次。兩次都對，把配方記進筆記——規範字串（鍵排序、巢狀方括號、假值過濾、& 連接）→ SHA-1 → MD5，簽名放請求的簽名欄位。下次遇到同樣是 32 位的簽名，別忘了先問「裡面有沒有套第二層」。

做完長什麼樣

完成的狀態是：你手上有分發器的呼叫方式（window.loader）、簽名模組的 id（"W2Yj"）、以及完整配方筆記；一支 get_sign 腳本隨傳隨得，輸出與瀏覽器一致。更重要的是方法已經沉澱下來——插探針找模組 id、讀匯出函式拆管線、認常數定雜湊身分——這套流程對任何打包檔裡的簽名都通用。

小結

財联社的簽名埋在 webpack 模組裡，管線是「排序序列化 → SHA1 → MD5」兩層雜湊。手法分三段：用 loader 的探針與 window.loader 分發器定位簽名模組 "W2Yj"；讀匯出函式拆出序列化與兩層雜湊的順序；用常數認身分——crypto.subtle 的 "sha-1" 是 SHA-1，1732584193 與 _ff/_gg/_hh/_ii 是 MD5。重現路線照第四節的規則走：管線與環境糾纏在打包檔裡，呼叫原 JS 是省力的預設值。

走到這裡，簽名與雜湊這條線的全貌就齊了：三個組成（拼接規則、金鑰、雜湊）、兩大拼接家族（排序拼接、固定順序）、兩類雜湊（標準 MD5／SHA 系列、自家配方）、一條重現路線的抉擇規則（翻 Python 或呼叫 JS），以及最後一課——輸出形狀只反映最後一層。帶著這套判讀流程去面對下一個陌生的 sign，你會知道先問什麼、再查什麼。
