簽名的三個組成：拼接規則、金鑰、雜湊

Step 1/5 · 案例：簽名與雜湊演算法

學習目標

看到一個 sign 欄位時，能把問題拆成「拼了哪些欄位、加了什麼金鑰、用哪個雜湊」三件事來追。

前言：同一個請求，為什麼換個字就失效？

你從 DevTools 把一個翻譯網站的請求複製成 cURL，貼進終端機重放一次，伺服器乖乖回了翻譯結果。你心想這個站沒什麼保護，十分鐘後把查詢字改成另一個詞再送一次，卻只拿到一個乾淨的錯誤訊息。回頭打開 Network 面板比對兩次請求，欄位幾乎一模一樣，只有一個叫 sign 的欄位變了——第一次是 1be3315fc3cd8097a033646862b6e5db，第二次換成另一串 32 位的十六進位。

這個欄位就是爬蟲工程師最常撞到的那道牆。它不是密碼，抄一次就能一直用；它也不是亂數，因為伺服器每次都驗得過。它是網站用一小段 JavaScript 現算出來的簽名（sign）：把這次請求的內容按規則拼成一行字、混進一串只有網站自己知道的固定密文，再壓成一串定長的亂碼。伺服器收到請求後用同樣的規則重算一次，對得上才放行。

要重現簽名，與其在壓縮過的 JS 裡亂逛，不如先學會問對問題。一條簽名配方拆開來只有三個組成，這一節就把這三個組成立起來；後面四節各拿一個真實網站，把其中一種配方從定位到用 Python 跑通走完一遍。

簽名在保護什麼

先講清楚簽名要防的是什麼。HTTP 請求送出後，中間任何一個環節都能改掉它的內容：把每頁 10 筆改成每頁 1000 筆、把會員 ID 換成別人的、把價格改成負數。伺服器光看請求內容，沒辦法分辨「這是瀏覽器照規則算出來的」還是「這是有人手動改過的」。

簽名就是瀏覽器替請求開的一張發票。發票上的編號是根據「買了什麼、數量多少、哪個分店、什麼時間」這些欄位算出來的；收銀台只要重算一次編號，就知道單據有沒有被動過手腳。因為開票的規則裡藏了一枚只有店家知道的暗章（金鑰），外人就算知道規則也開不出能過關的發票。

這也解釋了開頭那個現象：查詢字一換，被拼進發票的內容就變了，簽名當然要重算。你抄下來的舊簽名只對「那一組內容」有效，這正是它跟密碼最大的差別——簽名驗的是內容的完整性，不是你的身份。

三個組成，三個問題

拿到一個 sign 欄位，不要急著猜演算法。一條簽名配方永遠可以拆成三件東西，對應三個你必須回答的問題：

組成要回答的問題逆向時的線索
拼接規則哪些欄位、按什麼順序、用什麼分隔符號拼成一行字？JS 裡把參數物件展開成字串的那段程式；排序還是寫死順序
金鑰（secret）拼完之後混進去的固定密文是什麼？JS 裡一串又長又沒意義的常數字串，或被當成參數塞進雜湊的欄位
雜湊（hash）最後用哪個演算法把「字串＋金鑰」壓成定長輸出？呼叫 MD5 / SHA 的函式；或一坨看不出名字的自製迴圈

第一個組成常被叫做規範字串（canonical string），意思是「同一組參數，不管字典順序怎麼排，都必須拼出完全一樣的那行字」。它是簽名的地基：拼錯一個欄位、少一個分隔符號、順序不同，後面算出來的雜湊就整個不對。實務上最常見的兩大類拼法，一類是「把欄位按鍵名排序後拼起來」，另一類是「照 JS 寫死的順序拼」——後面的配方一、配方二就是這兩類的代表。

第二個組成是金鑰。它通常長得像隨手亂敲的字串，藏在 JS 的常數裡，例如一串 32 位的十六進位、一個 UUID，或一個叫 appSignKey 的欄位值。它的作用是讓「知道規則」不等於「能開出發票」：沒有這串密文，你拼出的字再正確也過不了驗證。

第三個組成是雜湊。雜湊演算法（hash）做的事情是：不管輸入多長，都壓成固定長度的一小段輸出，而且從輸出倒推不回輸入。MD5 壓出 32 位十六進位，SHA-1 壓出 40 位，SHA-256 壓出 64 位。它還有一個對簽名特別有用的性質：輸入改動一個字元，輸出會面目全非——所以哪怕請求只被改掉一個欄位，伺服器一比對就能察覺。

把三個組成套在一個真實案例上

有道翻譯的 webtranslate 介面是練這套拆解最好的起點，因為它的簽名輸入字串完整寫在程式裡，三個組成一眼可見。用 Python 重現它時，簽名部分只有短短幾行：

# （1）构建sign值
e = str(int(time.time() * 1000))
t = 'fsdsogkndfokasodnaso'
d = "webfanyi"
u = "fanyideskweb"
s = f"client={u}&mysticTime={e}&product={d}&key={t}"

m = hashlib.md5()
m.update(s.encode())
sign = m.hexdigest()
print(sign)

照三個組成來讀這段程式：

  1. 拼接規則：固定順序拼出 client=…&mysticTime=…&product=…&key=… 這行字，欄位之間用 & 分隔，每個欄位寫成「鍵名＝值」的形式。四個欄位的順序是寫死的，不是排序出來的。
  2. 金鑰：fsdsogkndfokasodnaso。它看起來像亂敲的鍵盤，實際上是整條配方的命根子——它被當成最後一個欄位 key 拼進字串裡。
  3. 雜湊：MD5。整行字丟進 hashlib.md5()，取十六進位輸出（hexdigest()），得到一串 32 位的 sign。

注意 mysticTime 的值是 int(time.time() * 1000)——當下的毫秒時間戳記。它一邊參與簽名計算，一邊也放進表單送出去（'mysticTime': e），伺服器重算簽名時用的就是這個值。這就是簽名每次都不一樣的原因：不是演算法變了，是拼進去的內容裡有一個一直在動的時間欄位。

為什麼用雜湊，而不是把內容加密起來

剛接觸簽名的人常會問：既然要防篡改，為什麼不直接把請求內容加密？關鍵在於兩者的任務不同。加密是為了「讓別人看不懂」，收件方要有辦法解回來；簽名是為了「讓別人改不了」，伺服器根本不需要看懂什麼，它只要拿同樣的內容重算一次、比對輸出就好。雜湊的單向性（算得出、倒不回）配上固定長度，正好符合這個需求——請求內容照原樣送出，簽名當附屬的驗證欄位，伺服器的計算成本也低。

金鑰在這裡的角色值得再想一下。如果配方裡沒有金鑰，任何人知道拼接規則都能自己算出合法簽名；混進一串伺服器與頁面共享、但不公開給第三方的密文之後，「能重現簽名」就等於「真的讀懂了頁面的 JS」。反過來說，這也是為什麼逆向簽名的終極答案永遠是把 JS 裡的那串密文找出來——金鑰找不到，雜湊算得再準都沒有用。

接下來的四種配方

三個組成是骨架，配方的變化全落在「拼接規則」和「雜湊」上。這個節點接下來四節各拆一種真實配方：

  • 配方一（排序拼接＋salt → MD5）：福建電子交易平台把參數按鍵名排序後拼起來，前面再補一串 salt。難點在排序規則與 JSON 字串化必須跟 JS 一模一樣。
  • 配方二（固定順序＋固定金鑰 → MD5）：xdf 新東方與有道翻譯都照 JS 寫死的欄位順序拼字串。難點在簽名用的字串和送出時要編碼的字串不一定相同。
  • 不是 MD5 的情況：丁香網用的是純 JS 手寫的 SHA-1，百度翻譯更是一套自家 hash。看到 32 位十六進位就當 MD5，會在這裡栽跟頭。
  • 打包檔裡的雙層雜湊：財联社把「排序序列化 → SHA1 → MD5」兩層雜湊塞在 webpack 模組裡，考驗的是先找到簽名模組、再認出每一層的功夫。

每個配方都會用兩條路跑通：一條是純 Python 重現（用 hashlib 把配方抄寫過來），另一條是 execjs 直接呼叫網站的原 JS。哪條路該走、什麼時候放棄翻譯，正是第四節要做的抉擇。

小結

簽名是瀏覽器替請求開的發票：把請求內容按拼接規則拼成一行字、混進一串固定金鑰，再用雜湊壓成定長輸出，伺服器重算比對就完成驗證。拆任何簽名都只問三件事——拼了哪些欄位、按什麼順序？金鑰是哪串密文？最後用哪個雜湊？有道翻譯的案例裡這三件東西全部攤在陽光下：固定順序的查詢字串、金鑰欄位 key=fsdsogkndfokasodnaso、以及 MD5。
