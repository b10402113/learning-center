配方二：固定順序＋固定金鑰的 MD5 簽名（xdf 與有道翻譯）

Step 3/5 · 案例：簽名與雜湊演算法

學習目標

照著做能重現「固定順序拼接＋固定金鑰 → MD5」的簽名，並處理簽名用原始字串、送出要編碼的落差。

前言：不排序的網站，順序寫在 JS 裡

上一節的福建案例把排序規則寫在演算法裡——參數先按鍵名排好再拼，所以字典怎麼塞都不影響結果。但你很快就會遇到不買單的網站：xdf 新東方的課程搜尋介面（dsapi.xdf.cn/product/v2/class/search）要求請求頭帶一個 sign，而它的欄位拼接順序既不排序、也不看字典，是 JS 裡一行一行寫死的。你把 pageIndex 搬到 cityCode 前面，簽名立馬對不上。

這是配方家族的第二類：固定順序拼接＋固定金鑰 → MD5。金鑰的登場方式也跟 salt 不同——福建的 salt 黏在字串最前面，xdf 的金鑰是一個 UUID 黏在尾巴，有道翻譯更直接，金鑰本身就是拼接字串裡的最後一個欄位。這一節用 xdf 與有道兩個真實案例把這條配方跑通，順便解掉它最陰險的陷阱：簽名計算用的字串，和送出請求時要編碼的字串，不一定是同一種長相。

目標與前置條件

做完這一節，你會有兩份可用的簽名產生器：xdf 的走 execjs 呼叫原 JS，有道的走純 Python 重寫，兩者都能讓請求拿到資料。動手前你需要：會用 execjs 把 JS 函式接進 Python（Node 執行那個節點講過），以及第一節的三個組成框架——看到 sign = MD5(拼接字串＋金鑰) 的配方能立刻反應過來。

案例一：xdf 的 sign 欄位

先看請求端。Python 準備一組查詢參數，把整包丟給 JS 的 get_sign，拿回簽名和拼好的參數字串，各就各位送出去：

params = {
    'appId': '5053',
    't': '1762598499160',
    'cityCode': '110100',
    'pageIndex': '1',
    'pageSize': '5',
    'keyword': urllib.parse.quote("英语"),
    'order': '0',
}

ret = execjs.compile(open("05 xdf.js").read()).call("get_sign", params)
print("ret:::", ret)
headers["sign"] = ret["sign"]

p = ret["params"]

url = 'https://dsapi.xdf.cn/product/v2/class/search'
response = requests.get(url, params=p, headers=headers)
print(response.text)

注意 get_sign 的回傳值是一個字典，包含兩樣東西：ret["params"] 是 JS 幫你拼好的參數字串，直接當查詢字串送出；ret["sign"] 是簽名，掛進請求頭 headers["sign"]。簽名放 header、參數放 query string——這個站的擺法就這樣，逆向時順手記進筆記，別把 sign 硬塞進 params。

JS 端的配方其實很短。它把 appId 和 t 固定放在開頭，接著把其餘非空欄位依序拼上去，整串叫參數字串 t；最後算 sign = MD5(t + "750F82C2-D8F6-49F6-878C-1E7EBEBC8DA2")——那個 UUID 就是這站的金鑰，黏在參數字串的尾巴。欄位順序由 JS 的插入順序決定（appId、t、cityCode、pageIndex、pageSize、keyword、order），這就是「固定順序」的意思：配方不在演算法裡，在程式碼的行序裡。

案例一的陷阱：簽名字串與編碼字串

請再看一次 params 裡的那一行：'keyword': urllib.parse.quote("英语")。中文關鍵字「英语」不是直接放進去的，而是先做過一次 URL 編碼（percent-encoding，把非 ASCII 字元轉成 %E8%8B%B1%E8%AF%AD 這種形式），編碼後的字串才進到參數字典、才參與簽名計算。

這個順序不能亂。簽名驗證的做法是伺服器拿「它看到的欄位值」重算一遍，所以你簽的是哪個版本的字串，送出時就必須讓伺服器看到哪個版本。如果簽名時用原文「英语」、送出時卻變成編碼後的 %E8%8B%B1...，兩邊重算的結果就會錯開。實務上只要記一條規則：進簽名的欄位值，就是伺服器最終解析到的欄位值；需要編碼的欄位先編碼、再簽名、再原樣送出。

案例二：有道翻譯的金鑰欄位

有道翻譯的 webtranslate 介面是同一種配方的另一種金鑰擺法。它的簽名計算在純 Python 裡長這樣：

# （1）构建sign值
e = str(int(time.time() * 1000))
t = 'fsdsogkndfokasodnaso'
d = "webfanyi"
u = "fanyideskweb"
s = f"client={u}&mysticTime={e}&product={d}&key={t}"

m = hashlib.md5()
m.update(s.encode())
sign = m.hexdigest()
print(sign)

拼接順序同樣是寫死的：client、mysticTime、product、key，中間用 & 連接、每個欄位寫成「鍵＝值」。差別在金鑰的擺法：fsdsogkndfokasodnaso 不是黏在整串的頭或尾，而是當成 key 欄位本身拼在最後一位。形式不同，本質一樣——固定密文參與拼接，沒有它就算不出正確簽名。

算出來的簽名要放回表單裡跟著其他欄位一起送出，而 mysticTime 這個時間欄位是雙重身份：它既是簽名的輸入，也是表單的欄位。伺服器收到後拿表單裡的 mysticTime 重算簽名，所以這兩個值必須是同一個——你在簽名時用 A 時間、表單裡填 B 時間，一樣過不了驗證：

data = {
    'i': wd,
    'from': 'auto',
    'to': '',
    'domain': '0',
    'dictResult': 'true',
    'keyid': 'webfanyi',
    'sign': sign,
    'client': 'fanyideskweb',
    'product': 'webfanyi',
    …
    'pointParam': 'client,mysticTime,product',
    'mysticTime': e,
    …
}

順帶一提，表單裡的 pointParam 值是 client,mysticTime,product——它幾乎是把「哪些欄位參與簽名」寫在臉上，是逆向時最肥的線索。

兩條路跑出同一個簽名

有道這個案例剛好示範了「Python 與 execjs 兩路都跑通」的完整對照。純 Python 路線就是上面這幾行：字串自己拼、hashlib 自己算。execjs 路線則是把網站的簽名 JS 編譯進 Python、呼叫它的 get_sign(t)，JS 內部用 Node 的 crypto.createHash("md5") 算出一模一樣的值。兩條路的輸入相同、輸出就相同——如果你的兩個實作結果不一致，問題一定出在字串化細節，而不是演算法。

xdf 的 05 xdf.js 又是另一種型態：JS 寫好了 get_sign 整套流程，Python 只負責傳參數、拿結果。當簽名邏輯裡帶很多分支（areaCode 強制未定義、欄位合併之類的小動作）時，這種「把翻譯工作交回給原 JS」的做法最省事，也最不容易漏細節。

跟配方一差在哪

配方一（福建）配方二（xdf／有道）
欄位順序鍵名排序（不區分大小寫）JS 寫死的插入順序
金鑰擺法salt 黏在整串最前面UUID 黏在尾巴／當最後一個欄位
重現難點排序與 JSON 字串化要對齊簽名字串與送出編碼要對齊

兩種配方的骨架其實一模一樣——「拼接字串＋固定金鑰 → MD5」——變的只有拼接規則和金鑰的位置。這也是為什麼逆向簽名時第一個問題永遠是「拼了哪些欄位、什麼順序」，而不是「這是什麼演算法」。

做完長什麼樣

驗收標準是兩邊同時成立：其一，換一組查詢（不同城市、不同關鍵字、不同時間戳），你的簽名與瀏覽器對同樣輸入算出的簽名逐字元相同；其二，請求真的拿到資料——xdf 回課程清單 JSON，有道回翻譯結果（它的回應本體是加密的，那是對稱解密的另一個案例）。做到這裡，固定順序這條配方就算跑通了。

小結

「固定順序＋固定金鑰 → MD5」的欄位順序寫在 JS 程式碼裡，重現時要照抄插入順序，不能排序；金鑰可能黏在尾巴（xdf 的 UUID）或當成最後一個欄位（有道的 key）。最陰險的陷阱是字串版本：進簽名的欄位值必須和伺服器解析到的值一致，要編碼就先編碼再簽名。同一條配方用純 Python 與 execjs 各跑一次、輸出相同，才算真正掌握。

兩種配方都以 MD5 收尾，很容易讓你養成「sign 就是 MD5」的直覺。下一節就來拆掉這個直覺：丁香網的簽名是 40 位的 SHA-1，百度翻譯的簽名乾脆連標準雜湊都不是——該翻譯還是該呼叫 JS，需要一套判斷規則。
