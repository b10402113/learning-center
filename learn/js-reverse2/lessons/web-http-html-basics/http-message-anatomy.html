拆開一個 HTTP 訊息：請求行、標頭與狀態碼

Step 2/4 · Web、HTTP 與 HTML：爬蟲在跟什麼打交道

學習目標

讀懂一個原始 HTTP 請求和回應，指出方法、標頭與狀態碼各自的角色，並分辨 GET 與 POST 的差異。

前言：那一大坨密密麻麻的文字到底是什麼

上一節確定了爬蟲是在用 HTTP 跟伺服器對話。現在你把畫面帶到 DevTools：打開 Network 面板、重新整理頁面，點進其中一個請求，右邊冒出一大坨密密麻麻的文字，有英文、有斜線、有冒號。很多人到這裡就放棄了，直接去找「複製成 cURL」的按鈕。

但這坨文字其實很有秩序。它是由一行一行排好的 HTTP 訊息（message），分成請求與回應兩種，而且每個區塊都有固定位置。這一節的目標，就是讓你看到這坨文字時，能一眼認出：哪一行是方法、哪些是標頭、哪個數字是狀態碼。認出來之後，你才有辦法自己判斷「這個請求帶了什麼、伺服器回了什麼」。

HTTP 訊息：請求與回應都由四段組成

用於 HTTP 互動的資訊叫做 HTTP 訊息。客戶端送出的叫請求訊息，伺服器回覆的叫回應訊息。不管是哪一種，訊息本身都是多行文字拼起來的，而且結構固定。先看請求這邊的四段：

请求行：			请求方法 请求url 协议/版本号
请求头部【报文头】：各种键值对
空行回车
请求体【报文体】：具体的请求数据。

四段分別是：請求行、請求頭、一個空行，以及請求體。請求行說明「我要用什麼方法、要哪個位址、用哪個協定版本」；請求頭是一堆鍵值對，向伺服器自我介紹；空行用來分隔頭部與主體；請求體則裝著真正要傳給伺服器的資料。

請求行：方法、URL 與版本

請求行的第一個字是請求方法（method），接著是請求的 URL，也就是位址，最後是協定版本。用一個貼近生活的例子：假設你想在網站上搜尋「爬蟲」，瀏覽器送出的請求行就長得像這樣。

GET /search?wd=爬蟲 HTTP/1.1

這裡的 GET 是方法，/search?wd=爬蟲 是位址，HTTP/1.1 是版本。之後你在逆向時抓到的加密參數，多半就掛在這個位址的問號後面，或藏在底下的請求體裡。

請求頭：請求的自我介紹

請求頭存的是這個請求的主要說明，伺服器靠它認識客戶端。常見的幾個欄位如下：

請求頭它告訴伺服器什麼
User-Agent請求載體的身分識別。你在爬蟲裡偽裝成瀏覽器，改的就是它。
Referer客戶端是從哪個頁面來的。網站常拿它做防盜鏈。
Host想訪問哪一台主機。
Accept客戶端能接受的資料類型。
Accept-Charset客戶端支援的字元集。
Accept-Encoding客戶端支援的壓縮格式。
Accept-Language客戶端的語言環境。
If-Modified-Since快取資料的時間。
Connection請求完之後要斷開連線，還是保持連線。
X-Requested-With值為 XMLHttpRequest 時，代表這是用 ajax 方式發出的請求。

其中兩個之後會一直遇到。User-Agent 是「你是誰」的身分證，網站用它判斷來的是瀏覽器還是程式；Referer 是「你從哪來」的來源證明，圖片與影片站常用它擋掉直接連圖的請求。這兩者也是爬蟲最常需要模仿或補上的標頭。

請求體：要傳給伺服器的資料

請求體又叫請求參數，裝的是將要傳送給伺服器的資料。資料放哪裡，取決於請求方法。GET 與 POST 是最常用的兩種，差別如下：

面向GETPOST
資料放哪放在 URL 之後放在請求體裡
格式以 ? 和網址分隔，參數間用 & 相連，例如 EditBook?name=test1&id=123456資料不接在 URL 上
大小限制有，因為瀏覽器對 URL 長度有限制沒有大小限制
可否明文看到參數直接明示在網址上不會明文連在 URL 中

還記得上一節「爬蟲就是模擬瀏覽器」嗎？GET 與 POST 的差別，正是模擬時最常出錯的地方：如果一個搜尋是 POST 送出，你在爬蟲裡卻用 GET 去帶參數，伺服器自然不認。判斷方法就是看它的資料放在網址上還是請求體裡。

回應訊息：伺服器回的四段

伺服器回過來的回應訊息，結構跟請求對稱，一樣是四段：

状态行：协议版本/1.1 状态码 状态码的解释短语
响应头部：各种键值对
空行回车
响应正文【数据】：html文件/其他数据

開頭的狀態行，把請求行的「方法與位址」換成了「協定版本、狀態碼與狀態碼的說明」。回應頭一樣是鍵值對，空行一樣是分隔線，最後的回應正文才是伺服器真正要給你的資料，通常是一份 HTML 文件或一段 JSON。

回應頭：伺服器回覆的說明

回應頭存的是這個回應的主要說明，客戶端靠它認識伺服器，也靠它決定拿到資料後怎麼處理。常見欄位如下：

回應頭它告訴瀏覽器什麼
Location要跳轉到哪裡。重導向時的重點欄位。
Server伺服器的型號。
Content-Type回送資料的類型，例如是 HTML、JSON 還是圖片。爬蟲判斷怎麼解析它，就看這個。
Content-Encoding資料的壓縮格式。
Content-Length回送資料的長度。
Content-Language語言環境。
Content-Disposition指定以「下載」方式處理資料。
Transfer-Encoding資料是否以分塊方式回送。
Refresh要瀏覽器定時重新整理。
Expires、Cache-Control、Pragma控制瀏覽器要不要快取這份資料。

對爬蟲來說，Content-Type 是最該先看的一個。它會直接告訴你回應正文是網頁、是 JSON，還是二進位圖片，你也才知道該用 .text、.json() 還是 .content 去接。

狀態碼：這次請求的結果

狀態碼是伺服器收到請求後回報的結果。它是三位數字，藉由這個數字，客戶端能知道伺服器是正常受理了請求，還是出了什麼問題。數字的第一位就決定了大方向：

開頭代表常見例子
2xx成功，請求被正常處理200 OK
3xx重導向，資料在別的位置301、302，通常搭配 Location
4xx客戶端出錯，請求本身有問題403 Forbidden（被拒）、404 Not Found（找不到）
5xx伺服器端出錯500 Internal Server Error

之後爬蟲抓不到資料時，狀態碼會是你第一個該看的線索。看到 403，通常代表你被反爬機制擋下；看到 302，要想是不是少了登入憑證或標頭。

小結

一個 HTTP 請求由四段組成：請求行（方法、URL、版本）、請求頭（鍵值對的自我介紹）、空行、請求體。回應同樣四段，開頭換成帶狀態碼的狀態行。GET 把參數放在 URL 上，POST 放在請求體裡。User-Agent、Referer、Content-Type 與狀態碼，是爬蟲最常回頭檢查的幾個欄位。

看完請求與回應，你會發現它們都只是單次對話，講完就忘。那登入這種「要跨好幾次請求記住你是誰」的需求，到底怎麼達成？下一節要看的就是把無狀態補起來的機制：Cookie。
