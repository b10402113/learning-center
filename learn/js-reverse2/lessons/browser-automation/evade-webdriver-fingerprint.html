被認出來了：navigator.webdriver 指紋與 stealth 注入

Step 4/6 · 瀏覽器自動化與動態渲染

學習目標

解釋網站如何靠 navigator.webdriver 分辨自動化瀏覽器，並用 CDP 在頁面載入前注入腳本，把這個指紋藏起來。

前言：第一次跑很順，第二次就被擋了

前面兩節你已經能穩定地把頁面渲染出來、也等得到元素。照理說，接下來只要取 page_source 就大功告成。但實務上更常見的是另一種結局：程式跑起來了，網站卻跳出滑動驗證，或直接回你一頁「環境異常，請稍後再試」。你反覆檢查定位與等待，都沒問題，因為問題不在你的程式，而在瀏覽器已經被認出來是自動化的。

許多大型網站會主動偵測「這個瀏覽器是不是被程式控制」。這一節要拆解其中最常被檢查的一個訊號，並說明為什麼一定要在頁面載入之前處理，以及業界常用的 stealth 腳本在做什麼。這是讓自動化能正常走下去的關鍵補丁。

前置條件：你已完成 Selenium 的基本操作與等待策略（step 2–3），知道怎麼建立 driver 與取 page_source。

最容易被抓到的破綻：navigator.webdriver

網站分辨自動化與真人的方式有很多，但最簡單、最普遍的一種，是去讀瀏覽器上的一個屬性。正常的、你手動打開的瀏覽器裡，window.navigator.webdriver 的值是 undefined 或 false；但只要瀏覽器是被 Selenium 這類工具控制，這個屬性就會是 true。網站只要一行判斷，就能把你跟一般人分開。

這裡有個很容易被忽略的細節：檢測通常發生在頁面最早期。網站不會等到你慢慢取資料時才檢查，而是在頁面腳本一開始載入時就讀取這個值。所以如果你是在 get() 打開頁面、或甚至抓到資料之後，才用 execute_script() 去把 webdriver 改成 false，那就太晚了，對方早就讀到 true 並記下來了。

對策的核心：在頁面載入前先改好

既然檢測發生在最早，我們就必須在任何頁面腳本執行之前，先把這個屬性改掉。Selenium 提供了直接下 Chrome DevTools Protocol（CDP，瀏覽器開發者工具背後的那套通訊協定）指令的能力，叫 execute_cdp_cmd()。其中 Page.addScriptToEvaluateOnNewDocument 這個指令的用途，正是「註冊一段腳本，往後每一個新文件建立時都先執行它」。

把一段修改 navigator.webdriver 的腳本註冊進去，之後無論瀏覽器打開哪個頁面，這支腳本都會搶在頁面自己的程式碼之前跑完，於是網站讀到的就是被改過的值。實務上通常不會自己從頭寫，而是載入社群維護的 stealth 腳本：

from selenium.webdriver import ActionChains
from selenium.webdriver import Chrome

driver = Chrome('./chromedriver',options=chrome_options)
#Selenium在打开任何页面之前，先运行这个Js文件。
with open('./stealth.min.js') as f:
    js = f.read()
#进行js注入，绕过检测
#execute_cdp_cmd执行cdp命令（在浏览器开发者工具中执行相关指令，完成相关操作）
#Page.addScriptToEvaluateOnNewDocument执行脚本
driver.execute_cdp_cmd("Page.addScriptToEvaluateOnNewDocument", {
  "source": js
})

driver.get('https://www.taobao.com')

逐段看：先把 stealth.min.js 整個檔案讀成字串 js；再透過 execute_cdp_cmd 把這段腳本註冊到「每個新文件載入時執行」；最後才 get() 打開目標頁。順序是重點：註冊一定要在 get() 之前，否則第一個頁面就已經穿幫了。（範例裡的 chrome_options 需要你在前面先建立好並設定好瀏覽器參數。）

為什麼用 stealth.min.js，而不是自己改一行

你可能會想：既然只是把 webdriver 改成 false，自己寫一行 Object.defineProperty 不就好了？可以，但通常不夠。因為 navigator.webdriver 只是眾多指紋的其中一個，網站還會交叉檢查好幾個特徵：例如 navigator.plugins 的內容、navigator.languages、window.chrome 物件存不存在，以及各種瀏覽器環境細節。單改一個欄位，其他欄位露出的破綻照樣會被拼湊出來。

stealth.min.js 就是為此存在的社群腳本，它一次補齊這些常見特徵。它本身是一支被壓縮、混淆過、沒有可讀結構的長腳本，你不需要逐行看懂它，把它當成一份「隱藏自動化特徵的補丁」來載入與註冊即可。同樣的手法在別的工具上也相通：Pyppeteer 沒有 CDP 這層包裝時，會直接在頁面內用 page.evaluate 執行 Object.defineProperties(navigator, {webdriver: {get: () => false}})，把取值改成永遠回傳 false。

邊界與取捨：它不是萬靈丹

要把它放在正確的位置看。第一，隱藏 webdriver 只解決了「最明顯的那一個訊號」，網站還有其他層次的偵測：請求的 TLS／HTTP 指紋、滑鼠移動與打字節奏等行為特徵、甚至 Canvas 繪圖的細微差異。第二，改寫瀏覽器原生屬性本身也可能被反偵測：有些網站會比對函式的 toString() 是否還顯示原生程式碼，來判斷你有沒有動過手腳。也就是說，這是一場貓捉老鼠，而不是裝一次就永久免疫。

更重要的定位是：我們隱藏指紋的目的，只是讓頁面願意正常渲染，好讓你看見它原本的邏輯。真正困難、也真正有價值的工作，是看懂它的請求怎麼被簽名、參數怎麼被加密，這件事是後面逆向章節的主題。另外，這些技術請用在合法、被授權的範圍內，並留意網站的服務條款與 robots 規範，技術可行不等於可以任意使用。

小結

自動化瀏覽器最明顯的破綻是 navigator.webdriver：正常瀏覽器是 false／undefined，被控制時是 true。網站通常在頁面最早期就讀取它，所以必須用 CDP 的 Page.addScriptToEvaluateOnNewDocument，在每次新文件建立時搶先執行腳本，把指紋改掉；實務上直接載入社群維護的 stealth.min.js 一次補齊多個特徵。它只是第一道補丁，不是萬靈丹。

這也是「換工具」的動機之一：既然偵測與反偵測這麼麻煩，有沒有另一種驅動瀏覽器的方式，設定更省事、又能自然接上非同步流程？下一步要看的 Pyppeteer 就是這樣的一個替代方案。
