瀏覽器還是封包？DrissionPage 的模式切換

Step 6/6 · 瀏覽器自動化與動態渲染

學習目標

在 ChromiumPage、SessionPage、WebPage 之間選對工具，並用模式切換處理「登入嚴格、資料好抓」的網站。

前言：整場都開著瀏覽器，是不是有點浪費？

前面幾節你學會了用 Selenium 與 Pyppeteer 開真瀏覽器。但每次抓資料都開著一個瀏覽器，其實又慢又吃資源，尤其當你只是要抓幾頁清單、打幾個 API 而已。偏偏很多網站的設計是這樣：登入那一關非常嚴格，但登入之後的資料端點卻意外地好打。這種網站如果全程用瀏覽器，等於殺雞用牛刀；如果全程用封包請求，又卡在登入過不去。

這一節要介紹的 DrissionPage，就是把這兩件事放進同一個工具：它既能控制瀏覽器，也能像 requests 一樣收發封包，而且兩者之間可以切換。你要做的決定，就是「什麼時候用瀏覽器、什麼時候切回封包」。這是一個取捨問題，不是哪個工具比較高級。

前置條件：你已完成本事前面的瀏覽器自動化步驟，並學過 requests 與 Cookie／Session 維持。這一節的操作目標網站需要登入帳號，請用你自己的測試帳號。

三個頁面類：先看你在選什麼

DrissionPage 用「頁面類」來區分能力。同一個套件裡有三個主要類別，選錯了不是不能用，只是會多繞路或多浪費效能。

頁面類能力適合什麼情況
ChromiumPage只控制瀏覽器，操作真實頁面與元素需要 JS 渲染、點擊、輸入、登入
SessionPage只收發封包，像 requests，但內建查找元素的語法端點已知、不需要執行 JS
WebPage兩者兼具，可用 change_mode() 切換模式需要先用瀏覽器登入，再切封包快速採集

可以這樣理解：ChromiumPage 是「重的、完整的」，SessionPage 是「輕的、快的」，WebPage 是「兩者合一、能換檔」。多數時候，如果網站不需要 JS 就能拿到資料，你根本不會走進這一節，直接用 SessionPage 就好；這一節真正的主角是 WebPage 的切換能力。

選項一：全程瀏覽器（ChromiumPage）

先看純瀏覽器模式長什麼樣。以下範例用 ChromiumPage 打開 gitee 登入頁、填入帳密並登入。注意它的定位語法：ele() 找第一個符合的元素、eles() 找全部；#user_login 是 CSS 式的 id 定位，@value=登 录 則是依「屬性等於某值」定位。

from DrissionPage import ChromiumPage

# 创建页面对象，并启动浏览器
page = ChromiumPage()
# 跳转到登录页面
page.get('https://gitee.com/login')

# 定位到账号文本框，获取文本框元素
ele = page.ele('#user_login')
# 输入对文本框输入账号  
ele.input('您的账号')
# 定位到密码文本框并输入密码
page.ele('#user_password').input('您的密码')
# 点击登录按钮:@attrName=value,这是根据属性和属性值进行标签定位的方式
page.ele('@value=登 录').click()

這裡有一個很體貼的新手設計：ele() 內建了等待，如果元素還沒載入，它會等到元素出現或到達時限，預設是十秒。也就是說，上一節那些等待策略，DrissionPage 已經幫你在查找元素這一步預設墊好了一層，你比較不會一開局就踩到「太早找元素」的坑。

但全程瀏覽器有代價：它開著一個真的 Chromium，慢、吃記憶體。抓一兩頁還好，要翻幾十頁清單就不划算。

選項二：全程封包（SessionPage）

如果你的請求不需要瀏覽器渲染，那用 SessionPage 就對了。它的 get()／post() 語法跟 requests 一致，只是回傳值不同（回傳的是布林值，代表成功或失敗），而且它內建了查找元素的方法，讓你不用另外接 BeautifulSoup。下面這個範例抓 gitee 推薦頁前三頁的開源庫名稱與連結：

from DrissionPage import SessionPage

# 创建页面/请求对象
page = SessionPage()

# 爬取3页
for i in range(1, 4):
    # 访问某一页的网页
    page.get(f'https://gitee.com/explore/all?page={i}')
    # 获取所有开源库元素列表(所有库的链接的a标签的class属性值都是一样的)
    links = page.eles('.title project-namespace-path')
    # 遍历所有元素
    for link in links:
        # 打印链接信息：
        print(link.text, link.link)

這裡的 page.eles('.title project-namespace-path') 回傳一批元素，link.text 取文字、link.link 取它的 href 或 src。SessionPage 也內建了自動的 User-Agent 設定，而且 get() 有連線失敗重試，比原生 requests 稍微省事一些。它快的關鍵在於：它不開瀏覽器，只是一個包裝過的封包客戶端。

選項三：切換模式（WebPage 的 change_mode）

真正的重點來了。當一個網站「登入很嚴格、但登入後資料很好打」，你可以先用瀏覽器的模式完成登入，再切到封包模式去採集資料。WebPage 提供 change_mode() 做這件事：切換時，程式會在新模式重新訪問當前 URL，之後的請求就走封包。以下範例登入 gitee 後切換、再抓個人主頁左下角的組織名稱：

from DrissionPage import ChromiumOptions
from DrissionPage import WebPage

# 创建页面对象
page = WebPage()
# 访问网址,进行登录
page.get('https://gitee.com/login?redirect_to_url=%2F')
# 定位到账号文本框，获取文本框元素
ele = page.ele('#user_login')
# 输入对文本框输入账号
ele.input('1xxx535')
# 定位到密码文本框并输入密码
page.ele('#user_password').input('bxxx35')
# 点击登录按钮:@attrName=value,这是根据属性和属性值进行标签定位的方式
page.ele('@value=登 录').click()

# 切换到收发数据包模式
page.change_mode() #切换的时候程序会在新模式重新访问当前 url。
#切换模式后，重新访问基于登录状态后新的url（个人主页）
page.get('https://gitee.com/Mr_bobo')

# 根据class属性值获取div标签，然后将该div下面class为item的元素标签批量获取
items = page.ele('.ui middle aligned list').eles('.item')
# 遍历获取到的元素
for item in items:
    # 打印元素文本
    print(item('.content').text)

這段的重點在 page.change_mode() 那一行：它把「瀏覽器控制」換成「封包收發」，之後的 get() 就用輕量的請求去拿資料，但保留剛剛登入得到的狀態。另一種等價的寫法是開兩個物件：先用 ChromiumPage 登入，再建一個 SessionPage 去打登入後的頁面，兩種做法概念相同，只是 WebPage 把它收斂在一個物件上。

順帶把 DrissionPage 的定位語法整理成一張小表，之後查閱用：

語法意思
ele('@id=one')屬性 id 等於 one 的第一個元素
eles('@|id=row1@|id=row2')或（OR）條件
ele('@@class=p_cls@@text()=第三行')且（AND）條件
eles('@id:ow')id 含 ow（模糊）
eles('@id^row')／ele('@id$w1')開頭為 row／結尾為 w1
ele('#one')／ele('.p_cls')CSS 式的 id／class 定位
ele('text=第二行')／ele('tag:div')文字等於／標籤定位
eles('xpath://div/p[@id="row1"]')用 XPath 定位

怎麼選：兩個自我提問

把選擇收斂成兩個問題，你幾乎不會選錯：

  1. 取得資料之前，需要瀏覽器渲染，或需要像人一樣的複雜互動嗎？如果需要，就用瀏覽器模式（ChromiumPage 或 WebPage）。
  2. 登入完成之後，資料端點是不是用簡單請求就能拿到？如果是，就在登入後切到封包模式（change_mode() 或 SessionPage）來採集，省下開瀏覽器的成本。

反例：切模式救不了的情況

切換模式很方便，但它不是萬能。第一，登入密碼若是密文，你直接打登入 API 是行不通的，因為密碼欄位在送出前已經先被 JS 加密過。這種情況真正該做的是逆向前端的密碼加密，這是後面逆向章節的任務，不是換個模式能解決的。第二，SessionPage 不會執行 JS；如果那份資料真的靠 JS 在瀏覽器裡算出來，切到封包模式一樣拿不到，你得留在瀏覽器模式。第三，切模式改變的只是「資料往來的方式」，登入狀態能不能延續，取決於網站的登入態放在哪裡；如果它只存在瀏覽器的記憶體裡，切過去之後未必能沿用，這時就要確認對應的 cookie 有沒有被帶上。

所以真正的判準不是「哪個模式比較潮」，而是：這一步需要瀏覽器還是只需要封包？需要瀏覽器的環節就老實用瀏覽器，能省則省的地方才切回封包。

小結

DrissionPage 把「控制瀏覽器」與「收發封包」合成同一個工具：ChromiumPage 只開瀏覽器、SessionPage 只打封包、WebPage 兩者兼具並能用 change_mode() 切換。面對「登入嚴格、資料好打」的網站，正解是先用瀏覽器完成登入，再切回封包快速採集。但若登入本身需要逆向密碼加密，或資料真的靠 JS 渲染，切模式救不了，該做的是逆向或留在瀏覽器模式。
