## Sections (L2)

### Wiring ProjectRead into the API
- Locator: [[sources/pro-python/completed/20260903_29.md#wiring-projectread-into-the-api]]
- Summary: Replaces the inline Pydantic `ProjectRead` class with SQLModel-based models, importing from the centralized `models.py` instead of defining validation schemas inline.
- Key claims: SQLModel replaces Pydantic BaseModel for API schemas; centralized model definitions in `models.py` prevent duplication; the mock database is replaced with real database queries.
- Learner-relevant: Moving from inline schemas to centralized models is the transition from prototype to production code.

### Alembic setup and configuration
- Locator: [[sources/pro-python/completed/20260903_29.md#alembic-setup-and-configuration]]
- Summary: Alembic is initialized in the project with `alembic init`, creating an INI config file and `env.py` that must be configured to know the database URL and SQLModel metadata location.
- Key claims: `alembic.ini` stores the database URL; `env.py` runs on every Alembic command and must import SQLModel metadata; `script.py.mako` is a template that auto-adds SQLModel imports to generated migrations; `pydantic-settings` reads environment variables for database configuration.
- Learner-relevant: Alembic configuration is a one-time setup that pays off every time the database schema changes.

### Migration revisions
- Locator: [[sources/pro-python/completed/20260903_29.md#migration-revisions]]
- Summary: Migrations work by creating revision files that describe how to move the database forward (upgrade) and backward (downgrade), enabling safe schema evolution.
- Key claims: `alembic revision --autogenerate` detects model changes and creates a migration; `alembic upgrade head` applies all pending migrations; `alembic downgrade` reverts to a previous revision; each migration is a Python file with upgrade/downgrade functions.
- Learner-relevant: Understanding upgrade/downgrade gives you the ability to safely roll back schema changes in production.
