## Sections (L2)

### Refactoring to crud.py
- Locator: [[sources/pro-python/completed/20260903_33.md#refactoring-to-crudpy]]
- Summary: Extracts database operations from `main.py` into a dedicated `crud.py` module, so `main.py` handles HTTP routing and parameter injection while `crud.py` handles database queries and transaction management.
- Key claims: CRUD functions call `session.add()`, `session.commit()`, `session.refresh()`; routes handle HTTP concerns (status codes, exceptions); no API behavior changes during the refactor; `main.py` calls into `crud.py` for data access.
- Learner-relevant: Separation of concerns makes code maintainable — HTTP logic and database logic have different reasons to change.

### Guidelines for the refactor
- Locator: [[sources/pro-python/completed/20260903_33.md#guidelines-for-the-refactor]]
- Summary: CRUD functions manage transaction boundaries; routes must not touch session.add/commit/refresh on the success path; the refactoring must not change any API behavior.
- Key claims: Transaction boundaries stay in crud.py; routes only handle HTTP-level concerns; existing tests serve as the safety net for the refactor; `select()` with `order_by()` replaces raw dictionary operations.
- Learner-relevant: Refactoring with tests as guardrails is a professional development practice — it lets you restructure code confidently.

### Verifying with tests
- Locator: [[sources/pro-python/completed/20260903_33.md#verifying-with-tests]]
- Summary: After refactoring, running the existing test suite confirms that no API behavior changed — the tests serve as the contract that the refactored code still works correctly.
- Key claims: `uv run pytest` should pass with zero changes to test files; if tests fail, the refactor broke the API contract; test-first development enables safe refactoring.
- Learner-relevant: Tests are your safety net during refactoring — they tell you immediately if something broke.
