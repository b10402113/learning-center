測試重複專案回傳 409 Conflict

Centralized exception handling · Step 4

學習目標

能寫一個測試，用重複的專案名稱送出 POST 請求，並斷言回應狀態碼為 409 Conflict 且包含有意義的 detail 訊息。

測試的價值

處理器寫好了，但我們要確認它真的在重複名稱時回傳 409，而不是 500。測試會幫我們捕捉回歸——萬一有人改壞了處理器，測試會先失敗。

測試步驟

  1. 先建立一個專案（第一次 POST 應該成功）。
  2. 用同一個名稱再送一次 POST。
  3. 斷言回應狀態碼是 409。
  4. 斷言回應 body 包含 detail 訊息。

測試範例

from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)

def test_create_duplicate_project_returns_409():
    # 第一次建立應該成功
    response = client.post("/projects", json={"name": "existing"})
    assert response.status_code == 200

    # 第二次建立同名專案應該回傳 409
    response = client.post("/projects", json={"name": "existing"})
    assert response.status_code == 409
    assert "detail" in response.json()

斷言細節

除了狀態碼，我們也檢查 detail 欄位是否存在。這確保處理器確實回傳了 JSON 回應，而不是空 body 或 HTML 錯誤頁面。

assert response.status_code == 409
assert "detail" in response.json()

為什麼這個測試重要？

如果未來有人移除了處理器，或者把狀態碼改成了 400 或 500，這個測試就會失敗。它守護的是「API 對資料衝突的回應方式」這個契約。

總結

寫一個測試：先建立一個專案，再用同名送出第二次 POST，斷言狀態碼為 409 且 body 包含 detail。這個測試確保集中式處理器持續保護你的 API。
