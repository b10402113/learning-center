用 Pydantic 模型塑形回應

學習目標

定義 Pydantic BaseModel 來規範 API 回應的結構，理解 response_model 的作用。

問題：回傳的資料長什麼樣？

到目前為止，我們的路由直接回傳 dictionary：

@app.get("/projects/{project_id}")
def get_project(project_id: int):
    project = PROJECTS.get(project_id)
    if project is None:
        return {"error": "Project not found"}, 404
    return project

這能運作，但有兩個問題：

  1. 沒有合約：呼叫者不知道回應裡有哪些欄位，只能猜
  2. 沒有過濾：如果 dictionary 裡有不想暴露的欄位（例如 internal_notes），它們會全部回傳

我們需要一個方式來定義「API 回應應該長什麼樣」。

Pydantic BaseModel

Pydantic 是一個資料驗證庫。它的核心是 BaseModel 類別——你用它定義資料的結構：

from pydantic import BaseModel

class ProjectRead(BaseModel):
    id: int
    name: str
    slug: str

這個 ProjectRead 類別定義了三件事：

  • 回應必須有 id（整數）
  • 回應必須有 name（字串）
  • 回應必須有 slug（字串）

其他欄位？不會出現在回應裡。ProjectRead 就像一個模板——只有模板上有的欄位才會被保留。

命名慣例：Read 後綴表示「讀取/回應」模型。之後你會看到 Create（建立請求）、Update（更新請求）等。這種命名讓模型的角色一目了然。

response_model：把模型掛到路由上

定義好模型後，用 response_model 參數把它掛到路由裝飾器上：

@app.get("/projects/{project_id}", response_model=ProjectRead)
def get_project(project_id: int):
    project = PROJECTS.get(project_id)
    return project

現在 FastAPI 做了三件事：

  1. 過濾：只回傳 ProjectRead 定義的欄位（id、name、slug），其他欄位被移除
  2. 序列化：把 Pydantic 模型轉成 JSON
  3. 文件：在 Swagger UI 裡顯示回應的結構

實際效果

假設 mock 資料裡多了一個不想暴露的欄位：

PROJECTS = {
    1: {
        "id": 1,
        "name": "Project Alpha",
        "slug": "project-alpha",
        "internal_notes": "客戶要求延後交付"  # 敏感資料
    },
}

沒有 response_model：internal_notes 會出現在 API 回應裡。

有 response_model=ProjectRead：回應只有 id、name、slug，internal_notes 被過濾掉。

完整範例

把所有東西組合起來：

from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class ProjectRead(BaseModel):
    id: int
    name: str
    slug: str

PROJECTS = {
    1: {"id": 1, "name": "Project Alpha", "slug": "project-alpha"},
    2: {"id": 2, "name": "Project Beta", "slug": "project-beta"},
    3: {"id": 3, "name": "Project Gamma", "slug": "project-gamma"},
}

@app.get("/projects", response_model=list[ProjectRead])
def list_projects():
    return list(PROJECTS.values())

@app.get("/projects/{project_id}", response_model=ProjectRead)
def get_project(project_id: int):
    project = PROJECTS.get(project_id)
    if project is None:
        return {"error": "Project not found"}, 404
    return project

注意 list[ProjectRead]——這告訴 FastAPI 回應是一個 ProjectRead 的陣列。Python 3.9+ 支援這個語法。

為什麼要分離內部資料和 API 輸出？

在真實的應用程式裡，資料庫的模型（之後會用 SQLModel 定義）通常比 API 回應包含更多欄位。例如：

資料庫欄位API 回應？
id✅ 需要
name✅ 需要
slug✅ 需要
created_at看情況
internal_notes❌ 不暴露
owner_password_hash❌ 絕對不暴露

用 response_model 做一道防火牆：資料庫模型管儲存，Pydantic 模型管輸出。兩者分離，各管各的。

小結

Pydantic BaseModel 定義資料結構。response_model 把模型掛到路由上，自動過濾、序列化、生成文件。這種分離讓你的 API 有明確的合約——呼叫者知道會收到什麼，你也能控制哪些資料不該暴露。

到這裡，你已經有一個完整的 FastAPI 應用程式：路由、路徑參數、型別驗證、Pydantic 回應模型。資料還存在 dictionary 裡，但核心機制都到位了。之後的課程會逐步引入真正的資料庫、測試、部署。
