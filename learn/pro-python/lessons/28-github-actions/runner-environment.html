Reproducible runner environments

CI 的命令只有在 runner 擁有正確且可重現的環境時才有意義。

為什麼本機成功還不夠

你的電腦可能已經安裝了某個 Python 版本、快取了套件，或有未提交的環境設定。GitHub Actions 的 runner 是一次性的乾淨機器。這個差異很有價值：它迫使 CI 明確描述程式需要什麼，而不是依賴某位開發者的電腦狀態。

容器（container）也遵循同一個想法：把 interpreter、依賴和啟動方式固定在一個可攜的 artifact 中。CI 不一定要用 Docker，但「明確、可重現」是共同目標。

典型初始化順序

steps:
  - uses: actions/checkout@v4
  - uses: astral-sh/setup-uv@v5
    with:
      enable-cache: true
  - run: uv python install 3.14
  - run: uv sync --dev
  - run: uv run pytest
  1. checkout 讓 runner 取得提交中的程式碼。
  2. 安裝 UV，讓團隊使用同一套依賴工具。
  3. 選定 Python 版本，避免不同 runner 默認版本造成差異。
  4. 依照 lockfile 和專案設定安裝開發依賴。
  5. 最後才執行檢查。

順序本身就是診斷線索。若 checkout 失敗，不必看 pytest；若 sync 失敗，先檢查 Python 版本、lockfile 或套件設定。

重現性的三個支點

支點固定什麼解決的問題
版本Python 與工具版本不同版本的行為差異
依賴lockfile 與 dev dependencies今天安裝到不同套件
命令uv run 的檢查命令每個人執行不同檢查
