選擇 production 的秘密儲存方式

讓部署平台在執行時注入秘密，而不是把它放進檔案

目標

你會說明為什麼 production 不該依賴 .env，並在三種常見方案之間做出選擇：平台原生環境變數、Kubernetes Secrets、HashiCorp Vault。

先看理想流程

# 部署設定（範例：平台環境變數）
DATABASE_URL = 平台秘密儲存 > 注入容器環境
JWT_SECRET   = 平台秘密儲存 > 注入容器環境

# 應用程式只讀環境
import os
DATABASE_URL = os.environ["DATABASE_URL"]
JWT_SECRET = os.environ["JWT_SECRET"]

秘密的真實值存在平台的管理系統中，應用程式啟動時才被注入。.env 在這裡沒有位置，因為它通常以明文存放在映像檔或主機磁碟上。

三種常見方案

方案運作方式適合情境
雲端平台原生環境變數由雲端供應商的管理服務保存並注入使用單一雲端平台的服務
Kubernetes Secrets以 Kubernetes 物件管理，可加密靜態資料部署在 Kubernetes 的工作負載
HashiCorp Vault集中管理，提供細粒度存取控制與稽核多環境、多團隊與合規需求

三者不是互斥取代關係。你可能在雲端平台上執行 Kubernetes，同時用 Vault 管理高敏感度憑證。

為什麼不使用 .env

.env 的設計目標是簡化本機載入。到了 production，它會帶來實際風險：檔案明文落地、容易在打包映像檔時被一起帶上、缺乏存取稽核，也難以集中輪換。平台的秘密管理服務則通常提供權限控制、稽核紀錄與輪換流程。

# Dockerfile 反例：永遠不要把秘密複製進映像檔
COPY .env .env   # 錯誤：秘密會被寫進映像層

選擇順序

  1. 先確認部署環境：單一雲端、Kubernetes，還是混合。
  2. 接著選擇該環境原生的方案，取得最少整合成本。
  3. 當需要跨環境集中治理或更細的權限時，再加入 Vault 等集中式方案。

無論選哪一種，應用程式的讀取介面都維持一致：從環境變數或專用 SDK 取得值，程式碼不硬編碼秘密。
