用 .env 管理本機開發設定

讓本機設定方便載入，同時不把密碼送進版本控制

目標

你會把資料庫連線等專案設定放進本機 .env，並知道這個檔案的安全邊界：它適合開發便利，不適合當 production 的秘密儲存庫。

先看使用方式

# .env，只存在你的本機
DATABASE_URL=postgresql://dev:dev@localhost:5432/tasks
JWT_SECRET=local-only-development-key
DEBUG=true
# config.py
import os

DATABASE_URL = os.environ["DATABASE_URL"]
JWT_SECRET = os.environ["JWT_SECRET"]
DEBUG = os.environ.get("DEBUG", "false").lower() == "true"

應用程式從環境變數讀值，程式碼本身不需要知道每台機器的密碼。os.environ["NAME"] 在設定遺失時會立即報錯，適合要求一定存在的值；os.environ.get("NAME", default) 則能提供預設值，適合可選設定。

.env 解決什麼問題

如果你每天切換兩個專案，直接在 shell 裡反覆執行 export DATABASE_URL=...，容易忘記目前 shell 服務的是哪個專案。.env 把專案專屬設定集中在專案根目錄，開發工具或 dotenv 載入器可以在啟動時讀取它。

這種便利不代表檔案已經被加密，也不代表任何讀到檔案的人沒有風險。它只是把設定從程式碼移到另一個本機檔案。

永遠放進 .gitignore

# .gitignore
.env
.env.*
!.env.example

.env 可能包含資料庫密碼、JWT secret 或 API key。將它加入 Git 的忽略清單，避免誤 push。若團隊需要知道有哪些欄位，建立不含真實值的 .env.example：

DATABASE_URL=postgresql://user:password@localhost:5432/database
JWT_SECRET=replace-me
DEBUG=false

.env.example 是欄位名稱與格式的文件，不是秘密本身。真正的 .env 要由每位開發者在本機建立。

本機與 production 的分界

本機的 .env 可以讓你快速啟動服務。production 不應把同樣的檔案打包進 Docker image 或部署到伺服器。正式環境應由部署平台在啟動服務時注入設定，後面的課程會比較可用的方案。

記住：「不在程式碼裡」只是第一步；「不在版本控制裡」也不等於「已經安全」。
