Raising Exceptions

Node 34 · Step 1 / 4 · pro-python

Learning goal

Use raise to throw ValueError and other exceptions when code cannot complete safely.

When things go wrong

Imagine you're writing a function that creates a new project. The caller passes in a name. What happens when they pass in an empty string? A None? A name that's already taken?

You could return None and hope the caller checks. You could return a tuple (success, error) and hope the caller unpacks it. But in Python, the idiomatic way to say "this cannot continue" is to raise an exception.

The raise keyword

raise stops the normal flow of your function and creates an exception object. The exception bubbles up through the call stack until something catches it — or until it hits the top and crashes the program.

def validate_project_name(name: str) -> None:
    if not name:
        raise ValueError("Project name cannot be empty")

Here, ValueError is the right choice because the value of the argument is wrong. Python's built-in exceptions cover most common cases:

ExceptionUse when
ValueErrorValue is wrong type or invalid
TypeErrorWrong type entirely
KeyErrorDictionary key missing
IndexErrorList index out of range
FileNotFoundErrorFile doesn't exist
Rule of thumb: raise as early as possible. Fail fast, fail loud. The closer the raise is to the actual problem, the easier it is to debug.

Adding context to the message

A good exception message tells the caller what went wrong and why. Don't just say "invalid input" — say what was invalid and what was expected.

# Bad
raise ValueError("Invalid input")

# Good
raise ValueError(f"Project name must be 1-50 characters, got {len(name)}")

Don't raise when you can avoid it

Raising isn't free. It breaks the normal flow and forces the caller to handle it. If you can return a sensible default or validate before calling, that's often cleaner. Raise when continuing would cause worse problems — data corruption, security holes, or silent wrong answers.
