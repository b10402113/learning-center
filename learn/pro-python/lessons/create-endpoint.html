Create endpoint (POST)

Node 13 · Step 2 of 4

Learning goal

Implement a POST endpoint that validates incoming JSON, generates a slug, writes to the database inside a transaction, and returns the complete created record.

The anatomy of a write endpoint

A read endpoint fetches data. A write endpoint changes it. In REST, creation maps to POST. The request carries a JSON payload — the project's name, description, and version — and the response returns the newly created record, including server-generated fields like id and created_at.

Every write endpoint follows the same rhythm:

PhaseWhat happens
ValidateFastAPI parses JSON into a Pydantic schema
TransformDerive fields the client didn't send (slug, timestamps)
Persistsession.add() → session.commit()
Refreshsession.refresh() pulls server-generated values
RespondReturn the complete object to the client

Defining the input schema

The client sends what they know — name, description, version. They don't send id, slug, or created_at, because those are server-side concerns. A separate ProjectCreate schema captures exactly what the client is allowed to provide:

class ProjectCreate(BaseModel):
    name: str
    description: str = ""
    version: str = "0.1.0"

Notice there's no id field. If the client tried to send one, Pydantic would silently drop it (or raise an error, depending on configuration). That's the boundary between client input and server authority.

Writing the endpoint

With the schema in place, the endpoint itself is compact:

@app.post("/projects", response_model=ProjectRead)
def create_project(
    project_in: ProjectCreate,
    session: Session = Depends(session_dep),
):
    slug = slugify(project_in.name)
    project = Project(**project_in.model_dump(), slug=slug)
    session.add(project)
    session.commit()
    session.refresh(project)
    return project

Three things happen between session.add() and return project:

  1. session.add(project) stages the object for insertion — it's queued but not yet written.
  2. session.commit() executes the INSERT against the database and ends the transaction.
  3. session.refresh(project) re-reads the row from the database to populate auto-generated columns.

Why session.refresh() is non-negotiable

After session.commit(), the project object still has id=None and created_at=None in Python memory. Those values were generated by the database — auto-incrementing sequence, default timestamp — and SQLAlchemy doesn't automatically push them back into the object.

If you skip session.refresh(), the client receives a response with "id": null. That's a bug that's easy to miss in testing (the object "looks" right) but breaks every downstream consumer that needs the new record's ID.

session.refresh(project) issues a SELECT to fetch the latest state. It costs one extra query, but it guarantees the response is complete and accurate.

Unpacking the payload with model_dump()

project_in.model_dump() converts the Pydantic schema into a dictionary: {"name": "...", "description": "...", "version": "..."}. The ** operator unpacks it as keyword arguments to the Project constructor:

Project(**project_in.model_dump(), slug=slug)
# equivalent to:
Project(name="...", description="...", version="...", slug="...")

This pattern keeps the endpoint clean — you don't manually assign every field — while still letting you inject server-side values like slug.

Handling validation errors

If the client sends {"name": 123} (a number instead of a string), FastAPI returns a 422 Unprocessable Entity response before the endpoint body even runs. The Pydantic schema is the first line of defense — it rejects malformed payloads automatically.

If the client sends a duplicate name and your database has a unique constraint, the session.commit() will raise an IntegrityError. That's a server error (500) unless you catch it. Later in this node you'll learn how to handle that gracefully.
