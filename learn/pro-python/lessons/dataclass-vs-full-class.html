什麼時候該用完整類別？

學習目標：能根據「資料容器 vs 行為載體」的判斷準則，決定一個型別該用 @dataclass 還是手寫完整類別。

不是所有東西都適合 dataclass

前面三課都在講 @dataclass 有多方便，但這不代表你應該把整個專案全部的類別都換成 dataclass。@dataclass 是一個工具，不是信仰。知道它擅长什麼、不擅长什麼，比盲目使用更重要。

dataclass 的核心假設是：這個物件主要是一堆欄位的容器，行为只是附加的。一旦這個假設不成立，樣板減少的效益就會被其他限制抵銷。

什麼時候該用 dataclass

只要下面任何一個條件成立，dataclass 就是個好選擇：

條件例子
主要目的就是裝資料API 回傳的 JSON 形狀、資料庫 row 的對應物件
欄位數量多，手寫樣板煩有 10 個欄位的配置物件
需要值語意（== 比較、hash）座標、貨幣、日期範圍
希望自動產生 __repr__ 方便除錯幾乎所有資料物件都受惠
不需要複雜的初始化邏輯絕大多數情境

什麼時候該用完整類別

下面任何一個條件成立，手寫完整類別通常會比硬套 dataclass 更好：

條件為什麼 dataclass 不適合
建構子需要複雜的初始化邏輯dataclass 的 __init__ 就是「把參數塞進屬性」，客製化空間有限
需要大量自訂特殊方法（__enter__、__call__ 等）dataclass 是為了簡化樣板，不是為了取代所有特殊方法
繼承階層很深，而且父類行為很複雜dataclass 對多重繼承和複雜 MRO 的支援有限
需要控制記憶體佈局（__slots__）或底層行為dataclass 目前對 __slots__ 的支援還不夠直覺
物件生命周期複雜（開啟/關閉、連線/中斷）這通常需要 context manager，不屬於 dataclass 要解決的問題

一個具體的判斷流程

下次在決定用哪一種的時候，可以這樣問自己：

Q1：這個類別的主要責任是什麼？

如果答案是「裝資料」→ 先考慮 @dataclass。如果答案是「執行某個行為」或「管理某個資源」→ 考慮手寫完整類別。

Q2：我需要客製 __init__ 嗎？

如果你的初始化邏輯不只是「把參數塞進去」，而是需要做 IO、查資料庫、複雜計算 → 手寫 __init__ 比較清楚。

Q3：我會繼承這個類別嗎？繼承階層複雜嗎？

單層、簡單的繼承，dataclass 處理得了。多層或需要覆寫一大堆父類方法的時候，手寫類別比較不會踩雷。

真實世界的混合用法

在 FastAPI 專案裡，你會看到一種很常見的組合：用 dataclass 或 Pydantic 的 BaseModel 來裝請求和回應的資料形狀，但 router、service、repository 這些管理行為的元件，通常還是手寫完整類別或甚至只是函式。

這樣做很合理：邊界上（API 進出口）用資料容器確保形狀清晰，核心邏輯（怎麼處理這些資料）用完整類別或函式保持彈性。不是非此即彼，而是看位置決定工具。

不要過度工程

最後提醒一句：如果一個類別目前只需要 3 個欄位，而且未來很長一段時間也不會變，那用 @dataclass 就好，不要因為「搞不好以後會變複雜」就先手寫完整類別。等到真的需要的那天，再加上去也不遲。

總結：dataclass 是你的預設起點，不是終點。需求變複雜的時候，隨時可以退一步手寫完整類別；但不要在手寫樣板寫到煩的時候，還死守著「完整類別比較正規」的偏見。
