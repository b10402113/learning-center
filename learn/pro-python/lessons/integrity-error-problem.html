當唯一約束被違反時會發生什麼？

Centralized exception handling · Step 1

學習目標

理解當資料庫的唯一約束被違反時，SQLAlchemy 如何拋出 IntegrityError，以及 FastAPI 預設如何將它變成 500 Internal Server Error。

從使用者按下送出開始

假設你的 API 允許建立專案，而 name 欄位有唯一約束（unique constraint）——不允許兩個同名專案。當使用者送出一個已經存在的名稱時，資料庫會拒絕這筆寫入，因為違反了約束。

SQLAlchemy 的反應：拋出 IntegrityError

當底層資料庫回傳約束違反錯誤時，SQLAlchemy 會把它包裝成一個 IntegrityError（IntegrityError，完整性錯誤）。這個例外的名字來自資料庫術語：資料完整性（data integrity）被破壞了——現有的規則被違反了。

IntegrityError 是 SQLAlchemy 的例外，不是 FastAPI 的。它可能來自唯一約束違反、外鍵約束違反、或者 NOT NULL 欄位收到 None 等情境。

FastAPI 的預設回應：500 Internal Server Error

如果你沒有特別處理 IntegrityError，它會一路往上傳播（propagate），FastAPI 最終把它變成 HTTP 500 Internal Server Error。對呼叫端來說，500 代表「伺服器內部出了某種問題」——但它完全沒有說明 什麼 出了問題。

這會導致兩種困擾：

  • 開發者除錯時不知道是資料衝突還是真正的伺服器臭蟲。
  • 呼叫端無法區分「名稱已經存在」跟「伺服器壞掉了」，所以無法給使用者正確的提示。

問題的根源：例外沒有被處理

在每個路由裡面寫 try/except IntegrityError 當然可行，但這会产生嚴重的重複——每個寫入路由都要複製一段相同的錯誤處理邏輯。只要漏改一個地方，又會回到 500。

更好的方式是在一個地方統一攔截：FastAPI 的集中式例外處理器（centralized exception handler）。

總結

資料庫約束違反 → SQLAlchemy 拋出 IntegrityError → FastAPI 預設回應 500。我們要做的，是在一個統一的位置把這個例外轉換成對呼叫端有意義的狀態碼。
