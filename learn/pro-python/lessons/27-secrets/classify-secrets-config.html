分辨秘密與一般設定

先判斷洩漏的代價，再決定儲存方式

目標

面對一個設定值時，不要靠「看起來敏不敏感」猜測。使用一條明確規則：它洩漏後，是否必須輪換憑證？

一條實用的判斷線

如果資料外洩會迫使團隊更換金鑰、密碼或連線憑證，它就是秘密（secret）。秘密的價值不在於字串長得像亂碼，而在於它能讓持有者通過身分驗證或取得權限。

值分類洩漏後的處理
JWT secret秘密輪換簽章金鑰，檢查既有 token
含密碼的 DATABASE_URL秘密更換資料庫密碼與連線設定
Postgres 管理者密碼秘密立即輪換並檢查存取紀錄
DEBUG=true/false一般設定修正部署設定，不需輪換憑證
LOG_LEVEL=INFO一般設定調整輸出等級，不需更換金鑰

秘密與一般設定不是同一種風險

DATABASE_URL=postgresql://app:password@db.internal/tasks
JWT_SECRET=very-long-random-value
DEBUG=true
LOG_LEVEL=DEBUG

前三個值都放在設定來源裡，不代表它們的安全性質相同。資料庫 URL 和 JWT secret 可以直接成為攻擊入口，因此需要秘密管理。DEBUG 和 LOG_LEVEL 是行為設定，公開它們通常不會讓攻擊者取得憑證。

DEBUG 不是秘密，但 production 仍要關閉

DEBUG=true 不需要像密碼一樣輪換，所以它不是秘密。不過 production 的除錯模式可能在錯誤回應中展示完整 traceback、檔案路徑、請求資料或其他敏感資訊。它的風險是資訊洩漏，不是「有人拿它登入系統」。

# 安全預設
DEBUG=false
LOG_LEVEL=INFO

把安全的預設值寫進部署設定，開發時再明確開啟詳細輸出。不要因為 DEBUG 不是秘密，就把它在正式環境長期設為 true。

遇到疑似外洩時的反應

  1. 先把暴露來源隔離，例如撤回公開提交或限制權限。
  2. 對真正的秘密立即輪換，讓舊值失效。
  3. 檢查存取紀錄與使用中的部署設定。
  4. 修正秘密注入流程，再部署新值。

這個流程也說明了分類規則為什麼重要：只有秘密需要憑證輪換，但任何錯誤設定都可能需要修正。
