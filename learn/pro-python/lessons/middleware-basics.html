Middleware 基礎與執行順序

請求進來、回應出去之間，程式碼怎麼攔截每一條路徑

Middleware 是什麼？

Middleware（中介層）是一段在「每個請求進來之前」和「每個回應出去之前」都會執行的程式碼。它像一個檢查站，站進去之前能改請求、站出來之後能改回應。

在 FastAPI 裡，你不用自己刻一個框架，只要用 @app.middleware("http") 裝飾一個 async 函式，FastAPI 就會在每個 HTTP 請求通過時呼叫它。

最簡 Middleware 骨架

@app.middleware("http")
async def log_requests(request: Request, call_next):
    # 這裡是 pre-route 工作（端點執行前）
    response = await call_next(request)
    # 這裡是 post-route 工作（端點執行後）
    return response

call_next 是 middleware 的核心：呼叫它會把請求往下傳給路由端點（或下一個 middleware），等端點跑完再回傳 response。這讓你在「端點之前」和「端點之後」都能插入自訂邏輯。

Pre-route vs Post-route

位置可以做什麼
call_next(request) 之前記錄請求開始時間、驗證 token、修改請求標頭
call_next(request) 之後記錄回應時間、加上自訂標頭、修改回應內容

多個 Middleware 的執行順序

一個 FastAPI app 可以註冊多個 middleware，它們會像俄羅斯娃娃一樣層層包覆。重點是：註冊順序和執行順序相反。

app.add_middleware(LastMiddleware)
app.add_middleware(MiddleMiddleware)
app.add_middleware(FirstMiddleware)

請求進來時的執行順序（由外到內）：

  1. LastMiddleware（最先接觸請求）
  2. MiddleMiddleware
  3. FirstMiddleware
  4. 路由端點（route handler）

回應出去時的順序則反過來（由內到外）：

  1. 路由端點回傳
  2. FirstMiddleware
  3. MiddleMiddleware
  4. LastMiddleware（最後接觸回應）

為什麼順序重要？

如果 middleware A 負責「驗證使用者身分」、middleware B 負責「記錄請求時間」，你會希望 B 在 A 的外層，這樣即使驗證失敗，時間還是會被記錄。搞錯順序會讓某些請求跳過驗證，或記錄不到完整資訊。
