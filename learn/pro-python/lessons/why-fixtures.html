為什麼測試需要隔離的資料庫？

學習目標

理解測試共用資料庫時產生的狀態污染問題，以及為什麼每個測試需要獨立、隔離的資料庫實例。

測試危索共用資料庫的風險

你的 API 測試正在跑，一切看起來沒問題。但你發現只要調換兩個測試的執行順序，其中一個就會失敗。更詭異的是，单独跑每個測試都通過，合在一起就跑不這種「測試危索（test interference）」的罪魁禍首就是共用狀態（shared state）——多個測試寫入同一張表、讀取同一個資料庫。

具體來想一個情境：測試 A 建立了一個專案，測試 B 查詢所有專案並斷言數量。如果測試 A 先跑，測試 B 會看到這筆資料，數量斷言就錯了。資料庫是測試之間溝通的暗通道，你以為在測 B，其實在測 A+B 的組合。

清理不是好辦法

最直覺的解法是「每個測試跑完就刪除資料」。聽起來可行，但實務上問題很多：

  • 忘記清理：一個測試失敗、拋出例外，清理程式碼沒執行，汙染後續測試。
  • 清理本身也是測試：你還得測試「清理有沒有成功」，巢狀驗證沒完沒了。
  • 平行測試衝突：如果兩個測試同時跑，一個在刪資料、一個在讀，race condition 就出現了。

清理是把「維持公共空間整潔」的責任塞給每個測試。隔離則是「每個測試有自己的房間」，從根本上消除干擾。

隔離資料庫的原則

每個測試擁有獨立的資料庫實例，跑完就拋棄。因為互不共用，所以：

  • 執行順序不相關：測試 A 怎麼跑都不會影響測試 B。
  • 失敗不擴散：一個測試弄髒自己的資料庫，其他測試完全不受影響。
  • 可以平行執行：每個測試跑在自己的資料庫裡，不需要互相等待。
