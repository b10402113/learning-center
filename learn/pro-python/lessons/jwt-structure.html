Node 22 — Step 2/3 · JWT tokens

JWT 的結構：header、payload、signature

學習目標

能拆解 JWT 的三個部分，區分「編碼」與「加密」，並解釋常見 claims 的用途。

把 JWT 拆開來看

一個 JWT 長得像這樣：

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJhbGljZSIsImV4cCI6MTczNjAwMDAwMH0.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

看起來是一串亂碼，但它其實由三個 base64 編碼（Base64URL）的部分組成，用句點 . 分隔：

部分內容用途
Header（標頭）演算法與 token 類型告訴伺服器「用哪種演算法驗證簽章」
Payload（載荷）Claims（關於使用者的聲明）攜帶使用者身份與過期時間等資訊
Signature（簽章）Header + Payload 的雜湊防止內容被竄改

Header：用哪種演算法？

Header 通常只有兩個欄位：alg（演算法）和 typ（類型，固定是 "JWT"）。例如：

{
  "alg": "HS256",
  "typ": "JWT"
}

這串 JSON 經過 Base64URL 編碼後，就變成 JWT 第一段 eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9。任何人都可以解碼它——Header 不是秘密，它只是告訴伺服器「驗證我請用 HMAC SHA-256」。

Payload：攜帶聲明（Claims）

Payload 是 JWT 真正放資料的地方。這裡面的 JSON 物件稱為 Claims（聲明）——就是「關於這個 token 的一件事」。

常見的標準 claims：

Claim全稱用途
subSubjecttoken 的主人是誰（通常是使用者名稱或 ID）
expExpirationtoken 的過期時間（Unix timestamp）
iatIssued Attoken 何時發行
issIssuer誰發行了這個 token

一個實際的 payload 可能長這樣：

{
  "sub": "alice",
  "exp": 1736000000
}

跟 Header 一樣，Payload 也是 Base64URL 編碼，不是加密。任何人拿到 token 都能解碼看到 sub 和 exp。所以絕對不要在 Payload 裡放密碼或敏感資訊——它只是「可閱讀但不可竄改」。

Signature：防偽簽章

Signature 是 JWT 安全的核心。它的產生方式：

  1. 把編碼後的 Header 和 Payload 用句點連起來：header.payload
  2. 用 Header 指定的演算法（例如 HS256）加上伺服器密鑰（secret key）去算雜湊
  3. 把雜湊結果 Base64URL 編碼，變成第三段

當伺服器收到 token 時，它會用同樣的密鑰和演算法重新算一次雜湊，跟 token 裡的 Signature 比對。如果吻合，代表：

  • Header 和 Payload 沒有被竄改（一改，雜湊就變了）
  • token 一定是持有密鑰的人發出的（沒有密鑰算不出對的雜湊）
編碼（Encoding）≠ 加密（Encryption）。Base64 是為了傳輸方便，不是為了保密。JWT 的保全靠的是 Signature，不是靠隱藏內容。
