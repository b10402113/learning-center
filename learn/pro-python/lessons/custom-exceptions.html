Custom Exceptions

Node 34 · Step 3 / 4 · pro-python

Learning goal

Create domain-specific exception classes by subclassing Exception for clearer error handling.

Why custom exceptions?

Built-in exceptions like ValueError tell you what went wrong in general terms. But in a real application, you often need to distinguish between different kinds of failures. A "user not found" error and a "database connection lost" error are both exceptions, but you handle them very differently.

Custom exceptions let you:

  • Distinguish domain errors from generic Python errors
  • Attach extra context (the user ID, the query that failed)
  • Handle specific failures at the right layer

Defining a custom exception

Subclass Exception — or a more specific built-in if it fits. The body is usually just pass. The class name is the documentation.

class ProjectNotFoundError(Exception):
    """Raised when a project_id does not match any row in the database."""

class DuplicateProjectError(Exception):
    """Raised when a project with the same slug already exists."""
Naming matters. End your exception class names with Error or Exception. ProjectNotFoundError reads clearly in tracebacks; ProjectNotFound is ambiguous.

Adding context

You can accept extra arguments in __init__ and store them as attributes. This lets the handler access the problematic value without parsing a string.

class ProjectNotFoundError(Exception):
    def __init__(self, project_id: int):
        self.project_id = project_id
        super().__init__(f"Project {project_id} not found")

# Later, in a handler:
except ProjectNotFoundError as e:
    logger.warning("Lookup failed for project_id=%d", e.project_id)
    raise HTTPException(status_code=404, detail=str(e)) from e

Exception hierarchies

You can create a base exception for your whole application, then subclass it for specific areas. This lets callers catch at whatever granularity they need.

class AppError(Exception):
    """Base for all application-specific errors."""

class DatabaseError(AppError):
    """Base for database-related errors."""

class ProjectNotFoundError(DatabaseError):
    pass

class DuplicateProjectError(DatabaseError):
    pass

Now a handler can catch DatabaseError to handle all database failures, or ProjectNotFoundError for just that case.

When not to create custom exceptions

If a built-in exception already says what you need, use it. Don't create MyValueError when ValueError works fine. Custom exceptions shine when you need to distinguish failures that built-ins can't tell apart.
