遷移修訂的運作方式

理解遷移檔的結構：upgrade() 如何把資料庫往前推進、downgrade() 如何回溯，以及為什麼每次遷移都是一個獨立的 Python 檔案。

遷移檔是什麼？

當你修改 SQLModel 定義（例如新增一個欄位、修改索引、甚至刪除表格）時，資料庫本身不會自動知道這些變更。你需要一個「遷移檔」（migration revision）來描述如何從舊的資料庫狀態走到新的狀態。

每個遷移檔都是一個獨立的 Python 檔案，放在 alembic/versions/ 目錄下。它包含一個唯一的 revision ID（像是 a1b2c3d4e5f6），以及兩個核心函式：upgrade() 和 downgrade()。

upgrade()：往前走

upgrade() 描述的是如何從上一個版本走到這個版本。例如你新增了一個 email 欄位，upgrade() 裡面就會有 op.add_column() 相對應的 SQL 操作。

當你執行 alembic upgrade head 時，Alembic 會按照遷移檔的順序，逐一執行每個還沒套用過的 upgrade()。head 代表最新的那個版本。

downgrade()：走回去

downgrade() 描述的是如何從這個版本退回到上一個版本。它是 upgrade() 的逆向操作。如果 upgrade() 新增了欄位，downgrade() 就要刪除那個欄位。

為什麼需要回溯？因為在生產環境中，如果發現新的遷移檔有問題（例如資料遺失、效能下降），你需要能夠安全地回到上一個穩定的版本，而不是只能砍掉重練。

遷移鏈

遷移檔不是獨立的，它們形成一條鏈。每個遷移檔都會記錄它的 down_revision（上一個版本的 revision ID）。這讓 Alembic 知道遷移的順序，也能從任何一個版本開始往前或往後走。

revision: a1b2c3d4e5f6
down_revision: 9f8e7d6c5b4a  # 指向上一份遷移檔

當你想回溯到特定版本時，可以執行 alembic downgrade <revision_id>，Alembic 會從目前位置開始，逐一執行 downgrade() 直到到達目標版本。

autogenerate 的運作

手動寫遷移檔很花時間，所以 Alembic 提供了 --autogenerate 選項。它會比對 SQLModel 的 metadata 與資料庫現狀，自動產生對應的 upgrade() 和 downgrade() 程式碼。

但 autogenerate 不是萬能的：它能偵測到欄位的新增、刪除、型別變更，但對於重新命名、複雜的資料轉換、或自訂的 SQL 操作，通常還是需要手動調整產生的遷移檔。

重點整理

  • 每個遷移檔是一個獨立 Python 檔案，包含 upgrade() 和 downgrade()
  • upgrade() 往前走，downgrade() 回溯到上一個版本
  • 遷移檔透過 down_revision 形成一條鏈，讓 Alembic 知道順序
  • --autogenerate 可以自動比對模型與資料庫，產生遷移檔
  • 在生產環境中，downgrade() 是你出錯時的安全網
