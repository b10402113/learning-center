Delete endpoints (soft vs hard)

Node 13 · Step 4 of 4

Learning goal

Implement a DELETE endpoint that supports both hard deletion (permanently removing a record) and soft deletion (hiding it behind a flag), and understand when to use each in production.

The two ways to delete

When a user clicks "delete" on a project, what should happen? There are two answers, and they lead to very different implementations.

TypeWhat happensReversible?
Hard deleteRow is permanently removed from the databaseNo
Soft deleteRow stays, but gets flagged as archivedYes

Hard deletion is simple — session.delete(obj) followed by session.commit(). The row is gone forever. If someone accidentally deletes a project, the only way to recover it is from a backup.

Soft deletion adds an archived boolean column to the model. "Deleting" a project sets archived = True. The row remains in the database, but every query filters out archived records by default. The project disappears from the API and the frontend, but it's still there for audit, analytics, or recovery.

Hard delete implementation

The hard delete endpoint is the simplest write endpoint you'll ever write:

@app.delete("/projects/{project_id}", status_code=204)
def delete_project(
    project_id: int,
    session: Session = Depends(session_dep),
):
    project = session.get(Project, project_id)
    if not project:
        raise HTTPException(status_code=404, detail="Project not found")

    session.delete(project)
    session.commit()

Notice the status_code=204. A successful delete returns 204 No Content — the resource is gone, so there's nothing to return. The client doesn't need a copy of the deleted object; they just need confirmation it's no longer there.

session.delete(project) stages the object for deletion. session.commit() executes the DELETE statement. After that, the row is physically removed from the table.

Soft delete implementation

Soft delete requires an extra column on the model:

class Project(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    name: str
    description: str = ""
    version: str = "0.1.0"
    slug: str
    archived: bool = False

The endpoint sets the flag instead of removing the row:

@app.delete("/projects/{project_id}", status_code=204)
def archive_project(
    project_id: int,
    session: Session = Depends(session_dep),
):
    project = session.get(Project, project_id)
    if not project:
        raise HTTPException(status_code=404, detail="Project not found")

    project.archived = True
    session.add(project)
    session.commit()

It looks almost identical to an update endpoint — because that's what it is. The only difference is which field you're setting.

Filtering out archived records

Setting the flag is only half the solution. Every query in your application must exclude archived records, or they'll keep showing up in the API:

@app.get("/projects", response_model=list[ProjectRead])
def list_projects(session: Session = Depends(session_dep)):
    statement = select(Project).where(Project.archived == False)
    return session.exec(statement).all()

Project.archived == False (or ~Project.archived for the inverse) is the filter that hides soft-deleted records. It belongs in every SELECT, every GET /projects/{id} lookup, and every join query.

This is the hidden cost of soft deletion: you add a column, and then you add a WHERE clause to every query. Miss one, and archived records leak through.

When to use each

Use hard deletion when:

  • The data has no regulatory or audit value
  • Storage costs matter and records accumulate fast
  • The user explicitly expects permanent removal (e.g., GDPR "right to be forgotten")

Use soft deletion when:

  • You need an audit trail for compliance
  • Users expect an "undo" option
  • Other records reference this one via foreign keys
  • You want to analyze deletion patterns later

In practice, most production systems default to soft deletion. It's safer — you can always hard-delete later in a cleanup job, but you can't recover a hard-deleted row without a backup.
