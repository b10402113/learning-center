<LearningGoal>
能拆解 JWT 的三個部分，區分「編碼」與「加密」，並解釋常見 claims 的用途。
</LearningGoal>

## Lesson

一個 JWT 看起來像一串亂碼：<code>eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJhbGljZSIsImV4cCI6MTczNjAwMDAwMH0.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c</code>。但它其實由三個 base64 編碼（Base64URL）的部分組成，用句點 <code>.</code> 分隔。

Header 通常只有兩個欄位：<code>alg</code>（演算法）和 <code>typ</code>（類型，固定是 <code>"JWT"</code>）。例如 <code>{"alg":"HS256","typ":"JWT"}</code>。任何人都可以解碼它——Header 不是秘密，它只是告訴伺服器「驗證我請用 HMAC SHA-256」。

Payload 是 JWT 真正放資料的地方。這裡面的 JSON 物件稱為 <strong>Claims（聲明）</strong>——就是「關於這個 token 的一件事」。常見的標準 claims 包括 <code>sub</code>（Subject，token 的主人）、<code>exp</code>（Expiration，過期時間）、<code>iat</code>（Issued At，發行時間）、<code>iss</code>（Issuer，發行者）。

跟 Header 一樣，Payload 也是 Base64URL 編碼，不是加密。任何人拿到 token 都能解碼看到 <code>sub</code> 和 <code>exp</code>。所以<strong>絕對不要在 Payload 裡放密碼或敏感資訊</strong>——它只是「可閱讀但不可竄改」。

Signature 是 JWT 安全的核心。它的產生方式：把編碼後的 Header 和 Payload 用句點連起來，用 Header 指定的演算法（例如 HS256）加上伺服器密鑰（secret key）去算雜湊，再把雜湊結果 Base64URL 編碼。當伺服器收到 token 時，它會用同樣的密鑰和演算法重新算一次雜湊，跟 token 裡的 Signature 比對。如果吻合，代表 Header 和 Payload 沒有被竄改，且 token 一定是持有密鑰的人發出的。

編碼（Encoding）≠ 加密（Encryption）。Base64 是為了傳輸方便，不是為了保密。JWT 的保全靠的是 Signature，不是靠隱藏內容。
