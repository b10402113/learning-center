<LearningGoal>
能說出 HTTP 無狀態特性帶來的身份識別問題，以及 JWT 如何讓伺服器在不儲存 session 的情況下驗證使用者。
</LearningGoal>

## Lesson

HTTP 是無狀態的——伺服器處理完一個請求，就忘記你是誰了。這在單純的頁面瀏覽無妨，但一旦你的 API 需要知道「這個請求是誰發的就執行，不是誰發的就拒絕」，問題就來了：你得在每個請求裡證明自己的身份。

傳統的做法是 Session：登入後伺服器在記憶體裡記住你的身份，發給你一個 session ID，之後你每次帶這個 ID 來，伺服器就去記憶體裡查。這在單機伺服器上行得通，但當你的服務開始水平擴展——三台、五台伺服器背後一起扛流量——第一台伺服器認識你，第二台可不認識。要嘛你得把 session 存在所有伺服器都能查的地方（例如 Redis），要嘛你得想另一招。

JWT 換了一招：與其讓伺服器記住你是誰，不如直接給你一張「有防偽簽章的通行證」。你每次請求都帶著這張通行證，伺服器只要檢查簽章是不是真的，就知道你是誰——完全不需要查資料庫。

這就是 JWT 最核心的三個特性：

| 特性 | 意義 | 為什麼重要 |
| --- | --- | --- |
| 便宜驗證（Cheap to verify） | 伺服器只需檢查簽章，不用查資料庫 | 即使流量暴增，驗證成本幾乎不變 |
| 難以偽造（Hard to forge） | 沒有密鑰就無法產生有效簽章 | 攻擊者無法假造別人的身份 |
| 自我攜帶（Self-contained） | token 裡已經包含使用者資訊 | 伺服器不需要儲存 session 狀態 |

JWT 不是「加密」你的身份，而是「簽名」你的身份——就像在駕照上蓋鋼印，不是把駕照裝進保險箱。

JWT 特別適合「無狀態 API」場景：你的 FastAPI 服務不需要跟其他伺服器共享 session，每個請求自帶 token，水平擴展變得很簡單——加一台新伺服器，它馬上就能驗證 token，因為驗證只需要密鑰，不需要查共享的 session 儲存。
