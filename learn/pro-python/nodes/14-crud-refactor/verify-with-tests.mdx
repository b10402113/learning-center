<LearningGoal>
執行既有測試來確認重構沒有破壞任何 API 行為，理解測試作為安全網的角色。
</LearningGoal>

## Lesson

重構完之後，很多開發者的直覺是「繼續寫下一步」。但真正專業的作法是先停下來，跑一次測試。這一步看起來平淡，卻是整個重構流程裡最關鍵的安全確認。

**測試是重構的安全網**

想像你在走鋼索。底下有一張網，就算你失足，網也會接住你。在軟體開發裡，自動化測試就是那張網。當你要重構——搬動程式碼、重組結構——測試會在你「失足」的時候立刻告訴你：「嘿，你弄壞東西了。」

沒有測試的重構就像走鋼索不掛網：也許你技術很好，但只要一次疏忽，程式就會壞掉，而且你可能要等到使用者抱怨才發現。

**重構的黃金流程**

把資料庫操作抽到 `crud.py` 之後，下一步不是繼續寫新功能，而是跑測試：

```bash
uv run pytest
```

如果所有測試都通過，恭喜——你成功地把程式碼搬動了，而且沒有弄壞任何東西。如果測試失敗，代表你的重構改變了 API 行為，必須回頭檢查改了什麼。

這裡的重點是：**測試檔本身完全不改**。測試是合約，是判斷重構是否成功的標準。如果你為了通過測試而改測試，等於是在改合約的條款來配合你，那測試就失去意義了。

**測試通過代表什麼？**

測試通過代表「API 行為跟重構前完全一樣」。具體來說：路由回傳的狀態碼沒變、回傳的 JSON 結構沒變、錯誤處理的方式沒變、資料庫裡的資料沒變。

這正是我們想要的。重構只改結構，不改行為。測試通過就是最有力的證明。

**測試先行的價值**

這個流程背後有一個更深的觀念：**先寫測試，再寫實作**（test-first development）。當你先寫好測試，你就定義了「什麼是正確的行為」。之後不管怎麼重構，只要測試都通過，你就知道程式還是正確的。

這讓你敢做大規模的程式碼更動。沒有測試，開發者通常不敢動舊程式碼，能加新功能就加，能不動就不動，最後整個程式碼庫變得越來越僵硬。有測試，你隨時可以安全地整理程式碼。
