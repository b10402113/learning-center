# GitHub Actions CI

## Learning goal
Set up CI to run Ruff, MyPy, pytest, and coverage on every push

## Steps

1. [[learn/pro-python/nodes/28-github-actions/workflow-foundations|GitHub Actions workflow foundations]] — Explain how a repository event becomes a repeatable CI job.
2. [[learn/pro-python/nodes/28-github-actions/runner-environment|Reproducible runner environments]] — Configure the runner and install the project reproducibly. (after step 1)
3. [[learn/pro-python/nodes/28-github-actions/quality-gates|CI quality gates]] — Run Ruff, MyPy, pytest, and coverage as automated gates. (after step 2)
4. [[learn/pro-python/nodes/28-github-actions/secrets-and-failures|Secrets, health checks, and failure diagnosis]] — Keep secrets safe and classify failures quickly. (after step 3)

## Lesson

Continuous integration makes the repository prove its quality on every push instead of relying on a developer to remember local commands. A workflow responds to a repository event, creates a clean runner, installs the pinned project environment, and executes the same quality commands contributors use locally. The result is a repeatable signal: a change either passes the gates or shows exactly which gate failed.

The four steps build that signal from the outside in. First understand workflow orchestration, then make the runner reproducible, then compose the quality gates, and finally handle secrets and service health without confusing an environment failure with a code failure.
