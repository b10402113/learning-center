# Structured logging and middleware

## Learning goal

Add request timing middleware, configure structured JSON logging

## Steps

1. [[learn/pro-python/nodes/20-structured-logging/middleware-basics|Middleware basics and execution order]] — Understand what FastAPI middleware is, how `app.middleware` registers it, and why execution order matters
2. [[learn/pro-python/nodes/20-structured-logging/request-timing-middleware|Request timing middleware]] — Build a middleware that times requests and emits structured log lines (after step 1)
3. [[learn/pro-python/nodes/20-structured-logging/structured-logging-config|Programmatic structured logging configuration]] — Replace `basicConfig` with structured, timestamped log output
4. [[learn/pro-python/nodes/20-structured-logging/env-driven-config|Environment-controlled log levels]] — Control log level via environment variables and `.env` files (after step 3)

## Lesson

Production APIs need more than print statements — they need structured, searchable logs and visibility into every request that passes through. This node teaches two complementary techniques that together give you production-grade observability.

Middleware is the FastAPI mechanism that lets you run code before and after every request. The first step explains what middleware is, how `app.middleware` registers it, and the counterintuitive execution order when multiple middlewares are stacked. The second step puts that knowledge to work by building a timing middleware that records how long each request takes and emits a structured log line — giving you a clear picture of API performance and a trail you can search when things go wrong.

Structured logging replaces the one-line `basicConfig` setup with a programmatic configuration that outputs clean, parseable log lines with timestamps, levels, and module names. The third step walks through `configure_logging` and shows why a structured format matters once logs leave the terminal and enter a file or log aggregator. The fourth step ties configuration to the environment: a `.env` file keeps DEBUG output local while production stays at INFO, with no code changes between environments.

By the end of the node, your API will emit structured, timestamped log lines for every request and its duration, and you'll control verbosity through environment variables — the same patterns used in real Python services.
