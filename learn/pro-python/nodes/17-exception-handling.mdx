# Centralized exception handling

## Learning goal

Catch IntegrityError globally, return 409 Conflict

## Steps

1. [[learn/pro-python/nodes/17-exception-handling/integrity-error-problem|當唯一約束被違反時會發生什麼？]] — 理解 SQLAlchemy 的 IntegrityError 如何產生，以及 FastAPI 預設如何回應
2. [[learn/pro-python/nodes/17-exception-handling/centralized-handler|用集中式例外處理器攔截 IntegrityError]] — 用 @app.exception_handler 建立全域處理器（after step 1）
3. [[learn/pro-python/nodes/17-exception-handling/http-409-semantics|為什麼 409 Conflict 是對的狀態碼？]] — 分辨 409 與 400、404 的差異（after step 1）
4. [[learn/pro-python/nodes/17-exception-handling/testing-conflict|測試重複專案回傳 409 Conflict]] — 寫測試驗證重複 POST 回傳 409（after steps 2–3）

## Lesson

這一節要解決一個具體的問題：當使用者嘗試建立一個名稱已經存在的專案時，資料庫會拒絕這筆寫入，但 FastAPI 預設會把這個錯誤變成 500 Internal Server Error。對 API 的呼叫端來說，500 代表「伺服器內部出錯了」，而不是「這個名稱已經用過了」——兩者需要完全不同的處理方式。

我們會在這裡走完整個流程：先看到問題（IntegrityError 如何產生、為什麼預設是 500），再建立一個集中式例外處理器，把 IntegrityError 轉換成 409 Conflict。接著會討論爲什麼 409 是對的狀態碼，以及它跟 400、404 的差異。最後，我們會寫一個測試，確認重複的 POST 請求確實回傳 409，而不是 500。

走完這四步之後，你的 API 就能用正確的語意回應資料衝突，而不是用一個籠統的伺服器錯誤把問題藏起來。
