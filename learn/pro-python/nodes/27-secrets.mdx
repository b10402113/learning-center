# Managing secrets and .env

## Learning goal

能在本機用 `.env` 提供設定、用「洩漏後是否必須輪換憑證」分辨秘密與一般設定，並為 production 選擇平台原生的秘密儲存方式。

## Steps

1. [[learn/pro-python/nodes/27-secrets/manage-env-development|用 .env 管理本機開發設定]] — 把專案設定放進 `.env`，並知道它為什麼不進版控
2. [[learn/pro-python/nodes/27-secrets/classify-secrets-config|分辨秘密與一般設定]] — 用「洩漏後是否必須輪換憑證」這條線區分兩者（after step 1）
3. [[learn/pro-python/nodes/27-secrets/choose-production-secret-storage|選擇 production 的秘密儲存方式]] — 比較平台環境變數、Kubernetes Secrets 與 Vault（after steps 1–2）

## Lesson

應用程式上線前一定會遇到同一個問題：資料庫密碼、JWT 簽章金鑰這些東西要放哪裡？把它們寫死在程式碼裡會進版控，貼進 shell 又會污染你的環境。`.env` 檔案解決的是**本機開發**的這個痛點——讓每個專案自帶一組設定，切換專案不用重新 export。

但 `.env` 只是開發便利工具，不是秘密儲存庫。要判斷什麼東西不能隨便放，你需要一條可操作的線：**這個值洩漏之後，你是否必須更換憑證或輪換金鑰？** 是的話它就是秘密，需要更嚴格的儲存與存取控制；不是的話它只是一般設定，例如 log level 或除錯開關。除錯模式本身不是秘密，但它在 production 應該預設關閉，因為開啟會把詳細 traceback 和敏感資料寫進回應或日誌。

到了 production，`.env` 檔案便不再合適：它通常以明文存在磁碟、容易被誤加入映像檔，也沒有稽核或權限控制。雲端平台的原生環境變數、Kubernetes Secrets、HashiCorp Vault 這三種方案，分別對應「託管」、「與部署環境整合」、「細粒度存取控制」的需求。走完這三步，你就能替每個值選對收納方式，而不是把所有東西都塞進同一個檔案。
