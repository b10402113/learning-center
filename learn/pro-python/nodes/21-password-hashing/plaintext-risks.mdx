<LearningGoal>
理解明文密碼儲存的風險：資料庫外洩、SQL 注入、備份外流與設定錯誤都可能一次曝光所有使用者的原始密碼，且因密碼重複使用會引發連鎖危機。
</LearningGoal>

## Lesson

想像一個情境：你的 API 資料庫因為雲端儲存桶設定失誤，被搜索引擎索引到了。如果資料庫裡存的是明文密碼，攻擊者不需要任何技術門檻——直接打開就能看到幾千使用者的帳號和密碼。這不是假設，而是真實發生過幾十次的外洩事件。

儲存明文密碼的風險之所以致命，是因為它把「系統漏洞」直接變成「使用者資產損失」。常見的攻擊路徑有四種。

第一種是**資料庫被入侵（Database Compromise）**。攻擊者透過 SQL 注入、未修補的資料庫漏洞或內部威脅直接拿到資料庫內容。如果密碼是明文的，使用者當下就失去帳戶控制權，攻擊者可以立刻登入。

第二種是**SQL 注入（SQL Injection）**。如果你的程式碼沒有使用參數化查詢，攻擊者可以在輸入欄位塞入惡意 SQL，把整個使用者資料表拉走。明文密碼在這種攻擊下毫無防備能力。

第三種是**備份外流（Leaked Backups）**。很多團隊會定期備份資料庫，備份檔案可能存放在物件儲存、外接硬碟、版本控制倉庫或協力廠商服務。備份的存取權限通常比正式環境更鬆散，明文密碼在備份鍊裡面會不斷複製、擴散。

第四種是**雲端設定錯誤（Cloud Misconfiguration）**。S3 bucket 設為公開、資料庫連接埠對外開放、環境變數裡的金鑰暴露在 log 裡——這些都是常見的操作失誤。明文密碼一旦在這種場景曝光，規模可以從幾千到幾億筆都有。

但真正讓明文密碼變成災難的，不是單一外洩事件，而是**密碼重複使用（Password Reuse）**。多數人會在不同網站使用相同或類似的密碼。當一個小論壇的明文資料庫外洩，攻擊者拿這批帳號密碼去主流服務（Gmail、GitHub、銀行）嘗試登入，這個攻擊手法稱為**憑證填充（Credential Stuffing）**。一次小外洩可以引爆連鎖性的帳戶接管（Account Takeover）。

明文密碼的風險不是理論問題，而是工程底線。作為開發者，你的責任是假設資料庫「總有一天會被入侵」，並在那一天到來之前，確保即使資料表被整包偷走，攻擊者也無法拿到可以用來登入的密碼。這就是密碼雜湊存在的理由。
