<LearningGoal>
理解依賴注入解決了什麼問題：手動管理資料庫 session 的生命週期容易遺漏 commit 或 close，導致連線洩漏與資料不一致。
</LearningGoal>

## Lesson

現在你已經會寫 CRUD 端點了，但每次都要自己手動拿到 session、手動 commit、手動 close。看起來還行，但只要一個端點忘了 close，資料庫連線就會洩漏；忘了 commit，資料就沒寫進去。當端點變多，這些生命週期的細節會變成隱藏的炸彈。

依賴注入（Dependency Injection，DI）把「資源怎麼來、怎麼結束」這件事從端點裡面抽出來，交給框架管理。FastAPI 的 DI 系統讓你在端點函式上宣告「我需要一個資料庫 session」，框架就會在請求進來時自動建立 session、在請求結束時自動清理，你不需要自己寫 try/finally。

先看看沒有 DI 的時候，一個典型的端點長什麼樣子。你拿到 session 之後，必須確保不管發生什麼事，session 都要被關掉。如果中間出了例外，你還得決定要不要 rollback。這些邏輯跟真正的業務無關，但每一行都在分散注意力。

```python
@app.get("/projects/{project_id}")
def get_project(project_id: int):
    session = Session(engine)
    try:
        project = session.get(Project, project_id)
        if project is None:
            raise HTTPException(status_code=404)
        return project
    finally:
        session.close()
```

現在把 session 的建立和關閉交給 FastAPI。你只需要宣告「我要一個 session」，框架會幫你處理剩下的。端點裡面只剩下真正的業務邏輯：查詢、判斷、回傳。

```python
@app.get("/projects/{project_id}")
def get_project(project: ProjectDep):
    return project
```

DI 不只是少寫幾行 code。它改變了端點的責任邊界：端點只負責「拿到資源之後要做什麼」，資源的生命週期交給框架。這樣一來，測試的時候你可以注入假資源，部署的時候你可以換成連線池，端點本身都不用改。

把這背後的設計想法講得更清楚一點：軟體設計裡有一個原則叫「分離關注點（Separation of Concerns）」——每個模組應該只負責一件事。端點的責任是處理 HTTP 請求、執行業務邏輯、回傳結果。session 的建立、提交、關閉是「資源管理」，是另外一件事。當你把資源管理從端點搬走，端點就變得更專注、更容易測試、更容易重用。

DI 還帶來一個隱藏的好處：一致的錯誤處理。當每個端點自己管理 session，有人會忘記 rollback，有人會忘記 close，有人會在 commit 之前就把 session 關了。這些 bug 很微小，但在生產環境會慢慢侵蝕穩定性。交給框架之後，清理邏輯只有一份，要改也是改一個地方。

最後來想一個反面場景：假設你的 API 有 30 個端點，每個端點都需要 session。如果哪天你要把資料庫從 Postgres 換成 MySQL，或者要把 session 換成連線池，在手動管理的世界裡你要改 30 個端點。在 DI 的世界裡，你只需要改 `get_session` 的實作，30 個端點全部自動更新。這就是依賴注入「反轉控制（Inversion of Control）」的價值——資源怎麼來，端點不決定，框架決定。
