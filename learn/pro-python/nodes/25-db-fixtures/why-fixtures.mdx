<LearningGoal>
理解測試共用資料庫時產生的狀態污染問題，以及為什麼每個測試需要獨立、隔離的資料庫實例。
</LearningGoal>

## Lesson

你的 API 測試正在跑，一切看起來沒問題。但你發現只要調換兩個測試的執行順序，其中一個就會失敗。更詭異的是，單獨跑每個測試都通過，合在一起就跑不過。這種「測試危索（test interference）」的罪魁禍首就是**共用狀態（shared state）**——多個測試寫入同一張表、讀取同一個資料庫。

具體來想一個情境：測試 A 建立了一個專案，測試 B 查詢所有專案並斷言數量。如果測試 A 先跑，測試 B 會看到這筆資料，數量斷言就錯了。資料庫是測試之間溝通的暗通道，你以為在測 B，其實在測 A+B 的組合。

最直覺的解法是「每個測試跑完就刪除資料」。聽起來可行，但實務上問題很多：忘記清理——一個測試失敗、拋出例外，清理程式碼沒執行，汙染後續測試；清理本身也是測試——你還得測試「清理有沒有成功」，巢狀驗證沒完沒了；平行測試衝突——如果兩個測試同時跑，一個在刪資料、一個在讀，race condition 就出現了。清理是把「維持公共空間整潔」的責任塞給每個測試。隔離則是「每個測試有自己的房間」，從根本上消除干擾。

每個測試擁有獨立的資料庫實例，跑完就拋棄。因為互不共用，所以執行順序不會影響結果，一個測試失敗不會汙染其他測試，測試也可以安全地平行執行。pytest 的 fixture 系統正是為了這種「每個測試一套環境」的需求設計的。下一課會教你怎麼用 in-memory SQLite 搭配 fixture 在幾毫秒內建立一個全新的資料庫給每個測試用。
