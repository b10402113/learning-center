<LearningGoal>
能理解端點行為改變時，測試必須同步更新，並動手修改查詢參數與斷言。
</LearningGoal>

## Lesson

API 在開發過程中會不斷演化：欄位改名、查詢參數調整、回應結構變動。測試是端點行為的合約——端點改了，測試必須跟著改，否則要麼測試失敗（false negative），要麼測試通過但沒測到對的東西（false positive）。

場景：原本端點用查詢參數 `name` 來過濾專案：

```
GET /projects?name=API v2
```

現在改為用 `slug` 過濾，因為 slug 對 URL 更友好：

```
GET /projects?slug=api-v2
```

這看起來是小改動，但測試裡的查詢參數和斷言全部要跟著變。

舊測試：

```python
def test_list_projects_by_name():
    response = client.get("/projects?name=API v2")
    assert response.status_code == 200
    assert len(response.json()) == 1
    assert response.json()[0]["name"] == "API v2"
```

新測試：

```python
def test_list_projects_by_slug():
    response = client.get("/projects?slug=api-v2")
    assert response.status_code == 200
    assert len(response.json()) == 1
    assert response.json()[0]["slug"] == "api-v2"
```

改了三個地方：函式名稱、查詢參數（`name` → `slug`）、斷言欄位（`name` → `slug`）。

Slug 是「URL 友好的識別碼」——全部小寫、用連字號取代空格、不含特殊字元。例如 "API v2" 的 slug 是 `api-v2`。在 URL 裡傳遞 `?name=API v2` 需要編碼（變成 `?name=API%20v2`），而 `?slug=api-v2` 不需要。這讓 API 更乾淨、更容易測試、也更符合 REST 慣例。
