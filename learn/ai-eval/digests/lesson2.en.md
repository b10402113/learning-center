# L1 overview

- **Office-hours format** — Week 1 Q&A session (about an hour) answering assignment, setup, and tooling questions live with screen demos; BrainTrust credits ($10–20, negotiated to $20) and small models to keep experiment cost low.
- **The three legs, restated across tools** — Dataset (versioned regression/unit/red-team sets), metrics plus judge, and an experiment runner are the same in BrainTrust, LangSmith, CrewAI, etc. Judge types: human, LLM-as-judge, hybrid, and Jev (a non-transformer "system one" judge). Week 2 focuses on building and aligning LLM judges.
- **Grading pass/fail in week 1** — The week-1 Pronto agent is deliberately bounded/hard-coded (regex, no LLM), so pass/fail is about whether the requested behavior (e.g. asking for an order ID before acting) is right, not about absolute answer quality; the skill being built is reading traces and grouping failures. Grade both per-turn and final session outcome.
- **Trace anatomy and plumbing** — Runtime traces live in memory then must be persisted to an observability platform. Hierarchy is session → turn → root span → LLM span → tool-call spans; spans carry model, input/output, token counts, duration, TTFT, and tool calls. Traces should be organized into projects for permission/governance, especially for sensitive HR or PII data.
- **Two ways to run evals** — SDK/API calls (e.g. `braintrust eval`, LangSmith `evaluate`) for scale and CI/CD, versus the UI for small unit tests, dashboards, and labeling. Playground = ad hoc single tests and A/B across prompts/models; experiments = batch/automated suites, optionally triggered by code changes or scheduled overnight.
- **Synthetic data and test rubrics** — Test scenarios can be generated from an agent's jobs-to-be-done metadata, but synthetic data is lower quality, so hand-written scenarios matter. A test run combines test target, test type (single-turn vs conversation-level), data, and metrics; out-of-box metrics plus custom scorers (e.g. faithfulness for RAG) form the full rubric.
- **Platform-agnostic philosophy** — Agent runtime can be local, Cursor/Claude Code, OpenAI/Google, or a vendor platform; the eval tool is interchangeable. 80% of tools share the same concepts under different labels (metric = score = measure, test set = dataset); tools may change, but the "why evals are hard" understanding does not.
- **Assignment clarifications** — Harness limits (stateless agent, lost context across turns, missing agent IDs) are harness bugs rather than product bugs; multi-turn CSV formatting must preserve per-turn inputs/outputs; the companion "how to write eval for anything" article frames week 1 as code-based graders before week 2's model-based graders.
