# Eval Rubric（評測規準）

<!--image:1-->

## 問題

開發 AI 產品或 Agent 時，若只憑「感覺回答得不錯」來評估，很容易在後期才發現問題。

模型可能最終給出了答案，背後卻呼叫了過多次工具，耗費大量 Token。系統也可能產生不合規或體驗極差的回應。

動工前若沒有具體的評估標準，團隊無法客觀驗證每次調整。工程師與 PM 將難以判斷修改 Prompt 或流程更動是改善還是退步。

## 前置條件

制定評測規準前，團隊需要先具備以下條件：

- 清楚定義的業務目標與功能範疇。
- 跨職能團隊參與，包含 PM 與 AI 工程師；若涉及介面互動，也應納入產品設計師。
- 預期會呼叫的 Tools 清單，以及基本系統架構。

## 步驟

將模糊的期待拆解為可判定的具體維度：

1. **定義產出成果（Outcome）**：列出模型最終必須達成的成功指標。確認模型是否正確解決問題、回傳資料格式是否正確、資訊是否完整。
2. **規劃使用者體驗（Experience）**：訂立回應風格、等待時間與互動邏輯的標準。確保語氣符合品牌形象，面對無法回答的問題時也有合適的應對機制。
3. **規範執行軌跡（Trajectory）**：評估 Agent 從接收指令到輸出結果的中間路徑。檢查工具呼叫順序是否最短且最有效率，避免陷入無效迴圈或繞遠路。
4. **設定治理與合規邊界（Governance）**：明訂安全邊界、隱私限制與系統權限規則。確保模型不會洩漏敏感資訊，也不會執行未授權的操作。
5. **轉化為可判定測試案例**：為每個維度撰寫測試案例與明確的通過條件（Pass/Fail 或評分級距），作為自動化評測或人工抽檢的依據。

## 例子

以「客服訂單查詢 Agent」為例，評測規準可拆解如下：

- **Outcome（成果）**：必須正確查出訂單狀態與出貨日期。格式為標準 JSON 與一段摘要，資訊正確率需達 100%。
- **Experience（體驗）**：回覆口吻需溫和專業。單次完整回覆的生成時間需在 3 秒以內。
- **Trajectory（軌跡）**：直接呼叫 `get_order_by_id` 工具取資料。若連續呼叫同一工具超過 3 次，或單次查詢消耗超過 2,000 Token，即判定該軌跡不合格。
- **Governance（治理）**：使用者若詢問他人訂單編號，系統必須直接拒絕並觸發驗證流程，不得將個資外洩給未授權帳號。

## 失敗模式

- **只看最終結果而忽略執行軌跡**：模型雖然最後回答正確，但中間可能卡在迴圈長達 30 分鐘並消耗大量 Token。忽視軌跡會讓產品上線後營運成本暴增、回應延遲過長。
- **職責切分過於僵化**：傳統流程中 PM 負責寫 PRD，工程師只管實作。如果 PM 不參與軌跡與失敗案例的定義，或工程師不理解體驗標準，評測規格就會與真實產品需求脫節。
- **標準主觀且無法判定**：使用「語氣要自然」或「回答要聰明」等抽象描述，會讓不同人員或評測模型每次給出互相矛盾的結果。

## 進階

建立評測規準後，團隊能將「軌跡評測」回饋到 Prompt 工程。

當發現 Agent 總是繞遠路呼叫多餘工具時，可以直接定位該段軌跡。

接著在 System Instructions 加入 Negative Examples 或路徑限制，引導模型選擇最短的工具呼叫路徑。
