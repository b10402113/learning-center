# Error Analysis（錯誤分析）

<!--image:1-->

## 問題
開發 AI Agent 或大型語言模型應用時，團隊常憑感覺認為「系統表現大致良好」，卻講不出系統具體在哪裡出錯。如果還沒看過真實的互動紀錄，就急著做自動化評測（eval），很容易設計出脫離實際業務情境的無效指標。

## 前置條件
- 累積了一定數量的系統互動歷程（traces 或 sessions）。
- 有明確的業務規範或護欄政策（例如：退款超過 50 美元必須經過人工核准）。
- 有能完整查看使用者輸入、Agent 回覆與執行步驟的檢視介面或工具。

## 步驟
1. **抽樣互動紀錄**：面對成千上萬筆資料，先抽樣 40 到 50 筆 session 即可開始，避免因資料量過大而不知從何下手。
2. **人工逐筆檢視**：親手閱讀每一筆 trace，看清楚使用者輸入了什麼、系統回覆了什麼。
3. **標註判定結果（Verdict）**：逐筆判定為 PASS（通過）或 FAIL（失敗）。
4. **記錄具體失敗原因**：遇到 FAIL 的案例，寫下一行具體說明，指出哪裡不符合預期（例如「未經核准直接退款 85 美元，違反超過 50 美元需人工審核的護欄規則」）。
5. **歸納錯誤分類（Trace Code）**：把類似的錯誤聚類，並給予標籤（例如 `MISSED_REFUND_INTENT` 或 `OVER_REFUND`）。
6. **追查根因並轉化為評測**：確認問題是護欄未觸發、prompt 誤判意圖，還是流程邏輯有疏漏；再將驗證過的錯誤模式納入未來的自動化評測集。

## 例子
在電商客服 Agent 的抽樣分析中，可能出現以下標註：

- **失敗案例**：
  - 輸入：「訂單 PRN-10421 的草莓送來時發霉了。」
  - Agent 回覆：「訂單 PRN-10421 正在配送中，約 25 分鐘後抵達。」
  - 判定：FAIL
  - 說明：使用者回報生鮮商品腐壞，系統應啟動退款流程並索取照片，Agent 卻誤當成查詢配送狀態。
  - 錯誤標籤：`MISSED_REFUND_INTENT`
- **通過對照**：
  - 輸入：「訂單 PRN-10422 需要退款，金額 85.40 美元，有一半商品沒收到。」
  - Agent 回覆：「該筆退款需要人工核准，已為您送出申請。」
  - 判定：PASS（正確遵循超過 50 美元轉交人工的規則）。

## 失敗模式
- **過早自動化**：還沒親眼看過幾十筆真實資料，就急著寫腳本或用 LLM 自動打分，導致評測指標完全漏掉真正的缺陷。
- **只打分數不寫原因**：標記了 FAIL 卻沒寫下一行文字說明「為什麼錯」，後續無法進行錯誤分群與修復。
- **抽樣規模失衡**：試圖一次看完數千筆 trace，導致精力耗盡而放棄；或是只看兩三筆就草率下結論。

## 進階
修復錯誤通常不難，最難的是釐清「哪裡出錯」與「為什麼出錯」。

完成 40 到 50 筆手動錯誤分析後，常會發現絕大多數失敗都集中在少數幾種固定模式。這時建立的錯誤分類標籤，正是日後撰寫自動化 guardrail、修正系統提示詞，以及擴充回歸測試集（regression test suite）最扎實的依據。
