內建生圖：先確認視覺方向，再開始蓋網站

Step 4/5 · 桌面 app 的前端開發工具面

學習目標

完成這一節後，你會知道內建生圖使用哪一份額度，也能分辨它在「產生視覺資產」和「確認視覺方向」這兩種情境中的用法。

為什麼要在動工前先看一眼

前端專案最麻煩的錯誤，往往不是按鈕壞掉，而是一開始就走錯視覺方向。

例如，你要做一個 landing page，需要一張主視覺；或是要做一個 dashboard，腦中只有「要有科技感」這種模糊想法。以前你可能會先離開 app 找圖片，也可能直接叫 Codex 開始蓋。等畫面完成後才發現：「不是這個感覺。」這時候，版面、配色和元件可能都得重做。

Codex 桌面 app 內建了生圖能力。它的價值不只是幫網站產生圖片，而是把「動工前先確認方向」放進同一條工作流，讓發現方向不對的成本，從整個前端重做，降到先看一張概念圖。

內建生圖用的是哪一份額度？

Codex 裡的生圖能力，和你在 ChatGPT 中使用的生圖能力相同，只是現在直接放進 Codex 工作流程裡。

關鍵在於：它使用你的訂閱額度，而不是 API。因此不會另外產生一筆 API 帳單，而是使用你原本就有的訂閱配額。對已經訂閱的使用者來說，這讓生圖可以自然地成為開發流程中的一環，而不必再切換到另一個服務。

情境一：產生網站需要的視覺資產

最直接的用法，是替網站產生圖片。

當 Codex 判斷前端專案需要視覺素材時，它可以使用內建生圖產出圖片。你不必另外搜尋授權不明的素材，也不必離開 Codex 開啟其他生圖服務；圖片可以直接成為專案的一部分。

情境二：先驗證視覺方向

更值得注意的用法，是在開始寫前端之前，先請 Codex 提出視覺方向。

你可以把它想成蓋房子前先看設計草圖。Codex 先產生一張概念圖，讓你確認它打算採用的風格；你覺得方向正確，再讓它依照這個方向開始動手。

先給我三個不同的視覺方向，
各生一張概念圖讓我挑，
選定之後再開始蓋。

這個順序的重點，不是多做一張圖，而是提早暴露問題。

如果一開始就寫程式，等成品出來才發現方向不對，前面做好的版面、配色與元件很可能都要重來。相反地，先用概念圖確認方向，就能在成本還很低時修正。圖像一旦讓你說出「對，就是這個感覺」，後面的實作才有比較明確的靶心。

所以可以把這個工作流記成一句話：先對方向，再動手。

把兩種用法放在一起看

用法 解決的問題
產生視覺資產 網站需要圖片或其他素材時，直接在 Codex 中產出。
驗證視覺方向 開始開發前，先確認風格是否符合期待，避免整個專案蓋錯方向。

前者是在專案進行中補素材；後者則是在專案開始前降低風險。兩者都使用同一項內建生圖能力，但解決的是不同問題。

小結

Codex 桌面 app 的內建生圖能力，和 ChatGPT 的生圖能力相同，但使用的是你的訂閱額度，不走 API，也不會另外產生 API 帳單。它有兩種主要用法：一是產生網站需要的視覺資產；二是在動工前先產生概念圖，確認視覺方向。先用低成本的圖擋住高成本的重做，記住：先對方向，再動手。

到這裡，你已經能在自己的專案裡完成一輪前端工作：把專案跑起來、檢視畫面、調整外觀、處理除錯，再補上需要的素材。

不過，前端工作很少只由一個人完成。你可能會收到同事開的 PR、被 tag，或需要在特定的 worktree 裡執行指令。下一步要看的，就是如何把這些協作情境也留在 Codex app 裡完成。
