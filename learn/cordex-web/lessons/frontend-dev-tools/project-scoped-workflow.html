把 Codex 綁進專案資料夾，並在 app 內把網站跑起來

Step 1/5 · 桌面 app 的前端開發工具面

這一步要完成什麼？

完成後，你會在 Codex 桌面 app 建立一個綁定本地資料夾的 project，發出 prompt，將產物轉成真正的 app，啟動 dev server，最後用內建瀏覽器看到可以互動的畫面。

開始前，你需要先準備一個要工作的資料夾，例如名為 example demo 的空資料夾，並在電腦上開啟 Codex 桌面 app。

為什麼要先綁定資料夾？

你可能已經在 Codex 裡問過問題，也看過它產生的 HTML 或小元件。但把內容複製到自己的專案後，常會遇到畫面跑不起來，或 Codex 改到了不對的地方。

問題不一定出在程式碼，而可能是 Codex 根本不知道自己應該在哪個資料夾工作。

第一次打開 Codex 桌面 app 時，它看起來像一般聊天視窗。若沒有指定 project，Codex 會使用所有聊天共用的預設資料夾。建立 project 並綁定本地資料夾，就像先替它圈好施工範圍：之後的檔案與指令都會在指定的位置進行。

五個動作：從資料夾到看見畫面

接下來依序完成：建立 project、發 prompt、建立 app、啟動 dev server，最後用內建瀏覽器查看結果。

1. 建立綁定本地資料夾的 project

在 Codex app 新增一個 project，然後選取要使用的資料夾，例如 example demo。

預期結果：介面會顯示你正在某個 project 裡工作，而不是停留在沒有歸屬的通用聊天。這也是後續工作的前提：Codex 和內建瀏覽器都必須知道要在哪個資料夾裡產生與執行內容。

2. 發出第一個 prompt

建立 project 後，就可以直接輸入指令。若任務很單純，可以先使用較低的 reasoning effort，不必一開始就動用最重的思考資源。

例如，請 Codex 建立一個簡單的天氣視覺化：

Can you create a very simple HTML visualization
of the weather in Minneapolis today?

這個例子會使用 visualization skill，專門產生視覺化內容。

預期結果：聊天視窗中會出現視覺化結果，而不只是幾段文字說明。

3. 把聊天產物變成真正的 app

聊天裡的視覺化雖然看得到，但還不等於一個可以執行或部署的專案。接著請 Codex 把它轉成真正的 app，例如 React app。

預期結果：Codex 會在你指定的資料夾裡建立最小的專案結構，並告訴你要執行哪個指令才能把它跑起來。

4. 啟動 dev server

這一步有一個常見陷阱：不要直接雙擊產生的 HTML 檔案。

那個檔案需要透過 dev server 提供服務。若直接打開，畫面可能會是空的。請選擇以下其中一種做法：

  1. 按 Command+J 打開 app 底部面板，將 Codex 告訴你的指令貼到終端機並執行。
  2. 直接對 Codex 說 run it，讓它替你執行指令。

預期結果：dev server 會啟動，終端機會顯示它正在某個本地位址上監聽。

底部面板整合了終端機。之後要在 Codex app 裡執行指令，就可以從這裡完成。

5. 用內建瀏覽器查看結果

dev server 啟動後，打開 Codex 的內建瀏覽器，就能看到剛才建立的畫面。

你可以直接在頁面上互動、加上標註，或將頁面開到一般瀏覽器中查看。

這樣一來，「修改一次、查看一次」的迴圈就留在同一個視窗裡，不必在編輯器、終端機與瀏覽器之間反覆切換。

順手開啟的設定：防止電腦睡眠

如果你常讓 Codex 執行比較久的任務，或會暫時離開筆電，可以在設定裡開啟「Codex 執行期間防止睡眠」。

這樣 Codex 能繼續完成任務，也不會因為筆電進入睡眠而中斷。

完成後，你應該看到什麼？

桌面 app 的前端工作流，第一步是「圈地」：先把 Codex 綁進本地資料夾的 project，避免它在錯的位置修改檔案。接著在 app 內發出 prompt，把產物轉成 app，再用整合終端機（Command+J）或一句「run it」啟動 dev server，最後在內建瀏覽器中看到畫面。不要直接雙擊 HTML 檔案，因為它需要透過 dev server 提供服務。

做到這裡，你已經能在同一個 Codex 視窗裡建立專案、啟動它，並看到實際畫面。下一步會處理另一個實作問題：當你覺得畫面「看起來不太對」時，如何用內建瀏覽器與標註工具，把模糊的感覺變成指向具體元素的修改指令。
