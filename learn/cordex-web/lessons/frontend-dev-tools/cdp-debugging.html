CDP：讓 Codex 直接看見 log 與 network

Step 3/5 · 桌面 app 的前端開發工具面

為什麼畫面正常，功能卻壞了？

有一類 bug 很難只靠畫面找出來：你按下按鈕，什麼都沒發生；表單看似送出，資料卻沒有進資料庫；圖片位置正確，內容卻是一片空白。

這時候，問題不一定在畫面上，而可能藏在瀏覽器背後。你需要知道：console 有沒有拋出錯誤？API 請求有沒有真的送出去？回應是 200 還是 500？如果這些資訊都看不到，除錯就像閉著眼睛找漏水的位置，只能一直猜。

以前，你得自己開 DevTools，逐項查看，再把結果描述給 Codex。CDP 解決的正是這段來回：讓 Codex 直接取得瀏覽器裡的除錯資料，少掉人工轉抄與猜測。

CDP 是什麼？

CDP 的全名是 Chrome DevTools Protocol（Chrome 開發者工具協定）。它是一套讓外部工具與瀏覽器溝通的協定。

你平常使用的 Chrome DevTools，本身就是透過這套協定和瀏覽器對話。因此，CDP 不是另一個只負責顯示畫面的工具，而像是一條通往瀏覽器內部資訊的通道。只要工具接得上這條通道，就能取得原本藏在開發者工具裡的除錯資料。

Codex 桌面 app 能讓 Codex 接上 CDP。接通後，Codex 可以直接取得前端除錯最常用的兩類資訊：logs 與 network。原本需要你手動查看、再轉述的內容，現在能直接成為 Codex 判斷問題的證據。

CDP 讓 Codex 看見什麼？

這兩類資料，剛好對應前端最常見的兩種故障：

資料它回答的問題沒有它會怎樣
logs（主控台訊息）程式碼有沒有拋錯？邏輯走到哪一步？只能猜錯誤可能發生在哪一行
network（網路請求）請求有沒有送出？回應是什麼狀態？載入失敗在哪裡？很難判斷問題在前端還是後端

例如，按鈕沒有反應時，logs 可以告訴 Codex 程式是否在事件處理函式中拋錯；如果表單送出後資料沒有出現，network 則可以確認請求是否發出，以及伺服器回傳了什麼狀態。

這會改變除錯的迴圈。以前你可能只能對 Codex 說：「我覺得是 API 壞了，你往那邊看看。」接上 CDP 後，Codex 可以直接看到失敗的請求與狀態碼，從實際證據開始縮小範圍。

CDP 和標註：一個看外觀，一個看行為

標註工具處理的是「畫面看起來對不對」：元素位置歪了、間距不一致，或某個區塊的外觀需要調整。CDP 處理的則是「畫面背後有沒有正常運作」：程式是否拋錯、請求是否成功、資料是否載入。

兩者不是替代關係，而是互補：

問題類型適合的工具
外觀、位置、間距不正確標註工具
程式拋錯、請求失敗、資料載入異常CDP

把兩條線分開，Codex 才能同時理解畫面與行為：看起來不對時檢查外觀，動起來不對時查看瀏覽器內部的證據。

把 CDP 記在腦中

CDP（Chrome DevTools Protocol）是一套讓工具與瀏覽器溝通的協定，Chrome DevTools 自己就是用它。Codex 桌面 app 讓 Codex 直接接上 CDP，因此能取得 logs 與 network 這類除錯資訊：主控台訊息回答「有沒有拋錯」，網路請求回答「請求成不成功」。它的意義是把除錯從猜測變成查證；而它與標註分別負責行為與外觀，彼此互補。

到目前為止，我們處理的都是「已經存在的畫面」：把它跑起來、改好看，再修正它的行為。但有時候需要的素材根本還沒被生出來，例如網站插圖，或動工前的產品概念圖。下一步要介紹的內建生圖，正好補上這一塊。
