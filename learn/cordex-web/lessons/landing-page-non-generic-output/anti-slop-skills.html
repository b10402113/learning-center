把品味寫成 skill：write-practical-copy 與 design-ui-with-restraint

Step 2/5 · Landing page：不要產出 AI 味

前言：方向對了，怎麼讀起來還是很「AI」

上一節我們把「AI 味」的來源指向一件事：沒有視覺方向。方向給了之後，網站的整體氣質確實會明顯不同。但如果你真的照著做完一輪，多半會撞上另一種失望：排版和氛圍都對了，標題讀起來卻像行銷罐頭，或者頁面上多了一堆沒人要看的說明文字。

這些殘留的味道不歸視覺方向管。它們來自模型寫字和畫介面時的習慣，得用另一套規則去擋。這一節要處理的就是這個問題：怎麼把「什麼是好的、什麼是爛的」這種通常只存在設計師腦袋裡的品味，變成 Codex 每次動工都會自動遵守的規則。

skill 是什麼：一份放進 repo 的編採手冊

先講清楚這裡的 skill 是什麼，免得誤會。它不是外掛，也不是連到外部服務的 connector，而是一份寫給 Codex 的指示文件：描述某一類工作該怎麼做，讓模型在相關情境下自動讀取並遵守。

這門課的 repo（katia-openai/master-dev-workshop）在 .agents/skills/ 底下帶了兩個很短的 skill。短到可以一眼讀完，卻剛好各擋住一種常見的 AI 味。

用生活化的說法，這像是給一位新進編輯一份「編採手冊」。你不用每次開會重講一遍自家的文字標準，手冊放在那裡，他拿到稿子自然會翻。把品味寫成 skill，等於讓 Codex 每次動工前都先讀過那份手冊，而不是靠你在 prompt 裡反覆碎念同一段話。

write-practical-copy：擋掉「文字腔」

模型說話有一種很明顯的習慣：偏好宏大的措辭，把小事情講得很戲劇化，也很愛用「短句。短句。短句。」這種一連串短句加句號的節奏。這些句子單看漂亮，放到網站上只讓人覺得浮誇又空。第一個 skill 就是專門對付這件事。

它給的規則很直白：標題和標籤直接講出那是什麼東西，一個區塊配一個清楚的標題；說明文字用平實的語言講清楚某樣東西是什麼、做什麼、代表什麼，不重複標題，也不講廢話；用具體的例子和正確的產品名稱，句子要連得起來；行動呼籲，也就是按鈕上那類字，要具體有用。原文的規則長這樣：

## Descriptions and body copy

- Explain what something is, does, or means in plain language.
- Include enough detail to be useful, but do not repeat the title or describe what is already obvious.
- Use concrete examples, accurate product names, and connected sentences.
- Make calls to action specific and useful.

更實用的是它附的那張「避免」對照表，把 AI 味句型和建議改寫並排放在一起。下面重現其中幾列：

AI 味句型範例建議改寫
硬要對比「方向盤是羅盤，不是合約。」「用色環找出能搭配的顏色。」
詩意但沒意思「讓房間感覺無可避免。」「打造一個你住起來舒服的空間。」
聰明但看不懂的標題「一天的形狀」「議程」
模糊的區塊名「我們一起做什麼」「團隊技能」
自我重要的框架「一個值得重複使用的 prompt」「範例 prompt」
戲劇化的破碎句「按鈕動了。標籤變了。」「介面會隨著你的操作而更新。」

這張表的價值不只是「別這樣寫」。它把一種原本只能靠直覺判斷的東西，變成 Codex 可以逐條核對的清單。往後你若看到產出的文案還是聞得到那股味道，就代表規則沒涵蓋到那一類，直接往這張表補一條即可。

design-ui-with-restraint：擋掉「多餘的資訊」

第二個 skill 管的是介面。模型的另一個傾向是「給你更多」：用的是示範資料，它就主動在頁面上加一句「這不是真實資料」；一張卡片明明已經叫「行事曆」，上面還要再疊一個「排程」；順序根本不重要，卻硬加上裝飾性的 01、02、03。這些東西對使用者沒有幫助，只會讓介面變吵。

這個 skill 把規則分成結構、視覺、編輯三類，核心精神是「有用才留、沒用就拿掉」。它的結構規則原文是：

## Structure and hierarchy

- Build the layout around what the user needs to understand or do.
- Give each page, section, or card one clear title.
- Add headings, labels, badges, numbers, and descriptions only when they provide useful information.
- Use cards, navigation, buttons, and other familiar patterns when they suit the content, not by default.
- Keep implementation notes, demo-data disclaimers, and internal explanations out of the interface unless they matter to the user.

最後那條特別值得記住。它明文把「實作筆記、示範資料警語、內部說明」擋在介面之外，正好收拾掉前面說的「這是虛構資料」那類贅字。至於編輯那一類，判斷準則只有一句話：只改需求要求的部分，其餘保留；某個元素什麼都沒加值就拿掉，有幫助才留。

小結：方向管整體，skill 管細節

write-practical-copy 擋的是文字腔：宏大、誇張、短句加句號、空泛的行動呼籲；design-ui-with-restraint 擋的是多餘的介面資訊：重複標題、裝飾編號、示範資料警語。把品味寫成 skill，等於讓 Codex 每次動工都先讀一遍你家的工作標準，不必靠你在 prompt 裡反覆交代。

回到最開頭那個問題：方向對了卻還是很 AI，原因就是視覺方向只管得住整體氛圍，管不住逐字逐句的細節。現在你手上有兩樣互補的東西：一份拉開預設的視覺方向，和兩個擋細節味道的 skill。這兩者掛在同一條線上：方向決定「看起來像不像樣」，skill 決定「讀起來、用起來順不順」。下一節的問題是，視覺方向該由你定，還是可以跟 Codex 一起想出來。
