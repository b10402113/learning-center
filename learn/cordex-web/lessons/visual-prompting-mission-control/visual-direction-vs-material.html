為什麼只用文字描述會做出通用介面：視覺方向與素材

Step 1/4 · 用視覺範例提示：Mission Control

學習目標

能說出為什麼「用文字描述你想要的樣子」常常做出通用介面，並分辨 moodboard（視覺方向）、fixtures（資料素材）與真實 plugin 三者在 prompt 裡各自扮演的角色。

前言：一句「做個好看的儀表板」，換來一個到處都見過的介面

你可能遇過這種情況：請 Codex 做一個個人工作儀表板，還特地交代要「現代、乾淨、有質感」。它很快交出一版可以跑的頁面，但那個介面你怎麼看都眼熟：藍紫漸層、大圓角卡片、置中的標題，換掉文字之後，放在任何一個產品 demo 裡都不違和，卻也沒有任何一點是為你做的。

問題通常不在 Codex 不夠努力，而在你給的指令等於沒給。「現代、乾淨、有質感」這些形容詞，對模型來說正好對應到它最常見的預設樣板；你以為在指定方向，其實是在描述平均值。這一課要講的，就是把「用文字描述你要什麼」換成「直接給它看」：給一張圖當視覺方向，給一組資料當素材。這兩件事，是讓產出脫離通用感的關鍵。

為什麼「把預設值講出來」幾乎沒有作用

語言模型受過的訓練，是從大量資料裡學會「最可能的下一步」。當你說「做一個專業的財務儀表板」，它腦中浮現的是訓練資料裡成千上萬個財務儀表板的平均樣貌。你越是只用抽象形容詞描述，輸出就越會往那個平均值靠攏，結果就是一個「誰都像、誰都不是」的介面。

打個比方。你請一位裝潢師傅把客廳弄得「溫馨一點」，他會照自己的經驗做；你給他一張你喜歡的空間照片，他才會做出你心裡那個樣子。形容詞把決定權交回給對方的預設值，圖片則把方向直接說死。對 Codex 也是一樣：視覺範例不是輔助說明，而是比文字更精確的指令。

視覺方向：moodboard 是拿來「翻譯」的，不是拿來「照抄」的

最直接的視覺範例是 moodboard（情緒板，把色彩、材質、氛圍的參考圖拼在一起的一張圖）。Mission Control 的範例 prompt 就指定用 repo 裡的 assets/mission-control-moodboard.png 當視覺方向，並附上一句關鍵指令：把它當作 art direction（藝術指導），而不是照著它的版面複製。

這句話值得拆開看。moodboard 傳達的是「感覺」：某組顏色、某種材質的觸感、柔和的形狀、大方的留白、像便當格一樣的拼貼構圖。你要的是把這些元素翻譯進一個實用的介面，而不是把 moodboard 上的方塊照位置排一遍。少了「translate, not copy」這句，Codex 有可能把參考圖當成線框圖來臨摹，做出一個看著像、卻不好用的畫面。

視覺方向不必自己畫。你有三種取得方式：

來源做法適合誰
自己提供的參考圖把你喜歡的網站截圖、品牌素材或 moodboard 一起丟給 Codex，叫它翻譯色彩與材質有既存品牌或明確喜好的人
請 Codex 先生一張用 image generation 依你的描述產生一張 moodboard，再拿它當方向還沒有參考圖、想先看方向的人
plugin 的內建 skill用 Sites 或 Build Web Apps plugin 時，裡面的 skill 會在建置前自動產生視覺方向想少寫幾句、直接開始的人

第三種特別值得一提。Sites 是一個含有一堆 skill 的 plugin，其中一個 skill 會在動手 build 之前，先用 image generation 產生一張視覺方向圖。所以使用 Sites 時，你會看到 Codex 先給你看一張圖、再開始蓋頁面。如果你沒用 plugin，也可以自己補上這個行為：在 prompt 裡加一句「動手前先停一下，用 image generation 產生視覺方向，再開始 build」，通常會比讓它直接從零蓋一個介面來得好。

素材：fixtures 或真實 plugin，決定資料從哪裡來

視覺方向處理的是「看起來像什麼」，素材處理的則是「裡面裝什麼資料」。Mission Control 是一塊把優先事項、訊息、行事曆、待辦全部集中起來的儀表板，所以它需要資料。取得資料有兩條路：

用 repo 的 fixtures接真實 plugin
資料來源repo 內附的虛構 JSON（calendar、Gmail、Slack、tasks）你真正的 Gmail、Slack 等工具
怎麼接在 prompt 裡指向 fixtures 資料夾先到 plugins 安裝（例如 Gmail 按 install、走完 onboarding），再在 prompt 裡用 @Gmail、@Slack 提及
優點可公開分享、可重現、不需要任何帳號真的能反映你的日常，實際幫上忙
限制資料是假的，只能當示範含個人資訊，不能公開分享成果

兩條路不是二選一的正確答案，而是看你當下要的是「可示範」還是「真有用」。課程範例用 fixtures，是因為無法公開自己的 Slack 與 email；但講者也直接建議跟著做的人，如果做得到，就用真實資料，因為那才真的會改變你的工作方式。真的接上 plugin 時，記得一件事：發佈前確認頁面上沒有露出任何個人資訊。

兩種輸入，兩種問題，別混在一起

把視覺方向與素材分開看，會讓 prompt 清楚很多。視覺方向回答「這個介面該給人什麼感覺」，素材回答「這個介面要呈現哪些內容」。前者用圖片溝通，後者用資料或 plugin 溝通。之所以要分，是因為它們對應兩種完全不同的失敗：沒有視覺方向，產出會變成通用的樣板；沒有明確的素材，Codex 只好自己編造看起來合理的假資料，而你需要的是真的能餵進去的結構。

還有一個常見的誤解：以為給了 moodboard 就等於給了設計。其實 moodboard 只給方向，介面的階層、標題、留白與互動，仍要靠 prompt 裡的規則去約束，那會是後面第三課要拆的部分。

小結

用抽象形容詞描述介面，等於把決定權交給模型的預設值，結果就是一個「哪裡都適用」的通用介面。解法是給兩種具體輸入：moodboard 提供視覺方向（記得要求翻譯、不要照抄），fixtures 或真實 plugin 提供資料素材。視覺方向可以自己給、請 Codex 先生，或交給 plugin 的內建 skill；素材則依你要可示範還是真有用來挑，接真實 plugin 時要守住隱私。

視覺方向給了、素材也有了，但這裡先按住一個問題：那份烘培機資料（fixtures）本身是怎麼設計的？它能不能重跑、會不會覆蓋你自己加的任務，決定了這個 app 能不能被信任。下一課就要把這份 fixture 的資料契約一項一項攤開。
