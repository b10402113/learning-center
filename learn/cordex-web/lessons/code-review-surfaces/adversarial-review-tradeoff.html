Adversarial 互審：多輪攻防，還是單次審查就夠？

Step 4/4 · Code review：Codex review 與第二個模型

當一段程式碼牽涉金流、安全或並發競態時，只讓一個模型看一遍，可能還是不夠。但如果每次改個小地方都讓兩個模型來回爭辯，token 很快就會像漏水的水桶一樣見底。

這一節要做的決定很直接：什麼時候該用 adversarial 多輪互審，什麼時候單次第二模型審查就已經足夠？你也會知道，多輪互審到底貴在哪裡。

先把兩個選項放在一起比較

面向單次第二模型審查Adversarial 多輪互審
做法請第二個模型獨立審查一次，再由你閱讀結果讓兩個模型互相質疑、反駁與修正，來回多輪，直到形成站得住腳的結論
成本支付一次審查所需的 token成本非常高，一輪就可能吃掉小方案一整個期間的額度

Adversarial 互審到底多做了什麼？

它不是單純請兩個模型各審一次。這個 skill 會要求兩個模型互相爭論，並且來回好幾輪：一方提出問題，另一方反駁或修正；接著交換攻守，繼續追問，直到逐步逼近雙方都能接受的結論。

可以把它想成兩位審查者在同一張白板前打乒乓球。單次審查是多看一雙眼睛；多輪互審則是讓這雙眼睛追問第一個判斷的理由，再檢查修正後的說法是否真的成立。

它可能更準的原因，在於兩個模型的視角不必完全重疊。一方提出的假設，可能正好被另一方戳破；被戳破後再修正，另一方的漏洞也可能被反過來抓出來。這就是 adversarial code review（對抗式程式碼審查）的核心。

做決定前，先問自己三題

  1. 這段程式碼出錯時，代價有多大？ 如果涉及安全、金流或並發競態，錯誤可能造成嚴重後果，多花 token 逼近真相通常值得。若只是修改文案、排版或變數名稱，就沒有必要。
  2. 目前的方案額度撐得住嗎？ 這是硬門檻。先確認訂閱方案能承受多輪互審，再考慮啟用它。
  3. 單次審查後，我還有沒有具體疑問？ 如果第二模型已經指出問題，而且你看完也有把握，就停在單次審查。只有仍有懸而未決的疑點，才值得升級成多輪互審。

反例：額度不夠時，互審可能根本跑不完

Adversarial 互審的成本不是只「貴一點」，而是可能直接把可用額度打穿。

講者曾用每月約 20 到 25 美元的 Claude 方案執行這支對抗式 review skill，結果一輪就用光該方案在 5 小時期間可用的 token。換句話說，小方案不是省著用就能順利完成，而是可能連一輪都撐不完。

因此，這支 skill 比較適合同時擁有兩邊高階方案、手上有足夠 token 餘裕的人。即使額度充足，日常小改動也不值得使用：為了一個不影響行為的變數名稱，讓兩個模型長時間辯論，成本遠高於問題本身。

反過來說，如果程式碼位在高風險、複雜的關鍵路徑，而且方案額度充足，多輪互審才有機會帶來相應的價值。

可以直接採用的決策規則

預設使用單次第二模型審查。只有在「出錯代價高」、「單次審查後仍有具體疑問」，而且「token 額度撐得住」這三個條件同時成立時，才升級成 Adversarial 多輪互審。

這樣安排，Codex review 負責提供不帶既有脈絡的獨立檢查，第二個模型補上不同視角；只有真正需要反覆攻防的高風險程式碼，才動用昂貴的多輪互審。
