為什麼模型審自己的 code，仍然有根本盲點？

Step 2/4 · Code review：Codex review 與第二個模型

學習目標

看完這一節，你應該能說清楚：為什麼讓同一個模型審自己寫的 code，仍然有先天限制；也能理解，為什麼實務上值得保留第二個模型做 review。

先看一個實際情境：多開一個 instance，就真的換了一雙眼睛嗎？

上一節提到 Codex review：它會開一個獨立、沒有目前對話脈絡的 instance 來檢查程式碼。這樣做確實能避免審查者被原本的討論帶著走。

但如果 Codex 寫完 code，接著仍然由 Codex review，問題只解決了一半。因為你換掉的是「它剛才看過哪些內容」，卻沒有換掉「它是誰」。

這就像讓同一位作者把稿子收起來，隔天再拿回來校對。時間和桌子都換了，但他的語感、偏好，以及容易忽略的錯誤，仍然沒有變。

真正的差別：脈絡不同，視角不一定不同

這裡要分清楚兩個概念。

脈絡是模型在這個 session 裡看過、記得的內容，例如先前的對話、修改理由和目前的任務狀態。Codex review 開新的 instance，主要換掉的就是這一層。

視角則是模型經過什麼訓練、習慣注意什麼，以及習慣忽略什麼。只要審查者仍然是 Codex，這一層就沒有改變。

因此，即使寫 code 和 review code 是兩個不同 instance，兩者仍然共享同一套模型訓練，以及相近的「什麼算是好程式碼」的判斷方式。寫的時候沒注意到的問題，審查時也可能照樣被略過。

為什麼多審幾輪，通常補不上這個盲點？

直覺上，你可能會想：那就要求模型多審幾次，或每次用不同提示，總會找到問題吧？

這能增加檢查次數，卻不一定能增加檢查角度。如果盲點來自同一套視角，重跑十次，就像同一位編輯用十種標記色校對同一篇文章：看得更久，仍可能漏掉同一類錯誤。

同一位作者校對自己的稿子時，也容易跳過慣用詞和習慣句型。不是他不夠認真，而是大腦早已把那些內容視為「正常」。另一位編輯則可能一眼看出反覆出現的語病，因為他帶來的是不同的判斷標準。

所以，這裡真正需要增加的不是次數，而是視角的差異。

第二個模型的價值：讓盲點不要完全重疊

這也是為什麼實務上值得為 code review 保留第二個模型。講者同時付費訂閱 Codex 和 Claude，並刻意讓 Claude 審查 Codex 產出的 code。他的經驗是，第二個模型「總是一直找到東西」（they constantly find stuff）；在他的使用情境裡，Claude 做 code review 的效果也更好。

這不代表 Claude 在所有事情上都一定比 Codex 強。重點是：不同來源、不同訓練方式養成的模型，盲點不會完全重疊。

做法 換掉了什麼 仍然保留什麼
同一模型，開新的 review instance 對話脈絡與 session 狀態 相同的模型視角與訓練傾向
改用第二個模型 review 審查者的模型視角 仍需人工判斷 review 結果

Claude 可能看到 Codex 漏掉的問題；Codex 也可能看到 Claude 忽略的地方。兩個模型一起用，價值不在於其中一顆必然比較厲害，而在於它們不完全一樣。

這對實務設計代表什麼？

如果模型要審查自己產出的程式，這個限制不會因為模型變快、提示寫得更長，或 review 跑得更多次，就自然消失。

能真正改變審查品質的，是換掉審查者的視角。對企業或需要穩定品質的團隊來說，為此多保留一筆訂閱、安排另一個模型專門做 review，可能比單純要求同一個模型「再仔細一點」更有價值。

小結：換 instance 是隔離脈絡，換模型才是引入不同視角

Codex review 換掉了對話脈絡，卻沒有換掉模型本身。同一個模型審自己寫的程式，仍然使用同一套訓練與判斷視角，因此同一種盲點可能同時出現在撰寫與審查階段。多跑幾輪不一定能修好這件事；真正需要的是不同視角。實務上，可以保留第二個模型，例如 Claude，來審查 Codex 的產出，而這個模型常常能找到原本漏掉的問題。

把這個觀念掛在前一節旁邊記住：新的 instance 能隔離脈絡；第二個模型則能引入不同視角。知道為什麼需要它之後，下一個問題就變得很具體：在 Codex 裡要怎麼跑 review、要審查什麼、選哪一顆模型，以及遇到授權提示時怎麼處理？
