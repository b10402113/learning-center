跑一次第二模型審查：讓 Claude 審 Codex

Step 3/4 · Code review：Codex review 與第二個模型

當程式碼只是小修小補，多跑一輪 review 可能不值得；但遇到高風險、複雜，或哪裡「怪怪的」的改動，另一個模型就像多請一位同事從旁邊看一次。這一節會帶你在 Codex 裡實際跑一輪第二模型 Claude 的 code review，最後拿到一份 review 結果，再由你判斷哪些建議真的要改。

先確認前置條件

開始前，先確認以下條件。它們會決定你能不能取得真正不同的審查視角。

  1. 你要能叫到第二個模型。 講者的做法是同時訂閱 Codex 和 Claude 兩個方案。若只有一個方案，就只有一顆模型，也就沒有「不同視角」可談。
  2. 要審查的程式碼必須在 git 裡。 你可以審查尚未 commit 的改動，也可以比較目前分支與一條 base branch 的差異。
  3. （可選）準備一個第二模型的 review skill。 講者有一個 Claude code review skill，可以從 Codex 裡叫 Claude 來審查；但這不是必要條件，你不需要為了本節額外安裝它。

步驟 1：先決定要審查的範圍

先選範圍，再下指令。就像請人檢查房子時，要先說是看剛裝好的那扇門，還是整層樓的施工結果。

  • 審查 uncommitted changes：檢查工作區中還沒進 git 的改動。適合「我剛寫完，但還沒整理成 commit」的情況。
  • 審查對 base branch 的差異：以一條基準分支為基準，檢查目前分支多出來的所有 commit。講者更常用這種方式，因為他經常從 worktree 出發，而 worktree 是獨立分支、獨立複本。

如果你是在 worktree 裡完成一整項功能，通常就以 base branch 為基準，讓第二個模型一次看完整條分支。

步驟 2：選擇由誰執行 review

接著決定要用 Codex 自己的 review，還是切到第二個模型，讓它使用自己的內建工具。

路線 A：使用 Codex 內建的 review

留在 Codex 對話裡，直接要求它針對 base branch 進行 review：

code review against a base branch

這樣會得到 Codex 自己產出的 review 結果。

路線 B：讓 Claude 使用自己的內建 review

另外開一個 Claude 視窗，進入同一個目錄，要求 Claude 審查這個 app 最近的一個 commit：

Do a code review on the last commit in this app.
Do not use any Claude custom review skills.
Just use your own internal review tools.

這裡最重要的是最後兩句：明確要求它使用自己的內建 review 工具，不要使用 Claude custom skill。

講者曾遇到一個陷阱：他在 Codex 裡下 review 指令時，Codex 差點改用那支「從 Codex 叫 Claude」的個人 skill。這類 skill 可能被誤觸，所以如果你的目標是讓 Claude 直接執行自己的 review，就要把限制寫進指令裡。

步驟 3：選擇適合的模型

review 是抓錯的工作，不是只要產生一段看起來合理的文字。因此，模型的判斷力比省下幾個 token 更重要。

角色建議模型理由
Codex 做 review直接使用最強的模型講者的做法是把最強的模型直接用上去
Claude 做 reviewOpus；最低 Sonnet；不要 Haiku便宜模型漏掉問題的代價，可能高過省下的 token

講者的原則是：Codex 做 review 時，傾向直接使用最強的模型；叫 Claude 做 code review 時，則使用 Opus，最低也要 Sonnet，絕不使用 Haiku。

原因很直接：如果模型判斷力不足，可能漏掉真正的問題。這樣看似省了 token，實際上卻讓你得到一份不可靠的檢查結果。講者也說，除了最強的模型之外，他還沒有試過其他模型跑 Codex review，因此不替其他組合背書。

步驟 4：處理外部服務授權

第二個模型執行 review 時，可能會跳出提示，詢問是否允許把程式碼送到外部服務。

若你確認這是自己的訂閱與預期操作，就明確允許。這是必要的授權，不是 review 卡住了。講者的做法是告訴它：「可以，你有權把這段程式碼送出去。」

這個提示之所以值得提前知道，是因為它可能讓流程暫停，卻不代表工具發生錯誤。它是在要求你確認程式碼可以送出，只是每次可能都要重新點頭。

步驟 5：讀 review，逐條判斷是否採用

拿到 review 結果後，不要把每一條建議都當成必修作業。第二個模型提供的是另一個視角，不是另一個真相。

講者示範時，第二個模型指出「過期的拍賣出現在 live catalog」、「slug 分配的競態」等問題；但講者當下沒有處理，因為那個 app 根本沒有 slug。換句話說，模型提出了一個與實際程式碼不相符的問題。

讀 review 時，可以逐條確認：

  1. 這個問題真的存在於目前的程式碼嗎？
  2. 它描述的功能或資料，在這個 app 裡真的存在嗎？
  3. 問題的風險是否值得現在處理？

若建議與實際程式碼不符，就不要因為它寫得很肯定而照改。你要把 review 當成待驗證的輸入，最後的判斷仍然在你手上。

什麼時候值得跑第二模型

講者的觸發條件很清楚：只要程式碼有風險、很複雜，或任何地方讓你覺得不對勁，他幾乎一定會叫 Claude 做一次 code review。

反過來，日常的小改動如果風險很低，就不一定值得多跑一輪。實務上常見的流程是：從 worktree 開一條分支完成功能，再以 base branch 為基準，讓第二個模型審查整條分支。

做完後，你應該得到什麼

完成這套流程後，你應該有一份由第二個模型產出的 review，並且能說清楚：

  • 自己審查的是 uncommitted changes，還是對 base branch 的差異。
  • 使用的是 Codex 內建 review，還是第二個模型自己的內建 review 工具。
  • Codex 使用最強模型；Claude 使用 Opus，最低 Sonnet，不使用 Haiku。
  • 遇到外部服務授權提示時，知道那是程式碼外送確認，並能依自己的授權意願處理。
  • 能把 review 建議逐條對照實際程式碼，而不是無條件照改。
流程是：先決定審 uncommitted changes 還是對 base branch；再決定用 Codex 內建 review，或切到第二個模型，使用它自己的內建工具並明確禁止誤觸個人 skill；模型選擇上，Codex 用最強的，Claude 用 Opus，最低 Sonnet，絕不用 Haiku；遇到外送授權就明確允許；最後把結果當成輸入，自己判斷哪些要改。只要程式碼有風險或複雜，就跑這一輪。

你現在已經能穩定取得第二個模型的獨立審查。下一步還有更激進的做法：讓兩個模型多輪互相反駁，直到逼近共識。這種方式可能更有用，但成本也更高；最後一節會協助你判斷，什麼時候值得升級。
