Codex review：不帶對話脈絡的獨立審查者

Step 1/4 · Code review：Codex review 與第二個模型

學習目標

學完這一節，你會知道 Codex review 是什麼、它和一般對話有什麼不同，也能分辨它要審查的兩種範圍，以及如何設定自訂 review 規則。

前言：功能做完了，真的能送出去嗎？

想像一下：你花了一整個下午和 Codex 來回討論，終於把一個功能完成。過程中，你解釋了為什麼不能碰某個舊模組、某個欄位為什麼只能這樣命名，也說明了一段看似奇怪、其實不能修改的程式碼。

現在功能做好了，你想先找人 review，再送出去。最直覺的做法，是回到原本的對話，請 Codex「幫我 review 一下剛剛寫的」。但這樣的審查效果，可能沒有你想像中好。

原本的 Codex 記得你說過的每一句話，也記得它當初為什麼那樣實作。它會沿著你們共同建立的思路閱讀程式碼；那些你「因為知道原因，所以覺得沒問題」的地方，它也容易跟著放過。

真正容易挑出問題的，往往是完全不知道來龍去脈的人。Codex 內建的 review mode 正是在模擬這種情境：它另外開一個不帶目前對話脈絡的 instance 來審查程式碼。這一節先理解這個工具能做什麼；後面三節再處理它為什麼仍然不夠，以及要怎麼補強。

Codex review 是什麼：一位沒參加會議的審查者

Codex review 是專門用來審查程式碼的模式。切換進去後，Codex 會建立一個獨立於目前對話的 instance。這個 instance 看不到目前 session 的歷史，也不知道你「當初為什麼要這樣實作」。它拿到的是一組程式碼差異，接著只根據這些差異進行分析並提出改進建議。

你可以把它想成：把 patch 交給一位沒有參加過會議的資深工程師。會議中的討論、臨時妥協，甚至老闆那句「先這樣上線再說」，他全部不知道；他只看程式碼本身是否站得住腳。

這正是 Codex review 的價值。它不會被你當下的思路牽著走，反而可能挑出那些「只有知道內情才說得通」的寫法。而這些地方，通常也是下一位閱讀程式碼的人最容易卡住的地方。

不過，沒有脈絡也是它的限制。它可能把真正有意為之的設計，誤判成 bug。因此，review 的輸出應該被視為提供判斷的材料，而不是直接下達的判決。你仍然需要根據專案背景確認建議是否適用。

它審查的兩種對象

Codex review 可以針對兩種不同範圍進行審查。實務上，這通常是你首先要選擇的項目：

審查對象它是什麼適合的時機
Uncommitted changes工作區中尚未 commit 的改動想直接檢查目前最新、最原始的修改時
Base branch與一條基準分支比對，審查目前分支領先基準分支的所有 commit建立 PR 前，或從 worktree 開始工作時

第一種可以理解成：「幫我看看工作區裡目前還沒進 git 的這些改動。」第二種則是：「以某條分支為基準，檢查我這條分支多出來的內容。」

講者自己更常使用後者，因為他習慣從 worktree 開始工作。worktree 會建立獨立的分支，甚至可以是整份 git repo 的獨立複本；因此，直接和 base branch 比對，正好符合這種工作方式。

自訂 review 規則：把審查標準固定下來

近期的 Codex 也支援自訂 code review 規則。你可以在 review mode 中指定審查時必須遵守的規則，之後每次進行 code review，Codex 都會依照這些規則檢查。

這看似只是多了一個設定，實際上卻把「審查標準」從每次臨時輸入的 prompt，變成一套可以重複使用、持續累積的規則。過去，你可能每次都要重新提醒：「我們不接受這種寫法」、「這個 pattern 必須使用專案現有的 helper」。現在，這些要求可以集中寫進規則，讓每次 review 自動套用。

這種「用 review 的角度掃描一份內容，找出需要改善的地方」的做法，也不只適用於程式碼。講者提到，同樣的方法可以用來做 repo hygiene（專案整潔）：讓 review mode 掃描整個 repo，找出已經過時、應該移除的文件或 skill。

小結

Codex review 是一個獨立、沒有目前對話脈絡的 instance，專門分析一組程式碼差異並提出改進建議。它可以審查尚未 commit 的工作區改動，也可以審查目前分支相對於某條基準分支的差異；後者特別適合使用 worktree 的工作方式。你還能套用自訂 review 規則，把團隊的審查標準固定下來。同樣的 review 思路，也能延伸到 repo hygiene。

到這裡，你可能會以為「模型自我審查」的問題已經解決了：Codex 開了新的 instance，也不帶原本的對話脈絡，應該就等於換了一雙眼睛。

但新的 instance，不代表新的模型，也不代表真正不同的判斷方式。Codex review 解決的是「不要被原對話牽著走」，下一節要接著看的是更根本的問題：為什麼開一個新的 instance，仍然不等於換了一雙眼睛。
