動手寫一份 AGENTS.md

Step 3/4 · AGENTS.md：把 repo 變成 Codex 的上下文

這一課要完成什麼

這一課會帶你在一個真實的 repo 裡，從零整理出一份可操作的 AGENTS.md。完成後，Codex 會知道專案怎麼啟動、重要檔案各自負責什麼、遇到特定工作該讀哪個 skill，以及完成修改後要怎麼驗證與準備 PR 證據。

動手前，請先準備一個已經有程式碼與 package.json 的 repo。你也需要知道專案平常怎麼啟動、建置和驗證；如果是自己的 side project，直接打開檔案確認即可。

先提醒一件重要的事：AGENTS.md 只能寫真的存在的東西。指令、路徑或套件只要寫錯，Codex 就會拿錯誤資訊當地圖，走得越快，離目的地反而越遠。因此第一步不是建立 AGENTS.md，而是先讀 repo。

一、先讀 package.json，找出真實指令

打開專案的 package.json，找到 scripts 區塊。以課程的 user-insights 專案為例：

"scripts": {
  "dev": "vite --host 0.0.0.0",
  "build": "tsc -b && vite build",
  "preview": "vite preview --host 0.0.0.0",
  "typecheck": "tsc -b --pretty"
}

這裡有四個指令，各自負責一件事：

  • dev：啟動本機服務。
  • typecheck：執行 TypeScript 型別檢查。
  • build：產生正式建置結果。
  • preview：預覽建置後的結果。

同樣要記下「沒有」的東西：這個 repo 沒有測試腳本、格式化腳本或 CI 設定。這不是要補成一份理想清單，而是要如實記錄目前的專案。若你的 repo 需要啟動多個服務，也要在這一步確認啟動順序。

二、寫入 Start here

把剛才確認過的指令整理成 AGENTS.md 的第一個區塊。除了列出怎麼操作，再加上一條防呆規則：沒有配置的東西，不要假裝存在。

## Start here

- Inspect `package.json` before running or claiming a project command.
- Run `pnpm run dev` for the local Vite dashboard.
- Use `pnpm run typecheck` for focused TypeScript verification.
- Run `pnpm run build` before describing a feature as ready for a pull request.
- Do not claim that browser tests, formatting scripts, CI, a Git remote, or a hosted preview exist unless they are actually configured.

預期結果是：Codex 之後需要執行或描述專案指令時，會先回頭檢查 package.json，而不是憑常見專案的印象自行補一個指令。最後一條規則尤其重要，它會擋住模型最容易犯的錯：把「通常會有」誤寫成「這裡真的有」。

三、建立 repository map

接著把 repo 整理成一張地圖。不要試圖列出每個檔案，而是說清楚「哪一類責任由哪裡負責」。這樣 Codex 要修改狀態、資料或樣式時，就不會像第一次進城的訪客一樣到處敲門。

## Repository map

- `src/App.tsx` owns dashboard composition, the selected region, selected cities, and the shared date period.
- `src/components/` contains the globe, analytics cards, geography table, navigation, and live insights rail.
- `src/components/ui/` contains the local card, chart, button, tabs, avatar, and separator primitives.
- `src/data/insights.ts` contains seeded cities and the authoritative region, country, and audience-growth helpers.
- `src/lib/utils.ts` contains class-name and number-formatting helpers.
- `src/index.css` owns the dark theme, visual tokens, analytics-card styling, and responsive breakpoints.

預期結果是：讀完這張地圖，即使是不熟悉 repo 的人，也知道改 dashboard 狀態要先看 src/App.tsx，找資料要看 src/data/insights.ts，調整整體樣式則要看 src/index.css。這些原本只存在於團隊成員腦中的默契，現在變成了可查詢的上下文。

四、設定 skill 路由

如果 repo 已經有 skill，就把「哪種工作要讀哪個 skill」寫出來。AGENTS.md 不需要複製 skill 的完整流程；它比較像路標，負責把工作導向正確的檔案。

## Choose the matching skill

- For a new dashboard card, analytics panel, chart, engagement metric, regional breakdown, table, or compact insight, read and follow `skills/blossomview-card-builder/SKILL.md`.
- Use the skill's `references/dashboard-card-patterns.md` for the existing component, data, chart, styling, and layout contracts.
- Use `assets/active-engagement-card.tsx` only as an adaptable implementation asset, not as a requirement to add that exact card.
- Keep implementation detail in the skill. Do not duplicate its full workflow here.

這裡要先做一個判斷：

  • 若這類工作會反覆出現，而且有固定步驟，例如新增教學或壓縮並上傳媒體，先把流程整理成 skill，再在 AGENTS.md 建立路由。
  • 若只是一次性的規則，就直接寫在慣例區塊，不要為了湊一個路由硬生出 skill。

簡單說，有 skill 才寫路由；沒有 skill 不必勉強建立。

五、寫下程式與設計慣例

這一區要告訴 Codex：新增功能時，哪些東西應該沿用，哪些邊界不能踩過去。寫得清楚，Codex 就會優先使用現成元件與設計系統，而不是重新發明一套。

## Code and component conventions

- Use React, strict TypeScript, and the `@/` import alias.
- Reuse the existing card and chart primitives, `recharts`, `lucide-react`, design tokens, and CSS classes before adding a dependency or a component system.
- Derive region-sensitive content from the filtered `cities` passed down from `App`.
- Keep the interactive globe as the visual focus of the dashboard.
- Preserve existing cards, interactions, keyboard accessibility, meaningful labels, and reduced-motion behavior.
- Make the smallest relevant change. Do not redesign adjacent components.

這段的作用很具體：Codex 要做新 dashboard card 時，會先找既有的 card、圖表 primitives、recharts、lucide-react 和 design tokens。最後兩條則劃出修改邊界：保留既有互動與可及性，並且只做完成工作所需的最小變更。

六、定義 UI 驗證與 PR 證據

接下來把「怎樣才算檢查過」寫成條件。UI 驗證至少要交代要看的視窗寬度、要檢查哪些項目，以及什麼情況算 overflow。PR 證據則要說明截圖種類、命名方式與存放位置，讓視覺變更可以被快速比對。

同時，把 commit subject 與 pull-request title 的格式固定下來：

- Use `(): ` for commit subjects and pull-request titles.

完成後，Codex 就能依規則準備 before／after 視覺證據，並使用像 feat(dashboard): add active engagement card 這樣的標題。審查者不用重新猜測變更範圍，也不用手動拼出比較條件。

七、在規則旁邊補上理由

最後檢查每一條重要規則，看看是否需要補一句「為什麼」。例如，不要只寫「不要重新設計旁邊的元件」，也說明這樣做是為了減少審查負擔，並保留使用者已經熟悉的操作方式。

規則告訴 Codex 要做什麼，理由則幫助它處理沒有被逐字列出的邊界情況。當遇到一個介於「新增功能」和「順手重做整頁」之間的要求時，理由會成為判斷方向，而不只是死背一條句子。

驗證你真的寫對了

  1. 重新檢查 AGENTS.md 裡的每個指令、路徑、套件與檔名，確認它們都能在 repo 中找到對應。
  2. 對 Codex 提出一個普通 prompt，不特別提設計系統或套件名稱。
  3. 觀察它是否會自己尋找既有元件、資料 helper 和相關 skill，並按照 repo 的風格產出修改。
寫 AGENTS.md 的流程是：先讀 package.json，抄下真實指令；再依序寫入 Start here、repository map、skill 路由、程式與設計慣例、UI 驗證和 PR 證據；最後補上規則背後的理由。核心原則只有一個：只寫真的存在的東西，並把「你希望別人理所當然知道」的默契編碼進去。

如果 Codex 能在沒有額外提示的情況下找到正確檔案、沿用既有元件，並產出符合專案風格的改動，這份 AGENTS.md 就已經發揮作用。至於哪些內容應該留在 AGENTS.md、哪些流程應該搬進 skill，會在下一步處理。
