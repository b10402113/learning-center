什麼進 AGENTS.md、什麼進 skill？

Step 4/4 · AGENTS.md：把 repo 變成 Codex 的上下文

先解決一個實際問題：這段內容到底該放哪裡？

你已經知道怎麼寫 AGENTS.md，也看過一份完整的 AGENTS.md 長什麼樣。接下來最容易卡住的地方是：repo 裡有兩個地方都能放知識——AGENTS.md 和專案 skill。同一段內容，究竟該放在哪裡？

這不是整理檔案的偏好問題，而是會直接影響 Codex 的工作方式。放錯位置，輕則每次都載入一大堆用不到的細節，把 context 塞滿；重則 Codex 根本不知道何時該啟用哪個 skill，最後又變成每次各做各的。

你要做的決定很簡單：哪些內容必須每次都知道，哪些內容只有執行特定工作時才需要？

選項比較：三種位置，三種角色

位置角色什麼時候被讀適合放
AGENTS.md政策與地圖進入 repo 就會被讀指令、邊界、慣例、驗證與 PR 規則、skill 路由
SKILL.md導覽Codex 判斷 skill 可能相關時這個 skill 在什麼情況用、要依序讀哪些檔案
references/ 與 assets/細節倉庫真正需要時才去抓深度契約放 references；範例程式與可執行腳本放 assets

這三層是在處理同一個取捨：既要讓 Codex 找得到規則，又不能讓每次工作都背著整套文件到處跑。

AGENTS.md 的優點是「一定會被讀到」。因此，政策、指令和邊界放在這裡最保險。缺點是它會被反覆讀取；如果連大量實作細節也塞進去，每次工作都會帶著一堆這次用不到的內容，context 很快就會變得擁擠。

skill 則剛好相反。它只在 Codex 判斷「這個任務可能用到」時才載入，適合放特定類型的深度細節。但如果你把關鍵規則全藏在 skill 裡，Codex 在還沒決定要不要載入之前，就不知道這些規則存在，可能因此錯過該做的事。

還有一個容易忽略的機制：Codex 一旦覺得某個 skill 可能相關，就會去讀那份 SKILL.md；如果 SKILL.md 本身很肥，這一讀就可能把 context 撐爆。

所以問題不只是「放 AGENTS.md 還是 skill」，還包括「skill 裡面要不要繼續分層」。完整元件範例、圖表設定細節，或一整套 pattern 文件，都不適合直接塞進 SKILL.md。

比較好的做法是：讓 SKILL.md 只保留導覽，深度契約放到 references/，範例程式與可執行腳本放到 assets/。Codex 真的需要時才去讀，像把大型工具放進倉庫，而不是每次出門都整座倉庫扛在身上。

你也可以把範例程式放進 skill 的 assets/，再附一支腳本，等真正要用時才把需要的範例複製進 repo。這樣既提供參考，又不用讓每個讀到這個 skill 的工作都先吞下整包範例。

記住這個原則：skill 提供「怎麼去哪找」，而不是「把所有東西一次攤開」。

判別問句：四個問題幫你做決定

遇到一段內容不知道放哪裡時，不要靠感覺，依序問自己下面四題。

  1. 這是「每次都要遵守的規則」，還是「做某件事才需要的步驟」？前者放 AGENTS.md，後者放 skill。
  2. 這件事會不會重複發生？會重複的工作流程，才值得做成 skill；一次性的規則寫在 AGENTS.md 就好。
  3. Codex 需要在還沒決定要做什麼之前就知道它嗎？例如「哪些資料夾不能動」或「做完要附截圖」。如果需要，就放 AGENTS.md。
  4. 它是深度的實作細節，還是可以直接複製的範例？細節放 references/；範例與腳本放 assets/。

這四題可以把模糊的「應該放哪裡」轉成可檢查的條件：先判斷是否每次都適用，再判斷是否會重複使用，最後才決定 skill 內部要不要拆到更深的層級。

一個好的 SKILL.md：只負責帶路

課程裡的 blossomview-card-builder 就是這種分層方式。它的 SKILL.md 本體很短，開頭直接把工作拆成「先讀哪些檔案，再決定要做哪種卡片」，像一張路線圖：

## Start with the existing system

1. Read `src/App.tsx` to locate the existing dashboard state and the two card placement options.
2. Read `src/components/ui/card.tsx` and reuse `Card`, `CardHeader`, `CardTitle`, `CardDescription`, and `CardContent`.
3. Read `src/components/audience-chart.tsx` and `src/components/geographic-table.tsx` for full-size analytics cards, or `src/components/insights-rail.tsx` for a compact sidebar section.
4. Read `src/data/insights.ts` and `src/lib/utils.ts`. Derive metrics from the existing `UserCity[]`, `getCountryTotals`, `getGrowthData`, `compactNumber`, and `preciseNumber`.
5. Read the relevant `.analytics-*`, `.rail-*`, and breakpoint rules in `src/index.css`.

這段內容幾乎沒有解釋原理，而是清楚列出「接下來該看哪些檔案」。深度的 component、data、chart contract 放在同一個 skill 的 references/dashboard-card-patterns.md；完整的範例卡片則放在 assets/active-engagement-card.tsx。

這就是三層分工：SKILL.md 負責指路，references/ 負責保存深度細節，assets/ 負責保存可以取用的範例與腳本。context 只有在需要時才展開。

反例：規則會翻轉的三種情況

第一，簡單的小專案不必硬拆。

如果 repo 只有一兩個人使用，工作也不太重複，把所有說明放在 AGENTS.md 就好。課程講者在示範 user-insights 時也提到，這種簡單專案通常不需要把每一件事都拆進 AGENTS.md 的不同區塊；那些分層設計主要是給「難以理解、需要上下文」的大型生產系統使用。

如果硬拆出一堆 skill，維護的檔案變多，找規則反而更麻煩。分層是為了降低複雜度，不是為了讓目錄看起來更專業。

第二，需要 repo 內真實元件的 skill，應該放在專案裡。

像 screenshot-to-component 這種 skill，需要取用該專案真正使用的元件與設計系統，因此應該放進 repo 內，讓所有貢獻者共用同一套內容。

相反地，和特定 repo 無關、你在每個專案都想使用的個人習慣，才適合放到使用者層級。判斷重點是：這個 skill 是否依賴某個專案的真實檔案與規則。

第三，把所有細節貼進 SKILL.md，會得到反效果。

Codex 只要覺得這個 skill「可能相關」，就會讀取 SKILL.md。如果整份深度文件都塞在裡面，一次可能只是試探性的載入，就會吃掉大量 context。

正確做法是保持 SKILL.md 精簡，把重量移到 references/ 與 assets/，讓 Codex 在確定需要時才讀取。

最後的決策規則

政策與地圖放 AGENTS.md，可重複的流程放 skill。skill 內部再分三層：SKILL.md 只當導覽，深度契約放 references/，範例與腳本放 assets/，需要時才去抓。判準是：每次都要遵守 → AGENTS.md；重複發生的工作 → skill；只是深度細節 → references；可複製的範例 → assets。簡單專案不必硬拆。

你可以用這份檢查表替自己的 repo 做最後判斷：

  • 每次進 repo 都要知道的政策、邊界與驗證規則：放 AGENTS.md。
  • 只有執行某類重複工作時才需要的流程：建立 skill。
  • skill 的用途與檔案閱讀順序：放 SKILL.md。
  • 需要深入查閱的契約與 pattern：放 references/。
  • 可以複製、執行或套用的範例：放 assets/。
  • 如果專案很小、工作不重複：先不要硬拆。

沿著這四步，你就能把上下文寫進 repo、寫出 AGENTS.md，再把政策與流程分到正確的位置。找一個自己的 side project，依照這份規則做一次，讓 Codex 能自己找到該遵守的規則與該載入的細節。
