讓 repo 自己說故事：把上下文寫進版本庫

Step 1/4 · AGENTS.md：把 repo 變成 Codex 的上下文

這一課要解決什麼問題？

當團隊開始用 Codex 寫程式，最常見的麻煩不是程式跑不起來，而是「看起來能跑，卻不像這個專案會寫出來的東西」。它可能重新刻一套卡片元件、引入另一個圖表套件，或自行發明一種資料格式，明明旁邊早已有現成的做法。

這時工程師只好在 PR 裡逐項糾正，甚至覺得自己重寫還比較快。問題未必是 Codex 不夠聰明，而是 repo 沒有告訴它：「我們在這裡通常怎麼做事。」

這一課要建立的觀念很簡單：把原本藏在資深工程師腦中的默契，搬進版本庫，讓 Codex 找得到、讀得懂，也能在下一次工作時沿用。

共享 repo 的真相：它不是「你的」repo

想像一個已經運作好幾年的網站 repo。裡面有自己的設計系統、圖表套件和資料夾慣例，但這些規則沒有集中寫在任何文件裡，而是散落在幾位資深工程師的記憶中。

某天，一位設計師想加一個小功能，請 Codex 直接產生程式碼。Codex 很快交出一份可以執行的實作，看起來也沒有明顯錯誤。可是工程師打開 PR 後，發現這份改動像是來自另一個專案：它自己做了卡片元件、自己拉進新的圖表函式庫，還自行決定資料格式，完全沒有使用 repo 裡原本的工具。

這就是共享 repo 的第一個現實：除了你以外，還有其他人會對同一份程式碼做修改。第二個現實則是，你不一定擁有完整上下文。你可能不知道某個資料夾為什麼這樣命名，也不知道團隊為什麼不用某個看似熱門的套件。

過去沒有 AI 時，這些缺口通常靠人來補：口頭說明、PR 留言，或讓新人慢慢摸索。雖然速度不快，但至少做決定的人通常知道背景。

Codex 不一樣。它讀不到別人的腦，只能讀 repo 裡的檔案、指令、設定與文件。沒有寫下來的規則，對它而言就像不存在。

因此，對 Codex 來說，repo 就是唯一的共同真相（ground truth）。與其說 Codex「不守規矩」，不如先問：這些規矩是否真的被寫進 repo，讓它有機會遵守？

沒有把上下文寫下來，會發生什麼？

Katia 在課堂上提到一個具體例子。OpenAI 的開發者網站一開始沒有把太多上下文編碼進 repo，許多規則只留在工程師腦中。有位設計師想加功能，便用 agent 產生程式碼，結果建立了一批新元件。

那份 PR 的問題不一定是功能不能用，而是它沒有接上原本的專案。工程師必須花大量時間說明哪些元件已經存在、哪些工具應該重用，以及為什麼這裡不能再發明另一套做法。最後，審查這份改動甚至比工程師自己從零重做還慢。

原因在於，缺乏上下文時，Codex 很容易把 repo 的其他部分當成不存在。它會用最直覺、最通用的方式補上空白，於是同一個 repo 逐漸出現兩套卡片、兩種圖表風格和兩種資料處理方式。

每個人都能貢獻，表面上像是效率提升；但分歧最後會集中到工程師身上，全部變成 review 負擔。工程師就像唯一能通過的窄門，整個團隊被卡在審查瓶頸。

這裡還有一個容易忽略的責任歸屬：從技術角度看，工程師必須負責把這些判斷標準寫進 repo。當「為什麼這個 PR 看起來不對」只能靠現場解釋，就代表團隊的標準還沒有被編碼成 Codex 能使用的上下文。

理想狀態：不用一直問人，也能正確貢獻

反過來看，理想的 repo 應該讓不同角色都能在不反覆詢問工程師的情況下完成合理的修改。OpenAI 現在讓產品經理、設計師、專案經理與成長團隊都能貢獻程式碼。他們可以先在產品裡做原型，工程師仍然會審查成果，但不必從頭補充整個專案的背景。

關鍵在於，repo 裡已經放了足夠的知識，Codex 找得到，也能在實作時使用。這些知識主要放在兩個位置：

放置位置負責內容例子
AGENTS.md（專案指令）專案層級的政策與指令，例如有哪些指令、該使用哪個 skill、repo 如何分區，以及要遵守哪些慣例與驗證規則「修改前端前先讀這兩個 skill」、「先看 package.json，再聲稱可用哪些指令」
專案 skill可重複的工作流程與實作細節，例如某類功能要怎麼做、要讀哪些檔案，以及必須遵守哪些資料契約「新增一張 dashboard 卡片」的完整流程

還有兩塊地基也需要刻意經營。

第一是可重用的 helper 與工具。如果更新資料庫、清除快取等操作已經有現成函式，Codex 就能直接使用，而不是另外想一套做法。

第二是清楚的設計系統與元件。當 repo 裡有明確的元件庫，Codex 就比較會沿用既有設計，而不是重新發明輪子。

把這四者放在一起看，它們其實都在實現同一個原則：凡是你希望別人理所當然知道的事，都要寫進 repo。

對熟悉專案的人來說，這些規則可能自然得不需要解釋；但對沒有背景的人，尤其是平常不接觸生產系統最佳實務的人，它們一點也不理所當然。Codex 面對的正是這個落差，因此必須由 repo 把缺少的上下文補上。

把 repo 想成新人的第一天

你可以把 AGENTS.md 想成新進員工第一天拿到的工作手冊。

一本好的手冊不會從「什麼是程式」開始教起，而是直接說明：「在這個團隊裡，要完成這件事，我們通常這樣做。」它會列出常用指令，指出不同模組的位置，說明命名與風格慣例，也會交代送出 PR 前要執行哪些檢查。

差別只在於，這本手冊的讀者現在換成 Codex。它不需要人情世故，而需要可以直接執行的規則：指令要是真的，路徑要正確，慣例要能套用。

所以，AGENTS.md 不是一份裝飾性的說明文件，而是把團隊默契轉成 Codex 能使用的專案上下文。它和 skill、helper、設計系統彼此接在一起，共同回答一個問題：這個 repo 已經知道什麼，以及新的貢獻應該如何接上既有的知識。

小結

在共享 repo 裡，Codex 只看得到 repo，因此 repo 就是它唯一的共同真相。沒有被寫下來的知識，Codex 就可能自行發明一套做法，最後把分歧轉成工程師的 review 負擔。把專案政策寫進 AGENTS.md，把可重複流程寫進 skill，再提供可重用的 helper 與清楚的設計系統，才能讓更多人安全地貢獻程式碼。

這個觀念也替後面的內容掛上一個位置：AGENTS.md、skill、helper 和設計系統不是各自獨立的文件或工具，而是同一套「把團隊知識寫進 repo」的方法。下一課會拆開一份真實的專案 AGENTS.md，看看它包含哪些區塊、每個區塊在回答什麼問題，以及 Codex 如何決定要讀哪一份。
