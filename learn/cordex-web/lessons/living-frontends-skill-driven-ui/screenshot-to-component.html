動手做 screenshot-to-component：把截圖重建成可編輯的元件

Step 3/4 · Living frontends：skill 驅動的介面

學習目標

能寫出一段 prompt 讓 Codex 用 skill creator 產出 screenshot-to-component skill，並說出驗收它做對了沒有的檢查點。

前言：那些每改版一次就要重截的插圖

上一課看到，網站上的插圖如果是一張張截圖，只要介面一改版，它們就全部過期，你得一張一張重截。這個問題在 Codex 這種「介面一直在變」的產品上特別痛：你今天才重截好一批，過兩週新功能上了，圖又不對了。screenshot-to-component 這個 skill 就是為了這件事而做：它把一張截圖重建成「真正的元件」，之後介面改版，元件會自己跟上，而不是變成另一張等著被淘汰的圖。

這一課要動手做的是「產出這個 skill」。我們不是自己手寫它的實作，而是寫一段 prompt，請 Codex 用 skill creator 把這個 skill 建出來。做完之後你會得到一個住在專案裡的能力：任何人丟一張截圖進去，它都能把那張圖重建成可編輯的元件。

動手前需要具備什麼

這個 skill 之所以能做得「像」，是因為它可以去看專案裡真正的元件。所以動手前，你需要的東西如下：

  1. 一個已經有設計系統的專案。例如一個像 User Insights 那樣、有現成元件、樣式與設計 token 的 repo。skill 要能去讀這些東西，才複製得像產品的一部分。
  2. skill creator。它是一個「用來產生 skill 的 skill」，負責幫你把新 skill 的名稱、描述、位置與結構搭好。
  3. 一張真實的截圖。驗收時要用真的圖片測，不是用示意圖。
  4. 專案的驗證指令。例如 typecheck 與 build，做完要拿它們確認沒有改壞東西。

前置條件裡最重要的其實是第一個。沒有可重複使用的元件與樣式，這個 skill 的重現度會明顯下滑，因為它沒有真實的東西可以對照，只能靠自己猜。

步驟一：把 prompt 寫清楚，交給 skill creator

整個做法的主體就是一段 prompt。它要交代四件事：用哪個工具做、skill 叫什麼、它該怎麼運作、以及做完要通過哪些檢查。課程裡用來產生這個 skill 的 prompt，原文如下：

Use $skill-creator to make a skill called screenshot-to-component for the User Insights project. The idea is that when I give Codex a screenshot, it should recreate that UI as an editable React illustration.

Before it builds anything, it should look through the User Insights code and reuse the actual components, styles, tokens, and icons from the site so the result feels like part of the product instead of something copied from scratch. It should build real UI rather than putting the screenshot on the page, and the result should be responsive, accessible, and easy to edit. Put the skill in user-insights/skills/screenshot-to-component, test it with one real screenshot, and run the project's typecheck and build commands.

這段 prompt 不長，但每一句都在拆掉一種失敗模式。下面把它的要求逐條拆開，說明「如果不講，會發生什麼事」。

步驟二：指定要重用真正的元件與樣式

prompt 裡有一句是硬性要求：在建任何東西之前，skill 必須先翻過 User Insights 的程式碼，重用網站裡真正的元件、樣式、token 與圖示，讓成果感覺像產品的一部分，而不是從頭複製出來的東西。

這句為什麼重要？因為不講清楚，Codex 很可能自己發明一套元件來畫那張截圖。它畫出來的圖可能「看起來對」，但用的字型、間距、顏色都跟產品不一樣，整體就像外包做的插圖，放在頁面上會一眼看出是外來的。「重用而不是重造」是這個 skill 能不能融入產品的分界線。

步驟三：強調要做「真的 UI」，不是把圖貼上去

下一句是：要做出真正的 UI，而不是把那張截圖放到頁面上。這是在堵一個偷懶的做法：直接把你給的截圖當成圖片貼上去，看起來最快，但那還是一張圖，不能改、不能響應、不會跟著主題變，等於完全沒有解決問題。

真正要的是把截圖「翻譯」成程式碼：用元件、用樣式把它重新組出來。這樣出來的東西才是活的。

步驟四：要求響應式、可存取、好編輯

prompt 接著開出三個品質條件：成果要 responsive（響應式）、accessible（可存取）、easy to edit（好編輯）。這三個不是隨便加的裝飾，而是「元件」相對於「圖片」的全部好處所在。響應式讓它換到不同螢幕寬度時會自己重排；可存取讓它對螢幕閱讀器與鍵盤操作也友善；好編輯則意味著它是真的程式碼，你可以直接進去改。

步驟五：指定落點，並用真實截圖驗收

最後一句把交件條件講死：skill 要放在 user-insights/skills/screenshot-to-component，用一張真實的截圖測試它，然後跑專案的 typecheck 與 build 指令。這裡有三個檢查點：位置對不對、用真圖測過沒有、專案有沒有被改壞。少跑 typecheck 或 build，你就不知道這個新 skill 有沒有在專案裡留下問題。

做完之後，它實際跑起來長什麼樣

skill 建好之後，真正的用法是：你把一張截圖丟進去，它就去讀 Codex app 的程式碼、把截圖當成「方向」，再把圖重建成一個真正的 HTML 元件。它的邏輯不是照著圖片描邊，而是「我看著產品真正的程式碼，加上你給的方向，重新用元件把它組出來」。

驗收的畫面大概是這樣：整個網站上的插圖都變成了 HTML 元件。你可以直接對它下指令，例如請它把畫面上某個分支的名稱改成「Codex Updates」，改了之後，排版會跟著重新流動，這就是它「響應式」的證據；切換主題時，它也會自動換色。甚至連構圖都可以用程式碼控制，比如請它把某一塊放到另一塊前面，而那些全都是元件，不是拼貼的圖片。

一句話：以前要一張張手動重截的插圖，現在變成一組會自己跟上介面變化的元件。

小結

screenshot-to-component 的產出，就是一段寫清楚的 prompt：叫 skill creator 在 User Insights 專案裡做一個同名 skill，要求它先讀過專案、重用真正的元件與樣式，把截圖重建成「真的 UI」而不是貼上去的圖，並確保它響應式、可存取、好編輯；最後指定放進 user-insights/skills/screenshot-to-component，用一張真實截圖測試，並跑 typecheck 與 build。做完的成果，是網站上原本一張張會過期的截圖，變成一組會自己跟上介面的元件。前提是那個專案裡真的有元件可以重複使用。

會做不等於該做。下一步要處理的是取捨：什麼樣的東西值得從靜態插圖改成活元件、什麼時候維持靜態就好，以及這些互動未來要怎麼曝露給使用者與 browser agent。
