grill-with-docs：把決策寫進 context.md，切成能驗收的功能

Step 3/5 · Plan mode 與 grilling：逼出決策

學習目標

這一節會帶你看懂 grill-with-docs 如何把 grilling 與 domain modeling 串在一起，最後留下三種可以交接與驗收的產出：context.md、Mermaid 流程圖，以及垂直切片。

先解決一個麻煩：談好的決策會消失

想像你和 Codex 花了一輪 grilling，把一棵決策樹走到底，每個問題也都得到明確答案。可是，這些答案如果只存在對話裡，對話一旦被壓縮、換了 session，或交給隔天接手的同事，原本的共識就可能全部不見。

模型又回到「什麼都不知道」的狀態。你先前花力氣逼出的決策，像寫在沙灘上的字，下一個浪打來就消失了。

因此，grilling 不能只停在提問與回答。它還需要下半場：把決策寫成之後查得到、接手得了的文件。這正是 grill-with-docs 要處理的事。它把訪談結果留下來，並進一步整理成流程圖與可實作的工作切片。

grill-with-docs：把提問和記錄綁在一起

grill-with-docs 可以看成一個組合技。它的核心做法是：使用 domain modeling（領域建模）skill，來執行一場 grilling session。

它不是重新發明一套問答方式，而是把 grill-me 負責的追問，和 domain modeling 負責的記錄接在一起。你不需要自己記得「先 grill，再整理文件」這兩個步驟；呼叫 grill-with-docs 後，它會把這條流程串起來。

這也顯示了 skill 的一個重要特性：一個 skill 可以呼叫其他 skill。被呼叫的 skill 甚至可能繼續使用工具、讀取檔案系統，或再呼叫其他 skill。對使用者來說，你只要指定想完成的工作，不必親自維護每個內部步驟。

domain modeling 的工作：把商業詞彙寫進 context.md

domain modeling 會把 grilling 中出現的重要概念，整理到一份叫作 context.md 的檔案。這份檔案記錄的不是程式碼，而是商業術語與商業需求：那些模型在後續工作中應該持續記得的規則。

你可以把 context.md 想成一份功能的設計契約。它會釐清這類問題：

  • 什麼叫「一場拍賣」？
  • 「出價」遵循什麼規則？
  • 誰是賣家，誰是買家？
  • 金額使用什麼單位？

這些定義如果只留在對話中，很容易隨著 context 壓縮或 session 更換而遺失；一旦寫進檔案，就能跨過這些限制。下一位接手的人，或下一個 Codex session，只要讀取這份文件，就能接回先前建立的共識。

所以兩者的分工很清楚：grill-me 負責把決定問出來，domain modeling 負責把決定記下來。一個負責問，一個負責記。

順帶產出的兩樣東西：流程圖與垂直切片

完成 grilling 後，Codex 通常會再把對系統的理解整理得更具體，產出 Mermaid 流程圖與垂直切片。

Mermaid 流程圖：把抽象計畫攤開來看

Mermaid 是一套用文字描述流程圖的語言，模型很適合產生這種圖。以課程示範的拍賣網站為例，流程圖會呈現這些關係：

  • 前端的啟用使用者，以及頁尾的使用者切換器，會把選擇存進 local storage。
  • 其他請求會送進 Fastify API。
  • API 處理 users、auctions，以及被接受的 bids。
  • 最後資料會落到 Postgres 的 auction part two 資料庫。

單看文字計畫，這些關係可能要在腦中拼湊；流程圖則像把電路板攤平，資料從哪裡流到哪裡一眼就能看見。

垂直切片：每一段都能端到端跑起來

另一項產出是「垂直切片」（vertical slices）。它不把工作切成「先做完全部後端，再做全部前端」的橫向分層，而是切成一個個可以從頭跑到尾的功能片段。

以這個拍賣網站為例，切片可能依序是：

  • 由資料庫驅動的市集與使用者切換。
  • 貼出拍賣。
  • 出價，以及檢視出價。

每個切片都能單獨展示進度，也方便逐段驗收。你先確認這些切片代表正確的產品範圍，再進入實作；這比先把整個後端蓋完，最後才發現方向不對，更容易控制。

為什麼要把決策前移：確定性與 back pressure

把整條流程串起來看，grill-with-docs 的目標很簡單：在開始建造之前，先確定要建造的是什麼。

人們和 LLM 協作時常說的「漂移」，不一定代表模型能力不足。很多時候，是因為有些事情一開始根本沒有被說清楚，模型只好自行補完，接著做出你沒打算要的選擇。

把決策前移，就是先在動手之前處理這些模糊處。接著，domain modeling 把決策寫進 context.md，讓文件成為後續工作的約束。這種約束就是 back pressure（反向壓力）：模型之後的行為會受到已經記錄的規則限制，不容易又飄到另一個方向。

因此，完整的 grilling 不是「問完就算了」，而是依序形成一條連結：先透過訪談逼出決策，再把決策寫成文件，最後才根據文件切成可以實作與驗收的功能。

把這個觀念掛回整體流程

grill-with-docs 是一個複合 skill：它使用 domain modeling 來執行 grilling，把商業術語與需求記進 context.md，補上「談完就忘」的缺口。它也會產出描述系統流向的 Mermaid 流程圖，以及可以端到端驗收的垂直切片。整套流程的目的，是把決策前移並寫成文件，讓你更確定要建造什麼，也讓這些紀錄對模型形成 back pressure。

到這裡，你可以把 grilling 理解成一個有前後兩半的機制：前半段負責把模糊處問清楚，後半段負責讓答案留下來，並轉成可視化、可驗收的工作範圍。下一節會把這套觀念落到實際操作：安裝相關 skill，對真實功能發起 grilling，並在兩輪內收斂出決策。
