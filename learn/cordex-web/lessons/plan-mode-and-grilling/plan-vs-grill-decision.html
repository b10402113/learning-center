該用 plan mode，還是 grilling？

Step 5/5 · Plan mode 與 grilling：逼出決策

做新功能時，真正棘手的往往不是「怎麼寫」，而是「哪些事情還沒決定」。如果方向已經清楚，只需要整理實作輪廓，原生 plan mode 通常就夠了；但如果金額單位、權限規則或結標方式都還有分叉，太早開工，之後很可能得拆掉重做。

Codex 提供兩種「先別急著動手」的方式：原生的 plan mode，以及會持續追問的 grill-me／grill-with-docs。前者速度快，後者會逼你把設計決策說清楚。這一節的目標，就是在兩者之間做出合適選擇，並知道什麼時候該停手。

先看兩者差在哪裡

可以把它們想成兩把刀：plan mode 適合快速削出輪廓，grilling 則像把設計拆成一層層的岔路，確認每個分叉都有人做決定。

面向原生 plan modegrill-me／grill-with-docs
身分Codex 內建功能另外安裝的自訂 skill

對抗漂移有限，討論共識未必會留下較強，決策會被寫下來，繼續約束模型

真正的差異，不是「有沒有計畫」，而是決策被逼出來的程度，以及這些決策有沒有被留下來。plan mode 比較像整理已知資訊；grilling 則是挖出你還沒想清楚的未知。

判別問句：先問自己四件事

不用死背整張表。開工前，依序問自己下面四個問題：

  1. 這個功能是否還有沒決定的產品或領域分叉？例如金額使用哪種單位、誰有權限執行某個動作、結標要怎麼計算。只要有一個答案尚未確定，就值得使用 grilling。
  2. 如果某個假設錯了，回頭修改的代價高不高？資料表結構和 API 契約一旦定下來，改動通常會牽動很多地方。這類高代價決策，適合先追問清楚。
  3. 這些決策是否需要留下紀錄，供不同 session 或其他同事使用？如果未來需要查閱或接手，就應該使用 grill-with-docs，把決策寫進 context.md。
  4. 我現在是否願意花兩輪時間回答問題？grilling 的成本不只是模型運算，而是你本人必須下場思考。如果現在沒有這個時間，就不要假裝自己正在做 grilling。

如果四題的答案都偏向「沒有、不高、不需要、不願意」，那麼使用 plan mode，甚至直接開工，都可能更有效率。只要有兩題以上偏向「有、高、需要、願意」，grilling 通常就是更划算的選擇。

反例：規則什麼時候會翻轉

plan mode 並不是不值得用。當功能方向已經明確，只是想先整理出實作輪廓時，它快速又省事。問題在於把它拿來處理尚未釐清的產品決策：模型可以替你整理已知內容，卻不一定會主動逼你面對所有設計分叉。

grilling 也不是越多越好。拿它處理改一個按鈕顏色這類小改動，兩輪問完，你可能只是回答一堆原本就沒有疑問的問題。

另一個失敗模式是追問過度。問到第三輪時，人容易開始疲乏，最後亂答，甚至直接選擇「全部採用建議」。這等於把設計權整包交回模型；如果最後會變成這樣，一開始使用 plan mode 反而更誠實、更有效率。

還有一點容易被忽略：grilling 不只適用於新專案。它同樣可以用在既有的 codebase，也就是棕地專案，因為它會讀取 repo 裡的檔案。因此，「這是舊專案」不是跳過 grilling 的理由；真正要看的，仍然是前面的四個判別問題。

用了 grilling，什麼時候停手？

選擇 grilling 之後，還要替自己設一個煞車。實用的停手規則是：最多跑兩輪。

第一輪處理主要決策，第二輪補上第一輪延伸出的細節，接著就進入實作。停手不是偷懶，而是因為「夠好的設計」通常比「窮盡所有可能的設計」更能讓工作真正開始。之後如果在垂直切片中遇到新的決策，再針對那個局部問題重新叫一次 grilling 即可。

把選擇收斂成一句規則

看兩件事：決策分叉的密度，以及錯誤假設的代價。功能小、方向明確、決策瑣碎，就用原生 plan mode，甚至直接開工；功能存在真正的產品或領域分叉、改錯代價高，而且決策需要留下紀錄，就用 grill-me／grill-with-docs。使用 grilling 時最多跑兩輪，絕不要用「全部採用建議」代替自己的判斷。

當場可以直接套用這個檢查句：只要有一個設計問題我答不出來，就用 grilling；一個都沒有，就用 plan mode 或直接開工。兩者沒有誰比較高級，只有是否用在正確的場合。
