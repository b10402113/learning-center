原生 plan mode：先定義，再動手

Step 1/5 · Plan mode 與 grilling：逼出決策

學習目標

完成這一節後，你應該能說明原生 plan mode 在解決什麼問題、它和直接開工有何不同，以及為什麼光靠它仍然不夠。

前言：那個「先做再說」的下午

你對 Codex 說：「幫我把拍賣網站加上貼文拍賣的功能。」話才送出，它就開始修改檔案。等你回過神，資料表已經長了一半，欄位命名和你的想法不同，圖片處理方式也不是你要的。

你想喊停，卻發現錯誤的假設早已寫進程式碼。接下來不是單純補一個欄位，而是得回頭拆掉一串建立在錯誤方向上的修改。

需求很明確時，「先做再說」可能不會出問題。但需求一旦模糊，每個沒想清楚的決定都可能變成之後要拆掉的東西。Codex 內建的 plan mode，就是用來先踩煞車的。

這一節先看懂它怎麼運作、解決了什麼問題，以及為什麼它仍然需要另一種更會追問的方法。

plan mode 是什麼：先把功能說清楚

在 Codex 裡輸入 /plan，對話框下方會出現 plan mode 的提示。進入這個模式後，Codex 的任務不是立刻修改程式，而是先把你想做的功能定義清楚。

換句話說，你現在不是要它「建置功能」，而是要它先回答：「這個功能到底包含什麼？」

可以這樣對比：

模式 主要工作
一般對話 定義需求並開始建置
plan mode 先定義需求，暫時不建置

它把「思考」和「動手」切成兩個階段：先整理出計畫，讓你確認方向；等你接受後，才進入實作。

這看似只是多了一個流程關卡，實際上擋住了模型一個很危險的行為：一邊猜、一邊改。否則早期還沒有把握的假設，很容易直接變成程式碼的一部分。

它解決了什麼問題

先想像沒有 plan mode 的情況。當 Codex 直接開工，它必須在寫下每一行程式的同時，替所有尚未討論的細節做決定：

  • 資料要怎麼儲存？
  • 誰可以看見資料？
  • 時間要怎麼計算？
  • 操作失敗時要怎麼處理？

這些決定不一定會先拿來問你。Codex 可能會自行選一個看似合理的答案，然後繼續往前寫。等你看到結果時，往往已經有好幾十個決定疊在一起。只要其中幾個和你的想法不同，就可能得回頭大改。

plan mode 做的事，是把這些決定往前搬。它先把預計要做的內容整理成一份計畫，攤在你面前。你可以逐項確認、提出修改，等方向一致後再讓它動手。

因此，當你「大概知道想要什麼，但不想讓 Codex 自作主張」時，plan mode 很有用。它像施工前先攤開的藍圖：即使還沒蓋房子，你也能先看出房間是不是放錯位置。

為什麼它還是不夠

不過，使用幾次後你可能會遇到另一個問題：計畫看起來很完整，你也按了接受，實作到一半卻發現，某個最關鍵的決策從頭到尾都沒被討論。

問題不一定出在計畫整理得不好，而是 plan mode 問得不夠多。

它能產出一份條理分明的計畫，卻不一定會像設計評審那樣，把需求裡沒說清楚的地方一個個挑出來，逼你做選擇。它比較像一位可靠的祕書：會把已知事項整理成議程，但不會主動追問你為什麼漏掉某個議題。

這裡的風險在於，一份「看起來完整」的文件，很容易讓人誤以為設計已經完成。那些沒有被問到的分叉，仍然存在，只是被推遲到實作階段才爆開。

所以，plan mode 的角色可以這樣記：

它擅長的事 它不擅長的事
整理已知需求 找出你沒想到的問題
把決定往實作前移 逼你處理所有設計分叉
降低邊想邊改的風險 保證計畫沒有遺漏關鍵決策

小結：它是煞車，不是完整的設計評審

原生 plan mode 是 Codex 內建的「定義模式」。輸入 /plan 後，先讓 Codex 把功能講清楚、暫時不要修改程式，避免需求模糊時邊猜邊改，讓錯誤假設直接固化進程式碼。

但 plan mode 主要整理已知內容，不一定會主動追問那些尚未決定的關鍵問題。因此，對單純、方向已經明確的功能，它可能已經夠用；對充滿設計分叉的功能，光有一份計畫仍然可能把不確定性推到實作階段。

把 plan mode 想成施工前的藍圖檢查，就能記住它和後續工具的關係：它先阻止 Codex 太早動工，但不負責把所有設計問題問到底。下一步要看的 grill-me skill，正是用更像設計評審的方式，沿著決策樹追問，補上 plan mode 留下的空白。
