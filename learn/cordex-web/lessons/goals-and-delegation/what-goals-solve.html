/goal 解決什麼問題：為什麼 Codex 做一輪就停

Step 1/4 · Goals：把需要長時間打磨的工作交給 Codex

先看它解決了什麼問題

想像你請 Codex 做一個滾動式的 3D 網頁體驗。十幾分鐘後，它回報完成。你打開一看，整體確實成形了，卻發現精靈物件會在星球正中央突然淡出，切換城市時動畫也不夠順。

它不是把事情做壞了，而是把「做出一版能跑的東西」當成了完工。可是你真正想要的，通常不是第一版，而是持續修到某個品質標準為止。

這種需要反覆檢查、修正、再檢查的工作，就是 /goal 要解決的問題。本課先釐清它為什麼存在：一般 prompt 為什麼常常只換來一輪輸出，而 goal 又如何讓 Codex 持續工作，直到驗收條件成立。

一般 prompt：做一輪，然後把控制權交還給你

平常使用 prompt 時，Codex 的節奏很像一問一答：

  1. 你交代一個任務。
  2. Codex 規劃並動手執行。
  3. 它回報目前結果。
  4. 接著停下來，等你告訴它下一步。

對「一次就會對」的小事，這種節奏很方便。但真實工作往往不是一次就能完成。3D 動畫的流暢度、不同裝置上的版面、需要反覆測試的整套遷移，通常都要第二次、第三次 prompt。每次你都得再提醒它：「還沒好，繼續修。」

課程中的示範很能說明這件事。同一個對話持續跑了十分鐘，Codex 不斷開啟瀏覽器、點擊畫面、截圖，再反覆檢查結果。它不是突然變得特別勤奮，而是那次 prompt 清楚寫出了品質要求，還特別提醒它：要實際查看畫面，不能只因為程式碼能編譯，就把工作當成完成。

真正讓它願意多跑幾輪的，不是把 prompt 寫得更長，而是先說清楚什麼才算做好。

/goal：把停止條件交給驗收結果

/goal 是讓 Codex 專注在最終結果上的工作模式。你需要交代兩件事：

  • 要完成什麼事情。
  • 用什麼驗收條件判斷可以停止。

於是，Codex 的工作方式會從「我做了一版，現在回報」變成「我會繼續修改，直到能驗證條件成立」。它會一輪一輪地執行、觀察與修正，直到結果達到你定義的門檻。

可以把兩者想成不同的委託方式：一般 prompt 是請工班「蓋一面牆」；/goal 則是請工班「蓋到通過這份驗收清單為止」。差別不只在工作量，而在於你把「什麼時候算完」的判定方式也交代清楚了。

互動節奏做一輪後回報持續循環，直到達標
什麼時候停止Codex 認為自己做完了驗收條件成立
適合的任務一次就能完成的小事需要多輪打磨的長工
執行中能否調整—可以中途送出新的 prompt

這裡也要先排除一個常見誤解：/goal 不是「丟出去就不管」。它在執行期間仍然可以接受新的 prompt。你可以觀察進度，發現方向不對時介入修正；它不是完全碰不到的黑盒子，而是一個會持續工作的對話階段。至於如何監督與調整，會在本節最後一課再談。

驗收條件可以是一條門檻，也可以是一張清單

前面 3D 體驗的例子中，停止條件包含許多具體要求：

  • 手機、平板與桌面等不同 viewport 都看得到地球。
  • 轉場維持順暢。
  • 地球標記清楚可見。
  • 鍵盤焦點的移動行為正確。

這些要求合在一起，就是驗收條件。它不一定要是一個簡短、單一的數字，也可以是一份需要逐項確認的檢查清單。對視覺與互動品質來說，清單往往比一句「做得漂亮一點」更有用，因為 Codex 知道自己要實際檢查哪些地方。

另一種形式，是把評估資料當成驗收條件。假設你正在製作一個回答使用者問題的網站，可以先準備一組「問題加標準答案」的資料。標準答案由熟悉領域的人撰寫，再交給另一個 LLM 擔任裁判，判斷每個回答是否達標。

這時，goal 可以寫成：「至少 95% 的回答是好答案，執行多久都可以。」只要最終結果明確，而且能被檢查，Codex 就有機會自己驗證、自己迭代。

課程中提到，有一個這樣的 goal 執行了超過十小時；也有人讓 goal 持續好幾天，把一款遊戲移植成原生 iOS 版本。這類工作都具備同一個特徵：任務很大、需要長時間修正，而且最後能用某種方式判斷是否達標。

什麼時候不該使用 /goal

/goal 不是每個任務都需要。小事情通常不必啟動它，Codex 用一般 prompt 就能順利完成；硬要使用，反而增加不必要的複雜度。

它真正適合的是「大而久」的工作，例如複雜遷移、整個應用程式改用另一套框架，或需要數小時到數天反覆重構的任務。

還有兩點要注意：

  • 不要把 /goal 和 grill-me 混在同一個流程裡。如果需要透過追問逼出決策，應該先在啟動 goal 之前完成。
  • 不要把目前的底層實作方式當成永遠不變的規格。它未來可能改變，OpenAI 官方也曾如此說明。比較好的理解方式，是把 goal 當成一種可以依賴的工作模式，而不是死守某個固定實作。

把 goal 掛回整個工作流程

一般 prompt 是一問一答，Codex 常常完成一版就停；/goal 則把「什麼時候可以停」說清楚，讓 Codex 持續工作直到驗收條件成立。這個條件可以是一條門檻，也可以是一長串檢查清單。大而久、需要反覆打磨的任務適合使用它；一次就能完成的小事，則不必出動。

因此，goal 的核心不是「讓 Codex 更努力」，而是把完工的判定方式交代清楚。當結果可以被觀察、被檢查、被評估，Codex 才有機會知道自己還差什麼，並在下一輪繼續修正。

下一課會進一步拆解 goal 的寫法：為什麼條件寫得寬、只描述成敗標準，有時反而比把每一步都寫死更有效；同時也會介紹前端視覺檢查，以及 eval／golden set 這兩種驗收方式。
