把真實工作餵進 goal：ticket、spec 與獨立 worktree

Step 3/4 · Goals：把長工交給 Codex 自走

一張 ticket 通常只是一句需求；要讓 Codex 長時間工作，還需要把決策、驗收條件與工作範圍整理好。這一課會帶你走完一條可重複的動線：從 tracker 拉票，先用 grill-me 問清楚，再把結論寫成 repo 裡的 spec，最後在獨立 worktree 上啟動引用這份 spec 的 /goal。

做完這一課，你會得到什麼

你會得到一條把「真實的票」轉成可長時間自走 goal 的固定流程：

  1. 讓 Codex 讀得到 ticket。
  2. 用 grill-me 把尚未決定的事情問清楚。
  3. 把決策寫成 repo 裡的規格檔。
  4. 在獨立的 worktree 或 branch 上啟動 goal。

動手前，你需要上一課那份會執行的 goal，以及一個能接上的 ticketing system。使用 GitHub 時，先安裝並登入 gh 這個命令列工具；使用 Jira 時，則要接上 Jira 的 MCP server。

第一步：決定 tracker 怎麼接

要讓 Codex 幫你「領一張票來做」，它必須先能讀到那張票。接法取決於團隊使用的追蹤系統，主要限制來自 tracker 本身，而不是 Codex。

Tracker接法你能做的事
GitHub使用已登入的 gh 命令列工具讀 issue、留言、開 pull request
Jira接上 Jira 的 MCP server把票的內容拉進 context 再開工

MCP server 可以理解成一個外接工具的接口：它把 Codex 接到 Jira 這類外部系統，讓 Codex 能讀取或操作那裡的資料。Jira 有官方的 MCP server，你可以直接搜尋或詢問 LLM 設定方式，也可以請它協助設定。

無論使用哪一種 tracker，只要 Codex 能取得 ticket，又能存取你的程式庫，這條流程就能運作。

第二步：先用 grill-me 做決策

不要把 grill-me 和 goal 混成同一個流程。兩者的工作方式相反：

  • grill-me 會停下來反覆提問，逼你確認真正的需求。
  • goal 會依照目標持續推進，直到完成驗收條件。

因此，先 grill-me，再啟動 goal。這就像先把施工圖畫完，才讓施工隊進場；如果一邊施工、一邊決定規格，工作很容易在中途改方向。

第三步：把決策寫進 spec 檔

完成 grill-me 後，把討論結果整理成一份 spec（規格）檔，放進 repo，再讓 goal 引用它。不要只把決策留在對話裡，因為 goal 執行期間可能發生 context 壓縮或對話重開；對話中的細節可能消失，repo 裡的檔案則能持續留下來，成為穩定的工作依據。

一個引用規格檔的 goal 可以短成這樣：

/goal 依照 repo 根目錄的 SPEC.md，完成「結標後通知得標者與賣家」這個功能。
驗收條件：
- 結標的拍賣會產生一筆 outbox 事件，並由通知 worker 消費
- 得標者與賣家都會收到對應的通知
- 相關測試全數通過
不要停，直到以上每一項都成立。

這個 goal 沒有重新貼上所有規格細節，只做兩件事：

  1. 指定 Codex 要遵循 repo 根目錄的 SPEC.md。
  2. 列出必須達成的驗收條件。

細節放在 SPEC.md，goal 負責照著規格執行到達標。上一課也提到，如果 goal 本身長到約四千個字元，系統會自動幫你拆成規格檔；即使你直接貼上一大段決策，也有機會由系統整理成檔案。

第四步：在獨立的 worktree 或 branch 上開跑

goal 會實際修改程式碼，而且可能執行好幾個小時，甚至好幾天。不要直接在主線上啟動。先建立一個新的本地 worktree，或從主分支切出一個獨立 branch，讓 Codex 在隔離的工作區內修改。

這樣做的好處很直接：如果 goal 走偏或改壞內容，不會污染主要分支；你可以檢查、丟掉，或重新開始。

如果目標是某個 branch，開跑前也要先準備好環境。例如先執行一次 pnpm install，避免 goal 一開始就卡在相依套件尚未安裝，而不是卡在真正的工作上。

第五步：拉票、開工，並明確指定 repo

環境準備好後，把 ticket 拉進來並開始工作。下面這個指令會指定 GitHub 上某個 repo 的 issue，要求 Codex 讀完後開始處理；如果還有少量關鍵問題，就先提問。完成後，再開一個 PR：

/goal pull in issue 2 from GitHub for this repo, read it,
start work on it, or grill me minimally with questions.
When you are confident the issue is done, open a PR.

送出後，畫面可能出現「pursuing goal」之類的狀態。這表示 Codex 已經記下目標並開始推進，不會在中途因為一般性的停頓就隨意結束。

危險步驟：接上 GitHub 代表給出帳號層級權限

在送出指令前，先確認你理解授權範圍。當你授權 Codex 操作 GitHub，給出的不是「只有目前這個 repo」的權限，而是你帳號底下任何一個 repo 的權限。

課程講者用「here be dragons」形容這個位置：這裡有龍，必須小心。雖然多數時候 Codex 會照你指定的範圍工作，但你仍應在指令裡清楚寫出只能操作哪一個 repo，把出錯範圍壓到最小。

這是一個不可逆、也不該輕忽的授權動作。確認工作範圍後，再交出權限。

做完長什麼樣

完成後，你應該能重複走完這條動線：

  1. 確認 tracker 已經接好：GitHub 使用 gh，Jira 使用 MCP server。
  2. 用 grill-me 把需求與決策問清楚。
  3. 把決策寫成 repo 裡的 spec 檔。
  4. 建立獨立的 worktree 或 branch。
  5. 用 /goal 引用 spec，拉入 ticket 並開始執行。
  6. 看到 goal 進入追求目標的狀態。

到這裡，你已經能把一張真實 ticket 變成可長時間自走的 goal。至於 goal 執行期間要怎麼監督、什麼時候該插手，屬於下一步的判斷問題；本課先完成「怎麼餵」這件事。

小結

把真實工作餵給 goal 的順序是：先決定 tracker 怎麼接（GitHub 用 gh、Jira 用 MCP server），再用 grill-me 逼出決策並寫成 repo 裡的 spec 檔，然後在獨立的 worktree 或分支上開跑，用 /goal 引用那份 spec。過程中要記住，接上 GitHub 等於給出帳號層級的權限，務必在指令裡明確限制它只碰某一個 repo。

現在你已經能寫 goal，也能把真實的票接進來。但 goal 啟動後，會自行判斷進度、自我驗證，甚至自行尋找下一步。什麼時候可以放手、什麼時候需要插手，下一課會給你一套判別方式，也會示範如何用新的 prompt 把偏離方向的 goal 拉回來。
