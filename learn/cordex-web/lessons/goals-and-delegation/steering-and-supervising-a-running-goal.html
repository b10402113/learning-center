跑到一半該不該插手：監督、修正與收尾的判準

Step 4/4 · Goals：把長工交給 Codex 自走

先決定：現在該放手，還是送一個新 prompt？

你已經在 Codex 裡開起一個 goal，它正在執行。這時最實際的問題不是「它能不能做」，而是：我現在該讓它繼續自己跑，還是該出手把方向拉回來？

放手，可能省下大量等待時間；但如果它朝錯的方向使勁，等你回頭時，可能已經改了一大片。反過來說，太早插手也會打斷它原本能自己完成的驗證與修正。

這一課要建立的判準很簡單：先看成果能不能被清楚驗證，再判斷任務是否需要人的品味與意圖。前者通常可以放手，後者則要準備隨時送出新 prompt。

兩個選項，差在誰能判斷「做對了」

監督一個正在執行的 goal，基本上有兩條路。先把差異並排看，再決定要不要介入。

放手讓它自走送新 prompt 修正
適合的情況「對不對」能用清楚的條件驗證「好不好、像不像我要的」需要品味與意圖判斷
典型任務經典 SaaS 的錯誤、測試、遷移大膽或新穎的前端、動畫、互動意圖
你要付出的成本偶爾查看進度即可必須先想清楚，並說得出你要什麼

放手不是把工作丟著不管，而是因為這類任務有明確的驗收條件，goal 能自己對照並修正。送新 prompt 也不代表你不信任 Codex，而是有些答案根本藏在你的腦袋裡：程式碼可以告訴你功能是否運作，卻不一定能告訴你成果是否符合你的品味。

做決定前，先問這四個問題

不要只憑「看起來好像沒問題」來決定。用下面幾個可以實際回答的問句檢查，答案通常會直接指出方向。

  1. 我能不能用一句話驗證「做對了」？如果成功條件明確，而且 goal 能自己檢查，就可以放手。若你連自己都說不清楚「對了」長什麼樣，就應該先把意圖想清楚，再送出新 prompt。
  2. 這是經典 SaaS 類型的工作嗎？課程講者觀察，這類專案通常能讓 Codex 自己找出不對的地方並繼續修正，因此適合放手。
  3. 這需要判斷「好不好看、像不像我要的」嗎？如果答案是肯定的，就不要期待它自己拍板。你需要在適當時機當裁判，指出哪裡不對、真正想要的方向是什麼。
  4. 它說完成時，我看得到它真的驗證過嗎？收尾不能只讀它的總結，還要核對它宣稱做過的檢查是否真的發生。

為什麼它有時候可以自己跑到底？

你之所以能放手，不是因為 goal 會憑感覺亂試，而是因為它有一套追蹤進度與驗證成果的機制。

首先，goal 會在內部建立一份任務清單，並把任務存進小型 SQLite 資料庫。接著，它會持續檢查應用程式與任務的狀態，對照自己是否真的達成目標。

這就是它能「不達標就繼續」的技術基礎。它不是只在腦中記住一個模糊目標，而是拿著一份可追蹤的清單，一項一項確認。

遇到前端任務時，它還能使用一整組驗證工具：用 browser use 實際操作頁面，透過 CDP（Chrome DevTools Protocol）查看畫面相關的 log、network 與 layout，也會自行截圖，比對「應該長什麼樣」和「目前長什麼樣」。

如果目標不是網頁，而是像手機模擬器這類無法在瀏覽器裡直接操作的介面，就要改用 computer use。這些工具串成一個「診斷 → 修正 → 驗證」的迴圈，讓 goal 能在沒有人持續盯著的情況下往前推進。

再加上它通常會先跑一次 build，才宣布工作完成，課程講者表示，她已經很久沒遇到「它說做完，結果東西壞掉」的情況。這代表它在能用內建方式驗證的錯誤上，通常可以可靠地自我收斂。

反例：程式碼正確，成果卻不符合你的意圖

規則會翻轉的地方，是成果需要人的品味或意圖判斷時。

課程裡有一個很具體的例子：一個滾動式的 3D 體驗中，東京那段城市的精靈物件跑到了地球後方，看起來像是穿幫。這不是程式無法執行，而是畫面效果不符合原本的設計意圖。

「我原本是想要它繞著地球轉」這件事，沒有辦法單靠程式碼推導出來。即使指令裡寫了「旋轉」，LLM 也很難自行判斷這裡的「旋轉」其實代表「繞過地球，而且要在前方出現」。這時需要人直接說：「這不對，我其實要的是這個。」

所以關鍵不是 Codex 夠不夠聰明，而是問題屬於哪一類。經典 SaaS 專案常能自己判斷哪裡不對；越是新穎、越偏前端、越依賴視覺品味的專案，就越需要人提供方向。課程講者估計，這樣的分工大約各半：有些事情它能自己解決，有些事情一定要人來裁判。

還有一條容易混淆的界線：browser use 只能操作瀏覽器裡執行的內容；如果目標是原生 App，必須透過模擬器操作，就要使用 computer use。工具選錯時，goal 可能會對著錯誤的介面一直嘗試。

可以直接使用的決策規則

下次你看著一個正在執行的 goal，不確定是否該插手時，依序檢查三件事：

  1. 先問：「做對了」能不能被清楚驗證？能，就放手；不能，就先由你定義清楚，再送新 prompt。
  2. 再問：這是不是需要判斷「好不好看、像不像我要的」？是，就在它跑偏時介入，明確說出「這不對」以及「我其實要的是這個」；不是，就讓它繼續自己收斂。
  3. 最後核對收尾證據：它宣稱做過的 build、檢查或驗證，是否真的發生，而不是只看它貼出的完成摘要。
能用明確條件驗證的任務，就讓 goal 自走；需要品味與意圖判斷的任務，就準備在跑偏時送新 prompt。放手的前提不是盲目信任，而是你知道它有任務清單、SQLite 狀態追蹤，以及 browser use、CDP、computer use 組成的自我驗證迴圈。收尾時，記得核對驗證是否真的做過。
