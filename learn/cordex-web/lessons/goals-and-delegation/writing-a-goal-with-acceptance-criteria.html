寫一個 goal：寬的目標，加上可驗收的停止條件

Step 2/4 · Goals：把長工交給 Codex 自走

有些工作不是改一行程式就結束，而是要反覆調整、檢查，直到畫面或答案真的達標。這時候，單次 prompt 很容易讓 Codex 做完一小段就停下來。你需要的是一份能讓它持續追蹤的 goal：目標保留足夠空間，驗收條件則清楚到可以判斷「現在能不能停」。

這一課會做出什麼

你會寫出一份可以直接送出的 goal，包含兩個部分：一個描述結果的寬目標，以及一組具體、可驗證的成功條件。你也會學會依任務類型選擇驗收方式：前端工作用視覺檢查，問答或文字產生工作則用 eval／golden set。

動手前只需要準備兩樣東西：上一課對 goal 的基本觀念，以及一件需要跑好幾趟才能完成的長工。如果手邊沒有特定任務，就拿目前正在拖延的工作當練習對象。

第一步：用 /goal 開始

在 Codex 裡輸入 /goal，再貼上你寫好的內容。這裡有個容易誤會的小細節：選取 /goal 後，那幾個字會消失。

這不是操作失敗，而是 Codex 已經切換到 goal 模式。送出後，畫面會顯示它正在追求這個目標。只要這個狀態還在，就表示目前工作階段會以「尚未達標就繼續」的方式執行。

第二步：目標寫寬，描述結果，不要寫死路徑

goal 最重要的寫法是：給它一個寬的目標，再附上成功標準。不要把每個檔案、每一行修改方式都指定好。

直覺上，指示越精確好像越安全；但如果把做法全部寫死，Codex 就只剩下照表操課的空間。它可能完成你列出的修改，卻沒有真正確認結果是否符合需求。

相反地，只描述想要的結果與判定方式，Codex 才能自行選擇實作路徑，並依驗收條件反覆檢查。課程講者轉述 OpenAI 的說法：goal 最有效的用法，是提供寬的目標與成功條件，而不是指令式的細節。不過，這項特性未來若隨底層實作改變，也可能跟著調整。

先看一個把做法寫死的版本：

/goal 幫我在 src/components/Globe.tsx 第 42 行把 opacity 改成
Math.max(0, 1 - depth)，然後在 styles.css 加一段 transition 0.3s，
再把 store.ts 裡的 state 欄位改名叫 spriteDepth，最後跑 build。

這個版本指定了要改哪裡、怎麼改，以及最後跑什麼指令，卻沒有說明畫面應該達到什麼效果。再看一個以結果和驗收為核心的版本：

/goal 把 A Year and a Day 的 3D 體驗打磨到可以對外發表。
驗收條件：
- 精靈在前景時完整顯示，轉到地球後方才淡出
- 手機、平板、桌面三種 viewport 地球都不被裁切
- 全程轉場流暢不掉格
- 鍵盤焦點移動行為正確
- 請實際打開瀏覽器看畫面，不要只憑編譯就當作完成
不要停，直到以上每一項都成立。

第二種寫法沒有規定一定要改哪一行，卻清楚說明最後要看到什麼：精靈要在正確時機淡出，地球不能被裁切，轉場要順，鍵盤焦點要正常，並且必須實際檢查瀏覽器畫面。這才是 goal 要提供的方向。

第三步：把驗收條件寫成真的能檢查的東西

驗收條件決定 Codex 什麼時候可以停，所以不能只寫「做好看一點」或「品質要好」。它必須能被檢查。常見形式有兩種，選擇方式取決於任務是在看畫面，還是在判斷答案。

形式適用任務驗收條件怎麼寫
前端視覺檢查3D 體驗、動畫、版面等有明確畫面目標的工作列出要逐一檢查的視覺項目，例如地球可見、轉場順、標記可見、鍵盤焦點正確，並要求實際查看畫面
eval／golden set問答、回覆產生等有「好答案」可對照的工作準備一組標準問答，用裁判模型評分，並把條件寫成例如「95% 以上是好答案」

前端任務：寫成視覺檢查清單

如果你做的是前端工作，就把畫面上必須成立的事情一項項列出來。例如前面的 3D 體驗，需要檢查精靈在前景與地球後方的顯示狀態，也要分別確認手機、平板和桌面 viewport。

還要明確要求 Codex 實際打開瀏覽器查看畫面。編譯通過只代表程式碼能建置，不代表畫面沒有裁切、轉場沒有掉格，或鍵盤操作真的正確。驗收條件若只寫「build 成功」，就檢查不到這些問題。

問答任務：用 eval／golden set 變成分數

如果任務是產生回答或文字，就準備一組問題與最佳答案。這些標準答案由熟悉領域的人先寫好，再交給另一個 LLM 當裁判，逐一評分。

如此一來，驗收條件可以寫成：「不要停，直到這組題目有 95% 以上被判為好答案。」原本模糊的「答得好」就變成可計算的分數，Codex 才能判斷目前是否已經達標。

第四步：goal 很長時，讓 Codex 自己拆成規格檔

如果目標包含很多步驟，不必為了維持短小而刪掉必要細節。當 goal 長到一定程度，大約四千個字元左右，Codex 會自動把內容拆成一份規格檔放進 repo，接著依照那份規格執行。

因此，需要交代的背景、限制和驗收條件都可以寫清楚；內容夠長時，系統會在需要時自行整理成檔案。

第五步：送出後確認它仍在追蹤目標

貼上內容並送出後，先看一眼畫面上的狀態。確認它顯示正在追求你剛給的目標，而不是回到一般問答模式。

這個確認很小，卻能避免一個常見誤判：你以為 Codex 還在持續工作，實際上它可能早已停下來等待下一個指示。

做完長什麼樣

完成後，你應該有一份符合以下條件的 goal：

  • 目標夠寬，描述想要的結果，而不是指定每一步怎麼改。
  • 驗收條件具體，而且每一項都能被檢查。
  • 前端任務使用視覺檢查清單，問答任務使用 eval／golden set。
  • 送出後，畫面確實顯示 Codex 正在追求這個目標。

這樣 Codex 才會一輪一輪地執行與檢查，直到能證明條件成立。至於為什麼寬的目標反而能保留更好的解法空間，這裡不展開原理；下一步是把真實工作接進來。

小結

寫 goal 的順序是：用 /goal 開頭，把目標寫成寬而明確的結果，再補上具體可驗證的停止條件。內容很長時，可以讓 Codex 自己拆成規格檔。送出後，確認狀態仍顯示它正在追求這個目標。前端任務用視覺清單驗收，問答任務則用有分數的 eval／golden set 驗收。

下一課會處理真正的工作來源：把一張 ticket 接進來，先 grill 出規格，再讓 goal 引用它，並在獨立的工作區上開始執行。
