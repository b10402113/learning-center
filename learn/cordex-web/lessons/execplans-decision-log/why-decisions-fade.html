為什麼 Codex 會忘記你當初這樣做的理由

Step 1/5 · Execplans：讓決策撐過 compaction

學習目標

這一課要先看懂兩個風險：對話變長後，Codex 為什麼會逐漸抓不住重要決策；以及為什麼你換了 session，甚至換成同事的 Codex，原本的決定仍可能被改回去。

前言：一個下午的心血，吃頓飯後就找不到理由

想像一下：你花了一整個下午，和 Codex 一起把演算法調到正確。前後改了二十輪，每一輪都有原因：參數為什麼調小、某條分支為什麼移除、快取為什麼不能省。你們反覆測試，終於得到符合預期的結果。

你去吃晚飯，回來後問 Codex：「為什麼這個參數是 0.3，不是 0.5？」它卻答不出來，甚至很熱心地把參數改回 0.5。

Codex 不一定是在偷懶；它可能真的已經忘了。要理解這種情況，得先知道 Codex 的記憶如何運作。這一課會拆開兩個問題：對話為什麼會讓決策逐漸消失，以及為什麼新 session 或另一位同事的 Codex 也會再次遺忘。

context 有預算，而且用久了會逐漸失準

一次 Codex 對話能容納的內容有限，這個範圍叫做 context window（上下文視窗）。可以把它想成一張大小固定的工作桌：工具輸出、草稿、你說過的話，以及它讀過的檔案，全都要放在桌面上。

問題不只是桌子會不會被擺滿。實務上觀察到，對話內容超過 window 約四成後，輸出品質就會開始慢慢下滑。它不會突然故障，而是逐步退化：漏掉細節、抓錯重點，或把早先的約定說得含糊不清。

因此，即使你沒有明確做錯什麼，只是讓對話繼續進行，Codex 對「我們之前決定了什麼」的掌握也可能悄悄變差。你以為它還記得整張工作桌，其實它已經看不清桌上的每張紙。

compaction 為什麼像在擲骰子

當 context 快滿時，系統會把前面一大段對話壓縮成較短的摘要，為後續內容騰出空間。這個動作叫做 compaction（上下文壓縮）。

乍看之下，這是合理的整理方式；但關鍵在於：哪些內容該留下，是由模型判斷，不是由你指定。模型可能正確丟掉一段閒聊，卻也可能把「這個參數不能改，因為客戶的舊資料要靠它」這種關鍵決策一起刪掉。

Katia 在課堂上把這件事形容成某種程度的擲骰子：你無法保證哪些重要內容會被保留下來。真正麻煩的不是記憶變短，而是留下什麼不受你控制。越需要長期保留的決策，越可能在某次壓縮中被當成雜訊捨棄。

第二種失憶：跨 session、跨同事

即使沒有發生 compaction，Codex 仍有另一個常見的遺忘來源：它的記憶綁在單次對話上。對話結束後，這段記憶就不會自動延續。你明天開一個新 session，它不知道昨天為什麼做出那些選擇；同事在自己的電腦上請另一個 Codex 接手，也同樣不知道。

因此，「決策只存在對話裡」並不是可靠的做法。真正能延續到下一次工作的，是被寫下來、留在共同工作空間裡的內容。對 Codex 而言，這個共同工作空間就是 repo。

一個很貴的反例：被改回去的 legacy 套件

假設你的 repo 因為安全團隊要求，或因為某個相依元件只支援舊版，而必須使用一個 legacy 套件。若這個理由沒有被記錄，下一個 Codex instance 看到它，很可能只會得到一個直覺：

「這個套件看起來太舊，應該升級。」

於是它順手換成新版，整條流程可能因此壞掉。你花了很多時間追查，最後才發現問題來自那次看似善意的升級。

重點是：沒有被記錄的決策，對下一個 Codex 而言就像從未發生過。它只能看到目前的狀態，看不到狀態背後的理由，因此可能做出「合理但錯誤」的改動，把你已經想清楚的決定整個拆掉。

小結

Codex 的記憶有兩個破口。第一，context 超過約四成後，品質會逐漸退化；而 compaction 會挑選內容留下，等於讓你無法控制哪些決策被保留。第二，記憶綁在單次對話上，換 session 或換同事的 Codex，就可能重新開始。結果是，同一個決策可能被下一個 instance 善意地改回去，例如把安全團隊指定的舊套件升級，最後弄壞系統。要補上這兩個破口，就得把決策寫進 repo。

現在可以看出問題的連結了：對話是暫時的，repo 才能讓決策跨過時間、session 與不同的 Codex instance。下一課會介紹 exec plan，看看如何把這些決策寫進 Codex 讀得到、也能持續維護的地方。
