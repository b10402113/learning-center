什麼時候值得開 exec plan？

Step 5/5 · Execplans：讓決策撐過 compaction

先解決一個實際問題：不是每件事都值得記錄

前面四課，你已經學會找出決策為什麼會消失、認識 exec plan、親手寫過一份，也把它接進 AGENTS.md 自動化。現在真正要面對的是：是不是每件工作都該開 exec plan？

答案不是單純的「要」或「不要」。重要工作不留下紀錄，可能讓你幾小時後重新追查一個早已做過、甚至被改回去的決定；但每改一行文字就開一份文件，也會讓資料夾充滿沒人想看的內容。久而久之，真正重要的 exec plan 反而會被一起忽略。

所以這一課的重點，是在動手前判斷工作的份量與未來價值：該完全不寫、留下簡單的決策日誌，還是建立完整的 exec plan。

先比較三種選項

實際上，你面對的不是二選一。課堂上提到，有些人不寫完整的 exec plan，而是維護一份簡單的 log 檔：請 Codex 每完成一件事或一個步驟，就編輯一次 Markdown 檔或決策日誌。

因此，最實用的選項有三種：

選項長什麼樣適合什麼情況
不寫什麼都不留下沒有重要決策，也沒有未來讀者的小改動
決策日誌簡單的 log 檔，每完成一步記一筆長時間 goal、複雜演算法的反覆迭代
完整 exec plan四塊俱全、由 Codex 自動建立的活文件新功能、重要架構決定、值得日後回顧的工作

中間這一檔很重要。假設你正在執行一個會跑好幾個小時的 goal，需要的可能只是「每完成一步就記一筆」的簡單日誌，不一定要先寫出結構完整的大計畫。它的維護成本較低，卻能留下 compaction 最容易遺失的資訊：這次改動為什麼要這樣做。

判別問句：動手前問自己三題

不確定要不要記錄時，不必憑感覺。逐一回答下面三個問題，只要有一題是「是」，就值得留下紀錄；三題都是「否」，通常可以略過。

  1. 這件事會不會產生「不寫下來就難以理解」的決策？

    例如安全團隊指定使用舊套件，或為了相容性而刻意保留某種看似奇怪的寫法。這類理由不一定能從程式碼本身看出來。如果只留在人的記憶或當下對話裡，下一個 Codex 很可能把它當成問題，重新改掉。

  2. 這段工作會不會執行很久，或在過程中反覆迭代？

    例如會跑好幾個小時的 goal，或像調整演算法一樣來回修改二十輪。時間越長、迭代越多，發生 compaction 的機會越高；而每一輪也可能都有一個日後想不起來的修改理由。

  3. 未來會不會有其他 Codex 或同事接手？

    只要你可能換 session、請同事的 Codex 繼續處理，或這個 repo 本來就是多人共用，「留給下一個人讀」就已經是實際需求，不是額外的禮貌。

反例：什麼時候不用開，開了反而更糟

第一種反例，是小而且沒有決策的改動。把文案改順、把按鈕顏色調深，通常沒有需要保存的選擇，也沒有跨時間的讀者。這時硬開一份 exec plan，只會讓資料夾堆滿沒有價值的檔案。

更麻煩的是，這會逐漸訓練大家忽略 exec plan。當重要與不重要的工作都留下同樣形式的文件，所有人最後都會覺得它們不重要；在這種情況下，不寫反而比濫寫好。

第二種反例，是把「前端」誤解成永遠不需要 exec plan。講者提到，exec plan 可能用在前端，但更多時候會出現在後端服務或較大型的專案。這句話的判斷重心其實是決策密度與專案規模，不是前端或後端的標籤。

小型前端專案如果決策少、接手的人也少，自然不需要每件事都記錄；但多人協作、前後端都有的專案，即使你負責前端，只要某個視覺決定背後有一段重要理由，一樣值得留下紀錄。

第三種反例，是以為「寫了」就等於「做了」。exec plan 只是承載決策的容器。如果內容是空的，或建立後從來不更新，它對 compaction 沒有實質幫助。決定要開之前，也要確認自己或 Codex 真的會維護它。

把判準收斂成一句話

只要一件事會產生「未來的人無法從程式碼看出原因」的決定，就留下紀錄；如果工作還會拖很久，或之後會由別人接手，就把紀錄升級成完整的 exec plan。

你也可以在動手前快速檢查：

  1. 程式碼背後有沒有藏著重要理由？有，就至少記一份決策日誌。
  2. 工作會不會執行很久、反覆迭代？會，就在每完成一步時記一筆。
  3. 會不會換 session，或交給其他 Codex、同事接手？會，就把紀錄放進 repo 的專屬資料夾。
  4. 三題都答「否」？略過，把力氣留給真正需要保存的決策。

exec plan 不是每件事都要開。你有三個選項：不寫、使用簡易決策日誌，或建立完整 exec plan。判斷時問三題：有沒有不寫就難以理解的決策、工作會不會長時間反覆迭代、未來會不會有人接手。任一題為「是」，就留下紀錄；三題皆為「否」，就可以略過。

走完這五步，你應該能在真實 repo 裡做出判斷：什麼時候要留下 exec plan、什麼時候簡單記一筆就夠，以及什麼時候完全不用寫。小改動不必硬套流程；長時間的 goal、後端服務、大型專案與多人協作，則是最值得使用它的地方。
