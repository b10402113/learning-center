Exec plan：把 Codex 的工作決策寫成 repo 裡的活文件

Step 2/5 · Execplans：讓決策撐過 compaction

先解決一個常見問題：對話結束後，決策去哪裡了？

你可能在 Codex 的對話裡討論過很多重要事情：這次功能要做到什麼、哪些檔案不能動、遇到 build error 要怎麼處理。當下看來都很清楚，但對話結束、換個 session，甚至換位同事接手後，這些脈絡就可能找不到了。

上一課的結論是：重要決策要寫進 repo。但「寫進 repo」還不夠具體。要放在 README、issue，還是程式碼註解裡？如果每次都用不同形式記錄，Codex 也不知道該去哪裡找，更不知道什麼時候要更新。

exec plan 就是用來解決這個問題的工作習慣：把一次工作的目的、進度、意外與決策，整理成一份放在 repo 裡、會隨工作持續更新的 Markdown 文件。

先認識這個名字：它不是業界標準

exec plan 是 Codex 團隊自己使用的稱呼，不是業界標準術語，也沒有一份所有工具都必須遵守的官方規格。因此，你不需要擔心自己是不是漏看了某份「exec plan 標準文件」。

你可以把它理解成一種固定的記錄方式：在 repo 裡放一個資料夾，讓 Codex 為每個新功能或重要決定，留下完整的工作脈絡。名稱可以叫 exec plan、決策日誌或進度紀錄；真正重要的是它被寫下來、放在 repo 裡，而且會持續更新。

第一個特徵：它在 repo 裡，不只存在對話中

exec plan 是一份實體的 Markdown 文件，存在專案的版本庫裡，能和程式碼一起提交、分享。只要有人或 Codex 正在查看這個 repo，就能讀到同一份內容。

這和對話裡的計畫很不一樣。對話裡的計畫就像寫在白板上的字：討論時很有用，但離開那個 session 後就不一定找得回來。repo 裡的 exec plan 則像放進專案資料夾的工作紀錄，不會因為換電腦或換對話而消失。

第二個特徵：它是「活的」文件

課堂上展示過一份真實的 exec plan，內容和 OpenAI 將開發者網站從 cookbook.openai.com 搬到 developers.openai.com 有關。文件一開始就說明，它是一份 living document，也就是「活的文件」。

「活的」不是指文件會自己變動，而是指它不會在一開始寫完後就被冷凍。工作繼續進行時，文件也跟著長大：

  • 完成幾個任務，就更新進度與任務清單。
  • 遇到 build error，就記下發生了什麼。
  • 和使用者討論出新的決定，就補進決策紀錄。

所以，exec plan 比較像工作日誌，不像只在開工前寫一次的企畫書。任務結束時，它也正好留下了這次工作的完整脈絡。

第三個特徵：設定好之後，由 Codex 自動建立

單純在 repo 裡放一個空資料夾，Codex 不會因此自動開始記錄。你需要在 AGENTS.md 這份 Codex 會讀取的專案說明檔中，寫清楚什麼是 exec plan，以及什麼情況下應該建立它。

設定完成後，當 Codex 要實作全新的功能，或遇到重要決定時，就能依照這份指引建立 exec plan。你不用每次都重新提醒它：「記得寫計畫」。

這就像把工作習慣寫成專案規則：不是靠你每次想起來才做，而是讓 Codex 在符合條件時自動採用。至於 AGENTS.md 的指引要怎麼寫，會在下一課詳細處理；這一課先記住，它是啟用自動建立的開關。

它記錄什麼：目的、進度、意外與決策

exec plan 不只是待辦事項清單，也不只是功能指引。它要保留的是「這次工作怎麼進行，以及為什麼這樣做」的脈絡。

以搬站的案例來看，內容可以整理成幾個區塊：

區塊記錄什麼課堂上的實際例子
目的這次工作要達成什麼說明從 cookbook 搬到 developers 的遷移目的
進度與任務做了哪些事，目前進行到哪裡列出遷移過程中已完成的任務
意外與發現過程中出現的問題與新資訊記錄 build error，以及發現部分資產缺漏
決策紀錄做了哪些選擇，以及選擇的理由維持資源主題頁不變，並完全比照既有的資料結構

這些欄位看起來很樸素，價值卻在於它們把通常只存在某個人腦中的資訊留下來。下一個 Codex 讀到「這裡為什麼要維持原狀」時，就不必重新猜測。

把三個特徵連在一起

exec plan 是 Codex 團隊自創的說法，不是業界標準。它是一份放在 repo 裡、會持續更新、並可由 Codex 自動建立的活文件。它和只存在對話中的計畫不同：放在 repo 裡，所以能跨 session、跨同事保存；它是活的，所以會隨工作進展更新；設定好 AGENTS.md 後，Codex 可以在需要時自動產生，不必每次提醒。內容大致涵蓋目的、進度與任務、意外與發現，以及決策紀錄。

因此，exec plan 不是另一種漂亮的文件格式，而是把工作記憶接回 repo 的方式：對話負責討論，exec plan 負責留下能被後續工作讀取的脈絡。下一課會先帶你親手寫出一份最小可用的版本，再處理如何讓 Codex 自動建立。
