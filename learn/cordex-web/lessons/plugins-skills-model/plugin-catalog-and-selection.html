該裝哪個 plugin？先分清楚你要連服務，還是要做成品

Step 4/4 · Plugin、App、MCP 與 Skill 的分野

先解決眼前的問題：清單這麼長，該從哪裡下手？

你打開 Codex app 的 plugin 區，看到 Slack、GitHub、Vercel、iOS、games 等一長排選項。每個看起來都很有用，但你不可能全裝，也不需要全裝。

真正要做的決定是：面對手上的任務，你需要的是讓 Codex 連上某個既有服務，還是讓它更會做某一類成品？先分清楚這兩股需求，再看 plugin 清單，就不會像在超市裡漫無目的地把東西丟進購物車。

這一節的目標，是讓你認得 plugin 的幾大分類，並依照任務判斷該裝哪一類、什麼情況下其實不該裝。

選項比較：plugin 主要分成哪幾類？

分類典型代表什麼時候會用到
工作情境與溝通Slack、Gmail、Google Drive想讓 Codex 讀懂「公司裡現在發生什麼事」
原始碼控管與審查GitHub要看 PR、審查程式碼、操作 repo
專案追蹤Linear要對接任務、issue、專案進度
託管與部署Vercel、Cloudflare、Render、Convex要查明部署、自動接上託管平台
服務供應商Supabase、Neon要讀取服務的 log，讓 Codex 更獨立地處理
Builder workflowsBuild Web Apps、iOS、macOS、React Native、web data viz、games正在動手做某一種類型的 app

前五類的共同點，是讓 Codex「連上服務」。它們比較接近前面談過的 app（connector）與 MCP server：你完成授權後，Codex 就能代你存取資料，或呼叫對方提供的能力。

最後一類 Builder workflows 的性質不同。它比較像把很多 skill 打包在一起的 plugin，由熟悉特定工作流的專家整理而成，裡面可能包含該用哪些函式庫、怎麼除錯等知識；有些還會附上整合或 MCP server，例如 React Native 對應的 Expo。

所以，安裝 builder plugin 時，你主要拿到的不是某個服務的登入權，而是一整套做這類工作的做法。

判別問句：三個問題就能縮小選擇

不用背整張表。安裝前，先依序問自己三個問題：

  1. 我在找的是 Codex 能碰到的某個既有服務嗎？
    如果是，就從工作情境、原始碼審查、專案追蹤、託管或服務供應商這五類中，挑出對應的 plugin。你需要的是授權與工具，不是另一套做法。
  2. 我正要動手做某一種類型的成品嗎？
    如果是，就找對應的 builder workflow。它的價值在於專家整理好的知識與工作流，而不是替你登入某個服務。
  3. 我真正想解決的，是每次都要重講同一套做法嗎？
    如果是，你缺的可能不是 plugin，而是一份 skill。先把規則與做法寫下來，通常比再安裝一個 plugin 更直接。

三個問題問完，候選通常只剩一兩個。接著再問一句：這個任務現在真的需要它嗎？「現在需要」才是最後的安裝門檻。

反例：什麼時候規則會翻轉？

第一種常見錯誤，是「先裝起來放著」。你還沒要寫 iOS app，卻先安裝 iOS 的 builder plugin；它帶進來的一大組技能與整合，對當下的 web 專案完全用不上，只會讓清單變得更雜。Plugin 不是越多越好，沒有用到的 plugin 不會讓你更強。

第二種錯誤，是把 builder plugin 當成萬能工具。它通常是針對某一種技術棧與生態系設計的。如果你要做的東西和它預設的技術棧不同，那一整包專家知識未必幫得上忙，甚至可能把 Codex 往錯的方向帶。Builder plugin 有用，但前提是你正在做它擅長的那一類事。

第三種錯誤，是拿 plugin 解決「重複交代」的問題。你一次又一次告訴 Codex「我們的規則要這樣」，於是直覺想找個 plugin 來裝；但這種一致性問題通常應該用 skill 處理，而不是多裝一個包裹。先把需求對到正確的零件，才不會繞遠路。

最後的決策檢查表

裝 plugin 前，先檢查這四件事：
① 我是要「連上某個既有服務」，還是「做某一類 app」？
② 如果是連服務，就從工作情境、原始碼、專案追蹤、託管或服務供應商中挑對應分類。
③ 如果是做 app，就挑對應的 builder workflow；它帶的是整組 skill，也可能附上整合。
④ 如果兩者都不是，而是想統一重複使用的做法，就先寫一份 skill，別急著裝 plugin。
最後確認：這個任務現在真的需要它，才裝。

你現在有兩層判斷地圖。第一層是零件的分工：skill 是做法，app 是授權，MCP server 是介面，plugin 則是把相關零件收在一起的容器。第二層是選擇方法：先分辨自己要連服務還是做成品，再用「現在需要嗎」當最後一道閘門。
