Skill 是什麼：讓 agent 每次都照同一套方法工作

Step 3/4 · Plugin、App、MCP 與 Skill 的分野

先解決一個你一定遇過的問題

你是不是曾經在不同對話裡，一再提醒 Codex：「元件要放在這個資料夾」、「命名要遵守這個規則」、「改動前先跑測試」？你明明已經交代過好幾次，但每次開新對話，它又像第一次加入團隊一樣，得重新聽一遍。

前兩節談的是「能力」：App 讓 Codex 連得上外部服務，MCP server 讓它叫得動工具。但很多日常工作缺的不是新能力，而是一致的做法。Skill 解決的正是這件事：把你腦中、口頭上反覆交代的工作流程，寫成 agent 每次都能讀到的指示。

Skill 是寫給 agent 的工作流程指示

Skill 是給 Codex 或其他 coding agent 遵循的工作流程指示。它會針對某一類任務，寫下「這件事應該怎麼做」，讓 agent 下次遇到相同類型的工作時，可以依照同一套規則處理，不必再等你口頭重講。

Skill 的核心其實很樸素：就是文字。它可以只是一份純文字檔，內容寫著「先做什麼、接著做什麼，以及哪些規則不能違反」。你不是在教模型一個全新的能力，而是提供一份它能重複查閱的行動指南。

可以把它想成團隊裡的 SOP。新同事原本就會寫程式，但沒有 SOP 時，每個人可能用不同方式完成同一件事；有了 Skill，agent 就能按照你認可的流程工作，產出也更容易維持一致。

組成：文字是必要的，素材與腳本是選配

一份 Skill 不一定只有說明文字。除了核心指示之外，你也可以依照工作流的需要，放入 assets 和 scripts。

組成部分是否必要它在做什麼
文字說明必要描述工作流的步驟、規則與注意事項
Assets（素材）選配提供產出時可以直接引用的範本、圖片或範例資料
Scripts（腳本）選配把流程中的某些步驟寫成可以執行的程式

因此，Skill 不必然是一個複雜的套件。最簡單的形態，就是一份文字檔；需要更完整的自動化時，才再加上素材與腳本。真正重要的不是內容有多長，而是它有沒有清楚寫出這個工作流的關鍵判斷與規則。

放在哪裡，決定它對誰生效

Skill 本質上是檔案，所以存放位置會影響它的適用範圍。放在某個 repo 裡，它就是這個專案的 Skill，通常提供在該專案中工作的 session 遵循；安裝在個人層級，則會跟著你，跨越不同專案與 session 生效。

同一份指示，換一個位置，就像把公司的 SOP 從「某個專案資料夾」搬到「個人工作手冊」：內容沒有變，但管轄範圍變了。

Plugin 之所以會把一組相關的 Skill 打包，也是同樣的道理。當某一類工作需要一整套做法，例如製作某種前端 app，把相關 Skill 一起帶進來，會比你逐一蒐集方便得多。Skill 可以單獨存在於 repo 或個人設定中，也可以被收進 Plugin，和其他零件一起安裝。

邊界：Skill 提供做法，不提供能力

最容易混淆的地方是：Skill 不會讓 Codex 突然「能」做原本做不到的事。

它不會替你連上某個外部服務，那是 App 的工作；它也不會憑空增加可呼叫的工具，那是 MCP server 的工作。Skill 改變的是 agent 的工作方式：它該採用哪些步驟、遵守哪些規則，以及最後應該產出什麼樣的結果。

你缺少的是什麼應該看哪個零件
無法連上外部服務App
沒有可呼叫的工具或介面MCP server
每次做法不一致、需要反覆交代Skill

用職場來比喻，App 和 MCP server 像是替新同事開通門禁、準備工具與權限，讓他有能力工作；Skill 則像交給他團隊 SOP，讓他按照團隊的方式工作。

只有門禁和工具，事情也許做得出來，但每次結果可能不同；只有 SOP，卻沒有服務權限或工具，agent 又無法完成任務。這三者處理的是不同層次的問題，不能互相取代。

把三個零件放回同一張圖

Skill 是給 agent 照著做的工作流程指示，核心是一份文字說明，也可以選擇性加入 assets 與 scripts。它放在 repo 裡，就服務這個專案；安裝在個人層級，就能跨專案使用；Plugin 則可以把一組相關 Skill 打包。Skill 提供的是「做法」，不是「能力」：它不會替你連上服務或叫動工具，而是讓 agent 用你認可的方式工作，省下每次重複交代的力氣。

到這裡，三個零件的關係就清楚了：Skill 是做法，App 是授權，MCP server 是介面。下一節會把它們放回真實情境：Codex App 裡可能有一整排 Plugin，但你不必全部安裝，而要依照手上的任務，挑出真正需要的類型。
