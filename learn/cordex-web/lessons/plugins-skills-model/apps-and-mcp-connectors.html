App 與 MCP server：一個負責授權，一個負責提供工具

Step 2/4 · Plugin、App、MCP 與 Skill 的分野

學習目標

看完這一節，你應該能分辨 app（connector）與 MCP server 的角色：前者讓 Codex 在你授權後存取外部服務，後者則把服務裡的功能暴露成 agent 可以呼叫的工具。

先判斷：Codex 卡在哪一扇門？

想像你對 Codex 說：「幫我看一下這個 repo 最近的 PR。」它卻回答看不到。這時候，問題可能完全不同。

第一種可能是：Codex 根本沒有你的 GitHub 授權，連門都進不去。第二種可能是：它已經能連到 GitHub，但「看 PR」這件事沒有被整理成它可以呼叫的動作。

前一種是 app 的問題，後一種是 MCP server 的問題。先分清楚卡在哪裡，才知道該補授權，還是該補工具。

App：解決「能不能進去」

App 有時也稱為 connector（連接器），指的是 GitHub、Slack、Notion 這類外部服務。它的核心是授權：你登入服務並授權後，Codex 才能代你存取其中的內容。

Codex 並不是突然擁有一個自己的 GitHub 帳號，而是使用你的授權去讀你的 repo、查看你的 PR，或發送你的訊息。這一層回答的是身分問題：

「這個 agent 是誰？它有資格碰這個服務嗎？」

沒有 app 授權時，Codex 對該服務就是局外人。接上 Slack，它才可能讀取你的待辦訊息；接上 Google Drive 或 Gmail，它才讀得到裡面的資料。App 就像把你的門禁卡交給 Codex，但仍然是以你的身分進入。

MCP server：解決「進去後能做什麼」

能進入服務，不代表什麼動作都做得到。

假設你經營一個 SaaS 產品，希望 coding agent 幫你列出客戶、任務和產品。你的系統裡也許早就有這些功能，但 agent 不知道該怎麼呼叫它們。這時就需要 MCP server（Model Context Protocol server）。

MCP server 會把系統內部的功能暴露成工具，並說明這些工具該如何呼叫。Agent 只需要知道工具名稱與參數，不必理解背後的資料庫結構或商業邏輯；複雜的處理仍由你的服務負責。

因此，MCP server 的核心是介面。它像一張對外的工具選單，例如：

  • list customers
  • list tasks
  • list products

這些工具決定的是：agent 進入服務後，能對服務做哪些事。它不負責判斷 agent 能不能進入服務，那是 app 的工作。

把兩者放在一起看

App 和 MCP server 通常會成對出現在同一個服務上，因為一個服務通常同時需要兩件事：先讓 agent 進來，再告訴它能做什麼。

但「成對出現」不代表「是同一件事」。授權成功，只代表拿到門票；工具暴露完整，才代表進門後有事情可以辦。

也可以把一個服務想成一棟大樓：

  • App 是門禁卡，決定你能不能進門，以及你以什麼身分進去。
  • MCP server 是服務台的辦事選單，決定進門後有哪些窗口可以辦事，以及每項手續要怎麼申請。

有門禁卡但沒有選單，你進得去，卻不知道能做什麼；有選單但沒有門禁卡，你連大廳都到不了。兩者都具備，事情才辦得成。

兩道獨立的關卡

最常見的誤解，是把「已授權」當成「什麼都能做」。其實授權與能力是兩道獨立的關卡。

授權讓 Codex 取得服務中的資料；至於能不能執行某個動作，則取決於該動作是否被包成 MCP 工具。反過來，即使工具清單寫得很完整，沒有授權，Codex 仍然拿不到資料。

所以當 Codex 說它做不到某件事時，可以先問兩個問題：

  1. 它有這個服務的授權嗎？如果沒有，是 app 的問題。
  2. 這個動作有被暴露成工具嗎？如果沒有，是 MCP server 的問題。

MCP server 作為介面，也帶來一項維護成本：它是一份需要持續維護的契約。工具名稱、參數與回應格式都必須說清楚；只要定義不完整，agent 就可能用錯。

這也是為什麼 builder plugin 常會附上一個現成的整合或 MCP server。例如，某些工具已經替特定生態系（例如 React Native 的 Expo）整理好可供 agent 使用的功能，你就不必從頭設計這層介面。

把這個分工記在腦中

App 和 MCP server 都在讓 Codex 碰得到外部服務，但分工不同：app（connector）處理授權與身分，讓 Codex 代你進入 GitHub、Slack 這類服務；MCP server 處理介面，把服務功能暴露成 agent 叫得動的工具選單。兩者常成對出現，卻不能互換：授權不等於能力，工具清單也不等於門票。

到這裡談的是「讓 Codex 能連到什麼、能叫什麼」。但有些需求既不是連接服務，也不是新增工具，而是希望 Codex 每次都依照你的做法工作。那是另一個零件 skill 要處理的問題，也是下一節的主題。
