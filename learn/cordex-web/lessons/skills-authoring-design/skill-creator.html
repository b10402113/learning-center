Skill creator：用一個 skill 生出另一個 skill

Step 1/4 · Skill 的撰寫與設計

前言：你不是不會寫，而是不想再猜格式

你可能已經發現，自己一直在重複交代同一套做法。每次新增 dashboard 卡片，都要再次說明「先讀哪些檔案、元件放在哪裡、資料怎麼接」。於是你決定把這套流程寫成 skill，讓 Codex 下次能自己讀懂。

但檔案一打開，問題就來了：名稱該怎麼取？要放在哪個資料夾？除了操作說明，還需要哪些欄位？

Skill 有自己的慣例。檔名、資料夾結構，以及開頭的描述，都會影響 Codex 能不能找到並使用它。只憑感覺手寫，很可能做出一份看似完整、實際上 Codex 根本不會讀的檔案。

這一節要介紹一條更省力的路：不要自己猜，讓一個專門建立 skill 的 skill 來處理。

學習目標

學完這一節，你應該能說明 skill creator 是什麼、它實際做了哪些事，以及為什麼每次建立 skill 時，都適合先從它開始。

Skill creator：用來建立 skill 的 skill

Skill creator 本身就是一個 skill，只是它產出的不是程式碼或一般文件，而是另一份 skill。

這個定位聽起來有點繞：用 skill 生出 skill。但它的價值也正在這裡。每當你想建立一個新的 skill，就可以先交給 skill creator，省下自己摸索格式細節的時間。

它會處理幾個最容易卡住的部分：替 skill 取合適的名稱、寫出清楚的 description、組好檔案結構，並判斷應該安裝到哪裡。原本需要自己記住的規則，變成 skill creator 內建的能力。

它實際跑起來時，會做什麼？

當你叫用 skill creator，它首先會讀取你指定的專案原始碼，掃過 codebase，找出可以重複利用的內容，例如現成元件、工具函式，以及專案沿用的樣式規則。

接著，它會把這些發現和你的需求放在一起比對，再組出一份符合專案情境的 skill。

關鍵是：你只需要描述想完成什麼，細節交給它從專案裡推斷。

例如，官方示範要建立一個「screenshot-to-component」skill。你只要告訴它：「給我一張截圖時，我希望產出真正的 UI 元件，而不是一張插圖。」

skill creator 就會去讀取專案，找出可重用的元件和樣式，再把這些內容寫進 skill 的指示裡。你不需要逐一列出元件名稱或檔案路徑；這些資訊會由它從 repo 中找出來。

Skill 組好後，它還會替你安裝到正確的位置，而不是只產出一個檔案，等你自己搬到某個資料夾。這一步不能省，因為一份內容再好的 skill，只要放錯地方，Codex 就可能在需要時找不到它。

裝在專案裡，還是裝成個人 skill？

skill creator 可以產出兩種層級的 skill。差別不只在安裝位置，也在於這份 skill 是否需要讀取特定專案的程式碼。

安裝層級放置位置適合的情境
專案 skill專案 repo 內需要使用專案實際元件與設計系統的工作流
個人 skillCodex home 層級只和個人習慣有關、希望跨專案使用的流程

如果工作流和特定專案綁在一起，就把 skill 安裝在 repo 裡。這樣它能讀到該專案真正使用的元件、設計系統與可重用零件，產出的結果也比較容易和現有程式碼接軌。

相反地，如果流程和任何特定專案都無關，只是你個人的辦事習慣，就可以請 Codex 把它安裝在 Codex home 層級。這樣一來，它就能在不同 session、不同專案中使用。

前面提到的「screenshot-to-component」之所以適合做成 repo 裡的專案 skill，就是因為它需要使用該專案的真實元件與樣式。

為什麼不自己寫就好？

你可能會想：最後不就是一份文字說明嗎？自己寫，應該也一樣。

差別在於，skill creator 不只是替你填好格式。它還會先到 repo 裡尋找可重用的零件，而這正是手寫時最容易漏掉的一步。

少了這一步，你寫出的 skill 可能只是一份泛用指示；有了這一步，skill 裡會帶著這個專案真正的元件名稱與路徑，讀起來就像熟悉這個 codebase 的人整理出來的工作方法。

所以，建立 skill 時的預設動作，應該是先叫用 skill creator，而不是立刻開一個空白的 SKILL.md 自己填。

把它放回整體觀念裡

Skill creator 是一個用來建立 skill 的 skill，也是每次撰寫 skill 時的預設入口。它會讀取你的專案，找出可重用的元件與既有慣例，替你組好名稱、描述和結構，並安裝到正確的位置。你可以讓它產出綁定 repo 的專案 skill，也可以產出跨專案使用的個人 skill。

現在你知道了「要用哪個工具生出 skill」。下一個問題是：它產出的檔案裡究竟寫了什麼？又為什麼要用那種方式組織？下一節會拆開 skill creator 的成品，帶你看清楚一份 SKILL.md 的骨架。
