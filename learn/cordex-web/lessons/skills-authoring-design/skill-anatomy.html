SKILL.md 的骨架：讓 Codex 知道何時使用、接著怎麼做

Step 2/4 · Skill 的撰寫與設計

先解決一個問題：好手冊為什麼還是可能派不上用場？

想像你請 Codex：「在 BlossomView dashboard 加一張顯示各國活躍度的卡片。」它手上可能有好幾份 skill，也要同時遵守其他 repo 指示。這時真正的問題不是「有沒有一份寫得很詳細的手冊」，而是兩件事：

第一，Codex 能不能辨認這份手冊和目前的任務有關？第二，辨認出來之後，手冊能不能告訴它如何融入現有的 codebase，而不是重新發明一套做法？

SKILL.md 的骨架正是為了分開處理這兩件事：開頭的 metadata 負責「要不要用」，正文負責「怎麼做」。只把正文寫得很長，卻沒有把觸發情境說清楚，就像把工具放進倉庫，卻不貼標籤；工具再好，也可能找不到。

開頭的 metadata：name 與 description 負責「要不要用」

一份 SKILL.md 最上面通常是 YAML frontmatter，至少包含 name 與 description。

name 是 skill 的識別名稱。description 則不是普通的產品簡介，而是提供給 Codex 的線索：目前任務出現什麼情境時，應該考慮載入這份 skill。

下面是 BlossomView 卡片 skill 的 frontmatter 原文：

---
name: blossomview-card-builder
description: Build or update cards, charts, metrics, tables, and insights for the BlossomView React dashboard. Use when asked to add a new dashboard card, analytics panel, engagement or retention metric, regional insight, live-activity section, or chart while matching BlossomView's existing Card primitives, Recharts wrappers, selected-region data, styling tokens, accessible controls, and responsive layout.
---

這段 description 刻意寫得具體。它列出可能觸發 skill 的任務，包括新增 dashboard card、analytics panel、engagement 或 retention metric、regional insight、live-activity section，以及 chart。

它也說明完成任務時不能只做出「看起來像卡片」的東西，還要配合 BlossomView 已有的 Card primitives、Recharts wrappers、selected-region data、styling tokens、accessible controls 和 responsive layout。

換句話說，這段文字同時回答兩個問題：

  • 什麼需求會叫到這份 skill？
  • 叫到之後，應該遵守哪些專案脈絡？

如果只寫「幫助你建立卡片」，描述就太模糊。Codex 可能無法把「新增區域洞察圖表」和這份 skill 連起來；即使載入，也不知道這個專案有哪些既有元件和資料規則。

正文區：把「怎麼做」寫成專案施工說明

metadata 只負責把正確的手冊找出來。真正指導實作的是它下面的正文。BlossomView skill 一開始就用一句話定下工作方式：

Build a new card as though its author already knows this codebase. Reuse the dashboard's actual components, data, formatting, and visual language.

這句話的重點不是「建立一張 card」，而是「像熟悉這個 codebase 的作者一樣建立」。好的 skill 不是泛用的 React 卡片教學，而是把團隊成員腦中的專案知識，整理成 Codex 可以依循的施工說明。

接著，正文用幾個段落把工作切開。每一段都在回答實作時會遇到的一個具體問題：

段落它要回答的問題
Start with the existing system開始前要先讀哪些檔案，例如 App、card 元件、範例卡片、資料層與 CSS？
Choose the right card這次要做獨立的 analytics 卡片、精簡的 rail insight，還是圖表？
Preserve the data contract資料是否沿用既有 props 與型別 helper，而不是自行發明 endpoint 或狀態？
Match BlossomView是否使用 @/ 別名、既有 CSS class、token 與 lucide 圖示，維持原本的視覺和版面？
Verify and hand off是否執行 typecheck／build、在不同斷點檢查瀏覽器畫面、測試 Europe 篩選，並按照 repo 規則交付？
Example requests有哪些可以直接複製使用的叫用範例？

這份清單的價值，在於它沒有停在「遵循現有風格」這種抽象提醒，而是把風格具體落到檔名、函式名、CSS class、元件、資料型別和驗證指令上。

因此，Codex 面對「新增一張卡片」時，不是從空白畫布開始，而是先查看現有系統，再選擇合適的卡片形式，沿用資料契約，最後用專案原本的工具驗證。這就像接手一間廚房：skill 不只說「煮一道菜」，還告訴你食材放在哪裡、該用哪口鍋，以及端菜前要檢查什麼。

兩種入口：自動觸發與主動叫用

除了 SKILL.md，一個完整的 skill 資料夾通常還有 agents/openai.yaml。這個檔案放的是提供給 Codex 介面的 metadata，例如 display_name、short_description 與 default_prompt。

default_prompt 會用 $skill-name 的格式叫用 skill。以這份卡片 skill 為例，會使用 $blossomview-card-builder。

這個以 $ 開頭的寫法，是你在對話中主動選擇 skill 的入口。輸入錢字號後，Codex 會列出 repo 裡的 skill、個人層級的 skill，以及系統內建的 skill，讓你直接挑選。

兩者的分工可以這樣記：

位置主要用途
SKILL.md 的 name 與 description提供觸發線索，讓 Codex 判斷某個任務是否適合這份 skill。
SKILL.md 的正文提供實作工作流，說明要讀什麼、沿用什麼，以及如何驗證。
agents/openai.yaml提供介面顯示資訊與主動叫用方式。

把這個骨架記在腦中

一份 SKILL.md 有兩塊：開頭的 name 與 description 是觸發資訊，讓 Codex 判斷這個任務該不該載入這個 skill；正文則把工作流拆成可執行的段落。name 是識別名稱，description 要具體列出觸發情境；正文的判準是「寫得像作者本來就懂這個 codebase」，放真實的檔名、元件與驗證步驟，別寫泛泛的通則。agents/openai.yaml 再用 $skill-name 的慣例讓你能主動叫用它。

這個骨架也說明了為什麼正文不該把所有細節都塞在同一份檔案裡。它可以清楚指向其他檔案，把需要時才讀取的深度內容留在外部。這不是偷懶，而是在控制每次任務需要載入的 context。
