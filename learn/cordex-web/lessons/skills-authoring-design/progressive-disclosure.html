分層設計：讓 SKILL.md 當導航，細節交給 references 與 assets

Step 3/4 · Skill 的撰寫與設計

先解決一個實際問題：細節太多，Codex 反而抓不到重點

你可能會想：既然專案地圖、資料契約和範例程式都很重要，乾脆全部寫進 SKILL.md，讓 Codex 一次讀完，不是最方便嗎？

實際上，這很容易讓 skill 變得難用。Codex 讀取 SKILL.md 時，可能只是在確認「這份 skill 跟目前的任務有沒有關係」，還沒有決定要不要真的使用它。此時如果檔案已經塞滿完整規則與大量程式碼，這些內容就會先占掉 context，反而擠壓真正與任務相關的資訊。

所以，skill 的關鍵不是把所有內容放在同一份檔案，而是把資訊分到適合的層級：先用短文件指路，需要時再深入細節，真正動手時才取出可用素材。

核心觀念：載入不等於使用

當 Codex 判斷某個任務可能和一份 skill 有關，它會先讀取那份 SKILL.md。讀進來，不代表接下來一定會照著做。它可能讀完才發現只需要其中一小段指引，也可能確認這份 skill 根本不適用。

因此，SKILL.md 應該像入口處的導覽牌，回答幾個基本問題：這個 skill 用來處理什麼情況？大致要往哪裡走？有哪些關鍵提醒？它不需要承擔整套施工手冊的重量。

更深入的內容，等 Codex 確定真的需要時再讀；範例程式和腳本，則等到真的要動手時才取出。這樣可以保留完整性，又不會在一開始就浪費 context。

三層分工：導覽、深度內容、可用素材

一個 skill 資料夾通常可以分成三層。它們的差別不只是檔案放在哪裡，也包括「什麼時候才需要讀取」。

層放什麼什麼時候被讀到
SKILL.md導覽：skill 的用途、大致流程與關鍵要點一被判定可能相關就載入
references/深度細節：各種模式、進階指引與完整規則需要深入某一部分時才讀取
assets/可直接引用的範例程式與腳本真的要使用時才複製進 repo
 
blossomview-card-builder/
├── SKILL.md                     ← 導覽：用途、流程、要點
├── references/
│   └── dashboard-card-patterns.md   ← 深度：專案地圖、資料契約、卡片／圖表模式
├── assets/
│   └── active-engagement-card.tsx   ← 素材：一份可改編的實際卡片
└── agents/
    └── openai.yaml              ← 介面 metadata

SKILL.md：像目錄，不要像整本施工手冊

SKILL.md 的工作是快速交代方向，並把 Codex 引到下一層。例如檔案裡可以只保留這樣的指示：

Read [references/dashboard-card-patterns.md](references/dashboard-card-patterns.md) before choosing the implementation.

這一句沒有試圖解釋所有實作細節，而是告訴 Codex：要選擇實作方式前，先讀哪一份文件。這正是導覽檔應有的角色。

references/：需要深入時，再打開完整規則

真正厚重的內容可以放在 reference。以這份 card skill 為例，reference 裡包含專案地圖、資料契約，連同 useState 與 getCities 的片段，還有完整尺寸的 analytics 卡片模式、使用 ChartContainer 和 Recharts 的圖表模式、精簡側欄模式，以及視覺與互動的斷點規範。

如果把這些內容全部塞進 SKILL.md，檔案很快就會膨脹好幾倍。拆成 reference 後，Codex 只有在確定要挑選實作方式時，才需要把這些細節拿出來。導覽保持輕巧，深度則沒有被犧牲。

assets/：範例程式等到要用時再拿

assets 放的是可以直接使用或改編的素材。這份 card skill 的 assets 裡有一份 active-engagement-card.tsx，是一張真的能跑的卡片，示範如何從 cities 推導資料、排序前六名國家，再透過既有的卡片元件與 token 樣式畫出圖表。

SKILL.md 對它的定位，是把它當成起點，依實際需求改名和改寫，而不是原封不動掛上去。

assets 也可以放腳本。常見做法是準備一支腳本，等需要時再把 assets 裡的範例檔複製進 repo。如此一來，範例程式平常只是安靜地放在 assets 裡，不會占用 context；等真正要實作時，才由腳本搬進工作區。

這和把大量範例程式直接寫進 SKILL.md 的差別，就像工具箱和背包的差別：工具箱可以很完整，但你不必每天把所有工具背在身上。

三層如何串在一起

實際使用時，流程大致是這樣：Codex 先因為任務可能相關而載入 SKILL.md，讀取 skill 的用途、方向與關鍵提醒；接著，如果確定需要更深的模式，就去讀 references；最後，真的要動手時，再取出 assets 裡的範例或腳本。

沒有被用到的層，就不必在一開始載入。這就是分層設計的價值：不是把資訊藏起來，而是讓資訊在正確的時機出現。

可以把它想成一本旅遊指南：

  • SKILL.md 是書封與目錄，讓你快速知道這本書在講哪個城市，以及是否適合目前的旅程。
  • references/ 是各區域的深度介紹，決定要去某一區時再翻。
  • assets/ 是書末附的地圖與表格，需要時才拆下來帶著走。

好的旅遊指南不會把整本內容塞進目錄裡；好的 skill 也不會把所有細節塞進 SKILL.md。

把這個判斷記住

Codex 載入 SKILL.md，不等於一定會使用它。因此，SKILL.md 要短，負責說明用途、方向與要點；深度內容放進 references/，需要時才讀；可直接引用的範例程式與腳本放進 assets/，真的要用時才複製進 repo。三層分工後，Codex 平常只讀到薄薄的導覽，需要時才逐層往下取，context 就不會在一開始被灌滿。

掌握這個分層方式，你就能寫出結構清楚、載入成本合理的 skill。接下來要處理的是另一個判斷：當某個工作流反覆出現時，什麼情況值得把它做成 skill？它又應該放在專案裡，還是安裝在自己的層級？
