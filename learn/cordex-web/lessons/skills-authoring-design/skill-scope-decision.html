專案 skill 還是個人 skill：工作流該放在哪裡？

Step 4/4 · Skill 的撰寫與設計

先解決一個常見問題：skill 到底該放哪裡？

前三節你已經走過 skill 的完整流程：用 skill creator 產生它、理解 SKILL.md 的骨架，也知道如何用三層分工控制 context。接下來最容易遇到的問題是：一個重複出現的工作流，究竟該寫進專案，還是裝在自己的 Codex 環境裡？

這不是單純的檔案位置問題，而是使用範圍的選擇。工作流如果依賴某個 repo 裡的元件、資料或設計系統，放錯位置就像拿錯工具箱；反過來，一個跨專案都適用的習慣若綁在單一 repo 裡，每次換專案都得重新搬一次。

還有第三種情況：有些規則根本不該寫成 skill，而應該放在 AGENTS.md。下面用比較表和判別問題，把這幾種情況分開。

兩個選項：放在專案裡，還是跟著你走

選項放在哪裡它讀得到什麼適合的情況
專案 skill專案 repo 內，例如 skills/這個專案實際使用的元件、資料、樣式與檔案路徑工作流必須使用這個 codebase 的真實零件
個人 skillCodex home 層級你寫下的通用指示，不依賴特定專案程式碼工作流跨專案都適用，而且你希望每個 session 都能使用

判斷關鍵在於：這個 skill 是否需要碰到真實的程式碼。

專案 skill 可以直接指向該 repo 裡真正存在的元件與設計系統。例如 BlossomView 卡片 skill 能指定實際的 src/components/ui/card.tsx，也能使用現有的 compactNumber helper。這讓 Codex 產出的結果貼近專案現況。

個人 skill 則不能預設任何特定檔案。它跟著你跨專案移動，因此適合放不依賴特定 codebase 的工作方法，而不是某個專案的零件清單。

判別問句：先問自己三件事

不要靠直覺選位置，可以依序回答下面三題：

  1. 這個工作流需要 repo 裡真實的元件、設計系統或檔案路徑嗎？如果需要，就寫成專案 skill。只有放在 repo 裡，它才取得到那些零件，產出也才會跟專案一致。
  2. 這個工作流和任何特定專案都無關，而且你跨專案都會用嗎？如果是，就裝成個人 skill。這樣每個 session 都能呼叫，不必在不同專案裡重寫。
  3. 你已經重複執行這個工作流很多次了嗎？如果只是一次性的任務，先不要急著建立 skill。skill 需要建立與維護成本，重複次數不夠多時，通常不划算。

另一個判斷：這是慣例，還是工作流？

還要多問一題：這件事是整個 repo 都該遵守的通則，還是有明確輸入與產出的工作流？

例如「改前端前先讀哪兩份 skill」或「一律使用某個套件畫圖表」，這類規則是 repo 的一般慣例，應該放進 AGENTS.md，而不是 skill。

可以這樣分工：

  • AGENTS.md：放一般慣例與路由規則，告訴 Codex 在這個 repo 裡通常該怎麼做。
  • 專案 skill：放可重複執行的實作細節，告訴 Codex 如何完成某一類具體工作。

把 repo 通則寫成 skill，就像把大樓入口的公告藏進某本工具手冊裡：規則雖然存在，卻不一定會在正確的時機被看見。

哪些重複工作值得做成 skill？

當一個工作流會反覆出現，而且有固定的實作細節可以整理，就值得考慮做成 skill。常見例子包括：

  • 資料驅動的定期更新：例如定期抓 analytics，依瀏覽量更新「熱門使用案例」清單的排序。計算與更新流程固定，很適合交給 skill。
  • 標準化的狀態元件：如果全 app 的空狀態與載入狀態都要一致，可以把產生這些畫面的方式整理成 skill，避免每次重新設計。
  • 使用既有設計系統組合複合介面：如果團隊已有 design system 或 Storybook，可以把「如何用既有元件組出新畫面」寫成 skill，讓產出維持一致。
  • 組裝插圖：把多個小型插圖零件放進 assets，再用腳本依規則拼成完整構圖。這是 assets 資料夾搭配腳本的典型用法。

反例：不是所有規則都該變成 skill

有幾種情況，建立 skill 反而會增加維護負擔：

  • 一次性的任務：做完就不會再用，沒有必要承擔建立成本。
  • 整個 repo 都適用的通則：應該放在 AGENTS.md，而不是藏在 skill 裡。
  • 已經有現成指令或測試負責的規則：不需要再用 skill 重述，否則可能出現兩份不同步的規範。

這裡的判斷不是「能不能寫成 skill」，而是「寫成 skill 後，是否真的比現有做法更可靠」。如果只是把同一條規則複製到另一個地方，最後可能多出一份需要同步的文件。

可以直接套用的決策規則

先問：這個工作流會反覆出現嗎？不會，就不要做成 skill。會的話，再問它是否需要 repo 裡真實的元件與設計系統：需要，就放在專案 skill；不需要，而且跨專案都適用，就裝成個人 skill。若它只是整個 repo 都該遵守的通則，就寫進 AGENTS.md。

要碰到 repo 的真實零件，放專案；只跟你的通用習慣有關，跟著你走；只是 repo 通則，交給 AGENTS.md。

小結：做決定前的快速檢查表

  • 會不會反覆執行？不會：先不要做 skill。
  • 需要 repo 的元件、設計系統或路徑嗎？需要：專案 skill。
  • 跨專案都適用嗎？適用：個人 skill。
  • 是整個 repo 都該遵守的慣例嗎？是：AGENTS.md。

值得做成 skill 的工作，常見有資料驅動的定期更新、標準化的空狀態與載入狀態、用設計系統組合複合介面，以及用 assets 搭配腳本組裝插圖。

到這一步，你已經能用 skill creator 生出 skill、看懂 SKILL.md 的骨架、用三層分工控制 context，也能判斷工作流是否值得做成 skill，以及它應該放在專案層級、個人層級，還是根本應該交給 AGENTS.md。
