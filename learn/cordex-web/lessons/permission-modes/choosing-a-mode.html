怎麼選 permission mode：一份可以直接照做的決策規則

Step 4/4 · Permission mode：在安全與自動化之間做取捨

你現在要做的決定

前面已經看過四種 permission mode：每次都要求你核准的 Ask for approval、由另一條執行緒協助判斷的 Approve for me、完全不詢問的 Full access，以及由你自訂規則的 Custom。

現在真正的問題不是「每個模式是什麼」，而是：你的機器、工作內容和操作習慣，適合把多少決定交給 Codex？選得太保守，agent 會一直卡在等你；放得太寬，則可能讓不該執行的動作直接通過。

下面先用一張表快速對照，再用四個問題判斷特殊情境。最後也會說明幾個規則會翻轉的反例，避免把建議當成永遠不變的答案。

先用情境比較四個模式

情境建議模式取捨

用四個問題判斷

如果你的情境沒有完全落在表格裡，依序問自己下面四個問題。它們比單純問「我信不信任 AI」更有用，因為真正的風險通常來自機器、動作和工作方式。

一、這台機器上有沒有你輸不起的東西？

只要答案是「有」，就不要選 Full access。這裡看的不是你此刻有多放心，而是機器上是否有重要資料、正式環境或其他無法承受的損失。

二、這個動作做錯後，能不能收回來？

如果動作不可逆，讓它先問你。Approve for me 會攔下它判斷為危險的操作；但如果你連「由它判斷安全」這件事都不想賭，就改用 Ask for approval，逐步確認每一個動作。

三、你是不是同時跑好幾個 agent？

如果是，通常不要選「每個動作都問」。你很快就會被一堆核准請求綁在螢幕前，既無法同時照顧多個 agent，也失去讓它們並行工作的好處。

四、你要的是「幫我判斷」，還是「照我的規則」？

如果你希望 Codex 依照情境判斷哪些操作需要攔下來，用 Approve for me。如果你需要一套完全可預期、只有符合條件才放行的規則，就用 Custom。

反例：規則什麼時候會翻轉

上面的建議不是死規則。幾個關鍵情境改變後，選擇也會跟著改變。

Full access 不是永遠不能用。如果你是在專門跑過夜 agent 的隔離機器上工作，那台機器沒有重要資料，還使用獨立的 Git 帳號，Full access 就可能是合理選擇。但同一個人回到工作機時，應該切回 Approve for me。決定界線的是「機器上有什麼」，不是「你是否信任 AI」。

Ask for approval 也不是永遠太慢。當動作不可逆，而且你事先無法清楚描述哪些情況應該放行時，慢一點是值得的。真正麻煩的不是偶爾慢，而是把它設成日常預設，最後被大量核准請求拖垮。

Custom 也不是規則越嚴越好。如果規則訂得太死，又沒有隨專案更新，合法的工作也可能被擋下來。到頭來你必須不斷手動放行，反而失去自訂規則原本想帶來的穩定性。

搭配使用的操作習慣

模式選對之後，幾個小習慣會直接影響你是否需要一直盯著畫面。

如果你同時跑多個 agent，可以善用 app 裡的 pet。它會在畫面上顯示各個對話的狀態，讓你在使用其他 app 時，也能快速看出哪個對話正在等你核准、哪個已經完成。你可以在設定中選擇或建立 pet，也可以匯入家中狗狗的照片來製作。它的用途就像一位站在旁邊的提醒員，替你留意那些真的需要出手的時刻。

最常觸發核准的動作是 computer use，也就是 Codex 直接在你的電腦上點選和操作。桌面版能存取本機檔案與應用程式，因此它能碰到的範圍比純雲端版本更大；這也是為什麼這道核准關卡更值得保留。

有一條規則可以直接記住：工作機永遠不要使用 Full access。其他選擇可以依照情境調整，但這條界線不要拿工作機來測試。

最後的決策檢查表

先問：這台機器上有我輸不起的東西嗎？有，就不要選 Full access。再問：這個動作不可逆嗎？是，就讓它先詢問；如果連模型判斷安全都不想承擔，就用 Ask for approval。接著問：我同時跑多個 agent 嗎？是，就不要讓每個動作都停下來等核准。最後問：我要 Codex 幫我判斷，還是嚴格照我的規則？前者用 Approve for me，後者用 Custom。一般情況預設選 Approve for me；Full access 只留給隔離、可拋棄的機器；工作機永遠不選 Full access。

這套規則的核心很簡單：把安全而重複的操作交給自動化，把不可逆或高風險的判斷留給人。下次切換 permission mode 時，不必重新猜一次，照著機器、動作、並行數量與規則需求逐項檢查，就能做出合適的選擇。
