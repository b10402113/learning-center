Permission mode 解決什麼問題：自動化與安全的那條線

Step 1/4 · Permission mode：安全與自動化的取捨

學習目標

看完這一節，你應該能說明 permission mode 在解決什麼問題，也能辨認「每件事都要你核准」和「完全不核准」這兩個極端，為什麼都不適合長時間使用。

先看情境：為什麼 Codex 要停下來問你？

你把任務交給 Codex，起身去倒杯水。回來時卻發現它卡在原地，只等你按一下「核准」。原來它想安裝一個套件，而這個動作被權限設定攔住了；你按下核准，它才繼續工作。

這種停頓確實令人煩躁，但它其實在處理一個很根本的問題：一個會自己執行動作的 agent，什麼時候可以直接做，什麼時候應該先問你？

反過來想，如果完全關掉核准，Codex 想做什麼都能直接做。當模型判斷錯誤，或你下的指令有歧義時，它可能在你沒注意的時候刪掉資料夾。這類錯誤一旦發生，往往很難收拾。

permission mode 處理的，就是自動化效率和操作安全之間的界線。先理解這條界線，後面才知道該把它畫在哪裡。

為什麼需要這道關卡？

Codex 在工作時可能會執行終端機指令、安裝函式庫、新增或修改檔案；桌面版甚至能存取你電腦上的檔案與應用程式。

這些動作的風險並不相同。讀取檔案、執行測試，或安裝一個套件，通常就算做錯，也還能修正。但刪除不該刪的資料，或把變更推送到錯誤的位置，就可能無法恢復。

問題在於，同一個工作迴圈裡往往同時混著這兩類動作：有些安全，可以自動執行；有些危險，最好先讓你確認。因此需要一個判斷點，決定每個動作要直接放行，還是暫停並請你核准。

這就是 permission mode 的角色。它不是單一的開關，而是一條從「每件事都要問」到「完全不問」的光譜。

兩個極端，失敗方式剛好相反

光譜的一端是每個指令都要你核准。這種方式看起來最安全，因為沒有任何動作會在你不知情時發生；代價是你必須一直盯著螢幕。

如果你同時開著三、五個 agent，讓每個指令都停下來等你按核准，就很難真正放手讓它們工作。最後你不是在管理任務，而是在不停替 agent 按按鈕。自動化的好處也因此消失了。

另一端是完全不經核准。它的速度最快，工作不會被打斷，但你等於把整台機器交給一個偶爾會誤判的模型。它可能只是想清理暫存資料，卻刪到其他資料夾；也可能在你開會時改掉重要設定。

風險不在於它每次都會出錯，而在於出錯時你可能根本不在場。等你發現問題，動作往往已經完成，甚至無法回復。

模式對你的要求壞在哪裡
全部要你按每個指令都停下來等你核准你被綁在螢幕前，無法放著跑，也很難同時管理多個 agent
全開完全不問你可能在你不知情時做出不可逆的事，例如刪掉資料夾

把它想成施工時的鑰匙

可以把這件事想成請師傅到家裡施工。

如果你堅持站在旁邊，每一道門都親自開，師傅雖然不會拿錯工具，卻也無法真正替你省事。相反地，如果你把所有鑰匙都交給他，自己出門，他就可能敲錯一面牆，而你直到回家才發現。

比較合理的做法，是讓一個可信任的機制協助看守：安全的動作直接放行，看起來有風險的動作才回頭詢問你。這樣既保留自動化的速度，也不會把所有不可逆的決定完全放手。

把 permission mode 放回整個工作迴圈

Codex 的工作迴圈會執行指令、修改檔案；桌面版還可能存取你電腦上的檔案與應用程式。這些動作有的安全、有的不可逆，因此需要一道判斷關卡。什麼都問，會把你綁在螢幕前；什麼都不問，則可能讓 Codex 在你沒注意時做出無法挽回的事。合理的設計是自動放行安全的多數，只把危險的少數交回給你確認。這正是 approve for me 所扮演的角色。

所以，permission mode 不是在「安全」和「速度」之間二選一，而是在工作迴圈中替不同風險的動作安排不同程度的自主權。接下來要看的 approve for me，正是把這條中間路線具體化：由另一條執行緒判斷指令是否安全，再決定哪些動作可以自動放行，哪些仍然必須回頭問你。
