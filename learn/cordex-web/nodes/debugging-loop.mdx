# 除錯迴圈：browser use／CDP／computer use

## Learning goal

能用 browser use／CDP／computer use 跑出「重現→診斷→修→驗證」的前端除錯迴圈，並判斷何時需要人類介入。

## Steps

依序讀：先建立「除錯迴圈是默認工作流」的心智模型，再看懂它手上的四種工具各自看到什麼，接著照著跑一次完整的迴圈，最後學會判斷何時該放手、何時得自己當 judge。

1. [[learn/cordex-web/nodes/debugging-loop/debugging-loop-default|為什麼除錯迴圈才是 Codex 的默認工作流]] — 理解「重現→診斷→修→驗證」為何是默認工作流，以及重現為何要先做
2. [[learn/cordex-web/nodes/debugging-loop/codex-debug-toolbox|Codex 的除錯工具箱：browser use、CDP、截圖與 computer use]] — 分辨四種工具各自看到什麼，以及 browser use 與 computer use 的差別（after step 1）
3. [[learn/cordex-web/nodes/debugging-loop/reproduce-fix-verify|跑一次除錯迴圈：從 bug 報告到根因修復]] — 用一則「症狀＋期望行為」的 bug 報告跑完重現→修根因→多斷點驗證（after step 2）
4. [[learn/cordex-web/nodes/debugging-loop/human-in-the-loop|什麼時候該放手、什麼時候得自己當 judge]] — 用判別條件決定何時放手自走、何時人類介入（after step 3）

## Lesson

前面幾個節點教你用 Codex 把東西「做出來」，但真實專案裡絕大多數時間是花在「東西壞了、把它修好」。這個節點講的是那件事背後的默認節奏：除錯迴圈。它的骨架只有四步——先重現一個穩定重複的問題，再讓 Codex 用它的工具去診斷，接著修掉根因，最後驗證真的修好了。很多人做不出成果，不是因為不會下 prompt，而是因為跳過了第一步：對一個只出現過一次、根本重現不出來的現象猛猜。

Codex 之所以能把這個迴圈跑起來，是因為它手上有四種「感官」：browser use 讓它真的去點、去捲、去重現；CDP（Chrome DevTools Protocol）讓它看到你在 DevTools 裡看到的 logs、network、layout；它還能自己截圖；而 computer use 把同樣的能力延伸到瀏覽器以外、任何桌面上開得起來的 app。搞懂每個工具看到什麼，你才知道一句模糊的「畫面怪怪的」為什麼它能查、又能查到多深。

但有工具不代表全自動。這個節點最後會逼你做一個判斷：哪些問題放手讓 Codex 自己跑一輪就對了，哪些問題非得你出面說「這才是我要的」不可。走完之後，你拿到的不只是修 bug 的手法，而是「除錯這條路什麼時候自己走、什麼時候喊人」的分寸感。
