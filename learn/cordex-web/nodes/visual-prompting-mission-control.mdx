# 用視覺範例提示：Mission Control

## Learning goal

能用視覺範例（moodboard／fixtures／真實 plugin）提示 Codex，產出貼合方向的 dashboard。

## Steps

1. [[learn/cordex-web/nodes/visual-prompting-mission-control/visual-direction-vs-material|為什麼只用文字描述會做出通用介面：視覺方向與素材]] — 分辨 moodboard、fixtures 與真實 plugin 各自解決什麼問題
2. [[learn/cordex-web/nodes/visual-prompting-mission-control/deterministic-fixture-contract|Fixture 資料契約：穩定 ID、refresh 與 reset]] — 出一份生成式 app 必須遵守的資料契約（after step 1）
3. [[learn/cordex-web/nodes/visual-prompting-mission-control/mission-control-prompt-anatomy|拆解 Mission Control 的 prompt：把 moodboard 與 fixtures 收斂成一份 spec]] — 照結構寫出一份 dashboard prompt（after steps 1–2）
4. [[learn/cordex-web/nodes/visual-prompting-mission-control/visual-iteration-loop|用 annotation、appshot 與 browser use 把產出調到你要的方向]] — 用視覺回饋迭代，而不是只用文字描述（after step 3）

## Lesson

用文字描述你要的畫面，Codex 只會回你一個「哪裡都適用」的通用介面。視覺範例提示解決的正是這件事：與其把預設值講成一段形容詞，不如直接給它一張 moodboard 當視覺方向、給它一組 fixtures 當資料素材，讓產出一開始就落在你要的調性上。

這一節用 Mission Control（個人工作儀表板）當範例，走完四個步驟。第一步先建立觀念：視覺方向與素材是兩種不同的輸入，moodboard 負責「看起來像什麼」，fixtures 或真實 plugin 負責「裡面有什麼資料」。第二步把 fixtures 的資料契約攤開——虛構標記、固定時間基準、穩定 ID，以及 refresh 與 reset 的差別，這些是生成式 app 之後能不能正確重跑的前提。第三步拆解 Mission Control 的 prompt 結構，看它怎麼把 moodboard、fixtures 與功能清單收斂成一份可執行的 spec。最後一步講迭代：用 annotation 把意見釘在元件上、用 appshot 帶上 app 上下文、用內建瀏覽器的 picture-in-picture 在各斷點自己驗證。

四步走完，你會有一套可重複的視覺提示流程：方向用圖給、素材用資料給、品質用驗證收尾，而不是全部塞進一段文字裡祈禱它猜對。
