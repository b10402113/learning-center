# Goals：把長工交給 Codex 自走

## Learning goal

能寫出帶驗收條件的 /goal，讓 Codex 長時間自走並在跑動中修正方向。

## Steps

1. [[learn/cordex-web/nodes/goals-and-delegation/what-goals-solve|/goal 解掉什麼問題：為什麼 Codex 只跑一輪就停]] — 說出 goal 與一般 prompt 的差別，以及長工為什麼需要驗收條件
2. [[learn/cordex-web/nodes/goals-and-delegation/writing-a-goal-with-acceptance-criteria|寫一個 goal：寬的目標，加上可驗收的停止條件]] — 動手寫出「寬目標＋驗收條件」，含前端視覺檢查與 eval／golden set 兩種形式（after step 1）
3. [[learn/cordex-web/nodes/goals-and-delegation/feeding-a-goal-real-work|把真實工作餵進 goal：ticket、spec 與獨立 worktree]] — 接 ticketing system，用 grill-me → spec 檔 → /goal 把一張票變成可自走的長工（after step 2）
4. [[learn/cordex-web/nodes/goals-and-delegation/steering-and-supervising-a-running-goal|跑到一半該不該插手：監督、修正與收尾的判準]] — 判斷何時放手、何時插手，並知道它靠什麼自我驗證（after step 2）

## Lesson

`/goal` 是 Codex 用來跑長工的模式：你給它一個結果，再給它「怎樣算做完」的驗收條件，它就會一輪一輪做下去，直到能證明條件成立才停。這和一般 prompt 最大的不同，在於一般 prompt 常常只換來一輪輸出，遇到需要反覆打磨、需要多趟驗證的任務，Codex 很容易做了一版就停手；goal 正是補上那個「不要停，直到某個狀態為真」的缺口。

這個節點把 goal 拆成四步。第一步先建立心智模型：goal 解掉什麼問題、什麼時候該用、什麼時候根本不值得用。第二步動手寫：一顆好的 goal 出乎意料地是「寬的目標＋驗收條件」，而不是把所有細節都寫死，驗收條件又分成前端視覺檢查與 eval／golden set 兩大類。第三步把 goal 接上真實工作流——從 ticketing system 拉一張票，先 grill 出規格檔，再讓 goal 引用它，並在獨立的 worktree 上開跑。第四步談自走時的監督：它內部用什麼在追蹤進度、它如何自我驗證、什麼情況一定要人來當「好不好看」的裁判，以及你該在什麼時候送新 prompt 修正方向。

走完之後，你手上會有一套把「動輒數小時到數天的任務」交出去的寫法，而不是每次都下一個只能撐一輪的 prompt。
