# Living frontends：skill 驅動的介面

## Learning goal

能理解並實作 skill 驅動的 living frontend（視覺化輸出、互動文件、screenshot-to-component）。

## Steps

1. [[learn/cordex-web/nodes/living-frontends-skill-driven-ui/what-are-living-frontends|什麼是 living frontends：Codex 當場發明的新互動]] — 說出 living frontend 的定義，以及為什麼要把它寫成 repo 裡的 skill
2. [[learn/cordex-web/nodes/living-frontends-skill-driven-ui/visualized-output-and-interactive-docs|視覺化輸出與互動文件：把答案畫出來，把程式碼重建成體驗]] — 解釋 visualized skill 與「指著程式碼重建體驗」的模式（after step 1）
3. [[learn/cordex-web/nodes/living-frontends-skill-driven-ui/screenshot-to-component|動手做 screenshot-to-component：把截圖重建成可編輯的元件]] — 用一段 prompt 產出 skill，並知道驗收檢查點（after steps 1–2）
4. [[learn/cordex-web/nodes/living-frontends-skill-driven-ui/when-to-build-living-frontends|什麼時候該做 living frontend：靜態插圖 vs 活元件]] — 判斷該靜態還是改造成活元件，兼顧維護與曝露給 agent（after steps 2–3）

## Lesson

這個節點談的是一種新的前端用途。前面幾個節點都在處理「怎麼用 Codex 把一般前端做得更快、更穩、更貼合設計系統」；這裡要往下一步問：如果 Codex 能當場發明一種全新的互動、一個原本不存在的元件，那會是什麼樣子？Katia 把這種東西叫 living frontend——不是把介面做得更花俏，而是生出新的互動型態，例如讓答案用圖表呈現而不是一段文字、讓文件本身就變成可操作的小應用、讓一張截圖被重建成真正能改的程式碼元件。

這種能力的關鍵瓶頸不是技術，而是「換別人就做不出來」。一位很強的工程師可以親手刻出各種動畫、可以手做某個元件，但當另一個人也想替同一個 repo 加上同樣風格的東西時，他得把原作者找來才有辦法。skill 解掉的就是這件事：把「怎麼做出這種互動」寫進 repo，變成任何人都能重複呼叫的流程。於是 living frontend 就從一個人一次的炫技，變成團隊的常備能力——這也是它和單純「更快的 AI 前端」最大的差別。

四步的順序是：先建立定義（living frontend 是什麼、為什麼要 skill 化），再看三個從 learn.chatgpt.com 借來的實例（visualized 輸出與互動文件），接著動手做最實用的那個 skill（screenshot-to-component），最後回到判斷：什麼時候值得把一塊靜態的東西改成活的、要怎麼維護它不會過期，以及把這些互動曝露給 browser agent 之後的未來長什麼樣。走完你應該能分辨「這只是一張插圖」和「這是一個能自己活的元件」，並且知道用手上的 Codex 把後者做出來。
