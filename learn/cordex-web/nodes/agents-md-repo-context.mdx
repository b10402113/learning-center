# AGENTS.md：把 repo 變成 Codex 的上下文

## Learning goal

能為一個 repo 寫出讓 Codex 自我引導的 AGENTS.md（設計系統、指令、repo map），讓非工程師也能安全改動。

## Steps

1. [[learn/cordex-web/nodes/agents-md-repo-context/why-repo-context|為什麼 repo 要自己說故事：把上下文寫進版本庫]] — 搞懂共享 repo 為什麼要把上下文編碼進 repo，以及不編碼會付出什麼代價
2. [[learn/cordex-web/nodes/agents-md-repo-context/agents-md-anatomy|AGENTS.md 裡該有什麼：一份可查閱的區塊清單]] — 認出六類區塊與 Codex 的解析規則（after step 1）
3. [[learn/cordex-web/nodes/agents-md-repo-context/writing-agents-md|動手寫一份 AGENTS.md]] — 照程序寫出真實指令、repo map、skill 路由、慣例與 PR 證據（after step 2）
4. [[learn/cordex-web/nodes/agents-md-repo-context/agents-md-vs-skills|什麼進 AGENTS.md、什麼進 skill]] — 用判別條件切開政策與可重複流程，避免 context 爆掉（after step 2）

## Lesson

一個共享的 repo，最貴的資源不是程式碼，而是「大家腦子裡的那套默契」——哪個資料夾屬於誰、圖表要用哪個套件、改 UI 要驗哪些斷點、PR 要附什麼證據。當這些默契只存在工程師腦中，Codex 每個人都會用自己的一套做法，工程師就被卡成審查瓶頸。這一節課要做的，就是把默契從腦中搬到版本庫裡，變成一張 Codex 讀得到的地圖。

這張地圖主要是 AGENTS.md，但光有一份 AGENTS.md 不夠。政策類的東西（指令、邊界、慣例、驗證與 PR 規則）寫在 AGENTS.md；可重複的實作細節（某類卡片怎麼組、要讀哪些檔案）留給專案的 skill，並用 SKILL.md／references／assets 分層控制載入量。四步走完，你會知道為什麼要寫、一份完整的 AGENTS.md 長什麼樣、怎麼動手寫，以及什麼時候該把它拆到 skill 裡。
