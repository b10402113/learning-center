# Execplans：讓決策撐過 compaction

## Learning goal

能用 execplans 把架構決策寫進 repo，撐過 context compaction 與跨 session、跨同事的 Codex。

## Steps

1. [[learn/cordex-web/nodes/execplans-decision-log/why-decisions-fade|為什麼 Codex 會忘記你當初為什麼這樣做]] — 搞懂 context 退化與 compaction 為什麼會弄丟重要決策
2. [[learn/cordex-web/nodes/execplans-decision-log/what-is-an-execplan|Exec plan 是什麼：寫在 repo 裡的活文件]] — 認出 exec plan 的定義與它「活的」在哪裡（after step 1）
3. [[learn/cordex-web/nodes/execplans-decision-log/write-a-decision-log|寫一份撐得過 compaction 的決策日誌]] — 照著寫出最小可用的四塊內容（after step 2）
4. [[learn/cordex-web/nodes/execplans-decision-log/wire-execplans-into-agents-md|讓 Codex 自己寫 exec plan：AGENTS.md 指引與專屬資料夾]] — 用 AGENTS.md 與專屬資料夾讓 Codex 自動產生計畫（after step 2）
5. [[learn/cordex-web/nodes/execplans-decision-log/when-execplans-matter|什麼時候值得開 exec plan]] — 用判別條件決定哪些工作值得開、哪些划不來（after steps 3–4）

## Lesson

Codex 的記憶有一個實體限制：context window 塞到一定程度之後，輸出品質會慢慢下墜，而 compaction（把上下文壓成摘要）本質上是在擲骰子，你無法保證哪些重要決策會被留下。當你反覆迭代一個介面、或在一段跑好幾個小時的 goal 裡來回修改演算法，一被壓縮，Codex 就可能忘記「當初為什麼要這樣改」，於是把一個深思熟慮的決定改掉。

這個節點談的解法很務實：把每一個決策寫進 repo。Codex 團隊把這種寫在 repo 裡、隨工作持續更新、由 Codex 自動建立的活文件叫做 exec plan，它不是什麼業界標準，只是他們自己取的名字。當 AGENTS.md 裡有「什麼是 exec plan、什麼時候該建立」的指引，再加一個專屬資料夾，Codex 每加一個新功能或下一個重要決定，就會自己把計畫寫下來。

五步走完，你會先懂「決策為什麼會消失」，再認出 exec plan 是什麼；接著動手寫一份含目的、進度、意外與發現、決策紀錄的日誌，並把它接進 AGENTS.md 讓 Codex 自動維護；最後拿到一組判別條件，知道哪些工作值得開 exec plan——長時間的 goal、複雜演算法的反覆迭代、後端或大型專案、以及需要跨 session 或跨同事協作的時候。
