# Skill 的撰寫與設計

## Learning goal

能用 skill creator 打造專案／個人 skill，並用 SKILL.md＋references／assets 的分層設計控制 context。

## Steps

1. [[learn/cordex-web/nodes/skills-authoring-design/skill-creator|Skill creator：用一個 skill 生出 skill]] — 認識 skill creator 是什麼，以及它為什麼是建立 skill 的預設入口
2. [[learn/cordex-web/nodes/skills-authoring-design/skill-anatomy|SKILL.md 的骨架：觸發描述與指引段落]] — 讀懂一份好 SKILL.md 由哪些部分組成（after step 1）
3. [[learn/cordex-web/nodes/skills-authoring-design/progressive-disclosure|分層設計：SKILL.md 當導航，references 與 assets 放細節]] — 用三層分工把 context 控制在該用的地方（after step 2）
4. [[learn/cordex-web/nodes/skills-authoring-design/skill-scope-decision|專案 skill 還是個人 skill：工作流該放在哪]] — 判斷一個重複工作流該不該變成 skill、又該放在哪一層（after steps 1、3）

## Lesson

前面幾個節點談的是「用 Codex 出貨」，這一節換一個角度：把自己反覆交代的做法，變成 Codex 下次讀得到的固定指示，也就是 **skill**。你不會從空白檔開始手寫——建立 skill 的標準做法是先叫出 **skill creator**，讓它去讀你的 repo、抓出可重用的元件與慣例，替你組好 name、description 與骨架。你真正要做的是設計：這份 SKILL.md 只放「導航」——什麼情況該用它、大致流程長怎樣——而把深度的模式放進 **references/**、把可引用的範例程式與腳本放進 **assets/**。這樣 Codex 在被觸發時讀到的是一份短文件，只有在真的需要時才往下一層拿細節，context 才不會一開場就被灌爆。最後回到取捨：這個工作流需要 repo 裡真實的元件與設計系統，就該寫成專案 skill；只跟你的習慣有關、跨專案都用得上，才適合裝成個人 skill。
