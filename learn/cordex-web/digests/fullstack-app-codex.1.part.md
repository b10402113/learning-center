# Digest — fullstack-app-codex (part 1)

## Overview (L1)

- **Course framing & mental model (0–2).** Spencer Schneidenbach (Avaron Labs, Microsoft MVP) teaches "Backend Development with Codex" by building a real auction/bids site. Core thesis: an agentic harness is just a loop (model + file-system access + shell), and the engineer's job is to make a non-deterministic system as deterministic as possible via guardrails, constraints, and back pressure. He prescribes an opinionated, minimalist setup: Codex desktop app, GPT-5.6 Sol at medium effort/fast mode, approve-for-me permissions, no MCP servers, a few custom skills. Thinking effort ranges medium→extra-high/Ultra; Ultra fans out to subagents and is token-heavy; delegating to cheaper models (Luna max effort) stretches usage.
- **Setup & planning workflow (3–7).** Deliberately choose the tech stack rather than vibe it: TypeScript, React (Vite), Fastify, Zod, Socket.io, Playwright, Docker, Postgres, Redis, RabbitMQ, Jaeger. Install small global custom skills via `npx skills@latest add schneidenbach/skills` (grill-me, grill-with-docs, domain-modeling). Enable native browser-use/computer-use instead of Chrome MCP; write a curated `agents.md` for repo context (Claude imports it via `claude.md`). Start a feature by grilling: plan mode is native but shallow, so `grill-me` asks relentless branching questions and `grill-with-docs` captures answers in a context/glossary doc; answers force upfront decisions and add certainty/back pressure.
- **Building the CRUD core (8–9).** Copy foundation into tiered folders and build vertical slices. Slice 1 persists auctions, bids, and a mocked user table (10 seeded users, footer switcher, active user in localStorage) in Postgres via raw SQL + explicit migrations (no ORM). Slice 2 posts auctions; slice 3 places bids with validation (no self-bidding, min +$1, ended auctions rejected, compact bid history). Codex generates Mermaid diagrams, tests, and runs browser verification itself.
- **Concurrency & row locking (10–14).** The naive `INSERT` bid allows competing bids to read the same stale price and produce duplicate equal bids. Rather than vibe-fixing, write a Playwright "bidding war" (four tiled browser windows, chaos, sellers/bidders) that reproduces the bug, then grill a fix. Fix = a short Postgres transaction that `SELECT ... FOR UPDATE` locks the auction row, reads latest bid, checks clock/amount, inserts, commits — serializing bids per auction; loopback invalid bids reject gracefully. Inject a single mockable app clock (not database clock) as source of truth; define closing boundaries and stale-bid recovery in the API/frontend.
- **Review & real-time (15–18).** Codex has built-in code review (uncommitted changes or vs a base branch), but models reviewing their own code is fundamentally limited — keep a second model (Claude/Opus) to review. Real-time bids replace refresh with WebSockets (Socket.io), backed by Redis pub/sub as a backplane so events cross multiple API replicas; Redis is treated as ephemeral, Postgres stays authoritative, and clients refetch after reconnect. A planted `FOR SHARE` (instead of `FOR UPDATE`) defect is found even by cheap models; git-history investigation is a strong bug-finding technique.
- **Auction close, queue & checkout (19–23).** Model real-world event-driven workflows: a close worker polls Postgres for past-due auctions, commits the close plus a transactional-outbox event, publishes over RabbitMQ to a separate notification worker, which pushes a WebSocket modal to winner and seller. Discuss idempotency (at-least-once delivery), durable exchanges/queues, retries/back-off, dead-letter queue, and `SKIP LOCKED` batch claiming. Then `/goal` reads a GitHub issue and runs autonomously for a long time, producing a Drizzle-refactor PR; winner checkout is mocked against Stripe (webhook + replay-safe purchase records). Reviewing the PR catches an unverified claim — human-in-the-loop still needed.
- **Observability & wrap-up (24–26).** Add OpenTelemetry spans/traces with Jaeger: one high-signal trace follows the winning bid through bid → close → RabbitMQ notification → checkout, with business outcomes (rejected bids, declines) kept out of red error spans. Emphasize low-noise spans, metadata (auction/bid/purchase IDs), and safe read-only LLM navigation of observability. Wrap-up recaps the stack, the certainty/back-pressure philosophy, and subscription-stretching via delegated subagents.

### 13-row-locking-in-postgresql
- Locator: [[sources/cordex-web/20261004/fullstack-app-codex/13-row-locking-in-postgresql.txt]]
- Summary: How the transaction row lock fixes the race — explained via side chat, with a line-by-line code walkthrough.
- Key claims: locking a row means no other transaction can edit it, making requests effectively serial; the sequence is pool.connect → BEGIN → `SELECT ... FOR UPDATE` (lock the auction row) → read latest bid → check closing time → check amount → insert if valid → COMMIT (ROLLBACK on error to release the lock fast); locks are held only milliseconds here; the lock is like a single "talking stick" per auction; Postgres locks can cause problems at high volume/bad SQL if overused; isolation levels matter (read committed is the common/safe default, serializable is strongest but cancels transactions), default is fine but worth learning; the rerun bidding war shows strictly increasing bids (101,102,104,106,107) with no duplicates — the fix empirically works.
- Learner-relevant: implement `FOR UPDATE` transaction locking, explain serialization of competing bids, and know when locking/isolation levels become risky.

### 19-closing-auction-plan
- Locator: [[sources/cordex-web/20261004/fullstack-app-codex/19-closing-auction-plan.txt]]
- Summary: Designing the event-driven auction-close workflow (polling service + RabbitMQ + notification service + Jaeger), and testing prompt prescriptiveness.
- Key claims: don't wait for a page visit to tell the backend an auction ended; instead a dedicated service polls the auction table for past-due non-closed auctions and triggers a close workflow; it publishes over RabbitMQ to a separate notification service (separate memory space) that pushes a WebSocket modal to winner and seller; RabbitMQ is a message queue — exchanges route by routing key (with wildcards), consumers subscribe, and it embodies loosely-coupled async communication so services needn't be up simultaneously; decisions — winner is the highest bidder from Postgres (never inferred from browser/socket state); zero bids closes with no winner; handle idempotency because RabbitMQ guarantees at-least-once delivery (redelivery must not double-notify); send to every connected session for seller/winner; modal is intentionally intrusive/requires dismissal; target notification within ~5 seconds; use a transactional outbox (message committed atomically with the DB transaction) for the DB→RabbitMQ handoff; use durable topic exchange, durable queue, bounded retry/back-off, and a dead-letter queue (described but deliberately NOT built here); poll every second and claim due auctions in bounded batches with `SKIP LOCKED`; closed status + winning-bid reference become authoritative application state; the agents.md had already biased the design toward "auction close worker / notification worker" — agents files shape results in ways you may not notice; a comparison run without prescriptiveness converged to nearly the same architecture.
- Learner-relevant: design a polling + queue + worker workflow, apply outbox/idempotency/at-least-once reasoning, and see how prompt prescriptiveness and agents.md bias results.

### 20-messaging-with-rabbitmq
- Locator: [[sources/cordex-web/20261004/fullstack-app-codex/20-messaging-with-rabbitmq.txt]]
- Summary: Reviewing the RabbitMQ implementation — outbox, close worker, notification worker, and end-to-end verification.
- Key claims: exchanges receive messages, routing keys (wildcard-capable) route to queues, and consumers choose what to pull; RabbitMQ chosen for ubiquity (so LLMs understand it) and being free; HTTP between the three services would be fragile (all must be up) whereas the queue acts as a temporary database/post office and supports multiple consumers/workflows; loose coupling is the point; implementation includes an `outbox` table (message respected by the app transaction, picked up later), a `close-auctions` migration updating auction rows with a denormalized winning-bid reference, a separate `auction-close` service that polls and commits, and a `close worker` that broadcasts to the notification service; a notification worker consumes and pushes to winner + seller; reliability touches (publish-pending outbox, failing-retry) and updated bidding-war tests; final four-window bidding war shows auction closed + congratulations modals for both winner and seller.
- Learner-relevant: understand exchanges/routing keys/queues, implement outbox + worker services, and verify an async workflow end to end.

### 25-observability-with-jaeger
- Locator: [[sources/cordex-web/20261004/fullstack-app-codex/25-observability-with-jaeger.txt]]
- Summary: Reading the Jaeger trace end to end and safety considerations for letting LLMs use observability.
- Key claims: definitions — a span is a single timed operation, a trace is a collection of spans comprising a full workflow; the auction-bid trace shows the API, insert queries, the auction close worker, and the notification worker all correlated to one workflow; a "connection refused" error appears and a rejected bid was mis-recorded as an error (business outcomes should not be red); of the added infra, he considers Postgres and Jaeger the two most important (observability is critical for debugging); Jaeger is free and runs locally (or use cloud/Datadog); a good exercise for learners is to give the LLM a problem solvable only via Jaeger (or malformed messages/disabled services) and have it navigate and curl the traces; safety — use business subscriptions with different retention, and any production interface must use a read-only key; the classic disaster is leaving a prod DB/CLI open so the LLM drops it; local models (DeepSeek on DGX Spark, LM Studio on a 128GB Mac) work but are too slow for agentic coding; you can wire Codex subagents to local models.
- Learner-relevant: interpret Jaeger traces/spans, debug a full workflow, and safely expose observability tooling to agents.
