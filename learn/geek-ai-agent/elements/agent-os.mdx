# Agent OS（Agent 操作系統）

## Problem Statement

一個人或一家企業要同時跑多個 AI Agent，事情很快就會失控。每個 Agent 都要接大模型、接工具、管記憶、管權限、管審計。如果每個 Agent 各寫一套後端，同一套接線工作重複做 N 遍，安全策略各不相同，出了事無從追查。傳統作業系統解決的是「一台機器上同時跑多個程序」的重複問題，Agent 世界缺的是同一個問題的對應物：一個底座，讓 N 個 Agent 共享接線、記憶、工具與治理。

## Why it matters

Agent OS 是判斷所有 AI Agent 產品的一把尺。理解了它的定義與五項能力清單，你就能把「這只是個框架」「這是個編排平台」「這是個 Agent OS」分清楚，也能看懂 OryxOS 為什麼把自己定位在這一層，而不是去跟 Dify 搶流程編排的位置。

## How it works

Agent OS（Agent 操作系統）是裝在用戶或企業自己的機器上、用來運行和管理多個 AI Agent 的基礎系統。它和「讓一個 Agent 跑起來」的 agent runtime 是兩層東西，runtime 只管單個 Agent 的執行，Agent OS 要回答的是「一個用戶同時跑 N 個 Agent 時，共享基礎設施層應該長什麼樣」。一個合格的 Agent OS 至少要提供五件事：

| 能力 | 做什麼 |
| --- | --- |
| Agent 配置與生命週期 | 建 Agent、啟動、停用、管理配置 |
| 統一外部通道 | 接 IM、郵件、Web、HTTP 等外部入口 |
| 統一內部系統訪問 | 接 LLM、工具、IT 系統、知識庫 |
| 統一記憶 | 跨會話保留上下文與長期記憶 |
| Tool 調用與沙箱執行 | 讓 Agent 調工具，並在受控環境裡跑 |

部署形狀很關鍵。一個 Agent OS 實例裝在用戶自己的機器、伺服器或 K8s 上，配一個 Web 控制台或 CLI。業務方只做兩件事：寫一個 Tool（任何語言都行）和配置一個 Agent 用這個 Tool。他們不碰 Agent 後端代碼，不處理消息路由、LLM 調用、認證、審計、上下文。所有橫切關注點都是 Agent OS 的事，這就是「Agent 是配置出來的，不是寫出來的」這句口號的來歷。

拿邊界去看，Agent OS 和三個鄰居不重疊。編排平台（Dify、Coze、扣子）產出的是工作流，可以跑在 Agent OS 上當後端；框架（LangChain、Spring AI、LangChain4j）產出的是代碼，可以當 Agent OS 的底層元件；大廠 SaaS（Glean、Bedrock AgentCore、Agentforce）是綁定雲的完整應用，不是能私有部署的底座。Agent OS 是開源、可私有部署、不鎖定生態的那一檔。

行業裡兩個最有代表性的開源 Agent OS 是 OpenClaw 和 Hermes Agent。OpenClaw（Node.js，2025 年 11 月發布，MIT，20+ 通道、10k+ 社區 skills、2026 年 4 月 GitHub 超 30 萬星）是消費級、開發者優先，企業安全與治理弱，出過 CVE 和惡意 skill 竊取憑證的事件。Hermes Agent（Python，2026 年 2 月發布，MIT，三層記憶、技能自演化、安全掃描、多用戶隔離，2026 年 5 月約 15 萬星）是工程級、穩健優先，離企業更近，但仍然缺多租戶 RBAC、SSO 和完整審計。兩者合起來把開源 Agent OS 的版圖定成「個人/小團隊產品」，留出了企業治理、深層 IT 系統整合、Java 生態三塊空白。

OryxOS 就落在這塊空白上：Java 原生、企業可控、私有可審計的統一 Agent 底座，裝在企業自己的 K8s/伺服器/物理機上，跑著共享通道、模型路由、記憶、工具調用與安全審計的業務 Agent。它的邊界是「runtime，不是編排」，多 Agent 管理、多租戶、審計都在範圍內，但故意不做可視化流程編排、複雜任務分解和顯式的多 Agent 協作。安全是 day-one 設計，刻意反著 OpenClaw 的弱點來：受控的 Skill/Tool 來源、最小權限、強制沙箱隔離、憑證不落明文、防 prompt injection、全鏈路結構化審計。

## In plain terms

把傳統作業系統搬到 Agent 世界。Windows 或 Linux 管的是程序和文件，Agent OS 管的是 Agent。你在上面「裝」一個 Agent，就像裝一個軟體，它自己知道怎麼接模型、怎麼用工具、怎麼記東西。裝完你只管跟它說話。

## Analogy

一家公司請了很多員工（Agent）。每個員工都要領電腦、領門禁卡、走報銷流程，如果每個員工都自己搞定這套行政，公司會亂成一團。行政部門就是 Agent OS：它統一發電腦（模型接入）、發門禁卡（通道與權限）、記考勤（記憶）、審核支出（審計）。業務部門只需要招人（配置 Agent）和安排具體工作（寫 Tool），不用管行政細節。

## Practical use

用這把尺去給任何 AI Agent 產品定位。看到一個東西，先問它產出的是什麼。產出代碼的是框架，產出工作流的是編排平台，產出「裝好就能用的常駐 Agent」的是 Agent OS。這套分類在 OryxOS 的選型與對外說明裡天天用，也適用在現實裡評估新出現的產品。

## Questions

### Q1. Agent OS 和 agent runtime 的差別是什麼？
A1. runtime 讓一個 Agent 跑起來，管單個 Agent 的執行；Agent OS 管的是 N 個 Agent 在企業裡同時運行時的共享基礎設施，包括生命週期、統一通道、統一內部訪問、統一記憶、Tool 調用與沙箱。

### Q2. 一個合格的 Agent OS 至少要提供哪五項能力？
A2. Agent 配置與生命週期、統一外部通道（IM/郵件/Web/HTTP）、統一內部系統訪問（LLM/工具/IT 系統/知識庫）、統一記憶、Tool 調用與沙箱執行。

### Q3. 編排平台、框架、大廠 SaaS 和 Agent OS 各自產出什麼？為什麼 OryxOS 拒絕做流程編排？
A3. 框架產出代碼，編排平台產出工作流，大廠 SaaS 產出綁定雲的完整應用，Agent OS 產出配置好的常駐 Agent。OryxOS 把自己定位在 runtime 層，只提供 Channel、Provider、Memory、Tool、多租戶、SSO、審計、可觀測；複雜工作流可以讓 Dify 這類平台跑在它上面調用 API，兩者互補不競爭。

### Q4. OpenClaw 和 Hermes Agent 共同留下的三塊空白是什麼？OryxOS 為什麼能補上其中兩塊？
A4. 空白是完整企業治理（多租戶 RBAC、SSO、審計架構）、與企業 IT 系統的深層整合、Java 生態缺位。OryxOS 以「企業治理 + Java 原生」為定位直接對應前兩塊，安全設計刻意反著 OpenClaw 的弱點來，因此它的價值不繫在「Agent OS」這個詞上，而繫在不會變的企業需求上。
