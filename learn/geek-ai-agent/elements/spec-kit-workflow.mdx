# Spec-Kit 工作流 (The Spec-Kit Workflow)

## Problem Statement

讓 AI 從零構建一個九模塊的項目，最大的風險是「vibe coding」失控。AI 寫著寫著就脫離需求文檔，自己編出和方案對不上的結構，事後才發現。Spec-Kit 就是為了治這個病：把需求文檔和技術方案喂給工具，讓它生成規範、計劃和任務，讓規範成為代碼行為的唯一真實來源，而不是讓 AI 邊寫邊編。

## Why it matters

Spec-Kit 是 OryxOS 動手階段的實際操作方法。理解了這個工作流，你才知道「從 0 寫出 OryxOS」不是讓 AI 自由發揮，而是一套有規範、有計劃、有任務、有驗收的流程。這套方法本身可以遷移到任何 AI 主導的 greenfield 項目。

## How it works

整體策略是雙階段混合：主構建用 Spec-Kit，增量用手動提示詞。主構建從零開始，九個模塊邊界清楚、文檔齊全，跑完整的 spec-driven 流程（constitution → specify → plan → tasks → implement），讓產出對齊需求、避免 vibe-coding 漂移。增量階段是 1–3 個文件的改動（擴展、修 bug、新 Plugin Tool），切換成用 Claude Code 手動提示詞，因為為小改動跑一輪完整 Spec-Kit 是殺雞用牛刀。邊界很乾淨：大粒度 greenfield 用 Spec-Kit，小增量用手動提示詞，工具選擇跟工作性質匹配。

Spec-Kit 是 2026 年增長最快的開發工具，支持 20+ AI 編程 agent，把 AI 輔助編碼結構化成 specify → plan → tasks → implement，規範是代碼行為的唯一真實來源。它適配中大型 greenfield、需求明確、AI agent 協作、方法論驅動的團隊；不適配小功能、快速原型、單文件改動、大型 brownfield 重構和探索性研究。OryxOS 每個適配條件都命中（純 greenfield、九模塊中等規模、文檔齊全、Claude Code 當構建 agent），所以 Spec-Kit 是主構建的正解。

準備階段做三件事。裝 Specify CLI（Python 3.11+，建議用 uv 裝）和配置 Claude Code；寫 constitution.md（七條原則，AI 永不改它）；用 /speckit.specify 把需求文檔變成五個 user story 的規範，用 /speckit.plan 把技術方案變成模塊計劃。關鍵是喂最新的文檔，喂舊版技術方案，生成的計劃會按錯誤的模塊數切分。

七條憲法原則是從需求文檔第三章設計目標和技術方案第一節關鍵決策提煉的：① JDK 21 + Spring Boot 3.x 單體、Maven 九模塊、單個二進制；② 五項能力優先，治理層留擴展；③ 自研 ReAct 循環，不用 Spring AI 的 Agent 抽象；④ Spring AI 只用一半，Provider 抽象/協議轉換/@Tool schema 生成，自動工具執行禁用，調度交給 ReActLoop+ToolExecutor，這條最容易被寫錯；⑤ Plugin Tool 三級，SKILL.md+MCP 零代碼優先；⑥ SQLite + MEMORY.md 在核心，向量檢索留擴展，審計表第一天就寫；⑦ 每個 user story 以 demo 收尾，優先跑通不追求完美。憲法寫一次，AI 永不改，原則錯了就停下來重新討論。

主構建拆成五個 user story，按依賴排序：US-1 對接 LLM（無依賴），US-2 ReAct 循環（依賴 US-1），US-3 Memory 三層記憶（依賴 US-2），US-4 Plugin Tool 體系（依賴 US-2，與 US-3 並行），US-5 Web Service（依賴前四個）。US-5 放最後是依賴關係決定的，不是重要性問題，它其實是關鍵差異化。驗收 demo 直接複用需求文檔第三章的五個 demo。

構建過程的協作紀律：每個 user story 結束後跑 /speckit.analyze（官方防漂移命令），檢查 constitution/spec/plan/tasks/code 的一致性；AI 違反憲法（用非 JDK 21 特性、改了 ReAct 實現、啟用了 Spring AI 自動執行、拆了 Tool 模塊、Provider 類型掃描）要當場糾正；上下文丟了讓 AI 重讀 spec.md + plan.md + 最近代碼；每個 story 結束 git commit 便於回滾。

Spec-Kit 自身也有限制和對策：小增量太重，所以小改動切手動提示詞；規範不會自動跟實現同步，所以每個 story 跑 analyze；大型 brownfield 上下文裝不下，OryxOS 是純 greenfield 不適用；工具本身演化快，所以整個主構建固定一個 Specify CLI 版本，實現時查官方文檔，避免 70+ 個社區擴展，只用官方核心命令。

## In plain terms

Spec-Kit 就是把「先寫清楚要做什麼，再讓 AI 寫代碼」變成一套工具流程。先立規矩（憲法），再寫需求說明書（spec），再寫施工計劃（plan），再拆任務（tasks），最後讓 AI 按任務幹活。每幹完一單就檢查一次有沒有跑偏。幹完大工程後，小修小補就不走這套流程，直接跟 AI 說清楚改哪裏就行。

## Analogy

建一棟樓。Spec-Kit 是總包流程：先定建築規範（憲法）、出設計圖（spec）、出施工方案（plan）、拆成一道道工序（tasks）、讓工人按工序幹（implement）。每完成一層樓驗收一次（analyze），不對就改。房子蓋好後，換個燈泡、修個門鎖（小增量）就不需要走完整流程了，直接叫師傅來處理（手動提示詞）。

## Practical use

動手建 OryxOS 時照這個順序走：準備（裝工具、寫憲法、生成 spec 和 plan）→ 按依賴順序跑 US-1 到 US-5 → 每個 story 結束跑 analyze 並 git commit → 主構建完成後進入增量階段，小改動直接手動提示詞 + PR。這套方法同樣適配你未來主導的其他 greenfield 項目。

## Questions

### Q1. 雙階段混合策略的分界線是什麼？為什麼這樣切？
A1. 主構建（從零、九模塊、文檔齊全）用 Spec-Kit 跑完整流程，增量階段（1–3 個文件的改動）用手動提示詞。因為大粒度 greenfield 需要規範防漂移，小改動跑完整 Spec-Kit 成本大於任務本身。

### Q2. 七條憲法原則裡哪兩條最容易被 AI 忽略？為什麼？
A2. 第四條（Spring AI 只用一半，自動工具執行禁用）和第六條（SQLite + MEMORY.md 在核心，審計表第一天就寫）。第四條容易寫成讓 Spring AI 自動執行工具導致雙調用，第六條容易漏寫審計表以為日誌就夠。

### Q3. 五個 user story 的依賴 DAG 是什麼？為什麼 US-5 放最後？
A3. US-1 → US-2 →（US-3 ∥ US-4）→ US-5。US-5 放最後是依賴關係決定的，不是它不重要，Web Service 反而是關鍵差異化。

### Q4. /speckit.analyze 是幹什麼的？多久跑一次？
A4. 官方防漂移命令，檢查 constitution/spec/plan/tasks/code 的一致性，發現漂移當場修正。每個 user story 結束後跑一次，是硬性要求不是可選項。
