# 五項核心能力 (The Five Core Capabilities)

## Problem Statement

一個 Agent 底座到底要會什麼？如果不先把這個問題答清楚，項目就會在「先做個聊天機器人」和「先做個完整企業平台」之間搖擺。五項能力就是需求文檔給出的回答，它同時界定了核心範圍的最短路徑，讓 4 週 12 小時的預算有處可放。

## Why it matters

五項能力是 OryxOS「做什麼」的完整答案，也是後續技術方案和 AI 編程指南五個 user story 的骨架。記住這五項和它們各自的用例，你就能看懂任何一個 OryxOS 功能點屬於哪一層。

## How it works

五項核心能力加一個基礎模塊，是需求文檔給 OryxOS 開出的清單。

| 能力 | 做什麼 | 典型用例 |
| --- | --- | --- |
| Provider（模型接入） | 對接 LLM 的抽象層 | 運行時切換模型不鎖死供應商，本地 Ollama/vLLM 讓數據留在公司 |
| ReAct 循環 | Agent 的核心機制 | 由 Agent 自己決定何時調工具，不寫死流程 |
| Memory（三層記憶） | 跨會話保留狀態 | 會話記憶（自動壓縮）+ 長期記憶（MEMORY.md），情節記憶以後再說 |
| Plugin Tool | 外部能力接入 | 三級插件：零代碼 SKILL.md+MCP、輕代碼 MCP server、重代碼 @Tool Spring Bean |
| Web Service | 對外的 REST API | 把 AI 嵌進既有系統的唯一通道，六類 API |
| Channel（基礎模塊，不屬五項） | 消息進出 | 核心階段只有 CLI Channel；IM 通道走擴展 |

這五項組合起來就能覆蓋常見業務場景，不需要為每個場景專門造模塊。全渠道客服、運維助手、研發助手、知識管理、銷售助手、數據分析，都是這幾項能力的排列組合。

範圍上，需求文檔把功能分成三級。核心功能是「配置一個 Agent、跟它對話、它調工具」的最短路徑，4 週 12 小時內做完；擴展功能是生產級治理（多租戶、SSO、審計、Tool Policy、完整 sandbox、集群）；社區功能是長期共建（Skills Marketplace、多語言 SDK、視覺化 Profile 編輯器、Kubernetes Operator）。判斷一個功能進哪一級，看它是不是讓最小可運行的 Agent 底座跑起來。

驗收落到五個 demo，每個 demo 對應一個 user story：① 對接 LLM+ReAct「查天氣並寫日報」；② Memory 跨對話記偏好；③ Plugin Tool+MCP 跨工具任務；④ Web Service 同步調用生命週期；⑤ Web Service 多端點聯動（info→profiles→tools→invoke→memory）。五個 demo 是發布的硬條件。

## In plain terms

五項能力就是「一個 Agent 底座要會的五件事」：會接模型、會自己循環思考調工具、會記住事情、會用工具、會開門讓外部系統調用。加上一個負責消息進出的 Channel。其他都是這五件事的排列組合。

## Analogy

把 OryxOS 想成一家餐飲公司。Provider 是採購（進貨渠道，今天換供應商不用改菜單），ReAct 循環是廚師（看單做菜，缺材料就讓采購買），Memory 是後廚的菜譜和備忘錄（記住老客人口味），Plugin Tool 是菜刀鍋鏟（用什麼工具做菜，還能外購新工具），Web Service 是外賣窗口（客人/系統從外面下單）。Channel 是堂食窗口和電話訂餐。

## Practical use

看任何 OryxOS 的功能點或 user story，先問它屬於哪一項能力。US-1 是 Provider，US-2 是 ReAct，US-3 是 Memory，US-4 是 Tool，US-5 是 Web Service。這個分類讓你讀技術方案時不會迷路，因為技術方案的架構就是按這五項能力組織的。

## Questions

### Q1. 五項核心能力是什麼？Channel 為什麼不算其中一項？
A1. Provider（模型接入）、ReAct 循環、Memory 三層記憶、Plugin Tool、Web Service。Channel 是基礎模塊，負責消息進出，但它不是五項之一，需求文檔把它單列。

### Q2. 為什麼說五項能力「組合起來就能覆蓋常見業務場景」？舉一個例子。
A2. 因為場景是能力的排列組合，不需要為每個場景造模塊。例如全渠道客服就是 Channel + Provider + ReAct + Memory + Tool 的組合，銷售助手是 CRM 連接器 + 企查查 MCP 工具 + 知識庫 Tool 的組合。

### Q3. 需求文檔把功能分成哪三級？判斷標準是什麼？
A3. 核心（最短路徑跑通「配置 Agent、對話、調工具」）、擴展（生產級治理）、社區（長期共建）。判斷標準是看它是不是讓最小可運行的 Agent 底座跑起來。

### Q4. 五個驗收 demo 分別對應哪個 user story？為什麼 demo 五是「info→profiles→tools→invoke→memory」這個順序？
A4. demo 一對應 US-1+US-2（LLM+ReAct），demo 二對應 US-3（Memory），demo 三對應 US-4（Plugin Tool），demo 四和五對應 US-5（Web Service）。demo 五的順序就是 Web Service 對外能力的一個完整使用流程，從看系統信息、列 Profile、看可用工具，到調用 Agent、查記憶，覆蓋了 API 的主要入口。
