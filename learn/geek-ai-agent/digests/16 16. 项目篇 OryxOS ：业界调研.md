# Digest — 16 16. 项目篇 OryxOS ：业界调研

## Overview (L1)
- 一、什么是 Agent OS — Defines Agent OS as the base system for running/managing AI Agents on the user's own machine, lists the five things a qualified Agent OS must provide, contrasts it with agent runtime, and draws the boundary against orchestration platforms, frameworks, and big-vendor SaaS.
- 二、业界两个最具代表性的开源 Agent — Compares OpenClaw (Node.js, consumer-grade, 30万+ stars, security weak) and Hermes Agent (Python, engineering-grade, three-tier memory, safer), then identifies the gaps they jointly leave: enterprise governance, deep enterprise IT integration, and the missing Java ecosystem.
- 三、企业为什么需要一个私有可控的 Agent 底座 — Core argument of the research: real demand is a private, controllable, auditable Agent base, anchored in the non-negotiable needs of strictly-regulated enterprises, not in the "Agent OS" concept itself; supported by Anthropic 2026 State of AI Agents data.
- 四、Java 生态在这件事上的位置 — Java has frameworks (Spring AI, Spring AI Alibaba, LangChain4j) but no Agent OS base; the gap is worth filling for ecosystem completeness, with concrete enablers (Spring Boot standard, LLM connectors, JVM toolchain, GraalVM) and Spring AI's rise as a leading signal.
- 五、OryxOS 的定位与愿景 — Positions OryxOS as a Java-native, private, auditable Agent base anchored in the enterprise need rather than the concept; vision summarized as 统一、私有、易接入、可观测; boundary is runtime-not-orchestration; security design deliberately inverts OpenClaw's weaknesses.
- 六、未来方向：从单机到分布式 — Current version is single-machine private deployment; mid-term evolution to stateless instances with externalized state and distributed deployment (HA, scaling); long-term vision of distributed Agent collaboration atop a dedicated Agent communication base.
- 附录 A：关键术语 — Glossary defining Agent OS, Agent, Skill, Tool, Channel, LLM Provider, MCP, orchestration platforms, frameworks, multi-tenancy, Gateway, Spring AI, Spring AI Alibaba.
- 附录 B：主要参考资料 — Reference lists for OpenClaw, Hermes Agent, Java ecosystem, industry standards, reports, and security disclosures (incl. CVE-2026-25253, Trend Micro malicious skill report).

## Sections (L2)
### What is Agent OS
- Locator: `[[sources/geek-ai-agent/16 16. 项目篇 OryxOS ：业界调研.html#what-is-agent-os]]`
- Summary: Defines Agent OS as the base system that runs and manages multiple AI Agents on the user's/enterprise's own machine, and lists the five required capabilities: Agent configuration & lifecycle, unified external channel access (IM/email/Web/HTTP), unified internal system access (LLM/工具/IT 系统/知识库), unified memory, and Tool calling with sandbox execution.
- Key claims: An Agent is configured on the base, not written as code; Agent OS ≠ agent runtime — runtime makes one Agent run, Agent OS manages many Agents in an enterprise; Agent OS answers "what should the shared infrastructure layer look like when a user runs N Agents at once."
- Learner-relevant: Anchor: the working definition and five-capability checklist used to evaluate and position OryxOS against the industry.

### What Agent OS looks like
- Locator: `[[sources/geek-ai-agent/16 16. 项目篇 OryxOS ：业界调研.html#agent-os-shape]]`
- Summary: Describes the deployment shape: one Agent OS instance (single service) on the user's machine/server/K8s with a Web console or CLI; business parties write Tools and configure Agents, never writing Agent backend code or dealing with message routing/LLM calls/auth/audit/context.
- Key claims: Business writers only implement a Tool (any language) and configure an Agent to use it; Agents can run automatically; all cross-cutting concerns are the Agent OS's job.
- Learner-relevant: Anchor: the "Agent is configured, not written" experience that OryxOS's Profile/CLI design targets.

### Boundaries vs adjacent concepts
- Locator: `[[sources/geek-ai-agent/16 16. 项目篇 OryxOS ：业界调研.html#adjacent-concepts]]`
- Summary: Draws a comparison table distinguishing Agent OS from orchestration platforms (Dify/Coze/扣子 — a workflow), frameworks (LangChain/Spring AI/LangChain4j — code), and big-vendor middleware/SaaS (Glean/Bedrock AgentCore/Agentforce — full apps bound to clouds).
- Key claims: Orchestration platforms can run on top of Agent OS as its backend; frameworks can serve as Agent OS's underlying components; big-vendor SaaS are a different quadrant, not privately deployable; Agent OS is an open-source, privately-deployable base that doesn't lock an ecosystem.
- Learner-relevant: Anchor: the ecosystem-positioning mental model for classifying any AI-agent product the learner meets later.

### OpenClaw and Hermes Agent
- Locator: `[[sources/geek-ai-agent/16 16. 项目篇 OryxOS ：业界调研.html#openclaw-hermes]]`
- Summary: Profiles the two representative open-source Agent OS projects: OpenClaw (PSPDFKit founder Peter Steinberger, Nov 2025, Node.js, MIT, 20+ channels, 10k+ community skills, 300k+ GitHub stars by Apr 2026, fastest-growing project) and Hermes Agent (NousResearch, Feb 2026, Python, MIT, three-tier memory, self-evolving skills, security scanning, HERMES_HOME multi-user isolation, ~150k stars by May 2026).
- Key claims: OpenClaw = consumer-grade, developer-first, weak on enterprise security/governance (CVE, malicious skills, credential harvesting; needs Tank OS hardening); Hermes = engineering-grade, robustness-first, closer to enterprises but still missing multi-tenant RBAC/SSO/full audit; together they define the open-source Agent OS landscape as personal/small-team products.
- Learner-relevant: Anchor: concrete benchmark data on the two projects OryxOS positions itself against.

### The shared gaps left behind
- Locator: `[[sources/geek-ai-agent/16 16. 项目篇 OryxOS ：业界调研.html#shared-gaps]]`
- Summary: Lists the unfilled positions in open-source Agent OS: complete enterprise governance (multi-tenant RBAC, SSO, audit architecture, compliance evidence — PTG/Tank OS are patches, not day-one design), deep integration with enterprise IT systems (ERP/CRM/CMDB/monitoring), and the missing Java ecosystem.
- Key claims: Both projects serve personal/small-team; enterprise IM channels only via community extensions; no Java project positions itself as Agent OS.
- Learner-relevant: Anchor: the exact whitespace OryxOS claims — enterprise governance + Java-native + deep IT integration.

### Why enterprises need a private controllable Agent base
- Locator: `[[sources/geek-ai-agent/16 16. 项目篇 OryxOS ：业界调研.html#private-controlled-base]]`
- Summary: Builds the research's core argument: enterprise demand is real (Anthropic 2026 State of AI Agents: 500+ tech leaders, majority already deploying multi-step agent workflows), but the hard part is running Agents controllably in production, not making one Agent; strictly-regulated enterprises (banks, government, telecom, energy, healthcare) have hard rules that only a private, auditable, aligned base satisfies.
- Key claims: Many agent pilots never reach production and many enterprise pilots fail to scale; top challenges are integration, data access quality, implementation cost, change management; most orgs reported AI-agent security incidents and few have full IT/security approval at production; tool-calling has a high silent-failure rate; the need is anchored in enterprise constraints, so it won't change with the "Agent OS" buzzword.
- Learner-relevant: Anchor: the demand-side argument and the iron rules of strictly-regulated enterprises that justify OryxOS's whole positioning.

### The value anchor
- Locator: `[[sources/geek-ai-agent/16 16. 项目篇 OryxOS ：业界调研.html#value-anchor]]`
- Summary: States the concrete value of a private controllable base: direct cost reduction, efficiency gains, cross-system collaboration, compliance/audit that can actually be implemented, and giving ordinary employees AI capability; the deepest anchor is knowledge sedimentation.
- Key claims: The Skill system turns senior employees' experience into assets that stay in the enterprise and can be inherited by new employees — the fundamental value that distinguishes a private base from SaaS.
- Learner-relevant: Anchor: the knowledge-sedimentation rationale that motivates the SKILL.md / Skill 体系 in the OryxOS design.

### Java ecosystem status: frameworks but no base
- Locator: `[[sources/geek-ai-agent/16 16. 项目篇 OryxOS ：业界调研.html#java-ecosystem-status]]`
- Summary: Surveys Java AI engineering: Spring AI (official Spring LLM-call abstraction, prompt templates, RAG, Tool Calling), Spring AI Alibaba (Alibaba-driven, 10+ mainstream LLM connectors in a year: 通义/文心/DeepSeek/Kimi/智谱/混元/豆包 etc.), LangChain4j (LangChain's Java port); inference ecosystems (ONNX Runtime Java, DJL) are a different layer.
- Key claims: All are libraries/frameworks whose output is code requiring the developer to handle runtime; a Java "install-and-run" Agent OS base is nearly zero in the industry; OpenClaw and Hermes are not Java — a clear vacancy.
- Learner-relevant: Anchor: the mapping of what Java does and does not have at the Agent OS layer.

### Why filling the gap matters: ecosystem completeness
- Locator: `[[sources/geek-ai-agent/16 16. 项目篇 OryxOS ：业界调研.html#ecosystem-completeness]]`
- Summary: Argues from ecosystem completeness: a healthy tech ecosystem should have its own implementation at every key layer, otherwise the break is bridged by fragile, costly glue; Java/Spring's enterprise backend stack is extremely complete (Spring Boot, Spring Cloud, Nacos, Sentinel, SkyWalking, Arthas, Prometheus+Grafana).
- Key claims: Java enterprises wanting a private Agent base today must use Node.js OpenClaw or Python Hermes and write glue at the seams of two stacks — the most painful point for Java-ecosystem users; filling the gap is the same logic as Spring AI filling "Java's LLM-call layer."
- Learner-relevant: Anchor: the ecosystem-completeness argument the learner can reuse to justify Java-native Agent OS to stakeholders.

### Concrete supports for doing it in Java

- Key claims: A Java Agent OS is a Spring Boot app that drops into existing ops/audit; Native Image still carries compilation-time config cost for reflection-heavy frameworks like Spring AI, but the path works and is maturing.

### What OryxOS is

### OryxOS's vision

### Boundary: runtime, not orchestration
- Locator: `[[sources/geek-ai-agent/16 16. 项目篇 OryxOS ：业界调研.html#runtime-not-orchestration]]`
- Summary: Clarifies the boundary: OryxOS holds the runtime layer (below orchestration platforms and applications) but remains a full Agent OS — multi-Agent management, multi-tenancy, audit are all in scope; it deliberately does not do visual workflow orchestration, complex task decomposition, or explicit multi-Agent collaboration.
- Key claims: OryxOS provides Channel, LLM Provider, Memory, Tool registration, Sandbox, multi-tenancy, SSO, audit, observability, Web console; if complex workflows are needed, Dify-style platforms run on top calling OryxOS's API — complementary, not competitive.
- Learner-relevant: Anchor: the positioning statement that keeps OryxOS focused on the base layer and defines what it refuses to build.

### What OryxOS is not: vs Dify workflows and LangChain frameworks
- Locator: `[[sources/geek-ai-agent/16 16. 项目篇 OryxOS ：业界调研.html#not-orchestration-frameworks]]`
- Summary: Re-derives the boundaries from OryxOS's viewpoint across three dimensions (artifact, who uses it, layer): frameworks (LangChain/Spring AI) produce code the developer deploys; orchestration platforms (Dify/Coze) produce a workflow the business user drags; OryxOS produces configured resident Agents on a run-it-yourself base.
- Key claims: Dify orchestrates "流程" (flows), OryxOS carries "常驻的 Agent" (resident Agents) — different layers, Dify can run on top; frameworks give materials to build a house, OryxOS delivers a move-in-ready house; OryxOS reuses frameworks (LLM calling via Spring AI) and hosts orchestration platforms (as backend runtime).
- Learner-relevant: Anchor: the memorable analogy (房子 metaphor) and three-way classification for fielding common "how is this different from X" questions.

### Security: not repeating OpenClaw's mistakes
- Locator: `[[sources/geek-ai-agent/16 16. 项目篇 OryxOS ：业界调研.html#security-day-one]]`
- Summary: Argues OpenClaw's security problems are structural (open low-barrier third-party skill ecosystem + lax default permissions + weak isolation), so OryxOS — targeting strictly-regulated enterprises — makes security day-one design and inverts OpenClaw's approach.
- Key claims: Controlled Skill/Tool sources (registration, review, signing, versioning, no unrestricted marketplace); least privilege instead of default-all; mandatory sandbox isolation with per-tenant isolation; credentials never land in plaintext (KMS/Vault integration, auditable); proactive prompt-injection and data-exfiltration defense (borrowing Hermes's scanning); full-chain structured audit as a base capability (SIEM-exportable); fit into existing enterprise security-review flows as a Java/Spring system.
- Learner-relevant: Anchor: the concrete security principles that later drive the Sandbox, Tool Policy, and audit design in the technical docs.

### Relationship with other industry projects

### Future direction: from single machine to distributed
- Locator: `[[sources/geek-ai-agent/16 16. 项目篇 OryxOS ：业界调研.html#single-to-distributed]]`
- Summary: States the current version is single-machine private deployment (deliberate: easiest to run through one scenario, easiest to operate/audit), then lays out the evolution: mid-term to stateless instances with externalized state and distributed deployment; long-term to distributed Agent collaboration.
- Key claims: Single instance hits three walls at company scale (throughput, single-point failure, scaled governance); two distinct "distributed" meanings — base-replica distribution (ops level, 6.1–6.4) vs Agent-to-Agent collaboration (node = Agent, 6.5).
- Learner-relevant: Anchor: the three-phase roadmap table (当前/中期/远期) that frames OryxOS's near-term scope.

### Principle: stateless instances, externalized state
- Locator: `[[sources/geek-ai-agent/16 16. 项目篇 OryxOS ：业界调研.html#stateless-externalized-state]]`
- Summary: The key step to clustering is stripping state out of instances: session/short-term context to Redis, long-term memory and Skill library to PostgreSQL (pgvector or a standalone vector store), audit logs and large files to object storage, Agent config and tenant info to config center/database.
- Key claims: Instances only "接消息、调模型、跑工具、读写外置状态" and hold no unreconstructable state; without this step, HA and horizontal scaling are impossible.
- Learner-relevant: Anchor: the externalized-state principle that underpins the distributed design.

### Coordination problems in multi-instance mode
- Locator: `[[sources/geek-ai-agent/16 16. 项目篇 OryxOS ：业界调研.html#multi-instance-coordination]]`
- Summary: Lists coordination issues once instances are stateless: channel messages must not be consumed twice (unified message distribution layer / MQ consumer group, stateless Gateway, preemptive or sharded consumption); Agent scheduling/ownership for stateful long tasks and cron (lightweight scheduling layer with distributed locks/leases); multi-tenant isolation must move to the storage layer (key prefixes/schemas/DBs, tenant ID on every request).
- Key claims: Because state is externalized, any instance can serve any Agent's request; each of the three problems has a named solution approach.
- Learner-relevant: Anchor: the concrete distributed-system checklist to revisit when OryxOS scales.

### High availability and horizontal scaling
- Locator: `[[sources/geek-ai-agent/16 16. 项目篇 OryxOS ：业界调研.html#ha-horizontal-scaling]]`
- Summary: With stateless instances and externalized state, HA and scaling become natural: multiple instances behind a load balancer on K8s, traffic fails over on instance failure, horizontal scale-out without data migration; storage layers do their own mature HA.
- Key claims: Instance failure loses no state (it lives in external storage); scaling needs no data migration because instances are stateless.
- Learner-relevant: Anchor: the HA/scaling mechanics of the mid-term distributed phase.

### Why Java makes distributed natural
- Locator: `[[sources/geek-ai-agent/16 16. 项目篇 OryxOS ：业界调研.html#java-distributed]]`
- Summary: Distributed systems concerns (service discovery/config, rate limiting/circuit breaking, distributed tracing, load balancing) have mature Java solutions that enterprises already use: Nacos, Sentinel, Spring Cloud Gateway, SkyWalking, Prometheus+Grafana.
- Key claims: Distributed/HA/service governance is Java/Spring's most mature, most-trusted strength — OpenClaw (Node) and Hermes (Python) would struggle where Java is "顺手"; distributed is reuse, not building from scratch; the doc re-emphasizes these are evolution plans, current focus is single-machine solidity.
- Learner-relevant: Anchor: another concrete instantiation of the "Java native" advantage at the distributed layer.

### Further vision: distributed Agent collaboration
- Locator: `[[sources/geek-ai-agent/16 16. 项目篇 OryxOS ：业界调研.html#distributed-agent-collaboration]]`
- Summary: The most forward-looking vision: dozens of Agents across departments/machines/partners (运维/财务/法务) discover each other, delegate tasks reliably, share context, and collaborate across nodes — an "Agent version of a distributed system"; industry multi-agent work is still mostly in-process delegation, cross-node collaboration infrastructure is nearly blank.
- Key claims: Agent world is roughly at the "single-machine multi-process" stage; the middleware connecting multi-node Agents reliably doesn't exist yet; OryxOS is the single-node Agent runtime while a separate Agent communication base connects OryxOS nodes — two things that evolve separately and merge into a complete "distributed Agent OS"; explicitly marked as vision, not near-term demand.
- Learner-relevant: Anchor: the boundary discipline (current/mid/far) and the vision of an Agent communication base that frames the far-term horizon.
