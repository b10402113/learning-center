# Digest — 直播1：企业需要怎样的 Agent 底座

## Overview (L1)

- 行业格局 — 2026 sees big tech all in on enterprise Agent platforms (Huawei AgentArts, Alibaba Wukong, ByteDance Coze/HiAgent, Baidu AgentBuilder, Tencent Yuanqi); the convergence is "base + ecosystem", with two routes — bottom-up base-building vs top-down ecosystem-building.
- 必要性 — why enterprises must own a base: four things platforms can't give (data sovereignty, audit/compliance, multi-Agent governance, model freedom); the line is "platform for commodity flows, self-built for differentiated ones".
- Agent OS 架构 — a base that runs and manages Agents: the five things a base must solve (lifecycle, outward channels, inward access, unified memory, tool sandbox) and the eight capability blocks.
- 用 AI 做底座的方法 — contracts first, deliver in blocks, judge runnable (Harness): AI is bad at architectural decisions under ambiguity and good at high-intensity output under clear constraints.
- 回到开发者 — what's depreciating (translating clear requirements to code, memorizing APIs) vs what stays (turning fuzzy problems into clear specs, architecture judgment, verification design, accountability); plus the four-step ability path and the case for one big project.

### 行业格局-大厂在做什么-路线差异在哪

- Locator: `[[sources/geek-ai-agent/20260922/直播1：企业需要怎样的 Agent 底座.pdf#行业格局-大厂在做什么-路线差异在哪]]`
- Summary: By 2026 enterprise Agent platforms have become contested ground: Huawei AgentArts, Alibaba Wukong, ByteDance Coze/HiAgent, Baidu AgentBuilder, Tencent Yuanqi all entered. Commonality: none sells only a model — they sell "base + ecosystem", packaging Agent running/orchestration/governance into a platform. Divergence: cloud vendors build up from infrastructure, platform players build down from the app ecosystem — different bets. Six positions from open-source frameworks to managed bases: Huawei AgentArts (cloud + compute + models, infrastructure up), Alibaba AgentScope (open-source multi-agent framework: framework + Runtime + Studio), Alibaba Wukong (enterprise Agent platform, scaling), AWS AgentCore (managed base: Runtime/Gateway/Identity/observability), ByteDance Coze·HiAgent (light integration, fast deploy, app ecosystem), Baidu AgentBuilder/Tencent Yuanqi (Agent-building platforms within their ecosystems). Two samples: AgentScope (open-source framework, code/deploy in your hands, dev-oriented multi-agent collaboration) vs AgentCore (cloud-managed, no infra to run, enterprise-oriented, any framework/model can run). Name dispute: Agent platform/framework is about "how to develop Agents" (orchestration, templates, low-code, multi-agent collaboration — developer productivity); Agent OS/base is about "how a group of Agents is managed" (lifecycle, channels, memory, permissions, audit — enterprise runtime/governance).
- Key claims: Both routes fail to solve one thing — your own differentiated flows, private data, and governance requirements, which is exactly the starting point for self-building a base; the two routes make different assumptions (bottom-up: enterprises will eventually run Agents themselves; top-down: build volume first, the standard becomes mine); don't obsess over the name — look at which problems it actually solves.
- Learner-relevant: The market map and the naming disambiguation that frames "Agent OS".

### 必要性-为什么企业必须有自己的底座

- Locator: `[[sources/geek-ai-agent/20260922/直播1：企业需要怎样的 Agent 底座.pdf#必要性-为什么企业必须有自己的底座]]`
- Summary: The question is no longer "self-build vs buy" — the consensus is hybrid: commodity flows use platforms, differentiated flows stay owned. The test is concrete: does this Agent itself count as your competitiveness? If so, you must hold orchestration, data, and model choice. Another real constraint: at a certain scale of call volume and complexity, self-building's three-year TCO is actually more economical. Four things money can't buy: data sovereignty (private data, knowledge base, session records don't leave the enterprise; models can change, data stays), audit and compliance (every tool call and decision chain traceable, meeting internal and regulatory requirements), multi-Agent governance (registration, permissions, quotas, lifecycle of dozens of Agents managed centrally), and model freedom (multi-Provider abstraction, switch/mix anytime, no single-vendor lock-in). The dividing line: give platforms standard Q&A, doc summarization, generic customer service, one-off low-value non-differentiated scenarios, and rapid validation; keep to yourself the orchestration/tools coupled with core business, links involving private data/permissions/audit, and parts that evolve long-term and sediment into assets. Practice advice: use platforms to validate scenarios, use a self-built base to carry long-term assets — they're a division of labor, but the base must be in your hands.
- Key claims: Platforms give capability, not control; control can only be self-built.
- Learner-relevant: The business case for a self-built Agent base and the build/buy line.

### Agent-OS-架构-底座定义与五件事

- Locator: `[[sources/geek-ai-agent/20260922/直播1：企业需要怎样的 Agent 底座.pdf#Agent-OS-架构-底座定义与五件事]]`
- Summary: Agent OS definition: the base system that runs and manages AI Agents — upward it gives all kinds of Agents (ops, customer service, HR, sales…) a unified runtime, downward it connects models, channels, tools, memory, identity, and audit. Agent runtime vs Agent OS: runtime makes "one" Agent run (LLM calls, tool execution, context, loop control); Agent OS makes "a group" of Agents managed in an enterprise (lifecycle, unified access, unified memory, multi-tenancy, audit) — runtime is like a single process's execution environment, Agent OS like the layer managing a group of processes, scheduling resources, and providing shared services. A base must solve five things or it isn't a base: (1) Agent lifecycle — registration, start, monitoring, destruction; each Agent has an independent prompt/model/tools/channels/memory; (2) unified outward channels — IM (WeCom/feishu/dingtalk/Slack), email, Web, HTTP API sharing one channel layer; (3) unified inward access — LLM Providers, tools (MCP/plugins), enterprise IT systems, knowledge bases sharing one access layer; (4) unified memory — cross-session long-term memory, reusable skills, cross-Agent knowledge sedimentation; (5) tool invocation and sandbox — Function Calling-driven execution in a sandbox, holding the security boundary.
- Key claims: The overall architecture has eight blocks — Provider, Memory, Tool, ReAct, Sandbox, Notify, security audit, distributed.
- Learner-relevant: The definitional clarity of Agent OS vs runtime and the five-must-have checklist for a base.

### 能力拆解-Provider-ReAct-Tool-Memory-渠道

- Locator: `[[sources/geek-ai-agent/20260922/直播1：企业需要怎样的 Agent 底座.pdf#能力拆解-Provider-ReAct-Tool-Memory-渠道]]`
- Summary: Capability block 1 — LLM Provider abstraction is the precondition for model freedom: collect "calling a model" into one interface with stable contracts for text, streaming, Function Calling, and multimodal; run multiple Providers (OpenAI-compatible, domestic models, privately deployed) on the same upper-layer code; key design is capability probing (does this model support tools/vision) + failure degradation + timeout/retry; on the engineering side, Provider is a plugin so adding a vendor doesn't change upper-layer business code — it ranks first because model iteration is far faster than business code. Block 2 — ReAct reasoning loop is the Agent's heartbeat: Reason → Act → Observe → judge (continue or finish), looping until the goal or a stop condition; engineering must manage max iterations, context-length control, and exit strategy on failure/ambiguity; observability matters — leave a trace for every round's Reason/Act/Observe. Block 3 — Tool invocation: Function Calling describes tools as schema to the model, which decides which to call and with what parameters, results fed back into the next round; MCP standardizes tool/data-source access, one integration reused by many Agents; the base must provide tool registration/discovery, parameter validation, permissions/quotas, call tracing, and retry; the security baseline is tools run in a sandbox with keys injected by the base, never into prompts or logs. Block 4 — Memory gives continuity: short-term/session (current context, window-limited, needs trimming and summarization), long-term/user (cross-session preferences/facts/conclusions, retrievable), knowledge/retrieval (enterprise KB/docs, RAG recall into context), skill/reuse (sedimented Skill templates shared across Agents); the hard part isn't "storing" but "when to fetch, how much, how not to pollute context" — overdoing memory is worse than none. Block 5 — WebService and channel access: outward IM/email/Web/HTTP API share one channel layer that flattens message formats, rich text, files, @/threads, rate limiting, retry; inward unified HTTP/gRPC for business systems; plus session routing (whose message to which Agent) and identity mapping (enterprise account ↔ Agent user) — many Agent projects die here (model works but can't plug into the enterprise's existing communication/system flows).
- Key claims: These five blocks are the substance of a base; getting channels wrong is a common death.
- Learner-relevant: The capability-by-capability breakdown, each with its key engineering concerns.

### 工程设计-插件化与生产门槛

- Locator: `[[sources/geek-ai-agent/20260922/直播1：企业需要怎样的 Agent 底座.pdf#工程设计-插件化与生产门槛]]`
- Summary: Plugin-ization lets the base evolve long-term: Provider plugins (change model without changing upper layers), Tool plugins (add tools without touching the core), Memory/storage plugins (change storage by adding an implementation); the approach is to define interfaces in the core and put implementations in plugin directories loaded via SPI/registry. Benefits: the core stays small and stable, extension is delegated to plugins, and community/teams contribute in parallel. The test: adding a model/tool, does it require changing core code? If yes, the abstraction is wrong. Production threshold (determines "can it be used"): multi-tenant isolation (different departments/businesses' Agents, data, quotas don't interfere), permissions and quotas (who can call which tool, how many times daily, what happens when exceeded), Tool sandbox (execution has resource and network boundaries; errors don't affect the base), full-chain audit (every call traced: who, when, what, result). Demo stage nobody cares about these; entering an enterprise, the first review asks exactly these.
- Key claims: Plugin architecture as the condition for long-term evolution, and the four production-readiness blocks.
- Learner-relevant: The plugin/SPI design principle and the production-governance checklist.

### 用-AI-做底座的三件事-契约-分块-判官

- Locator: `[[sources/geek-ai-agent/20260922/直播1：企业需要怎样的 Agent 底座.pdf#用-AI-做底座的三件事-契约-分块-判官]]`
- Summary: Can AI build such a base? The conclusion: the core code can mostly be written by AI — provided you design "how to write" well. AI is bad at architectural decisions under ambiguity and good at high-intensity output under clear constraints; the key isn't prompt tricks but three things. (1) Contracts first: nail cross-module things first — the core domain model (what an Agent/session/tool call looks like) and each layer's interfaces; only then split into modules, otherwise each block defines its own and they can't assemble (the most common AI-big-project failure). Contracts are the single source of truth: change the interface, change the contract first, let implementation follow, no reverse drift. (2) Deliver in blocks: each block has clear input (what it does, interactions, interfaces, parameters), constraints (what it mustn't touch, stop when unsure), and acceptance (auto-judgeable assertions + required tests); hand AI one block at a time and only move on when acceptance is green — controlled process, localizable errors; the human defines input/acceptance and reviews key boundaries, and can be absent mid-execution. (3) Judge runnable: without verification, AI confidently errs; the judge is automated tests, type checking, compilation, CI, answering "did it work right" every round; the greatest risk is the judge being bought off (AI changes/deletes tests to go green), so tests are made non-rewritable rules and heavy verification goes to CI (out of AI's reach). This is the Harness: code conventions + security red lines + acceptance judge; it determines how many reworks you do. For Agent OS-like projects, acceptance focuses on tool-call correctness, permission boundaries, and session consistency.
- Key claims: The bases' core can be AI-written if you design the "how"; contracts-first + block delivery + runnable judge is the lesson's throughline for 11 weeks.
- Learner-relevant: The concrete method for steering AI on a large project.

### 对这一层的判断

- Locator: `[[sources/geek-ai-agent/20260922/直播1：企业需要怎样的 Agent 底座.pdf#对这一层的判断]]`
- Summary: How the Agent base evolves over the next three years: protocols converge (tool/data access standardizes progressively — MCP-like protocols will be like JDBC/ODBC); the base sinks into infrastructure (like today's message queues and registries, becoming a standard enterprise layer); the competition point shifts from "can it run" to "governance and cost" (audit, permissions, quotas, observability, multi-model scheduling); open source will hold a substantial share (enterprises wanting control need a base they can inspect and modify themselves). The opportunity: in the window where the standard isn't fixed and the base isn't yet shaped, individuals and small teams can cut in.
- Key claims: The window is open now, which is why cutting in is worthwhile.

### 回到开发者-能力与作品

- Locator: `[[sources/geek-ai-agent/20260922/直播1：企业需要怎样的 Agent 底座.pdf#回到开发者-能力与作品]]`
- Summary: The job is changing: "can use AI" is now a default in hiring, and what's really assessed is whether you can deliver a system; the work content is changing (coding's share drops, understanding requirements/defining contracts/designing verification rises); the evaluation is changing (interviews and promotions increasingly look at "what have you independently carried", not "how many lines did you write"). So the question becomes: do you have a system-level work you can explain and defend under questioning? What's depreciating: skill at translating clear requirements into code, memorizing API usage/framework config details, only "knowing a tool" at one point. What's more valuable: turning fuzzy problems into clear specs, architecture judgment and tech selection (aligned to the scenario), verification design (how to prove it's right), and accountability/reputation for results — AI replaces "execution", leaving "definition, judgment, accountability", exactly what veteran engineers accumulate most. Four-step ability path: (1) specification ability (write fuzzy requirements into verifiable specs — What/boundaries/acceptance), (2) architecture judgment (do selection comparisons: why this not that), (3) verification design (design tests for key failure modes, not coverage-chasing), (4) steering method (contracts-first + block delivery + runnable judge, turning AI into capacity). Why do a big project: it simultaneously gives technical ability, a talkable work, and an open-source identity — the three amplify each other; the practical advice is not to invent a "perfect project" from zero but pick a real, continuously-evolving direction.
- Key claims: AI replaces execution, leaving definition/judgment/accountability — grow ability toward those three; one real project carried end-to-end is the most effective practice.
- Learner-relevant: The career/capability takeaway and the concrete four-step practice path.
