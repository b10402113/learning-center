# Digest — 03-20 20. 项目篇 When：业界调研

## Overview (L1)

- Purpose — pre-project industry research for When: survey how delayed delivery (延时投递) is actually done in industry — what exists, what is missing, and where each approach's boundary lies — before deciding what When should build.
- Demand is real and broad — delayed delivery appears in e-commerce/transactions (order auto-cancel, coupon expiry, refund timeout, group-buy settlement), push/notification, tasks/workflows (exponential-backoff retry, scheduled reports, reconciliation, approval timeout), risk/audit (delayed settlement, threshold-triggered rules, archival), and misc (meeting reminders, IoT wakeups, A/B delayed effects) — precision tiers are second/minute/hour-day and reliability tiers vary by business.
- Message-middleware delay capabilities — Kafka has none natively (external ZSet or internal-topic time-bucketing workarounds); RocketMQ 4.x has 18 fixed delay levels (max 2h; 5.0 adds time-wheel arbitrary delay but low adoption); Pulsar supports arbitrary delay natively but is heavy; RabbitMQ needs TTL+DLX or the delayed-message plugin — the common flaw is all are bound to a specific middleware and cannot cover non-MQ downstreams.
- SDK approaches — Redis ZSet delayed-queue SDKs (Redisson, HDT3213/delayqueue, Curator) suffer big-key risk, SDK-form limitations (client polling/retry/state, hard upgrades, poor observability, no cross-language), and dependence on the business's own Redis, so they cap out at small-scale.
- Independent delay-service attempts — Airbnb Dynein (AWS-bound, old stack, stagnant), Netflix Dyno-queues (Dynomite-bound, cold), DiDi DDMQ + Chronos (RocketMQ-bound, deep stack, low community activity) — the position is empty; QMQ (Qunar) has the most respected delay design (disk schedule-log hourly + in-memory 500ms hash wheel, O(1), 2-year span, lazy loading) but is still an MQ.
- Related-but-distinct categories — task queues (BullMQ/Celery/Sidekiq) center on worker execution, not precise delivery; task schedulers (XXL-JOB/PowerJob/Quartz) center on cron-style predefined jobs, not runtime-generated per-message delay.
- Cloud-hosted schedulers — AWS EventBridge Scheduler and GCP Cloud Tasks are serverless and cheap at small scale but vendor-bound, target-range-limited, and unsuitable for most domestic/private deployments.
- Underlying algorithms — six approaches (DB polling, RocksDB+time wheel, Redis ZSet+hash pool+workers, RocketMQ fixed levels, QMQ multi-level wheel, multi-level wheel+LSM); selection dimensions: write throughput, scheduling precision, time span, memory, multi-replica, implementation complexity — no silver bullet.
- Language ecosystems — Node/Python/Ruby have complete but task-queue-leaning options; Go is essentially empty; Java has the densest demand but no project focused on general delayed delivery.
- Judgment — demand real/broad/long-term; solutions scattered and limited; the independent general-purpose delayed-delivery service has no de facto standard.

### 一、延时投递这件事在哪些地方出现

- Locator: `[[sources/geek-ai-agent/20260922/03-20 20. 项目篇 When：业界调研.html#一延时投递这件事在哪些地方出现]]`
- Summary: Confirms the demand side with typical scenarios and shared characteristics.
- Key claims: e-commerce/transaction, push/notification, task/workflow, risk/audit all need it; the core is triggering an action at a precise future time, while "where it is delivered" is the boundary; scale ranges from 10k–1M (SMB) to 1B+ daily (top internet firms); precision tiers second/minute/hour-day; reliability tiers strict (order/payment), tolerant (push), best-effort-with-compensation (archival).
- Learner-relevant: Establishes why a general delayed-delivery component is a legitimate infrastructure need.

### 二、消息中间件的延时能力

- Locator: `[[sources/geek-ai-agent/20260922/03-20 20. 项目篇 When：业界调研.html#二消息中间件的延时能力]]`
- Summary: Reviews built-in delay capabilities of Kafka, RocketMQ, Pulsar, RabbitMQ.
- Key claims: Kafka has no native delay (ZSet+worker or internal-topic time-bucketing workarounds, neither clean); RocketMQ 4.x has 18 fixed levels (1s…2h), 5.0 adds time-wheel arbitrary delay but low adoption; Pulsar natively supports arbitrary delay via Delayed Message Tracker but the whole system is heavy; RabbitMQ uses TTL+DLX (coarse, ordering issues) or the delayed-message plugin (built for small scale); all bind delay to a specific middleware, whereas real downstreams are HTTP/RPC/Push/ClickHouse etc., and businesses often use multiple downstreams at once.
- Learner-relevant: The root boundary of middleware-native delay — coverage of the target space.

### 三、SDK 类延时方案

- Locator: `[[sources/geek-ai-agent/20260922/03-20 20. 项目篇 When：业界调研.html#三sdk-类延时方案]]`
- Summary: Analyzes Redis-ZSet-based delay-queue SDKs.
- Key claims: main SDKs are Redisson DelayedQueue (Java), HDT3213/delayqueue (Go), Curator DistributedDelayQueue (ZK, poor at scale); three layers of problems — big key (a single ZRANGE/ZREM can block Redis for hundreds of ms; sharding only mitigates), SDK-form limits (client polling/retry/state, hard upgrades, observability on the business, version fragmentation, no cross-language), and dependency on the business's Redis (QPS impact, big-key risk, ambiguous ops responsibility); SDKs solve small-scale delay, not general infrastructure.
- Learner-relevant: Why When's storage design must avoid big keys.

### 四、独立延时服务的尝试

- Locator: `[[sources/geek-ai-agent/20260922/03-20 20. 项目篇 When：业界调研.html#四独立延时服务的尝试]]`
- Summary: Reviews independent delay-service attempts and why they failed.
- Key claims: Airbnb Dynein (2019) split scheduling (DynamoDB) and queue (SQS), stateless on K8s, but AWS-bound, old Java/Dropwizard stack, stagnant community, no web console; Netflix Dyno-queues is Dynomite-specific and cold; DiDi DDMQ + Chronos is the most complete domestic case — PProxy `sendDelay` → inner topic → RocksDB storage engine + time wheel → back to PProxy — with LSM write advantages, second-level/cyclic delay, multi-language clients, but deep stack (PProxy+RocketMQ+Chronos+RocksDB), self-managed RocksDB replication, RocketMQ-bound, low community activity; conclusion — the position of a widely-adopted, general, active independent delay service is still empty.
- Learner-relevant: Design precedents and anti-patterns (vendor/infra binding, ops weight, community neglect).

### 五、QMQ：延时设计最被业界认可的开源 MQ

- Locator: `[[sources/geek-ai-agent/20260922/03-20 20. 项目篇 When：业界调研.html#五qmq延时设计最被业界认可的开源-mq]]`
- Summary: Details QMQ's two-level hash-wheel delay design.
- Key claims: first layer on disk — one file (schedule log) per hour, up to 17,568 files for 2 years; second layer in memory — 500ms granularity, loading the upcoming hour's message index (offset+size) from disk; advantages: O(1) insert/delete, huge time span via multi-level, memory-friendly via lazy loading, delay messages stored separately (no impact on normal message space reclamation); still an MQ, not an independent service, with limited open-source community.
- Learner-relevant: The reference engineering model (schedule log + multi-level wheel) for any delay storage engine.

### 六、任务队列和任务调度：边界要划清楚

- Locator: `[[sources/geek-ai-agent/20260922/03-20 20. 项目篇 When：业界调研.html#六任务队列和任务调度边界要划清楚]]`
- Summary: Distinguishes task queues and task schedulers from delayed delivery.
- Key claims: task queues (BullMQ/Celery/Sidekiq/Resque/Faktory) center on distributing tasks to workers, delay is an add-on; delayed delivery centers on precisely triggering a message to a downstream with no worker concept; a comparison table contrasts core action, design center, downstream binding (worker process vs any downstream), and business intrusion; task schedulers (XXL-JOB/PowerJob/ElasticJob/Quartz) center on cron-style predefined jobs, whereas delayed delivery generates per-message delays at runtime with differing targets/delays/content/context — neither can replace a delayed-delivery component.
- Learner-relevant: Prevents product-boundary confusion when defining When.

### 七、云厂商的托管延时服务

- Locator: `[[sources/geek-ai-agent/20260922/03-20 20. 项目篇 When：业界调研.html#七云厂商的托管延时服务]]`
- Summary: AWS EventBridge Scheduler and GCP Cloud Tasks.
- Key claims: AWS EventBridge Scheduler (Nov 2022) is serverless, supports one-time/recurring at arbitrary precision, 200+ AWS targets/6000+ API operations, built-in retry (185 attempts/24h) + DLQ, 14M free calls/month; GCP Cloud Tasks predates it by 4 years; boundaries — vendor-bound/not portable, targets limited to cloud-internal services, and unsuitable for most domestic core businesses.
- Learner-relevant: When a managed option is reasonable and when it is not.

### 八、延时投递的底层算法

- Locator: `[[sources/geek-ai-agent/20260922/03-20 20. 项目篇 When：业界调研.html#八延时投递的底层算法]]`
- Summary: Six implementation approaches and selection dimensions.
- Key claims: (1) DB periodic scan — simple but B+Tree poor for heavy writes; (2) RocksDB + time wheel (Chronos) — LSM write throughput but heavy HA; (3) Redis ZSet + hash pool + multi-worker — performant/simple but big-key and single-thread sensitive; (4) RocketMQ fixed levels — simple but inflexible/max 2h; (5) QMQ multi-level wheel — O(1), large span, memory-friendly, complex; (6) multi-level wheel + LSM — theoretically optimal, most complex; selection dimensions: write throughput, scheduling precision, time span, memory, multi-replica, implementation complexity — no silver bullet.
- Learner-relevant: The algorithmic landscape behind storage/scheduling choices.
