# Digest — 03-22 22. 项目篇 When：技术方案文档

## Overview (L1)

- Purpose — the How document for When, carrying forward the requirements doc; it targets the 3-week MVP = a production-usable distributed delayed-delivery component (cluster coordination, Master/Slave replicas, automatic failover, node scaling), excluding extension capabilities (more Sinks, auth, console enhancement, DLQ, SDKs).
- Core technical decisions — ETCD over ZooKeeper/Consul (cloud-native, simple API, light clients); Redis over RocksDB/MySQL (fast writes, fast key access, TTL); multi-layer time wheel over DelayQueue/Quartz/ZSet (O(1), in-memory, high precision); Master/Slave over Raft/Paxos (fast switch, not strong consistency); HTTP outside + gRPC inside; Java; and why cluster/HA is in-scope in 3 weeks.
- Overall architecture — business → When cluster (homogeneous nodes, Controller as a role) → external deps (ETCD/Redis) → downstream Sinks; node modules: ingress, router, time-wheel engine, replica synchronizer, Sink deliverer, ETCD client, Redis client, observability; production starts at 3 nodes.
- Cluster formation/coordination — node registration `/when/nodes/{node_id}` with a 10s Lease; heartbeat KeepAlive on an isolated thread every 3s; Controller election via atomic PUT/Txn on `/when/controller`; Watch-based node join/leave awareness (PUT→rebalance, DELETE→promote Slave); ETCD key-space design principles (clear hierarchy, small keys, distinct lifecycles).
- Multi-layer time wheel — ring array + pointer; layers 60×1s / 60×1min / 24×1h / 30×1d covering 30 days; multiple wheels per node (id per wheel in ETCD); scheduling loop keeps I/O async and uses `sleep_until_next_slot()` to avoid drift.
- Replica mechanism — async Master→Slave sync; sync failure marks out-of-sync and triggers rebuild; failure detection purely via Lease; failover sequence (failure→Controller→promote→new Master restores from Redis→assign new Slave) within 10s; no-loss via "Redis persistence before returning" + "new Master restores from Redis"; at-least-once because delivery-then-delete can duplicate.
- Scaling/load balancing — node join (register→rebalance→migrate Slave→sync→promote role), node exit (active/abnormal), rebalance algorithm (1M+1S, different nodes, ±1, prefer migrating Slave, gradual), triggered on changes plus a 5-minute periodic check.
- Message lifecycle — write/schedule-deliver/cancel/query flows and Node restart recovery (load from Redis before registering).
- Persistence layer — Redis key design (`/when/messages/{message_id}` STRING with TTL deliver_at+7d, `/when/timewheels/{tw_id}/index/{message_id}`, slot SET only for recovery); read/write strategies (Pipeline); explicit big-key avoidance (no ZSet, no big Hash, index split by wheel); Redis HA left to deployers.
- API, Sink, console, observability, deploy — three core APIs with schemas; Sink interface + SPI + HTTP/Kafka implementations + retry policy; Vue3/Element Plus console and its admin APIs; Prometheus metrics + trace_id JSON logs + `/health`/`/ready`; three deployment forms with env-var config.
- Risks, follow-up, summary — risks (big key, memory, slave lag, burst expiry, ETCD partition, gRPC forwarding latency, Snowflake clock rollback) and open items; evolution (more Sinks, auth/rate-limit, DLQ, priority, cross-region, Operator, MCP); summary of six decisions.

### 4-集群组建与协调

- Locator: `[[sources/geek-ai-agent/20260922/03-22 22. 项目篇 When：技术方案文档.html#4-集群组建与协调]]`
- Summary: Registration, heartbeat, election, awareness, key space.
- Key claims: 4.1 register `/when/nodes/{node_id}` with a 10s Lease so failures auto-remove; 4.2 heartbeat KeepAlive every 3s on an isolated thread/connection (not business threads); 4.3 election via atomic Txn/PUT on `/when/controller` with Lease, new Controller loads cluster state then loops; 4.4 Watch `/when/nodes/` — PUT→rebalance, DELETE→promote Master's Slave + assign new Slave, declarative/event-driven not active probing; 4.5 key space `/when/nodes|controller|timewheels|config` with hierarchy/small-key/lifecycle principles.

### 5-多层时间轮设计

- Locator: `[[sources/geek-ai-agent/20260922/03-22 22. 项目篇 When：技术方案文档.html#5-多层时间轮设计]]`
- Summary: Single-layer principle, multi-layer cascade, cluster distribution, scheduling loop.
- Key claims: ring array of slots, pointer advances per tick, message placed by delay — O(1) insert/trigger but limited span; multi-layer 60×1s/60×1min/24×1h/30×1d with cascade downgrade; multiple wheels per node (2–4 default) for concurrency/fault isolation/load balancing, consistent hash by message ID selects the wheel (so query/cancel route correctly), gRPC-forward if Master elsewhere; scheduling loop only reads/triggers, does async Redis delete and async Sink submit, and uses `sleep_until_next_slot()` for absolute precision; no strict order within a slot.
- Learner-relevant: The cascade downgrade and non-blocking loop are core to precision.

### 6-Master/Slave 副本机制

- Locator: `[[sources/geek-ai-agent/20260922/03-22 22. 项目篇 When：技术方案文档.html#6-masterslave-副本机制]]`
- Summary: Replica concepts, async sync, failure detection, failover, no-loss/no-duplicate.
- Key claims: 1 Master + 1 Slave per wheel on different nodes; async sync (a few ms) never blocks writes; Redis is the single source of truth so brief lag is acceptable; sync failure marks out-of-sync and triggers rebuild; detection via Lease (no false positives from GC/network jitter); failover within 10s with writes briefly unavailable but stored messages never lost; no-loss = Redis-write-before-return + new Master restore; at-least-once because delivery-before-delete can duplicate; cross-system exactly-once is not worth the complexity (Kafka/RocketMQ/Pulsar all at-least-once).
- Learner-relevant: Why at-least-once + idempotency is the industry default.

### 7-节点扩缩容与负载均衡

- Locator: `[[sources/geek-ai-agent/20260922/03-22 22. 项目篇 When：技术方案文档.html#7-节点扩缩容与负载均衡]]`
- Summary: Join/exit flows and rebalance.
- Key claims: 7.1 join — register→PUT event→rebalance→migrate Slave→new node syncs→takes Slave role, always prefer migrating Slave (Master migration interrupts writes); 7.2 exit — active (SIGTERM→deregister→promote Master's Slave within ~1s→assign new Slave) and abnormal (Lease expiry, same but seconds); 7.3 rebalance rules (1M+1S, different nodes, balanced totals, triggered on changes) and pseudocode (target = total_replicas/node_count, migrate from overloaded to underloaded, prefer Slave, gradual, ±1), plus periodic 5-minute check.
- Learner-relevant: Migrating Slaves first is a business-continuity principle.

### 8-延时消息生命周期

- Locator: `[[sources/geek-ai-agent/20260922/03-22 22. 项目篇 When：技术方案文档.html#8-延时消息生命周期]]`
- Summary: Write, schedule/deliver, cancel, query, restart recovery.
- Key claims: write — validate→Snowflake ID→consistent-hash route→gRPC forward if needed→Redis persist (message + index) before returning→in-memory insert→async Slave sync, P99 ≤100ms; deliver — pointer→slot→downgrade→Sink pool async→success deletes Redis keys + syncs Slave delete, failure retries; cancel — locate wheel, O(1) remove, Redis delete, Slave sync; if already delivered returns "cannot cancel"; query — route to Master, read memory or Redis, five states; restart — initialize but do NOT register until data is loaded from Redis, then register (avoids "registered but not ready").
- Learner-relevant: Ordering guarantees and states define correctness.

### 9-持久化层设计

- Locator: `[[sources/geek-ai-agent/20260922/03-22 22. 项目篇 When：技术方案文档.html#9-持久化层设计]]`
- Summary: Redis key design, read/write strategy, big-key avoidance, HA.
- Key claims: 9.1 `/when/messages/{message_id}` STRING (JSON) TTL deliver_at+7d, `/when/timewheels/{tw_id}/index/{message_id}` STRING (deliver_at), `/when/timewheels/{tw_id}/messages_in_slot/{slot_key}` SET only for restart recovery; message body split per message ID, index split by wheel, TTL as a safety net; 9.2 write path Redis-first with Pipeline, else return failure and do not write memory; schedule path reads memory and async-deletes Redis; query reads memory cache then Redis; 9.3 explicitly no ZSet and no big Hash; cost is many small keys (millions fine for Redis); 9.4 MVP Redis single/master-slave, HA by deployer; on Redis outage writes fail and business retries.
- Learner-relevant: The concrete big-key avoidance everyone else fails at.
