### 二、OryxOS 定位与设计（Q3, Q14, Q17, Q21, Q22）
- Locator: `[[sources/geek-ai-agent/20260922/7.26 直播.pdf#OryxOS定位与设计]]`
- Summary: What OryxOS is for, how it compares to frameworks, its relationship to agent definitions, its security model, and whether to self-build.
- Key claims: writing an agent is easy but reliably running a fleet of agents in an enterprise is not —底座 value is private deployment/data residency, unified model access, shared memory/tools as public capabilities, multi-agent orchestration, fault recovery, permissions/audit (token audit is the least of it); analogies — framework is to app what OS/K8s is to services; LangGraph is a development framework, OryxOS is a runtime底座; for building an agent app now, use mature frameworks, treat OryxOS as a learning case (early project); framework vs AgentOS is "build vs run," not "technical vs non-technical"; agent definition (LLM/Tools/Loop/Memory/Environment) matches OryxOS core necessarily because it hosts agents, but elevates private per-agent implementations into shared public capabilities; MCP identity issue — OryxOS must pass through the end-user identity via OAuth-like tokens rather than substituting its own, keeping fine-grained authZ in the app while OryxOS does coarse orchestration and full-chain audit; do not clone a general底座 — use existing tools as the capability layer and build only the company-specific thin layer (internal system access, company processes/permissions/compliance, orchestration glue).
- Learner-relevant: Agent-OS vs framework concepts, enterprise agent governance, and the identity-pass-through security pattern.

### 三、Agent 技术与选型（Q10, Q11, Q15）
- Locator: `[[sources/geek-ai-agent/20260922/7.26 直播.pdf#Agent技术与选型]]`
- Summary: ReAct vs embabel/GOAP, Rust agent frameworks, and self-build vs SDK decisions.
- Key claims: ReAct lets the LLM decide the next step (flexible but unpredictable, each step burns LLM calls); embabel's GOAP uses a deterministic planner (explainable, predictable, fewer LLM calls, but requires modeling goals/actions/pre-postconditions), and "moving planning out of the LLM into deterministic algorithms" is important for reliable/explainable enterprise scenarios, echoing Loop Engineering's distrust of LLM autonomy; embabel is a JVM-native (Spring) framework, worth watching for Java/Spring enterprise work; for Rust, Rig (0xPlaygrounds, MIT, ~7600 stars by 2026-06, 20+ providers, OpenTelemetry, MCP, WASM; a library not a full framework) is the most mature LLM integration layer, with AutoAgents/rs-graph-llm/OpenFANG as options, nearly all built on Tokio; selection — application companies should use SDKs, platform/infrastructure companies should self-build the core mechanisms (Loop/Memory/orchestration) only when they are the differentiation; blindly copying big-tech self-build is a common mistake.
- Learner-relevant: A reusable framework-vs-self-build decision principle and concrete ecosystem picks.

### 四、职业发展与能力提升（Q5, Q12, Q13, Q16, Q9, Q4, Q6, Q8）
- Locator: `[[sources/geek-ai-agent/20260922/7.26 直播.pdf#职业发展与能力提升]]`
- Summary: How to grow from "understand" to "explain," how to train judgement, workflow design at the micro scale, the value of documents/judgement, open-source onboarding, git submodule, model channels, and review priorities.
- Key claims: "understand" is passive recognition while "explain" is active reconstruction — close the gap via Feynman restatement, reimplementation, and output-forcing input; judgement has no standard tutorial — define it as a reasoned trade-off under incomplete information, measure it by whether you can say why A over B and what you gave up, and train it via technical-selection writing, retrospectives, and reading others' trade-offs; workflow-design force is not building a whole pipeline from scratch but designing your own micro-workflow within a company's fixed skeleton (Loop Engineering, task cards, requirement grill); program value is judgement and documents are its carrier, so roles shift structurally toward judgement rather than simply shrinking; open-source onboarding is more about collaboration norms (Git flow, CONTRIBUTING, small good-first-issue, communication etiquette) than raw technical skill; git submodule solves version-locking but has fractured UX — prefer monorepo unless referencing an independently-evolving external repo; prefer official model channels, avoid proxy stations; review documents proportional to downstream impact — review spec and plan closely, skim tasks (fixing upstream beats arguing downstream).
- Learner-relevant: Direct, practical career and learning guidance tied to the course philosophy.
