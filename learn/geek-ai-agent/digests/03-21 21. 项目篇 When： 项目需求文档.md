# Digest — 03-21 21. 项目篇 When： 项目需求文档（需求文档）

## Overview (L1)

- Purpose — defines When's functional and non-functional requirements (What, not How); it is the basis for the technical solution doc, implementation, and training-camp teaching.
- Project overview — When is a general, independently-deployable distributed delayed-delivery component in Java that precisely delivers a message to any downstream (HTTP/Kafka/gRPC/MQ) at a specified time; it fills the open position identified by the industry research; long-term project in three phases (3-week MVP, student maintenance, community co-build); dual positioning as a real component and as an AI-programming teaching sample.
- AI-programming constraint — a hard requirement: ≥90% of core code written by AI (target 95%), all AI output human-reviewed, review must be real and recorded; use AI in an engineered way (Spec first, CLAUDE.md, Skills, Hooks, Plan Mode for important changes); several disallowed practices (human rewrite, 50/50 mixing, no-review merge, AI-as-autocomplete); a full-chain demo from one-line requirement to deployment.
- Design goals and non-goals — goals: general, extensible (pluggable Sink), reliable (cluster, Master/Slave, no loss), easy to integrate (plain HTTP API), operable (metrics/logs/health/console); explicitly not: task scheduler, message queue, worker framework, all-in-one MQ, payload parsing, downstream business logic guarantee.
- Users and scenarios — business developers, ops, platform admins, community contributors; scenarios: e-commerce order timeout, push scheduled send, task failure retry; anti-scenarios: daily cron batch, huge short-delay (ms) messages, business-code async execution, persistence/replay.
- 3-week MVP — message submit/query/cancel HTTP API, HTTP + Kafka Sinks, Redis storage, single-node multi-layer time wheel, deployment (Docker/K8s) + docs, two console pages, basic Prometheus metrics + structured logs; explicitly excludes cluster/Controller/master-slave/failover, other sinks, auth/rate-limit, DLQ, SDK, multi-tenant, cross-region, Operator, MCP.
- Follow-up and community — production reliability (cluster coordination, Master/Slave + failover) then high-frequency features (more sinks, auth/rate-limit, DLQ/custom retry, console enhancement, priority); GitHub community handoff with a long-term maintainer grown from students.
- Non-functional, flows, data model, milestones, risks, acceptance — QPS/latency/precision targets for MVP vs long-term; key flows (write, schedule/deliver, restart recovery); message data model fields; weekly milestones; identified risks (Redis big key, wheel memory, single-node restart, burst expiry); 7-item MVP acceptance including the special AI-output acceptance.

### 10-关键流程

- Locator: `[[sources/geek-ai-agent/20260922/03-21 21. 项目篇 When： 项目需求文档.html#10-关键流程]]`
- Summary: Write, schedule/deliver, and restart-recovery flows (MVP).
- Key claims: write — validate → generate global ID → write Redis (message by ID + time index) → add to in-memory wheel → return ID (P99 ≤100ms); schedule/deliver — pointer advances, batch messages at the second, submit to delivery pool, Sink by type, write result back, retry failures; restart recovery — reload pending/delivering indices from Redis, rebuild the wheel, then schedule (node unavailable during restart, business retries); full failover left to later.
- Learner-relevant: The exact ordering ("Redis write before returning") that guarantees no loss.
