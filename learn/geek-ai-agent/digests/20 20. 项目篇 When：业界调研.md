# Digest — 20 20. 项目篇 When：业界调研

## Overview (L1)
- 一、延时投递这件事在哪些地方出现 — 需求侧扫描：电商订单超时、消息推送、任务重试、风控审计等场景都依赖延时投递；需求规模分层（万级到十亿级）、精度分三档（秒/分钟/小时天）、可靠性分层（不丢不重/容忍丢失/可补偿）。
- 二、消息中间件的延时能力 — Kafka 无原生延时（靠外挂 Redis ZSet 或时间分桶）、RocketMQ 4.x 固定 18 档（5.0 起有任意时延）、Pulsar 原生 deliverAfter/deliverAt、RabbitMQ TTL+DLQ 或 Delayed Message Plugin；共同问题是绑定特定 MQ。
- 三、SDK 类延时方案 — Redis ZSet 类 SDK（Redisson DelayedQueue、HDT3213/delayqueue、Curator）三层问题：大 Key、SDK 形态局限、依赖业务自己的 Redis；只能解决小规模延时。
- 四、独立延时服务的尝试 — Airbnb Dynein（SQS+DynamoDB）、Netflix Dyno-queues（Dynomite）、滴滴 DDMQ+Chronos（RocksDB+时间轮）都没能形成事实标准；独立通用延时服务的"位置"是空的。
- 五、QMQ：延时设计最被业界认可的开源 MQ — 两级时间轮（磁盘小时级 schedule log + 内存 500ms 级），O(1) 操作、支持 2 年跨度、内存友好，但仍是绑定 MQ 的能力。
- 六、任务队列和任务调度：边界要划清楚 — BullMQ/Celery/Sidekiq 是"worker 执行任务"；XXL-JOB 等是 cron 调度平台；两者都不是延时投递，不能代替。
- 七、云厂商的托管延时服务 — AWS EventBridge Scheduler、GCP Cloud Tasks 托管省运维，但绑定云厂商、target 范围限于自家服务、不适合私有化/国内业务。
- 八、延时投递的底层算法 — 六种主流实现方案（DB 扫描、RocksDB+时间轮、Redis ZSet+Hash Pool+多 worker、RocketMQ 档位、QMQ 多级时间轮、多级时间轮+LSM）与选型维度对照。
- 九、不同语言生态在这件事上的状态 — Node/Python/Ruby 各有事实标准（BullMQ/Celery/Sidekiq）但偏任务队列；Java 需求最密集但没有专注项目；Go 基本空着。
- 十、综合判断 — 需求真实且广泛，现有方案分散且各有局限，通用且独立且专注延时投递的开源项目当下没有事实标准。
- 附录 A/B — 关键术语表与主要参考资料链接。

### where-delayed-delivery-appears

- Key claims: 订单 30 分钟未支付取消、优惠券提醒、退款超时自动确认、拼团结算是典型场景；指数退避重试是延时最经典应用；头部互联网公司延时消息日流水达十亿级；精度分秒级/分钟级/小时到天级三档，绝大多数场景需求在秒级到分钟级；可靠性分严格不丢不重、容忍丢失、容忍小概率丢失+补偿三层。

### mq-built-in-delay-capabilities
- Locator: `[[sources/geek-ai-agent/20 20. 项目篇 When：业界调研.html#二、消息中间件的延时能力]]`
- Summary: 逐一分析 Kafka、RocketMQ、Pulsar、RabbitMQ 的延时能力及各自边界，指出共同问题是延时能力绑定特定 MQ 体系。
- Key claims: Kafka 无原生延时，外挂方案为 Redis ZSet+定时投递或内部 topic 时间分桶，都不干净；RocketMQ 4.x 只支持 18 个固定档位（1s 到 2h），不能任意秒级延时，5.0 有"任意时延消息"但生产采用率不高；Pulsar Delayed Message Tracker 原生支持任意延时（deliverAfter/deliverAt），但体系重（broker/bookie/ZK）是"杀鸡用牛刀"；RabbitMQ TTL+死信队列粒度粗、消息只能按入队顺序过期，官方 Delayed Message Plugin 基于 Mnesia、不适合大量延时；这些方案都覆盖不了"投到 HTTP/Push/ClickHouse 等多下游"的场景。
- Learner-relevant: 支撑 When"不绑定特定 MQ、Sink 可插拔"的核心决策，也解释了为什么不能直接复用现有 MQ。

### sdk-delay-solutions
- Locator: `[[sources/geek-ai-agent/20 20. 项目篇 When：业界调研.html#三、SDK 类延时方案]]`
- Summary: 分析基于 Redis ZSet 的延时队列 SDK（Redisson、HDT3213/delayqueue、Curator）及其三层问题与天花板。
- Key claims: Redisson DelayedQueue 是 Java 生态用得最多的；HDT3213/delayqueue 是 Go 生态 stars 较高的 SDK（支持 worker 横向扩展、Redis Cluster）；Curator DistributedDelayQueue 基于 ZK、生产基本没人用；三层问题：Redis ZSet 大 Key（ZRANGE/ZREM 可能卡实例几百毫秒，分片只能缓解）、SDK 形态局限（客户端要轮询/幂等/重试、升级难、可观测差、跨语言难）、依赖业务自己的 Redis（QPS 冲击、运维责任不清）；SDK 只能解决小规模延时，做不了通用基础设施。
- Learner-relevant: 锚定"大 Key 是 SDK 方案的经典坑"，为 When 的存储设计（按消息 ID 拆 key、不用 ZSet）提供依据。

### independent-delay-service-attempts
- Locator: `[[sources/geek-ai-agent/20 20. 项目篇 When：业界调研.html#四、独立延时服务的尝试]]`
- Summary: 考察 Airbnb Dynein、Netflix Dyno-queues、滴滴 DDMQ+Chronos 三个独立延时服务尝试，总结它们都没活下来的原因。
- Key claims: Dynein（2019 开源）把延时拆成"调度+队列"，调度层 DynamoDB、队列层 SQS，但强绑定 AWS、Java+Dropwizard 技术栈偏老、开源后无持续投入、无 Web 管理台；Dyno-queues 基于已停维护的 Dynomite、通用性不强已冷；Chronos 基于 RocksDB 自研延时消息队列（生产经 PProxy 的 sendDelay RPC 到 inner topic，消费存本地 RocksDB 构造时间轮，到期回送 PProxy），支持秒级/循环延时、多语言客户端（PHP/Java/Go/C++/Python）、Thrift RPC/HTTP 推送/第三方直写，但层级深、自管 RocksDB 多副本重、绑定 RocketMQ 不能独立部署、社区活跃度低；独立通用延时服务当下没有事实标准，"位置是空的"。
- Learner-relevant: 直接论证 When 的市场空位与差异化机会；Chronos 的 RocksDB 时间轮是"When 技术选型对照"的参考。

### qmq-multi-level-timewheel
- Locator: `[[sources/geek-ai-agent/20 20. 项目篇 When：业界调研.html#五、QMQ：延时设计最被业界认可的开源 MQ]]`
- Summary: 介绍去哪儿网 QMQ 的两级 hash wheel 延时设计（磁盘小时级 schedule log + 内存 500ms 级）及其优势，并说明它仍是绑定 QMQ 的能力。
- Key claims: 第一层磁盘每小时一刻度生成 schedule log，默认支持 2 年延时、最多 2×366×24=17,568 个文件；第二层内存 500ms 刻度，投递时间临近时把该小时消息索引加载进内存；优势：时间轮 O(1) 插入删除免排序、多级支持超大跨度、延时加载内存友好、schedule log 单独存储不影响正常消息空间回收；但要用其延时必须用 QMQ，社区规模有限，主要是去哪儿网内部使用。
- Learner-relevant: QMQ 的 schedule log + 多级时间轮是"When 时间轮设计"最直接参考范本。

### task-queue-vs-scheduling-platform
- Locator: `[[sources/geek-ai-agent/20 20. 项目篇 When：业界调研.html#六、任务队列和任务调度：边界要划清楚]]`
- Summary: 划清任务队列（BullMQ/Celery/Sidekiq/Resque/Faktory）和任务调度平台（XXL-JOB/PowerJob/ElasticJob/Quartz）与延时投递的边界。
- Key claims: 任务队列核心动作是"把任务交给 worker 执行"，延时是附带功能；任务调度平台核心是 cron 风格预定义任务+执行器集群（XXL-JOB 约 29.6k stars），与"业务运行时凭空产生一条延时消息"的需求模型完全不同；两者都不专注延时投递，不能代替。
- Learner-relevant: 支撑 When"不做任务调度平台、不做 worker 执行框架"的范围决策，避免产品形态混淆。

### cloud-managed-delay-services
- Locator: `[[sources/geek-ai-agent/20 20. 项目篇 When：业界调研.html#七、云厂商的托管延时服务]]`
- Summary: 介绍 AWS EventBridge Scheduler 与 GCP Cloud Tasks，指出云厂商方案的边界。
- Key claims: EventBridge Scheduler（2022 年 11 月推出）Serverless、支持 one-time/recurring、200+ AWS 服务 target、6000+ API operations、默认重试 185 次持续 24 小时+DLQ、14M 调用/月免费；局限：强绑定 AWS、一次性任务需主动删除否则占配额、规模受 open tasks 数限制、不适合私有化/混合云/跨云；GCP Cloud Tasks 早 4 年（2018 起）类似；对国内业务（大多不在公有云跑核心业务）基本不在选择范围。
- Learner-relevant: 补充 When"独立部署、可私有化、不绑定云"的差异化价值。

### bottom-layer-algorithms
- Locator: `[[sources/geek-ai-agent/20 20. 项目篇 When：业界调研.html#八、延时投递的底层算法]]`
- Summary: 对比延时投递的六种主流底层实现方案（数据库定时扫描、RocksDB+时间轮、Redis ZSet+Hash Pool+多 worker、RocketMQ 档位制、QMQ 多级时间轮、多级时间轮+LSM 综合），并给出算法选型关键维度。
- Key claims: DB 扫描实现简单但写入性能崩、适合小规模原型；RocksDB+时间轮（Chronos 方案）写入吞吐高（LSM Tree）但需自实现多副本；Redis ZSet+Hash Pool+16 分片+多 worker 性能高部署简单但有大量 Key 问题；档位制简单但只有 18 档、最长 2 小时；QMQ 多级时间轮 O(1)、支持 2 年、内存友好但实现复杂；多级时间轮+LSM 理论上最优组合但复杂度最高；选型维度：写入吞吐（LSM 优于 B+Tree）、调度精度（时间轮>ZSet>DB 扫描）、时间跨度（多级时间轮>单级）、内存占用（延时加载，QMQ schedule log 为范本）、多副本、实现复杂度（DB 扫描<档位<ZSet<单级时间轮<多级时间轮）；没有银弹。
- Learner-relevant: 为 When 的时间轮调度算法与存储选型提供完整对比框架和判断依据。
