# Digest — 第28节：全流程串联（二）让底座自己跑得稳

## Overview (L1)

- 本节目标 — connect the other half: the base must stay correct when nobody is watching ("没人问、也照样干活；重启了、也不失忆；多个 Agent、互不打架"), across three verifiable pillars: a full scheduled-task subsystem, restart recovery, and multi-Agent coexistence.
- 定时任务子系统 — a skill-defined cron task that runs "查天气 → notify 推送" by itself, persists task status and execution history to SQLite, and is viewable/manageable (run-now / enable-disable) in the admin — up from lesson 25's in-memory-only cron registration.
- 重启恢复与多 Agent — kill and re-serve: sessions, memory, scheduled tasks (status + history), and audit all return; two different Profiles run on one instance with tool / session / schedule isolation intact.
- 从能跑到跑得稳 — timeouts everywhere, human-readable error messages, one clear log line per trigger, and external MCP failures never dragging down startup.
- 验收 — four groups: `ScheduledTaskE2ETest` (mock, in-gate, no key), `SchedulerFlowIT` (real key), `RestartRecoveryIT` (real key), and a multi-Agent isolation test, plus the Demo prerequisite checklist for lesson 31.

- Summary: Lesson 27 verified "有人问、答得对"; this lesson wants "nobody asks but it still works; restart but it doesn't forget; multiple Agents but they don't fight". Three verifiable pillars: (1) scheduled-task subsystem — one skill defines a scheduled task → it fires "check weather → notify push" → result persisted to SQLite (task status + execution history, survives restart) → visible and manageable in the admin (run-now / enable-disable); (2) restart recovery — kill and re-serve and sessions, memory, schedules (status + history), audit all return; (3) multi-Agent coexistence — two visibly different Profiles run on the same instance with tool, session, and schedule isolation held.
- Key claims: These three are the watershed between an Agent OS and "an Agent demo" — a demo only needs to live during the demo minutes, a base must stay correct unwatched.
- Learner-relevant: The "unwatched correctness" goal and the schedule-chain diagram (cron trigger → same `AgentService.process` → ReAct → notify → DB), framed as "human-push chain with a different trigger head and a push tail".

### 二-1-定时任务子系统-从定义-执行到管理

- Locator: `[[sources/geek-ai-agent/20260922/第28节：全流程串联（二）让底座自己跑得稳.pdf#二-1-定时任务子系统-从定义-执行到管理]]`
- Summary: A scheduled task must be definable, self-running, remembered, and manageable — built in four blocks. (1) Definition still uses skill — one task = one `schedules` entry (`id + cron + zone + message`), the message being the prompt handed to `AgentService.process`; consistent with lesson 29's skill-centric stance, no second definition source. (2) Execution — a test Profile fires every two minutes with "查一下北京天气，把穿搭建议推送出去", and reconciliation expects: the `scheduler`-channel session is reused (second trigger appends to the same history), `llm_calls` = 2, `tool_invocations` = 2 (`http_get` + `notify`), and the webhook really receives it; pitfall one is session reuse (two triggers still one row), pitfall two is push failure (off-whitelist domain → Sandbox blocks, one `success=false`, scheduler not dragged down). (3) Persistence — two hand-built tables `scheduled_tasks` (`task_id/profile_name/cron/zone/message/enabled/next_run_at/last_run_at/last_status/run_count`) and `task_executions` (`task_id/session_id/started_at/success/error_message/duration_ms`), behind a `ScheduledTaskStore` core interface with a JPA implementation in storage (dependency inversion); `AgentScheduler` registers each task with computed `next_run_at`, splits "check enabled → execute", skips disabled tasks, writes executions and updates status, and adds `runNow(taskId)`. (4) Management — four endpoints (`GET /schedules`, `GET /schedules/{id}/executions`, `POST /schedules/{id}/run`, `PUT /schedules/{id}`) plus an admin "定时任务" page (list + run-now + enable/disable), the first write-operation page on lesson 26's read-only admin.
- Key claims: Defining schedules never adds a new definition source; persistence turns "schedules came back after restart" from a log-reading exercise into a single `GET /api/v1/schedules` assertion.
- Learner-relevant: How to grow a thin scheduler into a manageable subsystem while keeping skill as the single definition source and storage behind an interface.

### 二-2-跨重启恢复

- Locator: `[[sources/geek-ai-agent/20260922/第28节：全流程串联（二）让底座自己跑得稳.pdf#二-2-跨重启恢复]]`
- Summary: The architectural promise "all state lives outside the process (SQLite + filesystem), the process itself stores nothing" is verified by one restart: run dialogues, accumulate memory, let a scheduled task fire at least once, then kill and re-serve. Check each: sessions return (`GET /sessions/{id}` shows pre-restart history, since it's in SQLite); memory returns (MEMORY.md is a file, inherently cross-restart); scheduled tasks return (definitions re-registered from skill, status/history still in `scheduled_tasks`/`task_executions`, visible via `GET /api/v1/schedules`); audit is continuous (pre/post-restart `llm_calls` unbroken).
- Key claims: Any item that fails to return proves some state was secretly kept in process memory — a hazard that must be eliminated before going distributed ("stateless instances" is the tech-plan premise).
- Learner-relevant: The restart test as the way to expose hidden in-memory state.

### 二-3-多-Agent-并存

- Locator: `[[sources/geek-ai-agent/20260922/第28节：全流程串联（二）让底座自己跑得稳.pdf#二-3-多-Agent-并存]]`
- Summary: The core-phase minimum for "OS": multiple Profiles on the same instance. Configure two visibly different Profiles (one with only file tools, one with only HTTP tools), alternate them, and verify three isolation boundaries: tool isolation (A's dialogue tool list must not contain B's exclusive tools — `tools` filtering works), session isolation (A and B sessions don't mix — the id carries the Profile name, but watch for code using a "default Profile" that mixes them), and schedule isolation (A's scheduled task throwing must not stop B's next trigger — lesson 25's failure isolation re-verified in multi-Agent).
- Key claims: Isolation must be verified across all three dimensions, not just tool lists.
- Learner-relevant: The minimal multi-tenant boundary for an Agent OS.

### 二-4-从能跑打磨到跑得稳

- Locator: `[[sources/geek-ai-agent/20260922/第28节：全流程串联（二）让底座自己跑得稳.pdf#二-4-从能跑打磨到跑得稳]]`
- Summary: A final polish pass of small but demo-visible items: everything that should time out does (model call, tool execution, notify push), so one stuck call can't stall the whole virtual thread, with an overall 60s cap per Agent call (set in lesson 26); error messages are human-readable (`error_message` stores reasons like "域名不在白名单内: evil.com", not a stack trace — the audit table is for humans); one trigger is one clear log mainline (a dialogue/trigger traceable by session id without digging through hundreds of lines); an external MCP being down never drags OryxOS down (log WARN, skip its tools, start normally — someone else's availability must not become yours).
- Key claims: These are "stability" requirements that distinguish a base from a demo, and the MCP rule restates "external dependency must not drag down startup".
- Learner-relevant: The concrete stability checklist.

### 二-5-为-Demo-备好环境-前置条件清单

- Locator: `[[sources/geek-ai-agent/20260922/第28节：全流程串联（二）让底座自己跑得稳.pdf#二-5-为-Demo-备好环境-前置条件清单]]`
- Summary: Six prerequisites for lesson 31's two demos, configured and checked off once: (1) domain whitelist includes weather API + webhook domains; (2) notification channel configured and a manual notify received in the group; (3) news MCP declared in `mcp_servers.yaml` and its tools visible via `oryxos tool list`; (4) memory already contains a preference (talked about "更关注 AI 和芯片" into MEMORY.md); (5) cron expressions + explicit timezone (Asia/Shanghai) checked; (6) cross-restart verified (session persists, scheduled tasks re-register).
- Key claims: The easiest self-trip is the whitelist blocking your own demo — Sandbox defaults to deny-all, so three domains must be explicitly added: weather source `api.open-meteo.com`, the team notification webhook (e.g. feishu `*.feishu.cn` / WeCom `qyapi.weixin.qq.com`), and any news source; `file`/`shell` whitelists stay deny-all (unused by these demos); also confirm `OpenAiAutoConfiguration` was excluded or `serve` won't start.
- Learner-relevant: A deploy-readiness checklist that prevents a half-good environment during a live demo.

### 三-怎么验收-把对账固化成测试

- Locator: `[[sources/geek-ai-agent/20260922/第28节：全流程串联（二）让底座自己跑得稳.pdf#三-怎么验收-把对账固化成测试]]`
- Summary: Two verification lines for the subsystem — mechanism verification (registration/execution/persistence/management) using the mock provider in the gate, plus real-key chain verification (weather/notify really push). Four groups. Main: `ScheduledTaskE2ETest` (mock, in-gate, no key) — temp workspace with a `provider: mock` Agent carrying schedules (cron set far out, triggered via run-now), start registers it (run_count=0, enabled=true), `POST /schedules/{id}/run` runs a real ReAct, assert run_count=1/last_status=success/one execution record/memory queryable, then `PUT` disables it. Chain: `SchedulerFlowIT` (integration, real key) — test Profile firing "查北京天气推送穿搭", assert session reused, `llm_calls`=2, `tool_invocations`=2, test webhook received, and the off-whitelist failure path leaves `success=false` without killing the scheduler. Restart: `RestartRecoveryIT` (integration) — kill/re-serve, assert session history, core memory, schedules with status/history, continuous audit. Multi-Agent: two Profiles, three boundaries.
- Key claims: The acceptance list requires all of: skill-defined task registered at startup, run-now persisting run_count/last_status/history, disable stopping triggers, real-key chain reconciliation, failure isolation, restart recovery of all four, multi-Agent isolation, stability items, demo prerequisites, and `mvn clean verify` green.
- Learner-relevant: Two-line verification (no-key mechanism + real-key chain) and the full acceptance checklist.
