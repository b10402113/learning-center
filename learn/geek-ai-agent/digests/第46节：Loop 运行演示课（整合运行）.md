# Digest — 第46节：Loop 运行演示课（整合运行）

## Overview (L1)

- What this section does (这一节做什么) — A Loop runbook (not a module task spec) that fills in the root project, application assembly, and test support; runs the §40–45 module specs, integrates their outputs, and verifies whether the specs are precise enough. When a spec problem is found, the doc is revised first and the run repeats from a clean state. Structure: run goal → prerequisites → acceptance environment → execution steps → observed signals → problem handling → final acceptance.
- Prerequisites (跑之前要具备什么) — Materials for §40–45 each have explicit inputs, decidable acceptance, boundaries, and section-specific Harness and all cite §39; public seams (`TimeWheelRegistry`, `ClusterView`, `DueMessageHandler`) are frozen; external deps run via docker-compose etcd + Redis; the root-project baseline (JDK 21, Maven Wrapper, root dependencyManagement, module dirs/packages) is frozen; the overall Harness is assembled; and a test Sink records calls and returns success. First execution starts from a docs-only clean repo.
- Assembling the Harness (怎么组装整体 Harness) — Overall Harness = common Harness + per-section Harness + root skeleton + composition entry + test doubles + final acceptance + reproducible runtime. Covers the Maven multi-module layout, the single Composition Root (`when-app`) with a fixed 8-step startup order, the first-run due closure via `when-test-support` (`RecordingTestSink`, `TestDueMessageHandler`, `StaticClusterView`), static time-wheel maps (single/three node), the unified config contract, and executable judges.
- Loop Runner (怎么读取原料并推进) — Defines a two-layer loop: the outer Runner reads §46 + loop.yaml, selects a stage, prepares context, launches the inner loop, checks stage evidence, and saves checkpoints; the inner module loop reads one module's material → read-only check → plan → implement → run judge → read failure → fix within boundary. Includes per-stage context loading, `loop.yaml` as the machine-readable stage list, the stage state machine, checkpoints/run records/recovery, human handoff conditions, and the first-run stage order.
- Signals & honest week-7 scope (观察信号+第七周范围) — Signals to watch: Runner stage/status/attempt/judge, context, guardrails, recovery, automated acceptance, handoff reports, assembly, startup, end-to-end, routing, and cluster. The seventh-week scope completes the single-node core path, firing precision, no-message-loss restart, basic three-node cluster, and reproducible assembly; it explicitly excludes real HTTP/Kafka Sink, Master/Slave replica + 10s failover, and Controller dynamic rebalance.
- Problem handling (发现问题怎么办) — The section's core lesson: when tests fail, contracts conflict, or implementations overreach, first decide whether the spec is missing or the implementation violated it. A missing spec means revising the corresponding §40–45 doc and re-running from a clean branch; an already-clear spec means keeping it and letting Loop fix the implementation — never delete or loosen acceptance to pass tests. Includes a problem-to-section mapping table.
- Acceptance / boundary / deliverables (验收+边界+交付物) — Acceptance is the full week-7 automated set (loop.yaml parse, dry-run order, one active stage, minimal context, judge-failure stays, protected-file hash detection, max-attempts stop, interrupt recovery, Maven skeleton, docker-compose, startup lifecycle, end-to-end, due closure, cancel, precision, restart, static maps, cross-node, cluster, negative assembly, clean shutdown, green CI). Boundary: Runner is engineering orchestration, not a production business module and cannot lower standards. Deliverables include loop.yaml, harness/loop, state schema, fixed Maven skeleton, when-app, when-test-support, when-acceptance, config/first-run, and a reproducible run record.
