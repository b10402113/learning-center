# Digest — 18 18. 项目篇 OryxOS：技术方案文档

## Overview (L1)
- 方案概述 — Answers "How": OryxOS is a Spring Boot 3.x monolith on JDK 21, LLM calls via Spring AI Alibaba, self-implemented ReAct loop, single executable JAR; lists the 7 key technical decisions (ReAct self-implemented, Spring AI boundary, sync+virtual threads, Tool registration, MVC HTTP, whitelist sandbox, SQLite+audit tables) and the full tech stack.
- 整体架构 — One engine (ReAct loop) with two entrances (CLI Channel, Web Service) scheduling three capabilities (Provider, Memory, Tool) over a storage layer; four-layer view and the dependency relations among the five capabilities.
- 核心能力一：对接 LLM — ProviderService wrapping Spring AI Alibaba's ChatClient, Function Calling adapter, provider-name→ChatModel explicit mapping (not type scanning), no fallback/hedge racing in core, token cost logging.
- 核心能力二：ReAct 循环 — The core algorithm (Reason+Act, max 10 iterations), modules ReActLoop/PromptBuilder/ToolExecutor, message accumulation for auditability, context truncation (N=20 turns default).
- 核心能力三：Memory 三层记忆 — A unified MemoryService facade over session (SQLite) + long-term (MEMORY.md); MEMORY.md file design, injection into system prompt, USER.md vs MEMORY.md distinction, and what core stage omits.
- 核心能力四：Tool 体系 — OryxTool abstraction (getName/getDescription/getInputSchema/execute) unifying built-in/Plugin/MCP Tools; five built-in Tools; three Plugin modes; ToolRegistry; SandboxChecker with Path/Pattern whitelists.
- 核心能力五：Web Service — WebServer (Spring MVC + virtual threads, port 8080), six ApiControllers, GlobalExceptionHandler, OpenAPI via springdoc; the 10 core endpoints; error-code/limit/timeout design; extension endpoints and skipped items.
- 支撑模块 — InitCommand, ProfileLoader/ProfileRegistry, ContextLoader (Bootstrap+SKILL.md unified), CliChannel, three run modes, Picocli 12 subcommands, ConfigLoader with `${ENV_VAR}` placeholders.
- 数据持久化 — SQLite + Spring Data JPA choice rationale (no vector DB in core: LanceDB Java embedded not ready, others need external processes); three core tables (sessions, tool_invocations, llm_calls); audit write day one; file-system data; SQLite ALTER TABLE / ddl-auto warning.
- 项目工程结构 — Maven multi-module, 9 modules (oryxos-core, -provider, -memory, -tool, -web, -channel-cli, -storage, -cli, -boot) with responsibilities and fat-JAR packaging.
- 关键流程 — Five end-to-end flows matching the five acceptance demos (weather+ReAct, cross-dialogue memory, zero-code PR digest, Web Service sync call, multi-endpoint flow).
- 实施节奏（4 周） — Week-by-week build plan (Maven skeleton + Provider + ReAct; Memory + Tool; Web Service; multi-Agent + engineering) each with a demoable outcome.
- 性能和可扩展性考虑 — How targets are met: virtual threads, ~1000 concurrent Sessions ~50MB, MEMORY.md read 1–2ms, startup 2–4s (native <100ms later).
- 总结 — Recaps the core solution and the 4-week rhythm, storage choice, and positioning (runtime kernel now, governance layer extension).

### Key technical decisions
- Locator: `[[sources/geek-ai-agent/18 18. 项目篇 OryxOS：技术方案文档.html#key-decisions]]`
- Summary: The 7 decisions with reasons: ① self-implement ReAct loop (full control of Agent core); ② Spring AI used only for protocol conversion + schema generation, auto tool execution disabled (otherwise tools run twice); ③ sync-blocking execution model with virtual threads (intuitive code + concurrency); ④ @Tool annotation + OryxTool abstraction layer (ReAct unaware of Tool source); ⑤ Spring MVC + virtual threads (thousands of concurrent requests per node); ⑥ Path/Pattern whitelist sandbox, not SecurityManager (unusable on JDK 21); ⑦ SQLite + MEMORY.md with audit tables (tool_invocations, llm_calls) written from day one.
- Key claims: Decision two is the most bug-prone spot — Spring AI's built-in auto tool-calling must be disabled or tools get invoked twice; decision seven means auditable data foundations exist from the start, avoiding later log re-parsing.
- Learner-relevant: Anchor: the decision table that the AI-coding guide elevates into constitution principles (esp. ② and ⑦).

### Overall architecture
- Locator: `[[sources/geek-ai-agent/18 18. 项目篇 OryxOS：技术方案文档.html#architecture]]`
- Summary: A Spring Boot monolith with two entrances (CLI Channel for local interaction, Web Service for REST integration) converging into one engine — the ReAct loop — which schedules Provider (LLM calls), Memory (session + long-term), and Tool (execution + MCP Client); storage below: SQLite for session/audit, filesystem for Profile/Bootstrap/Memory/Skill.
- Key claims: Everything converges into one engine, one storage, one process — matching "single binary, install-and-run"; engine↔capability and capability↔external are decoupled via abstract interfaces so extension-stage additions happen at the edges without touching the core engine.
- Learner-relevant: Anchor: the one-engine architecture that later modules and the AI-coding tasks implement.

### Relations among the five capabilities
- Locator: `[[sources/geek-ai-agent/18 18. 项目篇 OryxOS：技术方案文档.html#capability-relations]]`
- Summary: ReAct loop is the engine fed by the other three: Provider (one LLM call per reasoning turn), Memory (context injected each prompt assembly), Tool (execution when the LLM decides); Web Service is the external exit packaging the four capabilities as REST, an entry/exit for the loop rather than part of it.
- Key claims: Simplification — Provider、Memory、Tool 供养 ReAct 循环这个引擎，引擎跑出的能力通过 CLI 和 Web Service 两个入口对外提供.
- Learner-relevant: Anchor: the dependency structure that determines user-story ordering in the AI-coding guide.

### Capability one: Provider abstraction
- Locator: `[[sources/geek-ai-agent/18 18. 项目篇 OryxOS：技术方案文档.html#provider]]`
- Summary: ProviderService wraps Spring AI Alibaba's ChatClient into an internal abstraction shielding ReAct from vendor differences; Function Calling adapter converts OryxTool to Spring AI's tool format (OpenAI/Anthropic/Gemini protocols handled by Spring AI, only format conversion, no auto execution); Provider config in application.yaml creates ChatModel beans.
- Key claims: Core stage has no fallback/hedge racing (errors surface directly to the Agent); cost transparency is basic — per-call token/Provider/model written to llm_calls table.
- Learner-relevant: Anchor: the module boundaries reused in oryxos-provider and US-1 tasks.

### Provider-name to ChatModel explicit mapping
- Locator: `[[sources/geek-ai-agent/18 18. 项目篇 OryxOS：技术方案文档.html#provider-name-mapping]]`
- Summary: Highlights a subtle point: with multiple Providers in Spring, multiple ChatModel beans exist and type-scanning cannot reliably distinguish deepseek from kimi (same bean type, bean name ≠ provider name); OryxOS maintains an explicit provider-name → ChatModel mapping (via Spring Qualifier or a config table, decided in R&D).
- Key claims: The "explicit mapping, not type scanning" principle must be held or multi-Provider fails; Profiles reference Providers by name.
- Learner-relevant: Anchor: a known AI-agent pitfall — the AI-coding guide flags "Provider 用类型扫描" as a top error to catch.

### Capability two: ReAct loop
- Locator: `[[sources/geek-ai-agent/18 18. 项目篇 OryxOS：技术方案文档.html#react-loop]]`
- Summary: The algorithm (append message → assemble prompt → LLM call → no Tool call? return; else execute, append result as tool message, loop; forced end at max iterations default 10) and its modules: ReActLoop (engine, ~tens of Java lines, not Spring AI's Agent abstraction), PromptBuilder (four-part assembly), ToolExecutor (finds Tool in registry, sandbox check, executes, wraps ToolResult, writes tool_invocations).
- Key claims: MAX_ITERATIONS default 10 (Profile-overridable) prevents Tool-call loops; every iteration appends LLM response + Tool result to Session messages, making the full chain queryable and auditable; context kept as system prompt + last N turns (default 20, Profile-configurable); core skips parallel Tool calls, agent-to-agent delegation, and streaming.
- Learner-relevant: Anchor: the exact algorithm and defaults that become the hardest task in the AI-coding guide (US-2).

### Capability three: Memory
- Locator: `[[sources/geek-ai-agent/18 18. 项目篇 OryxOS：技术方案文档.html#memory]]`
- Summary: A unified MemoryService facade exposes a single interface to ReAct, internally delegating session memory to SessionManager (SQLite) and long-term memory to LongTermMemory (MEMORY.md); LongTermMemory exposes append/load/recallByKeyword/truncateIfNeeded with an interface reserved for semantic upgrade (recall with a mode param); MemoryTools registers save_memory/recall_memory as @Tool built-ins.
- Key claims: This facade is a key adjustment vs the original plan (avoids Memory straddling two modules with no unified entry); long-term memory is re-read every prompt assembly (no cache) so a save is visible next turn; MEMORY.md is a simple markdown list with date headers, format intentionally loose.
- Learner-relevant: Anchor: the MemoryService facade design that the tech plan stresses (AI-coding guide checks the agent doesn't collapse Memory into Session).

### MEMORY.md vs USER.md
- Locator: `[[sources/geek-ai-agent/18 18. 项目篇 OryxOS：技术方案文档.html#memory-vs-user]]`
- Summary: USER.md is a Bootstrap file, user-written and OryxOS read-only — the user's "初始设定"; MEMORY.md is long-term memory written by the Agent via save_memory — the Agent's "成长记录"; both enter the system prompt but differ in source and lifecycle.
- Key claims: Core stage omits auto-extraction, semantic recall, episodic memory, Memory Wiki, and compression (plain truncation instead).
- Learner-relevant: Anchor: the role distinction learners need to avoid conflating the two files in implementation.

### Capability four: Tool system
- Locator: `[[sources/geek-ai-agent/18 18. 项目篇 OryxOS：技术方案文档.html#tool-system]]`
- Summary: OryxTool is the unified Tool interface (getName/getDescription/getInputSchema/execute returning ToolResult with success/result/error/retryable); five built-in Tools in three groups — FileTools (read_file/write_file/list_dir, path whitelist), ShellTools (bash with timeout + command whitelist), HttpTools (http_get/http_post, domain whitelist) — plus save_memory/recall_memory; Tool module is a three-in-one module (built-in + MCP Client + ToolRegistry + SandboxChecker) rather than separate builtin/skill/mcp modules.
- Key claims: Plugin mode one (zero-code SKILL.md + reused MCP servers) is the recommended path — SKILL.md has frontmatter (name/description/trigger/required_tools) + body, loaded into system prompt, no workflow engine, all logic left to the LLM; mode two = self-written MCP server configured in mcp_servers.yaml (name/transport/command/env), McpClientService connects at startup, tools/list → OryxTool wrapping, handles disconnects; mode three = @Tool-annotated Spring Beans (in-process, no MCP protocol, best performance, for deep Java integration); ToolRegistry scans @Tool methods + MCP-registered tools, Profile filters the usable subset.
- Learner-relevant: Anchor: the OryxTool interface and three Plugin modes that US-4 tasks implement (incl. the stdio-first MCP Client advice).

### Sandbox check
- Locator: `[[sources/geek-ai-agent/18 18. 项目篇 OryxOS：技术方案文档.html#sandbox]]`
- Summary: Core-stage sandbox is application-layer whitelist validation configured in application.yaml (file.allowed_paths, shell.allowed_commands, http.allowed_domains); SandboxChecker has checkFilePath (normalize then whitelist), checkShellCommand (first token), checkHttpUrl (host wildcard match); any failure throws SandboxViolationException terminating the Tool.
- Key claims: Sandbox + whitelist is the only Tool-governance mechanism in core; Profile-level Tool Policy (allow/deny per Agent) is extension-stage — though the Profile tools field already limits the usable subset as a governance prototype; extension adds subprocess + bwrap or Docker for full isolation.
- Learner-relevant: Anchor: the concrete whitelist mechanics and the governance-progress note used in the risk register.

### Capability five: Web Service
- Locator: `[[sources/geek-ai-agent/18 18. 项目篇 OryxOS：技术方案文档.html#web-service]]`
- Summary: WebServer starts Spring MVC on port 8080 (`oryxos serve`) with virtual threads; six ApiControllers (Session/Agent/Profile/Memory/Tool/System) that only do validation/wrapping/error handling while delegating to core services; GlobalExceptionHandler returns standard JSON errors (errorCode/message/timestamp); springdoc-openapi exposes OpenAPI 3.0 at /swagger-ui.
- Key claims: The 10 core endpoints: 4 session (POST /sessions, POST /sessions/{id}/messages, GET /sessions/{id}, DELETE /sessions/{id}), 1 Agent invoke (POST /agents/{name}/invoke), 3 info (GET /profiles, /memory, /tools), 2 system (GET /health, /info); design details — HTTP status + internal error codes (400/404/500/503), CORS open in core, 32KB max message, history capped at last 100, 60s invoke timeout → 504; skipped in core: auth, SSE, WebSocket, RBAC, rate limiting; extension adds Profile CRUD/reload, Memory append/clear/search, Tool describe/history, LLM call history/token stats, webhook, SSE, Prometheus metrics, OpenAPI spec.
- Learner-relevant: Anchor: the endpoint list and error/timeout design reused verbatim in US-5 tasks and acceptance demos.

### Support modules
- Locator: `[[sources/geek-ai-agent/18 18. 项目篇 OryxOS：技术方案文档.html#support-modules]]`
- Summary: InitCommand creates `.oryxos/` structure (profiles/, memory/MEMORY.md, skills/, mcp_servers.yaml, sessions/, logs/, AGENTS.md/SOUL.md/USER.md, oryxos.db); ProfileLoader parses/validates Profiles into ProfileRegistry (in-memory index, invalid Profiles logged without blocking startup); ContextLoader unifies Bootstrap + SKILL.md loading into system-prompt context (re-read each assembly, no cache); CliChannel implements `oryxos chat` reading stdin/writing stdout, maintaining the current Session; three run modes share Profile config and Session storage; OryxOsCli (Picocli, the main function) registers 12 subcommands — commands not needing Spring (init, profile list) run file operations fast, LLM-needing commands (chat, serve, gateway) start the Spring context; ConfigLoader loads sensitive config from env vars or local config, Profile YAML uses `${ENV_VAR}` placeholders, with validation and clear errors.
- Key claims: ProfileRegistry enables multiple Agents coexisting on one instance — the minimal "OS" manifestation in core; SKILL.md is prompt input, so it belongs to ContextLoader (core), not the Tool module.
- Learner-relevant: Anchor: the module responsibilities that map to oryxos-cli, oryxos-channel-cli, oryxos-core and the 12-command list.

### Persistence
- Locator: `[[sources/geek-ai-agent/18 18. 项目篇 OryxOS：技术方案文档.html#persistence]]`
- Summary: Core chooses SQLite + Spring Data JPA + MEMORY.md + keyword recall; explains why no vector DB in core: LanceDB Java local-embedded support is still in development (Java SDK only supports remote Cloud/Enterprise — conflicts with single-binary positioning), Qdrant/Chroma/Milvus need external processes, pgvector needs external PostgreSQL, JVector is a pure-Java embedded option but maturity unproven; extension upgrade paths: A) LanceDB Java embedded GA (keeps single binary), B) PostgreSQL pgvector (most mature), C) JVector pure-Java dual-write.
- Key claims: Three core tables — sessions (metadata + JSON dialogue history), tool_invocations (per-Tool-call records), llm_calls (per-LLM-call records); audit tables are written in core stage (not just logs) because "可审计" is a differentiation selling point — query interfaces/reports in extension; engineering warning: SQLite ALTER TABLE is limited, hibernate.ddl-auto=update is weak for schema evolution — maintain manual migration scripts or introduce Flyway/Liquibase; filesystem data (.oryxos/: Profile YAML, Bootstrap, MEMORY.md, SKILL.md, MCP config, logs) stays on filesystem for user editability/git-tracking/backup.
- Learner-relevant: Anchor: the storage trade-off reasoning and the SQLite-migration warning that the AI-coding guide's risk section touches.

### Project structure
- Locator: `[[sources/geek-ai-agent/18 18. 项目篇 OryxOS：技术方案文档.html#project-structure]]`
- Summary: Maven multi-module with 9 modules: oryxos-core (engine + abstractions: ReActLoop, PromptBuilder, ToolExecutor, ContextLoader, Session, Profile, OryxTool — all modules depend on it), oryxos-provider (capability 1: ProviderService, Function Calling adapter, provider-name mapping), oryxos-memory (capability 3: MemoryService facade, LongTermMemory, MemoryTools), oryxos-tool (capability 4: built-in Tools, MCP Client, ToolRegistry, SandboxChecker), oryxos-web (capability 5: WebServer, six controllers, GlobalExceptionHandler, OpenAPI), oryxos-channel-cli (CLI Channel), oryxos-storage (SQLite layer: three tables), oryxos-cli (Picocli 12 subcommands), oryxos-boot (Spring Boot launcher, fat JAR).
- Key claims: Modules decouple via interfaces — adding a Channel/Tool later means a new module without touching core; all Channel modules call oryxos-web's Agent API; `mvn clean package` produces a fat JAR, `java -jar` to run, GraalVM Native Image in extension.
- Learner-relevant: Anchor: the authoritative 9-module layout that both the plan review and the AI-coding user stories check against.

### Key flows (demos)

### Performance and scalability
- Locator: `[[sources/geek-ai-agent/18 18. 项目篇 OryxOS：技术方案文档.html#performance]]`
- Summary: How the NFR targets are met: virtual threads (each Agent is a small Profile object + Session list; tens of OS threads suffice for thousands of concurrent requests; IO-blocking LLM calls yield OS threads); ~1000 concurrent Sessions at ~50KB each ≈ 50MB is fine; SQLite writes on every append in core (optimize to batch if paged); MEMORY.md read once per prompt assembly at 1–2ms (cache + file-watch in extension); startup 2–4s on JDK 21 (fine for resident services, too slow for CLI — fast-path commands skip Spring context; GraalVM Native Image <100ms in extension).
- Key claims: The numbers directly back the performance acceptance targets (200ms P99 session creation, 50ms internal overhead).
- Learner-relevant: Anchor: the reasoning that ties the stack choices to measurable performance.
