# Digest — 17 17. 项目篇 OryxOS：需求文档

## Overview (L1)
- 项目概述 — Defines OryxOS as a Java-based, enterprise-facing Agent OS installed on the enterprise's own K8s/servers; separates agent runtime from Agent OS (OS adds lifecycle, unified access, memory, multi-tenancy, audit); delivery is two-stage — core runtime kernel first, governance layer via extension/community.
- 1.2 OryxOS 能干什么 — Enumerates the five core capabilities (对接 LLM、ReAct 循环、Memory 三层记忆、Plugin Tool、Web Service) plus Channel, with example use cases for each and six combined business scenarios.
- 术语和概念 — Fixes the shared terminology aligned with open-source Agent OS de-facto standards: Agent, Profile, Provider, ReAct 循环, Tool, Memory, Channel, Web Service, Session, Sandbox, Tool Policy, Skill, Bootstrap (AGENTS.md/SOUL.md/USER.md), Workspace (.oryxos/).
- 设计目标 — The four-word design goals: 统一、私有、易接入、可观测.
- 典型场景 — Three end-state scenarios (运维助手, 知识管理助手, 销售助手) showing full-form OryxOS usage across IM channels, MCP, Memory, and Skill runbooks.
- 核心功能 — The 4-week (12-hour) shortest-path core scope: workspace init, Profile config, Provider abstraction, ReAct loop, two-tier Memory, Tool system (built-in + 3-tier Plugin), CLI Channel, Web Service (10 endpoints), Session management, three run modes, 12 CLI commands, config/key loading, project homepage.
- 扩展功能 — The governance layer to be filled later: multi-Channel, Provider Fallback/Adaptive Routing, Memory auto-extraction/semantic recall/episodic/Memory Wiki/Skill 体系, MCP Server exposure, Tool Policy, Tool LRU, full Sandbox, Web dashboard, SSO+multi-tenancy, audit, observability, clustering, enterprise IT connectors.
- 社区共建功能 — Community-driven long-term features: remaining docs, Skills Marketplace, multi-language SDK, visual Profile editor, native file generation, multi-region deployment, Kubernetes Operator, mobile console, Voice Channel, RISC-V/edge deployment.
- 非功能需求 — Performance (≥10 Agents, ≥100 concurrent Sessions/node, P99 <200ms session creation, <50ms internal overhead), reliability, operability, compatibility (JDK 21+, specific Linux distros, OpenAI-compatible protocol), security (HTTPS, encrypted storage, whitelist isolation), compliance (data residency, audit/SIEM/SOC2/GDPR/HIPAA/等保三级 in extension).
- 关键流程 — Step-by-step core flows: workspace init, Profile creation & Agent startup, message handling, Tool invocation, Session context management.
- 数据模型 — Field specs for Profile (YAML), Session (SQLite), Memory (MEMORY.md file, schema-less), Tool Invocation, and LLM Call entities.
- 里程碑规划 — 4-week plan (week 1 LLM+ReAct, week 2 Memory+Tool, week 3 Web Service, week 4 multi-Agent + engineering wrap-up) each with demonstrable outcomes.
- 风险与未决事项 — Risks (scope, Spring AI compatibility, Tool execution safety, Java startup/memory, community continuity, positioning misread, OpenClaw/Hermes relations) and open decisions (Provider abstraction layer, SQLite vs H2, Bootstrap loading order, GraalVM timing).
- 验收标准 — Four acceptance tiers: functional (every core module with E2E tests), performance (10 Agents 4h stable, 100 concurrent Sessions, P99 <200ms), operability (deploy docs, 30-min setup), scenario (five demo Agents as a hard release condition).

### Core function: workspace init
- Locator: `[[sources/geek-ai-agent/17 17. 项目篇 OryxOS：需求文档.html#workspace-init]]`
- Summary: `oryxos init` creates `.oryxos/` with five subdirectories (profiles/, sessions/, skills/, logs/, tools/) and three bootstrap files (AGENTS.md, SOUL.md, USER.md) plus a default Profile (profiles/default.yaml) that is immediately usable.
- Key claims: Bootstrap files auto-load into the system prompt so the Agent knows project background, identity, and user preferences; a default Profile with one Provider, a few base Tools, and CLI Channel makes first use instant.
- Learner-relevant: Anchor: the first-run experience and directory layout referenced by the tech plan's InitCommand.

### Core function: Profile config
- Locator: `[[sources/geek-ai-agent/17 17. 项目篇 OryxOS：需求文档.html#profile-config]]`
- Summary: Profile is the complete Agent config as a YAML file with five field groups: identity (name/description/persona prompt or SOUL.md ref), provider (name/model/params, optional fallback), tools (Tool list with optional args), channels, bootstrap (files loaded into system prompt); managed via `oryxos profile create/list/show` and YAML edits.
- Key claims: Profile edits take effect on next Agent start without restarting OryxOS; core stage manages Profiles on the filesystem (no Web console UI); multiple Profiles/Agents coexist on one instance — the minimal "OS" manifestation in the core stage.
- Learner-relevant: Anchor: the Profile concept that every module (Provider, Tool filtering, Channel, bootstrap) hangs off.

### Core function: Provider abstraction
- Locator: `[[sources/geek-ai-agent/17 17. 项目篇 OryxOS：需求文档.html#provider-abstraction]]`
- Summary: All LLM calls go through a Provider interface built directly on Spring AI Alibaba's ChatClient, wrapping mainstream connectors (DeepSeek、通义、文心、Kimi、智谱、混元、豆包、Anthropic、OpenAI); each Provider instance has name/model/API key/optional base URL, referenced by Profile.
- Key claims: Core stage does no fallback or hedge racing — Provider failure errors directly to the Agent; token usage per call is logged for basic cost transparency (aggregation and Web dashboard in extension).
- Learner-relevant: Anchor: the Provider layer's scope boundary (no reliability features yet) used to calibrate expectations.

### Core function: ReAct loop
- Locator: `[[sources/geek-ai-agent/17 17. 项目篇 OryxOS：需求文档.html#react-loop]]`
- Summary: ReAct (Reason+Act) is the Agent's core mechanism and OryxOS's most critical code: append message to Session history → assemble prompt → call LLM → if no Tool call, return; else execute Tool, append result as tool message, loop until final answer or max iterations.
- Key claims: Core loop is ~tens of lines of Java, self-implemented (not Spring AI's Agent abstraction) so implementers fully understand the mechanism; max iterations default 10, overridable per Profile; every LLM and Tool call logs structured logs; Tool retry with limited retries in ToolResult; core stage skips parallel Tool calls, dynamic context compression, and sub-Agent delegation.
- Learner-relevant: Anchor: the exact algorithm and default (10) that the tech plan and AI-coding tasks implement.

### Core function: three-tier Memory
- Locator: `[[sources/geek-ai-agent/17 17. 项目篇 OryxOS：需求文档.html#memory]]`
- Summary: Agent retains state across dialogues; core stage does a minimal two tiers: session memory (via Session management, persisted to local SQLite, restorable after restart, truncates early turns beyond context window) and long-term memory (single `.oryxos/memory/MEMORY.md` file, kept across all dialogues, read/written via two built-in Tools save_memory/recall_memory, whole file injected into system prompt at start, truncated past ~4000 chars).
- Key claims: Core stage does not do auto fact-extraction (LLM decides when to call save_memory), semantic retrieval (keyword match only), episodic memory, Memory Wiki/claim-evidence, contradiction detection, or freshness management; the user-visible payoff is the Agent naturally remembering preferences — what distinguishes an Agent OS from a chatbot.
- Learner-relevant: Anchor: the deliberate minimalism of the memory design and its extension upgrade path.

### Core function: Tool system
- Locator: `[[sources/geek-ai-agent/17 17. 项目篇 OryxOS：需求文档.html#tool-system]]`
- Summary: Tools are external capabilities invoked via LLM Function Calling; two types: built-in (FileTools read_file/write_file/list_dir with path whitelist, Shell with timeout+command whitelist, HTTP with domain whitelist, plus save_memory/recall_memory — five built-ins total) and Plugin Tools in three levels by difficulty.
- Key claims: Plugin level one (zero-code) is the recommended way: write a SKILL.md describing intent + reuse community MCP servers, LLM composes them (e.g. daily PR-digest pushed to Slack, zero lines of code); level two (light-code) is writing your own MCP server (JSON-RPC, moderate effort, for company-internal systems); level three (heavy-code) is @Tool-annotated Java Spring Beans (deepest integration, best performance); selection rule: use level one unless you must use two, use two unless three; core stage ships a minimal MCP Client wired via `.oryxos/mcp_servers.yaml`.
- Key claims (sandbox): Core-stage sandbox is application-layer whitelist validation (path/command/domain) with timeout and resource limits — NOT Java SecurityManager (deprecated since JDK 17, unusable in JDK 21, conflicts with the JDK 21+ requirement); full bwrap/Docker/K8s-pod container sandbox goes to extension.
- Learner-relevant: Anchor: the three-level Plugin model and the sandbox decision (JDK 21 constraint) that the tech plan turns into OryxTool + SandboxChecker.

### Core function: Channel access
- Locator: `[[sources/geek-ai-agent/17 17. 项目篇 OryxOS：需求文档.html#channel]]`
- Summary: Channel handles "消息进来、响应出去"; core stage ships only the CLI Channel (`oryxos chat`, multi-turn, view context and Tool-call records); HTTP access belongs to Web Service, not Channel.
- Key claims: IM Channels (企业微信/飞书/钉钉/Slack) are extension features — their complexity (webhook, cards, media, org structure, OAuth, enterprise qualification) is out of the 12-hour scope; extension IM Channels call Web Service underneath rather than reimplementing Agent logic.
- Learner-relevant: Anchor: the Channel/Web Service boundary and why CLI is the core-stage interaction surface.

### Core function: Web Service
- Locator: `[[sources/geek-ai-agent/17 17. 项目篇 OryxOS：需求文档.html#web-service]]`
- Summary: Web Service is OryxOS's complete outward-facing REST API and the key differentiator from personal-assistant projects; six API operation categories (session mgmt, Agent invoke, Profile mgmt, Memory ops, Tool info, system status); core stage implements the 10 most critical endpoints (4 session, 1 agent invoke, 3 profile/memory/tool info, 2 health/info), with 15 more in extension.
- Key claims: Core stage omits auth (assumes intranet; extension adds API Key+JWT), SSE streaming (sync blocking now), WebSocket, RBAC, rate limiting; integration scenarios are sync invoke, session persistence, webhook trigger, and cross-language HTTP calls.
- Learner-relevant: Anchor: the endpoint table (POST /api/v1/sessions, POST /sessions/{id}/messages, GET /sessions/{id}, DELETE, POST /agents/{name}/invoke, GET /profiles, /memory, /tools, /health, /info) reused verbatim in tech plan and demos.

### Core function: Session management
- Locator: `[[sources/geek-ai-agent/17 17. 项目篇 OryxOS：需求文档.html#session]]`
- Summary: Session is a dialogue context container (start/end time, user identity, Agent ID, dialogue history, current context, temp variables), identified by the channel+user+Agent combination; core stage persists to local SQLite under `.oryxos/sessions/`, restorable after restart.
- Key claims: Cross-session long-term memory, context compression, and Memory Wiki are extension features; over-context sessions are simply truncated keeping recent turns; public Session APIs are create/append-message/get-history/end.
- Learner-relevant: Anchor: the Session entity and its SQLite persistence reused in the data model and tech plan.

- Summary: Four acceptance tiers: functional (all core modules with at least one E2E test — init, multi-Profile, Provider for DeepSeek+Kimi, ReAct multi-turn Tool calls with correct termination at max iterations, save_memory/recall_memory, built-in Tools, Plugin level-one SKILL.md+MCP and level-three @Tool, MCP Client, CLI Channel, 10 Web Service endpoints, SQLite Session restore, 12 commands, config/key loading); performance (10 Agents stable 4h, 100 concurrent Sessions, P99 <200ms, <50ms overhead — targets not blocking release but optimized in extension); operability (deploy doc for 30-minute single-node setup, clear CLI help/errors, homepage); scenario (five demo Agents as the hard condition for release).
- Key claims: Demo list — ① 对接 LLM+ReAct "查天气并写日报", ② Memory preference across dialogues, ③ Plugin Tool+MCP cross-tool task, ④ Web Service sync call lifecycle, ⑤ Web Service multi-endpoint flow (info→profiles→tools→invoke→memory).
