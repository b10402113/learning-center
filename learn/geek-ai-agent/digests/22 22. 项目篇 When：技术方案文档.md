# Digest — 22 22. 项目篇 When：技术方案文档

## Overview (L1)
- 1. 概述 — 3 周 MVP 是生产可用的分布式延时投递组件（集群、多副本、自动故障切换、扩缩容），回答 How；核心决策是整套架构的地基。
- 2. 核心技术决策 — 七个 why：ETCD（非 ZK/Consul）、Redis（非 RocksDB/MySQL）、多层时间轮（非 DelayQueue/Quartz/ZSet）、Master/Slave（非 Raft/Paxos）、外部 HTTP 内部 gRPC、Java、3 周内做集群高可用。
- 3. 整体架构 — 四部分（业务方/When 集群/外部依赖/下游 Sink）；无差别多节点同构架构、Controller 是角色不是专用节点；节点内八模块；生产三节点起步。
- 4. 集群组建与协调 — 基于 ETCD：节点注册（Lease 10s）、心跳保活（独立线程 3s 续约）、Controller 选举（原子 PUT）、节点上下线感知（Watch 事件驱动）、key 空间设计。
- 5. 多层时间轮设计 — 单层环形数组 O(1) 原理、四层结构（秒/分/时/天）覆盖 30 天、集群中多个时间轮分布、调度循环关键设计。
- 6. Master/Slave 副本机制 — 热备概念、异步同步、Lease 故障检测、10 秒内切换流程、不丢消息（Redis 是唯一真理之源）与不重复投递（至少一次语义）的关键设计。
- 7. 节点扩缩容与负载均衡 — 节点加入/退出流程（优先迁移 Slave）、时间轮 rebalance 算法。
- 8. 延时消息生命周期 — 写入/调度投递/取消/查询/节点重启恢复五条完整流程。
- 9. 持久化层设计 — Redis key 结构、读写策略（Pipeline）、大 Key 规避保证、Redis 高可用边界。
- 10. API 设计 — POST/GET/DELETE /api/v1/messages 三个核心 API 的完整请求响应与校验规则、通用约定。
- 11. Sink 插件层设计 — Sink 接口契约、SPI 加载机制、HTTP Sink、Kafka Sink、统一重试策略。
- 12. Web 管理台设计 — Vue 3 + Element Plus、管理台 API、任务列表页、投递日志页。
- 13. 可观测设计 — Prometheus 指标（Micrometer）、JSON 结构化日志（trace_id 跨节点）、liveness/readiness 健康检查。
- 14. 部署架构 — 本地 docker-compose（三节点+ETCD+Redis+Kafka）、单机生产、Kubernetes yaml、环境变量配置管理。
- 15. 风险与未决事项 — 已识别风险技术应对与未决事项（Snowflake 节点 ID、时间轮参数、副本数等）。
- 16. 后续演进 — 更多 Sink、鉴权限流、死信队列、优先级队列、跨地域部署、Kubernetes Operator、MCP Server 的技术思路。
- 17. 总结 — 六大核心决策与技术路线收束。

### core-tech-decisions
- Locator: `[[sources/geek-ai-agent/22 22. 项目篇 When：技术方案文档.html#2. 核心技术决策]]`
- Summary: 给出七个关键技术决策及其理由。
- Key claims: ETCD 优于 ZooKeeper（API 底层复杂）与 Consul（偏服务发现），API 简洁（Put/Get/Watch/Lease），K8s 生态成熟；Redis 优于 RocksDB（需部署服务、生态不熟）与 MySQL（随机读写弱、不适合短生命周期），普及度高、接入门槛最低，存储设计规避大 Key；多层时间轮 O(1)、内存调度，QMQ 是最佳参考，优于 Java DelayQueue（O(log n)）、Quartz（cron 场景、重度依赖 DB）、Redis ZSet（大 Key）；Master/Slave 优于 Raft/Paxos（强一致太重、增加投递延迟），Redis 兜底可快速 recover；外部 HTTP（最低接入门槛、curl 即测）内部 gRPC（性能+强类型）；Java（中间件生态最成熟，Kafka/RocketMQ/Pulsar 皆 Java/JVM，兼顾运维与人才市场）；3 周内做集群高可用四理由：样本说服力、ETCD 封装复杂度、业界方案成熟、AI 编程让快速实施可行。
- Learner-relevant: When 架构地基与选型论证，是学员理解整体设计的关键。

### cluster-coordination
- Locator: `[[sources/geek-ai-agent/22 22. 项目篇 When：技术方案文档.html#4. 集群组建与协调]]`
- Summary: 详述基于 ETCD 的节点注册、心跳保活、Controller 选举、上下线感知与 key 空间设计。
- Key claims: 注册 key /when/nodes/{node_id} 绑 Lease（TTL 10s），Lease 过期自动删除提供"节点故障自动下线"语义；心跳用独立线程独立 ETCD 连接、3s 续约（不能依赖业务线程，避免 GC/网络抖动影响）；Controller 选举用 ETCD Txn 原子 PUT（IF NOT EXISTS /when/controller THEN PUT）保证唯一；Controller 起来后加载集群状态并检查时间轮重分配；Watch /when/nodes/ 前缀：PUT 事件触发 rebalance 分配 Slave，DELETE 事件提升 Slave 为 Master 并补新 Slave；声明式事件驱动，不用主动 ping；key 空间：nodes（带 Lease）、controller（带 Lease）、timewheels（持久化）、config（持久化，cluster_size/replica_count=2/timewheel_count=节点数×2-4）。
- Learner-relevant: 分布式协调机制的核心实现细节，支撑故障切换与扩缩容。

### timewheel-design
- Locator: `[[sources/geek-ai-agent/22 22. 项目篇 When：技术方案文档.html#5. 多层时间轮设计]]`
- Summary: 从单层原理到四层时间轮结构、集群分布与调度循环。
- Key claims: 单层环形数组、指针随秒推进、插入触发 O(1)，但 60 槽只表示 60 秒（86400 槽表示一天内存浪费）；默认四层：60 槽×1s、60 槽×1min、24 槽×1h、30 槽×1d，覆盖 30 天，单实例内存几百 MB；消息逐层"降级"到第一层精确触发；集群多个时间轮（每节点默认 2-4 个）提升并发、故障隔离、负载均衡；一致性 hash 按消息 ID 定时间轮（查询/取消能准确路由），元数据存 /when/timewheels/tw-N（master/slave/status）；调度循环只做读和触发（Redis 删除异步批量、Sink 异步投递线程池）、用 sleep_until_next_slot() 补偿漂移、槽内消息顺序不保证。
- Learner-relevant: When 核心调度算法的完整设计，直接对应 TW-001 等任务拆解。

### master-slave-replication
- Locator: `[[sources/geek-ai-agent/22 22. 项目篇 When：技术方案文档.html#6. Master/Slave 副本机制]]`
- Summary: 副本同步、故障检测、故障切换流程与不丢/不重语义。
- Key claims: 每个时间轮 Master+Slave 两个副本且必须不同节点（Rebalance 硬约束）；同步异步（gRPC，几毫秒），同步失败标记 out-of-sync 并让 Controller 触发 Slave 从 Redis 全量重建；故障检测靠 ETCD Lease（独立续约线程，无心跳误判）；切换流程：Lease 过期 → Watch DELETE → 检查 Master 时间轮 → 提升 Slave → 新 Master 从 Redis 恢复 → 分配新 Slave，10 秒内完成；不丢消息两层保证：Redis 持久化先于返回业务方 + 新 Master 从 Redis 恢复，Redis 是唯一真理之源（内存/副本只是加速层）；不重复投递：投递成功与 Redis 删除之间有窗口导致重复，这是"至少一次"语义来源，跨系统精确一次需分布式事务太重，至少一次+业务方幂等是事实标准（Kafka/RocketMQ/Pulsar 同此）。
- Learner-relevant: 高可用与投递语义的核心机制，支撑 RP-002 等副本任务。

### scaling-and-rebalance
- Locator: `[[sources/geek-ai-agent/22 22. 项目篇 When：技术方案文档.html#7. 节点扩缩容与负载均衡]]`
- Summary: 节点加入/退出流程与时间轮 rebalance 算法。
- Key claims: 加入：启动→注册 ETCD 绑 Lease→Controller Watch PUT→rebalance→迁移 Slave 副本→新节点拉全量数据→承担 Slave 角色；优先迁移 Slave 非 Master（Master 迁移影响写入路径）；主动退出（SIGTERM）先注销 ETCD，Slave 提升 1 秒内完成，写入无中断；异常退出靠 Lease 过期，延迟变几秒；rebalance 规则：每时间轮唯一 Master+唯一 Slave、主从必须异节点、每节点时间轮总数尽量均匀；算法找过载/过空节点、从过载迁移 Slave 到过空，target_per_node ±1 不追求绝对平均、渐进迁移避免震荡；Controller 每次集群变化触发一次、日常每 5 分钟检查一次。
- Learner-relevant: 集群弹性与负载均衡的工程实现。

### message-lifecycle
- Locator: `[[sources/geek-ai-agent/22 22. 项目篇 When：技术方案文档.html#8. 延时消息生命周期]]`
- Summary: 走完写入、调度投递、取消、查询、节点重启恢复五条流程。
- Key claims: 写入：POST→校验→Snowflake 生成 ID→一致性 hash 定时间轮→（跨节点 gRPC 转发）→Redis 持久化（消息体+时间索引）→内存时间轮插入→异步 Slave 同步→返回 ID；Redis 持久化必须先于返回（业务方拿到 ID 即已落库）；调度投递：指针推进触发→上层降级/第一层入投递流程→Sink 投递器线程池调插件→成功删 Redis 并同步删 Slave，失败进重试重回时间轮；投递异步化保证调度循环不被慢 Sink 拖住；取消 O(1)（在时间轮内删+Redis 删），已投递则返回 409；查询五状态 pending/delivering/delivered/failed/cancelled，MVP 统一走 Master 路由；重启恢复：先查 ETCD 确定角色→从 Redis 全量重建→注册（先加载后注册避免未就绪窗口），Controller 通常不切回。
- Learner-relevant: 端到端数据流的完整叙述，是集成测试场景来源。

### persistence-layer
- Locator: `[[sources/geek-ai-agent/22 22. 项目篇 When：技术方案文档.html#9. 持久化层设计]]`
- Summary: Redis key 结构、读写策略与大 Key 规避保证。
- Key claims: key 空间：/when/messages/{message_id}（STRING，TTL deliver_at+7 天）、/when/timewheels/{tw_id}/index/{message_id}（STRING 到期时间戳，同 TTL）、/when/timewheels/{tw_id}/messages_in_slot/{slot_key}（SET，仅重启恢复用）；消息体按 ID 拆 key、索引按时间轮维度拆分，从根本上规避大 Key；写入：先 Redis（两个 SET 用 Pipeline）成功后再入内存，失败直接返回失败不写内存，保证"内存里的一定也在 Redis 里"；调度读内存、删除用 Pipeline 批量降 QPS；查询优先内存缓存再 Redis；代价是几十万到几百万小 key，Redis 承受力极强；MVP 用单实例/主从，生产高可用由部署方保证，Redis 短暂不可用时 When 暂停接收新消息可降级运行。
- Learner-relevant: 存储层实现细节与大 Key 规避论证，对应 Redis 客户端模块任务。

### api-design

### sink-plugin-layer
- Locator: `[[sources/geek-ai-agent/22 22. 项目篇 When：技术方案文档.html#11. Sink 插件层设计]]`
- Summary: Sink 接口契约、SPI 加载机制、HTTP/Kafka 两种内置实现与重试策略。
- Key claims: Sink 接口：type() 唯一标识、validateConfig()（接入层校验）、deliver() 返回 DeliveryResult（success/retryable/errorMessage/durationMs）、默认 healthCheck()；SPI：META-INF/services 声明 + ServiceLoader 加载注册到 Map；新增 Sink 流程：实现接口→注册→打包放插件目录→重启；HTTP Sink：OkHttp/HttpClient，body 为 payload 原始字节，默认超时 5s，2xx 成功、5xx 可重试、4xx 不可重试、网络异常可重试；Kafka Sink：官方 Java Producer，bootstrap_servers 为 cache key 复用 Producer，acks=1、retries=3、超时 5s、callback 异步；统一重试策略：最大 5 次、指数退避初始 30s 翻倍封顶 30 分钟（30s/1min/2min/4min/8min）、超次数状态变 failed 留 Redis。
- Learner-relevant: 扩展点设计（核心能力），是 Sink 相关任务与社区贡献的入口。

### observability
- Locator: `[[sources/geek-ai-agent/22 22. 项目篇 When：技术方案文档.html#13. 可观测设计]]`
- Summary: Prometheus 指标、结构化日志与健康检查的实现。
- Key claims: /metrics 指标分组：流量（API 请求/提交/投递计数）、存量（各状态消息数、每时间轮消息数）、质量（API/投递耗时分布、delivery_lag、sink 失败率）、集群（节点数、Controller 选举、master_failover 等）、资源（Redis/ETCD 操作计数）；原则：关键路径必有指标、label 不用高基数（如 message_id）、覆盖故障场景；用 Micrometer 实现；日志 JSON 格式含 timestamp/level/logger/trace_id/node_id/message_id/tw_id 等，接入层生成 trace_id 经 SLF4J MDC 传递、跨节点放 gRPC metadata，运行时日志级别可调；健康检查 GET /health（liveness）+ GET /ready（readiness：ETCD/Redis 连接、至少一个时间轮已加载，可选 Kafka Producer，不满足返回 503 被 K8s 摘流量）。
- Learner-relevant: 监控运维接入的具体契约，对应可观测模块任务。

### risks-and-evolution

- Key claims: 大 Key 靠 key 拆分+不用 ZSet；内存膨胀靠多级时间轮+延迟加载（30 天跨度单轮几百 MB）；Slave 同步落后靠 Redis 兜底；集中到期靠投递线程池限流（默认 200 并发）+错峰（同一秒打散到几百毫秒）；ETCD 分区由 ETCD Raft 保证（3 节点容忍 1 故障）；gRPC 跨节点延迟后续可缓存路由表；Snowflake 时钟回拨靠 NTP+节点 ID；未决：Snowflake 节点 ID（环境变量 WHEN_NODE_ID 数字部分）、时间轮参数（60/60/24/30 槽默认，测试后微调）、副本数默认 2、每节点时间轮默认 4（3 节点 12 时间轮 24 副本）；演进：更多 Sink（gRPC 优先）、鉴权限流（AuthFilter+token、滑动窗口/令牌桶）、死信队列（failed→dead_letter，留 7 天，可人工重投）、优先级队列（槽内链表按优先级分桶）、跨地域（时间轮按地域分配+ETCD/Redis 跨地域+region 标签路由）、Kubernetes Operator（CRD WhenCluster/WhenNode/WhenSink，Operator SDK/Kubebuilder）、MCP Server（JSON-RPC over stdio/SSE，包装 submit_delay_message/query_message/cancel_message）。
