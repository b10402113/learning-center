### 一-五周走过的路

- Locator: `[[sources/geek-ai-agent/20260922/第32节：第一阶段总结、后续规划与社区推进.pdf#一-五周走过的路]]`
- Summary: Five weeks and 32 lessons from cognition to a tagged Agent OS: week one (1–7) cognition and judgment; week two (8–14) tools/methodology/workflow, understanding Agent OS, reviews/preparation/Spec-Kit; week three (15–20) base capabilities — foundation, Provider, ReAct, CLI, Notify, Tool; week four (21–26) core support — Memory, Sandbox, scheduler, Web Service; week five (27–32) connect and release — integration, plugin Agent, two demos, v0.1.0. - Key claims: The first two weeks build judgment, the last three turn judgment into a system running two real Agents; the code is a product of that judgment — what's really delivered is a transferable workflow.

### 二-最重要的一张图-底座与-Agent-的分界

- Locator: `[[sources/geek-ai-agent/20260922/第32节：第一阶段总结、后续规划与社区推进.pdf#二-最重要的一张图-底座与-Agent-的分界]]`
- Summary: If only one architectural insight is taken from phase one, it's this boundary. The overall architecture layers: LLM Providers (DeepSeek/Qwen/Kimi, OpenAI/Anthropic, Ollama, Spring AI Alibaba) and MCP servers; Channel/Trigger layer (CLI, REST API, Scheduler — human-push and clock-push); Agent layer (one business Agent = one directory, AGENT.md = frontmatter who/when/how + body what-to-do, optional skills/ and scripts/, zero code); Engine layer (oryxos-core: ReActLoop reason+act max 10 iterations, PromptBuilder system+memory+history+tools, ToolExecutor sandbox check + audit write); Capability layer (Provider routing, Memory session+long-term/core-archive, Tool built-in+MCP, Notify outbound push + Sandbox NotifyTools); Storage layer (SQLite `oryxos.db`: sessions/tool_invocations/llm_calls; Filesystem `.oryxos/`: profiles/MEMORY.md/skills); external deps (Notify targets, business systems, gateway, protocol). Everything lessons 1–28 built is base, not Agent — like an OS offering process scheduling and syscalls while itself being no particular program.
- Key claims: The real business Agent appears only in lesson 29 (one directory = one Agent inserted onto the base); the two demo Agents total under a hundred lines of text and zero Java — this disproportion is the direct measure of base value: the better the base, the cheaper defining an Agent.
- Learner-relevant: The single most important architecture diagram and the base-vs-Agent mental model.

### 三-四条反复出现的设计母题

- Locator: `[[sources/geek-ai-agent/20260922/第32节：第一阶段总结、后续规划与社区推进.pdf#三-四条反复出现的设计母题]]`
- Summary: Thirty-two lessons reduce to four design motifs that are portable to any project. (1) Interface-first, implementation staged — define an interface expressing intent with no implementation detail, fill only the lightest stage in core phase: Notify's `NotifyChannelAdapter` (19), Memory's `MemoryService` (21/22), Sandbox's `Sandbox.enforce` (23/24); the test is to mentally fit the heaviest future implementation (WeCom SDK, vector retrieval, microVM) into the interface — if it fits, the wall holds. (2) Signal-driven upgrades, not gut feel — when to use vector retrieval, container isolation, or automatic memory extraction is never "everyone's doing it" but a set of written real signals (retrieval starts missing, need to run untrusted code, manual memory visibly drops things); when no signal appears, hold the line. (3) Phase-wise restraint — every lesson has a "don't do these yet" section (fallback, SSE, distributed locks, Tool Policy, auto-extraction); not unimportant, just not this phase; the goal is a minimal complete runtime kernel, not a big-all. (4) Same entry, reuse not rewrite — human-push and clock-push share one `AgentService`; API-created and file-created Agents share one validation/registration; notify reuses Sandbox whitelist and ToolExecutor audit; whenever a "second path" appears, "two paths behaving differently" eventually appears — the lesson's hardest bugs all came from this.
- Key claims: These four motifs are reusable beyond OryxOS and are the transferable design pattern.
- Learner-relevant: The distilled design heuristics worth carrying to new projects.

### 四-你带走的工作流

- Locator: `[[sources/geek-ai-agent/20260922/第32节：第一阶段总结、后续规划与社区推进.pdf#四-你带走的工作流]]`
- Summary: More valuable than the code is a rhythm repeated a dozen times and practiced into the hands. The same four-step form for every module: principle (what/why) → think before building (boundaries, pitfalls, what not to do) → implement together with AI (execution to AI, Spec-Kit turns documents into tasks) → verify and explain the code (check against the list, only understanding counts). Docs-as-spec: lessons 16–31's documents are themselves Spec-Kit inputs — write clearly "what it should look like" and the implementation grows from it; this is SDD in a real project. Reconciliation method: a call should leave exactly these traces, reconcile table by table (27/28) — the demon-revealing mirror for integration problems and the daily use of audit capability. Front-loading pitfalls: JPA scanning, double tool calls, dependency versions, cache slip-ups — each pit named in the "think clearly" step; pits become the next project's checklist, which is the real payoff.
- Key claims: The workflow — not the code — is the transferable asset.
- Learner-relevant: The concrete four-step rhythm and method list to apply to future work.

### 五-后续规划-扩展阶段的路

- Locator: `[[sources/geek-ai-agent/20260922/第32节：第一阶段总结、后续规划与社区推进.pdf#五-后续规划-扩展阶段的路]]`
- Summary: Extension points reserved in the tech plan all now have clear mount positions; listed by module direction, mount point, and trigger signal: multi-Channel (WeCom/feishu/dingtalk/Slack) at the Channel Adapter plugin slot (8.4) when there's a real IM need; a dedicated Notify channel Adapter (new `NotifyChannelAdapter` implementation) when webhook can't do rich cards; Memory vector retrieval (swap implementation behind the `MemoryService` facade) when keyword retrieval misses or memory exceeds a thousand; Sandbox container → microVM (new `Sandbox` implementation) when running untrusted code / multi-tenant; Tool Policy, auth, SSO, multi-tenant at the reserved governance slot when leaving the intranet / multi-team sharing; audit query API and dashboards on top of the two audit tables on the day someone wants reports; SSE streaming, distributed deployment, GraalVM at their reserved slots when interaction/scale/startup-time becomes the bottleneck.
- Key claims: Every item is "add an implementation, don't change the interface" — the payout list of all phase-one "interface-first" investments.
- Learner-relevant: The extension roadmap expressed as signal-triggered, non-breaking additions.

### 六-社区推进-把它接到更长的路上

- Locator: `[[sources/geek-ai-agent/20260922/第32节：第一阶段总结、后续规划与社区推进.pdf#六-社区推进-把它接到更长的路上]]`
- Summary: OryxOS's long-term goal is written on day one: enter the Apache Foundation and become a top-level project. From v0.1.0 to that, near-term concrete steps: open it up (public repo, License and contribution guide, project homepage from lesson 5 with a quick-start and these docs); lower the first-contribution barrier (good first issues carved from the extension table — a new NotifyAdapter or a new built-in Tool are a few hundred lines with an existing interface, good first-PR material); let the Agent ecosystem run first (defining an Agent needs no Java, so contributors needn't know Java — sharing a useful Agent directory is a contribution, the widest community entry); teach the next batch with these docs (the course docs, tech plan, requirements docs three-piece set are onboarding material). For the learner: phase one practiced "steering" — building a real project from zero; the next level generalizes that ability (new domain, new stack) with the four-step rhythm, four motifs, and reconciliation method reused.
- Key claims: Cognition and judgment are what the course really wants to give; OryxOS is their first product, not the last.
- Learner-relevant: The open-source/community path and the personal growth direction.
