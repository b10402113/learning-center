# Digest — 第33节：分布式 - 集群化架构：原理 + 拆解

## Overview (L1)

- Motivation — A single machine hits two ceilings: capacity (RAM/CPU/disk) and single point of failure. Clustering (集群化) = horizontal scaling + removing single points, but it introduces six new problems: membership (成员感知), unique decision (唯一决策), data location (数据定位), failover (故障接管), replica consistency (副本一致), and common coordination (公共协调).
- Panorama — Requests hit any node, are routed to a sharded Master, and are forwarded over gRPC if non-local; ETCD is the coordination plane (heartbeat leases, Controller election, route metadata synced cluster-wide via Watch).
- Mechanism 1 · membership — Heartbeat + lease turns "is the node alive" into "has the lease expired"; detection latency floor = TTL, and renewal runs on an independent thread.
- Mechanism 2 · unique decision — Leader election via CAS guarantees uniqueness; consensus (Paxos/Raft) needs a majority quorum (N/2+1) to prevent split-brain; never build consensus yourself.
- Mechanism 3 · data location — Messages are sharded (by hash/range) and located through a "shard → replicas" metadata table kept by the Controller in ETCD, watched and cached locally; lookup, not hash-the-node, locates the Master.
- Mechanism 4 · failover — Detect (lease expiry) → decide (single Controller) → execute (switch role + backfill the data gap); backfilling the replication gap is the hardest, most error-prone step.
- Mechanism 5 · replica consistency — Sync vs async is CAP in engineering: sync does not lose but is slow and Slave jitter drags the Master; async is fast but may lose the tail on crash. With a reliable external source of truth (Redis), async's loss is only the in-memory view, so When picks async.
- Mechanism 6 · common coordination — One strongly consistent public store + change notification (ETCD/ZooKeeper/Consul/DB table) hosts "who is online, who decides, where is the data"; choose by timeliness, consistency, and ops cost.
- Map & closing — A problem↔mechanism table closes the loop; three general judgments: borrow don't build, externalize state, and choose by scenario.

### cluster-panorama
- Locator: `[[sources/geek-ai-agent/20260922/第33节：分布式 - 集群化架构：原理 + 拆解.pdf#cluster-panorama]]`

- Key claims: The six blocks expand in order — membership, election, shard routing, replica/failover, replication, coordination.
- Learner-relevant: The whole-system mental model before the details.

### membership
- Locator: `[[sources/geek-ai-agent/20260922/第33节：分布式 - 集群化架构：原理 + 拆解.pdf#membership]]`
- Summary: Explains heartbeat + lease: register and bind a lease (TTL 10s), keepalive every ~3s on an independent thread; failure to renew expires the lease and ETCD auto-deletes the registration key, which other nodes detect via Watch.
- Key claims: The essence is converting "node alive" into the deterministic question "lease expired"; detection latency floor = TTL, and smaller TTL means faster detection but heavier renewal pressure — a trade-off.
- Learner-relevant: The mechanism underlying failure discovery and its tuning trade-off.

### leader-election
- Locator: `[[sources/geek-ai-agent/20260922/第33节：分布式 - 集群化架构：原理 + 拆解.pdf#leader-election]]`
- Summary: Shows normal election (CAS grab of /leader, only one Put succeeds, others Watch standby) versus split-brain from a network partition (two leaders, conflicting decisions, corrupted data).
- Key claims: Consensus (Paxos/Raft) uses a majority quorum (N/2+1) so only the majority side can elect a leader — natural split-brain prevention; CAS = etcd Txn (compare createRevision==0 then Put) is the hard guarantee of uniqueness; consensus is extremely hard — never self-build.
- Learner-relevant: Why quorum and CAS matter, and the build-vs-borrow judgment.

### data-locator
- Locator: `[[sources/geek-ai-agent/20260922/第33节：分布式 - 集群化架构：原理 + 拆解.pdf#data-locator]]`
- Summary: A routing metadata table (maintained by the Controller, stored in ETCD) maps each shard to its Master and Slave nodes; sharding assigns a message to a shard (by message_id hash or range), and the table locates the node.
- Key claims: Locating a node is table lookup, not computing a hash; sharding by hash is only one assignment strategy; the Controller maintains the table, writes it to ETCD, and each node Watches + caches locally — migration and switchover are essentially edits to this table; consistent hashing minimizes migration when shards change.
- Learner-relevant: The route/locate primitive that request paths depend on.

### failover
- Locator: `[[sources/geek-ai-agent/20260922/第33节：分布式 - 集群化架构：原理 + 拆解.pdf#failover]]`
- Summary: Three stages — detect (lease expiry, ≤ TTL), decide (single Controller rules to prevent split-brain), execute (switch roles + backfill the data gap); a dead Master's Slave is promoted.
- Key claims: The hardest part is step 3, backfilling the gap: under async replication the Slave lags the Master tail, and When answers by reloading/reconciling from Redis; the three stages depend on lease / Controller / replicas and form the most error-prone flow.
- Learner-relevant: The failover contract that later tests and correctness must verify.

### replication
- Locator: `[[sources/geek-ai-agent/20260922/第33节：分布式 - 集群化架构：原理 + 拆解.pdf#replication]]`
- Summary: Contrasts sync replication (write Master → replicate → ACK → return) with async (write Master → return immediately → background replicate).
- Key claims: Sync doesn't lose but is slow and Slave jitter drags the Master; async is fast but loses the tail at crash; with a reliable external source of truth (Redis) the async loss is only the in-memory view, not the data — hence When chooses async.
- Learner-relevant: The CAP trade-off and the reasoning behind When's async choice.

### coordination
- Locator: `[[sources/geek-ai-agent/20260922/第33节：分布式 - 集群化架构：原理 + 拆解.pdf#coordination]]`
- Summary: Defines the coordination layer as a reliable, strongly consistent public store + change notification that hosts member registration/lease, election/consensus, and route metadata/global sync (Watch); compares ETCD, ZooKeeper, Consul, and DB tables.
- Key claims: Regardless of choice, it's always three moves — members/survival (Lease/TTL or heartbeat table), election (grab lock via CAS/unique key), change sync (Watch push or periodic pull with local cache); selection depends on timeliness, consistency strength, and ops cost.
- Learner-relevant: The selection frame for the coordination plane.

### mechanism-map
- Locator: `[[sources/geek-ai-agent/20260922/第33节：分布式 - 集群化架构：原理 + 拆解.pdf#mechanism-map]]`
- Summary: A closing table mapping each new problem to its mechanism and key points: membership→heartbeat+lease, unique decision→Controller election+consensus, data location→sharding+route metadata, failover→replicas+switchover, replica consistency→sync/async, common coordination→coordination service.
- Key claims: Detection floor = TTL; quorum prevents split-brain; consistent hashing saves migration; failover's hard part is the data gap; with an external source of truth async is safe; pick coordination by timeliness.
- Learner-relevant: A revision one-pager tying the six mechanisms together.

### closing-principles
- Locator: `[[sources/geek-ai-agent/20260922/第33节：分布式 - 集群化架构：原理 + 拆解.pdf#closing-principles]]`
- Summary: Three general judgments for distributed design: borrow don't build (use mature components for consensus/coordination), externalize state (put non-losable state in reliable storage; stateless nodes scale and switchover better), and choose by scenario (timeliness/consistency/ops cost — enough is enough).
- Key claims: Over-design is the enemy; next lesson contrasts why OryxOS and When take two different distributed paths.
- Learner-relevant: The portable design heuristics; bridges to lesson 34's comparison.
