# Digest — 第25节：定时任务模块 原理解析、实现与代码讲解

## Overview (L1)

- 定时任务是什么 — the third trigger source ("clock-push"): at a scheduled time the system assembles a message and feeds it to the same `AgentService` entry as CLI/Web.
- 动手前想清楚 — keep the module narrow (no workflow engine); use Spring's `TaskScheduler`; four traps — config-driven schedules, overlapping executions, failure isolation, timezone.
- 代码怎么写 — one `AgentScheduler` (`registerAll` + `runOnce`) plus `ScheduleConfig`, dynamic cron registration and per-task local locks.
- 验收 harness — one `AgentSchedulerTest` covering the four traps, with a "second entry" assertion to catch missing unlock.
- 做完怎么验 — real scheduled trigger, config-driven cron change without recompilation, end-to-end rehearsal for the demo agents.

## Sections (L2)

### 一-定时任务是什么

- Locator: `[[sources/geek-ai-agent/20260922/第25节：定时任务模块 原理解析、实现与代码讲解.pdf#一-定时任务是什么]]`
- Summary: Earlier triggers (CLI, Web Service) are "human-push"; many scenarios need the Agent to know "it is time" without anyone asking. Scheduled tasks are not a new capability but a third trigger source: at the time, the system assembles a message and feeds it to the same processing entry as CLI/Web.
- Key claims: `ReActLoop`, Tool execution and Provider calls need no change at all; this is the missing "who calls it at the time" for the two acceptance demos (daily weather, daily tech digest, lesson 31).
- Learner-relevant: Frames scheduling as a trigger source, reinforcing the "engine stable, add entries without touching it" theme.

### 二-动手前先想清楚

- Locator: `[[sources/geek-ai-agent/20260922/第25节：定时任务模块 原理解析、实现与代码讲解.pdf#二-动手前先想清楚]]`
- Summary: `AgentScheduler` only reads cron config, triggers, assembles a message for `AgentService`, prevents overlapping execution of the same task, and records trigger success/failure. It does not decide what the message says (Profile/SKILL.md), how it is processed (ReActLoop), or which instance executes (Phase-2 distributed coordination). Use Spring's built-in `TaskScheduler` (standard cron, dynamic registration) instead of writing one. Four traps: config source (cron and message must come from Profile/SKILL.md, not Java constants — "配置即 Agent"); overlap (if a run outlasts the interval, a process-local lock suffices for single-instance core phase, no distributed lock); failure isolation (a crashed run must not crash the scheduler nor fail silently — audit `llm_calls`/`tool_invocations` as usual); timezone (cron defaults to server timezone, so the config must specify zone explicitly).
- Key claims: The module should end up as a thin scheduling layer: config-driven, local-lock protected, audit-on-failure, explicit timezone.
- Learner-relevant: The four traps and the "don't invent new capability, reuse the platform" principle.

### 三-代码怎么写

- Locator: `[[sources/geek-ai-agent/20260922/第25节：定时任务模块 原理解析、实现与代码讲解.pdf#三-代码怎么写]]`
- Summary: `AgentScheduler` holds `ThreadPoolTaskScheduler`, `ProfileRegistry`, `AgentService` and a `ConcurrentMap<String, Lock>`. `registerAll` iterates all Profiles' `schedules` and calls `taskScheduler.schedule(() -> runOnce(profile, sc), new CronTrigger(sc.getCron(), sc.getZoneId()))`. `runOnce` gets/creates a `ReentrantLock` per task id, `tryLock`s (skip + log if busy), then `sessionManager.getOrCreate("scheduler", "scheduler", profile.getName())` and `agentService.process(session, sc.getMessage())`, catching exceptions with `log.error` and always `unlock` in `finally`.
- Key claims: Dynamic registration via `TaskScheduler.schedule(...)` is used instead of a hardcoded `@Scheduled` annotation so changing a trigger time is config-only, not a recompile; the scheduler session identity is fixed `("scheduler", "scheduler", profileName)` with history bounded by `max_history_turns`; audit flows through the same `llm_calls`/`tool_invocations` as a manual conversation. Deferred: distributed coordination (leader election, distributed locks, leases), automatic retry and failure alerting.
- Learner-relevant: The concrete code and the "same entry, no special-casing for scheduled triggers" property.

### 四-验收-harness

- Locator: `[[sources/geek-ai-agent/20260922/第25节：定时任务模块 原理解析、实现与代码讲解.pdf#四-验收-harness]]`
- Summary: The trick is not to wait for real time — `runOnce` is extracted so it can be called directly; cron firing itself is Spring's job, so tests only verify "registration parameters are correct". One `AgentSchedulerTest` covers the four traps: `CronTrigger` carries configured cron and zone (ArgumentCaptor), a held lock skips this trigger without queuing, `runOnce` throwing does not propagate and the lock is released in `finally`, and two triggers get the same Session triple.
- Key claims: The most valuable second half of the exception test runs `runOnce` again to prove the lock was released — only this "second entry" assertion catches a missing `unlock`.
- Learner-relevant: A test-design pattern for locks and failure isolation.

### 五-做完怎么验

- Locator: `[[sources/geek-ai-agent/20260922/第25节：定时任务模块 原理解析、实现与代码讲解.pdf#五-做完怎么验]]`
- Summary: Manual checks: set a schedule to every minute and observe the Agent auto-initiating a dialogue with audit records; change the cron expression, restart and see it follow the new time (config-driven); run the full path "scheduled trigger → ReAct loop → audit records" as groundwork for the lesson-31 timed demos.
