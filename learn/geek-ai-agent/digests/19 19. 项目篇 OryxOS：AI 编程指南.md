# Digest — 19 19. 项目篇 OryxOS：AI 编程指南

## Overview (L1)
- 实施总览 — Overall approach: a hybrid of Spec-Kit for the main greenfield build (feed the existing requirements + tech-plan docs into Spec-Kit, split into 5 user stories) and manual prompting with Claude Code for later small increments; user stories are ordered by dependency, not by time.
- Spec-Kit 跟 OryxOS 的匹配度评估 — Evaluates whether Spec-Kit fits OryxOS: fits medium/large greenfield with clear requirements and AI-agent collaboration; OryxOS matches every criterion; documents Spec-Kit's limits (heavy for small increments, spec-drift, brownfield context limits, fast evolution) and the countermeasures.
- 准备阶段 — Scaffolding: install Specify CLI (Python 3.11+, uv) + configure Claude Code; write constitution.md (7 principles); /speckit.specify turns the requirements doc into 5 user-story specs; /speckit.plan turns the tech plan into a module plan; deliverables checklist.
- 基于 Spec-Kit 的实施拆解 — Breaks each of the 5 user stories into core goal, Maven modules, task-splitting thinking, key task granularity, and acceptance demo; plus cross-story collaboration (analyze after each story, correct constitution drift, re-read spec when context is lost, git-commit per story).
- 项目交付物 — Beyond the runnable 1.0: project homepage (VitePress), Spec-Kit artifacts retained in repo, community docs (API reference, ops manual, CONTRIBUTING) via PR.
- 增量阶段：手动提示词模式 — Why switch (small granularity, 1–3 files, no cross-module work), the community contribution workflow (issue → fork → Claude Code → PR), and how constitution/spec remain as long-term references; new large features may rerun Spec-Kit.
- 风险和注意事项 — Spec-Kit current limits (version-lock the CLI, consult official docs, avoid community extensions) and common challenges (constitution drift, cross-story context breaks, skipping analyze, MCP integration pitfalls, Java basics prerequisite).
- 总结 — Two-phase strategy recap: Spec-Kit for the main build, manual prompting for increments; feed existing docs rather than rewriting; order by user-story dependencies (US-1→US-2→(US-3∥US-4)→US-5).

## Sections (L2)
### Main approach: Spec-Kit + manual prompting hybrid
- Locator: `[[sources/geek-ai-agent/19 19. 项目篇 OryxOS：AI 编程指南.html#approach]]`
- Summary: Two phases with different tools: the main build (from zero, all 9 Maven modules, clear boundaries, complete docs) runs the full Spec-Kit spec-driven flow (constitution → specify → plan → tasks → implement) to keep output aligned with the requirements and avoid vibe-coding drift; the incremental phase (small 1–3 file changes: extensions, bug fixes, new Plugin Tools) switches to manual prompting with Claude Code because a full Spec-Kit run is overkill for small increments.
- Key claims: The boundary is clean — Spec-Kit for large-granularity greenfield, manual prompts for small increments; tool choice matches work nature.
- Learner-relevant: Anchor: the two-phase tool-selection rule (also the doc's core contribution to the project's implementation method).

### Relation to requirements and tech-plan docs
- Locator: `[[sources/geek-ai-agent/19 19. 项目篇 OryxOS：AI 编程指南.html#doc-relations]]`
- Summary: The guide does not rewrite the docs — it feeds them to Spec-Kit: requirements doc → /speckit.specify input (turned into 5 user-story specs for the five capabilities); tech plan → /speckit.plan input (modular implementation plan); requirements ch.3 design goals + tech plan §1.1 key decisions → constitution.md; requirements ch.13 five acceptance demos → acceptance criteria of the 5 user stories.
- Key claims: The plan's module structure must match tech plan §10's 9 modules — feed the latest tech plan or the generated plan will split by the wrong module count.
- Learner-relevant: Anchor: the doc→artifact mapping table reused to prepare Spec-Kit inputs.

### Decomposition: by user story, not by time
- Locator: `[[sources/geek-ai-agent/19 19. 项目篇 OryxOS：AI 编程指南.html#user-stories]]`
- Summary: The main build is organized as 5 user stories with dependency-driven ordering: US-1 对接 LLM (base, no deps), US-2 ReAct 循环 (depends US-1), US-3 Memory 三层记忆 (depends US-2), US-4 Plugin Tool 体系 (depends US-2, parallel with US-3), US-5 Web Service (depends on the first four).
- Key claims: US-5 last is about dependency, not importance — Web Service is a key differentiator; the doc avoids P1/P2/P3 priority labels to prevent misreading "later = optional"; this ordering naturally fits Spec-Kit's /speckit.tasks, which organizes tasks by user story with dependency sorting and parallel marking.
- Learner-relevant: Anchor: the dependency DAG (US-1→US-2→(US-3∥US-4)→US-5) that structures all implementation work.

### Does Spec-Kit fit OryxOS
- Locator: `[[sources/geek-ai-agent/19 19. 项目篇 OryxOS：AI 编程指南.html#fitness]]`
- Summary: Spec-Kit is a GitHub open-source spec-driven development toolchain (fastest-growing dev tool of 2026, high adoption, supports 20+ AI coding agents), structuring AI-assisted coding as specify → plan → tasks → implement, with the spec as the single source of truth for code behavior — a cure for vibe coding.
- Key claims: It fits medium-to-large greenfield, clear requirements, AI-agent collaboration, and methodology-driven teams; it does not fit small features/quick prototypes/single-file changes, large brownfield refactors (context limits), or exploratory research; OryxOS matches every fit criterion (pure greenfield, medium scale of 9 modules, complete docs, Claude Code as the build agent), so Spec-Kit is the best tool for the main build — brownfield criticisms don't apply.
- Learner-relevant: Anchor: the fit assessment the learner can reuse when choosing tools for other greenfield projects.

### Spec-Kit limitations and countermeasures
- Locator: `[[sources/geek-ai-agent/19 19. 项目篇 OryxOS：AI 编程指南.html#limitations]]`
- Summary: Four known limits with responses: ① heavy for small increments → main build is large-grained, small increments switch to manual prompts (the two-phase rationale); ② spec doesn't auto-sync with implementation drift → run /speckit.analyze after each user story (the official anti-drift command, recommended before implement); ③ context limits on large brownfields → not applicable to pure-greenfield OryxOS (all code fits in context); ④ Spec-Kit itself evolves fast (commands, artifact formats, Claude Code integration moving to skills mode) → don't lock to a version's details, follow official docs at implementation time.
- Learner-relevant: Anchor: the /speckit.analyze habit and the version-flexibility stance carried into the risk section.

### Preparation: install and configure

### Constitution
- Locator: `[[sources/geek-ai-agent/19 19. 项目篇 OryxOS：AI 编程指南.html#constitution]]`
- Summary: constitution.md holds the non-negotiable principles distilled from requirements ch.3 + tech plan §1.1 — seven principles: ① JDK 21 + Spring Boot 3.x monolith, Maven 9 modules, single binary; ② five capabilities first, governance layer in extension; ③ self-implemented ReAct loop, not Spring AI's Agent abstraction; ④ Spring AI used only halfway — Provider abstraction/protocol conversion/@Tool schema generation, auto tool execution disabled, scheduling by ReActLoop+ToolExecutor (singled out as the most likely to be written wrong); ⑤ Plugin Tool three tiers, SKILL.md+MCP zero-code as primary; ⑥ SQLite + MEMORY.md in core, vector retrieval in extension, audit tables (tool_invocations, llm_calls) written from day one; ⑦ every user story ends with a demo, priority is 跑通 not 完美.
- Key claims: Principles ④ and ⑥ are the most likely to be ignored and must be upheld; constitution is written once and never changed by the AI agent — if a principle is wrong, stop and re-discuss.
- Learner-relevant: Anchor: the seven principles the AI agent must re-read whenever code drifts.

### Plan

- Summary: /speckit.plan takes tech plan + spec.md + constitution.md and outputs the implementation plan: tech stack (JDK 21 + Spring Boot 3.x + Spring AI Alibaba + SQLite + Picocli), 9 Maven module responsibilities (per tech plan §10), expanded key decisions, data flow and module collaboration (PromptBuilder + ProviderService + ToolExecutor + MemoryService three-tier facade).

### US-1: LLM integration
- Locator: `[[sources/geek-ai-agent/19 19. 项目篇 OryxOS：AI 编程指南.html#us1]]`
- Summary: Goal: call any mainstream LLM with the Agent unaware of vendor. Modules: oryxos-core (OryxTool, Session, Profile, ContextLoader), oryxos-provider, oryxos-boot. Task categories: environment (Maven 9-module skeleton, Spring Boot config, Spring AI Alibaba deps), core abstractions (OryxTool, Profile/Message structures), Provider impl (ProviderService, provider-name→ChatModel explicit mapping, Function Calling adapter), config (application.yaml with at least DeepSeek or Kimi, API key via ConfigLoader/env).
- Key claims: The task note must call out that ProviderService must NOT distinguish Providers by scanning all ChatModel beans (ambiguous when multiple exist) — maintain an explicit name mapping (tech plan §3.2); AI agents easily write type-scanning; US-1 has no standalone demo — it demos together with US-2.
- Learner-relevant: Anchor: the explicit-mapping pitfall embedded in task notes.

### US-2: ReAct loop
- Locator: `[[sources/geek-ai-agent/19 19. 项目篇 OryxOS：AI 编程指南.html#us2]]`
- Summary: Goal: implement the Agent's core mechanism (LLM reasons → calls tool → sees result → next step). Modules: oryxos-core (ReActLoop, PromptBuilder, ToolExecutor, ContextLoader), oryxos-tool (one HTTP Tool + simplified SandboxChecker URL whitelist), oryxos-channel-cli, oryxos-cli (init + chat). Task categories: ReAct loop (main loop, PromptBuilder, ToolExecutor, MAX_ITERATIONS), CLI Channel (CliChannel, chat, init), base Tool (HTTP), Profile YAML parsing (SnakeYAML, validation), Session (in-memory SessionManager; persistence deferred to US-5).
- Key claims: Complex tasks to split fine: ReActLoop main loop (~tens of Java lines but engineering parts — error handling, logging, message accumulation, iteration control — split into 2–3 subtasks), PromptBuilder four-part assembly (several subtasks); constitution principle ④ again — disable Spring AI auto tool execution or tools get called twice; run /speckit.analyze after US-1+US-2; acceptance is Demo 一 (查天气穿衣 with DeepSeek or Kimi).
- Learner-relevant: Anchor: the task-granularity guidance and the double-invocation pitfall to watch.

### US-3: Memory
- Locator: `[[sources/geek-ai-agent/19 19. 项目篇 OryxOS：AI 编程指南.html#us3]]`
- Summary: Goal: cross-dialogue state retention with a minimal two-tier version — one MEMORY.md file + two built-in Tools. Module: oryxos-memory (MemoryService three-tier facade, LongTermMemory, MemoryTools). Task categories: MemoryService facade (one interface for ReAct, delegating session→SessionManager, long-term→LongTermMemory), LongTermMemory (append/load/recallByKeyword/truncateIfNeeded, interface reserved for recall-with-mode semantic upgrade), MemoryTools (save_memory + recall_memory via @Tool), PromptBuilder integration (inject memory without breaking US-2's ReAct loop), MEMORY.md file management (location, format, truncation).
- Key claims: US-3 is relatively independent (depends US-2, doesn't block US-4); tasks are small-grained; the PromptBuilder integration is a modification-type task requiring care not to break existing logic; run analyze after; acceptance is Demo 二 (cross-dialogue preference memory surviving restart).
- Learner-relevant: Anchor: the small-granularity example and the "don't break the working loop" caution.

### US-4: Plugin Tool system
- Locator: `[[sources/geek-ai-agent/19 19. 项目篇 OryxOS：AI 编程指南.html#us4]]`
- Summary: Goal: let business parties extend OryxOS via the three Plugin tiers; core stage completes all three tiers' infrastructure plus the built-in Tool set. Modules: oryxos-tool (complete File Tools + Shell Tool, MCP Client, full SandboxChecker, ToolRegistry — one merged module), oryxos-core (SKILL.md loading belongs to ContextLoader, not the tool module). Task categories: built-in Tool completion (read_file/write_file/list_dir, Shell with whitelist, full SandboxChecker), MCP Client (mcp_servers.yaml parsing, McpClientService connect + tools/list, McpToolAdapter → OryxTool), SKILL.md (ContextLoader appends to system prompt), Profile upgrade (skills + mcp_servers fields).
- Key claims: MCP Java ecosystem is less mature than Python — implement stdio transport first (most common), defer SSE; split stdio MCP Client into subtasks (connection management, tools/list, tool/call, error recovery); full SandboxChecker splits into 3 subtasks (file path, shell command, HTTP domain whitelists); acceptance is Demo 三 (zero-code PR digest with a community github-mcp).
- Learner-relevant: Anchor: the stdio-first MCP strategy and the SandboxChecker task split.

### US-5: Web Service
- Locator: `[[sources/geek-ai-agent/19 19. 项目篇 OryxOS：AI 编程指南.html#us5]]`
- Summary: Goal: expose all capabilities via REST for business-system HTTP integration — the differentiator from personal assistant projects. Modules: oryxos-web (WebServer, six controllers, 10 endpoints), oryxos-storage (SQLite Session persistence upgrade + audit-table writes), oryxos-cli (complete 12 Picocli commands), oryxos-core (ConfigLoader, ContextLoader Bootstrap completion). Task categories: Web Service base (WebServer + virtual threads, GlobalExceptionHandler, OpenAPI), six parallelizable ApiControllers, the 10 REST endpoints, persistence upgrade (SessionRepository, messages_json serialization, audit tables), config/context (ConfigLoader, Bootstrap loading + PromptBuilder integration), CLI completion, engineering (Logback/SLF4J structured logs + error handling).
- Key claims: US-5 is last and has the highest task density; audit-table writes land here (constitution principle ⑥) — the AI easily omits them thinking logs suffice, so the task must call it out; 6 controllers are mutually independent and parallelizable; acceptance is Demo 四 (sync call lifecycle) + Demo 五 (multi-endpoint flow: info→profiles→tools→invoke→memory).
- Learner-relevant: Anchor: the "audit day one" note that closes the audit-data gap if missed.

### Collaboration patterns during implementation

- Learner-relevant: Anchor: the operational rhythm for keeping an AI agent on track across a multi-story build.

### Incremental phase: why manual prompting
- Locator: `[[sources/geek-ai-agent/19 19. 项目篇 OryxOS：AI 编程指南.html#incremental-why]]`
- Summary: Post-main-build work differs fundamentally: small granularity (one Channel, one bug, one Plugin Tool), few files (1–3), no cross-module collaboration, existing-code context rather than from-zero design — a full Spec-Kit cycle costs more than the task itself; manual prompting with Claude Code directly edits in the existing context, tests, and opens a PR without formal spec/plan artifacts.
- Learner-relevant: Anchor: the workload-based rationale for switching tools.

### Incremental workflow
- Locator: `[[sources/geek-ai-agent/19 19. 项目篇 OryxOS：AI 编程指南.html#incremental-workflow]]`
- Summary: Typical flow: contributor claims an issue (labeled good-first-issue / feature-request / long-term-goal) → fork + clone → open Claude Code and describe the change → Claude edits, adds tests, runs them → open PR → maintainer reviews and merges; Spec-Kit is not mandatory for increments, though a strict large feature may choose to run it.
- Learner-relevant: Anchor: the community-contribution playbook used after core-stage handoff.

### Handoff with main-stage artifacts
- Locator: `[[sources/geek-ai-agent/19 19. 项目篇 OryxOS：AI 编程指南.html#handoff]]`
- Summary: constitution.md remains non-negotiable for community code (JDK 21+Spring Boot, self-implemented ReAct, half-Spring-AI, three-tier Plugin); spec.md stays the capability contract — changes to a core capability must not break its acceptance criteria; plan.md is mostly frozen after the main build, the tech plan stays as reference; new user stories: small features go manual-prompt + PR, large features (new Maven module, constitution change, cross-capability) go through a full Spec-Kit run at maintainer discretion.
- Learner-relevant: Anchor: the rules for keeping post-main-build contributions aligned with the original contract.

### Risks: Spec-Kit current limits
- Locator: `[[sources/geek-ai-agent/19 19. 项目篇 OryxOS：AI 编程指南.html#risks-speckit]]`
- Summary: Spec-Kit is still evolving fast — countermeasures: pin a specific Specify CLI version for the whole main build (commands, artifact formats, integrations change between versions), consult official docs at implementation time, and avoid Spec-Kit's 70+ community extensions (use only official core commands to reduce uncertainty).
- Learner-relevant: Anchor: the version-pinning and extension-restraint policy.

### Risks: common implementation challenges
- Locator: `[[sources/geek-ai-agent/19 19. 项目篇 OryxOS：AI 编程指南.html#risks-challenges]]`
- Summary: Common challenges with countermeasures: AI drifts from constitution (check after each implement; the most-often-wrong spots are Spring AI auto execution not disabled, Provider type-scanning, Tool re-split into multiple modules, SkillLoader treated as Tool, audit tables not written — focus checks there); cross-story context breaks (have the AI re-read spec.md + plan.md + recent code before each story); /speckit.analyze skipped (make it a hard requirement per story to prevent drift); MCP server integration pitfalls (Java MCP Client less mature than Python, stdio transport may hit process-start/encoding issues — test connectivity with a minimal MCP server before US-4); Java engineering basics are a prerequisite (unfamiliar Spring Boot/Maven/JPA slows the rhythm — ensure team proficiency first).
- Learner-relevant: Anchor: the risk register that mirrors and extends the requirements doc's risks for the AI-coding context.
