# Digest — 23 23. 项目篇 When：AI 编程实施指引

## Overview (L1)
- 这份指引是给你的 — 解释写作缘由：需求文档只讲"要怎么样"、技术方案讲"怎么设计"，这份指引填执行层空缺，说明 3 周里每天做什么、用什么工具、怎么把任务下给 AI。
- 整体思路：六步走全链路 — 选轻量手工模式（CLAUDE.md + Skills + 手工任务清单，不用 Spec-Kit）并说明理由；六阶段：设计 Harness、拆 Spec、任务执行、测试、部署脚本和 CI、部署上线和监控运维。
- 第一步：设计 Harness，建立护栏 — 项目根 CLAUDE.md、模块级 CLAUDE.md、Skills 库、Hooks 自动化（Spotless/Checkstyle/SpotBugs/PMD/JaCoCo）、Plan Mode 规则；第一周准备好。
- 第二步：从需求和设计拆 Spec — 文档驱动加任务清单；第一层按七个核心模块拆、第二层拆成 100-500 行/一 PR 的子任务；任务卡片结构（TW-001 与 RP-002 两个真实例子）；任务/PR/Issue 一一对应；清单持续更新；轻量手工模式的边界。
- 第三步：任务执行 — 开始任务、让 AI 写代码的节奏（关键节点介入）、卡住的四种情况与应对、review 看什么、什么样的 PR 能合并。
- 第四步：测试 — 单元测试让 AI 写（覆盖率 80%、避免凑覆盖率等坑）、集成测试用 Testcontainers、故障注入测试、性能测试（JMH+wrk）。
- 第五步：部署脚本和 CI — Dockerfile、docker-compose、Kubernetes yaml、GitHub Actions CI phase、PR/Issue 模板、CI 出问题的处理。
- 第六步：部署上线和监控运维 — 三种环境部署节奏、Prometheus/Grafana 接入、出问题用 AI 排查（证据→分析→Runbook）、真实部署产出物。
- 工具全景 — 每个阶段用什么工具汇总。
- 反模式：这些做法不允许 — 七种禁止做法（AI 当自动补全、人重写、人手写一半、不 review 合并、绕过 CLAUDE.md、任务中途改卡片、用工具堆砌掩盖思考缺失）。
- 三周怎么落地 — 每周具体安排（第一周 Harness+任务清单、第二周核心调度单节点、第三周集群/HA/管理台/部署/发布）；结语讲"姿势对了招式自然长出来"。

### overall-six-step-approach
- Locator: `[[sources/geek-ai-agent/23 23. 项目篇 When：AI 编程实施指引.html#整体思路：六步走全链路]]`
- Summary: 说明 Why 选轻量手工模式而非 Spec-Kit 专业 SDD 工具，并给出六步走的总体路径。
- Key claims: 业界 SDD 两种姿势：Spec-Kit（GitHub 2025 年推出，/specify /plan /tasks /implement 四阶段）与轻量手工模式（CLAUDE.md + Skills + 手工任务清单）；When 选轻量手工模式的四理由：已有需求+技术方案文档（即 /specify /plan 产出，再跑是重复）、3 周时间紧不能耗在工具学习、更接近真实工作场景、后续 AgentOS 项目会用 Spec-Kit 演示完整 SDD 工具链（两种模式是教学设计）；轻量手工模式保留 SDD 核心思想（规约先行、AI 按规约写代码、人 review），用 CLAUDE.md 承载项目级规约、Skills 承载标准模式、任务清单承载具体任务；六步：设计 Harness 建护栏、从需求和设计拆 Spec（智力中枢）、任务执行（流水线）、测试、部署脚本和 CI、部署上线和监控运维；六步互相支撑、每步产出是下步输入；核心思路是全链路 AI 协作、人在更高维度做判断，AI 写 90%+ 是自然结果。
- Learner-relevant: 实施指引的全局框架，解释 When 的 AI 协作姿势。

### step1-harness
- Locator: `[[sources/geek-ai-agent/23 23. 项目篇 When：AI 编程实施指引.html#第一步：设计 Harness，建立护栏]]`
- Summary: Harness 五件套：项目根 CLAUDE.md、模块级 CLAUDE.md、Skills 库、Hooks 自动化、Plan Mode 规则。
- Key claims: 项目根 CLAUDE.md 三类信息：项目身份（When 是什么/3 周 MVP 阶段）、技术栈约束（Java 11+、Spring Boot 3.x、Maven、Lettuce、jetcd、grpc-java、阿里规范、SLF4J、不引入新依赖除非 review）、禁区和原则（不能改的目录、不能跑的命令、不用 ZSet 大集合）；核心原则是写真正决定 AI 行为的事，不写废话；动态文档随跑偏补条目；模块级 CLAUDE.md 按七模块（接入层/路由层/时间轮调度引擎/副本同步器/Sink 投递器/ETCD 客户端/Redis 客户端）就近放约束，Claude Code 按路径自动加载最近的；Skills 沉淀标准模式（add-sink、add-api-endpoint、add-metric 等），判断标准"同一个模式做到第三次"；Hooks：Spotless 保存即格式化、Checkstyle/SpotBugs/PMD 自动 Lint、JaCoCo+Surefire 改模块跑相关测试、Maven 提交前全量构建，早反馈自动反馈不让人做机器的事；Plan Mode 强制场景：改时间轮调度算法、改持久化 key 结构、改 Master/Slave 同步协议、大规模重构、删公共接口、改超 50 行、改超 3 个文件；Plan Mode 核心价值是把事后 review 改错代码变成事前 review 改对方向；第一周备齐：根+七份模块 CLAUDE.md、基础 Hooks、几个确定 Skills。
- Learner-relevant: 教学案例的完整 Harness 样板，可直接迁移到其他 AI 编程项目。

### step2-spec-breakdown
- Locator: `[[sources/geek-ai-agent/23 23. 项目篇 When：AI 编程实施指引.html#第二步：从需求和设计拆 Spec]]`
- Summary: 用文档驱动加任务清单的方式拆 Spec，包括两层拆分、任务粒度判断、任务卡片结构、两个真实例子与任务/PR/Issue 对应。
- Key claims: 不写专业 Spec（需求+技术方案文档已覆盖 /specify 与 /plan），只做 /tasks 阶段的事，markdown（tasks/ 目录）+ GitHub Issues 同步维护；第一层按七个核心模块+第八个"基础设施"模块（可观测/CI/部署）拆，依据技术方案 3.2 节，编号如 tasks/01-ingress.md；第二层拆子任务四原则：一个任务一个 PR、100-500 行核心代码（AI 一次跑完、人能 review 完）、依赖关系清晰、有明确验收标准；粒度信号：核心代码量、单一职责、可验证验收、不跨模块；任务卡片字段：任务 ID（TW-001）、标题、目标、输入（前置任务/参考文档/已有代码）、输出（文件路径）、验收标准（功能/质量/性能）、禁区、预估；TW-001 例（SingleLayerWheel 类、四个公开方法、JaCoCo 85%、add P99≤100 微秒、1000 并发 10 万次不出错、槽位级 lock）；RP-002 例（ReplicationService.proto 三个方法、MasterReplicator/SlaveReplicator、同步延迟 P99≤50ms、失败注入通过、禁区：不同步阻塞/不强行一致/不做 Slave 状态判断）；"任务卡片本身就是 Spec"；对应关系：一个任务=一个 Issue=一个 PR，Issue 标题带 ID、labels 标 module/phase、分支名 feat/tw-001-single-layer-wheel、PR 里 Closes #N，实现端到端追溯；任务清单不是一次性写完，改清单不改在做任务，所有改动走 PR；轻量手工模式边界：适合已有完整文档/任务 100 以内（When 约 60-80 个）/小团队/学员熟悉基础姿势；不适合从零项目、大规模、强合规。
- Learner-relevant: 拆 Spec 的完整方法论与模板（任务卡片是可直接复用的样板）。

### step3-task-execution
- Locator: `[[sources/geek-ai-agent/23 23. 项目篇 When：AI 编程实施指引.html#第三步：任务执行]]`
- Summary: 开始任务、和 AI 协作的节奏、卡住的应对、review 看什么与合并条件。
- Key claims: 每天从任务清单/Issues 挑任务并 assign 自己，原则是"做能完整完成的任务"，按模块包干（一人一个模块依赖最简单）；从主干建分支（命名规范在根 CLAUDE.md）；把任务卡片完整内容交给 AI，补充临时上下文要在开工前说清；节奏：复杂任务先 Plan Mode、简单任务（有 Skill 兜底）直接写；关键介入节点：AI 选技术决策时、接近完成时先 review 再跑测试、测试失败时判断测试本身是否有问题；卡住四种情况：反复改不对（回头改任务卡片+新对话）、偏离约束（回头补 CLAUDE.md）、缺上下文（告诉 AI 已有工具类、必要时写进 CLAUDE.md）、任务粒度太大（重新拆成 2-3 个子任务）；总原则"问题出在哪里就在哪里修"；review 按重要性：对不对（符不符合卡片/方案/禁区）、质量（边界条件/吞错误/日志/注释一致）、测试（是否凑覆盖率、补真实价值测试）、集成（影响其他模块/接口/兼容）；review 留痕通过 PR comments，不允许 AI 不改 comment 就合并；PR 合并硬条件：CI 全绿、至少一个真实 review（非空 approval）、任务卡片全部验收通过、commit message 清晰（标 AI/人改动，是占比统计依据）、任务卡片更新一起合并。
- Learner-relevant: 每天怎么和 AI 协作、怎么守住 review 纪律的可操作流程。

### step4-testing
- Locator: `[[sources/geek-ai-agent/23 23. 项目篇 When：AI 编程实施指引.html#第四步：测试]]`
- Summary: 单元测试、集成测试、故障注入测试、性能测试各自的做法人机分工。
- Key claims: 单元测试让 AI 写（写代码同时写测试，不是事后补），覆盖率默认 80%（JaCoCo CI 强制）；AI 写单测三个坑：凑覆盖率（测 getter setter，删掉）、只测正常路径（卡片里写明覆盖边界/并发路径）、测试与实现耦合太紧（只用公开接口）；卡片里测试部分要具体（列场景：空轮 add、单消息 add/tick、满槽位、并发 add 10 线程各 1000 条）；集成测试用 Testcontainers（自动启停 ETCD/Redis/Kafka 容器），覆盖核心场景（30s 后 HTTP 回调、1000 条精度正负 1 秒、杀 Master 10 秒内 Slave 接管消息不丢、取消不投递、Kafka Sink 到 topic），CI 里跑；故障注入测试：随机杀 Master、ETCD/Redis 短暂不可用（降级模式）、网络分区（toxiproxy/iptables），主干合并时跑，测试代码本身要仔细 review；性能测试 JMH+wrk（预热/采样/统计模板进 Skill），每周末跑完整基准看趋势。
- Learner-relevant: 测试策略与坑位清单，直接支撑测试任务与 CI 设计。

### step5-deployment-and-ci
- Locator: `[[sources/geek-ai-agent/23 23. 项目篇 When：AI 编程实施指引.html#第五步：部署脚本和 CI]]`
- Summary: Dockerfile、docker-compose、Kubernetes yaml、GitHub Actions CI、PR/Issue 模板与 CI 排障。
- Key claims: Dockerfile 多阶段构建（builder 编译/runtime 只放 jar+JRE）、Eclipse Temurin 或 Amazon Corretto、JVM 参数、暴露 HTTP/gRPC 端口、健康检查命令，可做 Skill；docker-compose 含三节点+ETCD+Redis 主从+Kafka，AI 易错点：容器名 hostname、depends_on 顺序、端口映射、每节点不同环境变量（WHEN_NODE_ID），本地 up 后 curl 全流程验收；K8s yaml：Deployment/Service/ConfigMap/Secret/HPA/PDB（保证至少 2 副本存活），人 review 资源限制/健康检查/滚动升级/PDB，minikube 或 kind 验收；GitHub Actions phase：Build（Maven+Spotless+Checkstyle+SpotBugs+PMD）、Unit Test（JaCoCo）、Integration Test（Maven verify+Testcontainers）、Docker Build、Publish（仅主干，推 Docker Hub/GHCR、git tag、GitHub Release）；每 PR 跑前三 phase；PR 模板（Issue 编号/改动概述/AI 代码占比/Review checklist）、Issue 模板（Bug/Feature/Task，Task 字段与任务卡片一致）；CI 失败四类处理：Lint（回修 Hooks）、单测失败（AI 分析代码还是测试问题）、集成测试 flaky（Re-run、还失败看日志）、覆盖率不达标（回让 Hooks 跑 JaCoCo）；"不要责怪 CI，要修 CI 配置和测试本身"。
- Learner-relevant: 自动化质量门与发布管线的具体配置，是 CI/CD 任务与运维参考。

### step6-deploy-and-operate
- Locator: `[[sources/geek-ai-agent/23 23. 项目篇 When：AI 编程实施指引.html#第六步：部署上线和监控运维]]`
- Summary: 三种环境部署节奏、Prometheus/Grafana 接入、AI 排查问题与真实部署产出物。
- Key claims: 本地环境第二周末跑通（稳定性要求最高、PR 合并前先本地验证）；单机生产第三周初（云主机 docker 跑 When+ETCD+Redis）；K8s 第三周中后期（EKS/GKE 或 minikube/kind），是 1.0"生产部署样本"；每种环境跑完做端到端验证（提交/查询/取消/不同 Sink/故障切换）；Prometheus 30s 抓 /metrics（deploy/prometheus.yml），Grafana Dashboard（deploy/grafana-dashboard.json）面板：集群概览、流量、质量（成功率/耗时 P50/P95/P99/精度分布）、存量、资源（JVM/GC/CPU/Redis QPS/ETCD QPS）；AI 排查姿势：先收集证据（Grafana 曲线、grep trace_id 日志、etcdctl get --prefix /when/、redis-cli key 数、jstack/jmap）再让 AI 分析，逐个验证可能原因；每次排查写成 Runbook（现象/原因/解决/预防，docs/runbooks/，AI 写第一版人 review）；真实部署产出物：可演示集群+访问地址+curl 脚本+Grafana 链接、完整部署文档（30 分钟复现）、Dashboard JSON、至少 3 个 Runbook，随 GitHub Release 发布。
- Learner-relevant: 从代码到运行系统的收尾路径，以及运维知识沉淀的 Runbook 实践。

### three-week-roadmap
- Locator: `[[sources/geek-ai-agent/23 23. 项目篇 When：AI 编程实施指引.html#三周怎么落地]]`
- Summary: 把六步走放进 3 周真实时间的具体节奏与交付物。
- Key claims: 第一周 Harness+任务清单（1-3 天根/七模块 CLAUDE.md、基础 Hooks、最初 Skills；4-5 天建八模块任务清单、周五达成共识并创建全部 Issues）；第二周核心调度和单节点版本（按模块分工，1-3 天接入层/路由层/Redis 客户端/ETCD 客户端，4-5 天时间轮+HTTP Sink，周五单节点端到端跑通：curl 30 秒延时消息 POST 到测试接口）；第三周集群/HA/其他 Sink/管理台/部署（1-2 天集群协调+副本同步，3 天 Kafka Sink/管理台/Prometheus，4 天 Docker/docker-compose/K8s yaml/CI，5 天真实部署+完整演示+故障注入+发布 1.0）；每周末复盘（AI 占比/PR review 质量/测试覆盖率/CI 稳定性）；3 周末交付物：运行中的集群、完整代码仓库（80%+ AI 完成）、完整文档、Grafana Dashboard、3-5 个 Runbook、社区接力 onramp（Contributor Guide/Good First Issues）；结语：指引讲不变的姿势，具体招式在实操中长出。
- Learner-relevant: 训练营每周执行计划与最终交付验收清单，与需求文档里程碑互相印证。
