# 插件化 Agent 與動態管理

## Learning goal

懂一目錄一 Agent 的載入機制（AGENT.md→Profile→註冊→自跑）與動態管理（免重啟掃描、上傳即上線、一句話生成）。

## Lesson

OryxOS 在第二十八節之前已經有一座完整的核心（kernel）：Provider、ReAct、內建 Tool、Memory、Sandbox、排程、Web。但「能跑一個 Agent」還不等於「是 Agent OS」。作業系統之所以是作業系統，不在核心多強，而在於它提供一套標準機制，讓你能在不改核心、不重新編譯的前提下，安裝並執行任意多個互相隔離的程式。第二十九與三十節補上的，正是這套機制：**定義一個 Agent、安裝它、讓它自己跑**。

這套機制的核心是一條邊界：**底座（base）是所有人共用的系統能力，Agent（業務層）是一個自足的目錄**。一個 Agent 就是 `.oryxos/agents/<name>/` 底下的一個目錄，裡面用 `AGENT.md` 帶身分與設定、帶任務指令，其餘檔案（腳本、子指令、欄位參考）各自用到才進上下文。目錄的形狀借自 Anthropic Agent Skills，但定義的單位被釘死為「一個目錄 = 一個 Agent」——skill 降級成這個目錄內部的選用元件，不存在跨 Agent 的能力庫或全域索引。

真正讓「目錄」變成「會自己跑的 Agent」的，是四步鏈路：掃描 `.oryxos/agents/`、把 `AGENT.md` frontmatter `deriveProfile` 成底座認識的 `Profile`、註冊進可變的 `ProfileRegistry`（排程同時交給 `AgentScheduler`）、觸發時走同一條 `AgentService.process` 自跑。關鍵在於底座從頭到尾只認 `Profile` 這個值物件，所以「從 Profile YAML 讀」換成「從 Agent 目錄推導」時，底座一行都不用改——這也是整個插件化最省力、最關鍵的一步。

第三十節把這條鏈路從「登入伺服器放檔案、重啟才生效」升級成動態管理：一個真相源 `.oryxos/agents/`、兩條錄入路徑（API 上傳與目錄即時監看），共用同一個註冊入口，所以「上傳即上線」等於「丟目錄即上線」；再補上 CRUD 端點、一句話生成，以及刪除／更新時「先動排程 handle、再動索引與目錄」的順序紀律。最後一條是誠實的信任邊界：安裝一個帶腳本的 Agent，等於信任它的作者，因為子程序網路能繞過內建 `http_get` 的域名白名單。
