# 集群化六機制與選型

## Learning goal

能用成員、唯一決策、資料定位、故障接管、複製一致性、協調選型六機制拆解任何叢集系統，並判斷 OryxOS 與 When 為何選不同路線。

## Steps

1. [[learn/geek-ai-agent/nodes/distributed-clustering-fundamentals/why-cluster-and-panorama|為何要叢集化：單機的兩道天花板與六問題全景]] — 說出叢集化的動機、六問題與執行期全景
2. [[learn/geek-ai-agent/nodes/distributed-clustering-fundamentals/membership-and-election|成員感知與唯一決策：心跳、租約與選舉]] — 講清租約偵測與 CAS／多數派保證唯一決策（after step 1）
3. [[learn/geek-ai-agent/nodes/distributed-clustering-fundamentals/data-location-and-replication|資料定位與複製一致性：分片路由與同步／非同步]] — 用路由表定位 Master，並比較同步與非同步複製（after step 1）
4. [[learn/geek-ai-agent/nodes/distributed-clustering-fundamentals/failover|故障接管：偵測、決策、回填資料缺口]] — 拆解三階段，指出最難的是回填資料缺口（after steps 2–3）
5. [[learn/geek-ai-agent/nodes/distributed-clustering-fundamentals/coordination-and-selection|公共協調層與選型：OryxOS 為何用 DB，When 為何用 etcd]] — 用三個判斷與三問決策選出協調方案（after steps 1–4）

## Lesson

一台機器跑得再好，也會撞到兩道牆：**容量**（記憶體、CPU、磁碟放不下）與**單點故障**（一當機，所有還沒完成的任務全丟）。叢集化就是同時對付這兩道牆的答案——水平擴充加上消除單點。但這個答案不是免費的：原本一台機器上理所當然的事，一旦拆到多台，全都變成真問題。

這堂課把那些問題收斂成六個，並各配一個機制去解：**成員感知**（誰還活著）用租約與心跳；**唯一決策**（誰說了算）用選舉與共識；**資料定位**（東西在哪台）用分片與路由元數據；**故障接管**（死機後誰頂上）用副本與切換；**複製一致性**（副本怎麼同步）用同步／非同步取捨；**公共協調**（以上資訊放哪、怎麼通知）用一個強一致的公共儲存加變更通知。六個問題、六個機制，就是一張可以套用到任何叢集系統的拆解地圖。

最後一步走出原理，進到選型：OryxOS 是離線排程型系統，十幾秒後才被接管、重新跑一次在業務上無感，所以它用企業本來就有的 MySQL／PostgreSQL，靠資料列鎖與心跳表做協調；When 是即時投遞型系統，必須準時、不丟、10 秒內接管，所以它引進 etcd 的租約、選舉與 Watch，並用 Redis 當零遺失的底。兩者做的是同一件事—多節點協調—差別只在「要多即時」，而這一條就決定了整個架構的重量。讀完這五步，你應該能拆開任何叢集系統，也能替一個新系統選出它該走的路線。
