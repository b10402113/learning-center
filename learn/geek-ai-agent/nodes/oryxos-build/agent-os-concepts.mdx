# Agent OS 概念與行業格局

## Learning goal

理解 Agent OS 的定義、五項能力清單、與編排平台和框架的邊界區分，認識 OpenClaw 和 Hermes Agent 兩大開源代表的特徵與局限，掌握企業私有可控底座的剛性需求以及 Java 生態的缺口所在。

## Lesson

### 一個人用一個 Agent，很棒。那十個呢？

你在終端裡開一個 coding agent，丟進 prompt（發給模型的一段指示），它乖乖去讀檔案、改程式碼、跑測試。一個 agent 一個人用，什麼都好說。但場景換到一家公司。運維要一個 agent 幫忙處理告警，客服要一個 agent 回覆使用者問題，銷售要一個 agent 整理客戶資料，HR 要一個 agent 篩選履歷。每個都得接大語言模型（LLM）、調用工具、記住上下文、管好使用者身份、留下操作紀錄。

你第一個想到的辦法是什麼？大概是：每個 agent 各寫一套後端，接 LLM 的工作做四遍，安全策略各管各的，審計紀錄散落四方。聽起來合理，但你仔細想，Windows 或 Linux 之所以存在，就是為了不讓一台機器上的每個程式自己管記憶體、自己管硬碟。作業系統管的就是這堆公共的事。

Agent 世界一直缺那一層。一個人同時跑 N 個 agent 的時候，這些 agent 共享的基礎設施層長什麼樣，這個問題的答案就是 [[learn/geek-ai-agent/elements/agent-os|Agent OS]]。

### 先說定義，但只說一句

Agent OS（Agent 操作系統）是裝在用戶或企業自己機器上、用來運行和管理多個 AI Agent 的基礎系統。向上給各類 Agent 提供統一的運行環境，向下接入模型、渠道、工具、記憶、身份驗證和審計這些基礎設施。Agent 跑在它上面，跨 Agent 的公共能力由它統一提供。

這句話講完就好。重點不是背定義，而是拆解它。

### 五件事，衡量任何 Agent OS 的尺

一個合格的 Agent OS 必須回答五件事。這張表是你評估任何產品時的第一把尺。

| 能力 | 說明 |
| --- | --- |
| Agent 配置與生命週期管理 | 能註冊、啟動、監控、停用多個 Agent，每個 Agent 有獨立的 prompt、模型、工具、渠道、記憶 |
| 統一對外渠道接入 | 企業微信、飛書、釘釘、Slack、Telegram、郵件、Web、HTTP API，所有 Agent 共用一套渠道層 |
| 統一對內系統接入 | LLM 供應商、工具（透過 MCP 協議暴露）、企業 IT 系統、知識庫，所有 Agent 共享一套接入層 |
| 統一記憶 | 跨 Session 的長期記憶、可複用的 Skill 模板、跨 Agent 的知識累積 |
| Tool 調用與沙箱執行 | Agent 透過 Function Calling 調用 Tool，Tool 在沙箱裡執行，守住安全邊界 |

評估一個產品，先問這五件事有沒有做。沒有這五件事，它就不是 Agent OS，只是一個 agent 的執行環境。

### runtime 跟 Agent OS 是兩件事

這組詞最容易搞混。老王把它們拆開。

agent runtime 是讓單個 Agent 跑起來的執行核心，負責 LLM 調用、工具執行、上下文管理、循環控制。五件事裡的 Tool 調用和沙箱執行大致落在這一層。

Agent OS 的內核確實包含一個 agent runtime，但它在 runtime 之上還多管了四件事：多個 Agent 的生命週期管理、統一的對外對內接入、統一記憶、多租戶和審計。

借作業系統的類比。runtime 像單個進程的執行環境，Agent OS 像管理一群進程、調度資源、提供共享服務和治理的那一層。runtime 讓一個 agent 跑起來，Agent OS 讓一群 agent 在企業裡被管起來。兩者不是同一件事。

### 部署形狀：Agent 是配置出來的

Agent OS 的部署形態很具體。用戶部署一個實例，裝在自己的機器、伺服器或 K8s（Kubernetes，容器編排平台）上，自帶 Web 管理台或 CLI 工具。透過 Web 或 CLI 創建 Agent、註冊 Tool 和 Skill、配置渠道。Agent 跑起來後，終端用戶透過 IM 或 Web 跟它對話。

業務方要做的事只有兩件。寫一個 Tool 實現某個具體功能，任何語言都行。然後在 Agent OS 上配置一個 Agent 把 Tool 用起來。業務方不寫 Agent 後端代碼，消息從哪裡來、LLM 怎麼調、用戶身份怎麼管、審計紀錄怎麼留、上下文怎麼延續，全部由 Agent OS 處理。

Agent 是配置出來的，不是寫出來的。這是 Agent OS 跟框架最直觀的差別。

### 跟三類鄰居怎麼區分

Agent OS 容易跟三類東西搞混。擺在一張表裡看最清楚。

| | 產物 | 誰在用 | 部署形態 | 跟 Agent OS 的關係 |
| --- | --- | --- | --- | --- |
| 編排平台（Dify、Coze、扣子） | 一條 workflow（工作流） | 業務人員、開發者 | 多為 SaaS 或自部署平台 | 可跑在 Agent OS 之上，拿它當後端 |
| 框架（LangChain、Spring AI、LangChain4j） | 代碼 | 開發者 | 自己搭運行環境 | 可當 Agent OS 的底層組件 |
| 大廠 SaaS（Glean、Agentforce） | 完整應用 | 企業採購方 | SaaS，綁雲生態 | 不同象限，無法私有部署 |
| Agent OS | 配置出來的常駐 Agent | 企業 IT、業務方 | 裝在自己機器上的運行時 | 它自己 |

編排平台是視覺化工作流構建器，產物是流程。Agent OS 的產物不是 workflow，是配置出來的、常駐運行的 Agent。兩者不在同一層，Dify 完全可以跑在 Agent OS 之上，把 Agent OS 當後端來調。

框架是一組庫或 SDK（軟體開發套件），給開發者用代碼寫 Agent，運行環境要開發者自己搞定。框架好比給你材料讓你自己蓋房子，Agent OS 是蓋好的房子拎包入住。兩者是復用關係，不是競爭關係。Agent OS 內部的 LLM 調用層，可以直接復用 Spring AI 或 LangChain4j 這類框架。

大廠 SaaS 產品是綁定各自雲生態的完整應用，形態是 SaaS，不裝在用戶自己機器上。Agent OS 是開源、可私有部署的底座，不鎖生態。

### 業界兩個代表性項目

開源 Agent OS 領域目前最有代表性的兩個項目是 OpenClaw 和 Hermes Agent，取向正好兩頭。

OpenClaw 由 PSPDFKit 創始人 Peter Steinberger 在 2025 年 11 月發布，Node.js 實現，MIT（寬鬆的開源許可證）協議。它代表消費級、開發者優先的取向，二十多個渠道、上萬個社區 skill、可玩性極強，到 2026 年 4 月 GitHub 超過 30 萬顆星，是 GitHub 歷史上增長最快的開源項目。強項是社區活力和能力豐富度，軟肋是企業級安全和治理。CVE（公共漏洞與暴露）、惡意 skill、憑證收割這類結構性問題反覆出現，企業要上生產得靠 Tank OS 這類二次加固才能勉強過關。一句話，OpenClaw 是個人和小團隊的 Agent OS。

Hermes Agent 由開源 AI 實驗室 NousResearch 在 2026 年 2 月發布，Python 實現，MIT 協議。它代表工程級、穩健優先的取向，有三層記憶、自我演化的 skill 機制、安全掃描、HERMES_HOME 多用戶隔離，到 2026 年 5 月約 15 萬顆星，日活推理量一度反超 OpenClaw。它比 OpenClaw 更接近企業需求，但企業級 OS 治理這塊，多租戶 RBAC（基於角色的權限控制）、SSO（單點登入）、完整審計，仍然是空白。一句話，Hermes 是更偏團隊和小企業的 Agent OS。

### 兩者共同留下的三塊空白

兩個項目合起來，把開源 Agent OS 的版圖定在個人和小團隊產品。它們共同留下三塊空白。

第一塊是完整的企業級治理。多租戶 RBAC、SSO 接入、審計架構、合規留證，這些企業級能力在兩者身上都是空白。PTG 和 Tank OS 這類二次加固方案存在，但那是打補丁，不是設計進架構裡的東西。

第二塊是企業 IT 系統的深度集成。兩個項目對企業 IM 渠道都靠社區擴展支持，但企業現有的 ERP（企業資源計劃）、CRM（客戶關係管理）、CMDB（配置管理資料庫）、監控系統，深度對接要靠每家自己寫適配。

最後一塊是 Java 生態缺位。OpenClaw 是 Node.js，Hermes 是 Python，Java 生態裡沒有一個項目把 Agent OS 當定位。

### 企業為什麼需要私有可控的底座

[[learn/geek-ai-agent/elements/enterprise-java-gap|企業需求與 Java 生態缺口]] 把這條需求的論證攤得更完整。老王在這裡只講要害。

需求側的數字很明確。Anthropic 2026 State of AI Agents 報告調查 500 多位技術負責人，超過半數已經部署多步驟 agent 工作流，絕大多數計劃在 2026 年擴展更複雜的用例，多數回報 AI Agent 投資帶來可衡量的經濟回報。需求不是問題。

問題出在從 demo 到生產的過程。做一個能演示的 Agent 不難，一旦要跑在生產環境、服務全公司，立刻撞上一堆工程問題。同一份報告裡最硬的數據指向的就是這些工程問題：企業認為最大的挑戰是系統整合、數據訪問質量、實施成本、變更管理。安全治理上，多數組織在過去一年報告過 AI-agent 安全事件，只有很小比例在 agent 進生產時拿到完整的 IT 和安全審批。Tool calling 在生產環境的失敗率不低，而且多數是靜默失敗。這些問題沒有一個靠換更強的模型能解決，全都出在底座不夠穩、不夠可控。

把鏡頭對準最硬的那批客戶。銀行、政府、電信、能源、醫療這些嚴格受監管的企業有幾條不能破的規矩：核心業務數據不能出企業，系統必須完全可審計，任何新組件都要過現有的安全和合規流程，技術棧要跟現有體系一致。在這些規矩下，選擇被極大收窄。不會把核心 Agent 跑在 SaaS 上，數據出企業這關過不去。不會跑在綁定公有雲的產品上，怕鎖生態。很難把一個有 CVE 和憑證收割史的開源項目放進生產，安全審查過不去。它們需要的是私有部署、完全可審計、能納入現有 IT 治理、跟現有技術棧一致的 Agent 底座。

這個需求錨在企業本質的約束上，不是錨在「Agent OS」這個概念上。無論這個詞將來流不流行，這個中間層是獨立存在還是被吸收進上下層，嚴格受監管企業要一個自己完全掌控的 Agent 底座這件事都不會變。

### 價值錨點：不只是省錢

私有可控的底座對企業的價值是具體的。省成本、提效率、跨系統協作、合規審計能落地、讓普通員工也能用上 AI 能力。這些都好理解。

但最深的一個價值錨點是知識沉澱。透過 Skill 體系，把資深員工的經驗變成留在企業裡的資產，新人入職可以直接繼承。沉澱的知識、經驗和 AI 能力永遠屬於企業，這是私有底座跟 SaaS 最根本的差別。SaaS 帶不走這些東西，私有底座能留下。

### Java 生態在這一層的位置

供給側看 Java，缺口一眼可見。Java 在 AI 工程上有框架，但沒有一個是 Agent OS 這一層的底座。

Spring AI 是 Spring 官方推出的 Java AI 應用開發框架，做 LLM 調用抽象、Prompt 模板、RAG（檢索增強生成）、Tool Calling 這類能力。Spring AI Alibaba 是阿里推動的 Spring AI 擴展，一年內做出十餘個主流 LLM 的 connector（連接器），通義、文心、DeepSeek、Kimi、智譜、混元、豆包都在列，真實的企業部署案例已經出現。LangChain4j 是 LangChain 的 Java 移植，功能類似，也是框架。再往下的推理生態，ONNX Runtime Java、DJL 這類解決模型推理問題，跟 Agent OS 不在同一層。

這些全是庫或框架，產物是代碼，運行環境要開發者自己搞定。Java 寫的、裝好就能跑的 Agent OS 底座，業界幾乎為零。OpenClaw 是 Node.js，Hermes 是 Python，Java 在這一層是空的。

### 生態完整性：為什麼這個缺位值得補

換個角度想這件事。一個健康的技術生態，每一個關鍵層級都應該有自己的實現。哪一層空著，那個生態在那一層就斷了一截，斷層處只能靠跨生態的膠水去接，膠水是脆的、成本是持續的。

Java 和 Spring 的企業後端棧極其完整。Web 框架有 Spring Boot，微服務有 Spring Cloud，配置註冊有 Nacos，限流熔斷有 Sentinel，分佈式追蹤有 SkyWalking，線上診斷有 Arthas，監控告警有 Prometheus 加 Grafana，每一層都有成熟、互相咬合的實現。企業的 ERP、CRM、CMDB、SSO、監控，大量是 Java 接口或 Java SDK。唯獨 Agent OS 這一層是空的。

後果很具體。Java 體系的企業想要私有可控的 Agent 底座，今天只能用 Node.js 的 OpenClaw 或 Python 的 Hermes，然後在兩套技術棧的接縫處寫大量膠水，對接自己的 Java 服務、複用自己 Java 的運維工具鏈、走自己 Java 的審計流程。這道接縫正是最痛的地方。Spring AI 當年補上 Java 的 LLM 調用層，走的就是同一條邏輯。

### Java 做這件事的具體支點

缺位現在值得補、也補得動，有幾個具體支點。

Spring Boot 是企業後端的事實標準。一個 Java Agent OS 就是一個 Spring Boot 應用，運維體系無縫對接，IT 部門不用學新東西。

Spring AI Alibaba 提供現成的主流 LLM connector，十幾個大模型的接入不用重新造輪子，LLM Provider 這一層站上現成肩膀。

JVM（Java 虛擬機）成熟的運維工具鏈能直接複用。Nacos、Sentinel、SkyWalking、Arthas、JFR、Prometheus 加 Grafana，跟 Java Agent OS 無縫銜接，企業現有運維體系不用為它單獨搭一套。

跟企業現有 Java 系統對接成本最低。Tool 直接調企業現有 Java 服務，不用寫跨語言的膠水。

嚴格受監管行業的私有部署要求讓 Java 成為確定性選擇。這些行業的核心系統大量是 Java，私有部署、完全審計、合規過審是硬要求，用 Java 實現可以走企業現有的 Java 審計流程。

GraalVM Native Image 補上啟動和內存的短板。JDK 21 加 Spring Boot 3.x 加 GraalVM，啟動速度和內存佔用能接近 Node.js 和 Python，單二進制部署可行。代價也要說清楚，Native Image 對 Spring AI 這類重反射、重動態代理的框架仍有編譯期配置的工程成本，AOT（提前編譯）適配不是零成本，但這條路在持續成熟。

### Spring AI 的崛起是先行信號

Spring AI 在 2024 年發布，Spring AI Alibaba 一年內做出十餘個主流 LLM connector，說明 Java 生態在 AI 工程上的追趕速度很快。Spring AI 解決了底層 LLM 調用能力，缺的正是上面那層 Agent OS。阿里官方在 Spring AI Alibaba Admin 項目裡做企業級 Agent 應用的最佳實踐，積累了一定的社區認知。Java AI 工程的基礎設施層在 2025 年解決，自然往 Agent OS 這一層走，這是技術棧演化的順序。

### OryxOS 把自己錨在哪裡

把前面所有線收到一起，OryxOS 是企業能完全掌控、Java 原生、私有可審計的統一 Agent 底座。裝在企業自己的 K8s、伺服器或物理機上，跑各種業務 Agent，共享一套渠道接入、模型路由、記憶系統、工具調用、安全審計。數據完全留在企業自己的基礎設施，不鎖任何雲生態。

它用「Agent OS」這個框架來理解和構建自己，但錨點放在背後那個不會變的需求上。嚴格受監管企業要私有可控、要跟 Java 體系一致，這件事不會因為概念演進而消失。錨在需求上，不錨在概念上。

### 做 runtime，不做編排

OryxOS 在分層上守住 runtime 這一層，不往上做編排。它站在編排平台和應用之下，做承載 Agent 跑起來的底座，但仍然是完整的 Agent OS，多 Agent 管理、多租戶、審計都在範圍內。

它提供 Channel、LLM Provider、Memory、Tool 註冊、Sandbox、多租戶、SSO、審計、可觀測性、Web 管理台。業務方在上面配置 Agent，Agent 跑起來。

它故意不做視覺化 workflow 編排、複雜任務分解、多 Agent 顯式協作。企業真需要複雜 workflow，可以用 Dify 這類編排平台跑在 OryxOS 之上。兩者是互補關係。這條邊界讓 OryxOS 專注做好底座一件事。

### 安全，從第一天就設計

OpenClaw 的安全問題是結構性的。開放的低門檻第三方 skill 生態，加上默認寬鬆的權限和較弱的隔離，出事只是時間問題。OryxOS 定位嚴格受監管企業，安全必須是第一天就設計進架構的東西，並且在幾件事上走相反的路。

Skill 和 Tool 的來源受控，不提供任何人上傳、任何 Agent 隨意拉取的開放市場。企業內的 Skill 和 Tool 要過註冊、審核、簽名、版本管理，來源可追溯。

最小權限，每個 Agent 和 Tool 拿到的是顯式授予的最小集合，文件系統、網絡、shell 的訪問範圍默認收緊，按需放開。

沙箱隔離是強制的。Tool 在隔離環境裡執行，有明確的資源和能力邊界，多租戶之間完全隔離。

憑證不落明文，走企業現有的密鑰管理體系，使用全程可審計。

prompt injection（提示詞注入）和數據外泄要主動防禦，記憶寫入和工具輸入都過安全掃描。

從頭到尾的審計是底座能力，誰、在什麼時候、讓哪個 Agent、調了什麼 Tool、訪問了什麼數據、產生了什麼結果，全程結構化留痕，可以接進企業現有的審計和 SIEM（安全信息與事件管理）系統。OryxOS 本身是 Java 和 Spring 實現，跑在企業自己的基礎設施上，能直接納入企業現有的代碼審計、安全掃描、合規過審流程。安全從架構裡長出來，不是事後加的殼。

### 路線，從單機到分佈式

當前版本做的是單機私有部署。一個實例裝在企業的一台伺服器或一個容器裡，跑一組 Agent，服務一個部門或一個場景。這是刻意的選擇，絕大多數企業落地 Agent 底座，都是先從一個場景跑通、跑穩開始，單機最簡單、最易接入、最容易納入現有運維和審計。

架構上為未來留了方向。當企業從一個部門試點走向服務全公司，單機會撞到扛不住量、扛不住故障、扛不住規模化治理這三件事。中期走向實例無狀態、狀態外置的分佈式部署，解決扛量、高可用和規模化治理。長遠圖景是分佈式 Agent 協作，讓跨部門、跨機器的 Agent 互相發現、委託、協作。方向先想清楚，是為了讓單機版本不堵死未來的路，複雜度留到真需要時再壓上來。
