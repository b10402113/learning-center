# Spec-Kit 主導的 AI 編程實作

## Learning goal

真動手跑通 Spec-Kit 主導的 AI 編程全流程，從 0 寫出可運行的 OryxOS（JDK 21 + Spring Boot + 自研 ReAct loop）——本課程唯一真動手項目。你不會只是看 AI 自由發揮，而是跟著規範、計劃和任務走，每一步都有驗收，最後拿到可以跑的代碼。

## Lesson

### 老王的開場白：AI 寫代碼怎麼就這麼「飛」？

說實話，我很早就開始用 AI 輔助寫代碼。最開始的感覺是：哇，這東西真強，五分鐘就能寫完一個功能。但隨著項目變大，我就發現問題了。AI 寫著寫著就跑偏了，生成的東西跟需求文檔不對應，類別名亂改，邏輯走歪，事後才發現原來是它跑偏了。我以為是我 prompt 的問題，嘗試優化 prompt，結果越優化越嚴重，AI 好像越畫外靶。

然後我碰到了 Spec-Kit。我以為它是什麼神奇的prompt技巧，結果它不是。它是一套工具流程，把「先寫清楚要做什麼，再讓 AI 寫代碼」變成一套有規範、有計劃、有任務、有驗收的流程。主構建用 Spec-Kit，增量用手動提示詞。大粒度 greenfield 用 Spec-Kit，小改動跑完整 Spec-Kit 成本大於任務本身，直接跟 AI 說清楚改哪裏就行。

So here comes the contradiction. If you just dump a whole requirement doc into AI and say "build me OryxOS", it will generate code that looks plausible at first but diverges from the spec before you know it. The more complex the project, the easier it drifts. You think you're feeding it a whole book, but it only "sees" a few pages at a time. That's why chunking exists — but Spec-Kit goes further: it doesn't just cut the text into pieces, it forces you to spell out the rules first (the constitution), then translate those rules into a spec, then into a plan, then into concrete tasks. Each task has a demo at the end. You finish one task, you check if it drifts, you fix it, you commit. Only then do you move to the next task.

You might think, "Then I'll just cut the fragments even smaller, by word." 

But if you cut too small, every piece loses context. A single instruction like "use Spring Boot" without the surrounding "Maven multi-module, JDK 21, nine modules" means nothing. You need the right-sized chunk — big enough to keep semantic connections, small enough to keep details in view. That's exactly what Spec-Kit forces you to do: user stories that are large enough to carry meaning, but small enough to finish and verify in one go.

### 從「亂來」到「有規範」

我們先看看什麼是「vibe coding」失控。AI 寫著寫著就脫離需求文檔，自己編出和方案對不上的結構。事後才發現，為什麼？因為 AI 沒有被約束住。它只是單純根據概率預測下一個字，沒有人工介入去檢查「這行代碼對不對應規範」。

Spec-Kit 就是為了治這個病。它的核心思想是：規範是代碼行為的唯一真實來源。不是讓 AI 邊寫邊編，而是把需求文檔和技術方案喂給工具，讓它生成規範、計劃和任務，然後每完成一任務就檢查一次有沒有跑偏。如果跑偏，當場糾正，不讓它繼續往下走。

七條憲法原則是從需求文檔第三章設計目標和技術方案第一節關鍵決策提煉的：① JDK 21 + Spring Boot 3.x 單體、Maven 九模塊、單個二進制；② 五項能力優先，治理層留擴展；③ 自研 ReAct 循環，不用 Spring AI 的 Agent 抽象；④ Spring AI 只用一半，Provider 抽象/協議轉換/@Tool schema 生成，自動工具執行禁用，調度交給 ReActLoop+ToolExecutor，這條最容易被寫錯；⑤ Plugin Tool 三級，SKILL.md+MCP 零代碼優先；⑥ SQLite + MEMORY.md 在核心，向量檢索留擴展，審計表第一天就寫；⑦ 每個 user story 以 demo 收尾，優先跑通不追求完美。

主構建拆成五個 user story，按依賴排序：US-1 對接 LLM（無依賴），US-2 ReAct 循環（依賴 US-1），US-3 Memory 三層記憶（依賴 US-2），US-4 Plugin Tool 體系（依賴 US-2，與 US-3 並行），US-5 Web Service（依賴前四個）。US-5 放最後是依賴關係決定的，不是重要性問題，它其實是關鍵差異化。驗收 demo 直接複用需求文檔第三章的五個 demo。

### 老王的實作實驗：我怎麼跟著 Spec-Kit 跑了一遍

我決定親自跟著 Spec-Kit 走一遍，看看到底困在哪裏。首先我準備了環境：裝 Specify CLI（Python 3.11+，建議用 uv 裝）和配置 Claude Code；寫 constitution.md（七條原則，AI 永不改它）；用 /speckit.specify 把需求文檔變成五個 user story 的規範，用 /speckit.plan 把技術方案變成模塊計劃。關鍵是喂最新的文檔，喂舊版技術方案，生成的計劃會按錯誤的模塊數切分。

我第一個 story 是 US-1 對接 LLM。無依賴，最開始的東西。我跑 /speckit.specify，它把需求文檔第三章提煉出五個 user story，然後我手動檢查，看看有沒有漏掉什麼。然後跑 /speckit.plan，生成模塊計劃。發現如果技術方案過時，生成的計劃就會錯，模塊數切分不對。所以必須確保喂的是最新版技術方案。

每個 story 結束後跑 /speckit.analyze（官方防漂移命令），檢查 constitution/spec/plan/tasks/code 的一致性。AI 違反憲法（用非 JDK 21 特性、改了 ReAct 實現、啟用了 Spring AI 自動執行、拆了 Tool 模塊、Provider 類型掃描）要當場糾正；上下文丟了讓 AI 重讀 spec.md + plan.md + 最近代碼；每個 story 結束 git commit 便於回滾。

### US-1：對接 LLM——無依賴的第一步

US-1 是對接 LLM，無依賴，可以獨立跑。我跑 /speckit.specify，它從需求文檔第三章提煉出 user story，然後生成 spec。spec 裊定了 LLM 提供商、模型名、基礎參數。然後跑 /speckit.plan，生成模塊計劃。US-1 完成後，跑 /speckit.analyze，檢查 constitution/spec/plan/tasks/code 一致性。發現 AI 生成的代碼確實跟 spec 對不上，某個地方用了錯誤的模型參數，當場糾正，重新生成。

然後 git commit，記錄下來。US-1 完成，進入 US-2。

### US-2：ReAct 循環——依賴 US-1 的核心

US-2 是 ReAct 循環，依賴 US-1。因為 US-1 完成了 LLM 對接，有了基礎的模型連通能力。US-2 的目的是構建自研的 ReAct 循環，不用 Spring AI 的 Agent 抽象。我跟著 spec 走，寫 ReActLoop，配置 ToolExecutor。發現最容易出錯的地方在於第四條憲法原則：Spring AI 只用一半，自動工具執行必須關閉。如果沒關，Spring AI 會和自研的 ReActLoop 都去執行工具，工具被調用兩次。

我手動檢查，發現確實有這個問題。AI 生成的代碼裡，工具被調用了兩次，邏輯就亂了。所以我手動改了，關掉 Spring AI 的自動工具執行，只讓 ReActLoop 去調用。然後跑 analyze，檢查一致性，通了。git commit，進入 US-3。

### US-3：Memory 三層記憶——依賴 US-2

US-3 是 Memory 三層記憶，依賴 US-2。因為 US-2 完成了 ReAct 循環，有了核心引擎。US-3 的目的是構建 Memory 系統：跨會話保留長期記憶、可複用的 Skill 模板、跨 Agent 的知識累積。我跟著 spec 走，配置 MemoryService 門面、LongTermMemory、MemoryTools。然後跑 analyze，檢查一致性。發現某個地方忘記寫審計表，當場補上。因為「可審計」是 OryxOS 的差異化賣點，後補要回頭解析日誌，又貴又容易漏。tool_invocations 和 llm_calls 從核心階段就開始寫，等於審計數據的地基第一天就打好。

git commit，進入 US-4。

### US-4：Plugin Tool 體系——依賴 US-2 與 US-3 並行

US-4 是 Plugin Tool 體系，依賴 US-2 與 US-3 並行。因為 US-2 和 US-3 都完成了，現在可以開始配 Plugin Tool。Spec-Kit 這條路線是：主構建從零開始，九個模塊邊界清楚、文檔齊全，跑完整的 spec-driven 流程。但增量階段是 1–3 個文件的改動（擴展、修 bug、新 Plugin Tool），切換成用 Claude Code 手動提示詞，因為為小改動跑一輪完整 Spec-Kit 是殺雞用牛刀。

我這次是跑主構建，所以還是走 Spec-Kit。我配置了三級 Plugin Tool：SKILL.md+MCP 零代碼優先。然後跑 /speckit.specify，生成 user story，跑 /speckit.plan，生成模塊計劃。跑 analyse，檢查一致性。發現 AI 生成的 Tool 實現跟方案衝突，比如把 Tool 拆成三個模塊、把 SkillLoader 當成 Tool、把 Memory 塌縮進 Session，這些都和方案衝突，要在構建時當場糾正。

每個 story 結束 git commit，記錄下來。US-4 完成，進入 US-5。

### US-5：Web Service——依賴前四個

US-5 是 Web Service，依賴前四個。因為前四個 story 都完成了，有了引擎、記憶、Plugin Tool，現在可以構建 Web Service 了。我跟著 spec 走，配置 WebServer、六個控制器、GlobalExceptionHandler、OpenAPI。然後跑 analyse，檢查一致性。發現某個地方 exception handling 的邏輯跟方案不一致，當場糾正。

每個 story 結束 git commit，記錄下來。US-5 完成，主構建全部完成。

### 從主構建進入增量階段

主構建完成後，進入增量階段。小改動直接手動提示詞 + PR。比如再加個功能、修個 bug、新增個 Plugin Tool，直接跟 AI 說清楚改哪裏就行，不需要跑完整的 Spec-Kit 流程。因為大粒度 greenfield 用 Spec-Kit，小改動跑完整 Spec-Kit 成本大於任務本身。

這套方法同樣適配你未來主導的其他 greenfield 項目。不管是什麼項目，先立規矩（憲法），再寫需求說明書（spec），再寫施工計劃（plan），再拆任務（tasks），最後讓 AI 按任務幹活。每幹完一單就檢查一次有沒有跑偏。幹完大工程後，小修小補就不走這套流程了，直接跟 AI 說清楚改哪裏就行。

### 老王的自嘲與尾聲

說實話，這個方法不是萬能的。你跟著 Spec-Kit 走，AI 也有可能答錯，因為它本來就會犯錯，這是它的天性，你騙不了自己。但至少，Spec-Kit 讓你知道哪裡跑偏了，然後你可以當場糾正。切塊能讓 AI 「看得見」你的內容，這是第一步。

下次你看到一堆英文字母 Spec-Kit、constitution、spec、plan、tasks，不要怕。它就是把「先寫清楚要做什麼，再讓 AI 寫代碼」變成一套工具流程。先有這個直覺，後面再講多高深都不難了。

Keep what's important, and discard what's not.

### 小結

這一篇筆記記錄了我跟著 Spec-Kit 走一遍的過程。從對接 LLM，到 ReAct 循環，到 Memory、Plugin Tool、Web Service，每一步都有規範、有計劃、有任務、有驗收。主構建完成後進入增量階段，小改動直接手動提示詞 + PR。這套方法同樣適配你未來主導的其他 greenfield 項目。

希望這篇筆記對你有幫助。老王就先這樣了，我們下篇見。
