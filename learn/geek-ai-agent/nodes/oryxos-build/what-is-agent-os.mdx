# 什麼是 Agent OS，為什麼企業需要一個 Java 的 Agent 底座

## Learning goal

能說出 Agent OS 的定義與五項能力清單，分辨 agent runtime 與 Agent OS 的差別，並解釋企業為什麼需要私有可控的 Agent 底座、Java 生態在這一層缺了什麼

## Lesson

### 一個人同時跑十個 Agent，會發生什麼

你大概天天在用 AI 編程 agent。開個 opencode 或 Claude Code，發一段 prompt（發給模型的一段指示文字），讓它讀文件、改代碼、跑測試，一個 agent 用起來很順。現在把場景放大到一家公司。運維、客服、銷售、HR，每個崗位都想配一個 AI 助手，每個都得接大模型、接工具、記住上下文、管身份權限、留下操作記錄。要是每個 agent 各寫一套後端，同樣的接線工作要做 N 遍，安全策略各管各的，出了事無從追查。

作業系統早就解決過這個問題。Windows 或 Linux 管一台機器上同時跑的一堆程序，調度資源、分配內存、管理文件。Agent 世界一直缺對應的那一層。一個人同時跑 N 個 Agent 時，這些 Agent 共享的基礎設施層該長什麼樣，長久沒人系統回答。這個問題的答案就是 Agent OS。

### 定義與五項能力清單

[[learn/geek-ai-agent/elements/agent-os|Agent OS（Agent 操作系統）]] 是裝在用戶或企業自己機器上、用來運行和管理多個 AI Agent 的基礎系統。向上給各類 Agent（運維助手、客服助手、HR 助手、銷售助手）提供統一的運行環境，向下接模型、渠道、工具、記憶、身份和審計這些底層設施。Agent 靠它在上面跑，跨 Agent 的公共能力由它統一提供。

一個合格的 Agent OS 至少要提供五件事。

| 能力 | 做什麼 |
| --- | --- |
| Agent 配置與生命週期管理 | 註冊、啟動、監控、停用多個 Agent，每個 Agent 有獨立的 prompt、模型、工具、渠道、記憶 |
| 統一對外渠道接入 | IM（即時通訊，如企業微信、飛書、釘釘、Slack）、郵件、Web、HTTP API，所有 Agent 共用一套渠道層 |
| 統一對內系統接入 | LLM（大語言模型）供應商、工具、企業 IT 系統、知識庫，所有 Agent 共享一套接入層 |
| 統一記憶 | 跨會話保留長期記憶、可複用的 Skill（技能模板）、跨 Agent 的知識累積 |
| Tool 調用與沙箱執行 | Agent 透過 Function Calling（模型決定調哪個工具的機制）調用 Tool（工具），Tool 在沙箱（隔離執行環境）裡執行，守住安全邊界 |

把這張表記住，後面評估任何 AI Agent 產品，都可以拿它當尺，先問這五件事有沒有。

### agent runtime 跟 Agent OS 是兩層

這組詞最容易混。agent runtime（Agent 執行內核）是讓單個 Agent 跑起來的執行核心，負責 LLM 調用、工具執行、上下文管理、循環控制，上面五件事裡第五件大致落在這一層。Agent OS 的內核確實包含一個 agent runtime，但它在 runtime 之上還要管前四件事，再加上多租戶（一個實例同時服務多個組織或部門，各自的數據完全隔離）和審計。

借用操作系統的類比。runtime 像單個進程的執行環境，Agent OS 像管理一群進程、調度資源、提供共享服務和治理的那一層。用一句話收住，runtime 讓一個 agent 跑起來，Agent OS 讓一群 agent 在企業裡被管起來。所以看一個產品，別只看它能不能把一個 agent 跑起來，要看它有沒有回答多 Agent 共享基礎設施這個問題。

### 部署形狀，Agent 是配置出來的

Agent OS 的部署形態很具體。用戶在自己的機器、伺服器或 K8s（Kubernetes，容器編排平台）上裝一個 Agent OS 實例，單一服務，自帶 Web 管理台或 CLI。透過 Web 或 CLI 在底座上創建 Agent、註冊 Tool 和 Skill、配置渠道。Agent 跑起來之後，終端用戶透過 IM 或 Web 跟它對話，Agent 也可以自動運行。

業務方要做的只有兩件事。寫一個 Tool 實現某個具體功能，任何語言都行。然後在底座上配置一個 Agent 把這個 Tool 用起來。業務方不寫 Agent 後端代碼，消息從哪來、LLM 怎麼調、用戶身份怎麼管、審計怎麼落、上下文怎麼續，一概不感知。這就是「Agent 用配置產生，後端代碼一行都不用寫」這句說法的來歷。OryxOS 後續的 Profile 和 CLI 設計，瞄準的正是這個體驗。

### 跟三類鄰居的邊界

Agent OS 容易跟三類東西混在一起，擺在一張表裡看就清楚了。

| | 產物 | 誰在用 | 部署形態 | 跟 Agent OS 的關係 |
| --- | --- | --- | --- | --- |
| 編排平台（Dify、Coze、扣子） | 一條 workflow（工作流） | 業務人員、開發者 | 多為 SaaS 或自部署平台 | 可以跑在 Agent OS 之上，拿它當後端 |
| 框架（LangChain、Spring AI、LangChain4j） | 代碼 | 開發者 | 自己搭運行環境 | 可當 Agent OS 的底層組件 |
| 大廠中台／SaaS（Glean、Bedrock AgentCore、Agentforce） | 完整應用 | 企業採購方 | SaaS，綁雲生態 | 不同象限，無法私有部署 |
| Agent OS | 配置出來的常駐 Agent | 企業 IT、業務方 | 裝在自己機器上的運行時 | 它自己 |

編排平台是視覺化工作流構建器，業務人員或開發者拖拽節點拼成一條 workflow，平台負責執行，產物是流程。框架是一組庫或 SDK（軟體開發套件），開發者寫代碼造 Agent，產物是代碼，運行環境自己搞定。大廠中台和 SaaS 是綁定各自雲生態的完整應用，形態是 SaaS，不裝在用戶自己機器上。Agent OS 是開源、可私有部署、不鎖生態的底座。

一個好記的比喻。框架是給你材料讓你自己蓋房子，Agent OS 是蓋好的房子拎包入住。編排平台編排的是流程，Agent OS 承載的是常駐的 Agent，兩者不在同一層，Dify 完全可以跑在 Agent OS 之上，把它當後端來調。

### 行業裡兩個代表性項目

目前開源裡最有代表性的兩個 Agent OS 是 OpenClaw 和 Hermes Agent，取向正好兩頭。

OpenClaw 由 PSPDFKit 創始人 Peter Steinberger 在 2025 年 11 月發布，Node.js 實現，MIT（寬鬆的開源許可證）協議。它代表消費級、開發者優先的取向，二十多個渠道、上萬個社區 skill、可玩性極強，到 2026 年 4 月 GitHub 超過 30 萬顆星，是 GitHub 史上增長最快的開源項目。強項是社區活力和能力豐富度，軟肋是企業級的安全與治理，CVE（公共漏洞與暴露）、惡意 skill、憑證收割這類結構性問題反覆出現，企業要上生產得靠 Tank OS 這類二次加固才能勉強過關。一句話，OpenClaw 是個人和小團隊的 Agent OS。

Hermes Agent 由開源 AI 實驗室 NousResearch 在 2026 年 2 月發布，Python 實現，MIT 協議。它代表工程級、穩健優先的取向，有三層記憶、自我演化的 skill 機制、安全掃描、HERMES_HOME 多用戶隔離，到 2026 年 5 月約 15 萬顆星，日活推理量一度反超 OpenClaw。它離企業更近，但企業級 OS 治理這塊，多租戶 RBAC（基於角色的權限控制）、SSO（單點登入）、完整審計，仍然空白。

兩個項目合起來，把開源 Agent OS 的版圖定成個人和小團隊產品。它們共同留下三塊空白。第一塊是完整的企業級治理，多租戶 RBAC、SSO、審計架構、合規留證，PTG 和 Tank OS 這類二次加固方案存在，但是補丁，不是設計進架構裡的東西。第二塊是企業 IT 系統的深度集成，兩個項目對企業 IM 渠道都靠社區擴展支持，現有的 ERP（企業資源計劃）、CRM（客戶關係管理）、CMDB（配置管理資料庫）、監控系統，深度對接要靠每家自己寫適配。最後一塊是 Java 生態缺位，OpenClaw 是 Node.js，Hermes 是 Python，Java 裡沒有任何一個項目把 Agent OS 當定位。

### 企業為什麼需要私有可控的底座

[[learn/geek-ai-agent/elements/enterprise-java-gap|企業需求與 Java 生態缺口 (Enterprise Need and the Java Gap)]] 把需求側的論證攤開，分三步走。

先確認需求是真的。Anthropic 2026 年的 State of AI Agents 報告訪問了 500 多位技術負責人，超過半數已經在部署多步驟 agent 工作流，絕大多數計劃在 2026 年擴展更複雜的用例，多數回報 AI Agent 投資帶來了可衡量的經濟回報。需求側沒有懸念。

難點擺在讓 Agent 在企業裡受控地跑起來。做一個能演示的 Agent 不難，做成企業級，跑在生產環境，服務全公司，會立刻撞上一堆工程問題。同一份報告裡最硬的數據指向的正是這些工程問題，企業認為最大的挑戰是集成、數據訪問質量、實施成本、變更管理。安全治理上，多數組織在過去一年報告過 AI-agent 安全事件，只有很小比例在 agent 進生產時拿到完整的 IT 和安全審批。Tool calling 在生產環境有不低的失敗率，而且多數是靜默失敗，系統不報錯，等用戶發現時已經晚了。這些問題沒有一個靠換更強的模型能解決，全都出在底座不夠穩、不夠可控。

最後對準最硬的那批客戶。銀行、政府、電信、能源、醫療這些嚴格受監管的企業有幾條不能破的規矩。核心業務數據不能出企業，系統必須完全可審計，任何新組件都要過現有的安全和合規流程，技術棧要跟現有體系一致。在這些規矩下，選擇被極大收窄。它們不會把核心業務的 Agent 跑在 SaaS 上，數據出企業這關就過不去。不會跑在綁定公有云的產品上，怕鎖生態。也很難把一個有 CVE 和憑證收割史、默認權限寬鬆的 Node.js 開源項目放進生產，安全審查這關過不去。它們需要的是私有部署、完全可審計、能納入現有 IT 治理、跟現有技術棧一致的 Agent 底座。

這個需求錨在企業本質的約束上，錨不住在「Agent OS」這個詞上。這個詞將來流行不流行，這個中間層獨立存在還是被吸收進上下層，規矩都不會變。嚴格受監管企業要一個自己完全掌控的 Agent 底座，這件事不會因為概念演進而消失。

### 價值錨點

私有可控的底座對企業的價值是具體的。省成本，提效率，跨系統協作，合規審計真的能落地，還有讓普通員工也能用上 AI 能力。這些都好理解。

最深的一個錨點是知識沉澱。透過 Skill 體系，把資深員工的經驗變成留在企業裡的資產，新人入職可以直接繼承。這些留下來的知識、經驗和 AI 能力永遠屬於企業，這是私有底座跟 SaaS 最根本的差別。SaaS 帶不走它們，私有底座能。這也正是 OryxOS 設計 SKILL.md 兼容的 Skill 體系的動機。

### Java 生態的位置

供給側看 Java，缺口一眼可見。Java 在 AI 工程上有不少框架，但沒有一個是 Agent OS 這一層的底座。

Spring AI 是 Spring 官方推出的 Java AI 應用開發框架，做 LLM 調用抽象、Prompt 模板、RAG（檢索增強生成，讓模型先查資料再作答）、Tool Calling 這類能力。Spring AI Alibaba 是阿里推動的 Spring AI 擴展，一年內做出十餘個主流 LLM 的 connector（連接器），通義、文心、DeepSeek、Kimi、智譜、混元、豆包都在列，真實的企業部署案例已經出現。LangChain4j 是 LangChain 的 Java 移植，功能類似，也是框架。再往下一層的推理生態，ONNX Runtime Java、DJL 這類解決模型推理，跟 Agent OS 不在同一層。

這些全是庫或框架，產物是代碼，運行環境要開發者自己搞定。一個 Java 寫的、裝好就能跑的 Agent OS 底座，業界幾乎為零。OpenClaw 和 Hermes 都不是 Java。Java 生態在 Agent OS 這一層是一塊明擺著的空缺。

### 為什麼值得補，生態完整性的邏輯

換個角度想這件事。一個健康的技術生態，應該在每一個關鍵層級都有自己的實現。哪一層空著，那個生態就在那一層斷了一截，斷層處只能靠跨生態的膠水去接，而膠水是脆的，是要持續付出成本的。

Java 和 Spring 的企業後端棧極其完整。Web 框架有 Spring Boot，微服務有 Spring Cloud，配置註冊有 Nacos，限流熔斷有 Sentinel，分佈式追蹤有 SkyWalking，線上診斷有 Arthas，監控告警有 Prometheus 加 Grafana，每一層都有成熟、互相咬合的實現。企業的 ERP、CRM、CMDB、SSO、監控系統，大量是 Java 接口或 Java SDK。唯獨 Agent OS 這一層是空的。

後果很具體。一個 Java 體系的企業想要私有可控的 Agent 底座，今天只能去用 Node.js 的 OpenClaw 或 Python 的 Hermes，然後在兩套技術棧的接縫處寫大量膠水，對接自己的 Java 服務，複用自己 Java 的運維工具鏈，走自己 Java 的審計流程。這道接縫正是 Java 體系用戶最痛的地方。一個完整生態在關鍵層級留空，早晚要用脆弱的膠水來補，補上的成本只會更高。Spring AI 當年補上 Java 的 LLM 調用層，走的正是這條邏輯。

### Java 為什麼現在補得動

這個缺位現在值得補、也補得動，有幾個具體支點。

Spring Boot 是企業後端的事實標準。Spring Boot 是 Spring 官方讓應用「裝好配置就能跑」的框架，一個 Java Agent OS 就是一個 Spring Boot 應用，運維體系無縫對接，IT 部門不用學新東西，裝上就能納入現有體系。

Spring AI Alibaba 提供現成的主流 LLM connector，十幾個大模型的接入不用重新造輪子，直接複用 Spring AI 的 ChatClient（對話客戶端）抽象，LLM Provider 這一層站上現成肩膀。

JVM（Java 虛擬機，跑 Java 程式的地方）成熟的運維工具鏈能直接複用。Nacos、Sentinel、SkyWalking、Arthas、JFR（JVM 飛行記錄器，低開銷記錄運行時數據的工具）、Prometheus 加 Grafana，跟 Java Agent OS 無縫銜接，企業現有運維體系不用為它單獨搭一套。

跟企業現有 Java 系統對接成本最低。Tool 直接調企業現有 Java 服務，不用寫跨語言膠水。

嚴格受監管行業的私有部署要求讓 Java 成為確定性選擇。這些行業的核心系統大量是 Java，私有部署、完全審計、合規過審是硬要求，用 Java 實現可以走企業現有的 Java 審計流程，不用為新組件單獨搭一條合規通道。

GraalVM Native Image 補上啟動和內存的短板。JDK 21 加 Spring Boot 3.x 加 GraalVM Native Image（把 Java 程式提前編譯成原生二進制的工具），啟動速度和內存佔用能接近 Node.js 和 Python，單二進制部署可行。代價也要講清楚，Native Image 對 Spring AI 這類重反射、重動態代理的框架仍有編譯期配置的工程成本，AOT（提前編譯）適配不是零成本，但這條路是通的，而且在持續成熟。

### Spring AI 的信號

時機上有一個先行信號。Spring AI 在 2024 年發布，Spring AI Alibaba 一年內做出十餘個主流 LLM connector，說明 Java 生態在 AI 工程上的追趕速度很快。Spring AI 解決了底層 LLM 調用這層，缺的正是上面那層 Agent OS。阿里官方在 Spring AI Alibaba Admin 項目裡做企業級 Agent 應用的最佳實踐，也積累了一定的社區認知。Java AI 工程的基礎設施層在 2025 年解決，自然往 Agent OS 這一層走，這是技術棧演化的順序。

### OryxOS 是什麼

把前面所有線收到一起，OryxOS 可以這樣定義。它是企業能完全掌控、Java 原生、私有可審計的統一 Agent 底座，裝在企業自己的 K8s、伺服器或物理機上，上面跑各種業務 Agent，共享一套渠道接入、模型路由、記憶系統、工具調用、安全審計。數據完全留在企業自己的基礎設施，不鎖任何雲生態。

業務方在上面配置 Agent（prompt、模型、Tool 列表、渠道綁定），寫 Tool（用 Java、Python、Shell 或任何語言，透過 MCP 協議暴露）。MCP（Model Context Protocol，模型上下文協議）是 Anthropic 在 2024 年 11 月提出的開放協議，把 LLM 和外部工具、數據源連起來，目前是 Agent 生態的事實標準。業務方不需要寫 Agent 後端代碼，只需要寫 Tool 實現和 Skill 配置。

### 錨在需求上，錨不住在概念上

OryxOS 用「Agent OS」這個框架來理解和構建自己，因為這個框架好用，五件事講得清，操作系統的類比有助於思考。但它把自己錨在背後那個不會變的需求上，錨不住在「Agent OS」這個詞上。錨在概念上，哪天這個詞被別的說法取代，或者這個中間層被上下層吸收，項目就失去了立足點。錨在需求上，無論技術概念怎麼演變，嚴格受監管企業要私有可控、要跟 Java 體系一致這件事都還在。OryxOS 把根扎在不變的東西上。

### 邊界，做 runtime，不做編排

OryxOS 有一條清晰的邊界。在分層上守住 runtime 這一層，不往上做編排。它站在編排平台和應用之下，做承載 Agent 跑起來的底座，但仍然是一個完整的 Agent OS，多 Agent 管理、多租戶、審計都在範圍內。

它提供的是 Channel（渠道）、LLM Provider（模型供應商抽象）、Memory（記憶）、Tool 註冊、Sandbox（沙箱）、多租戶、SSO、審計、可觀測性、Web 管理台。業務方在上面配置 Agent，Agent 跑起來。

它故意不做視覺化 workflow 編排、複雜任務分解、多 Agent 顯式協作。企業真需要複雜 workflow，可以用 Dify 這類編排平台跑在 OryxOS 之上，Dify 作為客戶端調 OryxOS 的 API。兩者是互補關係，競爭關係不存在。這條邊界讓 OryxOS 專注做好底座一件事。

### 安全，從第一天就設計

OpenClaw 的安全問題是結構性的。開放的、低門檻的第三方 skill 生態，加上默認寬鬆的權限和較弱的隔離，出事只是時間問題。OryxOS 既然定位嚴格受監管企業，安全必須是第一天就設計進去的東西，並且在幾件事上跟 OpenClaw 走相反的路。

Skill 和 Tool 的來源受控。不提供任何人上傳、任何 Agent 隨意拉取的開放 skill 市場，企業內的 Skill 和 Tool 要過註冊、審核、簽名、版本管理，來源可追溯。社區的優質 Skill 可以導入，但要先過企業自己的審查關。

最小權限。每個 Agent、每個 Tool 拿到的是顯式授予的最小集合，文件系統、網絡、shell 的訪問範圍默認收緊，按需放開。

沙箱隔離是強制的。Tool 在隔離環境裡執行，有明確的資源和能力邊界，多租戶之間完全隔離，一個租戶或 Agent 越界不會波及別人。

憑證不落明文。API key、token、企業系統的憑證不硬編碼、不明文存儲，走企業現有的密鑰管理（KMS、Vault 這類），使用全程可審計。

prompt injection（提示詞注入）和數據外泄要主動防禦。借鑑 Hermes 的做法，記憶寫入和工具輸入都過安全掃描，檢測注入和外泄模式，對 Agent 能訪問的數據範圍和能外發的目標做約束。

從頭到尾的審計是底座能力。誰、在什麼時候、讓哪個 Agent、調了什麼 Tool、訪問了什麼數據、產生了什麼結果，全程結構化留痕，可以接進企業現有的審計和 SIEM（安全信息與事件管理）系統。這正是 OpenClaw 和 Hermes 都缺、嚴格受監管企業必須有的東西。OryxOS 本身是 Java 和 Spring 實現，跑在企業自己的基礎設施上，能直接納入企業現有的代碼審計、安全掃描、合規過審流程。安全從架構裡長出來，不是事後加的一層殼。

### 未來，從單機到分佈式

路線圖也很清楚。當前版本做的是單機私有部署，一個實例裝在企業的一台伺服器或一個容器裡，跑一組 Agent，服務一個部門或一個場景。這是刻意的選擇，絕大多數企業落地 Agent 底座，都是先從一個場景跑通、跑穩開始，單機最簡單、最易接入、最容易納入現有運維和審計。架構上為未來留了方向。中期走向實例無狀態、狀態外置的分佈式部署，解決扛量、高可用和規模化治理。長遠圖景是分佈式 Agent 協作，讓跨部門、跨機器的 Agent 互相發現、委托、協作。方向先想清楚，是為了讓單機版本不堵死未來的路，複雜度留到真需要時再壓上來。
