# Provider 抽象

## Learning goal

看懂 Provider 只做選模、呼叫、轉換、審計，並能用顯式 name→ChatModel 映射與工具 schema 轉換實作一層薄介面。

## Steps

1. [[learn/geek-ai-agent/nodes/oryxos-provider/provider-frontdesk|什麼是 Provider：Agent 與 LLM 之間的前台]] — 前台定位、四件事與一件事不做，為什麼換模型只改配置
2. [[learn/geek-ai-agent/nodes/oryxos-provider/explicit-mapping-and-traps|動手前先想清楚：三個陷阱與顯式映射]] — 型別掃描陷阱、自動執行陷阱、未驗證依賴陷阱（after step 1）
3. [[learn/geek-ai-agent/nodes/oryxos-provider/two-layer-config-and-profile|兩層配置與 Profile 系統]] — 應用層＋Profile 層、ProfileLoader/Registry 與硬失敗驗證（after step 2）
4. [[learn/geek-ai-agent/nodes/oryxos-provider/chat-and-tool-schema|一次呼叫與工具 schema 轉換]] — chat 呼叫路徑與 ToolSchemaAdapter「只翻譯不執行」（after steps 2–3）
5. [[learn/geek-ai-agent/nodes/oryxos-provider/audit-and-acceptance|llm_calls 審計與驗收 Harness]] — day-one 雙向審計與 mock/integration 驗收（after step 4）

## Lesson

這個節點把 OryxOS 五大能力的第一個——「對接 LLM」——拆成一層刻意做薄的介面。主線一句話：Provider 是 Agent 與各家大模型之間的前台，它替上層 ReAct 循環吸收掉「不同廠商的 API 長得完全不一樣」這件事，但絕不替上層做任何它該自己做的決定。

沿著這條主線，節點先釘死 Provider 的職責邊界（選模、一次呼叫、schema 轉換、審計；工具執行權在 ToolExecutor），再處理動手前最容易被坑的三個陷阱——其中最致命的是「同型別的 ChatModel Bean 無法靠掃描區分」，因此「顯式 name→ChatModel 映射」成為首要設計原則。接著看兩層配置怎麼把「有哪些 provider」與「這個 Agent 用哪個模型」分開管理，並透過 ProfileLoader／ProfileRegistry 在啟動時驗證、索引。之後走一遍 ProviderService.chat 的真實呼叫路徑，理解工具 schema 為什麼是「只翻譯不執行」——模型想調工具時，Provider 只回傳「它想呼叫 X」的請求，真正執行權仍留在 ReAct 迴圈。最後是審計與驗收：llm_calls 表成功失敗都寫、手寫 schema，再用 mock ChatModel 的單元測試與一個 integration smoke 測試把前面每個陷阱都釘成回歸測試。

五步合起來回答同一個問題：怎麼在「換模型只是改配置」與「工具不被執行兩次」之間，找到一條只有十幾類物件、一次呼叫就能講完的薄介面。
