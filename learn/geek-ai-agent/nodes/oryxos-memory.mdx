# Memory

## Learning goal

能比較業界記憶方案（Mem0／MemGPT／Zep 等），說清短期 vs 長期、壓縮 vs 提煉，並實作 facade + 可插拔三後端。

## Steps

1. [[learn/geek-ai-agent/nodes/oryxos-memory/memory-why-stateless|為什麼 Agent 需要記憶：無狀態 LLM 與短期／長期記憶]] — LLM 每次呼叫無狀態、context window 有限且貴，記憶要在視窗之外管理；分清短期工作記憶與長期記憶（情節／語意／程序）
2. [[learn/geek-ai-agent/nodes/oryxos-memory/memory-compression-extraction|壓縮 vs 提煉：上下文壓縮、記憶壓縮與完整循環]] — 上下文壓縮把眼前對話變短、記憶壓縮把長期倉庫整理精簡；提煉決定品質，閉環把兩者串成一個系統（after step 1）
3. [[learn/geek-ai-agent/nodes/oryxos-memory/memory-industry-landscape|業界記憶方案盤點與 MemGPT／Mem0 解剖]] — 六個開源方案定位、MemGPT 記憶即 OS、Mem0 add 即消解、時序知識圖譜，以及自造 vs 集成的判斷錨（after step 2）
4. [[learn/geek-ai-agent/nodes/oryxos-memory/memory-interface-wall|介面牆與三層設計：MemoryService、四契約、信號驅動升級]] — 先釘門面與後端介面、三後端共守四契約、core／session／archival 三層、Agent 主動寫入、三個向量升級信號（after step 3）
5. [[learn/geek-ai-agent/nodes/oryxos-memory/memory-three-backends|可插拔三後端：Markdown／SQLite／Mem0]] — 三檔實作與定位，只改 memory.backend 就換後端、門面以上零改動（after step 4）
6. [[learn/geek-ai-agent/nodes/oryxos-memory/memory-tools-wiring-harness|記憶工具、Prompt 注入與契約測試]] — save_memory／recall_memory、PromptBuilder 注入、MEMORY.md vs USER.md，用一份參數化契約測試守住介面牆（after step 5）

## Lesson

Memory 是 Agent 三大能力（ReAct 會想、Tool 會做、Memory 記得住）裡的「記得」。它的存在理由很單純：LLM 每次呼叫都是無狀態的，歷史得由呼叫方自己塞回去；而 context window 又小又貴，塞不下全部過去。所以 Agent Memory 的本質，是**在有限視窗之外管理「記住」這件事**——短期（工作）記憶就是當前對話留在視窗裡的那一段，長期記憶則落地到視窗之外、需要時再檢索回來。

真正讓記憶可用的關鍵步驟是**提煉**：把冗長低訊號的原始對話，抽成結構化、精煉的記憶條目。提煉得好，檢索就有用；提煉得差，長期記憶只是垃圾場。這裡要分清兩個常被混談的概念——**上下文壓縮**縮短的是「眼前正在說的」（壓對話），**記憶壓縮**整理的是「長期倉庫裡已累積的」（合併去重、抽象化）。兩者一起構成記憶的完整閉環：對話中累積 → 壓縮＋提煉 → 寫入長期 → 定期整合 → 檢索並重新注入上下文。

OryxOS 的設計原則不是做最強的記憶系統，而是做**夠用、可控、能平滑長大**的那個：先把 `MemoryService` 門面這道「介面牆」釘死，實作只填最輕的一檔。階段一用檔案式 `MEMORY.md` 加 SQLite 會話記憶，借 MemGPT 的三層切成 core（常駐小塊）／session（當前會話）／archival（按需檢索）；寫入由 Agent 主動呼叫 `save_memory`，不做系統自動抽取。等出現三個真實信號——關鍵詞檢索開始漏掉同義記憶、歸檔量到數百上千、真的需要精準跨會話召回——再在門面之後換上向量檢索。換後端改的是門面以下，上層一行不動；這正是這道牆的價值。最後用一份跑在三檔上的參數化契約測試，把「介面不變、實作自由替換」變成自動化保證。
