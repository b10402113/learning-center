# Notify 出站

## Learning goal

能設計 NotifyChannelAdapter 介面與 Webhook 實作，理解 Agent 如何主動推送結果、以及如何擴到企業主流渠道。

## Steps

1. [[learn/geek-ai-agent/nodes/oryxos-notify/notify-why|為什麼需要 Notify：觸發斷裂與出站職責]] — 「到點自動」如何打破入站回應路徑，Notify 補上「結果送到哪」
2. [[learn/geek-ai-agent/nodes/oryxos-notify/interface-first-design|動手前先想清楚：介面先行與四個決策]] — 介面表達意圖、核心只做 webhook、安全留給 Sandbox、目的地放 Profile（after step 1）
3. [[learn/geek-ai-agent/nodes/oryxos-notify/writing-notify|程式碼怎麼寫：NotifyChannelAdapter、NotifyTarget、WebhookNotifyAdapter、NotifyTools]] — 四個類別與渠道中性的介面簽名（after step 2）
4. [[learn/geek-ai-agent/nodes/oryxos-notify/acceptance-security|驗收 harness 與安全順序：enforce 必須在 send 之前]] — 兩批測試與白名單防線的順序斷言（after step 3）
5. [[learn/geek-ai-agent/nodes/oryxos-notify/enterprise-channels|擴到企業主流渠道：場景、webhook 差異與延伸路徑]] — 依場景選渠道與三原則延伸路徑（after step 3）

## Lesson

Notify 是 OryxOS 的出站通道：前面所有模組都在回答「誰觸發 Agent、Agent 怎麼想、怎麼做」，Notify 回答最後一公里「跑完的結果怎麼主動送出去」。它有別於 CLI／Web Service 那樣的「人問機器答」——當觸發變成都市報表那類「到點自動」，就沒有請求方在等回應，Agent 必須自己決定往哪送、送什麼。整個節點的核心是一個**介面先行的插件模式**：訂出一個不含任何渠道概念的 `NotifyChannelAdapter` 介面，核心階段只給一份通用 webhook 的輕量實作，再把企業微信、飛書、釘釘、Slack 那些格式各異的主流渠道留在擴展階段補上。這樣一來，「推送一件訊息」這件被所有業務 Skill 重複需要的事，被收斂成一個統一動作，而不是每個 Skill 各自對接一套 webhook。

安全與擴展是這條主線的兩翼。安全上，Notify 不是新的豁免通道——webhook 目標域名同樣要過 Sandbox 的白名單，而且 `enforce` 必須在 `send` 之前，順序反了等於白名單被繞過，這是驗收 harness 裡最關鍵的一條斷言。擴展上，「所有 webhook」不等於「同一種 JSON 格式」：每家渠道的 webhook payload 都不同，對接要過建機器人、放環境變數、Profile 設定、域名白名單、實測五道手續；而遇到 payload 對不上的渠道，三原則決定走專用 adapter 還是 MCP。
