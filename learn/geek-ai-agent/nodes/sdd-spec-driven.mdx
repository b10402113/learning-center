# SDD：規格驅動開發

## Learning goal

理解 spec-as-source 與 SDD 的三種落地模式（Spec-Kit／OpenSpec／手作），並能判斷一個專案該不該用、用哪種。

## Steps

1. [[learn/geek-ai-agent/nodes/sdd-spec-driven/why-sdd|為什麼需要 SDD：vibe coding 的四個硬問題]] — 說出需求漂移、架構失控、回退困難、無法協作，以及為什麼要加一層結構化需求層
2. [[learn/geek-ai-agent/nodes/sdd-spec-driven/spec-as-source|spec-as-source：規格即源頭與三大支柱]] — 講清 spec → plan → tasks → code 的推導鏈與 constitution／閉環／analyze（after step 1）
3. [[learn/geek-ai-agent/nodes/sdd-spec-driven/spec-kit|Spec-Kit：四階段閉環與 6+3 命令]] — 掌握自動化模式的重武器與它的適用邊界（after step 2）
4. [[learn/geek-ai-agent/nodes/sdd-spec-driven/openspec|OpenSpec：delta-spec 與三態流程]] — 掌握增量模式與 brownfield-first 的差異化（after step 2）
5. [[learn/geek-ai-agent/nodes/sdd-spec-driven/choosing-sdd|選型：什麼情況用哪種 SDD]] — 用 greenfield／brownfield 與成熟度選模式，並知道何時根本不該用（after steps 3–4）

## Lesson

這個節點處理的是 AI 編程裡「想」的那一半。AI 把「做」（敲程式、生成實作）拿走了，卻把「想清楚要什麼」的責任整包丟回給人。你如果只是用自然語言跟 AI 一來一往地猜，遲早會撞上四個硬問題：專案跨多個 session 後需求漂移、程式碼庫在多次迭代後架構失控、出錯時不知道該退回哪個狀態、多人協作時各講各的。這些問題在小工具上不明顯，在中大型專案上就是致命傷。SDD（Spec-Driven Development，規格驅動開發）的解方，是在提示詞之上補一層結構化的需求層——把藏在腦中的隱性意圖，變成可審查、可共享、可被 AI 消化的顯性產物。

這層產物的核心叫 spec-as-source（規格即源頭）：spec 不是一份寫完就歸檔的需求文件，而是整個專案的源頭，plan、tasks、code 全部從它派生；spec 一改，下游全部重新生成。Spec-Kit 用「非協商的 constitution + 四階段閉環 + analyze 防漂移」把這件事做成一條帶門禁的流水線；OpenSpec 反過來，用 delta-spec（只描述這次改動的增量）與 Propose → Apply → Archive 三態流程，把 SDD 變輕、對既有專案友善。兩者哲學正好對立：一個像現代化的瀑布、主張嚴格上游設計，一個像工程化的敏捷、主張增量演進。

但工具不是重點——SDD 的核心是思考方法。真到選型時，你要判斷的是專案是 greenfield 還是 brownfield、規模多大、團隊多成熟、你自己的工程判斷力夠不夠，然後在重（Spec-Kit）、輕（OpenSpec delta）、極輕（不用工具、純 CLAUDE.md + Skill 的輕量手工模式）三種落地模式裡挑一種；有時候答案甚至是「這個專案根本不需要 SDD」。這條節點走完，你拿到的不是某個工具的語法，而是一套能反覆使用的判斷標準——先選 Spec-Kit 把範式練熟，再切 OpenSpec 感受增量風格，是這門課建議的路徑。
