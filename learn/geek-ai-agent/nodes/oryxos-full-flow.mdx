# 全流程串聯

## Learning goal

能把模組對表對賬成一條真能跑的主流程，找出五條典型縫隙，並驗證重啟恢復與多 Agent 並存。

2. [[learn/geek-ai-agent/nodes/oryxos-full-flow/five-integration-seams|五條典型縫隙與單一來源修法]] — 症狀在執行期、根因在交接處（after step 1）

4. [[learn/geek-ai-agent/nodes/oryxos-full-flow/scheduled-tasks-subsystem|定時任務子系統：定義、執行、持久化、管理]] — skill 定義、兩表持久化、四端點管理（after step 2）

## Lesson

前面每一節都在蓋一層樓：Provider 抽象、ReAct 迴圈、CLI、Notify、Tool、Memory、Sandbox、定時任務、Web Service。但單模組測試全綠，不等於這台機器能跑——縫隙從來長在兩個模組的交接處，而不是任何一個模組內部。這個節點就是「把零件裝成一台機器，並且證明它真的會動」。

上半場（第 27 節）驗的是**有人問、答得對**。方法叫對賬：先對表，確認每個模組承諾的對外能力都還在位；再用一句真的有代表性的對話（「今天北京天氣怎麼樣，穿什麼合適」）從入口走到出口，逐張表核對留下的痕跡——`sessions` 該有一條完整歷史，`llm_calls` 恰好兩筆，`tool_invocations` 恰好一筆，而 `MEMORY.md` 不該被動到。這裡的紀律是雙向的：「該有的要在」與「不該有的不能有」同樣重要，多一筆和少一筆一樣都是 bug。要讓「三面同源」可自動驗證，每條痕跡都得先有可查端點，所以補上列出會話的 `GET /api/v1/sessions`，並把管理台接上同一個引擎的第三個視角。

下半場（第 28 節）驗的是**沒人問也照樣幹活**：定時任務到點自己組一趟訊息、投進同一條 `AgentService` 入口，執行結果與狀態落進 SQLite，重啟後不失憶；同一實例上跑兩個不同的 Profile，工具、會話、排程三條邊界互不打架。最後把對賬固化成測試——一條進 gate、無需 key 的 mock 供應者鏈路，加一條真 key 的鏈路——讓「這台機器跑得穩」從讀日誌的體感，變成每次 `mvn verify` 都會回答的確定事實。
