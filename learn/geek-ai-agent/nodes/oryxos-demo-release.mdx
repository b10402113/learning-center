# Demo 與發布

## Learning goal

能從三個業務 Agent 的目錄差異（光桿 AGENT.md／帶子指令／帶腳本）看清插件化的威力，並完成 v0.1.0 打包與驗收。

## Steps

1. [[learn/geek-ai-agent/nodes/oryxos-demo-release/demo-bare-agent-weather|Demo 一：光桿 AGENT.md 的每日天氣 Agent]] — 一個光桿 AGENT.md 就能定義一個自跑 Agent，含三道環境閘門與「先推再看時鐘」的除錯順序
2. [[learn/geek-ai-agent/nodes/oryxos-demo-release/demo-sub-instruction-digest|Demo 二：目錄帶子指令的每日科技日報]] — 長篇規範放子指令、read_file 按需載入，長期記憶偏好讓日報天天把 AI／晶片排前面（after step 1）
3. [[learn/geek-ai-agent/nodes/oryxos-demo-release/demo-bundled-script-github|Demo 三：目錄帶腳本的每日 GitHub 日報]] — 確定性抓取寫成目錄腳本、shell 執行，子行程連網繞過網域白名單、信任轉移到作者（after steps 1–2）
4. [[learn/geek-ai-agent/nodes/oryxos-demo-release/base-agent-boundary|底座與 Agent 的分界]] — 前二十八節全是底座，業務 Agent 只是插上去的一個目錄；底座越厚、定義 Agent 越便宜（after step 3）
5. [[learn/geek-ai-agent/nodes/oryxos-demo-release/release-v0-1-0|發布 v0.1.0：打包、產物與可操作性驗收]] — fat JAR + .oryxos 工作區兩個產物，「乾淨機器 30 分鐘跑起兩個 Agent」才算可發（after step 3）
6. [[learn/geek-ai-agent/nodes/oryxos-demo-release/portable-workflow|帶得走的工作流、設計母題與後續路徑]] — 四步節奏、四條設計母題，以及「新增實作、不改介面」的擴展路徑（after steps 4–5）

## Lesson

這個節點是 OryxOS 第一階段的收尾：把前面二十八節累積的底座能力，一次變成「真的有人在用」的業務 Agent。三個 Demo 刻意挑了目錄貧富程度不同的三種形態——光桿的 AGENT.md、帶 skills 子指令的目錄、帶 scripts 腳本的目錄——來說明插件化的威力不是抽象口號，而是「加一個檔案就多一種能力」的具體落差。三者合起來，正好把 Provider、ReAct、CLI、Notify、Tool、Memory、Sandbox、排程與 Web 全部壓過一遍。

看穿三個 Demo 之後，真正的洞見是那張「底座與 Agent 的分界」圖：前二十八節做的全部是底座，業務 Agent 只出現在第二十九節之後，而且兩個 Demo Agent 加起來不到一百行文字、零行 Java。這個不成比例本身就是底座價值的度量——底座越厚，定義一個 Agent 就越便宜。發布 v0.1.0 則把「能用」升級成「別人也能用」：打包成單一 fat JAR 與可備份的 .oryxos 工作區，並以「乾淨機器三十分鐘從零跑起兩個 Agent」當作可操作性驗收門檻。

最後把眼光從這個專案移開：一趟走完，真正能帶去下一個專案的不是程式碼，而是每個模組重複四次的工作節奏（原理→動手前想清楚→與 AI 實作→驗證並講解程式碼）與四條設計母題。後續每一項擴展都被設計成「新增一個實作、不改介面」，並由具體訊號觸發，而不是靠「大家都在做」的直覺。
