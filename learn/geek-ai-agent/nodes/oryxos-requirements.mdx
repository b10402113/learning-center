4. [[learn/geek-ai-agent/nodes/oryxos-requirements/design-goals-and-scenarios|四個設計目標與三個典型場景]] — 統一／私有／易接入／可觀測與場景樣貌（after step 2）

## Lesson

需求文件是整個 OryxOS 專案的錨：它決定「要蓋什麼」，技術方案決定「怎麼蓋」，AI 編程指南決定「怎麼餵給 AI 蓋」。這個節點把那份需求文件壓成一條可複述的主線。

主線的第一句是定位：OryxOS 是裝在企業自己 K8s／伺服器上的 Agent OS，向上給各種業務 Agent 一個統一 runtime，向下接模型、渠道、工具、記憶、身份與審計。它不是「一個 Agent」，而是「跑一群 Agent 的作業系統」——這條界線決定了後面每個模組的存在理由。第二句是交付方式：核心階段只用 4 週 × 3 小時蓋出最短可跑的 runtime kernel（五大能力），多租戶、SSO、審計、工具治理這些讓它「真企業級」的治理層放到擴展階段。先證明引擎能跑，再證明它敢進企業。

接著把五個能力拆開看：Provider 管模型自由、ReAct 是心跳、Memory 給連續性、Tool 是行動邊界、Web Service 是對外接口。它們不是五個獨立模組，而是互相供養的一條鏈——少了 Provider 迴圈沒得想，少了 Tool 迴圈只能動嘴，少了 Memory 每次都失憶。術語表（Profile、Session、Channel、Tool Policy、Skill、Bootstrap、Workspace）把這條鏈講清楚，九個 Maven 模組則把它落成程式碼骨架。

最後用兩把尺收尾：一把是範圍尺（核心／擴展／社區），一把是驗收尺（功能、性能、可運維、場景四層，加五個必過 Demo 與性能／可靠性／安全硬指標）。這兩個清單會在後續每個模組節點被反覆回頭參照——當你不確定某個功能該不該做、做到什麼程度，答案幾乎都在這裡。
