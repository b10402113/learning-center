# CLI 與 Session

## Learning goal

看懂 CLI 作為薄入口的輕/重命令切分，以及 Session 的持久化與冪等 session id 設計。

## Steps

1. [[learn/geek-ai-agent/nodes/oryxos-cli-session/cli-overview|CLI 是什麼：薄入口與十二個子命令]] — 說出 CLI 定位與三個命令族群
2. [[learn/geek-ai-agent/nodes/oryxos-cli-session/cli-command-split|動手前的四個決定：輕/重命令切分與 JPA 掃描坑]] — 複述四個決定並能解釋掃描失敗（after step 1）
3. [[learn/geek-ai-agent/nodes/oryxos-cli-session/session-identity|Session：冪等 session id 的單一真相]] — 講清三元組與單一拼裝點（after step 1）
4. [[learn/geek-ai-agent/nodes/oryxos-cli-session/session-persistence-verify|Session 持久化與驗收 harness]] — 講清 JSON 持久化與兩個測試的意義（after steps 2–3）

## Lesson

CLI 是 OryxOS 打到手上的第一塊「真的能摸到」的表面：跑完 Provider 與 ReAct 之後，這一節讓你在終端機裡真的跟自己的 Agent 對話。但這一步真正要教你的不是「怎麼寫一份 main」，而是兩個會貫穿整個底座的重複設計母題。

第一個母題是「入口要薄」。CLI 是門，不是工人——12 個子命令只是把訊息從標準輸入接進來、呼叫同一個引擎，引擎與三大能力塊才是幹活的。這個薄薄的入口還必須在意啟動延遲：`init`、`profile list` 這類純檔案命令不該為了查一個列表而啟動整個 Spring 容器，所以 OryxOS 把命令切成輕、重兩類，重命令才開 Spring。第二個母題是「狀態要有單一真相」。Agent 要記得對話，就得有 Session；而 Session 的身份是一個 channel+user+profile 三元組，拼裝只能發生在 SessionManager 內部一處——任何入口自己拼 session id，就會讓同一個用戶裂成兩段互相不認識的歷史。

把這兩個母題講透，就是本節的四步：1) 看清 CLI 的定位與 12 個子命令怎麼分組；2) 動手前的四個決定，尤其是輕重切分帶出來的 JPA 掃描坑；3) Session 的冪等身份設計——這是後面 Web Service 與排程入口都會複用的單一規則；4) Session 怎麼用 JSON 存進 SQLite、重啟後怎麼恢復，以及 SessionManagerTest／SessionRepositoryTest 各自釘住了哪個契約。
