# 存儲與元數據

## Learning goal

能設計 StoragePlugin 與 Redis key 結構（避開 big-key），並在 ZK／etcd／Consul 間選型與定義 etcd key space。

## Steps

1. [[learn/geek-ai-agent/nodes/when-storage-metadata/storage-contract|為什麼訊息要先落地：StoragePlugin 契約]] — 落地不變量與五方法介面（deep）
2. [[learn/geek-ai-agent/nodes/when-storage-metadata/redis-key-design|Redis key 結構與避開 big-key]] — 三類 key、TTL 規則與拆小 key 的理由（after step 1, deep）
3. [[learn/geek-ai-agent/nodes/when-storage-metadata/persist-order-and-transition|寫入順序、原子轉移與重啟恢復]] — 先 Redis 後記憶體的順序、CAS 搶投遞權、先載後註冊（after step 2, deep）
4. [[learn/geek-ai-agent/nodes/when-storage-metadata/metadata-vs-data|元數據與訊息資料的分工：ZK、etcd、Consul 選型]] — 小量強一致 vs 大量求快，以及選 etcd 的理由（after step 1, deep）
5. [[learn/geek-ai-agent/nodes/when-storage-metadata/etcd-key-space|etcd key space 與心跳約定]] — 四類 key、生命週期、Lease 6 秒／續約 2 秒（after step 4, deep）

## Lesson

When 要把兩條資料線分開處理：一頭是「量大、短命、只求快」的延遲訊息，一頭是「量小、要強一致、關心誰還活著」的叢集元數據。這個節點先把訊息落地這件事講清楚——延遲訊息在進記憶體時間輪之前必須先寫進儲存，否則節點一重啟就整批消失；落地用的是 StoragePlugin 這個只依賴介面的插件，第一個實作是 Redis，key 的拆法刻意做到「很多個小 key」以避開 big-key。

接著把鏡頭轉到協調平面：訊息資料放 Redis，元數據放另一種儲存。ZK、etcd、Consul 三套都能做協調，但 etcd 的 Put／Get／Watch／Lease 原語最貼合這個專案，維運負擔也最輕，因此選它。最後把 etcd 的 key space 與 Lease 心跳約定釘死，讓後面註冊、選舉、故障偵測的模組都照同一套契約走。
