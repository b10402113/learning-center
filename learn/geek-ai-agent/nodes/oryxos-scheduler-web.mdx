# 定時任務與 Web Service

## Learning goal

理解定時任務作為第三個觸發源與 Web Service 如何把引擎變成 REST 介面，並掌握 10 端點與管理平台。

## Steps

1. [[learn/geek-ai-agent/nodes/oryxos-scheduler-web/scheduler-third-trigger|定時任務：第三個觸發源]] — 人推與時鐘推的對比，引擎零改動
2. [[learn/geek-ai-agent/nodes/oryxos-scheduler-web/scheduler-thin-layer-traps|動手前先想清楚：薄排程層與四個陷阱]] — 五件事的職責邊界與四個陷阱（after step 1）
3. [[learn/geek-ai-agent/nodes/oryxos-scheduler-web/writing-agent-scheduler|AgentScheduler 實作與驗收：動態註冊、本地鎖、第二次進入]] — registerAll／runOnce、鎖與「第二次進入」斷言（after step 2）
4. [[learn/geek-ai-agent/nodes/oryxos-scheduler-web/web-service-showcase|Web Service：10 端點把引擎變成 REST 介面]] — 六控制器、兩條整合路徑、admin 純消費端（after step 1）
5. [[learn/geek-ai-agent/nodes/oryxos-scheduler-web/web-service-design-and-verify|動手前先想清楚到驗收：五個決定與統一異常出口]] — 薄控制器、錯誤碼、內部細節不漏 500（after steps 2, 4）

## Lesson

這一節把 OryxOS 底座的最後兩塊外部介面補齊：一個來自時鐘，一個來自 HTTP。定時任務不是新能力，而是第三個觸發源——到點時由系統自己組裝一趟訊息、投進與 CLI／Web 完全同一條 `AgentService` 入口，剩餘的 ReAct、Provider、工具執行與審計一概不動。Web Service 則把引擎變成可供任何業務系統呼叫的 REST 表面：10 個端點、6 個控制器，後台管理平台只消費這 10 個端點，本身就證明了這組 API 夠完整。兩者背後的紀律是同一句：引擎保持穩定，新增入口不碰核心。
