# When 調研與需求

## Learning goal

能說明延遲投遞的真實需求與現況缺口，並界定 When 的目標/非目標、AI 編程約束、3 週 MVP 與驗收標準。

## Steps

1. [[learn/geek-ai-agent/nodes/when-spec/delay-demand-and-gap|延遲投遞的需求與現況缺口]] — 從場景與既有方案找出缺口
2. [[learn/geek-ai-agent/nodes/when-spec/delay-algorithm-landscape|延遲投遞的底層演算法與選型]] — 六種實作路徑與六個選型維度（after step 1）
3. [[learn/geek-ai-agent/nodes/when-spec/when-positioning-and-nongoals|When 的定位與非目標]] — When 是什麼、雙重定位與五大目標（after steps 1–2）
4. [[learn/geek-ai-agent/nodes/when-spec/ai-programming-constraints|AI 編程約束：讓 AI 寫 90%]] — 硬約束、可量測與強制 review（after step 3）
5. [[learn/geek-ai-agent/nodes/when-spec/mvp-and-acceptance|三週 MVP 與驗收標準]] — 做/不做清單、非功能指標與七項驗收（after steps 3–4）

## Lesson

When 是一個把「在未來某一刻精確投遞一則訊息」這件事獨立出來的分散式元件。這個節點不急著寫程式，而是先把兩份文件讀懂：業界調研回答「這件事為什麼值得做、現有方案卡在哪」，需求文件回答「When 到底要做什麼、不做什麼、三週要交出什麼、憑什麼算過關」。

五個步驟沿著一條決策鏈走。先看需求場景與現有方案的共同缺口——延遲投遞的需求真實、廣泛、長期，但現有做法不是綁死某個中介軟體，就是停留在 SDK 或託管服務的形態，沒有一個通用、獨立、被廣泛採用的標準。接著看底層演算法景觀：六種實作路徑各有取捨，沒有任何一種同時滿足寫入吞吐、調度精度、時間跨度、記憶體、多副本與實作簡單，選型本質上是取捨。有了這個缺口與取捨的判斷，才能理解 When 的定位與非目標——它選擇做一個獨立的延遲投遞服務，並且刻意不當任務調度器、不當訊息佇列、不當 worker 框架。

最後兩步把定位收斂成可交付的約束：AI 編程硬約束要求核心程式碼 ≥90% 由 AI 撰寫且必須真 review，這不是噱頭，而是把「交付一個專案」同時當成「驗證一套 AI 工作流」；三週 MVP 與七項驗收則把「做什麼、怎麼算完成」寫成可檢查的門檻。走完這五步，你手上就有了整條 When 交付線的驗收尺規。
