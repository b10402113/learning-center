30% 現實與自動化邊界

Step 3/5 · 工作流設計與自動化邊界

學習目標

用「30% 提速是頂級水平」的現實與成功自動化案例的五個共同條件，判斷一個具體任務 AI 能不能自動做。

行銷話術與真實數據的落差

廠商說「十倍生產力」，但真實生產環境的數據是：開發時間縮短 30%，已經算頂級水平。這個落差不是誰在說謊，而是有系統性的來源——顧問賣的是願景，產品商賣的是工具，沒有人賣「現實」。所以判斷自動化邊界時，第一個動作是過濾資訊源，只採信中立、可複核的數據。

更關鍵的是：「AI 能自主寫完大軟體」目前仍停在展示階段。真正的瓶頸不是能力（模型能不能寫），而是可靠性（寫出來的東西能不能穩定地被信任）。企業要求數個 9 的可用性，而 AI 產出是機率性的——這兩件事之間有一道很深的溝。

兩邊的證據都要看

要校準期待，不能只看樂觀案例或只看翻車案例。把兩邊並列，才會看到真實的位置。

樂觀面懷疑面
Claude Code 已占某公司 4% commitsAnthropic 自己也發生過：誤刪遠端 git 分支、上傳憑證、跑生產 DB migration
Spotify 自 12 月起無手寫程式碼GitHub Issue #42796：agent 會退化成「又懶又錯」
C 編譯器用約 2000 個 session 做出來研究整理 3800+ 個 agent 問題、SitePoint 收錄的失敗模式

把兩邊合起來，得出一個校準後的結論：AI 無法從零自主建出大型新系統，但可以穩定完成「有界的中大型任務」。瓶頸是可靠性，不是能力。

Bun 案例的真正啟示

回到那個六天 96 萬行的案例，把它拆開，會發現它其實不具備「從零自主」的條件：

  • 它是遷移，不是從零：原本的 Zig 程式與測試完整存在，等於有一套現成的驗證標準。
  • 先做了深度工程準備：300 條翻譯規則寫進 PORTING.md，還先抽了智慧指標的抽象層。
  • 人一直在迴圈裡：Sumner 決定開始、停止、合併的節奏，不是放手不管。
  • 99.8% 測試通過不等於可上線：測試只能證明「有 bug 存在」，不能證明「沒有 bug」。第二個 PR 就被以「AI 垃圾」關掉，後續還需 6–12 個月的生產驗證。
  • 它是 Anthropic 自己的 dogfooding：示範場的條件無法直接搬到一般企業。

這個案例的價值不在於「AI 好強」，而在於它精準示範了人+AI 協作的天花板長什麼樣，以及該怎麼誠實地讀它。

成功自動化案例的五個共同條件

把所有「真的自動化成功」的案例放在一起，會發現它們共享同一組條件：

條件為什麼重要
範圍清楚任務邊界明確，AI 不必猜要做多廣
可驗證有測試或明確成功標準，對錯能被機械判定
上下文有限不需要跨越巨大且分散的知識才能做對
不是從零有既有程式、範例或參考實作可以對照
有參考實作有正確答案的樣本，AI 是「照著改」而非「憑空想」

這五個條件就是一把判斷尺：一個任務符合越多，越能交給 AI 自動；越少，就越需要人介入、把規格與驗證設計得更嚴。

企業「全流程 AI 化」為什麼頻頻失敗

企業導入最常見的失敗，是把系統問題當成工具問題。買了工具、發了帳號，卻沒有打通階段之間的資訊流，於是 AI 在需求端拿到的東西，到開發端就斷了。即使是 McKinsey 的四級模型，多數企業也只到第二級，而第四級的願景仍然是「AI 晚上跑、人白天判斷」——不是無人化。

企業內部 AI 知識庫也常失敗，因為四個缺口會相乘而不是相加：文件覆蓋率（常低於 50%）、文件品質、檢索能力、使用者能力。缺一個，整體效果就大打折扣（實際常落在約 24%）。共識因此是：砍掉「全流程」的野心，聚焦 1–2 個真實痛點，用真實指標衡量，接受 5–10 年的時間尺度。

判斷界線的口訣：範圍清楚、可驗證、上下文有限、不是從零、有參考實作——符合這些，才輪到 AI 自動；不符，就是人的判斷要進場的地方。
