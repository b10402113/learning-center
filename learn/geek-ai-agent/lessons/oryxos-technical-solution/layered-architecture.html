四層架構與五大能力的互相供養

Step 2/5 · OryxOS 技術方案

學習目標

能畫出 access／engine／capability／foundation 四層，並說明五大能力如何各自供養 ReAct 引擎、又如何在兩端被暴露出去。

把一個作業系統拆成四層

七個決策講完「選哪條路」，接著就要回答「整個東西長什麼樣」。OryxOS 是一個單體（monolith）的 Spring Boot 應用——不是微服務，而是一個程式，內部再分成四層。每層只做自己那一段，並只透過介面跟上下層說話。

層放什麼一句話角色
access（接入層）CLI Channel、Web REST API外界從哪裡進來
engine（引擎層）ReActLoop、PromptBuilder、ToolExecutorAgent 怎麼想與動
capability（能力層）Provider、Memory、Tool引擎能用的三種資源
foundation（基礎層）Profile／Bootstrap／Skill 載入、Session 儲存、SQLite、config/secrets一切運轉的地基

注意兩個關鍵設計：接入層有兩個入口（CLI 與 Web），但它們餵給的是同一個引擎；而能力層只有三個成員（Provider、Memory、Tool），並不含 ReAct——因為 ReAct 是引擎本身，是「使用者」，不是「被使用的資源」。

五大能力怎麼互相供養

需求文件裡的五大能力是 Provider、ReAct、Memory、Tool、Web Service。到了技術方案，它們的關係被講得更精確：ReAct 是引擎，另外三個是餵給引擎的資源，Web Service 是把引擎能力開放出去的出口。

用一句話概括：Provider／Memory／Tool 供養 ReAct 引擎；引擎的能力再透過 CLI 與 Web Service 暴露。

  • Provider 讓迴圈「有得想」——沒有它，模型呼叫無從發生。
  • Memory 讓每一輪「不必從頭」——它給迴圈上下文。
  • Tool 讓迴圈「能動手」——它給迴圈執行力。
  • ReAct 把上面三者串成一個會自己迭代的過程。
  • Web Service 把整個過程包成 REST，讓外部系統能叫它。

這個視角很重要：五大能力不是五個平行模組，而是一條有方向的鏈。缺任何一環，Agent 都會退化——少了 Tool 只能動嘴，少了 Memory 每次失憶，少了 Provider 就沒有腦。

資料怎麼流過這四層

把一輪對話攤開來看，四層各司其職：

使用者輸入
  → [access] CLI 或 Web 收到請求，建立 Session
  → [engine] ReActLoop 啟動一輪
      → [capability] MemoryService 給歷史與長期記憶
      → [engine] PromptBuilder 組裝 prompt
      → [capability] Provider 呼叫模型
      → [capability] ToolExecutor 執行工具（含沙箱檢查）
      → [engine] 把結果附加回上下文，再問一次模型
  → [foundation] Session、審計表寫入 SQLite
  → [access] 回覆使用者

這就是「四層架構」真正的作用：把「進來的路」「想事情的路」「能用的資源」「記得住的地基」切乾淨。切乾淨之後，擴展只需要動邊緣——例如新增一個企業 IM 渠道，只是多一個接入層的 adapter，呼叫既有的 Agent API，完全不用碰引擎與能力層。

為什麼單體反而是正確答案

聽到「作業系統」很容易想像成微服務大軍，但核心階段的 OryxOS 刻意選單體：一個 JAR、一個行程、四層清楚切開。理由和七個決策一脈相承——分散式會帶來網路、協調、部署的複雜度，而核心階段要的是最短可跑。單體不是妥協，而是把「先讓引擎正確地跑起來」放在「先讓它分散」前面。

而四層架構確保了單體不會變成大泥球：層與層之間靠介面，所以未來要拆模組、加渠道、加工具，都有乾淨的接縫可切。
