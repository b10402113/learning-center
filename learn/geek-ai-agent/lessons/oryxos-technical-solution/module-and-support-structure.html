九個 Maven 模組與支撐層

Step 4/5 · OryxOS 技術方案

學習目標

能列出九個 Maven 模組與依賴方向，並說明 Profile、ContextLoader、Channel、三種運行模式、CLI 與 ConfigLoader 在支撐層的角色。

從架構到工程：模組怎麼切

四層架構是心智模型，到了工程上要落成實際的 Maven 模組。OryxOS 切成九個模組，其中五個對應core、四個是支撐：

類別模組職責
核心能力oryxos-provider對接 LLM
oryxos-coreReAct 引擎與所有抽象（大家都在依賴它）
oryxos-memory記憶
oryxos-tool工具與沙箱
oryxos-web對外服務
支撐oryxos-boot啟動與組裝
oryxos-cliPicocli 命令列
oryxos-storage持久化
oryxos-channel-cliCLI 渠道

依賴方向是刻意設計的：所有模組都依賴 oryxos-core（引擎與介面定義都在那裡），再由 oryxos-boot 組裝成一個可執行 JAR。Provider、Memory、Tool 都只透過介面被引擎使用，所以未來要新增渠道或工具，只需要多一個模組，不需要改動 core。這正是四層架構留出來的接縫。

支撐層一：工作區初始化與 Profile

oryxos init 會建立一個工作區 .oryxos/，內容包括：profiles/、memory/MEMORY.md、skills/、mcp_servers.yaml、sessions/、logs/、Bootstrap 檔（AGENTS.md／SOUL.md／USER.md）以及 oryxos.db，並寫入預設模板與一個預設 Profile。

Profile 是 OryxOS 的「設定單元」。ProfileLoader 把 YAML 解析成 ProfileRegistry，並在啟動時驗證：provider 是否存在、引用的 tool 是否已註冊、channel 是否支援、bootstrap 檔是否存在。驗證不通過只記 log、不阻擋啟動——避免一個壞 Profile 讓整個系統起不來。

多個 Profile 可以並存，各自有不同的身份、工具、技能與渠道。這就是核心階段「最小可用的作業系統」：同一套引擎，掛不同設定，跑不同 Agent。

支撐層二：ContextLoader 與 Channel

ContextLoader 統一載入兩類東西：Bootstrap（AGENTS.md／SOUL.md／USER.md）與 Skill（SKILL.md）。之所以合併，是因為兩者本質相同——都是要注入 system prompt 的 markdown。而且它每次組 prompt 都重新載入、不快取，跟 Memory 的處理一致。這是一個重要的架構修正：SKILL.md 屬於 ContextLoader，而不是 Tool。

Channel 負責「訊息從哪來」。核心只有 CliChannel（oryxos chat，用 stdin/stdout，綁定當前 Session）。企業 IM（企業微信、飛書、釘釘、Slack）留到擴展階段，屆時是寫一個 Channel Adapter，呼叫 Web Service 的 Agent API——HTTP 接入屬於 Web Service，不屬於 Channel。

支撐層三：三種運行模式

同一個核心，有三個入口：

模式命令用途
互動oryxos chat終端機一問一答
服務oryxos serve啟動 Web Service
閘道oryxos gateway常駐守護，同時掛多個渠道

三者共用同一份 Profile 設定與 Session 儲存，差別只在接入層。這再次印證了分層的價值：核心完全不用知道自己被哪個入口喚醒。

支撐層四：CLI 與 ConfigLoader

CLI 用 Picocli 實作，主類別 OryxOsCli 註冊 12 個子命令（init／status／chat／serve／gateway／profile 系列／provider list／tool list／session list）。一個巧思是：不需要 Spring context 的命令（例如 init、profile list）直接執行，跳過啟動 Spring 的 2–4 秒，讓常用操作瞬間回應。

ConfigLoader 統一載入 LLM API key、provider 憑證、MCP 憑證。核心從環境變數或獨立的本地設定檔讀取，Profile 裡用 ${ENV_VAR} 佔位；載入時驗證必填與格式，錯誤要講清楚。完整的加密、輪替、KMS（金鑰管理服務）留到擴展階段——但這個模組必須從第一天就存在，因為憑證載入跟審計一樣，是企業級的底線。

為什麼是九個，而不是更多或更少

模組數量的答案是架構推出來的：五個能力各給一個模組，加上啟動、命令列、儲存、渠道四個支撐。這個切法讓每個模組有單一職責，又不會切得太碎而互相糾纏。當你在實作階段不確定某段程式該放哪個模組時，回頭看這張表通常就有答案——而如果答案是「不知道放哪」，往往代表它其實屬於 oryxos-core 的抽象。
