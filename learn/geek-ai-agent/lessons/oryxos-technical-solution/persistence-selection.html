持久化選型：SQLite、MEMORY.md 與檔案系統

Step 5/5 · OryxOS 技術方案

學習目標

能解釋為什麼核心用 SQLite + MEMORY.md 而不用向量庫，以及三條升級路徑與各自的代價。

資料放哪裡：三個儲存目的地

一個 Agent 系統會產生很多狀態。OryxOS 的核心只用三種儲存，各管一類資料：

儲存放什麼選它的理由
SQLite（+ Spring Data JPA）會話、工具呼叫、模型呼叫紀錄單檔、免外部行程、關係查詢
MEMORY.md長期記憶人可讀、可手改、LLM 可直接解讀
檔案系統Profile、Bootstrap、Skill、MCP 設定、日誌使用者要維護、要能 git 與備份

為什麼核心不用向量資料庫

講到「長期記憶」，直覺會想到向量資料庫（vector database）——把文字轉成向量，做語義檢索。但核心階段的 OryxOS 明確不用，理由是四個選項在當下都不划算：

  • LanceDB：Java 端的本地嵌入（embedding）能力還沒就緒。
  • Qdrant／Chroma／Milvus：都需要額外跑一個外部行程，破壞「單一可執行 JAR」。
  • pgvector：需要外部 PostgreSQL，同樣引入依賴。
  • JVector：嵌入式可行，但當時尚未被驗證。

於是核心改用最笨但可靠的方法：整份 MEMORY.md 注入 prompt + 關鍵字召回。這不是否定向量檢索，而是把「更聰明的檢索」推遲到擴展階段，並在介面上先預留。這正是前面那個共同模式：核心留主幹，介面先留好。

三張表：SQLite 到底存什麼

關係型資料庫裡有三張表：

  • sessions——會話的 metadata 與 JSON 格式的歷史。
  • tool_invocations——每一次工具呼叫。
  • llm_calls——每一次模型呼叫（provider、模型、tokens）。

後兩張是審計表，呼應「第一天就寫」的決策：即使核心階段還沒有查詢它們的端點，也先開始記錄。

這裡有一個很實際的工程風險要記住：SQLite 的 ALTER TABLE 能力很弱，而 Hibernate 的 ddl-auto=update 對 schema 變更並不可靠。所以正式做法是手寫遷移腳本，或引入 Flyway／Liquibase。這是一個「看起來節省、其實會踩雷」的典型，越早釘死越好。

為什麼有些資料留在檔案系統

Profile YAML、Bootstrap 檔、MEMORY.md、SKILL.md、MCP 設定、日誌——這些都放在檔案系統，不進資料庫。判斷標準是：使用者需要看見、編輯、版控或備份的東西，適合檔案系統；系統自己產生、需要查詢的狀態，適合資料庫。

把 MEMORY.md 留在檔案系統尤其關鍵：使用者可以直接打開、讀懂、手動修正 Agent 的記憶。這帶來資料庫給不了的透明感與可控制感——對一個企業要「敢用」的 Agent 底座來說，這不是小事。

三條升級路徑

當記憶量成長到關鍵字檢索不夠用時，介面已經預留好，可以走三條路之一：

路徑做法代價
A等 LanceDB GA，用本地嵌入需等成熟度
BPostgreSQL + pgvector引入外部資料庫
CJVector 嵌入式生態未經大規模驗證

三條路都不必改動上層：這就是「介面先留好」的回報。

效能與可擴展性

核心階段的效能數字有明確理由支撐：

  • 虛擬執行緒承載高併發，只需少量作業系統執行緒。
  • 1000 個 sessions 約 50MB——記憶體不是瓶頸。
  • MEMORY.md 每次重讀約 1–2ms，所以「不快取、每輪重讀」是可接受的取捨。
  • 啟動約 2–4 秒——靠 CLI 拆分命令緩解；未來可用 GraalVM 原生映像壓到 100ms 以下。
  • SQLite 一開始每次都寫，若真成為瓶頸再加批次。

這些數字不是拍腦袋的樂觀，而是把「為什麼這個取捨在核心階段成立」量化出來。當你之後重讀這份技術方案，遇到任何「為什麼不做得更好」的疑問，多半都能在這一串數字裡找到答案：不是做不到，而是現在做不划算。
