七大關鍵技術決策

Step 1/5 · OryxOS 技術方案

學習目標

能說出 OryxOS 的七個關鍵技術決策，並解釋每一個決策擋掉的是什麼風險。

為什麼技術方案要從「決策」開始

需求文件說「要蓋什麼」，技術方案說「怎麼蓋」。蓋法有無數種，但其中有七個岔路口，一旦走錯，後面再怎麼補救都會付雙倍代價。技術方案的第一段不是架構圖，而是先把這七個選擇釘死——每一個都在回答同一句話：「這裡很容易走偏，我們選哪條、為什麼。」

先看整體技術棧，它是這些決策的落地材料：JDK 21 + Spring Boot 3.x，用 Spring AI Alibaba 呼叫模型，自己手寫 ReAct loop，Spring MVC 對外，Picocli 做 CLI，SQLite 做關聯式儲存，最後打包成單一可執行 JAR。一句話記法：JDK 21 + Spring Boot 3.x + Spring AI Alibaba + 自寫 ReAct + SQLite + Picocli。

決策一：自己手寫 ReAct loop，不用框架的 Agent 抽象

ReAct（Reason + Act，推理與行動交錯）是整個系統的心跳。市面上有現成的 Agent 框架抽象可以直接用，但 OryxOS 選擇自己寫——因為這段迴圈只有幾十行，而自己寫才能完全掌握它「什麼時候想、什麼時候動手、每輪帶了什麼上下文」。

框架黑盒最大的問題不是效能，而是不可觀測：你不知道它內部替你做了哪些決定，出錯時也無法沿著每一輪的 Reason / Act / Observe 去追。手寫這幾十行，換來的是可除錯、可審計，以及對整個 Agent 行為的完整理解。

決策二：只用 Spring AI 的一半，並關掉自動工具執行

這是七個決策裡最容易寫錯的一個。Spring AI 提供的不只是「呼叫模型」，它還能自動幫你執行工具呼叫（function calling）。聽起來很方便，但如果同時保留了這個自動執行，又在前面的 ReAct loop 裡自己執行一次工具，結果就是同一個工具被呼叫兩次。

所以 OryxOS 只用 Spring AI 的兩塊：Provider 抽象（接各家模型）與 schema 生成（把工具描述轉成模型看得懂的格式），然後關閉自動工具執行。工具「什麼時候執行」永遠由自己的 ReAct loop 決定。

決策三：同步阻塞 + 虛擬執行緒

呼叫模型是 I/O 密集工作，會等待。傳統上有兩條路：寫 reactive（反應式）非阻塞程式，或寫同步阻塞程式。OryxOS 選了後者，因為同步程式碼好讀、好除錯、好維護。

但同步的傳統缺點是「一條執行緒卡在等待」。JDK 21 的虛擬執行緒（virtual thread）解決了這點：可以在少數作業系統執行緒上掛起成千上萬條虛擬執行緒，讓同步寫法也能承載高併發。於是「好寫」與「能撐併發」不再二選一。

決策四：@Tool 註解 + OryxTool 抽象

工具可能來自三個地方：內建工具、Spring AI 的 @Tool 註解方法、以及外部的 MCP（Model Context Protocol，模型上下文協議）server。來源不同，格式各異。

OryxOS 用一層 OryxTool 抽象把它們全部包成同一個介面。這樣 ReAct loop 在呼叫工具時，完全不需要知道工具從哪來——它只看得到「一個有名字、有描述、有輸入 schema、能執行」的物件。

決策五：Spring MVC + 虛擬執行緒

對外服務沒有選更新的 WebFlux，而是選成熟的 Spring MVC，再搭配虛擬執行緒。理由和決策三一致：MVC 的同步心智模型簡單，虛擬執行緒補上併發能力，團隊不需要為了非阻塞而改寫整個程式風格。

決策六：路徑／模式白名單沙箱，不用 SecurityManager

Agent 能讀檔、跑指令、打 HTTP，安全邊界不能沒有。傳統 Java 會想到 SecurityManager，但它在 JDK 21 已經被停用、不再可用。於是 OryxOS 改用應用層白名單：路徑白名單、指令白名單、網域白名單，三類檢查都放在工具真正執行之前。這也呼應決策四——檢查點統一掛在 OryxTool 的執行路徑上。

決策七：SQLite + MEMORY.md，且第一天就寫審計表

儲存不做向量資料庫，而是SQLite + MEMORY.md（下一節的持久化選型會詳談理由）。這個決策的重點其實在後半句：第一天就寫審計表。

工具呼叫寫進 tool_invocations，模型呼叫寫進 llm_calls。即使核心階段還沒有查詢這些表的端點，也必須先開始記錄——因為可審計性是企業級 Agent 的底線，而且事後補記會永遠缺資料。這和決策一是同一個價值：讓系統的每一步都留下痕跡。

七個決策其實在保護同一件事

把它們排在一起看，會發現它們都指向「核心階段要最短可跑」這個目標，並各自擋掉一種會讓專案失控的風險：

決策擋掉的風險
自寫 ReAct黑盒不可觀測、無法除錯
只用半個 Spring AI工具被重複執行的隱藏行為
同步 + 虛擬執行緒為併發而犧牲可讀性
@Tool + OryxTool工具來源外洩到迴圈
Spring MVC整個 Web 層被迫改寫
白名單沙箱Agent 越權存取資源
SQLite + 第一天審計不可審計、事後補不回來

這七條是後面每一步的護欄。之後談架構、談模組、談持久化時，凡是看到「為什麼要這樣切」，答案幾乎都會回到這裡。
