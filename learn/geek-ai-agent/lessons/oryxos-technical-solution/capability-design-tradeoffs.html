五大能力的設計取捨

Step 3/5 · OryxOS 技術方案

學習目標

能說出技術方案對 Provider、ReAct、Memory、Tool、Web 各下了哪些關鍵設計決定，以及哪些刻意留到擴展階段。

能力一：Provider——只做轉接，不做聰明事

Provider 的職責被壓到最小：把「呼叫一個模型」收斂成一個服務，內部用 Spring AI 的 ChatClient 去接各家供應商。它只做三件事：選模型、呼叫、把工具描述轉成模型看得懂的 schema。至於成本與可靠性的花招，核心階段全部不做：沒有失敗降級、沒有多路競速（hedge racing），模型出錯就直接往上拋給 Agent。

這裡有一個很具體、很容易踩的坑：當系統同時註冊多個 provider 時，會存在多個型別相同的 ChatModel bean，光靠型別掃描無法判斷誰是誰。所以 OryxOS 不用型別掃描，而是維護一份顯式的「provider 名稱 → ChatModel」映射。每個 Provider 宣告一個唯一名稱，Profile 用名稱來引用它。原則是：不明確映射，多 provider 就會壞。

成本透明也只做基本盤——把 tokens、provider、模型記進 llm_calls 表。完整的成本聚合與儀表板留到擴展階段。

能力二：ReAct——七步演算法與上下文紀律

ReAct 迴圈的核心是一段七步演算法：附加訊息 → 組裝 prompt → 呼叫 LLM → 若沒有工具呼叫就回傳最終答案 → 否則執行工具並把結果附加回去 → 繼續迴圈 → 撞到最大迭代次數時強制結束（預設 10 次，可在 Profile 覆寫）。

loop (max 10):
  context.append(message)
  prompt = build()
  resp = llm(prompt)
  if resp.hasToolCall:
      result = execute(resp.toolCall)
      context.append(result)
  else:
      return resp

它由三個模組組成：ReActLoop（幾十行的引擎）、PromptBuilder（四段組裝：system prompt、Memory 注入、對話歷史、可用工具清單）、ToolExecutor（找工具、過沙箱、執行、包 ToolResult、寫 tool_invocations）。

上下文管理有明確紀律：保留 system prompt 加上最近 N 輪對話（預設 20）。核心階段刻意不並行呼叫工具、不做子 Agent 委派、也不做串流輸出。這不是能力不足，而是先把「一輪一輪正確地跑」做穩。

能力三：Memory——一個 facade，一個檔案

記憶在設計上有三層，但核心階段只做兩層，並且用一個統一的 facade（門面）把它們包起來，讓 ReAct 只呼叫一個介面。

層核心階段做法
會話記憶做由 SessionManager 存進 SQLite
長期記憶做一個 MEMORY.md 檔，用 save_memory／recall_memory 兩個工具存取
情景記憶推遲核心階段不做

長期記憶的實作非常樸素：就是一個 markdown 檔，用日期當標題列，格式不嚴格、交給 LLM 自己解讀。它提供 append、load、recallByKeyword（關鍵字召回）、truncateIfNeeded（超長截斷）四個動作。

Memory 注入 system prompt 的方式也很直接：每次組 prompt 都重新讀一次整個 MEMORY.md，不快取。這樣 save_memory 寫入後，下一輪立刻生效。代價是多一次檔案 I/O（約 1–2ms），核心階段認為可以接受。

還有一個常見混淆點：MEMORY.md 跟 USER.md 是兩回事。USER.md 是使用者手寫的 Bootstrap 檔，OryxOS 對它唯讀，屬於「使用者的初始設定」；MEMORY.md 是 Agent 透過 save_memory 寫入的長期記憶，屬於「Agent 的成長記錄」。兩者都會進 system prompt，但來源與生命週期完全不同。

核心階段也不做自動事實抽取、語義檢索、記憶 wiki、矛盾偵測與壓縮——只做簡單截斷，並在介面上預留向量檢索給擴展階段。

能力四：Tool——一個抽象，三種擴展

所有工具都收斂到 OryxTool 這個介面，只有四個方法：getName、getDescription、getInputSchema（JSON Schema）、execute（JSON 進、ToolResult 出）。ToolResult 帶四個欄位：成功旗標、內容、錯誤、是否可重試。內建工具、@Tool 外掛、MCP 工具全都包成 OryxTool，所以 ReAct 看不到差異。

外掛擴展依成本分三級，原則是能用低成本的就別用高成本的：

級別形式什麼時候用
第一級零程式碼：SKILL.md + 現成 MCP能用現成能力解決就優先用這級
第二級輕程式碼：自寫 MCP server需要一點客製邏輯時
第三級重程式碼：Java @Tool Bean要深度接進企業系統時

第一級值得多說一句：它不是工作流程引擎。OryxOS 只把 SKILL.md 的內容載入 system prompt，由 LLM 自己決定要用哪些工具、怎麼組合——OryxOS 不解析任務步驟、也不執行流程。這也是為什麼 SkillLoader 被歸在 ContextLoader，而不是 Tool 模組。

註冊與安全集中在兩個元件：ToolRegistry 在啟動時掃描 @Tool 方法、加上 MCP 註冊的工具，全部包成 OryxTool；SandboxChecker 在執行前檢查檔案路徑、shell 指令、HTTP 網域三類白名單，違規則拋例外。核心階段不做容器隔離，那是擴展階段的事。

能力五：Web——十個端點，先不認證

Web 層用 Spring MVC（埠 8080、虛擬執行緒、oryxos serve 啟動），由六個 ApiController 組成：Session、Agent、Profile、Memory、Tool、System，外加 GlobalExceptionHandler 與 OpenAPI 文件。Controller 的職責很薄：只做驗證、包裝回應、處理錯誤，商業邏輯全部委派給 core 的服務。

核心階段只做 10 個端點：Session 四類（建立、送訊息、取歷史、歸檔）、Agent 直接 invoke、查詢類（profiles／memory／tools）、維運類（health／info）。其餘 15 個端點推遲。核心不做認證（假設跑在內網，API Key 與 JWT 留到擴展）、不做 SSE、WebSocket、RBAC、限流。

但邊界寫得很明確：訊息大小上限 32KB、session 歷史最多保留 100 條、Agent 呼叫 60 秒逾時回 504、錯誤碼用 HTTP status 加上內部碼（400／404／500／503）。核心階段的 CORS 全開——這正是「內網假設」的直接體現。

一個共同模式：核心只留主幹，介面先留好

把五個能力並排看，會發現同一個模式反覆出現：核心階段只實作最短可跑的主幹，把其餘明確推遲，但介面先預留。Provider 不降級、ReAct 不並行不委派、Memory 不用向量庫、Tool 不容器隔離、Web 不認證——每一項「先不做」都寫成了一句可驗證的理由。這讓後續實作有明確的護欄，也讓擴展階段知道該往哪裡加。
