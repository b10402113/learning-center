延遲投遞的底層演算法與選型

Step 2/5 · When 調研與需求

學習目標

能列出延遲投遞的六種底層實作路徑，並用六個維度說明為什麼沒有萬能解。

為什麼要先談演算法

上一課確認了「延遲投遞需要一個獨立元件」。但一個服務的核心是「把訊息存在哪裡、到點怎麼找出來」，這件事一旦選錯，後面再怎麼補救都有限。業界走過的路可以歸納成六種實作路徑，每一種都在不同的維度上取捨。先看懂取捨，後面 When 的技術決策才不會像憑空冒出來。

六種實作路徑

路徑做法強項代價
① 資料庫定期掃描訊息存進 DB，輪詢掃出到期的實作最簡單B+Tree 不擅長大量隨機寫入
② RocksDB + 時間輪LSM 儲存引擎搭配時間輪（Chronos）寫入吞吐高HA 與運維很重
③ Redis ZSet + hash poolZSet 依時間排序，多 worker 取出效能好、實作簡單big-key、Redis 單執行緒敏感
④ RocketMQ 固定級別預設有限個延遲級別直接可用不靈活、最大 2 小時
⑤ QMQ 多層時間輪磁碟排程檔加記憶體雜湊輪O(1)、跨度大、省記憶體實作複雜
⑥ 多層時間輪 + LSM把⑤的儲存換成 LSM理論最優複雜度最高

為什麼「時間輪」能做到 O(1)

時間輪（timing wheel）像一個時鐘：它的每個槽位對應一個時間刻度。要插入一則在未來 T 時刻到期的訊息，只要算出它落在哪個槽位，把它掛進那個槽位的鏈結串列即可——成本與「目前有多少訊息」無關，所以是 O(1)。刪除同理，定位到槽位後從鏈結串列摘除。

問題是：如果只用一層、每格一秒，要覆蓋 30 天就得有 259 萬個槽位，記憶體吃不消。於是有多層時間輪：低層用細粒度（例如秒級），高層用粗粒度（例如小時、天級）。當一則訊息的到期時間超出當前層的覆蓋範圍，就往上一層放；時間推進時，高層的訊息會逐層「下放」到低層——這個過程叫級聯（cascade）。這樣既能保持 O(1)，又能覆蓋很大的時間跨度。

深入看 QMQ：磁碟與記憶體兩層

前面提過 QMQ 的設計被視為業界參考，值得拆開看：

  • 第一層在磁碟：每小時寫一個排程檔（schedule log）。兩年的跨度只需要約 17,568 個檔案。
  • 第二層在記憶體：以 500 毫秒為粒度，只載入「即將到來那一小時」的訊息索引（每筆是 offset 加 size），而不是全部訊息。

這個兩層結構同時拿到三個好處：插入與刪除都是 O(1)；靠多層覆蓋很長的時間跨度；靠懶載入（lazy loading）省記憶體。還有一個容易被忽略的優點：延遲訊息被獨立存放，不會干擾正常訊息的空間回收。

選型的六個維度

把上表收斂成可比較的維度，就是選型時真正在拉扯的六件事：

  1. 寫入吞吐：每秒能收進多少則訊息。
  2. 調度精度：能不能精確到秒、甚至毫秒。
  3. 時間跨度：最遠能排到多久之後。
  4. 記憶體：為了調度要付多少記憶體成本。
  5. 多副本：能不能安全地做副本與故障接管。
  6. 實作複雜度：要花多少人月、多少運維心力。

關鍵在於：這些維度彼此衝突，沒有銀彈。想要高精度，可能得犧牲記憶體；想要大跨度，可能要犧牲簡單度。資料庫掃描最簡單，但大量寫入會壓垮 B+Tree；Redis ZSet 精度好、實作簡單，卻換來 big-key 與記憶體風險；RocksDB 寫吞吐好，但 HA 很重。所以真正的工作不是「找出最好的演算法」，而是「根據你的規模與精度要求，選一組可接受的取捨」。

延遲投遞的演算法選擇，本質是一組取捨：寫入吞吐、調度精度、時間跨度、記憶體、多副本、實作複雜度。你選的不是最強的方案，而是最適合你那個約束組合的方案。
