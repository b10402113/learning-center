延遲投遞的需求與現況缺口

Step 1/5 · When 調研與需求

學習目標

能說明延遲投遞在哪些場景出現、它的精確度與可靠性分級，並指出現有方案共同的邊界缺口。

先看一件事：所謂「延遲投遞」到底是什麼

在未來的某一個精確時刻，把一則訊息投遞到指定的下游——這就是延遲投遞（delayed delivery）。它要解決的不是「怎麼處理這則訊息」，而是「時間到了才把它送出去」。所以它的核心動作是到點觸發；而「投遞到哪裡」決定了它的邊界。理解這一點，才能分清它與訊息佇列、排程器的差別。

需求真實且廣泛：四類場景

延遲投遞不是冷門需求。它出現在幾乎所有需要「未來某刻做某事」的業務裡：

場景類型典型例子對精確度／可靠性的要求
電商／交易訂單逾時取消、優惠券到期、退款逾時、團購結算精確度中，可靠性嚴格
推送／通知定時推送、喚醒提醒精確度中，可靠性可容忍
任務／工作流指數退避重試、定時報表、對帳、審批逾時精確度分級差異大
風控／審計延遲結算、閾值觸發規則、歸檔精確度低，盡力而為加補償

再加上會議提醒、IoT 喚醒、A/B 測試的延遲效果等雜項。這些場景共享幾個特徵：精確度分成秒、分鐘、小時到天三級；可靠性分成三級（嚴格如訂單支付、容忍如推送、盡力而為加補償如歸檔）；規模從中小企業的每天一萬到一百萬則，到頭部網路公司的每天十億則以上。需求真實、廣泛、長期，這是這個元件值得存在的前提。

現有方案一：訊息中介軟體內建的延遲能力

最直覺的想法是「用 MQ 的延遲功能」。但每一家的做法都不一樣，限制也不同：

  • Kafka：原生沒有延遲能力。得靠外部 Redis ZSet 加 worker，或用內部 topic 做時間分桶，兩者都不乾淨。
  • RocketMQ 4.x：內建 18 個固定延遲級別（從 1 秒到 2 小時），但不靈活；5.0 加入時間輪支援任意延遲，採用率仍低。
  • Pulsar：原生支援任意延遲（Delayed Message Tracker），但整個系統偏重。
  • RabbitMQ：要用 TTL 加死信佇列（DLX，粒度粗、有順序問題），或延遲訊息插件（為小規模設計）。

它們有一個共同的缺陷：延遲能力被綁死在某個特定中介軟體上。但真實的下游可能是 HTTP、RPC、Push、ClickHouse 等各式各樣的服務，而且企業往往同時使用多個下游。把延遲綁在 MQ 上，就等於把投遞目標綁死在 MQ 上。

現有方案二：SDK 類方案

另一條路是用 Redis ZSet 實作的延遲佇列 SDK，例如 Redisson 的 DelayedQueue（Java）、HDT3213/delayqueue（Go）、Curator 的 DistributedDelayQueue（ZooKeeper）。它們有三層問題：

  • big-key 風險：把所有延遲訊息塞進同一個 ZSet，單次 ZRANGE／ZREM 就可能阻塞 Redis 數百毫秒；分片只能緩解。
  • SDK 形態的限制：輪詢、重試、狀態都落在客戶端，升級困難、可觀測性由業務自己扛、版本碎片化、無法跨語言。
  • 依賴業務自己的 Redis：會影響業務 Redis 的 QPS、帶來 big-key 風險，而且維運責任歸屬模糊。

所以 SDK 只解決小規模的延遲，不是通用基礎設施。

現有方案三：獨立延遲服務的嘗試，以及那個空著的位置

既然 SDK 和 MQ 都不夠，業界有人嘗試做獨立服務，但都沒站穩：

嘗試做法為什麼沒成
Airbnb Dynein調度與佇列分離，K8s 上無狀態綁死 AWS、Java/Dropwizard 老堆疊、社群停滯
Netflix Dyno-queues綁定 Dynomite生態冷、依賴特定基礎設施
滴滴 DDMQ + ChronosRocksDB 儲存引擎加時間輪堆疊極深（PProxy+RocketMQ+Chronos+RocksDB）、綁 RocketMQ、社群低

其中延遲設計最受業界認可的是去哪兒的 QMQ：磁碟上每小時一個排程檔（schedule log），兩年只需約 17,568 個檔；記憶體裡用 500 毫秒粒度的雜湊輪，只載入即將到來那一小時的訊息索引。它的插入與刪除都是 O(1)，時間跨度大、記憶體友善。但 QMQ 終究是一個 MQ 模組，不是獨立服務，開源社群也有限。

結論很清楚：一個通用、獨立、以延遲為核心、被廣泛採用的開源專案，到今天仍沒有事實標準。這個位置是空的。

順手排除混淆項：任務佇列與任務調度

有兩個常被誤認為同類的東西，必須劃清界線：任務佇列（BullMQ、Celery、Sidekiq）的核心是把任務分配給 worker 執行，延遲只是附加功能；任務調度器（XXL-JOB、PowerJob、Quartz）的核心是 cron 式的預定義週期任務。延遲投遞則是在執行時才生成、每一則的延遲不同、目標／內容／上下文都不同，而且沒有 worker 的概念。三者無法互相取代。至於雲廠商的託管服務（AWS EventBridge Scheduler、GCP Cloud Tasks），小規模便宜，但綁定特定雲、投遞目標受限，不適合多數私有部署。

把需求、現有方案、與演算法景觀放在一起看，得到的判斷是：需求真實、方案拼湊、獨立服務的位置空著。這正是 When 存在的理由。
