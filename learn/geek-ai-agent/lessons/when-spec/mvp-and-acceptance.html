三週 MVP 與驗收標準

Step 5/5 · When 調研與需求

學習目標

能界定三週 MVP 的做與不做、非功能指標，並複述七項驗收標準（包含 AI 產出驗收）。

貫穿整個 MVP 的原則：主流程優先

三週做出一個分散式系統，最危險的不是技術難，而是範圍失控。所以 MVP 只守一個原則：主流程優先（main-flow first），能 demo 勝過完美。先讓「提交一則訊息，時間到，它被送到下游」這條路真的跑通，其餘一切都可以之後再補。這個原則會在下方的做與不做清單裡反覆出現。

MVP 要做的八件事

面向MVP 範圍
主流程提交與投遞；延遲範圍 1 秒到 30 天，精度目標 99% 落在 ±1 秒
三個 HTTP APIPOST／GET／DELETE /api/v1/messages
訊息payload 直通、上限 64KB；at-least-once
狀態機pending → delivering → delivered／failed，另有 cancelled
SinkHTTP 與 Kafka 兩種；SPI 從第一天就存在
持久化Redis，以訊息 ID 分片的 key，禁止用 ZSet 大集合；單機或主從，Redis ≥5.0
調度單機多層時間輪（受 QMQ 啟發），重啟時從 Redis 重建
交付配套半小時可部署、兩個管理台頁面（任務列表、投遞日誌）、Prometheus 指標 + JSON 日誌 + /health

其中「SPI 從第一天就存在」與「以訊息 ID 分片 key」是兩個關鍵的設計選擇：前者確保擴充下游不用改核心，後者直接避開上一課談過的 big-key 風險。

MVP 明確不做的事

這份清單和「要做」一樣重要：

  • 不做叢集、Controller、Master/Slave、故障接管（failover）。
  • 不做 HTTP／Kafka 之外的 Sink。
  • 不做驗證與限流（auth／rate-limit）。
  • 不做死信佇列（DLQ）與自訂重試策略。
  • 不做 SDK、多租戶、跨區部署。
  • 不做 Kubernetes Operator、MCP Server。

這些不是永遠不做，而是留給後續階段。把它們擋在 MVP 之外，三週才有可能跑完主流程。

非功能指標：MVP 與長期的差距

功能有範圍，效能也一樣，先看 MVP 的門檻，再看長期目標：

指標3 週 MVP長期
寫入／投遞 QPS≥1000≥10,000，叢集線性擴展
容量穩定 10 萬則訊息每節點 100 萬則
精度99% 落在 ±1 秒維持，且不遺失
API 延遲P99 ≤100ms維持
故障接管不做（單機妥協）Master 故障後 Slave ≤10 秒接手

值得注意的是那條「單機妥協」：MVP 不做故障接管，所以重啟期間服務不可用，靠業務端重試來補。這是刻意的範圍取捨，不是疏漏。

七項驗收標準

三週結束時，要用這七項來判定專案是否過關：

  1. 功能：三個 API + 兩種 Sink + 兩個管理台頁面 + 可重現的部署。
  2. 精度：延遲在 1 秒到 1 小時範圍內，99% 落在 ±1 秒。
  3. 效能：QPS ≥1000 持續 5 分鐘，穩定承載 10 萬則。
  4. 部署：第三方能在半小時內端到端部署完成。
  5. 可觀測：Prometheus 接上 Grafana、結構化日誌含 trace ID、健康檢查可用。
  6. Demo：10 分鐘端到端演示，分別投遞到 HTTP 與 Kafka。
  7. AI 產出驗收：累計 AI 比例 ≥90%、每個 PR 有真實 review、沒有空批准。

第七項是整體驗收的必要條件——少了它，其他六項再漂亮也不算通過。這正是把上一課談的 AI 編程約束，真正寫進驗收尺規的方式。

三週怎麼排

  • 第 1 週：需求與設計定案；AI 工程鷹架（Spec、CLAUDE.md、Skills）就緒。
  • 第 2 週：核心調度與儲存完成；用 curl 提交一則 30 秒後到期的訊息，能在 ±1 秒內送到測試 HTTP 端點；AI 比例 ≥90% 且 review 清楚。
  • 第 3 週：Kafka Sink、管理台、部署、可觀測；在雲主機上用 docker-compose 跑起來，看得到 Grafana 指標，AI 比例再次 ≥90%。

已知風險

需求文件誠實列出四個風險，後續技術方案會逐一回應：Redis big key（用每訊息 ID 的 key 緩解）、時間輪記憶體膨脹（多層加懶載入）、單機重啟不可用（MVP 的妥協）、爆量到期（投遞池限流與削峰）。把它們記在心上，第四課的技術決策才不會顯得突然。
