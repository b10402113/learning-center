三週 MVP：做什麼、怎麼驗收

Step 5/5 · When 調研與需求

學完這篇，你要能做什麼？

你要能清楚劃出三週 MVP 的邊界：哪些一定要做、哪些先不要碰；同時訂出非功能指標，並說明七項驗收標準，包含 AI 產出的品質要求。

整個 MVP 只守一個原則：主流程先跑起來

三週要做出分散式系統，最容易失控的通常不是技術，而是範圍。這個 MVP 採用主流程優先（main-flow first）：先讓「提交一則訊息，時間到，訊息被送到下游」完整跑通。能 demo，比一開始就追求完美更重要。

其他功能不是永遠不做，而是先排到後面。只要主流程還沒跑通，就不該把時間花在叢集、SDK 或跨區部署上。

MVP 要做的八件事

面向MVP 範圍
主流程支援訊息提交與投遞；延遲範圍為 1 秒到 30 天，精度目標是 99% 落在 ±1 秒內
三個 HTTP APIPOST／GET／DELETE /api/v1/messages
訊息payload 直通，大小上限 64KB；交付語意採 at-least-once
狀態機pending → delivering → delivered／failed，另有 cancelled
Sink支援 HTTP 與 Kafka 兩種；SPI 從第一天就建立
持久化使用 Redis，以訊息 ID 分片建立 key；禁止使用 ZSet 大集合；支援單機或主從，Redis ≥5.0
調度使用單機多層時間輪，設計受 QMQ 啟發；重啟時從 Redis 重建
交付配套半小時內可部署；提供兩個管理台頁面：任務列表、投遞日誌；提供 Prometheus 指標、JSON 日誌與 /health

這裡有兩個設計選擇特別重要。第一，SPI 從第一天就存在，之後增加下游類型時，不必把核心程式拆開重寫。第二，Redis 使用以訊息 ID 分片的 key，避開上一課提過的 big-key 風險。

MVP 明確不做什麼？

「不做清單」和「要做清單」同樣重要。它替系統畫出一道邊界，避免三週計畫被不斷追加的需求拖垮。

  • 不做叢集、Controller、Master/Slave 與故障接管（failover）。
  • 不做 HTTP／Kafka 之外的 Sink。
  • 不做驗證與限流（auth／rate-limit）。
  • 不做死信佇列（DLQ）與自訂重試策略。
  • 不做 SDK、多租戶與跨區部署。
  • 不做 Kubernetes Operator 與 MCP Server。

這些功能不是永遠排除，而是留給後續階段。MVP 先把主流程跑穩，三週才有機會真的交付。

非功能指標：先看 MVP 門檻，再看長期目標

功能有邊界，效能也要有邊界。MVP 追求的是能穩定驗證主流程，不是一次達到最終規模。

指標3 週 MVP長期
寫入／投遞 QPS≥1000≥10,000，並能隨叢集線性擴展
容量穩定承載 10 萬則訊息每節點 100 萬則
精度99% 落在 ±1 秒內維持相同精度，且不遺失訊息
API 延遲P99 ≤100ms維持
故障接管不做，接受單機妥協Master 故障後，Slave 在 ≤10 秒內接手

「單機妥協」是刻意的取捨，不是漏做。MVP 不提供故障接管，因此重啟期間服務會不可用，靠業務端重試補回。這種限制必須明白寫進規格，團隊才不會把它誤認為尚未完成的 bug。

七項驗收標準：用尺規判斷有沒有過關

三週結束時，不靠「看起來差不多」判斷，而是逐項對照以下標準：

  1. 功能：三個 API、兩種 Sink、兩個管理台頁面，以及可重現的部署流程。
  2. 精度：在延遲 1 秒到 1 小時的範圍內，99% 的訊息落在 ±1 秒內。
  3. 效能：QPS ≥1000 並持續 5 分鐘，同時穩定承載 10 萬則訊息。
  4. 部署：第三方能在半小時內完成端到端部署。
  5. 可觀測性：Prometheus 能接上 Grafana；結構化日誌包含 trace ID；健康檢查可用。
  6. Demo：在 10 分鐘內完成端到端演示，並分別投遞到 HTTP 與 Kafka。
  7. AI 產出驗收：累計 AI 比例 ≥90%；每個 PR 都有真實 review；不得出現空批准。

第七項是整體驗收的必要條件。即使前六項都達標，只要 AI 產出的 review 流程不可信，專案仍不算通過。這是把上一課的 AI 編程約束，直接變成可以檢查的驗收規則。

三週怎麼排？

  • 第 1 週：定案需求與設計；準備 AI 工程鷹架，包括 Spec、CLAUDE.md 與 Skills。
  • 第 2 週：完成核心調度與儲存。用 curl 提交一則 30 秒後到期的訊息，確認它能在 ±1 秒內送到測試 HTTP 端點；AI 比例 ≥90%，且 review 內容清楚。
  • 第 3 週：完成 Kafka Sink、管理台、部署與可觀測性。在雲主機上用 docker-compose 跑起系統，確認能看到 Grafana 指標；AI 比例再次達到 ≥90%。

已知風險：先知道哪裡可能爆

需求文件先列出四個風險，後續技術方案會逐一處理：

  • Redis big key：改用每則訊息一個 ID key 來緩解。
  • 時間輪記憶體膨脹：採用多層時間輪，搭配懶載入。
  • 單機重啟不可用：MVP 接受這項妥協。
  • 訊息同時大量到期：透過投遞池限流與削峰。

這些風險不是附註，而是後續技術決策的出發點。下一課看到 Redis key、時間輪或投遞池的設計時，都能對上它們要解決的問題。
