When 的定位與非目標：只負責把訊息送到未來

Step 3/5 · When 調研與需求

學完這一篇，你應該能判斷什麼？

你會知道 When 是什麼、為什麼同時扮演兩種角色、接下來分哪三個階段發展，也能說清楚它的五大設計目標與明確不做的事。

When 是什麼：一個只管時間與投遞的元件

When 是一個通用、可獨立部署的分散式延遲投遞元件，以 Java 實作。它的責任很單純：先收下一則指定未來時間投遞的訊息，時間到了，再把訊息送到任意下游。

下游可以是 HTTP、Kafka、gRPC 或其他 MQ。業務方透過 HTTP API 提交訊息；到了指定時間，When 負責送達。至於下游收到後要怎麼處理，則不在 When 的責任範圍內。

為什麼需要獨立做這一層？因為延遲投遞是常見需求，卻沒有一個通用、獨立的元件專門填補這個空位。When 不把自己塞進某個 MQ 或排程器，而是站在兩者之外，專心處理「什麼時候送、送到哪裡」。

雙重定位：既是產品，也是 AI 編程教學樣本

When 同時扮演兩種角色：

  • 真實可用的元件：在企業環境中解決實際的延遲投遞問題。
  • AI 編程教學樣本：示範如何由 AI 主導，完成一個企業級專案的開發與交付。

第二個角色帶來一項硬約束：核心程式碼要有至少 90% 由 AI 撰寫。否則，專案本身就無法示範「用 AI 交付軟體」這件事。另一條主線，則是把從「一句需求」一路走到「生產部署」的完整流程展示出來。

三階段發展路線：先跑起來，再變可靠

When 是一個長期專案，因此不把所有能力一次做完，而是分成三個階段：

  1. 三週 MVP：先跑通核心主流程，做到能 demo、能部署。
  2. 學生維護：由受訓學員接手，逐步把系統推向生產可靠。
  3. 社群共建：以開源方式長期演進，發展多語言 SDK、多租戶等能力。

五大設計目標：用什麼標準判斷 When 是否合格

設計目標不是功能清單，而是用來判斷架構是否走在正確方向上的標準：

目標意思
通用（general）不綁定特定中介軟體，也不綁定特定下游。
可擴展（extensible）投遞目標透過插件式 Sink 擴充；新增下游時，不必修改核心。
可靠（reliable）支援叢集化與 Master/Slave，並且不丟訊息。
易整合（easy to integrate）對外提供一套簡單的 HTTP API。
可運維（operable）提供指標、日誌、健康檢查與管理台。

非目標：When 刻意不做什麼

非目標比目標更能畫出架構邊界。When 明確不是以下這些東西：

  • 不是任務調度器：不是 XXL-JOB、PowerJob 或 Quartz。
  • 不是訊息佇列：不是 Kafka、RocketMQ 或 Pulsar。
  • 不是 worker 框架：不是 BullMQ、Celery 或 Sidekiq。
  • 不是 all-in-one MQ：不把所有訊息能力都包進來。
  • 不解析 payload：訊息內容對 When 是不透明的，When 只負責送達。
  • 不保證下游的業務邏輯：訊息送到之後，下游如何處理不歸 When 管。

為什麼要花力氣說清楚「不做」？因為這些領域都有成熟工具。When 如果什麼都想包辦，最後會同時和排程器、MQ、worker 框架競爭，卻說不清楚自己的價值。

把 payload 當成黑盒、把業務邏輯留給下游，反而讓 When 保持通用。它只處理兩件事：時間到了，以及把訊息投遞出去。

交付語義：至少一次，而不是剛好一次

When 承諾的是 at-least-once（至少一次） 投遞：

  • 訊息保證不遺失。
  • 訊息可能被重複投遞。
  • 下游必須自行實作冪等，才能安全處理重複訊息。

這是刻意的取捨。在分散式環境裡，要做到「絕不重複」通常比做到「絕不遺失」昂貴得多；而多數業務可以透過冪等處理重複投遞。When 因此選擇先守住訊息不遺失，再把重複處理交給真正了解業務的下游。

先建立共同語言

後續內容會反覆使用以下術語。先把每個詞固定下來，讀架構時才不會把不同層次的概念混在一起：

術語意思
延遲訊息（delayed message）一則被指定未來投遞時刻的訊息。
投遞（delivery）到達指定時間後，把訊息送往下游的動作。
Sink抽象的投遞目標；每種下游透過 SPI 插件實作。
時間輪（time wheel）／多層時間輪負責在到點時找出訊息的調度結構。
節點（node）叢集中的一個 When 實例。
Controller由 etcd 選舉產生的唯一決策者；它本身也是普通節點。
