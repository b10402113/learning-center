When 的定位與非目標

Step 3/5 · When 調研與需求

學習目標

能說明 When 是什麼、它的雙重定位與三階段發展路線，並說出五大設計目標與它明確不做的事。

When 是什麼：一句話定位

When 是一個通用、可獨立部署的分散式延遲投遞元件，以 Java 實作。它的職責單一：在指定時間，把一則訊息精確投遞到任意下游——HTTP、Kafka、gRPC 或其它 MQ 都可以。業務方透過 HTTP API 提交訊息，時間到了，When 負責送達。

為什麼要做它？因為上一課看到的缺口真實存在：延遲投遞是高頻需求，但沒有一個通用、獨立的專案填補它。When 選擇站在這個空位上，而不是再往 MQ 或排程器裡擠。

雙重定位：一個元件，兩個身分

When 同時是兩樣東西，這是它最特別的地方：

  • 一個真實可用的元件：要能在企業裡解決真實的延遲投遞問題。
  • 一個 AI 編程教學樣本：要用整條開發流程示範「用 AI 主導交付一個企業級專案」。

第二個身分直接推導出一條硬約束：核心程式碼要 ≥90% 由 AI 撰寫。因為如果這個專案本身不是被 AI 寫出來的，它就不具備教學價值。另一條主線則是展示從「一句需求」到「生產部署」的完整流程。

三階段發展路線

承認這是一場長期專案，比較務實。When 拆成三個階段：

  1. 三週 MVP：先跑通核心主流程，能 demo、能部署。
  2. 學生維護：由受訓學員接手，把系統推向生產可靠。
  3. 社群共建：以開源方式長期演進，長出多語言 SDK、多租戶等能力。

五大設計目標

「設計目標」回答的是：一個合格的 When 應該具備什麼性質。共有五項：

目標意思
通用（general）不綁定特定中介軟體、不綁定特定下游
可擴展（extensible）投遞目標以插件式 Sink 擴充，加新下游不改核心
可靠（reliable）叢集化、Master/Slave、不丟訊息
易整合（easy to integrate）對外就是一套簡單的 HTTP API
可運維（operable）有指標、日誌、健康檢查與管理台

非目標：明確不做的事

比起目標，非目標更重要，因為它決定邊界。When 明確不是這些東西：

  • 不是任務調度器（不是 XXL-JOB、PowerJob、Quartz）。
  • 不是訊息佇列（不是 Kafka、RocketMQ、Pulsar）。
  • 不是 worker 框架（不是 BullMQ、Celery、Sidekiq）。
  • 不是 all-in-one MQ：不試圖把所有訊息能力都包進來。
  • 不做 payload 解析：訊息內容對 When 是不透明的，它只負責送達。
  • 不保證下游的業務邏輯：訊息送到了，下游怎麼處理不歸它管。

為什麼「不做」這麼重要？因為這些領域都已經有非常成熟的工具。When 若什麼都做，就會和它們硬碰、模糊自己的價值。把 payload 當黑盒、把業務邏輯留給下游，正是它能保持「通用」的原因——它只做時間與投遞這一件事，把它做到最好。

交付語義：至少一次

When 承諾的投遞語義是 at-least-once（至少一次）：訊息保證不遺失，但可能重複投遞，因此下游必須自行實作冪等。這是一個刻意的取捨——在分散式環境裡，「絕不重複」比「絕不遺失」貴得多，而多數業務用冪等就能安全地消化重複。

先建立共同語言

後面幾個節點會反覆用到這批術語，先在這裡釘住：

術語意思
延遲訊息（delayed message）一則被指定了未來投遞時刻的訊息
投遞（delivery）在到點時把訊息送往下游的動作
Sink抽象的投遞目標，每種下游以 SPI 插件實作
時間輪（time wheel）／多層時間輪負責在到點時把訊息找出來的調度結構
節點（node）叢集中的一個 When 實例
Controller由 etcd 選舉產生的唯一決策者，本身也是普通節點
