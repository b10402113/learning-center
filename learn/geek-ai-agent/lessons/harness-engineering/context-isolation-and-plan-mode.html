學習目標

能判斷何時該派 Subagent 做上下文隔離（並看懂 4 個 subagent 並行初始化 11 個模組的案例），以及哪些情境必須先進 Plan Mode 才動手。

上下文污染：為什麼 AI 越到後面越笨

想像你要初始化一個有 11 個模組的專案，於是叫 AI 一個一個模組建。每建完一個，那個模組的檔案內容、編譯錯誤、討論過程全都留在同一段對話裡。到第五個模組時，對話已經塞滿前四個模組的細節——AI 的注意力被稀釋，開始漏看你的要求，品質明顯下滑。

這就是上下文污染：不是 AI 變笨了，而是它每一輪要處理的相關與無關資訊一起變多，真正重要的訊號被淹沒。它有兩個解法，分別對應「在哪裡做」和「什麼時候做」。

解法一：Subagents——把子任務丟到乾淨的 context

Subagent（子代理）是一個獨立執行子任務的代理，擁有自己的、乾淨的 context。它做完只把結果交回主代理，過程中的檔案內容與錯誤不會污染主對話。

做法主 context品質與速度
序列初始化（主代理自己做完 11 個模組）不斷膨脹注意力被稀釋、品質逐漸下降
並行 Subagents（每個負責一批模組）只收結果，保持乾淨品質穩定、約 4 倍速度

一個真實案例：4 個 subagent 並行初始化 11 個模組

把 11 個 Maven 模組切成四份，派四個 subagent 各自在乾淨 context 裡開工：

  • A：核心 + Provider（ReActLoop／PromptBuilder／ToolExecutor／OryxTool／Session／Profile，以及 ProviderService 與 function-calling 轉接）。
  • B：Memory + 內建工具（MemoryService／MemoryTools，FileTools／ShellTools／HttpTools／SandboxChecker）。
  • C：Skill + MCP 工具（SkillLoader，McpClientService／McpToolAdapter）。
  • D：Web + 儲存 + CLI + 啟動（WebServer 與六個 controller、SessionRepository、Picocli 與 Spring Boot fat JAR）。

每個 subagent 交付模組目錄、pom.xml、核心類別骨架與基本測試，驗收標準是 mvn compile 通過。最後的結果是：11 個模組都能編譯、沒有依賴衝突、核心介面都定義好了，還有一個能跑的 fat JAR，而架構漂移檢查是 0。這不是示範用的玩具程式，而是一個真的可編譯的多模組骨架。

什麼時候不該用 Subagent

Subagent 不是萬靈丹。在輕量模式的小任務裡，光是拆任務、寫清楚 subagent 的指令、再把結果整合回來，成本就高於直接做——這時它反而是負擔。判斷原則：任務夠大、夠獨立、且會明顯污染主 context 時才派。

解法二：Plan Mode——把錯誤擋在動作之前

Subagent 管「在哪裡做」，Plan Mode（計畫模式）管「什麼時候做」。它要求 AI 在動手修改之前，先產出一份計畫給你確認。

為什麼它是最划算的一道防線？因為此時錯誤還只是文字，改一行計畫的成本，遠低於改十個檔案。反過來說，有些情境幾乎一定該先進 Plan Mode：

  • 有風險的操作——會影響資料、部署或共用模組。
  • 不熟悉的程式碼或技術棧——AI 只能猜，猜錯機率高。
  • 第一次做這件事——沒有先例可循，先對齊方向再動手。

換句話說，Plan Mode 是對「未知與後果」收的保險費；對熟悉、低風險、改一行的小事，硬要走計畫流程只是拖慢速度。

兩者合起來

這兩個工具處理的是同一個大問題的不同切面：上下文污染來自「太多資訊擠在一個地方」，Subagent 用隔離解決它；盲目動手來自「還沒想清楚就開始改」，Plan Mode 用事前確認解決它。下一個步驟，我們補上最後兩道防線——動作前攔阻的 Permission，與動作後驗證的 Hooks。
