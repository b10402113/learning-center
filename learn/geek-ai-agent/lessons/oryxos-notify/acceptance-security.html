驗收 harness 與安全順序：enforce 必須在 send 之前

Step 4/5 · Notify 出站

學習目標

能說明兩批測試各測什麼、為何 enforce-before-send 的順序斷言是白名單防線的關鍵，以及「未設定」要 loudly fail 而不能靜默。

程式碼寫完，不代表做對了

上一課把四個類別寫出來了。但「寫出來」和「做對了」之間隔著一道驗收。Notify 的驗收拆成兩批測試，分批的理由是相依就位：WebhookNotifyAdapterTest 現在就能寫；NotifyToolsTest 要等 Tool 註冊（@Tool）與 Sandbox（enforce）就位——所以先做第一批，第二批 hook 好之後補。這跟上一課講的「完成點在 24 課之後」是同一個節奏。

第一批：WebhookNotifyAdapterTest——單一實作的行為

用 MockWebServer（一個在測試裡起真實 HTTP 服務的假 server）測 adapter 真正發出去的請求，斷言三件事：

斷言驗證的目的
POST 的 body 帶了 contentadapter 真的把要通知的內容放進請求裡
URL 來自 NotifyTarget.config 而非 hardcodeadapter 是從目標設定取位址，不是寫死某個網址
5xx 會被傳出去、不吞掉目標回錯誤時要讓呼叫端知道，不能假裝成功

第三個斷言特別提醒一個壞習慣：有些實作會把例外 catch 起來「靜默吞掉」，讓「通知失敗」看起來像「通知成功」。adapter 必須把錯誤往上拋。

第二批：NotifyToolsTest——把整條鏈的規則釘死

對 Sandbox 與 Adapter 都用 mock（替身），把 NotifyTools 當成黑盒來測它的三個行為規則：

  • 沒設定 notify_channels 時，要明確報錯——不能默默選一個「預設」然後發出去，因為推錯了地方比不推更糟。
  • 缺 channel 時，用第一個渠道——這是上課學過的「非必填」行為，要用測試證實。
  • enforce 在 send 之前呼叫——用 Mockito 的 InOrder 斷言兩次呼叫的次序。

最關鍵的斷言：create 順序，inOrder

這一條要單獨拿出來講，因為它是安全防線的地基。程式碼可以「看起來一樣」，但呼叫次序不同，安全性天差地遠：

// 對（enforce 先、send 後）
sandbox.enforce(action);
adapter.send(target, content);

// 錯（send 先、enforce 後）
adapter.send(target, content);
sandbox.enforce(action);

第二種寫法、訊息先出去了才檢查——檢查等於沒有檢查，白名單形同廢紙。所以測試用 InOrder 明確斷言「enforce 先於 send」，順序反了＝白名單繞過。這是驗收 harness 裡最不能砍的一條斷言。

兩個安全文化：Loud Fail + 順序敏感

把兩批測試背後的設計態度總結成兩條規則，將來任何模組都適用：

  1. 未設定必須大聲失敗（fail loud）。「沒配通知渠道」和「不通知」是兩回事；前者是設定錯誤，要讓使用者立刻看到「notify_channels 未設定」的明確錯誤，而不是讓訊息消失。
  2. 安全檢查的順序是值得用測試釘死的契約。能用 InOrder 斷言次序，就不該只靠 code review 靠肉眼。

實作完之後，怎麼用怎麼驗

測試批次之外，還有一層手動驗收（怎麼用做完怎麼驗）：設定好 notify_channels 後，讓 Agent 自主決定何時呼叫（例如天氣 Agent 把每天的天氣推到群組），然後人工檢查：

  • 真的收到——找一個真實 webhook（或自己的測試組），確認訊息真的到了目標群組。
  • 介面中性自測——問自己：現在要換成微信 SDK，需要改函數簽名嗎？答案必須是「不用」。

前者驗「鏈真的通」，後者驗「介面真的中性」——兩題都過，Notify 才算完成「Agent 不只會說話、還會對外送達」的出口。
