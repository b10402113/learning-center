動手前先想清楚：介面先行與四個決策

Step 2/5 · Notify 出站

學習目標

能複述動手前的四個決策（介面表達意圖、核心只做通用 webhook、安全留給 Sandbox、目的地放 Profile），並解釋入站 ChannelAdapter 與出站 NotifyChannelAdapter 的對稱性。

一件事：動手之前，先把介面想清楚

上一課確定了「要有出站抽象」。這一課回答「這個抽象長什麼樣子」。原則是介面先行（interface first）：先定義一個表達「意圖」的介面，再決定實作。這是整個 Notify 模組的施工順序，也是後面 Memory、Sandbox 模組都會重複使用的習慣——先釘介面，再談實作。

為什麼順序這麼重要？因為介面是通往未來擴展的牆壁。如果你先寫死「推送 = 對企業微信 webhook 發 POST」，那下個月要接飛書、釘釘、Slack、Telegram，每一家都得改這面牆。如果你先把「意圖」抽象出來，牆壁一次釘好，實作怎麼換都不會碰到它——測試的方法是：把最重的未來實作（例如整個微信 SDK）放進這個介面，看看塞不塞得進去，塞得進去牆就立住了。

四個決策

動手前，原案把問題拆成四個明確的決策，每寫一行程式碼之前就定下來：

決策一：介面要表達意圖，不表達渠道

介面簽名描述「把內容送達一個通知目標」這件事，不能出現任何渠道專屬的詞彙——沒有 webhook、沒有企微、沒有 JSON。簽名長這樣（細節下一課展開）：

interface NotifyChannelAdapter {
    void send(NotifyTarget target, String content);
}

NotifyTarget 只是「一個通知目標」的描述，不牽扯是哪家渠道。這樣換渠道時，呼叫端零改動。

決策二：核心階段只做一種通用的 webhook

企業主流通知渠道（企業微信、飛書、釘釘、Slack…）幾乎都提供 webhook 位址，核心階段只實作一個通用的 WebhookNotifyAdapter——把 content 包成指定的 JSON、發一次 POST。簽名算法、AccessToken 刷新那些各家專屬認證細節，核心階段通通不做，留給擴展階段逐家接。通用 webhook 之後、逐家專屬 adapter 之前，中間的關係是「一個介面、多份實作」。

決策三：安全驗證留給 Sandbox 模組

發 webhook 是網路請求，該不該放行是安全邊界的事。核心階段這裡只留一個佔位，真正細講在 Sandbox 模組（23/24 課）——就像後面全流程串聯看到的 Sandbox.enforce(...)。設計立場很明確：Notify 不自己發明安全，它復用已有的白名單機制。

決策四：目的地放 Profile 設定，不放對話內容

「推送去哪裡」這件事，由 Agent 的 Profile 設定（notify_channels）決定，不讓 LLM 從對話內容裡臨時決定。Profile 範例：

notify_channels:
  - type: webhook
    url: ${TEAM_WEBHOOK_URL}

這樣的目的很實際：通知目標是系統性、要被人管理的配置，不是每次對話的變數。把目的地交給模型隨口說，等於把「今天通知去哪」交給不可控的推斷；放在 Profile，人管渠道，Agent 只決定「要不要推、推什麼」。

為什麼選成本最低的通用 webhook？

你可能會問：為什麼不一次到位，把企業微信、飛書、釘釘全接上？因為「全接」不是核心階段要證明的東西。核心階段的目標是「最短可跑的 runtime kernel」——先證明「Agent 能把結果推出去」這條鏈真的通，至於推給哪家，都是同一套 webhook 機制。選通用 webhook 的理由是它能用一份實作覆蓋最多渠道的入門形態，邊際價值最高，成本最低。

這也呼應整門課的階段克制紀律：不是每件事都該現在做，是有信號才做。webhook 接不通、要富文本卡片——那才啟動擴展階段的專屬 adapter 或 MCP（第五課詳談）。

對稱性是刻意的：入站 / 出站雙向插件

這裡的 ChannelAdapter（8.4 Channel 接入：定義「什麼進來了」）和 NotifyChannelAdapter（定義「結果出去哪」）是鏡像對稱的兩個抽象。它們共享同一個 plugin 模式，但不合成一個介面——因為語義方向相反。實作上，同一個企業微信群，完全可能同時是某個 Agent 的入站 Channel、又是另一個 Agent 的出站通知目標。入站收、出站送，兩件事分開建模，介面才乾淨。

完工順序不是教學順序

順帶拆穿一個常見的誤解：NotifyChannelAdapter／NotifyTarget／WebhookNotifyAdapter 這三件現在就能實作，但完整的 NotifyTools 要等兩件事就位——Tool 的 @Tool 註冊（Tool 模組）和 Sandbox.enforce（Sandbox 模組）。所以程式碼的「完成點」在 24 課之後。這叫做教學順序與建造順序分離：先把介面釘死，實作等相依模組就位。
