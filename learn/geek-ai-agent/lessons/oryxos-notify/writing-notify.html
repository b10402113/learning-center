程式碼怎麼寫：NotifyChannelAdapter、NotifyTarget、WebhookNotifyAdapter、NotifyTools

Step 3/5 · Notify 出站

學習目標

能說出四個類別各自的職責、介面簽名為何不含任何渠道概念，以及 channel 非必填時的行為。

四個類別，三個角色

動手前的四個決策釘完了，現在把它們落成四個類別。它們不是平起平坐，而是三層分工：

類別角色一句話職責
NotifyChannelAdapter介面表達「把內容送達一個通知目標」的意圖，不含任何渠道詞彙
NotifyTarget資料描述「一個通知目標」：渠道類型 + 設定 Map
WebhookNotifyAdapter實作核心階段唯一的實作：POST {"content": ...} 到目標 URL
NotifyTools扳機把「推送」變成 LLM 可呼叫的 Tool：解析目標 → 過沙箱 → 送

介面：把意圖寫在簽名裡

public interface NotifyChannelAdapter {
    void send(NotifyTarget target, String content);
}

這個簽名只用「目標 + 內容」，一個渠道專屬的概念都不帶。這正是介面先行的成果：把 webhook 換成任何一家專屬 adapter，NotifyTools 一行都不用改。

資料：NotifyTarget 把「目標」描述清楚

public record NotifyTarget(String channelType, Map<String, String> config) {}

channelType 說「這是哪一種渠道」（webhook／企業微信／飛書…），config 用一個 key-value Map 帶該渠道需要的設定（例如 webhook 類的 url）。把設定包成 Map 而不是固定欄位，是為了讓同一個介面能承載不同渠道不同的欄位需求。

實作：WebhookNotifyAdapter 做最小的事

public class WebhookNotifyAdapter implements NotifyChannelAdapter {
    @Override
    public void send(NotifyTarget target, String content) {
        String url = target.config().get("url");
        // 發 HTTP POST，body: {"content": content}
    }
}

URL 從 target.config() 讀，不 hardcode，所以同一份 adapter 能送給任何 webhook 位址。核心階段的職責就到這裡——把「內容包成 {"content": ...} 的一次 POST」——不做簽名、不接 token 刷新。

扳機：NotifyTools 把整條鏈接起來

@Tool
public String notify(String content, String channel) {
    NotifyTarget target = resolveFromProfile(channel);  // 1. 解析目標
    sandbox.enforce(new SandboxAction(HTTP_REQUEST, url)); // 2. 過白名單
    return adapter.send(target, content);                 // 3. 送出
}

三個動作，順序是刻意設計的：

  1. 解析目標——從當前 Profile 的 notify_channels 回解析出 NotifyTarget。用 ProfileContext（ThreadLocal 持有當前 Profile）。
  2. 過安全——sandbox.enforce(...HTTP_REQUEST...) 檢查目標域名在白名單內。
  3. 送出——真正交給 adapter。

兩個重要的行為細節：

  • channel 參數非必填——省略時預設用 notify_channels 的第一個渠道。
  • Profile 設定範例：notify_channels: [{type: webhook, url: ${TEAM_WEBHOOK_URL}}]——網址帶環境變數，貫徹「敏感資訊不放明文設定」的原則。

一個關鍵心智模型：介面中性

整段程式碼的精華在於「介面中性（channel-neutral）」。你可以做一個自測題：現在要換掉 webhook，全部改用企業微信 SDK。NotifyTools 要改幾行？——零行。它呼叫的還是同一個 NotifyChannelAdapter.send(NotifyTarget, String)。要變的只有：註冊到 registry 的實作從 WebhookNotifyAdapter 換成 WeComNotifyAdapter。介面把變化隔離在實作層。

如果把「通知」寫死成 webhook 的呼叫，換渠道就得翻動所有呼叫它的業務 Skill；介面中性讓「要不要推、推什麼」與「怎麼推」徹底解耦。

跟在後面的安全掛鉤

注意 sandbox.enforce 呼叫在 adapter.send 之前。這個順序就是下一課驗收 harness 裡最重要的一條斷言：順序反了，等於訊息先送出去、白名單檢查變成馬後炮——白名單防線就形同虛設。現在記住「先 enforce、後 send」，下一課我們用測試把它釘死。
