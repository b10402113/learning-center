擴到企業主流渠道：場景、webhook 差異與延伸路徑

Step 5/5 · Notify 出站

學習目標

能依場景選通知渠道、看懂各家 webhook 格式差異與對接坑，並用三原則決定「純文字→webhook、特殊格式→專用 adapter、富卡片→MCP」的延伸路徑。

先問場景，再挑渠道

企業通知渠道不是越多越好，而是按場景選。OryxOS 按使用情境把渠道分成四類：

場景代表渠道特點
團隊協作企業微信、飛書、釘釘、Slack進群、@人、多人可見，Agent 日報的主戰場
個人通知Telegram、ntfy個人裝置直接收，適合個人專案的提醒
告警值班（alert-on-call）PagerDuty、Opsgenie真的要出事的告警，帶升級與值班流程
正式觸達Email、合規平台給客戶／外部對象，要走正式渠道

判斷規則很務實：一次 POST 到 URL 就搞定的 = 核心階段可達；要建連線、token 刷新、請求簽名的 = 擴展階段再做。

「所有 webhook」≠「同一種 JSON」

最常踩的坑：以為各家渠道既然都叫 webhook，格式一定一樣。實際上核心 WebhookNotifyAdapter 送的是 {"content": ...}，而每家渠道的 payload 都不同——企業微信、飛書、釘釘、Slack、Discord、Telegram、ntfy、Teams 各有各的欄位約定。舉幾個真實差異：

  • 釘釘要求三選一的安全設定（加簽／關鍵詞／IP 白名單），漏了就要接特別處理。
  • 飛書的簽名是可選的。
  • Teams 的經典 webhook 已退役，改走 Power Automate。

所以「對接渠道」這四個字背後，是逐家的 payload 對照與坑位清單，不是一份 doc 打天下。

對接一家渠道的五步流程

不管接哪家，流程是同一套，順序也固定：

  1. 建機器人——在渠道管理後台建一個群機器人，拿到 webhook URL。
  2. 網址放環境變數——例如 TEAM_WEBHOOK_URL，不明文寫死在設定檔。
  3. 配置到 Profile——寫進 notify_channels。
  4. 把域名加進 Sandbox 白名單——讓 enforce 放行這個 webhook 網址。
  5. 發一條測試訊息——確認真的進群。

每一步卡住都有明確的修法，例如飛書要多做一步簽名可選的判斷，釘釘要注意它的三選一安全設定。

三原則：什麼時候該動手寫 adapter？

通用 webhook 是核心階段的「下限」。遇到 payload 格式不對的渠道，用三原則決定走哪條路：

需求選擇理由
純文字就能表達notify + webhook核心已經幫你統一掉了，不用寫東西
特殊格式或認證步驟專用 NotifyChannelAdapterpayload 對不上，就寫一個專屬 adapter，介面不用動
富卡片、複雜互動MCP（方式二）要官方富文本卡片這種格式，直接接專用 MCP server

關鍵在於：不管走哪條路，NotifyChannelAdapter.send(NotifyTarget, String) 這個簽名永遠不用改——介面中性的紀律到擴展階段依然成立。

安全紅線：webhook URL 本身就是憑證

這條要格外記住：webhook URL 裡的 token 本身就是認證憑證——拿到 URL 就等於拿到往群組發訊息的鑰匙。所以它必須：絕不明文落進設定檔、絕不寫進記錄（log）、絕不進 Git 提交。一律走環境變數，必要時加密儲存。

回到整條鏈：Notify 只是「推送」這一步

把視角拉大：Notify 不是「另一個系統」，它是 OryxOS 底座能力的一環。天氣 Agent、科技日報 Agent、GitHub 日報 Agent 全部是同一條鏈——「查資料 → 組內容 → notify(channel, content) 推送」。而 Agent 到底用哪個渠道，靠的是 Profile 設定（notify_channels）＋ Agent 的決定（要不要推）。渠道多、格式雜，靠介面隔離；這正是 OryxOS 敢在外接一大堆企業渠道的原因。
