為什麼需要 Notify：觸發斷裂與出站職責

Step 1/5 · Notify 出站

學習目標

能說出「到點自動」觸發如何讓入站請求／回應路徑失效，並指出 Notify 是 Agent 主動決定「把結果送到哪」的對應補位。

先從一個問題開始：誰在等 Agent 的回答？

到目前為止 OryxOS 的兩條主路徑都是「人問、機器答」：CLI 是你敲一行 oryxos chat ...，Web Service 是你的系統打一個 REST API，然後 Agent 把結果回給你。這兩條路徑有個共同前提——有一個請求方在現場等回應。你問，它答，你收走，就完結了。

現在換一個場景：一個每天早上八點自動跑的「每日天氣 + 穿搭建議」Agent。到點之後，沒有任何人敲鍵盤、沒有任何人打 API，程式自己醒過來。它查完天氣、生成完建議——然後呢？結果要送去哪？誰會來領？沒有請求方。

這一瞬間，原本設計好的「人問機器答」路徑就地斷裂。你可以把整批結果寫進 Session、留在資料庫裡，但那就是讓結果爛在 Session 裡——沒人會打開某個 sqlite 表去翻今天的天氣建議。這不是「多一個功能」的問題，而是整個觸發模型反過來了。

觸發斷裂：從「被拉」到「被推」

把兩條路徑攤開看差異：

面向CLI / Web Service定時任務 + Notify
誰發起人（或業務系統）主動時鐘（到點自動）
有沒有人在等有，同一個請求方在等回應沒有，誰都不在現場
結果的去向沿通訊路徑原路返回必須由 Agent 自己決定、自己送出
Agent 的角色被動回應主動出站（outbound）

關鍵詞是出站（outbound）：前面所有模組（Provider、ReAct、CLI、Tool）幾乎都在處理「請求進來、處理、回應回去」，方向是進出成對的。Notify 是這個系統第一次真正把「Agent 主動把訊息推出去」當成一等公民來設計——沒有入站請求，也要能把結果送達。

所以 Notify 的定義一句話：Notify（Notify 通知） 讓 Agent 在「沒有請求方等待」的場景下，決定往哪個通知目標、發什麼內容，把結果主動推送出去。它在排程（scheduled）觸發、日報／天氣這類「到點自動」的場景才真正發光。

對稱的另一半：入站与出站都該是插件

這裡有個很容易忽略的設計呼應：OryxOS 已經有一個處理「訊息怎麼進來」的抽象——入站的 ChannelAdapter（看 03-18 技術方案的 8.4 Channel 接入：CLI、之後的企業微信／飛書／釘釘／Slack 都走這個插件位）。現在要處理「訊息怎麼出去」，出站也要一個對稱的 adapter 插件：NotifyChannelAdapter。

為什麼必須對稱？因為如果不抽這層，給扳機的情境會變成：每個業務 Skill 為了「把結果推出去」，各自手寫自己的 webhook／MCP 對接，企業微信一套、飛書一套、釘釘一套，散落各處。而「推送一條訊息出去」其實是所有 Auto Agent 都會重複需要的一件事——把它抽成一個統一動作（NotifyTools）放在底座，業務 Skill 就只要呼叫「推送」，不用管底層是哪家渠道。

這張圖就是整個 Notify 模組的心智模型：入站用 ChannelAdapter 收，出站用 NotifyChannelAdapter 送，中間是同一個 Agent 引擎。入站決定「什麼觸發 Agent 開始跑」，出站決定「Agent 跑完把結果送到哪」——方向相反、設計對稱。

它解決的問題，具體到能驗證

把視角拉到「底座有沒有這個能力」的驗收層：有了 Notify，Agent 才能從「只會說話」升級成「會對外送達」。少了它，定時任務就算能準時觸發、能生成完美的內容，結果也永遠困在系統裡。你可以把「定時任務＋Notify」想成一把鎖的兩片鑰匙：排程負責「什麼時候醒」，Notify 負責「醒來之後去哪裡」，缺一片就開不了門。

往後看，天氣 Agent、GitHub 日報 Agent、訂單對賬 Agent 全部是「查完 → 組內容 → notify 推送」這同一條鏈。你現在先看懂「為什麼要有一個出站抽象」，下一課再決定這個抽象的形狀。
