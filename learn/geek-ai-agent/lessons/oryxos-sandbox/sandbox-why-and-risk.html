為什麼 Agent 一定要有沙箱：風險模型與四維隔離

Step 1/4 · Sandbox

學習目標

能說出 Agent 情境為什麼不能沿用「信任自己寫的程式」的舊假設，並用檔案系統、網路、程序/系統呼叫、資源四維隔離去拆解任何沙箱要防守的風險面。

先看一件事：Agent 執行的是誰的指令？

傳統軟體的安全假設，建立在「你寫的程式裡做什麼事，你都看得懂」。一個 Java 服務不會自己半夜冒出一句「刪掉這台機器上所有檔案」——會出事的通常是不小心、是 bug，是程式設計師自己的失誤。

Agent 打破了這個假設。它會在運行時自己產生要執行的指令——這些指令是 LLM 當下「想」出來的，沒有一行經過人工審查。

這些指令可能來自四個源頭，全都不可信：

  • Agent 自己的破壞性失誤——模型一時糊塗，產生了刪檔、蓋檔、亂 call 的指令。
  • 提示注入（prompt injection）——網頁內容、郵件、別人的訊息都是潛在的惡意輸入，可以誘使 Agent 執行它原本不想做的事。
  • 工具回傳的「髒資料」——結果本身就是聲音，會被當成下一步決策的原料。
  • 多租戶、多 Agent 共存下的越界——租戶 A 的 Agent 絕不能讀租戶 B 的資料、影響租戶 B 的運行。

環境維度：五元件裡的 Environment

回到最早的 Agent 五元件心智模型（LLM + Tools + Memory + Loop + Environment），LLM 只管輸出結構化指令，真正執行的框架；沙箱就是 Environment 的安全設計——它決定了 Agent 的「能力天花板」也決定了「安全地板」。沒有隔離，你不敢讓 Agent 做任何有副作用的動作，它就永遠只是個只會聊天玩具。

用一句話記住這個位置：LLM 出主意，沙箱管底線。

四維隔離：拆任何沙箱的眼鏡

不管哪一套沙箱技術，翻來覆去都是在防守四個維度：

維度防守什麼出事畫面
檔案系統（Filesystem）不能任意讀寫主機檔案讀走 API key、設定檔、別人的工作目錄；把整顆磁碟蓋掉
網路（Network）不能任意向外連線把資料外洩（data exfiltration）、拿主機當跳板去打內網
程序/系統呼叫（Process/Syscall）不能做危險操作、提權fork bomb、掛載、改權限、影響主機其他行程
資源（Resources）不能吃光 CPU／記憶體／磁碟resource bomb 拖垮整台機器與其他租戶

這四個維度是後面所有內容的評估眼鏡：看到任何一個沙箱方案，先問「它四維各覆蓋到什麼程度？代價是多大？」下一課的四檔方案，本質就是「四個維度各用多深的邊界去擋」的取捨。

動手先摸一摸

你不需要現在寫任何程式。先做一次「風險盤點」：把你手上現有的 Agent（自己的 ReAct loop、或日常用 Claude Code／opencode）想一遍——讀檔、寫檔、跑 shell、發 HTTP 這四件事，目前有沒有任何一層在檢查？如果都沒有，你現在就站在「不敢讓它做有副作用的事」的那條線前面。
