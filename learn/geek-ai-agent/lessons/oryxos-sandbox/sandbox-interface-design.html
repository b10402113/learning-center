介面先行的 Sandbox 抽象：不讓第一檔帶偏

Step 3/4 · Sandbox

學習目標

能把「方向／介面／實作」三層拆開設計 Sandbox，讓介面只表達意圖（enforce 一個動作），並用「microVM 能不能乾淨塞進去」作為介面中性的反向驗證，且背出兩個升級訊號。

回顧：我們站在哪條線上

上一課看到四檔方案都是一條「強度 ↔ 開銷」線上的點。現在問題變成：如果今天只打算做第一檔，這道牆要怎麼設計，才不會在明年要升級到容器／microVM 時整面重寫？這一課的答案是一句可搬走的話：

方向現在就定，介面現在就釘，實作只做現在需要的。

設計原則：方向／介面／實作三層

為了多階段演進而設計，不代表現在就寫未來的程式碼，而是把工作切成三層、各用自己的節奏：

  • 方向現在定——應用層 → 容器 → microVM，以及各自什麼訊號觸發（下一步「升級訊號」）。
  • 介面現在釘死（最重要）——把「這面牆長什麼樣」定下來，這是所有投資回報率最高的一層。
  • 實作只做第一檔——但只用現在需要的量。

這三個動作的分界線是介面牆：牆之上的（抽象、契約）現在設計；牆之下的（具體實作）只寫現在需要的。這跟 Memory 模組的「方向／介面／實作」三合一原則、以及排程器是同一套系統思考。

介面表達意圖，不表達實作

最關鍵的設計準則：Sandbox 的介面抽象的是意圖——「在一個受控環境裡執行這個動作」——而不是實作。絕不放進「白名單」「容器 image」「VM 設定」這些字眼。

// 介面：只說要做什麼
interface Sandbox {
    void enforce(SandboxAction action);
}
record SandboxAction(ActionType type, String target); // enum + 目標

隔離的需求也不寫死在介面簽名裡，而是放在一個策略物件（strategy object）裡跟著走：允許的路徑／網域、資源上限、要求的隔離等級（basic／container／microVM）。

  • 每個檔次是一個獨立可插拔的實作，對應某個隔離等級。
  • 核心階段只有應用層實作，但介面＋策略保留了「隔離等級」這個維度。
  • 以後加容器 = 新增一個實作類別去回應 container 等級，不是介面修改——開／閉原則（open/closed principle）。

別讓介面被第一檔帶偏（最重要的一課）

當你只有一個實作時，最誘人（也最危險）的作法是把介面設計成「為這個實作量身打造」：方法叫 checkPath／checkCommand——但那根本塞不下一個容器（容器的回答是「我提供一個隔離的檔案系統」，不是「我檢查一個路徑」）。

解法：設計時想最重的那一檔（microVM），然後問「一個 microVM 實作能不能乾淨地塞進這個介面？」如果不行，介面就被第一檔帶偏了。

第二個提醒來自 Hermes 的警告：隔離介面必須為將來覆蓋 MCP 子行程與行程內能力留空間，不能焊死成「攔截一次工具呼叫」。OryxOS 的 enforce 只覆蓋工具執行路徑——MCP 子行程與行程內直接呼叫仍然裸露，這是階段一必須承認的邊界。

介面中性的反向驗證：KataMicroVmSandbox 測試

動手前的最後一個自我檢查：想像現在要寫一個 KataMicroVmSandbox。

  • 它需要新增方法嗎？不需要——乾脆地呼叫同一個 enforce(SandboxAction)，自己決定怎麼隔離。
  • 它的簽名裡會出現第一檔的字眼嗎？不會。

答案有任一個「是」，介面就被第一檔綁死了。

升級訊號：不是「大家都用容器」

升級永遠由真實的信任等級觸發，不靠趕流行：

  • 訊號 1（應用層 → 容器）：開始跑「相對不可信」的程式／指令，或需要多租戶。
  • 訊號 2（容器 → microVM）：要跑「完全不可信」的程式（例如公開上傳），或要靠強度＋密度同時放大一堆互相不信任的沙箱。
沒有訊號，就不升級。這叫「有訊號才動」——和 Memory、排程器的強度節制是同一條原則。

分階段路線總覽

階段做什麼隔離強度
第一天起（永久）介面層：意圖抽象 + 含隔離等級的策略，microVM 反向驗證—
核心階段應用層白名單（file／command／domain），零依賴、單二進位，誠實標為第一層勸阻第一檔
訊號 1 →容器隔離（namespaces + cgroups + seccomp，四維）第二檔
訊號 2 →microVM（Kata／Firecracker）第三檔

全程不變的三件事：網路出口管控、資源配額、全鏈審計——它們不隨隔離檔次而變。
