實作 WhitelistSandbox 並接進既有工具

Step 4/4 · Sandbox

學習目標

能用 Sandbox／SandboxAction／ActionType 最小物件先釘介面，實作 WhitelistSandbox 的三個私有檢查，並在每個 @Tool 方法開頭只加一行 enforce 接進既有工具。

這一節的邊界：只做最小的有用增量

上一課把介面牆釘死了。這一節做三件事：把介面背後的空白填上白名單實作，並把它接進既有工具。明確不做兩件事：不寫容器／microVM 實作，也不改 ToolExecutor 的審計邏輯——它的失敗路徑已經存在，一次沙箱拒絕就是一次很普通的工具失敗。

Sandbox 違規只是一隻普通的 RuntimeException。它從 Tool 丟出來，就自動走掉既有 success=false 的工具審計路徑——不需要任何新程式碼。

動手前先拆任務

實作順序與上一課的設計順序保持一致：

  1. 定義 Sandbox、SandboxAction、ActionType、SandboxViolationException 並凍結。
  2. 寫 WhitelistSandbox：讀 file.allowed_paths、shell.allowed_commands、http.allowed_domains 三個組態，做檔案路徑／shell 指令／HTTP 網域三個檢查。
  3. 在每個 Tool 的 execute 開頭插 sandbox.enforce(...)。
  4. 確認失敗路徑不需要新程式碼。
  5. 自我檢查介面中立性（想像一個 microVM 實作）。

全部放在 oryxos-tool 模組，既有的 IO 程式碼一行不動。

程式怎麼寫：最小物件先凍結介面

// 1. 介面：只表達意圖
interface Sandbox {
    void enforce(SandboxAction action);
}

// 2. 動作：type + target，沒有白名單/容器/鏡像字眼
record SandboxAction(ActionType type, String target) {}

// 3. 動作類型：讀寫拆開，為未來「讀/寫各自權限」留路
enum ActionType {
    FILE_READ, FILE_WRITE, SHELL_COMMAND, HTTP_REQUEST
}

// 4. 違規例外：復用既有工具的失敗路徑
class SandboxViolationException extends RuntimeException {
    public SandboxViolationException(String msg) { super(msg); }
}
注意介面紀律：SandboxAction 裡不放任何與白名單、容器、鏡像有關的字眼——那是上一課對意的介面的承諾。

WhitelistSandbox：三個私有檢查

@ConfigurationProperties(prefix = "file")  record FileSandboxProperties   (List<String> allowedPaths) { }
@ConfigurationProperties(prefix = "shell") record ShellSandboxProperties(List<String> allowedCommands) { }
@ConfigurationProperties(prefix = "http")  record HttpSandboxProperties  (List<String> allowedDomains) { }

class WhitelistSandbox implements Sandbox {
    void enforce(SandboxAction a) {
        switch (a.type()) {
            case FILE_READ, FILE_WRITE -> checkFilePath(a.target(), fileProps);
            case SHELL_COMMAND       -> checkShellCommand(a.target(), shellProps);
            case HTTP_REQUEST        -> checkHttpUrl(a.target(), httpProps);
        }
    }
    private void checkFilePath(String p, FileSandboxProperties props) {
        Path abs = Path.of(p).normalize().toAbsolutePath();
        if (props.allowedPaths().stream()
                .noneMatch(allow -> abs.startsWith(Path.of(allow).normalize().toAbsolutePath())))
            throw new SandboxViolationException("路徑不在白名單: " + p);
    }
    private void checkShellCommand(String cmd, ShellSandboxProperties props) {
        String firstToken = cmd.trim().split("\\s+")[0];
        if (!props.allowedCommands().contains(firstToken))
            throw new SandboxViolationException("指令不在白名單: " + cmd);
    }
    private void checkHttpUrl(String url, HttpSandboxProperties props) {
        // 精確匹配，或 *.example.com 萬用準配 api.example.com
        if (!allowed(props.allowedDomains(), hostOf(url)))
            throw new SandboxViolationException("網域不在白名單: " + url);
    }
}

三個檢查都設為 private，對外只暴露 enforce——這正是上一課「不讓介面被第一檔帶偏」的一次實作落地。

最常被漏掉的一行是這裡：Path.normalize().toAbsolutePath() 擋住了 ../../etc/passwd 這種目錄穿越——應用層最常見的洞。

接進既有工具：一行 enforce

正確的抽象讓接線成本小得不成比例：

@Component class FileTools {
    @Tool public ToolResult readFile(@ToolParam String path) {
        sandbox.enforce(new SandboxAction(ActionType.FILE_READ, path)); // ← 一行
        return doRead(path); // doRead 一行不動
    }
}
@Tool public ToolResult writeFile(...)  { sandbox.enforce(FILE_WRITE, path); return doWrite(path); }
@Tool public ToolResult shell(String cmd) { sandbox.enforce(SHELL_COMMAND, cmd); return doExecute(cmd); }
@Tool public ToolResult http_get(String url) { sandbox.enforce(HTTP_REQUEST, url); return doGet(url); }

對 ShellTools、FileTools（readFile／writeFile）、HttpTools 都是在 @Tool 方法頂端加一行；doExecute／doRead／doWrite／doGet 全部不動。NotifyTools 也一樣，在發送前先過 Sandbox.enforce(HTTP_REQUEST)。

驗收 Harness：allow + reject + bypass 三件套

測試照三個族群組織（檔案路徑／shell 指令／HTTP 網域），每一組都有三種：准（allow）、拒（reject）、繞（bypass）。

  • 相對路徑穿越：靠 normalize 攔截。
  • shell：第一個空白 token 的空白／大小寫變體。
  • 網域：精確匹配 + 萬用 *.example.com 匹配 api.example.com，但不匹配 evil-example.com。
那個經典的洞："evilexample.com".endsWith("example.com") 是 true——所以萬用匹配必須含「點邊界」（.example.com），否則 evil-example.com 就繞過去了。

其次，只斷言「丟了例外」是不夠的——接線回歸測試還必須證明真實 IO 沒有發生：verify(executor, never())，斷言被擋的輸入之下，真正的讀檔／寫檔／執行從沒被呼叫。「能不能被繞」比「准不准」更值得測。

做完怎麼驗

  • 真實鏈路整合：白名單只放 ls，跑一個被擋的指令，確認丟 SandboxViolationException、tool_invocations 出現 success=false 且 message 可讀。
  • 介面中立性自查：KataMicroVmSandbox 需要新方法嗎？不需要。
  • 組態語意寫清楚：空的白名單 = 「什麼都不准」，不是「跳過驗證」（fail-closed）。
  • 被改動的四個 Tool 原測試保持綠。

誠實的邊界：enforce 目前只覆蓋工具執行路徑；MCP 子行程與行程內直接呼叫仍然裸露，方向是未來做整個行程的隔離。
