spec-as-source：規格即源頭

Step 2/5 · SDD：規格驅動開發

學習目標

能講清 spec-as-source（規格即源頭）的推導鏈 spec → plan → tasks → code，以及支撐它的三大支柱（constitution、四階段閉環、analyze 防漂移），並分辨 SDD 與瀑布、Cursor Rules／AGENTS.md 的差別。

spec 是「源頭」，不是「附件」

上一歩說 SDD 要在提示詞之上加一層結構化需求層。這一歩要講清楚這層東西的地位：它不只是眾多文件中的一份，而是整個專案的源頭。

spec-as-source（規格即源頭）的意思是：spec 檔案本身就是專案的源頭，所有其他東西——plan、tasks、程式碼——都從 spec 派生。如果 spec 變了，下游一切都要重新生成。

這跟大部分的工程文件不同。一般文件是「做出來之後的紀錄」，改了程式碼未必改文件；spec-as-source 是反過來的：spec 是因，程式碼是果。你可以把它想成一條單向的推導鏈：

spec.md  →  plan.md  →  tasks.md  →  code
（要什麼）  （怎麼做）   （做哪些）   （產出）

鏈上每一環都是下一環的輸入。因為源頭只有一個，所以「需求改了」這種事只需要在 spec 改一次，下游能整條重算——這正是它能同時對抗需求漂移與架構失控的原因。

三大支柱

spec-as-source 不是只有一條推導鏈，它背後有三根支柱撐著。少了任何一根，推導鏈都會走歪：

支柱它做什麼為什麼重要
constitution（項目憲法）把專案的非協商原則（用什麼技術棧、什麼編碼規範、什麼測試要求）固化成一份 artifact，後續所有命令都引用它讓 AI 不再憑「感覺」決定專案方向；違反憲法的方案會在 plan 階段就被排除
四階段閉環每個 feature 都走完整四階段：specify → plan → tasks → implement，前一階段輸出是後一階段輸入沒有跨階段的 shortcut，沒有「跳過 plan 直接寫程式」
analyze（一致性檢查）跨 artifact 檢查：constitution 與 spec 是否一致、spec 與 plan 是否一致、plan 與 tasks 是否一致它是防「spec 漂移」的核心工具，發現漂移立刻修正

三大支柱的分工可以這樣記：constitution 管「不可協商的地基」，四階段閉環管「流程不許跳步」，analyze 管「各份文件不要各說各話」。前者是靜態約束，後兩者是動態檢查。

四份會生成的產物

跑完一輪，你在專案裡會看到四份關鍵檔案。它們正好對應上面的推導鏈與支柱：

檔案內容角色
constitution.md技術棧、編碼規範、測試要求等非協商原則整個專案期間寫一次、不輕易改
spec.mduser story、acceptance criteria、功能邊界、非目標源頭，所有下游從這裡派生
plan.md技術選型、模組劃分、資料流、關鍵技術決策把「要什麼」翻成「大致怎麼做」
tasks.md依 user story 組織的有序任務，標記依賴與可並行項把「方案」翻成「可執行清單」

AI 時代的 SDD 跟瀑布差在哪

「先寫需求文件再寫程式」聽起來很像瀑布開發。但兩者關鍵差別在於 spec 是活的還是死的：

  • 傳統瀑布的 spec 是「死的」：寫完就歸檔，跟程式碼同步全靠人工，最後一定脫節。
  • SDD 的 spec 是「活的」：AI 幫你維護它，讓它跟程式碼持續保持同步。

還有一層更深的分別：傳統瀑布的 spec 是給人看的；SDD 的 spec 是給 AI 看的（同時也給人看）。spec 等於是 AI 的 system prompt，更新 spec 就等於更新 AI 的工作上下文。這讓 spec 從「存檔」變成「運轉中的零件」。

它跟 Cursor Rules、AGENTS.md 差在哪

你可能會想：那我用 Cursor Rules 或 AGENTS.md 把背景交代清楚，不也一樣？差別在「靜態背景」與「強制工作流」：

機制本質它不做的
Cursor Rules / Claude Project docs給 AI 一份靜態 context 背景說明書不約束工作流：用什麼順序做、做什麼階段、產什麼 artifact，都沒規定
AGENTS.md給 AI agent 的靜態背景，描述專案是什麼、AI 該怎麼工作不強制產 spec、不強制產 plan、不強制產 tasks
SDD 工具工作流層：給 context 之外，還強制階段化—（它就是來規定「先 specify 再 plan 再 implement，不能跳」的）

一句話總結：Cursor Rules 和 AGENTS.md 只描述背景，SDD 還會生成正式 artifact 把決策固化下來，並強制階段順序。

SDD 的獨特價值

把 SDD 放進整個 AI 編程輔助譜系裡看，它的獨特價值有五點：

  1. 它是工作流層，套在 AI agent 之上，不替代 AI agent。
  2. 它強制階段化，從需求到程式碼有正式 artifact 流轉。
  3. 它把「決策」持久化，spec 跟程式碼一起版本管理。
  4. 它讓 AI 跟人有「協議」，spec 是雙方都遵守的契約。
  5. 它支持長期專案演進，不會因為 session 切換就丟失上下文。

所以 SDD 是 AI 編程從「作坊」到「工程」的關鍵一步。接下來兩步，我們要分別看它最成熟的兩種落地工具——重流程的 Spec-Kit，與輕流程的 OpenSpec——它們都把 spec-as-source 這套哲學做成了可操作的命令。
