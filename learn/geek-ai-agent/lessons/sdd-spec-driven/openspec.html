OpenSpec：輕武器的增量路線

Step 4/5 · SDD：規格驅動開發

學習目標

掌握 OpenSpec 的 delta-spec（ADDED／MODIFIED／REMOVED）與 Propose → Apply → Archive 三態流程，並說清 brownfield-first 為什麼是它不可被模仿的差異化。

它是什麼：哲學跟 Spec-Kit 正好對立

OpenSpec 是社群開源的 SDD 工具（Fission-AI 出品，2026 年 1 月發布 1.0），設計哲學跟 Spec-Kit 正好相反：輕量、靈活、增量友好。

它用 Node.js 寫，需要 Node.js 20.19.0 以上，裝好後用 openspec init 在專案裡初始化 openspec/ 工作區。它支援 30 多個 AI 編程工具（Claude Code、Codex、Cursor、Copilot 等），init 時會掃描專案裡既有的 AI 工具設定目錄並自動預選。

設計哲學：三個核心點

一、delta-spec 範式

Spec-Kit 每次都要求寫「完整 spec」；OpenSpec 要求寫的是 delta（增量）spec——只描述「這次改動相對於現有系統的差異」。delta 用三個 marker 標記：

marker意思
ADDED Requirements這次新增的需求
MODIFIED Requirements這次修改的需求（要寫明「之前是什麼」）
REMOVED Requirements這次刪除的需求

這是 OpenSpec 最關鍵的設計。因為每個 change 只描述差異，兩個並行的 change 可以同時修改同一份 spec 的不同 requirement，互不衝突；archive 階段再把 delta 合併回主 spec。

二、三態流程：Propose → Apply → Archive

OpenSpec 把每個 change 看成一個狀態機：

狀態發生什麼
Propose寫出這個 change 的 proposal、design、tasks、delta spec；此時還沒被實施
ApplyAI agent 按 tasks 執行生成程式碼；完成後程式碼就位
Archive把 change folder 移到 openspec/changes/archive/，並把 delta 合併到 openspec/specs/（主 spec）

每個 change 是獨立的 folder，多個 change 可以並行 propose、互不干擾，按需要的順序 archive。1.0 之後更升級為 action-based workflow——可以靈活編輯任何 artifact，不強制走完 Propose → Apply → Archive 的固定順序，比 Spec-Kit 的四階段剛性流程又更輕了一層。

三、brownfield-first

OpenSpec 官方文件用三個詞定位自己：fluid not rigid, iterative not waterfall, easy not complex, brownfield-first。它假設專案已經有程式碼，需求是「在既有系統上加 X、改 Y、刪 Z」，整個工作流都圍繞這個假設設計。

delta-spec 是 Spec-Kit 當下無法模仿的差異化。Spec-Kit 後來加了 brownfield 擴展，但 spec-as-source 的本質決定了它在既有專案上的工程開銷永遠大於 OpenSpec——因為它每次都要你面對一份完整 spec，而 delta-spec 只面對「這次的邊界」。

命令體系：以 /opsx: 觸發

OpenSpec 的命令以 /opsx:（OpenSpec 縮寫）前綴觸發。

profile命令作用
core（預設）/opsx:propose建立 change folder：proposal.md、design.md、tasks.md、delta specs
core/opsx:explore先跟 AI 討論，分析程式庫、比較方案、畫架構圖；不產 artifact
core/opsx:applyAI 按 tasks 執行生成程式碼
core/opsx:sync同步狀態、刷新 artifact graph
core/opsx:archive合併 delta 到主 spec，把 change folder 移到 archive
擴展（按需）/opsx:new · continue · ff · verify · bulk-archive · onboard多步驟流程、一次產一個 artifact、fast-forward、archive 前檢查、批量 archive、把現有專案接入

它還支援 custom schemas：可以定義自己的 artifact 類型（例如加一份 ADR 架構決策記錄、加一份研究報告），這比 Spec-Kit 更靈活。

典型工作流

  1. 初始化：跑 openspec init，掃描並選要啟用的 AI 工具，生成 openspec/specs/、openspec/changes/、openspec/AGENTS.md。既有專案可跑 /opsx:onboard 反向理解現況。
  2. 寫 project.md（新專案）：描述技術棧、整體架構、關鍵決策，是 OpenSpec 專案的「世界觀」。
  3. propose：跑 /opsx:propose add-dark-mode，AI 在 openspec/changes/add-dark-mode/ 下生成 proposal、design、tasks、delta specs。
  4. review proposal：人工讀 proposal、design、tasks，跟 AI 討論調整。propose 階段是設計協商，不是一次定終身。
  5. apply：跑 /opsx:apply，AI 逐個完成 tasks（例如「加 theme context provider → 建 toggle 元件 → 加 CSS 變數 → 接 localStorage」）。中途出問題可從斷點 resume，不用從頭來。
  6. verify（可選）：/opsx:verify 跨 artifact 一致性檢查，給 CRITICAL／WARNING／SUGGESTION 三檔報告，不阻塞 archive。
  7. archive：/opsx:archive 把 change folder 移到 archive/<date>-<name>/，delta 合併進 openspec/specs/<domain>/spec.md。
  8. 進入下一個 change：每個 change 獨立，archive 後立即能開始下一個，也可並行多個。

spec 怎麼寫：RFC 2119 加 Given/When/Then

OpenSpec 的 spec 用兩種標準寫法：

  • RFC 2119 keywords（MUST、SHALL、SHOULD、MAY）描述需求強度——明確區分「必須」與「應該」。
  • Given/When/Then 描述場景——這跟 BDD（Behavior-Driven Development，行為驅動開發）一致，方便每個 requirement 直接轉成測試案例。

適用邊界：它是「輕武器」

適合不適合
brownfield 增量改造：在既有專案上加／改／刪功能0 到 1 大型新專案：缺乏 constitution 這種憲法級強約束，新專案容易跑偏
多 change 並行：團隊多人同時做不同 feature，各 change 獨立不衝突企業合規重的專案：靈活變成「沒有強制門禁」，跨階段審計追溯不如 Spec-Kit
快速迭代節奏：3 態流程比 4 階段閉環更輕需要完整方法論訓練的團隊：成員可以「繞過」SDD 環節，對學習不利
小 feature 也願意上 SDD：流程輕，社群有人說「連小 feature 也願意走 SDD」—

一句話：OpenSpec 輕在流程靈活、artifact 少，缺點是約束力不夠。用在合適的場景體驗流暢，用在不合適的場景容易失控。

兩個工具的圖像都清楚了：一個是防跑偏的重炮，一個是防過度設計的輕騎。最後一步要做的，就是把它們放回你的專案情境裡選一個——甚至有時候答案是「兩個都不用」。
