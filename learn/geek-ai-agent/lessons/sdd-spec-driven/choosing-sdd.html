選型：什麼情況用哪種 SDD

Step 5/5 · SDD：規格驅動開發

學習目標

能用 greenfield／brownfield、專案規模與團隊成熟度選出對的 SDD 落地模式（Spec-Kit／OpenSpec delta／輕量手工），並判斷什麼情況根本不該用 SDD。

選型要同時看兩個軸

走到這裡你已經認識兩個工具，但選型不是「Spec-Kit 還是 OpenSpec」這麼簡單。實際上 SDD 有三種落地模式，而 Spec-Kit 與 OpenSpec 只是其中兩種：

模式核心動作工具
自動化模式AI 自動拆任務並執行，你寫 spec、檢查 plan、review 程式碼Spec-Kit
手動控制模式你自己拆任務，AI 只執行單一任務，每個任務完成你 reviewOpenSpec
輕量手工模式方案在腦中跑通，AI 一段一段執行，你一段一段 review不用 SDD 工具，只用 CLAUDE.md + Skill

輕量手工模式長什麼樣

第三種模式在實踐中很常見，卻很少被正式講。它的流程是：拿到需求後完整想透技術方案、模組劃分、關鍵決策、邊界處理——但不寫成 spec.md，就在腦中跑通，最多在紙上畫幾筆架構圖。然後把工作拆成一系列小任務，粒度小到「AI 一次能寫完、你一次能 review 完」，通常是一個函式、一個類、一段幾十行的邏輯。逐個交給 AI，寫完立刻 review，不滿意就改。

工具上只用 Harness 最基礎的兩件：CLAUDE.md 提供專案上下文與編碼規範，Skill 封裝重複模式。不用 Subagents、不用 Plan Mode、不用 Hook。它的優勢是品質可控、程式碼可 review、可維護、速度其實不慢、工具學習成本極低——但它不適合完全陌生的領域、需要大量探索的專案、規模過大的專案、純產品驗證型專案。

三種模式的本質區別：六個軸

把三種模式放在一起比，有六個本質區別。這六個軸是選型時真正要看的東西：

軸自動化（Spec-Kit）手動控制（OpenSpec）輕量手工
全局視角在誰手裡AI 同時持有全局（拆任務）與局部（執行），但全局是從 spec 推斷、失真嚴重永遠在人手裡，AI 只做局部永遠在人手裡，AI 只做局部
AI 誤差放大倍數兩輪推斷（拆＋執行），誤差相乘一輪推斷（僅執行）一輪推斷（僅執行）
任務粒度AI 決定，通常偏大（一整個功能甚至模組）你決定，一般按功能切最小：一個函式、一個類、幾十行邏輯
發現問題的時機最後 review 整體程式碼才發現，回溯成本大每個任務完成立刻發現，代價線性每段幾十行完成立刻發現，糾錯成本最低
工程師角色像產品經理：前期寫 spec、後期 review像團隊 leader：貫穿全程做工程決策就是工程師本人，只是把「敲鍵盤」外包了
對能力要求相對低，會寫 spec 是核心高：spec 寫作＋拆任務判斷＋review＋改 AI 程式碼最高，且不能藏拙

用一句話壓縮這張表：全局視角在你手裡越久、AI 的推斷輪數越少、任務顆粒越小、錯誤被發現得越早，你對產出的控制力就越強，但對你自己能力的要求也越高。

Spec-Kit 對 OpenSpec：兩種哲學

如果把焦點收回兩個工具本身，差別可以歸到三處：

維度Spec-KitOpenSpec
哲學spec-as-source：spec 是源頭，一切派生自它；像現代化的瀑布，主張嚴格上游設計delta-spec：spec 會成長，每次只描述差異；像工程化的敏捷，主張增量演進
流程四階段閉環，每階段有 artifact、禁止跳步；一致性和約束力強三態流程加 action-based 工作流，可靈活編輯；迭代快、壓力小
輸出量constitution＋spec＋plan＋tasks 完整下來，中等專案上千行，完整但厚重每次 change 是一份小 delta，archive 後併入主 spec，輕量但需長期維護主 spec

兩者輸出量差距約 3 倍——這是「Spec-Kit 重、OpenSpec 輕」最直接的體現。哲學沒有絕對對錯，greenfield 大專案用 spec-as-source 防跑偏，brownfield 增量專案用 delta-spec 防過度設計。

決策：什麼專案用什麼

情境選擇理由
新手／中級工程師，新專案從零，中等複雜度Spec-Kit用它建立 SDD 基本流程，即使產出不完美，也能在過程裡學會 SDD 思維
資深工程師，新專案從零，系統級OpenSpec 手動控制關鍵架構決策不能交給 AI，你必須全程在場；代價是高投入，但產出可控
資深工程師，熟悉的專案，增量或關鍵路徑輕量手工腦中能跑通整個方案，工具反而拖慢節奏；CLAUDE.md 加 Skill 就夠
老專案改造OpenSpec delta spec你不是在寫未來，是在改過去；delta 把「改什麼、不破壞什麼」工程化
開源貢獻（寫 PR）OpenSpec delta spec一個 PR 本質上就是一份 delta spec
團隊協作混用tasks.md 當對齊契約，關鍵任務手動控制、次要任務自動化

什麼情況根本不該用 SDD

選型也包含「選擇不用」。以下情境硬上 SDD 是 overkill：

  • 個人小工具：直接用提示詞加 Claude Code 就夠。
  • 小 feature、單檔改動、快速原型：流程開銷大於收益；社群共識是 Spec-Kit 的 800 行 spec 對小增量過重。
  • 探索性研究：需求未定就跑 spec 只會反覆返工。
  • 純產品驗證型專案：品質要求低、速度優先。

最後一條判斷

三種模式都該會，場景不同切換用。它們不是替代關係，而是互補關係：Spec-Kit 給你完整流程的腳手架，適合不熟的場景；OpenSpec 給你 delta spec 與手動控制的靈活性，適合改造與系統級；輕量手工給你最高的產出可控性，適合熟悉的場景。成熟的 AI 編程工程師工具箱裡，三種模式都該有。

還有一條學習路徑的建議：先選 Spec-Kit 學 SDD 範式，再切 OpenSpec 體驗增量風格。Spec-Kit 的強制流程是最好的方法論訓練場；反過來先學 OpenSpec 的風險，是容易養成「輕流程」的習慣，回頭再上 Spec-Kit 會覺得繁瑣。而無論你選哪個工具，要記住 SDD 的核心是思考方法——當你對專案足夠熟悉、規模可控、任務粒度天然小，SDD 的「想清楚再做」在你腦中就能完成，產物不需要外化，這不是 SDD 失效，而是它已內化成你的工作習慣。
