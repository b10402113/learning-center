Spec-Kit：重武器的完整流程

Step 3/5 · SDD：規格驅動開發

學習目標

掌握 Spec-Kit 的 6 個核心命令加 3 個可選命令與四階段工作流，並說清它為什麼是「重武器」、適合與不適合哪些場景。

它是什麼：套在 agent 之上的工作流層

Spec-Kit 是 GitHub 開源的 SDD 工具鏈，本質是一個 CLI 加一套 slash command 集合。它本身不是 AI agent，而是套在 AI agent 之上的一層工作流——負責規定 agent 按什麼階段、產什麼 artifact 地工作。

它支援 20 多個 AI agent（Claude Code、Copilot、Cursor、Gemini CLI、Codex 等），裝一次 Spec-Kit，用哪個 agent 都可以。它是 spec-as-source 最純粹的形式：spec 檔案就是專案源頭，plan、tasks、code 全從它派生，spec 一變下游全部重算。

設計哲學：三根柱子

Spec-Kit 的設計哲學可以用三點概括，恰好對應上一歩講的三大支柱：

  1. constitution 是非協商的項目憲法。每個專案第一件事是寫 constitution.md，把技術棧、編碼規範、測試要求等非協商原則固定下來。後續所有命令都引用它，AI 跑偏會被人工糾正。
  2. 四階段閉環：specify → plan → tasks → implement。每個階段都有正式 artifact，前一階段輸出是後一階段輸入，沒有跨階段 shortcut。
  3. 三個可選命令加強品質：clarify、analyze、checklist。不是必須，但嚴格專案裡強烈推薦，尤其 analyze——它是防 spec 漂移的核心工具。

核心命令體系：6 + 3

Spec-Kit 共 6 個核心命令加 3 個可選命令，都以 /speckit. 前綴觸發。

6 個核心命令（必走的閉環）

命令做什麼記法
/speckit.constitution寫項目憲法，定義非協商原則每個專案只寫一次
/speckit.specify把需求轉成 spec，產出 user story 加 acceptance criteriaspec-as-source 的源頭
/speckit.plan依 spec 加 constitution 生成技術方案含技術棧、模組、資料流、關鍵決策
/speckit.tasks把 plan 拆成有序任務，按 user story 組織標記依賴與可並行項
/speckit.taskstoissues把任務列表轉成 GitHub issues，方便專案管理選用於專案管理
/speckit.implementAI agent 按 tasks 逐個執行生成程式碼最後一步，前面備齊才能跑

3 個可選命令（加強品質）

命令時機作用
/speckit.clarifyspecify 之後、plan 之前AI 找出 spec 的模糊點，反過來問你，逼你回答，減少 plan 階段返工
/speckit.analyzetasks 之後、implement 之前跨 artifact 一致性檢查：constitution↔spec↔plan↔tasks，發現漂移立刻修正
/speckit.checklist專案客製需求時自訂品質校驗清單，如「測試覆蓋率達標」「公開 API 都有文件」

典型工作流

跑完一個 Spec-Kit 專案從頭到尾的標準流程：

  1. 初始化：裝 Specify CLI，跑 specify init 生成 .specify/ 工作區（含 constitution / spec / plan / tasks 等占位檔），選主 agent。
  2. 寫 constitution：跑 /speckit.constitution，AI 引導你回答專案類型、技術棧、非協商原則，生成 constitution.md。寫一次定下來。
  3. specify：跑 /speckit.specify，提供高層需求，AI 生成 spec.md（user story、acceptance criteria、功能邊界）。這份 spec 通常約 800 行，很厚但完整。
  4. clarify（可選但推薦）：AI 反問模糊點，你回答後 spec 被更新。
  5. plan：跑 /speckit.plan，AI 讀 spec 加 constitution 生成 plan.md。plan 階段會主動檢查與 constitution 的一致性，違反的方案不被採納。
  6. tasks：跑 /speckit.tasks，把 plan 拆成有序任務（典型幾十到上百個），按 user story 分組。
  7. analyze（可選但強烈推薦）：跨 artifact 檢查一致性，只讀不改，只報告問題。
  8. implement：跑 /speckit.implement，逐個執行任務。可一次跑完，也可一個一個跑（推薦後者，方便中途審查）。
  9. review 加 commit：每個任務完成後人工 review、git commit。人始終在 review 環節。

注意「人始終在 review」不是客套話。Spec-Kit 的自動化程度最高，但它同時也最容易讓人誤以為「AI 自己會搞定」。真正的人類工作被壓縮成三件事：寫第一份 spec、檢查 plan、最後 review 程式碼。

適用邊界：它是「重武器」

適合不適合
medium 到 large greenfield 專案（從零、中大型、跨多個資料夾）小 feature、快速原型、單檔改動（流程開銷大於收益）
需求清晰（上游有明確需求文件或產品決策）大型 brownfield 改造（legacy 上下文太複雜，context 不夠）
用 Claude Code、Copilot、Cursor 等 agent 做主體開發探索性研究（需求未定就跑 spec 會反覆返工）
團隊要學 SDD 工程方法論的場景個人快速實驗（6+3 個命令對一個人的小專案太重）

重在哪，代價是什麼

Spec-Kit 是「重武器」：重，在它強制完整流程、產出結構化 artifact；缺點是流程開銷大。它的代價也很清楚：

  • 任務拆分品質的天花板是你 spec 的品質。spec 寫得再好，也無法包含你腦中所有的工程直覺。
  • 兩輪推斷疊加：AI 拆任務一輪推斷、執行任務再一輪推斷，誤差是相乘而不是相加。拆任務對了 80%、執行對了 80%，最終只有約 64% 接近你真正想要的。
  • 任務粒度偏大：AI 在大任務裡更容易湊合、跳過、幻覺。
  • 最致命：AI 不理解時不會停下來問，而是編造一個看似合理的實作。你最後 review 整體程式碼時，已經發現不了「任務拆錯了」——錯誤源頭在前，代價在後。

tips：課後的 OryxOS 專案主體開發會用 Spec-Kit。可以先想一下——OryxOS 是從零開始的中大型 greenfield 專案、需求清楚、由 agent 主導開發，正好落在 Spec-Kit 的甜蜜區。

但如果你的專案不是 greenfield，而是在一個既有的專案上做增量改動，Spec-Kit 這門重炮就會顯得笨拙。下一個工具就是為此設計的。
