一輪 Loop 的原料：把技術方案變成可判定的任務

Step 2/5 · When Loop 模型與驗收體系

這一課要解決什麼？

你要能寫出一份會收斂的 Loop 原料，也就是 part doc 或任務卡。重點不是把文件寫得漂亮，而是把工作收斂成兩件事：Loop 知道要做什麼，也知道什麼時候算做完。

Loop 吃的是文件，不是模糊的任務

上一課把 When 拆成兩次執行。每次開跑前，都要先準備好這一輪的文件，也就是 part doc。它把技術方案中的一大塊，翻譯成 Loop 看得懂、做得到、驗得完的原料。

這份原料必須同時回答兩邊的問題：

  • 要做什麼：功能、互動與時序、介面、參數。
  • 怎麼算做完：驗收標準、必測項目、禁止事項，以及遇到不確定情況時必須停下來的邊界。

少了其中一邊，Loop 就像只有施工圖的一半：只有功能，卻沒有驗收，Loop 不知道何時該停；只有驗收，卻沒有功能，Loop 也不知道要蓋出什麼。

一份 part doc 的六個區塊

區塊要回答的問題
功能這一塊到底要做什麼？能不能用一句話說清楚？
互動與時序訊息進來後，誰先動、誰後動？什麼時候觸發？
介面對外提供 HTTP 還是 gRPC？輸入與輸出長什麼樣子？
參數與欄位有哪些欄位、型別、預設值與限制？
驗收與必測怎麼判定做對了？哪些情境一定要測？
邊界與禁止哪些程式碼或設計不能碰？什麼情況必須停下來詢問？

這六塊應該能在二十分鐘內寫完。寫不完，通常不是工具不熟，而是這一塊的設計還沒想清楚。這時不要急著開跑；文件本身就是第一個需要修正的地方。

最有價值的區塊：可判定的驗收

驗收是六個區塊裡最值錢、也最容易寫空的一塊。它有一個硬條件：可判定。也就是能直接轉成自動測試，執行後明確回答「對」或「不對」。

「效能應該好一點」或「使用者體驗要順」都不能拿來收工。這些句子沒有量尺，Loop 無法據此判斷該繼續修，還是可以停止。

你要把它壓成可量測的斷言，例如：

  • 延遲必須落在 1 秒到 1 小時的範圍內，且 99% 的投遞結果都在目標時間的 ±1 秒內。
  • Master 故障後，已儲存的 N 則訊息必須零遺失。

如果寫不出可判定的驗收，問題通常不在 Loop 不夠聰明，而在需求還沒被想清楚。這條規則看似嚴格，實際上是在開工前替你攔住模糊地帶，避免把錯誤一路帶進實作。

一輪 Loop 的執行順序

  1. 讀取 part doc，理解這一塊的目標與驗收方式。
  2. 建立隔離分支，讓失敗不會污染主線。
  3. 先寫測試，再進行實作，接著執行測試。
  4. 閱讀失敗訊息，定位問題並修正，再回到上一步。
  5. 全部測試通過後停止，把結果交給人 review。

有四種情況必須立刻停下來，不要硬撐：

  • 所有驗收測試都已通過。
  • 迭代次數超過上限，例如 15 輪。
  • 文件的語意不清楚。
  • 需要修改任務邊界之外的程式碼。

其中最重要的是「文件語意不清就停下來問」。一旦 Loop 開始猜測，錯誤可能會像滾雪球一樣，從一個模糊句子擴大成整段錯誤實作。

停止後的處理方式，和結果不符合期待時一樣：先修文件，再從乾淨狀態重新執行。這看起來比在對話裡和 AI 拉扯十輪更笨，實際上更有效，因為你是在修正輸入，而不是反覆擦掉同一個錯誤輸出。

從技術方案拆成任務卡

part doc 再往下，就能拆成一張張可派工的任務卡。拆分分成兩層：第一層是模組，也就是七個核心模組加上基礎設施；第二層是具體任務。

任務粒度抓在核心程式碼約 100 到 500 行，並且符合三個條件：單一職責、驗收清楚、不跨模組。切得太大，Loop 會失去方向；切得太散，則難以交付和 review。

一張任務卡應包含以下欄位：

  • ID 與標題：例如 TW-001 單層時間輪、RP-002 Master 到 Slave 的 gRPC 同步。
  • 目標：這張卡要完成什麼。
  • 輸入與輸出：從哪裡取得資料，要產出什麼。
  • 驗收：怎麼判定完成，而且必須可判定。
  • 禁止事項：哪些程式碼或設計不能碰。
  • 估時：預期的工作規模。

規則很簡單：一張任務卡對應一個 Issue，也對應一個 PR。任務清單不是開工前一次寫死的規格，而是一份會隨著 PR 演進的施工單。

卡住時，先修源頭，不要先怪 AI

Loop 跑不動時，常見原因通常有四種：

  • 驗收不夠清楚，代表規格不足。
  • CLAUDE.md 缺少必要約束，代表有約束缺口。
  • 缺少關鍵上下文。
  • 任務切得太大，代表粒度有問題。

這四種狀況都應該修正源頭，而不是只修 AI 產生的結果。你若只是把錯誤輸出改到看似能用，下一輪仍會從同一個缺口重新跌倒。

三個一定要避開的反模式

  • 開跑前不寫任務卡：等於沒有提供 Loop 的輸入。
  • 執行中途修改任務卡：等於一邊施工，一邊改設計圖。
  • 用對話中的臨時約束取代 CLAUDE.md：等於把規則鎖在某一次對話裡，下一次執行就消失。

會重複出現的約束，就應該沉澱進 CLAUDE.md。這樣每一輪 Loop 都能拿到同一份邊界，任務才會真的收斂，而不是每次重新靠記憶補洞。
