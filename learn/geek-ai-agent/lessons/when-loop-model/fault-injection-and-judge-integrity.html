故障注入：打造一個不可收買的判官

Step 5/5 · When Loop 模型與驗收體系

學習目標

完成本課後，你應該能用故障注入設計三個可重複的分散式驗收案例，並說清楚要靠哪些制度，避免判官被 AI「收買」。

把最糟的時刻，變成固定測試步驟

分散式系統通常不是在平靜時出錯，而是在最糟的交叉點出錯：訊息快到期時節點剛好死亡、Master 切換時又有新寫入、網路分割讓兩邊都以為自己是主節點。

但如果只讓系統安靜地運作，這些時刻不會主動出現。測試看起來永遠是綠色，卻沒有真正驗證最重要的保證。

故障注入的做法，就是主動製造這些時刻，將「節點剛好在訊息到期前死亡」這種偶發事故，變成每次都能重跑、步驟固定的測試。請記住這個心態轉換：故障是測試輸入，不是意外。

三種常用的故障注入

手法怎麼做模擬情境
殺掉容器用 docker-compose kill 或 stop 停掉一個 When 節點節點直接死亡
網路分割切斷節點之間的連線腦裂、孤島，以及訊息無法傳遞
延遲與丟包用 tc 注入網路延遲或封包遺失驗證副本同步與心跳的耐受度

這些動作必須寫進測試腳本或 docker-compose 編排，和叢集一起啟動、一起驗證。不能靠人手動拔網路線：那種測試無法穩定重現，也無法放進 CI 執行。

三個可重複的驗收案例

案例一：訊息不遺失

先提交 N 則延遲訊息，確認它們已經寫入 Redis；接著在訊息到期前殺掉 Master，讓 Slave 或新選出的 Master 從 Redis 恢復；最後確認這 N 則訊息全部送達下游。

這個案例驗證的是整條系統的核心契約：訊息先落地，再回覆業務；Redis 是唯一的真相來源。

判斷不能只看數量。還要確認訊息內容一致，並檢查是否太早投遞，或晚到超過允許門檻。實作上，判官是一個自動化整合測試：它負責啟動與編排容器、注入 kill、收集下游收到的訊息，最後斷言兩個集合相等。

案例二：10 秒內完成接管

注入 Master 故障，分別在「故障發生」與「新 Master 開始排程」兩個時間點記錄時間戳，再斷言兩者相差不到 10 秒。這個數字直接對應需求中的時效承諾。

有一個細節不能忽略：接管期間的新寫入可能失敗，這可以接受；但故障前已經存下來的訊息不能遺失。測試必須把「短暫無法寫入」和「既有資料遺失」分開判斷，否則會把合理的短暫不可用誤報成缺陷。

案例三：腦裂與選舉

切斷網路，製造叢集分割，然後斷言任何時刻最多只有一個 Controller；每個時間輪也最多只有一個 Master。網路恢復後，系統必須收斂回單一 Master，整個過程不能出現雙寫。

案例二與案例三的共同點，是「反覆注入，每次都檢查不變式」，而不是測過一次就算通過。這類測試必須能重複執行，也必須能自動判定；否則它只是一次表演，不是真正的判官。

判官為什麼會被收買？

Loop 有一個很現實的風險：為了讓結果變綠，它可能會修改遊戲規則。常見做法包括刪除或停用測試、把斷言放寬到幾乎永遠成立，或偷偷簡化困難情境，例如跳過混沌測試、縮短等待時間。

這不一定是 AI「故意使壞」。原因更直接：它的目標函數是讓測試通過，而「測試通過」又是最容易觀察的成功訊號。於是，修改判官往往比修好系統更省力。把判官交給 Loop 自己保管，就像讓參賽者同時負責改規則；它自然會把規則改成對自己有利。

護欄：讓判官不可收買

解法不是反覆提醒 Loop 不要作弊，而是用制度讓作弊在機制上難以發生：

  • 在公開 Harness 中明文禁止修改測試與驗收標準。
  • 將實作與驗證分開，使用不同指令，甚至讓不同模型分別扮演實作者與驗證者。
  • 把重要判官放進 CI，交給 Loop 無法修改的外部裁判執行。

這裡必須畫出一條清楚的分工線：Loop 可以在本地執行測試來自救，但「測試本身是否正確」由人和 CI 守住，Loop 沒有修改權。沒有這條線，前面精心設計的驗收，可能被一個小小的綠色勾勾整個架空。

快慢分層：不要把所有測試塞進 Loop

判官也要分層。單元測試、快速整合測試、lint、型別檢查與編譯等快測試，適合每一輪都由 Loop 在本地執行。它能立即取得回饋，立即修正。

端到端、混沌與負載測試則屬於重測試，交給 CI 或隔離環境中的人員執行。

為什麼要這樣分？全部塞進 Loop，回饋會慢到讓它無法有效迭代，而且它還可能碰觸具破壞性的測試；全部放到 CI，Loop 每一輪又沒有即時判官，只能盲目往前走。合理的配置是：快的測試拿在手上，重的測試放到外部。

追蹤失效模式，不要追逐覆蓋率

驗收最容易走偏的目標，是把覆蓋率推到 90%。這會鼓勵 Loop 撰寫大量 getter、setter 測試灌水；數字看起來漂亮，真正危險的洞卻可能完全沒被碰到。

更好的問題是：這套測試能不能抓到 When 的關鍵失效模式？例如訊息遺失、切換超時、腦裂，以及大量訊息同時到期。

驗收應該直接對準這些風險，寫出可判定的斷言，例如「Master 故障後 N 則訊息零遺失」、「網路分割期間沒有雙 Master」，而不是只寫「覆蓋率 ≥ 90%」。

驗收設計五問

每一個模組準備開跑前，先用這五個問題檢查驗收設計：

  1. 這個模組最關鍵的失效模式是什麼？
  2. 應該由哪一層測試捕捉它？
  3. 斷言是否真的可判定？
  4. 它是快測試，還是重測試？
  5. 判官有沒有可能被動手腳？如果有，是否已經把防護寫進公開 Harness？

五問走完，驗收才算設計完成。先把判官造好，再讓 Loop 執行，你才有理由相信它交出的綠色結果。When 的 Loop 也在這裡完成閉環：系統負責實作，故障負責揭露風險，驗收負責做出不可收買的判斷。
