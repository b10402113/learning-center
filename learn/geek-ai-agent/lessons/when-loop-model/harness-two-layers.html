兩層 Harness：公開護欄與模組驗收

Step 3/5 · When Loop 模型與驗收體系

學習目標

讀完這一課，你應該能分清兩件事：公開 Harness 是一開始就建好的共用紅線；模組 Harness 則是跟著任務卡走、負責驗收單一模組。也要知道每一層該放什麼，避免把所有規則混成一團。

Loop 會放大 Harness 的品質

Loop 的本質，是一台高速反覆運轉的機器。每一輪都會問三個問題：「我做對了嗎？符合規則嗎？安全嗎？」答案不在 Loop 自己身上，而在 Harness 裡。

Harness 夠強，Loop 才能逐輪修正，慢慢收斂到正確結果；Harness 夠弱，Loop 也會很有效率地把錯誤放大。速度越快，錯誤累積得也越快。

所以 Harness 不是附加配套，而是整套流程的決勝點。你花時間把規則和驗收建好，後面就少幾輪重工。

可以把它想成自動化產線：Loop 是不停運轉的機器，Harness 則是品管和安全規範。產線不會因為能自動運轉，就不需要品管；正好相反，跑得越快，越需要可靠的檢查。

Harness 同時守住三件事

面向內容它在守什麼
代碼結構、命名、分層與 lint 規則產出的程式碼能不能長期維護
安全禁止硬編密碼、使用依賴白名單、不提權，密鑰一律走環境變數避免 AI 為了跑通而跨過安全紅線
驗收單元測試、整合測試、CI 與端到端測試提供 Loop 唯一可靠的判定依據

三者之中，驗收是 Loop 的命脈，也是下一課的主角。本課先把整體分層講清楚：哪些規則全專案共用，哪些規則只屬於目前這個模組。

兩層 Harness：共用紅線與模組驗收

Harness 不是一整包規則，而是分成兩層。兩層的責任不同，建立時機也不同。

公開 Harness模組 Harness
建置時機專案一開始就建好，全專案共用跟著每個部分的任務卡建立
內容安全紅線、代碼規範與 lint、CLAUDE.md 上下文、CI gate該部分專屬的驗收測試與邊界約束
寫在哪專案根目錄與 CI 設定對應的 part doc
比喻工廠共用的安全規範與品管流程每張工單附上的檢驗表

順序不能反過來：先建好公開 Harness，再讓每個模組帶著自己的驗收。

如此一來，Loop 不管正在處理哪一塊，都會待在同一組共用護欄裡。如果每個模組都各自發明一套規則，最後很可能出現互相衝突的標準。Loop 看似有很多規則可遵守，實際上卻更難判斷該聽誰的。

公開 Harness：全專案共用的地板

公開 Harness 主要來自專案根目錄的 CLAUDE.md 與自動化設定。它不該變成知識百科，而應該只放真的會改變 AI 行為的規則。雜訊太多，重要約束反而會被淹沒。

  • 根目錄 CLAUDE.md：說明專案身分、技術棧與版本約束，以及禁區和基本原則。
  • 核心模組各自的 CLAUDE.md：例如時間輪模組必須宣告執行緒安全，使用 ReentrantLock，且禁止阻塞式 IO。
  • Skills：把反覆出現的標準動作固定下來，例如新增 Sink、新增 API 端點或新增指標。同一種模式第三次出現時，就該考慮把它沉澱成 Skill。
  • Hooks：執行自動格式化、lint 與測試，例如 Spotless、Checkstyle／SpotBugs／PMD、JaCoCo 加 Surefire，以及完整的 Maven build。
  • CI gate：把上述檢查變成合併前必須通過的關卡。
  • Plan Mode 規則：遇到高風險操作時，強制先提出計畫再動手。演算法、儲存或協定的變更，大型重構，以及超過 50 行或超過 3 個檔案的改動，都屬於這類操作。

模組 Harness：這一塊自己的判官

模組 Harness 跟著任務卡走，範圍比較窄，只處理目前這一塊的驗收測試與邊界約束。

例如 Redis 儲存插件，模組 Harness 會規定原子狀態轉移要怎麼測，也會規定不能依賴其他實作模組。這些要求不一定適用於整個專案，卻是判斷 Redis 儲存插件是否完成的關鍵。

可以這樣分工：公開 Harness 管全專案的地板，確保所有程式碼至少符合共同的安全與品質標準；模組 Harness 管這一塊的天花板，定義它要做到什麼程度才算完成。

兩者缺一不可。只有公開 Harness，Loop 可能守規則卻做不完任務；只有模組 Harness，Loop 可能知道局部目標，卻踩過全專案的安全紅線。

七個會讓 Harness 失效的反模式

  • 把 AI 當成 IDE 的自動完成，只讓它補幾行，卻沒有交付完整任務。
  • AI 寫完後由人整段重寫，等於白跑一趟，也失去從結果中學習的機會。
  • 一半由人寫、一半由 AI 寫，兩者混在一起，最後沒人說得清楚哪段程式碼是誰負責的。
  • 沒有 review 就直接合併；沒有實質檢查的批准，不算 review。
  • 用對話中的臨時約束繞過 CLAUDE.md，讓重複出現的規則永遠無法沉澱。
  • 任務進行到一半才修改任務卡，讓 Loop 一邊施工、一邊被迫改圖。
  • 不斷增加工具數量，卻用工具堆疊掩蓋自己其實沒有想清楚規則與責任。

這七個壞習慣的共同問題，是讓 Harness 失去約束力。Harness 一旦失效，前面談到的兩層 Loop 和可判定驗收也會一起失靈。

真正可運作的結構很簡單：先用公開 Harness 固定全專案的紅線，再用模組 Harness 定義每張任務卡的完成條件。Loop 才有一致的規則可守，也有明確的結果可以判定。
