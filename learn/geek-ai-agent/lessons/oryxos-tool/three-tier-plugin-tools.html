三級 Plugin Tool：零代碼、輕代碼、重代碼

Step 3/5 · Tool 體系

學習目標

能說出三級 Plugin Tool 各自的適用場景與代碼量（方式一零代碼 SKILL.md＋MCP、方式二自寫 MCP server、方式三 @Tool Java Bean），並遵循「能用方式一就不用方式二，能用方式二就不用方式三」的選型規則。

業務要的不是「又一種工具」，是「我能自己接」

平台作者把九個內建工具寫好很容易——難的是讓企業自己把「查 CRM」「推 Slack」「拉 GitHub PR」這些自家能力接進 Agent。這條路不能只給一種走法：有的業務想要零代碼、半天接完；有的業務願意寫程式、要深度整合。OryxOS 於是設計了三級 Plugin Tool，按代碼量從零到重排成一條漸進的階梯。

方式一：零代碼——SKILL.md ＋ 複用現成 MCP server（推薦首選）

場景：市面上已有開箱即用的 MCP server（GitHub、Slack 都有社區版的），你只要把它接上，再寫一段「任務說明」教 Agent 怎麼用。

做法只有兩步：

  1. 寫一個 markdown 的 SKILL.md——frontmatter 帶 name、description、trigger、required_tools 等欄位，正文寫任務描述（例如「把每日 PR 摘要推送到某 Slack 頻道」）。
  2. 在 Profile 裡引用這個 skill，並把對應的 MCP server 配置進 mcp_servers.yaml。

OryxOS 啟動時把 SKILL.md 內容注入 system prompt，模型自己決定用哪些 MCP 工具、怎麼組合完成任務。注意一個關鍵設計：OryxOS 不解析任務步驟、也不跑 workflow 引擎——它把判斷完全交給模型。也正因如此，SKILL.md 歸 ContextLoader（上下文裝載）管，而不是 Tool 系統管；它不是一個會被執行的工具，而是一張「給模型看的說明卡」。

代碼量：零。這是教學 Demo 三的標準示範——業務方寫一份 daily-pr-digest.md、接 github-mcp 和 slack-mcp、建一個 Profile，第二天就能跑。

方式二：輕代碼——自己寫一個 MCP server

場景：社區沒有現成 server，但你願意寫一點程式（任何語言都可以），把自家系統包成標準的 MCP 服務。某些 SDK 語言，例如 Go、Python、TypeScript，都有 MCP 官方或社區 SDK，寫一座「橋」接自家 API 即可。

做法：McpClientService.connectAll 在啟動時讀 .oryxos/mcp_servers.yaml，透過 stdio 或 SSE 連上你的 server，呼叫它的 tools/list 拿到工具清單，把每一條包成 McpToolAdapter 註冊進系統。之後模型呼叫時，adapter 用 JSON-RPC 把請求轉給你的 server。

這裡有一條很重要的韌性設計：某個 MCP server 連不上，只記 WARN、跳過它，絕不讓整個系統啟動失敗。外部依賴不該成為內部的單點故障。呼叫失敗則被包成一個 retryable 的 ToolResult 交給迴圈決定重試。

代碼量：中——一座跨語言的小服務。對比方式一，你能把自家獨有邏輯完整放進工具。

方式三：重代碼——用 Spring AI 的 @Tool 寫 Java Spring Bean

場景：工具就要跟 Java 核心深度整合——要直接呼叫內部 Java 服務、要重用 Spring Bean、要跟 Spring Security 一起做權限，全部在進程內完成，不經過 MCP、不做序列化。

做法：把 Spring AI 的 @Tool 註解標在一個 Java 方法上，啟動時系統掃描並註冊成 OryxTool。跟內建工具的寫法一模一樣，性能最好。

代碼量：高——你要寫 Java、過 Spring 的生命週期。這是整合深度換來的，通常在企業想讓 Agent 直接操作自家核心系統時才值得。

選型規則：能用簡單的，就不用複雜的

三條路不是並排任挑，而是有明確的優先順序：

能用方式一就不用方式二，能用方式二就不用方式三。

為什麼？方式一代價最低且可維護性最好——它不寫代碼，純由模型驅動；方式二把邏輯放進自家可控的服務，但要維護一座 server 的生命週期；方式三最強，卻把自己綁死在 Java 進程裡，只有當「深度整合是剛需」時才值。

這條規則保證平台新增業務能力的成本跟業務的複雜度成比例——簡單的事用便宜的方式，複雜的事才付出高的代價。而不管選哪一條，對 OryxTool 那張統一的臉來說，一切照舊。

一步一驗

接完之後怎麼確認真的能跑？加工具遵循同一套三級路徑，用 oryxos tool list 看註冊結果。方式一：SKILL.md 做好、真實 MCP server 在線，跑一次任務應該真的完成（例如真的把 PR 推到 Slack）。方式三：@Tool 的範例要能出現在清單、能被呼叫。而且每一筆工具呼叫都要寫進 tool_invocations 審計表——驗證時直接看有沒有這筆記錄。
