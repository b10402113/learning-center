把內建工具補齊到業界水準

Step 5/5 · Tool 體系

學習目標

能說出對標 Claude Code／Cursor／OpenAI Assistants 後補上的五個高頻工具（edit_file／ask_user／grep／glob／web_search）各自的設計要點，並解釋「好抽象讓新增工具成本恆定」的道理。

九個工具就夠了嗎？拿去跟行家比一比

上一課我們有九個內建工具、三級插件、統一的執行鏈——一切都很完整。但當你真的拿 OryxOS 去跟 Claude Code、Cursor、OpenAI Assistants 這幾位「行家」比，會發現一件事：別人搜尋、改檔、問人、查網路都有一整套，我們的核心列表還太薄。工具清單不是「加上就是贏」，而是要用真實工作頻率去對標。這一課就是一次成品審視：缺了什麼、補上什麼、補完之後驗證什麼。

五個從業界實務補上的高頻工具

對標完畢，缺了五個高頻使用、而且跨 Agent 都通用的工具。它們是「基礎工具」不是「業務能力」，所以該放進內建清單：

1. edit_file：唯一且精準的原地替換

寫檔案很容易，但要「在長檔裡改一小段」就需要精確度。edit_file 的做法是唯一舊文本替換：你必須提供「要替換的舊文字」與「新文字」，工具在檔案裡找這一段。找不到就報錯，找到多個也報錯——寧可失敗，也絕不誤改。這是把「該改哪」的決定權交給模型，同時把「絕不改錯地方」的底線焊死。

2. grep：正規表示式的內容搜尋

依檔名找檔是 list_dir／glob 的事，但「在內容裡找關鍵字」得靠 grep。設計上它有兩個保護：一次最多回 200 筆結果（防止記憶體爆炸），並跳過二進位與非 UTF-8 檔（避免把亂碼塞回上下文）。

3. glob：萬用字元的檔名搜尋

用 **/*.java 這種 wildcard 描述要找哪些檔，跟 grep 共用同一個 200 筆上限。

4. ask_user：把人類拉進審查迴路

Agent 不該永遠自作主張——碰上「要不要刪這個資料夾」「這個金額對嗎」，正確動作是停下來問人。ask_user 透過一個 UserInteraction 介面完成，介面下有兩個實作：Console（CLI 下即時問答）與 Unsupported（不支援此渠道時，直接回傳「此環境不支援人工確認」）。介面先行，是它最重要的設計。

5. web_search：讓 Agent 能查最新網路資訊

要查「今天」的即時資料，光靠 http_get 撞特定網址不夠，需要真正的搜尋。它透過 SearchProvider 介面接上搜尋引擎，預設用 DuckDuckGo。因為它本質上是網路請求，自然走 http_get 的網域白名單，安全檢查照舊生效。

「新增工具成本恆定」才是真正的考驗

五個工具各有各的新邏輯，但把它們加進系統的成本，說起來會讓你吃驚：每加一個，只需要「寫一個類 + 註冊一個 adapter」。為什麼這麼便宜？

  • Sandbox 檢查——不用改，自動套用（edit_file 走檔案白名單、web_search 走網域白名單）。
  • tool_invocations 審計——不用改，執行鏈自動記錄。
  • Profile 過濾——不用改，tools 欄位照樣篩。

這正是前三課那套抽象（統一 OryxTool、單一 ToolExecutor、白名單在先）的兌現：好抽象讓「新增工具」這個動作的成本保持恆定、不隨數量成長。反過來說，如果某天你發現「加個工具還要改核心」，那就是抽象破功的警訊。

用四大測試區塊驗證整套設計

加了新工具不能拍拍屁股就說完成，需要用測試把行為釘住。課程給了一套「驗收 harness」，四大區塊：

  1. OryxToolContractTest——參數化跑過每一個註冊的工具，斷言 name／description／inputSchema 都不為空。任何一個工具漏了 getInputSchema，立刻被紅旗標出（否則 Provider 的 Function Calling 翻譯會卡死）。
  2. ToolRegistryTest——驗證三種來源都註冊成 OryxTool，Profile 過濾後拿到「不多不少」的精確子集。
  3. FileToolsTest／ShellToolsTest／HttpToolsTest——每個工具的「正常＋被擋」兩條路：正常該成功就成功，白名單外該被擋就要被擋。
  4. McpToolAdapterTest／McpClientServiceTest——用 mock client，驗證壞掉的 MCP server 只記 WARN、不拖垮啟動。

這套 harness 跟「抽象價值」是同一枚硬幣的兩面：抽象讓加工具便宜，測試確保便宜不等於隨便。

回到本節的意義

把九個補到十四個，不是湊數量，而是完成一次「對標業界 → 補齊基礎 → 驗證抽象」的閉環。你現在手上握著整套 Tool 心智模型：統一抽象（OryxTool＋ToolResult）→ 三級插件（零／輕／重）→ 唯一執行鏈（Registry＋Executor＋白名單）→ 好抽象讓成本恆定。閉上眼，你應該能回答：一個新業務工具要進 OryxOS，我會走哪條路、在哪裡被檢查、會被記錄到哪——這，就是這個節點真正要交付的東西。
