ToolRegistry、ToolExecutor 與安全白名單

Step 4/5 · Tool 體系

學習目標

能說出 ToolRegistry 如何匯集三種工具來源、Profile 如何用 tools 欄位過濾工具子集，以及每次工具執行前為何必須先通過路徑／命令／網域白名單的 Sandbox 檢查。

一把「所有工具都得經過」的門

前三課讓我們有了統一的 OryxTool，也有了三種插件方式。但工具這麼多，總得有個地方把它們收在一起、讓迴圈能找得到——那就是 ToolRegistry（工具註冊表）。而真正「動手前一刻」的關卡，則在 ToolExecutor（工具執行器）與 Sandbox 檢查。本課把這三件事連成一條完整的執行鏈。

ToolRegistry：三種來源，一本總清冊

ToolRegistry 是唯一知道「世界上有哪些工具」的地方。它囊括三種來源：

  • 內建工具＋方式三的 @Tool Java Bean：啟動時掃描自帶的 @Tool 方法，統統包成 OryxTool。
  • 方式二的 MCP 工具：McpClientService 連上的 server，每個 tools/list 條目也包成 OryxTool 註冊進來。

所以不管你用哪種方式加工具，最終都是把自己交進 ToolRegistry 這本總清冊。設計上的一個關鍵決定：註冊表只用「名稱」當鑰匙，反覆強調「顯式映射」而非類型掃描。

但工具不能不分青紅皂白全給每個 Agent 用。一個只管天氣查詢的 Agent，不需要（也不該要）shell 權限。於是每個 Profile（Agent 的設定檔）帶一個 tools 欄位，列出這個 Agent 可以使用哪些工具。ToolRegistry 提供全部，Profile 過濾出子集——迴圈在組 prompt 時只把這個 Agent 允許的工具清單列給模型，等於做了最粗一層的極小權限。

ToolExecutor：唯一的執行路徑

工具找到了，接著就要執行。OryxOS 規定一條鐵律：執行工具的路徑只能有一條 ToolExecutor，迴圈不能繞過它直接用某個工具實作。它的流程是固定四步：

  1. 按名稱找工具——從 ToolRegistry 依名字撈對應的 OryxTool。
  2. 過 Sandbox 白名單——動手前先檢查這次操作是否在允許範圍內（下一秒詳述）。
  3. 執行並包裝——呼叫 execute，把結果包成 ToolResult（success／content／errorMessage／retryable）。
  4. 寫入審計——把這次呼叫（工具名、參數、結果、成敗）寫進 tool_invocations 表。沒有查詢介面也照寫，這是「可審計」的底線。

這條路徑同時解決了兩個問題：一是執行權收斂，任何工具都得經過同一套檢查與記錄；二是審計完整，之後任何「這工具幹了什麼」的疑問都有據可查。

Sandbox 檢查：動手前先過安全門

核心階段的安全治理，靠的是「每次執行前面對世界的一張白名單」。JDK 21 早已沒有 SecurityManager，所以 OryxOS 用應用層的白名單檢查達成隔離。它按工具觸碰的資源分類：

資源白名單內容受保護的是
檔案允許的路徑（file.allowed_paths）Agent 只能碰工作區內能寫的目錄，不能亂讀系統檔
命令允許執行的命令（shell.allowed_commands）只能跑白名單裡的命令，例如 git、python
網路允許的網域（http.allowed_domains，用萬用字元）http_get 只能打允許的 API 網域，防跳板、防 SSRF

檢查失敗就拋 SandboxViolationException，這次執行到此為止，不會真的動手。這張白名單的設定寫在 application.yaml，屬於「應用層配置」，是核心階段唯一的工具治理機制。

「先檢查、後執行」是一條硬規則

注意一個很容易被忽略、卻是最重要的設計：檢查必須在 execute 之前，且內建工具自己也要做。以 http_get 為例，它的真實作法是「先呼叫 sandbox.enforce(...) 檢查目標網域，再發請求」——不是等資料都抓回來才發現被擋。任何一個新工具寫出來，都要遵守同一個「先檢查後動手」的節奏，這樣安全就不是事後補丁，而是焊在執行鏈裡的一環。

把這課跟上一課結合：不管工具來自方式一、二、三，進了 ToolRegistry 就是 OryxTool；不管它是誰，都要過 ToolExecutor 這條唯一的門；不管它多遜，動手前都得過白名單。三層疊起來，就是「全部收編、統一入口、先查再動」的完整治理。
