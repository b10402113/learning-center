OryxTool 單一抽象與 ToolResult

Step 2/5 · Tool 體系

學習目標

能說明 OryxTool 的四個方法（getDescription／getName／getInputSchema／execute）與 ToolResult 的四個欄位，並解釋為何 ReAct 迴圈不必知道工具來自內建、MCP 還是 Java Bean。

從「九個工具」到「一種工具」

上一課數出了九個內建工具，之後還會有插件工具、MCP 工具、Java Bean 工具。如果每個工具都長得不一樣——有的用 JSON、有的用 YAML、有的直接把方法名當名字——ReAct 迴圈就得懂每一種，每接一個新工具就要改一次迴圈。這正是模組化最怕的噩夢。

解法是在動手寫工具前先做一個設計決定：把所有工具抽象成同一個介面 `OryxTool`。內建的、MCP 的、Java Bean 的，通通包裝成這個介面；對外只有一張臉，裡面愛怎麼做都行。

OryxTool：四個方法

介面非常小，只有四個方法——這是刻意的。方法越少，任何工具就越容易滿足它：

  • getName()：工具的唯一名稱，例如 read_file。模型靠這個名字指定要呼叫誰。
  • getDescription()：一段給模型看的人話描述，說清楚這工具做什麼、何時該用。模型靠它決定「這步我該不該呼叫這個工具」。
  • getInputSchema()：描述輸入參數的 JSON Schema 文字。Provider 在翻譯 Function Calling（函式呼叫）時消費它——沒有它，模型不知道該傳哪些參數。這是早期版本最常被漏掉的方法，一旦漏掉，Function Calling 直接卡死。
  • execute(JsonNode input)：真正執行的入口。輸入是 JSON 節點，丟回一個 ToolResult。整個 Agent 的努力，最後就是落在這一行上。

注意 getInputSchema() 是「字串」不是物件——它是 JSON Schema 的文本，等著被 Provider 拿去轉成各家模型 API 的格式。這把「工具的輸入長怎樣」這個問題，從核心完全剝離出去。

ToolResult：四個欄位

執行完工具，迴圈要的不只是一段文字，而是一個「可判斷成敗」的結果。ToolResult 用四個欄位表達這件事：

欄位意義
success這次執行是成功還是失敗
content要交給模型看的實際內容（例如天氣 JSON）
errorMessage失敗時的錯誤訊息
retryable這個失敗值不值得重試——外部服務暫掛通常可重試，業務邏輯錯誤則不行

retryable 是容易被忽略但極重要的一欄：它讓「這次失敗了」多了一個維度。迴圈可以根據它決定「是不是拉高重試」「要不要把錯誤原樣丟回給模型讓它換個策略」。一個 API 暫時連不上是暫時性失敗，而「參數格式寫錯」是謬誤——兩者後續的處理完全不同。

為何統一抽象：三個來源，一張臉

OryxTool 的價值在於「來源無知」（source-agnostic）。上一課的分界在這裡兌現：

  • 內建工具（FileTools、ShellTools、HttpTools）直接實作 OryxTool。
  • MCP 工具被包成 McpToolAdapter——把 MCP server 的 tools/list 條目包進同一個介面，對外看不出是跨進程。
  • Java Bean 工具（下一課的第三種插件方式）也包成 OryxTool。

結果是 ReAct 迴圈根本不需要知道自己呼叫的「手」是內建的還是外部的。它只跟 OryxTool 打交道，程式整個乾淨了。這也解釋了為什麼 OryxTool 的依賴只有 Jackson 的 JsonNode——刻意保持零框架依賴，任何來源都能輕鬆包裝。

設計帶來的附帶好處

統一抽象不只是為了好寫程式，它同時是治理的入口。既然是「所有工具都得過這張臉」，那「在每次執行前加一道檢查」就有了天然的位置——那道檢查就是第四課的安全白名單。抽象的價值，於是在安全、審計、測試這些橫切面上全部放大。
