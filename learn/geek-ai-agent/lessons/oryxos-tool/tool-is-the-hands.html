Tool 是什麼：Agent 的「手」

Step 1/5 · Tool 體系

學習目標

能說出 LLM 只產文字、工具讓 Agent 真正動手（讀檔案／跑命令／呼叫 API），並數出核心階段九個內建工具各自的定位，以及內建 Tool 與 Plugin Tool 的分界。

先看一個「只會想、不會做」的模型

你把「幫我查北京今天天氣、建議穿什麼」丟給一個純 LLM。它會回你一段很漂亮的文字，但如果你真想要「今天」的氣溫，它做不到——它只能訓練時學過的舊資料裡猜。為什麼？因為 LLM 本質上只產文字：它沒有手去開瀏覽器、沒有鍵盤去敲指令、也沒有權限去讀你磁碟上的檔案。

於是 Agent 的架構裡有個明確分工：Loop（迴圈）負責想，Tool（工具）負責做。迴圈每一輪讓模型決定「下一步要不要動手、動哪一雙手」；只要模型說「要查天氣」，迴圈就把這個請求交給對應的工具去執行，再把真實結果拿回來給模型看。這就是 ReAct 迴圈裡那個「Act（行動）」步驟的具體實作——工具是 Agent 名副其實的「手」。

核心階段的九個內建工具

既然是「手」，先備齊最基本的幾雙。OryxOS 核心階段內建了九個工具，可以分成四個領域。記住它們不難——因為每一類剛好對應 Agent 要碰的一種世界：

領域工具做什麼
檔案read_file／write_file／list_dir讀、寫、列出檔案與目錄——Agent 工作區的基本盤
命令shell執行一條命令——讓 Agent 能跑測試、起服務
網路http_get／http_post發 HTTP GET／POST 請求——呼叫天氣、抓網頁、打業務 API
記憶save_memory／recall_memory寫入／讀回長期記憶（MEMORY.md）——跨對話記住偏好
通知notify把結果主動推出去——webhook 或 IM 渠道

這九個是「平台底座」的工具，覆蓋一條最短可行鏈：讀檔案 → 改檔案 → 跑命令 → 呼叫外部 API → 記筆記 → 通知人。有了它們，ReAct 迴圈第一次能在真實世界留下痕跡，而不是只做文字接龍。

內建 Tool vs. Plugin Tool：平台與業務的分界

九個內建工具解決的是「所有 Agent 都需要的共通用法」，但它們**不**是全部。業務能力——比如「查 CRM 的客戶資訊」「把 PR 摘要推到 Slack」——不該屬於平台，而該由使用平台的人自己帶來。所以 Tool 被切成兩大類：

  • 內建 Tool（Built-in Tool）：平台作者維護的平台底座工具，通用、跨 Agent 都受益。
  • Plugin Tool（插件工具）：業務方擴充的商業能力，本節課的重點——怎麼讓企業自帶的系統被 Agent 呼叫。

這個分界的意義在下一課會展開：不管工具是內建還是插件、不管插件用什麼技術寫的，對 Agent 來說它們都必須長成同一張臉。現在先記住：平台管基礎、業務管能力，而分界線畫在「通用 vs 特定」。

回到 Demo：一次真的「去查天氣」

把這個節點接到前面的 Demo 一：「查北京天氣、建議穿衣」。當時表面上是迴圈在轉，實際動手的是 http_get——是它真的把天氣 API 的 JSON 帶回來，模型才看到 8 度的數值、才有資格建議你穿外套。工具的價值就在這：模型負責判斷，工具負責讓判斷變成事實。沒有一雙手，Agent 只是個會講話的百科全書；有了手，它才是能幹活的員工。
