可插拔三後端

Step 5/6 · Memory

學習目標

能實作 Markdown、SQLite、Mem0 三檔 LongTermMemoryStore，說清各自定位與四契約如何落地，並證明只改 memory.backend 設定就能換後端而門面以上零改動。

動手前：兩層、三檔、四契約

實作前先把形狀定清楚。MemoryService 朝上（方法固定給 PromptBuilder 與工具用），LongTermMemoryStore 朝下（三個實作）。三檔的定位對應第 21 節的演進路線：

後端定位何時用
Markdown階段一預設，零依賴、人可讀、git 可追蹤預設
SQLite結構化升級，支援 scope／時間查詢、LIMIT 截斷記憶量變大
Mem0外部集成檔，需自架 mem0 server，資料留在內網真需要自動抽取／語意檢索

四契約（不快取、核心不截斷、scope 顯式、檢索只在歸檔區）是三者共同的行為底線，差別只在「怎麼落地」。

檔一（預設）：MarkdownMemoryStore

長期記憶存在一個 Markdown 檔，用兩個區塊組織：## 核心記憶 與 ## 歸檔記憶。每條記憶是一行：- [yyyy-MM-dd HH:mm:ss] 內容。內容進檔前會壓成單行、並把區塊頭字面量中和掉（否則使用者可控的文字會被誤當成分區邊界，導致核心記憶被截斷或串區）。

## 核心記憶
- [2026-09-22 10:03:11] 後端技術棧：Spring Boot 3.x on K8s
## 歸檔記憶
- [2026-09-22 10:05:40] 上週三部署因 OOM 失敗，重啟後恢復

四契約的落地方式很直觀：load() 每次 Files.readString、不快取（契約一）；截斷只接歸檔區那段字串裁尾、物理上碰不到核心區（契約二），上限 MAX_ARCHIVE_CHARS = 4000；寫核心還是歸檔由 scope 決定（契約三）；recallByKeyword 只掃歸檔區、不分大小寫（契約四）。寫入用「先寫暫存檔再原子改名」，並對每個檔案加鎖——讀-改-寫整段互斥，避免並行會話互相覆蓋。

檔二（結構化升級）：SqliteMemoryStore

記憶量變大後，改用 SQLite 按條存進 memory_entries 表（欄位含 agent、scope、content、時間）。同樣四契約，只是換了實現手段：

契約Markdown 檔SQLite 檔
不快取每次讀檔每次查庫
核心不截斷只裁歸檔那段字串核心用 WHERE scope='CORE' 全量取
scope 顯式寫入對應區塊寫入 scope 欄位
檢索只在歸檔掃歸檔區行SQL LIKE

歸檔區用「最近 N 條」實現截斷：先按 id 倒序取 LIMIT 100，再翻回時間正序拼接。截斷從「字串裁尾」變成「查詢 LIMIT」，語意一致但更精準。

檔三（外部集成）：Mem0MemoryStore

這一檔把 append／load／recallByKeyword 翻譯成 {@code mem0} 自架 server 的 REST 呼叫（POST /memories、POST /search、GET /memories）。它的能力宣告是 DELEGATED——意思是「後端自帶語意」，底座不再自己建索引。最關鍵的一組映射：

  • 寫核心：infer:false，原文一字不差落庫（保住核心的保真）。
  • 寫歸檔：infer:true，把提煉／衝突消解交給 mem0。
  • 檢索：search 帶 filters:{scope:ARCHIVAL}，返回側再按 metadata 防禦性過濾（因為 mem0 filters 有版本性 bug），杜絕核心區串入檢索。

換句話說，在 Mem0 檔裡，截斷、提煉、衝突消解全被下放給 mem0，這一檔只做協定翻譯，契約四也被「升級」成語意檢索。但要注意：Mem0 是外部服務，記憶資料會流經它的管線，所以對「資料不出域」有嚴格要求的場景，必須在內網自架——這正是為何預設是 Markdown，而不是功能更強的 Mem0。

換後端：只改一個設定

配置一鍵：memory.backend: markdown | sqlite | mem0，裝配時注入對應 store。

因為 MemoryService 是唯一門面，換後端改的是「注入哪個 LongTermMemoryStore」，門面以上（PromptBuilder、記憶工具、測試）一行都不用動。這就是介面牆最直觀的回報：設定從 markdown 改成 mem0，上層毫無感覺。
