壓縮 vs 提煉

Step 2/6 · Memory

學習目標

能用一句話分辨上下文壓縮（把眼前的對話變短）與記憶壓縮（把長期倉庫整理精簡），並解釋記憶提煉為何決定長期記憶品質，最後能畫出記憶的完整閉環。

先分清楚兩個常被混談的詞

「壓縮」在記憶系統裡出現兩次，但指的完全是兩件事。混在一起講，設計時就一定會做錯決策。一句話分清楚：

上下文壓縮縮短的是「眼前正在說的」；記憶壓縮整理的是「長期倉庫裡已累積的」。
上下文壓縮（context compression）記憶壓縮（memory compression）
對象當前會話的對話內容已存進長期記憶的條目
目的別讓眼前的對話撐爆視窗讓長期倉庫保持精簡、可檢索
手段摘要、裁掉過舊的輪次合併、去重、抽象化
時機每輪／接近視窗上限時寫入前後、定期整合時

兩者都會讓「文字變少」，但一個發生在寫入前端、一個發生在倉庫端。OryxOS 在核心階段甚至刻意不做自動的上下文壓縮（只按輪數截取最近歷史），把力氣集中在長期記憶的提煉上。

記憶提煉：讓長期記憶從垃圾場變成資產

原始對話有兩個致命特徵：冗長（一句話能講完的事聊了十輪）與低訊號（大量寒暄、確認、被推翻的中間產物）。如果原封不動地存，長期記憶很快就變成一堆沒法用的雜訊。

所以寫入長期記憶前要先提煉（extraction）：把原始對話抽成結構化、精簡的記憶條目。例如把「嗯對，我們公司後端用 Spring Boot 跑在 K8s 上，對，就是 3.x」抽成「後端技術棧：Spring Boot 3.x on K8s」。

提煉通常交給模型做（可搭配規則）。這裡有個殘酷但重要的結論：

提煉品質直接決定長期記憶品質。提煉得好，檢索回來的東西有用；提煉得差，倉庫就是垃圾場——存得越多越糟。

這也預告了後面一個關鍵設計取捨：OryxOS 核心階段選擇由 Agent 主動提煉並呼叫 save_memory 寫入，而不是系統自動抽取。因為「何時觸發自動提煉」本身是個沒有驗證過的需求，硬做只會多花模型呼叫又常常寫錯。

把兩者串成一個閉環

這些概念不是六個獨立名詞，而是同一套系統在不同階段的動作。完整循環如下：

  1. 對話中累積：訊息進入當前會話（短期記憶）。
  2. 壓縮＋提煉：把值得記的內容變短、變結構化。
  3. 寫入長期：落到視窗之外的儲存。
  4. 定期整合：合併重複、消解矛盾、抽象化（記憶壓縮）。
  5. 檢索並重新注入：需要時把相關記憶撈回上下文。
  6. 回到第一步：新對話繼續累積。

看懂這個迴圈，就懂了為什麼「短期 vs 長期」「壓縮 vs 提煉」必須放一起講——它們是同一條生產線上的不同工站。

接到 OryxOS：階段一怎麼落地這個閉環

OryxOS 核心階段對這個閉環做了一個刻意的簡化版本：累積（SQLite 會話）→ 由 Agent 提煉後呼叫 save_memory → 寫入 MEMORY.md 的核心／歸檔兩區 → 每輪 PromptBuilder 把核心區全量、歸檔區截斷後注入。自動的「定期整合」與「寫入前自動提煉」都被延後到擴展階段，等真實信號出現再說。這是一個最小完整但誠實的閉環。
