介面牆與三層設計

Step 4/6 · Memory

學習目標

能設計 MemoryService 門面與 LongTermMemoryStore 後端介面這道「介面牆」，背出三後端共守的四條行為契約，定位 core／session／archival 三層，並說出觸發向量檢索升級的三個真實信號。

設計原則：不是最強，而是夠用、可控、能長大

OryxOS 對記憶的第一原則，不是做最強的記憶系統，而是做一個夠用、可控、能平滑長大的：方向清楚、介面正確，實作只做到現在該做的。這條原則和後來 Sandbox、排程模組共用，都是「分階段克制、不過度設計」。而分隔「現在」與「未來」的那條線，就是介面牆。

介面牆的兩側

把記憶拆成兩個方向明確的介面，牆就立起來了：

介面面向方法
MemoryService（門面）朝上，給 PromptBuilder 與記憶工具用buildContext(session)、remember(content, scope)、recall(keyword)、readAll(agentName)
LongTermMemoryStore（後端）朝下，由三檔實作append、load、recallByKeyword、capabilities、archivalEntries

引擎只呼叫抽象方法，永遠不知道後端是檔案、SQLite、向量庫還是外部框架。這正是 MemGPT 把穩定記憶操作藏在背後換入換出的同一招。先釘死介面，比先選儲存重要得多。

三後端共守的四條行為契約

介面牆要成立，不能只靠簽名，還要靠行為。所有後端實作都必須遵守四條契約——它們也是「一份測試跑三檔」的前提：

  1. 不快取：每次 load 都重新讀檔／查庫／呼叫 API。這樣 Agent 剛寫的 save_memory 下一輪立刻可見。
  2. 核心記憶永不被截斷：截斷只作用在歸檔區；核心區完整返回、不參與檢索、也不進向量索引。
  3. 寫哪一區由呼叫方顯式指定：透過 scope 傳入，系統不猜；做不到分區語義的實作在裝配期就被可讀地拒絕。
  4. 檢索只在歸檔區：而且形態可按能力三態降級——語意路缺席時回落成關鍵詞＋時間兩路，關鍵詞行為是統一底線。

注意契約一和二特別重要：不快取讓「寫了就有感」，核心不截斷保證常駐事實永遠在場。誰違反，參數化的契約測試就會在那一行變紅。

三層記憶落在哪

借 MemGPT 的分層，OryxOS 把記憶切成三層，各自職責分明：

層存在哪特性
Core（核心）檔頭一小塊固定區永遠在場、精煉、不檢索、不截斷
Session（會話）SQLite當前會話的對話歷史
Archival（歸檔）檔案，關鍵詞匹配按需檢索、量大、可截斷

核心與歸檔由 Agent 主動呼叫 save_memory 寫入，不是系統自動抽取。為什麼？因為自動抽取是尚未被驗證的需求，硬做要多花模型呼叫、還要一套「何時觸發」的邏輯；所以延後到擴展階段，等真實信號。整個階段一閉環零外部依賴，剛好符合 OryxOS 的單一二進位目標。

信號驅動的階段二：向量檢索何時上場

什麼時候該升級成向量檢索？不是「大家都在用」，而是出現以下三個真實信號之一：

  1. 關鍵詞檢索開始漏掉同義記憶——明明存過，卻撈不到。
  2. 歸檔量跨進數百到數千條——關鍵詞掃描開始力不從心。
  3. 真的需要精準的跨會話召回——業務場景逼出來的。

升級方式是把 MemoryService 之後的實作換掉，介面不變、上層一行不改。沒有這些信號就上向量，是過度設計＋背了一個重依賴。這條「信號驅動」規則，Sandbox 與排程模組也一樣在用。

自查：五個問題

在動手寫程式前，先過一遍這份評審自查：能一句話分辨短期／長期與上下文／記憶壓縮嗎？這道 MemoryService 牆夠不夠密（ReAct 知道實作細節嗎）？三層各住在哪、為什麼由 Agent 主動寫？三個向量升級信號背得出來嗎？自造還是集成的錨是什麼？——只要有任何一題的答案靠「大家都在用」，設計就還沒想清楚。
