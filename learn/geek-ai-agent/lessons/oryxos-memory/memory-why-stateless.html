為什麼 Agent 需要記憶

Step 1/6 · Memory

學習目標

能說清 LLM 每次呼叫都無狀態、context window 有限且昂貴，因此 Agent 必須在視窗之外管理記憶；並能區分短期（工作）記憶與長期記憶（情節／語意／程序）。

先看一個真實到讓人尷尬的故事

一個 Agent 星期一通過了所有評測，表現得像個可靠的助理。星期三，同一個使用者回來，Agent 卻問他「請問您怎麼稱呼？」。模型沒換、程式沒改，為什麼短短兩天就「失憶」了？

這不是模型問題，是記憶問題。而且它不是個案——把 Agent 從 demo 推進到生產，記憶是第一號障礙。

根本原因一：LLM 每一次呼叫都是無狀態的

你呼叫一次模型，它生成一次回覆，然後就把這次互動忘得乾乾淨淨。它沒有「上一次我們聊到哪」的概念。所以如果希望它記得，歷史必須由呼叫方自己在每一次請求裡重新塞回去。

打個比方：你每次打電話給同一位顧問，但他每次接起電話前都被施了一次失憶咒。要讓他接得上話，你得在開口前先把整段前情提要重講一遍。

這解釋了為什麼「多輪對話」其實是個錯覺：模型不是記住了，是每一輪都有人（你的程式）把過去的訊息重新餵給它。

根本原因二：context window 又小又貴

就算你想把所有歷史都塞回去，也塞不下。context window（上下文視窗）是模型單次能看到的文字總量，它有兩個硬限制：

  • 有限：視窗再大也有上限，跨會話、跨月累積的偏好與事實必然超出去。
  • 昂貴：塞進去的每個字都要計費，而且越長越貴、越長模型越容易分心抓不到重點。

所以真正的答案不是「塞更多」，而是在視窗之外管理記憶——該留的留下、該撈的撈回來、該忘的丟掉。這就是 Agent Memory 的本質。

短期記憶 vs 長期記憶

要管理記憶，先得分清楚兩種。它們不是「同一種東西的長短版」，而是位置與壽命都不同的兩層：

短期／工作記憶長期記憶
放在哪當前對話／任務的上下文，就在視窗裡落地到視窗之外，需要時再檢索回來
壽命短，會話結束就沒了跨會話、跨天數持續存在
容量受視窗限制理論上可持續累積
速度快，直接就在眼前慢，要先撈出來才能用

長期記憶內部還能再細分成三類，這個分類在後面挑選方案時很有用：

  • 情節記憶（episodic）：發生過的事件——「上週三部署失敗過一次」。
  • 語意記憶（semantic）：事實與偏好——「使用者偏好用繁體中文、關注 AI 與晶片」。
  • 程序記憶（procedural）：怎麼做某件事，有時以技能或規則形式存在——「這個專案的發版流程要先跑 mvn verify」。

兩層之間的迴圈

短期與長期不是各管各的。核心迴圈是：把短期裡重要的內容搬進長期儲存，並在需要時把相關的長期內容撈回上下文。搬得太少，會話一結束就白聊；搬得太多，長期倉庫變垃圾場、檢索變噪音。這個取捨就是後面幾步要展開的「提煉」與「壓縮」。

接到 OryxOS：這個能力長在哪

OryxOS 把記憶列為三大核心能力之一——ReAct 負責「會想」、Tool 負責「會做」、Memory 負責「記得住」。具體落點在 ReAct 迴圈組裝 prompt 的那一步：PromptBuilder 每一輪都會把長期記憶注入 system prompt 的一個獨立段落。換句話說，Agent 之所以看起來記得，就是因為每一輪都有人把記憶重新放回它眼前。這條注入管線怎麼接、記憶又存在哪裡，是接下來五步的主線。
