業界記憶方案盤點與 MemGPT／Mem0 解剖

Step 3/6 · Memory

學習目標

能盤點 Mem0／Zep／Letta(MemGPT)／Cognee／LangMem／ReMe 的定位差異，說清 MemGPT「記憶即作業系統」與 Mem0「add 即消解」兩個核心思想，並用「記憶是否為核心差異化能力」這個錨判斷自造或集成。

為什麼要先看業界

2026 年開源記憶生態已經成熟到「不缺實作，缺的是選型判斷」。同樣一組問答，不同架構在時間性檢索上能差出約 15 個百分點——所以關鍵問題不是「要不要用記憶框架」，而是哪種架構適合我的場景。先看清楚別人做了什麼，才不會重造輪子、也不會盲目集成。

2026 開源記憶生態一覽

方案定位記憶體

兩個值得記住的觀察：第一，LongMemEval 已是事實上的壓力測試，架構差異會直接反映在分數上；第二，多數框架不碰上下文壓縮，而是傾向把狀態外部化——這和 OryxOS 的思路一致。

思想一：MemGPT——把記憶當作業系統管

MemGPT 的核心洞見是一組對照：LLM 的上下文就像記憶體（快、貴、小），外部儲存就像磁碟（慢、便宜、超大）。要管好兩者，就該像作業系統管虛擬記憶體那樣——分層、換入換出。

它把記憶切成兩層：主上下文裡有一小塊永遠在場的 Core Memory，外部則有 Archival Memory 與完整歷史，需要時才檢索進主上下文。更關鍵的是，MemGPT 給 Agent 自己管理記憶的工具，並在上下文快滿時發出一個「記憶壓力」訊號，讓 Agent 自己決定要摘要什麼、寫什麼、歸檔什麼、丟什麼。

其中兩個想法直接影響了 OryxOS：核心記憶這一層（階段一就採用）與壓力觸發的整合（列為擴展候選）。

思想二：Mem0——add 即消解

Mem0 把自動提煉、衝突消解、混合儲存、多 scope 全打包成一個 library，對外只露 add／search。它最核心的地方不是「存」，而是寫入時的比較與更新：新增一條事實時，先拿它跟既有記憶比對——

新事實與既有記憶的關係動作
互相矛盾update（更新舊條目）
重複merge（合併）
無關add（新增）

這個「add 即消解」正是記憶壓縮的實務落地，也恰好照出 OryxOS 純追加式 MEMORY.md 的弱點：只會一直往後疊，不會消解矛盾。但它也有代價——每次 add 多一次模型呼叫、衝突消解是黑箱、資料會流經它自己的管線。值得注意的是：Mem0 是可自架的 library，不是 runtime，所以它跟 OryxOS 的定位不衝突。

知識圖譜：向量檢索的盲點

向量檢索擅長「語意相近」，卻對關係與時間兩件事視而不見。經典反例：使用者換了工作，向量檢索可能仍把舊的「在 A 公司任職」撈出來，壓過新的「在 B 公司任職」——因為兩句話語意太近了。

Graphiti／Zep 的時序知識圖譜正是來補這個洞：實體是節點、帶時間戳的關係是邊；新事實不是覆蓋舊邊，而是讓舊邊過期。於是可以回答「誰在什麼時候跟誰有關」。三種儲存各有所長：

  • 檔案／KV：適合「是什麼」的離散事實。
  • 向量：適合「語意相近」的模糊召回。
  • 知識圖譜：適合「誰跟誰、在什麼時候」的關係與時間查詢。

OryxOS 的目標場景以偏好與事實為主、關係複雜度低，所以把圖記憶排在向量之後，時序一致性先靠 Agent 判斷；若真要圖記憶，也應集成可自架的 Graphiti，而不是自己造。

自造還是集成：一個判斷錨

選型的關鍵，是先分辨對方是「執行時」還是「可集成的零件」：

  • Letta 是執行時——它是有狀態的 Agent 執行時，站在 OryxOS 同一層，屬於同儕／競品。這種絕不集成，只學它的思想（核心記憶、壓力觸發）。
  • Mem0 是零件——它是設計來被集成的 library。若記憶屬於「必要但不差異化」的能力，可以集成。
選型錨：記憶是不是我的核心差異化能力？

OryxOS 目前的傾向：核心階段的檔案式記憶自造（簡單、可控、可私有部署）；階段二的向量層優先薄自造以守住資料主權，只有在自造明顯落後、且記憶確實不是重點時，才集成可自架方案。如果一個決定的理由只剩「大家都在用」，那這個設計就還沒想清楚。
