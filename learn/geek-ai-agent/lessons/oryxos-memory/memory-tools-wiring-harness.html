記憶工具、Prompt 注入與契約測試

Step 6/6 · Memory

學習目標

能把 save_memory／recall_memory 兩個內建工具接上 MemoryService，讓 PromptBuilder 每輪注入長期記憶，並用一份參數化契約測試證明三後端行為一致、切換後端上層不變。

兩個內建工具：把記憶暴露給 Agent

記憶要能被 Agent 使用，得先變成工具。這裡落地第 20 節預留的兩個內建工具：

工具輸入行為
save_memorycontent、scope（core／archival）轉發 remember(content, scope)，回「已記住」
recall_memorykeyword轉發 recall(keyword)，命中逐行回、沒命中回「沒有找到相關記憶」

幾個關鍵設計：save_memory 的 scope 缺省為 archival（不確定就存一般事件與結論）；遇到無法辨識的 scope 明確報錯並點名，不靜默落錯區。recall_memory 沒有命中時回一句可讀訊息而不是拋例外，對話不中斷。而整個 MemoryTools 只認 MemoryService 門面，對底層是哪一檔後端完全無感——所以換後端不用碰它。

scope 的語意也值得記住：core = 少量常駐事實（身份／偏好／硬約束，每輪都在場、務必精煉）；archival = 一般值得記住的事件與結論（按需檢索找回）。

注入 Prompt：每輪都重新想起

工具負責「寫」，PromptBuilder 負責「讀回來用」。ReAct 迴圈每輪組裝 prompt 分成四段：system prompt（含當前時間）、長期記憶、最近 N 輪對話歷史、可用工具列表。其中長期記憶那一段就是呼叫 memoryService.buildContext(session) 得到的——核心區全量＋歸檔區截斷後。

因為契約一是「不快取」，load 每輪重新讀：Agent 這一輪呼叫 save_memory，下一輪組 prompt 時記憶就真的在場了。

這裡也順帶分清兩個常被搞混的檔案：USER.md 是使用者手寫的初始設定，OryxOS 只讀不寫；MEMORY.md 是 Agent 透過 save_memory 自己寫的成長記錄，OryxOS 讀寫。一個是「我告訴你我是誰」，一個是「你逐漸認識我」。

契約測試：一份測試守住三檔

介面牆要真的成立，不能只靠人工。最有價值的設計是一份參數化契約測試 MemoryStoreContractTest——同一組斷言跑在三檔後端上，每條斷言對應一條契約：

斷言對應契約
寫入後立刻讀得到一：不快取
截斷只動歸檔、核心保持完整二：核心不截斷
scope 路由到正確的區三：scope 顯式
檢索只搜歸檔區四：檢索限歸檔

它的威力在於：任何一檔破壞任一契約，就會在它那條參數化斷言上變紅，而且你能立刻知道是哪一檔壞了。此外各檔還有自己的實作測試（Markdown 的字串截斷與表頭解析、SQLite 的 schema／LIMIT／LIKE、Mem0 用 mock 的 RestClient），以及 MemoryToolsTest（scope 缺省與未命中訊息不拋例外）與 MemoryServiceImplTest（buildContext）。

人工驗收：換後端，感受一樣

自動測試之外，最後的驗證是人跑一遍：把 memory.backend 在 markdown／sqlite 之間切換，跑同一段對話，感受「換了後端、體驗一模一樣」；有條件就自架 Mem0，確認 save_memory 進得去、recall 能語意撈回。再跑一段真實模型對話：Agent 呼叫 save_memory，然後開一個新 session，看核心記憶是否出現在 system prompt 裡。順帶確認 USER.md 唯讀不變。

走到這裡，「會想（ReAct）、會做（Tool）、記得住（Memory）」就齊了——Demo 二「每日科技日報反映使用者偏好」正是靠這條記憶管線才成立。而整條設計留給你的可複製動作是：先釘介面牆、實作只填最輕一檔、用契約測試守住、等真實信號再升級。
