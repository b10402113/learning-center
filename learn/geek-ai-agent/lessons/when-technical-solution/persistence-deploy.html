持久化 key 設計與部署形態

Step 5/5 · When 技術方案

學習目標

能畫出 When 的 Redis key 結構並解釋如何避開 big-key，說清重啟恢復順序與三種部署形態的取捨。

Redis 只放三種東西

前面提過，Redis 是訊息的「唯一真相」。但要讓它又快又省，不能什麼都往裡塞。When 把 Redis 的資料精簡成三類 key：

Key 樣式型別存什麼生命週期
/when/messages/{message_id}STRING（JSON）訊息本體TTL = deliver_at + 7 天
/when/timewheels/{tw_id}/index/{message_id}STRING到期時間（deliver_at）投遞或取消後刪除
/when/timewheels/{tw_id}/messages_in_slot/{slot_key}SET哪個槽位有哪些訊息僅用於重啟恢復

三個設計要點藏在這裡。第一，訊息本體以 message_id 拆開，一則一 key。第二，索引按時間輪（tw_id）拆分，而不是全域共用一個大結構。第三，TTL 當安全網：正常流程會在投遞或取消後主動刪除 key，但如果哪裡漏刪了，deliver_at 再加 7 天的到期時間會自動清掉，避免垃圾無限累積。

big-key 是 Redis 的頭號敵人

big-key 指的是單一 key 底下的資料量過大（例如一個塞了幾百萬成員的集合）。它的危害是：讀寫該 key 會佔用大量記憶體與 CPU、在叢集擴容時難以搬遷、某個熱 key 可能拖垮整個實例。

When 明確不用 ZSet，也不用大 Hash——因為它們天生會把大量成員收在同一個 key 底下。取而代之的是「很多個小 key」，訊息本體一則一 key、索引按輪拆開。Redis 對數百萬個小 key 的處理能力很強，這個代價是划算的。方案也把 big-key、時間輪記憶體、Slave 落後、到期洪峰列為主要風險，並各自給了對策。

讀寫策略與重啟恢復

三個路徑的行為要分清楚：

  • 寫入：先寫 Redis（用 Pipeline 批次送以降低往返次數），成功才寫記憶體並回傳成功；Redis 失敗就回報失敗，絕不留下「記憶體有、Redis 沒有」的訊息。
  • 排程／投遞：以記憶體為準讀取，非同步刪除 Redis 的 key，不阻塞指針。
  • 查詢：先讀記憶體快取，找不到再讀 Redis。

重啟恢復有一個容易寫錯的順序。節點啟動時，必須先把 Redis 裡的資料載回記憶體、把時間輪重建完成，才能向 ETCD 註冊。如果反過來先註冊，叢集會以為這台節點已經可以服務，而它其實還在載入——這正是「已註冊但還沒就緒」的典型陷阱。先載資料、後註冊，才能確保被派工時真的接得住。

至於 Redis 本身的高可用，MVP 階段只做單機或主從，並把真正的 HA 留給部署方決定。Redis 若中斷，寫入會失敗，業務方依約重試即可。

三種部署形態

When 提供三種部署方式，對應不同階段的需求：

形態用途內容
docker-compose本機開發與示範ETCD + Redis + Kafka + 三個 When 節點，各自帶環境變數
單機生產小型正式環境ETCD、Redis，三個 When 節點置於 Nginx 之後；文件細到每條指令，約半小時可裝好
Kubernetes雲原生生產Deployment（replicas=3）加探針、Service、ConfigMap、Secret，可選 HPA 與 PDB；不含 Operator；ETCD 與 Redis 用 Helm 安裝

K8s 形態裡有一個和前面呼應的細節：Deployment 的 replicas 固定 3，對應「三節點是最小 HA」；同時掛上 liveness 與 readiness 探針，讓還沒載完資料的節點不會被導進流量——這正是重啟恢復順序在部署層的體現。組態一律走環境變數，符合 12-factor（十二要素應用）原則，同一個映像檔可以在三種形態中通用。

把技術方案收在一條線上

回頭看，這個節點的每一步都在回答同一個問題：怎麼讓一個分散式的延遲投遞元件，用最少的自製程式碼撐住可靠性。六個決策把協調外推給 ETCD、把可靠外推給 Redis；架構讓節點保持同質、狀態盡量外部化；時間輪專注把排程做到 O(1)；Master/Slave 用非同步複製換取十秒內的快速接管；最後用拆散的 key 與「先載後註冊」把持久化與恢復釘死。技術方案的價值不在功能清單，而在於每個「不做什麼、為什麼」都寫成了一句可驗證的理由。
