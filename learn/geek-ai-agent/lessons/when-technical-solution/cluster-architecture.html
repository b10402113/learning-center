整體架構與同質節點

Step 2/5 · When 技術方案

學習目標

能用業務／叢集／外部依賴／下游 Sink 四塊畫出 When 的整體架構，並說明同質節點、Controller 角色與節點內部模組如何切分。

先看四塊：一張架構圖的分區方式

When 的整體架構可以切成四塊，由左到右是一條資料流：

區塊角色內容
業務方需求來源透過 HTTP API 提交訊息、查詢、取消
When 叢集核心多個同質節點，其中一台被選為 Controller
外部依賴被外推的難題ETCD 負責協調、Redis 負責訊息與索引的持久化
下游 Sink投遞出口HTTP、Kafka 等，以 SPI 插件方式接入

這四塊裡有一個關鍵的設計態度：ETCD 與 Redis 是「拿來用」而不是「拿來自己重寫」的。When 不重新發明協調服務，也不重新發明可靠的鍵值儲存；它只負責把訊息排進時間輪、時間到時交給 Sink。

同質節點：Controller 是一個角色，不是一台專用機器

叢集裡的每個 When 節點跑的程式完全一樣，這叫同質（homogeneous）節點。它們都在做同一件事：接收訊息、排程、投遞。Controller 不是另一種機器，而是一個被選舉出來的角色——某一個時刻剛好有一台節點擔任它。

這樣設計的好處是：沒有「專用節點掛掉就群龍無首」的單點，擴容時也只要多開一個一樣的節點。Controller 的職責是做全域決策（例如重新分配副本、指派新 Slave），但資料與排程仍然散在每台節點上。

節點內部的八個模組

把一個節點打開，會看到八個模組，每個都對應一個清楚的職責：

  • ingress（接入）——接收業務的 HTTP 請求，做驗證。
  • router（路由）——用一致雜湊（consistent hashing）決定訊息屬於哪個時間輪；若該輪的 Master 在別台節點，就透過 gRPC 轉發。
  • time-wheel engine（時間輪引擎）——記憶體中的排程核心，決定訊息何時到期。
  • replica synchronizer（副本同步器）——把 Master 的變更非同步同步給 Slave。
  • Sink deliverer（投遞器）——到期後把訊息送給下游，內含執行緒池與重試。
  • ETCD client——註冊、心跳、選舉、Watch。
  • Redis client——訊息與索引的讀寫。
  • observability（可觀測）——指標、結構化日誌、健康檢查。

模組的切法反映了資料流：ingress → router → time-wheel engine → Sink deliverer 是主線，其餘是支撐。

叢集怎麼組起來

叢集的形成與協調全部透過 ETCD，共四個動作：

  1. 註冊：節點啟動後把自己的資訊寫到 /when/nodes/{node_id}，並綁定一個 10 秒的 Lease（租約）。租約到期若沒續，ETCD 會自動移除這個節點——這就是「失敗自動下線」的機制。
  2. 心跳：節點每 3 秒 對租約做一次 KeepAlive，在獨立的執行緒與連線上進行，不佔用業務執行緒，避免忙碌時心跳遲到而被誤判死亡。
  3. 選舉：想當 Controller 的節點，對 /when/controller 做一次原子的寫入（Txn／PUT，同樣綁 Lease）。ETCD 保證只有一個成功，成功者就是 Controller；新 Controller 先載入叢集狀態，再開始巡邏。
  4. 感知：所有節點 Watch /when/nodes/ 的變化。有節點加入（PUT）就觸發重新平衡；有節點消失（DELETE）就立刻把它名下的 Slave 提升為 Master，並補一個新 Slave。這是事件驅動，不是主動輪詢——不需要有人定期去問「你還好嗎」。

ETCD 的 key space 因此被規劃成清楚的四個層級：/when/nodes、/when/controller、/when/timewheels、/when/config，原則是「階層清楚、key 要小、生命週期分明」。

擴縮容：先搬 Slave，別動 Master

有新節點加入時，流程是：註冊 → 觸發 PUT 事件 → Controller 重新平衡 → 把某個 Slave 搬到新節點 → 新節點同步完成後正式接下 Slave 角色。這裡有一條貫穿全篇的原則：優先搬 Slave，不急著搬 Master，因為搬 Master 會中斷寫入。

節點離開分兩種。主動離開走優雅關機：收到 SIGTERM → 主動註銷 → Controller 在約 1 秒內提升它名下 Slave 為新 Master → 再補一個新 Slave。異常離開則靠 Lease 到期發現，流程一樣，只是要等租約失效，時間落在數秒級。

重新平衡的目標很單純：每個時間輪維持 1 個 Master + 1 個 Slave，兩者放在不同節點，且每台節點手上的副本數盡量平均。演算法會從超載的節點把副本搬到空閒的節點，一次只微調一台（±1），優先搬 Slave，並在每次成員變動時觸發，另外每 5 分鐘做一次週期性檢查。

為什麼生產環境從三節點起跳

三節點是最小的 HA 組態，因為它容得下一個節點故障：一台走了，還有兩台可以接手它的 Master 與 Slave。這是 When 定義「生產可用」的門檻，也是後續部署形態反覆出現「3 個 When 節點」的原因。
