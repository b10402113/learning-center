Master/Slave 複製與 10 秒接管

Step 4/5 · When 技術方案

學習目標

能說清 Master/Slave 非同步複製、用 Lease 偵測故障、10 秒內完成接管的完整順序，以及為何只保證 at-least-once。

問題：一台節點死了，排程中的訊息怎麼辦

訊息存在記憶體中的時間輪裡。如果負責某個輪的節點突然掛掉，那個輪上所有還沒到期的訊息不就消失了？HA（高可用）要解決的正是這件事。When 的答案是：每個時間輪都有 1 個 Master 加 1 個 Slave，兩者刻意放在不同的節點上，Master 出事時由 Slave 接手。

為什麼是 Master/Slave，而不是共識演算法

先釐清副本的真正目的：它不是為了讓資料有多份以保證不丟，而是為了讓切換夠快。因為所有訊息在寫入記憶體之前，都已經先寫進 Redis 了——Redis 才是可靠性的來源，也就是「唯一真相（single source of truth）」。副本只是為了在 Master 死亡時，有一個已經在記憶體中排好隊的替補可以馬上接手，不必重新從 Redis 把整個輪重建起來。

既然不需要跨節點的強一致性投票，就不用背上 Raft / Paxos 的延遲與複雜度。這是第一步「副本用 Master/Slave」決策在架構上的落實。

非同步複製：不擋寫入，容許幾毫秒的落後

Master 收到變更後，把操作非同步推給 Slave，不等 Slave 確認就回覆完成。整個同步通常只花幾毫秒，而且永遠不會阻塞寫入路徑。

這個設計容許 Slave 短暫落後（lag）。因為 Redis 保存了完整資料，即使 Slave 少同步了一兩筆，最壞情況也只是接管後需要從 Redis 補上，不會造成訊息遺失。這就是「有唯一真相來源」帶來的好處：副本可以允許不精確，因為它不是最後一道防線。

如果同步本身失敗呢？系統不會硬撐，而是把該副本標記為 out-of-sync（不同步），並觸發重建——從 Redis 重新把狀態補回 Slave。

用 Lease 偵測故障，而不是猜

「Master 掛了嗎？」這個判斷很容易出錯。如果用「心臟跳動超過幾秒沒來就判定死亡」的啟發式做法，一次 GC 暫停或網路抖動就可能誤判，導致健康的 Master 被換掉，反而製造中斷。

When 把故障偵測完全交給 ETCD 的 Lease：節點用 10 秒的租約註冊，並在獨立執行緒上每 3 秒續約。只有當續約真的失敗、租約真的過期，ETCD 才會移除該節點。這是一個由共識系統背書的判定，不會因為短暫的停頓而產生偽陽性。故障偵測因此是「免費」拿到的，不需要 When 自己寫一套心跳判斷。

十秒接管的完整順序

當 Master 所在的節點死亡，接管在 10 秒內完成，順序如下：

  1. 故障被發現：該節點的 Lease 到期，ETCD 移除它。
  2. Controller 收到通知：所有節點都 Watch 著 /when/nodes/，Controller 看到 DELETE 事件。
  3. 提升 Slave：Controller 把死亡節點名下對應的 Slave 提升為新的 Master。
  4. 新 Master 從 Redis 恢復：新的 Master 以 Redis 中的訊息與索引為準，把記憶體中的時間輪補齊——包含那些還沒同步過來的落後資料。
  5. 指派新 Slave：Controller 再挑一個節點擔任新的 Slave，重建 1 Master + 1 Slave 的組態。

在這 10 秒內，寫入會短暫不可用（因為 Master 正在換手），但已經存進 Redis 的訊息永遠不會遺失。這是「可用性短暫下降，但資料不丟」的取捨。

不丟失是怎麼保證的

「不丟失」不是靠副本，而是靠兩條規則的組合：

  • 回傳前先寫 Redis：訊息必須先成功寫入 Redis，API 才會回覆成功。若 Redis 寫入失敗，就直接回報失敗，且不寫入記憶體——寧可讓業務重試，也不留下「記憶體有、Redis 沒有」的訊息。
  • 新 Master 從 Redis 恢復：接管時，新 Master 的狀態以 Redis 為唯一依據，任何記憶體中漏掉的都能補回。

只要這兩條成立，即使副本完全沒同步到，訊息依然存在。

為什麼只保證 at-least-once

投遞流程是「先投遞、成功後才刪除 Redis」。如果在「投遞成功」與「刪除成功」之間節點崩潰，訊息還在 Redis 裡，接管後會被再投一次——所以系統的語意是 at-least-once（至少一次），可能重複，但不會遺漏。

要跨系統做到 exactly-once（恰好一次）代價極高，而且業界主流也不這麼做：Kafka、RocketMQ、Pulsar 都只提供 at-least-once。正確的用法是把「去重」交給下游用冪等（idempotency）處理——例如業務方以 message_id 為鍵，重複收到時直接忽略。這是分散式系統的產業共識，不是 When 的偷懶。
