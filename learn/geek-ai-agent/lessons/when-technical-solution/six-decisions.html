六大技術決策與 3 週 HA 的理由

Step 1/5 · When 技術方案

學習目標

能說出 When 的六大技術決策，並解釋每個決策為什麼勝過它的替代方案，以及為何三週內做 HA 是合理的。

為什麼技術方案從「決策」開始

When 要做的是一個分散式的延遲投遞元件：業務把訊息丟進來，指定一個未來時間，時間到了就把它投遞給下游。聽起來簡單，但只要加上「分散式」三個字，就會連續撞上六個岔路口。技術方案的第一段不是畫架構圖，而是先把這六個選擇釘死——每個岔路口都在回答同一句話：「這裡很容易走偏，我們選哪條、為什麼。」

先記住六個決策的名字，後面的架構都是它們的展開：ETCD 管協調、Redis 存資料、多層時間輪做排程、Master/Slave 做副本、對外用 HTTP 內部用 gRPC、整體用 Java。

決策一：協調用 ETCD，不用 ZooKeeper 或 Consul

叢集要能知道「有哪些節點活著、誰是 Controller、組態有沒有變」，這類工作統稱協調（coordination）。When 選 ETCD，理由是它的 API 極簡：只有 Put、Get、Watch、Lease 四個動作，客戶端很輕，而且是雲原生生態的標準配備，運維熟悉。

相較之下，ZooKeeper 的客戶端較重、內部一致性協議（ZAB）較複雜，整體給人 JVM 時代的重量級印象；Consul 則偏向服務發現這個單一用途。When 需要的是穩定的協調原語，不是一整套服務網格，所以選了最薄的那個。

決策二：持久化用 Redis，不用 RocksDB 或 MySQL

延遲訊息的特徵是「寫入頻繁、生命週期短、之後要能快速按 key 取回」。Redis 三個特性一次滿足：寫入快、按 key 讀取快、原生支援 TTL（存活時間，時間到自動刪除）。

RocksDB 是嵌入式儲存引擎，不是一個現成的託管服務，部署與運維都要自己扛；MySQL 面對這種大量隨機、短生命週期的 key，寫入與清理都不划算。Redis 唯一的代價是記憶體成本，所以方案裡特別要求「避免 big-key（單一超大 key）」，這一點會在持久化那一節展開。

決策三：排程用多層時間輪，不用 DelayQueue、Quartz 或 ZSet

要「在未來某個時刻觸發某件事」，有三種常見做法，但都被淘汰。JDK 的 DelayQueue 每次插入與取出是 O(log n)，而且只能單機；Quartz 是給 cron 型排程用的，排程資訊壓在資料庫上，對毫秒級的大量延遲訊息太重；Redis 的 ZSet（有序集合）靠分數排序，天生會長成 big-key。

時間輪（timing wheel）的價值在於：插入與觸發都是 O(1)——常數時間，跟訊息數量無關，而且完全在記憶體中運作，精度高。這是 When 整個技術方案的心臟，後面會單獨用一節講。

決策四：副本用 Master/Slave，不用 Raft 或 Paxos

副本的目的是「Master 掛掉時能快速切換」，不是「讓每一份資料都被多數派確認」。Redis 已經保存了所有訊息，是可靠性的來源；副本只是為了縮短中斷時間。既然不需要跨節點的強一致性投票，就沒必要背上 Raft / Paxos 這種共識演算法的高延遲與實作複雜度。

於是 When 採用最單純的 1 Master + 1 Slave 非同步複製：Master 寫入後不等待 Slave 確認，切換快、平時不吃效能。

決策五：對外用 HTTP，內部用 gRPC

兩個介面服務的對象不同，選型就該不同。對外 API 面對的是業務方，HTTP／REST 最好接入、最好用 curl 除錯；節點之間需要互相轉發訊息（例如某個訊息的主人不在這台機器上），改用 gRPC，換來高效能與強型別的契約。

決策六：整體用 Java

語言選擇看的是生態成熟度、運維體系與人才供給。企業後端在 Java 上有完整的監控、部署、安全生态，團隊也最容易接手，這對一個要交付給企業的元件是關鍵。

第 2.7 條：為什麼三週敢做叢集與 HA

技術方案裡還有一條看似不屬於選型的決策：三週的 MVP 就要包含叢集、HA 與自動 failover（故障接管）。這需要辯護，因為它讓範圍變大。方案給了四個理由：

  • HA 就是這個 sample 的說服力——一個能撐住節點死亡的元件，才證明 Loop 工程真能做出企業級系統。
  • ETCD 把協調的複雜度藏起來了——成員、選舉、失敗偵測都由 Lease 與 Watch 代勞，When 不用自己寫共識。
  • 架構本身已經成熟——時間輪、Master/Slave、Redis 持久化都是有大量先例的組合。
  • AI 讓實作變快——在規格先行、護欄齊備的前提下，程式碼產出速度足以支撐這個範圍。

六個決策其實在保護同一件事

把它們並排看，會發現每個決策都在做同一種取捨：把「困難且已被解決」的問題外推給成熟元件，自己只保留真正核心的那件事。When 只專心做好記憶體中的時間輪，其餘的協調、儲存、切換都交給 ETCD、Redis 與一套簡單的 Master/Slave。

決策選它淘汰誰理由
協調ETCDZooKeeper / ConsulAPI 最薄、雲原生、運維熟悉
持久化RedisRocksDB / MySQL寫快、按 key 快、原生 TTL

這六條是後面每一步的護欄。之後看架構、看時間輪、看複製時，凡是遇到「為什麼要這樣切」，答案幾乎都會回到這張表。
