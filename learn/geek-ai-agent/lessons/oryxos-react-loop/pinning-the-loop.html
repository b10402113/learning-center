用測試與 Demo 釘死迴圈

Step 5/5 · 手寫 ReAct 迴圈

學習目標

能設計五個單元測試類的覆蓋重點與兩個最值錢的回歸測試，並說出 Demo 1（北京天氣＋穿搭建議）的驗收標準為什麼能證明迴圈是手寫的。

為什麼單元測試特別重要

迴圈是 Agent 底座的心跳——如果它會無限轉、會失憶、會洩漏身分，上面長的所有能力（記憶、工具、Web）全部白搭。全部五個測試類都不需要網路、不需要真實模型，用假的 Provider 與假的工具就能一次跑完，因此可以當成最便宜的第一道防線。

五個測試類，各盯一個面向

測試類釘死的行為
ReActLoopTest一輪直接結束、工具往返（call→result 回到迴圈）、到達最大迭代就停、過程全部累積
PromptBuilderTest四段組裝順序、歷史截斷到 N 輪、日期時間後綴
ToolExecutorTest成功與失敗都寫稽核表
AgentServiceTestProfileContext set 之後，即使處理拋異常也會在 finally 清掉
ContextLoaderTest不落快取（改檔後再讀是新內容）、缺檔處理

兩個最值錢的回歸測試

不是每個測試份量一樣。講師明說有兩個回歸「最值錢」：

  1. 「模型一直要求工具 → 在第 10 次迭代被強制停住」——這直接釘死上一節的 MAX_ITERATIONS 安全帶。模型對著迴圈 pipe 大量工具要求不稀奇，稀奇的是迴圈不會陪它無限轉。沒有這個測試，死迴圈會以「看起來很忙、永遠沒結果」的形式活在產品裡。
  2. 「即使 process 拋異常，ProfileContext 也要在 finally 清掉」——這釘死 ThreadLocal 洩漏。單次請求的測試永遠測不出來，因為每次都是新執行緒、新身分；只有模擬「同一條執行緒上，上一個請求炸了、下一個請求進來」才算數。

做完怎麼驗：Demo 1 端到端

單元測試只能證明「零件沒壞」。要證明「整台機器真的會想事」，OryxOS 用 Demo 1 收尾：

  1. 跑一串真實多輪對話：「查北京天氣，建議該穿什麼。」
  2. 完整走一遍：CLI → AgentService → ReActLoop → PromptBuilder（組上下文）→ 模型（DeepSeek 等）回一個 http_get 工具呼叫 → ToolExecutor 過 Sandbox 執行 → 天氣 JSON 回到 Session → 第二輪 → 模型給穿搭建議。
  3. Code review 確認迴圈是手寫的：沒有任何框架的 Agent 包裝，主迴圈就是自己那幾十行。

所以 Demo 1 的驗收標準其實是兩件事的合體：「端到端能跑」＋「跑的方式確實是手寫」。前者證功能，後者證明你不欠框架黑盒任何東西——兩者缺一，都不是這個節點的過關線。

核心階段刻意不做的事

迴圈節點把邊界畫得很清楚——以下全部推遲到擴展階段，核心階段不做：

  • 並行工具呼叫：一次只執行一個工具。
  • Agent 委派：Agent 呼叫另一個 Agent。
  • 串流（streaming）：逐 token 吐出回應。
  • 上下文壓縮：核心階段只「保留最近 N 輪」，不重寫歷史。
「這些事很重要，只是不是這個階段」——這是前面工作流與需求節點一再強調的紀律：先釘死能跑的最小完整核心，差異化留給訊號出現後的擴展階段。

把整套迴圈打包帶走

到這裡，你已經從「迴圈是什麼」一路走到「怎麼驗證迴圈不會偷偷壞」。剩下的問題只有一個：怎麼把這副骨架搬回你自己的專案。答案就是這五節的主線——先想清楚職責邊界，再寫那幾十行，再用兩個最值錢的回歸把行為釘死。
