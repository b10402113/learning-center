手寫 ReActLoop、PromptBuilder、ToolExecutor

Step 3/5 · 手寫 ReAct 迴圈

學習目標

能手寫 ReActLoop 的主迴圈、PromptBuilder 的四段組裝與 ToolExecutor 的執行路徑，並解釋「執行權只放在 ToolExecutor 一處」這條規則。

三個類別，一份分工

實作落在三個類別，職責就是前一節那張表：

  • ReActLoop——主迴圈：組 prompt、叫模型、看要不要停、執行工具、累積結果。
  • PromptBuilder——組裝「模型每輪看到的東西」。
  • ToolExecutor——唯一允許執行工具的地方。

ReActLoop.run：每一步都在累積

主迴圈的偽碼長這樣（真實版約幾十行）：

loop(turn = 1 .. MAX_ITERATIONS):
    想 = promptBuilder.build(session)          # 組出這輪送給模型的全部內容
    回覆 = providerService.chat(session.id, 想) # 委派給 Provider 呼叫 LLM
    session.append(回覆)                        # 模型的回應累積回 Session
    if 沒有 工具呼叫: return 回覆                # 停止條件 1：任務完成
    for 每個 toolCall in 回覆工具呼叫:
        結果 = toolExecutor.execute(session.id, toolCall)  # 委派執行
        session.append(結果)                    # 工具結果也累積回 Session
    # 回到迴圈開頭，重組 prompt —— 因為新的結果已經在 Session 裡了
return MAX_ITERATIONS_REPLY                      # 停止條件 2：強制結束

三個關鍵動作：promptBuilder.build、providerService.chat(session.id(), ...)、toolExecutor.execute(...)。迴圈自己一行都沒動到模型或工具——它只負責確保「每一次動作的結果都進入 Session」，下一輪的 prompt 自然就看得到。

注意 session.id() 被傳進模型呼叫與工具執行兩側：Session 是唯一真相源，模型呼叫（llm_calls）與工具執行（tool_invocations）都掛在它下面，整條決策鏈才可稽核。

PromptBuilder 的四段組裝

每一輪送給模型的 prompt 固定四段，順序不能動：

段落內容來源
1. System promptsystem prompt＋目前日期時間ContextLoader＋時鐘
2. 長期記憶跨對話的 Memory（MEMORY.md）MemoryService
3. 對話歷史最近 N=20 輪對話Session（有界，前幾節說的截斷）
4. 可用工具清單這個 Profile 能用的工具ToolRegistry／Profile

第 3 段就是「上下文累積與管理」的落點：只保留最近 20 輪，system prompt 每次固定組裝，讓 context 有界且可控。第 4 段排除了 Profile 沒授權的工具——模型根本看不到它，因為執行權在別處。

ToolExecutor：執行權只在一處

執行路徑是四步：

  1. 找工具：依名稱從 ToolRegistry 取出（找不到就回報錯誤）。
  2. 安全檢查：跑 Sandbox／白名單檢查（路徑、命令、URL），違規直接擋下。
  3. 執行：呼叫工具，把結果包成 ToolResult（success、content、error、retryable 四個欄位）。
  4. 稽核：不管成功或失敗，都寫入 tool_invocations。

為什麼「執行權只放在 ToolExecutor 一處」會是一條鐵律？因為框架（Spring AI）預設會自動執行工具——如果你開了它，同一個工具會被呼叫兩次（框架一次、你的迴圈再一次）。OryxOS 的技術決策明確寫著：只用 Spring AI 的 Provider 抽象與 schema 產生，關掉自動工具執行，把執行權唯一收斂在 ToolExecutor。這是整個 Agent 最容易出錯的地方。

Sandbox 只是其中一道

ToolExecutor 先過 Sandbox 白名單，進入具體工具後（例如 http_get）工具內部還會再 call 一次sandbox.enforce(...)。這是「兩道門」：介面層的統一檢查＋工具內部的防線。Sandbox 違規當成一次普通工具失敗處理——會被 catch、會寫稽核，不會整個迴圈爆炸。

三個類別都有了，但誰在 CLI、Web、排程三條路都統一叫它們？答案是 AgentService——它負責身分（Profile）的傳遞，這正是下一節的主題（ProfileContext 與 ContextLoader）。
