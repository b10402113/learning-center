迴圈只做排程：職責分離與為什麼手寫

Step 2/5 · 手寫 ReAct 迴圈

學習目標

能畫出 ReActLoop／PromptBuilder／ProviderService／ToolExecutor 的職責分工，說出為什麼要手寫而不用框架黑盒，並指出三個經典陷阱。

主迴圈其實只有幾十行

上一節說「迴圈只指揮、動手全交給別人」。這不是比喻，而是刻意到極致的設計：真正的迴圈主體只有幾十行。難的不是那幾十行，而是幾十行之外的邊界——「誰負責準備上下文、誰負責呼叫模型、誰負責執行工具、什麼時候該停」——這些如果不在動手前就想清楚，事後補丁只會愈補愈亂。

四職責分離

角色只負責一件事它不負責
ReActLoop排程：決定每輪做什麼、檢查停不停不呼叫模型、不執行工具、不打 prompt
PromptBuilder組裝這一輪送給模型的上下文不決定策略，只負責拼出「模型看到什麼」
ProviderService呼叫 LLM（上一節學過）不執行工具，工具呼叫只是「要求」不是「動作」
ToolExecutor執行工具、檢查權限、記錄稽核不決定該不該叫這個工具——那是模型的決定
一句話記法：ReActLoop 想、PromptBuilder 寫、ProviderService 問、ToolExecutor 做。每個角色都只看得到自己那張票據。

為什麼手寫，不用框架黑盒

用框架的 Agent 抽象（例如某個現成的 Agent driver）看似省事，但四個東西你必須能控制，而黑盒把它們藏起來：

  1. 停止條件——什麼時候算任務完成、迭代上限設多少，你要能決定。
  2. 工具失敗——工具報錯時要怎麼往回走、要不要重試，得由你的規則決定。
  3. 上下文成長——每輪對話與工具結果都長大，塞爆 context 時誰負責截斷。
  4. 模型切換——換模型、換 provider 時行為不能偷偷變。

除此之外還有一個直接理由：你寫一遍，才真正懂這個 Agent 是怎麼運作的。OryxOS 把所有能力（Provider、Tool、Memory）都長在自寫迴圈的骨架上，前提是這副骨架是你自己搭的。

三個經典陷阱

不管是不是手寫，迴圈設計有三個坑，幾乎每個實作者都會踩：

陷阱沒管的後果解方
沒有迭代上限死迴圈：模型一直叫工具、永不收尾第 1 節的 MAX_ITERATIONS=10
上下文無界成長context 愈積愈大，最後爆掉或變慢只保留最近 N 輪（預設 20）＋固定 system prompt
回應與結果沒累積回 Session下一輪看不到上一輪做了什麼、回應了什麼每輪模型回應與工具結果都 append 進 Session

第三個最隱蔽：迴圈轉了，但模型永遠「失憶」——上一輪查到的天氣，這一輪就看走了。迴圈的整個目的就是「累積」，把過程證據一條條留下來，下一輪才有得推理。

這套紀律會一路借用

「短迴圈、委派職責、邊界自主控制」不只是 ReAct 的寫法。OryxOS 後面的 Memory、Tool、Sandbox、Web，全部長在這一副骨架上；連 When 專案的迴圈工程也是同一套紀律。這一節的思考方式，是你把 Agent 能力「搬回自己的專案」時最值錢的東西。
