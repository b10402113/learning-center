ReAct 迴圈是什麼

Step 1/5 · 手寫 ReAct 迴圈

學習目標

能說出 ReAct 迴圈的單輪結構（Reason→Act→Observe）與兩條停止條件，並講清「單次 LLM 呼叫＝聊天機器人、達成迴圈＝Agent」的分界。

先看一台「會想事」的機器

你請一個人幫你查北京天氣、再建議穿什麼。他的動作不是一次做完的：先想「我要查天氣」→ 去查 → 看到結果 → 再想「氣溫 8 度應該穿外套」→ 回答你。中間每一步的結果都餵回他的判斷。

Agent 要「自主做事」，走的也是同一條路。這條路在 2022 年被整理成一個明確的框架，現在幾乎是所有 Agent 系統的事實標準：ReAct（Reasoning + Acting，推理與行動）。

單輪結構：Reason → Act → Observe

ReAct 把每一輪固定成三個動作，順序不能亂：

階段做什麼產出
Reason（推理）模型根據目前看到的上下文，決定下一步要做什麼「我要查天氣」這個決定；可能是要呼叫某個工具，也可能是直接回答
Act（行動）執行模型選的那個工具（例如查天氣、讀檔案）工具回傳的原始結果
Observe（觀察）把工具結果收回來，放進模型的上下文下一輪能看到的資料

這一輪走完，模型看到比上一輪更多的資訊，於是重新 Reason，再 Act，再 Observe……一直到任務做完。每一步的「結果」都成為下一步的「輸入」，這就是迴圈的意義。

兩條停止條件

迴圈不能永遠轉下去，它有兩個終點：

  1. 模型不再發出工具呼叫——它決定直接回覆最終答案，這代表任務被認為做完了，迴圈把這個回覆當成結果交出去。
  2. 碰到最大迭代數上限——預設 10 輪（MAX_ITERATIONS，可覆寫）。就算模型一直要求呼叫工具，到達上限就強制結束，回覆一段「到達最大迭代數」的訊息。
為什麼要第二條？因為模型可能陷入「不斷想做事、卻沒真做完」的死迴圈（例如一直查同一個檔案）。沒有一條硬性上限，一部機器會無限燒錢與時間。這條上限是整個迴圈的第一道安全帶。

ReAct 自己不做，只指揮

這裡有個新手最容易搞錯的點：ReAct 迴圈本身既不呼叫模型，也不執行工具。它只是排程——負責決定「這一輪要做什麼」，真正動手的是另外兩個角色：

  • 呼叫 LLM 的工作，委派給 Provider（上一節的 ProviderService）。
  • 執行工具的工作，委派給 ToolExecutor。

所以迴圈像一台機器的「腦」：它想、它指揮、它看結果，但動手的是手腳。這個「迴圈只排程、動手全委派」的職責切割，是下一節的主角。

七步算法

把上面濃縮成 OryxOS 技術方案裡那份核心算法，就是七步：

  1. 把使用者訊息加進 Session（append message）
  2. 組裝這一輪的 prompt（assemble prompt）
  3. 呼叫 LLM
  4. 若模型沒發出工具呼叫 → 回傳最終回覆
  5. 否則執行工具，把結果加回上下文
  6. 回到第 2 步，重複
  7. 到達 max iterations（預設 10）→ 強制結束

為什麼「迴圈」等於「Agent」

把分界講清楚：單次 LLM 呼叫只是聊天機器人；只有進入「決策→行動→觀察」的迴圈，才算 Agent。Claude Code、Cursor、LangChain 的 agent 底層全是這個模式——它們的迴圈長得一樣，差別只在工具種類與執行環境的深度。

這也對應你每天在用的工具：Claude Code 幫你改檔時，它就是在跑 ReAct——決定改哪個檔、呼叫讀檔工具、看了結果再改。把這層窗戶打開，你就在看自己正在用的機器的心跳。
