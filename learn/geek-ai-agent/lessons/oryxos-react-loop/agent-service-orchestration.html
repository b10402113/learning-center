單一編排器：AgentService、ProfileContext、ContextLoader

Step 4/5 · 手寫 ReAct 迴圈

學習目標

能說清 AgentService.process 為什麼是 CLI／Web／排程唯一的編排入口，以及 ProfileContext（ThreadLocal）與 ContextLoader（每次重讀、不落快取）各自解決什麼問題。

問題：三條路，一份核心

Agent 有至少三種進入方式：人在 CLI 打一輪、外部系統打 Web API、排程器到了時間自動打一輪。如果三條路各自呼叫不同程式，壞事很快就會來——同一份規則 Token 三次，兩個入口的行為開始分歧。

第一性規則是「同一個入口，重用不要重寫」：人推（human-push）與鐘推（clock-push）共用同一個 AgentService；凡是出現「第二條路」，不久就會出現「兩條路行為不一致」的 bug。OryxOS 多數最難解的 bug 都從這裡來。

解法：把「處理一輪」這件事收斂成單一函式 AgentService.process，CLI、Web、排程全都叫它。

AgentService.process：一輪的生命週期

process 幹的事不多，但都串在「一輪」的生命週期上：

  1. 設定身分（Profile）與追蹤上下文
  2. 讀取 Session（含 Session id 的確定）
  3. 呼叫 ReActLoop 跑完整個迴圈
  4. 把結果存回 Session

它不決定「模型回什麼」，也不決定「工具跑不跑」——那些分別是迴圈與 ToolExecutor 的事。它是編排：確保每一次「Agent 想事情」前後，身分、Session、稽核都對得上。

ProfileContext：一個 ThreadLocal 的故事

這裡有一個非常實務的坑：OryxTool.execute(JsonNode) 的簽名沒有帶 Profile（身分）參數。工具端真正要知道「現在是哪個 Agent 在叫我、它的 provider 是什麼、它被授權用哪些東西」——但這個資訊沒有從迴圈一路傳下去。

解法是用 ProfileContext：一個以 ThreadLocal 存身分的容器。

  1. process 開頭把 Profile 放進 ProfileContext（set）
  2. 整條呼叫鏈（loop → Provider → ToolExecutor → 工具）都在同一條執行緒裡，工具隨時可用 ProfileContext 取到身分
  3. 處理結束（含異常路徑）在 finally 清掉（clear）
第三個「finally 清掉」是最容易被忽略的一步：執行緒會被容器重用。如果不清，下一個請求會撿到上一個請求的 Profile——這種錯在單次請求測試裡完全不見，等流量一大才爆。

這條執行緒用虛擬執行緒（virtual thread）跑，阻塞式同步模型，讓 ThreadLocal 沿著單一執行緒自然傳遞。

ContextLoader：每次重讀，不落快取

Agent 的人設來自一堆 Markdown 文件：Bootstrap（AGENTS.md／SOUL.md／USER.md）與 Skill（SKILL.md），全部會注入 system prompt。問題是：如果 ContextLoader 有快取，改了 SOUL.md，Agent 的人設會莫名其妙還維持舊的，或者要重啟才生效。

OryxOS 的決定很乾脆：每次組 prompt 都重讀文件、完全不落快取。記憶成本就是一次 1–2 ms 的檔案 IO，換來「改檔立即生效」與「不可能讀到髒資料」。

另外兩個規則：

  • Profile 明確引用了某個檔案但檔案不存在 → 直接報錯，不偷偷跳過（否則 Agent 的人設會靜默消失，非常難查）。
  • 連 Memory 的整棵 MEMORY.md 也用同樣精神：每輪重新讀，讓 save_memory 下一輪就生效。

把三節串成一條鏈

回顧整條主鏈：CLI／Web／排程都進 AgentService.process → 它設定身分並呼叫 ReActLoop.run → 迴圈用 PromptBuilder 組上下文（ContextLoader 每次重讀＋MemoryService 提供記憶）→ 委派 ProviderService 呼叫模型 → 需要時委派 ToolExecutor（ProfileContext 供身分、Sandbox 做安全、寫稽核）→ 每輪結果累積回 Session。你現在看懂的，就是整個 Agent 底座的心跳。
