五狀態訊息狀態機與轉移語義

Step 2/5 · 公共契約與接入路由

學習目標

能畫出 PENDING／DELIVERING／DELIVERED／FAILED／CANCELLED 五個狀態與五種合法轉移，並說明為什麼每次轉移都必須原子且只有一個執行者能持有投遞權。

一則訊息的一生，是一台小小的狀態機

上一步定義了 Message 長什麼樣。但光有欄位還不夠，欄位會隨時間改變，而「什麼時候可以從什麼變成什麼」如果沒規定，每個模組就會各有一套默契。所以契約要一起定義狀態機：一則延遲訊息從出生到結束，只能落在五個狀態之一。

狀態意思此刻誰在動作
PENDING已建立、等待到點沒有人，時間輪排程中
DELIVERING正在投遞，已取得投遞權唯一一個執行者
DELIVERED投遞成功，終態完成，等保留期滿才清
FAILED不可重試或重試耗盡，終態完成（失敗收場）
CANCELLED被取消，終態完成（人為中止）

只有五種合法轉移

狀態多不是重點，重點是轉移。When 只允許這五條路：

轉移觸發情境關鍵動作
PENDING → DELIVERING到點，某個執行者搶到投遞權鎖定這則訊息，不讓別人再搶
DELIVERING → DELIVERED投遞成功寫下 deliveredAt
DELIVERING → PENDING可重試的失敗（例如下游暫時不可用）重排 nextAttemptAt，之後再試
DELIVERING → FAILED不可重試的失敗，或重試次數耗盡記下 lastError，不再重試
PENDING → CANCELLED使用者要求取消只有還沒開始投遞的才准取消

有兩條路是刻意不存在的。第一，沒有任何一條路直接從 PENDING 跳到 DELIVERED，因為投遞一定要經過 DELIVERING。第二，DELIVERING 不能直接回到 CANCELLED，因為一旦開始投遞，就沒有「假裝沒發生」這回事。終態（DELIVERED／FAILED／CANCELLED）則不再轉移出去。

為什麼要有 DELIVERING 這個中間狀態

如果狀態只有「待送」和「送完」，會發生一件可怕的事：兩個執行者同時看到一則 PENDING 的訊息，兩邊都覺得該由自己送，結果同一則訊息被送了兩次。問題不是執行者不乖，而是契約根本沒給它一個「暫時佔用」的位置。

DELIVERING 就是那個位置：它代表「這則訊息的投遞權已經被某一個執行者拿走了」。契約規定，一則訊息同時只有一個執行者能持有投遞權。想從 PENDING 進入 DELIVERING，必須是一場原子操作：要嘛你搶到，要嘛你沒搶到，不能有「兩個人都搶到一半」的中間狀態。這就像一間手術室：同一時間只能有一組人動刀，門口那盞「手術中」的燈一亮，其他人就得等。

原子性：轉移不能被打斷

「原子」的意思是這一步要嘛整個成功，要嘛完全沒發生。所有狀態變更都必須走同一個入口，也就是儲存層的 transition 操作，由它保證原子性。如果允許各模組自己讀出狀態、在記憶體裡改一改、再寫回去，就會出現經典的競態：A 讀到 PENDING，B 也讀到 PENDING，兩邊都以為自己可以做下一步。

一條規則要記牢：狀態不可以各自為政地改。要改，就走原子的 transition，讓「檢查目前狀態」和「寫入新狀態」在同一把鎖裡完成。

狀態存在哪：Redis 是真相，時間輪只是索引

這裡要分清楚兩個地方。訊息的權威狀態（現在到底是 PENDING 還是 DELIVERED）儲存在 Redis；而時間輪只是記憶體裡的排程索引，它記的是「這則訊息大概什麼時候該處理」。為什麼要分開？因為記憶體裡的東西一關機就沒了，而 Redis 不會。

這個分工帶來最重要的好處：節點重啟時，時間輪可以從 Redis 重建。權威狀態從頭到尾都在 Redis 手上，記憶體的索引弄丟了再重建就好，訊息不會因此少一則。儲存契約還規定了四個基本能力：建立／查詢（create / get）、原子轉移（transition）、把未完成的訊息撈回來恢復（recovery）、以及在保留期滿後清掉終態訊息（cleanup）。

終態為什麼還要留著

投遞成功或失敗後，訊息不是立刻消失，而是要在保留期內繼續查得到：管理台要能查「這則訊息最後怎麼了」，重試與對帳也需要它。契約的規定是：終態訊息在保留期內仍可查詢，只有保留期滿才進行清理。這解釋了第一步那個整合災難：如果投遞層一送完就刪，查詢方就會撲空。
