gRPC 傳輸契約與驗證分層

Step 4/5 · 公共契約與接入路由

學習目標

能說明 When 為何對內用 gRPC、對外用 HTTP，設計出 Submit／Query／Cancel 三個 RPC 的 proto 契約，並分清契約層結構驗證與執行時配置驗證。

模型與介面有了，客戶端怎麼講話？

到目前為止，契約處理的是「系統內部」的事：資料長什麼樣、模組之間用什麼介面。但使用者與外部系統要怎麼把一則延遲訊息送進來？這需要另一種契約：傳輸契約。它的難題是語言：客戶端可能用 Java、Go、Python 寫，總不能要求大家都讀 Java 的類別定義。

When 的答案是 proto。它是語言無關的介面定義語言：寫一份 .proto，工具就能替各種語言產生客戶端與伺服器的程式碼骨架。這就像各國海關的報關單：不管出口商用什麼語言談生意，填的都是同一套標準欄位，海關才收得進來。

為什麼對內用 gRPC、對外用 HTTP

傳輸方式有兩種選擇，When 兩個都用，但用在不同的地方：

面向用什麼為什麼
節點之間、內部客戶端gRPC叢集節點呼叫頻繁；二進位傳輸加強型別契約，比裸 HTTP 更有效率也更不易錯
管理台、業務呼叫方HTTP API外部整合友善、除錯直觀；與 gRPC 共用同一套操作語義，但傳輸契約分開

這就是技術方案裡的決策：「HTTP outside, gRPC inside」。對內講效率與型別安全，對外講整合便利。兩邊的操作語義一致（都能送出、查詢、取消），所以業務邏輯只需要認得一套語義，傳輸的差異則被擋在介面之外。這種分工也叫「傳輸層與應用層分離」：gRPC server 只管把請求翻譯成內部命令，真正的業務邏輯留給後面的接入層。

三個操作：Submit、Query、Cancel

對外的訊息操作只有三種，全部定義在 when-api.proto：

RPC輸入輸出
Submit訊息內容、延遲或送達時間、投遞目標全域唯一的 message_id，狀態 PENDING
Querymessage_id目前狀態與各時間戳
Cancelmessage_id取消結果；已投遞的訊息不能取消

三個操作合起來就是一則訊息的基本生命週期：送進來、查現在怎樣、不想送了就取消。這裡有一個關鍵紀律：Submit 回傳的 message_id 必須是全域唯一的。這是後面路由與查詢能穩定運作的基礎：同一個 id 到哪裡都指向同一則訊息。

不重複定義，只引用公共模型

when-api.proto 不會重新定義 Message、MessageStatus、SinkType、SinkConfig，而是 import 公共模型那份 proto。這個動作看起來很小，意義卻很大：如果 api 這份檔案自己再定義一次狀態列舉，哪天公共模型多了一個狀態，兩份就會不同步。契約只能有一個定義處，其他地方用引用。

強型別的 sink_config：不要讓實作去猜 key

投遞目標的設定是最容易出錯的地方。如果 sink_config 只是一個通用的鍵值對（map），HTTP 的實作就得自己猜裡面有沒有 url、Kafka 的實作得自己猜有沒有 topic，猜錯只會在執行時炸開。When 改用 proto 的 oneof，讓它變成強型別：

message SinkConfig {
  oneof config {
    HttpConfig http  = 1;
    KafkaConfig kafka = 2;
  }
}
// HttpConfig: url, headers, timeout_ms
// KafkaConfig: bootstrap_servers, topic

如此一來，HTTP 的 Sink 拿到的一定是有 url、headers、timeout_ms 的物件；Kafka 的 Sink 拿到的一定是有 bootstrap_servers、topic 的物件。型別本身就把「這個分支該有哪些欄位」講清楚了，不必靠默契。敏感的憑證則透過環境變數注入，不寫進設定檔。

伺服器只做三件事：解析、驗證、委派

gRPC server 的程式骨架刻意做得很薄。它的工作固定是這條流水線：

  1. 解析請求（request parser）；
  2. 做基本驗證；
  3. 呼叫被注入的應用層處理器（DelayMessageHandler）並委派；
  4. 把結果或錯誤映射回回應。

它不產生訊息 ID、不碰儲存、不調度時間輪、不真正投遞、不做跨節點路由。那些都屬於後面的模組。伺服器依賴的 DelayMessageHandler 只有三個方法：submit、query、cancel。測試時可以塞一個測試用的處理器，驗證 gRPC 呼叫、委派與回應映射是否正確；真正的實作則由接入層提供。這種「只做協議轉換、其餘靠介面外接」的設計，就是埠與配接器（port / adapter）的概念：傳輸是配接器，應用層是核心。

驗證分兩層：契約層看結構，執行時看環境

驗證不是全部塞在一處，而是分層。gRPC 這一層只檢查「proto 表達得出來的結構性約束」：

檢查項目規則
時間二選一deliver_at（Unix 毫秒）與 delay_seconds 必須恰好填一個
時間範圍送達時間必須在未來；延遲必須介於 1 秒到 2,592,000 秒（30 天）
分支一致sink_config 的分支要和 sink_type 對上（HTTP 要 url、Kafka 要 bootstrap_servers 與 topic）
內容大小payload 解碼後不得超過 64KB

驗證失敗要回傳 INVALID_ARGUMENT，並在訊息裡指名是哪個欄位錯，否則呼叫方只看到「參數錯誤」，根本不知道要改什麼。另外兩種錯誤也有固定映射：查不到訊息回 NOT_FOUND；嘗試取消一則不可取消的訊息回 FAILED_PRECONDITION。

至於「這個 URL 真的連得到嗎」「Kafka 的位址通不通」這類問題，gRPC 這一層管不著，要留給實際投遞的模組在執行時檢查。結構驗證與執行時驗證分開，每一層只回答自己答得出來的事。

這一節的邊界

要抵抗「順手多做一些」的誘惑，就要把非目標寫清楚。這一節不實作訊息 ID 產生、狀態儲存、時間輪調度、真正的 Sink 投遞、跨節點路由，也不提供 HTTP API 或驗證／限流。它的停止條件是：契約穩定、proto 產生出 stub、伺服器啟動成功、驗收測試通過。做到這裡就停，剩下的交給後續的接入層。
