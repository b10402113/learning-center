四大公共介面與契約地圖

Step 3/5 · 公共契約與接入路由

學習目標

能說出 StoragePlugin、TimeWheel、Sink、Router 四個公共介面各自的職責，並用契約地圖指出每個契約是誰定義、誰實作、誰使用。

契約有兩種：資料與行為

前兩步講的是資料契約：一則 Message 長什麼樣、狀態怎麼流轉。但光有資料還不夠，模組之間還要能互相呼叫。形容資料的是模型，形容行為的是介面。When 把模組之間的互動收斂成四個公共介面，它們就是整個系統的四道接縫。

標準化的價值可以借用貨櫃來說明：以前每一種貨物各自裝箱，船、吊車、卡車都得為它量身打造；貨櫃把尺寸統一之後，任何運輸工具只要認得這個箱子就能搬。四個公共介面就是 When 的「貨櫃規格」：任何模組只要認得這些介面，就能跟其他模組協作。

四個介面各自的職責

介面職責誰實作誰使用
StoragePlugin訊息的建立與查詢、原子的狀態轉移、未完成訊息的恢復、終態的清理儲存模組（Redis 插件）時間輪、接入與路由、副本同步
TimeWheel記憶體中的排程索引：加入（add）與移除（remove）時間輪模組接入與路由、恢復流程
Sink真正把訊息投遞出去，例如 HTTP 或 Kafka投遞模組（HTTP／Kafka 兩種實作）投遞流程
Router路由：把 messageId 映射到穩定的 tw_id接入與路由模組時間輪與跨節點轉發

Router 只回答「這則訊息該去哪個輪子」，不負責「那個輪子在哪一台機器」。尋找節點、跨機轉發是接入與路由層的編排工作，不屬於路由介面本身。把純粹的計算（雜湊）和會動的編排分開，介面才容易測試、也容易替換。

契約地圖：誰定義、誰實作、誰使用

當系統有幾十個模組，最怕的就是「好幾個地方都在定義同一件事」。所以除了介面本身，還要有一張契約地圖，寫清楚每個契約的唯一擁有者：

契約定義實作使用
Message、MessageStatus公共模型不適用（是資料，不是行為）所有模組
SinkType、SinkConfig公共模型不適用傳輸層搬運、接入層轉換、投遞層使用
StoragePlugin公共模型儲存模組時間輪、接入與路由、副本同步
TimeWheel、Router公共模型時間輪、接入與路由接入與路由、時間輪
Sink公共模型投遞模組投遞流程

這張地圖的用途很實際：當某個契約需要改動，你知道要從哪裡改起、改完要通知哪些人。規則和第一步一樣：先改定義處，再逐一檢查所有實作者與使用者。舉例來說，SinkConfig 由公共模型定義，傳輸層只負責搬運它的格式，接入層把它轉成 Message 的一部分，最後投遞層才真正拿它去送。沿著這條鏈，任何一環偷偷改欄位，都會與其他人對不上。

只依賴介面，不依賴實作

四個介面還有一個關鍵作用：它們讓模組之間只依賴抽象，不依賴具體實作。接入層需要儲存訊息，但它不直接呼叫 Redis，而是依賴 StoragePlugin；需要時間輪，就依賴 TimeWheel。這樣做的好處在測試時最明顯：測試可以塞進一個假實作，不必真的開一台 Redis。依賴方向因此變成單向的：核心邏輯指向公共介面，實作掛在介面底下。

分層與依賴方向不是造型，而是可替換性的前提。只要大家都對著介面寫，儲存從 Redis 換成別的、投遞從 HTTP 增加 Kafka，都不必改動上游模組。

公共規則：所有模組都遵守的護欄

除了資料與介面，還有一組橫向的公共規則（公共 Harness），每個模組都必須遵守：

規則要求
安全不得把帳號密碼、金鑰硬寫在程式碼裡
分層程式碼歸屬在 api / core / plugin / cluster 這幾層之一，不能亂放
依賴模組只能依賴公共介面，不能直接依賴別人的實作
驗收測試不能為了讓進度好看而被刪除

公共 Harness 管的是全專案共同的規矩；每個模組再往上加自己的規則，例如「時間輪的執行緒禁止同步 I/O」「Redis 禁止 big-key」「敏感設定用環境變數」。兩層合起來，才是完整的約束。

這一節的完成標準

這一步的交付物是可編譯、可檢查的：Java 公共型別與四個介面、公共 proto（SinkType、MessageStatus、強型別 SinkConfig），以及寫進專案根目錄 CLAUDE.md 的公共 Harness。完成之後，後續每個模組就只實作自己的責任，不再重新定義公共物件。
