契約先行與 Message 公共模型

Step 1/5 · 公共契約與接入路由

學習目標

能說明為什麼 When 必須先統一公共模型再分模組實作，並描述一則 Message 的身份／時間、投遞意圖與執行狀態三組欄位。

先看一個失敗現場

假設 When 有五個模組：接入層、路由層、排程的時間輪、儲存層、投遞層。如果讓每個人各自開工，很可能出現這種結果：五個模組各自都寫完了，單元測試全綠燈，進度報告漂亮得很。等到把它們接在一起跑，系統卻到處出錯。

錯在哪？接入層收到的請求裡，訊息的編號欄位叫 taskId；儲存層存的欄位叫 messageId。兩邊都是「這則訊息的編號」，但名字不一樣，接起來就是抓不到。再比如，投遞層把一則訊息成功送出後就把它從儲存刪掉，但管理台還想查這則訊息的狀態，於是查到一半資料不見了。還有一種更隱蔽的：兩個執行者同時撈到同一則待投遞訊息，都以為自己該送，結果同一則訊息被送了兩次。

這類問題有個共同點：它們不會在單元測試裡出現，只會在整合時爆發。因為每個模組自己測自己，欄位名、狀態值、生命週期都由它自己說了算，測試自然會過。真正的衝突發生在模組的邊界上，而修這種錯，往往要同時改好幾個模組，成本遠高於一開始就講清楚。

所以第一步不是寫程式，而是定義契約

When 的作法是：在任何模組動手之前，先把「大家共用的事實」定義下來。這套事實有兩個部分：一個共用的資料模型（Message），以及一組共用的介面（後面步驟會談）。所有後續模組都指向同一份契約，最後系統才能正確地拼起來。

可以把它想成鐵路的軌距。每一段鐵路各自鋪自己的軌，鋪得再直再穩，只要軌距不一樣，火車就是開不過去。契約先行（contract-first）就是在鋪軌之前，先講好軌距是多少。

契約先行的重點不是「先寫文件」，而是「先讓所有模組面對同一組事實」。當大家共用同一份模型，模組才能平行開發、獨立實作，最後還能正確組合。

一份 Message 走遍全流程

When 裡的每一則延遲訊息，從進入系統到被送出，會經過接入、路由、調度、儲存、投遞這幾個階段。關鍵設計是：這一路用的都是同一個 Message 物件，沒有任何一個模組可以另外定義一個「長得很像」的訊息物件。欄位分成三組：

欄位家族包含什麼回答的問題
身份與時間messageId / traceId、createdAt / deliverAt、nextAttemptAt這是哪一則訊息、什麼時候該送、下次重試是哪時
投遞意圖sinkType + sinkConfig、payload（≤ 64KB）、businessTag要送到哪裡、送什麼內容
執行狀態timeWheelId / status、retryCount / deliveredAt、lastError現在進度到哪、失敗過幾次、最後一次錯什麼

把這三組分清楚，後面每一步才有共同的語言。身份與時間是訊息的座標，投遞意圖是它的目的，執行狀態是它的進度。少了任何一組，某個模組就得自己另外記一份，於是又回到剛才的整合災難。

契約如何在模組之間流動

同一個 Message 不是被複製到每個模組，而是透過公共介面在模組之間傳遞。介面就是模組之間的接縫：接入層把請求變成 Message，儲存層負責把它原子地寫入與改狀態，時間輪只記住它在記憶體裡的排程位置，投遞層最後把它送到目標。契約定得好，每個模組只要專心做好自己那一小段，接縫自然對得上。

這一節的交付物

這一節做完之後，手上應該有三樣可檢查的東西：第一，可以編譯的 Java 公共型別（Message、StatePatch 與四個公共介面）；第二，公共的 proto 定義（SinkType、MessageStatus 與強型別的 SinkConfig）；第三，寫進專案根目錄 CLAUDE.md 的公共 Harness（規範）。從下一節開始，每個模組只實作自己的責任，不能重新定義公共物件。

契約要改的時候怎麼辦

現實中契約一定會變。規則是：一旦發現欄位或介面衝突，先回頭改這份公共契約，再逐一檢查所有實作者與使用者。順序不能顛倒。如果讓某個模組偷偷改自己的版本，整合失敗就會重演。契約先行的價值，就在於讓「改一處、查全部」這條路徑清楚可行。
