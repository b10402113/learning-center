三層關係與邊界

Step 5/5 · Loop Engineering

學習目標

能畫出 SDD → Harness → Loop 的三層依賴，並用「可驗證性／出錯成本」判準決定一個任務該進 Loop 還是留給人。

先想：Loop 不是孤島

前面四步都在講迴圈本身。但一個迴圈能不能跑，其實取決於它底下站著什麼。把方法論攤開，AI 編程有三根支柱，而 Loop 站在最上層——底下兩層沒立起來，Loop 根本無從運轉。

層名稱它負責一句話
最上層Loop自主執行：做—測—修反覆跑怎麼自動化
中間層Harness造環境：規範、工具、權限、測試、隔離怎麼做對
底層SDD（規格驅動開發）想清楚：把模糊需求變成可執行規格怎麼拆、要做什麼

依賴方向是自下而上的：SDD 給目標，Harness 給邊界，Loop 給受控的執行，三者合起來才是一個完整閉環。這裡有一個很硬的推論：一個沒有自動化測試的專案，根本跑不了 Loop——因為它沒有判官。Loop 是給工程基本盤夠好的人用的；基礎設施是地基，Loop 長在地基上。

同一件事的三種思維

拿到一個專案，不要從「第一行程式碼」開始想，而是用三個角度各問一次：

  • SDD 思維：怎麼把模糊需求拆成邊界清楚、可獨立驗收的小塊？
  • Harness 思維：要立哪些規範、邊界與驗證，才能讓每塊自動被判對錯？
  • Loop 思維：哪些步驟讓 AI 在迴圈裡自主跑，檢查點要放在哪裡？

落成一條可以重複用的思考路徑：想清楚（SDD）→ 立規範與邊界（Harness）→ 設計自動化執行（Loop）→ 人驗收收尾。順序不必死板，但這個骨架最穩定。要注意的是：只有第三步的執行交給 AI，其餘三步都是你的。

邊界判準：可驗證性 × 出錯成本

有了迴圈，下一個真問題是：哪些任務該丟進迴圈，哪些永遠由人主導？判準只有一條：一個任務能不能被便宜且確定地驗證，以及做錯了代價大不大。兩個維度一交叉，分工就出來了。

驗證便宜、錯了也便宜難驗證、錯了很貴
交給 Loop資料結構、邊界清楚的模組、格式轉換、樣板程式碼、有測試護著的 refactor—（這一格不存在）
人主導—（人可以順手做，但沒必要）分散式一致性、failover 正確性、金錢與安全、長期演進的架構決策

用具體的例子會更清楚。AI 很擅長：多層時間輪演算法、儲存層的 key 設計與 IO、介面與序列化、投遞插件與重試——這些都是輸入輸出清楚、行為確定、測得出來的工作。AI 容易翻車：副本一致性、選舉與腦裂、failover 的時序、以及像「至少一次 vs 恰好一次」這種本質上是產品取捨的語義決策。

為什麼容易翻車的偏偏是這些？因為它們有兩個致命的共同點：只在精確的那一刻失敗（平常跑都好好的，偏偏在節點真的死了的那一秒出錯），一般的測試會過（所以判官抓不到），而且修起來非常貴。這種工作，AI 可以幫你做分析與實作，但方案本身必須由人來定。

邊界只在一句話：把「便宜、可確定驗證、錯了也便宜」的工作交給迴圈；把「難驗證、錯了很貴」的工作留給自己。一致性、金錢、安全，永遠是人主導。

實作上，這個判準要在切任務的時候就標記——還記得任務卡的最後一欄「執行模式」嗎？那正是你把「這塊誰主導」寫下來的地方。切錯這一欄，代價通常比你親手寫那一塊更高。

業界收斂：三個人，同一套結構

這套東西不是某個人的發明，而是前線實務者各自摸出來的同一個結論：

實踐者他的做法展現的要素
Ralph一個 while 迴圈，每次都丟同一份提示，但每輪用全新的實例可判目標 + 隔離 + 停止
Boris Cherny數百個並行迴圈，讀 GitHub／Slack 決定要做什麼，實作與驗證分離，失敗回饋進規則判官 + 防作弊 + 規模化
Andrew Ng三層嵌套迴圈：Agent 寫程式 / 人審查 / 真實使用者回饋人類檢查點 + 分層判官

三種說法用詞不同，但拆開來看都是同一組五要素。這種獨立收斂正是這套框架值得學的理由：不是因為某個大師說了算，而是不同的人在沒有互通的情況下，都走到了同一個結構。

規模化：一次一個模組，判官逐級升級

當一個迴圈跑順了，怎麼放大？原則是一次一個模組，配一次人工驗收——不要妄想一個迴圈吃下整個專案。以分散式元件為例，可以拆成一張張任務卡（接入與介面契約、路由雜湊、多層時間輪、儲存、協調、副本與 failover、投遞與重試），每張卡都帶著可自動跑的驗收，讓迴圈一張張跑；而 failover 的正確性這種難驗證的部分，始終由人帶著。

規模化時，判官也要逐級升級：本地快速測試 → PR／CI → 雙 Agent 交叉驗證。同時把狀態外部化成一份 STATUS.md，讓進度不藏在某個對話的上下文裡。這樣即使同時跑很多張卡，你仍然掌握全域。

那三件 AI 拿不走的事

Loop Engineering 把執行外包出去，把人從「做」拉回「判斷」，但它拿不走三件事：

  • 判斷力：這個計畫對不對？這個取捨值不值得？什麼時候該停？
  • 思考力：問題到底是什麼？為什麼是這個問題？還有沒有別條路？
  • 產品感：這是給誰用的？他為什麼要用？該砍掉什麼？

這三件事反而因為 AI 的放大而更值錢——當執行變便宜，稀缺的就是「知道要做什麼」。所以 Loop Engineering 對一人公司的意義不是「不用思考」，恰恰相反：它逼你把 70% 的精力花在定義問題與驗收標準上，因為那才是迴圈唯一無法替你完成的部分。
