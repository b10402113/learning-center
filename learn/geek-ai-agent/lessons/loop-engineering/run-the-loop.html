跑一輪 Loop

Step 4/5 · Loop Engineering

學習目標

能走完一輪「讀任務卡 → 先寫測試 → 實作 → 跑驗收 → 讀失敗修正」，講出四個停止條件，並寫出一張六欄位的任務卡交給 /loop。

先想：迴圈真正在跑的是什麼

前兩步講了原則：五要素、判官與防作弊。現在把它落成一個每天真的能跑的動作。整個迴圈其實就是一個不斷重複的小循環，外加四道「什麼時候該退出」的閘門。你可以把它想成一台自動除錯機：丟進一張清楚的任務卡，它自己跑到驗收變綠。

一輪循環的五個動作

每一輪，迴圈做這五件事，然後回到第一步：

  1. 讀任務卡——先弄清楚這次要做什麼、驗收標準是什麼。
  2. 先寫測試（TDD）——把驗收標準寫成會失敗的測試。這一步是「先立判官，再做實作」。
  3. 實作——寫程式讓測試有機會通過。
  4. 跑驗收——執行測試／編譯／lint，拿到一個客觀的「過或不過」。
  5. 讀失敗、定位、修——不是瞎改，而是讀錯誤訊息、找到原因、針對性地修，然後回到第 4 步重跑。

這個循環會一直轉到驗收全綠，或者撞到下面四個停止條件之一。注意第 2 步的順序：先寫測試再實作，是讓判官在實作之前就存在，避免「邊做邊改測試」的作弊空間。

四個停止條件

一個沒有停止條件的迴圈是危險的——它會無限地轉、或者無聲地跑歪。要事先寫死四種「必須停」的情況：

停止條件停下來做什麼
所有驗收測試通過停，交出成果給人做最終驗收
迭代次數超過上限（例如 15 輪）停，回報目前卡在哪、還差什麼，不硬撐
任務卡有歧義、無法判定停下來問，絕不自己猜一個方向
需要動到邊界以外的程式碼停下來確認，不擅自越界修改

後兩個條件是精髓：停下來問，永遠比猜錯後重跑十輪便宜。迭代上限則防止它陷入無限迴圈，也逼它在卡住時把狀態交還給人。

任務卡：餵給迴圈的輸入合約

迴圈好不好跑，八成取決於你餵進去的輸入。這個輸入叫任務卡，寫起來大約 20 分鐘，有六個必填欄位：

欄位要寫什麼
模組這次要動哪個模組／檔案範圍
目標這個功能要做什麼
驗收標準什麼情況算完成——必須是可判定的
需要的測試要寫哪些測試來驗收
邊界不准碰什麼、不准做什麼
執行模式這張卡由誰主導（交迴圈，或人主導）

關鍵在驗收標準與測試必須「可判定」——機器能自動判對錯。「效能要好一點」不是驗收標準，因為沒有東西能自動判定它過或不過；「P99 延遲低於 50ms」才是。如果你寫不出可判定的驗收，代表你還沒把問題想清楚，這時候不該開工。

還有一個容易搞混的界線：任務卡不是 mini-spec。架構決策、選型、跨模組的約定，屬於技術方案與 CLAUDE.md 之類的專案規範，不塞進卡片。卡片只裝「這次要完成的增量」——小到 20 分鐘能寫完，邊界清楚到能獨立驗收。

任務卡是迴圈的輸入合約。卡片模糊，迴圈就沒有收斂的目標；卡片可判定，迴圈才知道什麼叫做完。

把它固化成一個 /loop Skill

這些規則不需要每次重講，可以沉澱成一個 Agent Skill（例如 .claude/skills/loop/SKILL.md），裡面保留三個骨架區塊：

  1. 輸入驗證——檢查任務卡六欄位是否齊全、驗收是否可判定；不齊就拒收。
  2. 停止條件——寫死上面那四條。
  3. 絕對禁止——不准改測試、刪測試、停用測試，不准繞過驗收。

另外，要宣告「只在被明確叫用時才啟動」，讓人決定何時進迴圈，而不是 AI 自己判斷要不要開跑。這個 Skill 最可貴的地方，是它把你對「什麼是好工作」的判斷，變成一個可以重複使用的資產。

人只做三件事

整套跑順之後，人的工作被壓縮成三個動作：

  1. 寫任務卡——把這次的增量、驗收、邊界寫清楚。
  2. 跑一行——/loop TASK-001.md，它在隔離的分支上自己轉到完成或停止。
  3. 最終驗收——看它回報的完成狀態、關鍵判斷與待決事項，決定收下或退回。

中間的執行整段不需要你。而當結果不對時，最好的做法通常不是跟 AI 在對話裡爭十輪，而是直接去改那張任務卡，然後從乾淨的狀態重跑一次。因為爭論只會把上下文弄髒；改卡片才是修正了迴圈的輸入，然後讓它用乾淨的狀態重新跑。前者是治症狀，後者是治因。
