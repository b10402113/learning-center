為什麼要寫自己的 init skill

Step 3/5 · 工程地基（init skill）

學習目標

能對比通用 init skill 與專屬 init skill 的得失，說出 OryxOS 為何要寫自己的 init skill，以及這背後的「何時把流程磨成 skill」方法論。

先看一個選擇：新專案要用誰的 init skill

上一課的結論是「六塊地基應該一次安裝」。市面上一定有人寫過通用的 init skill——一個能在任何專案裡初始化工程地基的流程。那直接拿來用不就行了？

OryxOS 團隊試過這條路，發現關鍵問題：通用 skill 不懂 OryxOS。它不知道 OryxOS 有九個 Maven 模組、不知道憲法技術棧的決定、不知道專案裡的命名與目錄慣例。於是你不能拿來直接用——你得對它做大量改造：把模組結構塞進去、把技術選型塞進去、把命名規則塞進去。改完之後你會發現，你其實已經在寫一個 OryxOS 專屬的 skill 了。

通用 skill 的落腳處

通用 init skill 不是沒有價值——它把「標準部分」先做好一版，讓專屬 skill 不用從零發明。但對 OryxOS 來說，通用的那一版只是素材：真正要落地的是「這個專案」的地基，而 OryxOS 的地基本身就帶有 OryxOS 的規格。通用工具可以被當成地基的一部分（例如把標準工具如 Spotless、Checkstyle 裝起來），但「OryxOS 的九模組結構」這種資訊，通用 skill 天生不知道，必須由專屬 skill 自己編碼。

OryxOS 專屬 init skill 的三個價值

價值它做了什麼通用版做不到的事
九模組骨架入體skill 知道 OryxOS 是 Maven 多模組、知道要建哪些模組、知道 parent pom 與 oryxos-boot 的角色——第一次跑就建出正確的骨架
憲法對齊skill 遵守憲法的技術選型（JDK 21、Spring Boot 3.x、開箱即用的 SQLite…），不會自己「選」一套不同的
標準工具照樣落地雖然是專屬 skill，它仍然安裝標準工具（日誌、監控、安全四件套），不重新發明

這裡有一個看起來矛盾、其實成立的組合：訂製的流程 ＋ 標準的工具。訂製的是「專案結構與慣例」，標準的是「每個企業都要的工程能力」。專屬 skill 把前者編碼進來，同時繼承後者。

方法論：何時該把流程磨成 skill

這背後是一條可複製的方法論：一個流程如果通用、可重複、會一再發生，就值得把它磨成 skill。判斷的三個問題：

  • 它反覆發生嗎？每個新專案、每個新模組都要做，不是一次性動作。
  • 它有明確定義的結果嗎？「地基起好」有可驗收的結果（mvn verify 全綠），不是模糊的目標。
  • 它包含專案的慣例嗎？如果包含（模組結構、命名、技術選型），通用工具就要讓位給專屬 tool，把慣例直接寫進流程。

OryxOS 把這條方法論真正落地：不是寫一份文件描述「該怎麼初始化」，而是寫一個 SKILL.md，讓 AI 跑一遍就能按同樣步驟完成。這正是 skill 相對於文件的差別——它是可執行的。

長期的回報：團隊與社群可重用

寫成專屬 skill 的投資，在專案生命週期裡反覆回收：團隊任何一個人開新模組，跑同一個 skill 就得一致的結果；未來 OryxOS 走向開源社群，這個 skill 也變成「任何人 30 分鐘復刻 OryxOS 骨架」的入口。這正是「把知識寫進流程，而不是寫進人腦」。
