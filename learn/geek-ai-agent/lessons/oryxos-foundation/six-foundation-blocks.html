六塊工程地基

Step 2/5 · 工程地基（init skill）

學習目標

能說出六塊工程地基各自是什麼、用什麼工具落地，以及為什麼它們都是與業務無關、每個專案都需要的通用能力。

先看一個畫面：企業級專案的「地基清單」

上一課講了紀律——先起地基，再寫業務。這一課把它變成具體清單。OryxOS 的地基是六樣東西，每一樣都是「不屬於任何業務，但少了它整個專案會出事」的基礎建設：

地基用什麼工具落地它解決什麼
結構化日誌SLF4J + Logback，輸出 JSON + traceId線上出錯能從日誌串起一次請求的完整旅程
監控Actuator + Micrometer + Prometheus系統慢、漏記憶體時，數字先於使用者發出警報
HTTP serverSpring MVC + JDK 21 Virtual Thread高併發下不用把程式碼寫成反應式，也能扛住大量連線
API 規範springdoc OpenAPI＋統一回應＋全局異常處理所有端點長得一致，外部調用者一次學會全部
代碼標準Google 風格（Spotless）＋阿里巴巴 P3C 規約AI 生成的程式碼與手寫的程式碼風格統一，可 review
安全檢查SpotBugs + Find Security Bugs + PMD + OWASP 依賴掃描上線前攔下靜態漏洞與有已知漏洞的依賴

六塊各自在守什麼

結構化日誌：事故現場的可追蹤性

企業系統裡，最貴的一句話是「它現在出事了，但我不知道為什麼」。結構化日誌把日誌從「一行一行的人讀文字」變成「機讀的 JSON」，每一行都帶 traceId——同一次請求從進入系統到完成，所有日誌共用同一個 id。SLF4J 是日誌門面（程式碼只依賴介面），Logback 是實作（決定輸出成什麼格式）。之後查問題就是「拿 traceId 搜一個旅程」，而不是翻大海撈針。

監控：讓數字先於使用者發現問題

沒有監控，系統變慢時，通常使用者先知道，你後知道。監控要解決的正是這個順序問題。Actuator 暴露運行時指標（health、metrics endpoints），Micrometer 把指標以標準格式爆出來，Prometheus 定時拉取、儲存、畫圖。於是你不是等使用者抱怨，而是看著 CPU、記憶體、請求延遲的曲線自己先轉彎。

HTTP server：Virtual Thread 的併發紅利

OryxOS 是同步阻塞的寫法，為什麼能扛併發？因為 JDK 21 的 Virtual Thread（虛擬執行緒）：每一條連線有一個輕量執行緒，阻塞在 I/O 上時會自動讓出，OS 執行緒不會被「一個連線卡住就空轉」。程式碼保持直覺的同步風格，卻能處理大量並行請求。這是一塊地基式的選型——它決定整個專案能否用「簡單寫法」換到「高併發」。

API 規範：接口的一致性契約

OryxOS 有 10 個端點。若每個端點各自決定回應格式，前端與外部調用者就得學 10 種脾氣。地基的做法是一次釘死三件事：springdoc OpenAPI 自動生成 API 文件（/swagger-ui 可以直接探索）、統一回應格式（成功失敗都包成同一個形狀）、全局異常處理（error 不會裸拋到客戶端，而是被同一個 handler 轉成統一格式）。

代碼標準：AI 時代的可協作性

這在 AI 大量生成程式碼的專案裡格外重要。沒有標準，AI 每次生成的格式都不一樣，與團隊手寫的程式碼互相打架。OryxOS 用兩層標準：Spotless 套 Google 格式（機械性、自動格式化），再加上阿里巴巴 P3C 規約（阿里巴巴 Java 開發規範的檢查規則）。機械部分交給工具，規範部分由檢查守門。

安全檢查：上線前的四道閘

安全不是補丁，是地基。OryxOS 的安全是一組「四件套」：SpotBugs（靜態分析找 bugs）、Find Security Bugs（專門找安全相關的程式碼模式，如 SQL injection、路徑穿越）、PMD（可自訂規則的靜態分析）、OWASP 依賴掃描（檢查每個依賴有沒有已知 CVE）。四者全部被接進 mvn verify——意思是不需記得手動跑，每次驗證自動全部執行。

為什麼這六塊可以「一次安裝」

關鍵特質：六塊沒有一樣依賴「這個專案是做 Agent 還是做電商」。它們是通用且可重複的——任何 Java 企業專案都需要日誌、監控、HTTP、API 契約、代碼標準、安全檢查。既然每開一個新專案都要重做這套，而這套又完全是標準動作，唯一合理的下一步，就是把它們包進一個可以重複執行的流程——這正是下一課〈為什麼要寫自己的 init skill〉的開場。
