從單機到分散式：狀態外置與 Agent 協作的遠景

Step 5/5 · 分散式的第一步不是多開幾台，而是先把狀態搬出去

學習目標

說明「實例無狀態、狀態外置」為何是分散式的第一步，並描述多實例要解決的協調問題、高可用與水平擴展的模型，以及更遠的跨節點 Agent 協作遠景。

起點：目前是單機私有部署

OryxOS 現在的樣子是一台機器上的單一實例，私有部署。這對很多企業已經夠用，但只要業務量長大、只要不能停機，就一定會走到「多實例一起跑」這一步。而從單機到叢集，關鍵的第一步幾乎所有人都會猜錯。

核心原則：實例無狀態，狀態外置

大部分人以為分散式的第一步是「多開幾台機器、前面掛負載均衡」。但如果每一台實例自己的硬碟裡都存著不能重建的狀態，那你只是把一個會壞的系統變成四個會壞的系統——而且更難修。

真正的第一步是：讓實例不持有任何「不可重建」的狀態，把所有狀態外置到共用的儲存層。

具體搬去哪裡，其實都是企業早就有的中間件：

狀態搬到哪
Session／短期上下文Redis
長期記憶／Skill 庫PostgreSQL（pgvector）或獨立的向量庫
審計日誌／大檔案物件儲存
Agent 設定／租戶資訊配置中心＋資料庫

做完這一件事，實例就變成「可拋棄的」——壞了就重開一台，狀態從共用儲存重建即可。這是後面所有分散式能力的地基。

多實例下要解決的幾件事

狀態外置之後，新的問題才會浮現。它們都是「多個實例同時在看同一份狀態」造成的：

問題解法方向
渠道訊息被重複消費統一訊息分派層／佇列的 consumer group，確保一則訊息只被處理一次
Agent 調度與歸屬用分散式鎖／lease 管理定時任務與長任務，避免兩個實例同時跑同一個 Agent
多租戶隔離在儲存層用 key 前綴／schema 隔離，並讓租戶身分一路帶在請求路徑上

注意這裡的「重複消費」與「同一個 Agent 被跑兩次」都是靜默錯誤——系統不會當掉，只會偷偷做兩次事。這類錯誤比崩潰更難發現，也是分散式最貴的地方。

高可用與水平擴展

做完上面兩步，高可用與擴展就變得很自然：無狀態實例放上 K8s，前面掛負載均衡；某台實例掛掉，流量自動轉移；要擴容就多開幾台，不需要搬資料；儲存層各自用自己的 HA 機制（都是企業熟悉的中間件）。

換句話說：難的不是「多開幾台」，難的是「讓多開幾台是安全的」。前者是運維動作，後者是設計決定。

為什麼 Java 生態做分散式是順手的

這裡又回到 Java 的優勢。分散式需要的整套工具鏈，Java 生態早就有了：Nacos 做註冊與配置、Sentinel 做限流與斷路、Spring Cloud Gateway 做閘道、SkyWalking 做追蹤、Prometheus＋Grafana 做監控。而且這些東西企業裡本來就在跑。

反過來說，Node.js／Python 的專案要做到同樣的分散式與服務治理，多半得自己補一整套。分散式、高可用、服務治理，正是 Java／Spring 最強的地方。

更遠的願景：跨節點的 Agent 協作

上面談的都還只是「同一個底座多開幾台副本」。再往前一步，是真正意義上的跨節點 Agent 協作：不同部門、甚至不同組織的 Agent，能夠互相發現、可靠地把任務委派出去、共享必要的上下文。

這個場景可以類比成「服務發現、RPC、訊息中介出現之前的早期分散式系統」——大家都知道最終需要它，但標準與基礎設施還沒成形。它需要的是一個獨立的 Agent 通訊底座：OryxOS 負責單節點 runtime，通訊底座負責把節點連起來。

必須說清楚：這是方向性的願景，不是當前的需求。現階段的務實目標是單機私有部署，中期是實例無狀態＋狀態外置的分散式底座，遠期才是跨節點協作。

順便看一眼這一層的三年判斷

把視角拉到未來三年，有幾個趨勢判斷值得記住：協定會收斂（工具與資料接入會逐步標準化，MCP 這類協定會像 JDBC／ODBC 一樣）；底座會下沉成基礎設施（像今天的訊息佇列與註冊中心，成為企業的標準一層）；競爭點會從「能不能跑」轉向「治理與成本」（審計、權限、配額、可觀測、多模型調度）；而開源會佔相當份額，因為想掌握控制的企業需要一個能自己看、自己改的底座。

在標準還沒定死、底座還沒成形的這個窗口裡，個人與小團隊才有切進去的機會。

帶回自己

你之後會用 Loop 工程做一個分散式延遲投遞元件（etcd 協調、時間輪、Master／Slave、10 秒 failover），那是「分散式中間件」的分散式；OryxOS 這裡是「Agent 底座」的分散式。兩者手段相似（無狀態、外置狀態、lease、consumer group），但目標不同——前者的難點在協調與故障轉移的精確性，後者的難點在把一整套狀態安全地搬出實例。把這一課的原則記住：先問「這個狀態能不能重建、該放哪」，再談要開幾台。
