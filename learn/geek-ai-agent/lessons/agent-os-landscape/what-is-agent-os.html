Agent OS 是什麼：運行時之上的作業系統

Step 1/5 · 先把名詞釘死，後面四步才有共同語言

學習目標

說出 Agent OS 的定義與五大職責，並分辨它與 agent runtime（代理運行時）、編排平台、框架、SaaS 的差別。

從「一個 Agent 能跑」到「一群 Agent 一起跑」

你已經寫過一個會跑的 Agent：一個 ReAct loop、幾個工具、一份 system prompt，就能查天氣、讀檔案、發通知。當這個專案只有你一個人、只有一個 Agent，一切都很順。

但把場景換到企業：客服一個 Agent、運維一個 Agent、人資一個 Agent、銷售一個 Agent，每個都要接飛書／企業微信、都要呼叫自家 LLM、都要記住跨對話的偏好、都要能碰內部系統。這時候你會發現，真正難的不是「再寫一個 Agent」，而是這一群 Agent 共用的一堆橫切面——渠道、模型、記憶、工具、權限、審計——每個 Agent 各寫一套，等於把同一段基礎設施重寫 N 次，而且沒人管得住。

runtime 讓「一個」Agent 跑起來；Agent OS 讓「一群」Agent 在企業裡被管起來。

Agent runtime 與 Agent OS 的差別

這兩個詞常被混用，但分工很清楚：

Agent runtime（代理運行時）Agent OS（代理作業系統）
管什麼一個 Agent 的執行：LLM 呼叫、工具執行、上下文組裝、loop 控制一群 Agent：生命週期、統一接入、統一記憶、多租戶、審計
數量單位一個一隊
類比單一行程的執行環境管理一群行程、調度資源、提供共用服務的那一層

換句話說，Agent OS 裡面一定包含一個 runtime，但它多了 runtime 沒有的東西：多 Agent 的生命週期管理、對外對內的統一接入、跨 Agent 的記憶、以及企業要的多租戶與審計。

一個底座必須解決的五件事

「底座」不是隨口喊的稱號。缺了下面任何一件，它就不算底座：

#職責具體內容
1Agent 生命週期註冊、啟動、監控、銷毀；每個 Agent 有自己的 prompt／模型／工具／渠道／記憶
2對外統一渠道IM（飛書／企業微信／釘釘／Slack）、郵件、Web、HTTP API 共用一層渠道層
3對內統一接入LLM Provider、工具（MCP／插件）、企業 IT 系統、知識庫共用一層接入層
4統一記憶跨對話的長期記憶、可重用的 Skill、跨 Agent 的知識沉澱
5工具調用與沙箱由 Function Calling 驅動、在沙箱中執行，守住安全邊界

把這五件事再往工程拆，就是底座常見的八個能力區塊：Provider（模型接入）、Memory（記憶）、Tool（工具）、ReAct（推理迴圈）、Sandbox（沙箱）、Notify（通知）、安全審計、分散式。這八塊也是你接下來重建 OryxOS 時的地圖。

Agent OS 長什麼樣

它通常是你自己機器／伺服器／K8s 上的單一實例，內建一個 Web 控制台或 CLI。Agent 不是用程式碼「寫」出來的，而是用設定「配」出來的：業務方只要寫一個 Tool、填一份 Agent 設定，終端使用者就能在自己的 IM／Web 裡跟它對話。

這裡藏著一句很重要的設計宣言：

Agent 是「配」出來的，不是「寫」出來的。業務方完全不需要知道訊息從哪來、LLM 怎麼被呼叫、身分怎麼驗、審計怎麼記、上下文怎麼組。

這些「不需要知道」的事，正是底座要替所有人扛下來的部分。

跟三個容易混淆的概念劃清界線

市面上有一堆東西都自稱在「做 Agent」，但產出的東西完全不同：

類別代表產出的是什麼跟 Agent OS 的關係
編排平台Dify、Coze一條可視化工作流跑在 Agent OS 之上，把 OryxOS 當客戶端；互補不互斥
框架LangChain、Spring AI可被引用的程式碼／元件位在 Agent OS 之下，被 Agent OS 重用
大廠中台／SaaSGlean、Bedrock AgentCore、Agentforce一個完整但鎖在別人雲上的應用無法私有部署、生態鎖定，是嚴監管企業的排除項

一句話收斂：框架在底層被重用，編排平台在上層當客戶端，Agent OS 自己站在 runtime 這一層。

順手釐清一個常見的命名之爭

「Agent 平台／框架」談的是怎麼開發 Agent——編排、模板、低程式碼、多 Agent 協作，本質是開發者生產力。而「Agent OS／底座」談的是一群 Agent 怎麼被管理——生命週期、渠道、記憶、權限、審計，本質是企業的運行時與治理。

名稱之爭不重要，重要的是別把「開發工具」誤當成「運行底座」。真正決定成敗的，是後者有沒有被解決。

帶回自己的 runtime

把這一課對照回你自己寫的 ReAct loop：那個 loop 是 runtime，它讓「一個」Agent 能跑。當你想讓它變成底座，缺的通常正是五件事裡的前四件——生命週期、統一渠道、統一接入、統一記憶。這一層的決策與語言無關，Java runtime 一樣要面對；差別只在你是否意識到它存在。
