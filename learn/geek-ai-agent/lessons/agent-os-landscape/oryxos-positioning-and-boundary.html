OryxOS 的定位、邊界與安全設計

Step 4/5 · 一句話定義、一條邊界、一套安全觀

學習目標

用一句話定義 OryxOS，說清它的四字願景、做 runtime 不做編排的邊界，以及它與框架、編排平台、其他開源專案的關係與 day-one 安全設計。

OryxOS 是什麼：一句話

OryxOS 是一個企業完全可控、Java 原生、私有部署、可審計的統一 Agent 底座。

把它展開：它部署在你自己的 K8s／伺服器／實體機上，同時跑各種業務 Agent，讓它們共用渠道接入、模型路由、記憶、工具呼叫與安全審計。業務方要做的只有兩件事——配置一個 Agent、用 MCP 寫一個 Tool。資料留在企業內，不綁任何雲；業務方不需要寫 Agent 的後端程式碼。

它是一個採用 Apache 2.0、可完整審計、可 fork 的開源專案。這個授權選擇本身就是定位的一部分：嚴監管企業要的是「能自己看、自己改」的底層。

它把錨下在哪裡

OryxOS 借「Agent OS」這個框架來描述自己，但它刻意不把錨下在概念上，而是下在不變的需求上：嚴監管企業需要一個完全可控的 Agent 底座。

這個區別很關鍵。如果你錨在「Agent OS」這個詞，哪天這個詞被換掉、被行銷用爛，你就失去了立足點；但如果你錨在「企業需要一個完全可控的底座」這個需求，無論概念怎麼變，需求都還在。

四字願景：統一、私有、易接入、可觀測

字意思
統一一群 Agent 共用同一套渠道、接入、記憶與工具層
私有資料與能力都留在企業自己的基礎設施上
易接入像安裝一個 Spring Boot 應用一樣自然，業務方只負責業務
可觀測每一次呼叫、每一段決策都可被追蹤與審計

這裡最深的價值錨點還是知識沉澱：透過 Skill 系統，資深員工的經驗會被寫成可重用的技能，留在企業裡，而不是隨著人員流動帶走。

邊界：做執行時，不做編排

一個底座最怕什麼都想做。OryxOS 很清楚自己守在哪一層——runtime：

它做（runtime 層）它不做（編排層）
Channel（渠道）、LLM Provider、Memory、Tool registry、Sandbox可視化工作流編排
多租戶、SSO、RBAC、審計複雜任務分解
可觀測、Web 控制台顯式的多 Agent 協作編排

看懂了嗎？編排平台（像 Dify）其實可以跑在 OryxOS 之上，把 OryxOS 當成一個客戶端。這不是退讓，而是分工：OryxOS 守著底座，編排在它上面蓋。

OryxOS 不是什麼：三方對比

用「產出什麼、給誰用、站在哪一層」三個維度看，一切就清楚了：

框架（LangChain／Spring AI）編排平台（Dify）OryxOS
產出程式碼一條工作流被配置好的常駐 Agent
給誰用開發者業務人員業務方配置＋寫 Tool
站在哪層最底層的元件應用層runtime 層

所以 OryxOS 同時「重用框架」與「支撐編排平台」，而自己佔住 runtime 這一層。

安全：把它當第一天的設計，而不是補丁

前一步看過 OpenClaw 的教訓——它的安全問題是結構性的。OryxOS 選擇在每一點上都走相反的路：

面向OryxOS 的做法
Skill／Tool 來源受控註冊與審查，不做無界的公開技能市集
權限最小權限，而不是預設全開
隔離強制沙箱，檔案／網路／shell 預設收緊
憑證走企業金鑰系統（KMS／Vault），憑證不落地、不進 prompt／log
攻擊防禦主動防 prompt injection（提示注入）與資料外洩，記憶寫入與工具輸入都過安全掃描
審計全鏈路審計是底座能力，且輸出到企業 SIEM
流程對接因為是在企業基礎設施上跑 Java／Spring，能直接過既有安全審查

最後一點常被忽略但最重要：安全不是自己說安全，而是要能被企業既有的審查流程接受。Java／Spring 的技術選型在這裡再次變成優勢。

它跟其他專案的關係

OryxOS 並不重新發明輪子。它借用 OpenClaw／Hermes 已經驗證過的設計哲學——Agent 生命週期、Channel 抽象、三層記憶、以 SKILL.md 描述技能（相容 agentskills.io 開放標準）、MCP 工具呼叫、單一二進位打包——然後用 Java 重新實作，再補上多租戶、SSO、RBAC、審計、Web 控制台與深度整合。

同一個類別，不同定位：OpenClaw 服務個人，Hermes 服務小團隊，OryxOS 服務嚴監管企業；與編排平台互補，與 Java AI 框架是重用關係。

工程設計：插件化與生產門檻

底座要能長期演進，靠的是插件化：Provider 插件（換模型不改上層）、Tool 插件（加工具不動核心）、Memory／儲存插件（換儲存只加一個實作）。做法是在核心定義介面、把實作放進插件目錄，用 SPI／registry 載入。檢驗標準只有一句：

加一個模型或工具，需不需要改核心程式碼？如果需要，代表抽象錯了。

而從 demo 走進企業，會遇到四道「生產門檻」，也是企業第一次評審必問的：

門檻要求
多租戶隔離不同部門／業務的 Agent、資料、配額互不干擾
權限與配額誰能呼叫哪個工具、每日幾次、超額怎麼辦
工具沙箱執行有資源與網路邊界，出錯不影響底座
全鏈路審計每次呼叫都可追溯：誰、何時、做了什麼、結果如何

帶回自己

用「邊界」和「生產門檻」兩把尺，量一下你想做的底座：它有沒有正在偷做編排的事？加一個新模型時，你得動核心碼還是只加一個插件？企業第一次評審問你多租戶與審計時，你答得出來嗎？這三題決定了它是玩具還是底座。
