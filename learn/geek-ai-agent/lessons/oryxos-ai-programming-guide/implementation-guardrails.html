實施護欄：讓 AI 跑在軌道上

Step 4/5 · OryxOS AI 編程指南

學習目標

能列出跨 US 的協作動作與五個最容易寫錯的點，並在 AI 跑偏時知道怎麼修正。

為什麼需要護欄

即使準備階段做得再完美，真正的實作還是會遇到一個根本問題：AI agent 的上下文會斷。它做 US-3 的時候，可能已經忘了 US-1 定下的 provider 規則；它生成程式碼的時候，可能已經偏離了憲法。護欄就是為了在偏離發生時把它拉回來。

跨 US 的四個協作動作

整個實作過程有四個必須反覆執行的動作：

  1. 每個 US 跑完後跑一次 /speckit.analyze。它做跨 artifact 的一致性檢查（constitution ↔ spec ↔ plan ↔ tasks），只讀不改、只報告問題。官方建議的時機是 tasks 之後、implement 之前。
  2. 發現 AI 偏離憲法時立刻糾正。不要等到整個 US 做完才回頭改——那時錯誤已經擴散。
  3. 上下文丟失時，重讀 spec、plan 與最近的程式碼。這是把斷掉的上下文重新接上的標準動作。
  4. 每個 US 完成後做一次 git commit。有了 commit 邊界，出錯時才知道該退回哪裡。

五個最容易寫錯的點

這些是 OryxOS 專案裡反覆出問題的地方，值得事先背下來：

易錯點正確做法
Spring AI 自動工具執行被打開在任務裡明確關閉，工具才不會被呼叫兩次
provider 用型別掃描自動註冊改用顯式的 name → ChatModel 映射
Tool 被拆成多個模組保持 Tool 的單一抽象，不要按工具種類拆模組
SkillLoader 被當成 ToolSkillLoader 是載入器，不是工具；兩者職責不同
審計表沒有被持久化US-5 就要把審計表寫進 SQLite，對應憲法原則

這五點的共通性很明顯：它們都是憲法已經寫明、但 AI 因為上下文丟失或偷懶而略過的地方。這也是為什麼 analyze 要反覆跑——它正是用來抓這種跨階段的遺漏。

實作上的常見挑戰

除了上述五個易錯點，還有幾個會拖慢進度的現實挑戰，以及它們的處理方式：

  • AI 偏離憲法：重讀 constitution.md，把偏離的地方擋下。
  • 跨 US 的上下文斷裂：重讀 spec、plan 與最近的程式碼。
  • analyze 被跳過：把它設成硬性步驟，不是「有空才跑」。
  • MCP 整合踩坑：先用一個最小的 MCP server 測連線，確認通了再接真的工具。
  • Java 基礎不足：這是前提——Spring Boot、Maven、JPA 不熟的話，會卡在跟 AI 無關的地方。

工具本身的使用紀律

最後是關於 Spec-Kit 這把工具本身的三條紀律：

  1. 主體開發期間鎖定一個特定的 Specify CLI 版本，避免工具更新造成行為漂移；
  2. 永遠以官方文件為準，不要憑記憶或二手教學操作；
  3. 只用官方核心命令，不要用社群那七十多個擴充套件——它們品質不一，會引入不確定性。

護欄的本質不是「不信任 AI」，而是承認上下文會斷、上下文斷了行為就會漂——所以要用外部機制（analyze、commit 邊界、憲法）把漂移拉回來。
