按 user story 拆解，不按時間拆

Step 3/5 · OryxOS AI 編程指南

學習目標

能按 user story 把 OryxOS 專案拆成有依賴順序的可執行任務，並說出五個 US 各自的核心任務類別。

為什麼是「按 user story」而不是「按時間」

最直覺的拆法是按時間：第一週做 A、第二週做 B。這種拆法在 AI 編程裡行不通，因為它把相依的東西硬切成時間片段，最後會得到一堆無法獨立驗收的半成品。

另一種拆法是按 user story。它好在兩點：第一，每個 user story 都能獨立驗收（有對應的 demo），做完就有一個能跑的東西；第二，依賴關係自然浮現，你可以一眼看出誰一定要先做、誰可以並行。而 Spec-Kit 的 /speckit.tasks 天生就按 user story 組織任務——OryxOS 的五個能力剛好可以用五個 user story 表達，兩边的拆解方式天然對齊。

主幹：一條依賴鏈

五個 user story 之間的依賴關係非常清楚：

User story能力依賴
US-1對接 LLM（Provider）無，是地基
US-2ReAct 迴圈依賴 US-1
US-3Memory 三層記憶依賴 US-2，與 US-4 獨立
US-4Plugin Tool 體系依賴 US-2，與 US-3 獨立
US-5Web Service依賴前四個

所以實作順序是 US-1 → US-2 →（US-3 與 US-4 並行）→ US-5。US-3 和 US-4 可以同時做，因為它們都只依賴 US-2、彼此之間沒有依賴。US-5 一定要最後，因為它要把前面所有能力透過 REST 暴露出去。

US-1：對接 LLM

目標：讓 OryxOS 能透明地呼叫任何主流 LLM，並具備選模、呼叫、轉換、審計的能力。涉及模組：core、provider、boot。任務大致分成四類：環境搭建、核心抽象、provider 實作、設定。

這裡有一顆地雷：provider 要用顯式的名稱映射（name → ChatModel），不要用型別掃描。AI 很愛用掃描自動註冊 provider，但那會讓啟動行為不可控。

US-1 本身沒有 demo。原因很簡單——LLM 對接是底層能力，要等 US-2 的 ReAct 迴圈把它串起來，才能跑出第一個可展示的東西。

US-2：ReAct 迴圈

目標：做出 Agent 的核心機制。涉及模組：core、tool、channel-cli、cli。任務類別：ReAct 迴圈本體、CLI 通道、基礎工具、Profile 的 YAML 定義、Session（記憶體版）。

這個 user story 的關鍵是和 AI 的對話：要把 ReActLoop 與 PromptBuilder 拆成兩個子任務分別做，並且在任務裡明確寫出「關閉 Spring AI 的自動工具執行」。為什麼？因為 AI 很容易預設啟用它，結果工具被呼叫兩次——一次由 Spring AI 自動執行、一次由你自己的迴圈執行。這個坑在 US-2 就要堵住。

Demo 1：天氣查詢加穿搭建議。這是 OryxOS 的第一個可運行展示。

US-3：Memory 三層記憶

目標：讓 Agent 有跨對話的狀態。涉及模組：memory。任務類別：MemoryService 門面（facade）、LongTermMemoryStore 的四個方法（並為將來的語意檢索升級預留位置）、MemoryTools（以 @Tool 形式暴露給 Agent）、把 Memory 接進 PromptBuilder、MEMORY.md 檔案管理。

US-3 和 US-4 彼此獨立，所以順序可以換。但要注意一個風險：把 Memory 接進 PromptBuilder 時，不能弄壞已經能跑的 ReAct 迴圈——這是典型的「新功能回歸破壞舊功能」。

Demo 2：跨對話的偏好回憶。你上次告訴 Agent 的偏好，下一次對話它還記得。

US-4：Plugin Tool 體系

目標：做出業務擴展的三級制——零碼（SKILL.md 加 MCP）、輕碼（自寫 MCP server）、重碼（@Tool）。涉及模組：tool、core。任務類別：內建工具、MCP client（先做 stdio）、透過 ContextLoader 載入 SKILL.md、Profile 升級。

這裡的任務粒度要特別細。MCP 的 Java 生態成熟度比 Python 低，所以要把 stdio client 拆成連接、列工具、呼叫工具、錯誤恢復四個子任務，逐一驗證。SandboxChecker 的完整版也拆成三個子任務。

Demo 3：零碼 PR 摘要。不寫 Java，只靠 SKILL.md 就讓 Agent 多出一項能力。

US-5：Web Service

目標：把所有能力透過 REST 暴露出去。涉及模組：web、storage、cli、core。任務類別：Web 基礎、六個 ApiController（可並行）、十個端點、持久化升級（Session 進 SQLite 加審計表）、設定與上下文、完整 CLI、工程化（日誌）。

這是五個 user story 裡最密的一個。有一個很容易被 AI 省略的點：審計表的寫入屬於 US-5（對應憲法第六條「審計第一天就要寫」），AI 傾向於不做持久化。另外，六個 ApiController 因為彼此獨立，可以標記為可並行任務。

Demo 4 與 Demo 5：管理平台與完整的 REST 驗收。

任務粒度：一到兩個檔案

/speckit.tasks 產出的任務，粒度控制在一到兩個檔案：每個任務只碰一到兩個檔案，彼此獨立的標為可並行（parallelizable），並按依賴排序。這樣切有兩個好處：每個任務的範圍小到 AI 不會「湊合」，而且每個任務結束都產出能跑的程式碼——不是半成品。當後續 AI agent 一次只看見一個任務時，它跑偏的機率就大幅下降。

記住這個節點的第二個判斷：拆解單位是能獨立驗收的能力，不是能塞滿的時段。
