增量階段：換輕工具，但別丟掉契約

Step 5/5 · OryxOS AI 編程指南

學習目標

能跑一遍 issue → fork → Claude Code → PR 的增量工作流，並說清增量產物怎麼跟主體階段的 artifact 對齊。

為什麼主體做完要換工具

主體階段結束，OryxOS 1.0 的核心能力已經跑起來。接下來的工作性質變了：補一個擴展、修一個 bug、寫一個小工具，通常只碰一到三個檔案，而且沒有一件需要跨模組協作。更關鍵的是，上下文不再是「待發想的規格」，而是「既有的程式碼」。

在這種情況下，Spec-Kit 的完整流程（specify → plan → tasks → implement）就是過度工程。所以增量階段把手動提示詞加 Claude Code 拿回來：直接在 agent 裡描述要改什麼、改完、測試、送 PR，不產出正式的 spec 與 plan 文件。

增量開發的標準工作流

這條流程和開源社群貢獻的流程幾乎一樣：

  1. 認領一個 issue。issue 通常分三類：good-first-issue（新手入門）、feature-request（功能需求）、long-term-goal（長期目標）。
  2. fork 加 clone 專案，把 repo 拉到本機。
  3. 用 Claude Code 打開專案，描述要改什麼。因為上下文是既有程式碼，agent 可以直接讀、直接改。
  4. 修改與測試。改完跑測試，確認沒有回歸。
  5. 送 PR，進入 review 與 merge。

注意：Spec-Kit 在增量階段不是強制的。只有當某個增量其實是個大 feature 時，才可以選擇性地回到 specify → plan → tasks 的重流程。

切換工具，但不切斷契約

這是本節最重要的一點。雖然工具換了，主體階段留下的三份 artifact 仍然是約束：

Artifact在增量階段的角色
constitution.md仍然不可協商，任何改動都不能違反它
spec.md能力的契約，社群改動必須守住核心能力的驗收標準
plan.md大致凍結，只在必要時局部調整

換句話說：手動提示詞只是換了「怎麼做」，沒有換「不能違反什麼」。一個小 PR 如果踩到憲法（例如引入了被禁止的框架抽象），一樣要被擋下。大 feature 如果超出原本 spec 的能力範圍，可以重跑一次 specify → plan → tasks；但小 feature 就老老實實走「手動提示詞加 PR」。

社群的產物怎麼併進來

OryxOS 的目標之一是讓社群一起推進，所以增量階段的工作流本質上就是社群貢獻流程。社群提交的 PR 要尊重主體階段定下的核心能力驗收標準——這也是為什麼主體階段的 constitution 與 spec 不能刪：它們是後來所有人的共同基準。專案交付時留下的社群文件（API 參考、部署手冊、CONTRIBUTING）也是靠這樣的 PR 累積出來的。

回顧這個節點：先用重工具把範式練熟、把契約釘死（Spec-Kit），再用輕工具快速演進、但不違約（手動提示詞加 PR）。這才是「兩階段混合」完整的意思。
