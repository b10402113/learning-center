兩階段混合模式：工具要配得上工作的性質

Step 1/5 · OryxOS AI 編程指南

學習目標

能判斷什麼工作用 Spec-Kit、什麼工作用手動提示詞，並說出兩階段混合模式為什麼是 OryxOS 的正解。

為什麼不是「一套工具打天下」

OryxOS 的需求文件與技術方案都已經寫完，接下來的問題是：怎麼把這些文件變成一個真能編譯、能跑的系統？答案不是「找一個最強的工具從頭用到尾」，而是按工作的性質換工具。

專案的性質不是恆定的。第一階段是從零蓋一個底座，跨九個 Maven 模組、每個決定都會牽動其他模組；第二階段是在已有程式碼上補功能、修 bug，通常只動一到三個檔案。前者需要一套能約束全局、留下完整決策紀錄的重流程；後者如果也套同一套流程，光是寫 spec 和 plan 的開銷就超過改動本身。

這就是 OryxOS 的兩階段混合模式：主體開發用 Spec-Kit，增量開發改用手動提示詞加 Claude Code。核心原則只有一句——工具選擇匹配工作性質。

主體階段：為什麼 Spec-Kit 是 OryxOS 的甜蜜區

Spec-Kit 的適用條件很明確，而且必須同時滿足：中大型的 greenfield（從零開始）專案、需求清楚、由 AI agent 主導開發、團隊有學方法論的目標。只要有一項不成立，它的重流程就會變成負擔。

拿 OryxOS 逐條對：

匹配條件OryxOS 的實際狀況
中大型 greenfield純從零開始，九個 Maven 模組的規模，不是玩具專案
需求清楚需求文件與技術方案都已定稿，Spec-Kit 的任務是「轉換」，不是「重新發想」
AI agent 主導開發以 Claude Code 為主要開發者
方法論場景本身就是要示範 SDD 怎麼落地

四項全中，所以 Spec-Kit 是 OryxOS 主體開發的最佳解。那些「brownfield 改造不適用」的爭議，在這個專案上根本用不到。

增量階段：什麼時候該把手動提示詞拿回來

主體蓋完五個核心能力之後，剩下的工作大多是一到三個檔案的小改動：加一個擴展、修一個 bug、寫一個小工具。這類工作有三個特徵：

  • 改動範圍小，不會跨模組協作；
  • 上下文是既有的程式碼，不是一份待寫的新 spec；
  • 驗證方式很直接——改完、跑測試、發 PR。

對這種工作，Spec-Kit 的完整流程（specify → plan → tasks → implement）是殺雞用牛刀。所以增量階段切回手動提示詞模式：直接在 Claude Code 裡描述要改什麼，改完測試，然後送 PR，不產出正式的 spec 與 plan 文件。主體階段留下的 constitution 與 spec 則退居為參考基準，而不是每次改動都要重跑一遍的流程。

認清 Spec-Kit 的局限，才不會期待錯

選 Spec-Kit 不等於它沒有代價。它有四個已知局限，每一個都有對應的處理方式：

局限應對
對小增量而言太重分階段：主體用 Spec-Kit，增量改手動提示詞
spec 不會自動同步在 tasks 之後、implement 之前跑 /speckit.analyze 檢查漂移
context 上限讓大型 brownfield 失敗OryxOS 是 greenfield，此局限不適用
Spec-Kit 自身迭代很快不要鎖死版本細節，跟著官方文件走

另一份教學把它放進更大的工具版圖裡：Spec-Kit 是 GitHub 開源的規格驅動開發工具鏈，2026 年成長最快的開發工具之一，支援二十多種 AI agent；但它是一把「重武器」，適合需求清楚的中大型 greenfield，不適合小型改動、快速原型、單檔修改、大型 brownfield 與探索性研究。這正好解釋了為什麼 OryxOS 需要兩階段，而不是一套工具用到底。

一句話記住這個節點的第一個判斷：工作性質決定工具，不是工具決定工作性質。
