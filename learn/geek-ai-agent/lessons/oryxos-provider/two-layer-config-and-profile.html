兩層配置與 Profile 系統

Step 3/5 · Provider 抽象

學習目標

能解釋 Provider 的「兩層配置」：應用層宣告 provider 與憑證、Profile 層宣告用哪個模型與溫度，並闡述 ProfileLoader／ProfileRegistry 如何載入、驗證與索引 Profile，以及「引用不存在的 Provider 必須硬失敗」的理由。

為什麼要兩層，而不是一張配置表

把「這個系統有哪幾家模型供應商」和「這一個 Agent 用哪個模型」混在一張表裡，會發生什麼？答：每次新增一個 Agent，都要去動那份「供應商清單」，接著很容易不小心改到別人正在用的模型，或把憑證攤給所有人。兩件事的變動頻率與影響範圍完全不同，所以拆成兩層：

層宣告什麼範例
應用層（application.yaml）有哪些 provider、各自的 API key 與 base URLdeepseek、kimi、qwen 各一條
Profile 層（Profile YAML）這一個 Agent 用哪個模型、什麼溫度「本 Agent → deepseek／deepseek-chat／0.7」

應用層回答「系統認識誰」，Profile 層回答「這個 Agent 用誰」。Profile 用 provider name 引用應用層的供應商，兩層透過 name 連起來。

應用層：provider 清單與憑證

應用層以 oryxos.providers 宣告 provider 清單。每個 provider 有三個欄位：name、apiKey、baseUrl。第二個原則是憑證不走明文——Profile 或 provider 設定裡用 ${ENV_VAR} 佔位，真正值從環境變數讀取：

providers:
  - name: deepseek
    apiKey: ${DEEPSEEK_API_KEY}
    baseUrl: https://api.deepseek.com

這層要負責啟動驗證：name 非空且不重複、api-key 已解析非空、base-url 非空。缺哪個就點名報錯，不靜默失敗——「驗證失敗必須大聲說」是安全管理原則延伸出的硬要求。

另外，OryxOS 內建一個名為 mock 的保留 provider：它不連真實端點，專門給你「沒有 API key 也能全鏈路自測」用。

Profile 層：一個 Agent 一份設定

Profile 是一個 Agent 的完整設定投影，用 YAML 寫在 .oryxos/profiles/*.yaml（或由 Agent 目錄的 AGENT.md frontmatter 派生）。它記錄這個 Agent 的長相：名字、描述、身份、人格、以及最重要的——provider ref：

name: ops-agent
description: 運維助手
provider:
  name: deepseek          # 對應應用層的 provider name
  model: deepseek-chat
  temperature: 0.7
  api_key: ${DEEPSEEK_API_KEY}

Profile 層只回答「用哪個模型、多高的溫度」，它不重複辦理憑證——那是應用層的事。

載入、驗證、索引：Loader → Registry

Profile 從檔案變成可用物件，走三個角色：

  1. ProfileLoader：掃描 .oryxos/profiles/*.yaml，做 YAML 解析與 ${ENV} 解析。發現壞掉的 Profile（例如格式錯、cron 錯）→ 記錄錯誤日誌但不阻斷啟動。
  2. ProfileRegistry：啟動時把 Profile 建到一個記憶體索引，按 name 快速查詢。Channel 收到訊息時，從這裡拿對應的 Profile 繼續處理。
  3. 驗證掛勾：Validator 檢查 Profile 引用的東西是否真的存在——尤其是 provider 名。

「引用不存在的 Provider」為什麼要硬失敗

這裡有個對比要記住：Profile 本身格式壞掉 → 軟失敗（跳過它、記日誌、繼續啟動）；但 Profile 引用了不存在的 provider → 硬失敗。

為什麼態度差這麼多？因為前者是一個壞掉的 Agent 檔案，不影響別人；後者意味著「這個 Agent 被設定成用一個系統根本不認識的模型」——它一旦上線，每輪呼叫都是在用不存在的東西，而且往往要等到使用者真正問問題時才暴露。與其讓它靜默地一直壞，不如在啟動時就把問題點破，逼你立刻修正。

整條血拼起來

應用層定義「系統認識哪些模型供應商」。Profile 層定義「這個 Agent 用哪家、哪個型號、多少溫度」。ProfileLoader 把 Profile 從檔案載入並做格式／環境變數解析，ProfileRegistry 把它們建成按名查詢的索引，並在放入時驗證 provider 名確實存在——不存在的就硬失敗。之後 ReAct 迴圈每輪呼叫，就只要帶著 sessionId 與 Profile，遞給 ProviderService。
