一次呼叫與工具 schema 轉換

Step 4/5 · Provider 抽象

學習目標

能說出 ProviderService.chat 一次同步呼叫的完整路徑（Profile 路由 → 構建 Prompt → 關閉工具自動執行 → 呼叫 ChatModel → 回傳 text／toolCall／usage），並解釋 ToolSchemaAdapter 為何「只翻譯不執行」。

一趟呼叫從哪裡開始

上層（ReAct 迴圈）跟 ProviderService 說話時，只傳三個東西：sessionId（審計用）、Profile（決定用哪個模型）、ProviderRequest（這次要送的內容：system prompt、結構化對話、可用工具清單）。一次呼叫的旅程，大致是：

chat(sessionId, Profile, request):
  model   = 依 Profile 從顯式映射找 ChatModel
  prompt  = 構建 Prompt（關閉工具自動執行 + 工具 schema + 消息）
  resp    = model.call(prompt)          ← 真正的網路呼叫
  return  (text, toolCalls, usage)      ← 原樣轉回給迴圈

第一步：Profile 路由到模型

「選模」這一步在 code 裡靠按 name 的顯式查詢完成：把 Provider name 送進去，從映射表取出對應的 ChatModel。這裡有個值得注意的實作技巧：模型實例會依「apiKey|baseUrl」的組態指紋快取——同一指紋沿用舊實例，配置變了就原地重建替換。好處是：反覆改 key／url 不會累積一堆無法回收的舊模型實例，符合「動態 provider」的胃口。

第二步：構建 Prompt 的關鍵——關閉自動執行

構建 Prompt 時，OpenAiChatOptions 裡必須設定 internalToolExecutionEnabled = false。這一步就是陷阱二的落點：Spring AI 預設會自動執行工具，你要在這裡明確關掉，讓「執行權只在 ToolExecutor」這件事落實到每次呼叫的請求裡。選模、構建、呼叫、回傳——每一環都不碰工具執行。

構建的另一方面是保留結構化消息：system prompt 之外，逐條轉換對話消息，並保留 assistant tool_calls 與 tool 結果的 tool_call_id 配對。為什麼重要？多步 ReAct 裡，模型必須能從消息看出「某工具已經被呼叫過、結果是 X」，否則它會反覆重呼叫同一個工具。

第三步：ToolSchemaAdapter——只翻譯、不執行

送進請求的工具，必須先從 OryxOS 內部的 OryxTool 長相翻成 Spring AI 認得的工具描述。這份翻譯由 ToolSchemaAdapter 負責：它讀 OryxTool 的三要素——name、description、inputSchema——產出對應的 ToolDefinition。

關鍵在它的名字：SchemaOnly。這個 adapter 產出的 callback只攜帶 schema 描述，不攜帶任何可執行邏輯。萬一有人誤觸它的 call()，它直接丟例外："Provider 只翻譯工具、不執行工具"。這是一個「雙保險」：正常流程靠 internalToolExecutionEnabled=false 擋住；就算框架失靈想執行，這個的 call() 也會爆炸給你聽，提醒你執行權放錯地方了。

第四步：呼叫與回傳

一切就緒後呼叫 model.call(prompt)。回傳的 ChatResponse 被轉成 OryxOS 自己的 ProviderResponse：text（純文字回答）、toolCalls（模型想要呼叫的工具請求，帶 id／name／引數）、usage（這次的 token 用量）。

如果 toolCalls 非空，Provider 只是把它原樣交回給迴圈。迴圈看到後，才讓 ToolExecutor 真正執行。Provider 的職責在呼叫返回那一刻就結束了。

流式呢？（一個優雅的回退）

ProviderService 還提供 chatStream。它的介面設計很克制：chatStream 有一個預設實作——非同步呼叫 chat，收到完整回應後把全文一次性交給 onToken 回呼。若某個實作真的支援流式，就覆寫這個方法做逐段回呼。也就是說，「流式」是可選的升級，而不是必須的平行世界。而且為了不拖垮合法呼叫，流式取得失敗且結果殘缺時，實作必須上拋錯誤，絕不能把殘缺內容當完整回傳。
