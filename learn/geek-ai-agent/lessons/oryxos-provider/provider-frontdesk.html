什麼是 Provider

Step 1/5 · Provider 抽象

學習目標

能說出 Provider 在整個 Agent 架構中的位置（前台）、它承擔的四件事與絕不承擔的一件事，並解釋為什麼換模型可以只改配置。

先看一個場景：換模型為什麼讓你頭大

假設你寫好了 ReAct 迴圈，呼叫的是 DeepSeek。突然決定切到 Kimi，或兩家都上線做對比。最直接的改法，是到迴圈裡把所有請求格式、端點、參數通通改一遍——然後很快發現每家廠商的 API 格式長得完全不一樣：bename、message 結構、tool call 的形狀各有各的脾氣。你的 Agent 邏輯還沒長大，就先被這種「協議差異」淹沒了。

Provider 要解決的正是這個。它的位置，在 Agent 與 LLM 之間——像一間公司大樓的前台：樓上的人（ReAct 迴圈）不用知道裡面每個部門怎麼運作，把需求遞給前台，前台替你找到對的人、把需求翻譯過去、再把結果帶回來。

Provider 是什麼：一句話定義

Provider 是 Agent 與 LLM 之間的抽象層（前台）。上層只傳兩個東西：一個 Profile（設定檔，告訴它要用哪個模型）和一段 Prompt（提示詞）。Provider 負責選出對應的模型、完成一次呼叫，然後把原始回應原樣交回來。上層完全不接觸「OpenAI 的 JSON 長怎樣、Anthropic 的格式長怎樣」這些細節。

Provider 是一個工程接縫：把「LLM 這個大腦」從 Agent 的五元件（LLM + Tools + Memory + Loop + Environment）裡隔離出來，底下換誰，上面不用動。

四件事做，一件事絕不做

Provider 的職責被刻意收窄成四件事：

職責它做什麼一句話記憶
選模依 Profile 選擇對應的模型看名單找人
呼叫完成一次 LLM 呼叫並取回原始回應打完電話回報
轉換把工具 schema 翻譯成各家模型的格式把需求翻成對方聽得懂的話
審計記錄這次呼叫（成敗、token、模型）每次通話留底

而它絕不執行工具。當模型說「我想呼叫 http_get 這個工具」時，這只是 Function Calling 回傳的一個「想呼叫 X」的請求。Provider 把它原樣交回給迴圈，由 ToolExecutor 決定要不要真正執行。這個分工是憲法層級的原則：執行權只在一處，否則工具會被執行兩次。

為什麼換模型可以是純配置

因為四個職責裡，「選模」是唯一的入口。Profile 用 provider name（一個字串，例如 deepseek）來指名要用哪個模型，而不是直接寫死某個類別或 Bean。Provider 內部維護這張 name → 模型的對照表。於是你把 Profile 裡的 name 從 deepseek 改成 kimi，換模型就完成了——上層的迴圈、記憶、工具一行都不用改。

介面長什麼樣（先看契約，不看實作）

在 OryxOS 裡，契約是一支叫 ProviderService 的介面，放在 core：

ProviderResponse chat(String sessionId, Profile profile, ProviderRequest request);

輸入包括 session id（給審計用）、Profile（決定選哪個模型）、以及一次呼叫的請求（系統提示＋對話＋可用工具）。回傳的 ProviderResponse 只有三樣：文字回覆 text、工具呼叫請求 toolCalls、token 用量 usage。這個契約刻意不使用任何 Spring AI 的型別——core 不依賴框架，具體協議轉換由 provider 實作模組完成。依賴是倒過來的：介面在 core，實作在底部。

把職責邊界記成一句話

遇到任何跟 Provider 有關的設計問題，先問：這是「選模、呼叫、轉換、審計」裡的一件事嗎？如果是「執行工具」「決定迴圈順序」「累積上下文」——那不屬於 Provider，往別處找。
