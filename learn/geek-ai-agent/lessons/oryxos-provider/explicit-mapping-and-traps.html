動手前先想清楚

Step 2/5 · Provider 抽象

學習目標

能逐一說出設計 Provider 前必須釘死的三個陷阱（型別無法區分多 Provider、Spring AI 自動執行工具、未驗證 starter 依賴），並解釋「顯式 name→ChatModel 映射、不靠型別掃描」為什麼是首要原則。

為什麼「先動手」反而最慢

Provider 看起來很直觀：寫個類別呼叫模型而已。但實務上，幾乎所有嚴重的 bug 都是在一開始沒想清楚邊界造成的——而且往往要到整合時才爆。設計 Provider 之前，有三個陷阱值得先釘死。它們有一個共同特徵：都是「框架給了你預設行為，而這個預設行為剛好不是你要的」。

陷阱一：型別無法區分多個 Provider

假設你同時接 DeepSeek、Kimi、Qwen。用的是 Spring AI，各家都會註冊成 ChatModel Bean。問題是：它們的型別一模一樣——容器裡放著好幾個 ChatModel，但你光靠「掃描容器裡所有 ChatModel」來找，根本不知道哪個是 DeepSeek、哪個是 Kimi，因為 Bean 名未必等於 provider name。

解法不是猜，而是維護一份顯式的 provider name → ChatModel 對照表：

Map<String, ChatModel> providerMap = Map.of(
    "deepseek", deepseekChatModel,
    "qwen",     qwenChatModel,
    "kimi",     kimiChatModel
);

這條原則在 OryxOS 的技術方案裡被寫死：「顯式映射、不靠型別掃描，否則多 Provider 跑不起來」。Profile 透過 provider name 引用，啟動時按 name 建表，多 Provider 並存才有確定性。

陷阱二：Spring AI 會自動執行工具

這是整個 OryxOS 最常踩、也最容易出事的陷阱。Spring AI 的 ChatClient.prompt().call() 這條捷徑，內建了「偵測 tool call → 自動幫你執行工具」的行為。如果你用了它，模型想呼叫 shell 或 http_post，框架就自己先跑了一次——然後你的 ReActLoop／ToolExecutor 又跑第二次。工具被執行兩次，後果可能是重複發 HTTP、重複送訊息、甚至重複扣錢。

OryxOS 的解法是：明確關閉 Spring AI 的 tool 自動執行（internalToolExecutionEnabled=false），只用它做兩件事——LLM 協議轉換、與 @Tool 的 JSON Schema 生成。工具被回傳成「想呼叫 X」的請求後，執行權完全交給 ToolExecutor。這同時守住前面說的「工具執行權只在一處」。

陷阱三：範例用的 provider 名，先去驗證依賴

課堂或範例裡看到 deepseek、kimi、qwen 這些名字，很容易直接寫進配置。但「名字存在」不等於「你的 Spring AI BOM 鎖定了對應的 starter 依賴」。如果沒鎖，啟動時可能根本建不出對應的模型。

動手前先跑 mvn dependency:tree，確認你要的 provider starter 在鎖定的 BOM 裡解析得出來。這是一個「開發前先驗證」的習慣：先證明依賴存在、能被聯絡，再寫呼叫程式碼——避免做出一個無法連結、或連結到錯誤物件的地方。

三個陷阱 → 三條測試

把每一個陷阱釘成回歸測試，是這個節奏最漂亮的地方：

陷阱它該被什麼測試釘住
型別無法區分 Provider兩個 Provider 之間不得互相竄線（各走各的模型）
自動執行工具捕捉到的請求裡，自動執行必須是關閉的
未驗證依賴（手動）BOM 能解析、integration 冒煙測試有真實呼叫

往後在講驗收的那一步，會看到這三條如何變成真正可跑的測試。
