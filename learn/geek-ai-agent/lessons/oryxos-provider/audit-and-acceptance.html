llm_calls 審計與驗收 Harness

Step 5/5 · Provider 抽象

學習目標

能解釋 llm_calls 為何成功與失敗都要落庫（day-one 審計、兩欄位設計、手寫 schema 而非 ddl-auto），並說出頂尖三條測試的由來與 mock／integration 測試的切分。

審計：為什麼「只記成功」是災難

假設你要調查為什麼某個 Agent 昨天半夜連續失敗。如果你只記錄成功的呼叫，資料表裡就空空如也——一次真實事故完全沒留下痕跡。可審計是 OryxOS 的核心差異點（企業願意換底座，往往就是為了「每一筆呼叫都能追」），而這必須從第一天就做到。

所以 Provider 的規矩是：成功和失敗都要寫進 llm_calls 表。失敗時照樣落一筆，標記 success=false 並記下錯誤訊息；然後才把錯誤往上拋。

llm_calls 表：需要哪兩欄就設計哪兩欄

因為失敗也要落庫，llm_calls 表就不能只有「成功」那一欄。它需要兩個字段：

字段意義
success（布林）這次呼叫成不成功
error_message（文本，可空）失敗時記下錯誤訊息

再加上 provider、model、token 用量（prompt／completion）、門檻毫秒數與時間戳，就構成一筆完整的呼叫留痕。抓住「失敗也要寫」這個需求，設計上自然不會漏掉欄位。

手寫 schema，不要 ddl-auto=update

一個容易被忽略、但很痛的表結構陷阱：OryxOS 的schema是手寫遷移腳本（SQLite 底下由手寫 schema 腳本管理），而不是依賴 JPA 的 ddl-auto=update。為什麼？因為 SQLite 的 ALTER TABLE 能力很弱，依賴框架自動改表結構在實務上不可靠。表是契約，契約要用明確的遷移腳本版本控管，而不是交給框架偷偷改。

驗收：mock 即可，別每次都打真實模型

Provider 的測試必須能又快又穩定地跑，不能每次跑測試都消耗真實 token。所以切分原則是：

  • 單元測試：用一個 mock 的 ChatModel 去測試路由、驗證、審計、翻譯這些邏輯——快、不依賴網路、可以天天跑。
  • integration 冒煙測試：真打一次模型，驗證「真的能連通」。用 @Tag("integration") 標起來，CI 預設跳過，由你在有 key 時手動跑。

這樣把「邏輯對不對」和「真的連不連得上」分成兩層驗證。

頂尖三條測試（把每個陷阱釘死）

設計時抓住的每一個陷阱，都值得一條回歸測試。其中最有價值的三條：

測試它釘住什麼
兩個 Provider 不互相竄線顯式映射真的有效，各走各的模型
失敗仍寫 success=false 審計失敗路徑也會落庫，不是只記成功
捕捉的請求確認自動執行是關的internalToolExecutionEnabled=false 真的生效

這三條正好對上前一步的三個陷阱：映射陷阱、審計缺口、自動執行陷阱。你把設計時怕的事變成測試，測試就變成會替你守門的警衛。

做完怎麼驗：手動檢查清單

光有自動測試還不夠，發布前走一遍手動清單：

  1. starter 依賴確認：要用的 provider starter 在鎖定 BOM 中可解析。
  2. 冒煙測試跑過：用真實 API key 跑一次 integration 冒煙測試，真的拿到回應。
  3. 無明文金鑰：grep -r "sk-" 在你的 codebase 裡找不到任何金鑰殘留。

另外要記住 Provider 的完成定義：它沒有自己獨立的入口，驗證方式是「支援 Demo 的 LLM 呼叫，並驗證與 ReAct 一起跑通」。一次穩定成功的呼叫就是完成線——fallback、hedging、circuit breaker 這些更強的重力方案，通通留到擴展階段。
