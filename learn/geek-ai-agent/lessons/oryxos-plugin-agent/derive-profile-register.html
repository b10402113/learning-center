掃描→deriveProfile→註冊→自跑：底座零改動的插件機制

Step 3/5 · 插件化 Agent 與動態管理

學習目標

能說出「掃描→deriveProfile→註冊→自跑」四個步驟各自做什麼，並解釋為什麼這條路徑讓底座一行都不用改。

問題：目錄憑什麼被系統認得？

上一課我們已經能寫出一個自足的 Agent 目錄。但目錄本身只是檔案——系統要怎麼「發現」它、把它變成一份可執行的設定、並且讓它到點自己跑起來？

這裡有一個很容易走偏的誘惑：既然每種 Agent 需求不同，乾脆改一改 AgentService、改一改排程器，讓它們直接去讀 AGENT.md。這條路一旦走上去，每加一種 Agent 就要動一次底座，底座很快會變成一團泥巴。

OryxOS 選了另一條路，一條原則講完：不改寫底座，只加一個 Profile 的來源。

為什麼只加一個來源就夠？

因為底座從第二十八節走到現在，一直只認一個值物件：Profile。`AgentService`、`ReActLoop`、`PromptBuilder`、`AgentScheduler` 全都消費 Profile——它們不關心這份 Profile 是怎麼來的，只關心它裡面有什麼。

所以插件化的核心，只是把一句話換掉：

原本：從 Profile YAML 讀出一份 Profile。
現在：從 Agent 目錄的 AGENT.md frontmatter 推導出一份 Profile。

換句話說，「推導 Profile」就是整個插件化機制。改變的只有 Profile 的產生方式，後面的註冊、驗證、執行、排程，全部沿用。

四個步驟：掃描 → 推導 → 註冊 → 自跑

把上面的原則拆成具體鏈路，就是四步：

步驟做什麼主要角色
1. 掃描啟動時掃 .oryxos/agents/ 底下的每個目錄組裝層
2. 解析把 AGENT.md 的 frontmatter（設定）與 body（指令）切開，並記下 scripts/、skills/、REFERENCE.md 的路徑AgentLoader／AgentMarkdown.split
3. 推導deriveProfile(agentDir) 把 frontmatter 映射成 Profile：name／provider／tools／notify_channels／schedulesAgentLoader.deriveProfile
4. 註冊把 Profile 放進 ProfileRegistry；排程交給 AgentScheduler.registerProfileProfileRegistry／AgentScheduler

註冊時的驗證沿用既有的規則（第 16 節那一套）：provider 必須存在、tool 必須是已註冊的能力。缺了 AGENT.md 的必填欄位，錯誤會直接點名是哪個欄位；引用了不存在的工具則會警告。

第四步之後，這件事就結束了。之後任何觸發——不管是排程到點還是 API 呼叫——都走同一條 AgentService.process，ReAct、Tool、Provider 一行都沒動。

觸發 → AgentService.process(Profile, ...) → ReActLoop → ToolExecutor → Provider
                                                  ▲
                                   這整段完全不知道 Agent 從哪來

排程從 Agent 身上長出來，所以排程器不用改

排程這一塊值得單獨提一句。因為 schedules 是從 Agent frontmatter 推導進 Profile 的，AgentScheduler 只需要照著 Profile.schedules 去排，它自己的程式碼改變行數是零。這就是「Profile 取用」的威力：新能力接進來的成本，取決於舊模組是否已經在消費那個抽象。

為了下一課，先鋪好兩個可變的掛鉤

到這裡，「一個目錄推導出一個會自跑的 Agent」已經機制完整。但入口仍然是「登入伺服器、把檔案放上去、重啟才生效」。為了下一課的動態管理，這一課先做兩件小小的改造：

  • ProfileRegistry 從不可變改成可變的並行 Map——提供 register(Profile)／remove(String)／exists(String)。這樣「啟動掃描」和「執行時新增」走的是同一份程式碼、同一套驗證。
  • AgentScheduler 抽出 registerProfile，並加一張 Map<String, ScheduledFuture<?>> 的 handle 表——把每個排程的「取消把手」存起來，下一課要註銷或更新排程時才有東西可操作。

另外，ContextLoader 負責把 Agent body 注入系統提示。它不做快取，所以 Agent body 一改，下次觸發立即生效——這條「改指令立即生效」的行為在第 17 節的 ContextLoaderTest 已經用 no-cache 回歸測試釘死，本課不必重測。

這一課的驗收，釘的是機制

因為機制是「掃描 → 推導 Profile → 註冊 → 自跑」，驗收測試就一段一段打：AgentLoaderTest 驗 frontmatter／body 切分與資源辨識；DeriveProfileTest 驗欄位正確映射、schedules 有帶過去；AgentScanRegisterTest 驗掃 N 個目錄就有 N 個進 ProfileRegistry；ProfileRegistryRuntimeTest 驗執行時註冊立刻可見；AgentSchedulerRegisterTest 驗 handle 存在；ProgressiveDisclosureTest 驗 body 進系統提示、參考與腳本不預載。

其中最重要的一條判斷標準是：由目錄推導出來的 Agent，和手寫 Profile 的 Agent，必須走同一套驗證與同一條底座。 只要這一點成立，「定義一個 Agent 不必寫 Java」才是真的。
