一目錄一 Agent：為什麼這叫 Agent OS

Step 1/5 · 插件化 Agent 與動態管理

學習目標

能說清「一目錄一 Agent」為什麼是 Agent OS 的分界線，以及它借了 Skill 目錄形態、卻定義 Agent 的關鍵差別。

先看一個尷尬的處境

走到第二十八節，OryxOS 的核心已經很完整：Provider 能選模、ReAct 能自己想與做、Tool 體系能呼叫外部能力、Memory 能記住、Sandbox 能擋、排程能到點觸發、Web 能對外開介面。這是一顆像樣的 kernel。

但這時候你要跑一個業務 Agent——比如「每天早上九點對賬並推送到運維群」——還是得把它的指令硬寫進一份設定、手工把模組組起來。也就是說，核心能跑「一個」Agent，卻沒有一套標準方式去「定義、安裝、執行任意多個」Agent。系統離「是 Agent OS」還差最後一塊拼圖。

作業系統的定義不在核心，而在機制

一條判斷準則：能跑一個程式的東西不叫作業系統；作業系統是「你可以在上面安裝並執行任意多個程式，彼此隔離，且不必修改或重新編譯核心」。

Windows 之所以是作業系統，不是因為它的核心多強，而是因為它同時提供了三件事：一個標準的可執行檔格式（exe）、一個載入器（loader）把檔案變成執行中的程式、一個排程器決定誰在什麼時候跑。有了這套機制，開發者不必碰核心，就能發佈無數個程式。

OryxOS 缺的正好是這套「定義 → 載入 → 排程」的機制。第二十九節把它補上，這也是整門專案裡「敢叫 Agent OS」的關鍵一課。

兩層架構：底座是核心，Agent 是可執行程式

補上這塊拼圖後，整個系統切成一條清楚的邊界：

層作業系統類比內容
底座（base）核心 / 共用系統能力Provider、ReAct、內建 Tool（read_file／shell／http_get／notify／save_memory…）、Memory、Sandbox、排程、Web
Agent 層一支可執行程式 / 套件一個 .oryxos/agents/<name>/ 目錄，自足地帶身分設定、任務指令、腳本、參考檔案

底座是所有 Agent 共用的系統能力；Agent 是一個自足的目錄。這條「底座 vs Agent」的切分，就是整個架構的中心邊界。

它有一個可驗證的終態：丟進一個 Agent 目錄 → 它出現在 Agent 清單 → 到它聲明的時間自己跑起來（思考 → 呼叫系統能力 → 回答 → 推送），全程留審計 → 你改它的指令，下次觸發立即生效 → 而且這一切不需要寫一行 Java，也不需要碰底座。

借了 Skill 的形態，但定義的是 Agent

這套目錄模型借了 Anthropic Agent Skills 的形態——一個目錄，裡面有主指令檔加腳本加參考資料——但沒有借它的命名。差別很關鍵：

  • 一目錄 = 一 Agent。 在 OryxOS 裡，這樣一個目錄定義的是一個「會自己跑的業務程式」，而不是「附掛在別人身上的某個能力」。
  • skill 降級成內部元件。 「skill」在這個模型裡只是該 Agent 目錄內一個選用的子指令 .md，不是頂層單位。早期教材曾在「一個 Skill = 一個 Agent」與「Skill = 可重用能力」之間搖擺，這個版本把它釘死。
  • 沒有跨 Agent 的能力庫。 OryxOS 不做全局索引、不做 use_skill、不做跨 Agent 能力重用。每個 Agent 獨立自足，只呼叫底座提供的系統能力。

那它到底向 Anthropic 學了什麼？學的是 progressive disclosure（漸進式揭露）：Agent 目錄裡的東西按階段、按需要才進上下文，而不是一次全塞進 prompt。這正是下一課要拆的目錄結構重點。

為什麼這條邊界值錢

把「N 個業務 Agent」與「一座底座」解耦之後，新增一個 Agent 的成本降到「丟一個目錄」；多個 Agent 之間互相隔離、互不干擾；底座保持穩定，不必為了新業務改動核心。這就是從「一個能跑 Agent 的框架」變成「一個能跑 N 個 Agent 的 OS」的意義。

不過「丟一個目錄」只是終態的門面。目錄裡到底裝什麼、憑什麼被底座認得、又憑什麼會自己跑起來，是接下來三課的主線。
