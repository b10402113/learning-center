一句話生成與腳本信任邊界

Step 5/5 · 插件化 Agent 與動態管理

學習目標

能說出「一句話生成」為何必須人審、最終落地為何改成模板骨架，以及安裝帶腳本的 Agent 等於信任作者的信任邊界。

問題：運維不會寫 AGENT.md

動態管理讓「丟一個目錄」變得可行，但還有一個現實門檻：運維人員不會寫 AGENT.md。他們的訴求是一句話——「每天早上九點查北京天氣，把穿搭建議發到團隊群」。所以還需要一條「一句話生成一個 Agent」的路。

它的本質是一次 LLM 呼叫：把使用者那句話，加上「OryxOS 的 AGENT.md 格式規範」丟給模型，讓它產出一份合規的 AGENT.md——完整的 frontmatter 加清楚的 body。

關鍵：一句話不能直達上線

危險就在「直達」兩個字。正確設計是兩步、有人在迴路中（human in the loop）：

  1. POST /api/v1/agents/generate 收下那句話 → LLM 產生 AGENT.md 草稿 → 原樣回傳給前端預覽，不落地、不註冊。
  2. 使用者看過、可以改（尤其是 schedules 裡的 cron 與 tools 權限）→ 再呼叫 POST /api/v1/agents 正式建立。

這一步不能省，理由很具體：模型可能把 cron 的時間讀錯，或是一個不小心開放過多工具權限。人必須掃一眼。而且生成本身也是一次 LLM 呼叫，要進 llm_calls 審計——這是憲章要求（每次呼叫都留痕）。

最終落地：設計演進與模板骨架

上面那個「generate 端點回草稿」是最初的設計，值得保留當作設計演進的紀錄；但最終實作改了方向：

  • POST /agents/generate 被取消。建立改成 POST /agents {name, description}，由後端從模板腳手架（scaffold）出一個完整目錄（AGENT.md + scripts/ + skills/ + REFERENCE.md）。
  • 「用 LLM 生成」下沉為對既有 Agent 的按需重生成：端點 POST /api/v1/agents/{name}/generate-files {description} 一次 LLM 呼叫產生 {相對路徑 → 內容} 供預覽，再以 POST /api/v1/agents/{name}/files {files} 寫入（先驗 AGENT.md 可解析，再覆寫並重新註冊）。
  • 生成用 ProviderService.chat(genSessionId, ProviderRequest.of(prompt)).text()（沒有 complete，只有 chat），並新增設定鍵 oryxos.author.provider / oryxos.author.model；沒有「預設模型」時，空的 model 回一個可讀的 503，而不是把 model=null 送給 OpenAI 相容端點。

為什麼最後選「模板先行、LLM 其次」？因為模板腳手架出來的是一份立刻合法、可執行、可審計的骨架——建立一個 Agent 不需要賭模型輸出。LLM 更適合用在「針對某個已經存在的 Agent 迭代內容」，而不是從零建立。

最終落地還順帶補了四項能力：每個 Agent 自己的記憶（全域 MEMORY.md 改為 .oryxos/agents/<name>/MEMORY.md，靠 ToolExecutionContext 這個 ThreadLocal<String> agentName 讓工具知道自己在為哪個 Agent 執行）；每個 Agent 一個固定 session（channel="admin"、user="console"、profile= Agent 名，冪等地拿到一個常數 admin:console:<name>）；檔案可編輯（POST /api/v1/workspace/file，沿用目錄穿越防護）；以及生成／編輯 Agent 的兩個端點。其中編輯 AGENT.md 要走 AgentLifecycleService.update（寫入＋驗證＋重新註冊），因為 macOS 的 WatchService 不監看子目錄內的檔案變更。

誠實的信任邊界：腳本即任意程式碼

整課最需要誠實面對的地方，是腳本的沙箱邊界。一個 Agent 的腳本是透過底座的 shell／python 執行的，而白名單管的是「直譯器（python／bash）＋ 只允許這個 Agent 自己 scripts/ 目錄底下的腳本」。

但這裡有一條不能裝作看不見的界線：腳本就是任意程式碼。一旦你允許了 python scripts/foo.py，這支腳本自己就能讀寫檔案、發出網路請求——它繞過了 http_get 的域名白名單。因為那個白名單只管內建的 http_get，管不到子程序的網路行為。

結論：安裝一個帶腳本的 Agent，等於信任它的作者。 核心階段的沙箱只做到「直譯器 + 目錄」的白名單；要把第三方 Agent 關進受限容器、做網路隔離，是擴展階段的任務。

也因為這條邊界，有些事這一階段刻意不做：Agent 版本管理、Agent 市集與分享、跨 Agent 能力重用、L3 容器／網路隔離、名稱衝突政策。範圍停在「一個目錄推導出一個會自跑的 Agent」，加上執行時註冊與動態管理。

驗收：生成與信任的測試

生成路徑要驗的是「只生成、不落地」：GenerateTest 確認產出的草稿能被 AgentLoader 解析、確認它沒有被持久化也沒有被註冊；若 LLM 吐出的不是合法 AGENT.md，要回 400 並帶可讀原因。至於信任邊界，它不是靠單元測試能證明的性質——它是設計上必須明說的限制，並用白名單把可攻擊面收斂到「直譯器 + 本目錄腳本」。

走到這裡，插件化與動態管理這條線就完整了：目錄定義 Agent、deriveProfile 接上底座、watcher 與 API 共用註冊、生命週期編排保證一致、生成由人把關、腳本信任邊界誠實劃出。
