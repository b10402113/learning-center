動態管理：免重啟掃描、上傳即上線與生命週期編排

Step 4/5 · 插件化 Agent 與動態管理

學習目標

能設計「免重啟」的動態註冊：兩條錄入路徑共用同一個 register，並說出刪除／更新為何必須先處理排程 handle。

還差最後一哩：重啟這條尾巴

第三課結束時，一個目錄已經能推導出一個會自跑的 Agent。但入口仍然是「登入伺服器、把檔案放上去、重啟才生效」。這對業務系統來說等於不可達：管理台只能看，不能管；業務想上一個新 Agent，得找工程師上機器操作。

這一課要把「重啟」這條尾巴剪掉，做到三件可驗證的終態：

  1. 建立／上傳即上線——POST /api/v1/agents 回 200，免重啟，Agent 立刻出現在清單、到點自跑。
  2. 丟目錄即上線——用 scp／git／編輯器把一個目錄放進 .oryxos/agents/，幾秒內自動註冊可用，不必經過 API。
  3. 一句話生成——在管理台說「每天早上九點查北京天氣，把穿搭建議發到團隊群」，系統用 LLM 產出一份合法的 AGENT.md 供預覽、編輯、一鍵建立（這一條下一課細講）。

一個真相源，兩條錄入路徑

設計的第一個決定：真相源只有一個——.oryxos/agents/，一個子目錄一個 Agent。但有兩條路可以走進來：

  1. API 上傳：POST /api/v1/agents，本質是「驗證後把 Agent 目錄寫進 .oryxos/agents/<name>/」。
  2. 手動丟目錄：透過 scp、git pull 或編輯器放進去。

關鍵在於：目錄是即時被監看的，不是啟動時掃一次。新增一個 WorkspaceWatcher，開機時做一次全掃，之後用 JDK WatchService 盯著 .oryxos/agents/。它被設計成唯一的註冊入口：

目錄被新增/修改/刪除
        │
        ▼
WorkspaceWatcher → deriveProfile 驗證
        │
        ▼
ProfileRegistry.register/remove
AgentScheduler.registerProfile/unregister

因為只有一個入口，所以「API 上傳即上線」跟「丟目錄即上線」是同一件事——API 只是幫你把目錄寫好，再叫同一個 register(agentDir)；watcher 則是收到檔案事件時叫同一個 register(agentDir)。刪除也是對稱的。

為什麼這樣設計？ 動態管理的本質是「改目錄就等於改執行時」。如果 API 一條實作、watcher 又一條，兩邊遲早行為不一致。收斂到單一入口，就保證了兩條路造出來的 Agent 一模一樣。

另外，WorkspaceWatcher 是一個背景 daemon 執行緒（跟排程執行緒同性質）。它是基礎設施，不在請求鏈裡做非同步模型，所以不違反「同步加虛擬執行緒」的憲章原則。

端點與生命週期：只編排，不重複實作

端點本身不引入新能力：deriveProfile、register／unregister／validate 全部沿用第三課；唯一新增的是一個編排者 AgentLifecycleService，負責把步驟排好、失敗時回滾。端點表面：

端點作用
POST /api/v1/agents驗證 → 寫入目錄 → deriveProfile → 註冊 → 有排程就排
POST /api/v1/agents/generate一句話 → LLM 產生草稿，只回傳、不落地、不註冊
GET /api/v1/agents、GET /{name}查詢已定義的 Agent
PUT /api/v1/agents/{name}編輯 body／provider／notify；若排程變了，先註銷舊 handle 再註冊新的
DELETE /api/v1/agents/{name}註銷排程 → 移出索引 → 目錄封存到 .oryxos/archive/
POST /api/v1/agents/{name}/invoke第 26 節的無狀態呼叫，不變

判斷標準仍然是第三課那一條：API 建立的與手動丟進去的 Agent，行為必須一致；兩者都收斂在 register(agentDir)，沒有第二份實作。

刪除與更新：先把語義定死

刪除與更新是最容易藏 bug 的地方，所以語義要提前定死。

刪除的順序是固定的三步：

  1. 先註銷排程，用第三課存下的 handle。
  2. 再從 ProfileRegistry 移除。
  3. 最後把整個目錄移到 .oryxos/archive/。

刻意不做物理刪除，是因為它做過的事已經留在審計表裡，它的定義也應該可追溯。

更新：改 body 就是覆寫 AGENT.md；因為 ContextLoader 每次都重新讀，所以下次觸發立即生效。但如果排程也變了，必須先註銷舊 handle、再註冊新的——否則舊的 cron 會跟新的並存，等於同一個 Agent 觸發兩次。手動刪目錄也對稱：watcher 收到 delete 事件後註銷；API 刪除只是「刪目錄 + 封存」這個更整齊的版本。

順序反了會怎樣？ 如果先移除索引與目錄、最後才停排程，中間存在一個時間窗：cron 觸發時去查一份已經不存在的 Profile。這種時序 bug，手動驗收幾乎測不出來，但單元測試用 InOrder 很容易釘死。

建立流程與失敗回滾

AgentLifecycleService.create() 依序做四件事，全部複用第三課：

  1. 驗證——provider／tool 存在、名稱不衝突。
  2. 寫入 Agent 目錄。
  3. 呼叫與 WorkspaceWatcher 共用的 register(agentDir)。
  4. 若有排程，註冊排程。

任何一步失敗就回滾：刪掉剛寫入的目錄，絕不留一個半成品 Agent。錯誤碼沿用第 26 節的口徑：名稱已存在、欄位非法、引用不存在的 provider 都是 400（不同代碼）；查詢／更新／刪除不存在的 Agent 是 404；全部走同一套 ApiResponse 外殼，不新造狀態碼。

工作區瀏覽：必須防目錄穿越

動態管理順帶給了管理台一個工作區檔案瀏覽器，端點是 GET /api/v1/workspace/tree 與 GET /api/v1/workspace/file?path=...。這裡有一條強制防線：目錄穿越（directory traversal）防護。

做法是把傳入的 path 正規化，要求它必須落在 .oryxos/ 底下，否則回 400。最關鍵的回歸測試就是 file?path=../../etc/passwd 必須被擋成 400——少了這一步，瀏覽器就變成任意檔案讀取漏洞。

驗收：把編排與失敗路徑固化成測試

這一課的複雜度幾乎全在「編排順序」與「失敗回滾」，正好是單元測試的守備範圍：mock 掉 agentStore／profileRegistry／agentScheduler／agentLoader／providerService，用 InOrder 釘順序、用注入例外釘回滾。最有價值的兩條斷言是：

  1. 註冊失敗時，必須回滾已寫入的目錄，而且絕不進到排程註冊。
  2. 刪除時，必須先停排程再動索引與目錄。

另外 WorkspaceWatcherTest 要驗「手動丟目錄會觸發註冊、刪除會註銷、一個壞目錄不會拖垮 watcher」；WorkspaceApiControllerTest 要驗目錄穿越回 400。
