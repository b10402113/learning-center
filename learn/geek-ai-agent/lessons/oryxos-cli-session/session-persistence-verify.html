Session 持久化與驗收

Step 4/4 · CLI 與 Session

學習目標

能說明 session 歷史以 JSON 存進 SQLite 的 sessions 表、重啟後如何恢復，並能複述 SessionManagerTest 與 SessionRepositoryTest 各驗證了什麼。

對話要能活過重啟

Session 身份想清楚了，下一步是「它記在哪」。如果 Session 只在記憶體，關機就忘——你昨天問到一半的專案背景，今天開 chat 全沒了。OryxOS 核心階段把 Session 存進 SQLite。

一張表：sessions，一格 JSON

核心階段只有一張主表：sessions。Metadata（session id、Profile 等）拆成欄位，而整段對話歷史序列化成 JSON，塞進一格 messages_json。

欄位內容
idsession id（三元組拼出來的那格）
messages_json整段對話歷史，打成一份 JSON
其他 metadata關聯的 Profile、時間等

選擇「塞一個 JSON」而非「每則訊息一行」有兩個後果：實現極簡（讀一個欄位就拿到整段歷史），代價是每輪都整段覆寫（訊息的追加式更新在核心階段不細做，效能問題留給後面）。

手維護 schema，不要迷信自動更新

技術方案的選型提醒很實際：SQLite 的 ALTER TABLE 很弱，而 Hibernate 的 ddl-auto=update 對 SQLite 不可靠。所以 sessions 表的 schema 是手寫維護的——不要指望框架幫你遷移，要遷就寫腳本或用 Flyway／Liquibase。

兩個測試，各釘一個契約

CLI 是薄殼所以程式層沒多少好測；OryxOS 把驗收火力集中在 Session 層，用兩個測試各守一條契約：

測試驗證什麼契約
SessionManagerTest同樣三元組 → 同一個 Session；任一欄位不同 → 不同 Session冪等性（id 拼裝在一處、結果可重現）
SessionRepositoryTest手建的 sessions 表能寫能讀；模擬重啟後歷史還在持久性（重啟恢復）

為什麼這樣測最划算？因為 Session 契約的 bug（id 拼錯、寫了讀不回）是之後第七層「縫隙分析」最難追的那種——現在用兩個測試釘死，比之後在整條主流程裡排查便宜得多。

怎麼手動驗收整條 CLI

最後用真實操作收一遍尾：chat 多輪對話 + /quit；輕命令秒回、啟動紀錄出現 N > 0 個 JPA repositories；chat／serve／gateway 三種模式共用同一份 Profile 與 Session 存儲（在 chat 產生的歷史，切到 serve 也看得到）；12 個子命令 --help 都能跑。到這一步，你的底座第一次「真的能在終端機裡被自己用起來」。
