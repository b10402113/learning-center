動手前的四個決定

Step 2/4 · CLI 與 Session

學習目標

能複述動手前的四個決定（不碰 Agent 邏輯、輕重切分、Picocli、顯式 JPA 掃描），並能解釋「Found 0 JPA repository interfaces」這個陷阱的成因與修法。

寫 CLI 之前，先想清楚四件事

CLI 太容易寫成「一把抓」：反正終端機指令嘛，能在 main 裡把參數解析、呼叫引擎、順便管理 Session 全寫在一起。但 OryxOS 動手前就先釘死四個決定，避免事後被啟動延遲和 Spring 的隱形行為咬到。

決定一：CLI 永遠不碰 Agent 邏輯

CLI 只發命令、收回應。它不該自己判斷該調哪個模型、不該自己拼 prompt、不該自己決策工具呼叫。所有腦力都在引擎（AgentService → ReActLoop）與能力塊裡。這個決定讓 CLI 保持薄，也讓測試能被縮到很小——因為沒什麼可測的。

決定二：輕/重命令切分

不是每個命令都值得啟動整個 Spring 容器。啟動 chat 需要引擎，所以必須開 Spring；但 init 只是複製幾份檔案、profile list 只是列個目錄，開整套 Spring 是白付啟動延遲。

種類例子需要 Spring？行為
輕命令init、profile list否直接走檔案 API，瞬間回
重命令chat、serve、gateway是啟動 Spring、載引擎

啟動延遲是有感的：一個 2–4 秒的 chat 可以忍，但每次查 Profile 都要 4 秒就很煩。輕重切分本質上是「啟動延遲預算」的分解。

決定三：用 Picocli，不自己拆參數

子命令一多，手寫 args 解析就會變成災難（錯誤訊息不一致、help 不統一、縮排對不齊）。OryxOS 用 Picocli：一個子命令對一個 @Command 類別，參數、說明、錯誤處理全部交給框架。12 個子命令就 12 個類別，每個都極薄。

決定四：重命令要顯式宣告 JPA 掃描範圍（這是個坑）

這是輕重切分最容易踩的真實陷阱。你用 @SpringBootApplication(scanBasePackages=...) 指定了套件掃描範圍，但這個 scanBasePackages 並不自動攜帶 JPA 的 repository／entity 掃描。也就是說，即使你的 SessionRepository 在掃描範圍裡，Spring Boot 自動設定的 @EnableJpaRepositories 拿到的還是預設的「當前套件」，於是啟動就報：

Found 0 JPA repository interfaces

修法很直接：在重命令的啟動類別上顯式宣告掃描範圍，把底座真正的儲存套件指進去：

@EnableJpaRepositories(basePackages = "io.oryxos...storage...")
@EntityScan(basePackages = "io.oryxos...domain...")

輕命令不受影響，因為它們根本不開 Spring、不碰 JPA。這個坑的教訓是：走「自訂掃描 + 自動設定」這條路時，永遠要懷疑 Spring 的自動設定到底掃了哪裡。

怎麼驗證命令切分對

驗證不需要重邏輯——主要是看行為：輕命令要「秒回」（不該有數秒的 Spark 啟動打嗝）、啟動紀錄要能看到 N > 0 個 JPA repository 被找到、12 個子命令的 --help 都能正常列出。
