Session：冪等 session id

Step 3/4 · CLI 與 Session

學習目標

能說出 session id 是 channel+user+profile 三元組、為什麼必須只在 SessionManager 內部拼裝，以及冪等的定義（同樣的三元組 → 同一 session）。

先看它要解決的問題

Agent 要有連續性：你說「查一下北京天氣」→ 它查完回你；你接著說「那杭州呢」→ 它得知道「那」指的是「天氣」。所以對話歷史要被記得。OryxOS 把「一段要被記得的對話」叫一個 Session（會話）。

問題來了：同一句話 agentService.process(...)，怎麼知道該接在哪段歷史後面？這就是 session id 的用途——它是「哪一段對話」的身份證。

session id = channel + user + profile 三元組

OryxOS 的 session id 不是隨機 UUID，而是由三個欄位拼出來的：

欄位這是誰為什麼要進身份證
channel哪個入口CLI 傳 "cli"、Web 傳 "web"——同樣的人在不同入口可有不同語境
user哪個使用者不同使用者不會共用歷史
profile哪份 Profile換 Profile（像是換 Agent「人格」）就算重開一段語境

這個三元組決定了「冪等性」：同樣的 (channel, user, profile) 一定得到同一個 session。你 chat 十次、退出十次，只要三元組不變，歷史都在。

關鍵規則：拼裝只能發生在一處

三個欄位怎麼組成一格 id？元組的格式（例如 cli:alice:weather）只有 SessionManager 內部知道。所有入口——CLI、Web、後來的排程——都只把「三元組的三個值」傳進去，由 SessionManager.getOrCreate(channel, user, profile) 統一拼。

任何入口都不准自己拼 session 字串。否則兩個入口用不同的拼接規則，同一個使用者就會裂成兩段「互相不認識」的歷史。

舉例：CLI 拼成 "cli:alice:weather"，某天有人偷懶在 Web 端自己拼成 "cli_alice_weather"——表面上看起來都在存取「weather」的對話，實際上存到了兩把不相干的鑰匙，Agent 的連續性就斷了。

程式怎麼接

ChatCommand 的迴圈長這樣：讀 stdin 的一行 → 若 /quit 就退出 → 否則拿到三個值（"cli"、目前使用者、Profile 名）丟給 sessionManager.getOrCreate(...)，把回傳的 Session 和那一行一起丟進 agentService.process(session, line)。

// 概念示意，省略細節
Session s = sessionManager.getOrCreate("cli", currentUser(), profileName);
agentService.process(s, line);

引擎側的 AgentService 則依賴 SessionManager 幫它取 Session、存 Session——它自己不需要知道 session id 是什麼形狀。

這個規則是「單一真相」的起點

session 身份只存在 SessionManager 一個地方亂拼，這條規則會被後面的 Web Service、定時任務、IM 渠道反覆複用。一旦你在哪個入口自己拼了 id，你就在引擎不知情的地方製造了第二個真相——這是「明明寫對卻找不到對話」的經典來源。
