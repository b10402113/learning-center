CLI 是什麼：薄入口

Step 1/4 · CLI 與 Session

學習目標

能說出 CLI 的定位是「門不是工人」、核心階段 12 個子命令怎麼分成三組，以及三種運行模式如何共用同一個引擎與同一份 Session 存儲。

一張圖先擺好：CLI 站在哪

OryxOS 包成一個可執行的 JAR，`main` 就是 OryxOsCli。整個底座有兩個「人推」的入口：CLI 與 Web Service，兩者都餵進同一個 ReAct 引擎；引擎再調度 Provider／Memory／Tool 三大能力塊。（之後第 25 節的定時任務會加上第三個「時鐘推」的入口。）

CLI 是門，不是工人。那扇門只負責把訊息接進來；真正的活是引擎在幹。

這句話是理解本節所有設計的鑰匙：編排、呼叫 LLM、調工具、記憶，沒有一樣屬於 CLI。CLI 只管「把標準輸入的一行字送到引擎，再把引擎的回應印回標準輸出」。

核心階段的 12 個子命令

核心階段（對應需求文件的「核心範圍」）有 12 個子命令，可以大致分成三組：

族群命令幹嘛用
啟動 Agent（跑起來）chat / serve / gateway三種運行方式，差別只在訊息從哪來
查看狀態（檢查）status、profile list/create/show/delete、provider list、tool list、session list看組態、看資料、看會話
初始化（引導）init生出一份乾淨的工作區骨架

命令的分組不是隨意分的：「啟動 Agent」這組要開 Spring 容器（重），「查看狀態」大半不用（輕）——輕與重怎麼切，是 Step 2 的主題。這裡只要先記住這 12 個命令存在，以及它們在設計上分成三個角色。

三種運行模式：一魚三吃

chat（互動對話）、serve（開 Web Service）、gateway（很多渠道的守護行程）共用三樣東西：一份 Profile 組態、一個 Session 存儲、同一個底層引擎。它們唯一的不同是訊息從哪裡來：

  • chat —— 從標準輸入（stdin）來，印到標準輸出（stdout）。
  • serve —— 從 HTTP REST 來，走 Web Service。
  • gateway —— 從各聊天渠道來，走 Channel 抽象。

這意味著你在 chat 裡產生的一段對話，印證「狀態在引擎，不在入口」——換個入口，對話還在同一個 Session 上。

動手先摸一摸

整組命令的日常長這樣：

oryxos init                 # 生出工作區
oryxos profile list         # 看有哪些 Profile
oryxos chat                 # 進互動對話
oryxos chat --profile weather  # 用 weather 這個 Profile 進對話
oryxos serve                # 開 Web Service
oryxos status               # 看目前的狀態

這是 Provider 與 ReAct 之後你第一次真的在終端機「跟自己的 Agent 講話」——從這裡開始，底座不再是紙上架構。
