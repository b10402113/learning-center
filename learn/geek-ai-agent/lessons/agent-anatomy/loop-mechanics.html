Loop：ReAct 迴圈

Step 3/5 · Agent 五元件與真偽判別

學習目標

能畫出 ReAct 迴圈（Reasoning → Acting → Observation）並解釋為什麼「單次 LLM 呼叫是聊天機器人、只有循環的決策—行動—觀察才是 Agent」，以及一個好迴圈必須處理的四件事（停止條件、錯誤恢復、上下文壓縮、多模型切換）。

分界線：一次呼叫 vs 反覆循環

五個元件裡，LLM、Tools、Memory、Environment 都是「零件」，只有 Loop 是把它們串起來的「引擎」。這裡有一條清楚的分界線：

單次 LLM 呼叫是聊天機器人；只有循環的決策—行動—觀察，才讓它變成 Agent。

差別不在模型多強，而在「它能不能根據上一次行動的結果，自己決定下一步」。能，就是探索性的 Agent；不能，就是照著輸入產出輸出的聊天機器人。

ReAct：Reason + Act

ReAct 是 Reasoning（推理）與 Acting（行動）的縮寫，三個動作一直轉：

  1. Reasoning（推理）——LLM 看目前狀態，想「下一步該做什麼」。
  2. Acting（行動）——決定呼叫某個工具，並給出參數；或直接產出答案。
  3. Observation（觀察）——工具執行的結果回到迴圈裡，成為下一輪推理的輸入。

然後回到第 1 步，直到達成目標。聽起來簡單，但魔鬼全在「一直轉」這三個字。

一個好迴圈必須處理的四件事

真正把 ReAct 寫進生產系統時，挑戰不在主流程，而在四個旁支問題——它們是框架八成複雜度的來源：

要處理的事不處理會怎樣典型做法
停止條件模型永遠覺得「還差一點」，迴圈停不下來設定最大迭代次數（例如 MAX_ITER = 10）與完成判斷
錯誤恢復工具一報錯，整個流程就死在那裡把錯誤當成一種 Observation 回填，讓模型有機會重試或換路
上下文壓縮歷史越積越長，超過模型能吃的長度保留近期歷史、摘要或截斷較舊的內容
多模型切換簡單步驟用了貴模型，成本失控或速度太慢依步驟難度路由到不同模型

這四件事會反覆出現：後面 OryxOS 的 ReActLoop 之所以要寫這麼多控制邏輯，就是在處理它們。以 OryxOS 為例，迴圈設了 MAX_ITER = 10，每一輪的 LLM 回應與工具結果都會累積進 session 歷史（這讓每一步都可事後審計），而當歷史長到超過上下文視窗時，就保留近期歷史。整套東西在 OryxOS 裡用不到 100 行 Java 就能寫完——ReAct 沒有任何魔法，它是可以被完整推導出來的。

不是每一輪都要叫工具

回到翻譯 README 的例子：第 1 輪呼叫讀檔工具、第 3 輪呼叫寫檔工具，但第 2 輪的「翻譯」是 LLM 自己完成的。這點很重要——迴圈的每一輪不一定都有工具呼叫。推理本身就能產出進展；工具只是當需要碰外部世界時才出場。把 Loop 想成節拍器，不是每一拍都要敲鼓。

為什麼這一節要獨立成一步

因為當你能拆解任何 Agent 之後，真正決定成敗的往往不是「有沒有用某個模型」，而是這個迴圈設計得好不好：停得下來嗎？錯得起的嗎？記得住又不爆掉嗎？成本控得住嗎？這四個問題就是後面 Loop Engineering 方法論的起點。
