動手前先想清楚到驗收

Step 5/5 · 定時任務與 Web Service

學習目標

能複述 Web Service 動手前的五個決定（薄控制器共用引擎、單一異常出口、核心期非目標、serve 單 key、admin 唯讀），並說清 400／404／500／503／504 錯誤碼的對應與「內部細節絕不漏進 500」的驗收。

五個決定，一次想完

動手寫任何一個 controller 之前，先把五件事釘死。它們決定了 Web Service 是「引擎的一層皮」還是「第二套系統」。

決定一：控制器必須薄，並且共用同一顆引擎

POST /sessions/{id}/messages 呼叫的，必須是 oryxos chat 用的同一個 AgentService.process，沒有第二條處理鏈。最大的誘惑是「在 controller 裡順手加一點邏輯」——每加一點，Web 就跟 CLI 岔開一點，最後變成兩套行為不一致的系統。這是會破壞架構的那條紅線。

決定二：單一異常出口，固定的錯誤碼

六支控制器不各自處理例外，全部交給一支 GlobalExceptionHandler，產出統一的 JSON（包含 errorCode、message、timestamp）：

HTTP 狀態代表什麼
400參數錯誤（例如訊息超過 32KB）
404資源不存在（例如 session 找不到）
500內部錯誤（訊息不洩露內部細節）
503Provider 服務不可用
504Agent 呼叫超過 60 秒逾時

決定三：核心期非目標，寫清楚不該做什麼

認證（內網假設，Auth 留給擴展）、SSE 串流、WebSocket、rate limiting、RBAC——這些核心期明確不做。只保留兩道請求尺寸防護：單則訊息上限 32KB、session 歷史保留最近 100 則。把非目標寫進文件，是為了防止開發到一半「順手加上去」。

決定四：serve 必須能用單一 provider key 啟動

Spring AI 的 OpenAiAutoConfiguration 會急切地要求 spring.ai.openai.api-key，沒有就啟動失敗。解法不是塞一個假 key，而是把它排除在自動配置之外——和排除 DashScopeAutoConfiguration 是同一個手法。這樣 serve 就只認 DEEPSEEK_API_KEY 一個 key。

決定五：admin v1 唯讀

管理平台可以看 session、Profile、Tool、記憶、狀態，但不能建立或編輯 Agent——那需要第 29／30 節的端點。UI 上不放「假按鈕」，做不到的操作就不要畫出來。

程式怎麼寫：薄控制器與虛擬執行緒

設定上開啟 spring.threads.virtual.enabled: true，每個請求跑在一個虛擬執行緒（virtual thread）上——高並發時不必為每個連線開一條 OS 執行緒。典型控制器 SessionApiController.send 只有三步：驗證 content 非空且 ≤32KB；載入 session，找不到就丟 404；然後 agentService.process(session, req.content())。其餘端點（invoke、profiles、tools、memory、health、info）一樣直接。OpenAPI 規格由 springdoc 自動產生，掛在 /swagger-ui。

驗收 harness：三種測試各自抓什麼

  • @WebMvcTest 切片（mock 掉 AgentService）——只掛 MVC，不啟動模型與資料庫，跑得快。SessionApiControllerTest 斷言 >32KB → 400、session 不見 → 404、以及 agentService.process 恰好被呼叫一次（證明 controller 沒偷偷加邏輯）。
  • @SpringBootTest（真實 context、無模型）的 GlobalExceptionHandlerTest——逐個確認例外對到議定的狀態碼與統一 body，以及 500 不洩露內部例外訊息。
  • WebSmokeIT 走真實路徑打 /health、/info、/profiles、/tools，驗證 bean 組裝與掃描——也順帶抓回第 18 節那類「Found 0 repositories」的 JPA 掃描 bug。
最關鍵的一條回歸：內部細節（例如一段 JDBC 連線字串）絕不能出現在 500 的回應 body 裡。對外門面照顧的不只是可用性，還有把內部世界洩漏出去的問題——這條在測試裡釘死，漏出去任何內部訊息都算測試失敗。

人做完的驗證清單

測試綠以後，人類再做一遍真實驗證：開啟 oryxos serve 後用 curl 走完 10 個端點（含一次真實模型的 POST /sessions/{id}/messages）、確認 CLI 建立的 session 用 Web 讀得到（兩個入口共用儲存）；把 Provider 關掉看 503、把呼叫拖到 60 秒以上看 504（真實故障注入）；跑 200 個並發 invoke 看虛擬執行緒撐不撐得住；最後確認 admin 五個頁面都渲染真實資料、沒有任何寫入口，/swagger-ui 完整。

收尾：從「散落零件」到「整條鏈」

到這裡，五大核心能力都各有對外出口——CLI、Web、排程三條入口共享同一顆引擎。但 Agent 仍然只是「散落的零件」：還沒有人把整條鏈拉起來跑。接下來的兩節（全流程串聯）就是把這十幾個模組對表對賬、串成真能運作的完整流程。
