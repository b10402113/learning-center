AgentScheduler 實作與驗收

Step 3/5 · 定時任務與 Web Service

學習目標

能手寫 registerAll／runOnce：用 ThreadPoolTaskScheduler 動態 schedule（CronTrigger 帶時區）、每任務一個 ReentrantLock 做 tryLock、固定 scheduler session 身分、finally 解鎖，並用「第二次進入」的斷言證明鎖確實釋放。

AgentScheduler 手上有什麼

實作上只靠四個成員就夠，沒有多餘的依賴：

  • ThreadPoolTaskScheduler——Spring 提供的排程執行器，負責到點呼叫。
  • ProfileRegistry——到哪找所有 Agent 的排程配置（每個 Profile 的 schedules）。
  • AgentService——真正處理訊息的單一編排入口。
  • 一張 ConcurrentMap<String, Lock>——每個任務一把鎖。

registerAll：把「配置」變成「到點動作」

啟動時，排程器遍歷所有 Profile 的 schedules，對每一筆排程呼叫：

taskScheduler.schedule(
    () -> runOnce(profile, sc),
    new CronTrigger(sc.getCron(), sc.getZoneId()));

關鍵在 new CronTrigger(sc.getCron(), sc.getZoneId())——時區在這裡就明確綁進觸發器，而不是靠伺服器預設。這正是上一節「時區陷阱」的落腳：陷阱二的坑，在程式裡用一行 getZoneId() 堵死。

為什麼用 TaskScheduler.schedule 動態註冊，而不寫 @Scheduled 註解？因為 @Scheduled 的 cron 在編譯時就釘死了，要改觸發時間就得改程式、重新編譯。動態註冊讓「改觸發時間」退化成純配置變更——改 Profile 的 cron 欄位，重啟生效，一行 Java 都不動。

runOnce：加鎖進場、固定身分、finally 出場

每次觸發都會進到 runOnce(profile, sc)：

  1. 先按任務 id 從那張 Map 取得（或建立）一把 ReentrantLock，tryLock()；鎖被佔著就跳過並記錄，不排隊。這對應「重疊陷阱」——上一次還沒跑完，這趟就放棄，而不是疊加執行。
  2. 接著 sessionManager.getOrCreate("scheduler", "scheduler", profile.getName())——排程器的 session 身分是固定三元組，代表「scheduler 這個通道、scheduler 這個使用者、這個 Agent」。歷史長度由 max_history_turns 截斷。
  3. 呼叫 agentService.process(session, sc.getMessage())——和 CLI、Web 完全同一條路，審計照樣寫進 llm_calls／tool_invocations。
  4. 整段包在 try/catch 裡，例外用 log.error 記下但不往上一層拋（失敗隔離）；不管成功失敗，finally 裡必定 unlock()。

身分配號：runs 之間保持連續

同一個任務的兩次觸發，會進到同一個 session 三元組，所以第二次觸發是接續第一次的歷史，而不是另起爐灶。對「每日天氣」這類連續性任務，這是刻意設計：排程是同一場「與這個 Agent 的長期對話」，只是對話由時鐘來推進。

驗收：不等真實時間, 重演四個陷阱

測試最快樂的思考是「別真的等到那時刻」。排程器把 runOnce 抽成獨立方法，測試就直接呼叫它；fire 正不正確是 Spring 的事，測試只驗證「註冊參數對不對」。一個 AgentSchedulerTest 就把四個陷阱全部重演：

陷阱斷言方式
時區／配置用 ArgumentCaptor 抓到 CronTrigger，確認它帶著配置裡的 cron 與時區
重疊先佔住鎖，再觸發一次，斷言這次被跳過、沒有排隊
失敗隔離讓 runOnce 拋例外，斷言例外不外洩、且鎖在 finally 被釋放
session 身分連續兩次觸發，斷言拿到同一個 session 三元組

最有價值的一半：第二次進入

最容易被漏掉的是失敗隔離那條的第二半——例外測完之後，再呼叫一次 runOnce，斷言這次能正常進場。為什麼？因為如果 finally 忘了 unlock，第一次測試也許照樣通過（例外沒外洩就算過），鎖卻一直卡著，之後排程永久失靈。只有「第二次進入」能證明鎖真的有被釋放——這是一個專門抓「漏了解鎖」的測試設計。

做完怎麼驗

自動測試之外，人還要做一遍真實演練：把某個排程設成每分鐘觸發一次，觀察 Agent 自主發起對話、審計有紀錄；改掉 cron 表達式再重啟，看它照新時間走——這同時驗證了「配置驅動、免重新編譯」。這趟「觸發 → ReAct 迴圈 → 審計紀錄」全路徑，也正是下一節 Web Service 與之後三支 Demo Agent 的基石。
