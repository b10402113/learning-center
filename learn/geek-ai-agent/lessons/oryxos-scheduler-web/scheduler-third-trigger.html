定時任務：第三個觸發源

Step 1/5 · 定時任務與 Web Service

學習目標

能認出定時任務不是一個新能力，而是第三個觸發源（clock-push）：到點時由系統組裝訊息、餵進同一條 AgentService 入口，ReActLoop、Provider、工具執行全都零改動。

先看一個「不被問也會做事」的需求

想一下「每天早八點幫我查天氣、再建議穿什麼」這種需求。你不是站在終端機前打字，也沒有一個系統會來問你；但你希望 Agent 在那一刻自動醒來做事。換句話說，Agent 需要跟上班打卡一樣——時間一到，它自己知道該上工了。

人推 vs 時鐘推：兩種觸發

回顧前面已有的入口：CLI（`oryxos chat`）和 Web Service（HTTP 端點）都是「人問、機器答」——有人發起對話，引擎回應。這叫做人推（human-push）。

但很多場景裡，沒有任何人來問，Agent 卻必須主動做事：定時報表、每日科技日報、庫存對帳。這條路徑是時鐘推（clock-push）——由時鐘決定「誰在哪一刻被呼叫」。

定時任務不是新能力，是第三個觸發源

這是整節最重要的一句話：定時任務不是一種新的「能力」，而是一個新的「觸發源」。所謂能力，是引擎裡那些真正做事的部分——ReAct 迴圈、工具執行、Provider 呼叫。加入定時任務時，這些部分一行都不用改。

定時任務做的事很簡單：時間到了，系統組裝出一個訊息（例如「查一下北京天氣，給穿搭建議」），然後把它投進跟 CLI／Web 完全同一條入口——AgentService.process。從那一刻起，引擎就像收到一次普通對話一樣處理它。

為什麼能做到零改動？因為 OryxOS 的引擎只有一個編排入口。AgentService.process 是 CLI、Web、排程三者共用的單一入口，誰呼叫它不重要，重要的是呼叫的方式相同。少了定時任務，缺的從來不是「處理能力」，而是「到點時由誰去呼叫它」這最後一格。

為什麼現在才做：給兩個 Demo 補上最後一格

回想計畫裡兩個驗收型 Agent：每日天氣、每日科技日報。它們的共同點是「時間到了自己跑」。沒有排程，這兩個 Agent 只能被人手動喊醒——那就不叫「自動」。所以定時任務是這兩支 Demo Agent 成立的前置條件，而不是錦上添花的選項。

引擎保持穩定，新增入口不碰核心

把這節學到的放回整條主線：Provider、ReAct、CLI、Notify、Tool、Memory、Sandbox 都就位之後，基底仍然少一塊「時間感」。加上定時任務，OryxOS 的入口補齊成三個——CLI、Web、排程——全部餵同一顆引擎。這正是整個底座反覆強調的紀律：引擎穩定，新增入口不碰核心。下一步我們會看動手前要想清楚的邊界，把這層「薄排程層」的職責釘死。
