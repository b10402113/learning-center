動手前先想清楚：薄排程層與四個陷阱

Step 2/5 · 定時任務與 Web Service

學習目標

能界定 AgentScheduler 只做「讀排程、觸發、組裝訊息、防重疊、記成敗」五件事，選擇 Spring 內建 TaskScheduler 而非自寫，並講出配置來源、重疊、失敗隔離、時區四個陷阱。

動手之前，先問「它到底負責什麼」

定時任務模組看似簡單，但新手容易讓它越長越胖：有人想讓它決定「訊息內容」，有人想讓它管「哪台機器跑」，有人甚至想寫一套排程引擎。動手前必須先把職責邊界定死。

AgentScheduler 只做五件事：

  1. 讀取 cron 排程配置
  2. 在到點時刻觸發
  3. 組裝一個訊息交給 AgentService
  4. 防止同一個任務重疊執行
  5. 記錄觸發的成敗

它刻意不做的事

反面清單和正面清單同等重要。AgentScheduler 不決定：

  • 訊息內容說什麼——那是 Profile／SKILL.md 的職責（配置即 Agent）。
  • 訊息怎麼被處理——那是 ReActLoop 的事。
  • 由哪個實例執行——分散式協調是第二階段的議題（leader election、分散式鎖、Lease）。

換句話說，它是一片薄排程層：只管「幾點叫誰」，不管「叫了之後發生什麼」。

不要自己寫排程器

第二個決定很務實：直接用 Spring 內建的 TaskScheduler，不自寫。它支援標準 cron 語法與動態註冊，正是這個模組需要的——既可以手寫成 `@Scheduled` 那類靜態排程，也能在執行中期動態掛入新任務。重新發明一個排程引擎，只會把維護負擔攬回自己身上。

四個陷阱

整個設計的精神，都濃縮在四個陷阱裡。每個陷阱都是一個「不看就會出事」的點：

陷阱一：配置來源——cron 與訊息必須來自 Profile／SKILL.md

排程時間和觸發訊息不能寫死在 Java 常數裡。要改觸發時間，應該是改配置檔，而不是改程式、重新編譯。這個原則叫配置即 Agent——一個 Agent 的外觀樣貌與行為，全部由它的配置文件決定，Java 端只是執行器。

陷阱二：重疊執行——單實例用程序內鎖就夠

如果上一次執行還沒結束、下一個週期又到了，理論上同一個任務可能同時跑兩趟。對單實例的核心期來說，一把程序內（process-local）的鎖就足夠了——不需要分散式鎖。分散式鎖是第二階段的事。

陷阱三：失敗隔離——執行崩了不能拖垮排程器，也不能靜默

一趟排程執行拋出例外，排程器本身必須照常運作；但不代表可以假裝沒發生。這趟失敗照樣要走平時的審計路線——寫進 llm_calls／tool_invocations——讓它被看見，而不是默默吞掉。

陷阱四：時區——cron 預設用伺服器時區

cron 表達式本身不含時區資訊，預設跟著伺服器的時區走。如果你的「早 8 點」指的是北京時間，而伺服器在 UTC，就會差八個小時。所以配置裡必須明確指定時區，不能靠預設。

四個陷阱的共同點是同一件事：排程器應該是一層薄薄的通用機制，所有「業務相關」的決定都留在配置與既有引擎裡。誰碰壞這條邊界，誰就把薄層變厚，把重疊、時區、失敗這些麻煩全部攬進 Java 程式碼。
