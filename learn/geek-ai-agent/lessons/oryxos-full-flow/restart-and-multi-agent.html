跨重啟恢復與多 Agent 並存

Step 5/6 · 全流程串聯

學習目標

能用一次 kill／重啟驗證狀態全數外置，並用兩個不同 Profile 驗證工具、會話、排程三條隔離邊界互不打架。

測試的可以是一句架構承諾

技術方案裡有一句很硬的承諾：所有狀態都活在進程之外（SQLite 加上檔案系統），進程本身什麼都不存。這句話不是設計偏好，而是未來要邁向分布式的前提——只有當每個實例都是無狀態的，你才能放心地起第二個、第三個實例，然後讓流量在它們之間流動。

但承諾要能被驗證才有意義。驗證方法出奇簡單：讓它死一次，再活過來，看該不該忘的東西有沒有忘。這就是跨重啟恢復測試。

怎麼跑這一趟

先在活著的系統上累積狀態：跑幾段對話、寫進一些記憶、讓一個定時任務至少觸發過一次。然後 kill 掉進程、重新 serve 起來，逐項核對：

要回來的東西為什麼它該回來怎麼看
sessions對話歷史存在 SQLiteGET /sessions/{id} 看得到重啟前的完整歷史
memoryMEMORY.md 是一個檔案檔案天生跨重啟，讀出來即可
scheduled tasks定義從 skill 重新註冊，狀態與歷史還在兩張表GET /api/v1/schedules 一次看全部
audit審計落庫、不隨進程消失重啟前後的 llm_calls 連續、不中斷

哪一項沒回來，就是一個隱患

這裡的判讀邏輯要反過來想：任何一項沒能回來，都證明某個狀態偷偷留在了進程的記憶體裡。例如排程觸發次數如果重啟後歸零，代表 run_count 其實只記在記憶體，只是「看起來」有在累加。這種隱藏狀態在單機時可能無害，一旦走向分布式就會變成致命傷——兩個實例各自記一半，誰都不是真相。

所以重啟測試不是在驗「資料庫有沒有壞」，而是在逼出所有偷偷留在記憶體裡的狀態。這是走向分布式之前必須先消滅的一類隱患。

多 Agent 並存：同一個實例，兩個不同的 Agent

「OS」這個字要成立，核心階段的最低門檻是：同一個實例上能跑多個 Profile。做法是配置兩個明顯不同的 Profile——例如一個只掛檔案工具、一個只掛 HTTP 工具——然後交替使用它們，驗證三條隔離邊界。

隔離邊界要驗什麼
工具隔離A 的對話裡，工具清單不得出現 B 的專屬工具（tools 過濾確實生效）
會話隔離A 與 B 的 session 不混在一起——session id 帶著 Profile 名；要特別留意有沒有程式碼用了「預設 Profile」而把兩者混在一起
排程隔離A 的排程任務拋出例外時，不得阻止 B 的下一次觸發

這三條必須全部驗，不能只看工具清單。工具隔離最容易被想到，但也最容易讓人誤以為「驗完工具就等於驗完隔離」。真正會出事的往往是會話混線與排程互相拖累——它們不會在畫面上一眼看出來，只會在使用者發現「我怎麼看到別人的歷史」時才爆開。

為什麼這是底座與 Demo 的分水嶺

把這一課放回整條主線看：一個 Agent demo 只需要在演示的那幾分鐘裡活著，關掉重開就算資料沒了也無所謂；但一個底座必須在沒人看的時候仍然維持正確——重啟不失憶、多個 Agent 不打架。前者是表演，後者是基礎設施。

跨重啟恢復與多 Agent 並存，正是這兩者之間的分水嶺。走過這一課，你手上才真的是一台「自己跑得穩」的底座，而不只是一條跑得起來的主流程。
