跨重啟恢復與多 Agent 並存

Step 5/6 · 全流程串聯

學習目標

能用一次 kill／重啟驗證狀態全數外置，並用兩個不同 Profile 驗證工具、會話、排程三條隔離邊界互不打架。

底座的核心承諾：狀態全在進程之外

一個 Agent 底座跟一個 Agent demo 的分水嶺，就在這裡：demo 只需要在示範的那幾分鐘活著，底座必須在沒人看的時候也保持正確。要證明這點，OryxOS 立下一條架構承諾——所有狀態都活在進程之外（SQLite + 檔案系統），進程本身不存任何東西。這條承諾不是嘴上說說，而要用一次重啟去驗。

用一次 kill／重啟來驗

方法很直接：跑幾段對話、累積一些記憶、讓排程至少觸發一次，然後 kill 掉進程、重新 serve。接著逐項檢查：

狀態重啟後應該為什麼
會話GET /sessions/{id} 顯示重啟前的歷史歷史在 SQLite 裡
記憶MEMORY.md 內容還在它是檔案，天生跨重啟
排程定義重新註冊、狀態與歷史還在定義在 skill、狀態在兩張表
審計重啟前後的 llm_calls 連續不中斷審計 day one 就落庫

這張表就是「狀態外置」的照妖鏡：任何一項沒回來，就代表有狀態被偷偷藏在進程記憶體裡——那是走向分散式之前必須除掉的隱患，因為「無狀態實例」正是技術方案的前提。

多 Agent 並存：一個 OS 的最小門檻

如果一台機器只能跑一個 Agent，那它就只是「一個 Agent 的程式」，稱不上 OS。核心階段的最低門檻是：同一個實例上同時跑多個 Profile。驗證方法很具體——設定兩個看得出差異的 Profile（一個只帶檔案工具、一個只帶 HTTP 工具），輪流使用，然後查三條隔離邊界：

邊界要驗證什麼
工具隔離A 的對話裡，工具清單不能出現 B 專屬的工具——tools 過濾要真的生效
會話隔離A 與 B 的會話不混在一起——id 有帶 Profile 名，但要提防程式用「預設 Profile」把它們攪在一起
排程隔離A 的排程拋例外，不能擋住 B 的下一次觸發——失敗隔離在多 Agent 下再驗一次

重點是：隔離必須三個維度都驗，不能只驗工具清單。只看到 A 沒用到 B 的工具，不代表 A 的排程掛了不會連累 B。

一句話收束

把這一課濃縮成兩句話：「重啟不失憶」靠狀態外置，用一次 kill／重啟來證；「互不打架」靠隔離，用工具、會話、排程三條邊界來證。前者保證單一實例的耐久，後者保證多租戶的乾淨。下一課做最後一道打磨，把「能跑」變成「跑得穩」，再把這一切固化成 mvn verify 都會回答的確定事實。
