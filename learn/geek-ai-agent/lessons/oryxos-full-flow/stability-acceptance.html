從能跑到跑得穩：穩定打磨與兩線驗收

Step 6/6 · 全流程串聯

學習目標

能列出讓底座「跑得穩」的打磨項目，並把對賬固化成「無 key 機制驗證 + 真 key 鏈路驗證」兩線驗收，讓 mvn verify 回答整台機器是否可用。

能跑之後，還差的是「穩」

主流程打通、排程會跑、重啟不失憶、多 Agent 不打架——這些讓底座「能跑」。但能跑和跑得穩之間，還隔著一批小、卻在演示時一眼看得見的打磨項目。它們不改變架構，卻決定了這台機器在真實環境裡是可靠還是脆弱。

打磨項目：五件小事

項目要求
該逾時的要逾時模型呼叫、工具執行、notify 推送都要有逾時，一通呼叫卡住不能拖垮整個虛擬執行緒；整通 Agent 呼叫另設 60 秒上限
錯誤訊息人類可讀error_message 存的是原因（例如「網域不在白名單內: evil.com」），不是堆疊追蹤——審計表是給人看的
一次觸發一條日誌主線用 session id 就能把一次對話／觸發追出來，不必翻幾百行日誌
外部 MCP 掛掉不拖垮自己外部 MCP 不可用時記 WARN、跳過它的工具、正常啟動——別人的可用性不能變成你的

最後一條值得多說一句：把外部依賴的失敗直接放大成自己的啟動失敗，是最常見的自傷。一個新聞 MCP 沒起來，不該讓整個 OryxOS 起不來。

Demo 前置清單：先別被自己絆倒

演示或部署前，把這六項一次設定並核對完：

  1. 網域白名單包含天氣 API 與 webhook 網域。
  2. 通知渠道設定完成，並手動收到過一則推送。
  3. 新聞 MCP 在 mcp_servers.yaml 宣告，且工具在 oryxos tool list 看得見。
  4. 記憶裡已經有一條偏好（例如把「更關注 AI 和芯片」談進 MEMORY.md）。
  5. cron 運算式與明確時區（例如 Asia/Shanghai）都檢查過。
  6. 跨重啟驗證過：session 持久、定時任務重新註冊。

其中最容易自己踩的坑是第一項。Sandbox 預設是 deny-all，所以三個網域必須顯式加白：天氣來源（例如 api.open-meteo.com）、團隊通知 webhook（例如飛書 *.feishu.cn 或企業微信 qyapi.weixin.qq.com）、以及任何新聞來源。

同時要記得：file 與 shell 這兩個白名單維持 deny-all（這些 demo 用不到）；另外要確認 OpenAiAutoConfiguration 已被排除，否則 serve 根本起不來。這些檢查一次做完，才不會在台上發現環境只對了一半。

把對賬固化成兩線驗收

人工對賬做完，最後一步是把它變成會自己重複執行的測試。這裡刻意分成兩條線，因為它們的前置條件完全不同：

線代表測試前置驗什麼
機制線（無 key）ScheduledTaskE2ETest、MockProviderFlowTest、MockAgentE2ETest不需要 key 與網路，進 gate註冊／執行／持久化／管理的機制，以及整條鏈會跑
鏈路線（真 key）SchedulerFlowIT、RestartRecoveryIT、HumanTriggerFlowIT需要真 key 與網路，預設 CI 略過天氣／推送真的送出、重啟真的恢復、對賬真的對平

無 key 那條線怎麼可能驗全鏈？

關鍵在 mock provider。在顯式映射下開一個 mock 名字，它不接真模型、不需要 key，只照劇本演一段 ReAct：第一輪要求呼叫工具，第二輪呼叫 save_memory（真的去寫 MEMORY.md，留下一個可觀察的檔案寫入），然後回傳最終答案。

這裡的紀律是：只有「模型」是假的。ReActLoop、ToolExecutor、Memory、Session、審計全部走真實路徑。所以它能驗的是「整條鏈的接線」，而不是「模型答得好不好」。為了讓測試互不干擾，工作區根目錄支援以系統屬性 oryxos.root 指定（預設 .oryxos），測試就指向一個臨時工作區。

以 ScheduledTaskE2ETest 為例：在臨時工作區放一個 provider: mock 的 Agent 並帶 schedules（cron 設得很遠，改用 run-now 觸發），啟動後斷言它已註冊（run_count=0、enabled=true）；接著 POST /schedules/{id}/run 跑一次真正的 ReAct，斷言 run_count=1、last_status=success、有一筆執行紀錄、記憶可查；最後用 PUT 把它停用。整個過程不需要 key。

真 key 那條線驗的是「鏈路」

無 key 的測試驗不到「天氣真的查回來、推送真的送到」。所以另有一條真 key 的線：SchedulerFlowIT 用測試 Profile 觸發「查北京天氣推送穿搭」，斷言 session 被重用、llm_calls=2、tool_invocations=2、測試 webhook 收到，並額外驗白名單外的失敗路徑留下 success=false 而不殺死排程。

再加上 RestartRecoveryIT（kill／重新 serve 後斷言四項都回來）與多 Agent 隔離測試，整條真 key 線就把「機制對」升級成「真的有用」。

收尾：把體感變成事實

這一課之後，「這台機器跑得穩」不再是你讀日誌後的體感，而是每次 mvn verify 都會回答的確定事實——機制線在 gate 裡每次跑，鏈路線需要 key 時手動跑。驗收清單的最後一項也因此很簡單：mvn clean verify 全綠。

到這裡，底座的第一部分完成了：人推的問答答得對、排程的任務能定義／執行／管理／對賬、重啟不失憶、多個 Agent 不打架。但我們其實還沒真正定義一個業務 Agent——那正是下一課的視角轉換：底座是底座，Agent 是 Agent。
