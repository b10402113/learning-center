從能跑到跑得穩：穩定打磨與兩線驗收

Step 6/6 · 全流程串聯

學習目標

能列出讓底座「跑得穩」的打磨項目，並把對賬固化成「無 key 機制驗證 + 真 key 鏈路驗證」兩線驗收，讓 mvn verify 回答整台機器是否可用。

能跑，還不夠

前面五課把機器裝起來、會答、能自己跑、重啟不失憶、多 Agent 不打架——這些是「能跑」。但「能跑」跟「跑得穩」之間，還隔著一批小而關鍵的打磨。這些項目單看都不起眼，卻正是 demo 現場最容易翻車的地方。

四件打磨：逾時、可讀錯誤、單一日誌主線、MCP 隔離

  • 該逾時的都逾時：模型呼叫、工具執行、notify 推送都設逾時，避免一個卡住的呼叫拖垮整條虛擬執行緒；每次 Agent 呼叫另設 60 秒整體上限（第 26 節訂下）。
  • 錯誤訊息要人看得懂：error_message 存的是「域名不在白名單內: evil.com」這種理由，而不是一堆 stack trace——審計表是給人看的。
  • 一次觸發、一條清晰日誌主線：一段對話或一次觸發，要能靠 session id 一路追下去，不必在幾百行日誌裡大海撈針。
  • 外部 MCP 掛了不連累底座：外部 MCP 伺服器沒回應時，印 WARN、跳過它的工具、照常啟動——別人的可用性，不能變成你的可用性。

這四件合起來，就是「底座」和「demo」的差別：demo 賭的是現場那幾分鐘不出事，底座賭的是長期沒人看也不出事。

把對賬固化：兩線驗收

人工對賬做得再細，也只是一次性的。要讓「整台機器跑得穩」變成每次建置都會回答的事實，得把對賬固化成測試，而且拆成兩條線：

  • 機制線（無 key、進 gate）：用一個 mock provider 取代真實模型——它照著劇本演 ReAct：第一輪要求呼叫工具、第二輪真的寫進 MEMORY.md（留下可觀察的檔案寫入）、最後回傳答案。只有「模型」是假的，ReActLoop、ToolExecutor、Memory、Session、審計全都走真實路徑。因為不碰網路、不需要 key，這條線能進 gate，隨 mvn verify 自動跑。
  • 鏈路線（真 key、手動）：拿真實模型把「查天氣 → notify 推送」真的走一遍，確認 session 重用、llm_calls = 2、tool_invocations = 2、webhook 真的收到，以及失敗路徑留下 success=false 且不拖垮排程。

機制線保證「整條鏈的骨架是通的」，鏈路線保證「真實模型上真的能跑」——兩者互補，缺一不可。

驗收群組一覽

這一階段最終的測試分成四群，每群守住一塊承諾：

測試守住的承諾要不要 key
ScheduledTaskE2ETest排程註冊、run-now 執行、狀態與歷史持久化、停用生效不用（mock）
SchedulerFlowIT真 key 鏈路：session 重用、審計筆數、webhook 收到、失敗隔離要（真 key）
RestartRecoveryITkill／重啟後四類狀態全回來要（真 key）
多 Agent 隔離測試工具、會話、排程三條邊界不打架視情境

再配上一份 Demo 前置清單——把白名單、通知通道、MCP、記憶偏好、時區、跨重啟這六件事事先配好勾掉——demo 現場才不會被自己的沙箱白名單絆倒（沙箱預設 deny-all，最容易絆倒自己的正是它）。

收束：整台機器有了體檢報告

到這裡，全流程串聯畫下句點。上半場證明了「有人問、答得對」，下半場證明了「沒人問、也照樣幹活；重啟了、也不失憶；多 Agent、互不打架」，最後再把它們固化成一張每次 mvn verify 都會自動交出的體檢報告。「這台機器跑得穩」從讀日誌的體感，變成了一個可重複、可回歸的確定事實。下一節要換一個視角：底座是底座，Agent 是 Agent——真正「定義」一個業務 Agent，才剛剛要開始。
