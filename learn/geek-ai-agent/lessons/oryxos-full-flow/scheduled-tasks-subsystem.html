定時任務子系統：定義、執行、持久化、管理

Step 4/6 · 全流程串聯

學習目標

能把薄排程層長成完整子系統：skill 定義任務、共用 scheduler 會話執行、兩張表持久化狀態與歷史、四個端點加上管理台可即時執行與啟停。

從「會觸發」到「能管理」

第 25 節的定時任務只做到「cron 到點會觸發」，狀態全在記憶體裡，重啟就忘，也沒法看、沒法管。這一課要把它長成一個完整子系統：一個任務要能被定義、自己跑、記得起來、還能被管理。四件事對應四塊積木，我們一塊一塊看。

第一塊：定義——永遠只有 skill 一個來源

任務怎麼定義？答案跟前幾節一致：用 skill。一個任務就是 schedules 條目裡的一筆，欄位是 id + cron + zone + message，其中 message 就是要交給 AgentService.process 的提示詞。這樣做的好處是：不新增第二個定義來源——Agent 的行為由 skill 定義，排程的行為也由 skill 定義，整台機器只有一個「說清楚誰該做什麼」的地方。

第二塊：執行——共用同一個 scheduler 會話

到點之後，排程器把 message 組成一則訊息，投進跟 CLI、Web 完全同一條 AgentService.process 入口。以一個測試 Profile 每兩分鐘跑「查一下北京天氣，把穿搭建議推送出去」為例，對賬時要看到：llm_calls = 2、tool_invocations = 2（http_get + notify）、而且 webhook 真的收到推送。

這裡有兩個坑要先防。坑一：會話重用——scheduler 頻道的會話要重複使用，觸發兩次仍是同一列歷史，而不是每跑一次就開一列新會話。坑二：推送失敗隔離——若推送目標域名不在白名單內，Sandbox 會攔下，留下一筆 success=false，但排程器本身不能被拖垮，下一次觸發照常跑。

第三塊：持久化——兩張表藏在介面之後

要讓「重啟後排程還在」，狀態就得落進 SQLite。這裡有兩張手工建立的表：

  • scheduled_tasks：任務本身（task_id、profile_name、cron、zone、message、enabled、next_run_at、last_run_at、last_status、run_count）；
  • task_executions：每次執行的歷史（task_id、session_id、started_at、success、error_message、duration_ms）。

這兩張表藏在一個核心介面 ScheduledTaskStore 之後，由 storage 模組用 JPA 實作——這就是依賴倒置：核心只認介面，不知道底下是 SQLite 還是別的東西。AgentScheduler 註冊每個任務時算出 next_run_at，觸發時先檢查 enabled，跳過已停用的任務，跑完寫執行紀錄、更新狀態，另外加一個 runNow(taskId) 供手動即時執行。

第四塊：管理——四個端點 + 管理台第一個寫入頁

最後補上管理面。四個端點：

  • GET /schedules：列出所有排程；
  • GET /schedules/{id}/executions：查某排程的執行歷史；
  • POST /schedules/{id}/run：即時跑一次；
  • PUT /schedules/{id}：啟用／停用。

管理台加上「定時任務」頁，可列、可即時執行、可啟停——這正是第 26 節唯讀管理台上的第一個寫入操作頁。持久化之後，「排程重啟後還在」從「讀日誌的體感」變成一句 GET /api/v1/schedules 的確定斷言。

一張圖記住整個子系統

把四塊拼起來，這條鏈就是：cron 觸發 → 同一條 AgentService.process → ReAct → notify 推送 → 落兩張表。它跟人推鏈是同一條主幹，只是換了一個「時鐘」的頭、加了一個「推送」的尾。下一課要驗證的正是這條鏈最關鍵的承諾：狀態全在進程之外，重啟不失憶，而且多個 Agent 並存互不打架。
