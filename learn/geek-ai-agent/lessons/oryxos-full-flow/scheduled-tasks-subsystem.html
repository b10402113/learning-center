定時任務子系統：定義、執行、持久化、管理

Step 4/6 · 全流程串聯

學習目標

能把薄排程層長成完整子系統：skill 定義任務、共用 scheduler 會話執行、兩張表持久化狀態與歷史、四個端點加上管理台可即時執行與啟停。

為什麼排程要從「薄層」長成「子系統」

排程模組的定位一直很清楚：它是一個觸發源，不是新能力。時間到了，系統組裝一個訊息，投進與 CLI／Web 完全同一條 AgentService.process。ReActLoop、工具執行、Provider 全都不用改。

但「能觸發」和「能管理」是兩件事。一個只會在記憶體裡註冊 cron 的薄排程層，能應付課堂演示，卻撐不起一個底座——重啟之後任務就不見了，出了幾次執行、成不成功也沒人知道，更別提在管理台即時跑一次或臨時停掉。要讓底座「沒人問也照樣幹活」，排程必須長成完整子系統，而完整子系統要同時具備四塊：定義、執行、持久化、管理。

第一塊：定義——仍然只有 skill 一個來源

定義一個定時任務，不需要新的設定檔，也不需要在 Java 裡寫常數。做法仍然是 skill：一個任務 = 一條 schedules 條目，內容是 id + cron + zone + message。

其中 message 就是到點時要交給 AgentService.process 的 prompt。這點很重要：排程層不決定訊息寫什麼，它只是把這條訊息端到引擎面前。任務的「內容」屬於 Agent 的定義，「何時觸發」才是排程的職責。

紀律：定義排程永遠不新增第二個定義來源。如果 cron 一下子來自設定檔、一下子來自 Java 註解，之後你就會有兩個地方要改，而且它們遲早會不一致。

第二塊：執行——同一條入口，換一個頭

用一個測試 Profile 每兩分鐘觸發一次，訊息是「查一下北京天氣，把穿搭建議推送出去」。這一趟的對賬預期是：

痕跡預期
scheduler 渠道的 session被重用——第二次觸發會 append 到同一份歷史，而不是另開一個
llm_calls2 筆（先決定查天氣、再依結果組推送內容）
tool_invocations2 筆：http_get（查天氣）與 notify（推送）
webhook真的收到推送

這裡有兩個最容易踩的陷阱。

陷阱一：session 重用。排程不是每次觸發都開新對話。它固定用同一組 session 身分（渠道 scheduler），所以兩次觸發仍然是同一列 session，歷史被續寫。若對賬時發現 session 變成兩筆，就代表 session 身分沒有固定。

陷阱二：推送失敗拖垮排程。如果推送目標的網域不在白名單內，Sandbox 會擋下，留下一筆 success=false。這正是要的——一次推送失敗不該把排程器本身弄掛，下一次觸發照常進行。

第三塊：持久化——兩張表，一個介面

要讓「重啟後排程還在」變成事實，狀態必須落到 SQLite。這裡手工建兩張表：

表欄位
scheduled_taskstask_id、profile_name、cron、zone、message、enabled、next_run_at、last_run_at、last_status、run_count
task_executionstask_id、session_id、started_at、success、error_message、duration_ms

關鍵在架構而非欄位：這兩張表背後是一層 core 介面 ScheduledTaskStore，真正的 JPA 實作放在 storage 模組。這是依賴倒置——核心定義「我需要能存排程狀態與執行歷史」，具體怎麼存由儲存層決定。核心因此不必認識任何 ORM 註解。

對應地，AgentScheduler 的職責也從「只讀 cron」擴充成：註冊時算出 next_run_at、把流程拆成「檢查 enabled → 才執行」、跳過被停用的任務、寫入執行紀錄並更新狀態，另外加上一個 runNow(taskId) 供即時觸發。

第四塊：管理——四個端點與第一個寫操作頁

有了持久化，管理就有東西可管。四個端點：

  • GET /schedules：列出所有任務
  • GET /schedules/{id}/executions：看某個任務的執行歷史
  • POST /schedules/{id}/run：立刻跑一次
  • PUT /schedules/{id}：啟用／停用（或修改）

管理台再補上一個「定時任務」頁：列出任務、即時執行、啟用／停用。這是先前那版唯讀管理台的第一個寫操作頁面——它會改變系統狀態，因此也象徵管理台開始從「看板」邁向「控制台」。

收斂成一句

排程子系統的四塊其實共用兩條紀律：定義永遠只有 skill 一個來源；儲存永遠藏在介面之後。做到這兩條，持久化帶來的回報就是——「重啟後排程回來了」不再是靠讀日誌猜的體感，而是一句 GET /api/v1/schedules 就能對平的斷言。這也為下一課的跨重啟恢復鋪好了路。
