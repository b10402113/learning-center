全流程串聯：真能用的標準與對賬方法

Step 1/6 · 全流程串聯

學習目標

能用一個可證偽的標準定義「主流程真能用」，並用對表與逐表對賬兩步方法，判斷一台組裝好的 Agent 底座是否真的打通。

為什麼單模組測試全綠，還是不敢說「能跑」

走到這裡，Provider、ReAct、CLI、Notify、Tool、Memory、Sandbox、排程、Web Service 每一層都有自己的驗收測試，而且都是綠的。但這只證明「每個零件單獨裝在測試台上會動」，不證明「這些零件接成一條線之後整台機器會動」。

原因很簡單：縫隙從來長在兩個模組的交接處，而不是任何一個模組內部。單模組測試各自把邊界 mock 掉了，恰恰把最容易出事的那一段遮住。所以「全流程串聯」這一課不新增任何能力，它要做的事只有一件——把零件裝成一台機器，並且證明它真的會動。

先給「真能用」下一個可證偽的標準

「能用」如果只是一種感覺，就沒法驗收。所以要先把感覺翻譯成三條可以當場檢查的斷言，而且三條必須同時成立：

#斷言怎麼檢查
1答得出來問一句有代表性的話，系統走完整條鏈並真的給出答案（例：兩個模型回合 + 一次工具呼叫）
2帳記得對這一趟在 sessions、llm_calls、tool_invocations 留下的痕跡，數量與內容恰好符合預期
3三面同源同一份資料，從 CLI、REST、管理台三個入口看過去完全一致

這三條把「能跑」變成一句可以被推翻的話。任何一條不成立，就是這台機器還沒組裝完，而不是「差不多可以了」。

第一步：對表——整合前先確認每個模組都在位

動手把模組接起來之前，先花十分鐘做一件看似多餘的事：把前面每一課的驗收清單壓縮成一份點名表，逐項確認「這個模組當初承諾的對外能力，現在還在」。這叫對表。

為什麼值得？因為你要裝的是一台機器，不是一堆零件。裝上一顆壞零件，之後每一次失敗都會變成假警報——你以為是接線接錯，其實是零件本來就壞的。先把零件驗乾淨，後面的問題才指向真正的縫隙。

模組要確認在位的能力
Provider顯式映射路由正確、自動工具執行已關閉、成功與失敗都寫 llm_calls
ReAct達最大迭代有回退處理、每一輪結果累積回 Session
CLI輕／重命令切分正確、能進能出
Notifywebhook 推送可用、渠道未設定時有清楚錯誤
Tool內建工具可呼叫、三種來源統一成 OryxTool
Memory核心記憶恆在、先寫後讀且不走快取
Sandbox三條白名單確實攔截、違規寫進 tool_invocations
Schedulercron 到點會觸發、本地鎖避免疊跑
Web Service端點齊全、錯誤 JSON 統一、Vue 管理台已建進 static/admin/

任何一格沒打勾，就回去那一課先修好，不要帶著它往下整合。

第二步：對賬——拉一句對話走一遍，逐站核對痕跡

對表是靜態的點名，對賬是動態的實測。對賬的做法是：挑一句真的有代表性的話，讓它從入口走到出口，然後在每一個該留下痕跡的站點，核對「痕跡對不對」。

這句代表性的話是：「今天北京天氣怎麼樣，穿什麼合適」。它好在哪裡？它既需要查外部資料（觸發工具），又需要模型做兩次判斷（先決定要不要查、再根據結果組答案），剛好把主流程的關鍵分支都走過一遍。在 oryxos chat 裡問出這句話之後，逐張表核對：

表／檔案預期痕跡
sessions恰好 1 筆記錄，含完整歷史：使用者問句、兩則模型回覆、一筆天氣結果
llm_calls恰好 2 筆（先決定是否呼叫工具、再組答案），同一 session id、皆成功、token 非零
tool_invocations恰好 1 筆（http_get 查天氣），成功、延遲正常
MEMORY.md沒有被改動——這趟對話不涉及記憶

對賬最容易被忽略的一半：不該有的不能有

很多人對賬只做一半：確認「該有的都在」。但紀律是雙向的——「該有的要在」與「不該有的不能有」同等重要。多一筆和少一筆一樣都是 bug。

以上面的例子來說，llm_calls 若出現 3 筆，代表迴圈多繞了一圈；tool_invocations 若出現 2 筆，代表工具被重複執行（常見於自動工具執行沒關乾淨）；MEMORY.md 若被動到，代表有東西在不該寫記憶的時候寫了記憶。這些「多出來的痕跡」往往比缺漏更難查，因為系統表面上「跑成功了」，只有對賬會把它抓出來。

換一條入口再對一次帳

CLI 對完，接著用 REST 再走一遍：POST /sessions 建會話、POST /sessions/{id}/messages 送同一句話，然後再做一次同樣的逐表核對，確認結果一模一樣。

這一步的價值不只是「REST 也能用」，而是把「兩個入口共用同一個引擎」從一句口號，變成一筆當場可以對平的帳。CLI 與 Web 最後都收在 AgentService.process 這一個編排入口上，所以兩條入口留下的痕跡應該完全一致；只要有一處不同，就代表某條入口偷偷多做了事。

為什麼要把「對賬」講得這麼細？因為它是後面所有整合工作的通用方法。同一套手法之後會用來驗排程鏈、驗重啟恢復、驗多 Agent 並存——差別只在於「換哪一句觸發、對哪幾張表」。

把這套方法收進口袋

這一節的收穫不是新程式，而是一套可重複的驗收姿勢：先對表（靜態點名），再對賬（動態核對），而且兩個方向都要看。接下來兩課會分別處理「對賬時最常撞到的五條縫隙」與「讓對賬可自動化所需的查詢端點與管理台」，最後再把它固化成每次 mvn verify 都會回答的測試。
