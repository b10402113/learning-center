全流程串聯：真能用的標準與對賬方法

Step 1/6 · 全流程串聯

學習目標

能用一個可證偽的標準定義「主流程真能用」，並用對表與逐表對賬兩步方法，判斷一台組裝好的 Agent 底座是否真的打通。

單元測試全綠，不代表機器會動

走到這一步，OryxOS 已經把九個模組都立起來了：Provider 抽象、ReAct 迴圈、CLI、Notify、Tool、Memory、Sandbox、定時任務、Web Service。每一個模組都有自己的測試，而且都綠燈。問題是：每個零件單獨驗過，跟把它們裝成一台機器之後會不會動，是兩件事。

縫隙從來不長在任何一個模組「內部」，而長在兩個模組的「交接處」。Provider 把結果交給 ReAct、ReAct 把工具呼叫交給 ToolExecutor、ToolExecutor 把留痕寫進審計表——每一條交接地帶都可能悄悄漏掉一筆。單元測試看不到這些，因為它每次只讓一個模組上場。

什麼叫「真能用」：一個可證偽的標準

「跑得起來」這種說法太模糊，無法驗收。所以要先把「真能用」定義成一個可以被推翻（可證偽）的具體標準。挑一句有代表性的話——「今天北京天氣怎麼樣，穿什麼合適」——它必須同時滿足三件事：

  • 答得對：這句話會走完「想 → 查 → 答 → 記帳」整條鏈，觸發兩次 LLM 呼叫（第一次決定要不要查、第二次把答案組織出來）加一次工具呼叫（查天氣）。
  • 記帳正確：沿途留下的痕跡在 sessions、llm_calls、tool_invocations 三張表裡，一筆不多、一筆不少。
  • 三面同源：CLI、REST、管理台這三個入口，看到的都是同一份資料。

這三件事必須同時成立，缺一不可。這就是「真能用」的定義——不是一句口號，而是一份可以被自動斷言檢查的清單。

第一步：對表，先確認每個模組都在位

動手串聯之前，花十分鐘做「對表」：把前面每一節的驗收清單濃縮成一行行，逐行確認每個模組承諾的對外能力還在位。這張表本身就是一張跨模組的能力地圖：

模組要確認的對外承諾
Provider顯式映射路由正確、自動工具執行關閉、成敗都寫 llm_calls
ReAct達上限有 fallback、每輪結果累積回 Session
CLI輕／重命令切分、對話能進能出
NotifyWebhook 能推、通道未設定時錯誤清晰
Tool九個內建工具可呼叫、三個來源統一成 OryxTool
Memory核心記憶恆在、寫入後立刻讀得到（無快取）
Sandbox三張白名單強制生效、違規寫進 tool_invocations
定時任務cron 會觸發、本地鎖防重疊
Web Service10 個端點、統一錯誤 JSON、Vue 產物在 static/admin/

任何一行沒勾上，代表那個零件是壞的，就該先回那一節修好。用一個壞零件裝機器，後面每一次故障都會是「假警報」——你永遠分不清是整合錯了，還是零件本來就壞。

第二步：對賬，拉一句話走一遍、逐表核對

對完表之後才真正拉對話。在 oryxos chat 裡問那句代表句，然後逐表對賬，把每一張表該出現的痕跡核對一遍：

檢查點期望值
sessions恰好 1 筆，歷史完整（用戶問題、兩則模型回覆、一次天氣結果）
llm_calls恰好 2 筆，同一 session id、都成功、token 非零
tool_invocations恰好 1 筆（http_get 查天氣），成功、延遲正常
MEMORY.md不變——這段對話不涉及記憶，動了就代表有東西不分青紅皂白在寫記憶

接著再用 REST 重跑一遍（POST /sessions 加 POST /sessions/{id}/messages），確認對賬結果一模一樣。這證明了「兩個入口共用一顆引擎」不是口號，而是一筆你算得清的帳。

紀律：該有的要在，不該有的不能有

對賬這門功夫有一條最反直覺、卻最重要的紀律：「該有的痕跡要在」和「不該有的痕跡不能有」同等重要。多一筆跟少一筆，一樣都是 bug。少了 llm_calls 代表審計漏寫；多了一筆 tool_invocations 代表某個工具被重複執行、或某處不該寫記憶卻寫了。

把這條紀律刻進心裡，整合期的除錯才會從「到處猜」變成「逐表算」：每一張表都是一本帳，帳對得上，機器才真的打通。下一步我們看對賬時最容易撞上的五條典型縫隙——症狀都出現在執行期，根因卻都在交接處。
