三面同源：補列會話端點與管理台

Step 3/6 · 全流程串聯

學習目標

能說清「一進程兩面」的啟動模型，實作列出會話的 GET /api/v1/sessions 端點，並讓 CLI、REST、管理台三面顯示同一份資料。

為什麼要為了對賬補一個端點

上一課的對賬是人工的：打開資料庫，逐張表數筆數。人工對賬可以偶爾做，卻沒法每次都做，更沒法進 CI。要讓「三面同源」變成可以自動化驗證的東西，前提是——每一條痕跡都必須先有一個可以查的 HTTP 端點。

沒有端點，就沒有東西可以被斷言；不能被斷言，就只能靠人看。所以這一課要補的其實不是一個「功能」，而是把對賬從「人看」升級成「網頁／測試看」所缺的最後一格。

先盤點：10 個端點裡缺了哪一個

Web Service 那一課給了 10 個端點，涵蓋會話明細、記憶、工具、Profile、系統狀態。把它們列出來逐一對照「管理台需要看什麼」，會發現只有一個缺口：「列出所有會話」。

原本只有「依 id 查單一會話」（GET /sessions/{id}），卻沒有「列出會話清單」。結果就是管理台的會話頁永遠是空的——它拿得到某一個會話，卻不知道有哪些會話存在。

修法很直接：新增 GET /api/v1/sessions，回傳一份會話摘要清單。

這個端點長什麼樣

項目設計
排序依最後活躍時間（last-active）倒序，最近的排前面
預設數量100 筆摘要
回傳欄位session id、Profile 名稱、渠道、使用者、狀態、建立／最後活躍時間、訊息數
不回傳完整對話正文（那是明細端點的事）
可選過濾?status=active

為什麼只給摘要、不給全文？因為列表頁和對賬要回答的問題是「有哪些會話、各自多大、最近什麼時候動過」，而不是「某一句話講了什麼」。把全文塞進列表，既拖慢回應，也讓欄位失去焦點。要看正文，走既有的明細端點。

實作只加三樣東西

這個擴充刻意做得跟上一課的 archive()／readAll() 一模一樣，維持同一種擴充模式：

  1. SessionManager.listRecent(int)：底層透過 SessionRepository 撈出最近若干筆。
  2. 一個沒有 {id} 路徑變數的 @GetMapping：這就是與明細端點唯一的分野。
  3. 一個 session-summary DTO：把清單要的欄位挑出來，不直接把整顆 Session 丟出去。

注意這裡沒有任何業務邏輯進到 Controller：它只做「驗參數、包回應、交錯誤」，真正的查詢落在 SessionManager。這條紀律在整條主線上反覆出現——加端點不能讓引擎分岔。

一進程兩面：Web Service 與管理台是同一個進程

管理台不是另一個服務。oryxos serve 起的這一個 Spring，同時服務兩件事：/api/v1/** 的 REST 介面，以及 /admin 的管理台頁面。沒有第二個進程、沒有第二份部署。

這個模型直接決定了「三面同源」為什麼成立：CLI、REST、管理台看到的都是同一顆引擎、同一個資料庫裡的同一份資料。管理台只是換一個視角把它畫出來。

啟動管理台是「建置」，不是「打開網頁」

很多人第一次會卡在這裡：以為開瀏覽器連 /admin 就會有頁面。其實要先把它建出來：

  1. 前端執行 npm run build，產物輸出到 oryxos-web/src/main/resources/static/admin/。
  2. Spring 托管 /admin，並把未匹配的 /admin/** 一律 fallback 到 index.html——這樣前端自己的路由（例如 /admin/sessions）直接輸入網址也不會 404。/api/v1/** 不受這個 fallback 影響。

另外有兩個前置條件，缺一個管理台就空轉：

  • export DEEPSEEK_API_KEY=...：因為啟動時排除了 Spring AI 的 OpenAiAutoConfiguration，服務只認這把 key。
  • 前端已經建置到 static/admin/。

完整的啟動流程

把上面的步驟串起來：建置前端 → mvn clean package -DskipTests → java -jar oryxos-boot/target/oryxos-boot-*.jar serve --port 8080。起來之後用 curl .../health 確認活著，再開 /admin 與 /swagger-ui。

這裡的發布形態是「一個 jar 托管全部」：前端產物被打進 jar，REST 與頁面同源。所以文件要記載的發布方式是這個 jar，而不是開發者本機的 npm run dev——後者只是開發時的熱更新，不是交付形態。

收尾：第三個視角正式上線

補完端點、建好管理台之後，在管理台打開「會話」頁，應該看到剛剛那筆天氣／穿搭對話——跟 CLI、REST 看到的一模一樣。這一刻，「同資料、同引擎、第三個視角」的三面同源才算真正落地，而且因為有了 GET /api/v1/sessions，這份一致性從此可以被自動斷言，而不是靠人再看一遍。
