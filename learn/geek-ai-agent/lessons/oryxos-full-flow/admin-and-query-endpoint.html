三面同源：補列會話端點與管理台

Step 3/6 · 全流程串聯

學習目標

能說清「一進程兩面」的啟動模型，實作列出會話的 GET /api/v1/sessions 端點，並讓 CLI、REST、管理台三面顯示同一份資料。

為什麼要補「列出會話」這個端點

上一課說對賬是「逐表核對」，可是要自動核對，就得先能問得出來。回顧 Web Service 的 10 個端點：查單一會話、查記憶、列工具、列 Profile 都有，唯獨「列出所有會話」是缺口——第 26 節只有「依 id 查一個」，所以管理台的「會話」頁一直是空的。

這不是小事：一個痕跡若沒有可查的端點，就永遠只能靠人讀日誌，無法變成自動斷言。所以這課補上 GET /api/v1/sessions，讓「三面同源」可以真正被驗證。

一進程兩面：Web 與管理台共用同一個 Spring

先搞清楚管理台是怎麼跑起來的。很多人以為管理台是另一個獨立服務，其實不是：oryxos serve 一個進程同時服務兩面——同一個 Spring 既處理 /api/v1/** 的 REST，也提供 /admin 的頁面，不需要第二個進程。

管理台的啟動是「建置」而不是「開網頁」：先 npm run build 把前端產物輸出到 oryxos-web/src/main/resources/static/admin/，Spring 接著託管 /admin，並把未命中的 /admin/** 路徑回退到 index.html——這樣前端路由才不會 404，而 /api/v1/** 完全不受影響。

兩個前置條件，缺一就閒置

這台機器要真的動起來，有兩個前置條件：

  • export DEEPSEEK_API_KEY=...——因為 OpenAiAutoConfiguration 被排除了，不設 key 引擎就沒有模型可呼叫。
  • 前端已經 build 進 static/admin/——沒建置，/admin 就是一片空白。

完整的啟動序列是：建置前端 → mvn clean package -DskipTests → java -jar oryxos-boot/target/oryxos-boot-*.jar serve --port 8080 → 用 curl .../health 確認健康 → 打開 /admin 與 /swagger-ui。

補上 GET /api/v1/sessions

這個端點的職責是「列出會話摘要」：按最後活躍時間遞減排序，預設回傳 100 筆摘要（session id、Profile 名稱、channel、user、狀態、建立／最後活躍時間、訊息數），不含完整對話內文，另可帶 ?status=active 過濾。

實作沿著第 26 節 archive()／readAll() 的同一套擴充模式走：

  • SessionManager.listRecent(int) 經 SessionRepository 查最近 N 筆；
  • 一個不帶 {id} 的 @GetMapping；
  • 一個 session-summary DTO 把內文剝掉、只留摘要。

補上之後，管理台的「會話」頁就接到這個端點，跟 CLI、REST 看到同一批會話——這就是三面同源的落點。

三面同源 = 一個引擎 + 每個痕跡都可查

把這一課的收穫歸成一句話：三面同源不是把資料複製三份，而是三個入口讀同一顆引擎。CLI、REST、管理台都不是資料的「源頭」，真正的源頭是引擎背後的 SQLite 與檔案；三個入口只是三扇不同的窗，望向同一個房間。要做到這點，每個痕跡都得先有可查的端點——補上 GET /api/v1/sessions 就是補上這扇窗的最後一塊玻璃。
