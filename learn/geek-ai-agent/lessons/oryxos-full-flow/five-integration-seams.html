五條典型縫隙與單一來源修法

Step 2/6 · 全流程串聯

學習目標

能認出整合期最常見的五條縫隙（JPA 掃描、工具重複執行、session id 不一致、Bootstrap 靜默跳過、失敗路徑缺審計），並說出每一條對應的單一來源修法。

症狀在執行期，根因在交接處

把模組接起來之後，你會撞到的 bug 有一個共同長相：症狀出現在執行期，但根因從來不在出症狀的那個模組裡，而在兩個模組的交接處。這正是為什麼單模組測試抓不到它們——每個模組單獨看都對，兩個接在一起才錯。

下面五條是整合時最常撞到的縫隙。它們看似無關，卻都收斂到同一種解法：把某件事的決定權收回到唯一一個地方（單一來源）。認出「這是哪一種單一來源被破壞」，你就能自己修沒見過的第六條。

縫隙一：啟動時 Found 0 JPA repositories

症狀。服務能啟動，但日誌裡出現 Found 0 JPA repositories，接著任何用到資料庫的操作都失敗。

根因。啟動類上的 scanBasePackages 只會掃描 Spring 的元件，它拖不動 JPA 自己的 @EnableJpaRepositories 與 @EntityScan。你的 Repository 和 Entity 明明存在，卻被掃描範圍漏掉了。

修法。在啟動類上顯式聲明兩者各自的 basePackages，不要指望一個 scanBasePackages 包辦三種掃描。

驗收。日誌裡的 repository 數量必須大於 0（例如 Found N JPA repositories，N > 0）。看到 0 就是還沒修好。

縫隙二：工具被執行兩次

症狀。一次對話裡，同一個工具被呼叫了兩次，結果重複。

根因。Spring AI 的自動工具執行沒有被完全關閉。這個坑在 Provider 那一課就埋過雷：只要你用 ChatClient 的「自動工具執行」寫法，框架會自己跑一次工具，而你的 ToolExecutor 又跑一次。

修法。確認工具執行權只存在於 ToolExecutor 一處。Provider 只負責呼叫模型、拿回意的 tool call，實際執行交給 ToolExecutor。回到 Provider 一課，把自動執行關乾淨。

驗收。對賬時 tool_invocations 的筆數要恰好等於預期（天氣對話恰好 1 筆）；出現 2 筆就是這個坑復發。

縫隙三：同一個使用者分裂成兩份歷史

症狀。同一個人在 CLI 問過的話，到了 REST 或管理台卻看不到；或反過來，兩邊各自長出一份自己的歷史。

根因。session id 不是隨手取的，它有固定結構——「渠道 + 使用者 + Profile」三者組合而成。如果 CLI 和 Web 各自用自己的方式拼接這個 id，同一個使用者就會被算成兩個不同的 session，歷史自然對不上。

修法。id 只在 SessionManager 裡生成一處；各入口傳進來的是三個原料（渠道、使用者、Profile），而不是自己拼好的字串。這樣無論從哪條入口進來，同一組原料一定得到同一個 id。

驗收。CLI 建一個 session，用 REST 依同一個 id 查得到，且管理台顯示的是同一筆。

縫隙四：Bootstrap 檔被靜默跳過

症狀。Agent 的人格（persona）莫名其妙消失了，回答的語氣與設定完全不同，但沒有任何錯誤訊息。

根因。Bootstrap 檔（例如定義人格的 SOUL.md）如果不存在，ContextLoader 會安靜地略過它。既然沒有人報錯，也就沒有人知道人格已經悄悄不見了。

修法。缺失至少要在日誌留下 WARN；如果某個 Profile 顯式引用了一個不存在的檔案，就該直接硬性報錯，而不是吞掉。無聲的降級是最危險的降級。

驗收。故意移除一個被引用的 Bootstrap 檔，啟動時應該看到明確警告或錯誤，而不是安靜地跑起來。

縫隙五：審計只記了成功那一半

症狀。一切正常時審計表看起來很完整；一旦出錯，卻查不到任何痕跡。

根因。整合時很容易只顧著讓「成功路徑」跑通，忘了失敗路徑也要留痕。而審計的價值恰恰在出錯的時候——Provider 逾時、Sandbox 攔截、工具拋例外，這些都應該留下一筆 success=false 的紀錄。

修法。把失敗路徑當成一等公民來對賬：主動製造這三種失敗（Provider 逾時、Sandbox 阻擋、工具例外），逐一確認每一種都留下 success=false，而且系統不會因此崩掉。

驗收。三種失敗各觸發一次，對應的表上都有一筆失敗紀錄。

把五條收斂成一句

縫隙被破壞的單一來源
Found 0 JPA repositories掃描範圍只宣告了一處，漏掉另外兩種
工具被執行兩次工具執行權有兩個地方（框架 + ToolExecutor）
session id 不一致id 生成散落在各入口，而非 SessionManager
Bootstrap 靜默跳過檔案缺失的決定被吞掉，沒有單一負責人發聲
失敗路徑缺審計審計的單一義務只覆蓋成功一半

所以修法不是逐個打補丁，而是把每件事的決定權收回唯一一處。這也是下一課要延續的主題：要讓對賬能自動化，每條痕跡都得先有一個可查的單一端點。
