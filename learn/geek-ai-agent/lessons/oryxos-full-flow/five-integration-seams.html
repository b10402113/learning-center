五個典型 gap 與單一來源修法

Step 2/6 · 全流程串聯

學習目標

能認出整合期最常見的五個 gap（JPA 掃描、工具重複執行、session id 不一致、Bootstrap 靜默跳過、失敗路徑缺審計），並說出每一條對應的單一來源修法。

症狀在執行期，根因在交接處

串聯時最難修的 bug，問題往往不在任何一個模組內部，而在兩個模組的交接處。單元測試各自都過，拼起來就出事。以下是整合期最常見的五個 gap。

gap 1：Found 0 JPA repositories

啟動時明明寫了 @EnableJpaRepositories 和 @EntityScan，卻找不到任何一個 JPA repository。問題出在 Spring Boot 的 scanBasePackages：掃描主類所在的套件時，它不會自動把 JPA 的 repository 與實體掃描一起拖過來。

做法是把依賴的 basePackages 在啟動類上明確宣告，不要靠「猜」。驗收標準是啟動日誌裡掃到的 repository 數量 N > 0；看不到 N 大於零，就代表這個 gap 還在。

gap 2：工具被調了兩次

同一個工具在同一次對話裡跑了兩次，結果重複。原因出在 Spring AI 的自動工具執行沒關乾淨：引擎自己排程了工具，Spring AI 又幫你跑了一遍。

要把執行權收回單一來源：工具該不該跑、什麼時候跑，只由 ToolExecutor 決定。任何繞過它的第二條執行路徑都要砍掉。判斷標準很簡單：一次對話裡某個工具的 tool_invocations 應該恰好一筆。

gap 3：session id 前後不一致

同一段對話，CLI 查到的歷史跟 Web 查到的不一樣，好像被劈成兩半。問題出在 session id 的組成方式「channel + user + Profile」：如果 CLI 和 Web 各自把三段拼一次，只要拼法有一絲不同，同一個用戶就會被拆成兩條歷史。

把 id 的產生收到一個地方：SessionManager。其他入口只負責把 channel、user、Profile 三個「原料」傳進來，由 SessionManager 統一拼出 id。拼法只有一種，結果就只有一種。

gap 4：Bootstrap 檔案被靜默跳過

Agent 的人格突然「消失」，開始用最平庸的語氣回答。問題常出在 SOUL.md 這類 Bootstrap 檔案不存在，而 ContextLoader 遇到缺檔時選擇靜默跳過，人格就悄悄不見了，也沒人發現。

缺檔要有聲：檔案缺失時至少要印一條 WARN；當某個 Profile 明確引用了一個不存在的檔案時，要直接報硬錯誤，而不是當作沒這回事。

gap 5：失敗路徑缺了審計

成功的呼叫都留下痕跡，失敗的卻一片空白。整合期最需要留痕的偏偏就是失敗路徑：Provider 逾時、Sandbox 攔截、工具拋例外，每一種都該留下一筆 success=false 的紀錄。

審計要記帳到失敗那一半：把三種失敗模式（Provider 逾時、Sandbox 阻擋、工具例外）都實際造出來，逐一確認它們各留了一筆失敗紀錄、且沒有把整台機器拖垮。少記一筆失敗，就跟多記一筆成功一樣是 bug。

共同的修法：單一來源

這五個 gap 的根因是同一個：同一件事的決定權被分散到兩個以上的地方。JPA 掃描、工具執行、session id、Bootstrap 加載、審計留痕，每一件都該只有一個來源。

下一課把同樣的紀律用在一個具體問題上：讓 CLI、REST、管理台三個入口顯示同一份資料。要真正做到「三面同源」，靠的是一個引擎，加上每個痕跡都有可查的端點。
