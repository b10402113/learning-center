為什麼訊息要先落地：StoragePlugin 契約

Step 1/5 · 存儲與元數據

學習目標

能說明延遲訊息為何必須先寫入儲存才能進記憶體與回傳，並說出 StoragePlugin 五個方法各自的職責。

一個會消失的承諾

先想像一個場景。使用者送出一筆「三天後提醒我續約」的延遲訊息。排程節點收到之後，把它放進記憶體裡的時間輪，回報「已受理」。三天之內，這個節點因為部署更新重啟了一次，記憶體裡的時間輪跟著清空，那筆提醒就此人間蒸發。使用者不會收到任何錯誤，因為系統當下確實回了「已受理」。

延遲訊息和一般請求最大的差別，就在這裡：它是一張「未來的兌現承諾」，從接單到履約之間可能隔好幾個小時、甚至好幾天，而這段時間裡節點幾乎不可能不重啟。如果記憶體是唯一的真相，那承諾隨時會被重啟吃掉。

延遲訊息必須在進入記憶體之前先落地。重啟可以丟掉記憶體，但不能丟掉已經答應別人的訊息。

落地不變量：先寫儲存，再進記憶體

When 把這件事寫成一條不變量：任何進入記憶體時間輪的訊息，儲存裡一定已經有一份。落地的東西除了訊息本體，還有排程索引；重啟之後，系統得靠它知道「哪些訊息還在等、分別等到什麼時候」。

要做到這件事，寫入的順序就沒有模糊空間。呼叫方送進來的訊息，一定先寫進 Redis，確認成功之後才放進記憶體、才回報受理。反過來（先進記憶體、後寫 Redis）會出現最糟的情況：使用者看到受理，節點一重啟訊息卻不見了，而且儲存裡完全沒有線索可以補救。

Redis 短暫不可用時，這個設計也給出明確的行為：寫入失敗就讓 API 回錯，由業務呼叫方自行重試。這種「寧可當下失敗」的策略叫 fail-down，重點是不要產生「記憶體有、儲存沒有」的幽靈訊息。

為什麼要把儲存做成插件

企業用的基礎設施五花八門：有人只有 Redis，有人有 RocksDB，有人想接自己的 MySQL。如果呼叫方直接綁死一個 Redis client，換儲存就等於改一輪程式碼。

When 的作法是把它抽象成 StoragePlugin：上層只依賴這個介面，完全不知道背後是 Redis 還是別的。要換一套儲存，只是多寫一個實作類別，排程、投遞、路由那些模組一行都不用動。這是典型的埠與配接器（port/adapter）模式：介面是埠，Redis 實作是插上去的配接器。

StoragePlugin 的五個資料方法

介面本身定義在公共契約裡，這個模組的任務是「實作它」，而不是重新定義它。資料操作有五個方法，外加一個 type() 用來標識這是哪種儲存（Redis 實作回傳 "redis"，由插件註冊表載入）。

方法做什麼誰會用到
create(Message)把訊息寫進儲存，成功後才進記憶體接入層在回覆受理前
get(messageId)依 id 讀回訊息本體查詢、除錯、補救
transition(messageId, expected, target, patch)狀態等於預期值時才更新，並原子地補上重試次數等欄位投遞、故障轉移
loadPendingByTimeWheel(twId)撈出這一輪裡「還在等排程」的 PENDING 訊息節點重啟、故障轉移後的恢復
deleteExpired(messageId)終態訊息過了保留期後，刪掉本體與索引清理排程工作

一句話看五個方法的關係：create 負責進場，get 負責查，transition 負責原子地改狀態，loadPendingByTimeWheel 負責重啟後把還在等的訊息撈回來，deleteExpired 負責收尾清理。

為什麼第一個插件是 Redis

延遲訊息對儲存有三個硬需求：寫得快、單一 key 的讀寫快、要有 TTL 可以自動清理。Redis 三個都滿足，而且到處都裝得到。RocksDB 速度也好，但要另外部署維運；MySQL 面對大量隨機的小 key 讀寫相對吃力。所以第一個插件選 Redis，其餘的留給之後按需要補。

這個模組的邊界也要說清楚：它只做儲存插件。時間輪排程、Sink 投遞、叢集協調、故障切換都不在這裡；Redis 自己的高可用（Cluster／Sentinel／AOF／異地備援）也交給部署方，插件只管單機或主從。
