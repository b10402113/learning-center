元數據與訊息資料的分工：ZK、etcd、Consul 選型

Step 4/5 · 存儲與元數據

學習目標

能說出元數據與訊息資料在一致性與生命週期上的差異，並用能力契合度與維運負擔比較 ZK／etcd／Consul 後選出 etcd。

兩種資料，兩種完全不同的需求

When 叢集要處理的資料其實分成兩大類，而它們的性格幾乎相反。

訊息資料叢集元數據
內容延遲訊息本體與排程索引節點清單、Controller、時間輪分配、叢集組態
數量極大，數百萬則極小，相對訊息量微不足道
生命期短，投遞完就該清掉與叢集同壽命，有人上線下線就變
最在意寫得快、讀得快一致性、變更通知、存活判斷
放哪裡Redisetcd

把兩者混在一起放，會兩邊都做不好：用 Redis 存元數據，得到的是一致性不足與沒有可靠的變更通知；用 etcd 存訊息，等於拿一台需要 Raft 共識的協調服務去扛海量短命資料，成本高又不必要。所以 When 做的是分流：大量求快的進 Redis，少量要強一致的進 etcd。

元數據到底存哪四類東西

  • 節點註冊：每一台還活著的節點一筆記錄，含 IP、port、啟動時間、負載，並綁一個 Lease（租約），讓節點意外掛掉時記錄自動消失。
  • Controller：目前哪一台節點是 Controller，同樣綁 Lease。
  • 時間輪 metadata：每一輪的 Master／Slave 分配與狀態，是持久資料。
  • 叢集組態：副本數、時間輪數量等，持久但可以動態調整。

這裡的重點是「誰該綁 Lease、誰該持久」。會隨節點生死消失的（節點、Controller）用 Lease；代表叢集組態、必須長期存在的（時間輪、config）就持久保存。搞混這兩種生命週期，後面註冊與選舉的模組就會一團亂。

ZK、etcd、Consul 比一比

方案強項弱點
ZooKeeper成熟、生態完整（Kafka、Pulsar 都用它）API 偏底層、client 複雜、維運負擔重
etcd雲原生事實標準（K8s 核心）、API 簡單、內建 Raft設計目標較專注，不主打服務發現生態
Consul服務發現與健康檢查很強協調語意不若 etcd 直接

三套其實都能做協調。差別在於「誰的原語最貼合這個專案」。etcd 提供的就是 Put／Get／Watch／Lease 這幾件事，client 很輕，內建 Raft 直接給你強一致性，維運負擔最輕；而且只要環境裡跑 K8s，etcd 本來就在。ZooKeeper 不是不好，是這個專案不需要為它付那筆維運學費；Consul 則是強在服務發現，跟這裡要的協調語意有一點距離。

選型的重點在能力曲線是否貼合需求，以及維運代價能不能接受。

有一個容易搞錯的細節：When 用的是獨立、或平台另外提供的業務 etcd，不會去連 Kubernetes 控制平面自己的 etcd。控制平面的 etcd 是叢集的命脈，拿它來存業務資料，等於把自家的延遲訊息壓在整個 K8s 的心臟上。

Lease 與 Watch 為什麼剛好夠用

etcd 的兩個原語，正好對上叢集最需要的兩件事：

  • Lease（租約）：替一個 key 設定期限。節點只要持續續約，key 就一直有效；節點一旦停止續約（掛了、斷線、被隔離），Lease 到期後 key 自動被刪除。這等於一個不用自己寫的存活探測器。
  • Watch（監看）：訂閱某個 key 或整段前綴的變化，有人新增或刪除時立刻收到通知。節點上下線、Controller 換人，其他節點能馬上知道，不必輪詢。

把這兩個原語組合起來，後面章節要做的節點註冊、存活偵測、Controller 選舉、成員變更通知，就都有現成的積木可用。這是選 etcd 的核心理由：它的原語集合跟需求一對一對上。

這個模組做到哪裡為止

職責界線要劃清楚：這個模組只做選型結論 + 元數據 key space 契約 + etcd client 封裝 + 測試。節點註冊的流程、Controller 怎麼選、故障怎麼感知，都留給下一個模組；etcd 自己的高可用（三節點容忍一台故障）屬於部署責任，不在程式範圍裡。這樣切，是為了讓後面所有叢集模組都共用同一套 key 契約，而不用各自重新發明。
