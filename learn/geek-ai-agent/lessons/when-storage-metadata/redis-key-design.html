Redis key 結構與避開 big-key

Step 2/5 · 存儲與元數據

學習目標

能畫出 When 的三類 Redis key、說出每類的型別與 TTL 規則，並解釋這樣設計如何避開 big-key。

訊息進 Redis 之後長什麼樣

訊息落地不能只是「把 Message 物件丟進去」。重啟恢復時，系統不只要找回訊息本體，還要知道它「排在什麼時間、屬於哪一輪時間輪」。所以 When 把要存的東西拆成三類 key：本體一類，排程索引一類，重啟恢復用的槽位索引一類。

Key 樣式型別存什麼生命週期
when:msg:{message_id}STRING（JSON）序列化後的訊息本體TTL = deliver_at + 7 天
when:tw:{tw_id}:idx:{message_id}STRING這則訊息的到期時間投遞或取消後刪除
when:tw:{tw_id}:slot:{slot_key}SET槽位裡有哪些訊息 id只用於節點重啟恢復，不做日常排程

三個設計決定藏在表裡。第一，本體以 message_id 拆開，一則訊息一個 key。第二，索引按時間輪 id 拆開，而不是全部丟進同一個大結構。第三，TTL 當安全網：正常流程會在投遞或取消後主動刪 key，但如果哪裡漏刪了，到期時間會自動清掉，不讓垃圾無限累積。單則訊息本體抓在 64KB 以內（含 metadata 通常數十 KB）。

big-key 為什麼是 Redis 的頭號敵人

big-key（大 key）指的是單一 key 底下的資料量過大，例如一個塞了幾百萬成員的集合。它可怕的地方在於，Redis 執行命令是單執行緒的：一次只能處理一件事。當某個請求要去搬動、刪除或掃描一個巨大的 key，整條執行緒就被它佔住，其他所有請求只能排隊。除此之外，大 key 在叢集擴容時難以搬遷，也很容易變成熱點，拖垮它所在的那個實例。

單執行緒是 Redis 快的原因，也是它怕 big-key 的原因。你不能讓任何一個 key 大到足以擋住所有人的路。

很多延遲佇列的 SDK 會把所有延遲訊息放進同一個 ZSet，用到期時間當分數排序。這在資料量小的時候很優雅，量一大就變成一個不斷長大的 big-key，每次讀寫都要碰它。When 明確反其道而行：不用 ZSet，也不用大 Hash。每一則訊息都是自己的小 key，十萬則訊息就是十萬個獨立的小 key，而不是一個裝了十萬成員的大集合。

這樣做的代價是 key 的數量多（從數十萬到數百萬個），但 Redis 對「大量小 key」的處理能力很強，這個代價遠比養一個 big-key 划算。

TTL 不只是清理，還是正確性

TTL 的設定規則不是隨手填一個數字。它必須不早於這則訊息所有可能被用到的時間點，也就是 max(deliverAt, nextAttemptAt, deliveredAt) 再加上一段保留期。為什麼要抓最大值？因為重試會把下一次嘗試的時間往後推，投遞成功則會記下 deliveredAt；如果 TTL 只看到最初的 deliverAt，一則正在重試的訊息可能在半路被過期清掉。

反過來說，當狀態改變讓計畫時間往後延，TTL 就必須跟著延長。這是很多實作會漏掉的一步，也是驗收會特別檢查的地方：每一個寫進去的 key 都必須有 TTL，而且要以 deliver_at + 7 天 為基準通過檢查。

key 的字首集中管理

所有 key 都掛在同一個字首 when: 底下，而字首本身集中在常數裡，不准在各處用字串拼出來。理由很實際：哪天要換命名、要加環境前綴、要做掃描清理，只需要改一個地方。這個約定在後面的模組會被強制遵守，因為模組之間就是靠同一套 key 命名在對話。
