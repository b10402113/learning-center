etcd key space 與心跳約定

Step 5/5 · 存儲與元數據

學習目標

能畫出 etcd 的四類 key space 與生命週期，並說出 Lease TTL 6 秒、續約 2 秒與獨立執行緒／連線的理由。

四類 key，四種生命週期

etcd 裡的所有 key 都掛在 /when/ 底下，依用途分成四類。分類的依據是它何時該消失，跟資料的內容無關。

Key內容生命週期
/when/nodes/{node_id}{ip, port, start_time, load}綁 Lease，節點停止續約就自動消失
/when/controller目前 Controller 的 node_id綁 Lease，Controller 掛掉就自動消失
/when/timewheels/{tw_id}{master, slave, status}持久保存，由系統維護
/when/config/*replica_count、timewheel_count 等持久保存，可動態調整

上半部（nodes、controller）代表「現在誰還活著、誰在做主」，所以用 Lease；下半部（timewheels、config）代表「這個叢集被設定成什麼樣子」，所以持久保存。把這兩種混用，就會出現「節點一重啟，時間輪分配也一起消失」這種災難。

設計 key space 的三個原則

  • 清楚的階層：每一類資料有自己的前綴。這樣才能用 Watch("/when/nodes/", ...) 一次訂閱整段前綴的變化，不必一個 key 一個 key 去盯。
  • 小 key 優先：每個 value 抓在幾百 bytes 以內，不要把大型物件塞進 etcd。etcd 是協調服務，不是資料庫，塞大物件會拖垮共識效能。
  • 生命週期分離：會隨節點生死自動清除的，和必須長期存在的，分開放。這是上一條「四類 key」的由來，也是所有叢集模組都要遵守的紀律。

心跳約定：TTL 6 秒、續約 2 秒

節點註冊用的 Lease TTL 定為 6 秒，續約間隔定為 2 秒。這兩個數字不是隨便挑的。整個系統給故障切換的預算是 10 秒，Lease 過期是其中的第一段；TTL 取 6 秒，等於留了 4 秒給後面的偵測、選舉與接管流程。續約取 2 秒，則是在 6 秒的期限內可以容許連續兩次續約失敗才判定死亡，避免一次網路抖動就誤殺一台好節點。

Lease 的秒數是在「太快誤判」與「太慢切換」之間取平衡，最終仍要靠故障注入測試來驗證。

還有一個容易寫錯的地方：續約要用獨立的執行緒和獨立的 etcd 連線，不可以跟業務執行緒共用。理由是 Java 的 GC 或業務尖峰會讓執行緒短暫卡住；如果續約跟業務綁在一起，一次漫長的 GC 就可能讓續約遲到、Lease 過期，叢集於是誤判這台健康的節點已經死亡。把心跳隔離出來，才能讓「活著」的訊號真正反映節點狀態。

etcd client 封裝：五個原語

整個叢集只准透過一個封裝好的 client 存取 etcd，這個封裝提供五組操作：

操作用途
putWithLease(key, value, ttl) / keepAlive(lease)註冊與心跳續約
get(key) / getPrefix(prefix)讀單一 key 或整段前綴
watch(prefix, handler)訂閱前綴下的新增與刪除事件
txnPutIfAbsent(key, value)只有 key 不存在時才寫入，原子操作

最後一個 txnPutIfAbsent 值得多看一眼：它「不存在才寫」的語意，正是後面 Controller 選舉的地基：多個節點同時搶著寫同一個 key，只有一個會成功，那個成功者就是新的 Controller。

驗收方式是把這些操作全部拿到真實的 etcd 上跑：透過 Testcontainers 起一個 etcd，驗證 Lease 停止續約後會自動刪 key、keepAlive 能維持住 key、watch(prefix) 收得到 PUT 與 DELETE、txnPutIfAbsent 在 key 已存在時回報失敗。另外還有一組 key space 慣例測試，確認四類前綴的讀寫與結構都符合約定。不用 mock，因為 Lease 過期、Watch 事件、Txn 原子性這些行為，mock 假不出來。

用 Harness 把規則釘住

為了不讓「單一入口」「小 key」「生命週期分離」這些約定被後來的程式碼繞過，這個模組用 Harness 強制幾件事：etcd 存取集中在 cluster/etcd 套件，是叢集端唯一的 etcd 入口；key 的拼接與 /when/ 前綴集中在常數裡；端點與憑證一律從環境變數讀，不寫進程式；節點 metadata 裡不得出現任何敏感憑證；依賴只准用 when-common 與官方 jetcd。

把整個節點收在一條線上

回頭看，這個節點其實在回答同一個問題：When 該把哪些狀態交給外部儲存，又該怎麼切分？訊息這條線，是把大量短命的資料交給 Redis，用一則一 key 的拆法避開 big-key，用固定寫入順序與原子 transition 守住一致性。協調這條線，是把少量關鍵的資料交給 etcd，用清楚的 key space 與 Lease 心跳讓節點活得明白、死得乾脆。兩條線的交會點是「狀態外部化」：節點本身盡量無狀態，重啟後只要把 Redis 與 etcd 的狀態讀回來，就能無縫接回叢集。
