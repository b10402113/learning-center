寫入順序、原子轉移與重啟恢復

Step 3/5 · 存儲與元數據

學習目標

能複述 create 的固定寫入順序、原子 transition 如何保證只有一個執行者取得投遞權，以及重啟時為何要先載資料再對外服務。

create 的固定寫入順序

上一課說「先寫儲存、再進記憶體」，但儲存本身其實有兩個東西要寫：訊息本體，以及排程索引用來記錄到期時間。順序和批次方式都是固定的：

  1. 把 Message 序列化成 JSON。
  2. 用 Pipeline 一次送出兩個寫入：先 SET 本體（when:msg:{id}），再 SET 索引（when:tw:{tw_id}:idx:{id}）。
  3. 確認 Redis 回報成功。
  4. 把訊息放進記憶體時間輪。
  5. 回報呼叫方受理成功。

用 Pipeline（管線）是為了把兩個命令一次送出去、一次收結果，省掉一趟網路往返。而「確認成功」這一步不能省：任何一個步驟失敗，就直接回報失敗，完全不去碰記憶體。這條規則保證了反方向的一致性：記憶體裡有的，Redis 一定有。

寧可少一則訊息，也不要多一則只在記憶體裡的幽靈訊息。少的那則呼叫方會重試，幽靈的那則沒人救得回來。

這也解釋了 Redis 掛掉時的行為：create 拋出錯誤，呼叫方收到失敗、自行重試。系統不會偷偷先把訊息塞進記憶體假裝成功。

transition：只准一個執行者拿到投遞權

訊息到期之後，最怕的是「同一個訊息被投遞兩次」。會發生這種事的場景很多：時間輪指針剛好掃到、節點同時在做故障轉移、重試排程又剛好醒來。如果沒有防護，兩個執行緒可能都覺得「該我送了」。

transition 就是用來擋這件事的。它只在一種條件下動手：目前狀態等於預期狀態。例如把 PENDING 轉成 DELIVERING，只有當這則訊息現在真的是 PENDING，更新才會生效，而且會在同一筆操作裡原子地補上重試次數、錯誤訊息、下次嘗試時間等欄位。實作上可以用 Lua 腳本，或等效的交易機制。驗收裡有一個很直接的測試：同時發 100 個 PENDING → DELIVERING 的請求，只准一個成功。贏的那個拿到投遞權，其餘全部失敗、摸摸鼻子退開。

另一個容易被忽略的紀律是：排程執行緒永遠不做同步的 Redis 讀寫。時間輪的指針一旦被 Redis 的網路延遲卡住，整個排程就會歪掉。所以指針掃到到期訊息時，它只負責把工作交給非同步的執行器，由執行器去呼叫 transition 搶投遞權、更新結果。指針本身繼續往前走。

重啟恢復：先把資料載回來，再對外服務

節點啟動時，記憶體是空的，但 Redis 裡還留著一堆「還沒排到的 PENDING 訊息」。恢復的動作是呼叫 loadPendingByTimeWheel(twId)，把每一輪裡還在等的訊息撈回來，重建記憶體時間輪。這裡只載 PENDING，因為已經在投遞中的、已完成的都不需要再排進時間輪。

關鍵在於順序：必須等資料載完、時間輪重建完成，節點才能對外表示自己可以服務（在叢集裡就是完成註冊）。如果反過來先註冊、後載入，叢集會以為這台節點已經準備好了，把工作派給它，而它其實還在慢慢載資料，接不住。這就是典型的「已註冊但未就緒」陷阱。

終態訊息怎麼收尾

訊息投遞成功、或重試耗盡進入終態之後，並不會立刻從 Redis 消失，而是保留一段時間供查詢與排查。過了保留期，清理工作會呼叫 deleteExpired(messageId)，把本體和索引一起刪掉。刪除同樣用 Pipeline 批次處理，避免一則一則慢慢刪。

把效能約束變成測試

「不要出現 big-key」「要用 Pipeline」這種話，如果只寫在文件裡，遲早會被改壞。這個模組把三件事寫成必須存在的測試：

  • big-key 反回歸測試：斷言 key 的數量隨訊息量線性成長，而且不存在任何單一的大型集合。只要有人偷偷改回 ZSet，這個測試就會亮紅燈。
  • 寫入失敗測試：讓 Redis 不可用，斷言 create 會拋錯，且呼叫方失敗時訊息沒有進到記憶體時間輪。
  • Pipeline 斷言：本體與索引的寫入走 Pipeline，刪除也走 Pipeline。

其他驗收還包括：type() 回傳 "redis"、create 後 get 能拿回一模一樣的訊息、每個寫入的 key 都有 TTL、終態訊息在保留期內查得到而 deleteExpired 後本體與索引都消失。這些測試跑在 Testcontainers 起出來的真實 Redis 上，不是用 mock 假裝。
