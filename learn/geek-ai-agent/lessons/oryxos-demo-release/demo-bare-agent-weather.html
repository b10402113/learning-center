Demo 一：光桿 AGENT.md 的每日天氣 Agent

Step 1/6 · Demo 與發布

學習目標

能用一個光桿 AGENT.md 定義出每日 08:00 自動推送天氣與穿搭建議的 Agent，說清它的最小設定、三道環境閘門，以及「先推再看時鐘」的除錯順序。

第一階段的驗收長什麼樣

前面二十八節把 OryxOS 的底座一層層蓋起來，但底座本身沒有使用者。第一階段的驗收，是三個真的會在固定時間自己跑起來、把結果推給人的業務 Agent，再加上一個打了標籤、別人也能部署的版本。三個 Demo 是刻意挑的，它們的目錄貧富程度一檔比一檔高，正好把插件化「多一個檔案就多一種能力」的落差量出來。

Demo 一：一個檔案就是一個 Agent

天氣 Agent 的定義放在 .oryxos/agents/weather-daily/AGENT.md。你可以用管理台的「新建 Agent」表單建立，也可以打 POST /api/v1/agents，兩條路最後都產生同一份檔案。它有兩個部分：frontmatter 回答「誰、什麼時候、用什麼」，body 回答「做什麼」。

---
name: weather-daily
provider: deepseek/deepseek-chat
tools: [http_get, notify]
notify_channels:
  - "${TEAM_WEBHOOK_URL}"
schedules:
  cron: "0 0 8 * * *"
  zone: Asia/Shanghai
  message: 到点了，按你的说明执行。
---
每天早上查詢北京天氣，給出穿搭建議，然後通知團隊。

這裡有三個設計選擇值得停下來看。第一，tools 只給了 http_get 與 notify——它不讀子指令、不跑腳本，所以不需要 read_file 或 shell，這是最小權限原則，工具給得越少，出事的面越小。第二，網址用 ${TEAM_WEBHOOK_URL} 這種環境變數佔位，密鑰不寫死在檔案裡。第三，schedules 用標準 cron 表示式，六欄位的 0 0 8 * * * 就是每天 08:00，並明確指定時區，避免伺服器在哪個時區就幾點推的模糊。

body 只有一句話，卻已經說完了整個流程的意圖。更完整的版本會告訴它：用 http_get 打 https://api.open-meteo.com/v1/forecast，帶上北京的經緯度與 current=temperature_2m,precipitation,wind_speed_10m，拿到資料後給出穿搭建議，最後呼叫 notify 推播。天氣源刻意選 open-meteo：免費、免金鑰、直接回 JSON，避免 Demo 當天因為對外服務要申請而翻車。

三道環境閘門：沒過就靜默待命

檔案寫好不代表就會跑。這個 Agent 要真的動起來，必須先過三道環境閘門，任何一道沒過，它只會安靜地待命，不會報錯提醒你——這也是新手上路最容易卡住的地方。

  • 模型金鑰：因為設定裡排除了自動配置，你必須先 export DEEPSEEK_API_KEY，否則呼叫不到模型。
  • 網域白名單：http.allowed_domains 必須包含 api.open-meteo.com 與 webhook 的網域（飛書是 *.feishu.cn、企業微信是 qyapi.weixin.qq.com）。少了任何一個，工具會在白名單那關被擋下。
  • Webhook 可達：通知要送得出去，webhook 位址必須是活的。

除錯順序：先推再看時鐘

不要傻等 08:00。除錯的順序是「先手動推一次，再回過頭看時鐘」。手動觸發有兩個等價入口：oryxos chat --profile weather-daily，或 POST /agents/weather-daily/invoke。這兩條路和時鐘觸發走的是同一條主鏈，所以手動能跑通，時鐘就能跑通。

手動推的價值在於它會立刻把問題攤開：白名單沒設好，工具呼叫當場被攔；body 寫得太含糊（例如只寫「查天氣」而沒說用哪個工具），模型可能根本不去呼叫工具，只回一段廢話。這些問題在真正推送前修掉，成本最低。

時鐘真的響了之後，怎麼對賬

等到 cron 真的觸發，一次成功的自動推送會留下固定的痕跡。把它們一條條對上，你就確認了整條鏈：

  • cron 觸發，排程把 body 當提示注入；
  • Agent 呼叫 http_get，通過 Sandbox 白名單（tool_invocations 第 1 筆）；
  • LLM 生成穿搭建議（這一步產生兩次 llm_calls）；
  • 呼叫 notify 推播，再次通過白名單（tool_invocations 第 2 筆），群組收到訊息。

驗收的硬指標因此很具體：沒有人手動觸發它、兩個對外呼叫都過白名單且留下審計、兩次 llm_calls、GET /sessions/{id} 能看到整段被自動觸發的對話、群組真的收到訊息。這些指標之所以能逐條核對，是因為審計從第一天就寫進資料庫；沒有審計，「感覺有跑」和「確定有跑」就分不出來。
