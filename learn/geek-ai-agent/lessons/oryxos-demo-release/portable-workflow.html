帶得走的工作流、設計母題與後續路徑

Step 6/6 · Demo 與發布

學習目標

能複述每個模組重複四次的工作節奏（原理→動手前想清楚→與 AI 實作→驗證並講解程式碼）與四條設計母題，並用「新增一個實作、不改介面」的訊號觸發方式說明後續擴展路徑。

比程式碼更值錢的那件事

走完整個第一階段，程式碼會留下來，但真正能被複製到下一個專案的，是一套重複了十幾次、已經練進手裡的節奏。程式碼綁專案，節奏不綁。這一節把節奏、母題與後續路徑收在一起。

四步節奏：每個模組都走同一套

幾乎每個模組都用同一個四步形式走完，這是第一階段最穩定的重複單元：

  1. 原理（是什麼、為什麼）：先講清楚它在 Agent 系統裡扮演什麼角色、為什麼需要它。
  2. 動手前想清楚：先談邊界、坑與「這一階段不做什麼」，把最容易寫錯的地方先釘死。
  3. 與 AI 一起實作：執行交給 AI；文件透過 Spec-Kit 轉成任務，而不是憑感覺下指令。
  4. 驗證並講解程式碼：對照清單檢查，並要求能講解——只有「懂了」才算真的完成。

這四步之所以有效，是因為它把「想」放在「做」之前，把「懂」放在「動」之後。少了前面，就會邊做邊改；少了後面，就會有跑得動但沒人懂的程式碼。

文件即規格、對賬法、前置坑

三個具體方法撐起了這個節奏。文件即規格（docs-as-spec）：這一階段第二到第三十一節的技術文件，本身就是 Spec-Kit 的輸入——你把「它應該長什麼樣」寫清楚，實作就會從文件長出來，這正是真實專案裡的 SDD。對賬法：一次呼叫應該留下剛好那些痕跡，於是一張表一張表對（這是第二十七、二十八節的用法），它既是整合問題的照妖鏡，也是審計能力的日常應用。前置坑：JPA 掃描、工具重複呼叫、依賴版本、快取疏忽——每個坑都在「動手前想清楚」那一步被點名；把坑變成下一專案的清單，這才是它真正的報酬。

四條設計母題

把三十二節攤開，會發現反覆出現的四條設計母題。它們不綁 OryxOS，可以搬到任何專案。

  • 介面先行、實作分階段：介面只表達意圖、不含實作細節，核心階段只填最輕的那一檔——Notify 的 NotifyChannelAdapter、Memory 的 MemoryService、Sandbox 的 Sandbox.enforce 都是這樣。測試的方法是：把未來最重的實作（企業微信 SDK、向量檢索、microVM）在腦中塞進這個介面——塞得進去，這道牆才成立。
  • 訊號驅動升級，不靠直覺：什麼時候該上向量檢索、容器隔離、自動記憶抽取，答案從來不是「大家都在做」，而是一組寫下來的真實訊號——檢索開始漏、需要跑不可信程式碼、手動記憶明顯掉東西。沒有訊號出現，就守住現狀。
  • 階段克制：每一節都有「這階段先不做」的清單（fallback、SSE、分散式鎖、Tool Policy、自動抽取）。它們不是不重要，只是不屬於這一階段；目標是一個最小可用的執行核心，而不是大而全。
  • 同一入口、重用不重寫：人推與時鐘推共用同一個 AgentService；API 建立與檔案建立的 Agent 共用同一套驗證與註冊；notify 重用 Sandbox 白名單與 ToolExecutor 審計。只要出現「第二條路」，早晚會出現「兩條路行為不一致」——這一階段最難的 bug 幾乎都來自這裡。

後續怎麼擴：新增實作，不改介面

第一階段留下的每一個掛點，現在都對應到一個明確的擴展方向，而且用「模組方向／掛點／觸發訊號」三欄就能講清楚：

方向掛點觸發訊號
多 Channel（企微／飛書／釘釘／Slack）Channel Adapter 插件槽（8.4）出現真實 IM 需求
專用 Notify 通道 Adapter新增一個 NotifyChannelAdapter 實作webhook 做不出富卡片
Memory 向量檢索換掉 MemoryService facade 後面的實作關鍵字檢索漏、記憶破千
Sandbox 容器 → microVM新增一個 Sandbox 實作要跑不可信程式碼／多租戶
Tool Policy、認證、SSO、多租戶保留的治理槽離開內網／多團隊共享
審計查詢 API 與儀表板兩張審計表之上有人要報表的那一天
SSE 串流、分散式、GraalVM各自的保留槽互動／規模／啟動時間成瓶頸

這張表的共同點是：每一項都是「新增一個實作、不改介面」。這正是前面所有「介面先行」投資的兌現清單——當初忍住沒有把介面綁死在某一種實作上，換來的就是今天可以平順地往上加。

更長的路

OryxOS 的長期目標從第一天就寫著：進入 Apache 基金會、成為頂級專案。從 v0.1.0 走到那裡有幾個具體步驟——開源（公開 repo、授權與貢獻指南、專案首頁與快速開始）、降低首次貢獻門檻（把擴展表拆成 good first issue，一個新的 NotifyAdapter 或內建 Tool 只要幾百行，是很好的第一個 PR）、讓 Agent 生態先跑起來（定義一個 Agent 不需要 Java，所以貢獻者不必懂 Java，分享一個好用的 Agent 目錄就是一種貢獻，這是門檻最寬的社群入口）、用這批文件去教下一批人（課程文件、技術方案、需求文件就是最好的 onboarding 教材）。

對你個人而言，第一階段練的是「操盤」——從零把一個真專案做起來。下一個層次是把這個能力泛化到新領域、新技術棧：四步節奏、四條設計母題與對賬法都能重用。認知與判斷才是這門課真正想給的東西，OryxOS 只是它們的第一個作品，不會是最後一個。
