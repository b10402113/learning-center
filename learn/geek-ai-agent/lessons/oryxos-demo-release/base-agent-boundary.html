底座與 Agent 的分界

Step 4/6 · Demo 與發布

學習目標

能用「底座 vs Agent」分界圖說明 Provider／ReAct／CLI／Notify／Tool／Memory／Sandbox／排程／Web 全都屬於底座，而真正的業務 Agent 只是插上去的一個目錄，並解釋為何底座越厚、定義一個 Agent 就越便宜。

先看一組不成比例的數字

三個 Demo Agent，一個光桿 AGENT.md、一個帶子指令、一個帶腳本，加起來不到一百行文字、零行 Java。它們卻能在固定時間自己醒來、呼叫模型與工具、把結果推進群組。前面二十八節寫了那麼多程式，這裡卻幾乎沒寫程式——這個落差不是巧合，而是要理解的核心。

如果第一階段只能帶走一張圖，就是這張分界圖。它把整套系統切成「底座」與「Agent」兩邊，讓你一眼看出力氣該花在哪裡。

這張圖的七層

  • LLM Providers：DeepSeek／Qwen／Kimi、OpenAI／Anthropic、Ollama、Spring AI Alibaba，以及 MCP servers。
  • Channel／Trigger 層：CLI、REST API、Scheduler——也就是「人推」與「時鐘推」兩種觸發來源。
  • Agent 層：一個業務 Agent 就是一個目錄。AGENT.md 的 frontmatter 回答「誰、何時、怎麼」，body 回答「做什麼」；目錄可選帶 skills/ 與 scripts/，零程式碼。
  • Engine 層（oryxos-core）：ReActLoop 負責「想＋做」、最多迭代 10 次；PromptBuilder 組出 system＋memory＋history＋tools；ToolExecutor 執行前先過 Sandbox 檢查、執行後寫審計。
  • Capability 層：Provider 路由、Memory 的 session＋長期＋core-archive、Tool 的內建＋MCP、Notify 出站與 Sandbox NotifyTools。
  • Storage 層：SQLite 的 oryxos.db 存 sessions／tool_invocations／llm_calls；檔案系統的 .oryxos/ 存 profiles／MEMORY.md／skills。
  • 外部依賴：Notify 目標、業務系統、閘道、協定。

真正的洞見：前十幾節做的全是底座

把節數對到這張圖上，會發現一件反直覺的事：第一到第二十八節做的 Provider、ReAct、CLI、Notify、Tool、Memory、Sandbox、排程、Web，全部都是底座，不是 Agent。它們就像作業系統提供行程排程與系統呼叫——OS 本身不是任何一個特定的應用程式，卻讓應用程式得以存在。

真正的業務 Agent 只在第二十九節之後才出現：一目錄一 Agent，被插到這個底座上。所以三個 Demo 加起來不到一百行、零 Java，這個不成比例本身就是底座價值的量尺——底座越厚、越完整，定義一個新 Agent 就越便宜。 如果每個業務 Agent 都要重寫 ReAct 迴圈、Notification、Sandbox，那底座就白做了。

底座和框架，差在哪裡

常有人把 OryxOS 和 LangGraph 直接比。把它們放回這張圖就清楚了：寫一個 agent 不難，難的是在企業裡可靠地跑一「隊」agent。底座要解決的是私有部署與資料駐留、統一模型接入、共享記憶與工具這些公共能力、多 agent 編排、故障恢復、權限與審計。框架之於應用程式，就像作業系統或 K8s 之於服務——LangGraph 是開發框架，OryxOS 是執行期底座；兩者的差別是「build vs run」，不是「技術 vs 非技術」。

企業為什麼需要它，可以用一句話收束：寫一個 agent 容易，可靠地運行一批 agent 很難。 這句話也解釋了為什麼工程師應該在這裡練判斷——因為難的不是能不能寫出來，而是出事時能不能查、能不能接管、能不能審計。

這個分界怎麼幫你做決定

有了這張圖，選型就變成一個可以回答的問題：你正在做的事情，是「某個業務 Agent 的內容」，還是「所有 Agent 共用的底座能力」？前者應該用一目錄一 Agent 的方式宣告，越薄越好；後者是底座投資，值得好好設計介面、分階段實作。弄混這兩者，就會發生「為了一個小需求改底座」或「把該進底座的公共能力在每個 Agent 裡重寫」兩種典型的浪費。
