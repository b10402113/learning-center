Demo 三：目錄帶腳本的每日 GitHub 日報

Step 3/6 · Demo 與發布

學習目標

能說明為何把抓取 GitHub trending 的確定性工作寫成目錄裡的 Python 腳本、由 Agent 用 shell 執行，並解釋子行程自行連網如何繞過 http_get 網域白名單、把信任轉移到 Agent 作者身上。

確定性的事，就交給確定性的工具

天氣與日報都是「抓一段文字，讓模型重組」。GitHub 日報不同：它要的是 GitHub 上「今日熱門、本月熱門、本月 AI 熱門」三組排名，這些是可以精確算出來的資料。如果硬用 http_get 抓網頁再讓模型拼，模型可能漏抓、可能順序顛倒，這種確定性工作交給模型是自找麻煩。

正確的分工是：把抓取寫成腳本，讓確定性的部分確定地完成；把組稿留給模型，讓語言的部分由 LLM 處理。 腳本負責拿到結構化資料，模型負責把資料寫成人話。

目錄長什麼樣

Agent 目錄是 .oryxos/agents/github-daily/，比日報多了一個 scripts/ 子目錄。AGENT.md 的 frontmatter 把工具換成 shell 與 notify：

---
name: github-daily
provider: deepseek/deepseek-chat
tools: [shell, notify]
schedules:
  cron: "0 30 9 * * *"
  zone: Asia/Shanghai
  message: 到点了，按你的说明执行。
---

body 描述的流程是：執行 python scripts/github_trending.py 拿到 JSON（內含 today、month、ai 三組，每項有 name／stars／desc／url）→ 組成三段（今日 top5、本月 top5、本月 AI）→ AI 段優先套用記憶偏好 → 通知。

腳本 scripts/github_trending.py 用 GitHub 的 Search API（https://api.github.com/search/repositories），以 created:>日期 搭配 stars 排序來「近似 trending」——因為 GitHub 官方沒有 trending API。未認證的呼叫每分鐘上限 10 次，零外部依賴，夠這個每天跑一次的 Agent 用。

關鍵觀念：子行程連網，繞過了白名單

這裡有一個必須對觀眾講清楚的信任邊界。前面的 http_get 會受 http.allowed_domains 的網域白名單管轄，但那個白名單只約束「內建工具」，管不到 Python 子行程自己發出的網路請求。也就是說，github_trending.py 對 api.github.com 的連線，是子行程自己發的，不受白名單檢查。

這帶來一個誠實的結論：安裝 github-daily 這個 Agent，等於信任它的作者。 腳本裡寫了什麼網路行為，你只能靠信任作者來保證。這不是設計缺陷，而是「一目錄一 Agent」機制的必然——把能力交給使用者自由擴充，就必須把信任一併移轉過去。這也是為什麼核心階段的 Sandbox 只做兩道白名單：shell.allowed_commands 允許 python、file.allowed_paths 把檔案存取限制在 Agent 自己的 scripts/。這兩道能限制「能跑什麼、能碰哪些檔」，但不能限制「子行程連去哪裡」。

Sandbox 的前提因此有三項：允許 python、把 api.github.com 加進 http.allowed_domains（主要為了審計與未來收緊）、以及讓 file.allowed_paths 涵蓋 .oryxos/agents/github-daily/。

播種偏好與對賬

先種偏好：「我更關注 Agent 框架和推理引擎方向的開源項目」。接著用同一招除錯——先推再看時鐘。對賬要核對四件事：腳本真的跑了（tool_invocations 裡有 shell／py 的呼叫）、程式碼本身沒有進入 context 但它的 JSON 進去了、記憶偏好讓 Agent 框架與推理引擎的專案排到前面、以及最後由 LLM 完成組稿而 OryxOS 不解析任何步驟。

「程式碼不進 context、JSON 才進」這點值得多想一秒：Agent 執行的是腳本這個動作，模型看到的是腳本的輸出，而不是腳本內容。這正是確定性資料與語言組稿各司其職的證據。

三種目錄形態，到此收齊

Demo目錄多出來的一層交給誰
每日天氣無，光桿 AGENT.mdLLM + 內建工具
每日科技日報skills/*.md 子指令LLM + 按需載入的規範
每日 GitHub 日報scripts/*.py 腳本腳本取得資料、LLM 組稿

三個 Demo 合起來，就是第二十九節「一目錄一 Agent」的完整驗收：目錄能容納多豐富的能力，取決於你往裡面放什麼，而不是改動底座。
