發布 v0.1.0：打包、產物與可操作性驗收

Step 5/6 · Demo 與發布

學習目標

能複述 v0.1.0 的打包指令（mvn clean verify／package、git tag）、兩個發布產物（fat JAR 與 .oryxos 工作區），並用「乾淨機器 30 分鐘從零跑起兩個 Agent」的可操作性驗收標準判斷一個版本能不能發。

三個 Agent 穩定跑之後，才輪到「發布」

三個 Demo Agent 都能連續穩定自跑之後，下一個問題是：怎麼把它變成一份「別人也能用」的交付物。這裡的順序很重要——先把東西跑穩，再談打包；否則包裝的只是個跑不起來的空殼。

打包：三條指令

mvn clean verify        # 跑完整驗證，綠燈才繼續
mvn clean package       # 產出 fat JAR
git tag v0.1.0 && git push --tags   # 打標籤、推上去

mvn clean verify 是發布前的守門員：測試與檢查全過，才有資格進到打包。通過之後 mvn clean package 產出 fat JAR。git tag v0.1.0 則把這個可交付的狀態釘在版本歷史上，日後任何人想看「v0.1.0 長什麼樣」都能精確取得那一點。

兩個發布產物

發布出來的東西有兩個，一個是程式、一個是資料，兩者分開。

  • 程式：oryxos.jar。它把九個模組與全部依賴打包成單一檔案，用 java -jar 就能跑，不需要任何外部服務。這是單檔部署，也是技術方案第一章就承諾的形態：一個檔案就是一個系統。
  • 工作區：.oryxos/。它由 oryxos init 產生，內含 profiles 與 skills 這兩份 Agent 定義、memory/MEMORY.md、mcp_servers.yaml、oryxos.db 與 Bootstrap。裡面的東西全是文字與 SQLite——可以備份、可以直接進 git，等於你的 Agent 設定與記憶是可以被版本控管的資料，而不是藏在某個黑盒裡的狀態。

發布不只是打包：可操作性驗收

發布真正的門檻不是「檔案有沒有產出來」，而是「別人拿得到、跑得起來」。這就是可操作性驗收：在一台乾淨的機器上（或把本機的 .oryxos/ 刪掉），照著 README 從零走一遍——java -jar oryxos.jar init、設定 API key 環境變數、設定白名單與 webhook、放進三個 Agent 目錄、看它們跑起來。

驗收標準是一個具體的數字：一個新人必須在 30 分鐘內完成。 超過、或任何一步卡住，代表的不是程式缺功能，而是文件缺說明——因為程式已經在開發者機器上跑得動了。把「新人 30 分鐘從零到兩個 Agent 正常工作」當成發布門檻，會逼你把安裝文件寫到真正能照做的程度。

做完怎麼驗：三張驗收清單

三個 Demo 各有自己的綠燈條件，合起來就是第一階段的驗收清單：

Demo綠燈條件
每日天氣連續兩天 08:00 自動推送穿搭建議；審計精確對賬；先推與時鐘行為一致；光桿 AGENT.md，無子指令與腳本
每日科技日報連續兩天 09:00 自動推送；tool_invocations 有對 skills/digest-format.md 的 read_file；內容反映記憶偏好；零 Java
每日 GitHub 日報連續兩天 09:30 自動推送；tool_invocations 有 shell／py 呼叫；today／month／AI 三段完整且 AI 段反映偏好；JSON 進 context、程式碼不進

最後還有一個驗收彩蛋，用來展示「宣告式 + 立即生效」：現場改 github-daily/AGENT.md 的 body，例如加上「AI 段每條加一句一句話點評」，不重啟，下次觸發就吃到新版本。這一手之所以能成立，是因為 Agent 的定義就是那份檔案，改檔案等於改行為，不需要重新編譯或重啟服務。

這個版本在課程作業脈絡裡的位置

發布 v0.1.0 對應的正是第二週的必做作業：clone oryx-labs/oryxos、把它跑起來、設定第一個 Agent 並發出一則通知、送出第一個 PR（就算只有一行文件也算）、研究並跑 Hermes Agent 後比較 OryxOS 與 Hermes 的功能／架構／企業價值、用四份技術文件以 Spec-Kit 拆出第一個任務，並幫 OryxOS 與 robustmq 兩個開源專案按星星。這些動作把「讀過」變成「真的動手碰過」，也讓你親手驗證一次這套發布與驗收流程。
