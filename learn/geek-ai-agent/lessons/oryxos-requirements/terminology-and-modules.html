術語表與九個 Maven 模組

Step 3/5 · OryxOS 需求

學習目標

能用自己的話定義 Agent、Profile、Provider、Session、Channel、Tool Policy、Skill、Bootstrap、Workspace 等核心術語，並把五大能力對應到九個 Maven 模組中的哪幾個。

為什麼先統一術語

一份需求文件最貴的資產不是功能列表，而是一套所有人共用、不會各說各話的詞彙。當十幾個模組都用同一套術語，模組之間才接得起來；否則最常見的 AI 大專案失敗就是「每一塊自己定義自己的 Agent，最後拼不起來」。OryxOS 的術語刻意對齊開源 Agent OS 的事實標準命名，讓熟悉 OpenClaw / Hermes 的人能直接看懂。

核心術語表

術語定義
Agent一個由 Profile 定義、能呼叫模型與工具、自主跑的實體
ProfileAgent 的完整設定（YAML）：身份、provider、工具、渠道、bootstrap。一個 Profile 就是一個 Agent
Provider對某個模型供應商的呼叫抽象；有 name / model / API key / base URL
ReAct 迴圈Reason + Act：想一步、做一步、觀察結果，直到完成或到上限
ToolAgent 能呼叫的能力，分內建（builtin）與插件（Plugin）
Memory三層：session（會話）、long-term（長期）、episodic（情景）
Channel訊息進出的通道，例如 CLI、企業微信、飛書
Web Service把引擎暴露成 REST 介面的服務
Session對話上下文的容器：時間、使用者身份、Agent id、歷史、臨時變數
Sandbox工具執行的安全邊界
Tool PolicyProfile 層級的工具允許／拒絕清單，最輕量的治理手段
Skill用 SKILL.md 描述的能力包，相容 agentskills.io 標準
Bootstrap啟動時注入的引導檔：AGENTS.md / SOUL.md / USER.md
Workspace工作區目錄 .oryxos/，存放 profiles、sessions、skills、logs、tools

這張表是往後每一份 OryxOS 文件的閱讀基礎。看到「Profile」就知道是一個 Agent 的設定，看到「Session」就知道是對話狀態，看到「Channel」就知道是進出口——不需要每次都回頭查。

從文件到模組：九個 Maven 模組

術語定義了「概念」，模組定義了「程式碼住哪裡」。OryxOS 拆成九個 Maven 模組，剛好是五個核心能力 + 四個支撐模組：

模組類型負責什麼
provider核心能力一對接 LLM
core核心能力二ReAct 引擎（整個底座的心臟）
memory核心能力三記憶
tool核心能力四工具與沙箱
web核心能力五對外 REST 服務
boot支撐啟動裝配：把各模組組起來
cli支撐命令列入口
storage支撐持久化
channel-cli支撐核心階段的唯一渠道（CLI）

這張對應表有一個很實用的判斷價值：當你後面看到某個功能要改，先問「它在哪個模組」。引擎是 core（ReAct），它被 Provider / Memory / Tool 三個模組餵養，再由 CLI / Web 兩個入口暴露出去——模組的依賴方向，就是能力的供養方向。

三層範圍，先說清楚「核心」的邊界

需求文件把功能分三層，核心階段只做第一層：

  1. 核心功能：最短可跑的鏈——用 Profile 設定 Agent、用 CLI 對話、呼叫 LLM 與工具、用 REST API 暴露。對應 4 週 × 3 小時 = 12 小時的硬預算。
  2. 擴展功能：生產必需但不在核心，含企業治理層。
  3. 社區共建功能：長期方向，不影響主線。

把範圍和模組疊在一起看，你會得到一個很重要的心智模型：核心階段做的九個模組，是整個 OryxOS 的地基；三層範圍則是往後所有取捨的依據。任何新需求進來，先問它落在哪一層——核心已滿，就代表它得排隊。
