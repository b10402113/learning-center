核心／擴展／社區範圍與驗收標準

Step 5/5 · OryxOS 需求

學習目標

能分清核心、擴展、社區三層各放什麼，複述四層驗收標準與五個必過 Demo，並說出核心階段的性能、可靠性與安全硬指標。

三層範圍：什麼現在做、什麼以後做

層放什麼誰做、什麼節奏
核心最短可跑的鏈：Profile 設定、CLI 對話、呼叫 LLM 與工具、REST 暴露4 週 × 3 小時 = 12 小時，必須做完
擴展生產必需但不在核心：企業治理層核心完成後接手，跟隨社區節奏
社區長期方向：文件、Skills 市集、多語言 SDK、視覺化編輯器等無時間表，不影響主線

擴展層裡最關鍵的是治理和運維層，它才是 OryxOS 真正的差異化所在：Web 儀表板、SSO 與多租戶（SAML／OIDC、AD／Okta／Entra ID／阿里雲 IDaaS／企業微信認證，三級租戶模型，RBAC 細到 Agent／Tool／Skill 層級）、審計與追溯（JSON 事件、trace ID、脫敏、匯出到 SIEM）、可觀測，以及叢集化高可用（Nacos／ETCD、Controller 選舉、自動故障切換）。核心階段只蓋 runtime kernel，這些是讓它「真企業級」的第二階段。

里程碑：四週的節奏

週能力Demo
W1LLM + ReAct多輪對話 + HTTP 工具
W2Memory + ToolMEMORY.md、內建工具、MCP、SKILL.md
W3Web ServiceSpring MVC、6 個 controller、10 個端點
W4多 Agent + 工程收尾多 Agent 並存、打包

節奏是「順序與韻律」的骨架，不是死時刻表：每週一組能力、每週一個 demo，確保永遠有東西可展示。

驗收標準：四層尺

層驗收條件
功能所有核心模組完成，且每個有端到端測試
性能單節點 10 個 Agent 連續跑 4 小時、100 個並發 Session、Session 建立 P99 < 200ms、內部轉發開銷 < 50ms
可運維照文件 30 分鐘內能部署；CLI help 清楚；專案首頁可存取
場景五個 Demo Agent 全部可跑——這是硬性發布條件

「五個 Demo」分別是：LLM + ReAct、Memory、Plugin Tool + MCP、Web Service 同步呼叫、Web Service 多端點。它們不是加分項，是發布的門檻：跑不起來就不算完成。

非功能硬指標

性能

單節點至少 10 個 Agent、至少 100 個並發 Session；Session 建立 P99 低於 200ms；內部轉發開銷低於 50ms。要留意的是，LLM 的回應延遲取決於 Provider，不是底座能控制的——所以這些指標衡量的是底座自身的效率，不是模型的速度。之後靠水平擴展做叢集。

可靠性

兩個基本契約：已註冊的 Profile 設定與已寫入的 Session 資料不能遺失；Provider 失敗往上拋錯；Tool 失敗則用指數退避重試，最多三次。這裡的「不能遺失」是企業使用者最在意的底線。

安全

核心階段做三件事：HTTPS、敏感設定加密儲存、應用層白名單（路徑／指令／網域三類檢查），確保工具不會越權讀到主程序的資料。完整的認證、Docker 沙箱、SSO 都屬擴展階段。合規上，OryxOS 不主動把資料送出去，資料都留在企業基礎設施；它提供達成合規的技術能力，但不代替企業做認證。

已知風險：這份文件自己划的重點

  • 範圍風險：12 小時內要塞進五個能力，範圍控制是最大挑戰。
  • Spring AI 相容性：與框架的整合可能有地雷。
  • 工具執行安全：白名單夠不夠擋住危險指令。
  • Java 啟動與記憶體：Java 底座的啟動成本是個現實問題。
  • 社區不確定性：擴展層依賴社區，節奏不可控。
  • 定位被誤讀：核心階段只是 kernel，差異化在治理層——若不說清楚，容易被誤判為「功能太少」。

需求文件也把一些未定問題留給技術方案：Provider 抽象層怎麼定義、SQLite 與 H2 怎麼選、Bootstrap 的載入順序、何時引入 GraalVM。這些不是遺漏，而是刻意把決策留到它該被決定的階段。

怎麼用這份驗收標準

往後每個模組節點都應該回頭對這四層尺。當你不確定某個功能該不該做、要做到什麼程度時，答案幾乎都在這份需求文件裡：先問它在核心／擴展／社區哪一層，再問它對應哪一條驗收標準。這份需求文件之所以是「錨」，是因為它把範圍與完成定義都寫死了。
