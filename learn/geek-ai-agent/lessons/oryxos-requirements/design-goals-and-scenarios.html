四個設計目標與三個典型場景

Step 4/5 · OryxOS 需求

學習目標

能背出「統一、私有、易接入、可觀測」四個設計目標並解釋各自對應的工程要求，再用三個典型場景說明這些能力組合起來長什麼樣。

四個設計目標：八個字的取捨尺

需求文件用四個詞總結整個產品的核心目標。這八個字不是口號，每一個都對應到具體的工程要求，也是往後每個設計決策的評分標準。

目標意思對應的工程要求
統一多個業務 Agent 共用同一個底座一套 Profile／渠道接入／模型路由／工具/記憶，服務多個 Agent
私有資料留在企業自己的基礎設施上模型可接外部 API，也可接本地的 Ollama / vLLM
易接入用企業熟悉的方式接進來標準 Spring Boot 結構，直接整合 ERP／CRM／CMDB／SSO／監控；工具用 MCP 或 Spring Bean
可觀測跑起來之後看得見Prometheus 指標、結構化 JSON 日誌、健康檢查、Web 儀表板

這四把尺要一起用，因為它們經常互相拉扯。舉例來說，「私有」可能逼你放棄某個只有雲端版本的最強模型；「統一」可能逼你在單一 Agent 的彈性上妥協；「可觀測」意味著每個模組都得留痕跡，而不是跑得通就好。當兩個方案難分高下時，回頭看這四個詞，答案通常就出現了。

三個典型場景：全形使用的樣子

場景描述的是「目標形態」——五個能力都做完之後，業務方實際怎麼用。核心階段先交付 runtime kernel，場景要等擴展階段才完整成立。

場景一：運維助手

運維團隊在企業微信裡問 Agent：「昨晚那台機器的告警怎麼回事？」Agent 透過渠道收到訊息，呼叫監控告警介面查詢、讀取 runbook 知識庫、必要時執行自癒腳本，最後把處置建議回覆到群裡。這裡用到的是渠道接入 + Tool（企業系統）+ Memory（記住這次故障）。

場景二：知識管理助手

法務或業務在飛書裡問：「這份合約的違約條款怎麼寫的？有沒有跟去年那份衝突？」Agent 檢索合約與法律知識庫，帶著引用出處回答。這裡考驗的是長期記憶與檢索品質，以及「答案必須可溯源」這種企業級的硬要求。

場景三：銷售助手

業務在 CRM 裡問：「幫我整理明天要拜訪的客戶簡報。」Agent 把 CRM 的客戶資料、企查查的 MCP 工具查到的工商資訊、以及內部知識庫整合起來，輸出一份客戶簡報。這裡展示的是多個外部系統 + MCP 工具 + 模型輸出的組合。

場景背後的共同結構

三個場景看起來完全不同，但拆開來都是同一個骨架在動：訊息從某個渠道進來 → ReAct 迴圈規劃並呼叫工具 → 工具存取企業系統或知識庫 → Memory 保留上下文 → 結果從渠道出去。業務方不需要知道底下有幾個模組；他們只需要設定一個 Profile、寫一個 Plugin Tool、呼叫 Web Service。這正是「底座」的價值——場景不是獨立模組，而是五個能力的組合。

所以需求文件才會說：只要五個能力夠紮實，業務側要做的不過是三件事——設定 Profile、寫 Plugin Tool、呼叫 Web Service。這句話是整個 OryxOS 分層哲學的縮影。
