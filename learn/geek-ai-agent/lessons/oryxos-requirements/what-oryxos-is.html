OryxOS 是什麼

Step 1/5 · OryxOS 需求

學習目標

能用一句話說清 OryxOS 是一個裝在企業自己基礎設施上的 Agent OS，並解釋它的兩階段交付（先做 runtime kernel、後做治理層）為什麼是這樣切的。

先看一個對比：runtime 與 Agent OS

「讓一個 Agent 跑起來」和「讓一群 Agent 在企業裡被管起來」是兩件不同的事。前者叫 Agent runtime（Agent 執行環境）：它負責 LLM 呼叫、工具執行、上下文累積、迴圈控制。後者叫 Agent OS（Agent 作業系統）：它負責生命週期、統一入口、統一記憶、多租戶與審計。

runtime 之於 Agent OS，就像「單一程式的執行環境」之於「管理一群程式、調度資源、提供共享服務的作業系統層」。

這個區分很重要，因為它直接決定了 OryxOS 的定位。OryxOS 要做的是後者——它是那個「跑一群 Agent 的底座」，不是某一隻 Agent 本身。

一句話定義

OryxOS 是一個以 Java 寫成、面向企業的 Agent OS，安裝在企業自己的 K8s 或伺服器上。向上，它給各種業務 Agent（運維、客服、HR、銷售……）一個統一的 runtime；向下，它接住模型、渠道、工具、記憶、身份與審計。

它要解決的不是「怎麼寫一個 Agent」，而是「一個企業怎麼同時跑好幾十個 Agent，還共用同一套渠道接入、模型路由、工具呼叫、記憶與沙箱執行」。這也是它被歸類為「OS」而不是「框架」的原因。

為什麼企業非得有自己的底座

企業不是買不到平台能力——大廠的 Agent 平台一應俱全。真正的問題是平台給的是能力，不是控制權。有四件事是花錢買不到的：

買不到的東西為什麼平台給不了
資料主權私有資料、知識庫、會話記錄不能離開企業；模型可以換，資料必須留下
審計與合規每一次工具呼叫、每一條決策鏈都要可追溯，滿足內控與監管
多 Agent 治理幾十個 Agent 的註冊、權限、配額、生命週期要集中管理
模型自由多 Provider 抽象，隨時切換或混用，不被單一供應商鎖死

所以實務上的分界線很清楚：標準化、低價值的場景交給平台（通用問答、文件摘要、一次性驗證）；與核心業務耦合、涉及私有資料／權限／審計、會長期沉澱成資產的部分，必須自己做。兩者是分工，但底座得握在自己手上。

交付方式：先核心、後治理

OryxOS 的交付切成兩個階段，這是一個很刻意的取捨：

階段目標內容
核心階段最短可跑的 runtime kernel只用 4 週 × 每週 3 小時（12 小時），蓋出五大能力，對齊開源 Agent OS 的基本盤
擴展階段讓它「敢進企業」的治理層多租戶、SSO、審計、工具治理、企業系統整合；後續由社區長期維護

為什麼不一次做完？因為在 12 小時的硬約束下，先證明「引擎能跑」比先證明「治理完整」划算得多。核心階段刻意不做的東西很多：Provider 不做 fallback 與競速、ReAct 不做並行工具呼叫與上下文壓縮、Memory 不做自動事實抽取與語義檢索、Tool Policy 與容器沙箱推遲、Web Service 不做認證。這些不是能力不足，而是範圍控制。

核心階段的成果，是一個可示範的最小完整 Agent OS runtime kernel；企業級的差異化，留給之後的治理層。這條「先 kernel 後治理」的主線，會貫穿整個 OryxOS 的需求、技術方案與實作。
