# Deployment workflow and SPA routing

## Learning goal

Execute the build → S3 → invalidate pipeline; fix client-side routing with custom error pages and Lambda@Edge

## Steps

1. [[learn/aws-v3/nodes/deployment-workflow-and-spa-routing/deployment-workflow|部署工作流：build → S3 → invalidate]] — 完整的部署流程，以及為什麼只上傳 S3 使用者仍看到舊版
2. [[learn/aws-v3/nodes/deployment-workflow-and-spa-routing/client-side-routing-problem|SPA 用戶端路由的 404 問題]] — 為什麼 /about、/notes/123 這些深層連結回傳 404（after step 1）
3. [[learn/aws-v3/nodes/deployment-workflow-and-spa-routing/custom-error-pages|自訂錯誤頁面：把 404/403 導回 index.html]] — 把錯誤回應對應到 index.html 並以 200 回傳，讓 SPA router 接管（after step 2）
4. [[learn/aws-v3/nodes/deployment-workflow-and-spa-routing/lambda-at-edge|Lambda@Edge：在邊緣執行的進階路由邏輯]] — 當自訂錯誤頁面不夠時，在邊緣節點執行的進階方案（after step 3）
5. [[learn/aws-v3/nodes/deployment-workflow-and-spa-routing/course-wrapup|課程收尾：可程式化的 CDN 與下一步]] — 總結可程式化 CDN 的成果與後續探索方向（after steps 1, 4）

## Lesson

前面幾個節點分別教了 S3 靜態託管、CloudFront 加速與快取控制，這節把它們串成一套真正能上線的部署流程，再補上 SPA 落地前最常踩的坑。上傳到 S3 不等於部署完成——只要 CloudFront 邊緣快取還在，使用者就會一直看到舊版；所以完整流程是 build、上傳 S3、再 invalidate 快取，三步缺一不可。

第二個坑是路由。SPA 的 /about、/notes/123 是瀏覽器端路由，不是 S3 裡的真實檔案，直接訪問會回傳 404。解法有兩層：先用自訂錯誤頁面把 404/403 導回 index.html，讓 router 接手；更複雜的需求則交給 Lambda@Edge 在邊緣執行程式邏輯。走完五步，你就擁有了一套可程式化的 CDN，也能在面試中把「部署、快取、路由」這條鏈路講清楚。
