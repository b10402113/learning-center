# CloudFront caching

## Learning goal

Configure TTL, run invalidations, and tune behavior settings for different content types

## Steps

1. [[learn/aws-v3/nodes/cloudfront-caching/how-cloudfront-caching-works|快取如何運作：為什麼部署後使用者還看到舊內容]] — 建立「邊緣快取 vs origin」的心智模型，看懂 TTL 何時讓 CloudFront 回 origin 檢查
2. [[learn/aws-v3/nodes/cloudfront-caching/ttl-and-cache-control|TTL 與 Cache-Control：新鮮度與效能的取捨]] — TTL 預設從 behavior 來、origin 的 Cache-Control 可覆寫，以及新鮮度與效能的取捨（after step 1）
3. [[learn/aws-v3/nodes/cloudfront-caching/cache-invalidation|快取失效（Invalidation）：強制拋棄邊緣快取]] — invalidation 做什麼、如何在全球傳播，部署後如何讓使用者拿到新內容（after step 1）
4. [[learn/aws-v3/nodes/cloudfront-caching/invalidation-costs|Invalidation 的計費：前 1,000 次免費與 wildcard 代價]] — 計費規則與如何設計部署以減少 invalidations（after step 3）
5. [[learn/aws-v3/nodes/cloudfront-caching/behavior-settings|Behavior 設定：依內容類型調校快取]] — 按 path pattern 設定、header/cookie 對 cache key 的影響、靜態 vs 動態內容的調校（after steps 2–3）

## Lesson

CDN 的快取讓內容在邊緣節點就近服務，代價是「內容會變舊」。部署新版本後，使用者仍可能從邊緣節點拿到舊檔案——因為 CloudFront 不知道 origin 已更新。這個節點講的就是控制這組時間差的旋鈕：TTL、invalidation、behavior settings。

快取怎麼運作、為什麼會變舊，是一切的前提；接著 TTL 與 Cache-Control 決定「多久回 origin 檢查一次」，invalidation 則提供「立刻拋棄舊快取」的強制手段。用完要付費，所以還要懂計費規則；最後 behavior settings 把這些旋鈕按 path pattern 分配到不同內容類型——靜態資源可以快取很久，動態頁面則要更頻繁回 origin。五步走完，你就能回答「為什麼部署後還是舊版、該怎麼修」，也能在面試中解釋 TTL 與 invalidation 各自扮演的角色。
