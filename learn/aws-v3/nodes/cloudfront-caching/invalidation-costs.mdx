# Invalidation 的計費：前 1,000 次免費與 wildcard 代價

<LearningGoal>
能說出 invalidation 的計費規則（每月前 1,000 次免費、wildcard 計多次），並據此設計部署流程。
</LearningGoal>

## Lesson

### 失效是要錢的

上一課你學會了 invalidation 怎麼用。但它不是免費的——AWS 按失效請求計費。好消息是，門檻很高，對你這種規模幾乎不會碰到。但知道了規則，你才不會在某一天收到意外的帳單。

每個月前 1,000 次 invalidation 免費；超過之後，每一次失效請求收 `$0.005`（約新台幣 0.16 元）。

### Wildcard 的代價

這裡有個容易踩的坑：用 `/*` 這種 wildcard（萬用字元）路徑失效時，不是算一次，而是按它涵蓋的路徑數量計費。也就是說，一個 `/*` 失效請求，會按你 distribution 裡實際存在的路徑數去拆算多次請求。資料量大的網站，一次 `/*` 就可能吃掉你整月的免費額度。

所以「省事、清光光」的 `/*`，在有大量路徑時反而最貴。這正是為什麼上一課要強調：失效清單要精準——列 index.html 和幾個 public 檔案就好，不要動不動就失效全部。

### 別為了「聰明」而過度失效

不要寫一個 script，故意「為每個變更的檔案都做一次失效」。這種自作聰明的做法只會讓你的失效次數暴增、費用上升、部署流程變慢——而它買來的「好處」幾乎沒有。有時「簡單、甚至有點笨」的版本才是更好的版本。與其細緻地逐檔失效，不如把帶 hash 的資產處理好，讓失效清單永遠只有寥寥幾個檔案。

回想第一課的架構：如果你的建置工具把每個檔案都加上 hash，那唯一需要失效的永遠只有 `index.html` 這類沒 hash 的入口檔案。用「hash 替身」來避免失效，才是從源頭省錢的做法——這比任何失效優化都有效。

### 把規則套回你的部署

把前兩課學的合起來，一個合理的部署流程是：

1. 建置出帶 hash 的資產 + index.html
2. 同步所有檔案上 S3
3. 只失效 `/index.html`（加上變動的 public 檔案）

以你目前每月幾次部署的頻率，失效次數離 1,000 的免費門檻非常遠。真的有一天你一個月失效超過 1,000 次——那你每天部署 30 次以上，那時「失效費」會是你最不煩惱的問題。

### 自檢

- 免費額度是多少？超過後每一次多少錢？
- 為什麼 `/*` 失效可能一次吃掉大量額度？
- 「逐檔失效」的 script 為什麼是壞主意？
- 從源頭把失效次數降到最低的做法是什麼？
