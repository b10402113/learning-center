# Digest — aws-v3

## Overview (L1)

- Deploying new app versions — When deploying a new version of a web app to S3 behind CloudFront, the old cached version persists at edge locations until invalidated. The deployment workflow is: build the app, upload to S3, then invalidate CloudFront cache.

## Sections (L2)

### New deployment

- Locator: `[[sources/aws-v3/deploying-new-versions#new-deployment]]`
- Summary: Covers uploading a new version of the application to S3 as the deployment step.
- Key claims: S3 holds the authoritative version of the app; uploading new files to S3 updates the origin; S3 uploads are fast but do not immediately affect what users see.
- Learner-relevant: Understanding that S3 upload alone is insufficient for deployment — the CDN layer must also be addressed.

### Cache persistence

- Locator: `[[sources/aws-v3/deploying-new-versions#cache-persistence]]`
- Summary: Explains that without invalidation, CloudFront edge locations continue serving the old cached version even after S3 has been updated.
- Key claims: Cached content at edge locations is independent of origin updates; old versions persist until TTL expires or invalidation is triggered; users may see inconsistent versions during the window.
- Learner-relevant: This is the key deployment gotcha — without invalidation, deploying to S3 does not actually deploy to users.

### Deployment workflow

- Locator: `[[sources/aws-v3/deploying-new-versions#deployment-workflow]]`
- Summary: Defines the complete deployment pipeline: build the application, upload build output to S3, then invalidate CloudFront cache to propagate changes globally.
- Key claims: The workflow is build → S3 upload → CloudFront invalidation; each step is necessary and order matters; the workflow can be automated via scripts or CI/CD.
- Learner-relevant: Provides the complete, repeatable deployment pattern for static sites on S3 + CloudFront.
