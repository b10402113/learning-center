快取如何運作：為什麼部署後使用者還看到舊內容

學習目標：說出邊緣快取與 origin 的關係，並解釋部署後為何使用者仍可能看到舊內容。

先看現象：部署完了，使用者卻還在用舊版

假設你剛把網站的新版本推到 S3，打開 CloudFront 的網址確認——哇，是新版。但你的朋友在別的城市打開，看到的還是舊的。不是你沒部署好，而是快取在作怪。

上一節你建立了 CloudFront distribution，知道內容會被複製到全球的邊緣節點（edge location）——離使用者最近的快取伺服器。使用者的請求打到最近的邊緣節點，如果那裏有快取，就直接回傳，根本不會問 origin（你的 S3 bucket）。

問題就在這：CloudFront 不知道你的 origin 已經更新了。它只知道「我手上的這份快取還沒過期，照舊服務就好」。於是舊版本繼續被服務，直到某個機制告訴它「該回去看看了」。

核心概念：TTL 決定「多久回去問一次」

那個機制就是 TTL（Time To Live，存活時間）——一份快取在邊緣節點上可以存活的時間。TTL 沒過期，CloudFront 就直接回傳快取；TTL 過期了，它才回到 origin 檢查有沒有新版。

用快遞來想：你公司每個月送一次月刊到各分店。分店把月刊放櫃檯，客人來就拿走。TTL 就是「這期月刊可以放多久」。只要期限沒到，分店不會打回總公司問「有沒有新的一期？」——這樣又快又省。但代價是：總公司換了新封面，分店櫃檯還是舊的那期，直到期限到、重新進貨為止。

核心概念 CDN 的取捨本質是「快」與「新」的對抗：快取越久，回應越快，但內容越容易變舊；快取越短，內容越新鮮，但每次都要打回 origin，更慢也更貴。TTL 就是這把旋鈕。

為什麼有些檔案「永遠」不會舊，有些卻會

這裡有個很關鍵的細節，跟你的前端工具鏈有關。Vite 或 webpack 這類建置工具，會把 CSS 和 JavaScript 產出成帶指紋（fingerprinted）的檔名，像是 index-8f3c9a.js——檔名裡有內容的 hash。

內容一變，檔名就變。所以舊的 index-8f3c9a.js 再也沒人會去請求——瀏覽器要的是新的 index-4b2d7e.js。這類資產就算快取設很久也沒問題，因為根本不會被重複用到舊版本。

但 index.html 不一樣：它沒有 hash，檔名永遠不變，而且它永遠指向最新的帶 hash 資產。你的部署流程通常是「把一堆新資產同步上 S3 + 更新 index.html」——偏偏 index.html 這份快取最有可能在邊緣節點上存留，導致使用者開啟舊網頁、再引用到舊的 JS。所以 index.html 是整個系統裡「最容易變舊、最需要處理」的那一個。

一句話記法 帶 hash 的資產靠「改名」解決變舊問題；不帶 hash 的檔案（尤其 index.html）只能靠 TTL 到期或主動失效來解決——後者就是下一課的 invalidation。

那部署的正確姿勢是什麼？

所以完整的部署不該只是「把檔案丟上 S3」就結束。標準流程是：先同步資產上 S3 → 等全部上傳完 → 再想辦法讓舊快取失效 → 使用者下次請求就拿新內容。你可以在 CloudFront 控制台手動做這件事，也可以寫成 script 或 GitHub Action，讓它在每次部署後自動執行。

Steve 在課程裡還點了一個經典梗：電腦科學的兩大難題是「命名、快取失效，和 off-by-one 錯誤」——第三個是笑點，但也說明快取失效（cache invalidation）在業界有多麻煩。你現在會親手處理它，很好。
