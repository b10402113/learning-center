SPA 用戶端路由的 404 問題

學習目標：能解釋為什麼 SPA 的深層連結（如 /about、/notes/123）在 CloudFront 上回傳 404，以及這如何破壞深層連結與重新整理頁面。

先回到一個老問題：URL 是真的檔案嗎？

在傳統的多頁網站裡，每個 URL 對應一個真實存在的 HTML 檔案：/about 就是 about.html，/notes/123 就是某個資料夾裡真的存在的頁面。伺服器照著 URL 找檔案，找到就回傳。

但你的 React app 是單頁應用（SPA，Single-Page Application）。S3 裡其實只有少數幾個真實檔案：index.html、一個帶 hash 的 index-xxxx.js、一個 index-xxxx.css。剩下的路由，例如 /about、/notes/123，都是由瀏覽器端的用戶端路由（client-side router）虛擬出來的——URL 看起來很漂亮，但 S3 裡根本沒有這些檔案。

核心概念 SPA 路由是虛擬路徑，不是檔案。 用戶端 router 在瀏覽器裡把 URL 對應到不同的畫面（view），但不會在伺服器上產生對應的檔案。

現象：直接訪問深層連結 → 404

假設你在瀏覽器網址列直接輸入 https://your-site/notes/123，或是在這個頁面按 F5 重新整理。瀏覽器會把請求送到 CloudFront，CloudFront 照著 URL 去 S3 找一個叫 notes/123 的物件——當然找不到，因為它根本不存在。

於是 CloudFront 回傳 404 Not Found。更糟的是，你的 SPA 根本沒機會載入——因為沒有 index.html 被回傳，瀏覽器就沒東西可跑，user router 根本沒上場。

場景發生什麼
使用者從首頁點連結進入 /notes/123Router 在瀏覽器內切換畫面，一切正常
直接輸入 /notes/123 或按 F5瀏覽器把請求送給 CloudFront → S3 找不到檔案 → 404

這叫深層連結（deep link）被破壞：任何「直接訪問某個路由」或「重新整理頁面」的使用者，都會撞上 404。對一個把連結分享出去的 SPA 來說，這是致命的——別人收到你分享的 /notes/123 連結，點開卻是錯誤頁面。

為什麼「使用者端 route」不行，得靠伺服器

關鍵在於誰來「解釋」這個 URL。在 SPA 裡，解釋 URL 的是瀏覽器裡的 JavaScript；但瀏覽器只有在拿到 index.html 並執行完 JS 之後，才知道該顯示哪個畫面。伺服器端（這裡是 CloudFront / S3）對這些虛擬路由一無所知——它的工作只是「給定路徑，找檔案」。

所以解法必須在伺服器這一側動手腳：讓 CloudFront 遇到「找不到的路徑」時，別回 404，而是把 index.html 交給瀏覽器，讓 router 接手。這就是下一課的自訂錯誤頁面。

一句話記法 SPA 把「URL 對應畫面」的工作放在瀏覽器，伺服器不知道你的路由。 所以任何直接訪問深層連結的請求，伺服器都只能聳肩說 404。

回到面試語言

把問題收成一句話：「SPA 的路由是客戶端虛擬出來的，不是 S3 裡的真實檔案。因此直接訪問深層連結或重新整理時，CloudFront 找不到對應物件而回傳 404，破壞了深層連結。解法是在伺服器端把這些路徑導回 index.html，讓 router 接管。」
