課程收尾：可程式化的 CDN 與下一步

學習目標：能總結這次部署的成果——一套可程式化的 CDN——並說出接下來值得探索的 AWS 主題（資料庫、邊緣運算）。

你完成了什麼？一套可程式化的 CDN

回顧整個學習路徑，從「為什麼需要 AWS」一路走到現在，你最終建好的是：一個用 S3 當 origin、用 CloudFront 加速與控管的靜態網站部署，而且整套 CDN 的運作方式都可以由你設定。

「可程式化」不是形容詞，是能力清單。回想你一路調過的旋鈕：

  1. Behavior 設定 — 依 path pattern 決定不同內容的快取策略
  2. TTL / Cache-Control — 控制內容多久回 origin 檢查一次
  3. Invalidation — 部署後強制拋棄舊快取
  4. Custom error responses — 把 404/403 導回 index.html，解決 SPA 路由
  5. Lambda@Edge — 在邊緣執行真正的程式邏輯

每一項都是「設定 CDN 的行為」。你不再只是把檔案丟上去，而是擁有了一座可以照你的意思調整的內容分發基礎設施。這就是這個課程的目標：got a programmable CDN——一套能真正上線、也能在面試中講清楚的靜態站部署。

核心概念 可程式化 CDN = 靜態快取 + 你可控的行為設定。 快取管「快」，設定管「怎麼快、給誰、要不要改寫」。

整套鏈路的心智模型

把十五個節點收成一句話的記憶錨點：

內容進得去（S3 物件儲存），發得出去（CloudFront 全球快取），變得了（TTL + invalidation），認得路（custom error + Lambda@Edge 路由）。

面試時，別人問「你部署過什麼」，你可以說：我把 React 靜態站部署到 S3 + CloudFront，用 bucket policy 控制存取、用 TTL 與 invalidation 管理快取、用 custom error responses 解決 SPA 深層連結，還知道 Lambda@Edge 能把它變成 programmable 的 CDN。

接下來值得探索的方向

AWS 的世界遠比 S3 與 CloudFront 大。這個課程為你鋪了三條路：

方向是什麼為什麼值得
資料庫Aurora（SQL，MySQL 相容）、DynamoDB（NoSQL）讓你的應用從「靜態」變「動態」
邊緣運算Lambda@Edge 讀 Redis、資料庫、改寫請求把邏輯帶到離使用者最近的節點
Lambda 與環境變數用 env vars 設定行為，不改程式碼安全地存放 API key 等設定

特別是 Lambda@Edge——上一課我們看到它能在邊緣做 URL 改寫、驗證、A/B 測試。當你開始把資料庫接進 Lambda，你的 CDN 就真的從「分發靜態檔」升級成「動態的程式化邊緣」了。

一句話記法 你已經有了 CDN 的引擎，接下來的課程只是往引擎上加零件。 Aurora / DynamoDB 是記憶，Lambda@Edge 是思考，環境變數是設定。
