CDN 是什麼：邊緣節點與快取階層

學習目標：說出邊緣節點 / 區域邊緣快取 / origin 的分層架構，以及首次請求 vs 後續請求的延遲差異。

心智模型：一份 origin，全球快取副本

上一步我們說「把 bucket 放到每個區域」不現實。CDN 的做法是反過來：內容只有一份放在 origin，但在全球各地放快取副本。

Steve 的說法很直白：不要只有一個 bucket、一個地方，而是在全世界放很小的基礎設施。第一個使用者付費，之後所有人都受益（AWS 課程 13，cdn-concept）。

三層快取階層

層級位置角色
Edge location（邊緣節點）離使用者最近第一線快取，回答「有沒有快取」
Regional edge cache（區域邊緣快取）地理區域層級彙整一個區域的請求，減少打回 origin
Origin（origin 伺服器）S3 bucket（美東）唯一權威內容來源

請求流程：使用者連到最近的邊緣節點 → 有快取就回傳 → 沒有就往區域邊緣快取找 → 再沒有才打到 origin（caching-tiers）。

首次請求 vs 後續請求

核心概念 第一個使用者付冷啟動成本。 澳洲西岸第一個使用者要一路打到美東 origin；但只要澳洲東岸有人先訪問過，區域邊緣快取就填滿了，西岸使用者只要到東岸拿快取即可——差距是幾毫秒對上約 200ms。

Steve 用真實數據證明：CDN Perf 測試中，距離 origin 越近的地方延遲越低，越遠越糟；掛上 CDN 後，從墨爾本訪問的延遲大幅下降——「請求幾乎像是從屋子裡發出的」。

額外紅利：可靠性

就算 S3 出了狀況，每個還有快取的區域節點依然能正常供服務——那一刻根本沒在讀 bucket。S3 的 SLA 是 99.9%（目標 99.99%），但「用不到的保護」讓日常體驗更好，也多了幾層緩衝。

代價：複雜度

多一層基礎設施，就多一點可以壞掉的東西。緩解冷啟動的手段（例如用 Pingdom 定期 ping 自己的 CDN 來 warm up cache）也是額外基礎設施。Steve 的建議：先測量，再決定——如果你的使用者就在附近，這層優化未必值得。

面試要點 「CloudFront 是 AWS 的 CDN，採用三層快取：邊緣節點最靠近使用者，區域邊緣快取彙整地理區域，origin 是權威內容來源。第一個請求打到 origin 付冷啟動成本，之後的使用者從最近的快取層取資料。」
