物件儲存 vs 檔案系統：差異與 EFS

學習目標：能分辨物件儲存與檔案系統的差異，並說出什麼時候需要改用 EFS。

一個你會遇到的困惑

你在自己的電腦上整理檔案，習慣了這些操作：雙擊改一個檔案、存檔、鎖定某個檔案讓別人不能動、在資料夾之間搬來搬去。現在你開始用 S3，第一個困惑就來了——「我怎麼不能像平常那樣改檔案？」

不是你不會操作，而是 S3 從設計上就不做檔案系統做的事。它兩者天生不同，不是同一件事的兩種版本。

檔案系統會做、S3 不做的事

行為傳統檔案系統S3
就地編輯檔案可以，直接在原檔案上改不行，要上傳一個新版本取代舊的
檔案鎖定可以鎖住檔案沒有鎖定的機制
資料夾與路徑有真正的目錄結構扁平的 key 命名空間
核心概念 S3 沒有「就地編輯」或「檔案鎖」。你更新一個物件，本質上是「上傳一份新的，讓它取代舊的那份」——S3 根本不認識「檔案開啟、修改、儲存」這套流程。

當你真的需要檔案系統：EFS

那如果某個專案就是需要真正的檔案系統語意呢？比如很多台伺服器要共用同一份檔案、要鎖定檔案、要就地修改。AWS 為這個場景準備了另一個服務：EFS（Elastic File System，彈性檔案系統）。

EFS 提供的是貨真價實的檔案系統——有目錄、有路徑、可以被多台機器當成一般磁碟掛載使用。它解決的是 S3 天生做不到的那一類需求。

這個區別為什麼影響架構

搞錯這兩個概念，你的架構選擇就會出錯。舉例：你想讓使用者上傳頭像並隨時修改——用 S3 就好，換版本就上傳新的。但如果你的應用需要多台運算實例即時共享並鎖定同一份設定檔——那就是 EFS 的領域。先搞清楚「我要的是不是檔案系統行為」，再決定用哪個服務。

面試要點 「S3 是物件儲存，不支援就地編輯和檔案鎖等檔案系統語意。當我需要真正的檔案系統（例如多台機器共享並鎖定檔案）時，會用 EFS。」
