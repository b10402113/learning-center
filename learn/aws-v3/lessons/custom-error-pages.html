自訂錯誤頁面：把 404/403 導回 index.html

學習目標：能設定 CloudFront 自訂錯誤頁面，把 404 與 403 回應對應到 /index.html 並以 200 狀態碼回傳，讓 SPA router 接管路由。

好消息：這是設定，不是寫程式

上一課我們診斷出問題：直接訪問 /notes/123 時，CloudFront 去 S3 找不到檔案，回傳 404，router 沒機會上場。好消息是——這個問題不需要改任何程式碼，改 CloudFront 的設定就能修好。

CloudFront 有一個功能叫自訂錯誤回應（custom error responses），或稱自訂錯誤頁面。它的概念是：「當 origin 回傳某個錯誤碼時，不要照著回傳給使用者，而是改用我指定的替代方案。」

核心概念 把「找不到」轉譯成「給 index.html」。 對 SPA 來說，任何路徑都該得到 index.html，讓 router 決定顯示什麼。錯誤頁面設定做的就是這件事。

具體怎麼設：404 → /index.html，狀態碼 200

我們需要兩條規則：

origin 回傳CloudFront 改成
404 Not Found回傳 /index.html，狀態碼 200 OK
403 Forbidden回傳 /index.html，狀態碼 200 OK

在 CloudFront 控制台的 distribution 設定裡，有個「Error Pages」分頁，你可以新增錯誤回應：設定「錯誤碼 = 404」「回應頁面路徑 = /index.html」「HTTP 回應碼 = 200」。403 也做一組一模一樣的。為什麼 403 也要？因為當 S3 bucket 設定成不允許公開存取某些路徑時，origin 會回傳 403 而不是 404——兩種都可能出現，乾脆一起處理。

這樣一來，發生了什麼？

使用者訪問 /notes/123 → CloudFront 去 S3 找不到 → 原本要回 404 → 依設定改回傳 index.html 並標成 200 → 瀏覽器載入 index.html，執行 JS → router 啟動 → router 看到目前 URL 是 /notes/123，顯示對應的筆記畫面。整個鏈路就通了。

換句話說：錯誤頁面設定把「伺服器決定回什麼」改成了「把決定權交還給 SPA」。伺服器不知道 /notes/123 是什麼，但它知道把 index.html 給你，你自己想辦法。

一個誠實的瑕疵：假的 200

這個解法有個被許多人接受的瑕疵：當使用者訪問一個真的不存在的路徑（例如 /totally-bogus）時，伺服器也會回傳 index.html 並標成 200。你的 app 內部可能顯示「404 頁面」，但 HTTP 狀態碼是 200——對瀏覽器、對 SEO、對監控工具來說，這看起來像「一切正常」。

對大部分應用這無傷大雅，業界也普遍這麼做。但如果你的需求是「真的讓不存在的頁面回傳真正的 404」，就需要更聰明的方案——那正是下一課 Lambda@Edge 的用武之地。

一句話記法 錯誤頁面設定 = 伺服器的「全都要 index.html」開關。 一行設定，讓深層連結與重新整理都能正常工作。

回到面試語言

「SPA 部署到 CloudFront 後，要設定 custom error responses：把 404 與 403 對應到 /index.html、回應碼設成 200。這樣深層連結和重新整理時，CloudFront 一律把 index.html 交給瀏覽器，由 client-side router 接手。代價是真正不存在的頁面也會回 200——要更精確的話，改用 Lambda@Edge。」
