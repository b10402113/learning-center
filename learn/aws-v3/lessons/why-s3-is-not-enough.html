為什麼 S3 單獨不夠：三個硬限制

學習目標：說出 S3 靜態網站託管的三個硬限制，並解釋為何正式上線需要 CDN。

回顧：S3 靜態託管「能看」但「不能上線」

上一節你完成了第一次部署——打開 website endpoint，網站能跑。Steve 的總結很直接：S3 靜態網站託管的唯一賣點是「簡單」，一顆按鈕就上線。 但除此之外，它是所有選項裡最差的那個（AWS 課程 12，s3-hosting-limitations）。

問題不是「你設定錯了」，而是功能根本不提供。這三個限制是硬性的，不是任何配置選項能繞過的。

限制一：自訂網域沒有 HTTPS

S3 的 website endpoint 只支援 HTTP。瀏覽器現在對非 HTTPS 網站會直接警告，而且許多現代瀏覽器 API——navigator.clipboard、geolocation——只有在 HTTPS 下才能用。

面試要點 「S3 靜態網站託管只提供 HTTP endpoint，無法在自訂網域上直接啟用 HTTPS。而瀏覽器對非 HTTPS 的限制越來越嚴格，所以這對正式產品是硬傷。」

限制二：不能設定 cache-control 標頭

你用過 Vercel 或 Netlify——部署完圖片秒開，重複訪問幾乎零延遲。這背後是 CDN 的快取。但 S3 靜態託管沒有讓你設定 cache-control 的介面，瀏覽器每次都要重新抓取檔案。

沒有快取意味著：每一次請求都打到 origin、每一次都重新下載。對靜態資產來說，這既慢又貴。

限制三：內容只從單一區域送出

你的 bucket 放在美東（如 us-east-1）。一個在台北的使用者打開網站，請求要穿越整個太平洋。Steve 用 CDN Perf 測過：從美東 ping 到澳洲要 253ms，而這還只是 ping——連第一個 byte 都還沒傳（transition-to-cloudfront）。

所有使用者都被迫走到同一個數據中心，距離問題完全沒被解決。

核心概念 CDN 要解決的就是這三個問題：HTTPS、可設定的快取、全球邊緣分發。而 CloudFront 正是 AWS 的 CDN——坐在 S3 前面，把這三件事一次補齊。

所以下一步：CloudFront

接下來的四步你將：建立 CloudFront distribution、把 S3 bucket 設為 origin、綁定自訂網域、用 ACM 開啟 HTTPS。最後再把 S3 的靜態網站託管關掉，避免兩套入口打架（disabling-s3-website-hosting）。

一個關鍵的心理準備：CloudFront 不是選配，是正式上線的必要下一步。 這也正是面試時「為什麼用 S3 + CloudFront 而不是只用 S3」的標準答案起點。

動手前想一想 你可能會想：「那把 bucket 放在離使用者最近的區域就好了？」——但使用者分佈在全球，不可能每個區域都放一份。CDN 用「一份 origin + 全球快取副本」解決，這正是下一課的主題。
