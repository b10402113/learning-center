Lambda@Edge：在邊緣執行的進階路由邏輯

學習目標：能說明 Lambda@Edge 是什麼、在 CloudFront 邊緣能做哪些事，以及它與自訂錯誤頁面方案的取捨。

當「假的 200」不夠用的時候

上一課的自訂錯誤頁面能解決 90% 的 SPA 問題，但它有一個瑕疵：不存在的路徑也回 200，而且它不能「看懂」URL 內容，只會盲目地把所有錯誤導到 index.html。

如果你的需求更複雜——例如「只有 /notes/* 導到 index.html，其餘真的 404」、或「把舊網址重新導向到新網址」、或「要求某些路徑先登入」——你需要真正的邏輯，而不只是靜態設定。這就是 Lambda@Edge 出場的時機。

核心概念 Lambda@Edge = 在 CloudFront 邊緣節點執行 Lambda 函式。 它讓你在請求「到達 origin 之前」和「從 origin 回來之後」的路上，用 JavaScript 插手處理請求與回應。

它是怎麼運作的

還記得第一課的架構嗎？請求的路徑是：使用者 → CloudFront 邊緣節點 → origin（S3）→ 回傳給使用者。

Lambda@Edge 就是在邊緣節點這個位置上，插入了執行 JavaScript 的鉤子。請求進來時可以先跑一段程式，再決定要不要送給 origin；回應出來時也可以再跑一段程式，改寫之後再回傳給使用者。

一個具體例子：你收到一個請求 /notes/123。普通的錯誤頁面設定只會「找不到就給 index.html」。Lambda@Edge 可以做到——在請求到達 origin 之前，就把這個 URL 改寫成 /index.html（URL rewriting），甚至先查一下「這個使用者是不是被封鎖的」，是的話直接改寫回應狀態碼、連 origin 都不用去。

能力怎麼用
URL 改寫（URL rewriting）把 /notes/123 改寫成 /index.html 再送 origin
請求攔截與驗證查封鎖名單，決定放行或直接拒絕
A/B 測試依條件把部分流量導向不同版本
動態內容在邊緣讀 Redis、資料庫，改寫回應
精確狀態碼真的不存在的頁面回真正的 404，而不是假的 200

為什麼「因為它是 Lambda」很重要

Lambda@Edge 裡跑的是完整的 Lambda 函式，用的是 JavaScript。這意味著它可以做的事，跟你在伺服器上寫的任何程式一樣多——它不是一個被侷限的設定值。你可以讀環境變數（environment variables）來設定行為而不改程式碼，可以連接 Redis 或資料庫來做判斷（例如查「這個使用者是否被封鎖」），可以在回應路徑上改寫任何東西。

這就開啟了「邊緣運算（edge computing）」的概念：把計算帶到離使用者最近的節點，而不是集中在一台伺服器。你的 CDN 從「靜態快取」升級成「可程式化（programmable）的 CDN」。

什麼時候用哪個？

兩個方案不是競爭，而是階梯：

方案複雜度適合
Custom error responses純設定，零程式碼標準 SPA：讓所有路由落到 index.html
Lambda@Edge要寫與維護函式需要判斷、改寫、驗證、精確狀態碼
一句話記法 錯誤頁面是「開關」，Lambda@Edge 是「程式」。 開關能解決一般 SPA；要更聰明、更精確，就寫程式。

回到面試語言

「Custom error responses 能把 404/403 導回 index.html，但無法分辨『真 404』和『SPA 路由』，也回不了精確的狀態碼。Lambda@Edge 讓我在 CloudFront 邊緣執行 Lambda——可以做 URL 改寫、驗證、A/B 測試，還能在請求到達 origin 前直接決定回應。代價是要寫函式、更複雜。它是把 CDN 變成 programmable 的關鍵一步。」
