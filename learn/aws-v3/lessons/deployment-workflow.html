部署工作流：build → S3 → invalidate

學習目標：能說出並執行 build → S3 上傳 → CloudFront invalidation 的完整部署流程，並解釋為什麼只上傳 S3，使用者仍然會看到舊版。

先看一個現象：上傳了，但什麼都沒變

你已經把 React app 建置成靜態檔案、上傳到 S3、接上了 CloudFront，一切看起來都運作正常。現在你修好一個 bug，重新 npm run build，把新的 dist/ 同步上 S3。結果你重新整理網頁——使用者還是看到舊版。

問題出在哪？S3 的確已經更新了，檔案是最新的。但使用者根本沒從 S3 拿檔案——他們是從 CloudFront 的邊緣節點（edge location）拿的，而邊緣節點還留著舊的快取。

核心概念 邊緣快取獨立於 origin。 S3 更新不會通知 CloudFront，邊緣節點也不會自己知道 origin 變了。除非 TTL 到期去重新檢查，或有人主動觸發失效（invalidation），否則舊版會一直撐在那裡。

為什麼「上傳完成」不等於「部署完成」

回到前面節點學過的心智模型：你的架構是 S3（origin，原始來源）→ CloudFront（快取層）→ 使用者。上傳只更新了 origin 這一層，而使用者看到的快取層完全沒動。

這帶來一個實際的困擾：在「S3 已是新版」但「邊緣仍是舊版」的這段視窗裡，不同的使用者可能看到不同版本——有人命中已更新的節點拿到新版，有人命中舊節點拿到舊版。對你自己測試很迷惑，對使用者就是 bug。

所以部署有三個步驟，缺一不可，而且順序很重要：

步驟做什麼如果漏掉會怎樣
1. build產生新的靜態產物（dist/）沒有新檔案可傳
2. 上傳 S3讓 origin 擁有權威版本origin 還是舊的，之後一切白做
3. invalidate CloudFront拋棄舊的邊緣快取使用者繼續看舊版——上傳形同沒發生

前兩個步驟你應該很熟了。第三步是這節課的重點：invalidation（快取失效）——告訴 CloudFront「這些路徑的舊快取不要再用了」，它就會讓所有邊緣節點拋棄舊檔，使用者下一次請求回到 origin 拿最新內容。

把流程變成可重複的腳本

每次部署都手動跑三個步驟很煩，而且第二步上傳後很容易忘了第三步。正確的做法是把它寫成一條指令，例如：

aws s3 sync dist/ s3://your-bucket --delete
aws cloudfront create-invalidation \
  --distribution-id YOUR_DIST_ID \
  --paths "/index.html"

這正是你在 GitHub Actions 或任何 CI/CD 工具裡會寫的內容：同步資產上 S3，全部上傳成功之後，再執行 invalidation。把「順序」寫死進 pipeline，就不會再發生「上傳了卻忘了失效」的慘劇。

一個細節：失效的路徑要列得精準。帶 hash 的資產（如 index-8f3c9a.js）內容變了檔名就變，舊檔名沒人請求，不需要失效；真正要失效的通常是 index.html 這類檔名不變、內容會變的入口檔案。

一句話記法 S3 是你的倉庫，CloudFront 是你的店面。換了倉庫的貨，不叫店面，店裡還擺著舊貨。 部署 = build → 上貨 → 清貨架。

回到面試語言

把這節課收成一句能說出口的話：「部署靜態站到 S3 + CloudFront，不能只上傳 S3——因為邊緣快取獨立於 origin，必須再對 CloudFront 執行 invalidation，才能讓使用者拿到新版。整個流程是 build → upload → invalidate，並把它自動化。」
