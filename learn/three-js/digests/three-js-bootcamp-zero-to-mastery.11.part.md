# Digest — three-js-bootcamp-zero-to-mastery (part 11)

## Overview (L1)

- **0066 Shadow Properties** — Spotlight and directional light shadow tuning: map size (512 default, power-of-two upgrades), radius blur, and the shadow camera's near/far properties. Directional light uses an orthogonal camera controlled by left/right/top/bottom instead of FOV.
- **0067 Shadow Properties** — PointLight shadows explained: six directional cameras make them expensive. Near/far properties behave unexpectedly — far also clamps the light itself, so avoid low values; prefer spot/directional shadows for performance.
- **0068 Shadow Map Types** — Renderer `shadowMap.type` options compared: `BasicShadowMap` (fast, low quality), `PCFShadowMap` (default), `PCFSoftShadowMap` (softer, ignores radius), and `VSMShadowMap` (unexpected artifacts). Recommends default or soft for quality/performance balance.
- **0069 Introduction** — Course congratulates the learner and introduces the capstone solar-system project in three.js: a portfolio-ready scene combining everything learned so far.
- **0070 Planning Our Project** — Project plan scaffolded: sun and planets as spheres, planets rotating on own axes and orbiting the sun, satellites orbiting planets, and reusable JavaScript functions to generate bodies instead of manual duplication.
- **0071 Adding Meshes** — First meshes added: sun (yellow `MeshBasicMaterial`, scaled 5), earth (blue, positioned at x=10), moon (gray, scaled 0.3, child of earth at local x=2). Establishes parent-child inheritance for orbital transforms.
- **0072 Planetary Orbit** — Circular orbit implemented via `Math.sin`/`Math.cos` on x/z axes driven by `Clock.getElapsedTime()`, multiplied by orbit radius. Naive parent-rotation approach rejected for multi-planet scenes because it locks all orbits to one rhythm.

## Sections (L2)

### 0066

- Locator: `[[sources/three-js/20260907/0066. Shadow Properties.srt#0066]]`
- Summary: Tuning spotlight and directional-light shadows through map size, blur radius, and shadow-camera frustum properties; directional light swaps FOV for an orthographic camera controlled by left/right/top/bottom.
- Key claims: Default shadow map size is 512 and must be a power of two; higher resolutions (1024/2048) reduce pixelation at performance cost; the `radius` property applies a cheap box blur to soften edges; spotlight shadow camera exposes near/far but FOV is currently non-functional; directional light uses an `OrthographicCamera` with left/right/top/bottom to bound the shadow frustum.
- Learner-relevant: Gives the learner a mental model of shadow rendering as a secondary camera pass and the knobs available to trade sharpness for performance — directly applicable to scene optimization.

### 0067

- Locator: `[[sources/three-js/20260907/0067. Shadow Properties.srt#0067]]`
- Summary: PointLight shadows are generated by six cameras (one per face plus up/down), making them expensive; the shadow camera's `far` property unexpectedly also limits the light's own range, so low values can kill shadows on nearby surfaces.
- Key claims: PointLight shadow uses six directional cameras to cover all directions; `near` works as expected but `far` clamps the light distance itself — a value too low removes shadows from surfaces within the light's range; the instructor advises against PointLight shadows in favor of cheaper spot or directional lights.
- Learner-relevant: Teaches a non-obvious engine quirk (shadow `far` vs. light range coupling) and reinforces choosing the cheapest shadow-casting light type for a given scene.

### 0068

- Locator: `[[sources/three-js/20260907/0068. Shadow Map Types.srt#0068]]`
- Summary: The renderer offers four shadow-map types set via `renderer.shadowMap.type`: `BasicShadowMap`, `PCFShadowMap` (default), `PCFSoftShadowMap`, and `VSMShadowMap`; the latter produces unexpected artifacts.
- Key claims: `BasicShadowMap` is faster but lower quality; `PCFSoftShadowMap` ignores the light's `radius` property and looks similar to default PCF with blur; `VSMShadowMap` yields undesirable results in the demo; default or soft shadow maps offer the best quality/performance balance.
- Learner-relevant: Provides a decision framework for shadow quality settings so the learner can tune the renderer globally rather than per-light when needed.

### 0069

- Locator: `[[sources/three-js/20260907/0069. Introduction.srt#0069]]`
- Summary: The instructor congratulates the learner on reaching the project section and previews the solar-system capstone as a portfolio piece that synthesizes prior lessons.
- Key claims: The project is a solar system built in three.js; it is not overly complex but should look impressive; future lessons will cover 3D models and custom shaders.
- Learner-relevant: Sets motivation and context — the learner transitions from concept drills to an integrated build, making earlier topics feel cohesive.

### 0070

- Locator: `[[sources/three-js/20260907/0070. Planning Our Project.srt#0070]]`
- Summary: Project planning breaks the solar system into sun, orbiting planets (self-rotating), and orbiting satellites, with an intent to use reusable JavaScript functions rather than manual mesh duplication.
- Key claims: Sun and planets are spheres; planets rotate on their own axis and orbit the sun; satellites orbit planets and inherit parent transforms; reusable functions abstract body creation.
- Learner-relevant: Introduces the design pattern of generator functions for scene population and foreshadows the trigonometry needed for orbital motion.

### 0071

- Locator: `[[sources/three-js/20260907/0071. Adding Meshes.srt#0071]]`
- Summary: The first meshes are added — a sun (`MeshBasicMaterial` yellow, scaled 5), an earth (blue, at world x=10), and a moon (gray, scaled 0.3, added as a child of earth at local x=2) — establishing parent-child inheritance for later orbital animation.
- Key claims: All bodies share a unit sphere geometry scaled per-mesh via `mesh.scale.set`; the sun uses `MeshBasicMaterial` to act as an emitter; the moon's local position is relative to its parent earth, so any positive x places it to earth's right.
- Learner-relevant: Demonstrates geometry reuse, mesh scaling, and the local-vs-world position distinction that underpins hierarchical orbital transforms.

### 0072

- Locator: `[[sources/three-js/20260907/0072. Planetary Orbit.srt#0072]]`
- Summary: Circular orbital motion is achieved by driving `mesh.position.x` with `Math.sin(t) * radius` and `position.z` with `Math.cos(t) * radius` using `Clock.getElapsedTime()`; the naive parent-rotation technique is rejected because it forces all child bodies into the same orbital period.
- Key claims: Sine on one axis plus cosine on a perpendicular axis traces a circle; the amplitude multiplier sets orbit radius; a shared parent rotation would make all planets orbit in lockstep, preventing independent orbital speeds.
- Learner-relevant: Gives the learner a reusable trig-based orbit primitive and a concrete reason why scene-graph parenting alone is insufficient for multi-body systems.
