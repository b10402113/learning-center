requestAnimationFrame 渲染迴圈

掌握 requestAnimationFrame 的遞迴呼叫模式，理解它如何與螢幕刷新率同步、為什麼比 setInterval 和 while 迴圈更適合做渲染。

螢幕有自己的節奏

你的螢幕不是「隨時都在刷」，而是每隔一段時間重畫一次——這個頻率叫刷新率。多數螢幕是 60Hz（每秒 60 次），高階螢幕可能是 120Hz 或 240Hz，部分省電裝置只有 30Hz。每一次刷新，瀏覽器都有極短的一次機會可以塞進一張新畫面。

渲染迴圈的任務，就是每次都搶在刷新之前算好一張圖，交給瀏覽器。算太慢會掉幀，算太快則徒勞無功——因為螢幕還沒準備好接收下一張。

先看看「錯」的方法

最先想到的可能是 setInterval：

function animate() {
  cube.rotation.x += 0.01;
  renderer.render(scene, camera);
}
setInterval(animate, 16); // 嘗試每秒跑 60 次
這個寫法看起來合理，其實有兩個致命問題。

第一，時間不精確。setInterval 只保證「至少」等 16 毫秒，實際觸發時間會被其他任務排擠。當瀏覽器忙碌時，迴圈可能跑得比預期慢，畫面就會卡頓。

第二，與刷新率脫鉤。60Hz 的螢幕每 16.67 毫秒刷一次，但 120Hz 的螢幕每 8.33 毫秒刷一次。你無法用一個固定數字同時適配兩種螢幕。

while 迴圈更糟

有人可能會想：那用 while (true) 不斷跑呢？

while (true) {
  animate();
}

這會立刻卡死瀏覽器。JavaScript 是單執行緒，while (true) 永遠不還手控制权，瀏覽器既無法回應點擊、也無法重繪畫面、更無法執行其他腳本。頁面就此定格，只能強制關閉分頁。

瀏覽器給的專屬門票

requestAnimationFrame（簡稱 rAF）是瀏覽器專門為動畫設計的 API。它的運作方式優雅：

  1. 你呼叫 requestAnimationFrame(animate)，告訴瀏覽器「下次刷新前，請幫我跑這個函式」。
  2. 瀏覽器在下一次刷新之前、最恰當的時間點呼叫你的 animate。
  3. 你在 animate 裡面做完狀態更新和渲染後，再次呼叫 requestAnimationFrame(animate)，排隊等下一次刷新。

這個遞迴模式確保每一幀只跑一次 animate，而且與螢幕刷新率完美同步。

最小渲染迴圈

實際的程式碼非常短：

function animate() {
  requestAnimationFrame(animate);  // 預約下一幀
  cube.rotation.x += 0.01;         // 1. 更新狀態
  renderer.render(scene, camera);  // 2. 渲染
}

animate();  // 啟動迴圈

注意第一行就預約了下一幀——這不是浪費，而是確保迴圈永遠不會停。只要頁面還開著，animate 就會一直被呼叫。

rAF 的額外好處

  • 背景分頁自動暫停：當瀏覽器分頁被切換到背景，rAF 會暫停呼叫，不浪費電力和 CPU。
  • 自動適配刷新率：60Hz 的螢幕每秒約跑 60 次 animate，120Hz 的螢幕自動變成 120 次，不需要你寫任何判斷。
  • 不阻塞渲染：rAF 的回呼（callback）被安排在渲染管線中，不會像 setTimeout 那樣被其他任務延遲。

為什麼不寫成 setTimeout

setTimeout(animate, 1000 / 60) 勉強能用，但終究是妥協：它不知道螢幕何時刷新、無法暫停在背景分頁、也無法適配 120Hz 螢幕。requestAnimationFrame 是瀏覽器原生方案，永遠是首選。
