财联社案例：get_sign() 与 W2Yj 签名模块定位

学习目标：跑通「扣 loader + 三 mod → Node 里出 sign」的最小工作流，掌握先读文件头判定结构、再按模块 ID 精确定位的省力读法。

财联社签名的工作流

财联社网站的请求带有一个签名字段，由前端 JS 生成。这个签名不是简单的 MD5，而是由一个 webpack 模块 W2Yj 计算得出。整个调用链是：

get_sign()
  → window.loader("W2Yj")(data)
    → 返回签名结果

其中 data 是固定参数：

{"os": "web", "sv": "7.7.5", "app": "CailianpressWeb"}

站点用这组固定参数算 sign，说明签名与时间戳无关，只需要模块 W2Yj 被正确调用即可。

三个 mod 的分工

财联社的 loader 顶部 require 了三个 mod 文件，它们各司其职：

mod 文件chunk ID内容需要细读吗
mod1[4]React/Redux 运行时 + W2Yj 签名模块✅ 找 W2Yj
mod2[0]core-js polyfill（Object.keys、Array 迭代器）❌ 必须加载，但不用读
mod3[3]Promise、setImmediate、querystring❌ 必须加载，但不用读

为什么三个都要 require？因为 webpack 的依赖是闭环的——mod1 的 W2Yj 可能间接依赖 polyfill，polyfill 又依赖 Promise。少一个都会在调用时报"X is not defined"。

先读 300 行判定结构

打开 mod1（4260 行），不要从头读。先看头 100-300 行，你会看到：

window = global;
(window.webpackJsonp = window.webpackJsonp || []).push([[4], {
  "q1tI": function(e, n, t) { /* React 运行时 */ },
  "p9MR": function(e, n, t) { /* core-js 入口 */ },
  // ...几百个无关模块...
  "W2Yj": function(e, n, t) { /* 我们要的签名模块 */ }
}]);

看到 "q1tI"（React 的 webpack 模块 ID）就能判断：这是 React 技术栈的 chunk。看到头部 window = global，说明这个 mod 已经自己补了浏览器环境。

按模块 ID 精确定位

判定结构后，用编辑器搜索 "W2Yj"，直接跳到签名模块的源代码。W2Yj 模块通常只有几十到几百行，内部是字符串拼接 + 摘要算法的组合。

定位到模块后，验证它确实被 get_sign() 调用：在 loader 文件里搜 get_sign，你会看到类似这样的代码：

function get_sign() {
  var data = {"os":"web","sv":"7.7.5","app":"CailianpressWeb"};
  var sign = window.loader("W2Yj")(data);
  console.log(sign);
}

这就是本地复现的验收点：你在 Node 里跑完三个 mod 后，调 get_sign()，如果能打印出跟真实请求一样的签名格式，说明环境搭对了。

为什么调度函数带 try/finally

财联社的 loader 调度函数 u(r) 里有一处特别处理：

try {
  e[r].call(o.exports, o, o.exports, n);
} finally {
  o.l = !1;
  delete n[r];  // 注意：这里是清缓存，不是删模块
}

这里的 delete n[r] 是在模块执行抛错时清缓存，防止"执行失败的脏 exports"留在调度表里污染后续调用。这是 webpack 错误恢复的标准做法，不影响正常路径。

本地复现的完整代码

// 1. 补环境
global.window = global;

// 2. 按顺序加载
require("./05_loader.js");   // 财联社 loader
require("./06_mod1.js");     // chunk 4，含 W2Yj
require("./07_mod2.js");     // chunk 0，core-js
require("./08_mod3.js");     // chunk 3，Promise

// 3. 调用验收
get_sign();

注意这里不需要手动调 window.loader("W2Yj")，因为 loader 末尾自带的 get_sign() 已经帮你调了。真实站点的 loader 文件末尾往往有类似的测试调用，这是逆向者最好的验收信号。

多 chunk 依赖闭环的处理

财联社这个案例有个教学重点：三个 mod 都要 require，但只有 mod1 需要细读。mod2 和 mod3 是 polyfill chunk，没有业务逻辑，但它们被 W2Yj 间接依赖。

判断哪些 mod 需要细读的方法：

  • 看 loader 顶部的 require 顺序——它列出了所有直接依赖的 chunk。
  • 看 loader 的 chunk 异步加载表——f.e 里列出的 chunk 不一定全要 require，只有直接入口的才需要。
  • 看报错信息——运行时报 "X is not a function"，就说明缺了某个依赖 chunk。
