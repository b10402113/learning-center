webpack 混淆 chunk 結構

面對上萬行的混淆程式碼，正確姿勢是不通讀，靠全域物件反查模組 id。

學習目標

理解巨型 webpack 混淆 chunk 的註冊機制，以及如何從中定位目標模組而不通讀全文。

chunk 是什麼？

webpack 打包網站 JS 時，不會把所有程式碼壓成一個檔案，而是拆成多個「chunk」。每個 chunk 就是一個用 window.webpackJsonp.push 註冊進去的模組集合。拼多多頁面至少包含兩個 chunk：

chunk大小內容
mod1（id 34）約 24,000 行業務邏輯與第三方套件，包含風控模組 fbeZ
mod2（id 0）約 12,000 行core-js 風格 polyfill，提供 ES 標準函式庫墊片

模組註冊機制

每個 chunk 的檔案開頭都長這樣：

window.webpackJsonp.push([[34], {
  "+s0g": function(module, exports, require){ ... },
  "fbeZ": function(module, exports, require){ ... },
  "WEpk": function(module, exports, require){ ... }
}]);

[34] 是 chunk 的 id，後面的物件是一張「模組表」：key 是短哈希字串（如 fbeZ），value 是模組本體。所有 chunk 共用同一張表，透過 webpackJsonp.push 不斷疊加。

如何定位目標模組？

面對兩萬多行程式碼，從頭讀到尾不但慢，還會被大量無關的 vendor 程式碼淹沒（mod1 裡就混雜了 moment.js 的國際化檔）。正確做法是反向搜尋：

  1. 先找出目標模組「最後會把結果掛到哪個全域物件上」。例如風控模組會掛出 window.lt 和 window.dt。
  2. 用 grep "window\.lt" 或 grep "window\.dt" 在 chunk 檔案裡搜尋。
  3. 找到負責掛全域物件的那行程式碼，它所在的模組 id 就是我們要的入口。

在拼多多案例裡，這個入口是 fbeZ。

mod1：風控核心

fbeZ 模組被執行後，會掛出兩個關鍵物件：

  • window.lt：內含 updateServerTime 等更新介面，用來同步時間因子。
  • window.dt：取值函式，呼叫後會回傳產生好的加密字串（也就是 anti_content）。

mod1 同時也讀取了 window.location、window.history、window.addEventListener 等環境點，這些就是我們上一步補環境時必須湊齊的物件。

mod2：不可或缺的墊片

mod2 看起來很無聊，裡面大量是這種東西：

"WEpk": function(module, exports){
  exports = n("WEpk").Symbol;
}

這是 core-js 風格的 polyfill，提供 Symbol、Set、Object.getPrototypeOf 等 ES 標準功能。mod1 在執行時會用 require 呼叫這些墊片，如果 mod2 沒載入，mod1 的依賴鏈就會斷裂，直接報錯。

這教訓是：從站點抽 JS 時，chunk 要抓全。漏掉任何一個，都可能讓目標模組在 require 鏈上斷掉。

兩個 chunk 一個模組空間

mod1 和 mod2 雖然是不同檔案，但它們 push 到同一個 webpackJsonp 陣列，所以共用同一張模組表。mod1 的 fbeZ 可以直接 require mod2 的 WEpk，反過來也行。這就是為什麼 loader 需要一次載入所有 chunk，才能正確解析跨 chunk 依賴。
