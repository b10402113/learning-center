分散式與增量式爬蟲

js-reverse · Step 5/5 · 約 20 分鐘

這節課你會學到什麼

理解原生 Scrapy 無法分散式的根因，掌握用 scrapy-redis 改造 CrawlSpider 為分散式版本的完整流程，並能用 redis set 實現只爬新增資料的增量式爬蟲。

情境：單機爬蟲不夠用了

你的 CrawlSpider 要爬 10 萬頁資料，單機跑需要 8 小時。你想：能不能開兩台電腦一起跑，每台爬 5 萬頁，時間減半？

問題來了：Scrapy 的調度器（Scheduler）和管道（Pipeline）都在各台機器的記憶體裡，兩台電腦無法共享同一個調度器——它們不知道對方已經爬了哪些 URL，結果不是重複爬就是漏爬。

原生 Scrapy 為什麼無法分散式

兩個原因：

  • 無法共享調度器：每台機器的 Scrapy 有自己的 URL 佇列，無法跨機器同步「哪些 URL 已爬、哪些未爬」
  • 無法共享管道：每台機器的管道各自寫入自己的檔案或資料庫，無法統一管理

解法：引入 scrapy-redis 元件，把調度器和管道搬到 Redis 這台中央伺服器上，所有 Scrapy 實例都連到同一個 Redis，就能共享佇列和去重清單。

分散式改造八步

Step 1：安裝 scrapy-redis

pip install scrapy-redis

Step 2：爬蟲父類改為 RedisCrawlSpider

# spiders/myspider.py
from scrapy_redis.spiders import RedisCrawlSpider
from scrapy.linkextractors import LinkExtractor
from scrapy.spiders import Rule

class MySpider(RedisCrawlSpider):  # 父類改這裡
    name = 'myspider'
    # start_urls 不再使用，改用 redis_key
    redis_key = 'myspider:start_urls'

    rules = (
        Rule(LinkExtractor(allow=r'page=\d+'), callback='parse_item', follow=True),
    )

    def parse_item(self, response):
        yield {'title': response.xpath('//h2/text()').extract_first()}

redis_key 是 Redis 裡的佇列名稱，程式啟動後會監聽這個佇列，等待別人把起始 URL 推進來。

Step 3：settings.py 指定共享管道

ITEM_PIPELINES = {
    'scrapy_redis.pipelines.RedisPipeline': 300,
}

Step 4：settings.py 指定共享調度器

SCHEDULER = "scrapy_redis.scheduler.Scheduler"
DUPEFILTER_CLASS = "scrapy_redis.dupefilter.RFPDupeFilter"
SCHEDULER_PERSIST = True  # 允許暫停後繼續（不清空佇列）

Step 5：settings.py 指定 Redis 連線

REDIS_HOST = '192.168.1.100'  # Redis 伺服器 IP
REDIS_PORT = 6379

Step 6：修改 Redis 設定，解除本機綁定

Redis 預設只允許本機連線，必須修改 redis.conf：

# 註解掉這行
# bind 127.0.0.1

# 關閉保護模式
protected-mode no

Step 7：啟動多台機器的爬蟲

在每台機器上跑：

scrapy crawl myspider

程式會啟動並等待，不會立刻開始爬——因為 redis_key 對應的佇列還是空的。

Step 8：push 起始 URL 到 Redis

在 Redis 用戶端執行：

lpush myspider:start_urls https://example.com/page/1

多台機器同時監聽到有新 URL 出現，就會各自取出 URL 開始爬取，並把新發現的連結寫回 Redis 佇列，形成分散式協作。

分散式爬蟲的注意事項

課本提醒：分散式在日常開發中並不常用，只是一個噱頭。原因：

  • 大多數爬蟲的瓶頸不是 CPU 或頻寬，而是反爬機制（IP 封鎖、驗證碼）
  • 維護多台機器 + Redis 的成本，遠高於單機跑一夜
  • 真正需要大規模爬取時，通常用 Scrapy + 代理池 + 分散式訊息佇列（如 RabbitMQ）從頭設計

但理解分散式改造的原理，對掌握 Scrapy 的調度器、管道、去重機制很有幫助。

增量式爬蟲：只爬新增資料

增量式爬蟲（Incremental Crawling）是一種程式設計思路：監測網站資料更新，只爬最新資料，不重複爬已經抓過的內容。

核心是去重：需要一個「記錄表」，記錄哪些資料已經爬過，每次爬取前先檢查。

記錄表的要求

記錄表必須同時具備兩個特性：

  • 去重：能快速判斷某個 URL 是否已經爬過
  • 持久化：程式重啟後記錄表不能遺失

Python 的 set 能去重，但無法持久化（程式結束就消失），所以不適用。Redis 的 set 既能去重又能持久化，是合適方案。

增量式實作：用 redis set

import redis
import scrapy

class IncrementalSpider(scrapy.Spider):
    name = 'incremental'

    def __init__(self):
        # 連線到 Redis
        self.conn = redis.Redis(host='localhost', port=6379)

    def parse(self, response):
        # 提取詳情頁 URL
        detail_urls = response.xpath('//a/@href').extract()
        for url in detail_urls:
            # sadd 寫入詳情頁 URL 作為唯一標識
            # 回傳 1 表示之前沒爬過（有更新），回傳 0 表示已爬過
            if self.conn.sadd('data_id', url) == 1:
                yield scrapy.Request(url, callback=self.parse_detail)
            else:
                print(f'暫無資料更新: {url}')

    def parse_detail(self, response):
        yield {'content': response.xpath('//div[@class="content"]/text()').extract_first()}

關鍵在 sadd 的回傳值：

  • 回傳 1：元素新增成功，表示之前沒爬過 → 發請求
  • 回傳 0：元素已存在，表示已爬過 → 跳過

判斷標準是 sadd 的回傳值，而不是先查詢再寫入——因為 sadd 本身是原子操作，並發安全。

增量式爬蟲的適用場景

  • 監測新聞網站：每小時跑一次，只抓新發布的文章
  • 監測商品價格：每天跑一次，只抓價格有變動的商品
  • 監測職缺網站：每天跑一次，只抓新發布的職缺

增量式爬蟲的重點不是用什麼技術，而是「只爬新增資料」的設計思路——用 Redis set 只是最常見的實現方式。

小結

原生 Scrapy 無法分散式，因為多台電腦無法共享調度器和管道。scrapy-redis 提供可共享的調度器和管道，改造流程包括：父類改 RedisCrawlSpider、start_urls 換成 redis_key、settings 指定共享管道/調度器/去重/Redis 連線、修改 Redis 設定解除本機綁定、lpush 起始 URL 啟動爬取。增量式爬蟲用 Redis set 做去重記錄表，sadd 回傳 1 表示有更新才發請求，實現只爬新增資料。
