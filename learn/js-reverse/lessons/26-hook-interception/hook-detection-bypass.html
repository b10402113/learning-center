Hook 檢測與反檢測

你 hook 了網站的函數，網站也想知道自己有沒有被 hook——一場圍繞 toString() 的貓鼠遊戲。

學習目標

理解網站用 toString() 與 Function.prototype.toString.call 兩級檢測識別 hook 的原理，掌握重寫實例 toString 與重寫原型鏈 toString 兩種破解及各自代價。

攻防的另一面

hook 不是聖誕老人的禮物——一些網站會嚴格檢測自己的關鍵函數或屬性是否被「別有用心的人」動過手腳。檢測抓到異常，輕則拒絕服務，重則上報風控。所以做逆向必須理解兩個問題：網站怎麼檢測 hook？又怎麼破解這種檢測？

檢測法：toString() 現出原形

JS 裡每個函數都有 toString() 方法，返回函數的源代碼字符串。但有一類函數是例外：瀏覽器內置函數。它們的實現藏在瀏覽器底層（C++），JS 層面拿不到源碼，於是 toString() 返回的是一個特殊標記：

// 原生 atob 的 toString() 結果：
"function atob() { [native code] }"

[native code]（原生代碼標記）的含義是：這個函數的實現被隱藏了。這對提高代碼的安全性和封裝性有一定作用——而對網站來說，它恰好是一個絕佳的「純真證明」。

現在對比被 hook 之後的 atob：

// 被 hook 後 atob.toString() 的結果：
"function (str) {
    console.log(\"正在執行atob方法, 參數:\", str);
    let result = _atob(str);
    ...
}"

兩個結果一眼就能分辨：原生返回 [native code] 標記，被 hook 後返回的是你的包裹函數源碼。網站只要執行一次 atob.toString()、檢查結果裡有沒有 [native code]，就知道函數有沒有被動過。這就是 toString() 檢測法。

破解一：重寫實例上的 toString

思路很直接：既然檢測方靠 toString() 識破偽裝，那就把 toString 也 hook 掉，讓它撒一個「我很原生」的謊：

_atob = atob; // 保存原函數

atob = function (str) {
    console.log("正在執行atob方法, 參數:", str);
    let result = _atob(str);
    console.log("正在執行atob方法, 返回值:", result);
    return result;
};
// 重寫 atob 函數的 toString 方法
atob.toString = function () {
    return 'function atob() { [native code] }';
};

代價很小、效果立竿見影——但只對「直接調 atob.toString()」的檢測有效。對方一旦升級，這個謊言就破了。

檢測法升級：原型鏈上的 toString

檢測方的反制是繞開實例上那個被你重寫的 toString，直接去函數的原型對象上取：

Function.prototype.toString.call(atob)
// 調用函數原型對象中的 toString 進行檢測，
// 而不是 atob 實例對象上的 toString 了

原理：atob.toString() 走的是實例屬性查找，你在實例上重寫就能攔截；而 Function.prototype.toString.call(atob) 明確指定用原型鏈上的版本，你掛在實例上的假貨根本沒機會執行。函數的真身再次暴露。

破解二：重寫原型鏈上的 toString

再升一級：連原型鏈上的 toString 也一併重寫：

// 重寫原型鏈上的 toString 方法
Function.prototype.toString = function () {
    return `function ${this.name}() { [native code] }`;
};

注意兩個細節：

  • 為什麼用 this.name：this 是 toString 的調用者。this.name 動態取出調用者的函數名——Location.toString() 時 this.name 就是 "Location"，結果自然是 function Location() { [native code] }。
  • 寫死的代價：如果把 this.name 直接寫死成 atob，那以後任何函數調 toString() 都返回 function atob() { [native code] }——Location.toString() 也變成了 atob，反而露出更明顯的馬腳。

而即便用 this.name 動態適配，重寫原型鏈的代價也比實例級大得多：你改的是所有函數共享的原型，整個頁面裡每個函數的 toString() 行為都被污染。這是全攻全守的打法——能騙過原型鏈檢測，但影響面越廣、被更精巧的檢測（比如對比兩個無關函數的 toString 來源）抓到的風險也越高。

本節小結

hook 會增加被檢測的風險，攻防圍繞 toString() 展開兩級對抗：第一級，網站調 atob.toString() 找 [native code] 標記，你重寫實例上的 toString 撒謊；第二級，網站用 Function.prototype.toString.call(atob) 繞開實例重寫，你把原型鏈上的 toString 也重寫，並用 this.name 動態適配調用者名字。破解級別越高、污染面越大。判斷該破解到哪一級，取決於對方檢測的深度——先觀察、最少改動，是逆向的通用紀律。
