瀏覽器先手 hook：atob 與 cookie

頁面腳本還沒跑，hook 已經蹲好了——這就是「先手」。

學習目標

在真實瀏覽器裡用「Script 事件監聽 + Snippets」搶在頁面腳本之前完成內置函數（atob）與 cookie 屬性的 hook，並理解為什麼時機必須早於頁面加載。

最大的難題不是寫法，是時機

前兩步的 hook 寫法，搬到瀏覽器裡有一個致命問題：太慢。等頁面加載完、你再打開控制台粘貼 hook 代碼時，網站的加密代碼早就跑完了——該解的 base64 解完了，該寫的 cookie 寫完了，你的 hook 一次都沒被觸發。

所以瀏覽器環境的 hook 有一條鐵律：hook 時機必須在頁面加載出來之前。要搶先，就要讓頁面腳本在起跑線上停下來等你——這件事靠 DevTools 的兩個功能配合完成：Script 事件監聽負責「讓頁面停下來」，Snippets 負責「趁停頓注入 hook」。

先手 hook 的五步操作鏈

以瀏覽器自帶的 base64 解碼函數 atob 為例（它是逆向 base64 數據的常用起手式）：

步驟操作目的
1在一個空白頁面打開 DevTools準備好調試環境，此時還沒有目標頁面干擾
2開啟事件監聽斷點裡的 Script（腳本）事件讓頁面在任何 script 執行前先斷住
3訪問目標頁面頁面開始加載，Script 斷點立刻把執行停住
4Sources → Snippets 新建 hook 代碼片段，打上斷點，右鍵 Run 運行趁頁面腳本還停著，搶先完成同名覆蓋
5取消 Script 事件監聽，讓頁面繼續跑（不可刷新頁面）hook 已就位，之後每次 atob 調用都會被監控

hook atob：攔截 base64 解碼

第 4 步的 Snippets 裡，寫的還是那副「保存原函數 + 同名覆蓋」的骨架：

_atob = atob;  // 保存原函數

atob = function (str) {
    console.log("正在執行atob方法, 參數:", str);
    let result = _atob(str);
    console.log("正在執行atob方法, 返回值:", result);
    return result;
};

把這段代碼存成 Snippet、Run 一次。等頁面繼續加載、開始處理 base64 數據時，控制台就會一行行打出每次 atob 的輸入與解碼結果。逆向 base64 混淆的參數時，這一步能直接告訴你「原文長什麼樣」。

hook cookie：監控憑證的讀寫

cookie 是屬性，不是函數，所以寫法換成 Object.defineProperty，但操作鏈完全一樣（同上面的五步）：

_cookie = document.cookie;  // 保存原值

Object.defineProperty(document, 'cookie', {
    get(){
        console.log("正在獲取cookie:", _cookie);
        return _cookie;
    },
    set(value){
        console.log("正在設置cookie:", value);
        _cookie = value;
    }
});

這段 hook 的價值在於：網站什麼時候讀 cookie、什麼時候寫入新的 cookie，全都會打印出來。當你追查「登入憑證／風控字段是怎麼生成、何時種下的」，這就是最直接的線索。

為什麼最後一步不能刷新頁面

hook 是「同名覆蓋」——它改變的是當前頁面運行時裡 atob 和 document.cookie 指向什麼。一旦刷新，整個頁面上下文重建，你的覆蓋全部作廢，網站又拿回了原生函數。所以先手 hook 完成後：可以繼續操作頁面、可以發請求，但不能刷新，直到你收集完數據為止。
