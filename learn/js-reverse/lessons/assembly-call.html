組裝與呼叫 anti_content

把補環境、chunk、loader 按順序組裝，包成一個可被外部呼叫的純函式。

學習目標

將補環境、chunk、loader 按順序組裝，並呼叫 get_anti_content() 生成風控 token。

組裝順序

所有零件都摳出來之後，最後一個 JS 檔案（05 pdd.js）負責把它們按正確順序黏起來。順序是：

require('./01 env.js');    // 1. 先補環境
require('./02 mod1.js');    // 2. 再掛 chunk
require('./03 mod2.js');    // 3. 再掛另一個 chunk
require('./04 loader.js');  // 4. 最後跑 loader

順序不能錯。如果 loader 在 chunk 之前跑，webpackJsonp.push 還沒被劫持，chunk 就無法正確註冊。如果 chunk 在 env 之前跑，JS 會因為找不到 window.location 而崩潰。

封裝成純函式

組裝完成後，我們定義一個對外的純函式 get_anti_content()。這個函式就是等等 Python 透過 execjs 呼叫的入口：

function get_anti_content() {
  window.loader("fbeZ");                          // 初始化風控模組
  window.lt['updateServerTime'](Date.now());     // 更新時間因子
  return window.dt();                            // 回傳加密字串
}

三步固定套路

仔細看 get_anti_content() 內部，它永遠照這三步執行：

  1. 初始化：window.loader("fbeZ") 手動載入風控模組。每次呼叫前重新執行這一行，可以重置模組內部狀態，避免舊狀態污染新結果。
  2. 更新時間：window.lt['updateServerTime'](new Date().getTime()) 把本地時間傳進去。時間因子參與加密結果，所以每次都要用當下時間，不能用固定值。
  3. 取值：window.dt() 回傳最終的 anti_content 字串。

時間因子的重要性

updateServerTime 雖然名字有「Server」，但我們傳的是本地時間。這是因為加密演算法通常只驗證「時間是否在合理範圍內」，而不是要求與伺服器完全同步。只要本機時鐘不要偏差太大（例如差幾天），就能通過驗證。

這也解釋了為什麼 anti_content 不能复用：每次用舊的時間戳生成，伺服器一比對發現時間太古老，就會拒絕。所以每個請求都必須重新跑一次 get_anti_content()。

為什麼要重新初始化？

每次呼叫 get_anti_content() 都重新執行 window.loader("fbeZ")，看似浪費，其實是為了重置狀態。風控模組內部可能記住上次的輸入或中間變數，如果不重置，第二次以後的結果可能不如預期穩定。

完整組裝模板

把以上合起來，就是「摳出來之後怎麼組裝」的固定模板：

// 1. 補環境
// 2. 掛 chunk（所有 chunk）
// 3. 跑 loader
// 4. 定義對外純函式
function get_anti_content() {
  window.loader("fbeZ");
  window.lt['updateServerTime'](new Date().getTime());
  return window.dt();
}

這個模板幾乎適用於所有「在本地重現站點 JS 加密」的場景：補環境 → 掛 chunk → 跑 loader → 包一個可被外部呼叫的純函式。
