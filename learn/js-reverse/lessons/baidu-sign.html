百度翻译 get_sign 算法与 gtk 补环境

实战：SHA1 与百度 sign · 步骤 4/5

学习目标

能看懂百度翻译 get_sign 里 gtk 拆段、字符转码、魔数字符串驱动位运算的逻辑，并说出为什么 Node 里要先写 window = global; window.gtk = ... 才能跑通。

先看现象：sign 随 query 变化

在百度翻译输入不同单词，每次请求的 form 数据里 sign 都不同。但 token 和 domain 是固定的，ts 是毫秒时间戳。这说明 sign 是 query 的函数，而且算法藏在 JS 里。

gtk：藏在 window 里的全局变量

打开扣下的百度翻译 JS，第一行就是：

window = global;
window.gtk = '320305.131321201'

gtk 不在函数参数里，而是挂在 window 上。在浏览器里，window.gtk 是页面加载时由其他脚本设置好的全局变量。但在 Node.js 里，window 根本不存在——你不补这两行，get_sign 读到 window.gtk 就会报 ReferenceError: window is not defined。

这就是「补环境」最直觉的含义：让扣下来的代码在 Node 里还能找到它依赖的浏览器属性。

get_sign 的三步逻辑

步骤做了什么一句话
1. 文本截取超过 30 字符的文本，截取前 10、中间 10、末尾 10 字符长文本只取头中尾
2. 字符转码把每个字符转成 UTF-16 编码（处理代理对）字符 → 数字数组
3. 位运算循环用两个魔数字符串驱动 n() 函数做移位、异或、加法魔数字符串驱动位运算

魔数字符串：+-a^+6 和 +-3^+b+-f

这两个字符串看起来像乱码，其实是位运算的指令集：

w = "+-a^+6"
k = "+-3^+b+-f"

function n(t, e) {
    for (var n = 0; n < e.length - 2; n += 3) {
        var r = e.charAt(n + 2);
        r = "a" <= r ? r.charCodeAt(0) - 87 : Number(r);
        r = "+" === e.charAt(n + 1) ? t >>> r : t << r;
        t = "+" === e.charAt(n) ? t + r & 4294967295 : t ^ r;
    }
    return t;
}

它每次取 3 个字符：第一个是运算符（+ 表示加法/异或），第二个是方向（+ 表示右移，- 表示左移），第三个是操作数（字母代表 10 以上数字）。这是一种经典的混淆手法——把简单的位运算拆成字符串解析，增加阅读难度。

gtk 怎么参与运算

gtk 的值是 '320305.131321201'，get_sign 把它按 . 拆成两段整数：f = 320305、m = 131321201。f 作为位运算的初始值，m 作为最后的异或操作数。

最终输出格式是 (b % 1e6).toString() + "." + (b ^ f)——一个六位数加一个点加一个整数，这就是你在请求里看到的 sign。

负数转正的技巧

位运算结果可能溢出成负数，百度翻译用这一行把它转回正数：

(b ^= m) < 0 && (b = 2147483648 + (2147483647 & b))

这是 32 位有符号整数转无符号的标准写法。2147483647 & b 把符号位清零，再加上 2147483648（即 2^31），等价于给负数加上 2^32。

小结

百度翻译的 sign 不是标准算法，而是一段被混淆过的位运算。真正让新手卡住的不是位运算本身，而是 gtk 这个环境依赖。补环境就是让扣下来的代码在 Node 里还能找到它依赖的浏览器属性。下一步我们就把 get_sign 挂到 Python 里，拼出完整的 POST 请求。
