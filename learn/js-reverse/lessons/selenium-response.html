中間件結合 Selenium 篡改回應

js-reverse · Step 3/5 · 約 20 分鐘

這節課你會學到什麼

掌握在 process_response 中用 Selenium 渲染動態頁面並替換原回應的完整方案，理解「Scrapy 調度 + Selenium 渲染」混合架構的適用場景。

情境：Scrapy 拿到的回應是空的

你想爬網易新聞（https://news.163.com/）的國內板塊。用 Scrapy 直接請求板塊頁，拿到回應後用 XPath 解析——卻發現什麼都拿不到。原因是這個頁面的新聞列表是 JavaScript 動態載入的：伺服器回傳的 HTML 裡只有一個空殼容器，真正的資料是瀏覽器執行 JS 後另外發 Ajax 請求填進去的。

Scrapy 本身不執行 JavaScript，所以它拿到的回應就是那個空殼。這就是「回應不滿足需求」的典型場景。

解法：Scrapy 調度 + Selenium 渲染

既然 Scrapy 不執行 JS，那就把「需要 JS 渲染的頁面」交給 Selenium（或 Pyppeteer）處理。具體做法：

  1. 爬蟲類裡例項化一個瀏覽器物件（bro = webdriver.Chrome()）
  2. 中介物的 process_response 裡，判斷當前 URL 是不是需要渲染的動態頁面
  3. 如果是，用瀏覽器打開這個 URL、等 JS 執行、滾動到底、取 page_source
  4. 用 page_source 建構一個新的 HtmlResponse，替換掉原本的空殼回應
  5. 爬蟲拿到新的回應後，就能用 XPath 正常解析了

這種架構讓 Scrapy 繼續負責「發請求、調度、解析、儲存」，只有「需要 JS 渲染的頁面」才交給瀏覽器，靜態頁面仍然走原生管線。

完整程式碼

爬蟲檔案：定義瀏覽器與動態 URL 清單

# spiders/news163.py
import scrapy
from selenium import webdriver

class News163Spider(scrapy.Spider):
    name = 'news163'
    start_urls = ['https://news.163.com/']

    # 爬蟲類屬性：瀏覽器物件
    bro = webdriver.Chrome()

    def parse(self, response):
        # 解析首頁，提取五個板塊的 URL
        model_urls = []
        # ... XPath 提取 ...
        for url in model_urls:
            yield scrapy.Request(url, callback=self.parse_model)
        # 把動態 URL 清單存到爬蟲物件，中介件才能讀取
        self.model_urls = model_urls

    def parse_model(self, response):
        # 此時 response 已經被中介件替換成渲染後的 HtmlResponse
        titles = response.xpath('//div[@class="news_title"]/h3/text()').extract()
        for title in titles:
            item = {'title': title}
            # 詳情頁用 meta 傳 item，延續深度爬取套路
            detail_url = '...'
            yield scrapy.Request(detail_url, callback=self.parse_detail, meta={'item': item})

    def parse_detail(self, response):
        item = response.meta['item']
        item['content'] = response.xpath('//div[@class="content"]/text()').extract_first()
        yield item

    def closed(self, spider):
        # 爬蟲關閉時關閉瀏覽器
        self.bro.quit()

中介件檔案：在 process_response 中替換回應

# middlewares.py
from scrapy.http import HtmlResponse
from time import sleep

class SeleniumMiddleware:
    def process_response(self, request, response, spider):
        # 判斷當前 URL 是不是需要渲染的動態頁面
        if request.url in spider.model_urls:
            # 用爬蟲持有的瀏覽器物件打開頁面
            spider.bro.get(request.url)
            sleep(2)  # 等 JS 執行
            # 滾到底部，觸發懶載入
            spider.bro.execute_script('window.scrollTo(0, document.body.scrollHeight)')
            # 取渲染後的原始碼
            page_text = spider.bro.page_source
            # 建構新的 HtmlResponse，替換掉原本的空殼回應
            new_response = HtmlResponse(
                url=request.url,
                body=page_text,
                request=request,
                encoding='utf-8'
            )
            return new_response
        # 不是動態頁面，原樣返回
        return response

關鍵步驟解析

1. 為什麼用 spider.bro 而不是在中介件裡新建瀏覽器？

瀏覽器物件（webdriver.Chrome()）啟動較慢，如果每個請求都新建一個瀏覽器，速度會慢到無法接受。把瀏覽器作為爬蟲類的屬性，整個生命週期只啟動一次，中介件透過 spider.bro 取用，是效能與簡潔的折衷。

2. 為什麼要滾動到底？

很多動態頁面使用「懶載入（Lazy Load）」：只有當使用者滾動到某個位置時，才載入更多資料。window.scrollTo(0, document.body.scrollHeight) 把捲軸滾到最底，觸發所有懶載入的內容。

3. 爲什麼用 HtmlResponse 而不是直接回傳 page_source？

process_response 必須回傳一個 Response 物件。HtmlResponse 是 Scrapy 內建的 Response 子類，能直接被 XPath 解析。建構時要傳入 url、body（原始碼）、request、encoding 四個參數。

4. 為什麼在 closed 裡關閉瀏覽器？

爬蟲結束時，瀏覽器行程不會自動關閉。closed(self, spider) 是 Scrapy 的內建信號函式，爬蟲關閉時自動被呼叫，在這裡呼叫 self.bro.quit() 釋放資源。

混合架構的適用場景

「Scrapy 調度 + Selenium 渲染」不是萬靈丹，它有明確的適用場景：

  • 適用：大部分頁面是靜態、只有少數頁面需要 JS 渲染（如網易新聞的首頁是靜態、板塊頁是動態）
  • 不適用：整站都是 JS 渲染（這種情況直接用 Selenium 或 Pyppeteer 從頭寫比較快）

原則是：讓 Scrapy 做它擅長的事（調度、管線、併發），只把「必須執行 JS 的頁面」交給瀏覽器。

小結

當 Scrawy 拿到的回應是動態載入的空殼時，可以在 process_response 中用 Selenium 渲染頁面、用新的 HtmlResponse 替換原回應。瀏覽器物件作為爬蟲類屬性只啟動一次，中介件透過 spider.bro 取用。這種「Scrapy 調度 + Selenium 渲染」的混合架構，是應對動態載入站點的主力方案。
