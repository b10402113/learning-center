scrapy 五大核心组件与数据流

深度爬取与 POST 请求 · 步骤 1/4

学习目标

理解 scrapy 五大核心组件的职责分工与请求/响应的数据流，并掌握两条最低成本的性能调优配置。

为什么需要理解组件？

写 scrapy 爬虫时，你写的代码只占框架的一小部分——Spider 负责解析，Pipeline 负责存储。但请求是怎么从 Spider 发到网站的？响应又是怎么回到 Spider 的？这些幕后工作由 scrapy 的五大核心组件协作完成。

不理解这五个组件，你只能照搬模板；理解了它们，你才能知道中间件该插在哪个位置、请求在队列里怎么排队、并发数调的是哪个参数。这是后续学习中间件、分布式、深度爬取的共同地基。

五大核心组件

scrapy 的五大组件各司其职，请求和响应像流水线上的工件一样在它们之间流转：

组件职责一句话记法
引擎（Engine）处理整个系统的数据流、触发事务总指挥，不发请求不存数据，只调度
调度器（Scheduler）接收引擎的请求、压入队列、返回下一个请求URL 优先队列，负责去重和排队
下载器（Downloader）基于 twisted 异步模型下载网页内容真正发请求的工人，把响应交回引擎
爬虫（Spider）从特定网页提取 Item，也可提取链接继续抓取解析员，决定"抓什么"和"抓完后下一步抓哪里"
项目管道（Pipeline）持久化、验证、清洗 Item仓库管理员，负责把数据存到文件/数据库

一次请求的完整旅程

假设你的 Spider 解析完一页，yield 了一个新请求。这个请求会经历以下旅程：

  1. 引擎收到 Spider 的 Request，交给调度器。
  2. 调度器把它压入队列，按优先级排队、去重。
  3. 调度器把排在最前面的请求交回引擎。
  4. 引擎把请求交给下载器。
  5. 下载器通过 twisted 异步模型发出 HTTP 请求，拿到响应。
  6. 引擎把响应交回给 Spider 的回调函数。
  7. Spider 解析响应，yield 新的 Request 或 Item。
  8. 如果是 Item，引擎把它交给 Pipeline 处理。

整个过程是异步非阻塞的——下载器在等网站响应时，引擎可以继续调度其他请求。这就是 scrapy 默认并发 32 个请求而不卡死的原因。

两条最低成本的性能调优

当你的爬虫跑得慢时，先别急着加机器。scrapy 有两个 settings 级参数，改一行配置就能明显提速：

1. 增加并发请求数

scrapy 默认同时发 32 个请求。如果你的目标网站响应快、带宽够，可以把它调大：

# settings.py
CONCURRENT_REQUESTS = 100

注意：并发数不是越大越好。设太高会被目标网站封 IP，或者把对方服务器打挂。一般 50~100 是比较安全的范围。

2. 降低日志级别

scrapy 默认会打印大量 DEBUG 日志（每个请求的 URL、状态码、耗时）。日志输出本身会消耗 CPU，在 Windows 上尤其明显。把日志级别调高可以省下一部分 CPU：

# settings.py
LOG_LEVEL = 'ERROR'

这样只有报错时才打印日志。调试时可以用 'WARNING'，正式跑时用 'ERROR'。
