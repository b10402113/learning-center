25-pdd-supplement-env / loader-runtime

loader 執行時

把 webpack 的 JSONP loader 摳出來，改造成可按 id 查詢的模組庫。

學習目標

掌握 webpack JSONP loader 的最小執行時結構，能夠按模組 id 按需呼叫目標模組。

loader 的角色

每個 chunk 只是「資料」：一張模組表。但誰來管理這張表？誰來決定什麼時候執行哪個模組？這就是 loader 的工作。它是一個約 120 行的 webpack runtime，負責：

  • 攔截 webpackJsonp.push，把每個進來的 chunk 登記進模組表。
  • 維護已載入模組的快取（cache）。
  • 提供 require 函式，讓模組之間能互相引用。
  • 把載入函式掛到 window.loader，讓我們能手動觸發任意模組。

劫持 push

loader 最關鍵的一行是劫持 webpackJsonp.push：

f.push = r;

原本 push 只是陣列的內建方法，loader 把它替換成自訂的 r 函式。從此以後，每當任何 chunk 呼叫 webpackJsonp.push(...)，不但會登記模組表，還會立刻執行「等待這個 chunk 的依賴回呼」。這就是為什麼只要 loader 跑起來，所有 chunk 就能自動就位。

模組表與快取

loader 內部用兩個物件管理模組生命週期：

l.m = {};  // 模組表：id → 模組本體
l.c = {};  // 快取：id → 已執行過的 exports

模組表記錄「每個 id 對應的程式碼是什麼」，快取記錄「每個 id 執行後的結果是什麼」。當一個模組第一次被 require 時，它會被放進模組表、執行、結果存進快取；第二次以後直接從快取拿，不會重複執行。

按需載入

loader 把載入函式 l 掛到 window.loader，這就是我們手動呼叫任意模組的入口：

window.loader = l;

只要知道模組 id，就能在任何時候載入它。在拼多多案例裡，我們用 window.loader("fbeZ") 來觸發風控模組。

interop 輔助

loader 內建了 l.d、l.r、l.t、l.n 等 helper，處理 ESM/CJS 的模組格式轉換。還原 loader 時必須一併保留，否則某些模組會因為格式不相容而報錯。

模組載入日誌

講師在 loader 裡加了一行：

console.log("r:::", r);

這行會在每次 push 被呼叫時印出參數，讓我們觀察「哪些 id 實際被載入」。這是逆向時的鷹眼：如果 fbeZ 沒被載入，代表依賴鏈有問題；如果載入順序不對，代表 chunk 放錯位置。

loader 的最小結構

總結 loader 的四個核心零件：

零件作用
f.push = r攔截 chunk 註冊，觸發依賴回呼
l.m / l.c模組表與快取
window.loader = l手動載入任意模組的入口
l.d / l.r / l.t / l.nESM/CJS interop 輔助
