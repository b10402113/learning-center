补环境的基本形态：window = global

让扣下来的浏览器代码在 Node 里跑起来的第一步

为什么扣下的代码跑不通？

用 DevTools 抠下一段加密脚本，复制粘贴到 Node.js 里运行，最常见的报错不是「算法看不懂」，而是某个全局对象 undefined。浏览器代码默认活在浏览器里，能随手使用 window.atob、window.screenX、window.localStorage 这些浏览器内建的全局对象。Node.js 没有浏览器，自然不存在这些东西。

补环境的核心矛盾就在这里：代码依赖浏览器全局对象，Node.js 没有，所以报错。

最简补法：把 window 指向 global

浏览器里，window 就是全局对象。Node.js 里，全局对象叫 global。只要让 window 这个名字也指向 global，代码里所有 window.xxx 的访问就会落到 global 上，报错了就少了一大半。

window = global;

这一行是补环境的第一行。它不是模拟浏览器，而是给浏览器代码一个能落脚的全局对象。

缺什么补什么

但只写一行 window = global 还不够。global 里没有 screenX、screenY 这些浏览器属性，扣下的代码如果读了它们，依然会拿到 undefined。这时候的做法很朴素：缺什么补什么。

比如扣下的代码用到了 window.screenX 和 window.screenY，就在执行之前手动补上：

window = global;
window.screenX = 0;
window.screenY = 37;

function foo() {
    return window.screenX + window.screenY + "asdfgh";
}

console.log(foo());  // 输出 "37asdfgh"

注意这里的策略：不是把整个浏览器搬进 Node（那是 jsdom 干的事），而是只补代码实际用到的属性。用到什么补什么，少了就加。

补环境的工作流

完整的补环境流程是三步循环：

  1. 执行：运行扣下的代码，看报什么错。
  2. 定位：从报错信息里找到缺了哪个属性。
  3. 补齐：手动在 window 上补上这个属性，再跑一次。

循环到代码能跑通为止。这个过程就叫「补环境」。它不是一个工具，而是一个思路：用最小的代价，让扣下来的代码在 Node 里复现浏览器里的行为。

什么时候需要补环境？

所有「扣下来直接跑」的浏览器 JS 都可能需要补环境。常见场景：

  • 请求签名算法里读了 window.screenX、window.gtk、window.btoa 等浏览器属性。
  • 响应解密算法里用了 window.atob 做 base64 解码。
  • 加密代码访问了 document.cookie、navigator.userAgent 等浏览器环境。

判断标准很简单：只要代码在浏览器里跑通过，在 Node 里跑挂了，第一步就是补环境。
