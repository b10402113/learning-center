execjs 混合路线：什么时候该用 Python 调 JS？

实战：sign 逆向（JS 执行） · 步骤 1/5

学习目标

能说明 Python 原生复现与 execjs 混合路线各自的适用边界，以及在什么条件下应该选 execjs。

回顾：Python 原生复现的代价

上一节我们直接用 Python 的 hashlib.md5 复现了有道翻译的 sign 生成逻辑。核心代码是把 client=fanyideskweb&mysticTime={时间戳}&product=webfanyi&key=fsdsogkndfokasodnaso 拼起来取 MD5。

这条「纯 Python」路线能跑通，是因为 sign 算法足够简单：字符串拼接 + 标准 MD5，Python 原生库直接就能做。但现实中，你遇到的加密逻辑往往更复杂。

三种让 Python 原生复现变难的情况

1. 加密依赖浏览器对象

有些 sign 算法会调用 window.navigator.userAgent、document.cookie、location.href 等浏览器内置对象。这些对象在 Python 里根本不存在，硬要复现就得先伪造整个浏览器环境——工作量直接爆炸。

2. 加密调用了 node 专有模块

node 的 crypto 模块提供了底层的加密原语（createHash、createCipheriv），而浏览器端的 crypto-js 也有自己的一套 API。如果你的目标 JS 代码已经用了这些模块，用 Python 的 hashlib/Cryptography 重新实现，等于把同一种逻辑用两种语言写两遍，维护成本翻倍。

3. 加密逻辑被混淆或闭包层层包裹

很多网站会对 JS 做混淆：变量名替换成 _0x1a2b3c、字符串数组化、控制流平坦化。硬抠 Python 复现时，你得像翻译一样一行行对照，稍不留神就漏掉一个条件分支，sign 就算不对。

execjs 的核心思路

execjs 说：既然加密逻辑已经写在 JS 里了，那就别翻译了，直接在 Python 里跑 JS。

它的分工很明确：

  • JS 负责：加密、解密、签名——任何依赖浏览器/node 对象的逻辑
  • Python 负责：发请求（requests）、处理响应、存储数据、调度任务

这样你保留了 JS 的原始实现，不需要任何跨语言移植，sign 算法怎么改你就怎么改。

什么时候该选 execjs？

条件纯 Python 复现execjs 混合路线
算法是标准 MD5/SHA1/BASE64✓ 推荐可用但没必要
算法依赖浏览器对象（window、document）✗ 需要伪造环境✓ 推荐
算法已用 crypto-js 实现需要重写✓ 推荐
算法被严重混淆、闭包层层包裹抠代码很累✓ 推荐
只需要纯计算、无外部依赖✓ 推荐可用但没必要

execjs 的安装与环境

execjs 本身只是一个桥接器，它需要系统里有一个 JS 运行环境。Mac 上通常已经预装了 node，所以安装很简单：

pip install PyExecJS

安装后可以用一行代码验证是否可用：

import execjs
print(execjs.get().name)  # 输出：Node.js (V8)

如果输出 Node.js (V8)，说明 execjs 已经能调用 node 执行 JS 代码了。

一个最小示例

下面这段代码展示了 execjs 最核心的用法——在 Python 中执行一段 JS 代码，并拿到返回值：

import execjs

# 编译 JS 代码
js_compile = execjs.compile("""
function add(a, b) {
    return a + b;
}
""")

# 调用 JS 函数
result = js_compile.call("add", 1, 2)
print(result)  # 输出：3

compile() 把你的 JS 代码编译成一个可调用的对象，call() 按函数名调用，参数直接往后传，返回值就是 JS 函数的返回值。

小结

execjs 混合路线的本质是「让加密逻辑留在它最熟悉的环境里」。当 Python 原生复现的成本（伪造环境、重写算法、抠混淆代码）超过引入一个 JS 运行时的时候，就应该切换到 execjs。下一步，我们就把有道翻译的 sign 生成逻辑搬到 JS 里。
