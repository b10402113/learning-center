加密值三大藏身处

js-reverse · 步骤 2/4 · 抓到请求后先检查这三个位置

当你用抓包工具或者浏览器 Network 面板拿到一个 HTTP 请求之后，下一步就是找出里面哪个参数是加密过的。请求体那么长，不可能从头到尾一个字段一个字段地猜。加密值在请求里出现的位置，翻来覆去只有三个地方。

第一藏身地：查询参数与 form 数据

这是最常见的位置。POST 请求体里的 sign、token、password，GET 问号后面的 ?key=xxx，都属于这一类。它们就明明白白地躺在请求体或者 URL 里，看起来是一串毫无规律的字符，比如 1be3315fc3cd8097a033646862b6e5db。

抓包的时候，先看 POST 的 Form Data 或者 Request Payload。如果里面有一串长度固定、字符集有限（十六进制或者 Base64）的值，大概率就是加密后的结果。有道翻译的 sign 字段就是这种情况。

第二藏身地：请求头

有些网站不把加密参数放在请求体里，而是塞进 HTTP Header。常见的名字有 Authorization、X-Token、X-Sign、Cookie 里的某个键值。

请求头里的加密值通常比请求体里的更长，格式也更多样：可能是 Bearer token、JWT 三段式、或者自定义的 sign: xxx。抓包的时候别只看请求体，把 Headers 选项卡也展开看一眼。

第三藏身地：Cookie

Cookie 是第三类藏身地，但它的特殊之处在于：Cookie 通常是服务器生成之后下发给客户端的，客户端下次请求时自动带上。所以 Cookie 里的加密值，往往是会话标识或者服务器签名的结果，而不是客户端实时计算出来的。

不过也有例外。有些网站会在前端用 JavaScript 往 Cookie 里写入一个加密后的时间戳或者用户标识，下次请求时带上。这时候 Cookie 里的值就是客户端加密的结果，同样需要逆向。

为什么是「三大藏身处」而不是「四大」

因为 HTTP 请求的结构就是这三块：URL/请求体、Header、Cookie。加密值说到底也是数据，数据只能放在这三个位置之一。建立这个心智模型之后，你抓到一个新请求，不用从头翻到尾，直接按顺序检查：

  1. 先看请求体里有没有看起来像加密结果的字段
  2. 再看请求头里有没有 sign、token、authorization 之类的键
  3. 最后看 Cookie 里有没有可疑的键值

三个地方都看完了，如果还没找到，再考虑是不是加密值被拆散放在了多个字段里，或者经过了二次编码（比如先 Base64 再 URL encode）。

一个判断加密值的快速方法

怎么判断一个字段是不是加密过的？看长度和字符集。MD5 固定 32 位十六进制，SHA-1 固定 40 位，Base64 只包含 A-Z、a-z、0-9、+、/、=。如果一个字段的值符合这些特征，而且每次请求都不一样，那基本就是加密或者签名后的结果。
