回呼地獄：串行異步的嵌套困境

理解「回呼地獄（callback hell）」的成因——串行異步任務的嵌套寫法為何導致代碼右移、難以閱讀和維護，並體會 Promise 要解決的核心痛點。

現象：任務一個接一個

想像你在爬一個需要登入的網站。流程是這樣的：先发請求 A 拿到 token，再用 token 发請求 B 拿到列表，最後用列表第一項的 id 发請求 C 拿到詳情。三個任務必須串行——前一個沒做完，下一個不能開始。

JavaScript 裡，最直覺的寫法是在前一個任務的回調裡啟動下一個任務：

console.log("發送A請求")
setTimeout(function () {
    console.log("A請求結束")
    console.log("發送B請求")
    setTimeout(function () {
        console.log("B請求結束")
        console.log("發送C請求")
        setTimeout(function () {
            console.log("C請求結束")
        }, 3000)
    }, 2000)
}, 1000)

注意 `console.log("next ...")` 會先於所有回呼執行——因為 setTimeout 不會阻塞後續同步代碼。這就是「異步」：定時器到點了，回呼才被放進隊列執行。

爲什麼這叫「地獄」

三層嵌套已經讓代碼向右偏移了。如果再加兩層，整段代碼會縮到螢幕最右邊，幾乎讀不了。這就是「回呼地獄（callback hell）」：

  • 閱讀成本高：眼睛要從最內層一路追到最外層，才能看清整體流程。
  • 錯誤處理難：每一層都要單獨處理失敗，無法統一捕獲。
  • 插入邏輯難：想在任意兩步之間加一步，必須拆開嵌套重新組裝。

用 $.ajax 寫起來更明顯——success 回調裡再包一個 $.ajax，三層下來就是九層縮排。

Promise 的動機

Promise 的出現不是為了取代回調，而是為了把「串行異步 + 回調」的嵌套結構拉平。它把一個異步操作封裝成一個對象，讓你用鏈式寫法取代層層嵌套。
