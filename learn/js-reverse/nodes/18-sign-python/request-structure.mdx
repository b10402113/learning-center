# 有道翻译请求结构与 pointParam

## Learning goal

能分析有道翻译完整 POST 请求体中各字段的含义，区分静态字段、动态字段、签名密钥字段，并理解 pointParam 如何标记参与签名的参数集合

## Lesson

把有道翻译的 POST 请求体全部摊开来看，大概有二十个字段。乍一看很吓人，但只要按功能分类，其实只有四类。

第一类是**业务参数**。这是服务器真正用来完成翻译任务的字段：`i` 是要翻译的原文，`from` 是源语言，`to` 是目标语言，`domain` 是领域，`dictResult` 是是否返回词典结果，`keyid` 是固定标识。这些字段和签名无关，直接照抄抓包值或者按需求修改就行。

第二类是**客户端身份参数**。`client` 标识客户端类型，`product` 标识产品线，`appVersion` 是版本号，`vendor` 是供应商，`keyfrom` 是来源页面。这些字段每次请求都一样，属于静态参数，复制一次就能反复使用。

第三类是**签名相关参数**。`sign` 是计算出来的签名值，`mysticTime` 是计算签名时用的毫秒时间戳，`pointParam` 是签名参数的名单。这三个字段是一个整体，每次请求都需要重新生成或计算。

第四类是**其他辅助参数**。`mid`、`screen`、`model`、`network`、`abtest`、`yduuid` 这些字段大多是客户端环境信息，对签名没有影响，保持默认值即可。

`pointParam` 这个字段值得单独拿出来说。它的值是 `client,mysticTime,product`，用逗号分隔，恰好对应参与签名计算的三个请求参数。但前面已经说过，签名时实际还多了一个硬编码的 `key`。所以 `pointParam` 的准确含义是：「从请求体里取这些字段，加上代码里写死的密钥，一起算签名」。

理解请求结构对逆向有两点价值。第一，你在复现请求时知道哪些字段必须保留、哪些可以删掉、哪些必须重新生成。第二，当你在其他网站上遇到类似的签名机制时，可以快速套用同样的分类逻辑，而不是被一长串参数吓住。

一个实际的检查清单：拿到一个陌生请求时，先找 `sign`、`token`、`_signature` 这类明显是签名的字段；再找 `time`、`t`、`_` 这类明显是时间戳的字段；然后找 `pointParam`、`sign_params`、`keys` 这类名单字段；最后剩下的就是业务参数和辅助参数。按这个顺序过一遍，通常能在几分钟内还原出签名逻辑的全貌。
