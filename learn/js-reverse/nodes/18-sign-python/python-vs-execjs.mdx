# Python 原生复现 vs execjs 混合路线

## Learning goal

能对比 Python 原生复现与 execjs 混合路线的优缺点，判断在何种场景下应坚持纯 Python、何种场景下应切换到 JS 执行环境

## Lesson

有道翻译的 sign 逆向有两种完全不同的实现路线。第一种是 Python 原生复现，也就是前面四步一直在做的——用 `hashlib.md5` 直接计算签名，不依赖任何 JavaScript 运行时。第二种是 execjs 混合路线——把生成签名的 JS 代码原封不动地保留在 JS 文件里，Python 通过 `execjs` 调用 Node.js 执行这段 JS，拿回计算结果。

两条路线各自有鲜明的优劣。

**Python 原生复现的优势**在于零依赖。`hashlib` 是 Python 标准库的一部分，不需要额外安装任何包。代码量通常只有十几行，运行速度快，部署到任何有 Python 的环境里就能直接跑。对于 MD5、SHA1、SHA256 这类标准摘要算法，以及拼接逻辑不复杂的签名，纯 Python 复现永远是第一选择。

**Python 原生复现的劣势**在于复现成本。如果 JS 代码里用了浏览器特有的对象（`document.cookie`、`window.location`），或者用了复杂的编码转换、自定义哈希函数、反调试陷阱，用 Python 逐行翻译这些逻辑就变得非常痛苦。每遇到一个浏览器对象，你都得手工找替代品；每遇到一个混淆变量，你都得靠上下文猜含义。当翻译成本超过一定程度，继续坚持纯 Python 就是一种浪费。

**execjs 混合路线的优势**在于忠实还原。你不需要翻译任何逻辑，直接把 JS 源码加载进来，调用里面的函数就行。只要 JS 代码能在 Node.js 里跑通，Python 就能拿到结果。对于那些依赖浏览器环境、逻辑复杂、或者频繁变动的签名算法，execjs 是最稳妥的折中。

**execjs 混合路线的劣势**在于额外的运行时依赖。目标机器必须安装 Node.js，而且每次调用都涉及进程间通信，性能比纯 Python 差一个数量级。代码结构也因此变得更复杂——你要维护一份 JS 文件、一份 Python 文件，两边要保持同步。

**决策标准其实很简单**：先试纯 Python。如果你能在半小时内把签名逻辑用 `hashlib` 复现出来，就绝不碰 execjs。如果遇到浏览器对象、复杂编码、或者逻辑看不懂，再切换到 execjs。不要把 execjs 当成默认选项，但也不要因为「纯 Python 更酷」就拒绝用它。工具服务于目的，反过来不行。

这个判断标准不仅适用于 sign 逆向，也适用于后续所有的加密参数逆向。下一节的 DES/AES 案例、SHA1 案例，以及 webpack 模块化分析，都会反复面对同样的路线选择。先把这个决策框架内化，后面就能快速做出判断。
