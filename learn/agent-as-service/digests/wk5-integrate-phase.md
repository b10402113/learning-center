# L1 overview

- Jay teaches the second delivery phase: integrating the demoed MVP into the client's real environment — real systems, real data, live constraints (you can't stop their production system to install your agent).
- Three integration models, chosen by client needs and desired relationship: (1) Managed service / done-for-you — everything stays on your side, you run it ongoing, client pays a retainer; (2) Implementation / done-with-you — you get credentials, build inside their tools (e.g. a leads log in their Notion HQ), then they take over; (3) BOT (build-operate-transfer) — build in your own environment, operate to prove it, package with a README and hand over (rare; needs a technical client, more common in enterprise).
- Getting access: a quick 10-minute screen-share call beats insecure email/chat for credentials and API keys; common needs are login credentials, API keys, and sample data; state access requirements in the kickoff call or contract.
- Handover training before handoff (how it works, how to monitor, common pitfalls, what to do if it breaks — the free one-month tuning support in the proposal exists for this), a 5–10 minute Loom walkthrough plus even a simple screenshot document as reference artifacts, an agent-written README that future LLMs can parse, and credential security: no Slack DMs or plain-text email, rotate API keys for long-term clients, store keys in a `.env` file (auto-ignored by GitHub and most upload tooling).

# L2 detail

- `#L1-L84` — Module intro: BIT recap, integration defined as getting the solution working in the client's world; it's often the hardest part because of real systems, real data, real constraints, and live environments where the client's current system can't be stopped to accommodate the install.
- `#L85-L189` — Model 1, managed service (done-for-you): you get access, build, set up, and run it ongoing; client never touches it; you're responsible for everything; earns higher recurring revenue via retainers (the tune phase). Example: managing a content system/pipeline that turns long-form videos into shorts with auto-posting. Applied to the running website-redesign example: all the anti-gravity code and files stay on your side, run daily or weekly, paid retainer.
- `#L189-L273` — Model 2, implementation (done-with-you): you work inside their tools/environment for a week or month using their credentials, then they take over maintenance. Example: a client running on Notion wants a proper log of contacted leads — they grant access to their Notion database, you build the right data tables and views linked back to the pipeline, then hand it over.
- `#L273-L412` — Model 3, BOT (build-operate-transfer): build entirely in your own environment, operate and test to prove it works, document everything, transfer when proven. Applied example: run the automation a few weeks, demonstrate results, zip the workspace and send it over. Rare — needs a client technical lead; more common in large enterprise engagements. Includes the verbatim handover prompt example ("I want to hand this over to a client. Can you put everything in a zip file... include a readme that provides instructions for their technical team... Let me know also the steps that you would take") and how the agent cleans up the workspace. Decide the model upfront and communicate it clearly — it affects pricing, scope, and expectations before the engagement starts.
- `#L413-L480` — Getting access to client accounts: a quick 10-minute call instead of email (insecure for passwords anyway); screen-share, have them log in, direct them to settings to fetch API keys on the spot — easier and more secure than sending keys over email or chat.
- `#L481-L540` — What you commonly need: login credentials (or they create an account for you, like the Notion example), API keys (private keys that connect programmatically — how anti-gravity/Claude Code connect to tools), and sample data (e.g. their existing database's column structure to emulate on your device for smoother integration). Be upfront: include access requirements in the kickoff call or contract to avoid surprises.
- `#L541-L688` — Handover training before handoff (don't just dump it): teach how it works, how to monitor it, common pitfalls, and what to do if something breaks; nurtures the relationship that later drives referrals and word-of-mouth when scaling past one client. Ties back to the proposal's free one-month tuning support — assurance that they won't be alone when something breaks. Artifacts: a 5–10 minute Loom walkthrough they can rewatch, plus documentation (even a simple screenshot document beats nothing). Package with a README the agent writes itself — a wall of text is fine because soon everyone will feed it to their LLM/agent and it will instantly understand the workspace; this is how community templates are packaged for hundreds of people.
- `#L689-L796` — Credential security: treat client access with care; don't send API keys in Slack DMs or plain-text email; rotate API keys for long-term clients to lessen breach risk (one breach severely impacts the client and, by extension, you). Store keys in a `.env` file — it has default protections: GitHub and many upload sites automatically ignore `.env`, so if the client pushes the workspace to GitHub the keys are excluded. Shows the `.env` file on screen (API tokens field covered).
- `#L797-L817` — Summary: know the right integration model (managed service, implementation, or build-operate-transfer), get access via a quick call, know the common platforms, train the client before the proper handoff, keep credentials secure. Teaser: the tuning phase — ongoing optimization and results reporting.
