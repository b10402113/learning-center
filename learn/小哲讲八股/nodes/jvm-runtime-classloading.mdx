# JVM 執行時與類載入：類別怎麼被載入、物件存在哪

## Lesson

這個節點要回答的是同一個問題的兩個面向：**你寫的 Java 程式碼，最後是在哪裡、用什麼方式跑起來的？**

第一個面向是「怎麼跑」。`javac` 把 `.java` 編成平台無關的 `.class` 位元組碼，JVM 再用解釋器逐行翻譯；但真正讓 Java 跑得快的是 JIT——它在執行時挑出反覆執行的熱點程式碼，直接編成機器碼放進 Code Cache。JIT 還會做逃逸分析這類 `javac` 做不到的優化，把沒有逃出方法的物件拆解到棧上，省下堆分配與 GC 的負擔。理解了這一層，你才會知道「Java 是編譯型還是解釋型」不是二選一，而是兩種機制各司其職。

第二個面向是「在哪跑、資料放哪」。JVM 把記憶體切成五塊：執行緒共享的堆與方法區，以及執行緒私有的虛擬機棧、本地方法棧與程式計數器。堆是最大的一塊、也是 GC 的主戰場；方法區在 JDK 8 從永久代改成放到本地記憶體的元空間，解決了動態代理類撐爆固定上限的老問題。而當你 `new` 一個物件，它在堆裡其實是「物件頭 + 實例資料 + 對齊填充」三塊，物件頭裡的 Mark Word 甚至會隨鎖狀態改變長相。

最後是「類別怎麼進來」。`.class` 檔不是丟進記憶體就能用，它要經過載入、驗證、準備、解析、初始化五個階段，其中準備階段只給靜態變數零值、初始化階段才真正執行 `<clinit>` 與靜態程式碼區塊——這正是「`static int a = 666` 為什麼一開始是 0」的答案。類別該由哪個載入器載入，則由雙親委派決定：向上委託、向下載入，用砂箱安全與避免重複載入換來核心 API 的穩定。而當基礎層需要呼叫使用者層（SPI），或容器需要多版本共存（Tomcat）時，就得刻意打破委派。

這六步走完，你對「物件存在哪、類別怎麼被載入」會有一套可以從現象講到機制的說法，而不是背下五個名詞。
