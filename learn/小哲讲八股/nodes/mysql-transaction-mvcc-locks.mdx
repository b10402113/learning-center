# 事務、MVCC 與鎖

## Learning goal

講清楚 ACID 各自靠什麼機制、隔離級別與三種異常、MVCC 版本鏈與 ReadView、行/間隙/臨鍵鎖與死鎖。

## Steps

1. [[learn/小哲讲八股/nodes/mysql-transaction-mvcc-locks/acid-and-implementation|ACID：四個承諾與 InnoDB 的四套機制]] — 把原子性、持久性、隔離性各自對應到 Undo Log、Redo Log/WAL、鎖與 MVCC，並說明一致性是前三者共同撐出來的結果
2. [[learn/小哲讲八股/nodes/mysql-transaction-mvcc-locks/isolation-levels-and-anomalies|隔離級別與三種異常：髒讀、不可重複讀、幻讀]] — 用假資料、變資料、新資料分辨三種併發異常，並講清四種隔離級別各攔下什麼、MySQL 預設是哪一級（after step 1）
3. [[learn/小哲讲八股/nodes/mysql-transaction-mvcc-locks/mvcc-version-chain-and-readview|MVCC：隱式欄位、版本鏈與 ReadView]] — 拆解 DB_TRX_ID/DB_ROLL_PTR、Undo 版本鏈與 ReadView 可見性演算法，並解釋 RC/RR 只差在快照時機（after step 2）
4. [[learn/小哲讲八股/nodes/mysql-transaction-mvcc-locks/innodb-locks|InnoDB 的鎖：粒度、屬性與行鎖演算法]] — 從全局/表/MDL/行鎖、S/X/意向鎖講到 Record/Gap/Next-Key，並說明 RR 為何比 RC 更容易衝突（after step 2）
5. [[learn/小哲讲八股/nodes/mysql-transaction-mvcc-locks/deadlock-and-optimistic-lock|死鎖與樂觀鎖：AB-BA、wait-for graph 與 version CAS]] — 用轉帳場景復現死鎖與回滾、給出防治策略，再對比樂觀鎖與悲觀鎖的鎖持有時間（after steps 3、4）

## Lesson

資料庫最怕的從來不是「單一條 SQL 寫錯」，而是「多個交易同時跑，結果彼此打架」。兩筆轉帳互相看不到對方、一個查詢前後讀到不同數字、兩條 UPDATE 卡住彼此不放——這些現象在單人開發時永遠測不出來，卻偏偏在生產環境最繁忙的時刻冒出來。追根究柢，它們都指向同一組問題：多個事務同時讀寫同一批資料時，誰看得見誰、誰必須等誰。

這個節點沿著「隔離性到底怎麼做出來」這條線走五步。第一步先把 ACID 四個承諾攤開，對應到 InnoDB 的四套機制——原子性靠 Undo Log、持久性靠 Redo Log 與 WAL、隔離性靠鎖加上 MVCC，而一致性不是第四套機制，是前面三者合作後的自然結果。第二步把隔離性要解決的具體病症講清楚：髒讀是讀到別人的草稿，不可重複讀是同一筆資料前後變了樣，幻讀是查詢結果無中生有多出幾筆；再對照四種隔離級別，看看各級別攔下了哪些病。

接下來第三步與第四步，從兩個角度拆解相隔離性的手段。第三步看「讀」這一側：MVCC 靠隱式欄位與 Undo Log 串出資料的歷史版本鏈，再用 ReadView 的可見性規則決定一條查詢該讀到哪個版本，這也解釋了 RC 與 RR 為什麼只差在生成快照的時機。第四步看「寫」這一側：MySQL 的鎖要從粒度、互斥屬性、行鎖演算法三個維度一起講才完整，而 RR 預設的 Next-Key Lock 正是它比 RC 更容易塞車、也更容易死鎖的原因。

最後一步回到最實戰的兩個場景：AB-BA 交叉死鎖怎麼發生、InnoDB 如何用 wait-for graph 檢測並回滾，以及該用什麼開發習慣避開它；再順著鎖的持有時間，說明樂觀鎖的 version CAS 為什麼明明底層也用到行鎖，卻仍被叫做「樂觀」。

走完之後，你應該能把「隔離級別」講成一張對照表：每一級用什麼手段、擋掉哪種異常、又要付出什麼代價，而不是把 MVCC、鎖、死鎖當成三個互不相干的名詞背下來。
