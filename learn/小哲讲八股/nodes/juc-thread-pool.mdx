# 執行緒池打滿、任務堆積

## Learning goal

講清楚執行緒生命週期、執行緒池七參數與四步流程、四種拒絕策略、Executors 快捷工廠的 OOM 陷阱，以及虛擬執行緒如何改寫高併發模型。

## Steps

1. [[learn/小哲讲八股/nodes/juc-thread-pool/thread-lifecycle|執行緒有幾種狀態？六個狀態與容易搞混的三組]] — 講清楚 Java 六個執行緒狀態、RUNNABLE 為何合併 OS 的就緒與運行，以及 BLOCKED／WAITING／TIMED_WAITING 的差別
2. [[learn/小哲讲八股/nodes/juc-thread-pool/pool-why-and-sizing|為什麼不能一直 new Thread？池化與執行緒數設置]] — 從 new Thread 的成本推導出池化的三個好處，並用 CPU／IO 密集型公式決定執行緒數（after step 1）
3. [[learn/小哲讲八股/nodes/juc-thread-pool/seven-parameters|執行緒池的七個參數：用銀行網點一次記住]] — 用銀行比喻把七個參數分成「人員數量、等待區、兜底輔助」三類，各自講清作用（after step 2）
4. [[learn/小哲讲八股/nodes/juc-thread-pool/execution-flow|任務提交後發生什麼？四步執行流程]] — 照核心執行緒、任務佇列、最大執行緒、拒絕策略四關逐步追蹤一個任務，並解釋為何先排隊才擴容（after step 3）
5. [[learn/小哲讲八股/nodes/juc-thread-pool/rejection-and-executors|拒絕策略怎麼選？Executors 為什麼被禁用]] — 在四種拒絕策略之間依「能不能丟、要不要回壓」做選擇，並說出 Executors 五類快捷池的 OOM 陷阱（after step 4）
6. [[learn/小哲讲八股/nodes/juc-thread-pool/virtual-threads|虛擬執行緒：為什麼百萬併發不再需要複雜的執行緒池]] — 講清楚虛擬執行緒的 M:N 調度與阻塞卸載，以及它對「一請求一執行緒」模型的改變（after step 5）

## Lesson

執行緒池這一塊，背下七個參數的名稱不難，難的是把它們串成一條「為什麼」的因果鏈：`new Thread` 的成本逼出了池化，池化的資源取捨逼出了核心與非核心的區分，這個區分又決定了任務提交後的四步流程，流程的盡頭才輪到拒絕策略登場。面試問「執行緒池打滿了怎麼辦」，真正想聽的是你能不能沿著這條鏈往回推——是核心數配小了、佇列無界把記憶體吃光，還是拒絕策略選錯把請求默默丟掉。

六個步驟照這條鏈排。先建立執行緒的生命週期與六種狀態（第 1 步），因為後面所有「執行緒在等什麼」都要用這組狀態描述；再從 `new Thread` 的成本推導池化的三個好處與執行緒數公式（第 2 步）；有了「為什麼要池」，才看得懂七個參數各自在管什麼（第 3 步）；接著把參數放進提交任務的四步流程裡跑一遍，理解「先排隊、後擴容」這個最容易被追問的設計（第 4 步）；然後處理兩個實戰問題——過載時拒絕策略怎麼選、Executors 的無界池為什麼被阿里手冊禁用（第 5 步）；最後把視角拉到 JDK 21，看虛擬執行緒如何用 M:N 調度讓「一請求一執行緒」重新變得可行（第 6 步）。
