# 執行緒池打滿、任務堆積

## Learning goal

能對「服務卡住、任務堆積、執行緒池打滿」這類線上狀況講出一條完整因果鏈：執行緒有哪些狀態、為什麼要池化、七個參數怎麼協同、任務提交後走哪四關、過載時拒絕策略如何兜底、Executors 為什麼不能直接用在生產，以及虛擬執行緒改變了什麼。

## Lesson

這一課要回答一個線上事故題：服務突然卡住，日誌裡一堆任務沒被執行，監控上執行緒數頂到上限，到底是怎麼回事。要講清楚這件事，得從「執行緒本身」一路講到「池子怎麼調度」，最後再看新一代的執行緒模型改寫了什麼。

第一步先把執行緒的六種狀態弄明白。NEW 是還沒 `start()`、RUNNABLE 是「在跑或等 CPU」、BLOCKED 是等 `synchronized` 鎖、WAITING 和 TIMED_WAITING 是主動掛起、TERMINATED 是結束。這裡最容易被追問的是 BLOCKED 與 WAITING 的差別：一個是被動等鎖，一個是主動等人叫醒。

接著問「為什麼不乾脆每個任務都開一條執行緒」。答案是 `new Thread()` 又貴又不可控：建立與銷毀要系統呼叫、每條執行緒吃掉約 1MB 堆外堆疊、併發一高就失控。執行緒池用池化解決這件事：複用、排隊、統一調度。而池子裡為什麼要分核心與非核心？核心執行緒是常駐的正式員工，保證日常延遲；非核心執行緒是臨時工，只在佇列也滿了時才加開，撐過尖峰就回收。這正是「彈性伸縮」的來源。

要真正看懂調度，就得掌握 `ThreadPoolExecutor` 的七個參數。把它想成一間銀行網點：`corePoolSize` 是正式員工數、`maximumPoolSize` 是所有窗口上限、`keepAliveTime` 與 `unit` 是臨時工的待命時間、`workQueue` 是候客區、`threadFactory` 是人力資源部、`handler` 是滿載時的保全。七個參數分成「人員數量」「等待區」「兜底輔助」三類來記，就不會漏。

有了參數，任務提交後的四步流程就說得通了：核心執行緒未滿就直接開人；滿了先把任務丟進佇列排隊（不是立刻擴容）；佇列也滿了才加開非核心執行緒；連最大執行緒都滿了，才輪到拒絕策略兜底。這裡的關鍵反直覺點是「先排隊、後擴容」，它決定了執行緒池在突發流量下是溫和堆積還是猛烈擴容。

最後兩步是收尾與展望。收尾是把 Executors 的坑補上：`newFixedThreadPool` 與 `newSingleThreadExecutor` 用無界佇列會堆到 OOM，`newCachedThreadPool` 的執行緒數上限是 `Integer.MAX_VALUE`，會瞬間開出成千上萬條執行緒。這也是阿里手冊要求手動 new `ThreadPoolExecutor` 的原因。展望則是 JDK 21 的虛擬執行緒：它把執行緒從 1:1 的內核綁定改成 M:N 的 JVM 調度，阻塞時自動卸載，讓「一個請求配一條執行緒」這種最好寫的同步程式碼，也能撐起百萬級併發。

六步走完，你手上就有一條從「一行 `new Thread()`」到「虛擬執行緒」的完整線，中間任何一環被追問都能往下接。
