# 日誌、WAL、複製與主從

## Learning goal

## Lesson

你在程式裡寫一句 `UPDATE user SET balance = balance - 100 WHERE id = 1;`，資料庫回你「Query OK」，這中間其實發生了一整套動作。如果它老老實實把磁碟上那一頁 16KB 的資料讀出來、改完、再寫回去，每次改幾個位元組都要付出一次隨機 I/O，寫入吞吐量根本撐不起線上流量；但如果它為了快，只改記憶體就說成功，那碰上斷電，改動就全不見了。這個節點要回答的，就是 MySQL（InnoDB）怎麼同時滿足「快」和「不丟」，而答案的起點是三個字：寫日誌。

第一步先把三種日誌攤開。Redo Log 是物理日誌、循環寫，負責崩潰恢復與持久性；Undo Log 是邏輯日誌、追加寫，負責回滾與 MVCC 的歷史版本；Binlog 屬於 Server 層、也是追加寫，負責主從複製與歸檔恢復。把這三者的定位、記錄內容、寫入方式分清楚，同時也就理解了 WAL（Write-Ahead Logging）「先寫日誌、再寫磁碟」為什麼是整條寫入鏈路的地基——它用順序的日誌寫入，換掉了慢吞吞的資料頁隨機寫入。

不過 Redo Log 和 Binlog 分屬引擎層與 Server 層，既然要一起變，就一定會有「一個寫了、一個還沒寫」的斷電風險。第二步的兩階段提交，就是把 Redo Log 的寫入拆成 Prepare 與 Commit 兩段，中間夾著 Binlog 的落盤，再靠崩潰恢復時的判斷規則，保證主庫與從庫不會出現「一邊有一邊沒有」。第三步則回到記憶體這一側：Buffer Pool 如何把讀寫都搬到記憶體、它的 LRU 為什麼要拆成新舊兩區，以及 Change Buffer 為什麼只對普通二級索引有效，這些都是同一個「減少磁碟 I/O」主題下的寫入優化。

最後兩步把視角拉到多台機器。主從複製靠 Binlog 與三個線程接力——主庫的 Binlog Dump Thread 發送、從庫的 I/O Thread 寫入中繼日誌、從庫的 SQL Thread 重放，而中繼日誌的存在是為了把「網路接收」與「SQL 執行」解耦。因為預設是異步複製，從庫難免落後，第五步就專門拆解主從延遲的根因與解法。走完這個節點，你應該能用「日誌分工 → WAL → 2PC → 記憶體緩衝 → 複製鏈路 → 延遲治理」這條線，把「資料庫為什麼不會丟資料、主從又為什麼會不同步」一次講清楚。
