# 鎖、JMM 與無鎖原子

## Learning goal

講清楚 synchronized 的 Monitor 與鎖升級、ReentrantLock、AQS、volatile/JMM/happens-before、CAS/ABA 與 LongAdder。

## Steps

1. [[learn/小哲讲八股/nodes/juc-locks-jmm-cas/synchronized-and-monitor|synchronized 是怎麼上鎖的？Monitor、可重入與鎖升級]] — 從 monitorenter/monitorexit 講到 Monitor 的 Owner 與計數器，並說明偏向、輕量級、重量級三級鎖各自解決哪種競爭場景
2. [[learn/小哲讲八股/nodes/juc-locks-jmm-cas/reentrantlock-and-aqs|ReentrantLock 與 AQS：state、CLH 佇列與 CAS]] — 比較隱式鎖與顯式鎖的差異與三大高階功能，並拆解 AQS 的 volatile state、CLH 變體佇列與 CAS 如何管理排隊執行緒（after step 1）
3. [[learn/小哲讲八股/nodes/juc-locks-jmm-cas/jmm-and-volatile|JMM 與 volatile：可見性、有序性與併發三大原則]] — 用主記憶體與工作記憶體解釋原子性、可見性、有序性三個問題，說明 volatile 為何保證可見性與有序性、卻不保證原子性（after step 1）
4. [[learn/小哲讲八股/nodes/juc-locks-jmm-cas/happens-before-and-dcl|happens-before 與 DCL：為什麼單例要加 volatile]] — 講清 happens-before 的定義與六條規則，並用指令重排序解釋 DCL 不加 volatile 時為何會拿到半初始化物件（after step 3）
5. [[learn/小哲讲八股/nodes/juc-locks-jmm-cas/cas-aba-and-longadder|CAS、ABA 與 LongAdder：無鎖原子與熱點分散]] — 說明 CAS 的 V/A/B 邏輯與硬體基礎、ABA 的問題與版本號解法，並解釋 AtomicInteger 高競爭變慢與 LongAdder 分治優化（after steps 2、4）

## Lesson

多執行緒出錯的現場，往往長得很像：計數器少加了幾次、共享物件明明還沒初始化就被別條執行緒拿去用、兩個執行緒各等對方放手而一起卡死。這些現象看起來是三個不同的 bug，追到最底層其實是同一件事——當多條執行緒同時讀寫同一塊記憶體，如果沒有任何約定，誰先誰後、誰看得到誰的修改，全都沒有保障。

這個節點就沿著「怎麼讓多條執行緒安全地共用記憶體」這條線走五步。第一步先看最經典的鎖：`synchronized` 靠物件頭裡的 Monitor 做到互斥與可重入，而 JVM 又用偏向、輕量級、重量級三級鎖，依照競爭激烈程度決定要不要驚動作業系統。第二步換到 `ReentrantLock`，看它如何用 AQS 這個「state 加排隊佇列」的框架，補上可中斷、公平鎖與多條件佇列這些原生鎖做不到的能力。第三、四步把鏡頭轉到記憶體模型：為什麼執行緒會讀到舊值、為什麼指令會被重排，以及 volatile 和 happens-before 如何用「承諾可見性」的方式把這些不確定性收斂掉——順便回答單例雙重檢查鎖為什麼非加 volatile 不可。最後一步則是硬幣的另一面：不加鎖的 CAS 怎麼靠 CPU 原子指令做到原子更新，它會踩到什麼 ABA 的坑，以及當熱點競爭太激烈時，LongAdder 如何用分治把壓力拆開。

走完之後，你應該能用「互斥、可見、有序、原子」四個詞，串起這一整組鎖與無鎖的取捨，而不是把每個 API 當成互不相干的孤立知識點。
