# 鎖、JMM 與無鎖原子

## Learning goal

講清楚 synchronized 的 Monitor 與鎖升級、ReentrantLock 與 AQS、volatile/JMM/happens-before，以及 CAS/ABA 與 LongAdder，能把「多執行緒為什麼出錯」與「JUC 怎麼補救」串成同一條因果鏈。

## Steps

1. [[learn/小哲讲八股/nodes/juc-locks-jmm-cas/synchronized-monitor-upgrade|synchronized 怎麼實現？Monitor、物件頭與鎖升級]] — 從字節碼與物件頭講到 Monitor、可重入與鎖升級四狀態
2. [[learn/小哲讲八股/nodes/juc-locks-jmm-cas/reentrantlock-and-aqs|ReentrantLock 與 AQS：一個 state 加一條等待佇列]] — AQS 的 state、CLH 佇列與 CAS，以及 ReentrantLock 比 synchronized 多出的能力（after step 1）
3. [[learn/小哲讲八股/nodes/juc-locks-jmm-cas/jmm-volatile-happens-before|JMM、volatile 與 happens-before：為什麼改了別的執行緒看不到]] — 用原子性、可見性、有序性串起 JMM、volatile 與 happens-before（after step 2）
4. [[learn/小哲讲八股/nodes/juc-locks-jmm-cas/dcl-why-volatile|為什麼 DCL 單例一定要加 volatile？半初始化物件的陷阱]] — 用 new 三步與指令重排序解釋 DCL 的 volatile 為什麼不能省（after step 3）
5. [[learn/小哲讲八股/nodes/juc-locks-jmm-cas/cas-aba-longadder|CAS、ABA 與 LongAdder：無鎖原子怎麼做到，又會在哪裡翻車]] — CAS 的 V／A／B、ABA 版本號解法，以及 LongAdder 分段累加（after step 4）

## Lesson

這個節點要回答的是一個很具體的問題：多執行緒明明共用同一塊記憶體，為什麼還會「我看不到你改的值」「你的建立到一半就被我拿去用」？答案分兩層，一層是硬體與 JVM 為了效率偷偷做的事——CPU 快取、指令重排序、物件建立拆成好幾步；另一層是 Java 為了把這些偷做的手腳管住，提供的工具——鎖、volatile、CAS。

五個步驟照著「先出錯、再補救、後優化」的順序走。第 1、2 步先把兩把互斥鎖講清楚：synchronized 是 JVM 用物件頭 Monitor 做的原生鎖，靠鎖升級在無競爭時省下作業系統切換；ReentrantLock 則是站在 AQS 這個同步器框架上，用一個 state 加一條等待佇列換來公平、可中斷、多 Condition 的彈性。第 3 步換到另一個角度，把原子性、可見性、有序性三個問題擺出來，用 JMM 的主記憶體／工作記憶體模型解釋 volatile 到底保證了什麼、又保證不了什麼，並用 happens-before 當作判斷可見性的規則書。第 4 步把這些抽象概念押在一個經典案例上：DCL 單例為什麼少一個 volatile 就會拿到半初始化物件。第 5 步走到無鎖路線，看 CAS 如何用一條 CPU 原子指令取代鎖，以及它在高競爭與 ABA 場景下會在哪裡翻車，最後用 LongAdder 的分段累加收尾。

學完之後，你應該能把「多執行緒為什麼出錯」與「JUC 怎麼補救」講成同一條因果鏈，而不是背下一堆名詞。
