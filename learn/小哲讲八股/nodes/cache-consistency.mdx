# 快取模式與資料一致性

## Learning goal

## Lesson

快取幫你把資料庫的壓力擋在前面，但快取本身也會出事。這一節圍繞兩個問題展開：當快取「失效或不存在」時，流量會怎麼打穿到資料庫；以及當資料真的變更時，本地快取、Redis 與 MySQL 這三層之間要怎麼收斂到一致。

第一個問題的三種典型是穿透、擊穿與雪崩。它們看起來都像「請求打到資料庫」，但成因完全不同：穿透查的是根本不存在、連資料庫也沒有的資料；擊穿是單一熱點 Key 突然過期，瞬間把高併發放進資料庫；雪崩則是大量 Key 同時失效、或快取層本身掛掉，導致整面流量一起湧入。分清楚這三者，你才不會把「加隨機 TTL」這種雪崩解法拿去回答擊穿。防穿透最有力的工具是布隆過濾器——它用一個位陣列加上多個雜湊函式，換來「說不存在就一定不存在」的保證，代價是會誤判存在、而且不能刪除。

第二個問題是快取一致性的主線。實務上很少去追強一致，而是用旁路快取（Cache-Aside）模式追求最終一致：變更時刪快取而不是更新快取，並且先寫庫、再刪快取。這套順序把併發下「後寫先至」的髒資料窗口縮到最小，但仍要靠延遲雙刪與 MQ 重試來兜底。更進一步，可以把刪快取的工作從業務程式碼裡拿出來，交給 Canal 訂閱 MySQL 的 Binlog，由它投遞事件、驅動下游清理，讓業務只管寫庫。

把這些拼起來，你就能回答面試裡最常追問的一句話：「Redis 你可以刪，但一百台機器記憶體裡的本地快取，你要怎麼刪？」答案是廣播失效訊息加上短 TTL 兜底，而這正是下一步要拆的機制。
