# GC、記憶體壓力與線上排查

## Learning goal

面對「記憶體一直漲、GC 頻繁」的告警，能講清楚可達性分析與四種引用、三種收集演算法與分代收集、STW 的成因、收集器從 Serial 到 ZGC 的演進與選型，並給出一條可操作的線上排查路徑。

## Steps

1. [[learn/小哲讲八股/nodes/jvm-gc-tuning/reachability-and-references|物件是垃圾嗎？可達性分析與四種引用]] — 講清楚 JVM 用可達性分析而非引用計數來判定物件死活，以及四類 GC Roots 與四種引用強度
2. [[learn/小哲讲八股/nodes/jvm-gc-tuning/collection-algorithms-and-stw|垃圾怎麼收？三種演算法、分代收集與 STW]] — 講清楚標記-清除／複製／整理各自的取捨、分代收集怎麼搭，以及 STW 為什麼躲不掉（after step 1）
3. [[learn/小哲讲八股/nodes/jvm-gc-tuning/collector-evolution-and-selection|收集器怎麼選？從 Serial 到 ZGC 與三色標記]] — 用取捨與判準決定該用哪個收集器，並看懂 G1 與 CMS 的底層差異（after step 2）
4. [[learn/小哲讲八股/nodes/jvm-gc-tuning/gc-frequent-diagnosis|線上 GC 頻繁怎麼查？從告警到根因的四步法]] — 面對頻繁 GC 告警，能照觀測、隔離、分析、解決四步定位根因（after step 3）

## Lesson

GC 這一塊真正會考的，不是背出「可達性分析、標記清除、G1、CMS」這些名詞，而是把它們串成一條因果鏈：JVM 先用可達性分析決定誰是垃圾，再用某種收集演算法把垃圾搬走，演算法的取捨逼出了不同的收集器，而每個收集器又用不同的方式控制 STW 的長度。當線上出現「記憶體一直漲、GC 頻繁」時，你其實是在沿著這條鏈往回找：是垃圾變多了、存活對象變久了，還是收集器與參數沒配好。

這四個步驟就是照這條鏈排的。先建立「誰能被回收」的判定規則與四種引用強度（第 1 步），再理解垃圾實際被收走時三種演算法的取捨、以及為什麼再怎麼優化都躲不掉 STW（第 2 步）；有了這兩層，才看得懂收集器從 Serial、Parallel、CMS 到 G1、ZGC 的演進其實是在同一組取捨上做不同的選擇（第 3 步）；最後把理論接回實戰，用 jstat、jmap、MAT 走完線上排查的四步法（第 4 步）。
