# Spring 事務管理與失效場景

## Learning goal

講清楚聲明式事務的 AOP 原理、回滾規則、七種傳播行為，並列出常見的事務失效場景。

## Steps

1. [[learn/小哲讲八股/nodes/spring-transaction/declarative-tx-and-aop-principle|從 JDBC 到 @Transactional：宣告式事務與 AOP 原理]] — 從手寫 commit 的痛點講到編程式與宣告式的分野，拆解 @Transactional 靠動態代理「開啟、提交、回滾」的流程，並帶出三個必懂的設定維度
2. [[learn/小哲讲八股/nodes/spring-transaction/rollback-rules|回滾規則：為什麼碰上受檢異常就不回滾]] — 講清楚 RuntimeException/Error 與 Checked Exception 的差別，以及 rollbackFor 為什麼幾乎是實務標配（after step 1）
3. [[learn/小哲讲八股/nodes/spring-transaction/propagation-behaviors|七種傳播行為：REQUIRED、REQUIRES_NEW 與 NESTED]] — 用 A 呼叫 B 的場景比較「共用、獨立、嵌套」三種關係，並帶過其餘四種的約束（after step 1）
4. [[learn/小哲讲八股/nodes/spring-transaction/failure-scenarios|宣告式事務失效：自調用、異常被吞、型別不符與修飾符]] — 把失效歸成四類踩坑，逐一指出它繞過代理或破壞回滾條件的機制與解法（after steps 2、3）

## Lesson

@Transactional 是那種「寫一行就以為萬事太平、出事才發現根本沒生效」的註解。多數人第一次遇到事務問題，不是因為不懂隔離級別，而是因為迴圈裡的一次 `this.save()` 讓整個回滾悄悄失效，或是 catch 了一個 checked exception 卻沒告訴 Spring「這也要回滾」。這些坑的共同點，是它們都發生在「Spring 到底有沒有攔到你的方法」和「Spring 到底認不認這個異常」這兩條線上。

前三步把這條線拆開來看。第一步先回到沒有框架的年代：用 JDBC 得自己 commit、rollback，於是 Spring 用 AOP 代理把這段樣板邏輯包起來，這就是宣告式事務的原理；代理在方法前開事務、方法後依結果提交或回滾，也因此衍生了「傳播行為、隔離級別、回滾規則」三個設定維度。第二步專攻回滾規則，講清楚為什麼預設只認 RuntimeException 與 Error，而 IOException、SQLException 這類受檢異常不配 rollbackFor 就不會回滾。第三步換到「方法互相呼叫」的場景，比較七種傳播行為：REQUIRED 是共用同一個物理事務、一起生一起死；REQUIRES_NEW 是掛起當前事務、自立門戶，常用於記錄日誌；NESTED 則是靠保存點做出可部分回滾的父子關係。

第四步把前面三條線收束成實戰場景。方法自調用之所以失效，就是因為 `this` 呼叫繞過了代理；異常被吞、型別不符、修飾符不對，則分別破壞了回滾的觸發條件或代理的增強前提。走完這四步，你應該能把「@Transactional 沒 rollback」這句含糊的描述，拆成一條可以排查的決策鏈：先問有沒有經過代理，再問有沒有拋出對的異常。
