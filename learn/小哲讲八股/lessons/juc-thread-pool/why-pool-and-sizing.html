為什麼要池化：從 new Thread 到核心與非核心執行緒

執行緒池打滿、任務堆積 · Step 2/6 · 學習目標：說明 new Thread 的三個問題、執行緒池的三個優勢、CPU／IO 密集型任務的執行緒數公式，以及核心與非核心執行緒如何分工。

前言：為什麼不能「來一個請求，就開一條執行緒」？

假設你接到一個需求：每收到一筆匯入任務，就在背景執行。最直覺的寫法可能是 new Thread(() -> 處理()).start()。測試環境中請求不多，程式看起來完全沒問題。

但到了生產環境，尖峰時段一來，大量請求同時建立執行緒。服務可能開始變慢、任務大量堆積，甚至因為記憶體被吃光而整個節點掛掉。這時候問題不一定出在任務本身，而可能是執行緒數量失去了控制。

多執行緒確實能提高吞吐量，但執行緒本身也是需要管理的資源。這一課會從三個相互連結的問題開始：為什麼需要多執行緒？為什麼執行緒不是越多越好？執行緒池又是如何把這件事管住的？

先問：我們為什麼要多執行緒？

多執行緒的價值，可以從三個常見場景看出來。

第一，是提高 CPU 利用率。現在的 CPU 幾乎都是多核心的。如果程式只有一條執行緒，通常只能同時使用其中一個核心，其他核心就像坐在旁邊等開工。多執行緒可以讓多個核心同時處理工作。

第二，是應對 IO 阻塞。讀檔、查資料庫、發送網路請求，都可能需要等待外部結果。假設 A 執行緒正在等資料庫回應，如果整個程式只有這一條執行緒，CPU 也只能跟著閒著。使用多執行緒後，A 等待時，CPU 可以先交給 B 執行緒處理其他工作。

第三，是提升響應速度與使用體驗。如果主執行緒直接執行一份耗時很久的報表，介面或請求就會被卡住。把這種任務交給背景執行緒，主執行緒才能繼續回應其他操作。

所以，多執行緒的重點不是單純「多開幾個人手」，而是讓一條執行緒等待時，其他執行緒可以利用 CPU。只是，這不代表執行緒可以無限制增加。

為什麼執行緒不是越多越好？

直覺上，做事的人越多，完成工作應該越快。但電腦裡有一個很容易被忽略的成本：上下文切換（Context Switch）。

CPU 從一條執行緒切換到另一條執行緒時，必須先保存目前執行緒的狀態，例如暫存器與程式計數器，再載入下一條執行緒的狀態。這些動作本身不會產生業務結果，卻需要花時間。

當執行緒數量太多，CPU 可能把大量時間花在「切換誰來執行」，而不是實際處理任務。就像一間廚房裡塞滿廚師，大家不斷閃身、讓路、搶同一個爐子，最後忙的都是協調，不是炒菜。

除了上下文切換，還有兩項成本也不能忽略：

  • 資源成本：每個 Java 執行緒預設約需要 1MB 的堆疊空間。建立幾千條執行緒時，光是堆疊就可能消耗大量記憶體。
  • 競爭成本：執行緒越多，搶同一把鎖的機會越高。大量執行緒如果都卡在等鎖，並不會讓處理速度變快，反而會拖慢整體吞吐量。

因此，解釋「為什麼不能亂開執行緒」時，可以記住三種成本：上下文切換傷時間，執行緒堆疊傷記憶體，鎖競爭傷吞吐量。

那到底該開幾條？先看任務是 CPU 密集還是 IO 密集

合理的執行緒數量，取決於任務主要是在使用 CPU，還是在等待 IO。常見可以分成兩種情境。

CPU 密集型任務的特徵是大量計算，例如加密解密、影片壓縮，以及複雜的正規表示式匹配。這類任務通常會讓 CPU 長時間維持高使用率。

既然 CPU 已經很忙，就不應該再建立大量執行緒讓它們互相切換。常見的建議公式是「CPU 核心數 + 1」。多出來的 1，可以在某條執行緒偶爾因缺頁中斷等原因暫停時，補上短暫的空檔，避免 CPU 完全閒著。

IO 密集型任務則包括 Web 應用、資料庫查詢、檔案讀寫與網路請求。這些任務的大部分時間可能都在等待結果，CPU 並沒有持續滿載。

這時可以多開一些執行緒，讓 A 執行緒等待 IO 時，CPU 轉去處理 B 執行緒。粗略的經驗公式是「2 × CPU 核心數」；如果要估算得更精確，可以使用「CPU 核心數 ×（1 + 等待時間 / 計算時間）」。等待時間占比越高，通常就越需要更多執行緒來填補 CPU 的空檔。

池化解決了什麼：把「用完就丟」改成「重複利用」

回到一開始的 new Thread()。它的問題可以整理成三點：

  • 建立成本高：作業系統需要為執行緒分配記憶體，並註冊相關的核心物件。
  • 銷毀成本高：任務完成後，執行緒與相關資源又要被回收。
  • 數量不可控：每來一個請求就開一條，併發一高，CPU 與記憶體可能瞬間被撐爆。

執行緒池的做法，就像把「每接一通電話，就臨時招募一名客服」改成「客服中心裡原本就有一批人」。客服接完一通電話後不會離職，而是回到座位等待下一通；這就是執行緒複用。

如果同時打進來的電話太多，客服忙不過來，系統也不會無限招人，而是先讓來電進入等待佇列；這就是任務排隊。再搭配統一的調度與監控，執行緒池就能把執行緒變成一種可限制、可觀察、可重複使用的資源。

因此，執行緒池主要帶來三個優勢：

  • 降低資源消耗：重複使用既有執行緒，減少反覆建立與銷毀的成本。
  • 提高響應速度：任務到達時，如果池中已有空閒執行緒，就能直接執行，不必等待新執行緒建立。這就像計程車已經在門口，不需要現叫車。
  • 提高可管理性：可以透過參數限制最大併發量，像防洪堤一樣擋住流量，避免請求一多就無限制建立執行緒。

核心執行緒與非核心執行緒：讓執行緒池可以彈性伸縮

執行緒池通常會把執行緒分成核心執行緒與非核心執行緒。這個設計是為了處理真實系統中很常見的流量波動。

如果按照最高峰流量配置所有執行緒，低谷時就會有大量執行緒閒置，卻仍然佔用記憶體。如果只按照平常流量配置，尖峰到來時又可能沒有足夠的處理能力。

核心執行緒負責支撐常態流量，可以把它想成公司的正式員工。它們平常就待在池中，任務到來時可以直接開始工作，不必臨時經歷建立與啟動執行緒的過程，也能避免執行緒不斷被銷毀、重建。核心執行緒對應的是系統的常態流量。

非核心執行緒則負責應付短時間的流量高峰，比較像臨時支援的人力。當核心執行緒忙不過來，而且排隊區也已經塞滿時，執行緒池才會增加非核心執行緒。

非核心執行緒的重點是可回收。如果它們閒置超過 keepAliveTime，就會被銷毀。尖峰過去後，這些臨時增加的執行緒不會在低谷期持續佔用記憶體。它們對應的是系統的峰值流量。

如果沒有核心與非核心的區分，系統通常只能在兩個壞結果中選一個：要嘛維持一個巨大的常駐執行緒池，平常浪費資源；要嘛執行緒池太小，尖峰時任務大排長龍。

核心執行緒負責守住日常流量，非核心執行緒負責吸收短暫高峰。兩者配合，才能在「節省資源」與「扛住突發流量」之間取得彈性。

小結

多執行緒的價值，在於利用等待時間並讓多核心 CPU 一起工作；但執行緒不是越多越好，因為會付出上下文切換、約 1MB 堆疊空間與鎖競爭三種成本。執行緒數量要先看任務類型：CPU 密集型可參考「核心數 + 1」，IO 密集型可參考「2 × 核心數」，或進一步考慮等待時間與計算時間的比例。執行緒池則把「用完就丟」改成「複用、排隊、統一管理」，再由核心執行緒處理常態流量、非核心執行緒吸收尖峰流量，讓系統能在可控的前提下彈性伸縮。
