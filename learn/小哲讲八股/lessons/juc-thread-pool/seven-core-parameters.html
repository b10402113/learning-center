七個核心參數：把執行緒池想成一間銀行

執行緒池打滿、任務堆積 · Step 3/6 · 學習目標：用銀行網點的比喻記住七個核心參數，並分成人員數量、等待區、兜底輔助三類。

前言：參數沒配好，執行緒池照樣會出事

你在 code review 裡看到一段建立執行緒池的程式碼：建構子塞了七個引數，數字看起來像是隨手填的。你可能知道其中幾個和「執行緒數量」有關，卻說不清楚第七個參數負責什麼，也不知道到底是哪個設定，會讓系統在尖峰時任務堆積，或在低谷時浪費資源。

執行緒池的行為，最後都會落到這七個參數上。它們就像一間銀行的營運規則：平常安排多少正式員工、尖峰時最多開幾個窗口、客戶太多時要在哪裡排隊，以及所有位置都滿了之後該怎麼處理。

搞懂這套規則，你才有辦法回答：「這個池子大概能承受多少併發？」「為什麼佇列一直變長？」「為什麼空閒執行緒沒有立刻回收？」接下來就用銀行網點的情境，把七個參數一次串起來。

核心類別：ThreadPoolExecutor

Java 執行緒池的標準實作是 ThreadPoolExecutor。它的建構子一共接受七個參數，可以先分成三類來掌握：

  • 配置人員數量：決定平常有多少執行緒，以及尖峰時最多能增加多少。
  • 配置等待區：暫時處理不了的任務要放在哪裡排隊。
  • 兜底與輔助：如何建立執行緒，以及滿載時如何處理新任務。

先逐一看懂每個參數，再回頭用這三類整理，面試時就不容易漏答。

人員數量類：corePoolSize、maximumPoolSize、keepAliveTime 與 unit

corePoolSize（核心執行緒數）是執行緒池平常維持的核心執行緒數量。它像銀行裡的正式員工：平常就坐在櫃檯，負責處理日常業務。這個數字決定了系統在常態流量下，至少有多少基本處理能力。

maximumPoolSize（最大執行緒數）是執行緒池允許建立的執行緒總數上限，也就是核心執行緒加上非核心執行緒的總和。它像銀行裡的所有窗口：正式員工使用的窗口，加上尖峰時臨時開出的窗口，最多只能開到這個數量。

keepAliveTime 和 unit 是一組搭檔。當執行緒數超過核心數時，多出來的非核心執行緒如果沒有任務可做，最多可以等待多久，這段時間由 keepAliveTime 決定；unit 則指定時間單位，例如秒或毫秒。

用銀行來比喻，這就是臨時員工的待命時間。尖峰時多請了幾位臨時員工，等業務量下降後，如果他們空等了一段時間仍沒有新客戶，就可以關閉臨時窗口、回收這些執行緒，避免長期占用資源。

等待區類：workQueue

workQueue 是用來存放「等待執行任務」的阻塞佇列。當核心執行緒都在忙時，新任務通常不會立刻建立更多執行緒，而是先放進佇列等待。

它就像銀行裡的候客區：所有正式窗口都有人辦理業務，新來的客戶先拿號碼、坐下排隊，而不是每來一位客戶就立刻再蓋一個窗口。

常見的佇列實作有兩種：

  • LinkedBlockingQueue：以鏈結串列實作，可以指定容量；如果不指定，容量預設很大。
  • ArrayBlockingQueue：以陣列實作，建立時必須指定容量。

佇列有沒有界，會直接影響執行緒池過載時的行為：任務可能持續堆積，也可能較快觸發拒絕策略。這也是後面理解 Executors 陷阱的重要基礎。

兜底與輔助類：threadFactory 與 handler

threadFactory（執行緒工廠）負責建立新執行緒。實務上通常會自訂它，替執行緒取有意義的名稱。這樣日後查看日誌或 thread dump 時，才能知道是哪一類任務正在執行。

它像銀行裡的人力資源部：負責招募人員、發放識別證，並把新員工正式登記進系統。

handler（拒絕策略）則處理最壞的情況：佇列已經滿了，執行緒數也達到最大值，這時又有新任務送進來。

它像銀行門口的保全。候客區坐滿、所有窗口也都開了，保全必須決定接下來怎麼辦：拋出錯誤請客戶稍後再試、讓提交任務的執行緒自己處理，或直接拒絕這位客戶。

七個參數放進建構子長什麼樣

ThreadPoolExecutor executor = new ThreadPoolExecutor(
    4,                                  // corePoolSize：正式員工 4 人
    8,                                  // maximumPoolSize：所有窗口上限 8 個
    60L, TimeUnit.SECONDS,              // keepAliveTime + unit：臨時工待命 60 秒
    new ArrayBlockingQueue<>(100),      // workQueue：候客區容量 100
    new CustomThreadFactory("order"),   // threadFactory：自訂執行緒名稱
    new ThreadPoolExecutor.AbortPolicy()// handler：滿載時拋出異常
);

把這段程式碼翻成銀行規則，就是：平常安排 4 位正式員工，最多開到 8 個窗口；臨時員工空閒 60 秒後可以回收；候客區最多容納 100 個任務；新執行緒由自訂工廠建立；所有資源都用滿時，直接拋出異常。

這樣看，七個參數就不再是七個孤零零的欄位，而是一整套營運規則：養幾位正式員工、最多開幾個窗口、臨時員工等多久、候客區多大，以及滿載後由誰處理。

面試時怎麼講得清楚：用「三類」串起來

如果面試官問 ThreadPoolExecutor 的七個核心參數，不建議直接從第一個背到第七個。比較穩的說法是先講：「我會把它們分成配置人員數量、配置等待區、兜底與輔助三類。」接著再逐類展開。這樣即使一時緊張，也比較不會漏掉參數。

第一類是配置人員數量：corePoolSize 是核心執行緒數，代表平常維持的基本執行緒數；maximumPoolSize 是執行緒總數上限；keepAliveTime 與 unit 則共同定義非核心執行緒的保活時間。超過核心數的執行緒如果空閒達到這段時間，就會被回收。

第二類是配置等待區：workQueue 用來存放暫時無法處理的任務。核心執行緒忙碌時，新任務會先在這裡等待。

第三類是兜底與輔助：threadFactory 負責建立新執行緒，通常會自訂名稱，方便觀察與除錯；handler 則在佇列已滿、執行緒數也達到上限時，決定如何處理新任務。

這種回答方式有兩個好處：先讓面試官聽見整體結構，再補上每個參數的細節。相比零散列舉，更有條理，也比較能接住後續追問。

小結

ThreadPoolExecutor 有七個核心參數，可以用銀行網點來記憶：corePoolSize 是正式員工、maximumPoolSize 是所有窗口的上限、keepAliveTime 與 unit 是臨時員工的待命時間、workQueue 是候客區、threadFactory 是人力資源部、handler 是滿載時的保全。回答時分成人員數量、等待區、兜底輔助三類，就能講得有條理，也不容易漏項。
