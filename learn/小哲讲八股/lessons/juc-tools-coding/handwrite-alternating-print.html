手寫交替打印：如何精準喚醒下一條執行緒

Step 5/6 · 併發工具與手寫併發題

學習目標

完成這一課後，你應該能用 ReentrantLock 搭配多個 Condition，寫出三條執行緒依序打印 A、B、C 的程式；也能用取模與 wait/notifyAll，處理 N 條執行緒依序打印數字的題目。

前言：不要把所有人都叫醒

面試裡常見一種併發題：啟動三條執行緒，讓它們輪流打印 A、B、C，最後得到 ABCABC；或者啟動 N 條執行緒，依照 0、1、2，一直到 N 減 1 的順序輪流打印。

題目看起來像是在考「怎麼印字」，其實真正考的是執行緒之間如何協調。當一條執行緒完成自己的工作後，它要怎麼通知下一條執行緒？如果每次都大喊「大家起床」，所有執行緒就會一起醒來搶鎖，結果多數執行緒發現還沒輪到自己，只好再睡回去。這樣既浪費效能，也可能因為叫醒了錯的人，讓真正該執行的執行緒一直等不到通知。

因此，這類題目要抓住兩個核心：第一是用狀態決定目前輪到誰，第二是用合適的喚醒方式通知下一個角色。接下來會比較兩種做法：一種是用多個 Condition 精準點名，另一種是用 notifyAll() 廣播，再讓每條執行緒自行判斷。

交替打印 ABC：用多個 Condition 精準點名

第一種解法使用 ReentrantLock 搭配三個 Condition。可以把每個 Condition 想成一間專屬等待室：A、B、C 三條執行緒各自等待在自己的房間裡。

另外，再用共用的 state 記錄目前的輪次。state % 3 等於 0 時輪到 A，等於 1 時輪到 B，等於 2 時輪到 C。每條執行緒只在輪到自己時打印，完成後把狀態往前推進，並叫醒下一位。

ReentrantLock lock = new ReentrantLock();
Condition cA = lock.newCondition();
Condition cB = lock.newCondition();
Condition cC = lock.newCondition();
int state = 0;

Thread a = new Thread(() -> {
    for (int i = 0; i < 3; i++) {
        lock.lock();
        try {
            while (state % 3 != 0) cA.await();  // 還沒輪到我就等
            System.out.print("A");
            state++;
            cB.signal();                        // 點名叫醒 B
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } finally {
            lock.unlock();
        }
    }
});

B 與 C 的程式邏輯相同，只是等待條件和通知對象不同：

  • B 等到 state % 3 == 1，打印 B 後呼叫 cC.signal()。
  • C 等到 state % 3 == 2，打印 C 後呼叫 cA.signal()，把下一輪的 A 叫醒。

這樣就形成 A → B → C → A 的閉環。每條執行緒做完自己的工作，只通知下一條執行緒，不會把所有等待中的執行緒都驚醒。這就是「精準喚醒」：像點名一樣，輪到誰就叫誰。

這裡的 while 不能改成 if。執行緒被喚醒，不代表它一定能立刻取得鎖，也不代表取得鎖時條件仍然成立。此外，執行緒還可能因為虛假喚醒而醒來。因此，醒來後必須重新檢查輪次；如果還沒輪到自己，就繼續等待。

N 執行緒順序打印：廣播，再讓大家自行判斷

第二種題目把執行緒數量擴充成 N 條。這時可以使用 synchronized、wait/notifyAll，再搭配取模運算完成輪轉。

第 i 號執行緒只關心一個條件：目前數字除以 N 的餘數是否等於 i。例如 N 是 3，當前數字的餘數是 0，就由 thread 0 打印；餘數是 1，就由 thread 1 打印；以此類推。

private int currentNumber = 1;
private final int N = 3;

public synchronized void printNumber(int threadId) throws InterruptedException {
    while (currentNumber % N != threadId) {
        this.wait();               // 不是輪到我，繼續等
    }
    System.out.println("Thread-" + threadId + " : " + currentNumber);
    currentNumber++;
    this.notifyAll();              // 廣播，讓下次該跑的人自己醒來
}

這個版本和多個 Condition 的差別在於：大家共用同一個等待集合。每次有執行緒完成打印，就呼叫 notifyAll()，讓所有等待中的執行緒醒來，再各自檢查目前的數字是否輪到自己。

為什麼不能隨便把 notifyAll 改成 notify

這是這類題目最容易寫錯的地方。notify() 只會隨機叫醒一條等待中的執行緒。假設目前應該輪到 thread 1，卻剛好叫醒了 thread 0，thread 0 檢查後發現條件不成立，只能再次等待。此時真正該執行的 thread 1 並沒有被叫醒，整個流程就可能停在原地。

notifyAll() 的做法比較吵，但更安全：它把所有等待中的執行緒叫醒，大家各自重新檢查條件。只有符合目前餘數的那一條會繼續往下執行，其他執行緒則回到等待狀態。

這種方式可能造成多餘的喚醒與鎖競爭，也就是常說的驚群現象。不過在共用同一個判斷條件、又無法直接指定下一條執行緒的情況下，廣播可以避免「剛好叫錯人」導致流程卡住。

為什麼條件一定要放在 while 裡

不論使用 Condition.await()，還是使用 Object.wait()，都不能只在等待前檢查一次條件：

if (conditionNotMet) {
    wait();
}

問題在於，執行緒被喚醒後，條件不一定仍然成立。它可能只是遇到虛假喚醒，也可能在重新取得鎖之前，已經有其他執行緒先改變了共用狀態。

因此，正確的思路是讓執行緒反覆確認：

while (conditionNotMet) {
    wait();
}

每次醒來都重新判斷。條件不成立就繼續等，只有真的輪到自己，才可以打印並更新狀態。

兩種喚醒策略的取捨

面向多個 ConditionnotifyAll 廣播
喚醒範圍只叫醒指定的下一條叫醒等待集合裡全部執行緒
鎖的型別ReentrantLock 加 Conditionsynchronized 加 wait/notifyAll
效率較高，沒有無謂競爭較低，可能出現驚群
寫法難度要維護多個等待室與狀態機靠取模讓大家自己判斷

如果每個角色都有清楚、獨立的等待條件，多個 Condition 會比較直接。A 做完叫 B，B 做完叫 C，程式的流程像接力賽一樣清楚。

如果所有執行緒共用同一套判斷規則，只是各自等待不同的餘數，那麼使用 notifyAll() 會比較容易擴充。代價是每次廣播都可能叫醒一群暫時還不能工作的執行緒。

小結

交替打印的重點，不只是把字元印出來，而是要讓正確的執行緒在正確的時機醒來。使用 ReentrantLock 加多個 Condition 時，可以讓每條執行緒待在自己的等待室，完成工作後用 signal() 精準點名下一條，並透過 state % 3 形成 A、B、C 的輪轉。N 執行緒順序打印則可以使用 synchronized 加 wait/notifyAll，讓所有執行緒醒來後自行檢查取模結果。這個版本一定要使用 notifyAll，因為 notify 可能只叫醒錯的人，讓真正該執行的執行緒繼續沉睡。無論採用哪一種做法，等待條件都必須放在 while 中重新檢查。
