ThreadLocal 執行緒隔離：每條執行緒都有自己的私有抽屜

Step 1/6 · 併發工具與手寫併發題

學習目標

這一節會帶你弄懂 ThreadLocal 如何做到執行緒隔離：每個 Thread 都持有自己的 ThreadLocalMap，Map 裡的 Key 是弱引用，Value 則是強引用。你也會知道，為什麼這種設計在線程池中可能造成記憶體洩漏、為什麼用完一定要 remove()，以及 InheritableThreadLocal 在執行緒池裡為何可能帶來上下文污染，最後再看 TTL 怎麼處理這個問題。

前言：當「大家共用一份」開始添麻煩

寫 Web 後端時，常會遇到這樣的需求：同一個請求從 Controller 進入，經過 Service、DAO，甚至到了日誌與攔截器，都需要知道「這是哪位使用者發出的請求」。

最直接的做法，是替每個方法加上一個 userId 參數，再一路往下傳。可是這樣一來，方法簽名會愈來愈肥，許多中間層的方法明明不需要使用者編號，卻只能被迫當資料搬運工。

另一個常見例子是 SimpleDateFormat。它建立成本高，大家自然會想共用一個靜態實例。但它不是執行緒安全的，多條執行緒同時呼叫 parse，可能讀到錯亂的日期，甚至直接拋出例外。

這些問題的根源，不只是「共用」本身，而是把原本應該各自擁有的資料，硬塞進同一個共享位置。當然可以用鎖保護它，但鎖會讓執行緒排隊；在高頻讀取的場景裡，大家只是拿一份資料，卻要輪流等待，代價不小。

ThreadLocal 採取另一種思路：不要讓所有人搶同一份資料，而是替每條執行緒準備一份自己的副本。這一節會從資料實際存放的位置開始，說清楚它如何做到執行緒隔離，以及那個幾乎每個人都可能踩到的坑：記憶體洩漏。

用空間換時間，避免大家排隊

面對共享變數的執行緒安全問題，最直覺的做法是加鎖。例如用 synchronized 保護臨界區，規定同一時間只允許一條執行緒進入。

這種方案的優點是容易理解，也能保證正確性；但代價是其他執行緒必須等待。執行緒越多、存取越頻繁，排隊與上下文切換帶來的成本就越明顯。這可以看成是用「時間」換安全：資料只有一份，但大家要輪流使用。

ThreadLocal 則反過來，用「空間」換取安全。它為每條執行緒準備一份獨立副本，A 執行緒修改自己的資料，B 執行緒修改自己的資料，兩者不會互相干擾，因此也沒有競爭同一份資料的問題，通常不需要加鎖。

這種做法特別適合一次請求內會頻繁取用、但不希望層層傳參的上下文資訊，例如使用者身分、請求上下文或追蹤資訊。

資料到底放在哪裡：一個容易搞反的結構

不少人第一次接觸 ThreadLocal 時，會以為 ThreadLocal 自己維護了一個 Map，Key 是執行緒，Value 是資料。實際上剛好相反。

真正的結構是：每一條執行緒自己帶著一個 Map。這個 Map 掛在 Thread 物件上，型別是 ThreadLocalMap。ThreadLocal 比較像是一把用來查找資料的鑰匙，而不是資料真正存放的容器。

Thread（每一個執行緒物件）
  └── threadLocals : ThreadLocalMap
        ├── key   = ThreadLocal 實例（弱引用）
        └── value = 你要存的資料（強引用）

當你呼叫 threadLocal.set(value) 時，實際流程是先取得目前執行緒的 threadLocals，再把這個 ThreadLocal 實例當成 Key，將 value 存進 Map。

呼叫 get() 時也是同一套邏輯：到目前執行緒自己的 Map 裡，用這個 ThreadLocal Key 找回對應的值。只要記住「Map 在 Thread 裡，而不是在 ThreadLocal 裡」，後面記憶體洩漏與清理規則就會變得容易推導。

記憶體洩漏：弱引用 Key 與強引用 Value 的組合

ThreadLocalMap 的 Key 使用弱引用，Value 使用強引用。這樣的設計本身不一定立刻出問題，但在線程池中，如果沒有主動清理，就可能留下難以察覺的記憶體洩漏。

假設一條線程池中的工作執行緒，建立了一個 ThreadLocal 物件並存入資料。後來，程式中已經沒有其他地方持有這個 ThreadLocal 物件的引用。垃圾回收發生後，Map 裡的 Key 可能就會變成 null。

但這條工作執行緒仍然活著，而 Value 仍由 Map 強引用著。於是就出現一個尷尬的狀態：Key 不見了，程式再也找不到這筆資料；Value 卻還被 Map 抓住，無法回收。

如果執行緒很快結束，問題通常會隨著執行緒一起消失。但線程池中的工作執行緒往往會長時間重複使用，甚至直到應用程式關閉才結束。這些找不到、卻又回收不了的 Value，便可能一點一點堆積起來。

解法只有一句：誰建立，誰清理。使用完畢後，務必在 finally 裡呼叫 threadLocal.remove()。雖然 JDK 在執行 set 或 get 時，可能順手清理部分 Key 已經是 null 的槽位，但這只能算是額外的清理機會，不能當成你的資源管理策略。你無法預測下一次操作何時發生，也不該把清理責任交給「剛好下一次有人來存取」。

父子執行緒之間，資料怎麼傳遞？

ThreadLocal 的隔離範圍是「執行緒」。因此，父執行緒設定的值，子執行緒預設看不到。

如果真的需要傳遞，有兩種方向。第一種是回到共享記憶體，將變數設計成共享資料，再搭配 volatile 或鎖，處理可見性與執行緒安全。

第二種是使用 InheritableThreadLocal。它會在建立子執行緒的那一刻，把父執行緒當下的變數複製一份給子執行緒，因此常被用來傳遞全鏈路追蹤的 traceId。

不過，這裡有一個關鍵限制：複製只在 new Thread() 建立子執行緒時發生。線程池中的執行緒會反覆重複使用，提交任務時通常不會重新建立執行緒，因此也不會再次觸發這個複製動作。

結果可能是：目前任務拿到上一個任務留下的舊值，造成上下文污染，甚至出現使用者身分串號。這種問題通常不會每次都發生，卻可能在高併發或特定執行順序下突然出現，所以特別難追查。

常見的標準做法，是改用阿里開源的 TransmittableThreadLocal，簡稱 TTL。它把上下文傳遞拆成「捕獲、回放、還原」三個時機：提交任務時先捕獲目前上下文，任務在線程池中執行前再回放進去，執行完成後還原原本狀態。

這樣一來，即使工作執行緒會被重複使用，也能讓每個任務取得正確的上下文，避免把上一個任務的資料帶到下一個任務。

小結

ThreadLocal 透過「用空間換時間」，為每條執行緒提供自己的資料副本，避免多條執行緒競爭同一份資料，也就不必依賴鎖來保護。資料不是存放在 ThreadLocal 實例本身，而是存放在每條執行緒自己的 ThreadLocalMap 裡；ThreadLocal 實例是 Key，而且是弱引用，資料則是 Value，而且是強引用。這種組合在線程池中可能留下無法再存取、卻又無法回收的 Value，因此用完一定要呼叫 remove()。父子執行緒之間可以使用共享變數或 InheritableThreadLocal 傳遞資料，但後者只在建立執行緒時複製，放在線程池裡可能造成上下文污染；正式場景通常改用專門處理執行緒池透傳的 TTL。
