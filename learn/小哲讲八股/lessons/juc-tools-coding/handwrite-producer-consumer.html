手寫生產者消費者：等待與通知的攻防

Step 4/6 · 併發工具與手寫併發題

學習目標

你會寫出一個以 synchronized、wait() 與 notifyAll() 實作的生產者消費者程式，也能說清楚為什麼要用固定容量、為什麼必須釋放鎖，以及為什麼條件判斷要放在 while 裡。

前言：白板上最常出現的一題

面試官把白板筆推過來，說：「寫一個生產者消費者。」這題表面上是在考 API，實際上是在確認你是否理解執行緒之間最基本的等待與通知。

放到工作場景裡，它對應的是一個有界佇列。生產端不能因為下游太慢，就一直把資料塞進記憶體，最後把記憶體撐爆；消費端也不能在沒有資料時不斷輪詢，對著空佇列空轉、白白燒掉 CPU。兩邊需要一個能暫存資料的中間區域，也需要一套互相協調的規則。

這套規則其實很直觀：條件不滿足就先睡，睡之前要把鎖讓出來；有人改變了條件，就通知可能正在等待的執行緒。真正容易出錯的地方，通常不是「會不會呼叫 wait()」，而是醒來之後能不能正確地重新確認條件。那也是面試官最常追問的 while 迴圈。

核心思路：中間容器加等待通知

生產者與消費者不直接碰面，中間放一個固定容量的倉庫。這個倉庫同時解決兩個問題。

第一，它負責解耦。生產者只要把資料放進倉庫，消費者只要從倉庫取資料，兩邊不需要知道彼此的執行細節。第二，它提供緩衝，吸收兩邊速度不一致的落差。

當倉庫滿了，生產者不能再放，就必須等待；當倉庫空了，消費者沒有東西可取，也必須等待。等另一邊完成操作、讓條件發生變化後，再通知可能正在等待的執行緒。

實作時還要保護臨界區。倉庫裡的 LinkedList 不是執行緒安全的，而生產與消費都會修改它，所以同一時間只能讓一條執行緒操作倉庫。

完整程式碼

class Storage {
    private final int MAX_SIZE;
    private final LinkedList<Object> list = new LinkedList<>();

    public Storage(int maxSize) {
        this.MAX_SIZE = maxSize;
    }

    // 生產：滿了就等，醒來再檢查
    public synchronized void produce() throws InterruptedException {
        while (list.size() == MAX_SIZE) {
            this.wait();          // 釋放鎖並進入等待
        }
        list.add(new Object());
        System.out.println("生產一個，庫存 " + list.size());
        this.notifyAll();         // 叫醒可能在等的消費者
    }

    // 消費：空了就等，醒來再檢查
    public synchronized void consume() throws InterruptedException {
        while (list.size() == 0) {
            this.wait();          // 釋放鎖並進入等待
        }
        list.removeFirst();
        System.out.println("消費一個，庫存 " + list.size());
        this.notifyAll();         // 叫醒可能在等的生產者
    }
}

主程式只要建立兩條執行緒：一條反覆呼叫 produce()，另一條反覆呼叫 consume()。當倉庫滿或空時，對應的一方會暫停；條件改變後，另一方再被喚醒繼續工作。

三個一定要講清楚的細節

1. 為什麼要加鎖？

倉庫是多條執行緒共用的可變狀態。假設一條執行緒正在 add，另一條執行緒同時進行 removeFirst，兩個操作可能交錯執行，造成狀態讀寫不一致。

用 synchronized 保護方法，就是讓同一時間只能有一條執行緒進入生產或消費的臨界區。這把鎖像倉庫的唯一鑰匙：拿到鑰匙的人才能查看並修改庫存，其他人必須先在外面等。

2. 為什麼 wait() 必須釋放鎖？

假設倉庫已經滿了，生產者需要等待。如果它睡著了卻仍然抓著鎖不放，消費者就進不來取走資料。沒有人能改變「倉庫已滿」這個條件，也就沒有人能讓生產者重新開始工作，整個程式會卡住。

Java 的 wait() 會在讓執行緒進入等待狀態的同時，釋放它持有的監視器鎖。其他執行緒因此有機會進入臨界區，消費資料或補進資料，讓等待條件發生變化。

被 notify() 或 notifyAll() 喚醒的執行緒，也不會立刻從 wait() 後面繼續執行。它必須重新競爭同一把鎖，成功拿到鎖後，才會繼續往下走。

3. 為什麼要用 while，不能用 if？

這是整題最關鍵的細節。wait() 可能發生虛假喚醒，也就是沒有收到有效通知，執行緒卻自己醒來。此外，即使執行緒確實是被通知而醒來，在它重新搶到鎖之前，其他執行緒也可能已經先改變了倉庫狀態。

所以，執行緒醒來後不能直接假設條件已經成立，而要重新檢查一次。如果條件仍然不滿足，就繼續等待。這正是 while 的作用。

反例：把 while 寫成 if (list.size() == 0) wait();。如果倉庫原本只有一件商品，兩個消費者同時被喚醒，第一個消費者拿到鎖後取走商品；第二個消費者接著拿到鎖，卻因為沒有重新檢查，直接呼叫 removeFirst()。這時倉庫其實已經是空的，程式就會拋出例外。改成 while 後，第二個消費者會發現條件仍然不成立，於是回到等待狀態。

notify() 還是 notifyAll()？

這題通常還會被追問：「為什麼使用 notifyAll()，而不是 notify()？」關鍵在於，生產者與消費者共用同一把鎖，也共用同一個等待集合。

notify() 只會隨機喚醒一條等待中的執行緒。如果剛好喚醒的是「同一類」執行緒，問題就可能沒有被解決。假設倉庫剛剛有空間，一個生產者完成操作後呼叫 notify()，結果喚醒的卻是另一個生產者。被喚醒的生產者檢查後發現倉庫仍然滿了，只好繼續睡；真正等待資料的消費者卻沒有被叫醒，流程就可能卡住。

notifyAll() 則會喚醒等待集合裡的所有執行緒。它們接著各自競爭鎖，並重新檢查條件；條件不成立的繼續等待，條件成立的執行緒才會繼續操作。

這樣做的代價是可能一次喚醒太多執行緒，讓它們一起競爭鎖，這種現象通常稱為驚群。但在生產者與消費者共用一把鎖的場景中，notifyAll() 比只喚醒一個「不一定對的人」更安全。

日常開發：直接使用 BlockingQueue

在實際開發中，通常不需要自己重新實作這套機制。JDK 提供的 BlockingQueue 已經把鎖、等待與條件判斷封裝起來。

put() 在佇列滿了時會阻塞，take() 在佇列空了時會阻塞。像 ArrayBlockingQueue 這類實作，可以直接拿來建立生產者與消費者之間的緩衝區。

不過，面試要求手寫這題，看的不是你平常是否會使用 BlockingQueue，而是你能不能說明它背後的原理：誰在等待、何時釋放鎖、條件為什麼要重查，以及為什麼需要廣播通知。

小結

生產者消費者透過固定容量的中間容器，把生產端與消費端解耦，再利用等待與通知平衡兩邊的速度：滿了，生產者等待；空了，消費者等待；誰改變了條件，誰就負責通知可能正在等待的執行緒。實作時要記住三件事：用 synchronized 保護共享倉庫；用 while 而不是 if，醒來後重新檢查條件；用 notifyAll() 廣播通知，避免通知被同類執行緒接走而讓真正需要工作的執行緒繼續沉睡。wait() 會釋放鎖，正因如此，其他執行緒才有機會進來改變條件。
