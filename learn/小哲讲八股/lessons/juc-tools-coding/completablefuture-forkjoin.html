CompletableFuture 與 ForkJoinPool：把非同步任務串起來，也把工作分配好

Step 3/6 · 併發工具與手寫併發題

先抓住兩個問題：怎麼同時做事？做完後怎麼接著做？

假設首頁需要呼叫三個下游服務。如果一個接一個呼叫，總延遲就會變成三個服務耗時的總和。前一個服務還沒回來，後面的服務就只能在旁邊等，主線程也像站在櫃檯前排隊一樣，什麼都做不了。

比較理想的方式，是把三個請求同時送出去，等結果全部回來後，再一次組合成首頁需要的資料。這裡其實有兩個問題：任務要如何並行執行？前一個任務完成後，下一步又要如何自動接上？

你可能會先想到 ExecutorService 加 Future。它確實能把任務送出去，但取得結果時通常要呼叫 get()，這會讓目前的執行緒阻塞。如果要等待多個 Future，程式碼很快就會充滿等待、判斷與輪詢，任務之間的組合關係也不容易表達。

CompletableFuture 解決的正是這一段。它可以把「任務完成後，自動執行下一步」串成一條鏈，讓主線程不必停在原地等結果。

另一個常見問題是分治。假設要統計一個很大的陣列，可以先把陣列切成幾段，再讓多個執行緒平行計算。這時候，執行緒池的任務分配方式就很重要。

一般的 ThreadPoolExecutor 讓所有工作執行緒共用一個佇列；ForkJoinPool 則讓每條執行緒擁有自己的佇列，閒下來時還能向其他執行緒「偷」任務。這兩個主題也彼此相關，因為 CompletableFuture 沒有指定執行緒池時，預設使用的就是 ForkJoinPool.commonPool()。

CompletableFuture 的底層：用狀態機記錄結果，用無鎖棧接起回調

先看它如何管理「任務是否完成」。每個 CompletableFuture 內部都有一個 volatile Object result。這個欄位同時扮演兩種角色：它保存任務結果，也用來表示任務目前的狀態。

當欄位仍是 null，或處在某個中間狀態時，代表任務尚未完成。當欄位被設定成正常結果或異常物件，就代表任務已經結束。換句話說，它把「結果」和「狀態」放進同一個位置管理，像在門口掛一個牌子：牌子還沒掛好，表示事情未定；牌子一旦掛上去，其他人就知道結果了。

完成操作靠的是 CAS，也就是「比較並交換」。complete() 的核心工作，可以理解成嘗試使用 Unsafe.compareAndSwapObject，把 result 從 null 更新成實際結果。

多條執行緒可能同時嘗試完成同一個任務，但只有一條執行緒能成功 CAS。成功的那條執行緒，就負責宣告任務完成。這樣可以避免多條執行緒同時改寫狀態，也不需要使用傳統鎖。

回調怎麼排隊：Treiber Stack 與 postComplete()

接著看 .thenApply()、.thenAccept() 這類操作。呼叫它們時，主線程不會停下來等前一個任務完成。CompletableFuture 會先把後續操作包裝成一個 Completion 節點。

如果前一個任務還沒完成，這個節點就會被放進一個 Treiber Stack。它是一種以 CAS 維護的無鎖並發棧，可以把它想成「先登記，等前一個任務完成時再叫我」。

如果前一個任務在註冊回調之前就已經完成，CompletableFuture 就不必再把節點放進棧裡，而是直接觸發後續操作。這避免了回調永遠掛著，也處理了「註冊時任務剛好完成」這種競爭情況。

前序任務完成後，會先透過 CAS 成功更新 result，接著呼叫 postComplete()。這個方法會持續從棧中取出 Completion 節點，並呼叫每個節點的 tryFire()，讓下一個任務開始執行。

因此，一個任務完成，就能自動觸發下一個任務；下一個任務完成，又能繼續觸發後續節點。整條鏈像骨牌一樣往下倒，但中間不需要主線程一直站著輪詢。

面試時可以把它概括成一句話：CompletableFuture 以基於 CAS 的狀態管理結果，再用 Treiber Stack 維護待觸發的回調鏈，任務完成後透過 postComplete() 逐步推進後續操作。

預設執行緒池：方便，但別把阻塞任務丟進公共池

如果建立 CompletableFuture 時沒有指定執行緒池，非同步任務預設會使用全域共用的 ForkJoinPool.commonPool()。它的工作執行緒數量預設是 CPU 核數減一。

這個預設值很方便，卻也埋著一個容易被忽略的問題：commonPool 是整個 JVM 共用的公共資源。你的程式碼、其他模組，甚至平行流，都可能使用同一個池。

如果把大量阻塞式 IO 任務丟進去，工作執行緒就會長時間卡在網路或磁碟操作上。它們雖然沒有在計算，卻仍然佔著執行緒名額。結果是其他原本不相關、同樣依賴 commonPool 的任務，也可能拿不到執行緒。

因此，判斷方式很簡單：如果任務會阻塞，就明確傳入自訂執行緒池，不要讓它和整個 JVM 的其他工作擠在同一個公共池裡。

ForkJoinPool 與 ThreadPoolExecutor：公共佇列，還是各自排隊再互相支援？

兩者都是執行緒池，但設計目標不同。關鍵差異不在名稱，而在「任務放在哪裡」以及「執行緒沒工作時怎麼辦」。

ThreadPoolExecutor：大家搶同一個公共佇列

ThreadPoolExecutor 通常採用單一公共佇列。所有工作執行緒都從同一個地方取任務，就像多位店員共用一個待辦清單。

這種設計很適合彼此獨立的任務：任務進來後，哪條執行緒拿到都可以直接執行，不需要處理子任務或等待其他工作。

但當執行緒很多、任務也很多時，大家都要競爭同一個佇列。共享資料越集中，競爭就越容易成為瓶頸。

ForkJoinPool：先做自己的，再去幫忙偷任務

ForkJoinPool 是為分治任務設計的。每條工作執行緒都有自己的雙端佇列，平常優先從自己的佇列取任務執行，因此不必每次都和其他執行緒爭搶同一個公共佇列。

當某條執行緒把自己的任務做完、暫時無事可做時，它會到其他執行緒的佇列尾端「偷」一個任務回來執行。這就是工作竊取。

為什麼要一個從頭部取、一個從尾部偷？因為這樣可以降低兩邊同時操作同一位置的機會。原本的佇列主人從頭部取自己的工作，來幫忙的執行緒則從尾部偷工作，彼此較少碰撞，鎖競爭也比較低。

這種設計特別適合可以不斷拆成子任務的遞迴分治。例如把大陣列切成多段，先平行處理各段，再合併結果。任務多的執行緒能繼續分割工作，任務少的執行緒則可以主動幫忙，讓 CPU 更不容易閒下來。

面向ThreadPoolExecutorForkJoinPool
佇列結構單一公共佇列每條執行緒一個雙端佇列
任務分配所有執行緒從同一個佇列搶任務平常取自己的頭部，空閒時偷別人的尾部
衝突程度共享佇列，競爭較高各自處理為主，衝突較低、CPU 利用率較高

平行流，也就是 stream().parallel()，預設同樣使用 commonPool。它適合 CPU 密集的計算；如果在平行流裡進行阻塞式 IO，也可能長時間佔住公共池，影響其他使用者。

把整張圖串起來

CompletableFuture 內部用 volatile Object result 同時保存結果與狀態，complete() 透過 CAS 更新它。thenApply 這類後續操作會被包成 Completion 節點，放進 Treiber Stack 這個無鎖棧；前序任務完成後，由 postComplete() 逐一取出節點並呼叫 tryFire()，把回調鏈往後推進。它預設使用全域共用的 ForkJoinPool.commonPool()，因此阻塞任務應該使用自訂執行緒池，避免拖慢其他工作。ForkJoinPool 透過每條執行緒的雙端佇列與工作竊取，適合可分治的遞迴任務；ThreadPoolExecutor 透過單一公共佇列，適合彼此獨立的任務。
