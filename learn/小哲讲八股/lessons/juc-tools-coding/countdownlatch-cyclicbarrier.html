CountDownLatch 與 CyclicBarrier：先搞懂「誰在等誰」

Step 2/6 · 併發工具與手寫併發題

前言：同樣是等待，關係可能完全不同

商品詳情頁通常要同時取得庫存、價格與評論。這三個下游服務彼此獨立，如果一個接一個呼叫，總延遲就會變成三者耗時的總和；主線程也只能站在原地乾等。比較好的做法，是讓三個任務平行執行，最後由主線程等它們全部回報完成。

另一種情況是批次運算。假設資料被切成四份，四條執行緒各自處理一份。每條執行緒算完後，不能立刻進入下一階段，而是要先等其他三條也完成，大家到齊後才能一起合併結果。這個流程可能還會重複好幾輪。

這兩個場景都有「等待」，但等待關係不一樣：前者是「一個人等多個人」，後者是「多個人互相等」。JDK 提供了 CountDownLatch 與 CyclicBarrier 來表達這兩種語義。工具選錯時，程式也許仍然能勉強運作，但程式意圖會變得模糊，後續維護就像拿錯登機門的行李，越整理越容易出問題。

學習目標

看完這一課，你應該能分辨 CountDownLatch 的「一個等多」與 CyclicBarrier 的「多個互等」，並理解兩者的底層差異：前者基於 AQS 共享模式，後者則是 ReentrantLock 搭配 Condition。你也會知道一次性與可循環這兩種設計，各自適合什麼場景。

CountDownLatch：一個等多，而且只等一次

CountDownLatch 的模型很像火箭發射前的檢查流程。主線程是指揮官，開始後就在發射台等待；檢查引擎、注入燃料、確認天氣等任務，則由不同執行緒各自完成。每項工作做完，就回報一次。等所有檢查項目都完成，指揮官才下令點火。

它的核心是一個計數器。建立時先指定初始值，子任務完成後呼叫一次 countDown()，讓計數減一；主線程呼叫 await() 暫停自己，直到計數器歸零才繼續往下執行。

CountDownLatch latch = new CountDownLatch(3);

for (int i = 0; i < 3; i++) {
    new Thread(() -> {
        try {
            doWork();          // 各項檢查
        } finally {
            latch.countDown(); // 回報完成，計數減一
        }
    }).start();
}

latch.await();                 // 主線程等到計數歸零
System.out.println(\"全部完成，可以發射\");

這裡有一個很重要的限制：計數器只能減少，不能增加。當它歸零後，所有等待中的執行緒都會被放行，這個 Latch 也就完成任務。若下一輪還要等待，必須重新 new 一個新的 Latch，因此它是「一次性」的同步工具。

CyclicBarrier：多個互等，然後一起往前走

CyclicBarrier 比較像公司旅遊時的集合點。大家可以從不同地方出發，但每個人都必須先抵達集合點；等所有人到齊後，司機才發車。這裡沒有一個特別的「主線程」負責等其他人，所有參與者的地位相同，每條執行緒都呼叫 await()，彼此等待。

它同樣有一個計數器，但計數代表的是「還有幾條執行緒尚未抵達集合點」。每到一條執行緒，計數就減一。當最後一條執行緒抵達時，障礙被打開，原本被擋住的執行緒一起繼續執行。

CyclicBarrier 還能設定 barrierAction。這段動作會由最後抵達的執行緒執行，適合處理「所有人到齊後」才能進行的彙總工作。

名稱中的 Cyclic 代表它可以循環使用。這一輪的障礙打開後，計數器會自動重置，下一輪可以繼續使用同一個物件，不必重新建立。因此，它很適合分階段、分輪次的平行運算。

底層實作：一個走 AQS，一個走鎖加條件

兩者表面上都在處理「等待」，底層卻是兩套不同的機制。理解這個差異，能幫助你在面試或實作時說清楚：它們不是只有名稱不同，而是等待模型本身就不同。

CountDownLatch 直接建立在 AQS 的共享模式上。它的計數器就是 AQS 裡的 state：

  • countDown() 相當於釋放共享資源，讓 state 減一。
  • await() 相當於嘗試取得共享資源。只要 state 還不為零，執行緒就會進入 AQS 佇列等待。
  • 當 state 歸零時，等待中的執行緒會被喚醒並放行。

這條路徑不需要另外加一把鎖來保護計數器，因為 AQS 已經透過原子操作與佇列機制處理了狀態變更與執行緒等待。

CyclicBarrier 則比較像一個高階封裝。它內部使用一把 ReentrantLock 搭配一個 Condition。它的計數不是 AQS 的 state，而是由這把鎖保護的普通變數。

執行緒抵達集合點後，會在持有鎖的情況下呼叫 await()，本質上是進入 Condition.await() 的條件佇列等待。最後抵達的執行緒會負責執行 signalAll()，喚醒其他等待者，並把計數重置。

為了區分不同輪次，CyclicBarrier 還會維護一個「代」的標記。這能避免上一輪被喚醒的執行緒，把自己誤判成下一輪的參與者。

面向CountDownLatchCyclicBarrier
等待關係一個（或多個）執行緒等其他人所有執行緒互相等
底層實作AQS 共享模式，計數即 stateReentrantLock 加 Condition
可否重用一次性，歸零即報廢可循環，自動重置
典型場景主線程聚合多個下游結果多執行緒分階段同步

選用時，先問兩個問題

第一個問題是：是不是有一方要等其他人交差？如果是，使用 CountDownLatch。例如主線程等多個下游任務完成，或測試程式等待多個初始化工作結束。

如果是大家都要一起通過某個時間點，就使用 CyclicBarrier。例如多條執行緒都完成第一階段後，必須同時進入第二階段。

第二個問題是：這個等待會不會重複發生？如果流程需要多輪同步，CyclicBarrier 通常更直接，因為它會自動重置。如果每一輪的參與者不同，或每一輪都需要更靈活的控制，則可以建立幾個獨立的 Latch，組合出更符合流程的等待方式。

實務陷阱：Barrier 可能進入破損狀態

CyclicBarrier 的 await() 會拋出 BrokenBarrierException。當某條執行緒在等待時被中斷或超時，這個 Barrier 就可能進入破損狀態；其他還在等待的執行緒，也會收到相同的例外。

這個設計是為了避免其他執行緒永遠卡住。既然其中一個參與者已經不可能正常抵達，繼續等待也沒有意義。因此，使用 CyclicBarrier 時，不能只處理「正常到齊」的路徑，也要把中斷、超時與例外處理完整。

小結

CountDownLatch 是「一個等多」，計數器就是 AQS 的 state；每次呼叫 countDown() 都讓它減一，歸零後放行，而且用過一次就不能重用，適合主線程聚合多個子任務。CyclicBarrier 是「多個互等」，底層是 ReentrantLock 加 Condition；計數器由鎖保護，障礙打破後會自動重置，適合多輪次、分階段的同步。兩者都有「計數歸零後放行」的動作，但等待的主體、底層結構與能否重用，都不相同。
