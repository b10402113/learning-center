垃圾怎麼收？三種演算法、分代收集與 STW

Step 2/4 · GC、記憶體壓力與線上排查

前言：知道誰是垃圾，接著要怎麼清？

上一節我們解決了「哪些物件可以丟」。但在 JVM 裡，判斷垃圾只是第一步；真正把它們清掉時，還得面對另一個問題：怎麼清，才不會讓記憶體變得坑坑洞洞，或讓服務停頓太久？

假設記憶體裡還剩下不少空間，卻被切成東一塊、西一塊的碎片。這時候即使總空間足夠，也可能找不到一段連續區域來放入大物件，最後只好再次觸發 GC。這就像倉庫裡明明還有很多空位，卻全都散落在貨架縫隙中，放不下一件完整的大貨物。

這一節會比較三種基礎垃圾收集演算法，接著看 JVM 為什麼採用分代收集，最後拆解後端工程師很在意的 STW。它代表服務暫時停下來，讓 GC 有機會安全地整理記憶體，也是各種收集器持續想縮短的停頓來源。

學習目標

學完這一節，你應該能比較標記-清除、標記-複製、標記-整理三種演算法的取捨，說明分代收集為什麼讓新生代使用複製、老年代使用清除或整理，也能解釋 STW 為什麼無法完全消除。

三種基礎演算法：其實是在交換時間與空間

標記-清除：簡單，但容易留下碎片

標記-清除的流程很直接：先把垃圾標記出來，再把它們清掉；仍然存活的物件則留在原本的位置，不需要搬動。

它的優點是做法簡單，也不必為了整理記憶體而搬移存活物件。不過，清除之後會留下許多不連續的空白區域。你可以把它想成一張被剪得千瘡百孔的紙：空白面積其實不少，但每一塊都太零碎，想畫一張大圖時，卻找不到完整的位置。

對 JVM 來說，這就是記憶體碎片。明明還有可用記憶體，卻塞不下一個需要連續空間的大物件，最後可能被迫提前再次觸發 GC。

標記-複製：用額外空間換取連續記憶體

標記-複製是為了解決碎片問題而來。它會把記憶體切成兩半，平常只使用其中一半。這一半快滿時，就把仍然存活的物件全部搬到另一半，接著把原本使用中的那一半整塊清空。

因為存活物件是集中搬到另一側的，新的記憶體空間自然會保持連續。之後配置物件時，只要把指標往後移動即可，速度很快，也不容易產生碎片。

代價是需要準備額外空間。看起來就像花兩份錢，卻只有一半面積能在同一時間使用。不過，JVM 觀察到新生代的物件大多「朝生夕死」：它們通常活不過一次 GC。既然每次真正需要搬移的存活物件很少，就不必把空間嚴格切成一半。

HotSpot 會把新生代分成 Eden 與兩塊 Survivor，比例是 Eden 比 Survivor 等於 8 比 1。這樣的設計只需要犧牲約 10% 的空間，就能保留複製演算法的優點。

標記-整理：適合存活率高的老年代

老年代的物件通常活得比較久，存活率也比較高。如果還使用標記-複製，就代表每次 GC 都要搬動大量物件，而且還需要額外的空間當作備份區，成本太高。

標記-整理的做法是：先標記垃圾，但不急著直接清除；接著把所有存活物件往記憶體的一端推，讓它們集中排列，再把邊界以外的區域一次清掉。

這樣做可以同時避免碎片，並充分利用記憶體空間。不過，整理的過程需要搬動物件。搬動期間，使用者執行緒必須暫停，因此整體開銷會比較大。

分代收集：讓不同年齡的物件，用不同方式處理

真實的 JVM 不會只押寶在單一演算法上，而是根據物件的年齡與存活特性，把堆分成不同區域，再分別採用適合的收集方式。這就是分代收集，也是商業虛擬機長期採用的主流策略。

區域物件特性使用的演算法原因
新生代朝生夕死，存活率低標記-複製要複製的存活物件少，成本低
老年代存活久，沒有額外空間擔保標記-清除（CMS）或標記-整理（Parallel Old、G1）存活物件多，不適合整塊複製

這個分工可以用一句話理解：大部分物件很快就會死亡，所以新生代用複製演算法快速清理；少數撐過多次 GC 的物件，才會晉升到老年代，再用標記-清除或標記-整理處理。

這樣做的好處，是不必用同一把工具處理所有物件。拿小掃把清理新生代的短命物件，拿更適合整理大型區域的方式處理老年代，整體成本才比較合理。

STW：為什麼 GC 總要讓程式停一下？

不管是標記存活物件，還是複製存活物件，只要 GC 正在判斷「哪些物件還活著」，使用者執行緒就不能毫無限制地繼續修改記憶體。這段讓應用程式暫停的狀態，就叫做 Stop The World，簡稱 STW。

可以把 GC 想成在人來人往的廣場上打掃。如果清潔工一邊掃，行人一邊丟垃圾，甚至把已經掃到旁邊的東西又拿回來，那麼清潔工很難知道哪些東西真的已經清乾淨。更糟的是，他可能把人家正在使用的物品誤當成垃圾丟掉。

放到程式裡，就是 GC 可能把仍然存活的物件誤判成垃圾並回收。之後程式一旦存取那個物件，就可能發生錯誤，甚至因為空指標而崩潰。因此，在進行可達性分析時，尤其是根節點枚舉與最終標記等關鍵階段，必須先讓程式暫停，取得一個穩定的狀態，再完成掃描。

所有收集器都有 STW，只是停法不同

即使是標榜低延遲的 CMS 或 G1，也無法完全避開 STW。它們能做的是把工作切成更多階段，讓大部分耗時工作與應用程式並行，並把真正需要暫停的部分縮短，或分散到較短的停頓中。

真正棘手的是 Full GC。它通常需要掃描整個堆，停頓時間可能比一般 GC 長得多，嚴重時會讓服務幾十秒，甚至幾分鐘無法正常回應。

因此，線上排查 GC 問題時，第一步通常是先分清楚：到底是 Young GC 太頻繁，還是 Full GC 太頻繁。兩者的成因、影響與後續排查方向都不一樣，不能混在一起處理。

GC 調優：吞吐量與響應時間的取捨

JVM 調優的核心目標之一，是縮短 STW 停頓。不過，這不是單純把停頓時間降到越低越好，因為你通常得在吞吐量與響應時間之間做選擇。

如果優先考慮吞吐量，策略可能是寧願每次停久一點、少停幾次，讓更多 CPU 時間留給真正的運算工作。這類取向比較適合後台運算。

如果優先考慮響應時間，策略則可能是允許多停幾次，但每次停頓都要非常短，讓使用者幾乎感覺不到卡頓。這類取向比較適合 Web 應用。

兩種方向沒有絕對的好壞，重點在於這台機器服務的是誰，以及你的系統更在意整體處理量，還是單次請求的反應速度。

小結

三種演算法各有取捨：標記-清除做法簡單，但會產生碎片；標記-複製沒有碎片，但需要額外空間；標記-整理同樣能避免碎片，也比較省空間，卻必須搬動物件，開銷較大。分代收集把新生代的複製，與老年代的清除或整理接在一起使用。無論採用哪一種方式，GC 在分析存活物件時都需要某種程度的 STW。收集器一路演進，核心就是持續縮短這段停頓時間。
