物件什麼時候會變成垃圾？從可達性分析到四種引用

Step 1/4 · GC、記憶體壓力與線上排查

學習目標

這一節要帶你弄清楚三件事：JVM 為什麼採用可達性分析，而不是引用計數；哪些物件可以成為 GC Roots；以及四種引用強度，如何影響一個物件「什麼時候才會被回收」。

前言：記憶體一直漲，重啟就好嗎？

你可能遇過這種服務：剛上線時一切正常，記憶體卻慢慢往上爬。撐了三、五天之後，服務開始變慢甚至卡住；重啟一下，記憶體又恢復正常，但過幾天相同的問題再次出現。當同事問「到底是哪裡漏了」，你盯著程式碼，卻很難立刻說出答案。

要找出記憶體問題，得先從一個更基本的問題開始：JVM 到底怎麼判斷一個物件「已經沒人用了，可以丟掉」？如果連物件生死的規則都不清楚，就很難解釋它為什麼沒有被回收。

這一節會把這條規則拆開來看。JVM 的判斷不是「沒有人直接指向我，就把我丟掉」，而是「從幾個固定的根出發，如果一路走不到我，我才可能被回收」。

先看一個行不通的做法：引用計數

最直覺的想法，是替每個物件放一個計數器。有人引用這個物件，計數器就加一；引用斷開，計數器就減一。當計數器變成零，就代表沒有任何地方使用它，可以回收。

這種方法叫做引用計數法。它的邏輯很簡單，問題卻出在一個始終無法解決的死角：循環引用。

假設物件 A 持有物件 B，而物件 B 又持有物件 A。除此之外，外界已經沒有任何地方引用它們。A 和 B 明明都已經沒有用了，卻因為彼此互相指著對方，兩個計數器都會維持在 1，永遠不會歸零。

結果就是：這兩個物件其實是垃圾，卻一直無法被回收，記憶體也因此被占住。正因為引用計數法有這個根本上的缺陷，HotSpot 這類工業級 JVM 並不採用它作為主要的垃圾判斷方式。

JVM 真正使用的方法：可達性分析

JVM 採用的是可達性分析。你可以把記憶體裡的所有物件想成一張大型關係圖，物件之間的引用就是圖上的連線。

接著，JVM 會選定幾個固定的起點，這些起點稱為 GC Roots。垃圾回收器會從 GC Roots 出發，沿著物件之間的引用一路往下走：

  • 從 GC Roots 走得到的物件，代表仍然可達，會被視為存活。
  • 從任何 GC Roots 都走不到的物件，代表已經不可達，便可能被回收。

這有點像查看一張地鐵路線圖：只要能從家門口出發，沿著路線抵達某個車站，那個車站就還在可達範圍內；完全接不上任何路線的車站，就像被整張網路遺落的物件。

因此，關鍵不是「有沒有其他物件指向我」，而是「從 GC Roots 出發，能不能走到我」。回頭看前面的 A 和 B，即使它們彼此互相引用，只要從任何 GC Root 都走不到它們，兩者仍然會被判定為垃圾。

哪些物件可以當作 GC Roots？

這是面試很常追問的細節。常見的 GC Roots 主要有四類：

  1. 虛擬機棧中，區域變數所引用的物件。虛擬機棧是方法執行時使用的記憶體。例如方法裡寫了 User u = new User();，只要這個方法還沒有結束，u 就可以視為一個根；它所指向的 User 物件也就仍然可達。
  2. 方法區中，靜態屬性（static）所引用的物件。例如 public static User user;，只要這個類別仍然被載入，這個 user 引用就可能成為根。
  3. 方法區中，常數（final）所引用的物件，例如字串常量池裡保存的引用。
  4. 本地方法棧中，JNI，也就是 Java 呼叫 C/C++ 原生方法時所引用的物件。

記住這四類之後，你就多了一個判斷記憶體問題的方向：到底是哪個 GC Root 還牽著這個物件？排查記憶體洩漏時，MAT 工具裡的 Path to GC Roots，做的正是沿著引用關係反向追蹤，找出「是誰還沒有放手」。

四種引用強度：決定物件什麼時候才會被回收

可達性分析回答的是「這個物件還能不能從 GC Roots 走到」。但即使物件看起來還活著，GC 對不同類型的引用，處理態度也不完全一樣。

Java 提供了四種引用強度，讓程式可以表達物件的重要程度。它們最核心的差異，可以記成一句話：GC 到底要等到什麼情況，才願意回收它？

引用寫法GC 的態度典型用途
強引用Object o = new Object()通常不會主動回收；記憶體不足時，寧願拋出 OutOfMemoryError日常最普通的物件引用
軟引用SoftReference記憶體充足時保留，記憶體快不足時才回收對記憶體敏感的本地快取，例如圖片快取
弱引用WeakReference只要發生 GC，不論當下記憶體是否充足，都會回收ThreadLocal 的 key、WeakHashMap
虛引用PhantomReference無法取回物件本身，只在物件即將被回收時發出通知管理堆外記憶體的釋放

強引用就是平常最常寫的引用。只要它仍然指向某個物件，GC 就不會輕易動它；即使記憶體快要撐爆，也可能先讓程式拋出 OutOfMemoryError。

軟引用代表「這個物件有用，但不是非留不可」。它很適合用在快取上：記憶體足夠時就先保留，讓後續可以快速重用；記憶體開始吃緊時，GC 再回收它，把空間讓給更重要的物件。這樣可以避免快取反過來把整個系統撐死。

弱引用比軟引用更短命。只要 GC 開始執行，不管當下還有沒有足夠的記憶體，弱引用所綁定的物件都可能被回收。常見例子包括 ThreadLocal 裡的 key，以及 WeakHashMap。

當某個 key 不再被外部的強引用持有時，WeakHashMap 對應的鍵值對就能被自動清理，避免一堆不再使用的資料一直留在記憶體裡。

虛引用是最弱的一種引用。你無法透過 get() 取回原本的物件，呼叫後永遠會得到 null。它的用途不是讓你繼續使用物件，而是搭配引用隊列，在物件被回收時收到通知，通常用來協助處理堆外記憶體的清理。

小結

JVM 判斷物件是否可回收，靠的是可達性分析，而不是引用計數，因為引用計數無法處理循環引用。可達性分析會從四類 GC Roots 出發：能走得到的物件仍然存活，完全走不到的物件才可能被回收。至於物件什麼時候會被放手，則取決於引用強度：強引用很難放手，軟引用在記憶體不足時才放，弱引用遇到 GC 就放，虛引用則只負責通知回收事件。
