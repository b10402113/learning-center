收集器怎麼選？從 Serial、Parallel 到 CMS 與 G1

Step 3/4 · GC、記憶體壓力與線上排查

學習目標

學完這一節，你應該能從「吞吐量」與「延遲」兩個角度，分辨 Serial、Parallel、CMS、G1 的適用場景；也能說明 G1 相對 CMS 的三個優勢，並用三色標記與寫屏障解釋：GC 和使用者執行緒同時執行時，為什麼不會把還活著的物件誤刪。

前言：面試官問你「線上用哪個收集器？」

前面兩節談的是 GC 原理，但真正在線上環境工作的，是一個個具體的收集器。當面試官問「你們線上用哪個收集器？為什麼這樣選？」他通常不是要你把名詞背一遍，而是想確認你有沒有想清楚兩件事：系統比較在意吞吐量，還是比較在意延遲？

這個選擇很像在安排工廠的生產線。你可以讓所有機器暫停一下，集中火力一次清得很乾淨；也可以讓清潔人員和生產線一起工作，盡量縮短停工時間，只是管理方式會更複雜。

這一節會先把四個主要收集器放在同一條演進線上比較，再拆開 G1 與 CMS 的差異。最後，我們會處理一個很容易只背結論、卻說不出原因的底層問題：GC 一邊標記，使用者執行緒一邊修改引用時，為什麼不會把活著的物件誤判成垃圾？答案就在三色標記與寫屏障。

四個收集器，按目標分成三條路線

Serial：單執行緒的基本款

Serial 的典型搭配，是新生代的 Serial 加上老年代的 Serial Old。

它的做法很直接：GC 執行緒單獨工作，回收期間則暫停所有使用者執行緒，等 GC 完成後再繼續執行。這就是典型的 STW（Stop-The-World）。

這種方式簡單，但停頓時間可能比較明顯，因此現在的伺服器端幾乎不會優先選它。它比較常出現在記憶體很小的客戶端應用中，因為這類環境的 CPU 與記憶體資源有限，簡單有時反而是優點。

Parallel：吞吐量優先

Parallel 的代表組合是 Parallel Scavenge 加上 Parallel Old，也是 JDK 8 的預設收集器。

它使用多個執行緒並行回收，核心目標是提高吞吐量。換句話說，就是盡量降低 GC 佔用的總時間，讓 CPU 把更多時間花在真正的業務計算上。

它的取捨很清楚：寧可單次停頓久一點，也要讓整體 CPU 使用率與工作完成量更高。因此，Parallel 適合後台運算、批次處理、報表產生等對即時互動要求不高的場景。

CMS：響應時間優先

CMS 的典型搭配是 ParNew 加上 CMS。

它最大的改變，是讓 GC 執行緒與使用者執行緒在部分階段同時執行。這就像清潔人員不再等工廠完全停工才進場，而是趁生產線運轉時分區清理，因此可以大幅縮短 STW 停頓，適合 Web 伺服器這種對響應速度敏感的應用。

但 CMS 也有明顯代價。它採用標記-清除，清掉垃圾後不會搬移存活物件，因此容易留下記憶體碎片。它也比較依賴 CPU 資源，當應用程式本身已經很忙時，GC 和使用者執行緒可能互相搶資源。

CMS 已經在 JDK 14 被移除，不過許多仍在運作的老系統，依然可能使用它。

G1：以停頓目標為中心

G1 唸作 Garbage First，不是「G 一」。它把整個堆切成數千個大小相同的小區塊，每個區塊稱為一個 Region。

過去的收集器通常把堆分成新生代與老年代，而且這些區域在物理上有較固定的配置。G1 改成用 Region 管理堆，讓新生代與老年代不必再被固定綁在某些連續記憶體區域上。

每次回收時，G1 會估算不同 Region 的回收收益，優先挑選垃圾最多、最值得清理的區域。這就是 Garbage First 名稱的由來：先處理「垃圾最多」的地方。

你也可以透過使用者設定的目標，例如「停頓時間不要超過 200 毫秒」，讓 G1 根據目標安排一次要回收多少個 Region。G1 是 JDK 9 之後的預設收集器，適合 6G 以上的大記憶體、多核心伺服器端應用。

G1 相比 CMS 強在哪裡？

G1 的出現，主要就是要處理 CMS 在大記憶體場景下留下的問題。兩者的差異，可以從三個面向理解。

第一，G1 能整理碎片

CMS 使用標記-清除。它只清掉垃圾，不搬移存活物件，所以回收後的記憶體可能變得坑坑洞洞，就像蜂窩煤一樣。

這會造成一個很麻煩的情況：整個堆的剩餘空間明明足夠，卻找不到一段連續空間來配置大物件。此時系統可能被迫觸發 Full GC，帶來長時間停頓。

G1 則是從整體來看採用標記-整理；從局部的 Region 來看，則是把存活物件從原本的 Region 搬到另一個空的 Region。搬移的同時，也順手完成整理，因此不容易累積記憶體碎片，Full GC 的觸發機率也能大幅降低。

第二，G1 能設定可預測的停頓目標

CMS 的目標是「盡可能快」，但它無法保證每次究竟會停多久。實際停頓時間會受到垃圾量、堆大小等因素影響。

G1 則提供 -XX:MaxGCPauseMillis，讓使用者指定期望的停頓時間。G1 會根據這個目標，挑選回收收益較高的 Region，並控制每次回收的工作量。

這不是保證每次都一定不超過設定值，而是提供一個可供收集器調度工作的目標。相比之下，CMS 沒有這種以停頓目標為核心的回收模型。

第三，G1 的記憶體配置更有彈性

G1 以 Region 管理堆，把整體記憶體切成許多小區塊。每次只回收其中一部分，而不是總要掃描或處理整個堆。

這種「化整為零」的方式，讓 G1 更容易支撐大堆，也能根據當下的停頓目標，彈性決定這一輪要處理哪些區域。

為什麼併發標記不會誤殺物件：三色標記

CMS 和 G1 都允許使用者執行緒與 GC 執行緒同時執行。問題也隨之而來：GC 正在標記物件時，使用者執行緒可能同時修改物件之間的引用關係。那麼，GC 會不會因此把還活著的物件當成垃圾？

為了描述每個物件被掃描到哪個階段，JVM 使用三種顏色。

顏色狀態說明
白色還沒被訪問過分析結束時仍是白色，代表不可達，是垃圾
灰色已經訪問過，但子引用還沒掃完代表目前正在處理中的中間狀態
黑色自己和子引用都已經掃完代表已確認存活，是安全的物件

整個流程可以想成一場從 GC Roots 出發的尋寶遊戲。

一開始，所有物件都是白色。GC 先把 GC Roots 直接引用的物件塗成灰色，表示「我已經找到你，但還沒檢查完你認識的所有物件」。接著，GC 從灰色集合中取出一個物件，將它引用的子物件塗成灰色，再把自己塗成黑色。

這個動作會持續進行，直到灰色集合清空。最後仍然是白色的物件，就代表從 GC Roots 出發找不到它，因此會被視為垃圾。

併發標記的風險：對象消失問題

真正棘手的地方，發生在 GC 與使用者執行緒同時修改引用時。

假設 GC 已經把某個物件塗成黑色，表示它認為這個物件以及它的子引用都掃描完了。此時，使用者執行緒做了兩件事：

  • 讓這個黑色物件新增一條指向白色物件的引用。
  • 同時，原本某個灰色物件指向這個白色物件的引用被切斷。

這兩個條件同時成立時，白色物件就可能從 GC 的搜尋路徑中消失。

黑色物件已經被判定為掃描完成，GC 不會再回頭檢查它新增的引用；灰色物件原本通往白色物件的路徑又被切斷了，GC 也無法再從那裡找到它。結果，這個其實仍然存活的白色物件可能被漏標，最後被當成垃圾回收。程式之後一旦存取它，就可能發生錯誤，甚至直接崩潰。

兩種寫屏障解法

為了避免上述情況，JVM 會在修改引用的賦值動作上加入攔截機制，這就是寫屏障。

寫屏障像是引用關係上的門衛：每當程式要建立或刪除一條引用時，門衛會先留下記錄，提醒 GC「這裡的關係剛剛發生變化，不能完全照原本的標記結果看待」。主流做法主要有兩種。

CMS：增量更新

CMS 使用增量更新，針對的是「黑色物件新增指向白色物件」這個條件。

只要黑色物件插入了一條指向白色物件的新引用，寫屏障就會把這個黑色物件重新標記為灰色，讓 GC 之後再重新掃描它。這樣一來，新建立的引用就不會被忽略。

可以用一句話記住它：黑色物件只要新交了朋友，就要被拉回來重新審查。

G1：原始快照 SATB

G1 使用原始快照，簡稱 SATB（Snapshot-At-The-Beginning）。它處理的是另一個條件：灰色物件原本指向白色物件的引用被切斷。

當這條引用即將被刪除時，寫屏障會先把原本指向的白色物件記錄下來。之後不管程式怎麼修改引用，GC 都會把「標記開始那一刻」的關係當成一份快照來看待。原本斷掉的路徑，在這份快照裡仍然被視為存在。

這種做法可能讓少數原本已經可以回收的物件多存活一段時間，但它能避免活著的物件被漏標，整體效率也比較高。

小結

選收集器，本質上是在吞吐量與延遲之間做取捨：Parallel 以吞吐量為優先，CMS 以較低的響應延遲為目標，G1 則透過 Region 化管理，在大記憶體場景下同時改善記憶體碎片與停頓可預測性。這也是 G1 相對 CMS 的三個關鍵優勢：能整理碎片、能設定停頓目標，以及記憶體配置更有彈性。併發標記之所以能安全運作，則依靠三色標記搭配寫屏障：CMS 用增量更新把相關的黑色物件拉回灰色，G1 用原始快照記錄被刪除的引用，避免仍然存活的物件被漏標。

到這裡，你已經掌握收集器的選擇邏輯，也知道併發標記背後如何避免誤刪物件。下一節會把這些概念帶進線上排查：當監控跳出「GC 頻繁」的告警時，如何從一個 PID 開始，一步步找到真正造成問題的物件。
