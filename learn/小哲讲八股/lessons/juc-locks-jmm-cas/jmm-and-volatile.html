JMM 與 volatile：看懂可見性、有序性與原子性

Step 3/5 · 鎖、JMM 與無鎖原子

前言：明明改了值，另一條執行緒卻看不到

有一種併發 bug 特別折磨人：主執行緒把停止開關設成 true，另一條正在忙等的執行緒卻像完全沒收到訊號，迴圈一直跑個不停。程式邏輯看起來沒有問題，也沒有明顯的鎖衝突；換個 JDK 版本或換台機器，結果甚至可能又不一樣。

另一個常見情境是計數器。你讓多條執行緒用 i++ 加了幾百萬次，最後的數字卻少了一截。這時直覺可能會說：「把 i 宣告成 volatile 不就好了嗎？」但答案通常是否定的。

要理解這些現象，得先接受一個反直覺的前提：Java 程式碼寫下的順序，和機器實際執行的順序，不一定完全相同。編譯器、CPU 快取與指令重排都可能影響結果。Java 用一套規則把這些硬體細節抽象起來，這套規則就是 Java 記憶體模型（JMM）。

學習目標

看完這一課，你應該能用主記憶體與工作記憶體解釋原子性、可見性、有序性這三個併發問題，也能說明為什麼 volatile 保證可見性與有序性，卻不保證原子性。

JMM：替硬體細節劃出一條規則

真實的電腦裡有多層快取，CPU 會亂序執行，編譯器也會為了效能重新安排指令。如果 Java 直接把這些硬體差異交給開發者處理，同一段程式可能換台機器就有不同結果，也很難跨平台執行。

JMM（Java Memory Model）的作用，就是建立一層抽象規則。它不要求你直接處理每個 CPU 快取或硬體細節，而是告訴你：在什麼情況下，一條執行緒的修改一定能被另一條執行緒看見，以及哪些操作能限制指令順序。

先用一個簡化模型來看，JMM 有兩個重要區域：

  • 主記憶體：所有共享變數都存放在這裡。
  • 工作記憶體：每條執行緒各自擁有一份，用來存放它正在使用的變數副本。它可以視為 CPU 快取的抽象。

執行緒讀取或修改變數時，通常是在自己的工作記憶體上操作，而不是直接碰主記憶體。執行緒之間要交換資料，也必須透過主記憶體。

因此，一條執行緒改到的可能只是自己的副本。這個修改什麼時候同步回主記憶體，其他執行緒什麼時候能取得最新值，都需要額外的同步規則。原子性、可見性與有序性這三個問題，就是從這裡產生的。

併發三大問題：到底是哪裡出錯？

Java 併發程式設計中的許多技巧，最後都在處理下面三件事。先分清楚問題的來源，才不會拿錯工具。

問題描述常見解法
原子性一組操作被執行緒切換打斷，沒有完整執行synchronized、Lock、Atomic 類
可見性一條執行緒修改了值，其他執行緒卻看不到最新結果volatile、synchronized、Lock
有序性編譯器或 CPU 重排指令，實際順序與程式碼順序不同volatile（記憶體屏障）、synchronized

原子性：看似一行，其實是三個步驟

原子性可以想成「一組操作要嘛全部完成，要嘛完全不做，中間不能被切開」。它主要受到執行緒切換影響。

例如 i++ 看起來只有一行，底層其實包含三個步驟：

  1. 讀出 i 的值。
  2. 計算 i + 1。
  3. 把結果寫回 i。

假設執行緒 A 讀到 i，還沒寫回結果，CPU 就切換到執行緒 B。B 也讀到相同的舊值，計算後寫回；接著 A 恢復執行，也把自己的結果寫回。兩條執行緒各自加了一次，最後卻可能只增加一次。

這就是原子性被打破。要解決它，可以用 synchronized 或 Lock 把三個步驟包成不可分割的整體，也可以使用 AtomicInteger 這類基於 CAS 的輕量方案。

可見性：修改可能只停在自己的快取裡

可見性指的是：一條執行緒修改共享變數後，其他執行緒能取得最新值。

問題的來源可以用 CPU 快取來理解。為了提高速度，每個 CPU 核心都可能保留自己的快取。執行緒修改變數時，修改可能先停留在這個快取中，尚未同步回主記憶體；另一條執行緒讀到的，於是仍然是舊值。

前言中的停止開關就是這種問題：主執行緒已經寫入 true，工作執行緒卻可能持續讀到快取中的 false。

常見解法是 volatile。它會要求 JVM 在相關讀寫上建立可見性保證，讓一條執行緒的修改能被其他執行緒看見。synchronized 與 Lock 也能保證可見性，因為它們在解鎖前會處理共享資料的同步。

有序性：程式碼順序不一定是執行順序

有序性指的是：多執行緒觀察到的執行結果，不能因為指令重排而違反程式設計需要的順序。

編譯器與 CPU 會在不影響單執行緒結果的前提下，重新安排指令，藉此提升效能。單執行緒通常感覺不到差異，但多執行緒會互相觀察對方的狀態，原本不明顯的順序變化就可能造成錯誤。

最經典的例子是單例模式的雙重檢查鎖：物件可能還沒完成初始化，參考就先被另一條執行緒取得。這時對方拿到的不是完整物件，而是半初始化的狀態。

volatile 會透過記憶體屏障限制特定類型的指令重排；synchronized 則把臨界區變成串行執行，也能提供相應的有序性保證。

volatile：輕量，但不是萬能的同步工具

volatile 可以視為 Java 裡一種較輕量的同步機制。它不會像鎖一樣把其他執行緒擋在外面，而是針對這個變數的讀寫提供兩項主要保證：

  • 保證可見性。
  • 保證有序性。

但它不保證原子性。這三句話要一起記，少記任何一句，都可能在實戰中誤用 volatile。

保證可見性

當一條執行緒寫入 volatile 變數時，JVM 會建立相應的記憶體可見性保證，讓這個修改能同步出去；其他執行緒讀取時，也會取得最新值，而不是一直使用自己快取裡的舊副本。

拿停止開關來看，下面的寫法可以讓工作執行緒看見主執行緒的修改：

class Worker extends Thread {
    volatile boolean flag = false;   // 拿掉 volatile，迴圈可能永遠不結束

    public void run() {
        while (!flag) {
            // 忙等
        }
        System.out.println("看到 flag，結束迴圈");
    }
}

沒有 volatile 時，工作執行緒可能一直讀到自己快取裡的舊 flag，因此持續看見 false。加上之後，主執行緒修改旗標，工作執行緒就能取得這個更新。

保證有序性

volatile 的第二項保證，是限制指令重排序。它會在讀寫操作前後建立記憶體屏障（memory barrier）。

對寫操作來說，屏障會限制相關寫入被移到不該出現的位置；對讀操作來說，屏障會限制後續讀取被提前。這些限制讓其他執行緒觀察到的操作順序，符合必要的同步規則。

這也是下一節解釋「雙重檢查鎖為什麼要加 volatile」的關鍵：它不只是讓參考變數的更新可見，也要避免物件初始化相關的指令被錯誤重排。

不保證原子性

既然 volatile 能讓每次讀取都取得最新值，那兩條執行緒一起對 volatile int i 做 i++，是不是就安全了？答案仍然是不安全。

i++ 還是由讀取、計算、寫回三步組成。假設執行緒 A 讀到 i = 5，正準備計算 6；此時 CPU 切換到執行緒 B。B 也讀到 5，算完後寫回 6。接著 A 恢復執行，也把 6 寫回去。兩次加一，最後只留下增加一次的結果。

volatile 保證的是每次讀寫具備可見性，卻沒有把「讀、算、寫」這三個步驟包成不可分割的整體。因此，需要原子性時，仍然要使用鎖或 AtomicInteger。

小結

JMM 用主記憶體與工作記憶體描述執行緒如何共用變數，並帶出原子性、可見性、有序性三個問題：原子性源自執行緒切換，靠鎖或 Atomic 類解決；可見性源自 CPU 快取，靠 volatile 或鎖解決；有序性源自指令重排序，靠 volatile 的記憶體屏障或鎖解決。volatile 保證可見性與有序性，但因無法包住複合操作，所以不保證原子性。

「透過記憶體屏障保證有序性」這件事，最有代表性的實戰案例就是單例的雙重檢查鎖。下一節會先把 happens-before 這套規則講清楚，再用它解釋 DCL 為什麼不加 volatile 可能拿到半初始化的物件。
