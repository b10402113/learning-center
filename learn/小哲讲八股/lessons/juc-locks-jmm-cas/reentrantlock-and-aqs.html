ReentrantLock 與 AQS：state、CLH 佇列與 CAS

Step 2/5 · 鎖、JMM 與無鎖原子

學習目標

這一課會比較 synchronized 與 ReentrantLock 的差異，並釐清它們各自適合的場景。你也會看懂 AQS 如何透過 volatile state、CLH 變體佇列與 CAS，管理共享資源和等待中的執行緒。

前言：鎖不夠用的時候

想像一下，服務啟動時有一條執行緒正在等待一把鎖。這時使用者按下取消，但如果它使用的是 synchronized，這條執行緒通常只能繼續等，無法在等待期間回應中斷。

另一個常見場景是生產者與消費者共用一個緩衝區。當緩衝區出現新資料時，你只想喚醒消費者，不想把生產者也一起叫醒。可是，synchronized 搭配 wait/notify 只有一個等待集合，沒辦法精準區分要喚醒哪一群執行緒。

這些需求不是少見的例外，因此 JDK 提供了 ReentrantLock。不過，ReentrantLock 更重要的價值，還在於它是 java.util.concurrent 同步器家族共同地基 AQS 的第一個具體入口。看懂它如何使用 AQS，之後再遇到 CountDownLatch 或 Semaphore，就不必把每個工具當成獨立知識硬背。

一個是關鍵字，一個是 API 類別

兩者最根本的差異，在於它們所處的層級不同。synchronized 是 Java 關鍵字，由 JVM 直接支援，底層使用上一節提到的 Monitor。加鎖與解鎖都是隱式進行：你寫好同步區塊，剩下的工作交給 JVM 處理。即使區塊中途拋出例外，JVM 也會保證鎖被釋放。

ReentrantLock 則是 JDK 提供的類別，建立在 AQS 之上。加鎖與解鎖都是顯式操作：你必須自行呼叫 lock()，也必須在最後呼叫 unlock()。這份自由帶來更多功能，但同時也把正確釋放鎖的責任交給了開發者。

ReentrantLock lock = new ReentrantLock();
lock.lock();
try {
    // 臨界區
} finally {
    lock.unlock();   // 一定要放在 finally，否則鎖可能永遠不釋放
}

這段 try-finally 不是可有可無的程式風格，而是標準且必要的寫法。假設臨界區中途拋出例外，而 unlock() 沒有放在 finally 裡，執行緒就可能永遠不釋放鎖，其他執行緒也會跟著卡住。

這正是 synchronized 常被認為「比較安全」的原因：釋放鎖的工作由 JVM 負責，而不是要求開發者自己記得處理。

ReentrantLock 多出來的三項能力

既然 synchronized 使用簡單，還能由 JVM 自動釋放鎖，為什麼仍然需要 ReentrantLock？因為在某些實際場景裡，光是「能加鎖」還不夠。ReentrantLock 多出的三項能力，剛好對應了三種常見痛點。

等待可以被中斷

synchronized 一旦開始等待鎖，通常就只能繼續等，無法在等待期間取消。ReentrantLock 提供 lockInterruptibly()，讓正在等待鎖的執行緒可以回應中斷，選擇放棄等待。

這對「等不到就取消」的流程很重要。例如某個操作有逾時限制，執行緒不應該因為一直拿不到鎖，就無限期卡在那裡。可中斷的等待能讓系統及時收回這條執行緒，而不是讓它慢慢累積成新的壓力。

支援公平鎖

synchronized 只能使用非公平鎖，也就是不保證先來先得。哪條執行緒先搶到，哪條就先取得鎖。

ReentrantLock 可以在建構時傳入 true，開啟公平鎖，讓執行緒大致按照排隊順序取得鎖。公平鎖在極端情況下有助於避免某些執行緒長期搶不到資源，也就是避免飢餓；但它通常會犧牲一部分吞吐量，因此只在確實需要時才值得使用。

可以綁定多個條件佇列

synchronized 搭配 wait/notify 時，只有一個等待集合。喚醒時只能選擇喚醒一條執行緒，或把所有等待中的執行緒都叫醒，無法精準指定是哪一類等待者。

ReentrantLock 則可以透過 newCondition() 建立多個 Condition，把不同用途的執行緒分開排隊。以生產者與消費者為例，緩衝區出現新資料時，可以只喚醒消費者；緩衝區有空間時，也可以只喚醒生產者，不必把另一邊的執行緒一起叫醒。

藏在這一切底下的 AQS

不論功能看起來多複雜，ReentrantLock 本質上都在處理兩個問題：目前共享資源是否被佔用？沒有搶到資源的執行緒要排在哪裡？

這兩個問題不只 ReentrantLock 需要處理，CountDownLatch 與 Semaphore 也一樣需要。因此，JDK 把共通的部分抽出來，形成 AQS（AbstractQueuedSynchronizer，抽象佇列同步器）。AQS 負責管理共享資源的狀態，以及等待中的執行緒如何排隊；不同同步器只需要定義自己的資源規則即可。

AQS 的結構可以先記成一句話：state（資源狀態）＋ CLH 變體佇列（執行緒排隊）＋ CAS（原子操作）。下面分成三部分來看。

核心資源：volatile int state

AQS 內部維護一個變數：

private volatile int state;

它代表共享資源目前的狀態，但具體意義會依照使用它的同步器而改變。

在 ReentrantLock 裡，state 為 0 代表鎖目前沒有被佔用；為 1 代表鎖已被取得；大於 1 則代表同一條執行緒重入了多次。這個角色，正好對應上一節 Monitor 中的計數器。

到了 CountDownLatch，同一個 state 會表示還剩多少次倒數；到了 Semaphore，則會表示還剩多少張許可證。這就是 AQS 抽象之處：框架負責管理狀態的讀寫與排隊，至於狀態代表什麼，交由子類別自行定義。

修改機制：CAS

多條執行緒可能同時搶同一個 state，因此修改動作必須是原子的。否則可能出現兩條執行緒同時讀到「鎖是空的」，最後都以為自己成功取得鎖的問題。

AQS 使用 CAS 指令修改 state。哪一條執行緒的 CAS 成功，真的把 state 從舊值改成新值，哪一條執行緒就取得了資源。

CAS 的細節會留到第五節再展開。這裡先記住它解決的問題：「只有當目前值等於我預期的舊值時，才幫我改成新值。」這是一個不會在中途被其他執行緒插入的硬體級原子操作。

排隊機制：CLH 變體佇列

那些 CAS 失敗、沒有搶到鎖的執行緒要去哪裡？AQS 不會讓它們一直留在原地空轉，而是會把每條執行緒包裝成一個 Node，再接到雙向鏈結串列中排隊。

這條佇列是以 CLH 鎖——一種以串列為基礎的自旋鎖——為基礎改造而來，因此通常稱為 CLH 佇列。AQS 的做法並不是讓所有執行緒同時瘋狂重試，而是讓排隊中的節點先被掛起。

等到前一個節點釋放資源並喚醒它，它才會再次使用 CAS 嘗試取得 state。整個流程可以想成：「搶不到就排隊，被前一個節點喚醒後再搶。」這比讓所有執行緒無止境空轉更有效率。

效能方面，JDK 1.6 以前，synchronized 確實常被認為比較慢。不過，後來加入偏向鎖、輕量級鎖等最佳化後，兩者在一般使用情況下已經相當接近。

因此，選擇哪一個時，重點不該只是「誰比較快」，而是先問自己：是否需要可中斷等待、公平鎖或多條件佇列？如果不需要，synchronized 往往已經足夠；如果需要這些控制能力，才考慮使用 ReentrantLock。

小結

synchronized 是 JVM 層級的隱式鎖，使用簡單，並且會自動釋放；ReentrantLock 是建立在 AQS 上的顯式鎖，換來可中斷等待、公平鎖與多條件佇列三項能力，但也要求開發者用 try-finally 正確釋放鎖。AQS 的核心則是由 volatile state 表示共享資源、由 CAS 決定誰成功取得資源，再用 CLH 變體佇列安置搶輸的執行緒。至於 state 具體代表什麼，則會隨著同步器而改變，這正是它成為 JUC 同步器共同地基的原因。

這一課處理的是「多條執行緒如何互斥」。但即使完全不共用鎖，一條執行緒修改了變數，另一條執行緒仍然可能讀到舊值。這不是鎖本身能解決的問題，而是記憶體模型層級的問題。下一節就從主記憶體與工作記憶體開始，看看這種可見性差異是怎麼發生的。
