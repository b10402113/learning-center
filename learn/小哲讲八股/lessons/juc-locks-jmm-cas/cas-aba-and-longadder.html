CAS、ABA 與 LongAdder：無鎖原子操作，如何避開熱點競爭

Step 5/5 · 鎖、JMM 與無鎖原子

學習目標

這一節會帶你看懂 CAS 的 V、A、B 邏輯與硬體基礎，理解 ABA 問題為什麼會發生，以及版本號如何解決它。接著，我們會比較 AtomicInteger 和 LongAdder，看清楚為什麼前者在高競爭下可能變慢，以及後者如何把單一熱點分散開來。

前言：不加鎖，也能安全地改值

前面幾節討論的做法，大多像是在入口處安排一位門衛：同一時間只讓一條執行緒進入，其他人先在外面等。這就是鎖的基本思路。它很可靠，但也有代價——搶不到鎖的執行緒可能被掛起，之後還要再被喚醒；當競爭不高時，這些成本或許不明顯，一旦執行緒數量增加，就可能變成效能瓶頸。

因此，還有另一種思路：不先把人擋在門外，而是讓大家直接嘗試更新資料。只要更新時確認「我剛才讀到的值還沒被別人改過」，就可以安全地寫入；如果發現值變了，就重新讀取，再試一次。這就是 CAS，也是 Java 併發套件中許多原子類別的基礎。

不過，CAS 也不是任何場景下都更快。你可能會看到一個很反直覺的現象：AtomicInteger 明明是為了高併發而設計，競爭非常激烈時，效能卻可能比單純加鎖還差，甚至讓 CPU 使用率飆高。

原因不在於 AtomicInteger 不安全，而在於所有執行緒都在搶同一個變數。這一節會先把 CAS 的運作方式講清楚，再說明 ABA 問題與版本號解法，最後看 JDK 8 的 LongAdder 如何把這個單點熱點拆開。

CAS：先假設沒有衝突，失敗再重試

CAS 的全名是 Compare And Swap，也就是「比較並交換」。它是一種樂觀鎖的做法，不像 synchronized 那樣先把其他執行緒擋住，而是假設目前不太會發生衝突，先直接嘗試更新。

CAS 有三個核心操作數：

  • V：記憶體中目前的值（Value）。
  • A：我預期的舊值（Expected）。
  • B：我想寫入的新值（New）。

它的規則可以濃縮成一句話：只有當記憶體中的實際值 V 等於預期的舊值 A，才會把 V 更新成 B。

假設執行緒先讀到值 A，準備把它改成 B。在它真正寫入之前，如果另一條執行緒已經先改過資料，記憶體中的值就不再是 A。這時 CAS 會失敗，執行緒不會直接覆寫別人的結果，而是重新讀取目前的值，再試一次。

這種「失敗就再試」的做法叫做自旋。它和等待鎖的差別在於，執行緒不會立刻掛起，而是暫時留在 CPU 上反覆嘗試。

CAS 的原子性不是 JVM 自己用 Java 程式碼拼出來的，而是依賴硬體提供的原子指令。Java 會透過 Unsafe 類別呼叫底層能力，最後在 x86 上對應到像 cmpxchg 這類 CPU 指令。

因為整個比較與更新的動作由硬體保證不可分割，所以它不需要使用作業系統的互斥量，也能避開部分執行緒切換成本。當競爭不高時，CAS 通常能有很好的效能。

ABA 問題：值回來了，不代表過程沒變

CAS 有一個著名的陷阱：它比較的是「現在的值是否等於預期值」，卻不會自動檢查中間發生過什麼事。也就是說，它只看結果，不看過程。

假設記憶體中的變數一開始是 A：

  1. 執行緒 1 讀到 A，準備把它改成 C，但在寫入前因為 CPU 調度而暫停。
  2. 執行緒 2 執行，先把 A 改成 B，再把 B 改回 A。
  3. 執行緒 1 恢復執行，拿著原本讀到的 A 去和記憶體中的值比較。
  4. 執行緒 1 發現目前仍然是 A，於是 CAS 通過，誤以為這段期間沒有人動過資料。

這個過程就是 ABA：資料從 A 變成 B，又回到 A。對 CAS 來說，起點和終點看起來一樣，但中間其實發生過變更。

如果操作的是單純數值，例如 AtomicInteger 的加減，ABA 通常不會造成實際問題，因為最後的值確實又回到原本的數字。但在鏈結串列或堆疊這類依賴節點參考的資料結構裡，情況就危險得多。

例如某個節點被移除、回收，之後又被重新使用。此時 A 和 B 可能再次指向相同的記憶體位址。執行緒 1 看到熟悉的參考後，以為節點從未被動過，便可能在錯誤的前提下更新指標，最後讓整個資料結構失效。

加上版本號，讓 CAS 看見「中間發生過什麼」

處理 ABA 的標準方法，是不要只比較資料本身，也一起比較版本號。原本的變化可能是：

A → B → A

加上版本後，就會變成：

1A → 2B → 3A

執行緒 1 一開始拿到的是 1A。即使它恢復時看到的資料仍然是 A，版本已經變成 3，因此實際值是 3A。兩者不相等，CAS 就會失敗，執行緒 1 必須重新確認目前狀態。

這個思路和資料庫樂觀鎖裡加入版本號或時間戳很像：資料內容可能回到原樣，但版本號會留下「它曾經被更新過」的痕跡。Java 的 AtomicStampedReference 就是這類解法的實作。

AtomicInteger 為什麼在高競爭下可能變慢？

看到 CAS 這麼輕量，你可能會直覺認為：用 AtomicInteger 做計數器，既安全又不需要加鎖，應該永遠很快。

低競爭時確實如此。但如果大量執行緒同時更新同一個計數器，情況會改變。問題出在 AtomicInteger 的內部只有一個 value 變數。

假設有 N 條執行緒同時對這個變數執行 CAS(expect, update)。硬體會保證同一時間只有一條執行緒成功，其餘 N-1 條執行緒都會失敗。

失敗的執行緒不會立刻掛起，而是原地自旋、重新讀值、再次嘗試。當競爭越激烈，CAS 失敗次數就越多，執行緒花在重試上的時間也越多。CPU 看起來很忙，卻有大量運算只是徒勞地繞圈。

這就是單點熱點問題：所有人都擠在同一扇門前，而這扇門一次只能讓一個人通過。門本身沒有壞，但人一多，排隊與反覆嘗試就會吞掉效能。

LongAdder：把一個熱點拆成很多個

JDK 8 引入了 LongAdder，以及用途相近的 DoubleAdder，用來改善高併發寫入時的競爭。

它的核心想法是分治，也可以理解成「用空間換時間」。既然所有執行緒搶同一個變數會塞車，那就不要只準備一個變數，而是準備多個位置，讓執行緒分散更新。

LongAdder 內部維護一個 Cell[] 陣列，主要運作方式如下：

  1. 沒有發生競爭時，直接更新 base 變數，這時的行為和 AtomicInteger 類似。
  2. 一旦發生競爭，例如某次 CAS 失敗，就不再一直卡在 base 上，而是根據目前執行緒的雜湊值，映射到 Cell 陣列中的某個槽位，在那個槽位上執行 CAS。
  3. 需要取得總數時，呼叫 sum()，把 base 和所有 Cell 的值加總後回傳。

原本的狀況是多條執行緒搶同一個位置；改成 LongAdder 後，執行緒會分散到多個位置。衝突機率下降，自旋重試造成的浪費也會跟著減少。

但這個設計有一個重要取捨：sum() 得到的是「最終一致」的結果，不保證是某個瞬間絕對精確的數字。如果加總進行到一半時，仍有執行緒正在更新某個 Cell，你拿到的結果可能不是當下最完整的值。

對高併發的統計計數來說，這種取捨通常可以接受。例如統計請求數、累計事件數時，重點往往是讓大量寫入順利完成，而不是每一次讀取都必須看見絕對即時的數字。

相對地，AtomicInteger 的 get() 取得的是即時且精確的值。這就是兩者選擇上的關鍵：你要的是即時精確的讀取，還是高競爭下更好的累加吞吐量？

小結

CAS 是一種樂觀鎖，透過 V（目前值）、A（預期舊值）與 B（新值）三個操作數進行更新。只有當 V 等於 A 時，才會把值改成 B；如果比較失敗，就自旋重試。它的底層依賴 Unsafe 呼叫 CPU 原子指令，因此能避開部分鎖與執行緒切換成本。

CAS 的陷阱是只看結果、不看過程，可能遇到 ABA 問題。加入版本號後，即使值從 A 變成 B 又回到 A，版本仍然不同，便能偵測出中間曾經發生過更新；AtomicStampedReference 就是這類解法。

AtomicInteger 在高競爭下可能變慢，原因是所有執行緒都搶同一個 value，失敗者又會大量自旋。LongAdder 則透過 base 加上 Cell 陣列，把單一熱點分散到多個位置；代價是 sum() 只保證最終一致，而不是每個瞬間都絕對精確。

到這裡，你手上已經有兩套不同方向的工具。一套是把人擋在門外的鎖，例如 synchronized、ReentrantLock 與 AQS；另一套是不先阻塞執行緒，而是讓它們分頭嘗試更新的無鎖原子機制，例如 CAS 與 LongAdder。

至於可見性與有序性，則由 JMM、volatile 與 happens-before 這套記憶體規則一起兜住。接下來的節點會把這些工具往更高階的併發編排延伸，處理精準喚醒、CountDownLatch 與 CompletableFuture 等常見手寫題與實戰場景。
