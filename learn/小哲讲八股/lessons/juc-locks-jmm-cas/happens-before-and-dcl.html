happens-before 與 DCL：為什麼單例一定要加 volatile

Step 4/5 · 鎖、JMM 與無鎖原子

先想一個工作中很難抓的 bug

你可能遇過這種情況：程式碼看起來沒有問題，測試也都通過了，但上線後偶爾有執行緒拿到一個「還沒準備完成」的物件。錯誤不一定每次出現，log 也很難留下明確線索，像是 bug 在跟你玩躲貓貓。

這類問題，常常和 Java 記憶體模型（JMM）有關。面試問到 happens-before 時，很多人會直覺回答：「就是 A 發生在 B 之前。」但面試官通常會再追問：「所以 A 一定在時間上比較早執行完嗎？」如果回答「對」，就容易掉進陷阱。

happens-before 談的其實不是手錶上的先後，而是一個執行緒對資料的修改，另一個執行緒是否一定看得到。這個觀念也正好能解釋：JVM 為什麼可以重排指令來換取效能，以及單例模式的雙重檢查鎖（Double-Checked Locking，DCL）為什麼一定要搭配 volatile。

為什麼需要一份「可見性的承諾」

編譯器與 CPU 會為了效能調整指令順序，處理器快取也可能讓一個執行緒的修改，沒有立刻被另一個執行緒看見。若完全沒有任何限制，多條執行緒同時執行時，誰先做、誰看得到誰的資料，就沒有可靠保障。

JMM 因此提供了一份規則：只要程式符合特定條件，就保證 A 操作的結果對 B 操作可見，即使底層實際進行了某些重排。 這份規則就是 happens-before。

它比較像是交通規則，而不是時間軸。交通規則不會告訴你每台車幾點幾分到達，只會告訴你哪些車流關係必須被遵守，才能避免撞車。

happens-before 談的是可見性，不是物理時間

當我們說「A happens-before B」，代表兩件事：

  1. A 的執行結果對 B 是可見的。
  2. A 在邏輯順序上排在 B 之前。

它不代表 A 在物理時間上一定先執行完。只要重排後的結果，和按照 happens-before 順序執行所得的結果一致，JMM 就允許這樣的重排。

所以，happens-before 的用途不是拿來製作「每個指令何時執行」的時間表，而是協助我們判斷資料是否能正確同步，以及這段程式是否具備執行緒安全。

六條面試與實務上最常用的規則

JMM 的規則不只有六條，但下面這些最常用。真正重要的不是死背名稱，而是知道它們如何串成一條可見性的因果鏈。

規則內容用途
程式次序同一條執行緒內，前面的操作 happens-before 後面的操作說明單執行緒內的邏輯順序
管程鎖定對同一把鎖，unlock happens-before 後續的 lock解釋 synchronized 為什麼也能保證可見性
volatile 變數對同一個 volatile 變數的寫入，happens-before 後續對它的讀取保證 volatile 寫入的可見性
傳遞性A hb B 且 B hb C，則 A hb C把多條規則串成完整的可見性關係
執行緒啟動主執行緒呼叫 start() 前的操作 hb 子執行緒內任意操作讓子執行緒看得到啟動前的設定
執行緒終止子執行緒內所有操作 hb 主執行緒從 join() 返回讓主執行緒在 join 之後看得到子執行緒的結果

其中，管程鎖定與 volatile 變數，分別對應「鎖能保證可見性」和「volatile 能保證可見性」。真正容易被低估的是傳遞性。

假設 A hb B、B hb C，那麼 A hb C。也就是說，如果對某個 volatile 變數的寫入被另一條執行緒看到了，那麼在這次寫入之前、同一條執行緒內完成的普通變數修改，也會透過這條 happens-before 關係對後續執行緒可見。這就是為什麼 volatile 有時可以像「發布開關」一樣使用。

實戰案例：雙重檢查鎖為什麼要加 volatile

單例模式如果希望「用到時才建立」，同時又要讓多條執行緒安全地取得同一個物件，常見做法是雙重檢查鎖。程式大致如下：

public class Singleton {
    private static volatile Singleton instance;   // 少了 volatile 就會出事

    public static Singleton getInstance() {
        if (instance == null) {                    // 第一次檢查：避免每次都加鎖
            synchronized (Singleton.class) {
                if (instance == null) {            // 第二次檢查：確保只建立一次
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

這段程式看起來很合理。第一次檢查可以避免每次呼叫都取得鎖，第二次檢查則能確保多條執行緒排隊進入鎖之後，不會重複建立物件。

但如果把 volatile 拿掉，程式就可能回傳一個「半成品」物件。問題不在兩次 if，而在於 new Singleton() 並不是底層的一個不可分割步驟。

new 其實不是一步，而是三步

在程式碼裡，我們只看到一行 new Singleton()。但從 JVM 的角度看，建立物件大致可以拆成三個步驟：

  1. 分配記憶體：memory = allocate(); 先替物件準備一塊空間。
  2. 初始化物件：ctorInstance(memory); 呼叫建構子，設定物件的成員變數。
  3. 建立關聯：instance = memory; 讓 instance 指向這塊記憶體。此時 instance 已經不再是 null。

我們期待的順序是 1 → 2 → 3。不過，步驟 2 和步驟 3 之間沒有明顯的資料依賴，編譯器與 CPU 可能為了效能，把它們重排成 1 → 3 → 2。

在單執行緒情境下，這樣做通常看不出差異，因為同一條執行緒最後仍然會完成初始化。但一旦另一條執行緒在中途讀取 instance，問題就出現了。

災難現場：另一條執行緒拿到半初始化物件

假設執行緒 A 進入同步區塊建立 Singleton，而且發生了 1 → 3 → 2 的重排。A 先分配記憶體，再讓 instance 指向這塊空間；但物件初始化，也就是步驟 2，還沒有完成。

此時，instance 已經不是 null，但物件內的欄位可能仍然是預設值。就在這個短暫空檔，執行緒 B 進入 getInstance()，並在同步區塊外的第一次檢查看到：

instance != null。

B 於是以為物件已經建立完成，直接把它回傳出去。它拿到的其實是一個半成品：欄位可能尚未初始化，後續使用時可能得到空值，甚至產生錯誤結果。

這種 bug 特別難抓，因為它取決於非常細的執行時序。測試時可能幾千次都沒發生，上線後卻在高併發或特定硬體環境中偶爾出現。

volatile 如何阻止這個問題

在 instance 上加上 volatile 後，JMM 會透過記憶體屏障建立必要的順序限制，禁止物件初始化與參考賦值之間發生這種危險的重排。

因此，執行緒 B 看到的 instance 要嘛是 null，要嘛就是已經完成初始化的物件，不會看到「參考已經寫入，但內容還沒準備好」的半成品。

整個 DCL 的因果鏈可以這樣記：

new 會拆成三步 → 步驟 2 與步驟 3 存在重排空間 → 先賦值再初始化會產生半初始化物件 → volatile 透過記憶體屏障禁止這種重排。

只要能把這條鏈講清楚，就不只是背出「DCL 要加 volatile」，而是真的理解它為什麼需要 volatile。

小結

happens-before 是 JMM 提供的可見性承諾，不是物理時間順序。A happens-before B，代表 A 的結果對 B 可見，而且在邏輯上排在 B 前面；只要不改變程式結果，JMM 仍然允許指令重排。常用的六條規則是程式次序、管程鎖定、volatile、傳遞性、執行緒啟動與執行緒終止。傳遞性會把不同規則串起來，也讓 volatile 能像一個發布開關。DCL 之所以要加 volatile，是因為 new 可以拆成三步，若先把參考賦值、後完成初始化，其他執行緒就可能拿到半成品；volatile 的記憶體屏障正好能禁止這種重排。
