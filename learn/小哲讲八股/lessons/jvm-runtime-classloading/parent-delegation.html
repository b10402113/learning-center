雙親委派：為什麼你寫的 String 蓋不過 JDK？

JVM 執行時與類別載入 · Step 5/5 · 學習目標：理解「向上委託、向下載入」的流程、三個核心類別載入器，以及 SPI、Tomcat 為什麼需要打破雙親委派。

前言：為什麼你自己寫的 String，永遠贏不過 JDK？

假設你一時好奇，在專案裡自己寫了一個 java.lang.String，想測試能不能蓋掉 JDK 原生的版本。結果不管你把檔案放在哪裡，程式執行時使用的仍然是 JDK 自帶的 String，你寫的那份完全沒有機會上場。

但在另一個真實場景裡，同一個 Tomcat 卻可能同時跑著兩個應用程式：A 應用使用 Spring 4，B 應用使用 Spring 5，而且兩個版本可以和平共存。為什麼一個類別不能隨便覆蓋，卻又可以同時存在兩份？

這兩個看似矛盾的現象，都和類別載入器以及雙親委派模型有關。上一課談的是類別載入有哪些階段；這一課要進一步回答：這些階段由誰執行？類別載入時要先找誰？框架又為什麼有時候必須故意繞過這套規則？

三個核心類別載入器

Java 的類別載入體系，可以先用三層來理解：

類別載入器層級負責載入什麼
Bootstrap ClassLoader（啟動類別載入器）最上層，使用 C++ 實作JDK 核心類別庫，例如 rt.jar 裡的 String、Object
Extension ClassLoader（擴充類別載入器）中層JDK 的擴充目錄，例如 jre/lib/ext
Application ClassLoader（應用程式類別載入器）下層Classpath 下的應用程式類別，也就是你自己寫的程式

這裡的「父」不是 Java 繼承中的父類別，而是類別載入器之間的邏輯上下層關係。Application ClassLoader 的父載入器是 Extension ClassLoader，Extension ClassLoader 的父載入器則是 Bootstrap ClassLoader。

Bootstrap ClassLoader 是由 C++ 實作，不是一般的 Java 物件。因此在 Java 程式碼中取得它的父載入器時，看到的會是 null。這是面試中常出現的小細節。

委派流程：先往上問，再往下找

雙親委派模型可以記成八個字：向上委託，向下載入。

當一個類別載入器收到載入請求時，它不會立刻自己尋找檔案，而是先把請求交給父載入器。這個請求會一路往上傳，直到 Bootstrap ClassLoader。只有當上層載入器找不到這個類別時，請求才會一層一層退回來，最後由最初收到請求的載入器處理。

以 AppClassLoader 載入 User.class 為例，流程如下：

  1. 先檢查快取： AppClassLoader 先確認自己是否已經載入過這個類別。如果載入過，就直接回傳快取中的結果。
  2. 向上委託：如果快取中沒有，AppClassLoader 不急著自己找，而是把請求交給 Extension ClassLoader。
  3. 繼續往上：Extension ClassLoader 再把請求交給 Bootstrap ClassLoader。
  4. 頂層先找：Bootstrap ClassLoader 會在自己的核心類別庫範圍內尋找。找到就直接回傳；找不到，就告訴下一層「我這裡沒有」。
  5. 逐層往下找：Extension ClassLoader 接著在 ext 目錄尋找。如果仍然找不到，請求才回到 AppClassLoader。
  6. 由應用程式載入：最後，AppClassLoader 才會到 Classpath 中尋找並載入 User.class。

可以把它想成公司處理問題：員工遇到事情，先向經理請示；經理處理不了，再往上報給董事長。董事長若也沒有答案，問題才會逐層退回，最後由最接近實際工作的員工處理。

為什麼要設計成這麼繞？

如果每個類別載入器收到請求後，都直接在自己的範圍內尋找，表面上比較快，實際上卻會帶來兩個嚴重問題：核心類別可能被偽造，還可能被重複載入。

一、保護核心 API，避免被篡改。

回到開頭的 java.lang.String 實驗。如果沒有雙親委派，AppClassLoader 收到載入 java.lang.String 的請求後，就可能直接載入你放在 Classpath 裡的版本。這等於讓應用程式有機會替換 JDK 的核心類別，整個執行環境就像把大門鑰匙交給了任何人。

有了雙親委派，請求會一路送到 Bootstrap ClassLoader。它在核心類別庫中找到正版的 String 後，就會直接回傳那個版本。你自己寫的同名類別因此沒有機會取代 JDK 核心類別，這就是雙親委派提供的沙箱安全性。

二、避免類別被重複載入。

Java 判斷兩個類別是否相同時，看的不只是類別全名，還要看載入它的類別載入器。也就是說，類別的身分是由「類別全名 + 類別載入器」共同決定。

如果沒有委派，同一個 String 可能先被 Bootstrap ClassLoader 載入一次，又被 AppClassLoader 載入一次。雖然名稱相同，JVM 仍會把它們視為不同的類別，後續可能造成型別轉換錯誤，也浪費記憶體。

雙親委派讓核心類別優先由最上層的 Bootstrap ClassLoader 載入，避免每個下層載入器都各自建立一份。

雙親委派的限制：上層看不到下層

雙親委派很安全，但它也有一個天生的限制：類別的可見性主要是由上往下傳遞，父載入器看不到子載入器負責的類別。

這在一般情況下沒有問題，因為 JDK 核心類別不需要知道你的應用程式細節。但如果出現「基礎類別要呼叫使用者提供的實作」，或者「同一個類別需要同時使用多個版本」的需求，這個限制就會變成絆腳石。這時候，框架就必須刻意繞過雙親委派。

場景一：SPI，讓基礎類別找到使用者實作

JDBC 是典型例子。JDK 核心類別庫定義了 java.sql.Driver 介面，這個介面由 Bootstrap ClassLoader 載入；但真正的資料庫驅動程式，例如 MySQL 驅動，則是由第三方提供，放在 Classpath 中，通常由 AppClassLoader 載入。

問題在於：Bootstrap ClassLoader 位於上層，按照雙親委派，它不能反過來到 AppClassLoader 的範圍尋找 MySQL 驅動。那麼，管理驅動程式的 DriverManager 要怎麼找到這個實作？

解法是使用執行緒上下文類別載入器（Thread Context ClassLoader）。DriverManager 初始化時，會取得目前執行緒的 context class loader。這個載入器預設通常是 AppClassLoader，接著再用它尋找 SPI 介面的實作類別。

可以把它想成上層主管需要使用基層團隊的工具。主管本身不能直接走進基層資料夾找檔案，但可以借用目前執行緒提供的「上下文載入器」這把鑰匙，主動請子載入器完成尋找。

場景二：Web 容器隔離，讓多個版本共存

一個 Tomcat 可能同時部署多個 Web 應用程式。假設 A 應用依賴 Spring 4，B 應用依賴 Spring 5。如果所有應用都嚴格共用同一個類別載入器，某個版本的 Spring 一旦先被載入，後續載入另一個版本時，就可能被誤認為「這個類別已經存在」，最後造成版本衝突。

Tomcat 的做法是提供自訂的 WebAppClassLoader，並調整載入順序：先到自己的應用程式目錄，例如 /WEB-INF/lib，尋找類別；找不到時才向上委託。

這和標準的雙親委派順序相反，但換來了應用程式之間的隔離。A 應用可以載入自己的 Spring 4，B 應用也可以載入自己的 Spring 5，兩者由不同的類別載入器負責，因此 JVM 能把它們視為不同的類別。

所以，「同一個類別可以有兩份」並不矛盾。真正的判斷條件不是只有類別名稱，而是「類別全名 + 載入它的類別載入器」。

小結

雙親委派模型用「向上委託、向下載入」規定類別的尋找順序。請求會先交給父載入器，只有父載入器找不到時，子載入器才會負責載入。

三個核心類別載入器由上到下是 Bootstrap、Extension、Application。這套設計主要解決兩個問題：第一，保護 JDK 核心 API，避免應用程式偽造或覆蓋；第二，避免同一個核心類別被重複載入。

判斷兩個類別是否相同時，看的不是類別全名而已，而是類別全名加上類別載入器。當基礎類別需要找到使用者提供的實作時，SPI 會透過 Thread Context ClassLoader 打破單向限制；當 Web 容器需要讓不同應用程式使用不同版本的類別時，Tomcat 則會透過 WebAppClassLoader 實現隔離。
