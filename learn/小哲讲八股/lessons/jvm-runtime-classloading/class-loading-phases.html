類別載入七階段：從 .class 到 Class 物件

JVM 執行時與類別載入 · Step 4/5 · 學習目標：掌握類別載入的七個階段，分清準備階段的零值、初始化階段的真正賦值，以及 static final 編譯期常數的例外。

前言：static int a = 666，到底哪一刻才會變成 666？

你可能看過這樣的程式碼：public static int a = 666;。直覺上，宣告寫完的那一刻，a 好像就應該是 666。但 JVM 實際處理時，會先替 a 配置記憶體，再放入型別的預設值；真正把 666 寫進去，則是後面另一個階段的工作。

也就是說，「準備好空間」和「執行賦值」不是同一件事。中間還隔著類別載入、驗證、解析等步驟。面試若問你：static int a = 666 在哪個階段變成 666？只背「類別載入會初始化」很容易答錯；你必須知道每個階段各自負責什麼。

這一課就把這條流程攤開來看。JVM 不會把 .class 檔案讀進來後直接執行，而是像工廠流水線一樣，依序完成讀取、檢查、配置、解析，最後才執行靜態初始化。

類別載入要解決什麼問題？

類別載入，簡單說就是：把磁碟上的 .class 檔案讀進記憶體，並為它建立一個 java.lang.Class 物件。

這個 Class 物件可以想成應用程式通往該類別的一把鑰匙。你要用反射取得方法、欄位或標註，都要透過它。至於類別的結構資訊，則會放在 JVM 管理的類別資訊區域；應用程式拿到的 Class 物件，則是存取這些資訊的入口。

整個生命週期可以拆成七個階段：

  1. 加載
  2. 驗證
  3. 準備
  4. 解析
  5. 初始化

這裡常說的「七個階段」，是因為連接（Linking）還可以再細分為驗證、準備、解析三個階段；連同加載與初始化來看，就是面試最常考的完整流程。接著依序拆開。

第一階段：加載（Loading）

加載是整個流程中，主要負責讀取類別檔案的階段。JVM 會根據類別的全限定名，也就是套件名稱加上類別名稱，找到對應的 .class 檔案，並把其中的二進位位元組流讀進記憶體。

讀取完成後，JVM 會在堆中建立一個代表這個類別的 java.lang.Class 物件。這個物件就是之後使用反射或取得類別資訊的入口。

可以這樣記：

  • .class：磁碟上的類別檔案。
  • 類別資訊：JVM 管理的類別結構資料。
  • Class 物件：程式存取該類別資訊的入口。

加載的重點不是「開始執行程式碼」，而是先把類別的原始材料搬進 JVM，讓後續階段有東西可以檢查與處理。

第二階段：連接（Linking）

連接可以想成正式使用類別前的施工階段。JVM 會先確認這份位元組碼能不能安全執行，再替靜態變數準備空間，最後把類別中尚未對應到實際目標的引用解析完成。

驗證（Verification）：先確認這份位元組碼能不能信任

驗證有點像替程式碼「查毒」和「驗身分」。JVM 必須確認這份位元組碼符合虛擬機規範，不能因為檔案損壞或內容不合法，就讓 JVM 執行到一半出現危險狀況。

常見的檢查包括：

  • 檔案開頭的魔數是否正確，也就是 0xCAFEBABE。
  • 位元組碼中是否包含非法的跳轉指令。
  • 型別檢查是否通過。
  • 操作數堆疊的使用是否符合規則。

如果驗證沒有通過，JVM 就不會放心讓這個類別繼續往下走。這一步解決的是「這份程式碼能不能安全交給 JVM 執行」的問題。

準備（Preparation）：先開空間，再放入預設值

準備階段會替類別變數，也就是使用 static 修飾的變數，分配記憶體並設定預設初始值。

例如：

public static int a = 666;

在準備階段結束時，a 還不是 666，而是整數的預設值 0。因為這個階段只負責「把位置準備好」，不會執行程式碼中的賦值動作。

不同型別會有不同的預設值：

  • 整數型別：0
  • boolean：false
  • 物件參考：null

等到後面的初始化階段執行 static int a = 666;，a 才會從 0 變成 666。這就是準備與初始化最容易混淆的地方：前者負責配置與零值，後者才負責執行賦值。

static final 編譯期常數：準備階段的例外

如果宣告的是編譯期就能確定的常數，例如：

static final int a = 666;

它可能在準備階段就直接被設定成 666，而不用等到初始化階段。

原因在於，這種常數的值在編譯時就已經知道。編譯器可能會把它放進 ConstantValue 屬性，JVM 在準備階段就能直接套用這個值。

所以面試時要分清楚兩種情況：

  • static int a = 666;：準備階段先是 0，初始化階段才變成 666。
  • static final int a = 666;：如果是編譯期常數，準備階段就可能直接是 666。

解析（Resolution）：把名稱線索換成真正目標

解析負責處理常數池中的引用。類別剛載入時，某些引用還只是「名稱線索」，稱為符號引用；JVM 需要把它換成可以直接找到目標的直接引用。

例如，符號引用可能只是字串形式的 com.test.User。它就像一張只寫著店名的紙條，還沒有對應到實際位置。解析之後，JVM 會把它對應到記憶體中真正的類別或欄位位置，之後執行時就能更直接地找到目標。

需要注意的是，解析不一定在所有情況下都一次完成。有些解析可以延後到真正使用該引用時才進行，但它解決的核心問題不變：把「名稱」轉成 JVM 能使用的實際引用。

第三階段：初始化（Initialization）

初始化是類別載入流程中，真正開始執行 Java 程式碼的階段。

JVM 會執行類別的 <clinit>() 方法。這不是你在原始碼中直接寫出的方法，而是編譯器把類別中的靜態變數賦值與靜態程式碼區塊，依照原本的順序整理、合併後產生的類別初始化方法。

例如：

public static int a = 666;

到了初始化階段，這個賦值動作才會被執行，a 才會從準備階段的 0 變成 666。如果類別中還有靜態程式碼區塊，也會按照原始碼出現的順序執行。

因此可以用一句話記住兩個階段的差異：

準備階段先把靜態變數放好並填入零值；初始化階段才執行靜態賦值與靜態程式碼區塊。

此外，JVM 會確保同一個類別的 <clinit>() 在多執行緒環境下只被正確執行一次。即使多個執行緒同時第一次使用這個類別，也不會讓靜態初始化被重複執行。這項保證也是靜態內部類別單例能安全延遲載入的基礎之一。

什麼時候會觸發初始化？

類別不一定要等到你執行 new 才開始被載入；而初始化也不是所有「看到類別名稱」的情況都會發生。常見的初始化觸發時機包括：

  • 使用 new 建立這個類別的實例。
  • 讀取或設定這個類別的靜態欄位，但編譯期常數通常是例外。
  • 呼叫這個類別的靜態方法。
  • 使用反射，例如 Class.forName() 主動載入類別。
  • 初始化某個類別時，發現它的父類別還沒有初始化，會先初始化父類別。
  • 啟動程式的主類別，也就是包含 main 方法的類別。

這些規則說明了一件事：JVM 通常會在類別第一次被「實際使用」時，才推進到需要的載入或初始化階段，而不是程式一啟動，就把所有類別全部初始化。

用一條流程線記住七個階段

遇到面試題時，可以沿著這條順序回答：

加載 → 驗證 → 準備 → 解析 → 初始化

其中，驗證、準備、解析合稱連接。真正容易被追問的是準備與初始化：

  • 加載：讀取 .class，建立 Class 物件。
  • 驗證：確認位元組碼合法且安全。
  • 準備：替 static 變數配置空間，並設定零值。
  • 解析：把符號引用對應成直接引用。
  • 初始化：執行 <clinit>，真正執行靜態賦值與靜態程式碼區塊。

因此，static int a = 666 在準備階段是 0，到了初始化階段才是 666；而編譯期可確定的 static final 常數，則可能在準備階段就直接設定完成。

小結

類別載入不是單一動作，而是一條從檔案到可執行類別的流水線。JVM 先加載 .class 並建立 Class 物件，再經過驗證、準備、解析等連接步驟，最後才進入初始化。

記住最重要的分界：準備階段只替靜態變數配置空間並放入預設值；初始化階段才執行 <clinit>，讓靜態賦值與靜態程式碼區塊真正生效。唯一常見的例外，是值在編譯期就已經確定的 static final 常數。
