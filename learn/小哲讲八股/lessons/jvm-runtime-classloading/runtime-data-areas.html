JVM 五個執行時資料區：一次分清堆與棧

JVM 執行時與類載入 · Step 2/5 · 學習目標：畫出 JVM 五個執行時資料區，分清哪些區域由執行緒共享、哪些屬於執行緒私有，從四個維度比較堆與棧，並說明方法區為什麼從永久代走向元空間。

前言：都是「記憶體爆了」，症狀卻完全不同

線上服務半夜告警，你打開日誌，看到 java.lang.OutOfMemoryError: Java heap space。隔天另一個服務出事，訊息卻變成 StackOverflowError。

這兩種錯誤常被籠統地叫作「記憶體爆了」，但它們壞掉的地方完全不同。一個是放物件的堆空間滿了；另一個則是方法呼叫疊得太深，把某個執行緒自己的棧撐爆了。

如果分不清這兩者，排查方向就會整個歪掉。遇到堆空間不足時，你應該檢查物件為什麼回收不掉，或評估是否需要調整堆大小；遇到棧溢出時，則要先看是不是遞迴太深，或迴圈根本沒有出口。

要看懂這些症狀，得先知道 JVM 在執行時把記憶體分成哪些區域、每一區負責什麼。這一課先把整張地圖畫出來，再放大比較最常被拿來一起考的堆與棧。

五個執行時資料區：先分共享與私有

依照 Java 虛擬機規範，JVM 的執行時資料區通常分成五塊。最重要的分類方式，是看它屬於「執行緒共享」還是「執行緒私有」。

共享區域跟著整個虛擬機的生命週期存在；私有區域則跟著個別執行緒建立與消失。可以先用「兩塊共享、三塊私有」記住整體結構。

區域歸屬主要裝什麼滿了會怎樣
堆（Heap）執行緒共享幾乎所有物件實例與陣列OutOfMemoryError
方法區（Method Area）執行緒共享類別資訊、常數、靜態變數、編譯後程式碼元空間耗盡時發生 OOM
虛擬機棧執行緒私有每個方法的棧框：局部變數、運算元棧等StackOverflowError／OOM
本地方法棧執行緒私有與虛擬機棧類似，服務 native 方法同上
程式計數器執行緒私有目前執行到哪一行位元組碼不會溢出

堆與方法區由所有執行緒共用，因此其中一區出問題時，通常可能影響整個行程。虛擬機棧、本地方法棧與程式計數器則是每個執行緒各有一份；某個執行緒的私有區域出錯時，通常會先表現在該執行緒身上。

兩塊共享區域

堆是 JVM 記憶體中最大的一塊，也是垃圾回收（GC）的主戰場，所以有時會直接稱為「GC 堆」。平常寫下的 new User()、new int[100]，物件本體和陣列通常都配置在這裡。

因為所有執行緒都能存取堆裡的物件，所以多執行緒同時操作同一個物件時，就必須考慮同步問題。當堆已經放不下更多物件，又無法再擴張時，JVM 就會拋出 OutOfMemoryError。

方法區存放的是與「類別」有關的資料，包括已載入的類別資訊、常數、靜態變數，以及即時編譯器編譯後的程式碼。

這裡有一段常被問到的演進歷史：JDK 7 及以前，方法區通常以「永久代（Permanent Generation）」實作，並且屬於堆的一部分；JDK 8 開始，則改稱為「元空間（Metaspace）」，並搬到本地記憶體中，不再受 JVM 堆大小的直接限制。至於為什麼要這樣改，後面會單獨說明。

三塊執行緒私有區域

虛擬機棧可以看成 Java 方法執行時所使用的執行緒記憶體模型。每當一個方法被呼叫，JVM 就會在棧頂建立一個棧框（Stack Frame），用來放這個方法執行時需要的資料，例如局部變數表、運算元棧、動態連結與方法出口。

方法執行結束後，對應的棧框就會彈出，所占用的空間也會自動歸還，不需要 GC 介入。若遞迴太深，棧框一層層疊上去，超過深度限制，就會拋出 StackOverflowError。如果棧需要擴張，卻申請不到足夠的記憶體，則可能拋出 OOM。

本地方法棧的角色和虛擬機棧很接近，只是它專門服務 native 方法。這些方法通常使用 C、C++ 等非 Java 語言實作，再透過 JNI 提供 Java 呼叫。由於它們執行時不走 Java 位元組碼，因此需要自己的棧來支援執行。

程式計數器是五個區域中最小的一塊，但用途很關鍵。它記錄目前執行緒正在執行哪一行位元組碼。

當執行緒被切換出去，之後又切換回來時，JVM 必須知道要從哪裡接著執行，程式計數器就像一個小小的書籤，記下了這個位置。分支、迴圈、跳躍與例外處理，都需要依靠這個位置資訊。

它還有一個常考特性：程式計數器是 JVM 中唯一不會發生記憶體溢出的區域，因為它儲存的資訊非常少，而且大小相對固定。

堆與棧的四個維度對比

堆與棧是最常被放在一起比較的一組。可以先用一句話抓住核心：

棧是執行時的單位，負責「程式怎麼執行」；堆是儲存的單位，負責「資料怎麼存放」。

再往下拆，可以從四個維度把它們講清楚。

一、記憶體位置與分配方式

棧的記憶體通常是連續的，資料依照「先進後出」的方式一格一格進出。方法結束後，棧框就能直接彈出，分配與釋放速度很快，也不需要垃圾回收。

堆的記憶體通常不連續。配置物件時，JVM 必須尋找可用空間；物件不再使用後，還要依靠 GC 的標記、清除或複製等機制回收。相較之下，堆的管理成本更高。

這也是為什麼「能不能少建立一些堆上的物件」會影響效能：物件越多，配置與回收的工作就越多，GC 也可能更頻繁。

二、儲存什麼內容

棧主要存放局部變數、運算元棧與動態連結。不過，這裡有一個很常見的誤解需要釐清。

如果變數是基本型別，例如 int，棧框裡通常放的是值本身；如果變數是物件，棧框裡放的則只是一個參考（reference），物件本體仍然位於堆中。

因此，User u = new User(); 可以拆成兩個部分來看：u 這個參考位於棧框中，而 new User() 建立出的物件實例則位於堆中。

三、執行緒可見性

棧是執行緒私有的。每個執行緒都有自己的棧，彼此不會直接共用同一個棧框，因此棧上的局部資料通常不需要透過鎖來保護。

堆則是執行緒共享的。所有執行緒都可能存取堆裡的同一個物件，所以當多個執行緒同時修改它時，就必須自行處理同步問題。堆本身是共享的，並不代表放在堆裡的物件自然就是執行緒安全。

四、可能出現的異常

棧空間不足，而且無法再擴張時，通常會拋出 StackOverflowError。最典型的原因是遞迴太深，讓棧框不斷累積。

堆空間不足時，則會拋出 OutOfMemoryError。常見情況是建立了太多物件，或者物件一直被參考著，導致 GC 無法回收。

回到開頭的兩個錯誤訊息：它們雖然都和記憶體有關，卻分別指向不同的區域。排查時先確認是哪一區出問題，才能找到正確的方向。

方法區為什麼從永久代改成元空間

這是一段由實際痛點推動的演進。JDK 8 之前，方法區通常以永久代實作。永久代在邏輯上是獨立區域，但在物理上仍屬於堆的一部分，而且大小通常透過 -XX:MaxPermSize 設定上限。

問題在於，這個上限很難設定得剛剛好。現代框架，例如 Spring、Hibernate，會大量使用 CGLib 產生動態代理類。這些類別是在執行期間持續產生的，很容易把永久代撐爆，最後出現：

java.lang.OutOfMemoryError: PermGen space

當然可以把永久代調大，但究竟要設多大並不容易。設得太小，服務容易因為類別資料太多而出錯；設得太大，又可能白白保留一塊用不到的空間。

JDK 8 將類別的元資料從堆裡搬到本地記憶體，並改由元空間管理。這樣一來，元空間不再直接受 JVM 堆上限限制，而是受到作業系統可用實體記憶體的限制，需要時也能自動擴張。

這降低了永久代因固定容量不足而 OOM 的機率，但不代表元空間永遠不會滿。當載入了太多類別，或類別持續被動態產生而沒有被卸載，仍然可能看到元空間相關告警。這時出問題的不是堆，而是存放「類別資訊」的區域。

小結

JVM 的執行時資料區分成五塊：堆與方法區是執行緒共享區域；虛擬機棧、本地方法棧與程式計數器則是執行緒私有區域。

堆是最大的區域，主要存放物件實例與陣列，也是 GC 的主戰場。方法區存放類別相關資訊，JDK 8 之後從永久代改為位於本地記憶體的元空間。

棧與堆最核心的差別，可以整理成四點：棧是執行單位、通常連續、執行緒私有，而且不需要 GC；堆是儲存單位、通常不連續、由執行緒共享，並且依賴 GC 管理。
