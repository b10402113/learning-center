位元組碼怎麼跑：半編譯、半解釋與 JIT

JVM 執行時與類載入 · Step 1/5 · 學習目標：說出 Java 從 .java 到執行的完整鏈路，解釋為什麼需要解釋器搭配 JIT，並理解逃逸分析如何讓物件有機會不進堆。

前言：CPU 上跑的，真的就是你寫的那份檔案嗎？

你把 .java 檔案改了幾行，在 IDE 裡按下編譯、打包，最後丟到伺服器上執行。表面上看起來像是「編譯成功，程式就能跑」，但中間其實還隔著幾層轉換。

伺服器的 CPU 只認得自己的機器指令；你寫的 Java 原始碼不是機器指令，而編譯後的檔案也不是 CPU 能直接執行的格式。那麼，javac 到底編出了什麼？它產生的是介於原始碼與機器碼之間的中間產物：位元組碼（bytecode）。

真正負責把位元組碼變成實際機器動作的，是 JVM。這一課會沿著「原始碼 → 位元組碼 → 機器碼」走一遍，也會回答一個常被問到的問題：既然 Java 已經編譯過了，為什麼執行時還需要解釋器，甚至還需要即時編譯器？先把這條鏈路理清楚，後面學 JVM 記憶體與類載入時，就不會只剩下零散名詞。

Java 到底是編譯型，還是解釋型？

這個問題看起來像選擇題，其實不能只回答「是」或「不是」。要先看看兩種典型的執行方式。

編譯型語言以 C、C++ 為代表。原始碼會先由編譯器整份翻成特定平台的機器碼，產生可執行檔。程式執行時，CPU 可以直接跑這些機器指令，中間不需要再翻譯。

這種方式的好處是執行效率高，但代價是平台相依。換了作業系統或 CPU 架構，通常就得重新編譯一份。

解釋型語言則像早期的 JavaScript、Python。程式執行到某個位置時，才把該位置的程式碼翻成機器能理解的動作。這樣不必事先把整份程式編譯完，啟動可以比較快；但如果每一行都要邊翻邊執行，長時間跑起來就容易付出效能代價。

Java 兩邊都使用了。它先透過 javac，把 .java 原始碼整份編譯成平台無關的位元組碼 .class，這部分像編譯型語言；接著由 JVM 在執行時，把位元組碼轉成目前平台需要的機器指令，這部分又像解釋型語言。

因此，比較準確的說法是：Java 是一門「半編譯、半解釋」的混合型語言。

為什麼中間要多一層位元組碼？

你可能會想：既然最後都要轉成機器碼，為什麼不直接像 C 一樣，一開始就編譯成目標機器的指令？

答案和 Java 常被提到的口號有關：「一次編寫，到處執行」。

位元組碼不是寫給 CPU 看的，而是寫給 JVM 看的。同一份 .class，可以交給 Windows 上的 JVM、Linux 上的 JVM，或 ARM 架構上的 JVM。至於如何把這份位元組碼轉成各自平台的機器指令，交給對應的 JVM 處理。

如果直接把 Java 原始碼編譯成某一種 CPU 的機器碼，跨平台的成本就會回到應用程式開發者身上。加入位元組碼這個中間層後，開發者只需要交付一份位元組碼，平台差異則由各平台的 JVM 吸收。這也是 Java 能在企業後端長期使用的重要原因之一。

只有解釋器不夠快，所以需要 JIT

最直接的做法，是讓 JVM 從頭到尾都使用解釋器：程式執行到哪裡，就翻譯到哪裡。這樣程式可以啟動，但對長時間執行的服務來說，效能通常不夠理想，因為相同的程式碼可能每次執行都要重新解釋。

那能不能在程式啟動時，就像靜態編譯一樣，把整份程式一次轉成機器碼？這也有代價：

  • 啟動時需要先花時間編譯，程式會比較晚才能開始提供服務。
  • 程式還沒真正跑起來以前，編譯器不知道哪些路徑最常被走，也不敢做太激進的最佳化。

JIT（Just-In-Time，即時編譯）就是用來處理這個取捨的。它不急著一開始就編譯全部程式，而是先讓解釋器執行，觀察哪些程式碼真的被反覆使用。等某段程式碼變成「熱點」後，再把它編譯成機器碼。

這個策略很像餐廳先觀察哪些菜最常被點，再把熱門菜的備料和製作流程最佳化。偶爾才點一次的菜，不值得提前投入大量成本；真正反覆出現的熱點，才值得花力氣處理。

因此，Java 的執行流程可以整理成這樣：

  1. .java 原始碼先由 javac 編譯成位元組碼。
  2. 程式啟動後，解釋器先逐步執行位元組碼。
  3. JVM 找出反覆執行的熱點程式碼。
  4. JIT 將這些熱點編譯成機器碼。
  5. 之後再次執行相同熱點時，直接使用機器碼，不必重新解釋。

這就同時兼顧了兩件事：啟動時比較快，因為不必先編譯整個程式；長期執行時也比較快，因為常用的部分已經變成機器碼。

JVM 怎麼知道哪段程式碼「很熱」？

JVM 會做熱點探測。常見做法是使用計數器：某個方法被呼叫一次，就增加一次計數；當計數累積到某個閾值，JVM 就會判斷這個方法值得編譯。

以 HotSpot 的 Server 模式為例，這個閾值大約是一萬次左右，Client 模式則比較低。實際上不需要死背這個數字，重點是：JVM 是根據程式的實際執行狀況「量」出熱點，而不是由開發者事先指定哪些方法一定要編譯。

編譯後的機器碼放在哪裡？

JIT 編譯出的機器碼會放在一塊稱為 Code Cache（程式碼快取）的區域。

之後同一段熱點程式碼再次被呼叫時，JVM 就可以直接從 Code Cache 取出已經編譯好的機器碼執行，跳過原本的解釋流程。

這也解釋了為什麼長時間執行的服務，常常會在啟動後的前幾分鐘到幾十分鐘逐漸「熱起來」。剛開始時，許多程式碼還在被解釋；等熱點陸續被編譯並放入 Code Cache，效能才會慢慢趨於穩定。

JIT 能做的，不只是把位元組碼翻成機器碼

JIT 在執行期間可以看到實際的型別、呼叫次數與執行路徑，因此有些最佳化是靜態編譯器做不到，或不敢太早做的。

  • 方法內聯（inlining）：把小方法的內容直接展開到呼叫處，省掉方法呼叫的成本，也讓後續最佳化有更多空間。
  • 死程式碼消除：如果某個分支根據實際執行結果永遠不會走到，JIT 可以把那段程式碼移除。
  • 逃逸分析：判斷物件是否會離開目前的方法或執行緒。若物件沒有外流，JIT 就有機會進一步減少堆分配與同步成本。

其中，逃逸分析特別值得理解，因為它會直接影響物件配置與 GC 壓力。

逃逸分析：物件有機會不進堆

我們平常會說：「使用 new 建立的物件會放在堆裡。」這是一個好用的通則，但不是永遠不變的鐵律。

JIT 會做逃逸分析（escape analysis），檢查某個物件的參考是否會「逃出」目前的方法或目前的執行緒。

例如，物件如果被 return 給呼叫方、被存進全域變數或靜態欄位，或者被放進其他執行緒也能存取的容器，就代表它可能在目前方法結束後仍被使用。這種物件就是已經逃逸。

反過來，如果物件從建立到使用完畢，都只存在於目前方法內，方法結束後外部再也拿不到它，那麼它就可能被判定為「未逃逸」。

確認物件未逃逸後，JIT 可能進行幾種最佳化：

  • 棧上分配：物件不一定要配置在堆上，而有機會放進目前方法的棧框。方法結束、棧框彈出後，相關空間就能一併回收，不必等待 GC 處理。
  • 標量替換：把物件拆成其中的基本型別成員，直接當成區域變數使用，連物件本身的外殼都不需要建立。實務上，HotSpot 主要會透過這種方式達到類似「棧上分配」的效果。
  • 同步消除：如果物件只會被單一執行緒使用，附加在這個物件上的 synchronized 鎖就沒有實際意義，JIT 可能直接移除這段同步成本。

這也說明了為什麼有些效能建議會鼓勵優先使用區域變數，而不是動不動就把物件存成成員變數或全域變數。物件越不容易外流，JIT 就越有機會判斷它不需要長期存在於堆中，進而減少堆分配與 GC 壓力。

當然，這不是一條只要照做就必然生效的規則。JIT 必須根據實際執行狀況進行判斷；如果它無法證明物件不會外流，或判斷存在風險，就會採取保守做法，讓物件照常配置在堆裡。

小結

Java 不是單純的編譯型語言，也不是單純的解釋型語言。它先由 javac 把原始碼編譯成平台無關的位元組碼，再由 JVM 在執行時協調解釋器與 JIT。

解釋器負責讓程式快速啟動，也負責執行還不值得編譯的冷程式碼；JIT 則透過熱點探測找出反覆執行的程式碼，將它們編譯成機器碼並放進 Code Cache。由於 JIT 掌握了實際執行資訊，它還能進行方法內聯、死程式碼消除與逃逸分析等最佳化。

逃逸分析最直接的效果，是讓沒有外流的物件有機會不進堆，甚至被拆成幾個區域變數使用，從而減少堆分配與 GC 壓力。
