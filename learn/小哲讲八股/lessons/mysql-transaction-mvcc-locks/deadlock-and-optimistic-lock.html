死鎖與樂觀鎖：AB-BA、wait-for graph 與 version CAS

Step 5/5 · 事務、MVCC 與鎖

學習目標

能用轉帳場景復現 AB-BA 死鎖、說明 wait-for graph 如何檢測與回滾，並講清樂觀鎖的 version CAS 與悲觀鎖在鎖持有時間上的本質差別。

前言：兩個轉帳服務各握一半

有一類線上事故特別難查：服務沒有當機，日誌裡卻不斷跳出 Deadlock found when trying to get lock，而且頻率不高、難以重現。翻開程式碼才發現，罪魁禍首是兩個看似無害的轉帳方法：一個把錢從 A 轉到 B，另一個把錢從 B 轉到 A。它們各自先鎖住自己扣款的那個帳戶，再去鎖對方要加款的帳戶。

結果就是上一節講的那種「互相卡住」被推到極致：交易 A 握著 id=1 等 id=2，交易 B 握著 id=2 等 id=1，形成一個誰也打不開的環。這一節先把這個死鎖完整復現一次，看看資料庫怎麼處理它；接著再講另一種常被拿來對比的策略，也就是樂觀鎖，它明明底層也用到行鎖，為什麼還被叫做「樂觀」。

死鎖的本質：等待關係繞成一個環

死鎖的本質，就是兩個或多個交易在執行過程中爭奪資源，最後形成「互相等待」的僵局。最經典的形態是 AB-BA 交叉死鎖：我拿著 A 等 B，你拿著 B 等 A，我不放手你也不放手，於是大家都動不了。

用轉帳場景復現死鎖

準備一張只有兩行資料的帳戶表：

CREATE TABLE account (
  id INT PRIMARY KEY,
  balance INT
) ENGINE=InnoDB;

INSERT INTO account VALUES (1, 1000), (2, 1000);

接著開兩個連線，模擬兩個併發的交易：

時間點交易 A（Session A）交易 B（Session B）狀態
T1BEGIN;BEGIN;兩交易開啟
T2UPDATE account SET balance = balance - 100 WHERE id = 1;A 取得 id=1 的行鎖
T3UPDATE account SET balance = balance - 100 WHERE id = 2;B 取得 id=2 的行鎖
T4UPDATE account SET balance = balance + 100 WHERE id = 2;A 想鎖 id=2，被 B 占著，進入等待
T5UPDATE account SET balance = balance + 100 WHERE id = 1;B 想鎖 id=1，被 A 占著，死鎖形成
結果（繼續等待）ERROR 1213: Deadlock found...MySQL 檢測到死鎖，回滾 B

把過程拆開看：T2 時 A 鎖住 id=1，T3 時 B 鎖住 id=2，於是 T4 時 A 想申請 id=2 只能等，T5 時 B 想申請 id=1 也只能等。到這裡，A 等 B、B 等 A，等待關係繞成一個閉環，死鎖成形。

InnoDB 怎麼處理死鎖：wait-for graph

好消息是 InnoDB 不會傻等。它的死鎖檢測機制會維護一張 wait-for graph（等待關係圖），把「誰在等誰」畫成一張有向圖。一旦圖上出現環，就代表死鎖發生。這時資料庫為了打破僵局，會選擇回滾代價較小的那個交易（通常是持有較少鎖、修改較少列的那一方），讓另一個交易繼續執行。上例中回滾的就是 B，A 得以完成轉帳。

要注意的是，死鎖不是 bug，而是併發系統的正常現象。找到它的成因比責怪它更重要。從剛才的復現可以看出，環是怎麼形成的：兩個交易對同一批資源用了相反的加鎖順序。

怎麼預防死鎖：三個開發習慣

既然死鎖來自「相反的加鎖順序」與「鎖持有太久」，防治策略也就繞著這兩點走：

  1. 固定順序加鎖：規定所有交易都按同一個順序（例如 id 由小到大）去更新資料。大家都先鎖 id=1 再鎖 id=2，就不可能出現一方等 id=1、一方等 id=2 的交叉。
  2. 大事務拆小：鎖的持有時間越短，發生衝突與死鎖的機率越低。能在一段邏輯裡做完的事，不要拆成一個拖很久的長交易；尤其不要在持有鎖的情況下呼叫外部介面。
  3. 一次性鎖定：如果業務允許，盡量一次把需要的資源都申請完，而不是邊做邊拿。資料庫層面不容易做到，但在應用層可以用分散式鎖先把整組資源圈起來。

這三條之外，還有一個實務守則：在程式裡妥善處理死鎖異常，遇到 Deadlock found 時做有限次數的重試，而不是直接把錯誤丟給使用者。因為資料庫已經幫你回滾了其中一方，重試通常就能成功。

樂觀鎖：底層也有行鎖，為什麼還叫樂觀？

死鎖、等待、互斥，這些都是「先防賊、再做事」的思路，我們稱之為悲觀鎖：一開始就預設有人會來搶，所以先把資源鎖住。另一種思路則相反，先假裝天下太平，等真正要寫入的那一刻才檢查有沒有衝突，這就是樂觀鎖。

先釐清一個常見的困惑：樂觀鎖不是 MySQL 資料庫層自帶的功能（像 SELECT ... FOR UPDATE 那樣的悲觀鎖才是）。樂觀鎖本質上是一種應用層的邏輯設計，通常靠 CAS（Compare-And-Swap）的思路實現，最常見的做法是在表裡加一個 version 欄位。

流程是這樣的：

  1. 讀資料：SELECT id, value, version FROM table WHERE id = 1;，假設讀出來 version 是 1。
  2. 記憶體計算：在應用層把 value 算成新值，這段期間完全不加鎖。
  3. 原子更新：UPDATE table SET value = new_value, version = version + 1 WHERE id = 1 AND version = 1;

關鍵在第三句的 WHERE version = 1。如果這段期間沒有別人改過，更新會成功，影響行數是 1；如果別人搶先把 version 改成 2 了，這個條件就對不上，更新的影響行數是 0，應用層就知道「資料被別人動過」，可以選擇重試或報錯。

為什麼底層加了行鎖還叫「樂觀」？

你可能會想：那句 UPDATE 執行時，InnoDB 明明也對 id=1 加了行級排他鎖，這不也是鎖嗎？沒錯，但差別在於鎖持有的範圍與時間長短。

比較點悲觀鎖樂觀鎖
加鎖起點SELECT 時就 FOR UPDATE讀取與計算階段完全不加鎖
鎖持有時間查詢到提交的全程僅 UPDATE 那一瞬間
衝突處理一開始就排隊等鎖靠版本條件不符後重試
適合場景寫衝突高的場景讀多寫少的場景

悲觀鎖從 SELECT ... FOR UPDATE 就開始持鎖，一路蓋住「查詢 → 業務邏輯處理（可能包含網路傳輸、呼叫第三方）→ 更新 → 提交」的全程。如果業務處理很慢，這行資料就被鎖死很久，其他人完全進不來。樂觀鎖則只在最後執行 UPDATE 的那一瞬間借用資料庫的行鎖，毫秒甚至微秒級，之後立刻釋放。

它之所以叫「樂觀」，是因為它樂觀地假設業務處理期間不會有人來改資料。萬一真有人改了，就靠版本條件造成的「影響行數為 0」來兜底。所以樂觀鎖本質上是用「更短的鎖時間」和「應用層的重試成本」，去換「更高的併發讀取能力」。它非常適合讀多寫少的場景；但如果寫衝突本身就很頻繁，大量重試反而會白耗 CPU，那種情況用悲觀鎖更划算。

小結

死鎖的本質是等待關係繞成環，最典型的是 AB-BA 交叉：兩交易以相反順序鎖住同一組資源。InnoDB 用 wait-for graph 檢測環，並回滾代價較小的一方。防治靠固定順序加鎖、大事務拆小、一次性鎖定，並在應用層對死鎖異常做有限重試。樂觀鎖是應用層的 CAS 邏輯，用 version 欄位搭配 WHERE version = old 判斷影響行數；它只在 UPDATE 瞬間持有行鎖，與悲觀鎖的差別在於鎖的持有時間，適合讀多寫少的場景。

到這裡，事務、MVCC 與鎖這條線就完整了：我們從 ACID 的四套機制出發，走過隔離級別與三種異常，拆解了 MVCC 的版本鏈與 ReadView，攤開了 MySQL 的鎖分類，最後用死鎖與樂觀鎖收尾。當你再被問到「MySQL 怎麼保證隔離性」，可以沿著「隔離級別 → 讀走 MVCC、寫走鎖 → RR 的 Next-Key 與幻讀邊界」這條線一路講下去，而不是零散地背名詞。
