隔離級別與三種異常：髒讀、不可重複讀、幻讀

Step 2/5 · 事務、MVCC 與鎖

學習目標

能用「假資料、變資料、新資料」分辨髒讀、不可重複讀與幻讀，並說出四種隔離級別各自攔下哪些異常、MySQL 預設是哪一級。

前言：兩個視窗在改同一筆餘額

上一節講到，隔離性是靠「寫寫用鎖、讀寫用 MVCC」撐起來的。但「互相干擾」這句話還是很抽象。到底什麼叫干擾？我們用一個具體場景來看。

想像你開兩個資料庫連線，模擬兩個使用者。使用者 A 正在把某個帳戶的餘額從 100 改成 200，但還沒提交；這時候使用者 B 去查這筆餘額，他會看到多少？如果 A 最後反悔回滾了，B 剛才看到的數字算不算數？換一個順序：B 先查了一次是 100，A 改成 200 並提交，B 再查一次變 200，同一個交易裡兩次查詢結果不同，這又該不該允許？

這些「多個交易同時跑，讀到的東西不如預期」的情況，資料庫把它歸納成三種典型病症。搞懂這三種病症，才看得懂隔離級別到底在防什麼。

三種併發異常：假資料、變資料、新資料

這三種病症經常用一句話來記：髒讀是讀到「假資料」，不可重複讀是讀到「變資料」，幻讀是讀到「新資料」。 下面逐一拆開。

髒讀：讀到別人還沒提交的草稿

交易 A 把餘額從 100 改成 200，但還沒提交。這時交易 B 進來，讀到了 200。結果 A 後來反悔、執行回滾，餘額變回 100：那 B 剛才讀到的 200 就是一份從未真正存在的髒資料。所謂髒讀，就是讀到了別人的「臨時草稿」。

不可重複讀：同一筆資料前後變了樣

交易 A 第一次讀餘額是 100。接著交易 B 把餘額改成 200 並提交。交易 A 再讀一次，發現變成 200 了。在同一個交易裡，同樣的查詢，前後結果竟然不同，這破壞了交易應有的「快照感」。不可重複讀針對的是 UPDATE 或 DELETE：資料本身被改動了。

幻讀：查詢結果無中生有多出幾筆

交易 A 統計表裡有幾個人，得到 5 筆。這時交易 B 插入一個新人並提交。交易 A 再統計一次，變成 6 筆了。A 覺得見鬼了：剛才明明只有 5 筆，怎麼憑空冒出一個？幻讀針對的是 INSERT：不是既有資料被改，而是「符合查詢條件的新列」冒了出來。

把這三種病放在一起比較，關鍵差異在下表：

異常一句話觸發操作解法方向
髒讀讀到未提交的假資料別人 UPDATE 未提交只能讀已提交版本
不可重複讀同一筆前後變了樣UPDATE／DELETE鎖住滿足條件的行
幻讀結果多出／少了幾筆INSERT連行之間的空隙一起鎖

這裡有一個面試很愛追問的細節：不可重複讀和幻讀到底差在哪？ 差在「被改動的是什麼」。不可重複讀是同一批行被改，所以只要鎖住那些行就能解決；幻讀是冒出了新行，你鎖住現有的行也沒用，因為新行還不存在、鎖不到，所以必須進一步鎖住行與行之間的空隙，讓別人插不進來。這個「空隙鎖」就是下一節之後會反覆出現的 Gap Lock。

四種隔離級別：一級一級往上加保險

既然有這些病，資料庫乾脆提供四個隔離檔次，讓你在「安全」與「效能」之間選。原則是：級別越高，資料越安全，但速度越慢；級別越低，跑得越快，但越容易出錯。

隔離級別機制仍可能出現的問題誰在用
Read Uncommitted（讀未提交）別人未提交的修改也看得到髒讀幾乎沒人用
Read Committed（讀已提交）只讀已提交的資料不可重複讀Oracle、PostgreSQL 預設
Repeatable Read（可重複讀）交易開始時拍一張快照理論上有幻讀MySQL 預設
Serializable（串行化）所有交易排隊執行理論上沒有極高安全需求的金融系統

Read Uncommitted（讀未提交）最寬鬆，別人改到一半、還沒提交的資料你也可以讀。這就直接導致髒讀，生產環境幾乎不使用。

Read Committed（讀已提交）要求對方提交後你才看得到，髒讀被解決了。但它仍會出現不可重複讀：第一次讀 100，別人改並提交之後，第二次就讀到 200。這個級別是 Oracle、PostgreSQL 的預設值，不少網路公司為了追求高併發，也會刻意把 MySQL 調成它。

Repeatable Read（可重複讀）是 MySQL 的預設級別。它的做法是：交易一開啟就拍一張「快照」，之後不管你外面怎麼改，我在這個交易裡看到的都固定是開始那一刻的樣子。這就解掉了不可重複讀。按照 SQL 標準，這個級別理論上仍擋不住幻讀，但 MySQL 的 InnoDB 透過 MVCC 加上 Next-Key Lock，已經能在絕大部分場景中把幻讀也處理掉，這是常被當成加分項的重點。

Serializable（串行化）最嚴格，乾脆讓所有交易排隊一個一個跑，讀加讀鎖、寫加寫鎖，所有併發問題理論上都消失。代價是效率極低，就像所有人排隊進一間單人廁所，除非是安全級別極高的場景，否則不會使用。

級別的選擇本質是取捨

看完四級，你可能會想「那全部用最嚴格的 Serializable 不就好了」。問題是隔離級別本質上是一場交易：你買到多少安全，就要付多少效能。級別越嚴格，代表鎖越多、排隊越久、死鎖越容易發生，系統能承受的同時連線就越少。

反過來說，也要注意一個容易搞混的點：級別高不等於「一定比較慢」。例如 RC 每次查詢都要重做一份可見性判斷，理論上比 RR 多做工，但在真正的併發壓力下，RC 往往反而比 RR 快，因為 RR 為了防幻讀加了太多間隙鎖，讓大家頻頻排隊。這個反直覺的現象，等到講完鎖的那一節會完整解釋。

小結

三種併發異常可以用一句話記住：髒讀讀到假資料、不可重複讀讀到變資料、幻讀讀到新資料。不可重複讀針對 UPDATE／DELETE，鎖住滿足條件的行即可；幻讀針對 INSERT，必須連行之間的空隙一起鎖。四種隔離級別（RU／RC／RR／Serializable）就是四種安全與效能的取捨檔次，MySQL 預設是 Repeatable Read，且 InnoDB 用 MVCC 加 Next-Key Lock 解決了大部分的幻讀。

提到好幾次的 MVCC，下一節終於要拆開來看：一份資料到底是怎麼同時存在多個版本，資料庫又憑什麼決定一條查詢該讀到哪個版本。
