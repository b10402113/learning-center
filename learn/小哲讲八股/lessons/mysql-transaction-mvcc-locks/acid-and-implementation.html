ACID：四個承諾與 InnoDB 的四套機制

Step 1/5 · 事務、MVCC 與鎖

學習目標

能講出 ACID 四特性各自對應的 InnoDB 機制（Undo Log、Redo Log／WAL、鎖與 MVCC），並說清楚為什麼「一致性」不是一套獨立機制，而是前三者的共同結果。

前言：兩行 UPDATE 背後的承諾

先看一個你大概寫過的轉帳功能：從 A 帳戶扣 100 元，再把這 100 元加進 B 帳戶。程式碼拆開來就兩句 UPDATE，看起來再簡單不過。但上線之後，客訴開始出現：有人說錢扣了、對方卻沒收到；有人說餘額明明還有 500，卻只能領出 400；還有人說他看到的數字過了一秒又變了。

這些問題都不是 SQL 語法寫錯，而是「同時」發生的交易在互相干擾，或是「做到一半」的時候機器出了狀況。資料庫用一組承諾來描述「一個交易應該可靠到什麼程度」，這組承諾就是 ACID。面試問 ACID，真正想聽的通常不是把四個英文字背出來，而是：這四個承諾，各自靠什麼機制撐住？這一節就把四套機制對到位。

ACID 四個字各自在承諾什麼

一個交易（Transaction）指的是一組「要嘛全部成功、要嘛全部當作沒發生」的資料庫操作。ACID 就是這組操作的品質保證，四個字母分別是：

  • 原子性（Atomicity）：交易裡的操作是一個整體，不能只做一半。
  • 持久性（Durability）：只要交易提交了，就算下一秒斷電，資料也不能丟。
  • 隔離性（Isolation）：多個交易同時跑時，不能互相看到對方還沒完成的半成品。
  • 一致性（Consistency）：交易前後，資料的完整性約束不能被打壞，例如轉帳完總金額不變。

記住這四個承諾之後，重點來了：InnoDB 並不是為了每個字各寫一套系統，而是用 Undo Log、Redo Log、鎖與 MVCC 這幾樣工具去撐住前三者，一致性則是它們合作之後的結果。下面一個一個對。

原子性：Undo Log 是交易的後悔藥

原子性要解決的是「做到一半失敗」的情況。假設轉帳的第一句扣款已經執行了，第二句加款卻因為程式錯誤沒跑，此時 A 的錢少了、B 的錢沒多，總額就憑空消失了。

InnoDB 的做法是：在修改任何一筆資料之前，先記一條「反向操作」到 Undo Log（回滾日誌）。你 INSERT 一筆資料，它就記一條對應的 DELETE；你把 a=1 改成 a=0，它就記下原本是 a=1。等交易中途崩掉，或使用者手動執行 ROLLBACK，MySQL 就翻開這本帳，照著反向操作把資料還原回交易開始前的樣子。

打個比方，Undo Log 就是交易的「後悔藥」。藥不是為了治病，而是為了在事情失控時，把狀態倒回你還沒動手之前。也因為它保存的是「舊版本」，後面講 MVCC 時你會發現，它還有第二份兼職。

持久性：Redo Log 與 WAL 把慢寫變快寫

持久性要解決的是「提交之後才斷電」。你可能會直覺想：那把資料直接寫進磁碟上的資料檔不就好了？問題是磁碟上的資料頁是散落各處的，每次修改都去動它，等於讓磁頭到處亂跳，這種隨機 I/O慢到會拖垮整個系統。

InnoDB 改用一套叫 WAL（Write-Ahead Logging，預寫日誌） 的規則，核心只有一句話：先寫日誌，再寫磁碟。修改資料時，它先不碰資料檔，而是把變更記錄追加到 Redo Log（重做日誌） 的尾端，再回報交易成功。日誌是追加寫入的，這是順序 I/O，速度比隨機 I/O 快上許多。真正的資料頁則由背景執行緒慢慢、批次地刷回磁碟。

你可以把它想成老派掌櫃的記帳法：客人來賒帳，掌櫃先在手邊的「流水帳」上快速記一筆，等晚上打烊有空了，再把流水帳謄寫到正式的「總帳」上。日後要對帳或帳本毀了，翻流水帳就能重新抄一遍。Redo Log 就是那本流水帳，它是固定大小的檔案，採「循環寫」，寫滿一圈就覆蓋最開頭，因為它的任務只是崩潰恢復，不需要永久保留所有歷史。

隔離性：寫寫靠鎖，讀寫靠 MVCC

隔離性要處理的是「同時進行的交易互相干擾」。這裡要拆成兩種情境來看，因為它們用的手段不同。

第一種是寫和寫的衝突。兩個交易想改同一行資料，總不能讓它們同時改，否則誰覆蓋誰說不準。這種情況靠鎖來排隊，行鎖保證同一行同一時間只有一個交易能改。

第二種是讀和寫的衝突。如果每次有人要改資料，所有想讀的人就得排隊等，系統吞吐量會非常難看。InnoDB 於是用 MVCC（Multi-Version Concurrency Control，多版本並發控制） 來解：它讓讀取的人去看資料的歷史快照，寫入的人去改最新版本，兩邊互不阻塞。於是「讀的時候可以寫、寫的時候可以讀」，隔離性守住了，效能卻沒有犧牲。MVCC 的細節會在第三步展開。

一致性：不是一套機制，而是總目標

最後一個字最容易被誤解。很多人以為一致性也對應某個元件，像是「一致性靠 XX 模組」。其實它不是一套獨立機制，而是前面三個承諾都做到之後，自然得到的結果。

回到轉帳：如果原子性沒做好，扣了款卻沒入帳，資料就不一致；如果隔離性沒做好，兩個交易交錯讀寫，可能把餘額算錯；如果持久性沒做好，提交後斷電丟了資料，餘額也對不上。所以一致性是「目的」，原子性、持久性、隔離性是「手段」。面試時若能講出這一層，就比只會條列四個名詞的人高一階。

小結

ACID 是交易的四大承諾。InnoDB 的對應關係是：原子性靠 Undo Log 記下反向操作以便回滾；持久性靠 Redo Log 搭配 WAL「先寫日誌再寫磁碟」，把隨機寫變成順序寫；隔離性對寫寫衝突用鎖、對讀寫衝突用 MVCC；而一致性不是獨立機制，是前三個特性共同保證的總目標。

不過「隔離性」這三個字還是太籠統了。所謂「互相干擾」到底長什麼樣子？下一節會用三種具體的病症把講清楚：髒讀、不可重複讀、幻讀，再對照四種隔離級別，看看各級別分別攔下了哪些病。
