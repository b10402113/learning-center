MVCC：隱式欄位、版本鏈與 ReadView

Step 3/5 · 事務、MVCC 與鎖

學習目標

能拆解 MVCC 的隱式欄位與 Undo Log 版本鏈，套用 ReadView 可見性規則判斷某個版本看不看得到，並解釋 RC 與 RR 只差在生成 ReadView 的時機。

前言：為什麼有人正在改，我還能讀？

上一節留下一個問題：MySQL 預設的可重複讀，是怎麼做到「同一個交易裡，不管外面怎麼改，我讀到的永遠是開始那一刻的樣子」？更進一步問：如果一條執行緒正在改某一行，另一條執行緒去讀同一行，為什麼通常不用排隊等？

如果只有鎖，答案會很悲觀：讀的人要等寫的人放鎖，寫的人要等讀的人放手。這種「讀寫互相阻塞」的模型，在高併發下幾乎無法運作。InnoDB 靠的不是更聰明的鎖，而是換一個思路：它讓每一行資料都保留多個歷史版本。你讀你的舊版本，我改我的新版本，互不干涉。這套機制就是 MVCC（多版本並發控制）。這一節要把它的三個零件全部拆開：隱式欄位、Undo Log 版本鏈、ReadView。

零件一：每行資料都藏了兩個欄位

InnoDB 在每一行資料後面，都偷偷加了幾個你看不見的欄位，其中對 MVCC 最關鍵的是兩個：

  • DB_TRX_ID（事務 ID）：記錄「最後一次修改這行資料的是哪個交易」。
  • DB_ROLL_PTR（回滾指標）：指向 Undo Log 裡這行資料的「上一個版本」。

這兩個欄位是整個 MVCC 的地基。第一個告訴你「這行是誰改的」，第二個則像一條繩子，把同一個資料列的所有歷史版本串在一起。哪怕這行資料被改了 100 次，順著指標就能一路追到最原始的樣子。

零件二：Undo Log 串出「版本鏈」

延續上一節提過的 Undo Log：當你更新一行資料，InnoDB 不會直接蓋掉舊值，而是先把舊版本複製進 Undo Log。新的資料行用 DB_ROLL_PTR 指向這個舊版本，舊版本又可以再指向更舊的版本。於是一個資料列的所有版本，就被串成了一條鏈表，這就是所謂的版本鏈。

鏈頭是最新的資料，鏈尾是最老的資料。有了這條鏈，資料庫就能同時「存在」這行資料的很多個過去。使用者的查詢要讀哪一個，就交給下一個零件決定。

零件三：ReadView 決定你該看哪個版本

版本鏈上有 10 個版本，一條查詢進來，到底該讀哪一個？這需要一個裁判，這個裁判就是 ReadView（讀取視圖）。

當交易發起一次快照讀（也就是普通的 SELECT）時，MySQL 會生成一個 ReadView，裡面主要記錄「當前系統裡還有哪些交易是活著的、也就是還沒提交的」。這些活躍交易的 ID 集合，通常記作 m_ids。有了這份名單，就能對版本鏈上每個版本的 DB_TRX_ID 做可見性判斷。

可見性判斷規則

假設當前資料行的事務 ID 是 trx_id，判斷流程可以這樣記：

  1. 如果 trx_id 小於當前最小的活躍交易 ID：代表改這行資料的人早就提交了，這是最老、已經定案的資料，判定為可見。
  2. 如果 trx_id 大於當前交易自己的 ID：代表這是「未來」才出現的新交易改的，在我開始之後才發生，判定為不可見。
  3. 如果 trx_id 落在中間範圍，就查活躍事務列表 m_ids：
    • 在列表裡：改這行的人還沒提交，判定為不可見（這就是防髒讀的關鍵）。
    • 不在列表裡：雖然 ID 比我大，但它其實已經提交，判定為可見。

如果判定「不可見」，就順著 DB_ROLL_PTR 往版本鏈的上一個版本找，再套一次同樣的規則，直到找到第一個可見的版本為止。這條「找不到就往前翻」的路徑，就是為什麼你能讀到「過去的資料」：你讀的其實是 Undo Log 裡保存的舊版本，而不是現在的資料列。

RC 與 RR 的差異：只差在「什麼時候拍快照」

這裡有個很漂亮的收斂：Read Committed 和 Repeatable Read 這兩個級別，用的都是同一套 MVCC 機制，差別只有一個：生成 ReadView 的時機不同。

級別ReadView 生成時機結果
Read Committed每次執行 SELECT 都重新生成一份能看到別人剛提交的新資料
Repeatable Read只有交易裡第一次 SELECT 生成，之後重複使用看到的永遠是交易開始時的樣子

RC 每次查詢都重新拍快照，所以別人一提交，我下一查就看得見，這正是它產生「不可重複讀」的原因。RR 只在第一次查詢時拍一張，後面不管查幾次都拿同一張來判斷，於是同一筆資料在我眼裡始終不變，不可重複讀就被擋住了。

這也回答了一個常被追問的細節：RR 下會不會看到新插入的資料？對快照讀（普通 SELECT）來說不會，因為新交易的 ID 落在我的 ReadView 名單裡，判定不可見。這就是 RR 靠 MVCC 防幻讀的原理。

快照讀與當前讀：兩種讀，兩套防線

但小心，MVCC 只保護得了「快照讀」。InnoDB 把讀取分成了兩種模式：

  • 快照讀（Snapshot Read）：一般的 SELECT。靠 MVCC，讀的是 ReadView 認可的歷史版本。
  • 當前讀（Current Read）：SELECT ... FOR UPDATE，以及 UPDATE、DELETE。它不看歷史版本，只看最新的資料，並且會加鎖。當前讀防幻讀靠的是 Next-Key Lock，不是 MVCC。

多數情況下，這兩條防線各司其職，幻讀看不到。但在一個很刁鑽的操作順序下，幻讀還是會「漏網」，這個案例能測出你到底懂不懂快照讀與當前讀的差別。

RR 下幻讀漏網的邊界案例

假設有一張 teacher 表：

  1. 交易 A 開啟，執行 SELECT * FROM teacher WHERE id = 5，結果是空的。此刻 A 生成了自己的 ReadView。
  2. 交易 B 開啟，插入一筆 id = 5 的資料並提交。
  3. 交易 A 執行 UPDATE teacher SET name = 'X' WHERE id = 5。關鍵來了：UPDATE 是當前讀，它看得到 B 剛提交的那筆資料，所以更新成功；而這次更新，會把該行的 DB_TRX_ID 改成 A 自己的 ID。
  4. 交易 A 再執行 SELECT * FROM teacher WHERE id = 5。這次 MVCC 拿版本鏈一查，發現「這行的交易 ID 不就是我自己嗎」，判定可見。

結果就是：A 第一次查不到，第二次卻查到了。幻讀就這樣漏了出來。這個案例說明，一套機制管快照讀、一套機制管當前讀，只要「先快照讀、再當前讀更新、再快照讀」混著走，就可能繞過防線。面試時能講出這個邊界，通常就代表你真的理解 MVCC，而不是背課文。

小結

MVCC 的目標是「讀寫互不阻塞」。它由三個零件組成：每行資料的隱式欄位 DB_TRX_ID 與 DB_ROLL_PTR、由 Undo Log 串起的版本鏈，以及判斷可見性的 ReadView。判斷時拿版本的 trx_id 去比對「最小活躍 ID、自己的 ID、活躍事務列表」，不可見就沿版本鏈往前找。RC 與 RR 都用這套機制，只差在 ReadView 的生成時機：RC 每次 SELECT 重拍，RR 只在第一次拍、之後重複使用。另外要分清楚快照讀走 MVCC、當前讀走 Next-Key Lock，兩者混用時仍可能漏出幻讀。

到這裡我們一直在講「讀」這一側。但當兩個交易都要「寫」同一批資料時，靠的就不是版本鏈，而是鎖。下一節要把 MySQL 的鎖從粒度、互斥屬性到行鎖演算法完整攤開，並解釋 RR 的 Next-Key Lock 為何讓它比 RC 更容易塞車。
