InnoDB 的鎖：粒度、屬性與行鎖演算法

Step 4/5 · 事務、MVCC 與鎖

學習目標

能用粒度、互斥屬性、行鎖演算法三個維度講清 MySQL 的鎖分類，並說明 RR 的 Next-Key Lock 為何讓它比 RC 更容易塞車與死鎖。

前言：改一行，為什麼卡住另一個不相干的查詢？

有個線上事故你一定聽過：某個工程師在業務低峰期執行了一條 ALTER TABLE，想幫一張大表加個欄位。指令送出去之後，那張表上的所有查詢突然全部卡住，接著整個服務開始超時，最後只能緊急重啟。他明明只是「改表結構」，為什麼會把讀取也一起鎖死？

又或者，你的服務明明只 UPDATE 了 id=1 這一筆資料，另一個交易却在改 id=5 時被卡住。兩個交易操作的根本不是同一行，怎麼會互相妨礙？

要回答這些問題，得先知道 MySQL 的鎖不是只有一種。它橫跨了「鎖多大範圍」「允不允許別人讀」「用什麼演算法鎖」，三個維度各自有不同種類。搞混其中任何一個，就會對線上行為做出錯誤的預測。這一節按這三個維度逐一拆解，這也是回答「MySQL 有哪些鎖」這道題的標準骨架。

維度一：按鎖的粒度分，從整棟大樓到單一房間

把鎖想成一棟大樓的門禁系統：有的鎖管整棟樓，有的鎖管一層樓，有的鎖只鎖一個房間。鎖的粒度就是這個概念，而粒度越細，能同時做事的人越多。

粒度範圍常見形式特點
全局鎖整個資料庫實例FLUSH TABLES WITH READ LOCK全庫唯讀，多用於備份
表級鎖整張表表鎖、MDL 元資料鎖開銷小、加鎖快，衝突機率高
行級鎖單一索引記錄InnoDB 的行鎖開銷大，但併發度最高

全局鎖讓整個資料庫進入唯讀狀態，其他連線的增刪改全部阻塞。它最典型的用途是做全庫的邏輯備份，確保備份期間資料不會被改動。實務上因為代價太高，已經很少直接使用。

表級鎖鎖住整張表，成本低、加鎖快，而且不會產生死鎖，但代價是鎖衝突的機率很高、併發度低。MyISAM 引擎就只支援表鎖。表級鎖裡除了顯式用 LOCK TABLES ... READ/WRITE 加的鎖，還有一個隱形卻極危險的角色：MDL（Metadata Lock，元資料鎖）。

MDL 不用你手動加，它是自動的：執行 SELECT 時自動加上 MDL 讀鎖，修改表結構（ALTER TABLE）時自動加 MDL 寫鎖。問題在於讀鎖與寫鎖互斥，而 MDL 要等交易提交才釋放。所以只要有一個交易還在跑、還沒提交，它身上的 MDL 讀鎖就會擋住後面所有想 ALTER TABLE 的請求；而排隊等 MDL 寫鎖的 ALTER，又會反過來擋住它後面新進來的查詢。前言那個「改個表結構就把整張表鎖死」的事故，元凶就是它。這也是為什麼 DDL 要在離峰時段、用工具分批執行。

行級鎖是 InnoDB 最核心的特性，鎖的是具體的索引記錄，範圍最小、併發度最高。代價是加鎖開銷大、鎖管理複雜，也比較容易發生死鎖。要注意一個常見誤解：行鎖鎖的是索引記錄，不是「你以為的那一列資料」；如果查詢沒走到索引，InnoDB 可能得掃過大量記錄再一一上鎖，效果就接近鎖全表了。

維度二：按互斥屬性分，S 鎖與 X 鎖

第二個維度看的是「這把鎖允許別人做什麼」。最基本的兩種是共享鎖與排他鎖。

  • 共享鎖（S 鎖，讀鎖）：我讀的時候，別人也只能讀，不能改。多個 S 鎖可以同時持有。
  • 排他鎖（X 鎖，寫鎖）：我改的時候，別人既不能讀（指加鎖讀）也不能改。X 鎖與任何鎖都互斥。

除此之外，InnoDB 還引入了一種意向鎖（Intention Lock），它比較特別：它是表級鎖，但作用不是保護資料，而是為了提高「加表鎖」的效率。當你想對整張表加鎖時，如果沒有意向鎖，資料庫得一行一行去檢查有沒有人鎖了某筆記錄，非常沒效率。有了意向鎖，只要看表頭上有沒有標記，就知道這張表裡有沒有人正在鎖行。

意向鎖分成兩種，剛好對應兩種行鎖：IS（意向共享鎖）表示「我打算在某行加 S 鎖」，IX（意向排他鎖）表示「我打算在某行加 X 鎖」。它們只在加表鎖與加行鎖的判斷上起作用，日常開發不會直接碰到。

維度三：按 InnoDB 行鎖演算法分，三種演算法

第三個維度最核心，也是面試區分高手的地方。InnoDB 在可重複讀（RR）級別下，為了處理併發問題，實作了三種行鎖演算法：

  1. Record Lock（記錄鎖）：鎖住單一的索引記錄。例如 UPDATE ... WHERE id = 1 就把 id=1 那筆鎖住。
  2. Gap Lock（間隙鎖）：鎖住索引記錄之間的空隙。例如鎖住 5 到 10 之間的區間，別人想在這裡插入 7 就會被擋住。它唯一的目的就是防止幻讀，因為幻讀來自 INSERT，而 INSERT 進來的正是某個空隙。
  3. Next-Key Lock（臨鍵鎖）：Record Lock 加上 Gap Lock，也就是「鎖住記錄本身，加上它前面的空隙」，形成一個左開右閉的區間。這是 InnoDB 在 RR 級別下的預設加鎖單位。

回到前言那個疑問：為什麼我改 id=1，卻可能卡住改 id=5 的交易？因為在 RR 下，加的往往是 Next-Key Lock，它不只鎖住 id=1 這筆記錄，還鎖住它前面的空隙。如果 id=5 正好落在某個被鎖住的間隙裡，即便不是同一行，插入或修改一樣會被擋下。這就是「操作不同行卻互相卡住」的原因。

為什麼 RC 的效能通常比 RR 好？

這裡可以回答前面埋的伏筆。RC 每次查詢都要重新生成 ReadView，理論上比 RR 多做工，但在高併發環境下，RC 的效能往往反而更好。原因幾乎全在鎖：

比較點RR（可重複讀）RC（讀已提交）
行鎖算法預設 Next-Key Lock（含間隙）關閉間隙鎖，只用 Record Lock
鎖衝突範圍非同一行也可能因落在同間隙而衝突只有真的動到同一行才衝突
死鎖機率高，間隙鎖讓等待關係變複雜低，關係單純
不匹配記錄的鎖掃過就加鎖，到交易提交才釋放不滿足條件的行立刻釋放鎖

第一，鎖的範圍不同。RR 為了防幻讀預設開啟 Next-Key Lock，連間隙一起鎖，於是兩個交易就算操作的不是同一行，只要落在同一個間隙裡也會衝突。RC 則關閉了間隙鎖，只用 Record Lock，你改 id=1 我就只鎖 id=1，不誤傷 id=2，鎖衝突機率大幅下降。

第二，死鎖機率不同。RR 因為有間隙鎖，常出現「A 等 B 的間隙、B 等 A 的行鎖」這種複雜循環，是死鎖的高發區；資料庫偵測死鎖、回滾交易的代價並不小。RC 少了間隙鎖，死鎖機率低很多。

第三，不匹配記錄的鎖釋放機制不同。假設執行 UPDATE user SET age = 10 WHERE age > 20，掃描過程中會讀到一些不滿足條件的行。RR 會把這些掃過的行也鎖住，直到交易提交才放；RC 則做了優化：一旦引擎層發現某行不滿足 WHERE 條件，就立刻釋放它的鎖，不必等到交易結束。這讓 RC 的鎖持有時間更短。

所以「RC 比較快」不是因為可見性判斷便宜，而是因為它少鎖了很多不必要的東西。這也是為什麼不少網路公司會把 MySQL 從預設的 RR 改成 RC，用「接受不可重複讀、但換取更高併發」的方式來調優。

小結

MySQL 的鎖可以從三個維度記：粒度分全局鎖、表級鎖（含危險的 MDL）、行級鎖；互斥屬性分共享鎖 S、排他鎖 X，以及只為加表鎖效率服務的意向鎖 IS／IX；行鎖演算法分 Record Lock、Gap Lock、Next-Key Lock，其中 Next-Key 是 RR 的預設單位。RR 比 RC 慢，是因為 Next-Key Lock 多鎖了間隙、拉長了鎖持有時間，而 RC 關掉間隙鎖並提早釋放不匹配的鎖。

鎖的範圍一旦擴大、等待關係一旦交錯，就很容易出現一種最棘手的狀況：兩個交易各握著對方想要的鎖，誰也不肯放。下一節就用一個轉帳場景把它復現出來，講清楚死鎖怎麼被檢測與回滾，以及實務上該怎麼預防；最後再補上「樂觀鎖」這個名字很反直覺的收尾。
