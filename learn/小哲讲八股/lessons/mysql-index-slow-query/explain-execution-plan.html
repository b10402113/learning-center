用 EXPLAIN 讀懂優化器的執行計畫

索引與慢查詢優化 · Step 5/6 · 學習目標：能看懂 EXPLAIN 的 type、possible_keys/key、key_len、rows、Extra 五個核心指標，判斷一條 SQL 是不是全表掃描、聯合索引命中幾列，以及有沒有覆蓋索引或檔案排序。

前言：拿到一條慢 SQL，你要怎麼「看穿」它？

前面四節都在講原理：B+ 樹怎麼長、回表為什麼貴、最左前綴怎麼斷、哪些寫法會讓索引失效。但你到了生產現場，面對的是一條活生生、跑得很慢的 SQL。這時候光靠讀 SQL 用肉眼猜「大概是索引沒走」，並不夠可靠，你需要一個工具，把優化器「打算怎麼跑這條 SQL」攤開給你看。

這個工具就是 EXPLAIN。它不會真的執行 SQL，而是列出這條語句的執行計畫：用哪個索引、掃多少行、還有哪些額外動作。EXPLAIN 的欄位很多，但真正需要盯住的只有五個。這一節把它們一個一個拆開，並順便破除一個常見誤解：EXPLAIN 印出來的 rows 會不會偷偷讓資料庫去掃全表。

第一步：讀 type，先判斷「是不是全表掃描」

type 是最核心的性能指標，它告訴你 MySQL 是用什麼方式在找資料。它的效率由快到慢有一條明確的順序：

system > const > eq_ref > ref > range > index > ALL
type意思常見場景
system表只有一行系統表，幾乎不會遇到
const等值命中主鍵或唯一索引，一次定位WHERE id = 1
eq_refJOIN 時被驅動表用主鍵或唯一索引匹配一對一關聯
ref普通索引的等值查找WHERE name = '張三'
range索引上的範圍查找WHERE age > 18
index掃描整棵索引樹（比 ALL 好一些）覆蓋索引但無定位條件
ALL全表掃描沒有可用索引

實務上的底線是：生產環境至少要達到 range 或 ref。一旦看到 ALL，就代表發生了全表掃描，得認真優化，除非這張表真的很小（幾百行）。看到 const 是最好的等值查詢，看到 index 則要留意：它雖然掃的是索引而不是表，但仍然是把整棵索引掃一遍，資料量大時一樣慢。

第二步：看 possible_keys 與 key，確認有沒有命中索引

這一組欄位是一對「備胎與正選」。

  • possible_keys：理論上可能用到的索引，是候選名單（備胎）。
  • key：實際上真正用到的索引（正選）。

最需要警覺的情況是：possible_keys 有值，key 卻是 NULL。這代表 MySQL 明明有索引可選，最後卻決定不用。原因通常是兩類：一是你踩了上一節的索引失效（最左前綴斷了、隱式型別轉換等），讓索引失去作用；二是優化器算了成本，覺得走索引要回表太多次，不如直接全表掃描划得來。

第三步：用 key_len 判斷聯合索引到底命中幾列

key_len 表示這個索引被使用了多少位元組。對單欄位索引來說意義不大，但對聯合索引它非常好用。比如索引是 (a, b, c)，如果 key_len 很短，可能只命中了 a 這一列，後面的 b、c 因為最左前綴斷掉而沒用上。你可以用它來驗證「我以為走了三列，實際上只走了一列」這種落差。

第四步：看 rows，估算要掃多少行

rows 是 MySQL 估算為了找到結果需要掃描的行數，用來估計這個查詢的規模，數字越小越好。如果 rows 動輒幾十萬、幾百萬，通常意味著索引過濾性不好，或者需要回表的資料太多。

rows 是怎麼算的？會因此全表掃描嗎？

這裡有個很多人會誤會的地方。有人以為 EXPLAIN 既然能統計 rows，是不是偷偷把全表掃了一遍。答案是不會。InnoDB 探取的是採樣估算：它隨機抽取少量資料頁（預設約 8 頁），算出這些頁裡平均每頁有多少行、有多大的密度，再乘上總頁數，得到一個近似值。所以 rows 只是一個估計數字，不會因為執行 EXPLAIN 就觸發全表掃描。

既然是採樣，就有不準的時候。當你懷疑統計資訊過期、優化器選錯了執行計畫時，可以執行 ANALYZE TABLE 重新採樣。但要注意，大表執行它會有一定成本，不要動不動就在生產環境跑。

第五步：看 Extra，這裡有最直白的紅綠燈

Extra 是額外資訊欄，裡面藏著幾個一看就懂的關鍵字。

Extra 內容燈號意思
Using index綠燈用到覆蓋索引，不需要回表，性能最好
Using filesort紅燈無法利用索引的順序，需要額外的檔案排序，耗 CPU
Using temporary紅燈用到了臨時表，常見於 GROUP BY 或 DISTINCT，耗記憶體或磁碟

看到 Using index 就可以放心，這正是上一節講的覆蓋索引，查詢所需欄位全在索引裡，不必回表。相反的，只要出現 Using filesort 或 Using temporary，就要當成嚴重的效能訊號處理，通常得靠調整索引或重寫 SQL 來消除。

把五個指標串成一條判斷流程

實際排查時，不用一次看全部，照這個順序走就行：

  1. 先看 type：是 ALL 或 index 就要警覺，目標是 range 或 ref。
  2. 再看 key：是 NULL 就查是不是索引失效，或優化器放棄了索引。
  3. 如果是聯合索引，看 key_len：確認到底命中了幾列。
  4. 看 rows：評估掃描規模是否合理。
  5. 最後看 Extra：有沒有 Using index 這個綠燈，或 Using filesort、Using temporary 這兩個紅燈。

把這五個欄位練熟，你面對任何一條慢 SQL 都能說出一套具體的診斷，而不是只丟一句「好像沒走索引」。

小結

EXPLAIN 展示優化器打算如何執行一條 SQL，重點看五個欄位：type 判斷存取方式（底線是 range/ref，看到 ALL 就是全表掃描）；possible_keys 與 key 判斷有沒有命中索引（possible 有值而 key 為 NULL 是警訊）；key_len 判斷聯合索引命中幾列；rows 是採樣估算的掃描行數，不會觸發全表掃描，可用 ANALYZE TABLE 重新採樣；Extra 裡 Using index 是覆蓋索引的綠燈，Using filesort 與 Using temporary 是必須處理的紅燈。

有了 EXPLAIN 這個工具，我們終於可以回頭處理最棘手的兩種慢查詢：一種是分頁翻到很後面就越來越慢，另一種是明明走了索引卻依然快不起來。下一節把深分頁的成因與三種優化講清楚，並串起完整的慢 SQL 排查流程。
