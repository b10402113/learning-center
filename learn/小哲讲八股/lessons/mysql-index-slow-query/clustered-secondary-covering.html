索引即資料：聚簇索引、輔助索引、回表與覆蓋索引

索引與慢查詢優化 · Step 2/6 · 學習目標：能講清楚 InnoDB 的聚簇索引與輔助索引各存什麼、回表為什麼多一趟隨機 I/O，以及覆蓋索引如何用「查詢所需欄位都在索引裡」避免回表。

前言：同樣一個 name 索引，為什麼查的東西不一樣快？

上一節我們知道 B+ 樹很矮、查得快。但實際工作中你可能遇過一個更奇怪的現象：某一條 SQL 明明走了索引，卻還是很慢；而同事把 SELECT * 改成 SELECT id, name 之後，速度立刻快了好幾倍。索引是同一個，SQL 邏輯也一樣，差別到底在哪？

答案藏在 InnoDB「索引即資料」這個設計裡。它把資料本身直接種在索引的葉子裡，索引不只是指路的地圖。這帶來一個很特別的後果：用主鍵查和用普通欄位查，走的是兩棵不同的樹，而第二棵樹的葉子裡並沒有完整資料，於是就要「回表」。這一節要把這兩棵樹、那一趟回表，以及省掉回表的覆蓋索引講清楚。搞懂它們，你才看得懂為什麼「加索引」不一定等於「變快」。

InnoDB 的核心設計：索引就是資料本身

先建立一個畫面。InnoDB 的一張表，它的資料檔本身就是一棵 B+ 樹，這棵樹就是主鍵索引。也就是說，資料並沒有被搬到別的地方，它直接按主鍵排好、長在樹上。這種「資料和索引聚在一起」的結構，叫做聚簇索引（Clustered Index）。它的葉子節點裡裝的不是指標，而是完整的一行資料。所以你拿著主鍵去查，走到葉子節點的那一刻，所有欄位都到手了，一趟搞定。

但一張表通常不只一個索引。除了主鍵，你還會為 name、age 這些常用查詢欄位建索引，這些叫輔助索引（Secondary Index），也叫二級索引。它的葉子節點裝的是主鍵的值，而不是完整資料。

為什麼輔助索引只存主鍵，而不直接存資料行的位址？這是一個很聰明的取捨。如果存的是位址，一旦資料頁分裂、資料搬家，位址就變了，所有輔助索引都得跟著改，維護成本高得嚇人。存主鍵值就沒有這個問題：資料怎麼搬，主鍵都不會變。代價則是多了一趟「回頭查主鍵樹」的動作，這趟就叫回表。

回表：為什麼查一筆資料要跑兩棵樹？

把流程攤開來看就清楚了。假設 user 表有主鍵 id，另外給 name 建了輔助索引，現在執行：

SELECT * FROM user WHERE name = '張三';
  1. 第一趟：先去 name 的輔助索引樹裡找 '張三'。找到之後，拿到的是它對應的主鍵值，比如 id = 10，而不是完整資料。
  2. 第二趟（回表）：拿著 id = 10，再去主鍵索引樹裡查一次，這次才拿到包含 age、sex 等所有欄位的完整行。

這就是「回表」：先查輔助索引拿主鍵，再回主鍵索引拿完整資料。單筆查詢時多一趟還不致命，真正可怕的是範圍查詢。假設某個條件的資料有 10 萬筆，走輔助索引會先拿到 10 萬個主鍵，然後就得回表 10 萬次。而每一次回表，都可能是在主鍵樹裡跳到不同位置，屬於隨機 I/O。回表越多次，隨機 I/O 越恐怖，這也是很多慢查詢的真正病因。

覆蓋索引：把要查的欄位全部備齊，就免了這一趟

既然回表的痛點在「索引裡沒有我要的欄位」，那解法就很直覺：讓索引裡剛好有我需要的所有欄位。當一條 SQL 所需要用到的欄位（包含 SELECT 要輸出的欄位，以及 WHERE 用來過濾的欄位）全部都在同一個索引樹裡時，資料庫就沒有必要再回主鍵樹，直接把索引葉子裡的資料回傳即可。這種狀態叫做覆蓋索引（Covering Index）。

這裡有個很容易講錯的點：覆蓋索引不是一種特殊的索引型別，而是一種「查詢剛好被索引覆蓋住」的狀態。同一條 (name, age) 聯合索引，對某些查詢是覆蓋索引，對另一些卻不是。看個例子：

-- 建立聯合索引
ALTER TABLE user ADD INDEX idx_name_age (name, age);

-- 這個查詢會被覆蓋：name 用來找，age 直接從索引拿
SELECT age FROM user WHERE name = '張三';

執行上面這條 SQL 時，資料庫去 idx_name_age 樹裡找 '張三'，葉子節點裡本來就存著 age 的值，於是直接把它回傳，完全不需要回表。但如果查的是 SELECT age, sex FROM user WHERE name = '張三'，因為 sex 不在索引裡，就還是得回表把整行撈出來。這也解釋了前言那個現象：SELECT * 幾乎永遠無法被覆蓋索引救到，因為它要所有欄位；而只挑少數欄位就有機會命中覆蓋索引。

實務上的做法是：如果某個查詢非常高頻，而且只需要少數欄位，就把這些欄位一起建進聯合索引，人為地製造出覆蓋索引。例如業務常跑 SELECT age FROM user WHERE name = ...，那就建 (name, age)，讓查詢直接被覆蓋。

順帶對照：MyISAM 的索引長得完全不一樣

InnoDB 是「聚簇索引」，資料就在主鍵樹上；MyISAM 則是「非聚簇索引」，索引和資料是分開放的。MyISAM 的索引檔（.MYI）和資料檔（.MYD）是兩個獨立檔案，索引的葉子節點裡存的是資料行的物理位址（指標），找到索引後還得照這個位址去另一個檔案把資料讀出來。

還有一個差別：在 MyISAM 裡，主鍵索引和輔助索引的結構完全一樣，差別只在前者要求唯一、後者不要求。它們存的都是物理位址，所以 MyISAM 沒有所謂「回表」的概念，但它的索引一旦遇到資料搬移就得更新位址。把兩種引擎對照著記，你就會明白 InnoDB 為什麼堅持在輔助索引裡只存主鍵。

小結

InnoDB 的資料檔本身就是主鍵 B+ 樹，葉子存完整行，這叫聚簇索引；輔助索引的葉子只存主鍵值，所以要查完整資料時得先拿主鍵、再回主鍵樹查一次，這就是回表，代價是額外一趟隨機 I/O。當一條查詢需要的欄位全都在某個索引裡，就形成覆蓋索引，可以不回表，把查詢欄位建進聯合索引即可製造。MyISAM 則是非聚簇索引，索引與資料分離，葉子存物理位址，主鍵與輔助索引結構相同。

目前為止我們談的都是單一欄位的索引或簡單的聯合索引。但真實世界的查詢條件常常是好幾個欄位湊在一起，於是就浮現一個核心問題：聯合索引 (a, b, c) 到底怎麼運作？為什麼查 b 不查 a 就完全用不上？下一節要拆解最左前綴匹配原則的底層原因。
