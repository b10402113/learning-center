為什麼是 B+ 樹：從磁碟 I/O 反推索引結構

索引與慢查詢優化 · Step 1/6 · 學習目標：能從「資料存在磁碟上」這個前提，淘汰二叉樹、Hash、B 樹，講出 B+ 樹贏在哪，並用 16KB 頁反推樹高與實際磁碟 I/O 次數。

前言：面試官問「為什麼不用二叉樹」，你答得出來嗎？

你可能遇過這種對話。線上某張表查詢突然變慢，同事看了一眼說「索引沒走好吧」，你加了索引，情況好轉，但為什麼加了就有用、為什麼是這種資料結構，卻說不出所以然。更常見的是面試場景：面試官問「MySQL 為什麼用 B+ 樹當索引，而不是二叉樹、Hash 或 B 樹？」如果只回一句「因為 B+ 樹比較快」，這個問題的追問才正要開始。

要答得漂亮，不能從「哪個資料結構比較酷」出發，而要從一個物理事實出發：資料存在磁碟上，而磁碟很慢。整個索引結構的選型，本質上都在回答同一個問題：怎樣用最少的磁碟讀取次數，找到你要的那筆資料。這一節就沿著這條線，把二叉樹、Hash、B 樹一個個請下場，最後看 B+ 樹憑什麼留下來，並且實際算給你看：一棵存了上千萬行的表，樹到底有多高。

先把前提講清楚：為什麼一次磁碟 I/O 這麼貴？

記憶體的讀取是奈秒等級，磁碟的一次隨機讀取卻是毫秒等級，兩者差了十萬倍以上。這代表只要一次查詢多讀幾次磁碟，時間就會被拖垮。資料庫因此把資料切成一頁一頁來管理，InnoDB 預設一頁是 16KB，每次讀寫至少以頁為單位。你只要記住這兩個數字：磁碟很慢、一頁 16KB。後面所有的推導都從這裡長出來。

另外還要先認識一個詞：索引的樹高（Depth）。樹高有幾層，代表從根走到葉子要經過幾個節點。如果每個節點都放在磁碟上，樹高幾乎就等於「要讀幾次磁碟」。所以資料結構的目標很明確：把樹壓矮。

第一個被淘汰的：二叉樹（含紅黑樹、AVL 樹）

二叉樹的規則是每個節點最多分兩個叉，左邊小、右邊大，查詢時一層層往下比。它的邏輯很漂亮，問題出在「每個節點只能分兩個叉」這件事上。假設你有一千萬行資料，這棵樹會長成一個又瘦又高的形狀，樹高可能到 20 層。資料又在磁碟上，於是每查一次就要讀 20 次磁碟。就算一次只要 10 毫秒，20 次就是 0.2 秒，對資料庫來說這慢到無法接受。

紅黑樹、AVL 樹這類平衡二叉樹只能讓樹「不歪」，沒辦法讓它「變矮」，因為分叉數被鎖死在 2。資料量一大，樹高就跟著漲，這是它天生的天花板。

第二個被淘汰的：Hash 表

Hash 表看起來很有希望，因為等值查詢極快。它把 key 丟進雜湊函式算出位置，直接跳過去，查 WHERE id = 1 是 O(1)，一步到位。既然如此，為什麼不用它當主流索引？

因為真實業務不是只有等值查詢。你經常要寫 WHERE age > 18、WHERE create_time BETWEEN ... AND ...，或者 ORDER BY 排序。Hash 的致命傷就在這裡：雜湊值本身是無序的。一個 key 算出來的位置和它的大小沒有任何關係，所以範圍查詢和排序完全借不上力，只能放棄索引、老老實實全表掃描。這就是 Hash 索引只能用在極少數等值場景、無法成為通用索引的原因。

最接近的對手：B 樹，為什麼還是輸給 B+ 樹？

B 樹已經解決了「樹太高」的問題，它是一種多路平衡查找樹，一個節點可以分很多叉，樹一下就變矮了。B+ 樹和它長得很像，但贏在兩個關鍵細節。

細節一：B+ 樹能存更多索引，所以更矮。 B 樹的每個節點裡既存索引（key）又存真正的資料（value），一個 16KB 的頁塞不下幾個節點，樹就還是會偏高。B+ 樹則規定非葉子節點只存索引，不存資料，真正的資料全部放在葉子節點。少了資料佔位，同樣一頁就能塞進更多的 key，分叉數暴增，樹自然更扁，I/O 次數更少。

細節二：B+ 樹是範圍查詢的神器。 B 樹的資料散落在樹的各層，你要查 id 從 10 到 100，就得在樹裡跳上跳下，產生大量隨機 I/O。B+ 樹把所有資料集中在葉子節點，而且葉子節點之間用雙向鏈表串起來。查範圍時只要先找到起點，之後順著鏈表往後拉就行了，這是高效的順序 I/O。一個隨機跳、一個順著拉，差距非常明顯。

結構致命傷B+ 樹的優勢
二叉樹 / 紅黑樹每層只分兩叉，樹太高，I/O 次數多多路平衡，樹高壓到 3～4 層
Hash 表雜湊值無序，不支援範圍查詢與排序索引有序，天生支援範圍與排序
B 樹非葉節點也存資料，樹偏高；範圍查詢要跳著找非葉只存 key 更矮，葉子鏈表順序掃描

算筆帳：一棵樹到底能存多少、要讀幾次

光說「B+ 樹很矮」還不夠，面試官要的是數字。我們用幾個合理假設來推：一頁 16KB；主鍵用 BigInt 佔 8 位元組，加上 InnoDB 的指標 6 位元組，一個索引項大約 14 位元組；一筆業務資料平均 1KB。

先看非葉子節點能分幾個叉：16384 ÷ 14 ≈ 1170，所以一個目錄頁能指向 1170 個下一層節點。再看葉子節點能存幾行：16384 ÷ 1024 ≈ 16，一頁放 16 行。把這兩個數字乘起來，樹的容量就出來了。

樹高容量計算大約能存
2 層1170 × 16約 1.8 萬行
3 層1170 × 1170 × 16約 2000 萬行
4 層2000 萬 × 1170約 200 億行

結論很直觀：只要資料在兩千萬行以內，樹高就是 3 層；就算是千億級的大表，4 層也綽綽有餘。所以生產環境裡 B+ 樹的高度通常落在 3 到 4 層。

那是不是每次查詢都要讀 3、4 次磁碟？不一定。關鍵在於根節點幾乎永遠常駐在記憶體（Buffer Pool）裡。三層的樹，第一次查根節點是記憶體操作，第二次查目錄頁大概率也命中記憶體，只有第三次查葉子節點才可能真的碰磁碟。所以實際的物理磁碟 I/O 通常只有 1 次，甚至 0 次。這才是「為什麼 B+ 樹查得快」最完整的說法：結構矮是一半，另一半是熱門節點被快取住了。

小結

索引結構的選型，本質是「減少磁碟 I/O」的競賽。二叉樹每層只分兩叉，樹太高；Hash 等值快但不支援範圍與排序；B 樹雖然多路，但非葉也存資料，樹仍偏高、範圍查詢是隨機 I/O。B+ 樹非葉只存 key 所以更矮，葉子用雙向鏈表串起所以範圍查詢變順序 I/O。以 16KB 頁推算，一棵 3 層的樹可存約 2000 萬行，根節點常駐記憶體後，實際物理 I/O 通常只有 1 次甚至 0 次。
