深分頁與慢 SQL：走索引為什麼還是很慢

索引與慢查詢優化 · Step 6/6 · 學習目標：能解釋 LIMIT offset 為何越翻越慢並給出延遲關聯、游標法、業務限制三種優化，說出「走了索引仍慢」的四類成因，並用慢 SQL 三步法排查。

前言：翻到第 500 頁，後台就卡死了

前五節我們把索引從裡到外講了一輪，也學會用 EXPLAIN 診斷。你可能因此產生一個錯覺：只要 EXPLAIN 的 key 不是 NULL，查詢就應該很快。但真實世界裡有兩種慢查詢，專門打臉這個錯覺。

第一種是後台報表的深分頁。使用者一路翻頁，前十頁都很順，翻到第幾百頁時頁面突然轉圈圈，資料庫 CPU 也跟著飆高。第二種更詭異：EXPLAIN 顯示索引命中、rows 也不大，查詢卻依然慢。這一節要把這兩種情況都拆開，先講深分頁為什麼「越翻越慢」以及三種救法，再把「走索引仍慢」的成因與完整的慢 SQL 排查流程收尾。

深分頁的病灶：它不是「跳過去」，而是「讀出來再丟掉」

問題出在 LIMIT offset, size 這個語法的實作方式。假設你執行：

SELECT * FROM orders LIMIT 1000000, 10;

你的直覺是「MySQL 直接跳到第 100 萬行，拿 10 筆走人」。但現實完全不是這樣。MySQL 會先查詢 offset + size，也就是先取出 1,000,010 筆資料，然後把前面的 100 萬筆全部丟掉，只留下最後 10 筆回傳給你。

這中間的浪費有兩層。第一層，如果它走的是索引，而查詢又不是覆蓋索引（例如 SELECT *），那它就得拿著這 100 萬個主鍵去回表 100 萬次，每一次都可能是隨機 I/O，這正是上一節講的回表代價被放大到極限。第二層，就算不談回表，光是「讀出來再丟掉」本身也消耗了大量 CPU、I/O，還會把無用的資料頁塞進 Buffer Pool，擠掉真正熱的資料。

結論很明確：offset 越大，要丟棄的資料越多，回表次數越多，查詢就越慢。 這就是深分頁。

三種優化：把「讀一百萬再丟」變成「只讀十筆」

方案一：覆蓋索引 + 子查詢（延遲關聯，最通用）

既然回表最耗時，那就先別回表。做法分兩段：先在索引樹上把目標那 10 筆的 id 找出來（索引樹小、不回表，速度快），再拿這 10 個 id 回主表撈完整資料。

-- 優化前（慢）：先取 100 萬筆再丟掉
SELECT * FROM orders LIMIT 1000000, 10;

-- 優化後（快）：只掃索引取得 10 個 id，再關聯取完整資料
SELECT * FROM orders t1
JOIN (SELECT id FROM orders LIMIT 1000000, 10) t2
ON t1.id = t2.id;

效果是：同樣要掃過前面那段，但這段只掃索引、不讀資料頁，最後真正回表只有 10 次。效能通常能提升幾十倍，而且它保留了「可以跳頁」的能力，是最通用的方案。

方案二：游標法 / Seek 法（性能最高，限制最大）

既然問題出在 offset，那乾脆不要 offset。不記「第幾頁」，改成記「上一頁最後一筆的 id」，查詢時用條件直接定位：

SELECT * FROM orders WHERE id > {last_id} LIMIT 10;

這樣無論翻到第幾億頁，都是走索引直接定位，時間複雜度是 O(1)，性能無敵。代價是它只能連續往後翻，不能「跳頁」（例如直接跳到第 500 頁），而且要求排序欄位是有序、連續遞增的。它適合「下一頁」這種無限滾動的場景，不適合有頁碼跳轉的後台。

方案三：業務限制或換搜索引擎（終極方案）

還有一個很務實的答案：限制深度。你看百度和 Google 搜尋，翻到七十幾頁就不讓你再翻了，因為幾乎沒有人真的會看第 1000 頁。如果業務是「只在前面幾頁找資料」，直接限制最大頁碼即可。如果真的有海量資料的搜尋需求，那就不該用 MySQL 硬扛，而是接上 ElasticSearch 這類專為全文檢索設計的引擎。

另一種慢：走了索引，為什麼還是慢？

排查時最容易被忽略的，就是「key 不是 NULL，卻依然慢」。走了索引只證明你「找」得快，但如果你要「拿」的東西太多、有人擋著你、或路本身堵住了，照樣慢。常見有四類成因。

  1. 索引區分度太低（回表代價太高）： 假設你有 100 萬行，給只有 0 和 1 兩種值的 status 建索引，查 WHERE status = 1 有 50 萬行。雖然走了索引，但要回表 50 萬次。而回表是隨機 I/O，全表掃描是順序 I/O，此時走索引反而比全表掃描更慢。MySQL 優化器有時會聰明地主動放棄索引改走全表，但它也有判斷失準的時候。
  2. 深分頁 / 大結果集： 就是前面講的 LIMIT 100000, 10，即使走了索引，也得回表讀 10 萬多行再丟掉。
  3. 鎖等待： SQL 本身沒毛病，索引也完美命中，但要查的那幾行剛好被別的事務加了排他鎖（X 鎖），或表正在被加元資料鎖（MDL 鎖）。你的執行緒只能在門口乾等。監控上顯示這條 SQL 跑了 10 秒，其實 9.9 秒都在等鎖，真正執行只花了 0.1 秒。
  4. 資料庫在刷髒頁： 平時很快的 SQL 突然偶爾變慢，可能是 Redo Log 寫滿，或 Buffer Pool 記憶體不足，MySQL 必須暫停手上的活，把記憶體裡的髒資料刷回磁碟。你的 SQL 剛好撞上，被迫等這個磁碟 I/O 完成。

把這四類記住，你就知道「走了索引還慢」不是玄學，而是回表、分頁、鎖、刷盤這四件事之一。

完整的慢 SQL 排查流程：先定位，再分析，最後看資源

最後把工具串起來。當你收到「某個介面變慢」的回報，標準的三步是這樣走的：

  1. 第一步，定位是哪條 SQL： 開啟慢查詢日誌（slow_query_log），設定門檻 long_query_time（例如 0.5 秒或 1 秒），凡是超過門檻的 SQL 都會被記錄。再用 mysqldumpslow 之類的工具，找出出現頻次最高或平均耗時最長的語句，優先處理。
  2. 第二步，分析執行計畫： 對目標 SQL 執行 EXPLAIN，重點看上一節講的五個欄位。多數慢 SQL 到這一步就能靠調索引或改寫 SQL 解決。
  3. 第三步，分析資源消耗： 如果 EXPLAIN 看起來沒問題（走了索引、掃描行數也少）卻還是慢，就輪到 SHOW PROFILE 上場。它會告訴你這條 SQL 的時間到底花在哪：是 CPU 計算、是磁碟 I/O（Sending data）、還是搶鎖（Locking）。這一步正好對應前面「走索引仍慢」的四類成因。

注意一個常見的資深加分點：MySQL 8.0 之後官方更推薦用 Performance Schema，但在面試裡能講出 SHOW PROFILE 的耗時分析，反而更能證明你懂底層。

小結

深分頁的病灶是 LIMIT offset, size 會先取出 offset+size 筆、丟掉前 offset 筆，offset 越大回表越多、越慢。三種優化是延遲關聯（先掃索引取 id 再關聯主表，可跳頁）、游標法（WHERE id > last_id，O(1) 但不能跳頁）、業務限制或改用 ElasticSearch。走索引仍慢的成因有四類：區分度低導致回表太多、深分頁、鎖等待、刷髒頁。慢 SQL 標準排查是慢查詢日誌定位、EXPLAIN 分析計畫、SHOW PROFILE 看資源耗在哪。

走完這六步，你手上有了一條完整的線：從磁碟 I/O 推出 B+ 樹，從聚簇與輔助索引推出回表與覆蓋索引，從多級排序推出最左前綴，從「變」推出索引失效與索引下推，再用 EXPLAIN 把這些變成看得見的欄位，最後用深分頁與慢 SQL 排查收束。下次被問到慢查詢，你腦中的順序會是：先看結構、再看索引、再看計畫、最後看資源與鎖。
