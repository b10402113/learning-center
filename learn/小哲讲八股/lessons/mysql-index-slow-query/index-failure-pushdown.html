索引失效的三大忌與兩個坑，加上索引下推

索引與慢查詢優化 · Step 4/6 · 學習目標：能列出讓索引失效的三大忌（列加工、前置 %、隱式型別轉換）與兩個坑（違反最左前綴、OR），並解釋索引下推如何把過濾下沉到引擎層以減少回表。

前言：索引明明建好了，EXPLAIN 卻顯示全表掃描

上一節我們講了最左前綴，那是「查詢順序對不對」的問題。但還有一種更常見的狀況：索引欄位對、查詢順序也對，EXPLAIN 的 type 卻仍然是 ALL，掃描行數幾百萬。你反覆確認索引存在，卻找不到哪裡出了問題。

這種情況，十之八九是你對索引欄位「動了手腳」，或踩到幾個很隱蔽的坑。索引失效的核心原因其實可以濃縮成一個字：「變」。只要讓資料庫覺得「原本有序的索引變得無序」，或者「必須先算出結果才能查找」，索引就廢了。這一節先把最常見的失效場景整理成「三大忌」和「兩個坑」，再補上一個專門用來救回表次數的機制：索引下推。

三大忌：這些寫法會讓索引直接報廢

第一忌：對索引列做運算或加函數

最典型也最常見。例如：

-- 對索引列做數學運算
SELECT * FROM t WHERE id + 1 = 10;

-- 對索引列套用函數
SELECT * FROM t WHERE LEFT(name, 3) = 'abc';

為什麼會失效？因為 B+ 樹裡存的是 id 的原始值，不是 id + 1 的值。你叫資料庫去找 id + 1 = 10，它沒辦法用樹直接定位，只能把全表每一行的 id 都撈出來、各自加一、再比對。把計算寫在索引列上，等於逼它放棄索引、逐行計算。正確的改法是移到等號右邊：WHERE id = 10 - 1，讓索引列保持乾淨。

第二忌：模糊查詢以 % 開頭

SELECT * FROM t WHERE name LIKE '%劉';

索引是按字串的前綴排序的，就像電話簿按姓排。你查「姓劉的」（LIKE '劉%'），它能快速翻到「劉」那一頁；但你要查「名字最後一個字是劉的」，因為不知道前面是什麼，索引的排序完全幫不上忙，只能全表掃描。前置 % 破壞了前綴匹配的能力，這就是它失效的原因。

第三忌：隱式型別轉換（最隱蔽的坑）

這個坑很多人踩過卻不知道。假設 phone 欄位是 VARCHAR，存的是字串，但查詢時你忘了加單引號：

-- phone 是字串型別，卻傳入數字
SELECT * FROM t WHERE phone = 13800000000;

MySQL 在後台會偷偷把每一行的字串轉成數字來比較。這相當於對索引列套用了一個型別轉換函數，於是就踩到第一忌，索引直接失效。正確寫法是加上引號：WHERE phone = '13800000000'。之所以說它隱蔽，是因為程式碼看起來完全沒有「計算」或「函數」，但型別轉換是悄悄發生的。

兩個坑：不那麼明顯，但一樣致命

第一個坑：違反最左前綴

上一節已經詳細講過，簡短複習：聯合索引 (a, b, c) 只查 WHERE b = 1，跳過了最左的 a，在 B+ 樹裡 b 是無序的，無法定位，自然走全表掃描。

第二個坑：用 OR 連接條件

-- 假設 id 有索引，age 沒有
SELECT * FROM t WHERE id = 1 OR age = 18;

看你可能會想：「前面 id = 1 有索引，應該能利用吧？」但資料庫必須回傳同時滿足兩個條件的所有資料。就算它靠索引找到了 id = 1 的那一筆，它還是得為了 age = 18 再做一次全表掃描。既然橫豎都要掃全表，那個索引用了也是白用，乾脆放棄。解法是讓 OR 兩邊的欄位都有索引，否則通常還是失效。

還有一個隱形殺手：優化器主動放棄索引

前面講的都是「語法讓索引用不了」，但還有一類是索引明明能用，優化器卻選擇不用。原因是它會做成本估算：如果走索引要回表太多次、隨機 I/O 的開銷比直接順序掃全表還大，它就會主動選全表掃描。典型場景是表很小，或你要查的資料佔了整張表的很大比例（例如查一個有 50 萬行的狀態值）。這不是失效，而是權衡後的選擇。但它也提醒你，索引不是加了就一定被用。

索引下推：把過濾工作下沉到引擎層

講完失效，我們回頭補上一節欠的債。對於「被最左前綴或範圍查詢斷掉」的欄位，MySQL 5.6 引入了一個補救機制，叫索引下推（Index Condition Pushdown，簡稱 ICP）。它的目的只有一個：減少回表次數。它不改變任何索引的排序規則，只是換個地方做過濾。

用一個倉庫比喻就很好懂。Server 層是老闆，儲存引擎層是倉庫管理員，兩者透過「回表」來傳遞完整資料。

  • 沒有 ICP 時： 老闆說「把所有姓張的檔案拿給我」。管理員跑進倉庫，把所有姓張的檔案（假設 100 份）都搬出來，回表取出完整內容交給老闆。老闆一份份翻：「這個年齡不對、那個也不對……」最後只剩 2 份合格，扔掉 98 份。那 98 次回表全是白費力氣。
  • 有了 ICP 之後： 老闆說「把所有姓張且 10 歲的檔案拿給我」。管理員在倉庫裡就能多看一眼：索引的葉子節點裡本來就存了 age 的值。他發現姓張的裡面只有 2 個是 10 歲，於是只搬這 2 份上樓。回表次數從 100 降到 2。

把這個過程翻成 SQL 就清楚了。假設有聯合索引 (name, age)：

SELECT * FROM user WHERE name LIKE '張%' AND age = 10;

依照最左前綴，name LIKE '張%' 是範圍查詢，匹配到 name 就停了，age 理論上用不上索引定位。也就是說，光靠索引能找到所有「姓張」的人，卻沒辦法直接鎖定 age = 10。差別就在這裡：

引擎層做什麼回表次數
沒有 ICP只找出所有姓張的，全部回表交給 Server 層過濾100 次
有 ICP利用索引裡已存的 age 先在引擎層過濾，符合才回表2 次

務必記住一句話：索引下推沒有改變索引的排序規則，age 依然不能拿去二分定位，它只是把「不符合就別回表」的判斷提前到引擎層。它是覆蓋索引之外的另一種減少回表的手段，兩者可以並存。

小結

索引失效的核心是一個「變」字：對索引列做運算或函數（含隱式型別轉換）、LIKE 以 % 開頭、違反最左前綴、OR 一側無索引，都會讓 B+ 樹失去二分查找的能力而改走全表掃描；此外優化器也可能因成本主動放棄索引。索引下推（ICP）則是在不改變排序規則的前提下，把索引中已包含欄位的過濾下沉到引擎層，讓不符合的資料不必回表，典型能把回表從 100 次降到 2 次。

到目前為止，我們講的都是「怎麼寫會讓索引有效或失效」的原理。但實際排查慢查詢時，你不可能靠肉眼猜，你需要一個工具告訴你優化器到底打算怎麼跑。下一節就來學怎麼讀 EXPLAIN 的執行計畫，把前面這些概念變成看得見的欄位。
