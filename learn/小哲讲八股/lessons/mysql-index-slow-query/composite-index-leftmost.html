聯合索引與最左前綴：多級排序在哪裡斷掉

索引與慢查詢優化 · Step 3/6 · 學習目標：能用「多級排序」解釋最左前綴匹配原則，判斷 (a,b,c) 聯合索引在 WHERE b=1、WHERE a=1 AND c=1、WHERE a=1 AND b>2 AND c=3 下各命中幾列。

前言：索引明明建了，某些查詢卻完全不買帳

上一節我們看到，一個輔助索引可以幫查詢省掉回表。於是很多人建索引的直覺是「把常一起出現的欄位都串成一個聯合索引」，例如給 (a, b, c) 建一個索引，想說這樣查 a、查 b、查 c 就都能用。結果上線後發現，只有某些查詢變快，其他照樣全表掃描。你打開 EXPLAIN 一看，key 是 NULL，滿臉問號。

問題不在索引建錯了，而在聯合索引的運作方式跟單欄位索引很不一樣。聯合索引在 B+ 樹裡是靠「多級排序」組織起來的，這套排序有嚴格的先後順序，一旦你用查詢條件跳過了前面的欄位，後面的欄位就會變成無序、沒辦法二分查找。這條規則，就是傳說中的最左前綴匹配原則。這一節除了告訴你規則是什麼，也要讓你從排序的底層理解它為什麼成立。

先建立畫面：聯合索引就是一頁電話簿

聯合索引 (a, b, c) 可以想成一本電話簿，它先按「姓」排，姓一樣的再按「名」排。或者更精確地講，它是一層一層往下排的多級排序：

  • 全局先按 a 有序；
  • 在 a 相同的一群資料裡，按 b 有序；
  • 在 b 相同的一群資料裡，再按 c 有序。

關鍵在最後一句的「反過來不成立」。你可以從 a 的秩序推出 b 的局部秩序，但如果你不知道 a 是什麼，直接看 b，它在全局就是亂的。用電話簿想像：翻到「張」那一頁，裡面的名字是有排序的；但如果你說「我要找所有名字叫『三』的人」，不管姓什麼，那這些「三」就散落在整本電話簿的各個角落，根本沒法快速翻。

規則一：不能跳過第一列

查詢條件必須從索引的最左欄位開始。對 (a, b, c) 來說：

  • WHERE a = 1：用到索引。因為 B+ 樹先按 a 排，你能直接二分定位到 a = 1 的區段。
  • WHERE b = 2：完全用不到索引，走全表掃描。因為在 a 未知的前提下，b 在全局是無序的，B+ 樹沒辦法二分查找。

用圖書館比喻更好懂：書架號是按「樓層－書架－層數」編的，a 是樓層、b 是書架。現在你只說「我要找第 1 號書架」，卻不知道在第幾層，那你只能從一樓爬到頂樓，把每一層的第 1 號書架都看一遍，這就是全表掃描。

規則二：不能跳過中間列

如果查 WHERE a = 1 AND c = 3，結果是只走一半索引：a 用到了，c 沒用到。

原因是索引的有序性是「連續」的。當 a = 1 確定後，在那個範圍內 b 是有序的，但你跳過了 b，直接看 c，此時 c 就是無序的。資料庫能靠索引快速找到所有 a = 1 的資料，但接下來只能把這些資料一筆一筆撈出來、逐個檢查 c 是不是 3。也就是說，c 在這裡的角色只是過濾條件，並沒有參與「快速定位」。這就是「只走一半」的意思：定位靠 a，過濾靠 c。

規則三：遇到範圍查詢就停止匹配（面試最大的坑）

最容易被忽略的是這一條。查 WHERE a = 1 AND b > 2 AND c = 3 時，a 用到了，b 也用到了（因為它負責範圍查找），但 c 用不到了，索引匹配會在 b 這裡斷掉。

為什麼？因為在 b > 2 的範圍裡，c 並不是全局有序的。打個比方：b = 3 時 c 可能是 5，b = 4 時 c 可能是 1，b 和 c 之間沒有統一的秩序。B+ 樹沒辦法在這種情況下用索引去直接定位 c = 3，只能先圈出 b > 2 的一大段，再一筆筆檢查 c。所以實務上的結論是：聯合索引中一旦出現範圍條件，範圍之後的欄位通常就無法再用於定位。

實戰演練：聯合索引 (a, b, c) 的兩種典型查詢

把上面的規則套到兩個常見題目上，答案就一目了然。

題目一：WHERE b = 1 會走索引嗎？ 完全不走，全表掃描。因為跳過了最左的 a，b 在全局無序，B+ 樹無從二分。這裡有個加分的例外：如果你的 SQL 是 SELECT b FROM t WHERE b = 1，因為查詢只用到 b，符合覆蓋索引，MySQL 有可能掃描整棵索引樹（Index Full Scan）來避免掃表，但這仍然不是「透過索引快速定位」，本質上是把整棵索引從頭到尾看一遍。

題目二：WHERE a = 1 AND c = 1 會走索引嗎？ 走一半。a 命中索引負責定位，c 因為跳過了中間的 b 而無序，只能當過濾條件。

查詢條件abc結果
WHERE a = 1定位——走索引
WHERE b = 1———全表掃描
WHERE a = 1 AND c = 1定位跳過過濾只走 a
WHERE a = 1 AND b = 2 AND c = 3定位定位定位三欄全命中
WHERE a = 1 AND b > 2 AND c = 3定位範圍斷掉只走 a、b

你可能會問：那被「斷掉」的 c，資料庫真的只能笨笨地逐筆過濾嗎？其實從 MySQL 5.6 開始有一個補救機制叫索引下推，它雖然不能讓 c 重新參與定位，卻能把「檢查 c = 3」這個動作下沉到引擎層先做，提早丟掉不合格的資料、減少回表。這個機制我們留到下一步連同索引失效一起講。

小結

聯合索引在 B+ 樹裡是多級排序：先按 a 排，a 相同再按 b 排，b 相同再按 c 排。由此推出最左前綴匹配原則：查詢必須從最左欄位開始（WHERE b 用不上），中間不能斷層（WHERE a AND c 只有 a 有效），且遇到範圍條件後續欄位停止匹配（WHERE a AND b>… AND c，c 斷掉）。判斷的關鍵永遠是同一個問題：在這個查詢確定的範圍內，下一個欄位到底有沒有序。

最左前綴是「用得對不對」的問題，但還有一類問題更常讓索引直接報廢：不是查詢順序不對，而是你對索引列動了手腳。下一節要整理讓索引失效的三大忌與兩個坑，並把索引下推講完。
