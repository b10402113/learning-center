主從延遲：成因與四種解法

Step 5/5 · 日誌、WAL、複製與主從

學習目標

能講出主從延遲的根本成因（主庫多線程並發寫、從庫單線程串行回放，加上大事務路障），並給出並行複製、拆分大事務、核心讀主、緩存兜底四類解法。

前言：剛註冊完，為什麼登不進去

你有沒有遇過這種客訴：使用者剛註冊完帳號，馬上點登入，系統卻回他「用戶不存在」；他等了幾秒再試一次，又正常了。你去看資料庫，帳號明明就在，資料一點問題也沒有。這種「等一下就好」的怪現象，十之八九是主從延遲在搗鬼。

上一節講到，MySQL 的主從複製默認是異步的：主庫寫完就回報成功，不等從庫。這換來了好效能，代價是從庫的資料永遠慢那麼一小步。一般情況下這個時間差很短，你感覺不到；但只要主庫突然寫得很兇，或某一筆交易特別大，從庫就會明顯落後。這一節要把這個時間差的來源拆開，再給出對應的解法，因為它幾乎是所有採讀寫分離架構的團隊都會踩到的坑。

延遲的本質：生產速度大於消費速度

主從延遲的核心，用一句話就能概括：主庫的生產速度，大於從庫的消費速度。回想主從複製的鏈路：主庫負責產生 Binlog，從庫的 SQL Thread 負責回放。只要產生的速度持續超過回放的速度，Binlog 就會在從庫這一端排隊，這個排隊的時間差就是延遲。除了網路抖動、從庫機器比主庫差這些硬體因素之外，軟體層面最大的兩個原因如下。

原因一：並發能力不對等

這是延遲最根本的來源。主庫面對的是線上的業務流量，可能有成百上千個執行緒同時在寫；而從庫在早期版本裡，負責回放的 SQL Thread 只有一個，所有 Binlog 都得由它一條一條依序重放。你可以想成主庫是「十車道高速公路」，車流再大都能並行通過；到了從庫這裡，卻突然收束成「單車道」，車一多必定塞住。後來的 MySQL 版本雖然引入了並行複製，讓從庫也能多車道回放，但如果配置不當，還是會慢。

原因二：大事務是路障

第二個原因是大事務（Big Transaction）。假設你在主庫執行一條 DELETE，一次刪掉 1000 萬行、耗時 10 分鐘。這個交易的 Binlog 傳到從庫後，從庫的 SQL Thread 也得老老實實跑上 10 分鐘才能重放完。問題是，在這 10 分鐘裡，後面所有的 Binlog 都得排隊等它，延遲可能一下子飆到幾百秒。大事務就像在單車道上停了一台大卡車，自己走得久，還把整條路堵死。

四種解法：兩類思路

解法可以分成兩類：一類是「讓從庫變快」，治本；一類是「在業務上繞過」，治標。實務上通常兩類並用。

第一類：讓從庫變快

開啟並行複製（MTS）：MySQL 5.7 之後支援真正的並行複製，做法是在從庫設定 slave_parallel_workers > 0，讓從庫也開多條車道並行回放 Binlog。這是目前解決延遲最有效、最通用的技術手段。它的思路是基於組提交（Group Commit）把可以並行的事務分組，讓多個 SQL 執行緒同時重放。

拆分大事務：這屬於開發規範層面。嚴禁在線上執行一次刪掉或更新大批資料的操作，把它改寫成「循環 1000 次、每次刪 1000 行」。這樣從庫回放時，中間就能穿插執行別的交易，不會造成長時間的堵車。這兩招一起用，效果最好。

第二類：在業務上繞過

核心業務強制讀主：有些資料天生不能容忍延遲。例如「剛註冊完的帳號馬上去登入」，如果讀到從庫，就會出現前言那個「用戶不存在」的笑話。這種對強一致性有要求的讀取，直接在程式碼裡指定去查主庫；只有那些對延遲不敏感的資料，例如報表、歷史記錄，才交給從庫。

緩存兜底：還有一招是寫主庫的同時，順手把資料寫一份到 Redis。讀取時先讀 Redis，Redis 裡沒有再查從庫。既然資料庫同步慢，就用快取來補上那一小段空窗。這招對「剛剛寫入、馬上要讀」的場景特別有效。

四種解法對照

解法類別做法主要效果
並行複製（MTS）治本從庫設 slave_parallel_workers > 0多車道回放，最有效
拆分大事務治本大批操作拆成循環小批次避免單一交易堵住回放
核心讀主治標強一致需求的讀取直接走主庫商業上掩蓋延遲
緩存兜底治標寫主庫同時寫 Redis，讀取先讀快取補上同步的空窗

小結

主從延遲的本質是「生產速度大於消費速度」：主庫多線程並發寫，從庫默認只有單一 SQL Thread 串行回放，中間的時間差就是延遲；大事務則像路障，會讓後續 Binlog 全部排隊。解法分兩類：治本的是開啟並行複製（MTS）與拆分大事務；治標的是核心業務強制讀主，以及用 Redis 等緩存兜底。最佳實踐是「MTS 並行複製 + 嚴控大事務 + 核心讀主」三者並用。
