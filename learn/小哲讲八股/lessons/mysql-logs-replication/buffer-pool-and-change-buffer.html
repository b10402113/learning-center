Buffer Pool 與 Change Buffer：記憶體裡的寫入緩衝

Step 3/5 · 日誌、WAL、複製與主從

學習目標

能講清楚 Buffer Pool 如何用記憶體加速讀寫、為什麼它的 LRU 要分成新舊兩區，以及 Change Buffer 為什麼只對普通二級索引有效、對唯一索引無效。

前言：為什麼 UPDATE 不用每次等磁碟

前面兩節都在講日誌：Redo Log 讓交易提交後不怕斷電，兩階段提交讓主從不會各說各話。但你可能會好奇一個更前面的問題：當你執行一筆 UPDATE，InnoDB 到底在哪裡改資料？如果每次都要把磁碟上那頁 16KB 的資料讀出來、改完再寫回去，就算日誌再快，光等磁碟就夠你受了。事實上，你平常感受到的「更新完馬上就看到新值」，很多時候根本沒碰過磁碟。

這是因為 InnoDB 在最前面放了一道記憶體防線，先擋掉絕大多數的磁碟往返。這道防線分成兩個元件：負責讀寫資料頁的 Buffer Pool，以及專門處理索引變更的 Change Buffer。這一節把這兩個元件講清楚，你就能回答「為什麼 InnoDB 的寫入比你想的輕、快取為什麼不容易被一次大查詢洗掉」這類問題。

Buffer Pool：用記憶體的速度補磁碟的慢

Buffer Pool（緩衝池）是 InnoDB 最核心的一塊記憶體。它存在的理由很單純：磁碟太慢、記憶體很快，那就把常用的資料頁搬進記憶體，之後讀寫都先找記憶體。它的工作可以分成「加速讀」與「加速寫」兩半。

先看讀。當你要查一筆資料，InnoDB 不會直接殺去磁碟，而是先看 Buffer Pool 裡有沒有這一頁。如果有，稱為命中（Hit），直接從記憶體回傳，這是微秒級的速度；如果沒有，稱為未命中（Miss），才去磁碟把這一頁載進來，載完順手放進 Buffer Pool，下次就能命中。它快取的東西不只是資料本身，還包括索引頁、實作回滾用的 Undo 頁，甚至鎖相關的資訊。

再看寫。當你執行 UPDATE，InnoDB 並不會立刻把資料寫回磁碟，而是只修改 Buffer Pool 裡那一頁，並把這一頁標記成髒頁（Dirty Page），然後就回報你「更新成功」。真正的刷盤交給背景執行緒，等它有機會再一次處理。這樣做的好處是：如果你連續改同一個頁好幾次，這些修改會合併成一次 I/O；如果有多個不連續的頁要寫，也能被合併成批次的 I/O 一起送出去。

為什麼 Buffer Pool 不能用普通 LRU

記憶體有限，Buffer Pool 裝滿了總得淘汰一些頁。最直覺的做法是 LRU（Least Recently Used，最近最少使用）：把頁排成一條鏈，有人用就移到最前面，要淘汰就從最後面丟。這個想法在一般快取裡很合理，但放到資料庫會出一個致命的問題：全表掃描。

想像你偶爾跑一次「把整張大表掃一遍」的查詢。按普通 LRU 的規則，這一趟掃描碰到的每一頁都會被插到鏈的最前面，把原本天天在用的熱點資料一路擠到尾部，最後全被淘汰。等這個全表掃描結束，Buffer Pool 裡幾乎只剩那些只被讀過一次的冷資料，快取命中率瞬間崩掉。這種現象有時被形容成「熱資料被洗掉了」。

InnoDB 的解法是把 LRU 鏈切成兩段：靠近頭部的新生代（New Sublist，約占 5/8）放真正的熱資料，尾部的老年代（Old Sublist，約占 3/8）負責緩衝。關鍵規則是：新讀進來的頁，一律先放在老年代的頭部，不是直接進新生代。只有當這一頁在老年代裡待得夠久、又被再次訪問時，才有資格被晉升到新生代。如此一來，全表掃描帶來的一次性冷資料只會堆在老年代、很快被淘汰，搆不到真正的熱點資料。這一套改良版 LRU，也順帶解掉了「偶發大查詢把快取洗掉」的線上抖動。

Change Buffer：把「欠帳」先記下來

Buffer Pool 解決了大部分讀寫，但還有一種寫入場景特別尷尬：假設你執行 INSERT INTO user ...，這筆新增要同時更新主鍵索引和幾個二級索引。如果相關的索引頁剛好不在 Buffer Pool 裡，那為了改它，InnoDB 就得先從磁碟把索引頁讀進記憶體（一次隨機 I/O），改完再讓它慢慢刷回去。對於寫多讀少的業務，這種「為了改而先讀」的開銷會不斷累積。

Change Buffer（變更緩衝）就是用來省掉這趟讀取。當要更新一個二級索引、而對應的索引頁不在記憶體時，InnoDB 不讀磁碟，而是先在 Change Buffer 裡記一筆「我要對第 X 頁做一個插入」。這動作像是先賒個帳。等之後有人真的查這個頁，或者背景執行緒空閒時，再把這些「欠帳」合併（Merge）進真正的索引頁。省下的正是一次又一次的隨機讀。

但這裡有個面試最愛追的細節：Change Buffer 只對「普通二級索引」有效，對唯一索引（包含主鍵）無效。原因和唯一索引的職責有關，它必須保證資料不重複。當你插入一筆新資料，唯一索引必須立刻確認「這個值是不是已經存在」，而要確認這件事，就非得把那個索引頁讀進記憶體來比對不可。既然頁已經被讀上來了，直接更新記憶體裡的頁就好，Change Buffer「避免讀取」的意義自然消失。所以不是不想用，是根本用不上。

兩個元件怎麼分工

元件加速的對象運作方式適用限制
Buffer Pool資料頁的讀與寫讀命中直接回；寫只改記憶體、標髒頁後異步刷盤記憶體有限，靠改良 LRU 管理
Change Buffer二級索引的變更寫入頁不在記憶體時先記欠帳，之後再 Merge僅普通二級索引；唯一索引無效

小結

Buffer Pool 是 InnoDB 最核心的記憶體，讀的時候先找它、命中就回，寫的時候只改它、把頁標成髒頁再交給後台異步刷盤，用合併 I/O 換效能。它的淘汰不能只靠普通 LRU，否則一次全表掃描就會把熱資料洗光，所以切成新生代與老年代，新頁先進老年代。Change Buffer 則專門快取「頁不在記憶體時」的二級索引變更，避免多餘的隨機讀；但它只對普通二級索引有效，因為唯一索引插入時本來就必須讀頁做去重檢查。
