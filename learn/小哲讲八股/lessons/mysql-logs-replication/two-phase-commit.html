兩階段提交：Redo 與 Binlog 怎麼保持同步

Step 2/5 · 日誌、WAL、複製與主從

學習目標

能說出兩階段提交為何存在、三個階段（Prepare、寫 Binlog、Commit）各做什麼，並解釋崩潰發生在不同時間點時，MySQL 如何判斷該回滾還是提交。

前言：一次斷電，為什麼主從對不上

上一節我們把三種日誌分了工：Redo Log 決定主庫能不能恢復，Binlog 決定從庫能不能同步。現在把兩者放在同一筆交易裡看，就會冒出一個很具體的意外。假設你剛提交一筆轉帳，主庫的 Redo Log 寫好了，Binlog 卻還在半路，此時機房突然斷電。重啟後：主庫靠 Redo Log 把這筆交易恢復了，餘額是對的；但從庫當初是照 Binlog 同步的，Binlog 根本沒送出，從庫完全不知道這筆交易。結果就是主庫有、從庫沒有。

把斷電的時間點換一下，情況會反過來：如果 Binlog 寫完、Redo Log 還沒寫就斷電，從庫照著 Binlog 同步成功，主庫重啟後卻因為 Redo Log 沒寫而丟掉這筆交易。這次變成從庫有、主庫沒有。不管你讓哪一份先寫，只要允許中間斷電，主從就會不一致。這一節要講的兩階段提交，正是 MySQL 用來堵住這個縫的機制。

問題的本質：兩個層級要一起改

先講清楚為什麼會有這個縫。Redo Log 屬於 InnoDB 引擎層，Binlog 屬於 Server 層，兩份日誌由不同層各自負責寫入。一筆交易提交時，這兩份都必須寫，而且是邏輯上的一體：Redo Log 決定主庫的資料，Binlog 決定從庫的資料。只要兩者不一致，主從同步就會出錯。

如果沒有特殊機制，讓它們「先寫 A 再寫 B」，就會出現前言說的兩種壞情況：先寫 Redo Log 再寫 Binlog，中間斷電會讓主庫有、從庫沒有；先寫 Binlog 再寫 Redo Log，中間斷電則讓從庫有、主庫沒有。所以問題不是「誰先寫」，而是「不允許只寫一半」。既然兩件事不能拆成兩次獨立的成功，就得設計成一組原子操作：要嘛兩個都成，要嘛兩個都不成。兩階段提交（Two-Phase Commit, 2PC）要達成的，就是這個目標。

三階段流程：Prepare、寫 Binlog、Commit

MySQL 的兩階段提交，把 Redo Log 的寫入刻意拆成前後兩步，中間夾著 Binlog 落盤。假設你執行一條 UPDATE，在提交的那一刻，內部流程是這樣走的：

  1. 階段一（Prepare）：InnoDB 先把這次的修改寫進 Redo Log，並把 Redo Log 的狀態標記為 PREPARE。此時資料已經有日誌，但狀態是「待定」，還不算完成。
  2. 階段二（寫 Binlog）：MySQL Server 層把 SQL 語句或行變更寫進 Binlog，並確保它刷到磁碟。這一步是整個機制的關鍵：Binlog 是否完整落盤，成為之後判斷交易生死的依據。
  3. 階段三（Commit）：InnoDB 收到「Binlog 已經寫好」的通知後，把 Redo Log 的狀態從 PREPARE 改成 COMMIT，交易正式完成。

你可以把它想成簽一份雙聯合約：先把第一聯蓋上「待確認」的章（Prepare），再去簽第二聯（Binlog），最後回頭把第一聯改成「已生效」（Commit）。過程中任何一步斷掉，都能靠兩聯的狀態對照，判斷這份合約到底算不算數。

崩潰恢復：掃 Binlog 決定生死

真正巧妙的地方，在於崩潰之後怎麼判斷。MySQL 的規則可以簡化成一句：Redo Log 是 Prepare 還是 Commit 不是重點，關鍵是 Binlog 完不完整。分兩種情況看：

  • 崩潰在 Prepare 之後、寫 Binlog 之前：重啟恢復時，MySQL 發現 Redo Log 停在 PREPARE 狀態，而且 Binlog 裡沒有對應記錄。因為 Binlog 不完整，從庫不會有這筆資料，所以主庫也必須放棄，系統判定交易失敗，回滾。
  • 崩潰在寫完 Binlog 之後、Commit 之前：重啟時 Redo Log 雖然還是 PREPARE，但 Binlog 裡已經有完整記錄。既然從庫會拿到這筆資料，主庫就必須有，否則又會不一致，系統因此判定交易成功，提交（必要時靠掃描 Binlog 來強制完成）。

為什麼要讓 Binlog 來當裁判，而不是 Redo Log？因為主從一致性的本質是「兩邊都有或兩邊都沒有」。Binlog 是從庫唯一的資料來源，它有沒有這筆記錄，直接決定從庫的結果；所以以 Binlog 的完整性為準，反過來決定主庫要不要提交，就能保證兩邊站在同一邊。這也回應上一節的結論：Redo Log 和 Binlog 不是替代關係，而是必須被綁在一起提交的一對。

小結

Redo Log 屬 InnoDB、決定主庫資料，Binlog 屬 Server 層、決定從庫資料，兩者若不一致就會主從脫節。兩階段提交把 Redo Log 的寫入拆成 Prepare 與 Commit，中間夾一次 Binlog 落盤，讓它們成為一組原子操作。崩潰恢復時以 Binlog 是否完整為裁判：Binlog 沒寫完就回滾，Binlog 寫完就提交，確保主庫與從庫永遠同進退。

到這裡，我們把「日誌怎麼保證交易不丟、主從不錯」講完了。但日誌只是寫入鏈路的一半，另一半在記憶體：那些被改動的資料頁，究竟在 Buffer Pool 裡怎麼被管理、又怎麼被刷回磁碟？下一節會把鏡頭轉向記憶體這一側，談 Buffer Pool 與 Change Buffer。
