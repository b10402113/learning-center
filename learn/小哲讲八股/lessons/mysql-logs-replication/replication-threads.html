主從複製三線程：Binlog 如何搬到從庫

Step 4/5 · 日誌、WAL、複製與主從

學習目標

能用「主庫寫日誌、從庫抄日誌、重放日誌」講清楚主從複製的三個線程（Binlog Dump、I/O Thread、SQL Thread）與中繼日誌的角色，並比較異步、半同步、全同步三種複製模式的一致性代價。

前言：只寫主庫，從庫的資料哪來的

線上系統通常不會只有一台資料庫。常見的安排是一主多從：寫入都打主庫，查詢分散到從庫，主庫萬一掛了還有從庫可以頂上。這個架構聽起來很自然，但有個問題很容易被忽略：你從來沒有對從庫下過任何 INSERT 或 UPDATE，那從庫的資料是怎麼變出來的？

答案不是「你寫兩次」，而是主庫把每一筆變更記錄下來，再傳給從庫照著做一遍。前幾節提到的 Binlog 在這裡正式上場：它不只是歸檔用的帳本，更是主從之間唯一的資料管道。這一節把這條管道拆開來看，講清楚中間有三個線程、一條中繼日誌，以及「主庫到底要等從庫多久才敢說成功」這個決定一致性與效能的關鍵選擇。

一句話講完主從複製

整個主從複製的邏輯，可以壓縮成一句話：主庫寫日誌，從庫抄日誌，重放日誌。打個比方，這就像老師（主庫）在黑板上寫解題步驟（Binlog），學生（從庫）先把黑板上的內容抄到自己的草稿本（Relay Log）上，再照著草稿本自己在腦子裡算一遍（執行 SQL）。黑板、草稿本、腦袋，對應的正是三個線程各管一段的接力。

這整條鏈路完全依賴 Binlog。回想前幾節：Redo Log 是 InnoDB 專屬的、循環寫的、只為崩潰恢復而生；只有 Binlog 是跨引擎通用、邏輯、能保存全量歷史的格式。要讓資料能同步到從庫、甚至餵給其他系統，非得用 Binlog 不可。

三個線程的接力賽

複製過程由三個線程合作完成，分別落在主庫與從庫兩端。我們照資料流的方向，一段一段看。

第一段：主庫的 Binlog Dump Thread（記錄與發送）

當主庫發生寫操作，它會把變更記錄進 Binlog。等到有從庫連上來時，主庫會為這個從庫建立一個 Binlog Dump Thread。顧名思義，它的工作就是把 Binlog 的內容持續發送給從庫。主庫本身不需要知道從庫收到後要做什麼，它只負責「把帳本遞出去」。

第二段：從庫的 I/O Thread（接收與暫存）

從庫這邊會啟動一個 I/O Thread。它負責連上主庫、請求讀取 Binlog，收到資料後並不直接執行，而是先寫進從庫本地的一個檔案，叫做中繼日誌（Relay Log）。這裡值得多問一句：為什麼要多一層中繼日誌，不直接執行就好？答案是解耦。網路傳輸的速度和 SQL 執行的速度本來就不一樣，如果邊收邊做，接收端就得被執行端拖著走；先全部存下來，兩邊就變成典型的「生產者—消費者」模型，I/O Thread 只管收、SQL Thread 只管做，各自照自己的節奏跑。

第三段：從庫的 SQL Thread（重放與執行）

從庫還有第三個線程，也就是 SQL Thread。它專門盯著中繼日誌，一發現有新內容，就讀出來、解析成 SQL 語句或行變更，在從庫上重新執行一遍。執行完成後，從庫的資料就和主庫一致了。要注意的是，這個重放是「照著主庫的變更順序做」，而不是重新讓應用程式再發一次請求，這也是為什麼從庫不需要你的業務程式碼。

主庫要等多久：三種複製模式

到這裡，鏈路已經通了，但還剩一個關鍵設計問題沒回答：主庫寫完之後，到底要等從庫多久，才敢回報客戶端「成功」？這個等待的程度，直接決定系統的一致性與效能，也就是異步、半同步、全同步三種模式的差別。用寄快遞來比喻最貼切。

  • 異步複製（默認）：主庫自己寫完 Binlog、提交交易，立刻回報成功，完全不管從庫有沒有收到。就像你把包裹丟進郵筒就走人，不必等對方簽收。效能最好，主庫毫無拖累；但安全性最差，如果主庫剛寫完就掛掉、Binlog 還沒傳出去，這筆資料就永久丟失。
  • 半同步複製：主庫寫完 Binlog 後必須等待，等到至少一個從庫收到 Binlog、寫進中繼日誌並回傳一個 ACK 確認，主庫才敢回報成功。像快遞要求「至少一個收件人簽收」。代價是多了一個網路往返（RTT）的延遲，但安全性大幅提高，至少保證有一個從庫握有資料，資料遺失風險趨近於零。它是目前生產環境做高可用時的首選。
  • 全同步複製：主庫要等到所有從庫都提交了交易才能回報成功。標準的 MySQL 原生複製做不到這件事（太慢），通常指的是 MGR 或 Galera 這類基於共識協定的集群方案。安全性最高，所有節點資料完全一致；但性能最差，任何一個節點慢，整個集群就跟著慢，一個節點掛了還可能導致集群不可用。

三種模式對照

模式主庫等待程度效能資料安全
異步（默認）不等待從庫最好可能丟資料
半同步等至少一個從庫 ACK中等風險趨近於零
全同步等所有從庫提交最差強一致

小結

主從複製就是「主庫寫日誌、從庫抄日誌、重放日誌」。主庫的 Binlog Dump Thread 把 Binlog 送出去；從庫的 I/O Thread 接收後寫進中繼日誌，用來把網路接收與 SQL 執行解耦；從庫的 SQL Thread 再從中繼日誌讀出來重放，資料於是與主庫一致。整條鏈路依賴跨引擎通用的 Binlog。至於主庫要等從庫多久，分成異步（不等待、可能丟）、半同步（等至少一個 ACK、高可用首選）、全同步（等全部提交、強一致但最慢）三種模式。

因為默認是異步複製，主庫不必等從庫，這雖然換來了好效能，卻也埋下一個日常會遇到的問題：從庫的資料總是慢半拍。剛註冊完的帳號馬上去登入卻查不到、報表數字落後，這些都是「主從延遲」在作怪。下一節就專門拆解延遲的根因與解法。
