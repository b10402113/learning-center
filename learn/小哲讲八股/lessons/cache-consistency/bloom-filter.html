布隆過濾器：用位陣列換一個「一定不存在」

快取模式與資料一致性 · Step 2/5 · 學習目標：講清楚位陣列加多個雜湊函式的寫入與查詢流程，解釋為什麼它只會誤判「存在」、為什麼不能刪除，以及工程上如何處理誤判率升高。

前言：擋住不存在的查詢，又不能存下所有資料

上一課講到防穿透，最推薦的一招是在 Redis 前面放一個布隆過濾器。但這裡馬上出現一個矛盾：你要判斷某個 ID「一定不存在」，總得先知道所有存在的 ID 長什麼樣。如果把幾億筆 ID 全部存起來比對，光是記憶體就先爆了，那你又何必用快取？

布隆過濾器解決的正是這個矛盾。它不存資料本身，只存資料的「指紋」。它用一個很長的位陣列加上幾個雜湊函式，就能回答「這個元素在不在集合裡」，而且只允許一種錯誤：把不存在的東西說成可能存在。這種「寧可錯殺、絕不放過」的特性，剛好完美契合防穿透，只要它說不存在，你就可以放心攔截。

這一課拆開它的位陣列、寫入與查詢流程，並解釋它為什麼天生不能刪除。

它是什麼：一個位陣列加上幾個雜湊函式

布隆過濾器（Bloom Filter）本質上由兩部分組成：一個很長的二進位向量，也就是位陣列；以及一系列隨機映射函式，也就是雜湊函式。

位陣列就是一個長度為 m 的陣列，裡面每個格子只存 0 或 1，初始狀態全部是 0。它極度省空間，存一億個狀態，可能只需要幾十 MB。雜湊函式的數量設為 k 個，每個都是一個能把任意輸入映射成一個數字的函式。

它不保存元素的具體內容，只保存「指紋」。所以你永遠無法從布隆過濾器裡反推出「redis 這個字串存在」，只能得到「可能存在」或「一定不存在」這兩種答案。

寫入流程：把 k 個位置設成 1

把一個元素加入過濾器時，例如字串 "redis"，會做以下三步：

  1. 用那 k 個不同的雜湊函式分別計算 "redis"，得到 k 個雜湊值。
  2. 把這 k 個值分別對陣列長度 m 取模，得到 k 個位置索引。
  3. 把位陣列上這 k 個位置的 bit 全部設為 1。

注意，多個元素可能把某個位置「共用」設成 1。例如 "oracle" 和 "kafka" 算出來的位置，可能有一部分剛好落在同一個格子上。這正是後面誤判的來源，也是它不能刪除的根本原因。

查詢流程：看到 0 就一定不存在

查詢一個元素，例如 "mysql" 是否在集合中，流程和寫入對稱：

  1. 用同一組 k 個雜湊函式計算 "mysql"，得到 k 個位置。
  2. 檢查位陣列上這 k 個位置的值。

接著就是兩種結果的判斷，這是整個結構最關鍵的地方。

情況 A：只要有任何一個位置是 0。這說明這個位置從來沒有被任何元素設成 1。既然加入過的元素都會把它算到的位置設成 1，那 "mysql" 若真的加入過，就不可能留下 0。所以結論是 100% 準確的："mysql" 一定不存在。

情況 B：所有位置都是 1。這說明這 k 個位置都被設成 1 了。但這些 1 不一定是 "mysql" 自己填的，很可能是 "oracle"、"kafka" 等其他元素湊巧分別佔滿了這幾個格子。所以結論只能是："mysql" 可能存在。這就是雜湊碰撞造成的誤判。

把這兩種結果合起來看，就是布隆過濾器的招牌特性：它說不存在，一定不存在；它說存在，可能只是誤判。誤判的方向是單向的，只會把「不存在」誤判成「存在」，絕不會把「存在」誤判成「不存在」。

為什麼不能刪除

標準的布隆過濾器不支援刪除元素。原因就藏在剛才的「共用位置」裡：某個位置的 1，可能是好幾個元素一起貢獻的。假設 "redis" 和 "mysql" 都把第 7 格設成了 1，現在你要刪除 "redis"，如果把第 7 格直接改回 0，那麼 "mysql" 之後來查詢時，就會發現有一個位置是 0，被誤判成「不存在」，也就是把真正存在的元素誤殺掉了。

要安全地刪除，你就得知道每個位置到底被哪些元素佔用，但那等於要把所有元素都存下來，空間優勢就消失了。所以標準版乾脆不對外提供刪除。這也帶出下一個現實問題：如果系統長期運行，資料不斷被刪除，位陣列裡的 1 只會愈來愈多，雜湊碰撞的機會愈來愈大，誤判率就會一路升高。

誤判率升高怎麼辦：重建或改用計數布隆

資料被刪除而過濾器不能刪，會讓誤判率失控。工程上有兩條路可以處理。

第一條是定時重建。這是最常見也最省成本的做法。做法是新建一個空的布隆過濾器，把目前資料庫裡仍然有效的資料重新載入進去，載完之後再原子地替換掉舊的過濾器。這樣誤判率就被重置回設計值。它的缺點是需要額外一份空間，替換的瞬間也要處理好讀取的一致性。

第二條是改用計數布隆過濾器（Counting Bloom Filter）。它把每個 bit 換成一個小計數器，加入元素時計數加一，刪除時計數減一，歸零才代表這個位置真的空了。這樣就支援刪除了。代價是空間開銷會膨脹到標準版的 3 到 4 倍，等於拿空間換取刪除能力。

實務上，多數場景會選擇定時重建，因為它簡單、成本低；只有在刪除非常頻繁、重建代價太高的情況下，才會考慮計數布隆。

優劣與典型應用

相較於 HashSet 或 HashMap，布隆過濾器的優勢很明確：不需要存原始資料，空間佔用極小，插入與查詢的時間複雜度都是 O(k)，常數極低、速度極快。劣勢也同樣明確：存在誤判率，且標準版不支援刪除。

它最經典的應用就是解決 Redis 的快取穿透：把所有存在的資料庫主鍵預熱載入到布隆過濾器裡，請求進來先問它，它說不存在就直接攔截，保護資料庫不被海量無效請求打垮。除此之外，網路爬蟲用它做 URL 去重、郵件系統用它過濾垃圾郵件，也都是同一個特性，「用一點誤判，換取大量的空間與速度」。

面試時如果被追問應用場景，你可以直接點出這個共同點：只要你能接受「偶爾把不存在的東西誤判成存在」，而且不能接受把存在的東西誤判成不存在，布隆過濾器就很適合。

小結

布隆過濾器是一個位陣列加上 k 個雜湊函式。寫入時把元素經過 k 次雜湊對應到的位置設成 1；查詢時只要有一位是 0，就 100% 確定不存在，全為 1 則只能說可能存在。它只會單向誤判，把不存在誤判成存在，因此最適合用來防快取穿透。代價是不支援刪除，資料被刪得多了誤判率會升高，實務上用定時重建或改用空間大 3 至 4 倍的計數布隆來處理。
