Canal 與 Binlog：把快取同步從業務程式碼裡拆出來

快取模式與資料一致性 · Step 5/5 · 學習目標：講清楚 Canal 如何偽裝成 MySQL Slave 訂閱 Binlog、解析成結構化事件並投遞下游，以及它為什麼比業務雙寫更解耦可靠。

前言：每個寫入方法都要記得刪快取，這合理嗎

上一課把一致性的主線定下來了：先寫庫、後刪快取。但當你把這條規則鋪進專案，很快就會發現一個現實問題，任何一處修改商品、修改訂單、修改庫存的程式碼，都得在正確的位置補上一段刪快取的邏輯。少寫一處，就是一筆永久的不一致；寫錯順序，就是另一種 bug。而且當系統要同步的目標不只 Redis，還有 Elasticsearch、其他服務的快取時，業務程式碼會愈來愈臃腫。

這種「雙寫」的麻煩，來自一個根本的錯位：資料變更的事實，其實已經被 MySQL 自己完整記下來了。與其讓每個業務方法自己去通知快取，不如請一個專門的元件去讀 MySQL 的變更日誌，再由它統一發布。Canal 就是幹這件事的。

先懂地基：MySQL 的主從複製

要理解 Canal，得先知道 MySQL 主從複製怎麼運作。MySQL 的主庫（Master）會把所有變更寫進一份二進位日誌（Binlog）。從庫（Slave）連上主庫後，主庫就會把 Binlog 推送給它，從庫重放這些日誌，讓自己跟主庫保持一致。

關鍵在於：主庫並不會去「驗證」連上來的到底是不是一台真的 MySQL 從庫，它只認協議。Canal 就是鑽了這個空子，它照著 MySQL 的底層通訊協議，把自己偽裝成一台普通的從庫。

Canal 的第一步：偽裝成 Slave，把 Binlog 拿過來

Canal 啟動後，和 MySQL 的互動完全遵循 MySQL 的標準協議，流程共四步：

  1. 建立連接：Canal 與 MySQL 建立 TCP 連線。
  2. 身份認證：Canal 發送帳號密碼進行登入。
  3. 發送指令：Canal 發送 COM_BINLOG_DUMP 命令，並指定要從哪個日誌檔、哪個位置開始讀取。
  4. 接收資料：MySQL Master 收到命令後，開始把二進位日誌事件透過網路推送給 Canal。

這四步，完全可以想成 Canal 對 MySQL 說了一句話：「我是你的從庫，請把最新的 Binlog 發給我。」MySQL 分辨不出真假，照常推送。這也解釋了為什麼 Canal 能拿到的是「增量」資料，它訂閱的正是資料庫每一次變更產生的日誌流。

實務上，這裡有兩個細節值得記住：Canal 指定了 binlog 檔名與位移（position）之後，就能從任意時間點開始訂閱，所以它也能被拿來做歷史資料的增量同步。一旦斷線重連，只要記住上次消費到的位置，就能續傳，不會漏掉中間的變更。

第二步：把二進位流解析成看得懂的事件

MySQL 推過來的是原始的二進位流，人和普通程式都讀不懂。Canal 的核心價值就在它的解析器：它把這串二進位位元流解析成具體的事件，再轉成易於處理的資料模型，通常叫一個 Entry。

一個解析出來的 Entry 會包含這些資訊：資料庫名、表名、操作類型（INSERT、UPDATE 或 DELETE），以及最關鍵的變更前的資料（Before Image）和變更後的資料（After Image）。有了前後兩個版本，下游不只知道「有一列被改了」，還知道「它從什麼變成什麼」，能做更精細的判斷。Canal 常以 Protobuf 格式輸出這份結構化資料，方便跨語言消費。

這一步是整個方案裡最耗工的部分，因為 MySQL 的 Binlog 格式本身在演進，不同版本、不同 row 格式的解析細節都不一樣。Canal 把這些複雜度都吸收在內部，對外只給你乾淨的結構化事件。

第三步：投遞下游，驅動快取同步

解析完的事件，通常不會直接由 Canal 自己去刪快取，而是先投遞到訊息佇列，例如 Kafka 或 RocketMQ；也可能是直接同步到目標儲存，例如 Elasticsearch 或 Redis。

這樣安排的好處是，業務系統只要監聽訊息佇列，就能即時感知資料庫的變化。以快取同步為例，整條鏈路會變成：業務寫 MySQL → MySQL 產生 Binlog → Canal 解析 → 投遞到 MQ → 下游消費者收到事件，刪掉對應的 Redis Key。業務程式碼從頭到尾都只管寫庫，完全不碰快取。同樣一條鏈路，也能拿來同步 Elasticsearch、維護其他異構資料。

為什麼它比業務雙寫更好

回頭對比上一課的「業務雙寫刪快取」，Canal 的優勢就清楚了。業務雙寫要求每一個寫入路徑都記得正確地刪快取，任何一處遺漏或順序錯誤都會造成不一致；而 Canal 是從資料庫的變更日誌出發，只要資料庫寫進去了，事件就一定會產生，不存在「忘記通知」的問題。它把「快取維護」這件事，從幾十上百個業務方法裡，收斂到一條獨立的同步鏈路，解耦得更乾淨，可靠性也更高。

面試時，這通常是最後一層的加分回答：先講旁路快取與先寫庫後刪，再補一句「如果要更解耦，我會用 Canal 訂閱 Binlog，把刪快取交給下游消費者」。如果能順口說出 Canal 偽裝從庫、發 COM_BINLOG_DUMP、解析出帶 Before／After Image 的 Entry，這題就答得很完整了。

小結

Canal 的原理是把自己偽裝成 MySQL 的從庫：建立連線、認證、發送 COM_BINLOG_DUMP、接收 Binlog，這四步完全照著 MySQL 的底層協議走。拿到二進位日誌後，它用解析器把資料流轉成結構化的事件（Entry），裡面包含庫名、表名、操作類型，以及變更前後的資料映像。這些事件通常投遞到 Kafka、RocketMQ，或直接同步到 Elasticsearch、Redis，由下游消費者刪除對應快取。它比業務雙寫更好的地方在於：只要資料庫寫成功，事件必然產生，不存在漏通知，業務程式碼也因此不必再碰快取，快取同步被收斂成一條獨立鏈路。
