快取失效三兄弟：穿透、擊穿與雪崩

快取模式與資料一致性 · Step 1/5 · 學習目標：用「資料存不存在、是不是熱點、失效範圍多大」三個維度分辨穿透、擊穿與雪崩，並各說出一組防禦方案。

前言：加了快取，資料庫怎麼還是被打死

你把一套查詢接口改成了「先查 Redis、查不到再查 MySQL、查到就補回 Redis」。上線前壓測一切正常，資料庫的 QPS 掉了九成。結果上線沒幾天，線上告警響了：MySQL 的連線數突然衝到上限，整個服務卡死，而 Redis 看起來卻很閒。

快取本身沒有壞，只是在你沒預料到的時刻「失效」了。快取失效有很典型的三種形態，業界習慣叫它們穿透、擊穿與雪崩。它們的共同後果一樣，請求穿過快取、直接砸到資料庫，但成因完全不同，解法也完全不一樣。用錯了藥，不但沒救，還會讓你在面試裡露餡。

這一課的目標，是讓你在聽到任何一種失效時，能立刻判斷它屬於哪一類，並說出對應的處理方式。

三種失效，先各給一句話

把所有情況攤開來看，差別其實只在三件事：要查的資料到底存不存在、失效的是不是單一熱點、以及失效的範圍有多大。用這三個維度對照，三兄弟就分開了。

類型要查的資料觸發條件問題範圍
穿透快取和資料庫都沒有的資料反覆查一個不存在的 Key點（單一非法查詢）
擊穿資料庫有，只是快取剛過期單一熱點 Key 在高併發下過期點（單一熱點）
雪崩資料庫有，但快取大面積失效大量 Key 同時過期，或快取層宕機面（整個快取層）

記住這張表，面試時先講「它們都是快取失守導致流量打到資料庫，但一個查不存在、一個是熱點過期、一個是大面積失效」，後面再逐個展開。

一、穿透：一直查根本不存在的資料

穿透的場景很單純：客戶端請求的資料，快取裡沒有，資料庫裡也沒有。因為資料庫查不到，通常會回傳 null，而這個 null 你也不會寫進快取。於是下一次同樣的請求來，還是直接打到資料庫，形成一個繞過快取、反覆打在資料庫上的死循環。

這種情況最常出現在兩種場合。一種是惡意的攻擊，例如有人拿 id=-1 或隨機的 UUID 瘋狂刷你的接口；另一種是業務邏輯的 bug，程式碼要求了一個根本不會存在的鍵值。兩者的結果都一樣：資料庫被迫去處理一個又一個注定查不到的查詢。

防穿透的核心思路是「攔住非法請求」，在請求碰到資料庫之前就把它擋掉，常見有兩招。

第一招是布隆過濾器。在 Redis 前面放一個布隆過濾器，把所有可能存在的 ID 預先存進去。請求進來時先問過濾器：如果它說「不存在」，就直接回傳，絕不讓請求碰到資料庫；如果它說「可能存在」，才放行往下查。它的威力在於用極小的空間就能擋掉海量的無效請求，代價是會有一點誤判率，下一課會專門拆開它。

第二招是快取空物件。如果資料庫查不到，就把這個 Key 也寫進 Redis，值設成 null 或一個特殊標記，並配上一個較短的過期時間，例如 30 秒。這樣下一次同樣的請求就會命中快取，直接拿到「不存在」的答案，不會再去打資料庫。要注意這個 TTL 必須短，否則萬一之後這筆資料真的被建立了，你會在過期前一直讀到「不存在」。

二、擊穿：一個熱點 Key 剛好過期

擊穿和穿透只差一個字，場景卻完全不同。這裡查的是真實存在、而且非常熱門的資料，例如首頁某個熱搜的內容。它一直靠快取扛著高併發，忽然某一刻，這個 Key 過期了。

關鍵就在過期後的這幾百毫秒。快取失效的瞬間，本來該由快取吸收的高併發，例如十萬個請求，會在同一時間全部湧向資料庫。它們都在問同一筆資料，而快取還沒來得及重建，資料庫就被瞬間壓垮。擊穿是「單點」問題，重點在併發：大量請求同時打在同一個缺口上，跟資料多寡無關。

處理擊穿的核心是「控制重建的併發」或「乾脆不要真的過期」，常見兩招。

第一招是互斥鎖。當發現快取過期時，不讓所有執行緒都去查資料庫，而是先搶一把 Redis 的分散式鎖。只有搶到鎖的那一個執行緒去查資料庫、重建快取，其他執行緒在旁邊等一下，等快取被重建好再讀。這樣十萬個併發就被壓縮成一次資料庫請求，資料庫自然不會被打死。它的代價是其他執行緒需要等待，所以鎖的逾時與持有時間要設好。

第二招是邏輯過期。很多高併發場景索性把 Key 設成永不過期，但把一個時間戳記在值裡面。查詢時，如果發現值裡的時間戳已經過了「邏輯上的」保鮮期，就開一個背景執行緒去非同步重建新快取，而當前這個請求直接回傳舊值。這樣請求永遠不會落空，可用性最高，缺點是會有一段時間回傳到稍微過期的資料。

三、雪崩：快取大面積同時失效

雪崩是「面」的問題。它指的是快取層出現錯誤，或者大量 Key 在同一時間一起過期，導致流量像雪崩一樣瞬間湧入資料庫。最典型的原因，是你設定快取時全部用了固定的過期時間，例如通通是 expire 60。系統啟動一分鐘後，這批 Key 就會在同一秒整批消失，資料庫迎來一波集體衝擊，量級往往比擊穿還大。

雪崩的另一個成因是快取層本身掛了。不管是 Redis 單點宕機，還是整個快取叢集失效，只要快取整層不見，所有流量都會直接落到資料庫。這種情況靠調整 TTL 是救不了的，必須靠架構。

雪崩的處理核心是「打散過期時間」加上「高可用架構」，通常三招一起上。

第一招是隨機 TTL。設定過期時間時不要固定 60 秒，而是設成 60 + random(0~10) 秒。這樣每個 Key 的過期時間被隨機打散，就不會同時失效，等於把一次集體衝擊攤平成一段時間內的小衝擊。

第二招是 Redis 高可用。用 Sentinel 或 Cluster 叢集，讓快取層不會因為單一節點故障就整層消失。這一招解的是「快取掛掉」這個成因，無法用 TTL 解決。

第三招是降級與限流。如果雪崩真的發生了，就在閘道層限流，或開啟服務降級、回傳預設值，先保住資料庫不被打死。這一招管的是災後處理：雪崩真的發生時用來控制損失、保住資料庫，屬於兜底。

面試時怎麼講得清楚

被問到這三者時，建議先給一句總起：「這三個都是快取失效導致大量請求穿過 Redis、直接打到 MySQL，但它們的成因不同。」然後按順序講，

穿透是查不存在的資料，快取和資料庫都沒有，解法是布隆過濾器或快取空物件；擊穿是單一熱點在高併發下過期，解法是互斥鎖或邏輯過期；雪崩是大面積失效或快取層宕機，解法是隨機 TTL、高可用叢集加上限流降級。

最後補一句點出關鍵差別：「穿透是查的東西不存在，擊穿強調併發、是單點，雪崩強調批量、是整面。」這樣講，對方會知道你分得清，而不是把三個詞背在一起。

小結

穿透、擊穿、雪崩都是快取失守、流量打穿到資料庫的場景。穿透查的是根本不存在、連資料庫都沒有的資料，用布隆過濾器或快取空物件攔截；擊穿是單一熱點 Key 在高併發下剛過期，用互斥鎖控制重建併發，或用邏輯過期永不落空；雪崩是大量 Key 同時過期或快取層宕機，用隨機 TTL 打散、用 Sentinel／Cluster 保高可用、出事時再限流降級。辨識它們的關鍵維度是：查的東西存不存在、是不是單一熱點、失效範圍有多大。
