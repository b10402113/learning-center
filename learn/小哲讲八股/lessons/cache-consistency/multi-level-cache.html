多級快取：L1 本地加 L2 Redis 的分工與代價

快取模式與資料一致性 · Step 3/5 · 學習目標：講清楚 L1 本地快取與 L2 Redis 各自的定位、逐級讀取與回填流程，以及它為什麼值得用一致性麻煩換熱點保護。

前言：Redis 明明很快，為什麼還需要本地快取

Redis 單機就能扛幾萬 QPS，對絕大多數系統來說已經綽綽有餘。可是當某個 Key 特別熱門，例如微博熱搜、秒殺商品詳情頁，情況就變了：如果同一時間有一百萬人要讀這一個 Key，這些請求都會送到 Redis 的同一台節點上。Redis 執行命令本身再快，也擋不住網卡頻寬被瞬間打滿，結果是整個 Redis 叢集跟著不可用。

問題不在 Redis 快不快，而在熱點太集中。要解決集中，就得把請求在更前面就吸收掉。於是人們在應用服務自己的記憶體裡再放一層快取，讓絕大多數請求連網路都不用走。這一課講的就是這個「本地加遠端」的雙層結構，以及在換來抗熱點能力的同時，你要付出什麼代價。

雙層結構：L1 本地，L2 遠端

標準的多級快取架構，通常是「L1 本地快取加 L2 分散式快取」的兩層。這個設計可以直接類比 CPU 的快取層級：離運算單元愈近的愈快、容量愈小，L1、L2、L3 一層一層往外。快取也是一樣，離應用程式愈近愈快。

L1：本地快取

L1 選型通常是 Caffeine，位置就在應用服務自己的 JVM 記憶體裡。它的特點是極快，訪問它就像訪問一個 HashMap，微秒級回應，完全沒有網路消耗。代價是容量小，受限於堆記憶體，只能存「熱點中的熱點」。它還有一個關鍵特性：有狀態。叢集裡 Server A 的本地快取，Server B 是拿不到的，每一台機器都各有一份。

L2：分散式快取

L2 就是 Redis，獨立部署的快取中介軟體。它的特點是快，毫秒級回應，但多了網路 IO 的開銷；容量大，可以存幾百 GB 甚至 TB 級資料；而且是無狀態的，所有應用節點共享同一份資料，一台機器看到的和另一台看到的完全一樣。

讀取流程：逐級往下查，查到就往回填

有了這兩層，一次讀取請求會依序問三個人，這是多級快取最核心的流程：

  1. 查 L1：請求進來先查 Caffeine。命中就直接回傳，這是最快的一條路。
  2. 查 L2：L1 沒命中，去查 Redis。命中就回傳，同時把資料回填到 L1，讓下次同一個請求能在本地命中。
  3. 查 DB：Redis 也沒命中，才去查資料庫。命中就回傳，並依序回填到 Redis 和 L1。

這個「逐級往下、命中往回填」的模式，讓資料會自動往最靠近使用者的地方聚集：愈熱門的資料，愈容易被留在 L1。這也是它對抗熱點的關鍵，熱點資料一旦被填進 L1，後續請求就在本機記憶體消化掉了。

一致性痛點：一百台機器的本地快取怎麼刪

多級快取真正難的地方，不在讀，而在寫之後的失效。這是面試官最想聽的部分。

當資料變更時，Redis 這一層很好處理：它是一個共享的遠端服務，你只要刪掉 Redis 裡對應的 Key，所有應用節點下次查詢就會一併看到新值。但 L1 完全不一樣，應用伺服器有一百台，這一百台機器記憶體裡的 Caffeine 各有一份拷貝，你刪得了 Redis，卻沒辦法用一個指令就刪掉一百台機器的本機記憶體。

解法是主動通知加上被動兜底：

  • 主動通知：資料變更時，先更新 DB、再刪除 Redis，同時發一條「資料變更訊息」到 MQ 的廣播 Topic。所有應用節點都監聽這個 Topic，一收到訊息就立刻清除本地 Caffeine 中對應的 Key。這樣一百台機器都能在同一時間附近完成失效。
  • 被動兜底：如果某台機器剛好掉線、沒收到廣播，本地的舊值就會殘留。所以 L1 的每一筆快取都必須設一個較短的 TTL，當作最後一道保險，保證舊值最多存活一小段時間就會自然消失。

這裡有個容易被追問的點：通報機制為什麼不用 Redis 的 Pub/Sub？因為 Pub/Sub 是「即發即棄」，訂閱者短暫斷線期間的訊息會永遠丟失，不保證可靠。相對地，MQ 的廣播有持久化與重試，更能保證每個節點都收到。工程上常兩者搭配，MQ 廣播為主、短 TTL 兜底為輔。

為什麼值得：本地快取換來的是熱點保護

面試官很可能會反問：「Redis 已經很快了，為什麼非要引入本地快取，把系統搞得更複雜？」答案其實只有兩個字：熱點。

回到最前面的極端場景：一百萬人同時請求同一個 Key。如果只有 Redis 這一層，一百萬個請求全都會送到 Redis 的同一個節點，它的網卡頻寬會被瞬間打滿，整個叢集跟著癱瘓。但加入 L1 之後，這一百萬個請求分散在一百台應用伺服器上，每一台機器只需要去 Redis 拉一次資料，剩下的九千九百九十九次請求全部在本地記憶體裡就消化掉了。

換句話說，本地快取把 Redis 的網路與頻寬壓力，轉移到了應用層的 CPU 與記憶體上。用一些一致性上的麻煩，換來對熱點的保護，這筆交易在多數網際網路場景裡是划算的。也因為這個價值，L1 通常不需要存太多東西，只要鎖定那幾個真正熱的 Key 就夠了。

小結

多級快取是「L1 本地加 L2 分散式」的雙層結構。L1 用 Caffeine，微秒級、容量小、有狀態，每台機器各一份；L2 用 Redis，毫秒級、容量大、無狀態，全體共享。讀取時逐級往下查，命中就往回填，讓熱資料自動聚到最前面。最大的難點是資料變更時要讓一百台機器的 L1 一起失效，做法是先更新 DB、再刪 Redis，同時用 MQ 廣播通知所有節點清本地快取，並替每筆 L1 快取設短 TTL 兜底。它存在的理由是抗熱點，把 Redis 單節點的頻寬壓力轉移到應用層的記憶體上。
