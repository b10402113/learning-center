從 JDBC 到 @Transactional：宣告式事務與 AOP 原理

Step 1/4 · Spring 事務管理與失效場景

學習目標

能講清楚 Spring 為什麼要把事務管理收進框架、編程式與宣告式兩種寫法的差別，以及 @Transactional 背後 AOP 代理「開啟、提交、回滾」的完整流程，並說出使用時要關注的三個設定維度。

前言：少了 commit 的那一行

先想像你寫了一個轉帳方法：從 A 帳戶扣一百元，再往 B 帳戶加一百元。上線後客訴來了，有人說錢被扣了、對方卻沒收到。追下去才發現，第二句 UPDATE 因為某個檢查失敗停了下來，但第一句早就送進資料庫了，於是錢就憑空少了一百。

根本問題在於：這兩句 UPDATE 必須「一起成功、一起失敗」，而資料庫預設的每次執行都是各自獨立的事。如果你用最原始的 JDBC 寫這段程式，那麼「一起」這件事完全是你的責任。你得手動關掉自動提交，成功時 commit、失敗時 rollback，而且每個會動到多張表的業務方法都要重寫一遍同樣的邏輯。這一節要講的，就是 Spring 怎麼把這段又長又容易漏的樣板程式，變成一行的 @Transactional。

沒有 Spring 的時代：JDBC 的樣板地獄

先看一段真實會出現的程式碼。假設我們要用 JDBC 做轉帳，並且確保兩句 UPDATE 同進同退，大概會寫成這樣：

Connection conn = dataSource.getConnection();
try {
    conn.setAutoCommit(false);        // 關閉自動提交：從這裡開始算一個交易
    deduct(conn, fromId, 100);        // 扣款
    add(conn, toId, 100);             // 加款
    conn.commit();                    // 兩句都成功，才一起提交
} catch (Exception e) {
    conn.rollback();                  // 任何一句出事，全部撤銷
    throw e;
} finally {
    conn.close();                     // 記得還連線
}

這段程式本身沒有錯，問題出在它會出現在每一個需要交易的業務方法裡。轉帳要一份、下單扣庫存要一份、退款要一份，複製貼上十幾次之後，只要有一段忘了 commit()、或是 catch 裡忘了 rollback()，就是一個線上事故。更麻煩的是，這些「開交易、提交、回滾、關連線」的程式和真正的業務邏輯（扣多少錢、檢查什麼條件）全部纏在一起，你想看懂「這支方法到底做了什麼生意」，還得先撥開一堆 JDBC 的噪音。

兩種寫法：編程式事務與宣告式事務

Spring 把「管理交易」抽出來，變成一個獨立的東西，叫做事務管理器。它的工作只有一句話：幫你開交易、提交、回滾。你只要告訴它「這段程式是一個交易」，剩下它處理。按照「你怎麼告訴它」的方式，分成兩種寫法。

第一種叫做編程式事務（programmatic transaction）。顧名思義，就是在程式碼裡自己下指令控制交易。例如 Spring 提供的 TransactionTemplate：

transactionTemplate.execute(status -> {
    deduct(fromId, 100);
    add(toId, 100);
    return null;
});

它比裸 JDBC 好多了，至少提交與回滾不用你管，但交易的邊界仍然硬寫在業務程式碼裡。業務邏輯一改、交易範圍要跟著調，你就得回來動這段程式。這種「框架的東西滲進業務程式」的特性，叫做侵入性。

第二種叫做宣告式事務（declarative transaction），也就是我們平常用 @Transactional 的那種。你只要在方法上掛一個註解，聲明「這裡是一個交易」，交易就自動生效：

@Transactional
public void transfer(Long fromId, Long toId, BigDecimal amount) {
    deduct(fromId, amount);
    add(toId, amount);
}

你看，業務邏輯乾淨得像什麼都沒發生。沒有 commit、沒有 rollback、也沒有連線管理，可是交易該有的行為一個都沒少。這種「不侵入業務程式碼」的優點，正是宣告式事務在實務上幾乎全面取代編程式事務的原因。而它之所以能這麼神奇，靠的就是 Spring 的另外一塊基石：AOP。

@Transactional 背後：代理物件在幫你開關交易

宣告式事務的原理是 AOP，具體做法是動態代理。當 Spring 啟動時掃到你的 Bean 上有 @Transactional，它不會直接把原本的物件放進容器，而是另外生成一個「代理物件」包在外面，再把代理物件交出去。別人注入拿到的、呼叫的，其實是這個代理。

當有人透過代理呼叫你的方法時，代理會偷偷插入一段交易邏輯，流程固定是這三步：

  1. 方法執行前：代理先向事務管理器要一個交易，底層做的事是關閉連線的自動提交（等同於剛剛 JDBC 範例裡的 setAutoCommit(false)）。
  2. 執行目標方法：代理把呼叫轉給真正的目標物件，跑你自己寫的業務邏輯。
  3. 方法執行後：如果一切正常、沒有異常往外丟，代理就提交交易；如果捕捉到異常，就回滾交易。

你可以把代理想成一位「代書」。你把文件交給代書，他在送件前先幫你蓋好章、填好表格，送件後再依照結果幫你歸檔或撤件。你本人從頭到尾只負責「把文件準備好」這件事，也就是寫業務邏輯；那些公務流程，代書全包了。所以講到宣告式事務，一句話總結就是：Spring 用代理把「開交易、提交、回滾」這段固定流程包在方法的外面，讓業務程式碼完全不必知道自己被交易包住。

這裡先埋一個伏筆，因為它正是後面失效場景的頭號兇手：既然交易是靠代理插進來的，那麼「呼叫有沒有經過代理」就決定了交易會不會生效。稍後會看到，同一個類別裡用 this.b() 互相呼叫時，走的根本不是代理，交易自然就消失了。

使用 @Transactional 要關注的三個維度

理解了代理流程，接下來要知道的是：這個代理的行為是可以調的，而面試與實務上真正要講清楚的，是三個維度。它們分別回答三個不同的問題：

維度它回答什麼問題預設值
傳播行為（propagation）一個有交易的方法去呼叫另一個有交易的方法時，兩者是共用一個交易，還是各開各的？REQUIRED（有就加入，沒有就新建）
隔離級別（isolation）多個交易同時跑時，彼此能看到對方多少還沒提交的資料？跟隨底層資料庫的預設值
回滾規則（rollback rule）方法丟出哪一種異常時，交易才該回滾？只對 RuntimeException 與 Error 回滾

隔離級別這個維度，Spring 自己不定調，通常直接沿用資料庫的設定；例如 MySQL 的 InnoDB 預設是可重複讀（REPEATABLE READ）。所以真正容易踩坑、也最常被追問的，是另外兩個：傳播行為決定「多個方法之間交易怎麼傳」，回滾規則決定「什麼樣的異常才觸發回滾」。這兩個維度各自會在後面用一節的篇幅展開，因為它們正是「明明加了註解卻沒回滾」的兩大來源。

小結

Spring 事務管理的目的是把「開啟、提交、回滾」這段與業務無關的樣板程式集中起來，讓業務程式碼保持乾淨。宣告式事務靠 AOP 動態代理實現：呼叫經過代理時，代理會在目標方法前開啟交易、方法後依有無異常決定提交或回滾。使用時要掌握三個維度：傳播行為管方法之間交易怎麼傳，隔離級別通常跟隨資料庫，回滾規則預設只認 RuntimeException 與 Error。

這三個維度裡，回滾規則是最容易讓人「以為寫對了、其實沒回滾」的一個。下一節就從一個問題出發：如果我的方法丟出的是受檢異常，例如 IOException，為什麼資料最後還是被提交了？答案就藏在 Spring 預設的回滾規則裡。
