七種傳播行為：REQUIRED、REQUIRES_NEW 與 NESTED

Step 3/4 · Spring 事務管理與失效場景

學習目標

能用「A 呼叫 B」的場景講清楚七種傳播行為是什麼，尤其是 REQUIRED、REQUIRES_NEW、NESTED 三者的差異，並說出各自適合與不適合的業務場景。

前言：兩個都有交易的方法碰在一起

上一節把單一方法內的回滾規則講完了，但真實的後端服務很少只有一個方法在動。常見的長相是：下單的 OrderService.create() 裡，除了寫入訂單，還會呼叫 LogService.record() 寫一筆操作日誌。如果這兩個方法都掛了 @Transactional，問題就來了：它們是各自開一個交易，還是共用同一個？更關鍵的是，如果我希望「訂單寫失敗要回滾，但日誌無論如何都要留下來」，這該怎麼設定？

這個問題的答案就是傳播行為（propagation）。它專門用來回答「一個有交易的方法，去呼叫另一個有交易的方法時，交易要怎麼傳遞」。Spring 總共定義了七種，但實務上九成的情況只會用到前三種。這一節就把這三種講透，其餘四種知道用途即可。

用一個比喻先抓住三種關係

在你還沒記住七個英文名字之前，先想像一間公司裡的兩種做事方式。第一種是「同一份合約」：A 部門和 B 部門一起負責一件案子，合約只有一份，案子成功一起記功、失敗一起負責，這就是共用。第二種是「另簽一份合約」：B 部門自己出去談一份獨立合約，A 部門原本的案子暫停等它；B 談成了算 B 的，談砸了也燒不到 A 的原始合約，這就是獨立。第三種是「同一份合約裡切出一個小階段」：B 的行為被記在這份大合約的某個階段裡，B 那個階段做壞了可以單獨作廢，但整份大合約一旦失敗，B 的階段也跟著一起完蛋，這就是嵌套。

共用、獨立、嵌套，正好對應 REQUIRED、REQUIRES_NEW、NESTED。抓住這三種關係，剩下的細節就只是填空。

REQUIRED：有就加入，沒有就新建

REQUIRED 是 Spring 的預設值，也是 90% 業務場景的選擇。它的規則是：如果呼叫進來時已經有交易，就加入那個交易；如果沒有，就自己開一個新的。

假設 OrderService.create() 是 A、LogService.record() 是 B，兩者都用預設的 REQUIRED。當 A 執行到一半呼叫 B 時，A 已經開啟了一個交易，B 看到有交易正在跑，就直接加入，不會另開。結果是 A 和 B 共用同一個物理交易。這件事最實際的後果是：只要 A 或 B 任何一方報錯回滾，整個交易（A 加 B 的所有操作）會一起回滾，誰也跑不掉。

所以「用 REQUIRED 把日誌和業務綁在一起」在大部分情況下是危險的。業務失敗時，你不想留下的失敗記錄往往也一起被抹掉了。這正是需要第二種行為的場合。

REQUIRES_NEW：掛起當前交易，自立門戶

REQUIRES_NEW 的規則是：不管當下有沒有交易，都自己開一個全新的交易；如果當下有交易，先把它掛起（suspend）。等 B 執行完、提交了，A 原本的交易才恢復繼續跑。

用業務日誌的例子就很好懂：

@Service
public class OrderService {

    @Autowired
    private LogService logService;

    @Transactional                      // 預設 REQUIRED
    public void create(Order order) {
        orderMapper.insert(order);
        logService.record("建立訂單 " + order.getId());   // 另開獨立交易
        // 若後面還有其他操作失敗，訂單會回滾，但日誌已獨立提交
    }
}

@Service
public class LogService {

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void record(String message) {
        logMapper.insert(message);
    }
}

這段設定的效果是：record() 的交易和 create() 的交易在物理上完全隔離。就算 A 之後發生錯誤整筆回滾，日誌因為已經在 B 的交易裡提交過了，不會被牽連。反過來，B 提交失敗或拋出異常，也不會直接導致 A 回滾，除非 A 自己捕捉到 B 的異常後決定跟著回滾。

這裡有個很常被追問的細節：因為 REQUIRES_NEW 是「掛起一個、再開一個」，同一時間就有兩個交易並存，而每個交易都要佔用一條資料庫連線，所以它會比 REQUIRED 多吃一條連線。在高併發又用著有限連線池的系統裡，如果濫用 REQUIRES_NEW，是有可能把連線池佔滿的。知道這一層，面試時就比只會背「自立門戶」多一分。

NESTED：同一交易內的保存點

NESTED 的規則是：如果當下已經有交易，就在那個交易裡建立一個保存點（savepoint）來執行；如果沒有，行為就跟 REQUIRED 一樣，自己開一個新的。

它和 REQUIRES_NEW 最大的差別，在於「獨立到什麼程度」。REQUIRES_NEW 是兩個真正獨立的物理交易；NESTED 則始終待在同一個物理交易裡，只是在裡面插了一個可以單獨回滾的記號點。它的回滾行為因此是不對稱的：

  • 如果子方法 B 出錯：只回滾到保存點，也就是只撤銷 B 自己的操作。A 可以選擇接住這個異常、繼續往下做，A 前面的操作完全不受影響。
  • 如果外層 A 出錯：既然大家其實在同一個物理交易裡，A 一旦回滾，B 做過的事也會一起被撤銷。

換句話說，NESTED 建立的是一種「父子關係」：子可以單獨死，但父一死，子一定跟著陪葬。它適合那種「子操作失敗無所謂、但母交易成功時子操作要留下」的情境，例如批次匯入時，每一筆的失敗只跳過自己那一筆，其他筆照樣提交。要注意的是，NESTED 依賴資料庫的保存點功能，所以只有在使用支援保存點的資料庫與對應的事務管理器時才成立。

三種關係的對照

把三種放在同一張表上看，差異會更清楚：

行為與當前交易的關係B 失敗時A 失敗時典型場景
REQUIRED（預設）共用同一個物理交易A、B 一起回滾A、B 一起回滾一般業務流程，最常用
REQUIRES_NEW掛起 A，另開獨立交易只影響 B（除 A 自行處理）A 自己回滾，B 不受影響日誌、稽核等必須留下來的操作
NESTED同交易內建保存點只回滾到保存點，A 可續行B 跟著 A 一起回滾批次中單筆失敗可跳過

另外四種：對交易狀態的硬性約束

剩下四種在一般業務開發中用得少，但它們的用途都可以用「對交易狀態的約束」來理解：

  • SUPPORTS：有交易就用，沒有就當一般非交易程式跑。適合「有被包在交易裡就順便，沒被包也無所謂」的查詢工具方法。
  • NOT_SUPPORTED：要求以非交易方式執行。如果當下有交易，先把它掛起。適合不希望被交易拖著、例如要立刻看到資料庫真實狀態的操作。
  • MANDATORY：要求一定要有交易，如果呼叫進來時沒有交易就直接丟出異常。它是一種「強制規定」，用來確保這個方法只能被包在別人的交易裡呼叫。
  • NEVER：要求一定不能有交易，如果呼叫進來時有交易就直接丟出異常。和 MANDATORY 剛好相反。

把這四種和前面三種合起來，就是完整的七種傳播行為。面試時切記：不要試圖一次背七個。先把 REQUIRED、REQUIRES_NEW、NESTED 用場景講清楚，再補一句「其餘四種是對交易狀態的約束，實務少用」，這樣的回答比流水帳清楚得多。

小結

傳播行為解決的是「業務方法互相呼叫時，交易怎麼傳遞」。最重要的是三種：REQUIRED 是「有就加入、沒有就新建」，共用同一個物理交易，一起成功一起失敗，是預設值；REQUIRES_NEW 會掛起當前交易、另開一個獨立交易，適合日誌這種不能跟著業務回滾的操作，代價是多吃一條資料庫連線；NESTED 是在同一交易裡建保存點，子回滾不影響父、父回滾子跟著走。其餘四種（SUPPORTS、NOT_SUPPORTED、MANDATORY、NEVER）則是對交易狀態的硬性約束，一般業務少用。

到這裡，宣告式事務的三塊拼圖已經湊齊：代理原理、回滾規則、傳播行為。但知道規則不等於規則一定會生效。實務上最常出事的，往往是規則明明寫對了，卻因為某個小細節而完全沒被觸發。最後一節要把四種最經典的失效場景攤開來看。
