回滾規則：為什麼碰上受檢異常就不回滾

Step 2/4 · Spring 事務管理與失效場景

學習目標

能說出 Spring 預設只對 RuntimeException 與 Error 回滾這條規則、分辨受檢與非受檢異常的差別，並解釋為什麼 rollbackFor 在實務上幾乎是必加的設定。

前言：異常明明丟出來了，資料卻沒回滾

上一節我們確認了一件事：代理會看著方法有沒有丟出異常，來決定提交還是回滾。於是很多人就有一個直覺：「我只要在方法裡丟異常，交易就會回滾」。聽起來很合理，但實際上你很可能遇過這種情況：程式碼裡明明 throw new IOException("檔案壞了")，執行完去查資料庫，發現資料竟然已經提交、沒有撤銷。

這不是 Spring 壞了，而是它的預設規則和你想的不一樣。這一節要把這條規則講清楚：Spring 預設只認某些種類的異常。搞懂它，你才知道為什麼有些異常丟了有用、有些丟了等於沒丟。

先分清楚：受檢異常與非受檢異常

要理解這條規則，得先回到 Java 的異常階層。所有可以被丟出的東西都繼承自 Throwable，它底下再分成兩大支：一支是 Error，一支是 Exception。而真正關鍵的分界，落在 Exception 這一支裡面，它又分成兩種個性完全不同的異常。

分類代表類別編譯器會管嗎典型情境
非受檢異常（unchecked）RuntimeException 及其子類，例如 NullPointerException、IllegalArgumentException不管，可以丟也可以不接程式錯誤、參數不合法、狀態不對
受檢異常（checked）Exception 底下非 RuntimeException 的類別，例如 IOException、SQLException會管，要嘛 catch 要嘛在方法上宣告外部環境問題：檔案、網路、資料庫

兩者最大的差別在「編譯器管不管」。受檢異常被迫你要面對它：要嘛用 try-catch 接住，要嘛在方法簽章上寫 throws 把它往外丟。非受檢異常則沒有這個限制，程式設計師通常不會特地處理它，因為它代表的是「不該發生卻發生了」的狀況。

Spring 的預設規則：只認 RuntimeException 與 Error

現在回到那條讓很多人栽跟頭的規則：當 @Transactional 沒有特別設定時，Spring 只在方法丟出 RuntimeException 或 Error 時回滾。如果你丟的是受檢異常（例如 IOException、SQLException），而且沒有另外設定，Spring 會把這個方法當成「正常結束」，然後照常提交交易。

為什麼會有這麼不直覺的預設？這背後是 Spring 對異常的一種設計假設。受檢異常在 Java 的定義裡，代表「這是方法契約的一部分、是可以預期發生的情況」；你既然在方法上宣告了它可能丟出，就表示呼叫方本來就該針對它做處理，也許補救、也許重試，不必然要整筆交易作廢。反過來，RuntimeException 通常代表「沒有預期到的錯誤」或「程式邏輯壞了」，這種狀況下繼續把交易提交下去是不安全的，所以預設回滾。也就是說，Spring 會這樣設計，是因為它判斷受檢異常不一定代表業務失敗。

問題是，這個假設和實務常常對不上。很多團隊的業務異常，例如「庫存不足」、「帳戶已凍結」、「餘額不夠」，都被寫成自訂的受檢異常。這時候如果沒有額外設定，一筆該回滾的交易就會被默默提交，錯誤就此埋下。

解法：用 rollbackFor 把範圍畫大

要讓受檢異常也能觸發回滾，做法是在註解上明確指定。最常見的寫法是把回滾範圍擴大到整個 Exception：

@Transactional(rollbackFor = Exception.class)
public void transfer(Long fromId, Long toId, BigDecimal amount) throws BusinessException {
    deduct(fromId, amount);
    if (amount.compareTo(BigDecimal.ZERO) <= 0) {
        throw new BusinessException("金額必須大於零");
    }
    add(toId, amount);
}

這裡的 rollbackFor 意思很直接：「只要丟出 Exception 這個家族（含所有子類，當然也含各種受檢異常），就回滾」。既然 RuntimeException 本來就是 Exception 的子類，這個設定等於把「預設只認一部分」變成「全部都認」，因此實務上幾乎是標配。面試時如果只回答「預設只對 RuntimeException 回滾」，那只是講了規則；能補上「所以我們通常會加 rollbackFor = Exception.class」，才是把規則接到實務。

反過來也有一個對應的設定叫 noRollbackFor，用來指定「就算丟出這個異常也不要回滾」。它適合那種「雖然丟了異常，但業務上仍想把已完成的資料保留」的特例。不過老實說，這種情境不多，真正天天會用到的是 rollbackFor。

還有一個容易被忽略的前提：異常要能「跑出來」

設定正確的回滾規則只是第一步。別忘了代理是怎麼判斷的：它在方法外面等，看有沒有異常穿過它的地盤往外跑。如果異常在到達代理之前就被你自己的程式碼攔下來了，代理根本不會知道出過事。

換句話說，就算你加了 rollbackFor，只要你的 catch 區塊把異常吃掉、沒有再往外丟，交易照樣會提交。這個「異常被吞」的坑，會和自調用、型別不符、修飾符不對一起，在第四節完整展開。這裡先記住一句：回滾規則是「認哪些異常」，而異常必須真的被代理看見，規則才有機會啟動。

小結

Spring 宣告式事務預設只對 RuntimeException 與 Error 回滾，遇到受檢異常（如 IOException、SQLException）不會回滾，除非明確設定。這條規則背後是 Spring 對異常的假設：受檢異常算可預期的狀況，不一定代表業務失敗。實務上為了避免漏回滾，通常會直接在 @Transactional(rollbackFor = Exception.class) 把範圍擴大到全部異常；而無論怎麼設定，異常都必須真的往外丟到代理手上，回滾才會啟動。

到這裡，單一方法內「什麼情況會回滾」已經講完了。但真實的系統很少只有一個方法在動，服務 A 呼叫服務 B、B 再呼叫 C，如果每個方法都掛了 @Transactional，它們之間到底是共用一個交易，還是各開各的？這就是下一節要處理的傳播行為。
