宣告式事務失效：自調用、異常被吞、型別不符與修飾符

Step 4/4 · Spring 事務管理與失效場景

學習目標

能歸納出 @Transactional 失效的四類場景：方法自調用、異常被吞、異常型別不符、修飾符不對，指出每一類分別是「繞過代理」還是「破壞了回滾條件」，並說出對應的解法。

前言：註解在、異常也在，交易卻沒生效

前面三節把規則一條一條建立起來：代理會在方法前後開關交易、預設只對 RuntimeException 回滾、不同傳播行為決定交易怎麼傳。照理說，只要 @Transactional 標上去、該丟的異常丟出去，交易就該運作。但實務上最讓人心累的，偏偏是那種「每一條規則看起來都對，結果資料還是被提交了」的狀況。

這一節是這個節點的收尾，也是最有實戰價值的一節。我們要把這些踩坑歸納成四類，而且會發現它們其實只有兩條根：要嘛是呼叫繞過了代理，要嘛是異常沒能觸發回滾條件。抓住這兩條根，你就不必死背案例。

根因一：繞過代理，等於沒人幫你開交易

還記得第一步的結論嗎？交易是代理插進來的，所以「呼叫有沒有經過代理」決定了交易存不存在。偏偏有一種寫法，會讓呼叫神不知鬼不覺地跳過代理，那就是方法自調用，也是最經典、最容易踩的失效場景。

場景：類別內部的 this 呼叫

想像一個 Service，對外的方法 A 沒有交易，它去呼叫同一個類別裡標了 @Transactional 的方法 B：

@Service
public class OrderService {

    public void create(Order order) {
        saveOrder(order);
        this.pay(order);          // 直接用 this 呼叫，走的是目標物件本身
    }

    @Transactional
    public void pay(Order order) {
        // 這裡的扣款、更新狀態，本該在同一個交易裡
    }
}

你以為 pay() 有交易，但實際上它完全沒有。原因是：Spring 交給外部的是代理物件，而 create() 被呼叫時，執行的是「目標物件」的方法；當它在內部寫 this.pay()，this 指向的就是目標物件本身，不是代理。等於你自己把代理繞過去了，AOP 的攔截器根本沒機會插手，交易邏輯自然不會執行。這就像你把文件直接交給了本人，而不是交給會幫你辦流程的代書；代書從頭到尾沒經手，當然沒有幫你蓋章。

解法有三種，實務上最推薦的是把 B 抽到另一個 Service，讓呼叫變成跨物件的呼叫，自然會經過代理：

@Service
public class OrderService {
    @Autowired
    private PaymentService paymentService;

    public void create(Order order) {
        saveOrder(order);
        paymentService.pay(order);   // 跨 Bean 呼叫，經過代理，交易生效
    }
}

如果礙於結構不方便抽出去，也可以透過 AopContext.currentProxy() 拿到當前代理再呼叫，或在類別裡把自己注入進來呼叫；但後兩者都比較繞，而且 AopContext 還需要額外開啟 exposeProxy = true，所以能抽就抽是比較乾淨的做法。

根因二：異常沒能觸發回滾條件

另一條根比較隱晦：呼叫確實經過了代理，但代理最後沒收到「該回滾」的訊號。這種情況底下有三種常見的成因。

場景一：異常被業務程式碼吞掉了

很多人在 @Transactional 方法裡順手寫了 try-catch，想把異常記個 log：

@Transactional
public void transfer(Long fromId, Long toId, BigDecimal amount) {
    try {
        deduct(fromId, amount);
        add(toId, amount);
    } catch (Exception e) {
        log.error("轉帳失敗", e);      // 只記錄，沒有再丟出去
    }
}

這段程式碼的意圖很好，但後果是：代理在方法外面等異常，結果什麼都沒等到。在它眼裡，這個方法「正常結束」了，於是照常提交。要記住 AOP 的判斷邏輯極其單純：捕捉到異常就回滾，沒捕捉到就提交。異常被你自己 catch 住又沒繼續往外丟，等於把證據藏了起來。要修很簡單：catch 之後 throw e; 再丟出去；如果當下不方便往外丟，也可以在 catch 裡呼叫 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()，手動把當前交易標記成「只能回滾」。

場景二：異常型別不符

這個場景其實就是上一節講的規則落到實戰。方法丟出了異常，但那是 Spring 預設不認的受檢異常，例如 IOException、SQLException，於是交易沒有回滾。解法也一樣：在註解上補 rollbackFor = Exception.class，把回滾範圍擴大到所有異常。這裡之所以再提一次，是因為它在失效排查裡太常出現了。當你確認「呼叫有經過代理、異常也有丟出」，下一步就該檢查「丟出來的異常型別，Spring 認不認」。

場景三：方法的修飾符不對

最後一種情況是註解本身「掛錯了地方」：你把 @Transactional 加在 private、final 或 static 方法上。

為什麼這會失效？回到代理的兩種實作就知道。JDK 動態代理是「基於介面」的，它產生一個實作同樣介面的代理類別，把呼叫導向攔截器；private 方法根本不屬於介面，代理無從攔截。CGLIB 則是「基於繼承」的，它產生目標類別的子類別、覆寫方法來插入增強；但 private 方法不能被子類別覆寫，final 方法被明令禁止覆寫，static 方法屬於類別而不是物件、也不會被多型覆寫。三種修飾符都會讓「覆寫或實作方法」這件事做不到，代理自然加不進去。解法很單純：把要交易的方法改成 public，並拿掉 final（也不要放在 static 方法上）。

順帶一提，還有一個相關但常被忽略的前提：這個被呼叫的物件本身必須是 Spring 容器管理的 Bean。如果你自己 new 一個 Service 出來用，那它從頭到尾都沒有被代理過，任何事務設定都不會生效。

四類失效場景總整理

把四類放在一起，可以清楚看到它們各自落在哪條根上：

失效場景現象根本原因解法
方法自調用同一類別內呼叫，交易沒生效繞過代理（this 呼叫目標物件）抽到另一個 Service；或用 AopContext 取當前代理
異常被吞明明出錯，資料卻提交了異常沒傳到代理catch 後重新丟出；或手動 setRollbackOnly
異常型別不符丟了異常，卻沒回滾受檢異常不在預設回滾範圍補 rollbackFor = Exception.class
修飾符不對註解加了等於沒加private/final/static 無法被代理覆寫改成 public 且非 final/static

把它變成一條排查決策鏈

與其背四個案例，不如記住一條可以被反覆使用的檢查順序。當你遇到「@Transactional 好像沒作用」，依序問三個問題：

  1. 這次呼叫有沒有經過代理？是不是同一個類別裡用 this 呼叫？被呼叫的物件是 Spring 管理的 Bean 嗎？
  2. 異常有沒有真的丟到代理面前？是不是被 catch 吞掉了、沒有再往外丟？
  3. 丟出的異常型別，Spring 認不認？方法修飾符允許被代理嗎？是不是受檢異常沒設 rollbackFor？方法是不是 private、final、static？

這三個問題問完，九成以上的事務失效都能定位。面試時若能把失效「歸因到繞過代理或破壞回滾條件這兩條根」，再順著決策鏈說明四類案例，會比零散背誦有說服力得多。

小結

宣告式事務失效看似五花八門，本質只有兩條根：繞過 AOP 代理，或異常沒能觸發回滾。對應四類經典場景：方法自調用走的是目標物件而非代理，交易邏輯根本沒被執行；異常被吞讓代理誤以為方法成功而提交；異常型別不符時受檢異常不在預設回滾範圍，需要 rollbackFor；修飾符不對時 private、final、static 方法無法被代理覆寫，註解形同虛設。排查時依序確認「有沒有經過代理、異常有沒有丟出來、型別與修飾符對不對」即可。
