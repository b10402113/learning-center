HashMap 的演進與併發 Map

Step 6/6 · 從 1.7 到 1.8，看見資料結構與併發粒度的雙重進化

前言：一個 CPU 突然衝到 100% 的夜晚

有個經典的線上事故：某個服務上線後，大部分時間都運作正常，偶爾卻會毫無預警地把 CPU 撐到 100%。重啟服務後又恢復正常，讓人一度以為是暫時性的故障。

最後查出來，兇手是一個被多個執行緒共用的 HashMap，而且服務執行在 JDK 1.7 上。它在併發擴容時把鏈結串列串成了環，之後任何一次 get 只要走進那個桶，就會在環裡無限繞圈。

這個事故同時帶出兩個面試很常追問的問題：HashMap 的內部結構為什麼從 1.7 演進到 1.8？它又為什麼不是執行緒安全的？把這條線講清楚之後，ConcurrentHashMap 為什麼要一步步縮小鎖的粒度，也就不再只是背誦結論。

這一節會從 HashMap 的結構、插入與擴容方式開始，接著說明紅黑樹的 8/6 閾值與 0.75 負載因子，最後再看 ConcurrentHashMap 如何把併發控制細化到單一桶位。

結構演進：從「陣列＋鏈結」到「陣列＋鏈結＋紅黑樹」

JDK 1.7 的 HashMap 底層是 Entry 陣列。當多個 key 的 hash 值落在同一個下標時，就使用拉鏈法，在該位置掛上一條鏈結串列。

這種設計在一般情況下查詢很快，但它有一個明顯弱點：如果大量 key 的 hash 值相同，或只是運氣不好，許多資料都集中在同一條鏈上，查詢複雜度就會從 O(1) 退化成 O(N)。鏈結越長，查詢需要走過的節點越多，CPU 也會跟著忙起來。

JDK 1.8 把結構升級成 Node 陣列，並加入紅黑樹作為退化時的兜底方案。當鏈結長度超過 8，而且陣列長度大於 64 時，鏈結會轉成紅黑樹，查詢複雜度便能從 O(N) 降到 O(log N)。即使一個桶裡掛了一萬筆資料，樹查找也只需要十幾次比較。

不過，紅黑樹不是預設選項。樹節點大約比鏈結節點多佔一倍空間；在資料量很少時，直接遍歷鏈結反而比操作紅黑樹更快，因為紅黑樹還要處理旋轉與變色。因此，HashMap 的策略是：平常使用鏈結，真的發生嚴重碰撞時，才升級成樹。

頭插法改成尾插法：不只是寫法不同

兩個版本在插入鏈結節點時，也採用了不同策略。JDK 1.7 使用頭插法，新節點會直接放到鏈結最前面。當時的想法是，新加入的資料可能很快又會被訪問，把它放在前面可以少走幾步。

JDK 1.8 則改用尾插法，新節點會放到鏈結尾端。這個改動在擴容時特別重要：搬移資料後，鏈結中元素的相對順序可以維持，不會像頭插法那樣整條鏈被倒置。

而且，為了判斷鏈結是否需要樹化，本來就必須遍歷鏈結。既然已經走到尾端，順手把新節點接在後面，並不會額外增加太多成本。更重要的是，保持順序能避開 JDK 1.7 併發擴容時可能形成環的問題。

為什麼樹化閾值是 8，退化閾值是 6？

既然紅黑樹查詢比較快，為什麼不從一開始就全部使用紅黑樹？原因很實際：樹節點比較佔空間，而且在資料很少時，鏈結的簡單遍歷通常更快。紅黑樹的角色是處理極端碰撞，而不是取代所有鏈結。

那麼，為什麼樹化閾值選在 8？根據 JDK 原始碼註解，在 hash 函式設計良好的情況下，節點在各個桶中的分布大致服從泊松分布。一個桶裡有 1 個節點的機率約為 60%，但有 8 個節點的機率只有約 0.00000006，不到億分之一。

換句話說，正常情況下幾乎不會走到 8。當一個桶真的長到這麼長，通常代表 hash 演算法可能有問題，或系統正遭遇 Hash DoS 攻擊。這時候，犧牲一些記憶體空間來換取穩定的查詢時間，才有意義。

退化閾值則設為 6，是為了避免資料結構在鏈結與紅黑樹之間來回震盪。假設樹化與退化都使用同一個數字 8，當資料量反覆在 8 附近變動時，幾次 put 和 remove 就可能讓結構不斷切換。

把退化閾值降到 6，中間保留 7 這個緩衝區，就能避免這種「剛樹化又立刻退化」的顛簸。

擴容：容量翻倍，以及更聰明的搬移方式

HashMap 內部有一個擴容門檻：

threshold = capacity * loadFactor

預設容量是 16，負載因子是 0.75，所以預設門檻為：

16 × 0.75 = 12

當元素數量超過這個門檻，HashMap 就會觸發 resize()，建立一個容量變成兩倍的新陣列。

JDK 1.7 搬移資料時，做法比較直接：遍歷舊陣列中的每個元素，重新計算 hash，再使用 hash % newCap 算出新下標。資料量一大，這個過程就會花費不少時間。

JDK 1.8 利用了「容量一定是兩倍」這個條件，設計出更簡單的判斷方式。容量翻倍後，元素的新位置只有兩種可能：

  • 留在原本的下標。
  • 移動到「原下標 + 舊容量」的位置。

判斷時只要檢查：

e.hash & oldCap

結果為 0，就留在原本的位置；結果不為 0，就搬到原下標加上 oldCap 的位置。這樣不需要重新計算 hash，也能把原本較長的鏈結拆散，搬移效率更高。

負載因子為什麼是 0.75？

負載因子代表陣列使用到什麼程度時，HashMap 應該擴容。它本質上是在時間與空間之間做取捨。

如果設成 1.0，陣列幾乎填滿後才擴容，記憶體利用率看起來比較高，但桶中的碰撞會變多，查詢效率可能逐漸往 O(N) 靠近。

如果設成 0.5，陣列只用到一半就擴容，碰撞會比較少，查詢也比較快；但另一半空間還沒充分使用，就必須建立兩倍大的陣列，記憶體浪費與擴容成本都會增加。

0.75 是根據統計規律得到的折中點：它讓碰撞機率維持在可接受的低水準，同時也不會讓陣列長期留下過多空間。

JDK 1.7 的死循環是怎麼發生的？

回到文章開頭的 CPU 事故。JDK 1.7 的 transfer() 在搬移資料時使用頭插法，因此會把鏈結順序反轉。原本的鏈結如果是：

A -> B

搬到新陣列後，可能會變成：

B -> A

現在假設兩個執行緒 T1、T2 同時觸發擴容。T1 處理到節點 A 時，暫時記住：

e = A
next = B

接著 T1 被 CPU 暫停。T2 趁機完成擴容，因為使用頭插法，新陣列中的鏈結變成 B -> A。

當 T1 醒來時，它手上的資訊仍然是舊的鏈結關係，繼續依照原本的指標搬移資料。兩個執行緒交錯操作後，可能形成：

A.next = B
B.next = A

這就把鏈結串成了環。之後任何一次 get 只要走進這個桶，就會在 A 與 B 之間無限循環，CPU 也就一路飆到 100%。

JDK 1.8 改用尾插法後，擴容時會維持鏈結中元素的相對順序，不再因為鏈結倒置而形成上述環狀結構，因此根除了這個死循環問題。

但要注意：這不代表 JDK 1.8 的 HashMap 就變成執行緒安全。它仍然可能在併發寫入時覆蓋彼此的資料，或發生遺失寫入。需要多執行緒安全的 Map 時，應該使用 ConcurrentHashMap。

ConcurrentHashMap：把鎖的粒度一路縮小

JDK 1.7：分段鎖

JDK 1.7 的 ConcurrentHashMap 使用「分段鎖」設計。它像是一個套娃：最外層是 Segment 陣列，每個 Segment 裡面又包含一個小型的 HashEntry 陣列。

換句話說，一張大哈希表被切成了多個區段，預設通常是 16 個。每個 Segment 直接繼承 ReentrantLock。要修改某筆資料，必須先取得它所在 Segment 的鎖。

這比整張表只使用一把鎖好很多，但鎖的粒度仍然偏粗。假設某個 Segment 裡有幾千筆資料，只要其中一筆正在修改，其他執行緒想修改同一個 Segment 裡的任何資料，都必須排隊等待。

而且，併發度也受限於 Segment 的數量。預設是 16 個 Segment，初始化後這個數量還不能再擴大。因此，即使系統有更多執行緒可以同時工作，也可能被這 16 把鎖卡住。

JDK 1.8：CAS 加上 synchronized

JDK 1.8 重新設計了 ConcurrentHashMap，直接沿用 HashMap 的「陣列＋鏈結＋紅黑樹」結構，移除 Segment，改用 CAS + synchronized：

  • 如果目標槽位是空的，就不需要加鎖，直接使用 CAS 嘗試放入新節點；如果失敗，再重試。
  • 如果目標槽位已經有資料，才使用 synchronized 鎖住該鏈結或紅黑樹的頭節點。

這樣一來，鎖的粒度就從「一個 Segment」縮小到「一個桶」。同一個陣列中的其他桶，只要沒有資料衝突，仍然可以被其他執行緒同時修改。

那為什麼不用 ReentrantLock，而改用 synchronized？因為 JDK 1.6 之後，synchronized 已經經過許多最佳化，例如偏向鎖與輕量級鎖。在低競爭場景下，它的效能不輸 ReentrantLock，而且不需要額外維護 AQS 佇列，記憶體成本也比較低。

因此，JDK 1.8 的並發粒度更細。陣列有多長，理論上就能提供多少個獨立的桶位；隨著陣列擴容，能夠同時處理不同桶位的執行緒數量也會跟著增加。

多執行緒協助擴容

JDK 1.8 的 ConcurrentHashMap 甚至讓擴容也能由多個執行緒一起完成。它使用一個游標變數 transferIndex，把整個陣列切成一段一段的任務區間。

每一段的步長，也就是 Stride，預設約為 16。多個執行緒透過 CAS 競爭領取工作區間，領到哪一段，就負責搬哪一段，彼此之間不會重複處理同一批桶位。

那麼，一個正在執行 put 的執行緒，怎麼知道某個桶是不是正在擴容？ConcurrentHashMap 使用一個特殊節點 ForwardingNode 來傳遞這個訊息。

當某個槽位的資料搬移完成後，原本的位置會放入一個 hash 值為 -1 的 fwd 節點。其他執行緒如果剛好要對這個下標執行 put，發現它是 fwd，就知道這裡正在擴容，而且這個槽位已經搬完。

它不會阻塞等待，也不會傻傻地停在原地，而是直接呼叫 helpTransfer()，到 transferIndex 領取一份尚未完成的任務，加入搬運工作。

搬遷時仍然使用與 HashMap 1.8 相同的規則，透過：

hash & oldCap

判斷元素要留在原位置，還是移動到「原下標 + oldCap」的位置。至於讀操作，如果遇到 fwd 節點，就會直接轉往新陣列查找，因此擴容期間的讀寫都不需要完全停下來等待。

兩個容易被追問的細節

為什麼 ConcurrentHashMap 不允許 key 或 value 為 null？

核心原因是要消除「二義性」。單執行緒使用 HashMap 時，null 可以代表兩種情況：

  • 這個 key 不存在。
  • 這個 key 存在，但對應的 value 是 null。

在 HashMap 中，呼叫 get 得到 null 後，還可以再呼叫 containsKey 確認是哪一種情況。因為只有一個執行緒，這兩次操作之間的資料不會突然被其他執行緒改掉。

但在多執行緒環境下，這種「先檢查，再採取行動」不是原子的。你呼叫 get 得到 null，還沒來得及呼叫 containsKey，另一個執行緒可能已經刪除了這個 key，或修改了它的 value。

此時，第二次檢查得到的結果可能已經和第一次不同。為了避免這種無法說清楚的狀態，ConcurrentHashMap 乾脆禁止 key 與 value 使用 null。

size() 如何在高併發下統計？

ConcurrentHashMap 的 size() 不會遍歷所有鏈結，也不會只依賴一個 AtomicLong。如果幾百個執行緒同時更新同一個 AtomicLong，就會競爭同一個變數，CAS 失敗率升高，執行緒可能反覆自旋。

它採用類似 LongAdder 的「分散熱點」策略，內部包含一個 baseCount 與一個 CounterCell 陣列。

併發程度較低時，執行緒直接使用 CAS 更新 baseCount。如果更新失敗，代表競爭變激烈，就依照執行緒的探針雜湊值，把更新分散到某個 Cell，對那個 Cell 個別執行 CAS。

呼叫 size() 時，再把 baseCount 與所有 Cell 的值加總起來，就能得到目前的元素數量，而不需要加鎖。

這種做法的代價是結果具有弱一致性。你剛算出 100，下一毫秒可能就有另一個執行緒加入資料，使數量變成 101。它適合用來取得一個當下的近似值，而不是把結果當成永遠不變的精確快照。

把整條演進路線串起來

從 HashMap 1.7 走到 1.8，再看到 ConcurrentHashMap，表面上是在學幾個集合類別的實作細節，實際上是在看同一組工程問題如何被逐步處理。

資料結構方面，HashMap 從單純的陣列加鏈結，演進到加入紅黑樹來處理極端碰撞；插入方式則從頭插法改成尾插法，避免擴容時鏈結倒置與形成環。

擴容方面，JDK 1.8 利用容量翻倍的特性，透過 hash & oldCap 快速判斷元素的新位置，省下重新計算 hash 的成本。ConcurrentHashMap 更進一步，讓多個執行緒能透過任務分段協助搬移資料。

併發控制方面，設計則從 JDK 1.7 的「一個 Segment 管一大片資料」，縮小到 JDK 1.8 的「一個桶各自處理」。空桶用 CAS，已有資料的桶才鎖住頭節點，讓彼此沒有衝突的操作可以同時進行。

當你能把這些變化按照「原本遇到什麼問題、改動解決了什麼、付出了什麼代價」講一遍，HashMap 的面試題就不再只是零散的八股。你其實已經理解了它為什麼這樣設計，以及每一次演進究竟在換取什麼。
