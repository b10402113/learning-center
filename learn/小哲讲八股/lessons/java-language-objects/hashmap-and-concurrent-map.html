HashMap 的演進：從鏈表，到紅黑樹與併發版本

Step 6/6 · Java 語言與物件

學習目標：看懂 HashMap 從 JDK 1.7 到 1.8 的結構、插入與擴容差異；理解紅黑樹的 8／6 閾值、0.75 負載因子的取捨，以及 ConcurrentHashMap 兩代如何逐步縮小鎖的範圍。

先抓住主線：1.7 到 1.8 改了什麼

HashMap 的版本演進，不是單純「換了個資料結構」，而是針對幾個實際問題逐一補強：鏈表太長時查詢變慢、並發擴容可能形成死循環，以及搬遷資料時不必每次都重新計算 hash。

面向JDK 1.7JDK 1.8
資料結構陣列 + 鏈表陣列 + 鏈表 + 紅黑樹
插入方式頭插法尾插法
擴容搬遷重新計算每個節點的 hash用 hash & oldCap 判斷留在原位或搬到原位加舊容量

1.7 使用頭插法，平常在單執行緒下沒有問題；但多執行緒同時擴容時，鏈表順序可能被改亂，甚至形成環。1.8 改用尾插法，保留原本的鏈表順序；同時加入紅黑樹，處理極端的 hash 衝突；擴容時也改用位元運算，省下重新計算位置的成本。

鏈表為什麼要變成紅黑樹

雜湊表的理想狀態，是每個桶裡只有少量節點。但如果很多 key 剛好落進同一個桶，鏈表就會越串越長。查找原本接近 O(1)，一旦退化成長鏈表，最壞情況就會變成 O(N)，像是在抽屜裡找東西，卻把所有物品疊成一條長龍。

紅黑樹能把最壞查找成本壓到 O(logN)。不過，樹節點比鏈表節點大約多佔一倍空間，衝突不嚴重時，直接用樹反而浪費。因此 HashMap 不是一開始就建樹，而是等鏈表長到一定程度，才把它轉成紅黑樹。

為什麼轉樹是 8，退回鏈表是 6

轉樹閾值設定為 8，和雜湊分布的機率有關。在理想的雜湊函式下，桶內節點數大致服從泊松分布，同一個桶累積到 8 個節點的機率約為 0.00000006，幾乎不會發生。也就是說，能長到 8 個，通常代表這個桶的衝突已經嚴重到值得用樹處理。

退樹閾值則設為 6，而不是同樣設成 8。這中間刻意留下緩衝區，避免節點數在 7、8 附近上下波動時，資料結構不斷在鏈表與紅黑樹之間切換，像是門被風吹得反覆開關。

還有一個前提：只有在陣列長度至少 64 時才會轉樹。若陣列還太小，HashMap 會優先擴容，先用增加桶數的方式稀釋衝突，而不是立刻付出紅黑樹的額外空間成本。

擴容：為什麼是 0.75 負載因子

HashMap 會在「容量 × 負載因子」超過門檻時擴容。預設容量是 16，負載因子是 0.75，因此門檻為 12。放入第 13 個元素時，就會觸發擴容，容量變成原來的兩倍。

負載因子其實是在交換兩種成本：

  • 設得太高，例如 1.0：表格可以塞得更滿，但碰撞增加，鏈表可能變長，查詢速度變慢。
  • 設得太低，例如 0.5：碰撞較少，但表格空間很多，擴容更頻繁，也更浪費記憶體。

0.75 是時間與空間之間的折衷：不要讓桶塞得太滿，也不要為了避免碰撞而預留過多空間。

// 1.8 擴容搬遷的核心：只看 hash 與舊容量的一個位元
// 結果只有兩種：留在原索引，或搬到 原索引 + oldCap
if ((e.hash & oldCap) == 0) {
    // 留在低位鏈
} else {
    // 搬到高位鏈
}

因為容量每次都是加倍，擴容後的索引只會有兩種結果：留在原本的位置，或移到「原索引 + oldCap」的位置。1.8 只要檢查 hash & oldCap 的結果，就能判斷節點要去哪裡，不必重新計算完整 hash。

1.7 的死循環：頭插法在並發擴容時翻車

1.7 的頭插法，遇到兩個執行緒同時擴容時，可能把同一條鏈表重新排列。由於每個節點都插到鏈表頭部，兩個執行緒交錯執行後，鏈表順序可能被顛倒，甚至讓節點彼此指向，形成一個環。

一旦成環，之後的 get 會沿著指標一直繞圈，永遠走不到 null，CPU 可能直接衝到 100%。這是把非執行緒安全容器拿去多執行緒寫入時，最經典的翻車案例之一。

1.8 改用尾插法，搬遷時維持原本的鏈表順序，因此根除了這種死循環。但「不再形成死循環」不代表 HashMap 已經變成執行緒安全。多執行緒同時寫入時，資料仍可能互相覆蓋；需要併發存取時，應該使用 ConcurrentHashMap。

ConcurrentHashMap：鎖的範圍越來越小

HashMap 解決的是單執行緒下的資料組織問題；ConcurrentHashMap 則要面對另一個問題：多個執行緒同時讀寫時，怎麼避免整張表被一把大鎖卡住。

JDK 1.7JDK 1.8
鎖粒度分段鎖 Segment，一個 Segment 鎖一段拋棄 Segment，CAS 加 synchronized 鎖單一桶的頭節點
併發度固定為 16（Segment 數量）隨陣列長度成長，粒度更細
空桶插入鎖住整個 Segment用 CAS 無鎖寫入

JDK 1.7 把整張表切成 16 個 Segment，每段各有一把鎖。這比整張表共用一把鎖好，最多可以讓 16 個執行緒同時寫入；但併發度也因此被固定在 16。

JDK 1.8 直接拿掉 Segment，改成更細的桶級別控制：

  • 空桶插入時，使用 CAS 嘗試寫入，不需要先取得鎖。
  • 桶裡已有節點時，才用 synchronized 鎖住該桶的頭節點。

鎖的範圍從「一整段」縮小成「單一桶」。不同桶之間可以同時操作，陣列越大，能夠並行處理的區域也越多。

ConcurrentHashMap 如何協助擴容

擴容是併發容器最麻煩的時刻：舊表的資料要搬到新表，但其他執行緒不能全部停在原地等候。JDK 1.8 因此把搬遷工作切成一小段一小段，讓多個執行緒可以分頭處理。

它使用 transferIndex 記錄尚未搬遷的範圍。某個執行緒領到一段工作後，就負責搬那一段；其他執行緒也能接著領取不同區段，一起完成擴容。

正在搬遷的桶會放入 ForwardingNode。這是一個特殊標記，裡面指向新表：

  • 其他寫入執行緒遇到它，不會傻等，而是加入擴容工作。
  • 讀執行緒遇到它，會轉到新表繼續查找。

因此，擴容不再只是某一個執行緒獨自搬完整張表，而是可以由多個執行緒協助完成。

為什麼 ConcurrentHashMap 不允許 null

HashMap 允許 key 或 value 是 null，但 ConcurrentHashMap 明確禁止。關鍵不在於 null 本身，而在於多執行緒環境下，null 會造成結果無法判讀。

假設：

map.get(k)

回傳 null，這可能代表兩件事：

  • key 根本不存在。
  • key 存在，但 value 就是 null。

單執行緒時，可以再呼叫 containsKey 進一步確認。但在併發環境，這兩次操作之間可能有另一個執行緒修改資料。也就是說，先檢查、再採取行動的 check-then-act 並不是原子操作，第二步看到的世界可能已經變了。

禁止 null 後，get 回傳 null 就只代表一件事：找不到這個 key。這是用限制 API 的方式，消除併發情境下的二義性。

高併發下，size() 怎麼算

如果每次修改元素都更新同一個全域計數器，所有執行緒會搶同一個位置，計數器反而變成新的瓶頸。因此 ConcurrentHashMap 的 size() 不使用全域鎖，而是採用類似 LongAdder 的分散式計數方式。

  • 沒有太多競爭時，執行緒用 CAS 更新共用的 baseCount。
  • 如果 CAS 競爭激烈、更新失敗，就改寫入自己負責的 CounterCell。
  • 需要計算總數時，再把 baseCount 與所有計數格的值加總。

這種設計把大家搶同一個櫃檯，改成分散到多個櫃檯辦理，能減少高併發下的衝突。但代價是 size() 具有弱一致性：計算期間仍可能有其他執行緒寫入，所以得到的是當下的近似值，不是精確、不可變動的瞬時值。

把整節串起來

HashMap 1.8 的三個關鍵改動，各自對應一個問題：

  • 紅黑樹：處理極端 hash 衝突，避免長鏈表讓查找退化。
  • 尾插法：維持搬遷後的鏈表順序，根除 1.7 並發擴容可能形成的死循環。
  • 位元運算搬遷：利用容量加倍的特性，只判斷節點留在原位，還是移到原索引加上舊容量的位置。

紅黑樹的 8 與 6，是在空間成本、衝突機率和避免反覆轉換之間取得平衡；0.75 則是在查詢效率與記憶體使用量之間取捨。

ConcurrentHashMap 也沿著同一條思路演進：JDK 1.7 用 Segment 分段加鎖，JDK 1.8 改成 CAS 加上桶級別的 synchronized。再配合 ForwardingNode，讓多個執行緒能協助擴容。禁止 null 和讓 size() 保持弱一致，則是為了避開多執行緒下無法可靠判讀或維護的狀態。
