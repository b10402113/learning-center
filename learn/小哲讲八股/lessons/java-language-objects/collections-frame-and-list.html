集合框架地圖：List 怎麼選，為什麼 ArrayList 常是預設答案

Step 5/6 · Java 語言與物件

前言：一個訂單列表，為什麼不只是「能放資料就好」

你正在寫一支查詢訂單的 API，從資料庫讀出幾百筆資料後回傳給前端。打開 IDE，眼前有好幾種 List 實作：ArrayList、LinkedList，還有名字很長的 CopyOnWriteArrayList。

多數時候，手一滑就寫下 new ArrayList<>()，功能也能正常運作。但如果面試官接著問：「為什麼選它？換成另一種會怎樣？」這時只會背 API 名稱就不夠了。你需要知道容器底下究竟是陣列還是鏈表、資料如何在記憶體裡排列，以及讀取和寫入的成本分別是多少。

這也是「介紹一下 Java 集合框架」真正想考的地方。對方不是要你背完所有類別，而是想確認你腦中有沒有一張地圖：哪些容器屬於同一個家族、各自解決什麼問題，以及什麼情境該選哪一個。這一課先把整張地圖攤開，再聚焦在最常用的 List 家族，讓選型從憑習慣變成有依據的判斷。

學習目標

學完後，你應該能畫出集合框架的兩大派系，並從底層結構、擴容成本與 CPU 快取等角度，說明 ArrayList、LinkedList 和 CopyOnWriteArrayList 該怎麼選。

兩大派系：Collection 與 Map 是兩個家族

Java 集合框架最上層有兩個平起平坐的根介面。這裡很容易講錯：Map 不繼承 Collection，它是另一個獨立的家族。

  • Collection：儲存「單一元素」的集合，底下主要分成三個分支。
    • List：有序、允許重複，像排隊一樣，也能按照索引存取。代表實作是 ArrayList 與 LinkedList。
    • Set：不允許重複，概念上接近數學裡的集合。代表實作是 HashSet（速度快但不保證順序）與 TreeSet（能自動排序）。
    • Queue：常見模型是先進先出（FIFO），可以拿來當緩衝區。代表實作是 PriorityQueue 與 ArrayDeque。
  • Map：儲存「鍵值對」，鍵必須唯一，但值可以重複。代表實作是 HashMap（JDK 8 為陣列、鏈表與紅黑樹的組合）、ConcurrentHashMap（適合高併發），以及 TreeMap（按鍵排序）。

還有兩個常被混淆的配角。Collections 結尾有一個 s，它不是集合，而是操作集合的工具類，提供排序、洗牌和二分查找等靜態方法。Iterator 則是遍歷集合的標準方式，後面談到 fail-fast 時還會遇到它。

ArrayList 與 LinkedList：連續陣列對上散落的鏈表

List 家族的兩個主角，看起來都能裝資料，但底層結構完全不同。這個差異會直接影響查詢、插入、刪除，以及記憶體使用方式。

維度ArrayListLinkedList
底層結構Object 陣列，記憶體連續雙向鏈表，節點散落在堆中
隨機訪問O(1)，知道首地址與下標就能算出偏移量O(N)，沒有真正的下標，只能從頭或尾逐個尋找
中間插入刪除O(N)，插入點後面的元素都要搬移改變指標是 O(1)，但按索引操作仍要先花 O(N) 找到位置
記憶體主要存放資料本身，利用率較高每個節點還要存 prev 與 next，64 位系統下多佔約 16 位元組

「LinkedList 增刪很快」這句話只說對了一半。若是在頭尾增刪，確實可以直接調整鏈結；但如果你要在第 100 個位置插入，還是得先花 O(N) 找到那個節點，省下來的只有後續搬移資料的成本。

所以，LinkedList 真正有優勢的場景，是把它當成鏈式結構，頻繁在兩端增刪。它不是「只要插在中間就一定很快」的萬用解答。

ArrayList 的擴容：懶加載、1.5 倍與一次搬家

ArrayList 底層是陣列，而陣列建立後長度固定。既然如此，它為什麼能一直呼叫 add？做法是：容量用完時，建立一個更大的陣列，把舊資料搬過去。這個過程就叫擴容。

JDK 1.8 之後，new ArrayList<>() 不會立刻建立一個長度為 10 的陣列，而是先指向空陣列。直到第一次 add，才真正初始化成預設容量 10。這種「用到時才建立」的方式叫懶加載（lazy initialization），可以避免集合建立了卻沒有放入資料時，仍然白白佔用空間。

當陣列已經放滿，還要繼續加入元素時，就會觸發 grow()。新容量是舊容量的 1.5 倍，原始碼寫成 oldCapacity + (oldCapacity >> 1)。其中 >> 1 代表右移一位，效果等同除以 2。

例如，容量 10 會擴成 15；容量 15 會擴成 22，也就是 15 加上 7。算出新容量後，因為陣列需要一段連續的實體記憶體，不能直接在舊陣列後面隨意接一段，所以 JVM 必須申請新的連續空間，再透過 System.arraycopy 搬移舊資料，最後讓舊陣列等待 GC 回收。

這次搬家需要處理原本的 N 筆資料，因此成本是 O(N)。如果擴容頻繁發生，效能就會受到影響。

為什麼是倍數擴容，而不是每次只加一格

既然擴容需要搬移資料，你可能會想：那每次只增加剛好需要的容量，不是比較省空間嗎？問題在於，這會讓搬家發生得太頻繁。

假設每次 add 都只把容量增加 1，加入第 11 個元素時要複製 10 筆資料，加入第 12 個元素時要複製 11 筆資料，之後一路增加。放入 N 個元素時，總複製次數會變成 1 加 2 加 3，一直到 N。

這是一個等差數列，總和會隨 N 呈平方成長，時間複雜度退化成 O(N²)。資料量一大，程式就像每放一件行李都要重新換一台更大的車，搬運成本會迅速失控。

改用 1.5 倍擴容後，搬家變成「偶爾發生一次」，而不是「幾乎每次都發生」。例如容量從 1000 擴到 1500 時，這一次確實要複製 1000 筆資料；但接下來的 500 次 add 都可以直接放入空位，不需要再次擴容。

把這次昂貴的成本分攤到後續操作上，每次插入的均攤複雜度（amortized complexity）就能維持在 O(1)。這也是倍數擴容的核心：不是讓每一次操作都便宜，而是讓昂貴操作不要發生得太密集。

當然，這樣做會浪費一點空間。容量擴到 1500，但目前只放入 1001 筆資料時，還有 499 個空位。這是典型的「空間換時間」：用一些額外記憶體，換取較少的資料搬移。

如果你事先知道大概會放多少資料，實務上可以直接指定初始容量，例如 new ArrayList<>(1000)。這樣能減少不必要的擴容，避免集合一路長大時反覆搬家。

現代 CPU 下，為什麼 ArrayList 常常比 LinkedList 更快

教科書通常會說 LinkedList 的插入和刪除比較快，但在真實環境裡，甚至連插入操作都可能是 ArrayList 表現較好。原因不只在 Big O，還在於 CPU 如何從記憶體搬資料。

CPU 從記憶體取資料時，通常不是只拿一個位元組，而是一次載入一整塊連續資料，通常是 64 位元組，這一塊資料叫做 Cache Line（快取行）。

ArrayList 的資料在記憶體裡連續排列。當你讀取 arr[0] 時，CPU 可能順手把附近的 arr[1] 到 arr[7] 一起載入 L1 快取。接下來要讀 arr[1] 時，資料已經在快取裡，不需要再次前往較慢的主記憶體。這種「使用一筆資料時，附近資料也很可能很快被使用」的特性，就叫空間局部性（spatial locality）。

LinkedList 的節點則是分別透過 new 建立，可能散落在堆記憶體的不同位置。你讀取 node1 時，CPU 順手載入的是 node1 附近的資料，但 node2 可能位於很遠的地方。CPU 找不到它，只好重新前往主記憶體，形成 Cache Miss，在等待資料期間就無法有效執行後續工作。

LinkedList 還有資料密度較低的問題。同樣大小的 64 位元組 Cache Line，ArrayList 裡主要都是資料本身；LinkedList 的節點卻要分出空間存放 prev 與 next 指標，快取裡真正有用的資料變少了。

這就是為什麼理論複雜度只是起點。實際效能還會受到記憶體配置、CPU 快取和資料搬移方式影響。很多情況下，ArrayList 即使在理論上需要搬移資料，整體表現仍可能勝過 LinkedList。

CopyOnWriteArrayList：用昂貴寫入，換取讀取時不必加鎖

如果多個執行緒會同時讀取同一份清單，而你又不希望讀取被鎖住，可以考慮 CopyOnWriteArrayList。它的名稱已經說明了核心策略：寫時複製（Copy-On-Write）。

讀取時，它完全不加鎖。底層是一個被 volatile 修飾的陣列參照，讀取時直接取得目前的陣列，效率接近 ArrayList。

寫入時則完全不同：先取得一把可重入鎖，確保同一時間只有一個執行緒寫入；接著複製整個陣列，在新陣列上完成修改，最後再把底層參照切換到新陣列。舊陣列則等待 GC 回收。

它不直接修改原本的陣列，是因為可能仍有其他執行緒正在讀取。若讀取中的陣列突然被改動，讀者可能看到不一致的內容；先複製、再切換，就能讓正在讀取的人繼續使用舊版本。

這也讓它的迭代器具備弱一致性（weak consistency）。建立迭代器的那一刻，它取得的是當時的陣列快照。即使其他執行緒之後把底層參照換成新陣列，你手上的迭代器仍然會繼續讀舊陣列。

因此，迭代器看不到建立之後的新修改，但遍歷時也不需要加鎖，並且不會因為集合被修改而拋出 ConcurrentModificationException。

這種設計適合讀多寫少的場景，例如白名單、黑名單或監聽器列表。缺點也很明顯：每次寫入都要複製整個陣列，資料量一大，寫入就會變成 O(N)，同時還可能產生較多暫時陣列，增加 GC 壓力。寫入頻繁的場景使用它，系統可能慢得像蝸牛。

fail-fast 與 fail-safe：遍歷時修改集合會怎樣

選擇集合時，還要問一個實際問題：遍歷資料的同時，集合是否可能被修改？不同容器對這件事的處理方式並不一樣。

java.util 底下的普通集合，例如 ArrayList、HashMap 和 HashSet，通常採用 fail-fast。集合內部維護一個 modCount 計數器；迭代器建立時，會把當下的值保存成 expectedModCount。

之後每次呼叫 next() 或 remove()，迭代器都會先檢查兩個計數器是否一致。如果有人在迭代器之外修改了集合結構，兩個數值就會不同，迭代器會立即拋出 ConcurrentModificationException。

這是一種防禦式設計。它寧可早一點報錯，也不要讓程式在資料狀態已經混亂的情況下繼續執行，最後產生更難追查的結果。

JUC 套件下的併發容器，例如 CopyOnWriteArrayList 和 ConcurrentHashMap，則常被歸類為 fail-safe。它們靠副本或弱一致性來處理並行修改，因此遍歷期間即使集合被改，也不會拋出例外。

代價是，遍歷結果可能不是最新資料，而且部分實作會使用更多記憶體。也就是說，fail-safe 並不是「沒有代價的安全」，而是用資料即時性或空間，換取遍歷過程的穩定性。

機制代表容器遍歷時被修改代價
fail-fastArrayList、HashMap、HashSet立刻拋出 ConcurrentModificationException嚴格，但可能誤報
fail-safeCopyOnWriteArrayList、ConcurrentHashMap不拋例外，繼續執行可能讀到舊資料，也可能佔用更多記憶體

重點回顧

  • 集合框架分成兩大派系：Collection（List／Set／Queue）與獨立的 Map；Collections 則是操作集合的工具類。
  • ArrayList 使用連續陣列，隨機訪問是 O(1)，中間增刪通常是 O(N)；LinkedList 使用雙向鏈表，只有在頭尾增刪時才真正有優勢，而且會使用更多記憶體。
  • ArrayList 採用懶加載，預設容量為 10，容量不足時以 1.5 倍擴容，並透過 System.arraycopy 搬移資料。
  • 倍數擴容是為了把偶爾發生的搬移成本攤平，讓插入的均攤複雜度維持在 O(1)，避免每次只增加一格所造成的 O(N²)。
  • 由於 CPU 快取與空間局部性，實務上 ArrayList 常常比 LinkedList 更快。
  • CopyOnWriteArrayList 讀取時不加鎖，寫入時複製整份陣列，適合讀多寫少的場景，但只提供弱一致性。
  • fail-fast 透過 modCount 偵測結構修改並拋出例外；fail-safe 則靠副本或弱一致性避免例外，但可能讀到舊資料。
