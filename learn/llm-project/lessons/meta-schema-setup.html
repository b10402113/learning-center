元數據表結構與業務含義

Step 2/3 · 演示數據與 SQL 腳本

學習目標

能說清 4 張 meta 表的元數據內容，理解 column_info.role 如何區分 primary_key / foreign_key / measure / dimension。

數據庫有了，然後呢？

上一步建好了 dw 庫——5 張表、116 筆訂單。但 NL2SQL 系統不能直接去猜表結構。當用戶問「上週華東地區的訂單總金額」時，系統需要知道：哪些列是「金額」？哪些列是「地區」？哪張表是事實表、哪張是維度表？

這些信息存在另一個庫—— 庫。它是一個元數據知識庫（metadata knowledge base），專門回答「dw 庫裡有什麼、每個字段是什麼意思、它們之間有什麼關係」。meta-schema-data.sql 這份腳本就是建這個庫的。

4 張表一覽

table_info —— 告訴你「dw 裡有幾張表、各自是什麼角色」
    ↓
column_info —— 告訴你「每張表的每列是什麼、什麼類型、什麼角色」
    ↓
metric_info —— 告訴你「有哪些業務指標、怎麼定義的」
    ↓
column_metric —— 告訴你「每個指標關聯哪些列」

1. table_info：表級元數據

最簡單的一張表——登記 dw 庫裡每張表的角色和描述。

字段類型說明
idvarchar(64)表名（如 fact_order）
namevarchar(128)表名（冗餘，方便展示）
rolevarchar(32)fact（事實表）或 dim（維度表）
descriptiontext表的業務描述

5 行數據，對應 dw 庫的 5 張表。role 字段只有兩個值：fact 和 dim——這是星型模型的基本分類。當 LLM 生成 SQL 時，它需要知道哪張表是事實表（放度量的），哪張是維度表（放屬性的），才能正確地 JOIN 和聚合。

2. column_info：列級元數據

這是 meta 庫最核心的一張表——為 dw 庫的每一列建立「身份證」。

字段類型說明
idvarchar(64)列的全限定名（如 fact_order.order_amount）
namevarchar(128)列名（如 order_amount）
typevarchar(64)數據類型（如 float、varchar(20)）
rolevarchar(32)列角色——下面重點講
examplesjson示例值（如 [8999.0, 6999.0, 125.0]）
descriptiontext列的業務描述
aliasjson中文別名（如 ["銷售額", "訂單金額", "收入"]）
table_idvarchar(64)所屬表名

role 字段的四種值

role 是 column_info 裡最重要的字段——它直接決定 LLM 在生成 SQL 時怎麼用這列：

role含義SQL 行為示例列
primary_key主鍵，唯一標識一行通常不出現在 SELECT 裡，用於 JOIN 條件fact_order.order_id、dim_customer.customer_id
foreign_key外鍵，指向另一張表的主鍵用於 JOIN 條件，連接事實表和維度表fact_order.customer_id、fact_order.region_id
measure度量，可聚合的數值用於 SUM/AVG/COUNT 等聚合函數fact_order.order_amount、fact_order.order_quantity
dimension維度，描述性屬性用於 WHERE 條件、GROUP BY 分組dim_product.category、dim_region.region_name

舉個例子：用戶問「華東地區的訂單總金額」。LLM 看到 region_name 的 role 是 dimension，就知道可以用 WHERE region_name = '華東'；看到 order_amount 的 role 是 measure，就知道可以用 SUM(order_amount)。

alias 字段：語義匹配的橋樑

alias 存的是中文別名，是一個 JSON 數組。比如 order_amount 的 alias 是 ["銷售額", "訂單金額", "收入"]。

當用戶說「銷售額」時，系統通過 alias 匹配到 order_amount 這個字段名。這就是 NL2SQL 裡「語義匹配」的核心機制——自然語言和數據庫字段之間的映射，靠的就是這些別名。

examples 字段：讓 LLM 理解數據長什麼樣

examples 存的是示例值，也是 JSON 數組。比如 member_level 的 examples 是 ["黃金", "白銀", "青銅", "鉑金"]。

這些示例值有兩個作用：一是幫助 LLM 理解這列存的是什麼類型的數據（是文本、數字還是枚舉值），二是在生成 SQL 時提供具體的值參考（比如 WHERE member_level = '黃金'）。

3. metric_info：指標定義

業務指標是從原始數據計算出來的衍生值。meta 庫定義了 13 個指標，覆蓋了常見的電商分析場景。

字段類型說明
idvarchar(64)指標編碼（如 GMV）
namevarchar(128)指標名稱
descriptiontext指標定義和計算邏輯
relevant_columnsjson計算此指標需要的列
aliasjson中文別名

幾個核心指標：

ID名稱計算邏輯別名
GMVGross Merchandise ValueSUM(order_amount)成交總額、訂單總額
AOVAverage Order ValueAVG(order_amount)平均單價、平均訂單金額
ORDER_COUNT訂單總數COUNT(DISTINCT order_id)訂單數、下單量
SALES_QUANTITY商品銷售總量SUM(order_quantity)總銷量、銷售件數

每個指標的 relevant_columns 字段列出了計算此指標需要關聯哪些列。比如 GMV 的 relevant_columns 是 ["fact_order.order_amount"]——只需要 order_amount 一列就能算。而 DAILY_GMV 的 relevant_columns 包含了 order_amount 和 dim_date 的所有時間列——因為需要按日期分組。

4. column_metric：列-指標關聯

一張多對多的關聯表，把「哪些列參與計算哪個指標」的關係顯式化。

字段類型說明
column_idvarchar(64)列的全限定名
metric_idvarchar(64)指標 ID

比如 fact_order.order_amount → GMV，表示 order_amount 列參與 GMV 指標的計算。fact_order.order_quantity → AOV，表示 order_quantity 列參與 AOV 的計算。

這張表的價值在於：當系統需要回答「GMV 怎麼算」時，可以直接查 column_metric 找到相關列，再查 column_info 拿到這些列的詳細信息，最後組裝成 LLM 需要的上下文。

meta 庫的整體設計邏輯

四張表形成一個從粗到細的描述鏈：

table_info（有哪些表、什麼角色）
    ↓
column_info（每列是什麼、什麼類型、什麼角色、叫什麼別名）
    ↓
metric_info（有哪些指標、怎麼定義、需要哪些列）
    ↓
column_metric（列和指標的多對多關係）

這個結構對應的是 NL2SQL 的核心需求：先理解業務語義，再生成 SQL。LLM 不需要去猜「銷售額對應哪個字段」——meta 庫已經把這些映射關係準備好了。這就是 RAG（Retrieval-Augmented Generation）的「R」——先從元數據知識庫裡檢索相關信息，再餵給 LLM 做生成。

小結

meta-schema-data.sql 建了 4 張元數據表：table_info 登記表角色，column_info 為每列建立身份證（類型、角色、別名、示例值），metric_info 定義業務指標，column_metric 記錄列與指標的關聯。其中 column_info 的 role 字段（primary_key / foreign_key / measure / dimension）是 LLM 生成 SQL 時判斷「該用這列做什麼」的核心依據。
