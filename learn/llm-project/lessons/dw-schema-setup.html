數倉表結構與演示數據

Step 1/3 · 演示數據與 SQL 腳本

學習目標

能說清 dw-schema-data.sql 中 5 張表的建表語句與演示數據的規模、覆蓋範圍。

為什麼要從 SQL 腳本開始？

掌柜問數是一個 NL2SQL 系統——用戶說自然語言，系統生成 SQL 去查數據。那數據從哪裡來？答案是：一個名為 dw 的 MySQL 數據庫，裡面是一套星型模型（star schema）結構。這套結構由 dw-schema-data.sql 這份腳本一次性搞定：建庫、建表、插數據。

跑通這份腳本，是你理解整個系統的第一步——因為後面所有的檢索、SQL 生成、結果返回，都是圍繞這 5 張表展開的。

星型模型：1 張事實表 + 4 張維度表

星型模型是數據倉庫最經典的建模方式。核心思想：把「發生了什麼」和「是誰/在哪/什麼時候/什麼東西」分開存。

  • 事實表（fact table）：記錄「發生了什麼」——每筆訂單的金額、數量，以及指向維度表的外鍵
  • 維度表（dimension table）：記錄「是誰/在哪/什麼時候/什麼東西」——客戶信息、日期、商品、地區的描述性屬性

畫出來是這樣的：

        dim_customer
            |
dim_date — fact_order — dim_product
            |
        dim_region

事實表在中間，四張維度表像星星的角一樣向外輻射——這就是「星型」名字的由來。

5 張表逐一拆解

1. dim_customer（客戶維度表）

存客戶的基本信息。每行一個客戶，20 行。

字段類型角色示例
customer_idvarchar(20)主鍵（PK）C001
customer_namevarchar(50)維度李偉
gendervarchar(10)維度男 / 女
member_levelvarchar(20)維度黃金 / 白銀 / 青銅 / 鉑金

會員等級分四檔：黃金、白銀、青銅、鉑金。20 位客戶覆蓋了男/女和四個等級的組合，足以驗證「按會員等級統計 GMV」這類查詢。

2. dim_date（時間維度表）

存日期信息，90 行，覆蓋 2025 年 Q1（1 月 1 日到 3 月 31 日）。

字段類型角色示例
date_idint主鍵（PK）20250101
yearint維度2025
quartervarchar(2)維度Q1
monthint維度1
dayint維度1

日期表支持多時間粒度查詢：按日、按月、按季度。因為整個數據集只有一個季度，所以 quarter 永遠是 Q1，但結構上支持擴展。

3. dim_product（商品維度表）

存商品信息，15 行。

字段類型角色示例
product_idvarchar(20)主鍵（PK）P001
product_namevarchar(200)維度iPhone 15 Pro
categoryvarchar(50)維度手機數碼
brandvarchar(50)維度蘋果

15 件商品覆蓋 6 個品類（手機數碼、家用電器、鞋靴、服飾、食品飲料、休閒零食）和多個品牌。這讓「按品類統計銷量」「按品牌統計 GMV」這類分析有足夠的切面。

4. dim_region（地區維度表）

存地區信息，6 行。

字段類型角色示例
region_idvarchar(20)主鍵（PK）R001
provincevarchar(50)維度廣東省
region_namevarchar(50)維度華南
countryvarchar(50)維度中國

6 個地區覆蓋華南（廣東）、華東（浙江、上海）、西南（四川）、華北（北京）、華中（湖北），足以驗證「按地區查詢訂單」這類場景。

5. fact_order（訂單事實表）

這是整個星型模型的核心——每筆訂單一行，約 116 行。

字段類型角色說明
order_idvarchar(30)主鍵（PK）訂單唯一標識，格式 ORD+日期+序號
customer_idvarchar(20)外鍵（FK）指向 dim_customer
product_idvarchar(20)外鍵（FK）指向 dim_product
date_idint外鍵（FK）指向 dim_date
region_idvarchar(20)外鍵（FK）指向 dim_region
order_quantityint度量（measure）購買數量
order_amountfloat度量（measure）訂單金額

事實表只存「數字」（數量、金額）和「外鍵」（指向誰）。描述性的信息（客戶叫什麼、商品叫什麼）全部在維度表裡。這是星型模型的核心約定：事實表存度量，維度表存屬性。

訂單金額範圍從 35 元（一包奧利奧）到 9499 元（一部 Galaxy S24 Ultra），覆蓋了低單價和高單價的分析場景。

建表語句的關鍵細節

腳本開頭有兩行值得注意：

SET NAMES utf8mb4;
SET FOREIGN_KEY_CHECKS = 0;

utf8mb4 確保中文字符正確存儲。FOREIGN_KEY_CHECKS = 0 關閉外鍵約束檢查——因為建表順序是先建事實表再建維度表（腳本先 DROP/CREATE fact_order），如果不關閉外鍵檢查，MySQL 會報錯。腳本結尾再把外鍵檢查開回來。

所有表都用 InnoDB 引擎、utf8mb4 字符集、Dynamic 行格式——這是 MySQL 8.0 的推薦配置。

數據規模總覽

表行數覆蓋範圍
dim_customer204 檔會員 × 男/女
dim_date902025 Q1（90 天）
dim_product156 個品類 × 多品牌
dim_region65 大區 × 6 省份
fact_order~116Q1 全部訂單

數據量很小，但維度覆蓋面廣。這是刻意設計的：Text2SQL 系統的演示數據不需要大，但需要覆蓋足夠多的分析切面，讓每一種查詢（按時間、按地區、按品類、按會員等級）都有對應的數據可以跑。

小結

dw-schema-data.sql 用一份腳本完成了三件事：建庫、建表、插數據。5 張表構成星型模型——1 張事實表存訂單的數字，4 張維度表存描述性屬性。數據覆蓋 2025 Q1 的 116 筝訂單，橫跨時間、地區、品類、品牌、會員等級五個分析維度。這就是整個 NL2SQL 系統的「答案數據集」。
