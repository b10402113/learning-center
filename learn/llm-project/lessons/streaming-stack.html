流式響應與全棧串接

Step 4/4 · 一個查詢的完整旅程

學習目標

能解釋 LangGraph 的 astream 如何橋接為 HTTP SSE 流，說清 progress/result/error 三種事件的用途與前端消費方式。

為什麼需要流式響應？

上一步我們走完了 12 個節點的工作流。但實際使用時，用戶不會願意等所有節點跑完才看到結果——整個過程可能要幾秒甚至十幾秒。如果前端只在最後才顯示結果，用戶會以為系統卡死了。

SSE（Server-Sent Events）解決了這個問題：它讓後端能以 HTTP 長連接的方式，把數據「推」給前端。前端不需要反覆輪詢，後端有新數據時直接推送過來。這比 WebSocket 輕量，比輪詢高效，非常適合「單向推送進度和結果」的場景。

SSE 協議基礎

SSE 的數據格式很簡單：每個事件是一行 data: {JSON}\n\n。前端通過 EventSource API 接收這些事件。服務器不需要特殊的庫——只要設置好 HTTP 響應頭 Content-Type: text/event-stream，然後逐行寫入 data: 開頭的文本就行。

在 FastAPI 裡，這通過 StreamingResponse 實現：

@query_router.post("/api/query")
async def query(
    query: QuerySchema,
    query_service: QueryService = Depends(get_query_service)
):
    return StreamingResponse(
        query_service.query(query.query),
        media_type="text/event-stream"
    )

關鍵在於 query_service.query() 是一個 async generator（異步生成器）——它不返回一個完整的響應，而是逐塊 yield 數據。FastAPI 的 StreamingResponse 會把每次 yield 的數據以 SSE 格式推送到客戶端。

三種事件類型

掌柜問數定義了三種 SSE 事件，每種有不同的用途：

事件類型格式用途
progress{"type":"progress","step":"...","status":"running/success/error"}推送執行進度
result{"type":"result","data":[...]}推送查詢結果
error{"type":"error","message":"..."}推送錯誤信息

progress 事件

每個 Agent 節點在執行時都會推送 progress 事件，包含三個字段：

  • step——節點名稱的中文描述（如「抽取關鍵詞」「召回字段」）
  • status——三種狀態：running（開始執行）、success（執行成功）、error（執行失敗）

前端收到 progress 事件後，可以實時更新進度條或步驟列表，讓用戶知道系統正在幹什麼。

result 事件

SQL 執行成功後，查詢結果通過 result 事件推送。data 字段是一個數組，每個元素是一行查詢結果（鍵值對格式）。前端拿到後直接渲染成表格。

error 事件

如果整個流程中出現未捕獲的異常（比如數據庫連接超時），系統會推送 error 事件。message 字段包含錯誤描述，前端可以顯示錯誤提示。

從 LangGraph 到 SSE 的橋接

核心橋接邏輯在 QueryService.query() 裡：

async def query(self, query: str):
    context = DataAgentContext(...)
    state = DataAgentState(query=query)
    try:
        async for chunk in graph.astream(
            input=state, context=context, stream_mode="custom"
        ):
            yield f"data: {json.dumps(chunk, ensure_ascii=False)}\n\n"
    except Exception as e:
        yield f"data: {json.dumps({'type':'error','message':str(e)})}\n\n"

幾點要注意：

  • graph.astream() 是 LangGraph 的異步流式執行方法，stream_mode="custom" 表示使用節點內部 stream_writer 推送的自定義數據
  • 每次 yield 的 chunk 就是一個 dict（如 {"type":"progress","step":"召回字段","status":"running"}）
  • json.dumps(ensure_ascii=False) 確保中文不會被轉成 \uXXXX 編碼
  • 整個 generator 被 StreamingResponse 包裝成 SSE 流

依賴注入鏈

FastAPI 的依賴注入（Dependency Injection）在這裡起了關鍵作用。整個注入鏈是這樣的：

query_router
  └─ Depends(get_query_service)
       ├─ Depends(get_embedding_client)
       ├─ Depends(get_column_qdrant_repository)
       ├─ Depends(get_value_es_repository)
       ├─ Depends(get_metric_qdrant_repository)
       ├─ Depends(get_meta_mysql_repository)
       │    └─ Depends(get_meta_session)
       └─ Depends(get_dw_mysql_repository)
            └─ Depends(get_dw_session)

每個 Depends 函數負責創建一個資源（數據庫 session、向量庫客戶端等）。FastAPI 自動管理這些資源的生命週期——請求開始時創建，請求結束時關閉。這就是為什麼你不需要手動管理 session 的開啟和關閉。

Lifespan 生命週期管理

除了請求級的資源管理，還有應用級的資源——MySQL 客戶端、Qdrant 客戶端、ES 客戶端、Embedding 客戶端。這些客戶端在 FastAPI 啟動時初始化，關閉時釋放：

@asynccontextmanager
async def lifespan(app: FastAPI):
    # 啟動時：初始化所有客戶端
    embedding_client_manager.init()
    qdrant_client_manager.init()
    es_client_manager.init()
    meta_mysql_client_manager.init()
    dw_mysql_client_manager.init()
    yield
    # 關閉時：釋放所有客戶端
    await qdrant_client_manager.close()
    await es_client_manager.close()
    await meta_mysql_client_manager.close()
    await dw_mysql_client_manager.close()

這個函數被註冊到 FastAPI 的 lifespan 參數上，框架會在啟動和關閉時自動調用。

前端消費 SSE

前端通過 JavaScript 的 EventSource 或 fetch + ReadableStream 來消費 SSE 流。收到的事件根據 type 字段分發處理：

收到的 type前端動作
progress + running更新進度列表，顯示「正在...」
progress + success標記該步驟完成（打勾）
progress + error標記該步驟失敗（紅叉）
result渲染結果表格
error顯示錯誤提示

前端項目基於 Vue + Vite 構建，通過 npm install 安裝依賴，npm run dev 啟動開發服務器，連接後端 SSE 接口完成全棧聯調。

Request ID 追蹤

在生產環境中，多個用戶同時提問時怎麼區分誰的日誌是誰的？系統用 ContextVar（Python 的上下文變量）為每個請求生成唯一的 request_id，中間件在請求進入時設置，日誌系統在輸出時自動附帶。這樣你在日誌裡搜索一個 request_id，就能看到一個完整請求的所有處理過程。

小結

SSE 把 LangGraph 的流式輸出橋接到 HTTP 長連接，三種事件類型（progress/result/error）覆蓋了進度、結果和錯誤的全場景。FastAPI 的依賴注入鏈自動管理請求級資源，lifespan 管理應用級資源，ContextVar 實現請求級日誌追蹤。前端通過 EventSource 消費 SSE 事件，實時渲染進度和結果。整個全棧串接的設計非常乾淨，是搭建類似系統的標準模式。
