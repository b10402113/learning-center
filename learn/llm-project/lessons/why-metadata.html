為什麼 NL2SQL 需要元數據知識庫

元數據知識庫結構 · Step 1/4

學習目標

能解釋「自然語言問數」場景下，為什麼不能把用戶的問題直接丟給 LLM 生成 SQL，而需要一個元數據知識庫做語義中間層。

一個問題，兩種理解

假設業務同學在聊天框裡問了一句：「上週華東地區 GMV 多少？」

這句話對人來說很直覺，但對 LLM 來說，它面臨三個不確定性：

「華東」是什麼？ 數據庫裡對應的到底是 dim_region.region_name 的值「華東」，還是某個 province 包含「華」字的記錄？

「GMV」是什麼？ 數據庫裡有 order_amount 這一列，但 LLM 不知道「GMV」= SUM(order_amount)。它甚至不知道這個指標叫 GMV。

「上週」怎麼翻譯？ 需要知道 dim_date 表的 date_id 格式是 yyyyMMdd，以及「上週」對應的具體日期範圍。

如果直接把用戶問題和數據庫 DDL 扔給 LLM，它要同時解決語義匹配、指標理解、SQL 語法三件事——這太難了，容易出錯。

元數據知識庫的角色

元數據知識庫本質上是一份「數據庫的說明書中心」。它把數據庫裡「有什麼表、有什麼列、列是什麼角色、有哪些業務指標、指標怎麼算」這些信息登記在四張專門的表裡。

表登記什麼一句話
table_info每張表的角色這張表是事實表還是維度表
column_info每列的類型、角色、別名這列是主鍵、外鍵、度量還是維度
metric_info業務指標的定義GMV 是什麼、由哪些列算出來
column_metric列與指標的關聯order_amount 參與了 GMV 計算

有了這份說明書，LLM 不用猜——它可以直接查到：「GMV」對應的指標 ID 是 GMV，涉及的列是 fact_order.order_amount，角色是 measure。

為什麼不能只靠 LLM 自己猜？

你可能會問：現在的大模型這麼聰明，直接把表結構告訴它不就行了？為什麼還需要元數據？

原因有三：

第一，自然語言和數據庫語言之間有語義鴻溝。 用戶說「銷量」，數據庫裡叫 order_quantity；用戶說「成交總額」，數據庫裡叫 order_amount。元數據的 alias 字段就是為了填平這道溝——它把每個列的中文別名登記好，讓 LLM 能做精確匹配。

第二，指標的計算邏輯不能靠猜。 「AOV」是平均訂單金額，計算公式是 SUM(order_amount) / COUNT(DISTINCT order_id)。如果 LLM 不知道這個定義，它可能只算 SUM(order_amount)——結果差了十倍。元數據的 metric_info 表把每個指標的描述和相關列登記清楚，LLM 才能生成正確的聚合邏輯。

第三，表的語義角色決定 JOIN 邏輯。 fact_order 是事實表，dim_region 是維度表。當用戶問「華東地區的訂單數」，系統需要 JOIN 這兩張表。元數據的 role 字段（fact / dim）直接告訴 LLM 哪些表需要 JOIN、怎麼 JOIN。

元數據知識庫在整個系統中的位置

在掌柜問數的架構裡，元數據知識庫處於「數據倉庫」和「智能體」之間：

數據倉庫（dw 庫）存的是業務數據——訂單、客戶、商品、地區、日期。

元數據知識庫（meta 庫）存的是「關於數據的數據」——每張表是什麼角色、每列是什麼含義、有哪些業務指標。

智能體（LangGraph Agent）拿到用戶問題後，先從元數據知識庫中召回相關的表、列、指標，再結合 LLM 生成 SQL。

簡單說：元數據知識庫是 LLM 理解業務數據的「字典」。沒有這本字典，LLM 就是在黑暗中寫 SQL。

小結

元數據知識庫解決的核心問題是：讓 LLM 從「猜」變成「查」。用戶說「GMV」，LLM 不用猜，直接查元數據就知道對應 fact_order.order_amount 的 SUM。接下來三步，我們逐張看這四張表的具體結構。
