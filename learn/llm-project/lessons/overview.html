系統全貌：從提問到結果的完整旅程

Step 1/4 · 一個查詢的完整旅程

學習目標

能畫出從用戶提問到結果返回的完整數據流，說清每個階段的輸入與輸出。

為什麼需要一個「問數」系統？

想像你是個電商運營，老闆突然問：「上週華東地區的訂單總金額是多少？」你腦子裡第一個反應是——我得寫 SQL。但你不是數據工程師，就算寫得出 SELECT SUM(order_amount) FROM fact_order JOIN dim_region ...，你也未必知道該 JOIN 哪些表、用哪個字段。

掌柜問數就是來解決這個問題的：你只要打字問一句，系統自己搞定剩下的。它是一個面向數據倉庫的 NL2SQL 智能分析系統——NL 是 Natural Language（自然語言），SQL 是結構化查詢語言。把自然語言翻譯成 SQL，再把查出來的數據變成你能看懂的表格，這就是它的全部使命。

數據倉庫是什麼？

要理解這套系統，先得搞懂它背後的數據存在哪裡。

業務庫管「幹活」，數據倉庫管「復盤」——這句話是理解整個架構的起點。業務庫（比如 MySQL 裡的訂單表）存的是當下正在發生的交易：誰下了單、付了多少錢、貨發到哪裡。數據倉庫（Data Warehouse）則是把這些零散的業務數據，經過抽取、清洗、轉換後，按主題域整合起來，專門用來做分析和決策。

為什麼不直接查業務庫？因為業務庫是為了「記帳」設計的，結構-normalized、數據量大、查分析型查詢很慢。數據倉庫是為了「看帳」設計的——數據按分析場景組織，查起來快，結構也對分析更友好。

數據倉庫的數據來源主要有兩種：

來源內容採集方式
業務系統訂單、用戶、商品、支付等交易數據CDC（實時）、全量/增量同步
日誌數據用戶行為、埋點、服務端日誌Kafka、Logstash 採集

完整數據流：五個階段

當用戶打字提問「上週華東地區的訂單總金額」時，數據要經過五個階段才能回到用戶手裡。畫出來是這樣的：

用戶提問
  ↓
① 關鍵詞抽取
  ↓
② 多路召回（字段 / 指標 / 取值）
  ↓
③ 合併過濾 + SQL 生成 + 校驗
  ↓
④ 執行 SQL，拿到結果
  ↓
⑤ 流式返回前端，渲染表格

下面逐步拆開。

階段一：關鍵詞抽取

用戶說的是自然語言，但檢索系統需要的是關鍵詞。系統用 jieba（中文分詞庫）把「上週華東地區的訂單總金額」拆成關鍵詞：上週、華東、地區、訂單、總金額。這一步的輸出是一組關鍵詞列表。

階段二：多路召回

拿到關鍵詞後，系統同時走三條路去找相關信息：

召回路徑去哪裡找找到什麼
字段召回Qdrant 向量索引相關的表字段（如 order_amount、region_name）
指標召回Qdrant 向量索引相關的業務指標（如訂單總金額的定義）
取值召回Elasticsearch 全文索引維度值的真實取值（如「華東」對應 region_name）

為什麼要走三條路？因為自然語言的模糊性——「訂單總金額」可能對應字段 order_amount，也可能對應指標「訂單金額合計」的定義。「華東」需要匹配到數據庫裡真實的維度值 region_name = '華東'。三路並行，覆蓋面最廣。

階段三：合併過濾 + SQL 生成

三路召回的結果先合併成一份「候選表/字段/指標清單」，然後用 LLM（大語言模型）做兩件事：

  1. 過濾——從候選清單裡挑出真正有用的表和字段，去掉不相關的噪音
  2. 生成 SQL——把用戶問題 + 篩選後的元數據一起餵給 LLM，讓它生成 SQL 語句

生成的 SQL 還要過一道校驗：用 EXPLAIN 語句檢查語法是否正確。如果校驗失敗，系統會自動用 LLM 校正，再重新校驗，直到 SQL 能跑通為止。

階段四：執行 SQL

校驗通過的 SQL 被送到數據倉庫執行，拿到原始結果（一組行數據）。這一步的輸入是 SQL 字符串，輸出是結構化的查詢結果。

階段五：流式返回

系統不會等所有步驟跑完才一次性返回結果——它用 SSE（Server-Sent Events）協議把每一步的進度實時推送到前端。前端用戶能看到「正在抽取關鍵詞...」「正在召回字段...」這樣的進度提示，最後再拿到查詢結果渲染成表格。

整體架構一覽

把上面五個階段放回系統架構裡看：

層級組件職責
前端Vue 應用接收 SSE 事件，渲染進度與結果表格
API 層FastAPI + SSE接收查詢請求，橋接 LangGraph 流式輸出
Agent 層LangGraph 狀態機編排 12 個節點的工作流
檢索層Qdrant + Elasticsearch向量語義召回 + 全文關鍵詞召回
存儲層MySQL（元數據 + 數據倉庫）結構化元數據 + 星型模型數據

整個系統的核心設計思想是 RAG（Retrieval-Augmented Generation，檢索增強生成）——先從元數據知識庫裡檢索出相關信息，再把這些信息和用戶問題一起餵給 LLM，讓它生成更準確的 SQL。這比直接把整個數據庫的 schema 塞給 LLM 要高效得多，也準確得多。

小結

一個查詢從用戶手指到結果返回，要經過：關鍵詞抽取 → 三路並行召回 → 合併過濾 → SQL 生成與校驗 → 執行 → 流式返回。每一步的輸入和輸出都很明確，這是搭建類似系統的心智模型基礎。接下來三步會逐一拆開每個階段的細節。
