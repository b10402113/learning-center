元數據基礎：支撐 RAG 的知識庫

Step 2/4 · 一個查詢的完整旅程

學習目標

能說清元數據知識庫的三層結構——MySQL 結構化存儲、Qdrant 向量索引、ES 全文索引——以及它們各自解決什麼問題。

什麼是元數據？

上一步我們知道系統要用 RAG 來增強 LLM 的 SQL 生成能力。問題是：LLM 需要什麼信息才能生成準確的 SQL？它需要知道數據倉庫裡有哪些表、每張表有哪些字段、每個字段是什麼意思、有哪些業務指標、字段裡實際存了什麼值。

這些「關於數據的數據」就是元數據（metadata）。你可以把它想成數據倉庫的「說明書中心」——它不是業務數據本身（不是訂單金額、不是用戶名），而是描述業務數據的結構和含義。

元數據知識庫的三層架構

掌柜問數把元數據分三層存儲，每一層解決一個不同的問題：

層級存儲系統存什麼解決什麼問題
結構化存儲MySQL表/字段/指標的定義精確查詢：「fact_order 有哪些字段？」
語義向量索引Qdrant字段名/描述/別名的向量語義匹配：「訂單金額」→ order_amount
全文索引Elasticsearch維度字段的實際取值值匹配：「華東」→ region_name

為什麼不只用一層？因為三層各自解決不同類型的匹配問題，少了任何一層都會影響召回率。

第一層：MySQL 結構化存儲

元數據的核心是四張 MySQL 表：

表名存什麼舉例
table_info表的元信息fact_order 是事實表，存訂單交易數據
column_info字段的元信息order_amount 是 FLOAT 類型的度量，描述是「訂單實付金額」
metric_info業務指標的定義「訂單總金額」= SUM(order_amount)
column_metric字段與指標的關聯order_amount 屬於「訂單總金額」指標

以 fact_order.order_amount 為例，它在 column_info 裡長這樣：

字段值
idfact_order.order_amount
nameorder_amount
typeFLOAT
rolemeasure（度量）
description訂單實付金額，單位：元，不含運費/優惠
alias["訂單金額", "實付金額"]
examples["8999.00", "6999.00"]

MySQL 這層的作用是讓系統能精確查詢：「fact_order 有哪些字段？order_amount 的類型是什麼？它有哪些別名？」這些結構化信息是 SQL 生成的直接依據。

第二層：Qdrant 向量索引

MySQL 能回答「order_amount 是什麼」，但回答不了「用戶說的『訂單金額』對應哪個字段」。因為「訂單金額」和 order_amount 在字面上不完全匹配——一個是中文別名，一個是英文列名。

這就需要語義匹配。系統用 Embedding 模型（BGE-large-zh）把字段名、描述、別名轉成向量，存入 Qdrant。當用戶說「訂單金額」時，系統把這句話也轉成向量，然後在 Qdrant 裡做相似度搜索，找到最接近的字段。

具體來說，系統為每個字段建了三條向量記錄：

記錄類型示例作用
字段名order_amount精確匹配英文列名
字段描述訂單實付金額，單位：元語義匹配含義
字段別名訂單金額、實付金額匹配用戶口語化表達

拆成三條而不是合成一條，是為了提高召回覆蓋率——用戶可能用任何一種方式來描述同一個字段。

第三層：Elasticsearch 全文索引

向量索引解決了「字段名匹配」的問題，但還有一類匹配它搞不定：維度值的匹配。

用戶說「華東地區」，系統需要知道 region_name 字段裡存的是「華東」這個值。但「華東地區」和「華東」在向量空間裡未必足夠接近——ES 的全文索引 + IK 分詞器正好能處理這種場景。

ES 對維度字段的實際取值建立倒排索引。比如 dim_region.region_name 裡存了「華東」「華南」「華北」「華中」等值，這些值被分詞後存入 ES。當用戶說「華東地區」時，IK 分詞器把它拆成「華東」「地區」，然後在 ES 裡匹配到 region_name = '華東'。

三層如何協作？

回到上一步的「三路召回」，現在你能看清每一路背後的存儲了：

用戶問題：「上週華東地區的訂單總金額」
  ↓
關鍵詞：上週、華東、地區、訂單、總金額
  ↓
┌─ 字段召回 → Qdrant（語義匹配字段名/描述/別名）
├─ 指標召回 → Qdrant（語義匹配指標名/描述/別名）
└─ 取值召回 → ES（全文匹配維度值）
  ↓
三路結果合併 → 候選表/字段/指標清單

三層存儲各司其職：MySQL 供結構化查詢，Qdrant 供語義匹配，ES 供值匹配。少了任何一層，召回的覆蓋率和準確率都會下降。

小結

元數據知識庫是 RAG 的語義基礎。MySQL 存結構化定義（精確查詢），Qdrant 存向量索引（語義匹配），ES 存全文索引（值匹配）。三層協作，確保用戶的自然語言能被準確地映射到數據倉庫的表、字段和取值。
