metric_info 與 column_metric：指標定義與多對多關聯

元數據知識庫結構 · Step 3/4

學習目標

能說清 metric_info 和 column_metric 的字段含義，理解指標如何通過關聯表與數據列建立多對多關係。

metric_info：業務指標的「身份證」

在業務對話中，用戶不會說「請幫我 SUM(order_amount)」，他們會說「GMV 多少」「平均單價多少」。LLM 需要知道每個指標對應的計算邏輯——metric_info 就是登記這些的地方。

CREATE TABLE metric_info (
  id                VARCHAR(64)  PRIMARY KEY,  -- 指標編碼，如 'GMV'
  name              VARCHAR(128),              -- 指標名稱
  description       TEXT,                      -- 指標描述（含計算邏輯）
  relevant_columns  JSON,                      -- 關聯的列
  alias             JSON                       -- 指標別名
);

實際數據示例

idnamedescriptionrelevant_columnsalias
GMV GMV Gross Merchandise Value，所有訂單的成交金額總和 ["fact_order.order_amount"] ["成交總額", "訂單總額"]
AOV AOV Average Order Value，所有訂單的成交金額平均值 ["fact_order.order_quantity"] ["平均單價", "平均訂單金額"]
DAILY_GMV 日成交總額 按日期維度統計的每日 GMV ["fact_order.order_amount", "dim_date.date_id", ...] ["日GMV", "每日成交總額"]
GMV_BY_BRAND 品牌成交總額 按商品品牌統計的成交總額 ["fact_order.order_amount", "dim_product.brand"] ["品牌GMV", "各品牌銷售額"]

description 的關鍵作用

description 不只是個標籤——它包含指標的計算邏輯。LLM 讀了 description 就知道：

  • GMV = SUM(order_amount)，需要聚合
  • AOV = SUM(order_amount) / COUNT(DISTINCT order_id)，需要兩個列配合
  • DAILY_GMV 需要按 date_id 分組

如果 LLM 不知道 AOV 的定義，它可能只算 SUM(order_amount)——結果差了十倍。description 就是防止這種錯誤的保險。

alias：指標的中文別名

和 column_info 的 alias 一樣，metric_info 的 alias 也是 JSON 數組。當用戶說「成交總額」，LLM 查 alias 發現匹配 GMV——語義匹配完成。

-- GMV 的 alias
["成交總額", "訂單總額"]

-- AOV 的 alias  
["平均單價", "平均訂單金額"]

-- ORDER_COUNT 的 alias
["訂單數", "下單量"]

column_metric：多對多關聯表

一個指標可能涉及多個列，一個列也可能參與多個指標。比如 order_amount 既參與 GMV 計算，也參與 AVG_AMOUNT_BY_CUSTOMER 計算。這種多對多關係通過 column_metric 關聯表實現。

CREATE TABLE column_metric (
  column_id  VARCHAR(64),  -- 列編號（指向 column_info.id）
  metric_id  VARCHAR(64),  -- 指標編號（指向 metric_info.id）
  PRIMARY KEY (column_id, metric_id)
);

實際關聯示例

column_idmetric_id含義
fact_order.order_amountGMVorder_amount 參與 GMV 計算
fact_order.order_amountAVG_AMOUNT_BY_CUSTOMERorder_amount 參與客戶平均消費額
fact_order.order_amountGMV_BY_BRANDorder_amount 參與品牌成交總額
fact_order.order_quantityAOVorder_quantity 參與 AOV 計算
fact_order.order_quantitySALES_QUANTITYorder_quantity 參與銷售總量

注意看：order_amount 一行對應三個指標，GMV_BY_BRAND 一行對應兩個列（order_amount + brand）。這就是多對多。

為什麼需要 column_metric？

你可能會問：metric_info 裡不是已經有 relevant_columns 了嗎？為什麼還需要 column_metric 關聯表？

原因是 relevant_columns 是 JSON 字段，方便 LLM 快速讀取；而 column_metric 是關係型關聯表，方便：

  • 數據一致性：通過外鍵約束確保關聯的列和指標都存在
  • 高效查詢：「哪些指標用到了 order_amount？」一句 SQL 就能查出來
  • 動態維護：新增或修改關聯時不需要改 JSON 字段

relevant_columns vs column_metric

實際上系統同時使用兩種方式存儲列-指標關聯：

存儲位置格式誰用場景
metric_info.relevant_columnsJSON 數組LLM快速讀取指標涉及哪些列
column_metric關係表SQL 查詢高效反向查詢「某列參與了哪些指標」

兩者存的是同樣的信息，但服務不同的使用場景。這是一種常見的冗餘設計——用空間換查詢效率。

小結

metric_info 為每個業務指標建檔——名稱、描述、計算邏輯、別名。column_metric 把列和指標的多對多關係登記清楚。兩張表配合，LLM 就能從「成交總額」定位到 GMV，再從 GMV 找到需要聚合的列。接下來最後一步，我們把四張表串起來看完整的 NL2SQL 流程。
