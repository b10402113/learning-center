元數據協同：四張表如何驅動 NL2SQL

元數據知識庫結構 · Step 4/4

學習目標

能完整說清一個用戶問題從「自然語言」到「SQL 查詢」的過程中，四張元數據表各自扮演什麼角色。

完整流程：從「GMV 多少」到 SELECT SUM(order_amount)

讓我們用一個真實例子串起四張表。用戶問了一句：「華東地區 Q1 的 GMV 多少？」

第一步：語義匹配（column_info + metric_info）

LLM 拿到用戶問題後，首先做關鍵詞抽取和語義匹配：

用戶說的查什麼表匹配結果
GMVmetric_info.alias匹配 GMV 指標
華東column_info.alias匹配 region_name 列
Q1column_info.alias匹配 quarter 列

如果沒有元數據，LLM 要自己猜「GMV」是什麼意思——它可能猜對，也可能猜成 COUNT(order_id)。有了元數據，匹配是確定性的。

第二步：定位列和表（column_info + table_info）

匹配到列名後，LLM 需要知道這些列來自哪些表、是什麼角色：

列table_idtable_info.rolecolumn_info.role
order_amountfact_orderfactmeasure
region_namedim_regiondimdimension
quarterdim_datedimdimension

LLM 現在知道：

  • order_amount 來自事實表，role 是 measure → 需要聚合（SUM）
  • region_name 和 quarter 來自維度表，role 是 dimension → 需要過濾或分組
  • 事實表需要 JOIN 維度表才能拿到維度信息

第三步：確認指標邏輯（metric_info）

LLM 查 metric_info 確認 GMV 的計算邏輯：

metric_info WHERE id = 'GMV'
→ description: "Gross Merchandise Value，所有訂單的成交金額總和"
→ relevant_columns: ["fact_order.order_amount"]

確認：GMV = SUM(order_amount)，不需要去重，不需要其他列配合。

第四步：確認 JOIN 鍵（column_info）

LLM 需要 JOIN fact_order 和 dim_region、dim_date。它查 column_info 找外鍵：

fact_order.region_id → role: foreign_key → JOIN dim_region.region_id (primary_key)
fact_order.date_id   → role: foreign_key → JOIN dim_date.date_id (primary_key)

外鍵-主鍵配對告訴 LLM 用什麼列做 JOIN。

第五步：生成 SQL

所有信息到齊，LLM 生成：

SELECT SUM(f.order_amount) AS gmv
FROM fact_order f
JOIN dim_region r ON f.region_id = r.region_id
JOIN dim_date d ON f.date_id = d.date_id
WHERE r.region_name = '華東'
  AND d.quarter = 'Q1';

這個 SQL 的每個元素都有元數據支撐：

  • SUM(order_amount) ← metric_info 的 description
  • JOIN dim_region ← column_info 的 foreign_key + primary_key
  • WHERE region_name = '華東' ← column_info 的 alias 匹配
  • AND quarter = 'Q1' ← column_info 的 alias 匹配

四張表的角色總結

表在流程中的角色沒有它會怎樣
table_info告訴 LLM 哪些是事實表、哪些是維度表LLM 不知道該 JOIN 哪些表
column_info告訴 LLM 每列的角色、別名、示例數據LLM 無法匹配自然語言到列名
metric_info告訴 LLM 指標的計算邏輯LLM 可能生成錯誤的聚合表達式
column_metric登記列與指標的多對多關聯LLM 不知道哪些列參與了指標計算

與召回機制的銜接

元數據知識庫不只被 LLM 直接查詢——它還被同步到 Qdrant（向量索引）和 Elasticsearch（全文索引）：

  • Qdrant：對 column_info 的 name/description/alias 和 metric_info 的 name/description/alias 建立向量索引。語義召回（「銷量」→ order_quantity）走這裡。
  • Elasticsearch：對維度列的實際取值建立全文索引。值召回（「華東」→ region_name）走這裡。

元數據知識庫是整個 NL2SQL 系統的語義基礎——它不只是一份說明書，更是多路召回和 SQL 生成的核心數據源。

小結

四張表各司其職：table_info 定義表的角色，column_info 定義列的語義，metric_info 定義指標的邏輯，column_metric 登記它們的關聯。它們共同構成了 LLM 理解業務數據的「語義中間層」，讓自然語言問數從「靠猜」變成「靠查」。
