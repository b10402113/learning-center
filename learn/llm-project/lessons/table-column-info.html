table_info 與 column_info：結構化元數據

元數據知識庫結構 · Step 2/4

學習目標

能說清 table_info 和 column_info 兩張表的字段含義，理解 role 字段如何把表和列分類。

table_info：每張表是什麼角色？

在星型模型的數據倉庫裡，表分兩種：事實表（fact）和維度表（dim）。table_info 就是登記這件事的地方。

CREATE TABLE table_info (
  id          VARCHAR(64)  PRIMARY KEY,  -- 表編號，如 'fact_order'
  name        VARCHAR(128),              -- 表名稱
  role        VARCHAR(32),               -- 'fact' 或 'dim'
  description TEXT                       -- 表的業務描述
);

實際數據是這樣的：

idnameroledescription
fact_orderfact_orderfact訂單事實表，記錄訂單數量和金額等核心指標
dim_customerdim_customerdim客戶維度表，描述下單客戶的基本屬性
dim_datedim_datedim時間維度表，用於多時間粒度分析
dim_productdim_productdim商品維度表，描述商品的基本屬性信息
dim_regiondim_regiondim地區維度表，用於描述訂單發生的地理區域

role 字段只有兩個值：fact 和 dim。當 LLM 看到用戶問「訂單金額」時，它通過 role 知道要從事實表 fact_order 取數據，然後 JOIN 維度表來補充維度信息。

column_info：每列的完整檔案

column_info 是四張表裡字段最多的，也是最核心的。它為數據倉庫的每一列建檔：

CREATE TABLE column_info (
  id          VARCHAR(64)  PRIMARY KEY,  -- 列編號，如 'fact_order.order_amount'
  name        VARCHAR(128),              -- 列名
  type        VARCHAR(64),               -- 數據類型
  role        VARCHAR(32),               -- primary_key / foreign_key / measure / dimension
  examples    JSON,                      -- 數據示例
  description TEXT,                      -- 列描述
  alias       JSON,                      -- 列別名（中文）
  table_id    VARCHAR(64)                -- 所屬表編號
);

role 字段：四種角色

column_info 的 role 有四個值，分別對應列在星型模型中的角色：

role含義示例對 SQL 生成的影響
primary_key主鍵，唯一標識每一行order_id用於 COUNT(DISTINCT ...) 去重計數
foreign_key外鍵，關聯到維度表customer_id用於 JOIN 維度表
measure度量，數值型可聚合order_amount用於 SUM / AVG 等聚合
dimension維度，描述性屬性region_name用於 GROUP BY / WHERE 條件

舉個例子：當 LLM 需要生成「華東地區的訂單總金額」時，它會查 column_info 發現：

  • order_amount 的 role 是 measure → 需要 SUM
  • region_name 的 role 是 dimension → 需要 GROUP BY 或 WHERE
  • region_id 在 dim_region 中是 primary_key，在 fact_order 中是 foreign_key → 用它做 JOIN

alias 字段：填平語義鴻溝

alias 是 JSON 數組，存儲列的中文別名。這是讓 LLM 能理解自然語言的關鍵：

-- order_amount 的 alias
["銷售額", "訂單金額", "收入"]

-- order_quantity 的 alias
["銷量", "購買數量", "件數"]

-- region_name 的 alias
["地區", "區域", "大區"]

當用戶說「銷售額」，LLM 查 column_info 的 alias 字段，發現匹配 order_amount——語義鴻溝被填平了。

examples 字段：給 LLM 看真實數據

examples 也是 JSON 數組，存儲列的真實數據示例。它的作用是讓 LLM 理解這列存的是什麼格式的數據：

-- customer_id 的 examples
["C001", "C002", "C003", ...]

-- order_amount 的 examples  
[8999.0, 6999.0, 125.0, 899.0, ...]

-- member_level 的 examples
["黃金", "白銀", "青銅", "鉑金"]

有了這些示例，LLM 知道 member_level 存的是「黃金/白銀/青銅/鉑金」，而不是數字。當用戶說「黃金會員」，LLM 就能精確匹配。

table_id 的關聯方式

column_info 的 table_id 字段指向 table_info 的 id。這樣就把列和表關聯起來了：

column_info.table_id = table_info.id

例如：
  column_info ('fact_order.order_amount').table_id = 'fact_order'
  table_info ('fact_order').role = 'fact'

LLM 通過這層關聯，能知道 order_amount 來自事實表 fact_order，role 是 measure——需要聚合。而 region_name 來自維度表 dim_region，role 是 dimension——需要分組。

小結

table_info 告訴 LLM 每張表是事實表還是維度表；column_info 告訴 LLM 每列的角色、別名、示例數據。兩張表配合，LLM 就能從自然語言精準定位到數據庫的列，並知道該對它做什麼操作。接下來看指標層——metric_info 和 column_metric。
