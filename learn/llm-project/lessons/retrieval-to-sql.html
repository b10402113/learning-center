多路召回到 SQL 生成

Step 3/4 · 一個查詢的完整旅程

學習目標

能畫出「關鍵詞抽取 → 三路並行召回 → 合併過濾 → SQL 生成 → 校驗校正」的完整管線，說清每個節點的輸入與輸出。

12 個節點的工作流

上一步我們知道了元數據知識庫的三層結構。現在要看的是：系統怎麼利用這些元數據，從用戶的一句話一步步生成最終的 SQL。整個過程由 LangGraph（基於圖結構的 Agent 編排框架）驅動，一共 12 個節點。

這 12 個節點可以分成五大階段：

START
  ↓
① extract_keywords（關鍵詞抽取）
  ↓ ┌──────────┬──────────┐
  ↓ recall_column  recall_metric  recall_value  ← 三路並行
  ↓ └──────────┴──────────┘
  ↓
② merge_retrieved_info（合併召回信息）
  ↓ ┌──────────┬──────────┐
  ↓ filter_table    filter_metric        ← 並行過濾
  ↓ └──────────┴──────────┘
  ↓
③ add_extra_context（注入額外上下文）
  ↓
④ generate_sql → validate_sql
  ↓                     ↓
  ↓              ┌──────┴──────┐
  ↓        error=None    error≠None
  ↓              ↓            ↓
  ↓        execute_sql   correct_sql
  ↓              ↓            ↓
  ↓              └──────┬──────┘
  ↓                     ↓
  END ← execute_sql

階段一：關鍵詞抽取

輸入：用戶的自然語言問題（如「上週華東地區的訂單總金額」）。

系統用 jieba 中文分詞庫對問題進行分詞，然後按詞性篩選出關鍵詞。jieba 會把句子拆成：上週/t（時間）、華東/n（名詞）、地區/n、訂單/n、總金額/n。名詞和時間詞被提取出來，作為後續三路召回的檢索詞。

輸出：關鍵詞列表。

階段二：三路並行召回

關鍵詞列表出來後，系統同時發起三路召回。注意這裡的「並行」是真正的並行——LangGraph 的圖結構讓三個節點同時執行，不互相等待。

字段召回（recall_column）

系統先把關鍵詞餵給 LLM，讓 LLM 擴展出更多相關詞（比如「訂單」可能擴展出「交易」「消費」），然後把擴展後的詞轉成向量，在 Qdrant 的 data-agent-column 集合裡做相似度搜索。搜到的結果是相關字段的完整信息（名稱、類型、描述、別名等）。

指標召回（recall_metric）

和字段召回類似，但搜索的集合是 data-agent-metric。指標召回找到的是業務指標的定義（如「訂單總金額 = SUM(order_amount)」），這些定義是 SQL 生成的語義依據。

取值召回（recall_value）

這路走的是 Elasticsearch。關鍵詞（如「華東」）被送到 ES 做全文搜索，在 data-agent-value 索引裡匹配維度值。找到的結果包括具體的值和它所屬的字段 ID，這樣系統就知道「華東」對應的是 region_name 字段。

三路召回的輸出格式統一：一組候選記錄，每條記錄帶有來源信息（來自哪個集合/索引）。

階段三：合併過濾

合併（merge_retrieved_info）

三路召回的結果先匯合到一起。合併節點做三件事：

  1. 補充主外鍵——召回結果裡可能只有用戶問到的字段，但 SQL 生成需要主外鍵來做 JOIN。合併節點會從 MySQL 補查每張表的主鍵和外鍵字段。
  2. 補充取值示例——把取值召回找到的具體值（如「華東」）補到對應字段的 examples 列表裡，讓 LLM 知道這個字段裡實際存了什麼值。
  3. 按表分組——把字段按所屬表分組，形成「表 → 字段列表」的映射結構。

輸出：結構化的表信息列表 + 指標信息列表。

過濾表（filter_table）和過濾指標（filter_metric）

合併後的候選清單可能有噪音——比如用戶問的是「訂單金額」，但召回結果裡可能帶上了「發貨地址」這種不相關的字段。過濾節點用 LLM 做精篩：

  • filter_table——把用戶問題和候選表信息一起餵給 LLM，讓它判斷哪些表和字段是真正需要的，輸出一個「表名 → 選中字段」的映射。
  • filter_metric——同樣用 LLM 過濾，只保留和用戶問題相關的指標。

兩個過濾節點也是並行執行的。過濾後，候選清單縮減到最小必要集合。

階段四：SQL 生成與校驗

注入額外上下文（add_extra_context）

在生成 SQL 之前，系統還要補充兩個信息：當前日期（讓 LLM 知道「上週」是哪一週）和數據庫方言（MySQL 的語法細節）。這些信息被注入到狀態中，和元數據一起傳給下一個節點。

生成 SQL（generate_sql）

這是核心節點。輸入是：

  • 用戶的原始問題
  • 過濾後的表/字段/指標信息（最小必要 schema）
  • 當前日期和數據庫方言

LLM 根據這些信息生成一條 SQL 語句。Prompt 裡有嚴格的約束：必須用提供的表和字段名、必須遵循指標的定義口径、不能編造不存在的表或字段。

校驗 SQL（validate_sql）

生成的 SQL 不直接執行——先用 EXPLAIN 語句做語法校驗。如果 SQL 有語法錯誤，EXPLAIN 會報錯。

校驗結果決定走向：

結果走向
error = None（通過）→ execute_sql
error ≠ None（失敗）→ correct_sql

校正 SQL（correct_sql）

如果校驗失敗，系統把原始 SQL 和錯誤信息一起餵給 LLM，讓它修正。校正後的 SQL 會重新回到 validate_sql 再校驗一次，形成一個校正回路。

階段五：執行 SQL

校驗通過的 SQL 被送到數據倉庫執行，拿到查詢結果。結果通過 stream_writer 以 SSE 格式推送到前端，格式是 {"type": "result", "data": [...]}。

流式輸出機制

整個工作流的每個節點在執行時，都會通過 LangGraph 的 stream_writer 實時推送進度：

{"type": "progress", "step": "抽取關鍵詞", "status": "running"}
{"type": "progress", "step": "抽取關鍵詞", "status": "success"}
{"type": "progress", "step": "召回字段", "status": "running"}
...（其他節點）
{"type": "result", "data": [{"region_name": "華東", "order_amount": 2000}]}

前端收到這些事件後，實時更新進度提示和結果表格。

小結

12 個節點分成五大階段：關鍵詞抽取 → 三路並行召回 → 合併過濾 → SQL 生成校驗 → 執行。並行分支提高效率，條件分支處理錯誤校正，流式輸出保障用戶體驗。每個節點的輸入輸出都很明確，這是搭建類似系統的核心骨架。
