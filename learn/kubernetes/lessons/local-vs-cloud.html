Kubernetes 是標準，不是地方

建立本地開發環境 · 第 1 步

學習目標

能說出為什麼 Kubernetes 是一個 API 標準而非特定基礎設施，並解釋同一份 manifest 如何跨環境部署。

Kubernetes 到底是什麼？

很多人聽到 Kubernetes（K8s），直覺會想「是不是又一個伺服器平台？」「是不是要用 AWS？」這些聯想都有原因——大部分教程都從雲端講起。但 Kubernetes 的核心定義其實很簡單：

Kubernetes 是一個容器編排的 API 標準，不是一台伺服器，也不是一個雲端服務。

什麼是「API 標準」？意思是 Kubernetes 定義了一套完整的規格：怎麼描述你想要什麼（desired state）、怎麼管理容器的生命週期、怎麼做服務發現、怎麼擴縮。這套規格跟「跑在哪裡」完全無關。

同一份 manifest，跑在任何地方

你在筆電上寫了一個 Deployment manifest，宣告「我要 3 個 nginx 副本」。這份 YAML 檔案可以用 `kubectl apply` 套用到：

  • 你筆電上的 Kind 集群
  • 公司機房的 on-premise 集群
  • AWS EKS 的雲端集群
  • 甚至 Raspberry Pi 上的 microK8s

指令一樣，manifest 一樣，操作方式一樣。改變的只有底層基礎設施——從 Docker 容器變成 EC2 實體機器，從 local-path 變成 EBS 磁碟——但 Kubernetes API 是恆定的。這就是「定義留下，位置改變」。

這跟以前的做法形成強烈對比。以前用 Docker Compose，你得在每台機器上裝 Docker Compose，然後 SSH 過去跑指令。用 Ansible，你得針對每種基礎設施寫不同的 playbooks。Kubernetes 把這層差異抽象掉了。

多雲變得微不足道

因為 Kubernetes 是標準，所以多雲（multi-cloud）在 Kubernetes 世界裡變成一件很簡單的事。你的 manifest 可以同時存在三個地方——筆電做開發、EKS 做 staging、GKE 做 production——切換只是換一個 kubeconfig 指向不同集群。

這不是理論。你在筆電上用 Kind 做的所有操作，未來遷移到 EKS 時，manifest 不用改、kubectl 指令不用改、你的操作流程不用改。唯一要適應的只是「這裡的磁碟更快了」「這裡有真實的 Load Balancer 了」。

K8s 可以跑在哪？

既然 K8s 是標準，那它能跑的地方比你想像的多：

環境實作適用場景
筆電本地Kind, Minikube, k3d開發、測試
邊緣裝置K3s, MicroK8sIoT、Raspberry Pi
公司機房kubeadm, RancherOn-premise 部署
雲端EKS, GKE, AKS生產環境

Kind 的特殊之處在於：它把整個 K8s 集群跑在 Docker 容器裡。對 Kubernetes 來說，底層是容器還是 VM 還是裸機，它不在乎。它只在乎 API 是否一致。

實際操作

在接下來的步驟中，你會用 Kind 在筆電上建一個本地集群。但在那之前，先確認你已經裝好 Docker 和 kubectl：

# 確認 Docker 正在運行
docker version

# 確認 kubectl 已安裝
kubectl version --client

如果你有 Docker Desktop，kubectl 通常會一起安裝。如果沒有，可以從 Kubernetes 官網下載。
