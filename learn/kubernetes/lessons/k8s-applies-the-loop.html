Kubernetes 如何套用 Reconciliation Loop

Kubernetes 核心：Reconciliation Loop · Step 2/3

學習目標

說明 Kubernetes 將 loop 應用在容器、Volume、IP、Load Balancer 等資源上的方式，以及為什麼 loop 是整個平台唯一一致的組件。

Kubernetes 裡有成千上萬個 Loop

上一步你學到，reconciliation loop 就是「聲明期望 → 觀察實際 → 關閉差距」。在 Kubernetes 裡，每一個資源都有自己的 loop 在跑。不是只有一個大循環——而是成千上萬個小循環同時運作，各自管理各自的資源。

舉幾個例子：

資源類型期望狀態（Desired）實際狀態（Actual）Reconcile 動作
Container（容器）容器應該在跑容器停了重新啟動容器
Volume（儲存卷）磁碟應該掛載到 Pod磁碟未掛載掛載磁碟
IP 位址Pod 應該有 IPPod 沒有 IP分配 IP
Load Balancer流量應該導到健康的 Pod某 Pod 不健康從負載均衡移除該 Pod

每一個 loop 都在做同一件事：檢查「你想要什麼」和「實際上有什麼」之間的差距，然後想辦法關閉。

Loop 是唯一一致的東西

Kubernetes 生態系龐大得嚇人——有數千個不同的組件、控制器、Operator、插件。但所有這些東西，不管它們做什麼，底層都在跑同一個 reconciliation loop。

這意味著loop 是你在 Kubernetes 裡唯一可以完全依賴的一致機制。不管遇到什麼問題——Pod 跑不起來、Service 沒有流量、儲存卷掛不上——你都可以回到同一個思考框架：

  1. 期望狀態是什麼？（你寫的 manifest 裡聲明了什麼）
  2. 實際狀態是什麼？（kubectl get / kubectl describe 看到什麼）
  3. 差距在哪？怎麼關閉？

這就是為什麼 Kubernetes 雖然學起來很重，但一旦學會就非常好除錯——因為所有的問題都可以用同一個邏輯拆解。

Controller 就是 Loop 的管理者

在 Kubernetes 裡，管理某個資源的 reconciliation loop 的組件叫做 Controller（控制器）。例如：

  • Deployment Controller 管理 Deployment 的 loop：你聲明要 3 個 Pod，它確保確實有 3 個在跑
  • Node Controller 管理節點的 loop：你聲明要 5 個 worker node，它確保有 5 個 healthy 的節點
  • Service Controller 管理 Service 的 loop：你聲明要一個 Load Balancer，它確保雲端真的建立了一個

每個 Controller 只管自己的資源，但機制完全相同：desired → actual → reconcile。這種設計讓 Kubernetes 能夠用一致的方式管理截然不同的基礎設施。

操控面板（Control Plane）：所有 Loop 的總管

這些 Controller 都跑在一個叫做 Control Plane（控制平面）的地方。Control Plane 是整個集群的大腦——它不直接跑你的應用，它負責：

  • 儲存整個集群的狀態（存在 etcd 這個分散式資料庫裡）
  • 執行所有 Controller，讓它們各自的 loop 持續運作
  • 接收你的 manifest（透過 API Server），更新期望狀態

當你執行 kubectl apply -f deployment.yaml，你其實是在告訴 API Server：「我想要 3 個 Pod 在跑。」API Server 把這個期望狀態存進 etcd，然後 Deployment Controller 的 loop 偵測到差距，開始建立 Pod。

整個過程沒有任何人在旁邊按按鈕——loop 自己發現、自己調整、自己完成。

小結

Kubernetes 的每一種資源——容器、儲存、網路、負載均衡——都由各自的 Controller 透過 reconciliation loop 管理。loop 是整個平台唯一一致的機制，也是你除錯時的思維起點。下一個問題是：這種 loop 架構和我們熟悉的 Ansible 等指令式工具有什麼不同？
