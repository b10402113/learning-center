Deployment 與自我修復

Kubernetes · Tier 1 · 第一個應用部署（POC）

學習目標

理解 Deployment 如何管理 Pod 的生命週期，並能示範刪除 Pod 後 Deployment 自動重建的自我修復機制。

裸 Pod 的問題回顧

上一節你跑了一個裸 Pod，然後刪掉了它——Pod 就此消失。這就是裸 Pod 的致命缺陷：沒有控制器在背後監督，Kubernetes 不知道你「想要」多少個 Pod 在跑。

真正的應用不能這樣。你需要一種機制，讓 Kubernetes 知道「我永遠要有一個 Nginx 在跑」，不管發生什麼——Pod 崩潰、節點重啟、甚至整個 Node 宕機——它都會想辦法讓那個 Pod 回來。

這個機制就是 Deployment。

什麼是 Deployment？

Deployment 是 Kubernetes 的一個控制器（controller）。它的職責很簡單：確保集群的實際狀態符合你指定的期望狀態。

當你建立一個 Deployment 並告訴它「我要 1 個 Nginx Pod」時，Deployment 會：

  1. 創建一個 Pod
  2. 持續監控這個 Pod 的狀態
  3. 如果 Pod 消失了（被刪除、崩潰、節點故障），立刻創建一個新的 Pod

你不需要手動重建，不需要寫腳本，不需要 SSH 進去重啟。Deployment 的 reconciliation loop（協調循環）會自動處理一切。

Deployment 是你跟 Kubernetes 的合約：你說「我要 N 個 Pod 在跑」，它就想辦法讓這件事永遠成真。

建立你的第一個 Deployment

用命令式方式建立一個 Deployment：

kubectl create deployment nginx --image=nginx --port=80

確認它已經在跑了：

kubectl get deployments
kubectl get pods

你會看到 Pod 的名稱現在有一個隨機後綴，像是 nginx-7c5ddbdf54-abc12。這個命名格式是 <deployment-name>-<replicaset-hash>-<pod-hash>。ReplicaSet 是 Deployment 背後的另一層控制器——Deployment 管理 ReplicaSet， ReplicaSet 管理 Pod。

自我修復：刪掉 Pod 看看

現在，找到你的 Pod 名稱，然後刪掉它：

kubectl delete pod nginx-7c5ddbdf54-abc12

等幾秒鐘，再看一次：

kubectl get pods

你會看到一個新的 Pod 出現了——名稱的最後一段 hash 不一樣了。Deployment 發現 Pod 不見了，立刻創建了一個新的。整個過程在幾毫秒內完成。

這就是自我修復（self-healing）。它不是一個需要你啟用的功能，而是 Deployment 的內建行為。只要 Deployment 存在，它就會永遠試圖讓 Pod 的數量符合你的期望。

控制器模式（Controller Pattern）

這個「期望 vs 實際」的模式是 Kubernetes 的核心設計哲學。你在前面的章節已經學過 reconciliation loop——現在你親眼看到了它的運作：

概念在 Deployment 中的表現
期望狀態（desired state）「我要 1 個 Nginx Pod 在跑」
實際狀態（actual state）Pod 的即時運行狀態
協調循環（reconcile）Deployment 控制器持續比對，不一致就修正
修正動作刪除多餘的 Pod、重建缺少的 Pod

Kubernetes 裡幾乎所有資源都遵循這個模式：Deployment、Service、ConfigMap、Ingress——它們都有各自的控制器在背後運行 reconciliation loop。

Deployment 擁有 Pod

有一個很重要的概念要記住：你改變的是 Deployment，不是 Pod。

當你需要更新映像版本、修改環境變數、調整資源限制時，你應該改 Deployment 的設定，然後讓它去更新 Pod。直接改 Pod 的設定是沒有意義的——下次 Deployment 重建 Pod 時，你的修改會被覆蓋。

這就像你跟一個自動駕駛系統互動：你設定目的地（期望狀態），系統負責開車（實際狀態）。你不會跳進去手動轉方向盤——你改的是設定，不是結果。

清理

刪掉這個 Deployment，它管理的 Pod 也會一併被刪除：

kubectl delete deployment nginx

這再次證明了控制權的歸屬：Deployment 擁有 Pod，你刪除 Deployment，Pod 也跟著消失。

小結

你現在理解了 Deployment 的核心機制：

  • Deployment 是一個控制器，確保 Pod 的數量符合期望
  • 自我修復是 Deployment 的內建行為，不需要額外啟用
  • 你改變的是 Deployment（期望狀態），不是 Pod（實際狀態）
  • 控制器模式（reconciliation loop）是 Kubernetes 的設計基石
