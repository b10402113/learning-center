# 有了 CLAUDE.md 之後，怎麼讓它自己慢慢變好

兩份都找到，也決定先把重心放在專案那份之後，下一個問題就變成：這份檔案的規則要怎麼維護。

你已經有一份 CLAUDE.md 了。每次想加一條規則，你打開檔案、想措辭、貼上去、存檔。這件事做個三次就開始拖，因為寫一條規則要花的力氣，比那條規則能解決的問題還多，於是你就不寫了。

課程的講法很直接：這類 markdown 檔案，你其實不需要用手寫。Claude Code 內建一個指令叫 `/init`，意思是 initialize（初始化）。它會讀你整個 workspace，把這份員工手冊的初稿或改進方向交回給你。

## /init 做兩件事，差別在你有沒有檔案

如果 workspace 裡還沒有 CLAUDE.md，`/init` 會幫你起草一份。如果你已經有一份，它不會覆蓋，而是針對你現有的內容給建議，告訴你可以怎麼改得更好。

<!--image:1-->

這個指令預設就在 Claude Code 裡，打出來送出，它就會開始分析你整個 workspace。

## 它給的不只是清單，還有一句判斷

跑完之後，你會看到一串建議，外加一段 Claude Code 根據它內部最佳實務給的意見：你該改、該修，還是該整段換掉。

課程示範的那份 workspace 裡，`/init` 建議把 `agents.md` 寫進文件，那是講者拿來接 CodeX（OpenAI 那個 app）的橋樑；也建議把幾個資料夾的位置標出來；還因為它知道你用一個 dashboard 管理 agent，建議把這件事寫成常駐能力放進 CLAUDE.md。

這些建議沒有一條會自動生效。你要自己決定套用哪些；看不懂某條建議在講什麼，也可以直接要 Claude 再解釋一次。

## 平常不要管它，等它開始搞錯再跑

講者特別提醒一個原則：只有在「你覺得 Claude 開始搞不懂你的請求」時，才需要做這一步。

日常工作中，你該少花力氣在 CLAUDE.md 上，讓它跟著你和 Claude Code 一起用久，自然長好。

## 自評 prompt：把四根柱子當檢查表

除了 `/init`，課程另外給了一支 prompt，讓 Claude Code 對照四個支柱，自己評估這份 CLAUDE.md 還能補什麼。

<!--image:2-->

四根柱子在上一段拆過，這裡換個用途：不是拿來寫，是拿來當檢查表。

- **Identity（身分）**：除了交代 agent 是誰，也交代你這個人是誰。講者的版本只有三行：替 agent 取了名字、給了一個「chief of staff」的角色，再加一句關於氣質的描述。
- **Goals（目標）**：你希望它每次都記住的具體目標。不用寫得很細，但當你就某一段工作提問時，要讓它知道你心裡的終點在哪，它才能對著那個終點給你建議。
- **Rules（規則）**：真正像員工手冊的那一塊，告訴它怎麼動作、怎麼應對、哪些東西不要碰。
- **Map（地圖）**：把 CLAUDE.md 當成你 workspace 或 second brain 的地圖。講者的版本替自己列了內容、社群、產品開發、設計、營運這些領域，也標出各領域的專案在哪個資料夾。

## 讓它自己動手改

四根柱子裡最實用的一條，不管你用哪個 workspace 都成立：當你覺得某條規則應該存在，就直接要 Claude 去改它自己的 CLAUDE.md，把那條規則加進去。

<!--image:3-->

這比你自己開檔案寫還短，而且它會照著整份文件的語氣與結構放進去，不是硬插一段。課程也把這條列成建議：讓 Claude 在合理的時機，主動對自己的 CLAUDE.md 提出修改。

## 只在跑歪的時候自評

講者的結論很收斂：隨著你越用越多，只有在 CLAUDE.md 沒有達到預期，或它做的事跟你要的不一致時，才真的需要讓它自我更新。

反過來說，只要這份員工手冊至少涵蓋了你的身分、你替它設定的目標、規則，以及 workspace 的地圖，一份簡單的 CLAUDE.md 就夠你走很遠了。
