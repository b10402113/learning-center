# Audit：讓 agent 用 Playwright 把所有按鈕和表單點過一遍

你的網站看起來很完整：按鈕有陰影，表單有動畫，手機版也沒有跑版。

直到你把網址傳給朋友。他按下「聯絡我們」，送出表單，畫面卻什麼也沒發生。

上一課只把一張表單接上 Resend，其他按鈕和表單還沒人碰過。這一課把 CRAFT 的 Audit 做完：在上線前，讓 agent 自己走訪網站，一個一個點按鈕、填表單。

## 先看看網站怎麼壞掉

很多人做前端，做到「畫面做得出來」就停了。

畫面有了，版面也正確，點下去甚至會有反應；但按鈕後面沒有接上功能。表單收得到輸入，卻沒有結果。

上一課用餐廳比喻說明過：前端像外場，功能像廚房。你只點亮了一張桌子，廚房還沒替其他桌開火。

「看起來漂亮」跟「實際能用」是兩件事，而且後者不會自己發生。

## Rig 做完了，但那只是一張表單

上一課的 rig 只做完三件事：把表單內容送到正確的地方、用 API key 讓 Resend 接受請求、實際送一次確認信收得到。

其中第三件事最容易被跳過。很多人接好線就宣布完成，心裡想著「應該會動」；但一張表單測過，不代表其他按鈕也活著。

## Audit：讓 agent 自己當第一個使用者

功能接好了，問題還在後面。

網站上可能有很多按鈕和表單，你剛才測過的只是一個。其他地方你沒點過，也不知道哪些有問題。

Audit 的做法，是讓 agent 自己打開瀏覽器，把網站當成新訪客走一遍。

這一步用的工具是 Playwright。它免費，能讓 agent 操作瀏覽器：開頁面、點按鈕、填表單、看結果。

工具不是重點，重點是由誰挑出問題。

自己檢查很容易漏掉。你可能會直接點自己知道能用的地方，跳過那些擔心會出錯的地方。agent 則照著流程一步一步來：每個按鈕都點，每張表單都填，出問題的地方就會浮現。

跑完之後，它交回來的是一份問題清單，不是一句「看起來沒問題」。

## 你要它檢查什麼

Audit 要找的，是「使用者會遇到、但你自己沒遇到」的狀況。

想像一個第一次造訪網站的人。他不知道哪些按鈕只是裝飾，哪些真的能用；可能到處亂點，也可能只填一半就送出。agent 要走的就是這條路，不是你熟悉的那條。

所以下指令時要把範圍說清楚：整個網站、每一個按鈕、每一張表單。範圍講得越模糊，回來的報告就越沒用。

## 把 rig 和 audit 串成一個循環

Rig 一次，audit 一次，然後重複。

這門課特別強調這一點：audit 不是最後收尾做一次，是可以反覆跑的循環。每次 build 都走同一條路：先加功能，再接線，最後讓 agent 檢查一遍。

流程固定，檢查的內容也跟著固定。你不用每次重新想「這次要特別看什麼」，也比較不會因為趕時間就跳過 audit，它本來就是流程的一部分。

順序也不能顛倒。先 rig 再 audit，agent 才有功能可以檢查。反過來先 audit，檢查到的只是一個還沒有功能的空殼。

## 想確認它真的有在檢查

你可以故意把網站弄壞一次。

例如改掉某個按鈕的連結，或拿掉表單的 API key，再跑一次 audit，看 agent 能不能指出問題在哪。

如果它抓到了，你得到的是一次真的檢查，不是一份寫得漂亮的「一切正常」。

如果它沒抓到，先別急著改網站，該改的可能是你給它的檢查範圍。

## 上線前的最後一道檢查

Audit 排在上線前，是最後一道檢查。

前面的步驟在處理「網站看起來好不好看」，這一步在確認「按下去有沒有反應」。兩者的驗收標準不一樣，不能用同一種感覺判斷。

網站好看，不代表網站能用。Rig 讓網站有功能，audit 幫你確認功能沒出問題。

完成這兩步，你才比較敢把網址傳出去。不是因為你猜它會動，而是 agent 已經替你逐一點過一輪。
