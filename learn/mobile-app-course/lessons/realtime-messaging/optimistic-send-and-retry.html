樂觀送出與重試：pending outbox 與 requestId 對帳

Step 4/5 · 即時私訊

學習目標

學完這一節，你能在前端先顯示 pending 訊息、用 requestId 與後端訊息對帳，並在失敗時提供可重試的狀態。

前言：為什麼訊息要「先出現」

前一節把伺服器端的 send 準備好了，它不怕你重送。現在鏡頭切到手機這一端。

使用者在對話框打完字、按下送出。從按下到後端回覆，可能只要兩百毫秒，也可能在訊號不好時拖好幾秒。如果畫面堅持「等後端確認才顯示訊息」，那幾秒裡輸入框清空了、對話卻沒有任何動靜，使用者會以為訊息沒送出去，於是再按一次。這種不確定的感覺，是聊天體驗裡最傷的一種。

解法叫樂觀更新：按下送出的那一刻，就先讓訊息出現在畫面上，假裝它已經成功；同時在背景真的把它送出去。如果成功，畫面幾乎無縫接軌；如果失敗，才把狀態改成「未送出」並提供重試。這一節要處理的，就是這個「假裝」要怎麼收尾才會乾淨。

動手前你需要具備什麼

這一節用到三個現成零件：一個跨畫面共用的 outbox（負責存待送訊息）、對話歷史的即時查詢（負責提供後端正式訊息），以及顯示訊息的聊天畫面（負責把 pending 與正式訊息一起畫出來）。後端的 send 必須支援 requestId 去重——也就是上一節完成的東西。

第一步：按下送出，先在本地佔一個位

type Pending = {
  id: string; conversationId: Id<'conversations'>;
  text: string; createdAt: number;
  status: 'pending' | 'failed';
};

function send(conversationId, text) {
  const item = {
    id: randomUUID(), conversationId, text,
    createdAt: Date.now(), status: 'pending',
  };
  setPending(items => [...items, item]);
  void retry(item);
}

待送訊息存成一個陣列，每一項都有自己的 id。這個 id 是用 randomUUID() 現產的，而它同時就是等等要傳給後端的 requestId。先用本地的 UUID 佔位，是整個對帳機制的起點：本地知道「我送的是哪一則」，後端也用同一把鑰匙去重。

send 只做兩件事——把項目丟進 pending 陣列、然後呼叫 retry。注意它沒有直接呼叫後端 mutation，而是繞了一手。這是刻意的。

第二步：讓「第一次送」與「重試」走同一條路

async function retry(item) {
  if (busy.current.has(item.id)) return;
  busy.current.add(item.id);
  setPending(items => items.map(row =>
    row.id === item.id ? { ...row, status: 'pending' } : row));
  try {
    await mutate({
      id: item.conversationId, text: item.text, requestId: item.id,
    });
    setPending(items => items.filter(row => row.id !== item.id));
  } catch {
    setPending(items => items.map(row =>
      row.id === item.id ? { ...row, status: 'failed' } : row));
  } finally {
    busy.current.delete(item.id);
  }
}

retry 是唯一真正呼叫後端的地方。成功時把項目從 pending 移除——因為接下來它會以正式訊息的身分出現在歷史查詢裡；失敗時把它留在陣列裡，狀態改成 failed。由於第一次送出也是呼叫它，兩條路徑的行為天生一致，不會有「重試走另一套比較容易出錯的邏輯」這種事。

開頭的 busy 集合用來擋掉重複點擊。雖然後端的去重會確保資料不會重複，但前端也不該濫發請求；有人連續猛點「重試」時，這個集合會讓第二次之後的點擊直接返回。

狀態只有三種：pending（正在送）、failed（送失敗，可重試），以及「已經不在陣列裡」（後端已收到）。畫面的責任，就是把這三種狀態誠實地呈現出來。

第三步：把 pending 疊到歷史訊息上

聊天畫面同時有兩份資料。一份是後端的歷史訊息，由訂閱取得，裡面是「已經正式存在」的訊息；另一份是本地 outbox 的 pending 陣列，裡面是「還沒被後端確認」的訊息。畫面要把它們合併成一個列表來顯示。

const history = usePaginatedQuery(
  api.messaging.history, { id }, { initialNumItems: 30 });
const outbox = useMessages();

// 歷史查詢是新的在前，畫面要舊的在前，所以先反轉。
const messages = history.results.slice().reverse().map(item => ({
  id: item._id, text: item.text, outgoing: item.outgoing,
  time: messageTime(item._creationTime),
}));

// 把還沒被後端確認的 pending 疊上去。
for (const item of outbox.pending) {
  const alreadySaved = item.conversationId === id &&
    history.results.some(saved =>
      saved.outgoing && saved.requestId === item.id);
  if (alreadySaved) continue;

  messages.push({
    id: item.id, text: item.text, outgoing: true,
    time: messageTime(item.createdAt),
    status: item.status, retry: () => outbox.retry(item),
  });
}

關鍵在那個 alreadySaved 判斷。歷史訊息裡每一則都帶著當初送出的 requestId，而 pending 項目的 id 就是同一個值。所以只要歷史查詢裡出現了一則 outgoing 且 requestId 相符的訊息，就代表這則訊息已經被後端收下了，本地那個 pending 版本不該再顯示。這一比對就是所謂的「對帳」：把本地的臨時版本，換成後端的正式版本。

如果少了這個判斷，畫面會同時畫出 pending 與正式訊息，使用者就會看到同一句「明天見」出現兩次——一個寫著「Sending…」，一個寫著正式時間。後端的去重保證資料庫裡只有一則；前端的對帳則保證螢幕上也只顯示一則。兩邊各管一件事。

第四步：把狀態誠實地畫出來

<Text>
  {message.status === 'pending' ? 'Sending…' : message.time}
</Text>
{message.status === 'failed' && (
  <Pressable onPress={message.retry}>
    <Text>Not sent · Tap to retry</Text>
  </Pressable>
)}

聊天畫面根據 status 決定要顯示什麼。還在送，就顯示「Sending…」，讓使用者知道它正在路上；失敗了，就顯示「Not sent · Tap to retry」，並把點擊接回 retry。因為 retry 用的還是原本那個 requestId，這次重試就算後端其實早就收過，也只會拿回同一則訊息，不會產生第二則。

完整流程走一次

使用者打出「明天見」並按下送出。send 立刻用一個新的 UUID 建立 pending 項目，畫面出現一顆寫著「Sending…」的藍色泡泡。同時 retry 在背景呼叫 send mutation。

如果一切順利，後端寫入訊息並回傳。後端的即時歷史查詢更新，帶著同一個 UUID 的正式訊息出現在 history.results 裡。下一次畫面重繪時，alreadySaved 成立，pending 不再被疊上去；泡泡上的「Sending…」換成正式時間。使用者幾乎感覺不到中間發生過什麼。

如果請求失敗，項目留在陣列裡、狀態變成 failed，泡泡下面出現「Not sent · Tap to retry」。使用者點一下，retry 用同一個 UUID 重送。這次成功後，它就跟前面那條路徑匯流，pending 被移除、正式訊息接手。

小結

樂觀送出是三個零件的合作：前端用 randomUUID() 在本地先建一個 pending 項目並立刻顯示；同一個 UUID 當作 requestId 傳給後端；當即時歷史查詢裡出現相同 requestId 的正式訊息時，就把 pending 版本移除。後端的去重防止資料重複，前端的對帳防止畫面重複，重試則讓失敗有第二條路可以走。

訊息可以送了，還剩下最後一塊拼圖：對方怎麼知道有未讀、而讀過之後那個標記又是怎麼消失的。下一步會回到 inbox 上的兩個序號，把「未讀」講清楚。
