未讀與已讀：用 sequence 比對，而不是布林旗標

Step 5/5 · 即時私訊

學習目標

學完這一節，你能解釋未讀為何由 latestIncomingSequence 與 lastReadSequence 比較得出，以及 markRead 在什麼時機被觸發、收件匣的未讀篩選怎麼運作。

前言：那個小藍點，什麼時候該消失？

前四步走完，你已經能開對話、送訊息，而且訊息會即時出現在對方的畫面上。最後剩下一件很日常、卻很容易做壞的事：對方要怎麼知道有未讀？而當他真的讀了，那個提示又要怎麼正確地消失？

最直覺的答案是在訊息上掛一個 read 布林值：收到時設 false，讀了設 true。可是很快你就會遇到麻煩。訊息一多，是每一則各記一個布林，還是整條對話記一個？如果是整條對話記一個，那「讀完之後又來一則新訊息」要怎麼處理？如果使用者只讀到一半，剩下的算不算未讀？這些問題會逼你不斷在各種時機手動翻轉那個布林值，只要漏掉一個地方，未讀就會顯示錯誤。

這個節點選擇另一條路：不記「讀了沒」，改記兩個數字，讓「未讀」永遠是算出來的結果，而不是需要小心維護的狀態。

兩個數字，取代一個布林值

回到第一步的 inbox 表。每個使用者的那一列上，有兩個序號欄位：

欄位意思
latestIncomingSequence我收到的最新訊息，是第幾號
lastReadSequence我已經讀到的位置，是第幾號

當一則新訊息送達，send 會把收件者的 latestIncomingSequence 更新為這則訊息的 sequence。而當使用者真的讀了，markRead 會把 lastReadSequence 往前推。於是「有沒有未讀」就只是一個比較：

unread = latestIncomingSequence > lastReadSequence

這個算法最大的好處是可以重複計算。不管你在什麼時候、重算幾次、兩次事件誰先到，只要這兩個數字當下是多少，答案就是多少。你不需要記得「上一次有沒有把 unread 翻成 true」，也不需要擔心漏掉某個時機會讓標記永遠卡住。未讀變成一個從資料推導出來的結論，而不是一份需要同步的副本。

面向布林旗標兩個序號比對
狀態來源手動翻轉，需要記得每個時機由資料推導，隨時重算
漏掉一次更新標記可能永遠錯誤下次重算就修正
只讀到一半難以表達「讀到哪」用序號精確表達位置
事件順序顛倒可能把新訊息誤標已讀比大小，與順序無關

markRead：把「讀到哪」往前推

使用者讀訊息時，前端會呼叫 markRead。它的工作是把 lastReadSequence 更新到「這次確實看到的最新序號」，然後重算未讀。

export const markRead = mutation({
  args: { id: v.id('conversations'), throughSequence: v.number() },
  returns: v.null(),
  handler: async (ctx, args) => {
    const { me, conversation } = await requireConversation(ctx, args.id);
    if (!Number.isInteger(args.throughSequence) ||
        args.throughSequence < 0 ||
        args.throughSequence > conversation.latestSequence)
      throw new ConvexError('Invalid read position.');

    const row = /* 我的 inbox 列 */;
    const lastReadSequence =
      Math.max(row.lastReadSequence, args.throughSequence);
    if (lastReadSequence !== row.lastReadSequence)
      await ctx.db.patch('inbox', row._id, {
        lastReadSequence,
        unread: row.latestIncomingSequence > lastReadSequence,
      });
    return null;
  },
});

這裡有兩個細節值得注意。第一，throughSequence 是「我讀到第幾號」，不是「全部已讀」。這讓讀取可以精準：如果使用者在讀的過程中，又有新訊息（第 9 號）進來，而他只看到第 7 號，那 lastReadSequence 只推到 7，第 8、9 號仍然算未讀。如果用「全部標已讀」，剛到的新訊息就會被誤清成已讀。

第二，Math.max 讓 lastReadSequence 只前進、不後退。就算重複呼叫、或兩個請求幾乎同時到達，讀取位置也不會被拉回去。而且只有在真的改變時才寫入，避免無意義的資料庫寫入。

什麼時候才算「讀了」？

既然要把讀取位置往前推，就得定義「怎樣算讀」。聊天畫面用了三個條件同時成立才觸發 markRead：畫面是聚焦的、App 在前景、而且使用者滾到了底部。

useFocusEffect(useCallback(() => {
  setFocused(true);
  return () => setFocused(false);
}, []));

useEffect(() => {
  const sub = AppState.addEventListener('change', state =>
    setActive(state === 'active'));
  return () => sub.remove();
}, []);

const latest = history.results[0]?.sequence;
useEffect(() => {
  if (focused && active && atBottom && latest)
    void markRead({ id, throughSequence: latest });
}, [id, latest, markRead, focused, active, atBottom]);

為什麼要三個條件？如果只要畫面開著就標已讀，那使用者在列表上滑過、或 App 在背景時收到訊息，都可能把未讀清掉，而他其實根本沒看到內容。要求「前景 + 聚焦 + 在底部」，才符合「他真的看到最新的訊息了」這個語意。

atBottom 是從滾動事件算出來的：當捲動位置加上可視高度，已經接近內容底部（差距在 40 點以內）就算在底部。只有當使用者停在最新訊息附近，才把讀取位置推到最新那一則的序號。

收件匣怎麼只顯示未讀

未讀算出來之後，最後要把它用在對話列表上。列表的查詢接受一個 unreadOnly 參數，決定要不要只回傳未讀的對話。

const result = args.unreadOnly
  ? await ctx.db.query('inbox')
      .withIndex('by_userId_and_hasMessages_and_unread_and_lastMessageAt', q =>
        q.eq('userId', me._id)
         .eq('hasMessages', true)
         .eq('unread', true))
      .order('desc')
      .paginate(args.paginationOpts)
  : await ctx.db.query('inbox')
      .withIndex('by_userId_and_hasMessages_and_lastMessageAt', q =>
        q.eq('userId', me._id).eq('hasMessages', true))
      .order('desc')
      .paginate(args.paginationOpts);

兩個分支都用不同的複合索引，這是第一步替 inbox 建好索引的用途。要看全部時，用「使用者 + 有沒有訊息 + 最後時間」的索引，依最後訊息時間由新到舊排出列表；要看未讀時，改用「使用者 + 有沒有訊息 + 未讀 + 最後時間」的索引，把未讀的對話挑出來。兩者都帶上 hasMessages: true，所以剛建立、還沒開始的對話不會出現在列表上。

畫面上對應的是一排篩選標籤。當使用者切到「未讀」，畫面把 unreadOnly 設為 true 重新訂閱查詢；每一列的右側則依 unread 顯示一個小藍點。

const rows = usePaginatedQuery(
  api.messaging.list, { unreadOnly: unread }, { initialNumItems: 20 });

外送訊息的勾勾，和真正的已讀狀態

聊天畫面裡，自己送出的訊息旁邊會有一個勾勾圖示。這個勾勾是「已送出」的視覺表示，屬於呈現層。真正被完整使用、也是這個節點著力的已讀狀態，是收件匣上那組序號的比對：誰的 lastReadSequence 有沒有追上 latestIncomingSequence。

換句話說，你在這一節學到的「已讀」，重點是使用者自己那一側的未讀怎麼被消除，以及對話列表如何反映它。至於對方讀到哪、要不要在氣泡上顯示雙勾，則可沿用同一組序號，只是目前這個實作選擇把力氣放在收件匣的未讀正確性上。

小結

未讀不是一個要小心維護的布林值，而是 latestIncomingSequence 與 lastReadSequence 這兩個數字的比較結果。送出時只推收件者的「收到位置」；讀取時用 Math.max 把「讀到位置」單向前推，並只在真的改變時才寫入。觸發已讀的條件是前景、聚焦、且滾到底部，收件匣則用對應的複合索引只撈未讀。因為未讀是算出來的，漏掉一次更新也不會讓它永遠錯誤。

走完這五步，你手上有一個完整的一對一私訊：三張表各司其職，對話的唯一性由資料形狀保證，送出用 requestId 去重、用 sequence 定序，前端先顯示再對帳，未讀則是兩個序號的比較。把這條線收進自己的 app 時，你只需要換掉「誰可以對話」與「訊息長什麼樣」，其餘的骨架都可以照搬。
