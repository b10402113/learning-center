私訊的三張表：一對對話、訊息流與每人一份收件匣

Step 1/5 · 即時私訊

學習目標

學完這一節，你應該能說出 conversations、messages、inbox 三張表各自負責什麼，以及為什麼一對一私訊要拆成「唯一的對話配對、單調遞增的訊息流、每人一份的收件匣」。

前言：一條訊息，為什麼要動到三張表？

先想像一個很普通的畫面。使用者 A 在對話裡送出「明天見」，使用者 B 的手機幾乎同時跳出通知：訊息列表最上面那一列跳到最前面、預覽文字換成「明天見」、右邊多一個未讀的小藍點。過一會 B 點進對話、滑到底，那個藍點才消失。

這整段體驗，其實是同一條訊息造成的三個不同後果：對話要存在、訊息要留下、而 B 的收件匣要更新。如果你只用一張 messages 表來裝，就會發現每個後果都在逼這張表做它不擅長的事。列出 B 的對話列表時，你得把所有訊息掃過一遍、按對方分組、挑出每組最新的一則；算未讀時，又得在訊息上掛一個「已讀」布林值，然後祈禱每個地方都記得改它。

這一節不寫程式，先建立資料模型。當你知道三張表各自在管什麼，後面四個步驟的每一行程式碼都會有地方可以掛。

一張表撐不住的三個需求

把需求攤開來看，會發現它們天生互相拉扯。對話列表要的是「摘要」：最新的時間、預覽、有沒有未讀。歷史訊息要的是「完整內容」，而且只增不改。未讀狀態是「每個人各自一份」的，同一條訊息對 A 是已送出，對 B 是未讀。

這三種東西如果擠在同一張表，每次列表查詢都要為「摘要」付出掃描全部訊息的代價；每次送訊息又會去改動大量列，讓高頻寫入和穩定資料綁在一起。拆表的目的不是為了表多，而是讓每種查詢只碰它真正需要的那一份資料。

需求只有一張表時拆成三張表後
列出對話列表掃描全部訊息再分組取最新直接讀 inbox 摘要，依時間排序
計算未讀訊息上掛布林值，容易漏改兩個序號比大小，重算也安全
載入歷史訊息和列表資料混在一起只查 messages，依序號分頁
高頻送訊息改動整張大表只動 messages 與 inbox 的摘要列

接下來的三節，就分別看這三張表。

conversations：一對參與者，只能有一條對話

對話表記錄的是「誰和誰在對話」這個身分，以及一條用來排序訊息的計數器。它的欄位很少：

欄位型別用途
participantAprofiles 的 id參與者之一
participantBprofiles 的 id另一位參與者
latestSequencenumber這條對話目前最大的訊息序號

這裡藏了一個很重要的設計：兩個參與者要先用排序固定下來，再寫進 participantA 與 participantB。程式裡就寫成 [me._id, other._id].sort()。原因是資料庫要能保證「A 找 B」和「B 找 A」命中同一條對話，否則同一組人會生出兩條平行對話，訊息從此各走各的。

const [participantA, participantB] = [me._id, other._id].sort();
const existing = await ctx.db
  .query('conversations')
  .withIndex('by_participantA_and_participantB', q =>
    q.eq('participantA', participantA).eq('participantB', participantB))
  .unique();
if (existing) return existing._id;

排序之後再搭配複合索引 by_participantA_and_participantB，查詢就能用 .unique() 直接斷言「這組人最多只會有一條」。這個唯一性不是靠應用層自律，而是靠資料形狀本身擔保。

messages：只增不改的流水帳

訊息表是對話的內容本體，而且設計成一條只增不改的流水帳。每送出一則訊息，就新增一列，不回頭修改舊列。

欄位用途
conversationId這則訊息屬於哪條對話
senderId誰送的
text訊息內容
requestId客戶端產生的識別碼，用來去重
sequence這條對話裡的排序號，從 1 開始遞增

為什麼不用時間戳排序，而要另外做一個 sequence？因為兩台裝置的時鐘可能不同步，同一秒也可能送出好幾則訊息。序號由伺服器在寫入時統一配發，就能給出一個沒有歧義的順序：sequence 比較大的一定比較晚。這個序號同時也是後面「未讀」要靠的基準。

訊息表上有兩個關鍵索引。第一個是 by_conversationId_and_sequence，讓歷史訊息可以按對話查、按序號排序與分頁。第二個是 by_senderId_and_requestId，它讓「同一個人、同一個 requestId」只能有一則訊息，這是重試安全的基礎。

inbox：每個人的那一份摘要

如果說 conversations 是兩人的共同事實，inbox 就是「每個人各自看到的版本」。一條對話會產生兩列 inbox，一人一列，專門服務對話列表與未讀。

欄位用途
userId這列屬於誰
conversationId指向哪條對話
otherId對話另一個人，列表要顯示對方名字與頭像
hasMessages是否已有訊息，用來隱藏剛建立、還空著的對話
unread這個人有沒有未讀
lastReadSequence這個人讀到哪個序號
latestIncomingSequence這個人收到的最新訊息序號
lastMessageAt最後訊息時間，列表用它由新到舊排
preview預覽文字，列表不必再去讀 messages

有了這些欄位，對話列表的查詢就變得非常單純：找出我的 inbox 列、只留 hasMessages 為真的、按 lastMessageAt 由新到舊排。想看未讀，就再加上 unread 為真。這些條件各自都有對應的複合索引，所以列表不必掃描任何一則訊息內容。

你可能已經注意到 lastReadSequence 和 latestIncomingSequence 這一對欄位。未讀不是一個要小心維護的布林值，而是「我收到的最新序號」減去「我讀到的序號」：只要前者大於後者，就是有未讀。這個算法即使重複執行、順序顛倒，結果都一樣。第五步會把它的細節講完，現在只要記得這兩個欄位是為它準備的。

「即時」其實是訂閱查詢，不是一直輪詢

到目前為止講的都是資料怎麼放，但這個功能叫「即時私訊」，你一定會問：B 的手機是怎麼在 A 送出訊息的瞬間就知道的？

答案不在資料表，而在查詢方式。對話列表、對話資訊與歷史訊息，在這套後端裡都是 query：list 回傳收件匣、get 回傳對話與對方資訊、history 回傳分頁後的訊息。前端用 usePaginatedQuery 訂閱它們。當 messages 或 inbox 有任何寫入，後端會重新計算受影響的查詢，並把新結果推給所有訂閱中的畫面。

換句話說，這裡沒有「每三秒問一次好了沒」的輪詢。畫面之所以會動，是因為它訂閱的資料變了。這也是為什麼拆表不會拖慢即時性：送訊息時只寫 messages 與 inbox，被影響的查詢就那幾個，推送自然又快又精準。若你想複習這套機制，可以回到 Convex 後端模型的 reactive 查詢那一節。

小結

一對一私訊被拆成三份責任：conversations 保存「這一對人的唯一對話」與序號計數器；messages 是只增不改的訊息流，靠伺服器配發的 sequence 排序；inbox 則是一人一份的摘要，讓對話列表、預覽與未讀都能不碰訊息內容就算出來。資料拆對了，後面建立對話、送出訊息、樂觀更新與未讀回條，才會各自有乾淨的落點。

資料表只是舞台，還沒有人上台。下一步要建立第一條對話：用 start 讓同一組人永遠命中同一條對話，並且用一道存取守衛擋住不是參與者的人。
