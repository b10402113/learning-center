開啟對話與存取守衛：start 與 requireConversation

Step 2/5 · 即時私訊

學習目標

學完這一節，你能用 start 建立或重用唯一的對話，並用 requireConversation 擋下非參與者與不可用帳號。

前言：按下「傳訊息」的那一刻

上一節把三張表的位置擺好了：對話、訊息、收件匣。這一節要讓它們真的動起來。使用者在搜尋名單裡點了一個人的名字、按下「傳訊息」，App 必須先回答一個問題：「我和這個人之間，已經有一條對話了嗎？」如果有，就沿用；如果沒有，才建立一條，並替雙方各鋪一列收件匣。

聽起來簡單，但這裡出錯的後果不小。如果沒有擋好，同樣兩個人可能生出兩條對話，訊息從此分岔；如果存取權沒守好，任何知道對話 id 的人都能偷看或冒充別人送訊息。所以這一節有兩個主角：負責開門的 start，和負責守門的 requireConversation。

動手前你需要具備什麼

這段程式建立在兩個前提上。第一，schema 裡已經有 conversations、messages、inbox 三張表（含上一節提到的複合索引）。第二，你的後端已經接好身分驗證，有一個 requireProfile 會從登入憑證推導出「現在這個使用者是哪一列 profile」——它絕不接受前端自己傳來的 id。若這兩件事還沒就緒，先回去看 Convex 後端模型與 Convex × Clerk 身分驗證。

完成之後你會得到兩個可驗證的結果：同一組人重複呼叫 start 永遠拿到同一條對話；非參與者呼叫任何對話操作都會被拒絕。

start：只做「找到或建立」這一件事

先看整段程式，再逐段拆。

export const start = mutation({
  args: { profileId: v.id('profiles') },
  returns: v.id('conversations'),
  handler: async (ctx, args) => {
    const me = await requireProfile(ctx);
    const other = await ctx.db.get('profiles', args.profileId);
    if (!other || other.isDemo || other.deletionRequested)
      throw new ConvexError('Fictional demo profiles cannot receive messages.');
    if (other._id === me._id)
      throw new ConvexError('You cannot message yourself.');

    const [participantA, participantB] = [me._id, other._id].sort();
    const existing = await ctx.db
      .query('conversations')
      .withIndex('by_participantA_and_participantB', q =>
        q.eq('participantA', participantA).eq('participantB', participantB))
      .unique();
    if (existing) return existing._id;

    const id = await ctx.db.insert('conversations', {
      participantA, participantB, latestSequence: 0,
    });
    for (const userId of [participantA, participantB]) {
      await ctx.db.insert('inbox', {
        userId, conversationId: id,
        otherId: userId === participantA ? participantB : participantA,
        hasMessages: false, unread: false,
        lastReadSequence: 0, latestIncomingSequence: 0,
        lastMessageAt: 0, preview: '',
      });
    }
    return id;
  },
});

第一行 requireProfile(ctx) 先在伺服器端確定「我是誰」。這件事不能靠前端傳參數，因為任何人都能偽造。接著載入對方，並用一個條件擋掉三種人：不存在、是種子產生的虛構帳號、或是已申請刪除帳號。虛構帳號的訊息沒人會回，對它開對話只會讓使用者困惑，所以這裡直接拒絕。第三個條件則擋下「傳訊息給自己」。

通過檢查後，就把兩個 id 排序，寫進 participantA 與 participantB。然後用上一節的複合索引去查有沒有已存在的對話。.unique() 的意思是「我斷言這裡最多只會有一筆」；如果真的有，直接回傳它的 id。這一步就是「重用」。

只有查不到時才建立。建立時會做兩件事：插入一條 latestSequence 為 0 的對話，以及替雙方各插入一列 inbox。注意這兩列的初始值：hasMessages 是 false、預覽是空字串、序號都是 0。它們是刻意留下的「空對話」，收件匣列表會靠 hasMessages 把這種還沒開始的對話藏起來。這也呼應一個設計決定：start 不是 create，它被呼叫很多次也沒關係，結果永遠是同一條對話。

如果你只記得一句：對話的「唯一」是由排序後的兩個參與者加上唯一索引擔保的，不是靠前端記得先查再建。前者不會出錯，後者只要兩台裝置同時按就會破功。

requireConversation：每個讀寫動作前的守門員

對話建好之後，任何要碰它的動作——讀取、載入歷史、送訊息、標記已讀——都得先過一道關。這道關被收斂成一個小函式，避免每個 mutation 各自寫一次授權邏輯、然後某一個不小心漏掉。

async function requireConversation(ctx, id) {
  const me = await requireProfile(ctx);
  const conversation = await ctx.db.get('conversations', id);
  if (!conversation ||
      (conversation.participantA !== me._id &&
       conversation.participantB !== me._id))
    throw new ConvexError('Not authorized to access this conversation.');

  const other = await ctx.db.get('profiles',
    conversation.participantA === me._id
      ? conversation.participantB
      : conversation.participantA);
  if (!other || other.deletionRequested)
    throw new ConvexError('This member is unavailable.');

  return { me, conversation };
}

它依序做四件事。先確認我是誰；再把對話撈出來；接著檢查我的 id 有沒有出現在兩個參與者欄位裡，只要不是其中之一就擋掉。最後把對方的 profile 一起載入，如果對方已申請刪除，就回報「成員不可用」。這樣一來，就算某個使用者從別處拿到了對話 id，只要他不是參與者，什麼都讀不到、也寫不了。

回頭看上一節的 get、history，以及下一節的 send、之後的 markRead，開頭都是這一行 requireConversation。唯一例外是對話列表 list，因為它是「列出我的收件匣」，只需要知道我是誰，用 requireProfile 就夠了。

get：把對話變成畫面要的樣子

start 回傳的只是一個 id，畫面還需要對方的名字、頭像與其他公開資訊。於是 get 查詢會組合出一個給畫面用的物件：{ _id, other, latestSequence }。其中 other 是經過 publicProfile 投影後的結果——只保留可以公開的欄位，並附上相對於觀看者的狀態。這種「回傳前先塑形」的習慣，讓內部欄位（例如 storage id、Clerk 識別碼）不會不小心流到前端。

畫面上的流程：NewConversation

在手機這一端，建立對話的入口是一個「新訊息」畫面。它先讓使用者搜尋成員，過濾掉自己與種子帳號，然後在點擊時呼叫 start，成功就導到該對話。

const members = result.results.filter(item => !item.isOwn && !item.isDemo);

onPress={async () => {
  setOpening(true);
  try {
    const id = await start({ profileId: item._id });
    close();
    router.push({ pathname: '/chat/[id]', params: { id } });
  } catch (e) {
    Alert.alert('Could not open chat', errorMessage(e));
  } finally {
    setOpening(false);
  }
}}

這段有兩個值得帶回自己 app 的習慣。第一，名單在前端就先過濾掉不該傳的人，但真正的拒絕仍然在後端——前端過濾只是體驗，不是安全。第二，start 是非同步的，畫面用一個 opening 狀態避免使用者連點兩次；就算真的連點了，後端的唯一性也會讓第二次回傳同一條對話。

完成的樣子是這樣：第一次對某人按下「傳訊息」，資料庫會多一條 conversation 與兩列 inbox，畫面直接進入對話頁；第二次對同一個人按，任何事情都不會多出來，只會回到那條既有的對話。

小結

start 的價值在於「找到或建立」而不是「建立」：排序後的參與者配對加上唯一索引，讓同一組人永遠只有一條對話，並替雙方鋪好收件匣。requireConversation 則把存取權收斂成一道必經的守衛，所有讀寫都先確認你是參與者，也順手擋掉已不存在或已刪除的對象。開門與守門分開，功能才有安全的地基。

有了對話，就可以開始講話了。下一步要寫伺服器端的 send：它不只是把文字存起來，還要處理重複送出的可能，並讓收件匣的摘要同步更新。
