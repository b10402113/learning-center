Server Component 直接查 DB：為什麼不用繞 HTTP

Step 1/5 · 員工 Dashboard（Server Components）

學習目標

說出為什麼手機 App 只能繞 HTTP API、而網頁後台卻能直接用 Server Component 查資料庫，並認得這條分界對型別、密鑰與互動性的影響。

前言：同一天，兩個畫面

先想像診所裡的一個下午。櫃檯同事的電腦開著員工後台，畫面上是今天一整排預約；與此同時，另一位護理師用手機打開病人端的 App，看到自己今天要處理的那幾筆。兩個畫面背後是同一份資料，卻是用兩套完全不同的方式拿到的。

手機 App 得先呼叫一支 API，請伺服器幫忙查，再把結果用 JSON 送回來；網頁後台則大方地把資料庫連線直接 import 進來，當場就查。為什麼會有這種差別？這不是誰偷懶，而是因為這兩個前端「站在不同的地方」。這一節要把這條分界線講清楚，因為後面四個步驟——守衛、行程頁、病歷頁、Server Actions——全都掛在這條線上。

手機在信任邊界外，網頁在前端的另一側

手機 App 的程式碼被安裝在病人的裝置上。裝置在使用者手上，網路可以被人攔截，App 的內容也可以被人反組譯。因此它絕不能持有資料庫的連線字串或任何伺服器密鑰，否則等於把診所的資料庫鑰匙複製一份發給每個人。它唯一能做的事，就是隔著網路、帶著登入憑證，去敲伺服器的大門，請伺服器代為查詢。

網頁後台就不一樣了。它跑的 Next.js 伺服器，和瀏覽器看到的那個頁面是兩件事：真正執行頁面邏輯的地方，就是那台已經握有資料庫連線的伺服器。既然程式本來就住在資料庫旁邊，就沒有必要再繞出去、打自己家的 API、再走回來。

用餐廳比喻：手機 App 像坐在位子上的客人，想吃什麼只能舉手請服務生（API）進廚房拿；網頁後台像廚師本人，他本來就站在廚房裡，直接打開冰箱拿就好，不需要先寫一張點菜單再請人送進來。

React Server Component 到底是什麼

Server Component（伺服器元件）是 React 元件的一種。它的程式碼只會在伺服器上執行，永遠不會被打包進送到瀏覽器的那份 JavaScript。這件事有兩個直接後果：第一，它可以安全地引用只有伺服器才有的東西，例如資料庫 client、密鑰、檔案系統；第二，它可以是一個 async 函式，直接 await 一個查詢，等結果回來再繼續往下渲染。

相對地，我們熟悉的、能用 useState、useEffect、onClick 的元件叫 Client Component，需要檔案最上方寫 'use client'。它才會被送進瀏覽器執行、才處理得了互動。同一個頁面裡，兩者可以混用：外層用 Server Component 把資料查好，需要點擊的那一小塊再切出去當 Client Component。

直接查 DB 長什麼樣

下面這段就是 dashboard 首頁的骨架。注意它沒有 fetch、沒有 API 路徑，只有一個 async 元件、一次身分檢查、一次 Drizzle 查詢：

import { db } from '@/db';
import { appointments } from '@/db/schema';
import { requireStaff } from '@/lib/auth';

export default async function DashboardPage() {
  await requireStaff();

  const rows = await db.select().from(appointments);

  // rows 的欄位型別是由 schema 推導出來的，
  // 直接帶進下面的 JSX，不需要另外宣告。
  return <AppointmentTable rows={rows} />;
}

這裡有兩個值得停下來看的細節。第一，requireStaff() 被放在查詢之前。直接查資料庫不代表頁面公開，它仍然是一頁員工限定內容，只是檢查身分的方式從「路由守衛」換成了「在頁面裡呼叫函式」。第二，這裡的 db 和 requireStaff，跟 app/api/ 底下那些 Route Handler 用的是同一套。程式碼重用了，差別只差在一個回傳 JSON、一個回傳 HTML。

另一條路：手機走 HTTP

手機端走的是傳統路線。伺服器先提供一支 API，例如列出預約的端點，裡面同樣做身分檢查與查詢，但最後把結果序列化成 JSON：

// app/api/appointments/route.ts（給手機用的版本）
export const GET = route(async () => {
  const user = await requireAuth();
  const rows = await db.select().from(appointments);
  return json(rows);
});

手機再透過 fetch 呼叫這個端點。整條路是：App → 網路 → Route Handler → 資料庫，查完再原路折返。把兩條路並排，差別就一目了然：

面向手機 App（Expo）網頁後台（RSC）
程式執行位置病人的裝置持有 DB 連線的伺服器
取得資料fetch 一支 API 端點直接 import db 查詢
身分檢查Route Handler 裡的 requireAuth頁面或 layout 的 requireStaff
跨越網路的是JSON渲染好的 HTML
能用互動 hook可以不行，要切 client component

這條分界買到了什麼

型別一路到底。當查詢與 JSX 在同一個檔案、同一次執行裡，Drizzle 從 schema 推導出來的欄位型別會直接跟著 rows 走進畫面。你不用再手寫一份 API 回應的型別，也不用擔心後端改了欄位名稱、前端還停在上一個版本。

少一層搬運。資料不必先變成 JSON、穿過網路、再被前端解析回物件。它從 Postgres 出來之後，就直接被伺服器拿去組 HTML。

不必為了自己的 UI 另外開 API。如果這些資料只有這個後台會用，就沒有理由再多維護一組對外端點。端點是給「外部呼叫者」用的，而頁面自己就是內部呼叫者。

密鑰與病人資料留在伺服器。只有最後的 HTML 會送進瀏覽器；資料庫連線、查詢字串、原始的病人資料列，全部停在伺服器這一側。

代價與邊界：直讀不是萬能

天下沒有白吃的午餐，直接查資料庫也有它的限制。最明顯的是互動性：Server Component 沒有狀態、沒有事件處理、沒有瀏覽器 API。一個會展開收合的選單、一個按下就送出表單的按鈕，都必須切成一塊 Client Component 才行。實務上的分法是：能用伺服器做的（查資料、組版面）留給 Server Component；非互動不可的一小塊才交棒給瀏覽器。

其次，直讀不等於免檢查。每個會碰到病人資料的頁面，仍然要在最前面呼叫 requireStaff()。少了它，這一頁就會變成任何人都能打開的資料外洩入口。至於「查完之後畫面怎麼更新」，是另一個要留到最後一節處理的問題：寫入資料後要用 revalidatePath 讓伺服器重新查一次，畫面才會帶上新資料。

小結

手機 App 執行在信任邊界之外，只能帶著憑證呼叫 API；網頁後台的 Server Component 與資料庫同住一台伺服器，所以可以 import db 直讀。直讀讓你拿到端到端的型別、少一層序列化、不必自建 API、密鑰不外流，但代價是它不能互動（要切 Client Component），而且每一個頁面仍須自己做身分檢查。

現在你知道了「為什麼可以直接查」。但一個後台不是單一頁面，而是一整個子樹：行程、名冊、病歷頁都要守住。下一節要處理的就是這道門該放在哪裡——為什麼 Dentify 把守衛放在 layout，而不是塞進 proxy 做路徑比對。
