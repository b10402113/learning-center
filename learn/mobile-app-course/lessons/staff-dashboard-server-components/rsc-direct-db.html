Server Component 直接查 DB：為什麼不用繞 HTTP

Step 1/5 · 員工 Dashboard（Server Components）

學習目標

能說出同樣一個 Next.js 專案裡，為什麼手機 app 只能走 API、員工 dashboard 卻可以直接 import db 查 Postgres，並分辨 Server Component 與 client component 的邊界。

前言：同一個後端，兩條完全不同的資料路

先想像一個很具體的場景。病房的護理師在手機上打開 app，想看某位病人今天的預約；同一個時刻，櫃檯的員工用筆電打開診所的後台網頁，也在看同一批預約。這兩邊畫面上長得很像，但它們拿到資料的方式完全不一樣。

手機 app 是 Expo 寫的，跑在病人或護理師自己的裝置裡。那台裝置跟診所的伺服器之間隔著網路，誰都可以假裝自己是 app 送請求，所以手機只能透過公開的 API 端點拿資料。而員工 dashboard 是一個 Next.js 網頁，它跟資料庫住在同一台伺服器上。它其實就是「在伺服器裡面」的那個程式，根本沒有必要先繞出去打一支 API、再走回來。

如果你沒把這條分界線想清楚，會發生兩種錯：一種是把明明可以直接查的資料，硬是包成一支 API，多寫了一堆沒必要的程式；另一種更危險，是把「可以直讀資料庫」誤解成「這個頁面是公開的」，於是把病歷赤裸裸地攤在網路上。這一節先把第一種錯講清楚，下一節再來處理第二種。

React Server Component：只跑在伺服器的那半邊

要理解這條分界，得先認識 React 這幾年最大的一次觀念轉變：Server Component（伺服器元件）。傳統的 React 元件全部會被編譯、打包成 JavaScript，送到瀏覽器裡執行。Server Component 不一樣：它的程式碼只會在伺服器上執行，永遠不會被打包進瀏覽器。

這個「永遠不會進瀏覽器」的保證非常關鍵，因為它解除了好幾種長年以來的限制。既然程式碼不會被使用者下載，它就可以安心地碰到那些不能外流的東西：資料庫連線字串、API 金鑰、後端服務的憑證。它也可以直接 import { db }，當場把查詢送進 Postgres，再把結果渲染成 HTML。

當然，天下沒有白吃的午餐。Server Component 沒有 useState、沒有事件處理函式、也碰不到任何瀏覽器 API（像是 window 或 localStorage）。它是一段「跑完就結束、把畫面吐出來」的程式，不是一個會在使用者裝置上持續反應的元件。所以真正需要互動的地方（按鈕、輸入框、下拉選單）仍然得切出來，寫成 client component（用戶端元件）。

兩條路，同一批資料

於是同一個專案裡，就出現了兩種很不一樣的「前端」。把它們並排看，差異一目了然：

手機 app（Expo）員工 dashboard（Next.js）
程式碼跑在哪使用者的裝置診所自己的伺服器
怎麼拿資料呼叫 app/api/ 的 Route Handler直接 import { db } 查 Postgres
為什麼裝置在網路另一端，碰不到資料庫跟資料庫同一台機器，沒有必要繞路
信任邊界公開，要有身分驗證與輸入驗證仍在伺服器內，但也絕非公開

dashboard 這一條路常被形容成「沒有 HTTP hop」：沒有那種「自己打自己」的來回。傳統做法裡，前端要跟同一台伺服器要資料，還是得 fetch('/api/appointments')，走一輪序列化與反序列化。Server Component 直接呼叫函式、直接拿回型別化的結果，中間那段手寫的 API 合約就整個省下來了。

打個比方：手機 app 像是在電話裡點餐，它只能透過話筒把需求講給廚房聽；而 dashboard 就是廚房本身，它可以直接伸手進冰箱拿食材，不需要先打電話給自己。同樣一道菜（同一筆資料），路徑卻因為「站在哪裡」而不同。

看一段真實的程式碼

Dentify 的今日行程頁，就是一個標準的 Server Component。它開頭那段查詢，把上面講的觀念全部落實了：

/** Server Component hitting Drizzle directly — no HTTP hop (PLAN.md architecture). */
export default async function DashboardPage({ searchParams }: PageProps<'/dashboard'>) {
  await requireStaff();

  const params = await searchParams;
  const dateParam = typeof params.date === 'string' ? params.date : undefined;
  const day = dateParam ? parseDay(dateParam) : clinicDayOf(new Date());

  const dayStart = clinicInstant(day, 0, 0);
  const dayEnd = new Date(dayStart.getTime() + 24 * 3600_000);

  const rows = await db
    .select({ /* … */ })
    .from(appointments)
    .innerJoin(patients, eq(patients.id, appointments.patientId))
    .innerJoin(dentists, eq(dentists.id, appointments.dentistId))
    .innerJoin(services, eq(services.id, appointments.serviceId))
    .where(and(gte(appointments.startsAt, dayStart), lt(appointments.startsAt, dayEnd)))
    .orderBy(asc(appointments.startsAt), asc(dentists.displayName));

注意幾個地方。這個函式被宣告成 async，因為它要等資料庫。它回傳的是 JSX，不是 JSON。它在伺服器上就把查詢結果排版成 HTML 了。而它 import 進來的 db 與 schema，是貨真價實的資料庫連線，這在瀏覽器裡是不可能執行的；它之所以能存在，正因為這段程式碼永遠不會被送到瀏覽器。

還有一個容易被忽略的好處：Drizzle 從 schema 推導出來的型別，會一路帶進 JSX。rows 裡每個欄位的名稱與型別，編譯器都知道。你不用在兩端各寫一份 TypeScript interface，也不用擔心 API 改了欄位而某個頁面悄悄壞掉，因為根本沒有那個「中間的 API」。

邊界在哪：什麼時候得切出 client component

Server Component 很方便，但它不能處理互動。一個頁面往往是「伺服器先把資料查好、渲染成 HTML，再把一小塊互動元件交棒給瀏覽器」的組合。以病患病歷頁為例，整頁的病歷、時間軸、附件都是在伺服器讀好的，但「新增術後衛教」的表單、「標記完成」的按鈕，必須是 client component，因為它們要處理打字、點擊和載入狀態。

這條邊界不是用「重要／不重要」來分的，而是用「這個東西需不需要在使用者的裝置上活著」來分。查資料是伺服器的事；互動是瀏覽器的事。下一節會看到，互動元件呼叫伺服器的那條線，正是 Chapter 最後一節要講的 Server Action。

另外，這個世代 Next.js 的頁面 props 是 非同步的。你會看到 await searchParams、之後在病歷頁會看到 await params。這是框架的新約定，把 URL 參數也當成需要等待的資源；寫法上先記得「要用之前先 await」就好，細節留到下一節親手寫時再說。

小結

Server Component 的程式碼只跑在伺服器，永遠不會被打包進瀏覽器，所以它能安全地 import db、碰金鑰，並把 Drizzle 推導的型別帶進 JSX。代價是它沒有 useState、事件處理與瀏覽器 API，需要互動的地方得切出 client component。手機 app 在裝置上跑，只能走公開 API；員工 dashboard 跟資料庫同機，可以直接查、省掉那趟 HTTP 來回。但「可以直讀」不等於「公開」。誰能看到這些資料，是下一個要處理的問題。

既然 dashboard 能直接讀到全診所的資料，那下一個問題就很自然了：誰有資格打開這個後台？總不能每個登入的人都看得到病歷。下一節要把守衛放在對的位置，讓它跟它保護的資料待在一起。
