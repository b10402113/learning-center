Server Actions：不用寫 API 也能寫入，revalidatePath 自動更新

Step 5/5 · 員工 Dashboard（Server Components）

學習目標

用 'use server' 寫出 addVisitNote 與 completeAppointment 兩個 Server Action，在裡面完成授權、驗證、稽核與 revalidatePath，並用 useActionState／useTransition 從 client 呼叫。

前言：最後一哩是「寫入」

前四步處理的都是「讀」：把行程、名冊、病歷查到畫面上。但診所後台不只是看板，醫師看完診要寫術後醫囑、要把某筆預約標記為完成。這是一個真正的寫入動作：它要改資料庫、要留下「是誰改的」的紀錄、還要讓剛剛那頁立刻反映新狀態。

過去做這種事，我們會開一支 POST 的 API Route Handler，前端再用 fetch 去打它。但在這個後台裡，還有一條更短的路：Server Action。它讓你在伺服器端寫一個普通函式，client 端的元件就能像呼叫本地函式一樣呼叫它，中間不必自己維護 API 路徑與請求／回應格式。這一節要把這條路走完，並強調一件不能省的事——少了授權，再方便的捷徑都會變成漏洞。

第一步：用 'use server' 宣告一個 Server Action

'use server';

import { eq } from 'drizzle-orm';
import { revalidatePath } from 'next/cache';

import { db } from '@/db';
import { appointments, patients, visitNotes } from '@/db/schema';
import { audit } from '@/lib/audit';
import { requireStaff } from '@/lib/auth';
import { visitNoteSchema } from '@/lib/validation';

檔案開頭的 'use server' 是關鍵。它告訴 Next.js：這個檔案裡匯出的函式都是 Server Action，只能在伺服器執行。這些函式看起來就像普通的 async 函式，但 Next.js 會在背後把它們編譯成可被呼叫的伺服器端點；client 元件 import 之後呼叫，請求就會自動送到伺服器。因為函式在伺服器執行，它自然可以 import db、寫資料庫、讀環境變數。

第二步：addVisitNote，把醫囑寫進去

export async function addVisitNote(_prev: unknown, formData: FormData) {
  const staff = await requireStaff();

  const parsed = visitNoteSchema.safeParse({
    appointmentId: formData.get('appointmentId'),
    body: formData.get('body'),
  });
  if (!parsed.success) {
    return { error: parsed.error.issues[0]?.message ?? 'Invalid note' };
  }

第一行再一次是 requireStaff()。這點必須反覆強調：Server Action 是一個可以被呼叫的端點，不是只有你的按鈕能碰到的內部函式。把按鈕藏起來不是安全措施，任何人都可能直接送出這個動作。所以每個 action 都要自己重新驗身分，不能假設「使用者是從員工頁面按的」。

接著用 Zod 驗證輸入。表單傳進來的一切都是不可信的：長度、型別、必填欄位都要檢查。驗證失敗時回傳一個帶錯誤訊息的物件，而不是丟出例外——因為這個回傳值要回到 client，讓表單顯示提示。注意函式的第一個參數 _prev，那是 useActionState 用來傳入「上一次結果」的，這裡用不到，所以以底線開頭命名。

  const [appointment] = await db
    .select()
    .from(appointments)
    .where(eq(appointments.id, parsed.data.appointmentId));
  if (!appointment) return { error: 'Appointment not found' };

  await db.insert(visitNotes).values({
    appointmentId: appointment.id,
    body: parsed.data.body,
    createdBy: staff.id,
  });
  await audit(staff.id, 'create', 'visit_notes', appointment.id);

  revalidatePath(`/dashboard/patients/${appointment.patientId}`);
  return { ok: true as const };
}

驗證過後，先確認這筆預約真的存在，再把醫囑寫入。createdBy 用的是 staff.id，也就是從登入 session 推導出來的伺服器端身分——不是 client 傳來的任何值。寫入之後立刻 audit，記錄「誰建立了哪一筆 visit_notes」。最後呼叫 revalidatePath，告訴 Next.js「這個病患頁的快取已經過期了，下次請求重新查資料」。這一招讓畫面自動更新，不需要前端自己重抓。

第三步：completeAppointment，改狀態也更新最後看診日

export async function completeAppointment(appointmentId: string) {
  const staff = await requireStaff();

  const [updated] = await db
    .update(appointments)
    .set({ status: 'completed' })
    .where(eq(appointments.id, appointmentId))
    .returning();
  if (!updated) return { error: 'Appointment not found' };

  await db
    .update(patients)
    .set({ lastVisitAt: updated.startsAt })
    .where(eq(patients.id, updated.patientId));
  await audit(staff.id, 'update', 'appointments', appointmentId);

  revalidatePath(`/dashboard/patients/${updated.patientId}`);
  revalidatePath('/dashboard');
  return { ok: true as const };
}

這個 action 做了兩個關聯的更新：把預約狀態改成 completed，並把病患的「最後看診時間」更新成這筆預約的開始時間。.returning() 讓你可以拿到更新後的資料列，好用來知道要更新哪一位病患、以及要 revalidate 哪些路徑。這裡要注意revalidatePath 被呼叫了兩次：一次是病患頁，一次是 /dashboard 行程頁——因為標記完成同時會影響這兩個畫面的內容。

第四步：client 端用 useActionState 接表單

'use client';

import { useActionState } from 'react';
import { addVisitNote } from './actions';

export function AddNoteForm({ appointmentId }: { appointmentId: string }) {
  const [state, action, pending] = useActionState(addVisitNote, null);

  return (
    <form action={action}>
      <input type="hidden" name="appointmentId" value={appointmentId} />
      <textarea name="body" required maxLength={5000} />
      <button disabled={pending}>{pending ? 'Saving…' : 'Add note'}</button>
      {state && 'error' in state && state.error && <span>{state.error}</span>}
      {state && 'ok' in state && state.ok && <span>Saved</span>}
    </form>
  );
}

表單所在的元件是 Client Component，因為它需要 useActionState 這個 hook。這個 hook 回傳三樣東西：目前的狀態 state、要綁到 <form action> 的動作、以及一個 pending 布林值。把 action 直接接到表單的 action 屬性，Next.js 就會在送出時呼叫對應的 Server Action，並把表單欄位包成 FormData 傳進去。

這裡有一個順帶的好處：即使 JavaScript 還沒載入，這個表單也能送出，因為它用的就是瀏覽器原生的表單提交。這種「漸進增強」讓頁面在弱網或腳本載入失敗時仍然可用。

第五步：用 useTransition 處理按鈕

'use client';

import { useState, useTransition } from 'react';
import { completeAppointment } from './actions';

export function CompleteButton({ appointmentId }: { appointmentId: string }) {
  const [pending, start] = useTransition();
  const [error, setError] = useState<string | null>(null);

  return (
    <button
      type="button"
      disabled={pending}
      onClick={() => start(async () => {
        const result = await completeAppointment(appointmentId);
        setError(result.error ?? null);
      })}
    >{pending ? 'Saving…' : 'Mark complete'}</button>
  );
}

不是每個動作都來自表單。「標記完成」是一顆按鈕，沒有欄位要送，所以用 useTransition：在 start 裡呼叫 Server Action，呼叫期間 pending 為真，按鈕變灰並顯示「Saving…」。回傳的結果若有錯誤就存進 state 顯示。這種寫法和表單版的差別只在「觸發方式」——一個靠送出、一個靠點擊——但兩者呼叫的都是同一個在伺服器上執行的 action。

為什麼可以不用 API：以及不能省的那一步

Server Action 之所以能取代一支 API，是因為它把「端點」隱形化了：你不用想路徑叫什麼、請求要送 JSON 還是 FormData、回應怎麼包。但方便並不等於可以放鬆紀律。每個 action 仍然要：驗身分（requireStaff）、驗輸入（Zod）、留稽核（audit）。這三件事在 API 版本裡你做過的，在這裡一樣都不能少。只要你把 action 當成「內部函式」而不是「公開端點」，就會漏掉授權，然後在某一天收到一份不該被寫入的醫囑。

revalidatePath 是最後一塊拼圖

資料寫入之後，畫面為什麼會更新？因為 revalidatePath 讓 Next.js 知道先前快取的某個路徑已經失效，下一次請求會重新執行伺服器端的查詢。這正好把第一步到第四步串成一個完整迴圈：Server Component 負責讀、Server Action 負責寫、revalidatePath 負責讓讀的那一端知道「該重來了」。你不需要在前端手動重抓，也不需要把資料複製一份到 client 的 state。

小結

Server Action 是標了 'use server' 的伺服器函式，client 元件可以像呼叫本地函式一樣呼叫它，因此後台不必為自己的寫入再開一支 API。每個 action 都必須自己做 requireStaff、Zod 驗證與 audit；做完寫入後用 revalidatePath 讓對應路徑重新查資料。client 端表單用 useActionState、按鈕用 useTransition，並用 pending 狀態給使用者即時回饋。

走完這五步，你已經看完整個員工後台的資料流：Server Component 直讀 Drizzle，守衛與資料同層，讀取留下稽核，寫入走 Server Action 並自動重新整理。之後無論是回頭讀 Dentify 的程式，或替自己的專案長出一個後台，你都有一套可以照著搭的骨架了。
