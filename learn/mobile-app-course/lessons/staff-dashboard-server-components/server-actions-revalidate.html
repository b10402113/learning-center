Server Actions：不用寫 API 也能寫入，revalidatePath 自動更新

Step 5/5 · 員工 Dashboard（Server Components）

學習目標

能用 'use server' 寫出直接寫 DB 的 Server Action，跑完 revalidatePath 讓畫面自動更新，並在 client 端用 useActionState／useTransition 接住狀態。

動手前：從「讀」跨到「寫」

前面四節走完的，全是讀取。可是員工後台真正的工作有一半是寫入：看完診要留下術後衛教，一筆預約結束要標記為完成。在手機 app 那邊，寫入就得多開一支 API Route Handler；但在 dashboard 裡，你其實可以讓一個表單直接呼叫伺服器上的函式。

這一節要做的就是這件事：把寫入包成 Server Action（伺服器動作），寫完資料後讓 Next.js 自動把畫面更新。你會親手看過兩個 action、兩個 client 元件，以及那個讓一切自動重繪的關鍵函式 revalidatePath。

第一步：一個被標記的函式，就是一個端點

Server Action 的定義方式簡單到有點反直覺：在一個函式所在的檔案最上方寫一行 'use server'，這個檔案裡匯出的函式就全部變成可以從瀏覽器呼叫的伺服器動作。以下是病歷頁那支動作檔的開頭：

'use server';

import { eq } from 'drizzle-orm';
import { revalidatePath } from 'next/cache';

import { db } from '@/db';
import { appointments, patients, visitNotes } from '@/db/schema';
import { audit } from '@/lib/audit';
import { requireStaff } from '@/lib/auth';
import { visitNoteSchema } from '@/lib/validation';

那行 'use server' 對 Next.js 來說是明確的指令：這個檔案裡的函式不會被打包進瀏覽器，而是由框架幫你建立一個對應的伺服器端點，讓前端用「呼叫函式」的方式觸發。你不需要自己開 route 檔、不需要決定 HTTP 方法、也不需要手寫 JSON 的請求和回應格式。

第二步：addVisitNote，一個完整的寫入

第一個動作是新增術後衛教筆記。它的簽章看起來有點特別，第一個參數是 _prev，這是為了搭配 useActionState 用的，稍後會解釋。

/** Post-op instructions. Patient-readable, so they land in the mobile visit history. */
export async function addVisitNote(_prev: unknown, formData: FormData) {
  const staff = await requireStaff();

  const parsed = visitNoteSchema.safeParse({
    appointmentId: formData.get('appointmentId'),
    body: formData.get('body'),
  });
  if (!parsed.success) {
    return { error: parsed.error.issues[0]?.message ?? 'Invalid note' };
  }

  const [appointment] = await db
    .select()
    .from(appointments)
    .where(eq(appointments.id, parsed.data.appointmentId));
  if (!appointment) return { error: 'Appointment not found' };

  await db.insert(visitNotes).values({
    appointmentId: appointment.id,
    body: parsed.data.body,
    createdBy: staff.id,
  });
  await audit(staff.id, 'create', 'visit_notes', appointment.id);

  revalidatePath(`/dashboard/patients/${appointment.patientId}`);
  return { ok: true as const };
}

它做的每一件事，都跟我們在 API Route Handler 裡建立的紀律一模一樣。先 requireStaff()，這是關鍵，因為 Server Action 是公開端點，任何人都能呼叫，所以它跟 API 一樣必須自己重新確認身分。接著用 Zod 驗證輸入，safeParse 把 appointmentId 與 body 當成不信任的資料檢查一遍；失敗就回一個 { error }，而不是丟錯讓整個頁面崩掉。然後確認這筆預約真的存在，才 insert。寫入後補一筆 audit，記錄「某位員工建立了這筆筆記」。最後呼叫 revalidatePath，再把成功訊息回傳。

別看這個結構平凡，它其實就是「Server Action 不是後門」的證明：驗證、授權、稽核，一個都沒少。唯一的差別只是呼叫的方式，不是安全的要求。

第三步：completeAppointment，一次改兩張表

第二個動作是把預約標記為完成。它同時動了兩張表：預約本身的狀態，以及病人身上的「上次看診日」。這個欄位以前是名冊頁要顯示的資料，正是靠這裡被更新。留意它用 .returning() 把更新後的資料列拿回來，這樣才有 patientId 與 startsAt 可以用：

/** Marking a visit complete is what moves it into the patient's history. */
export async function completeAppointment(appointmentId: string) {
  const staff = await requireStaff();

  const [updated] = await db
    .update(appointments)
    .set({ status: 'completed' })
    .where(eq(appointments.id, appointmentId))
    .returning();
  if (!updated) return { error: 'Appointment not found' };

  await db
    .update(patients)
    .set({ lastVisitAt: updated.startsAt })
    .where(eq(patients.id, updated.patientId));
  await audit(staff.id, 'update', 'appointments', appointmentId);

  revalidatePath(`/dashboard/patients/${updated.patientId}`);
  revalidatePath('/dashboard');
  return { ok: true as const };
}

最後呼叫了兩次 revalidatePath：一次更新這位病人的病歷頁，一次更新整個 dashboard。為什麼要兩個都做？因為這次改動同時影響兩個畫面：病歷頁的時間軸要把這筆預約標成已完成，而今日行程頁的統計數字也會跟著變。哪一個畫面改變了，就把它加入重繪清單。

第四步：revalidatePath 到底做了什麼

這是整節最值得停下來想一下的地方。Server Component 的輸出是會被快取的：當一位員工打開病歷頁，伺服器查完資料、把 HTML 渲染好之後，這份結果可能被存起來，讓下一個人也更快看到。

問題是，當 completeAppointment 把資料改掉之後，那份被快取起來的舊 HTML 就過時了：它還顯示「booked」，上面的統計也還是舊數字。如果你什麼都不做，下次有人打開頁面，看到的會是舊的內容。

revalidatePath('/dashboard/patients/…') 就是在告訴 Next.js：「這條路徑的快取失效了，下次請求重新查、重新渲染。」於是畫面自動帶著新資料更新，而用戶端完全不用寫一行「重新抓取」的程式。

把它跟手機 app 對照就更有感。手機 app 送出寫入後，通常得在本地狀態裡手動更新、或重新呼叫一次 API 拉最新資料，否則畫面不會動。Server Action 把「改資料」和「讓畫面反映改動」綁在同一個地方，少掉一整類「改了卻忘了刷新」的 bug。

第五步：client 端用 useActionState 接表單

動作寫好了，前端怎麼呼叫？以新增筆記的表單為例：

'use client';

import { useActionState } from 'react';

import { addVisitNote } from './actions';

/** Post-op notes: what the patient reads at 11pm instead of phoning the clinic. */
export function AddNoteForm({ appointmentId }: { appointmentId: string }) {
  const [state, action, pending] = useActionState(addVisitNote, null);

  return (
    <form action={action} className="mt-3">
      <input type="hidden" name="appointmentId" value={appointmentId} />
      <textarea
        name="body"
        rows={2}
        required
        maxLength={5000}
        placeholder="Post-op instructions the patient will see in the app…"
        className="w-full resize-y rounded-[14px] border border-hairline bg-white p-3.5 text-[13.5px] text-navy placeholder:text-muted/70 focus:border-aqua/50 focus:outline-none focus:ring-4 focus:ring-aqua/10"
      />
      <div className="mt-2 flex items-center gap-3">
        <button
          type="submit"
          disabled={pending}
          className="btn-aqua rounded-full px-4 py-2 text-[13px] font-semibold transition-transform active:scale-[0.98] disabled:opacity-50"
        >
          {pending ? 'Saving…' : 'Add note'}
        </button>

useActionState(addVisitNote, null) 回傳三個東西：目前的狀態 state、可以直接掛到 <form action=…> 的 action、以及一個 pending 布林值。null 是初始狀態，也就是 _prev 第一次會收到的值，這就是為什麼動作的第一個參數是 _prev。

把 action 掛到表單上之後，送出表單就會自動呼叫那個 Server Action，而 pending 會在等待期間變成 true，拿來把按鈕變成「Saving…」並禁用，避免重複送出。狀態回來後，再依 state 顯示錯誤或「Saved」。這種「pending 由框架直接給你」的設計，少寫了很多手動的載入狀態。

順帶一提，因為這是一個真正的表單動作，即使 JavaScript 還沒載入完成，表單也能先送出、由伺服器處理，這就是所謂的「漸進式增強」。

第六步：不是表單的按鈕，用 useTransition

「標記完成」按鈕不是一個表單，它只是一個點擊。這種情況用 useTransition，它讓你能把「呼叫 server action」包在一段過渡狀態裡：

'use client';

import { useState, useTransition } from 'react';

import { completeAppointment } from './actions';

/** Marking a visit complete is what moves it into the patient's visit history. */
export function CompleteButton({ appointmentId }: { appointmentId: string }) {
  const [pending, start] = useTransition();
  const [error, setError] = useState<string | null>(null);

  return (
    <>
      {error && <span className="text-[12px] text-coral">{error}</span>}
      <button
        type="button"
        disabled={pending}
        onClick={() =>
          start(async () => {
            const result = await completeAppointment(appointmentId);
            setError(result.error ?? null);
          })
        }

useTransition 給你一個 start 函式與一個 pending。把它想成「我要開始一件會非同步完成的事，過程中請把 pending 設起來」。在 start 裡 await completeAppointment(...)，做法跟呼叫一般 async 函式沒兩樣，因為對前端而言，Server Action 就是一個回傳 Promise 的函式。

一個務必記住的警告

Server Action 讀起來像在呼叫本地函式，這件事太好用了，好用到很容易讓人忘記：它骨子裡仍是一個公開的 HTTP 端點。任何知道怎麼觸發它的人，都可能直接送出請求。所以絕對不能因為「這是我們自己頁面上的按鈕」就省掉 requireStaff()、Zod 驗證或稽核。把每個 Server Action 都當成一支陌生人在打的 API 來寫，這條紀律就不會出錯。

小結

Server Action 用 'use server' 把伺服器函式變成可從前端呼叫的端點，省掉 route 檔與 JSON 合約，但驗證、授權、稽核一樣都不能少。addVisitNote 與 completeAppointment 寫完 DB 後呼叫 revalidatePath，讓被改到的畫面重新查詢、重新渲染；哪個畫面變了就重繪哪個。client 端用 useActionState 接表單、用 useTransition 接按鈕，pending 與錯誤狀態都由框架幫你準備好。

走到這裡，你手上已經有了完整的員工後台資料流：Server Component 負責讀、Server Action 負責寫、守衛放在資源旁邊、PHI 的每一次讀取都留下紀錄。下次你要替自己的專案長出一個 admin 頁，就能判斷哪些資料該直讀、哪一塊該切 client、哪一步一定要稽核。
