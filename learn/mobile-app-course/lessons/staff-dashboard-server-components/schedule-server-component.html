今日行程 Server Component：typed params 與診所日查詢

Step 3/5 · 員工 Dashboard（Server Components）

學習目標

照著 dashboard 首頁的程式碼，用 async Server Component 讀取 typed searchParams、算出診所日時間窗，join 出當日行程並渲染成表格。

前言：把「今天」變成資料庫聽得懂的問題

經過前兩步，你已經知道 Server Component 可以直接查資料庫，也知道整個後台被 layout 的守衛好好包住。現在要動手做第一個真正的畫面：今日行程。看起來只是「列出今天的預約」，但要讓它正確，需要先回答一串很具體的問題：今天是指哪一個時區的今天？使用者按「前一天」時，參數從哪裡來？一筆預約要顯示病人、牙醫師、療程，怎麼在一次查詢裡湊齊？

這個步驟的成品，是一個打開 /dashboard 就能看到當日所有預約的頁面：上方三格統計、下方一張表格，還有「前一天／今天／後一天」的切換。前置條件是你已經走過前兩步，並且對 Drizzle 的 select、innerJoin 有基本認識。動手前先把目標記住：全程不寫任何 API，資料直接從 Postgres 到畫面。

第一步：宣告一個 async 的頁面元件

export default async function DashboardPage({ searchParams }: PageProps<'/dashboard'>) {
  await requireStaff();

頁面元件的型別寫成 PageProps<'/dashboard'>，這是 Next.js 針對每個路由自動產生的型別。它的好處是：searchParams 這個 prop 的形狀由路由本身推導，你打錯欄位名稱時編輯器會直接報錯，不必自己維護一份介面。函式前面的 async 是關鍵——它讓你在元件裡直接 await，把「查資料」寫成看似同步的一行。第一行仍然先 requireStaff()，守衛永遠在最前面。

第二步：等 searchParams，決定要看哪一天

  const params = await searchParams;
  const dateParam = typeof params.date === 'string' ? params.date : undefined;
  const day = dateParam ? parseDay(dateParam) : clinicDayOf(new Date());

在新版的 Next.js 裡，searchParams 是一個 Promise，所以要先 await 再讀。這裡的 date 查詢參數是網址上的 ?date=YYYY-MM-DD，也就是「切換日期」按鈕傳進來的值；如果沒有帶，就退回「診所當地的今天」。

要注意 parseDay 回傳的不是一個 Date，而是一個 { year, month, day } 的結構。為什麼不直接用 new Date('2026-10-02')？因為那個寫法會被當成 UTC 的午夜來解析，在時區偏移下常常變成「前一天」或「後一天」。把一天表示成純粹的日曆三欄，後續做加減與比較時就不會偷渡時區進來了。

第三步：把診所的一天換成時間窗

  const dayStart = clinicInstant(day, 0, 0);
  const dayEnd = new Date(dayStart.getTime() + 24 * 3600_000);

clinicInstant(day, 0, 0) 把「診所當地時區的某日 00:00」轉成一個真正的 UTC 時間點，這才是資料庫裡 starts_at 能比較的值。dayEnd 則是它的 24 小時之後。於是這一頁要查的區間，就是這個時間窗。

接下來的查詢用半開區間 gte(dayStart) && lt(dayEnd) 來表達「從當天午夜起、到隔天午夜前」。用 < 而不是 <=，可以避免剛好在午夜整點的那筆預約同時落進兩天，這是處理時間區間時很常見的小心機。

第四步：一次 join 出表格要的所有欄位

  const rows = await db
    .select({
      id: appointments.id,
      startsAt: appointments.startsAt,
      status: appointments.status,
      patientId: patients.id,
      firstName: patients.firstName,
      lastName: patients.lastName,
      dentist: dentists.displayName,
      service: services.name,
      isTeleconsult: services.isTeleconsult,
    })
    .from(appointments)
    .innerJoin(patients, eq(patients.id, appointments.patientId))
    .innerJoin(dentists, eq(dentists.id, appointments.dentistId))
    .innerJoin(services, eq(services.id, appointments.serviceId))
    .where(and(gte(appointments.startsAt, dayStart), lt(appointments.startsAt, dayEnd)))
    .orderBy(asc(appointments.startsAt), asc(dentists.displayName));

這一段有三個設計點值得記住。第一，只選需要的欄位：表格要顯示什麼，select 就列什麼，不必把整張預約表拉進來。第二，用 innerJoin：每一筆預約必定屬於一位病人、一位牙醫師、一項療程，這三個關聯是資料庫保證存在的，所以用 innerJoin 是對的；如果是「可能沒有」的關聯，才需要用 leftJoin。第三，排序先按開始時間、再按牙醫師名字，讓同一時段的預約有穩定順序，畫面不會每次重新整理就跳來跳去。

第五步：從同一批資料算出統計數字

  const dentistCount = new Set(rows.map((r) => r.dentist)).size;
  const teleconsults = rows.filter((r) => r.isTeleconsult).length;

上方的三格統計不需要再查一次資料庫——它們全部可以從已經拿到的 rows 現算。牙醫師人數用 Set 去重，因為同一位牙醫師今天可能有多筆預約；視訊門診數則直接篩選。能在記憶體裡用幾行算完的東西，就不要多打一次資料庫。

第六步：日期切換按鈕

  const shift = (days: number) => {
    const d = new Date(Date.UTC(day.year, day.month - 1, day.day));
    d.setUTCDate(d.getUTCDate() + days);
    return `/dashboard?date=${d.toISOString().slice(0, 10)}`;
  };

「前一天」與「後一天」其實只是連結，指向帶了不同 date 參數的同一個頁面。這裡刻意用 UTC 來做加減，因為 day 本身是沒有時區的日曆三欄；用 UTC 運算可以確保加一天就是日曆上的下一天，不會被本地時區的日光節約時間干擾。最後 toISOString().slice(0, 10) 取出的 YYYY-MM-DD，正好就是 parseDay 讀得懂的格式，形成一個閉環。

第七步：渲染成統計格與表格

拿到的 rows 會被畫成三格 StatTile（預約數、牙醫師數、視訊數），下面接一張表格。表格的幾欄各有對應的格式化：開始時間用 formatClinicTime 轉成診所當地的時鐘時間；病人姓名做成連結，指到 /dashboard/patients/<id>；牙醫師欄位帶一個小頭像；狀態欄則用 StatusPill。

狀態欄有一個小分支：如果這筆預約是視訊門診、而且狀態還是已預約，就顯示成 video 這個狀態；否則顯示資料庫裡真正的狀態。這類「顯示用的衍生值」放在伺服器端算，能讓前端只要負責畫，不必自己重新判斷業務規則。若當天沒有任何預約，則改顯示一個空狀態，而不是一張空表格。

做完長什麼樣

打開 /dashboard，你會看到今天的日期標題、三格統計與當日預約表；點「前一天／後一天」會換日、點「Today」回到今天，全部都由同一個 Server Component 依查詢參數重新查詢、重新渲染。整個過程沒有出現任何 API 端點——資料從 Postgres 直接進到 HTML。這一步的目的是把「怎麼查、怎麼組」，為什麼要這樣分工則回到第一步的觀念。

小結

今日行程頁示範了一個 async Server Component 的基本功：用 typed PageProps 讀 searchParams、把診所日換成 UTC 半開時間窗，再用 innerJoin 與 gte／lt 一次撈出病人、牙醫師、療程與狀態，並用同一批 rows 現算統計。日期切換只是帶不同 date 參數的同一個頁面，全程不經 API。

行程表會連到病患頁，所以下一步要往資料的另一端走：病患名冊的聚合查詢，以及單一病患病歷頁要怎麼只讀「這一位」的資料，還留下稽核紀錄。
