今日行程 Server Component：typed params 與診所日查詢

Step 3/5 · 員工 Dashboard（Server Components）

學習目標

能照著寫出一個讀 searchParams、把診所當地的一天換成 UTC 時間窗、再用 join 撈出當天行程的 Server Component。

動手前：你會得到什麼

做完這一節，你會有一個完整的今日行程頁：網址上帶著日期（/dashboard?date=2026-10-03），頁面顯示那一天的每一筆預約，附上「前一天／今天／後一天」的切換，以及三格統計數字。你要先具備的，是上一節那個已經被守衛保護好的 /dashboard，以及對 Drizzle 基本查詢的認識。

這一節的主角是「怎麼做」，所以會按著真實程式碼的順序走。每一段我都會說清楚它在做什麼，以及你應該看到什麼結果。

第一步：先守衛，再讀網址參數

頁面的函式一開頭，先做兩件事：確認身分，然後把網址上的查詢字串讀出來。這個世代 Next.js 的頁面 props 是非同步的，所以 searchParams 要用 await 拿。

export default async function DashboardPage({ searchParams }: PageProps<'/dashboard'>) {
  await requireStaff();

  const params = await searchParams;
  const dateParam = typeof params.date === 'string' ? params.date : undefined;
  const day = dateParam ? parseDay(dateParam) : clinicDayOf(new Date());

這裡的型別 PageProps<'/dashboard'> 是這個 Next 版本提供的頁面 props 型別，它知道這個路徑的參數長什麼樣，所以你在裡面打錯欄位名稱編譯器會直接抱怨。另一個重點是那個 typeof ... === 'string' 的檢查：searchParams 的每個值可能是字串、字串陣列，或根本不存在。先把它收斂成「字串或 undefined」，後面的邏輯才不會被奇怪的型別偷襲。

如果網址沒有帶日期，就預設今天是診所當地的今天。注意，這裡用的是 clinicDayOf(new Date())，而不是隨便 new Date() 之後切字串。原因等一下會講。

第二步：把「診所的一天」變成一個日曆結構

parseDay() 與 clinicDayOf() 回傳的不是 JavaScript 的 Date，而是一個 CalendarDay：一個只有 { year, month, day } 三個欄位的結構。這是一個刻意的設計。

用 new Date('2026-10-03') 這種寫法處理日期，是個經典的坑：它會被當成 UTC 午夜來解讀，於是在診所當地時區把日期印出來，可能已經變成前一天或後一天。CalendarDay 把「一個日曆上的日子」和「時間軸上的一個瞬間」徹底分開：日子就是日子，沒有時區，也就不會不小心被換算。clinicInstant() 才是真的把某一天、某個時刻的牆上時間，換算成真正的 UTC 瞬間。

第三步：建出當天的 UTC 時間窗

有了 day，接著要把「診所當地的一天」變成資料庫查得懂的範圍：

const dayStart = clinicInstant(day, 0, 0);
const dayEnd = new Date(dayStart.getTime() + 24 * 3600_000);

clinicInstant(day, 0, 0) 把「這一天的 00:00（診所當地時間）」轉成 UTC 的瞬間。因為診所有日光節約時間，這一步不能自己用手算，得交給那層專門處理時區的程式（這正是先前預約領域節點裡 time.ts 的職責）。而 dayEnd 是起點加 24 小時。

你可能會想：日光節約時間那天不是 23 或 25 小時嗎？這裡刻意用「加 24 小時」而不是「隔天同一時刻」，是因為這個查詢要的是連續的 24 小時窗口。查詢用了半開區間：startsAt >= dayStart 且 startsAt < dayEnd。左邊包含、右邊不包含，所以剛好落在下一日 00:00 的預約不會被重複算進今天，也不會被漏掉。

第四步：join 出當天的行程

接著是核心查詢。它從 appointments 出發，沿途接到病人、牙醫、服務三張表：

const rows = await db
  .select({
    id: appointments.id,
    startsAt: appointments.startsAt,
    status: appointments.status,
    patientId: patients.id,
    firstName: patients.firstName,
    lastName: patients.lastName,
    dentist: dentists.displayName,
    dentistPhoto: dentists.photoUrl,
    service: services.name,
    isTeleconsult: services.isTeleconsult,
  })
  .from(appointments)
  .innerJoin(patients, eq(patients.id, appointments.patientId))
  .innerJoin(dentists, eq(dentists.id, appointments.dentistId))
  .innerJoin(services, eq(services.id, appointments.serviceId))
  .where(and(gte(appointments.startsAt, dayStart), lt(appointments.startsAt, dayEnd)))
  .orderBy(asc(appointments.startsAt), asc(dentists.displayName));

幾個值得留意的選擇。第一，select 裡只挑畫面真正要用的欄位，而不是把整列撈回來：病歷可能很敏感，能少碰就少碰。第二，三個 join 都是 innerJoin：一筆預約一定屬於某位病人、某位牙醫、某項服務，這是由外鍵保證的，所以用 inner join 不會有錯，也不需要處理「找不到關聯」的情況。第三，orderBy 先用時間、再按牙醫名字，這樣同一時段的預約會聚在一起、比較好讀。

執行完你應該看到：rows 就是當天所有預約的陣列，每一列都已經帶著病人姓名、牙醫、服務名稱，可以直接餵給 JSX 渲染。

第五步：算出「前一天／後一天」的連結

頁面上有切換日期的按鈕，它們的網址是怎麼算出來的？靠一個小函式：

const shift = (days: number) => {
  const d = new Date(Date.UTC(day.year, day.month - 1, day.day));
  d.setUTCDate(d.getUTCDate() + days);
  return `/dashboard?date=${d.toISOString().slice(0, 10)}`;
};

注意這裡用 Date.UTC 建構一個日期。這不是要把 CalendarDay 變成時間軸上的瞬間，而是把它借來當一個日曆計算機：在 UTC 的世界裡加減天數，不會有時區干擾，也不會碰到日光節約。day.month - 1 是因為 Date 的月份從 0 開始；toISOString().slice(0, 10) 則是把結果格式化成 YYYY-MM-DD。最後產出的就是像 /dashboard?date=2026-10-04 這樣的網址。

「今天」那一顆按鈕則直接連到 /dashboard，不帶日期，讓頁面回到預設值。

第六步：渲染統計與表格

最後把資料鋪上畫面。上方三格統計數字，分別是預約數、當天有排班的牙醫數、以及視訊門診數：

const dentistCount = new Set(rows.map((r) => r.dentist)).size;
const teleconsults = rows.filter((r) => r.isTeleconsult).length;

牙醫數是用 Set 去掉重複的名字算出來的，而不是再多跑一次資料庫查詢，資料都已經在 rows 裡了，在記憶體裡算就好。表格的每一列則顯示時間、病人（連到病歷頁的連結）、服務、牙醫、狀態。

狀態欄有個小細節：如果這筆預約是視訊門診、而且還沒看診（booked），就顯示成 video 這個狀態：

<StatusPill status={r.isTeleconsult && r.status === 'booked' ? 'video' : r.status} />

這種「把某個組合條件對應到一個顯示狀態」的判斷，放在伺服器端做，用戶端就只需要把結果畫出來，不必再懂業務規則。

小結

今日行程頁的骨架是：先 requireStaff()，再 await searchParams 讀日期；把日期解析成 CalendarDay，用 clinicInstant 建出當天 00:00 到 +24 小時的 UTC 半開區間；從 appointments 對病人、牙醫、服務做三個 innerJoin，用 gte／lt 過濾後按時間排序；切換日期的網址則靠 UTC 日期加減天數算出來。所有查詢都直接在伺服器完成，型別一路帶進 JSX。

「今天有哪些預約」解決了，但櫃檯常常要問的是更深一層的問題：這位病人過去看過幾次？他的病歷、過往的術後筆記、上傳的 X 光片在哪？下一節要處理的是聚合查詢，以及一個更嚴肅的課題：病歷屬於高度敏感資料，每一次讀取都必須留下紀錄。
