病患名冊與病歷頁：聚合查詢與 PHI 讀取紀錄

Step 4/5 · 員工 Dashboard（Server Components）

學習目標

能用 count() 加 groupBy 做出看診次數聚合，並把筆記與附件嚴格鎖在該病患身上、每次讀取都寫一筆 audit。

動手前：這一節多了一個不能妥協的條件

前三節處理的是「怎麼把資料正確地查出來」。這一節要查的是同一批資料裡最敏感的部分：病人的病歷、過往的術後筆記、以及他們上傳的 X 光片。這些都屬於 PHI（Protected Health Information，受保護的健康資訊）。

所以除了寫出查詢，這一節還要同時守住兩條紀律：只讀這個病人自己的資料，不要讓別人的病歷不小心被載進記憶體；以及不管誰讀了病歷，都留下一筆稽核紀錄。做完你會有兩頁：一頁是全院病患名冊，一頁是單一病患的病歷頁。

第一頁：病患名冊，連「讀一眼」都要記

名冊頁要顯示每位病人的姓名、生日、電話、看診次數與上次看診日。它開頭先做兩件事，確認你是員工，然後把這次讀取寫進稽核表：

export default async function PatientsPage() {
  const staff = await requireStaff();

  // A roster read is still a read of the patients table.
  await audit(staff.id, 'read', 'patients', null);

注意註解那句話：「讀一份名冊，仍然是一次對 patients 資料表的讀取。」很多系統只在「打開某個人的病歷」時才記稽核，覺得「只是看一眼列表」沒什麼。但名冊本身就已經包含病人的姓名、生日與電話，這些都是 PHI。既然讀了，就要留下誰在什麼時候讀過的痕跡。

requireStaff() 這次回傳的不是隨便一個使用者，而是那位員工的資料列，因為稽核需要記下「是誰」讀的。audit() 收到的參數是：誰（staff.id）、做了什麼（'read'）、碰了哪張表（'patients'）、以及哪一筆（這裡整份名冊，所以是 null）。稽核只記識別碼，不記內容。紀錄本身不該變成另一份病歷外洩。

聚合查詢：count 加 groupBy 算出看診次數

名冊最麻煩的欄位是「看診次數」，因為它不在 patients 表裡，而是得從 appointments 數出來。做法是聚合：

const rows = await db
  .select({
    id: patients.id,
    firstName: patients.firstName,
    lastName: patients.lastName,
    dateOfBirth: patients.dateOfBirth,
    phone: patients.phone,
    isSelf: patients.isSelf,
    lastVisitAt: patients.lastVisitAt,
    accountEmail: users.email,
    visits: count(appointments.id),
  })
  .from(patients)
  .innerJoin(users, eq(users.id, patients.accountUserId))
  .leftJoin(appointments, eq(appointments.patientId, patients.id))
  .groupBy(patients.id, users.email)
  .orderBy(asc(patients.lastName), asc(patients.firstName));

這裡有兩個關鍵。第一個是 count(appointments.id)，搭配 groupBy，把「同一位病人的所有預約」壓成一列，並算出數量。如果少了 groupBy，資料庫會不知道要拿什麼分組，查詢就不合法。

第二個是 join 的選擇：接 users 用 innerJoin，因為每位病人一定屬於某個帳號；但接 appointments 用 leftJoin，因為有些病人可能一次都還沒看診。用 left join，沒有預約的病人仍會出現在名冊上，次數顯示為 0；若用 inner join，這些人就整個消失了。

還要留意 groupBy 裡放的是 patients.id 與 users.email，而不是照抄 select 的所有欄位。標準 SQL 要求：select 裡非聚合的欄位，都得是分組依據。因為 patients.id 是主鍵，同一 id 的其他欄位必然唯一，所以資料庫允許這樣寫。你不需要去記這條規則的每個細節，只要知道「非聚合欄位要能被分組涵蓋」就好。

第一頁的渲染：名冊表格與住戶統計

查完後，頁面把 rows 鋪成一張表，依賴者（!isSelf）多加一個「Dependent」標籤。上方的三格統計也順手從資料裡算出來，例如住戶數就是把不重複的帳號 email 放進 Set 再取大小。這些都只是把已經查回來的資料做點整理，不需要再打一次資料庫。

第二頁：單一病患病歷，把資料鎖在這個人身上

點進名冊上的名字，會進到病歷頁。這一頁的路由帶了病人 id（/dashboard/patients/[id]），開頭先守衛、再讀出 id，然後把病人本人找出來：

export default async function PatientPage({ params }: PageProps<'/dashboard/patients/[id]'>) {
  const staff = await requireStaff();
  const { id } = await params;

  const [patient] = await db.select().from(patients).where(eq(patients.id, id));
  if (!patient) notFound();

  // The account the patient belongs to — staff need a way to reach the family.
  const [account] = await db.select().from(users).where(eq(users.id, patient.accountUserId));

兩個新東西。第一，params 也是非同步的，要用 await 拿；型別 PageProps<'/dashboard/patients/[id]'> 會知道裡面有個 id。第二，找不到這位病人時直接 notFound()，讓框架回一個標準的 404 頁面。這比回一個半殘的空頁面清楚，也不會讓錯誤繼續往下傳。

讀病歷，就要留紀錄

拿到病人之後，緊接著是這一節最重要的紀律：記下兩筆稽核。一筆是讀取病人基本資料，一筆是讀取醫療史：

// HIPAA posture: a staff read of a patient record and their medical history
// is auditable, and this is the path that makes it so.
await audit(staff.id, 'read', 'patients', patient.id);
await audit(staff.id, 'read', 'medical_histories', patient.id);

為什麼要分成兩筆？因為這是兩種不同等級的敏感度。medical_histories 是整個 schema 裡所謂「THE PHI table」：過敏、用藥、慢性病、是否懷孕、焦慮程度，全都在這張表。名冊頁的稽核只知道「有人看了病患清單」，而這裡的兩筆則明確記下「某位員工看了某一位病人的醫療史」。日後要追查「誰看過這位病人的病歷」，靠的就是這一條路徑。

把筆記與附件鎖在這個病人身上

病歷頁還要顯示每次看診的術後筆記，以及病人事先上傳的 X 光片、處方或轉診單。這兩類資料都存在各自的表裡，但都只透過 appointmentId 跟預約關聯，而預約又屬於病人。所以查詢時要「以這位病人的預約 id 為範圍」：

// Scoped to THIS patient's appointments — an unscoped select here would pull
// every patient's post-op notes into memory.
const notes = visits.length
  ? await db
      .select()
      .from(visitNotes)
      .where(inArray(visitNotes.appointmentId, visits.map((v) => v.id)))
      .orderBy(desc(visitNotes.createdAt))
  : [];
const notesFor = (appointmentId: string) => notes.filter((n) => n.appointmentId === appointmentId);

那個 where(inArray(...)) 就是這道鎖。如果偷懶寫成 db.select().from(visitNotes) 不做範圍限制，資料庫會把全院所有病人的術後筆記通通撈進這台伺服器的記憶體，然後你在程式裡才把不要的濾掉。但傷害已經造成：資料離開了它該在的範圍。正確的做法是讓「只屬於這位病人」成為查詢條件本身，根本不要把別人的資料載進來。前面那個 visits.length ? ... : [] 也很重要：沒有預約時 inArray 會拿到空陣列，不如直接回空陣列，避免產生沒有意義的查詢。

附件用的是同一種範圍鎖：

// What the patient sent ahead of the visit — X-rays, prescriptions, referral
// letters. Scoped to this patient's appointments for the same reason as the
// notes above. URLs are signed here and expire; the files are private.
const files = visits.length
  ? await db
      .select()
      .from(appointmentAttachments)
      .where(inArray(appointmentAttachments.appointmentId, visits.map((v) => v.id)))
  : [];
const filesFor = (appointmentId: string) =>
  files
    .filter((f) => f.appointmentId === appointmentId)
    .map((f) => ({ id: f.id, ...signedAttachment(f.path) }));

還有一個容易忽略的安全設計：檔案本身是私有的，不能直接給一個固定網址。所以每一次讀取時，才用 signedAttachment(f.path) 現簽一組「會過期」的網址。這樣就算某個連結不小心被外流，它也活不了多久。附件的資料範圍與筆記完全一樣，只限這位病人的預約。

執行到這裡你應該看到：病歷頁上只有這一位病人的醫療史、時間軸、筆記與縮圖，而且每一次重新整理，稽核表就會多一筆紀錄。

小結

名冊頁用 count(appointments.id) 加 groupBy 算出每位病人的看診次數，並用 leftJoin 保住零預約的病人；連「看名冊」都寫一筆稽核。病歷頁用兩個稽核（patients 與 medical_histories）留下誰讀了誰的病歷，並把筆記與附件用 inArray 嚴格鎖在此病人的預約 id 上，附件再現簽一組會過期的私有網址。安全不是多加一道檢查，而是讓「只看該看的」變成查詢條件本身。

讀取的路徑到這裡就完整了。但員工後台不可能只讀不寫：看診完要留下衛教筆記、要把預約標記為完成。這些寫入過去得各寫一支 API，下一節要示範一種更直接的做法：Server Action，寫完資料、跑一下 revalidatePath，畫面就自動帶著新資料更新。
