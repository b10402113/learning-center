Dashboard 外殼與守衛：把 requireStaff 放在資料旁邊

Step 2/5 · 員工 Dashboard（Server Components）

學習目標

說明為什麼 dashboard 的權限守衛放在 layout 這種「資源旁邊」，而不是放進 proxy 做路徑比對，以及未登入與非員工兩種情況各自怎麼被處理。

前言：看到「Staff access only」不是壞掉

你登入了後台，卻看到一頁寫著「Staff access only」，底下還附一句話，要管理員去 Clerk 後台把角色的 public metadata 設成 {"role":"staff"}。第一次遇到的人常以為是程式壞了，其實這正是守衛在正常工作——系統認得你，但不認為你有員工身分，所以只讓你看到一頁說明，而不是病人資料。

守衛做得對不對，差別很大：做得太鬆，一個普通使用者就能看到全診所的病歷；做得太散，每個頁面各檢查一次，遲早有人漏掉一頁。Dentify 的選擇是把守衛集中在一個地方，而且放在「資料旁邊」。這一節要解釋那個選擇背後的理由。

守衛能放在哪三個地方

在 Next.js 裡，擋下未授權存取至少有三個落點，各有各的個性：

位置它看得到什麼適不適合當後台守衛
proxy（前身是 middleware）只看到請求的路徑與標頭適合做全站通用的登入態注入
layout路徑、且能在同一層取用資料與角色適合守住一整個後台子樹
每個 page 自己該頁的完整上下文必要，但不能當成唯一防線

proxy 的問題是：它只知道「你正在拜訪 /dashboard」，卻不知道「你是不是這家診所的員工」這種跟資源綁在一起的事。它比較像門口的警衛，認得你有沒有掛識別證，但認不得你有沒有權限進某一間辦公室。資源層級的判斷——這個角色能不能看病人資料——應該跟資源放在一起。

為什麼是 layout：一次守住整棵子樹

app/dashboard/layout.tsx 這個檔案，是 /dashboard 底下所有頁面的共同外框。Next.js 會用它把子頁面包起來，所以只要在這個 layout 裡檢查一次，整個後台子樹——行程、名冊、病歷頁——就都被涵蓋。這是一個「守住一個範圍」而不是「守住一條路徑」的做法，也因此它與被保護的資料處在同一個資料夾階層，讀程式碼時不會失聯。

export default async function DashboardLayout({ children }: LayoutProps<'/dashboard'>) {
  const { userId } = await auth();
  if (!userId) redirect('/');

  try {
    await requireStaff();
  } catch (err) {
    if (err instanceof ApiError && err.status === 403) return <NotStaff />;
    throw err;
  }

  return ( /* 側邊欄 + children */ );
}

這段程式碼把兩種失敗分開處理。第一種是根本沒登入：auth() 拿不到 userId，於是 redirect('/') 把他送回登入入口。第二種是登入了但不是員工：requireStaff() 會丟出一個狀態碼 403 的 ApiError，layout 攔下來，改渲染一頁 NotStaff 說明。其他非 403 的錯誤則被重新丟出去，交給上層的錯誤處理——不要順手把真正的系統錯誤吞掉。

為什麼每個 page 還要再檢查一次

看到這裡，你可能會想：layout 都守好了，裡面的 page 還需要再呼叫一次 requireStaff() 嗎？答案是需要。原因是 Next.js 在伺服器上渲染時，layout 與 page 是平行處理的，page 不能假設「layout 的守衛一定已經先跑完」。如果某個 page 只依賴外層守衛，就有機會在守衛完成之前先執行了查詢。最保險、也最不容易出錯的寫法，是每個會碰病人資料的 page 自己再確認一次身分——守衛多寫一次的成本很低，漏掉一次的代價卻是一筆資料外洩。

NotStaff 這一頁在做什麼

NotStaff 不是冷冰冰的「403 Forbidden」，而是一頁帶著指示的說明。它告訴使用者：這個帳號不是員工；管理員可以在 Clerk 的 public metadata 裡設定角色來開通。課程裡特別提醒了一個很容易踩的語法陷阱：在 Clerk 後台填的是 JSON，所以要用冒號 "role": "staff"，不是等號 role = staff。填錯格式，守衛就會一直把你擋在門外，而你會以為程式有問題。

外殼本身：側邊欄與登出

守衛之外，layout 還負責整個後台的一致外觀。它渲染一條固定在左側的側邊欄，放上品牌標誌、導覽選單、登出按鈕與使用者頭像。導覽選單 SidebarNav 需要知道「現在在哪一頁」才能把當前項目highlight起來，而判斷當前路徑要用到瀏覽器的 usePathname，所以它是一個標了 'use client' 的 Client Component；layout 與 children 其餘部分則維持在伺服器端。側邊欄在窄螢幕上預設隱藏，只有夠寬的畫面才以 lg:flex 展開——這是純版面考量，跟權限無關。

角色是從哪裡來的

「是不是員工」這個判斷，主要來自 Clerk 的使用者 public metadata。不過資料庫裡也有一份鏡射的使用者資料，而 webhook 同步可能有延遲，所以判斷當下資料庫那份可能還落後。Dentify 的 requireStaff() 因此兩邊都看：Clerk metadata 說是員工就放行，資料庫那份也一樣被信任，藉此吸收同步的延遲。這個「同一個事實有兩個來源、要能容忍短暫不一致」的模式，在後端整合裡很常見。

小結

後台的守衛放在 dashboard/layout.tsx，因為它一次包住整個 /dashboard 子樹，又和資料處在同一層。未登入者被 redirect('/') 送走；已登入但非員工者看到 NotStaff 說明。因為 layout 與 page 平行渲染，每個 page 仍要自己再 requireStaff() 一次。角色主要來自 Clerk public metadata，但判斷會同時容忍資料庫那份可能的延遲。
