Dashboard 外殼與守衛：把 requireStaff 放在資料旁邊

Step 2/5 · 員工 Dashboard（Server Components）

學習目標

能解釋 dashboard 的守衛為什麼放在 layout 而不是 proxy，並說出未登入與登入但非員工兩種情況各自會發生什麼。

前言：能直讀資料庫的頁面，怎麼可能不危險

上一節我們確認了：員工 dashboard 因為跟資料庫同機，可以直接查詢、不用繞 API。這個結論很方便，但也馬上帶來一個令人不安的疑問：如果這個頁面隨手就能撈出全診所的病歷，那豈不是任何知道網址的人都能看？

不會，前提是你把守衛放在對的地方。「能直讀」講的是技術上做不做得到；「誰能進來」講的是權限，是兩件不同的事。這一節要處理的就是後者：一個前端頁面，該在哪一層檢查「你是不是員工」？放錯地方，不是漏守，就是把規則寫得到處都是、改都改不動。

先看一個很直覺、但會被淘汰的做法：路徑比對

大多數人第一個想到的，是在請求進入頁面之前就攔下來，做法是在 proxy（舊版 Next.js 叫 middleware）裡比對路徑，寫成「凡是 /dashboard 開頭的請求都要登入」。這個思路聽起來很合理，而且有一段時間確實是官方推薦的寫法。

但它有個結構性的缺點：它把「規則」和「被保護的資源」硬生生拆到兩份檔案裡。你在 proxy 裡寫了一行路徑比對，卻得跳到另一個很遠的資料夾才知道那個路徑底下到底放了什麼。哪天有人把頁面搬到別的路徑，這條比對就默默失效了；而它失效的方式是「不再擋人」，不是「報錯」，所以你不會立刻發現。更別說新版的 Next.js 已經把這種用路徑比對的寫法視為過時，方向轉向所謂的「以資源為基礎」的守衛。

Dentify 的選擇：守衛跟資料住在一起

Dentify 把守衛放在 dashboard/layout.tsx。這個檔案的註解一句話就把理由講完了：「dashboard 的守衛放在這裡，而不是 proxy.ts：一個以資源為基礎的檢查，就放在它保護的資料旁邊。」

/**
 * The dashboard's guard lives here rather than in proxy.ts — a resource-based
 * check, next to the data it protects.
 */
export default async function DashboardLayout({ children }: LayoutProps<'/dashboard'>) {
  const { userId } = await auth();
  if (!userId) redirect('/');

  try {
    await requireStaff();
  } catch (err) {
    if (err instanceof ApiError && err.status === 403) return <NotStaff />;
    throw err;
  }

為什麼放在 layout 特別有效？因為在 App Router 裡，layout.tsx 包住了整個 /dashboard 子樹。無論使用者開的是今日行程、病患名冊，還是某一位病人的病歷頁，都一定會先經過這個 layout。於是一次檢查，就守住了底下所有子頁面，不需要每一頁各自記得檢查，也不會有人漏掉。

這就是「守衛跟資料放在一起」的價值。你打開這個檔案，看到的不是一條抽象的路徑規則，而是「任何要進入這個後台的請求，都必須先過這一關」的完整意圖。要改規則時，也只有這一個地方要改。

兩種失敗，兩種處理

仔細看上面那段程式，它其實處理了兩種截然不同的情況。

第一種是根本沒登入。auth() 拿不到 userId，於是 redirect('/')，把使用者送回首頁。這是「你是誰」的問題：連身分都沒有，沒什麼好說的，請先登入。

第二種是有登入，但不是員工。requireStaff() 會丟出一個狀態 403 的 ApiError；這裡把它接住，然後不是丟錯、也不是轉址，而是直接渲染一個 <NotStaff /> 頁面。這是「你能做什麼」的問題：身分確認過了，只是權限不足。

為什麼第二種要特別畫一個頁面，而不是一概轉回首頁或丟錯？因為登入但沒有權限的人是真實存在的人，而且他的問題是可以解決的：可能是剛到職的牙醫助理，管理員還沒把他的角色設好。如果你把他默默轉回首頁，他只會覺得莫名其妙：「我明明登入了，怎麼又被踢出來？」丟一個 500 更是糟糕，他完全不知道下一步該做什麼。給他一個講清楚原因的頁面，才是把人當人看。

那個頁面寫得很直白，直接告訴他怎麼取得權限：

<h1 className="mt-4 text-[26px] font-bold tracking-tight text-navy">Staff access only</h1>
<p className="mt-3 text-[15px] leading-relaxed text-muted">
  This account is not a staff member. An admin can grant access by setting{' '}
  <code className="rounded bg-powder px-1.5 py-0.5 text-[13px] text-aqua-ink">
    {'{ "role": "staff" }'}
  </code>{' '}
  in the user's public metadata in the Clerk dashboard.
</p>

它告訴使用者：管理員只要在 Clerk 的 public metadata 裡加上 {'{ "role": "staff" }'}，你的權限就會生效。把「為什麼被擋」和「怎麼解決」放在同一個畫面，比任何錯誤代碼都更有用。

重複守衛：頁面自己再檢查一次

還有一個耐人尋味的細節。上一節看到的今日行程頁，除了 layout 的守衛之外，自己的函式裡又 await requireStaff() 了一次。看起來像是多餘，但這是刻意的「縱深防禦」。

理由是：頁面不應該假設自己一定是被 layout 包住的。也許未來有人把某個頁面搬到別的 layout 底下，或在某個測試情境裡單獨渲染它。如果安全只依賴「它剛好被某個 layout 包住」，那這個保證其實很脆弱。讓每個需要保護的頁面自己再確認一次，成本只有一行，卻能讓安全不依賴外部的巧合。

外殼本身：側邊欄與登出

layout 做的事情不只有守衛。它同時畫出了整個後台的「外殼」：左側那條固定不動的側邊欄、SidebarNav 導覽、以及底部的登出按鈕與使用者頭像（Clerk 的 SignOutButton 與 UserButton）。子頁面透過 {children} 被放進右邊的主內容區。

把導覽與登出放在 layout，跟守衛放在 layout 是同一個道理：它們都是「所有子頁面共享」的東西，寫一次就好。切換頁面時，外殼不會重新繪製，只有中間的內容改變，這對使用體驗來說也比較穩定。

小結

Server Component 直讀資料庫不代表它公開，反而因為它站在資料旁邊，最適合把守衛放在同一層。Dentify 把 requireStaff() 放在 dashboard/layout.tsx，用一次檢查守住整個子樹，也讓規則與它保護的資料待在一起。未登入的人被 redirect('/') 請出去；登入但不是員工的人看到一段 <NotStaff /> 說明，告訴管理員去 Clerk 補上 {'{ "role": "staff" }'}。頁面自己再檢查一次，是刻意的縱深防禦。

到目前為止，我們有了資料路徑的判斷，也有了守衛。接下來可以真的動手做頁面了。下一節要用這個底座寫出第一頁，也就是今日行程：讀取網址上的日期、把診所當地的一天換成正確的 UTC 時間窗，再用 join 撈出當天的每一筆預約。
