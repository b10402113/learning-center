路由保護要放在哪裡：matcher 還是資料旁邊

Step 5/5 · Monorepo 與 Next.js 後端骨架

學習目標

用一套判準決定路由保護要寫在 proxy 的 matcher 還是資料旁邊的 resource-based guard，並說明 Clerk Core 3 為什麼放棄 createRouteMatcher。

前言：身分已經認出來了，那誰來擋人？

上一節的 proxy.ts 解決了「你是誰」的問題：它透過 clerkMiddleware 把每個請求的身分脈絡準備好，讓後面的程式碼讀得到 userId。但知道你是誰，不等於知道你能進哪裡。病人和診所員工都是合法的登入者，可是病人不該看到全診所的排班，也不能讀別人的病歷。

於是問題來了：這些「誰可以看什麼」的判斷，到底要寫在哪裡？傳統做法是在 proxy 裡用路徑比對，例如「凡是 /dashboard 開頭的都擋起來」。Dentify 卻反其道而行，把守衛全部搬到資料旁邊。這個選擇不是隨口決定的，有它想過的取捨。這一節要把兩個選項攤開來比較，讓你以後遇到類似情境時，知道怎麼選。

兩個選項：在門口比對路徑，還是貼著資料檢查

第一種做法叫 path-based（以路徑為準）。你在 proxy 裡定義一份「受保護路徑」的清單，請求進來時比對網址，符合就要求登入或特定角色。它通常搭配 Clerk 舊版的 createRouteMatcher，寫起來很直覺：把 /dashboard(.*) 這種樣式列出來就好。

第二種做法叫 resource-based（以資源為準），也就是 Dentify 採用的方式。守衛不放在門口，而是放在真正需要它的地方：需要檢查角色的地方呼叫 requireStaff()，需要檢查登入的地方呼叫 requireAuth()，需要確認「這筆病歷是不是你的」的地方呼叫 requireOwnedPatient()。每個守衛都緊貼著它保護的那筆資料。

兩者的根本差別在「判斷的對象」。網址是一串字，而資料是一筆真實存在的紀錄。當你要回答的問題是「這個人能不能讀這份病歷」，答案不在網址裡，而在那筆病歷的擁有者是誰。用網址去推論資料層級的權限，等於多隔了一層猜測。

為什麼 Clerk Core 3 放棄 createRouteMatcher

Dentify 的 proxy.ts 註解把理由寫得很直接：createRouteMatcher 被 deprecated，改用 resource-based 檢查，因為路徑比對可能和 Next 實際的路由結果不一致，而這種不一致會讓某個受保護的資源被摸到。

 * This does no route matching on purpose. Clerk Core 3 deprecated
 * `createRouteMatcher` in favour of resource-based checks, because path
 * matching can diverge from how Next actually routes and leave a protected
 * resource reachable. So every guard lives next to the data it protects:
 * `requireStaff()` in the dashboard layout, `requireAuth()` in each API route.

「路徑比對可能和實際路由不一致」聽起來抽象，但後果很具體。你寫的比對規則是一種「我以為 Next 會這樣路由」的猜測；只要有一條路徑的實際解析和你的正規表達式不同，那道門就形同虛設，而你不會收到任何錯誤訊息。安全機制最怕的就是「看起來有裝，其實沒裝」。把守衛貼在資料旁邊，就不需要猜路由。不管請求從哪條路徑進來，要動到那筆資料，就一定得通過那道守衛。

判別問句：三個問題幫你決定守衛放哪

面對一個新的保護需求，先問自己這三個問題，答案會直接指向做法。

  1. 這個守衛要判斷的是「網址」還是「一筆資料」？如果答案是資料（這份病歷、這個預約、這則訊息），那它必須放在碰得到那筆資料的地方，也就是 route 或 layout 裡，因為只有那裡才讀得到資料。
  2. 如果不看網址，這個判斷做得出來嗎？角色（是不是員工）與登入狀態可以不靠網址；擁有權（這筆資料是不是你的）更是只能靠資料。只有「整區都要登入」這種規則，才勉強可以靠路徑。
  3. 如果 Next 明天改變路由方式，這個守衛還對嗎？如果你的保護會因此失效，那它就不該只依賴路徑。

在 Dentify 裡，這三個問題的答案分別把守衛推向了不同的位置。員工後台的門檻是角色，於是 requireStaff() 放在 app/dashboard/layout.tsx：那個 layout 是整個後台區塊的共同入口，放一次就能擋住底下所有頁面。

而「這筆病患資料是不是你的」這種擁有權問題，就被收斂到單一一個守衛 requireOwnedPatient()。任何帶有 patientId 的路由都經過它，所以這條規則只實作一次，不會有某支端點忘了檢查。

export async function requireOwnedPatient(user: AppUser, patientId: string) {
  const [patient] = await db
    .select()
    .from(patients)
    .where(and(eq(patients.id, patientId), eq(patients.accountUserId, user.id)));
  if (!patient) throw notFound('Patient not found');
  return patient;
}

反例：這條規則什麼時候會翻轉

「一律用 resource-based」不是無條件成立的鐵律，有幾種情況會讓你重新考慮。

第一種是連資料都還不存在的入口。例如一個全新的使用者第一次打 API，資料庫裡根本沒有他的 row；requireAuth() 這時不是去比對網址，而是先確認登入、再順手把使用者的資料補上（Dentify 的 ensureUser() 就是做這件事）。這裡的重點仍然是「以狀態為準」，而不是「以路徑為準」。

第二種是公開頁面。首頁、隱私政策、服務條款本來就不需要登入，也不該被任何守衛攔住。如果你用路徑式的「全部都要登入」再開白名單，很容易在新增公開頁面時忘了放行，反而製造 bug。Dentify 把公開頁面放進 (site) 群組、後台放進 dashboard，讓「需要守衛」這件事自然地跟著資料夾走，而不是靠一份容易過期的清單。

第三種是角色可能來自多個來源。員工角色的判斷，理論上以 Clerk 的 publicMetadata 為準，但資料庫的鏡射 row 可能因為同步延遲而落後。Dentify 的 requireStaff() 選擇「兩邊任一邊說是員工就算」，寧可暫時放行也不要誤擋，這是實務上的取捨。這種邏輯放在守衛裡可以寫清楚，塞進 proxy 的路徑比對則無處安放。

小結：一句話的決策規則

先用一個問題分類：這個守衛要判斷的是「一筆資料」還是「一個網址」？是資料，就放它旁邊；是範圍性的登入門檻，就放共同的 layout。proxy 只負責辨識身分，不負責決定放行；任何需要看資料才能下的判斷，都不要寫在 matcher 裡。

把這條規則帶著走，你以後不管是接 Clerk、Auth.js 還是自製的驗證，都不會再糾結「守衛到底該放 middleware 還是 route」。你也會發現，這個節點走完的其實是一個更通用的後端骨架：一個 repo 放兩個 app、一個 Next.js 部署同時當網站與 API、一道在正確位置把關的保護層。接下來，這套骨架就可以開始長出真正的功能：預約、病歷、聊天。每一支 API 都會沿用你在這裡學到的守衛紀律。
