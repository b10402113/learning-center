路由保護要放在哪裡：matcher 還是資料旁邊

Step 5/5 · Monorepo 與 Next.js 後端骨架

學習目標

能用判準決定路由保護該寫在 proxy 的 matcher 還是 resource-based guard（requireStaff／requireAuth），並說出為什麼 Clerk Core 3 放棄 createRouteMatcher。

前言：同一道鎖，要裝在大門還是房門？

上一節我們讓 proxy.ts 負責辨識身分，但它不做授權。於是一個很自然的問題就來了：那「只有員工能進 /dashboard」、「只有登入的人能打這支 API」這種規則，到底要寫在哪裡？

這個選擇之所以值得停下來想，是因為兩條路看起來都能達到目的，但失手的後果完全不同。一條是把規則集中寫進 proxy 的路徑 matcher，像在大門貼一張名單；另一條是寫在每一段資料存取旁邊，像每個房間自己上鎖。選錯了，你不會馬上發現——直到某天有人繞過大門，走進了一間你以為鎖著的房間。這一節要把兩股張力攤開，給你一套當場能用的判準。

兩個選項長什麼樣子

選項 A：proxy 路徑 matcher。在 proxy.ts 裡用一段樣式比對網址，例如「凡是 /dashboard 開頭的請求，沒登入就攔下來」。舊版 Clerk 就是用 createRouteMatcher(['/dashboard(.*)']) 搭配 auth.protect() 做這件事。

選項 B：resource-based guard。把守衛寫在你「真正要動那筆資料」的地方旁邊：後台的 layout 裡呼叫 requireStaff()，每一支 API route 裡呼叫 requireAuth()。也就是說，存取資料的路徑上一定會先經過守衛。

比較點proxy 路徑 matcher資料旁的 guard
放在哪集中在 proxy.ts 一個檔案貼在每個 layout／route 的資料存取旁
守的是什麼一串 URL 樣式你真正要拿的那個資源
能不能判斷角色／擁有權很難，它只看得到網址能，資料就在手邊
失手的方式樣式與實際路由分岔，資源變成可達（門戶大開）新路由忘了加守衛（但可靠設計讓它必經）
怎麼測偏整合，要整條請求跑起來可單元測試，貼著函式測

為什麼 Core 3 放棄 createRouteMatcher

Clerk Core 3 把 createRouteMatcher 淘汰了，理由正是上表第三、第四列。路徑 matcher 用的是字串比對，但 Next.js 有 route group、動態段、layout、rewrite，最後實際被路由到的位置，未必長得跟你比對的字串一樣。只要兩邊一分岔，你以為鎖上的資源就可能有人走得到。這種「規則寫在 A，實際路由在 B」的落差，是路徑比對天生的弱點，不是設定沒調好。

所以 Dentify 的 proxy.ts 把職責縮到最小：只附掛身分。真正的把關，交給每一段資料自己的守衛。

三個判別問句

面對一個新的保護需求，先問自己這三題：

  1. 這個判斷需要知道「角色」或「擁有權」嗎？例如「他是不是員工」、「這筆預約是不是他的」。需要 → 一定放資料旁邊；proxy 看不到這些。只問「有沒有登入」→ proxy 也許能勝任。
  2. 被保護的東西，用網址就認得出來，還是要先把資料撈出來才知道？如果得先讀到那筆資料才能判斷能不能給，那守衛自然要跟在那筆資料旁邊。
  3. 明天多一條 API 路由時，哪種設計會「忘了就破功」？如果忘了加 matcher 的後果是資源直接可達，那就是一個危險的預設；要讓系統在忘記時「進不去」，而不是「全部都給你」。

反例：matcher 也不是完全不能用

這條規則會翻轉的地方在於「用途」。proxy 的 matcher 不是不能用，而是不能拿它當安全邊界。它適合做兩種事：

  • 純 UX 轉址：讓沒登入的人從後台被導去登入頁，體驗順一點。這只是禮貌，不是鎖——真正的鎖還在資料旁。
  • 便宜地擋掉明顯匿名的流量：在請求一進來就擋掉大量沒帶 token 的呼叫，省後端資源。同樣地，它不能取代授權判斷。

反過來，也不是每個路由都需要守衛。像官網首頁、隱私政策、服務條款這種本來就要給所有人看的頁面，硬加一道登入反而擋掉了潛在客戶。守衛要加在「有東西要保護」的地方，不是加好加滿。

小結

授權判斷（角色、擁有權）一律放在資料旁邊的 resource-based guard，例如後台 layout 的 requireStaff()、每支 API route 的 requireAuth()。proxy 的 matcher 只拿來做 UX 轉址或擋匿名流量，不當安全邊界。Core 3 放棄 createRouteMatcher，就是因為路徑比對可能和實際路由分岔而漏掉保護。判斷時問三件事：需要角色嗎？要撈資料才知道嗎？忘了加會 fail open 還是 fail closed？
