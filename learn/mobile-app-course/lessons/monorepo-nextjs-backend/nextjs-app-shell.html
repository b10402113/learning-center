Next.js App Router 外殼：一個部署，三種身分

Step 3/5 · Monorepo 與 Next.js 後端骨架

學習目標

能讀懂 App Router 的檔案慣例（layout、page、route handler），說出 root layout 用 ClerkProvider 包住整棵樹的意義，以及一個 Next.js 部署如何同時扮演 dashboard、API 與 webhook。

前言：一個資料夾，怎麼同時當網站和後端？

上一節我們把兩個 app 擺好了，也證明了 npm run web 真的能啟動 Next.js。但你可能還沒細看：這個 apps/web 明明只有一份程式碼，為什麼可以既給員工看網頁、又回答手機 app 的資料請求、還要收 Clerk 打進來的 webhook？

答案藏在它採用的 App Router。它把「路由」這件傳統上要另外設定的東西，直接變成資料夾結構：你開一個資料夾，就等於開一段網址；你在資料夾裡放什麼檔名的檔案，就決定那個位置是「給人看的頁面」還是「回資料的端點」。這一節要把 app/ 底下的規則讀懂，因為後面無論是後台、API 還是 webhook，都是照同一套規則長出來的。

App Router 的四種關鍵檔案

Next.js 的 App Router 用檔案名稱決定這個檔案的角色。你只要記住底下幾種：

檔案角色回傳什麼
layout.tsx包住某一段路徑的外殼，可以巢狀共用版型（HTML 骨架、Provider）
page.tsx某段網址的畫面給人看的 HTML
route.tsHTTP 端點（Route Handler）給程式呼叫的資料
(資料夾)route group，只是分類，不影響網址例如 (site) 放官網、放隱私政策

最外層的那個 layout.tsx 稱為 root layout，它負責整棵樹最底層的框架：裡面的 <html> 與 <body> 標籤就是從這裡出來的。路徑更深的 layout 會一層一層被包進去，所以共用版型只要寫一次。

Root layout：把 Provider 掛在整棵樹的最外層

打開 apps/web/src/app/layout.tsx，內容很短，但每一個 import 都有意思：

import { ClerkProvider } from '@clerk/nextjs';
import type { Metadata } from 'next';

import './globals.css';

export const metadata: Metadata = {
  title: 'DentaCare — Staff Dashboard',
  description: 'Schedule, patient records and post-op notes for the clinic.',
};

export default function RootLayout({ children }: LayoutProps<'/'>) {
  return (
    <html lang="en">
      <body className="antialiased">
        <ClerkProvider>{children}</ClerkProvider>
      </body>
    </html>
  );
}

逐一拆開看。metadata 是這個頁面的靜態詮釋資料，會變成 HTML 的 <title> 與描述。globals.css 是整站共用的樣式。而 RootLayout 這個函式回傳的，就是每個頁面都會套用的最外層結構。

最關鍵的是 <ClerkProvider> 把 {children} 整個包住。意思是：不管下面哪一個頁面、哪一個 server component 被渲染，它都在 Clerk 的身分環境裡。這是「登入狀態」能一路傳到最底層頁面的原因。你可以把 root layout 想成診所大樓的一樓大廳：所有要進到不同房間的人，都得先經過這裡，而 ClerkProvider 就是大廳櫃台，先確認你是誰，再把身分帶進後面的每一個房間。

附帶一提，layout 預設是 Server Component，也就是它在伺服器上渲染，不會把多餘的程式碼送到瀏覽器。像掛 Provider、讀 metadata 這種不需要互動的事，放在這裡最自然。

page 與 route handler：給人看 vs 給程式用

同樣在 app/ 底下，page.tsx 和 route.ts 是兩種不同的出口。page.tsx 產出的是畫面——員工打開 /dashboard 看到的病人清單，就是某個 page.tsx。route.ts 產出的則是資料，它匯出 GET、POST 這些函式，對應到不同的 HTTP 方法：

// apps/web/src/app/api/appointments/route.ts
export async function GET() {
  // 回傳預約清單給呼叫端
}

export async function POST() {
  // 建立一筆新預約
}

注意：page.tsx 是給「人」用的，它回傳的是 HTML；route.ts 是給「程式」用的，手機 app 就是打這一種。兩者都住在 app/ 底下、共用同一套路由規則，只差在檔名決定它是畫面還是端點。

三種身分怎麼對應到資料夾

把上一節講的三個身分，對回來看資料夾就一目了然了：

  • 員工後台 → app/dashboard/... 底下的 page.tsx。
  • 手機呼叫的 API → app/api/... 底下的 route.ts，例如預約、可預約時段、目前使用者、AI 助理。
  • Webhook 接收端 → app/api/webhooks/clerk/route.ts，等 Clerk 主動打進來。

它們全部在一個 Next.js 專案裡，所以只需要部署一次。建置設定也在這裡，例如 next.config.ts 會把 Sentry 的設定包進 Next 的設定裡。這也是為什麼「一個部署、一份 schema」說得通：後台和 API 是同一個程式，改動一起上線，不會有其中一邊落後。

一個容易踩的坑：這不是你想像的 Next.js

Dentify 用的是 Next.js 16，這個版本和很多人的訓練資料、或網路上舊教學裡的版本並不一致。連 layout 的型別都變了——範例裡的 LayoutProps<'/'> 就是新版的寫法。所以這個 repo 的 apps/web/AGENTS.md 開頭就寫著：動手寫任何程式碼之前，先讀這個版本隨附的官方文件，不要憑記憶。版本會動，記憶會過期，文件才是準的。

小結

Next.js 的 App Router 用檔名決定角色：layout.tsx 是外殼、page.tsx 是畫面、route.ts 是端點、括號資料夾只是分類。root layout 是最外層，用 ClerkProvider 包住整棵樹，讓每個頁面都拿得到登入狀態。後台、API 與 webhook 都只是 app/ 底下不同的檔案，因此共用同一個部署。這個版本的 Next.js 與舊教學不同，動手前先讀版本對應的文件。
