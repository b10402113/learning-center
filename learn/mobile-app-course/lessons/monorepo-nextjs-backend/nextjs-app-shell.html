Next.js App Router 外殼：一個部署，三種身分

Step 3/5 · Monorepo 與 Next.js 後端骨架

學習目標

讀懂 layout、page、route 三種檔案的慣例，以及 root layout 為什麼要用 ClerkProvider 包住整棵樹。

前言：同一個 app，要同時當網站、後台和 API

上一節我們把 apps/web 建起來了，但它現在還只是一團「Next.js 專案」。打開它的 src/app/ 資料夾，你會看到一堆檔名：layout.tsx、page.tsx，某些資料夾底下還有 route.ts。同一個資料夾結構裡，卻要同時長出三種截然不同的東西：給一般訪客看的首頁與隱私政策、給診所員工用的病歷後台、以及給手機 app 呼叫的 API。

這一節要講的，就是 Next.js 的 App Router 如何用「資料夾與檔名」這套約定，把這三種身分放進同一個部署。搞懂之後，你看任何一個 Next.js 專案，只要看檔案樹就知道哪些網址會存在、哪些是頁面、哪些是端點。而這一切的最外層，是一個用 ClerkProvider 包住整棵樹的 root layout，它也是後面談身分驗證的地基。

資料夾就是網址，檔名決定角色

App Router 的核心規則只有一句：src/app/ 底下的資料夾對應網址的一段，資料夾裡的特殊檔名決定這個網址是什麼。例如 app/dashboard/page.tsx 對應 /dashboard，app/dashboard/patients/page.tsx 對應 /dashboard/patients。你不需要另外寫一份路由表，檔案放在哪裡，網址就長在哪裡。

三種最常出現的特殊檔名各有明確的角色，差別在「它產生的是畫面還是資料」。page.tsx 是一個網址的主要畫面；layout.tsx 是包住這個網址與其子網址的外框，而且切換頁面時它不會重新渲染；route.ts 則不是畫面，它是一個 HTTP 端點，用 export const GET、POST 這種方式回應請求。同一個資料夾可以有 page，也可以有 route，但不能兩者同時存在，因為它們會搶同一個網址。

檔名它產生什麼Dentify 的例子
page.tsx一個網址的畫面app/(site)/page.tsx 是行銷首頁；app/dashboard/page.tsx 是今日排班
layout.tsx包住子畫面的外框，切換時保留app/layout.tsx 提供 <html> 與 ClerkProvider；app/dashboard/layout.tsx 提供側邊欄與身分守衛
route.ts一個 HTTP 端點app/api/me/route.ts 讓手機拿到自己的身分與角色

這裡有個容易混淆的地方：page.tsx 和 route.ts 都是「某個網址的處理者」，差別在它們回傳的東西。頁面回傳的是要被渲染的 UI，端點回傳的是資料（通常是 JSON）。手機 app 不會去渲染你的 React 畫面，它只會打端點拿 JSON，所以給手機用的東西一律寫成 route.ts。

root layout：整棵樹最外層的那一層

網頁身分的最外層是 app/layout.tsx。它很特別，是唯一被要求一定要回傳 <html> 和 <body> 的 layout，因為它是整棵畫面的根。打開 Dentify 的 root layout，可以看到它做了三件事：匯入全域樣式、匯出 metadata（讓瀏覽器分頁標題顯示 DentaCare），以及把 {children} 包在 ClerkProvider 裡。

import { ClerkProvider } from '@clerk/nextjs';
import type { Metadata } from 'next';

import './globals.css';

export const metadata: Metadata = {
  title: 'DentaCare — Staff Dashboard',
  description: 'Schedule, patient records and post-op notes for the clinic.',
};

export default function RootLayout({ children }: LayoutProps<'/'>) {
  return (
    <html lang="en">
      <body className="antialiased">
        <ClerkProvider>{children}</ClerkProvider>
      </body>
    </html>
  );
}

為什麼是包在這一層？因為 ClerkProvider 決定的是「這個請求是誰送出的」。把它放在根，等於告訴整個 app：不管你走到哪個頁面、哪個 layout，都可以用 Clerk 來判斷登入狀態。反過來說，如果你只把它包在 dashboard 裡，那公開首頁與 API 就拿不到這層脈絡。這正是後面 proxy.ts 與守衛能運作的前提：身分的來源必須先鋪在樹根。

另外注意 metadata 這個匯出。它不是元件，而是 Next.js 認得的特殊變數，用來描述這個頁面的標題與說明。你看不到它出現在畫面上，但它會進入 HTML 的 <head>，影響搜尋結果與瀏覽器分頁。

巢狀 layout：外框可以一層一層疊

layout.tsx 可以出現在任何資料夾，於是外框就能分層。最外層是 root layout，裡面的某個區塊可以再有自己的外框。Dentify 的公開網站就是一個例子：它把首頁、隱私政策、服務條款三個網址放進一個叫 (site) 的資料夾，並用一個 layout 幫它們加上共同的導覽列與頁尾。

import { SiteFooter, SiteNav } from '@/components/site-chrome';

export default function SiteLayout({ children }: LayoutProps<'/'>) {
  return (
    <div className="flex min-h-screen flex-col">
      <SiteNav />
      <div className="flex-1">{children}</div>
      <SiteFooter />
    </div>
  );
}

這裡出現一個很實用的慣例：資料夾名稱用括號包起來，叫做 route group（路由群組）。它的意思是「這是一個用來分類的外框，但括號本身不會變成網址的一段」。所以隱私政策的網址是 /privacy，不是 /site/privacy。(site) 幫你套用了共同的網站外框，卻沒有在網址上留下痕跡。

員工後台也是同樣的道理。app/dashboard/layout.tsx 提供固定的側邊欄、登出按鈕，並且在「這個 layout 自己」裡面呼叫 requireStaff() 來擋掉非員工。它不是靠網址比對來擋，而是在渲染這個區塊以前就先確認身分，這個設計選擇是下一節之後的重點。

一個部署，兩種讀資料的方式

到這裡，你可以用一句話描述 Dentify 的 web：它是同一個 Next.js 部署，裡面同時有公開網站、員工後台與手機 API。但有趣的是，這三種身分拿資料的方式並不完全一樣，這也解釋了為什麼要有 page 和 route 兩種檔案。

員工後台用的是 Server Component：page.tsx 直接在伺服器上執行，可以透過 Drizzle 直接查資料庫，中間不需要繞一趟 HTTP。因為後台和資料庫都在同一個伺服器裡，直接查最省事，也少一層網路延遲。而手機 app 不在這個伺服器裡，它只能透過網址講話，所以給手機用的資料一律寫成 app/api/ 底下的 route.ts，回傳 JSON。

可以想成同一棟大樓有兩個門：後台是員工走內部通道，直接進資料庫；手機是外送員，只能走大門的收發櫃檯（API）。兩個門後面是同一棟樓、同一份資料，但走法不同。

這也是為什麼 apps/web 明明只是一個 Next.js 專案，卻能同時扮演「網站」和「後端」。它不是把兩套系統硬塞在一起，而是同一個 App Router 用不同的檔案類型，服務不同的對象。

小結

App Router 用資料夾與檔名決定網址與角色：page.tsx 是畫面、layout.tsx 是可疊層的外框、route.ts 是 HTTP 端點。root layout 是唯一要有 <html>／<body> 的一層，並用 ClerkProvider 把身分脈絡鋪到整棵樹。route group 用括號分類卻不佔網址。後台用 Server Component 直接查資料庫，手機則透過 app/api 的端點拿 JSON：同一份資料，兩個門。

不過到目前為止，我們都假設「身分」是理所當然拿得到的。實際上，手機送來的請求帶著一張通行證（Bearer token），伺服器必須有辦法讀到它。下一節要看的就是讓每張通行證都被辨識的那個檔案：proxy.ts。
