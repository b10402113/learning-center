Monorepo 的形狀：為什麼一個 repo 裝兩個 app

Step 1/5 · Monorepo 與 Next.js 後端骨架

學習目標

能說出 apps/mobile 與 apps/web 各自負責什麼、為什麼 web 是唯一部署，以及為什麼商業邏輯一律留在 web。

前言：診所裡有兩種人，卻只能有一份事實

Dentify 這個 app 有兩種使用者。第一種是躺在沙發上滑手機的病人，他想預約週三下午的洗牙，順便看一下上次的術後注意事項。第二種是坐在診所櫃檯的員工，她要用桌機的後台看今天的排班、點開病人的病歷、補一筆術後叮嚀。

這兩種人用的介面完全不一樣：一個是手機上的 Expo app，一個是瀏覽器裡的網頁。但他們看的其實是同一份資料、同一套規則。如果病人剛取消的那個時段，後台沒有立刻空出來，員工就會把同一個時間排給另一個病人，等到有人到診所才發現重複預約。這種錯誤不是介面沒做好，而是兩個 app 各自記了一份事實。

這一節要處理的，就是這個最上層的形狀問題：這兩個 app 該怎麼放、誰說話算數、程式碼又要擺在哪裡。先把這個骨架想清楚，後面的預約、病歷、聊天才有地方可以長。

不是開兩個 repo，而是一個 repo 裡放兩個 app

最直覺的做法是把病人 app 和員工後台拆成兩個獨立的 repository，各自開發、各自部署。聽起來很乾淨，但實際上你會馬上撞到幾件事。第一，資料庫的 schema、API 的請求格式、預約時間的計算規則，兩邊都得各寫一份；只要有一邊改了欄位名稱而另一邊忘了跟上，型別檢查抓不到，因為它們在不同的專案裡。第二，你要在兩個地方分別跑測試、分別部署，還要祈禱兩邊的版本是對得上的。第三，當你請 AI agent 幫忙時，它每次只看得到半個系統。

所以 Dentify 選的是另一種形狀：一個 repository，裡面住著兩個應用程式。根目錄底下有一個 apps/ 資料夾，apps/mobile 放手機 app，apps/web 放網頁後端。它們共用同一個根目錄的 package.json、同一把版本鎖、同一組指令，也共用同一份資料庫 schema。這種「一個 repo 裝多個專案」的安排，一般叫做 monorepo（單一倉庫）。

{
  "name": "dental-app",
  "private": true,
  "workspaces": [
    "apps/*",
    "packages/*"
  ],
  …

這裡的關鍵字是 workspaces。它告訴 npm：「apps/ 底下的每個資料夾都是一個子專案，請把它們當成同一個大專案來管理。」至於它實際怎麼運作、根目錄那些指令怎麼寫，下一節會一步步帶你做；這一節先把「為什麼是這個形狀」講清楚。

apps/mobile 與 apps/web 各自負責什麼

apps/mobile 是給病人用的 Expo React Native 應用。它負責畫面與互動：登入、問卷式的 onboarding、四個主分頁、三步驟的預約流程、AI 助理、聊天與視訊通話。它也會呼叫後端的 API 拿資料，但它本身不決定規則，只是把伺服器回傳的東西畫出來。

apps/web 是 Next.js 專案，它同時扮演三個角色，這點最容易被忽略。

角色使用者做什麼
員工後台診所員工、牙醫師用瀏覽器看今日排班、病人名冊、病歷與術後筆記
手機的 APIExpo 病人 app提供預約、可預約時段、病患資料、AI 對話、Stream 憑證等端點
Webhook 接收端Clerk 等外部服務接收 user.created 這類事件，把身分同步進資料庫

這三個角色共用同一個部署、同一份 schema。你不需要為了 API 另外開一台伺服器，也不必為了後台再開一個專案；它們就是同一個 Next.js app 裡的不同路由。這種安排的好處很直接：資料庫連線只有一組、型別只有一份、網址也只有一個。apps/web 的定位，簡單講就是「一個部署，一個 schema」。

商業邏輯為什麼一律留在 web

既然有兩個 app，下一個問題就是：規則要寫在哪一邊？Dentify 的答案很明確：商業邏輯全部住在 apps/web，apps/mobile 只負責呈現 API 回傳的結果。

原因跟信任有關。手機 app 裝在使用者的裝置上，使用者可以拆開它、改它、假造請求。如果「這個預約能不能取消」是手機自己判斷的，那有心人只要改一下本機的判斷，就能取消一個早就超過期限的預約。所以這類判斷必須在伺服器端做：後端算出 canCancel、canJoin 這些欄位，連同預約資料一起回傳，手機只是照著顯示按鈕。同理，服務時長、通話房間的 id、某個病患是不是屬於這位使用者，全都由後端決定，client 傳來的值一律當成不可信的輸入。

把商業邏輯想成診所的櫃檯：病人可以在家用 app 填表，但最後蓋章生效的一定是櫃檯。手機是那張表，web 才是那顆章。

那 apps/mobile 還剩下什麼？它還是有很多事要做：本機的畫面狀態、導航、表單驗證（為了體驗，不是為了安全）、以及網路請求的封裝。它只是不持有規則。

共用程式碼放在哪裡：先別急著抽 package

看到這裡，你可能會想：既然兩邊都要用同一套型別，那是不是該開一個 packages/shared，把 Zod schema 放進去讓兩邊 import？這個想法不算錯，但 Dentify 的 v1 刻意沒有這樣做。目前 Zod schema 就放在 apps/web/src/lib/validation.ts，因為現在只有一個消費者（web 自己）。等手機真的需要 import 某個型別的那一天，再把它抽成 package；在那之前先抽，只會多一層建置與版本管理的負擔。

根目錄的 workspaces 雖然寫了 packages/*，但這個資料夾到目前為止是空的。它比較像是先預留好的車位，而不是非停不可。判斷的準則很簡單：有第二個消費者出現，才值得抽共用套件。

如果不用 npm workspaces，會發生什麼事

你可能也聽過 pnpm 或 Turborepo，會想說「monorepo 不是該配 pnpm 嗎」。在 Expo 專案裡，這件事有兩個很現實的坑。第一，Expo 的打包工具 Metro 無法解析 pnpm 那種以符號連結串起來的 node_modules；要用 pnpm 就得把它設成 hoisted 模式，而那正好丟掉 pnpm 主打嚴格依賴的最大好處。第二，這個專案只有兩個 app，還不需要 Turborepo 或 Nx 這種建置協調器。npm 本身就會 hoist 依賴、也已經裝在每台機器上，對這個規模來說是最省事的選擇。

所以這個 repo 的取捨是：用 npm workspaces，不用 pnpm，也不用 Turborepo。這不是「npm 最好」，而是「在這個只有兩個 app 的規模下，多引入一個工具換不到對應的好處」。

小結

Dentify 用一個 monorepo 裝兩個 app：apps/mobile 是病人用的 Expo app，只呈現畫面與資料；apps/web 是 Next.js，同時當員工後台、手機的 API、以及 webhook 接收端，一個部署、一個 schema。所有商業邏輯與安全判斷都留在 web，手機端的輸入一律不信任。共用程式碼不急著抽 package，等第二個消費者出現再說。這個形狀就是接下來所有功能的地基。

知道為什麼要長成這個形狀之後，下一個問題是：它實際上要怎麼擺？下一節會用 npm workspaces 動手，把 Expo app 移進 apps/mobile、建立 apps/web，並用根目錄的 scripts 一次啟動兩邊。
