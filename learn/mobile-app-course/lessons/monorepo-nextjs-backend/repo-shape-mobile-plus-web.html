Monorepo 的形狀：為什麼一個 repo 裝兩個 app

Step 1/5 · Monorepo 與 Next.js 後端骨架

學習目標

能說出 apps/mobile 與 apps/web 各自負責什麼、為什麼 web 要同時是 dashboard、API 與 webhook 的唯一部署，以及 business logic 為什麼集中在 web。

前言：一張病歷，兩種人要用

想像你正在做 Dentify 這個診所 app。手機上，病人用它預約看診、跟診所傳訊息；診所裡，員工登入一個網頁後台，看今天的排班、翻病歷、補上診後叮嚀。這兩個介面差別很大，一個是直式的手機畫面，一個是橫式的桌面後台，但它們回答的其實是同一組問題：同一位病人、同一段時間、同一份病歷。

最直覺的做法是開兩個專案：一個放手機 app，一個放網頁後台。但這樣做不用多久就會出事。後台定義「病人」有姓名、生日、電話三個欄位，手機 app 卻自己記成「病人有姓名和電話」；後台改了欄位，手機那邊不知道。同一條預約規則，你在兩個地方各寫一次，改了一個忘了另一個，兩邊就開始給出不同的答案。這一節要先把整個 repo 的形狀想清楚，因為後面所有程式碼都會蓋在這個形狀上。

一個 repo 裝兩個 app：monorepo

這個專案選的是 monorepo（單一倉庫）：一個 git repo 裡裝著不只一個應用程式。以 Dentify 來說，根目錄底下有一個 apps 資料夾，裡面住著兩個獨立的 app：

位置它是什麼誰在用
apps/mobileExpo（React Native）寫的手機 app病人
apps/webNext.js 寫的網頁，同時是後端 API診所員工，以及手機 app 背後的呼叫

右邊那格是這個形狀的關鍵：apps/web 不只是「員工用的網站」，它同時是整個系統的大腦。這是 monorepo 在這裡真正要解決的問題，而不只是把兩個資料夾放在一起而已。

apps/web 的三個身分

把 apps/web 打開，你會發現它一次扮演三個角色，而且只部署一次：

身分它是什麼例子
員工後台給人看的網頁排班表、病人清單、病歷頁面
手機要呼叫的 API回傳資料的端點預約、可預約時段、目前使用者、AI 助理
Webhook 接收端第三方服務主動打進來的端點Clerk 的 user.created 事件

為什麼要把三件事綁在同一個部署裡？因為它們讀的是同一份資料庫、同一份 schema、同一組環境變數。如果 API 是另一個獨立服務，手機和後台就可能對「一個預約有哪些欄位」有不同版本的理解。放在一起，改 schema 的人、寫 API 的人、畫後台的人，改到的是同一個 commit。這就是一句話：一個部署、一份 schema。

你可以把這個專案想成一間診所：病人走前門（手機 app），員工走側門（網頁後台），但兩扇門通往的櫃台後面是同一間病歷室。門有兩個，資料只有一份。

商業邏輯只能有一個家

有兩個入口，就會想問：規則寫在哪？答案是 business logic 一律留在 apps/web，手機 app 只負責把 API 回傳的內容畫出來。也就是說，手機 app 是一個「顯示器」，不是第二個真相來源。它不自己判斷這段時間能不能預約、不自己算價格、不自己決定誰能看哪筆資料；這些問題它都問 API。

為什麼要這麼嚴格？因為同一條規則如果手機和網頁各實作一次，就一定會有分岔的一天。假設「看診前 24 小時內不能取消」，手機端寫成 24 小時、網頁端寫成 48 小時，那病人和櫃台就會看到不同的答案，而且沒人知道哪個才對。把規則收在一個地方，任何入口都得到同一個答案。

那共用程式碼要不要抽成 package？

monorepo 常會附帶一個 packages/ 資料夾，用來放兩個 app 共用的型別或工具。但 Dentify 這裡刻意沒有建立 packages/shared，原因是「今天只有一個消費者」。手機還不需要匯入 web 的型別，所以先讓驗證用的 schema 留在 apps/web 裡就好；等到手機真的需要匯入一個共用型別的那一天，再把它升成 package。這是一個可以帶走的習慣：共用層要等真的有第二個使用者才抽，不要預先為了對稱而建。

小結

monorepo 把 apps/mobile（病人用）與 apps/web（員工後台 + API + webhook）放進同一個 repo。apps/web 的三個身分共用一個部署與一份 schema，所以手機和後台不可能對資料有不同版本的理解。商業邏輯集中在 web，手機只渲染 API 回傳的內容；共用 package 則等真的有第二個消費者再抽。
