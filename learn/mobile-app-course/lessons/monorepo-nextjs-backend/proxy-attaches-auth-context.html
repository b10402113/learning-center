proxy.ts：讓每個請求都帶著身分

Step 4/5 · Monorepo 與 Next.js 後端骨架

學習目標

解釋 clerkMiddleware 如何在每個請求上附掛 Clerk 的 auth context，讓 Route Handler 讀得到 Expo 帶來的 Bearer token，以及為什麼 proxy.ts 刻意不做 path matching。

前言：手機沒有瀏覽器，哪來的登入狀態？

上一節我們把 ClerkProvider 放在 root layout，讓整個 app 都拿得到身分脈絡。但那套機制的前提是「使用者在瀏覽器裡」。員工在瀏覽器登入診所後台時，Clerk 會把登入狀態放在 cookie 裡，之後每個請求都自動帶著它，伺服器一看就知道你是誰。

手機上的 Expo app 完全不是這樣。它沒有 cookie、不是由伺服器渲染的頁面，而且它跟你的 Next.js 專案是兩個獨立的程式。當病人打開 app，app 要打 GET /api/me 問「我是誰、我是不是已經完成 onboarding」，它靠的是在標頭裡夾一張通行證：Authorization: Bearer <session token>。問題是，你的 Route Handler 如果預設只看 cookie，就完全讀不到這張通行證，於是 auth() 回傳 null，所有請求都會被當成未登入。

這一節要講的 proxy.ts，就是負責在每個請求抵達終點前，先把這張通行證認出來、附上身分脈絡的那個檔案。

proxy.ts 是什麼：Next 16 對 middleware 的改名

在 Next.js 裡，有一個檔案會在「請求進來、但還沒被路由處理」的階段先執行，這種檔案過去叫 middleware.ts。Next 16 把它改名為 proxy.ts，行為不變，只是換了名字。課程裡講得很直白：這是一個你可以用來保護路由的檔案，而且大部分時候你不會親自去改它，需要調整時直接請 agent 處理就好。

它的位置在 apps/web/src/proxy.ts，內容短到第一次看到的人會懷疑它到底有沒有用。但這幾行正是手機能通過身分驗證的關鍵。

import { clerkMiddleware } from '@clerk/nextjs/server';

/**
 * Next 16 renamed `middleware.ts` to `proxy.ts`. Same behaviour, new filename.
 *
 * This does no route matching on purpose. Clerk Core 3 deprecated
 * `createRouteMatcher` in favour of resource-based checks, because path
 * matching can diverge from how Next actually routes and leave a protected
 * resource reachable. So every guard lives next to the data it protects:
 * `requireStaff()` in the dashboard layout, `requireAuth()` in each API route.
 *
 * What this still does — and why it must stay — is attach Clerk's auth context
 * to every request, which is what lets a Route Handler read the
 * `Authorization: Bearer <session token>` the Expo app sends (PLAN.md R9).
 */
export default clerkMiddleware();

export const config = {
  matcher: [
    '/((?!_next|[^?]*\\.(?:html?|css|js(?!on)|jpe?g|webp|png|gif|svg|ttf|woff2?|ico|csv|docx?|xlsx?|zip|webmanifest)).*)',
    '/(api|trpc)(.*)',
  ],
};

clerkMiddleware 做了什麼：把通行證變成身分脈絡

整份檔案最重要的那一行是 export default clerkMiddleware();。一個請求穿過 proxy 時，clerkMiddleware 會做這些事：檢查請求有沒有帶 Clerk 的登入憑證（瀏覽器是 cookie，手機是 Authorization: Bearer 標頭）、向 Clerk 驗證這張憑證、然後把驗證出來的使用者資訊附掛到這個請求的脈絡上。之後在同一個請求生命週期裡執行的 Route Handler，就可以用 auth() 拿到 userId 與 sessionClaims。

換句話說，clerkMiddleware 不決定「你能不能通過」，它只負責「把你身上的證件讀出來，翻譯成伺服器看得懂的格式」。真正決定放不放行的，是後面每一個端點裡的守衛。Dentify 的 requireAuth() 就寫得很清楚，註解直接點名：每個病人端點都從這裡開始，而它能接受 Expo 的 Bearer token，正是因為 clerkMiddleware 已經先處理過了。

/** Every patient-facing route starts here. Accepts the Expo Bearer token via clerkMiddleware. */
export async function requireAuth(): Promise<AppUser> {
  const { userId } = await auth();
  if (!userId) throw unauthorized();
  return ensureUser(userId);
}

這裡有一個很重要的分工：auth() 本身不會去讀 cookie 或標頭，它只是去拿「clerkMiddleware 已經放好的脈絡」。如果 proxy 沒有先跑，auth() 就會兩手空空。所以沒有 proxy 這幾行，整個 API 就認不出身分。

可以把 clerkMiddleware 想成大樓門口的警衛：他不會攔人，只會看每個進來的人的證件，然後在訪客單上蓋一個「這個人是誰」的章。真正決定你能進哪間辦公室的是各樓層的門禁。

config.matcher：哪些請求要經過 proxy

你可能會問：如果每個請求都要驗證，那載入圖片、CSS、JavaScript 這些靜態檔案時也要驗嗎？當然不用，那只是浪費。這就是 config.matcher 的工作：它是一份正規表達式清單，決定哪些路徑要送進 proxy。

這份 matcher 看起來很嚇人，其實邏輯只有兩條。第一條是一個「排除式」的模式：它比對幾乎所有路徑，但用 (?!...) 把 _next 這種 Next.js 內部路徑，以及結尾是 .css、.js、.png 等靜態附檔名的請求排除掉。第二條則是明確點名 /api 與 /trpc 底下的所有路徑，確保 API 一定經過驗證。

請求會經過 proxy 嗎為什麼
/dashboard會這是頁面，需要知道你是誰
/api/me會被第二條 matcher 明確納入
/_next/static/chunk.js不會排除式模式濾掉，靜態資源不需要身分
/logo.png不會有圖片附檔名，直接放行

你可以把 matcher 想成機場的安檢動線：托運行李不用排隊過海關，只有要進登機門的旅客才需要。它決定的是「誰需要被查驗」，而不是「查驗後能不能通過」。

它偏偏不做路由保護，為什麼？

看到這裡，最反直覺的一點是：這個檔案明明是「可以保護路由」的地方，但 Dentify 的 proxy 卻刻意不做任何路徑比對式的保護。註解裡寫得明白：Clerk Core 3 把 createRouteMatcher 標為 deprecated，改用「resource-based」的檢查，因為路徑比對可能和 Next 實際的路由結果不一致，反而讓某個受保護的資源被摸到。

所以這個檔案只保留它非做不可的事：附掛身分脈絡。至於「誰可以進哪裡」的判斷，全部交給守衛，放在資料旁邊。這個決定牽涉到取捨，也是下一節（這個節點最後一步）要展開的主題。現在你只要記住這個分工：proxy 管「你是誰」，守衛管「你能不能」。

小結

Next 16 把 middleware.ts 改名為 proxy.ts，行為不變。Dentify 的 proxy 只做一件事：用 clerkMiddleware() 把每個請求的登入憑證驗成身分脈絡，包含 Expo 手機送來的 Authorization: Bearer 標頭，好讓 Route Handler 裡的 auth() 讀得到。它靠 config.matcher 跳過靜態資源、納入 /api，但刻意不做路徑式的路由保護，因為那種比對可能與實際路由不一致。它負責辨識身分，不負責決定放行。

既然 proxy 只認身分、不擋人，那「誰能看 dashboard、誰能讀別人的病歷」到底寫在哪裡？下一節要比較兩種做法，並給出一套可以帶著走的判斷準則。
