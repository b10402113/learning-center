proxy.ts：讓每個請求都帶著身分

Step 4/5 · Monorepo 與 Next.js 後端骨架

學習目標

能解釋 Next 16 為何把 middleware.ts 改名為 proxy.ts、clerkMiddleware() 在請求上附掛了什麼，以及為什麼 Route Handler 讀得到 Expo 帶來的 Bearer token。

前言：門開著，但警衛怎麼知道你是誰？

上一節我們把 apps/web 的外殼組好了：頁面、API、webhook 都在 app/ 底下，而且 ClerkProvider 也掛在最外層。但外殼掛好不代表安全——現在的網頁和 API 其實是誰敲門都回應。員工後台不能隨便給人看，手機 app 打 API 時也得先表明身分，問題是：伺服器要怎麼在請求一進來的時候，就知道「來的人是誰」？

手機 app 跟瀏覽器不一樣，它不是靠瀏覽器自動帶上的 cookie，而是自己帶著一張 token 來敲門。如果伺服器沒有在門口先把這張 token 讀懂、驗證，後面的 API 根本無從判斷身分。這一節要看的 proxy.ts，就是站在門口處理這件事的那一層。

middleware 是什麼，又為什麼改名成 proxy

在 Next.js 裡，有一種函式會在請求「還沒到達目標路由」之前先跑，傳統上叫 middleware（中介層），檔案名稱是 middleware.ts。Next.js 16 把它改名為 proxy.ts。這是整個節點最容易讓人誤會的一點：它不是新功能、也不是新的架構，只是同一個東西換了檔名，行為完全一樣。

也因為這樣，如果你憑舊印象記著「要去改 middleware.ts」，在 Dentify 裡會找不到那個檔案——它現在叫 proxy.ts。

整份 proxy.ts 在做什麼

這個檔案很短，只有十幾行，但每一行都值得看：

import { clerkMiddleware } from '@clerk/nextjs/server';

export default clerkMiddleware();

export const config = {
  matcher: [
    '/((?!_next|[^?]*\\.(?:html?|css|js(?!on)|jpe?g|webp|png|gif|svg|ttf|woff2?|ico|csv|docx?|xlsx?|zip|webmanifest)).*)',
    '/(api|trpc)(.*)',
  ],
};

核心只有一行：export default clerkMiddleware()。這個函式做的事情是——在每一個符合條件的請求上，附掛 Clerk 的身分脈絡（auth context）。所謂的脈絡，就是一個「這個請求代表哪個使用者」的資訊包，掛上去之後，後面接手的程式才拿得到。檔案裡的註解講得很白：這是你之所以能在 Route Handler 裡讀到 Expo app 送來的 Authorization: Bearer <session token> 的原因。

matcher：哪些請求要走這道門

如果每個請求都跑一次這個檢查，那連圖片、字型、CSS 都要白白繞一圈。所以下面用 config.matcher 限定了範圍。兩條規則分別是：

  • 第一條是一段「排除法」的正則：除了 Next.js 內部的 _next 路徑，以及各種靜態檔（html、css、js、圖片、字型、ico、csv、zip……）之外，其餘都套用。
  • 第二條是明確把 /api 與 /trpc 開頭的請求也納進來——因為手機 app 打的正是 API，這些請求一定要經過身分附掛。

換句話說，matcher 決定的不是「誰可以通過」，而是「哪些請求要經過這一關」。它是一道篩選，不是一道判決。

它刻意不檢查路徑，只負責附掛身分

這是 proxy.ts 裡最重要、也最容易寫錯的觀念。舊版的 Clerk 讓你用 createRouteMatcher(['/dashboard(.*)']) 直接在 middleware 裡比對路徑、當場攔下沒登入的人。但 Dentify 這裡刻意不做任何路徑比對，原因有兩個：

  1. Clerk Core 3 已經淘汰了 createRouteMatcher 這種做法。
  2. 更根本的是，靠路徑字串比對來做保護並不可靠。Next.js 有 route group、動態段、layout、rewrite，路徑比對的字串很可能和實際路由長得不一樣；一旦兩者分岔，你以為鎖住的資源就可能被人走到。

所以這個檔案的職責被縮到最小：只把身分附掛上去。真正的把關（誰是員工、誰能看哪筆資料）交給每一個資源自己的守衛。這件事下一節會專門談，這裡先記住一句話：proxy 只辨識身分，不做授權。

打個比方：proxy.ts 像大樓門口的刷卡機，它讀你的識別證、發一張訪客證，讓你知道「你是誰」；但它不決定你能進哪幾個房間。每個房間門上還有自己的鎖，那才是真正的授權。

Bearer token 的完整旅程

把整個流程串起來，你會更清楚為什麼這一層非存在不可：

  1. 使用者在手機 app 上用 Clerk 登入。
  2. Clerk 發給 app 一張 session token。
  3. app 每次呼叫 API，都在標頭帶上 Authorization: Bearer <token>。
  4. 請求進到 Next.js 時，先經過 proxy.ts 的 clerkMiddleware()，token 被驗證、身分被附掛到請求上。
  5. Route Handler 接手，用 Clerk 提供的 auth() 取得「現在是誰在呼叫」，再決定要不要放行。

少了第 4 步，第 5 步的 auth() 就什麼都讀不到，手機端的每一次呼叫都會被當成匿名。這就是為什麼註解會說這個檔案「必須留著」。

小結

proxy.ts 是 Next 16 對 middleware.ts 的改名，行為不變。它用 clerkMiddleware() 在每個請求上附掛 Clerk 的身分脈絡，並用 config.matcher 排除靜態檔、納入 /api，決定哪些請求要經過。它刻意不做路徑比對，因為那不可靠、而且已被 Core 3 淘汰；它只辨識身分，授權留給資源自己的守衛。少了它，手機 app 帶來的 Bearer token 就沒人讀得到。

現在你知道 proxy 只會辨識身分，那真正的把關要寫在哪裡？在 proxy 的 matcher 裡？還是貼在資料旁邊？下一節要把這個選擇攤開來比，給出一套可操作的判準。
