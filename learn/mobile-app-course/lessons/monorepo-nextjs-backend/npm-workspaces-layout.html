用 npm workspaces 擺好 apps/mobile 與 apps/web

Step 2/5 · Monorepo 與 Next.js 後端骨架

學習目標

能把 Expo app 移進 apps/mobile、建立 apps/web，用根目錄的 npm workspaces 與 scripts 從根目錄啟動兩個 app，並說出 Expo 為何選 npm 而不是 pnpm。

前言：兩個 app，指令該從哪裡下？

上一節確定了形狀：一個 repo，apps/mobile 給病人用，apps/web 當後台加 API。現在問題很實際——你要怎麼讓這兩個 app 同時活著？總不能每次開發都開兩個終端機、各自 cd 進去、各自 npm install，然後還得記得哪個資料夾裝了哪些套件。這一節要做的就是把它們「擺好」，讓你在根目錄下一條指令就能啟動其中一個。

動手前先確認的前置條件

  • 你已經有一個用 Expo 建好、可以在模擬器跑起來的手機 app（上一節的前提）。
  • Node 版本至少 22，npm 已經裝好。
  • 目前的進度已經 commit 過一次。大搬家之前先留下一個乾淨的 git 快照，出錯才好回頭。

步驟一：把 Expo app 移進 apps/mobile

如果你還沒建，先在一個空資料夾用官方指令就地生成，並選最新的 SDK：

npx create-expo-app@latest .
# 選單出現時選最新 SDK（錄製當下是 57）

接著把整個 App 移進 apps/mobile，替未來的 apps/web 騰出位置。搬完之後，在 mobile 裡執行 reset 腳本，把範例畫面與示範樣式清掉，得到一個乾淨的起點：

mkdir -p apps
mv <剛剛生成的那些檔案> apps/mobile
cd apps/mobile
npm run reset-project

預期結果：apps/mobile 底下只剩 Expo 的專案骨架，沒有預設的 demo 分頁。

步驟二：在 apps/web 建立 Next.js 專案

後端與後台都住在 apps/web。用 Next.js 官方指令在該路徑生成，或在已經有 plan.md 的情況下，請 agent 照著 plan 建出這個資料夾。重點是它必須是一個獨立的 app，有自己的 package.json。

npx create-next-app@latest apps/web

步驟三：在根目錄宣告 workspaces

這一步是讓兩個 app 變成「同一個 npm 專案家庭」的關鍵。根目錄放一份 package.json，用 workspaces 告訴 npm，哪些資料夾裡的專案都算這個 repo 的一部分：

{
  "name": "dental-app",
  "private": true,
  "workspaces": [
    "apps/*",
    "packages/*"
  ],
  "engines": {
    "node": ">=22"
  }
}

apps/* 代表 apps 底下的每一個資料夾都是 workspace，所以 apps/mobile 與 apps/web 都會被認得；packages/* 先留著，是給未來共用套件的位置。注意 private 一定要是 true，這個根專案不會被發佈到 npm 上。

步驟四：用 -w 把指令接到根目錄

有了 workspaces，就可以在根目錄的 scripts 裡用 -w（workspace）指定要把指令轉發給哪個 app。這樣你人在根目錄，也能指揮任意一個子專案：

{
  "scripts": {
    "mobile": "npm run start -w apps/mobile",
    "web": "npm run dev -w apps/web",
    "test": "npm run test -w apps/web",
    "typecheck": "npm run typecheck --workspaces --if-present",
    "db:generate": "npm run db:generate -w apps/web",
    "db:migrate": "npm run db:migrate -w apps/web",
    "db:seed": "npm run db:seed -w apps/web"
  }
}

每一條都只是「進到某個 workspace、跑它自己 package.json 裡的 script」。以 db:generate 為例，它其實就是去 apps/web 跑 drizzle-kit generate，因為只有 web 管資料庫。反過來，typecheck 用的是 --workspaces --if-present，意思是「每一個 workspace 都跑，沒有這個 script 的就跳過」。

子專案自己的 scripts 長什麼樣

根目錄只是轉發，真正的指令定義在各自的 package.json。apps/web 大致是這樣：

{
  "name": "web",
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "typecheck": "tsc --noEmit",
    "db:generate": "drizzle-kit generate",
    "db:migrate": "drizzle-kit migrate"
  }
}

apps/mobile 則帶著 Expo 與 EAS 的指令：

{
  "name": "mobile",
  "scripts": {
    "start": "expo start",
    "ios": "expo run:ios",
    "android": "expo run:android",
    "build:ios": "npx eas-cli build --profile development --platform ios"
  }
}

步驟五：只在根目錄 npm install 一次

workspaces 的重點之一就是依賴統一安裝。你不需要分別進兩個資料夾各裝一次；在根目錄跑一次就好，npm 會把共用的套件提升到根目錄的 node_modules，並幫你把兩個 app 的依賴都裝齊。

npm install

這也代表根目錄的 .gitignore 要涵蓋兩個 app 會產生的東西，才不會把雜物 commit 進去：

node_modules/
.env
.expo/
.next/
dist/
apps/mobile/ios/
apps/mobile/android/
.DS_Store

步驟六：從根目錄啟動，開兩個終端機

擺好之後，日常開發就是兩個終端機、兩條指令：一條跑手機 app，一條跑 web 與 API。手機要拿資料時，web 必須開著，否則 API 沒人回應。

# 終端機 A
npm run mobile     # 啟動 Expo，按 i 開 iOS 模擬器

# 終端機 B
npm run web        # 啟動 Next.js，含後台與 API

預期結果：A 終端機跑起 Expo、模擬器出現你的 app；B 終端機跑起 Next.js、瀏覽器打開後台。兩邊都從根目錄一條指令搞定。

為什麼是 npm，不是 pnpm？

很多人會直覺想用 pnpm，因為它的 node_modules 佈局更嚴格、更省空間。但 Expo 的打包器 Metro 沒辦法解析 pnpm 那種符號連結的佈局，你得額外設定把連結改成「提升」版本，而那一步正好丟掉 pnpm 最大的優點。npm 原生就會提升依賴，而且你電腦裡本來就有，所以這個專案選 npm。也不需要 Turborepo 或 Nx 這類建置協調工具——只有兩個 app，還不到需要它們的規模。

小結

把 Expo app 放進 apps/mobile、Next.js 放進 apps/web，根目錄用 workspaces 認得它們，再用 -w 把常用指令接到根目錄。依賴只在根目錄 npm install 一次，日常就是兩個終端機跑 npm run mobile 與 npm run web。選 npm 是因為 Metro 對 pnpm 的連結佈局不友善，而不是 npm 比較潮。

骨架擺好了，兩個 app 也都能啟動。但 apps/web 這個 Next.js 專案到底是怎麼把「後台、API、webhook」三種身分裝進同一個資料夾的？下一節要打開 app/ 目錄，看懂它的檔案慣例與那層 ClerkProvider 外殼。
