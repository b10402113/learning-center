修完、驗證、合併

Step 5/5 · 大規模 PR 安全審查

這一節要完成什麼？

前面四節鋪完了整條線：知道規模會讓審查失效、認得七類安全問題、真的把 PR 開起來讓 CodeRabbit 掃過、也對每一則 finding 做了修或保留的判斷。現在，你手上有幾批「要修」的修正，以及一條已經推上 GitHub 的 web-and-api 分支。這一節要把這些修復套用、驗證，然後安全地合併回 master。

做完後你會得到：安全問題已被修掉、修正以第二個 commit 落在同一條分支上、PR 在確認可運作之後合併進主分支，而你本機的 master 是最新的。前置條件是前四節的產物都在——分支、PR、以及分好類的修正清單。

第一步：讓平行 session 各自修完一批

把「要修」的那堆依模組或檔案分組，開多個 agent session 同時處理。每個 session 拿到的是它自己那批的彙整 prompt，改動的範圍盡量不要和其他 session 重疊，避免之後合併時衝突。

# 概念示意：不同 session 負責不同模組
# session A → app/api/webhooks/*
# session B → app/api/appointments/*
# session C → lib/auth/*

如果兩個 session 非改到同一個檔案不可，就把它們排成先後，不要同時進行。分派前先看一眼每則問題落在哪個檔案，是避免這件事最省力的動作。

第二步：逐批檢查 diff，再 commit

session 改完不等於可以直接送出去。翻一下它改的 diff，確認內容真的對應到那則 finding，而且沒有順手改掉不相關的地方。

git diff

git add .
git commit -m "fix: 依安全審查修正授權與輸入驗證問題"
git push

這第二個 commit 會直接更新原本那個 PR——你不需要另開一個 PR。課程裡的流程就是：同一條分支、修正集中成第二個 commit、推回遠端，PR 自動更新。

第三步：合併前先驗證

合併是會改變主分支狀態的動作，而且不容易乾淨地退回。所以在按下 merge 之前，至少確認這幾件事：

  • PR 的變更清單與你的預期一致，沒有意外的檔案被帶進來。
  • 修正過的程式能跑——重新啟動 app，走一遍最關鍵的流程。
  • 你刻意保留的那些 finding（例如 masks: false）沒有在修正過程中被一起改掉。

課程中提到，修正完成、commit、push 之後，不需要特地等 CodeRabbit 再跑第二輪才能合併。因為這批修正本來就是針對它已經指出的問題；真正該做的驗證，是把程式實際跑起來確認行為正確。

第四步：合併 PR，切回 master 同步

確認無誤後，在 PR 頁面按下合併，把整條分支的成果併回 master。合併完成後，切回 master，把最新的內容拉下來，確保本機與遠端一致。

git checkout master
git pull

這一步常被忽略：如果只合併、不同步，你的本機還停留在舊版本，接著開新分支時就會從過時的起點出發。切回 master 並 pull 一次，是這個流程的收尾儀式。

第五步：合併後，在 master 上再確認一次

合併之後，切到 master 上把 app 再跑一次。重點是確認「合併這個動作本身」沒有帶來問題——例如兩批平行修正雖然各自正確，合在一起卻互相衝突。確認沒問題，這批上萬行的改動才算真正落地。

做完的結果：要修的 finding 已由平行 session 修完、以第二個 commit 落在同一條分支；驗證通過後 PR 合併回 master；本機 master 已同步；刻意保留的 finding 維持原狀。到這裡，一個上萬行的初始 PR 在安全把關後合併完成。

整套流程的道理，其實收束在最前面那一節：當改動大到人眼放棄，安全靠的不是更努力地看，而是一張好地圖（嚴重度排序、分類堆疊、安全清單）、加上你在關鍵處做的判斷、以及一個能重複套用的合併流程。把這三步固定下來，下次 AI 再一次生成整個後端時，你就有辦法把它安全地帶進主線。
