修完、驗證、合併

Step 5/5 · 大規模 PR 安全審查

學習目標

平行套用修復、二次 commit，驗證後合併回 master。

前言：把判斷變成真的改動

上一步你已經把 CodeRabbit 的 finding 分成兩堆：要修的和要保留的。現在要把「要修」的那堆，實際套用進程式碼，收成第二個 commit，驗證之後把這個 PR 合併回 master。

這一步的關鍵不是寫修復，而是「怎麼不排隊」。十幾則修復如果依序跑，你會坐在那裡等一輪又一輪；但如果你把它們拆成獨立的 session 同時進行，你只花一次「貼 prompt」的時間，它們卻並行完成。做完之後，PR 上會有兩個 commit：第一個是原始的一萬五千行，第二個是審查後的修復。動手前請確認：你已經決定好要修的清單與對應的修復 prompt，而且你還在同一個 branch 上。

第 1 步：平行套用修復

替每一則要修的問題開一個獨立的 agent session，各自貼上那則問題的修復 prompt。核心心法是：不要讓後面的修復等前面的修復跑完。作者在示範裡就是這樣做的：把每一則 prompt 分別貼進不同的 session，讓它們同時運行。下面這個結構只是節奏示意，實際請依你手上那幾則 finding 的內容替換：

Session A：貼上 finding #1 的修復 prompt
Session B：貼上 finding #2 的修復 prompt
Session C：貼上 finding #3 的修復 prompt
...其餘要修的問題以此類推

這樣做的另一個好處是隔離。每一則修復只動它該動的地方，若某一則改壞了，你能一眼看出是哪一則造成的，而不是十幾則混在同一個 diff 裡。

第 2 步：確認每一則修復都符合預期

等所有 session 完成後，逐一確認改動。至少要做到兩件事：確認它真的修掉了那則 finding，以及確認它沒有動到不該動的地方。如果某則修復會改變功能行為，就在合併前把功能再跑一次。安全修復偶爾會不小心收緊到正常流程也被擋掉，這在合併前抓出來最省事。

第 3 步：在同一個 branch 上收成第二個 commit

確認完畢後，在同一個 branch（也就是原本那個 web-and-api）上，把修復 stage、產生新的 commit message、commit，然後 sync 推回同一條 branch：

git add -A
git commit -m "Fix security and review findings from CodeRabbit"
git push

推上去之後回到 PR 頁面，你會看到 commit 數從一個變成兩個：一個是原始的實作，一個是審查後的修復。這樣 PR 的歷史就很清楚：「這一版做了什麼」和「這一版被審查後修了什麼」分開記錄。

第 4 步：要不要等 CodeRabbit 再掃一次？

新的 commit 推上去後，CodeRabbit 會再對它跑一輪審查。你可以選擇等它跑完，看修復有沒有被接受；但這不是必要步驟。示範裡的選擇是不等：修完自己的修復之後，不需要為了 AI 的二次複審而卡住流程。你可以把這當成預設：修完、確認過，就往下合併；除非這則 PR 特別敏感，才值得多等一輪。

第 5 步：合併 PR

回到 PR 頁面，執行 merge，確認畫面顯示 successfully merged。合併代表這兩個 commit 正式進入主線。這一步是不可逆的，所以先確認：PR 的目標分支是 master、你要合併的內容就是這兩個 commit、而且沒有未提交的本地改動還沒處理。

第 6 步：切回 master 並同步

合併後切回 master，把遠端的最新改動拉回本地：

git switch master
git pull

完成後，本地 master 就包含剛剛那兩個 commit。整個循環到此結束：從一萬五千行無人能審的 diff，到一輪 AI 安全審查、一份經你判斷的修復，最後安全地落地到主線。

做完長什麼樣

驗證方式很直接：PR 頁面顯示兩個 commit 且狀態為 merged；切到 master 後，本機 git log 看得到那兩筆提交；先前 CodeRabbit 標記的 major security findings，在你選擇修的那些上已經消失或標為已解。至於每個類別背後的原理，屬第 2 步；怎麼判斷該修哪些，屬第 4 步；這裡只負責把程序安全地走完。

小結

替每一則要修的問題開獨立 session、平行套用修復，避免依序排隊。確認每則修復符合預期後，在同一個 branch 上 stage、產生新 commit message、commit 並 push，讓 PR 累積成兩個 commit。CodeRabbit 的二次複審可等可不等，預設不等。接著 merge PR、確認成功，切回 master 並 pull，把最新改動同步回本地。

你已經走完這個節點的完整循環：建立規模的觀念、拿到分類地圖、跑一次大型 PR 審查、做出修與留的判斷、把修復落地並合併。下一次面對「AI 一次生成整個後端」，你已經有一套能重複的做法，而不是把危險直接合併進主分支。
