在大型 PR 上跑安全審查

Step 3/5 · 大規模 PR 安全審查

學習目標

把上萬行改動開成 PR，讓 CodeRabbit 產出安全清單與 Change Stack。

前言：現在要把「審查」真的跑一次

前兩步建立了兩個基礎：你知道規模會讓逐行審查失效，也有了七大類問題的分類地圖。但地圖不是現場。這一節要動的是手，不是腦：把一萬五千行的改動從本機推到 GitHub，開成一個 PR，交給 CodeRabbit 掃，然後讀懂它回來的東西。

做完之後，你手上會有一份依照類別與嚴重度整理好的安全清單，以及每一則問題對應的修復建議；其中「給 AI agent 的修復指令」整段可以直接複製。動手前請先確認：功能已經完成並且你手動測過會動、CodeRabbit 已經連上你的 GitHub repo、你目前停在 master、而且本機的改動是乾淨的。

先看整體流程

把這次要跑的步驟攤開，順序如下。先掃一遍，知道等一下每個動作會在哪裡發生：

  1. 建一個描述這次改動的 branch，不要直接在 master 上做。
  2. 把改動 stage、產生 commit message、commit、publish。
  3. 在 GitHub 上建立 pull request。
  4. 確認這次 PR 的規模。
  5. 等 CodeRabbit 掃描完成，讀它的 summary 與逐檔 walkthrough。
  6. 打開 Change Stack，看它怎麼把改動分類。
  7. 看安全區塊的 major findings。
  8. 複製「給 AI agent 的修復指令」，留給第 4、5 步使用。

第 1 步：開一個 branch

即使只有你一個人，也不要把這麼大的改動直接推進 master。開一個描述性 branch，萬一審查發現問題，整個改動可以獨立檢視或丟掉，不會污染主線。這個例子的 branch 叫做 web-and-api，因為這次改動主要是 web 應用與 API 後端：

git switch -c web-and-api

名字本身不重要，能描述這次改動在做什麼就好。若你習慣用編輯器的指令面板，也可以用「create a new branch」的指令來完成同一件事。

第 2 步：stage、commit、publish

依序把全部改動加進暫存區、產生 commit message、commit，然後 publish 這個 branch。commit message 可以由 AI 依 diff 產生，這是這個流程裡少數可以放心交給 AI 的地方。它讀得到全部改動，你只要確認描述合理即可：

git add -A
git commit -m "Add web app and API backend for the clinic app"
git push -u origin web-and-api

第 3 步：建立 pull request

回到 GitHub，這個新 branch 會出現「Compare & create pull request」的按鈕。點下去、確認它要比對的是 master，送出。PR 建立之後，CodeRabbit 會自動接手開始掃描，你不需要額外觸發什麼。

第 4 步：先確認規模

在 PR 頁面上先看它顯示的數字。這個例子的結果是 11,000 行新增、約 4,000 行刪除，總計約 15,000 行、橫跨 54 個檔案。看到這個量級，就再次確認你為什麼不是用手審：15,000 行要在十分鐘內看完，平均每行 0.04 秒，人眼做不到。這也是為什麼這一節要把判斷交給工具產出的結構化清單。

第 5 步：讀 CodeRabbit 的 summary 與逐檔 walkthrough

等大約十分鐘，CodeRabbit 回來的第一塊是快速摘要，包含整體改動在幹嘛，以及它對每一個更新檔案的重點說明。先讀這一塊，讓自己重新拿到「這次 PR 在做什麼」的整體感。這正是大型 PR 最難維持的東西。如果摘要裡出現你沒預期的模組被改動，這裡就會看到。

第 6 步：打開 Change Stack，看它怎麼分類

接著進到 Change Stack。這是 CodeRabbit 把整包改動整理成可瀏覽結構的地方，也是它和一般 Git 平台最大的差別。GitHub 或 GitLab 面對一萬五千行的 diff，通常只能讓你一個檔一個檔手動翻；Change Stack 則把改動依主題分成一群一群（這個例子大約 12 類，例如 Next.js authentication guidance、Expo setup、onboarding、profile、home tab 等），並依字母排序。

你可以逐類展開，每一類旁邊會標示它涉及哪些檔案、增減了幾行，點進去看細節。這個介面真正的價值是：它把「54 個檔案」變成「十幾個你可以分別消化的主題」。如果某一類特別大、或特別敏感，你一眼就能看出來。

第 7 步：看安全區塊的 major findings

Change Stack 之外，捲到安全掃描的區塊。這個例子裡 CodeRabbit 抓到數個 major security issues，類別落在第 2 步那份地圖上：injection、authorization bypass、XSS、SSRF、CSRF、broken authentication、security misconfiguration。每一則都會附上問題說明，以及它建議的修法。

當問題很多時，CodeRabbit 會把最嚴重的（critical）以內嵌註解的方式直接標在對應的程式碼行上，讓你不用在一長串清單裡自己找。掃過去時，先鎖定 major／critical，minor 可以先放著；這個取捨是下一步的主題。

第 8 步：複製修復指令

CodeRabbit 對每一則問題都提供「給 AI agent 的修復指令」。除了逐則複製，它也能產生一段總結全部 review comments 的 prompt。把這段先複製下來放著，下一步會用它來一口氣把該修的問題交給 agent 處理。先講清楚：這一節只負責讓清單出現，修不修、要不要全部修，留到下一步判斷。

複製修復 prompt 之前，先讀懂那則問題在講什麼。這不是形式要求，AI 產生的 finding 本身也需要你的判斷，下一步會說明哪些該修、哪些該保留。

做完長什麼樣

回到 PR 頁面，成功的狀態長這樣：這個 PR 上多了一輪 CodeRabbit 的審查紀錄，裡面有一份整體摘要、一份依主題分類的 Change Stack、一組標好類別與嚴重度的安全 findings，以及幾段可以直接貼給 agent 的修復指令。你還沒有修改任何程式碼，只是先把「看不完的一大包」變成「可處理的清單」。至於每個類別背後在防什麼，屬第 2 步的範圍；哪一則該修、哪一則該留，屬第 4 步的範圍。

小結

在 master 之外開一個描述性 branch（如 web-and-api），stage、commit、publish，再於 GitHub 建立 pull request。先確認規模（示例為約 15,000 行／54 檔），等 CodeRabbit 約十分鐘，依序讀 summary 與逐檔 walkthrough、打開 Change Stack 看分類、進安全區塊鎖定 major findings，最後複製給 AI agent 的修復指令。整段流程只把清單生出來，還沒有決定要修什麼。

清單已經在手上，但清單不是答案。下一步要面對這個節點最核心的判斷：CodeRabbit 列的每一則 finding，你都要修嗎？哪些該修、哪些其實該保留？
