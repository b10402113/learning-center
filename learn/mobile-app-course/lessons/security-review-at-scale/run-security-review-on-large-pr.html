在大型 PR 上跑安全審查

Step 3/5 · 大規模 PR 安全審查

這一節要完成什麼？

前一節認識了七類安全問題，這一節要真的把它們找出來。做完之後，你會有一個開在 GitHub 上的 PR，裡面是那批上萬行的後端與 API 改動，而 CodeRabbit 已經幫你完成逐行審查與安全掃描，回傳一份分類好的問題清單。

開始前需要具備三件事：一，後端與 API 的改動都已完成，app 能跑；二，這個 repo 是放在 GitHub 上、而且你已經把 CodeRabbit 連上這個 repository；三，確認 .env 已經在 .gitignore 裡。第三點是動手的門檻，因為這一步會把所有改動一次推上遠端，如果金鑰還被追蹤，它就會一起被推出去。若 .env 還沒排除，先把它加進 .gitignore 並從版控移除，再繼續。

第一步：把所有改動集中到一條分支

大改動一律走分支，不要直接推上 main。分支的作用是隔離：在審查完成之前，這些程式碼都還不算是主線的一部分。

# 建立並切到這條分支（課程用的名稱是 web-and-api）
git checkout -b web-and-api

為什麼要一條專門的分支？因為這個 PR 的規模大到一旦出錯就很難收拾。隔離在分支上，你隨時能重來、能比較，也不會讓主分支在審查期間處於不穩定狀態。

第二步：stage、產生 commit message、commit

把這批改動加入暫存區，再提交。commit message 交給 agent 產生即可，它會讀過改動後給一句摘要。

git add .

# 讓 agent 產生 commit message，或自己下一個清楚的標題
git commit -m "feat: 建立 web dashboard 與後端 API"

課程中的這個 PR 大約是 11,000 行新增、4,000 行刪除。在按下去之前，先快速確認推出去的內容裡沒有密鑰檔。如果看到 .env 出現在變更清單裡，停下來處理，不要 commit。

第三步：推上遠端，開 PR

把分支推上 GitHub，然後建立 Pull Request。來源是 web-and-api，目標是 main。

git push -u origin web-and-api

推上去之後，GitHub 通常會直接顯示 compare & pull request 的提示；按下它，確認來源與目標分支，填好標題，就能開 PR。從 VS Code 操作時，順序會是建立分支、stage、commit、publish、建立 PR。

第四步：等 CodeRabbit 跑完 review 與安全掃描

PR 一開好，CodeRabbit 就會被觸發，逐行審查這個 PR 的改動，同時執行安全掃描。改動量大的時候需要一點時間——課程裡的範例約 十分鐘。這段時間不需要盯在螢幕前，可以去處理別的事，回來再看結果。

萬一你想在等待時去忙別的，記得：掃描是在 GitHub 上進行的，跟你本機的終端機無關，所以關掉編輯器也不會中斷。等它跑完再回到 PR 頁面即可。

第五步：把輸出讀成一張清單

處理完之後，PR 頁面上會多出幾種輸出。這一節的重點不是修，而是讀懂它給了什麼：

輸出你要從裡面拿到什麼
PR 摘要一句話掌握這批改動在做什麼，先有全貌
逐檔導覽每個檔案改了哪些地方，需要時下鑽
嚴重度排序的行內註解critical / major / minor 分級，最該處理的排在前面
Change Stack依改動性質分成十幾個類別，能按主題讀
安全掃描清單把 injection、授權繞過等安全問題獨立列出

讀的時候有一個實用順序：先看安全清單，因為那是「可以被攻擊」的問題；再看 critical 等級的行內註解；最後才依 Change Stack 的分類把其餘的看過。不要把清單從第一個字讀到最後一個字，而是先挑最危險的。

第六步：先別動手修，把彙整 prompt 留下來

看到一長串意見，很容易想立刻一則一則修。先忍住。CodeRabbit 提供一個功能，能把所有 review 意見彙整成「給 AI agent 的完整 prompt」。這一節先把那份 prompt 複製下來，因為下一步要做的判斷，是「哪些該修、哪些該保留」，判斷完再分派出去修。

做完這一節，你應該看到：一條名為 web-and-api 的分支已推上 GitHub，PR 開好且目標是 main，CodeRabbit 已完成審查與安全掃描，輸出裡有一份分類好的安全清單與 Change Stack，而你手上留著一份彙整好的 review prompt。程式還沒改動——那是下一步的事。

為什麼原理留給別處？這一節是操作，目標是「把審查跑起來並拿到可用的輸出」。至於那七類安全問題各自是什麼，上一節已經交代；拿到清單後怎麼判斷，下一節處理。

現在你有一份清單了，但清單上的每一則都該照做嗎？下一節要處理這個最容易做錯的判斷：AI 的審查意見也是 AI 生成的，有些要修，有些其實是你刻意設計的結果。
