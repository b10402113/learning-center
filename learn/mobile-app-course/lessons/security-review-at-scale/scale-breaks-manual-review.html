為什麼上萬行的 PR 不能靠人眼審

Step 1/5 · 大規模 PR 安全審查

學習目標

判斷一份 PR 是否已大到人眼無法逐行審查，並理解為什麼需要結構化輸出。

前言：一個下午，一萬五千行

想像這個畫面：你請 AI 一個下午就把整個後端做出來。它不只寫了頁面，還建了 API、資料庫、業務邏輯，順手補了驗證與錯誤處理。你打開 GitHub 準備開 PR，看到的第一行數字是「11,000 additions、約 4,000 deletions」，換算下來大約 15,000 行改動，分散在 54 個檔案裡。

你告訴自己：十分鐘看完就好。但你算一下，15,000 行除以 600 秒，等於每一行只有 0.04 秒。你不是在讀程式，你是在把畫面往下捲。這一節要處理的就是這件事：當「審查」的對象大到人眼放棄，你原本熟悉的那套 review 流程就整個失效了。先把它失效的原因講清楚，後面的四個步驟才有立足點。

人眼 review 其實有個沒說出口的假設

過去我們對 PR review 的直覺，建立在一個隱含假設上：diff 的量是可以消化的。幾十行、幾百行、最多一千多行，你可以在一個工作時段內讀完，讀的時候腦中還能維持一份「這個改動整體在做什麼」的地圖。

這個假設一旦被打破，壞掉的不只是速度。注意力會先崩潰：review 從「讀懂每一段」退化成「掃過去」，而危險的程式碼正是靠著混在合法程式碼中間才躲得掉。你還是會點下 Approve，只是你心裡知道自己其實沒看懂。

接著是遺漏的型態改變。小型 PR 的 bug 通常很明顯：功能壞掉、頁面空白、按鈕沒反應，你一眼就看得出來。但大型 AI 生成 PR 裡最危險的東西長得完全不一樣：它能跑、測試也過，卻可以被攻擊。這種問題不會讓功能壞掉，所以「操作一遍看看」根本測不出來。

能跑的程式，不代表是安全的程式

把「會壞的 bug」和「能跑但危險的漏洞」並排看，差異就很清楚：

面向會壞的 bug能跑但危險的漏洞
你怎麼發現功能做不出來，操作一遍就看到功能完全正常，操作看不出來
測試會抓到嗎通常會，因為測試驗的是你想到的情境通常不會，攻擊發生在你沒想到的輸入
錯過的代價使用者抱怨，你回頭修資料外洩或權限被繞過，而且往往沒人回報
在小 PR 裡明顯，review 會攔下來罕見，容易人工看出
在大 PR 裡仍然明顯混在同類程式碼中間，最容易被掃過去

第二欄才是這個節點真正在防的東西。SQL injection（把使用者輸入當成 SQL 指令執行）、authorization bypass（沒確認這個人有沒有權限，就直接讓他拿到別人的資料）都屬於這一欄。它們的共同點是：程式「看起來在工作」，所以你不會特別停下來。

測試為什麼救不了你？因為測試驗證的是你「想到」的情境。你寫測試時想的是「使用者點下按鈕會發生什麼」，不是「如果我送出一段帶有 SQL 片段的字串會發生什麼」。安全問題恰好住在你沒想過的那些輸入裡。這正是為什麼「有測試」不能取代一輪針對安全設計的審查。

規模讓 review 從瓶頸變成天花板

把鏡頭拉遠一點，這裡還有一個速度差的問題。AI 生成程式碼的速度，已經遠遠超過人類審查的速度：它十分鐘生一萬五千行，你十分鐘只能審幾百行。當生成速度和審查速度差到這個程度，實務上只剩兩條路：要嘛跳過審查直接合併，要嘛把未審的程式碼堆在分支上等，等到它跟主分支愈差愈遠。

你在「版控與 AI Code Review」那個節點已經看過同一個矛盾的雛形：review 會成為整條流程的瓶頸。那時處理的是功能層級的小 PR，靠的是「勤勞地審」加上一輪 CodeRabbit。到了這裡，光靠勤勞已經不夠了。不是你不夠認真，而是這個量級下，逐行閱讀本來就不會產生正確結果。

解法不是看更快，而是換一種看法

先講清楚一件事：這一節不是要你放棄 review，是要換掉「用眼睛逐行讀」這個方法。當你不可能讀完每一行，你需要的是幾種不同的能力：掃描整個 codebase（不是只看這個 diff）、把問題依類別整理（不是散落在幾百個檔案裡）、標出嚴重度（讓你先處理該處理的），最後產生可以直接執行的修復指令。

打個比方：人眼逐行審一萬五千行，像是拿顯微鏡檢查一整座機場的每一顆螺絲。你檢查得很仔細，但檢查不完，也看不到整體哪裡結構有問題。你需要的其實是 X 光機，掃過全部、把異常挑出來、還依類型排好，讓你只看那幾張有問題的片子。

CodeRabbit 的 AI 審查就是這台 X 光機：它掃描整個 PR、把改動依類別收進一份「Change Stack」，並把安全問題依類別與嚴重度列出來，還附上修復建議。它不會取代你的判斷，但它把你從「不可能讀完」的處境，換成「面對一份可處理的清單」。下一節要給你的，就是這份清單上的分類地圖。

這個觀念該掛在哪裡

把它接回你腦中既有的那張圖：「版控與 AI Code Review」教你的是功能層級的 review，前提是 diff 小到可以讀；而「規模本身就是問題」這個觀念，說明的是那個前提什麼時候會消失。一旦消失，你需要的不再是更努力的眼睛，而是一套結構化的輸出。這就是後面四步要建立的東西：先拿到安全問題的分類地圖，再實際跑一次大型 PR 的審查、讀懂輸出，然後做出最關鍵的判斷（AI 說的每一則都要修嗎），最後把修復套用、驗證、合併。

小結

人眼 review 的隱含假設是「diff 量可以消化」。當一份 PR 來到數十個檔案、上萬行，這個假設破功：注意力崩潰、能跑但危險的漏洞躲過檢查、而測試無法涵蓋你沒想到的輸入。解法不是看更快，是改用能掃描整個 codebase、依類別與嚴重度整理問題、並產生可執行修復的結構化工具。
