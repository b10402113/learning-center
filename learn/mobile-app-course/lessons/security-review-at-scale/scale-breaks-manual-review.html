為什麼上萬行的 PR 不能靠人眼審

Step 1/5 · 大規模 PR 安全審查

前言

想像這個畫面：你剛讓 AI 把整個後端和 API 生出來，功能測試一路過關，畫面上每個按鈕都正常運作。接著你打開那個準備合併的 Pull Request，看到一行字——54 個檔案、約 15,000 行改動，其中約 11,000 行是新增、4,000 行是刪除。你的任務是在合併進主分支之前，把這些程式碼看過一遍。

問題是，沒有任何人能在十分鐘內真的看完這 15,000 行。更麻煩的是，程式「跑得起來」和程式「安全」是兩回事：功能測試會過，只代表正常路徑沒壞，不代表沒有人能從旁邊繞進去。這一節要處理的，就是當改動大到這個程度時，為什麼「自己看」不再是選項，以及我們靠什麼把審查這件事重新變得可行。

前面的「版控與 AI Code Review」處理的是功能層級的審查——一條小分支、一個 PR、讓 CodeRabbit 看過。這一節是它的放大版：當審查對象從幾千行變成上萬行、從 UI 變成後端與 API 時，難度不是等比例增加，而是換了一個量級。

審查的瓶頸，會隨規模突然斷掉

先看小 PR 的狀況。一條功能分支改動兩千行、跨十幾個檔案，對一個熟悉這個專案的人來說，花個十來分鐘逐一讀過是合理的。這也是多數人對「code review」的預設想像：打開 diff，從第一個檔案看到最後一個。

但當改動變成上萬行、數十個檔案時，這個方法不是「變慢一點」，而是直接失效。原因不是你不夠努力，而是人眼的兩個限制被放大了：

  • 注意力是有限的。讀到第 8,000 行時，你對「這行有沒有問題」的判斷力已經比剛開始弱很多。後面幾千行不是被讀過，只是被滑過。
  • 風險不是平均分布的。15,000 行裡真正致命的可能只有五、六處，但它們和其他一萬多行長得一模一樣。沒有人告訴你該把注意力放在哪，你只能平均分配——而平均分配等於每一處都看不仔細。

這就像海關要檢查一整個貨櫃的貨物，卻沒有任何掃描設備，只能靠人手一件一件翻。你翻得完，但翻不完的部分，正是最容易被夾帶東西的地方。程式碼也一樣：當 diff 大到沒有自然的閱讀順序，漏看就不是意外，而是必然。

「能跑」為什麼騙得了人

還有一個更隱微的問題：上萬行的初始 PR 幾乎一定「測得過」。開發時你會打開 app、點幾個流程、看到畫面正常，就覺得沒問題。但功能測試只走正常路徑，而安全漏洞住在不正常的路徑裡。

舉幾個例子。一個 API 端點會正確地回傳資料，但只要你把網址裡的預約編號換成別人的，它也照樣回傳——因為它只檢查「有沒有登入」，沒檢查「這是不是你的」。畫面上完全看不出異狀，因為正常使用者不會去做這件事。又如某段程式把使用者輸入直接拼進資料庫查詢字串，平常怎麼用都正常，直到有人輸入一段帶有查詢語法的字串。這些都不是「壞掉」，而是「可以被利用」。

所以，能夠手動測過一遍，反而容易讓人放心得太早。真正需要的是換一個角度，用「攻擊者會怎麼做」去看這批程式碼，而這個角度，正是人眼在 15,000 行面前最難維持的。

讓審查重新可行的，是結構化輸出

既然逐行看不可行，解法就不是硬看，而是把這批改動先整理成一張「地圖」，再照著地圖去看該看的地方。CodeRabbit 這類 AI 審查工具真正有價值的地方，不在於它比人聰明，而在於它能把一大坨沒有結構的 diff，壓縮成人能消化的幾種輸出：

輸出它幫你解決的問題
嚴重度排序的行內註解把最該優先處理的 critical 問題直接標在對應那行，你不再需要平均分配注意力
Change Stack（變更堆疊）把幾十個檔案依改動性質分成十幾個類別，你可以按主題讀，而不是從頭滑到尾
PR 摘要與逐檔導覽先給你鳥瞰，再讓你能下鑽到某個檔案，補上「這批改動在做什麼」的全貌
安全掃描清單把 injection、授權繞過這類安全問題獨立列出來，不混在一般的風格建議裡

這裡的關鍵轉變是：你不必再當那個逐件翻貨櫃的人，而是先拿到一份掃描報告，知道哪幾箱要優先打開。審查的品質不再取決於你撐了多久，而是取決於你有沒有拿到足夠好的地圖。

規模本身就是一個獨立問題。同一套審查流程，遇到上萬行的 PR 就會失效；讓它重新可行的不是更努力，而是把改動先壓縮成嚴重度排序、分類堆疊與安全清單這類結構化輸出。

下一節要把這張地圖裡最要緊的一塊攤開：那個「安全掃描清單」到底在講什麼。injection、authorization bypass、XSS、SSRF、CSRF、broken auth、security misconfiguration——這七個詞各防的是哪一種攻擊，你得先認得出來，才有辦法判斷 AI 指出的問題是不是真的嚴重。
