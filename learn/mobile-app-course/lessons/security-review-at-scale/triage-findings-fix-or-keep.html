哪些 finding 該修、哪些該保留

Step 4/5 · 大規模 PR 安全審查

學習目標

對每一則 AI finding 做判斷，決定修或保留，並批次分派。

前言：清單有了，但清單不是聖旨

上一步結束時，你手上多了一長串 CodeRabbit 的 finding，每一則都附著問題說明與建議修法。面對它，最直覺的兩個反應是：「AI 掃得比我仔細，全部照修最安全」或「反正它常常誤判，先全部略過」。兩個都省事，但兩個都錯。

這一節要做的是這個節點真正的心臟：判斷。AI 審查給你的是一份高品質的候選清單，不是一份命令。你要在「漏修一個可能被攻擊」和「全盤接受會修掉刻意的設計、浪費時間甚至弄壞東西」這兩股力量之間做選擇。做得好，你既不會漏掉真正危險的問題，也不會被雜訊拖著跑。

三種處理方式，先看清各自的代價

做法什麼時候看起來對代價
全盤接受 怕漏掉任何一個安全問題，乾脆全部照修 會改到刻意的設計、花時間重跑測試、甚至引入新問題
全盤忽略 覺得 AI 常常誤判，不想被雜訊干擾 真正 critical 的漏洞被跳過，直接合併進主分支
分流處理 願意逐則判斷，把力氣放在真正重要的地方 需要你花時間讀懂每一則，判斷力不夠時可能誤判

這門課要的是第三種。它的前提是先承認一件事：AI finding 是「另一個 AI」產生的草稿，值得讀，但需要你讀懂之後再決定信不信。

逐則判斷時，問自己這幾個問題

把每一則 finding 當成一個小決定，依序問自己：

  1. 這是「能跑但可被攻擊」的問題，還是風格偏好？ injection、authorization bypass、XSS 這類屬前者，該進正式處理；命名、排版、寫法偏好屬後者，可以延後或略過。
  2. 它對上的是不是一個刻意做的決定？ 這是最容易被誤判的一類。例如某個圖片的 masks: false 是你故意保留的設定，AI 卻把它當成遺漏而建議開啟。這種 finding 要保留，並在 PR 留言寫明理由。
  3. 嚴重度標在哪一級？ CodeRabbit 會把問題分成 critical、major、minor。量大的時候，先處理 critical 與 major；minor 可以最後一起掃、或直接略過。
  4. 修了會不會改變行為？ 安全修復常常會動到既有邏輯。若會，就不能只看 diff 通過，還要重新驗證功能；若只是收緊設定，風險就低得多。
  5. 我真的讀懂這則問題了嗎？ 如果看不懂，先不要按修復。看不懂就套用，等於把判斷權整包讓給 AI，那就失去分流的意義了。

規則會翻轉的情況

上述的「先判斷、不急著全修」不是鐵律，遇到下面這些情況要反過來：

安全敏感又接近上線時，寧可保守。 如果這個 PR 就要合併進正式環境，而 finding 屬於 injection、authorization bypass 這一類高風險且修法明確，那就先修再合併，不要為了省時間把它留到下一個 PR。

當 AI 明顯誤判時，保留並留下理由。 判斷「這是誤判」本身需要勇氣，也需要紀律：不要只是默默略過，要在 PR 上寫一句「這個 masks: false 是刻意的，故不套用」，讓下一個看 PR 的人知道你不是漏看。

不要把修復全部串成同一條排隊。 如果你把十幾則修復 prompt 依序貼進同一個 session，就得等第一則跑完才能開始第二則。更好的做法是替每一則開一個獨立的 session，平行處理。這個技巧是下一步的主軸。

把判斷批次分派的樣子

當你已經把 finding 分成「要修」與「保留」兩堆，接著才是分派。做法是替每一則要修的問題開一個獨立的 agent session，各自貼上對應的修復 prompt，讓它們同時進行。Critical 與 major 先送，minor 視情況最後一起處理。這樣你只花了「讀懂清單」的時間，卻讓多個修復同時在跑。

判斷的先後順序建議是：先安全、後風格；先 critical／major、後 minor；先能講清楚後果的、後只是偏好的。避免邊看邊修，先把「要修哪些」定下來，再進到套用階段。

一句可帶走的決策規則

看到一則 finding，先問：「這是能跑但可被攻擊的問題，還是我刻意設計的取捨？」是前者且嚴重度在 major 以上，就修；是後者，就保留並寫下理由；判斷不出來，就先讀懂，別急著按套用。把每一則都走過這個問句，你就完成了分流。

小結

AI finding 是候選清單，不是命令。先在全盤接受、全盤忽略、分流處理三者中選分流。逐則問：是安全問題還是風格偏好？是否違背我刻意的設計？嚴重度是哪一級？修了會不會改行為？我真的讀懂了嗎？安全敏感且接近上線時寧可保守；明顯誤判則保留並註明理由。最後替每一則要修的問題開獨立 session，分批平行處理。

哪些要修已經決定了，接下來就是把這些決定的修復套用上去、收成第二個 commit，驗證之後把 PR 合併回 master。這就是最後一步。
