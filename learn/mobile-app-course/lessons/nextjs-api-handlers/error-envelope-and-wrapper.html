route() 包裝與錯誤信封

Step 2/5 · Next.js API Route Handlers

先想像一個沒有統一出口的 API

當手機呼叫 API 時，最怕的不是「有錯誤」，而是每個端點都用不同方式出錯：有時回一段字串，有時回一個不一樣的 JSON，遇到資料庫例外時甚至把內部細節整包倒給 client。手機端就像拿著一疊沒有標籤的包裹，只能逐一猜裡面裝的是什麼。

這一節要建立的，就是 API 的統一錯誤出口。你會看到 route() 如何接住 handler 丟出的錯誤，將預期中的業務錯誤與 Zod 驗證錯誤整理成固定格式；同時把未預期的錯誤留在伺服器內部，避免資料庫訊息或 PHI（受保護的健康資訊）從錯誤回應中外流。

學習目標

能說明 route() 如何把丟出的 ApiError 與 ZodError 收斂成一致的 JSON 回應，以及為什麼原始錯誤不能原封不動回給 client。

錯誤一冒出去，就可能來不及了

上一節我們開出了第一個端點，也在每個 handler 外面套了 route()，但還沒有仔細說明它到底在做什麼。先把這層包裝拿掉來看：假設某個 handler 正從資料庫讀資料，途中拋出例外，而程式沒有任何地方接住它，例外就會一路往上冒，最後變成一個 500。

手機端看到的可能只是一個沒有固定格式、難以辨認的回應。使用者只能看到「Something went wrong」，你則得回到 log 裡翻找，才能猜是哪一步出了問題。

安全性也會一起受影響。Drizzle 拋出的錯誤訊息可能長得像 Failed query: <SQL>\nparams: <綁定的值>，而綁定的值很可能就是病人的姓名、生日等 PHI。如果把原始錯誤直接回給 client，就等於替資料庫開了一個不該存在的出口。

所以這一節的目標很明確：讓所有 handler 都遵守同一套錯誤規則。錯誤怎麼丟、怎麼接住、最後回應長什麼樣子，集中在一個地方決定。

先定義錯誤：ApiError 與它的家族

要統一處理錯誤，第一步是讓「預期中的錯誤」有共同型別。這個 app 定義了 ApiError，裡面帶著 HTTP 狀態碼、給人看的訊息，以及可選的錯誤代碼。

訊息與代碼分開保存，是因為它們服務不同對象：訊息給人閱讀，代碼給程式判斷。之後手機若要判斷「這是不是搶位失敗」，應該依賴穩定的代碼，而不是可能隨產品文案調整的訊息文字。

/** Thrown anywhere below a route handler; `route()` turns it into a response. */
export class ApiError extends Error {
  constructor(
    readonly status: number,
    message: string,
    readonly code?: string
  ) {
    super(message);
  }
}

export const unauthorized = (m = 'Sign in required') => new ApiError(401, m);
export const forbidden = (m = 'Not allowed') => new ApiError(403, m);
export const notFound = (m = 'Not found') => new ApiError(404, m);
export const badRequest = (m: string) => new ApiError(400, m);
export const conflict = (m: string, code?: string) => new ApiError(409, m, code);

下面這排小函式可以看成「快速丟錯」的語法糖。原本可能要寫 throw new ApiError(404, 'Not found')，現在可以直接寫 throw notFound('Patient not found')。

它的價值不只是少打幾個字。當整個專案都使用 unauthorized、forbidden、notFound 和 conflict，401、403、404、409 這些常見狀態就會有一致的預設訊息。conflict 還多收一個 code，因為 409 只表示「發生衝突」，實際上還需要知道是哪一種衝突。

這裡要畫出一條重要界線：ApiError 代表「預期中、可以對使用者說明的錯誤」，例如使用者尚未登入、資料不存在，或某個時段已被搶走。

至於資料庫連線中斷、程式 bug 等「未預期的錯誤」，就不應該假裝它們也是業務結果。讓它們維持原樣往上拋，再由 wrapper 統一記錄與遮蔽。接下來的 route() 正是這個分流器。

route() 的機制：一個 catch 管全部

有了共同的錯誤型別，包裝器就能用一個 try/catch 收斂各種情況。它會把原本的 handler 包進一個新函式：正常時照常執行，出錯時則根據錯誤種類決定回應。

/**
 * Wraps a route handler so thrown errors become clean JSON instead of a 500.
 * Keeps every handler down to its actual business logic.
 */
export function route<Args extends unknown[]>(
  fn: (...args: Args) => Promise<Response>
): (...args: Args) => Promise<Response> {
  return async (...args: Args) => {
    try {
      return await fn(...args);
    } catch (err) {
      if (err instanceof ApiError) {
        return Response.json({ error: err.message, code: err.code }, { status: err.status });
      }
      if (err instanceof ZodError) {
        return Response.json(
          { error: 'Invalid request', issues: err.issues.map((i) => ({ path: i.path, message: i.message })) },
          { status: 400 }
        );
      }
      …
      Sentry.captureException(err);
      …
      return Response.json({ error: 'Something went wrong' }, { status: 500 });
    }
  };
}

從上往下看，這個 wrapper 主要處理三種情況。

第一種是 ApiError。它會被翻成 { error, code }，HTTP 狀態碼則使用錯誤物件自己帶的值。這讓 handler 可以專注在商業邏輯，而不必每次都手動組出 Response。

第二種是 Zod 的驗證錯誤 ZodError。它固定回傳 400，並附上每個欄位出錯的位置與原因，讓 client 能把錯誤標回表單。

第三種是其他未預期的錯誤。程式會先送到 Sentry、再寫一行 log，但回給 client 的只有 Something went wrong。原始錯誤不會跟著回應一起出門。

特別注意 500 的分支：它刻意不把 err.message 放進回應。因為原始錯誤可能包含 query text，而 query text 可能進一步包含 PHI。即使是伺服器內部的 log，也不能完全放心地保留原文；只要 log sink 多一個匯出目的地，原本的內部邊界就可能被打開。

錯誤信封的形狀：手機只需要懂一套

這個 wrapper 最重要的產出，是把不同來源的錯誤裝進固定形狀的「錯誤信封」。不管是哪個端點出錯，手機收到的都會落在以下幾種格式：

狀況HTTP 狀態回應內容
預期中的業務錯誤401／403／404／409…{ "error": "訊息", "code": "可選代碼" }
請求欄位不合法400{ "error": "Invalid request", "issues": [ … ] }
未預期的伺服器錯誤500{ "error": "Something went wrong" }

格式一旦固定，手機端的錯誤處理就只需要寫一次。它可以固定讀取 error 與 code；看到 409 加上 slot_taken，就顯示「這個時段剛剛被搶走了，換一個」；看到 issues，就把欄位錯誤標回表單。

反過來說，如果每個 handler 都自由發明自己的回應格式，手機就得為每個端點客製一套解析器。那就像每個房間都有不同尺寸的門，維護起來才是真正的地獄。

還有一個容易漏看的細節：回應用的 json() helper 會固定加入 Cache-Control: no-store。這些回應都與特定身分有關，可能包含你的預約、病歷，或只屬於你的簽名檔網址，不能被其他人共用或快取。

export function json(data: unknown, status = 200) {
  // Every response from this helper is scoped to the caller — a patient's own
  // records, and signed attachment URLs that are identity-specific and expire.
  // Nothing here is shared, so nothing here is cacheable.
  return Response.json(data, { status, headers: { 'Cache-Control': 'no-store' } });
}

順手洗掉不該外流的資料

接著補上一個安全性小工具。前面提到，Drizzle 的錯誤訊息可能把綁定值一起印出來，而這些值可能是病人資料。app 使用 scrubQuery，把訊息中 params: 後面的整段內容替換掉，只留下有助於定位 bug 的 SQL 部分。

export function scrubQuery(message: string): string {
  return message.replace(/\nparams: [\s\S]*/, '\nparams: [scrubbed]');
}

這個清理會同時套用在兩個錯誤可能抵達的終點：Sentry 事件與 console log。這樣即使錯誤被記錄下來，診斷資訊與敏感資料也不會整包綁在一起。

另外還有一個 isExclusionViolation，專門辨認 Postgres 的排除約束違反，也就是錯誤碼 23P01。防止重複預約的資料庫約束被觸發時，就會送出這個訊號；handler 收到後，會把它轉成 409 的 conflict。到了第 5 步處理 booking handler 時，會再看到這個函式如何接上整條錯誤流程。

把這些觀念接在一起

route() 把每個 handler 包在一個 try/catch 裡，讓 handler 本體只留下商業邏輯。預期中的錯誤用 ApiError 家族丟出，會被翻成固定的 { error, code } 信封；Zod 驗證失敗回 400 加 issues；未預期的錯誤送 Sentry、寫洗過的 log，回給 client 只有一句 500。錯誤形狀統一，手機才只需要懂一套解析；原始錯誤不外流，PHI 才不會從錯誤訊息漏出去。

因此，route() 不只是少寫幾個 try/catch 的便利工具。它把「handler 如何表達錯誤」、「API 如何對外回應」與「敏感資訊停留在哪裡」這三件事接成同一條邊界：內部可以保留足夠線索來除錯，外部則只收到穩定、安全、可供程式判斷的信封。

錯誤有了統一出口，下一個要處理的就是入口：誰可以進來。如果身分判斷散落在每個 handler 裡，早晚會有人寫出「相信 client 傳來的 userId」這類漏洞。下一節會把這條規則集中到守衛身上：requireAuth、requireStaff 與 requireOwnedPatient。
