route() 包裝與錯誤信封：讓每個 handler 只留商業邏輯

Step 2/5 · Next.js API Route Handlers

學習目標

能說出 route() 包裝把 ApiError、Zod 的驗證錯誤與未知例外各自轉成什麼回應，並解釋 json() 為何一律加上 no-store，以及為什麼原始錯誤訊息不能原樣回傳給 client。

前言：每個端點都自己 try/catch，很快就會崩

上一節我們把端點開了出來，但還沒有處理「出錯的時候會發生什麼事」。如果什麼都不做，某個 handler 裡丟出一個例外，Next.js 會回一個 HTML 錯誤頁或一段堆疊。手機端拿到這種東西，根本沒辦法判斷「是沒登入？輸入錯了？還是伺服器壞了」，只能一律顯示「發生錯誤」。

更麻煩的是，如果放任每個 handler 自己寫 try/catch，你會得到十幾種不同的錯誤格式，每加一個端點就多一次重複。這一節要示範的做法，是把錯誤處理集中到一個包裝函式裡，讓 handler 本體只留下它真正該做的事。

先定義一種「可被翻譯的錯誤」：ApiError

要讓錯誤能被統一處理，第一件事是給它一個一致的類型。這支 API 自訂了一個 ApiError，帶著 HTTP 狀態碼、訊息，以及選用的錯誤代碼：

export class ApiError extends Error {
  constructor(
    readonly status: number,
    message: string,
    readonly code?: string
  ) {
    super(message);
  }
}

export const unauthorized = (m = 'Sign in required') => new ApiError(401, m);
export const forbidden    = (m = 'Not allowed')      => new ApiError(403, m);
export const notFound     = (m = 'Not found')        => new ApiError(404, m);
export const badRequest   = (m: string)              => new ApiError(400, m);
export const conflict     = (m: string, code?: string) => new ApiError(409, m, code);

這些 helper 讓 handler 可以用一句 throw badRequest('Invalid appointment time') 表達「這是使用者的輸入問題」，而不必當場決定要回什麼 JSON。錯誤被丟出去之後，由外層的包裝接手。

這裡的 code 欄位值得注意。它是一個給程式看的短字串，例如預約被搶走時會帶 'slot_taken'。訊息是給人看的，code 是給手機端判斷分支用的——手機可以根據 code 決定要不要提示「重新選一個時段」。

三種錯誤，三種出口

包裝函式 route() 的工作，就是接住任何被丟出來的東西，判斷它是哪一類，再轉成對應的回應。它會遇到三種情況。

第一種是自己丟出的 ApiError。這種最好處理，因為狀態碼和訊息本來就寫好了，直接包成 JSON 回傳。第二種是 Zod 的 ZodError，也就是請求輸入沒有通過 schema 驗證；這種一律回 400，並附上每個欄位錯在哪裡。第三種是其他所有意料之外的例外：記錄到 Sentry、寫一行 log、回一個不含細節的 500。

export function route<Args extends unknown[]>(
  fn: (...args: Args) => Promise<Response>
): (...args: Args) => Promise<Response> {
  return async (...args: Args) => {
    try {
      return await fn(...args);
    } catch (err) {
      if (err instanceof ApiError) {
        return Response.json(
          { error: err.message, code: err.code },
          { status: err.status }
        );
      }
      if (err instanceof ZodError) {
        return Response.json(
          { error: 'Invalid request', issues: err.issues },
          { status: 400 }
        );
      }
      Sentry.captureException(err);
      console.error('[api] unhandled error', scrubQuery(err.message));
      return Response.json({ error: 'Something went wrong' }, { status: 500 });
    }
  };
}

寫出來的 handler 就會長成這樣，整個函式只保留商業邏輯，看不到半個 try/catch：

export const POST = route(async (req: Request) => {
  const user = await requireAuth();
  const body = createAppointmentSchema.parse(await req.json());
  // ...真正的工作
  return json({ appointment }, 201);
});

換句話說，route() 是錯誤唯一會穿越邊界的地方。handler 內部愛丟什麼就丟什麼，丟出去之後的行為是統一的。

狀態碼的意義要固定

錯誤信封能運作的前提，是每個狀態碼都有一致的意義。這組 helper 把約定固定下來，手機端就能靠狀態碼做決策：

helper狀態碼代表的意思手機可以怎麼反應
unauthorized()401沒有有效的登入憑證導回登入
forbidden()403登入了，但這個角色不能做顯示「沒有權限」
notFound()404沒有這筆資料，或不屬於你回到上一頁
badRequest()400輸入本身不合法提示使用者修正
conflict()409狀態衝突，例如時段被搶走重新整理可選時段

把「不存在」和「不是你的」都收斂成 404，是一個刻意的安全選擇。如果別人的病歷回 403、不存在的病歷回 404，攻擊者就能用兩者的差別去探測「哪些 id 真的存在」。一致回 404，等於不洩漏任何存在性資訊。下一節講守衛時會再看到同一個原則。

把資料庫的例外翻譯成 app 的語言

有些錯誤不是你的程式丟的，而是資料庫丟的。預約系統靠 Postgres 的排除約束（exclusion constraint）防止重複預約；當兩個請求幾乎同時搶同一時段，其中一個會被資料庫擋下，丟出錯誤碼 23P01。這個碼對手機毫無意義，所以 API 用一個小函式認出它，再翻譯成乾淨的 409：

export function isExclusionViolation(err: unknown): boolean {
  const code = err?.code ?? err?.cause?.code;
  return code === '23P01';
}

// 在 handler 裡：
catch (err) {
  if (isExclusionViolation(err)) {
    throw conflict('That time was just taken. Please pick another.', 'slot_taken');
  }
  throw err;
}

注意這裡的 catch 只攔一種例外，其他一律再丟出去，交給外層的 route()。這是一個好的分工：handler 只翻譯它懂的那一種，其餘的不要吃掉。

500 不能把內部細節說出來

未知例外回的那句 { error: 'Something went wrong' } 看起來很敷衍，但它其實是刻意的。Drizzle 在查詢失敗時，錯誤訊息會長成「Failed query: <SQL>」後面接著「params: <綁定的值>」，而那些綁定的值就是病歷的欄位——姓名、生日、病史。如果把原始訊息回給 client，等於把 PHI（受保護的健康資訊）送了出去。

所以這支 API 做了兩層防護。回給 client 的，永遠是固定的泛用訊息；寫進 log 與 Sentry 的，則先經過 scrubQuery() 把參數那一段塗掉，只留下能定位 bug 的 SQL：

export function scrubQuery(message: string): string {
  return message.replace(/\nparams: [\s\S]*/, '\nparams: [scrubbed]');
}

原則是：內部看得到的，保留能除錯的部分；外部看得到的，只給最少的資訊。log 本身也算「內部」，但因為 log 只要被匯出一次就不再是內部的，所以它也一起被塗掉。

回應預設不快取

最後一個小地方是 json() 這個回傳 helper。它做的事情很單純，但有一個關鍵設定：

export function json(data: unknown, status = 200) {
  return Response.json(data, {
    status,
    headers: { 'Cache-Control': 'no-store' },
  });
}

為什麼每一則回應都加上 no-store？因為這些回應都是「針對呼叫者」的：某個病人的預約、會過期的簽章附件網址。這種資料一旦被任何中間的快取存下來，就可能被下一個人拿到。對身分相關的回應來說，快取不是優化，而是風險，所以一律關掉。

小結

錯誤處理集中在 route() 一個地方：ApiError 轉成對應狀態碼的 JSON、ZodError 轉成 400、其他例外記到 Sentry 後回泛用的 500。code 欄位給程式判斷分支，狀態碼的意義固定。資料庫的 23P01 被翻譯成 409，500 不回傳內部細節並用 scrubQuery() 擋掉 PHI，json() 一律 no-store。判斷的原則是：把錯誤集中在一處翻譯，把內部資訊留在內部。

有了統一的錯誤語言，下一步是把「你是誰」也交給同一層守衛來判斷。下一節要看 requireAuth、requireStaff 與 requireOwnedPatient，以及為什麼身分只能從 session 推導、不能相信 client 傳來的任何 id。
