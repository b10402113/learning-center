route() 包裝與錯誤信封

Step 2/5 · Next.js API Route Handlers

學習目標

能說明 route() 如何把丟出的 ApiError 與 ZodError 收斂成一致的 JSON 回應，以及為什麼原始錯誤不能原封不動回給 client。

前言：錯誤一冒出去，就來不及了

上一節我們開出了第一個端點，也在每個 handler 外面套了 route()，但還沒有說它到底在幹嘛。先想像沒有它的世界：某個 handler 裡有一行從資料庫讀資料，如果那裡拋出例外，而你什麼都沒接住，這個例外會一路往上冒，最後變成一個 500。手機端看到的就是一個沒有格式、無法辨認的回應，使用者只會看到「Something went wrong」，你則在 log 裡翻半天還不知道是哪一步壞的。

更麻煩的是安全性。Drizzle 拋出的錯誤訊息長得像 Failed query: <SQL>\nparams: <綁定的值>，而綁定的值很可能就是病人的姓名、生日這類 PHI（受保護的健康資訊）。如果你把原始錯誤直接回給 client，等於把資料庫裡的資料從 API 漏出去。這一節要做的，就是給所有 handler 一套統一的錯誤處理：錯誤怎麼丟、怎麼被接住、最後長成什麼形狀，全部集中在一個地方決定。

先定義錯誤：ApiError 與它的家族

要統一處理錯誤，第一步是讓「預期中的錯誤」有個共同的型別。這個 app 定義了一個 ApiError，裡面帶著 HTTP 狀態碼、給人看的訊息，以及一個可選的錯誤代碼。訊息給人看，代碼給程式判斷，兩者分開是有原因的：之後手機要判斷「這是不是搶位失敗」，看的是穩定的代碼，而不是可能會改來改去的訊息文字。

/** Thrown anywhere below a route handler; `route()` turns it into a response. */
export class ApiError extends Error {
  constructor(
    readonly status: number,
    message: string,
    readonly code?: string
  ) {
    super(message);
  }
}

export const unauthorized = (m = 'Sign in required') => new ApiError(401, m);
export const forbidden = (m = 'Not allowed') => new ApiError(403, m);
export const notFound = (m = 'Not found') => new ApiError(404, m);
export const badRequest = (m: string) => new ApiError(400, m);
export const conflict = (m: string, code?: string) => new ApiError(409, m, code);

下面那排小函式是「快速丟錯」的糖。原本你可能要寫 throw new ApiError(404, 'Not found')，現在直接 throw notFound('Patient not found') 就好。這不只是少打幾個字，而是讓「401、403、404、409」這幾種常見狀態在整個專案裡有一致的預設訊息；像 conflict 還多收一個 code，因為 409 常常要帶「是哪一種衝突」。

這裡有個關鍵的分界線：ApiError 代表「我預期會發生的錯誤」，像是使用者沒登入、資料不存在、時間被搶走。至於「我不預期的錯誤」，像是資料庫連線斷了、程式有 bug，就讓它維持原樣。底下你會看到，wrapper 對這兩種的處理方式不同。

route() 的機制：一個 catch 管全部

有了共同的錯誤型別，包裝器就能用一個 try/catch 收斂所有情況。它的做法是把你的 handler 包進一個新函式，先執行原本的邏輯，出錯時再依錯誤種類決定回什麼。

/**
 * Wraps a route handler so thrown errors become clean JSON instead of a 500.
 * Keeps every handler down to its actual business logic.
 */
export function route<Args extends unknown[]>(
  fn: (...args: Args) => Promise<Response>
): (...args: Args) => Promise<Response> {
  return async (...args: Args) => {
    try {
      return await fn(...args);
    } catch (err) {
      if (err instanceof ApiError) {
        return Response.json({ error: err.message, code: err.code }, { status: err.status });
      }
      if (err instanceof ZodError) {
        return Response.json(
          { error: 'Invalid request', issues: err.issues.map((i) => ({ path: i.path, message: i.message })) },
          { status: 400 }
        );
      }
      …
      Sentry.captureException(err);
      …
      return Response.json({ error: 'Something went wrong' }, { status: 500 });
    }
  };
}

從上往下看，它處理三種情況。第一，如果丟出的是 ApiError，就把它翻成 { error, code }，狀態碼用錯誤自己帶的。第二，如果丟出的是 Zod 的驗證錯誤 ZodError（下一節的主角），就回一個固定的 400，並附上每個欄位哪裡不對。第三，其他沒預期到的錯誤，先送 Sentry、再寫一行 log，但回給 client 的訊息只有一句 Something went wrong，絕不夾帶原始內容。

注意那個 500 的分支。它刻意不把 err.message 放進回應，理由是註解寫得很直白：原始錯誤可能帶著 query text，而 query text 可能帶著 PHI。log 的那行雖然在伺服器內部，也一樣會被洗過，因為 log sink 只要多一個匯出，就已經不在邊界內了。

錯誤信封的形狀：手機只需要懂一套

這個 wrapper 最重要的產出，是「錯誤信封」的形狀固定下來。不管哪個端點出錯，手機收到的永遠是這幾種之一：

狀況HTTP 狀態回應內容
預期中的業務錯誤401／403／404／409…{ "error": "訊息", "code": "可選代碼" }
請求欄位不合法400{ "error": "Invalid request", "issues": [ … ] }
未預期的伺服器錯誤500{ "error": "Something went wrong" }

形狀一致這件事，讓手機端的錯誤處理只需要寫一次。它固定去讀 error 與 code，409 加 slot_taken 就顯示「這個時段剛剛被搶走了，換一個」；看到 issues 就把欄位錯誤標回表單。如果每個 handler 各自回不同的形狀，手機就得為每個端點客製一套解析，那才是真正的地獄。

補充一個容易忽略的細節：回應用的 json() 這個 helper 會固定加上 Cache-Control: no-store。原因是這些回應都是「身分專屬」的，你的預約、你的病歷、你的簽名檔網址，沒有任何一份可以共用或快取。把它設成不快取，是避免中間層或瀏覽器把某個人的資料留給下一個人。

export function json(data: unknown, status = 200) {
  // Every response from this helper is scoped to the caller — a patient's own
  // records, and signed attachment URLs that are identity-specific and expire.
  // Nothing here is shared, so nothing here is cacheable.
  return Response.json(data, { status, headers: { 'Cache-Control': 'no-store' } });
}

順手洗掉不該外流的資料

回頭補一個安全性小工具。前面提到 Drizzle 的錯誤訊息會把綁定的值一起印出來，而這些值可能是病人資料。這個 app 用一個 scrubQuery 把訊息裡 params: 之後的整段換掉，只留下能定位 bug 的 SQL 部分，把值丟掉。它同時用在兩個「錯誤會到達的終點」：Sentry 的事件與 console 的 log。

export function scrubQuery(message: string): string {
  return message.replace(/\nparams: [\s\S]*/, '\nparams: [scrubbed]');
}

另外還有一個 isExclusionViolation，專門辨認 Postgres 的排除約束違反（錯誤碼 23P01）。這正是「防重複預約」那道約束在資料庫層擋下人時會丟出的訊號，handler 收到它之後會轉成一個 409 的 conflict。這個函式我們到第 5 步走 booking handler 時會再遇到。

小結

route() 把每個 handler 包在一個 try/catch 裡，讓 handler 本體只留下商業邏輯。預期中的錯誤用 ApiError 家族丟出，會被翻成固定的 { error, code } 信封；Zod 驗證失敗回 400 加 issues；未預期的錯誤送 Sentry、寫洗過的 log，回給 client 只有一句 500。錯誤形狀統一，手機才只需要懂一套解析；原始錯誤不外流，PHI 才不會從錯誤訊息漏出去。

錯誤有了統一的出口，下一步要處理「誰可以進來」。如果身分判斷散落在每個 handler 裡，早晚會有人寫出「相信 client 傳來 userId」的漏洞。下一節把這條規則集中到守衛身上：requireAuth、requireStaff 與 requireOwnedPatient。
