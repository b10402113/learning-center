手機要的 API：Next.js Route Handler 入門

Step 1/5 · Next.js API Route Handlers

學習目標

能說明 Next.js Route Handler 是什麼、route.ts 檔案與 HTTP method 的對應規則，以及為什麼手機 app 必須透過一個 HTTP API 拿資料，而不是直接連你的資料庫。

前言：手機不在你的 server 裡

你在員工 dashboard 上寫了一個 Server Component，它直接 import 資料庫、下 Drizzle 查詢，把結果畫成表格。這一切之所以行得通，是因為那段程式碼就在伺服器上跑，資料庫連線字串從來沒有離開過伺服器。

把手機 app 放進來，情況就變了。手機是放在使用者口袋裡的另一台電腦，它跟你的伺服器之間隔著網路，也不可能拿到你的 Postgres 密碼。你真正需要的，是一個雙方講好格式的窗口：手機送出一段請求，伺服器檢查身分、執行商業邏輯、再回一段資料。

這個窗口就是接下來五節的主角。這一節先把它的形狀講清楚，後面幾節再一層一層加上錯誤處理、權限與型別。

Route Handler 就是一個資料夾裡的函式

在 Next.js 的 App Router 裡，只要你在 app/api 底下開一個資料夾，放進一個名為 route.ts 的檔案，它就變成一個端點。檔案路徑決定網址，檔案裡匯出的函式名稱決定它接哪一種 HTTP method。

apps/web/src/app/api/
  appointments/
    route.ts        → /api/appointments
    [id]/
      route.ts      → /api/appointments/:id
  availability/
    route.ts        → /api/availability
  me/
    route.ts        → /api/me
  webhooks/
    clerk/
      route.ts      → /api/webhooks/clerk

打開 appointments/route.ts，最上面是匯入，接著你會看到兩個模組層級的匯出：export const GET 與 export const POST。Next.js 就是靠這兩個名字，把進來的 GET 和 POST 請求分派到對應的函式。要再加一個刪除端點，就再匯出一個 DELETE，不需要另外註冊路由。

函式的簽章用的是標準 Web API：收一個 Request，回一個 Response（或它的 Promise）。你不用學 Next.js 專屬的請求物件，因為它就是瀏覽器 fetch 背後那一套。例如讀查詢字串會這樣寫：

export const GET = route(async (req: Request) => {
  const scope = new URL(req.url).searchParams.get('scope') === 'past'
    ? 'past'
    : 'upcoming';
  // ...
});

這一段外層還套了 route() 包裝，下一節會專門講它。現在只要先認出三件事：檔案路徑對應網址、匯出函式名稱對應 method、參數是標準的 Request。

為什麼手機不能自己連資料庫

既然你是全端工程師，可能會想：「資料庫就在那裡，為什麼不讓手機直接查？」這個念頭要立刻打消，原因有三個。

第一是憑證。手機 app 會被打包、上架、被使用者下載，任何寫進 app 的字串都可能被挖出來。把資料庫連線字串放進去，等於把整間診所的資料鑰匙公開。第二是網路與環境。手機可能處在不穩定的行動網路上，而 Postgres 的連線池與協定也不是設計來讓成千上萬支手機直接連的。第三，也是最重要的，是商業邏輯與權限。誰能看哪一筆預約、能不能取消、算不算重複預約，這些規則必須由你掌控的伺服器執行，不能交給使用者手上的裝置。

打個比方：資料庫像醫院的病歷室，Route Handler 像櫃檯。病人不會自己走進病歷室翻抽屜，而是到櫃檯說明需求，由櫃檯核對身分、判斷你有沒有權限，再把需要的那一份拿出來。手機唯一能對話的對象是櫃檯，不是病歷室。

同一支 web app，身兼三種角色

在這個架構裡，apps/web 這個 Next.js 專案同時是三個東西：員工用的 dashboard、手機 app 呼叫的 API，以及第三方服務打進來的 webhook 入口。它們共用一份程式碼、一個資料庫連線、一次部署。

這件事最大的好處是商業邏輯只有一份。手機要的預約資料怎麼算、能不能取消，跟 dashboard 上看到的其實是同一套規則；差別只在 dashboard 用 Server Component 直接讀，手機走 HTTP。把兩者放在同一個 repo，就不會出現「網頁版本已經修好、手機版本還在用舊規則」這種漂移。

Route Handler 和 Server Component 的差別

兩者都在伺服器上執行，都能碰到資料庫，差別在「誰在呼叫他」。

Server ComponentRoute Handler
誰觸發頁面 render 時，伺服器自己呼叫任何外部 client 發 HTTP 請求
回傳什麼HTML 與元件的輸出JSON 或任何 HTTP response
典型用途網頁 dashboard 直接讀 Drizzle給手機 app、給第三方 webhook 的 API
能否被手機呼叫不行，它不是一個端點可以，這正是它存在的理由

所以判準很簡單：如果這段資料只有你自己的網頁要用，寫成 Server Component 最省事；只要有一個不在你伺服器裡的 client（手機、另一個服務、別人的系統）需要拿到它，就得開一個 Route Handler。手機 app 完全屬於後者。

端點是照資源切的

實際的 API 不是憑感覺命名，而是照「資源」分檔。課程裡的診所後端，app/api 底下有：appointments（預約的列表與新增）、availability（可預約時段）、dentists 與 services（可選的醫師與療程）、patients（家人檔案與病歷）、me（目前登入者）、ai/chat（助理對話）、stream（視訊 token）、webhooks/clerk（身分同步）。每個資料夾是一組資源，而 [id] 這種帶中括號的資料夾代表動態片段，用來指向某一筆特定資料。

拿到一支端點時，先問「它是哪個資源、要做什麼動作」，通常就能推出網址與 method。列表與查詢用 GET，建立用 POST，部分更新用 PATCH，刪除用 DELETE。

小結

Route Handler 是 app/api 底下的一個 route.ts 檔，用匯出的函式名稱對應 HTTP method，用標準 Request 與 Response 收送資料。手機不能直接連資料庫（憑證、網路、權限都不允許），所以需要這層 HTTP API；同一支 Next.js app 同時服務 dashboard、手機與 webhook，邏輯只寫一份。判斷該不該開端點，就看有沒有一個不在你伺服器上的 client 需要這筆資料。

現在你已經有了「端點長什麼樣」的地基。但一個 endpoint 如果每次出錯都直接噴一個 500，手機根本不知道發生什麼事、該不該重試。下一節要處理的就是這件事：用 route() 包裝與統一的錯誤信封，把每一種失敗都翻譯成手機看得懂的 JSON。
