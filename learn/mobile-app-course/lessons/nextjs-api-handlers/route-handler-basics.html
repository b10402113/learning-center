手機怎麼拿到資料？從 Next.js Route Handler 認識 API

Step 1/5 · Next.js API Route Handlers

先看全貌：手機和資料庫之間，少不了一扇門

想像你的診所 app 要顯示「今天的預約」。在 dashboard 裡，資料似乎很容易出現：頁面程式碼和資料庫都在同一台伺服器、同一個執行環境裡，程式可以直接呼叫資料庫，像在同一個房間裡伸手拿東西。

手機 app 卻在使用者的口袋裡，和你的伺服器隔著整個網際網路。它沒有你的 server 程式碼，也不能直接碰你的資料庫。手機能做的事，是送出 HTTP 請求；伺服器則回傳 HTTP 回應。

因此，手機和資料庫之間需要一扇門：手機把請求送到這扇門，server 在門內查詢資料，再把結果整理成手機看得懂的回應。Next.js 的 Route Handler，就是用來建立這扇門的入口。

如果沒有這層 API，手機只能把資料硬寫在 app 裡。資料一改，就得重新上架；而且每個使用者看到的內容都會一樣。這個課程先從硬寫資料的版本開始，後來再用一個 prompt「把整個 app 接上已經做好的 web 和 API routes」，一次修改二十幾個檔案，讓手機真正顯示 server 上的資料。這一步的核心很單純：讓手機用 HTTP 說話，讓 server 有地方可以接住它。

這一節要建立的觀念

讀完後，你應該能辨認三件事：Route Handler 放在哪裡、檔案怎麼對應到網址，以及不同的 HTTP method 要怎麼匯出。你也要能說明，為什麼手機不能像 dashboard 一樣直接讀資料庫。

Route Handler 是什麼：網址與方法的對應表

在 Next.js 的 App Router 裡，Route Handler 是一個放在 app/api 底下、名稱為 route.ts 的檔案。它會對應到一個 API 端點。

可以把資料夾結構想成一張地址地圖：檔案放在哪個資料夾，就決定 API 的網址長什麼樣子。

apps/web/src/app/api/
├── services/route.ts              →  GET /api/services
├── availability/route.ts          →  GET /api/availability
├── appointments/route.ts          →  GET、POST /api/appointments
└── appointments/[id]/route.ts     →  GET、PATCH /api/appointments/:id

檔案裡匯出的名稱，則決定它接受哪一種 HTTP method。匯出 export const GET，代表端點接受 GET；匯出 export const POST，代表端點接受 POST。同一個 route.ts 可以匯出多個 method，因此同一個網址可以分別處理查詢與建立資料。

像 [id] 這種用方括號包起來的資料夾，代表動態區段。實際的 id 會從網址傳進來，所以 /api/appointments/123 可以對應到 /api/appointments/[id]/route.ts。

這裡還有一個值得記住的邊界：handler 不需要 import Next.js 專屬的 Request 或 Response。它收到的 Request 和回傳的 Response，都是瀏覽器與 Node 都認得的標準 Web 物件。也就是說，這套 handler 的基本骨架不會完全綁死在 Next.js 上，未來更換框架時，大部分概念仍然可以沿用。

一個最簡單的 handler：三件事完成一次查詢

先看服務清單這個端點。它的工作很集中：先確認使用者已登入，再從資料庫撈出仍在啟用中的服務，最後把結果包成 JSON 回傳。

import { asc, eq } from 'drizzle-orm';

import { db } from '@/db';
import { services } from '@/db/schema';
import { requireAuth } from '@/lib/auth';
import { json, route } from '@/lib/http';

/** Drives the booking "reason" picker and onboarding step 3. */
export const GET = route(async () => {
  await requireAuth();
  const rows = await db
    .select()
    .from(services)
    .where(eq(services.isActive, true))
    .orderBy(asc(services.name));
  return json({ services: rows });
});

這段程式裡有兩個之後會反覆出現的角色。requireAuth() 是守衛，負責確認呼叫者的身分；如果沒有登入，就會擋下請求。route(...) 是包裝器，負責把 handler 裡發生的錯誤整理成乾淨的 JSON，而不是讓錯誤一路冒出去，最後只剩一個難以理解的 500。

現在先不用急著深入這兩個工具的內部實作。先建立一個閱讀 handler 的習慣：外層通常會套上 route()，內容一開始通常會先經過身分驗證，接著才執行資料庫查詢或其他商業邏輯。

同一個端點，也可以處理不同方法

再看預約端點。它和服務清單不同，同一個檔案同時支援 GET 與 POST。GET 用來列出整個家庭的預約；POST 則用來真正建立一筆預約。

/** GET /api/appointments?scope=upcoming|past — across the whole family. */
export const GET = route(async (req: Request) => {
  …
});

/**
 * The aha moment. The server computes ends_at from the service duration and
 * lets the Postgres exclusion constraint decide the race — a violation becomes
 * a clean 409 the app shows as "just taken, pick another".
 */
export const POST = route(async (req: Request) => {
  …
});

GET 的查詢範圍也可以放在網址的 Query 參數裡。例如 ?scope=past 會被從 req.url 解析出來，用來決定要查過去的預約，還是未來的預約。

這裡再次看見標準 Web API 的好處：你直接從 Request 讀取網址，不必另外學一套框架專用的參數取出方式。Route Handler 就像一個翻譯站，負責把手機送來的 HTTP 請求，接到 server 既有的資料與邏輯上。

弱做法：讓手機直接讀資料庫

你可能會想：既然 dashboard 可以直接讀資料庫，手機為什麼不行？第一個原因是實際上的連線限制——手機不在你的 server 裡，根本不能像 Server Component 一樣直接呼叫資料庫。

第二個原因更重要：安全性。資料庫連線字串等於整個資料庫的鑰匙。如果把它放進手機 app，就等於把鑰匙發給每一個下載 app 的人。只要有人反編譯 app，就可能把這把鑰匙拿走。

所以，讓手機直接連資料庫是弱做法；把資料庫留在 server，由 Route Handler 代為查詢並回傳必要資料，才是較安全、也更容易控制的分工。

比較Server Component（dashboard）Route Handler（手機用）
執行位置你的伺服器，與 DB 同一台你的伺服器，手機透過網路呼叫
怎麼拿資料直接呼叫 Drizzle，不繞 HTTP由 handler 查 DB，再把結果回傳
身分驗證由 layout 的守衛負責每個 handler 自己呼叫守衛
回傳形式直接產生 HTML回傳 JSON 或串流

在這個 app 裡，兩種入口各自負責不同的工作：dashboard 使用 Server Component，直接讀取資料庫；手機則呼叫 Route Handler，透過 API 取得 JSON。至於「這筆預約能不能取消」這類商業邏輯，只寫一份，放在 lib 裡讓兩邊共用。

這個安排很像把交通規則放在同一份法規裡，而不是讓兩個城市各自抄一份。入口可以不同，但判斷規則必須一致，才不會因為 dashboard 和手機各寫一次，最後產生兩套互相矛盾的結果。

Route Handler 應該掛在哪裡？

Route Handler 就是 app/api 底下的一組檔案：資料夾路徑決定網址，匯出的名稱（GET、POST、PATCH）決定接受的 HTTP method，而收送的 Request／Response 都是標準 Web 物件。手機不在伺服器裡，唯一能碰到資料的方式就是呼叫這些 HTTP 端點；把資料庫的鑰匙留在 server 端，正是這層 API 存在的主要理由。

現在可以把這個觀念和前面的 app 分工接起來：Server Component 適合在 server 內部直接拿資料；手機則需要一個對外的 HTTP 入口。Route Handler 就是這個入口，不是另一套資料庫，也不是把商業邏輯重寫一次，而是把 server 裡的資料與規則，以手機能理解的方式送出去。

不過，入口開出來只是第一關。假設 requireAuth() 發現使用者沒有登入，它丟出一個錯誤之後，這個錯誤要怎麼回到手機？如果直接讓錯誤冒出去，使用者可能只收到看不懂的 500，甚至看到資料庫的原始錯誤訊息。下一步會處理這個邊界：用 route() 把錯誤統一包成一致的 JSON 信封。
