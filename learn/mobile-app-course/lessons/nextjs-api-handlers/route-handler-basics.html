手機要的 API：Next.js Route Handler 入門

Step 1/5 · Next.js API Route Handlers

學習目標

能說出 Route Handler 的檔案位置與 HTTP method 匯出慣例，並解釋手機為什麼只能透過 HTTP API 拿到資料。

前言：手機不在你的 server 裡

先想一個很日常的場景。你的診所後台 dashboard 要顯示「今天的預約」，你打開頁面，資料就出來了。這很自然，因為 dashboard 的程式碼和資料庫跑在同一台伺服器、同一個行程裡，它可以直接伸手去資料庫拿資料，中間不用繞路。

但手機 app 完全不是這樣。手機在使用者的口袋裡，跟你隔著整個網際網路。它沒有你的程式碼，也碰不到你的資料庫，它唯一會講的語言就是 HTTP。所以「手機要顯示今天有誰預約」這件事，實際上是手機送出一段 HTTP 請求、你的伺服器回一段 HTTP 回應。這一節要做的，就是蓋出那個伺服器端的入口：Next.js 的 Route Handlers。

如果沒有這層入口，手機就只能把資料硬寫在程式碼裡，改一次要重新上架一次，而且每個使用者看到的都一樣。課程裡就是先做出這種硬寫資料的版本，後來才用一個 prompt「把整個 app 接上已經做好的 web 和 API routes」，一次改了二十幾個檔案，手機才開始顯示真的資料。這一步只是要讓「手機說 HTTP，server 聽得懂」這件事成立。

Route Handler 是什麼：網址與方法的對應表

Route Handler 說穿了很樸素。在 Next.js 的 App Router 裡，你把一個叫 route.ts 的檔案放在 app/api 底下，它對應到的就是一個 API 端點。檔案放在哪個資料夾，就決定網址長什麼樣子。

apps/web/src/app/api/
├── services/route.ts              →  GET /api/services
├── availability/route.ts          →  GET /api/availability
├── appointments/route.ts          →  GET、POST /api/appointments
└── appointments/[id]/route.ts     →  GET、PATCH /api/appointments/:id

最關鍵的慣例是：檔案裡「匯出什麼名字」，就對應到「哪個 HTTP method」。你寫 export const GET，這個端點就接受 GET；寫 export const POST，就接受 POST。同一個檔案可以同時匯出好幾個，也就是一個端點可以支援多種方法，各自處理不同的事。方括號的資料夾像是 [id] 代表動態區段，實際的 id 會從網址傳進來。

還有一個心態要換掉：這裡不 import 任何 Next.js 專屬的東西。handler 收到的 Request 和回出去的 Response，都是瀏覽器、Node 都認得的標準 Web 物件。所以同一套寫法不會綁死在 Next.js 上，你之後換框架，這些 handler 的骨架大部分可以整段帶走。

一個最簡單的 handler 長什麼樣子

先看一個幾乎沒有邏輯的端點，服務清單。它做的事只有三件：確認呼叫的人有登入、從資料庫撈出還啟用中的服務、把結果包成 JSON 回傳。

import { asc, eq } from 'drizzle-orm';

import { db } from '@/db';
import { services } from '@/db/schema';
import { requireAuth } from '@/lib/auth';
import { json, route } from '@/lib/http';

/** Drives the booking "reason" picker and onboarding step 3. */
export const GET = route(async () => {
  await requireAuth();
  const rows = await db
    .select()
    .from(services)
    .where(eq(services.isActive, true))
    .orderBy(asc(services.name));
  return json({ services: rows });
});

這裡有兩個之後會一直被用到的名字。requireAuth() 是守衛，負責確認身分，沒有登入就當場擋掉（第 3 步會細講）。route(...) 是包裝器，把整個 handler 包起來，讓裡面丟出的錯誤最後會變成乾淨的 JSON，而不是一團 500（第 2 步會細講）。現在你只要先記得：每個 handler 外面幾乎都套著 route()，裡面開頭幾乎都先呼叫一個守衛。

再對照一個支援多個方法的端點。預約端點同一個檔案裡就有 GET 和 POST，GET 負責列出全家人的預約，POST 負責真正建立一筆預約。

/** GET /api/appointments?scope=upcoming|past — across the whole family. */
export const GET = route(async (req: Request) => {
  …
});

/**
 * The aha moment. The server computes ends_at from the service duration and
 * lets the Postgres exclusion constraint decide the race — a violation becomes
 * a clean 409 the app shows as "just taken, pick another".
 */
export const POST = route(async (req: Request) => {
  …
});

看到 Query 參數也是從 req.url 自己解析，例如 GET 會把 ?scope=past 讀出來決定要抓過去還是未來的預約。這也是標準 Web API 的好處：你不需要學一套框架專屬的參數取出方法。

為什麼不讓手機直接讀資料庫就好？

你可能會想，既然 dashboard 可以直接讀資料庫，為什麼不讓手機也這樣？除了「手機根本連不到你的資料庫」這個物理限制外，還有一個安全理由：資料庫連線字串等於整個資料庫的鑰匙。把它放進手機 app，等於把鑰匙發給每一個下載 app 的人，任何人反編譯就能拿走。

比較Server Component（dashboard）Route Handler（手機用）
執行位置你的伺服器，與 DB 同一台你的伺服器，手機透過網路呼叫
怎麼拿資料直接呼叫 Drizzle，不繞 HTTP由 handler 查 DB，再把結果回傳
身分驗證由 layout 的守衛負責每個 handler 自己呼叫守衛
回傳形式直接產生 HTML回傳 JSON 或串流

所以這個 app 的分工很明確：dashboard 走 Server Component 直讀資料庫，手機走 Route Handler 打 API，而商業邏輯（例如「這筆預約可不可以取消」）只寫一份，放在 lib 裡，兩邊共用。這樣同一條規則不會因為兩個入口而各寫一次、慢慢走鐘。

小結

Route Handler 就是 app/api 底下的一組檔案，資料夾路徑決定網址，匯出的名字（GET、POST、PATCH）決定接受的 HTTP method，收送的 Request／Response 都是標準 Web 物件。手機不在伺服器裡，唯一能碰資料的方式就是打這些 HTTP 端點；而把資料庫鑰匙留在 server 端，正是這層 API 存在的主要理由。

現在你知道怎麼開一個端點了，但端點開著就會出事。假設 requireAuth() 發現你沒登入，它丟出一個錯誤，然後呢？如果就這樣讓它冒出去，使用者會收到一個看不懂的 500，甚至可能夾帶資料庫的原始錯誤訊息。下一步要把這件事收乾淨：用 route() 把錯誤統一變成一致的 JSON 信封。
