Zod 請求邊界：不要相信 client 傳來的關鍵欄位

Step 4/5 · Next.js API Route Handlers

先想像一個沒有門的 API

一個 booking 端點收到請求時，不能只因為程式碼裡寫了 TypeScript 型別，就假設 client 傳來的資料一定正確。請求可能帶著錯誤格式、過大的數值，甚至是刻意操控安全與商業結果的欄位。

這一課要把 API 入口想成一道城門：先確認資料長得像不像合法請求，再把身分、所有權與商業規則交給各自負責的機制處理。你會看到 Zod 驗證什麼，也會分清楚哪些欄位即使 client 傳來了，server 也不該相信。

學習目標

學完後，你應該能說明 Zod 在 handler 入口驗證的內容，以及哪些關鍵欄位必須由 server 自己推導，不能交給 client 決定。

為什麼 TypeScript 型別不夠？

很多使用 TypeScript 的人會有一種錯覺：既然已經定義了型別，client 傳來的東西應該就會符合那個型別。但這件事在 runtime 完全不成立。

TypeScript 的型別在編譯之後會被移除。HTTP 請求進入 handler 時，內容只是一份可能包含任何 JSON 的資料。你在編輯器裡寫 body.patientId 時能得到自動補齊，只代表編譯器相信你的宣告，不代表 runtime 真的檢查過這個欄位。

假設 booking 端點沒有驗證。有人送來 durationMinutes: 9999，或把 startsAt 塞成 "昨天"，這些值就可能一路穿過 handler，最後進入資料庫。運氣好只是留下髒資料，運氣不好則會讓查詢直接失敗。

更麻煩的是，有些欄位看起來完全合法，卻不應該由 client 決定。client 如果能自行指定療程長度，就可能預約一整天；如果能自行指定通話 id，就可能嘗試混進別人的通話。

因此，handler 一開始需要一道城門，先回答：「這份請求是否符合我定義的合約？」這道門就是 Zod。

Zod 在入口檢查的是什麼？

這個 app 將請求合約集中放在 lib/validation.ts，每個 schema 對應一組端點。做法不是在 handler 裡手寫一大串 if (!body.patientId) ...，而是先宣告一份「合法資料應該長什麼樣子」的規則，再在入口用 parse 檢查。

先看建立預約的合約：

export const createAppointmentSchema = z.object({
  patientId: z.string().uuid(),
  serviceId: z.string().uuid(),
  dentistId: z.string().uuid(),
  /** The client never sends a duration — the server derives ends_at. */
  startsAt: z.string().datetime({ offset: true }),
});

這幾行定義了四件事。

  • 四個欄位都必須存在。
  • patientId、serviceId 與 dentistId 必須是合法的 UUID（通用唯一識別碼），不能隨便塞一段字串。
  • startsAt 必須是帶有時區偏移的 ISO 時間字串，例如 2026-10-03T14:30:00+08:00。
  • client 不會送 duration；預約的結束時間由 server 自己推導。

最後一點尤其重要。schema 不只是在檢查「client 送了什麼」，也在明確界定「client 不可以決定什麼」。

schema 定義「允許什麼」，不代表「相信什麼」

驗證常被簡化成「確認資料對不對」，但實際上，schema 主要回答的是：「欄位存在嗎？格式正確嗎？」它不負責判斷這個值在目前情境下是否真的合理。

例如，patientId 是合法 UUID，不代表這位病人就屬於目前登入的帳號；serviceId 是合法 UUID，也不代表這項服務目前仍在啟用。格式合法與內容正確，是兩件不同的事。

因此，這個 app 把責任分開：Zod 負責入口資料的形狀，後面的守衛與商業邏輯負責更深一層的正確性。handler 執行 parse 之後，仍然要呼叫 requireOwnedPatient() 確認所有權，也要查詢 service 與 dentist 是否啟用。

驗證通過比較像拿到入場券，而不是代表整筆交易已經合法。

要確認的問題負責的機制例子
欄位存在嗎？格式正確嗎？Zod schemapatientId 是不是 UUID、startsAt 是不是帶時區的時間
這個人是誰？他能碰這筆資料嗎？守衛（requireOwnedPatient）這位病人是否屬於目前帳號
這筆交易合不合理？商業邏輯（booking）這個時段是否真的可以預約

關鍵欄位一律由 server 推導

除了檢查輸入格式，還有一項更嚴格的紀律：任何會影響安全或商業結果的欄位，都不讓 client 決定。

建立預約時，client 只送 startsAt。結束時間則由 server 根據服務本身的長度計算。通話 id 也不是由 client 傳入，而是等預約建立後，使用預約編號組合出來。

  const startsAt = new Date(body.startsAt);
  const endsAt = new Date(startsAt.getTime() + service.durationMinutes * 60_000);

這樣做的理由很直接：只要欄位交給 client 決定，就多了一個需要防守的破口。

如果 duration 可以由 client 傳入，他就能宣稱自己的療程長達 30 個小時。如果 streamCallId 可以由 client 傳入，他就能嘗試指定要加入別人的視訊。把這些值收回 server 自己計算，client 就算惡意，也沒有對應的欄位可以填。

用 discriminatedUnion 表達互斥的操作

取消與改期是另一個很適合用 schema 表達的例子。這兩個動作需要的輸入不同：

  • 取消只需要動作名稱。
  • 改期除了動作名稱，還需要新的時間，也可以選擇新的牙醫。

如果把兩種操作硬塞進一個寬鬆的 schema，就可能出現「取消卻帶著 startsAt」這類矛盾輸入。這個 app 使用 discriminatedUnion，也就是可辨識聯合，以 action 作為判別鍵，分出兩份互斥的合約。

export const patchAppointmentSchema = z.discriminatedUnion('action', [
  z.object({ action: z.literal('cancel') }),
  z.object({
    action: z.literal('reschedule'),
    startsAt: z.string().datetime({ offset: true }),
    dentistId: z.string().uuid().optional(),
  }),
]);

解析之後，這份資料在 TypeScript 裡會自動縮窄成兩條分支之一。當 handler 判斷 body.action === 'reschedule' 時，編譯器就知道 body.startsAt 一定存在，不需要再補一輪檢查。

這是一個小而實用的設計：讓合法狀態清楚地被表達，也讓矛盾的輸入更早被排除。取消請求不會和改期欄位混在一起，改期請求則不會忘記必要的時間。

驗證錯誤如何變成 API 回應？

Zod 的 parse 失敗時會丟出 ZodError。回想上一節，route() 會接住這個錯誤，轉成附帶 issues 陣列的 400 回應。

因此，handler 不需要為每個欄位各寫一套錯誤處理。只要在入口執行 parse，驗證失敗就能透過既有的 route()，轉成手機端看得懂的格式。

把觀念掛回整體架構

TypeScript 的型別在 runtime 不存在，請求 body 進入 handler 時只是一份 JSON。Zod 在入口使用 parse 檢查資料形狀，包括欄位是否存在、格式是否合法；失敗時丟出 ZodError，再由 route() 轉成 400。

但格式合法不等於內容正確。所有權由守衛確認，交易是否合理則交給商業邏輯判斷。時間長度、通話 id 這類關鍵欄位，一律由 server 自己推導，client 即使想送，也沒有對應的欄位可以控制。discriminatedUnion 則讓互斥操作各自擁有清楚的合約，避免矛盾輸入混在一起。
