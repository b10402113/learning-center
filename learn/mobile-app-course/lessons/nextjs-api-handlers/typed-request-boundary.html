Zod 請求邊界：不信任 client 傳來的欄位

Step 4/5 · Next.js API Route Handlers

學習目標

能說出 Zod 在 handler 入口驗證了什麼，以及哪些關鍵欄位必須由 server 自己推導、不能相信 client。

前言：型別檢查救不了執行中的請求

很多寫 TypeScript 的人會有一種錯覺：既然我定義了型別，client 傳來的東西應該就是那個型別吧。但這件事在 runtime 完全不成立。TypeScript 的型別在編譯之後就被抹掉了，HTTP 請求進到 handler 時只是一個字串，裡面可能是任何 JSON。你在編輯器裡寫 body.patientId 能自動補齊，純粹是因為編譯器相信你，不是因為 runtime 檢查過。

假設 booking 端點少了驗證。有人送來一個 durationMinutes: 9999，或把 startsAt 塞成 "昨天"，這些值會一路穿過 handler 進到資料庫，運氣好就是髒資料，運氣不好就是查詢直接爆掉。更陰險的是那種「看起來合法」的欄位：如果 client 自己決定療程長度，他就能預約一整天；如果 client 自己決定通話 id，他就能混進別人的通話。

所以 handler 的一開頭需要一道城門，負責回答一個問題：「這個請求的內容，有符合我定義的合約嗎？」這道門就是 Zod。

Zod 在入口做的事：parse 一個物件

這個 app 把所有請求的合約集中放在 lib/validation.ts，每個 schema 對應一組端點。它們的做法不是手寫一堆 if (!body.patientId) ...，而是宣告一份「合法長相」，然後在入口用 parse 檢查。先看建立預約的合約。

export const createAppointmentSchema = z.object({
  patientId: z.string().uuid(),
  serviceId: z.string().uuid(),
  dentistId: z.string().uuid(),
  /** The client never sends a duration — the server derives ends_at. */
  startsAt: z.string().datetime({ offset: true }),
});

短短幾行，卻定義了四件事。第一，這四個欄位都必須存在。第二，前三個必須是合法的 UUID（通用唯一識別碼），隨便塞字串會被擋。第三，startsAt 必須是帶時區偏移的 ISO 時間字串，像 2026-10-03T14:30:00+08:00。第四，也是最有意思的一行：註解直接寫明「client 永遠不送 duration，結束時間由 server 推導」。這行註解在講的，就是下一段的觀念。

schema 是「允許什麼」，不是「相信什麼」

很多人把驗證想成「確認資料對不對」。但其實驗證只回答「這個欄位存不存在、格式對不對」，它沒有回答「這個值是不是合理的」。舉例來說，patientId 是合法 UUID，不代表這筆病人屬於你；serviceId 是合法 UUID，不代表這個服務還在啟用中。格式合法跟內容正確，是兩件不同的事。

因此這個 app 的規則是：Zod 只管入口的形狀，真正的正確性檢查交給後面的守衛與商業邏輯。這也是為什麼 handler 在 parse 之後，還要再呼叫 requireOwnedPatient() 確認所有權、查一次 service 與 dentist 是否啟用。驗證通過只是拿到「入場券」，不代表這筆交易合法。

問題誰負責例子
欄位存在嗎？格式對嗎？Zod schemapatientId 是不是 UUID、startsAt 是不是帶時區的時間
這個人是誰？能碰這筆資料嗎？守衛（requireOwnedPatient）這筆病人屬不屬於當前帳號
這筆交易合不合理？商業邏輯（booking）這個時段是不是真的可供預約

關鍵欄位一律由 server 推導

驗證之外，還有一個更強的紀律：不讓 client 決定任何會影響安全或商業結果的欄位，即使它能送，我們也不理它。最清楚的例子是時間長度與通話 id。client 送的是 startsAt，但結束時間由 server 用服務本身的長度算出來，通話 id 則由建立後的預約編號組出來，client 從頭到尾碰不到這兩個值。

  const startsAt = new Date(body.startsAt);
  const endsAt = new Date(startsAt.getTime() + service.durationMinutes * 60_000);

為什麼要這麼堅持？因為只要有一個欄位由 client 決定，你就多了一個要防守的破口。如果 duration 讓 client 送，他就能宣稱自己的療程是 30 個小時；如果 streamCallId 讓 client 送，他就能指定要加入哪一通別人的視訊。把這些值收回 server 自己算，client 就算惡意也無從下手，因為他根本沒有對應的欄位可以填。

用 discriminatedUnion 表達「兩種互斥的操作」

還有一個很實用的技巧，出現在取消與改期的端點。這兩個動作的輸入完全不同：取消只需要一個動作名稱，改期除了動作名稱還需要新的時間。硬把它們塞進同一個寬鬆 schema，會出現「取消卻帶著 startsAt」這種矛盾輸入。這個 app 的解法是用「可辨識聯合」（discriminated union）：以 action 欄位為判別鍵，分出兩條互斥的合約。

export const patchAppointmentSchema = z.discriminatedUnion('action', [
  z.object({ action: z.literal('cancel') }),
  z.object({
    action: z.literal('reschedule'),
    startsAt: z.string().datetime({ offset: true }),
    dentistId: z.string().uuid().optional(),
  }),
]);

這樣一來，解析出來的值在 TypeScript 裡會自動縮窄成兩條分支之一。handler 判斷 body.action === 'reschedule' 之後，編譯器就知道 body.startsAt 一定存在，不需要再多做檢查。這是「讓合法的狀態無法被表達錯誤」的一個小例子：錯誤的輸入在型別層就進不來。

順帶一提，Zod 的 parse 失敗時丟的是 ZodError。回想上一節：route() 正好會接住它，轉成一個附帶 issues 陣列的 400。也就是說，驗證失敗不需要在 handler 裡寫任何處理，只要在入口 parse，錯誤就會自動變成手機看得懂的格式。

小結

TypeScript 的型別在 runtime 不存在，請求 body 進到 handler 時只是 JSON。Zod 在入口用 parse 檢查形狀（欄位是否存在、格式是否合法），失敗時丟出 ZodError，由 route() 轉成 400。但格式合法不等於內容正確：所有權交給守衛，合理性交給商業邏輯。而時間長度、通話 id 這類關鍵欄位，一律由 server 自己推導，client 就算想送也沒有欄位可以送。discriminatedUnion 則讓互斥的操作各有一份合約，矛盾輸入在型別層就進不來。

現在四個零件都到齊了：Route Handler 的骨架、route() 的錯誤信封、身分與所有權守衛、Zod 的請求邊界。最後一步要把它們組起來，完整走一遍 POST /api/appointments，看看真實的預約寫入是怎麼把這些零件串在一起的。
