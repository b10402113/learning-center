Zod 請求邊界：不信任 client 傳來的欄位

Step 4/5 · Next.js API Route Handlers

學習目標

能用 Zod schema 在 handler 入口擋掉不合法的輸入，並說明為什麼像服務長度、通話 id 這類欄位要由伺服器推導，而不是讓 client 傳。

前言：TypeScript 的型別到了 runtime 就消失了

你寫了一個 interface CreateAppointment，TypeScript 會在編譯時幫你檢查形狀。但請求是從網路進來的，那段 JSON 在 runtime 完全不受型別約束。手機可以送出少一個欄位的物件、把 uuid 換成一段亂碼、或故意塞一個超大的數字。TypeScript 的型別在這裡幫不上忙，因為它根本不存在於執行中的伺服器記憶體裡。

換句話說，req.json() 拿到的東西，在驗證之前都只是「未知」。這一節要看的是：如何在 handler 的第一行，把這團未知變成可信任的型別。

把 schema 當成入口的城門

這支 API 把所有請求的形狀集中在 lib/validation.ts，用 Zod 定義。Zod 是一套「執行時」的驗證工具：它產生的 schema 物件同時是驗證器與型別來源。handler 在拿到 body 後，第一件事就是 parse：

export const POST = route(async (req: Request) => {
  const user = await requireAuth();
  const body = createAppointmentSchema.parse(await req.json());
  // 到這裡，body 已經是通過驗證的型別
  // ...
});

parse 成功時，它回傳一個被轉換、被信任的物件；失敗時，它丟出 ZodError。上一節的 route() 包裝認得這個錯誤型別，會自動把它轉成 400，並附上每個欄位錯在哪裡。所以 handler 本身不需要寫任何「檢查有沒有缺欄位」的 if。

以建立預約的 schema 為例，它規定三個必填的 uuid 與一個帶時區的 ISO 時間字串：

export const createAppointmentSchema = z.object({
  patientId: z.string().uuid(),
  serviceId: z.string().uuid(),
  dentistId: z.string().uuid(),
  /** client 不送 duration，ends_at 由伺服器自己算 */
  startsAt: z.string().datetime({ offset: true }),
});

查詢參數一樣要驗。可預約時段的端點收 serviceId、選填的 dentistId，以及兩個日期：

export const availabilityQuerySchema = z.object({
  serviceId: z.string().uuid(),
  dentistId: z.string().uuid().optional(),
  from: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
  to:   z.string().regex(/^\d{4}-\d{2}-\d{2}$/).optional(),
});

同一個端點、兩種動作：discriminatedUnion

預約的 PATCH 可以「取消」也可以「改期」，兩者需要的欄位不同：取消不用帶時間，改期要帶新的時間。用一個寬鬆的物件、把所有欄位都設成 optional，會讓「取消卻帶了時間」這種矛盾狀態通過驗證。

比較嚴謹的做法是用 z.discriminatedUnion，以一個共同的 action 欄位當判別鍵，只有對應的分支會被接受：

export const patchAppointmentSchema = z.discriminatedUnion('action', [
  z.object({ action: z.literal('cancel') }),
  z.object({
    action: z.literal('reschedule'),
    startsAt: z.string().datetime({ offset: true }),
    dentistId: z.string().uuid().optional(),
  }),
]);

在 TypeScript 這一側，它還會自動窄化型別：當你判斷 body.action === 'reschedule'，編譯器就知道 body.startsAt 一定存在。驗證與型別安全在同一個地方解決。

schema 也能做正規化

Zod 不只驗證，還能轉換。手機的生日欄位用 MM/DD/YYYY 輸入，但資料庫要存 YYYY-MM-DD。這支 schema 先驗證兩種格式都接受，再用 transform 統一轉成後者，最後再確認它是一個真實存在的日期：

const dateOfBirth = z.string().trim()
  .refine((v) => /^\d{2}\s*\/\s*\d{2}\s*\/\s*\d{4}$/.test(v)
              || /^\d{4}-\d{2}-\d{2}$/.test(v))
  .transform((v) => {
    if (/^\d{4}-\d{2}-\d{2}$/.test(v)) return v;
    const [mm, dd, yyyy] = v.split('/').map((s) => s.trim());
    return `${yyyy}-${mm}-${dd}`;
  })
  .refine((v) => !Number.isNaN(Date.parse(v)));

這樣做的效果是：混亂的輸入在邊界就被收斂成單一格式，資料庫與後面所有邏輯都只需要處理乾淨的值。

能自己算的，就不要讓 client 送

驗證只保證「送來的東西符合格式」，不保證「送來的東西是對的」。一個通過 uuid 驗證的 patientId，仍然可能是別人的；一個合法的時間字串，仍然可能不是可預約的時段。所以除了驗格式，還要刻意區分：哪些欄位 client 有資格決定，哪些必須由伺服器自己算。

欄位誰決定如果交給 client 會怎樣
startsAt（開始時間）client 送，但仍要通過可預約檢查送到不合法的時段（由下一節的寫入守衛擋下）
endsAt（結束時間）伺服器，用服務長度算client 把 30 分鐘的療程改成 8 小時
streamCallId（視訊通話 id）伺服器，由預約 id 推導client 傳別人的通話 id，混進他人的視訊
canCancel / canJoin伺服器，依當下時間判斷規則散在手機端，改一條要重發 app
durationMinutes伺服器，從資料庫的服務讀client 自己宣稱療程長度，繞過排程引擎

實際的程式碼就是這樣。client 只送 startsAt，伺服器從資料庫讀出這個服務的長度，自己乘出結束時間：

const startsAt = new Date(body.startsAt);
const endsAt = new Date(
  startsAt.getTime() + service.durationMinutes * 60_000
);

視訊通話 id 也是。它不是由 client 指定，而是在預約寫入成功、拿到資料庫產生的 id 之後，才由伺服器推導出來：

if (service.isTeleconsult) {
  await db.update(appointments)
    .set({ streamCallId: `appointment-${created.id}` })
    .where(eq(appointments.id, created.id));
}

這樣做同時解決了兩種問題。第一是正確性：療程多長、通話屬於哪一筆預約，這些事實的來源是資料庫，不是手機。第二是安全：如果通話 id 可以由 client 決定，那它就能指定別人的通話室，直接混進去。刻意讓它無法指定，這個攻擊面就不存在。

回應的形狀也在伺服器決定

同樣的原則往回應方向延伸。手機的預約卡片需要顯示「能不能取消」「能不能加入通話」，但這兩個問題的答案隨時間改變，規則也屬於商業邏輯。這支 API 不讓手機自己判斷，而是在序列化時就先算好：

return {
  id: a.id,
  startsAt: a.startsAt.toISOString(),
  canCancel: a.status === 'booked' && canCancel(a.startsAt, new Date()),
  canJoin: a.status === 'booked'
    && Boolean(row.service?.isTeleconsult)
    && Boolean(a.streamCallId)
    && canJoinCall(a.startsAt, new Date()),
  // 時間標籤也先格式化成診所時區
  dateLabel: formatClinicDate(a.startsAt),
  timeLabel: formatClinicTime(a.startsAt),
  // ...
};

這樣一來，手機只是「把伺服器給的結果畫出來」，它不需要知道自己位於哪個時區，也不需要知道取消的分界是幾小時。規則要調整時，改伺服器就好，不用等 app 重新上架。這個原則其實是整個專案的非協商條款：商業邏輯住在 web，mobile 只渲染 API 回傳的東西。

小結

TypeScript 型別在 runtime 不存在，所以請求進到 handler 時必須當成未知，用 Zod 在入口 parse。parse 失敗丟出 ZodError，由 route() 轉成 400。discriminatedUnion 讓同一個端點的取消與改期各自帶對的欄位，schema 也能用 transform 正規化輸入。驗證之外還要區分欄位主權：endsAt、streamCallId、canCancel 這些能由伺服器算的，一律不要讓 client 送，既保正確性也關掉攻擊面。

到這裡，四個零件都齊了：端點、錯誤信封、守衛、型別邊界。下一節把它們全部放進同一支 POST /api/appointments，照著順序走一遍，看看一筆預約從手機送出到寫進資料庫、再到被拒絕的 409，每一層各自負責什麼。
