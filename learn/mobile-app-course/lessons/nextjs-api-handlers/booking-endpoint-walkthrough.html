走一遍 POST /api/appointments：受保護的預約寫入

Step 5/5 · Next.js API Route Handlers

學習目標

能照順序寫出一個受保護的寫入 handler：驗身分、驗輸入、驗擁有權、重跑可預約檢查、寫入，最後把資料庫例外轉成 409，並回傳由伺服器組好的形狀。

前言：把零件組成一個端點

前四節分別講了端點、錯誤信封、守衛與型別邊界。現在把它們放進同一支 POST /api/appointments，跟著一筆預約從手機送出到寫進資料庫的順序走一遍。你不需要懂排程引擎的內部演算法，這一節的重點是「每一層在什麼時機被呼叫、它擋掉什麼」。真正難的時區與可預約計算，屬於另一個節點。

動手前的前置條件：你已經有 route()、json() 與 conflict() 這些 helper，有 requireAuth 與 requireOwnedPatient 守衛，以及 createAppointmentSchema。函式的外框長這樣：

export const POST = route(async (req: Request) => {
  // 以下逐步填入
});

步驟 1：確認身分

第一行永遠是身分。沒有任何參數來自 client，身分只從 session 推導；沒有登入就丟 401，由 route() 翻譯成回應。

const user = await requireAuth();

預期結果：這行通過後，user 是一個資料庫裡真實存在的使用者，而且 webhook 來不及建立的那一列也被補上了。

步驟 2：驗證輸入

接著把 request body 交給 schema。這一步同時做兩件事：確認格式，並把未知的 JSON 轉成可信任的型別。parse 失敗會丟 ZodError，你不需要在這裡處理，外層包裝會回 400。

const body = createAppointmentSchema.parse(await req.json());

預期結果：body 裡有合法的 patientId、serviceId、dentistId、startsAt。少了任何一個或格式錯誤，請求在這一關被擋下。

步驟 3：確認這筆病人資料是你的

格式對不代表有權限。這裡呼叫擁有權守衛，把「傳入的 patientId」與「目前登入者」一起比對。不是自己的，守衛丟 404。

const patient = await requireOwnedPatient(user, body.patientId);

預期結果：patient 是呼叫者名下的病人。這一關確保了攻擊者不能替別人掛號，也不能用亂猜的 patientId 建立資料。

步驟 4：確認醫師與服務存在且啟用

接下來兩個查詢把選項查實。服務與醫師都可能是停用的，或根本不存在；兩者都用 notFound 擋掉。這裡刻意不直接相信 client 傳來的 id 組合。

const [service] = await db.select().from(services)
  .where(eq(services.id, body.serviceId));
if (!service || !service.isActive) throw notFound('Service not found');

const [dentist] = await db.select().from(dentists)
  .where(and(eq(dentists.id, body.dentistId), eq(dentists.isActive, true)));
if (!dentist) throw notFound('Dentist not found');

預期結果：拿到了這個服務的長度與是否為視訊，以及一位有效醫師。若有人用已下架的療程 id，請求在這裡就被拒絕。

步驟 5：由服務長度算出結束時間

client 只送了開始時間。結束時間由伺服器用資料庫裡的服務長度算出來，這樣療程長度就無法被竄改。

const startsAt = new Date(body.startsAt);
const endsAt = new Date(
  startsAt.getTime() + service.durationMinutes * 60_000
);

預期結果：startsAt 與 endsAt 都是伺服器算出的時間，而不是 client 宣稱的值。

步驟 6：重跑一次可預約引擎

這一步是整個寫入路徑的核心。手機在選擇時段時，是打 GET /api/availability 拿到一份清單；但到了送出預約時，client 完全可能送一個不在清單上的時間。所以伺服器在這裡把同一套排程引擎再跑一次，拒絕任何它在查詢時不會提供、但在寫入時卻被送來的時間。

await assertSlotBookable({
  dentistId: dentist.id,
  serviceId: service.id,
  durationMinutes: service.durationMinutes,
  startsAt,
});

它內部的判斷會回兩種結果，各自對應不同的錯誤：

  1. 若判定為 taken（時段已被佔用），丟出 conflict(..., 'slot_taken')，也就是 409。
  2. 若判定為 invalid（凌晨三點、不在排班內、還在預約前置時間內、或醫師根本不做這個療程），丟出 badRequest，也就是 400。

預期結果：只有「讀取時會提供、且現在仍可預約」的時間能通過。少了這個守衛，唯一的防線只剩下資料庫的排除約束，而它只擋重疊，擋不了凌晨三點或療程不符。

步驟 7：寫入，並攔住搶位子的例外

前面都是檢查，這裡才是真正寫入。因為兩個請求可能在幾乎同一瞬間通過步驟 6，最後由 Postgres 的排除約束仲裁誰先。失敗的那一個會丟出錯誤碼 23P01，我們把它翻譯成乾淨的 409。

try {
  const [created] = await db
    .insert(appointments)
    .values({
      patientId: patient.id,
      dentistId: dentist.id,
      serviceId: service.id,
      startsAt,
      endsAt,
    })
    .returning();

  // 步驟 8 ...
} catch (err) {
  if (isExclusionViolation(err)) {
    throw conflict('That time was just taken. Please pick another.', 'slot_taken');
  }
  throw err;
}

警告：這個 catch 只攔一種例外，其餘一律再丟出去。不要把整個資料庫錯誤都吞成 409，否則真正的程式 bug 會被誤導成「時段被搶走」。另外要記得，重複預約的防線是資料庫的排除約束，不是應用層的檢查；不要用一段「先查再寫」的程式碼取代它，那在併發下一定失效。

步驟 8：若是視訊，由伺服器推導通話 id

寫入成功、拿到資料庫產生的 id 之後，如果這個服務是視訊門診，才補上通話 id。它是由預約 id 推導的，client 無法指定。

if (service.isTeleconsult) {
  await db.update(appointments)
    .set({ streamCallId: `appointment-${created.id}` })
    .where(eq(appointments.id, created.id));
  created.streamCallId = `appointment-${created.id}`;
}

預期結果：視訊預約多了一個由伺服器產生的 streamCallId；非視訊預約則保持為 null。

步驟 9：回傳伺服器組好的形狀

最後把資料庫的列交給 serialize()，讓它算好 canCancel、canJoin 與診所時區的日期標籤，再用 json() 以 201 回傳。手機拿到的是已經能直接渲染的物件。

return json(
  { appointment: serialize({ appointment: created, patient, dentist, service }) },
  201
);

預期結果：手機收到一個 201 與完整的預約物件。之後它依 canCancel、canJoin 決定按鈕，不需要自己判斷任何規則。

同一個檔案裡的 GET

這支 route 檔案同時匯出了 GET，用來列出整個家庭的預約。它的分支邏輯值得看一眼：讀取 ?scope= 參數決定要看 upcoming 或 past，再把這個值同時用在查詢條件與排序方向上——未來用「開始時間大於等於現在」並遞增排序，過去看「小於現在」並遞減排序。若是過去，還會把就診後的醫囑（visit notes）一起 join 進來。這些都驗證了同一件事：查詢條件的形狀由伺服器決定，client 只表達它要看哪一種。

小結

一支受保護的寫入 handler 有固定的順序：requireAuth 確認身分 → Zod parse 驗輸入 → requireOwnedPatient 驗擁有權 → 載入服務與醫師 → 伺服器算 endsAt → assertSlotBookable 重跑可預約引擎 → 寫入並攔 23P01 轉 409 → 視訊補 streamCallId → serialize 後回 201。每一層只做一件事，錯誤由 route() 統一翻譯。做完之後，你得到的不是一支端點，而是一個可以複製到任何新資源的模板。

這五節從「端點長什麼樣」一路走到「一筆預約怎麼被安全地寫入」。你現在手上有一組可以重複套用的模式：先把身分與輸入收在邊界，再讓商業邏輯在伺服器裡跑完，最後把結果的形狀也留在伺服器。換成你自己的 app 時，改的是資源與查詢，這套骨架不需要重寫。
