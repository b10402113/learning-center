一步步完成 POST /api/appointments

Step 5/5 · Next.js API Route Handlers

這一步要完成什麼

這一節會把前面四步的零件接成一支真正能工作的寫入端點：POST /api/appointments。完成後，這支 handler 能接收手機送來的請求，確認使用者身分與病人所有權，驗證輸入資料，計算正確的結束時間，檢查時段是否仍可預約，最後安全地寫入資料庫。

動手前，請先準備好四個接點：Route Handler 的檔案慣例與 Request／Response 用法、route() 與 ApiError 家族、requireAuth() 與 requireOwnedPatient() 守衛，以及 createAppointmentSchema 這份 Zod 合約。這一節不重新解釋它們，而是把它們依照正確順序串起來。

先看完整流程：每一道門各自負責什麼

一筆預約請求會依序通過五道門：

  1. 確認呼叫者已登入，並驗證請求格式。
  2. 確認病人屬於目前帳號，服務與牙醫也確實存在且啟用。
  3. 由 server 計算結束時間，再重新確認時段真的可預約。
  4. 把合法資料寫入資料庫，並推導不該交給 client 決定的欄位。
  5. 若有人同時搶走時段，把資料庫錯誤轉成手機能處理的 409。

這個順序像機場安檢：先確認你是誰，再確認行李格式，接著確認目的地與規則，最後才讓你登機。任何一道門沒通過，都不應該讓資料庫留下半成品。

步驟一：用 route() 包起來，先驗證身分與格式

所有寫入 handler 都從同一個骨架開始：外層套上 route()，進入函式後第一件事先確認登入狀態，接著驗證請求內容。

export const POST = route(async (req: Request) => {
  const user = await requireAuth();
  const body = createAppointmentSchema.parse(await req.json());

requireAuth() 會取得資料庫裡對應的使用者。若請求者沒有登入，它會直接丟出 401，後面的程式不會執行。

下一行先用 await req.json() 讀取請求內容，再交給 createAppointmentSchema.parse()。解析成功後，body 就是符合合約的資料；若欄位缺少或格式錯誤，Zod 會丟出 ZodError，由 route() 統一轉成 400。

到這裡，handler 才能相信兩件事：呼叫者已登入，而且送來的資料形狀符合預期。

步驟二：確認病人所有權，以及服務和牙醫是否可用

身分正確、格式正確，還不代表這筆交易合法。接下來要確認目前帳號能操作這位病人，並且預約的服務與牙醫都存在且可使用。

  const patient = await requireOwnedPatient(user, body.patientId);

  const [service] = await db.select().from(services).where(eq(services.id, body.serviceId));
  if (!service || !service.isActive) throw notFound('Service not found');

  const [dentist] = await db
    .select()
    .from(dentists)
    .where(and(eq(dentists.id, body.dentistId), eq(dentists.isActive, true)));
  if (!dentist) throw notFound('Dentist not found');

requireOwnedPatient() 會把「這位病人屬於目前帳號」直接放進查詢條件。若病人不存在，或存在但不屬於這個帳號，就回 404，而不是 403。這樣可以避免讓呼叫者藉由錯誤回應猜出某筆資料是否存在。

接著查詢服務與牙醫。服務必須存在，而且 isActive 必須為真；牙醫也必須存在且啟用。

預期結果：只要其中一項檢查失敗，請求就會在這裡停止，回傳 404，資料庫不會被寫入。先檢查、後動手，是所有寫入端點都該遵守的基本順序。

步驟三：由 server 計算結束時間，再確認時段可預約

這是 handler 的核心。client 只送開始時間，結束時間由 server 根據服務長度計算；接著，server 還要重新執行可預約性檢查，不能只相信 client 傳來的時間。

  const startsAt = new Date(body.startsAt);
  const endsAt = new Date(startsAt.getTime() + service.durationMinutes * 60_000);

  // The client never gets to invent a time: this re-runs the same engine that
  // produced the slot list and rejects anything it would not have offered.
  await assertSlotBookable({
    dentistId: dentist.id,
    serviceId: service.id,
    durationMinutes: service.durationMinutes,
    startsAt,
  });

startsAt 是請求中的開始時間。endsAt 則是開始時間加上服務的 durationMinutes；其中 60_000 用來把分鐘換成毫秒。

注意，client 從未提供療程長度，因此無法偷偷把一次預約拉長。這是 server 根據資料庫裡的服務資料推導出的欄位。

assertSlotBookable() 會再次執行排程引擎，確認這個時間是否真的會出現在可預約清單裡。這一步會擋下 client 自己發明的時間，例如三更半夜、根本不在候選清單裡的時段、距離現在太近的時段，或牙醫沒有提供該服務的時段。檢查失敗時，函式會丟出 badRequest 或 conflict。

export async function assertSlotBookable({
  dentistId,
  serviceId,
  durationMinutes,
  startsAt,
  excludeAppointmentId,
}: {
  dentistId: string;
  serviceId: string;
  durationMinutes: number;
  startsAt: Date;
  excludeAppointmentId?: string;
}): Promise<void> {

這個函式還提供 excludeAppointmentId 參數。建立預約時用不到，但改期時會用到：系統必須排除「正在被搬動的那筆預約」，否則預約會被自己的舊時段擋住。

讀取端用它產生可預約時段，寫入端也用它做最後確認。兩邊共用同一顆排程引擎，才不會出現「畫面說可以預約，但送出後卻被另一套規則拒絕」的情況。

不要因為資料庫有排除約束，就把 assertSlotBookable() 拿掉。排除約束只負責阻止兩個時段重疊；半夜時段、非候選時段、前置時間不足，以及牙醫沒有提供這項服務，都不是它負責的事情。排程引擎與資料庫約束各自守不同的門，不能互相取代。

步驟四：通過檢查後才寫入，並由 server 推導欄位

前面的條件都通過後，才進入真正的資料庫寫入。這段 try 不只負責插入，也會捕捉另一種情況：兩個人幾乎同時搶同一個時段。

  try {
    const [created] = await db
      .insert(appointments)
      .values({
        patientId: patient.id,
        dentistId: dentist.id,
        serviceId: service.id,
        startsAt,
        endsAt,
      })
      .returning();

    // Teleconsult call id is derived, never client-supplied (PLAN.md phase 6).
    if (service.isTeleconsult) {
      await db
        .update(appointments)
        .set({ streamCallId: `appointment-${created.id}` })
        .where(eq(appointments.id, created.id));
      created.streamCallId = `appointment-${created.id}`;
    }

.returning() 會在插入後把新資料列取回來，包含資料庫自動產生的 id。拿到這個 id 後，遠距診療才有辦法組合出通話識別碼。

如果服務是遠距診療，streamCallId 就由 server 組成「appointment- 加上預約 id」。client 沒有機會自行傳入這個欄位，也就不能任意指定通話對象或識別碼。

步驟五：把排除約束轉成乾淨的 409

即使前面的可預約性檢查通過，仍然可能在檢查結束與資料庫插入之間發生競爭：另一位使用者剛好先搶走同一個時段。這時，資料庫的排除約束會擋下插入，並產生 23P01 錯誤。

handler 不該把這種資料庫內部訊息直接丟給手機，而要辨識它，再轉成前端能理解的狀態。

    return json(
      {
        appointment: serialize({
          appointment: created,
          patient: { id: patient.id, firstName: patient.firstName, lastName: patient.lastName },
          dentist: {
            id: dentist.id,
            displayName: dentist.displayName,
            title: dentist.title,
            specialty: dentist.specialty,
            photoUrl: dentist.photoUrl,
          },
          service,
        }),
      },
      201
    );
  } catch (err) {
    if (isExclusionViolation(err)) {
      throw conflict('That time was just taken. Please pick another.', 'slot_taken');
    }
    throw err;
  }
});

成功時回傳 201。serialize() 會把資料庫資料整理成手機畫面可以直接使用的 appointment 物件。

失敗時只特別處理排除約束錯誤。若 isExclusionViolation(err) 判斷為真，就轉成 409，並附上 slot_taken 代碼；手機端看到這個代碼，就能顯示「這個時段剛剛被搶走了，請換一個」。

其他錯誤則繼續往上丟，交給 route() 統一處理，例如送到 Sentry，並回傳 500。

使用者之間的 race condition 不需要靠應用層鎖來處理。「時段能不能重疊」交給資料庫排除約束；「這個時段本身合不合法」交給排程引擎；handler 只負責把兩者的結果轉成合適的 HTTP 回應。每個元件守好自己的責任，程式就不必維護兩套互相打架的規則。

驗證完成後的結果

現在可以用不同情境檢查這支 handler：

  • 送出合法的預約請求：收到 201，以及可直接渲染的 appointment 物件。
  • 送出格式錯誤的請求：收到 400，並附上 issues。
  • 送出剛被其他人搶走的時段：收到 409，並附上 slot_taken。

查看資料庫時，會看到新增一筆預約。endsAt 是 server 依照服務長度算出的值；如果是遠距診療，streamCallId 也會由 server 產生。

到這裡，整條鏈路就接起來了：Route Handler → 錯誤信封 → 身分守衛 → Zod 邊界 → 可預約性檢查 → 資料庫寫入 → 例外轉換。

這支 handler 能維持短小，是因為每個元件只負責自己的工作：錯誤處理由 route() 統一處理，身分由守衛確認，輸入由 Zod 驗證，時段由排程引擎判斷。handler 本身只留下商業流程的順序，負責把這些零件接起來。

小結

完整的寫入 handler 可以依序拆成五段：先用 requireAuth() 與 parse 確認身分和資料形狀；再用 requireOwnedPatient()、服務檢查與牙醫檢查確認資源合法；接著由 server 推導 endsAt，並重跑 assertSlotBookable()，避免 client 發明不存在的時間；寫入後再推導 streamCallId；最後在 catch 中把排除約束轉成 409 與 slot_taken，其餘錯誤交回 route()。順序本身就是商業邏輯。

完成這一步後，你就有一支具備型別、受到保護，並能對手機回傳穩定錯誤代碼的預約 API。接下來可以往下一課前進，看看這些 handler 背後的預約領域模型是如何建模的。
