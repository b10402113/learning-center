走一遍 POST /api/appointments

Step 5/5 · Next.js API Route Handlers

學習目標

能照著順序把守衛、Zod 驗證、寫入與 409 例外處理串成一個完整的寫入 handler，並說出每一步為什麼存在。

前言：動手前，先確認你站在哪裡

這一節要把前面四步的零件全部組起來，完成整個節點最重要的那支端點：POST /api/appointments。它負責真正建立一筆預約。做完之後，你會得到一個能接收手機請求、驗證身分與所有權、算出正確時間、寫入資料庫，並且在時段被搶走時回一個乾淨 409 的 handler。

動手前需要先具備四樣東西，都已經在前幾步交代過：第一，Route Handler 的檔案慣例與 Request／Response 的用法；第二，route() 包裝與 ApiError 家族（包含 conflict 與 isExclusionViolation）；第三，requireAuth() 與 requireOwnedPatient() 這組守衛；第四，createAppointmentSchema 這份 Zod 合約。這四樣在這裡都只當接點，不會重講。

步驟一：用 route() 包起來，開頭先驗身分

所有的寫入 handler 都從同一個骨架開始：外面套 route()，裡面第一行呼叫守衛。做完之後你會看到 handler 的形狀是「一個被包裝的非同步函式，第一件事就是確認呼叫者有登入」。

export const POST = route(async (req: Request) => {
  const user = await requireAuth();
  const body = createAppointmentSchema.parse(await req.json());

第一行 requireAuth() 拿到的 user，是資料庫裡那一列使用者；沒登入的話它已經在上一行丟出 401，後面的程式根本不會被執行。第二行同時做兩件事：把請求的 JSON 讀出來，交給 schema 解析。解析成功得到一個有型別的 body；解析失敗則丟出 ZodError，由 route() 轉成 400。這兩行之後，你才可以開始相信「跟我講話的是一個登入者，而且他送的欄位形狀是對的」。

步驟二：確認這筆病人是他的，再確認服務與牙醫存在

身分對、格式對，都還不代表這筆交易合法。接下來要處理的是「他能碰這筆資料嗎」與「他要預約的東西真的存在嗎」。

  const patient = await requireOwnedPatient(user, body.patientId);

  const [service] = await db.select().from(services).where(eq(services.id, body.serviceId));
  if (!service || !service.isActive) throw notFound('Service not found');

  const [dentist] = await db
    .select()
    .from(dentists)
    .where(and(eq(dentists.id, body.dentistId), eq(dentists.isActive, true)));
  if (!dentist) throw notFound('Dentist not found');

requireOwnedPatient() 把「這筆病人屬於當前帳號」直接寫進查詢條件，不屬於就丟 404（還記得為什麼不是 403 嗎？避免洩漏資料是否存在）。接著查服務與牙醫：服務要存在且 isActive，牙醫也要存在且啟用。預期看到什麼：只要其中一個條件不成立，這個請求就停在這裡，回一個 404，資料庫不會被寫入任何東西。這種「先檢查、後動手」的順序，是寫入端點的基本禮貌。

步驟三：由 server 算出結束時間，重跑一次可預約性

這裡是整個 handler 最核心的兩段。第一段把結束時間算出來，第二段重新驗證這個時段真的可以預約。

  const startsAt = new Date(body.startsAt);
  const endsAt = new Date(startsAt.getTime() + service.durationMinutes * 60_000);

  // The client never gets to invent a time: this re-runs the same engine that
  // produced the slot list and rejects anything it would not have offered.
  await assertSlotBookable({
    dentistId: dentist.id,
    serviceId: service.id,
    durationMinutes: service.durationMinutes,
    startsAt,
  });

結束時間是 startsAt 加上服務本身的 durationMinutes，乘 60_000 是把分鐘換成毫秒。client 從頭到尾沒有送過長度，所以它沒有辦法偷偷把療程拉長。

真正重要的是 assertSlotBookable()。它會把同一個排程引擎再跑一次，檢查這個時間是不是「本來就會被列為可預約」。為什麼要重跑？因為 client 可能會自己發明一個時間，像是三更半夜、不在候選清單裡的時段、距離現在不到規定的前置時間，或者這個牙醫根本不看這個服務。這些都會被這道檢查擋下，丟出 badRequest 或 conflict。

export async function assertSlotBookable({
  dentistId,
  serviceId,
  durationMinutes,
  startsAt,
  excludeAppointmentId,
}: {
  dentistId: string;
  serviceId: string;
  durationMinutes: number;
  startsAt: Date;
  excludeAppointmentId?: string;
}): Promise<void> {

注意它有一個 excludeAppointmentId 參數。建立預約時不需要，但改期時會用上：那時要排除「正在被搬動的這筆預約」，否則它會擋住自己。這個設計讓讀取端（提供可預約時段）與寫入端（接受預約）共用同一顆引擎，兩邊永遠不會對不起來。

不要因為「反正資料庫有排除約束會擋重疊」就把 assertSlotBookable() 拿掉。約束只處理「兩個時段重疊」這一件事；半夜、非候選時段、前置時間不足、牙醫沒提供這個服務，這些它一概不管。兩者是互補，不是替代。

步驟四：寫入資料庫，並推導不該由 client 決定的欄位

檢查都過了，才真正寫入。插入用的 try 區塊同時處理最後一個意外：兩個人同時搶同一個時段。

  try {
    const [created] = await db
      .insert(appointments)
      .values({
        patientId: patient.id,
        dentistId: dentist.id,
        serviceId: service.id,
        startsAt,
        endsAt,
      })
      .returning();

    // Teleconsult call id is derived, never client-supplied (PLAN.md phase 6).
    if (service.isTeleconsult) {
      await db
        .update(appointments)
        .set({ streamCallId: `appointment-${created.id}` })
        .where(eq(appointments.id, created.id));
      created.streamCallId = `appointment-${created.id}`;
    }

.returning() 讓插入的同時把整列新資料拿回來，包含資料庫自動產生的 id，這樣才能接著組合通話 id。如果是遠距診療，streamCallId 會用「appointment- 加上這筆預約的 id」組出來，client 一樣沒有欄位可以插手。這一步是寫入端點的經典模式：能由資料庫或 server 生成的值，就不要向 client 要。

步驟五：接到排除約束的訊號，回一個乾淨的 409

如果你在檢查通過之後、插入之前，有人剛好搶走了同一個時段，會發生什麼事？資料庫那條排除約束會擋下這次插入，並丟出 23P01 的錯誤。handler 要做的是認出它，轉成使用者看得懂的回應。

    return json(
      {
        appointment: serialize({
          appointment: created,
          patient: { id: patient.id, firstName: patient.firstName, lastName: patient.lastName },
          dentist: {
            id: dentist.id,
            displayName: dentist.displayName,
            title: dentist.title,
            specialty: dentist.specialty,
            photoUrl: dentist.photoUrl,
          },
          service,
        }),
      },
      201
    );
  } catch (err) {
    if (isExclusionViolation(err)) {
      throw conflict('That time was just taken. Please pick another.', 'slot_taken');
    }
    throw err;
  }
});

成功時回 201，並用 serialize() 把資料庫那列轉成手機卡片要用的形狀。失敗時只認得排除約束這一種：是它，就轉成 409 並帶上 slot_taken 這個代碼；不是它，就原封不動往上丟，交給 route() 去送 Sentry、回 500。預期看到什麼：手機端收到 409 加上 slot_taken，就能顯示「這個時段剛剛被搶走了，換一個」。這就是整個預約流程裡最有價值的地方：搶位從一團模糊的失敗，變成一個手機能明確處理的狀態。

使用者端的 race（競爭條件）不需要用應用層的鎖去解。把「會不會重疊」交給資料庫的排除約束判斷，把「這個時段合不合法」交給排程引擎，handler 只負責把兩者的結果轉成合適的 HTTP 回應。責任分清楚，程式就短，也才不會有兩套邏輯互相打架。

做完會看到什麼

手機送出一筆合法的預約請求，會拿到 201 與一份可直接渲染的 appointment 物件；送出一筆格式錯誤的請求，會拿到 400 加 issues；送出一個被搶走的時段，會拿到 409 加 slot_taken。打開資料庫，會看到那筆預約多了一列，endsAt 是 server 算的、streamCallId（若是遠距）也是 server 給的。這一刻你就把「Route Handler → 錯誤信封 → 守衛 → Zod 邊界 → 寫入與例外」整條鏈路接完了。

這支 handler 之所以讀起來短，是因為原理都被抽到別的地方：錯誤處理在 route()、身分在守衛、輸入合約在 Zod、時段判斷在排程引擎。handler 自己只留下「依照商業順序把它們串起來」這件事。這種「知道什麼該留在 handler、什麼該搬出去」的分寸，才是這一步真正想教你的東西。

小結

一支完整的寫入 handler 有五段：requireAuth() 與 parse 確認身分和形狀；requireOwnedPatient() 加上服務／牙醫的存在檢查確認合法性；server 推導 endsAt 並重跑 assertSlotBookable() 防止 client 發明時間；插入後推導 streamCallId；最後在 catch 裡把排除約束轉成 409 slot_taken，其餘錯誤交給 route()。每一步都對應前面四步學到的零件，順序本身就是商業邏輯。

走到這裡，這一個節點就完整了：你有一座有型別、受保護，而且能對手機給出穩定錯誤碼的 API。接下來可以往下一課前進，去看這些 handler 背後的預約領域模型是怎麼建模的。
