requireAuth 與守衛：身分只從 session 來

Step 3/5 · Next.js API Route Handlers

學習目標

能解釋 requireAuth、requireStaff 與 requireOwnedPatient 各自擋下什麼，並說出身分為什麼只能從 session 推導、不能相信 client 傳來的任何欄位。

前言：一個容易踩的陷阱

假設你要寫一個「讀取我的預約」的端點。最直覺的寫法是讓手機把使用者 id 一起送上來，然後你拿這個 id 去查資料。這在很多教學範例裡都看得到，看起來也沒什麼問題。反正 app 是我寫的，它當然會送自己的 id。

問題在於：API 是公開的。只要有人拿得到網址，就可以用 curl 或 Postman 送出任何他想送的 id。你相信 client 傳來的 userId，等於把「我可以查誰的資料」這件事交給對方決定。攻擊者只要把 id 換成別人的，就能看到別人的病歷。這就是所謂的冒充漏洞。它最可怕的地方是，程式碼「看起來」完全正常，因為那個 id 確實是使用者自己送來的。

這一節要建立的紀律很簡單，但非常關鍵：身分只能從 session 推導。session 是伺服器驗證過 token 之後產生的，使用者改不了；client 傳來的任何欄位都只是「請求資料」，一律不能當成身分依據。

requireAuth：把「你是誰」變成一個函式

這個 app 用 Clerk 當身分供應商，並把「登入」包成一個所有端點都會呼叫的函式 requireAuth()。它回傳的是資料庫裡的使用者列，而不是 Clerk 的原始物件，因為後續的查詢都需要我們的 users.id。

/** Every patient-facing route starts here. Accepts the Expo Bearer token via clerkMiddleware. */
export async function requireAuth(): Promise<AppUser> {
  const { userId } = await auth();
  if (!userId) throw unauthorized();
  return ensureUser(userId);
}

看它做事的順序。先跟 Clerk 要當下這個請求的 userId，這個值來自請求帶的 token，是伺服器驗證過的，不是請求 body 裡的欄位。如果沒有 userId，直接 throw unauthorized()，也就是上一節學到的 401。如果有，交給 ensureUser() 把它對應到資料庫裡的那一列。

手機端是 Expo，跟網頁的登入方式不同，它帶的是 Bearer token。這裡之所以能拿到同一份 userId，是因為專案的 proxy（新版 Next.js 已把 middleware 改名）會把 Clerk 的驗證結果掛到每個請求上，所以不管你從網頁還是手機來，auth() 都讀得到。這是「在一個地方把身分準備好」的價值：handler 不需要各自處理 token 的差異。

ensureUser：跟 webhook 的最終一致性打一架

requireAuth() 最後呼叫的 ensureUser()，處理的是一個很真實的時序問題。這個專案原本靠 Clerk 的 webhook，在使用者建立時把資料同步進自己的 users 表。但 webhook 是「最終一致」的：一個剛註冊的使用者，很可能在 user.created 這個事件送達之前，就已經打開 app 打了第一個 API。

如果這時 handler 只會去 users 表找資料，就會找不到人，然後回一個使用者根本看不懂的錯誤。解法是不要等 webhook，直接從 session 的資料 upsert：找不到就建立，找到就回傳。webhook 則退居後援，負責之後的更新與刪除。

async function ensureUser(clerkId: string): Promise<AppUser> {
  const existing = await db.select().from(users).where(eq(users.clerkId, clerkId));
  if (existing[0]) return existing[0];

  const clerkUser = await currentUser();
  const email = clerkUser?.primaryEmailAddress?.emailAddress ?? null;
  const role = roleFromMetadata(clerkUser?.publicMetadata);

  const [created] = await db
    .insert(users)
    .values({ clerkId, email, role })
    .onConflictDoUpdate({ target: users.clerkId, set: { email } })
    .returning();
  return created;
}

這裡有一個值得學的設計：onConflictDoUpdate 讓這個 upsert 是冪等的。就算兩個請求幾乎同時到達、都決定要建立同一個使用者，資料庫的唯一鍵也會讓其中一次變成更新，而不是撞出重複資料。這種「不確定誰先誰後，但結果一定一樣」的寫法，是分散式系統裡的基本功。

requireStaff：角色判斷要信哪一邊

不是每個端點都給病人用，員工 dashboard 的功能就只有員工能碰。requireStaff() 比 requireAuth() 多一層角色檢查，但它的難處在於：角色有兩個來源，一個是 Clerk 的 publicMetadata，一個是我們自己資料庫的 users.role。

export async function requireStaff(): Promise<AppUser> {
  const { userId, sessionClaims } = await auth();
  if (!userId) throw unauthorized();

  const user = await ensureUser(userId);
  const claimRole = roleFromMetadata(
    (sessionClaims as { publicMetadata?: unknown } | null)?.publicMetadata
  );

  // Trust whichever side says "staff" — the DB row may lag a Clerk change.
  const isStaff =
    claimRole === 'staff' ||
    claimRole === 'dentist' ||
    user.role === 'staff' ||
    user.role === 'dentist';
  if (!isStaff) throw forbidden('Staff access only');

它的判斷原則是「哪邊說是員工就信哪邊」。為什麼不用嚴格交集，兩邊都說是員工才放行？因為資料庫那列可能落後於 Clerk 的變更，管理員剛把某人升成員工，但同步還沒跑完。反過來說，如果資料庫還留著舊的員工角色、Clerk 已經降回病人，這條規則會偏寬，但這裡選擇的是「避免把合法的員工擋在門外」。角色判斷的寬嚴取捨，取決於哪一種錯更痛；對員工入口來說，誤擋的痛通常大於短暫誤放。

requireOwnedPatient：真正的那道所有權鎖

最常見的越權情境不是「沒有登入」，而是「有登入，但想碰別人的資料」。一個診所帳號可能同時管理全家人的病歷，所以「有登入」和「能碰這筆病人資料」完全是兩件事。這個 app 用一個函式把這道鎖收在一起，所有帶 patientId 的端點都得過這一關。

/**
 * Resolves a patient the caller is actually allowed to touch. Every route that
 * takes a patientId goes through here — that is the whole ownership check, so
 * it is never re-implemented per route.
 */
export async function requireOwnedPatient(user: AppUser, patientId: string) {
  const [patient] = await db
    .select()
    .from(patients)
    .where(and(eq(patients.id, patientId), eq(patients.accountUserId, user.id)));
  if (!patient) throw notFound('Patient not found');
  return patient;
}

它的查詢條件同時包含「病人 id 等於傳進來的」和「這筆病人的帳號 id 等於你的」。兩個條件缺一不可：只有前者，你就能讀任何人的病歷；只有後者，你會撈到全家人而不是指定的那一個。這種「擁有權就是查詢條件的一部分」的寫法，比先查出來再在程式裡比對更安全，因為你根本不會把不該看的資料載進記憶體。

找不到時，為什麼回 404 而不是 403？

這裡有個容易被忽略、但很值得記住的選擇：當所有權檢查失敗，回的是 notFound() 而不是 forbidden()。原因是 403 等於在告訴對方「這筆資料存在，只是你沒權限」。攻擊者可以拿這句回饋來探測：「太好了，這個 id 真的有資料，我再試下一個。」把回應改成 404，存在與不存在長得一模一樣，對方就無從得知自己猜中了什麼。

守衛回答的問題失敗時
requireAuth()你是誰？有登入嗎？401（Sign in required）
requireStaff()你是員工或牙醫嗎？403（Staff access only）
requireOwnedPatient()這筆病人資料是你的嗎？404（Patient not found）

把這些守衛放在 lib/auth.ts、而不是每個 handler 各寫一次，還有另一個好處：規則只有一處，要改的時候不用擔心漏了哪個端點。這也是這個 app 一再出現的模式：把判斷收進一個有名字的函式，讓每個使用的地方都變成一行呼叫。

小結

身分只能從 session 推導，client 傳來的欄位一律不算數。requireAuth() 確認有登入並用 ensureUser() 補上 webhook 的時序落差；requireStaff() 檢查員工角色，角色兩邊來源取寬；requireOwnedPatient() 把「這筆資料是不是你的」直接寫進查詢條件，失敗時回 404 以免洩漏資料存在與否。守衛集中在 lib，每個 handler 只呼叫一行，就不會有人漏掉或寫錯。

到這裡，我們解決了「誰可以進來」與「能不能碰這筆資料」。但還有一個入口沒守住：請求 body 裡的欄位本身。就算身分正確，client 還是可能送來格式錯誤、超長、或乾脆偽造的欄位。下一節要在 handler 一開頭放一道 Zod 城門，把不合法的輸入全部擋在外面。
