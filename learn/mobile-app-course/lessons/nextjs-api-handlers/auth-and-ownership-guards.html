requireAuth 與守衛：身分只從 session 來

Step 3/5 · Next.js API Route Handlers

學習目標

能分辨 requireAuth、requireStaff、requireOwnedPatient 各自的職責，並說明為什麼身分必須由伺服器從 session 推導，以及別人的資料為什麼要回 404 而不是 403。

前言：一個看起來很方便、卻會出事的寫法

手機要拿自己的預約，最直覺的 API 設計是：讓手機在請求裡帶上自己的使用者 id，伺服器拿這個 id 去查資料。像是 GET /api/appointments?userId=abc。寫起來很順，測試也很快。

問題是，任何人只要改一下那個字串，就能查別人的預約。伺服器完全沒有能力分辨「這個 id 是手機自己的，還是它掰出來的」。同樣的漏洞也會出現在寫入端：如果建立預約時由 client 決定 patientId，那 attacker 就能替別人掛號。

正確的做法是把身分交給伺服器判斷。手機證明「我是誰」的方式，是帶著登入後拿到的 token；伺服器驗證 token，從中得到使用者 id，其餘一律不信。這一節要看的，就是包住這套判斷的三個守衛。

requireAuth：確認「你是誰」

第一個守衛 requireAuth 是幾乎每個病人端路由的入口。它做兩件事：向 Clerk 要出目前 session 的使用者 id，沒有的話就丟 401；有的話，確保資料庫裡有一列對應的使用者，再把它回傳。

export async function requireAuth(): Promise<AppUser> {
  const { userId } = await auth();      // 由 Clerk middleware 驗 token
  if (!userId) throw unauthorized();
  return ensureUser(userId);
}

這裡的 auth() 來自 @clerk/nextjs/server，它會驗證請求攜帶的 token；手機端則是在每次 fetch 時把 Clerk 的 Bearer token 放進 header。注意：函式裡完全沒有出現任何來自 request body 或 query 的 id。使用者的身分只有一個來源，就是被驗證過的 session。

為什麼 requireAuth 順便要 upsert？

ensureUser 的名字聽起來只是「取得使用者」，但它其實帶了一個重要的設計。回想 Clerk 與資料庫同步那一課：webhook 建立使用者資料是「最終一致」的，可能比第一次 API 請求晚到。如果 API 只會讀資料庫，新使用者登入後立刻打 API，就會找不到自己的那一列。

所以 requireAuth 選擇不等 webhook，直接從 session 補上：

async function ensureUser(clerkId: string): Promise<AppUser> {
  const existing = await db.select().from(users).where(eq(users.clerkId, clerkId));
  if (existing[0]) return existing[0];

  const clerkUser = await currentUser();
  const email = clerkUser?.primaryEmailAddress?.emailAddress ?? null;
  const role  = roleFromMetadata(clerkUser?.publicMetadata);

  const [created] = await db
    .insert(users)
    .values({ clerkId, email, role })
    .onConflictDoUpdate({ target: users.clerkId, set: { email } })
    .returning();
  return created;
}

這個做法讓請求路徑本身就能保證資料存在，webhook 則退居成「後續更新與刪除的備援」。onConflictDoUpdate 是關鍵：就算 webhook 剛好同時插入，也不會撞成兩列。

requireStaff：角色判斷，兩邊都信

員工 dashboard 與員工專屬端點需要更高的權限，這時用 requireStaff。它同樣先確認登入、確保使用者存在，接著判斷角色是不是 staff 或 dentist，不是的話丟 403。

比較特別的是判斷邏輯。角色可能來自兩個地方：session token 裡的 publicMetadata，或資料庫 users 表裡的 role。當管理員在 Clerk 後台把某人改成 staff，這個變更可能還沒同步到資料庫；反過來，資料庫也可能有 Clerk metadata 還沒反映的狀態。這支程式的選擇是「只要任一邊說是 staff 就算」：

const claimRole = roleFromMetadata(sessionClaims?.publicMetadata);
const isStaff =
  claimRole === 'staff' || claimRole === 'dentist' ||
  user.role === 'staff' || user.role === 'dentist';
if (!isStaff) throw forbidden('Staff access only');

通過之後，它還會把 database 的 role 更新成 token 裡的版本，讓 dashboard 那些直接讀 Drizzle 的頁面看到一致的角色。判斷角色的預設值是 patient：roleFromMetadata 只認得 'staff' 與 'dentist'，其他一律當病人，避免有人塞一個怪字串就拿到權限。

requireOwnedPatient：這筆資料是不是你的

確認了身分之後，還有最後一層：這支路由要操作的病人資料，屬於呼叫者嗎？這個問題每支帶 patientId 的路由都會遇到，所以它被收斂成一個守衛 requireOwnedPatient。

export async function requireOwnedPatient(user: AppUser, patientId: string) {
  const [patient] = await db
    .select()
    .from(patients)
    .where(and(
      eq(patients.id, patientId),
      eq(patients.accountUserId, user.id)   // 關鍵：同時比對擁有者
    ));
  if (!patient) throw notFound('Patient not found');
  return patient;
}

查詢條件是「id 等於傳入值」而且「accountUserId 等於目前使用者」。只要不是自己的，查詢就找不到，於是回傳 404。這裡的擁有權判斷只寫一次，所有病歷相關路由都呼叫它，不需要各自複製一段權限檢查——也就不會出現「有一支路由忘記檢查」的破口。

另外還有一個 selfPatient，用來取得帳號本人那一列（資料庫裡以 isSelf 標記）。它和 requireOwnedPatient 的差別是：前者用於「我只能操作我自己」，後者用於「我可以操作我名下的任何一位家人」。

把「別人的資料」當成不存在

你可能注意到，requireOwnedPatient 對「不是你的病人」回的是 404，而不是「你無權存取」的 403。這不是偷懶，而是一個一致的資安選擇。如果傳別人的 id 回 403、傳一個根本不存在的 id 回 404，攻擊者就能拿這兩個回應的差別，逐一探測「哪些病人 id 真的存在」。回 404 讓「不存在」和「不屬於你」在外部看起來一模一樣，洩漏的資訊最少。

同樣的原則也出現在 AI 對話的擁有權檢查：一個屬於別人的 conversation id，回的是 404，不是 403。

小結

身分唯一的來源是 session：requireAuth 驗 token、拿 userId，並順手從 session upsert 使用者，補上 webhook 的延遲。requireStaff 在此之上判斷角色，token metadata 與資料庫任一邊說是 staff 就算，預設一律是病人。requireOwnedPatient 把「這筆資料是不是你的」收斂成一個查詢，找不到就回 404，讓「不存在」與「不是你的」在外部無法區分。三者的共同原則是：永遠不信任 client 傳來的身分，擁有權只判斷一次。

守衛解決了「誰能碰這筆資料」，但還沒處理「你送來的內容長什麼樣子」。如果 body 裡少一個必填欄位，或格式根本不對，handler 不該直接拿去查資料庫。下一節要看 Zod 怎麼當入口的城門，以及為什麼像服務長度、通話 id 這些欄位必須由伺服器自己算。
