requireAuth 與守衛：身分只能從 session 推導

Step 3/5 · Next.js API Route Handlers

先想像一個容易出事的 API

假設你要做一個「讀取我的預約」端點。最直覺的做法，是讓手機把使用者 id 一起送到 API，伺服器再拿這個 id 查資料。這種寫法在教學範例裡很常見，因為看起來合理：app 是自己寫的，當然會送上自己的 id。

但 API 並不知道請求是不是來自你的 app。只要有人拿得到網址，就能用 curl 或 Postman 送出任何 id。只要伺服器相信 client 傳來的 userId，對方就等於拿到了「我可以查誰的資料」這把鑰匙。把 id 換成別人的，甚至可能就能看到別人的病歷。

這類問題叫做冒充漏洞。危險的是，程式碼表面上完全正常：那個 id 確實是使用者送來的，只是它不代表使用者真的有權限查那筆資料。

這一節要建立的紀律很簡單，卻是 API 權限設計的地基：身分只能從 session 推導。session 是伺服器驗證 token 後得到的結果，client 傳來的欄位則只是「請求資料」，不能拿來當身分證件。

學習目標

你會學會區分 requireAuth、requireStaff 與 requireOwnedPatient 各自守住哪一道門，也能說明為什麼身分必須從 session 推導，而不能相信 client 傳來的任何欄位。

requireAuth：把「你是誰」集中成一個函式

這個 app 使用 Clerk 作為身分供應商，並把登入檢查包成所有端點都能呼叫的 requireAuth()。它回傳的不是 Clerk 原始物件，而是資料庫裡的使用者資料列，因為後續查詢需要的是我們自己的 users.id。

/** Every patient-facing route starts here. Accepts the Expo Bearer token via clerkMiddleware. */
export async function requireAuth(): Promise<AppUser> {
  const { userId } = await auth();
  if (!userId) throw unauthorized();
  return ensureUser(userId);
}

這個函式的順序很清楚。它先向 Clerk 取得目前請求的 userId。這個值來自請求中的 token，已經由伺服器驗證過，不是 request body 裡任由 client 填寫的欄位。

如果沒有 userId，就直接 throw unauthorized()，回傳上一節介紹的 401。取得身分後，再交給 ensureUser()，把 Clerk 的身分對應到資料庫中的使用者資料列。

手機端使用 Expo，登入方式和網頁不同，請求帶的是 Bearer token。專案的 proxy——新版 Next.js 將 middleware 改了名稱——會先處理 Clerk 驗證，並把結果掛到每個請求上。因此無論請求來自網頁還是手機，auth() 都能讀到同一份 userId。

這就是把身分準備工作集中在一個地方的價值：每個 handler 不必各自理解 token 的差異，只要呼叫同一個守衛即可。

ensureUser：補上 webhook 的時間差

requireAuth() 最後呼叫的 ensureUser()，處理的是一個很實際的時序問題。這個專案原本依靠 Clerk webhook，在使用者建立時把資料同步到自己的 users 表。

然而 webhook 採用的是「最終一致性」。剛註冊的使用者，可能在 user.created 事件送達前，就已經打開 app 並送出第一個 API 請求了。

如果 handler 這時只查 users 表，可能會找不到這個人，接著回傳一個使用者完全看不懂的錯誤。比較穩妥的做法是不等待 webhook，而是直接根據 session 的身分資訊執行 upsert：找不到就建立，找到了就回傳。webhook 則作為後援，處理之後的更新與刪除。

async function ensureUser(clerkId: string): Promise<AppUser> {
  const existing = await db.select().from(users).where(eq(users.clerkId, clerkId));
  if (existing[0]) return existing[0];

  const clerkUser = await currentUser();
  const email = clerkUser?.primaryEmailAddress?.emailAddress ?? null;
  const role = roleFromMetadata(clerkUser?.publicMetadata);

  const [created] = await db
    .insert(users)
    .values({ clerkId, email, role })
    .onConflictDoUpdate({ target: users.clerkId, set: { email } })
    .returning();
  return created;
}

這段程式還示範了一個重要設計：onConflictDoUpdate 讓 upsert 具備冪等性。即使兩個請求幾乎同時抵達，而且都判斷出需要建立同一個使用者，資料庫的唯一鍵也會讓其中一次轉為更新，而不是產生兩筆重複資料。

換句話說，這種寫法不必賭「哪個請求先到」，因為不論順序如何，最後都會得到一致的結果。這是分散式系統中很實用的基本功。

requireStaff：角色判斷要看哪個來源？

不是每個端點都給病人使用。員工 dashboard 的功能，就應該只有員工能存取。requireStaff() 比 requireAuth() 多了一層角色檢查，但它也遇到一個常見問題：角色有兩個來源，一個是 Clerk 的 publicMetadata，另一個是我們資料庫中的 users.role。

export async function requireStaff(): Promise<AppUser> {
  const { userId, sessionClaims } = await auth();
  if (!userId) throw unauthorized();

  const user = await ensureUser(userId);
  const claimRole = roleFromMetadata(
    (sessionClaims as { publicMetadata?: unknown } | null)?.publicMetadata
  );

  // Trust whichever side says "staff" — the DB row may lag a Clerk change.
  const isStaff =
    claimRole === 'staff' ||
    claimRole === 'dentist' ||
    user.role === 'staff' ||
    user.role === 'dentist';
  if (!isStaff) throw forbidden('Staff access only');

這裡採用的規則是：只要其中一邊判斷為員工，就先視為員工。為什麼不是更嚴格地要求兩邊都說是員工才放行？因為資料庫的資料可能落後於 Clerk。

例如，管理員剛把某人升成員工，但同步尚未完成。如果此時要求兩邊完全一致，合法員工就會被擋在門外。反過來，若資料庫還留著舊的員工角色，而 Clerk 已經把對方降回病人，這套規則確實會比較寬鬆。

這不是單純的對錯題，而是風險取捨：要優先避免誤擋合法員工，還是優先避免短暫誤放？這個員工入口選擇了前者，因為角色同步的延遲可能造成合法使用者無法工作。

requireOwnedPatient：真正的所有權鎖

最常見的越權情境，不是「沒有登入」，而是「已經登入，卻想碰別人的資料」。一個診所帳號可能同時管理全家人的病歷，所以「有登入」和「可以讀取這筆病人資料」是兩件不同的事。

這個 app 將所有權檢查集中在 requireOwnedPatient()。凡是帶有 patientId 的端點，都必須先通過這道守衛。

/**
 * Resolves a patient the caller is actually allowed to touch. Every route that
 * takes a patientId goes through here — that is the whole ownership check, so
 * it is never re-implemented per route.
 */
export async function requireOwnedPatient(user: AppUser, patientId: string) {
  const [patient] = await db
    .select()
    .from(patients)
    .where(and(eq(patients.id, patientId), eq(patients.accountUserId, user.id)));
  if (!patient) throw notFound('Patient not found');
  return patient;
}

注意這個查詢同時檢查兩件事：病人 id 必須等於請求帶進來的 patientId，而且這筆病人的帳號 id 必須等於目前登入使用者的 id。兩個條件缺一不可。

如果只檢查前者，使用者就可能讀到任何人的病歷。如果只檢查後者，查詢結果可能會撈出這個帳號管理的所有家人，而不是指定的那一位。

把所有權直接寫進查詢條件，比先把資料查出來、再在程式裡比對更安全。因為不符合條件的資料根本不會被載入記憶體，像是在資料庫門口就先驗票，而不是把所有人都帶進場後才檢查身分。

找不到時，為什麼回 404 而不是 403？

所有權檢查失敗時，這裡回傳的是 notFound()，而不是 forbidden()。原因在於 403 可能會洩漏資料存在的訊息：它等於告訴對方「這筆資料存在，只是你沒有權限」。

攻擊者就能利用這個回應探測 id：「這個 id 有資料，只是不能看。」接著再換下一個 id 繼續猜。

改回 404 後，資料不存在和資料存在但無權限，對外看起來都是「找不到」。對方就無法從回應判斷自己是否猜中了有效的病人 id。

守衛它回答的問題失敗時
requireAuth()你是誰？有登入嗎？401（Sign in required）
requireStaff()你是員工或牙醫嗎？403（Staff access only）
requireOwnedPatient()這筆病人資料是你的嗎？404（Patient not found）

把這些守衛集中放在 lib/auth.ts，而不是讓每個 handler 各自實作，也能降低漏檢查或寫錯規則的機會。判斷只有一份，未來需要調整時也只要修改一個地方。每個使用端點則只需要呼叫一個有意義的函式名稱，程式碼會更容易閱讀和檢查。

把幾道門連在一起

身分只能從 session 推導，client 傳來的欄位一律不算數。requireAuth() 確認使用者已登入，並用 ensureUser() 補上 webhook 的時序落差；requireStaff() 檢查員工角色，兩個角色來源採取較寬的判斷；requireOwnedPatient() 則把「這筆資料是不是你的」直接寫進查詢條件，失敗時回 404，避免洩漏資料是否存在。這些守衛集中在 lib，handler 只要呼叫對應函式，就不必重複實作整套規則。

到這裡，我們守住了兩件事：誰可以進入，以及進來後能不能碰這筆資料。但還有一個入口尚未檢查：request body 裡的欄位本身。

即使身分正確，client 仍可能送出格式錯誤、過長，或刻意偽造的欄位。下一節會在 handler 一開始放上 Zod 這座城門，把不合法的輸入先擋在外面。
