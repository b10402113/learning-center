dev build、TestFlight 還是正式上架？

Step 4/6 · EAS Build、真機與 TestFlight

先決定：你要把哪一種版本交給誰？

你做完一個版本，想找人試用。這個人可能是你自己、坐在旁邊的同事，也可能是住在另一個城市的外部測試者。看起來都是「把 app 給別人打開」，背後卻是三種不同的情境。

開發時，你希望改一行程式碼，下一秒就看到結果；交給別人時，你又希望對方不必連著你的電腦，也能獨立打開 app。前者追求速度，後者追求接近真實使用。這兩股力量通常無法同時拉到最大，所以要先判斷自己現在站在哪一邊。

這一節的目標，是依照「誰要測、測什麼、要不要給外人」在 dev build、internal distribution、TestFlight 與 production 之間做選擇，也看清楚 TestFlight 相對於 dev build 的位置。

四個選項並排比較

選項誰能裝怎麼拿到改 code 能即時看到嗎適合情境
dev build你自己（或已註冊的裝置）掃 QR 安裝，再連上你的 Metro 伺服器可以，改完存檔立刻更新開發中、邊改邊看
internal distribution你註冊過的裝置EAS 產生 build，提供下載或 QR不行，要重新出 build給特定幾個人試一個固定版本
TestFlight受邀的測試者部署得像已上架，邀請後在手機上安裝不行，要重新發布給外部測試者、接近正式環境
production所有 App Store 使用者送審通過後正式上架不行，要重新送審真正的使用者、正式營運

先抓住最重要的分界：dev build 必須連著你的開發伺服器，才能顯示畫面。它像一台接著工作台的測試機，適合開發者邊改邊看。相較之下，internal distribution、TestFlight 和 production 都是獨立可執行的版本，對方不需要把你的電腦放在身邊。

TestFlight 位在開發與正式發布之間。它讓你用接近上架的方式部署 app，再邀請測試者在自己的手機上安裝。相較於 internal distribution，它更接近正式情境；當測試者不在你身邊，也不方便逐一註冊裝置時，TestFlight 就成了合適的交付介面。

用三個問題做選擇

遇到實際情境時，不必先背工具名稱。依序問下面三個問題，就能把選項篩出來。

  1. 這個人需要在我改完的下一秒就看到變化嗎？如果需要，選 dev build；如果不需要，繼續往下問。
  2. 測試者是少數固定的人，而且我可以先註冊他們的裝置嗎？如果可以，internal distribution 通常就夠了；如果不行，繼續往下問。
  3. 我要交給外部測試者，而且希望模擬接近正式發布的情境嗎？如果是，選 TestFlight；如果已經不需要測試，要直接提供給所有使用者，就是 production。

這條選擇路徑，可以想成從工作台一路走向舞台：越靠近開發端，更新越即時，但越依賴你的環境；越靠近發布端，使用情境越真實，但每次變更的成本也越高。你不需要每次都走最正式的路，也不該在還需要頻繁修改時，急著把版本送進 TestFlight。

反例：什麼時候不能照表操課？

第一個常見誤判，是把 TestFlight 當成開發迭代工具。TestFlight 沒有熱更新，每次調整都要重新產生 build 並重新發布。若你的工作節奏是「改一行、看一眼」，每次都走這條路，就像為了試吃一口湯，先把整間餐廳重新開張，流程會變得非常痛苦。

第二個誤判，是以為 internal distribution 可以無限制地交給任何人。它適合少數固定的人，但會受到裝置註冊限制。每增加一台新裝置，都要重新處理註冊；測試者一多，這個做法就不再划算。

第三個誤判，是忽略 build 數量的成本。免費方案每月有 build 數量上限。如果把測試流程設計成每天反覆產生好幾個 build，很快就可能撞到上限。因此，不能只看「技術上能不能做」，也要看這個流程是否適合你的測試頻率。

這個 demo app 目前還沒有正式上線，所以不需要動用 OTA 更新，也還沒走到真正的 TestFlight 發布。這不表示那些概念不重要，而是它們屬於 app 已經有真實使用者之後的階段。先確認 app 所處的階段，才不會拿發布工具處理開發問題。

把規則帶回自己的 app

選擇取決於兩件事：誰要測，以及要不要即時看到改動。dev build 連著你的伺服器，適合開發者邊改邊看；internal distribution 給已註冊的少數人一個獨立可跑的版本；TestFlight 部署得像已上架，適合邀請外部測試者；production 才是給所有使用者的正式上架。判準是一條線：越靠開發端越即時但越受限，越靠發布端越真實但越慢。TestFlight 不是開發迭代工具，internal distribution 會被裝置註冊數量綁住。

實際決策時，可以記住這個檢查順序：

  • 要不要改完立刻看到？要，就用 dev build。
  • 不需要即時更新，但測試者少而且裝置可註冊？用 internal distribution。
  • 測試者在外部，並且要模擬接近正式發布？用 TestFlight。
  • 已經要交給所有使用者？才進入 production。

不管選哪一種，只要 app 真的上線了，就會遇到下一個問題：一個小改動到底要不要重新送審？下一節要處理的，正是這條界線。
