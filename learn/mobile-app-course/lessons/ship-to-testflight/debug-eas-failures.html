build 失敗時：用完整 log 讓 AI 修好配置

Step 6/6 · EAS Build、真機與 TestFlight

這一節要完成什麼

完成後，你會知道如何在 EAS build 失敗時找到出錯的步驟、複製完整 log 交給 AI，取得可以執行的修法。你也會建立一套可重複的除錯迴圈：貼 log、修配置、先 commit、重新建置。

開始前：準備一個 EAS build

你可以直接使用已經失敗的 EAS build，也可以刻意重新執行一次，觀察失敗後的處理方式。

前面五節走的是順利完成的路線，但在真實專案裡，雲端 build 第一次就成功並不常見。建置會同時受到依賴、版本、原生環境與簽章設定影響，只要其中一個細節不一致，流程就可能停下來。

好消息是，EAS 會把建置過程保留在 log 裡。這份紀錄通常已經包含足夠線索，讓 AI 像讀診斷報告一樣，協助你找出問題。這一節不要求你先精通原生建置；你要先掌握的是兩件事：去哪裡拿 log，以及怎麼把完整內容交給 AI。

第一步：在 Expo 儀表板找到失敗的 build

建置完成或失敗後，開啟 Expo 儀表板（expo.dev），進入你的專案。專案頁面會列出所有 build 紀錄，其中也包含這次的 development build。

點進失敗的 build 後，畫面會把整段建置拆成一個個步驟。每個步驟旁都有狀態標記：成功的步驟會打勾，失敗的步驟會標紅。

往下查看時，請先找出第一個變成紅色的步驟。不要一看到最底下的錯誤就直接開始猜，因為後面的錯誤有時只是前面失敗造成的連鎖反應。

課程裡常見的失敗點是安裝原生依賴的步驟，例如 install pods。這一段比較容易受到環境與版本影響。找到第一個紅色步驟後，按下取得 log 的按鈕，開啟這一步的完整輸出。

第二步：把完整 log 交給 AI

取得 log 後，將整份內容複製下來，貼進你的 coding agent，並補充一句清楚的任務說明：

我的 dev build 失敗了，這是完整的 log，請幫我找出是哪個設定有問題，並告訴我怎麼修。

這裡最容易採用的錯誤做法，是只貼最後一行錯誤訊息。

不要只貼最後一行。最後一行通常比較像症狀，真正的線索可能藏在前面幾十行。

如果只提供最後一行，AI 看到的就像是只拿到病人的一句「我不舒服」，卻沒有前面的檢查紀錄。把完整 log 交給 AI，它才能沿著整段脈絡尋找根因，並提出可以照著做的修法。

課程裡的實例是：第一次建置出現 invalid version 錯誤。把完整訊息貼給 AI 後，AI 判斷問題與快取有關，並提供清理快取的修法。照著處理後重新執行指令，建置就成功了。你不需要事先知道什麼是快取問題，完整 log 會提供足夠線索，讓 AI 協助你定位。

第三步：套用修法，先 commit 再重建

拿到 AI 提供的修法後，照著修改專案裡的設定或檔案。修改完成後，先不要急著觸發下一次 build。

請先把變更提交到版控：

git add .
git commit -m "Fix EAS build configuration"
eas build --profile development --platform ios

這裡的順序很重要：先執行 git add 和 git commit，確認修改已經進入 repository，再執行 EAS build。

原因在於，雲端建置使用的是 repository 的狀態。如果你的電腦上還有一堆未提交的修改，EAS 取得的內容可能不是你以為的最新版本。這會讓你像對著舊地圖找新地址：明明已經改過問題，建置卻還在重現舊錯誤。

課程裡就曾遇到這種情況：一個已經過時的 build 一直失敗，原因是修改沒有先 commit。把改動提交上去，再重新建置後，問題就恢復正常了。因此，先 commit、再 build 不是單純為了保持專案整潔，也是在確保你除錯的對象確實是最新版。

第四步：根據結果決定下一個動作

提交完成後，重新執行建置指令。接著依照結果行動：

  1. 如果修法正確：儀表板上的步驟會一路變成綠色，建置完成後會再次出現 QR code。
  2. 如果又失敗：回到第一步，找出新的第一個紅色步驟，取得新的完整 log，再交給 AI 分析。

這個流程不要求你每次都一次猜中。重點是每一輪都使用最新的 log、最新的 commit 與最新的 build，讓問題逐步縮小，持續靠近答案。

怎麼確認修好了

成功的訊號很明確：

  • Expo 儀表板上的步驟全部變成綠色。
  • 終端機顯示建置完成。
  • 畫面再次出現 QR code。

拿到 QR code 後，就能回到前幾節的流程，把修好的 build 掃進手機，繼續進行真機測試。

做到這裡，你手上已經有一套完整的工作循環：能產生 build、安裝到真機、選擇散布方式、判斷更新路徑；即使 build 失敗，也知道要去哪裡找線索，以及如何請 AI 協助修正。

小結：把失敗變成可重複的流程

EAS build 失敗是常態，而且通常有機會修好。到 expo.dev 儀表板打開失敗的 build，找到第一個標紅的步驟，常見位置是 install pods 這類安裝依賴的步驟。接著取得完整 log，整份貼給 AI，請它找出設定問題與修法。套用修法後，先 commit，再重新執行建置。

不要只貼最後一行錯誤，也不要在有未提交改動時建置。成功時會看到整排綠燈與 QR code；如果再次失敗，就取得新的 log，重新跑一次這個迴圈。

這一節完成後，你的 app 已經能產生 build、安裝與測試，也知道上線後如何更新。接下來要處理的是上架前的合規文件與必要功能，那會是下一個節點的工作。
