這個改動要走 OTA，還是重新 build 送審？

Step 5/6 · EAS Build、真機與 TestFlight

App 上線後，你可能只想把按鈕上的一句話改得更自然：把「Continue with Apple」改成「Login with Apple」。修改本身也許只要五秒，但如果每個小改動都得重新送 App Store 審核，接著再等大約 48 小時甚至更久，修正的速度就會被審核流程卡住。

這時要做的決定很明確：這次改動能不能用 OTA（over-the-air，無線更新）直接推出？還是必須重新 build，再送 App Store 審核？兩者的差別，不在改動看起來大不大，而在於它有沒有碰到 native。

選項比較：OTA 熱更新，還是重新 build 送審？

OTA 熱更新重新 build 並送審
可以改什麼JavaScript 與 UI任何改動，包含 native
需要重新送 App Store 嗎不用要
使用者多久拿到下次開啟 app 時就更新等審核通過後才更新
典型例子改文案、調整樣式、修 JavaScript 邏輯新增 native module、改動原生依賴

OTA（over-the-air，無線更新）指的是 app 上線後，只更新 JavaScript 或 UI，接著把更新直接推出給使用者。這個流程不需要重新送審，也不用等審核完成。

因此，前面「修改 Apple 登入按鈕文案」的例子，就可以使用 OTA。這類改動只涉及介面文字，不需要改變 app 內建的原生程式碼。

你可以把 app 想成兩層。第一層是編譯進安裝檔的 native 程式碼；第二層是 app 執行時載入的 JavaScript bundle。App Store 審核的是已經編譯好的二進位檔，而 JavaScript bundle 可以在 app 啟動時下載並替換。

所以，改動如果只停留在 JavaScript 這一層，就像替換房間裡的布置，不必拆掉整棟房子；但只要動到 native，就等於改了房子的結構，必須重新 build，並再次送審。

判別問句：這個改動有沒有動到 native？

面對任何更新需求，先問自己一句：

這次修改有沒有新增或更動 native module（原生模組）？
  • 如果沒有，只是改 JavaScript 或 UI，就走 OTA。
  • 如果有，例如加入需要原生程式碼的新套件，就必須重新 build，並重新送審。

這個問題之所以好用，是因為它直接對應到 app 的實際組成。native 程式碼會被編進二進位檔；二進位檔一旦改變，就必須重新走 App Store 審核。相對地，JavaScript bundle 可以在既有 app 中事後替換，因此能透過 OTA 更新。

反例：哪些情況不能只靠 OTA？

OTA 不是一把萬用鑰匙。最典型的限制，是新增 native module。

假設你在專案中加入一個帶有原生程式碼的模組。舊版 app 的二進位檔裡根本沒有這段原生程式碼，即使你把需要它的 JavaScript 推送出去，舊版 app 也找不到對應的能力。這時只更新 JavaScript 不會解決問題，甚至可能讓 app 出錯；你必須重新 build、重新送審。

其他涉及 app 與作業系統介面的修改，也屬於同一類。例如：

  • 加入新的系統權限。
  • 使用新的原生 API。
  • 更動已簽署的設定。

判斷這些情況時，可以換一個角度想：是不是需要 iOS 系統重新認識你的 app？如果答案是「是」，就不能只推 OTA，而要走完整的 build 與送審流程。

別把「現在用不到」誤認成「以後不重要」

課程中的 demo app 目前還沒有正式上線，因此不會實際使用 OTA。OTA 是給已上線 app 使用的更新手段；在 app 尚未上線時，還沒有既有版本可以接收這類更新。

但這不代表這個概念可以先放一邊。正式 app 上線後，OTA 能讓你快速調整 UI，減少等待審核的時間，也不必為了小幅度的介面修正打斷使用者。授課者自己的正式 app 幾乎每天都會透過 OTA 修改 UI，正是因為它省時間，也比較不會影響使用者。

做決定前的快速檢查

  • 只是修改文案、樣式或 JavaScript 邏輯嗎？如果是，使用 OTA。
  • 有新增或更動 native module 嗎？如果有，重新 build 並送審。
  • 有涉及新的系統權限、原生 API 或已簽署的設定嗎？如果有，視為 native 改動，不能只靠 OTA。
  • 這個 app 已經上線了嗎？尚未上線時，OTA 還不是可用的更新路徑。

最後記住一條可以直接套用在自己 app 上的規則：只改 JavaScript 或 UI，就用 OTA；只要動到 native，就重新 build 並送審。前者更新的是可以在啟動時替換的 JavaScript bundle，後者改變的是 App Store 審核過的二進位檔。

到目前為止，你已經知道怎麼出 build、怎麼安裝到真機、怎麼選擇散布方式，也知道該如何判斷更新路徑。不過，雲端 build 不一定每次都成功。最後一節要處理的，就是 build 失敗時該怎麼辦。
