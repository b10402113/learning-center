NativeWind 是什麼：Tailwind 如何跑進 React Native

Step 3/5 · 建立 Expo 專案與 NativeWind

學習目標

讀完這一節，你應該能說明 React Native 為什麼沒有網頁那種 CSS，也能解釋 NativeWind 如何把 Tailwind 的 className 轉成 React Native（RN）使用的 style 物件。你還會知道，為什麼這件事需要 Babel、Metro、Tailwind 設定與 global.css 一起配合。

前言：那行 class，為什麼完全沒反應？

你剛把專案清成空白。上一節那張白紙上，index.tsx 用 StyleSheet.create 把一行字置中，你可能已經感受到那股囉唆：明明只是置中，卻得先寫一整個 style 物件。

於是你很自然地寫下這行：

<View className="flex-1 items-center justify-center bg-blue-500">

在網頁上，這樣寫就像點餐一樣俐落：藍色背景、內容置中，還要撐滿可用空間，一串 class 就全部交代了。可是存檔之後，模擬器裡的畫面紋風不動。沒有錯誤、沒有警告，就是什麼都沒發生。

這不是你打錯字，也不是 NativeWind 壞了；它只是根本還沒裝上。更重要的問題是：為什麼網頁上理所當然的 className，到了 React Native，卻得先接好一整套工具鏈才能運作？

弄懂這個原因，後面看到設定檔時，你就不必只是照文件複製貼上。每個檔案在處理什麼、哪裡接錯會出問題，也會變得有跡可循。

根本差異：React Native 沒有 DOM，也沒有 CSS

在網頁上，JSX 最後會變成瀏覽器裡的 DOM 節點。CSS 則是另一套語言，專門描述這些節點該長什麼樣子。

Tailwind 可以想成幫你快速寫 CSS 的工具。它掃描程式碼裡的 class 名稱，產生對應的 CSS 規則，再交給瀏覽器套用。整條路徑是：

你寫 class → Tailwind 產生 CSS → 瀏覽器把 CSS 套到 DOM 上。

React Native 走的是另一條路。它最後渲染的是 iOS 與 Android 的原生元件，中間沒有 DOM，也沒有瀏覽器替你套用 CSS。RN 描述樣式的方式，是把一個 JavaScript 物件透過 style prop 傳給元件：

<View style={{ flex: 1, alignItems: 'center', backgroundColor: '#3b82f6' }}>

這裡沒有 CSS 選擇器、沒有串接（cascade），也沒有 :hover 或 media query。樣式就是物件中的鍵值，直接對應到原生層的屬性。

所以，把 Tailwind 的 CSS 檔直接丟進 RN，根本行不通。RN 沒有瀏覽器，也沒有地方可以把那份 CSS 套上去。它需要的是能轉成 RN style 物件的結果。

NativeWind 的角色：把 class 翻成 style 的翻譯官

NativeWind 就像放在你和 React Native 之間的翻譯官。你可以用 Tailwind 的方式表達需求：

className="bg-blue-500 p-4"

NativeWind 再把它轉成 RN 能理解的樣式物件：

{ backgroundColor: '#3b82f6', padding: 16 }

表面上你仍然在寫 className，但最後真正傳進元件、交給原生層處理的，其實是 style。

關鍵在於：這個翻譯不是等 app 畫面出現時，才臨時找一本字典來查。它會在建置階段、程式碼被打包之前就先處理好。因為 RN 的執行環境沒有瀏覽器，不能在執行時臨時把 CSS 變成樣式，所以這件事必須由工具鏈提前完成。

也因此，安裝 NativeWind 不只是多裝一個套件。Babel 和 Metro 這兩個負責處理程式碼與打包的環節，也必須知道 NativeWind 要如何加入這條路徑。

可以把它想成同一台編譯器，換了不同的交貨對象：

  • 網頁版 Tailwind：把 class 編成 CSS，交給瀏覽器。
  • NativeWind：把 class 編成 RN 的 style 物件，交給原生元件。

輸入看起來相似，但目的地不同，背後需要的處理方式自然也不同。

四個檔案，各站哪一班崗

NativeWind 的設定分散在幾個檔案裡。第一次看到時，可能會覺得像一堆互不相干的接線；但如果把它們看成同一條生產線，每個檔案其實各自負責一個環節。

檔案它負責的環節
tailwind.config.js告訴 Tailwind 要掃描哪些檔案裡的 class（content glob），並載入 nativewind/preset 這組「class 對應到 RN 屬性」的規則與主題設定。
global.cssTailwind 的入口檔，裡面是 @tailwind base/components/utilities 三行指令。它就是被編譯的那份來源。
babel.config.js設定 jsxImportSource: 'nativewind' 與 nativewind/babel，讓 JSX 轉換階段就認得 className 這個 prop，知道要把它接進 NativeWind 的處理。
metro.config.js用 withNativeWind(config, { input }) 包住 Metro 設定，讓 Metro 的 CSS 流程去編譯 global.css，並把 NativeWind 掛進打包管線。

除此之外，還會有一個小小的 nativewind-env.d.ts。它只有一行型別參照，作用是讓 TypeScript 認得 className，不在 app 的執行路徑上。

global.css 也必須在 app 的根 layout 被 import 一次，確保這份樣式確實被載入。少了這個連結，即使其他設定看起來都正確，樣式仍可能沒有進入打包流程。

把整條生產線串起來，可以這樣看：

Babel 讓 JSX 認得 className → Metro 編譯 global.css 並接上 NativeWind → tailwind.config 決定要掃描哪些檔案、使用哪些規則 → NativeWind 根據這些資訊，把 className 轉成 style 物件。

和網頁版 Tailwind 的差異

如果你原本熟悉網頁版 Tailwind，最容易搞錯的地方，就是以為同一個 class 在 React Native 裡都會照樣有效。實際上，兩者的輸出目標和執行環境不同：

面向網頁 TailwindReact Native + NativeWind
輸出目標CSS 規則，交給瀏覽器JS style 物件，交給原生元件
誰負責套用瀏覽器（執行時）Babel / Metro（建置時）
可用的 class幾乎全部只對應得到 RN 樣式屬性的那部分
偽類與互動:hover、:focus 等齊全沒有滑鼠概念，互動樣式要用別的方式做

例如，React Native 沒有瀏覽器的滑鼠概念，因此網頁上的 :hover 不能直接照搬。NativeWind 能處理的是那些能對應到 RN 樣式屬性的 class；網頁 CSS 裡的所有能力，並不會自動出現在 RN。

另一個常見問題，是動態拼接 class。Tailwind 仰賴靜態掃描找出 class，因此像 `bg-${color}-500` 這種寫法，掃描器很可能看不出完整的 class 名稱，最後就漏掉對應樣式。這是網頁 Tailwind 會遇到的問題，在 NativeWind 裡也一樣存在。

把這個觀念掛回你的 app

當你在自己的 app 裡寫下 className 時，可以先問自己一個問題：這串文字最後要怎麼變成 RN 看得懂的 style？

RN 本身並不支援 Tailwind，真正在做轉譯的是 NativeWind 和整條建置工具鏈。tailwind.config.js 決定哪些 class 會被找到，global.css 提供 Tailwind 的入口，Babel 接住 JSX 裡的 className，Metro 則把相關流程接進打包管線。

React Native 沒有 DOM、沒有瀏覽器，樣式只能是傳給元件的 JavaScript 物件，所以網頁的 CSS / Tailwind 不能直接搬過來。NativeWind 是一個建置階段的翻譯官，把 Tailwind 的 className 翻成 RN 的 style 物件。因為 RN 沒有瀏覽器幫忙在執行時套用樣式，這個翻譯必須提前在 Babel 與 Metro 完成，這也解釋了為什麼要動到 tailwind.config.js、global.css、babel.config.js、metro.config.js 這幾個檔案，它們各站生產線上的一班崗。

下一節會把這條線實際接起來：安裝套件、建立 tailwind.config.js、加入 global.css，再調整 babel.config.js 與 metro.config.js，最後在根 layout 載入樣式。

你也可以把 NativeWind 官方文件交給 agent，請它協助完成設定。不過，先理解每個檔案在生產線上的位置，你才有辦法檢查它是否真的接對，而不是只看見畫面動了就以為一切沒問題。
