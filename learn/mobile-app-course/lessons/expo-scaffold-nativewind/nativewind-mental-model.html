NativeWind 是什麼：Tailwind 怎麼跑進 React Native

Step 3/5 · 建立 Expo 專案與 NativeWind

學習目標

能解釋 NativeWind 如何把 className 翻譯成 React Native 的 style，並說出為什麼這件事需要同時動到 Tailwind、Babel 與 Metro 三個設定檔。

前言：為什麼這個字串會突然有用？

上一節 reset 之後，你的 app 只剩一行字，樣式是用 StyleSheet.create 寫的。這樣的寫法在小畫面上還行，但等到你要做十幾個畫面、每個畫面又有幾十個元素時，就會開始想念網頁上那套 Tailwind：把 className="flex items-center gap-2" 掛上去，樣式就出來了。

問題是，React Native 根本不是瀏覽器。它沒有 DOM，也沒有 CSS 引擎；瀏覽器看得懂的 className 和 CSS，手機這一側完全看不懂。既然如此，為什麼你之後真的可以在 React Native 的元件上寫 className？

答案是有東西在中間做翻譯。NativeWind 就是這個翻譯者，而這一節要把它的翻譯流程拆開。理解這條流程的好處很實際：之後你寫了 className 卻發現畫面沒變時，你會知道要往哪幾個地方去查，而不是兩手一攤。

先看兩邊的世界各自長什麼樣

React Native 的樣式，本質上是 JavaScript 物件。它透過元件的 style 屬性傳進去，屬性名稱是 camelCase，數值代表裝置的邏輯像素：

const styles = StyleSheet.create({
  container: {
    flex: 1,
    alignItems: "center",
    justifyContent: "center",
  },
});

這個世界裡沒有階層、沒有選擇器、沒有 :hover、沒有 media query。你要某個元素長怎樣，就得把那個物件直接交給它，父子之間不會自動繼承樣式。

Tailwind 那一側則完全相反。className 只是一串字，Tailwind 本身也不是執行期的東西。它運作的方式是：在建置階段掃描你的原始碼，看看你用了哪些 class，然後產生對應的 CSS 檔；最後由瀏覽器讀懂這些 CSS 並套用到 DOM 上。真正懂 CSS 的是瀏覽器，不是 Tailwind。

把兩邊放在一起，缺口就很清楚了：Tailwind 的產出是 CSS，而 React Native 要的是 JS 樣式物件；React Native 沒有瀏覽器可以消化那段 CSS。所以如果只是把 Tailwind 裝進 React Native，className 還是一串沒人看得懂的字。

NativeWind 的角色：把 className 翻成 style

NativeWind 的定位，一句話就是「給 React Native 用的 Tailwind」。它做的事情不是重新發明一套樣式系統，而是在 Tailwind 與 React Native 之間補上翻譯層。整個流程可以拆成幾個接力站：

接力站設定檔它負責什麼
Tailwindtailwind.config.js掃描原始碼，決定哪些 class 要被產生
入口 CSSglobal.css用 @tailwind 指令標出 CSS 的進入點
Babelbabel.config.js改寫 JSX，讓 className 被辨識與轉換
Metrometro.config.js打包時把 CSS 編譯成 React Native 能吃的形式
型別nativewind-env.d.ts讓 TypeScript 認得 NativeWind 的型別

先看 Tailwind 這一站。它的設定檔告訴 Tailwind 要去哪裡找 class，並掛上 NativeWind 提供的 preset：

/** @type {import('tailwindcss').Config} */
module.exports = {
  content: ['./src/**/*.{js,jsx,ts,tsx}'],
  presets: [require('nativewind/preset')],
  theme: {
    extend: {},
  },
  plugins: [],
};

這裡的 content 很關鍵：它列出 Tailwind 要掃描的檔案範圍。只有落在這個範圍裡的 class 才會被產生。這也是之後「我明明寫了 class 卻沒生效」最常見的原因之一——檔案不在掃描範圍內，class 就被當成沒用過而丟掉了。

接著是 CSS 的入口。NativeWind 沿用 Tailwind 的三行指令當作起點：

@tailwind base;
@tailwind components;
@tailwind utilities;

Babel 這一站負責把 JSX 改寫。關鍵在 jsxImportSource 指向 nativewind，並加上 nativewind/babel：

module.exports = function (api) {
  api.cache(true);
  return {
    presets: [['babel-preset-expo', { jsxImportSource: 'nativewind' }], 'nativewind/babel'],
  };
};

最後是 Metro。它負責打包與開發伺服器，NativeWind 用一個包裝函式把它接上：

const { withNativeWind } = require('nativewind/metro');

const config = getSentryExpoConfig(__dirname);

module.exports = withNativeWind(config, { input: './src/global.css' });

真實專案裡的 metro.config.js 可能還有其他設定（例如 Sentry 的包裝），但最核心的就是這一行 withNativeWind(...)：它告訴 Metro「這個 CSS 是入口，請把它一起編譯進 bundle」。上面的 getSentryExpoConfig 是另一個功能帶進來的，跟 NativeWind 無關，這裡先略過。

把這幾站串起來，流程就是：Tailwind 掃描原始碼產生 CSS，Metro 把 CSS 打包成 React Native 能用的樣式表，Babel 在編譯時把 className 改寫成對應的樣式，最後執行期把樣式物件交給元件。你用起來只寫了一串 className，背後是一條接力。

為什麼不能只改一個設定檔

第一次看到要改這麼多檔案，很容易想問：難道沒有一個「打開 NativeWind」的開關嗎？

沒有，因為這幾個工具各自負責不同階段，而且它們本來就是獨立的。Tailwind 只懂掃描與產生 CSS，它不知道 JSX 長怎樣；Babel 只負責把原始碼轉成別的形式，它不知道 Tailwind 的 class 有哪些；Metro 只負責打包與解析模組，它不懂 CSS 的選擇器。NativeWind 的角色是提供這三者之間的介面：Tailwind 的 preset、Babel 的 jsxImportSource 與 Metro 的 wrapper。所以你不是在設定一個開關，而是在把三個獨立工具接上同一條管線。

也因為每個工具各管一段，故障的時候可以沿著這條線往回找：class 沒生效，先看 content 有沒有涵蓋那個檔案；改過 Babel 或 Metro 設定後樣式才壞掉，通常是快取沒清、或設定根本沒被讀到。這條管線就是你的除錯地圖。

邊界與取捨

NativeWind 不是把整個瀏覽器的 CSS 搬進手機，它有明確的邊界。React Native 沒有 DOM，所以依賴 DOM 結構或瀏覽器行為的功能不會存在；className 主要作用在 React Native 的核心元件（例如 View、Text、Pressable）上。當你使用第三方元件時，得看它有沒有支援 className，沒有的話還是要回到 style 屬性。

不過 className 與 style 並不完全互斥，兩者可以並用。真實專案裡就常看到這種寫法：大部分樣式交給 className，少數需要動態計算的值（例如依照安全區域算出來的邊距）則由 style 提供。

React Native styleNativeWind className
寫法JS 物件或 StyleSheet.create一串 class 名稱
執行方式執行期直接傳給元件建置期經由 Babel／Metro 轉換
動態值天然支援，可即時計算適合靜態樣式，動態值仍可搭配 style
規模變大時容易散落各處、重複可重用的 class 讓樣式保持一致

小結

React Native 只懂 style 物件，Tailwind 只產生 CSS，兩者之間原本接不起來。NativeWind 補上翻譯層：tailwind.config.js 決定掃描範圍、global.css 是入口、Babel 改寫 className、Metro 打包 CSS。會動到多個設定檔，是因為它是在串接三個獨立工具，而不是打開一個開關。

有了這張流程圖，動手接線就不再是照抄神秘設定，而是知道每一行為什麼存在。下一節就照著這個模型，把套件裝好、把四個設定檔接起來。
