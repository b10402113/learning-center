跑起來並確認樣式生效

Step 5/5 · 建立 Expo 專案與 NativeWind

學習目標

能用一個 className 改畫面、存檔後驗證熱更新生效，並在樣式沒出現時依序排查快取、設定檔、CSS 匯入位置與 class 寫法。

前言：它沒報錯，不代表它有用

上一節把 NativeWind 的管線接好了，但「接好」和「確認會動」是兩件事。這裡有一個很容易讓初學者吃悶虧的特性：當 className 沒有被正確編譯時，React Native 不會報錯。畫面只是維持原樣，安安靜靜地什麼都不說。

為什麼會這樣？因為對 React Native 來說，一個它不認得的屬性就只是被忽略而已。所以如果你沒有主動製造一個「看得見的改變」來驗證，很可能會在錯誤的基礎上往下做好幾個畫面，直到某天發現所有樣式根本沒生效。

這一節要做三件事：把畫面改成用 className 寫、存檔確認熱更新、然後學會沿著管線排查「樣式沒出現」的原因。做完之後，你就有一個真的活著、改了就變的空白 app。

動手前先確認的事

  • NativeWind 已安裝，四個設定檔都接好，並且用 npx expo start --clear 重啟過。
  • src/global.css 已在根 layout 被匯入。
  • 你知道樣式沒生效時不會有錯誤訊息，所以必須刻意驗證。

第一步：把 index.tsx 改成 className

先在 src/app/index.tsx 寫一個最小、明顯的版本，把原本的 StyleSheet 換成 className：

import { Text, View } from "react-native";

export default function Index() {
  return (
    <View className="flex-1 items-center justify-center bg-white">
      <Text className="text-2xl font-bold text-black">Hello NativeWind</Text>
    </View>
  );
}

跟 reset 後的版本比一下，差別很明顯：原本要另外寫一個 styles 物件、再透過 style={styles.container} 綁定，現在樣式直接以 class 名稱掛在元件上。這就是 NativeWind 帶來的寫法改變。

真實專案裡的畫面會更複雜，但道理一樣。例如下面是購物類 app 的一個區塊，用 className 控制排版、顏色、字重與間距：

<View className="mt-[22px] flex-row items-center justify-center gap-[10px]">
  <Image
    source={require("@/assets/images/logo-mark.png")}
    style={{ width: 41, height: 47, marginBottom: 8 }}
    contentFit="contain"
  />
  <Text className="text-[32px] font-bold text-black">Bulky AI</Text>
</View>

這裡也能看到剛剛提過的並用方式：外層 View 同時掛了 className 與 style，靜態樣式走 className，需要依照裝置動態計算的安全區域邊距走 style：

<View
  className="flex-1 bg-[#FEFDFD]"
  style={{ paddingTop: insets.top, paddingBottom: insets.bottom }}
>

第二步：存檔，觀察熱更新

存檔之後，Metro 應該會自動重新整理畫面。如果沒有，在跑著 npx expo start 的終端機按 r 重新載入。正常的話，你剛才寫的「Hello NativeWind」會以大字、粗體、置中出現在白色背景上。

接下來做一個更刻意的測試：把背景 class 從 bg-white 改成 bg-yellow-200，存檔。畫面應該立刻變成淡黃色。

這個小動作其實在做一件重要的事：它證明 className 真的被編譯、真的有作用，而不是 React Native 剛好幫你套了預設樣式。因為如果 NativeWind 沒接好，這一串 class 會被整個忽略，畫面不會有任何顏色變化。

熱更新更新了哪一層

存檔就變畫面這件事，背後是 Metro 把 JavaScript 重新打包、送到執行中的 app 裡。所以這種即時更新只涵蓋 JavaScript 這一層：樣式、文字、邏輯的改動都能立刻反映。

但如果你動的是原生那一層，例如安裝了一個新的 native module、或改了 app.json 裡牽涉原生設定的欄位，熱更新就幫不上忙，得重新做一次原生建置。這也是為什麼後面章節會把「什麼時候需要 dev build」單獨拿出來講。在目前這個節點裡，你改的全是 JS 與樣式，所以存檔即時生效是正常的。

把這條界線記在心裡，之後遇到「改了卻沒反應」時，你就能先判斷是快取問題、設定問題，還是根本需要重新建置——而不是亂槍打鳥。

第三步：樣式沒出現時，沿著管線排查

如果改了 class、存了檔，畫面卻紋風不動，別急著重裝套件。依照上一節的管線，從最可能的原因往後查：

  1. Babel 或 Metro 改過之後沒有清快取重啟。這是最常見的原因。設定改完後一定要用 npx expo start --clear，普通的熱更新不會重新套用建置期設定。
  2. 檔案不在 Tailwind 的 content 掃描範圍內。對照 tailwind.config.js 的 glob，確認你正在編輯的檔案真的被涵蓋。檔案在範圍外，class 就不會被產生。
  3. Metro 的 input 路徑和實際 CSS 檔不一致。一個寫 ./src/global.css、另一個放在別的位置，就找不到入口。
  4. 根 layout 忘了 import "@/global.css"。少了這一行，前面都對，執行期還是沒有樣式。
  5. class 掛在不支援的元件上。className 主要作用在 React Native 核心元件；第三方元件若沒支援，就得改用它的 style 或自訂屬性。

第四步：小心動態拼接 class

還有一個很隱蔽、之後一定會踩到的陷阱：Tailwind 是靠靜態掃描原始碼來決定產生哪些 class 的。所以如果你用變數把 class 名稱拼出來，Tailwind 掃描時看到的只是樣板字串，認不出完整的 class，那條樣式就不會被產生。

// 掃描時只看到 bg- 與 -500，認不出完整的 class
<View className={`bg-${color}-500`} />

正確的做法，是讓每個可能用到的 class 名稱完整地出現在原始碼裡，再用條件選擇其中一個：

<View className={active ? "bg-black" : "bg-white"} />

這樣 Tailwind 掃描時，bg-black 與 bg-white 都是完整的字串，兩者都會被產生，執行期再由條件決定用哪一個。記住這條規則，可以省下很多「為什麼這個顏色有時有、有時沒有」的困惑。

做完會看到什麼

到這裡，你應該有一個能在模擬器跑、存檔即時更新、而且 className 真的會生效的空白 Expo app。它沒有功能，但它是往後每一張畫面、每一個功能的落腳處。之後你請 AI agent 照著 plan.md 做 UI 時，依靠的就是這個已經接好樣式管線的環境。

這個節點的五步到此完成：scaffold、reset、理解 NativeWind、接線、驗證。你現在有了一個可靠的地基，可以開始往上蓋第一張真正的畫面了。

回頭看，這五步其實是一個很典型的「從零到可開工」流程：先拿到合法的初始專案，再清掉別人的痕跡，接著理解你要引入的工具在整條管線裡的位置，動手接好，最後刻意驗證。之後你換一個新點子、開一個新專案時，這套流程幾乎可以原封不動地重跑一次。真正會變的只有你要裝的套件與要寫的畫面，而「先確認地基會動，再往上蓋」這個習慣，才是這一段最值得帶走的東西。

小結

NativeWind 接好之後，要用一個明顯的 className 改動來驗證它真的生效，因為未編譯的 class 不會報錯。樣式沒出現時，依序檢查：清快取重啟、Tailwind 的 content 範圍、Metro 的 input 路徑、根 layout 的 CSS 匯入、元件是否支援 className。另外，class 名稱要完整出現在原始碼，不能被動態拼接掉。
