先用假資料，把 UI 做完整

Step 3/5 · 設計到 UI 的比對迴圈

前言：畫面要先完成，還是等資料庫？

你已經學會用截圖迴圈，把單一畫面做到接近設計稿。接著做首頁時，新的問題很快會出現：首頁需要顯示貼文、頭像、按讚數與留言數，但後端、資料庫和登入機制都還沒完成。

這時候，很多人會選擇先停下來，等後端做好再回頭做 UI。看起來是在等必要條件，但這其實是把兩條原本可以並行的工作綁在一起。畫面長什麼樣子，和資料從哪裡來，本來就是兩件不同的事。

這一節要建立的觀念很簡單：後端還不存在時，先用假資料把完整 UI 做出來；等真資料準備好，再把資料來源換掉。就像先把店面裝潢好，商品到貨後直接上架，而不是等商品全部進貨才開始裝潢。

學習目標

學完後，你應該能在後端尚未完成時，使用假資料與空狀態把整個 UI 建起來，也知道之後如何把真資料換進同一套畫面，而不必重新製作版面。

為什麼設計可以先於資料完成

重點是，設計和資料可以看成兩條分開處理的軸。

設計決定畫面上有哪些區塊、它們長什麼樣子，以及彼此如何排列。資料則決定每個區塊裡實際填入哪些內容。截圖迴圈要比對的是設計軸，所以畫面只要有符合形狀的內容，就能進行檢查；那些內容是不是來自真正的資料庫，並不是此刻的重點。

課程中的做法很直接：在資料庫還沒接上時，先告訴 agent：「目前沒有資料庫，也沒有任何資料，所以先建立一些假資料，按照參考圖把 UI 做出來。」agent 便能在畫面裡放入寫死的測試資料，先把版面、尺寸與內容排列完成。

等 UI 定案後，後端再把真實資料送進同一套元件。這時候通常只需要更換資料來源，畫面本身不必重新製作。設計一旦固定，替換資料往往是比較輕鬆的那一步。

弱做法：等後端完成，UI 才開始

「先等資料庫和 API 都好了再做畫面」聽起來很穩，實際上卻讓前端進度被後端卡死。後端延遲一天，UI 就跟著延遲一天；而且等真資料終於接上，才第一次看見真實內容塞進畫面的樣子，版面問題可能一次全部冒出來。

這種做法就像等家具、商品和所有設備都送到，才開始丈量店面。只要其中一樣延遲，整間店就無法動工。

強做法：先用形狀正確的假資料

更好的做法是先把資料來源暫時替換成假資料，但資料的欄位和形狀要接近未來的真資料。以貼文為例，假資料可以先包含作者、內容、按讚數、留言數與時間。

假資料不需要看起來很熱鬧，重點是它能撐起未來的 UI 結構。之後接上後端時，替換的是「資料從哪裡來」，不是「畫面要怎麼組成」。

你可以把它想成開店：先把貨架、動線、燈光與招牌做好，讓空間看起來就是一家店；商品到貨後直接上架即可。假資料就像先放在貨架上的樣品，作用是讓你檢查這家店好不好逛，而不是拿來真正販售。

假資料也要「長得像」真資料

假資料不能隨便塞幾個文字進去就算完成。它最好具備未來真資料會有的欄位與資料形狀，否則畫面現在看似完成，接上後端時仍可能需要大幅修改。

例如，貼文卡片如果預期會顯示作者、內容、按讚數、留言數與時間，假資料就應該先提供這些欄位。這樣元件可以先按照正式的資料結構建立，後續只要將測試資料替換成查詢結果。

這個做法讓截圖迴圈能在後端尚未完成時就開始運作。你可以先確認間距、比例、文字長度與卡片排列，而不是把這些問題全部留到最後才處理。

空狀態也是設計的一部分

假資料處理的是「有內容」的畫面，但新使用者第一次打開 app 時，可能根本沒有任何貼文。這時候畫面要顯示什麼？如果只留下一片空白，使用者很容易以為 app 壞掉了。

因此，空狀態（empty state）也要在 UI 階段一起設計。它不是等資料庫完成後才補的例外畫面，而是產品體驗的一部分，後端還沒做好時一樣能先做。

課程中的社群 app 就有一個清楚的例子。首頁的動態牆在沒有任何貼文時，會顯示引導文字和行動按鈕，而不是留一片空白。它的空狀態大致長這樣：

<View>
  <Text>Your feed starts here</Text>
  <Text>Share your first moment, or discover people to follow.</Text>
  <Pressable>Create a post</Pressable>
  <Pressable>Explore the community</Pressable>
</View>

這段內容是設計的一部分，不依賴資料庫裡存在任何真實資料，卻會直接影響新使用者對 app 的第一印象。

在使用假資料的階段，就把「有資料」和「沒有資料」兩種畫面都做完。等真資料接上後，只需要根據結果切換這兩條分支，兩邊的 UI 都已經準備好了。

用 feed.tsx 看懂「先假後真」

課程專案裡的動態牆元件，就是這個觀念的實際例子。它是一個 LiveHome 元件，使用 usePaginatedQuery 向後端取得貼文，再交給 FlatList 逐筆渲染成卡片。列表上方有標題與限時動態，下方則有載入更多的功能；當列表沒有內容時，就顯示前面介紹的空狀態。

在後端接上之前，這個元件的資料其實可以先寫成測試資料，但畫面仍然能完整呈現。這就是「先假後真」的價值：元件結構、版面比例與空狀態先定案，之後只替換資料來源。

元件裡有個細節：它用 const s = width / 390 算出縮放比例，讓所有尺寸按照裝置寬度等比例調整。這表示設計是以 390 點寬的參考圖為基準，換到其他寬度的裝置時，畫面會跟著縮放，而不是整個版面失去比例。

階段資料來源畫面如何確認
先做 UI畫面內寫死的假資料透過截圖迴圈比對並定案
接上後端真實的查詢結果版面維持不變，只替換資料來源
沒有資料時不需要資料顯示預先設計好的空狀態

把設計與資料接回同一個架構

設計與資料是可以分開處理的兩件事。後端還沒完成時，先用欄位與形狀正確的假資料，把整個 UI 和空狀態做完整；真資料到位後，再替換資料來源，畫面通常不需要大幅修改。假資料不是拿來假裝後端已經做好，它的用處是讓設計能早一點被看見、比對，然後定案。

現在你知道，畫面的建造順序可以先做 UI、再接資料。這也把前端與後端拆成兩條能夠並行的線：前者先確認設計，後者再提供真實內容。

不過，畫面還沒對齊時，還有一個更細的決定要面對：修改要一次改一項，還是把好幾個問題一起交給 agent？下一節就來談修改的粒度。
