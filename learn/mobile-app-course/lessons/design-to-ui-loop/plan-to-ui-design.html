從 plan 到 UI：先做出設計，再讓 agent 照圖施工

Step 1/5 · 設計到 UI 的比對迴圈

前言：規格書完成了，畫面卻還是空白

plan.md 寫完了。features、pages、tech stack 都列得清清楚楚，你打開編輯器，準備做第一個畫面，卻發現規格書只寫了「登入頁要有 Google 和 Apple 登入」，沒有告訴你按鈕長什麼樣、標題多大、間距多寬。

如果這時直接叫 agent「做一個登入頁」，它通常能生出一個可以執行的畫面，但風格像不像你想要的，幾乎要靠運氣。這也是許多人第一次用 AI 蓋 UI 時最容易卡住的地方：東西確實做出來了，卻總覺得不對；想請 agent 修改，又說不清楚什麼才算「對」。

這一節要建立的觀念很簡單：寫程式之前，先產出一份看得見的 UI 設計。它不只是給人看的參考圖，也會成為 agent 後續拿來比對的目標。有了目標，「做得對不對」就不再只是主觀感覺，而會變成可以檢查的問題。

你會得到什麼

學完後，你應該能把 plan.md 轉成一份 UI 生成 prompt，產出整個 app 的 UI 設計，再拆出 design system 與各個畫面的參考圖。同時，你也會知道這些圖該放進 design/，還是放進 assets/images/。

為什麼不能直接從 plan 寫程式

關鍵在於，plan.md 描述的是功能，不是視覺。它會告訴你這個 app 有登入、首頁和個人檔案，卻不會回答登入頁的標題該多大、按鈕要圓角還是方角，以及主色應該選什麼。

這些視覺決策如果留白，agent 只能自己猜。它猜出來的畫面也許可以執行，卻不一定符合你的期待。就像請工人蓋房子時只給他房間用途，卻沒有給平面圖、建材和樣式；房子可能蓋得起來，但最後長什麼樣，誰也說不準。

更重要的是，下一步的 screenshot-compare 迴圈需要一個明確目標。它的邏輯是：先做出畫面，再截圖，接著和設計比對；如果不像，就修改。沒有設計，就沒有東西可以比對，這個迴圈也無從開始。

所以這一節不是在做額外的美編工作，而是在替後續開發準備一個可檢查的標準。

把 plan.md 變成 UI 生成 prompt

第一步，是把 plan.md 當成原料，請 agent 幫你寫一份用來生成 UI 的 prompt。你可以這樣描述：「讀我的 plan.md，依照這份計畫中的畫面與功能，幫我產生一份 UI 生成 prompt。」接著附上一份現成的範例 prompt，讓 agent 參考格式。

agent 會依照範例的結構，把你的 plan 填進去。這裡有個容易忽略的重點：這份 prompt 應該從你的 plan 長出來，而不是憑空發想。

plan 裡有幾個畫面、每個畫面需要哪些功能，會決定 prompt 裡描述哪些介面。也正因如此，規劃必須先做；沒有 plan，生成出來的 prompt 就像沒有地基的房子，看起來或許完整，卻沒有可靠的根據。

拿到 prompt 後，把它貼進圖像生成模型，例如 GPT 或 Gemini，讓模型產出一張完整的 app UI 圖。這張圖通常會把好幾個畫面排在一起，像是整個 app 的縮影，方便你一次看見整體的風格走向。

第一版不理想，是正常的

圖生成出來後，先不要急著判定成功或失敗。實際經驗通常是：第一版「不醜，但太花俏」。作者第一次拿到的設計顏色太滿，不符合期待；他於是提供一張真實 app 的截圖當參考，並補上「要 light mode、去掉藍色系、盡量極簡」等限制，第二版才逐漸變成乾淨的樣子。

logo 的生成過程也很能說明這件事。原本只說「參考這些 logo」，結果不如預期；後來改成「參考 Apple 的 logo」，模型卻真的產出一堆蘋果。於是又補上「做一個不同於 Apple 的東西」，結果才慢慢收斂。

最後，還需要進一步指定「改成黑白、不要紫色、透明背景，並提供深色和淺色兩種版本」。這些限制越清楚，模型越容易朝你要的方向調整。

有件事值得記住：AI 不一定會在第一次就交出最好的結果。你需要多 follow up 幾次，提供參考圖，並把限制說清楚，才比較容易得到真正喜歡的設計。第一次不滿意是常態，不是失敗。

design system：把設計裡的零件單獨列出來

除了整張 app 設計總覽，還要請模型另外產出一張放大的 design system（設計系統）圖，並且讓每個畫面各自放大成一張參考圖。

最後你會得到三種素材：

  • 一張整個 app 的 UI 總覽。
  • 一張放大的 design system，也就是設計裡的零件表。
  • 一張張獨立的畫面參考圖。

為什麼不能只看總覽？因為總覽圖把許多畫面擠在一起，agent 要從裡面找出所有顏色、字體和元件，會相當吃力；而且總覽不一定會呈現每個細節。

單獨的 design system 圖則能把元件長相、色票、字體等資訊清楚放大，讓 agent 更容易讀取並沿用。

design system 像貼在牆上的色票與字體樣張，每張畫面參考圖則像建築立面圖。agent 是照著圖施工的師傅；兩種圖都準備好，它才不會憑空亂做。

你也不必一開始就把每個畫面全部設計完成。當手上累積了足夠的參考圖，agent 就能從既有設計推斷其他畫面應該長什麼樣。先處理重要的幾張，再讓它延伸其餘畫面即可。

design/ 與 assets/images/：兩種圖，兩種用途

設計產出後，要把它們收進 repo，而且必須分清楚兩類用途完全不同的圖片。課程裡的慣例，是在專案下建立 design/，同時沿用 Expo 原本的 assets/images/。

資料夾放什麼給誰用
design/整個 app 的 UI 設計圖、放大的 design system、每個畫面的參考圖給 agent 讀，作為比對目標
assets/images/app 實際會用到的圖片，例如 logo、示範用的 demo 圖給程式引用，會出現在執行中的畫面裡

分辨方式很直覺：如果圖片是「拿來對照的範本」，就放在 design/；如果圖片本身會被包進 app，並在執行時顯示，就放在 assets/images/。

例如，登入畫面裡那張示意手機的插圖，是 runtime 要顯示的資產，應該存進 assets/images/。登入畫面的設計參考圖則是給 agent 對照用的，應該放進 design/。

還有一個小細節可以先記住：logo 和其他會放進 app 的 runtime 圖片，最好請模型製作成透明背景。app 的底色通常是白色，如果圖片自己帶著一塊底色，貼上去時就會像多了一塊突兀的方形紙片。透明背景能讓圖片自然融入畫面。

小結：先有目標，才談得上像不像

在寫程式之前，先把 plan.md 變成一份看得見的 UI 設計。請 agent 從 plan 產生 UI 生成 prompt，再把 prompt 貼進圖像模型，產出整張設計圖。第一版通常不會理想，需要透過參考圖和明確限制多迭代幾輪。設計定案後，再拆成 design system 與各畫面的獨立參考圖，放進 design/；logo 等 runtime 資產則放進 assets/images/。這些圖不是裝飾，而是 agent 後續比對時使用的目標。

現在，你手上已經有一份可以對照的設計。下一個問題是：怎麼把其中一張參考圖，變成 app 裡真正能執行的畫面？這正是下一階段的核心：screenshot-compare 迴圈。
