screenshot-compare 迴圈：把參考圖變成一致的畫面

Step 2/5 · 設計到 UI 的比對迴圈

先確認目標與前置條件

這一節要讓你能把一個畫面完整跑過一次 screenshot-compare 迴圈：附上參考圖、要求 agent 建立畫面、從模擬器截圖比對，再持續修正，直到畫面達到可接受的一致程度。

上一節結束時，design/ 裡已經有登入畫面的參考圖。它可能看起來很漂亮，但終究只是一張圖；你真正要的是 app 裡能點、能輸入、能登入的畫面。

動手前要先確認兩件事。第一，app 必須能在模擬器裡跑起來，因為每一輪都需要從模擬器擷取畫面。第二，你手上要有目前畫面的參考圖，也就是上一節放進 design/ 的檔案。

啟動 app 可以使用 npx expo start。啟動後，在終端機按 i 開啟 iOS 模擬器，按 a 開啟 Android。若專案用了原生模組，例如之後會碰到的相機或 native tabs，則要改用 npx expo run ios 重建原生開發版。

先確認目標畫面真的能開，再開始比對。否則就像拿著尺去量一堵還沒蓋好的牆，後面的結果很難判斷。

先看完整流程：五個動作反覆跑

整個流程可以拆成五個動作。跑完一輪不代表結束，它會反覆繞回去：

  1. 把參考圖交給 agent。 你可以在對話裡附上設計圖，也可以在 prompt 裡用檔名指向它，例如 add homescreen-ref.png。檔名越明確，agent 越知道要拿哪一張圖當目標。
  2. 下達進入迴圈的指令。 指令要同時說清楚要建立什麼畫面，以及要如何驗證結果。
  3. 讓 agent 建立並檢查畫面。 它會把畫面做出來，從模擬器截圖，再和參考圖比較。
  4. 判斷是否達標。 若截圖和設計一致，就停止；若還有差異，就繼續修正。
  5. 修正後重新執行。 修完要再截圖、再比對，回到判斷這一步，直到畫面達到可接受的程度。

第一步：用參考圖設定目標

不要只對 agent 說「做一個好看的登入頁」。這種說法沒有清楚的驗收標準，最後很容易變成你盯著畫面想：「好像有點像，但哪裡又怪怪的。」接著只能反覆用模糊的文字描述差異。

請直接把參考圖附上，或在 prompt 中指定檔案名稱。這樣一來，agent 手上就有一張能拿來比較的具體目標，不再只是抽象的「像設計」。

第二步：下達核心指令

接著要求 agent 同時負責建畫面與驗證。課程裡使用的指令很直接，你可以先照著這個句型使用：

Build the authentication screen.
Take a screenshot from the simulator and compare it to the actual design.
If it is identical, just stop. If it is not, keep going.

這三句各自負責一件事：

  1. Build the authentication screen.：建立 authentication screen，也就是登入或驗證畫面。
  2. Take a screenshot from the simulator and compare it to the actual design.：從模擬器截圖，再拿它和真正的設計圖比較。
  3. If it is identical, just stop. If it is not, keep going.：如果已經一致就停止；如果還不一致，就繼續修改。

這個寫法的關鍵，在於把驗收依據交給截圖，而不是交給你臨時描述「左邊間距好像多了兩像素」。agent 可以根據畫面本身找差異，再自行進入下一輪修正。

作者把同一套方法用在 Claude 上時，稱它為 build and verify loop，也就是「建造與驗證迴圈」；在 Codex 上則稱為 screenshot-and-compare loop。名稱不同，做法相同：讓 AI 把畫面本身當成考卷。

之後每個畫面都可以沿用同一句指令，只要把 authentication screen 換成當下的畫面名稱。如果不想每次重新輸入這段文字，第五節會再教你把它整理成可以重複使用的 skill。

第三步：讓 agent 建畫面並自己檢查

以首頁為例，先附上 homescreen-ref.png，再告訴 Codex 進入這個迴圈，建立首頁。此時如果專案還沒有資料庫、也沒有任何資料，就先建立假資料，讓 UI 能按照參考圖呈現。

接下來 agent 會依序建立畫面、從模擬器截圖、和參考圖比對。比方說，它可能發現某個區塊發生 overflow，也就是內容溢出原本的容器；這時就修正版面，再重新截圖與比對。

你不需要每一秒都盯著它。作者提到，自己常常按下送出後先去做別的事，回來時 agent 可能還在迴圈中，也可能已經停在「看起來幾乎一模一樣」的狀態。差別在於，你不再和 agent 一來一往地猜問題，而是讓它在明確的目標下逐步收斂。

第四步：判斷什麼時候停止

這個迴圈要的是畫面一致到符合你的需求，不用做到像素級全等。AI 無法保證每次都能做到 100% 相同，但通常可以修到非常接近。

例如在 welcome 畫面的實作中，第一輪結果並不完美。經過幾輪比對後，三行文字調整成兩行，過重的字重也從約 700 調整到約 500，最後已經達到作者認為「基本上一模一樣」的程度。

因此，若截圖與參考圖已經符合你的判斷，就可以停止。若你仍能清楚看出差異，就回到修正步驟。重點是，這次的判斷有截圖作為依據，不再只是憑感覺說「好像不太對」。

第五步：卡住時，自己截圖再給精準指令

AI 不一定每次都能完美收尾。有時 agent 認為自己已經完成，但你看一眼就發現某個地方還不對。這時不要用一大段文字描述整個問題，直接自己截圖，貼進對話，再補上一句範圍明確的修正指令。

在 Mac 上，可以使用 command + control + shift + 4 截圖，完成後直接貼進聊天視窗。作者在處理 native tabs 後方的灰色背景時，就是附上截圖，再補充：「tabs 的樣子對了，但把灰色背景拿掉，讓後面的 app 透出來。」這樣很快就完成修正。

顯示目前狀態最快的方法，是截圖加上一句精確的修正，而不是用文字長篇描述問題。文字容易有歧義，截圖不會。

完成後，你應該看到什麼

一輪成功的 screenshot-compare 迴圈，會留下這樣的結果：

  • app 能在模擬器中開啟目標畫面。
  • agent 已經根據參考圖建立 UI。
  • 它能從模擬器擷取畫面並比較。
  • 發現差異時會修正並重新比對。
  • 最後畫面達到你認為可接受的一致程度。

換句話說，驗收變成固定執行「建畫面 → 截圖 → 比對 → 修正 → 重跑」，不再只是做完後你自己憑感覺看一下。這一節先處理單一畫面如何對齊設計；至於多個畫面應該按照什麼順序建立，則是下一節要處理的問題。

把參考圖當成目標，讓 agent 進入「建畫面 → 從模擬器截圖 → 跟設計比對 → 修正 → 重跑」的迴圈。關鍵指令是：建好畫面後自己截圖、跟設計比對，一樣就停，不一樣就繼續。agent 卡住時，自己截一張圖加一句精準修正，通常比用文字形容有效得多。迴圈追求的是一致到可接受，不是像素級全等。
