一次只改一個問題，只動該動的地方

Step 4/5 · 設計到 UI 的比對迴圈

前言：畫面對不上時，該怎麼下指令？

上一節把畫面的建造順序講清楚了。現在回到迴圈裡最常遇到的場景：截圖比對後，你發現畫面同時有三個問題：間距太大、標題字重太重，還有一個區塊 overflow 了。

這時，你會把三個問題一次交給 agent，還是一次只說一個？前者看起來比較省事，後者則比較容易追蹤結果。其實沒有永遠正確的答案，關鍵在於：這些修改會不會互相牽動。

這一節會提供一套判準，幫你決定什麼時候該一次改一項、什麼時候可以整批處理；如果你只想調整畫面的一小塊，也知道該怎麼描述範圍，免得把已經做對的部分一起改壞。

先把兩種做法放在一起比較

面向一次改一項整批一起改
速度來回次數較多，單輪比較慢一輪處理多個，看起來比較快
可除錯性修改完成後，容易知道是哪個改動造成結果結果不如預期時，很難分辨是哪個改動出了問題
風險範圍較小，比較不容易影響其他地方改動互相牽連時，容易顧此失彼
適合的場景彼此可能互相影響的視覺修正照文件執行的固定設定步驟

課程作者在實作時選擇「一次改一項」。首頁的流程就是這樣跑：先截圖，請 agent「修掉這個 overflow」；確認修好後，再提出下一個要求，例如「把這些 tab 換成 native tabs」。每一輪只有一個主要目標，完成後才往下一輪走。

這種做法的好處，是能把變數控制住。間距、字重、對齊等視覺屬性，常常像一排互相咬住的齒輪，動了一個，其他地方也可能跟著變化。如果一次修改三項，畫面最後仍然不對，你就很難判斷是哪一項沒做好，或是哪一項抵銷了另一項的效果。

先問自己三個問題

  1. 這幾個修正會不會互相影響？如果會，應該一次只改一項。
  2. 如果結果不對，我能不能確定是哪個改動造成的？如果不能，就把修改拆開。
  3. 這是不是一組照著文件執行的固定步驟？如果是，可以整批交給 agent 一次完成。

這三個問題的核心，是判斷你是否需要在每一輪之間觀察視覺結果。需要觀察，就不要急著把多個變數塞進同一個 prompt；不需要觀察，只是照既定文件完成設定，整批處理通常更合理。

反例：一次一項不是永遠的鐵律

如果把「一次只改一項」套用到所有工作上，反而會變得笨重。有些工作本來就是一整組固定流程，拆開後不但沒有更安全，還可能讓上下文斷掉。

例如安裝 NativeWind，或把 tab 換成 Expo 的 native tabs。這類工作有官方文件，也有既定的先後順序。你可以把整份文件交給 agent，請它照著完成，而不必把每個安裝步驟拆成獨立指令，一項一項等確認。

真正的分界線不是「一次幾個動作」，而是「中間是否需要根據視覺回饋做判斷」。需要看畫面、確認結果，再決定下一步的視覺修正，就一次一項；只是機械地依照文件執行，就可以整批處理。

只想動一小塊時，先把範圍框出來

除了修改的數量，「要改多大的範圍」也同樣重要。有時候畫面大部分已經符合預期，只有一小塊需要調整。此時不要只描述新的目標，也要清楚說明哪些地方必須保留。

課程裡重新設計貼文詳情頁時，作者先讓模型生成三個版本，再選定其中一個。接著，他要求 agent 只更新底部區塊，並保留目前比較好的頁首。最後，頁首完全沒動到，只有指定的區塊重新設計過。

如果當時只說「照這張新圖重做整個畫面」，agent 很可能會把整張頁面視為待重建的範圍，連原本已經做對的頁首也一起改掉。

把「保留什麼」講清楚，和把「要改什麼」講清楚一樣重要。你沒有劃出界線，agent 就可能合理地以為整張圖都要重來。

生成設計變體時，別忘了帶上 design system

同樣的範圍控制，也適用於生成新畫面的設計變體。想為某個畫面做幾種風格選項時，應該把既有的 design system 一起附在 prompt 裡，並要求新變體維持現有風格。

課程裡重新設計貼文詳情頁時，作者就是這麼做的：把 design system 提供給模型，請模型依照這套系統產生三個變體。如此一來，產出的版本會像同一個 app 的不同方案，而不是三個風格各自分家的產品。

所以，design system 不只是在實作時拿來對照，也能在生成新設計時限制風格。它像一條主線，把不同頁面和設計變體的風格串在一起，讓它們仍然像同一個 app。

最後的決策規則

視覺修正如果可能互相影響，就一次只改一項，保留清楚的因果關係；如果只是照文件執行的固定步驟，就整批交給 agent。只想調整局部時，明確說出「只動這裡、其餘保留」；生成新變體時，附上 design system，讓風格維持一致。

你可以把這段規則當成每次修改前的檢查表：會不會互相影響？需不需要看結果再決定？是不是固定文件流程？範圍是否已經畫清楚？先回答這幾個問題，再決定要拆開修改，還是整批交給 agent。

到這裡，你已經有一套把設計穩定轉成畫面的流程，也知道該如何拿捏修改粒度。最後一節會替這套流程收尾：與其每次重打那串迴圈指令，不如把它整理成可重複使用的 skill。
