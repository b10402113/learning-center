把登入接進 Expo：設定 Clerk SDK 與登入按鈕

Step 4/5 · Clerk 多供應商登入

這一節要完成什麼

這一節的目標，是把 Clerk 的 Expo SDK 接進 app，並在 onboarding 的最後一頁放上真正能使用的 Google 與 Apple 登入按鈕。完成後，使用者會先完成 onboarding，再進入登入流程。

你也會學會如何把設定工作交給 AI agent，以及怎麼驗收 agent 是否做對。最後，還要決定登入畫面要自己刻，還是先使用 Clerk 的預製 UI。

動手前先確認前置條件

開始之前，請確認以下項目都已經完成：

  • Clerk application 已建立。
  • Google 與 Apple 登入已啟用。
  • Native applications 已開啟。
  • .env 已填入 EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY。
  • Onboarding 畫面已在前一個節點完成。

另外，這個 app 之後要用 dev build 執行，而不是 Expo Go。Clerk 的原生登入流程依賴原生模組，需要 expo-dev-client，並透過 npx expo run ios 產生開發用建置。這一節先把程式接好，實際測試留到下一節。

先看整體流程：從設定到可登入

上一節完成的是 Clerk 後台設定：Google 與 Apple 已經打開，publishable key 也放進 .env。但這時候 app 還不知道 Clerk 的存在，就像家裡已經裝好網路，卻還沒有把路由器接上。

這一節會依序做四件事：

  1. 把 Clerk SDK 安裝並接到 app 的根層。
  2. 讓 onboarding 最後一頁的按鈕可以啟動 Google 與 Apple 登入。
  3. 把登入按鈕放到正確的位置，並調整成符合 app 主題的樣子。
  4. 根據設計需求，選擇自製原生登入畫面或 Clerk 預製 UI。

第一步：把 SDK 設定交給 agent

把上一節從 Expo quick start 複製的 prompt，貼進你的 agent，例如 Codex 或 Claude。請 agent 完成三件事：安裝 Clerk 的 Expo 套件、在 app 根層使用 Clerk 的 Provider 包住整個 app，並從環境變數讀取 publishable key。

根層的關鍵程式碼，概念上會長這樣。實際語法可能會依 SDK 版本略有差異，請讓 agent 依照最新文件處理：

// app/_layout.tsx
import { ClerkProvider } from "@clerk/clerk-expo";

export default function RootLayout() {
  return (
    <ClerkProvider publishableKey={process.env.EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY}>
      <Stack />
    </ClerkProvider>
  );
}

這段程式碼有兩個驗收重點。

  • ClerkProvider 要放在根層，包住整個 app。
  • publishableKey 要從 process.env.EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY 讀取。

Provider 可以想成登入狀態的總開關。它放在元件樹最上層，之後任何畫面都能從同一個來源取得登入狀態。如果只把 Provider 放在某個內頁，其他頁面就可能問不到 Clerk。

不好的做法：把 publishable key 直接寫死在程式碼裡，例如 publishableKey="pk_test_..."。這會讓金鑰跟著程式碼進入版控，切換環境時也必須修改程式。

正確做法：從 process.env.EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY 讀取。

第二步：讓登入按鈕啟動 Google 與 Apple 流程

Provider 接好後，接著要讓按鈕真的能發起登入。Clerk 的 Expo SDK 提供現成的 hook，可以處理社群登入流程，包括開啟授權畫面、接收回傳結果，以及更新 Provider 裡的登入狀態。

把需求交給 agent 時，先只描述這個行為：

「請在 onboarding 最後一頁加入 Continue with Google 與 Continue with Apple 兩顆按鈕。點擊後使用 Clerk 啟動對應的登入流程，登入成功後進入 app 主畫面。」

如果 agent 需要更具體的實作方式，再把 quick start 的程式片段一併附上。先讓按鈕能正確啟動登入，再處理外觀，會比較容易驗收。

若一開始就把功能、版面、陰影、logo 和動畫全部塞進同一個 prompt，agent 很可能在美化畫面時順手改動流程邏輯。比較穩定的做法是一次完成一個行為：先確認登入流程能啟動，再調整視覺呈現。

第三步：把按鈕放在 onboarding 尾端

這個 app 的 onboarding 是一道硬 gate：使用者必須完成問卷，才會進入登入。因此，登入按鈕應該放在 onboarding 的最後一頁底部，而不是直接放在 app 首頁。

整體流程會變成：

  1. 使用者先認識 app。
  2. 使用者填寫偏好。
  3. 使用者完成 onboarding。
  4. 使用者在最後一頁選擇 Google 或 Apple 登入。
  5. 登入成功後進入 app 主畫面。

這樣登入要求出現得比較自然，不會讓使用者一打開 app 就先被擋在登入頁。

第四步：再調整按鈕的視覺呈現

功能確認後，再處理登入按鈕的外觀。課程裡反覆調整過幾個細節：

  • 按鈕要有 box shadow。
  • 社交平台 logo 要清楚可見。
  • 「Continue with Apple」與「Continue with Google」的文字要夠大。
  • Google 的 icon 需要自行補上。
  • Apple 的 logo 通常由系統按鈕提供。

這些細節會直接影響使用者是否注意到登入入口。登入按鈕就像門口的招牌，功能再完整，如果字太小、logo 不清楚，使用者仍然可能找不到或不想按。

第五步：選擇自製登入畫面或 Clerk 預製 UI

接下來要做一個實際決定：登入畫面要自己刻，還是直接使用 Clerk 的預製 UI 元件？這不是固定的對錯題，而是取決於你目前的設計與開發目標。

做法優點代價適合的情況
自製原生登入畫面（課程採用的做法）與 design system 完全一致、控制權最高要自己處理 loading、錯誤、邊界狀態品牌感重、設計已有明確規範
Clerk 預製 UI 元件快、內建各種狀態與流程外觀受元件限制，客製要繞路想先求有、之後再美化

Cal AI、Codexgram 與 Dentify 三條路線都選擇自製原生畫面，因為它們在設計階段已經有明確的畫面參考。這時使用預製 UI，反而可能和既有設計互相衝突。

如果你目前只是想先確認登入流程能不能跑通，Clerk 預製 UI 會是很快的起點。可以用這個問題做決定：

我已經有一份必須長成的登入畫面設計了嗎？

  • 如果有，就自製原生登入畫面。
  • 如果沒有，就先用預製 UI 跑通流程，之後再美化。

完成後怎麼驗收

打開模擬器，走完 onboarding。最後一頁底部應該會出現兩顆按鈕：

  • Continue with Apple
  • Continue with Google

按下按鈕後，應該會開啟對應的授權流程。你可以在終端機與 Clerk 後台看到活動；至於登入是否真的成功，下一節會再透過 dashboard 的 users 清單確認。

這一節完成的結果，是 app 已經接上 Clerk、按鈕也能發起登入。下一節才會完整跑過登入流程，並處理模擬器上很常見的 Apple 登入錯誤。

小結

使用 Clerk 的 Expo quick start prompt，讓 agent 安裝套件，並在根層用 Provider 包住整個 app。這樣所有畫面才問得到登入狀態。publishable key 要從 EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY 讀取，不要寫死在程式碼裡。

登入按鈕放在 onboarding 最後一頁，使用 SDK 的 hook 發起 Google 與 Apple 登入流程。功能確認後，再調整 logo、字級與按鈕樣式。

如果手上已有明確的登入畫面設計，就自製原生登入畫面；如果只是想先驗證流程，則可以先使用 Clerk 預製 UI。

按鈕看起來能按，和登入真的成功，是兩件不同的事。下一節會把整個流程跑一遍，並說明 Apple 登入在模擬器上為什麼容易報錯，以及什麼時候不值得繼續硬修模擬器。
