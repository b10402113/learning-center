建立 Clerk application，開啟 Google 與 Apple 登入

Step 3/5 · Clerk 多供應商登入

這一步要完成什麼

這一節會把 Clerk 後台和 Expo 專案準備好。完成後，你會得到一個已建立的 Clerk application，只啟用 Google 與 Apple 登入，並把正確的 publishable key 放進專案的 .env。

動手前先準備兩樣東西：

  • 一個 Clerk 帳號。免費帳號即可，不需要綁定信用卡。
  • 一個已經能在模擬器中跑起來的 Expo 專案，也就是前面幾個節點建立的那個專案。

這些設定會直接影響下一節的串接。如果 key 放錯位置，app 會連不上 Clerk；如果沒有啟用 native applications，模擬器裡的登入可能會用很難追查的方式失敗。

第一步：建立 Clerk application

登入 Clerk 後台，建立一個新的 application。名稱可以直接使用你的專案名稱。

建立時，Clerk 會詢問你要整合的框架或平台。這裡先依照預設選項進行即可，真正重要的設定會在 application 建立完成後處理。完成後，你會進入這個 application 的管理頁面，左側可以看到 Configure 系列的選單。

Clerk 同時提供 development 與 production 兩種環境。開發階段請一律使用 development 的設定與金鑰，等到準備送審或正式上線時，再切換到 production。現在先不要使用 production，否則金鑰可能會和目前的專案環境對不上。

第二步：只啟用 Google 與 Apple

在登入方式的設定頁面，找到 SSO connections 或 User & Authentication，開啟 Google 與 Apple 兩個供應商。

依照上一節做出的決定，把 Email 登入關閉。這樣後台允許的登入方式，就會和 app 的產品規格一致。

要注意的是，在 Clerk 後台開啟供應商，只代表這個供應商「可以被呼叫」，不代表 app 一定要立刻實作它。例如你不小心開啟 Facebook，只要之後沒有把 Facebook 放進登入畫面，就不會因此多出一條實作義務。不過，實際會用到哪些供應商，最好只開哪些，後續維護會更清楚。

小提醒：在 development 環境中，Google 與 Apple 的 OAuth 憑證通常由 Clerk 代管。你不需要先到 Google Cloud Console 或 Apple Developer 後台申請憑證。等切換到 production 後，才需要自行處理憑證與 redirect URI。

第三步：選擇 Expo quick start

接著打開 Clerk 提供的串接說明，選擇 Expo（SDK）的 quick start。

這裡不要急著自己輸入一長串指令。2026 年的整合文件，主流做法是提供一段可以交給 AI agent 的設定 prompt。把這段 prompt 貼給 Codex 或 Claude，agent 就能依照你的專案結構，協助接上需要的套件、Provider 與環境變數。

因此，這一步的產出不是「已經把所有程式碼改完」，而是「取得正確的設定指示」。請確認選的是 Expo 的平台入口，並先把 quick start 提供的 prompt 複製下來。下一節才會把它實際執行到專案中。

第四步：啟用 native applications

回到同一個 application 的設定頁，找到 native applications，並確認它已經啟用。

Expo 打包出來的是原生 app，不是單純在瀏覽器執行的網頁。Clerk 必須知道這個 application 允許原生端使用，模擬器裡的登入流程才有正確的前提。

這個選項通常應該預設開啟，但不要只依賴預設值。若之後登入在模擬器裡以奇怪的方式失敗，native applications 就是值得優先檢查的設定。

第五步：把 publishable key 放進 .env

回到 application 首頁或 API keys 區域，複製 development 環境的 publishable key。接著打開專案根目錄的 .env，使用 Clerk 指定的變數名稱：

EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY=pk_test_xxxxxxxxxxxxxxxx

這一行有兩個地方不能寫錯。

  1. 變數名稱必須完全照文件使用。Expo 只會把以 EXPO_PUBLIC_ 開頭的環境變數打包到 client；如果前綴或拼字錯誤，app 就讀不到這個 key。
  2. .env 必須列在 .gitignore 中，不能提交到版本控制。現在放入的 publishable key 理論上可以公開，但同一個檔案之後可能會放入 secret key，先養成不提交 .env 的習慣最安全。
警告：不要把 sk_ 開頭的 secret key 放進 client 使用的環境變數，也不要 commit .env。secret key 可以在後端代表你的應用程式執行特權操作；一旦外流，別人就可能以你的名義管理使用者。這一節還用不到 secret key，下一個 webhook 節點才會使用，而且只能放在 server 端的環境。

第六步（建議）：安裝 Clerk AI skills

課程中還會順手安裝 Clerk 的 AI skills。你可以把 skill 想成寫給 agent 的操作手冊：它把某個服務的最新用法、慣例與常見陷阱整理成可重複使用的指示，放在 .claude/skills 或 .agents 資料夾中。

安裝後，agent 在實作 Clerk 功能時，就能參考較新的官方文件，不必只依賴過時的記憶猜測。這不是讓登入功能運作的必要條件，但會讓下一節的實作順利許多。之後串接 Trigger.dev 等服務時，也會再次用到安裝 skill 的做法。

完成檢查：你應該看到這些結果

請逐項確認：

  • Clerk 後台中的 Google 與 Apple 已啟用。
  • Email 登入已關閉。
  • native applications 已啟用。
  • 專案根目錄的 .env 中，存在 EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY。
  • .env 已被 .gitignore 排除。

完成這些檢查後，Clerk 後台和金鑰就準備好了。不過，app 此時還不知道 Clerk 的存在；Provider、登入按鈕與實際串接要留到下一節處理。

小結

建立 Clerk application 後，只啟用 Google 與 Apple，並關閉 Email。接著選擇 Expo quick start，取得一段交給 agent 的設定 prompt；再確認 native applications 已啟用。把 publishable key 以 EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY 放進 .env，並確保 .env 被 git 忽略。secret key 屬於後端，這一節用不到，也絕不能放進 client。最後，安裝 Clerk AI skills 是可選但建議的準備工作。

現在後台與金鑰都已就緒。下一步就是把 Expo quick start 的 prompt 交給 agent，將 Provider 接到根層，並在 onboarding 尾端放上登入按鈕。
