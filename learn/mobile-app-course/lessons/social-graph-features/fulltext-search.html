全文搜尋：什麼時候該用 searchIndex

Step 5/5 · 社交圖與貼文功能

學習目標

能判斷一個查詢該用一般複合索引，還是該動用全文搜尋索引；並知道把兩者用錯地方時，會各自失去什麼能力。

前言：使用者打「and」，你卻找不到 Andy

四步走完，社交圖的讀、寫、分頁都齊了。最後一個缺口出現在 explore 的搜尋框。使用者想找一個人，在框裡打了「and」，預期會看到 Andy Chen；但如果你用第一節建的 by_username 索引去查，查詢條件只能是「username 等於某個完整值」，打「and」完全對不上，因為資料庫裡存的是完整的「andychen」。

這裡的張力在於：一般的索引很擅長「精確命中」與「照順序排列」，但它不會拆字、不會模糊比對；而使用者對搜尋框的期待，恰恰是模糊的。這一節要決定的是——什麼時候該為搜尋換一套索引，什麼時候維持原本的就好。

兩個選項擺在一起比

Codexgram 的 profiles 同時掛了兩種索引，正好可以對照：

profiles: defineTable({ ..., username, name, searchText })
  .index('by_username', ['username'])                                  // 一般索引
  .searchIndex('search_profiles', { searchField: 'searchText' }),      // 全文搜尋索引
面向一般複合索引（withIndex）全文搜尋索引（withSearchIndex）
查詢方式q.eq 等值、q.gt / q.lt 範圍q.search('searchText', 文字) 分詞比對
適合什麼精確鍵、時間軸排序、關聯查詢名稱、標題、內文的模糊搜尋
排序用 order() 指定，如最新在前依文字相關度排序
你要先做什麼宣告索引的欄位順序宣告 searchIndex 與要搜尋的欄位
不支援什麼子字串、拆字、相關度精確的關聯鍵與自訂時間排序

全文搜尋索引要能運作，得先有一個「可以被搜尋的文字欄位」。profiles 的 searchText 是在建立或更新 profile 時組好的：`${username} ${name}`。也就是把使用者名稱和顯示名稱串成一段文字，讓搜尋索引去拆字。查詢時寫成：

const result = text
  ? await ctx.db.query('profiles')
      .withSearchIndex('search_profiles', q => q.search('searchText', text))
      .paginate(args.paginationOpts)
  : await ctx.db.query('profiles')
      .withIndex('by_creation_time').order('desc')
      .paginate(args.paginationOpts);

注意這裡的分流：有輸入文字才走全文搜尋索引，沒有輸入時退回一般索引拿最新的人。 因為搜尋索引是為「文字相關度」設計的，不適合當成預設清單的時間軸。

三個判別問句

面對一個新的查詢需求，先問自己這三題：

  1. 使用者是要「精確找到某一筆」，還是「打幾個字找相關的東西」？ 精確 → 一般索引；模糊找相關 → 全文搜尋。
  2. 查詢條件是某個欄位的完整值，還是它的一部分（子字串、多個關鍵字）？ 完整值 → 一般索引；只記得片段 → 全文搜尋。
  3. 結果要按什麼排序？ 按時間或自訂順序 → 一般索引的 order()；按文字相關度 → 全文搜尋。

三題都指向同一邊，答案就很清楚。如果兩邊各中一半，通常是「兩個查詢分開寫、依輸入分流」，而不是硬把一個索引當兩個用。

反例：用錯地方會怎樣

反例一：拿全文搜尋索引來排 feed。 假設你想讓 explore 的貼文按相關度排，於是把貼文也接上搜尋索引。但 feed 要的是「最新的在前」，那是 by_creation_time 的 order('desc') 擅長的事。搜尋索引按的是文字相關度，不是時間，硬用會讓時間軸失去意義。

反例二：以為全文搜尋等於 LIKE '%字%'。 搜尋索引會對文字分詞，它不保證任意子字串都能命中，而且你只能搜尋有被納入 searchText 的欄位。如果想讓人們用 bio 搜尋，就得把 bio 也組進 searchText（並重新索引），不是寫個查詢就自動生效。

反例三：以為一般索引可以「湊合」當搜尋。 有人會想用 by_username 加前綴範圍（找開頭是「and」的）來模擬。這對「從頭開始打」的情境勉強可行，但遇到「只記得名字中間幾個字」就無能為力，而且也沒有相關度排序。當需求真的是模糊搜尋時，就該老老實實建全文搜尋索引。

決策規則

把上面的判斷收斂成一張可以當場用的檢查表：

需要子字串、多關鍵字、相關度排序 → 用 withSearchIndex。
需要精確鍵、時間軸或關聯查詢 → 用 withIndex 的複合索引。
兩者都需要 → 分成兩個 query，依輸入有沒有文字來分流。
無論走哪一種，回傳前都要 publicProfile 塑形，並且要 paginate。

Codexgram 的 profiles.search 就是這條規則的具體實作：輸入 trimmed、去掉開頭的 @、截斷超長文字，有字才走 search index，沒字就走最新清單，兩條路最後都經過同樣的塑形與分頁。這也回應了前幾節的主題——不管查詢走哪條索引，都要維持一致的輸出形狀與分頁契約。

小結

一般索引擅長精確命中、範圍與時間排序；全文搜尋索引擅長分詞、模糊比對與相關度。判斷的關鍵是「使用者要精確找到，還是打幾個字找相關的」，以及「結果要按時間排，還是按相關度排」。要搜尋的文字必須先組成一個可被索引的欄位（如 searchText）。實務上兩者常常並存在同一張表，並用「有沒有輸入文字」來分流，最後都用同一套塑形與分頁收尾。

走到這裡，這個節點的五步都完成了：從 schema 的關係拆解與索引設計，到索引查詢、cursor 分頁、可重試寫入，最後是全文搜尋的取捨。你手上現在有一套能支撐社群 feed 的完整後端模式。接下來可以往即時私訊與後端測試前進，把同一套「唯一索引＋衍生欄位＋可重試寫入」的手法，搬到對話與 inbox 的 unread 判定上。
