用索引查 feed 與社交關係

Step 2/5 · 社交圖與貼文功能

學習目標

能用 withIndex 寫出 home、explore、profile 三種 feed 的查詢，以及 followers / following 清單；並說清楚像 isLiked、isFollowing 這種「因人而異」的欄位是從哪裡算出來的。

前言：同一張表，為什麼要長出三種 feed？

上一節把社交圖的資料建模好了，索引也掛上了。現在要把它變成畫面。但你很快會發現，光是「貼文列表」就有三種完全不同的意思：

  • Home feed：只顯示我追蹤的人（加上我自己）的貼文。
  • Explore：顯示所有人的最新貼文，讓我發掘新內容。
  • Profile：只顯示某一個人的貼文。

三種都是「讀 posts 表」，卻要用不同的方式篩選與排序。而每一篇貼文顯示時，又要根據「你是誰」決定愛心是不是亮著、是不是你自己的貼文。這一節要做的就是：把這些查詢通通寫成一條條走索引的路徑。

動手前先具備什麼

你需要記得兩個前提。第一，這裡的每個查詢都在 Convex 的 query 裡執行，而 query 是唯讀的，所有 DB 存取都經過 ctx.db。第二，使用者身分已經由 requireProfile(ctx) 在 server 端解析完成，回傳當下的 profile 文件；query 絕對不接受 client 傳來的「我是誰」。

核心手法：withIndex 指定查詢走哪條路

Convex 查詢的基本形狀是從一張表出發，指定一條索引，再給等值或範圍條件：

ctx.db.query('likes')
  .withIndex('by_userId_and_postId', q => q.eq('userId', me._id).eq('postId', post._id))
  .unique();

withIndex 的第一個參數是索引名稱，第二個參數裡的 q.eq 是等值條件。因為這條索引的前兩欄正好是 userId 與 postId，資料庫能直接跳到那一列，用 .unique() 取回（或回傳 null）。

這裡要刻意對比一個錯誤做法：

弱做法：ctx.db.query('likes').filter(q => q.eq(q.field('postId'), id)).collect()——這會先把資料取出來，再到記憶體裡篩選，資料一多就慢，而且吃交易資源。
強做法：ctx.db.query('likes').withIndex('by_postId', q => q.eq('postId', id)).collect()——篩選在查詢層用索引完成，只讀出需要的列。

一句話記住：能用索引回答的問題，就不要用 filter。 這也是為什麼上一節要替每個關係留兩條索引——一條對應一個查詢方向。

三種 feed 怎麼寫

posts.list 用一個 feed 參數分流，每一支都走索引：

const result = args.feed === 'profile'
  ? await ctx.db.query('posts')
      .withIndex('by_authorId', q => q.eq('authorId', args.profileId ?? me._id))
      .order('desc').paginate(args.paginationOpts)          // 某人的貼文，新的在前
  : await ctx.db.query('posts')
      .withIndex('by_creation_time')                         // 全部貼文，新的在前
      .order('desc').paginate(args.paginationOpts);

Explore 與 Profile 很直觀：前者用內建的 by_creation_time 索引拿全部貼文，後者用 by_authorId 限定作者，兩者都用 order('desc') 讓最新的排前面。分頁的細節留到下一節，這裡先看它確實有走索引。

真正的難題是 home feed。它要「我追蹤的作者的貼文」，但「我追蹤誰」在 follows 表、「貼文」在 posts 表，兩張表之間沒有單一索引可以直接串起來。Codexgram 的解法是：先掃一頁最新貼文，再逐篇用索引檢查作者是不是我追蹤的人。

const page = await Promise.all(result.page.map(async post => {
  if (args.feed === 'home' && post.authorId !== me._id) {
    const follow = await ctx.db.query('follows')
      .withIndex('by_followerId_and_followingId',
        q => q.eq('followerId', me._id).eq('followingId', post.authorId))
      .unique();
    if (!follow) return null;          // 沒有追蹤這個作者 → 這篇不進 home
  }
  return publicPost(ctx, post, me);    // 有追蹤或作者是我自己 → 塑形後回傳
}));
return { ...result, page: page.filter(p => p !== null) };

每一篇貼文的檢查，都是沿著 by_followerId_and_followingId 這條索引做一次「我 vs 作者」的 unique 查詢。這感覺像 N+1 查詢，但在 Convex 的交易式 query 裡，這些讀取都在同一個快照、本機完成，速度非常快。程式碼的註解特別提醒：即使過濾後這一頁可能只剩兩篇，也要保留原本分頁回傳的 cursor，這樣稀疏的追蹤 feed 才不會卡住。這個坑下一節會完整解釋。

追蹤清單與留言列表

人與人之間的清單用的是同一招。social.connections 依照 kind 選索引：

const result = args.kind === 'followers'
  ? await ctx.db.query('follows')
      .withIndex('by_followingId', q => q.eq('followingId', args.profileId))   // 誰追蹤我
      .order('desc').paginate(args.paginationOpts)
  : await ctx.db.query('follows')
      .withIndex('by_followerId_and_followingId', q => q.eq('followerId', args.profileId)) // 我追蹤誰
      .paginate(args.paginationOpts);

查到 follows 的列之後，還要把它轉成 profiles：followers 拿的是 row.followerId，following 拿的是 row.followingId，各自 ctx.db.get('profiles', ...)。留言列表也一樣，social.comments 用 by_postId 取某篇的所有留言，並支援 asc / desc 兩種排序。

為什麼要「塑形」：publicPost 與 publicProfile

查出來的資料不是直接丟給前端。每個結果都會經過 lib/views.ts 裡的 builder，例如 publicPost(ctx, post, me)：

export async function publicPost(ctx, post, me) {
  const author = await ctx.db.get('profiles', post.authorId);
  const like = await ctx.db.query('likes')
    .withIndex('by_userId_and_postId', q => q.eq('userId', me._id).eq('postId', post._id))
    .unique();
  return {
    _id: post._id, _creationTime: post._creationTime,
    author: await publicProfile(ctx, author, me),
    kind: post.kind, caption: post.caption,
    likesCount: post.likesCount, commentsCount: post.commentsCount,
    isLiked: !!like, isOwn: post.authorId === me._id,
  };
}

這支函式做了兩件事，都值得記下來。

第一，它把內部欄位藏起來。posts 文件裡有 storageId、uploadId，profiles 文件裡有 tokenIdentifier，這些不該出現在 API 回傳值裡。builder 只挑公開欄位，搭配 validator（例如 postView）固定形狀，前端拿到的型別就跟後端同步。

第二，它計算「因人而異」的衍生欄位。isLiked 不是存在 posts 裡的欄位，而是查「當下的 me 有沒有按過這篇」算出來的；isOwn 是比對作者是不是我；isFollowing 同理，是查 follows 得到的。同一篇貼文，對你和對我，isLiked 可能不同，所以它必須在回傳前用「你」的身分算一次，而不是存在資料列上。

這樣的分工很乾淨：資料庫存客觀事實（誰按過讚、誰追蹤誰），查詢時再依 viewer 組出主觀視角。

做完長什麼樣

完成這一節後，你會有三條真的走索引的 feed 查詢、一份雙向的追蹤清單，以及一組能依 viewer 產生 isLiked / isFollowing / isOwn 的塑形函式。驗證方式很直接：在 Convex dashboard 看這些 query 的回傳形狀是否符合 validator，並確認資料量變大時查詢仍然只讀取需要的列，而不是把整張表拉出來。

至於為什麼這裡每支列表都出現 paginate 而不是 collect，以及稀疏 home feed 為什麼要保留 cursor，原理留給下一節專門講。

小結

查詢的原則是「用索引回答，不要用 filter 掃」。三種 feed 都能走索引：explore 用 by_creation_time、profile 用 by_authorId、home 則是先掃一頁再用 follows 的複合索引逐篇檢查作者。追蹤清單靠兩條方向不同的 follows 索引。回傳前用 publicPost / publicProfile 塑形，藏住內部欄位，並依當下的 viewer 即時算出 isLiked、isFollowing、isOwn 這些衍生欄位。

下一步要處理列表躲不掉的問題：當資料有幾千筆，一次全撈會爆，於是要用 cursor 分頁。你會看到 Convex 的 paginate 回傳什麼、client 怎麼接，以及為什麼「先分頁再過濾」的 home feed 一定要保留原始 cursor。
