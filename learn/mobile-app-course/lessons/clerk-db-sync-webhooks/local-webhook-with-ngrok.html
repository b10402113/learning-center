用 ngrok 把本機 Clerk Webhook 接起來

Step 3/5 · Clerk 與資料庫同步（Webhook）

完成後，你會得到什麼？

完成這一節後，Clerk 發生使用者事件時，就能把 webhook 送到你正在本機執行的 app。你會建立一個訂閱 user 事件的 endpoint，用 ngrok 公開本機 URL，將 signing secret 放進 .env，並同時啟動 Expo、ngrok 與相關背景程序。

開始前先確認

動手前，請先確認以下條件都成立：

  • Clerk 應用程式已建立。
  • Google 或 Apple 登入能在模擬器中正常執行。
  • 專案可以正常啟動。
  • 專案根目錄有 .env，而且 .env 已加入 .gitignore。

.env 會放入 webhook 的 signing secret。它就像驗證來信真偽的印章，不能跟著程式碼一起進入公開版控。

先看整體流程

這次會把三個角色接在一起：

  1. Clerk：發生 user 事件後，向 webhook endpoint 發送 POST。
  2. ngrok：提供一個公開網址，再把請求轉送到你電腦上的 8081 port。
  3. 你的 app：在 /api/webhooks/clerk 接收事件，並用 signing secret 驗證請求。

問題在於，http://localhost:8081 只有你自己的電腦看得見。Clerk 的伺服器在網際網路上，無法直接連到這個位址。ngrok 就像替本機打開一扇臨時的對外大門，讓 Clerk 有路可以走進來。

步驟一：在本機啟動 ngrok

先開一個新的終端機視窗。第一次使用 ngrok 時，先安裝工具並設定 authtoken，接著把本機的 8081 port 公開出去：

# macOS，第一次安裝
brew install ngrok/ngrok/ngrok

# 到 ngrok 官網登入後取得 authtoken，設定一次
ngrok config add-authtoken <你的 token>

# 把本機 8081 port 公開出去
ngrok http 8081

最後一行會啟動一個持續執行的前景程序，並印出轉發位址：

Forwarding   https://a1b2-203-0-113-5.ngrok-free.app -> http://localhost:8081

這表示送到 https://a1b2-....ngrok-free.app 的請求，都會被轉送到你電腦的 8081 port。對 Clerk 來說，它是一個公開網址；對你的 app 來說，請求仍然是送進本機。

不要關掉這個終端機視窗。ngrok 程序一旦停止，隧道就會中斷，Clerk 也就無法送入 webhook。

步驟二：在 Clerk 建立 webhook endpoint

回到 Clerk 後台，依序選擇 Configure → Developers → Webhooks，再按 Add Endpoint。

你會看到 Endpoint URL 與 events 兩個必要設定。先把 ngrok 顯示的公開網址加上你的 webhook route，填入 Endpoint URL。這個課程使用的路徑是 /api/webhooks/clerk：

https://a1b2-203-0-113-5.ngrok-free.app/api/webhooks/clerk

不能只填 ngrok 的網域；少了 route 路徑，請求就不會到正確的 handler。

接著訂閱以下三個事件：

  • user.created
  • user.updated
  • user.deleted

建立 endpoint 後，Clerk 會提供一組 signing secret，通常長得像 whsec_...。下一步要把它放進專案，讓 webhook handler 能驗證事件來源。

ngrok 免費版的轉發網址每次重啟都會換一組。網址一換，Clerk 那邊的 endpoint URL 就失效，事件會送不進來。這是最常見的「昨天還能跑、今天就不動」原因——重新啟動 ngrok 後，記得回 Clerk 更新 URL。

步驟三：把 signing secret 放進 .env

複製 Clerk 提供的 signing secret，加入專案根目錄的 .env。變數名稱必須和程式讀取的名稱一致：

CLERK_WEBHOOK_SIGNING_SECRET=whsec_xxxxxxxxxxxxxxxxxxxx

接著再次確認 .env 已經寫在 .gitignore 裡。這組密鑰是驗證 webhook 真偽的唯一憑證；如果它被提交到公開 repo，其他人就可能偽造能通過驗簽的事件。

修改 .env 後，請重啟正在執行的 web server。環境變數通常會在程序啟動時載入，單純儲存檔案不會讓已經啟動的 server 自動更新。

步驟四：確認 Expo 真的提供 API route

Expo 的 API routes 需要把 app.json 的 web.output 設成 "server"。如果沒有這項設定，/api/webhooks/clerk 不會被提供，Clerk 送來的請求就會得到 404。

// app.json
"web": {
  "bundler": "metro",
  "output": "server"
}

如果你剛修改 app.json 或 .env，請先重啟 app server，再進行測試。

步驟五：分開啟動三個終端機程序

現在本機會有幾個需要持續執行的程序。建議各自使用不同的終端機視窗，這樣每個程序的 log 都容易查看：

終端機跑什麼用途
1Expo / app server提供 app 與 API routes，接收轉發進來的 webhook
2ngrok http 8081把本機 port 公開給 Clerk
3trigger.dev 的背景 worker執行同步任務（下一節才會用到）

這三個視窗可以想成三段接力：app server 負責接球，ngrok 負責把球送進來，背景 worker 則會在下一節處理後續同步工作。

步驟六：用登入流程驗證 webhook

現在做一次端到端測試：

  1. 確認 Expo、ngrok 與需要的背景程序都在執行。
  2. 在模擬器登出。
  3. 重新登入一次，觸發一則 user.created 事件。
  4. 檢查 Clerk 後台與本機終端機的紀錄。

預期會看到以下結果：

  1. Clerk 後台的 webhook delivery log：有一筆 user.created，回應碼是 200。
  2. 本機終端機的 log：看到 handler 收到事件，例如顯示已接收 user.created。

沒有成功時，照症狀排查

如果事件沒有進來，先不要同時亂改設定。依照回應症狀逐項檢查：

症狀可能原因
404路徑拼錯，或 app.json 沒設 output: "server"，或 server 沒重啟
400CLERK_WEBHOOK_SIGNING_SECRET 貼錯，或改了 .env 沒重啟
完全沒紀錄ngrok 沒在跑，或它的網址換了但 Clerk 還是舊的

如果是 Clerk 後台設定畫面卡住，可以把畫面截圖，再補上一句「我想讓這個 endpoint 收到 user.created」交給你的 AI agent。儀表板上的設定位置，通常用畫面比用文字描述更精確。

做完後，應該長什麼樣？

完成設定後，Clerk 的 webhook endpoint 應該使用「ngrok 公開網址 + /api/webhooks/clerk」；它訂閱 user.created、user.updated 與 user.deleted；signing secret 則存放在 .env，而不是程式碼或公開 repo。

當你重新登入觸發事件時，Clerk delivery log 應該回傳 200，本機終端機也應該看得到 handler 收到事件。這就代表請求已經成功穿過 ngrok，抵達你的本機 endpoint。

本機收不到 Clerk webhook，是因為 localhost 不是公開網址。解法是用 ngrok 開一條隧道，把本機 port 對外公開；在 Clerk 建立 endpoint，URL 填「ngrok 網址 + route 路徑」，訂閱三個 user 事件；把 signing secret 寫進 .env 並重啟 server；最後用 Expo、ngrok、trigger.dev 三個終端機一起跑，登入一次驗證事件有進來。ngrok 免費網址會變動，是常見的失效來源。

到這裡，你已經有一個能收到事件、也能驗證簽章的 endpoint。但「收到」不代表「處理完成」。資料庫寫入這種可能失敗的工作，應該放在哪裡執行，正是下一節要做的決定。
