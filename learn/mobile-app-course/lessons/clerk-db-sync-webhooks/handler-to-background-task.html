Webhook 收到之後：直接寫進資料庫，還是交給背景任務？

Step 4/5 · Clerk 與資料庫同步（Webhook）

學習目標

你會學會判斷：webhook 收到事件後，資料庫工作應該在 handler 裡直接完成，還是交給 trigger.dev 背景任務處理；同時也能說明 retry 語意與失敗處理的判準。

先決定工作該放在哪裡

你的 endpoint 已經能收到事件，也通過驗簽了。接下來要做的事很直白：把那位使用者寫進資料庫。

最直接的寫法，是在 handler 裡執行一次 insert 或 upsert，完成後回傳 200。多數時候，這樣確實能順利運作。

真正棘手的是剩下的那一小部分情況。資料庫可能暫時變慢，服務可能正在重啟，任務也可能第一次執行就遇到冷啟動。這時，如果寫入失敗，你得在兩個選項中做決定：

  • 回傳非 2xx，讓 webhook 投遞服務整包重送。
  • 回傳 200，把後續工作交給另一個機制處理。

第一種做法可能讓已經完成一半的副作用再次發生；第二種做法如果沒有補救機制，則可能讓使用者資料悄悄消失。

所以這一節真正要決定的，不是程式碼寫在哪一行，而是這份工作要放在哪個執行邊界：在 handler 內直接做完，還是驗簽後立刻回 200，再把工作交給背景任務？

這是可靠性的選擇，不只是程式風格的選擇。

兩個選項：速度、重試與複雜度的取捨

直接在 handler 裡處理，像是把包裹交到櫃檯後，站在現場等它完成。好處是流程短、容易理解，而且當下就知道資料庫寫入成功或失敗；但一旦失敗，你沒有一個乾淨、獨立的重試單位。

把工作交給背景任務，則像是先拿到收件證明，再由另一個工作站負責配送。webhook 可以快速回應，任務也能擁有自己的重試、退避與執行紀錄；代價是系統多了一個 worker，除錯時也要多看一個 dashboard。

trigger.dev 在這裡最重要的價值，是提供清楚的重試語意。它的設定是預設最多嘗試 3 次，間隔時間以 2 倍成長，從 1 秒開始退避，最多到 10 秒。

這些重試由任務層負責，和 webhook 的投遞完全分開。也就是說，webhook 早已回傳 200，背景任務仍然可以在自己的執行流程中安靜重試，直到成功或達到重試上限。

判別問句：用四個問題做選擇

你不需要死背哪種情境一定對應哪種做法。實際開發時，逐一問自己下面四個問題即可。

  1. 這份工作重跑一次，會不會產生副作用？ 如果不會，例如單純 upsert 一列，直接做也可以；如果會，例如重複寄信或重複扣款，就應該丟給任務，並在任務內用冪等方式處理。
  2. 這份工作夠快嗎？ 如果只是一次資料庫 round-trip，幾十毫秒內就能完成，直接做通常沒問題；如果會呼叫外部 API、執行 AI 或處理多個步驟，就交給任務，別讓 webhook 一直等。
  3. 失敗時，你想重跑什麼？ 如果你希望整個 webhook 被重新投遞，可以直接在 handler 裡處理；如果你只想重跑失敗的這一步，就交給背景任務。
  4. 是否已經有另一條路徑保證資料會存在？ 如果有，webhook 只是備援，直接做就可以；如果沒有，而 webhook 是唯一建立資料的路徑，就交給任務，讓重試有明確保障。

反例：規則會翻轉的時候

這套判斷有趣的地方在於：課程裡的兩個 app 做了相反的選擇，但兩種選擇都合理。

預約 app 的 Clerk webhook route，會在 handler 裡直接 upsert 資料庫。它之所以可以這樣做，是因為同一套後端還有一道 requireAuth() 守衛：使用者第一次呼叫 API 時，也會再 upsert 一次。

因此，webhook 在這裡是「備援」，不是唯一的關鍵路徑。即使 webhook 暫時失敗，使用者下一次發出請求時，資料仍然有機會被補上。這正好對應到第 4 個判別問句：只要存在另一條能保證資料建立的路徑，直接在 handler 裡處理就完全合理。

熱量追蹤 app 則選擇把工作丟給 trigger.dev。它把 webhook 視為唯一的自動同步路徑，不希望資料庫暫時中斷時，使用者就因此漏掉資料。

此外，重試交給任務層處理後，webhook 端可以維持又薄又快。這對應到第 3 個判別問句：它需要的是只重試失敗的那一步，而不是讓整個 webhook 再跑一遍。

兩個做法都不是「錯的」。差別在於：這個 webhook 是不是唯一會建立這筆資料的路徑，以及你希望失敗時重跑多大的範圍。

小結：一句可以直接拿來用的決策規則

問自己：「失敗時，我想重跑整個 webhook，還是只重跑這一步？」
如果想重跑整個 webhook，而且工作快速、具備冪等性，或本來就有其他保證路徑，就在 handler 內直接做。
如果只想重跑這一步，或工作較慢、容易失敗，需要獨立的重試與觀測，就丟給 trigger.dev，並在任務內使用冪等鍵加上 upsert，確保重複執行仍然安全。

決定完成後，這個課程會採用背景任務路線。下一節會把整條流程真正寫出來：驗簽後要觸發哪個任務、任務如何 upsert、刪除事件怎麼處理，以及如何確認整條鏈路確實正在執行。
