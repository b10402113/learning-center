實作同步：從 signature 到 task，再到 upsert/delete 的端到端驗證

Step 5/5 · Clerk 與資料庫同步（Webhook）

先確認目標與前置條件

這一課要把前面四步接成一條真正能執行的同步鏈路：Clerk 發生事件，送到你的 endpoint；endpoint 驗證 signature 後，觸發 Trigger.dev 背景任務；任務再依事件內容執行 upsert 或 delete。

完成後，使用者註冊時，資料庫會自動建立對應資料；使用者更新時，資料會同步；使用者刪除時，相關資料也會依 cascade 規則清理。你還能在 Trigger.dev dashboard 看到每一次任務的執行結果。

開始前，請確認以下項目都已就緒：

  • Clerk webhook endpoint 已建立，並訂閱 user.created、user.updated、user.deleted 三個事件。
  • ngrok 正在執行。
  • CLERK_WEBHOOK_SIGNING_SECRET 已放入 .env。
  • 資料庫已經有 users 表。
  • Trigger.dev 專案已建立，secret key 也已放入 .env。
  • Expo、ngrok、Trigger.dev 三個終端機都能正常開啟。

整體流程先看一遍

這次實作會依序完成五個部分：

  1. 建立 trigger.config.ts，設定任務位置、逾時與重試。
  2. 把 Expo 的輸出模式設成 server，讓 API route 真正存在。
  3. 撰寫 webhook handler，完成驗簽、建立冪等鍵並觸發任務。
  4. 撰寫同步任務，用 upsert 處理建立與更新，用 cascade delete 處理刪除。
  5. 刪除測試帳號後重新註冊，從 Clerk、資料庫與 Trigger.dev dashboard 驗證整條鏈路。

接下來照順序做。每一步都會說明「做了什麼」以及「應該看到什麼」。

步驟一：建立 trigger.config.ts

先在專案根目錄新增 Trigger.dev 設定檔。這個檔案像是任務的交通指揮中心：它告訴 Trigger.dev 要去哪裡找 task、每個 task 最多執行多久，以及失敗後要如何重試。

// trigger.config.ts
import { defineConfig } from "@trigger.dev/sdk";

export default defineConfig({
  project: "proj_xxxxxxxxxxxx",   // 從 Trigger.dev dashboard 複製
  dirs: ["./src/trigger"],        // 掃描這個資料夾裡的 task
  maxDuration: 60,                // 這些任務只有一次資料庫 round-trip，超過就是卡住
  retries: {
    enabledInDev: true,
    default: {
      maxAttempts: 3,             // 最多嘗試 3 次
      factor: 2,                  // 間隔每次乘 2
      minTimeoutInMs: 1000,       // 從 1 秒開始退避
      maxTimeoutInMs: 10000,      // 最多等 10 秒
    },
  },
});

這裡有四個設定值得確認：

  • project 是 Trigger.dev 專案識別碼，請從 dashboard 複製。
  • dirs 指向任務所在的資料夾。之後放進這個資料夾的 task，Trigger.dev 才能自動發現。
  • maxDuration 是單一任務的逾時上限。這裡設為 60 秒；同步一列資料不應該拖到這麼久，超過通常表示連線卡住。
  • retries 設定失敗後的重試規則。這裡最多嘗試三次，並使用指數退避，避免服務暫時不穩時立刻連續重打。

步驟二：把 Expo 的輸出切成 server

Expo 的 API routes 必須明確開啟 server 輸出模式。請打開 app.json，確認 web.output 設為 server：

// app.json
"web": {
  "bundler": "metro",
  "output": "server"
}

如果少了這一行，/api/webhooks/clerk 這個 route 就不會存在。Clerk 送來的 webhook 會直接收到 404。這是設定檔中很小、但很容易漏掉的一個開關。

步驟三：撰寫 webhook handler

接著建立接收事件的檔案。handler 要保持精簡，只做四件事：

  1. 驗證 Clerk webhook 的 signature。
  2. 建立冪等鍵，避免同一事件重複觸發。
  3. 依事件類型觸發對應的 Trigger.dev task。
  4. 處理完後回應 HTTP status。

請建立以下檔案：

// src/app/api/webhooks/clerk+api.ts
import type { UserJSON } from "@clerk/backend";
import { verifyWebhook } from "@clerk/backend/webhooks";
import { idempotencyKeys, tasks } from "@trigger.dev/sdk";

// 只做型別匯入：把任務實例 import 進來會讓它們被打包進 server
import type { clerkUserCreated, clerkUserDeleted, clerkUserUpdated } from "@/trigger/clerk-users";

function primaryEmail(data: UserJSON): string | null {
  const emails = data.email_addresses ?? [];
  const primary = emails.find((e) => e.id === data.primary_email_address_id);
  return primary?.email_address ?? emails[0]?.email_address ?? null;
}

export async function POST(request: Request) {
  let evt;
  try {
    // 讀 CLERK_WEBHOOK_SIGNING_SECRET；簽章錯誤或被重播都會 throw
    evt = await verifyWebhook(request);
  } catch (err) {
    console.error("Clerk webhook verification failed:", err);
    return new Response("Invalid signature", { status: 400 });
  }

  // Svix 重送時帶同一個 svix-id；global scope = 一個事件永遠只觸發一次
  const svixId = request.headers.get("svix-id");
  const idempotencyKey = svixId
    ? await idempotencyKeys.create(svixId, { scope: "global" })
    : undefined;

  switch (evt.type) {
    case "user.created": {
      await tasks.trigger<typeof clerkUserCreated>(
        "clerk-user-created",
        { clerkUserId: evt.data.id, email: primaryEmail(evt.data) },
        { idempotencyKey },
      );
      break;
    }
    case "user.updated": {
      await tasks.trigger<typeof clerkUserUpdated>(
        "clerk-user-updated",
        { clerkUserId: evt.data.id, email: primaryEmail(evt.data) },
        { idempotencyKey },
      );
      break;
    }
    case "user.deleted": {
      if (!evt.data.id) break;   // 刪除事件的 id 是選填的
      await tasks.trigger<typeof clerkUserDeleted>(
        "clerk-user-deleted",
        { clerkUserId: evt.data.id },
        { idempotencyKey },
      );
      break;
    }
  }

  // 已驗證就回 200，包含你不處理的事件——
  // 回非 2xx 會讓 Svix 對你故意忽略的事件無限重試
  return new Response("OK", { status: 200 });
}

逐段確認 handler 做了什麼

verifyWebhook 負責讀取 CLERK_WEBHOOK_SIGNING_SECRET 並驗證請求。如果 signature 不正確，或事件可能是被重播的內容，它會丟出錯誤；handler 就回傳 400，而不是讓未驗證的資料繼續往下走。

任務使用 import type 匯入。這只提供 TypeScript 型別，不會把 task 的實作打包進 webhook server。真正的任務會交給 Trigger.dev worker 執行，handler 不會在收到請求時直接操作資料庫。

primaryEmail 用來處理多個 email 的情況。陣列第一筆不一定是使用者目前的主要 email，因此程式會先找出符合 primary_email_address_id 的項目；找不到時，才退回第一筆 email。

接著從 svix-id 建立冪等鍵。Svix 重送同一個事件時會帶著相同的 svix-id，設定 scope: "global" 後，同一事件就不會重複觸發任務。

最後，依照 evt.type 觸發三種 task：

  • user.created 觸發 clerk-user-created。
  • user.updated 觸發 clerk-user-updated。
  • user.deleted 觸發 clerk-user-deleted。由於刪除事件的 id 是選填的，沒有 id 時就跳過。

要特別記住這個回應規則：驗簽成功就回 200；驗簽失敗才回 400。即使事件類型是你目前不處理的事件，也要回 200。否則 Svix 會以為你的 endpoint 失敗，持續重試那些你原本有意忽略的事件。

步驟四：撰寫同步任務

handler 只負責接收事件和觸發任務，真正碰資料庫的程式碼放在 task 檔案中。這裡會建立三個任務，分別對應建立、更新與刪除。

// src/trigger/clerk-users.ts
import { task } from "@trigger.dev/sdk";
import { eq, sql } from "drizzle-orm";

// 相對路徑，不是 "@/db"：這些任務由 Trigger.dev 打包，不是 Metro
import { db, users } from "../db";

type SyncUserPayload = { clerkUserId: string; email: string | null };

function upsertUser({ clerkUserId, email }: SyncUserPayload) {
  return db
    .insert(users)
    .values({ clerkUserId, email })
    .onConflictDoUpdate({
      target: users.clerkUserId,
      set: {
        // 不能把已知的 email 覆蓋成 null
        email: sql`coalesce(excluded.email, ${users.email})`,
        // $onUpdate 不會在 conflict-update 時觸發，要手動設
        updatedAt: new Date(),
      },
    })
    .returning({ id: users.id });
}

export const clerkUserCreated = task({
  id: "clerk-user-created",
  run: async (payload: SyncUserPayload) => {
    const [user] = await upsertUser(payload);
    return { userId: user.id };
  },
});

export const clerkUserUpdated = task({
  id: "clerk-user-updated",
  run: async (payload: SyncUserPayload) => {
    const [user] = await upsertUser(payload);
    return { userId: user.id };
  },
});

export const clerkUserDeleted = task({
  id: "clerk-user-deleted",
  run: async (payload: { clerkUserId: string }) => {
    // meals 會透過外鍵的 onDelete: "cascade" 一起被刪掉
    const deleted = await db
      .delete(users)
      .where(eq(users.clerkUserId, payload.clerkUserId))
      .returning({ id: users.id });
    return { deleted: deleted.length };
  },
});

建立與更新：共用同一個 upsert

upsertUser 使用 insert ... onConflictDoUpdate。衝突目標是 users.clerkUserId，也就是 Clerk 使用者 id。

為什麼不單純使用 insert？因為 POST /api/profile 可能比 webhook 更早抵達。兩條路徑都可能嘗試建立同一位使用者；只要都以 clerk_user_id 為唯一鍵，無論誰先到，最後都只會有一列資料，不會因競爭而產生兩筆。

這個 upsert 只更新 email 與 updatedAt。身高、目標和 onboarding 答案屬於 /api/profile 管理，不應該由 Clerk 同步任務整列覆蓋。否則使用者剛填完 onboarding，下一個 webhook 就可能把答案清掉。

coalesce(excluded.email, users.email) 則避免新事件的 email 是 null 時，把資料庫裡原本已知的 email 覆蓋掉。updatedAt 也要手動設定，因為 ORM 的自動更新機制不會在 conflict-update 這條路徑上自動觸發。

刪除：讓資料庫執行 cascade

刪除任務只要依 clerk_user_id 刪除 users 中的那一列。相關的 meals 資料會透過外鍵的 onDelete: "cascade" 一起刪除，不需要在 task 裡逐筆清理。

如果任務回傳 { deleted: 0 }，也不代表失敗。使用者可能從未完成 onboarding，因此資料庫原本就沒有對應的列。

步驟五：啟動 worker 並做端到端驗證

程式寫完後，先啟動 Trigger.dev worker。請在第三個終端機執行：

# 終端機 3：啟動 Trigger.dev worker
npx trigger.dev@latest dev

接著做一次完整測試：

  1. 確認 Expo、ngrok 與 Trigger.dev worker 都正在執行。
  2. 到 Clerk 後台刪除測試使用者。
  3. 在模擬器重新註冊。
  4. 到 Clerk 後台確認有新的使用者。
  5. 檢查資料庫的 users 表，確認多出一列相同的 clerk_user_id。
  6. 打開 Trigger.dev dashboard，確認出現對應的 task run。

正常情況下，Clerk 會先產生事件，webhook handler 驗證後觸發 clerk-user-created，worker 再執行 upsert。這時你應該能在 dashboard 看到任務 id、每次嘗試、執行時間與錯誤資訊。

症狀先檢查什麼
資料庫沒有新的一列Trigger.dev worker 有沒有在跑？TRIGGER_SECRET_KEY 有沒有設進 .env？
Trigger.dev dashboard 沒看到 runhandler 有沒有真的觸發任務？Clerk 的 delivery log 回應碼是多少？
同一使用者出現兩列upsert 的衝突目標是否設在 clerk_user_id；冪等鍵有沒有帶上
Clerk 一直重送同一個事件handler 是不是回了非 2xx，或回應逾時

排查時，可以把 Trigger.dev dashboard 和 Clerk 的 webhook delivery log 並排查看。前者告訴你任務有沒有被觸發、執行了幾次；後者則能確認 Clerk 送出事件後，endpoint 回了什麼。兩邊對起來，整條鏈路就不再像黑盒子。

完成後，你應該看到什麼

完成這次測試後，應該會得到以下結果：

  • Clerk 後台有重新註冊的測試使用者。
  • 資料庫的 users 表有一列相同 clerk_user_id 的資料。
  • Trigger.dev dashboard 有對應的 clerk-user-created run。
  • 重新送出相同事件時，冪等鍵能避免同一事件重複觸發。
  • 更新事件只會同步 email，不會覆蓋 profile 或 onboarding 欄位。
  • 刪除使用者時，相關 meals 資料會由資料庫外鍵的 cascade 一起清除。
整條同步鏈路由五個零件組成：trigger.config.ts 負責任務掃描、逾時與重試；app.json 的 output: "server" 讓 API route 存在；webhook handler 負責驗簽、建立冪等鍵、依事件觸發任務並回應 200；任務檔用 upsertUser 以 clerk_user_id 為衝突目標，只更新 email，刪除時則交給 cascade 清理關聯資料；最後用刪除帳號再註冊的方式，同時檢查 Clerk 與資料庫。核心順序就是：事件進來 → 驗簽 → 觸發 → 冪等寫入。

這樣一來，「登入」和「資料」之間原本的斷點就接起來了。之後資料庫即使增加更多表、外鍵、migration 與 seed 資料，新使用者仍會從這條同步鏈路進入系統；其他關聯到使用者的表，也能沿著 clerk_user_id 繼續建立。
