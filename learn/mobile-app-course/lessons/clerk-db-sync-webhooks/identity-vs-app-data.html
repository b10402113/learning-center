身分歸 Clerk，資料歸你：為什麼登入成功後 DB 還是空的？

Step 1/5 · Clerk 與資料庫同步（Webhook）

學習目標

學完這一節，你應該能說明 Clerk 和 app 資料庫為什麼是兩個獨立的身分與資料來源，也能解釋為什麼使用者明明登入成功，DB 卻仍然沒有資料。

前言：登入成功，資料庫卻一列都沒有

你在模擬器按下「Continue with Google」，登入流程順順完成，畫面也進到首頁。你打開 Clerk 後台，新使用者的頭像和 email 都在，看起來一切正常。

接著你切到 Neon 的資料庫儀表板，打開 users 表，卻發現裡面空空如也，一列資料都沒有。

第一個反應通常是：「是不是哪裡壞掉了？」但這其實不一定是 bug，而是兩個系統正照著各自的設計運作。Clerk 本來就沒有要替你寫入應用程式資料庫；你的資料庫也不會自動知道有人剛剛登入。

這一節要先釐清一個後面每一節都會用到的觀念：身分（identity）和應用資料（application data）是兩座獨立的倉庫，中間那條連線需要由你自己建立。

先看懂問題的本質，後面才會知道 webhook 到底是在補哪個洞。

兩座倉庫：一個管你是誰，一個管你有什麼

整條登入流程背後，其實有兩個不同的儲存來源。

第一個是 Clerk，也就是身分來源（identity provider）。它負責保管「你是誰」：帳號本身、email、你選擇 Google 還是 Apple 登入、目前有效的 session token、登入裝置，以及多因子驗證設定。

這些資料屬於「驗證」範圍，也是安全敏感的領域。把它交給專門處理身分驗證的服務，通常比自己從頭打造一套登入系統可靠。

第二個是你自己的 Postgres，本課程使用的是 Neon。它是應用資料來源（application data store），負責保管「你在這個 app 裡有什麼」：使用者填寫的身高、體重與減重目標，拍下的餐點照片與熱量分析，之後的預約紀錄、角色權限設定，以及所有需要查詢、關聯或製作報表的資料。

可以把它想成大樓門禁和你家的關係。Clerk 像大廳櫃檯，負責確認你的身分並發給你門禁卡；你的資料庫則像家裡的房間，裡面放著你的家具。櫃檯登記了「你是誰」，但不會自動把家具搬進你家。這是兩件不同的事。

你可能會問：「那為什麼不乾脆全部放在 Clerk？」原因是 Clerk 不是你的 app 資料庫。你需要用外鍵把「使用者」和「他的餐點」關聯起來，也需要對自己的資料進行查詢、建立索引和製作報表；這些事情都超出驗證服務原本的範圍。

如果把所有應用資料都塞進 auth 供應商，就像把整間店的商業邏輯鎖在一個不能輕易搬家的櫃子裡。未來想更換服務時，遷移成本會很高。

反過來也一樣。不要只為了省事，就自己刻一套登入系統。OAuth 流程、token 輪替和 Apple 的審核規則，每一項都比表面上更容易出錯。

橋樑是 clerk_user_id，不是 id

既然兩座倉庫要互相對應，就需要一個共同的識別碼。你的 users 表通常會長這樣：

users
  id             ← 你資料庫自己的主鍵
  clerk_user_id  ← Clerk 的使用者 id，唯一值
  email
  role
  created_at
  updated_at

關鍵就在 clerk_user_id。Clerk 發出事件時，帶的是它自己的使用者 id；你的資料表則把這個 id 存成外部識別碼。如此一來，你就能回答：「這個 Clerk 帳號，對應到我資料庫裡的哪一列？」

之後不論是同步使用者、刪除資料，還是查詢 profile，都會靠這個欄位把兩邊串起來。

不過，id 和 clerk_user_id 的工作不一樣。id 是你資料庫自己的主鍵；clerk_user_id 則是身分來源的識別碼。兩個欄位都可以存在，而且各自負責不同的事情。

如果你只存 Clerk 的 id，就等於把資料庫的識別責任也交給外部服務。這也是為什麼後面設計同步時，upsert 的衝突目標會放在 clerk_user_id。

為什麼「DB 是空的」其實是預設狀態

回到一開始的畫面。使用者登入成功時，發生的事情主要都在 Clerk 那一側：Clerk 驗證 Google 的憑證、建立自己的使用者記錄，並把 session token 發給手機。

在這個過程中，你的伺服器可能完全沒有參與，更不用說你的資料庫了。

所以「Clerk 有人、DB 沒人」不代表一定有設定錯誤。真正的原因是：目前沒有任何東西負責把 A 倉庫的資料複製到 B 倉庫。要讓資料庫多出一列，總得有某個程式明確執行寫入。

當然，你可以自己做這件事：在 Clerk 後台看到新使用者後，手動到資料庫 insert 一列。只有一個人時還能接受，十個人就開始勉強；等到一萬個人，這種做法一定會崩潰。

而且使用者修改 email 時，你還要再手動更新一次；使用者刪除帳號時，也要記得刪掉資料庫中的對應資料。手動同步最大的問題，不只是麻煩，而是規模一大就很難維持一致。

比較可靠的做法，是讓這件事自動發生：Clerk 在事件發生時主動通知你的 app，你的 app 收到通知後，再把資料寫入資料庫。

這種「事情發生時主動送出的訊息」就是 webhook。下一節會把它拆開來看。

一個現實的補充：同步不是瞬間完成的

即使你已經接好 webhook，事件送達仍然屬於「最終一致」（eventually consistent）。它通常很快，但網路或佇列都可能造成延遲。

因此，如果新使用者登入後立刻呼叫 API 取得資料，而 webhook 還沒有送到，資料庫可能仍然沒有他的那一列。

成熟一點的做法，是在真正需要資料的請求路徑上再做一次 upsert。如此一來，webhook 的角色是「補上同步」，而不是唯一的資料建立路徑。

課程裡的預約 app 就採用這個模式：webhook 是備援，而真正保證資料存在的，是使用者第一次發出請求時執行的 upsert。這個模式之後還會再遇到，現在先記住一件事：webhook 不代表即時保證。

小結：把兩個觀念接在一起

Clerk 是身分來源，管「你是誰」；你的 Postgres 是應用資料來源，管「你在 app 裡有什麼」。兩者預設互不干涉，所以登入成功後 DB 仍是空的。把兩邊接起來的鑰匙是 clerk_user_id，而自動同步的工具是 webhook。手動複製在小規模可行，在真實產品規模會崩。

現在你已經知道問題缺在哪裡：缺的不是資料庫，也不是登入功能，而是「有人通知你的 app，把資料寫入資料庫」這條連線。
