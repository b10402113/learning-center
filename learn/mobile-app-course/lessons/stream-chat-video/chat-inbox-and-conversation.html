訊息畫面：patient 的單一對話與 staff 的收件匣

Step 4/5 · Stream 即時聊天與視訊

學習目標

做完這一節，你會有一個同時服務兩種角色的 Messages 分頁：病人一打開就進入他和診所唯一的那個對話，員工則看到所有病人對話組成的收件匣，點進去開啟個別對話。你也會知道 typing、已讀、圖片與相機附件這些體驗，是 SDK 直接內建、不需要自己實作的。

前言：同一支程式，兩種完全不同的使用場景

病人打開 Messages 分頁時，心裡想的是「跟診所講話」。他跟診所只有一條對話，所以最合理的設計就是直接把他丟進那個對話，不用先看到一個只有一列的清單。但同一支 app 給診所員工使用時，情境完全相反：員工要面對的是幾十位病人，需要的是一份能依最新訊息排序的收件匣，點進某一列才看到那個病人的對話。

這兩個場景如果硬要共用同一個畫面，會變得很彆扭。Dentify 的做法是讓同一個分頁依角色分岔，但底層的對話元件共用。這樣改一行 header、加一顆通話按鈕，兩邊會同時生效，不會各自漂移。

第一步：一個分頁，三種結果

Messages 分頁的判斷其實就是三個分支：Stream 沒開起來、員工、病人。先把「不能用」的情況處理掉，畫面才不會因為缺少 Chat context 而崩潰：

const { ready, channelId } = useClinic();
const isStaff = me?.role === 'staff' || me?.role === 'dentist';

if (!ready) {
  return <ChatUnavailable message="Messaging is offline right now. Everything else still works." />;
}
if (isStaff) return <StaffInbox />;
if (!channelId) {
  return <ChatUnavailable message="Finish setting up your profile and the clinic will be able to message you." />;
}

ready 來自上一節的 StreamProvider：連不上 Stream 時它會是 false，這裡就顯示一段說明文字，而不是讓畫面爛掉。病人沒有 channelId 的情況，通常代表還沒完成 onboarding，所以先請他完成個人資料。

第二步：病人的畫面就是那個唯一對話

病人分支最後直接渲染共用元件，並帶入對話 id 與顯示用的標題副標：

<Conversation
  channelId={channelId}
  title="Clinic Team"
  subtitle="DentaCare · usually replies same day"
/>

這個 channelId 是上一節由 clinicChannelId(patientId) 推導來的，所以病人永遠只會進到自己的對話。

第三步：員工的收件匣——ChannelList

員工分支渲染一份清單，資料由 SDK 依成員身分查詢：

const filters = useMemo(
  () => ({ type: 'messaging', members: { $in: [userId!] } }),
  [userId]
);
const sort = useMemo(() => [{ last_message_at: -1 as const }], []);
const options = useMemo(() => ({ limit: 20, messages_limit: 30 }), []);

這裡的 useMemo 不是化妝，而是必要的。如果每次 render 都產生一個新的 filters 物件，SDK 會以為查詢條件變了，於是每一次 render 都重新查一次。filters 只依賴 userId，所以把它記住就能讓查詢穩定下來。

點選清單某一列時，傳進路由的是對話的 id，不是對話實例：

onSelect={(channel) => router.push(`/channel/${channel.id}`)}

理由跟後面其他地方一樣：路由參數必須是可序列化的，把一個帶方法的 SDK 物件塞進導覽狀態會出問題。

第四步：開啟個別對話

員工從收件匣點進來後，畫面用 id 重新取得對話，標題則從 client 的快取拿病人名字：

const name = client.activeChannels[`messaging:${id}`]?.data?.name;

return (
  <Conversation
    channelId={id}
    title={name ?? 'Patient'}
    subtitle="Patient conversation"
    onBack={goBackToInbox}
  />
);

為什麼不直接把對話物件傳過來？因為導覽參數必須能被序列化，對話實例不行。反正這個對話剛剛才在收件匣查詢裡出現過，client 的快取裡就有它的名字，重新用 id 取得一次不需要再多打一趟 API。

第五步：共用對話元件

兩種角色最後都收斂到同一個 Conversation。它由對話 id 重建 channel，再用 SDK 的 Channel 包住訊息列表與輸入框：

const channel = useMemo(() => client.channel('messaging', channelId), [channelId, client]);

return (
  <Channel channel={channel} keyboardVerticalOffset={0} topInset={0}>
    <View style={{ flex: 1, backgroundColor: PAGE.bg }}>
      <Header title={title} subtitle={subtitle} onBack={onBack} />
      <MessageList />
      <MessageComposer />
    </View>
  </Channel>
);

keyboardVerticalOffset={0} 與 topInset={0} 這兩個 0 是刻意的。SDK 會用這兩個值調整鍵盤與頂部的留白，但 Dentify 的 header 是畫在 Channel 裡面，上面已經沒有別的東西，所以一定要明確傳 0；如果省略，SDK 會拿到 undefined，版面就會偏移。

第六步：通話按鈕住在 header 裡

共用 header 的右側有一顆通話按鈕，它必須在 Channel 內部才能讀到這個對話的成員名單：

function CallButton() {
  const { channel } = useChannelContext();
  const ring = useRingCall();
  ...
  const memberIds = Object.keys(channel?.state.members ?? {});
  const started = await ring(memberIds);
  if (!started) Alert.alert('Nobody to call', 'There is no one else in this conversation yet.');
}

成員名單直接從 SDK 已經載入的狀態拿，不必額外查一次 API。這顆按鈕就是下一節要講的「即時 ring」入口。

第七步：這些體驗 SDK 已經內建，你只要學會用

課程 demo 裡展示了打字指示、已讀狀態、圖片與相機附件、訊息 threads、表情回應、編輯、置頂與刪除。這些不是 Dentify 自己寫的，而是 Stream Chat SDK 預設就有的功能。真正要做的是把它們接進畫面，而不是重新發明：

體驗來源
打字指示、已讀狀態SDK 內建，隨訊息事件更新
圖片與相機附件SDK 的 composer 提供
threads、表情回應SDK 內建訊息操作
編輯、置頂、刪除SDK 內建訊息操作
依最新訊息排序的收件匣SDK 的 ChannelList 查詢

用託管服務最大的價值就在這裡：這些 UX 是別人已經打磨過、能上線的預設行為，你要付的成本主要是「學會怎麼用」，而不是「從零做一套」。

小結

Messages 分頁依角色分岔：病人直接進入唯一對話，員工看到共享收件匣再點進個別對話。兩個角色最後共用同一個 Conversation 元件，由對話 id 重建 channel，再包上 Channel、MessageList 與 MessageComposer。清單的 filters 要 memoize，路由只傳可序列化的對話 id。打字、已讀、附件、threads、回應、編輯等常見聊天體驗，全部由 Stream SDK 內建提供。

訊息功能完成了。但共用 header 裡那顆通話按鈕還只是一個入口，按下去之後會發生什麼還沒交代。下一步要處理兩條完全不同的通話路徑：排程好的視訊看診，以及想到就打的即時鈴聲。
