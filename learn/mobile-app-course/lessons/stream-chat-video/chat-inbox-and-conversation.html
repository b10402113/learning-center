訊息畫面：patient 的單一對話與 staff 的收件匣

Step 4/5 · Stream 即時聊天與視訊

學習目標

能做出 patient 單一對話與 staff 收件匣兩種角色的訊息畫面，並解釋為什麼要傳 channel id 而不是 Channel instance。

前言：同一個頁面，兩種完全不同的體驗

client 接好了，資料也通了，但使用者到目前為止什麼都還看不到。這一節要把資料變成畫面。訊息這個功能在病人和員工眼中是兩個不同的東西：病人只有唯一一個跟診所的對話，打開就應該直接看到他跟診所的訊息；員工則同時跟很多病人對話，需要先看到一份清單，再點進某一筆。

動手的起點是上一節的成果：app root 已經把 ready、channelId、memberIds 放在 ClinicContext 裡，任何畫面都能用 useClinic() 拿出來。這一節要做的是建立兩個角色共用的畫面，讓同一個對話元件同時服務兩邊。做完之後，病人和員工打開 Messages 會看到截然不同的東西，但背後是同一個對話元件在運作。

第一步：用一個畫面分岔兩種角色

先看入口畫面 app/(tabs)/messages.tsx。它只做一件事：判斷現在是誰，然後決定要顯示什麼。

export default function Messages() {
  const { me } = useMe();
  const { ready, channelId } = useClinic();
  const isStaff = me?.role === 'staff' || me?.role === 'dentist';

  if (!ready) {
    return <ChatUnavailable message="Messaging is offline right now. Everything else still works." />;
  }
  if (isStaff) return <StaffInbox />;
  if (!channelId) {
    return <ChatUnavailable message="Finish setting up your profile and the clinic will be able to message you." />;
  }

  return (
    <>
      <StatusBar style="dark" />
      <Conversation
        channelId={channelId}
        title="Clinic Team"
        subtitle="DentaCare · usually replies same day"
      />
    </>
  );
}

這裡有四個分支，順序有意義。第一，如果 ready 是 false，代表 Stream 這一輪沒連上（還記得上一節的逾時降級嗎），顯示 ChatUnavailable 告訴使用者「聊天暫時離線，其他功能仍可用」。第二，員工走 StaffInbox。第三，病人如果還沒有 channelId，表示他還沒完成 onboarding、還沒有病人檔案，提示他去完成。最後才是病人的唯一對話。

注意 isStaff 的判斷同時接受 'staff' 和 'dentist'，這跟上一節 server 端的 isStaff 是同一個定義。前後端用同一套角色分類，才不會出現「server 當你是員工、畫面當你是病人」這種不一致。

第二步：共用同一個對話元件

病人的畫面與員工點進單筆對話後看到的，其實是同一個 Conversation 元件，定義在 components/chat.tsx：

export function Conversation({
  channelId,
  title,
  subtitle,
  onBack,
}: {
  channelId: string;
  title: string;
  subtitle: string;
  onBack?: () => void;
}) {
  const { client } = useChatContext();

  // Rebuilt from the id rather than passed through navigation — a Channel
  // instance must not ride in route params. Every conversation in this app is
  // `messaging`, so the type never needs to travel either.
  const channel = useMemo(() => client.channel('messaging', channelId), [channelId, client]);

  return (
    // The header is rendered inside Channel, so nothing sits above it to offset
    // against. Both props must be an explicit 0: Channel destructures
    // keyboardVerticalOffset with no default, so omitting it passes undefined.
    <Channel channel={channel} keyboardVerticalOffset={0} topInset={0}>
      <View style={{ flex: 1, backgroundColor: PAGE.bg }}>
        <Header title={title} subtitle={subtitle} onBack={onBack} />
        <MessageList />
        <MessageComposer />
      </View>
    </Channel>
  );
}

元件接收的是 channelId 這個字串，而不是一個已經建好的 Channel 物件。它用 client.channel('messaging', channelId) 現場重建出 channel 實例。這件事看起來只是瑣碎實作，其實是一個重要的紀律：Channel instance 不能放進導覽參數裡。導覽參數需要是可序列化的，而 channel 實例帶著連線狀態、事件監聽，塞進去只會出問題。所以跨畫面傳的永遠是 id，到了目的地再用 id 把實例重建出來。

裡面的三塊 Header、MessageList、MessageComposer 都是 Stream SDK 現成的元件。也就是說，訊息的捲動、輸入、送出，你幾乎不用自己寫；你要做的是把它們擺進自己的版型裡。那個 keyboardVerticalOffset={0} topInset={0} 是配合這個 app 的版面調整，讓鍵盤與安全區域的內距不會被重複計算。

第三步：員工的收件匣

員工端沒有單一對話，所以走另一條路：用 SDK 的 ChannelList 查出一份對話清單。關鍵是查詢條件必須穩定，否則每次重繪都會重新查一次：

function StaffInbox() {
  const { client } = useChatContext();
  const { top } = useSafeAreaInsets();
  const userId = client.userID;

  // Memoized: an unstable filter object makes ChannelList requery every render.
  const filters = useMemo(
    () => ({ type: 'messaging', members: { $in: [userId!] } }),
    [userId]
  );
  const sort = useMemo(() => [{ last_message_at: -1 as const }], []);
  const options = useMemo(() => ({ limit: 20, messages_limit: 30 }), []);

filters 的意思是「所有 messaging 類型、而且成員包含我的對話」。這正好對應到上一節 server 端做的事：每個病人的對話都把病人和全體員工放進成員名單，所以員工只要查「我在裡面的對話」，就會看到他負責的所有病人。sort 用最後訊息時間倒序，最新的排最上面；options 限制一次抓 20 個對話、每個對話帶 30 則訊息。

三個 useMemo 的依賴陣列幾乎都是空的或只有 userId，原因是註解那句：如果每次 render 都產生一個新的 filter 物件，ChannelList 會以為條件變了而重新查詢，效能會很糟。點選某一筆時，傳的是 channel 的 id：

<ChannelList
  filters={filters}
  sort={sort}
  options={options}
  // The id, never the Channel instance — route params must stay serializable.
  onSelect={(channel) => router.push(`/channel/${channel.id}`)}
/>

員工點進去的 /channel/[id] 畫面會從網址拿到這個 id，再交給剛剛那個共用的 Conversation 元件，附上返回按鈕。所以病人和員工其實共用同一個對話畫面，差別只在病人不需要返回、標題寫「Clinic Team」，員工需要返回、標題寫病人的名字。

第四步：補上型別，讓自訂欄位有名字

還記得第一節提到的 staff 和 name 這兩個自訂欄位嗎？它們是我們自己加到 Stream 資料上的，TypeScript 預設不認得。所以在 types/stream.d.ts 做模組擴充，把它們補進型別：

declare module 'stream-chat' {
  interface CustomChannelData {
    /** The patient's name — what staff see in the shared inbox. */
    name?: string;
  }
  interface CustomUserData {
    /** Lets either app label a participant as clinic-side without a lookup. */
    staff?: boolean;
  }
}

型別擴充本身不會改變執行時的行為，但它讓程式碼在讀取 channel.data.name 或 user.staff 時有型別可循，也讓前後端對「有哪些自訂欄位」有共同的認知。web 端有一份對應的宣告，兩邊必須一致，欄位才不會對不上。

第五步：你其實不用自己做這些功能

到這裡畫面只寫了幾個元件，但實際跑起來會發現聊天該有的功能都在了。把兩個 client 用真實裝置對開，你會看到打字狀態即時出現又消失、訊息已讀／未讀、對方離開的提示、送圖片、開相機拍照傳送。長按訊息還能回覆成討論串、加表情、編輯、釘選、刪除。

這些全都是 Stream 內建的，你只需要學會怎麼把它接起來，而不是自己刻一套。各項功能的分工是這樣：

功能來自哪裡你要做什麼
即時收發、打字、已讀Stream SDK 內建接上 client 與 Channel
附件、相機、影片Stream SDK 內建確認裝置權限
討論串、表情、編輯、釘選Stream SDK 內建長按訊息即可
收件匣清單Stream 的 ChannelList給穩定的 filters 與 sort

換句話說，你的工作從「實作聊天功能」變成「設計使用體驗與權限」。真正需要自己想清楚的，是病人只該有一個對話、員工該看到哪些對話、聊天離線時畫面要怎麼說，而這些正是前面幾步在處理的事。

小結

訊息畫面用同一個入口同時服務兩種角色：病人因為只有一個對話，直接進入 Conversation；員工走 StaffInbox，用 ChannelList 依「成員包含我」查出所有病人對話。Conversation 接收的是 channelId 字串而不是 Channel 實例，因為實例不能放進需要序列化的導覽參數，到了畫面再用 id 重建。ChannelList 的 filters、sort、options 都用 useMemo 固定住，避免每次重繪都重新查詢；最後用 stream.d.ts 補上自訂欄位的型別，並善用 Stream 內建的打字、已讀、附件、討論串等功能。

文字對話完成後，還有另一半的即時功能：視訊。下一節要處理兩種截然不同的通話入口：一種是根據預約、固定房間的排程看診，另一種是隨時可能響起的即時來電，而它們對「通話 id」的用法剛好相反。
