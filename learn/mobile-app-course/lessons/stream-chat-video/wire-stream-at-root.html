在 app root 接上兩個 client：一個 token、Chat 與 Video

Step 3/5 · Stream 即時聊天與視訊

學習目標

做完這一節，你的 Expo app 最上層會多一層 StreamProvider：它用 POST /api/stream/token 拿到的那張 token，同時建立 Stream Chat 與 Stream Video 兩個 client，並且在 12 秒內連不上時自動放棄，讓預約與 AI 助理等其他功能照常運作。

前言：token 有了，但要種在哪裡？

上一節的後端已經能發 token，也能指出病人該進哪個對話。但這個 token 要在 app 的哪一層被使用，是一個會影響全app的決定。如果每個畫面各自去打端點、各自建 client，你會很快遇到兩個問題：同一個使用者可能同時存在好幾條 Stream 連線，而登出時有些 client 沒被斷開，下一個使用者就沿用了上一個人的身分。

解法是把兩個 client 接到整個應用的最上層，只建立一次，登出時一起拆掉。這一節就是那個最上層的 StreamProvider。它除了接線，還處理一件很容易被忽略的事：當 Stream 掛掉時，app 要怎麼活下來。

為什麼兩個 client 都放在 root

聊天與視訊的狀態要在整個 app 都拿得到。病人在 home 畫面按「Video Consult」要能撥號、在 messages 分頁要能收訊息、在 booking 流程中還可能被來電打斷。這些畫面彼此不相關，唯一共同的地方就是它們都在 root 底下。

把兩個 client 放在 root 還有一個更實際的理由：登出。Chat 與 Video client 都綁著「目前登入的人是誰」，只要把它們的生命週期綁在一個會在登出時被卸載的元件上，斷線就會自動發生，不必手動記得去斷。

第一步：拿到 token 並存成 session

Provider 先向自己的 token 端點要身分，把回應存成 state：

type StreamSession = {
  apiKey: string;
  userId: string;
  name: string;
  role: 'patient' | 'staff' | 'dentist';
  token: string;
};

useEffect(() => {
  if (!isLoaded || !isSignedIn) return;
  let cancelled = false;
  call<StreamSession>('/api/stream/token', { method: 'POST' }).then(
    (next) => !cancelled && setSession(next),
    () => !cancelled && giveUpAt('token', 'error')
  );
  return () => { cancelled = true; };
}, [call, isLoaded, isSignedIn, giveUpAt]);

只有登入後才會打這支端點。拿到的 session 裡同時有 apiKey 與 token，接下來的兩個 client 都會用到它。

第二步：建立 Chat client

Chat 用 SDK 提供的 hook 建立，只需要 api key、一個會回傳 token 的函式，以及使用者資料：

const userData = useMemo(
  () => ({ id: session.userId, name: session.name }),
  [session.userId, session.name]
);

const chatClient = useCreateChatClient({
  apiKey: session.apiKey,
  tokenOrProvider: tokenProvider,
  userData,
});

注意 tokenOrProvider 傳的不是 token 本身，而是一個 tokenProvider 函式。這是為了讓 SDK 在 token 快過期時自己去更新，而更新的方式就是再打一次同一個端點：

const tokenProvider = useCallback(
  () => call<StreamSession>('/api/stream/token', { method: 'POST' }).then((s) => s.token),
  [call]
);

這個函式是穩定的，因為 useApiClient 把 Clerk 的 getToken 放在 ref 裡，所以它的依賴不會每次 render 都變，也就不會讓 Chat client 反覆重建。

第三步：建立 Video client，而且只建立一次

Video client 不能用 new，要用 getOrCreateInstance：

const videoClient = useMemo(
  () =>
    StreamVideoClient.getOrCreateInstance({
      apiKey: session.apiKey,
      user: userData,
      token: session.token,
      tokenProvider,
      options: { rejectCallWhenBusy: true },
    }),
  [session.apiKey, session.token, userData, tokenProvider]
);

差別在哪裡？第二個 client 實例會破壞來電鈴聲的狀態，也會讓推播喚醒對不上正確的連線。同一個使用者呼叫 getOrCreateInstance 是冪等的，所以放在 useMemo 裡重算也安全。options.rejectCallWhenBusy 則表示這個人正在講電話時，新來電會被自動拒絕，而不是兩個通話互搶。

最後，在元件卸載時把 video client 斷開，這就是登出時的自動清理：

useEffect(
  () => () => {
    videoClient.disconnectUser().catch(() => {});
  },
  [videoClient]
);

第四步：12 秒的耐心——連不上就讓 app 先活著

Stream 是一個外部服務，它有可能連不上。如果 app 傻傻地等它，整個介面會卡在轉圈圈，連跟聊天無關的預約功能都一起停擺。Dentify 的處理方式是設一個 12 秒的上限：

const CONNECT_TIMEOUT_MS = 12_000;

const giveUpAt = useCallback((stage: 'token' | 'socket', reason: 'error' | 'timeout') => {
  Sentry.logger.warn('stream unavailable, app running without messaging', {
    stage,
    reason,
    timeout_ms: CONNECT_TIMEOUT_MS,
  });
  setFailed(true);
}, []);

這裡的 stage 區分了兩種失敗：token 代表連後端拿 token 就失敗，socket 代表 token 拿到了、但聊天連線沒開起來。分開記錄是為了在監控上能分辨是後端問題還是 Stream 問題。reason 則區分是直接錯誤還是等超過時間。

當失敗發生時，Provider 不再包住 Chat 與 Video，直接把子元件原樣渲染：

if (!isLoaded) return <Connecting />;
if (!isSignedIn || failed) return <>{children}</>;
if (!session) return <Connecting />;

結果就是：聊天與視訊消失，但預約、AI 助理、個人資料全部照常。Messaging 是一個功能，不是整個 app 的地基。

第五步：登出時不留下上一個人的 token

還有一個容易漏掉的情境：使用者切換帳號。如果舊的 session state 還留著，而新的 token 還在路上，app 可能短暫用上一個人的身分連上 Stream。Dentify 在 render 期間比對登入狀態，一發現變化就清掉 session：

if (wasSignedIn !== isSignedIn) {
  setWasSignedIn(isSignedIn);
  setSession(null);
  setFailed(false);
}

把 session 清掉之後，ConnectedStream 會被卸載，兩個 client 也一起斷開。等新身分登入，一切從乾淨的狀態重建。

第六步：把主題接上，避免看起來像外掛的 SDK

最後一步是外觀。Stream 的預設主題是通用的，如果直接沿用，聊天畫面會和 app 的其他部分明顯不同。Dentify 把 Stream 的主題色改成自己的水藍與深藍，並把安全區域的 insets 接進 video 主題，讓通話畫面自己處理留白：

const videoTheme = { variants: { insets: { top, right, bottom, left } } };

原則是：聊天與通話要讀起來像同一個產品，而不是兩個硬塞進來的功能。這也是為什麼通話畫面不再自己包 SafeAreaView，否則會多留一次空白。

小結

StreamProvider 在 app root 只做一次接線：用 server 發的 token 建立 Chat 與 Video 兩個 client，Video 用 getOrCreateInstance 確保只有一個實例。連線設 12 秒上限，失敗時把畫面交還給 app，讓聊天以外的功能照常運作。登出或切換帳號時清掉 session，兩個 client 一起斷開。主題則接上 app 的配色，讓即時功能不像是外掛。

現在聊天與通話的「引擎」已經裝好，但沒有任何畫面用它。下一步要做出訊息分頁：病人直接進入唯一對話，員工則從共享收件匣開啟個別對話。
