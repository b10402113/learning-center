在 app root 接上兩個 client：一個 token、Chat 與 Video

Step 3/5 · Stream 即時聊天與視訊

學習目標

能在 app root 用同一張 server token 建立 Stream Chat 與 Video 兩個 client，並加上連線逾時降級，讓非即時功能不被拖垮。

前言：client 該在哪裡活著？

上一節把兩支端點寫好了：一支發 token，一支給病人的對話。現在手機知道要跟誰拿憑證了，但還沒有一個地方真的去拿、去連線。接下來的問題是：這兩個 client 該放在哪裡、由誰啟動、連不上時又該怎麼辦？

如果你把連線邏輯放在訊息畫面裡，會遇到一連串麻煩：病人一進到別的頁面，client 就被卸載、連線中斷、未讀狀態亂掉；而當 Stream 掛掉時，整張 app 會卡在一顆轉不停的圈圈，連跟聊天無關的預約、AI 助理都不能用。所以正確的位置是 app 的 root，一生只建立一次，並且把「連不上」當成一個正常的狀態來處理。這一節要做的就是這件事：在 root 建立兩個 client、共用同一張 token，並替連線加上逾時。

第一步：先定義這個 session 長什麼樣子

root 的檔案是 apps/mobile/src/lib/stream.tsx。先把 server 回的 token 回應定型，並定義一個逾時常數：

type StreamSession = {
  apiKey: string;
  userId: string;
  name: string;
  role: 'patient' | 'staff' | 'dentist';
  token: string;
};

/**
 * How long to wait for Stream before giving up and running without it.
 * Neither wait below is self-limiting — `fetch` has no timeout, and
 * `useCreateChatClient` retries a failing connection indefinitely — so without
 * this the whole app sits behind a spinner whenever the API or Stream is
 * unreachable. Messaging is a feature; booking and the assistant are not
 * allowed to die with it.
 */
const CONNECT_TIMEOUT_MS = 12_000;

StreamSession 的欄位正好對上上一節 token 端點回傳的內容。逾時訂在 12 秒，理由是註解裡那句話：這條鏈上有兩段等待本身不會自己結束，fetch 沒有預設逾時，useCreateChatClient 會在連線失敗時不斷重試。少了這個上限，只要 API 或 Stream 不可達，整個 app 就會永遠停在載入畫面。這個專案選擇的立場很明確：聊天是一個功能，但預約和 AI 助理不該陪它一起死。

第二步：建立祖先元件，決定要連線還是放行

StreamProvider 是掛在最外層的元件。它先讀 Clerk 的登入狀態，並準備一個放 session 的 state：

export function StreamProvider({ children }: { children: ReactNode }) {
  const { isLoaded, isSignedIn } = useAuth();
  const call = useApiClient();
  const [session, setSession] = useState<StreamSession | null>(null);
  const [failed, setFailed] = useState(false);

接著是「放棄連線」的處理。它不只是把狀態設成失敗，還要把是哪一段等待逾時記錄下來，方便日後在 Sentry 分辨是 token 出問題還是 socket 出問題：

const giveUpAt = useCallback((stage: 'token' | 'socket', reason: 'error' | 'timeout') => {
  Sentry.logger.warn('stream unavailable, app running without messaging', {
    stage,
    reason,
    timeout_ms: CONNECT_TIMEOUT_MS,
  });
  setFailed(true);
}, []);

然後是實際去拿 token 的 effect。注意它是用 useApiClient() 包好的 call，所以 Clerk 的 token 會自動帶上，不需要自己手動塞標頭：

useEffect(() => {
  if (!isLoaded || !isSignedIn) return;
  let cancelled = false;
  call<StreamSession>('/api/stream/token', { method: 'POST' }).then(
    (next) => !cancelled && setSession(next),
    () => !cancelled && giveUpAt('token', 'error')
  );
  return () => {
    cancelled = true;
  };
}, [call, isLoaded, isSignedIn, giveUpAt]);

這裡的 cancelled 是用來處理「元件已卸載但請求才回來」的情況，避免對已經不存在的畫面設定狀態。成功就存下 session，失敗就呼叫 giveUpAt('token', 'error')。

第三步：替兩段等待各設一個截止時間

剛剛處理的是 token 請求「失敗」的情況，但還有一種更常見的狀況：請求既沒有成功、也沒有失敗，就只是卡著。所以除了錯誤處理，還要替等待時間設上限。第一段是 token POST：

// Stage 1 deadline: the token POST. Stops once a session lands.
useEffect(() => {
  if (!isSignedIn || failed || session) return;
  const timer = setTimeout(() => giveUpAt('token', 'timeout'), CONNECT_TIMEOUT_MS);
  return () => clearTimeout(timer);
}, [isSignedIn, failed, session, giveUpAt]);

第二段的等待發生在稍後的 ConnectedStream 裡，是聊天 socket 的連線；元件卸載前要記得 clearTimeout，否則會對已經結束的流程誤報逾時。最後由 render 的條件決定畫面：

if (!isLoaded) return <Connecting />;
if (!isSignedIn || failed) return <>{children}</>;
if (!session) return <Connecting />;

return (
  <ConnectedStream session={session} onUnavailable={giveUp}>
    {children}
  </ConnectedStream>
);

這三行的差別很重要。還在讀登入狀態時顯示 Connecting；沒登入或已經放棄連線時，直接回傳 children，也就是讓整個 app 照常運作，只是沒有聊天；有 session 才進入 ConnectedStream。這就是「優雅降級」的實作：聊天不在，其他功能照跑。

第四步：在同一個地方建立兩個 client

ConnectedStream 是真正把兩個 client 生出來的地方。先做一個可重複使用的刷新函式，再把同一份使用者資料交給 Chat 與 Video：

// Re-hits the same authenticated endpoint on expiry. Stable, because
// `useApiClient` holds Clerk's getToken in a ref.
const tokenProvider = useCallback(
  () => call<StreamSession>('/api/stream/token', { method: 'POST' }).then((s) => s.token),
  [call]
);

const userData = useMemo(
  () => ({ id: session.userId, name: session.name }),
  [session.userId, session.name]
);

const chatClient = useCreateChatClient({
  apiKey: session.apiKey,
  tokenOrProvider: tokenProvider,
  userData,
});

這裡又一次看到「刷新就是再打同一支端點」。Chat client 由 useCreateChatClient 建立，傳入 apiKey、使用者資料與 tokenOrProvider；tokenOrProvider 這個名字的意思是：你可以直接給 token，也可以給一個會在需要時去拿 token 的函式。這裡給函式，所以過期時 SDK 會自己呼叫它換新的。

Video client 則刻意不用 new：

// getOrCreateInstance, never `new`: a second instance breaks ringing state
// and push wake-ups. Idempotent for the same user, which is what makes it
// safe to derive here rather than through an effect + setState.
const videoClient = useMemo(
  () =>
    StreamVideoClient.getOrCreateInstance({
      apiKey: session.apiKey,
      user: userData,
      token: session.token,
      tokenProvider,
      options: { rejectCallWhenBusy: true },
    }),
  [session.apiKey, session.token, userData, tokenProvider]
);

為什麼不能用 new？因為一個使用者只能有一個 Video client，如果畫面重整或元件重繪時又建了第二個，來電響鈴的狀態和推播喚醒都會壞掉。getOrCreateInstance 保證同一個使用者拿到同一個實例，所以放在 useMemo 裡、用 session 當依賴是安全的。rejectCallWhenBusy: true 則表示通話中再有來電會被拒接，避免同時接兩通。

第五步：處理登出，並把 client 傳下去

登出或換帳號時，最怕舊使用者的 token 還留著，導致新使用者短暫用錯身分連上。這個專案在 render 期間就把它清掉：

// Signing out — or switching account — must not leave the previous user's
// Stream token in play while the next one is still in flight, or the app
// briefly connects to Stream as the wrong person. Adjusted during render,
// matching MeProvider. https://react.dev/learn/you-might-not-need-an-effect
if (wasSignedIn !== isSignedIn) {
  setWasSignedIn(isSignedIn);
  setSession(null);
  setFailed(false);
}

最後是 provider 的 render 結構。Video 包在最外層，Chat 在裡面，而 RingingCalls 放在導覽器旁邊：

<StreamVideo client={videoClient} style={videoTheme}>
  <OverlayProvider value={{ style: chatTheme }}>
    <Chat client={chatClient}>
      <ClinicContext.Provider value={{ ready: true, ...clinic }}>
        {children}
      </ClinicContext.Provider>
    </Chat>
  </OverlayProvider>
  {/* Sibling of the navigator so a ring covers whatever screen is open. */}
  <RingingCalls />
</StreamVideo>

這個巢狀順序不是隨便排的：StreamVideo 提供視訊情境，OverlayProvider 帶入聊天的佈景主題，Chat 提供聊天情境，ClinicContext.Provider 再把「ready、channelId、成員名單」往下傳，讓任何畫面都能用 useClinic() 拿到。而 RingingCalls 放在導覽器旁邊，是為了讓來電覆蓋任何畫面，這在下一節講通話時會再看到。

小結

Stream 的兩個 client 應該在 app root 建立，而不是綁在某個畫面上。StreamProvider 用 Clerk 的登入狀態決定要不要連線，並替 token POST 與聊天 socket 各設一個 12 秒的截止時間，任一段放棄就讓 app 以「沒有聊天」的模式照常運作。ConnectedStream 用同一張 token 建立 Chat client 與 Video client，Video 用 getOrCreateInstance 保證單例，兩者共用一個 tokenProvider 負責過期刷新；登出時立刻清掉舊 session，避免用錯身分連上。

client 就緒之後，終於可以碰使用者真正看到的畫面了。下一節要在同一個訊息頁面上，做出兩種角色截然不同的體驗：病人直接進入唯一的診所對話，員工則看到每一筆病人對話組成的收件匣。
