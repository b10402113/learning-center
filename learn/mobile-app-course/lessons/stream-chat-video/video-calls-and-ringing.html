視訊通話：排程 teleconsult 與即時 ring 的兩種入口

Step 5/5 · Stream 即時聊天與視訊

學習目標

學完這一節，你應該能分辨兩種視訊通話入口的差別：排程好的 teleconsult 用一個由 server 推導的固定 call id，讓雙方不用協調就進到同一間房；即時 ring 則每次都建立一個新的 call id，並以覆蓋在最上層的畫面呈現，所以使用者不管在哪一頁都收得到來電。

前言：一顆按鈕，其實通往兩種完全不同的情境

上一節最後，共用的聊天 header 上有一顆視訊按鈕。但 Dentify 裡的視訊通話其實有兩個完全不同的入口，只是使用者看起來都像在「打視訊電話」。

第一個入口是預約好的視訊看診。病人在某個時間有一場 appointment，時間到了，他按下卡片上的 Join，診所的牙醫也從自己那一端加入，兩個人要進到同一間虛擬診間。第二個入口是即時鈴聲：病人可能在 AI 助理畫面，甚至在預約流程中，突然收到診所打來的視訊來電。一個是「約好時間、各自赴約」，另一個是「想到就打、對方可能在任何地方」。這一節要把這兩條路徑講清楚，因為它們用同一個 Video client，但進場方式和畫面呈現完全不同。

排程通話：call id 由 server 在預約時決定

排程看診的第一個難題是：雙方怎麼知道要進哪一間房？如果由客戶端自己想一個房間名稱，兩邊就會各進各的，永遠碰不到。Dentify 的解法是把這件事交給 server：預約建立時，就由 appointment 的 id 推導出 call id，寫成 appointment-{id}。之後不管是病人或牙醫，只要知道 appointment id，就能算出同一間房，完全不需要互相協調。

病人端按下 Join 後，畫面用這個 id 取得 call 物件：

const call = useMemo(
  () => (client && id ? client.call('default', id, { reuseInstance: true }) : undefined),
  [client, id]
);

reuseInstance: true 是一個重要細節。SDK 可能已經在別的地方建立過這個 (type, id) 組合，例如來電鈴聲或推播喚醒。如果這裡再建第二個實例，就會洩漏一條連線。加上這個選項，SDK 會沿用既有實例，整個畫面剛好只擁有一個。

加入時，先設定一個較寬鬆的斷線容忍時間，再嘗試加入：

call.setDisconnectionTimeout(120);
call.join({ create: true }).then(...);

setDisconnectionTimeout(120) 讓通話在網路短暫中斷時能撐過去，而不是病人走進電梯、訊號一閃就結束整場看診。成功加入與失敗都會寫一筆 log，而失敗訊息只會記錄 WebRTC 的錯誤字串，不會帶任何病人的資料。

離開畫面時則要掛斷，但必須先確認還沒離開：

return () => {
  if (call.state.callingState !== CallingState.LEFT) call.leave().catch(() => {});
};

因為 CallContent 自己的掛斷按鈕也可能已經讓通話離開，重複離開會拋錯，所以要先檢查狀態。真正畫出畫面的是 CallContent，它內建了靜音、開關鏡頭、掛斷等通話控制，我們不需要自己刻這些按鈕。

即時 ring：每次鈴響都是一個新房間

即時通話的邏輯和排程通話剛好相反。排程通話需要「固定」的 call id，即時鈴聲則需要「每次都不同」。原因藏在 Stream 對 call id 的定義：一個 call id 被當成一間持久的房間，重複使用同一個 id，會把上一次通話的殘留狀態一起帶回來。所以每次發動鈴聲都要用一個全新的識別碼：

const call = client.call('default', randomUUID(), { reuseInstance: true });
await call.getOrCreate({
  ring: true,
  video: true,
  data: { members: memberIds.map((user_id) => ({ user_id })) },
});

getOrCreate 帶上 ring: true，就是告訴 Stream「這是一通要響鈴的來電」，SDK 會負責讓被叫的那一端跳出來電畫面。members 是要邀請的人；如果名單裡只有自己一個人，那就沒有對象可打，函式會直接回傳 false，畫面再顯示「目前沒有人可以通話」。

前一節的聊天 header 按鈕和 home 畫面的 Video Consult 按鈕，呼叫的都是同一支 useRingCall，差別只在成員名單從哪裡來：聊天按鈕用對話的成員，home 畫面用 GET /api/stream/channel 回傳的 memberIds。

來電為什麼要畫在最上層，而不是一個畫面

即時鈴聲最難的地方不是撥出去，而是「被叫的那一端要怎麼被看見」。如果來電只是一個特定的畫面，那麼使用者只要不在那個畫面就收不到。病人可能正在填預約表單、正在跟 AI 助理對話、甚至手機剛從背景喚醒，來電都必須跳出來。

Dentify 的做法是把來電渲染成蓋在所有畫面之上的覆蓋層，而且掛在導覽器旁邊，而不是某個畫面裡：

function RingingCalls() {
  const ringingCall = useCalls().filter((c) => c.ringing)[0];
  if (!ringingCall) return null;

  return (
    <StreamCall call={ringingCall}>
      <View style={StyleSheet.absoluteFill}>
        <RingingCallContent />
      </View>
    </StreamCall>
  );
}

useCalls() 會拿到目前所有通話，篩出正在響鈴的那一通。真的有來電時，RingingCallContent 會自己在「收到來電」「撥出中」「已接聽」這幾種介面之間切換，我們不需要自己判斷該顯示哪一個。因為它掛在 root，任何畫面都能被它蓋住，這就是為什麼來電永遠不會漏接。

兩者最大的共同點是：通話控制（靜音、鏡頭開關、掛斷）都由 SDK 內建提供，開發者要處理的是「怎麼進到這通電話」以及「進來之後畫面蓋在哪裡」。

小結

同一套 Stream Video client 支援兩種通話入口。排程看診用 server 推導的固定 call id appointment-{id}，雙方不約而同進到同一間房，並用 CallContent 呈現內建的通話控制；即時鈴聲每次用一個新的 id，透過 getOrCreate({ ring: true }) 通知對方，並以掛在 root 的 RingingCalls 覆蓋層呈現，所以人在任何畫面都接得到。排程要固定、鈴聲要唯一，這是兩條路徑最根本的差別。

到這裡，Dentify 的即時聊天與視訊就完成了：身分由 server 決定，token 短效且會自動更新，兩個 client 在 root 接上，訊息與通話各自有清楚的入口。接下來你可以把同一套模式套回自己的 app，並思考一個問題：你的產品裡，聊天與視訊是「約好時間的功能」還是「隨時可打的功能」？答案會決定 call id 該由誰決定、該不該用覆蓋層。
