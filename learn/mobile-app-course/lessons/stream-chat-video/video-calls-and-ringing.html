視訊通話：排程 teleconsult 與即時 ring 的兩種入口

Step 5/5 · Stream 即時聊天與視訊

學習目標

能分辨排程通話的固定 call id 與即時 ring 的一次性 call id，並說明 ring overlay 為什麼要掛在 root 而不是各畫面。

前言：兩種叫得上人的時機

視訊在診所 app 裡有兩種完全不同的使用時機。第一種是事先約好的遠距看診：病人跟診所敲定了時間，時間一到，雙方都要進到「同一個房間」，不能各自跑到不同的通話裡。第二種是臨時的來電：診所看診到一半，想立刻打給病人問一件事，於是直接按下通話鍵，對方的手機就響了。

這兩種情境看起來只是同一顆通話鍵的兩種用法，但在 Stream 裡，它們對「通話 id 從哪裡來」的答案剛好相反。搞懂這個差別，才不會遇到「明明約好同一時間，卻進了不同房間」或「每次打過去都看到上一通通話的殘影」這種鬼問題。這一節就把兩種入口講清楚，並說明來電畫面為什麼要掛在整個 app 的最外層。

通話在 Stream 裡是一個「房間」

先建立一個核心觀念：在 Stream 的視訊模型裡，一個 call id 代表一個可以重複進出的房間，而不是一次通話事件。這個特性很方便：你只要知道房間號碼，就能隨時進去，不必先協調誰先開房。但它也有一個副作用：如果重複使用同一個 id，Stream 會把那個房間先前的狀態接回來，於是新的一通電話可能一開場就帶著上一通的參與者或畫面。

所以這個專案的規則很簡單：需要「固定房間」的情境就用推導出來的穩定 id；需要「一次性通話」的情境就每次產生新的 id。兩種需求、兩種 id 策略。

排程看診：固定房間，id 由 server 推導

約好的遠距看診屬於前者。它的房間 id 是 appointment-{id}，在預約建立時就由 server 算好，不是手機自己發明的。這帶來兩個好處：同一個預約的醫病雙方一定會算到同一個房間；而且 id 不是 client 提供的，病人無法自己指定要去哪個房間。

手機端的畫面在 app/call/[id].tsx，它拿到的 id 就是這個推導出來的值：

export default function CallScreen() {
  const { id } = useLocalSearchParams<{ id: string }>();
  const client = useStreamVideoClient();
  const [error, setError] = useState<string | null>(null);

  // reuseInstance: the SDK may already hold this (type, id) from a ring or a
  // push wake-up; constructing a second one leaks the SFU connection. The call
  // is derived rather than held in state so this screen owns exactly one.
  const call: Call | undefined = useMemo(
    () => (client && id ? client.call('default', id, { reuseInstance: true }) : undefined),
    [client, id]
  );

進房之前先設一個斷線容忍時間，然後才加入：

useEffect(() => {
  if (!call) return;
  // Ride out a lift or a tunnel instead of ending the consultation.
  call.setDisconnectionTimeout(120);
  const startedAt = Date.now();
  call.join({ create: true }).then(
    () =>
      Sentry.logger.info('teleconsult joined', {
        call_type: 'default',
        join_duration_ms: Date.now() - startedAt,
      }),
    (err) => {
      // A consultation nobody could join is the worst failure this app has —
      // the patient is sat waiting and the dentist is billing the slot.
      Sentry.logger.error('teleconsult join failed', {
        call_type: 'default',
        reason: err instanceof Error ? err.message : 'unknown',
        duration_ms: Date.now() - startedAt,
      });
      setError('Could not join the consultation. Check your connection and try again.');
    }
  );

  return () => {
    // Guarded: CallContent's hangup already left, and leaving twice throws.
    if (call.state.callingState !== CallingState.LEFT) call.leave().catch(() => {});
  };
}, [call]);

這裡有幾個判斷要看清楚。setDisconnectionTimeout(120) 讓使用者走進電梯或穿過隧道時，通話可以撐過短暫的斷線，而不是立刻結束看診。加入成功與失敗都寫進 Sentry，因為「約好的看診沒人能加入」是這個 app 最嚴重的故障之一：病人坐在那裡等，診所的時段也被佔住了。最後清理時要先確認狀態不是 LEFT，因為 CallContent 的掛斷按鈕可能已經離開過了，重複離開會丟錯。

即時來電：一次性的房間，id 每次重來

臨時要打給對方的情境屬於後者。它沒有預約、沒有事先談好的時間，所以不能沿用固定的房間號碼，否則會把上一通的狀態帶進來。這個專案的做法是：每次按下通話都產生一個全新的隨機 id。

/**
 * Places a ringing call. A fresh id per ring: Stream treats a call id as a
 * durable room, so reusing one replays the previous call's state.
 */
export function useRingCall() {
  const client = useStreamVideoClient();

  return useCallback(
    async (memberIds: string[]) => {
      // A call needs someone on the other end; one member is just yourself.
      if (!client || memberIds.length < 2) return false;
      const call = client.call('default', randomUUID(), { reuseInstance: true });
      await call.getOrCreate({
        ring: true,
        video: true,
        data: { members: memberIds.map((user_id) => ({ user_id })) },
      });
      return true;
    },
    [client]
  );
}

這段程式碼藏了三個設計決定。第一，randomUUID() 每次產生新的 id，對應到「這是一通新電話」。第二，memberIds.length < 2 就放棄，因為通話至少要有一個人接，成員只有自己等於沒人能接。第三，getOrCreate 的參數裡帶了 ring: true 和 video: true，前者讓它變成會響鈴的來電、後者指定用視訊，而 data.members 就是要把鈴聲送到哪些人手上。

在對話畫面的標題列上，那顆視訊按鈕就是呼叫這個函式。它從目前對話的成員名單取得要打給誰，然後回傳的布林值決定要不要提示「目前沒人可打」：

const memberIds = Object.keys(channel?.state.members ?? {});
const started = await ring(memberIds);
if (!started) Alert.alert('Nobody to call', 'There is no one else in this conversation yet.');

這也解釋了為什麼對話畫面裡有 CallButton、而看診畫面是獨立的一頁：來電是從對話發起的，所以按鈕長在對話裡；排程看診是從預約進去的，所以是一條獨立的 route。

來電畫面為什麼掛在 root，而不是某個畫面裡

還有一個很容易被忽略、但體感差很多的細節：當有人打電話進來時，不管使用者當下在哪一頁，都應該看到響鈴畫面。如果來電畫面只掛在訊息頁，那麼病人正在填預約、或正在跟 AI 助理對話時，來電就會被吃掉。

所以 RingingCalls 被放在最外層，和導覽器並排：

function RingingCalls() {
  const ringingCall = useCalls().filter((c) => c.ringing)[0];
  if (!ringingCall) return null;

  return (
    <StreamCall call={ringingCall}>
      <View style={StyleSheet.absoluteFill}>
        {/* Routes itself between incoming, outgoing and accepted UI. */}
        <RingingCallContent />
      </View>
    </StreamCall>
  );
}

useCalls() 會拿到目前所有的通話，這裡只挑第一個正在響鈴的；沒有就回傳 null，什麼都不渲染。StreamCall 提供這通電話的情境，RingingCallContent 則是一組現成的 UI，會自己判斷現在該顯示「有人來電」、「正在撥出」還是「已接通」三種畫面。包在 absoluteFill 裡，讓它蓋滿整個畫面，也就是蓋在當前任何頁面之上。

通話控制：SDK 已經做好，你只要別擋它

接通之後，畫面是由 CallContent 負責的。它已經內建了一組通話控制：靜音／解除靜音、開關鏡頭、掛斷，以及顯示對方離開、參與者狀態等。你在測試時會看到的就是這些：按一下麥克風就能消音，按一下鏡頭就能關閉視訊，這些都不需要自己寫。

有一個實作上的小陷阱要記得：CallContent 會自己從主題裡的 insets 去加安全區域的內距，所以通話畫面不要再包一層 SafeAreaView，否則內距會被加兩次，按鈕與視訊畫面就會被推到奇怪的位置。這也是前一節在 root 把 safe area 的值放進 videoTheme 的原因。

把兩種入口並排，差別就很清楚：

面向排程 teleconsult即時 ring
觸發時機預約時間到，兩邊各自進入從對話按下通話鍵的當下
call id固定：appointment-{id}每次新的 randomUUID()
id 從哪來server 在預約時推導client 按下時產生
房間語意可重複進入的同一個房間一次性的通話事件
畫面位置獨立的 /call/[id] 頁root 的響鈴 overlay

這張表的核心其實只有一句話：固定的目的用固定 id，一次的事件用一次性 id。 排程看診要的是「同一個房間」，即時來電要的是「一通全新的電話」，兩者對 id 的需求正好相反，所以實作也分開。

小結

在 Stream 裡，call id 代表一個可以重複進出的房間。排程的遠距看診用 server 在預約時推導出的固定 id appointment-{id}，雙方不必協調就會進到同一個房間；即時來電則每次用 randomUUID() 產生新 id，避免把上一通的狀態接回來。RingingCallContent 掛在 root、蓋在任何畫面之上，所以使用者在哪一頁都能收到來電；接通後的靜音、鏡頭、掛斷等控制由 CallContent 內建，只要記得不要再包一層 SafeAreaView，以免內距被重複計算。

走到這裡，這個節點的五步都完成了：你有了安全的身分模型、兩支後端端點、root 上的兩個 client、兩種角色的訊息畫面，以及兩種不同語意的視訊通話。它們其實共用同一條主軸：server 決定身分，client 只負責使用它；而聊天與視訊，只是同一套身分的兩種用法。
