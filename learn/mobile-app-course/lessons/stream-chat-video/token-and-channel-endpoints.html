Token endpoint 與 channel endpoint：server wrapper 與短效憑證

Step 2/5 · Stream 即時聊天與視訊

學習目標

能在 Next.js 後端寫出 mint token 與取得 patient clinic channel 的兩個端點，並說明短效 token 為什麼要設計成可重複刷新。

前言：把「誰能用」變成兩支真的 API

上一節把身分模型的規則講清楚了：手機不能自己報身分，一切由 server 決定。但規則不能只寫在紙上，得有人真的去簽那張通行證，也得有人告訴病人「你該進哪個對話」。這一節要做的就是這兩件事，寫成兩支 Next.js 的 Route Handler。

動手前先確認你具備什麼。你應該已經懂 Route Handler 的檔案位置與方法匯出慣例，也知道 requireAuth() 與 route() 包裝各自負責什麼；如果這兩件事還有點模糊，先回去看 Next.js API Route Handlers 那個節點。另外，Stream 應用程式要已經透過 stream login 建好，環境變數也放進 apps/web/.env。這節結束時，你會得到兩支可以實際呼叫的端點，而且它們回傳的內容正是下一步 app root 要用的。

第一步：放好環境變數

先確認 web 專案讀得到兩個值。一個是可以公開的應用程式 key，另一個是絕對不能外流的 secret：

export const STREAM_API_KEY = process.env.NEXT_PUBLIC_STREAM_API_KEY;
const STREAM_API_SECRET = process.env.STREAM_API_SECRET;

命名上的 NEXT_PUBLIC_ 前綴不是裝飾，它是 Next.js 的規則：有這個前綴的變數才會被打包進前端程式碼，所以 key 可以讓手機拿到。相對地，STREAM_API_SECRET 沒有前綴，它只存在於 server 的環境裡。這裡就是你「有沒有把萬用鑰匙留在 server」的實際檢查點。改完環境變數記得重啟 web server，否則舊行程讀不到新值。

第二步：寫一個 server 端的 Stream 入口

不要讓每個檔案各自 new 一個 Stream 物件。集中寫一個 wrapper，第一次呼叫時建立、之後重複使用，而且缺設定時立刻給出清楚的錯誤：

let cached: StreamChat | null = null;

export function streamServer(): StreamChat {
  if (!STREAM_API_KEY || !STREAM_API_SECRET) {
    throw badRequest('Stream is not configured');
  }
  cached ??= StreamChat.getInstance(STREAM_API_KEY, STREAM_API_SECRET);
  return cached;
}

這裡有三個手法值得記住。cached ??= ... 的意思是「如果 cached 還是空的，才建立並存起來」，也就是單例（singleton）；重複呼叫不會一直開新連線。StreamChat.getInstance(...) 是 Stream SDK 提供的取得實例方法。最後，如果兩個環境變數少了任何一個，就 throw badRequest，讓錯誤在呼叫端被 route() 包裝成乾淨的 JSON，而不是等到真正要用時才出現看不懂的崩潰。

第三步：簽一張短效 token

token 的有效期限寫在檔案上方，四小時：

/** Tokens are short-lived; the app re-hits /api/stream/token to refresh. */
const TOKEN_TTL_SECONDS = 60 * 60 * 4;

為什麼不簽一張永久有效的就好？因為憑證一旦外流，永久有效的代表永遠有效；短效憑證即使被偷，能用的時間也有限，而且每一次刷新都會重新跑一次身分驗證，等於定期重新確認「你還是你」。這也是為什麼刷新端點不能繞過驗證，它必須跟第一次簽發走完全一樣的守衛。

簽名的動作在 mintToken 裡：把現在的秒數加上 TTL 當到期時間，再交給 createToken。實際的程式碼上一節看過，重點是它永遠只接受一個 AppUser，而 AppUser 來自 session。

第四步：讓 Stream 先認識這個人

Stream 有一個脾氣：它不接受「不存在的成員」。如果 token 指向一個 Stream 還不認識的 user id，之後建立 channel、加入成員都會失敗。所以在簽 token 之前，要先把這個人的身分同步過去。顯示名稱的產生方式依角色而異：

/** What a Stream user looks like to the other side of a conversation. */
async function displayName(user: AppUser): Promise<string> {
  if (isStaff(user.role)) {
    const [dentist] = await db.select().from(dentists).where(inArray(dentists.userId, [user.id]));
    return dentist?.displayName ?? 'Clinic Team';
  }
  const self = await selfPatient(user);
  return self ? `${self.firstName} ${self.lastName}` : 'Patient';
}

/** Stream rejects members that don't exist yet, so every id is upserted first. */
async function upsertParticipants(accountUsers: AppUser[]) {
  const named = await Promise.all(
    accountUsers.map(async (u) => ({
      id: streamUserId(u),
      name: await displayName(u),
      // Read by the mobile app to label a caller as clinic vs patient.
      staff: isStaff(u.role),
    }))
  );
  await streamServer().upsertUsers(named);
}

員工會去 dentists 表查顯示名稱，找不到就退回 'Clinic Team'；病人則用自己檔案裡的名字。每個 upsert 的物件還帶了一個 staff: true/false，這是自訂欄位，之後手機可以靠它判斷來電者是診所還是病人，不必再多查一次資料庫。upsertUsers 是「有就更新、沒有就新增」，所以重複呼叫是安全的。

把上面兩個動作包成一個函式，就是簽 token 時要順便做的事：

/** Sync the caller's Stream identity. Called on every token mint. */
export async function syncStreamUser(user: AppUser): Promise<string> {
  const name = await displayName(user);
  await upsertParticipants([user]);
  return name;
}

第五步：token 端點本身

有了前面的零件，端點就只剩組裝。檔案是 apps/web/src/app/api/stream/token/route.ts，只匯出一個 POST：

export const POST = route(async () => {
  const user = await requireAuth();
  const name = await syncStreamUser(user);

  return json({
    apiKey: STREAM_API_KEY,
    userId: streamUserId(user),
    name,
    role: user.role,
    token: mintToken(user),
  });
});

預期看到的結果是：帶著有效 Clerk 登入去打這支端點，會拿到一包 JSON，裡面有可公開的 apiKey、這個人的 userId、name、role，以及重點 token。你可以在這裡做一個小驗證：故意把 Clerk 登入拿掉再打一次，應該被 requireAuth() 擋下。這證明「刷新」和「簽發」走的是同一支端點、同一道守衛。

第六步：channel 端點與 id 的推導

聊天需要一個「房間」。這個專案有一個刻意的設計決定：一個病人只跟診所有一個對話，而且這個對話的 id 直接從病人 id 推導出來，不另外開一張資料表記錄。

/** PLAN.md A9: one channel per patient, id derived — no channel table. */
export function clinicChannelId(patientId: string): string {
  return `patient-${patientId}`;
}

export const isStaff = (role: AppUser['role']) => role === 'staff' || role === 'dentist';

注意 isStaff 把 staff 和 dentist 都算成員工。這個判斷等一下會決定端點要回傳一個對話，還是回傳「你自己去收件匣看」。真正準備房間的函式是 ensureClinicChannel：

export async function ensureClinicChannel(user: AppUser) {
  const self = await selfPatient(user);
  if (!self) throw badRequest('Finish onboarding before messaging the clinic');

  const staff = await staffUsers();
  await upsertParticipants([user, ...staff]);

  const memberIds = [streamUserId(user), ...staff.map(streamUserId)];
  const channel = streamServer().channel('messaging', clinicChannelId(self.id), {
    members: memberIds,
    created_by_id: streamUserId(user),
    // Staff see a shared inbox, so the channel has to name the patient.
    name: `${self.firstName} ${self.lastName}`,
  });
  await channel.create();

  // Staff hired after the channel was created are not members yet.
  const existing = new Set(Object.keys(channel.state.members));
  const missing = memberIds.filter((id) => !existing.has(id));
  if (missing.length) await channel.addMembers(missing);

  return { channelId: channel.id!, memberIds };
}

這段程式碼有幾個關鍵。selfPatient(user) 要求病人已完成 onboarding，還沒完成就丟 badRequest，因為沒有病人檔案就沒有對話可言。成員清單是「這個病人 + 所有員工」，所以病人一開 app，診所所有人都已經在房間裡。建立時的 name 要放病人姓名，因為員工端看到的是共用收件匣，需要靠名字分辨是哪一位。channel.create() 是 idempotent 的，第一次呼叫真的建立，之後呼叫只會取回同一個；最後再補上新進員工，讓後來才到職的人也能加入。

最後把這些接進端點。檔案是 stream/channel/route.ts，只匯出 GET：

export const GET = route(async () => {
  const user = await requireAuth();
  if (isStaff(user.role)) return json({ channelId: null, memberIds: [] });
  return json(await ensureClinicChannel(user));
});

預期結果分成兩種角色。病人會拿到 { channelId, memberIds }，其中 memberIds 同時也是「可以打給誰」的名單，所以開通話不需要再多繞一趟。員工會拿到 { channelId: null, memberIds: [] }，因為員工沒有單一對話，他有的是收件匣；下一節的畫面會直接用 SDK 依成員身分查詢，不需要這支端點幫忙。

小結

這個節點把身分模型做成兩支端點。server wrapper streamServer() 用單例集中管理 Stream 連線，缺設定就立刻報錯。POST /api/stream/token 先 requireAuth() 確認身分、syncStreamUser() 把使用者 upsert 進 Stream，再回傳可公開的 apiKey 與短效 token；同一支端點也負責刷新。GET /api/stream/channel 則對病人推導出 patient-{id} 的對話並回傳成員名單，對員工回傳 null。整條路徑上，API secret 從不離開 server。

端點備好了，但現在手機還不知道怎麼用它。下一節要在 app 的 root 建立 Stream 的 Chat 與 Video 兩個 client，讓它們共用同一張 token，並且在 Stream 連不上時優雅降級，不讓整個 app 卡在轉圈圈。
