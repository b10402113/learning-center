Token endpoint 與 channel endpoint：server wrapper 與短效憑證

Step 2/5 · Stream 即時聊天與視訊

學習目標

做完這一節，你會得到兩個可用的 Next.js Route Handler：POST /api/stream/token 回傳一包含 token 的 session，GET /api/stream/channel 回傳這位病人該進的對話。前置是你要先有可用的 requireAuth() 守衛，以及 Stream 應用程式的 API key 與 secret。

前言：規則要變成兩個端點

上一節把規則講完了：身分由 server 決定、secret 只留 server、token 短效。但規則不會自己生效，它得落在兩個實際的請求端點上。第一個負責「你是誰、這張通行證給你」，第二個負責「那你該進哪一個對話」。

這一節的骨幹是程式碼，但請留意每個決定背後都對應上一節的原則。例如 token 端點完全不碰請求內容，就是「不信任 client 身分」的直接落實；channel 端點對員工回傳 null，則是「病人一人一對話、員工有共享收件匣」的模型差異。把這兩件事寫對，第四步的畫面才有正確的資料可用。

先把 Stream 的伺服器邏輯收進一個 wrapper

不要讓每個 Route Handler 各自呼叫 Stream SDK。Dentify 把所有伺服器端邏輯集中在一支 apps/web/src/lib/stream.ts，其他檔案只依賴它輸出的函式。這樣 secret 只被讀取一次，身分推導也只有一個地方，日後要改不用追很多檔。

第一步是建立唯一的 client 並讀取環境變數：

export const STREAM_API_KEY = process.env.NEXT_PUBLIC_STREAM_API_KEY;
const STREAM_API_SECRET = process.env.STREAM_API_SECRET;

let cached: StreamChat | null = null;

export function streamServer(): StreamChat {
  if (!STREAM_API_KEY || !STREAM_API_SECRET) {
    throw badRequest('Stream is not configured');
  }
  cached ??= StreamChat.getInstance(STREAM_API_KEY, STREAM_API_SECRET);
  return cached;
}

這裡有兩件事值得停下來看。第一，STREAM_API_KEY 用 NEXT_PUBLIC_ 前綴，代表它可以被前端看到，因為它只是一個應用程式代號；secret 則完全沒有這個前綴，只會被 server 讀到。第二，client 用 module 層的 cached 變數快取，避免每次請求都重建一個 Stream 連線。

接著是簽 token 的核心。它的時間戳是以秒為單位的現在時間，加上四小時的有效期：

const TOKEN_TTL_SECONDS = 60 * 60 * 4;

export function mintToken(user: AppUser): string {
  const exp = Math.floor(Date.now() / 1000) + TOKEN_TTL_SECONDS;
  return streamServer().createToken(streamUserId(user), exp);
}

streamUserId(user) 就是上一節那個「回傳 user.id」的函式。整條 token 的簽發完全建立在「user 物件來自登入 session」這個前提上。

端點一：POST /api/stream/token

有了 wrapper，token 端點本體短到只有幾行：

export const POST = route(async () => {
  const user = await requireAuth();
  const name = await syncStreamUser(user);

  return json({
    apiKey: STREAM_API_KEY,
    userId: streamUserId(user),
    name,
    role: user.role,
    token: mintToken(user),
  });
});

注意第一行就是 requireAuth()，而且整段程式沒有任何一處讀取 req。這正是上一節強調的：client 送來什麼都不重要，身分只從 session 來。syncStreamUser() 負責在每次發 token 時，順手把這個使用者更新到 Stream，因為 Stream 不允許對一個「不存在的人」發 token。

回傳的欄位都有用途：apiKey 讓 app 初始化 client，userId 與 name 是這張 token 的身分，role 讓 app 決定要顯示病人介面還是員工介面，而 token 則是真正的通行證。這個端點同時也是更新端點——token 過期時 app 再 POST 一次即可，因為 requireAuth() 每次都會重跑。

端點二：GET /api/stream/channel

第二個端點負責回答「這位使用者該進哪個對話」。它依角色分岔：

export const GET = route(async () => {
  const user = await requireAuth();
  if (isStaff(user.role)) return json({ channelId: null, memberIds: [] });
  return json(await ensureClinicChannel(user));
});

員工回傳 null，不是因為他們不能聊天，而是因為他們沒有「一個」對話，他們面對的是一整個共享收件匣。病人則回傳一個固定的對話 id 與成員清單，成員清單同時也是「要打視訊電話時該敲誰」的名單，所以通話不需要再另外查一次。

真正的建立邏輯在 ensureClinicChannel()。它的對話 id 是從病人 id 推導出來的，不另外開表儲存：

/** PLAN.md A9: one channel per patient, id derived — no channel table. */
export function clinicChannelId(patientId: string): string {
  return `patient-${patientId}`;
}

「推導」而不是「查表」帶來一個很實用的性質：同一個病人永遠只會命中同一個對話，不需要擔心重複建立。建立時把整個診所的員工都拉進成員，最後再補上新進員工：

const memberIds = [streamUserId(user), ...staff.map(streamUserId)];
const channel = streamServer().channel('messaging', clinicChannelId(self.id), {
  members: memberIds,
  created_by_id: streamUserId(user),
  name: `${self.firstName} ${self.lastName}`,
});
await channel.create();

const existing = new Set(Object.keys(channel.state.members));
const missing = memberIds.filter((id) => !existing.has(id));
if (missing.length) await channel.addMembers(missing);

return { channelId: channel.id!, memberIds };

這整段是冪等的：第一次呼叫會建立對話，之後再呼叫只會把後來加入的員工補進成員名單。名字用的是病人全名，這是為了讓員工在共享收件匣裡認得出是誰在對話。

部署前要確認 NEXT_PUBLIC_STREAM_API_KEY 與 STREAM_API_SECRET 都放進 apps/web/.env，並且改完環境變數後重啟 web server。安裝 Stream 這類含原生模組的套件之後，app 也必須重新 build 一次，否則裝置上跑的是沒有這個模組的舊版本。

做完會看到什麼

用已登入的帳號打 POST /api/stream/token，會拿到一包 JSON，裡面的 token 是一長串簽章字串，role 反映該帳號的身分。用病人帳號打 GET /api/stream/channel，會拿到 { channelId, memberIds }；同一個請求換成員工帳號，則拿到 { channelId: null, memberIds: [] }。兩個端點都受 requireAuth() 保護，未登入會直接被擋下。

小結

這兩個端點把身分規則落到實處。POST /api/stream/token 只從登入 session 取身分，簽發四小時的 token，同時回傳 apiKey、userId、name 與 role；而且因為每次都會重跑 requireAuth，它本身就是更新端點。GET /api/stream/channel 依角色分岔：病人拿到推導出的 clinic channel 與成員名單，員工拿到 null 去用共享收件匣。背後由 lib/stream.ts 集中管理 secret、token 與冪等的對話建立，讓其他程式碼不必碰 Stream SDK 的細節。

到這裡，後端可以發身分、也可以指出對話了，但手機端還沒有任何東西去接。下一步要回到 Expo app，在整個應用程式的最上層建立 Chat 與 Video 兩個 client。
