Stream 的身分與 token：為什麼 user id 只能由 server 決定

Step 1/5 · Stream 即時聊天與視訊

學習目標

能說出為什麼 Stream 的 user id 必須由 server 從 Clerk session 推導，以及 Chat 與 Video 為什麼共用同一個 token。

前言：如果手機能自己說「我是誰」

先想像一個很誘人的做法。你的 app 要接上聊天和視訊，於是你讓手機在連線時自己報上一個名字：「嗨，我是 staff-001，這是我的通行證。」聽起來很省事，因為身分由前端自己決定，server 不必多做事。

但這個做法只要被人看穿一次，整個診所的對話就門戶洞開。任何人只要下載你的 app，改幾行程式讓它報上員工的 id，就能拿到一張員工的通行證，然後把整間診所的病人對話全部讀走。問題不在於加密做得好不好，而在於「誰有權決定你是誰」這條界線一開始就畫錯了。

這一節要把 Stream 的身分模型講清楚。Stream 是一個託管的聊天與視訊服務，我們不自己碰 WebRTC、也不自己開 socket，只負責在 server 端回答一個問題：這個人是誰？把這個問題答對，後面所有的聊天與通話功能才有安全的地基。

聊天與視訊不是自己刻的：Stream 負責什麼

串流通訊這種東西，自己從零刻會踩到非常多坑：WebRTC 的連線協商、NAT 穿透、裝置權限、推播喚醒、已讀狀態、打字提示……任何一項都能吃掉好幾個禮拜。所以這個專案選擇把這些交給 Stream。Stream 提供聊天、視訊、動態牆與內容審核的 SDK，Bumble、Strava、Adobe、Walmart 這類產品都在用，它也提供免費方案讓你起步。

導入的方式不是進 dashboard 慢慢點，而是在終端機跑 stream login，選好應用程式後由 CLI 幫你產生 stream/ 資料夾並更新 .gitignore，接著安裝 Stream 的 agent skills。這些 skill 是一包 markdown 檔，會直接告訴 AI agent 這個 API 該怎麼用，agent 就不必靠猜。之後你只要對 agent 說「用 Stream 幫我做視訊通話」，它就知道要套哪一套寫法。

但無論工具多方便，有一件事永遠是我們自己的責任：決定「誰能用這套服務」。Stream 負責傳輸與功能，我們負責身分。

一個看似方便、其實危險的做法

最直覺的作法，是讓手機在請求 token 時順便附上自己的 user id，或更糟，讓手機自己拿著 API secret 去簽名。這樣寫起來很快，但等於把身分的決定權交到使用者手上。

這裡的關鍵差別是：一個「登入證明」和一個「服務憑證」是兩回事。使用者透過 Clerk 登入，那是他證明「我是這個帳號」的方式；但 Stream 的 API secret 是「我可以代表整個應用程式發言」的鑰匙，權限高得多。如果把 secret 放進手機 app，任何反編譯的人都拿得到，這把鑰匙能簽出任何人的 token。

兩種做法的後果差很多：

做法user id 從哪來後果
讓 client 自己報 id請求內容（可被任意修改）病人可偽造員工 token，讀光所有對話
把 API secret 放進 app任何人都能反編譯取得整把萬用鑰匙外流，形同門戶洞開
由 server 從 session 推導Clerk session，無法被 client 改寫你只能拿到自己的 token

正確的身分模型：server 推導、token 短效

正確的作法反過來：手機永遠不說自己是誰，它只會送出一段「我已登入」的請求；server 收到後，從 Clerk 的 session 裡讀出這個帳號，再決定對應的 Stream user id。這個 id 不是新發明的，就直接用我們資料庫裡的使用者 id，一對一對應。

/**
 * One Stream identity per account, keyed by our own `users.id`. Chat and Video
 * share it — a single token authenticates both products on the same API key.
 */
export function streamUserId(user: AppUser): string {
  return user.id;
}

export function mintToken(user: AppUser): string {
  const exp = Math.floor(Date.now() / 1000) + TOKEN_TTL_SECONDS;
  return streamServer().createToken(streamUserId(user), exp);
}

streamUserId 短到只有一行，但它是整個安全模型的支點：id 的來源是 AppUser，而 AppUser 是 server 從 session 驗證後才拿到的，不是 client 送上來的。接著 mintToken 用這個 id 加上一個到期時間簽出 token。這裡的 token 有效期限是四小時，屬於短效憑證；過期之後 app 再打一次同一支端點換新的，所以這支端點同時也是「刷新」端點。

來看看實際回傳什麼。端點的路徑是 POST /api/stream/token：

export const POST = route(async () => {
  const user = await requireAuth();
  const name = await syncStreamUser(user);

  return json({
    apiKey: STREAM_API_KEY,
    userId: streamUserId(user),
    name,
    role: user.role,
    token: mintToken(user),
  });
});

回傳的五個欄位各自有意義。apiKey 是可以公開的應用程式識別碼（對應環境變數裡的 NEXT_PUBLIC_STREAM_API_KEY），拿它配 token 才能連上你這個 app；userId、name、role 是這個人的身分與顯示資訊；token 才是那張短期通行證。注意這裡從頭到尾沒有出現 API secret，secret 只留在 server 行程裡，永遠不進到手機。

手機端的註解把這個契約寫得很白：

 * Both clients authenticate with one token from `POST /api/stream/token`. The
 * app never names its own Stream user id and never sees the API secret — the
 * server derives the id from the Clerk session, which is what stops a patient
 * minting a token for a staff member.

Chat 與 Video 為什麼共用一張通行證

Stream 的聊天和視訊雖然是兩個 SDK、兩個 client，但在身分這一層是同一件事。一行註解說得很清楚：One Stream identity per account... a single token authenticates both products on the same API key. 同一個 API key、同一個 user id、同一張 token，就能同時登入 Chat 與 Video。

這帶來一個很實際的好處：整張 app 只需要管理一條憑證的生命週期。登入時打一次 token 端點，把同一張 token 交給兩個 client；token 快過期時，兩個 client 都指向同一個刷新函式。如果 Chat 和 Video 各自要一套不同帳號、不同憑證，就得處理「其中一個登入成功、另一個失敗」這種半殘狀態，複雜度會高很多。

邊界的一個例外：病人名字

到這裡你可能會問：既然身分抓得這麼緊，那病人的名字是怎麼出現在員工的收件匣裡的？答案是，這是一個刻意開的例外。Stream 只擁有通話與訊息的內容，但員工需要看得懂「這是哪位病人傳來的」，所以顯示名稱會送給 Stream。這個 app 對第三方服務的通則是「PHI 絕不外流」，Sentry、log、推播都嚴格遵守；Stream 之所以能例外，是因為它簽了 BAA（商業夥伴協議），處理受保護的健康資訊是被允許的。

換句話說，這是一個經過判斷、也寫在計畫裡的取捨。什麼資料給誰，取決於對方有沒有能力和義務保護它。

小結

Stream 是託管的聊天與視訊後端，我們不碰底層傳輸，只負責在 server 決定「你是誰」。手機不能自己報上 user id，也不能持有 API secret；正確的作法是 server 從 Clerk session 推導 Stream user id，再簽出一張短效、可刷新的 token。Chat 與 Video 共用同一個 user id 與同一張 token，整張 app 只需管理一條憑證生命週期；而病人名字之所以能送到 Stream，是因為它簽了 BAA，是一個被允許、也經過判斷的例外。

畫好了「誰能用這套服務」這條界線，下一步就是把它做成真的端點。下一節要動手寫出兩支 API：一支發 token，一支順便告訴病人他該進哪個診所對話，並在 server 端把聊天用的 channel 準備好。
