Stream 的身分與 token：為什麼 user id 只能由 server 決定

Step 1/5 · Stream 即時聊天與視訊

學習目標

學完這一節，你應該能說出 Stream 的身分模型：為什麼 Stream 的 user id 一定要由 server 從登入 session 推導、為什麼 Chat 與 Video 共用同一個身分與 token，以及為什麼 API secret 絕對不能跑進 app 裡。

前言：聊天功能碰到的第一個問題，不是訊息，是「你是誰」

先想像你打開 Dentify 的病人 app，點進 Messages。畫面上要出現你和診所的對話，主機那端必須知道「現在連線的這個人是誰」，才能把正確的對話推給你。這件事聽起來很理所當然，卻藏著整個功能最關鍵的一個決定：這個身分，由誰說了算？

如果答案是由 app 自己報上名號，那任何一個已登入的病人，只要把程式改一改、把自己的 user id 換成某位員工的 id，就能拿到那位員工的通行證，然後讀完整間診所的對話。這不是誇張的假設，而是「token endpoint 接受 client 傳來的 user id」這個寫法必然的後果。

這一節先不寫功能。我們要把 Stream 這套託管服務的身分規則講清楚，因為後面四個步驟的每一段程式碼，都建立在同一條規則上：身分由 server 決定，client 只能使用它。

聊天與視訊為什麼通常不自己蓋

即時聊天和視訊通話背後是一整套很難的基礎設施。聊天要維護長連線、處理訊息送達順序、已讀狀態與推播；視訊更麻煩，要處理 WebRTC 的連線協商、把多路影像在伺服器端混流（SFU），還要撐住網路不穩時的斷線重連。這些東西自己蓋不是不行，但對一個一人團隊來說，光是把視訊接通就會吃掉整個專案的預算和時間。

Stream 就是這類需求的託管服務：你付錢，它幫你保管連線、訊息與通話狀態。我們自己在伺服器端只做兩件事——決定「這個登入者是誰」，以及發一張短效通行證給 app。剩下的即時功能，交給 Stream 的 SDK 處理。知道這條分工線之後，接下來就來看這張通行證到底長什麼樣子。

Stream 的四個角色：app、api key、secret、token

要聽懂身分模型，得先認識四個名詞。它們的角色差別很大，混在一起就會出錯。

角色是什麼放在哪
Stream user idStream 世界裡代表某個人的識別碼由 server 依我方 user id 推導
API key你的 Stream 應用程式代號，可以公開server 與 app 都能有
API secret用來簽發 token 的私密金鑰只存在 server 的環境變數
token用 secret 簽出的通行證，證明「這個 id 是我方認可的」server 簽好後才傳給 app

這裡的關鍵是：token 不是使用者密碼，而是「這個 user id 已經被我們驗證過」的簽章證明。因為它是由 API secret 簽出來的，任何人只要沒有 secret，就無法替別人的 user id 偽造一張 token。所以 secret 的存在位置就等於整個系統的安全邊界。

user id 由 server 推導，而不是由 client 提供

在 Dentify 裡，Stream user id 直接等於資料庫的使用者 id，函式只有一行：

/** One Stream identity per account, keyed by our own users.id. */
export function streamUserId(user: AppUser): string {
  return user.id;
}

注意這個 user 從哪裡來。token endpoint 裡，它是 requireAuth() 的回傳值，也就是從 Clerk 的登入 session 解出來的，不是從請求內容讀出來的：

export const POST = route(async () => {
  const user = await requireAuth();
  const name = await syncStreamUser(user);

  return json({
    apiKey: STREAM_API_KEY,
    userId: streamUserId(user),
    name,
    role: user.role,
    token: mintToken(user),
  });
});

對照一下壞做法，你就會明白差在哪。假設端點改成 const { userId } = await req.json()，那 token 就會被簽給任何一個 client 報上來的 id。這個漏洞不需要很高明的手法，只要會改一顆按鈕送出的參數就能利用。把身分來源換成 session 之後，client 根本沒有機會指定自己是誰，這條攻擊路徑就整條消失。

絕對不要在 token 端點讀取 client 傳來的 user id。使用者身分只能從登入 session 推導；否則任何已登入的人都能簽出員工的 token。

Chat 與 Video 共用同一個身分與 token

Stream Chat 和 Stream Video 雖然是兩個產品，卻可以掛在同一個應用程式的同一組憑證底下。這代表我們不需要為聊天和視訊各做一套身分，只要一個 user id、一張 token，就能同時連上兩邊。

/**
 * One Stream identity per account, keyed by our own `users.id`. Chat and Video
 * share it — a single token authenticates both products on the same API key.
 */

這個設計省下的不只是程式碼。如果聊天與視訊各有一套身分，你就得確保兩邊的 id 一一對應、登入登出時同步斷開、權限也各驗一次。共用身分之後，這些都變成同一個問題。第四、第五步會看到，同一個 auth 拿到的 token 會同時餵給 Chat client 和 Video client。

短效 token 與自動更新：把「一直驗身分」變成常態

Dentify 簽發的 token 只活四小時：

/** Tokens are short-lived; the app re-hits /api/stream/token to refresh. */
const TOKEN_TTL_SECONDS = 60 * 60 * 4;

短效的好處是，即使 token 真的外流，它的可用時間也有限。而當 token 快過期時，app 不是自己想辦法續約，而是再打一次同一個 token 端點。這個端點每次都會重新跑 requireAuth()，所以「驗身分」這件事情從來沒有被跳過，只是用重新發一張新 token 的形式發生。這也讓這個端點同時是「發 token」和「換 token」兩個角色，實作只需要一份。

一個刻意的例外：名字會過界到 Stream

在醫療類的 app 裡，通常有一條鐵律——病患資料不離開自己的系統。但托管的聊天服務需要能讓員工在收件匣裡看到「這是哪位病人」，所以病人的名字會刻意送到 Stream。這是一個有意識的取捨：Stream 在可簽署商業夥伴協議（BAA）的名單上，才讓這件事可以被接受；相較之下，Sentry、一般 log 或推播內容，就完全不允許出現病患資訊。

重點不是「永遠不准外送」，而是「每一種外送都要先確認對方是否有相應的合規承諾」。這個判斷會在整個後端反覆出現。

小結

Stream 是託管的聊天與視訊後端，我們在 server 端只負責決定身分與簽發短效 token。Stream user id 由登入 session 推導，絕不接受 client 傳來的值；API secret 只留在 server；Chat 與 Video 共用同一個身分與一張 token。短效 token 過期時，app 回頭打同一個端點換新，順便再驗一次身分。

身分規則講清楚了，但規則還停在紙上。下一步要把這條規則變成兩個真的端點：一個發 token，一個回傳這位病人該進的對話，並把 Stream 的伺服器端邏輯收進一個方便重用的 wrapper。
