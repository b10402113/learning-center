把法律頁接進 app：開啟方式與送審前檢查

Step 5/5 · App Store 合規與法律頁

先做一個關鍵決定：法律頁要放哪裡、怎麼開

前面幾節已經完成了幾個重要產出：法律頁有了 live 網址，app 裡也有能真的刪除帳號的流程。現在還差最後一哩路：讓使用者和審核人員都能找到這些內容。

設定頁上的「隱私政策」和「服務條款」如果只是按鈕，卻沒有接到任何頁面，就像商店掛了招牌，入口卻被牆封住。這一節要處理的，正是這條連線。

這裡有兩個選擇需要分開判斷：

  • 法律內容要打包進 app，還是留在 server 上？
  • 使用者點擊後，要用外部 Safari 開啟，還是用app 內的瀏覽器開啟？

答案會同時影響 App Store 審核，以及使用者讀完頁面後能不能順利回到 app。

選擇一：法律內容放在哪裡

先決定法律頁的「家」。常見做法有兩種：把 HTML 當成靜態資源，打包進 app 的 binary；或把內容放在 server 上，app 只保留一個網址。

做法優點缺點
打包進 app（bundled）離線可讀，不受網路影響內容會過時；改一次政策就要重新送審
放 server（live URL）改一次全部生效；符合公開存取要求離線時打不開

如果你的 app 要送上 App Store，這個選擇其實有一個明確底線：server-hosted 的 live URL 是必須的。因為 App Store Connect 要填的欄位本質上就是網址，而且該網址必須公開可存取。

因此，打包進 app 可以作為額外的離線版本，卻不能取代 live URL。法律內容可能會修改，例如新增收集的資料類型或更換第三方服務。放在 server 上，改一次就能對所有版本生效，不必為了一句條文重新送審。

用這個問題判斷：審核人員不登入，也找得到嗎？

法律頁的入口必須在不用登入的情況下就能開啟。這是一個很實際的判準：如果審核人員沒有帳號，是否仍然能從 app 找到隱私政策與服務條款？

有些 app 把隱私政策放在登入後的設定頁。這樣一來，沒有帳號的人根本點不到，頁面就算真的存在，也可能因為難以存取而被退回。

所以，法律頁的入口應該放在登入畫面，或放在未登入也能到達的地方。不要讓登入成為閱讀法律內容的門檻。

選擇二：法律頁要怎麼開啟

內容放在 server 上之後，還要決定 app 如何開啟這個網址。最直接的做法是交給系統，用外部 Safari 開啟；另一種做法是在 app 內顯示一個從底部升起的瀏覽器面板，也就是 sheet。

方式使用者體驗適用時機
外部瀏覽器（Safari）離開 app，回來要自己切回需要下載、登入或複雜互動的網頁
App 內 sheet 瀏覽器停在 app 內，讀完關掉就回來法律頁、說明頁這類純閱讀內容
自訂 WebView完全自行控制，但要多寫維護需要高度客製的網頁體驗

判斷方式可以很簡單：這個頁面是要讓使用者完成複雜任務，還是只需要「點開、讀一下、關掉」？

隱私政策和服務條款屬於後者，因此 app 內的 sheet 通常更順。使用者不必被丟到 Safari，讀完也不用另外找路回到 app。

在 Expo 裡，可以使用 expo-web-browser 的 openBrowserAsync，並指定 PAGE_SHEET，讓頁面從底部升起：

import * as WebBrowser from 'expo-web-browser';

await WebBrowser.openBrowserAsync('https://myapp-legal.pages.dev/privacy', {
  presentationStyle: WebBrowser.WebBrowserPresentationStyle.PAGE_SHEET,
  dismissButtonStyle: 'done',
  controlsColor: '#007AFF',
});

反例：哪些情況會讓規則翻轉

「法律頁放 server、用 app 內 sheet」是適合多數情況的選擇，但不是不必思考的死規則。

第一種反例是 app 的核心場景完全離線，例如登山或經常在飛航模式下使用。使用者可能真的會在沒有網路時想查看政策。這時可以把一份靜態版本打包進 app，作為離線備援。

不過，這份離線版本仍然不能取代 App Store Connect 所需的 live URL；兩者可以同時存在。

第二種反例是網址開啟失敗。沒有網路或網址暫時掛掉時，不要讓使用者卡在持續轉圈的畫面。用 try/catch 捕捉失敗，跳出提示，並顯示網址，讓使用者可以自行複製到瀏覽器：

try {
  await WebBrowser.openBrowserAsync(url, { presentationStyle: 'pageSheet' });
} catch {
  Alert.alert('無法開啟頁面', '請稍後再試，或手動開啟這個網址：\n' + url);
}

第三種反例是為了「統一體驗」，把法律頁塞進需要登入的流程。這會直接提高存取門檻，因此仍然應該重新檢查：使用者和審核人員在未登入時，是否能找到並開啟這些頁面？

送審前檢查表

送出審核前，把下面每一列都實際走過一次。只要有一項不能打勾，就先不要按 Submit。

項目檢查重點
隱私政策live URL、沒有 placeholder、免登入可開啟
服務條款live URL、可從 app 與 landing page 點到
Support URL可存取、有真的客服 email
刪帳號設定頁可達、有確認框、能真的刪三層資料
Sign in with Apple有 Google／其他社群登入時，選單裡也有它
App Store Connect 欄位Privacy／Support URL 填入正確網址
App Privacy 問卷申報的資料類型與隱私政策一致
連結開啟用 in-app sheet、失敗有 fallback

這張表也定義了「完成」的樣子：不是功能在本機會動就算結束，而是每一個合規入口都能被找到、被開啟，申報內容也彼此一致。

可以把最後的決策規則記成一句話：法律內容放 server、用 live URL；app 內優先用 in-app sheet 開啟；刪帳號與 Apple 登入依條件補齊，並在失敗時提供 fallback。

小結

法律頁的內容要放在 server 上、以公開的 live URL 提供，因為 App Store Connect 的欄位本身就需要公開存取，而且放 server 才能改一次全版本生效；打包進 app 只能當離線備援。開啟方式優先選 app 內的 sheet 瀏覽器（expo-web-browser 的 PAGE_SHEET），讓使用者讀完就回到 app，並用 try/catch 在失敗時顯示網址當 fallback。法律頁必須免登入可達。最後用送審前檢查表逐項核對：隱私政策與條款、support URL、能真的刪三層資料的刪帳號、條件觸發的 Apple 登入、App Store Connect 欄位與 App Privacy 問卷的一致性。
