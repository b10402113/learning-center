讓 agent 生成隱私政策、服務條款與 landing page

Step 2/5 · App Store 合規與法律頁

這一節要完成什麼

這一節的目標，是讓 agent 讀完整個 codebase，根據 app 真實的行為，一次產生三個可以部署的法律相關頁面：

  • landing page
  • privacy 隱私政策
  • terms 服務條款

三個頁面會放在 legal/ 資料夾，並共用一份 styles.css。完成後，你還要能找出哪些欄位 AI 無法猜測，必須由你親自補上。

開始前需要具備兩個條件：第一，你的 codebase 已經能讓 agent 看懂 app 在做什麼；第二，你知道自己或公司的正式名稱。這樣生成出來的內容才有實際依據，而不是一份到處都能套用的模板。

為什麼適合先做這三頁

上一節我們把合規清單攤開，其中有三頁本質上很像：它們都是不需要後端邏輯的靜態網頁。landing page、隱私政策與服務條款，只要準備 HTML 和共用樣式，就能放到網路上。

這讓它們成為很適合交給 AI agent 的工作。不過，法律頁最重要的不是「看起來像一份正式文件」，而是內容要符合你的 app 真實做法。

隱私政策必須描述你真的收集與處理哪些資料。如果直接使用網路上的通用模板，裡面可能寫著「我們可能收集位置、聯絡人、健康資料」，但你的 app 根本沒有碰這些資料。這種內容既不準確，也可能在審核時被質疑。

因此，正確的做法不是叫 agent 背模板，而是讓它先讀你的程式碼，再從實際流程推導出資料類型。

第一步：要求 agent 讀 codebase 後再生成

不要只下「幫我寫一份隱私政策」這種指令。這通常只會得到一份誰都能使用的通用模板。

你要明確要求 agent 掃過整個 repo，根據 app 的實際行為產生內容。可以使用下面這個 prompt：

閱讀我整個 codebase，判斷這個 app 會收集與處理哪些使用者資料
（例如帳號 email、上傳的照片、裝置資訊等）。

在 legal/ 資料夾建立一個靜態網站：
- index.html：landing page，風格要沿用 app 現有的主色與字體
- privacy.html：隱私政策
- terms.html：服務條款
- styles.css：三個頁面共用

landing page 要有導覽列與頁尾，兩者都要連到 privacy 與 terms。
所有我必須自己提供、你無法得知的資訊，用 [大寫方括號] 標成 placeholder。

這段 prompt 有三個關鍵要求。

  1. 要求讀 codebase。政策內容必須建立在 app 真實收集與處理資料的行為上。
  2. 指定檔案結構。三個頁面共用同一份 styles.css，避免每個頁面各自長出一套樣式。
  3. 事先規定 placeholder 格式。所有 agent 不知道、需要你補上的資訊，都用大寫方括號標示，之後可以快速搜尋。

例如，agent 讀到你的掃描流程會把照片送到 OpenAI 分析，就可能在隱私政策中提到「照片會傳送給第三方 AI 服務處理」。如果它讀到你使用 Clerk 登入，也可能提到帳號識別資訊由身分供應商處理。

這些細節不一定能靠人工憑記憶全部列出來，讓 agent 掃 codebase，就像請它沿著 app 的資料流走一遍，能比較完整地找出實際情況。

第二步：先驗收輸出格式，再檢查文字

生成完成後，第一件事不是逐字閱讀政策，而是先確認產出的格式正確。

最常見的失敗，是 agent 交給你 Markdown，而不是可以部署的 HTML 網頁。例如，privacy.html 裡可能只放了一大段 Markdown 文字，或 landing page 仍然混著 Markdown 語法。

如果遇到這種情況，不需要整個流程重來。直接要求它修正：

「請改成可以互相連結的 HTML 網頁，三個頁面共用 styles.css。」

格式修正後，再逐項檢查下面這些內容：

檢查點合格的樣子
檔案結構legal/ 下有 index、privacy、terms 與 styles.css
主題一致頁面沿用 app 的主色與字體，不像另一個網站
導覽與頁尾兩處都有連到 privacy 與 terms 的連結
文字對比頁尾連結顏色清楚可見，沒有深底配深色文字
placeholder所有需要人工填寫的欄位都用方括號標出

第三步：補上 AI 一定不知道的欄位

這是整個流程中不能外包的部分。AI 不知道你的法定名稱、註冊地址，也不知道你的客服信箱，因此它只能留下 placeholder。

部署前，請搜尋所有大寫方括號，逐一確認並替換。常見欄位包括：

  • 法定實體名稱，也就是公司或個人的正式名稱
  • 註冊地址或營業登記地址
  • 客服 email 與 support URL
  • 隱私政策的生效日期
  • 管轄法律與爭議處理條款所屬的國家／地區

這些欄位都有一個共同點：它們涉及「管轄權」或你的正式身分。agent 可以寫出條款的一般結構，卻無法知道你受哪一國法律管轄、地址在哪裡，或你的正式名稱究竟是什麼。

所以分工很清楚：AI 生成文件骨架與一般內容，人類補上只有自己知道的管轄細節。

第四步：用截圖迭代版面

第一次生成的版面通常不會一次到位。可能是間距太擠、hero 圖太大，或某段文字在手機上換行得很難看。

這類問題不用靠文字描述硬猜。你可以在模擬器或瀏覽器中截圖，再附上一句具體說明，例如：

「這個區塊在手機上會擠成一團，請縮小 hero 圖並加大行距。」

有了畫面和明確問題，agent 通常就能直接針對版面修改。

另外，換圖片後卻一直看到舊圖，也是常見的陷阱。這不一定代表 agent 沒有修改，可能只是瀏覽器或建置流程還在使用快取。

遇到這種情況，請明確要求：

「請清掉快取，並確認頁面引用的是新檔名。」

這能提醒 agent 同時檢查快取、檔名與實際引用路徑。

弱做法與強做法

弱做法是只對 agent 說：「幫我寫一份隱私政策。」結果通常會得到一份通用模板，裡面列出與你的 app 無關的資料類型。另一種弱做法，是讓三個頁面各自寫死樣式，之後每次換主題都要改三遍。

強做法則是把 codebase 當成內容依據，指定共同的檔案結構，並先規定未知資訊要用方括號標出。生成後，先確認拿到的是可部署的 HTML，再檢查主題、導覽、頁尾、文字對比與 placeholder。

這樣的分工比較可靠：AI 負責大部分文字與版面，你負責那 20% 只有自己知道、也不能猜錯的事實。

完成後，你應該看到什麼

完成這幾步後，本機的 legal/ 資料夾應該包含：

  • index.html：沿用 app 視覺風格的 landing page
  • privacy.html：根據 codebase 實際資料流程撰寫的隱私政策
  • terms.html：服務條款
  • styles.css：三個頁面共用的樣式

三個頁面應該是可以互相連結的 HTML，而不是 Markdown。所有法定名稱、地址、客服信箱、生效日期與管轄條款等資訊，也應該已經由你確認並替換完成。

讓 agent 掃過整個 codebase 再生成，隱私政策才會反映你實際收集的資料。一次 prompt 生出 landing page、privacy、terms 與共用 styles.css，並要求它把不知道的資訊標成方括號。生成後先驗收「是不是 HTML 網頁」——最常見的失敗是拿到 markdown——再檢查主題、導覽、頁尾與對比。最後由你補上法定名稱、註冊地址、客服 email、生效日與管轄條款這些帶有管轄權的欄位。版面不理想就用截圖迭代，換圖沒更新就提醒清快取。

現在三個頁面已經在本機的 legal/ 資料夾裡，但合規要求的是一個可以公開存取的網址。下一節會把這個資料夾部署到網路上，並將三個網址填入 App Store Connect 要求的欄位。
