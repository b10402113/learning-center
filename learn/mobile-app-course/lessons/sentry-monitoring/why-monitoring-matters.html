為什麼上線後一定要有錯誤監控

Step 1/6 · Sentry 錯誤監控

學習目標

完成這一節後，你應該能說明為什麼 app 上線後一定需要錯誤監控，了解 Sentry 這類服務的五個核心能力，也能分辨為什麼單靠 console.log 撐不起 production 的觀測需求。

先想像一個情境：你的 app 壞了，但你完全不知道

想像一下，你終於把 app 做到可以給朋友試用。畫面漂亮、流程順暢，你自己在模擬器上怎麼點都正常。把 build 傳給朋友後，過了兩天你問他：「用起來怎樣？」他只回一個字：「卡。」

你再追問是哪裡卡、什麼情況下卡、有沒有錯誤訊息，他也說不清楚。你想查，卻沒有線索可查。

更常見的是，朋友根本不會告訴你。他打開 app，發現登入畫面一直轉圈圈，或是掃描餐點時不斷失敗。試了兩次之後，他直接把 app 刪掉，再順手留下一顆星。整個過程你完全不知情，因為那支發生問題的手機不在你桌上，錯誤也沒有出現在你的終端機裡。

這一節要處理的就是這個問題：app 離開你的電腦後，你靠什麼知道它有沒有壞、壞在誰身上，以及為什麼會壞？答案不是「請使用者回報」，而是替 app 裝上一座瞭望塔。

先把「為什麼需要監控」想清楚，後面幾節在安裝與判讀 Sentry 時，才不會只是照著設定畫面一路點過去。

「本機能跑」和「上線能活」是兩件事

你的電腦是一個被精心控制的環境：作業系統版本固定、網路穩定，使用的資料也大多是你熟悉的格式。真實世界卻像一個沒有圍牆的測試場。

使用者拿的是各種型號的手機，OS 版本新舊不一；有人在捷運上使用，網路斷斷續續；有人上傳格式奇怪的圖片；也有人把系統語言切換成你從沒測過的組合。每一種差異，都可能變成一條通往錯誤的路。

所以，「我測過了，沒問題」真正代表的只是：「在我這台裝置、這條網路，以及這批資料上沒有問題。」app 一上線，edge case 一定會出現。這不一定表示你的程式寫得不好，而是真實世界本來就比測試環境複雜。

重點不是能不能把所有錯誤完全消滅，而是錯誤發生時，你有沒有辦法立刻知道。

使用者的沉默：錯誤報告不會自己送上門

很多人直覺會想：「app 壞了，使用者應該會回報吧？」實際上通常剛好相反。大多數使用者遇到錯誤時，不會寫信給你描述重現步驟，而是直接放棄：刪掉 app，留下一句「根本不能用」的一星評論。

最後你只看見下載數和評分下降，卻拿不到任何能用來修復問題的線索。

你真正需要的，是一則像這樣的通知：

剛剛有一台 iPhone 在某個版本上，執行餐點分析時發生錯誤。錯誤出現在第 42 行，當下使用者看到的畫面是這樣。

有了裝置、版本、堆疊資訊，以及錯誤發生前後的操作，你才有辦法開始修問題。錯誤監控工具的作用，就是把「使用者默默離開」變成「你收到一份可以動手處理的報告」。

Sentry 是什麼：app 的瞭望塔

Sentry 是一套錯誤追蹤與監控平台（error tracking and monitoring）。你可以把它想成架在 app 頂端的一座瞭望塔：它持續觀察 app 有沒有出狀況，一發生問題就記錄下來，並通知你。

通知預設會寄到 email，也可以接到 Slack、Discord 或 Microsoft Teams。這樣一來，事情發生時你就能看到，而不是等到使用者抱怨了才知道。

而且，Sentry 不只是「app 當掉時通知你」。完整來看，它提供五個互相搭配的能力：

能力它回答的問題
即時錯誤擷取現在壞了嗎？壞在哪一行？有多少人遇到？
結構化 logs錯誤發生前後，app 內部發生了哪些事？
Session replay使用者出錯時，螢幕上實際看到什麼、又做了哪些操作？
Performance traces哪一段操作變慢了？是在哪個服務呼叫上變慢？
即時警報出事時誰會被通知？多久之內能收到通知？

這五項不是五個互不相干的工具，而是同一條觀測鏈上的不同切面：

  • 錯誤擷取告訴你「壞了」。
  • logs 告訴你「壞掉前做了什麼」。
  • replay 讓你看見「使用者當下看到什麼」。
  • trace 告訴你「是不是某個環節變慢或逾時」。
  • 警報則確保「有人會及時知道」。

後面每一節都會把其中一項拆開來講。Sentry 也不是冷門工具，Cursor、GitHub、Vercel、Convex、Supabase 這些你日常會使用的服務都在使用它。

為什麼不能只靠 console.log

你可能會想：「我加一堆 console.log 不就好了？」在開發階段，這確實能幫你快速確認程式走到哪裡。但到了 production，console.log 有三個致命限制。

第一，它只存在使用者的裝置上。你在自己電腦的終端機裡看得到的 log，在別人的手機上你根本看不到。

第二，它是暫時的。app 一關掉，log 就消失了，沒有留下任何可以回頭查的紀錄。

第三，它只是純文字，和「哪一個錯誤」或「哪一條 trace」之間沒有自動連結。你只能靠肉眼比對時間，像是在一大疊沒有索引的紙張裡找某一行字。

Sentry 的結構化 logs 正好補上這三個缺口：它會把 log 傳到雲端保存，可以依照 tag 搜尋，還能自動關聯到對應的錯誤、trace 與 replay。

使用者只有十個時，你或許還能靠直覺和記憶追問題；但當使用者變成五百、五千，甚至五萬個時，能夠查詢和關聯的 log，才是你真正可靠的眼睛。

規模小的時候，才是最該先接好的時候

一個很容易掉進去的陷阱是：「現在又沒幾個使用者，等 app 紅了再接監控吧。」但監控真正有價值的時刻，往往正是你最忙、也最不能出錯的時候。

想像一個每天有五百筆結帳的電商 app，某天付款流程開始出錯。沒有結構化 log，你只知道「有人抱怨付不了款」。有了結構化 log，你就可以直接查詢：

  • level 是 error
  • 訊息包含 payment
  • 時間限定在最近 24 小時
  • 只查看某個城市的裝置

幾秒鐘內，你就能圈出受影響的範圍。這種查法，是單靠終端機裡的列印結果永遠做不到的。

而且，接上監控本身並不難。提早接好，就像先買好一份保險：真的出事時，你不用一邊承受使用者流失，一邊臨時研究監控工具要怎麼安裝。

小結：把監控掛回整個 app 的脈絡

本機能跑，不等於上線能活。真實世界的裝置、網路與資料充滿 edge case，而使用者遇到錯誤時，通常不會回報，反而可能直接刪掉 app、留下一星。因此，你需要監控工具主動告訴你發生了什麼。

Sentry 就像 app 的瞭望塔，提供即時錯誤擷取、結構化 logs、session replay、performance traces 與即時警報五個能力。console.log 只存在裝置上，app 關掉後就消失，也無法有效查詢和關聯，因此撐不起 production 的觀測需求。監控最好在使用者規模還小的時候就先接好。

知道「為什麼要監控」之後，下一步就是把它接進 app：建立 Sentry 專案、取得連線用的 DSN、設定給 source map 使用的 token，並記得 Sentry 是 native module，安裝完成後必須重新 build 一次。下一節會帶你一步一步走完安裝流程。
