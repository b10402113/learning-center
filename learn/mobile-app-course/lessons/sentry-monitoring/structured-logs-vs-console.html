Sentry logs 與 console.log：什麼時候該用哪一個？

Step 4/6 · Sentry 錯誤監控

先決定：這行 log 上線後還要不要找得到？

上一節你已經能抓到錯誤，但錯誤本身往往不足以還原現場。使用者回報「餐點分析一直轉圈圈」，你在 Sentry 只看到一則逾時錯誤，訊息只有「request timed out」。到底是圖片太大、AI 回傳格式不對，還是網路中斷？答案通常藏在錯誤前後的幾行 log 裡。

這時你會遇到一個很實際的選擇：要用熟悉的 console.log 隨手印出來，還是用 Sentry 提供的結構化 logger 送出去？兩者在開發時看起來很像，但 app 上線後，它們的命運完全不同。這一節要幫你建立一條清楚的判準，不再只是憑習慣打 log。

學習目標

學完後，你應該能判斷什麼情況適合使用 console.log，什麼情況該使用 Sentry 的結構化 logs，也能說明 log level、tag，以及把 logs 連回 errors、traces、replays 在實務上解決了什麼問題。

兩個選項，先放在同一張桌上比較

先不要急著選。把兩種 log 並排比較，差異就會很清楚：

比較項目console.logSentry 結構化 log
存在哪裡只在使用者裝置上送到 Sentry 雲端保存
app 關閉後消失，沒有任何痕跡仍留在後台，之後查得到
能不能搜尋不行，只能肉眼查看可以依 level、tag、訊息搜尋
結構化純文字可以帶 key-value 欄位與標籤
跟錯誤的關聯沒有，只能比對時間會自動連到 error、trace、replay
成本免費會佔用 Sentry 額度

最關鍵的是「跟錯誤的關聯」。Sentry 的 log 不是散落在角落的一份文字紀錄，而是會被綁進當下的 session 與 trace。當你點開一則錯誤，就能在旁邊看到那一刻 app 印出了哪些 log。錯誤和 log 排在同一條時間軸上，就像把案發現場的監視器畫面和報案紀錄放在一起；這是單靠 console.log 做不到的。

判別問句：這行 log 是給誰看的？

與其背一大串規則，不如每次都問自己三個問題：

  1. 這行 log 只有在開發時我會看嗎？如果它只是幫你確認某個函式有被呼叫，或查看某個變數的值，使用 console.log 就夠了，不必浪費 Sentry 額度。
  2. 上線後使用者出問題時，我會需要回頭查這行 log 嗎？如果答案是會，例如分析失敗、付款失敗或權限被拒，就該使用 Sentry logger，因為你才有機會在事後找到它。
  3. 這行 log 會不會帶到敏感資料？不論使用哪一種方式，姓名、email、病歷和付款資訊都不該放進 log。差別在於，console.log 留在使用者手機上，而 Sentry log 會上傳到雲端，因此外洩風險更高。

三個問題合起來，判準就很明確：

開發時用來除錯的訊息交給 console.log；上線後需要回頭查的事件交給 Sentry logger；任何敏感內容，兩者都不要送。

用 log level 表達事件的輕重

決定要送到 Sentry 後，還要決定它有多嚴重。Sentry logger 支援六個等級，從最不嚴重到最嚴重依序是 trace、debug、info、warning、error、fatal。這些等級不只是分類，也會影響你在 Dashboard 上篩選結果。

等級什麼時候用例子
trace / debug開發與細節追蹤快取命中、圖片壓縮後的大小
info正常但值得記錄的事件餐點已記錄、計畫已產生
warning還能繼續執行，但已偏離預期AI 回傳不合理，改用公式退路
error某個操作失敗餐點上傳回 502
fatal核心功能整片失效資料庫連不上，所有寫入都失敗

實際寫法可以是：

Sentry.logger.error('Meal upload failed', { reason: 'HTTP 502 from /api/meals', image_bytes: 2184302 })

第二個參數是結構化欄位，會變成可搜尋的 tag。使用前也要確認 Sentry.init 已經開啟 enableLogs: true，否則 logs 不會真的送出去。

Tag 是讓你查得到的關鍵

log 的訊息主要是給人讀的，tag 則是給系統查詢的。你可以在 log 上標記 feature: 'meal-analysis'、model: 'gpt-4o-mini'、meal_id: 'meal_8f2a41'。

當使用者只有十個時，直接閱讀訊息也許還應付得來。但當使用者變成五萬個、每天有五百筆結帳，你不可能一則一則翻。這時可以在 Dashboard 設定條件，例如找出「level 是 error、訊息包含 payment、發生在最近 24 小時，而且限定某個城市」的紀錄，幾秒內就能圈出受影響的範圍。能做到這件事，靠的就是可查詢的 tag。

反例：上線後也不是每一行都該送到 Sentry

「上線後要查，就用 Sentry log」是一條好規則，但不能毫無節制地套用。以下情況，規則反而需要踩煞車。

第一，高頻迴圈。如果動畫每一幀，或每秒觸發數十次的事件都送一則 Sentry log，額度可能很快被用光，app 效能也會受到拖累。這種地方要嘛不下 log，要嘛降到 trace 或 debug 等級，並且注意取樣。

第二，包含敏感資料。Sentry log 會送到雲端，因此病歷、個資和付款資訊絕對不能直接放進去。需要時應該先去識別化，或只記錄 id 與數量。

第三，只是開發時想看一眼的臨時訊息。這類訊息留在 console.log 就好。不要因為「反正有額度」就把所有暫時性的除錯內容都上傳。

可以直接套用的決策規則

這行 log 如果只是開發時給自己看的，就用 console.log；如果是上線後出事時需要回頭查的，就用 Sentry 結構化 logger。Sentry log 會存在雲端，可以依 level 和 tag 搜尋，也會自動連到 error、trace、replay，這是它勝過 console 的地方。用 trace 到 fatal 六個等級表達輕重，用 key-value 欄位協助查詢，並記得開啟 enableLogs。但高頻迴圈、含敏感資料，或只是臨時除錯的訊息，不該無腦送上雲端。

你現在已經能抓到錯誤，也能查到錯誤前後的 log。接下來還有一個問題：使用者抱怨「變慢了」時，你要怎麼知道慢在哪一段？這需要第三種觀測方式——tracing。下一節會把一次操作拆成好幾段，讓你一眼看出是哪個環節拖慢了整體流程。
