把使用者回饋接進 Sentry

Step 6/6 · Sentry 錯誤監控

完成後，你會得到什麼？

完成這一節後，使用者可以直接在 app 裡送出姓名、email 與問題描述。你則能在 Sentry Dashboard 的 User Feedback 找到這些回饋，並查看它們是否和錯誤事件連在一起。

開始前，請先確認 app 已經完成前面的錯誤監控與 logs 設定。使用者回饋是加在觀測系統上的一扇窗，不是地基；先確定錯誤抓得到，再接上這層資訊。

為什麼要接使用者回饋？

想像使用者遇到問題：他可能想說「我希望可以一次上傳多張照片」，也可能覺得「這個付費方案我搞不懂」，或只是單純抱怨「畫面好卡」。這些話不會自動變成 exception，也不會出現在 log 裡。

如果 app 沒有提供出口，這些聲音就會和使用者一起消失。錯誤監控能告訴你「程式在客觀上壞了」，但只有使用者回饋能告訴你「他怎麼感受、他真正想要什麼」。兩者像一張地圖的座標和註記：一個指出問題發生在哪裡，另一個補上使用者為什麼在意。

Sentry 可以把這兩種資訊掛在一起。使用者送出回饋後，你可以查看它是否連到某一則錯誤事件，進一步判斷這是個人偏好，還是確實踩到了 bug。

步驟一：初始化 feedback widget

Sentry 提供兩種使用方式。第一種是在初始化時加入 feedback 整合，之後再透過 Sentry API 顯示表單。先在 Sentry.init 裡完成設定：

Sentry.init({
  dsn: process.env.EXPO_PUBLIC_SENTRY_DSN,
  integrations: [
    Sentry.feedbackIntegration({
      colorScheme: 'light',
      formTitle: 'Share your feedback',
      messageLabel: 'What’s on your mind?',
      messagePlaceholder: 'Tell us what you love, what could be better, or what went wrong…',
      nameLabel: 'Name (optional)',
      emailLabel: 'Email (optional)',
      submitButtonLabel: 'Send feedback',
      isNameRequired: false,
      isEmailRequired: false,
      successMessageText: 'Thanks for helping us improve!',
    }),
  ],
});

這段程式做了三件事：

  1. 使用 Sentry.feedbackIntegration 把 feedback 功能接進 Sentry。
  2. 設定表單的標題、提示文字、欄位名稱、送出按鈕與成功訊息，讓表單語氣和 app 保持一致。
  3. 透過 isNameRequired: false 與 isEmailRequired: false，把姓名和 email 設為選填。

姓名和 email 通常不必一開始就設成必填。欄位越多，願意送出的人可能越少；先讓使用者方便留下問題，需要追問時，再透過 email 聯絡。

步驟二：在使用者找得到的地方放入口

完成初始化後，還要讓使用者知道從哪裡送出回饋。常見做法是在設定頁或個人頁放一列「Send feedback」，按下後顯示表單：

// 放在 profile / settings 的某一列
<Row
  label="Send feedback"
  onPress={() => Sentry.showFeedbackWidget()}
/>

這裡的關鍵是 Sentry.showFeedbackWidget()。它會叫出前一步設定好的 feedback 表單。

若這顆按鈕放在設定頁或個人頁，使用者遇到問題時通常比較找得到。反過來，若把它藏在測試頁或幾乎沒人會進去的角落，實際效果就像沒有提供回饋功能。

若 X 是使用者正在查看的設定頁或個人頁，就把回饋入口放在 X；若 X 是使用者剛遇到錯誤的畫面，也可以在當下提示他送出回饋，讓錯誤事件與使用者的描述更容易連在一起。

步驟三：到 Dashboard 確認回饋

使用者送出表單後，前往 Sentry 的 Issues → User Feedback。在這裡可以查看：

  • 是哪位使用者送出的回饋。
  • 使用者寫了什麼內容。
  • 這則回饋是否連到某一則錯誤事件。

測試時送出的假回饋，Sentry 會自動判定為 spam（垃圾訊息），因此不會和真實使用者的聲音混在一起。真實回饋則會進到 inbox，等待你處理。

把回饋接回整個觀測流程

當你把「錯誤 → 看 replay → 讀 log → 查 trace → 收使用者回饋」串起來，就形成了一個完整的閉環。

你不只知道系統哪裡出錯，也能理解使用者當時怎麼感受，接著判斷應該修 bug，還是新增某個功能。這正是使用者回饋和錯誤報告互補的地方。

警告：收到回饋後要真的處理

回饋功能最常見的失敗，不是技術接錯，而是「收了卻沒人看」。既然接上了，就把 Sentry 通知接到你每天真的會看的地方，例如 email 或 Slack，並定期查看 inbox。

使用者的抱怨如果能被快速回應，往往比單純修好一個 bug 更有機會留住使用者。不要把按鈕藏起來，也不要讓送進來的回饋在 Dashboard 裡悄悄堆積。

完成檢查

  1. 在 Sentry.init 裡加入 feedbackIntegration。
  2. 確認表單文字符合 app 的語氣。
  3. 確認姓名與 email 是否要設為選填。
  4. 在設定頁或個人頁放置按鈕，並呼叫 Sentry.showFeedbackWidget()。
  5. 實際送出一則測試回饋。
  6. 到 Issues → User Feedback 確認回饋是否出現，並檢查測試回饋是否被歸類為 spam。

小結

錯誤報告與使用者回饋是互補的：前者說「程式壞了」，後者說「使用者怎麼想」。在 Sentry.init 裡掛上 feedbackIntegration，自訂表單文字，姓名與 email 盡量設為選填；再於設定頁或個人頁放一顆按鈕呼叫 Sentry.showFeedbackWidget()。回饋會出現在 Issues → User Feedback，並可連結到對應的錯誤事件，測試回饋會被自動歸類為 spam。別把按鈕藏在測試頁，也別忘了定期處理收到的回饋——接了不看，等於沒接。

完成這六節後，你的 app 就從「本機能跑」走到「上線後看得見」：錯誤會自己找上你，log 可以查，效能有跡可循，使用者的聲音也有出口。把這套觀測能力帶回自己的 app，讓它成為每次開發時都會自然接上的基本配備。
