為什麼不能相信 client 傳來的 identity

Step 1/5 · Convex × Clerk 身分驗證

學習目標

完成這一節後，你應該能說出為什麼把 client 傳來的 userId 當成身分會出錯，並解釋 server 端如何從一個驗證過的 token，推導出可信的呼叫者。

前言：這則貼文真的是本人發的嗎？

假設你的 app 已經能貼文了。你在 Convex 寫了一個 mutation，簽名大概長這樣：createPost({ userId, caption })。client 那邊也很順，反正使用者登入之後，Clerk 已經知道他是誰，把 userId 一起傳進來就好。功能測起來完全正常，貼文會出現在牆上。

問題是，這段程式碼在「功能正常」的表象下，藏了一個很常見、但後果很嚴重的漏洞。任何一個登入的使用者，只要稍微改一下請求內容，就能用你的名字貼文、讀你的私訊、甚至刪掉你的資料。這一節要處理的，就是這個漏洞從哪裡來，以及正確的修法為什麼一定跟 token 有關。

最直覺但錯的做法：讓 client 決定自己是誰

把 userId 放在 mutation 的參數裡，本質上是讓「呼叫方」自己聲明「我是誰」。你會這樣寫，通常是因為客戶端真的知道答案：Clerk 的 SDK 在使用者登入後會拿到使用者資料，順手把它塞進請求裡看起來很自然。

但 server 收到這個 userId 時，它其實只是一段普通的資料，跟 caption 這種文字欄位沒有兩樣。server 沒有任何辦法分辨「這是本人填的」還是「這是攻擊者手動填的」。換句話說，你等於把門禁卡交給訪客，讓他自己寫上要進哪一戶。

為什麼 client 不能信

關鍵在於：client 是使用者完全掌控的環境。你的 app 安裝在他的手機上，他能看到你送出的每一個請求，也能用工具改寫它們，再原封不動地送到你的 server。對 server 來說，一份經過改寫的請求，跟一份正常的請求長得一模一樣。

所以只要身分是以參數的形式傳進來，攻擊者要冒充誰都行。他不需要破解你的密碼，也不用拿到你的 session，只要把 userId 換成別人的識別碼就好。這類「使用者可以自由指定自己身分」的破損存取控制，是後端最常見的安全問題之一，而且多半在功能驗收時完全看不出來。

正確的做法：由 server 從驗證過的 token 推導身分

修法的方向只有一句話：身分不能是輸入，必須是推導出來的結果。要推導，就需要一個 client 無法偽造的憑證。這個憑證就是 Clerk 簽發的 JWT（JSON Web Token，一種帶簽章的數位通行證）。

你可以把整個流程想成出入境：Clerk 是發照機關，負責確認申請人的身分，並且簽發一本別人偽造不了的護照。Convex 則是查驗護照的移民官，它會檢查這本護照的簽章是不是真的、是不是由它認可的機關發出，確認無誤之後，才在系統裡登記「這個人就是護照上的那個人」。client 的角色只是把護照帶在身上、在每次請求時出示，它不能自己決定護照上要寫誰。

實作上，使用者登入後，Clerk 的 SDK 會把 JWT 放在每個 Convex 請求裡送出。Convex 在執行你的函式之前先驗證這個 token；驗證通過，你的函式就能透過 ctx.auth.getUserIdentity() 取得呼叫者的身分。也就是說，在你程式碼裡唯一能信任的身分來源，是 ctx.auth，而不是函式的參數。

小結

身分不能當成參數傳，因為 client 是使用者能完全掌控的環境，任何傳進來的 userId 都可能是偽造的。正確做法是讓 client 出示 Clerk 簽發的 JWT，由 Convex 在 server 端驗證並推導出呼叫者，程式碼只信任 ctx.auth，不信任參數。

不過，ctx.auth 不會自己長出東西。要讓 Convex 認得 Clerk 的 token、讓 getUserIdentity() 不再回傳 null，你得先完成一件接線工作。下一步就來看怎麼開通 Clerk↔Convex 整合，並寫下那份關鍵的 auth.config.ts。
