JWT 驗證與 identity 物件：Convex 怎麼知道是你

Step 3/5 · Convex × Clerk 身分驗證

學習目標

完成這一節後，你應該能解釋 Convex 如何用 issuer 與公開金鑰驗證 Clerk 簽發的 JWT，說出驗證後拿到的 identity 物件裡有哪些欄位，並分辨 subject 與 tokenIdentifier 的差別與用途。

前言：一張字串憑什麼代表一個人？

上一節的 auth.config.ts 只做了一件事：告訴 Convex「這個 issuer 簽的 token 我認」。但這裡有個值得追問的細節——token 不過是一串文字，任何人複製之後都能重送，Convex 憑什麼相信它上面寫的身分是真的？

如果你不知道背後的機制，很容易做出錯誤的推論，例如以為「token 不能外流就等於安全」，或是把 token 當成可以直接信任的使用者資料。這一節要把這串文字拆開，看清楚它到底裝了什麼、驗證是怎麼發生的，以及驗證完成之後，你手上那個 identity 物件是什麼形狀。

JWT 的三個部分

JWT（JSON Web Token，一種帶簽章的數位通行證）字面上會看到用兩個點分隔的三段字串，長得像 xxxxx.yyyyy.zzzzz。這三段各有工作：

  • header：描述這個 token 用什麼演算法簽的，例如 RS256。
  • payload：一組稱為 claims 的欄位，裡面有 iss（issuer，誰發的）、sub（subject，發給誰）、aud（audience，簽給哪個用途）、exp（到期時間）等。
  • signature：Clerk 用只有自己握有的私鑰，對前兩段算出的簽章。

要注意的是，header 和 payload 只是 base64url 編碼，不是加密。任何人把 token 貼進解碼工具都讀得到內容，所以別把機密資料塞進 claims。真正提供保護的是第三段簽章：內容一旦被改過，簽章就會對不上。

驗證是怎麼發生的

關鍵在於簽章用的是非對稱金鑰。Clerk 用私鑰簽發，並公開一組對應的公鑰。任何人都能拿到公鑰去驗證「這是不是 Clerk 簽的」，但沒有私鑰的人做不出有效的簽章。Convex 就是這樣驗的：它會到 auth.config.ts 指定的 issuer 位址取得公開金鑰（一般走 OIDC 的 JWKS 端點），並且把公鑰快取起來，避免每個請求都去抓一次。

驗證時，Convex 至少會確認三件事：簽章是不是真的、iss 是不是自己認可的那個 issuer、aud 是不是對應你設的 applicationID。三關都過，它才把 payload 裡的身分資訊整理成 identity 物件交給你。這也是為什麼 auth.config.ts 裡的 domain 和 applicationID 缺一不可：domain 決定去哪抓公鑰、核對 issuer，applicationID 決定要接受哪一種用途的 token。

因為驗證靠的是數學與快取的公鑰，不是每次回頭問 Clerk，所以它很快。而 Clerk 的 SDK 會在使用者登入期間自動更新短效期的 token，你的 server 端只要負責驗，不需要自己管理更新。

驗證通過後：identity 物件

驗證成功之後，ctx.auth.getUserIdentity() 回傳的是一個 identity 物件。裡面最常被用到的兩個欄位是 subject 和 tokenIdentifier：

欄位內容特性
subjectClerk 內的使用者識別碼，例如 user_2abc...簡短，但單獨看不知道是誰發的
tokenIdentifierissuer 加上 subject 組成的完整識別字串帶了發照者，跨來源也不會撞號

除了這兩個，identity 通常還會帶著 issuer，以及你在 Clerk 範本裡加入的自訂 claims，例如姓名或大頭貼網址。原則是：只拿你真的需要的欄位，身分以外的資料（像個人簡介、追蹤關係）屬於你自己的 app 資料，不該期待它出現在 token 裡。

為什麼偏好 tokenIdentifier

既然 subject 又短又好讀，為什麼要用比較長的 tokenIdentifier？原因是 uniqueness（唯一性）。subject 只在某一個 issuer 的範圍內保證不重複；如果你之後又接了第二個身分來源，兩個系統各有自己的 user_1 是完全可能的，光看 subject 就分不出誰是誰。tokenIdentifier 把 issuer 一起帶上，等於寫清楚「哪個機關發的、號碼是多少」。

這就像在一個小村子裡喊「小明」大家都知道是誰，但跨國時就得加上國家與證件號碼。專案裡的 profiles 資料表就是用 tokenIdentifier 當索引鍵，正是為了讓身分在加入更多登入方式之後仍然穩定。把這個習慣記住，你之後就不容易踩到「換了 provider 之後使用者認錯人」的坑。

小結

JWT 是由 header、payload、signature 三段組成的簽章憑證，payload 只編碼不加密。Convex 用 auth.config.ts 指定的 issuer 取得公鑰，驗證簽章、issuer 與 audience 之後，把 claims 整理成 identity 物件。物件裡的 subject 是 Clerk 的使用者識別碼，tokenIdentifier 則帶有 issuer 前綴、跨來源唯一，因此適合當資料表的身分索引鍵。

到這裡，你已經能從 token 穩定地拿到「這個呼叫者是誰」。但那是 Clerk 視角的身分，你的 app 還有自己的 profile——而且不是每個登入者都已經有 profile。下一步要做的，就是在兩種 guard 之間做選擇：什麼時候只需要 identity，什麼時候非得有 profile 不可。
