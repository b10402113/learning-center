requireIdentity 還是 requireProfile？

Step 4/5 · Convex × Clerk 身分驗證

學習目標

完成這一節後，你能依「這個操作需不需要 app profile」來判斷該用 requireIdentity 還是 requireProfile，並說出 requireProfile 會擋下哪三種情況。

前言：登入了，然後呢？

上一節你已經能穩定地從 token 拿到 identity，知道呼叫者是 Clerk 的哪個使用者。但接下來的問題是：你的 app 並不認識每一個人。使用者第一次登入時，profile 根本還不存在——你得先請他取一個 username。另外，資料庫裡可能還有幾筆示範用的假帳號，以及一個正在進行刪除流程、暫時不該被當成正常使用者的帳號。

所以「有登入」跟「能用這個 app 的功能」是兩件不同的事。專案把這兩件事包成兩個 helper：requireIdentity 只確認有人登入，requireProfile 進一步確認這個人有可用的 profile。這一節要決定的，就是每個操作該用哪一個。

兩個 helper 在做什麼

先看它們的實作，差異會很清楚：

export async function requireIdentity(ctx: Pick<QueryCtx, 'auth'>) {
  const identity = await ctx.auth.getUserIdentity();
  if (!identity) throw new ConvexError('Please sign in to continue.');
  return identity;
}

export async function requireProfile(ctx: QueryCtx | MutationCtx) {
  const identity = await requireIdentity(ctx);
  const profile = await ctx.db
    .query('profiles')
    .withIndex('by_tokenIdentifier', (q) => q.eq('tokenIdentifier', identity.tokenIdentifier))
    .unique();
  if (profile?.deletionRequested) throw new ConvexError('Account deletion is in progress.');
  if (profile?.isDemo) throw new ConvexError('Fictional demo profiles cannot sign in.');
  if (!profile) throw new ConvexError('Choose your username to continue.');
  return profile;
}

requireIdentity 只做一件事：跟 ctx.auth 要身分，要不到就丟出「請先登入」。requireProfile 則先呼叫前者，再用 tokenIdentifier 去 profiles 表查資料，然後依序檢查三種不能放行的情況：正在刪帳號、是示範帳號、以及根本還沒有 profile。三者之外的正常使用者，才會拿到 profile 物件繼續往下做。

選項比較

面向requireIdentityrequireProfile
回傳identity 物件profile 文件
確認的事有人登入這個人有可用的 app profile
資料庫查詢不需要多一次 profiles 查詢
新使用者尚未建 profile放行擋下並要求取 username
示範 / 刪帳中帳號不特別處理明確拒絕
適合的場合只記錄事件、公開但可登入的查詢貼文、追蹤、私訊等掛在 profile 上的操作

三個判別問句

不確定該用哪個時，依序問自己三個問題：

  1. 這個操作讀寫的資料，是不是掛在某個 profile 上？如果它要建立貼文、追蹤別人、送訊息，答案幾乎都是「是」，用 requireProfile。
  2. 如果把 profile 拿掉，這個操作還成立嗎？例如純粹記錄一個系統事件、或某個不需要個人資料的查詢，可能只需要 requireIdentity。
  3. 新使用者還沒建 profile 時，這個操作該成功還是被擋？如果它不該成功（例如貼文），就用 requireProfile，讓使用者先完成 onboarding。

規則會翻轉的情況

只用 requireIdentity，然後自己拿 identity 去查 profile。這樣做等於把「profile 不存在」的處理散落在每個函式裡，有的地方忘了檢查就變成 bug。requireProfile 的價值就是把這些檢查集中在一個地方。

把 requireProfile 用在公開功能上。如果你的探索頁、公開貼文在未登入時也該看得到，硬套 requireProfile 會把整個功能鎖死給登入者。這種情況應該提供不需要登入的查詢，或是在查詢裡「可以選擇」地讀 ctx.auth，而不是強制要求 profile。

通過 guard 之後又相信 client 傳來的 profileId。很多人前面乖乖呼叫了 requireProfile，後面卻用參數裡的 id 去寫入資料，等於門鎖裝了卻把鑰匙留在門上。guard 回傳的 profile 才是唯一可信的來源，後面所有操作都要用它。

小結

requireIdentity 只保證「有人登入」，適合不需要 app 資料的操作；requireProfile 會再查一次 profiles，並擋下刪帳中、示範帳號與尚未建立 profile 這三種情況，適合所有掛在 profile 上的功能。判準是：這個操作需不需要一個真實可用的 profile。選擇之後，後續一律使用 guard 回傳的物件，不再相信 client 傳來的識別碼。

知道該用哪個 guard 之後，最後一步就是把它套進實際的 query 與 mutation，並用三種身分情境確認它真的在把關。
