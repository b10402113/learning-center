開通 Clerk↔Convex 整合並寫 auth.config

Step 2/5 · Convex × Clerk 身分驗證

學習目標

你會在 Clerk dashboard 打開 Convex 整合、把 issuer domain 設進 Convex 的環境變數、寫出 auth.config.ts，最後確認 ctx.auth.getUserIdentity() 不再回傳 null。動手前，你應該已經有一個 Clerk app、一個 Convex 專案，以及一個能登入的畫面。

前言：為什麼 getUserIdentity 一直是 null

上一節的結論是：身分只能由 server 從驗證過的 token 推導。當你興沖沖打開 Convex 的函式，想用 ctx.auth.getUserIdentity() 看看登入者，卻發現它不管怎樣都回傳 null。這不是你程式寫錯，而是因為 Convex 還不認識你信任的那個發照機關。

Convex 要驗證 token，得先知道「該相信誰」。這份信任關係分成兩半：一半在 Clerk 那邊，你要允許它把 Convex 當成一個可以簽發 token 的對象；另一半在 Convex 這邊，你要用一個設定檔告訴它「這個 issuer 簽的 token 我認」。兩邊都接好，getUserIdentity() 才會回傳東西。這一節就是來把這條線接完。

步驟一：在 Clerk dashboard 打開 Convex 整合

先到 Clerk dashboard，進到你的應用，沿著左側選單找到 Configure → Integrations → Developers，在這裡把 Convex 整合打開。

這一步在 Clerk 內部會建立一個名為 convex 的 JWT 範本。範本的概念類似「我要簽發哪一種通行證」——之後 Convex 送出的請求會附上這個範本簽出的 token，而 Convex 端也會用同一個名稱來對應。如果這裡沒開，後面的設定寫得再對，Convex 也拿不到可驗證的 token。

打開之後，順手把 Clerk 應用頁面上的 issuer 網址記下來。它的長相類似 https://你的app.clerk.accounts.dev，這是 Clerk 對外宣告「我簽的 token 是我發的」的位址，下一步要用到。

步驟二：把 issuer domain 設進 Convex 環境變數

回到 Convex 專案，在 dashboard 的 Settings → Environment Variables（部署環境的設定，不是你本機的 .env）新增一個變數：

CLERK_JWT_ISSUER_DOMAIN=https://你的app.clerk.accounts.dev

這裡要特別注意放的位置。Convex 的函式是在雲端執行的，它們讀的是部署環境的變數，而不是你電腦上那份 .env。很多人把值寫進本機檔案、測試一直失敗，就是因為 server 端根本沒看到這個值。當這個變數不存在時，process.env.CLERK_JWT_ISSUER_DOMAIN 會是 undefined，驗證一定不會通過。

步驟三：寫下 convex/auth.config.ts

接著在 convex/ 資料夾建立一個檔案 auth.config.ts。它的內容不長，但每一行都在回答「我相信誰」：

import type { AuthConfig } from 'convex/server';

export default {
  providers: [{ domain: process.env.CLERK_JWT_ISSUER_DOMAIN!, applicationID: 'convex' }],
} satisfies AuthConfig;
  • AuthConfig 是從 convex/server 匯入的型別，讓編輯器能檢查這個設定物件的形狀，寫錯欄位會立刻報錯。
  • providers 是一個陣列，代表「我認可的發照機關」。以後如果同時接兩種身分服務，就是往這個陣列再加一筆。
  • domain 指向剛剛設定的 issuer 網址。Convex 會到這個網址底下抓公開金鑰，用來驗證簽章。
  • applicationID: 'convex' 對應步驟一在 Clerk 建立的那個範本名稱，用來確認 token 是簽給這個用途的。

這個檔案就是整條信任鏈的開關。把它刪掉，ctx.auth.getUserIdentity() 會立刻回到永遠 null 的狀態。

步驟四：讓設定生效

檔案存好後，重新執行專案的開發指令（例如 npx convex dev），讓 Convex 把新的 config 推上部署環境。終端機會顯示它重新讀取了設定。如果這一步跳過，雲端上的 Convex 用的還是舊的、沒有 provider 的設定。

步驟五：確認身分真的進來了

驗證的時候，寫一個臨時的 query，回傳這個值就好：

import { query } from './_generated/server';

export const whoAmI = query({
  args: {},
  handler: async (ctx) => {
    const identity = await ctx.auth.getUserIdentity();
    return { signedIn: identity !== null, subject: identity?.subject ?? null };
  },
});

然後從你的 app（已經接好 Clerk 登入的那個畫面）呼叫它。未登入時應該拿到 signedIn: false，登入後應該拿到 signedIn: true，而且 subject 有一串使用者識別碼。

測試請從 app 發起，不要直接在 Convex dashboard 的函式測試器裡按執行。dashboard 的測試請求不會帶著你 app 的登入 token，在那裡呼叫 getUserIdentity() 永遠是 null，容易讓你誤判設定沒生效。

小結

要讓 Convex 認得 Clerk 的 token，得接兩條線：在 Clerk dashboard 打開 Convex 整合（建立 convex 範本），再於 Convex 設定 CLERK_JWT_ISSUER_DOMAIN 並寫下 auth.config.ts。設定要放在 Convex 的部署環境變數，且要重新部署才會生效。完成後，從 app 呼叫 getUserIdentity() 就會拿到身分。
