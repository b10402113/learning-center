把 guard 套進 query/mutation 並驗證

Step 5/5 · Convex × Clerk 身分驗證

學習目標

你會在 Convex 的 query 與 mutation 開頭套用 requireProfile，把參數裡的身分欄位拿掉，並用「未登入」「已登入但未建 profile」「已登入且有 profile」三種情境驗證授權真的生效。動手前，auth.config.ts 已設好，lib/auth.ts 也已經有這兩個 helper。

前言：門鎖裝好了，鑰匙交出去沒？

前面四步都在建立「可信的身分」：從理解為什麼不能信 client、接好 Convex 與 Clerk 的信任、看懂 token 如何被驗證，到決定用哪一個 guard。現在只剩最後一哩路，就是把 guard 真的放進每一支會動到資料的函式，並且確認它確實在把關。

這一步最常出錯的地方，不是 guard 本身，而是「套了 guard 之後又相信參數」。只要函式還留著一個 userId 參數當寫入依據，前面所有的努力都會白費。所以我們會從這個壞習慣開始改起。

步驟一：把參數裡的身分欄位拿掉

先看一段錯誤的寫法。它讓 client 傳入 userId，並直接拿來當貼文的作者：

export const createPost = mutation({
  args: { userId: v.id('profiles'), caption: v.string() },
  handler: async (ctx, args) => {
    await ctx.db.insert('posts', {
      userId: args.userId,
      caption: args.caption,
    });
  },
});

正確的版本是：參數只留下真正的資料（caption），作者身分由 server 自己推導：

export const createPost = mutation({
  args: { caption: v.string() },
  handler: async (ctx, args) => {
    const profile = await requireProfile(ctx);
    await ctx.db.insert('posts', {
      userId: profile._id,
      caption: args.caption,
    });
  },
});

兩個版本只差幾行，但安全性完全不同。當 args 裡不再有 userId，攻擊者就算想冒充也沒有欄位可以填；而 profile 是經過 token 驗證、再查過資料庫才拿到的，改不動也換不了。

步驟二：讓每個受保護函式從 guard 開始

把這個模式套到所有需要 profile 的函式上。原則是：handler 的第一件事就是取得 profile，後面所有寫入與查詢都用它。

export const deleteMyPost = mutation({
  args: { postId: v.id('posts') },
  handler: async (ctx, args) => {
    const profile = await requireProfile(ctx);
    const post = await ctx.db.get(args.postId);
    if (!post || post.userId !== profile._id) {
      throw new ConvexError('You can only delete your own posts.');
    }
    await ctx.db.delete(args.postId);
  },
});

注意這裡的重點：postId 可以由 client 指定，因為那是一筆「資料」的識別碼，不是身分；但「這筆資料是不是你的」要用 guard 回傳的 profile._id 來判斷。身分不能被指定，資料可以被指定——這條界線要抓穩。

步驟三：唯讀 query 也用 profile 做範圍限制

query 一樣需要把關。不要讓查詢接受 client 傳來的使用者 id，而是用 guard 得到的 profile 去限制查詢範圍：

export const myDrafts = query({
  args: {},
  handler: async (ctx) => {
    const profile = await requireProfile(ctx);
    return await ctx.db
      .query('posts')
      .withIndex('by_userId', (q) => q.eq('userId', profile._id))
      .take(50);
  },
});

如此一來，這個 query 只可能回傳「呼叫者自己的」草稿。少了這一步，任何人只要換一個 id 就能讀別人的資料。

步驟四：只需要登入的操作改用 requireIdentity

如果你正在寫的函式不需要 profile，例如記錄一個系統事件，就改用 requireIdentity，避免強迫使用者先去建立 profile 才能觸發：

export const logEvent = mutation({
  args: { name: v.string() },
  handler: async (ctx, args) => {
    const identity = await requireIdentity(ctx);
    await ctx.db.insert('events', {
      tokenIdentifier: identity.tokenIdentifier,
      name: args.name,
    });
  },
});

步驟五：把錯誤訊息交回 UI

requireIdentity 與 requireProfile 丟出的都是 ConvexError，它可以把訊息安全地傳回 client。你的畫面應該依訊息分流：看到「請先登入」就導向登入，看到「請取一個 username」就導向 onboarding，而不是把錯誤吞掉、讓使用者卡在一個沒有反應的按鈕上。

步驟六：用三種情境驗證

  1. 未登入：呼叫受保護的 mutation，應該收到 Please sign in to continue.。
  2. 已登入但還沒建 profile：應該收到 Choose your username to continue.，畫面導去 onboarding。
  3. 已登入且有 profile：操作成功。到 Convex dashboard 看 posts 表，新資料的 userId 應該等於你的 profile，而不是任何 client 指定的值。

再補一個偽造測試：檢查 mutation 的參數清單，確認它根本沒有 userId 這種欄位。如果沒有，攻擊者就沒有下手的地方。

最後做一次即時驗證：在另一個模擬器或裝置登入同一個 app，貼文完成後，那邊應該不重新載入就看到新內容。這同時證明兩件事：身分正確，而且資料真的落地了。

通過 guard 之後，千萬不要再回頭相信任何 client 傳來的識別碼。guard 回傳的物件是你唯一的寫入依據；只要函式裡還有第二個身分來源，等於門鎖裝好卻把鑰匙留在門上。

小結

把守護資料的做法收斂成一條規則：受保護的函式從 requireProfile(ctx) 開始，參數裡不留任何身分欄位，所有寫入與查詢都使用 guard 回傳的 profile。只需要登入、不需要 profile 的操作才用 requireIdentity。最後用未登入、未建 profile、正常使用三種情境驗證，並確認例外訊息能正確引導使用者。

走到這裡，你已經有一條完整的身分鏈路：client 出示 Clerk 簽發的 token，Convex 驗證後推導出呼叫者，guard 再把它接回 app 的 profile，並在每次操作前把關。這套模式會貫穿 Codexgram 後端所有的社交功能，也是「UI 驅動真後端」時最不該省略的一層。
