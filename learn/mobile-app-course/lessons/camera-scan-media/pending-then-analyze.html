先存下 pending，再交給背景分析：非同步管線的狀態機

Step 3/5 · 拍照掃描與媒體上傳

學習目標

這一節要看懂：為什麼餐點照片要先在資料庫建立一列，標記為 analyzing，再交給背景 task 分析；也要能追蹤每個出口，最後如何把狀態收斂到 completed 或 failed。

為什麼不能讓 HTTP 請求一路等 AI

想像使用者剛上傳照片，按下「Analyze the food」。接下來，視覺模型要辨識盤子裡的食物、估算份量，再換算熱量與三大營養素。這個過程可能要好幾秒，而且中間不一定順利：模型可能回傳格式不正確的內容，網路可能中斷，OpenAI 也可能暫時忙線。

如果我們讓按鈕背後的 HTTP 請求一直等到 AI 回覆，使用者會先遇到三個問題：畫面可能長時間停在不知道是否有進度的狀態；手機切到其他 app 或連線中斷後，整次分析可能白費；只要其中一次失敗，使用者最後拿到的就只有錯誤訊息。

比較穩妥的做法，是把「送出照片」和「等待分析結果」拆成兩件事。使用者按下按鈕時，server 只做幾個很快的動作，接著立刻回覆：「我收到了，正在分析。」真正耗時的 AI 工作在背景執行，完成後再更新資料庫；畫面則透過另一條通道即時收到結果。

這條管線可以想成一台狀態機。每一列餐點先從 analyzing 出發，最後應該走到 completed 或 failed。就像包裹從「配送中」開始，最後必須變成「已送達」或「配送失敗」；如果一直停在「配送中」，使用者就永遠不知道到底發生了什麼。

三個零件，靠一支 API route 接起來

這條管線有三個各自獨立的零件：ImageKit 負責存照片，Postgres 的 meals 表負責記錄餐點狀態，Trigger.dev 負責執行耗時的 AI task。它們彼此不需要知道太多對方的內部細節，真正負責接線的是 API route。

零件它負責什麼它不知道什麼
ImageKit保管照片，回傳照片網址這張照片屬於哪一餐，也不知道分析進行到哪裡
meals 資料列記錄餐點狀態與分析結果照片是如何上傳的，也不知道 task 執行到哪一步
Trigger.dev task呼叫視覺模型，再把結果寫回資料庫是哪個使用者發起，也不知道畫面要怎麼呈現

這樣切分職責的好處，是每個零件都可以單獨替換。想更換圖床時，不必重寫 AI task；想換另一顆模型時，也不必讓前端跟著改；前端改版時，ImageKit 同樣可以維持不動。API route 就像轉運站，把照片、資料列與背景 task 接在同一條路線上。

按下按鈕後：四個快速動作

使用者按下 Analyze 後，前端會把 base64 照片送到 POST /api/meals。這支 route 會先驗證身分、確認照片格式，再查出使用者。接著才進入管線的四個關鍵動作：上傳照片、建立資料列、觸發背景 task，以及記錄這次執行的識別碼。

// 1. 照片進 ImageKit，拿回網址
const imageUrl = await uploadToImageKit(parsed.data.image, `meal-${user.id}-${Date.now()}.jpg`);

// 2. 先在 DB 建一列，狀態預設就是 analyzing
const [meal] = await db.insert(meals).values({ userId: user.id, imageUrl }).returning();

// 3. 觸發背景 task，把這列交給它
const handle = await tasks.trigger<typeof analyzeMeal>('analyze-meal', {
  mealId: meal.id,
  imageUrl,
});

// 4. 記下這次 run 的 id，方便前端訂閱與除錯
await db.update(meals).set({ triggerRunId: handle.id }).where(eq(meals.id, meal.id));

return Response.json({ meal, runId: handle.id, publicAccessToken: handle.publicAccessToken });

這個順序不能任意交換。照片要先上傳，因為背景 task 需要一個網址；資料列也要先建立，因為 task 需要 mealId，才知道結果應該寫回哪一列。

API 回傳給前端的內容有三樣：這一列 meal、這次執行的 runId，以及 publicAccessToken。前兩樣是資料，第三樣則像一張門票，讓前端稍後能訂閱這次 run 的狀態。我們會在下一節處理這張門票如何派上用場。

還有一個容易被忽略的細節：analyzing 不是在 route 裡硬寫上去，而是由 schema 的預設值提供。

export const mealStatusEnum = pgEnum("meal_status", ["analyzing", "completed", "failed"]);

// ...
status: mealStatusEnum().notNull().default("analyzing"),

因此，一列餐點建立的那一刻，就自然處於 analyzing。這個預設值不是方便省事而隨手選的，而是狀態機的起點：結果尚未回來之前，最準確的事實就是「正在分析」。

背景 task：呼叫模型，依結果分流

背景這一側由 Trigger.dev 的 schemaTask 負責。可以把它理解成一個有輸入合約的背景工作：它先宣告輸入資料必須長什麼樣子，也宣告遇到暫時性錯誤時要怎麼重試。

export const analyzeMeal = schemaTask({
  id: "analyze-meal",
  schema: z.object({
    mealId: z.string().uuid(),
    imageUrl: z.string().url(),
  }),
  retry: { maxAttempts: 2 }, // 一次transient／parse 重試，之後才判失敗
  maxDuration: 120,
  run: async ({ mealId, imageUrl }) => {
    // ...
  },
});

retry: { maxAttempts: 2 } 表示這個 task 最多嘗試兩次。第一次如果因為暫時性錯誤而失敗，系統會自動再跑一次，使用者不需要介入。maxDuration: 120 則設定兩分鐘的時間上限，避免任務一直卡住。

這裡的重點是：失敗重試不必由我們自己寫一個迴圈。把策略交給背景執行的基礎設施，task 本身就能專心處理「如何分析一張照片」。

進入 run 後，task 會建立 OpenAI client，並用結構化輸出的方式請模型看圖。

const response = await openai.responses.parse({
  model: MODEL,
  input: [
    { role: "system", content: SYSTEM_PROMPT },
    {
      role: "user",
      content: [
        { type: "input_image", image_url: imageUrl + VISION_TRANSFORM, detail: "auto" },
      ],
    },
  ],
  text: { format: zodTextFormat(visionSchema, "meal") },
});

這段設計有兩個值得留意的地方。第一，送給模型的網址接上了 VISION_TRANSFORM，使用的是縮到 1024 寬的副本；原圖仍然保留在那列資料中，供畫面使用。這就像把原始檔留在倉庫，分析時則拿一份適合處理的工作副本。

第二，zodTextFormat(visionSchema, "meal") 把模型應該回傳的內容變成可驗證的合約。模型必須填入 is_food、name、calories、protein_g、carbs_g、fat_g 這些欄位，而不是自由發揮寫一段難以解析的文字。

三種出口：每一條路都要離開 analyzing

模型回覆後，task 會根據結果走向不同出口。無論走哪一條，都不能讓資料列一直留在 analyzing。

否則，首頁看到的就會是一個永遠轉不停的 spinner。這是非同步系統最常見、也最容易被忽略的問題：工作可能已經結束了，但資料庫沒有留下結束狀態，畫面只好一直猜它是不是還在跑。

出口一：照片裡不是食物

if (!out.is_food) {
  logger.warn("Photo is not food, discarding meal", { mealId });
  await db.delete(meals).where(eq(meals.id, mealId));
  return { status: "failed" as const, errorReason: "not_food" as const };
}

當模型用 is_food: false 表示照片裡沒有食物時，這列資料會直接被刪除。

這裡為什麼不是把它標成 failed？因為椅子的照片不是「分析失敗的餐點」，而是「根本不是餐點」。如果把它留下來，首頁餐點列表、每日總熱量和連續記錄天數，都必須額外處理這個特例；直接刪除後，這些地方就不用各自加一層判斷。

那畫面要怎麼知道該顯示「這不是食物」？它讀的是這次 run 的 output，而不是那一列資料。這個看似錯位的設計，會在下一節說明。

出口二：成功辨識

const result = {
  name: out.name,
  calories: out.calories,
  proteinG: out.protein_g,
  carbsG: out.carbs_g,
  fatG: out.fat_g,
};

await db.update(meals).set({ ...result, status: "completed" }).where(eq(meals.id, mealId));

return { status: "completed" as const, ...result };

成功時，task 會把模型回傳的六個欄位寫進資料列，並把狀態改成 completed。

同一份結果還會從 task 的回傳值送出去。這樣一來，掃描畫面可以直接讀取 run 的 output 來顯示數字，不必為了剛建立的資料列再查一次資料庫。資料庫負責留下長期結果，run output 則負責快速把這次分析的結果交給正在等待的畫面。

出口三：重試用完後仍然失敗

onFailure: async ({ payload, error }) => {
  logger.error("analyze-meal exhausted retries", { mealId: payload.mealId, error: String(error) });
  await db
    .update(meals)
    .set({ status: "failed", errorReason: "analysis_failed" })
    .where(eq(meals.id, payload.mealId));
},

如果兩次嘗試都用完，task 仍然無法完成，onFailure 會被呼叫。它會把資料列標成 failed，並記下 analysis_failed 這個原因。

不過，這裡有個需要誠實面對的邊界：onFailure 處理的是「重試耗盡」，但不一定涵蓋 CRASHED、SYSTEM_FAILURE 這類 task 本身無法正常收尾的狀況。遇到這些情形，資料列可能仍停在 analyzing。

這不代表狀態機的設計失敗，而是提醒我們：設計目標是讓每條路都收斂，但實作仍可能存在需要補強的縫隙。之後可以透過排程任務，定期清理長時間沒有進展的資料列。

把這個觀念接回你的 app

耗時的 AI 分析不能卡在請求路徑上等待，因此要拆成非同步管線。使用者按下 Analyze 時，API route 只做四件快速的事：把照片上傳到 ImageKit、建立一列預設為 analyzing 的 meals、觸發 analyze-meal task、記下 run id，並回傳 meal、runId 與 publicAccessToken。背景 task 使用結構化輸出請視覺模型分析照片，接著走三條出口之一：不是食物就刪除資料列並回傳 not_food；成功就寫回六個欄位並標記 completed；重試耗盡就由 onFailure 標記 failed。無論走哪一條，都必須讓資料列離開 analyzing，否則首頁會留下永遠轉不停的 spinner。

這個設計的核心，不只是「把工作丟到背景執行」，而是讓資料庫狀態、背景 task 與前端畫面各自扮演清楚的角色：API route 負責快速收件，資料列負責記錄目前狀態，背景 task 負責完成耗時工作，而 run output 則負責把結果送回正在等待的畫面。

到這裡，照片進入管線、狀態離開管線的路徑已經完整。不過前端此時手上只有一個 runId 和一枚 token，還不知道結果什麼時候準備好。下一節會比較兩種等待方式：針對單一 run 開啟即時訂閱，或針對一整批餐點進行輪詢，並說明為什麼這個 app 會同時使用兩條路。
