訂閱還是輪詢：前端怎麼知道分析完成了？

Step 4/5 · 拍照掃描與媒體上傳

先搞清楚：你要等的是哪一種變化？

上一節已經把管線接起來了：照片上傳後，背景 task 開始執行，分析結果也會寫回資料庫。可是對使用者來說，畫面可能還停在「Analyzing your meal…」。前端需要一個明確訊號，才能知道什麼時候該停止轉圈、顯示結果，或告訴使用者分析失敗。

這時有兩條路：訂閱單一背景 run 的即時狀態，或是輪詢一整批資料。訂閱像是在某個房間裝一支專線，只要那個房間有變化，server 就主動通知你；輪詢則像隔幾秒探頭問一次：「好了嗎？」

兩種方式都能用，但用錯地方就會付出代價。訂閱太多目標，可能維護一堆不必要的連線；輪詢整個列表，則可能不斷送出其實沒有新變化的請求。Cal AI 兩種方式都用了，關鍵在於它們分工清楚。

先比較兩個選項

先不要急著記 API 名稱。把它們放在一起比較，你會看到真正的取捨不只是速度，還包含關注對象、連線成本與實作方式。

面向Realtime 訂閱輪詢（polling）
關注對象單一 run 的狀態變化一整批資料中有沒有還在跑的
延遲幾乎即時（server 主動推）最多等一個間隔（例如 3 秒）
即時性成本一個目標一條連線每個間隔一次請求
需要的憑證runId + publicAccessToken一般的身分驗證（Bearer token）
適合的畫面掃描結果頁（等這一次）首頁餐點列表（等其中幾筆）

因此，掃描頁適合訂閱「剛剛按下分析的那一次 run」；首頁餐點列表則適合查詢「今天有哪些餐點還在分析」。前者是一個目標，後者是一批資料。

如果把訂閱套在首頁，每張餐點卡片都可能需要一條連線。假設畫面上有二十筆餐點，就得維護二十條連線，即使其中十九筆早已完成。反過來，如果掃描頁固定每 3 秒輪詢一次，又會在即時性與請求浪費之間拉扯。

判別問句：在自己的 app 裡問這三題

下面三個問題，可以幫你判斷該選哪一條路。

  1. 你盯著的是一個 run，還是一批資料？ 如果問題是「這次分析好了沒」，關注的是單一目標，適合用訂閱；如果問題是「今天有哪些餐點還在跑」，面對的是一批資料，適合用輪詢。這一題通常就能決定大方向。
  2. 你的資料裡有沒有「還在進行中」的旗標？ 例如 status === 'analyzing'。如果有，就能做出條件式輪詢，只在真的需要時重新請求；如果沒有，輪詢很容易變成不斷送出的空問。
  3. 你需要的是「完成了」，還是 run 的 output 本身？ 如果畫面需要直接取得這次 run 的 output，訂閱會比較直接；如果只想知道資料是否完成，輪詢資料列的狀態通常就夠了。

掃描頁的選擇：訂閱單一 run

掃描頁的問題很單純：「我剛剛按下分析，這一筆結果什麼時候好？」這個畫面已經握有 API route 回傳的 runId 與 publicAccessToken，所以可以直接訂閱這一次 run。

const { run, error } = useRealtimeRun<typeof analyzeMeal>(logged.runId, {
  accessToken: logged.publicAccessToken,
  skipColumns: ['payload'], // payload 只是一些 id，畫面要的是 output
});

const output = run?.output;
const notFood = output?.status === 'failed';

這裡有兩個值得帶回自己 app 的設計。

第一，訂閱只需要 runId 與 publicAccessToken。這枚 token 是 tasks.trigger 回傳的 handle 自帶的，不必再另外呼叫一次 auth.createPublicToken。觸發 task 的同時，也把後續訂閱所需的授權資訊一起拿到了。

第二，skipColumns: ['payload'] 是刻意設定的。payload 只是傳入的 id，畫面真正需要的是 output。省掉不需要的欄位，就能讓每次狀態更新更輕。

取得 output 後，畫面可以分成三種狀態：

  • 還在執行：顯示「Analyzing your meal…」。
  • completed：顯示餐名、熱量與三大營養素。
  • failed，也就是 not_food：顯示「That doesn't look like food」。

注意，這裡讀的是 run.output，不是資料庫裡的那一列。因此，即使 not_food 那列已經被刪除，畫面仍然能從 run 的 output 知道該顯示什麼。

首頁列表的選擇：只在需要時輪詢

首頁面對的是一整天的餐點，可能同時有好幾筆正在分析。這種情境不適合為每張卡片各開一條 Realtime 連線，因此改用輪詢。

但重點不是「使用輪詢」，而是不要無條件輪詢。首頁只有在確實存在 analyzing 的餐點時，才需要再次查詢。

return useQuery({
  queryKey: [...MEALS_KEY, date],
  queryFn: async () => { /* GET /api/meals?date=... */ },
  // 正在背景分析的列，是這個畫面唯一看不到變化的東西。
  // 只在這種情況輪詢，勝過每張卡片各開一條 Realtime 訂閱。
  refetchInterval: (query) =>
    query.state.data?.some((meal) => meal.status === 'analyzing') ? 3000 : false,
});

refetchInterval 不是固定寫死的秒數，而是一個會檢查目前資料的函式。只要有任何一筆仍是 analyzing，就每 3 秒重新查詢；當所有餐點都完成後，就回傳 false，完全停止輪詢。

這樣的做法把成本集中在真正需要更新的時候。首頁不需要為每張卡片維護即時連線，也不會在所有分析都結束後繼續送出請求。

另外，登入新餐點成功後，還要主動讓首頁查詢失效：

onSuccess: () => queryClient.invalidateQueries({ queryKey: MEALS_KEY }),

原因是首頁在原生分頁架構下可能一直掛在背景，不會因為你切回去就自動重新整理。如果不上這一行，畫面可能延遲顯示已經有數字的餐點，甚至漏掉剛新增的那一筆。

反例：兩種方式用錯時會怎麼壞

把訂閱套在整個首頁列表。 假設每一張餐點卡片都使用 useRealtimeRun，使用者有二十筆餐點，就會有二十條連線需要維護。即使十九筆早已完成，這些連線仍可能造成額外負擔。行動裝置的網路與電池，會很快反映出這個代價。

把固定輪詢套在掃描頁。 如果掃描頁每 3 秒問一次「好了沒」，而 AI 只花 2 秒就完成，使用者仍要等到下一次輪詢才看見結果；如果 AI 花了 15 秒，前端又會送出五次請求，其中多數只是重複確認還沒完成。

兩者都不使用。 如果畫面既沒有訂閱，也沒有輪詢，那個 spinner 就可能永遠轉下去。背景 task 也許早就完成了，但沒有任何訊號把結果送回畫面。

不過，這套判準也不是死規則。若首頁只顯示一筆正在追蹤的 run，訂閱可能反而合理；若某個單一 run 沒有可用的 Realtime 授權，短時間輪詢也可能是務實的替代方案。真正要看的，是畫面目前需要追蹤的對象數量、更新頻率，以及手上能取得的資料。

可以直接套用的決策規則

如果畫面正在等待一個特定 run 的結果，就用 Realtime 訂閱，並直接讀取 run.output。如果畫面要觀察一整批資料，就用條件式輪詢，只在資料中仍有 status === 'analyzing' 時重新請求。觸發 task 時一併保留 handle 附帶的 publicAccessToken，並在新增餐點成功後讓首頁查詢失效。

現在畫面已經能從「分析中」正確變成結果。但「能跑」不代表「跑對」：背景任務失敗時你可能看不到，env var 遺漏時可能在意外的地方炸掉，資料也不一定真的寫回去了。下一節會建立一組觀察與驗證的習慣，讓你能從一次失敗的掃描，一路追到它究竟死在哪一行。
