把照片安全送進 ImageKit：server-side 上傳與尺寸策略

Step 2/5 · 拍照掃描與媒體上傳

先確認目標與前置條件

這一節完成後，你會得到一條安全的照片上傳流程：app 把 base64 照片送到自己的 server，server 再拿著 ImageKit 的 private key 完成上傳。最後，資料庫的 `meals` 資料列會有可顯示的 `imageUrl`，ImageKit 的 `/meals` 資料夾也會多一個檔案，而 private key 從頭到尾都不會進入 app。

開始前，請先準備好一個受保護的 API route，並確認你知道如何讀取 `.env`。接下來還會一起處理兩個實務問題：檔名如何設計，才能刪除帳號時把照片清乾淨；同一張照片又如何用不同尺寸，同時服務畫面顯示與 AI 分析。

先看全流程：照片要走哪一條路

不要讓 app 直接呼叫 ImageKit。那樣雖然很快就能成功，卻會逼你把 private key 打包進 app。任何人只要拆開 apk，或用工具掃過 bundle，都可能把這把 key 挖出來。

一旦 private key 外流，別人就能使用你的額度上傳、刪除，甚至讀取你的媒體庫。比較安全的做法，是讓照片先送到你自己的 server，再由 server 代表 app 與 ImageKit 溝通：

  1. app 將 base64 照片送到受保護的 API route。
  2. server 從環境變數讀取 private key。
  3. server 以 `multipart/form-data` 呼叫 ImageKit 上傳端點。
  4. ImageKit 回傳 `url`，server 將它存進資料庫。
  5. 顯示時使用原尺寸網址；送給視覺模型時，則在網址上加上縮放與壓縮設定。

第一步：把 private key 關進 server-only 模組

警告：這個模組只能由 server 端 import，不能從 screen 或 component 引入。ImageKit 的 public key 可以給前端，但 private key 才是真正的授權本體。

/**
 * ImageKit media library, server-side only. The private key is the whole auth
 * story here — never import this from a screen or component.
 */
function authHeader() {
  const privateKey = process.env.IMAGEKIT_SECRET_KEY;
  if (!privateKey) throw new Error("Add IMAGEKIT_SECRET_KEY to your .env file");
  return `Basic ${btoa(`${privateKey}:`)}`;
}

這段程式做了三件事。

  1. 從環境變數讀取 `IMAGEKIT_SECRET_KEY`。
  2. 如果找不到 key，立刻丟出錯誤，避免拿 `undefined` 組出一個注定失敗的標頭。
  3. 把 private key 加上冒號後做 base64 編碼，組成 HTTP Basic 認證需要的內容。

把讀取環境變數包在函式裡，錯誤會在最靠近設定問題的地方被發現。與其等 ImageKit 回覆一個模糊的授權失敗，不如直接知道自己的 `.env` 少了設定。

第二步：把 base64 送到 ImageKit

接著建立一次 `multipart/form-data` 的 POST。ImageKit 的上傳端點可以接受 base64、二進位資料或 URL；目前 app 手上是 base64，所以直接把它放進 `file` 欄位。

export async function uploadToImageKit(base64: string, fileName: string) {
  const form = new FormData();
  form.append("file", base64);
  form.append("fileName", fileName);
  form.append("folder", "/meals");

  const response = await fetch("https://upload.imagekit.io/api/v1/files/upload", {
    method: "POST",
    headers: { Authorization: authHeader() },
    body: form,
  });

  if (!response.ok) {
    throw new Error(`ImageKit upload failed (${response.status}): ${await response.text()}`);
  }

  const { url } = (await response.json()) as { url: string };
  return url;
}

逐一看這三個欄位：

  • `file`：照片本體，也就是 base64 字串。
  • `fileName`：照片在 ImageKit 中使用的檔名。
  • `folder`：將檔案放進 `/meals` 虛擬目錄，方便日後分類與清理。

`fetch` 的 `Authorization` 標頭使用剛才產生的 Basic 認證。若回應不是成功狀態，錯誤訊息會同時包含 HTTP 狀態碼與 ImageKit 回傳的文字，讓 server log 不只顯示「上傳失敗」，也能看到服務端具體指出了什麼問題。

成功時，從回應取出 `url` 並回傳。這個網址就是之後要存進資料庫、提供畫面顯示，也能交給 AI 讀取的來源。

第三步：用檔名前綴讓刪除真的刪乾淨

上傳成功後，資料庫有了網址，但照片與使用者之間的所有權關係還需要一個可靠的標記。否則日後刪除帳號時，很容易只刪掉資料列，卻把 ImageKit 裡的檔案留下來。

這個問題在「這不是食物」的照片特別容易發生：如果應用程式先刪除了資料列，之後再依照資料列尋找照片，就再也找不到那個檔案。它會變成媒體庫裡的孤兒檔案。

因此，從上傳的第一刻就把 `userId` 放進檔名前綴：

const imageUrl = await uploadToImageKit(
  parsed.data.image,
  `meal-${user.id}-${Date.now()}.jpg`,
);

這會產生像 `meal-<userId>-<時間戳>.jpg` 這樣的檔名。刪除帳號時，不要只依賴資料庫裡還剩下哪些列，而是用這個前綴搜尋整個媒體庫：

const query = new URLSearchParams({
  searchQuery: `name : "meal-${userId}"`, // ':' 是前綴比對，區分大小寫
  limit: String(PAGE),
  skip: String(skip),
});

這樣即使資料列已經刪除，仍能找到屬於這位使用者的照片。前綴搜尋就像在每個檔案上貼了一張歸屬標籤，清理時可以沿著標籤一次找齊。

刪除流程還要注意數量限制：ImageKit 的檔案列表端點一次最多回傳一千筆（`PAGE`），批次刪除一次最多一百筆（`BATCH`）。因此，若搜尋結果超過單批上限，則要分頁抓取；若待刪除檔案超過單批上限，則要分批刪除。否則照片一多，就可能只清掉前面一部分。

第四步：在 API 入口限制 base64 大小

你可能會問：既然 ImageKit 最後接受的是 multipart，為什麼 app 不直接送 multipart 檔案？原因是 Expo SDK 57 將 `expo/fetch` 裝成原生端的全域 fetch，而它無法讀取 `{ uri }` 這種指向磁碟的 FormData part。

所以在 app 端，實務上要傳的是字串，也就是 base64。既然 API 明確接收 base64，就應該在自己的 server 先限制內容大小，而不是等 ImageKit 收到後才回報錯誤：

const logMealSchema = z.object({
  image: z.string().min(100).max(12_000_000), // 約 9MB 的 JPEG
});

`min(100)` 可以擋掉明顯不可能是照片的空字串或過短內容；`max(12_000_000)` 則限制可能拖垮請求的巨大 payload，約對應 9MB 的 JPEG。這些檢查放在 API 入口，server 就能更早拒絕不合適的請求。

第五步：用不同尺寸服務顯示與 AI

同一張照片會被兩種用途使用：

  • 畫面顯示：需要清楚，但通常不需要手機原圖的全部像素。
  • 視覺模型分析：需要模型看得懂的內容，但多出來的像素只會增加傳輸與處理成本。

手機原圖可能有四千像素、四 MB。若只是顯示縮圖，直接傳原圖會浪費頻寬；若送給視覺模型，模型最後也會把圖片壓到 1024 像素以下，原本多出的像素同樣沒有帶來相應價值。

ImageKit 可以根據網址即時產生不同變體，不必先在程式裡另外產生縮圖。送給模型的網址加上這段轉換設定：

// 只給模型的那份副本使用；資料列仍保留原尺寸網址供畫面顯示
const VISION_TRANSFORM = "?tr=w-1024,q-80,f-jpg";

這段設定代表：

  • `w-1024`：將寬度縮到 1024，並自動保持長寬比。
  • `q-80`：將 JPEG 品質設定為 80。
  • `f-jpg`：固定輸出為 JPEG。

這段參數只接在送給模型的網址後面。資料庫仍保留原尺寸網址，供畫面顯示或日後其他用途使用。換句話說，一張照片可以同時扮演兩個角色：原圖負責顯示，轉換後的版本負責 AI 分析，避免每個用途都背著同樣大的檔案走。

完成後，應該看到什麼

完成這幾步後，流程應該符合以下結果：

  • app 只把 base64 照片送到自己的 API，沒有接觸 ImageKit private key。
  • server 從環境變數讀取 private key，並以 Basic 認證呼叫 ImageKit。
  • ImageKit 的 `/meals` 資料夾出現 `meal-<userId>-<時間戳>.jpg` 類型的檔案。
  • 資料庫的 `meals` 資料列存有 ImageKit 回傳的 `imageUrl`。
  • 刪除帳號時，可以用檔名前綴搜尋並分頁、分批清理，連孤兒檔案也能處理。
  • 畫面使用原尺寸網址；AI 使用加上 `VISION_TRANSFORM` 的 1024 寬 JPEG 網址。
照片的上傳全程發生在 server：private key 由環境變數注入，放在只有 server 能 import 的模組裡，再透過 Basic 認證呼叫 ImageKit 上傳端點。成功回傳的 `url` 才會存進資料庫。檔名使用 `meal-<userId>-<時間戳>` 前綴，讓刪除帳號時能搜尋整個媒體庫，連資料列已刪除後留下的孤兒檔也一併清掉。由於 Expo 的原生 fetch 讀不到指向磁碟的 FormData part，app 端使用 base64，並用 Zod 限制長度。尺寸則交給 ImageKit 即時轉換：畫面使用原圖，視覺模型使用縮到 1024 寬的版本，以減少傳輸延遲與 token 使用量。

現在照片已安全地放進 ImageKit，資料庫也拿到了它的網址。不過，使用者按下 Analyze 後，AI 還需要幾秒鐘才能回覆；如果讓原本的請求一直等待，流程就會變得脆弱。下一節會處理這條非同步管線：先把照片寫成 `analyzing` 狀態，再由背景任務把各種處理結果收斂回資料庫。
