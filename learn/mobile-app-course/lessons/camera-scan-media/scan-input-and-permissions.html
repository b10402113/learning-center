開相機與選圖：處理權限、拍照與相簿輸入

Step 1/5 · 拍照掃描與媒體上傳

先看整體：這一節要完成什麼

你正在做一個 scan 畫面：使用者可以直接拍照，也可以從相簿挑一張照片，兩條路最後都交給同一段後續處理。這看起來像是放兩顆按鈕，但真正接上手機後，還要處理權限、相機生命週期，以及使用者拒絕權限時的替代方案。

想像你照著設計稿刻出 scan 畫面：一個大大的快門圓鈕、底下寫著「把整盤食物放進畫面」。模擬器上跑起來漂漂亮亮，你按下快門——什麼都沒發生。換到真機，系統跳出一個權限視窗，你選了「不允許」，整個畫面就此卡死，連「改用相簿」這條路都沒有。

這不是單純哪一行寫錯，而是行動裝置的輸入本來就有門檻。相機、相簿、麥克風、定位，都要先通過權限這道關卡。通過之後，還有另一個容易被忽略的問題：Expo 的原生分頁可能會先把所有頁面渲染好，導致使用者明明還在首頁，相機卻已經掛著、甚至持續開啟。

這一節會帶你完成兩件事：讓 scan 畫面同時支援拍照與選圖，以及在相機權限被拒絕或分頁失焦時，仍然維持正確的使用流程。

前置條件：開始前先確認

動手前，請先確認專案已經 scaffold 好，也知道新增 native module 之後必須重建 app。這裡要使用相機與相簿套件，因此要執行 npx expo run iOS，不能只靠重新整理 JS 或熱重載來查看結果。

完成後，scan 畫面會得到一個形狀一致的結果：{ uri, base64 }。uri 用來預覽本機照片，base64 則交給後續上傳流程。

第一步：在 app.json 宣告權限與說明文案

權限的第一個落點不是元件程式碼，而是 app.json。相機與相簿要在這裡掛上對應的 Expo plugin，並附上給使用者看的說明。

這在 iOS 上是必要設定：系統權限彈窗必須告訴使用者，這個 app 為什麼需要相機。如果沒有提供這段說明，權限就不會正常生效。

[
  "expo-camera",
  {
    "cameraPermission": "Bulky AI uses the camera to read the calories and macros in your meal."
  }
],
[
  "expo-image-picker",
  {
    "photosPermission": "Bulky AI reads the calories and macros from meal photos you pick."
  }
]

Android 則要在 android.permissions 明確列出 android.permission.CAMERA。

文案不是裝飾。若只寫「需要相機權限」，使用者很難知道允許之後能得到什麼；寫清楚用途，例如用照片讀出餐點的熱量與營養素，使用者才比較能做出有根據的選擇。

第二步：在真正使用相機時請求權限

完成宣告後，程式仍要在真的需要相機時請求權限。expo-camera 提供 useCameraPermissions() hook，它回傳的 permission 可能有三種狀態：

  • 若為 null，代表權限狀態仍在載入。
  • 若 granted 為 true，代表使用者已允許相機。
  • 若未授權，則要根據 canAskAgain 決定下一步。

不要把 null 當成「使用者拒絕」。那只是狀態還沒準備好；若太早顯示拒絕畫面，使用者會看到錯誤的提示。

const [permission, requestPermission] = useCameraPermissions();

if (!permission) return <Screen />; // 權限狀態還在載入

if (!permission.granted) {
  return (
    <Screen>
      <Pressable
        onPress={() =>
          permission.canAskAgain ? requestPermission() : Linking.openSettings()
        }>
        <Text>
          {permission.canAskAgain ? 'Allow camera' : 'Open Settings'}
        </Text>
      </Pressable>
    </Screen>
  );
}

這段程式的判斷順序很重要。

  1. 若 permission 還不存在，先顯示載入中的畫面。
  2. 若尚未取得權限，檢查 permission.canAskAgain。
  3. 若還能再次詢問，就呼叫 requestPermission()。
  4. 若不能再詢問，就呼叫 Linking.openSettings()，把使用者帶到系統設定。

使用者第一次拒絕時，系統通常還允許 app 再問一次，所以按鈕可以顯示「Allow camera」。但當使用者拒絕到系統不再顯示彈窗時，再按一次請求權限也不會有反應；這時按鈕應該改成「Open Settings」。按鈕文字跟著狀態改變，使用者才不會以為 app 壞掉了。

第三步：拍照並統一輸出格式

權限通過後，才渲染 CameraView。拍照時要先用 ref 抓住相機元件，再呼叫 takePictureAsync。

const cameraRef = useRef<CameraView>(null);

const capture = async () => {
  const picture = await cameraRef.current?.takePictureAsync({
    quality: 0.5,
    base64: true,
  });
  if (picture?.base64) setShot({ uri: picture.uri, base64: picture.base64 });
};

quality: 0.5 是刻意降低壓縮品質。手機相機原始 JPEG 可能有很大的尺寸與檔案大小，但掃描餐點通常不需要保留完整相機畫質。降低品質後，網路傳輸與後續處理都會輕一些。

base64: true 會讓結果包含可以直接放進 JSON 的字串版本。拍照完成後，shot 同時保存本機 uri 與 base64：前者用來顯示預覽，後者留給上傳流程。

第四步：從相簿選圖，保留替代路徑

相簿選擇器與直接讀取整個相簿不同。現代系統的選擇器只會把使用者親手挑選的照片交給 app，因此 iOS 與 Android 都不需要事先取得相簿的執行時權限。

這讓 scan 畫面多了一條重要的替代路徑：即使使用者拒絕相機權限，仍然可以按「Choose from gallery」選擇照片，不會整頁卡在權限提示上。

const pickFromGallery = async () => {
  const result = await ImagePicker.launchImageLibraryAsync({
    mediaTypes: ['images'],
    quality: 0.5,
    base64: true,
  });
  const asset = result.assets?.[0];
  if (asset?.base64) setShot({ uri: asset.uri, base64: asset.base64 });
};

這裡要注意，相機與相簿回傳的資料形狀不同：

  • 相機直接回傳一張 picture。
  • 相簿回傳的是 result.assets 陣列，因此要取第一筆資產。

兩邊最後都用 setShot 收斂成 { uri, base64 }。這樣下一段處理上傳時，就不必再分辨照片是拍出來的，還是從相簿選出來的。

在相機權限被拒絕的畫面中，請把「Choose from gallery」放在主要按鈕下方。若 canAskAgain 為 true，主要按鈕負責重新請求相機權限；若為 false，主要按鈕帶使用者前往系統設定，而相簿按鈕則始終提供可用的替代方案。

第五步：離開分頁時卸載相機

最後要處理的是 native tabs 的生命週期。Expo 的原生分頁會預先渲染所有分頁，因此使用者明明正在 Home，scan 分頁的 CameraView 仍可能掛著，持續占用相機與電力。

先用 useIsFocused() 判斷目前分頁是否真的可見，只有可見時才渲染相機：

const isFocused = useIsFocused();

// ...
{isFocused ? (
  <CameraView ref={cameraRef} style={{ flex: 1 }} facing="back" />
) : null}

當 isFocused 為 true 時，畫面才會掛載 CameraView。切換到其他分頁後，CameraView 會被卸載，相機也會隨之釋放。

這是使用 native tabs 時要特別留意的地方。一般的 tab 導航不一定會遇到相同情況，但只要你的導航方式會預先渲染分頁，就必須把相機的掛載條件綁在目前是否可見。

完成後應該看到什麼

現在可以用下面的流程驗證結果：

  1. 進入 scan 分頁，若尚未授權，看到相機權限請求畫面。
  2. 若可以再次詢問，按鈕會重新呼叫權限請求。
  3. 若系統不再允許詢問，按鈕會改為開啟系統設定。
  4. 即使相機被拒絕，也能按「Choose from gallery」選取照片。
  5. 拍照或選圖成功後，都能得到包含 uri 與 base64 的 shot。
  6. 離開 scan 分頁後，CameraView 不再掛載。
相機與相簿輸入要處理兩道關卡。第一道是權限：在 app.json 用 plugin 宣告權限與說明文案，執行時用 useCameraPermissions 分辨載入中、已允許與被拒絕，再用 canAskAgain 決定要重新請求，或帶使用者前往系統設定。相簿選擇器不需要執行時權限，因此相機被拒絕時仍能提供選圖這條路。第二道是生命週期：native tabs 會預先渲染分頁，必須用 useIsFocused 只在畫面可見時掛載 CameraView，避免相機在背景持續開啟。拍照與選圖最後都整理成同一個 { uri, base64 }，交給下一段處理。

做完這些設定後，scan 畫面就具備兩種輸入方式，也能面對權限被拒與分頁切換。下一節會處理照片上傳：把這份 base64 送進 ImageKit，並說明為什麼上傳一定要發生在 server 端。
