用 convex-test 與 vitest 建立測試

Step 3/5 · 寫實 Seed 與後端測試

學習目標

用 convexTest 與 import.meta.glob 起一個記憶體後端，並用 withIdentity、t.run、t.fetch 寫出第一個測試。

前言：不需要真的連上資料庫，也能測後端

上一節我們做出了一份可以重跑的 seeder，但要說「這個後端是對的」，光靠 seed 跑得起來還不夠。你可能會想：測後端不就得先開一個測試用的資料庫、準備一堆資料、測完再清掉嗎？那樣又慢又麻煩，而且很容易互相污染。

幸好 Convex 提供了一套 convex-test，它可以在記憶體裡起一個完整的後端實例：你的 schema、你的所有 query/mutation/action 都在裡面跑，每個測試拿到一個乾淨的資料庫，測完就消失。搭配 vitest 當測試框架，你就能用一般的 test()、expect() 寫後端測試。這一節把這個測試環境搭起來，並走過你會用到的每一種呼叫方式。前置條件是你已經熟悉 Convex 的 query 與 mutation。

第一步：安裝與取得所有後端模組

在專案裡安裝 convex-test 與 vitest 之後，測試檔的開頭要先把 schema 與「全部後端檔案」載入。關鍵是這一行：

const modules = import.meta.glob('./**/*.ts');

它告訴測試框架：「把這個資料夾底下所有 .ts 檔都收集起來」。Convex 的函式是靠檔案路徑對應到 API 名稱的，所以測試實例必須看得見每一支你寫的後端檔案，才能正確解析 api.profiles.create 這類呼叫。少載入一支檔案，就會在呼叫它時找不到。

第二步：用 convexTest 起一個記憶體後端

接著呼叫 convexTest，把 schema 與剛剛收集到的 modules 傳進去，就得到一個獨立的後端實例：

import { convexTest } from 'convex-test';
import schema from './schema';

const t = convexTest(schema, modules);

這個 t 就是你操作後端的入口。它是一個全新、空白的資料庫，每個測試都應該自己建一個，才能保證測試之間互不影響。測試跑完後這個實例會被丟掉，不會留下任何痕跡，所以你可以盡情在裡面建立、刪除、搞爛資料。

第三步：用 withIdentity 模擬登入身分

後端最常需要驗證的就是「誰在呼叫」。在真實世界這個身分來自 Clerk 簽發的 JWT，但在測試裡不需要真的走一次登入流程。withIdentity 讓你直接冒充一個已驗證的使用者：

const alice = t.withIdentity({
  subject: 'alice',
  tokenIdentifier: 'https://clerk.test|alice',
});
const bob = t.withIdentity({
  subject: 'bob',
  tokenIdentifier: 'https://clerk.test|bob',
});

之後你用 alice 呼叫的每個函式，在後端眼中都會是「alice 本人」；用 bob 呼叫則是 bob。這裡的 tokenIdentifier 是最重要的欄位，因為後端的授權邏輯通常以它為鍵。至於沒有掛上 identity 的原始 t，就代表一位匿名、未登入的訪客——這一點在測權限時非常關鍵。

第四步：用 mutation、query、action 呼叫後端函式

有了身分之後，就可以像前端一樣呼叫後端。語氣幾乎和 app 裡一模一樣：

const aliceId = await alice.mutation(api.profiles.create, {
  username: 'alice', name: 'Alice',
});
const me = await alice.query(api.profiles.me, {});
const totals = await t.query(internal.seed.summary, { username: 'alice' });

mutation 用來寫資料、query 用來讀資料、action 用來執行需要對外呼叫的動作，參數就是你在函式上宣告的 args。注意 internal 開頭的函式（例如 internal.seed.summary）也能在測試裡直接呼叫——這正是為什麼 seeder 那些不對外開放的函式仍然測得到。

第五步：用 t.run 直接檢查資料庫與檔案

有時候你想確認的不是「介面回傳什麼」，而是「底層的資料庫長什麼樣」。例如貼文刪除後，按下讚的紀錄是不是真的清掉了。這時用 t.run 拿到原始的 ctx，直接查表或查檔案：

const storageId = await t.run(async ctx => {
  const post = await ctx.db.get('posts', postId);
  return post!.storageId;
});

// 之後可以確認檔案是否真的被清掉
expect(await t.run(ctx => ctx.storage.get(storageId))).toBeNull();

t.run 是測試的 X 光機。正常的介面可能刻意隱藏某些欄位（例如不外洩的 storageId），但測試可以繞過介面直接驗證內部的真實狀態。要小心的是：它能做到的檢查不代表你該用它取代所有介面測試，通常只在需要確認「底層有沒有殘留」時才出動。

第六步：用 t.fetch 測 HTTP action

上傳與讀取媒體是走 HTTP 路由的（例如 /upload、/media），不是一般的 query/mutation。要測它們，用 t.fetch 發一個請求，拿回標準的 Response 物件：

const result = await alice.fetch(`/upload?id=${uploadId}`, {
  method: 'POST',
  headers: { 'Content-Type': 'image/jpeg' },
  body: new Uint8Array([255, 216, 255]),
});
expect(result.status).toBe(200);

因為它回傳的是真的 Response，你可以檢查 result.status、result.headers，甚至用 await result.arrayBuffer() 讀出內容。於是「未登入上傳要回 401」、「非擁有者要回 404」、「超過大小要回 413」這些 HTTP 層的行為，全都能自動化驗證。

把重複的設定抽成 setup()

幾乎每個測試都需要「兩個已登入的使用者」。與其每次重寫，不如抽成一個 setup()：

async function setup() {
  vi.useFakeTimers();
  const t = convexTest(schema, modules);
  const alice = t.withIdentity({ subject: 'alice', tokenIdentifier: 'https://clerk.test|alice' });
  const bob = t.withIdentity({ subject: 'bob', tokenIdentifier: 'https://clerk.test|bob' });
  const aliceId = await alice.mutation(api.profiles.create, { username: 'alice', name: 'Alice' });
  const bobId = await bob.mutation(api.profiles.create, { username: 'bob', name: 'Bob' });
  return { t, alice, bob, aliceId, bobId };
}

這裡先鋪了 vi.useFakeTimers()，是為了之後能控制「假時間」（排程清理的測試會用到，下一節細講）。另外用 afterEach(() => vi.useRealTimers()) 在每個測試結束後把時間還原，避免影響其他測試。回傳的物件讓每個測試都能拿到乾淨的 t 與兩個現成使用者，測試本身就能直接聚焦在要驗證的行為上。

小結

用 import.meta.glob 收集所有後端模組、交給 convexTest(schema, modules)，就得到一個乾淨的記憶體後端。用 withIdentity 冒充登入者，原始的 t 代表匿名訪客；用 mutation/query/action 呼叫介面、t.run 檢查底層資料、t.fetch 測 HTTP action。把共同設定抽成 setup()，測試就能保持精簡。
