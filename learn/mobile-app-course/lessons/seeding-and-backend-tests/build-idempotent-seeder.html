拆解冪等的寫實 Seeder

Step 2/5 · 寫實 Seed 與後端測試

學習目標

用 seedKey、確定性的 postPlan 與分批 action 拆解出一個可重複執行、不重複資料也不弄壞計數器的 seeder。

前言：把「跑一次就加一批」改造成可以反覆跑的流程

你已經知道 seed 必須冪等。現在的問題是：一支會產生 24 個 profile、上百篇貼文、以及每篇貼文上幾十個讚與留言的程式，要怎麼寫才不會在第二次執行時爆走？直覺的寫法是在一個迴圈裡 insert，但這樣一重跑就全部重複。

這一節要拆解的 convex/seed.ts 給出了答案。它不是一坨迴圈，而是一組各司其職的內部函式：有的建立帳號、有的註冊媒體、有的分批產生貼文、最後有一個彙總查詢讓你驗收。跟著這條線走完，你會看到一個可以穩定重跑的資料產生流程該長什麼樣子。動手前的前提是：schema、profiles、posts、social 這些模組已經存在，因為 seeder 會直接對它們產生的表寫入。

第一步：用環境檢查守住「只能在開發環境跑」

整份檔案的第一個守衛，是一支被每個函式呼叫的檢查函式。它比對當下的部署網址，不是指定的開發 deployment 就立刻丟錯中止。

function requireDevelopment() {
  if (env.CONVEX_CLOUD_URL !== 'https://savory-raven-325.eu-west-1.convex.cloud')
    throw new Error('Seeding is restricted to the codexgram development deployment.');
}

把它放在每個 internal 函式的開頭，就等於在整支 seeder 前面裝了一道閘門。即使有人誤把指令指向正式環境，第一行就會失敗，不會有任何一筆假資料被寫進去。這種「先驗環境再做事」是會被寫入資料的維運腳本的基本禮貌。

第二步：給每筆資料一個穩定身分 seedKey

冪等的核心是「寫入前先認身分」。身分不能是每次執行都不同的隨機值，必須是根據位置算出來、永遠一樣的字串。Codexgram 用一個小函式替第 i 個成員產生 key：

const seedKey = (i: number) => `${SEED_VERSION}:member:${i}`;

這裡的 SEED_VERSION 是像 community-v1 這樣的版本字串。它讓同一批資料有自己的命名空間；未來如果你想整批換掉舊種子資料，只要把版本號往上跳，舊的 key 就不會再被認到，新資料自然接上。接著在 initialize 裡，每個成員插入前都會先用這個 key 查一次：

const existing = await ctx.db
  .query('profiles')
  .withIndex('by_seedKey', q => q.eq('seedKey', seedKey(i)))
  .unique();
if (existing) { ids.push(existing._id); continue; }

如果查到了，就沿用既有的 _id 並直接跳過，完全不做多餘的寫入；只有查不到時才真的 insert。這樣第二次執行時每一位成員都「已經存在」，整段就變成只收集 id、不新增任何東西。貼文的 by_seedKey 查詢與跳過也是同一招。

第三步：讓資料的產生是「確定性」的

只認 key 還不夠。如果每次執行產生的貼文內容不同（例如作者、圖片、文字隨機挑），就算沒重複，同一篇貼文的長相也會換來換去，難以比對。所以 seeder 把「第幾篇貼文長什麼樣」寫成一個純函式 postPlan(index)：

export function postPlan(index: number) {
  const author = index % 6 === 0 ? 0 : 1 + index % 23;
  const image = (index * 7 + author) % captions.length;
  return {
    key: `${SEED_VERSION}:post:${index}`,
    author,
    asset: `photo-${image + 1}`,
    caption: captions[image][Math.floor(index / 9) % 3],
  };
}

同樣的 index 進去，永遠得到同樣的 key、作者、圖片與文案。這種「輸入相同、輸出必相同」的性質叫確定性（determinism）。它讓 seed 的結果可預測、可重現：第一個人跑出來的第 42 篇貼文，跟你在自己機器上跑出來的第 42 篇完全一樣。

第四步：把產生貼文拆成 action，並且分批做

建立貼文需要先取得圖片檔案，而讀寫檔案要用到 ctx.storage，那是 action 才能做的事。所以整條流程被拆成：populate 是一個 internalAction，負責跑迴圈與存取檔案；真正寫入資料庫的工作則用 runMutation 交給內部的 mutation。這個 action 有一個很硬的限制——它是分批執行的：

if (!Number.isInteger(args.count) || args.count < 1 || args.count > 12)
  throw new Error('Use batches of 1–12 posts.');

一次只做 1 到 12 篇，而不是把一百多篇塞進同一個動作。這在 serverless 環境裡很重要：action 有執行時間與記憶體上限，把工作切成小批，可以避免單次執行過久或吃光記憶體。實際使用時，你會叫它「從第 0 篇開始做 3 篇」，下一次再叫下一批，而不是一次全做完。

每一批裡面最重要的一句，是它會先問「這篇是不是已經有了」：

if (await ctx.runQuery(internal.seed.existingPost, { index: i })) {
  skipped++; continue;
}

已經存在的貼文直接記為 skipped，只有真正新建的才記為 created。所以重跑時你得到的回傳會是 { created: 0, skipped: 3 }，而不是又建了三篇。

第五步：每篇貼文擁有自己的檔案

媒體檔案有一個容易忽略的陷阱：如果多篇貼文共用同一個 storageId，那麼刪掉其中一篇時，清理邏輯會把檔案刪掉，其他還在的貼文就一起破圖了。Codexgram 的解法是讓每篇貼文在建立時各自複製一份檔案：

const blob = await ctx.storage.get(asset.storageId);
// Every post owns its file, so deleting one can never break another's media.
const storageId = await ctx.storage.store(blob);

如果後續的寫入沒有接受這個檔案（例如已經被別人搶先建立），程式會把自己剛存的那份刪掉，避免留下孤兒檔案。這個「自己存、自己負責刪」的模式，讓刪除操作可以安全地只清掉屬於該貼文的資源。

第六步：計數器只在真的寫入時更新

貼文上的 likesCount、commentsCount，以及會員的 postsCount、followersCount 都是重複計算的欄位（denormalized counters）。它們必須和實際的關聯資料數量一致，否則畫面顯示的數字就是錯的。seeder 的做法是：只有在真的插入貼文的分支裡，才會去累加作者的 postsCount；重跑時因為整篇都跳過了，這些累加根本不會執行，計數器自然不會被加第二次。

留言的冪等則靠 requestId。每一則種子留言都用像 ${plan.key}:comment:1 這樣穩定且唯一的識別碼，即使重複執行，資料層也只會認到同一則留言。

第七步：用 summary 驗收，而不是用眼睛

最後一支 internalQuery 叫 summary，它會回傳這次 seed 的成果統計：有幾個 profile、幾篇貼文、多少讚與留言，以及你這個觀眾帳號的追蹤數。它存在的意義是讓「測試」可以斷言結果，而不是靠你打開 dashboard 用眼睛數。一個健康的冪等 seeder，跑第一次與跑第二次之後呼叫 summary，應該得到完全相同的數字。

小結

冪等 seeder 靠四個手法撐起來：用 seedKey 當穩定身分，寫入前先查、存在就跳過；用確定性的 postPlan 保證每次產生同樣的資料；用 internal action 分批（1–12 篇）存取檔案並複製出每篇專屬的媒體；以及只在真的寫入時才更新計數器。整支流程包在 requireDevelopment() 的環境檢查裡，並用 summary 讓結果可被斷言。

現在你有一份可以反覆執行、結果穩定的種子資料了。但「跑起來看起來對」還不夠，接下來要讓它和後端的其他行為一起被自動驗證。下一節會搭建測試環境：用 convex-test 在記憶體裡起一個後端，並學會用不同身分呼叫它的函式。
