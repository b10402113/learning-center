Reactive 查詢：為什麼不用手動重抓資料

Step 4/5 · Convex 後端模型

學習目標

能解釋 Convex reactive query 的運作機制：前端為什麼不用輪詢或手動重抓，資料變動如何自動推送，以及樂觀更新和 reactive 之間是什麼關係。

前言：留言出現了，但畫面怎麼知道要更新？

上一節你寫好了 posts.list 這個查詢，手機端一打開就拿到一頁貼文。現在想像一個情境：A 同學正在看一篇貼文，B 同學在同一時間按了讚、留了言。A 的手機要怎麼知道畫面該更新？

如果照傳統直覺，你可能會想辦法「定時去問後端有沒有新資料」，也就是每隔幾秒重打一次 API；或者叫使用者自己下拉重新整理。這些做法都能動，但都要你額外寫很多協調的程式，而且很容易出現「明明資料變了，畫面還是舊的」的落差。

Convex 的查詢不是「問一次就拿一次答案」，而是訂閱。你用同一個查詢，資料一變，畫面自己就變，完全不用寫輪詢或重新整理的邏輯。這一節要把這個機制拆開，因為理解它之後，你才會知道為什麼 Convex 的 query 有一些特別的規則。

從「拉」到「推」的轉變

傳統的 API 呼叫是「拉（pull）」：前端主動去後端要資料，要完就結束。之後資料怎麼變，前端不知道。要維持即時，通常得靠下面幾種補救方式。

做法怎麼運作代價
手動重抓使用者下拉或切換頁面時再呼叫一次 API資料可能早就過期，體驗也差
輪詢每隔幾秒自動重打一次 API多數請求都是白問的，浪費流量與資源
自己接 WebSocket前後端維護一條長連線，後端主動推事件要自己設計事件格式、斷線重連、狀態同步
Reactive 查詢前端訂閱查詢，後端在資料變動時自動推送新結果幾乎不用寫協調程式，但查詢必須是確定性的

Convex 屬於最後一種：前端訂閱、後端推送。它的關鍵差別在於，你不用自己定義「什麼事件要推給誰」，只要把查詢寫成「我想要這段資料」，剩下的由 Convex 處理。你可以把它想成訂雜誌與每天跑書店的差別：輪詢是你每天特地跑一趟書店問「新的一期到了嗎」；reactive 查詢是你訂了雜誌，一出版就送到你家。

機制：Convex 怎麼知道你該更新了

要理解 reactive，關鍵是「追蹤依賴」這四個字。當一個前端元件訂閱了某個 query，Convex 在後端執行這個 query 時，會記下它實際讀取了哪些資料。以貼文清單為例，這個查詢讀了 posts 表的一頁資料，還可能讀了 follows 表來判斷追蹤關係。這些被讀到的範圍，就是這個查詢的依賴。

接下來，只要有任何一個 mutation 改動了這些依賴裡的資料，Convex 就知道「這個查詢的結果可能不一樣了」，於是自動重新執行它，再把新的結果推給所有訂閱這個查詢的前端。整個過程對你來說是透明的：你沒有寫任何「請更新畫面」的程式，只是把查詢掛上去，畫面就跟著資料走。

把這個流程拆成步驟看：

  1. 手機端訂閱 api.posts.list，Convex 執行查詢並回傳第一頁。
  2. Convex 記住這次查詢讀過哪些資料。
  3. 另一支手機呼叫 api.posts.publish 或 social.setLike，改動了 posts 或 likes。
  4. Convex 發現受影響的查詢，重新執行，把新結果推給所有訂閱者。
  5. A 同學的畫面自動更新，不必下拉，也不必重新進入頁面。

這也是為什麼課程裡說 Convex 的即時更新是「開箱即用」的。你什麼都沒設定，貼文一發布、留言一送出，畫面上的清單就自己變了。

為什麼 query 不能有副作用

理解了剛才的機制，就能明白一條硬規則：query 不能修改資料，也不該做出每次結果都不同的行為（例如讀取當下的系統時間當結果）。原因是 Convex 會在很多時機重複執行你的查詢——訂閱時跑一次、依賴的資料變動時再跑一次。如果 query 裡藏了寫入，那「只是重新看一下畫面」就可能意外改到資料；如果 query 的結果不確定，那麼即使資料沒變，畫面也可能每次顯示不同內容，reactive 的追蹤就失去意義。

所以 query 只能是「給定同一份資料，就得到同一個結果」的純函式。這不是風格建議，而是讓自動重跑這件事能成立的前提。真正需要寫入的動作，一律走 mutation；真正需要對外呼叫、有副作用的，走 action。

樂觀更新：reactive 之前的那一小段空白

Reactive 聽起來很完美，但它有一個本質上的時間差。使用者在手機上按下愛心，你呼叫 mutation；mutation 要送到後端、寫入資料、再觸發查詢重跑、把新結果傳回來。這中間可能經過幾百毫秒。人的眼睛等不了那麼久——如果愛心要等半秒才變紅，用起來會覺得卡。

所以社群 app 通常會搭配樂觀更新（optimistic update）：使用者一按，前端就先把本機畫面的愛心變成紅的、數字加一，假裝寫入已經成功。等後端真的處理完、reactive 查詢把權威資料推回來，畫面再對齊一次。如果後端失敗，就回滾成原本的樣子。

這裡的順序很重要：樂觀更新是「先騙一下眼睛」，reactive 查詢才是「最後的事實」。兩者搭配起來，使用者感覺是即時的，但資料的正確性仍然以後端為準。寫入時還要處理重送的風險，例如用一個 requestId 讓同一則留言重送兩次也只會存下一筆，這和上一節 publish 的 idempotent 判斷是同一個思路。

小結

Convex 的查詢是訂閱，不是問一次。後端會追蹤每個查詢讀了哪些資料，資料一被 mutation 改動，就自動重跑查詢並推給所有訂閱的前端——所以畫面不用輪詢、不用手動重抓。這個機制的前提是 query 必須是確定性的、不能有副作用，這就是 query 只管讀的原因。至於使用者按下按鈕到後端回傳之間的短暫空窗，則用樂觀更新先讓畫面反應，再讓 reactive 查詢把權威資料補上。

到這裡，你已經看懂 Convex 這一整套模型：用 schema 定義資料、寫 query 與 mutation、靠 reactive 自動更新畫面。最後一個問題回到選擇本身——什麼情況下該用 Convex，什麼情況下反而該自己寫一台 API server？下一節會用取捨與判準，幫你做出這個決定。
