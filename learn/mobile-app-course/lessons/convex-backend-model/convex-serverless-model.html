Convex 是什麼：把後端變成雲端上的函式

Step 1/5 · Convex 後端模型

學習目標

能說出 Convex 的後端心智模型：為什麼社群功能一定需要後端、convex/ 資料夾裡放什麼、query 與 mutation 各負責讀還是寫，以及為什麼開發時要同時開著 Expo 與 Convex 兩個終端。

前言：畫面都做好了，資料卻還是假的

假設你已經把 Codexgram 的介面做得有模有樣：首頁有貼文、貼文上有愛心、底下有留言、還有一個訊息分頁。你點下愛心，它變紅了；你打一句留言，它出現在列表上。一切看起來都很正常，於是你拿另一支手機打開同一個畫面，想看看互動有沒有同步。

結果那支手機什麼都沒變。愛心還是空的，留言也沒出現。你才意識到，剛剛那些「成功」的互動其實只發生在這支手機的記憶體裡——關掉 app 就消失了，而且沒有任何其他人看得到。

問題不在畫面，而在畫面背後沒有東西可以存資料、可以讓不同裝置共用同一份資料。這個東西就叫後端（backend）。這一節要把 Convex 這個後端講清楚：它跟你想像中「自己開一台 server、寫一堆 API 端點」哪裡不一樣，以及它在你的專案裡實際長什麼樣子。

為什麼社群功能一定需要後端

先不要想技術，先想你這個 app 要完成什麼事。張三發了一篇貼文，李四要在自己的手機上看到；李四按了讚，張三的愛心數字要加一；王五留言，所有人都要能在同一篇貼文底下看到。這些需求沒有一個能在單支手機裡完成，因為資料必須離開這台裝置，放到一個大家都能連到的地方。

歸納起來，後端要負責三件事。第一是存資料：貼文、按讚、留言、追蹤、私訊，都要有一份持久的紀錄，不能關掉 app 就消失。第二是跨裝置同步：不同人、不同手機看到的是同一份事實，而不是各自記各的。第三是跑需要信任的邏輯：誰有權刪這篇貼文、這個上傳是不是真的屬於你，這些判斷不能交給手機端自己講，必須在後端驗證。

所以當 Codexgram 的介面做完、要接上真的功能時，你會需要一個地方放資料庫和這些邏輯。傳統做法是自己寫一個 API server，例如用 Next.js 的 Route Handlers 開幾個端點，手機端再一支一支去呼叫。Convex 提供的是另一種選擇。

Convex 換掉的不是資料庫，是「端點」

Convex 是一套託管的後端服務。它幫你保管資料庫，但它真正改變你工作方式的地方，是你不用再自己設計 REST 端點。在傳統架構裡，手機端要拿貼文，你得先定義一個像 GET /api/posts 的網址，在伺服器端寫好路由、解析參數、查資料庫、組成 JSON 回傳，最後在手機端寫 fetch 和型別。每一個功能都要這樣繞一圈。

在 Convex 裡，你把這些邏輯寫成一個一個的函式，放進 convex/ 資料夾。例如有一個函式叫 api.posts.list，手機端不是去打一個網址，而是直接呼叫這個函式名稱。Convex 會幫你做三件傳統架構要自己來的事：把這些函式部署到雲端、根據你的定義自動產生型別、以及把查詢變成即時訂閱。你寫的是「這個功能要讀什麼、要寫什麼」，不是「這個端點要怎麼接」。

打個比方：傳統 API server 像是自己開一間店，從租店面、接水電、到畫菜單全部自己來；Convex 比較像進駐一間已經有水電和櫃檯的商場，你只要把「賣什麼、怎麼做」寫成一份份菜單放進去就好。要注意的是，商場幫你處理的是行政和維運，菜單的內容與邏輯還是你的責任，所以資料長什麼樣、誰能做什麼，仍然由你決定。

動手時你會看到的兩個終端

實際開始用 Convex 時，流程是這樣：在專案裡安裝套件後，執行 npx convex dev。第一次執行會要你登入、建立一個新專案，然後把你本機 convex/ 資料夾裡的程式碼部署到雲端。這個 convex dev 指令會一直開著，監看你對 convex/ 的每一次修改，一存檔就自動重新部署。

這就是為什麼從這裡開始，你會有兩個終端同時在跑：一個跑 Expo 的開發伺服器，負責手機 app 那一側；另一個跑 convex dev，負責後端那一側。很多人第一次用會忘記開第二個終端，然後納悶為什麼改了後端程式碼卻沒生效。只要記得「後端要有人幫你部署」，就不會漏掉它。

第一次啟動時，Convex 還會問你要不要產生一些 AI 輔助檔案，例如 agents.md 和一份 Convex 的寫法指南。這些檔案是給你的 coding agent 讀的，讓它知道這個版本的 Convex 有哪些規則、不要用憑印象寫出過時的寫法。實務上建議讓它生成，因為後端最容易出錯的地方就是「用舊習慣寫新工具」。

convex/ 資料夾裡有什麼

部署完成後，你的專案根目錄會多出一個 convex/ 資料夾。它就像是這個 app 的後端程式碼總部，幾個主要成員如下。

schema.ts 定義資料庫裡有哪些表、每張表有哪些欄位與索引，是整個後端的資料骨架。其他以功能命名的檔案，例如 posts.ts、social.ts、messaging.ts，則是各自功能的 query 與 mutation。你可能也會看到 lib/ 放共用的小工具，例如權限檢查與回傳格式。_generated/ 是 Convex 自動產生的檔案，內含型別與 API 對照表，不要手動去改它。之後談身分驗證時會用到的 auth.config.ts，也會放在這一層。

一個很直觀的重點是：這些後端檔案就是普通的 TypeScript 檔，放在你的 repo 裡、可以版控、可以讓 agent 讀。它不是一個黑盒子服務，你看得到裡面每一行。

query 與 mutation：讀與寫的兩種函式

Convex 的函式最常見的有兩種。query（查詢）負責讀資料，例如「給我首頁的貼文」或「這篇貼文有幾則留言」。它不能修改資料，你也不該在裡面做寫入。mutation（變更）負責寫資料，例如建立貼文、按讚、新增留言、追蹤某人。它會修改資料庫，而且整段執行會以交易的方式完成，中間出錯就整批回滾。

面向query（查詢）mutation（變更）
做什麼讀取資料新增、修改、刪除資料
能不能寫入不行可以
典型例子取得貼文列表、讀取留言發文、按讚、追蹤、傳訊息
前端怎麼用訂閱後自動更新呼叫一次，結果觸發相關查詢更新

除了這兩種，還有兩種比較進階的函式。action（動作）用在需要對外呼叫的場合，例如去打第三方 API，因為它不能直接讀寫資料庫，要做資料操作得再呼叫 query 或 mutation。internal（內部）函式則是不能被手機端直接呼叫的版本，只能由後端自己互相呼叫，適合放清理、排程這類不該對外開放的工作。這一節先記住 query 與 mutation 的差別就夠，action 和 internal 之後會在不同功能裡再遇到。

小結

社群功能需要後端來存資料、跨裝置同步，並在可信的一端執行邏輯。Convex 是一套託管後端，它把「自己開端點」換成「把函式放進 convex/」：query 負責讀、mutation 負責寫，Convex 幫你部署、生成型別、把查詢變成即時訂閱。開發時要同時開著 Expo 與 convex dev 兩個終端，後端程式碼就是 repo 裡普通的 TypeScript 檔。
