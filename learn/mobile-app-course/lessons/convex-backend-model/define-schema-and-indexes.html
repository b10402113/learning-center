用 schema.ts 定義資料模型與索引

Step 2/5 · Convex 後端模型

學習目標

能讀懂 Convex 的 schema.ts：用 defineTable 與 validator 定義每張表，用索引與複合索引支撐查詢，並說出為什麼要避免無界陣列、以及 denormalized counter 在 Convex 裡為什麼幾乎是必要的。

前言：先決定資料長什麼樣子，再談怎麼查

上一節我們知道 Convex 的後端是由一堆函式組成的，query 負責讀、mutation 負責寫。但你很快就會撞到一個更前面的問題：這些函式到底在讀什麼、寫什麼？貼文有哪些欄位？按讚要記哪幾筆資料？如果資料的樣子沒先講清楚，那查詢和寫入根本無從下手。

在傳統的關聯式資料庫裡，你可能習慣用圖形介面點一點建表，或另外寫一段 SQL migration。Convex 走的是「schema 即程式碼」這條路：所有的資料表、欄位、索引，都寫在一個叫 schema.ts 的檔案裡。這一節要把這個檔案讀懂，尤其是「為什麼有些欄位看起來冗餘、卻非留不可」這件事。

用 defineTable 描述一張表

打開 convex/schema.ts，你會看到兩個主要的匯入：defineSchema 和 defineTable 來自 convex/server，而 v 來自 convex/values。整個檔案的骨架，就是把 defineSchema 交給一份物件，物件的每個鍵是一張表，值則是那張表的欄位定義。

以貼文這張表為例，它大致長這樣：

posts: defineTable({
  seedKey: v.optional(v.string()),
  authorId: v.id('profiles'),
  uploadId: v.id('uploads'),
  storageId: v.id('_storage'),
  kind: mediaKind,
  width: v.number(),
  height: v.number(),
  duration: v.optional(v.number()),
  caption: v.string(),
  likesCount: v.number(),
  commentsCount: v.number(),
}).index('by_seedKey', ['seedKey']).index('by_authorId', ['authorId']),

每個欄位後面接的那個 v.string()、v.number() 或 v.id('profiles')，叫做 validator（驗證器）。它同時做兩件事。第一，它是型別的來源：Convex 會根據這些定義，知道你查出來的 post 物件有哪些欄位。第二，它是執行期的守門員：任何寫入這張表的 mutation，如果欄位型別不對，寫入就會被擋下來。這跟純靠 TypeScript 型別不一樣，因為 TypeScript 型別在程式跑起來之後就消失了，validator 還留在後端幫你檢查。

幾個常見的 validator 可以這樣理解：v.string() 是字串，v.number() 是數字，v.boolean() 是布林，v.id('profiles') 是「指向 profiles 表某一筆的識別碼」，v.optional(...) 表示這個欄位可以不存在。你也可以像 Codexgram 那樣自訂一個共用 validator，例如把圖片或影片的格式定義成一個 union，讓多張表共用同一套定義。

為什麼欄位裡看不到陣列？

如果你翻遍 schema.ts，會發現像「這篇貼文的所有留言」或「這個人的所有追蹤者」這種資料，都不是用陣列欄位存的，而是各自獨立成一張表，例如 comments、follows。這是一個刻意的設計。

在 Convex 裡，一筆文件如果帶了一個會不斷長大的陣列，問題會很嚴重。每次有人留言，你都要把整篇貼文的文件讀出來、把新留言塞進陣列、再整份寫回去。留言越多，這份文件越大，每次寫入就越慢，而且兩則同時進來的留言還可能互相覆蓋。這種「長度沒有上限的陣列」是 Convex 文件明講要避免的。正確的做法是把留言拆成自己的表，用欄位指向它屬於哪篇貼文，這樣新增一則留言就是單純插一筆小資料。

索引：讓查詢不必掃過每筆資料

假設 comments 表裡有一百萬則留言，現在你要查「某篇貼文底下的所有留言」。如果你只能從第一筆讀到最後一筆、逐筆檢查它屬於哪篇貼文，那會非常慢。索引（index）就是為了解決這件事：它替某個欄位另外建一份排序好的對照表，讓你能直接跳到符合條件的那一段。

在 schema 裡宣告索引，就是在表的後面接上 .index('索引名稱', ['欄位'])。例如貼文表用 .index('by_authorId', ['authorId'])，讓「查某個作者的所有貼文」可以直接從索引定位。Convex 官方的寫法指南有一條原則叫「prefer indexes over filters」：能用索引就用索引，不要讓查詢先把資料撈出來再用 filter 篩。你可以把索引想成書的目錄，沒有目錄，你只能一頁一頁翻；有了目錄，你直接翻到要的那一章。

複合索引：一組欄位合起來當條件

很多查詢的條件不只一個欄位。例如「我對這篇貼文按過讚了嗎」，需要同時比對 userId 和 postId。這種時候就適合用複合索引，也就是把多個欄位綁進同一個索引：

likes: defineTable({ userId: v.id('profiles'), postId: v.id('posts') })
  .index('by_userId_and_postId', ['userId', 'postId'])
  .index('by_postId', ['postId']),

by_userId_and_postId 這個複合索引，讓「同時指定某個使用者和某篇貼文」的查詢很快。它在社群 app 裡還有一個常見用途：搭配只取一筆的查詢，讓「同一個人對同一篇貼文只能有一筆讚」變成可檢查的規則。做法是先照這組索引去查，如果查到一筆，就表示已經按過讚，不要再插一筆。索引本身不會像關聯式資料庫那樣自動擋重複，真正把重複擋下來的是「先查再寫」這個動作；但有了複合索引，這個檢查才夠快、才能在交易裡安全地完成。同樣的手法也用在「一個人只能追蹤另一個人一次」。

除了複合索引，還有一種搜尋索引。以 profiles 表為例，它把使用者名稱、姓名、簡介等文字合併成一個 searchText 欄位，然後對這個欄位建立 searchIndex：

profiles: defineTable({
  // ...其他欄位
  searchText: v.string(),
}).searchIndex('search_profiles', { searchField: 'searchText' }),

有了這個搜尋索引，探索頁那種「輸入關鍵字找人」的功能才能實作。要注意的是，搜尋走的是文字比對，跟前面那種精確比對的索引是不同用途。

Denormalized counter：為什麼數字要重複存一份

看到 posts 表裡的 likesCount、commentsCount，或 profiles 表裡的 followersCount，你可能會想：這些數字不是可以從 likes、comments、follows 那幾張表數出來嗎？為什麼要多存一份，而且還要自己維護、冒著對不上的風險？

原因是 Convex 的查詢模型。一個 query 的執行速度，最好和各表資料量無關；如果你每次顯示貼文都要去 likes 表數「這篇有幾個讚」，那貼文一多，讀取就會拖慢。把計數直接存成貼文文件上的一個欄位，前端讀貼文時順便就拿到數字，速度是固定的。這種「把可以算出來的結果先存起來」的做法叫 denormalization（反正規化），而存下來的欄位就叫 denormalized counter。

它的代價是你必須在每次按讚或取消讚時，同時更新這個計數。所以 mutation 裡常會看到「插入一筆 like，然後把貼文的 likesCount 加一」這兩個動作綁在一起。這裡的設計原則很簡單：計數是拿來讀的、是快取的性質，真正的事實仍然是 likes 表裡的那幾筆資料；萬一哪天數字對不上，以明細為準。

小結

schema.ts 是 Convex 後端的資料骨架，用 defineTable 與 validator 定義每張表的欄位與型別。查詢要用索引，複合索引處理多欄位條件；文字搜尋另用 searchIndex。不要把會無限成長的資料塞成陣列欄位，要拆成獨立表。像按讚數、追蹤數這種可算出來的數字，要故意多存一份 denormalized counter，換取穩定的讀取速度，但記得在寫入時同步維護它。
