Convex 或自寫 API server：怎麼選

Step 5/5 · Convex 後端模型

學習目標

能在 Convex 與自寫 API server（例如 Next.js Route Handlers 搭配 Postgres）之間做出有理由的選擇：說清楚各自的取捨與適用條件，並用一份檢查表判斷下一個功能該用哪一邊。

前言：下一個專案，後端要怎麼開始？

前四節把 Convex 這套模型看完了：schema 定義資料、query 與 mutation 處理讀寫、reactive 查詢自動更新畫面。你可能已經覺得這套東西很好用，甚至想「以後每個 app 都用 Convex 就好」。但先別急著下結論。

同樣是這個課程，Cal AI 用的是完全不同的組合：Next.js 的 Route Handlers 當 API、Neon 的 Postgres 當資料庫、Drizzle 當 ORM，再另外用 trigger.dev 跑背景 AI 工作。Dentify 甚至還多了一個網頁 dashboard，直接讀同一份 Postgres。這些專案不是「還沒進化到用 Convex」，而是它們的需求本來就更適合自寫 API。這一節要處理的就是這個抉擇：到底什麼時候該用 Convex，什麼時候該自己寫後端。

兩條路線的取捨

先把它們並排看清楚。這裡的「自寫 API server」指的是你在 Next.js 之類的框架裡自己開端點，接上關聯式資料庫，例如 Cal AI 與 Dentify 的做法。

面向Convex 全託管後端自寫 API server + Postgres
即時更新查詢天生是訂閱，開箱即用要自己接 WebSocket 或輪詢
API 端點寫函式，不必設計路由自己定義與維護每個路由
型別同步由 validator 自動產生要自己維護前後端型別
關聯查詢用索引與反正規化，彈性較小SQL 的 join、聚合、報表隨你用
外部服務整合用 action，較受框架限制任何 Node 套件與 API 都能直接用
網頁後台共用要再經過 Convex 這一層Server Component 可直讀資料庫
維運與可攜性託管、省事，但綁定平台自己管，掌控與可搬遷性高

最直觀的分水嶺是「即時」與「查詢彈性」。如果你的功能核心是很多人同時在線、資料一動大家都要看到——聊天、動態牆、協作、通知——Convex 幫你省下的不只是打字量，而是整條即時同步的工程難題。反過來說，如果你的功能核心是複雜的資料分析，例如「上個月各地區的回購率排名」，那正是關聯式資料庫與 SQL 的強項，硬用 Convex 的索引模型去拼會又慢又痛苦。

還有一個容易被忽略的差異，是「誰要跟這份資料共用」。Cal AI 和 Dentify 都有網頁端需求：背景 task 要讀寫同一份資料、員工 dashboard 要直接查資料做報表。這種情況下，把 Postgres 當成唯一真相、讓手機與網頁都透過它工作，會比讓大家繞過一層託管服務更直接。

判別問句：問自己這幾題

不需要背哪個技術「比較好」，只要在下決定前，誠實地回答下面幾個問題。

  1. 這個功能需要多人即時同步嗎？如果使用者會盯著別人的動作看（聊天、按讚數跳動、協作編輯），Convex 的現成即時更新會替你省下大量時間。
  2. 你的查詢需要複雜的關聯、聚合或報表嗎？如果需要跨多張表統計、做排行、算趨勢，關聯式資料庫的 SQL 會比 Convex 的索引加反正規化好用得多。
  3. 你已經有一份既有的資料庫或資料倉儲要接嗎？若資料主體本來就在 Postgres 或既有的系統裡，自寫 API 直接接上去最省事；硬搬進 Convex 往往得不償失。
  4. 有沒有網頁端或背景服務要共用同一份資料？如果手機 app、網頁 dashboard、背景 task 都要讀同一份資料，讓它們都接同一個資料庫通常最單純。
  5. 會不會需要把後端搬走或做深度客製？如果未來可能換雲、或需要自己掌握底層，託管服務的綁定就要先列入考量。

把這幾題當成一條連續的光譜。愈往「即時、互動為主、快速迭代」那一端靠，Convex 的優勢愈明顯；愈往「複雜查詢、多端共用、資料既有」那一端靠，自寫 API 加關聯式資料庫愈合適。

反例：規則什麼時候會翻轉

任何「就用某個技術」的直覺都有例外，這裡舉三個常見的反例，幫你避免把判準用死。

第一個反例是「社群 app 就一定用 Convex」。如果這個社群 app 真正的價值在於推薦演算法、趨勢分析、廣告投放成效這類需要大量跨表計算的功能，那麼 Convex 的查詢模型反而會處處綁手綁腳。即時互動可以外包給 Convex，但分析型的資料處理仍可能需要另一套關聯式或分析型資料庫並存。

第二個反例是「自寫 API 比較能掌控，所以一定比較好」。如果你的功能只是聊天與動態牆，自己接 WebSocket、處理斷線重連、維護前後端即時狀態，工程成本很可能遠高於直接用 Convex。可掌控是一項優點，但優點不是免費的，它得用時間換。

第三個反例是「既然已有 Postgres，就絕對不能用 Convex」。這兩者不必然互斥。實務上常見的組合是：以即時互動為主的行動功能放在 Convex，需要長時 CPU 或對外呼叫的工作交給專門的背景任務服務，而既有資料庫繼續服務網頁後台。重點不是選邊站，而是把對的資料放在對的地方，並想清楚它們之間怎麼同步。

決策規則與檢查表

先用一句話定調：以即時互動為主、且沒有複雜 SQL 需求的新功能，預設用 Convex；牽涉複雜關聯查詢、既有資料庫、或多端共用同一份真相的功能，預設自寫 API + 關聯式資料庫。 接著用檢查表確認。
☐ 需不需要多人的即時同步？是 → 偏 Convex。
☐ 查詢有沒有大量 join、聚合、報表？是 → 偏自寫 API + SQL。
☐ 資料主體是否已經在既有的 Postgres 或其他系統？是 → 偏自寫 API。
☐ 手機、網頁、背景服務是否要共用同一份資料？是 → 偏自寫 API。
☐ 主要功能是不是即時動態與聊天？是 → 偏 Convex。
☐ 兩邊各有需求？可以並存，用背景任務或同步機制把資料接起來。

這份檢查表不是要你二選一，而是幫你在每次開新功能時，都能說出「我為什麼選這一邊」。把理由講得出來，就是這一整節要教你的能力。
