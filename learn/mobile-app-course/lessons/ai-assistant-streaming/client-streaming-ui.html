手機端逐字渲染與對話介面

Step 3/5 · 串流 AI 助理

學習目標

能用 useApiStream 邊收邊畫，分辨 JSON 分支與串流分支，並用 pending 閘門與錯誤降級避免過期回應蓋掉畫面。

前言：伺服器會串了，畫面還是空白

上一節我們把伺服器端的串流端點寫好了，它會一段一段把文字推出來。但如果手機端還是用原本那種「等整個回應結束才更新」的寫法，使用者看到的依然是轉圈圈。串流是一條水管，伺服器那一頭開了，接水的那一頭也得一邊流一邊接才行。

這一節要做的就是接水的那一頭。我們會看 useApiStream 這個 hook 怎麼發出請求、怎麼分辨「這次是錯誤 JSON 還是模型在串流」，然後回到 assistant.tsx 看畫面怎麼先把氣泡放上去、再讓尾端那一顆原地長大。動筆前你要先有一個會串流的端點，因為這裡的邏輯全是繞著它設計的。

整體順序

  1. 用 Expo 的 streamingFetch 帶著登入 token 發出請求。
  2. 先看回應的內容型別：是 JSON 就當一般回應處理，否則進入串流分支。
  3. 串流分支裡用 reader 逐塊讀，累積成目前為止的完整文字，每次回呼都送整份出去。
  4. 畫面在使用者送出時，同時放上自己的氣泡與一個空的 AI 氣泡。
  5. 每一段文字抵達時，改寫尾端那個 AI 氣泡的內容，讓它原地長大。
  6. 用 pending 當閘門，一次只允許一個請求在飛，並把載入歷史限制在進畫面時一次。
  7. 錯誤（包含伺服器的 503 文案）直接寫進氣泡，而不是跳一個對話框擋住。

第 1 步：用 streamingFetch 發出請求

手機端用 Expo 提供的 streamingFetch，而不是一般的 fetch，因為它才能讓你在回應還沒結束前就一段一段讀取 body。請求本身帶上登入 token 與 JSON 標頭，body 就是對話 id 與這句問話。

        const token = await tokenRef.current();
        const res = await streamingFetch(`${BASE}${path}`, {
          method: 'POST',
          headers: {
            ...(token ? { Authorization: `Bearer ${token}` } : null),
            'Content-Type': 'application/json',
          },
          body: JSON.stringify(body),
        });

第 2 步：先分辨 JSON 還是串流

拿到回應後，第一件事是看 Content-Type。還記得步驟 2 的設計嗎？緊急回覆與各種 503 都是 JSON，只有模型生成的那條路是純文字。所以客戶端也用同一個判準分岔。

        if (res.headers.get('content-type')?.includes('application/json')) {
          const data = await res.json().catch(() => null);
          if (!res.ok) {
            throw new ApiError(res.status, data?.error ?? 'Something went wrong', data?.code);
          }
          // The body is the other side of a network boundary, not a guarantee:
          // a proxy error page with a JSON content-type must not reach `.content`.
          if (typeof data?.message?.content !== 'string' || typeof data?.conversationId !== 'string') {
            throw new ApiError(res.status, 'The assistant sent back an unreadable reply');
          }
          onText(data.message.content);
          return data.conversationId;
        }

        const conversationId = res.headers.get('X-Conversation-Id');
        if (!res.body || !conversationId) {
          throw new ApiError(res.status, 'The assistant sent back an unreadable reply');
        }

JSON 分支裡有兩個動作要看。第一，如果狀態不是 2xx，就丟出一個帶狀態碼與錯誤代碼的 ApiError，把伺服器準備好的文案保留下來，等下在畫面上顯示。第二，就算狀態是 200，也不能直接相信 body。回應的另一頭是一個網路邊界，可能是一頁內容型別剛好標成 JSON 的代理錯誤頁。所以這裡會實際檢查 message.content 和 conversationId 是不是字串，不是就當作讀不懂的回應。

這一段的最後兩行是進入串流分支的通行證：對話 id 不在 body 裡，而在回應標頭 X-Conversation-Id；如果連 response body 都沒有，就沒得讀，直接報錯。

第 3 步：逐段讀純文字串流

確認是串流之後，用 body 的 reader 一塊一塊讀。每次讀到一塊就解碼、接在目前累積的文字後面，然後把「目前為止的完整文字」交給回呼 onText。

        const reader = res.body.getReader();
        const decoder = new TextDecoder();
        let text = '';
        for (;;) {
          const { value, done } = await reader.read();
          if (done) break;
          text += decoder.decode(value, { stream: true });
          onText(text);
        }
        return conversationId;

這裡有一個容易被忽略、但讓畫面端變得非常簡單的設計：onText 每次拿到的是「累積到現在的整份文字」，不是「這一塊的增量」。所以畫面端不需要自己拼貼增量，只要拿這份完整文字把氣泡內容覆蓋掉就好。最後函式回傳對話 id，讓呼叫端更新模組層級的 conversationId，下一輪才能接回同一串。

第 4 步：送出時，先把兩個氣泡放上去

回到 assistant.tsx 的 send()。使用者一送出，畫面不會等第一個字，而是立刻做出兩件事：加上使用者自己的氣泡，以及一個內容空白的 AI 氣泡。

  const send = async (q: string) => {
    const t = q.trim();
    if (!t || pending) return;
    setText('');
    setMsgs((m) => [
      ...m,
      { from: 'me', paras: [t], time: now() },
      { from: 'ai', paras: [], time: now() },
    ]);
    setPending(true);
    try {
      conversationId = await stream(
        '/api/ai/chat',
        { conversationId: conversationId ?? undefined, message: t },
        setReply
      );
    } catch (err) {
      setReply(err instanceof Error ? err.message : 'Something went wrong.');
    } finally {
      setPending(false);
    }
  };

為什麼要先放一個空的 AI 氣泡？因為答案需要有個地方「長出來」。在第一批文字抵達之前，這個空氣泡可以顯示轉圈圈；文字一到，它就變成內容的容器。第一行的 if (!t || pending) return; 看似只是防止送出空白訊息，其實它同時是最重要的競態防線，下一段會說。

第 5 步：讓尾端氣泡原地長大

每個串流區塊抵達時，回呼 setReply 會改寫最後一顆 AI 氣泡。它只換掉陣列最後一項，前面不動，所以畫面看起來就是同一顆氣泡在長大，而不是一直新增氣泡。

  /** Rewrites the trailing AI bubble — the one this turn is filling in. */
  const setReply = (content: string) =>
    setMsgs((m) => [
      ...m.slice(0, -1),
      { ...m[m.length - 1], paras: content.split(/\n{2,}/).filter(Boolean) },
    ]);

文字會依空行切成段落，所以助理回覆的兩段文字在畫面上仍然是兩段。正在串流的那顆氣泡還會多做兩件事：最後一行的尾端放一個游標，讓文字看起來是「長出來」的；以及暫時不顯示時間戳。

            {/* Caret sits on the last line, so the answer grows in front of it. */}
            {streaming && i === all.length - 1 ? (
              <Text style={{ color: A.blue }}>▍</Text>
            ) : null}

時間戳則等串流結束才出現。原始碼的理由很直白：在一則寫到一半的答案上蓋時間，是說謊，因為它其實還沒完成。

第 6 步：過期回應與競態

串流最怕的一件事，是上一輪的回應還沒結束，下一輪又開始，兩串文字互搶同一顆氣泡。這個 app 的解法很樸素：用一個 pending 狀態當閘門，一次只讓一個請求在飛。

送出前檢查 pending，輸入框在 pending 期間設為不可編輯，送出與附件按鈕也一併停用。因為新請求根本無法在使用中啟動，就不會出現「舊回應蓋掉新畫面」的情境。相關的還有載入歷史的時機：

  // Load once per mount, not on every focus: a refetch mid-stream would fight
  // the bubble being written. A failure just leaves the empty state up.
  useEffect(() => {
    call<{ conversationId: string | null; messages: StoredMsg[] }>('/api/ai/chat')
      .then((h) => {
        conversationId = h.conversationId;
        setMsgs(h.messages.map(toMsg));
      })
      .catch(() => {});
  }, [call]);

歷史只在進入畫面時抓一次，不在每次畫面重新取得焦點時抓。原因是：如果在串流進行中重新抓取，抓回來的資料會跟你正在寫的那顆氣泡打架。同樣的道理也反映在自動捲動上：內容變高時會捲到底部，但當串流進行中就不做動畫，因為每個字都觸發一次動畫會讓畫面抖動。這些小決定合起來，才讓「一次只處理一輪」這條規則真的站得住。

第 7 步：錯誤降級

最後是失敗路徑。還記得 send() 的 catch 嗎？它呼叫的是 setReply，也就是把錯誤訊息寫進那顆 AI 氣泡。這是刻意的：伺服器的 503 文案本身就有意義（例如「這個環境目前不開放助理」），用一個跳出來的對話框蓋住它，反而讓使用者得多按一下才能看到內容。把文案直接放進氣泡，使用者讀到的就是伺服器真正想說的話。

這裡也有一個例外，屬於照片附件的路徑：照片送出失敗時，因為失敗當下根本還沒放任何氣泡，沒有地方可以寫入，所以只能用一個對話框提示。這會在步驟 5 講到。

做完長什麼樣

驗收方式很直接：送出一個問題，你的氣泡立刻出現，AI 氣泡先顯示載入中，接著第一個字很快出現，文字持續補上，最後一行跟著一個游標，完成後時間戳才出現。串流期間輸入框與按鈕是停用狀態。故意把閘門關起來再送一次，錯誤文案會直接出現在 AI 氣泡裡，而不是彈出對話框。

小結

客戶端用 Expo 的 streamingFetch 發請求，先看 Content-Type：JSON 走一般分支（錯誤帶狀態與代碼、驗證 body 形狀），純文字則進入 reader 逐塊讀取。回呼 onText 送的是累積後的完整文字，畫面端因此只需覆蓋尾端氣泡。送出時先放兩個氣泡，再讓最後一顆原地長大並顯示游標；pending 當閘門、歷史只載入一次、串流期間不做捲動動畫，合起來避免過期回應互搶畫面。錯誤（含 503 文案）直接寫進氣泡。

到這裡，使用者已經能即時看到回覆了，但關掉 app 再打開，對話就消失了。下一步要處理資料層：把對話歷史持久化到資料庫，還要確保每個人只拿得到自己的那段對話。
