手機端逐字渲染與對話介面

Step 3/5 · 串流 AI 助理

學習目標

學完這一節，你應該能在 React Native 端做出逐字浮現的助理對話：用 useApiStream 送出帶有 Clerk token 的請求、一邊收字一邊更新畫面、用防重入機制避免重複送出，並處理空狀態、輸入區與錯誤降級。

前言：水管已經接好，但水龍頭還沒開

上一節把伺服器端的串流端點寫好了：它會逐段吐出助理的回答，對話編號放在 X-Conversation-Id 標頭。可是如果你現在拿一支手機打這個端點，看到的只會是一串文字慢慢出現在終端機裡——畫面還是空的。

這一節要處理的是水管的另一頭。手機端要做三件事：把請求送出去、把一段一段抵達的文字接起來、然後在畫面上讓它像有人在打字一樣長出來。前置條件是上一節的端點已經能運作，而且 app 已經有 Clerk 的登入狀態可以拿 token。

做完之後，你會有一個助理畫面：使用者送出問題後，一個空白的 AI 氣泡先出現，答案從裡面逐字長出來，最後停在完整的回覆上。

第一步：用對的 fetch，才有得讀

React Native 內建的 fetch 不支援讀取串流回應的 body。要逐段讀取，得改用 Expo 提供的版本：

import { fetch as streamingFetch } from 'expo/fetch';

這個版本的 fetch 回傳的 res.body 是一個可以 getReader() 的串流，這是整個逐字渲染的起點。如果用了錯的 fetch，你會發現 res.body 是空的，或根本沒有 getReader 可用，程式會直接壞在半路。

第二步：帶著 Clerk token 把請求送出去

助理的請求和其他 API 一樣，必須帶著登入身分。做法是從 Clerk 取出 token，放進 Authorization 標頭；token 用 ref 快取，避免每次 render 都重新取一次而讓 effect 反覆觸發。

async function stream(): Promise<string> {
  const token = await tokenRef.current();
  const res = await streamingFetch(`${BASE}${path}`, {
    method: 'POST',
    headers: {
      ...(token ? { Authorization: `Bearer ${token}` } : null),
      'Content-Type': 'application/json',
    },
    body: JSON.stringify(body),
  });

這裡沒有用 useApiClient，而是寫成一個獨立的 useApiStream。原因是它要處理的是串流，不能套用一般請求那套「等 JSON 回來」的邏輯。但也因為如此，它少了共用的錯誤回報，所以實作裡特別補上一段：助理失敗時要主動寫進 Sentry，但只記錄路徑、狀態碼、錯誤代碼與耗時，絕不記錄 prompt 或回覆內容，因為那是病患自己打的字。

第三步：先看內容型別，決定走哪條路

還記得上一節的分岔點嗎？回應可能是 JSON（錯誤、緊急訊息），也可能是純文字流（真的在生成）。手機端要自己判斷：

if (res.headers.get('content-type')?.includes('application/json')) {
  const data = await res.json().catch(() => null);
  if (!res.ok) {
    throw new ApiError(res.status, data?.error ?? 'Something went wrong', data?.code);
  }
  if (typeof data?.message?.content !== 'string' || typeof data?.conversationId !== 'string') {
    throw new ApiError(res.status, 'The assistant sent back an unreadable reply');
  }
  onText(data.message.content);
  return data.conversationId;
}

const conversationId = res.headers.get('X-Conversation-Id');
if (!res.body || !conversationId) {
  throw new ApiError(res.status, 'The assistant sent back an unreadable reply');
}

JSON 那條路很單純：如果是錯誤就丟出去，如果是正常內容（例如緊急卡片）就直接用 onText 一次交出全文。這裡有一道防線值得注意：即使內容型別是 JSON，也不代表 body 一定是我們預期的形狀——中間可能夾著代理伺服器的錯誤頁。所以檢查 message.content 與 conversationId 是不是字串，是必要的。

第四步：逐段讀，永遠回報「目前為止的全文」

純文字流這條路，就是用 reader 一段一段讀，並在每次讀到新片段時回報給畫面：

const reader = res.body.getReader();
const decoder = new TextDecoder();
let text = '';
for (;;) {
  const { value, done } = await reader.read();
  if (done) break;
  text += decoder.decode(value, { stream: true });
  onText(text);
}
return conversationId;

注意這裡累積成 text 之後，是把「目前為止的全文」交給 onText，而不是只交出這次的片段。這個設計會讓畫面端的程式碼變得非常單純：它不需要自己把片段接起來，只要把收到的字串直接畫成訊息就好。哪一端負責累積，是一個可以選擇的設計；Dentify 選擇讓 hook 累積、讓畫面變笨。

第五步：先放一個空氣泡，讓答案有地方長

送出問題時，畫面要同時把使用者的訊息和一個空白的 AI 氣泡放上去。這個空氣泡是關鍵——它是答案接下來要長進去的地方。

setMsgs((m) => [
  ...m,
  { from: 'me', paras: [t], time: now() },
  { from: 'ai', paras: [], time: now() },
]);
setPending(true);

在收到第一個字之前，這個空氣泡會顯示一顆小小的載入圖示；一旦第一個字抵達，就換成文字並開始長大。每一輪 onText 都重寫最後那個 AI 氣泡：

const setReply = (content: string) =>
  setMsgs((m) => [
    ...m.slice(0, -1),
    { ...m[m.length - 1], paras: content.split(/\n{2,}/).filter(Boolean) },
  ]);

它只動陣列裡最後一則訊息，也就是這一輪正在填的氣泡。回覆裡用連續換行分段，所以直接把字串切成一串段落交給氣泡渲染。

第六步：讓「還在寫」被看見

AI 氣泡接受一個 streaming 旗標。當這一輪還在串流時，最後一段文字的尾端會顯示一個閃爍的游標；同時，時間戳記會暫時隱藏。

{streaming && i === all.length - 1 ? (
  <Text style={{ color: A.blue }}>▍</Text>
) : null}

{/* A timestamp on a half-written answer is a lie — it lands when it lands. */}
{streaming ? null : (
  <Text className="mt-[10px] text-[12.5px]">{m.time}</Text>
)}

這兩行處理的是感受問題。游標讓使用者知道系統還在動，不是卡住了；隱藏時間是因為一段還沒寫完的回答標上時間是一種假資訊，時間要等答案落定才出現。另外，氣泡的進場動畫在串流時會被關掉——每一段文字都觸發一次動畫，會讓畫面看起來一頓一頓的。

第七步：把錯誤寫進氣泡，而不是彈窗

送出流程用 try / catch / finally 包起來。失敗時，錯誤訊息會被寫進那個已經在畫面上的 AI 氣泡；finally 則負責把 pending 關掉。

const send = async (q: string) => {
  const t = q.trim();
  if (!t || pending) return;
  // ...先把氣泡放上去
  setPending(true);
  try {
    conversationId = await stream(
      '/api/ai/chat',
      { conversationId: conversationId ?? undefined, message: t },
      setReply
    );
  } catch (err) {
    setReply(err instanceof Error ? err.message : 'Something went wrong.');
  } finally {
    setPending(false);
  }
};

為什麼不跳一個錯誤彈窗？因為伺服器回傳的 503 訊息本身就是有意義的文案，例如「這個環境目前無法使用助理」。彈窗會把它蓋在一個使用者得先關掉才能繼續的對話框裡，反而更差。把它直接寫進氣泡，使用者看得到、也能繼續讀上面的對話。

而 if (!t || pending) return 這一行，是防止使用者在等待時又按一次送出。串流還沒結束前，pending 都是 true，重複的請求就會被擋掉。這和一般列表頁用「請求序號」處理過期回應的機制不同：助理一次只有一輪在跑，用一個簡單的旗標就夠了。

第八步：歷史載入的策略也要配合串流

助理載入歷史的方式，和一般畫面不一樣。一般的資料畫面用「回到前景就重新抓」來保持最新，但助理刻意只在畫面掛載時抓一次：

// Load once per mount, not on every focus: a refetch mid-stream would fight
// the bubble being written. A failure just leaves the empty state up.
useEffect(() => {
  call<{ conversationId: string | null; messages: StoredMsg[] }>('/api/ai/chat')
    .then((h) => {
      conversationId = h.conversationId;
      setMsgs(h.messages.map(toMsg));
    })
    .catch(() => {});
}, [call]);

如果每次回到前景都重抓歷史，而使用者正好在等回覆，一次重新載入就會把你正在寫的那個氣泡蓋掉。所以策略是：進畫面時抓一次歷史就好，之後由串流自己維護畫面。載入失敗也不要彈窗，維持空狀態即可。

做完長什麼樣

完成後，這個畫面的行為可以逐項驗證：送出一句問題，空白的 AI 氣泡先出現並顯示載入指示；第一個字抵達後開始逐字成長，尾端有閃爍游標；完成後游標消失、時間出現。收到緊急訊息時，文字一次出現（因為那不是串流）。伺服器回 503 時，訊息直接寫進氣泡而不是彈窗。等待期間再按送出不會產生第二個請求。

畫面會長了，但每次重開 app 對話就消失——因為我們還沒把歷史接上去。下一步要把這條對話持久化到資料庫，讓重新打開 app 時看得到之前的往來。
