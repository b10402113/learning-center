串流回應的心智模型：為什麼 AI 助理不該只轉圈圈

Step 1/5 · 串流 AI 助理

學習目標

能講清楚逐字串流與一般 JSON 端點在資料傳輸上的差別，並說明它解決了 AI 助理體驗裡的哪個問題。

前言：你盯著的那顆圈圈

想像你打開診所 app 的 AI 助理，輸入「牙齦流血大概三天了」，然後按下送出。畫面中央開始轉圈圈。一秒、兩秒、五秒過去，你開始懷疑是不是自己網路有問題，手指已經移到關閉鍵上。就在第八秒，整段回覆忽然一次跳出來。

同樣一個問題，如果丟進 ChatGPT，感覺卻快很多。奇怪的是，兩邊用的其實是同一家模型，算一段答案所需的時間差不多。差別不在模型算得多快，而在它「什麼時候把字交出來」。這一節要建立的，就是這個心智模型：回應不一定要等整包做完才給你，它可以一邊產生、一邊送到畫面上。搞懂這件事，後面四個步驟才有意義，因為診所助理的整個技術選擇都是繞著它長出來的。

兩種回應：一次送達，還是邊產生邊送

先看一般的 API 端點。你送出請求，伺服器把資料查一查、算一算，組成一包 JSON（一種資料交換格式），然後一次送出。瀏覽器或手機的 fetch 會等到這一整包都到齊，才把 Promise 結算掉，你的程式才第一次拿到資料。在那之前，畫面上什麼都沒有。

你可以把這種模式想成叫一桌外送。廚房要等每一道菜都做好、裝箱、一起送出，餐點才會出現在你家門口。在那一刻之前，桌上完全是空的。這種模式很適合「查一份資料、算一個結果」的情境，因為答案本來就是一個完整的物件，早拿到一半也沒有意義。

串流是另一種節奏。伺服器回應的不是一個定型的物件，而是一條資料通道。它產生一小段、就推出一小段；客戶端收到一小段，就先畫一小段。這像接了一根水管：水還沒流完，但你已經可以開始喝，而不是提著一整桶水回家才喝。答案從「全部到齊才算完成」變成「先看到開頭，後面慢慢長出來」。

一般 JSON 端點串流端點
資料何時可用整包到齊才可用每一小段到就可用
回應內容型別application/jsontext/plain 或 text/event-stream
畫面能不能中途更新不能，只能等能，邊收邊畫
使用者感受先空白，再一次全部出現很快看到第一個字，然後持續增長

為什麼 LLM 特別需要串流

對「查一筆訂單」這種端點來說，串流沒有太大好處，因為資料庫一回就是完整一列，沒有「先給你一半」這種事。但大型語言模型（LLM）不一樣：它是逐個詞元（token，模型輸出的最小文字單位）生成答案的。生成一整段話，本來就是一個持續好幾秒的過程。

如果你用一般 JSON 端點包住模型，使用者感受到的延遲會是「首字時間」加上「整段生成時間」，全部加起來。回覆越長，等待越久，而且等待期間畫面完全沒動靜。串流把這段等待拆開：第一個詞元一產生就送出去，使用者零點幾秒內就看到第一個字，接下來的字陸續補上。總時間其實差不多，但「已經開始回答」的感覺完全不同。對一個放在醫療情境、使用者正在焦慮的助理來說，這個差別會直接決定它會不會被用下去。

附帶一個實務觀察：如果模型設定成最多只回兩段短文，答案很短，串流的效果看起來會不明顯，因為整段話本來就幾乎是瞬間完成。串流的價值在長回覆上最明顯。

串流在 HTTP 上長什麼樣子

串流不是什麼新協定，它就是 HTTP 回應的一種型態。伺服器不把 Content-Length 寫死，而是用分塊傳輸（chunked transfer）一段一段送出，連線保持開著，直到伺服器說結束。常見有兩種做法：一種是 SSE（Server-Sent Events，伺服器推送事件），內容型別是 text/event-stream，每一則訊息有固定的欄位格式；另一種是直接送純文字，內容型別是 text/plain。

這個診所 app 選了後者。為什麼？因為手機端根本不需要事件來源解析器，它只是要把文字一段一段接到畫面上，沒必要多一層格式包袱。原始碼裡把這個決定寫得很清楚：

 * Turns a chat-completion stream into a plain-text response body: raw deltas,
 * no SSE framing, because the phone has no event-source parser and does not
 * need one. `onDone` receives the assembled reply BEFORE the stream closes, so
 * persistence cannot be lost to the response finishing first — but a failure to
 * persist never takes the delivered answer with it.

這段註解同時透露另一個重點：串流結束之前，伺服器會先拿到拼好的完整回覆，用來存進資料庫。所以「顯示給使用者」和「保存歷史」是兩件事，可以在同一條串流裡各走各的。這個安排會在步驟 2 和步驟 4 再展開。

一個關鍵取捨：不是每個分支都能串

串流不是萬靈丹，也不是每個回應都該用它。在這個助理裡，只有「模型正在生成答案」這一條路走串流；其他情況，包括緊急狀況的制式回覆、環境沒設定好、外送未經核准，全部維持原本的 JSON 一次送出。

原因很直覺。緊急回覆是一段固定的文字，內容每次完全相同，沒有任何「邊產生」可言，而且它必須在模型之前就決定、不依賴模型，用串流只是多繞一圈。錯誤則需要攜帶結構化欄位，例如錯誤代碼，用 JSON 才放得下。把這兩類和串流分開之後，客戶端就能靠回應的內容型別判斷自己拿到的是哪一種：看到 application/json 就當一般回應處理，看到純文字就當作正在串流的答案。這個判斷會是步驟 3 的核心。

小結

一般 JSON 端點要等整包資料到齊才交出來，串流則是一產生就送、客戶端邊收邊畫。LLM 逐詞元生成、耗時好幾秒，如果等到整段完成才顯示，使用者會先面對一段沒動靜的空白；串流把首字時間和總生成時間拆開，讓「已經開始回答」的感覺提早出現。這個 app 用純文字串流、不用 SSE 格式，並且只讓模型生成那一條路串流，緊急回覆與錯誤仍走 JSON，讓客戶端用內容型別分辨兩者。
