串流回應的心智模型：為什麼 AI 助理不該只轉圈圈

Step 1/5 · 串流 AI 助理

學習目標

學完這一節，你應該能說清楚兩件事：為什麼 AI 助理的回應要用逐字串流，而不是轉圈圈等到整包好再顯示；以及串流發生在請求／回應邊界的哪一層，為什麼它和一般回傳 JSON 的端點根本不是同一種東西。

前言：一個讓人想直接關掉 app 的等待

想像你在 Dentify 的助理畫面裡打了一句「我牙齦這幾天一直流血，是什麼原因？」。按下送出之後，畫面只出現一顆轉圈圈的載入圖示。你盯著它，一秒、兩秒、五秒……。

其實模型早就開始思考了，甚至在第三秒就吐出了第一個字。問題是這個端點的回應方式，讓那些字全部卡在伺服器裡，要等整段話都生成完、包成一份完整的 JSON，才一次送到你手機上。你在等的不是模型，而是「整包一起送」這個設計。

把等待從十幾秒縮短成一兩秒當然有幫助，但真正的關鍵不是變快，而是改變等待的形狀：讓字一個一個浮出來。這一節先不寫程式，先把「逐字串流到底是什麼、它改變了哪條界線」講清楚，因為後面四個步驟的每一段程式碼，都建立在同一個畫面上。

先分清楚兩種回應：一次送完，還是邊產邊送

一般的 API 端點，例如「取得我的預約清單」，走的是同一個節奏：伺服器把資料準備好、組成一份 JSON、設定好狀態碼與標頭，然後一次性送出。對手機來說，這個回應就是一個完整、可預期的物件；拿到之後 res.json() 解析一下就有結果了。

這種模型的前提是「答案可以先準備好」。但 LLM 的回答不是查表查出來的，而是模型一個 token（詞元）接著一個 token 生成出來的。你可以把模型想成一個很會寫字但寫得慢的人：它不是先想好整段再抄給你，而是邊想邊寫，寫完一個字才想下一個字。既然答案本來就是一點一點長出來的，硬要等全部寫完才交出去，就等於把已經寫好的字通通鎖在抽屜裡。

串流做的事，是把伺服器的回應體從「一個寫死的字串」換成「一條隨時可以再塞東西進來的水管」。模型吐出一個字，水管就送一個字；手機那一端則是每收到一點就更新畫面。這是兩個截然不同的傳輸形狀，不是同一個東西調快或調慢。

串流的界線在哪一層：內容型別是分岔點

要聽懂後面的實作，得先記住一個判別依據：這個端點這次回的是 JSON，還是一條純文字流？

回應型別什麼時候出現client 怎麼處理
application/json錯誤、助理未設定、被擋下、緊急訊息當普通物件一次讀完
text/plain模型真的開始生成、要逐字送出用 reader 一段一段讀、邊讀邊更新

在 Dentify 的實作裡，這個分岔是刻意保留的。所有「還沒碰到模型」的分支——設定缺失、被環境關掉、偵測到緊急狀況——都仍然回傳 JSON，而且內容很短、沒有什麼好串的。只有當請求真的通過了層層關卡、要送進模型時，回應才會變成 text/plain; charset=utf-8 的串流。所以客戶端只要看內容型別，就能判斷這次拿到的是「一則通知」還是「一段正在長出來的回覆」，兩邊的程式碼走不同條路。

這裡有個容易忽略的細節：串流的回應沒有 JSON 的欄位可以放對話編號，所以 Dentify 把它放進標頭 X-Conversation-Id。這也提醒你，串流不是「把 JSON 換成另一種 JSON」，而是換了一種完全不同的回應體。

為什麼不用 SSE 或 WebSocket

你可能聽過另外兩種常見的「即時」做法：Server-Sent Events（SSE，伺服器推送事件）與 WebSocket（全雙工長連線）。它們確實也能做到逐字送出，但用在這個場景有點殺雞用牛刀。

SSE 會替每一段資料加上事件的框線格式，而且需要有對應的事件來源解析器；WebSocket 則要另外維護一條長連線與連線狀態。相較之下，這個助理的需求很單純：使用者送出一句話，伺服器在同一個請求裡把回覆的字流回來，結束就斷開。這種「一次請求、串流回應」的形狀，用一般的 HTTP 回應體就夠了，不需要額外的長連線，也不需要一個事件解析器。Dentify 的選擇就是把模型的原始輸出直接寫進純文字流，讓手機端一行 reader 迴圈處理完。

串流改變的不只是速度，還有三個地方

第一個是等待的感受。就算總時間一樣，先看到第一個字、再看到它慢慢長成一句話，和盯著一顆轉圈圈圖示十秒，心理感受差距很大。Dentify 的助理還特別加了一個閃爍的游標，讓「還在寫」這件事被看見，而不是讓使用者懷疑程式是不是壞了。

第二個是錯誤的時機。非串流的端點，錯誤一定發生在「還沒開始回」的時候，所以很單純。串流則可能在傳到一半才出錯——例如模型生成到一半、連線斷了。這件事逼你決定：已經送到使用者眼前的半段話，要保留還是丟掉？Dentify 的答案是保留，因為那些字對使用者已經有意義了；錯誤只寫進 log，不會把整個回應炸掉。

第三個是持久化的順序。既然回應邊產生邊送，那「把這輪對話寫進資料庫」就不能等串流結束後才做，否則回應一旦先關閉，這輪可能就來不及存。因此實作把「存檔」安排在關閉串流之前，確保歷史不會漏掉這一輪。

串流不是萬靈丹：什麼時候它幫不上忙

有兩種情況，串流看起來很多餘。第一種是回覆本來就很短。Dentify 的系統提示要求助理最多回答兩個短段落，所以當問題簡單時，模型可能幾乎是瞬間就吐出全部內容，你根本感覺不到「逐字」——這不是串流沒生效，而是沒有足夠的字可以慢慢流。

第二種是工作根本不需要使用者在線等。如果某件事要跑好幾分鐘、又容易失敗，正確的做法是把它丟到背景任務，讓使用者先離開、稍後再回來看結果。串流適合的是「使用者正在等、而且答案可以邊想邊給」的互動；需要長時間運算、或要在背景重試的工作，屬於另一個節點的主題。分清楚這兩種，才不會把所有 AI 功能都硬做成串流。

小結

一般端點是「答案準備好再一次送出」，而 LLM 的答案本質上是一點一點生成的，串流就是把這兩件事對齊：答案是水管，不是箱子。實作上用回應型別當分岔點——還沒碰到模型的錯誤與緊急訊息走 JSON，真正要生成的回覆走 text/plain 串流，對話編號改放標頭。串流不只讓等待感覺更短，也改變了錯誤處理與持久化的時機。

心智模型建立好了，但界線還停在紙上。下一步要把這條水管接到真的 AI 上：在 Next.js 的 Route Handler 裡，用領域 system prompt 框住助理、在模型之前先攔下緊急訊息、用一個預設關閉的傳輸閘門決定要不要送 OpenAI，最後把模型的輸出轉成一條純文字流。
