圖片附件：存進 ImageKit 的助理回合

Step 5/5 · 串流 AI 助理

學習目標

能完成照片上傳的助理回合：上傳前先確認對話歸屬、照片不送進模型、回覆用固定文案，並用 ImageKit 的模糊轉換做點擊才顯示的縮圖。

前言：有些狀況，用文字講不清楚

上一節我們把對話歷史存進資料庫了，使用者可以放心地聊。但有些狀況光靠打字很難描述，例如「牙齒上這個黑黑的是什麼」。使用者很自然會想拍張照傳給助理看。這時候如果照著一般做法把圖片丟給模型，會踩到一個問題：這個助理的 system prompt 明文禁止解讀影像，而一張照片加上「這是什麼」丟給看不到圖的模型，它只會編一個答案出來。

所以圖片附件這條路徑，從一開始就設計成不會經過模型。它是一條獨立的端點：把照片存進私有儲存，然後回一段固定文案。這一節會依序處理四件事：照片怎麼在上傳前縮小、上傳前怎麼確認歸屬、為什麼照片不進模型、以及那份「同一張檔案、兩種渲染」的模糊縮圖怎麼做。動手前你需要一個已設定好的 ImageKit 帳號與環境變數，以及步驟 4 的對話 resolver。

整體順序

  1. 從相簿挑照片，縮小後包成一個可以被上傳讀取的檔案。
  2. 呼叫附件端點，先確認對話歸屬，再上傳照片到私有資料夾。
  3. 寫入兩個回合：使用者的空內容照片回合，與助理的固定回覆。
  4. 上傳走伺服器，而不是讓手機直傳 ImageKit。
  5. 同一個檔案用 ImageKit 轉換產生模糊與完整兩個簽章網址。
  6. 手機端用這兩個網址做「點擊才顯示」，並在照片路徑失敗時用對話框提示。

第 1 步：挑照片、縮圖、包成可讀的檔案

先從相簿取得照片。挑選之後，重點是「在離開手機之前就縮小」，而不是等上傳到伺服器才處理。相機原圖動輒好幾 MB，手機網路不一定撐得住，而且最後也只是顯示在一個手機大小的氣泡裡。

export async function pickPhotos(limit = 1): Promise<PickedPhoto[]> {
  const picked = await ImagePicker.launchImageLibraryAsync({
    mediaTypes: ['images'],
    allowsMultipleSelection: limit > 1,
    selectionLimit: limit,
  });
  if (picked.canceled) return [];
  …
}

縮圖的邏輯另外寫在 shrink()：把寬度壓到不超過 1400 像素，再以 JPEG、品質 0.7 存檔。用 Math.min 是為了避免把一張本來就小的照片放大成更大的檔案。整個縮圖還被包在 .catch() 裡：縮圖只是最佳化，不是關卡，遇到不支援的格式時，原圖仍應該被送出去，讓伺服器去檢查型別與大小。

async function shrink(asset: ImagePicker.ImagePickerAsset) {
  const rendered = await ImageManipulator.manipulate(asset.uri)
    .resize({ width: Math.min(MAX_UPLOAD_WIDTH, asset.width || MAX_UPLOAD_WIDTH) })
    .renderAsync();
  return rendered.saveAsync({ compress: 0.7, format: SaveFormat.JPEG });
}

最後要包成一個可以上傳的檔案。這裡不能用 React Native 常見的 { uri, name, type } 描述物件，因為這個情境用的 fetch 是 Expo 的實作，它得能真的讀到位元組，遇到只能回傳路徑的物件會直接丟錯。所以要改用 Expo 的 File，它本身就帶著檔名與型別。

      // NOT React Native's `{ uri, name, type }` descriptor: `fetch` here is
      // Expo's, which builds the multipart body in JS and can only read a part
      // it can get bytes out of — a uri it would have to go to the filesystem
      // for throws `Unsupported FormDataPart implementation`. `File` is that
      // readable part, and it carries the name and `image/jpeg` with it.
      return { uri: jpeg.uri, file: new File(jpeg.uri) };

第 2 步：上傳前先確認對話歸屬

照片送到伺服器端的附件端點後，第一個動作不是存檔，而是確認這串對話真的是這位使用者的。順序很重要：先確認歸屬，再上傳檔案。

export const POST = route(async (req: Request) => {
  const user = await requireAuth();

  const form = await req.formData().catch(() => null);

  // Conversation first: `getOrCreateConversation` is what enforces that the id
  // belongs to this user, and it throws when it does not. Uploading before that
  // check leaves a private file in ImageKit that no row will ever reference.
  const conversationId = form?.get('conversationId');
  const conversation = await getOrCreateConversation(
    user.id,
    typeof conversationId === 'string' && conversationId ? conversationId : undefined
  );

  const path = await uploadPrivateImage(form?.get('photo'), photoFolder(user.id));

為什麼不能顛倒？因為上傳會真的在 ImageKit 留下一個私有檔案。如果先上傳、後檢查，結果發現對話不屬於這個人而中止，那個檔案就變成一個沒有人引用的孤兒，而且還是私有檔案，很難清理。先驗證歸屬，就等於先確定「這次上傳一定會有一列資料指向它」。

第 3 步：照片不進模型，回覆是固定的

檔案存好之後，寫入兩個回合：使用者的照片回合（內容是空的，只有圖片路徑），以及助理的固定回覆。

  // Empty content on purpose: it is the column the model reads as the patient's
  // turn, and there is no text here. ../chat/route.ts drops blank turns from the
  // history it sends, so the photo leaves no hole in the prompt.
  await db.insert(aiMessages).values([
    { conversationId: conversation.id, role: 'user', content: '', imagePath: path },
    { conversationId: conversation.id, role: 'assistant', content: PHOTO_REPLY },
  ]);

  return json({
    conversationId: conversation.id,
    image: signedPhoto(path),
    reply: PHOTO_REPLY,
  });

PHOTO_REPLY 是一段寫死的文字，不是模型生成的。理由跟緊急卡片一樣：system prompt 禁止解讀影像，而把一個「看不到卻要回答」的回合交給模型，它一定會編出內容。與其讓它猜，不如老實說「我沒辦法幫你看照片」。

/**
 * The reply to a photo. Hard-coded and never generated, for the same reason the
 * emergency card is: the system prompt forbids interpreting an image, and a
 * model asked to answer a turn it cannot see will invent something. The photo
 * itself never reaches OpenAI — it is stored and shown in the thread only.
 */

照片回合的 content 刻意留空，是因為 content 正是模型讀到的「病患這一輪」。如果塞一段像「（使用者傳了一張照片）」的文字，等於在騙模型說有人講了這句話。留空，並且讓聊天端點在組歷史時濾掉空白回合（步驟 2 做過），就不會在 prompt 裡留下一個說不通的洞。

也因為這是一條完整、不經模型的回合，所以附件端點不需要串流。它一次把圖片網址與固定回覆用 JSON 回傳，前端直接放上兩個氣泡就完成了。

第 4 步：上傳走伺服器，而不是手機直傳

這裡的檔案是從伺服器端上傳到 ImageKit 的，不是讓手機直接把位元組送到 ImageKit。這個選擇有明確的安全理由，原始碼把上傳函式寫成這樣：

export async function uploadPrivateImage(file: unknown, folder: string): Promise<string> {
  if (!(file instanceof File)) throw badRequest('No photo attached');

  const ext = TYPES[file.type];
  if (!ext) throw badRequest('That file type is not supported — send a photo.');
  if (file.size === 0) throw badRequest('That photo is empty.');
  if (file.size > MAX_BYTES) throw badRequest('That photo is too large.');

  const uploaded = await imagekit().upload({
    file: Buffer.from(await file.arrayBuffer()),
    fileName: `photo.${ext}`,
    folder,
    isPrivateFile: true,
    useUniqueFileName: true,
  });
  return uploaded.filePath;
}

如果是讓手機直接上傳，通常會用 ImageKit 的「已簽章參數」流程。問題在於：那個簽章只授權「一次上傳」，卻不限定「傳到哪裡」。資料夾、是否私有、檔名這些欄位都跟著手機端的請求走，等於任何已登入的病患都能把檔案寫到媒體庫的任何位置，包含覆蓋公開的牙醫照片。走伺服器端，這些設定才是我們能控制的。

幾個小地方也一起看：型別判斷用的是資料庫裡宣告的 MIME 型別，而不是客戶端給的檔名，避免拿副檔名做文章；isPrivateFile: true 讓檔案沒有簽章就打不開；useUniqueFileName: true 讓客戶端無法決定儲存路徑，因此沒有可穿越的路徑、也沒有可覆蓋的檔名。檔案大小上限訂在 4MB，低於部署平台的請求限制。

第 5 步：一份檔案、兩個渲染

照片顯示的時候有兩種樣子：平常是模糊的縮圖，點一下才顯示完整版。很多人會以為這是上傳了兩份檔案，其實不是。ImageKit 可以在「交付」時對同一個檔案做轉換，這個 app 用 signedPhoto() 一次簽出兩個網址。

export function signedPhoto(path: string): SignedPhoto {
  const ik = imagekit();
  const sign = (transformation: Record<string, string>[]) =>
    ik.url({ path, transformation, signed: true, expireSeconds: URL_TTL_SECONDS });

  return {
    blurred: sign([{ width: '400', blur: '40' }]),
    full: sign([{ width: '1200' }]),
  };
}

blur: '40' 是一種高斯模糊半徑，而且它排在縮小之後，所以是「先縮小、再模糊」，比對整張大圖模糊更便宜、也更難還原。因為 ImageKit 連轉換字串也一起簽章，模糊版與完整版是同一份檔案的兩個「各自簽章的渲染」，不是兩次上傳。

要特別記得：模糊只是隱私屏障，不是權限控制。它是防旁邊的人瞄到、或快速滑過時看到，真正保護照片的其實是它所在的私有資料夾與網址上的簽章。原始碼也提醒，如果哪天要防的是「鐵了心要看的人」，就必須改成第二次請求才把完整版交出去。

第 6 步：手機端的顯示與揭示

手機端拿到的是一組 { blurred, full }。畫面用一個布林狀態記住是否已揭示，點一下在兩者之間切換，因為兩個網址早就都拿到了，切換時不需要再抓任何東西。

function PhotoAttachment({ photo }: { photo: Photo }) {
  const [revealed, setRevealed] = useState(false);

  return (
    <Pressable
      onPress={() => setRevealed((r) => !r)}
      …
      <Image
        source={{ uri: revealed ? photo.full : photo.blurred }}
        style={{ width: 221, height: 221, backgroundColor: '#CFE4F2' }}
        contentFit="cover"
        transition={160}
      />

未揭示時，畫面還會蓋上一層「Tap to view」的提示，讓使用者知道可以點。送出流程則和傳文字不同：它用 FormData 帶上對話 id 與檔案，並把逾時拉長到 60 秒，因為行動網路上傳照片本來就比一般請求久。

  const attach = async () => {
    if (pending) return;

    setPending(true);
    try {
      const [photo] = await pickPhotos();
      if (!photo) return;

      const form = new FormData();
      if (conversationId) form.append('conversationId', conversationId);
      form.append('photo', photo.file);

      const sent = await call<{ conversationId: string; image: Photo; reply: string }>(
        '/api/ai/attachments',
        { method: 'POST', body: form, timeoutMs: UPLOAD_TIMEOUT_MS }
      );

      conversationId = sent.conversationId;
      setMsgs((m) => [
        ...m,
        { from: 'me', paras: [], time: now(), photo: sent.image },
        { from: 'ai', paras: sent.reply.split(/\n{2,}/).filter(Boolean), time: now() },
      ]);
    } catch (err) {
      // Nothing was added to the thread, so unlike `send` there is no bubble to
      // write the failure into — a dialog is the only place left for it.
      Alert.alert('Could not send the photo', err instanceof Error ? err.message : 'Try again.');
    } finally {
      setPending(false);
    }
  };

注意 catch 那一段：照片失敗時用的是 Alert，而不是像文字回覆那樣把錯誤寫進氣泡。差別在於，文字送出時畫面上已經先放了一個空氣泡可以承接錯誤；照片失敗時根本還沒放任何氣泡，沒有地方可以寫，就只能用對話框提示。這正是步驟 3 留下來的那個例外。

做完長什麼樣

驗證方式：在助理畫面按相機鈕、選一張照片，畫面上先出現你的照片氣泡與助理的固定回覆。照片一開始是模糊的，點一下才變清楚，而且切換時不會重新載入。重新開啟 app，照片與那則回覆都還在，因為它們已經跟著訊息存進資料庫。若把圖片網址硬打開，沒有簽章會被拒絕；換一個帳號，也拿不到別人的照片。

小結

圖片附件是一條不經模型的獨立回合。手機端先 pickPhotos，在裝置上縮到寬 1400 以內、JPEG 品質 0.7，並用 Expo 的 File 包成可讀取的檔案。上傳到附件端點後，先確認對話歸屬，再走伺服器端上傳到私有資料夾（型別依 MIME 判斷、私有、唯一檔名、上限 4MB），接著寫入空內容的照片回合與固定的 PHOTO_REPLY。最後用 signedPhoto() 對同一份檔案簽出模糊（寬 400、模糊 40）與完整（寬 1200）兩個網址，前端靠狀態切換顯示；模糊是隱私屏障，不是權限控制。
