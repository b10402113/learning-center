在 Next.js Route Handler 串出 AI 回應

Step 2/5 · 串流 AI 助理

學習目標

學完這一節，你應該能在 Next.js 的 Route Handler 寫出一個會串流的 AI 端點：用領域提示框住助理的範圍、在模型之前先攔截緊急訊息、用預設關閉的傳輸閘門決定要不要送 OpenAI，最後把 OpenAI 的串流轉成一條純文字回應體。

前言：上一節的水管，現在要接上真的模型

上一節我們把「串流是什麼」講清楚了：一般端點把答案準備好才一次送出，而 LLM 的答案本來就是一點一點長出來的，串流就是把這兩件事對齊。但那個模型還停在紙上，接下來要動手把它變成一個真的能回應的端點。

動手之前，先確認你手上已經有幾樣東西：一個 Next.js 專案、已經接好的 Clerk 身分驗證（也就是 requireAuth() 這類會從登入 session 推導使用者的函式）、一個 OpenAI API key 放在伺服器端的環境變數、以及資料庫裡已經有放對話與訊息的兩張表。這些屬於前面節點的成果，這一節不重講。

做完之後，你會得到一個 POST /api/ai/chat 端點：對它送出一句話與對話編號，它會逐字串回助理的回答。而且它同時要處理好幾種「還不能碰模型」的情況，因為在敏感的醫療情境裡，順序錯了會出大事。

第一步：先驗身分，再驗輸入

端點的第一件事永遠是確認「你是誰」。使用者身分只能從登入 session 推導，不能從請求內容讀；有了身分之後，才用 Zod 驗證請求的形狀。

export const POST = route(async (req: Request) => {
  const user = await requireAuth();
  const body = aiChatSchema.parse(await req.json());

  const conversation = await getOrCreateConversation(user.id, body.conversationId);

getOrCreateConversation 是整個節點裡唯一把「對話編號」換回資料列的地方。它帶著 userId = me 的條件去查，所以別人的對話編號根本查不到，會直接變成 404。把這個檢查集中在一個函式裡，其他路由就不用各寫一次，也不會有人漏寫。

第二步：在呼叫模型之前，先把該記的記下來

接下來要寫入使用者這一句話，並設定 Sentry 的 agent tracing。順序很重要：tracing 必須在模型呼叫之前設定，否則產生的 span 會變成孤兒、接不回這輪對話。

Sentry.setUser({ id: user.id });
Sentry.setConversationId(conversation.id);

await db.insert(aiMessages).values({
  conversationId: conversation.id,
  role: 'user',
  content: body.message,
});

注意 setUser 只傳了 id，沒有 email 或其他可識別資訊——User 欄位只需要一個穩定值來分組事件。而 setConversationId 讓同一個對話的每一輪，即使跨了好幾個請求與 trace，都能在 Sentry 裡被歸到同一條對話。這兩個設定本身監控用的，不是功能邏輯，但少了它們，之後在 Sentry 上就看不到 AI 功能的成本與延遲。

第三步：緊急訊息要在模型之前短路

這是整段程式碼最不能馬虎的地方。如果使用者描述的症狀可能危及生命，助理必須給出制式的處理指示，而且這件事絕對不能交給 LLM 判斷。理由很直白：模型的判斷力不適合用在「答錯會影響呼吸」的路上。

if (isEmergency(body.message)) {
  const [saved] = await db
    .insert(aiMessages)
    .values({ conversationId: conversation.id, role: 'assistant', content: EMERGENCY_REPLY })
    .returning();

  return json({
    conversationId: conversation.id,
    emergency: true,
    message: { id: saved.id, role: 'assistant', content: EMERGENCY_REPLY },
  });
}

isEmergency 是一組寫死的正規表達式，比對「呼吸／吞嚥困難、臉頸腫脹、止不住的出血、牙齒被打掉、下巴受傷、發燒合併牙齒或臉部問題」這幾類描述。EMERGENCY_REPLY 則是每次都一模一樣的固定文字，內容包含叫救護車或去急診、以及時間敏感處置的提醒。

緊急路徑在模型之前短路，而且完全不依賴模型。這代表即使 OpenAI 掛掉、或這個環境根本沒設定金鑰，緊急卡片照樣能回。

也因為它回的是 JSON，客戶端能用內容型別分辨「這是一則通知」還是「這是一段串流回覆」，對應到上一節講的分岔點。

第四步：金鑰與傳輸閘門，預設要關

通過緊急檢查之後，才輪到檢查「這件事到底能不能做」。這裡有兩道關卡，順序不能顛倒。

if (!process.env.OPENAI_API_KEY) {
  throw new ApiError(503, 'The assistant is not configured yet.', 'ai_unconfigured');
}

if (!externalTransmissionApproved()) {
  throw new ApiError(
    503,
    'The assistant is unavailable in this environment.',
    'ai_transmission_blocked'
  );
}

第一道是金鑰有沒有設定，沒有就回 503。第二道才是關鍵：externalTransmissionApproved() 只有在環境變數 OPENAI_TRANSMISSION_APPROVED 明確等於字串 'true' 時才回 true。任何其他值——沒設、"false"、"1"、"TRUE"——一律視為不准。

export function externalTransmissionApproved(): boolean {
  return process.env.OPENAI_TRANSMISSION_APPROVED === 'true';
}

這種寫法叫 fail-closed（失敗時關閉）：預設是不傳，要傳得先有人明確打開。為什麼要這麼嚴？因為「沒有病人的病歷被送出去」和「沒有任何病患資訊到達 OpenAI」是兩件不同的事——病患親手打的那段症狀描述，只要綁定到某個使用者，就已經是可識別資訊；病患也可能自己把名字或生日打進去。沒有任何 system prompt 能阻止這件事，也不該相信任何分類器能偵測它。所以傳不傳是一個部署決策，不是程式能從內容推斷的。

不要因為「模型需要看訊息才能回答」就把閘門預設打開。預設值一旦是開的，任何一次部署失誤都會直接把病患文字送進第三方。

第五步：組出要送進模型的歷史

真正要送給 OpenAI 的內容只有兩部分：system prompt，以及這條對話的訊息。沒有病歷、沒有預約紀錄，什麼額外的資料列都不掛。

const history = (
  await db
    .select({ role: aiMessages.role, content: aiMessages.content })
    .from(aiMessages)
    .where(eq(aiMessages.conversationId, conversation.id))
    .orderBy(asc(aiMessages.createdAt))
    .limit(30)
).filter((m) => m.content.trim());

這裡有兩個細節。第一是 limit(30)：只帶最近三十則，避免對話愈長、每一次請求送出的內容愈多而失控。第二是 filter：把內容空白的訊息濾掉。為什麼會有空白訊息？因為圖片附件的回合是用空字串存進去的（照片本身不會送給模型），一則空白的回合塞進 prompt 比沒有還糟。這兩件事都是為了讓送出去的內容保持乾淨。

第六步：要求串流，並保留 token 用量

const completion = await openai.chat.completions.create({
  model: AI_MODEL,
  messages: [
    { role: 'system', content: SYSTEM_PROMPT },
    ...history.map((m) => ({ role: m.role, content: m.content }) as const),
  ],
  max_tokens: 400,
  temperature: 0.3,
  stream: true,
  stream_options: { include_usage: true },
});

幾個欄位值得說明。stream: true 是這個端點的核心，它讓回傳的不再是一份完整結果，而是一個可以逐段取用的非同步迭代器。SYSTEM_PROMPT 定義了助理的範圍與規矩：只能做牙科衛教與分流、絕不診斷、不開藥、不判讀影像、不宣稱自己是牙醫或真人，回答最多兩個短段落，而且超出牙科範圍要明說。max_tokens: 400 與 temperature: 0.3 把回答長度與發散程度壓在保守範圍。最後的 stream_options: { include_usage: true } 是給監控用的——串流回應預設不附 token 用量，少了它，Sentry 上的成本估算就沒有數字。

還有一行包住 OpenAI client 的呼叫：Sentry.instrumentOpenAiClient(...)。它產生 gen_ai 的 span，記錄模型、token、成本與延遲；但 Sentry 設定裡的 genAI: { inputs: false, outputs: false } 會把 prompt 與回覆關掉，所以 Sentry 只看得到這條對話的輪廓，看不到任何訊息內容。

第七步：把迭代器轉成一條純文字流

OpenAI 給的是一串 chunk，每個 chunk 裡有當次生成的片段。我們要把它變成一個 ReadableStream，並在關閉之前把完整回答存進資料庫。

export function replyStream(
  chunks: AsyncIterable<StreamChunk>,
  onDone: (reply: string) => Promise<unknown>
): ReadableStream<Uint8Array> {
  const encoder = new TextEncoder();
  return new ReadableStream({
    async start(controller) {
      let reply = '';
      for await (const chunk of chunks) {
        const delta = chunk.choices?.[0]?.delta?.content;
        if (!delta) continue;
        reply += delta;
        controller.enqueue(encoder.encode(delta));
      }
      if (!reply.trim()) {
        reply = AI_FALLBACK_REPLY;
        controller.enqueue(encoder.encode(reply));
      }
      try {
        await onDone(reply);
      } catch (err) {
        console.error('[ai] persist failed', err);
      }
      controller.close();
    },
  });
}

這個函式把串流包成幾個清楚的規則：每收到一段文字就 enqueue 出去；如果整段回答都是空白，就用一句 AI_FALLBACK_REPLY 補上，避免使用者看到空氣；然後才呼叫 onDone(reply) 把完整回答寫入資料庫，最後關閉串流。

還有兩個容易被忽略的保護。第一，迴圈裡的錯誤不會被往外丟，而是只寫進 log——因為錯誤訊息可能引用 prompt，而 prompt 是病患自己打的字，不能讓它出現在使用者眼前。第二，onDone 即使失敗，也只是這一輪沒存進歷史，已送到使用者眼前的答案不會被收回。串流中途失敗時，已經送出的半段話同樣選擇保留。

第八步：回傳純文字流，對話編號放標頭

const stream = replyStream(completion, (reply) =>
  db.insert(aiMessages).values({
    conversationId: conversation.id,
    role: 'assistant',
    content: reply,
  })
);

return new Response(stream, {
  headers: {
    'Content-Type': 'text/plain; charset=utf-8',
    'Cache-Control': 'no-store',
    'X-Conversation-Id': conversation.id,
  },
});

純文字流沒有 JSON 欄位可以放對話編號，所以它放在 X-Conversation-Id 標頭；客戶端之後要繼續同一條對話，就靠這個值。Cache-Control: no-store 則是因為每一條對話都是特定使用者的內容，不該被任何快取留存。

做完長什麼樣

完成後，這個端點會有幾種可驗證的行為。送一句普通問題，回應的內容型別是 text/plain，文字會逐段抵達。送一句符合緊急樣式的訊息，回應是 JSON 且帶 emergency: true 與制式文字，完全沒有碰模型。當環境沒設金鑰或閘門沒開，回應是 503 的 JSON，帶著可以顯示給使用者的訊息。這三種結果互斥而且可預測，就是這個步驟要做到的成果。

至於「為什麼要這樣設計」的來龍去脈，屬於上一節的心智模型；這一節刻意只講怎麼做。水管接好了，下一步要處理的是水管的另一頭：手機端怎麼一邊收字、一邊把畫面長出來。
