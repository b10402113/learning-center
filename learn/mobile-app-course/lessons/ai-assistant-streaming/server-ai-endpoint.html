在 Next.js Route Handler 串出 AI 回應

Step 2/5 · 串流 AI 助理

學習目標

能寫出一個會串流的 AI 端點：用領域 system prompt 界定回答範圍、在模型之前短路緊急訊息、用 fail-closed 閘門擋下外送，再把 OpenAI 的串流轉成純文字 ReadableStream。

前言：一個檔案，四個責任

上一節我們把心智模型建好了：模型生成的答案要一段一段送，不要等整包。現在要把它變成真的程式碼。當你打開 apps/web/src/app/api/ai/chat/route.ts，會發現這個檔案並不只是「呼叫 OpenAI 然後回傳」。它在同一次請求裡依序做了四件事：認出使用者、決定這是不是緊急狀況、判斷現在到底准不准把文字送出去、最後才把模型輸出接成一條串流。

這個順序不是隨意的。緊急回覆必須在模型之前決定，不能依賴模型；外送閘門必須放在任何文字離開邊界之前；而串流只負責最後那一段模型生成。這一節就照著這個順序，把端點一層一層接起來。動手前先確認你手上已經有 Route Handler 的基本概念、一個能用的 requireAuth、Zod 驗證工具、Drizzle 的資料庫連線，以及一串 OPENAI_API_KEY。

先看整體流程

把這個 POST 回應的完整生命週期攤開，順序如下。先掃一遍，知道每個岔路在哪，後面再逐段拆：

  1. 認出使用者，驗證請求內容，取得或建立這串對話。
  2. 把使用者這一輪問句存進資料庫。
  3. 檢查是不是緊急訊息；若是，直接回固定的 JSON 並結束，完全不碰模型。
  4. 檢查環境是否設定好、以及外送是否已核准；任一不符就回 503。
  5. 撈出最近 30 則對話，濾掉沒有內容的回合，組成要送進模型的歷史。
  6. 呼叫 OpenAI，開啟串流。
  7. 把模型的非同步輸出轉成 ReadableStream，邊產生邊送出。
  8. 用純文字串流回應，並在標頭帶上對話 id。

第 1 步：認人、驗 body、拿對話

所有受保護的端點都從同一件事開始：確認來的人是誰。這裡用 requireAuth() 取得登入使用者，接著用 aiChatSchema 把請求內容解析成有型別的物件。通過之後，叫 getOrCreateConversation()，傳入使用者 id 與前端帶來的對話 id（第一次送出時會是 undefined），拿回這一輪要寫入的對話列。

export const POST = route(async (req: Request) => {
  const user = await requireAuth();
  const body = aiChatSchema.parse(await req.json());

  const conversation = await getOrCreateConversation(user.id, body.conversationId);

這個 getOrCreateConversation 是之後步驟 4 的主角，這裡先記得：對話 id 不是隨便就能拿來寫入，它會連同使用者 id 一起被檢查，別人的對話拿不到。

第 2 步：先存下使用者這一輪

在呼叫模型之前，先把使用者問的那句話落地。這樣做的好處是，就算後面的模型呼叫失敗，歷史上至少留下了使用者問了什麼。

  await db.insert(aiMessages).values({
    conversationId: conversation.id,
    role: 'user',
    content: body.message,
  });

第 3 步：緊急訊息在模型之前短路

接下來是這個端點最重要的一條岔路。如果使用者的問句符合緊急徵兆，例如「沒辦法呼吸」「臉腫起來」「血停不住」，系統不會把這句話交給模型判斷，而是在模型之前就直接回一段固定的處理指示。

  // The emergency path short-circuits BEFORE the model and must never depend
  // on it. Same words every time.
  if (isEmergency(body.message)) {
    const [saved] = await db
      .insert(aiMessages)
      .values({ conversationId: conversation.id, role: 'assistant', content: EMERGENCY_REPLY })
      .returning();

    return json({
      conversationId: conversation.id,
      emergency: true,
      message: { id: saved.id, role: 'assistant', content: EMERGENCY_REPLY },
    });
  }

判斷用的 isEmergency() 是一組寫死的正則表達式，比對「呼吸／吞嚥困難」「臉頸腫脹」「出血不止」「牙齒撞掉」「下顎骨折」「發燒合併牙齒或臉部」等字樣。為什麼不用模型來判斷？因為在「答錯的代價是一條呼吸道」這條路上，不能把判斷交給模型。固定字串每次一致、可以事先審過的 EMERGENCY_REPLY 才是。

還有一個容易忽略的細節：這個分支回的是 JSON，不是串流。這是刻意的。緊急卡片是有話要講的結構化回應（帶 emergency: true），而且它必須在模型不可用時照樣運作，所以留在 JSON 這一側最單純。

第 4 步：兩道 503 閘門

通過緊急檢查後，才輪到「准不准把病患文字送出去」這件事。這裡有兩道關卡，順序不能顛倒。

  if (!process.env.OPENAI_API_KEY) {
    throw new ApiError(503, 'The assistant is not configured yet.', 'ai_unconfigured');
  }
  …
  if (!externalTransmissionApproved()) {
    throw new ApiError(
      503,
      'The assistant is unavailable in this environment.',
      'ai_transmission_blocked'
    );
  }

第一道是環境根本沒設定好，沒有 API key，回 ai_unconfigured。第二道才是真正的政策閘門，由 externalTransmissionApproved() 決定：

export function externalTransmissionApproved(): boolean {
  return process.env.OPENAI_TRANSMISSION_APPROVED === 'true';
}

注意這個函式只認一個字串 'true'。沒設定、設成 'false'、'1'、'TRUE'，一律視為不通過。這種寫法叫 fail-closed（預設關閉）：要放行必須明確打開，任何模糊地帶都會擋下。為什麼要這麼小心？因為病患可以自己打症狀描述，也可能直接打上自己的名字或生日。系統沒有把病歷送給 OpenAI，並不等於「沒有任何可識別資訊流到 OpenAI」。這件事不是程式能從內容推論出來的，而是部署層級的決定，所以預設關閉、要人明確核准。

把緊急分支放在閘門之前，也是有意的：緊急回覆在本地就能完成，就算外送被擋、模型連不上，它也必須照樣給出正確的處理指示。

第 5 步：組出要送給模型的歷史

閘門通過，代表接下來這一步的文字會離開邊界。先撈出這串對話最近的訊息，按時間排序、限制 30 筆，然後把內容空白的回合濾掉。

  const history = (
    await db
      .select({ role: aiMessages.role, content: aiMessages.content })
      .from(aiMessages)
      .where(eq(aiMessages.conversationId, conversation.id))
      .orderBy(asc(aiMessages.createdAt))
      .limit(30)
    // A photo turn is stored with empty content — the image never goes to
    // OpenAI, and a blank turn in the prompt is worse than no turn at all.
  ).filter((m) => m.content.trim());

那個 filter 是為了圖片附件而留的。照片回合的 content 是空字串（圖片本身永遠不進模型），如果原封不動塞進 prompt，會留下一個沒有內容的洞。與其送一個空回合，不如直接跳過。圖片附件會在步驟 5 完整交代。

第 6 步：呼叫 OpenAI，開啟串流

資料備齊，終於可以呼叫模型。請求裡除了歷史訊息，還有一份固定的 system prompt，它決定助理回答什麼、不回答什麼。串流開關就是這裡的 stream: true。

  const completion = await openai.chat.completions.create({
    model: AI_MODEL,
    messages: [
      { role: 'system', content: SYSTEM_PROMPT },
      ...history.map((m) => ({ role: m.role, content: m.content }) as const),
    ],
    max_tokens: 400,
    temperature: 0.3,
    stream: true,
    // OpenAI omits token counts from streamed responses unless asked. Without
    // this the gen_ai span has no usage, and so no cost estimate.
    stream_options: { include_usage: true },
  });

逐項看：AI_MODEL 是 gpt-4o-mini；max_tokens: 400 把回覆長度壓在兩段短文上下；temperature: 0.3 讓語氣穩定、少即興；stream: true 打開串流；stream_options 則要求串流也附上 token 用量，否則追蹤資料裡會沒有成本估算。

範圍控制的關鍵在 system prompt。它的硬規則包含：絕不診斷、絕不開藥或給劑量、絕不解讀影像／X 光／檢驗、絕不宣稱自己是牙醫或人類、沒有病患紀錄也不會回答相關問題；回答要短、說明一般可能性而非斷定這個人得了什麼，並在最後引導預約。這些界線只寫在伺服器端，前端擋不掉也改不了，這正是重點。

第 7 步：把模型串流翻成 ReadableStream

OpenAI 回來的是一個非同步可迭代物件，每一塊帶著一小段文字增量。接下來的 replyStream() 負責把它抽乾、編碼、塞進一條 ReadableStream（可讀串流，一種可以被逐段讀取的資料來源）。

      let reply = '';
      try {
        for await (const chunk of chunks) {
          const delta = chunk.choices?.[0]?.delta?.content;
          if (!delta) continue;
          reply += delta;
          controller.enqueue(encoder.encode(delta));
        }
      } catch (err) {
        // Never echo the error: it can quote the prompt, and the prompt is
        // patient-typed free text.
        console.error('[ai] stream failed', err instanceof Error ? err.message : err);
      }

迴圈一次讀一塊：把文字增量累加到 reply，同時用 TextEncoder 編碼成位元組，透過 controller.enqueue() 推出去。這裡有兩個不能省的規矩。第一，發生錯誤時只記在伺服器日誌，絕對不要把錯誤原文回傳給使用者，因為錯誤訊息可能夾帶 prompt 的內容，而 prompt 是病患自己打的字。第二，一個已經送出的半成品不該因為中途失敗就被整段丟掉，使用者手上已經看到的字就留著。

串流收尾時，還要處理「模型什麼都沒吐」和「把答案存起來」兩件事：

      if (!reply.trim()) {
        reply = AI_FALLBACK_REPLY;
        controller.enqueue(encoder.encode(reply));
      }
      // The patient already has the answer on screen; a failed insert must not
      // error the stream out from under it. The turn is lost from history only.
      try {
        await onDone(reply);
      } catch (err) {
        console.error('[ai] persist failed', err instanceof Error ? err.message : err);
      }
      controller.close();

如果整段回覆是空的，就補上一句固定的 AI_FALLBACK_REPLY，至少讓使用者知道發生什麼、可以改預約。最後呼叫 onDone(reply)，把拼好的完整答案存進資料庫，才 close() 關閉串流。存檔被包在 try／catch 裡：使用者已經在畫面上看到答案了，存檔失敗不該把串流從他腳下抽掉，代價只是這一輪不進歷史。

第 8 步：回傳 Response 與標頭

最後把串流包成 HTTP 回應。因為內容是純文字，對話 id 沒有地方放，所以改用標頭帶出去。

  const stream = replyStream(completion, (reply) =>
    db
      .insert(aiMessages)
      .values({ conversationId: conversation.id, role: 'assistant', content: reply })
  );

  return new Response(stream, {
    headers: {
      'Content-Type': 'text/plain; charset=utf-8',
      'Cache-Control': 'no-store',
      'X-Conversation-Id': conversation.id,
    },
  });

Content-Type 是純文字，客戶端就靠這個判斷接下來要讀串流而不是解析 JSON。Cache-Control: no-store 是因為每個回應都跟身分有關，不該被任何快取留存。X-Conversation-Id 讓手機端把新的對話 id 記下來，下一輪才接得回同一串。

不能忘的旁支：別讓病患文字流進追蹤

這個端點還接了 Sentry（錯誤與效能追蹤服務）。它刻意只送可群組的識別資訊，不送對話內容：送出請求前設定 Sentry.setUser({ id: user.id })（只給 id，不給 email）與 Sentry.setConversationId(conversation.id)，並用 Sentry.instrumentOpenAiClient 包住 OpenAI client 來產生模型層級的 span。至於 gen_ai 的輸入與輸出，也就是 prompt 與回覆，設定成關閉，才不會讓病患的文字進到追蹤系統。這是「即使要觀測，也不能把 PHI 帶出去」的具體做法，細節屬於另一個節點。

做完長什麼樣

你可以用三種請求驗證這個端點。送一句日常問題，會收到 text/plain 的串流，內容陸續抵達，標頭帶著 X-Conversation-Id。送一句符合緊急徵兆的話，會收到 application/json，裡面有固定的緊急回覆與 emergency: true。把外送閘門關著再送一句日常問題，會收到 503 與 ai_transmission_blocked。三條路各自穩定，就代表這個端點接對了。至於原理與取捨的完整脈絡，屬於步驟 1 的觀念範圍，這裡只負責把流程做對。

小結

這個端點有固定的先後：先認人與驗 body，存下使用者這一輪，緊急訊息在模型之前短路並用 JSON 回應，接著才過兩道 503 閘門（未設定、外送未核准，且 fail-closed）。通過後撈最近 30 則、濾掉空白回合，用 system prompt 界定範圍並以 stream: true 呼叫模型，再用 replyStream 把非同步增量編碼進 ReadableStream；錯誤不原文外洩、存檔失敗不影響已送出的答案。最後以 text/plain 回應，對話 id 放在 X-Conversation-Id 標頭。

端點會串了，但使用者還看不到任何字。下一步要把鏡頭轉到手機端，看 useApiStream 怎麼一邊收一邊畫，怎麼分辨 JSON 分支和串流分支，以及怎麼避免過期回應蓋掉畫面。
