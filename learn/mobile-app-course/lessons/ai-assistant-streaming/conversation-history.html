把對話歷史持久化到資料庫

Step 4/5 · 串流 AI 助理

學習目標

學完這一節，你應該能設計出對話持久化的最小模型：用一個受 ownership 檢查的 resolver 取得對話、讓 GET 重新灌回歷史、用 DELETE 清乾淨歷史與附件，並知道歷史要限制長度、空白的圖片回合要過濾。

前言：關掉 app 再打開，對話不能人間蒸發

前兩節做完，助理已經會逐字回答了。但只要把 app 關掉再打開，畫面就會回到一片空白的初始狀態——不是資料不見了，而是我們根本沒把它顯示出來、也沒把「這是同一條對話」的線索留下來。使用者問了一輪、得到答案、過幾分鐘回來想接著問，卻發現前面全部消失了，這種體驗比沒有助理還糟。

這一節要做的事，是替這條對話接上記憶。前置條件是上一節的串流端點已經能運作，而且資料庫裡有放對話與訊息的兩張表。做完之後，重新打開 app 會看到之前的往來，按下清除也會乾淨地刪掉整條歷史與附帶的照片。

聽起來只是「把訊息存起來」，但要存得對，得先想清楚：對話的邊界是什麼、誰有權讀它、刪除時要連帶清掉什麼。這三個問題處理好，持久化才算完整。

第一步：資料模型——一條對話，底下掛著很多訊息

最基本的形狀是一張對話表與一張訊息表。aiConversations 代表「一條對話」，只記所屬的使用者與建立時間；aiMessages 代表對話裡的每一則訊息，用 conversationId 指回對話，並記角色（user 或 assistant）、內容與建立時間。

訊息表的外鍵要設成 on delete cascade。這樣刪掉一條對話時，底下所有訊息會由資料庫一併清掉，不會留下孤兒資料列。這個 cascade 會在第四步的刪除功能裡派上用場。

// aiMessages
conversationId  → aiConversations.id   (on delete cascade)
role            text
content         text
imagePath       text | null

// aiConversations
userId          text
createdAt       timestamp

至於「一位使用者可以有幾條對話」，Dentify 的選擇是：一位病人只有一條助理對話，而且每次取用時都拿最新建立的那條。這個簡化讓畫面不必處理對話列表，也讓「開啟 app 時要顯示什麼」有一個明確答案。

第二步：一個受檢查的 resolver，讓對話編號換回資料列

整個功能裡，凡是「把使用者傳來的對話編號變成資料庫裡的一條對話」的地方，都共用同一個函式：

export async function getOrCreateConversation(userId: string, conversationId?: string) {
  if (!conversationId) {
    const [created] = await db.insert(aiConversations).values({ userId }).returning();
    return created;
  }

  const [found] = await db
    .select()
    .from(aiConversations)
    .where(and(eq(aiConversations.id, conversationId), eq(aiConversations.userId, userId)));
  if (!found) throw notFound('Conversation not found');
  return found;
}

這個函式有兩個很重要的性質。第一，查詢條件同時包含 id 與 userId，所以別人傳來的對話編號根本查不到——ownership 檢查只存在這裡一份，其他路由不會漏寫。第二，查不到時回的是 404，不是 403。差別在於：403 等於承認「這條對話存在，只是你不能看」，那反而洩漏了別人的對話編號是有效的；404 則讓存在與不存在看起來一模一樣。

當 conversationId 是空的（例如第一輪對話），它就建一條新的。這就是「沒有就建、有就驗證後回傳」的 get-or-create 語意。

第三步：每一輪都先寫入，並回傳對話編號

還記得上一節的 POST 流程嗎？在呼叫模型之前，使用者的訊息就已經被寫進資料庫了。這是持久化的第一半——不論模型最後成不成功，使用者問了什麼都會留下來。

await db.insert(aiMessages).values({
  conversationId: conversation.id,
  role: 'user',
  content: body.message,
});

而助理的回答，則是在串流關閉之前、由 onDone 寫入。這樣一來，一輪對話的兩個角色都不會漏，而且使用者拿到回答的同時，這輪也已經在歷史裡了。

對話編號是怎麼回到手機上的？如果走串流，它放在 X-Conversation-Id 標頭；如果走 JSON 分支（例如緊急卡片），它放在回傳物件的 conversationId 欄位。手機端拿到之後會記住它，下一輪才能接續同一條對話。

第四步：GET 重新灌回歷史

重新打開 app 時，畫面呼叫 GET /api/ai/chat，由伺服器回傳最新那條對話與它的所有訊息。

export const GET = route(async () => {
  const user = await requireAuth();

  const [conversation] = await db
    .select()
    .from(aiConversations)
    .where(eq(aiConversations.userId, user.id))
    .orderBy(desc(aiConversations.createdAt))
    .limit(1);
  if (!conversation) return json({ conversationId: null, messages: [] });

  const messages = await db
    .select()
    .from(aiMessages)
    .where(eq(aiMessages.conversationId, conversation.id))
    .orderBy(asc(aiMessages.createdAt));

  return json({
    conversationId: conversation.id,
    messages: messages.map((m) => ({
      id: m.id,
      role: m.role,
      content: m.content,
      image: m.imagePath ? signedPhoto(m.imagePath) : null,
      createdAt: m.createdAt.toISOString(),
    })),
  });
});

三個細節值得停下來看。第一，沒有對話時回的是 { conversationId: null, messages: [] }，而不是報錯——「還沒聊過」是正常狀態，不是異常。第二，照片的網址是每次讀取時才用 signedPhoto 重新簽出來的，不是存下來的。因為私人檔案的簽名網址會過期，存下來的網址很快就會變成死連結；存的是路徑，讀的時候才換成當下的有效網址。第三，訊息的排序固定用建立時間遞增，畫面上的先後才會與實際往來一致。

第五步：DELETE 清乾淨歷史與附件

清除歷史不能只清畫面，要真的把伺服器上的對話刪掉。

export const DELETE = route(async () => {
  const user = await requireAuth();
  await db.delete(aiConversations).where(eq(aiConversations.userId, user.id));

  try {
    await imagekit().deleteFolder(photoFolder(user.id));
  } catch (err) {
    console.error('[ai] photo folder cleanup failed', err instanceof Error ? err.message : err);
  }

  return json({ ok: true });
});

第一步是刪掉對話列，訊息會因為 on delete cascade 自動跟著消失。第二步是刪掉 ImageKit 上的照片資料夾——否則資料庫的紀錄沒了，照片卻還留在雲端，等於「對使用者是刪掉了、對我們卻還留著」。因為每位使用者的照片都放在以 user id 命名的單一資料夾裡，這一步只需要一次呼叫。

這個資料夾刪除是刻意的 best-effort（盡力而為）：資料列早就刪掉了，如果這時候因為刪資料夾失敗而讓整個請求回錯誤，反而會告訴使用者「刪除沒成功」，但實際上大部分都成功了。所以失敗只寫 log。附帶一提，從未上傳過照片的使用者沒有資料夾，這種情況會回 404，是正常的，不該當成錯誤處理。

第六步：歷史要限長，空白要濾掉

把歷史存起來之後，下一個問題是「要送多少歷史給模型」。如果照單全收，對話愈長，每一次請求帶的內容就愈多，成本與延遲都會失控。所以組 prompt 的時候只取最近三十則：

.limit(30)
// ...
.filter((m) => m.content.trim())

limit(30) 是長度的上限，而 filter 處理的是另一種污染：圖片回合是用空字串存進去的，因為照片本身不會送給模型。一則空白的訊息塞進 prompt，比沒有這則還糟，所以送出去前要先濾掉。這也說明持久化的資料與送進模型的資料不必然相同——存的是完整歷史，送的是一份清理過的子集。

第七步：手機端記住對話編號，並用確認框保護刪除

手機端把對話編號放在一個模組層級的變數，而不是畫面狀態裡。這樣即使離開助理畫面再回來，編號還在，下一輪就能接上同一條對話。

let conversationId: string | null = null;

畫面掛載時呼叫 GET 把歷史灌進來，同時把 conversationId 指向伺服器回傳的那條。清除歷史則是先請使用者確認，再打 DELETE；伺服器成功之後才清空畫面。

const confirmClear = () =>
  Alert.alert(
    'Delete chat history?',
    'This permanently deletes your conversation with the assistant.',
    [
      { text: 'Cancel', style: 'cancel' },
      { text: 'Delete', style: 'destructive', onPress: clearHistory },
    ]
  );

注意清除的順序是「先伺服器、再畫面」。如果反過來先清空畫面、但刪除失敗了，使用者會以為資料沒了，其實還在——那等於在騙使用者。所以成功之後才清畫面，失敗則跳出提示。這是一個刪除類功能很常見的取捨：畫面必須誠實反映伺服器的狀態。

做完長什麼樣

完成後可以逐項驗證：傳幾輪訊息，關掉 app 再打開，之前的往來會重新出現；畫面上每一則訊息的角色與順序都正確；按下清除並確認後，歷史消失，重新開啟也不復見；有照片的對話，清除後照片的資料夾也一起被刪掉；還沒聊過的新使用者打開畫面，看到的是空狀態而不是錯誤。

到這裡，助理已經有記憶了。但使用者能傳的還只有文字。下一步要讓照片也能進到對話裡——而且會看到，照片的處理方式和文字完全不同，因為助理被禁止判讀影像，而照片也永遠不會送給模型。
