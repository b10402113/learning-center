把對話歷史持久化到資料庫

Step 4/5 · 串流 AI 助理

學習目標

能寫出受 ownership 檢查的對話 resolver，用 GET 回灌最新一串對話，並用 DELETE 同時清掉訊息與 ImageKit 照片。

前言：關掉 app，對話就不見了

上一節我們讓回覆能逐字長出來了，使用者總算有「真的在對話」的感覺。但接下來他滑掉 app、隔天再打開，畫面卻回到空白的初始狀態。明明剛剛聊了一長串，卻像沒發生過。會出現這個問題，是因為訊息只活在手機的記憶體裡，app 一關就散掉了。

這一節要把對話搬到伺服器端的資料庫，讓歷史在重新開啟 app 後還在。但「存進資料庫」只是表面，真正要小心的是歸屬：這串對話是誰的？別人有沒有辦法讀到、或刪掉不屬於他的對話？所以我們會先看資料表怎麼設計，再看一個集中處理 ownership 的 resolver，最後把 GET 和 DELETE 兩條路接好。動手前你需要一個能用的 Drizzle 資料庫連線，以及步驟 2 已寫好的端點骨架。

整體順序

  1. 先理解兩張表：對話與訊息，以及它們的 cascade 刪除關係。
  2. 寫一個集中檢查歸屬的 getOrCreateConversation()。
  3. 在 POST 時用它建立或驗證對話，再寫入訊息。
  4. 用 GET 撈出這位使用者最新的一串對話，回灌給手機端。
  5. 用 DELETE 刪掉對話（連帶刪訊息），再盡力清掉 ImageKit 的照片。
  6. 手機端用模組層級變數記住對話 id，刪除時先伺服器成功才清畫面。

第 1 步：兩張表與它們的刪除關係

資料模型很小，只有兩張表。ai_conversations 代表一串對話，透過 userId 指向使用者；ai_messages 代表其中一則訊息，透過 conversationId 指向對話，並有角色、內容與選填的圖片路徑。

export const aiConversations = pgTable('ai_conversations', {
  id: id(),
  userId: uuid('user_id')
    .notNull()
    .references(() => users.id, { onDelete: 'cascade' }),
  createdAt: createdAt(),
});

export const aiMessages = pgTable(
  'ai_messages',
  {
    id: id(),
    conversationId: uuid('conversation_id')
      .notNull()
      .references(() => aiConversations.id, { onDelete: 'cascade' }),
    role: aiRoleEnum('role').notNull(),
    content: text('content').notNull(),
    /**
     * ImageKit path of a photo the patient attached, private folder. Delivery
     * URLs are never stored — they expire, so they are signed on every read.
     * A photo message carries an empty `content`.
     */
    imagePath: text('image_path'),
    createdAt: createdAt(),
  },
  (t) => [index('ai_messages_conversation_idx').on(t.conversationId, t.createdAt)]
);

兩個 onDelete: 'cascade' 是這段的重點。刪掉一列對話，它底下的訊息會跟著被資料庫刪掉；刪掉一個使用者，他的所有對話也會跟著走。這個設計讓「清除歷史」變成刪一列，而不是逐則訊息掃描。另外那條複合索引把 conversationId 與 createdAt 綁在一起，正好對應我們每次都要「照時間撈某串對話」的查法。

第 2 步：一個地方做 ownership 檢查

接著是最容易被寫錯的部分。對話 id 由前端帶著，如果每個寫入或讀取的路由都各自檢查一次「這串對話是不是你的」，不但重複，還很容易漏。這個 app 把檢查集中在一支 resolver。

export async function getOrCreateConversation(userId: string, conversationId?: string) {
  if (!conversationId) {
    const [created] = await db.insert(aiConversations).values({ userId }).returning();
    return created;
  }

  const [found] = await db
    .select()
    .from(aiConversations)
    .where(and(eq(aiConversations.id, conversationId), eq(aiConversations.userId, userId)));
  if (!found) throw notFound('Conversation not found');
  return found;
}

邏輯分兩支。前端沒帶 id（第一次對話），就建立一列新對話。有帶 id，就同時用「對話 id」與「使用者 id」兩個條件去找，兩個都對才拿得到。找不到時丟出 notFound，也就是 404。

這裡有一個刻意的選擇：別人的對話會回 404，而不是 403。直覺上「存在但不准你看」好像該回 403，但那樣等於承認這串對話真的存在，洩漏了不該洩漏的資訊。回 404，對攻擊者而言就跟這串對話從來不存在一模一樣。

第 3 步：POST 先建立或驗證對話

回頭看步驟 2 的 POST 開頭，它正是先呼叫這支 resolver，再寫入使用者訊息。順序有意義：對話必須先被建立或驗證通過，後面的訊息才有合法的落點。如果這段跳過 resolver 直接寫，等於任何人都能往別人的對話裡塞訊息。

  const conversation = await getOrCreateConversation(user.id, body.conversationId);

第 4 步：GET 回灌最新一串對話

重新開啟 app 時，手機端呼叫 GET 把歷史抓回來。伺服器先找出這位使用者最新的一串對話（每位病患只有一串），再撈出其中所有訊息，照建立時間排序。

export const GET = route(async () => {
  const user = await requireAuth();

  const [conversation] = await db
    .select()
    .from(aiConversations)
    .where(eq(aiConversations.userId, user.id))
    .orderBy(desc(aiConversations.createdAt))
    .limit(1);
  if (!conversation) return json({ conversationId: null, messages: [] });

  const messages = await db
    .select()
    .from(aiMessages)
    .where(eq(aiMessages.conversationId, conversation.id))
    .orderBy(asc(aiMessages.createdAt));

  return json({
    conversationId: conversation.id,
    messages: messages.map((m) => ({
      id: m.id,
      role: m.role,
      content: m.content,
      // Signed fresh on every read rather than stored: a delivery URL for a
      // private file expires, so a persisted one would be a dead link.
      image: m.imagePath ? signedPhoto(m.imagePath) : null,
      createdAt: m.createdAt.toISOString(),
    })),
  });
});

找不到對話時回的是 { conversationId: null, messages: [] }，而不是錯誤。這是合理的：一個還沒聊過天的使用者，本來就該看到空的初始畫面，而不是一個錯誤。另外注意圖片那行，它沒有把圖片網址存在資料庫，而是每次讀取時用 signedPhoto 重新簽一個。原因很實在：ImageKit 的私有檔案網址會過期，如果當初存下來，過幾天就變成死連結。

第 5 步：DELETE 清掉訊息與照片

清除歷史這個動作，要同時處理資料庫與檔案儲存兩邊。資料庫那一半靠 cascade 一行解決；ImageKit 的照片則得另外呼叫刪除。

export const DELETE = route(async () => {
  const user = await requireAuth();
  await db.delete(aiConversations).where(eq(aiConversations.userId, user.id));

  // Dropping the rows would otherwise leave the photos themselves sitting in
  // ImageKit with nothing left pointing at them — deleted to the patient,
  // retained by us. One folder per user is what makes this a single call.
  //
  // Best-effort on purpose: the rows are already gone, and failing the request
  // now would tell the patient the delete did not happen when most of it did.
  try {
    await imagekit().deleteFolder(photoFolder(user.id));
  } catch (err) {
    // 404 is the normal case — a patient who never attached a photo has no
    // folder. Anything else is a real orphan worth knowing about.
    console.error('[ai] photo folder cleanup failed', err instanceof Error ? err.message : err);
  }

  return json({ ok: true });
});

順序是「先刪資料列，再刪照片」。如果先刪照片卻在刪資料列時失敗，畫面會顯示歷史還在、但照片已經壞掉，使用者會以為刪除沒成功。反過來，資料列先走，即使照片清理失敗，對使用者的語意也已經達成。

照片清理被包在 try／catch 且標成 best-effort（盡力而為），還有兩個理由。第一，從沒傳過照片的使用者根本沒有資料夾，ImageKit 回 404 是正常情況，不該讓整個請求失敗。第二，資料列都已經刪了，這時候回一個錯誤，反而讓使用者以為刪除整個失敗，但實際上大部分都成功了。每個人一個資料夾，這裡正好派上用場：清理只要呼叫一次 deleteFolder。

第 6 步：手機端接起來

手機端的重點有兩個。第一，對話 id 存在模組層級，而不是元件狀態裡。這樣使用者離開助理畫面再回來，同一個 id 還在，不必重新抓取就能接續同一串。

let conversationId: string | null = null;

第二，清除歷史要「伺服器先成功，畫面才清」。如果反過來先清畫面，結果 DELETE 失敗，畫面會呈現一個空白的假象，但伺服器上其實還留著資料，這是在騙使用者。

  /** Server first — clearing the screen on a failed delete would be a lie. */
  const clearHistory = () =>
    pending
      ? undefined
      : call('/api/ai/chat', { method: 'DELETE' })
          .then(() => {
            conversationId = null;
            setMsgs([]);
          })
          .catch((err) =>
            Alert.alert('Could not delete', err instanceof Error ? err.message : 'Try again.')
          );

畫面先用一個確認對話框擋一下，使用者按下紅色刪除才真的送出請求；這樣才不會誤觸就把整串對話清掉。

做完長什麼樣

你可以這樣驗證：跟助理聊幾句，關掉 app 再打開，剛才的對話經由 GET 回灌後仍然在畫面上。換一個帳號登入，看不到別人的對話；如果硬把別人的對話 id 塞進請求，會拿到 404。按下垃圾桶、確認刪除後，資料庫裡的對話與訊息都沒了，ImageKit 對應資料夾也被清除，畫面回到初始狀態。

小結

對話歷史靠兩張表落地：ai_conversations 與 ai_messages，兩層都用 onDelete: 'cascade' 串起來，刪一列就能清掉底下所有訊息。歸屬檢查集中在 getOrCreateConversation()，用「對話 id 加使用者 id」一起查，找不到回 404 而不是 403。POST 先建立或驗證對話再寫訊息；GET 撈最新一串並把圖片網址重新簽章；DELETE 先刪資料列再盡力清 ImageKit 照片。手機端把對話 id 放在模組層級，刪除時先伺服器成功才清畫面。

訊息與歷史都到位了，剩最後一塊拼圖：讓使用者能傳照片給助理。那條路徑很特別，照片不會送進模型，回覆也是固定文案，還牽涉 ImageKit 的私有儲存與模糊縮圖。下一步就來處理它。
