結構化 log：讓五萬個使用者的問題查得到

Step 1/5 · 觀測深化：Logs / Tracing / Agent Tracing

前言：錯誤列表只記錄壞掉的那一刻

前一個 Sentry 節點裡，你已經讓 app 出錯時「你會知道」：錯誤被抓下來、有 session replay、能進 Dashboard 判讀。那個能力解決的是「東西壞了嗎」。但當 app 真的上線，使用者從你手機上的那一個變成幾千幾萬個，你會撞到第一個新極限：錯誤列表只記錄壞掉的那一刻，卻說不出壞掉之前發生了什麼。

想像一位病人回報「我要預約，畫面一直轉圈圈」。你在 Sentry 看到一則逾時錯誤，訊息只有一句「request timed out」。是資料庫慢、是排班計算卡住，還是網路斷了？答案通常藏在錯誤發生前的那幾行事件紀錄裡。你需要的不再只是「錯誤」，而是一份可以回頭查、可以過濾的事件紀錄，這就是結構化 log。

學習目標

學完後，你應該能說出結構化 log 的三個組成：訊息、severity 等級、可查詢的屬性，並解釋為什麼只有等事件量放大之後，「可查詢」才會從一個舒服的功能變成真正救命的繩索。

先看 console.log 為什麼不夠

最直覺的做法是繼續用 console.log。開發時它很好用，但它有三個上線後才浮現的致命限制。第一，它只留在使用者的裝置上，app 一關就消失，你事後完全看不到。第二，它是純文字，你不能對它下「level 是 error、而且包含 payment」這種條件。第三，它和使用者當下的 session 與 trace 沒有任何連結，你只能靠時間戳自己猜哪一行對應哪一則錯誤。

一份只留在別人手機裡、還不能搜尋的純文字，在你有五萬個使用者的時候，等於沒有。這就是結構化 log 要補的洞。

結構化 log 的三個組成

一份結構化 log 可以拆成三個部分。第一個是訊息，給人讀的一句話，例如「appointment booked」。第二個是 severity 等級，決定這則事件有多嚴重。第三個是屬性（attributes，也常被叫做 properties），是一組 key-value 欄位，也是整份 log 能被查詢的關鍵。訊息告訴你發生什麼，等級告訴你多嚴重，屬性則是給機器過濾用的。

Sentry 的 severity 由輕到重分成六級：trace、debug、info、warning、error、fatal。它們不只是分類標籤，也會直接影響你在 Dashboard 上的篩選。判斷原則很簡單：正常但值得記錄的事件用 info；還能繼續跑、但已偏離預期用 warning；某個操作失敗用 error；核心功能整片失效才用 fatal。

屬性是 ids、counts、durations 與 enums，不是內容

屬性該放什麼、不該放什麼，是這個節點最重要的一條界線。Dentify 的 log 範例檔開頭就把規則寫死：屬性只放 id、數量、耗時與列舉值，永遠不放內容。沒有姓名、沒有生日、沒有病歷欄位、沒有訊息內文、沒有助理的 prompt。

/**
 * Every row fires a BATCH, because a single log line proves nothing: the point
 * of structured logs is the query you run once there are thousands, and you
 * cannot demo a query against six rows. The volume rows at the bottom exist so
 * the answer is genuinely un-scrollable.
 *
 * Two rules hold everywhere below, and they are the same two the real call
 * sites follow (`lib/api.tsx`, `booking/confirm.tsx`):
 *
 *  1. Attributes are ids, counts, durations and enums. Never content. No name,
 *     no DOB, no medical field, no message body, no assistant prompt — the
 *     CLAUDE.md non-negotiable does not get an exception for a demo. The
 *     `beforeSendLog` in `_layout.tsx` is the second door.
 *  2. Every log carries `batch_id` and `scenario`, so one run can be isolated
 *     out of the pile with `batch_id:<id>`.
 *
 * Reached from Profile, behind `__DEV__`.
 */

把屬性放 id 而不是內容，有兩個好處。一來敏感資料從源頭就不會外流；二來 id 是穩定、可精確比對的值，你可以在 Dashboard 上打出「這個 dentist_id、這個 error_code」把範圍縮到只剩幾筆，而不是逐字閱讀成千上萬行訊息。下面這段是預約成功路徑實際送出的 log，你可以看到每個屬性都只是數字、id 或列舉字串：

Sentry.logger.trace('availability window expanded', { ...tag, days: 14 });
Sentry.logger.debug('scheduling inputs loaded', {
  ...tag,
  dentist_count: 3,
  busy_intervals: int(8, 40),
  duration_ms: int(30, 90),
});
Sentry.logger.info('slot selected', {
  ...tag,
  dentist_id: dentist,
  lead_time_hours: lead,
  service: 'cleaning',
});
…
Sentry.logger.info('appointment booked', {
  ...tag,
  dentist_id: dentist,
  lead_time_hours: lead,
  service: 'cleaning',
  is_teleconsult: false,
  for_dependent: false,
  attachments: 0,
  duration_ms: int(180, 420),
});

附帶一個很容易漏掉的設定：結構化 log 要被送出去，Sentry.init 裡必須開啟 enableLogs: true。Dentify 的根 layout 刻意不搭配 consoleLoggingIntegration()，避免把每一行 console 都送上雲端；log 只在少數值得在 production 觀察的地方手寫。

// Structured logs. Deliberately NOT paired with `consoleLoggingIntegration()`
// — that would ship every console line to Sentry, which is exactly what
// `beforeBreadcrumb` below strips out. Logs are written by hand, at the few
// places worth watching in production.
enableLogs: true,

用 batch_id 與 scenario 把一次執行從資料堆裡撈出來

有了屬性之後，還需要一個方法把「同一次發生的所有事件」綁在一起。範例檔的做法是每一行都蓋上兩個標籤：batch_id 代表這一次執行的隨機編號，scenario 代表人看得懂的情境名稱。送出一批 log 之後，只要在搜尋欄打 batch_id:<那次的編號>，就能把這一批從整堆資料裡完整撈回來。

/** Stamped onto every line in a run so the run can be filtered back out. */
type Tag = { batch_id: string; scenario: string };

const newBatchId = () => Math.random().toString(36).slice(2, 8);

這兩個標籤解決的是「隔離」問題。當你同時在測很多情境，資料全部混在一起，你沒辦法判斷某筆 warning 是來自正常流程還是刻意製造的錯誤。有了 batch_id，你可以一次只挑一批出來看，像是把案發現場的每一段監視器畫面單獨調出來，而不是把所有畫面疊在一起。

為什麼要等量放大才顯出價值

到這裡要回答標題的問題：為什麼非得等使用者變多，這件事才重要？因為在一條或六條 log 面前，你怎麼看都看得到，查詢能力沒有意義。結構化 log 的價值，是在答案「多到無法用眼睛掃」的時候才浮現。範例檔裡有一個刻意設計的體積按鈕，一次送出 150 行雜訊，其中只埋了一則 fatal，註解寫得很直白：用捲動是找不到的，只有查詢找得到。

const total = 150;
const needle = int(30, total - 20);
for (let i = 0; i < total; i += 1) {
  if (i === needle) {
    Sentry.logger.fatal('token refresh failed, signing out', {
      ...tag,
      provider: 'clerk',
      session_age_minutes: int(240, 900),
    });
    continue;
  }
  …
}

真實世界就是這個樣子：每天幾十萬行 routine 的 debug，中間夾著一則真正重要的 fatal。你不可能一則一則讀，但你可以下一道條件「severity 是 fatal」或「error_code 是 payment_failed」，讓幾萬行瞬間縮成三筆。這就是結構化 log 的核心：它把「發生了什麼」變成一種可查詢的資料，而不是一段只能目視的文字。

小結

結構化 log 由三個部分組成：人看得懂的訊息、決定輕重的 severity 等級，以及機器查得到的屬性。屬性是整份 log 的靈魂，但只放 id、數量、耗時與列舉值，永遠不放姓名或病歷內容。當事件量大到無法用眼睛掃，能依屬性下條件、能把同一次執行用 batch_id 撈出來，才是它真正勝過 console.log 的地方。記得在 Sentry.init 開啟 enableLogs，並刻意不接上 console 整合。

現在你知道 log 該長什麼樣子，但資料送出去之後，實際上要怎麼在 Sentry 裡把它們一層一層篩出來？下一節會走一遍 Explore Logs 的操作：選專案、用 severity 與 property 搜尋、疊多個條件、看時間軸尖峰，最後把查詢存起來或匯出。
