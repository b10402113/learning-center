敏感資料該在哪一層被擋下

Step 3/5 · 觀測深化：Logs / Tracing / Agent Tracing

前言：log 送出去之前，誰來把關

你在前兩節學會了寫出可查詢的結構化 log，也學會在 Explore Logs 裡把問題圈出來。但只要你開始把真實使用者的資料送進雲端，就會撞上一個不能妥協的問題：姓名、生日、病歷、病人自己打進助理的症狀描述，這些東西一旦離開你的系統邊界，就再也收不回來。

常見的直覺是「寫個函式把名字遮掉就好」。但實際上，敏感資料會從好幾個地方溜出去：你自己寫的 log 屬性、SDK 自動複製到每一則 log 的使用者資訊、失敗請求的 request body、資料庫查詢的綁定參數，甚至是 session replay 錄下來的畫面。要在哪一層攔、要用什麼工具攔，是一組真正的取捨。這一節把選項攤開來比，讓你能為每一種資料挑對那一層。

學習目標

學完後，你應該能在「寫入時就不記」、「用 beforeSend / beforeSendLog 鉤子去識別化」與「在 instrumentation 關掉整類收集」這三層之間做選擇，並能說出每一層各自擋下什麼、又放過了什麼。

三個選項，先並排比較

先不要急著選。把三層防線放在同一張表上，差異就很清楚：

層做法擋下什麼放過什麼什麼時候用
第一層：寫入時不記呼叫 logger 前就不放內容，屬性只留 id、數量、耗時從源頭就沒有，根本沒東西可外流你原本想留的除錯內容不需要內容也能判斷問題時，一律優先
第二層：hook 攔截beforeSend / beforeSendLog 在送出前刪欄位、縮減 user、清洗訊息email、name、資料庫綁定參數等已知欄位你忘了刪的欄位、hook 沒涵蓋的事件類型資料結構固定、能精準指名要刪什麼
第三層：關閉整類收集dataCollection 關掉 genAI、db 參數、stack variables；關 console breadcrumb、關 replay 遮罩整類高風險資料一起不收集沒被列到的其他類別一整類都不該離開邊界時

這三層不是替代關係，而是同一條防線上不同的門。實務上通常是「預設第一層、需要保留欄位時用第二層、整類高風險的直接用第三層關掉」。

第二層長什麼樣：兩個鉤子各管一種事件

先看 app 端的鉤子。Dentify 的根 layout 在 Sentry.init 裡同時設定了 beforeSend 與 beforeSendLog。前者處理錯誤事件，把 user 縮成只剩 id；後者處理 log，因為 SDK 會把 scope 上的 user 複製到每一則 log，所以要手動刪掉 email 與 name。

  // PHI never leaves the boundary. A console breadcrumb carries whatever was
  // logged, so drop the category wholesale rather than pattern-matching a name,
  // and let an event carry the Clerk id but never an email or a display name.
  beforeBreadcrumb: (b) => (b.category === 'console' ? null : b),
  beforeSend: (event) => {
    if (event.user) event.user = { id: event.user.id };
    return event;
  },
  // `beforeSend` does not run on logs, and the SDK copies the scope's user onto
  // every one as `user.id` / `user.email` / `user.name` — a display name is a
  // patient name. Same reduction, second door.
  beforeSendLog: (log) => {
    delete log.attributes?.['user.email'];
    delete log.attributes?.['user.name'];
    return log;
  },

這裡藏著兩個很容易忽略的判別點。第一，beforeSend 不會在 log 上執行。如果你只設了它，log 裡的使用者資訊仍然會照樣出去。第二，console breadcrumb 的處理方式不是「把名字濾掉」，而是直接按 category 整類丟棄，因為一則 console 可能帶任何東西，用 pattern 去猜名字永遠猜不完。

同一份 Sentry.init 上方還有一行 sendDefaultPii: false，意思是不要預設附上個人身分資訊。這是把預設值關掉，和上面兩個鉤子是互補的：一個管預設，一個管例外。

第三層長什麼樣：整類資料直接不收集

有些資料不是「刪掉某個欄位」能解決的，而是一整類都不該被收集。伺服器端的 sentry.server.config.ts 就是用 dataCollection 處理這種情況。它把 request body 設成空陣列，並明確關掉三個會夾帶病歷的類別：genAI 的 inputs / outputs（病人自己打的症狀）、databaseQueryData（資料庫 span 的綁定參數）、stackFrameVariables（失敗處理函式裡的所有區域變數）。

  dataCollection: {
    // The one category we do NOT want: request bodies. `/api/patients/[id]`
    // and `/api/patients/[id]/medical-history` carry records, and no error is
    // easier to debug for having a medical history attached to it.
    httpBodies: [],
    // Every category left unset above defaults to permissive, so the three that
    // would carry PHI have to be named. `genAI` is the assistant thread — what
    // the patient typed about their own symptoms, which is exactly the content
    // Sentry's Conversations view is reconstructed from (see the PHI note in
    // `src/app/api/ai/chat/route.ts`). `databaseQueryData` is the bound
    // parameters on a db span: a name, a DOB, a medical-history row.
    // `stackFrameVariables` is every local in a failing handler, which is the
    // same data one frame up.
    genAI: { inputs: false, outputs: false },
    databaseQueryData: false,
    stackFrameVariables: false,
  },

註解點出了一個非常重要的陷阱：只要你有傳入 dataCollection，所有你沒有列出的類別都會回到「寬鬆的預設值」。換句話說，你以為自己只調了幾個開關，實際上可能把沒提到的類別全部打開了，其中就包含 genAI 的 prompt 與回覆擷取。這正是為什麼那三個類別必須被逐一指名關掉，而不是靠「應該預設就是關的」這種假設。

就算 span 屬性關掉了，還有一條路會漏：Drizzle 會把綁定參數放進它所拋出錯誤的訊息裡，而那個訊息會變成 Sentry 的事件標題。所以伺服器端還有一層 beforeSend，專門把例外訊息裡的參數洗掉。

  beforeSend: (event) => {
    for (const e of event.exception?.values ?? []) {
      if (e.value) e.value = scrubQuery(e.value);
    }
    return event;
  },

而這些伺服器端設定要真的被載入，靠的是 Next.js 的 instrumentation 鉤子。instrumentation.ts 在 node runtime 下動態匯入 sentry.server.config，並用 onRequestError 攔住那些在 route handler 之前就被 Next.js 處理掉的錯誤。也就是說，第三層防線是「設定檔 + 載入時機 + 錯誤攔截」三者一起才成立。

export async function register() {
  if (process.env.NEXT_RUNTIME === 'nodejs') {
    await import('../sentry.server.config');
  }
}

/** Catches server errors Next.js handles before a route handler can. */
export const onRequestError = Sentry.captureRequestError;

判別問句：這筆資料需要離開邊界嗎？

與其背規則，不如每次都問自己三個問題，順序就是由內到外。

  1. 沒有這筆內容，我還能不能判斷問題？如果光靠 id、數量與耗時就能知道發生什麼，就在第一層處理，根本不要寫進 log。這是最乾淨、也最不會出錯的一層。
  2. 如果非留這類欄位不可，它的結構固定嗎？結構固定、可以精準指名要刪哪個 key，就用第二層 beforeSend / beforeSendLog。但要記得檢查所有路徑：error 事件走 beforeSend，log 走 beforeSendLog，兩者不互通。
  3. 這一整類資料是不是根本不該被收集？如果答案是「對，連存在都不該存在」，就用第三層：在 dataCollection 裡明確關掉，或在 replay、console breadcrumb 的層級直接停用。前提是要把所有要關的類別都列出來，因為沒列的會回到寬鬆預設。

能不記就不記（第一層）；非記不可，就在送出前用 hook 精準刪除（第二層）；整類都不該收，就用 dataCollection 明確關閉並逐一指名（第三層）。

反例：這條規則什麼時候會翻車

第一，只設 beforeSend 就以為 log 也安全。log 不經過 beforeSend，這是這整套設定最容易中的一個錯。看到 log 裡出現 email，多數人第一個反應是去改 beforeSend，但那份鉤子根本不會被呼叫。

第二，用 pattern 去猜名字。有人會想「我把所有看起來像姓名的字串過濾掉就好」。但姓名沒有固定格式，病歷欄位更是五花八門，這種做法註定漏。正確的做法是源頭分類：console 整類丟棄、genAI 整類關閉，而不是逐一比對。

第三，忘了 replay 的遮罩。mobile replay 如果關掉遮罩，畫面上的姓名、生日、病歷列、聊天訊息會以影片形式整段進 Sentry。Dentify 的範例刻意在開發時關遮罩，是為了用假病人驗證流程；註解也明講，真實病人登入前必須把遮罩打開，或把取樣率降到 0。這是一個「規則會翻轉」的典型：開發環境的方便設定，到了 production 就是一個資安洞。

第四，以為關了 span 屬性就萬無一失。錯誤訊息裡的綁定參數是另一條路，必須靠第二層的 beforeSend 再洗一次。三層各管各的縫隙，缺一層都會漏。

可以直接套用的決策規則

看到一筆可能敏感的資料，先問「不記它我能不能除錯」：能，就在寫入時就別寫（第一層）。非留不可，就用 beforeSend 管錯誤、beforeSendLog 管 log，把 user 縮成 id 並刪掉 email / name（第二層）。整類都不該存在，就在 dataCollection 裡明確關掉 genAI、databaseQueryData、stackFrameVariables 與 http bodies，並記得未列出的類別會回到寬鬆預設（第三層）。最後檢查 replay 遮罩與 instrumentation 載入時機，因為這兩處各有自己的縫。

把資料擋在邊界內之後，你終於可以放心地往 AI 功能加觀測了。下一節要處理的正是：當 app 呼叫 LLM，你要怎麼知道它花了多少 token、等了多久、哪個工具被呼叫，同時又不讓病人的對話內容流進 Sentry。
