敏感資料該在哪一層被擋下

Step 3/5 · 觀測深化：Logs / Tracing / Agent Tracing

學習目標

學完這一節，你能在三個位置之間做選擇——寫 log 時就只記 id／數量／耗時、用 beforeSendLog 或 beforeSend 鉤子去識別化、在 instrumentation 的 dataCollection 關掉整類收集——並說出什麼時候該用哪一個。

前言：查得到的東西，也代表流得出去的

前兩節我們努力讓 log 更好查，欄位愈豐富、關聯愈完整，除錯就愈方便。但同一件事換個角度看就變成風險：log 是上傳到第三方雲端服務的。當你為了還原現場，把病歷、姓名、email 一起寫進去，這些資料就離開了你的伺服器。對醫療或金融類的 app 來說，這不只是技術問題，而是法律與合規問題。

於是你被兩股力量拉扯：一邊是「要能除錯，資料愈完整愈好」，另一邊是「要能合規，敏感資料愈少愈好」。真正的問題不是「要不要去識別化」——那一定要做——而是「到底該在哪一層把它擋下來」。這一節要幫你把這個決定講清楚。

學習目標回顧與情境

這個節點的 app 是一個牙醫診所系統：行動端給病患、網頁端跑員工 dashboard。系統會出現真正的病歷（PHI，protected health information，受保護的健康資訊），也會呼叫 OpenAI 做助理對話。也就是說，錯誤、log、trace 三條觀測管道，每一條都有機會夾帶病歷。我們要在這三條管道上，決定攔截點。

三個候選位置放在同一張桌上

去識別化不是單一動作，而是一組可以在不同層級做的事。先把它們並排比較：

攔截位置做法優點代價
寫入端（source）寫 log 時就只放 id、數量、耗時，不放內容最便宜、最直接，資料從沒離開過裝置靠紀律，漏寫一個欄位就破功
送出鉤子（hook）用 beforeSendLog／beforeSend 在上傳前改寫或刪除欄位集中一道關卡，能處理多處來源要預期各種資料形狀，改壞會影響判讀
收集設定（dataCollection）在 instrumentation 關掉整類收集，如 genAI inputs/outputs、資料庫查詢內容、堆疊變數最強的保證，整類資料根本不會被蒐集除錯資訊也一起少掉，範圍要拿捏

行動端與網頁端的實作各自展示了不同層次的組合。行動端的 Sentry.init 以「不主動送個資」為原則：關閉預設的 PII 傳送、過濾掉 console 的 breadcrumb，並用 beforeSend 與 beforeSendLog 把使用者資訊縮減到最小；行動端的 replay 仍保留，但預設遮罩。網頁端更嚴格：因為員工 dashboard 畫面上就是病歷，客戶端乾脆不開 session replay，並在伺服器端的收集設定裡把 AI 輸入輸出、資料庫查詢內容與堆疊變數整類關掉。

判別問句：用四個問題挑位置

與其背規則，不如每次拿這四個問題問自己：

  1. 這個欄位是我自己指定要寫的嗎？如果是你手寫的 log，最乾淨的做法就是在寫入端只放 id、數量、耗時，根本不要讓內容進入字串。能在源頭解決，就不要留到後面攔。
  2. 這類資料是否整批都不該出現？如果你的 app 有明確的敏感類別，例如「任何 AI 的輸入與輸出都不該上雲」，那就用 dataCollection 把它整類關掉，而不是逐筆靠 hook 判斷。整類禁止，用開關；個別例外，用鉤子。
  3. 資料是第三方 SDK 自動收集的嗎？有些 breadcrumb、網路請求內容、console 訊息，不是你寫的，而是 SDK 自動夾帶的。這種你控制不到寫入點，只能靠 hook 或收集設定來擋。
  4. 把它拿掉之後，我還 debug 得動嗎？去識別化的代價是失去資訊。請確認留下的 id 與耗時仍足以追查，否則你會把問題一起關掉。

反例：單靠一層為什麼會破功

只靠寫入端。你很有紀律，每行 log 都只放 id，但某個第三方 SDK 自動把 API 回應的內容塞進 breadcrumb，或在崩潰時附上區域變數。這些不是你寫的，寫入端的紀律管不到。

只靠 hook。beforeSendLog 確實是集中關卡，但它的邏輯要能預期資料的形狀。當 SDK 版本更新、多了一個新欄位，或物件結構改變，你的刪除條件可能就失準，敏感欄位悄悄溜過去。鉤子是補網，不是唯一防線。

把一切都關掉。如果為了安全，把 log、trace、replay 全部關閉，你確實不會外洩，但也等於放棄整個觀測體系。去識別化的目標是「留下能追查的骨架」，不是「什麼都不留」。像 AI 監控這種情況，關的是輸入與輸出的內容，但 token 數、延遲、模型名稱這些非內容的指標仍要保留——它們才是你診斷成本與效能的依據。

可以直接套用的決策規則

能在寫入端就不記的，就不要記，只留 id、數量、耗時。有整類資料永遠不該上雲的，用 dataCollection 整批關閉，而不是靠逐筆判斷。第三方 SDK 自動夾帶、你控制不到來源的，交給 beforeSend／beforeSendLog 這道集中鉤子去識別化。三層一起用，並在每次新增資料欄位時回頭問第四個問題：拿掉之後，我還查得下去嗎？

小結

去識別化不是單一設定，而是三層分工：能在寫入端就不記的，只留 id、數量與耗時；整類永遠不該上雲的，用 dataCollection 一次關掉；第三方 SDK 自動夾帶、你控制不到來源的，交給 beforeSendLog 與 beforeSend 集中攔截。判斷位置時問四個問題：欄位是不是我寫的、這類資料是否整批都不該出現、來源是不是 SDK 自動產生、拿掉後我還能不能追查。最後記得，去識別化的目標是留下可追查的骨架，而不是把觀測全部關掉。

當敏感資料確定被擋住，我們才敢放心把觀測往 AI 功能延伸。下一節會講 Sentry 的 agent tracing：它怎麼追蹤 token 用量、延遲與工具呼叫，又為什麼要另開一個 Next.js 專案、並搭配這一節剛建立的去識別化紀律。
