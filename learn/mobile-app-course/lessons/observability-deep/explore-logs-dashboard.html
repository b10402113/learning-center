在 Sentry Logs 視圖裡把問題圈出來

Step 2/5 · 觀測深化：Logs / Tracing / Agent Tracing

前言：資料送出去了，然後呢

上一節你已經知道結構化 log 該長什麼樣：訊息、severity 等級，加上一組只放 id、數量與耗時的屬性。但 log 送進 Sentry 之後，真正的功夫才開始：當畫面上是一萬行事件，你要怎麼在幾秒內圈出「昨天下午、錯誤等級、跟付款有關」的那一小塊？

這一節是一份操作程序。做完之後，你會得到一個具體的結果：能在 Explore Logs 裡用條件把問題縮小、能看出時間軸上的異常尖峰，並把這套查詢存下來或匯出，讓下一次同樣的排查不用從零開始。

學習目標

能照著步驟在 Sentry 的 Explore Logs 裡選對專案、讀懂一則 log 的細節，用 severity 與 property 條件逐層篩選、疊成多條件搜尋，讀出時間軸的尖峰，最後把查詢存成監控或匯出成 CSV / JSON。

動手前需要具備什麼

這份程序假設你已經完成兩件事：app 端已接好 Sentry，而且 Sentry.init 開了 enableLogs: true；同時，現實中已經有 log 被送進某個 Sentry 專案。如果 log 還是空的，先回到上一節確認 enableLogs 有沒有開，再回來走這幾步。

步驟一：進 Explore Logs，選對專案

打開 Sentry，進到 Explore 底下的 Logs 檢視。第一件事是選對專案。如果你同時有 mobile 與 web 兩個 Sentry 專案，這裡選錯就會看到完全不相關的資料。選好之後，log 不一定會立刻出現，因為 SDK 是把 log 緩衝起來、定時才批次送出，稍等一下或重新整理即可。

在 Dentify 的範例裡，還有一個刻意設計的小幫手：測試頁下方會顯示剛剛那一批的 batch_id，提示你把它貼進 Logs 搜尋欄，一次把那批執行完整撈出來。

Paste the batch_id into the Logs search bar to isolate one run. Every line also
carries a scenario, so `scenario:"Morning rush — 60 bookings"` pulls back a
whole rush across runs.

步驟二：先讀懂一則 log 的內容

在篩選之前，隨手點開一則 log，先看清楚它包含哪些資訊。你會看到兩類資料疊在一起：一類是你自己在程式裡寫的屬性，例如 dentist_id、duration_ms、service；另一類是 Sentry 自動補上的 context，例如作業系統、app 版本、environment、裝置型號。

更關鍵的是，log 旁邊通常會帶著連結，可以跳到同一時刻的 trace 與 session replay。也就是說，當你看到一則「appointment booked 但 duration 特別久」的 log，可以直接往下追到那一次的效能 span，或看回放確認當下畫面的狀態。這是結構化 log 和錯誤、trace、replay 綁在同一條時間軸上的價值。

步驟三：用 severity 把範圍砍一半

接著開始篩選。最省力的一刀是砍在 severity 上：如果你想找壞掉的事，先只留下 error 等級；想同時看警告，就把 warning 也納入。在搜尋欄打上一個 property 條件，例如 severity:error，結果就會從上萬行瞬間縮到幾十行。範例演示裡，這個條件把結果收斂到 22 筆。

severity:error

鬆一點的寫法是用 contains，意思是「這個欄位裡有出現 error 這個字」，適合欄位值不固定的情況；精確一點就用等號指定某個值。先用寬的條件確認資料長相，再逐步收緊，通常是比較順手的節奏。

步驟四：疊成多條件搜尋

單一條件不夠精準時，就往下疊。你可以組合不同欄位，例如「severity 是 error、而且 service 是 cleaning」；也可以對同一個欄位下多個可能值，例如同時要 info 與 error 兩種等級。除了字串條件，還能加上數值與日期條件，例如「duration_ms 大於 2000」或「發生在最近 24 小時」。條件的數量沒有限制，重點是每一步都讓結果更接近你心中那個問題。

severity:error service:cleaning
severity:info OR severity:error
duration_ms:>2000
batch_id:8f2a41

這裡有一個判讀上的細節：條件下得太多，可能一筆都不剩，但這不代表問題不存在，只代表你的條件彼此矛盾。遇到空結果時，先用兩個條件試，再慢慢加第三個，藉此確認資料本身符合預期。

步驟五：拉時間軸找尖峰

結果列表上方通常有一張隨時間變化的圖。當某個時間點突然湧入一批事件，圖上會翹起一個尖峰。你可以直接在那個區間上拖曳，把時間範圍縮到尖峰附近，再回頭看這一段裡的 log 有什麼共同特徵：是同一個 error_code、同一台裝置型號，還是同一個版本。尖峰本身不告訴你原因，但它幫你把「一整天的資料」縮成「那五分鐘的資料」，這正是後續判讀的起點。

步驟六：把查詢存下來、匯出去

如果你發現某組條件值得常常回來看，例如「付款相關的 error」，就把它存成 saved query，之後一鍵重跑；也可以進一步設成 monitor 或 widget，讓它在超過門檻時主動提醒你。需要離線分析或拿給同事時，Sentry 也支援把查詢結果匯出成 CSV 或 JSON。

這一步常被忽略，但它是把一次性排查變成可重複流程的關鍵。下一次同一種問題再發生，你不用重新摸索條件，只要打開存好的查詢就好。

小結

在 Explore Logs 裡的順序是：先選對專案、等 log 進來；點開一則確認它同時帶著自訂屬性與 Sentry 補上的 context，並能連到 trace 與 replay；再用 severity 砍掉大部分雜訊；不夠精準就疊成多條件搜尋，必要時加上數值與時間條件；遇到異常就拖曳時間軸、把範圍縮到尖峰附近找共同特徵；最後把常用條件存成查詢或監控，需要時匯出 CSV / JSON。整套動作的目的只有一個：用條件代替捲動，把問題圈到肉眼可讀的大小。

你現在能在資料裡把問題圈出來了。但圈出問題之後，下一個更根本的疑問會冒出來：這些 log 裡的資訊，有些根本不該被送上雲端。姓名、生日、病歷這類敏感資料，到底該在哪一層被擋下？下一節要處理的就是這件事。
