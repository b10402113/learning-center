在 Sentry Logs 視圖裡把問題圈出來

Step 2/5 · 觀測深化：Logs / Tracing / Agent Tracing

學習目標

這一節結束時，你能在 Sentry 的 Explore Logs 裡，用 severity 與 property 條件把幾千筆紀錄縮到幾筆，做出多條件搜尋，讀懂時間軸上的尖峰是怎麼回事，並把常用查詢存下來或匯出成 CSV／JSON。

前言：log 有了，但幾千筆要從哪一筆看起？

上一節我們確認了結構化 log 該長什麼樣：訊息、severity 等級，加上可查詢的 tag。現在假設資料已經送上去了，你打開 Sentry 的 Logs 視圖，迎接你的卻是一條長長的流水——幾千筆事件在同一分鐘內湧入，有正常紀錄，也有出錯的。這時候你可能會想：我明明有 log 了，為什麼還是找不到那筆關鍵紀錄？

問題出在「查」這個動作需要方法。結構化 log 的好處不是自動的，它要你下對條件才釋放出來。這一節就是動手操作：把「瀏覽」變成「下查詢」，一步一步把範圍從幾千筆縮到你能盯著看的那幾筆。

動手前先確認的三件事

這是程序型的一節，先確認前置條件都到位，後面才不會卡住。你需要：(1) app 端的 Sentry.init 已經開啟 enableLogs，否則 log 根本不會送出；(2) 有一批可查的資料，可以來自開發用的 log 測試頁，或你剛剛在真機上操作的紀錄；(3) 能進到 Sentry 專案的 Explore Logs，並且選得到正確的專案。

第一步：先用測試工具把資料灌進去

真實世界不會等你準備好才出錯，所以這個節點用一個開發用的 log 測試頁來演練。它準備了幾種情境：booking 正常與搶位衝突、助理對話、第三方服務降級、刪帳號後留下的孤兒資料，還有一顆會一次送出上百筆的批次按鈕。

按下去之後，預期會看到 log 陸續出現在 Dashboard。這裡有個容易忽略的細節：手機上的 log 是批次、非同步上傳的，程式關得太快可能就沒送出去。所以在送出後要主動觸發一次 flush，強制把緩衝區清空：

await Sentry.flush();  // 確保這批 log 真的送到 Sentry，而不是還沒送出就被關掉

先送出一批，再進 Dashboard。沒有資料的儀表板是空的，先造出可查的東西，後面每一步才看得到效果。

第二步：選對專案與時間範圍

進到 Explore Logs 後，第一件事是選對專案。這個節點的 app 有兩個 Sentry 專案——行動端一個、Next.js 網頁後端一個——log 會落在各自所屬的專案底下。選錯專案，你會以為「怎麼一筆都沒有」。

接著把時間範圍拉到剛剛送 log 的區間。範圍太大，幾週的紀錄會把畫面塞滿；範圍太小，可能剛好錯過你送出的那一批。養成「先縮時間，再縮條件」的順序，因為時間是最便宜、最沒有爭議的過濾器。

第三步：先過 severity，把雜訊切掉

時間範圍內一定混著各種等級的事件。info 是正常的紀錄，例如餐點已建立；真正要處理的是 error 與 fatal。在 Explore Logs 的查詢列，你可以用 property 條件把範圍限縮，例如：

severity contains error

這個查詢只留下等級欄位含 error 的紀錄。在示範資料裡，這一步可能就把幾千筆砍到幾十筆。預期看到的是列表縮短，而你要的錯誤類型開始浮出來。判讀 normalize 後的等級、把 warning 與 error 分開看，是這裡的主要動作。

第四步：用 property 把範圍再切細

只靠 severity 還不夠精準。回想上一節的欄位設計：我們在 log 上帶了 feature、scenario、batch_id。這些就是第二層條件。例如你想專注在預約流程的搶位衝突：

feature = booking
scenario = race

每加一個條件，結果就更接近你真正要問的問題。這就是為什麼欄位命名要一致——如果這次寫 feature、下次寫 module，條件就對不起來，log 再結構化也查不動。

第五步：多條件搜尋與時間軸尖峰

實務問題常常需要同時滿足好幾個條件，甚至要跨等級比較。Sentry 的查詢支援把條件疊起來，例如同時看 info 與 error：

severity = info AND severity = error

也可以加上數值或日期條件，例如只看 duration_ms 超過 1000 的紀錄，或限定最近兩小時。除了列表，畫面上方有一條隨時間變化的統計圖。當某個時間點的長條突然拉高，那通常代表一次集中的故障或尖峰。你可以直接在圖上拖曳一個區間，把它當成新的時間過濾器，只保留那段時間的 log。

拖曳時間軸這個動作，是把「什麼時候壞的」變成可操作的條件。很多線上事故不是慢慢累積，而是在某一分鐘突然爆發；能在圖上框出那一分鐘，就等於直接跳到案發現場。

第六步：把有用的查詢存起來、匯出

當你調出一組好用的條件——例如「severity 是 error 且 feature 是 booking」——不必每次重打。你可以把它存成已儲存的查詢，掛成 Dashboard 上的監控或小工具，之後一打開就看到這個數字。團隊還會把常見查詢固定下來，變成值班時的標準檢查表。

需要拿資料去跟別人討論或做後續分析時，Sentry 也支援把查詢結果匯出成 CSV 或 JSON。匯出的是你當下篩選後的資料集，所以請先確認條件正確，否則很容易把錯誤的範圍帶去開會。

小結

Explore Logs 的操作順序是：先選對專案與時間範圍，再用 severity 切掉雜訊，接著用 property 條件一層層收斂，需要時疊成多條件搜尋，並用時間軸的尖峰定位事故發生的那一刻。找到好用的條件就存成查詢與監控，要帶走資料就用 CSV／JSON 匯出。整個過程的關鍵心法只有一句：不要用眼睛翻，要用條件撈。

到這裡，你已經知道怎麼把有用的 log 查出來。但查得到的同時也代表一件事：log 是上傳到雲端的，如果裡面夾著不該外流的資料，你查得到，別人也可能查得到。下一節要處理的就是這條界線——敏感資料到底該在哪一層被擋下。
