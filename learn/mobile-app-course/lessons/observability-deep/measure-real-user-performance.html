用 Expo Observe 看上線後的效能

Step 5/5 · 觀測深化：Logs / Tracing / Agent Tracing

學習目標

學完這一節，你能說明 Expo Observe 量哪些真實使用者指標——app 開啟時間、JS 載入、首屏出現、可互動時間——並解釋為什麼在自己手機上測不出其他裝置與網路條件下的效能差異。

前言：你的手機，是全世界上最好的那台裝置

走到這裡，你已經能看見錯誤、查到 log、追蹤 AI 的成本與延遲。不過這些視角有一個共同點：它們大多發生在應用程式「內部」。而使用者實際感受到的，往往是另一件事——在他那台用了三年的手機上、在那個只剩一格訊號的地鐵裡，這個 app 到底開得夠不夠快。

而你用來開發的裝置，剛好是全世界上最好的那台：最新的手機、穩定的 Wi-Fi、系統快取還是熱的、離伺服器也近。你測起來一切流暢，很容易得出「效能沒問題」的結論。問題是，這個結論只對你成立。這一節要處理的，就是怎麼看見「真實使用者」的效能，而不是實驗室裡的效能。

為什麼開發機測不出真實效能

想像你在無風的室內放風箏。因為沒有風，你會誤以為這隻風箏根本飛不起來；但真實世界的變數從來不只一種。效能也是一樣：你的裝置、網路、作業系統版本、背景程式數量，全都和幾千名使用者不同。有人用入門機、有人開著省電模式、有人在跨國漫遊。同一個版本，在這些條件下可以差到好幾秒。

而且效能會「隨時間改變」。今天是好的，可能因為你新增了一個函式庫，明天啟動就慢了一截。開發機上的單點測試抓不到這種回歸，因為它只是一個瞬間、一個環境的數字。你需要的是持續、跨裝置、能看出變化的量測。

Expo Observe 量哪些指標

Expo 推出的 Observe 就是用來補這塊的：它在 app 上線後，追蹤真實使用者感受到的體驗。因為它跟 Expo／EAS 在同一個生態系裡，設定與發佈流程綁在一起。它量的核心指標有四項：

指標白話解釋
App 開啟時間從使用者點下圖示到 app 真的動起來的整體時間
JS 載入時間JavaScript 程式碼被下載與執行的時間，這是最容易隨版本變動的一段
首屏出現時間使用者第一次看到有意義的畫面（不是白畫面）要等多久
可互動時間畫面出現了，但什麼時候才真的能點、能滑、能操作

這四個指標的順序，正好對應使用者心中「app 到底啟動了沒」的四個階段。從點圖示、到程式碼載入、到畫面出現、到可以操作，任何一段變慢，使用者的體感就會打折扣。分開量它們的用意，是讓你能定位「慢在哪一段」，而不是只有一個籠統的「啟動很慢」。

它和 Sentry tracing 有什麼不同

你可能會問：前面不是已經學過 tracing 了嗎，為什麼還要 Observe？差別在觀測的範圍。Sentry tracing 的強項是「把一次操作拆開」，讓你看見某個請求、某個流程內部的每一段耗時，適合抓「這一次為什麼慢」。Expo Observe 看的則是「上線後整體使用者體驗的海量數據」，它把幾千台裝置上的同一個指標聚合起來，讓你看趨勢、看分佈、看某個版本上線後有沒有變。一個是顯微鏡，一個是氣象圖，兩者互補。

實際使用時，你會兩邊一起看。先用 Observe 發現「這個版本的啟動變慢了」，再用 tracing 與 log 去追是哪一行改動造成的。少了 Observe，你甚至不知道要追；少了 tracing，你只知道變慢卻找不到原因。

為什麼「變化」比「絕對值」重要

效能數字本身常常很難判斷好壞：首屏兩秒算快還是慢？不同裝置、不同地區的標準都不一樣。相對地，「變化」永遠有意義。Observe 會把指標隨時間畫成趨勢，所以你最該盯的是：某個新版本發佈之後，這些線有沒有明顯往上跳。

舉例來說，你在某次更新加了三個新的函式庫，發佈後發現「可互動時間」比上一版多了一秒。這個變化會出現在跨裝置的聚合圖上，因為它不是你的裝置特別慢，而是所有裝置一起變慢。這種「回歸」如果沒有持續量測，通常要等到客服收到抱怨才會發現，而那時候使用者已經開始流失了。

怎麼用它做判斷

實務上，把它當成版本的健康檢查表。每次發版後，比較啟動四個階段的中位數與前幾版，如果有明顯上升，再切到不同裝置、作業系統與網路條件去看，確認是普遍變慢還是特定族群受影響。必要時對照 Sentry 的 tracing 與 log，把範圍收斂到某一個功能或依賴。觀察的順序是「先看趨勢、再切維度、最後才鑽進單一操作」，這正好和前面 log 的操作順序相反——一個從全局往細節，一個從細節找特定事件。

小結

開發機是全世界上最好的裝置，測不出真實世界的效能差異；上線後要看的是跨裝置、跨網路、隨時間變化的數據。Expo Observe 量四個指標：app 開啟、JS 載入、首屏出現、可互動時間，各自對應使用者啟動體驗的一個階段。它和 Sentry tracing 互補——Observe 負責發現「哪個版本變慢了」，tracing 與 log 負責追「為什麼」。判讀時先看變化而不是絕對值，因為同樣的秒數在不同裝置上意義不同，而回歸趨勢永遠值得追。

這個節點到這裡告一段落。你現在手上有一套完整的觀測：用 Sentry 抓錯誤與結構化 log，用 beforeSendLog 一類的機制守住隱私，用 agent tracing 看 AI 的成本與延遲，再用 Expo Observe 掌握真實使用者的效能。把這套東西接進你自己的 app，你就不會再靠「使用者有沒有來信」來判斷它過得好不好。
