用 Expo Observe 看上線後的效能

Step 5/5 · 觀測深化：Logs / Tracing / Agent Tracing

前言：在我手機上明明跑很順

前面幾節談的錯誤、log、trace、AI 成本，全部都是「應用程式自己回報的數字」。你設定好、觸發它、它就乖乖把資料送上雲端。但有一件事，app 自己答不出來：真實使用者在他們自己的裝置上，實際等了多少秒才看到畫面。

你大概聽過這句話：「在我手機上跑很順啊」。問題是，你的手機是新的、網路是好的、快取是熱的，而你的使用者可能拿的是三年前的中階機、在捷運上訊號斷斷續續、而且還是當天第一次打開 app。第一次啟動要載入多少 JavaScript、多久才顯示第一個畫面、多久才能互動，在這些條件下會跟你的體驗完全不同。這一節要講的 Expo Observe，就是用來量這件 app 自己看不到的事。

學習目標

學完後，你應該能說出 Expo Observe 量的是哪幾個真實使用者指標：啟動時間、JavaScript 載入、首屏時間、可互動時間，並解釋為什麼「在我手機上很順」不能代表數千台裝置上線後沒問題，以及為什麼效能退步要靠「隨時間變化」才看得出來。

開發者手機的偏差

為什麼不能只靠自己的裝置判斷效能？因為你的測試環境是整個分布裡最好的那一端。你的手機型號新、記憶體大；你的網路是穩定的 Wi-Fi；你反覆測試時，很多資源早就被快取住。這三個條件同時成立，你就會得到一個樂觀到不真實的印象。

當 app 真的散到幾千台裝置上，分布會攤開：舊機 CPU 慢、記憶體小，冷啟動時要重新載入整個 JS bundle；弱網使用者下載資源的時間可能是你的十倍。這些情境在你的手機上根本不會發生，但它們才是多數使用者每天面對的現實。你需要的不是「最好的那一台跑起來怎樣」，而是「這幾千台跑起來，分布長什麼樣」。

Expo Observe 量的是哪幾個真實使用者指標

Expo Observe 是 Expo 推出的觀測工具，專門量 app 上線後在真實使用者端的效能。它關注四個關鍵時間點，沿著使用者從點開 app 到能操作它的那條線：

指標量的是什麼使用者感受到的對應體驗
App open time從點下圖示到 app 開始運作「我按了，它到底有沒有反應」
JavaScript load timebundle 下載與執行的時間從啟動到畫面出現前的那段等待
Time to first screen多久之後看到第一個畫面「是不是卡住了」的第一印象
Time until interactive多久之後畫面真的能操作看得到但按了沒反應的挫折感

這四個指標合起來，描述的就是使用者對「這個 app 快不快」的全部感受。尤其是最後一個，很多人只看「有沒有畫面出現」，但如果畫面出現了、按鈕卻還沒反應，使用者的體驗一樣是卡。這也是為什麼要把它拆成四個指標，而不是只看一個總時間。

為什麼它和 Expo / EAS 同一條生態特別有用

Expo Observe 的第一個優勢是它長在你原本的 Expo / EAS 生態裡。你不需要再另外接一套效能監控、另外學一套 SDK 與 Dashboard，它就跟著你出 build、發版的那條流程。這聽起來像小事，但它決定了你會不會真的去用：工具和你既有的工作流越近，你開啟它的頻率就越高。

第二個優勢更關鍵。因為它跨裝置、跨作業系統、跨網路條件持續收集，你可以把效能看成「隨時間變化的曲線」，而不是「某一天的一個數字」。這一前一後的差別，正是抓效能回歸的關鍵。

效能退步是「變化」，不是「狀態」

假設你的 app 啟動要 1.8 秒。這個數字本身沒有好壞，它只是一個狀態。但如果上週是 1.2 秒，這週變成 1.8 秒，那就是一個明確的訊號：某次更新做了什麼，讓啟動慢了 50%。

效能回歸幾乎都是這樣被抓到的。它不是某一天 app 突然壞掉，而是某個新功能、某個新依賴、某段沒注意的初始化程式碼，悄悄讓每一步都慢了一點。只看單點快照，你只會覺得「好像還行」；看時間軸，你才會看到那條線在某個版本之後翹起來。有了這個對照，你就能直接回頭查那次改動，而不需要在模糊的「最近好像變慢」裡瞎猜。

它和 Sentry 是互補的兩隻眼睛

走完這個節點，你手上其實有兩套互補的觀測。Sentry 負責「內部發生了什麼」：錯誤、結構化 log、trace、session replay，以及 AI 功能的 token 與成本。Expo Observe 負責「使用者在外面實際等多久」：啟動、載入、首屏、可互動時間在數千台裝置上的分布。

兩者的問題不一樣，所以不能互相取代。Sentry 告訴你某個 API 花了三秒，Observe 告訴你使用者從點開到能用等了四秒。你必須兩個都有，才能把「哪一段慢」和「使用者感受到多慢」對起來。

小結

「在我手機上跑很順」不是證據，因為開發者的裝置剛好是整個分布裡最快的那一端。Expo Observe 量的是真實使用者的四個時間點：app 啟動、JavaScript 載入、首屏出現，以及真正能互動。它長在 Expo / EAS 生態裡，跨裝置、跨 OS、跨網路持續收集，所以效能退步會以「隨時間變化的曲線」呈現。某次改版後啟動悄悄變慢，你才看得見。它和 Sentry 是兩隻互補的眼睛：Sentry 看內部發生了什麼，Observe 看使用者在外面等多久。

到這裡，這個節點的觀測地圖就完整了。你從結構化 log 學會把「發生了什麼」變成可查詢的資料，用 Explore Logs 把問題圈出來，用三層防線把敏感內容擋在邊界內，用 agent tracing 看見 AI 的成本與延遲，最後用 Expo Observe 接住真實使用者的效能感受。這五塊合起來，就是 app 上線之後你眼睛能看到的全部範圍。
