Agent tracing：看得見 AI 功能的成本與延遲

Step 4/5 · 觀測深化：Logs / Tracing / Agent Tracing

前言：AI 功能最貴、最慢的那一段，錯誤列表看不到

上一節你把敏感資料擋在邊界內，現在可以放心地問下一個問題：你的 app 開始呼叫 AI 了，但你知道它到底表現如何嗎？一則「助理回覆」在使用者眼裡只是幾秒鐘的等待，對你來說卻是一連串成本與效能的決定：這次用了哪個模型、吃掉多少 token、花了多少錢、等了幾秒、有沒有呼叫工具、回覆過程中有沒有出錯。

這些疑問，錯誤列表一題都答不了。因為 AI 功能最貴、最慢、最容易失控的那一段，通常不是「壞掉」，而是「勉強能跑但代價很高」。使用者不會回報「這次回答貴了三倍」，但月底的帳單會。這一節要講的 agent tracing，就是把這一整段從黑箱變成看得見的數字。

學習目標

學完後，你應該能說明 agent tracing 追蹤哪些指標（token、成本、延遲、工具呼叫、錯誤率），為什麼 AI 功能要用獨立的 Sentry 專案來接，以及怎麼在保留這些指標的同時，把病歷內容擋在 gen_ai span 之外。

Agent tracing 到底在追什麼

Agent tracing 是 Sentry 針對 AI 功能設計的一種觀測。它把每一次 LLM 呼叫變成一條 span，並在 span 上掛一組數字。你在 Dashboard 上看到的，大致是這幾類：

指標看什麼拿來回答什麼問題
Token 用量prompt 與 completion 各用了多少 token這段 prompt 是不是越長越肥
成本依模型單價換算的每次花費哪個功能在燒錢
延遲從送出到完成的毫秒數使用者為什麼等了那麼久
模型這次呼叫的是哪個模型不同模型的用量與表現如何分布
工具呼叫模型有沒有觸發工具、呼叫了哪些助理的行為是否符合預期
錯誤率模型呼叫失敗的比例供應商是不是在鬧脾氣

把這些數字放在一起，還能回答一個更高階的問題：這條 AI 功能值不值得留？當你看到某個捷徑回答平均要三秒、每次兩分錢，而使用者其實很少用，這個資訊會直接影響你的產品決策。Agent tracing 的定位就在這裡：它不是除錯工具，而是 AI 功能的成本與效能儀表板。

為什麼要另開一個 Sentry 專案

Dentify 的做法是為 agent tracing 建立一個獨立的 Sentry 專案，平台選 Next.js。原因是架構決定的：AI 的 API route 跑在 Next.js 的 web 專案裡，而不是 mobile app 裡。mobile 的錯誤、session replay 由 mobile 專案收；AI 的 token、成本與 gen_ai span 由 web 專案收。分成兩個專案，兩邊的資料不會互相稀釋，各自的取樣與額度也能分開控制。

要讓這條線成立，前提是伺服器端的 tracing 是開著的。設定檔裡有一行註解說得很明白：agent tracing 是搭在 tracing 之上的，所以 tracesSampleRate 必須大於 0，否則 span 根本不會產生。

  // ponytail: every transaction is sampled. Fine at this traffic — drop it to
  // ~0.1 (or a tracesSampler that keeps gen_ai traces at 1.0) once there is
  // real load. Agent tracing rides on tracing, so this must stay > 0.
  tracesSampleRate: 1.0,

怎麼接：包住 OpenAI client，再綁上對話與使用者

接線的動作只有兩步。第一步是在呼叫模型前，把使用者和對話標上。使用者只放 id，因為 email 也是一種識別碼，分組用一個穩定值就夠；對話則用 setConversationId 綁定。這個 id 同時也是 thread id，所以同一條對話在不同時間、不同請求進來的每一輪，都會落在同一個 Sentry conversation 裡，而不是散成好幾條孤立的 trace。

  // Agent tracing. Both are scoped to this request, and both have to be set
  // before the model call below or the span is orphaned.
  //
  // The thread id doubles as the conversation id, so every turn of one chat
  // lands in a single Sentry conversation across separate requests and traces.
  // The user is id-only on purpose: a patient's email is an identifier, and
  // the User column only needs something stable to group by.
  Sentry.setUser({ id: user.id });
  Sentry.setConversationId(conversation.id);

第二步是讓 Sentry 包住 OpenAI 的 client，並用它來發請求。真正的 span 是這個 wrapper 產生的，所以如果你直接 new OpenAI() 而不經過 instrumentOpenAiClient，模型照樣會回話，但你不會得到 token 與成本。另外，串流回覆要記得加上 stream_options: { include_usage: true }，因為 OpenAI 預設不會在串流結果裡附上 token 數量，沒有這個選項，gen_ai span 就沒有用量、也就沒有成本估算。

  // The wrapper is what produces the gen_ai span — model, tokens, cost and
  // latency. Not the prompt or the reply; see the PHI note at the top.
  //
  // ponytail: `openai@7` is past the range Sentry documents as supported
  // (>=4 <7); the wrapper only touches `chat.completions.create`, which has
  // not changed, and spans were verified landing. Recheck on an openai major.
  const openai = Sentry.instrumentOpenAiClient(
    new OpenAI({ apiKey: process.env.OPENAI_API_KEY })
  );
  const completion = await openai.chat.completions.create({
    model: AI_MODEL,
    messages: [
      { role: 'system', content: SYSTEM_PROMPT },
      ...history.map((m) => ({ role: m.role, content: m.content }) as const),
    ],
    max_tokens: 400,
    temperature: 0.3,
    stream: true,
    // OpenAI omits token counts from streamed responses unless asked. Without
    // this the gen_ai span has no usage, and so no cost estimate.
    stream_options: { include_usage: true },
  });

保護病歷：留下指標，關掉內容

這裡有一個張力：agent tracing 預設會擷取 prompt 與回覆，讓你在 Dashboard 上重播整段對話。但在醫療情境裡，病人自己打的症狀描述正是最敏感的內容。Sentry 的 Conversations 檢視就是靠這些輸入輸出重建出來的，如果照預設開著，等於把病歷整段送上雲端。

解法是把 genAI 的 inputs 與 outputs 關掉。關掉之後，你仍然拿得到 token、成本、延遲、模型與錯誤，只是 span 上不帶 prompt 與回覆；Conversations 還是能列出這條對話與它的輪次，但不會重播任何訊息內容。也就是說，指標全數保留，內容一個字都不進去。

    genAI: { inputs: false, outputs: false },

route 檔開頭的註解把這個取捨講得最清楚：那段自由文字不會進 Sentry，但 token、成本、延遲、模型與錯誤都會留下；只有當你確定跑的是假病人時，才可以考慮把兩個開關打開。

 * That same free text does NOT go to Sentry: `genAI: { inputs: false, outputs:
 * false }` in sentry.server.config.ts keeps the prompt and the reply off the
 * gen_ai span, so Conversations lists the thread and its turns but replays no
 * message content. Tokens, cost, latency, model and errors all survive that.
 * Flip the two flags to true only if PLAN.md A15 (seeded fake patients) is
 * still what is running — a real patient's symptoms are PHI.

小結

Agent tracing 把每一次 AI 呼叫變成帶數字的 gen_ai span：token 用量、成本、延遲、模型、工具呼叫與錯誤率。它用在 Next.js 專案，因為 AI 的 API route 跑在 web 端，所以另開一個 Sentry 專案接住這些資料，而且 tracesSampleRate 必須大於 0 才會有 span。接法是呼叫前先 setUser（只放 id）與 setConversationId，再用 instrumentOpenAiClient 包住 client，串流時加上 include_usage。最關鍵的取捨是把 genAI 的 inputs / outputs 關掉，指標全留、內容不進，讓 AI 功能看得見成本，又不讓病歷外流。

到這裡，你已經能在錯誤、事件、效能與 AI 成本四個層面看見 app 的內部狀態。但這些全部都是「應用程式自己回報的數字」。最後還有一塊拼圖：真實使用者在數千台不同裝置上，實際感受到的啟動與載入速度。下一節要講的 Expo Observe，處理的正是這件應用程式無法自己回答的事。
