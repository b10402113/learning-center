Agent tracing：看得見 AI 功能的成本與延遲

Step 4/5 · 觀測深化：Logs / Tracing / Agent Tracing

學習目標

學完這一節，你能解釋 Sentry 的 agent tracing 捕捉哪些東西——token 用量、延遲、工具呼叫、錯誤率、使用者輸入——以及它為什麼要用獨立的 Next.js Sentry 專案、又要關掉哪些資料收集，才不會把病歷一起送出去。

前言：AI 沒出錯，但帳單和等待時間悄悄失控

上一節處理完敏感資料的去識別化，我們終於可以放心把觀測延伸到 AI 功能。這裡有個新的盲點：傳統的錯誤監控只在你「失敗」時才出聲，可是 AI 功能最常見的問題不是失敗，而是「成功，但很慢、很貴」。使用者按了助理，等了八秒才開始回話；某一天 OpenAI 的費用突然翻倍，你卻不知道是哪個功能、哪個模型造成的。

一般的 tracing 能告訴你「這趟請求花了幾秒」，但它看不見 AI 特有的東西：這次用了多少 token、呼叫了哪個模型、有沒有動用工具、輸入被餵了什麼。要回答「AI 為什麼貴、為什麼慢」，你需要的是專門為 AI 設計的觀測，也就是這一節的主角：agent tracing。

AI 功能需要另一種儀表板

先把 agent tracing 和前面學過的 tracing 分開。一般 tracing 的對象是「一段程式執行」，例如一個 API 請求，它把時間拆成 span，讓你看見哪一段慢。agent tracing 的對象則是「一次 AI 代理的運作」，它除了時間，還加上了模型與代理相關的維度。兩者能接在同一條時間軸上，但關注的指標不同。

為什麼需要多這層？因為 AI 呼叫有幾個一般 tracing 量不到的成本來源。第一是 token：同一個功能，提示詞寫得囉唆一點，成本可能差好幾倍。第二是模型選擇：換一個模型，延遲與單價都會變。第三是工具呼叫：代理如果中途去查了資料庫、呼叫了外部 API，這些步驟會拉長整體時間。第四是使用者輸入：什麼樣的問題會讓代理繞遠路。這些都是「成功路徑」上的問題，錯誤列表看不到，只有 agent tracing 看得見。

Agent tracing 實際上捕捉什麼

接上之後，Sentry 的 AI agents 總覽會把這些維度攤開。它捕捉的核心指標包括：

指標回答的問題
Token 用量這次對話花了多少輸入與輸出的 token
延遲從送出請求到模型回完，總共等了多久
工具呼叫代理中途動用了哪些工具、次數多少
錯誤率AI 相關的請求有多少比例失敗
使用者輸入使用者問了什麼類型的問題（在去識別化前提下）

在總覽頁面上，這些會聚合成跑次數、成本、執行時間、各模型的 LLM 呼叫次數與 token 數量。你可以把它想成 AI 功能的「油耗表」：不是告訴你車子有沒有拋錨，而是告訴你每一趟開下來花了多少油、塞在哪一段路。當你調整整段提示詞或換模型時，這張表就是你判斷划不划算的依據。

為什麼要另開一個 Sentry 專案

這個 app 是 monorepo：行動端在 Expo，AI 的 API route 在 Next.js 的網頁專案裡。當你把 agent tracing 接進 AI 功能，追蹤的對象其實跑在伺服器端，而不是手機上。因此做法是：在同一個 Sentry 組織底下，另外建立一個 Next.js 平台的專案，取得它自己的 DSN，再把設定補齊。

多專案的結構反映的是架構的事實：行動端與網頁端是兩套部署、兩種執行環境。好處是各自的錯誤、log、trace 不會混在一起，你可以針對「網頁後端」單獨看 AI 的成本與延遲。這也是為什麼前面在 Explore Logs 時要不斷提醒「先選對專案」——專案就是觀測的邊界。

去識別化的 context：追得到，但看不到內容

agent tracing 最有價值的矛盾在這裡：你希望追蹤一次對話的完整足跡，卻不希望在雲端留下任何病歷。解法是把「身分」與「內容」拆開。身分用 id 表示，內容則整類關閉。

在 AI route 裡，典型做法是先設定使用者與對話，再把 OpenAI 客戶端包起來讓它自動產生 span。使用者只帶 id，不帶姓名或 email；對話用一個 conversationId 標記，讓同一次對話的多輪請求能被串在一起。示意如下：

Sentry.setUser({ id: userId });            // 只留 id，不帶姓名或 email
Sentry.setConversationId(conversationId);  // 把同一次對話的多輪請求串起來
instrumentOpenAiClient(openai);            // 讓 OpenAI 呼叫自動產生 span

接著在伺服器端的收集設定裡，把生成式 AI 的輸入與輸出整類關閉。這樣一來，你在總覽上仍然看得到「這次對話花了多少 token、等了幾秒、有沒有出錯」，但看不到對話的實際文字。搭配前面的 dataCollection 設定——關閉 AI 輸入輸出、資料庫查詢內容與堆疊變數——病歷就不會被夾帶進 trace。YouTube 上的示範就是這個組合：追得到足跡，但看不到內容。

這張儀表板能回答什麼

接好之後，最實用的幾種問法包括：哪一個模型在這條路徑上最慢；過去一週的成本趨勢是不是在漲；某一批對話為什麼錯誤率偏高；代理是不是常常繞去呼叫工具。這些問題都不是「有沒有壞」，而是「好不好、貴不貴、慢不慢」，正好補上錯誤監控的空白。

值得一提的是，agent tracing 的資料本身沒有內容，所以你不需要為了除錯而在 trace 裡看病人說了什麼。當你懷疑是提示詞或資料造成的問題，會改用 log 的 id 與計數去對照，而不是把原文撈回來。觀測與隱私在這裡不是互相妥協，而是靠「指標歸指標、內容歸內容」分工。

小結

AI 功能的典型問題是「成功但很慢、很貴」，錯誤監控看不到，要用 agent tracing。它捕捉 token 用量、延遲、工具呼叫、錯誤率與使用者輸入，並在 AI agents 總覽上聚合成成本、執行時間與各模型的呼叫次數。因為 AI 跑在 Next.js 網頁專案，所以要另開一個 Sentry 專案與 DSN，形成行動端加網頁端的多專案結構。最重要的是把身分與內容拆開：用 id 當使用者、用 conversationId 串對話、包住 OpenAI 客戶端產生 span，同時把生成式 AI 的輸入輸出整類關閉，讓病歷留在系統裡，只把可追蹤的骨架送上雲端。

到這裡，你已經能看見錯誤、查到 log、追蹤 AI 的成本與延遲。但這些都是「應用程式內部」的視角。使用者真正感受到的，往往是另一回事：在他那台舊手機、在那個訊號很差的地鐵上，app 到底開得夠不夠快？下一節要把視角拉到真實使用者，看 Expo Observe 怎麼量這件事。
