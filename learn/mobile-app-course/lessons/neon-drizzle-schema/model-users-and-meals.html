建 users 與 meals：從欄位到索引，看懂資料模型的設計

Step 2/5 · Neon + Drizzle 資料建模

學習目標

讀完這一節，你會看懂 users 與 meals 兩張表的欄位、關聯、索引與時間設計，也能說明每個設計決定正在解決什麼問題。

前言：一張會透露決策的資料藍圖

當使用者上傳一張餐點照片，app 需要知道這張照片屬於誰、AI 是否正在分析、分析出了多少熱量，以及這筆紀錄應該出現在使用者哪一天的餐點清單裡。這些需求最後都會落在資料模型上。

上一節確立了一件事：資料模型要用 TypeScript 寫成 schema，而且它是 app 與背景 task 共用的唯一事實。現在把鏡頭拉近，看看 Cal AI 的 schema 實際長什麼樣子。

讀 schema 時，不要只是把欄位名稱從頭唸到尾。可以把它看成作者留給你的決策清單：為什麼身分欄位要唯一？為什麼生日不用時間戳記、體重卻用數字？為什麼餐點表要特別做索引？每個看似普通的欄位，通常都對應一個已經踩過，或是想先避開的坑。

這個 app 的主線很單純：一個使用者會記錄很多餐。因此資料模型由兩張表組成，users 和 meals 之間是一對多關聯。接下來看到的 enum、外鍵、可空欄位與索引，都可以放回這條主線來理解。

先把值限制住：enum

schema 開頭定義了五個 enum，也就是「只允許特定幾個值」的欄位。與其讓欄位接受任意文字，不如先把合法選項寫清楚，讓不合法的資料在進入資料庫前就被擋下來。

export const unitPreferenceEnum = pgEnum("unit_preference", ["metric", "imperial"]);
export const goalEnum = pgEnum("goal", ["lose", "maintain", "gain"]);
export const activityLevelEnum = pgEnum("activity_level", ["sedentary", "light", "moderate", "very", "extra"]);
export const dietPreferenceEnum = pgEnum("diet_preference", ["classic", "keto", "vegan", "vegetarian"]);
export const mealStatusEnum = pgEnum("meal_status", ["analyzing", "completed", "failed"]);

以 meal_status 為例，一筆餐點只可能處於三種狀態之一：

  • analyzing：AI 正在分析。
  • completed：分析已完成。
  • failed：分析失敗。

如果這裡使用一般文字，某天程式不小心把 completed 拼成 complete，資料庫可能照收不誤，但首頁查詢如果只尋找 completed，這筆資料就會像突然蒸發一樣被漏掉。使用 enum 後，錯誤的值會直接被資料庫拒絕。

這裡也埋了一個伏筆：activity_level 裡的 extra 並不是最初建表時就存在，而是後來才加入。這會在下一節介紹 migration 時看到，正好可以用來理解 schema 如何隨需求演進。

users 表：自己的主鍵，外部身分的連結

users 表可以分成幾個區塊。最先要看的是它如何和 Clerk 對接：

export const users = pgTable("users", {
  id: uuid().primaryKey().defaultRandom(),
  clerkUserId: text().notNull().unique(), // Clerk is source of truth for identity
  email: text(),
  timezone: text(), // IANA, e.g. "America/New_York"
  unitPreference: unitPreferenceEnum(), // display only

id 是這張表自己的主鍵，由資料庫透過 defaultRandom() 產生 UUID，不依賴外部傳入的值。

clerkUserId 則是和外部身分系統接上的那條線。它存放 Clerk 提供的使用者 id，並標記為 unique，代表同一個 Clerk 身分在表中只能對應一列資料。註解也說得很明白：Clerk 是身分的來源，這張表負責保存對應關係。

為什麼不直接把 Clerk 的 id 當成主鍵？因為這會把內部資料模型綁死在特定的身分供應商上。現在是 Clerk，未來如果更換供應商，外部 id 可能需要調整；自己的 id 則可以繼續留在系統內，其他表的關聯也不用跟著重做。這就是「內部主鍵」和「外部身分 id」分開的價值。

timezone 存的是 IANA 時區名稱，例如 Asia/Taipei。後面的 seed 與查詢都會用到它，因為「今天吃了什麼」不是只看 UTC 日期，而是取決於使用者在哪個時區度過這一天。

users 表裡的資料，分別在描述什麼

除了身分連結，users 表還包含身體數據、目標設定，以及建立與更新時間。把這些欄位放在一起看，會比較容易理解它們各自的角色：

欄位型別設計用意
gender / dateOfBirthtext / date生日用 date，不用時間，因為生日沒有時區
heightCm / weightKgnumeric(mode: number)體重有小數，用 numeric 並轉成 number 方便運算
goal / activityLevel / dietPreferenceenum限制成問卷提供的選項
paceKgPerWeeknumeric每週想減或增幾公斤，供計算目標熱量
dailyCalories / proteinG / carbsG / fatGintegerAI 算出的每日目標，以整數克與大卡儲存
planRationale / planGeneratedAttext / timestamp目標產生的理由與時間，方便回溯
onboardingCompletedAttimestamp是否完成 onboarding 的判準

其中最值得停下來看的是 dateOfBirth。它使用 date({ mode: "string" })，在 TypeScript 裡會是日期字串，而不是 Date 物件。

原因很簡單：生日是一個日曆上的日子，不是一個需要精確到某個時區的時間點。如果把生日存成時間戳記，系統就可能開始處理「這是幾點的生日」，使用者跨時區後，生日甚至可能在畫面上往前或往後跳一天。這種麻煩完全沒有必要，所以用日期字串表達最直接。

體重則是另一種情況。70.5 公斤是合理值，因此使用 numeric 而不是整數，並轉成 number 方便後續運算。至於 AI 算出的熱量與三大營養素，畫面上的目標本來就是整數大卡與整數公克，就沒有必要保留小數。

共用的時間戳記：記住資料何時發生

兩張表共用同一組時間欄位：

const timestamps = {
  createdAt: timestamp({ withTimezone: true }).notNull().defaultNow(),
  updatedAt: timestamp({ withTimezone: true })
    .notNull()
    .defaultNow()
    .$onUpdate(() => new Date()),
};

withTimezone: true 對應到 Postgres 的 timestamptz。它表達的是一個絕對的時間點，而不是某個地區牆上時鐘顯示的模糊時間。

defaultNow() 會在新增資料時自動填入建立時間。$onUpdate 則會在資料更新時刷新 updatedAt。這組設定抽成共用區塊，讓兩張表使用同一套規則，不必各自重複撰寫。

meals 表：先建立紀錄，再逐步填入分析結果

meals 表是 app 持續累積的核心資料。除了要連回哪個使用者，還要描述一筆餐點目前分析到哪裡：

export const meals = pgTable(
  "meals",
  {
    id: uuid().primaryKey().defaultRandom(),
    userId: uuid()
      .notNull()
      .references(() => users.id, { onDelete: "cascade" }),
    imageUrl: text().notNull(), // ImageKit URL
    status: mealStatusEnum().notNull().default("analyzing"),

    name: text(),
    calories: integer(),
    proteinG: integer(),
    carbsG: integer(),
    fatG: integer(),

    errorReason: text(), // "not_food" | "parse_failed" | …
    triggerRunId: text(), // for Realtime subscribe / debugging

    loggedAt: timestamp({ withTimezone: true }).notNull().defaultNow(),
    ...timestamps,
  },
  (t) => [index("meals_user_logged_at_idx").on(t.userId, t.loggedAt.desc())],
);

userId 是外鍵，指向 users.id。它設定了 onDelete: "cascade"，表示刪除一列使用者時，底下相關的 meals 也會一併刪除。

這正好對應刪除帳號的需求：使用者按下刪除後，資料庫本身就能確保不會留下沒有主人的餐點紀錄。與其事後再靠程式逐筆清理，不如把這條資料完整性規則交給資料庫執行。

可空欄位，其實是在描述資料生命週期

status 的預設值是 analyzing。照片一上傳，app 可以立刻建立餐點紀錄並顯示「分析中」，不用等 AI 花上幾秒到十幾秒回應後，才讓使用者看到這筆資料。

因此，name、calories、proteinG 等分析結果欄位都允許空值。當狀態還是 analyzing 時，這些欄位本來就還沒有結果；如果分析失敗，也可能不會有完整的營養資料。

這裡的可空性不是「先放著，以後再說」，而是在反映資料的生命週期：餐點先被建立，接著進入分析，最後才可能填入完整結果。

errorReason 用來記錄失敗原因，例如照片裡沒有食物的 not_food，或解析失敗的 parse_failed。triggerRunId 則保存背景 task 的執行 id，前端可以用它訂閱即時進度，也能在發生問題時協助除錯。

為什麼 meals 需要索引

schema 的最後一行建立了這個索引：

index("meals_user_logged_at_idx").on(t.userId, t.loggedAt.desc())

它同時使用使用者與記錄時間兩個欄位，而且時間採遞減排序。這完全對應首頁最常見的查詢：「找出這個使用者某一天的餐點，新的排在前面。」

如果沒有索引，資料庫可能每次都得掃過整張 meals 表，再找出符合條件的紀錄。資料量小時也許感覺不出差異，但資料持續增加後，查詢就會越來越慢。

索引就像書末的索引頁。你不會為了找一個名詞，把整本書從第一頁重新讀一遍；你會先查索引，再直接翻到相關頁面。資料庫也是同樣的道理。

欄位順序也不是隨便排的：先放 userId，再放 loggedAt。因為查詢通常會先鎖定某個使用者，再按照時間排序，所以索引順序要貼近實際查詢條件，才能有效命中。

儲存使用 metric 與 UTC，顯示時才換算

schema 檔開頭的註解，其實抓住了整體設計的核心原則：儲存用公制與 UTC，換算只發生在顯示的那一刻。

不論使用者偏好公制或英制，也不論使用者住在哪個時區，資料庫裡一律儲存公制單位與 UTC 時間。使用者看到的英制數值與在地時間，則是在 app 準備顯示資料前才換算。

這個規則像是替資料庫訂出一把統一的尺。若資料庫裡同時混著公制與英制、各地當地時間，每次查詢都得先確認「這筆資料到底採用哪種單位或時區」，久了就很容易出錯。

把標準集中在儲存層，並把換算收斂到顯示層，資料庫就只需要維持一種可靠的內部格式；不同使用者的顯示偏好，也不會反過來污染原始資料。

把這張藍圖掛回 app

Cal AI 的資料模型只有兩張表：users 一對多 meals。用 enum 鎖住合法值，用 clerkUserId 對應外部身分並保留自己的主鍵，用 date 存沒有時區的生日，用 timestamptz 存絕對時間點。meals 用外鍵加上 cascade，讓刪除使用者時餐點自動清乾淨；分析結果欄位允許空值，反映「先建立、後填滿」的生命週期；再用一個 (userId, loggedAt desc) 的索引服務首頁最常見的查詢。整體原則是儲存公制加 UTC，換算只在顯示時發生。

現在可以把這份 schema 當成一張完整的資料藍圖來看：users 負責身分與個人設定，meals 負責一筆筆餐點紀錄；外鍵把兩者接起來，enum 和可空性描述資料的邊界與生命週期，索引則照顧 app 最常見的查詢。
