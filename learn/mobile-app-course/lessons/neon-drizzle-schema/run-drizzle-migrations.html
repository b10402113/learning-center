跑 migration：edit schema → generate → migrate

Step 4/5 · Neon + Drizzle 資料建模

這一節要完成什麼

上一節已經把 Drizzle 接到 Neon，資料庫連線也確認正常。這一節要再往前一步：把 src/db/schema.ts 裡的資料模型，真正變成 Neon 上的資料表。

完成後，你會得到一個可以重複執行、也能留下變更紀錄的流程：

  1. 修改 schema。
  2. 執行 npm run db:generate，產生 migration。
  3. 執行 npm run db:migrate，把 migration 套用到資料庫。

你也會知道怎麼閱讀 Drizzle 產生的 SQL，以及 drizzle/meta/ 裡的 journal 和 snapshot 在記錄什麼。

先記住整個迴圈：edit → generate → migrate

schema.ts 比較像是資料庫的藍圖。你把藍圖畫好，房子不會自己長出來；還需要把藍圖轉成施工圖，再實際施工。

  1. edit：修改 src/db/schema.ts，例如新增一個欄位或一張表。
  2. generate：執行 npm run db:generate。Drizzle 會比較目前的 schema 和上一次的 snapshot，算出差異，並產生新的 SQL migration。
  3. migrate：執行 npm run db:migrate。Drizzle 會依序執行尚未套用的 migration，真正建立或修改資料庫中的表。

這裡最容易混淆的是後兩步。generate 只是在產生施工圖，migrate 才是真的動工。因此，改完 schema.ts 後直接查看資料庫，發現裡面沒有變化，是正常的；你還必須完成 generate 和 migrate。

第一步：確認 schema 變更

先在 src/db/schema.ts 編輯資料模型。這個專案目前會建立 users 和 meals 兩張表，並包含 enum、外鍵、預設值與索引等設定。

只要你新增欄位、新增資料表，或調整既有欄位，就要把這次變更交給 Drizzle 產生 migration。不要直接手動修改資料庫，否則 schema、migration 和實際資料庫可能會逐漸對不起來。

第二步：產生 migration

在專案中執行：

npm run db:generate

第一次對空的資料庫模型執行 generate 時，Drizzle 會產生一個帶編號的 SQL 檔，例如 drizzle/0000_foamy_shatterstar.sql。檔案內容是標準的 Postgres DDL，會先建立 enum 型別：

CREATE TYPE "public"."activity_level" AS ENUM('sedentary', 'light', 'moderate', 'very');
--> statement-breakpoint
CREATE TYPE "public"."meal_status" AS ENUM('analyzing', 'completed', 'failed');
--> statement-breakpoint
CREATE TYPE "public"."unit_preference" AS ENUM('metric', 'imperial');

接著，migration 會建立資料表。先看 meals：

CREATE TABLE "meals" (
	"id" uuid PRIMARY KEY DEFAULT gen_random_uuid() NOT NULL,
	"user_id" uuid NOT NULL,
	"image_url" text NOT NULL,
	"status" "meal_status" DEFAULT 'analyzing' NOT NULL,
	"name" text,
	"calories" integer,
	"protein_g" integer,
	"error_reason" text,
	"logged_at" timestamp with time zone DEFAULT now() NOT NULL
);

讀這段 SQL 時，可以逐項對回原本的 schema：

  • id 是 UUID 主鍵，預設使用 gen_random_uuid() 產生。
  • user_id 和 image_url 使用 NOT NULL，代表不能省略。
  • status 使用 meal_status enum，預設值是 analyzing。
  • name、calories、protein_g 和 error_reason 沒有 NOT NULL，因此可以是空值。
  • logged_at 使用帶時區的 timestamp，預設值是目前時間。

接著檢查外鍵與索引。它們通常會出現在 SQL 檔案後段：

ALTER TABLE "meals" ADD CONSTRAINT "meals_user_id_users_id_fk"
  FOREIGN KEY ("user_id") REFERENCES "public"."users"("id")
  ON DELETE cascade ON UPDATE no action;
--> statement-breakpoint
CREATE INDEX "meals_user_logged_at_idx"
  ON "meals" USING btree ("user_id","logged_at" DESC NULLS LAST);

在 TypeScript schema 裡設定的 onDelete: "cascade"，在 SQL 裡就變成 ON DELETE cascade。而 index(...).on(...) 則變成資料庫中的索引。

命名也會依照設定轉換。TypeScript 裡的 userId、imageUrl 和 loggedAt，會在資料庫中變成 user_id、image_url 和 logged_at，這就是 casing: "snake_case" 發揮作用的地方。

讀懂 migration 檔名與分隔線

檔名中間的 foamy_shatterstar 是 Drizzle 隨機產生的名稱，主要用來讓 migration 有一個容易辨識的標籤。真正影響順序的是前面的編號，例如 0000。

檔案中的 --> statement-breakpoint 是 Drizzle 用來標記 SQL 語句邊界的分隔線。看到它時，可以把前後內容理解成兩個分開執行的 SQL 區段。

同步檢查 meta 檔

generate 不只會產生 SQL，也會更新 drizzle/meta/ 裡的檔案。這些檔案不是多餘的產物，而是 Drizzle 下一次計算差異時需要的紀錄。

第一類是 _journal.json。它記錄 migration 的順序：

{
  "version": "7",
  "dialect": "postgresql",
  "entries": [
    { "idx": 0, "tag": "0000_foamy_shatterstar", "breakpoints": true },
    { "idx": 1, "tag": "0001_narrow_bishop", "breakpoints": true }
  ]
}

可以把它想成 migration 的流水帳：每產生一份 migration，就登錄一筆。idx 表示順序，tag 對應 migration 名稱。

第二類是 snapshot，例如 0000_snapshot.json。它記錄某個時間點上，schema 的完整樣子。下一次執行 generate 時，Drizzle 會拿目前的 schema 和最近的 snapshot 比對，找出這次新增或修改的部分，然後只產生對應的差異。

因此，snapshot 必須進版控。它不是可以刪掉的暫存檔，而是下一次 generate 判斷差異的依據。少了它，Drizzle 可能會誤以為資料表都是新的。

第三步：執行 migrate

警告：只有在確認產生出的 SQL 符合預期後，才執行 migrate。這一步會真的修改 Neon 上的資料庫。

執行：

npm run db:migrate

Drizzle 會參考 _journal.json 的順序，把尚未執行的 migration 送到 Neon 執行。它也會記錄哪些 migration 已經套用，因此重複執行 migrate 是安全的，不會把同一份 migration 套用兩次。

執行完成後，回到 Neon dashboard，或開啟 db:studio 檢查結果。你應該會看到：

  • users 和 meals 兩張表已經存在。
  • 欄位名稱與型別符合 schema。
  • 外鍵已經建立。
  • 索引已經建立。

模型變更時：新增 migration，不要改舊檔

資料模型會持續演進，不會一次定案。這個專案就有一個例子：activity_level 後來需要加入 extra，但最初的 migration 0000 只建立到 very。

這時不要回頭修改已經存在的 0000，而是新增一份 migration：

ALTER TYPE "public"."activity_level" ADD VALUE 'extra';

這就是 0001_narrow_bishop.sql 的全部內容。它沒有重寫第一份 migration，而是使用新的 migration 擴充既有 enum。

原因是 0000 可能早已在某個環境執行過。這時即使你回頭修改檔案，已經建立好的資料庫也不會重新執行它；不同環境反而可能因為看到不同版本的 migration 而產生落差。

因此，規則很簡單：已經套用的 migration 不要回頭改；新的資料庫變更就新增一份 migration。

另外也要留意 enum 的限制。新增值通常是安全的 append 操作，但移除或重新命名既有值就複雜得多，通常需要重建型別。因此設計 enum 時，最好先想清楚可能會用到哪些值。

db:push：只適合丟棄式原型

Drizzle 也提供 db:push。它會直接把 schema 同步到資料庫，跳過產生 migration 檔。

如果你正在做一次性的原型實驗，或資料庫隨時可以丟棄，db:push 確實很方便。但這個專案的正式流程應該使用 generate 加 migrate。

原因是 db:push 不會留下完整的變更紀錄。當資料庫改動沒有對應到可以檢查、可以進版控的 SQL 檔時，你就很難回答「這次到底改了什麼」。正式環境需要可追溯的 migration 歷史，因此把 db:push 留給原型，正式流程則固定走：

edit schema → npm run db:generate → npm run db:migrate

完成檢查

做完這一節後，請確認以下結果：

  1. src/db/schema.ts 已經描述目前的資料模型。
  2. drizzle/ 裡有帶編號的 SQL migration。
  3. drizzle/meta/_journal.json 記錄了 migration 順序。
  4. snapshot 檔已經保留並加入版控。
  5. npm run db:migrate 已成功執行。
  6. Neon 或 db:studio 中可以看到 users 和 meals，以及對應的欄位、外鍵和索引。
改 schema.ts 不會自動改變資料庫，要走 edit → db:generate → db:migrate 這個迴圈。generate 會比對 schema 與最近快照，產生一份帶編號的 SQL migration；migrate 才依序把變更套用到資料庫，而且重複執行是安全的。meta 裡的 _journal.json 記錄順序、snapshot 記錄每個時間點的完整 schema，是下一次算差異的依據，必須進版控。模型要演進時，不要改舊的 migration，而是新增一份，就像 0001 用 ALTER TYPE ... ADD VALUE 替 enum 加上 extra 那樣。

現在，兩張表已經真實存在於 Neon 上。不過它們還是空的，首頁看不到任何資料，背景 task 也沒有資料可分析。下一節會寫一個 seed 腳本，灌入一組寫實的測試資料，並讓腳本可以重複執行、使用參數化查詢，還能把使用者的本地時間正確轉換成 UTC。
