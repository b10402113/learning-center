兩階段上傳：pending → ready → published 的生命週期

Step 2/5 · Convex 檔案儲存與上傳

學習目標

能描述 uploads 資料列從 pending 到 ready 再到 published 的狀態機，並說出擁有者如何從登入身分推導、purpose 為何要分離，以及一小時過期與排程清理在防什麼。

前言：檔案還沒到，資料庫要先寫什麼？

上一節我們知道檔案本體存在 _storage，文件只留一個 storageId。現在把鏡頭拉到使用者按下「發佈」的那一刻。照片還在手機上、影片可能幾十 MB、網路還可能中途斷掉。如果等到檔案完全上傳成功才寫資料庫，你在接收檔案的當下，根本不知道這個請求屬於誰、要拿來做貼文還是頭像，也就無法判斷「他有沒有資格上傳」。但如果你反過來，先寫資料庫再收檔案，那中途失敗時又會留下一筆永遠等不到檔案的紀錄。

解法是把一次上傳拆成兩個階段：先開一張「單子」記下意圖與擁有者，再把檔案送進來核銷這張單子。Codexgram 用一張 uploads 資料列來當那張單子，狀態就在 pending、ready、published 之間移動。

一次上傳會經過的三個狀態

先看全貌，再拆細節：

狀態代表的意思怎麼進入
pending有人打算上傳，但檔案還沒到client 呼叫 begin
ready檔案已存進 _storage，並綁定 storageIdHTTP action 呼叫 finish
published檔案已被貼文、頭像或限動正式採用發佈動作呼叫對應的 mutation

之所以要區分 ready 和 published，是因為「檔案傳完了」和「檔案正在被使用」是兩件事。傳完但還沒被採用的檔案，是隨時可以被清掉的暫存品；一旦被貼文採用，它就有了存在的理由，清理機制必須放過它。這個區分正是後面過期與取消邏輯的判準。

第一步：begin 先開一張 pending 單

流程從 begin 這個 mutation 開始。它接受用途、型別、寬高，以及影片才需要的時長，先做基本檢查，然後插入一筆狀態為 pending 的資料列：

export const begin = mutation({
  args: {
    purpose: v.union(v.literal('post'), v.literal('avatar'), v.literal('story')),
    kind: mediaKind,
    width: v.number(),
    height: v.number(),
    duration: v.optional(v.number()),
  },
  handler: async (ctx, args) => {
    const me = await requireProfile(ctx);
    // 寬高必須是合理範圍內的正整數
    if (![args.width, args.height].every(n => Number.isInteger(n) && n > 0 && n <= 30000))
      throw new ConvexError('Invalid media dimensions.');
    // 影片只能是貼文，且長度在 0 到 30 秒之間
    if (args.kind === 'video' && (args.purpose !== 'post' || !args.duration
        || !Number.isFinite(args.duration) || args.duration > 30 || args.duration <= 0))
      throw new ConvexError('Videos must be 30 seconds or shorter.');

    const id = await ctx.db.insert('uploads', {
      ...args, ownerId: me._id, state: 'pending',
      expiresAt: Date.now() + 60 * 60 * 1000,
    });
    await ctx.scheduler.runAfter(60 * 60 * 1000, internal.uploads.expire, { id });
    return id;
  },
});

這段程式有幾個值得留意的設計。首先，擁有者不是從參數傳進來的，而是用 requireProfile(ctx) 從登入身分查出來的；client 無法假裝自己是別人。其次，檢查的是「寬高是不是整數、有沒有超過三萬」這類範圍，而不是精確值，因為真正的檔案內容還沒到，這裡只能先擋掉明顯不合理的意圖。最後，資料列一建立就排定一小時後的 expire，這是清理孤兒的第一道保險。

回傳的 id 會被 client 帶去下一步的 /upload。有了這張單子，接收檔案的那一端才知道「這個請求屬於誰、上限是多少、要存成什麼用途」。

第二步：finish 綁定 storageId，狀態變 ready

檔案透過 HTTP action 存進 _storage 後，會呼叫一個 internal mutation finish，把剛剛拿到的 storageId 綁回那張 pending 單子：

export const finish = internalMutation({
  args: { id: v.id('uploads'), tokenIdentifier: v.string(),
          storageId: v.id('_storage'), duration: v.optional(v.number()) },
  handler: async (ctx, args) => {
    const upload = await ctx.db.get('uploads', args.id);
    const owner = upload && await ctx.db.get('profiles', upload.ownerId);
    if (!upload || owner?.deletionRequested
        || owner?.tokenIdentifier !== args.tokenIdentifier
        || upload.expiresAt <= Date.now())
      throw new ConvexError('Upload expired.');
    if (upload.storageId) return upload.storageId; // 幂等：已綁過就直接回傳
    await ctx.db.patch('uploads', upload._id, {
      storageId: args.storageId, state: 'ready',
      ...(args.duration ? { duration: args.duration } : {}),
    });
    return args.storageId;
  },
});

這裡有兩個關鍵。第一是身分複驗：單子上的擁有者 tokenIdentifier 要跟這次請求的身分一致，帳號也不能正在刪除中。第二是冪等（idempotent）：如果這張單子已經綁過 storageId，就直接回傳原本那個，不要重複寫入。上傳這種動作很容易因為網路重試而送達兩次，冪等設計讓重送不會產生第二個檔案。

另外，finish 是 internalMutation，不是一般的 mutation。意思是它只能被 server 端的其他函式呼叫，client 不能直接觸發。這樣就把「綁定 storageId」這個動作牢牢鎖在 /upload 的流程裡，別人無法跳過驗證自己亂綁。

第三步：published 才代表正式採用

檔案變成 ready 之後，還要等真正被使用時，才推進到 published。以頭像為例，setAvatar 會檢查這筆上傳的用途確實是 avatar、型別是圖片、狀態是 ready 且未過期，然後把使用者的 avatarId 指過去，並把上傳狀態改成 published：

if (me.avatarId) await ctx.storage.delete(me.avatarId); // 舊頭像當場刪
await ctx.db.patch('profiles', me._id, {
  avatarId: upload.storageId, avatarUrl: undefined, avatarUpdatedAt: Date.now(),
});
await ctx.db.patch('uploads', upload._id, { state: 'published' });

貼文與限動也是同樣的模式：發佈時把 storageId 寫進 posts 或 stories，並把對應的 upload 標成 published。這個標記的用處，在下一段就會看到。

過期與取消：不讓孤兒檔案留下來

使用者按了上傳又中途放棄，是再正常不過的事。如果沒有清理機制，pending 和 ready 的資料列與檔案就會一直堆著。Codexgram 用兩條路徑處理：

  • expire（internal）：由 begin 排定的一小時後執行。如果這筆上傳還沒 published，就刪掉檔案本體與資料列。
  • cancel（一般 mutation）：使用者主動取消時觸發，只有擁有者能呼叫，同樣會刪掉檔案與資料列，但 published 的不動。

兩個清理路徑都有一個共同前提：狀態是 published 就放過它。因為那代表檔案已經被某則貼文或某個頭像正式引用，刪掉會讓畫面開天窗。至於排程清理為什麼可靠，是因為它由 server 的 scheduler 觸發，就算 client 早就關掉 app，時間到了照樣會執行。

為什麼要分 post、avatar、story 三種用途

uploads 資料列上有一個 purpose 欄位，值只能是 post、avatar、story。這不是分類好看而已，而是把三種媒體的規則分開：

用途允許的型別特殊規則
avatar只有圖片檔案較小（上限 5MB），只能有圖片
post圖片或影片影片上限 30 秒、50MB
story只有圖片24 小時後過期

有了這個欄位，系統就能在接收檔案時拒絕「影片被當成頭像」這種錯誤組合。試想如果沒有 purpose，/upload 收到的只是一個檔案，它無法判斷現在該套用影片的 50MB 上限、還是頭像的 5MB 上限，也無法決定要不要解析時長。用途就是讓規則有地方落腳。

擁有者一律從登入身分推導

回頭看整個生命週期，擁有者從來沒有出現在 client 傳來的參數裡。begin 用 requireProfile(ctx) 取得目前使用者，把 ownerId 寫進單子；/upload 則把登入身分裡的 tokenIdentifier 帶進 forUpload 查詢，比對單子擁有者的 tokenIdentifier 是否一致。

這個原則值得單獨記住：身分只能從 server 端的登入狀態推導，不能信任 request 送來的值。如果把擁有者當成參數，攻擊者只要改一個欄位，就能把檔案掛到別人名下，或用別人的單子上傳。這也是為什麼單子上要存 tokenIdentifier，而不是只在 client 快取一個使用者 id。

小結

一次上傳被拆成三個狀態：begin 先開一張 pending 單子（記錄擁有者、用途與一小時後到期），/upload 收完檔案後用 internal finish 綁上 storageId 變成 ready，正式被貼文或頭像採用時才變 published。擁有者一律從登入身分推導；purpose 讓三種用途各自套用不同規則；expire 與 cancel 會清掉未發佈的孤兒檔案，但放過已 published 的檔案。

到這裡，單子開好了、狀態機也清楚了，但檔案還沒真的進來。接下來最關鍵的一步，是判斷「送進來的到底是什麼」。下一步要處理驗證問題：型別、大小與時長，該信 client 還是 server？
