GET /media：授權讀取與 Range 串流

Step 5/5 · Convex 檔案儲存與上傳

學習目標

能解釋為什麼「拿到 URL」不等於「有權讀取」，以及 /media 如何從登入身分推導可讀的檔案、用 HTTP Range 分段回傳影片。

前言：檔案給了網址，就等於給了權限嗎？

上一節結束時，照片和影片已經安全地躺進 Convex 的 _storage，也綁好了單子。剩下的最後一哩路，是讓 app 把這些媒體顯示出來。最直覺的做法，是把 storageId 或一條 getUrl 產生的網址直接交給 client，讓它塞進圖片元件或影片播放器就好——方便、快，也幾乎不用寫後端。

但第一節已經埋了一個伏筆：那種網址是一種能力，拿到的人不必登入就能讀。對一則公開貼文或許沒差，可是社群 app 裡有大量不該公開的媒體：還沒發佈的草稿、只有朋友看得到的內容、私訊附件、使用者刪帳號後理當消失的東西。如果每次都只發一條無法撤銷的網址，你就再也沒有機會說「這個人現在不能看了」。這一節要把讀取端點 /media 講清楚，它解決的就是這個問題。

兩種讀取模型

讀取檔案大致有兩種模型，差別在「授權在什麼時候決定」：

模型授權時機適合的情境
公開能力 URL發出網址的那一刻本來就該公開的素材，例如網站 logo
授權端點每一次讀取請求私人、會變動、需要撤銷的內容

公開能力 URL 的問題在於「發出去就收不回來」。使用者把圖片網址複製到別的地方，或轉傳給朋友，你無法阻止。授權端點則相反：每一次有人要讀，server 都重新檢查一次。群組成員被移除了、帳號正在刪除、限動過期了，這些狀態變化都能在下一次請求時立刻生效。

判斷該用哪一種，可以問自己三個問題：這個內容本來就該公開嗎？外流的話能不能接受？需要撤銷或逐次驗證嗎？只要有一題的答案偏向「不行」，就該用授權端點。Codexgram 的媒體大多是私人內容，所以選了後者。

請求長什麼樣子

/media 是一個 GET 端點，它長這個樣子：

GET /media?kind=post&id=<貼文 id>
Authorization: Bearer <Clerk token>

注意 client 傳的是「貼文 id」、「個人檔 id」或「限動 id」，不是 storageId。這是一個刻意的設計。讓 client 傳業務層級的 id，server 才有機會判斷「這個人能不能看這則貼文」，再自己把 id 解成 storageId。storageId 是內部實作，不需要、也不應該讓 client 知道。

第一步：從登入身分查出可讀的檔案

端點進來後，跟 /upload 一樣先認身分，然後交給一個 internal query 去解析：

const identity = await ctx.auth.getUserIdentity();
if (!identity) return response('Sign in required.', 401);

const url = new URL(req.url);
const kind = url.searchParams.get('kind') === 'avatar' ? 'avatar'
  : url.searchParams.get('kind') === 'story' ? 'story' : 'post';

const storageId = await ctx.runQuery(internal.uploads.media, {
  id: url.searchParams.get('id') ?? '',
  kind, now: Date.now(), tokenIdentifier: identity.tokenIdentifier,
});
if (!storageId) return response('Media unavailable.', 404);

const blob = await ctx.storage.get(storageId);
if (!blob) return response('Media unavailable.', 404);

真正判斷授權的是 internal.uploads.media 這個查詢。它的邏輯是先按 tokenIdentifier 找到目前的使用者，如果帳號正在刪除中就一律回 null；接著依 kind 走不同分支：

  • post：把 id 解成貼文，回傳它的 storageId。
  • avatar：把 id 解成個人檔，回傳它的 avatarId。
  • story：把 id 解成限動，只有在 expiresAt > now（還沒過期）時才回傳。

任何一個分支找不到、或條件不符，就回 null，端點便回應 404。這裡有一個重要觀念：授權判斷發生在「id 對應到 storageId」的過程中，而不是比對 URL。就算有人猜中了某則貼文的 id，他仍然得先登入、且通過刪帳號等檢查，才拿得到內容。

第二步：影片用 Range 分段回傳

找到 blob 之後，直接把整個檔案回傳，對小圖片沒問題，對影片就很糟。一支 50MB 的影片，如果使用者只想先看前幾秒、或想拖動進度條跳到中間，卻得先把 50MB 全部下載完，播放體驗會很糟，也浪費頻寬。HTTP 的 Range 請求就是為此而存在：client 可以指定「我要第幾個到第幾個位元組」。

實作時，先解析 Range 標頭：

const headers = { ...cors, 'Content-Type': blob.type,
  'Accept-Ranges': 'bytes', 'Cache-Control': 'private, no-store' };
const range = req.headers.get('Range');

if (range) {
  const match = /^bytes=(\d*)-(\d*)$/.exec(range);
  if (!match || (!match[1] && !match[2])) return response('Invalid range.', 416);
  const start = match[1] ? Number(match[1]) : Math.max(0, blob.size - Number(match[2]));
  const requestedEnd = match[1] && match[2] ? Math.min(Number(match[2]), blob.size - 1) : blob.size - 1;
  const end = Math.min(requestedEnd, start + 8 * 1024 * 1024 - 1);
  if (start > end || start >= blob.size)
    return new Response(null, { status: 416,
      headers: { ...headers, 'Content-Range': `bytes */${blob.size}` } });
  return new Response(blob.slice(start, end + 1), { status: 206,
    headers: { ...headers, 'Content-Range': `bytes ${start}-${end}/${blob.size}`,
      'Content-Length': String(end - start + 1) } });
}

有幾點值得拆開看。回應的狀態碼是 206 Partial Content，不是 200，並附上 Content-Range 告訴 client「這次給的是整份檔案的第幾段到第幾段、整份有多大」。即使 client 一次要一大段，這裡也把單次回傳上限壓在 8MB（start + 8MB - 1），避免某個請求一次把大檔整包拉走。如果範圍不合理、或起點已經超過檔案大小，就回 416。

還有一種常見情況：client 根本沒帶 Range，但這是一支超過 8MB 的影片。這時候不該硬塞整包，而是先回前面 8MB，並標成 206：

if (blob.size > 8 * 1024 * 1024 && blob.type.startsWith('video/')) {
  const end = 8 * 1024 * 1024 - 1;
  return new Response(blob.slice(0, end + 1), { status: 206,
    headers: { ...headers, 'Content-Range': `bytes 0-${end}/${blob.size}`,
      'Content-Length': String(end + 1) } });
}
return new Response(blob, { headers: { ...headers, 'Content-Length': String(blob.size) } });

這樣播放器能立刻拿到開頭、開始播放，之後再按需要抓後面。小於 8MB 的檔案（大部分圖片）則直接整包回傳，狀態碼 200。無論哪條路徑，回應都帶 Accept-Ranges: bytes，等於告訴 client「這個資源支援分段讀取，你隨時可以指定範圍」。

第三步：client 端怎麼配合

在 app 這一側，讀取媒體的方式是把 token 放進標頭。Codexgram 的 useMediaSource 會組出一個帶 bearer token 的 /media 網址，交給 expo-image 或影片元件。因為頭像會更新，它還會在網址上加一個 v=revision 的參數，讓圖片快取在頭像換掉時失效、不會一直顯示舊圖。

這裡也呼應了為什麼 Cache-Control 要設成 private, no-store。私人媒體本來就不該被共用快取保存，畢竟同一條路徑對不同使用者可能回傳不同內容。把它標成不儲存，能避免代理伺服器或中間層不小心把某個人的照片快取起來、之後餵給另一個人。CORS 標頭則把 Content-Range 等資訊暴露出去，讓瀏覽器端的播放器能正確處理分段回應。

小結

/media 是一個授權端點：每次請求都先從登入身分查出使用者，再由 internal.uploads.media 依 kind 把貼文、頭像或限動 id 解成 storageId，同時檢查帳號狀態與限動是否過期。網址不會帶著 storageId，所以猜到 id 也不能直接讀。影片支援 HTTP Range，以 206、Content-Range 分段回傳、單次上限 8MB，讓播放器可以邊播邊抓、拖動進度；沒有 Range 的大影片先回前 8MB。回應設定 private, no-store，不讓私人媒體被共用快取。

走完這五步，你有一套完整的媒體管線：檔案存在 _storage、文件只留 storageId；上傳走 pending → ready → published 的狀態機；格式、大小與時長都在 server 端用檔案內容驗證；讀取則由授權端點把關。把用途與限制值換成你 app 的設定，這套流程就能直接搬過去用。
