媒體驗證該信誰？MIME、magic bytes 與尺寸限制

Step 3/5 · Convex 檔案儲存與上傳

學習目標

能在「信任 client 帶來的檔名與型別」和「server 端重新驗證」之間做出選擇，並為不同用途挑對格式、尺寸與時長限制。

前言：client 說這是 JPEG，你就信嗎？

上一節把上傳拆成開單與核銷兩個階段，單子裡也記下了用途與限制。現在檔案真的要送進來了，client 會順手附上一些資訊：檔名叫做 photo.jpg、Content-Type 是 image/jpeg、大小大約兩 MB。這些資訊看起來很合理，也讓 server 很方便判斷。

但請記得，client 是使用者手上的裝置，上面跑的程式可以被改、請求也可以用 curl 自己發。那串 Content-Type 不來自檔案本身，而是發送者自己填的字串；檔名更是隨手就能改。於是一個很實際的決定擺在眼前：驗證到底該放在哪一側、又可以信任哪些資訊？這個決定做錯，輕則使用者體驗差，重則有人能塞進一個超大檔案把後端打爆。

兩股張力：體驗和安全

在 client 端驗證的好處很直觀。使用者一選完檔案，app 立刻就能說「這張圖太大了，換一張」，不必先花三十秒把檔案傳上去、再被 server 拒絕。它省頻寬、反應快，是好的使用者體驗。

但 client 端驗證有一個致命弱點：它只在你的 app 裡成立。任何人打開終端機，對著 /upload 直接發請求，就跳過了所有 app 端的檢查。所以 client 端的驗證是一種「善意提示」，不是安全邊界。

server 端驗證相反。它擋不掉使用者選錯檔，但沒有人能繞過它。它是唯一能保證「不管請求從哪來、長什麼樣，都必須遵守規則」的地方。代價是發現問題時，檔案往往已經傳進來了，頻寬已經花了。

所以這不是二選一，而是分工：client 端做早期回饋，server 端做強制執行。兩邊都做同一套規則，只是角色不同。

三個判別問句

每當你不確定某個檢查該放哪一側，問自己這三個問題：

  1. 這個檢查如果被繞過，會發生什麼事？ 如果後果是「塞爆儲存空間」、「讓 action 記憶體爆掉」、「塞進惡意內容」，那它必須在 server 端。如果後果只是「使用者選了一張不好看的圖」，client 端提示就夠了。
  2. 這個值 client 能不能改？ 只要是請求裡的值——檔名、Content-Type、宣稱的寬高——都能改。凡是能改的值，都不能當成安全判斷的依據。
  3. 這個檢查需要讀檔案內容嗎？ 如果需要（例如確認它真的是 JPEG），那只有 server 端能可靠地做，因為 client 宣稱的型別與內容是兩回事。

為什麼 MIME、副檔名和 Content-Type 都不可信

先把「不可信」說清楚。當 client 送出上傳請求，它會帶一個 Content-Type 標頭。這個標頭是發送者自己填的，不是系統從檔案內容推出來的。同樣地，圖片選擇器回傳的 mimeType 也可能只是依照副檔名猜的。把一個文字檔改名成 movie.mp4，再配上 video/mp4 的標頭，這些欄位看起來就完全正常。

要驗真正的格式，只能讀檔案的開頭幾個位元組，這叫做 magic bytes（檔頭簽章）。每種格式在一開始都有固定的位元組特徵，變不了：

格式檔頭特徵
JPEG前三 bytes 是 FF D8 FF
PNG第一 byte 是 89，接著是 PNG
WebP開頭是 RIFF，第 8 到 12 bytes 是 WEBP
MP4 / MOV第 4 到 8 bytes 是 ftyp

實務上只需要讀開頭 32 個 bytes 就夠了。Codexgram 的 /upload 就是這樣做：它把 blob 切出前 32 bytes，轉成字元，再按照宣稱的型別去比對對應的簽章。比對不通過就回一個錯誤，檔案從頭到尾沒有真的被存下來。

為每個用途挑限制值

再來是「限制的內容」。因為 uploads 有 purpose，同一套驗證可以依用途給不同上限。Codexgram 的選擇如下：

用途允許格式大小上限時長上限
avatarJPEG、PNG、WebP、HEIC、HEIF5MB不適用
post（圖片）JPEG、PNG、WebP、HEIC、HEIF10MB不適用
post（影片）MP4、QuickTime50MB30 秒
storyJPEG、PNG、WebP、HEIC、HEIF10MB不適用

這些數字不是什麼定律，而是產品決策。頭像在畫面上只佔一小塊，5MB 已經很夠；貼文圖片要能被放大觀看，給到 10MB；影片無論如何都比圖片大，給 50MB。換成你的 app，這些值完全可以調整。真正不變的是那條原則：限制要在 server 端強制，而且依用途分開。

影片時長特別值得一提。client 端可以讀取影片長度，選完檔就能立刻顯示「這支太長了」。但這個長度也是裝置算出來的，必須在 server 端用檔案的內容重新確認。第 4 步會看 server 怎麼只讀 MP4 的檔頭就得到真實時長，完全不必解碼整支影片。

規則會翻轉的反例

把限制寫死的時候，要小心它對真實裝置的影響。假設你的允許清單只列了 JPEG 和 PNG，看起來很標準。但 iPhone 預設拍出來的格式是 HEIC，於是一堆 iOS 使用者會發現「我手機裡的照片全部上傳失敗」。這就是為什麼上面那張表一定要把 HEIC、HEIF 放進去。驗證規則要跟著真實世界的檔案格式走，而不是跟著你的直覺走。

另一個反例是時長。30 秒對社群貼文是合理的，但如果你做的是短影音或教學平台，這個限制會直接砍掉大量正當內容。同樣地，5MB 的頭像上限對一般照片很夠，但如果你的 app 主打高解析度專業作品展示，這個值就太低了。限制值是可調的旋鈕，不是道德律令；該堅持的是「兩側都有檢查、server 做最後一道」。

決策規則：一張可以帶著走的檢查表

凡是安全邊界，一律在 server 端重新驗證；client 端只做早期回饋。能從檔案內容驗證的（magic bytes），就不要信任 client 宣稱的型別、檔名或 Content-Type。大小與時長依用途分開設定，且影片時長必須由 server 重新解析。限制值是產品決策，可以調；但「server 是最後一道」這條不能調。

驗證規則定好了，下一步就是把規則寫進真正接收檔案的 /upload HTTP action，並且在串流與記憶體的現實限制下，把它做得又快又安全。
