寫 task 並從 API route 觸發：generate-plan 實作

Step 3/5 · trigger.dev 背景任務與 Retry

學習目標

能照著寫出一個 schemaTask，從 API route 觸發它、拿到 run 與 runId，並說出每個關鍵設定在做什麼。

前言：動手前，先確認你站在哪裡

你要做的東西是這樣：onboarding 的使用者送出九題答案，後端把答案交給一個背景任務生成每日熱量與三大營養素，任務跑完後回傳一份計畫。做完之後，你會得到一個能跑的 generate-plan 任務，以及一條知道怎麼觸發它、把結果接回來的 route。

動手前需要先具備三樣東西。第一，輸入的欄位已經被定義成一份 schema，而且有可以驗證結果是否合理的邏輯；第二，任務的資料夾與 trigger.config.ts 已經存在；第三，你的 Trigger.dev worker 與 secret key 之後要能跑起來（最後一步會交代）。前兩樣屬於資料層與專案設定，這裡不重講，只把它們當接點。

步驟一：把輸入合約與輔助邏輯放在一起

先讓任務與 route 共用同一份輸入定義。把使用者的答案寫成一個 Zod schema，放在共用的 lib 裡，例如 lib/plan.ts。這樣 route 用它驗證請求、task 用它驗證輸入，兩邊只認一份合約。

同一個檔案裡也放任務會用到的兩個輔助函式。一個是 isPlausible，判斷 AI 回的數字是否落在合理範圍：熱量要在 1200 到 5000 之間，而且「蛋白質 × 4 + 碳水 × 4 + 脂肪 × 9」換算出來的熱量要和宣稱的熱量誤差在 15% 以內。另一個是 formulaPlan，用 Mifflin-St Jeor 公式算出一份保底計畫，當 AI 怎麼試都不行時可以退回去用。

把「什麼算合理」與「保底答案是什麼」定義在任務之外、可以被單獨測試的地方。任務負責流程，規則本身不該埋在流程裡。

步驟二：建立任務檔，定義 AI 的輸出格式

在 src/trigger/ 底下建立 generate-plan.ts。先匯入需要的東西：從 @trigger.dev/sdk 拿 schemaTask 與 logger，從 OpenAI 拿 client 與結構化輸出的輔助函式，從 zod 拿 z。

import { logger, schemaTask } from "@trigger.dev/sdk";
import OpenAI from "openai";
import { zodTextFormat } from "openai/helpers/zod";
import { z } from "zod";

// 相對路徑，不是 "@/"：這個任務由 Trigger.dev 打包，不是 Metro。
import { ageFrom, formulaPlan, isPlausible, planInputSchema } from "../lib/plan";

接著定義 AI 必須遵守的輸出格式。模型被要求用 snake_case（底線分隔的小寫）命名欄位，所以 schema 也用同樣的名字，回傳後再轉成 App 慣用的 camelCase（駝峰式）。這一步是關鍵：不要讓模型自由吐一段文字，再自己用字串切割去猜，而是用結構化輸出把它的回覆鎖進你定義的形狀裡。

const aiPlanSchema = z.object({
  calories: z.number().int(),
  protein_g: z.number().int(),
  carbs_g: z.number().int(),
  fat_g: z.number().int(),
  rationale: z.string(),
});

然後寫實際呼叫 AI 的函式。有兩個刻意的設計要說明：第一，OpenAI client 在每次呼叫時才建立，不是放在模組最上層。這樣如果缺少 API key，錯誤會發生在任務的 try 裡面，可以被捕捉；如果放在最上層，錯誤會在匯入模組時就爆掉，任務根本進不到自己的錯誤處理。第二，client 設 maxRetries: 0，把重試這件事完全交給任務層，不要兩套重試系統疊在一起。

async function askOpenAI(input) {
  const openai = new OpenAI({ timeout: 25_000, maxRetries: 0 });

  const response = await openai.responses.parse({
    model: MODEL,
    input: [
      { role: "system", content: SYSTEM_PROMPT },
      { role: "user", content: JSON.stringify({ ...input, age: ageFrom(input.dateOfBirth) }) },
    ],
    text: { format: zodTextFormat(aiPlanSchema, "daily_plan") },
  });

  const out = response.output_parsed;
  if (!out) throw new Error("OpenAI returned no structured output");
  return { calories: out.calories, protein: out.protein_g, /* ... */ };
}

步驟三：用 schemaTask 把工作包起來

現在把上面的東西組成一個任務。id 就是之後觸發時要指名的字串，schema 用剛剛共用的輸入合約，maxDuration 給它 120 秒的上限，run 裡寫流程。

export const generatePlan = schemaTask({
  id: "generate-plan",
  schema: planInputSchema,
  maxDuration: 120,
  run: async (input) => {
    // 一次生成、一次重試，再不行就用公式退路
    for (let attempt = 1; attempt <= 2; attempt++) {
      try {
        const plan = await askOpenAI(input);
        if (isPlausible(plan)) return { ...plan, source: "ai" };
        logger.warn("Implausible plan, discarding", { attempt, plan });
      } catch (error) {
        logger.error("OpenAI plan generation failed", { attempt, error: String(error) });
      }
    }
    return { ...formulaPlan(input), source: "formula" };
  },
});

注意兩個地方。第一，日誌用的是 logger 而不是 console.log。任務跑在 Trigger.dev 的 worker 上，這些 log 會跟著這次 run 保存下來，之後在 dashboard 上可以直接從 run 追回程式碼，這是下一步除錯的基礎。第二，這個任務的設計目標是「永遠不丟錯」：不管是 AI 回的數字不合理，還是呼叫直接失敗，跑完兩次之後都會退回公式，讓使用者一定拿得到一份計畫。

步驟四：從 API route 觸發，把結果接回來

route 的地方在 app/api/plan+api.ts。先驗證請求，再觸發任務。匯入 task 時只匯入型別，避免把任務實例打包進 server：

import { runs, tasks } from "@trigger.dev/sdk";
import { planInputSchema } from "@/lib/plan";
import type { generatePlan } from "@/trigger/generate-plan"; // 只匯入型別

觸發時用 tasks.trigger，並把 task 的型別傳進泛型，讓 payload 受到 TypeScript 檢查。回傳的 handle 帶著 run 編號：

const handle = await tasks.trigger<typeof generatePlan>("generate-plan", parsed.data);

接下來有兩種把結果接回來的方式，課程裡兩種都用了。

第一種是輪詢（poll）。 生成計畫的 route 用 runs.poll 每隔 500 毫秒問一次這次 run 好了沒，好了就把輸出回傳，失敗就回 502。這種做法把等待留在 route，換來最單純的體驗：一個 request、一個 response，不用前端額外訂閱。

const run = await runs.poll(handle, { pollIntervalMs: 500 });

if (run.status !== "COMPLETED" || !run.output) {
  console.error("generate-plan did not complete:", run.status, run.error);
  return Response.json({ error: "Could not build your plan" }, { status: 502 });
}
return Response.json(run.output);

第二種是即時訂閱（realtime）。 分析餐點的 route 完全不等待，它把任務觸發後，把 run 編號寫回資料庫，立刻回傳編號與 handle 附帶的 publicAccessToken：

const handle = await tasks.trigger<typeof analyzeMeal>("analyze-meal", { mealId: meal.id, imageUrl });
await db.update(meals).set({ triggerRunId: handle.id }).where(eq(meals.id, meal.id));

return Response.json({ meal, runId: handle.id, publicAccessToken: handle.publicAccessToken });

前端拿到這兩個值後，用 useRealtimeRun 訂閱這次 run，任務狀態或輸出一更新，畫面就跟著更新，使用者不需要手動重新整理。什麼時候用輪詢、什麼時候用即時訂閱，取決於這個等待發生在哪裡：如果 route 本來就要等結果（例如 onboarding 最後一頁的固定動畫），輪詢簡單；如果 App 是要在畫面上一邊顯示進度一邊等（例如掃描分析），即時訂閱體驗更好。

步驟五：把 worker 跑起來，確認任務真的執行

任務寫好之後，本機要有一個 Trigger.dev 的 worker 在跑，任務才會真的被執行。用 Trigger.dev 的開發指令啟動它（npx trigger.dev@latest dev），並確認 .env 裡有正確的 secret key。這個 worker 沒開，是你之後最常遇到、也最容易誤判的症狀——route 會看起來成功，但資料庫永遠等不到那一列，因為根本沒有人在執行任務。

做完會看到什麼： 送出一組 onboarding 答案後，Trigger.dev dashboard 的 Runs 頁面會出現一次 generate-plan 的 run，狀態變成 COMPLETED，輸出裡帶著 calories、protein、carbs、fat 與 rationale，並且標示這次是 ai 還是 formula。看到這個，就代表整條「route → 觸發 → 任務 → 輸出」的鏈路通了。

程序到這裡結束，原理留在別處：為什麼要重試、退路該怎麼設計、失敗時要留下什麼狀態，是下一步這個決定要處理的事，這裡先把鏈路打通。

小結

寫一個 task 是五件事：共用輸入 schema、把 AI 的輸出鎖進結構化格式、用 schemaTask 包起流程、從 route 用 tasks.trigger 觸發、再決定用 poll 還是 realtime 把結果接回來。每個關鍵設定都有理由：client 每次建立是為了讓缺 key 可以被捕捉、maxRetries 設 0 是把重試交給任務層、logger 是為了留下可追查的紀錄、型別匯入是為了不讓伺服器多背一份任務程式碼。

鏈路打通之後，你馬上會撞到一個每個背景任務都躲不掉的問題：失敗了怎麼辦？下一步要決定重試幾次、什麼時候該有退路、什麼時候要把狀態標成失敗。
