失敗之後怎麼選：重試、退路，還是標記失敗？

Step 4/5 · trigger.dev 背景任務與 Retry

先決定：失敗之後要走哪條路？

把慢工作交給背景任務之後，事情不會從此一帆風順。OpenAI 可能逾時、回傳格式可能不對，圖片也可能根本不是食物。真正需要設計的是：任務失敗時，要不要再試一次？要不要改用保底答案？還是應該直接把結果標記成失敗？

本節的目標，是讓你能依照工作的性質，選擇重試次數與失敗處理方式，並分辨哪些錯誤值得重試、哪些情況應該走退路，哪些結果則應該直接標記失敗。

「重試就好」聽起來簡單，卻不是萬靈丹。網路短暫抖動、服務冷啟動或 API 限流，屬於暫時性失敗，重新執行可能就能成功。相反地，如果輸入本身就不可能成功，例如一張椅子的照片，不管重試幾次都還是椅子。這種必然失敗若一直重試，只是在浪費時間與 API 費用。

還有一個更危險的情況：工作已經產生部分副作用時，重試可能讓同一件事發生兩次，例如重複扣款或重複寄信。因此，失敗處理不是在幾個按鈕裡隨便挑一個，而是要看失敗的性質與任務的合約。

四個選項，放在一起比較

先把常見的處理方式攤開來看，差異會比較清楚：

策略在做什麼適合的失敗課程例子
自動重試由任務層重新執行，並加入退避間隔暫時性問題，例如逾時、限流、冷啟動analyze-meal 的 maxAttempts: 2
應用層退路改用一個確定性的替代答案有保底解法，而且使用者一定需要結果generate-plan 退回公式計畫
標記失敗把任務狀態寫成 failed，讓 UI 能顯示正確結果失敗是合法結局，不能讓任務一直懸著onFailure 把餐點標成 analysis_failed
不重試的成功任務執行成功，但判斷結果是不符合需求結果本身就是必然不符合，重跑也不會改變照片不是食物，直接刪除該列

專案的 trigger.config.ts 先定義了所有任務共用的重試預設值：最多 3 次，每次間隔會以 2 倍成長，退避時間從 1 秒開始，最多到 10 秒。

單一任務也能覆寫這個設定。分析餐點的任務只使用 retry: { maxAttempts: 2 }，因為它只需要多一次機會來處理暫時性錯誤，不需要無止境地重試。

判別問句：先問自己這四件事

  1. 這個失敗是暫時的，還是必然的？ 逾時、限流與連線抖動通常屬於暫時問題，重試有機會成功。照片不是食物、欄位缺漏等輸入問題，則是必然失敗，重試不會改變結果。
  2. 有沒有確定性的替代答案？ 如果有，而且使用者無論如何都需要一個結果，就應該設計退路。generate-plan 就是這種情況：AI 無法產生計畫時，改用 Mifflin-St Jeor 公式算出一份計畫。
  3. 重跑會不會造成重複的副作用？ 如果可能重複扣款或寄信，重試前要先讓操作具備冪等性。也就是同樣的輸入執行多次，最後結果仍然一致。
  4. 使用者需要知道這次結果嗎？ 如果需要，每種結束狀態都必須寫回資料庫，不能讓資料永遠停在「處理中」。否則 Home 畫面上就會出現一個永遠轉不完的圈圈。

兩個任務，為什麼做出相反選擇？

generate-plan 選擇「有限重試，最後一定給答案」。 它的 run 裡有一個最多執行兩次的迴圈。第一次呼叫 AI 後，如果回傳的數字不合理，也就是 isPlausible 為 false，就記錄警告並再試一次。如果連呼叫本身都失敗，也會記錄錯誤後再試一次。

兩次都無法取得可用結果時，任務就改用公式產生計畫，並標上 source: "formula"。這個任務的合約是「永遠不丟錯」，因為它位在 onboarding 的最後一關，使用者必須拿到一份計畫，才能繼續往下走。

這裡還有一個容易忽略的取捨：重試是寫在任務自己的迴圈裡，而不是完全交給任務層的 retry。這個 route 會用 runs.poll 等待結果；如果把重試交給任務層，退避間隔變長時，route 的輪詢也會跟著被拖住。把重試限制為兩次，失敗後立即退回公式，等待時間才比較可預期。

analyze-meal 則選擇「重試一次，失敗就標記」。 它設定 retry: { maxAttempts: 2 }，因為圖片分析可能只是暫時遇到服務問題，值得再給一次機會。

但如果兩次都失敗，onFailure 就會把資料庫中的那一列更新成 status: "failed"，並寫入 errorReason: "analysis_failed"。這一步不能省略：route 在觸發任務前就先建立了資料列，初始狀態是「分析中」。如果任務失敗後沒有人更新它，這筆餐點就會永遠停在「分析中」。

任務失敗不會自動替你更新資料庫狀態。任務啟動時資料列是什麼狀態、失敗後要變成什麼狀態，都必須在 run 與 onFailure 裡明確寫出來。

反例：有些「失敗」其實不該重試

照片不是食物，就是最值得記住的反例。使用者可能上傳桌子、椅子，或一張模糊的風景照。模型回傳 is_food: false 後，任務會記錄一筆警告，刪除資料庫裡的那一列，最後回傳 { status: "failed", errorReason: "not_food" }。

這裡要分清楚兩件事。從執行角度看，這次 run 其實成功了：它順利呼叫模型、拿到結構化輸出，也做出了正確判斷。從結果角度看，這張照片的餐點分析失敗了。

正因為模型已經正確判斷出「這不是食物」，所以它不該被重試。椅子的照片重試一百次，仍然會是椅子。若把這種結果當成一般任務失敗，就會浪費資源，還可能讓已經刪除的資料列再次被處理。

另外，onFailure 只處理「重試次數耗盡」的失敗，不涵蓋 CRASHED、SYSTEM_FAILURE 這類非預期中斷。遇到這些狀況時，資料庫可能仍然留著一列「分析中」的資料。

實務上，還需要另外安排一個排程任務，定期掃描並清理這些卡住的資料。這也說明了：先建立資料列、再執行分析的設計，必須搭配失敗狀態的落地處理，否則 UI 很容易留下永遠不會完成的任務。

把判斷變成一句規則

先問：「這個失敗重跑一次，結果會不會不同？」
會，而且失敗是暫時的 → 設定自動重試，並加入退避間隔，避免持續打爆對端。
會，但使用者一定要拿到答案 → 限制重試次數，之後改用確定性的替代方案。
不會，而且失敗是合法結局 → 將狀態寫回資料庫並標記失敗，不要讓 UI 永遠轉圈。
不會，因為結果本身就不是你要的，例如照片不是食物 → 讓 run 成功結束，但把資料與 UI 帶到正確結果，不要重試。
