長工作別塞在請求裡：為什麼需要背景任務

Step 1/5 · trigger.dev 背景任務與 Retry

學習目標

學完這一節，你應該能辨認哪些 AI 工作既耗時又容易失敗，也能說明：把它們從請求路徑移到背景任務，究竟解決了哪些問題。

前言：按下按鈕後，那個轉圈圈從哪裡來？

使用者在 onboarding 的最後按下「建立我的計畫」，畫面開始轉圈圈；或者他在掃描頁拍下一張便當照，畫面顯示「分析中」。這兩個動作背後都要呼叫 AI：前者要生成每天的熱量與三大營養素目標，後者要從照片估算這餐吃了多少。

最直覺的寫法是：API route 收到請求後，直接在裡面呼叫 OpenAI，等它回傳結果，再把結果包成 response 傳回去。程式碼短短的，看起來也很乾淨。

但這樣一來，使用者按下按鈕的那一刻，整個系統就得開始等待一個「可能很慢、也可能失敗」的工作。原本只是一次請求，最後卻變成使用者、連線與伺服器一起陪 AI 等候。

這一節要建立的是一種判斷力：哪些工作可以在請求路徑裡當場完成，哪些工作應該搬出去，交給背景任務處理。先理解這個分界，後面學 task、retry 和 logs 時，才會知道它們是在解決什麼問題。

請求路徑是一條又短又窄的路

先把「請求路徑」說清楚。使用者按下按鈕，App 發出 HTTP 請求；伺服器上的 route handler 開始執行；工作完成後，伺服器回傳 response，連線結束。從頭到尾這段流程，就是請求路徑。

它的特性是同步而且短命：使用者正在等，連線保持開啟，伺服器也必須在合理時間內產生答案。因此，適合放在這條路上的工作通常具備三個條件：快、可靠、可預期。

例如查一筆資料、驗證一個 token，或把一小段文字寫進資料庫。這些工作通常幾十毫秒就能完成，而且不太容易失敗。就算偶爾出錯，重新執行整個請求通常也很安全。

AI 工作卻常常剛好相反。一次呼叫可能花上好幾秒到數十秒；同一個輸入也可能得到格式不正確的內容，甚至完全拿不到結構化結果。再加上它依賴外部服務，OpenAI 可能逾時、受到限流，或短暫無法使用。

把這種工作塞進請求路徑，就像叫一位必須準時交件的窗口，去等一個不知道何時回來、而且可能空手而歸的供應商。

把 AI 塞在請求裡，會發生哪四件事？

  1. 使用者被卡住。 畫面轉圈圈的每一秒，都是使用者在等伺服器把 AI 工作跑完。手機網路逾時、App 的前景限制，都可能在伺服器還沒回完之前，先把請求切斷。
  2. 伺服器被佔住。 每個請求都要保留一份資源，一路等 AI 回應。一次來十個人，就有十條請求一起停在那裡等待，而且還沒有真正完成其他工作。
  3. 失敗時沒有乾淨的重試單位。 如果 AI 跑到一半失敗，你要嘛回傳錯誤，讓使用者再按一次；要嘛在 route 裡自己寫重試迴圈。前者讓使用者承擔不好的體驗，後者則等於在 request 的生命週期裡重新發明一套重試系統。
  4. 已完成的工作可能白費或重複。 假設 route 已經把圖片上傳完成，資料庫也建立了一列紀錄，結果 AI 呼叫才失敗。若重新執行整個請求，就必須小心處理已經發生的副作用，避免再上傳一次圖片，或建立第二份資料。

把這四件事放在一起看，問題就不在 AI 本身，而在於工作被放錯了位置。慢又容易失敗的工作，不該和「使用者正在等、連線還開著、伺服器必須準時回應」的請求綁在同一條生命週期裡。

換個擺法：請求做快的事，慢的事交給背景任務

比較好的分工是：請求路徑只做它擅長的工作——驗證輸入、完成快速且可靠的動作，例如把照片上傳到圖床，或在資料庫建立一列狀態為「分析中」的紀錄。接著，請求把慢的 AI 工作交給獨立的背景任務，自己盡快回應。

背景任務不是把同一個 async function 換個檔案放置而已。它是一個被登記、被追蹤、被執行的獨立單位：有自己的編號、執行紀錄與重試規則。請求回應之後，任務仍能在背景繼續執行；即使第一次失敗，也能由任務層自行重試，不必要求使用者再按一次，更不會讓原本的請求繼續卡住。

可以把它想成餐廳。服務生代表請求，負責帶位、點餐和送餐；他把訂單送進廚房，也就是背景任務後，就能回頭招呼下一桌。客人拿到的是號碼牌，也就是 run 的編號，餐點完成後再收到通知。

如果服務生點完餐，卻一直站在廚房裡等廚師把燉菜燉上三小時，整間餐廳的動線很快就會堵住。服務生不該站在廚房裡等待，不代表餐廳不需要廚房；只是兩種工作應該分開，讓各自負責的角色都能繼續運作。

面向塞在請求路徑裡交給背景任務
誰在等使用者與連線一起等沒有人持續等待，任務自行執行
適合的工作快、可靠、可預期慢、容易失敗、依賴外部服務
失敗時重跑整個請求，副作用要自行處理由任務層獨立重試，重試範圍只限於這項工作
執行紀錄分散在 server log 中保留每次 run 的輸入、輸出與嘗試紀錄

課程裡的兩個真實案例

第一個案例是生成飲食計畫。使用者填完九題 onboarding 後，route 會先驗證答案，再把工作交給名為 generate-plan 的任務。

這個案例裡，外層流程仍然會等到結果可供 App 使用，但真正執行 AI 的，是一個獨立的 run。它有自己的執行紀錄，最多嘗試兩次；即使 AI 完全失敗，也會退回使用公式算出的數字，讓使用者仍然能拿到一份計畫。

第二個案例是分析餐點照片。掃描頁把 base64 圖片送到 route 後，route 會做三件事：上傳圖片、建立一列狀態為「分析中」的紀錄，再觸發名為 analyze-meal 的任務。完成這些快速工作後，route 就立刻回應一個 run 編號與一段授權 token。

App 拿著這組資訊訂閱該 run 的即時狀態。任務完成或失敗時，畫面會自行更新，不需要使用者重新整理頁面。

兩個案例的等待方式不同，但共同的骨架相同：慢又容易失敗的 AI 工作，被移出請求的執行生命週期，成為一個可追蹤、可重試，也能在事後除錯的獨立任務。

小結

請求路徑的設計前提是「快、可靠，而且使用者正在等」。AI 工作卻可能很慢、結果不確定，還依賴外部服務，兩者天生不合。把 AI 工作移到背景任務，不是為了讓程式看起來更漂亮，而是讓請求能準時回應、讓失敗擁有乾淨的重試單位，也讓每次執行都留下可以追查的紀錄。判斷的起點很簡單：如果這件事失敗或執行很久，你希望使用者跟著一起等嗎？
