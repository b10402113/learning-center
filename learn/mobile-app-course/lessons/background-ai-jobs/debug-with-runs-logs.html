用 runs 與 logs 除錯：從 dashboard 追回程式碼

Step 5/5 · trigger.dev 背景任務與 Retry

完成這一節，你會做到什麼？

你將能在 Trigger.dev dashboard 中，根據一次 run 的 payload、logs、output 與歷次 attempts，找出背景任務失敗的原因，並一路追到程式碼中實際出錯的分支。

開始前，請先確認兩件事：你的 app 已經使用 Trigger.dev 觸發背景任務，而且任務有設定重試與失敗處理。接下來會以 analyze-meal 為例，示範如何從一筆 run 開始調查。

先看全貌：除錯動線會經過哪裡？

當背景任務出問題時，建議依照這條順序處理：

  1. 確認本機 worker 與必要的 secret 是否正常運作。
  2. 從資料庫或 dashboard 找到正確的 run。
  3. 查看這次 run 收到的 payload。
  4. 閱讀 logs、output 與 error。
  5. 比較不同 attempts 的結果，判斷重試是否有效。
  6. 最後把 run 的狀態和資料庫中的資料狀態放在一起比對。

這樣做的好處是，不會一看到錯誤就直接鑽進程式碼。你會先確認「任務有沒有啟動」，再確認「它拿到什麼資料」，最後才判斷「哪一段邏輯出了問題」。

步驟一：先確認 worker 和 secret 都在

遇到「任務完全沒動靜」時，先檢查最基本的兩件事，不要急著讀程式碼。

第一，確認本機的 Trigger.dev worker 有沒有在執行。沒有 worker，任務根本不會被處理；但 route 仍可能看起來成功，因為 route 做的只是把資料送出去。

第二，確認 .env 裡的 secret key 是否正確、是否有漏掉任務需要的環境變數，例如資料庫連線字串。

這兩種問題的症狀很像：任務沒有出現在 Runs，或任務無法讀取環境變數。不過它們都還不是程式邏輯錯誤。先排除這些前置問題，可以省下很多時間。

步驟二：找到對應的那一次 run

打開 Trigger.dev dashboard 的 Runs 檢視。這裡會列出每一次任務執行，你可以依照 task 的 id、執行時間或 run 編號來搜尋。例如，餐點分析任務的 task id 可能是 analyze-meal。

run 編號通常可以從資料庫取得。route 觸發任務後，會把 handle.id 寫進該筆資料的 trigger_run_id。因此，你可以先從資料庫找到這次餐點對應的 run 編號，再拿到 dashboard 比對。

這樣就能鎖定唯一一次執行，不必在一大堆相似的 run 裡逐筆翻找。

步驟三：讀懂一個 run 的三塊內容

鎖定 run 後，先依序查看以下三個區塊。它們分別回答三個問題：任務收到了什麼、執行時發生什麼事，以及最後得到什麼結果。

  1. payload（輸入）：這次任務收到的參數。分析餐點的 payload 只有 mealId 與 imageUrl。如果輸入本身就不對，後面的分析再正確也沒有用。
  2. logs（過程）：任務執行期間由 logger 印出的訊息。這是你觀察任務內部進度與分支的主要窗口。
  3. output / error（結果）：任務成功時回傳的物件，或失敗時留下的錯誤內容與狀態。

另外還要查看 attempts（歷次嘗試）。任務設定重試後，同一次 run 底下可能會有好幾次 attempt；每次嘗試的 log 與錯誤都會分開保存。

如果你看到第一次失敗、第二次成功，代表重試機制正在運作。若每一次都失敗在同一行，則表示這比較可能是固定的邏輯或格式錯誤，單靠重試無法解決。

步驟四：用 logger 讓失敗可被看見

如果任務裡完全沒有 log，dashboard 上可能只會顯示一個紅色的 FAILED，卻不會告訴你它在哪個分支停止。關鍵的條件判斷與失敗處理，都應該留下足夠的訊息。

例如，analyze-meal 遇到模型判定照片不是食物時，可以記錄餐點 id，接著刪除資料並回傳失敗原因：

if (!out.is_food) {
  logger.warn("Photo is not food, discarding meal", { mealId });
  await db.delete(meals).where(eq(meals.id, mealId));
  return { status: "failed", errorReason: "not_food" };
}

當所有重試都用完，也要在 onFailure 中留下錯誤，並把資料庫狀態更新為失敗：

onFailure: async ({ payload, error }) => {
  logger.error("analyze-meal exhausted retries", { mealId: payload.mealId, error: String(error) });
  await db.update(meals).set({ status: "failed", errorReason: "analysis_failed" }).where(eq(meals.id, payload.mealId));
},

印 log 時，請把 mealId、attempt 和錯誤內容這類可辨識的欄位一起記錄。這些欄位就像追蹤包裹的編號，能讓你從 dashboard 上的一句訊息，直接對回程式碼裡的某一行 logger，判斷是哪個分支正在說話。

步驟五：分辨 run 狀態與資料庫狀態

這是最容易混淆、也最重要的一步。任務成功，不代表使用者看到的資料一定正確；任務失敗，也不代表資料庫完全沒有被修改。

兩種狀態描述的是不同事情：

  • run 的狀態，例如 COMPLETED、FAILED、CRASHED，描述的是「這段程式有沒有跑完」。
  • 資料庫那一列的 status，例如 analyzing、completed、failed，描述的是「這一餐目前處於什麼狀態」。

因此，除錯時兩邊都要看。

若任務回報成功，但資料庫那一列仍停在 analyzing，表示程式可能漏了更新狀態。若任務回報失敗，而資料庫已經是 failed，則可能正是預期的失敗處理結果。

做完後，你應該能說出什麼？

完成這套流程後，面對一筆失敗的 run，你應該能清楚回答：

  • 它收到了什麼輸入？
  • 目前是第幾次 attempt？
  • 哪一則 log 對應到失敗分支？
  • 錯誤發生在程式的哪個階段？
  • 最後資料庫那一列變成了什麼狀態？

這就完成了從 dashboard 追到程式碼的背景任務除錯動線。至於為什麼要這樣設計背景任務、重試與狀態管理，則留給其他單元深入說明；在實作上，先能從一筆 run 找到真正的失敗位置，才是你把這套流程接回自己 app 的第一步。

小結

除錯背景任務時，先確認 worker 與 secret 正常，再從 dashboard 依 task id 或 run 編號鎖定那一次 run。接著查看 payload、logs、output 與歷次 attempts，利用 logger 把失敗追回程式碼中的那一行，最後比對 run 狀態與資料庫狀態是否一致。請記住：任務的成敗描述的是程式，資料庫的狀態描述的是使用者看到的結果，兩者必須分開確認。
