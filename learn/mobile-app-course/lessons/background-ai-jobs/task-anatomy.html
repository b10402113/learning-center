Task 是什麼：看懂 schemaTask 的 id、schema 與 run

Step 2/5 · trigger.dev 背景任務與 Retry

先問一個實際問題：你交出去的工作，到底是什麼？

上一步，我們把「慢工作搬出請求路徑」。但把程式碼從 route 剪下來，貼到另一個檔案，再從某處呼叫它，真的就完成了嗎？接下來你需要知道：搬出去的不是一段孤零零的程式碼，而是一個可以被平台辨認、追蹤並重新執行的工作單位。

一般的 async function 跟著呼叫它的 process 一起活著。process 結束、當掉或重啟，這段工作可能就消失了，也沒有人記得它曾經做到哪裡。Trigger.dev 的 task 則像一張送進中央廚房的訂單：有訂單編號、有輸入內容、有處理紀錄，廚房中途出問題時，還能依照紀錄重新處理。

這一節會拆解一個 task 的三個核心零件：id、schema 與 run。看懂它們之後，你就能理解 task 為什麼不只是「換個地方執行的 async function」。

學習目標

完成這一節後，你應該能說清楚一個 Trigger.dev task 如何由 id、schema 與 run 組成，並解釋它和一般 async function 在執行生命週期上的差別。

一個 task 的三個零件

Trigger.dev 提供一個叫 schemaTask 的工廠函式。你把設定交給它，它就會回傳一個 task。以課程中的 generate-plan 為例，骨架如下：

export const generatePlan = schemaTask({
  id: "generate-plan",
  schema: planInputSchema,
  maxDuration: 120,
  run: async (input) => {
    // 真正的工作：呼叫 AI、驗證、必要時退回公式
  },
});

id：這個工作的穩定名字

id 是 task 的固定識別名稱。它會顯示在 dashboard 上，也是在 route 觸發 task 時用來指定目標的名稱。平台會靠這個 id 找到對應的 task 程式碼。

因此，id 不只是方便閱讀的變數名稱。task 上線後不要隨意更改，因為外部觸發與歷史紀錄都要靠它建立對應關係。

schema：輸入資料的合約

schema 定義 task 接受哪些資料，以及每個欄位應該符合什麼格式。這裡放的是 Zod schema，平台會在 task 開始前先檢查輸入內容。

例如，生成計畫的輸入可能包含使用者的性別、生日、身高、體重、目標、活動量與飲食偏好。分析餐點時，輸入則可能只有餐點的資料庫 id 與圖片網址：

schema: z.object({
  mealId: z.string().uuid(),
  imageUrl: z.string().url(),
}),

有了 schema，run 裡拿到的 input 就是已經通過格式檢查、也具備型別資訊的物件。你不需要在工作內容裡再重複防守一次基本格式錯誤。

這份合約也會一路延伸到觸發端。TypeScript 可以協助檢查你傳入的資料；如果少傳必填欄位，問題有機會在編譯階段就被抓出來，而不是等任務啟動後才發現。

run：真正執行工作的地方

run 是一個接收 input、並回傳輸出的 async 函式。它就是訂單上的工作內容：呼叫 AI、驗證結果，或在必要時退回公式處理，都會寫在這裡。

同一個 task 還可以搭配其他設定。例如，maxDuration 限制最多執行多久，retry 覆寫重試次數，onFailure 則定義重試耗盡後要做什麼。這些設定會在後面的步驟進一步說明。

真正的差別：durable execution

如果只把 task 想成「有名字的 async function」，還是漏掉最重要的部分。關鍵在於它們的執行生命週期不同。

一般的 async function 活在呼叫它的 process 裡。當你在 route 中寫下 await askOpenAI(input)，這個 promise 就綁在該次請求的記憶體與連線上。請求結束或 process 重啟後，這次執行可能就此消失；出了錯，也必須由呼叫端自行決定要不要再跑一次。

Trigger.dev task 的每次執行則稱為一次 run。當你觸發 task，Trigger.dev 會先把這份工作登記下來，再交給 worker 執行。這次 run 的輸入、每一次嘗試、過程中輸出的 log，以及最後的輸出或錯誤，都會被保存。

因此，即使 worker 中途掛掉，平台仍然知道有一個 run 尚未完成，也能依照設定重新嘗試。這就是 durable 的意思：它不是保證工作永遠不會失敗，而是讓工作在失敗或重啟後，仍保有紀錄與重試的能力。

面向一般 async functionTrigger.dev task
命名與識別只是變數名稱有穩定 id，dashboard 可查
輸入合約靠型別，執行時不驗證schema 在執行前驗證
執行紀錄沒有，跑完就散run 的輸入、log、輸出都留存
失敗後由呼叫端自己想辦法平台可自動重試
壽命綁在呼叫它的行程上獨立於請求，可被追蹤

可以把兩者想成不同的廚房。一般 async function 像在家裡現做一道菜：你離開廚房，火可能就關了。Trigger.dev task 則像送進中央廚房的訂單：訂單有編號、有單據，也有出餐紀錄。即使廚房暫停工作，之後仍能按照同一張訂單繼續或重做。

觸發 task 後，拿回來的是什麼？

從 route 觸發 task 時，回傳的不是最終結果，而是一個 handle，也就是之後用來追蹤這次工作的「握把」。其中最重要的欄位是 id 與 publicAccessToken。

id 是這次 run 的編號；publicAccessToken 則是一段授權 token，讓前端可以訂閱這次 run 的狀態。因為結果不會在觸發當下立刻出現，你需要靠這些資訊稍後取回結果，或持續接收它的更新：

const handle = await tasks.trigger<typeof generatePlan>("generate-plan", parsed.data);
// handle.id               → 這次 run 的編號
// handle.publicAccessToken → 讓前端能訂閱這次 run 的授權

每個 run 都會有自己的狀態。常見狀態包括執行中的 EXECUTING、成功完成的 COMPLETED，以及不同類型的失敗：FAILED、CRASHED、TIMED_OUT、SYSTEM_FAILURE 等。

這些狀態會直接影響 app 的行為。前端要根據狀態顯示成功、失敗，或繼續等待；當你需要除錯時，狀態也會成為追查 run 的入口。

為什麼 route 只匯入型別？

還有一個容易忽略的細節：route 匯入 task 時，只匯入型別，不要匯入 task 實例。寫法如下：

import type { generatePlan } from "@/trigger/generate-plan"

原因是 task 由 Trigger.dev 自己打包與執行。它可能使用相對路徑匯入自己的資料庫，例如 ../db；這和 App 使用的 Metro 打包是兩套系統。

如果 route 把 task 實例一起打包進 server，就會多背一份不該由 route 負責的程式碼。型別匯入只在編譯時存在，不會產生執行期負擔。換句話說，route 只需要知道「怎麼正確呼叫它」，不需要把整個 task 搬進自己的執行環境。

整個專案的共同規則：trigger.config

單一 task 有自己的設定，專案根目錄還有一個 trigger.config.ts，負責定義所有 task 共用的規則。

這些規則包括專案編號、task 所在的資料夾、預設最長執行時間，以及預設的 retry 策略。課程中的預設策略是最多重試 3 次，每次間隔以 2 倍成長，退避時間從 1 秒開始，最多到 10 秒。

單一 task 可以覆寫這些預設值。這會在下一節的實作，以及再下一節的 retry 決策中看到。

把這些觀念接回你的 app

當你的 app 有一個需要較長時間完成的工作，例如生成計畫或分析餐點，可以用下面這條關係來理解它：

  • id 告訴平台「這是哪一種工作」。
  • schema 告訴平台「這份工作需要哪些輸入，而且輸入格式是否正確」。
  • run 負責「實際完成工作，並產生結果」。
  • 觸發後取得的 handle，讓 app 能「找到這一次執行，並追蹤它的狀態」。

這些零件彼此相扣：沒有穩定的 id，平台無法準確辨認工作；沒有 schema，輸入合約就不清楚；沒有獨立的 run 紀錄，失敗後也無從追蹤與重試。

一個 Trigger.dev task 由三個零件組成：id 是它的名字，schema 是輸入的合約，run 是真正的工作。它和一般 async function 的根本差別，是每次執行都是一次被登記、被保存、可被重試的 run，而不是綁在請求行程上、跑完就散的程式碼。觸發它拿回來的是 handle，你得靠 run 編號與 token 稍後把結果取回或訂閱。

現在你已經看懂 task 的組成，以及它和一般 async function 的邊界。下一步就是把這些零件組起來：實際寫出一個 schemaTask，從 API route 觸發它，再決定要用輪詢或即時訂閱把結果接回 app。
