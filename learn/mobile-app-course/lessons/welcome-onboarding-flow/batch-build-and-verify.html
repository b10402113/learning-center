批次建造 onboarding：用設計參考與驗證迴圈逐頁收斂

Step 4/5 · Welcome 與 Onboarding 流程

先確認目標與前置條件

這一節完成後，你會有一套可重複使用的流程：把多頁 onboarding 分批交給 agent，讓它依照設計稿實作，再用驗證迴圈逐頁修正，直到畫面接近參考稿、題目也符合產品規格。

動手前，先準備好三樣東西：

  1. 把設計稿放在專案的 design/ 資料夾，不要散落在聊天室或雲端硬碟。
  2. 確認 plan.md 已經定義每一頁要問的問題、可選的選項，以及相關欄位。
  3. 熟悉「螢幕截圖比對」的驗證迴圈：讓 agent 截下模擬器畫面，和目標設計並排比較，再反覆修正。

這三樣缺一不可。沒有設計稿，agent 就沒有視覺上的比對目標；沒有 plan.md，它可能會自己猜題目；沒有驗證迴圈，它只能憑感覺做一次，缺少回饋來修正差異。

為什麼不能把十頁 mockup 一次丟進去

假設你已經有一條能跑的 onboarding，設計稿也完成了十頁。最直覺的做法，是把十張圖全部附上，請 agent「照這個做完」。

這樣做通常不太穩定。agent 可能在某一頁漏掉幾個元件，在另一頁自行發明題目；頁面越往後，前面建立的做法也越容易失控。就像一次把十個紙箱疊上去，底下哪一箱歪了，最後整疊都會跟著晃。

接下來的流程，就是處理模擬器畫面與設計稿之間的落差：把大量頁面拆開建造，讓規格與視覺參考各司其職，最後再用驗證把每一頁收斂到正確的位置。

第一步：分批處理，不要一次給十頁

先把十頁拆成兩批，例如前五頁一批、後五頁一批。第一批確認穩定後，再處理第二批。

每一批都依照同一套流程執行：

  1. 附上這一批的設計圖。
  2. 同時附上 plan.md。
  3. 要求 agent 逐頁實作，並用驗證迴圈比對畫面。
  4. 確認前一批穩定後，再用相同方式處理下一批。

這樣做的好處是，若第一批的實作方式有問題，你會在付出十頁的修改成本之前就發現。若直接一次做完十頁，問題可能要到最後才浮現，屆時很難判斷是哪一頁開始偏掉。

第二步：先清理 mockup，再交給 agent

設計稿是給人看的參考，不一定等於最終產品。以 Cal AI 的 onboarding 為例，設計圖裡好幾頁都有「Skip for now」按鈕，但這個 app 的流程不允許使用者跳過，因為缺少答案就算不出計畫。

因此，交給 agent 之前，先手動把這些按鈕從設計稿移除，再存回 design/。

這一步看似瑣碎，卻能避免一個很直接的問題：如果錯誤元素還留在參考圖裡，agent 很可能會忠實地把它做出來。你之後還得再請它刪除，等於多繞一圈。與其等錯誤進入實作後再修，不如先把錯誤來源清掉。

第三步：分開提供設計參考與產品需求

這是整個流程中最需要守住的分工：

  • 設計稿決定「長什麼樣」。
  • plan.md 決定「問什麼」。

不要讓 agent 只從圖片猜題目。圖片上的文字可能只是示範文案；真正要問的問題、選項清單，以及欄位對應的資料，都應該以 plan.md 為準。

如果只提供設計圖，agent 可能照著圖上的英文隨手填入內容，也可能把某個示範選項誤認為正式選項。請明確說出兩者的分工。

附上設計稿，說：「照這十張圖把 onboarding 做完。」
附上這一批的設計稿作為視覺參考，並請你依照 plan.md 裡定義的題目與選項實作每一頁；設計稿只用來對齊版面與樣式，題目內容一律以 plan.md 為準。完成後，請用驗證迴圈逐頁比對。

兩種說法的差別，在於前者要求 agent 照抄圖片，後者則要求它依照規格實作，再把畫面對齊圖片。設計稿提供方向，但不能取代產品需求。

第四步：用逐頁比對驗證畫面

實作完成後，讓 agent 截下模擬器畫面，和對應的設計稿並排比較。若有差異，就針對差異提出回饋，接著再次截圖確認。

這個迴圈的目標，不是讓 agent 回報「已完成」，而是讓你實際看到畫面已經接近參考稿。每一頁都要檢查，尤其是標題換行、字重、元件位置，以及不該出現的按鈕。

第五步：再用自動走訪確認流程接得起來

逐頁比對之外，請 agent 自己操作一次完整流程。它可以自行選擇選項、按下下一頁，一路走到目標畫面。

若自動走訪成功，代表頁面之間至少能順利串接。若某一步的按鈕一直沒有啟用，或流程卡在中途，就能在這個階段發現，而不必等人手動點到那一頁才知道。

自動走訪會比單純截圖慢，因為 agent 真的在操作介面。不過，這項檢查能抓出「單頁看起來沒問題，串起來卻走不通」的錯誤。

小提醒：自動走訪和逐頁比對是兩種互補的檢查，不能互相取代。前者確認流程能不能走通，後者確認每一頁長得對不對。

第六步：用同一套迴圈處理 welcome

同樣的流程也適用於第一個 welcome 畫面：附上設計圖與 logo，請 agent 實作並進行比對；如果有差異，就針對細節給回饋，再重新確認。

Cal AI 的 welcome 第一版其實已經很接近參考稿，但仍有幾處差異：

  • 參考稿的標題是兩行，實作後卻折成三行。
  • 實作畫面的字重偏重，看起來比設計稿更粗。

這些差異不一定會被 agent 自己察覺，必須有人把兩張圖放在一起比較。收到回饋後，將字重從約 700 調整到約 500，並把標題壓回兩行，畫面就幾乎與設計稿一致。

所以驗證迴圈的終點不是「agent 說做完了」，而是「你比對過，確認畫面確實一致」。

做完之後，應該看到什麼結果

完成後，design/ 裡的每一張 onboarding 設計圖，都應該有一個對應的實作畫面。兩批頁面的風格要一致，題目與選項要符合 plan.md，整個流程也要能透過自動走訪順利跑完。

你不需要手動點擊每一頁，只要在關鍵位置進行畫面比對與回饋，就能讓 agent 反覆修正。至於為什麼設計稿只能作為參考、產品規格才是內容的依據，前面幾節已經說明；本節只專注在把建造流程跑順。

小結

多頁 onboarding 不要一次全部丟給 agent。先分批處理，例如一次五頁；再把 mockup 上不該存在的元素移除。提供資料時，將設計稿和 plan.md 分開指定：設計稿決定長相，plan.md 決定題目。實作後用驗證迴圈逐頁比對，再用自動走訪確認流程接得起來。最後的判斷標準是「你比對過，確認畫面一致」，而不是 agent 回報已完成。

到目前為止，我們處理的都是使用者「怎麼填」問卷。接下來還有一個很容易做錯的問題：問卷和登入到底誰先誰後？如果使用者已經登入，卻還沒填問卷，app 應該怎麼處理？下一節會處理這道 gate。
