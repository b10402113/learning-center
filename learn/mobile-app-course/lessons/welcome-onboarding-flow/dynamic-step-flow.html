一條流程串起 N 頁：用動態 renderer 與共用版型完成 onboarding

Step 3/5 · Welcome 與 Onboarding 流程

先確認目標與前置條件

這一節的目標，是照著做出一條由單一動態頁面渲染 N 個步驟的 onboarding 流程。完成後，你會有九個可以實際點擊、填答、前進的畫面，而且每一頁都會共用同一套視覺骨架。

開始前，你需要準備兩樣東西：上一節建立的 steps 陣列，以及暫時存放答案的 answers 物件。steps 描述每一題要問什麼、使用哪種回答方式，以及答案要存到哪個欄位；answers 則像一份共用的答案草稿，讓每一頁都能讀寫同一份資料。

如果每一題都開一個檔案，標題位置、按鈕大小和進度條很快就可能各自走樣。這次我們改用一個動態 renderer，再搭配共用版型與作答元件，把「題目資料」和「畫面長相」接起來。

第一步：用一個動態頁面接住所有步驟

直覺的做法，是為九頁問卷各開一個檔案。這樣雖然一開始容易理解，之後只要調整題目順序或增加步驟，就得回頭修改許多頁面。

這裡改用一個動態路由 [step].tsx。它像一位櫃台人員：先看網址裡的 step 參數，再從 steps 陣列找出目前該顯示的題目。

核心邏輯可以濃縮成下面這樣：

export default function OnboardingStep() {
  const { step } = useLocalSearchParams();
  const index = stepIndex(String(step));
  const config = steps[index];

  // 依照 config.kind 決定要渲染哪一種回答介面
  // cards  → <OptionCard />
  // ruler  → <RulerPicker />
  // date   → 原生日期選擇器

  return (
    <OnboardingScreen
      progress={index / steps.length}
      title={config.title}
      subtitle={config.subtitle}
      onNext={() => router.push(`/onboarding/${steps[index + 1].key}`)}
    >
      {/* 依照 kind 放進對應的作答元件 */}
    </OnboardingScreen>
  );
}

接著逐一確認這段程式在做什麼。

  1. useLocalSearchParams 先從網址取出 step。
  2. stepIndex(String(step)) 把網址上的 key 換成 steps 陣列裡的位置。程式因此知道目前是第幾題，也能算出進度。
  3. const config = steps[index] 取出這一題的設定，包括標題、副標題、答案欄位與回答類型。
  4. config.kind 決定要放哪一種作答介面：cards 使用 OptionCard，ruler 使用 RulerPicker，date 使用原生日期選擇器。
  5. onNext 使用 steps[index + 1].key 動態算出下一頁，而不是把網址寫死。日後調整陣列順序時，這段邏輯不用跟著改。

使用者作答時，答案會寫回共用的 answers 物件。例如選中一張選項卡，就把 answers[config.field] 設成該選項的值。每一頁都在操作同一份答案草稿，只負責其中一個欄位，因此不需要各自保存一份獨立狀態。

第二步：用共用版型固定每一頁的骨架

動態 renderer 解決了「現在要顯示哪一題」，但每一頁還需要一個穩定的外殼。這就是 OnboardingScreen 的工作：把標題、副標題、進度、返回按鈕、主要按鈕與作答內容放在一致的位置。

它接受的參數不多，但會直接影響整條流程的使用感：

  • progress：零到一之間的目前進度。
  • title 與 subtitle：當頁顯示的文字。
  • onNext：按下主要按鈕後要執行的動作。
  • disabled：決定主要按鈕目前能不能按。
  • children：放入中間的作答區。

進度條不是一條連續伸縮的長條，而是固定顯示四段橫條。程式用下面這行算出目前要亮幾段：

const filled = 1 + Math.floor(progress * (SEGMENTS - 1));

當 progress 從零走到一，filled 就會從一段增加到四段。固定四段的好處是，使用者在手機上瞄一眼就能數出還剩幾格，不需要比較一條長條目前伸長了多少。

OnboardingScreen 也集中處理兩個常被漏掉的細節：左上角的返回按鈕，以及瀏海、底部手勢列等安全區域所需要的內距。這些共用功能放在同一處後，九個步驟就只需要專心描述自己的題目。

第三步：依照 kind 放入正確的作答元件

接下來，把 config.kind 對應到實際的回答介面。三種輸入各自負責一種互動，不要讓每一頁自己重新發明一套寫法。

若 kind 是 cards，使用 OptionCard

OptionCard 負責顯示選項卡。它接收標題、副標、圖示，以及一個 selected 狀態。

若選項被選中，邊框會從細的淺灰色變成粗的黑色，右側也會出現打勾圓標。這種明顯的視覺回饋，能讓使用者立刻知道自己的選擇已經生效，不必猜「我到底選了沒」。

若 kind 是 ruler，使用 RulerPicker

RulerPicker 負責數字題。它是一座會吸附的捲尺，使用垂直的 ScrollView，再設定 snapToInterval，讓捲動一次剛好停在一格。

每當使用者滑動，元件就把目前的偏移量換算成數字，並透過 onChange 回報出去。為了讓它看起來像真正的尺，刻度會由高到低排列；兩端再疊上好幾層淡化色塊，讓刻度在邊緣逐漸消失。

小提醒：數字題的吸附與換算很容易差一格，或差一個小數點。完成後，務必手動滑到最小值與最大值，確認畫面顯示的數字和實際回報的數字一致。

若 kind 是 date，使用原生日期選擇器

生日這類輸入交給系統原生的日期選擇器，通常比自己製作一套日期介面更不容易出錯。因此，date 不需要另外造輪子。

第四步：把答案與下一頁接起來

完成作答元件後，確認每一種輸入都會把值寫回共用的 answers 物件。

若使用者選擇選項卡，就把選中的值寫入 answers[config.field]；若使用捲尺，就在 RulerPicker 的 onChange 中寫入換算後的數字；若使用日期選擇器，也同樣把結果存到這一題設定的欄位。

若目前不是最後一步，按下下一步就依照 steps[index + 1].key 前往下一個網址。若目前已經是最後一步，則要依你的流程處理完成狀態；這一節的重點，是讓每個步驟能依照陣列順序正確渲染與前進。

做完後如何驗證

在瀏覽器或模擬器打開某一個 /onboarding/<key>，確認畫面顯示的是該 key 對應的題目。

  • 若更換網址中的 key，應該看到對應的步驟。
  • 按下一步時，應該依照 steps 陣列的順序前進。
  • 選擇 OptionCard 後，選項應該亮起並顯示選取狀態。
  • 滑動 RulerPicker 時，刻度應該吸附在每一格，回報的數字也要正確。
  • 答案應該持續寫入同一份 answers 草稿。
  • 九頁的字體、按鈕、進度條與安全區域內距應該保持一致。

完成後的樣子

完成之後，你只要打開某一個 /onboarding/<key>，就能看到對應的一頁。按下一頁會依照陣列順序前進；選項卡會亮起；捲尺會吸附；答案會寫進同一份草稿。

九頁共用同一層 OnboardingScreen 外殼，因此不會出現某一頁按鈕特別大、另一頁進度條位置不同的情況。這一節先專注在把流程實作出來；為什麼採用資料驅動畫面，而不是一頁一個元件，屬於設計取捨，上一節已經交代過。

小結

用一個動態頁面 [step].tsx 配上一份 steps 陣列，就能渲染出任意數量的步驟：stepIndex 決定現在第幾題，kind 決定使用哪種作答介面，onNext 動態算出下一頁。畫面骨架由 OnboardingScreen 統一提供，選項、數字、日期三種輸入則交給 OptionCard、RulerPicker 與原生選擇器。

現在你已經有一條能跑的 onboarding 流程。不過，「能跑」和「一次把十頁做得漂亮又一致」是兩回事。下一節會換到建造手法：怎麼把大量頁面分批交給 agent，再用驗證迴圈把品質收斂到設計稿的水準。
