把「誰什麼時候有空」建成資料

Step 2/5 · 預約領域模型（Drizzle + Neon）

學習目標

能讀懂 working_hours、time_off、services、dentist_services 與 appointments 的關聯，並說出每張表在「誰什麼時候有空」裡負責什麼。

前言：醫師的班表不是一張表就能講完

上一節你把時間的表示方式處理好了：牆鐘時間與絕對瞬間分清楚，時區換算集中在一個檔案。現在問題換了一個角度：就算時間算得再準，你還是得先知道「張醫師哪幾天上班、幾點到幾點」，才有東西可以拿來算。

麻煩的是，這件事沒辦法用一句話或一張表講完。張醫師一般週一到週五早上九點到下午五點看診，這是規律；但他下週三請假，這是例外；而週三早上十點已經有一位病人預約走了，這也是例外。規律和例外如果硬塞進同一張表，會變得又亂又難查。這一節要看診所怎麼把「誰什麼時候有空」拆成幾張各司其職的表，以及排班引擎最後是怎麼把這些表讀成同一種輸入。

兩類資料：固定規則與臨時例外

先建立一個分類。關於「有沒有空」的資料，其實只有兩類：第一類是會重複發生的規則，例如每週固定班表；第二類是打斷規則的例外，例如請假或已經被預約走的時段。診所把它們放在不同的表，正因為它們的性質完全不同。

working_hours 負責第一類。每一列代表「某位醫師、某個星期幾、從幾點到幾點」。

/** Clinic-local wall-clock times. Expanded to instants through CLINIC_TZ. */
export const workingHours = pgTable(
  'working_hours',
  {
    id: id(),
    dentistId: uuid('dentist_id')
      .notNull()
      .references(() => dentists.id, { onDelete: 'cascade' }),
    weekday: smallint('weekday').notNull(), // 0 = Sunday .. 6 = Saturday
    startTime: time('start_time').notNull(),
    endTime: time('end_time').notNull(),
  },
  (t) => [index('working_hours_dentist_idx').on(t.dentistId, t.weekday)]
);

這裡有個容易漏掉、卻很關鍵的細節：startTime 與 endTime 是 Postgres 的 time 型別，存的是像 09:00 這樣的牆鐘時間，不是絕對瞬間。原因是它本來就不是某個特定的日子，而是一條每週重複的規則：「早上九點」在這裡的意義，是診所牆上時鐘的九點，之後才會被展開到某個具體日期上。欄位上的註解寫得很明白：這些是診所當地牆鐘時間，要透過 CLINIC_TZ 才展開成瞬間。

weekday 用 0 到 6 表示，0 是星期日、6 是星期六，和 JavaScript Date.getDay() 的慣例一致。索引建在 (dentistId, weekday) 上，因為排班時最常問的問題就是「這位醫師在這一天有沒有班」。

例外一：請假

第二類資料由 time_off 負責。它記錄某位醫師從某個時刻到某個時刻不可用。

export const timeOff = pgTable(
  'time_off',
  {
    id: id(),
    dentistId: uuid('dentist_id')
      .notNull()
      .references(() => dentists.id, { onDelete: 'cascade' }),
    startsAt: timestamp('starts_at', { withTimezone: true }).notNull(),
    endsAt: timestamp('ends_at', { withTimezone: true }).notNull(),
    reason: text('reason'),
  },
  (t) => [index('time_off_dentist_idx').on(t.dentistId, t.startsAt)]
);

注意這裡的 startsAt 與 endsAt 是 timestamp with time zone，也就是絕對瞬間。請假是「某個真實時刻到某個真實時刻」，例如 3 月 11 日早上九點到下午五點，所以它應該存成瞬間，而不是牆鐘時間。這種對比很重要：規律用牆鐘時間，例外用絕對瞬間。

例外二：已經被預約走的時段

第三張表是核心的 appointments。它每一列代表一次預約，欄位裡同樣有 startsAt 與 endsAt 兩個絕對瞬間，另外還有狀態。

export const appointments = pgTable(
  'appointments',
  {
    id: id(),
    patientId: uuid('patient_id')
      .notNull()
      .references(() => patients.id, { onDelete: 'cascade' }),
    dentistId: uuid('dentist_id')
      .notNull()
      .references(() => dentists.id, { onDelete: 'restrict' }),
    serviceId: uuid('service_id')
      .notNull()
      .references(() => services.id, { onDelete: 'restrict' }),
    startsAt: timestamp('starts_at', { withTimezone: true }).notNull(),
    endsAt: timestamp('ends_at', { withTimezone: true }).notNull(),
    status: appointmentStatusEnum('status').notNull().default('booked'),
    streamCallId: text('stream_call_id'),
    cancelledAt: timestamp('cancelled_at', { withTimezone: true }),
    cancelledBy: uuid('cancelled_by').references(() => users.id, { onDelete: 'set null' }),
    reminder24hSentAt: timestamp('reminder_24h_sent_at', { withTimezone: true }),
    reminder1hSentAt: timestamp('reminder_1h_sent_at', { withTimezone: true }),
    createdAt: createdAt(),
  },
  (t) => [
    index('appointments_dentist_starts_idx').on(t.dentistId, t.startsAt),
    index('appointments_patient_starts_idx').on(t.patientId, t.startsAt),
  ]
);

status 是個 enum，可能是 booked、cancelled、completed 或 no_show。排班時只關心還在 booked 的那些，因為取消或完成的預約不再佔用時段。兩個索引分別服務「查某位醫師某段時間的預約」與「查某位病人某段時間的預約」這兩種查詢。

服務決定一個時段有多長

截至目前，你知道醫師哪時候上班、哪時候被佔走，但還缺一塊：一次預約要花多久？這件事不屬於醫師，也不屬於病人，而是「服務」的屬性。洗牙可能是 30 分鐘，根管治療可能是 90 分鐘。所以 services 表帶著 durationMinutes。

export const services = pgTable('services', {
  id: id(),
  /** Stable key the mobile UI already uses: checkup, cleaning, pain, white, ortho, resto. */
  key: text('key').notNull().unique(),
  name: text('name').notNull(),
  description: text('description'),
  durationMinutes: integer('duration_minutes').notNull(),
  isTeleconsult: boolean('is_teleconsult').notNull().default(false),
  isActive: boolean('is_active').notNull().default(true),
});

另外還有 isTeleconsult，用來標記這項服務是不是遠距視訊，最後一步會看到它怎麼影響通話的建立。isActive 則讓診所可以把某項服務下架，而不用刪除歷史資料。

不是每位醫師都能做每項服務

還有一層關係：醫療服務有專業分工，不是每位醫師都會做所有項目。這個「誰能做什麼」由一張連接表 dentist_services 表達，它只有兩個欄位，組成複合主鍵。

export const dentistServices = pgTable(
  'dentist_services',
  {
    dentistId: uuid('dentist_id')
      .notNull()
      .references(() => dentists.id, { onDelete: 'cascade' }),
    serviceId: uuid('service_id')
      .notNull()
      .references(() => services.id, { onDelete: 'cascade' }),
  },
  (t) => [primaryKey({ columns: [t.dentistId, t.serviceId] })]
);

多對多關係用一張只有兩個外鍵的表來表示，是關聯式資料庫的標準做法。複合主鍵確保同一個「醫師 × 服務」組合不會重複出現。查詢的時候，只要把病人選的服務拿去這張表過濾，就能得到「所有會做這項服務的醫師」。

引擎眼中的世界：其實只有兩種輸入

把表看完之後，真正巧妙的地方在於排班引擎並不直接讀資料庫。它只認兩種東西：工作時段，以及忙碌區間。程式碼裡用兩個型別定義它們。

export type WorkingHour = {
  dentistId: string;
  weekday: number; // 0 = Sunday
  startTime: string; // clinic-local 'HH:MM' / 'HH:MM:SS'
  endTime: string;
};

/** A booked appointment or a block of time off — both just make a dentist unavailable. */
export type BusyInterval = {
  dentistId: string;
  startsAt: Date;
  endsAt: Date;
};

那句註解是這一節最重要的一句話：一筆已經預約的門診，和一塊請假時間，對引擎來說是同一件事，都只是讓某位醫師不可用。time_off 的列和 appointments 裡狀態為 booked 的列，會被合併成同一份 busy 陣列送進引擎。引擎不需要知道誰是請假、誰是預約，它只需要知道「這段時間不能用」。

表代表什麼時間欄位型別
working_hours每週重複的固定班表牆鐘時間 time
time_off請假等臨時不可用區間絕對瞬間 timestamptz
appointments已成立的預約（含醫師、病人、服務）絕對瞬間 timestamptz
services服務項目與時長無時間欄位
dentist_services哪位醫師會做哪項服務無時間欄位

小結

「誰什麼時候有空」拆成兩類資料：規律（working_hours，用診所牆鐘時間）與例外（time_off、已預約的 appointments，用絕對瞬間）。服務時長放在 services，誰能做什麼放在 dentist_services。到了引擎面前，請假與已預約被合併成同一份「忙碌區間」，因為它們的意義完全相同：讓某位醫師在那段時間不能用。

資料有了形狀，下一步就是真正把它算成時段。下一節會看純函式排班引擎：它怎麼掃過每個工作天、用 15 分鐘粒度產生候選時間、扣掉與忙碌區間重疊的候選，再跳過太接近現在的前置期。
