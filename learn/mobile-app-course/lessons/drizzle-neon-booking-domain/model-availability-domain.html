把「誰什麼時候有空」建成資料

Step 2/5 · 預約領域模型（Drizzle + Neon）

學習目標

能讀懂 working_hours、time_off、services、dentist_services 與 appointments 的欄位與關聯，並說明每個設計正在解決預約系統的哪個問題。

前言：診所不是一本行事曆

上一節建好了時區層，讓「診所牆上的時間」能正確換成真正的瞬間。接下來的問題是：要拿哪些資料來算可預約時段？如果你腦中浮現的是一本行事曆，可能就低估了這件事。

一間診所不是「一張」行事曆，而是好幾位醫師共用一個空間。每位醫師一週的營業時間可能不同，有人週三休、有人只看上午；不是每個醫師都會做所有療程，植牙可能只有院長做；服務本身也有長有短，洗牙三十分鐘、根管治療可能要一個半小時。再加上請假、午休、已經排進去的病人——這些全部疊起來，才決定某個時段到底能不能約。

這一節要把上面那些話變成一組資料表。讀 schema 的時候不要只把欄位從頭唸到尾，把它當成作者留下的決策清單：為什麼這個欄位不需要時區？為什麼要有 dentist_services 這張多對多的表？為什麼移除服務要用 restrict、不能連著預約一起刪？每個選擇通常都對應一個踩過的坑。

三組資料：可約性、能力、事實

這組表可以分成三組，各自回答一個問題。

組別表回答的問題
可約性的來源working_hours、time_off這位醫師什麼時候本來就有空？
能做什麼services、dentist_services這個療程多久？誰會做？
已經發生什麼appointments哪些時段已經被佔走了？

後面你會看到，排班引擎其實只吃兩種輸入：每位醫師的「工作時段」與「忙碌區間」。其他表都是為了把這兩種輸入算出來而存在的。

working_hours：一週重複的牆鐘作息

export const workingHours = pgTable(
  'working_hours',
  {
    id: id(),
    dentistId: uuid('dentist_id')
      .notNull()
      .references(() => dentists.id, { onDelete: 'cascade' }),
    weekday: smallint('weekday').notNull(), // 0 = Sunday .. 6 = Saturday
    startTime: time('start_time').notNull(),
    endTime: time('end_time').notNull(),
  },
  (t) => [index('working_hours_dentist_idx').on(t.dentistId, t.weekday)]
);

這張表描述「哪位醫師、星期幾、從幾點到幾點看診」。weekday 用 0 到 6 表示（0 是星期日），startTime 與 endTime 則是 time 型別——注意，不是時間戳記。

這正是上一節的分界線：營業時間是牆鐘時間。「每週三 09:00 開門」不是時間軸上的某個瞬間，而是一個每週重複的作息，所以用純粹的時刻字串儲存。要換成真實瞬間時，再交給 clinicInstant 處理。

這個索引 (dentistId, weekday) 是為了最常見的查詢：「給我某位醫師某一天的工作時段」。有了它，查詢不必掃過整張表。

time_off：請假與午休，是真正的瞬間

export const timeOff = pgTable(
  'time_off',
  {
    id: id(),
    dentistId: uuid('dentist_id')
      .notNull()
      .references(() => dentists.id, { onDelete: 'cascade' }),
    startsAt: timestamp('starts_at', { withTimezone: true }).notNull(),
    endsAt: timestamp('ends_at', { withTimezone: true }).notNull(),
    reason: text('reason'),
  },
  (t) => [index('time_off_dentist_idx').on(t.dentistId, t.startsAt)]
);

請假和這裡的 working_hours 剛好相反：它描述的是「某月某日某段時間不進診所」，是一個一次性的、發生在時間軸上的區間，所以用 timestamptz（帶時區的時間戳記）儲存。

午休也可以放進這張表，因為對排班引擎來說，「醫師請假」和「醫師午休」是同一件事——這段時間不能看診。把兩者合併成同一種資料，引擎就不用為它們各寫一套邏輯。

services 與 dentist_services：療程與能力

export const services = pgTable('services', {
  id: id(),
  key: text('key').notNull().unique(), // checkup, cleaning, pain, white, ortho, resto
  name: text('name').notNull(),
  description: text('description'),
  durationMinutes: integer('duration_minutes').notNull(),
  isTeleconsult: boolean('is_teleconsult').notNull().default(false),
  isActive: boolean('is_active').notNull().default(true),
});

services 是療程目錄。durationMinutes 是最重要的一個欄位：它決定一筆預約要佔用醫師多久，也決定候選時段要留多少空間。少了它，排班引擎根本不知道一個「洗牙」是半小時還是一小時。

key 是一個穩定的英文鍵（例如 cleaning），讓手機端的畫面可以對應到固定選項；即使之後有人改了顯示名稱，鍵也不會變。isActive 則讓診所可以「下架」某個療程，而不是直接刪掉它——因為已經有預約指向它。

接著是容易被忽略、但少了會出事的關聯表：

export const dentistServices = pgTable(
  'dentist_services',
  {
    dentistId: uuid('dentist_id')
      .notNull()
      .references(() => dentists.id, { onDelete: 'cascade' }),
    serviceId: uuid('service_id')
      .notNull()
      .references(() => services.id, { onDelete: 'cascade' }),
  },
  (t) => [primaryKey({ columns: [t.dentistId, t.serviceId] })]
);

這是一張多對多的連接表：一位醫師會做多種療程，一種療程也可能有多位醫師會做。(dentistId, serviceId) 當複合主鍵，天然保證同一組配對不會重複。

為什麼這張表非有不可？想像沒有它的世界：病人選了「植牙」，系統列出所有醫師的可約時段，結果排到一位不做植牙的醫師。預約成功了，但到場才發現做不了。dentist_services 的存在，就是讓「誰有能力做這件事」變成可查詢的事實，而不是藏在某個人的記憶裡。

appointments：已發生的事實

export const appointments = pgTable(
  'appointments',
  {
    id: id(),
    patientId: uuid('patient_id')
      .notNull()
      .references(() => patients.id, { onDelete: 'cascade' }),
    dentistId: uuid('dentist_id')
      .notNull()
      .references(() => dentists.id, { onDelete: 'restrict' }),
    serviceId: uuid('service_id')
      .notNull()
      .references(() => services.id, { onDelete: 'restrict' }),
    startsAt: timestamp('starts_at', { withTimezone: true }).notNull(),
    endsAt: timestamp('ends_at', { withTimezone: true }).notNull(),
    status: appointmentStatusEnum('status').notNull().default('booked'),
    streamCallId: text('stream_call_id'),
    cancelledAt: timestamp('cancelled_at', { withTimezone: true }),
    cancelledBy: uuid('cancelled_by').references(() => users.id, { onDelete: 'set null' }),
    reminder24hSentAt: timestamp('reminder_24h_sent_at', { withTimezone: true }),
    reminder1hSentAt: timestamp('reminder_1h_sent_at', { withTimezone: true }),
    createdAt: createdAt(),
  },
  (t) => [
    index('appointments_dentist_starts_idx').on(t.dentistId, t.startsAt),
    index('appointments_patient_starts_idx').on(t.patientId, t.startsAt),
  ]
);

這張表是一筆筆真正發生的預約，也是排班引擎眼中的「忙碌區間」來源。幾個設計值得停下來看：

startsAt 和 endsAt 都是 timestamptz，因為預約是絕對瞬間。endsAt 不讓使用者填，而是由伺服器用服務時長算出來——如果讓前端自己送結束時間，就等於讓它偷偷改掉療程長度，佔用超過它該佔的時段。

status 是一個 enum，只允許 booked、cancelled、completed、no_show 四個值。沒有 enum 的話，某天有人把 cancelled 拼錯成 canceled，資料庫照收，但排班查詢只認得正確拼法，那筆預約就會像幽靈一樣同時「存在」又「不被計算」。

外鍵的刪除策略也不一樣：patientId 用 cascade，刪除病人時他的預約一併清掉；dentistId 與 serviceId 則用 restrict，只要還有預約指向這位醫師或這個療程，就不准刪除。這是在用資料庫保護歷史紀錄——你不會希望刪掉一位離職醫師，就讓所有他看過的預約憑空消失。

最後兩個索引分別服務「某醫師某天的預約」與「某病人某天的預約」，也就是排班與病人查詢最常走的路。

把事實接回引擎：忙碌區間怎麼來

排班引擎不需要知道「這是一個預約」還是「這是一段請假」，它只需要一串「某位醫師在某段時間不可用」的區間。所以實作上會把 appointments（狀態為 booked 的那些）和 time_off 合併成同一種 busy 區間：

// 對排班引擎而言，一筆已約的門診和一塊請假是同一件事：醫師不可用。
busy: [...booked, ...off]

這個「在對的地方合併」的決定，讓後面那顆引擎可以保持單純：它只認一種不可用區間，不必為不同來源寫不同分支。

小結

預約領域由三組表組成。working_hours 存每位醫師一週重複的牆鐘作息（所以用 time 字串，不是時間戳記）；time_off 與已約的 appointments 都是絕對瞬間，實作時合併成同一種「忙碌區間」；services 提供療程長度，dentist_services 用多對多關係回答「誰會做這個療程」；appointments 用 enum 鎖住狀態、由伺服器算 endsAt，並用 restrict 外鍵保護歷史。整套表的目的，就是替排班引擎準備兩種輸入：工作時段與忙碌區間。

現在資料齊了，但「怎麼算」還沒寫。下一節要把這些輸入交給一個不碰資料庫、不看系統時鐘的純函式，讓它產出所有可預約時段——也因為它夠純，日光節約與前置期這些邊界才能被單元測試牢牢釘住。
