讓讀與寫共用同一個引擎

Step 4/5 · 預約領域模型（Drizzle + Neon）

學習目標

能照著把 GET /api/availability 與 POST /api/appointments 接到同一份 loadSchedulingInputs 與 classifySlot，讓 API 提供的時段與它接受的時段不會分岔，並正確回傳 409 與 400。

前言：會算，不代表有人聽它的話

上一步的排班引擎是一台很可靠的計算機，但它有兩個天生的限制：它沒有資料，而且它不會攔人。純函式只負責「給輸入、算答案」，至於資料從哪來、有沒有人想偷偷送一個不存在的時間——那都是 API 這一層的事。

這一節要把引擎接進兩條路徑，而且是一條讀、一條寫。GET /api/availability 負責把可約時段列給病人看；POST /api/appointments 負責真的把預約寫進資料庫。最危險的作法是兩條路徑各寫一套規則，因為它們總有一天會分岔：畫面上顯示可以約，送出去卻被拒絕，或是反過來，一個明明不存在的時間被接受了。

動手前請先確認你具備三樣東西：上一節的 availableSlots 與 classifySlot、之前建好的五張表，以及一個能寫 Route Handler 並用 route() 包裝、用 requireAuth() 守衛的 API 骨架。如果你還沒看過 Route Handler 那條線，先去看隔壁節點，這裡不重講包裝與授權的細節。

步驟一：先寫一個兩邊共用的輸入載入器

整個接線的關鍵，是不要讓讀與寫各自去撈資料。先寫一個函式，專門把引擎需要的輸入從 Postgres 撈出來：

export async function loadSchedulingInputs(
  dentistIds: string[],
  from: CalendarDay,
  to: CalendarDay,
  options: { excludeAppointmentId?: string } = {}
): Promise<{ workingHours: WorkingHour[]; busy: BusyInterval[] }> {
  if (dentistIds.length === 0) return { workingHours: [], busy: [] };

  // 前後各放寬一天，讓跨午夜的預約也落在查詢範圍內。
  const rangeStart = clinicInstant(from, 0, 0);
  const rangeEnd = new Date(clinicInstant(to, 23, 59).getTime() + 24 * 3600_000);

  const [hours, booked, off] = await Promise.all([
    db.select().from(workingHours).where(inArray(workingHours.dentistId, dentistIds)),
    db.select({ /* startsAt, endsAt, dentistId */ })
      .from(appointments)
      .where(and(
        inArray(appointments.dentistId, dentistIds),
        eq(appointments.status, 'booked'),
        lte(appointments.startsAt, rangeEnd),
        gte(appointments.endsAt, rangeStart),
        options.excludeAppointmentId
          ? ne(appointments.id, options.excludeAppointmentId)
          : undefined
      )),
    db.select({ /* startsAt, endsAt, dentistId */ })
      .from(timeOff)
      .where(and(
        inArray(timeOff.dentistId, dentistIds),
        lte(timeOff.startsAt, rangeEnd),
        gte(timeOff.endsAt, rangeStart)
      )),
  ]);

  return {
    workingHours: hours.map((h) => ({ /* ... */ })),
    busy: [...booked, ...off], // 已約與請假，對引擎而言是同一種不可用
  };
}

做了什麼：用 Promise.all 並行讀三組資料——工作時段、已約的門診、請假；把後兩者合併成 busy。預期看到什麼：呼叫者拿到的形狀，剛好就是上一節 availableSlots 要的輸入。

這裡有兩個容易漏的細節。第一，時間範圍前後各放寬一天，因為一筆跨越午夜的預約，只查「當天」會漏掉它。第二，選擇性排除某一筆預約（excludeAppointmentId）是為了改期：當你把一筆預約往後移到新時間時，不能讓它自己擋住自己。

步驟二：GET /api/availability 把時段列出來

export const GET = route(async (req: Request) => {
  await requireAuth();

  const url = new URL(req.url);
  const query = availabilityQuerySchema.parse({
    serviceId: url.searchParams.get('serviceId') ?? undefined,
    dentistId: url.searchParams.get('dentistId') ?? undefined,
    from: url.searchParams.get('from') ?? undefined,
    to: url.searchParams.get('to') ?? undefined,
  });

  const [service] = await db.select().from(services).where(eq(services.id, query.serviceId));
  if (!service || !service.isActive) throw notFound('Service not found');

  const from = parseDay(query.from);
  const to = parseDay(query.to ?? query.from);

  const offering = await db
    .select({ dentistId: dentistServices.dentistId })
    .from(dentistServices)
    .innerJoin(dentists, eq(dentists.id, dentistServices.dentistId))
    .where(and(
      eq(dentistServices.serviceId, service.id),
      eq(dentists.isActive, true),
      query.dentistId ? eq(dentists.id, query.dentistId) : undefined
    ));

  const dentistIds = offering.map((d) => d.dentistId);
  if (dentistIds.length === 0) return json({ service, slots: [] });

  const { workingHours: hours, busy } = await loadSchedulingInputs(dentistIds, from, to);
  const slots = availableSlots({
    workingHours: hours,
    busy,
    durationMinutes: service.durationMinutes,
    from,
    to,
    now: new Date(),
  });

  return json({
    service: { id: service.id, name: service.name, durationMinutes: service.durationMinutes },
    slots: slots.map((s) => ({
      dentistId: s.dentistId,
      startsAt: s.startsAt.toISOString(),
      endsAt: s.endsAt.toISOString(),
      label: formatClinicTime(s.startsAt), // 診所當地時間字串，前端不必知道時區
    })),
  });
});

做了什麼：驗證查詢參數、確認服務存在且啟用、透過 dentist_services 找出會做這個療程的醫師，再把他們的資料餵進引擎。預期看到什麼：回應裡每個時段都帶著 dentistId（因為手機流程是先選時間、之後才需要知道醫師），以及一個已經格式化的 label。

那個 label 是刻意的：時區換算只發生在後端，前端拿到的就是診所當地的「09:00 AM」。手機完全不需要知道 CLINIC_TZ 是什麼，也就不可能用裝置時區把診所時間算到別的一天。

如果沒有任何醫師提供這個服務，直接回空陣列，而不是丟錯。空時段在 UI 上是「這個日期沒有可約時段」，是很正常的一種狀態。

步驟三：寫入前，重跑同一套判準

這一步是整節的核心。病人送出預約時，你不能只相信他送來的時間，因為客戶端可以捏造時間——就算它平常只是把手機拿到的 startsAt 原封不動傳回來。要在寫入前，用同一套規則再判一次：

export async function assertSlotBookable({
  dentistId, serviceId, durationMinutes, startsAt, excludeAppointmentId,
}: { /* ... */ }): Promise<void> {
  if (Number.isNaN(startsAt.getTime())) throw badRequest('Invalid appointment time');

  const [offers] = await db.select().from(dentistServices)
    .where(and(
      eq(dentistServices.dentistId, dentistId),
      eq(dentistServices.serviceId, serviceId)
    ));
  if (!offers) throw badRequest('That dentist does not offer this service.');

  const day = clinicDayOf(startsAt);
  const { workingHours: hours, busy } = await loadSchedulingInputs([dentistId], day, day, {
    excludeAppointmentId,
  });

  const verdict = classifySlot({
    workingHours: hours, busy, durationMinutes, dentistId, startsAt, now: new Date(),
  });

  if (verdict === 'taken') {
    throw conflict('That time was just taken. Please pick another.', 'slot_taken');
  }
  if (verdict === 'invalid') {
    throw badRequest('That time is not available. Please pick one of the offered slots.');
  }
}

做了什麼：先擋掉無效日期，再確認這位醫師真的做這個服務，然後用 clinicDayOf 把瞬間轉回診所日曆日，重新載入輸入並呼叫 classifySlot。預期看到什麼：只有 'ok' 會讓流程繼續，'taken' 丟 409、'invalid' 丟 400。

為什麼 classifySlot 要把 'taken' 和 'invalid' 分開？因為對病人來說，這兩件事的意義完全不同。'taken' 是一格「真的存在、但剛剛被別人搶走」的時段，值得回一句「剛剛被約走，換一個」；'invalid' 則是「這根本不是時段」——凌晨三點、不在十五分鐘格線上、落在前置期內，或是醫師不做的服務，這些都該回 400，而不是讓病人以為是別人搶走的。

還有一個實作上的小細節：classifySlot 判斷 'taken' 的方式，是先用完整忙碌清單算一次、再用空忙碌清單算一次。若第一次沒有、第二次有，代表它本來是合法時段，只是被佔用了。同一個純函式既能回答「可不可以」，也能分辨「為什麼不行」。

步驟四：POST /api/appointments 真的寫入

export const POST = route(async (req: Request) => {
  const user = await requireAuth();
  const body = createAppointmentSchema.parse(await req.json());
  const patient = await requireOwnedPatient(user, body.patientId);

  const [service] = await db.select().from(services).where(eq(services.id, body.serviceId));
  if (!service || !service.isActive) throw notFound('Service not found');

  const [dentist] = await db.select().from(dentists)
    .where(and(eq(dentists.id, body.dentistId), eq(dentists.isActive, true)));
  if (!dentist) throw notFound('Dentist not found');

  const startsAt = new Date(body.startsAt);
  const endsAt = new Date(startsAt.getTime() + service.durationMinutes * 60_000);

  // 重跑同一套引擎：客戶端不能自己發明一個時間。
  await assertSlotBookable({
    dentistId: dentist.id, serviceId: service.id,
    durationMinutes: service.durationMinutes, startsAt,
  });

  try {
    const [created] = await db.insert(appointments).values({
      patientId: patient.id, dentistId: dentist.id, serviceId: service.id,
      startsAt, endsAt,
    }).returning();
    // ... teleconsult 時由伺服器推導 streamCallId
    return json({ appointment: serialize({ /* ... */ }) }, 201);
  } catch (err) {
    if (isExclusionViolation(err)) {
      throw conflict('That time was just taken. Please pick another.', 'slot_taken');
    }
    throw err;
  }
});

做了什麼：授權、驗證、確認病人屬於這位使用者、確認服務與醫師有效，然後由伺服器用服務時長算出 endsAt，呼叫守衛，最後才 insert。預期看到什麼：成功時回 201 與完整預約；資料庫發生排除約束違反時，回一個乾淨的 409。

兩個地方要特別注意。第一，endsAt 由伺服器算，前端只送 startsAt；否則前端就能偷偷拉長療程，佔用不屬於它的時間。第二，insert 包在 try/catch 裡，並用 isExclusionViolation 認出 Postgres 的 23P01 錯誤——這是下一步要談的資料庫防線，現在只要先把接點留好。

步驟五：改期時排除自己

改期（reschedule）走的是另一條路徑，但守衛是一樣的，只多傳一個參數：

await assertSlotBookable({
  dentistId, serviceId, durationMinutes, startsAt,
  excludeAppointmentId: appointment.id, // 不要被自己擋住
});

少了這一行，當你把一筆 14:00 的預約改到 14:30，載入忙碌區間時會把自己也算進去，於是「14:00 已被佔用」，改期莫名其妙失敗。把目前這筆預約排除，它才能被移動到新時間。

做完長什麼樣

接線完成後，你應該能驗證這幾件事：GET /api/availability 列出的時段，拿同一個 startsAt 去 POST /api/appointments 會成功；捏造凌晨三點、09:07（不在格線上）、或明天早上九點（落在兩小時前置期內）會被回 400；兩個人搶同一個時段，先到的成功、後到的收到 409 與 slot_taken。

最重要的是，讀與寫現在共用同一份 loadSchedulingInputs 與同一個 classifySlot。只要有人改了規則，兩條路徑會一起改，不可能分岔。至於那個 409 為什麼會從「兩個地方」冒出來、以及資料庫到底怎麼仲裁競態，留給下一步的取捨。

小結

先寫一個共用的 loadSchedulingInputs，把工作時段、已約門診與請假撈成引擎要的輸入（改期時排除自己）。GET /api/availability 用它加 availableSlots 列出時段，並回傳診所當地時間的 label；POST /api/appointments 在寫入前用 assertSlotBookable 重跑同一套判準，把 'taken' 轉成 409、'invalid' 轉成 400。endsAt 一律由伺服器算，前端不能自己送。
