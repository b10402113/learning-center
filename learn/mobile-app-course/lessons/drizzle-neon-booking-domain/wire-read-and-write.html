讓讀與寫共用同一個引擎

Step 4/5 · 預約領域模型（Drizzle + Neon）

學習目標

能說明 GET /api/availability 與 POST /api/appointments 為什麼要共用同一份 loadSchedulingInputs 與 classifySlot，並把這個接線做出來。

動手前先確認

這是一個程序型的小節，做完之後你會得到：一個讀取端點與一個寫入端點，兩者對「什麼時間可以預約」的判斷完全一致，因此使用者無法繞過前端、自己捏造一個時間送進資料庫。動手前請先具備兩樣東西：上一節的純函式引擎 availableSlots 與 classifySlot，以及第二步建好的 working_hours、time_off、appointments、services、dentist_services 等表。

問題在哪裡：兩個端點，兩套規則

先看看最直覺、但也最容易出事的寫法。讀取端點 GET /api/availability 讀資料庫、算出可預約時段，傳給 app 顯示。寫入端點 POST /api/appointments 收到病人選的時間，直接把它存進資料庫。

這樣寫在正常情況下能動，但它埋了一個洞：兩個端點各有一套規則。讀取端點的規則是「載入 working hours、扣掉忙碌、濾掉前置期、以 15 分鐘產生」，寫入端點卻只剩「收到什麼存什麼」。只要使用者不透過 app，而是自己發一個請求、帶上凌晨三點的時間，寫入端點也照收。想補救就得在寫入端點把讀取端點那一整套規則重抄一遍，而兩份規則總有一天會不同步。

這一節的做法是把規則抽成一份，讓兩個端點都呼叫它。

第一步：做一個共用的輸入載入器

先處理「把資料庫的列轉成引擎看得懂的形狀」這件事。loadSchedulingInputs 是唯一負責這項工作的函式，讀與寫都呼叫它。

/**
 * Loads everything the scheduling engine needs for a date range.
 * Shared by `GET /api/availability` and the booking write path, so what the
 * API offers and what it accepts can never drift apart.
 */
export async function loadSchedulingInputs(
  dentistIds: string[],
  from: CalendarDay,
  to: CalendarDay,
  options: { excludeAppointmentId?: string } = {}
): Promise<{ workingHours: WorkingHour[]; busy: BusyInterval[] }> {
  if (dentistIds.length === 0) return { workingHours: [], busy: [] };

  // Widen by a day each side so a booking straddling midnight still counts.
  const rangeStart = clinicInstant(from, 0, 0);
  const rangeEnd = new Date(clinicInstant(to, 23, 59).getTime() + 24 * 3600_000);

  const [hours, booked, off] = await Promise.all([
    db.select().from(workingHours).where(inArray(workingHours.dentistId, dentistIds)),
    db
      .select({
        dentistId: appointments.dentistId,
        startsAt: appointments.startsAt,
        endsAt: appointments.endsAt,
      })
      .from(appointments)
      .where(
        and(
          inArray(appointments.dentistId, dentistIds),
          eq(appointments.status, 'booked'),
          lte(appointments.startsAt, rangeEnd),
          gte(appointments.endsAt, rangeStart),
          // A reschedule must not be blocked by the appointment it is moving.
          options.excludeAppointmentId
            ? ne(appointments.id, options.excludeAppointmentId)
            : undefined
        )
      ),
    db
      .select({
        dentistId: timeOff.dentistId,
        startsAt: timeOff.startsAt,
        endsAt: timeOff.endsAt,
      })
      .from(timeOff)
      .where(
        and(
          inArray(timeOff.dentistId, dentistIds),
          lte(timeOff.startsAt, rangeEnd),
          gte(timeOff.endsAt, rangeStart)
        )
      ),
  ]);

  return {
    workingHours: hours.map((h) => ({
      dentistId: h.dentistId,
      weekday: h.weekday,
      startTime: h.startTime,
      endTime: h.endTime,
    })),
    // A booked appointment and a block of time off are the same to the engine.
    busy: [...booked, ...off],
  };
}

這個函式有三個地方要看。

  1. 範圍左右各放寬一天。 查詢用的 rangeStart 是起始日的診所午夜，rangeEnd 則是結束日 23:59 再加 24 小時。為什麼要多這一天？因為一筆預約可能跨過午夜，如果只查當天，午夜另一側的忙碌就會被漏掉。放寬一天是為了安全邊界，多撈到的資料引擎自己會忽略。

  2. 三個查詢用 Promise.all 並行。 工作時段、已預約、請假三者彼此獨立，沒有先後依賴，同時發出可以省下等待時間。

  3. booked 與 off 直接合併成 busy。 這就是上一節那句「對引擎來說兩者是同一件事」的落實處。函式回傳的輸入形狀，正好就是 availableSlots 要的形狀。

選項裡的 excludeAppointmentId 是為改期準備的：當你在移動一筆預約時，那筆預約不該被自己擋住，所以查忙碌區間時把它排除。這個參數在第五步的守衛會用到。

第二步：讀取端點呼叫引擎

有了共用載入器，讀取端點的邏輯就變得很薄。它先驗證查詢參數、找出所有提供這項服務的醫師，然後把載入器與引擎串起來。

const from = parseDay(query.from);
const to = parseDay(query.to ?? query.from);

// Which dentists are in play.
const offering = await db
  .select({ dentistId: dentistServices.dentistId })
  .from(dentistServices)
  .innerJoin(dentists, eq(dentists.id, dentistServices.dentistId))
  .where(
    and(
      eq(dentistServices.serviceId, service.id),
      eq(dentists.isActive, true),
      query.dentistId ? eq(dentists.id, query.dentistId) : undefined
    )
  );

const dentistIds = offering.map((d) => d.dentistId);
if (dentistIds.length === 0) return json({ service, slots: [] });

const { workingHours: hours, busy } = await loadSchedulingInputs(dentistIds, from, to);

const slots = availableSlots({
  workingHours: hours,
  busy,
  durationMinutes: service.durationMinutes,
  from,
  to,
  now: new Date(),
});

查詢參數由 Zod schema（availabilityQuerySchema）驗證，其中 from 與 to 都必須是 YYYY-MM-DD。醫師清單是透過 dentist_services 連接 dentists 過濾出來的，只留 isActive 的醫師。

拿到 slots 之後，端點會把每個時段轉成 API 回應：dentistId、startsAt、endsAt，以及一個 label。那個 label 是用 formatClinicTime 算出來的診所當地時間字串，讓手機 app 直接顯示、不必自己處理時區。

第三步：寫入端點重跑同一套判斷

現在看寫入。這一步是整個接線的核心。端點收到病人選的時間後，並不直接相信它。

const startsAt = new Date(body.startsAt);
const endsAt = new Date(startsAt.getTime() + service.durationMinutes * 60_000);

// The client never gets to invent a time: this re-runs the same engine that
// produced the slot list and rejects anything it would not have offered.
await assertSlotBookable({
  dentistId: dentist.id,
  serviceId: service.id,
  durationMinutes: service.durationMinutes,
  startsAt,
});

try {
  const [created] = await db
    .insert(appointments)
    .values({
      patientId: patient.id,
      dentistId: dentist.id,
      serviceId: service.id,
      startsAt,
      endsAt,
    })
    .returning();

有兩個關鍵動作。第一，endsAt 是伺服器自己算的：從 startsAt 加上服務的 durationMinutes。createAppointmentSchema 裡病人只送 startsAt，從來不送時長。如果讓前端送時長，壞心的人就能送一個很短的長度，把預約擠進原本放不下的空檔。

第二，寫入前呼叫 assertSlotBookable。這個名字叫「斷言」的函式就是寫入守衛，它會重跑讀取端點用的同一套引擎；只要這個時間不是讀取端點會給出的時段，就直接擋下。註解把意圖寫得很清楚：「the client never gets to invent a time」。

第四步：寫入守衛檢查什麼

把守衛展開來看。

export async function assertSlotBookable({
  dentistId,
  serviceId,
  durationMinutes,
  startsAt,
  excludeAppointmentId,
}: {
  dentistId: string;
  serviceId: string;
  durationMinutes: number;
  startsAt: Date;
  excludeAppointmentId?: string;
}): Promise<void> {
  if (Number.isNaN(startsAt.getTime())) throw badRequest('Invalid appointment time');

  const [offers] = await db
    .select()
    .from(dentistServices)
    .where(
      and(eq(dentistServices.dentistId, dentistId), eq(dentistServices.serviceId, serviceId))
    );
  if (!offers) throw badRequest('That dentist does not offer this service.');

  const day = clinicDayOf(startsAt);
  const { workingHours: hours, busy } = await loadSchedulingInputs([dentistId], day, day, {
    excludeAppointmentId,
  });

  const verdict = classifySlot({
    workingHours: hours,
    busy,
    durationMinutes,
    dentistId,
    startsAt,
    now: new Date(),
  });

  if (verdict === 'taken') {
    throw conflict('That time was just taken. Please pick another.', 'slot_taken');
  }
  if (verdict === 'invalid') {
    throw badRequest('That time is not available. Please pick one of the offered slots.');
  }
}

它依序做四件事：先排除不合法的時間字串；再確認這位醫師確實提供這項服務（dentist_services 查不到就擋）；接著載入這位醫師當天的排班輸入；最後把判斷交給 classifySlot，並依判決轉成不同的錯誤。

判決分三種，因為病人的感受不同

classifySlot 是讀與寫真正共用的那顆大腦。它會回傳三種判決：ok、taken、invalid。

export type SlotVerdict = 'ok' | 'taken' | 'invalid';

export function classifySlot({
  workingHours,
  busy,
  durationMinutes,
  dentistId,
  startsAt,
  now,
}: {
  workingHours: WorkingHour[];
  busy: BusyInterval[];
  durationMinutes: number;
  dentistId: string;
  startsAt: Date;
  now: Date;
}): SlotVerdict {
  const day = clinicDayOfInstant(startsAt);
  const matches = (slots: Slot[]) =>
    slots.some((s) => s.dentistId === dentistId && s.startsAt.getTime() === startsAt.getTime());

  const input = { workingHours, durationMinutes, from: day, to: day, now };

  if (matches(availableSlots({ ...input, busy }))) return 'ok';
  // Real slot, just occupied — worth a different message than "not a slot".
  if (matches(availableSlots({ ...input, busy: [] }))) return 'taken';
  return 'invalid';
}

它的作法很聰明：把病人送來的時間當成「只有一天」的查詢，丟進同一個 availableSlots，看它會不會出現在結果裡。第一次用真實的忙碌區間算：如果這個時間在結果裡，代表它是合法的、而且當下有空，判為 ok。第二次刻意把忙碌區間清空再算：如果這次出現了、但第一次沒有，代表這個時間本來是個合法時段，只是剛好被佔走，判為 taken。兩次都沒有，代表它從頭到尾就不該存在（凌晨三點、不在 15 分鐘級距上、太接近現在），判為 invalid。

為什麼要分開？因為對病人來說這兩種失敗的意義完全不同。taken 是「有人比你快一步」，應該回一個 409，請他改選別的時段；invalid 是「這個時間本來就不存在」，應該回 400，告訴他這不是系統提供的選項。守衛依判決分別丟出 conflict(...) 與 badRequest(...)。

還有最後一道防線

寫入端點在 insert 外面包了一層 try/catch，攔截資料庫丟出的排除約束違反。

} catch (err) {
  if (isExclusionViolation(err)) {
    throw conflict('That time was just taken. Please pick another.', 'slot_taken');
  }
  throw err;
}

守衛擋得住「不該存在的時間」，卻擋不住「兩個請求在同一瞬間都通過檢查」。那個更細緻的競態，要交給第五步的資料庫約束來處理，這裡先把違反轉成乾淨的 409。

小結：做完之後，你應該得到什麼？

讀與寫現在共用同一份 loadSchedulingInputs 與同一個 classifySlot。GET /api/availability 把資料庫載成引擎輸入、算出時段；POST /api/appointments 在寫入前重跑同一套引擎，只接受讀取端點會提供的時間，並把 taken 轉成 409、invalid 轉成 400。因為時長由伺服器推導、時間由引擎驗證，使用者無法自己捏造一個預約。

課後你可以自己驗證：用一個不在 15 分鐘級距上的時間送出 POST，應該拿到 400；用一個合法但已被預約的時間，應該拿到 409。原理層面的純函式與測試留給第三步，資料庫層面的仲裁在下一步。
