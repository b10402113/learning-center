防重複預約守在哪一層？

Step 5/5 · 預約領域模型（Drizzle + Neon）

學習目標

能分辨應用層守衛與 Postgres 排除約束各自擋下什麼，並說出為什麼不能只靠其中一層。

前言：兩隻手指同時按下去

上一節你把讀與寫接上同一個引擎，病人再也無法自己捏造一個時間。看起來防護已經完整了，但還有一種情況沒處理：兩位病人在同一秒、分別在自己的手機上，按下了同一個時段。

兩個請求幾乎同時抵達伺服器。第一個請求通過了 assertSlotBookable，準備寫入；第二個請求也在它的資料庫讀取裡看到那個時段還是空的，同樣通過守衛。守衛是「先查、再寫」的兩步動作，兩個請求交錯在中間，誰都沒看到對方。結果兩筆預約都寫了進去，同一時間、同一位醫師，坐了兩位病人。這一節要做的決定是：面對這種競態，防線該放在應用層、資料庫層，還是兩者都要？

兩股張力：看得懂業務的規則 vs 原子性的仲裁

先講清楚兩邊各自的優勢，因為它們解決的其實不是同一個問題。

應用層的守衛（assertSlotBookable 與 classifySlot）看得懂業務語意。它知道「凌晨三點」不是上班時間、「不在 15 分鐘級距上」的候選不存在、「現在加兩小時」才是可預約的最早時間、「這位醫師根本不做這項服務」。這些規則都能用程式描述得很細，而且換了資料庫也照樣能用。

資料庫的約束（排除約束）則是完全相反的性格。它只認得一段幾何關係：「同一位醫師的兩個時間區間不能重疊。」它不懂什麼叫上班時間、什麼叫服務項目，但它有一個應用層永遠比不上的特性：原子性。當兩個寫入真的在同一瞬間發生，資料庫會替它們排出一個順序，讓其中一個成功、另一個失敗。

選項比較：它們各擋下什麼

應用層守衛Postgres 排除約束
擋下什麼不存在的時間：3am、非級距、前置期內、醫師不提供的服務同一位醫師、重疊的已預約區間
什麼時候生效寫入前先查一次，屬於建議性檢查寫入提交那一刻，屬於權威仲裁
併發時兩個請求可能都通過檢查一個提交、另一個被拒
懂不懂業務懂，能分辨各種不可預約的原因不懂，只認區間有沒有重疊
可移植性高，換資料庫仍可用Postgres 專屬

這張表說明了關鍵：兩者不是替代品，而是互補。應用層守衛無法解決競態，資料庫約束無法辨認業務規則。少了任何一邊，都會留下一種漏洞。

資料庫那一層長什麼樣

診所的排除約束是手寫在 migration 裡的，因為 Drizzle 產生不出這種 constraint。

-- Double-booking is prevented HERE, in the database, not in application logic.
-- Two simultaneous bookings for the same dentist and overlapping range: one
-- commits, the other raises 23P01 and the API turns that into a 409.
-- Hand-written: drizzle-kit cannot generate EXCLUDE constraints.
ALTER TABLE "appointments" ADD CONSTRAINT "appointments_no_double_booking"
  EXCLUDE USING gist (
    "dentist_id" WITH =,
    tstzrange("starts_at", "ends_at") WITH &&
  ) WHERE ("status" = 'booked');

逐段讀這個 constraint。它叫 EXCLUDE USING gist，意思是「用 GiST 索引來排除某些列的組合」。裡面的條件有兩行：dentist_id WITH = 表示兩列必須是同一位醫師；tstzrange(starts_at, ends_at) WITH && 表示兩列的時間區間必須重疊（&& 是 Postgres 的「區間重疊」運算子）。兩者同時成立時，資料庫會拒絕讓第二列存在。

最後的 WHERE ("status" = 'booked') 是一個部分條件：這個約束只管狀態為 booked 的列。所以已取消或已完成的預約不會佔位，歷史資料也能保留。前面先執行的 CREATE EXTENSION IF NOT EXISTS btree_gist; 則是為了讓 GiST 索引能同時處理等值比較（醫師 id）與區間比較。

這個約束是資料庫層級的，因此就算有人繞過 API、直接連資料庫寫入，它依然有效。這正是「守在最底層」的價值。

約束被觸發時，應用層要做什麼

資料庫拋出的錯誤帶著一個明確的代碼 23P01，代表排除約束被違反。應用層的責任不是重新實作約束，而是認出這個代碼，把低階的資料庫錯誤轉成病人看得懂的訊息。

/** Postgres exclusion-constraint violation — the double-booking guard firing. */
export function isExclusionViolation(err: unknown): boolean {
  const code = (err as { code?: string; cause?: { code?: string } })?.code
    ?? (err as { cause?: { code?: string } })?.cause?.code;
  return code === '23P01';
}

寫入端點接到這個判斷後，把錯誤轉成 409 與 slot_taken 代碼，讓 app 顯示「這個時段剛被搶走，請選別的」。

} catch (err) {
  if (isExclusionViolation(err)) {
    throw conflict('That time was just taken. Please pick another.', 'slot_taken');
  }
  throw err;
}

為什麼要分辨錯誤代碼、而不是把所有資料庫錯誤都當成「時段被搶走」？因為排除約束違反和連線失敗、欄位錯誤的意義完全不同。只認 23P01，才不會把真正的系統故障誤報成「手腳太慢」。

判別問句：這條規則該放哪一層？

面對一條新的「不許發生」規則，可以問自己兩個問題：

  1. 它能不能只用「哪些列不能同時存在」這種幾何關係描述？ 如果可以，例如「同一資源的區間不得重疊」，就把它交給資料庫，因為只有資料庫能提供跨請求的原子性。
  2. 它是不是需要看懂業務語意才能判斷？ 例如「這算不算上班時間」「這位醫師做不做這項服務」「是不是太接近現在」，這些只有應用層知道，留在 classifySlot 這一類純函式裡。

只要兩個問題的答案分屬兩邊，就代表你需要兩層。診所的預約正是這種情況。

反例：只靠一層會發生什麼

只靠應用層守衛

如果拿掉排除約束，只留 assertSlotBookable，平常看起來完全正常，taken 的判斷也會正確地擋掉大多重複預約。但前面那個「兩隻手指同時按下去」的場景會直接穿過去，因為守衛終究是「先查、再寫」的兩步。任何應用層的檢查都無法阻止兩個請求在中間交錯。

只靠資料庫約束

反過來，如果只留約束、拿掉守衛，情況一樣糟，只是錯在不同地方。排除約束只知道「重疊」，它會接受任何不與既有預約重疊的時間。所以凌晨三點、不在 15 分鐘級距上的時間、距離現在只剩十分鐘的時間、甚至這位醫師根本不提供的服務，都會被照單全收。約束擋得住「撞到別人的預約」，擋不住「這根本不是一個合法的預約」。

程式註解把這件事講得最直白：「Without this the only protection is the exclusion constraint, which stops overlaps and nothing else — 3am, off-grid, inside the lead time, or a service the dentist does not even perform would all be accepted.」

同一個陷阱的另一種樣子

有時候團隊會想「用應用層做到一樣的效果」，於是在插入前先 SELECT 查有沒有重疊，再決定要不要 INSERT。這其實就是把應用層守衛再寫一遍，完全繼承同一個競態問題。無論查詢寫得多仔細，兩個請求都能在查完、寫入前的那一刻交錯。這也是為什麼約束一旦存在，就不該用應用層邏輯取代它。

小結：可帶走的決策規則

能用「哪些列不得同時存在」描述的規則，交給資料庫的約束，由它提供原子仲裁；需要業務語意才能判斷的規則，留在應用層的純函式。兩者都做，但不要用應用層邏輯取代資料庫約束。應用層負責把約束違反（Postgres 23P01）轉成乾淨的 409，並保留其他錯誤的原貌。

回頭看這五步：時區層確保時間的表示正確，資料模型把「誰有空」變成可查詢的結構，純函式引擎把規則算成時段，接線讓讀與寫共用同一套判斷，最後由資料庫約束仲裁真正的競態。這一整套就是一個能直接搬到其他預約型產品的領域層，而不只是 Dentify 的某幾個檔案。
