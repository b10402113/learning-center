診所時區層：把牆上的時間換成真正的瞬間

Step 1/5 · 預約領域模型（Drizzle + Neon）

學習目標

能說出「日期字串」與「跨日加減」為什麼會出錯，並用 CalendarDay 與 clinicInstant 把診所牆上的時間正確換算成真正的 UTC 瞬間。

前言：一句「下週三早上九點」藏了多少陷阱

想像診所櫃檯跟病人說：「下週三早上九點，幫你排在張醫師那裡。」你在程式裡把這個時間存成 '2026-03-11T09:00'，看起來再合理不過。結果到了當天，病人的通知寫著下午一點，櫃檯一臉困惑，醫師也一頭霧水。

這種錯誤不是手滑打錯字，而是把兩種完全不同的東西混在一起：一種是「牆上時鐘顯示的時間」，另一種是「宇宙裡真正發生的那個瞬間」。診所說的九點，預設是診所當地牆上時鐘的九點；但電腦要存進資料庫、要跨手機、跨伺服器傳遞，靠的是絕對瞬間。這一節就是把這兩者分清楚，並且讓時區換算只發生在一個地方。因為只要換算散落在各處，總有一天會有一處漏了，而時間的錯誤最麻煩的地方在於：它平常看起來都對，只在特定日子出錯。

先看一個很多人踩過的坑：把日期字串直接丟給 Date

先講一個看起來很無害的寫法。你拿到 API 傳來的 '2026-03-11'，很直覺地寫 new Date('2026-03-11')，想說這不就代表那天嗎？問題是 JavaScript 對這種「只有日期、沒有時間」的字串，會用 UTC 的午夜來解讀。所以在紐約的診所，這個瞬間其實是當地 3 月 10 日的晚上七點。你以為拿到 3 月 11 日，實際上拿到的是 3 月 10 日。日期就這樣默默少了一天。

診所程式碼的解法很乾脆：不要讓字串直接變成 Date，而是先解析成一個結構化的「日曆日」。

export type CalendarDay = { year: number; month: number; day: number };

/** 'YYYY-MM-DD' → calendar day. Deliberately not `new Date(str)`, which is UTC-parsed. */
export function parseDay(iso: string): CalendarDay {
  const m = /^(\d{4})-(\d{2})-(\d{2})$/.exec(iso);
  if (!m) throw new Error(`Expected YYYY-MM-DD, got "${iso}"`);
  return { year: +m[1], month: +m[2], day: +m[3] };
}

CalendarDay 只是三個數字：年、月、日。它不帶時區，也不帶時間，因為它代表的是「日曆上那一格」，而不是某個瞬間。把日期限制成這個形狀之後，後面所有跟日期有關的運算就不會不小心沾到時區。

核心工具：clinicInstant 把牆鐘時間變成真正的瞬間

把「日曆日」想成一張掛在診所牆上的紙本月曆，你要在上面圈出「3 月 11 日」。但圈完之後，電腦還需要知道：3 月 11 日早上九點，換算成全球共通的時間點，到底是哪一刻？這件事由 clinicInstant 負責。

/** Single clinic, single timezone (PLAN.md A1). */
export const CLINIC_TZ = process.env.CLINIC_TZ ?? 'America/New_York';

/**
 * A clinic-local wall-clock time → the UTC instant it actually happens at.
 * This is the only place the timezone is applied, so DST lives here alone.
 */
export function clinicInstant(day: CalendarDay, hours: number, minutes: number): Date {
  const t = new TZDate(day.year, day.month - 1, day.day, hours, minutes, 0, 0, CLINIC_TZ);
  return new Date(t.getTime());
}

這裡用了 @date-fns/tz 套件提供的 TZDate。它做的事是：你給它一個「診所當地的牆鐘時間」（年、月、日、時、分），再加上診所時區 CLINIC_TZ，它會回傳那個時刻真正對應的絕對時間點。函式回傳的是標準的 Date，所以後續的比較、排序、存進資料庫，用的都是同一個絕對瞬間。

註解裡那句「the only place the timezone is applied」是整個設計的重點。時區換算是一件很容易錯、而且錯了很難查的事，所以他們選擇只留一個入口：所有牆鐘時間要變成瞬間，都走 clinicInstant。這樣日光節約時間（daylight saving time，簡稱 DST）的數學只活在這個檔案裡，要檢查、要寫測試都只有一處。

反過來：從瞬間問「這是診所當地的哪一天」

有時候你手上已經有一個瞬間，卻需要知道它在診所當地是星期幾、算哪一天。例如客人想預約的那個時間，到底是週三還是週四？這種反推由 clinicDayOf 處理。

/** The clinic-local calendar day an instant falls on, plus its weekday (0 = Sunday). */
export function clinicDayOf(instant: Date): CalendarDay & { weekday: number } {
  const t = new TZDate(instant.getTime(), CLINIC_TZ);
  return {
    year: t.getFullYear(),
    month: t.getMonth() + 1,
    day: t.getDate(),
    weekday: t.getDay(),
  };
}

它一樣靠 TZDate，只是方向相反：這次是拿一個絕對瞬間，放進診所時區裡看它落在哪一天。weekday 用 0 代表星期日、6 代表星期六，之後查工作時段時會用到。

為什麼「加一天」不能寫成「加 24 小時」

接下來看一個更隱蔽的錯誤。如果你要列出從今天到下週的每一天，最直覺的寫法是「每次把時間戳加 24 小時」。平常這樣做沒事，但碰到日光節約時間切換的那一天就會出錯：那天只有 23 小時或 25 小時，於是你會漏掉一天，或把同一天數了兩次。

診所的 eachDay 選擇用「日曆運算」而不是「加 24 小時」：它用 UTC 的年月日當作純粹的數字，每次只把日期加一。

/**
 * Inclusive range of clinic-local calendar days. Steps by calendar arithmetic,
 * not by adding 24h, so a DST day doesn't shift the sequence.
 */
export function eachDay(from: CalendarDay, to: CalendarDay, maxDays = 62): CalendarDay[] {
  const days: CalendarDay[] = [];
  const cursor = new Date(Date.UTC(from.year, from.month - 1, from.day));
  const end = Date.UTC(to.year, to.month - 1, to.day);
  while (cursor.getTime() <= end && days.length < maxDays) {
    days.push({
      year: cursor.getUTCFullYear(),
      month: cursor.getUTCMonth() + 1,
      day: cursor.getUTCDate(),
    });
    cursor.setUTCDate(cursor.getUTCDate() + 1);
  }
  return days;
}

注意這裡雖然用了 Date，但全程只看 UTC 欄位、只用 setUTCDate 加減。它把 Date 當成一台「只會數日期」的計算機，刻意的避開時區資訊，所以日光節約讓某天變成 23 小時或 25 小時，都動不了這個序列。

顯示的時候，才把時間轉成人看得懂的格式

資料庫和運算都用絕對瞬間，但最後要給病人看的時候，一定要轉回診所當地的時間。Intl.DateTimeFormat 可以指定 timeZone，而診所選擇在 API 回傳時就先把標籤格式好，讓手機 app 完全不需要知道 CLINIC_TZ 是什麼。

/** Clinic-local "3:00 PM" for display in API responses the mobile app renders verbatim. */
export function formatClinicTime(instant: Date): string {
  return new Intl.DateTimeFormat('en-US', {
    timeZone: CLINIC_TZ,
    hour: '2-digit',
    minute: '2-digit',
    hour12: true,
  }).format(instant);
}

這行 timeZone: CLINIC_TZ 是關鍵。如果不指定，它會用伺服器或手機的時區，那就又回到「每台裝置顯示的時間都不一樣」的老問題。指定之後，不管伺服器架在哪裡、病人手機設成哪個時區，顯示出來的永遠是診所當地時間。

這個觀念和後面的排班引擎怎麼接上

到這裡，你手上有了兩個基本積木：用 CalendarDay 表示「日曆上的一天」，用 clinicInstant 把牆鐘時間變成絕對瞬間。下一節會把「誰什麼時候有空」建成資料表，而工作時段存的就是診所當地的牆鐘時間；到了第三步，排班引擎會用 clinicInstant 把每個工作天轉成區間，因此就算遇到日光節約切換，診所實際工作的時數也不會被算錯。

把時區集中在一層，回報很直接：你在這裡把換算測對一次，後面所有跟時間有關的功能就都站在對的基礎上。

小結

「日曆上的一天」和「宇宙裡的瞬間」是兩回事，混用就會出現少一天、多幾小時的錯。診所用 CalendarDay（只有年月日的結構）表示一天，用 clinicInstant 把診所牆鐘時間換成真正的 Date，而且所有時區換算只集中在 time.ts 一個檔案。跨日加減用日曆運算而不是加 24 小時，顯示則用帶 timeZone 的 Intl.DateTimeFormat。

時間有了正確的表示方式，下一步才有意義：把「誰在什麼時候有空」變成資料表，讓排班引擎有東西可以算。下一節會看 working_hours、time_off、services 與 appointments 這幾張表怎麼分工。
