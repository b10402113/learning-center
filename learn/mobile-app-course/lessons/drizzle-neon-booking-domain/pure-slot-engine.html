純函式排班引擎：從 working hours 算出可預約時段

Step 3/5 · 預約領域模型（Drizzle + Neon）

學習目標

能說明 availableSlots 如何用半開區間、15 分鐘粒度、2 小時前置期與服務長度，從 working hours 與 busy 區間算出可預約時段。

前言：資料有了，那「怎麼算」呢？

上一節準備好了兩種輸入：每位醫師一週的牆鐘作息，以及一組「不可用」的忙碌區間。現在問題很具體——給定一個週三、一個三十分鐘的洗牙療程，要怎麼列出所有可以選的起始時間？

最直覺的寫法是在 API 裡直接查資料庫、當場一邊查一邊判斷。這種寫法能動，但很快會失控：日光節約的邊界、前置期的最後一分鐘、剛好接在別人後面的時段，全部散在查詢與迴圈之間，沒有一處可以單獨驗證。於是你會發現自己只能靠「手動選幾個時間試試看」來確認邏輯對不對。

這裡刻意反過來做：把整個計算抽成一個純函式。資料由呼叫者準備好再餵進來，答案由它算出來，它自己不去碰資料庫，也不偷看系統時鐘。這一節就來看這個函式怎麼運作，以及它為什麼能讓最難測的邊界變成幾行斷言。

「純」是什麼意思，為什麼要這樣設計

純函式的定義很簡單：同樣的輸入，永遠得到同樣的輸出；而且過程中不產生副作用。它不看 Date.now()、不查資料庫、不改外部狀態。

在這個設計裡，連「現在幾點」都當成參數傳進去，而不是讓函式自己去讀時鐘。這一點很關鍵：如果函式內部偷看真實時間，測試就會隨執行時間不同而時好時壞。把 now 變成輸入之後，測試可以假裝現在是六月一日，穩定地驗證任何時間點的行為。

你可以把純函式想成一台計算機：你把數字按進去，它算出答案，不會自己打開抽屜翻資料。availableSlots 就是這台計算機。

export type AvailableSlotsInput = {
  workingHours: WorkingHour[];
  busy: BusyInterval[];
  durationMinutes: number;
  from: CalendarDay;
  to: CalendarDay;
  now: Date;
};

先搞懂「重疊」：半開區間

整個引擎最常做的判斷是「這個候選時段有沒有撞到某個忙碌區間」。看起來只要比較兩個區間有沒有交集就好，但魔鬼在端點。

這裡採用的是半開區間（half-open interval）：一段時間包含起點、不包含終點。判斷重疊的函式只有一行：

export function overlaps(aStart: Date, aEnd: Date, bStart: Date, bEnd: Date): boolean {
  return aStart.getTime() < bEnd.getTime() && bStart.getTime() < aEnd.getTime();
}

注意兩邊都是嚴格的「小於」，不是「小於等於」。所以一段 13:00–13:30 的候選，和一段 13:30–14:00 的既有預約，不算重疊。這在診所是完全合理的：前一位病人 13:30 離開椅子，下一位 13:30 坐上去，中間不需要緩衝。

如果把條件寫成「小於等於」，端點相接就會被判定為衝突。結果是整個下午的時段會互相排擠，可預約的數量少得莫名其妙——而且很難看出原因，因為每一段單獨看都「好像有道理」。先用一行把重疊定義對，後面所有判斷才站得住。

引擎的輸入與三個常數

先把幾個規則寫成常數，而不是散落的魔法數字：

export const SLOT_GRANULARITY_MINUTES = 15; // 候選時段每隔 15 分鐘產生一個
export const MIN_LEAD_TIME_MINUTES = 120;   // 距離現在太近的時段不能約（2 小時）
export const CANCEL_CUTOFF_HOURS = 24;      // 取消/改期的截止線（後續會用到）

第一個常數決定「格線」：可預約時間只能是 09:00、09:15、09:30 這種十五分鐘的倍數，不會出現 09:07。第二個常數是前置期：病人不能預約兩小時內就要開始的診，因為診所需要時間準備。第三個常數今天用不到，但它和其他規則放在一起，是因為它們都屬於「診所的時間規則」。

演算法逐段拆解

現在看主體。它做的事其實很樸素：走過每一天，為每種工作時段產生候選起點，把不該出現的濾掉。分幾段看會更清楚。

第一段：準備前置期與分組

if (durationMinutes <= 0) return [];

const earliest = now.getTime() + MIN_LEAD_TIME_MINUTES * MINUTE;
const duration = durationMinutes * MINUTE;
const step = SLOT_GRANULARITY_MINUTES * MINUTE;

// 把忙碌區間依醫師分組，讓每個候選只掃自己的醫師。
const busyByDentist = new Map<string, BusyInterval[]>();
for (const b of busy) {
  const list = busyByDentist.get(b.dentistId);
  if (list) list.push(b);
  else busyByDentist.set(b.dentistId, [b]);
}

先把服務時長換成毫秒、算出前置期的最早可約時間，並把忙碌區間按醫師分堆。分堆的用意是效能與清晰：當我們在檢查「王醫師的某個候選」時，只需要翻王醫師自己的忙碌清單，不必掃過所有醫師的資料。

第二段：走過每一天與每個工作時段

for (const day of eachDay(from, to)) {
  const weekday = weekdayOf(day);

  for (const wh of workingHours) {
    if (wh.weekday !== weekday) continue;

    const [startH, startM] = parseClockTime(wh.startTime);
    const [endH, endM] = parseClockTime(wh.endTime);

    // 兩端都經過診所時區轉換，日光節約日也會得到診所實際工作的分鐘數。
    const windowStart = clinicInstant(day, startH, startM).getTime();
    const windowEnd = clinicInstant(day, endH, endM).getTime();
    if (windowEnd <= windowStart) continue;

    const dentistBusy = busyByDentist.get(wh.dentistId) ?? [];

這裡是上一節時區層派上用場的地方：clinicInstant 把「某天 09:00」換成真正的瞬間。因為兩端都經過時區轉換，遇到春天往前撥的那一天，視窗是診所實際工作的分鐘數，而不是剛好八小時的錯覺。

第三段：以固定步長產生並過濾候選

    for (let t = windowStart; t + duration <= windowEnd; t += step) {
      if (t < earliest) continue;

      const startsAt = new Date(t);
      const endsAt = new Date(t + duration);

      const blocked = dentistBusy.some((b) =>
        overlaps(startsAt, endsAt, b.startsAt, b.endsAt)
      );
      if (blocked) continue;

      slots.push({ dentistId: wh.dentistId, startsAt, endsAt });
    }
  }
}

迴圈條件 t + duration <= windowEnd 保證候選不會超出打烊時間：一個三十分鐘的療程，最後可約的起點必須讓它剛好在 17:00 前結束。接著三個過濾條件依序是：太接近現在（前置期）、與忙碌區間重疊、以及不成立就跳過。全部通過的，才是一格可預約時段。

第四段：排序後回傳

return slots.sort(
  (a, b) => a.startsAt.getTime() - b.startsAt.getTime() || a.dentistId.localeCompare(b.dentistId)
);

先按時間排、時間相同再按醫師排，讓 API 回傳的順序穩定可預期。

用具體數字感受一下

假設週一工作時段是 09:00–17:00，服務三十分鐘，粒度十五分鐘。候選起點從 09:00 開始，每十五分鐘一個：09:00、09:15、09:30⋯⋯。但最後一個起點必須讓服務在 17:00 前結束，所以 16:30 可以（16:30–17:00），16:45 不行（會拖到 17:15）。從 09:00 到 16:30，每十五分鐘一個，剛好是 31 個時段。

如果這段時間裡已經有一筆 10:00–10:30 的預約，哪些起點會被擋掉？候選 09:45 會跑到 10:15，撞上既有預約——擋掉；10:00 與 10:15 也擋掉。但 09:30 剛好在 10:00 結束（端點相接，不重疊），10:30 則緊接在既有預約後開始，兩者都仍然可約。這正是半開區間在實務上的樣子。

同一時間若兩位醫師都有空，引擎會回傳兩個時段（一位一個）。前端拿到後會依顯示標籤去重，只讓病人看到一格「09:00」，但底層其實保留了「哪一位醫師」這個選擇。

為什麼這些邊界非測不可

因為這個引擎是純的，日光節約與前置期這些最難手動重現的情況，可以用單元測試釘死。測試裡有幾個值得記住的案例：

  • now 距離 09:00 剛好兩小時，09:00 可以約；差一分鐘，最早只能約 09:15。
  • 春天往前撥之後的週一 09:00 是 UTC 13:00，切換前的週五 09:00 是 UTC 14:00，兩者顯示的都是「09:00 AM」，時段數也一樣。
  • 一個九十分鐘的療程，最後可約起點是 15:30（15:30 加九十分鐘剛好 17:00）。
  • 一個九小時的療程在 09:00–17:00 的視窗裡完全排不下，回傳空陣列。

這些案例如果用手動點畫面來測，大概要等到某一年日光節約切換才會發現錯了。抽成純函式之後，它們只是幾個穩定的斷言。

小結

availableSlots 是一台純計算機：輸入 working hours、busy 區間、服務時長、日期範圍與「現在」，輸出所有可預約時段。它用半開區間定義重疊（端點相接不算衝突），以 15 分鐘為步長產生候選，用服務時長確保不超時，用 2 小時前置期濾掉太近的時段，並把不同醫師的忙碌區間分開處理。因為它不碰資料庫也不看時鐘，日光節約與各種邊界都能被單元測試牢牢釘住。

引擎會算，但它不會自己擋人。下一步要把它接進兩條 API：一條負責列出可預約時段，一條負責真的寫入預約，而且兩條要用同一份輸入與同一套判準——否則「系統說可以約」和「系統真的讓你約」就會是兩套規則。
