純函式排班引擎：從 working hours 算出可預約時段

Step 3/5 · 預約領域模型（Drizzle + Neon）

學習目標

能用半開區間、15 分鐘粒度、120 分鐘前置期與服務長度，從 working hours 推出可預約時段。

前言：把班表和請假單丟進去，吐出可以選的時間

上一節把資料建好了：醫師每週的班表、請假區間、已被佔走的預約、服務要多久，通通有了去處。但病人打開 app 的那一刻，他想看到的不是這些表，而是一排可以直接點的時段，像是「週三 09:00、09:15、09:30⋯⋯」。

把「一堆規則和例外」變成「一排可選時間」的這段計算，就是這一節的主角。它有個很容易被低估的特性：它是一個純函式。純函式意思是，你只把資料餵進去，它就把結果算出來，過程中不碰資料庫、不讀系統時鐘、不產生副作用。為什麼這件事值得特別強調？因為時間相關的 bug，尤其像日光節約切換、前置期邊界這類，如果得連上資料庫才測得動，你根本沒辦法把邊界情況釘死。純函式讓這件事變成一份普通的單元測試。

先看整個引擎的輸入與輸出

這個函式的名字叫 availableSlots。輸入是一包資料，輸出是一個時段陣列。

export type Slot = {
  dentistId: string;
  startsAt: Date;
  endsAt: Date;
};

export type AvailableSlotsInput = {
  workingHours: WorkingHour[];
  busy: BusyInterval[];
  durationMinutes: number;
  from: CalendarDay;
  to: CalendarDay;
  now: Date;
};

輸入裡有工作時段、忙碌區間、這次要預約的服務時長、查詢的起訖日，還有「現在時刻」。輸出裡的每個 Slot 都帶著 dentistId，因為同一個時間可能有好幾位醫師都能提供服務，病人最後要選的其實是「哪個時間、哪位醫師」的組合。

引擎裡有三個常數先記住，它們都是寫死的，不是設定值：

  • SLOT_GRANULARITY_MINUTES = 15：時段以 15 分鐘為間隔產生。
  • MIN_LEAD_TIME_MINUTES = 120：距離現在不到兩小時的時段不接受預約。
  • CANCEL_CUTOFF_HOURS = 24：取消或改期必須在預約前 24 小時完成。

為什麼前置期要存在？因為病人不可能在開車前往診所的路上才按預約，櫃檯也需要時間準備。把「現在」一起當成輸入而不是在函式裡呼叫系統時鐘，正是純函式的一部分：測試時你可以指定任何一個假想的「現在」。

關鍵概念：半開區間，碰在一起不算重疊

整個引擎會不斷問同一個問題：「這個候選時段有沒有跟某個忙碌區間撞到？」這個判斷寫在 overlaps 裡。

/** Half-open intervals: touching at an endpoint is not an overlap. */
export function overlaps(aStart: Date, aEnd: Date, bStart: Date, bEnd: Date): boolean {
  return aStart.getTime() < bEnd.getTime() && bStart.getTime() < aEnd.getTime();
}

這叫半開區間：一段時間從起點「含」、到終點「不含」。所以 09:00 到 09:30 的預約，和 09:30 到 10:00 的候選，雖然在 09:30 這一點接觸，卻不算重疊。這正是診所排班想要的結果：前一位病人看到 09:30 結束，下一位就從 09:30 開始，中間不需要刻意空一分鐘。

判斷式是嚴格的「小於」而不是「小於等於」。只要 `aStart` 早於 `bEnd`，而且 `bStart` 早於 `aEnd`，兩段才算重疊。任何一端剛好相等，就當作沒撞到。

主函式：availableSlots

接下來是完整的引擎。它有點長，但一步一步拆開來看，其實很單純。

/**
 * Every bookable start time for a service across a date range.
 *
 * Pure: the caller loads the rows, this decides. That is what makes the DST
 * cases (PLAN.md R4) testable without a database.
 */
export function availableSlots({
  workingHours,
  busy,
  durationMinutes,
  from,
  to,
  now,
}: AvailableSlotsInput): Slot[] {
  if (durationMinutes <= 0) return [];

  const earliest = now.getTime() + MIN_LEAD_TIME_MINUTES * MINUTE;
  const duration = durationMinutes * MINUTE;
  const step = SLOT_GRANULARITY_MINUTES * MINUTE;

  // Group busy intervals per dentist so a candidate only scans its own dentist.
  const busyByDentist = new Map<string, BusyInterval[]>();
  for (const b of busy) {
    const list = busyByDentist.get(b.dentistId);
    if (list) list.push(b);
    else busyByDentist.set(b.dentistId, [b]);
  }

  const slots: Slot[] = [];

  for (const day of eachDay(from, to)) {
    const weekday = weekdayOf(day);

    for (const wh of workingHours) {
      if (wh.weekday !== weekday) continue;

      const [startH, startM] = parseClockTime(wh.startTime);
      const [endH, endM] = parseClockTime(wh.endTime);

      // Both endpoints go through the clinic timezone, so a spring-forward day
      // still yields the same number of working minutes the clinic actually works.
      const windowStart = clinicInstant(day, startH, startM).getTime();
      const windowEnd = clinicInstant(day, endH, endM).getTime();
      if (windowEnd <= windowStart) continue;

      const dentistBusy = busyByDentist.get(wh.dentistId) ?? [];

      for (let t = windowStart; t + duration <= windowEnd; t += step) {
        if (t < earliest) continue;

        const startsAt = new Date(t);
        const endsAt = new Date(t + duration);

        const blocked = dentistBusy.some((b) =>
          overlaps(startsAt, endsAt, b.startsAt, b.endsAt)
        );
        if (blocked) continue;

        slots.push({ dentistId: wh.dentistId, startsAt, endsAt });
      }
    }
  }

  return slots.sort(
    (a, b) => a.startsAt.getTime() - b.startsAt.getTime() || a.dentistId.localeCompare(b.dentistId)
  );
}

第一步：先把忙碌區間依醫師分組

在進入迴圈之前，程式先把 busy 陣列整理成一個 Map，key 是醫師 id。這樣做的原因很實際：如果每位醫師的候選時段都要掃過「所有人的」忙碌區間，複雜度會白白多一個數量級。分組之後，某位醫師的候選只需要跟他自己的忙碌區間比對。註解把這個考量寫得很白：「a candidate only scans its own dentist」。

第二步：逐日、逐工作時段展開

外層用 eachDay(from, to) 走過查詢範圍裡的每一天。對每一天，先問 weekdayOf(day) 它是星期幾，然後在所有工作時段裡找出 weekday 相符的那幾筆。

找到一筆工作時段後，把牆鐘的起訖時間經過 clinicInstant 換成真正的瞬間，得到 windowStart 與 windowEnd。這裡有個防禦性的檢查：如果換算後結束不晚於開始，就跳過這一筆，避免壞資料讓迴圈空轉。

還記得上一節那位在日光節約日出錯的同學嗎？這段註解就是解答：因為起點和終點都各自經過診所時區換算，所以春天少一小時的那天，診所實際上的工作分鐘數會被正確算出，而不是被硬生生的 24 小時假設弄歪。

第三步：以 15 分鐘粒度產生候選

內層迴圈是整個引擎的心臟。它從 windowStart 開始，每次前進 step（15 分鐘），條件是「候選的結束時間不能超過工作時段結束」。

for (let t = windowStart; t + duration <= windowEnd; t += step) {
  if (t < earliest) continue;

  const startsAt = new Date(t);
  const endsAt = new Date(t + duration);

  const blocked = dentistBusy.some((b) =>
    overlaps(startsAt, endsAt, b.startsAt, b.endsAt)
  );
  if (blocked) continue;

  slots.push({ dentistId: wh.dentistId, startsAt, endsAt });
}

這裡回答了三個問題。第一，時段從哪裡開始？固定以 15 分鐘為級距，所以不會出現 09:07 這種時間。第二，時段多長？由 durationMinutes 決定，也就是服務本身的長度。第三，怎麼濾掉不行的候選？兩個條件：如果起點早於 earliest（現在加兩小時前置期）就跳過；如果與任何一個忙碌區間重疊就跳過。

把服務長度帶進條件 t + duration <= windowEnd 很重要。假設診所開到 17:00，而某項服務要 90 分鐘，那麼 15:45 開始的候選會超過關門時間，必須被排除。時段不是「起點在營業時間內」就算數，而是「整段都放得下」才算數。

第四步：排序後回傳

最後，所有通過的時段會依開始時間排序；如果兩位醫師同一時間都有空，再用 dentistId 作穩定的第二排序鍵。穩定的順序讓 API 回傳的結果可預期，前端畫面也不會每次重新整理就跳來跳去。

為什麼引擎要維持「純」

函式不連資料庫，不是偷懶，而是設計選擇。載入資料的工作交給呼叫端；引擎只負責判斷。註解把理由講得很清楚：這正是日光節約的案例可以在沒有資料庫的情況下被測試的原因。

因為「現在」是輸入的一部分，你可以把 now 設成某個剛好跨越前置期邊界的時刻，測出「差一分鐘該不該出現」。因為日期是用 CalendarDay 進來的，你可以直接餵日光節約切換那一天，驗證工作日數與時段數都沒有跑掉。這些測試不需要資料庫、不需要等待、不會因為執行環境的時區不同而忽晴忽雨。

小結

availableSlots 把 working hours 與忙碌區間算成一排可預約時段。它用半開區間判斷重疊（端點相接不算撞到），以 15 分鐘粒度產生候選，用服務長度決定時段要多長，用 120 分鐘前置期濾掉太近的時段。因為它是純函式，時間的邊界情況可以用單元測試釘死，不需要資料庫。

引擎算得再準，也只是「讀」的那一半。如果寫入預約時不重跑同一套規則，病人就能自己捏造一個 3am、或不在級距上的時間送進來。下一節要處理的就是這個接線：讓讀與寫共用同一個引擎。
