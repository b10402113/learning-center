# trigger.dev 背景任務與 Retry

## Learning goal

把易失敗的長時 AI 工作移出請求路徑，寫 task、看 retry 語意、用 runs / logs 除錯

## Steps

1. [[learn/mobile-app-course/nodes/background-ai-jobs/why-background-jobs|長工作不能塞在請求裡：為什麼要背景任務]] — 認出長時且易失敗的 AI 工作，理解背景任務解決了什麼問題
2. [[learn/mobile-app-course/nodes/background-ai-jobs/task-anatomy|Task 是什麼：schemaTask 的 id、schema 與 run]] — 拆開一個 task 的三個零件，理解 durable execution 的意義（after step 1）
3. [[learn/mobile-app-course/nodes/background-ai-jobs/write-and-trigger-task|寫 task 並從 API route 觸發：generate-plan 實作]] — 寫出 schemaTask 並從 route 觸發、拿到 runId（after step 2）
4. [[learn/mobile-app-course/nodes/background-ai-jobs/retry-and-failure|失敗之後：重試語意、退路與標記失敗]] — 依工作性質決定重試次數、退路與失敗處理（after step 3）
5. [[learn/mobile-app-course/nodes/background-ai-jobs/debug-with-runs-logs|用 runs 與 logs 除錯：從 dashboard 追回程式碼]] — 用一次 run 的 payload、logs 與嘗試紀錄找出失敗原因（after step 4）

## Lesson

AI 工作有兩個麻煩的性質：慢，而且會失敗。叫一次 LLM 產生飲食計畫、分析一張餐點照片，動輒要好幾秒到數十秒；模型可能回傳格式不對、圖片可能不是食物、網路可能剛好抖一下。如果把這些工作直接塞在使用者點下按鈕的那條請求路徑裡，使用者就得盯著轉圈圈，伺服器也得一路等它跑完——一旦超時，前面做的一半全部白費。這個節點要處理的，就是怎麼把這類工作搬到請求路徑之外，交給 trigger.dev 變成有重試、有紀錄、可除錯的背景任務。

五步沿著一條真實的任務生命週期走：先建立「為什麼要搬出去」的判斷力，再拆解一個 task 的組成（id、schema、run）與它 durable 的執行模型；接著動手寫出 `generate-plan` 這個 schemaTask，並從 API route 觸發、拿到 runId；然後面對每個背景任務都會遇到的問題——失敗之後怎麼辦，是要重試、要有公式退路，還是直接標記失敗；最後學會在 Trigger.dev dashboard 上讀一次 run 的 payload、logs 與歷次嘗試，把線上錯誤追回程式碼。走完之後，你不只知道這兩個 demo task 在做什麼，而是能用同一套模式，把任何長時又易失敗的工作安全地移出請求路徑。
