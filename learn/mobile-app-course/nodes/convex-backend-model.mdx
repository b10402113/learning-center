# Convex 後端模型

## Learning goal

用 Convex 建 schema / queries / mutations 與 reactive 查詢，理解它與自寫 API server 的差異。

## Steps

1. [[learn/mobile-app-course/nodes/convex-backend-model/convex-serverless-model|Convex 是什麼：把後端變成雲端上的函式]] — 建立 Convex 的心智模型：為什麼需要後端、`convex/` 放什麼、query 與 mutation 各做什麼（deep）
2. [[learn/mobile-app-course/nodes/convex-backend-model/define-schema-and-indexes|用 schema.ts 定義資料模型與索引]] — 讀懂 Convex schema：validator、索引、複合索引與 denormalized counter（after step 1, deep）
3. [[learn/mobile-app-course/nodes/convex-backend-model/write-queries-and-mutations|寫 query 與 mutation：從 posts.ts 走一次]] — 照 posts.ts 的模式實際寫出查資料與寫資料的函式（after steps 1–2, deep）
4. [[learn/mobile-app-course/nodes/convex-backend-model/reactive-queries-and-realtime|Reactive 查詢：為什麼不用手動重抓資料]] — 解釋前端訂閱、伺服器自動推送的即時機制（after step 3, deep）
5. [[learn/mobile-app-course/nodes/convex-backend-model/convex-vs-custom-api|Convex 或自寫 API server：怎麼選]] — 用取捨與判準決定下一個功能該用哪個後端模型（after steps 1–4, deep）

## Lesson

到目前為止，Codexgram 的畫面做得再漂亮，資料都還是假的：貼文、按讚、留言、私訊，全部寫死在程式裡。要讓這些功能真的動起來，就需要一個後端來存資料、跑邏輯、認身分。Convex 是 Codexgram 選用的後端，它跟你想像中的「寫一支 API server」很不一樣——沒有你自己開的 REST 端點，而是在一個 `convex/` 資料夾裡定義函式，由 Convex 幫你把函式部署上雲、生成型別，還順便讓每個查詢自動變成訂閱。

這個節點把 Convex 的後端模型一次講清楚。第一步先建立整體心智模型：為什麼這類功能非有後端不可、`npx convex dev` 之後 `convex/` 裡冒出哪些檔案、query 和 mutation 各自負責讀還是寫。第二步鑽進 `schema.ts`，看懂資料表、validator、索引與 denormalized counter 的設計。第三步是動手：照著 `posts.ts` 的模式，走一次「定義 args → 用索引查 → 在 server 端認身分 → 回傳 view → 寫入並清理」的流程。第四步解釋 Convex 最有感的一點——reactive 查詢，前端不必輪詢或手動重抓，資料一變畫面就變。最後一步回到取捨：什麼時候用 Convex、什麼時候該自己寫 API server，用一套判準幫你做決定。

走完之後，你不只會看懂 Codexgram 的 `convex/` 資料夾，也能把同樣的模式套到自己的 app：定義資料模型、寫查詢與寫入、讓介面自動跟著資料更新，並在選後端時說得出理由。
