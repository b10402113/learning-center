# Monorepo 與 Next.js 後端骨架

## Learning goal

把 repo 重構成 apps/mobile + web monorepo，用 Next.js 與 proxy 做路由保護。

## Steps

1. [[learn/mobile-app-course/nodes/monorepo-nextjs-backend/repo-shape-mobile-plus-web|Monorepo 的形狀：為什麼一個 repo 裝兩個 app]] — 說出 apps/mobile 與 apps/web 各自負責什麼、為什麼 web 是唯一部署（deep）
2. [[learn/mobile-app-course/nodes/monorepo-nextjs-backend/npm-workspaces-layout|用 npm workspaces 擺好 apps/mobile 與 apps/web]] — 把 Expo app 移進 apps/mobile、建立 apps/web，用根目錄 scripts 啟動（after step 1, deep）
3. [[learn/mobile-app-course/nodes/monorepo-nextjs-backend/nextjs-app-shell|Next.js App Router 外殼：一個部署，三種身分]] — 讀懂 layout / page / route handler 與 ClerkProvider 外殼（after step 1, deep）
4. [[learn/mobile-app-course/nodes/monorepo-nextjs-backend/proxy-attaches-auth-context|proxy.ts：讓每個請求都帶著身分]] — 解釋 clerkMiddleware 如何附掛 auth context、供 Expo 的 Bearer token 使用（after step 3, deep）
5. [[learn/mobile-app-course/nodes/monorepo-nextjs-backend/where-guards-live|路由保護要放在哪裡：matcher 還是資料旁邊]] — 用判準決定 guard 的位置，理解 Core 3 為何放棄 createRouteMatcher（after step 4, deep）

## Lesson

Dentify 這個專案有兩種使用者：手機上的病人，以及診所裡的員工。病人用 Expo 做的 App 預約看診，員工則要登入一個網頁後台看排班與病歷。這代表 repo 裡其實住著兩個獨立的應用程式，卻得共用同一份資料與同一套商業邏輯。這個節點要處理的就是這個「一個 repo、兩個 app」的形狀問題：怎麼擺放、怎麼啟動，以及負責當後端的那個 Next.js 專案要怎麼把門顧好。

第一步先建立整體認知：為什麼不是開兩個 repo，而是把 `apps/mobile` 與 `apps/web` 放進同一個 monorepo；`web` 為什麼同時是員工後台、手機 App 呼叫的 API、以及 Clerk webhook 的接收端，而商業邏輯為什麼一律留在 web。第二步動手：用 npm workspaces 把 Expo App 移進 `apps/mobile`、把 Next.js 專案放進 `apps/web`，並用根目錄的 scripts 一次啟動兩邊。第三步鑽進 Next.js 的 App Router，看懂 `layout.tsx`、`page.tsx`、`route.ts` 各自的角色，以及 root layout 為什麼要用 `ClerkProvider` 包住整棵樹。第四步解釋 `proxy.ts`——Next 16 對 `middleware.ts` 的改名——它如何在每個請求上附掛 Clerk 的身分脈絡，讓 API route 能讀到手機 App 帶來的 Bearer token。最後一步是抉擇：路由保護到底該寫在 proxy 的 matcher，還是寫在資料旁邊的 resource-based guard，用一套判準決定。

走完之後，你拿到的不只是 Dentify 的資料夾長什麼樣，而是一個可重複的後端骨架：一個 repo 放兩個 app、一個 Next.js 部署同時當網頁與 API、一道在正確位置把關的保護層，然後才在上面蓋預約、病歷與聊天這些功能。
