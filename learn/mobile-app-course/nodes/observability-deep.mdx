# 觀測深化：Logs / Tracing / Agent Tracing

## Learning goal

深入 Sentry logs / tracing / agent tracing 與 beforeSendLog 去識別化，並用 Expo Observe 看效能

## Steps

1. [[learn/mobile-app-course/nodes/observability-deep/logs-that-scale|結構化 log：讓五萬個使用者的問題查得到]] — 講清楚結構化 log 的組成，以及它為什麼要等使用者變多才顯出價值
2. [[learn/mobile-app-course/nodes/observability-deep/explore-logs-dashboard|在 Sentry Logs 視圖裡把問題圈出來]] — 用 severity、property 與多條件搜尋在 Explore Logs 篩資料、看尖峰、存查詢與匯出（after step 1）
3. [[learn/mobile-app-course/nodes/observability-deep/scrub-before-send|敏感資料該在哪一層被擋下]] — 在「寫入時去識別化」、「hook 攔截」、「關掉整類收集」之間做選擇（after step 1）
4. [[learn/mobile-app-course/nodes/observability-deep/agent-tracing|Agent tracing：看得見 AI 功能的成本與延遲]] — 用獨立 Sentry 專案追蹤 token、延遲與工具呼叫，同時不讓病歷外流（after step 3）
5. [[learn/mobile-app-course/nodes/observability-deep/measure-real-user-performance|用 Expo Observe 看上線後的效能]] — 量真實使用者的啟動、JS 載入與首屏時間，看出跨裝置的效能回歸（after step 2）

## Lesson

前一個 Sentry 節點建立的是「app 出錯時你知不知道」：錯誤會被抓下來、有 session replay、能進 Dashboard 判讀。但當 app 真的上線、開始有幾千幾萬個使用者之後，光靠「錯誤列表」會遇到兩個新極限。第一，錯誤只記錄「壞掉的那一刻」，卻說不出壞掉前發生了什麼——你需要的是可以回頭查、可以過濾的事件紀錄，也就是結構化 log。第二，當你的 app 開始呼叫 AI，最貴、最慢、最容易失控的那一段往往不是錯誤，而是那幾次 LLM 請求：你花了多少 token、等了幾秒、模型被餵了什麼、哪個工具被呼叫，這些都不會出現在錯誤列表裡。

這個節點把觀測往更深一層推。先講清楚結構化 log 的三個組成，以及為什麼只有事件量放大後，「可查詢」才會變成真正的救命繩；接著實際走一遍如何在 Explore Logs 裡用 severity、property 與多條件搜尋把問題圈出來，並把查詢存成監控。再來處理隱私：日誌送到雲端之前，敏感資料該在哪一層被擋下——是寫的時候就不記，還是靠 `beforeSendLog` / `beforeSend` 鉤子去識別化，或直接在 instrumentation 關掉整類收集。有了這層保護，才輪到 AI 功能的 agent tracing：用另一個 Sentry 專案追蹤 token 用量、延遲、工具呼叫與錯誤率。最後把視角拉回真實世界，用 Expo Observe 看數千台裝置上的啟動、JS 載入與首屏時間，理解為什麼「在我手機上跑很順」不代表上線後沒問題。
