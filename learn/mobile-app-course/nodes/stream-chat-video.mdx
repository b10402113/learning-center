# Stream 即時聊天與視訊

## Learning goal

用 Stream 建即時聊天與視訊通話（token endpoint、typing / 已讀 / 附件、通話控制）。

## Steps

1. [[learn/mobile-app-course/nodes/stream-chat-video/stream-identity-and-token|Stream 的身分與 token：為什麼 user id 只能由 server 決定]] — 建立 Stream 的身分模型：server 推導身分、Chat 與 Video 共用一個 token
2. [[learn/mobile-app-course/nodes/stream-chat-video/token-and-channel-endpoints|Token endpoint 與 channel endpoint：server wrapper 與短效憑證]] — 寫出發 token 與開對話的兩個端點與 server wrapper（after step 1）
3. [[learn/mobile-app-course/nodes/stream-chat-video/wire-stream-at-root|在 app root 接上兩個 client：一個 token、Chat 與 Video]] — 在 root 建立兩個 client 並加上逾時降級（after step 2）
4. [[learn/mobile-app-course/nodes/stream-chat-video/chat-inbox-and-conversation|訊息畫面：patient 的單一對話與 staff 的收件匣]] — 做出兩個角色共用的訊息 UI（after step 3）
5. [[learn/mobile-app-course/nodes/stream-chat-video/video-calls-and-ringing|視訊通話：排程 teleconsult 與即時 ring 的兩種入口]] — 分辨固定 call id 與一次性 ring，並接上通話控制（after step 3）

## Lesson

聊天和視訊聽起來是兩個功能，但在 Dentify 裡它們其實是同一套身分的兩種用法。這個節點要蓋的核心，是先把「誰能用這套即時服務」講清楚。Stream 是一個託管的聊天與視訊後端，我們不自己碰 WebRTC 或 socket，只負責在 server 端決定「這個人是誰」，然後發一張短效通行證給 app。

身分決定三件事：app 不能自己宣稱自己是誰、不能看到 API secret、而且 Chat 與 Video 共用同一個 Stream user id 與 token。這條界線一旦畫對，很多安全問題會自動消失，例如病人不可能偽造一張員工的 token 去讀整間診所的對話。

界線畫好之後，剩下的就是實作順序。先在 Next.js 後端寫出 token endpoint，並順便回傳這個病人該進的 clinic channel；再在 app root 用這張 token 建立 Chat 與 Video 兩個 client；最後才做訊息畫面與通話畫面。每一步都比前一步多一層，但都接在同一條主軸上：server 決定身分，client 只使用它。
