# 即時私訊

## Learning goal

建 conversations / messages / inbox 的即時私訊，含 optimistic send / retry 與未讀指示。

## Steps

1. [[learn/mobile-app-course/nodes/realtime-messaging/messaging-data-model|私訊的三張表：一對對話、訊息流與每人一份收件匣]] — 讀懂 conversations / messages / inbox 的職責與拆表理由
2. [[learn/mobile-app-course/nodes/realtime-messaging/conversation-start-and-access|開啟對話與存取守衛：start 與 requireConversation]] — 建立或重用唯一對話，並擋下非參與者（after step 1）
3. [[learn/mobile-app-course/nodes/realtime-messaging/server-side-send|伺服器端送出：用 sequence 排序、用 requestId 去重]] — 寫出可重試的 send mutation 與收件匣寫入（after step 2）
4. [[learn/mobile-app-course/nodes/realtime-messaging/optimistic-send-and-retry|樂觀送出與重試：pending outbox 與 requestId 對帳]] — 前端先顯示、再與後端訊息對帳（after step 3）
5. [[learn/mobile-app-course/nodes/realtime-messaging/unread-and-read-state|未讀與已讀：用 sequence 比對，而不是布林旗標]] — 未讀的推導與已讀回條的觸發時機（after step 3）

## Lesson

一對一私訊看起來只是「把訊息寫進資料庫、畫面顯示出來」，但真正難的地方在於：兩個人的裝置要幾乎同時看到同一段對話，送訊息的人不能因為網路重試而留下兩則重複訊息，收到的訊息還要知道「哪些我還沒讀」。這三個需求各自指向不同的資料，硬塞進同一張表就會互相拖累。

這個節點把私訊拆成三張表來解：對話本身只記一對參與者與目前的序號，訊息是一條只增不改的流水帳，而每個使用者的收件匣則是一份為了列表與未讀而存在的摘要。拆開之後，列表可以只讀摘要、歷史可以只讀訊息，未讀也能用兩個序號比大小算出來，不必掃描整條對話。

接著我們照著這個模型把功能做出來：先建立或重用唯一對話並守住存取權，再寫出可重複呼叫也不會重複寫入的送出流程，然後在前端用樂觀更新讓訊息「先出現、再對帳」，最後處理未讀與已讀回條。走完這五步，你會得到一個在真實裝置上即時同步、失敗能重試、且未讀狀態正確的私訊功能。
