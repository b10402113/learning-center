# 寫實 Seed 與後端測試

## Learning goal

冪等 seed 出寫實資料量，用 convex-test + vitest 測權限、不變量、分頁與清理。

## Steps

1. [[learn/mobile-app-course/nodes/seeding-and-backend-tests/why-realistic-seed|為什麼要寫實 Seed 與後端測試]] — 說清楚 seed 解決什麼問題、為什麼必須冪等且限定開發環境、demo 帳號與真帳號的界線（deep）
2. [[learn/mobile-app-course/nodes/seeding-and-backend-tests/build-idempotent-seeder|拆解冪等的寫實 Seeder]] — 用 seedKey、確定性 postPlan 與分批 action 實作可重複執行的 seeder（after step 1, deep）
3. [[learn/mobile-app-course/nodes/seeding-and-backend-tests/convex-test-harness|用 convex-test 與 vitest 建立測試]] — 用 convexTest 起記憶體後端，用 withIdentity、t.run、t.fetch 寫測試（after step 1, deep）
4. [[learn/mobile-app-course/nodes/seeding-and-backend-tests/test-permissions-and-invariants|測權限與不變量]] — 用匿名／不同身分抓越權，用重複呼叫驗證冪等、計數器與唯一性（after steps 2–3, deep）
5. [[learn/mobile-app-course/nodes/seeding-and-backend-tests/test-pagination-and-cleanup|測分頁、排程與清理]] — 驗證 cursor 分頁不重疊，並用 fake timers 確認排程清理清乾淨（after step 3, deep）

## Lesson

一個社交 app 最陰險的 bug，往往不是出現在你手動點得到的畫面上，而是出現在第 200 筆資料、第二個使用者、或某個沒被測到的權限路徑裡。這個節點處理兩個讓後端「站得住」的工具：一份寫實又冪等的 seed，以及一套跑在記憶體裡的後端測試。

Seed 的用意是讓畫面在還沒有真實使用者時，就能被真實的資料量檢驗。貼文少少的看不出排版會不會爆掉，追蹤清單只有兩三個人也測不出分頁。但 seed 一旦寫得不夠小心，就會變成更大的麻煩：重跑一次就多一批重複資料、計數器被加兩次、甚至不小心把假資料寫進正式環境。所以 seeder 的設計核心不是「塞資料」，而是**可重複執行**——用穩定的 `seedKey` 當身分證、用確定性的規則產生貼文、在寫入前先查是否已存在，並把整支 seeder 擋在開發環境之外。

測試則是把「我剛才有點到，看起來沒壞」升級成「任何人都可以重跑，且永遠會過」。用 `convex-test` 起一個記憶體後端，不需要真的連上資料庫，就能用不同身分呼叫 mutation、用假時間推進排程、斷言匿名使用者被擋、重複送出的留言只有一筆、刪文之後按讚與檔案真的消失。走完這五步，你不只會看懂 Codexgram 的 `convex/seed.ts` 與 `convex/social.test.ts`，也能為自己的 app 寫出一份重跑不會壞的 seed，和一套真的在測權限、不變量、分頁與清理的後端測試。
