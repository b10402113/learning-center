# EAS Build、真機與 TestFlight

## Learning goal

用 EAS 出 build 到真機 / TestFlight，理解 OTA 能與不能更新什麼，並用 build log 修配置

## Steps

1. [[learn/mobile-app-course/nodes/ship-to-testflight/why-real-device|從模擬器到真機：Expo、EAS、TestFlight 各在做什麼]] — 建立「寫完程式之後」那條流程的心智模型：誰負責建置、誰負責散布、誰是測試沙盒
2. [[learn/mobile-app-course/nodes/ship-to-testflight/eas-cloud-build|用 EAS 在雲端出 dev build：從 eas.json 到掃 QR 安裝]] — 產生 `eas.json`、註冊裝置、跑雲端 build、掃 QR 把 build 裝進 iPhone（after step 1）
3. [[learn/mobile-app-course/nodes/ship-to-testflight/connect-dev-server|讓真機上的 app 連上 Metro：dev server 與 tunnel]] — 啟動 dev server、必要時改用 `--tunnel`，把 URL 貼進 dev client（after step 2）
4. [[learn/mobile-app-course/nodes/ship-to-testflight/dev-build-vs-testflight|dev build、TestFlight 還是正式上架？]] — 依測試對象與用途，在 dev build、internal distribution 與 TestFlight 之間選擇（after steps 1–2）
5. [[learn/mobile-app-course/nodes/ship-to-testflight/ota-vs-native-rebuild|OTA 熱更新與 native rebuild 的界線]] — 用「有沒有動到 native」判斷改動能不能跳過重新送審（after step 4）
6. [[learn/mobile-app-course/nodes/ship-to-testflight/debug-eas-failures|build 失敗時：用 log 讓 AI 修配置]] — 找到失敗步驟、把 log 交給 AI、修好後重建（after step 2）

## Lesson

這門課前面都在「把 app 做出來」：設計畫面、接上 Clerk、串好資料庫與 API。這個節點處理的是另一個常見的斷點——程式在模擬器上跑得好好的，然後呢？模擬器有一個很舒服的假象：它跟你同一台 Mac、同一個網路、同一份原始碼，所以它永遠不會遇到真機才會遇到的問題。一旦要把 app 交給別人（同事、測試者、未來的自己）裝在手機上，你就得跨過「建置」與「散布」這兩道手續，而 Expo 生態系把這些原本很麻煩的事收斂成一條流程。

這條流程的角色分工是這樣：**Expo** 讓同一份程式碼同時跑 iOS 與 Android；**EAS（Expo Application Services）** 負責在雲端把你的專案編譯成可安裝的 build，也負責後續的散布與送審；**Apple Developer Program** 是送審與對外散布的入場券；而 **TestFlight** 是上架前的測試沙盒，讓你像已經上架一樣把 app 發給測試者。走完這個節點，你會實際用 EAS 在雲端出一份 development build、掃 QR 裝進自己的 iPhone，並搞清楚它跟之後的 TestFlight、正式上架差在哪裡。

節點的第二條主線是「更新」。app 上線之後，不是每個改動都值得重新送審：只改 JavaScript 與 UI 可以走 OTA（over-the-air）熱更新，但改到 native module 就一定要重新 build、重新送審。這條界線如果不清楚，你會白等好幾天的審核，或是以為更新推得出去、結果使用者根本沒收到。最後，雲端 build 一定會失敗，而失敗時最有效的除錯路徑不是通靈，是把完整的 build log 交給 AI，讓它讀出是哪一步、哪個配置壞掉，修完再重建。這個節點要建立的就是這套「出 build、裝真機、散布測試、選對更新方式、失敗會查」的完整循環。
