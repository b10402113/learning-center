# Next.js API Route Handlers

## Learning goal

寫 Route Handlers + route() 包裝 + requireAuth / requireStaff 守衛，給 mobile 一個有型別、受保護的 API

## Steps

1. [[learn/mobile-app-course/nodes/nextjs-api-handlers/route-handler-basics|手機要的 API：Next.js Route Handler 入門]] — 看懂 route 檔案與 HTTP method 的對應，以及手機為何要打 HTTP API
2. [[learn/mobile-app-course/nodes/nextjs-api-handlers/error-envelope-and-wrapper|route() 包裝與錯誤信封]] — 把例外統一轉成 JSON，讓每個 handler 只留商業邏輯（after step 1）
3. [[learn/mobile-app-course/nodes/nextjs-api-handlers/auth-and-ownership-guards|requireAuth 與守衛：身分只從 session 來]] — 用守衛確認身分、角色與資料擁有權（after step 1）
4. [[learn/mobile-app-course/nodes/nextjs-api-handlers/typed-request-boundary|Zod 請求邊界：不信任 client 傳來的欄位]] — 在入口驗證輸入，並由 server 推導關鍵欄位（after steps 1–2）
5. [[learn/mobile-app-course/nodes/nextjs-api-handlers/booking-endpoint-walkthrough|走一遍 POST /api/appointments]] — 把守衛、驗證、寫入與 409 串成一個完整的寫入 handler（after steps 2–4）

## Lesson

dashboard 的網頁可以用 Server Component 直接讀資料庫，但手機 app 不在同一個 server 裡，它只能透過 HTTP 講話。這一課要建的，就是手機唯一能碰到的入口：Next.js 的 Route Handlers。它是一組位在 `app/api` 底下的檔案，每個檔案用 `export const GET`、`POST`、`PATCH` 這類匯出對應一個 HTTP method，收進來的 `Request` 與送出去的 `Response` 都是標準 Web 物件。

真正讓這組 API「能用」的，不是把端點開出來，而是三個包住它的紀律。第一，`route()` 包裝把任何被丟出的錯誤收斂成一致的 JSON 信封，讓 handler 本體只剩下商業邏輯。第二，`requireAuth`、`requireStaff`、`requireOwnedPatient` 這組守衛把「你是誰、你能不能碰這筆資料」全部鎖在 server 端，身分只從 session 推導，絕不相信 client 傳來的欄位。第三，Zod 在 handler 入口當城門，驗掉不合法的輸入，並讓服務長度、通話 id 這類值一律由 server 決定。

走完這五步，你會得到一個有型別、受保護，而且能對手機給出穩定錯誤碼的 API；最後一步會把這些零件在同一支 `POST /api/appointments` 裡串起來，讓你看到它們在真實預約寫入時怎麼合作。
