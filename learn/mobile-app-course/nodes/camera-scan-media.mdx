# 拍照掃描與媒體上傳

## Learning goal

做出拍照 / 選圖 → 上傳 ImageKit → pending → 非同步分析 → 即時更新的完整功能。

## Steps

1. [[learn/mobile-app-course/nodes/camera-scan-media/scan-input-and-permissions|開相機與選圖：權限、拍照與相簿輸入]] — 讓拍照與相簿兩種輸入都能用，並處理權限被拒與分頁失焦
2. [[learn/mobile-app-course/nodes/camera-scan-media/imagekit-upload|照片進 ImageKit：server-side 上傳與尺寸策略]] — 把 base64 照片安全送進 ImageKit，並用檔名前綴與 transform 解決刪除與尺寸（after step 1）
3. [[learn/mobile-app-course/nodes/camera-scan-media/pending-then-analyze|先存 pending 再背景分析：非同步管線的狀態機]] — 照片先落成 analyzing 狀態，再由背景 task 把每個出口收斂到 completed / failed（after steps 1–2）
4. [[learn/mobile-app-course/nodes/camera-scan-media/realtime-vs-polling|訂閱還是輪詢：前端怎麼知道分析完成了？]] — 依「單一 run 還是整個列表」選擇 Realtime 訂閱或輪詢（after step 3）
5. [[learn/mobile-app-course/nodes/camera-scan-media/debug-and-verify|除錯與驗證：runs/logs、retry 與資料落地]] — 用 runs/logs 追失敗、分辨 retry、驗證資料真的寫回 DB（after steps 3–4）

## Lesson

這個節點把 Cal AI 的核心功能做成一條完整的非同步管線：使用者拍一張餐點照片或從相簿挑一張，照片上傳到 ImageKit 拿到一個網址，資料庫馬上新增一列狀態為 `analyzing` 的餐點，接著由 Trigger.dev 的背景 task 把照片送給視覺模型估算熱量與三大營養素，最後結果寫回那一列，掃描畫面透過 Realtime 訂閱即時顯示分析中、完成、或「這不是食物」三種結局。

它同時是前兩個節點的匯流口。`neon-drizzle-schema` 給你一張 `meals` 表與它的狀態 enum，`background-ai-jobs` 給你 Trigger.dev 的 task 與 retry 語意；這個節點要做的，是把相機輸入、媒體儲存、資料列生命週期、背景任務、即時更新這五塊接成一條線。真正難的地方不在任何單一 API，而在**每個零件的邊界**：權限該在 `app.json` 宣告還是在執行時請求、照片要以什麼形式跨網路、private key 該留在哪一側、狀態該在什麼時機從 `analyzing` 移開、前端要用訂閱還是輪詢。五步走完，你應該能對著自己的 app 重畫出這條流水線，並說出每個決策背後避免的是哪一種災難。
