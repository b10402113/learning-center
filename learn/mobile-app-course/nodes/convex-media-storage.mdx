# Convex 檔案儲存與上傳

## Learning goal

在 serverless 後端處理檔案儲存、/upload 與 /media HTTP actions、影片時長解析與尺寸限制

## Steps

1. [[learn/mobile-app-course/nodes/convex-media-storage/convex-storage-model|Convex 的檔案儲存：_storage 與 storageId]] — 認識 Convex 內建檔案儲存與 storageId 的角色
2. [[learn/mobile-app-course/nodes/convex-media-storage/two-phase-upload|兩階段上傳：pending → ready → published 的生命週期]] — 用 uploads 資料列追蹤一次上傳從開始到發佈（after step 1）
3. [[learn/mobile-app-course/nodes/convex-media-storage/media-validation-limits|媒體驗證該信誰？MIME、magic bytes 與尺寸限制]] — 決定驗證放在哪一側、各用途的限制值（after step 2）
4. [[learn/mobile-app-course/nodes/convex-media-storage/upload-http-action|實作 POST /upload：串流限流、時長解析與綁定]] — 寫出會串流、驗檔、解析時長並綁定的 HTTP action（after step 3）
5. [[learn/mobile-app-course/nodes/convex-media-storage/authenticated-media-reads|GET /media：授權讀取與 Range 串流]] — 用登入身分決定誰能讀，並支援影片分段讀取（after step 2）

## Lesson

在一般的後端，上傳檔案通常代表要在物件儲存（S3、ImageKit 之類）開一個 bucket、發一組簽章網址、再自己維護「哪個檔案屬於誰」。Convex 把這一段收進平台本身：它內建一個檔案儲存區 `_storage`，檔案本體跟資料庫文件分開存，文件裡只留下一個 `storageId` 當指標。這一課要處理的，就是如何在這套模型上把「上傳」與「讀取」做成安全、可追蹤的流程。

整條流程的核心是一個狀態機。使用者按下送出時，client 先用 `begin` 開一張 `uploads` 資料列，狀態是 `pending`，並帶著用途（post / avatar / story）與預期的寬高、時長；真正的二進位檔則透過 `/upload` 這個 HTTP action 送進來。HTTP action 像一個守門員：它不信任 client 宣稱的型別與大小，而是邊接收邊限流、用檔頭的 magic bytes 認出真正格式、必要時解析影片時長，通過之後才把 blob 存進 `_storage`，再以一個 internal mutation 把 `storageId` 綁回那張 `pending` 資料列，狀態變成 `ready`。最後發佈成貼文或頭像時，狀態才走到 `published`。沒走完的資料列會在一小時後過期，由排程清理連同檔案一起刪掉。

讀取端則回答了另一個問題：檔案存好了，誰能看？`/media` 維持「拿到 URL 不等於有權限」的原則，它先從請求的登入身分查出這個人，再確認這個 storageId 指向的內容確實允許他讀；影片這種大檔還支援 HTTP Range，讓播放器可以分段抓取，而不是一次下載整個檔案。走完這一課，你手上會有一套可重複的媒體管線，之後換成自己的 app 時，只要改用途與限制值就能沿用。
