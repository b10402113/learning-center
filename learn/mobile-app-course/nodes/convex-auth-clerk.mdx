# Convex × Clerk 身分驗證

## Learning goal

開 Clerk↔Convex 整合、用 auth.config 驗 JWT、在 server 端推導身分且不信 client 傳來的 identity

## Steps

1. [[learn/mobile-app-course/nodes/convex-auth-clerk/server-derived-identity|為什麼不能相信 client 傳來的 identity]] — 認清把 client 傳來的 userId 當身分為什麼會被偽造，身分只能由 server 從驗證過的 token 推導
2. [[learn/mobile-app-course/nodes/convex-auth-clerk/enable-clerk-convex-integration|開通 Clerk↔Convex 整合並寫 auth.config]] — 在 Clerk dashboard 開整合、設 issuer domain、寫出 `auth.config.ts`，讓 `getUserIdentity()` 不再回 null（after step 1）
3. [[learn/mobile-app-course/nodes/convex-auth-clerk/jwt-verification-and-identity|JWT 驗證與 identity 物件]] — 看懂 Convex 如何用 issuer 與 JWKS 驗 Clerk 的 JWT，並分辨 `subject` 與 `tokenIdentifier`（after step 2）
4. [[learn/mobile-app-course/nodes/convex-auth-clerk/identity-vs-profile-guards|requireIdentity 還是 requireProfile？]] — 依操作需不需要 app profile 選擇 guard，並處理三種拒絕條件（after step 3）
5. [[learn/mobile-app-course/nodes/convex-auth-clerk/guard-and-verify|把 guard 套進 query/mutation 並驗證]] — 在 server function 開頭套用 guard，用三種身分情境驗證授權真的生效（after step 4）

## Lesson

上一個節點把資料搬進 Convex，這一節要處理一個更根本的問題：server 要怎麼知道「現在講話的人」是誰？很多初學者會讓 client 在呼叫 mutation 時順手帶一個 `userId`，看起來很方便，但這等於把門禁卡交給訪客自己填——任何人都能填別人的號碼。正確的做法是：client 只帶一個由 Clerk 簽發的 token，Convex 用 `auth.config.ts` 宣告信任的 issuer，驗證通過後由 `ctx.auth.getUserIdentity()` 在 server 端把身分還原出來。身分有了，還要接回你自己的資料：`requireIdentity` 只保證「有人登入」，`requireProfile` 才保證「這個人有 app 內的 profile」。五步走完，你會有一條從 token 驗證到授權 guard 的完整鏈路，也就補上了「UI 驅動後端」時最容易被忽略的安全缺口。
