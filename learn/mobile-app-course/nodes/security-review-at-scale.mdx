# 大規模 PR 安全審查

## Learning goal

對上萬行初始 PR 做 CodeRabbit AI 審查，處理 injection / auth bypass / XSS / SSRF / CSRF 等級問題並合併。

## Steps

1. [[learn/mobile-app-course/nodes/security-review-at-scale/scale-breaks-manual-review|為什麼上萬行的 PR 不能靠人眼審]] — 判斷一份 PR 是否已大到人眼無法逐行審查，並理解為什麼需要結構化輸出
2. [[learn/mobile-app-course/nodes/security-review-at-scale/security-finding-taxonomy|CodeRabbit 安全掃描的七大類問題]] — 認出 injection、authz bypass、XSS、SSRF、CSRF、broken auth、misconfiguration 各防哪種攻擊（after step 1）
3. [[learn/mobile-app-course/nodes/security-review-at-scale/run-security-review-on-large-pr|在大型 PR 上跑安全審查]] — 把上萬行改動開成 PR，讓 CodeRabbit 產出安全清單與 Change Stack（after steps 1–2）
4. [[learn/mobile-app-course/nodes/security-review-at-scale/triage-findings-fix-or-keep|哪些 finding 該修、哪些該保留]] — 對每一則 AI finding 做判斷，決定修或保留，並批次分派（after step 3）
5. [[learn/mobile-app-course/nodes/security-review-at-scale/heal-and-merge-large-pr|修完、驗證、合併]] — 平行套用修復、二次 commit，驗證後合併回 master（after step 4）

## Lesson

前面「版控與 AI Code Review」教你的是功能層級的審查：一條小分支、一個 PR、一輪 CodeRabbit。到了這一步，情況完全不同——你手上是一個已經長成完整後端與 API 的初始 PR，改動動輒上萬行、橫跨數十個檔案。想在 10 分鐘內逐行看根本不可能，而這裡面埋的安全問題，正好是 injection、authorization bypass、XSS、SSRF、CSRF 這一類「能跑、測試也過，但可以被攻擊」的問題。

這個節點處理的就是這個落差：當「審查」的對象大到人眼放棄時，流程要怎麼設計才不會把危險直接合併進主分支。五步沿著一條線走：先建立「規模本身就是問題」的觀念，接著拿到一份安全問題的分類地圖，再實際跑一次大型 PR 的審查、讀懂它的輸出，然後在最關鍵的一步做判斷——AI 說的每一則都要修嗎——最後把修復套用、驗證、合併。

學完這一節，你得到的不只是一次審查的經驗，而是一套面對「AI 一次生成整個後端」時，仍能把關並安全落地的做法。
