# Neon + Drizzle 資料建模

## Learning goal

用 Neon Postgres + Drizzle 建模、migrate、seed，理解 schema 是 app 與 task 的共同真相。

## Steps

1. [[learn/mobile-app-course/nodes/neon-drizzle-schema/schema-as-source-of-truth|Schema 是共同真相：為什麼資料模型要用程式碼定義]] — 建立信念：schema 不是資料庫的附屬品，而是 app 與 task 共用的單一真相
2. [[learn/mobile-app-course/nodes/neon-drizzle-schema/model-users-and-meals|建 users 與 meals：欄位、關聯、索引與時間的設計]] — 讀懂兩張表，並說出每個設計決定解決什麼問題（after step 1）
3. [[learn/mobile-app-course/nodes/neon-drizzle-schema/connect-drizzle-to-neon|接上 Neon：Drizzle client 與 drizzle.config 的設定]] — 把 TypeScript schema 接到 Neon，讓 app 與 task 共用一個 db 物件（after steps 1–2）
4. [[learn/mobile-app-course/nodes/neon-drizzle-schema/run-drizzle-migrations|跑 migration：edit schema → generate → migrate]] — 走一次 generate/migrate 迴圈，讀懂產生的 SQL 與 meta 檔（after step 3）
5. [[learn/mobile-app-course/nodes/neon-drizzle-schema/seed-local-data|Seed 測試資料：可重複執行與時區正確的寫法]] — 用參數化查詢與正確的時區轉換灌入假資料（after step 4）

## Lesson

這個節點處理的是整個 app 的資料底盤。你在前面的節點裡看過 Clerk 如何把使用者同步進 Postgres，但那張 users 表究竟長什麼樣子、由誰定義、改了要怎麼套用到真正的資料庫？這一節把答案講清楚：資料模型不是「用資料庫工具點一點就好」的東西，而是用 TypeScript 寫成程式碼、放進 repo、被 app 與背景 task 一起 import 的 schema。Cal AI 用的是 Neon（雲端 Postgres）加上 Drizzle（TypeScript ORM），這個組合讓「資料長什麼樣子」這件事只剩一個定義來源。

五步分成三層。第一層是觀念：先建立「schema 是共同真相」的信念，再讀懂 users 與 meals 的實際欄位、關聯、索引與時間設計。第二層是連線與建表：把 Drizzle client 接到 Neon，然後跑一次 edit schema → generate → migrate 的迴圈，看 Drizzle 如何把 TypeScript 定義翻成 SQL，並用 meta 檔追蹤每次變更。第三層是灌資料：寫一個可以重複執行、用參數化查詢、且把使用者本地時間正確換成 UTC 的 seed 腳本，讓 app 一啟動就有假的但寫實的資料可看。走完之後，你手上會有一套能重複套到自己專案的資料層工作流，而不只是看懂某個 demo 的檔案。
