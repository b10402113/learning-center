# Sentry 錯誤監控

## Learning goal

接 Sentry 抓真實錯誤與結構化 logs、session replay、tracing，並做測試頁與使用者回饋

## Steps

1. [[learn/mobile-app-course/nodes/sentry-monitoring/why-monitoring-matters|為什麼上線後一定要有錯誤監控]] — 用「watchtower」心智模型說明 Sentry 的五個能力，以及 console.log 為什麼不夠
2. [[learn/mobile-app-course/nodes/sentry-monitoring/install-and-configure-sentry|安裝並設定 Sentry：DSN、source map 與 native rebuild]] — 建專案、放 DSN、設 org token 上傳 source map、重建 dev build（after step 1）
3. [[learn/mobile-app-course/nodes/sentry-monitoring/verify-and-triage-errors|用測試頁驗證並在 Dashboard 判讀錯誤]] — 刻意丟錯、看 replay、讀 Issue 細節，最後拆掉測試頁（after step 2）
4. [[learn/mobile-app-course/nodes/sentry-monitoring/structured-logs-vs-console|Sentry logs 與 console.log：什麼時候用哪個]] — 用 log level 與 tag 把 log 變成可查詢的證據（after step 2）
5. [[learn/mobile-app-course/nodes/sentry-monitoring/performance-tracing|用 tracing 找出慢在哪一段]] — 一張 request 拆成 span，看出哪一段拖慢整體（after step 2）
6. [[learn/mobile-app-course/nodes/sentry-monitoring/user-feedback-widget|把使用者回饋接進 Sentry]] — 加 feedback widget，讓使用者直接從 app 內回報問題（after step 3）

## Lesson

Sentry 要解的問題不是「程式會不會出錯」，而是「出錯時你知不知道」。app 一旦離開你的電腦，使用者遇到當掉、畫面卡住、餐點分析失敗，絕大多數不會寫信給你，而是直接刪掉、留一顆星。這個節點把 Sentry 當成 app 的瞭望塔（watchtower）接進專案：先建立「為什麼要監控」的心智模型，再實際安裝 SDK、設定 DSN 與 source map、重建 dev build，接著用一個刻意丟錯的測試頁驗證整條管線，並學會在 Dashboard 上判讀錯誤、session replay 與 breadcrumbs。等錯誤抓得到之後，再把觀測往上加一層——用結構化 logs 記錄「發生了什麼」、用 tracing 記錄「花了多久」，最後接上使用者回饋。走完之後，你的 app 從「本機能跑」變成「上線後你看得見它怎麼壞、壞在哪、誰遇到」。
