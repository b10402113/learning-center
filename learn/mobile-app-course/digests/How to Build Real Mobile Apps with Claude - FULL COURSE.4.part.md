## Sections (L2)

### Finishing the Clerk-to-Postgres user sync and committing

- Locator: `[[sources/mobile-app-course/20261001/How to Build Real Mobile Apps with Claude - FULL COURSE.srt]]`
- Summary: Sets the trigger.dev secret key under its environment variable, kills and reruns the Expo project, deletes the test user, and signs in again so the `user.created` event fires; observes the run in the trigger.dev dashboard, confirms the new user appears in both the Clerk dashboard and the Postgres database, notes Trigger.dev will rerun a failed method, then recaps webhooks and commits.
- Key claims: The `user.created` event only fires on a genuinely new user, so the account must be deleted before re-testing; Trigger.dev retries a failed run automatically; webhooks are a transferable concept usable in any future project.
- Learner-relevant: A complete end-to-end verification habit for event-driven sync (delete → recreate → check both stores) and the reusable webhook mental model.

### Designing the home, profile, and scan screens with Expo native tabs

- Locator: `[[sources/mobile-app-course/20261001/How to Build Real Mobile Apps with Claude - FULL COURSE.srt]]`
- Summary: Takes a reference UI screenshot (from Cali) and explains the desired three tabs — home, profile, and a camera/scan screen — to Claude, explicitly requesting Expo native tabs to get the iOS liquid-glass effect out of the box. - Key claims: Expo native tabs provide the liquid-glass effect without extra work; the plan is not to copy the reference 100% but to stay close and get inspired; adding a native module requires a full native rebuild, not just a JS reload; when unsure, point the agent at `plan.md` rather than letting it guess.

### Fixing the sheet overlay and generating the plan with OpenAI

- Locator: `[[sources/mobile-app-course/20261001/How to Build Real Mobile Apps with Claude - FULL COURSE.srt]]`
- Summary: Notices the streak sheet's dark overlay slides in and should fade, has Claude change the animation type, then diagnoses that the displayed calories/protein/carbs/fat are hardcoded and the DB profile columns (gender, DOB, height, weight) are empty. Adds an OpenAI API key to the env file (notes Gemini/Google is a free alternative) and prompts Claude to send onboarding data to OpenAI, save the returned values to the database, and display them; reviews the `generate-plan` task using the Trigger.dev `task` API and a GPT model with a registered-dietitian/system prompt and schema.
- Key claims: Plan values must be generated by an LLM from onboarding data, not hardcoded; the generative work runs as a Trigger.dev background task; OpenAI is interchangeable with Gemini/other providers here.
- Learner-relevant: The pattern of persisting AI-generated values server-side, plus reading the actual task code (SDK import, task wrapper, prompt, schema) before trusting the output.

### Gating onboarding and debugging the missing secret / database values

- Locator: `[[sources/mobile-app-course/20261001/How to Build Real Mobile Apps with Claude - FULL COURSE.srt]]`
- Summary: Prompts Claude so any user who signs in without completing onboarding is still routed through it, manually walks the onboarding flow, and hits a failure when saving the user — traced to a missing/incorrect Clerk secret key. Re-copies the Clerk Node/Express quick-start values into the env file, kills and reruns the app, repeats onboarding, watches the `generate-plan` run complete in the dashboard, and confirms the generated calories (~3,740) and other profile values are saved to the database and shown in the UI.
- Key claims: Onboarding must be a hard gate regardless of how the user arrived; a missing environment variable silently breaks the save; real-world development is a loop of errors you fix, not a straight path.
- Learner-relevant: The debugging method — read the terminal error, identify the missing env value, fix and rerun — and the reminder that login-without-onboarding is a real edge case to handle.

### Building the scan screen and the asynchronous meal-analysis pipeline

- Locator: `[[sources/mobile-app-course/20261001/How to Build Real Mobile Apps with Claude - FULL COURSE.srt]]`
- Summary: Sketches the scan workflow before prompting Claude: user photographs a meal → API route uploads the image to ImageKit → meal is saved to Postgres with a `pending` state → a Trigger.dev task sends the image to OpenAI to analyze calories/protein/macros → the database row is updated and the UI reflects progress via Trigger.dev realtime. Adds camera permission through the Expo camera plugin in `app.json` (with a user-facing rationale string), explains `useCameraPermission`/`requestPermission` and the `useCameraPermission` hook, copies ImageKit public/secret keys and URL endpoint into the env file, and reviews the generated camera UI, the meals API endpoint (ImageKit upload + create analyzing row + return public access token), and the `analyze-meal` task (nutritionist prompt). Testing in the simulator reveals delay/retake bugs and a missing database URL env var for the task.
- Key claims: Camera access requires a declared permission with explanatory copy or it will not work; the meal row is created as `pending` before analysis finishes; the ImageKit upload, the Trigger.dev task, and the realtime channel are separate pieces wired by the API route; a missing `DATABASE_URL` in the task environment breaks the background job.
- Learner-relevant: A full async AI pipeline (upload → pending record → background vision task → realtime UI update) and the concrete permission + env setup needed to run it.
