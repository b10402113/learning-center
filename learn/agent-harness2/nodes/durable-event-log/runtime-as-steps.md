# 把 runtime 變成 step

上一篇文章最後留下了兩個實際問題：runtime 的範圍該怎麼界定，DBOS 才知道哪些內容算是一個 step？又該如何讓 DBOS 連上 Postgres？

這篇文章會回答這兩個問題：先談如何界定 step，再談資料庫連線。

## 不需要重寫 runtime

「持久化」聽起來好像需要做很多事，但實際上的改動比這個詞暗示的少得多。我們只要把現有的 runtime 拆成一個個 step，並將每個 step 的輸入和輸出記錄在資料庫裡。

![第 1 段配圖](./runtime-as-steps-assets/image-1.webp)

Agent 的行為完全不變。改變的是，step 的參數和執行結果會儲存在一個不會隨著程序結束而消失的地方。

負責記錄這些資料的就是 DBOS。它提供由 Postgres 支援的持久化 workflow，並追蹤你所建立的 workflow 中，每個 step 的輸入與輸出。

有了這些紀錄，重播就不必付出太多成本。需要重播時，DBOS 會檢查哪些工作已經完成，讓程序即使當機並重新啟動，也能從中斷的地方繼續執行。

## Workflow ID 能帶來什麼

以下是 Moss 用自己的話描述的流程。假設某件事失敗了，你可以重試；但這次不必盲目地從頭開始，而是先查看各個 step 的執行結果。

你會問：「這個 workflow ID 之前做過這件事了嗎？」如果答案是「有」，就跳過它。

![第 2 段配圖](./runtime-as-steps-assets/image-2.webp)

因此，workflow ID 就是某一次執行的識別碼；每個 step 記錄下來的輸入與輸出，則能證明這次執行進行到了哪裡。重試時，DBOS 不會重新執行已完成的工作，而是讀取先前的結果。

省下來的不是資料庫寫入，而是模型呼叫、工具呼叫，以及原本不必再寄一次的電子郵件。

## 冪等性仍然要由你負責

DBOS 可以告訴你某個 step 已經執行過，但無法確保這個 step 重複執行時仍然安全。

Moss 說得很明確：確保這些 step 具備冪等性，是我們自己的責任。也就是說，即使 step 再執行一次，也應該得到相同的結果。

這是一般分散式運算的原則，不是 DBOS 特有的規定。你需要設計出具備冪等性的動作。

回想上一篇文章中的 `sendReply`。如果這個 step 的效果是「寄出這封電子郵件」，那麼當機後重試，就會再寄一次。如果它的效果是「除非訊息 42 已標記為已寄出，否則寄出這封電子郵件」，那麼重試就不會造成額外影響。

## 另一種值得儲存的資料

workflow 的持久化並不是全部。我們也會保留一份事件紀錄，記下所有觸發的事件。

這份紀錄會依照發生順序，保存 Agent 做過的事。它同樣存放在 Postgres，但和 step 的檢查點分開。

先記住這個差別：檢查點會告訴 runtime 哪些工作已經完成；事件紀錄則會告訴人，或重新連線的用戶端，發生過什麼事。本文會先建立前者；接下來兩篇文章則會處理後者。

## 設定資料庫連線

首先要安裝三個相依套件：DBOS SDK、Drizzle，以及 Postgres 用戶端。

Drizzle 是一個 ORM，不需要為了這篇文章特地學會它。把它當成用來和資料庫溝通的 SDK 就可以了；這裡只會用到這個功能。

接著，在 harness 資料夾中新增一個檔案 `db.ts`。這個檔案很短：從 `drizzle-orm/postgres-js` 匯入 Drizzle，並匯入旁邊的 Postgres 用戶端。

資料庫方面，你需要一個 Postgres。使用你已經在用的本機資料庫也沒問題。

如果你沒有 Postgres，課程也提供了一個臨時選項。只要在瀏覽器中打開它，就能取得一組 URL，連線到一個可免費使用 72 小時的資料庫。不需要帳號或其他設定，只要複製那串字元即可。

把這串字元加到 `.dev.vars` 或 `.env`，並將變數名稱設為 `DATABASE_URL`。

貼上之前還要做一個修改。如果你的 Neon URL 含有 `-pooler`，請刪掉這一段。連線池會讓 DBOS 的設定變得更複雜，而我們在本機開發時並不需要它。移除 `-pooler` 後，就會改用同一個資料庫的非連線池版本。

![第 4 段配圖](./runtime-as-steps-assets/image-4.webp)
