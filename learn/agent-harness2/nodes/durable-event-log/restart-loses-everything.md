# 重啟之後，完全不知道發生什麼

## 前言

使用者才回覆到一半，Wi-Fi 就斷了。等他重新連線後，agent 卻完全不知道自己剛才在做什麼。這正是這一節要修復的第一個問題。

每當伺服器重新啟動、用戶端斷線，或程序在一輪處理到一半時停止，你都可能遇到這種情況。若沒有適當的機制，已經完成的工作就會這樣消失。

修復這個問題分成四個步驟。這篇文章會先介紹幾個相關用語——durable execution、checkpoint、replay 和 idempotency——並說明訊息只存在記憶體中會造成什麼問題。第二篇會把 runtime 拆分成 workflow steps，並連接 Postgres。第三篇會定義一個帶有 `seq` 欄位的 `event_log` 資料表。第四篇會改寫 `emit`、`subscribe` 和 `history`，讓事件在通知任何人之前，先寫入資料庫。

這篇要回答的問題是：程序在處理到一半時停止，我們會失去什麼？要恢復執行，又必須先滿足哪些條件？

## 用戶端應該期待什麼

Scott Moss 一開始便指出這一節要處理的核心情況：程序執行到一半時，伺服器或用戶端突然斷線。

想像你正在和 ChatGPT 聊天，看著它思考，這時 Wi-Fi 突然斷了。重新連線後，應該發生什麼事？

你應該能接續原本的對話，而不是從頭開始，也不是只收到一句道歉。

Moss 一語道破：無論你看不看得到，session 都應該持續存在。反過來也一樣。如果模型供應商的伺服器停機後又恢復，你也會期待能繼續原本的工作。

![第 1 段配圖](./restart-loses-everything-assets/image-1.webp)

要做到這點，就需要 checkpointing。系統必須記錄已完成的工作，才能分辨哪些工作「尚未完成」，哪些則是「你沒在看的時候已經完成」。

這一切都歸在同一個概念之下：durable execution。也就是讓執行中的工作具備持久性、韌性與容錯能力。

## 這是分散式系統問題

要實現 durable execution，就會碰上分散式運算：不同系統在不同程序中執行，彼此之間還需要互相配合。

對沒有做過後端工作的人，Moss 以 CI/CD 為例。你推送一個 commit，另一台機器上的獨立程序就會執行檢查——可能使用 Jenkins、GitHub Actions，或其他工具——再把狀態回報給 GitHub。

這條 pipeline 包含多個階段，每個階段都可以重試、重播，也可以部分使用快取。某個階段失敗時，你只要重跑該階段，不必重新執行前面已經通過的五個階段。

pipeline 執行期間，GitHub 上的狀態會持續更新，不論有沒有人正在查看頁面。即使 CI 系統本身停機，設計完善的系統也能在恢復後，從中斷處接續執行。

CI/CD 就是分散式運算，而且早已具備處理這些情況的能力。我們的 agent 也必須採用同樣的設計：執行不能依賴任何消費端或用戶端，還必須能承受程序終止與錯誤。

## 我們的 agent 會在哪裡出問題

接著來看 harness 中的具體問題。有人問：如果我們透過 WebSocket 發出事件，卻沒有人接收，會發生什麼事？

以目前的實作來說，答案很直接：我們只會把事件串流傳送給用戶端。目前的 agent 完全沒有持久化層。下游出問題時，事件就會遺失，不會留在任何地方。

從另一個角度來看，根本原因也相同：所有訊息都只存在記憶體裡。一旦重新啟動，agent 就完全不知道剛才發生了什麼事。

![第 3 段配圖](./restart-loses-everything-assets/image-3.webp)

沒有任何資料可以讀回來。使用者原本正在進行的對話，只是存在於一個已經不存在的程序中的物件。

修復方式可以用一句話概括：我們得把這些訊息存起來，之後才能重播並從中斷處接續執行，即使中間發生故障也一樣。

## 會造成破壞的動作需要 idempotency

光有持久化還不夠。Moss 舉了一個執行到一半發生錯誤的例子：`sendReply` 執行時發生錯誤。郵件到底有沒有寄出去？沒人知道，所以你再試一次，結果郵件就寄了兩次。

銀行轉帳也會遇到同樣的問題。轉帳執行到一半失敗，你重新執行一次，結果錢就被轉了兩次。

這比訊息遺失更麻煩，因為你沒辦法把事情復原。你不能收回已寄出的電子郵件，也不能在收件者打開郵件之前，伸手進他的收件匣把信拿回來。

![第 4 段配圖](./restart-loses-everything-assets/image-4.webp)

因此，這類動作必須具備 idempotency：即使重試多次，效果也不會重複產生。它應該用來保護副作用，而不是用來保護一份狀態副本。重試時，系統會確認這個效果已經記錄下來，因此不會再次執行。

## 為什麼選 DBOS

我們打算加入以 Postgres 為基礎的持久化儲存機制，使用的工具是 DBOS。

DBOS 提供以 Postgres 為基礎的持久化 workflow，並會保存每個步驟的輸入和輸出。需要重播時，DBOS 會檢查先前已完成哪些工作，讓程序即使當機、重新啟動，也能從中斷處接續執行。

Moss 稱它為資料庫骨幹，這正是重點所在。多數同類工具都是付費服務。Cloudflare 有一套，Inngest 是另一套，Upstash Workflows 也是，Vercel 現在也推出了 Vercel Workflows。規模最大的則是 Temporal。這些工具提供的都是 durable execution。

DBOS 的差異在於需要執行哪些元件，以及需要修改哪些程式碼。它以資料庫為基礎，因此不必另外維運一個服務，也不需要讓 Docker container 持續運作。而且採用它幾乎不必改動原有程式碼。

接下來要處理的是實作上的問題：要怎麼界定 runtime 的範圍，讓 DBOS 知道哪些內容算是一個步驟？又該如何先讓它連上 Postgres instance？
