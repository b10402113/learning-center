# Context 一直長大，模型就越笨

你的客服 Agent 從星期一開始，就一直在同一段對話裡工作。每次互動都會多留下一則訊息。到了星期四，送出的請求裡已經塞了幾百輪對話。

你問 Agent，客戶一開始想要什麼，它卻回答成兩輪前的內容。程式碼一行都沒改，變的是 Context：它越長越大。

## 三個問題一起出現

Context 太長，模型會變得更不聰明、更慢，也更花錢。這三種狀況會在同一個請求裡一起發生。

變慢和變貴，原因相同：每次呼叫模型時，執行框架都會把整段對話重新送一次。提示快取能降低費用，卻無法省掉重新傳送的時間。

<!--image:1-->

模型變笨，則是另一個原因。它比較容易注意到 Context 開頭和結尾的內容。

夾在中間的資訊，幾乎就像被忘掉了一樣。你一小時前貼上的退款政策，現在已經落在 Context 中段，最後可能根本沒影響模型的回答。

## 更大的 Context 視窗也救不了

現在市面上已經有百萬 Token 的 Context 視窗，但這無法改善問題。

Context 更多，不代表答案更好。實際上，中間那一大段只會變得更長，回答反而更差。

<!--image:2-->

所以，別把 Context 視窗當成倉庫。它應該只放模型回答這一輪所需的最少文字。

## 然後，系統就會停止運作

Context 持續變長，終究會碰上硬上限。請求一旦超出視窗容量，就會收到錯誤。

只要舊文字永遠不移除，任何對話式 AI App 最後都會出問題。這種故障不是偶發，而是遲早會發生。

## 你看到的，不等於模型看到的

畫面上會顯示你傳過的每一則訊息，但模型實際看到的，只有其中一部分。

你的 App 可能會自動壓縮內容，也可能由按鈕啟動壓縮；或者在背景用摘要取代一整段對話。這些變化不一定看得出來。

完整的對話紀錄，和單次呼叫模型時使用的 Context，是兩種不同的東西。這個節點會把它們分開處理。

<!--image:3-->

## 這個節點新增了什麼

執行框架原本就有一份可長期保存的事件紀錄，那就是對話歷史。它會隨時間膨脹，最後超出任何 Context 視窗的容量。

因此，我們新增兩個部分：當歷史紀錄超過 Token 預算時，由壓縮器縮短內容；接著由組裝器在呼叫模型前，整理出這一輪所需的 Context。

這裡的壓縮器刻意把 Token 上限設得很低，這樣你很快就能看到它啟動，不必等上一週。

在縮短內容之前，我們得先弄清楚要縮短哪些資料，以及要組裝哪些內容。接下來，我們會把歷史紀錄、狀態和 Context 拆成三個不同的東西。
