# 先開 plan mode，再談 sub-agent

如果你用過 Claude Code 或 Cursor，其實早就用過 sub-agent 了，只是你可能沒這樣稱呼它。

sub-agent 就像一名被臨時找來的助理：你把一小部分工作交給它，讓它獨立完成，再把結果交回負責統籌的主代理人。真正關鍵的是，判斷什麼時候值得這樣做。

<!--image:1-->

寫程式是最容易理解的情境。搭配 Git worktree，你可以把多個 agent 分派到不同任務，並為每個 agent 建立一份獨立的程式碼副本。這樣它們就能各自工作，不會互相踩到內容。不過，這只有在任務之間有清楚的分界時才有效，否則最後還是可能互相衝突。

研究則是另一種情況。你可以讓一個 agent 查這裡、一個查那裡，另一個再去找其他資料，最後把所有結果整合成一份答案。這不只是速度上的優勢，也能減輕上下文負擔：單一 agent 可能容納不了這麼多資訊，但它可以讀懂所有研究結果的摘要。

<!--image:2-->

但這套做法也可能失控。想像一下，sub-agent 各自埋頭工作，永遠不回來，還在暗中向某個主管報告。Scott Moss 認為這種情況很可怕；他說，大概只要過五分鐘，幻覺就會開始出現，「就像它們嗑了 LSD 之類的東西。」

所以，sub-agent 確實很有用，也值得理解背後的架構。負責任的做法，不是讓 agent 臨時決定要不要建立 sub-agent，而是先做好規劃。

這就是 plan mode 登場的地方。計畫應該是一個正式存在的產物，而不是只暫時留在對話串裡的東西。它會先被建立、儲存到某個位置，接著由一群 sub-agent 負責執行，並由一個 supervisor 統籌整個計畫。

<!--image:3-->

啟用方式和多數 agent 差不多：打開 plan mode，或使用斜線指令。這樣一來，agent 就不必自行判斷什麼時候需要 sub-agent，因為你已經事先告訴它了。

讓 agent 自己做這個決定，是下一個階段的問題，而且需要搭配 evals，也就是用來評估表現的測試。這部分不在本課程的範圍內。

因此，計畫就是其他一切工作的支點。接下來要問的是：這份計畫在程式碼裡究竟長什麼樣子？既然它是一個已儲存的產物，就需要有一種可以拿來檢查的結構；而我們接下來就會從這個結構開始建立。
