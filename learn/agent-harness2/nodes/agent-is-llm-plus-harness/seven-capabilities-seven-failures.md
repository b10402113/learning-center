# 七個能力，七種 production 故障

上一篇文章的結尾做出了一個承諾：這門課會打造一個 runtime，並介紹它新增的各項能力。本文將兌現這個承諾，逐一說明每項能力，以及它能修復的故障。

## 七種模式，一次看一種

課程的 repository 列出了七堂課。這種安排不太尋常，README 也特別說明了原因：每堂課都會介紹一種新的架構模式，接著示範如何用 TypeScript 和 Node.js 實作，然後就進入下一堂課。

這不是一個會在一整天裡逐步擴大的大型專案。真正逐步擴大的是 runtime。

不妨把這份清單看成一組組配對：每種模式都能修復一種特定故障。

## Harness 本身：context、工具與護欄

第一種模式是其他六種模式的基礎。README 將它稱為一層 middleware，負責提供 LLM 所需的 context、工具與護欄。

這就是上一篇文章提到的問題：缺少 context、工具和護欄的模型，只是一個 LLM 呼叫。它無法接觸任何東西，也沒有人能限制它的行為。

Moss 對這門課的 agent 設計說得很直接：課程的重點不是 agent。agent「基本上就是個無聊的 agent」，有些情況下用的還是模擬工具。他認為 agent 本身沒什麼值得深入探討的。真正讓 agent 變得可靠、值得信賴又聰明的，是 harness。

## Process 中途終止時：持久化執行

第二種模式是持久化執行。它會為 agent 的每個步驟建立 checkpoint，讓程式崩潰或遇到 rate limit 時，能從中斷處繼續執行。

它要修復的是分頁關閉、process 終止這類問題。十分鐘的研究任務不會自動撐過重新啟動；執行到一半遇上 rate limit，也不會等你回來後再繼續。

## 模型寫出程式碼時：安全沙箱

第三種模式是安全沙箱。它會把不受信任、由 agent 產生的程式碼放進隔離的 runtime 執行，並設定逾時時間。

它要修復的是模型寫出程式碼，卻沒有人限制程式碼能做什麼的問題。課程的示範展示了這項工具的實際操作。它叫做 Run Code，功能就如同名稱所示。

agent 會先寫程式碼，再執行程式碼。Moss 說明了這麼做的原因：遇到算術問題時，寫程式碼比使用內建工具反覆嘗試、直到 token 耗盡更有效率，也能幫助 agent 做出準確判斷。agent 會在沙箱中安全地執行程式碼，最後再把 context 合併回來。

## Context 錯誤或太大時：進階記憶

第四種模式是進階記憶。它會透過 state store、滑動視窗和摘要，載入正確的 context。

它要修復的是 context window 塞滿，或是裡面放了不相關內容的問題。示範中的 agent 一交接工作，需要把所有內容重新整合成一個答案時，就立刻遇上這個問題。

Moss 也不允許你跳過記憶這個模式。在課程最後的問答環節，有人問他：要打造一個面向使用者的聊天 agent，最精簡的技術堆疊是什麼？他的回答是：工具呼叫、記憶，以及記憶壓縮。這三者之中，他認為記憶壓縮「百分之百必要」。

## 不該讓一個 agent 包辦所有事時：交接與監督

第五種模式是協調。它會判斷意圖，並在分類 agent 和專家 agent 之間交接 context。

它要修復的是只有一個 agent、一組不分層的工具，以及一種固定性格的問題。示範展示了解法：agent 會使用工具判斷任務類型，再把任務交給更擅長處理的 agent。Moss 稱這個過程為 handoff。

第六種模式是階層式監督。監督者會規劃工作、啟動多個平行執行的子 agent，再合併它們的結果。

這種模式要修復的是只靠一個「頭腦」制定計畫的問題。示範中有一種 supervise 模式，會啟動一群各有不同 persona 的子 agent，讓它們共同制定計畫，並決定下一步該做什麼。Moss 說，這就像先請 code model 擬出計畫。

## 行動需要人來核准時：人在迴圈中

第七種模式是人在迴圈中。它運用持久化的暫停與恢復機制，等待人類核准；等待時間可能是幾分鐘，也可能是幾天。

它要修復的是上一篇文章提到的交易 agent 問題。花錢這類不可逆的行動，不能只憑 agent 自己的判斷就執行。由於等待時間可能很長，因此不能只把暫停狀態留在記憶體裡。這就是為什麼這種模式需要持久化的暫停機制，而不是等逾時後重試。

## 為什麼七種模式共用一個 runtime

七種模式聽起來像是七種產品，但課程把它們放在同一個地方。專案的設定清楚指出了這個地方：runtime 檔案是 harness 的核心，也是 agent 執行的所在。

Moss 把它比喻成遊戲：打造遊戲時，你會有遊戲迴圈；在這裡，你則會有 agent 迴圈。

<!--image:3-->

一開始，這個檔案幾乎什麼也沒做，這是刻意安排的。檔案裡大多是尚未實作的空殼，而你接下來一整天都會在這裡工作。你會看到 `emit` 呼叫出現在各處。Emit 的意思是：把某件事剛剛發生的訊息傳給想知道的人。

傳輸方式也說明了 runtime 為什麼採用這種設計。agent 是一個分散式的持久化執行層，因此 harness 必須能連上任何已連線的 client。Moss 選擇 WebSocket，是因為他需要雙向通訊、不必等待回應的傳送方式，以及接收回傳事件的能力。大多數 agent 則使用 SSE：送出請求後等待回應。

## 可以依序推出的功能

課程最後一場問答中的另一個回答也值得記下來。有人問最精簡的技術堆疊是什麼，Moss 並沒有把持久化執行列為第一項。

工具呼叫幾乎不用額外付出成本，而且每個 SDK 都有，因此不需要自己打造。記憶的成本也很低，但要把它存放在自己能掌控的地方，例如自己的資料庫；這門課就是這麼做的。至於記憶壓縮，則不能省略。

這些功能足以打造一個聊天 agent。接下來才是持久化執行，因為串流過程中一旦重新載入頁面，執行就會中斷。使用 SSE 時，重新整理頁面會讓 token 消失。Moss 認為，一開始遇上這種情況也沒關係。之後你會需要的是一個不依賴 client 的 agent。

## 這個系列的主張

回頭看看這三篇文章。同一個模型可能產生截然不同的結果，因為 harness 決定了模型能做什麼。更好的 harness 可以勝過更好的模型。而且，沒有 harness，就無法打造出使用者離開後仍能繼續執行的系統。

七種模式具體呈現了這個主張。每種模式都能排除一種會讓 harness 故障的情況，而它們全都位於同一個 runtime 中，隨著課程一堂接一堂逐步實作。
