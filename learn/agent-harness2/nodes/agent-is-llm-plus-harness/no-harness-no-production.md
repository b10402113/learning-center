# 沒有 harness，就上不了 production

上一篇文章探討了為什麼能在 notebook 裡執行的 demo，到了 production 卻可能失敗。要回答這個問題，Scott Moss 沒有先列出一串功能，而是先談起你想為使用者打造的體驗。

## Harness 要配合使用者體驗

Moss 說，harness 取決於你想為使用者提供什麼樣的體驗。必須先確定這一點，才能決定需要哪些元件。

<!--image:1-->

並非每個 agent 都是聊天型 agent。有些 agent 會接下任務，在背景持續處理；沒有人盯著它，也沒有人會輸入後續訊息。光是這個差異，就會改變 harness 必須負責的工作。

## 案例一：即使使用者關閉分頁，深度研究仍要繼續

第一個案例來自上一篇文章，值得仔細看看。深度研究 agent 大約需要 10 分鐘才能完成任務，但使用者卻關閉了 app。

即使如此，仍有三件事必須成立：agent 要繼續工作；使用者回來時，畫面要顯示研究仍在進行；之後，agent 還要能通知使用者。

單靠一次 LLM 呼叫做不到這些事。沒有 harness，你手上只有一次次交易式的推論呼叫；app 一旦關閉，呼叫也就結束了。這正是 Moss 認為這類系統若沒有某種 harness，就不能部署到 production 的原因。

## 案例二：趁你睡覺時運作的交易 agent

第二個案例是交易 agent。它會與股市互動，並自主運作；即使使用者睡著了，它也會繼續工作。

這時，harness 的設計重點不再是聊天，而是風險。Moss 列出了幾項因此必須考量的因素。

首先是故障處理。系統會持續運作，因此不能任由故障發生；harness 必須具備自我修復的能力。

其次是限制。由於牽涉到金錢，harness 必須設下防護措施和核准機制。Moss 說，金錢這件事「非常嚴肅」，因此才需要核准步驟。

<!--image:2-->

第三是安全性。agent 可能會接觸機密資料，例如你的財務資訊。因此，harness 需要具備處理 PII 等敏感資料的機制。

第四是 eval 循環。Moss 說，agent 應該能評估自己、改進表現並判斷成果，這樣他就不必親自處理。

## 這份清單並非放諸四海皆準

這四項並不是一份固定不變的檢查清單。Moss 說，具體需要什麼，取決於你想提供什麼樣的體驗。負責處理金錢的交易 agent 需要核准和安全機制；聊天型 agent 則可能完全不需要。

這個回答很坦白，卻也帶來一個不太方便的結論：你不能直接照搬其他團隊的 harness，並期待它一定適用。

## 幾乎每個 harness 都需要的元件

因此，Moss 將基本配備與其他需求分開討論。記憶功能肯定需要；工具呼叫大概也少不了。接著是持久化執行，不過他對這一點特別謹慎。

他不認為每個 agent 都需要持久化執行。這門課程會用到它，但不是因為每個 agent 的運作方式都一樣。許多 agent 只要送出一則訊息並取得回覆即可，而且在大多數情況下，它們不需要持久化執行。

深度研究 agent 和交易 agent 都需要持久化執行，因為即使使用者不再盯著它們，它們仍會繼續工作。差別就在這裡。

## 一句話串起整個概念

聊天室裡有人用一句話總結了這一節的重點，比投影片說得更清楚。Moss 認同這種說法，並重複了一次：

模型的運作方式，取決於 harness 允許它們如何運作。

<!--image:3-->

把這句話和上一篇文章放在一起看：模型負責推理，harness 則決定這些推理能影響什麼。在這一節的脈絡下，能力較弱的模型搭配嚴謹的 harness，仍有可能完成任務；能力很強的模型搭配鬆散的 harness，也仍然可能出錯。

## 留下來的問題

我們現在知道，難題會在哪些情境出現：app 被關閉、交易流程持續運作，或是某個動作會花掉金錢。我們也知道，解法取決於使用者體驗，因此沒有一份清單能涵蓋所有 agent。
