# 沒有 harness，你只有一次 LLM 呼叫

## 前言

問十個人什麼是 agent，你可能會得到十種答案。這不只是詞彙定義不清的小問題。當一個詞什麼都能指，你就無法明確說出自己需要打造哪些部分。你換了模型，結果還是不對；你讀了另一個框架的 README，卻發現各種說法彼此對不上。

當 agent 的執行時間超過一次回覆時，你就會第一次遇到這個問題。一項研究任務執行了十分鐘，使用者卻關閉了 app；某次工具呼叫執行到一半失敗。這時你得知道：是哪一層讓工作繼續進行、哪一層負責記憶，而哪一層只是根據 prompt 回答問題的模型。

這一節會用一句話幫你理清楚：agent 是 LLM 加上 harness。接著，我們會從三個角度說明這句話：先區分模型與 harness，再說明為什麼決定結果的是 harness，而不是模型，最後說明為什麼要將產品部署到正式環境，就不能沒有 harness。本節最後會列出這門課將為單一 runtime 加上的能力，以及每種能力要解決的正式環境問題。

本文要回答第一個問題：拿掉 harness 之後，還剩下什麼？

## 兩個沒人說得攏的詞

Scott Moss 從「agent」這個詞談起。他說，「harness 這個詞，老實說，跟 agent 一樣被用得太廣了。」他表示，問一個人什麼是 agent，每次得到的答案都不一樣。

他對 harness 也有同樣的看法。因此，他不打算爭論字典上的定義，而是提出一個定義，並在課程後續沿用。

## Agent 是 LLM 加上 harness

他的定義只有一行。提到 agent 時，他想到的是「LLM 加上 harness 的組合」。這就是 agent。

這句話把工作分成兩部分：模型負責推理，harness 則負責把回覆轉化為可用的成果。讓 agent 成為 agent 的，就是 harness。

## 沒有 harness，你就只有一次呼叫

拿掉 harness，模型還是會回答。這正是容易讓人誤判的地方：模型依然會回傳文字，所以整個系統看起來像是正常運作。

但你做的其實只是詢問 LLM，也就是發出一次性的呼叫。Moss 稱這種呼叫為「交易式推論呼叫」：送出一個請求，收到一個答案，之後的請求不會延續前一次的內容。

這時有四件事付之闕如：沒有對話、沒有記憶機制、沒有持久性，也沒有自我修復能力。你也無法依照不同問題切換架構。Moss 把這四項都歸在 harness 這一側。

## Harness 就是基礎設施

仔細看看 harness，就會發現它不只是個比喻，而是建立上述所有能力所需的基礎設施。

Moss 更進一步指出，在他看來，agent 本身就是基礎設施，而 harness 則是讓 agent 得以成立的基礎設施。

因此，他不認為沒有基礎設施也能稱作 agent。

沒有它，他說，你「至少做不出任何人會想用的東西」。

## Harness 負責的三類問題

Harness 負責處理三類問題。

第一類是記憶，涵蓋短期記憶、長期記憶、暫存區，以及事實資訊。

每一項都需要經過設計，而不只是宣告一個變數。

<!--image:2-->

第二類是工具。要如何引入工具？要採用自己的標準工具呼叫實作，還是使用 MCP 之類的方案？如果使用 MCP，又要如何管理這些伺服器？

第三類是長時間執行的任務，例如深度研究 agent。任務可能需要十分鐘才能完成，但使用者可能會在過程中關閉 app。Harness 必須讓工作繼續進行。使用者回來時，畫面仍應顯示 agent 正在研究；之後，agent 還必須能通知使用者。

## 沒有它，就無法上線

最後這個例子最能顯示問題的代價。使用者關閉分頁，不代表十分鐘的任務就會停止；但單獨一次 LLM 呼叫沒有地方可以接續執行，工作就這樣結束了。

因此，Moss 直接點出其中的限制：沒有 harness，就無法將產品上線。要部署到正式環境，就一定得有某種形式的 harness。

Harness 也能讓使用體驗好到足以實際使用。他列出 harness 帶來的好處：agent 更穩定、準確，能記住資訊，具備持久性，也更有韌性。用他的話來說，這就是確保 agent「不會出問題」所需的一切。

## 其他定義都是衍生說法

你可能會聽到別人用其他方式描述 harness。Moss 也聽過那些說法。他認為，其他所有描述都是從這個高層次的定義衍生而來。

要記住的，就是他反覆強調的這句話：沒有 harness，就沒有 agent，只有一次 LLM 呼叫。

這句話足以幫你分清楚各個層次，但還沒解釋為什麼兩個團隊使用相同的模型，結果卻不同。如果差異在 harness，接下來的問題就是：harness 由哪些部分組成？下一篇文章會打開 Claude Code，逐一拆解其中的部分。
