# 每一行都要過的兩個測試

你可能剛建立專案的 `AGENTS.md`，或用工具自動產生了一份，裡面列著建置指令、資料夾用途和常用檔案路徑。問題是，這些內容可能只是把程式碼和設定檔已經寫明的事再說一次；等專案改動後，路徑也可能過時。

判斷一條規則該不該留在 `AGENTS.md`，可以先問兩個問題：**agent 能不能自己查到？這條規則是否適用於整個 repo？**

## 測試一：agent 查不到嗎？

如果答案已經明確寫在專案裡，通常不用再抄進指令檔。

<!--image:1-->

例如，`package.json` 裡有建置指令，agent 可以直接查看；程式碼也能顯示結帳功能在哪裡。把這些資訊再寫一遍，未必能減少錯誤，反而多了一份日後需要維護的內容。

可以用一個簡單問題檢查：**拿掉這一行，agent 會因此做錯事嗎？**如果不會，這一行大概可以刪掉。

## 測試二：全 repo 都成立嗎？

有些規則確實重要，卻只適用於特定資料夾。比如只有退款測試使用 `fast-check`，就不該把它寫成全 repo 的通則；應該放在相關資料夾的指令檔，讓 agent 在處理那一區時才讀到。

<!--image:2-->

相對地，如果一條規則適用於整個 repo，就比較適合放在根目錄的 `AGENTS.md`。例如：不要手動修改 `drizzle/` 裡的 migration；應先修改 schema，再執行 `npm run db:generate`。

還可以再問一次：**如果移除這條規則，agent 是否更容易犯錯？**答案若是否定的，就不必留在指令檔裡。

## 不符合兩個測試，就換個地方

規則若只適用於某個資料夾，可以放進該資料夾自己的小型指令檔。操作流程，例如如何執行 migration，適合放在 skill；參考資料則放進文件，再從指令檔提供一個連結。

<!--image:3-->

如果規則能由機器直接檢查，例如「不要提交到 `main`」，就交給 hook 或 lint 規則。能讓工具檢查的要求，不必只靠 agent 記住。

根目錄的指令檔會在每次工作時進入 agent 的上下文，因此要控制長度。與其收錄所有可能有用的資訊，不如只留下「agent 自己查不到、而且全 repo 都成立」的規則。

最後還能多做一個檢查：更聰明的模型出現後，這條規則會不會變得多餘？如果會，它可能只是暫時補救模型弱點；但像 migration 這類專案特有的規則，不會因模型變強就失效。被這兩個測試刷掉的規則並不是全部都要丟掉，接下來要看它們各自該去哪裡。
