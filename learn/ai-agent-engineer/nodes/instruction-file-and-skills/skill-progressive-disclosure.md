# 一個資料夾，不是一段提示

操作流程適合放進 skill，但 skill 的價值不只在收納。每次叫 AI 修同一種問題，你可能都得重新交代：先看哪個 log、測試要怎麼跑、哪些設定不能動。把這些流程寫進一段很長的提示，短期看來方便，久了卻難維護；而且每次都載入全部內容，也會占用對話的 context。

Skill 的做法不同：把一套工作流程整理成資料夾，讓 AI 在任務需要時才載入。要寫得實用，關鍵有三個：控制內容何時載入、讓 description 能觸發正確的 skill，以及留下真正能改變行為的規則與經驗。

## 先把 skill 想成資料夾

Skill 的入口是 `SKILL.md`。檔案開頭的 frontmatter 放名稱和 description，後面才是指示；同一個資料夾也可以放腳本、參考文件和範例。

這種分層載入方式叫 progressive disclosure，也就是「逐步揭露」：開始時，AI 只需要知道有哪些 skill 和它們各自的 description；任務觸發某個 skill 後，才讀取其中的指示；執行到某一步需要細節時，再讀相關檔案或呼叫腳本。

因此，skill 不必把所有知識塞進一段提示。多個 skill 可以放在磁碟上，只有符合任務的內容才會進入 context。

## Description 是觸發器，不是摘要

AI 會先讀取各個 skill 的 description，判斷有哪些能力可用。描述太籠統，任務就可能對不上，skill 也就不會被載入。

<!--image:2-->

例如，只寫「協助部署」不一定能讓 AI 聯想到「把這版送上 staging」。比較有用的描述會直接寫出適用情境，以及使用者可能會說的詞，例如「部署到 production 或 staging；當使用者說 deploy、ship、release 或 push to prod 時使用」。

寫 description 時，可以先想兩件事：使用者遇到什麼狀況會需要這個 skill？他們會用哪些字描述？把這些觸發詞放在前面，讓 AI 能從日常說法找到對應的流程。除了自動觸發，使用者也可以直接用斜線指令叫出 skill，例如 `/debug-runbook`。

一個名稱清楚、觸發條件具體的 skill，才有機會在需要時出現，而不是只安靜地躺在資料夾裡。

## 刪掉不會改變行為的句子

Skill 的 context 有限，指示不能只求完整，還要有用。像「使用有意義的變數名稱」這類 AI 本來就會做的事，未必值得寫進 skill。

可以用一個簡單方法檢查：刪掉這句，AI 的行為會不會改變？如果不會，它可能是 no-op，也就是不產生實際效果的指示。這類句子只會占用 context，應優先移除。

<!--image:3-->

Skill 更值得記錄的是 AI 容易猜錯、或只有熟悉特定系統的人才知道的事。除錯流程裡，可能包括某種錯誤其實是測試位置或 alias 設定問題，不該先改設定；也可能是金額必須一路以整數分處理，不能在測試中換成浮點數或歐元金額。

這些具體陷阱適合整理成 gotchas（常見陷阱）。每當 AI 在這套流程中犯了錯，就加上一條清楚的提醒。這不是一般性的好習慣清單，而是記下哪些做法曾經出問題、下次要避開什麼。

## 固定步驟交給腳本，判斷留給指示

同一個要求，每次執行的結果可能不同。因此，如果某一步每次都必須得到相同結果，就適合做成腳本；如果需要根據情境判斷，就寫成指示。

<!--image:4-->

例如，跑指定測試、讀取一筆訂單或列出近期提交紀錄，都可以由腳本處理。至於要先查哪裡、報告的狀況是程式錯誤還是政策問題，則需要 AI 按情境判斷。

把固定操作放進 `scripts/`，能避免 AI 每次自行重寫執行方式。Skill 指示則保留真正需要判斷的部分。

## 從熟悉自己系統的流程開始

除錯手冊通常是好的起點，因為它會用到模型本來不知道的系統知識：出問題先看哪個 log、常見原因有哪些、哪些事絕對不能做。

整理時可以逐一確認：

- 使用者會怎麼描述觸發情境？
- 哪些資訊是模型不會自己知道的？
- 哪些操作必須禁止，例如不能更動資料庫？
- 哪些步驟每次都相同，應該做成腳本？
- Skill 要放在專案內，還是個人環境裡？

放在專案的 `.claude/skills/`，可以隨程式碼一起提交，讓取得專案的其他人也能使用；放在家目錄的 `~/.claude/skills/`，則可供同一台電腦上的各個專案使用。

寫好後，也要測試 description 是否真的能觸發：在不知道 skill 名稱的新對話中，用不同說法提出相關任務，確認 AI 會載入它；再用無關的要求確認不會誤觸。若相關任務叫不出來，description 可能不夠貼近使用者的說法；若無關任務也會叫出來，則可能寫得太寬。

好的 skill 不是把所有規則堆在 `SKILL.md` 裡，而是讓入口、觸發條件、判斷方式與固定工具各就各位。這樣 AI 需要時才讀到該讀的內容，也能記住那些真正能避免重蹈覆轍的經驗。知道資料夾該長什麼樣子之後，就能照同樣的結構，真的寫出一個會被載入的 skill。
