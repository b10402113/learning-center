# 其餘的規則，去哪？

前一步用「agent 查不到、全 repo 成立」兩個測試，篩掉了不該留在 `AGENTS.md` 的規則；剩下的問題是，這些內容該去哪裡。你打開專案的 `AGENTS.md`，看到一長串規則：怎麼建置、資料夾放什麼、某個流程要跑哪些步驟，還有「寫乾淨的程式碼」。這些內容看起來都重要，但不代表它們都該放在每次工作一開始就會讀取的檔案裡。

先替每一行做兩項檢查：代理程式能不能自己從程式碼或設定檔找出答案？這條規則是否適用於整個專案？如果答案分別是「能」或「否」，通常就不該留在根目錄的 `AGENTS.md`。

例如，建置指令若已寫在 `package.json`，就不必再抄一遍；某個資料夾的用途若能從程式碼看出來，也不必重述。但「不要手動修改 `drizzle/` 裡的 migration，應先改 schema，再執行 `npm run db:generate`」描述的是專案慣例，代理程式未必能自行推知，而且適用於整個專案，就值得留下。

還可以問一句：拿掉這一行，代理程式會因此犯錯嗎？如果不會，就刪掉。每次工作都會載入的指示應保持精簡，避免把本來能自行查到的資訊也塞進上下文。

## 依照規則的範圍與用途分流

不適合放進根目錄 `AGENTS.md` 的內容，可以按性質移到其他地方：

<!--image:1-->

- **只適用於某個資料夾的規則**，放在該資料夾自己的小型指示檔。代理程式處理那個資料夾時才需要讀到它。
- **操作流程**，例如「如何執行資料庫 migration」，放進 skill，讓代理程式需要照著做時再使用。
- **參考資料**，整理成 doc，並在指示檔裡留一個連結或簡短指引。
- **機器能檢查的規則**，例如禁止直接提交到 `main`，交給 hook 或 lint 規則處理。

特別要留意最後一類。如果一條規則可以由 linter 自動檢查，就不必只靠文字提醒。文字指示並不能保證代理程式每次都會照做；像「完成後跑完整測試」這類要求，有時仍可能只跑改動附近的測試。能用自動化檢查的，就讓自動化負責把關。

## 再做一次「到期測試」

每一行指示還可以再問一個問題：如果模型變得更聰明，這一行會不會就變得多餘？

<!--image:2-->

如果答案是會，它可能只是暫時的補救措施；模型升級後，就該重新檢查是否還需要。相反地，像專案限定的資料庫規則，模型再聰明也不會自動知道你們的做法，通常不會因模型更新而失效。

指示檔的載入位置也會影響規則適合放在哪裡：個人規則可放在家目錄的 `~/.claude/CLAUDE.md`，整個專案共用的規則放在 repo 根目錄，只適用於某個區域的規則則放在子資料夾。這些檔案會一起加入上下文；把一份長檔拆成啟動時就載入的多個匯入檔，並不會省下上下文空間。

## 逐行 audit：判斷它能不能變成 hook

整理指示時，可以逐行問：這條規則描述的是一個明確事件，還是需要判斷的原則？

<!--image:3-->

「完成程式碼後，執行測試」對應到代理程式完成工作的時刻，可以考慮用 hook 執行。「讀取檔案前，不要讀 `.env`」對應到讀檔之前，也有機會由 hook 把關。相較之下，「金額以整數分儲存，不使用浮點數」是需要理解程式內容的判斷，沒有單一事件可直接觸發 hook，較適合留在指示檔。

若一句話既不是明確事件，也不是有用的判斷原則，例如「寫出乾淨的程式碼」，通常也不必保留。把真正會影響代理程式行為的規則留下，其餘的移到適合的位置，或直接刪除。分流清單裡「操作流程放進 skill」這一項，是整個 node 接下來的主題。
