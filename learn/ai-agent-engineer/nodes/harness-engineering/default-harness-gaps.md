# 預設的 harness 不認識你的專案

知道 agent loop 是 harness 一輪一輪跑出來的之後，就能看出問題會出在哪。

你請 AI 助手替專案新增功能，它很快就寫出一段呼叫 API 的程式碼。程式看起來像模像樣，卻可能用錯介面；即使指令有執行，也不代表結果符合專案要求。

問題不一定是模型不夠聰明，也可能是外圍的執行環境，也就是 **harness**，不了解你的專案。Harness 負責把指令交給模型、執行模型要求的工具，再把結果回傳。模型負責判斷，harness 則讓判斷成為可靠的行動。

預設 harness 的缺口，常見於以下三種失敗。

## 只靠記憶猜 API

如果某個系統沒有提供可用工具，AI 可能憑記憶寫出 API 呼叫。它或許熟悉常見用法，卻不一定知道你的專案實際採用哪種介面，以及有哪些限制。

<!--image:1-->

光是提醒 AI「請仔細一點」，無法解決這個問題。Harness 若沒有提供專案專用的工具，模型就只能依照手上的資訊作答。可以把常用能力做成工具，由你的程式執行，再把結果交給模型。

## 分類器核准了有風險的指令

有些 harness 會在自動模式中，透過分類器判斷是否核准指令。但分類器也可能漏看有風險的操作。

核准機制不能只靠一次判斷。可以設定允許清單、使用沙箱或加入人工核准關卡，限制破壞性操作能做什麼，以及必須經過哪些步驟。權限應該訂成明確規則，而不是期待分類器每次都判斷正確。

## 沒有驗證，做完就停

AI 助手可能在它認為工作完成時停止，但停止執行不等於結果正確。沒有檢查，程式可能無法通過測試、資料格式可能不合規，甚至可能無法編譯。

<!--image:2-->

Harness 應在工作完成後執行專案測試、驗證資料結構，並拒絕無法通過編譯的成果。這些檢查能區分「看起來完成」和「確認符合要求」。

這三種失敗各自暴露不同缺口：沒有工具，模型只好猜 API；權限控管不夠穩妥，分類器可能放過危險指令；沒有驗證，系統就無法確認成果是否正確。替專案補上工具、權限規則與檢查，harness 才不只是把模型的回答送去執行，也能協助模型可靠地完成工作。

接著把這些缺口對回 harness 的零件：tools 補「不會做」，permissions 補「做過頭」。
