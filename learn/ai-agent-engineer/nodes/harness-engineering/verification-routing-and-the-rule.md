# 每犯一次錯，就加一條規則或一道檢查

tools 補上「不會做」、permissions 補上「做過頭」之後，還有第三個缺口：沒有人確認結果。

你讓 AI agent 修改程式，幾分鐘後它回報「完成了」，測試卻還是紅的。問題不只是它做錯了，而是整個 run 沒有可靠的完成訊號，無法確認結果是否真的符合目標。

要讓 run 證明自己已完成，就要用可檢查的訊號驗收，而不是只聽 agent 自己宣告。再搭配 routing，依照任務挑選模型，並在失敗時重試或切換備援，讓流程更有機會產出通過驗證的結果。

## 用檢查結果判定完成

Verification，也就是驗證，是由 harness 檢查成果是否符合要求。它可以執行測試、檢查資料格式是否符合 schema，或確認程式能否編譯。檢查沒通過，就不能把工作當成完成。

這和「請 agent 確認自己做完了」不同。agent 可能在測試還沒通過時就回報成功，因此完成條件必須依據它難以偽造的訊號，例如測試套件確實通過。

<!--image:1-->

如果 run 會自動反覆執行，就要先定義明確的目標檢查。檢查可以是必須通過的測試，也可以由另一個模型確認目標是否達成。這樣就能依據判準確認 run 是否完成，而不是相信它的自我評估。

## 用 routing 挑對模型，也安排失敗時的退路

Routing 是替不同工作選擇模型，並事先規劃呼叫失敗時的處理方式。需要複雜推理的工作，可以交給能力較強的模型。頻繁又簡單的呼叫，則可以使用成本較低的模型。主要模型失敗時，流程也可以重試，或切換到備援模型。

<!--image:2-->

Routing 和 verification 解決的是不同問題：前者安排「誰來處理，以及失敗時怎麼辦」，後者判定「結果是否過關」。換模型不會自動補上不足的檢查。如果模型缺少專案資訊、工具或必要的檢查，光換模型並不能解決這些問題。

送出私有程式碼前，也要確認模型在哪裡執行：供應商的雲端、路由服務，或自己的機器。選擇模型不只關係到能力與成本，也關係到程式碼會送到哪裡。

## 讓 run 有開始條件，也有停止條件

自動化的 run 可以由排程、事件或訊息觸發，這樣就不必每次都由人手動啟動。但 run 不會自然知道何時該停止，因此還要設好兩類界線：

<!--image:3-->

- **達成目標的檢查：**例如測試必須通過，或由另一個模型確認目標。
- **避免卡住的停止條件：**設定執行次數上限與 token 預算；如果 agent 一直重複相同呼叫，也要用無進展檢查終止它。

只有驗證訊號符合條件，run 才算完成。如果 run 一直無法達成目標，也會在預先設定的界線停止，不會無限重試或自行宣稱成功。

## 每犯一次錯，就補上相應的規則或檢查

每次出錯，都可以反問：缺少的是工具、權限規則、驗證，還是失敗處理？

<!--image:4-->

如果 agent 因為沒有工具而憑記憶猜 API，就補上合適的工具，讓結果能回到模型手上。如果它執行了不該執行的破壞性操作，就用允許清單、沙盒或核准關卡限制權限。如果它做完工作卻沒發現測試失敗，就補上測試或編譯檢查。

重點不是一味加長提示，而是把已經發生的錯，轉成 harness 能執行的規則或檢查。這樣不只能修正眼前的錯，也能讓下一次 run 更容易驗證，並在失敗時有路可退。

harness 解決的是單次 run 的可靠度；要讓經驗留到下一次，就輪到 memory 這一層。
