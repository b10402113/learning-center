# 規則，還是 hook？

你在 `AGENTS.md` 寫了「完成後請跑完整測試」，代理程式卻只跑了剛修改附近的測試，接著回報「全部通過」。問題不一定是規則寫得不清楚，而是文字只是提醒，不能保證代理程式每次照做。

要整理 `AGENTS.md`，可以逐行問三件事：**它對應什麼事件？需要判斷嗎？還是根本該刪掉？**

## 先分清文字規則和 hook

`AGENTS.md` 裡的規則是文字，代理程式可能遵守，也可能漏掉。曾有研究讓 Claude Code 遵守一條簡單規則：每個函式開頭加一行註解；結果它大約只在三分之二的情況做到。修改既有程式碼時，遵守比例還不到一半。

**Hook** 則是在指定事件發生時，由執行環境自動執行的腳本。事件可以是工作階段開始、執行命令前、編輯檔案後，或代理程式表示工作完成時。符合條件時，執行環境會觸發 hook，不必等代理程式記得規則。

<!--image:1-->

Hook 可以只提供資訊，例如載入工作階段背景；也可以成為 **gate（關卡）**，擋下命令或阻止代理程式結束工作。若要阻擋，最好同時說明原因和下一步，讓代理程式知道怎麼改走正確路徑。

## 用「事件、判斷、刪除」逐行審

### 1. 有明確事件：考慮改成 hook

> After you finish coding, run the tests.

「完成」是可辨識的時點，因此可以在代理程式表示完成時執行測試。**這一行最應該變成 gate**：測試沒通過，就不要讓工作直接結束；測試通過才放行。

<!--image:2-->

這比只寫「請跑測試」可靠，因為代理程式有時只跑修改附近的測試，卻宣稱全部通過。Hook 的測試關卡會在完成事件觸發測試，紅燈時要求繼續處理。

### 2. 有明確操作時點：用 hook 守住

> Never read the .env file.

這條規則對應「讀取檔案前」的事件，可以在讀取前檢查目標路徑，拒絕存取 `.env`，並提示改看 `.env.example`。

<!-- source: sources/ai-agent-engineer/20261103/The Agentic Coding Handbook.3.part.txt#L84-L88 -->

```bash
if [ -n "$path" ] && is_secret "$path"; then
echo "Blocked: $path holds secrets. Read .env.example instead: it lists every variable without the values." >&2
exit 2
fi
```

單一權限規則通常只管特定工具和模式。例如，禁止某個檔案讀取工具讀 `.env`，不一定也會擋住透過 Shell 執行的 `cat .env`。如果要求必須涵蓋所有會碰到該檔案的工具，就需要能在相關呼叫上檢查的 hook。

### 3. 沒有事件、需要判斷：留在文件裡

> Money is stored as integer cents, never floats.

這是程式設計約束，沒有一個自然的「現在就執行」時點可掛上 hook。它需要代理程式在設計和寫程式時理解，因此保留在 `AGENTS.md`。

不是每條規則都適合自動化。Hook 適合在明確時點執行檢查；像金額表示方式這類判斷，仍需要文字交代。

### 4. 沒有具體內容：刪掉

> Write clean code.

這句沒有說明怎樣算「乾淨」，也沒有指定可檢查的事件或標準。代理程式本來就知道這種泛泛要求，放在文件裡不會提供可執行的指引，刪掉反而讓真正重要的規則更醒目。

## Gate 是把關，不是萬能保證

如果一行規則描述了必須發生的時點，而且漏做會造成風險，就值得考慮做成 gate。完成時跑測試，是很清楚的例子；阻止讀取祕密檔案，也可以在檔案讀取前設關。

不過，Hook 不是防不勝防的牆。常見的模式檢查能擋住明顯錯誤，但複雜或刻意改寫的命令可能避開檢查；測試也可能根本無法通過。因此，人工審查和 CI 關卡仍然重要。

<!--image:3-->

整理 `AGENTS.md` 時，先找出「何時發生」；有明確事件的，評估能否交給 hook；需要理解與判斷的，留下文字；只有口號、沒有具體標準的，刪除。這樣才能把提醒和真正的把關分開。分流出來的規則裡，最該先變成 gate 的通常是危險指令。
