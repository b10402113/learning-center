# The gate

驗證首先要確認一件事：agent 寫的 code 能不能跑。

Code review 要檢查三件事：code 有沒有用、有沒有做出正確的東西，以及有沒有把事情做好。

這裡的檢查只負責確認 code 能不能跑。

問題是，就算有寫測試，也不代表測試一定會確實執行。

測試有沒有執行、執行得對不對，往往取決於執行者自不自覺，而不是由機制把關。

agent 和人都可能在這裡出錯。

## AGENTS.md 的一行字，攔不住 agent

你可以把「做完之前跑完所有測試」寫進 AGENTS.md。

但那只是一行文字，沒有任何機制能強迫模型照做。

一項實驗把一條再簡單不過的規則——每個函式開頭都寫一行註解——交給 Claude Code 執行了一千多個 session。

agent 大約只有三分之二的時間遵守這條規則。

改動既有 code 時，遵守率更不到一半。

## 「測試都過了」不是保證

規則攔不住，最後就得靠測試把關。

「做完之前跑完所有測試」，常常會變成 agent 只跑改動附近的幾個測試，接著回報「所有測試都通過」。

測試套件其他地方的錯誤，它根本沒看到。

<!--image:2-->

## 人也會失守

換成人來執行，問題只是變了個樣子。

agent 可能跳過測試，或謊報測試通過；人則可能忘了跑測試。

兩邊出錯的原因相同：檢查有沒有執行，靠的是執行者的記性與誠實，而不是流程本身。

<!--image:3-->

再往下看，模型再聰明，也得證明自己寫的 code 能跑。

在你的 repo 裡，這份證據就是你的測試。

模型不會知道你的測試指令、測試資料，也不知道你的 app 裡「done」代表什麼。

這些資訊都寫在你設計的測試裡。

每次改動都會跑測試，不管使用哪個模型。

## The gate：每個 PR 都跑同一套檢查，而且必須通過

Gate 會把檢查從「記得要跑」變成「每次都由機制執行」。

每個 pull request 都會跑完所有檢查，使用同一套方式，不論 code 是你、同事，還是 agent 寫的。

還要把檢查設為 required：只要有紅燈，GitHub 就會擋下 PR 的 merge，包括 agent 開的 PR。

重點不是「希望 agent 這次記得跑測試」，而是「測試沒全綠，就不能合併」。

在 TicketBay，這個 gate 是一個 GitHub Actions 檔案（`.github/workflows/gate.yml`）。

最後，打開 branch protection，將這些檢查設為 required。

<!--image:4-->

這樣一來，「證明 code 能跑」就不再靠每個人的記性，而是由每個 PR 都必須通過的同一道關卡來把關。

這個關卡在 TicketBay 具體長成什麼樣子，是下一段要打開來看的事。
