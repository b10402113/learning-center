# 先找出壞掉的那一層

知道 agent 是「模型加上 harness」之後，就能把七層拿來當排查工具。

你請 AI 代理修改程式，它卻猜了一個專案裡不存在的 API，最後還說「完成了」，但測試根本沒通過。

這時先別急著重寫提示詞。問題可能是它缺少合適的工具，也可能是整個流程沒有檢查結果。

排查時，先確認症狀，再找出該檢查哪一層。

| 你看到的症狀 | 優先檢查的層 |
|---|---|
| 呼叫成本太高，或程式碼不能離開你的電腦 | 模型 |
| 輸出格式不對，或代理自行補上你沒交代的預設做法 | 提示詞 |
| 它忘了前面交代的事，後來的表現也比一開始差 | 上下文 |
| 它猜了一個沒有工具可查的 API，或自認做完就停，卻沒人驗證結果 | Harness |
| 它在新一輪又選了你先前否決的做法 | 記憶 |
| 它一直跑不停，或目標還沒完成就停下來 | Loop |
| 一個錯誤指令可能碰到金鑰、其他專案或整個網路 | 邊界 |

## 先分清楚每一層負責什麼

**模型**提供推理能力。**提示詞**是這次任務的指令；**上下文**是模型單次呼叫時能看到的全部內容。

提示詞寫得再清楚，也無法解決上下文塞滿、導致早先指令被擠出去的問題。

**Harness**是模型周圍的執行環境，包括工具、權限、檢查與測試。**記憶**則是能留到下一次工作階段的檔案。

代理開始新一輪時可以讀取記憶，也可以把值得保留的經驗寫進去。

**Loop**負責啟動一輪工作，並判斷目標何時達成。**邊界**決定代理能接觸哪些環境，例如程式碼庫、測試、Git 紀錄，以及工具能連上的服務。

簡單說，代理是「模型加上 Harness」：它會使用工具、反覆執行，試著完成目標。單次執行結束後，上下文就會消失；記憶可以留到下一次，Loop 則能在沒有人手動啟動時，再開啟下一輪。

## 症狀指向 Harness 時，別只改提示詞

如果代理猜了一個自己沒有工具可查的 API，問題可能不是它沒讀懂指令，而是執行環境沒有提供查詢工具。

如果它說已經完成，測試卻沒通過，問題可能是缺少驗證結果的機制。

Harness 通常要處理四件事：提供工具或子代理、設定權限、驗證成果，並安排模型呼叫與失敗後的恢復方式。

驗證方式可以包括執行測試、檢查資料格式，或拒絕無法編譯的成果。權限則可以透過允許清單、沙箱，或破壞性操作的核准關卡來控制。

<!--image:2-->

每次代理犯錯，都可以考慮加上一條規則或一項檢查，避免同類錯誤再次發生。

提示詞改善的是單次呼叫。Harness 的工具與檢查則會在每次執行時派上用場，因此改善效果會累積到每一輪。

## Loop 要有可靠的完成訊號

如果沒有 Loop，每一步都得由你接手：你寫提示詞、讀取結果、決定下一步，再輸入新的提示詞。

Loop 可以把啟動和檢查交給流程處理，並由排程、事件或訊息觸發。

<!--image:3-->

不過，Loop 不會自然知道何時才算完成。代理也可能在測試仍未通過時，就回報成功。

因此，完成條件應該是代理不能只靠說法偽造的訊號，例如測試套件通過，或由另一個模型驗證目標。

還要設定停損條件，例如執行次數上限、Token 預算，以及偵測重複呼叫的無進展檢查。

Loop 改善的是整個目標如何持續執行與檢查。工作可以依排程啟動，也可以透過明確條件判定結果，就不必每一步都等人接手。

因此，Loop 的影響範圍比修正單次提示詞更廣。

## 自動執行前，也要檢查邊界

Loop 可能在人不在場時持續運作，當下也未必有人核准它執行的命令。

因此，代理能接觸到什麼，直接決定錯誤操作可能造成多大影響。

先確認代理能讀寫哪些檔案、使用哪些金鑰，以及連線到哪些服務，再限制不必要的存取。

排查時，先按症狀定位，別把所有問題都當成提示詞問題。

提示詞改善單次呼叫，Harness 改善每一輪執行，Loop 則讓工作依照觸發條件與檢查機制持續進行。

愈往外層修，改善效果愈能累積。地圖建立起來之後，接著從最內層開始，把 model、prompt、context 這三段分別弄對。
