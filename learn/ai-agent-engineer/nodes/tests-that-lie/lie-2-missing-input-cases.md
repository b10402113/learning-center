# 性質測試

第二種盲點是「只測了幾個例子，漏掉重要輸入」。你替 API 寫了幾個測試：正常查詢會成功、金鑰無效時會回傳錯誤、格式不正確的請求會被拒絕。這些測試都通過了，但使用者送來含有空字元的活動編號時，資料庫發生錯誤，API 卻回傳 500。

問題不一定出在測試寫錯，而可能是測試只檢查了幾種指定輸入。其他輸入組合可能完全沒有測到。

## 從「這個輸入會怎樣」改問「任何輸入都必須遵守什麼」

一般的範例測試（example test）會給程式一個確切輸入，再檢查確切結果。例如，確認兩座城市之間的最短路徑是否為 243 公里。這種測試很適合檢查重要情境，但輸入組合一多，就很難逐一列出。

<!--image:1-->

性質測試（property test）會先定義程式必須遵守的規則，再讓工具自動產生許多輸入，逐一檢查規則是否成立。這條規則稱為「性質」。例如，API 面對任何請求，都不應回傳 500，而且回應必須是 JSON 格式。

工具產生的請求裡，可能有正常資料、已撤銷的金鑰、非 JSON 內容，也可能夾帶控制字元的活動編號。這些都有機會測到人工列舉案例時容易漏掉的輸入。

## 讓失敗案例容易重現

性質測試通常依序做四件事：

<!--image:2-->

1. 寫下程式必須遵守的性質。
2. 讓工具產生許多不同的輸入組合。
3. 對每個輸入執行測試。
4. 檢查性質是否成立；如果失敗，就讓工具縮小出錯的輸入。

縮小失敗輸入的過程稱為「縮減」。工具會嘗試簡化造成錯誤的資料，直到留下仍能重現問題的最小案例。

例如，API 的性質測試在執行到第 52 個請求時失敗。工具把請求縮減成只含一個空字元的活動編號。資料庫拒絕這個字元，API 卻回傳 500。這個具體輸入補上了原本測試沒有涵蓋的情況。

## 性質不是列出更多範例

如果測試只是多加幾個手寫輸入，做的仍是逐一檢查案例。性質測試的關鍵，是清楚寫出「應該一直成立」的規則。

例如，最短路徑功能可以檢查：

<!--image:3-->

- 從 A 到 B 的距離，應該和從 B 到 A 相同。
- 距離不能是負數。
- 相同的兩座城市，每次查詢都應得到相同結果。

有了這些規則，工具就能用不同的城市組合測試程式，不必為每一對城市手寫一個案例。性質仍必須符合產品規則；如果路網是單行的，就不能直接套用「A 到 B 等於 B 到 A」這條規則。

性質測試無法保證測過所有可能的輸入。工具會依照設定產生大量案例，但測試結果還是取決於寫了哪些性質、輸入怎麼產生，以及執行幾次。它真正的用處，是補上範例測試涵蓋不到的地方，尤其是極端情況、邊界情況和不同輸入的組合。

因此，性質測試適合補充單元測試，而不是取代它。程式有明確規則可檢查時，例如金額計算、四捨五入、解析資料或狀態轉換，特別適合使用性質測試。如果程式只是把資料從一處傳到另一處，能寫出的實用性質可能就比較少。
