# 這個 loop 跑的是 session

memory 讓 agent 跨 session 記得事情，但不會自己啟動下一個 session。串起多個 session 的，是 loop。

你請 agent 修一個 bug，它完成一個步驟後就停下來，等你看結果、決定下一步，再輸入新指令。這時，串起整個工作的「loop」其實是你。

**Agent loop** 和**跨 session 的 loop**，差別就在這裡：前者讓 agent 在同一個 session 裡呼叫工具、完成工作；後者則負責啟動一輪又一輪的 session，直到工作通過檢查，或需要你介入。

跨 session 的 loop 通常由排程、事件或訊息觸發。每次啟動後，agent 會處理工作、檢查結果是否符合目標，再修正未通過的部分。

檢查通過後，loop 就停止並回報。遇到無法自行判斷的選擇，例如該採用哪一種修正方式，就會停下來詢問你。

## 一輪 loop 怎麼走？

每一輪通常會經過五個步驟：

<!--image:1-->

1. **Discover：找出需要知道的事。**  
   先蒐集完成任務所需的資訊。例如，收到客戶回報的 bug 後，先了解問題內容與相關脈絡。

2. **Plan：安排接下來的步驟。**  
   根據掌握的資訊決定處理方式，不要立刻動手。

3. **Do：執行工作。**  
   按照計畫進行修改或其他必要操作。

4. **Verify：檢查結果是否達標。**  
   用事先定義的方式檢查成果是否符合目標。不能只靠 agent 自己說「完成了」；例如測試仍未通過，就不能把 agent 的成功回報當成驗收結果。

5. **Fix：修正缺口，再跑一輪。**  
   檢查沒過，就針對問題修正並開始下一輪，直到結果通過檢查，或 loop 停止並把問題交還給你。

例如，把客戶回報的 bug 電子郵件轉成 pull request（PR，程式碼變更提案），可以把處理流程設計成一輪又一輪的工作：讀取回報、規劃修正、修改程式，再檢查結果。

這和單次 session 中 agent 做完一個動作就等你下指令不同；跨 session 的 loop 會安排後續輪次。

## 什麼工作適合交給 loop？

適合的任務通常有三個條件：會重複發生，值得把流程接起來；完成與否可以自動檢查；即使某次做錯，也能低成本丟棄重來。

其中最重要的是「能檢查」。如果還說不清楚怎樣才算完成，就無法可靠地設定 loop 的停止條件。Loop 需要可驗證的訊號，不能只讓 agent 自行判定任務成功。

## 先把邊界設好

較穩妥的做法，是先設計一個封閉的流程：目標清楚、步驟明確，每一步都有檢查，也知道何時停止或交回給你。

相較之下，開放式 loop 會讓 agent 自行探索，可能產生大量未指定的工作成果，因此不適合大多數團隊一開始就採用。

<!--image:3-->

Loop 會在沒有人盯著時執行，也可能不經人工批准就下指令。因此，除了設定 run 次數上限與 token 預算，也要安排無進展檢查，避免 agent 一再重複相同操作。

Agent 能接觸哪些檔案、金鑰與伺服器，也會影響出錯時可能造成的後果。

不過，不是每個任務都值得先建一套 loop；下一頁用三個條件先篩一次。
