# The stop has to be a signal it cannot fake

六個零件組起來之後，最關鍵的一項是「什麼時候停」。

把重複的開發任務交給 AI 代理，讓它自行執行、檢查並決定下一步，聽起來很方便。

但代理說「完成了」，不代表工作真的完成。

只要測試還是紅的，就不能因為代理這樣回報而停止。

要讓 loop（自動執行的循環）在真正完成時停下來，必須用代理無法自行改口的檢查結果判定完成。

## 先把完成條件設成 gate

Gate 是工作交付前必須通過的關卡。完成條件可以交給編譯器、測試套件或 CI 工作流程檢查。

這些檢查會明確回報通過或失敗，不會因為代理在文字回覆裡宣稱成功，就改變結果。

<!--image:1-->

假設代理修了一段程式，真正的完成條件是相關測試通過，不是代理回覆「已修好」。

如果代理犯了錯，可以把防止同類錯誤再發生的規則加進測試或 linter（程式碼檢查工具），讓 gate 每次都能抓出同類問題。

## 也要定義「還沒完成時怎麼停」

Gate 能判斷工作是否通過，但 loop 仍需要處理卡住的情況。以下幾個停止條件可以一起使用：

<!--image:2-->

- **Run cap**：限制一次執行最多跑多少輪，避免代理無止盡地重試。
- **Token budget**：限制可使用的 token 數量，避免卡住的執行持續消耗資源。
- **No-progress check**：檢查代理是否反覆做出相同呼叫，卻沒有實際進展。

這些條件不能證明任務成功，只能避免失敗的循環一直跑下去。

真正的成功，仍要由 gate 的結果確認。

## 自動化之前，先確認任務適不適合

適合放進 loop 的任務，通常會重複發生、能自動檢查是否完成，而且做錯後應該容易丟棄重來。

如果「怎樣才算完成」無法寫成檢查，就還不適合交給 loop 自動判定。

<!--image:3-->

設計停止機制時，可以先問兩個問題：什麼結果代表通過？如果一直通不過，何時必須停止？

前一個問題交給不可爭辯的 gate，後一個問題交給 run cap、token budget 和 no-progress check。

這樣一來，代理的成功宣告就不會取代真正的完成訊號。

loop 能自己跑之後，最後一層要處理的是它跑出去多遠：boundary。
