# Loop 的六個零件

確認任務值得進 loop 之後，接著要把它拆成可以各自負責的零件。

如果希望 AI agent 不必每做完一步就等你檢查、再下指令，就要把工作流程設計成能自行反覆執行的 loop。

以處理客戶回報的 bug 為例，loop 可以讀取問題、規劃修改、動手處理，再檢查結果。檢查沒通過，就修正後再跑一輪。

要讓流程穩定運作，需要六個各司其職的零件。

## 觸發器：決定何時開始

觸發器可以是排程，也可以是某個事件。

有了觸發器，loop 就不必等人手動啟動。例如收到新的問題回報時，loop 就能開始處理。

## 自己的程式碼副本：隔開每次執行

每次執行都在自己的 worktree，也就是獨立的工作目錄與分支。這樣一來，同時執行的工作不會碰到同一批檔案，能降低互相覆蓋的風險。

## Skills：提供目標與規則

Skills 是存放在檔案裡的目標和工作規則。

每次開始新的執行時，都會重新讀取這些內容，不必依賴上一輪留下的記憶，才能遵循一致的規範。

## Connectors：連上實際使用的工具

Connectors 是能連接外部工具的 MCP 伺服器。

透過 Connectors，loop 可以讀取或提交 pull request、工單和聊天訊息等實際工作，不必只在對話中描述結果。

## 獨立的 checker：檢查工作是否合格

Checker 是負責驗證結果的另一個 agent，也可以是一組測試。

它要確認工作是否符合目標，而不是只聽執行工作的 agent 自己說「完成了」。

Checker 最好由不同的 agent 或測試負責；這個角色不能由同一個 agent 兼任，因為執行工作的 agent 容易沿用動手時的假設，再用同一套想法檢查成果。換一個 agent 或交給測試套件，才能減少這種盲點。

<!--image:2-->

檢查最好設成明確的關卡，例如編譯器、測試和 CI。

這些檢查只會判定通過或失敗，不會因為 agent 在回覆裡辯解就改變結果。

如果 loop 一再犯同一種錯誤，可以補上規則，再用測試或 linter 確認這條規則確實能抓出問題。

## 執行之外的記憶：留下前幾輪的紀錄

還需要執行之外的記憶：記憶可以是一個檔案或標籤，記下先前執行留下的資訊，讓下一輪可以讀取。這能補足每次執行彼此獨立、重新開始的限制。

<!--image:3-->

把六個零件放進同一個流程後，還要先設定清楚的目標、執行步驟、各步驟的檢查方式，以及停止或交還給人的時機。

這樣 loop 才知道何時該繼續，何時算完成。而「何時算完成」正是下一個要處理的停止條件。
