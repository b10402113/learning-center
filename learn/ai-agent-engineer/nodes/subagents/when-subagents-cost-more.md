# 少即是多

讀取型工作適合多開代理，建置型工作適合少數。但「適合」不等於「免費」：你把工作拆給好幾個子代理，以為能把速度和成果一起放大；但每個子代理都得先讀取主代理已經掌握的資訊，回報時又會省略部分細節，主代理還要花時間分派工作、整合結果。代理一多，成本可能跟著上升，成果卻不一定更好。

<!--image:1-->

一個簡單的估算法是：先估出單一代理完成任務需要多少 token，再乘以 3 到 10，作為多代理方案的成本範圍。假設原本需要 10,000 token，多開子代理可能讓總量變成約 30,000 到 100,000 token。這是估算範圍，不代表每個任務都會剛好落在其中某個數字。

課程示範中，五個子代理平行研究 TicketBay 的雙重驗證登入，各自在自己的工作視窗讀取資料，合計約 171,000 token；主代理的訊息另用了約 31,000 token。兩者相加約為 202,000 token。這個例子沒有提供單一代理完成同一任務的 token 數，因此無法從中算出確切的倍數，但能看出多個工作視窗的成本會累積。

**適合加子代理的時機**，是工作大多能獨立進行，例如閱讀、審查或驗證程式碼。這些任務可以分頭處理，再由主代理整理結果。

<!--image:2-->

**不適合加子代理的時機**，則包括需要反覆討論協調、只是快速修改，或只需要迅速回答的任務。這時分派、重讀與整合的成本，可能比省下的時間更多。

因此，先用一個代理開始。只有在工作能清楚拆分、且子代理有明確的閱讀或查核任務時，再增加人手；代理數量增加，不等於成果也會按比例變好。
