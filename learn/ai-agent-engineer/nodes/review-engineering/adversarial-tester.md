# 對抗式測試者

上一節訂下的驗收準則，正好是這一步的輸入。程式改完、測試也全數通過後，你可能會想直接合併。但如果撰寫程式的代理人也負責審查，可能會沿用相同假設，漏掉自己沒想到的問題。這時可以請一名使用全新 context 的對抗式測試者，只看程式變更與相關規範，專門找出可能讓程式失敗的情況。

## 讓審查者從不同角度開始

對抗式測試者不是來稱讚程式，也不是重跑一般檢查。它的任務是像 QA 測試者那樣挑戰假設、探索邊界情況，找出開發者沒料到的失敗模式。

關鍵是使用全新的 context：審查代理人不應看到撰寫程式時的推理，而應只根據程式碼、驗收準則與專案規範做判斷。工具允許時，也可以使用不同模型。這樣審查者就比較不會跟著作者的盲點走。

## 先說清楚要審什麼

審查開始前，提供三項資訊：

<!--image:2-->

- **變更範圍**：例如某個 pull request 或指定的 diff。
- **驗收準則**：列出要逐項檢查的行為要求，最好直接提供原文。
- **專案規範**：提供 `AGENTS.md` 的位置；若專案使用 `CLAUDE.md`，也要提供該檔案。

審查範圍應該只涵蓋這次變更，還有它改變的行為。可以查看周邊程式與呼叫端，確認改動是否影響原本的使用方式；但變更前就存在的問題應另外列出，不該當成這次合併的阻擋理由。若未提供驗收準則，也要在報告中明確說明。

這樣能避免審查範圍不斷擴大、每次都重報舊問題，或把個人偏好的風格意見混進結果。

## 看懂 PROVED 和 REASONED

每個發現都要標出判斷依據，主要分成兩種：

<!--image:3-->

- **PROVED**：以失敗測試證明。報告應列出測試名稱、輸入、預期結果與實際結果。預期結果必須根據驗收準則、專案規範或程式明確定義的契約；不能只因為測試者覺得某種行為比較合理，就當成證明。
- **REASONED**：目前無法用測試證明，但根據特定檔案與行數提出具體疑慮。報告應說明推理、為什麼不容易或不適合寫成測試，以及需要人檢查或決定的事項。

`REASONED` 不是已證實的錯誤，而是需要人判斷的風險。閱讀者應核對所引用的程式碼，確認實際情況是否符合需求。不能把它改標成 `PROVED`，也不能把未實際執行的測試說成證據。

例如，某項驗收準則明確規定，三張票分三次取消時，退款仍應扣除五角手續費。若測試每次輸入一張票，結果卻沒有扣除這筆費用，就能依照準則判定為 `PROVED`。相較之下，如果退款預覽載入期間取消按鈕仍可操作，使用者可能確認自己沒看過的金額；若要精確控制瀏覽器時序才能驗證，這項疑慮就可能先列為 `REASONED`，交由人確認。

## 合併判決怎麼讀

報告應先列出問題，再說明其他內容，並將「由這次變更造成」與「變更前就存在」的發現分開。每個問題都要附上標籤與具體依據；若沒有發現問題，也要說明審查過哪些地方，以及哪些情況沒有出錯。

只要「由這次變更造成」的清單有任何發現，判決就是 **don't merge**。這也包括 `REASONED`：在有人檢查並確認或排除之前，它會阻擋合併。只有沒有尚待處理、且與變更相關的發現時，才適合判為 **merge**。原本就存在的問題應另外記錄，不列入這次的阻擋判決。

<!--image:4-->

對抗式審查的工作是找出問題並交代證據，不是順手修改程式。失敗測試應留在工作目錄，交由負責修正的人在下一輪處理。
