# 好 prompt 的四件事

模型選好之後，同樣的模型寫好 prompt 和寫壞 prompt，結果差很多。

如果只請 AI「替活動列表加上分頁」，它可能不知道為什麼要做、怎樣才算完成，也不清楚哪些地方不能改。結果可能不符合需求，還可能動到你不想修改的程式碼。

好的 prompt 不只要交代工作，也要把容易讓人猜錯的地方說清楚。先說明四件事：要達成什麼、為什麼要做、怎麼驗收，以及哪些範圍不能碰。再提供專案裡的程式碼作為參考。

## 先說要達成什麼，也說明原因

「加入分頁」只說了要做的事，卻沒有說明使用者遇到什麼問題。補上原因，AI 才能理解這項改動要解決什麼問題、帶來什麼結果。

<!--image:1-->

例如：「替活動列表加入分頁，讓有 200 場活動的主辦人也能找到需要的活動。」這裡要達成的成果是讓活動列表有分頁，原因則是幫助活動數量多的主辦人找到目標活動。

## 把完成條件寫成可檢查的事項

「做好分頁」很難判斷是否完成。應指定能實際執行的檢查方式，例如要求測試指令通過，並新增一個涵蓋第二頁的測試。

<!--image:2-->

這樣就不必只靠 AI 自己判斷是否完成，也能透過測試確認。

## 說清楚哪些範圍不能碰

如果有些檔案或功能不該修改，就直接列出來。例如：「不要修改 `src/domain` 或資料庫遷移檔。」

<!--image:3-->

沒有寫明限制時，AI 可能選擇它認為可行的做法，修改範圍也可能超出預期。列出不能碰的地方，能讓處理範圍更明確。

## 用專案裡的程式碼作為範例

與其讓 AI 自己想做法，不如請它參考專案裡已有的實作。例如：「依照 orders 模組的分頁方式。」

這樣 AI 就能依據專案現有程式碼來修改，不必憑空設計一套做法。

把這四件事合在一起，可以這樣寫：

> 替活動列表加入分頁，讓有 200 場活動的主辦人也能找到需要的活動。  
> 完成條件：`npm run test:unit` 通過，並新增一個涵蓋第二頁的測試。  
> 不要修改 `src/domain` 或資料庫遷移檔。  
> 依照 orders 模組的分頁方式。

寫完後，可以確認 prompt 是否回答了四個問題：要達成什麼成果、為什麼要做、怎麼確認完成，以及哪些地方不能碰。也要確認是否指出專案裡可供參考的程式碼。

不過，prompt 寫得再清楚，也會被一個東西抵銷：模型當下讀得到的 window 內容。
