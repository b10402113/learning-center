# 依工作挑模型

七層地圖的最內層是 model。寫程式時，有些工作需要模型深入推理，有些則只是頻繁的小任務。挑選模型不能只看知名度，還要考量工作難度、呼叫成本，以及程式碼會送到哪裡。

模型會讀取輸入並產生回答，但不會記住不同呼叫之間的內容，也不會自行執行程式。代理系統能做什麼，還要看外層的 harness，也就是負責串接模型與其他工具的執行框架。

## 先看工作難度與呼叫成本

需要處理困難推理時，可以選能力較強的模型；如果工作簡單、呼叫頻繁，則可考慮成本較低的模型。這樣能讓模型能力符合工作需求，不必每件事都選最強、也可能最貴的模型。

<!--image:1-->

封閉模型通常在供應商的雲端執行，費用可能按 token 計算，也可能採訂閱制；訂閱方案也可能設有使用限制。開放模型會公開權重，可以下載到自己的機器或雲端執行。

模型排行榜會持續變動。比較模型的程式能力時，可以參考最新評測結果，例如 SWE-bench Verified。過去的排名不代表長期結果，挑選模型前應確認最新排行榜。

## 傳送程式碼前，先確認它會去哪裡

如果工作涉及私人程式碼，挑選模型前，先確認模型實際在哪裡執行：供應商雲端、模型路由服務，還是自己的機器。不同模型與部署方式，會讓程式碼送往不同地方。

<!--image:2-->

因此，選擇時不能只看模型名稱，也要確認呼叫模型的路徑。先弄清楚資料會送到哪裡，再判斷是否適合用在手上的程式碼。

## 換模型前，先檢查 prompt、context 和 harness

模型答得不好，問題不一定出在模型能力不足。也可能是 prompt 沒有清楚說明需求、context 缺少必要資訊，或 harness 的串接方式有問題。

<!--image:3-->

遇到問題時，先檢查這些環節，再考慮換模型。若造成問題的條件沒有改變，即使換了模型，結果也未必會改善。

模型選定之後，下一個能直接動手改的是 prompt。
