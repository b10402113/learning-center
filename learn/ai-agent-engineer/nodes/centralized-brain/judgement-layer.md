# 決策不會被刪除，只會標成 superseded

你可能曾決定所有新專案都使用某種資料庫，幾個月後卻因專案需求而改變做法。若直接覆寫舊文件，日後就很難知道當初為什麼這樣選，也看不出決策為何改變。

比較可靠的做法，是把不同類型的規則和決策分開記錄，寫下理由、日期和來源。決策改變時，保留舊檔並標記為 `superseded`，表示「已被新決策取代」。

## 分清楚 guidelines、taste 和 decisions

這三種文件記錄的不是同一件事。

<!--image:1-->

- **Guidelines** 是每個專案都會採用的做法，例如「整合測試使用真正的資料庫，不使用 mock」。除了規則，也要寫清楚原因和執行方式。
- **Taste** 記錄你認為「什麼算好」的偏好。例如偏好熟悉、單純的方案，因為下一位維護者也要看得懂；或在兩種方案都可行時，選擇組成較少的那一種。每條偏好都應附上理由和日期。
- **Decisions** 記錄特定時間做出的決定。每項決策獨立成檔，說明決定內容、理由，以及何時需要重新檢視。

以資料庫為例，「整合測試必須使用真正的資料庫」可以是一條 guideline；「新專案預設採用 Postgres」則是一項 decision。前者是反覆適用的工作規則，後者是可能因專案需求而改變的選擇。

## 每條規則都要寫清楚原因

只寫「要用真正的資料庫」，很難幫助別人判斷這條規則為什麼存在。完整的 guideline 會說明：mock 只會回傳測試預先指定的結果，因此可能漏掉真實查詢、資料庫約束或交易中的問題。測試時應啟動真正的資料庫，並以接近正式環境的方式套用 migration。

<!--image:2-->

Taste 也需要理由。例如，「偏好成熟、常見的方案」，是因為下一位維護者還得接手；「選擇組成較少的方案」，是因為每個額外的部分都可能故障。寫清楚偏好背後的理由，之後才能套用到新情境，而不是只照抄一句規則。

文件也應保留日期和原始來源。來源檔案維持不修改，筆記或規則再連回原始資料，日後就能追查做法的由來。

## 決策改變時，保留新舊紀錄

決策檔可用日期和簡短主題命名，例如 `2026-01-15-postgres-default-database.md`。檔案內寫下日期、目前狀態、決策內容、理由，以及重新檢視的時機。新專案預設使用 Postgres，是因為團隊熟悉同一種資料庫，而且測試容器與正式環境可以使用相同的資料庫。若專案需要 Postgres 不擅長的功能，例如大規模全文搜尋，就應重新檢視這項決定。

如果後來做出不同決定，不要把舊檔刪掉，也不要直接改寫成新的結論。更新決策史時，依照以下步驟：

<!--image:3-->

1. 用新的日期建立一份決策檔。
2. 將舊檔狀態設為 `superseded`，並填上 `superseded_by`，連結到新檔案。
3. 在新檔填上 `supersedes`，連結回舊檔案。

這樣，讀者能從新檔了解目前採用的做法，也能從舊檔了解過去的決定、理由和後續變化。檢查工具還可以確認，每個 `superseded` 決策都連結到一份存在的檔案。

這些檔案不會自己長出來。它們靠每天的擷取、分類與檢查慢慢累積，也就是下一個主題。
