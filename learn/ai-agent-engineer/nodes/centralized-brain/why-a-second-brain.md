# 沒有共享記憶，你有三個壞選項

你開了一個新專案，請 AI 助手替你寫功能。它不知道你偏好的測試方式，也不知道你已經做過哪些技術決定，只能從頭猜起。

沒有共享記憶時，通常只有三種做法，但各有麻煩。

第一，每次開新對話，都重新交代規則。你得一再說明程式碼要怎麼寫、測試要怎麼安排，以及哪些決定已經定案。

第二，把規則複製到每個專案的 `AGENTS.md`。一開始看似方便，幾個月後，各專案的副本可能就不一致：這邊改了，卻忘了更新其他地方。

第三，把所有規則放進電腦上的全域設定檔。這可能只適用於某台電腦上的特定工具，其他工具、伺服器上的 AI 助手，或另一台電腦上的代理程式，都未必讀得到。即使每個代理程式各自有記憶和技能，累積的經驗也彼此分開，不知道其他代理程式學到了什麼。

解法不是把所有資訊塞進同一份專案說明，而是分成「專案層」和「大腦層」。

## 專案層：只放這個專案需要知道的事

專案層記錄單一專案的特殊資訊，例如專案根目錄的 `AGENTS.md`、特定資料夾的小型說明檔，以及只適用於這個專案的技能。

<!--image:1-->

這樣，代理程式處理專案時，只需讀取眼前工作所需的脈絡，不必連其他專案的細節也一併讀進來。

## 大腦層：保存跨專案都用得到的知識

大腦層收納跨專案適用的內容，例如程式碼撰寫準則、已做出的技術決定、各專案的簡短介紹，以及專案部署位置等管理資訊。

它可以是一個獨立的 Git 儲存庫，裡面放著 Markdown 檔案和跨專案共用的技能。不同專案中的代理程式、你本機使用的工具，以及在伺服器上工作的 AI 助手，都能讀取同一份資料。資料也能持續更新，讓新學到的經驗不只留在某個工作階段或某個代理程式裡。

<!--image:2-->

兩層各有分工：專案層處理「這個專案特有什麼」，大腦層處理「每個專案都用得上的知識」。跨專案的第二大腦能減少重複交代，也能避免規則散落各處、逐漸失去一致性。

一個示範清楚呈現了差別：代理程式第一次在空資料夾接到「寫一個儲存使用者的函式，並加上整合測試」的任務時，選了 SQLite。安裝第二大腦後，它在新的工作階段讀取索引、測試準則和資料庫決策，再做同樣的任務時便改選 Postgres，並用容器啟動真正的 Postgres 進行測試。它不必重新猜測，而能沿用先前留下的決定。

兩層的分工說清楚了，下一個問題是：那個大腦層的 Git 儲存庫裡，實際上分成哪些資料夾。
