# 一份 claim，一個全新的 judge

上一段留下的問題是：survivor 殺不掉時可以寫一份 claim。接下來要處理的就是那份 claim 交給誰、憑什麼被接受。

跑完 mutation tool 後，手上通常會剩下幾個殺不死的 mutant。

有些 mutant 確實殺不死：修改後的程式碼對所有輸入都回傳和原版相同的結果，任何測試都無法分辨兩者。

問題在於，誰來判斷 mutant 是否真的殺不死。最希望 gate 變綠的 agent，也最可能把其實殺得死的 mutant 判成殺不死。

所以第一條規則是：agent 絕不能自行標記 equivalent。

agent 能做的是提出 claim，說明為什麼沒有任何輸入能分辨 mutant 和原版，並清楚指出等價是 in isolation 成立，還是只在 context 裡成立。

claim 不是結論，而是等待檢驗的對象。

## 在別人的 context 裡判

每份 claim 都要交給全新的 agent 判斷，一份 claim 配一個 judge。

可以使用 harness 的 subagent（Claude Code 的 Agent tool）、其他 delegate 工具，或至少開一個新 session。

絕對不要在自己的 context 裡判，因為你已經在自己的 context 裡知道想要的答案。

交給 judge 的資訊必須嚴格限定。任務簡報要原封不動，另外只提供：

- 檔案路徑、被修改那一行的原文，以及包含該行的完整函式
- mutant：工具修改後那一行的內容，以及 mutator 名稱
- claim 本身：為什麼認為沒有輸入能分辨兩者，以及等價是 in isolation 還是 in context
- 執行測試的指令

其他資訊一律不提供。

不要提供你的推論、其他 claim 或 mutation 報告。

所有 judge 一起啟動，然後等全部判決回來。

## judge 的工作只有一件：殺掉它

judge 的立場和提出 claim 的人相反。

judge 的任務是證明 claim 錯誤：找出一個輸入，讓原版和 mutant 的結果不同，再寫出一條會在 mutant 上失敗的測試。

只要成功駁回 claim，judge 就完成任務。

「一個輸入」的範圍有明確界線：任何呼叫端能從公開入口傳入，而且會走到被修改那一行的值。

函式是 exported 或 public 時，入口就是該函式本身；否則，入口就是任何會呼叫到它的 exported 函式、route 或指令。

「在 context 裡等價」不能保護 exported 函式。

目前沒有呼叫端會送出某種輸入，不代表下一個呼叫端不會送出。

因此，直接呼叫這個 export 的測試，就是有效的 kill。

只有函式是 private 時，judge 才把輸入限制在它的呼叫端實際能產生的範圍內。

這時要去讀那些呼叫端。

有一種輸入不算數：如果每個入口在兩個版本裡都用相同方式錯誤地拒絕它，它就無法分辨兩者。

## 怎麼找那個輸入

步驟順序固定。

先讀函式，找出 mutant 改動了哪些判斷和數值，再推導每個被改動分支會回傳什麼。

接著，逐一測試這個參數型別能接受的輸入類別：

- 被改動那一行裡每個比較的邊界：該值本身、比它小的下一個值，以及比它大的下一個值
- 零、負零、負數、最小的正數
- NaN、無限大、null、undefined、空字串、空的集合
- 函式能接受的最大值，以及整數溢位
- 四捨五入的平局（x.5），以及會捨入成零的值

測完上述項目後，再自行設計三個針對被改動分支的輸入。

用不留檔案的 inline 指令檢查候選輸入：把函式複製成純程式碼，另外複製一份 mutant，讓兩份程式各自處理每個候選值，並印出結果不同的值。

比較時要使用語言中最嚴格的相等方式。

JavaScript 用 `Object.is`，不要用 `===`，因為 `===` 會把 `-0` 和 `0` 判成相等。

過程中不要修改 source 檔，也不要留下暫存檔。

## 兩種判決

只要找到能分辨兩者的輸入，判決就是 REJECTED。

這時 judge 要在專案自己的 test 目錄中，依照專案的命名風格新增一條測試。

檔名要說明測試保護什麼，不要叫「judge」。

測試要呼叫真正的公開入口，並斷言商業結果：使用者、客戶或呼叫端應該得到什麼。

接著用一句話說清楚這條測試替使用者保護了什麼。

如果說不出來，代表測試斷言的是 mutant 的行為。請改用另一個輸入，或改斷言其他結果。

最後，用指定的指令執行一次測試。

測試必須在原版程式碼上通過。

測完所有輸入類別，也加上自行設計的三個輸入後，如果仍然無法分辨兩者，就停下來。

不要再繼續想新輸入。

判決是 STANDS，固定寫成：judged: no distinguishing input found。

同時列出測過的輸入類別，並說明等價是在 in isolation 成立，還是只對這個 private 函式目前的呼叫端成立。

有兩條紀律：不要為了省時間，就把 claim 判成 STANDS；也不要為了讓測試在原版上通過，就把測試改弱。

錯誤的 STANDS，會把測試漏洞藏在排除註解後面。

## 排除要人類點頭，而且只問一次

所有判決回來後，工作還沒結束。

把所有站得住腳的 claim 和 judge 的判決註記整理成清單，一次詢問使用者，請他批准這些排除。

只有使用者回答 yes 後，才能在相應行加上工具的排除註解，並逐行寫明理由。

沒有得到 yes，就不能寫任何排除註解。

如果無法詢問使用者，例如在非互動執行或 CI 環境中，也不能寫排除註解。

這些站得住腳的 claim 必須回報為 open decisions，並讓 gate 保持紅燈。

因此，不要追求 100% 的 mutation score。

equivalent mutant 會讓 100% 根本無法達成；硬要達成，只會讓這個迴圈永遠無法收斂。

## 什麼時候算做完

- 沒有任何活著的 mutant 能改變金額、權限或已儲存的紀錄。
- 每個留下的 survivor，都有一份 fresh judge 無法殺掉的 claim。
- 每條排除註解都經過判斷並獲得使用者批准。未獲批准的 claim 是 open decision，而且沒有對應的排除註解。
- 每個 survivor 都有一句不負責寫測試的人也聽得懂的說明。

高分報告如果留下沒解釋的 survivor，就不算完成。

列出三個已解釋、已排序，並由使用者選擇接受的 survivor，才算完成。

mutation testing 管的是「已經寫好的測試有沒有檢查行為」。它看不到的是另一種漏：案例根本沒寫。那個缺口要換一種測試來補，也就是下一段的 property test。
