Skill 是什麼：把「你怎麼做事」存成一份檔案

Step 1/3 · Skill 是什麼、安裝一個來用

為什麼每次都要重講同一套做法？

想像你在一間行銷公司工作。每接到一個新客戶，你都會照固定流程開始：先研究客戶所在的產業和幾個主要對手，再盤點現有內容，找出三到五個可以切入的主題角度，替每個角度配上適合的格式，最後整理成策略簡報。這套流程你已經做過十幾遍，幾乎不用思考就能完成。

可是，每次你開啟 Claude 的新對話，畫面仍然是一張白紙。Claude 不知道你上次採用什麼順序，也不知道你有哪些固定偏好。於是，你得重新交代五個步驟，還要補充「角度不要超過五個」、「簡報先放結論」這些細節。

少講一句，產出的方向就可能偏掉。你只好再花一輪時間，把結果拉回自己熟悉的做法。

這裡的問題是：專案能記住背景，卻不一定記得你習慣怎麼做事。這一節要介紹的 skill，就是用來補上這個缺口。

Skill 是什麼

Skill 是一份保存下來的指令包。它把一套做法、規則和偏好寫成 Claude 看得懂的檔案。之後遇到符合條件的任務時，Claude 會讀取這份檔案，按照裡面的要求工作。

你可以把它想成公司給新進員工的標準作業程序，也就是 SOP。與其每來一位新人，就口頭說明一次，不如把流程整理成文件，需要的人直接照著看。

不過，skill 和真正的新進員工還是有一個重要差別：員工可能會自行判斷什麼時候該變通，skill 則主要依照你寫下的指令執行。因此，規則寫得越清楚，產出通常越穩定。

在 Claude 裡，skill 通常位於「Customize → Skills」。建立一個新 skill 時，主要會填寫三類內容：

  • 名稱：讓你在清單裡認出它。
  • 描述（description）：告訴 Claude 什麼情況下該使用這個 skill。
  • 做法與規則：說明工作要怎麼完成，以及產出要符合哪些條件。

其中，描述就像一個觸發器。它不是完整流程，而是在告訴 Claude：「遇到這種任務時，請把我叫出來。」

一份 Skill 裡面有哪些內容？

用一個實際例子來看會比較清楚。假設你希望 Claude 每次撰寫產品上線信時，都維持相同的風格，可以建立一個叫做「Product Launch Email」的 skill。

欄位內容範例作用
名稱Product Launch Email方便你在清單中辨認這個 skill
描述（觸發句）「當使用者要為即將在店裡上線的新商品寫上線信時使用這個 skill」決定 Claude 何時自動讀取它
做法與規則開頭用一句有力的話點出問題；用兩到三句介紹產品；全文壓在一百八十字以內；不准使用 excited 或 thrilled 這類字眼決定最後產出的寫法與限制

建立好之後，你只要說：「幫我寫 Leo Wireless 這款新品的上線信。」

Claude 會發現這個請求符合 skill 的描述，於是載入相關規則。你不用重新提醒字數限制，也不用再次交代不要使用哪些字詞，就能得到符合這套標準的信件。

Claude 讀取某個 skill 時，通常也會主動告訴你正在使用哪一個 skill。這像是把工作時使用的 SOP 放在桌角：你知道目前套用的是哪套規則，若結果不對，也比較容易回頭檢查。

Skill 不是什麼？先和兩個鄰居分清楚

Skill 很容易和專案（project）或 connector 混在一起。三者都能讓 Claude 更能完成工作，但各自負責的事情不同。

東西它記住的是什麼一句話的差別
專案（project）背景：你是誰、這件工作是什麼，以及相關的檔案與資料專案給背景（context）
Skill做法：這件事要按照哪些步驟與規則完成Skill 給做法（process）
Connector管道：讓 Claude 直接讀寫某個外部工具Connector 讓 Claude 接上工具並動手做事

可以把它們想成一起工作的三樣東西：專案像工作桌上的背景資料，skill 像放在旁邊的作業手冊，connector 則像通往外部系統的門。

例如，專案裡可以放品牌指南和受眾資料；skill 裡則寫著「如何撰寫一篇貼文」的流程。兩者一起使用時，Claude 既知道你是誰、要服務誰，也知道你希望用什麼方式完成工作。

兩組情況：該用 Skill，還是該用別的東西？

第一種情況是，Claude 缺少某份資料。

例如，你要求它按照公司最新的產品規格寫文案，但它根本拿不到那份規格。這時問題不在做法，而在背景資料不足。你需要處理的是專案或 connector，不是 skill。Skill 能告訴 Claude「拿到資料後要怎麼做」，卻不會自動提供只有你那裡才有的檔案。

第二種情況是，你只是想把一句話翻成英文。

這通常是一次性的小請求，不需要特別建立 skill。若一件事只做一次，或每次做法都不一樣，把它固定成 skill 反而會增加維護成本。

相反地，如果你每週都要寫產品上線信，而且每次都要求固定字數、固定結構和固定語氣，那就很適合使用 skill。它把重複交代的內容集中保存，讓每次產出都站在同一條起跑線上。

Skill 什麼時候最有價值？

Skill 的價值來自「同一套做法會被反覆使用」。通常符合以下情況時，建立 skill 很划算：

  • 這項工作會一再出現。
  • 每次的處理流程大致相同。
  • 你很在意產出的格式、語氣或限制保持一致。
  • 你常常需要重新解釋同一批規則。

相反地，如果工作只做一次，或你還在摸索最佳做法，就先不要急著建立 skill。做法還沒定型就把它寫死，之後可能會一直修改，像是把還在裝修的房間先釘死牆壁，反而更難調整。

一個實用的判斷方式是問自己：「哪些事情，我每次都在重複解釋？」

那些反覆出現、又需要維持一致的內容，就是最適合變成 skill 的候選。至於一次性請求、缺少外部資料的問題，則應該分別交給一般提示詞、專案或 connector。

把這個觀念放回整體工作方式

Skill 是一份可被自動觸發的指令包，把「怎麼做一件事」寫成 Claude 看得懂的檔案。它通常包含名稱、描述（觸發器）與做法規則，底層則是一個含有 skill.md 的資料夾。它和專案分工互補：專案記住背景，skill 記住做法；connector 則負責讓 Claude 連接外部工具。Skill 適合反覆發生、要求一致的工作，一次性的小任務不必特別建立。實用的起點，是先找出那些你一直重複解釋的內容。

因此，skill 不只是另一種提示詞，也不是用來存放所有資料的地方。它比較像一份會在適當時機被叫出的工作手冊：專案提供「要處理什麼」，skill 提供「要怎麼處理」。下一個問題就變成：手上的任務，到底該用一般提示詞、開一個專案，還是建立成 skill？
