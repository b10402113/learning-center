三層 context 與覆蓋規則

Step 4/5 · 專案與三層 context

學習目標

能畫出 Cowork 的 context 分層（global 指令、專案 claude.md、子資料夾 claude.md、參考檔案、你的提示），說明衝突時由「越具體的那一層」勝出，並用一句測試提示檢查 context 有沒有生效。

前言：讓 Claude 不用你提醒就知道規矩

上一節我們看到 Cowork 專案能讀檔、能寫檔，也能靠自訂指令和記憶知道你的偏好。但這裡有個實務問題：你是怎麼把「規矩」放進去的？如果你的報告永遠要從 executive summary 開始、檔名永遠要照某個格式、報表一律存成 .docx，這些規則總不能每次打提示時都重講一遍。

答案是把 context 分層放入。你可以把 context 想成調味：有些是整間廚房通用的底味，有些是這道菜專屬的調味，有些則是你當下加的那一匙。層跟層之間如果打架，也有明確的勝負規則。這一節就把這套分層規則講清楚。

三層 named context

Cowork 的 context 有三個有名字的層次，從最廣到最具體排下來是這樣：

層放什麼作用範圍
global 指令（global instruction）你是誰、你的通用偏好套用到所有 session
專案指令（project instructions）這個資料夾內任務的規則與輸出格式只套用到這個資料夾
資料夾內的參考檔案範本、背景資料、樣本供 Claude 讀取引用

第一層 global 指令是最外圈，它描述「你是誰」，不管你開哪個專案都會生效。例如你希望 Claude 動手前先問清楚、做事前先給計畫、命名檔案要用描述性的名字，這些都屬於跨專案通用的習慣，放這裡最合適。

第二層是專案指令，它管的範圍縮小到某一個資料夾裡的任務。以一份客戶報告專案來說，規則可能是「格式一律 .docx、最多六頁、一定要從 executive summary 開始、引用要從訪談筆記裡拉」。這些話只對這個資料夾有效，不會跑去管你別的專案。

第三層是資料夾裡的參考檔案。它們不是規則，是素材：報告範本、你的背景介紹、品牌樣本。Claude 讀了就知道「一份好的產出長什麼樣」，很多判斷是靠這些檔案補上的，而不是靠你逐條寫規則。

專案指令就是一個 claude.md 檔

這裡有一個很實用的細節：專案指令不是鎖在介面裡的黑盒子，它會被寫成一個純文字檔 claude.md，就放在那個資料夾裡。

這件事的意義是，你可以用兩種方式改它：直接打開 claude.md 編輯，或在對話裡請 Claude 幫你改。你如果偏好用手打字、想看得到每一行規則，就直接編檔；你如果在對話中發現「這裡的規則不太對」，也可以當場叫它修。規則是活的，不是設定完就動不了。

它們是怎麼疊起來的：連子資料夾也算一層

實際運作時，這三層還會再往下疊。除了上面說的 global、專案、參考檔案，如果資料夾裡還有子資料夾，子資料夾也可以有自己的 claude.md。最後，再加上你當下打的那段提示。

所以完整疊起來，從最廣到最具體大致是：

global 指令              （你是誰，套用到所有 session）
  └─ 專案 claude.md      （這個資料夾的規則）
       └─ 子資料夾 claude.md （更細的規則）
            └─ 資料夾內的參考檔案
                 └─ 你當下的提示（最即時、最具體）

看這個結構要抓一個重點：越下面的層，管得越細、越靠近眼前這件事；越上面的層，管得越廣、越像通用原則。

衝突時，越具體的那一層贏

既然這麼多層，難免會互相矛盾。假設 global 指令說「語氣一律正式」，但某個子資料夾的 claude.md 寫「這個客戶的文案要輕鬆口語」。這時候聽誰的？

規則是：越具體的那一層勝出。以這個例子來說，子資料夾的規則比 global 更具體，所以那個客戶的文案走輕鬆口語，其他情況才回到「正式」這個底味。同樣地，你當下打的提示通常是所有人的上級；只要不是荒唐的要求，當場說的那句話最有份量。

這個設計很符合直覺：通用的原則當預設值，真正靠近任務的人可以提出更精確的例外。你不需要為了某個客戶去改動整套 global 規則，只要在對應的那一層放上更精確的一句話就好。

該寫什麼進去：只寫「Claude 會做錯的事」

知道有這麼多層之後，很容易掉進一個陷阱：想把每一件事都寫下來，結果 context 變成一疊沒人讀的說明書。

比較好的做法，是只在裡面寫「Claude 如果不被告知，就會做錯的事」。它預設就會做對的，不必寫；它老是搞錯的格式、老是不懂的偏好，才需要寫進去。這樣每一條規則都有存在的理由，上下文也不會被稀釋。你可以把這想成「例外清單」而不是「百科全書」。

怎麼確認 context 真的生效了

設定完成後，怎麼知道它有沒有讀進去？有個很簡單的測試：直接問它一句「你知道我在這個專案裡是怎麼工作的嗎？」

Claude 會把它目前抓到的規則、背景、格式講給你聽。如果它說出來的東西符合你的預期，代表 context 疊對了；如果它漏掉某條重要規則，或講出你根本沒設定的東西，那就是哪裡沒對上，也許是某層放錯位置，也許是檔案沒被讀到。用一句話就能揪出缺口，比等到產出歪掉才回頭檢查省事得多。

小結

Cowork 的 context 是分層疊起來的：最外圈是 global 指令（你是誰，套用到所有 session），往內是專案指令（寫在資料夾的 claude.md 裡），再往下是子資料夾的 claude.md、資料夾內的參考檔案，最後是你當下的提示。衝突時，越具體的那一層勝出。claude.md 是純文字檔，可以直接編輯或請 Claude 改。要寫進去的，是「Claude 不講就會做錯的事」，不用什麼都寫。最後用「你知道我在這個專案裡是怎麼工作的嗎？」這句測試，就能檢查 context 有沒有真的生效。

到這裡，你已經懂專案的結構、會開兩種專案、也知道 context 是怎麼一層層疊起來的。最後一節要把大家最常踩的坑整理成一張診斷清單，讓你之後遇到「專案怎麼好像壞掉了」時，能自己找出原因。
