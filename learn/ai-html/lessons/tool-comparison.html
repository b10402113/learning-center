HTML 演示文稿工具生態與選擇

ai-html · Step 3/3

一句話回顧

前兩步我們理解了 HTML 是 AI 的原生輸出語言，以及零依賴單檔的架構設計。這一步看看整個 HTML 演示文稿的工具生態，以及怎麼根據你的場景做出正確選擇。

核心問題

搜尋「html presentations」的人，意圖是分裂的。有人要框架，有人要 Markdown，有人要 AI 生成的 HTML。這三種路徑各有適用場景，選錯了會浪費時間。

三種實現形式

1. 框架驅動（Framework-led）

代表工具：Reveal.js、WebSlides

這類工具提供一套 JavaScript 框架來管理投影片。你用 HTML 寫內容，框架處理導航、動畫、轉場。

優勢 劣勢
功能最強：嵌套投影片、自動動畫、PDF 匯出、演講者備註 編輯摩擦大：非技術人員無法輕易修改
完全控制運行時行為 需要理解 HTML/CSS/JS 才能有效使用
適合技術演講和產品展示 團隊協作困難

選擇 Reveal.js 當你需要：自訂互動、技術演講者、重視瀏覽器行為勝過非開發者編輯。

2. Markdown 驅動（Markdown-led）

代表工具：Slidev、Marp

這類工具讓你用 Markdown 寫投影片內容，編譯成 HTML。Markdown 保持簡潔，框架處理渲染。

工具 最適合 主要取捨
Slidev 開發者演講、程式碼密集的投影片 PPTX 匯出用的是圖片，文字不可選取
Marp 快速撰寫、可攜性高的投影片 互動性弱，不適合需要豐富行為的場景

選擇 Markdown 驅動當你需要：Markdown 作為主要撰寫格式、程式碼區塊和元件預覽、多種匯出路徑（HTML/PDF/PPTX）。

3. Agent 構建（Agent-built）

代表方案：AI coding agent（如 Claude Code）直接生成零依賴 HTML 檔案

這是我們在這個課程中會採用的方式。AI 根據你的需求直接產出完整的 HTML 投影片，不依賴任何框架或工具。

優勢 劣勢
最靈活：完全自由的設計和互動 需要自己管理投影片結構
零依賴：一個檔案就能運行 沒有內建的投影片管理功能
AI 可以直接修改和迭代 團隊協作需要額外機制

選擇的關鍵：看 Review 環節，不是 Generation 環節

這是一個重要的決策原則：

如果最終的投影片需要經過 AI 和非技術審閱者兩個環節，選擇工作流時應該看審閱環節，不是生成環節。首稿很少是最難的部分。最難的是首稿之後發生的事。

翻譯成白話：AI 生成第一版很容易。但之後呢？如果需要非技術同事審閱、修改、反饋，你就需要考慮他們能不能直接編輯你的產出。

需求 最佳選擇 原因
最大瀏覽器控制 Reveal.js 自訂運行時行為的功能最強
Markdown + 開發者工具 Slidev 撰寫速度快，AI 友好，匯出強
簡單撰寫 + 乾淨匯出 Marp 最低摩擦的 Markdown 工作流
快速模板化 HTML 故事 WebSlides 比手建更容易起步
完全客製的網頁投影片 Raw HTML/CSS 沒有框架限制

四個常見錯誤

錯誤 1：選了框架，但其實需要的是編輯器

Reveal.js 和 Slidev 解決了撰寫問題。但它們沒有解決審閱移交問題。如果投影片需要非技術人員編輯，要在開始之前就規劃好。

錯誤 2：以為匯出就是原生 PowerPoint

Marp 和 Slidev 可以匯出 PPTX，但匯出仍然是翻譯。Slidev 明確說明 PPTX 匯出用的是圖片。如果接收者需要在 PowerPoint 裡編輯文字、圖表、母版，就要從 PowerPoint 開始，或者在匯出前檢查物件結構。

錯誤 3：讓 AI 草稿成為最終版本

Claude、Codex 和其他 agent 非常擅長幫你做到第一版。但如果專案在那之後沒有穩定的編輯路徑，專案就會卡住。保持原始碼在本地、可讀、有結構。

錯誤 4：混用運行時目標

不要把 HTML 投影片用在所有場景。如果需要觀眾投票、課堂測驗控制、或企業投影片庫管理，那是不同的類別。HTML 投影片最強的時候，是瀏覽器本身就是產品介面。
