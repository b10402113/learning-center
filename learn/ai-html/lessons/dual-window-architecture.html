雙窗口同步架構

簡報模式 · Step 1/4

學習目標

能說出 BroadcastChannel 與 postMessage 在雙窗口簡報同步中各自的角色，並解釋 CURRENT/NEXT 兩個 iframe 如何以像素級精確度追蹤演示者視窗的導航狀態。

為什麼需要雙窗口？

投影片簡報有一個天然的矛盾：觀眾需要看到全螢幕、無干擾的投影片畫面；演示者卻需要看到下一頁預覽、講稿摘要和計時器。如果把這些控制元素放在同一個視窗裡，觀眾會看到你的提詞卡和倒數計時——這不是好的簡報體驗。

HTML 投影片的解法是打開兩個獨立的瀏覽器視窗。觀眾視窗維持全螢幕投影片，演示者視窗顯示控制面板。兩個視窗之間需要即時同步：演示者按下一頁，觀眾視窗立刻跟著跳。

核心思路：兩個視窗，各自渲染，透過瀏覽器原生 API 即時通訊。不需要伺服器、不需要 WebSocket、不需要第三方服務。

BroadcastChannel：跨視窗即時通訊

BroadcastChannel（廣播頻道）是瀏覽器提供的原生 API，讓同一個 Origin（協定 + 域名 + 埠號）下的所有視窗、Tab 和 iframe 能夠互相發送訊息。它的使用方式極其簡單：

// 在任何視窗中建立頻道（名稱必須一致）
const channel = new BroadcastChannel('presenter-sync');

// 發送訊息
channel.postMessage({ type: 'navigate', slideIndex: 3 });

// 接收訊息
channel.onmessage = (event) => {
  const { type, slideIndex } = event.data;
  if (type === 'navigate') {
    goTo(slideIndex);
  }
};

BroadcastChannel 的特點是廣播——你不需要知道對方是誰，只要在同一個 Origin 下、用了相同的頻道名稱，所有視窗都會收到訊息。這讓架構變得極簡：演示者視窗發一個 navigate 訊息，觀眾視窗自動收到並跳轉。

通訊方向多對多（廣播）一對一（點對點）

適用場景跨視窗狀態同步iframe 精確控制

postMessage：iframe 的精確導航

BroadcastChannel 適合「告訴另一個視窗該做什麼」，但有時候你需要更精確的控制——比如讓演示者視窗裡的一個 iframe 直接跳到第 5 張投影片。這時候用 postMessage。

演示者視圖裡有兩個 iframe（CURRENT 和 NEXT），它們分別載入同一份投影片 HTML，但加上了 ?preview=N 參數。這個參數讓 runtime 知道「現在是預覽模式」，只顯示第 N 張 slide，不顯示導航列和其他 chrome 元素。

// 演示者視窗：當前投影片 iframe
currentIframe.src = `./index.html?preview=${currentIndex}`;

// 透過 postMessage 通知 iframe 跳轉
currentIframe.contentWindow.postMessage(
  { type: 'navigate', slideIndex: currentIndex },
  '*'
);

// iframe 內部接收
window.onmessage = (event) => {
  if (event.data.type === 'navigate') {
    goTo(event.data.slideIndex);
  }
};

為什麼用 postMessage 而不是直接改 iframe 的 src？因為每次改 src 都會重新載入整份 HTML——所有動畫狀態、CSS transition 都會重置。用 postMessage 通知 iframe 內部的 runtime 做 goTo()，投影片的過渡動畫才會流暢銜接。

CURRENT / NEXT 雙 iframe 預覽

演示者視圖的左側有兩個 iframe，分別顯示：

卡片內容更新時機
CURRENT當前正在顯示的投影片演示者切頁時即時更新
NEXT下一張投影片的預覽跟著 CURRENT 同步更新

兩個 iframe 都以 1920×1080 的原始尺寸渲染，然後用 CSS transform 縮放到演示者面板的卡片大小。因為它們渲染的是同一份 HTML，所以投影片的排版、動畫、字型都和觀眾看到的完全一致——像素級精確。

?preview=N 模式的 runtime 行為有幾個關鍵差異：

  • 隱藏 deck-header、deck-footer、slide-number 等 chrome 元素
  • 不綁定鍵盤事件（避免演示者視窗的按鍵干擾投影片導航）
  • 只渲染第 N 張 slide，其他 slide 不進入 DOM（節省記憶體）

同步流程：從按鍵到畫面

把整條串起來，一次導航的完整流程是這樣的：

  1. 演示者在控制面板按下「下一頁」按鈕（或按鍵盤 →）
  2. 演示者 runtime 更新自己的 slide index，透過 goTo() 跳轉
  3. runtime 透過 BroadcastChannel 發送 { type: 'navigate', slideIndex: N }
  4. 觀眾視窗的 runtime 收到訊息，呼叫 goTo(N) 跳轉到同一張投影片
  5. 演示者 runtime 同時用 postMessage 更新 CURRENT 和NEXT 兩個 iframe
  6. 兩個 iframe 內的 runtime 收到 postMessage，分別渲染第 N 張和第 N+1 張投影片

整條鏈路不需要任何網路請求，全部在瀏覽器本地完成。延遲接近零——使用者體感是「按下去就跳了」。

觀眾視窗斷線與重連

實場簡報有一個常見問題：演示者打開了簡報模式，但觀眾視窗還沒開。或者觀眾視窗意外關閉了。BroadcastChannel 的處理方式很優雅：

  • 觀眾後開：觀眾視窗打開後，runtime 建立 BroadcastChannel 並發送一個 sync 請求。演示者視窗收到後，把當前 slide index 廣播回去。觀眾視窗自動跳到正確位置。
  • 觀眾重開：和「後開」一樣——重新建立頻道，重新 sync。不需要演示者做任何操作。
  • 演示者重開：演示者視窗發送 sync 訊息，所有觀眾視窗收到後跳到演示者的當前位置。
這就是 BroadcastChannel 的優勢：你不需要管理連線狀態，不需要處理 session。任何視窗隨時加入、隨時離開，sync 訊息自動讓所有視窗回到一致狀態。

預覽模式的 iframe 隔離

?preview=N 不只是「只顯示第 N 張」——它啟動了一個完全不同的 runtime 模式。iframe 裡的 JS 會偵測 URL 參數，進入預覽模式：

// runtime.js 裡的預覽模式偵測
const params = new URLSearchParams(window.location.search);
const previewIndex = params.get('preview');

if (previewIndex !== null) {
  // 預覽模式：隱藏 chrome、不綁定鍵盤、只渲染指定 slide
  document.body.classList.add('single');
  goTo(parseInt(previewIndex, 10));
  return; // 不繼續初始化完整 runtime
}

body.single class 觸發 CSS 規則，隱藏所有導航元素。runtime 在 goTo() 後直接 return，不綁定鍵盤事件。這樣演示者視窗的鍵盤操作不會「穿透」到 iframe 裡面干擾投影片。

小結：兩種 API，一個目標

BroadcastChannel 和 postMessage 解決的是同一個問題的不同層面：

問題解法原因
演示者 → 觀眾視窗的導航同步BroadcastChannel不需要知道觀眾視窗的 reference，廣播即可
演示者 → iframe 內的精確控制postMessage需要直接控制 iframe 內部的 runtime 狀態
觀眾後開 / 斷線重連BroadcastChannel sync自動廣播當前狀態，新加入的視窗自動同步

不需要伺服器、不需要 WebSocket、不需要第三方服務。兩個瀏覽器原生 API，就能做出專業級的雙窗口簡報同步。
