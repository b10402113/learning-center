兩層文件設計

投影片模板 · Step 2/3

Learning goal

能解釋 preview.md 與 design.md 的分工，以及 selection-index.json 如何驅動候選篩選。

每個模板的兩層文件

打開 bold-template-pack 的任何一個模板目錄，你會看到兩個文件：一個叫 preview.md，一個叫 design.md。這不是偶然——它們是一個刻意的兩層設計。

Preview.md：輕量風格卡片

preview.md 是一個「風格名片」。它的目的是讓代理在幾秒鐘內判斷這個模板是否適合當前的投影片。裡面包含：

  • 色票快照：主色、輔色、背景色的直覺描述（不是完整 CSS 變數）
  • Signature moves：這個模板最顯著的視覺特徵（如「像素霓虹」或「襯線字大標題」）
  • Preview 規則：用這個模板生成標題頁預覽時的注意事項

Preview.md 的核心原則是：夠用就好，不要多。它不是用來生成完整投影片的，只是用來做「這個模板適不適合」的快速判斷。

Design.md：完整設計系統 Recipe

design.md 是這個模板的「完整藍圖」。裡面包含：

區塊內容
Color tokens完整的 CSS custom properties 定義
Typography scale每一級字型的字體、字重、字號、行高
Component grammar標題、段落、卡片、按鈕等元件的 CSS 規格
Spacing rhythm間距系統：padding、margin、gap 的倍數關係
Decorative vocabulary裝飾元素：線條、形狀、紋理的使用規則
CJK support中文排版的特殊處理（字號降級、行高調整）
Slide-type blueprints封面、內頁、結尾頁的 HTML 骨架

Design.md 是代理在生成完整投影片時才會讀取的文件。它足夠詳細，讓代理可以直接照著 recipe 生成 HTML——不需要再回去讀原始的 template.html。

selection-index.json：機器可讀的索引

在兩層文件之上，還有一層更輕量的索引：selection-index.json。這是一個 JSON 檔案，裡面是一個陣列，每個元素對應一個模板的元數據：

{
  "slug": "bold-poster",
  "name": "Bold Poster",
  "tagline": "Editorial poster aesthetic with massive Shrikhand display...",
  "mood": ["bold", "editorial", "loud", "confident"],
  "tone": ["dramatic", "graphic", "sharp", "intentional"],
  "formality": "medium",
  "density": "low",
  "scheme": "light",
  "best_for": "Anything that should land like a magazine cover...",
  "avoid_for": "Decks that need to communicate dense information...",
  "preview_md": "bold-template-pack/templates/bold-poster/preview.md",
  "design_md": "bold-template-pack/templates/bold-poster/design.md"
}

這個索引的設計目的是讓代理可以不讀任何 markdown 文件就完成初步篩選。它用結構化的欄位（mood、tone、formality、density、scheme）取代自由文字描述，讓代理可以用程式化的方式匹配。

三步篩選流程

完整的模板選擇流程是這樣的：

  1. 讀 index：載入 selection-index.json（~20KB），根據當前投影片的需求（formality、density、scheme）篩選出 2-3 個候選
  2. 讀 preview：只讀候選模板的 preview.md，生成標題頁預覽給使用者看
  3. 讀 design：使用者選定後，只讀那一個模板的 design.md，開始生成完整投影片

關鍵約束：每次只讀一個 design.md。不要一次載入所有模板的完整規格。這是 progressive-disclosure 的核心——先粗筛，再精讀，最後只深入一個。

為什麼要分兩層？

如果把 preview 和 design 合成一個文件，會發生什麼？每次篩選都要讀完整的设计系統 recipe，34 個模板就是 34 次完整讀取。這對 context window 的壓力很大，而且大部分資訊在篩選階段是不需要的。

分兩層的結果是：

階段讀取量目的
篩選~20KB（index）從 34 個中選 2-3 個候選
預覽~6KB（2-3 個 preview）生成標題頁給使用者看
生成~5-10KB（1 個 design）照 recipe 生成完整投影片

從頭到尾，代理只需要讀取 ~30KB 的資訊。如果是一次全讀，則是 ~200KB。這就是 progressive-disclosure 的威力。
