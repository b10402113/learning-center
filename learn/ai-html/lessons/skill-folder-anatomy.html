Skill 資料夾結構

ai-html · Agent Skill 架構 · Step 2/4

上一課我們知道了 agent skill 是什麼——一套給 AI 代理執行的結構化工作說明。這一課打開 skill 的資料夾，看看裡面每個檔案和目錄各自扮演什麼角色。

一個典型 Skill 的目錄結構

以 beautiful-article 為例，它的資料夾長這樣：

beautiful-article/
├── SKILL.md              ← 主工作流文件（代理要讀的核心文件）
├── manifest.json         ← 版本號、作者、發佈資訊
├── references/           ← 按需載入的參考文件
│   ├── harness.md
│   ├── article-types.md
│   ├── theme-selection.md
│   ├── layout.md
│   └── ...（共 18 份文件）
├── scripts/              ← 確定性操作腳本
│   ├── scaffold.sh
│   ├── html-to-pdf.sh
│   └── source-to-markdown.py
├── templates/            ← 預設輸出格式（Vite 專案骨架）
│   └── scaffold-template/
├── theme-profiles/       ← 主題合約（Markdown 格式）
│   ├── index.json
│   ├── tufte.md
│   └── ...（共 11 個主題）
└── assets/               ← 範本和靜態資源
    └── scaffold-template/

每個目錄的角色

SKILL.md — 工作流的心臟

這是代理打開 skill 後第一個（也可能唯一一個）讀的文件。它定義了整個工作流：有哪些階段、每個階段要做什麼、什麼時候可以進入下一個階段。SKILL.md 的設計哲學是「短而精」——它不把所有細節都寫進去，而是指向 references/ 裡的文件，讓代理按需載入。

references/ — 按需載入的知識庫

參考文件是 skill 的深度知識。每份文件對應工作流中的某個階段或某個判斷點。比如 beautiful-article 有 18 份 reference 文件，代理在「風格選擇」階段才載入 theme-selection.md，在「排版」階段才載入 layout.md。這種設計的關鍵是：代理不會在第一步就把所有 reference 讀完，而是隨著工作流推進逐步載入需要的部分。

scripts/ — 確定性操作

有些操作不該讓代理「即興發揮」——比如 scaffold 一個新的 Vite 專案、把 HTML 轉成 PDF、從 PDF 提取文字。這些確定性操作被寫成腳本（bash 或 Python），代理只需呼叫對應的腳本，不用自己決定怎麼做。

例如：scaffold.sh 一行指令就建立一個完整的 Vite + React + TypeScript 專案骨架，裡面已經包含了必要的配置和目錄結構。代理不用「思考」要建立哪些檔案——腳本已經決定了。

templates/ — 輸出格式的骨架

模板定義了輸出的預設格式。frontend-slides 的 templates/ 裡有一個完整的 Vite 專案骨架，包括 index.html、package.json、vite.config.ts 和 src/ 目錄。代理拿到模板後，只需要填入內容，不用從零開始搭建專案。

theme-profiles/ 或 themes/ — 設計系統

主題是可替換的設計合約。beautiful-article 用 Markdown 格式定義 11 個編輯主題（tufte、press、bayer 等），每個主題定義了配色、字型、間距和語氣。frontend-slides 則用 JSON + CSS 格式定義 34 個模板，每個模板有 preview.md（輕量風格卡）和 design.md（完整設計系統規格）。

manifest.json — 版本與發佈

記錄 skill 的名稱、版本號、作者、授權、以及從哪裡安裝。類似 npm 的 package.json，讓 skill 可以被版本化管理和發佈。

不同 Skill 的結構差異

不是每個 skill 都有全部目錄。結構取決於 skill 的複雜度：

SkillSKILL.mdreferences/scripts/templates/themes/
beautiful-article✓ 466 行✓ 18 份文件✓ 5 個腳本✓ Vite 骨架✓ 11 個主題
frontend-slides✓ 核心文件✓ 模板 pack✓ 3 個腳本✓ 34 個模板✓ 12 個預設
boring-video✓ 編排文件✓ 各階段規格———

boring-video 的結構最簡單——它沒有 templates 和 themes，因為它專注於「規劃」而不是「產出視覺設計」。它的 references/ 裡放的是各階段（beats、narration、scenes、storyboard）的規格文件。

為什麼要這樣分層？

分層的核心目的是控制上下文佔用。AI 代理的上下文視窗是有限資源。如果把所有文件都塞進去：

  1. 上下文會被參考文件佔滿，代理沒空間做實際工作
  2. 代理會被不相關的資訊干擾，影響判斷品質
  3. 每次執行都要載入全部文件，浪費 token 和時間

分層之後，代理只需要在正確的時機載入正確的文件。SKILL.md 是入口，references/ 是按需載入的深度知識。這種設計讓一個複雜的 skill 也能在有限的上下文視窗中順利運作。
