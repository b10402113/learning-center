Progressive Disclosure 載入模式

ai-html · Agent Skill 架構 · Step 4/4

前三課我們看到了 skill 的定義、資料夾結構、和 SKILL.md 的工作流設計。這一課解決一個技術問題：當 skill 裡的參考文件很多很大時，怎麼讓代理有效地使用它們？答案是 Progressive Disclosure（漸進式揭露）——分層載入，按需取用。

為什麼不能一次全部載入？

假設 beautiful-article skill 有 18 份 reference 文件。如果代理在一開始就把全部 18 份文件讀進上下文：

  1. 上下文爆炸——18 份文件可能有數萬 token，直接佔滿上下文視窗，代理沒空間做實際工作
  2. 資訊過載——代理會被不相關的資訊干擾。在「來源提取」階段，它不需要知道「PDF 匯出」的規格
  3. 成本浪費——每次執行都要載入全部文件，即使 90% 在當前階段用不到

Progressive Disclosure 的解法是：把參考文件分成三層，代理只在需要的時候才載入更詳細的那一層。

三層載入架構

第一層：Index（索引）

最輕量的一層。代理一開始只讀 SKILL.md 裡的索引或摘要。比如 frontend-slides 的 selection-index.json 是一個 JSON 陣列，裡面有 34 個模板的元資料：名稱、標語、適用場景、避免使用場景。每個條目只有幾行，但足夠代理做初步篩選。

[
  {
    "slug": "bold-signal",
    "name": "Bold Signal",
    "tagline": "High-impact, minimal chrome",
    "mood": "confident",
    "best_for": "product launches, keynotes",
    "avoid_for": "academic, legal",
    "preview": "bold-signal/preview.md",
    "design": "bold-signal/design.md"
  },
  ...
]

代理讀完索引後，就知道有哪些候選，但還不知道具體長什麼樣。

第二層：Preview（預覽）

代理從索引中選出 2-3 個候選，然後載入它們的 preview.md。Preview 是一張輕量風格卡：配色快照、標誌性設計元素、適用場景。它足夠讓代理判斷「這個風格適不適合」，但不包含完整的設計規格。

frontend-slides 的預覽策略很聰明：從 34 個模板中選 1 個安全選項 + 1 個大膽選項 + 1 個野卡選項，然後用 preview.md 讓使用者快速比較。

第三層：Full Reference（完整參考）

使用者確認後，代理才載入對應的 design.md——完整的設計系統規格：配色、字型尺度、間距節奏、元件文法、CJK 支援、投影片類型藍圖。這是最大的文件，但只在確定使用後才載入。

實際流程圖

SKILL.md (入口)
  │
  ├── 載入 selection-index.json (索引，~2KB)
  │     │
  │     ├── 篩選 3 個候選
  │     │
  │     ├── 載入候選 A 的 preview.md (~1KB)
  │     ├── 載入候選 B 的 preview.md (~1KB)
  │     └── 載入候選 C 的 preview.md (~1KB)
  │
  ├── 使用者選擇 → 候選 B
  │
  └── 載入候選 B 的 design.md (~8KB)
        │
        └── 按 design.md 生成內容

總共載入量：索引 2KB + 3 個 preview 3KB + 1 個 design 8KB = 13KB。相比一次載入 34 個 design.md（~272KB），節省了 95% 的上下文佔用。

Boring-video 的 Progressive Disclosure

boring-video 也使用這種模式，但它的三層不是模板索引，而是工作流階段：

層級載入時機內容
L1: SKILL.md一開始工作流階段劃分、intake 問題、產物鏈順序
L2: 階段 SKILL.md進入該階段時to-spec-beats、to-narration 等各階段的完整規格
L3: references/階段內判斷時hyperframes-capability-envelope.md、scene-format.md 等深度參考

比如代理在執行 to-scenes 階段時，才載入 references/hyperframes-capability-envelope.md 來判斷場景的可行性——因為在前面的 beats 和 narration 階段，這個文件完全用不到。

Progressive Disclosure 的設計原則

1. 每一層都要有足夠資訊做判斷

索引要能讓代理篩選候選，preview 要能讓使用者做風格比較。如果某個層級資訊不足，代理就需要載入更多文件，progressive disclosure 就失效了。

2. 上一層的產出決定下一層的輸入

索引篩選出候選 → preview 決定最終選擇 → design 指導生成。每一步的產出是下一步的輸入，不能跳過。

3. 只在確定後才載入大文件

完整參考（design.md、harness.md）是最重量級的文件，只在使用者確認後才載入。這確保了上下文始終保持在可控範圍內。
