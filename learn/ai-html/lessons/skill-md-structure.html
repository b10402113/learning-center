SKILL.md 工作流設計

ai-html · Agent Skill 架構 · Step 3/4

上一課我們看到了 skill 的資料夾結構。這一課深入 SKILL.md 本身——它是 skill 裡最重要的一份文件，也是代理執行時的「聖經」。我們要理解它的段落結構、非妥協規則、和引用文件載入策略。

SKILL.md 的段落結構

一份好的 SKILL.md 通常包含這幾個段落：

1. 角色與目標（Role & Goal）

開頭就定義：這個 skill 要做什麼？代理在這個 skill 裡扮演什麼角色？比如 frontend-slides 的開頭是「你是一位頂尖的設計工程師」——這不是廢話，它把代理的行為框架從「通用助手」切換到「設計專家」。

2. 工作流階段（Workflow Phases）

把整個任務拆成有序的階段。每個階段有：

  • 名稱——這一步要做什麼
  • 輸入——需要哪些資訊
  • 動作——具體執行什麼
  • 完成標準——什麼時候可以進入下一步

例如 beautiful-article 的工作流階段：

Phase 0: 來源提取 — 從 PDF/URL/截圖提取文字
Phase 1: 計畫撰寫 — 定義文章類型、受眾、主題、結構
Phase 2: 雙重確認 — 使用者確認計畫後才繼續
Phase 3: 建構 — 按計畫逐段寫作
Phase 4: 最終審查 — 檢查品質、引用、格式
Phase 5: 修復 — 修正審查發現的問題

3. 非妥協規則（Non-negotiable Rules）

這些是不能違反的規則，通常用粗體或特殊標記強調。它們確保每次執行的結果都在品質範圍內。

frontend-slides 的非妥協規則：

  • 舞台必須是固定 1920×1080——不能用百分比或 viewport 單位
  • 不能使用 CDN 連結——所有資源必須內聯
  • 必須是零依賴單檔輸出——一個 HTML 檔案包含所有 CSS 和 JS
  • 不能使用 display:none 切換投影片——必須用 visibility 和 opacity

為什麼要「非妥協」？因為 AI 代理有時會「聰明過頭」——它會嘗試優化、簡化、或「改進」你的規則。非妥協規則就是告訴它：這些是底線，不能動。

4. 引用文件策略（Reference Loading）

SKILL.md 不把所有參考內容直接寫進去，而是用引用的方式指向 references/ 裡的文件。代理在特定階段才載入對應的文件。

例如在 beautiful-article 中：

Phase 1 (計畫撰寫):
  → 載入 references/article-types.md（文章類型規格）
  → 載入 references/plan-template.md（計畫模板）

Phase 3 (建構):
  → 載入 references/section-build.md（段落建構規則）
  → 載入 references/component-policy.md（元件協議）

Phase 4 (審查):
  → 載入 references/review-checklist.md（審查清單）

5. 交付規格（Delivery Spec）

定義最終產出的格式、結構、和品質標準。比如 frontend-slides 的交付規格要求：單一 HTML 檔案、所有 CSS/JS 內聯、包含印刷樣式和 reduced-motion 支援。

Frontend-slides 的六階段工作流

frontend-slides 的 SKILL.md 是一個很好的例子。它的六階段設計展示了如何把一個複雜任務拆成可管理的步驟：

階段動作關鍵輸出
Phase 0: 偵測模式判斷使用者要投影片、還是從 PPT 轉換模式判定
Phase 1: 內容探索讀取來源材料，理解要呈現的內容內容大綱
Phase 2: 風格探索讀取 STYLE_PRESETS.md 和模板索引，選定視覺風格風格決定
Phase 3: 生成按模板和風格產生 HTML 投影片HTML 檔案
Phase 4: 交付確認產出符合規格，處理部署或分享可分享的連結
Phase 5: 分享/匯出PDF 匯出或其他格式轉換最終檔案

Boring-video 的四階段規劃管線

boring-video 的 SKILL.md 展示了另一種設計思路：規劃和產出分離。它有四個規劃階段，每個階段產出一份持久的文件：

beats      → BEATS.md      （內容架構：論點、證據、節奏）
narration  → NARRATION.md   （口語稿：一句話一個想法）
scenes     → SCENES.md      （視覺方向：物理空間表達抽象概念）
storyboard → STORYBOARD.md  （HyperFrames 生產規格）

關鍵設計：每個階段的產出是一份持久文件，不只是一個參數。後面的階段讀前面的文件，前面的階段不會被後面的階段修改。這種「不可變產出」的設計讓整個管線可預測、可審查、可回溯。

品質門檻（Quality Gates）

Skill 裡的品質門檻分兩種：

硬門檻（Hard Checkpoint）

必須通過才能進入下一步。使用者必須確認。比如 beautiful-article 的 Phase 2「雙重確認」——代理把計畫呈交給使用者，使用者確認後才能開始寫作。不能跳過。

軟門檻（Soft Gate）

代理自己檢查，通過就繼續。比如 frontend-slides 的風格探索階段——代理自動從 12 個預設中選一個最適合的，不需要使用者確認。
