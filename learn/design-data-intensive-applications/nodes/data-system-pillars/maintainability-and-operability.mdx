## Learning goal

理解維護成本為何佔軟體總成本的絕大部分，掌握 operability、simplicity、evolvability 三個設計原則如何系統性地降低長期負擔。

## Lesson

### 📝 維護成本為什麼遠超初次開發？

一個系統從上線到退役，你會發現初次開發花的時間和金額只是冰山一角。真正的成本大頭出現在之後的幾年：修 bug、加功能、重構舊碼、回應監管要求、遷移基礎設施、訓練新人接手。

業界普遍估計，軟體生命週期中 **70% 到 80% 的總成本花在維護上**，而不是原始開發。這不是團隊偷懶，而是需求會變、技術棧會老、人員會流動，系統必須在這些變動中持續運作。

所以設計一個資料系統時，最重要的判斷標準不是它初次上線時有多快或多炫，而是它能不能在未來幾年以合理的成本持續演化。

**DDIA 將這個目標拆成三個互相支撐的原則：**

| 原則 | 核心目標 |
|---|---|
| Operability | 讓系統容易操作 |
| Simplicity | 讓系統容易理解 |
| Evolvability | 讓系統容易改變 |

接下來我們一個一個拆解。

---

### 🔧 Operability — 好的設計救不了糟糕的操作

Operability 的核心想法很直覺：好的操作實踐可以繞過壞的軟體設計，但再好的設計也救不了糟糕的操作。一個系統的可操作性好不好，取決於**日常運維工作有多輕鬆**。

[[design-data-intensive-applications/operability|Operability]] 涵蓋四個面向：

1. **可觀測性** — 系統必須輸出有意義的指標、日誌和追蹤資訊。值班人員半夜三點收到告警時，能快速判斷問題出在哪裡，而不是盲人摸象。

2. **自動化** — 重複性高的人工步驟應該由腳本或基礎設施即程式碼（IaC）取代。每次手動操作都是一個人為失誤的機會。

3. **好的預設值與防呆機制** — 最常見的事故來源之一是配置錯誤。某人改了一個參數，沒注意到它在另一個環境會引發連鎖反應。把危險的配置設成不易觸及的預設值、加入校驗層，能大幅降低風險。

4. **清晰的操作手冊（runbook）** — 問題發生時，值班工程師需要一份逐步指引：正常的排查流程是什麼、常見的失敗模式長什麼樣、每一種情形下應該採取什麼行動。

#### ⚡️ 反面案例：配置釀災

假設某個分散式資料庫需要調整快取超時參數，預設值是 30 秒。管理團隊發現另一個叢集用 5 秒效果更好，於是在維護窗口手動改了。幾週後，有人在同一個參數上設了 300 秒——不巧這時候正好有一波流量高峰，舊的快取條目堆積導致記憶體爆掉，整個叢集服務中斷。

事後調查發現：根本原因不是某個特定的數字有問題，而是系統沒有對參數的合理範圍做校驗，也沒有在配置變更時自動觸發壓力測試。這種「配置釀災」的模式在真實世界中反覆出現，而它的根源幾乎都指向**可操作性的缺失**。

### 📝 Simplicity — 抽象是消除意外複雜度的最強武器

Simplicity 在這裡不是指系統的功能很少，而是指內部結構清晰到每個人都能輕易理解。

這裡有兩個關鍵概念要分清楚：

- **Essential complexity（有意為之的複雜度）** — 系統為什麼存在特定的限制或行為，這是問題本身的複雜度。
- **Accidental complexity（意外複雜度）** — 因為歷史包袱、語言限制或設計失誤而堆疊出來的複雜度。

[[design-data-intensive-applications/simplicity-and-abstraction|Simplicity]] 的目標是消除後者。

#### 💡 關聯模型：經典的抽象範例

資料庫世界中最經典的抽象是關聯模型（relational model）。在它問世之前，程式設計師必須手動管理指標、決定資料的物理儲存順序、撰寫遍歷邏輯。

關聯模型用「表」和「關係」的語言，把這些內部細節全部藏了起來：

- 使用者只需要用 SQL 聲明式地描述「我想要什麼」
- 查詢優化器負責決定「怎麼拿到它」

這不只是語法上的便利，而是一次**認知層級的跳躍**——從「如何遍歷」升級到「語意是什麼」。

#### 💡 Schema 保護的實務價值

這個原則同樣適用於資料序列化的選擇。用 JSON 或 CSV 傳遞資料看似直觀，但它們：

- 不提供欄位型別的保證
- 不防止拼寫錯誤
- 不支援結構化的版本演進

當你的系統只有一兩個消費者時，這些問題尚可忍受；當消費者擴展到幾十個服務時，沒有 schema 保護的格式就變成了一座脆弱的橋樑。

這正是 [[design-data-intensive-applications/simplicity-and-abstraction|抽象]] 在實務中的價值所在：它不只是減少程式碼行數，更是減少**需要同時在腦中運作的心智模型數量**。

### 🔧 Evolvability — 讓改變不再痛苦

[[design-data-intensive-applications/evolvability|Evolvability]] 衡量的是系統面對變更時的彈性。需求會改變，業務會轉型，技術棧會迭代——好的系統設計必須讓這些改變成為可預期、可控的事件，而不是一場災難。

#### ⚡️ Schema-on-write vs Schema-on-read

資料編碼格式是影響可演化性的關鍵因素。比較兩種經典策略：

| 策略 | 運作方式 | 優點 | 缺點 |
|---|---|---|---|
| Schema-on-write | 寫入前嚴格校驗結構 | 保障資料一致性 | 結構變更需同步修改所有寫入端 |
| Schema-on-read | 讀取時才校驗結構 | 寫入端不需事先知道完整結構 | 結構問題延遲到讀時才發現 |

這兩種策略各有取捨，共通點是：當資料的生命週期比任何一段程式碼都長時，你必須認真考慮結構演進的方式。

#### ⚡️ 編碼相容性：滾動部署的生死線

當一個序列化格式需要改版時（例如在 Protobuf 的 `.proto` 檔案中新增或刪除一個欄位），必須同時考慮：

- **向後相容（backward compatibility）** — 新版本的讀取器能正確處理舊版本寫入的資料。
- **向前相容（forward compatibility）** — 舊版本的讀取器遇到新格式時不會崩潰。

缺乏相容性保障的直接後果是滾動部署失敗。假設你正在部署新的 API 版本，新欄位 `user_preferences` 被加入了。如果舊版消費者遇到這個未知欄位時直接拋出異常，滾動部署就會在第一台新機器上線時觸發全站故障。

這不是假設性的風險，而是每個採用結構化資料格式的團隊都必須面對的現實考驗。

### 💡 三個原則如何互相支撐？

這三個原則不是孤立的檢查清單，而是一張互相關聯的網路：

- **可操作性好的系統**更容易在發生問題後恢復 → 降低了演化過程中的風險。
- **簡潔的系統**更容易理解 → 進而更容易正確地擴展 → 提升了演化速度。
- **易演化的系統**結構清晰、歷史包袱少 → 反過來降低了操作與維護的難度。

它們形成了一個正向循環。

最終的衡量標準不是某個抽象的「設計優雅度」，而是一個非常務實的問題：**當你接到新的需求時，你能在不製造更多技術債的前提下，以多快的速度把它交付出去？**

一個能持續回答「還行」的系統，才真正具備了長期的維護價值。
