<LearningGoal>
理解同步、非同步與半同步複製的取捨，能在不同業務場景下判斷該選擇哪種複製策略，並解釋為什麼分散式資料庫必須在寫入延遲、資料安全性與可用性之間做出權衡。
</LearningGoal>

## Lesson

當你向一個分散式資料庫寫入一筆資料時，這筆資料首先出現在一個節點上——領導者（Leader）。但分散式系統的核心承諾是：資料不會只存在於一台機器。領導者必須把這筆變更傳送到其他節點——跟隨者（Follower）——才能真正「安全」。

問題出在「真正安全」這四個字上。領導者把寫入寫到本地磁碟後，要等跟隨者也確認收到才算完成嗎？還是先把「寫入成功」回傳給使用者，背景再慢慢送？這個看似微小的時機差異，牽動了整個系統的延遲、可用性和資料安全性。它不是一個實作細節——它是分散式資料庫最核心的架構決策之一。

**同步複製（Synchronous Replication）** 是最直覺的做法：領導者收到寫入後，把變更轉發給跟隨者，然後「等待」。只有當至少一個跟隨者回傳確認——表示它已經把變更寫入本地儲存——領導者才向使用者回傳「寫入完成」。

流程是這樣的：

1. 使用者向領導者發送寫入請求。
2. 領導者把變更寫入本地磁碟，同時轉發給跟隨者。
3. 跟隨者寫入本地磁碟，回傳確認給領導者。
4. 領導者收到確認，向使用者回傳成功。

這意味著在步驟 4 完成之前，資料已經存在於至少兩個獨立節點上。即使領導者此刻崩潰，跟隨者手裡還有完整的資料。資料的安全性在回傳成功的那一刻就有了保障。

但代價立刻浮現。每一次寫入都要等網路來回（Round-trip）加上跟隨者的磁碟寫入時間。如果跟隨者在另一個資料中心——例如跨洲部署——光是光速傳播就要數十毫秒。如果跟隨者的磁碟是旋轉硬碟（HDD）而不是固態硬碟（SSD），磁碟寫入本身可能就要好幾毫秒。更糟的是，如果跟隨者宕機或網路中斷，領導者會「卡住」：它不知道該繼續等待還是放棄，整個寫入操作被阻塞。

實際場景中，假設你有一個部署在台北和東京的雙機房架構。使用者在台北寫入資料，領導者位於台北的資料中心，跟隨者在東京。台北到東京的網路延遲大約 30–50 毫秒（來回）。如果採用同步複製，每一次寫入都要多等這段時間。對於每秒處理數萬筆寫入的金融交易系統，這意味著吞吐量可能下降一個數量級。

**非同步複製（Asynchronous Replication）** 是另一個極端：領導者收到寫入後，寫入本地磁碟就立刻回傳成功，完全不等待跟隨者確認。跟隨者在背景持續接收變更，但領導者的回傳不受影響。

流程是這樣的：

1. 使用者向領導者發送寫入請求。
2. 領導者把變更寫入本地磁碟。
3. 領導者立刻向使用者回傳成功。
4. 領導者在背景把變更傳送到跟隨者。
5. 跟隨者收到後寫入本地。

寫入延遲降到最低——使用者只等領導者的本地磁碟寫入時間，通常是個位數毫秒。即使所有跟隨者都離線，領導者仍然可以獨立接受寫入，系統不會因為副本故障就停止服務。

但這裡有一個不可忽視的風險：如果領導者在步驟 3 和步驟 4 之間崩潰——也就是寫入已經回傳「成功」但跟隨者還沒收到——那筆資料就永遠消失了。使用者以為寫入成功了，實際上資料不存在於任何地方。

這不是理論上的假設。在大規模叢集中，硬體故障是統計上幾乎必然會發生的事。一個擁有數千台機器的資料中心，每天可能有數台機器故障。如果領導者在寫入後的毫秒級窗口內崩潰，非同步複製就會丟失資料。

<DecisionTable>

| 維度 | 同步複製 | 非同步複製 | 半同步複製 |
|---|---|---|---|
| **寫入延遲** | 高（等網路來回 + 跟隨者磁碟） | 最低（只等本地磁碟） | 中等（等一個跟隨者，其餘非同步） |
| **資料安全性** | 強（寫入成功 = 至少兩份副本） | 弱（領導者崩潰可能丟資料） | 中等（至少一份同步副本） |
| **可用性** | 低（跟隨者故障會阻塞寫入） | 高（跟隨者故障不影響寫入） | 中高（同步跟隨者故障時降級） |
| **複製延遲** | 零（寫入成功時副本已同步） | 有（跟隨者落後領導者一段時間） | 同步副本零延遲，非同步副本有延遲 |
| **典型延遲增加** | 數十毫秒（取決於網路距離） | 無額外延遲 | 一個跟隨者的延遲 |

</DecisionTable>

**半同步複製（Semi-synchronous Replication）** 是實務中最常見的折衷方案。它的核心想法很簡單：不要求「所有」跟隨者都同步確認，但要求「至少一個」跟隨者同步確認。其餘的跟隨者仍然以非同步方式接收變更。

流程是這樣的：

1. 使用者向領導者發送寫入請求。
2. 領導者把變更寫入本地磁碟，同時轉發給所有跟隨者。
3. 至少一個跟隨者寫入本地磁碟，回傳確認。
4. 領導者收到確認，向使用者回傳成功。
5. 其餘跟隨者在背景繼續接收變更。

這個方案保留了同步複製的安全網——寫入成功時，至少有一個跟隨者持有完整資料——同時避免了同步複製的最壞情況：不需要等待所有跟隨者，只需要等一個。在多數部署中，半同步的延遲開銷只是一個跟隨者的網路往返，而不是所有跟隨者中最慢的那個。

MySQL 的半同步複製（Semi-synchronous Replication）是一個經典實作。透過 `rpl_semi_sync_master_wait_for_slave_count` 參數，你可以指定需要多少個跟隨者確認才算完成。PostgreSQL 的同步複製則允許指定 `ANY` 或 `FIRST` 等模式，在安全性和效能之間提供彈性。

半同步有一個重要的降級機制：當唯一的同步跟隨者故障時，系統自動退化為非同步模式。這確保了即使安全網暫時消失，系統仍然可以繼續接受寫入，而不是完全停擺。等同步跟隨者恢復後，系統再切回半同步。

<Analogy>
想像你寄一封掛號信。同步複製就像：你必須等郵局打電話來說「收件人已經簽收」，你才能安心離開。非同步複製就像：你把信投入郵筒就走了，不確認有沒有送到。半同步複製就像：你堅持要一個人簽收回條，另一個人隨便寄——你確保至少有人收到了，但不等所有人。
</Analogy>

**最終一致性（Eventual Consistency）** 是非同步複製的自然結果，而不是一個額外的設定。選擇非同步複製，就等於選擇了最終一致性。

為什麼？因為跟隨者落後於領導者。在領導者寫入成功到跟隨者收到變更之間的時間窗口（複製延遲，Replication Lag），不同節點上的資料是不一致的。使用者如果從跟隨者讀取，可能看到舊資料。

這種不一致不是 bug，而是一個刻意的設計選擇。系統沒有保證「多久之後」所有副本會一致——它只說「最終會一致」。如果複製中斷了三分鐘，使用者就可能三分鐘看到舊資料。如果中斷了三小時，就是三小時。

最終一致性引發三種可觀測的異常：

- **讀回自己的寫入（Reading Your Own Writes）**：使用者寫入資料後立刻從跟隨者讀取，看到的是舊資料。新寫入還沒複製到該跟隨者。
- **單調讀取（Monotonic Reads）**：使用者兩次讀取之間，第一次從領導者讀到新資料，第二次從跟隨者讀到舊資料。看起來資料「倒退」了。
- **一致前綴讀取（Consistent Prefix Reads）**：跨分區的寫入以因果倒置的順序呈現。例如，先看到「訂單已建立」再看到「使用者下單」。

這些異常不是分散式系統的缺陷，而是你選擇非同步複製時必須接受的後果。如果你的業務不能容忍這些異常，你需要在上層建立更強的一致性保證——例如寫後讀一致性（Read-your-writes Consistency），讓使用者的讀取路由到領導者，或者使用單調讀取保證（Monotonic Reads）確保不會看到倒退的資料。

<WarningBox>
「最終」是一個模糊的保證。系統沒有承諾一秒、一分鐘、還是一小時內會一致。在正常運作時，複製延遲可能只有幾毫秒。但在網路中斷、機房切換、或跟隨者重建的場景中，「最終」可能意味著分鐘甚至小時級別的延遲。你不能假設「最終」等於「很快」。
</WarningBox>

<DecisionTree>

1. **你的資料能承受遺失嗎？**
   檢查業務性質：金融交易、訂單紀錄不能丟失；社群動態、暫存資料可以。
   → 不能丟失：強烈考慮同步或半同步。
   → 可以承受少量遺失：非同步可能是更好的選擇。

2. **你的寫入延遲預算有多少？**
   評估使用者對延遲的容忍度：即時交易系統通常要求個位數毫秒；批次處理系統可以接受數百毫秒。
   → 延遲預算低：非同步或半同步（只等一個跟隨者）。
   → 延遲預算高：同步複製是可選項。

3. **你的跟隨者分佈在哪裡？**
   考慮地理距離：同機房的跟隨者延遲低（< 1ms）；跨洲的跟隨者延遲高（50–300ms）。
   → 跟隨者在同機房：同步複製的延遲成本低。
   → 跟隨者跨洲：同步複製幾乎不可行，半同步是務實選擇。

4. **跟隨者故障時你能承受什麼？**
   評估降級策略：同步模式下跟隨者故障會阻塞寫入；非同步模式下跟隨者故障不影響寫入。
   → 不能阻塞寫入：半同步（自動降級）或非同步。
   → 可以短暫阻塞：同步複製。

</DecisionTree>

<KeyInsight>
同步、非同步和半同步不是「好、壞、折衷」的線性排列。它們是針對不同業務約束的最優解。金融系統選同步不是因為它「更安全」，而是因為它的業務不能承受資料遺失。社群平台選非同步不是因為它「不在乎資料」，而是因為它的業務不能承受寫入延遲。選擇哪種複製策略，取決於你的業務在「寫入延遲」、「資料安全性」和「可用性」這三個維度上的優先順序。
</KeyInsight>

從更巨觀的角度看，這三種複製策略反映了分散式系統設計中的一個根本張力。當網路不可靠時——而現實中的網路從來都不是完美的——你被迫在一致性（Consistency）與可用性（Availability）之間做出選擇。這正是 CAP 定理在實務中的體現。

同步複製選擇一致性：如果跟隨者無法確認，領導者就阻塞寫入，寧可犧牲可用性也不要資料不一致。非同步複製選擇可用性：領導者永遠不會被跟隨者阻塞，但接受資料可能不一致甚至遺失的風險。半同步則試圖在兩者之間找到平衡點——正常情況下維持同步的安全性，異常時降級為非同步的可用性。

實務上，大多數分散式資料庫不會讓使用者在三種模式之間做二選一。它們提供的是彈性的配置空間：你可以指定哪些跟隨者需要同步、多少個跟隨者確認才算完成、以及同步跟隨者故障時是否自動降級。例如 PostgreSQL 允許你用 `synchronous_standby_names` 指定特定的同步跟隨者；MySQL 的半同步複製讓你設定等待的跟隨者數量。這些配置反映了同一個工程智慧：不要求完美的同步，但確保至少有一個安全網。

最後要注意的是，複製策略的選擇不是一勞永逸的。同一個系統可能在不同階段使用不同的策略：初期為了快速迭代選非同步；資料量成長後加入半同步；關鍵業務路徑切換到同步。理解這三種策略的機制和取捨，讓你能根據業務需求動態調整，而不是被鎖死在一個不適合的選擇裡。
