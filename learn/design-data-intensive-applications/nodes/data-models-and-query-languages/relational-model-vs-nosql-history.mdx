# 關聯模型稱霸三十年與 NoSQL 運動：資料模型的歷史選擇

## Learning goal

能說出關聯模型為何統治資料庫領域三十年，以及 NoSQL 運動在什麼條件下打破了這個格局。

## Lesson

### 📝 資料模型：你選的格式，決定了你能做什麼

在挑資料庫之前，先搞清楚一個更底層的問題：**什麼是資料模型？**

一筆資料從真實世界走到硬碟裡，中間經過好幾層抽象（Abstraction）：

- 最底層：磁碟或記憶體上的位元組（Bytes）
- 中間層：通用資料模型（General-Purpose Data Model）——例如關聯表、JSON 文件、圖結構
- 上層：應用程式的物件
- 最頂層：真實世界的事物

每一層都隱藏了下方的複雜度。

**為什麼這很重要？** 資料模型不只決定你的資料「長什麼樣子」，它還決定了你的系統**能做什麼操作、什麼操作會很快、什麼操作會很痛苦**。選錯模型，某些查詢寫起來彆扭、效能出奇地差、每次需求變更都要大改程式碼。選對模型，這些問題根本不會出現。

過去半世紀，有兩種資料模型主導了這個選擇：[[learn/design-data-intensive-applications/elements/relational-model|關聯模型 (Relational Model)]] 和 2000 年代後興起的 [[learn/design-data-intensive-applications/elements/nosql-movement|NoSQL 運動 (NoSQL Movement)]]。我們從歷史脈絡入手，理解它們各自解決了什麼問題、又帶來了什麼新的取捨。

---

### ⚡ 關聯模型：一張表征服三十年

1970 年，Edgar F. Codd 提出了一個激進的想法：把資料組織成**簡單的元組（Tuple）集合**，沒有巢狀結構（Nested Structure），沒有手動存取路徑（Access Path）。

聽起來很平凡？我們看看之前的人在做什麼。

#### 🔧 之前的資料庫長什麼樣

在關聯模型之前，主流的資料組織方式有兩種：

| 模型 | 代表系統 | 特徵 | 致命問題 |
|------|----------|------|----------|
| 階層模型（Hierarchical Model） | IBM IMS（1968） | 樹狀結構，每筆記錄只有一個父節點 | 新增查詢就要改寫應用程式碼 |
| 網路模型（Network Model） | CODACYL | 允許多個父節點 | 程式師必須在磁碟上手動追蹤指標（Pointer） |

這帶來一個核心問題：**每新增一種查詢，就得改寫應用程式碼。**

想知道「所有年薪超過一百萬的員工」？你得親自寫一段程式碼，從某個根節點開始，沿著指標一條一條走訪，才能找出符合條件的記錄。這就是所謂的**導航式查詢（Navigational Query）**——你告訴電腦「怎麼走」，而不是「要什麼」。

#### 🔧 關聯模型做了什麼不一樣的事

關聯模型把所有資料平鋪在一張由列（Column）和行（Row）組成的二維表格上：

- 每一行是一個元組，代表一筆記錄
- 每一列代表一個屬性（Attribute）
- 整個表的結構由固定的綱要（Schema）定義——資料在寫入時就必須符合這個結構（Schema-on-Write）

你在 PostgreSQL 裡寫的每一張 `CREATE TABLE`、每一個 `INSERT INTO`，都是這個思想的直接體現。

但關聯模型真正革命性的突破，**不是「用表格存資料」**——這之前也有人做過。真正的突破有兩個：

**1. 宣告式查詢語言（Declarative Query Language）**

以 SQL 為例：

```sql
SELECT name, salary
FROM employees
WHERE salary > 1000000;
```

你只說了「要什麼」（What），完全沒說「怎麼取」（How）。

**2. 查詢優化器（Query Optimizer）**

資料庫會在背後分析多種可能的執行計畫（Execution Plan），考量索引（Index）、統計資料和成本模型，自動選擇最有效率的那一個。

**為什麼這兩個突破如此關鍵？** 你新增一個索引之後，不需要改寫任何程式碼，所有相關查詢都能自動受益。查詢優化器是建造一次、惠及所有應用的基礎設施。這才是關聯模型稱霸數十年的真正原因——**對比導航式查詢，每一種新查詢都需要工程師手動設計存取路徑。**

#### ⚡ 三十年的統治

從 1970 年代到 2000 年代，關聯模型統治了資料庫領域將近三十年。在此期間，階層模型、網路模型、物件資料庫（Object Database）、XML 資料庫輪番挑戰，每一次都掀起一陣風潮，但沒有一個真正取代 SQL。關聯模型的通用性太強了——它不只適用於最初的商業資料處理場景，還能泛化到絕大多數的資料儲存需求。

### 💡 物件關聯不匹配：文件模型為什麼回來了

在關聯模型與文件模型之間，存在一個深層的張力：物件導向編程（Object-Oriented Programming）中的資料結構天然是巢狀的——一個物件包含另一個物件，物件內部又有陣列。但關聯表是扁平的。這就是所謂的**物件關聯不匹配（Object-Relational Impedance Mismatch）**。

#### 🔧 履歷的例子：為什麼文件模型有吸引力

一份履歷（Résumé）天然就是層級結構：

- 一個人有多段工作經歷
- 有多個學歷
- 有多種聯絡方式

在關聯模型裡，你必須把這份履歷「拆碎」成多張表：

| 表名 | 存什麼 | 問題 |
|------|--------|------|
| 個人資料表 | 姓名、電話、地址 | 與工作經歷分開儲存 |
| 工作經歷表 | 公司、職位、年份 | 每次讀取都要做 Join |
| 學歷表 | 學校、學位、年份 | 多張表的查詢往往比單次查詢慢 |

文件模型（Document Model）的做法完全不同：它直接把整份履歷塞進一個 JSON 文件裡。巢狀結構完整保留，一次讀取就能拿到所有資料，**局部性（Locality）更好**。

#### 💡 但這種想法其實不新

1968 年 IBM 的 IMS（階層模型）做的事跟 JSON 幾乎一樣——資料以樹狀結構組織，一對多（One-to-Many）關係天然對應。CODASYL 網路模型更進一步，允許多個父節點，但也帶來了更複雜的手動指標追蹤。

關聯模型的洞見正在於此：**把所有資料平攤在表面上，讓查詢優化器自動決定存取路徑。** 不需要手動追蹤指標，不需要預設資料的存取順序。文件資料庫重新擁抱了巢狀結構，確實解決了一對多關係的局部性問題，但在多對多（Many-to-Many）關係上仍然面臨關聯模型早已克服的困難。

---

### 🚀 NoSQL 運動：四股力量的匯聚

2009 年，一個 Twitter 話標籤（Hashtag）——"#NoSQL"——催生了一場聚會，主題是開源、分散式（Distributed）、非關聯式資料庫。這個詞後來被重新詮釋為「Not Only SQL」（不只是 SQL），而非「No SQL」（沒有 SQL）。

這個名稱具有誤導性：它並不指涉某項特定技術，而是一組共享相似驅動力的資料庫系統的統稱。

NoSQL 運動背後有**四股力量**同時發力：

#### ⚡ 四大驅動力

| # | 驅動力 | 關聯模型的限制 | NoSQL 的回應 |
|---|--------|---------------|-------------|
| 1 | **更高的擴展性需求** | 傳統仰賴垂直擴展（Vertical Scaling）——升級單台機器的硬體 | 從設計之初就支援水平擴展（Horizontal Scaling），把負載分散到數百台機器 |
| 2 | **開源偏好** | 商業授權成本高 | MongoDB、Cassandra、Redis 等開源替代方案 |
| 3 | **特殊查詢需求** | 圖遍歷、巢狀文件、高頻寫入等場景表達困難 | 圖資料庫、文件資料庫、鍵值資料庫各司其職 |
| 4 | **對僵硬綱要的挫折** | Schema-on-Write 要求寫入前就定義好表結構 | Schema-on-Read——結構在讀取時才由應用程式解釋，更靈活 |

#### 🔧 四大主流 NoSQL 資料庫

這四股力量共同催生了多種主流資料庫：

- **MongoDB**：文件資料庫（Document Database）——處理半結構化內容
- **Cassandra**：寬列儲存（Wide-Column Store）——高吞吐量寫入
- **Neo4j**：圖資料庫（Graph Database）——人物關係遍歷
- **Redis**：鍵值資料庫（Key-Value Store）——高頻快取，例如暫存 session 或熱資料

你在日常開發中很可能已經用過 Redis 來暫存 session 或熱資料——這正是**「多語系持久化」（Polyglot Persistence）**思維的體現：用最適合的工具處理最適合的任務。

**為什麼這很重要？** 在一個系統中，文件資料庫處理半結構化內容、圖資料庫處理關係遍歷、鍵值資料庫處理快取，各司其職。這不是一個技術選型問題，而是一個架構哲學的轉變。

---

### 📊 沒有銀彈：兩個模型正在相互靠攏

但更有趣的是，關聯式與文件式資料庫正在**相互吸收對方的長處**：

- **PostgreSQL 9.3+** 已原生支援 JSON 欄位，讓開發者能在關聯式系統中使用文件式的靈活結構
- **MySQL 5.7+** 同樣加入了 JSON 支援
- **MongoDB** 等文件資料庫也在逐步加入 join 功能

兩種模型的邊界正在模糊。

**為什麼這很重要？** 因為在實際的系統設計中，你很少會遇到「只能選一個」的場景。理解每種模型的歷史脈絡和核心取捨，才能在面對具體問題時做出有根據的判斷：

- 什麼時候該用關聯表的正規化（Normalization）來消除資料重複
- 什麼時候該用文件的巢狀結構來換取更好的局部性

---

### 💡 這段歷史告訴我們什麼

關聯模型不是過時的遺跡，NoSQL 也不是關聯模型的替代品。它們各自的設計哲學回應了不同時代的問題，而它們的取捨至今仍是每一個資料密集型系統設計的起點。

**關鍵 takeaway：** 不要問「哪個比較好」，要問「在這個具體場景下，哪個模型的取捨最符合我的需求」。歷史已經證明，沒有任何一個模型能永遠稱霸——但它們留下的設計洞見，會一直指引你做出更好的判斷。
