## Problem Statement

在非同步複製（Asynchronous Replication）的資料庫中，副本收到新資料的時間各不相同。當使用者頻繁地發出讀取請求時，可能遇到一種反直覺的現象：第一次讀取看到了最新的資料，第二次讀取卻回到了較舊的版本——彷彿資料在「倒退」。例如，使用者更新了自己的個人簡介，第一次讀取確認更新成功，刷新頁面後卻看到了舊版簡介，再次刷新又看到新版。資料在讀者的視角中來回跳動，時間線被攪亂了。

這個問題的根源在於：每次讀取可能被路由到不同的副本，而不同副本的複製進度不一致。如果第一次請求落在一個已同步的副本上，第二次落在一個尚未同步的副本上，讀者就會「倒退」到過去。

## Why it matters

單調讀（Monotonic Reads）之所以重要，是因為它保障了使用者對資料變化的合理預期：一旦你看到了某個版本的資料，之後的讀取不應該回到更舊的版本。這個預期違反時，後果不只是困惑：

1. **使用者信任崩塌**：當使用者親眼確認了更新成功，隨後卻看到舊資料，他會質疑系統的可靠性。在金融、醫療等場景中，這種「倒退」可能導致使用者基於過時資料做出錯誤決策。
2. **應用程式邏輯出錯**：許多應用程式的業務邏輯假設「看到的資料只會前進」。如果資料倒退，_conditional update_（基於當前版本的條件寫入）可能覆蓋掉正確的值，造成資料損壞。
3. **除錯困難**：資料倒退的異常往往難以重現——它只在特定的副本組合和網路延遲條件下才會觸發，讓問題排查變成一場運氣遊戲。

單調讀是一種弱於強一致性（Strong Consistency）、但強於最終一致性（Eventual Consistency）的保證。它不要求所有副本在任何時刻都一致，只要求對同一個讀者而言，資料不會倒退。這是在效能和正確性之間的一個務實平衡。

## How it works

單調讀的核心機制是：**確保同一個使用者的所有讀取請求，始終被路由到同一個副本**。只要一個使用者的所有讀取都命中同一個副本，而該副本的複製是單調前進的（即新資料按到達順序被應用），那麼這個使用者看到的資料就不會倒退。

最常見的實現方式是**基於使用者 ID 的哈希路由**（Hash Routing by User ID）：

```
副本選擇 = hash(使用者 ID) % 副本數量
```

系統對每個使用者計算一個固定的哈希值，決定其讀取始終路由到哪一個副本。只要副本數量不變，同一個使用者的讀取每次都落在同一台機器上。

這種策略的代價是：

- **副本間負載不均**：某些使用者的讀取量可能遠高於其他使用者，導致被分配到的副本過載。系統通常需要在「足夠的一致性」和「足夠的負載均衡」之間取捨——例如，使用一致性哈希（Consistent Hashing）而非簡單的模運算來平滑分配。
- **副本故障時的回退**：當被指定的副本不可用時，系統必須將讀取轉移到其他副本，此時單調讀的保證會暫時中斷。但由於故障是短暫的，且新副本的複製進度通常不會落後太多，實務上的影響有限。
- **不等於強一致性**：單調讀只保證單個讀者內部的單調性，不要求所有讀者在同一時刻看到相同的快照。不同使用者之間仍可能看到不同版本的資料。

值得注意的是，如果系統已經採用「每個使用者固定一個領導者」的寫入策略（例如 sharded by user ID），那麼單調讀通常自然而然地得到滿足——因為該使用者的寫入和讀取都路由到同一個分片的同一個副本。

## In plain terms

想像你在看電視上的新聞跑馬燈。正常情況下，新聞是一條一條往前播的——你先看到第 1 條，再看到第 2 條，再看到第 3 條。但如果電視機偶爾會「跳台」切到另一個訊號源，你可能先看到第 3 條新聞，然後跳回第 1 條，再跳到第 2 條。新聞的順序被搞亂了，你看得一頭霧水。

單調讀就像讓你的電視機永遠鎖在同一個訊號源——你看到的新聞只會往前播，不會倒退。不同的觀眾可以看不同的訊號源（不同副本），但每個觀眾自己的節目是單調前進的。

## Practical use

- **使用者設定頁面**：使用者修改密碼或個人資料後，重新整理頁面時不應該看到舊版。單調讀確保同一使用者的讀取始終看到最新的更新，不會在多次重新整理之間來回跳動。
- **購物車和訂單狀態**：使用者下單後查看訂單狀態，不應該看到「已付款」回到「待付款」。單調讀讓狀態只往前流動。
- **聊天訊息**：在分散式聊天系統中，使用者不应该在看到新訊息後，重新整理又回到舊訊息。單調讀保證訊息列表只會前進。
- **版本控制系統**：在使用多副本的 Git-like 系統中，單調讀確保你看到的 commit 歷史不會「倒退」——你看到的最新 commit 永遠比之前看到的更新。

### 實作上的取捨

在實務中，單調讀通常不需要顯式實作——它往往作為其他設計決策的副作用而自然出現。例如，如果你的系統已經按使用者 ID 分片（shard），每個使用者的寫入和讀取都路由到同一個分片，那麼單調讀就自動得到了滿足。

如果你的系統沒有按使用者分片，但需要單調讀的保證，最簡單的做法是為每個使用者維護一個「上次讀取的副本」的記錄。使用者的下一次讀取強制路由到那個副本。這種做法的代價是增加了路由的狀態管理，但換來了單調性的保證。

在效能敏感的場景中，可以考慮**副本複製延遲的監控**。如果某個副本的複製延遲過大，系統可以主動將該使用者的讀取路由到其他更新的副本上——但要注意，這會打破單調讀的保證，需要在「單調性」和「讀取新鮮度」之間做出明確的取捨。

## Connections

- [[learn/design-data-intensive-applications/elements/eventual-consistency|最終一致性 (Eventual Consistency)]]：單調讀是介於最終一致性和強一致性之間的一種保證。最終一致性只承諾「最終會一致」，但不保證順序；單調讀在此基礎上增加了「不會倒退」的約束。
- [[learn/design-data-intensive-applications/elements/reading-your-own-writes|讀回自己的寫入 (Reading Your Own Writes)]]：讀回自己的寫入保證你能看到自己寫入的最新資料；單調讀則保證你看到的所有資料都不會倒退。兩者解決的問題不同，但都與複製延遲直接相關。
- [[learn/design-data-intensive-applications/elements/consistent-prefix-reads|一致前綴讀取 (Consistent Prefix Reads)]]：一致前綴讀取保證因果順序不被違反；單調讀則只保證單個讀者內部的時間單調性。兩者在分區式架構中各自解決不同的一致性問題。

## Deep dive

單調讀的實現看似簡單——只要把同一個使用者的所有讀取路由到同一個副本就行了。但魔鬼在於「副本數量變動」這個場景。

當系統需要水平擴展（scale out）而新增副本時，一致性哈希（Consistent Hashing）的環會重新分配，部分使用者的讀取會從舊副本遷移到新副本。如果新副本的複製進度落後於舊副本，這些使用者在遷移瞬間可能看到較舊的資料——單調讀的保證被短暫打破。要避免這種情況，系統需要在新副本完全追上之後才將使用者遷移過去，或者在遷移時先將新副本的複製延遲降到可接受的範圍。

更深層的問題是：**單調讀和負載均衡天然矛盾**。單調讀要求把使用者固定在一個副本上，但負載均衡要求在副本之間分散流量。在實際系統中，這兩者之間的取捨往往是動態的——系統可以容忍輕微的負載不均來換取單調性，但在流量尖峰時可能不得不違反單調讀的保證以避免單一副本過載。這種「有條件的保證」在大多數實際系統中比「無條件的保證」更常見。

另一個值得深思的面向是：**單調讀是否足夠？** 對於許多應用來說，僅僅「不倒退」是不夠的——你可能需要同時看到「自己剛才寫入的資料」（讀回自己的寫入）或「所有相關寫入的因果順序」（一致前綴讀取）。單調讀解決的是一個特定的問題，而不是一致性問題的全貌。在設計系統時，應該明確判斷你需要的到底是哪一級的一致性保證，而不是混淆不同的模型。

## Questions

1. 為什麼把同一個使用者的所有讀取路由到同一個副本就能實現單調讀？如果副本的複製是單調前進的，這個機制還需要額外處理什麼場景？（提示：想想副本故障或副本數量變動時會發生什麼。）

2. 單調讀（Monotonic Reads）和讀回自己的寫入（Reading Your Own Writes）各自解決了什麼問題？一個系統能否只滿足其中一個而不滿足另一個？（提示：讀回自己的寫入關注「看到自己的寫入」，單調讀關注「不倒退」。）

3. 在分區式架構中，單調讀和負載均衡之間的矛盾如何體現？系統設計者通常如何在兩者之間取捨？（提示：想想把使用者固定在一個副本上的代價。）
