# Fault 與 Failure 的區別

## Problem Statement

工程師日常用語中，「系統出問題了」這句話其實把兩件截然不同的事混為一談：某個零件偏離了規格（fault），和整個系統停止服務（failure）。這兩個詞在英文裡長得像、日常對話裡常常互換，但在系統設計的語境裡它們的含義天差地遠。如果你分不清這兩個概念，你就沒辦法正確地推理「系統能不能承受某個異常」，而「容錯」（fault tolerance）這個詞也會變成一句空話。整本 DDIA 從頭到尾談可靠性，根基就是先把這兩個詞掰開。

## Why it matters

區分 fault 和 failure 不是文字遊戲，它直接決定你問的問題對不對。當某個磁碟壞了，你該問的是「這個 fault 有沒有導致 failure？」——而不是急著去修那個磁碟。因為好的系統設計就是讓單點故障（fault）不蔓延成系統癱瘓（failure）。你會看到 replication（複製）、consensus（共識）、error detection（錯誤偵測）這些機制，它們的共同目的都是在同一個地方：攔截 fault，不讓它升級成 failure。如果你把兩者混在一起，你就會把所有異常都當成「系統壞了」，然後在不該加冗餘的地方加冗餘，或在該加冗餘的地方漏掉。

## How it works

**Fault**：系統中某一個元件偏離了它被設計的規格。磁碟回傳讀取錯誤、網路封包在傳輸途中被丟棄、軟體 bug 導致某個節點 crash——這些都是 fault。Fault 是預期之內的、常態的，在大規模系統（上萬顆磁碟、上千個節點）的環境下，fault 不是偶發事件，而是每天都在發生的常態。

**Failure**：整個系統偏離了它對外承諾的服務規格。使用者打不开頁面、資料讀不到、寫入的資料丟了——這些才是 failure。Failure 是我們真正想預防的東西。

用三個具體例子來看兩者的邊界：

- 一個 RAID 陣列裡某顆磁碟壞了，這是 fault；但 RAID 陣列繼續正常讀寫，使用者感覺不到任何異常——沒有 failure。
- 一個軟體 bug 導致所有副本（replica）同時 crash，這是 failure。因為所有副本都跑同樣的程式碼，一個 bug 會同時打垮全部副本，這不是單點 fault，而是系統性的 failure。
- 一個網路分割（network partition）把叢集切成兩半，這是 fault；但只要系統的設計能在分割的兩側各自正確地處理讀寫請求，就沒有 failure。

關鍵洞察：**Fault 是常態，Failure 是我們要防止的結果。工程師的挑戰不是「消除 fault」，而是「讓 fault 不會變成 failure」。** 這句話是整本書可靠性的總綱。

## In plain terms

白話講，「壞掉」有兩種層次：某個零件出問題（fault），和整個系統掛掉（failure）。好的系統設計就是讓零件壞了系統照跑。硬體壞了有備援、節點掛了有副本、網路斷了有重試——這些都是在零件層級攔截 fault，不讓它往上蔓延成使用者感受到的 failure。

## Analogy

一家餐廳有 10 個廚師。一個廚師請假是 fault——個別異常，餐廳照常營業不是 failure。但如果所有廚師同時食物中毒，那就是 failure——整個餐廳沒辦法出餐了。好的系統就像有備份廚師的餐廳：個別廚師請假不影響服務，但如果你的菜單上有一道菜只能由一個特定廚師做（單點依賴），那他請假就真的會出問題。

## Practical use

在設計討論中，聽到「系統掛了」要先追問：「是哪個 component 出了 fault？還是整個 system failure？」這個追問直接決定你要修的是單點容錯還是全局設計。如果只是一個磁碟壞了，加 RAID 或副本就夠了；如果是所有副本同時 crash，你面對的是一個 correlated fault（關聯性故障），需要從程式碼層級去修，加再多副本都沒用。同樣的「系統出問題」，背後的根因和解法完全不同，分不清這兩個層次就會修錯地方。

## Deep dive

Fault 和 failure 的區別在可靠性工程裡有正式定義。Fault 是一個元件偏離其規格的狀態；failure 是整個系統偏離其服務規格的狀態。兩者之間的落差，正是 fault-tolerance engineering（容錯工程）的生存空間。

在大規模系統（一萬顆硬碟、一千個節點）的環境下，fault 不是罕見事件，而是每天都在發生的常態。硬體故障通常是不關聯的（uncorrelated）——一顆磁碟壞了不代表隔壁那顆也會壞。但軟體故障是高度關聯的（correlated）——同一個 bug 會同時打垮所有跑同樣程式碼的節點，這才是最危險的場景。2012 年 Linux kernel 的 leap-second bug 就是一個典型案例：一個軟體 fault 同時在全世界大量伺服器上觸發了 failure，因為所有伺服器跑的是同一份 kernel 程式碼。

工程上的核心挑戰在於：你不能假設 fault 不會發生，你只能假設它一定會發生，然後設計系統讓它不蔓延成 failure。這就是為什麼 replication、health checks、graceful degradation、circuit breakers 這些機制如此重要——它們不是在修 fault，而是在 fault 和 failure 之間築起一道牆。
