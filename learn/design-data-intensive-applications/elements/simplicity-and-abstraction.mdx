## Problem Statement
系統隨規模增長，偶然複雜度（accidental complexity）會層層堆疊——多種工具並存、workaround 套 workaround、假設從未被文件化。若不刻意做簡化，系統會複雜到沒有人能完全理解它，任何修改都變成高風險操作。

## Why it matters
複雜度是可靠性的頭號敵人。系統越複雜，可能失敗的方式越多，debug 越困難，新工程師上手越慢。透過抽象來簡化，是管理複雜度最有效的手段。

## How it works
複雜度分兩種：

- **本質複雜度（essential complexity）**：問題本身固有的。資料庫必須處理並發存取——這是問題本身的複雜度，無法消除。
- **偶然複雜度（accidental complexity）**：解決方案引入的。明明一個 store 就夠，卻用了五個；標準序列化格式夠用，卻自己造輪子寫了一套。

**抽象（abstraction）**把偶然複雜度藏在乾淨的介面背後。SQL 查詢隱藏了儲存引擎的細節、查詢最佳化器、執行計畫。檔案系統 API 隱藏了磁碟區塊管理、片段化、快取機制。

好的抽象有兩個共同特性：

1. 它們把大量實作細節封裝在一個簡單介面後面。
2. 它們是通用的——在多種不同場景下都有用。

關聯式模型就是典範：一個簡單的介面（tables、rows、SQL）隱藏了巨大的複雜度（查詢最佳化、索引、並發控制、崩潰復原）。抽象只建一次，所有應用程式都受惠。

實務上的簡化策略：

- **刪程式碼**：最好的程式碼是不存在的程式碼。移除已死的功能、沒人用的設定選項、 workaround 路徑。
- **減少元件數量**：技術棧裡的每一個 tool 都是複雜度的潛在來源。tool 越少＝互動越少＝越容易理解。
- **減少概念數量**：一個有 3 種節點類型的系統，比有 12 種的簡單得多。

## In plain terms
簡潔不是「寫很少的程式碼」，而是「不讓偶然複雜度侵入系統」。好的抽象像 SQL——用簡單的介面包住巨大的複雜度，讓使用者不需要理解底層細節就能正確使用。

## Analogy
遙控器是最直覺的例子。一個有 50 個按鈕的遙控器（accidental complexity）讓你連開電視都要找半天。一個只有 5 個按鈕的遙控器（好的 abstraction）讓你馬上知道怎麼用。設計系統也一樣——介面越簡潔，使用者（和維護者）越不容易犯錯。

## Practical use
在 code review 中問：「這段邏輯能不能用一個更簡單的方式表達？」在架構討論中問：「我們真的需要這個額外的 tool 嗎？」定期做 complexity audit——列出系統中的所有 tool 和概念，問每一個「如果拿掉會怎樣？」

## Deep dive
關聯式模型的成功，本質上是一個抽象的故事。在 Codd 提出關聯式模型之前，網路模型（CODASYL）要求程式設計師手動導航磁碟上的指標式存取路徑——每條查詢都要指定確切的遍歷順序。關聯式模型的突破在於讓存取路徑自動化：你只宣告要什麼資料（SQL），查詢最佳化器負責決定怎麼取。這個單一抽象消除了每一個應用程式中一大類的偶然複雜度。

諷刺的是，NoSQL 系統往往重新發明了這類複雜度——MongoDB 的 aggregation pipeline、Cassandra 的 CQL——逐漸發現關聯式模型的抽象當初為什麼有價值。這正說明了一個好的抽象不是「限制自由」，而是「把本質複雜度留下，把偶然複雜度移除」。
