# 關聯模型 (Relational Model)

## Problem Statement

在關聯模型出現之前，資料主要透過階層模型（Hierarchical Model）與網路模型（Network Model）來儲存。階層模型以樹狀結構組織資料，每一筆記錄只有一個父節點；網路模型則允許多個父節點，但也帶來了更複雜的結構。兩者的共同痛點在於：**程式設計師必須手動定義存取路徑（Access Path）**。每當需要新增一種查詢模式時，就得改寫應用程式碼，在磁碟上來回追蹤指標（Pointer），逐一走訪節點才能取出資料。這代表新增查詢等於重寫程式，資料重複（Duplication）四處可見，而且沒有一套通用的方法能靈活地查詢異質資料。隨著業務需求快速變動，這種「存取路徑綁死在程式碼裡」的做法，嚴重阻礙了系統的可演進性（Evolvability）。

## Why it matters

關聯模型是所有現代資料模型的比較基準。無論是文件模型（Document Model）還是圖模型（Graph Data Model），它們的設計初衷都是在關聯模型的基礎上解決某些特定場景的不足。理解關聯模型的核心思想——**將資料的邏輯結構與物理存取路徑分離**——是做出正確資料模型選擇的前提。不了解關聯模型，就無法真正理解文件模型的取捨，也無法在不同技術之間做出有根據的判斷。

## How it works

關聯模型由 Edgar F. Codd 於 1970 年提出，其核心思想可以拆解為以下幾個關鍵概念：

**資料以關聯表（Relation）的形式組織。** 每個關聯表就是一張由列（Column）和行（Row）組成的二維表格。每一行稱為一個元組（Tuple），代表一筆資料記錄；每一列代表一個屬性（Attribute）。整個表的結構由固定的綱要（Schema）定義——在寫入時就嚴格檢查資料是否符合規範，這就是所謂的「寫入時定義綱要」（Schema-on-Write）。

**宣告式查詢語言（Declarative Query Language）。** SQL 是關聯模型最廣為人知的查詢語言。它的關鍵突破在於：你只需要**說出你想要什麼**（What），而不需要告訴資料庫**如何去取得**（How）。這與之前的導航式（Navigational）查詢形成鮮明對比——導航式查詢要求程式師手動指定資料的存取順序和路徑，而 SQL 讓你只需描述結果集的特徵，由資料庫自行決定最佳執行方式。

**查詢優化器（Query Optimizer）：自動決定存取路徑。** 這是關聯模型最革命性的突破。當你執行一條 SQL 查詢時，查詢優化器會分析多種可能的執行計畫（Execution Plan），考量索引（Index）、統計資料和成本模型，自動選擇最有效率的那一個。這代表：新增一個索引後，即使不改寫任何程式碼，所有相關查詢都能自動受益。程式師不再需要為每一種查詢手動設計存取路徑，這是關聯模型稱霸數十年的真正原因。

**正規化（Normalization）與外部鍵（Foreign Key）。** 關聯模型透過正規化原則來消除資料重複：一個實體的屬性只存在於一張表中，不同表之間透過外部鍵建立關聯。當需要組合多張表的資料時，就使用連結（Join）操作。這種做法確保了資料的一致性（Consistency），也讓更新資料時只需修改一處，而不需要在多個副本中同步。

## In plain terms

想像你要管理一家公司的所有員工資料。

在舊的階層模型中，每個部門有一個檔案櫃，員工資料只能放在所屬部門的櫃子裡。如果你想知道「所有年薪超過一百萬的員工」，你必須**親自打開每一個檔案櫃**，逐格搜尋——存取路徑完全取決於你知道資料放在哪裡。

關聯模型就像一個統一的大型資料庫系統：所有員工資料平鋪在一張大表上。你只需要說「找出年薪大於一百萬的員工」，系統會自己決定要全表掃描（Table Scan）還是走索引（Index Scan），不需要你操心資料的物理存放位置。

## Practical use

你已經有 PostgreSQL 的經驗——PostgreSQL 就是關聯模型的典型實作。你熟悉的 `CREATE TABLE`、`INSERT INTO`、`SELECT ... JOIN` 都是關聯模型的直接體現。PostgreSQL 的查詢優化器在你每次執行查詢時都在背後默默工作：它會決定是否使用索引、以什麼順序執行 Join、如何過濾結果集。MySQL 和 SQLite 同樣實作了關聯模型，它們之間的核心概念是一致的：固定的綱要、宣告式查詢、外部鍵約束。當你下次需要設計資料表時，回想關聯模型的正規化原則——問自己「這兩個欄位是否應該分開成兩張表，用外部鍵關聯？」

## Questions

### Q1. 關聯模型相較於之前的階層模型與網路模型，最根本的突破是什麼？
A1. 最根本的突破是**將存取路徑從程式碼中解放出來**。在階層模型和網路模型中，程式師必須手動追蹤指標來存取資料；關聯模型透過查詢優化器自動決定最佳執行計畫，程式師只需用宣告式語言描述想要的結果。這使得新增查詢不再需要改寫應用程式碼。

### Q2. 關聯模型的「寫入時定義綱要」（Schema-on-Write）意味著什麼？
A2. 意味著資料在寫入資料庫時就必須符合預先定義好的表結構（綱要）。每一列的資料型態、約束條件（如 NOT NULL、UNIQUE）都在寫入時被嚴格檢查。這與文件模型的「讀取時定義綱要」（Schema-on-Read）相反——後者在寫入時不檢查結構，而是在讀取時才解釋資料的含義。

### Q3. 關聯模型與文件模型在處理多對多（Many-to-Many）關係時有何差異？
A3. 關聯模型透過外部鍵（Foreign Key）和連結（Join）操作來處理多對多關係，這是它的強項。文件模型在處理多對多關係時則顯得吃力——它缺乏原生的 Join 支援，往往需要應用程式碼來模擬連結，或者忍受資料重複。這也是為什麼在高度互連的資料場景下，關聯模型仍然比文件模型更為適用。

### Q4. 為什麼說查詢優化器是關聯模型能稱霸數十年的關鍵？
A4. 因為查詢優化器只建造一次，就能惠及所有應用。當你為某個查詢新增一個索引時，不需要改寫任何程式碼，查詢優化器會自動判斷是否使用這個索引。這種「一次投資、持續受益」的抽象，使得系統的演進成本遠低於導航式資料模型——後者的每一種新查詢都需要工程師手動設計存取路徑。
