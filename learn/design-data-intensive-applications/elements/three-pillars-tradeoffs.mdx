## 問題陳述

Reliability（可靠性）、Scalability（可擴展性）、Maintainability（可維護性）是資料密集型系統的三大支柱。但它們並非獨立存在——對其中一個的優化往往會影響另外兩個。設計系統時，你該如何思考這些取捨？

## 為什麼重要

每一個架構決策都牽涉到三大支柱之間的取捨。選擇高可靠性的複製方案可能會犧牲可擴展性（同步複製速度慢）。選擇最大的彈性（schema-on-read）可能會犧牲可維護性（沒有 schema 強制約束）。理解這些取捨，才能讓你做出有意識的選擇，而非無意間的妥協。

## 運作方式

先回顧三大支柱：

1. **Reliability（可靠性）**：系統在遇到問題時（硬體故障、軟體 bug、人為錯誤）仍能持續正確運作。
2. **Scalability（可擴展性）**：系統能應對負載增加（更多流量、更多資料、更多使用者）。
3. **Maintainability（可維護性）**：系統易於運作、易於理解、也易於演進。

核心取捨模式：

**Reliability vs Scalability**：同步複製提供強一致性（高可靠性），但每次寫入都增加延遲（在寫入密集的工作負載中傷害可擴展性）。非同步複製更快（更好的可擴展性），但故障時有資料丟失的風險（較低的可靠性）。這是最根本的複製取捨，將在第五章深入探討。

**Reliability vs Maintainability**：更多冗餘（更多副本、更多容錯邏輯）提升可靠性，但也增加運維複雜度（更多需要監控的東西、更多可能出錯的環節）。有時候最簡單的可靠系統，恰恰是元件最少的那個。

**Scalability vs Maintainability**：水平擴展（shared-nothing 架構）能達成極高的吞吐量，但引入了分散式系統的複雜度——資料分割、跨節點一致性、部分故障處理。單節點系統更容易維護，但吞吐量有上限。

**「先垂直擴展，被迫再轉分散」的原則**：常見的智慧是先從垂直擴展開始（更簡單、更便宜、更少的動態元件），只在達到垂直天花板時才轉向水平擴展。這尊重了可維護性的支柱——不需要的複雜度不要提早引入。

這些取捨的實際案例：

- Amazon 每 100 毫秒延遲導致 1% 銷售損失 → 對營收關鍵路徑，reliability 和 scalability 必須維持在高水準
- Netflix 的 Chaos Monkey → 可靠性投資（刻意注入故障）增加了運維複雜度（影響 maintainability），但預防了更嚴重的停機事故
- 選擇 PostgreSQL 而非分散式資料庫 → 用 maintainability（更簡單的運作）換取 scalability（放棄單節點的限制）

## 通俗來說

三個支柱不是互相獨立的——強化其中一個往往會影響另外兩個。好的系統設計是在三者之間找到適合你場景的平衡點，而不是追求每一個都做到極致。

## 類比

想像一個三角形的三條邊——reliability、scalability、maintainability。拉長一條邊，另外兩條會縮短。你不能把三條邊都拉到無限長。設計系統就像在這個三角形裡找到最適合你需求的位置。

## 實務應用

在設計文件中，明確標註每個選擇影響哪個支柱。例如：「選擇同步複製提升 reliability，但增加 write latency 影響 scalability。」這讓團隊看到取捨，而不是只看到「這樣比較好」。

## 深入探索

三大支柱的框架是刻意簡化的——實際系統還有更多考量（安全性、成本、法規遵循、延遲）。但这三個支柱抓住了資料系統設計中最核心的工程張力。DDIA 的其餘章節，本質上就是帶你走一遍不同的技術（複製、分割、交易、批次與串流處理）如何在這些取捨之間航行。

舉例來說，第五章的複製（replication）章節，其實就是在探討 reliability vs scalability 的取捨。第九章的共識（consensus）章節，則是如何在不犧牲太多 scalability 的前提下達成 reliability。第十一章的串流處理（stream processing）章節，展示了批次處理和串流處理在三大支柱上做出了哪些不同的取捨。

在深入細節之前，先理解這個框架，能讓你在閱讀後續每一章時都有一副透鏡可以觀察。
