# 資料模型選擇框架 (Data Model Decision Framework)

## Problem Statement

關聯模型（Relational Model）、文件模型（Document Model）與圖模型（Graph Model）各有其結構優勢與限制。面對一個具體的應用場景，如何從三者中做出正確選擇？沒有放諸四海皆準的答案——資料模型的選擇取決於資料本身的形狀與其間的關聯方式。缺乏一套系統化的判斷框架，開發者往往依賴個人經驗或直覺，導致選型失當、後期重构成本高昂。

## Why it matters

這是整合節點（Node）中所有資料模型概念的統合元素（Synthesis Element）。能否做出有理有據的選擇，正是本節點的核心學習成果。掌握這套框架，等於掌握了把「書本知識」轉化為「工程決策」的能力——這才是資料密集型系統設計的真正價值。

## How it works

一套實用的資料模型選擇框架，應從以下五個維度進行評估：

### 維度一：資料形狀（Data Shape）

- **樹狀結構（Tree-Shaped / One-to-Many）**：資料自然地呈現「一對多」的層級關係，例如一篇文章下有多則留言、一個產品下有多張圖片。此時 **文件模型** 最為直覺，因為文件本身就是一棵自包含的樹。
- **高度互連（Highly Interconnected / Many-to-Many）**：實體之間的多對多關係非常普遍，例如社交網路中的好友關係、推薦系統中的興趣關聯。此時 **圖模型** 最為自然，因為邊（Edge）就是一等公民。
- **混合型（Mixed）**：資料同時包含清晰的層級與複雜的關聯。此時 **關聯模型** 透過正規化（Normalization）能有效處理多對多，或採用混合架構（Polyglot Persistence）。

### 維度二：關聯遍歷頻率（Relationship Traversal Frequency）

- **很少遍歷關聯**：查詢主要是對單一文件的鍵值查找，關聯查詢極少。→ 文件模型，充分利用其**資料局部性（Locality）**——相關資料在同一文件中，無需額外 JOIN。
- **頻繁遍歷關聯**：查詢經常需要沿著關係鏈行走（例如「我朋友的朋友中，誰喜歡爵士樂？」）。→ 圖模型（原生遍歷）或關聯模型（JOIN 操作）。

### 維度三：Schema 演進速度（Schema Evolution Speed）

- **快速變動**：業務初期，資料結構可能每週都在改變，不同記錄可能有不同欄位。→ **Schema-on-Read**（文件模型），寫入時不強制結構，讀取時再解釋。
- **穩定不變**：資料結構已經明確定義，欄位類型嚴格。→ **Schema-on-Write**（關聯模型），寫入時即驗證結構，確保資料一致性。

### 維度四：查詢模式（Query Patterns）

- **以鍵為主的查找（Key-Based Lookups）**：例如「取出 ID 為 123 的訂單」。→ 文件模型效率最高，因為資料與 ID 直接對應，無需索引跳轉。
- **複雜的 JOIN 與聚合（Complex JOINs & Aggregations）**：例如「每個類別的平均評分，並篩選出高於 4.5 分的」。→ 關聯模型的強項，JOIN 和 GROUP BY 是其核心能力。
- **變長遍歷（Variable-Length Traversals）**：例如「找出所有間接關聯的節點，深度不限」。→ 圖模型的 MATCH 語法（如 Cypher）能以簡潔語法表達任意深度的遍歷。

### 維度五：規模需求（Scale Requirements）

- **單節點可承載**：資料量在單機處理能力之內。→ 關聯模型通常最簡單、最可靠。
- **寫入密集、需水平擴展（Write-Heavy, Horizontal Scaling）**：例如每日數十億條日誌。→ 文件模型（如 MongoDB）或圖資料庫（如 Neo4j 的叢集模式）提供更好的分散式支援。

### 收斂現實（The Convergence Reality）

現代資料庫正在模糊界線。PostgreSQL 支援 JSONB 欄位，帶來了文件模型的彈性；MongoDB 加入了 $lookup 關聯查詢，補足了 JOIN 能力。因此，選擇時應以**主要工作負載（Primary Workload）**為準，再用另一個模型補充次要需求。

### 多語堅持久化（Polyglot Persistence）

在大型系統中，不同子系統使用不同資料模型已成為常態：訂單服務用關聯資料庫、商品內容用文件資料庫、推薦引擎用圖資料庫。這是務實的工程選擇，而非理論上的「最佳模型」之爭。

## In plain terms

選擇資料模型就像選擇交通工具：

- **轎車（關聯模型）**：適合大多數日常通勤，穩定、安全、用途廣泛。
- **皮卡車（文件模型）**：適合載運大量貨物（自包含文件），在特定場景下效率極高。
- **摩托車（圖模型）**：在擁擠的交通（高度互連的關聯）中最靈活、最快到達目的地。

哪種車最好？取決於你的路線，而不是哪種車「客觀上最強」。

## Practical use

### 場景一：電商商品目錄

商品有類別、評價、推薦關聯。若讀取為主（使用者瀏覽商品頁），**文件模型** 較佳——商品資料與評價打包在一起，一次查詢即可載入，局部性好。若需要複雜的跨商品分析（如「某類別下所有商品的平均評分」），則 **關聯模型** 的 JOIN 與聚合更合適。

### 場景二：社交網路

好友關係、動態消息流、推薦系統。關聯遍歷是核心操作（「我朋友的朋友中誰去了這個活動？」），**圖模型** 是最自然的選擇。社交圖譜的邊就是一等公民，遍歷效率遠超 JOIN。

### 場景三：內容管理系統（CMS）

文章、標籤、作者資訊。每篇文章是自包含的實體，標籤與作者是附屬資訊，跨文章關聯稀少。**文件模型** 最為直覺——一篇文章就是一個文件，包含所有相關內容。

## Questions

### Q1. 如果你的資料結構每週都在變化，且不同記錄可能有不同欄位，你會選擇哪個模型？為什麼？

A1. 選擇文件模型（Document Model），採用 Schema-on-Read 策略。因為文件模型在寫入時不強制結構，允許每筆記錄有不同的欄位組合；讀取時才解釋結構。這在業務初期或異質資料場景下提供了最大的彈性，避免了頻繁的 Schema Migration。

### Q2. 在一個社交網路應用中，核心功能是「查詢某用戶的三度好友中有相同興趣的人」，應選擇哪個模型？

A2. 選擇圖模型（Graph Model）。因為這是一個典型的變長遍歷（Variable-Length Traversal）問題，需要沿著好友關係鏈行走多層。圖資料庫的遍歷操作是原生支援的，效率遠高於關聯模型的多次 JOIN，也比文件模型的手動關聯處理更自然。

### Q3. 給定以下場景：一個新聞平台，文章與作者、標籤、評論之間有複雜的多對多關係，且需要頻繁執行「找出某標籤下所有文章的作者及其粉絲數」這類跨實體聚合查詢。你會推薦哪個模型？為什麼？

A3. 推薦關聯模型（Relational Model）。多對多關係是關聯模型的強項，透過正規化與外鍵可以清晰表達。此場景的核心需求是跨實體的 JOIN 與聚合（GROUP BY、COUNT），這正是關聯資料庫數十年來最成熟的操作。文件模型在處理跨文件聚合時效率低下，圖模型則不擅長數值聚合。

### Q4. 什麼是「多語堅持久化」（Polyglot Persistence）？在什麼情況下你會採用這種策略？

A4. 多語堅持久化是指在同一個系統中，針對不同子系統或不同工作負載，選用不同的資料模型和資料庫技術。例如訂單服務使用關聯資料庫（需要交易一致性），商品目錄使用文件資料庫（需要彈性結構與高效讀取），推薦引擎使用圖資料庫（需要關係遍歷）。當系統規模足夠大、各子系統的需求差異明顯時，這種策略能讓每個部分都用上最適合的工具，代價是增加了跨資料庫的一致性與維護成本。
