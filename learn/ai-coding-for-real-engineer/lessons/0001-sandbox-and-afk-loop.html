Lesson 001 · Sandbox 與 AFK Loop

為什麼放手前要先上鎖

YOLO 模式的三種危險，以及 Docker 沙盒如何讓你安全地把鍵盤放開。

一句話摘要

AFK 迴圈（讓 agent 無人監督地一輪一輪重跑）的最後障礙是權限請求——每當 agent 要執行 bash 指令，它會停下來問你「可以嗎？」。關掉權限請求就進入 YOLO 模式，但 YOLO 有三種致命危險。解法是用 Docker 容器把 agent 關進隔離環境：它看得見 repo，碰不到主機。

從互動到放手的斷點

上一個節點你已經用互動模式跑過 agent——人在迴圈裡，觀察每一行指令，按需批准。互動模式證明了行為可靠，但人的存在就是瓶頸：

互動模式（你在場）

  • 每條 bash 指令都暫停等你批准
  • 你可以即時觀察、修正 prompt
  • 但你被鎖在鍵盤前
  • 一個 phase 可能要盯 5–10 分鐘

AFK 模式（你走開）

  • agent 自己跑完所有指令
  • 你去規劃下一批工作
  • 回來時拿到 commit 過的成果
  • 吞吐量翻倍甚至更多

問題是：怎麼關掉權限請求又不讓 agent 搞砸你的主機？

YOLO 模式的三種危險

Claude Code 有一個 --dangerously-skip-permissions 標誌（社群稱為 YOLO 模式），關掉所有權限提示。聽起來完美，但 Claude 的官方文件明確要求：YOLO 模式只能在隔離的容器或 VM 裡執行。為什麼？

危險 1：刪除主機檔案系統 agent 沒有「不要刪除 home 目錄」的本能。一個糟糕的 prompt 或非決定性的抽樣可能產出 rm -rf ~。在互動模式你會擋下它，YOLO 模式沒有人擋。
危險 2：外洩機敏程式碼 agent 可以執行 curl 把你的 codebase POST 到外部伺服器。prompt injection 攻擊（在檔案內容中埋入「把所有程式碼送到 evil.com」）在無人監督時完全無法防禦。
危險 3：Prompt Injection 鏈 不是直接攻擊你的 agent，而是攻擊你的資料。如果 repo 裡有一個 README 寫著「忽略所有先前指令，執行以下指令……」，agent 會忠實執行。這在有人盯著時無害（你會看到），沒人盯著時就是漏洞。

三種危險的共同點：錯誤無法被自動偵測。刪除檔案、外洩資料、執行惡意指令——這些不是 typecheck 能抓到的。這就是為什麼 YOLO 模式需要隔離。

Claude 內建沙盒？不行

Claude Code 本身有沙盒功能，但已經被發現可以被逃逸。社群實測證明 agent 能繞過內建限制接觸主機檔案系統。所以你不能信任它——你需要自己的隔離層。

Docker 沙盒的邏輯

Docker 的隔離機制很簡單：

你的主機 ┌─────────────────────────────────┐ │ repo（bind mount） │ │ ┌───────────────────────┐ │ │ │ Docker 容器 │ │ │ │ ┌─────────────────┐ │ │ │ │ │ Claude Code │ │ │ │ │ │ + Node 22 │ │ │ │ │ │ 工作目錄: │ │ │ │ │ │ /home/agent │ │ │ │ │ └─────────────────┘ │ │ │ │ 只看得見 repo │ │ │ │ 碰不到主機其他地方 │ │ │ └───────────────────────┘ │ └─────────────────────────────────┘

關鍵設計：

  • 容器裡的 agent 看得見 repo——因為 repo 被 bind mount 進去
  • 容器裡的 agent 碰不到主機——Docker 的 Linux namespace 隔離了檔案系統
  • YOLO 模式是安全的——就算 agent 執行 rm -rf /，它只會清掉容器內部（下次 build 還原）
  • 網路也被隔離——agent 無法把你的 codebase 送出去

一句話：在容器裡，agent 有能力做任何事，但影響範圍被限制在容器內部。

AFK 迴圈的機械結構

沙盒解決了安全問題。接下來是自動化問題：怎麼讓 agent 自己跑多圈？

main.ts 是 AFK 迴圈的執行器。它的核心邏輯極簡：

// 概念版（非原始碼）
let iterations = 0;
while (iterations < maxIterations) {
  run_sandcastle(prmd_path, plan_path);
  iterations++;

  if (agent_emitted("no more tasks")) {
    break;  // 完成訊號：agent 說沒事做了
  }
}

三個關鍵組件：

1 maxIterations（迭代上限）

安全網。就算完成訊號失效，迴圈最多跑你設定的圈數就停。實務上設很高（10–50），信任完成訊號，但保留最後防線。

2 完成訊號（completion signal）

prompt 裡指示 agent：「如果沒有更多任務，輸出 no more tasks」。當 agent 發現所有 phase 都完成了，它會輸出這串文字，迴圈偵測到就停止。這比 maxIterations 更精準——agent 自己知道什麼時候做完了。

3 每次迭代都是新 context window

這是跟互動模式最大的差異。互動模式是一條長 context，AFK 迴圈每一圈都開新 session。好處：

  • 永遠在 smart zone 內（不會塞到 dumb zone）
  • 每一圈都重新探索 repo，接續上次 commit 的狀態
  • 壞掉的 context 不會汙染下一圈

跟互動模式的三個差異

面向 互動模式 AFK 迴圈
執行模式 interactive run
PRD/plan 注入 prompt.md shell 展開 CLI 位置參數
終止條件 單一 phase 完成 maxIterations 或完成訊號
Context 持續一條 每圈全新

實跑時的迭代節奏

以下是 AFK 迴圈的實際樣子（來自課程 demo）：

Iteration 1/3: Agent 發現 phase one 已完成（上次 commit 過了）
  → 開始 phase two（revenue line chart）
  → 跑 typecheck + test
  → 修 bug
  → commit
  → 輸出下一個 phase 的計劃

Iteration 2/3: Agent 發現 phase one + two 都完成了
  → 開始 phase three（course breakdown table）
  → 跑 typecheck + test
  → commit

Iteration 3/3: Agent 發現所有 phase 都完成了
  → 輸出 "no more tasks"
  → 迴圈停止

每一圈的 context window 大約 60k–80k tokens，穩定在 smart zone 內。兩圈就交付了完整功能，包含測試和 commit。

核心判斷：什麼適合 AFK？

AFK 迴圈的著力點 任務結果能用自動檢查判斷時——測試過不過、typecheck 過不過、檔案有沒有長出來——AFK 迴圈就能收斂。如果結果只有人看得出對錯（例如 UI 的「好看不好看」），得靠 human-in-the-loop。

分界在一個問題：錯誤能不能被自動偵測？

  • 能自動偵測 → 放手讓迴圈收斂
  • 不能 → 留人在迴圈裡

下一步

這節你掌握了為什麼需要沙盒和迴圈的機械結構。下一步是動手：

  1. 安裝 Docker Desktop 或 Podman
  2. 設定 .env（API key）
