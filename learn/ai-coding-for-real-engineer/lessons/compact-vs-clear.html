compact 與 clear：sediment 問題

Node 6 · context-economy · Step 3/4 · 看懂 auto-compact buffer，別讓沉澱層堆起來

Learning goal

說出 auto-compact buffer 的運作、重複 compact 的 sediment 問題，並在「什麼時候 clear、什麼時候 compact」之間做出正確選擇。

context 到底了會發生什麼：auto-compact buffer

敲 /context 會看到 context window 的尾端留著一段 auto-compact buffer——以 200k window 為例約 33k tokens（16.5%），這塊不用來放 token、不影響 LLM，它是個安全氣囊。一旦 context 越過線「撞進」這個區域，就自動執行 compact。

compact 在幹嘛

compact 是用一個 LLM 把對話濃縮成一小份 markdown 摘要。以課程裡 49% 的 session 為例，compact 後降到 12%（23k tokens）。摘要會：

  • 把主要檔案留在 context 裡，次要檔案只留引用
  • 保留所有 user messages 跟尚未完成的任務（連你塞給它的「為什麼要 compact」都會被保留下來）
  • 把完整 transcript 存成一個檔案，需要時可回去查

compact 本身要花 token（用 LLM 摘要很貴），但重新探索 repo 也要花 token——兩邊都不是免費的。

sediment：重複 compact 的隱形代價

那為什麼不乾脆讓 context 一直長、撞到 buffer 就 compact、然後再長再 compact、無限續命？因為每次 compact 都會在 context 裡留下一層「沉澱」（sediment）。撞一次留一層，層層疊加，用不可預測的方式影響輸出——帶著沉澱層的 agent 處在一種「跟平常不同的狀態」，輸出變得不穩定。

相反地，如果你優化流程、讓 agent 幾乎總是以乾淨的 context開局，輸出會更可預測、花更少 token（不用付 compact 的錢）、有更多時間待在 smart zone——整體 code quality 更高。因此重複 compact 被視為 anti-pattern。講師註明這是他的心智模型／觀點，但社群也普遍同意。

記住：你的目標是設計一個「永遠不需要 compact」的工作流，而不是學會在 compact 之間求生。

什麼時候該 compact，什麼時候該 clear

講師自己很少 compact，通常每個 conversation 最多一次，且只在兩種情況：

  1. 剛結束一個大 session，想追加一點 feedback——clear 會連已實作的脈絡一起丟掉，不划算。
  2. debug 複雜錯誤——context 裡堆滿了「試過什麼、失敗在哪」，clear 會全部歸零，compact 則能留著這些嘗試再往下試。

除此之外，寧可 clear 重來：花一次重新探索的錢，換一個乾淨、可預測的 context。
