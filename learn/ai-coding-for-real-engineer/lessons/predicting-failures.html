用這些約束預測 agent 何時會出錯

學習目標：綜合二次方擴張、dumb zone、不可靠記憶與非決定性四項約束，預測 agent 在哪些情況下容易出錯，並說出對應的防範方式。

四條約束回顧

這四課學到的四條約束，每一條都指向一種失敗模式：

約束一句話主要失敗模式
二次方擴張token 越多，注意力越貴context 越大，負擔越重
Dumb Zone塞太滿就變笨推理退化、幻覺、召回失敗
不可靠記憶＋無狀態參數是模糊 JPEG，且不持久編造事實、忘光過去
非決定性從機率分布抽樣同指令每次結果不同

單獨看是四個現象，合起來看是一張「出錯預測表」——你能在 agent 出錯之前猜到它會在哪些場景翻車。

用約束預測出錯場景

場景一：context 越塞越多，聊到一半變笨

預測：你一直 @ 檔案、貼需求、讓它跑工具，token 逼近 80k–100k，agent 開始忘掉早前的指令、開始編造、推理跳針。防範：盯 /context 或 status-line，逼近門檻就 /clear 或 compact；探索性工作丟給 sub-agent，別把主窗口灌滿。

場景二：它「記得」的專案事實不可信

預測：你問它「這個 migration 檔叫什麼」，它憑參數記憶編出一個聽起來合理的檔名——機率很高是錯的。或是拿一年前的舊知識回你。防範：需要精確的事實就 @ 參照檔案、把慣例寫進文件與 AGENTS.md，讓它讀而不是回想。

場景三：開新 session，它對專案一無所知

預測：agent 完全無狀態，換 session 或 /clear 後它什麼都不記得，可能重做你已經做過的事、提出與既有決定衝突的方案。防範：把知識放進 codebase 與文件（它每次都能重新讀到）；長任務用 handoff 或 /resume 延續，不要指望它自己記得。

場景四：結果跟上次或跟示範對不上

預測：同一個 prompt 跑兩次，走的軌跡不同，出來的程式或答案也不同；跟課程示範對不上尤其常見。防範：不期待逐字相同——用測試與 typecheck 驗證結果對不對，對的留下、錯的再修，讓不同軌跡收斂到同一個正確終點。

核心概念 出錯前的檢查清單： context 用量逼近 80k–100k 了嗎？需要的事實有放進 context 嗎？新 session 該重讀的檔案讀了嗎？結果有 feedback loop 在驗證嗎？四個問題對應四條約束。

把約束變成習慣

四條約束其實指向同一組好習慣：保持 context 精簡、把事實放進 context 與文件、用測試驗證而不是對照範本。當 agent 出錯時，別急著怪它，先問是哪條約束在背後起作用——診斷對了，防範就順理成章。這正是後續課程（context economy、exploration、feedback loops）每一招的出發點。
