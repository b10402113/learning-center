SQLite 與 Drizzle：資料庫如何與 code 同步

Node 1 · db-sync · schema 不會自動生效，你要親自把它推上去

Learning goal

解釋為什麼 schema 改了不會自動生效，用 generate → migrate 讓 migration 檔案與資料庫跟上 schema，並用刪 data.db + reseed 重置資料庫。

SQLite：一個檔案就是一個資料庫

Playground 用的是 SQLite，不是架在主機上的 Postgres。SQLite 把整個資料庫存在本地檔案裡（data.db，加上 data.db-shm 與 data.db-wal 這兩個配套檔）。這帶來一個好處：重置超容易——刪掉 data.db 再 seed 一次就好，因為全部都是假資料。

Drizzle：schema.ts 是 source of truth，但改它不會自動生效

課程用 Drizzle ORM 管資料庫。真正的 source of truth 是 schema.ts——你定義資料表的地方。但這裡有個反直覺的陷阱：

改了 schema.ts，資料庫不會自動跟上。 沒有什麼魔法同步。你要親手把變更推下去，而推下去需要兩步。

兩步：generate → migrate

步驟命令做什麼改了什麼
1. generatedb generate從 schema 產出 migration 檔案新增 migration 檔（程式碼世界）
2. migratedb migrate把 pending migration 套到資料庫真的動到 data.db（資料庫世界）

generate 產生的是「migration 檔案」——記錄 schema 變更的指令集；migrate 才把這些指令套進實際的資料庫檔案。跳過 migrate，你的 schema 和資料庫就處於不同步狀態。

為什麼這對 agent 特別重要

課程的實戰觀察：agent 通常會自己想到要 generate，但常常漏掉 migrate。 於是你會看到「agent 以為自己動了資料庫，其實沒有」的假象——schema 檔改了、migration 產了，但資料庫裡什麼都沒發生。所以當 agent 在碰資料庫時，你要主動確認 migrate 有沒有跑。這是你在 HITL 模式要盯的第一個點。

重置：刪 data.db + reseed

任何時候想把資料庫退回乾淨狀態：

rm data.db        # 刪掉 SQLite 檔案
pnpm db:seed      # 重新種假資料

因為都是 dummy data，刪掉重來完全沒有損失。這也意味著你不需要「逆向」改資料庫——搞砸了就直接重置。
