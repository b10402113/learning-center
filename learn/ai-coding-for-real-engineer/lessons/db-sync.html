SQLite 與 Drizzle：資料庫如何與 code 同步

Step 2/3 · 把環境跑起來

學習目標：解釋為什麼 schema 改了不會自動生效，用 generate → migrate 讓 migration 檔案與資料庫跟上 schema，並用刪 data.db + reseed 重置資料庫。

SQLite 是什麼

Playground 用的資料庫是 SQLite——一個「一個檔案就是一個資料庫」的輕量資料庫。在你的專案目錄裡，它由三個檔案組成：

檔案 作用
data.db 主資料庫檔案
data.db-shm 共享記憶體（SQLite 併發用）
data.db-wal 預寫式日誌（Write-Ahead Logging）

跟 Postgres 或 MySQL 不同，SQLite 不需要跑一個伺服器。它就是一個檔案，讀寫都在本地。這讓重置超級容易——刪掉 data.db 再 seed 一次就好。

Drizzle ORM 與 schema.ts

這門課不用裸 SQL，而是用 Drizzle ORM（Object-Relational Mapping）來定義資料庫結構。你在 schema.ts 裡用 TypeScript 定義資料表和欄位，Drizzle 把它們翻譯成 SQL。

schema.ts 是整個資料庫的 source of truth（唯一真相來源）。你想改資料庫結構，改的是這個檔案。

反模式：直接手動改 data.db 或手動跑 SQL。你的改動會在下次 seed 時被覆蓋，而且 schema.ts 跟資料庫會永遠不同步。

核心陷阱：改了不會自動生效

這是整堂課最重要的反直覺點：你改了 schema.ts，資料庫不會自動跟上。

為什麼？因為 Drizzle 採用的是「先產 migration，再套 migration」的兩步流程。它不會在你存檔時自動偵測 schema 變更並同步——你必須手動推兩步：

Step 1：Generate migration

pnpm db generate

這一步從 schema.ts 產出 migration 檔案（SQL 腳本），放在 migrations 目錄裡。這是程式碼世界的產物——一個描述「資料庫該長什麼樣」的檔案。

Step 2：Apply migration

pnpm db migrate

這一步把 pending migration 套進實際的資料庫。這是資料庫世界的動作——真正的 data.db 被改寫。

類比：Generate 是畫建築圖、Migrate 是照圖施工。你畫了圖不代表牆會自己長出來——你得叫工人進場。跳過 migrate，就像畫了圖但沒施工，schema 和資料庫永遠不同步。

Agent 的常見錯誤

在實戰中，agent 通常自己會想到跑 generate，但常常漏掉 migrate。結果就是你會看到「agent 以為自己動了資料庫其實沒有」的假象——它跑完了 generate，覺得 schema 已經更新了，但資料庫還停留在舊版。

這是你在 HITL（Human-In-The-Loop）模式要盯的第一個點。每次 agent 改了 schema，你都要確認它跑了 migrate。

搞砸了怎麼辦：刪 data.db + reseed

不需要逆向 migration。因為全部都是假資料，最簡單的重置方式：

# 刪掉資料庫
rm data.db data.db-shm data.db-wal

# 重新 seed
pnpm db:seed

乾淨俐落，零損失。你在練習環境裡不需要擔心「資料備份」的問題。

決策樹

情況 做法
改了 schema.ts db generate → db migrate
Agent 改了 schema 但沒 migrate 手動跑 db migrate
資料庫壞了 / 想全部重來 刪 data.db + pnpm db:seed
不確定要不要重置 先 seed 看看，不行就刪重來

小結

資料庫同步流程：schema.ts 是 source of truth，改了要手動 generate → migrate。搞砸就刪 data.db + reseed。Agent 常漏 migrate，你在 HITL 模式要盯。
