實跑 GrillMe：從訪談到直上實作

Node interview-not-plan · grill-to-implement · 一次完整 lesson comments 實跑

Learning goal

能跟著 lesson comments 的完整實跑，走過 GrillMe 訪談 → 直接實作的流程，並用 reversibility（可否回退）思維挑選設計，理解為何對齊來自訪談、實作階段零 steering。

起手式：V1-first 的模糊需求

練習故意把需求留得很模糊：「做一個 lesson comments 功能」。用一個明確的 V1-first prompt 起手，剩下的全部交給 GrillMe 訪談——不進 plan mode，就是上一課的 default mode 沙盒。

訪談怎麼被驅動的

GrillMe 一題一題問，講師最常回的一句是 「Correct」——直接接受 agent 附上的推薦答案。這正是「給推薦答案」原則的威力：大部分決策講師只需要確認，省下的注意力拿來想真正重要的問題。當講師想比較兩個方案時，就自己追問，例如：「哪一個版本之後會很難回退（hard to row back from）？」——這一問把挑設計的鏡頭換成了 reversibility。

用 reversibility 挑設計

回退的容易程度是挑選設計的核心鏡頭：

  1. 純 flat（無層級）留言：最可回退——每則留言都是獨立資料，想改成有回覆層級隨時能加欄位。
  2. 巢狀 thread（有層級）：最難逃脫——資料的「意義」依賴於深度（第 3 層的留言和第 1 層的意義不同），改回 flat 等於重新解釋所有既有資料。

V1 該挑「純 flat」：它不是最好的留言體驗，但是最安全的地基。可回退的意思就是「以後要升級不綁死」——對一個連使用者都還沒確認的功能，這比完美重要。

被釘出來的 V1 scope

問題V1 決定
誰可以發文／閱讀已註冊學生 + 課程講師
範圍留言綁定單一 lesson
Threading 模型純 flat list（可回退）
內容格式純文字 + 自動連結
編輯／刪除只能 soft delete，不能編輯
放置位置lesson 內容／測驗下方的討論區
排序thread-like 排序（類似討論串的順序）
分頁一次載入全部
通知不做通知
字數上限2000 字元
管理admin 可以刪除

注意「一次一題」為什麼重要：問題太多時，人會不由自主地把困難的決策「延後略過」。一次一題逼你對 threading、編輯權限這些最傷筋骨的決定**現在就做**。

訪談完，直接實作

訪談結束時 context 約 40k tokens，還在 smart zone——而且沒有產生任何「計畫資產」：沒有 plan 文件、沒有牆式計畫。agent 直接進 implement，把訪談結果（schema、migration、comment service、tests、UI）一路做完，全部測試通過，到 UI 階段約 78k tokens。對齊完全來自訪談，實作階段零 steering。

QA：對齊的證據

QA 驗證的不是「畫面漂不漂亮」，而是「訪談的決定有沒有被照實實作」：James Park（未註冊該課）看不到留言、Olivia（一般學生）刪不了留言（權限控制正確）、soft-delete 的占位狀態正常。每個權限決定都是訪談釘出來的——實作只是把它們照做。
