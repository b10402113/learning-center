用 IDE 檢視與核准 diff

學習目標：用 /ide 啟動 IDE 整合，在 VS Code 檢視 rich diff，並用「Accept Proposed Changes」或直接存檔核准 agent 的編輯，把 review 變成上線前的 HITL 閘門。

為什麼要 IDE 整合？

Claude Code 預設跑在終端機裡，它改檔案時，diff 會以純文字形式塞在終端視窗裡——勉強能看，但很醜、難捲、難比較。這對「review agent 改了什麼」這件事是致命的：review 的目的是在上線前攔下壞編輯，但如果連看都看不清楚，review 就是走過場。

解決方法是把 Claude Code 接上你日常用的 IDE。課程用 VS Code，但 Cursor、Windsurf、Antigravity 也都行——整合的入口是同一個命令：

/ide

執行 /ide 會顯示目前的連線狀態，也會告訴你怎麼安裝對應 IDE 的 extension。裝好 extension 之後，Claude 改檔案產生的 diff 就不在終端裡了，而是出現在 IDE 的介面中。

它解決了什麼問題

假設你叫 Claude「把 package.json 裡的 test watch 命令拿掉」。它會先讀檔案、做一次編輯、產生一個 diff。沒有 IDE 整合時，你只能在終端看到一坨文字 diff；有了整合後，你可以：

  • 在編輯器裡看真正的檔案內容，不是縮在一格的文字差異
  • 上下捲動，看這個編輯到底影響了哪些地方
  • 逐行檢查是不是一個 decent edit
核心概念 IDE 整合的重點不是「讓 Claude 幫你在 IDE 裡寫程式」，而是diff 管理——讓你真正看得清楚 agent 改動了什麼，才有資格核准它。

核准的兩種方式

看完 diff 之後，你有兩種方式核准這個編輯：

  1. 按 IDE 介面上的 Accept Proposed Changes 按鈕
  2. 直接 儲存檔案（Ctrl-S / Cmd-S）——存檔就等於同意這份 diff

這個「先看、再核准」的流程，就是一個人類在迴路中的閘門（HITL gate）。agent 可以提議任何改動，但只有你按下去的那一瞬間，它才算生效。這是把控制權留在人手上的第一道防線。

為什麼老師在 VS Code 裡跑 Claude Code

課程示範都在 VS Code 的整合終端裡跑 Claude Code，理由正是這個：有些時候你需要「潛進去」把 Claude 的輸出稍微調整一下，而更新或 review diff 這種事，在真正的 IDE 裡做遠比在終端機舒服得多。

這不是可有可無的方便——它是你每一次交付前 review 的主戰場。學會在 IDE 裡檢視與核准 diff，等於學會「看清楚 agent 到底改了什麼」，這是一切信任的前提。

小結

  • /ide 啟動並顯示 IDE 整合狀態，讓 diff 從終端搬進 IDE
  • rich diff 可捲動、可逐行檢查，比終端文字強得多
  • 「Accept Proposed Changes」或存檔 = 核准；沒核准就不算數
  • 這是上線前的 HITL 閘門：看得清楚，才敢放手
