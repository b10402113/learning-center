為什麼這樣排

Step 2/3 · 七階段流程是什麼、為什麼有效

學習目標：解釋流程順序的道理：前面先把模糊的需求釘成可執行的規格，實作階段才能整段放手（AFK），人走開時用同一段時間規劃下一批工作，最後 review 守住品質。

順序本身就是風險管理

這七個階段不是隨便排的。順序本身在降低風險：前面的階段把「模糊」變成「決定」，後面的階段才能放手執行。而越晚發現決策錯，重做的代價越大。

想想最糟的情況：你跳過 grill 和 research，直接叫 agent implement。需求模糊 → agent 亂猜 → 你得逐行盯 → 既不能 AFK 又浪費時間。或者你做完了 prototype 才發現方向錯——這比在 grill 階段就問清楚貴十倍。

前半段：用便宜的手段處理最貴的不確定性

前三站是「探路」，花的是時間不是代碼：

階段 處理的不確定性 手段
Grill 需求最模糊、判斷最貴 一題一題把需求問到具體
Research 我們不知道的技術未知 人先查，不靠 agent 的模糊記憶
Prototype 設計上的未知數 最小代碼沖掉，避免做完才發現方向錯

Grill 排第一，是因為需求最模糊、判斷最貴——需求不清楚，後面做什麼都是白費。Research 排第二，因為 LLM 不是可靠的資料庫（它會幻覺），你不知道的東西 agent 也不會知道。Prototype 排第三，因為有些設計問題光靠問是問不出答案的，得跑一下才知道。

中間站：把決定凍結下來

PRD/plan 和 issues 是「凍結」階段：

  • PRD/plan 把方向寫成兩份文件——PRD 寫「做什麼」（問題、用戶故事），plan 寫「怎麼做」（技術方案、分期）。因為 LLM 無狀態，每次新 session 都是全新的，文件是唯一可靠傳遞「商量好的結論」的媒介。
  • Issues 再把文件切成邊界明確、可整段接手的任務。一個 issue 就是一段可以交給 agent 整段跑完的工作單元。
類比：你在蓋房子之前不會只跟建築師口頭說說就開始動工。你會拿到藍圖（PRD/plan），然後把藍圖拆成工單（issues）——水電工做水電的工單、泥作做泥作的工單。每一張工單的範圍都很清楚，工人進場就能整段做完。

後段：放手 + 守品質

implement 之所以能整段 AFK，是因為前面已經把所有該決定的都決定了。沒有模糊需求等著人現場解釋——人走開去規劃下一批工作（plan while the AI ships），這是吞吐量的真正來源：**一個人跟 agent 平行、同時做兩件事**。

review 最後守住品質。agent 再強也會出錯，人的閘門不可省。而審查把 codebase 維持在健康狀態，**agent 在好的 codebase 裡表現更好**，尾巴反過來餵養開頭，形成正循環。

對照組：直接叫 agent implement

如果你跳過前面所有階段，直接叫 agent implement：

有流程 無流程直接 implement
需求 已凍結（PRD/plan） 模糊，agent 亂猜
人的角色 AFK，做別的事 逐行盯，浪費時間
重做代價 低（問題在 grill 就解決了） 高（做完才发现方向錯）
Codebase 健康，正循環 混亂，技術債累積

小結

口訣：前面越用力，後面越能放手。前面的階段用便宜的手段處理最貴的不確定性，中間把決定凍結成文件，後面放手給 agent 跑，人去做下一件事。對照組是直接 implement——需求模糊、人被綁住、重做代價高。
