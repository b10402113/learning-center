為什麼這樣排

Node 1 · process-overview · 順序本身如何把風險一路降下來

學習目標：解釋流程順序的道理：前面先把模糊的需求釘成可執行的規格，實作階段才能整段放手（AFK），人走開時用同一段時間規劃下一批工作，最後 review 守住品質。

一句話：順序本身在降低風險

七階段的順序不是隨便排的。前面的階段把「模糊」變成「決定」，後面的階段才能放手執行。越早的階段，處理的是越貴的不確定性——因為一個決策錯得越晚，重做的代價越大。這條流水線把風險最高的判斷題全部往前挪。

前半段：把模糊釘成決定

  • Grill（訪談）：需求一開始是模糊的。Grill 用一題一題的訪談把它問到具體——你不知道要什麼，agent 更不知道，所以第一個動作就是把「人腦裡的模糊」變成「講得出口的規格雛形」。
  • Research（研究）：把我們不知道的未知補齊。這些東西 agent 也不會知道（LLM 不是可靠的資料庫），人要先查清楚。
  • Prototype（原型）：用最小代碼把設計上的未知數沖掉。與其寫一大堆正式代碼才發現方向錯，不如先丟一個可丟的小實驗，讓答案自己浮出來。

這三個階段共同的邏輯是：用便宜的方式先把不確定性處理完。訪談、查資料、寫小原型都比「寫完整個功能再砍掉」便宜得多。

中段：把決定寫下來、切成任務

決定做出來之後必須被凍結成文件：PRD（產品需求）把「做什麼」寫清楚，plan 把「怎麼做」寫清楚。為什麼要寫？因為 LLM 是無狀態的——每次新 session 都是全新的，文件就是唯一能可靠傳遞「我們商量好的結論」的媒介。

接著把文件切成 issues：一份可執行的任務清單。到這裡，每個任務的邊界、驗收標準都明確了，agent 才可以整段接手而不需要人一直在旁邊補上下文。

後段：放手，然後守品質

Implement（實作）之所以能整段 AFK，是因為前面已經把所有該決定的都決定了——沒有模糊需求等著人現場解釋。你放手讓 agent 跑，自己走開去規劃下一批工作（plan while the AI ships）。這才是吞吐量的來源：一個人跟 agent 平行，同時做兩件事。

Review（審查）在最後守住品質。agent 再強也會出錯，所以最後要有人的閘門。而且這裡有個正回饋：審查把 codebase 維持在健康狀態，而agent 在好的 codebase 裡表現更好——流程的尾巴反過來餵養流程的開頭。

對照：跳過前半段會發生什麼

想像你直接叫 agent「implement 這個功能」而沒有前面的階段：需求模糊 → agent 只能亂猜 → 猜錯 → 你得坐在旁邊逐行盯、隨時糾正 → 既不能 AFK，也浪費了人的時間。這正是「只能坐在那看 agent 做事」的來源——不是 agent 的問題，是你把該先決定的事丟給了他。

小結

順序的道理：前面用便宜的手段把貴的不確定性處理掉（訪談、研究、原型），中段把決定寫成文件並切成任務（PRD/plan、issues），實作才能放手 AFK，最後 review 把品質守住。越用力在前面，後面越能放手。
