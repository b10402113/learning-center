七階段流程總覽

Step 1/3 · 七階段流程是什麼、為什麼有效

學習目標：按順序說出七階段流程（grill → research → prototype → PRD/plan → issues → implement → review），並說出每個階段各自產出什麼。

不賣框架，擁有自己的流程

市面上有一堆包裝 AI coding agent 的大型框架——GSD、spec kits、be mad——但這門課的教練 Matt Pocock（三十年工程經驗）主張：你應該擁有自己的流程，而不是套一個別人的框架。

原因很直觀：框架是別人針對他們的場景設計的，你的 codebase、你的需求、你的團隊都不是他們的場景。把框架當聖經照抄，只會在不適用的地方硬套。但三十年的工程直覺可以濃縮成一條七階段流水線，你把它內化之後，就能根據自己的場景微調。

七階段流水線

每一站都在把「模糊」往「可執行」推一格：

# 階段 做什麼 產出
1 Grill（訪談） 一題一題把模糊需求問清楚 需求輪廓
2 Research 補齊我們不知道的未知（LLM 不是可靠的資料庫） 研究筆記
3 Prototype 用最小代碼沖掉設計上的未知數 可丟的實驗
4 PRD / Plan 把方向寫成「做什麼」與「怎麼做」兩份文件 PRD + plan
5 Issues 把文件切成邊界明確、可整段接手的任務 任務清單
6 Implement 整段放手讓 agent 跑，人走開去做別的事 能跑、有測試、已 commit 的代碼
7 Review 人守住品質，審查代碼 健康、可維護的 codebase

為什麼是這七個階段？

關鍵不在階段的數量，而在它們的排列順序。前面的階段用便宜的手段處理最貴的不確定性，後面的階段才能放心交給 agent。一句話：**前面越用力，後面越能放手**。

類比：蓋房子。你不會先把牆砌好再來問「這間房子要幾間房間？」。Grill 就是在問「要幾間房間」；research 就是在查「這塊地的土質能不能承重」；prototype 就是先打一根試樁看看；PRD/plan 就是最終設計圖；issues 就是工單；implement 就是工人進場施工（你人在別處監管別的工地）；review 就是最終驗收。

核心支柱：AFK（Away From Keyboard）

這套流程最關鍵的支柱是讓 implement 徹底 AFK——人不在鍵盤前，agent 自己跑完。

這才是吞吐量的真正來源：**plan while the AI ships**——趁 AI 交貨時，你用同一段時間去規劃下一批工作。一個人跟 agent 平行、同時做兩件事。如果 implement 還需要你逐行盯著，你就只是用 AI 加速了寫字，並沒有真正倍增產出。

正循環：好的 codebase 讓 agent 表現更好

這套流程本身會把你推向更健康的 codebase。Grill 讓需求清楚、plan 讓架構合理、review 守住品質——三者加起來，codebase 的結構會越來越好。而 agent 在好的 codebase 裡表現更好（更少幻覺、更少跑偏），讓你的下一輪 implement 更容易 AFK。這是一個正循環。

課程怎麼用這個流程

課程用一個約 20,000 行的 TypeScript / React playground 做 interactive exercises。你也可以把練習套在自己的 repo 上（跟練課程 repo 支援較多）。

接下來的課程會沿著這七個階段，一站一站帶你走。每一站都會給你一個具體的 exercise，讓你在 playground 上實跑。

小結

七階段流水線：grill → research → prototype → PRD/plan → issues → implement → review。每一站把模糊往前推一格，最後的 implement 才能徹底放手 AFK。前面越用力，後面越能放手。
