用「Explore」叫出深層 sub-agent

Node 7 · exploration · Step 3/4

Learning goal

理解「Explore」這個動詞如何連結到 Explore sub-agent，並說出深層探索的成本（token、tool calls）與換來的覆蓋深度。

換一個字眼，換一條路

上一課的基準線是 6 個檔案、沒有 sub-agent。現在課程換一個問法——追問一個具體主題，而且刻意用一個特殊的動詞：

Explore how PPP works in this repo.

（PPP = purchasing power parity，購買力平價，課程 repo 裡的一個實作。）同樣是在探索，這裡的字眼從「Tell me」換成「Explore」。就這一個動詞，agent 的行為完全不同了。

發生了什麼：Explore sub-agent 被叫出來

這次 UI 上出現一個方括號標題的「Explore」——orchestrator agent（你正在對話的那個）spawn 了一個 Explore sub-agent，用一份客製化的 system prompt 去專門探索 repo：

  • 它非常激進地搜尋檔案、搜尋各種不同的東西
  • 按 Ctrl-O 展開，可以看到讀的檔案數遠多於 6 份
  • 跑完後把一份 summary 回報給 parent orchestrator

這就是 lesson 16 講的 context-saving 機制：探索的髒活交給一個有獨立 context window 的子代理去燒 token，只把濃縮後的 summary 傳回來——主 context 保持乾淨，留給真正要動腦的實作。

成本數字：深層探索不是免費的

課程影片給了具體統計，讓你對「深層探索」的價碼有感：

指標數值
完成時間約 60 秒
用了多少 token64,000 tokens
佔它的 context window約 32%
tool calls25 次（bash、檔案讀寫等）

「64k tokens，約 32% 的 context window，這很 gnarly——燒了很多 token。但它回傳的是一份『幾乎像我們自己寫的』深度探索。」

這個成本是花在子代理身上，不是花在你正在對話的 orchestrator 身上——這正是它值得的原因：覆蓋深度大幅提升，而主 context 沒有被 64k token 的閱讀軌跡塞爆。

word choice：動詞連到 latent space

為什麼「Explore」一個字就有這個效果？課程的解釋是：這個動詞在模型的 latent space 裡連到了 Explore sub-agent——模型「知道」當它看到 Explore 這個動詞，就應該叫出 Explore sub-agent。而「Tell me what the tech stack is」沒有連到任何 sub-agent。
