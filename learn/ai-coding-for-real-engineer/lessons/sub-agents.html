用 sub-agent 把探索成本外包

Node 6 · context-economy · Step 2/4 · 把會燒 token 的活交給新的 context window

Learning goal

說明 orchestrator 為何把任務委派給帶全新 context window 的 sub-agent，並指出它如何保住主 agent 的 smart zone。

困境：探索跟實作搶同一塊 context

agent 每次進到一個 repo 都是「零記憶」——它得先探索才知道要幹嘛，然後才實作。兩件事共用同一個 context window：探索花的 token 越多，留在 smart zone 給實作的 token 就越少。

但矛盾的是，探索偷工減料也不行——花太少力氣探索，agent 對 repo 的 context 就少，實作品質跟著爛。要嘛 explore 少一點（實作變笨）、要嘛 explore 多一點（smart zone 被吃光）。

解法：sub-agent 是新開一間辦公室

Claude Code 的回答是委派。跟你對話的那個 agent 叫做 orchestrator（主控者），它會 spawn 出一個 sub-agent——本質上是新建一個全新的 context window，用這個新 window 去執行任務。

sub-agent 可以在它自己的 smart zone 裡盡情燒 token 做探索，做完只回傳一份摘要給 orchestrator。就像主開發把活丟給實習生：「去把這個 repo 摸清楚，回來報告你的發現」，實習生燒的是他的腦力，主開發的桌面保持乾淨。

本質：sub-agent 是 orchestrator 的 context-saving 機制。探索的 token 成本被轉嫁到一個全新的 context window，主 agent 的 smart zone 保住，給真正的實作用。

它還能平行、還能換模型

orchestrator 可以同時 spawn 多個 sub-agent 平行做事，全部做完再各自回報。而且 sub-agent 可以用不同的 system prompt 和不同的模型——像是探索這種相對簡單的任務，常見做法是用便宜又快的 Haiku，一樣高品質。

Claude Code 對這招用得極其積極——你在它的 UI 裡會隨處看到 sub-agent。它就是這個工具能撐起長 session 的核心把戲。

實戰線索：用「Explore」動詞觸發

課程稍早的練習證實：純技術棧 prompt 只讀 6 個檔案、不 spawn 任何 sub-agent；加上「Explore」這個動詞，就會觸發一個帶客製 system prompt 的 Explore sub-agent——花了約 60 秒、燒了 ~64k token（其 window 的 32%）、做了 25 次 tool call，換回深度好幾倍的探索結果。用字有差：動詞「Explore」正好對上模型潛在空間裡的 Explore sub-agent。

跟 monitor-context 的關係

上一步裝好 status-line 之後，你隨時看得到主 agent 的 token 數。sub-agent 就是保持那個數字低的手段之一——把最燒 token 的探索，整個移到你自己的 context window 外面去。
