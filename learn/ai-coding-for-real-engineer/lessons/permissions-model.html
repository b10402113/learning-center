用 permissions 設定管住風險

Step 4/4 · review diff、bash、風險控管

學習目標：理解 risk/reward 權衡，用 .claude/settings.local.json 的 permissions.allow/deny（含 wildcard）與 settings.json 預授權命令，並管控 web 存取等風險。

你願意讓它有多大權力？

跟 agent 合作的第一個問題是你願意讓它有多大權力。權力越大、能交付越多，但出事的後果也越大。最極端的例子：agent 有完全的 shell 權限，它可以 rm -rf / 刪掉整個檔案系統。你不會給一個實習生這個權力，你也不會給 agent。

Claude Code 的解法是一套詳細的 permissions 模型，預設非常嚴格。它不信任 agent——每次想跑命令，都先問你。

核准流程

當 Claude 想跑一個命令（例如 typecheck），它會先請求核准，畫面上顯示確切命令和原因，然後你有幾個選項：

選項 效果
允許這次 只這次放行，下次再問
以後都允許 這個專案內以後都放行，不再問
否決 不讓它跑這個命令
Tab 建議另一個命令 例如叫它用 npx tsc 代替 pnpm typecheck

極度安全的命令（如 echo hello）則直接跑不問。

Settings 文件：預授權的紀錄

你的核准會被記錄到 .claude/settings.local.json 的 permissions.allow / permissions.deny 陣列。你也可以自己手動編輯來預先授權。

規則支援 wildcard：

{
  "permissions": {
    "allow": ["Bash(pnpm:*)"],
    "deny": ["Bash(git push:*)"]
  }
}

"Bash(pnpm:*)" 一次允許所有 pnpm 開頭的命令——pnpm dev、pnpm test、pnpm build 都不用再問。這才是實際可用的粒度：你不會想每次 pnpm dev 都按一次核准。

Local vs Shared 設定

文件名 作用範圍 在 .gitignore 裡？
.claude/settings.local.json 只對你個人有效 是（不進 repo）
.claude/settings.json 整個 repo 的 Claude 實例共用 否（跟著 repo 走）

把 settings.local.json 改名成 settings.json，就能讓整個團隊共享同一套規則。新人第一次進 repo 就跑得起來——不用每次 session 都跟安全提示搏鬥。這就是repo 層級 agent 配置的種子。

Web 存取也是風險面

不只 bash 命令——web search / web fetch 也一樣受控。Agent 上網搜尋、抓取網頁，也是要管的風險面。它可能搜到惡意網站、抓到有毒內容、或洩漏你的專案資訊。Permissions 模型把 web 存取也納入管控。

Risk vs Reward 的平衡

Permissions 的本質是 risk/reward 權衡：

  • 權限越寬 → agent 能交付越多（reward 高）→ 但出事的後果越大（risk 高）
  • 權限越嚴 → agent 被卡住的次數越多（reward 低）→ 但出事的機率越低（risk 低）

最佳策略不是「全部開放」或「全部封鎖」，而是預授權一套已知安全的命令——把 risk 降到可控，同時讓 reward 最大化。這就是 settings.json 的用途：提前把安全的命令放進白名單，省去每次 session 都跟提示搏鬥。

類比：你請了一個管家（agent）幫你打理家務。你不會把所有鑰匙都給他（全部開放），也不會把他鎖在門外（全部封鎖）。你會給他大門和客廳的鑰匙（預授權），但保險箱的鑰匙你自己留著（deny）。Permissions 就是這套鑰匙系統。
口訣：預授權安全命令，其餘每次問。用 settings.json 管住 repo 層級的權限，用 settings.local.json 管你個人的偏好。風險面不只 bash——web 存取也要管。
