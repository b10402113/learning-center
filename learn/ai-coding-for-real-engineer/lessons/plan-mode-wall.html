plan mode 的牆式計畫：它做對了什麼、錯在哪

Node interview-not-plan · plan-mode-wall · 一堵很美、但跟你想的不一樣的牆

Learning goal

能說出 plan mode 的完整運作流程（探索、訪談、計畫 sub-agent、計畫選項），並指出它跳過 shared design concept、直接把答案壓成一面計畫牆的失敗模式。

先把 plan mode 的完整流程走一遍

plan mode 存在於 Claude Code、Codex 等主流 agent。課程的 lesson 20 實跑中，Claude 收到一個「做課程評分系統」的需求後自動進入 plan mode，流程大致是：

  1. 探索：spawn 一個 Explore sub-agent 去讀 codebase（每個 sub-agent 有自己全新的 context window，回報的只有摘要）。
  2. 訪談：用幾個釐清問題問你——這功能只有已註冊學生能用嗎、評分是 1–5 星嗎、要不要顯示在儀表板。你可以用 tab / 方向鍵 / 數字選答案，也可以 escape 自己追問。
  3. 計畫 sub-agent：再 spawn 一個 plan sub-agent——這是另一個 context-saving 機制，它讀檔案、設計一份實作計畫，只把計畫摘要帶回來。
  4. 吐出計畫牆：把一份多步驟、帶選項的完整計畫端到你面前。

計畫最後通常附四個選項：自動接受編輯、保留手動核准、清空 context 後自動接受、或直接修改計畫內容。之後 agent 才開始實作。

它做對了什麼

「先計畫」本身不是錯的。計畫強迫探索、強迫理解、強迫對齊——這三個都是好事。plan sub-agent 也是一個漂亮的 context-saving 技巧：讓一個乾淨 context 的子代理去燒 token 設計，主 context 不被塞爆。整段跑完 /context 大約 32–36%，還在 smart zone 裡。

它錯在哪：訪談被壓短，共識沒建立

問題不在「計畫」，在「計畫前的訪談太短」。實務上，plan mode 常常只問一兩個問題，就把答案壓成一整面牆的文字計畫——看起來完整、看起來專業，但你心中真正想要的那個設計概念，從來沒有被建立起來。

而人有個危險的習慣：面對一面牆的計畫，review 時會「跳過不齊的地方」——計畫看起來很長很完整，於是你假定它跟你腦中的東西一致，其實沒有。對齊沒發生，牆反而給了雙方「已經對齊」的錯覺。

一句話總結

plan mode 把「對齊」外包給一面牆。它做對的是探索與計畫架構，做錯的是把共享設計概念的建立階段（訪談）壓成兩個問題就交差。下一課看被它跳過的 shared design concept 到底是什麼。
