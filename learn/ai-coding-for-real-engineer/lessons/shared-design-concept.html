shared design concept：為什麼訪談才是核心

Node interview-not-plan · shared-design-concept · 設計概念是共享的，不是交付物

Learning goal

能說出設計概念是參與者之間短暫共享、而非可以交付的資產，並解釋為何 explore → interview → implement 能取代「計畫先行」的工作流。

設計概念不是資產，是短暫共享

Frederick P. Brooks 在《The Design of Design》裡點破一件事：設計概念（design concept）是**所有參與者之間短暫共享的那個東西**——你腦中的畫面、agent 腦中的畫面、Reviewer 腦中的畫面，如果對不上，後面所有文件都建立在沙上。它不是可以交付的資產：你寫不出「一份文件就等於設計概念」。它活在每個參與者的腦子裡，只有透過對話才能對齊。

plan mode 的真正失敗，不是計畫本身，而是跳過了「建立共享設計概念」這一步。訪談被壓成一兩個問題，概念沒對齊，牆式計畫就替換了所有參與者腦中的不同畫面——而且讓大家誤以為已經對齊。

agent 的能力，與 plan mode 關掉了什麼

先記住 default / implement 模式下 agent 有四種能力：寫檔案、讀檔案、跑 bash、呼叫 MCP server。進入 plan mode 後，agent 被**關掉寫檔案**、也被鼓勵不要主動做變更——它變成一個只會輸出文字的顧問。這對「計畫期間不想動 code」是安全的，但也讓它更傾向「把對齊外包給一面牆」。

explore → interview → implement：該走的順序

課程推薦的工作流是三個階段，重心完全不同：

  1. explore：agent 先讀 codebase，把「可以自己查到的事」查清楚。
  2. interview：**核心，可以花很久**——一題一題把模糊需求釘成 shared design concept。這階段的訪談內容（intent）是高價值資料，它把 context window 填滿「你要什麼」而不是「雜訊」。
  3. implement：概念對齊了，直接實作。

訪談的產出可以變成一份 spec，也可以**直接進實作**——反正核心是「對齊」，文件是手段不是目的。GrillMe 這份 skill 就是這套流程的具體化：它會 relentlessly 地訪談你，直到雙方共享理解成立，再進實作。

為什麼這能取代「計畫先行」

計畫先行把順序搞反了：先在資訊最少時吐一份完整計畫，再用這份計畫假裝對齊。explore → interview → implement 先花時間在**唯一無法被文件取代的事**——參與者之間的概念對齊——剩下的實作因為概念已經一致，反而零 steering。花在訪談上的時間，是省回實作階段所有「方向錯了重做」的時間。
