# 內容不可信 vs 過程不可重現，兩套不同的驗證

## The relationship

兩條天性都讓「agent 的輸出不能直接相信」，但不可信的方式相反。參數記憶（fuzzy-jpeg-memory，把訓練資料壓進參數後留下的世界知識）讓輸出內容不可靠，它把海量訓練資料壓成模糊 JPEG，講事實時 by design（刻意如此）會張冠李戴，講錯的跟講對的一樣流暢。非決定性（nondeterminism）讓輸出過程不可重現，它是 next-token 抽樣機器（每次生成下一個 token 都是從機率分佈裡抽），同一句話跑兩次結果不同，偶爾冒出怪異 outlier（離群值）。一個壞在「講出來的東西是錯的」，一個壞在「這次跟上次不一樣」。

## Why it matters

這兩種「不可信」要求不同的驗證手段，混在一起就會用錯工具。用「重跑一次對答案」去抓內容錯誤，會發現它兩次都錯得一樣流暢，重跑毫無收穫。用「把原始碼放進窗口」去抓過程隨機，會發現它讀了原始碼照樣每次不同。先弄清楚此刻是哪一種不可信，再選驗證手段，這是你每天跟 agent 打交道時最常做的診斷。

## When each applies

懷疑內容錯，驗證的對象是「它講的事實」，把原始碼、文件、輸出用 @（在提示詞中參照檔案，讓模型讀進窗口）帶進窗口，或翻文件對照，讓答案改由窗口內的原始資訊支撐。適用於它報的 API 簽名、版本行為、業務規則。懷疑過程不穩定，驗證的對象是「結果有沒有符合成功標準」，測試、型別檢查、lint、明確的完成定義，把「合理」變成可自動檢查的條件，收斂抽樣往好的一端。適用於它生成的程式能不能跑、測試過不過、交付物有沒有達標。對交付出錯的程式，兩種都要用，先驗內容後驗過程。

## Interleave

agent 說某個套件的最新版本改了一個 API。你懷疑兩件事，一是它把版本講錯，二是同樣的改法重跑可能完全不一樣。分別寫出針對每一種懷疑的驗證步驟，並說明為什麼對方的驗證手段對它無效。
