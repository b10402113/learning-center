# Digest — ai-coding-for-real-engineer (part 3: lessons 21-30)

## Overview (L1)

- lesson 21 — Agents are non-deterministic: LLMs are next-token choosers that sample from a probability distribution, so the same prompt yields different outputs. Mostly sensible, occasionally weird outliers; this is normal and you "ride the wave," with consistency improved later via feedback loops.
- lesson 22 — Set up a Claude Code status line to keep context-window usage visible at all times. Install a community package globally in `~/.claude` settings, then watch raw token count (smart/dumb zone): worry around 80k–100k tokens. Notes Anthropic's 1M-context Opus 4.6/Sonnet 4.6, which breaks percentage intuition.
- lesson 23 — Drop plan mode in favour of a "shared design concept" reached through relentless interview. Explains the four agent capability buckets and why plan mode's truncated interview causes misalignment (Brooks's "design concept"); introduces the GrillMe skill that interviews one question at a time before implementation.
- lesson 24 — Exercise brief: use the GrillMe skill to build a deliberately vague "lesson comments" feature. Start a new Claude Code session, avoid plan mode, use default mode, and invoke the `.claude/skills/GrillMe/SKILL.md` skill; note the skill's interview rules (design tree, recommendations, explore instead of asking, one question at a time).
- lesson 25 — Live GrillMe demo resolving the comments feature into a V1 spec: audience/permissions, flat threading, plain-text content, soft delete, discussion section, instructor badge, load-all, no notifications, admin delete. Implements and QA-passing with perfect alignment, no plan asset; reasons explicitly about reversible vs irreversible decisions.
- lesson 26 — How `compact` works at the context limit: the reserved auto-compact buffer triggers an LLM summary of the conversation (keeps key files, user messages, transcript), shown dropping 49% → 12%. Argues repeated compaction leaves "sediment" that degrades predictability; compact rarely, ideally once, and aim for a clean context.
- lesson 27 — The Handoff skill: write a temporary markdown summary so a fresh agent can continue the work in its own context window. Covers the `mktemp -t handoff.XXXXX` path, tailoring the doc to the next session's focus, suggesting skills, linking existing artifacts, and expand-and-contract flows (split off bug fixes, focused grilling).
- lesson 28 — Persistent memory via `AGENTS.md`/`CLAUDE.md`: an open "README for agents" supported by Gemini CLI, Devin, Codex, Cursor but not Claude Code, which reads `CLAUDE.md`. Warns it is global (loaded on every request, costs tokens), may be ignored by design, and `/init` output is often discoverable and stale; be paranoid about size.
- lesson 29 — Exercise brief: steer Claude Code with `CLAUDE.md` while implementing a bookmarks feature (private, persistent, inline). Tests whether the agent follows the codebase or the `CLAUDE.md` rule "use an object parameter instead of positional parameters when same-typed params exist"; observe which pattern wins.
- lesson 30 — Solution walkthrough: the agent used the `opts` object pattern from `CLAUDE.md` but forgot tests for `BookmarkService`, so the lesson adds a durable rule ("services must have accompanying `test.ts` files") and edits it mid-session with "review your work with the updated CLAUDE.md in mind." It writes the missing tests (10 pass) and QA confirms the feature.

## Sections (L2)

### lesson 21

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson21.en.srt#lesson21]]`
- Summary: A framing detour on what to expect from agents. LLMs are next-token choosers that select tokens probabilistically, so identical prompts to the same model can produce different answers — responses fall on a probability curve, mostly clustered around the sensible middle but sometimes with odd outliers. This non-determinism is baked in and normal.
- Key claims: agents are non-deterministic, not reproducible from identical inputs; responses sit on a probability distribution, mostly good/sensible with occasional weird outliers; this is a normal part of working with agents and you "ride the wave"; consistency can be improved later when the course covers feedback loops (AFK phase).
- Learner-relevant: Sets correct expectations so a learner doesn't think they did something wrong when their agent behaves differently from the instructor's. Foundational mental model ("agents are non-deterministic next-token machines") that motivates later practices like feedback loops and clean context.

### lesson 22

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson22.en.srt#lesson22]]`
- Summary: How to install a Claude Code status line so context-window usage is always visible. Claude Code's default UI hides context usage, unlike Cursor or OpenCode, so the instructor uses a community package installed globally in the user's `~/.claude` settings (not per project). It edits `settings.json` to add a `statusLine`, writes a cc-statusline settings JSON, and after restarting Claude Code the status line shows raw token count plus a dimmed percentage.
- Key claims: context usage should be monitored continuously to stay in the "smart zone"; get worried when usage reaches ~80k–100k tokens; the recording used a 200k limit, so 40% ≈ 80k tokens; Anthropic announced a 1M context window for Opus 4.6 and Sonnet 4.6, which makes percentage-based guidance less reliable, so the setup shows raw tokens first.
- Learner-relevant: A concrete setup/workflow skill (status line install, `settings.json` edit, `~/.claude` global user settings) and the smart-zone/dumb-zone model that underpins the rest of the course's context discipline.

### lesson 23

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson23.en.srt#lesson23]]`
- Summary: Why the instructor no longer recommends plan mode. Plan mode (available in Claude Code, Codex, and buildable in "pi") withholds file-writing so the agent only reads files, runs bash, and calls MCP servers; planning itself is valuable (alignment, exploration), but plan mode's interview phase is usually truncated — the agent explores, asks a question or two, then dumps a wall-of-text plan the user is forced to review and often skims, causing misalignment. He cites Frederick P. Brooks's *The Design of Design*: the missing thing is a shared design concept, an ephemeral understanding shared between collaborators, not an asset or plan.
- Key claims: an agent has four capability buckets — write files, read files, run bash scripts, call MCP servers; plan mode removes writing files; the recommended flow is explore → interview (can take a while) → implement, with the interview as the key alignment moment; the GrillMe skill relentlessly interviews until shared understanding and fills context with valuable user intent; almost every coding (and many non-coding) sessions start with GrillMe.
- Learner-relevant: A decision framework (plan mode vs. grilling) plus the "shared design concept" mental model. Introduces MCP servers as a forward reference and the GrillMe skill that is used for the next several lessons.

### lesson 24

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson24.en.srt#lesson24]]`
- Summary: Exercise briefing for using GrillMe to build a vague "lesson comments" feature. The prompt is deliberately underspecified so the learner must spend time with the agent resolving questions: can instructors comment/moderate/delete/hide, can students see others' comments, and who can see comments at all. Instructions: start a new Claude Code session, do not use plan mode, stay in default mode (not accept-edits, not auto), and invoke the GrillMe skill stored at `.claude/skills/GrillMe/SKILL.md`.
- Key claims: the entire GrillMe skill is tiny — "Interview me relentlessly about every aspect of this plan until we reach a shared understanding"; it walks down each branch of the design tree, resolving dependencies between decisions one by one; for each question it provides a recommended answer and asks one question at a time; if a question can be answered by exploring the codebase it explores instead, so it never asks questions it can answer itself; treat the lesson as a sandbox and record observations and possible skill improvements.
- Learner-relevant: Shows the exact skill file, invocation conventions (`.claude/skills/<name>/SKILL.md`), and the "one question at a time" interview pattern; sets up the next lesson's demo.

### lesson 25

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson25.en.srt#lesson25]]`
- Summary: A full live GrillMe session on the comments feature. The prompt asks to add lesson comments, keep V1 small and quickly working, with students and instructors able to comment. GrillMe explores a React Router course app (students/instructors/admins, per-lesson routes) and drives a design tree: permissions (enrolled students + instructor, scoped per lesson), threading, content format, edit/delete, placement, ordering, badges, pagination, notifications, character limit, and moderation. Each decision gets a recommendation, and the instructor sometimes accepts ("Correct") and sometimes disagrees (admins should be able to delete). It produces a light V1 spec, then implements with accept-edits-on through schema, service, tests, and UI, verified via the dev UI.
- Key claims: reasoning about reversibility — pure flat → one-level replies → fully nested is easy to escalate but nested → simple is hard because data meaning depends on depth, so choose the most reversible option (pure flat); content is plain text + auto link, not WYSIWYG; prefer soft delete (deleted placeholder) so threads don't lose context; resolve one question at a time to keep focus and avoid lazy one-shot planning; if you've reached a shared design concept you don't need to review the generated plan; still in the smart zone (~40k at implement start, 60k during service, ~78k at UI); outcome was a perfectly aligned implementation requiring no steering and no plan asset. Also: you are allowed to drive the conversation, not just answer A/B/C — the instructor asks a follow-up about "what would be hard to row back from."
- Learner-relevant: A worked example of converting vague intent into a precise design via interview, including the reversibility heuristic and the "one decision at a time" focus argument. Demonstrates a full toolchain: Drizzle migration (`db:generate`, `db:migrate`), comment service, tests copied from existing patterns, type checks, dev-UI QA with role switching (student/instructor/no-access).

### lesson 26

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson26.en.srt#lesson26]]`
- Summary: What actually happens when a context window fills to the limit. Running the `context` command shows an auto-compact buffer reserved at the end (~16.5% of the 200k window, e.g. 33k tokens) that holds no real tokens; crossing into it auto-runs `compact`, which uses an LLM to summarize a large context (repeated tool calls, low-value content) into a small one. A demo compacts a 49% session that had implemented the lesson comments feature down to 12% (~23k tokens), preserving main files, references, the plan file, all user messages, pending tasks, and the full transcript by reference. Custom summarization instructions (telling the LLM *why* you're compacting, e.g. "I just implemented a feature and want to QA it") improve results.
- Key claims: compact reduces a large context to a summary using an LLM and therefore costs tokens (though re-exploring the repo also costs tokens); every auto-compaction leaves "sediment" that layers up and affects output unpredictably, putting the agent in an unusual state; optimizing for a clean/empty context gives more predictable output, fewer tokens spent, and more time in the smart zone; compacting multiple times is an anti-pattern; compact at most once per conversation, mainly for long/difficult tasks or debugging where you want to keep prior attempts; the course's end goal is autonomous agents where you shouldn't need to touch the LLM, so relying on compact means relying on being present. (Explicitly framed as the instructor's mental model/opinion, shared by much of the community but contested by others.)
- Learner-relevant: Explains the mechanism behind the auto-compact buffer and `/context`, and gives a decision rule ("organize your harness to never need compact; when you do, do it once and give the summarizer your intent"). Reinforces the smart-zone/dumb-zone framing and the clean-context bias.

### lesson 27

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson27.en.srt#lesson27]]`
- Summary: Introduces the Handoff skill for splitting work across context windows. The motivating case: midway through a main session you discover a small side task (a broken test or a file needing an update) whose duration is unknown, so you don't want to burn the main session's budget or clear the context. Handoff writes a temporary markdown document summarizing the current conversation so a fresh agent can continue the work, saved to a path from `mktemp -t handoff.XXXXX` (the temp directory). The skill also suggests which skills the next session should use, avoids duplicating content already captured in other artifacts (linking them instead), and treats any user instructions as a description of the next session's focus to tailor the document.
- Key claims: originally conceived as "compact to file," renamed "handoff"; use it to spin a broken test/file fix into its own context window; use it to split a long GrillMe session so a sub-session can grill a specific part, prototype, do research, burn lots of context, then hand a condensed doc back to the original session; these "expand and contract" flows are powerful; keep it in mind whenever a session runs into the dumb zone.
- Learner-relevant: A concrete multi-agent/multi-session workflow with a named skill, temp-file path convention, and the "condense learnings into a handoff doc" pattern. Complements lesson 26 by offering an alternative to compaction.

### lesson 28

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson28.en.srt#lesson28]]`
- Summary: Persistent memory for coding agents via `AGENTS.md` / `CLAUDE.md`. Since LLMs forget everything when context is cleared, you need a place to store preferences and conventions. `AGENTS.md` is an open format — a "README for agents" — recognized by Gemini CLI, Devin, Codex, and Cursor, but notably not by Claude Code, which instead reads `CLAUDE.md`. A demo adds "always reply to me in pirate language" to `CLAUDE.md` and the agent complies after restart. The file is global: it is silently pulled into every conversation in the repo, cannot be scoped, and a 2000-line version burned ~10% of context (with an in-product warning that a large `CLAUDE.md` hurts performance).
- Key claims: anything in `CLAUDE.md` costs tokens on every single request and pushes you toward the dumb zone; the `/init` command generates a `CLAUDE.md` by exploring the repo, but the instructor does not recommend it because the content (e.g. `package.json` scripts) is trivially discoverable and quickly goes stale, requiring manual upkeep; Claude Code often ignores `CLAUDE.md` by design via an injected system reminder ("this context may or may not be relevant… do not respond unless highly relevant"), so steering is unreliable; summary — `agents.md` and `claude.md` are the same idea, Claude Code only listens to `claude.md`, it is often ignored, and it is global, so only include things relevant to every request.
- Learner-relevant: Names the actual files and support matrix, quantifies the context cost, and argues for paranoia about size. Sets up the steering exercises in lessons 29–30. References the HumanLayer article on optimizing `CLAUDE.md`.

### lesson 29

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson29.en.srt#lesson29]]`
- Summary: Exercise briefing for steering Claude Code with `CLAUDE.md`. The instructor provides a pre-made plan (created in plan mode) for a bookmarks feature: bookmarks are private per student, persist until manually removed, are inline only, and there is no dedicated bookmarks page. The learner copies the plan into Claude Code and observes whether the agent obeys `CLAUDE.md` or the existing codebase. The specific `CLAUDE.md` rule: "when you have a function with more than one parameter with the same type, use an object parameter instead of positional parameters" — because calling e.g. `addUserToPost(userId: string, postId: string)` with the arguments swapped is an easy, silent bug. The dummy repo is deliberately full of positional parameters, creating a conflict with the rule to see which wins.
- Key claims: positional parameters of the same type are error-prone and should be replaced by a named object parameter; a coverage conflict between `CLAUDE.md` guidance and existing codebase patterns is a useful test of steering; learners should watch which pattern the agent follows and note patterns worth steering against in `CLAUDE.md`; the goal is developing an instinct for steering the LLM even though `CLAUDE.md` is an imperfect place to do it.
- Learner-relevant: Hands-on practice connecting a concrete anti-pattern (same-typed positional params) to a durable `CLAUDE.md` rule, and builds intuition for instruction-following vs. codebase inertia.

### lesson 30

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson30.en.srt#lesson30]]`
- Summary: Solution walkthrough of the bookmarks steering exercise. The agent explored the codebase (no separate explore agent, since the plan was detailed and upfront work was done), added tasks, and implemented after Shift+Tab to allow all edits. Crucially, `BookmarkService` used the `opts` object-parameter pattern from `CLAUDE.md` (`userId`, `lessonId`), consistently across `isLessonBookmarked` and `getBookmarkedLessonIDs`, showing `CLAUDE.md` beat the positional-parameter codebase convention. However, it failed to write tests for `BookmarkService` (tests existed for other services, discoverable only from the filesystem, but tests weren't in the plan). The instructor adds a durable, high-leverage rule: "anything marked as a service by the file name (e.g. `AuthTokenService.ts`) should have tests in an accompanying `test.ts` file." Because it names no concrete files, the rule is unlikely to rot.
- Key claims: the `opts` object pattern from `CLAUDE.md` was followed across all affected functions, resolving the conflict in favour of the memory file; the agent skipped tests only because the plan omitted them, showing plans must specify testing; `CLAUDE.md` edits mid-session are not picked up until a new session, so prompt "review your work with the updated CLAUDE.md in mind" to pull the latest version without losing context; the "services must have accompanying `test.ts` files" rule is high-leverage and durable because "service" is sticky application jargon meaning a tested unit providing specific functionality; after the update the agent wrote bookmark-service tests (10 passed) while staying inside the smart zone, and QA confirmed bookmarks work inline.
- Learner-relevant: Demonstrates how to iterate on `CLAUDE.md` as a living artifact, the mid-session refresh prompt, and the criterion for a durable rule (jargon, not enumerating files). Completes the steering arc from lessons 28–30.
