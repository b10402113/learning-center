# Digest — ai-coding-for-real-engineer (part 9: lessons 81-90)

## Overview (L1)

- lesson 81 — Introduces the prototype skill for flushing out unknown unknowns during planning/grilling: a logic branch (tiny interactive terminal app that pushes a data model through hard-to-reason-about cases with key presses) and a UI branch (several radically different UI variations on one route, switchable via a URL search param and floating bottom bar).
- lesson 82 — Software architecture is the crucial human-in-the-loop place. Agents design systems that are hard for themselves to use; "deep modules" (Ousterhout) — a thin, rarely-changing interface hiding a large implementation — make codebases navigable and testable for AI and cut the human's cognitive load.
- lesson 83 — The `improve codebase architecture` skill: an explore subagent finds friction (file-bouncing, shallow modules, pure functions extracted only for testability, integration risk at seams), presents candidates, spawns parallel subagents to design radically different interfaces, recommends/combines, and emits a refactor RFC as a GitHub issue.
- lesson 84 — Demo of the architecture skill on a deliberately bad quiz-scoring service (raw `better-sqlite3` SQL mixed with the app's Drizzle ORM, no tests). Three interface designs are compared and design B (`createQuizModule` factory with injected scoring strategy and configurable XP) is chosen, with a hybrid borrowing design A's boolean XP flag.
- lesson 85 — Prevention: bake module awareness into planning. The two-PRD skill becomes three steps, adding a sketch of the major modules to build/modify, an active hunt for deep modules testable in isolation, and user confirmation before the template is written.
- lesson 86 — Course summary: the seven phases of AI development (grill, research, prototype, PRD, issues, implement, review) and the compounding loop of updating prompts/skills and writing down your process after each review.
- lesson 87 — Appendix on Greenfield projects. From a blank page: grill → save decisions as markdown docs in the repo → prototype → PRD. The first PRD must specify AX (agent experience) — feedback loops, technology choices, module shape, testing strategy — often before UX.
- lesson 88 — Appendix on `grill with docs`: the agent's four info sources, the two questions it struggles with ("why did you do it this way" → ADRs, "what is an XXX" → glossary/ubiquitous language), and the skill that creates a `context.md` glossary plus ADRs as a drop-in replacement for grill-me.
- lesson 89 — Week-two office hours #1: Q&A on DX vs AX docs, exploring repos (and skepticism of GraphiFi/knowledge graphs), burnout/tactical-vs-strategic programming, agent security (data exfiltration), smart/dumb zone and compaction, polyrepos, and a demo of the new stateful `teach` skill.
- lesson 90 — Week-two office hours #2: the seven phases, "good enough" and prototyping, large-team collaboration (GitHub ACE), cheaper sub-agent models, and a demo of GitHub Actions + Sandcastle workflows (agent implement/review labels, PRD→issues, merge-conflict, architecture-review cron).

## Sections (L2)

### lesson 81

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson81.en.srt#lesson81]]`
- Summary: Through building the course, Matt has shifted further toward prototyping as a way to flush out unknown unknowns during planning. He points to an in-progress `prototype` skill in his skills repo (churny, not yet course-ready) that runs during grilling or any planning stage. It has two branches: pure logic testing and UI testing.
- Key claims: The logic branch builds a tiny interactive terminal app that pushes a complicated, time-varying data model through cases hard to reason about on paper, driven by key presses to move it through time — useful because most apps are interactions on a piece of data; the UI branch generates several radically different UI variations on a single route, switchable via a URL search param and a floating bottom bar, so you can click left/right and iterate ("take a bit from C") for UI design; Matt uses the logic variant more often; more branches may be added.
- Learner-relevant: Gives a concrete mental model and tool for prototyping before the PRD — prototype logic loops and competing UI variants instead of trying to reason everything out in prose.

### lesson 82

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson82.en.srt#lesson82]]`
- Summary: Defining software architecture is the one place human-in-the-loop makes the crucial difference, because current agents are poor at architecture and design systems hard for themselves to use. Organizing a codebase for AI is therefore a high-impact, essential skill. A bad codebase is dozens of shallow modules whose import/export chains an agent must traverse from scratch; a human builds instinct about groups of files but the AI cannot.
- Key claims: Restructure into larger chunks and bake the code's intention into its structure — "deep modules" from John Ousterhout's *A Philosophy of Software Design*; a deep module is a thin interface (few functions/properties) hiding a large implementation, and the more implementation behind a simple interface the better; because the public interface rarely changes, its tests rarely change, giving stable feedback loops; deep modules also cut the developer's cognitive load, which AI-era work otherwise raises ("knackered" devs), and let the developer focus on interfaces while AI handles implementations — Matt reads tests more than implementations and treats modules as "gray boxes"; concrete example — his custom video editor (front-end reducer/selectors, ~20-file back-end API, a CLI monitoring OBS files and doing silence detection, local DB) had bugs at the seams between pieces, so he wrapped the whole flow in a service (an SDK for the front end plus a back-end API handler) turning it into one deep module and enabling TDD on the entire editor flow; identifying and fixing this is not something AI does without a human prompting it, so developers must "develop the language" to discuss deep modules and embed that thinking in planning.
- Learner-relevant: The central architecture model for the whole section — why deep modules help both AI navigation and human cognition, and how to recognize feedback-loop problems that are really architecture problems.

### lesson 83

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson83.en.srt#lesson83]]`
- Summary: Presents the `improve codebase architecture` skill, which turns a bad codebase into a good one. It defines a deep module (small interface hiding a large implementation), then tells the AI to explore the codebase organically using the agent tool with subagent type `explore`, noting friction where understanding one concept means bouncing between small files.
- Key claims: Friction prompts include shallow modules whose interface is nearly as complex as their implementation, pure functions extracted just for testability where the real bugs hide in how they are called (a common LLM pattern), and tightly coupled modules creating integration risk in the seams; after exploring it presents candidate clusters without proposing interfaces yet, and the user picks one; then step four spawns multiple subagents in parallel, each producing a radically different interface to maximize diversity; it then recommends the strongest design and proposes a hybrid if elements combine well; the user picks or accepts, and the skill creates a refactor RFC as a GitHub issue that can be turned into a Kanban board; Matt usually targets a suspected problem area but for the demo runs it "clean" and asks the learner to compare notes.
- Learner-relevant: A repeatable procedure — and explicit multi-agent diversity technique — for deepening a module, plus the convention of expressing the outcome as an RFC/issue rather than an immediate refactor.

### lesson 84

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson84.en.srt#lesson84]]`
- Summary: Demo of `improve codebase architecture` on the cohort app. Candidates include merging quiz scoring, CRUD, and XP awarding into one deep module, and consolidating the student progress system. Matt reveals he deliberately left one badly coded service: the quiz scoring service uses a raw database instead of the shared DB and has no tests — as if written by a contractor foreign to the codebase.
- Key claims: The tool recommends candidate #1 because it is the only place mixing raw `better-sqlite3` SQL with the app's Drizzle ORM; it then spawns three design agents — minimal interface, flexible interface, and caller-optimized interface — because seeing multiple options from the AI builds design taste and you can re-run the skill later to improve what you built; it recommends design B: a `createQuizModule(db, scoringStrategy, ...)` factory (injected/dynamic scoring strategy, XP amount configurable outside the module) exposing ~8 methods (get quiz for lesson, get best attempt, latest attempt, attempt history, get stats, submit attempt, save quiz, delete quiz) so instructor and student call the same module; the recommendation borrows design A's `xp awarded` boolean instead of a number-or-null because the XP amount is an implementation detail the caller shouldn't need; it emits a GitHub issue with a before/after showing callers going from several manual orchestration calls to one or two; the underlying diagnosis is that manual orchestration of three shallow, tightly coupled services is where the bugs come from; the result is a testable gray box; a learner takeaway is to ask the LLM directly what jargon like "side effects", "transactional domain operations", or "monolith" means, because learning those phrases lets you prompt the model with them.
- Learner-relevant: Concrete output shape of the architecture skill (candidate → parallel interface designs → recommendation/hybrid → RFC), a real example of deep-module design, and the habit of acquiring the LLM's own architectural vocabulary.

### lesson 85

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson85.en.srt#lesson85]]`
- Summary: The cure for a bad codebase is a human using `improve codebase architecture` iteratively over time. This lesson covers prevention: build module awareness into planning so shallow modules are never created in the first place, especially during multi-session AFK work. To that end the two-PRD skill is now a three-step process.
- Key claims: Just before writing the template, the skill says to sketch out the major modules you will need to build or modify to complete the implementation, actively look for opportunities to extract deep modules that can be tested in isolation (a deep module encapsulates a lot of functionality in a simple, testable, rarely-changing interface), and check with the user that these modules match their expectations; this puts module awareness at the most important moment — designing the new implementation — so the right seams are tested, TDD loops are properly enforced, and tests and implementation are higher quality; framing is prevention vs cure.
- Learner-relevant: How to prevent shallow-module debt by baking deep-module thinking into the PRD/planning step, not just cleaning up afterward.

### lesson 86

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson86.en.srt#lesson86]]`
- Summary: Course conclusion and synthesis. Matt describes AI development as seven phases worked through in a "weird security order" that loops back on itself: grill, research (and prototyping), PRD/spec, PRD-to-issues, implement (human-in-the-loop or AFK), and review.
- Key claims: The grill is the interview that hardens an idea before it becomes a PRD; research may be needed (third-party APIs, tooling, options) and may involve pausing grilling to prototype; all of it produces a PRD — a destination document that can be reviewed by the team; the PRD becomes issues with individual tickets and blocking relationships; implementation is either human-in-the-loop (you watching) or fully AFK (the agent picks up issues and reaches the destination); review checks the destination was reached, everything in the PRD was implemented, coding standards were met, and also reviews the process — updating prompts, changing skills, and writing the process down so you compound and get better; Matt stresses this order is just his "tech" and learners may find their own way and name phases as they like; AI coding gives permission to build things once thought impossible.
- Learner-relevant: The whole-course mental model tying planning, delegation, and review into one compounding loop, and permission to adapt the phase names/order to your own workflow.

### lesson 87

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson87.en.srt#lesson87]]`
- Summary: Appendix on Greenfield (blank-slate) vs Brownfield (existing) projects. Most of the cohort works brownfield ("the field is green" means nothing built there yet; brownfield means building on/integrated with what exists). For a blank page Matt starts with a grilling session, saves what he captures as markdown documents in the repo, iterates across multiple grilling sessions, then moves to prototyping to clarify the picture before writing the PRD.
- Key claims: Greenfield PRDs differ from brownfield because of UX vs AX — brownfield usually has the fundamentals nailed so you can focus on the end user's experience, but greenfield must start with AX (agent experience, the agent's experience working in the codebase), so the first PRD must address AX alongside UX goals; AX covers four things — feedback loops (types, tests, pre-commit hooks, formatting) that keep the agent producing high-quality code; technology choices (language, front-end framework) that are hard to swap later and should be grilled on; module shape (initial deep modules), because architecture is central to agent experience; and testing strategy (what to mock, whether to use a test database) which ties into module shape; the first PRD is crucial and you may need an AX PRD before even looking at UX; you cannot sacrifice AX for UX — they must be tied together and what you build feeds into how you build it; once AX is sorted (often via its own PRD) you can start implementing issues, reviewing, and you are effectively back in a brownfield loop, so the real difficulty of greenfield is just setting up the agent experience.
- Learner-relevant: A concrete greenfield workflow and the AX checklist (feedback loops, tech choices, module shape, testing strategy) to include in a first PRD so the blank-slate project becomes tractable.

### lesson 88

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson88.en.srt#lesson88]]`
- Summary: Appendix solving a problem that emerged from using GrillMe repeatedly on the same project. It maps the agent's sources of information — the code (current commit), the commit history (bisect, how things used to be), GitHub/issues via the GitHub CLI (what people said about the code, linked to issue numbers in commits), and user messages — then identifies two questions hard to answer from these alone. The first, "why did you do it this way", is addressed by ADRs; the second, "what on earth is an XXX", is addressed by a shared glossary.
- Key claims: ADRs (architectural decision records) are small markdown files in the codebase explaining why a decision was made and what alternatives were considered, easy for any agent to access, so the agent does not recommend repeating a trade-off; a glossary is needed for business jargon the agent does not know — Matt keeps his in a `context.md` at the repo root, defining terms like course, section, lesson, ghost lesson/ghost section, and "materialization cascade", so he can name the concept instead of spelling out a verbose definition; this comes from domain-driven design's "ubiquitous language" shared between domain experts, developers, and the code, which also makes naming variables and finding things easier; these docs should be created at the earliest moment of the grilling session, before the PRD, because otherwise issues get created with old language — grill, agree the glossary, add any ADRs, commit, then build the PRD on top; `grill with docs` is a drop-in replacement for grill-me (which is stateless), creates the `context.md` glossary and ADRs, and only offers ADRs when a decision is hard to reverse, surprising without context, or the result of a real trade-off; Matt uses grill-with-docs for code work and plain grill-me for non-code work.
- Learner-relevant: A concrete convention (root `context.md` glossary + ADR files) and skill for giving the agent the "why" and the domain language it cannot infer from code — created during grilling, before the PRD.

### lesson 89

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson89.en.srt#lesson89]]`
- Summary: Week-two office hours #1, formatted as 15 minutes of Q&A, a 15-minute demo, then 15 more minutes of Q&A (Slido questions are voted to the top). Q&A covers documenting a codebase for devs vs agents, exploring repos, tooling skepticism, burnout, agent security, context limits, and polyrepos; the demo introduces and runs the new `teach` skill on both a Rubik's Cube and the cohort repo.
- Key claims: DX (developer experience) vs AX (agent experience) — devs skim docs while agents use them well, so AX now matters more, though both need a well-designed codebase, automated checks/feedback loops, and human review; for exploring a repo Matt prefers letting the agent run unsteered and noting where it hits friction, and for personal learning the `teach` skill (`teach me about this code base`); he is skeptical that knowledge-graph tools like GraphiFi work well because Claude Code found the efficient approach is filesystem access plus powerful tools like grep, not an added summary layer; on AI overwhelm: harnesses (Claude Code, Cursor, Codex) have settled into a similar shape (a text box, a context window) since December, so refocus on your own process — tactical programming (on-the-ground coding) is being eaten by AI but strategic programming (what to build) still needs a human; security splits into the security of the software you create and of the agent itself, the main agent risk being data exfiltration — a `fetch` can also be an outbound push via prompt injection (evil.com tells the agent to curl your codebase elsewhere) — mitigated by sandboxing and restricting outbound network traffic to approved URLs; on the 120k "smart zone": the decline is a gentle curve, not a cliff, so decide whether the remaining work is easy enough to trust a dumber model to finish (some tasks run to 250k), or compact at the middle of a clearly-bounded task, and watch for lossless compaction changing this; polyrepos — use a wrapper repo (with worktrees) that references the other repos, holds `CLAUDE.md` and skills, and is where the agent runs, but a monorepo is best though every change can trigger deploys in both; the plugin `Git Worktree` / Sandcastle handles multiple sessions on one codebase; on coding standards — no standard is truly universal, so build a company-wide set (kept outside the repo and fetched in, via an RFC process) rather than everyone making their own; on getting AI to write to standards — add an automated review stage: implement to pass tests first, clear context, then have a fresh review agent apply coding standards to the diff (a red/green/refactor loop), since overloading the implementation agent makes it perform worse; cognitive debt is mitigated by deep modules and hiding complexity behind a tested interface; for prioritizing a raw pile of features, find the core value proposition and show something that invites rich feedback (learned from the book *Shape Up*); the `teach` skill is stateful (like grill-with-docs, unlike stateless grill-me) and saves a teaching workspace with `mission.md` (the learner's goal), reference docs (glossary, a condensed single-card cheat sheet), `resources.md` from high-trust resources rather than parametric knowledge, learning records, lessons, and notes, guided by knowledge/skills/wisdom and the zone of proximal development (always just-challenged-enough), and can onboard a new starter onto a repo (`teach me about this repo`), grounding lessons in a real vertical slice of code; Matt is a teacher, not a pundit, on questions of the future/cost of agentic coding, and recommends hooking coding agents to observability to compare models/sessions.
- Learner-relevant: A rich Q&A surface of practitioner positions (AX over DX, grep over knowledge graphs, sandboxing, smart/dumb zone, company-wide standards, implement-then-review) plus a working template for a stateful teaching skill that doubles as a codebase-onboarding tool.

### lesson 90

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson90.en.srt#lesson90]]`
- Summary: Week-two office hours #2, same 15/15/15 format. Q&A covers the Anthropic subscription change, "good enough", large-team adoption, cheaper sub-agent models, TypeScript/knowledge leverage, and continuous shipping; the middle demo shows GitHub Actions + Sandcastle workflows that implement, review, and de-risk PRs AFK.
- Key claims: Anthropic is moving plan usage so AFK work draws from a small bonus API budget rather than the main subscription, so Matt will move AFK work from Claude Code to Codex (which allows generous AFK use) and ship support into Sandcastle; the seven phases are grill, research (cache expensive exploration into a research doc), prototype, PRD/spec, PRD→issues, implement, and QA; "good enough" means the most relevant questions that define success have been answered — and prototyping is the secret weapon (build two contrasting prototypes, e.g. WebSockets vs SSE vs a third-party service, and feel which is better); large teams: 3–10 is the right size, everything up to the PRD should be collaborative (shared grilling with a single AI, GitHub ACE / agentic coding environment with a Slack-like interface, shared prototypes, feeding Google Meet transcripts to the agent), then one person implements the agreed issues and the group reviews together, avoiding the bus factor; skills are cross-agent (symbolic links / agent-agnostic); to route exploration to cheaper models, steer via `CLAUDE.md` (e.g. "whenever you use explore use Haiku" — two orders of magnitude cheaper, though behavior varies by model); learning a specific language like TypeScript pays off because your understanding gates the agent's output — you can encode knowledge into practices so agents never repeat the mistakes you can foresee; demo of Matt's open-source `course video manager` repo: label an issue `agent implement` → a GitHub Action checks out main, runs `sandcastle run` with a prompt file (similar to the Ralph prompt but no loop, ~54 lines, includes red/green/refactor) → commits, pushes, opens a draft PR with `agent review` → a second action runs a review agent (with a long built-in coding-standards prompt) that comments and marks it ready; an `update branch` workflow rebases/merges and lets an agent fix merge conflicts (more capable than the simpler Symphony); an `agent 2 issues` label on a PRD auto-creates sub-issues which `agent implement` then iterates like a Ralph loop; an `architecture review` cron at 9am on weekdays creates an issue suggesting an architecture improvement (a prompt derived from the `improve codebase architecture` skill, with a mermaid diagram); no Docker is needed on GitHub Actions and the token is read-only, which is fine for open-source repos but must be tightened for closed-source; PRs/PRDs belong in GitHub/Jira/Linear, not local files; they can be shown on a GitHub project Kanban (milestones via the API); on shipping, adopt continuous shipping (release every time CI runs) rather than big releases, keep tests high quality and run on every change, and QA has not changed pre/post AI — pull the PR down locally and test it hard; extract implicit coding standards by scraping your own PR review comments via the API into a growing dataset rather than asking the agent to infer standards from code it can already read; the AI SDK is still relevant but more for building AI-powered apps than for being an AI-powered developer; review now has three axes — UX, DX (still important but less so), and AX (critical: if agents can't find files, get concepts wrong, or get low-quality test feedback, they produce crap code).
- Learner-relevant: Shows how to turn the course's skills into a fully AFK, label-driven GitHub Actions pipeline (implement → review → update branch → architecture cron) and closes with the AX/DX/UX review framework that reframes what "good code" means in the agent era.
