# Digest — ai-coding-for-real-engineer (part 5: lessons 41-50)

## Overview (L1)

- lesson 41 — Introduces "tracer bullets" (from *The Pragmatic Programmer* by Thomas & Hunt): systems have layers, LLMs plan horizontally layer-by-layer, and you should instead slice work into phases that each touch every layer (vertical slices) so you get early, frequent feedback. AI already knows the term, so saying "use tracer bullets" plus a brief explanation is enough.
- lesson 42 — Exercise: open a fresh zero-context Claude session, use the new "PRD to plan" skill (written with the skill-writing skill, with tracer bullets baked in), delete the previous naive plan to keep the test fair, and compare the new plan against the old one.
- lesson 43 — Solution to the PRD-to-plan exercise: the skill runs an explore phase (on cheaper Sonnet 4.6), asks for feedback on proposed phases before committing, and writes a plan whose phase one is a tracer bullet/vertical slice. Instructs the AI to record only durable architectural decisions ("don't plan what you can't plan").
- lesson 44 — Exercise: feed the PRD and plan to a new Claude Code session, say "do phase one", turn on accept-edits (not plan mode), and watch it implement. Decide whether to clear context between phases and commit at the end of each phase.
- lesson 45 — Solution/walkthrough of phased implementation: the agent explores, builds a small tracer-bullet analytics service, passes tests, and wires the full stack, staying inside the context "smart zone". Demonstrates commits-as-safety-points, bug fixing, and why commit messages matter for future agent sessions.
- lesson 46 — Aside on Claude Code's "ask user question" multiple-choice UI: opt in per skill/prompt with "use the ask user question tool", or suppress it globally with a CLAUDE.md instruction. Instructor dislikes it and blocks it globally.
- lesson 47 — Morning office hours (Q&A via Slido): GitHub/Sandcastle as an agent runner, HITL vs AFK tasks, concise-skill writing, steering placement (review is best), context-window discipline (handoff/compact, progressive disclosure, kill auto-memory), MCP vs cached research, and the "code quality matters more" thesis.
- lesson 48 — Afternoon office hours (Q&A): encoding practices like DDD into every skill, TDD/red-green-refactor, fixing legacy/pre-AI code bases via test seams and feedback loops, tactical vs strategic programming, parallel agents, team handoff artifacts (primary/secondary sources), model/provider portability, and hating memory.md.
- lesson 49 — Lecture: "code is cheap" is wrong — software quality matters *more* in the AI age. Defines quality as "easy to change" (Ousterhout), explains software entropy and the cludge meter, and argues AI is an entropy accelerator because it copies the code base and lacks human memory/feedback loops.
- lesson 50 — Lecture: deterministic quality comes from feedback loops, not just probabilistic steering via AGENTS.md/skills. Uses strong types (TypeScript), type checking, and automated tests as feedback, and introduces the "do work" skill (plan → implement → seek feedback → commit) as the reusable loop.

## Sections (L2)

### lesson 41

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson41.en.srt#lesson41]]`
- Summary: The instructor's favourite discovery from *The Pragmatic Programmer* — tracer bullets. Systems are made of layers (database/API/front end, or services within an app) that must be integrated. LLMs default to planning "horizontally" (phase 1 = whole service + tests, phase 2 = whole component, phase 3 = whole route), so you get no end-to-end feedback until late. Tracer bullets (a.k.a. vertical slices) force each phase to pass through every layer.
- Key claims: LLMs tend to code horizontally by layer when they plan; the fix is phases that each touch every layer (vertical slices), borrowed from tracer bullets in *The Pragmatic Programmer*; the metaphor is WWII anti-aircraft guns loading a phosphorescent tracer round every ~6 rounds so gunners can see where shots are going and adjust — early feedback, as often as possible; tests for a service are "meaningless" if the service design won't match later phases; AI already knows the tracer-bullets concept, so the prompt can be as short as "use tracer bullets" plus a brief explanation.
- Learner-relevant: Gives a reusable two-word prompt and mental model for planning with AI; it is used throughout the rest of the course and underpins the PRD-to-plan skill and the phased implementation workflow.

### lesson 42

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson42.en.srt#lesson42]]`
- Summary: A hands-on exercise comparing plans. Open a new Claude session with zero context, invoke the newly added "PRD to plan" skill (written with the instructor's skill-writing skill and containing many tracer-bullet references), pass in the PRD, and run it. Delete the original naive plan first so the previous plan cannot influence the model, keeping the comparison fair.
- Key claims: The repo ships a "PRD to plan" skill; run it from a fresh Claude Code instance by typing the skill name and tabbing to autocomplete, passing the PRD as an argument; delete the old plan before running so it is a clear test against Claude's default planning; the exercise is to notice how the new plan differs and whether it improves on the naive plan.
- Learner-relevant: Teaches how to A/B a custom planning skill against a harness default, and reinforces the idea that the prompt/skill is where process control lives.

### lesson 43

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson43.en.srt#lesson43]]`
- Summary: The solution run of PRD-to-plan. It opens with an explore phase (visible as using Sonnet 4.6, a cheaper model — "a good use of resources"), then returns a proposed phase breakdown and asks for feedback on the phases *before* writing the plan. Phase one is deliberately a vertical slice: analytics service + instructor route + summary cards with the simplest possible data. The instructor merges five phases down to three (2+3 are UI concerns; 4+5 are small and touch the same code area).
- Key claims: PRD-to-plan asks for phase feedback before committing, which is where the human adds taste; phase one is the tracer bullet that "wires up the full stack" with the simplest data (three summary numbers), flushing out unknown unknowns before later phases; the skill instructs the model to "identify durable architectural decisions before slicing" — high-level decisions unlikely to change — i.e. "don't plan what you can't plan"; the resulting plan is more prose/spec than pseudo-code, with less implementation leakage; grouping small related phases (e.g. empty states + admin access) into one session is reasonable.
- Learner-relevant: Shows the concrete shape of a good plan: tracer-bullet phase one, durable decisions only, phase grouping by shared code area, and a human checkpoint before the plan is written.

### lesson 44

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson44.en.srt#lesson44]]`
- Summary: A short exercise kicking off phased implementation. With the PRD and plan in the repo, open a new Claude Code session, pass in both files, and say "do phase one". Toggle accept-edits on (shift+tab) rather than using plan mode, so the agent starts writing code immediately. Watch whether it explores first and how the code turns out.
- Key claims: Prompt the agent with the PRD + plan and "do phase one"; use shift+tab to accept edits (explicitly *not* plan mode) to let it churn out code; at the end of a phase you choose between clearing context and rerunning the prompt for the next phase, or continuing in the same context; default advice is to clear context at the end of each phase if unsure; commit at the end of each phase to create a safe restore point.
- Learner-relevant: Establishes the phase-by-phase, commit-per-phase implementation loop and the context-clearing decision that lesson 45 demonstrates in practice.

### lesson 45

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson45.en.srt#lesson45]]`
- Summary: Walkthrough of the phase-one implementation. The agent explores, creates its own tasks, builds a deliberately small analytics service ("only enough features to satisfy the tracer bullet"), passes 12 tests, then builds the dashboard component and route, ending around 32–34% context (still in the "smart zone"). The instructor commits, QAs the dev UI, finds a bug (total revenue shows "free"), fixes it in the same context, then completes phases two and three.
- Key claims: Tracer bullets keep early code intentionally minimal — the service starts small and grows later; the agent explores the codebase first (about a minute) even without plan mode; "smart zone" vs "dumb zone" is a working model for context health (clear around 35–40%, dumb zone roughly ~120k tokens); clearing context forces a re-explore that costs ~30s of catching up but keeps you in the smart zone; using Claude Code to commit produces detailed commit messages, and commit history is a high-value signal for future agent sessions (code + reason tied together); bug fixes can be done in-context when budget allows, otherwise batch bug fixes into one session; the implementation stage is largely hands-off because the PRD and plan specify a clear destination and journey.
- Learner-relevant: Turns the abstract plan into an observed workflow — tracer-bullet minimalism, context budgeting, commit hygiene, QA checkpoints, and the claim that the approach scales to large builds given a deeper PRD and a well-thought-out plan.

### lesson 46

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson46.en.srt#lesson46]]`
- Summary: A short aside on Claude Code's "ask user question" tool — an opt-in multiple-choice UI for asking the user questions during a skill or prompt. The instructor demonstrates it (asking eye colour), notes the user can select, free-type, or decline, then explains it divided opinion in the previous cohort and that he dislikes it.
- Key claims: "Ask user question" is a Claude-specific UI you opt into in any skill or prompt by saying "use the ask user question tool"; it presents options plus a free-text box and records things like "the user declined to answer questions"; the instructor finds it harder to navigate than reading plain text, so he has "don't use the ask user question tool" in his global CLAUDE.md to suppress it everywhere; if you like it, add it to your skills/prompts, and it is currently Claude-only (expect others to copy it with different names).
- Learner-relevant: Teaches a concrete harness behaviour and the pattern of controlling defaults via global CLAUDE.md versus opting in per skill — a small but real example of steering.

### lesson 47

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson47.en.srt#lesson47]]`
- Summary: The morning office-hours session (cohort 4, ~5,000 people; questions via Slido). It is casual in tone but dense with teaching: the instructor's biggest recent workflow change, HITL vs AFK task types, how to write skills, how not to micromanage AI, where to put steering instructions, context-window discipline, MCP versus cached research, and closing on why code quality matters more than ever.
- Key claims: Biggest personal workflow change is using GitHub as a first-class agent runner — running Sandcastle inside GitHub Actions so a label on an issue fires an action (local dev + Docker sandboxes otherwise); tasks split into HITL (human-in-the-loop, e.g. grilling interviews) and AFK (away-from-keyboard, well-specified long work suitable for cloud/delegation) — plan with human loop, execute AFK, often review human loop; the best way to scale is delegating AFK work; when scaffolding skills with AI, delete as much as possible, keep skills short and concise because long skills bury the important instructions, choose words carefully (ALL-CAPS "must" is a hammer; prefer a chisel/scalpel), and update them as you notice issues; don't micromanage the agent — widen your bounds of acceptability, but encode material issues (e.g. "don't use useEffect, use React Router primitives") as steering; code bases should be easy to change (Ousterhout's *Philosophy of Software Design*; Fowler's *Refactoring*); steering belongs at the *review* stage (not planning — too high-level and instruction-dense; not CLAUDE.md — pushed to every session; not implementation — context is strained), where automated review has license to change code; context-window tactics: handoff skill to a new session versus `compact` to summarize in place, keep the smart zone, dumb zone ~120k tokens; progressive disclosure via context pointers and linked docs beats CLAUDE.md "rules" that dump everything into the window (he has seen people start with 250k tokens already); he does not really use MCP servers — prefer caching needed docs in a local markdown file during a research phase rather than permanently adding context (Context7 mentioned but unused); short skills are impactful and easier to maintain/security-vet/vet (Grill Me as example); kill automatic memory (agents being stateless is good — optimize for the stateless agent and manage your own context); Goal mode blows through context (sessions to 500k) whereas AFK/Ralph-loop slicing gives control and is cheaper because token cost compounds deeper in the window; teaching needs knowledge (explainers), skills (interactive exercises), wisdom (real-world interaction/Discord), a mission, and challenge just enough (zone of proximal development) — encoded in his in-progress "teach" skill.
- Learner-relevant: A high-density source for the course's core operating principles — AFK delegation, concise skill authoring, steering placement at review, progressive disclosure, context-cost economics, anti-memory stance, and the "code base easy to change" definition of quality.

### lesson 48

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson48.en.srt#lesson48]]`
- Summary: The afternoon office-hours Q&A. It covers getting an agent to follow practices like DDD, TDD, and test seams; sharing skills across repos; skills cluttering the context window; tactical versus strategic programming; parallel agents; team-wide handoffs and progressive disclosure; the grill-with-docs → PRD → issues flow; model/provider portability; converting a pre-AI codebase; and why implementation time collapsing changes the SDLC.
- Key claims: To make an agent follow best practices (DDD = domain-driven development, the "blue book"), encode them in *every* skill you use, mention the things you truly care about in the planning phases (e.g. test seams — the places where you write tests), and if it still fails, invest more tokens in review (spend fewer/cheaper tokens in implementation, then have an expensive agent review against spec, coding standards, and best practices); agents have parametric knowledge (trained) and contextual knowledge (passed in), so believing they "know" DDD parametrically is not enough; TDD/red-green-refactor is an excellent way to get higher-quality code because agents thrive on feedback loops; no great setup for sharing/updating coding standards across repos (ideas: an NPM package with a post-install hook); be paranoid about the context window — skill *descriptions* live in it, so trim wordy descriptions and delete frameworks/skills you are not actively using; tactical vs strategic programming (Ousterhout): AI has eaten ~90–95% of tactical programming, but it is poor at strategic work (context-limited, better at narrow firefighting), so the strategic programmer is best positioned to get the most from AI; context-window size (1M) is partly marketing and partly billing (cost stacks with position); GPT 5.5 is ~400k; treat model evaluation like employee evaluation — set up processes above the model so you can swap providers quickly rather than evaluating each model; the "diagnose" skill attaches a feedback loop to bug fixing; run multiple parallel agents with worktrees via Sandcastle; every touch point in a team workflow should produce a handoff artifact (summarize a call transcript with an agent, feed it to a grilling session); use progressive disclosure / primary vs secondary sources (code base = primary; a summary of a conversation = secondary linking back to the primary transcript) and let the agent fetch deeper knowledge on demand; a working session flow is grill-with-docs → PRD → issues without clearing context between grill and PRD (the PRD is the handoff artifact), then clear if needed before issues, and don't over-grill the PRD (just implement once you know where you are going); large codebases are not inherently harder to explore than small ones if AGENTS.md points to the right files, the structure is well organized, there is a shared language between you and the AI, and you use "deep modules" (fewer large modules that break down, rather than many tiny ones); handoff (a flexible markdown artifact saveable to a temp dir, a GitHub issue, or a different agent) beats branch-fork (same project, same agent only); do not optimize for cost — optimize for quality, because below a quality bar you spend more time fixing agent mistakes than you saved; the teach skill encodes teaching practices and tracks progress/resources in a dedicated folder, and learning needs a mission; he uses the Anthropic skill-creator but finds it verbose and prefers first-pass AI then line-by-line human editing; memory.md is hated (context paranoia — anything entering the window without his knowledge); the SDLC changes because implementation time goes to ~zero, so there is far more planning and QA and estimates must change; his research is done without AI (books + an Obsidian graph); favourite prompt add-ons include "steelman this", "go up a layer of abstraction", "commit this", and "zoom out"; to make a pre-AI codebase AI-ready, do what Michael Feathers described in *Working Effectively with Legacy Code* (add test seams, tests, feedback loops, automated checks before refactoring) — good human code-base design is also good for AI.
- Learner-relevant: Extends the operating principles with concrete techniques for standards enforcement, TDD, context hygiene, parallel agents, team handoffs, and legacy migration, plus a strong statement of the strategic-programmer thesis.

### lesson 49

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson49.en.srt#lesson49]]`
- Summary: A lecture refuting the "code is cheap / the old rules are for boomers" narrative. The instructor defines software quality (borrowing Ousterhout) as "is the code base easy to change", explains software entropy and the cludge meter (Pragmatic Programmer), and argues that because AI multiplies commits but is bad at entropy-reducing commits, AI acts as a software-entropy accelerator — making quality matter *more*, not less.
- Key claims: "Code is cheap" is wrong; quality matters more now and AI agents are more sensitive to it than humans; quality = easy to change (Ousterhout's *Philosophy of Software Design*), i.e. related information grouped together, low ripple/risk of unintended consequences, and good feedback loops to catch bugs before production; software entropy (Pragmatic Programmer): software tends to get worse, not better — most changes are made without continually improving the code, and every non-thoughtful commit raises the "cludge meter" (only refactors/redesigns/test-suite additions lower it); AI massively increases the number of commits but currently does not make the entropy-saving commits well, and figuring out a better design to prevent entropy is harder than building features or fixing bugs for humans too; the three inputs to an AI coding session are the prompt, the steering (skills/CLAUDE.md), and the code base — and the code base is the most important because agents copy it by default as the source of truth; AI is more susceptible to cludge than humans because it blindly copies bad patterns (even when instructed otherwise), has fewer feedback loops, and is stateless (no human memory to work around weird patterns); "garbage in, garbage out".
- Learner-relevant: Provides the theoretical foundation for the whole feedback-loops section and the counter-argument to the "AI makes code quality irrelevant" claim; establishes the definition of quality the course optimizes for.

### lesson 50

- Locator: `[[sources/ai-coding-for-real-engineer/20261001/lesson50.en.srt#lesson50]]`
- Summary: How to keep the agent producing high-quality code — proactively steering through AGENTS.md/skills only raises the probability of the right path, whereas feedback loops *deterministically* enforce quality. It frames feedback loops as the same tried-and-tested loop great engineers use, then introduces the "do work" skill and how the repo's type-check and test commands provide that signal.
- Key claims: AGENTS.md/skills steer probabilistically; feedback loops (agent produces code → you give feedback → it produces more, until quality suffices) enforce it deterministically; great engineers do not trust their instincts and build many feedback loops, so the course just applies the same practice to agents; the more and better the feedback loops, the better the output; strong types (TypeScript over weakly typed JavaScript) give the agent compile errors to learn from; automated tests run the code and check logic, and a higher-quality test suite gives more signal; the repo already has a `typecheck` script (React Router TypeGen + the TypeScript CLI) and a `test` script (`vitest run`), with test files next to services (e.g. `purchase-service.test.ts`); rather than putting "always seek feedback" in CLAUDE.md (pushed to every session even when not needed), the instructor prefers a reusable "do work" skill that plans (optional if working to a pre-written plan), implements, seeks feedback, then commits — the nicest way he has found to steer the LLM into a repeatable repo loop.
- Learner-relevant: Turns the lesson 49 thesis into an actionable mechanism — prefer deterministic feedback loops (types, type checks, tests) over probabilistic instructions, and package the loop into a reusable skill; sets up the exercises that build the "do work" skill.
