# PRD-to-plan（PRD-to-Plan Skill）

## Problem Statement

PRD 寫好之後，下一步是把 destination 變成 journey，也就是把整份需求拆成一段一段可以執行的 phase。把 PRD 丟給 agent 只說一句「把這個變成一份 multi-phase plan」，它會吐出一份天真計畫，水平切層、過度指定實作細節、完全沒引用 user story。要怎麼穩定地得到一份垂直切片、只寫耐久決策、又能回溯到 PRD 的計畫？

## Why it matters

計畫是每段實作 prompt 的地圖。後續每個 phase 都用「do phase N + PRD + 整份 plan」執行，計畫寫得不好，agent 就先把錯的層做完、引用到早就不存在的函式，feedback 拖到很晚才來。PRD-to-plan 是把 PRD 轉成可用 journey 的那個 skill，它直接決定後面每一段實作站在什麼地基上。

## How it works

呼叫方式是「PRD to plan」，把 PRD 用 `@` 帶進 prompt。它的工作流有四段：

1. **explore**：先探索程式碼庫，理解現狀。這一步用較便宜的模型執行，是合理的資源分配。
2. **propose**：提出一個 phase 切分草案，通常是垂直切片。
3. **ask**：把草案端給你，寫檔之前先徵求回饋。
4. **write**：得到你的意見後，才把計畫寫成本機檔案。

skill 的指令裡還有一條關鍵要求，就是 [[learn/ai-coding-for-real-engineer/elements/durable-decisions|耐久決策 (Durable Decisions)]]，先找出耐久架構決策再切 slice。

## In plain terms

把 PRD-to-plan 想成一個「計畫代筆」。你遞給它 PRD，它先自己翻一下程式碼，擬一份拆法給你看，你點頭或修改後，它才把最終計畫寫成檔案存下來。

## Practical use

完整鏈路是 to-PRD 先產出 PRD，然後在乾淨的新視窗裡呼叫 PRD-to-plan，確認 phase 切分後拿到計畫檔。之後每一個實作 phase 都用 [[learn/ai-coding-for-real-engineer/elements/phase-prompt|phase prompt]] 帶上 PRD 和計畫執行。

## Questions

### Q1. PRD-to-plan 在寫檔之前一定要做什麼？
A1. 把擬好的 phase 切分端給人看，先徵求回饋，得到確認才寫。它 explore、propose、ask、write 四段走完，沒有跳過確認直接產檔。

### Q2. 相對於「把 PRD 丟給 agent 直接要一份計畫」，這個 skill 多做了哪些事，為什麼那些事值得做？
A2. 它先探索程式碼、提出垂直切片草案、寫前先確認，並要求先找出耐久決策。這些動作讓計畫引用真實存在的架構、切法可被人工校正、細節不會在執行前就過期，判斷的價值在於把「計畫品質」從運氣變成流程。
