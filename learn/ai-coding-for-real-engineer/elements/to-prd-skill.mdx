# to-PRD（To-PRD Skill）

## Problem Statement

[[learn/ai-coding-for-real-engineer/elements/two-document-model|兩文件模型]] 要求先有 destination（PRD），但一份好的 PRD 不會憑空出現。你腦子裡有一個模糊需求，怎麼把它變成一份嚴謹、可交接、別人看得懂的 PRD？如果直接手寫，容易漏掉決定、跳過取捨；如果直接交給 agent 寫，agent 又不知道你的 taste。兩文件模型的 destination 該怎麼被生產出來？

## Why it matters

to-PRD 是「把訪談結果變成文件」的那一步。沒有它，grill-me 訪談出來的共識只活在對話 context 裡，session 一結束就沒了，也無法跨到新視窗。to-PRD 把 conversation context 固化成一顆持久、可交接的 destination，是 grill → 文件 → 跨 session 執行這條鏈路的關鍵樞紐。

## How it works

to-PRD 是一個 skill：它讀取當前 conversation 的 context，然後在本機產出一份 PRD 檔案。標準工作流是兩段式：

1. **grill-me**：先跑一輪訪談，把模糊需求釘成 shared design concept，確定 destination。
2. **to-PRD**：如果這個 build 太大、放不進同一個視窗實作，就呼叫 to-PRD，讓它把整個訪談 context 轉成一份 PRD 存成本機檔案。

to-PRD 的產出結構（見 [[learn/ai-coding-for-real-engineer/elements/prd-structure|PRD 結構 (PRD Structure)]]）包含：problem statement、solution（都從使用者視角出發），以及一長串編號的 user stories。PRD 的具體模板仍在演進、尚有爭議，但「問題陳述 → 解法 → 編號 user stories」是核心骨架。

## In plain terms

把 to-PRD 想成訪談的「謄稿機」。你剛跟 agent 聊完一輪（grill-me），把想做的事都釐清了。to-PRD 把這整段聊出來的共識，整理成一份正式的「需求文件」存下來，之後任何人（或任何新 session）拿到這份文件，都知道當初討論出什麼。

## Practical use

實際流程：開一個 grill-me session 訪談 → 訪談到位、context 也慢慢填滿 → 判斷這個 build 太大，呼叫 to-PRD → 得到一份 PRD 存檔 → commit。之後這份 PRD 就是兩文件模型的 destination，也是後續 [[learn/ai-coding-for-real-engineer/elements/phase-prompt|phase prompt]] 和 plan 的輸入。

## Questions

### Q1. to-PRD 做的是什麼事？
A1. 讀取當前 conversation context，在本機產出一份 PRD 檔案，把 grill-me 訪談的共識固化成一顆可交接的 destination。

### Q2. 為什麼需要 to-PRD，而不直接手寫 PRD？
A2. 因為手寫容易漏決定、跳取捨，而 to-PRD 直接把完整訪談 context 轉成結構化文件，保留了人類在 grill 過程中逐題釘下的 taste。
