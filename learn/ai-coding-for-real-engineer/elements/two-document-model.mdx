# 兩文件模型（Two-Document Model）

## Problem Statement

任務大到塞不進單一 context window，於是把任務拆解成多個 phase、每個 phase 在新視窗執行（見 [[learn/ai-coding-for-real-engineer/elements/context-window-decomposition|大任務拆解 (Context-Window Decomposition)]]）。但拆開之後，每個新視窗的 agent 是全新的、什麼都不知道。它怎麼知道整體目標是什麼、要做到什麼程度、自己這個 phase 跟其他 phase 怎麼接？拆解本身沒有回答這個問題。

## Why it matters

這是整個大計畫路徑的骨架。如果你只有「拆解」沒有「文件」，等於把大任務切成互不相識的碎片，每個 agent 各做各的，最後拼不起來。兩文件模型回答了「拆解之後誰負責一致性」——它讓一份跨多個視窗的計畫能被順序執行，也是後續 PRD、plan、phased implementation 每一步共同依賴的容器。

## How it works

社區收斂出兩份文件，分別承載「目的地」與「旅程」：

1. **Document 1 — destination（目的地）：spec/PRD（產品需求文件）**。它編碼了人類的 taste——你要的是什麼、不要什麼、長什麼樣、優先順序、取捨。它回答「做到哪才算完成」。這是人對產品的判斷，不是 agent 能自己決定的。
2. **Document 2 — journey（旅程）：plan.md**。它把 PRD 拆成一段一段的 phase，說明每段做什麼、順序如何。它回答「怎麼一步步走到目的地」。

這兩份文件必須能跨越 context window 存活：被寫在檔案系統裡，可以被後續任何一個新 session 用 `@` 拉進來。執行的 prompt 變成「we're going to do phase N」+ PRD + 整份 plan，這樣每個 phase 都知道全局，phase 之間不會踩到彼此的腳。

## In plain terms

把兩文件模型想成一次遠足。destination 是地圖上你要去的那座山（目標、為什麼去、到了要看到什麼）；journey 是你拆成 Day 1、Day 2、Day 3 的行程表（每天走哪一段、住哪）。你不會靠「記住整趟路」來遠足，因為會忘；你會帶一份地圖和一份行程表，每天出發前都看一遍今天要走哪段、以及它通向哪座山。

## Practical use

當你判斷一個 build 太大，就先寫 PRD（destination）再寫 plan（journey）。寫完之後，每個 phase 的實作都開一個新 session，prompt 固定帶上「do phase N + PRD + 整份 plan」。寫出好的 PRD 和 plan 是本節（grill-to-prd 節點）的主題——如何透過 [[learn/ai-coding-for-real-engineer/elements/to-prd-skill|to-PRD]] 把訪談轉成 PRD，以及 [[learn/ai-coding-for-real-engineer/elements/prd-structure|PRD 結構 (PRD Structure)]]。

## Questions

### Q1. 兩文件模型裡，destination 和 journey 分別裝什麼？
A1. destination（PRD）裝人類的 taste，回答「做到哪才算完成」；journey（plan.md）把 PRD 拆成 phase，回答「怎麼一步步走到」。

### Q2. 為什麼兩份文件必須能跨 context window 存活？
A2. 因為每個 phase 都在新視窗執行、agent 是全新的，只有文件能被新 session 用 `@` 拉進來，才能讓每個 phase 都掌握全局、保持一致。
