# 耐久決策（Durable Decisions）

## Problem Statement

把 build 切成 phase 時，最容易犯的錯是連實作細節一起規劃，寫進「phase 1 呼叫這個函式、phase 2 改那支檔案」。問題是你根本規劃不了你還沒知道的東西。細節在實作進行中必然變動，人類改掉前一個 phase 的實作，後面的 phase 立刻引用到不存在的東西，整份計畫的每一行都過期。

## Why it matters

計畫能跨 phase 存活的唯一原因，是它只寫那些「現在是這樣、到了 phase 3 還是這樣」的決定。計畫的價值不在於劇透每一行程式碼，而在於把不會變的架構軌道先畫好，讓每個 phase 都在同一條軌道上執行。寫太多細節，反而把計畫變成一份會腐壞的承諾。

## How it works

原則一句話講得完，叫「別規劃你無法規劃的事」。實際做法是在切 slice 之前，先把耐久架構決策找出來，也就是那些高階、短期內不可能變動的決定。在 analytics dashboard 的例子裡，skill 捕捉到的耐久決策有六項：

- **route 位置**：API 入口開在哪
- **schema**：資料表的結構
- **新增 analytics service**：新模組要不要存在
- **auth helper**：權限檢查怎麼共用
- **dependencies**：依賴哪幾套函式庫

切完這些軌道之後，每個 phase 只在軌道內填實作，不再逐行指定內部細節。

## In plain terms

耐久決策是「蓋房子先定樑柱」。樑柱的位置現在定好，後面每一層都照著長；你不需要現在就決定第三層掛哪一幅畫。

## Practical use

跑完 PRD-to-plan 之後，回頭檢查計畫的前置段落，看它列出的耐久決策是不是真的「現在知道、以後也不會改」。實作到 phase 2、3 時，如果發現某條細節在變，先確認它是不是真的不該出現在計畫裡。

## Questions

### Q1. 耐久決策和一般實作細節的界線在哪裡？
A1. 耐久決策是現在就能確定、之後也不容易變動的高階架構決定，例如 route 位置、schema、要不要新增 service；實作細節是函式名稱、內部演算法這種會隨實作推進而改變的內容。

### Q2. 一份計畫寫太多實作細節，為什麼會讓後面的 phase 執行得更糟？
A2. 細節在人類調整前一個 phase 的實作時就過期，後續 phase 照著引用會撞上不存在的東西，agent 要嘛卡住要嘛自行偏離計畫，判斷的關鍵是計畫的價值在耐久性，不在劇透。
