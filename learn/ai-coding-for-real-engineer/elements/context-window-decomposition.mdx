# 大任務拆解（Context-Window Decomposition）

## Problem Statement

一個小型功能或 bug 修正，通常在單一 context window 的 smart zone 內就能完成。但一個大型重構，或一次要交付多個功能的 build，會一路把 context 填到 dumb zone，模型開始產生幻覺、推理變差、連之前討論過的決定都忘了。把整個任務硬塞進一個視窗，結果是品質崩盤。任務大到塞不進一個視窗，怎麼辦？

## Why it matters

這是整條「大計畫」路徑的起點。如果不知道任務為什麼必須被拆解、以及拆解後由誰來負責銜接，後面所有兩文件模型、PRD、plan、phased implementation 的技巧都會失去根據。理解「為什麼要拆」，才知道「拆完之後需要什麼文件來把碎片接回一體」。

## How it works

context window 的「smart zone」是有限的（受 attention 的二次方擴張所限）。當一個任務需要的資訊量超過這個範圍，模型會掉進 dumb zone。解法跟人類一直以來做大型工程一樣：把大任務分解成小任務，讓每個小任務在一個全新的視窗裡獨立執行。

但拆解會引入一個新問題：碎掉之後的每個小任務，彼此不知道對方做了什麼、不知道整體目標是什麼。所以拆解不是只把工作切開，而是要**用文件把拆開的碎片接回一體**——這些文件必須能跨越多個 context window 存活。

- 小型任務：單一 context window 即可，不需要文件。
- 大型任務：拆成多個 phase，每個 phase 在一個新視窗執行，靠文件維持整體一致性。

## In plain terms

想像你一次只能記住十件事，超過就會忘。一件需要記住五十件事的大任務，你不能硬扛，得拆成五件各記十件的小任務。可是拆開之後，怎麼確保這五個部分合起來還是一個完整且一致的東西？你得把它們寫在紙上（文件），讓每一份手寫的紙都能跨過「記不住」的界線，被下一張紙的工作者看到。

## Practical use

當你判斷一個 build 放不進單一 context window 時，你就不再直接讓 agent 開寫，而是先進入「兩文件模型」：寫一份 destination（規格/PRD）決定「要做到什麼程度、長什麼樣」，再寫一份 journey（plan）決定「拆成哪幾個 phase、每個 phase 做什麼」。之後每個 phase 的 prompt 都把 PRD 和 plan 一起帶上，讓新視窗的 agent 知道全局。這正是 [[learn/ai-coding-for-real-engineer/elements/two-document-model|兩文件模型 (Two-Document Model)]] 要處理的。

## Questions

### Q1. 為什麼大型任務不能直接塞進單一 context window？
A1. 因為 context window 有 smart zone 上限，超過後模型掉進 dumb zone，會幻覺、推理變差、忘了前面的決定，品質崩盤。

### Q2. 拆解任務後，靠什麼把碎片接回一體？
A2. 靠能跨越多個 context window 存活的文件——destination（PRD）+ journey（plan），每個新視窗的 phase 執行時都帶上這兩份文件。
