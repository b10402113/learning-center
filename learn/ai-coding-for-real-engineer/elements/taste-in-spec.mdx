# 規格裡的 taste（Taste in the Spec）

## Problem Statement

兩文件模型的 destination（PRD）被描述為「編碼了人類的 taste」（見 [[learn/ai-coding-for-real-engineer/elements/two-document-model|兩文件模型]]），但「taste」這個詞很抽象。到底什麼是規格裡的 taste？為什麼一份好的 PRD 的價值往往不在於把功能列全，而在於那些細微的取捨判斷——比如「sales 和 enrollments 是兩回事，不能混在一起」？如果說不清，就容易把 PRD 寫成一份羅列功能的清單，而失去了真正讓產品對的判斷。

## Why it matters

這是兩文件模型與 grill 流程的價值核心。agent 可以對抗式地一直問問題、幫你窮舉選項，但最終「要什麼、不要什麼、什麼才算對」是人類的判斷。把 taste 固化進 PRD，才讓 destination 有真正的內容，也才讓後續放手的實作不會偏離你的意圖。少了 taste 的 PRD，agent 實作時只能亂猜。

## How it works

在 grill → to-PRD 流程中，人類保持對 taste 的主導權，而 agent 扮演對抗式提問者。taste 具體透過以下幾種方式進入規格：

1. **Scope 決定**：grill 過程中一題一題釘下「做這個、不做那個」。例如 analytics dashboard 從「跨課程總覽（非單課程）」、到「新增 analytics route（不併入 instructor 頁）」、到「admin 也要有權限」、到「拉回以營收為主 + ratings（砍掉 quiz/geo）」——這些都是人類對產品價值的判斷。
2. **領域細節（domain nuance）**：好 spec 和模糊計畫的差別往往在這種細節。例如「sales ≠ enrollments」——因為有團隊購買（team purchase），一個人買了可能多人 enroll，所以銷售數字和報名人數不能混為一談，表格裡兩欄要分開。
3. **取捨與偏好**：例如「revenue 為主的 dashboard 加 ratings」「時間序列用 range selector（7d/30d/12m/all）並放 URL parameter」「單一 aggregate line chart + 可排序 per-course table」「用 bare recharts 不用 shadcn wrapper」「sidebar nav item」「30 天預設」「單一 no-revenue-yet empty state」——每個都是人類選擇，agent 無從替你決定。

## In plain terms

把 taste 想成做菜時的「手勁」。食譜（PRD）會寫明材料（功能）和步驟（user stories），但真正決定這道菜好不好吃的，是鹽放多少、火候到哪、哪個香料該少——這些是食譜寫不出來、只有做菜的人憑判斷決定的東西。規格裡的 taste 就是這些「鹽和火候」，讓同樣的食譜做出不同品質的菜。

## Practical use

當你跑 grill-me 時，對每一題都親自給出決定，而不是讓 agent 全權代答。把那些你「憑經驗覺得這樣才對」的取捨——尤其領域細節（如 sales vs enrollments）——明確講出來，讓它們被 to-PRD 固化進 PRD。這樣最後產出的 PRD 才不是一份功能清單，而是一份帶有你判斷的 destination，能讓放手的實作對準你的意圖。

## Questions

### Q1. 「taste」在規格裡具體指什麼？
A1. 人類對產品價值、scope、取捨與領域細節的判斷，例如「sales ≠ enrollments（因團隊購買）」、砍掉哪些功能、預設值用什麼。

### Q2. 為什麼 taste 不能交給 agent 決定？
A2. 因為 agent 可以窮舉選項、對抗式提問，但它不知道你的意圖與價值判斷；這些只有你能定，定完由 to-PRD 固化進 PRD，實作才不會偏離。
