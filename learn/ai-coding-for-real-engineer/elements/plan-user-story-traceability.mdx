# 計畫的 user story 回溯（Plan Traceability）

## Problem Statement

天真計畫列了一串 task，卻沒有一行說這些 task 是為了誰、為什麼。實作的 agent 在 phase 3 只知道「把這支檔案改掉」，不知道它在滿足哪一條需求；事後 reviewer 也答不出「這輪到底做完沒」。沒有 traceability 的計畫，是一份斷了根的清單。

## Why it matters

計畫的每個 phase 都要能指回 PRD 裡的一條 user story，這條線就是「為什麼」的載體。agent 知道自己在服務哪個需求，人知道某條 story 被哪個 phase 滿足，review 時直接拿 story 對答案。traceability 是讓計畫和 destination 保持同一個心智模型的黏著劑。

## How it works

PRD 的 user story 是編號的，格式是「as an instructor I want X so that Y」。編號就是計畫引用它們的鉤子。PRD-to-plan 寫出的計畫，每個 phase 都寫明「要建什麼、對應哪幾條 PRD user story」。以 analytics dashboard 為例，phase 1 的垂直切片對應的是「講師要看總營收」那一條，phase 3 的 admin route 對應「管理員要能代看任何講師的儀表板」那一條。

對照之下，天真計畫從頭到尾沒提過任何 user story，這是它失去「為什麼」的直接原因。而引用故事之後，整份計畫的實作洩漏也大幅減少，因為每一段工作都被釘回需求，agent 沒有空間自己加戲。

## In plain terms

計畫的每一站都要寫得出「這站是為了送誰到哪」。站與站之間的空洞，靠這條線補起來。

## Practical use

拿到 skill 產出的計畫後，逐 phase 檢查每條都引用了 PRD 的 user story 編號。review 到「這 phase 完成沒」的時候，直接回到它引用的那幾條 story，一條一條對。缺引用的 phase，當成計畫沒做完。

## Questions

### Q1. 為什麼 user story 一定要編號，計畫才能引用它？
A1. 編號給每一條需求一個穩定的位址，計畫才能精準寫「本 phase 對應 story 3」，不用重抄一整句需求，也讓 agent 和 reviewer 對到同一個位址。

### Q2. 計畫引用 user story 之後，為什麼實作洩漏會減少？
A2. 每段工作被釘回一條具體需求，agent 沒有空間自己補功能、改名函式或加戲，判斷的關鍵是引用讓「做什麼」和「為什麼做」綁在一起，遊走空間被收掉。
