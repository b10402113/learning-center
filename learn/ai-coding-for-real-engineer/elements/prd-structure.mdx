# PRD 結構（PRD Structure）

## Problem Statement

to-PRD 把訪談 context 產成一份 PRD（見 [[learn/ai-coding-for-real-engineer/elements/to-prd-skill|to-PRD]]），但「一份好的 PRD」到底包含哪些部分？如果只是幾段話描述需求，很容易模糊、缺取捨、缺驗收界線。兩文件模型的 destination 需要一個穩定的骨架，讓一份 PRD 對任何讀者（人或新 session）都足夠嚴謹、可執行、可判斷「做完了沒」。

## Why it matters

PRD 是兩文件模型的 destination，是所有後續工作的對齊基準。它的結構決定了資訊是否完整、決定是否被記錄、scope 是否被釘死。理解 PRD 結構，才知道 to-PRD 產出的東西為什麼能跨 session 存活並驅動實作，也知道一份「好 spec」和一份「模糊計畫」差在哪。

## How it works

to-PRD 產出的 PRD 由以下部分組成：

1. **Problem statement（問題陳述）**：從使用者視角描述要解決的問題，為什麼要做這件事。
2. **Solution（解法）**：從使用者視角描述解決方案長什麼樣、滿足哪些需求。
3. **User stories（使用者故事）**：一長串編號的清單，格式如「as an instructor I want X so that Y」——把需求拆成具體、可驗收的一條一條。
4. **Implementation decisions（實作決定）**：技術層面的實作選擇，例如新增哪個 service module、開哪條 route、共用哪個 component。
5. **Technical decisions（技術決定）**：架構/技術取捨。
6. **Testing decisions（測試決定）**：怎麼測、測哪些。
7. **Out-of-scope list（不做清單）**：明確列出這次不做什麼，畫出 scope 的界線。
8. **Further notes（其他註記）**：補充說明。

核心骨架是「problem statement → solution → 編號 user stories」，其餘部分（實作/技術/測試決定、out-of-scope）把 taste 和工程取捨也一併固化進文件。實作細節可以而且應該由人類指定。

## In plain terms

把 PRD 想成一張詳細的施工合約。上面寫清楚要解決什麼問題（problem）、蓋成什麼樣（solution）、一條一條的驗收項目（user stories）、用什麼材料怎麼施工（implementation/technical decisions）、哪些不做（out-of-scope）。任何接手的人，不管有沒有參與過前面的討論，光看合約就知道要交付什麼、標準是什麼。

## Practical use

grill 完 analytics dashboard 後，to-PRD 產出包含上述八個部分的文件：problem statement、solution、編號 user stories（as an instructor I want X so that Y）、implementation decisions（新增 analytics service module、instructor route、admin instructor route、shared component）、technical decisions、testing decisions、out-of-scope list、further notes。這份 PRD 隨後成為兩文件模型的 destination，接續 [[learn/ai-coding-for-real-engineer/elements/phase-prompt|phase prompt]] 和 plan。

## Questions

### Q1. PRD 的核心骨架是哪三部分？
A1. Problem statement（問題陳述）、Solution（解法）、編號的 User stories（使用者故事）。

### Q2. PRD 裡為何要有 out-of-scope list？
A2. 明確畫出 scope 的界線，列出這次不做什麼，避免後續執行時無限擴張，也讓「做完了沒」有明確判準。
