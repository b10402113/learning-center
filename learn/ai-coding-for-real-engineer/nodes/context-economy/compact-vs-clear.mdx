# compact 與 clear：sediment 問題

<LearningGoal>
說出 auto-compact buffer 的運作、重複 compact 的 sediment 問題，並在「什麼時候 clear、什麼時候 compact」之間做出正確選擇。
</LearningGoal>

## Lesson

context 越過尾端會自動執行 compact，因為 window 末端留著一段 **auto-compact buffer**（200k window 約 33k tokens、16.5% 的保留區，不放 token、不影響 LLM）。compact 用一個 **LLM** 把整段對話濃縮成小份 markdown 摘要：主要檔案留著、次要的只留引用、保留所有 user messages 與未完成任務、完整 transcript 存檔待查。49% 的 session 能被壓到 12%（23k tokens）——但摘要本身要花 token，重新探索也要花 token，兩邊都不是免費的。

那為什麼不讓 context 一直長、無限 compact 續命？因為每次 compact 都在 context 裡留下一層 **sediment（沉澱）**，撞 buffer 一次留一層，層層疊加，用不可預測的方式影響輸出；帶著沉澱層的 agent 處在跟平常不同的狀態。相反地，讓 agent 幾乎總以乾淨 context 開局，輸出更可預測、token 更省、更多時間待在 smart zone。因此重複 compact 是 anti-pattern。講師很少 compact（每個 conversation 最多一次），只在兩種情況：剛結束大 session 想追加 feedback、或 debug 複雜錯誤時想留著嘗試紀錄；其餘寧可 clear 重來，花一次重新探索的錢換乾淨的 context。
