# 公平比較的實驗設置（跑一次 PRD-to-plan）

## Learning goal

能在全新的零 context session 裡刪掉舊計畫檔、只帶 PRD，呼叫「PRD to plan」跑一次，並說出這樣設置為什麼能讓「新 skill 比舊方法好」這個結論成立。

## Lesson

你剛拿到一個新 skill，名字叫 PRD-to-plan，它宣稱能把一份 PRD 變成更好的執行計畫。想驗證這個說法，光看一次輸出還不夠。agent 的每個決定都由 context 裡的字驅動。context 是 agent 在當下能看到的全部文字，舊對話、舊檔案、舊計畫都算在內，每一行都會把輸出往某個方向帶。環境不乾淨時跑出一個好結果，你分不清功勞屬於新 skill，還是屬於視窗裡躺著的舊材料。所以要做的，是一場受控的比較。

比較要有基準，基準就是舊方法產出的天真計畫，naive plan。之前用最樸素的呼叫方式跑過一次。開一個新 session，把 PRD 用 `@` 帶進 prompt，只說一句「把這個變成一份 multi-phase plan，存成本機 markdown 檔」，後面什麼都不加。session 是跟 agent 的一段對話，prompt 是你丟給它的那句指令。PRD 是產品需求文件，把要做什麼功能、服務誰、為什麼要做寫清楚。agent 沒有 skill，沒有額外指令，憑直覺把需求切成一段一段的 phase。phase 是執行階段，一份大計畫拆成一塊一塊分開做。那份天真計畫長這樣。phase 1 把 analytics service 這整層做完，phase 2 做共享的 dashboard component，搭配 recharts 畫圖，phase 3 才接 route，phase 4 補 admin route 和連結。analytics service 是統計服務，route 是網址路由。四層沿著水平方向一路切過去，每一層單獨做滿，要到最後一個 phase，東西才真正接起來可以跑。中間那幾個 phase 全都無法驗證，跑完 phase 1，你只知道 analytics service 這層的程式編得過，不知道整條路通不通。計畫裡還直接寫死了函式名，那些函式在執行那一刻可能根本不存在，人只要在中途改掉某個 phase 的實作，這些名字當場過期。agent 急著交出看起來完整的東西，習慣把還沒寫的函式先命名好，好像這樣就更完整。名字比程式先死，計畫跟著過期。整份計畫也完全沒引用 PRD 裡的 user story。user story 是一句「作為某種角色，我想要某功能，以便某種目的」講完的需求陳述，沒引用它，等於把 why 弄丟了，agent 只記得要蓋什麼，不記得為什麼要蓋。這三個特徵先記住，水平切層、過度指定實作、丟失 why，待會逐條拿來對比。

新方法就是 [[learn/ai-coding-for-real-engineer/elements/prd-to-plan-skill|PRD-to-plan（PRD-to-Plan Skill）]]。skill 是一段固定的指令檔，把一套工作流寫成步驟，agent 照著走，等於把「怎麼做事」存成可以重複呼叫的命令。實驗設置有四步。第一步，開一個全新的 session，零 context，不留任何舊對話。第二步，把上一份天真計畫的檔案刪掉，讓 agent 無從讀取，也無從動手改它。第三步，把 PRD 用 `@` 的 tab 自動補全帶進 prompt，輸入 `@` 之後按 tab，從彈出的清單裡選取 PRD 檔案，整份內容就進到對話裡。第四步，呼叫「PRD to plan」，觀察它產出的計畫，跟天真計畫比，好在哪裡，還有哪裡能更好。這四步合起來，就是 [[learn/ai-coding-for-real-engineer/elements/fair-comparison-setup|公平比較的實驗設置 (Fair Comparison Setup)]]。

這四步每一步背後都有一個機制，先講零 context。agent 的輸出是視窗裡所有文字的延續，它從不憑空產生，只往下接。舊對話裡夾著你之前的試探、失敗和修改決定，這些文字會把新輸出往同一條路上帶。你在舊視窗裡多待五分鐘，測到的其實是那五分鐘對話的延續，你要測的 skill 只分到一小塊因果。開新 session，等於把歷史整段切掉，讓這次輸出只由你此刻帶進去的東西決定。這也解釋了為什麼要開全新的視窗，而不是把舊視窗清一清。舊內容清不乾淨，多留一行，就多一個干擾結論的變數。

刪舊檔這一步，是整套設置裡最容易偷懶跳過、也最要緊的一步。天真計畫的檔案躺在工作區裡，agent 看得見，就一定會處理它。要嘛讀一遍參考它的切法，要嘛直接動手改一版。檔案在，它就變成 agent 的輸入之一，最後你拿到的計畫，可能只是把舊計畫修過一輪的產物。你測到的是會複製貼上的 agent，你要測的 skill 根本沒上場。把檔案刪掉，等於把那份寫好的答案從桌上拿走，agent 剩下能靠的只有 PRD 和程式碼庫，輸出才歸得到 skill 頭上。PRD-to-plan 寫出來的檔名可能跟天真計畫同名，刪檔這一步尤其容易漏。檔名一樣，agent 更有可能直接打開舊檔續寫，刪了才斷得乾淨。

用 `@...tab` 帶進 PRD，則是把輸入關到只剩一樣。這個動作把整份 PRD 的內容真正放進 context。光提檔名不夠，檔名只是叫 agent 自己去開檔，開檔讀到什麼、讀多少，都不在你掌控裡。用 `@` 選檔，等於親手把檔案的內容塞進對話，PRD 成為這次實驗唯一帶進去的輸入，後續觀察到的差異，才能全部歸因到 skill 本身。多帶任何一樣東西，差異的來路就多一個可能，結論的可靠度就掉一分。輸入越少，結論越乾淨。

刪舊檔也不是要把工作區清空。agent 照樣會探索程式碼庫，看現有的 service 和 route 長什麼樣，這部分是 skill 設計的一環，該看就看。要拿掉的，只有「上一份計畫」這一個特定產物。程式碼庫是題目本身，考生該讀題。舊計畫是別人寫好的解答，把切法和函式名直接洩漏出去。留著解答考出來的成績，誰都不會信。

實際跑一遍是這樣的。開一個全新的 Claude Code 視窗，先下指令刪掉上一份 plan 檔，接著輸入 `@`，按 tab，從清單裡選到 PRD，再打「PRD to plan」，按 Enter。agent 先花一兩分鐘探索程式碼庫，看看現有的 service、route 長什麼樣。然後它貼出一份草案，第一個 phase 打算把 analytics service、instructor route、summary cards 串成一條垂直切片，用三個數字先跑通整條路。你看完草案，把 phase 2、3 合併，回一句這樣切可以。它才動手把計畫寫成本機 markdown 檔。前後五分鐘，你沒寫任何一行計畫，只做了兩件事，刪舊檔和給回饋。instructor route 是講師專用的檢視頁面，summary cards 是幾張摘要卡。

跑到這裡，比較的雙方都齊了，左邊天真計畫，右邊新 skill 的產出。對比要看的維度有四條，照著比，結論才不會停在「感覺新的比較好」這層。

| 比較維度 | 天真計畫 | PRD-to-plan 的產出 |
| --- | --- | --- |
| 切法 | 水平切層，每 phase 做一整層 | 垂直切片，每 phase 穿過所有層 |
| user story 引用 | 沒有引用，why 丟了 | 每個 phase 標明服務哪條 user story |
| 實作細節 | 直接寫函式名，執行前就過期 | 細節留給實作，只記耐久決策 |
| 寫檔前確認 | 直接吐檔 | 先 explore、propose，徵求回饋後才 write |

水平切層和垂直切片這組對比，決定 feedback 什麼時候來。feedback 指跑一跑、看看東西通不通的回饋。天真計畫的第一個 phase 只做完 analytics service 一整層，沒有 UI、沒有 route，這層通不通要等到最後一個 phase 才知道，中間幾個 phase 全在賭。垂直切片每個 phase 從資料層一路切到介面層，跑完一個 phase，整條路通不通立刻見分曉。水平切層之所以誘人，因為它順著直覺走，先打地基再蓋樓，每一層看起來都在推進，問題是它把驗證拖到最後。agent 一次只看得到一片，看不到整條路，等最後一個 phase 才發現地基跟 UI 對不上，前面幾個 phase 的時間已經花了。垂直切片把驗證提前，每一 phase 跑完都是一次確定的回饋。PRD-to-plan 提出的第一個 phase 正是這樣的一條切片，對比天真計畫的第一個 phase 只做了一層，差距一眼就出來。

PRD-to-plan 跑起來有四段，觀察時可以對照著看。先 explore，探索程式碼庫，這一步用比較便宜的模型執行，探索花的資源不算浪費。接著 propose，提出一份 phase 切分草案，通常是垂直切片。然後 ask，把草案端給你，寫檔之前先徵求回饋。最後 write，你確認了才寫成本機檔案。這四段裡，ask 那一段要看得格外仔細。它把計畫品質從運氣變成流程，人可以在寫檔前校正切法。真實的比較同時看產出和過程，它有沒有先探索、有沒有先問你，這些都算數。

打開新計畫，內容結構也值得比。每個 phase 都標明要蓋什麼、服務哪條 user story，實作細節幾乎不洩漏，那些會在執行前過期的函式名消失了，取而代之的是耐久決策。耐久決策指短期內不會變的架構決定。route 放哪裡、schema 怎麼定、要不要新增 analytics service、auth helper 要不要抽、依賴加哪些，這些值得在計畫裡寫死，因為執行時人不會想再改它。寫計畫的準則是先找出這些耐久架構決策，再往下切 slice。一件事現在就確定，後面就不用再計畫，計畫的價值在處理執行時無法預知的那些。新計畫的每個 phase 都回溯到 PRD 的 user story，這正是天真計畫丟掉的 why。

觀察完還要補最後一問，它能怎麼更好。比較的價值一半在判斷輸贏，一半在把輸的那部分撈回來。skill 沒引用哪條 user story、phase 切得還不夠垂直、耐久決策漏了哪個，都是下一次改進的入口，缺什麼就補什麼。skill 的本質是固定指令，哪裡不順就改指令，改完再跑同一場實驗，看有沒有改善。測出差距、修改 skill、再測一次，評估循環在這裡閉合。結論的標準只有一個，換一套乾淨環境再跑一次，結果還是一樣。能重現，你手上是一條真實的改進。不能重現，只是一次運氣。

比較的結論要寫得具體，別停在「新的比較好」。具體的意思是，能說出它贏在哪一條維度，又輸在哪一條維度。天真計畫的 user story 引用是零，新計畫每條都有，這是贏。新計畫的 phase 1 還是偏大，這是還能改的地方。寫得出這種句子，比較才變成下一次的輸入。寫不出來，結論只是感覺，感覺不能重現，也不能拿來改 skill。

常見的破壞方式有三種，都是讓結論退化成運氣。第一種，忘了刪舊檔，agent 讀到上一份計畫，直接把它的切法搬過來，表面是新 skill 贏，骨子裡是舊計畫贏。第二種，在舊 session 裡測，之前討論過這個專案，context 裡全是舊資訊，輸出早就被帶偏。第三種，除了 PRD 還順手把筆記也 `@` 進去，多一個輸入，就多一條無法控制的影響路徑。這三種坑，每一種都在說同一件事，比較的結論只對乾淨的輸入成立。

到這裡，新 skill 比舊方法好這個結論才站得住，它建立在受控的比較上。受控的比較是一套可以重複的姿勢，往後評估任何新 skill、新 prompt、新工具、新模型，都用同一套，把條件寫成檢查清單。

| 步驟 | 做什麼 | 防止什麼 |
| --- | --- | --- |
| 開新 session | 零 context，不留舊對話 | 舊歷史把輸出帶離 skill 本體 |
| 刪舊檔 | 把上一份計畫檔刪掉 | agent 讀它、抄它、改它，污染結果 |
| 只帶 PRD | 用 `@...tab` 放進 PRD 內容 | 輸入多帶，差異無法歸因 |
| 跑一次 | 呼叫「PRD to plan」 | 缺基準，無從比較 |
| 對比 | 逐維度跟天真計畫比 | 停留在感覺，結論無法重現 |

判斷一個 skill 有沒有用，最忌諱先射箭再畫靶。把舊計畫留著跑，agent 抄了舊計畫，你卻說新 skill 有效，那句話沒有地基。開新 session、刪舊檔、只帶 PRD、跑一次、逐維度對比，步驟做齊，這次真的贏了才變成可以再跑一遍的結論。
