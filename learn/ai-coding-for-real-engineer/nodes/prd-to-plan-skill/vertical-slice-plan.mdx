# 產出的計畫長什麼樣：tracer bullet、user story 引用、更少的實作洩漏

## Learning goal

能對照天真計畫，說出 skill 產出的三階段計畫好在哪，phase 1 為什麼是一條打通全棧的 tracer bullet，以及每個 phase 引用 PRD user story 為什麼能大幅減少實作洩漏。

## Lesson

功能大到塞不進一個 context window 的時候，工作就得拆開做。拆開的意思是先把一件事切成一批 phase，每個 phase 在自己乾淨的 context window 裡執行，做完一個再開下一個。讓每個 phase 的執行者都知道要往哪走，需要兩份文件。一份寫目的地，是 PRD，記載這個功能要服務誰、滿足哪些需求。一份寫路線，是計畫，把目的地切成一段一段的旅程。這裡要看的，就是這份計畫究竟長什麼樣。

用一個具體例子講，instructor analytics dashboard，一個讓講師看營收、enrollments、平均評分的功能。PRD 已經寫好，user story 一條一條編了號。同一份 PRD、同一個 codebase，用兩種不同方式去產出計畫，會得到品質差很多的兩份文件。一份是開新 session，把 PRD 用 @ 拉進 context，只對 agent 說「把它變成多階段計畫，存成 markdown 檔」，其他什麼都不加。另一份走 PRD-to-plan 這個 skill，讓它先探索、先提議、再寫檔。兩份計畫放一起對照，一份裡哪些欄位重要、哪些欄位寫了反而害事，立刻看得出來。

先看第一份，天真計畫。它長這樣，四個階段，每個階段負責一整個層。

| 階段 | 內容 | 觸及的層 |
| --- | --- | --- |
| 1 | analytics service | 資料層一整層 |
| 2 | 共用的 dashboard component 加 recharts | UI 元件一整層 |
| 3 | 把 UI 接上來的 route | route 一層 |
| 4 | admin route 和連結 | route 一層 |

它有幾個毛病，一個一個看。

第一個毛病是水平分層。一個系統有資料層、service 層、route 層、UI 層，要全部層都接上，才產生得出一個使用者真的能用的東西。天真計畫把每一層各自當成一個階段，於是階段一做完整條資料層，只有一堆算數字的函式，沒有畫面、沒有路徑，什麼都驗證不了。階段二做完整套 UI 元件，沒接到任何資料，畫面是空的。整條路第一次真的動起來，要等到很晚的階段。feedback 來得越晚，問題越難定位。假設最後才發現資料算錯，你根本不知道錯在 service、錯在 route 還是錯在 UI 顯示。要排查的範圍是整條路，等於把整合的賭注全押在最後一刻。

第二個毛病是過度指定實作。計畫裡直接寫上函式名稱、寫明要改哪支檔案。問題是你現在根本不知道實作跑完之後這些函式叫什麼。人類看完階段一，動了手，調整了 service 的寫法，原本計畫裡寫的函式名稱就消失了。階段二的執行者照著計畫去引用，撞上的是一個不存在的東西。實作進行中細節必然變動，寫進計畫的每一行細節都會過期。這份計畫變成一份腐壞的地圖。天真計畫裡只有一件事值得留下，每個 phase 附了 acceptance criteria，這是後來那份好計畫也保留的骨架。

第三個毛病也最隱蔽，是它從頭到尾沒提過 PRD 的 user story。user story 是 [[learn/ai-coding-for-real-engineer/elements/prd-structure|PRD 結構（PRD Structure）]] 裡編號的一條條需求，格式是「as an instructor I want X so that Y」，記載某個角色想要什麼、為了什麼。編號讓每條需求有穩定的位址。天真計畫一個編號都沒提。執行階段三的 agent 只知道「把這支檔案改掉」，不知道這支檔案在服務誰、滿足哪一條需求。事後 review 也答不出這一階段做完了沒，因為沒有半條需求可以拿來對答案。不引用 user story，就是丟掉做這件事的 why。

把這三項記住，再看 skill 產出的計畫。它每一項都對著修，而且修的方式很具體。

skill 產出計畫的流程先就不同。它先探索 codebase，用較便宜的模型，把貴的 token 省下來。探索完提出一份 phase 拆分的草案，先問人類的意見，等人確認了才把計畫寫成檔案。這是個「先提議、再確認」的 loop。天真計畫探索完直接寫檔，中間沒有確認這一步。一個把人的判斷擋在門外，一個把人留在 loop 裡。多問這一步很關鍵。計畫是要陪著人走好幾個 session 的承諾，人接下來每一句「do phase N」都照著它執行。一份沒經過確認就落地的計畫，等於替人做出了之後每個 phase 的決定。skill 先給草案，人只要掃一眼，看出問題當場改。五個 phase 合成三個，就是這一掃發生的。

寫檔之前，skill 先要求識別耐久決策。[[learn/ai-coding-for-real-engineer/elements/durable-decisions|耐久決策（Durable Decisions）]] 是那些高階、短期內不會變動的架構決定。原則一句話，別規劃你無法規劃的事。細節在實作時必然變動，能寫進計畫的，只有那些「現在是這樣、到 phase 3 還是這樣」的決定。在 analytics dashboard 上，捕捉到的耐久決策有五項。route 的位置、schema 的結構、要不要新增 analytics service、auth helper 怎麼共用、依賴哪幾套函式庫。拿 schema 和函式名對比，界線就清楚了。schema 是資料的形狀，現在定下來，之後每個 phase 照著它建，短期內不會改。函式名是實作內部的名字，實作一改就沒了。耐久決策把後者擋在計畫外，計畫才能跨 phase 存活。

切 phase 的時候，用的是垂直切片，也就是 [[learn/ai-coding-for-real-engineer/elements/tracer-bullet|Tracer Bullets（垂直切片）]]。這個概念出自 The Pragmatic Programmer。二戰防空砲兵裝上曳光彈，打一發，砲手看得到彈道往哪飛，立刻修正。寫程式是同一件事。與其先把地基整層蓋完再蓋一整面牆，不如先蓋一棟一樓高的小房子，每一層都有一間，走進去確定房子立得住，再往上加樓。垂直切片讓每個 phase 都穿過所有層，用最簡單的資料打通全棧，先確認整條路走得通，再回頭補厚度。

full stack，全棧，指的是從資料庫一路到使用者看到畫面的所有層，database、service、route、UI。打通全棧的意思是讓一份資料從最底層一路流到最上層，中間不繞路、不靠假資料騙自己。驗證一個 phase 是不是真的垂直切片，就問一句，這條路從頭到尾通到哪一層了。

把它用在 analytics dashboard，skill 提出的是五個 phase 的草案，人類做了兩次合併。第二次和第三次都是 UI 層的事，合併成一個。第四次和第五次是 admin 存取和 empty states，落在同一塊 code area，合併成一個。五個變三個。

| skill 草案 | 合併後 | 人類合併的理由 |
| --- | --- | --- |
| 1 analytics service + instructor route + summary cards | phase 1 | 已是完整切片，不動 |
| 2 UI 元件 | phase 2 | 都是 UI 層的事 |
| 3 UI 元件 | phase 2 | 同上 |
| 4 admin 存取 | phase 3 | 同一塊 code area |
| 5 empty states | phase 3 | 同上 |

合併的判斷標準是這樣。一個 phase 該不該拆，問它在同一個 context window 裡能不能一口氣做完。兩個 UI 元件要動同一批檔案、對著同一個畫面驗證，拆成兩個 phase 只是多開一次 session，沒有新增任何驗證點。admin 存取和 empty states 更明顯，empty states 就長在 admin 看得到的那個頁面上，同一支 route 同一塊 code，拆開反而讓第二個 phase 得重新認識第一個 phase 寫下的東西。phase 的邊界順著一件事做到底切，順著同一層或同一種技術切，只會把該一起驗證的拆散。

phase 1 是一條貨真價實的 tracer bullet。它把 analytics service、instructor route、summary cards 一次全部接起來，只用三個彙總數字當資料。三個彙總數字是 KPI strip 的三項，總營收、總 enrollments、平均評分。這條切片要證明的是整條路通，做不做得出成品是另一回事。phase 1 跑完，你已經在瀏覽器裡看到三個數字從資料庫一路流到畫面。整件事能動。unknown unknowns 也一併被沖出來。

unknown unknowns，未知的未知，是你連想都想不到自己不知道的事。資料層跟 UI 中間有沒有缺一個欄位、route 參數接得對不對、授權檢查卡在哪一層，這些東西在紙上規劃時完全看不見，只有整條路第一次真的串起來的那一刻才會現身。把它們排在第一個 phase，用最便宜的代價沖出來，後面的 phase 才不會埋在整合問題裡。便宜有兩層意思。一是資料最少，三個數字足以證明路通，不必等所有欄位做完。二是時間最早，第一個 phase 就撞上所有整合問題，撞完就沒了，不會累積到最後一次爆炸。

跑 phase 1 的那段時間，會把一堆紙上沒答案的問題逼到眼前。agent 要先看現有 schema，搞清楚 enrollments 存成什麼形狀、要不要排除還沒發布的課程。三個數字裡每一個都指向一張表、一條查詢，數字挑哪個版本，等於把資料的形狀定死。總營收和總 enrollments 還對不上，差在 team purchase 這種一次買一批座位、拆成好幾個人名下的情況，算一筆還是算多人，PRD 裡早就討論過，落到實作才第一次逼著人拍板。這些問題全在第一個 phase 冒出來，就是 unknown unknowns 現身的方式。數字少，問題反而誠實，整條路通不通，一個數字流到畫面上就見真章。

計畫的每個 phase，現在都寫明兩件事。要建什麼，以及引用哪幾條 PRD 的 user story。[[learn/ai-coding-for-real-engineer/elements/plan-user-story-traceability|計畫的 user story 回溯（Plan Traceability）]] 講的就是這條引用線。phase 1 對應的是「講師要看總營收」那一條，phase 3 的 admin route 對應的是「管理員要能代看任何講師的儀表板」那一條。user story 的編號就是計畫引用它們的鉤子。精準寫「本 phase 對應 story 幾」，agent 和 reviewer 就對到同一個位址，不用重抄整句需求。這條線，就是計畫和 PRD 講同一件事的地方。

引用 story 這件事，直接把實作洩漏降下來。實作洩漏，是計畫裡滲進實作細節的現象，函式名、檔案路徑、內部演算法，都算。機制是這樣的。每一段工作都被釘回一條具體需求，agent 在做的事變成滿足 story 14。它要服務的人、要達到的效果都寫在那一條裡。做什麼跟為什麼做綁在一起，它就沒有空間自己加戲，不會自己補功能、改名函式，或者去做計畫外的事。review 也簡單了，直接拿引用的那幾條 story 對答案，一條一條核，做完了沒當場見分曉。反觀天真計畫，沒有引用、沒有 why，review 只能憑感覺。

兩份計畫放上天平，差異集中在三件事。切的單位不同，一份切層、一份切切片。寫的內容不同，一份劇透細節、一份只畫軌道。對需求的鉤子不同，一份不引用 story、一份逐 phase 釘回 story。切的單位決定 feedback 來得多快，寫的內容決定計畫能活多久，對需求的鉤子決定 agent 知不知道自己在做什麼。

把三件事的對照排成一張表。

| 面向 | 天真計畫 | skill 產出的計畫 |
| --- | --- | --- |
| 切法 | 水平分層，一階段一整層 | 垂直切片，每階段穿過所有層 |
| 計畫裡寫什麼 | 指名函式，實作一變就過期 | 只留耐久決策，細節留到實作時 |
| user story 引用 | 從不引用，丟掉 why | 每 phase 寫明引用哪幾條 story |
| 產生流程 | 探索完直接寫檔 | 先探索、提議、問過再寫 |
| 第一次端到端 feedback | 很晚的階段 | phase 1 就看得到 |
| 實作洩漏 | 高 | 低 |

這份計畫接下來怎麼被吃掉的，也值得說清楚。每個 phase 在一台新的 session 執行，把 PRD 和整份計畫一起傳進去，只下一句「do phase N」。因為計畫裡只存耐久決策、每條 slice 又釘死了要滿足哪些 story，新 session 不需要前面任何 context 就能照著做。做完一個 phase 就 commit，下一個 phase 接著同一份計畫繼續。計畫跨 session 存活，靠的就是前面那些取捨。劇透細節的計畫活不過第一個人類動手，沒引用 story 的計畫活不過第一次 review。commit message 順手記下這一 phase 滿足了哪幾條 story，下一個 session 讀 commit 歷史，也知道前面走到哪。

一份好計畫的樣貌到這裡就完整了。它是活的軌道，跟著耐久決策走，每個 phase 都是能獨立驗證的切片，每一站都寫得出自己在送誰到哪。它不劇透程式碼，只畫出不會變的架構軌道，讓每個 phase 在同一條軌道上執行。執行到最後，PRD 裡被引用的那些 user story 一條一條被吃掉，destination 就到了。拿到任何一份計畫，用這三件事過一遍。切的是層還是切片，寫的是耐久決策還是劇透細節，每個 phase 有沒有釘回 story。三件事都過，這份計畫才陪得到最後一站。
