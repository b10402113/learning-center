# PRD-to-plan 怎麼運作（探索、提案、確認、寫檔）

## Learning goal

能說出 PRD-to-plan 的四段工作流（explore → propose → ask → write），並解釋為什麼探索階段用便宜的模型、為什麼寫檔之前一定要先徵求人的意見。

## Lesson

PRD 是目的地，計畫是行程。目的地記錄人想要什麼，行程把目的地拆成一格一格的階段，一格做一步。把目的地變成行程的工具，是 [[learn/ai-coding-for-real-engineer/elements/prd-to-plan-skill|PRD-to-plan（PRD-to-Plan Skill）]] 這個 skill。

先講幾個詞，後面才不會卡住。skill 是一段預先寫好的指令，agent 碰到對應的場景就照著執行。session 是一次對話，你在這個視窗裡跟 agent 講過的話、它讀過的檔案、它做過的事，全部叫做 context。agent 每次對話都從零開始，session 一關，context 就一起消失。prompt 是你丟給 agent 的那段開頭指令，token 是模型計數文字的最小單位。

PRD-to-plan 跑在 [[learn/ai-coding-for-real-engineer/elements/fair-comparison-setup|公平比較的實驗設置（Fair Comparison Setup）]] 搭好的環境裡。這個環境乾淨得很。session 是全新的，context 是零，先前那份天真計畫已經刪掉。PRD 用 @ 帶進 prompt，指令就一句 PRD to plan。

跑起來之後，整套動作分成四段，順序固定，一段都不能跳。探索（explore）把資訊收進來，提案（propose）把切法擬出來，徵詢（ask）把草案端給人看，寫檔（write）才把計畫落成本機檔案。下面一段一段講。

### 探索，先讀懂這個 repo

接過 PRD，skill 第一件事是去讀這個 codebase（程式碼庫）。它要知道 repo 現在長什麼樣，哪些 route 已經存在，analytics 相關的模組有沒有，權限檢查寫在哪裡，資料庫的 schema 怎麼排。route 是 API 的網址路徑，schema 是資料表的排列方式。這些它一律不知道。

模型每一次對話都從零開始，repo 對它來說是個陌生地方。別的 session 讀過什麼，先前那份計畫寫過什麼，全留在上一個 context 裡，這一刻幫不上忙。它唯一能依靠的，是現在這一輪親手讀到的東西。

探索讀回來的資訊，直接決定提案能不能引用真實存在的東西。後面的實作 phase 各自開新 context，它們照著計畫找檔案，計畫裡寫的名字必須在 repo 裡找得到。phase 是一段一段的實作階段，下面會一直用到。

探索的深度決定計畫的下限。只讀幾支檔案就提案，計畫裡引用的還是想像中的結構，後面照著找，檔案根本不存在。讀得夠深，哪條 route 已經有、哪些模組在哪裡，提案才有東西可站。skill 把探索排在最前面，就是讓這個下限先墊高。

探索在整個流程裡佔掉的 token 最多，難度卻最低。讀檔案、抓重點、回報現狀，動作量大，要求不高。skill 讓這一步跑在較便宜的模型上，例如 Sonnet 4.6。背後的道理是資源分配。每個 token 都要付錢，頂級模型在讀完一整批檔案、總結現狀這類工作上，比中階模型強不了多少，讓它去做反而是浪費。吃判斷的地方在後面，怎麼切，哪些決定值得寫進計畫。便宜的模型把探索量吞掉，昂貴的模型留著做決定，同一份計畫的成本就壓下來了。

探索的 token 花得不冤。它讀的是整批現有檔案，這份成本買到的是提案不會引用空名字。相比起來，提案階段犯錯、寫檔階段犯錯，每一處的代價都更貴。把錢花在探索，是整個流程裡最划算的一筆。

探索還附帶保住主視窗的空間。在 Claude Code 裡，探索通常交給 sub-agent（子代理）跑。sub-agent 有自己的 context window，把讀檔案燒掉的 token 消化在自己那裡，最後只回傳一份摘要。context window 是 agent 一次能裝進去的內容上限。主 context 沒有被整批檔案內容灌滿，後面提案、徵詢要用的思考空間就留在原位。

這點值得記住。context window 有上限，塞滿之後模型開始胡亂作答。把大量讀取隔在外層，判斷留在主視窗，是整個流程反覆使用的手法。

這個分工還有一個側面。探索的回報是一份摘要，這份摘要會進到提案階段，成為切 phase 的材料。便宜的模型做的是粗活，把現狀撈回來。把摘要變成切法的判斷，留給主視窗裡的主力模型。粗活和判斷分開，兩邊都省。

### 提案，把行程切成 phase

探索完，skill 提出 phase 切分草案。草案的關鍵在每個 phase 怎麼切。它提的第一個 phase 是一條完整的垂直切片，把 analytics service（資料服務）、instructor route（講師的網址路徑）、summary cards（摘要卡片）全部串起來，用最簡單的資料，三個匯總數字，讓整條路先走通。

這個切法有個名字，tracer bullet（追蹤彈），出自《The Pragmatic Programmer》這本書。先打一發穿過所有層的子彈，人看得見彈道，再慢慢校正。

垂直切片和水平切層是兩種相反的做法。水平切層把每一層當一個 phase。第一段把 analytics service 全部寫完，第二段做共享元件，第三段接 route，最後一段才把畫面接上。麻煩在回饋來得太晚。前三段做的東西沒有一樣能在瀏覽器裡看到結果，全部要等最後一段，才知道整條鏈路通不通。

垂直切片反過來。每個 phase 都橫跨每一層，service 寫一點，route 接一段，畫面長一點，phase 結束就有一個能開起來看的小功能。回饋早到，那些你連自己不知道的問題也提早浮出來。功能再複雜，第一段用最少的資料把鏈路打通，後面每一段都只是在同一條軌道上加厚。

三個匯總數字這個選擇有講究。它少到不足以代表完整功能，卻多到能把整條鏈路都走一遍。service 要真的查資料，route 要把資料送出去，卡片要把數字畫出來。任何一環斷掉，第一個 phase 就會露出來。用最少的資料驗證整條路，是垂直切片的第一個好處。

phase 的順序講的是依賴。第一段打通全疊層之後，第二段沿著同一條路加東西，第三段繼續疊。每結束一段，repo 都處在可以跑的狀態，隨時能停下來給人看。這個性質讓計畫可以中途調整。哪一段做完發現方向偏了，人可以在下一段開始前修正，前面已經驗證過的路不受影響。

切 phase 的界線，同時是 context window 的界線。後面的實作，每一個 phase 開一個全新視窗來跑，一個 phase 的大小要裝得進一個視窗，內容要能獨立跑完。界線切錯了，該放在一起的工作被拆到兩個視窗，第二個視窗開工時要重新讀、重新懂，前面的語境留不過來。

phase 的切分同時決定每一個視窗要做多少事、要碰哪些檔案。哪幾段工作屬於同一片程式碼，這是切 phase 時最該問的問題。phase 太大，一個視窗塞不下。phase 太小，光是開視窗、重新探索就划不來。界線落在讓每個視窗既裝得下、又不用重複讀太多東西的地方。

### 徵詢，寫檔前先給人看

Skill 擬好草案，不直接寫檔。它把草案端到人面前，問有沒有意見。這一步只花一次對話，卻擋掉大量事後重做。草案是模型對怎麼切的猜測。模型知道 repo 的現狀，知道 PRD 寫了什麼，但不知道人的判斷。哪些 phase 該併在一起，哪些決定以後會變，哪幾段工作動的是同一片程式碼，這些訊息只在人腦裡。

實際跑一次就看得很清楚。skill 原本提了五個 phase，人把它併成三個。第二和第三個 phase 都是 UI 的事，併成一個。第四和第五個 phase，admin 存取和空狀態，動的是同一片程式碼區域，也併成一個。

併法背後有道理。後面的實作，每個 phase 各自開一個新 context 來跑。改動的檔案範圍越連續，phase 之間越不容易互相踩。兩個 phase 碰同一片程式碼，前一個跑完，後一個開工時，面對的是前一個留下的狀態，容易撞出問題。把同區域的活放進同一個 phase，每個 phase 的觸碰面就乾淨了。

要不要併、怎麼併，是人的判斷。模型看得出檔案結構，看不出哪些改動是同一件事。徵詢這一步，把人的判斷補了進來。

人校的是方向，不是文字。草案端上來，該看的是幾件事。phase 的順序合不合理，每結束一段 repo 是不是處在可以跑的狀態，兩個 phase 之間有沒有重疊的工作，哪一段風險最大該最早做。這些判斷沒有一個能靠讀 PRD 得出來。repo 的現狀、程式碼的親疏、風險的分布，都在人的經驗裡。

草案的好處在它還是一份提議。人可以在上面調整，改的代價接近零。等它變成檔案、被後面的 session 照著執行，再動就貴了。

徵詢的形式可以是直接問，也可以是把自己的切法講給人聽，等人提出修改。不管哪種，重點都在寫檔前給人一個插手的機會，別讓計畫默默落地。人點頭之後，這份計畫就從模型的提議變成雙方都認的約定，後面的實作不再需要人盯，因為切法在寫檔前已經校過一遍。草案本身只是過程，這個轉變才是 ask 這一步真正的產出。

寫檔前徵詢還有一個理由，回饋成本差得很遠。計畫還沒寫成檔案時，改一句話就是一輪對話的事。計畫已經寫好、被幾個執行 session 各自讀過之後，再想改切法，要重新規劃、重新執行、甚至重做已經完成的 phase，代價是前者的好幾倍。人的一句話在最便宜的時候說出去，省的是後面一整串重做。

### 寫檔，讓計畫活過 context

人點頭，skill 才把計畫寫成本機檔案。寫成檔案這件事，值得想一下為什麼。模型無狀態，計畫如果只活在對話裡，下一個 session 開起來，這段對話已經不在了。實作階段的每個 phase 都是全新 context，它讀得到的只有檔案。計畫必須活在 context 外面，以檔案的形式存在，才接得住後面那一批 session。PRD 是目的地，計畫是行程，兩者都要是檔案，流程才串得起來。

計畫檔的位置也要固定下來。後面的實作 phase 用 @ 把它帶進視窗，檔名和路徑要是已知的，每個 session 都找得到。計畫和 PRD 擺在一起，實作時兩份一起讀。寫好的計畫值得立刻 commit 進 git。commit 的意思是給目前的檔案狀態留一個有記錄的版本。留進 git 歷史，任何一個 session 隨時可以找回。

計畫的壽命比任何一次對話都長。一個 phase 要跑好幾個 session，中間可能隔著好幾天。檔案一直在，進度才接得上。

寫出來的計畫長什麼樣，這裡只說個大概，細節是下一步的事。每個 phase 描述要做什麼，標明它對應 PRD 的哪幾條 user story（使用者故事）。實作細節的洩漏比天真計畫少得多。計畫引用的是真實存在的東西，後續 phase 不會撞上還沒出現的函式。

### 耐久決策，先定軌道再切 slice

Skill 的指令裡有一條硬要求，先找出耐久決策，再開始切 slice。耐久決策是現在定得下來、短期內不會變動的高階架構決定。例如 route 開在哪、schema 怎麼排、要不要新增一個 analytics service、權限檢查共用在哪裡、依賴哪幾套函式庫。

詳細拆解在下一步，這裡先抓住背後的道理。你不該規劃你規劃不了的事。實作細節必然在過程中變動，人改掉前一個 phase 的某個實作，後面的 phase 就引用到不存在的東西。耐久決策相反，現在是這樣，到 phase 3 還是這樣。把這些軌道先定好，每個 phase 在軌道內填實作，計畫才不會在執行前就腐壞。完整的耐久決策在 [[learn/ai-coding-for-real-engineer/elements/durable-decisions|耐久決策（Durable Decisions）]] 裡展開。

把四段串起來看，每段都堵著天真計畫的一個洞，前一段的產出又是後一段的輸入。沒有探索，計畫引用想像中的檔案。沒有徵詢，錯的切法直接進檔案。寫檔這一步，決定計畫能不能活過 context 清空。計畫一旦寫好，剩下的活就變成沿著軌道填，人的注意力從每一段實作上移開，改守在 phase 與 phase 之間。

這個 skill 有用的地方，在它逼著流程在探索、提案、徵詢、寫檔四處各停一次。計畫寫完，下一步輪到看它長什麼樣，耐久決策怎麼落進 phase 裡。
