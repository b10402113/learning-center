# 只寫耐久決策（別規劃你無法規劃的事）

## Learning goal

能說出「先找出耐久架構決策、再切 slice」的原則，舉出 analytics dashboard 計畫捕捉到的耐久決策，並判斷一份計畫裡什麼該寫、什麼該留給實作。

## Lesson

一份計畫最常見的死法是寫得太細。把 PRD（產品需求文件）丟給 agent，只交代一句「拆成多個 phase，存成 markdown 檔」，它往往吐出一份細到函式層級的計畫。phase 在這裡指階段，一份計畫分成幾段來寫。它寫著，phase 1 建立 computeRevenue 這個函式，phase 2 從 analyticsService 匯入某個方法。這種寫法叫過度指定。過度指定，就是計畫把實作內部的細節也一併寫死。這些字在寫下的那一刻就開始過期。原因很簡單。計畫寫在所有程式碼之前，寫的是還不存在的未來。替一個還沒誕生的函式命名，等於拿一個不存在的東西當依據。phase 1 寫完，人類動手改過幾個名字之後，phase 2 照著計畫去找那個函式，找不到。

PRD-to-plan 這套 [[learn/ai-coding-for-real-engineer/elements/prd-to-plan-skill|PRD-to-plan（PRD-to-Plan Skill）]] 就是繞著這個問題設計的。它的指令裡有一條，在切 slice（切片）之前先找出耐久架構決策。耐久架構決策，指那些關乎整體結構、短期內不會改變的決定。[[learn/ai-coding-for-real-engineer/elements/durable-decisions|耐久決策（Durable Decisions）]] 一句話講完，別規劃你無法規劃的事。整份計畫能不能活過實作，繫在這一條上。計畫裡每一行都是一句對未來的聲明。聲明分兩種。第一種說的是，這件事無論程式碼怎麼寫都會成立。第二種說的是，這件事要等某段程式被寫成某個樣子才成立。第二種依賴的事實還沒被造出來，人類在實作裡改動一下，事實就變了，聲明跟著變假。耐久決策要的是第一種。

耐久決策要符合三個條件。第一，它現在就確定，不需要等任何程式碼。第二，它描述的是樑柱，後面的每一層都沿著樑柱長。第三，它不會因為某一層的實作長得不一樣就跟著變。這三個條件缺一不可，少一個，這行字就有機會在實作中途變假。用蓋房子打比方。耐久決策是樑柱的位置，定下來之後，上面每一層都沿著樑柱長。掛哪一幅畫、牆面刷什麼顏色，屬於實作細節，等那一層真的蓋好再決定。樑柱現在就能定，畫和顏色必須等樓層成形才能定，硬要提前寫進計畫，就是替還沒出現的選擇先下結論。

analytics dashboard（分析儀表板）的計畫捕捉到的耐久決策，白話一項一項講。

| 耐久決策 | 白話解釋 | 為什麼現在就能定、之後也不變 |
| --- | --- | --- |
| route 位置 | 頁面掛在伺服器的哪個網址路徑底下 | 網址先訂，後面的程式、測試、連結全都往這個網址走 |
| schema | 資料的形狀，一筆資料有哪些欄位、每個欄位放什麼型別的資料 | 欄位在寫任何一層之前就要定，層與層之間靠這個形狀對接 |
| 新增 analytics service | repo（程式碼庫）多一個負責算彙總數字的模組，其他程式向它要資料 | 數字由誰算、模組要不要存在，是結構決定，寫完哪一段都不會改 |
| auth helper | 權限檢查的共用小工具，確認登入的人有沒有資格看這個頁面 | 權限規則先定，所有要檢查的地方共用同一份，誰都不用重寫 |
| dependencies | 專案引用的外部函式庫，別人寫好、直接拿來用的程式包 | 要畫圖表就引一套繪圖函式庫，動手之前就該定案 |

這五項的共通點在這裡。它們在你寫下計畫的那一天就成立，到了 phase 3 執行的時候仍然成立。它們沒有一項是「等某段程式碼出現才存在」的東西。route 在寫任何一行程式之前就可以決定，它只規定請求從哪個網址進來、交給誰處理，跟實作細節無關。schema 在寫任何一層之前就可以決定，層與層要對接，總得先有一份雙方都同意的資料形狀。analytics service 要不要存在，先於它內部怎麼寫這個問題。auth helper 先定的是規則，共用之後每個地方都照同一套檢查。dependencies 先定的是引哪幾套函式庫，不牽涉函式庫內部長什麼樣。這些決策共同的特徵，是它們只描述樑柱，不描述牆面的裝潢。

把這五項定下來，換到的是什麼。後面的每一個 phase 都沿著同一批樑柱長，agent 不用每次重新猜 route 開在哪、資料長什麼樣、數字找誰要。計畫的每一行都還信得過，不用邊做邊懷疑前面寫的還算不算數。一份會讓 agent 懷疑的計畫，比沒有計畫更糟。agent 遇到可疑的行，會拿自己的判斷去補，而它的判斷和你寫計畫時下的判斷未必一樣。耐久決策的價值，在於它先把「你寫的」和「agent 跑的」之間的差距鎖死。鎖住的部分越多，後面每一段實作越貼近你原本的意圖。反過來想，如果計畫裡全是會過期的行，agent 每跑一個 phase 就要修一次計畫。修到最後，計畫和實作各走各的，前面寫的只剩下一個大概的方向。

這裡有個看起來矛盾的點，值得說破。計畫要寫的，偏偏是那些現在就能知道的決定。不知道的事，例如 phase 2 寫完之後某個函式內部長什麼樣，留給實作當下決定。人寫計畫時，常覺得細節定得越細越安心。這條規則正好反過來。對 agent 來說，越細的計畫越早失效，那份安心是假的。能確定下來的只有整體結構那一層。把能確定的寫下來，把不能確定的空著，計畫反而更準。

過度指定之所以誘人，是因為它看起來很安心。把每個 phase 的函式名、變數名、檔案路徑都寫出來，好像每一步都被事先算好了，agent 只要照著填。這份安心建立在一個假設上，假設實作會照計畫一字不差地發生。實作幾乎不會照計畫一字不差地發生，寫程式本身就是發現的過程，人類看到實際的程式碼就會調整。每次調整都讓計畫裡多一行謊話。一行謊話的代價不輕。agent 讀到後面的 phase，發現計畫寫的東西不存在，要嘛停下來問人，把一個本來可以自動跑的 phase 變成一次手動排解。要嘛自己改主意繼續做，等於跳過你規劃時下的判斷。兩種情況都在消耗你寫計畫省下來的時間，而且你多半最後才知道。

反過來看實作細節為什麼會過期。細節描述的是某段程式碼被寫成什麼樣子，而這個樣子要到執行那一段實作的時候才被決定。執行實作的是 agent，旁邊還有一個在場的人類。人類會改名、會合併、會在看到實際程式碼之後改變主意。每一次改動，都在悄悄改寫後續 phase 依賴的事實。計畫不會自己更新。舉一個具體的過程。計畫寫，phase 1 建立 analytics service，裡面的函式叫 computeSummaries。phase 1 執行的時候，人類發現 repo 裡已經有一個用途相近的現成函式，決定把新邏輯併進去，函式改名成 getDashboardStats。phase 2 的計畫寫，從 analytics service 匯入 computeSummaries。agent 照著找，找到的只有 getDashboardStats。它要嘛卡住，回頭問人，浪費一趟來回。要嘛自己換個名字繼續寫，計畫不再指揮工作，agent 開始編自己的新計畫。你寫這份計畫的理由，到此就消失了。

把兩種行文擺在一起看。

| 一執行就過期的 | 能跨 phase 存活的 |
| --- | --- |
| 具體函式名稱、內部變數名、參數順序 | route、網址路徑 |
| 內部實作步驟、誰呼叫誰的層級關係 | schema、資料的欄位與型別 |
| 某一行在哪支檔案裡 | 模組邊界，例如要不要有 analytics service |
| 一段程式碼的內部演算法 | 權限規則，例如講師（instructor）只能看自己課程的數據 |
| 實作當下的臨時決定 | 依賴哪幾套外部函式庫 |

左邊那欄的共同點，是每一行都描述某段程式碼的內部長相。右邊那欄的共同點，是每一行都描述系統在外部看起來長什麼樣。外觀在寫程式之前就能拍板，內在必須等程式寫完才知道。計畫只寫外觀，不寫內在。

能存活的決策還有一個共同點。它們都在別人用到它們之前就定好了。route 位置在頁面、測試、連結出現之前就定好了，所有東西都掛在它下面，它當然不會變。schema 在產生資料的一方和使用資料的一方出現之前就定好了，兩邊都照它對接，它當然不會變。函式名稱恰好相反，它只在定義它的那一段程式碼裡存在，定義它的程式碼一改，這個名字連同所有引用它的人一起失效。判斷一行字耐不耐久，除了問「到 phase 3 還成立嗎」，還可以看這行字的壽命繫在誰身上。繫在一個還沒寫出來的函式上，壽命短。繫在一個動手前就拍板、之後人人靠它的決定上，壽命長。兩個問法得到的答案一致，前者過期，後者存活。

判斷一份計畫裡一行字該不該留，有一條可以直接套用的規則。問一句，這一行到 phase 3 執行的時候還成立嗎。phase 3 執行時，phase 1、phase 2 已經寫完，還被人類改動過。如果這一行的事實依賴前幾個 phase 的具體實作，它那時多半已經不成立了。如果它只依賴動手前就做好的決定，它那時仍然成立。這條規則有效，是因為它逼你把每一行拿到後面的 phase 正在跑的當下檢驗，計畫剛寫完的那一刻什麼都還沒發生，什麼都驗不出來。

拿幾句實際會出現在計畫裡的句子測試這條規則。phase 1 呼叫 getRevenueSummary()，這行到 phase 3 還成立嗎。不成立，它命名了一個只在前一個 phase 恰好照計畫寫出來時才存在的函式，人類一改名就作廢。dashboard 需要三個彙總數字，分別是總營收、開課數、註冊數，這行到 phase 3 還成立嗎。成立，它規定了資料的形狀，不管數字背後怎麼算，這三個數字都要出現。instructor 只能看自己課程的數據，成立，它是權限規則。用 recharts（一套畫圖表的函式庫）畫圖表，成立，它是依賴決定。前一句替不存在的東西命名，後三句描述系統的樑柱，測試結果自己就分開了。

順序也很重要。先找耐久決策，再切 slice。[[learn/ai-coding-for-real-engineer/elements/tracer-bullet|Tracer Bullets（垂直切片）]] 切的是貫穿所有層、每一段都有東西能跑的片段，而切片要沿著樑柱切。樑柱先立起來，切片才有地方落。analytics dashboard 的 build 裡，phase 1 是一條貨真價實的垂直切片，把 analytics service、instructor route、summary cards（摘要卡片）三樣東西接起來，只用三個彙總數字當資料，跑完就知道整條路通不通。計畫裡每個 phase 都寫明要做什麼、對應 PRD 的哪幾條 user story（使用者故事），計畫裡的實作細節比直接把 PRD 丟給 agent 時少一大截。耐久決策寫在計畫最前面，切片沿著這些決策切，user story 讓每一段都記得為什麼要切。三件事各司其職。

這條規則也能當實作中的檢查工具。跑到 phase 2、phase 3 的時候，回頭翻計畫前置段落，看它列的耐久決策是不是真的現在就確定、以後也不改。同時翻每一個 phase 的描述，哪一行讓你冒出「等等，那個函式是叫這個名字嗎」的疑問，哪一行就是該從計畫拿掉的。會讓你懷疑它還成不成立的行，本身就不成立。例如計畫寫「phase 1 把彙總數字暫存在記憶體裡」，phase 2 實作時發現根本沒有暫存這一層，這行直接刪。計畫寫「dashboard 只有開課的講師本人能看」，這行到最後都成立。計畫是樑柱的地圖，樑柱留著，牆面在實作當下砌起來。把地圖寫成牆面裝潢的說明書，地圖就在第一個 phase 結束時變成廢紙。
