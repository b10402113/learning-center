# 寫出抓住 taste 的 PRD

## Learning goal

用 GrillMe + to-PRD 把開放式需求轉成帶 user stories 的 PRD，包含 problem statement、implementation decisions、testing decisions、out-of-scope。

## Steps

1. [[learn/ai-coding-for-real-engineer/nodes/writing-prd/grill-then-capture|先訪談，再捕捉：grill-me → to-PRD 兩步流程]] — 說出 PRD 是訪談的結果、不是 prompt 直出，並認出 shared understanding 到位的訊號
2. [[learn/ai-coding-for-real-engineer/nodes/writing-prd/scope-decisions|grill 把開放式需求釘成 scope 決策]] — 用 analytics dashboard 的決策鏈示範開放式需求如何收斂成具體 scope（after step 1）
3. [[learn/ai-coding-for-real-engineer/nodes/writing-prd/prd-anatomy|to-PRD 產出文件的骨架]] — 認識 PRD 的 problem statement、user stories、implementation/testing decisions、out-of-scope 各區塊（after step 2）
4. [[learn/ai-coding-for-real-engineer/nodes/writing-prd/practice-and-commit|動手：寫一份 PRD、記下觀察、commit]] — 跑一遍 grill → 寫 PRD → 記觀察 → commit，把 template 當活文件經營自己的 taste（after step 3）

## Lesson

PRD 是「destination」——一份把人的 taste 寫死、可以交給任何一個全新 session 照做的規格文件。但它的價值不是「寫得漂亮」，而是「寫之前先被問過」。開放式需求（「我想給講師做個儀表板」）在寫成 PRD 之前，需要一個 grill-me 訪談把 scope 一題一題釘出來：範圍跨不跨課程、給誰看、捨棄哪些指標、某個欄位到底是 sales 還是 enrollments。這個訪談是人的 taste 與 agent 的對抗式追問交手的過程，PRD 只是把交手結果捕捉下來的文件。所以這節課的四步，依序是：先看懂「訪談 → to-PRD」兩步流程為什麼非這樣排，再看訪談如何把模糊需求收斂成具體 scope 決策，接著認識 to-PRD 產出文件的骨架（user stories、implementation/testing decisions、out-of-scope），最後自己動手跑一遍並 commit。走完之後，你手裡拿到的不是一份「寫得很好的文件」，而是一份被問清楚、能被後續 plan 和 issues 逐條引用的 destination。
