# plan mode 的牆式計畫：它做對了什麼、錯在哪

## Learning goal

能說出 plan mode 的完整運作流程（探索、訪談、計畫 sub-agent、計畫選項），並指出它跳過 shared design concept、直接把答案壓成一面計畫牆的失敗模式。

## Lesson

plan mode（Claude Code、Codex 都有）在課程的 lesson 20 實跑中走了一條固定流程：先 spawn 一個 Explore sub-agent 讀 codebase（每個 sub-agent 有全新 context window，只回報摘要），接著用一兩個釐清問題訪談你（tab/方向鍵/數字選答案，escape 可以自己追問），再 spawn 一個 plan sub-agent——這是另一個 context-saving 技巧，用乾淨 context 設計、只把計畫摘要帶回主 context——最後把一份多步驟、附四種選項（自動接受編輯／保留手動核准／清空 context 後自動接受／修改計畫內容）的計畫牆端到你面前，才開始實作。整段跑完 `/context` 約 32–36%，還留在 smart zone。

先計畫本身不是錯的：計畫強迫探索、理解、對齊。錯的是「計畫前的訪談被壓短」——實務上 plan mode 常常只問一兩個問題就把答案壓成一面牆，看起來長而完整，但設計概念根本沒建立。人面對牆式計畫有個危險習慣：review 時跳過不齊的地方，假定它跟自己腦中一致。對齊沒發生，牆反而製造「已經對齊」的錯覺，雙方到實作中段才發現落差。
