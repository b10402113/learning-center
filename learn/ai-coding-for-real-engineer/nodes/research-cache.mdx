# 快取昂貴的探索

## Learning goal

在 loop 前用 HITL research 把外部文件/決策快取成 research.md，省 token、保 smart zone。

## Steps

1. [[learn/ai-coding-for-real-engineer/nodes/research-cache/why-cache-research|為什麼要把探索快取下來]] — 探索階段為什麼貴、為什麼值得先做一次寫成 research.md，以及為什麼這件事得由人主導
2. [[learn/ai-coding-for-real-engineer/nodes/research-cache/run-a-research-spike|跑一次研究：把未知問成一份文件]] — 可重複的研究 prompt：多方案、反覆提問、上網驗證、輸出到 plans/（after step 1）
3. [[learn/ai-coding-for-real-engineer/nodes/research-cache/anatomy-of-a-research-doc|好的 research 文件長什麼樣]] — 一份研究文件該有的區塊，以及它為什麼是 repo 裡的檔案而非 issue（after step 2）
4. [[learn/ai-coding-for-real-engineer/nodes/research-cache/research-doc-lifecycle|research 文件的生命週期：何時該做、何時該刪]] — 判斷何時值得研究，以及文件何時該保留、何時該刪（after step 3）

## Lesson

AFK 迴圈裡最花錢、最花時間的一段，通常不是寫程式，而是「搞清楚這件事到底該怎麼做」。當任務牽涉到你沒用過的服務、查不到的內部文件、或幾個互相競爭的技術選項時，agent 每一輪都得重新上網讀、重新比較、重新下結論。開一輪迴圈付一次這個代價，開十輪就付十次。

這個節點的做法是：把這段昂貴的探索先搬到迴圈外面，由你陪 agent 做一次，然後把所有結論快取成 repo 裡的一份 `research.md`。之後每一輪迴圈一開場就讀到答案，探索階段被壓短，省下 token，也讓 agent 把有限的 context 留給真正的工作——維持在「smart zone」裡。

四步沿著一條線走。先講**為什麼**要做（探索為什麼貴、快取為什麼有效、為什麼這得由人主導）；再給一套**可重複的研究 prompt**，把未知問成一組被比較過、被驗證過的方案；接著看**一份好的研究文件長什麼樣**，以及它為什麼放在 repo 的 `plans/` 而不是 GitHub issue；最後處理最容易被忽略的一環——**這份文件是會過期的**，要像 steering 文件一樣定期審、該刪就刪。

走完之後，你能在自己的 side project 上示範：面對一個從沒碰過的技術決策，先用一次 HITL 研究換來一份能餵進 PRD 與 issue 的文件，而不是讓自走迴圈每一輪都重複摸索。
