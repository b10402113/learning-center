# PRD 變成 Kanban backlog

## Learning goal

用 PRD-to-issues skill 把 PRD 切成帶 dependency 的垂直切片 issues，標出 HITL/AFK，並留下 QA checklist issue 收尾。

## Steps

1. [[learn/ai-coding-for-real-engineer/nodes/kanban-backlog/plans-live-in-the-backlog|計畫搬進 backlog：PRD 與 plan 都變成 issue]] — 說明為什麼要把規劃文件變成 issue，讓功能與 bug 共用同一個佇列
2. [[learn/ai-coding-for-real-engineer/nodes/kanban-backlog/hitl-vs-afk|哪些留給人、哪些放手：HITL 與 AFK 的界線]] — 用「哪裡需要品味」判斷一件工作是 HITL 還是 AFK（after step 1）
3. [[learn/ai-coding-for-real-engineer/nodes/kanban-backlog/kanban-over-phased-plan|用 Kanban 取代多階段計畫]] — 一張有依賴關係的 issue 圖，為什麼比一份多階段計畫更好用（after step 1）
4. [[learn/ai-coding-for-real-engineer/nodes/kanban-backlog/prd-to-issues-skill|跑 PRD-to-issues：把 PRD 切成垂直切片]] — 實際跑 skill，產出垂直切片、blocked-by、HITL/AFK 標記與 QA issue（after steps 2–3）
5. [[learn/ai-coding-for-real-engineer/nodes/kanban-backlog/run-and-qa-the-board|跑 AFK 迴圈與人工 QA]] — 檢查 tracer bullet、跑 AFK 迴圈、人工驗收並把回饋變新 issue（after step 4）

## Lesson

到目前為止，agent 已經可以從 issue 佇列裡自己挑任務、自己修完、自己關掉那張 issue。但佇列裡放的都還是 bug。如果想把整套流程用來「出功能」，就得回答一個問題：一份動輒好幾頁的 PRD 與計畫，要怎麼塞進這個只用一張張 issue 溝通的世界？

這個節點給的答案，是把 PRD 與計畫也變成 issue，然後換一種拆法。不要再把 PRD 攤成一份「階段一到階段三」的線性計畫，而是拆成一張有依賴關係的 issue 圖 —— 有些 issue 可以同時被拿起來做，有些必須等別人做完才能動。這樣拆出來的每一張，都是一條從資料庫一路切到畫面的垂直切片，而且可以標成「需要人參與」或「可以全自動」。

能自動的放手給 agent，需要人的排進自己的時間。最關鍵的一條規則，是永遠留一張包含完整人工 QA 清單的 issue 收尾：agent 做完前面所有 AFK 工作後會停下來，等你照著清單逐項驗收，再把不滿意的地方寫成新的 issue。這一節走完，你就有一套把「想法 → PRD → 一板 issue → 自走實作 → 人工驗收」串起來的做法，而且規劃與實作可以同時進行，不必等一邊做完才換另一邊。
