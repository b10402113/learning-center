# destination（PRD）與 journey（plan）兩份文件

## Learning goal

能說出兩文件模型裡 destination 和 journey 各裝什麼，以及「do phase N + PRD + 整份 plan」的 prompt 為什麼要帶上整份 plan。

## Lesson

任務小到一次對話放得下時，你把規格講清楚，agent 一次就能做完。任務一大，情況就變了。比方說重構一整個模組，或從零搭一個帶登入、資料庫、報表的後台。一個 agent 的 context window 只能裝那麼多文字，超過某個量，它就開始胡亂猜。社群把這種現象叫做變笨，也就是進入 dumb zone。需求一味往裡塞，它的回應越來越像敷衍，該檢查的地方跳過，做出來的東西你不敢收。

context window 是 agent 一次能讀進來的內容範圍，大約幾萬到幾十萬個 token。token 是模型處理文字的最小單位，一句話往往對應幾個到幾十個。smart zone 是 agent 還能保持專注、做出對的取捨的內容量。超過這個量，它就開始變笨，這塊區域叫 dumb zone。這幾個詞先記著，後面都會用到。

做法就變成：把大任務切成小段，每一段開一個全新的視窗來做。新視窗很乾淨，agent 從頭開始、注意力集中，這叫回到 smart zone。這裡有個容易被忽略的地方。每個新視窗都是一個全新的 agent，腦子裡什麼都沒有。它不知道你的產品要服務誰，不知道做到什麼程度算完成，也不知道你上一段已經做完哪些。你切得再漂亮，丟進去的還是一個失憶的人。

光會拆解還不夠，問題是：誰來維持一致？你把大任務切成互不相識的碎片，每個 agent 各做各的，最後拼不回去。社群試了很久，最後統一成一套做法，也就是[[learn/ai-coding-for-real-engineer/elements/two-document-model|兩文件模型 (Two-Document Model)]]。拆解之後，就由兩份存在硬碟上的文件來維持一致。這兩份文件能跨 context window 存活，任何新視窗都拉得進來。

兩份文件，一份管目的地，一份管旅程。第一份叫 destination，就是規格，也就是 PRD（產品需求文件）。它裝的是人的 taste，也就是你的喜好和判斷。第二份叫 journey，是一個 plan.md，把 PRD 拆成一段一段的 phase，講每段做什麼、照什麼順序做。

| 文件 | 名稱 | 裝什麼 | 回答的問題 |
|---|---|---|---|
| destination | spec / PRD | 人類的 taste | 做到哪才算完成 |
| journey | plan.md | 拆成 phase 的順序 | 怎麼一步步走到 |

destination 裝的 taste 是人的判斷，agent 代替不了。它寫的是你要什麼、不要什麼、長相如何、優先級怎麼排，以及衝突時往哪邊倒。用一個具體的請求來看差別。你說「做一個登入頁」，agent 可能自作主張加上第三方社群登入，因為它覺得這樣比較完整。可這其實是你的取捨，你不想給第三方任何存取，寧可只用帳號密碼。把「只要帳號密碼、不接第三方、記住登入七天」寫進 PRD，後來的每個 agent 都不用重新猜一遍你的意思。taste 這個詞，指的就是這類只有人能做、機器代不了的主觀選擇。

destination 不只有功能清單，還得寫下那些講不太出來、卻決定成敗的偏好。同一套功能，兩種做法外觀可以差很多。你想像的介面是乾淨的表格，agent 腦裡可能是花俏的儀表板。兩邊都沒錯，只是不是同一個東西。PRD 把長相這類主觀偏好也寫下來，後續每個 agent 才不會各自發揮。還有一種 taste，是關於速度和取捨的。你這次只要核心功能先跑得起來，寧可求快、把邊緣案例留到後面；agent 卻可能想一次把所有錯誤處理做完，又慢又全。你把「先做通、後補齊」的順序寫進 PRD，agent 才知道該往哪邊收斂。這些都是人才能下的判斷，destination 正是拿來裝這種決定的。

journey 那張 plan.md 把 PRD 拆成一段一段。每段是一個 phase，寫明這一段做什麼、做完交付出什麼、照什麼順序接下去。它不重複 PRD 的 why，只負責把目的地切成一條能走的路。同一個 PRD，換一個人拆，phase 的切法完全不同，這是 journey 自己的功夫。一句話總結：destination 回答為什麼做、做到哪算好；journey 回答現在走到哪、下一步做哪段。

用一張更細的對照，把兩份文件的分工攤開。

| 面向 | destination（PRD） | journey（plan.md） |
|---|---|---|
| 回答的問題 | 做到哪才算完成 | 怎麼一步步走到 |
| 承載的內容 | 你要什麼、不要什麼，長相，優先級與取捨 | 每個 phase 做什麼，順序，跟前後怎麼接 |
| 誰來定 | 人，來自 grill 訪談 | 人拆的，範圍依賴 PRD |
| 被誰消費 | phase prompt 帶整份 | phase prompt 帶整份 |
| 少了它 | 新視窗不知目標，做到一半偏掉 | 新視窗不知銜接，phase 互相踩腳 |

destination 那欄回答「這是哪座山、到了要看到什麼」，journey 那欄回答「Day 1 走哪段、Day 2 走哪段」。兩欄缺一不可。少任何一個，phase prompt 都餵不飽那個失憶的 agent。

兩份文件必須寫進檔案系統，這是它們能跨視窗的關鍵。新開一個 session 時，用 @ 把 PRD 和 plan.md 拉進 context，agent 就知道要做什麼、做到哪一段。你不靠記憶，靠檔案，因為新視窗根本沒有記憶可以靠。

有人會問：agent 之間能不能靠記憶接起來？有些工具確實會讓 agent 把自己定的規矩寫進一個檔案，下次讀回來，比如「這個專案要用某個套件、某個指令」。可這種記憶不可靠，會過期，還會記下早就不存在的做法。跨 phase 的一致不能押在這種會變質的東西上，得押在固定的兩份文件上。你要的是確定性：每次開新視窗都拿到同一份 PRD、同一份 plan，不會因為 agent 上次心情不同而改變。

光有文件還不夠。文件寫好了，新 session 的 agent 打開一看，怎麼知道這次只做第 N 段，而不是把整個 build 一次做完？如果只把 PRD 丟過去，它看到完整的願景，很可能又想一口氣實現全部，再次爆回 dumb zone。拆解要真的有用，得靠那句[[learn/ai-coding-for-real-engineer/elements/phase-prompt|Phase Prompt (do phase N)]]把它接起來。

phase prompt 的形態是固定的。

```
we're going to do phase N
+ PRD（整份 destination）
+ 整份 plan（整個 journey）
```

三個部分缺一不可。第一句「做 phase N」告訴 agent 這次的範圍：整段旅程裡的第 N 段，不是全部。第二份是整份 PRD，讓 agent 握著全局目標和你的 taste，不會做著做著偏掉。第三份是整份 plan，讓 agent 知道這一段跟前段、後段怎麼接，哪些東西前一 phase 已經做過，哪些留給後一 phase。

關鍵在「整份」。你很容易想偷懶，只把第 N 段那一頁丟給 agent，其餘全藏起來。可 agent 要在全局脈絡裡才能做對取捨。它要看到第 3 段的前提是第 2 段建好了某個介面，才不會在第 3 段自己再造一個重複的。它要看到第 5 段會負責收尾，才知道第 4 段不用提前把邊角補完。帶整份 plan，就是要讓 phase 之間不踩到彼此的腳。

帶整份還有一層實際的理由：介面要對得上。前一 phase 建的查詢服務，函數叫什麼、回傳什麼結構，phase 2 要照著用。agent 只有看到整份 plan，才知道前一 phase 留下什麼形狀，才不會自己發明一套對不上的函數簽名（參數和回傳格式）。改成只帶第 N 段的話，這些對不上的情況全會冒出來，你就得回頭一個 phase 一個 phase 修。

舉個具體的例子。假設你要做一個課程平台的教師數據後台，讓老師看到自己的收益、報名數、平均評分。這東西塞不進一個視窗，於是拆成幾個 phase。phase 1 先把查詢服務層建起來，phase 2 做報表介面，phase 3 收尾，把路由和管理員入口接上。

你做完 phase 1，commit 一次，清空視窗，開一個新 session。這次你只說 we're going to do phase 2，然後把整份 PRD 和整份 plan 用 @ 拉進來。新視窗的 agent 讀完 PRD，知道目標是給老師看收益和評分，知道銷售額要跟報名數分開列，這是你的 taste。它讀完 plan，知道 phase 1 已經把查詢服務建好，就直接拿它來畫介面，不重做。它也知道 phase 3 才做路由，現在不用急著接進去。整個機制，一句話就把三樣東西同時餵給了失憶的 agent。

把第三段也走一遍，會看得更清楚。phase 2 做完，你照舊 commit、清空視窗，開新 session 說 we're going to do phase 3，同樣帶上整份 PRD 和整份 plan。新視窗的 agent 從 PRD 讀到一件事：這套後台要讓管理員也能進。這是後來加進去的範圍，而且你希望管理員跟教師共用同一份報表元件。它再從 plan 讀到，phase 2 已經把報表介面做成了可重用元件，路由還沒接上。於是它決定 phase 3 只做兩件事：把元件接到教師路由，再複製一份給管理員路由，介面不重畫。它沒有回頭改 phase 1 的查詢邏輯，也沒重做 phase 2 的介面，因為 plan 告訴它那兩段已經完成。做完照舊 commit。三個不同視窗的 agent 各自完成一段，靠的只是每開新窗就重讀一次那兩份文件。

那如果少了整份 plan 呢？假設你只說「做 phase 2」，沒給 plan。新視窗的 agent 不知道 phase 1 做過什麼，可能以為查詢服務還沒建，自己又建一套，最後跟 phase 1 留下的東西重複甚至衝突。或者它不知道 phase 3 要接路由，提早把路由寫死，後面的 phase 反而被綁住。它還可能換一套跟 phase 1 不同的圖表套件，整個專案的風格裂成兩半。這些都是不帶整份 plan 會踩到的腳。

踩到腳不是抽象的講法，我們說具體一點。假設 phase 1 已經把資料結構定成某個形狀：報表的每一列叫什麼欄位、金額是整數還是小數，都寫在那一 phase 的程式裡。phase 2 的 agent 若沒看到 plan，不知道這些欄位已經定好，就會自己重新定義一套。欄位名對不上，介面畫好了卻讀不到資料。若它看到了整份 plan，知道 phase 1 已把資料層鎖住，就只負責把介面接到那些欄位上。整份 plan 讓每個 phase 的 agent 都知道自己站在別人的地基上，該往上蓋，而不是重新挖。

每完成一個 phase，你就清空視窗、commit 一次，再開新 session 做下一段。destination 和 journey 在這個循環裡反覆被拿來用，同一份文件餵給一個又一個失憶的 agent。人的位置一直沒變：taste 從頭到尾由你決定，agent 只在每個 phase 的範圍內執行。最後一 phase 做完，整趟旅程的每一段都被不同視窗的 agent 依序完成。而把它們串成一個完整產品的，就是這兩份文件。

這一趟跑下來，文件也不是擺著不動的。某個 phase 做到一半，很可能冒出 PRD 沒寫到的情況，比如資料庫欄位比預想多，或某個介面比預期複雜。你當下把 PRD 或 plan 改一改，把新判斷寫進去，再開下一段。destination 和 journey 是活的，改完之後，後面的 phase 讀到的是新版本。「taste 一直由人掌握」也包括這一層：就算拆好寫好了，一樣能改；改完文件跟著變，後面的 agent 才不會拿舊版做下去。

那 PRD 裡面的 taste 又是從哪來的？它不是 agent 憑空想的，來自人跟 agent 的一場訪談，這個訪談叫 grill。grill 裡，agent 像審問一樣追著你把需求問清楚，問到每個細節都落地。這個階段的目的地，由人來定。目標明確之後，再用 to-PRD 這個技能，讓 agent 讀完一整場對話的上下文，在本地產出一份 PRD。to-PRD 產出的 PRD 有個固定骨架：一段 problem statement 講為什麼要做，一段 solution 講怎麼解決，後面跟著一長串編號的 user story。每一條都是「作為誰，我想要什麼，好讓什麼」。這樣寫出來，你對產品的判斷才變成一份能交到新視窗手上的文件，成為 destination 那張紙的實體。

user story 之所以要編號，是為了讓後面的 plan 能指回它。某個 phase 做的功能對應到 story 7，agent 動手時就知道自己在服務哪一條需求，不會做到一半忘了原本為什麼要做。這條線把 PRD 裡的人類判斷一路帶進實作，destination 和 journey 才不會是兩張各說各話的紙。grill 問出你的 taste，to-PRD 把它落成文件，兩文件模型負責讓這份文件在拆解之後活下來。

開頭說那個 agent 什麼都不知道，這句話要拆成兩半。關於「為什麼做、做到哪算好」，它不知道，靠 destination 補。那份 PRD 把你的 taste 一字不漏帶給它。關於「現在走到哪、下一步做哪段」，它也不知道，靠 journey 補。那份 plan 把它在整條路上的位置講清楚。而 phase prompt 是那個把兩份文件合起來、一次丟給 agent 的動作。缺了任何一份，新視窗的 agent 都只能瞎猜，又退回各做各的、最後拼不回來的結局。
