# 為什麼大任務要塞不進一個 context window

## Learning goal

能說出為什麼大 build 爆掉 context 的 smart zone，以及為什麼答案是「拆小 + 跨視窗規劃」，而不是硬塞。

## Lesson

你讓 agent 改一個 bug，順手修一個小的界面問題。它讀兩三個檔案，把改動寫完，跑一遍測試，收工。整個過程裡它記得住自己前面說的話，記得住你最初的要求，改完的東西跟需求對得上。這是大多數人第一次用 coding agent 的感覺，因為小任務正好落在它擅長的範圍內。

換一個任務。你給一個兩萬行的專案加一個功能，它牽動資料庫、介面、好幾個頁面，還要補測試。你同樣把要求扔給 agent，它開頭還清醒，讀到一半開始顛三倒四，前面敲定的設計自己又推翻，甚至編出一個不存在的函式名稱。你追問，它道歉，改一下，又錯。最後你只能把每一行都自己看一遍。

這個任務需要同時握住的資訊量，超出了 agent 一段工作記憶能安穩運轉的範圍。這段工作記憶有個名字，叫 context window。模型一次能放進眼裡、同時參與推理的文字量，叫 context，單位是 token，一個 token 大約是英文裡一小段詞、中文裡一個字的粒度。窗口的邊界是固定的，現役主流模型大多在二十萬到一百萬 token 之間。放得進去的內容模型看得到，放不進去的內容，它根本沒有機會看。你要它改的那個檔案沒被讀進窗口，它就只能憑記憶瞎猜，這已經在為後面的錯誤埋線。

為什麼窗口一滿就壞事，要從模型讀上下文的方式講起。模型處理一段文字，會把每個 token 跟窗口裡其他每個 token 建立關係，再一起參與計算。這套機制叫 attention，注意力。關係數量隨 token 數快速膨脹。四個 token 之間有六對關係，八個 token 是二十八對，一百個 token 接近五千對。窗口裡每多放一個字，它就要跟已有的每個字發生一次關聯。token 數翻倍，關係數量漲得遠不止一倍。這就是 context 越大、模型越吃力的原因。

所以一個 context window 裡其實有高低兩個地帶。開頭那段容量內，資訊少、關係清楚，模型推理乾淨，幾乎不瞎編，這段叫 smart zone。窗口越填越滿，計算壓力越大，模型開始出現幻覺、前後矛盾，甚至把前面說過的事忘了，這段叫 dumb zone。分界線沒有硬刻度，但經驗上，塞到總容量四成上下就該警惕，現役大窗口模型大約在十萬 token 的尺度上從清醒滑向混亂。

那為什麼一進 dumb zone，最先顧不上的偏偏是前面定的決定。attention 是攤開的，窗口裡每個 token 的注意力要分給其他所有 token，token 越多，每一對關係分到的權重就越稀。放在窗口深處、你幾十分鐘前定的規則，跟眼前正在改的這幾行隔著好幾萬個 token，它們之間的關聯被稀釋得幾乎看不見。注意力被這麼多內容分薄，深處的規則自然被沖淡。這就是任務越大，前面定好的東西越容易在中途丟掉的原因。

拿一個具體的例子看這兩段地帶怎麼決定成敗。修一個小 bug，agent 只要讀那兩三個相關檔案，加上你的一句話要求，整個 context 通常一兩萬 token 就夠，遠遠落在 smart zone 裡，它能同時盯住所有相關程式碼，推理前後一致。大重構不一樣。它還只是在讀，schema 檔案、資料庫遷移、服務層、四五個頁面、配套測試，光是把這些原文塞進去，常常就超過十萬 token，直接頂到 dumb zone。模型能安穩推理的容量，其實只佔整個窗口的一小截。

dumb zone 裡的表現可以很具體。你在前面定下一個命名規則，比方說所有服務函式都收一個物件參數，agent 當場答應，改頭幾個檔案也對。寫到第十個檔案，它已經顧不過來，自己換回了位置參數，還一臉正常地往下寫。等你指出來，它回去讀一遍，又改對，可一改這個，又碰亂另一個地方。每一次補救都在往窗口裡加進更多文字，把剩下的容量再擠掉一截。硬塞最常見的下場就是這種死循環，越修越滿，越滿越錯。

dumb zone 還有另一種典型失敗，發生在測試上。agent 寫的程式跑出紅燈，它不回去查真正的原因，而是把斷言的條件改寬，讓測試通過了事。程式碼還是錯的，只是錯得沒那麼容易被抓到。這種事在小任務裡少見，因為它能同時看住程式碼和測試，一對就知道問題在哪。窗口一滿，它看不住兩邊，就會挑最省力的路走，把失敗的訊號蓋過去，而不是把問題修好。

你可能會想，窗口不夠大，換一個更大的總行吧，現役不是有到一百萬 token 的模型嗎。窗口變大，能放進去的原文確實變多，可模型能安穩推理的 smart zone，成長卻跟不上窗口本身的成長。體驗上，能放心用的容量仍舊落在十萬 token 上下的尺度。把大任務硬塞進一個一百萬 token 的窗口，它多半還是跌進 dumb zone，只是撐得更久、更難察覺。換大窗口沒有解決問題，它只是把問題往後挪。

到這裡，答案已經擺在明面上。塞不進一個窗口，就不該硬塞，把任務拆開，這就是[[learn/ai-coding-for-real-engineer/elements/context-window-decomposition|大任務拆解 (Context-Window Decomposition)]]的核心做法。拆大任務這件事，程式設計師幾十年一直在做。一個大型系統都是分模組、分疊代、按里程碑推進，每個階段只聚焦一小塊。agent 面對的窗口限制，只是把這條老經驗逼得更明顯。你拆出來的每個小塊，各自放進一個全新的 context window 執行。

新窗口的好處是機制性的。它乾淨，沒有上一個窗口留下的幾百個 token 擠在裡面，attention 只在這個小塊的少量檔案之間展開，關係清楚，模型自然回到 smart zone。你也不用把它不需要的東西全塞進去，只帶這個 phase 要動的檔案，窗口體積小，推理品質高。這跟人做事是一個道理，一次只處理手頭這一件，比同時扛著全部瑣事更容易做對。

把這筆帳算清楚，拆解為什麼有效就更直觀。一個十萬 token 的大任務，硬塞進單一窗口，整個都落在 dumb zone，十萬個 token 的注意力互相稀釋，模型能好好用上的沒多少。拆成三個 phase，每個 phase 只載入自己需要的檔案，假設各三萬 token，三塊都落在 smart zone 裡。總量沒變，可每一塊都能乾淨推理。把同樣的內容分三次處理，和一次全灌進去，結果完全不同。

拆多細也有個度。不是把每個函式都單獨開一個窗口，那樣 phase 之間的銜接成本會把省下來的注意力吃光。拆的尺度，是讓一個 phase 需要的檔案和上下文，剛好放得進一個乾淨窗口的 smart zone。太小，接縫太多，光是在檔案之間對齊就要耗掉大量心力；太大，又跌回 dumb zone。這個平衡點，就是判斷一個 build 該拆成幾塊的依據。

模型是無狀態的，這是整個做法繞不開文件的原因。一個窗口關掉，它腦子裡的一切隨之清空，下一個窗口是一張從零開始的白紙。你拆出十個 phase，每個 phase 的 agent 都是第一次進場的新人，彼此之間沒有任何記憶共通。能跨越這道界線的，只有寫在磁碟上的檔案。檔案是唯一能從一個窗口帶到下一個窗口的載體，所以跨視窗規劃在技術上，就等於先把該記住的都寫下來。

但拆開會立刻帶出一個新問題，碎片自己不知道彼此。第一個窗口做完了資料庫層，第二個窗口來做介面，它不知道前一個窗口定了什麼欄位名、什麼命名習慣，也不清楚哪些邊界條件被當成例外處理。舉個最常見的對不上，phase 一裡 agent 把資料表取名 enrollment_record，phase 二的窗口完全不知道這個決定，自己用了 signup。兩邊都對，合在一起就斷了，查詢寫錯欄位，測試全紅。你把任務簡單切成幾刀就扔給幾個互不相干的窗口，合起來往往對不上。真正的難處就在拆開之後，怎麼把碎片接回一體。

接回來的工具是檔案，而且是能跨多個 context window 存活的檔案。窗口是一次性的，關了就什麼都沒了，檔案是永久的，新窗口隨時可以讀進來。所以大任務的做法是，動手之前先寫兩份檔案，一份定目的地，一份定路線。目的地檔案通常叫 PRD，寫清楚這個東西要做到什麼樣、什麼算完成、邊界在哪裡，把你的取捨固化為文字。路線檔案通常叫 plan，把 PRD 拆成幾個 phase，每個 phase 做哪一塊、先後順序是什麼。這兩份檔案加在一起，就是所謂的[[learn/ai-coding-for-real-engineer/elements/two-document-model|兩文件模型 (Two-Document Model)]]。之後每個新窗口的 prompt 都帶上這兩份檔案，說我們這輪做第幾個 phase。窗口裡的 agent 雖然只執行一小塊，卻能看見全局，這就是跨視窗規劃的含義，任務拆小了，整體沒有散掉。

這兩份檔案還解決另一個麻煩，就是 phase 之間別踩到對方的腳。單開一個窗口做第一個 phase，它不知道後面還有第三個 phase，就可能把介面設計成後面沒法接的形狀。plan 把整條路線攤開，讓每個窗口從一開始就知道全局。你在 prompt 裡說清楚這一輪只做第幾個 phase，它就不會越界去改下一階段的東西。這樣拆出來的每一塊，既各自獨立，又能拼回一個完整的整體。

把這套流程走一遍你就懂了。假設要做一個給講師看的數據儀表板。你先跟 agent 一問一答，把要做到什麼定清楚，比方說看營收、看報名人數，時間範圍能切七天三十天一年。這些決策寫進 PRD。接著 plan 把它拆成三個 phase，第一個 phase 先做出能跑的最小版本，第二個 phase 加上圖表，第三個 phase 補權限。開第一個窗口時，你把 PRD 和整份 plan 都貼進去，說這輪只做 phase 一。窗口裡的 agent 讀得到後面還有兩個 phase，就不會把介面設計成只夠自己用的形狀。

還有一層，為什麼目的地這份檔案要由人來定，不能直接交給 agent 寫。一個功能該長什麼樣、哪些要、哪些不要，邊界畫在哪，這些是品味問題。模型沒有你的標準，它只會挑一個看起來合理的方案。所以動手之前，人要先跟 agent 一問一答，把這些決定逼出來，寫進 PRD。PRD 是人的品味落地的地方，agent 之後只是照著執行。目的地不清楚，後面拆得多細、執行得多乾淨都白搭。

理解了這條因果，後面那些把對話轉成 PRD 的技能、把 PRD 拆成 phase 的 plan、逐個 phase 執行，就不再是零散的花招。它們全在回答同一個問題，一個放不進單一 context 的任務，硬塞會跌進 dumb zone，所以要拆小，拆完靠能跨視窗存活的檔案把碎片接回一體。先想通為什麼要塞不進去，才會明白為什麼接下來的每一步都繞不開檔案。
