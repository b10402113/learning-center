# grill 完，把它變成一份 PRD（to-PRD 流程）

## 這篇文章在講什麼

訪談（grill）做完之後，你手上有一堆共識。但這些共識全部只活在對話裡，一關視窗就消失。這篇文章要解決的問題很具體：**怎麼把訪談裡釘下來的決定，變成一份能跨視窗、跨工具、換人接手也還存在的文件。**

答案是一套兩段式流程：

1. **grill-me**：訪談，把模糊的需求一題一題問清楚。
2. **to-PRD**：把訪談的結果固化（寫死）成一份 PRD 檔案。

我們一步一步看，為什麼需要這套流程、它怎麼運作，以及最後產出的 PRD 長什麼樣子。

---

## 問題：訪談的共識，全都活在對話裡

訪談結束的時候，你手上有一堆共識。要做什麼、不碰什麼、哪裡可以將就、哪些取捨一步都不能退，這些答案是在 grill-me 那一輪一題一題釘下來的。

問題是，它們全都活在對話的 **context** 裡。context 可以想成 agent 當前看到的全部內容：你跟它在這個視窗裡講過的話、它讀過的檔案、它動手做過的事，全都在裡面。

你一關掉這個 session（這次對話），這堆東西就一起消失。再開一個新視窗，agent 是全新的。它不知道你剛才跟誰討論過什麼，也無從判斷那些決定為什麼是決定。

你花了一整輪訪談釘下來的東西，等於白問了。

---

## 兩個特別痛的時刻

這種「關掉就沒了」的痛，在兩個時刻特別明顯。

**第一個時刻：你想換工具。**

訪談在 Claude 裡做的，實作想交給別家的 agent，或者放到 GitHub 上的 runner 去跑。原來的對話帶不過去，過去的一切只剩你自己的記憶。

**第二個時刻：任務太大。**

大任務塞不進單一 **context window**。context window 是 agent 一次能記住內容的上限。超過某個量，它就開始忘、開始變笨，那條線業界叫 **dumb zone**（笨區）。

所以正規做法是把任務拆小，讓每一塊都留在聰明區裡跑完。可拆完之後，每個新視窗的 agent 誰也不認識誰。誰來告訴第二個視窗：第一個視窗做完了什麼、你原本要的到底是什麼？

---

## 解法：一份能跨視窗活下來的文件

所以要有一份能跨視窗活下來的文件。

社區（開發者社群）收斂出兩份，這就是 [[learn/ai-coding-for-real-engineer/elements/two-document-model|兩文件模型]]：

| 文件 | 白話叫法 | 它回答什麼 |
| --- | --- | --- |
| **destination** | 目的地 | 做到哪才算完成。它把人對產品的判斷全部寫死。 |
| **journey** | 旅程 | 怎麼一步步走到。它把 PRD 拆成一段一段的 phase。 |

- **destination** 就是 **spec（規格）** 或 **PRD（產品需求文件）**。它回答：做到哪一步，這東西才算完成。
- **journey** 就是 **plan（計畫）**。它把 PRD 拆成一段一段的 phase（階段），回答怎麼一步步走到。

兩份都寫成檔案放上磁碟。後續每個新 session 用 `@` 把檔案拉進來，agent 就掌握了全局。

到這裡，只剩一個問題：**PRD 不會憑空長出來，它得有人寫。**

---

## 誰來寫這份 PRD？

最了解內容的人是你，可你離線去寫會漏。

那些決定都是在對話裡一個一個做出的。當時有前後文托著，現在靠記憶重現，你記不全，也講不準。

交給 agent 自己寫，它又不知道你的 **taste**。taste 是你對產品的偏好：哪個細節重要、哪個取捨能接受。這些 agent 猜不出來，只能你親口講。

這是一個缺口。[[learn/ai-coding-for-real-engineer/elements/to-prd-skill|to-PRD (To-PRD Skill)]] 就是為這個缺口設計的。

---

## to-PRD 在做什麼

先講一下 **skill** 是什麼。skill 在這裡指一段預先寫好的指令文件，agent 碰到對應場景就會照著執行。

to-PRD 做的事，一句話講得完：**它讀取當前 conversation 的 context，把訪談這一路的問答全部接過去，在本機產出一份 PRD 檔案存下來。**

你不用重新講一遍，也不用自己把對話整理成摘要。它直接把完整脈絡轉成結構化的文件。

這就構成兩段式流程：

| 階段 | 名稱 | 做的事 |
| --- | --- | --- |
| 第一段 | **grill-me** | 訪談，把模糊需求釘成 **shared design concept**（共同設計概念）。大家對要做的東西，有了同一張圖。 |
| 第二段 | **to-PRD** | 固化。把訪談結果寫成 PRD 檔案。 |

**判斷的時機在這裡：** 這個 build 大到同一個視窗裝不下，就呼叫 to-PRD。小功能、修 bug 這種一次能做完的，不用走這步，訪談完直接做。真要拆 phase 的，才需要把它變成文件。

---

## PRD 的骨架：八個段落

to-PRD 產出的 PRD 有固定骨架，細節見 [[learn/ai-coding-for-real-engineer/elements/prd-structure|PRD 結構 (PRD Structure)]]。

骨架是整個流程的契約，讓任何讀者拿到文件，就能獨立判斷內容全不全。

核心三塊是：**problem statement（問題陳述）、solution（解法）、一長串編號的 user stories（使用者故事）**。另外還有幾段決定性段落，把工程取捨也一併寫死。

逐段來看：

### Problem statement（問題陳述）

描述一個具體的人卡在哪裡，把處境講清楚，解釋為什麼這件事值得做。它站在使用者的位置上寫，寫的是**人的處境**。

### Solution（解法）

同樣站在使用者這一邊，寫解決方案長什麼樣、怎麼回應前面那個問題。它寫的是**一個人用起來會是什麼感覺**。

### User stories（使用者故事）

一長串編號的清單。格式固定是「as an instructor I want X so that Y」——我是一名講師，我想要 X，這樣我才能 Y。

每一條是一個具體、可驗收的需求。**編號很重要**：後面的 plan 可以直接引用第幾條，實作時對得上需求，判斷做完了沒也拿它當依據。

### Implementation decisions（實作決定）

技術層面的具體選擇：新增哪個 **service module**、開哪條 **route**、共用哪個 **component**。

- **service module**：後端一個職責單一的模組。
- **route**：API 的入口路徑。
- **component**：前端可重複使用的介面元件。

這些細節可以而且應該由人指定。訪談裡你對專案結構的判斷，直接寫進這裡。

### Technical decisions（技術決定）

架構層的取捨：用哪套函式庫、要不要包一層包裝。

### Testing decisions（測試決定）

測哪些、怎麼測、測到什麼程度。

### Out-of-scope list（不做清單）

明確寫這次不碰什麼，把範圍的界線畫出來。

### Further notes（其他註記）

前面沒歸到任何一處的補充。領域知識、數據定義、需要注意的坑，都放這。

**小結：** 核心骨架是前三塊——問題陳述、解法、編號使用者故事。其餘段落是加分項，把 taste 和工程取捨一起固化進文件。

整個流程裡有一條最重要的分工：**agent 負責質疑、追問、查漏，人負責拍板。** to-PRD 固化的，正是人逐題拍下的那些板，也就是 [[learn/ai-coding-for-real-engineer/elements/taste-in-spec|規格裡的 taste]]。

## 實際例子：做一個分析儀表板

用一個例子走完整條路，你才看得見這套流程替換掉了什麼。

假設你負責一個線上教學平台。講師在平台上開課賣課，平台抽成。問題是：講師付了錢，卻看不見自己課程的數據。他不知道賣了多少錢、多少人報名，也看不出多少人上到一半就放棄。

你要把這個 **analytics dashboard**（分析儀表板）做進平台裡。

### 訪談階段：一題一題把範圍收緊

你開一個 grill-me session。agent 一題一題問：想看什麼、給誰看、預設時間範圍多長、要不要細分到單一課程、管理員要不要也能看。你每題都答，範圍就在問答裡收緊。

你原本想做一個包山包海的數據中心。問到一半，你把範圍收斂到「營收和評分」兩件事上。

**這個收緊，正是訪談的價值所在。** agent 的提問會戳到你沒想清楚的取捨。例如，你一開始沒決定要不要納入測驗和地理位置數據，被問了才發現這兩塊你用不上，想都不想就刪了。

### to-PRD 到底讀了什麼

先看對話本身長這樣：

- agent 問你想讓講師看到哪些數字，你說最起碼是營收和報名人數，最好再加一個平均評分。
- agent 追問管理員要不要也能看，你想了想說要。講師只能看自己的課，管理員得能代看任何一位講師的儀表板。
- agent 再問時間範圍，你回預設三十天，但切換要支援七天、三十天、十二個月和全部。

這幾句問答，全部進到 context。to-PRD 讀的就是這整段。它把你確認過的每一條答案，拆成獨立可驗收的使用者故事：

- 你講「預設三十天」，它就寫成 *as an instructor I want the dashboard to default to the last thirty days so that I always see a meaningful recent window*。
- 你講「管理員要能代看」，它就寫成 *as an admin I want to open any instructor's dashboard so that I can help them when they ask*。

編號從這裡長出來。第幾條對應你哪一句拍板，一對得上。

也因為故事是從你親口講的答案拆出來的，**每一條都有你在場，都有來源**。agent 無從憑空補一個你沒同意過的需求。

### 訪談到什麼程度可以呼叫 to-PRD

訪談進行到某個程度，agent 的提問會變成快速連發、題目也顯而易見。這通常是「共識已經建立」的訊號。

你判斷這個 build 太大，同一個視窗做完不划算，就呼叫 to-PRD。

它讀取了大約 **五萬兩千個 token** 的訪談 context。**token** 是模型計數文字的最小單位，幾萬個 token 大概相當於一份很長的對話稿。

它吐出的 PRD，有完整的**八段結構**：

- **問題陳述**：講師看不到課程的營收與參與度數據。
- **解法**：一個跨課程的營收儀表板，預設三十天。
- **使用者故事**：一條一條排下去，例如 *as an instructor I want to see total revenue so that I know how much my course earned*，以及 *as an admin I want to open any instructor's dashboard so that I can help them when they ask*。
- **實作決定**：新增一個 analytics service module；開一條講師的 route，再開一條管理員的 route；共用同一個畫圖的 component。
- **技術決定**：圖表直接裸用 **recharts**（一套畫圖的 JavaScript 函式庫），不包 **shadcn** 的殼（shadcn 是一套常見的 React 元件庫）。
- **測試決定**：測 service 的聚合邏輯，和 route 的權限檢查。
- **不做清單**：這次不做測驗分析、不做地理位置分析，單一課程的深挖同樣排到範圍外。
- **其他註記**：補一條——sales 和 enrollments 是兩個不同的數字，有團隊購買會一次買好幾份課程，銷售額對不上報名人數，欄位要分開。

### 落成一份實際的 PRD 檔

把上面說的落成實際的 PRD 檔，長這樣：

```markdown
## 問題陳述
講師看不到自己課程的營收和參與度，無法判斷課程賣得好不好。
## 解法
一個跨課程的分析儀表板，預設三十天，顯示總營收、總報名人數、平均評分，以及一張可按課程排序的明細表。
## 使用者故事
1. as an instructor I want to see total revenue so that I know how much my courses earned
2. as an instructor I want to see total enrollments so that I know how many students signed up
3. as an instructor I want to see average rating so that I know how students feel about the course
4. as an instructor I want a thirty-day default so that I always see a recent window
5. as an admin I want to open any instructor's dashboard so that I can help them when they ask
## 實作決定
- 新增 analytics service module
- 開一條講師 route 和一條管理員 route
- 共用同一個圖表 component
## 技術決定
- 圖表用 recharts，不包 shadcn 的殼
- 時間範圍用 URL 參數保留
## 測試決定
- 測 service 的聚合邏輯
- 測兩條 route 的權限檢查
## 不做清單
- 不做測驗分析
- 不做地理位置分析
- 不做單一課程深挖
- 不做匯出 CSV
## 其他註記
- sales 和 enrollments 是兩個數字，團隊購買讓兩者對不上
```

---

## 不做清單的份量，比看起來更重

看那份不做清單，它的分量比看起來更重。

實作的人拿不到「做完了沒」的判準，就會自己補。訪談時你順口提過一句，也許加個匯出 CSV 會很方便。這句話放進不做清單，寫明這次不碰，實作的人一看就懂：這是刻意略過，算一個正式決定。

反過來看，如果 scope（範圍）沒有界線，reviewer 或 agent 隨時會被新念頭勾走，每看完一版就問一句「要不要順便加個篩選、加個匯出」。build 永遠收不了尾。

out-of-scope 把界線釘死。當清單裡所有該做的都做完、清單外的一件都沒被拉進來，這一輪才算真的做完。它就是 **「done」這個詞的落點**。

---

## PRD 為什麼比手寫筆記值錢

這一段正是 PRD 比手寫筆記值錢的地方。

sales 不等於 enrollments，這個細節是在訪談裡釘下來的領域知識。它決定資料表的欄位怎麼設計、數字怎麼定義。

手寫很容易漏掉這種微妙處。寫了銷售額就夠了，等實作的人問「報名人數怎麼算」，兩個數字對不上，回頭補又得開一輪對話。

to-PRD 把整個訪談脈絡轉進去，這種微妙處就不會丟。

---

## 交接：存檔、commit、交給下一個視窗

PRD 寫出來之後，接下來是交接。

你把它存成本機檔案，**commit** 進 git。commit 的意思是：給目前的檔案狀態留一個有記錄的版本。

之後任何一個新視窗、任何一個 agent、甚至另一套工具，都能拿這份文件當起點。新 session 開起來，用 `@` 把 PRD 拉進去，再帶上 plan，就可以開始拆 phase 實作。

到這一步，訪談的共識終於離開對話視窗，變成磁碟上的一份 destination。跨 session、跨工具、換人接手，它都在。

兩文件模型裡，destination 和 journey 各司其職：

- to-PRD 產出的這份 PRD 就是 **destination**，回答「做到哪才算完成」。
- 接下來該 **plan** 出場，把 destination 拆成一段一段的旅程。

---

## 關於模板的最後一句話

to-PRD 產出的格式還沒有定案，八成還會被社區繼續吵很多年。

你不必等一份完美的模板才開始用。核心骨架有了——問題陳述、解法、編號使用者故事——剩下的段落是加分項。

先把流程跑起來：訪談完，在**同一個視窗裡**接著呼叫 to-PRD，別關掉重開，關了就沒有 context 了。

共識變成檔案存住，這一步做到，整條大任務的路才算真的開始。
