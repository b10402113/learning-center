# 一場真實的 grill，把 taste 釘進 PRD

## Learning goal

能透過 analytics dashboard 的完整 walked run，說出 grill 怎麼一題一題把 scope 與領域細節（如 sales≠enrollments）釘下來，以及這些 taste 怎麼被 to-PRD 固化進 PRD。

## Lesson

一個課程平台的老師想看看自己的課賣得怎樣。他打開後台，看得見課程頁面，卻看不到有多少人報名、收了多少錢、學生有沒有把課上完、又是在哪一課流失的。報名、測驗、觀看紀錄這些數字資料庫裡早就有，缺的只是把它們算出來、擺到老師面前的那個介面。這個功能就是後來的 instructor analytics dashboard，老師端分析儀表板。

「分析儀表板」這個名字底下藏著一大片決定空間。要放哪些數字，時間範圍拉多長，圖表長什麼樣，再加上誰有權限進得來。任何一個決定錯了，做出來的東西就不是老師要的。所以流程先從 grill 開始，一題一題把決定問出來，直接讓 agent 動手是後面的事。

先說 grill 是怎麼運作的。grill 讓 agent 扮演提問者，一次只問一個問題，每個問題附一個它自己準備的建議答案，由人拍板。agent 沿著設計樹往下走，把相關的決定一個一個解掉。設計樹就是這個功能的決定分支，一題一題往下長。它問得越緊，人被迫做的決定越多，等樹走完，這個功能長什麼樣也已經講清楚了。這裡直接看它在一場真實功能上是怎麼跑的。

grill 的開頭通常平淡。agent 先確認問題本身，老師現在看不到什麼、想看到什麼，接著第一個 scope 決定就來了。儀表板要一次顯示全部課程的總覽，還是讓老師一門一門切換？答案是跨課程總覽。老師想知道自己的整體業績，先看總盤子，再往下拆到單一課程。

這題值得停一下，因為它展示了 grill 的對抗性質。agent 給的建議答案，人未必接受。人拍板之後，agent 就順著這個答案往下一題走，不會硬要說服。對抗式指的是 agent 把每個決定都拿出來，逼你站穩立場。你站得穩，決定才記得牢；站不穩，趁現在改。這裡的理由是，老師的第一個問題永遠是「我整體賣得如何」，單課程的畫面要等第二個問題才出現。

接下來是入口的問題。儀表板放哪裡，併進現有的 instructor 頁面，還是開一條新的 analytics route？答案是開新 route。route 是 URL 和畫面的對應關係，後台頁面已經有它自己的職責，把圖表塞進去只會讓那頁變長變亂。新 route 帶來新的 URL、新的畫面，跟原本的後台互不干擾。

權限也要問。誰看得到這個儀表板？老師當然要，平台的管理員也要。管理員管的是整個平台的營收，不能只看自己名下的課。所以除了 instructor 的 analytics route，另外開一條 admin 專用 route，內容相同，入口不同。

問到一半，scope 開始收斂。儀表板最初的構想裡有課程完成率、測驗通過率、學生地理分布這類數字。它們都真實，也都有人想看，但人把它們砍掉了。測驗通過率要拉一整組查詢和圖表，地理分布又是一套，兩者都不像營收那樣直接告訴老師下一步該做什麼。砍掉它們連帶省掉各自的一組查詢、測試和空狀態，後面每一階段都少背一份包袱。拉回來，儀表板只留營收加評分，quiz 和 geo 整個拿掉。評分留下來，是因為營收講的是錢，評分講的是口碑，老師判斷課賣得好不好，兩個數字合起來才夠。這是一道純粹的取捨判斷，agent 無從替你決定。

有一題問的是表格欄位，答案裡藏著整場 grill 最重要的領域細節。表格要列出 list price、revenue、sales、enrollments、average rating 和評分數量。sales 和 enrollments 是兩筆不同的資料。一個機構幫整個團隊買一門課，這算一筆 sales，卻可能生出十個 enrollments，因為十個人分到了座位。把兩欄合併，營收數字看起來對，實際報名人數卻消失了。一份好的規格和一份模糊計畫的差別，常常就落在這種地方。

這個細節值得單獨拎出來講，因為它正是好 spec 和模糊計畫的分界。假設一門課一個月賣出一百筆 sales，卻因為機構團購產生三百個 enrollments。規格若只寫「顯示報名人數」，實作的 agent 多半會拿 enrollments 去填那個格子，老師看到三百，以為賣了三百筆，實際成交只有一百筆。定價、促銷、下一門課做不做，判斷全部建立在這個錯的數字上。領域細節不會報錯，它只會沉默地誤導。agent 不會知道你的生意裡有團購這件事，你不寫進規格，它就無從替你防錯。模糊計畫把欄位列出來就停手，好 spec 還多寫一層欄位背後的生意規則。

時間範圍接著登場。儀表板支援 7 天、30 天、12 個月、全部四種範圍，切換器放在畫面上，選中的範圍存成 URL parameter。存進 URL 的理由有兩個。老師把頁面分享給同事，或自己重新整理，看到的範圍要保持一致，不用重新點一次。瀏覽器的往前往後跳時，範圍也跟著 URL 走，畫面不會突然跳回預設值。預設值訂為 30 天，剛好夠看出一段趨勢，又不會被每天的小波動蓋過，七天太短看不出走勢，十二個月對眼前的決定又太遠。

再來是圖表怎麼畫。上面放一條總合的 line chart，顯示整體營收隨時間的走勢，下面擺一張可以排序的 per-course table，按課程列出前面那幾欄。線圖看整體，表格看個別課程，兩種視角互補，表格能排序，老師要找出賣得最好和最差的課就不用自己掃。繪圖用 recharts 直接畫，不套 shadcn 的 wrapper。recharts 是 React 的繪圖函式庫，shadcn 在它外面再包一層元件，直接用裸的 recharts 少一層抽象。這個選擇短期看不出差別，等三個月後有人要改圖表樣式，少一層包裝就少查一份文件，要追文件時只追一份，這也是 taste。

畫面邊角還有一串小決定。頂端放一排 KPI，總營收、總報名人數、平均評分三個數字，一進頁面先掃完總盤子。側邊欄加一個 nav item 讓老師點得進來，nav item 是側邊欄的導覽入口，沒有它，老師就算知道網址也得自己手打。篩掉未發布的課程，一張還在編輯的課，報名人數不是零就是半途的數字，算進總營收只會讓老師誤判。最後是空狀態，完全沒有資料時，畫面只顯示一句「no revenue data yet」，不替每張圖各自準備占位說明，一個統一的訊息比一片空殼清楚。

到這裡 scope 已經釘完。把整串決定攤開，一張清單長這樣

- 跨課程總覽，不做單課程頁
- 新增 analytics route，不併入 instructor 頁面
- admin 也要看得見，另開一條專用 route
- 只做營收加評分，砍掉 quiz 和 geo
- 時間範圍 7 天／30 天／12 個月／全部，預設 30 天，存成 URL parameter
- 單一條總合 line chart，加一張可排序的 per-course table
- 表格欄位 list price、revenue、sales、enrollments、average rating 加評分數量
- 用 bare recharts，不套 shadcn wrapper
- 頂端 KPI strip 顯示總營收、總報名人數、平均評分
- 側邊欄加 nav item
- 只顯示已發布課程
- 空狀態只有一句「no revenue data yet」

把這張清單讀一遍，產品形狀就浮出來了。老師從側邊欄點進分析儀表板，先看到三十天的 KPI，三個數字回答「整體如何」。下面線圖看走勢，再往下表格找賣得差的那門課，點進去看它的評分和報名。整個畫面只有一種資料視角，營收加評分，沒有一格是裝飾。這就是 grill 釘完 scope 之後的效果，規格還沒寫，畫面已經可以先在腦裡預覽。

這串決定有一個共同特徵，每一項都是人選的。agent 能做的，是把問題挖出來、把選項擺開，順便講講自己的建議，但「要做哪一個」是人的判斷。這就是 [[learn/ai-coding-for-real-engineer/elements/taste-in-spec|規格裡的 taste (Taste in the Spec)]]，對產品價值的取捨，它不來自任何演算法。

grill 走到尾聲有個明顯信號。問題開始變得又快又明顯，agent 問的每件事你幾乎都回答過類似的，答案不用想。問到後來，它確認的多半是已經定案的細節，瑣碎而不再意外。意思是共享理解快到了，agent 的提問不再打開新分支，只是在確認已經講定的事。反過來說，如果問題還在一題比一題意外，設計樹裡還有沒走完的分支，先別急著收工。

收工之後換 to-PRD 上場。to-PRD 是一個 skill，skill 是一份可複用的指令文件，掛在 agent 上，需要時才把內容載入。它讀取整段對話的 context，把討論整理成一份 PRD 存到本地。context window 是模型的即時工作記憶，一整場對話的內容都在裡面，tokens 是模型計數文字量的單位，那次跑的訪談全部加起來約 52.2k tokens。這一步不需要你重新講述任何東西，決定都在對話裡，to-PRD 只是把它們固化下來。

PRD 產出的文件由八個部分組成

- problem statement，從使用者視角講清楚要解決什麼問題
- solution，從使用者視角描述解法長什麼樣
- 一串編號的 user stories，格式是「as an instructor I want X so that Y」，一條一條可驗收。實際的例子像是，老師想要看到過去 30 天的總營收，好知道課程表現如何
- implementation decisions，實作層的選擇。那次跑法是新增 analytics service module、instructor route、admin 的 instructor route、共用元件
- technical decisions，技術與架構的取捨
- testing decisions，要測什麼、怎麼測
- out-of-scope list，明確寫下這次不做的清單
- further notes，剩下的補充

這就是 [[learn/ai-coding-for-real-engineer/elements/prd-structure|PRD 結構 (PRD Structure)]]。核心骨架是前三項，problem statement、solution、user stories，把做什麼、為什麼、做完了算不算數講死。後五項把工程選擇和 scope 界線一併寫進去，讓這份文件可以獨立存活。implementation decisions 那一格尤其該寫實，實作細節可以而且應該由人直接指定，chart 用哪個函式庫、route 開在哪裡，寫死比讓 agent 自由發揮穩。

grill 的對話本身沒有保留的必要。對話結束，context 清掉，裡面講過的一切就沒了，留在磁碟上、能跨場存活下來的只有這份 PRD。這個設計對模型的 stateless 特性是對症的，每一場新對話都是白紙一張，昨天的討論它一概不知道。PRD 可以交到一個全新的 session 手上，session 是一場全新的 agent 對話，那個 session 沒參加過任何討論，光靠文件就知道要做什麼、不做什麼、標準在哪。destination 這個名字就是這個意思，它是終點，人走開以後，它代表你繼續存在。

還有一個並行的技巧可以記。grill 只是對話，成本很低，真正的開銷在人的注意力上。每個 grill session 各自佔一個 context window，互相不干擾，訪談一結束，那場對話就能交出去變成下一階段的輸入。熟練之後可以同時開兩三個 grill session，各自 interview 不同的功能，另一邊再開一個視窗跑 planning。人一次應付好幾場訪談的決定，agent 同時把前一場訪談的產出變成計畫或程式碼。這個技巧的前提是決定權在你手上，你回答得過來，多開幾場就是多幾份活同時在跑；你回答不過來，再多視窗也只是排隊。這跟 plan while the AI ships 是同一個吞吐量思路，一行一行寫程式的是 agent，一排一排做決定的還是人。

規格裡的 taste 是靠每一題親自拍板進來的，尤其 sales 和 enrollments 這種領域細節，一題一題釘下去，文件才接得住你走開之後的意圖。整場 grill 到 to-PRD 走完，人做的全部事情，就是回答那些問題。
