# 為什麼這樣排

<LearningGoal>
解釋流程順序的道理：前面先把模糊的需求釘成可執行的規格，實作階段才能整段放手（AFK），人走開時用同一段時間規劃下一批工作，最後 review 守住品質。
</LearningGoal>

## Lesson

順序本身在降低風險：**前面的階段把「模糊」變成「決定」，後面的階段才能放手執行**，而越晚發現決策錯，重做的代價越大。前半段的三站都在用便宜的手段處理最貴的不確定性——grill 一題一題把模糊需求問到具體（需求最模糊、判斷最貴，所以排第一）；research 補齊我們不知道的未知（LLM 不是可靠的資料庫，這類東西 agent 也不會知道，得人先查）；prototype 用最小代碼沖掉設計上的未知數，避免寫完整個功能才發現方向錯。中間兩站把決定凍結下來：PRD/plan 寫成「做什麼」與「怎麼做」兩份文件——因為 LLM 無狀態，每次新 session 都是全新的，文件是唯一可靠傳遞「商量好的結論」的媒介；issues 再把文件切成邊界明確、可整段接手的任務。

後段就是「放手 + 守品質」。implement 之所以能整段 AFK，正是因為前面已經把所有該決定的都決定了，沒有模糊需求等著人現場解釋——人走開去規劃下一批工作（plan while the AI ships），這是吞吐量的真正來源：一個人跟 agent 平行、同時做兩件事。review 最後守住品質：agent 再強也會出錯，人的閘門不可省；而審查把 codebase 維持在健康狀態，**agent 在好的 codebase 裡表現更好**，尾巴反過來餵養開頭，形成正循環。對照組是你直接叫 agent implement：需求模糊 → agent 亂猜 → 你得逐行盯 → 既不能 AFK 又浪費時間。所以口訣是：前面越用力，後面越能放手。
