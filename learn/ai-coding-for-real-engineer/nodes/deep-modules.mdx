# 讓 codebase 對 agent 友善

## Learning goal

用 Ousterhout 的 deep modules 判斷 agent 好不好用你的 codebase，並用 architecture skill 找摩擦、提出 RFC。

## Steps

1. [[learn/ai-coding-for-real-engineer/nodes/deep-modules/deep-modules-concept|什麼是 deep modules，為什麼 agent 需要它們]] — 用薄介面＋厚實作的標準判斷 codebase 對 agent 友不友善，並看懂壞 codebase 的徵兆
2. [[learn/ai-coding-for-real-engineer/nodes/deep-modules/architecture-friction-signals|用 improve-codebase-architecture skill 找摩擦]] — 認識 skill 的探索流程與四個摩擦訊號，學會預測哪些 module 會被標為候選（after step 1）
3. [[learn/ai-coding-for-real-engineer/nodes/deep-modules/architecture-skill-run|實跑一輪：quiz subsystem 變成 deep module]] — 從實跑讀懂三種介面設計的選擇與混和，以及 RFC issue 的 before/after（after step 2）

## Lesson

讓 codebase 對 agent 友善，不是靠把文件寫厚，而是靠把 module 做深。Ousterhout 的 deep modules 給了你一把尺：好的 module 只有一個薄、少變的介面，底下藏著一大片實作——agent 讀介面就能立刻懂這塊在做什麼，不必沿著 import/export 鏈一個檔一個檔地追。反過來，幾十個小 module 不只讓 agent 在找功能上燒掉 context，還會產生脆弱、被變更耦合的測試。這節課先用這把尺判斷 codebase 的友善度，再教你用 improve-codebase-architecture skill 自動找摩擦——它探索 codebase、列出候選、平行生出分歧的介面設計、最後收斂成一份可轉成 Kanban 的 refactor RFC。看懂一次完整實跑（quiz subsystem 從混 raw SQL 與 Drizzle 的 service 變成 factory 形式的 deep module）後，你就知道介面設計是看多選項養成的技能，而「要不要加深 module」這種判斷得由你帶著 deep modules 的語言去 prompt agent，不能指望它自己發現。
