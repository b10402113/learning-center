# 先做 prototype

## Learning goal

對不確定的設計先做 throwaway prototype 沖出 unknown unknowns，把 taste 先灌進去，再讓 AFK loop 接手。

## Steps

1. [[learn/ai-coding-for-real-engineer/nodes/prototyping/prototype-vs-plan|為什麼要先做 prototype：把規劃變成可以玩的東西]] — prototype 補上文字規劃的哪個缺口，unknown unknowns 為何要在 AFK 之前沖掉
2. [[learn/ai-coding-for-real-engineer/nodes/prototyping/when-to-prototype|什麼時候該 prototype、什麼時候不用]] — 用「有沒有先例、未知多不多」判斷該不該先做 prototype（after step 1）
3. [[learn/ai-coding-for-real-engineer/nodes/prototyping/two-prototype-branches|prototype 的兩條分支：邏輯與 UI]] — 認得 logic branch 與 UI branch 各自查什麼、何時用（after step 1）
4. [[learn/ai-coding-for-real-engineer/nodes/prototyping/run-a-prototype|用 do-work 跑一個 prototype]] — 寫出一個指向 research、只給開發者看、產出可重用 asset 的 prototype 指令（after steps 2–3）
5. [[learn/ai-coding-for-real-engineer/nodes/prototyping/keep-prototype-production-ready|prototype 也要能直接上線：TDD、可重用元件與實測]] — 在 prototype 裡維持 TDD 與標準，接上服務實測後才交給 AFK（after step 4）

## Lesson

研究做完了，你手上有一份寫得很漂亮的 research.md：需求、比較過的四個服務、推薦哪一個、打算怎麼接。文件讀起來毫無破綻，但真正的未知還在原地 —— 這個服務接上你的登入流程會不會卡？那個資料模型遇到「有人中途關掉分頁」會怎樣？這些問題，用文字推理只會得到「應該可以」，而「應該」正是之後 AFK loop 停擺的種子。

這個節點要補的，就是這個缺口。在把工作丟進 Kanban 與 Ralph 迴圈之前，先花一小段時間做一個 prototype：一個故意做壞、之後就丟掉、只給開發者看的可玩版本。它的價值不在程式碼本身，而在把抽象文件推到真實世界裡撞一次，讓那些連你都問不出來的問題自己冒出來。原型還有一個更長遠的好處：它讓你在實作之前就把品味灌進去，而品味正是後面那條無人值守的 pipeline 最缺的東西。

四步走完，你會知道 prototype 為什麼是 human-in-the-loop 的工作、什麼時候該做、什麼時候該跳過，以及兩個現成的分支（邏輯與 UI）各自怎麼用。最後你會看到一個完整的實例：把 presence 研究做成一個 dev-only 的 throwaway route，接上 Ably、開兩個分頁，看著線上人數即時跳動——那一刻，所有 unknown unknowns 都被清掉了，剩下的交給 AFK loop 就只是照抄。
