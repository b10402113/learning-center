# 強制品質的迴圈

## Learning goal

寫出 do-work skill（plan→implement→validate→commit），跑它交付一個功能，再用 pre-commit hooks 讓 typecheck/test 每次 commit 前強制執行。

## Steps

1. [[learn/ai-coding-for-real-engineer/nodes/feedback-loops/feedback-loop-over-steering|迴圈強制品質，steering 只是提高機率]] — 理解 feedback loop 為何是確定性的品質保障，並認出 typecheck / test 兩個迴圈
2. [[learn/ai-coding-for-real-engineer/nodes/feedback-loops/do-work-skill|寫出 do-work skill]] — 在專案內寫出 ~35 行、light-steering 的 do-work skill（after step 1）
3. [[learn/ai-coding-for-real-engineer/nodes/feedback-loops/running-do-work|跑 do-work skill 交付一個功能]] — 用 do phase one + PRD 呼叫它，並設最小權限 allow-list（after step 2）
4. [[learn/ai-coding-for-real-engineer/nodes/feedback-loops/pre-commit-hooks|用 pre-commit hooks 強制每次 commit 跑迴圈]] — 讓 typecheck/test 在每次 commit 前確定性執行（after step 2）

## Lesson

steering 只能提高品質發生的機率；feedback loop 才確定性地強制品質。agent 產出程式碼 → 迴圈給回饋 → agent 迭代到品質足夠——這是把頂尖工程師「不信任直覺、靠迴圈」的做法套到 agent 上。TypeScript 的強型別（compile-time 抓錯）與自動化測試（真的把程式跑起來）是兩個核心迴圈，本 repo 已經有 `pnpm typecheck` 與 `pnpm run test` 可用。

把迴圈寫進 per-repo 的 do-work skill（plan → implement → validate → commit），每次變更就呼叫它，是讓 LLM 走進可迭代迴圈最乾淨的方式；skill 要短、要 project-local、只點名迴圈不要過度指定。接著在實際 PRD 上跑一次，觀察 agent 是否照做，並用最小權限 allow-list 只放行 feedback loop 需要的指令。最後用 pre-commit hooks 把迴圈變成「每次 commit 前一定執行」——對人類是摩擦的等待時間，對 agent 完全免費，於是這個迴圈從討厭變成確定性的守門員。
