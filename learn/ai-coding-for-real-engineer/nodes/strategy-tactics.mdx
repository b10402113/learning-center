# 什麼留著、什麼放手

## Learning goal

用 tactical vs strategic、HITL vs AFK、SDLC 崩壞等判斷，決定哪些事該自己留著、哪些放手給 agent。

## Steps

1. [[learn/ai-coding-for-real-engineer/nodes/strategy-tactics/hitl-afk-split|HITL 與 AFK：哪些事留人、哪些放手]] — 用「plan/review 留人、execute 放手」的規則把任務切成 HITL 與 AFK 兩類
2. [[learn/ai-coding-for-real-engineer/nodes/strategy-tactics/tactical-vs-strategic|Tactical 會被吃掉，Strategic 存活]] — 說出 tactical 約 90–95% 會被 AI 吃掉、strategic 才是人留著的領域（after step 1）
3. [[learn/ai-coding-for-real-engineer/nodes/strategy-tactics/sdlc-collapse|SDLC 崩壞：implementation 趨近零]] — 說出 SDLC 為何變成 planning-heavy 與 QA-heavy、估時失準（after step 2）
4. [[learn/ai-coding-for-real-engineer/nodes/strategy-tactics/steer-with-review|Steering 放在 review，不放 plan/CLAUDE.md/實作]] — 用 cheap implementation + expensive review 把最佳實踐編碼進 skill 與 review agent（after steps 1, 3）
5. [[learn/ai-coding-for-real-engineer/nodes/strategy-tactics/handoff-artifacts|每次交接留 handoff artifact]] — 用 grill→PRD→issues 一次做完、比較 handoff 與 fork/compact、別優化成本（after steps 3–4）

## Lesson

這個 node 站在「agent 能做的愈來愈多」的路口，問一個策略問題：到底什麼該留著自己來，什麼該放手？答案不是「全部放手」，而是兩套判斷切出邊界。

第一套是 HITL vs AFK：planning 與 review 留人、implementation 放手——把「做決定」與「驗收」留給人，把「執行」交給 agent，cloud sandbox 讓放手更安全。第二套是 tactical vs strategic：狹窄短期的 tactical 程式設計約九成五會被 AI 吃掉，長期設計與 velocity 的 strategic 工作才是人該留著的領域，也是職涯該押注的 skill。這兩套切完，自然推導出 SDLC 崩壞：implementation 成本趨近零，工作重心往 planning 與 QA 兩端移動，估時失準。

於是剩下的問題只剩「人在哪裡下功夫」。答案是 review——把 best practices 編碼進 skill 與 automated review agent，用便宜的 implementation 換昂貴的 review；以及每次交接都留下 handoff artifact（grill→PRD→issues 一次做完），讓下一個 session 或 agent 從文件接手，而不是靠記憶或 fork。看懂這兩套判斷，你就不再需要替 agent 逐行把關，只需要決定該盯哪裡。
