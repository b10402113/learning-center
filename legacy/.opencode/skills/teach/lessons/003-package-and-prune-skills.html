把流程做成 Skill，並修掉沒用的 Steering

Node: steering-across-sessions · Step 3/4

學習目標

能把穩定流程封裝成可攜式 skill，分辨 model-invoked 與 user-invoked 的差別，並用三個測試修剪 steering 檔案中的重複、沉積物與 no-op。

從 Doc + Pointer 到可攜式 Skill

上一課我們學會用 doc + pointer 降低 context load。但 pointer 有一個限制：它綁在 repo 的目錄結構裡。換一個專案、換一台機器、換一個 harness，原本的文件位置就未必還成立。

類比：agents.md 的 push 像每天把整本操作手冊背在身上；doc + pointer 像帶著寫有書架位置的紙條；portable skill 則像把那本手冊連同目錄、附件與索引裝進一個可攜式工具箱。工具箱不必每天打開，但需要時可以整箱搬走。

Skill 的基本形狀

一個 skill 通常是自包含的資料夾，核心檔案叫 skill.md。裡面至少有兩層：

my-deploy-skill/ ├── skill.md ← 名稱、description、完整流程 ├── checklist.md ← 附帶的檢查表 └── examples/ ← 範例與參考資料

名稱與 description 像更正式的 context pointer——先告訴 parent context 這個技能處理什麼類型的任務。等到任務真的符合條件，才載入完整的 skill.md。

由誰觸發？Model-Invoked vs User-Invoked

Model-Invoked User-Invoked
觸發方式 模型根據名稱與 description 自動判斷 使用者明確呼叫
Context load 較高（名稱與 description 每輪都出現） 幾乎為零（沒被叫到就不出現）
遺漏風險 低（模型自動發現） 高（使用者必須記得）
適合情境 常見、容易辨認、錯過代價高 低頻、意圖明確、使用者本來就知道
這不是「哪個比較自動化」，而是你把判斷責任交給誰。高風險且高頻的技能偏向 model-invoked；低頻且意圖明確的技能偏向 user-invoked。

放哪裡？User-Level vs Project-Level

範圍 放置位置 適合內容 分享方式
User-level .claude/skills/ 或 .agents/skills/ 個人偏好、跨專案快捷流程 跟著同一台機器上的使用者走
Project-level repo 內並提交 團隊共同程序、專案特有流程 隨 repo 分享給所有協作者

分界點不是資料夾名稱，而是規則的所有者，以及缺少它時誰會受影響。把個人偏好放在 project-level，團隊會誤以為那是專案要求；把團隊關鍵流程放在 user-level，流程就只在某一個人的環境有效。

修剪 Steering：三個測試

Skill 封裝完成後，原本的 steering 檔案仍可能留著舊副本。更常見的情況是它只增不減。對每一條規則做三個測試：

測試一：Single Source of Truth

這份資訊的權威版本在哪裡？

答案可能是程式碼、README、專門文件、skill 或另一份受控設定。若完整規則已經存在，就不要在 steering 檔案再抄一份。複製品表面上讓代理更容易看到，實際上卻增加同步風險。

測試二：Sediment（沉積物）

這條規則提到的目錄、工具、命令與流程是否仍然存在？

曾經在一次事故中有用，不代表它現在仍值得每次載入。專案可能從一個測試框架換成另一個，部署平台可能已經改變，某個手動步驟可能早已由 CI 自動完成。

測試三：No-Op（無作用）

暫時移除它，再用相同任務重跑，代理的表現是否真的變差？

如果行為沒有可觀察的變化，這條指示就是 no-op。它可能只是把常識說了一遍，也可能是代理本來就能從程式碼和工具結果推導出來。合理的句子不等於有效的句子。

三種處置結果

三個測試的目的不是把 steering 變成空檔案，而是把不同價值的內容重新分流：

✕
刪除 沒有現行價值，或測試證明是 no-op 的內容。
→
改成 Pointer 仍然重要，但只在特定任務使用的詳細程序。移到文件，留下短而準確的 pointer。
⧉
改成 Skill 需要在不同 repo 或 harness 重用的程序。封裝成 portable skill。

只有幾乎每次任務都適用，而且漏掉會造成高風險的短規則，才適合留在固定推入的位置。

完整的整理循環

整理現有專案時，不要一開始就重寫全部文件。按順序走這五步：

1
盤點 為每一條 steering 內容記下：它在保護什麼行為？權威來源在哪裡？它適用於哪些任務？刪掉後預期會有什麼變化？
2
留下全域規則 保留真正全域且短小的內容，例如不要提交秘密、修改前先讀相鄰程式碼、完成後執行現有驗證。
3
移出條件式流程 只在特定變更才需要的長流程，移到文件或 skill。
4
驗證 Pointer 檢查指向的檔案真的存在，名稱清楚，觸發條件也能讓使用者和模型辨認。
5
實驗可疑內容 對重複、過時和可能是 no-op 的句子做測試，不要只靠直覺保留。

也要審核自動產生的檔案

claude init 這類流程會掃描 repo，讓代理自行寫出一份可能上百行的 CLAUDE.md。這種檔案應視為草稿，不是完成品。用刪除、pointer、skill 三種選項逐項瘦身。

自我檢測

Q1. 你的 agents.md 裡有一條規則：「使用 Jest 時要用 .test.ts 後綴」。你的專案三年前從 Migrate 切到 Jest，但這條規則還留著。這是什麼問題？

  • No-op
  • Sediment（沉積物）
  • Single source of truth 重複
  • 應該改成 skill

Q2. 你有一套部署流程，不同專案都需要用。你應該？

  • 貼進每個專案的 agents.md
  • 放在 docs/ 裡用 pointer 指向
  • 封裝成 project-level 的 portable skill
  • 寫在 README 裡

Q3. 以下哪種 skill 最適合用 user-invoked？

  • 每次 schema 變更都要跑的 migration 流程
  • 漏掉就會資料不一致的 seed 同步
  • 把目前工作交接給下一個代理
  • 每次 commit 前的 type-check
