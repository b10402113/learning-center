# Skill 跟 MCP 到底差在哪?用「餐廳廚房」講給你聽

你可能以為,Skill 跟 MCP 都是「讓 AI 變強的外掛」,裝越多、AI 越厲害,反正都是「多一個功能」。

但實際上,這兩個東西解決的是完全不同的問題——這就像一間餐廳廚房裡,「送貨通道」跟「主廚的料理筆記本」的差別。送貨通道讓廚房**拿得到**食材,料理筆記本教廚師**怎麼做**這道菜。少了送貨通道,廚房巧婦難為無米之炊;少了筆記本,就算食材再新鮮,每個廚師炒出來的味道還是會不一樣。

這篇文章就是要把這兩個角色講清楚,而且全程用「廚房」這個畫面貫穿到底,保證你看完不會再搞混。

---

## 一、先建立心智模型:送貨通道 vs 料理筆記本

在動手寫任何設定檔之前,你腦中要先有這張圖:

| 模式      | 生活比喻                                       | 實際在做的事                                                                        | 適用情境                                                                                   |
| --------- | ---------------------------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **MCP**   | 廚房後門的**送貨通道**(連接超市、農場、供應商) | 讓廚房**接觸到外部世界**——拿到新鮮食材、即時的市場報價、冷藏庫裡現有的存貨          | 廚房本身沒有這個東西,得跟外面「要」——例如你的行事曆、資料庫、Slack 訊息、GitHub 上的程式碼 |
| **Skill** | 主廚手寫、放在流理台旁的**料理筆記本**         | 教新來的廚師**這道菜該怎麼做**——先炒什麼、後下什麼、火候多大,確保每次做出來味道一致 | 你希望 AI 每次處理同一類任務時,都用**你要的固定方法**去做,不用每次重新解釋一遍             |

**送貨通道解決「有沒有食材」的問題,料理筆記本解決「做得對不對」的問題——這是兩個完全不同層次的問題,所以不能互相取代。**

---

## 二、拆解 Skill:一本「翻開才看得到內容」的筆記本

先講 Skill。它本質上就是一個資料夾,裡面有一份叫 `SKILL.md` 的檔案,裡面寫著這道「菜」該怎麼做的步驟。

但這本筆記本有個很聰明的設計,叫**漸進式揭露**——白話講就是:**廚師平常不會把整本筆記本攤開來看,而是先看目錄,真的要做那道菜的時候,才翻到那一頁看細節;如果那道菜還需要用到某台特殊機器,機器的使用說明書也是要用到的時候才會抽出來看,不會平常就攤在桌上占位置。**

```
廚師接到一張點餐單(你的請求)
  ↓ 先掃過筆記本目錄(只有菜名 + 一句話說明)
發現「這張單子剛好對得上某道菜」
  ↓ 翻開那一頁,讀完整份做法
照做法開始備料、下鍋
  ↓ 如果做法裡提到「攪拌機用法看附錄」
才把附錄(額外的文件或程式腳本)抽出來讀
```

為什麼要設計成這樣,而不是把整本筆記本都攤開?**因為如果每次點餐,廚師都要把整本菜譜從頭讀到尾,不管有沒有用到,不但浪費時間,廚房裡的桌面(也就是 AI 的「注意力」)也會被一堆無關的紙張占滿,反而找不到真正要用的那一頁。**

Skill 的幾個關鍵特性,一樣用白話講:

| 項目                    | 白話說明它是什麼                                                       | 能不能公開分享給別人                           |
| ----------------------- | ---------------------------------------------------------------------- | ---------------------------------------------- |
| `SKILL.md` 檔案         | 筆記本的「這一頁」——寫著步驟、原則、注意事項                           | 可以,而且鼓勵你打包分享給團隊,大家用同一套做法 |
| 目錄裡的名稱+一句話說明 | 貼在筆記本封面的標籤,平常就看得到,幫廚師快速判斷「這道菜歸不歸我管」   | 一直都在,不用特別公開                          |
| 附錄文件、腳本          | 夾在那一頁裡的補充資料,或是可以直接跑的固定流程(例如自動排版)          | 只有真的翻到那頁才會被讀,平常不會拿出來        |
| 跨場景可攜帶            | 同一本筆記本,可以帶去 Claude.ai、Claude Code、API,不用每個廚房重寫一份 | —                                              |

**Skill 是知識,不是通道——它只教廚師「怎麼做」,不負責幫廚師「弄到」食材。**

## 三、拆解 MCP:讓廚房伸手碰到外面世界的通道

MCP(Model Context Protocol)則完全是另一回事。它是一套**開放的連接標準**,作用是把 AI 這間廚房,跟外面那些原本碰不到的系統——資料庫、你的信箱、公司的內部工具——接上線。

用畫面來想:**廚房本身不會自己種菜,MCP 就是那條接到外面農場、超市、瓦斯公司的管線。管線接上去之後,廚房才「拿得到」外面真實、即時的東西,而不是憑空猜「冰箱裡現在應該還有雞蛋吧」。**

```
你說「幫我看一下今天的行事曆」
  ↓ 廚房沒有行事曆這種食材,得靠管線去外面拿
MCP 通道連上「行事曆供應商」的後門
  ↓ supplier 把今天的資料整批送進來
廚房(AI)才真的「看得到」你今天有哪些會議
  ↓ 有了真食材,才能開始烹調(回答你的問題)
```

為什麼一定要靠這條管線,不能讓 AI 自己憑印象回答?**因為 AI 本身沒有你行事曆的即時內容,如果它憑猜的回答「你今天應該沒事」,結果你其實有一場重要會議,這種假消息比沒回答還糟糕。**

MCP 的幾個關鍵特性:

| 項目                       | 白話說明它是什麼                                                | 能不能公開分享給別人                               |
| -------------------------- | --------------------------------------------------------------- | -------------------------------------------------- |
| MCP 伺服器                 | 那條真正接到外部系統的管線本體,是一個持續在跑的程式             | 可以,很多公司會把自己的系統包成 MCP 伺服器讓別人接 |
| 工具定義(tool definitions) | 貼在管線口的標示牌,告訴廚房「這條管線可以送雞蛋、也可以送牛奶」 | 通常一直掛在那裡,讓廚房隨時知道能要什麼            |
| 開放標準                   | 這條管線的接頭規格是公開的,不是只有某一間廚房能用               | 天生就是公開設計,方便不同廚房都能接上              |

**MCP 是管線,不是食譜——它只負責把外面的東西送進來,不會教廚房這些東西該怎麼煮。**

## 四、兩個放在一起,才會做出一道完整的菜

單靠送貨通道,廚房拿得到食材,但可能每個廚師炒出來味道天差地遠;單靠料理筆記本,寫得再詳細,沒有食材照樣做不出菜。

```
MCP 通道送進「今天業績數據」
        ↓
Skill 筆記本翻到「業績報告怎麼寫」那一頁
        ↓
廚房照著固定格式,把新鮮送來的數據
做成一份你熟悉、風格一致的報告
```

**送貨通道決定廚房「碰得到什麼」,料理筆記本決定廚房「碰到之後怎麼處理」——真正厲害的廚房,兩樣都要有,而且分工要清楚。**

## 五、判斷該用哪一個:五步驟检查法

| 步驟 | 動作                                                       | 白話解釋為什麼要這樣做                                                                                                                |
| ---- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 先問:「AI 現在缺的是資料,還是缺的是做法?」                 | 因為這是最根本的分岔路——缺食材找 MCP,缺食譜找 Skill,問錯問題後面全部白搭                                                              |
| 2    | 如果缺的是「外面世界的即時東西」(資料庫、行事曆、票務系統) | 表示廚房裡真的沒有這個食材,得靠管線去外面拿,這是 MCP 的工作                                                                           |
| 3    | 如果缺的是「固定要照著做的流程」(公司格式、SOP、命名規則)  | 表示食材可能都在,只是每次做出來的「味道」不一致,這時該寫一份 Skill 讓大家照著做                                                       |
| 4    | 檢查兩者是不是同時缺                                       | 因為很多任務其實兩個都要——先靠 MCP 拿到真資料,再靠 Skill 把資料處理成你要的樣子                                                       |
| 5    | 寫完之後,自己重新讀一遍                                    | 因為不管是 Skill 裡的腳本,還是 MCP 串接的設定,都是「別人(或 AI)幫你組出來的東西」,你不看懂,出錯了也不知道問題出在管線接錯還是食譜寫錯 |

## 六、給用 AI 寫程式的人:為什麼不能全部丟給 AI 就不管了

現在很多人是讓 AI 代理(agentic 工作流)自己去接 MCP、自己去寫 Skill,聽起來很方便,一鍵搞定。但這裡有個很現實的問題:

**送貨通道接錯了,廚房可能誤把「別人家的食材」搬進自己的冰箱;料理筆記本寫錯了,廚房會用錯誤的方法,把好好的食材做壞。而這兩種錯誤,AI 自己是不會主動舉手說「欸我可能接錯了」的。**

所以就算是 AI 幫你生成的 MCP 設定或 Skill 內容,你還是得看得懂它到底：

- 這條「管線」接的是不是你以為的那個系統(會不會不小心把公司內部資料送到不該送的地方)
- 這本「筆記本」寫的步驟,順序跟邏輯是不是真的符合你要的結果,而不是「看起來很像對」

**AI 幫你把菜煮出來很快,但端上桌之前,你自己得先嚐一口——這不是不信任 AI,是廚房出餐前本來就該有的最後一道把關。**

---

## 七、收尾:兩道防線,一次記住

**第一道防線是 MCP,像是廚房的送貨通道——先確保拿到的食材是真的、是對的、是即時的,這一步做不好,後面煮什麼都沒意義。**

**第二道防線是 Skill,像是主廚留下的料理筆記本——確保不管誰來煮、煮幾次,做出來的東西都是同一個標準,不會今天鹹明天淡。**

下次再看到「該裝 MCP 還是寫 Skill」這種問題,你只要在心裡問自己一句:**「我現在是缺食材,還是缺食譜?」**——答案通常就出來了。
