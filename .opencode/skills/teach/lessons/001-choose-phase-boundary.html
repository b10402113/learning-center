轉場時怎麼選：五種 Phase Boundary 策略

Node: steering-across-sessions · Step 1/4

學習目標

能在 grilling、實作、QA 等工作階段之間辨認 phase boundary，理解邊界上的五種處理方式，並在轉場時主動做出選擇，而不是讓 auto-compaction 替你決定。

什麼是 Phase Boundary？

你在和 AI 代理合作時，常常不是只做一件事。前半段可能在釐清需求，中段開始讀檔、改檔、跑測試，後半段再進入 QA。這些都可能發生在同一個 session 裡。

這裡的 session，可以先把它想成一塊有限的工作記憶。從對話開啟到現在，所有東西都堆在裡面：你講過的限制、代理讀過的檔案、工具輸出、失敗嘗試、最後採用的方案，還有那些後來其實沒用上的探索痕跡。

所謂 phase boundary，就是你從一個工作階段轉到另一個工作階段的那個點。最常見的例子：

  • 從 grilling 轉進實作
  • 從實作轉進 QA
  • 從一個問題切到另一個獨立問題
  • 從自己繼續做，改成要交給別的代理或別的人
Phase boundary 不是系統保證會提醒你的事件，而是一個需要你主動辨認的決策點。你要問的不是「工具能不能繼續跑」，而是「現在這段脈絡，要怎麼帶去下一段工作」。

五種選擇：不是功能表，而是取捨

站在 phase boundary 上，你通常有五種選擇：

選擇 你做的事 主要好處 主要風險
繼續 留在原 session 往下做 摩擦最低，保留完整主要史料 上下文越來越長，品質慢慢下降
清空 丟掉舊上下文，開全新 session 最乾淨，立刻回到完整空間 容易丟掉實作理由與隱性限制
壓縮 先做 compaction 再開新 session 留住重點，放掉過程噪音 壓縮本質上有損，可能漏細節
交接 做 handoff 文件 能跨代理、跨目錄、跨人搬運脈絡 比壓縮多一步，操作成本較高
派子代理 把獨立工作丟給另一個代理 適合 AFK 工作，主線不必被切碎 邊界不清楚時增加協調成本
類比：Phase boundary 就像搬家。你不會每次換房間都把整間屋子的東西搬過去（繼續），也不會什麼都不帶就走（清空）。你會先整理行李（壓縮），或把東西寄到新地址（交接），或請搬家公司幫忙（派子代理）。

決策樹：五步走完

五種方法不需要一次全部比較。比較好的做法是用一連串問題把範圍慢慢縮小：

Phase Boundary 決策樹

1
現在還能不能安全繼續？ 看上下文還有沒有足夠的聰明區空間，原本的主要史料是否仍然很有價值。
→ 如果是：繼續留在原 session。
2
如果不能安心繼續，舊內容能不能完全丟掉？ 檢查那些只存在於對話裡、卻沒有完全寫進程式碼的東西——某個限制、某個已被否決的方案、某個失敗嘗試。
→ 如果可以全丟：清空上下文。
3
如果不能丟掉，是否需要跨邊界搬運？ 邊界包括另一個代理、另一個目錄、另一個 repo、另一位同事，或未來另一個時間點。
→ 如果需要：交接（handoff）。
4
如果不必跨邊界，任務能不能獨立在背景完成？ 例如自動化 review、固定格式的檢查、界線清楚的研究。
→ 如果可以 AFK：派子代理。
5
前面都不是，就壓縮。 把重要脈絡整理後帶進新 session，然後把下一個 phase 的意圖講清楚。
→ 壓縮（compact）。

為什麼 Auto-Compaction 不能代替你的判斷

Auto-Compaction 的危險

很多 harness 會在上下文接近緩衝區時自動做壓縮。它看起來像很方便的保護網，但 auto-compaction 通常只知道一件事：快滿了。它不知道你現在是在 grilling 的中段、實作的中段，還是剛好完成一個自然收尾點。

這差很多。如果壓縮發生在真正的 phase boundary，摘要可以圍繞一個清楚目標來整理。但如果壓縮發生在階段中間，摘要就得自己猜哪些半成品算重要、哪些限制是關鍵。

實作中途尤其危險。代理可能剛建立出一套一致的命名風格、錯誤處理方式與檔案組織。如果這時 auto-compaction 介入，新 session 只拿到部分整理後的資訊，接下來可能出現：

  • 改用另一套命名方式
  • 忽然換一種錯誤處理習慣
  • 重新走回你已經否決的設計
  • 把未完成的部分誤判成已完成
手動壓縮和 auto-compaction 的真正差別：差別不只是誰按下按鈕，而是有沒有工作意圖。手動壓縮時，你可以先讓當前 phase 收尾，也可以明確說出新 session 的目標。auto-compaction 服務的是容量，不是工作結構。

轉場前的檢查清單

不管最後選哪種方式，轉場前都值得先把下面幾件事想清楚：

  • 現在已經完成了什麼？
  • 還有哪些事情沒有完成？
  • 哪些選擇已經拍板？
  • 哪些選擇仍然開放？
  • 下一個 session 或下一位代理第一件事要做什麼？

這不需要寫成一篇長報告，但它能大幅降低壓縮、交接或清空之後只剩下一團模糊摘要的風險。

自我檢測

Q1. 你在做完一個 feature 後想做 QA。上下文已經很長，但你想在同一個目錄繼續。最佳選擇是？

  • 清空上下文，重新開始
  • 派子代理去做 QA
  • 壓縮後在同一個 session 繼續
  • 繼續留在原 session 不做任何處理

Q2. 你在 Claude Code 裡做完一個功能，想讓 Codex 來 review。這時最適合用？

  • 壓縮（compact）
  • 繼續留在原 session
  • 交接（handoff）
  • 派子代理

Q3. Auto-compaction 最危險的場景是？

  • 在 phase boundary 發生時
  • 在實作中途、命名風格剛建立時
  • 在 QA 階段開始時
  • 在 grilling 結束時
