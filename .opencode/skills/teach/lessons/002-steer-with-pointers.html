Lesson 002 · 跨階段引導

別把整本手冊塞進上下文：Push、Point 與 doc + pointer

Node: steering-across-sessions · Step 2/4

學習目標

能在新的 session 裡穩定傳遞專案慣例與陷阱，並判斷哪些內容該固定放進 agents.md（Push），哪些該放進文件後用 pointer 指向（Point）。

新 Session 裡到底有什麼？

模型不會保留上一輪對話的內在記憶。新的 session 開始時，harness 會重新組一份上下文：

  • 系統提示
  • 可用工具與工具規則
  • 專案層級的引導檔，例如 agents.md
  • 你的當前要求
  • 後續透過工具讀回來的檔案內容與命令結果
檔案「存在」不等於代理「一定會看到」。代理「看到」不等於代理「只在該用時才看到」。真正要設計的是載入時機。

Context Load：上下文不是免費的倉庫

每一段被預先塞進上下文的文字，都會帶來固定成本。這個成本分成兩部分：

傳送與計費成本

每次請求都會把所有固定引導重新送出。Token 成本會累積，請求也會變重。

注意力成本

模型要在更多規則裡判斷什麼跟眼前任務有關。無關文字越多，重要訊號越容易被稀釋。

類比：Push 像是每天出門都把整本工作手冊背在身上，不管今天是否會用到。Point 像是在口袋裡放一張紙條，寫著工作手冊放在哪裡；需要時再把手冊拿出來。

Push：把規則固定推進上下文

Push 就是主動把規則推進模型的起始上下文。最典型的做法是在 repo 裡放一份 agents.md，session 啟動時系統先把這些引導放進去。

什麼適合 Push

適合 Push 的規則有三個特徵：適用範圍非常廣、文字很短、漏掉時風險很高。

# agents.md — 只放這類規則 - 先閱讀相鄰程式碼再編輯 - 不要提交秘密 - 修改後維持可測試 - 只在必要時動用危險指令

什麼不適合 Push

agents.md 的沉積層問題

很多團隊的 agents.md 之所以越長越難用，就是因為每發生一次事故，就往裡面再加一段。久而久之，它變成一份事故沉積層——內容不是沒有價值，而是出現時機錯了。

不適合 Push 的是那種只在特定情境才有用、但內容又很長的程序。當每一條規則都被標成「永遠重要」，代理就很難判斷哪些是當前任務真的 relevant。

Point：只留下路標，需要時再讀全文

Point 是另一種思路。你不把完整流程常駐，而是在固定上下文裡留一個短 pointer，告訴代理：如果碰到某一類任務，請去讀哪一份文件。

# agents.md 裡只留這一句 當修改資料庫 schema 時，先閱讀 docs/database-migrations.md # 完整流程放在 docs/ 裡 # schema → migration → seed.ts → reseed → type-check

好的 Pointer 的條件

  • 觸發條件清楚（例如「修改 schema」而不是「有時候要看資料庫文件」）
  • 文件位置穩定、名稱清楚
  • 文件內容是最新的
  • 文件裡真的有可執行的完整流程
如果 pointer 很模糊，代理只會多一道探索成本。如果 pointer 指向過期文件，情況甚至比沒有 pointer 更糟，因為代理會很有信心地沿著錯誤路線做事。

怎麼判斷 Push 還是 Point？

問題 若答案多半是「是」 較適合
這條規則幾乎每個任務都會用到嗎？ 是 Push
漏掉它會造成高風險錯誤嗎？ 是 Push 或至少要有很強的 pointer
它是不是短到可以常駐而不造成膨脹？ 是 Push
它只在特定任務類型才 relevant？ 否 Point

實戰案例：Schema 變更的隱藏同步線

為什麼只改 schema 還是不夠

假設你的專案有三條同步線要一起成立：

1
schema 檔 — 描述資料表結構
2
SQLite 檔案 — 保存實際資料
3
seed.ts — 建立或重建示範資料

當你新增一個欄位，至少有兩條線要同步：

  • 第一條線：schema 和 migration — 處理「結構有沒有變」
  • 第二條線：seed.ts — 處理「重新初始化後的資料是否跟新結構對得上」

如果只改 schema，migration 可能會讓現有資料庫看起來暫時正常，但只要 seed 流程仍然照舊邏輯建立資料，問題就會浮出來。這是典型的 repo-specific gotcha——不是一般語言知識，而是這個 repo 的工作習慣、工具鏈和流程約定交疊出來的坑。

驗證：兩輪測試

跨 session steering 不能只看文件有沒有寫，還要看代理在對的時機會不會真的讀它。

第一輪：無關任務測試

做一個完全不碰資料庫的 dummy request（例如改一個 UI 文案）。觀察：

  • 固定上下文是不是變輕了
  • 代理是不是沒有被資料庫規則干擾

第二輪：觸發任務測試

給一個明確會碰 schema 的小變更。檢查代理是否：

  • 找到 migration 文件
  • 同步想到 seed.ts
  • 執行重新 seed
  • 做 type-check
  • 最後產出的檔案差異合理
真正要看的證據是檔案 diff、migration 歷史、seed 結果、測試或檢查輸出。Steering 設計的目的是改變代理的實際工作流程，而不是只讓它在回答裡看起來比較懂。

自我檢測

Q1. 以下哪一條規則最適合用 Push？

  • 修改資料庫 schema 時要同步更新 seed.ts
  • 部署前要跑完所有 migration
  • 不要提交秘密到 repo
  • 測試失敗時要先查 log

Q2. 你的 agents.md 有 200 行，其中 150 行是資料庫 migration 流程。你應該？

  • 全部保留，因為都是重要知識
  • 把 migration 流程移到 docs/，agents.md 只留 pointer
  • 全部刪掉，讓代理自己摸索
  • 把 agents.md 改名叫 CLAUDE.md

Q3. 為什麼 pointer 指向過期文件比沒有 pointer 更糟？

  • 代理會有信心地沿著錯誤路線做事
  • 會增加更多的 token 成本
  • 代理會無法找到任何文件
  • 會導致 auto-compaction 觸發
