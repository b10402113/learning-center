Why AWS for web deployment

content-written
解釋前端開發者為什麼需要 AWS——靜態檔案、延遲問題、CDN 概念
Steps（DAG）
  • 學習目標：理解靜態檔案如何從 FTP 伺服器遷移到 S3 雲端儲存，以及前端技能如何直接對接 AWS。

    你的技能已經夠了

    你會寫 HTML、JavaScript、CSS。你用 npm run build 產生 dist/ 資料夾。這些產出——那些 .html、.js、.css 檔案——就是靜態檔案。它們是純文字，不需要編譯器或執行環境就能被瀏覽器讀取。

    問題是：這些檔案現在只存在你的電腦上。要讓全世界的人都能訪問你的網站，你必須把它們放到網路上。

    古老的方式：FTP

    在雲端出現之前，做法很直接：

    1. 租一台伺服器（通常在某个機房）
    2. 用 FTP（檔案傳輸協定）把 build 出來的檔案上傳到那台伺服器
    3. 伺服器收到檔案後，透過 HTTP 把它們 serve 給訪客

    這能運作，但有幾個痛點：

    • 你必須管理伺服器——作業系統更新、安全性修補、流量配置，都是你的事
    • 單點故障——伺服器壞了，網站就掛了
    • 擴展困難——流量暴增時，你得手動升級伺服器規格

    現代的方式：S3

    AWS S3（Simple Storage Service）本質上是一個檔案櫃——你把檔案丟進去，它就幫你保管，並透過 URL 讓任何人都能存取。

    核心概念 S3 Bucket（儲存桶）就像一個超大資料夾。你把 dist/ 裡的所有檔案丟進去，S3 就把它們放到網路上。

    跟 FTP 伺服器相比：

    FTP 伺服器S3
    管理伺服器你要管AWS 管
    擴展手動升級自動
    可靠性單點故障99.999999999% durability
    費用固定月費用多少付多少

    這跟你的工作流程有什麼關係？

    你在本地執行 npm run build，得到一個 dist/ 資料夾。接下來你要做的事情，本質上就是把那個資料夾「搬」到 S3 上。

    # 你的工作流程
npm run build          → 產生 dist/ 資料夾
# 接下來要做的：
aws s3 sync dist/ s3://my-bucket  → 把檔案同步到 S3

    就是這麼簡單。你的前端技能——寫出好的 HTML/JS/CSS——就是你需要的一切。AWS 只是提供了一個更好的「放檔案的地方」。

    面試要點 「S3 是一個物件儲存服務。對於靜態網站部署，我把 build 產出的檔案同步到 S3 Bucket，設定為公開讀取，就能透過 S3 的網站端點訪問。不需要管理伺服器。」
    Sources: sources/aws-v3/01#introduction
  • 學習目標：理解距離造成的延遲問題，以及 CDN 如何透過全球分散解決它。

    一個物理學問題

    假設你的 S3 Bucket 在美東（維吉尼亞）。當一個在台北的使用者打開你的網站：

    1. 瀏覽器送出請求，穿越太平洋到達美東
    2. S3 回傳檔案
    3. 檔案再穿越太平洋回到台北

    光速是有限的。這個來回的物理距離就是延遲的根源。不管你伺服器多快，光跑一趟太平洋就需要約 150 毫秒。

    關鍵數字 人類感知的延遲門檻大約是 100ms——超過這個數字，使用者會明顯感覺「慢」。一個從美東到台北的來回請求，光傳輸延遲就可能接近這個門檻。

    不只是傳輸

    真實情境更複雜。除了物理距離，延遲還來自：

    • DNS 解析——把網域名稱轉成 IP 位址
    • TCP 握手——建立連線
    • TLS 握手——建立加密連線（HTTPS）
    • 伺服器處理——S3 找到檔案、準備回應

    每一個步驟都加上幾十毫秒。加起來，一個從亞洲訪問美東伺服器的請求，總延遲很容易超過 300ms。

    解決方案：把內容搬到使用者身邊

    如果伺服器在台北，延遲就低了。但你的使用者分佈在全球——不可能在每個城市都放一台伺服器。

    CDN（Content Delivery Network，內容傳遞網路）的做法是：

    1. 在全球各地部署伺服器節點（叫做 Edge Location）
    2. 把你的檔案複製到這些節點上
    3. 當使用者請求檔案時，CDN 從離他最近的節點回傳
    核心概念 CDN 本質上是一個全球分佈的檔案複製系統。它把你的內容從一個地點，變成在全球數十個地點都有副本。使用者永遠從最近的副本取檔案。

    這跟你用過的東西有什麼關係？

    你已經用過 CDN 了——只是不知道而已。當你執行 npm install 或 pip install 時，套件下載幾乎是瞬間完成，不管你在哪裡。那是因為 npm 和 PyPI 的套件檔案被放在全球 CDN 上。

    Vercel 和 Netlify 本質上也是 CDN——你 push 程式碼，它們 build 完就把靜態檔案放到全球邊緣節點。你這次要做的，是直接用 AWS 的 S3 + CloudFront 來實現同樣的效果。

    面試要點 「CDN 解決的是地理延遲問題。它在全球部署邊緣節點，把靜態內容複製到離使用者最近的位置，降低傳輸延遲。AWS 的 CloudFront 就是 CDN 服務。」
    Sources: sources/aws-v3/01#the-physics-problem
  • 學習目標：瀏覽 AWS 服務全景，聚焦到 S3 + CloudFront 這條部署路徑。

    AWS 有多大？

    打開 AWS Console 首頁，你會看到一整頁的服務——計算、儲存、資料庫、機器學習、IoT、安全……數十個類別，每類下面還有更多。這很容易讓人不知所措。

    但你不需要學全部。你要做的靜態網站部署，只需要其中兩個服務：

    • S3——放檔案
    • CloudFront——把檔案複製到全球

    S3：你的檔案櫃

    上一步我們已經介紹過 S3。它負責：

    • 儲存你的靜態檔案（HTML、JS、CSS、圖片）
    • 提供一個 URL 讓人存取
    • 處理存取控制（誰能看、誰不能看）

    CloudFront：你的全球快遞網路

    CloudFront 是 AWS 的 CDN 服務。它做的事情就是上一步介紹的 CDN 概念：

    1. 從你的 S3 Bucket 拉取檔案
    2. 把檔案複製到全球數十個 Edge Location
    3. 使用者請求時，從最近的 Edge Location 回傳
    核心組合 S3 + CloudFront 是 AWS 上靜態網站部署的黃金組合。S3 負責存儲，CloudFront 負責全球分發。兩者分開也能用，但組合起來才是完整方案。

    其他服務？先不管它們

    服務用途你需要嗎？
    EC2虛擬伺服器目前不需要
    Lambda無伺服器函數目前不需要
    RDS關聯式資料庫目前不需要
    Route 53DNS 管理之後會用
    ACM免費 SSL 憑證之後會用
    IAM權限管理之後會用

    你現在只需要專注在 S3 + CloudFront。其他服務會在需要時自然出現。

    你的部署路徑

    npm run build                     → 產生 dist/ 資料夾
aws s3 sync dist/ s3://my-bucket  → 檔案進 S3
CloudFront 拉取 S3 內容           → 全球邊緣節點都有了
使用者從最近的 Edge Location 取檔案  → 低延遲存取

    這就是你要學會的整條路線。接下來的課程會一步步帶你走過每個環節。

    面試要點 「AWS 的靜態網站部署路徑是 S3 + CloudFront。S3 負責物件儲存，CloudFront 負責 CDN 分發。搭配 Route 53 做 DNS、ACM 提供免費憑證，就能實現一個完整的、帶有 HTTPS 和自訂網域的靜態網站。」
    Sources: sources/aws-v3/06#aws-ecosystem, sources/aws-v3/06#service-overview, sources/aws-v3/01#workshop-format

AWS account and IAM

content-written
建立一個安全的 AWS 帳號，設定 admin user 並理解 IAM 的角色
Steps（DAG）
  • 學習目標：完成 AWS 帳號註冊，並理解 root user 為什麼是全帳號最大的安全隱患。

    為什麼要先有帳號？

    部署任何 AWS 服務之前，你必須先有一個帳號。帳號一建立就會產生一個 root user——它擁有所有資源的完整權限，包括帳單。

    這一步聽起來很瑣碎，但它是所有後續工作的前提。好消息是：帳號建立是整個課程中最麻煩的一步，之後每一步都會越來越簡單。

    核心概念 註冊過程需要：email、密碼、聯絡資訊、信用卡、身份驗證。大概 10-15 分鐘。撐過去就贏了。

    註冊步驟

    1. 前往 aws.amazon.com，點擊「Sign In to the Console」
    2. 選擇「Create a new AWS account」
    3. 輸入 root user 的 email 和密碼（這就是你的 root 憑證）
    4. 填寫聯絡資訊（個人或公司皆可）
    5. 輸入信用卡資訊（用於身份驗證和未來計費）
    6. 完成身份驗證（可能需要電話驗證）
    7. 選擇支援方案（選「Basic support — 免費」即可）

    Root User 的安全風險

    ⚠️ Root User 是全帳號最大的安全隱患 root user 擁有不受限制的存取權限——所有 AWS 資源、所有帳單設定、所有 IAM 操作。一旦被盜用，攻擊者可以立刻啟動高價運算資源（例如比特幣挖礦），而帳單是你的。

    這不是假設性的風險。 AWS 帳號被盜用後被用來挖礦的案例屢見不鮮。信用卡直接暴露在風險中。

    核心原則 完成帳號建立後，你就不应该再用 root user 做日常操作。建立一個 IAM 管理員帳號來取代它——這正是下一個 lesson 要做的事。

    類比

    Root user 就像一棟大樓的總钥匙。它能打開每一扇門、修改保全系統、甚至更改大樓所有者。你不會帶著總钥匙去買午餐——同理，你不會用 root user 去開 EC2 實例。

    註冊完成後的清單

    • 記下你的 AWS Account ID（12 位數字）
    • 記下你註冊用的 root email
    • 登入一次 Console，確認帳號正常運作
    • 關掉 Console——不要再用 root 登入了
    Sources: sources/aws-v3/02#account-creation, sources/aws-v3/02#security-stakes
  • 學習目標：理解 IAM 的身份驗證與授權機制，讀懂一份 IAM policy 的 JSON 結構，並說出最小權限原則的實作意義。

    IAM 是什麼？

    IAM（Identity and Access Management）是 AWS 的中央門禁系統。它回答兩個問題：

    問題說明
    你是誰？身份驗證（Authentication）—— 確認使用者的身分。root user、IAM 使用者、API Key 都是身份。
    你能做什麼？授權（Authorization）—— 決定這個身份能執行哪些操作、存取哪些資源。由 policy 定義。

    每一個 AWS 請求都會經過 IAM。你在 Console 按一個按鈕、用 CLI 執行一個指令、用 SDK 呼叫一個 API——全部都要先通過 IAM 的檢查。它是最底層的基礎設施，也是你最重要的安全防線。

    類比：IAM 就像一棟辦公大樓的門禁系統。身份驗證是你刷的那張感應卡（確認你是誰），授權是你卡片上的權限等級（能進哪些樓層、哪些房間）。Policy 就是那張卡片上寫的權限清單。

    IAM 的核心實體

    實體說明
    User一個長期存在的身份，對應到一個人或一個服務。有登入憑證（密碼、Access Key）。
    Group一群使用者的集合。把 policy 掛在 Group 上，裡面所有人都自動繼承那些權限。
    Role臨時身份，給 AWS 服務或外部程式用。不長期持有憑證，用 STS 拿臨時 Token。

    Policy：權限的 JSON 語言

    Policy 是一份 JSON 文件，定義了「允許或拒絕」哪些操作（Action）作用在哪些資源（Resource）上。

    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::my-portfolio-bucket/*"
    }
  ]
}
    • Version — policy 語言版本，固定寫 2012-10-17
    • Statement — 一組規則的陣列，可以有多條
    • Effect — Allow 或 Deny（只能二選一）
    • Action — 允許的 API 操作，格式是 服務:操作
    • Resource — 操作的目標，用 ARN（Amazon Resource Name）指定
    核心概念 deny 永遠優先。如果有一條 deny 規則和一條 allow 規則同時存在，deny 會贏。這讓你可以建立一道安全網，即使其他 policy 允許了不該發生的操作。

    最小權限原則

    最小權限原則（Least Privilege）說的是：給每一個使用者或服務恰好足夠的權限，不要多給。

    ✅ 正確做法 一個 CI/CD 部署機器人只需要 s3:PutObject 來把靜態檔案放進一個特定的 bucket。它不需要讀 DynamoDB、不需要開 EC2、不需要管理 IAM。所以你只給它那一條權限。
    ⚠️ 常見錯誤 因為「怕以後會用到」，就給所有使用者 AdministratorAccess。這樣一來，只要任何一個帳號被盜用，攻擊者就擁有整個帳號的完整控制權——包括刪除你的資料、開高價實例、修改帳單設定。
    Sources: sources/aws-v3/05#iam-concept, sources/aws-v3/05#least-privilege, sources/aws-v3/05#policies
  • 學習目標：在 AWS Console 建立一個帶有 AdministratorAccess 權限的 IAM 群組，建立一個日常使用的 IAM 使用者，並設定帳號別名讓登入更方便。

    為什麼需要一個日常帳號？

    在前兩個 lesson 裡，你已經建立了一個 AWS 帳號並理解了 IAM 的核心概念。現在是時候把它們串起來：建立一個你每天登入用的 IAM 使用者，而不是繼續用 root user。

    核心概念 完成這個 lesson 之後，你會有一個安全的日常登入帳號。你不再需要碰 root——root 只留著應付帳號層級的 emergencies（例如更改帳單資訊、刪除整個帳號）。

    建立步驟

    第一步：建立 IAM 群組

    1. 用 root user 登入 AWS Console
    2. 搜尋「IAM」並進入 IAM Dashboard
    3. 左側選單點「Groups」→「Create group」
    4. 群組名稱輸入 Admins（或你喜歡的名字）
    5. 在權限設定中搜尋 AdministratorAccess，勾選這條 AWS Managed Policy
    6. 點「Create group」完成
    ✅ 為什麼用 AdministratorAccess？ 這條 policy 給了幾乎所有權限——就像「城堡的幾乎所有鑰匙」。它讓你在後續課程中能自由地操作任何 AWS 服務。root user 始終保留 revoke 這些權限的能力，所以安全網還在。

    第二步：建立 IAM 使用者

    1. 在 IAM Dashboard 點「Users」→「Create user」
    2. 使用者名稱輸入 daily-admin（或你喜歡的名字）
    3. 勾選「Provide user access to the AWS Management Console」
    4. 選擇「I want to create an IAM user」
    5. 設定一個強密碼
    6. 在「Set permissions」步驟，選擇「Add user to group」
    7. 勾選你剛建立的 Admins 群組
    8. 點「Create user」完成

    第三步：測試日常帳號

    1. 登出 root user
    2. 用 daily-admin 的使用者名稱和密碼登入 Console
    3. 確認你能正常存取 IAM、S3 等服務
    4. 在 IAM Dashboard 確認你的身份是 daily-admin，不是 root

    第四步：設定帳號別名

    1. 以 daily-admin 登入 Console
    2. 進入 IAM Dashboard
    3. 在「IAM-dashboard sign-in link」區域點「Customize」
    4. 輸入一個全球唯一的別名（例如 andy-portfolio）
    5. 儲存

    設定完成後，你的登入 URL 變成：

    https://andy-portfolio.signin.aws.amazon.com/console

    類比：帳號別名就像你的辦公室門牌號。本來是「123456789012」（帳號 ID），現在是「Andy 的工作室」。別人要來拜訪你，不用記那串數字，只要記你的名字就好。

    完成後的狀態

    • root user — 收好，不再日常使用。只用於帳號層級的紧急操作。
    • daily-admin — 你的日常登入帳號，有 AdministratorAccess 權限。
    • Admins 群組 — 你未來可以繼續往裡面加使用者。
    • 帳號別名 — 方便記憶的登入 URL。
    Sources: sources/aws-v3/03#user-groups, sources/aws-v3/03#administratoraccess-policy, sources/aws-v3/04#account-alias
