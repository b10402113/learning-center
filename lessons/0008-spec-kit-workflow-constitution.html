Spec-Kit 工作流與七條憲法

本課目標：掌握 Spec-Kit 驅動的 AI 編程全流程，理解七條憲法原則和九模塊技術架構，能畫出五個 user story 的依賴 DAG。

雙階段混合策略

讓 AI 從零構建九模塊的項目，最大的風險是「vibe coding」失控。AI 寫著寫著就脫離需求文檔，自己編出和方案對不上的結構。Spec-Kit 就是為了治這個病。

整體策略分兩階段：

主構建：constitution → specify → plan → tasks → implement （九模塊 greenfield，跑完整 Spec-Kit 流程） 增量階段：手動提示詞 + Claude Code （1–3 個文件的改動，切換成直接跟 AI 說）

邊界很乾淨：大粒度 greenfield 用 Spec-Kit，小增量用手動提示詞。工具選擇跟工作性質匹配。

七條憲法原則

憲法寫一次，AI 永不改。原則錯了就停下來重新討論。七條從需求文檔第三章和技術方案第一節提煉：

  1. JDK 21 + Spring Boot 3.x 單體、Maven 九模塊、單個二進制
  2. 五項能力優先，治理層留擴展
  3. 自研 ReAct 循環，不用 Spring AI 的 Agent 抽象
  4. Spring AI 只用一半：Provider 抽象/協議轉換/@Tool schema 生成，自動工具執行禁用，調度交給 ReActLoop + ToolExecutor
  5. Plugin Tool 三級，SKILL.md + MCP 零代碼優先
  6. SQLite + MEMORY.md 在核心，向量檢索留擴展，審計表第一天就寫
  7. 每個 user story 以 demo 收尾，優先跑通不追求完美
最容易寫錯的兩條 第四條：忘了關 Spring AI 自動工具執行 → 工具被調用兩次，副作用和成本雙倍。第六條：漏寫審計表以為日誌就夠 → 回頭補要解析日誌，又貴又容易漏。

九模塊技術架構

一句話總結：JDK 21 + Spring Boot 3.x + Spring AI Alibaba + 自研 ReAct 循環 + SQLite + Picocli，打成一個可執行的 JAR。一個檔案，裝上就跑。

架構是「一引擎、兩入口、三能力」：兩個入口（CLI + Web），收進一個引擎（ReAct 循環），引擎調度三個能力（Provider、Memory、Tool），底下是存儲層。

oryxos-core
大腦。ReAct 循環、PromptBuilder、ToolExecutor、Session、Profile、OryxTool 抽象
oryxos-provider
翻譯官。對接各家模型，Function Calling 適配，名稱映射
oryxos-memory
記憶管家。MemoryService 門面、長期記憶、記憶工具
oryxos-tool
工具箱。內建工具、MCP Client、工具註冊表、沙箱
oryxos-web
Web 門面。伺服器、六個控制器、OpenAPI
oryxos-channel-cli
命令行入口
oryxos-storage
資料庫。SQLite 三張表（含審計）
oryxos-cli
Picocli 的 12 個子命令

第九模塊 oryxos-boot 是 Spring Boot 啟動器，負責打 fat JAR

五個 User Story 的依賴 DAG

US-1 對接 LLM → US-2 ReAct 循環 → US-3 Memory ‖ US-4 Plugin Tool → US-5 Web Service

US-5 放最後是依賴關係決定的，不是它不重要——Web Service 反而是關鍵差異化。每個 story 結束後跑 /speckit.analyze（官方防漂移命令），檢查 constitution/spec/plan/tasks/code 的一致性。

為什麼自研 ReAct 而不用 Spring AI？

Spring AI 的 Agent 抽象是個黑盒子。你把工具丟進去，它自己決定什麼時候調、調幾次。但你想完全掌控 Agent 的思考過程——每一步怎麼想、什麼時候決定用工具、用了之後怎麼反饋——你就管不了。

所以 ReAct 循環自己寫。Spring AI 只負責協議轉換（把不同模型的 API 格式抹平）和 schema 生成。這些瑣碎的活兒，自己寫太累了，交給它正好。但「要不要用工具」這個決定，只能由我們自己的 ReAct 循環來做。
