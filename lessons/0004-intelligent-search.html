智慧搜尋：MCP + Grounding + 兩段式時間戳

本課目標：能畫出搜尋請求從瀏覽器到 MCP 再回到 UI 的完整流程，說清「模型只選 ID、Sanity 供事實」的 grounding 原理，並理解 chapters-first 時間戳解析的兩階段機制。

搜尋功能最大的風險：不是「找不到」，而是「編造」

Vertex 的招牌功能是智慧搜尋——學習者輸入自然語言，平台從影片逐字稿中找出精確到秒級的片段。但搜尋功能最大的風險不是「找不到」，而是「編造」。

大型語言模型（LLM）在生成回應時，有能力自行組合看似合理的課程名稱、價格、時長、甚至時間戳——但這些資訊可能根本不存在於 Sanity 資料庫中。如果讓模型直接根據自己的「記憶」回答，使用者會得到完全虛構的搜尋結果。

核心風險 幻覺（hallucination）是 LLM 的內建傾向，不是偶爾發生的邊緣案例。它被訓練來生成「合理的」文本，而非「真實的」資料。搜尋功能的可信度完全建立在「結果不可能造假」這件事上。

（AGENTS.md #7：「Search is grounded. Say only what the data returns. Never invent a course, lesson, price, duration, or timestamp.」）

架構：瀏覽器永遠不直接呼叫 MCP 或 LLM

搜尋請求的完整流動路徑，和你在 Clerk node 學到的 server-client 邊界完全一致：

Browser (search UI)
    ↓ POST /api/search  { query: "如何快取資料" }
Server Route (Next.js)
    ↓ 連接 Sanity Context MCP
    ↓ 注入 schema + system prompt
    ↓ 呼叫 LLM（OpenAI）
    ↓ LLM 透過 MCP 工具寫 GROQ 查詢
    ↓ Sanity 執行查詢，回傳結果
    ↓ LLM 只返回 lesson IDs + 評分
    ↓ Server 用 IDs 查 Sanity 取得完整資料
    ↓ 結構化結果串流回 Browser
Browser (search UI)
    ↓ 渲染結果卡片（video result + lesson result）
關鍵規則 瀏覽器永遠不直接呼叫 MCP、LLM 或任何私有 API。 搜尋查詢先送到 Next.js 的 server route，再由 server route 連接 MCP。瀏覽器只做渲染，敏感操作全在 server 端。

Grounding：模型只選 ID，Sanity 供事實

Grounding 是確保搜尋結果不可能造假的核心機制：

Grounding 原理 模型不負責「知道」課程內容，模型只負責「選擇」哪個 ID 應該出現在結果中；Sanity 則負責「供應」所有的事實細節。

具體流程

  1. LLM 透過 MCP 工具寫 GROQ 查詢——它知道 Sanity 的 schema，能寫出正確的 GROQ 查詢語句。
  2. Sanity 執行查詢——回傳匹配的文件。
  3. LLM 只返回 lesson IDs——加上評分（relevance score），但不生成任何內容細節。
  4. Server 用 IDs 查 Sanity 取得完整資料——透過 lesson by ids 查詢，取得標題、描述、縮圖、模組標籤等所有展示欄位。
  5. 結果卡片的每一個欄位都來自 Sanity——模型從未生成這些內容。
欄位來源模型有沒有生成？
課程名稱Sanity 查詢否
模組標籤Sanity 查詢（從 array order 推導）否
縮圖 URLSanity 查詢否
時間戳影片文件的 chapter 或 chunk否
Relevance score模型生成是

（影片原話：「It made grounding structural as the model returns only lesson ids and every displayed field is read back from sanity via a new lesson by ids query with the 5.1 label derived from the array order.」）

影片文件是內部查表，不是獨立實體

影片文件（video document）在 Sanity 中是獨立的文件，包含章節列表和逐字稿區塊，但它永遠不會直接出現在搜尋結果中。搜尋結果中的「影片結果」實際上是「使用了某個影片的課程」的引用。影片文件的 id 是內部鍵，用於連結課程與影片內容，但對外展示時永遠透過課程呈現。

兩段式時間戳解析：Chapters-First, Transcript Fallback

當搜尋匹配到影片中的某個時間點時，系統需要決定如何展示。時間戳不是直接從逐字稿來的——它有兩階段機制：

階段匹配什麼結果
第一階段：Chapters 影片文件的章節列表（{ startSeconds, label }） 乾淨的章節標籤（如 "Caching Overview"）
第二階段：Transcript 逐字稿區塊（{ startSeconds, text }） 較嘈雜的內容描述（章節的後備方案）
為什麼 chapters-first？ 章節標籤是作者或 YouTube 自動產生的結構化資料，品質高、噪音低。逐字稿是語音辨識的結果，可能有錯字、贅詞、斷句不清。所以先匹配章節（高品質），匹配不到才用逐字稿（低品質但覆蓋率高）。

Transcript chunks 的設計

逐字稿不是整段儲存的。每部影片的逐字稿被切成短區塊（chunks），每個 chunk 約 45 秒、約 350 個字元，從不中斷句子。每個 chunk 都有自己的 startSeconds，確保每個時間點都是一個可搜尋的、可 seek 的真實時刻。

（影片原話：「Chunks are about 45 seconds each with about 350 characters. Never split mid Q. So every start seconds is a real seekable moment.」）

為什麼不能把整個逐字稿丟給模型？

陷阱 Never return a whole transcript or chunks array to the model. It overflows the context window. Vertex 有 120 部影片、4,000+ 個 chunks。把全部逐字稿丟給模型會超出 context window，而且大多數內容與查詢無關。所以只 fetch filtered matches，每部影片只取幾個 chunks。

搜尋設定：Config-as-Content

搜尋的行為不是寫死在程式碼中的，而是由 Sanity 中的一個 Context 文件（Context document）控制。這個文件包含：

  • Content scope filter——限制 AI 只能看到 content 類型（course、lesson、video），看不到 progress、config 等敏感資料。
  • Query instructions——搜尋行為的指令差異（deltas），例如「不要編造」、「wildcard 匹配」、「chapters-first」。

編輯 Context 文件後，下一次搜尋請求就會使用新的配置。但修改內聯系統提示（inline system prompt）則需要重新啟動伺服器。

關鍵規則的雙重寫入 有些搜尋規則太重要了，不能只寫在一個地方。例如「不要編造課程」這條規則，同時寫在 Context 文件和內聯系統提示中。這是因為模型更傾向於遵循內聯系統提示中的指令，但 Context 文件是動態可調的。將關鍵規則寫在兩處，確保底線規則始終被執行。

Search UI：全頁結果，不是聊天框

搜尋結果是一個完整的結果頁面，不是 compact widget，不是 chatbox：

Lesson result 課程名稱、模組標籤、key points、描述 導航到 lesson page

文本匹配規則

搜尋使用 token-based 匹配，不是整句匹配：

  • Wildcard 匹配——使用者輸入「快取」，匹配包含「快取」的所有文件。
  • OR 多詞匹配——使用者輸入「React 框架」，同時匹配包含「React」或「框架」的文件。
  • 不匹配整句——使用者輸入「React 框架的效能優化」，不會只匹配包含完整這個詞組的文件。
  • Portable Text 透過純文本投影匹配——富文本內容先轉成純文本再匹配。
