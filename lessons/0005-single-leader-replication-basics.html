單一領導者複製：Leader-Follower 的角色分工

本課目標：畫出「client → leader → follower」的完整寫入與讀取流程圖，並說出三個使用複製的理由。

為什麼需要複製？

你有一個 PostgreSQL 資料庫跑在一台機器上。某天硬碟壞了。資料全沒了。

這不是假設性的風險。Martin Kleppmann 在 Designing Data-Intensive Applications 中列出了複製的三個理由：

  1. 提高可用性（Availability）— 如果一個 node 掛了，另一個可以接手服務
  2. 降低延遲（Latency）— 讓使用者就近讀取最近的副本，而不是每次都跨洲連線
  3. 擴大讀取吞吐量（Read Throughput）— 多個副本分擔讀取壓力

注意：這三個理由都跟讀取有關。寫入的情況完全不同——稍後會看到。

基本架構：誰負責什麼？

單一領導者複製的核心想法極其簡單：

┌──────────┐ │ Client │ └────┬─────┘ │ │ ① 寫入 ▼ ┌──────────────┐ │ Leader │ ← 唯一接受寫入的 node └──┬────┬───┬───┘ │ │ │ │ │ │ ② 複製變更日誌 ▼ ▼ ▼ ┌─────┐┌─────┐┌─────┐ │Foll ││Foll ││Foll │ ← 只接受複製，不接受寫入 │ ow1 ││ ow2 ││ ow3 │ └─────┘└─────┘└─────┘

三個角色：

Leader（领导者）

  • 接受所有寫入請求
  • 將變更寫入本地儲存
  • 將變更日誌推送到所有 follower

Follower（追隨者）

  • 只接受來自 leader 的複製資料
  • 保持與 leader 相同的資料副本
  • 可以（但不一定）接受讀取請求

這個模式也叫 leader-follower、master-slave、primary-backup。名字不同，機制相同。DBA 現在傾向用 leader-follower，因為 master-slave 有歷史包袱。

寫入流程：一步步拆解

當 client 發出一個 INSERT 或 UPDATE 指令時：

  1. Client 連到 leader（不是 follower）
  2. Leader 將變更寫入本地的寫入日誌（write-ahead log, WAL）
  3. Leader 將日誌條目推送到所有 follower
  4. 每個 follower 收到日誌後，按照相同順序套用自己的本地副本

關鍵：寫入順序在所有 node 上完全一致。這確保了即使各 node 的處理速度不同，最終狀態也會收斂到相同結果。這跟「亂序寫入會造成不一致」是同一種防護模式——你之前在 design-system node 學到的「規則限制自由度」，在這裡變成了「順序限制一致性」。

常見誤解 Follower 不是「備份」。備份是離線的、低頻的、用來災難恢復的。Follower 是即時的、持續複製的、可以立即接管服務的。備份可以在任何時候取回；follower 如果 lag 太久，可能已經丟失了資料。

讀取流程：不一定只能從 Leader 讀

這裡有一個反直覺的選擇：

方案 A：只從 Leader 讀

  • 保證讀取到最新的資料
  • 但所有讀取壓力集中在 leader
  • 適合寫多讀少的場景

方案 B：從 Follower 讀

  • 讀取壓力分散到多個 node
  • 但可能讀到過時的資料（replication lag）
  • 適合讀多寫少的場景

大多數系統選擇方案 B，但需要處理 lag 帶來的問題。這就是 replication lag 的核心矛盾：你想要低延遲（就近讀取），但低延遲可能犧牲了一致性（讀到舊資料）。

實務連結 PostgreSQL 的 streaming replication 就是這個模型。Promotion of a standby 是 failover 的核心操作——standby 就是 follower，被 promote 後變成新的 leader。你可以在 PostgreSQL 官方文件 中對照本課的概念。

Quiz

總結

  • 複製的三個理由：可用性、延遲、吞吐量——全部跟讀取有關
  • Leader 負責所有寫入， follower 只做複製
  • 寫入順序在所有 node 上一致，確保最終收斂
  • 從 follower 讀取可以分散壓力，但要處理 replication lag
