Clerk 認證與安全邊界

本課目標：能接上 Clerk（sign-in/up、middleware）並說清「middleware 是 auth resolver 不是閘門」，以及 token 的 public/secret 分割與 server-only 邊界。

Step 1：安裝 Clerk、接上 Next.js、產生認證 UI

為什麼要接認證系統？

Vertex 是一個學習平台——學習者需要登入才能追蹤進度、保存「我的學習」清單。但認證系統是全端應用最複雜的子系統之一：session 管理、密碼流程、OAuth 第三方登入、Email 驗證、JWT 簽發與驗證、middleware 整合、路由保護、使用者檔案管理——全部從零實作，至少三週。

選擇 Clerk 的核心邏輯是：auth 是一個巨大的 surface area，把時間花在產品上而不是認證基礎設施上。免費方案支援最多 50,000 月活用戶，對原型和早期產品綽綽有餘。更關鍵的是，Clerk 的身份系統可以串接後續功能——例如用 Clerk user id 作為學習進度（progress）的 key。

但接上 Clerk 只是起點。你可能覺得「CLI 幫我生成了，我就不用管了」——在 agentic 工作流中，這是一個危險的心態。AI 代理也可能幫你生成 Clerk 整合的代碼，如果你不知道 middleware 在做什麼、環境變數怎麼分配，你就無法判斷 AI 是否做出了錯誤的決定。

Step 2：Middleware 是 Auth Resolver，不是閘門

一個反直覺的現象

你已經安裝了 Clerk，middleware 也接上了。現在你打開瀏覽器，訪問 Vertex 的首頁——它正常顯示，任何人都能瀏覽。課程總覽頁、課程詳情頁，全部都是公開的。但如果 middleware「保護路由」，為什麼這些頁面沒有被擋住？

關鍵概念 Middleware 是 auth resolver，不是 auth gate。 它「解析」認證狀態——讀取 session cookie、驗證 JWT、執行 handshake——然後把解析後的狀態附加到請求物件上。但它不阻擋任何路由。

Resolver vs Gate：兩種完全不同的心智模型

模型行為預設
Gate（閘門） 每個請求到達時檢查身份，有身份才放行，沒身份就擋住 所有路由預設受保護，必須逐一開放
Resolver（解析器） 解析認證狀態，附加到請求上，不阻擋路由 所有路由預設公開，保護是顯式的

為什麼 Vertex 用 Resolver 模型？ 因為 Vertex 是以內容消費為主的學習平台。首頁、課程總覽、課程頁都是公開的——學習者不需要登入就能瀏覽。只有「我的學習」和「進度追蹤」才需要登入。如果 middleware 是 gate，你要嘛全部放行（受保護頁面裸奔），要嘛全部攔截（公開頁面看不到）。Resolver 模型讓你做到「精準保護」。

Middleware 的真實執行流程

當一個 HTTP 請求到達 Next.js 時，middleware 的執行流程是：

  1. 讀取 session cookie — 瀏覽器在每個 HTTP 請求裡自動附上 cookie，Clerk 從中取出 session token。
  2. 驗證 JWT — 檢查 token 是否有效：未過期、簽章正確、屬於同一個 Clerk 應用。
  3. 執行 handshake — 如果 token 缺失、過期、或來自不同實例，Clerk 自動重新驗證身份。這就是為什麼你重新開啟頁面時有時候會「自動登入」。
  4. 附加 auth state — 把解析後的認證狀態（auth() 回傳值）附加到請求物件上，供後續 server component 或 route handler 使用。

關鍵：middleware 不會在任何路由上回傳 401 或 302。 它只是把認證狀態「解析」出來，附加到請求上。就像一個接待處——幫每個客人登記身份，但不會擋人。

Next.js 16 的 proxy 重命名

Next.js 16 把 middleware.ts 重新命名為 proxy.ts。這不是功能改變，而是語義更準確。傳統 middleware 定義是「攔截並修改請求」——但在 Next.js 裡，middleware 做的是「解析認證狀態並附加到請求」。proxy 的語義更接近它的實際行為。

什麼時候才需要保護路由？

在 resolver 模式下，路由保護是顯式的——你必須在特定路由上標記「這裡需要登入」：

路由保護狀態原因
/（首頁）公開學習者的第一印象
/courses（課程總覽）公開內容消費是核心
/courses/[slug]（課程詳情）公開銷售/展示頁面
/my-learning（我的學習）需要登入個人化頁面
/api/progress（進度 API）需要登入寫入操作必須驗證身份
AGENTS.md 的規則 「browsing stays public per AGENTS.md, and routes are gated only when a feature marks them protected」——這不是偏好，而是架構決策。AI 代理容易犯的錯誤就是在 middleware 裡加上「未登入就重導向」，導致所有頁面都變成必須登入才能看。

Step 3：Token 安全邊界與 Server-Only Auth State

一張表看懂所有金鑰

你的 .env.local 裡有一堆環境變數——它們看起來都是字串，但安全性完全不同。判斷原則：一個金鑰如果「只能做事、不能被拿來做別的事」，它就是 client-safe 的；如果「能做有副作用的操作」，它就絕對不能出現在瀏覽器端。

金鑰類型Client-safe？原因
Clerk publishable key是只能初始化 Clerk SDK，不能讀寫資料
PostHog public key是只能發送追蹤事件，不能讀取分析資料
Clerk secret key否能管理使用者、存取 session、執行管理操作
Sanity read token否能讀取私有資料集的完整內容
Sanity write token否能建立、修改、刪除 Sanity 裡的文件
OpenAI API key否能呼叫 AI API，費用由金鑰持有者承擔

NEXT_PUBLIC_ 前綴的機制

Next.js 的 bundler（webpack/Turbopack）在 build 時會：

  1. 掃描所有 process.env.NEXT_PUBLIC_*：把這些值硬編碼進 client bundle 的 JavaScript 裡。
  2. 忽略所有非 NEXT_PUBLIC_ 的環境變數：這些值只在 server 端可用，不會出現在 client bundle 裡。

這意味著：一個環境變數有沒有 NEXT_PUBLIC_ 前綴，直接決定它會不會出現在瀏覽器端。 這不是配置選項，而是 Next.js 的架構邊界。

被動防線的限制 這道防線只在 build 時生效——在 development 模式下，它不會阻止你。所以你不能依賴框架來擋安全問題，你需要在寫代碼時就遵守規則。

Vertex 的環境變數分佈

環境變數前綴出現在用途
NEXT_PUBLIC_CLERK_PUBLISHABLE_KEYNEXT_PUBLIC_Client bundle初始化 Clerk SDK
CLERK_SECRET_KEY無Server onlyClerk 管理操作
NEXT_PUBLIC_SANITY_PROJECT_IDNEXT_PUBLIC_Client bundleSanity 專案識別（非敏感）
SANITY_API_READ_TOKEN無Server only讀取 Sanity 資料集
SANITY_API_WRITE_TOKEN無Server only寫入 Sanity 資料集
OPENAI_API_KEY無Server only呼叫 OpenAI API

Server-Only Auth State：認證狀態的流動路徑

理解了金鑰的 client-safe 分類後，下一步是理解 auth state（認證狀態）本身的流動。在 Next.js App Router 中，auth state 的正確流動路徑是：

Clerk middleware (proxy)
    ↓ 讀取 session cookie，驗證 JWT
    ↓ 附加 auth state 到請求物件
Server Component / Route Handler
    ↓ 呼叫 auth()，取得 userId 和 session
    ↓ 在 server 端使用（查詢資料、驗證權限）
    ↓ 把需要的結果作為 props 傳給 client component
Client Component
    ↓ 只接收渲染所需的資料（例如使用者名稱、頭像 URL）
    ↓ 不持有 token、不持有 userId（除非是公開資訊）
關鍵規則 auth state 從 server 流向 client 的唯一管道是 props。 Client component 從 server component 接收資料，但它拿不到 token 本身——token 始終留在 server 端。

三道防線

防線角色時機
AGENTS.md 的規則預防AI 代理實作前讀取
npm run build 的被動防線檢測build 時檢查 client bundle 裡有沒有不該出現的 env
CodeRabbit 的 PR 審查兜底合併前掃描 secret key 洩漏

三道防線缺一不可——第一道是預防，第二道是檢測，第三道是兜底。
